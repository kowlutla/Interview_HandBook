# 043. Security and Authorization Masterclass

## Overview
Comprehensive security architecture involves safeguarding distributed systems, APIs, data stores, and cloud infrastructure against sophisticated threat vectors through defense-in-depth principles, robust authentication protocols, fine-grained authorization models, and end-to-end encryption.

---

## 1. Authentication (AuthN) Protocols & Standards

Authentication answers the question: *"Who is this entity?"*

### OAuth 2.0 & OpenID Connect (OIDC)
- **OAuth 2.0**: An authorization framework that enables third-party applications to obtain limited access to an HTTP service. It introduces access tokens and refresh tokens.
- **OpenID Connect (OIDC)**: An identity layer built on top of OAuth 2.0 that standardizes authentication via ID tokens (JWTs) containing verified user identity claims.

### JSON Web Tokens (JWT) vs. Stateful Sessions
- **JWT (Stateless)**: Cryptographically signed tokens containing claims. Enables decentralized verification without database lookups.
  - *Pitfall*: Revocation is difficult before expiration unless tracked in a token blacklist (Redis).
- **Stateful Session Tokens**: Random session ID stored in HTTP-only, Secure cookies pointing to server-side session stores (Redis/Memcached).
  - *Advantage*: Instant revocation and fine-grained session control.

## 2. Authorization (AuthZ) Models

Authorization answers the question: *"What is this entity allowed to do?"*

### Role-Based Access Control (RBAC)
- Users are assigned roles (e.g., `Admin`, `Editor`, `Viewer`), and roles are granted permissions.
- **Limitation**: Suffers from role explosion in complex enterprise environments.

### Attribute-Based Access Control (ABAC)
- Access decisions are evaluated dynamically based on attributes (user attributes, resource attributes, environmental context such as time of day, IP address, risk score).
- **Example**: "A user can view a medical record if `user.department == record.department` AND `request.ip in internal_subnet`."

### Relationship-Based Access Control (ReBAC) & Zanzibar
- Modeled as a graph of relationships (e.g., User $U$ is an editor of Folder $F$, Folder $F$ is contained in Organization $O$).
- **Google Zanzibar**: Industry standard for global-scale consistent authorization, utilizing distributed tuple storage and DAG traversal for access checks.

## 3. Cryptography & Data Protection

### Encryption At Rest
- Securing stored data on block storage, databases, and backups using symmetric encryption algorithms (AES-256).
- **Key Management Services (KMS)**: Utilizing hierarchical key architecture (Master Key -> Data Key) with automatic key rotation and hardware security modules (HSM).

### Encryption In Transit
- Securing network communication using TLS 1.3.
- **Mutual TLS (mTLS)**: Both client and server authenticate each other using X.509 certificates, foundational for Zero Trust service meshes (Istio, Linkerd).

---

## 4. Zero Trust Architecture (ZTA)
The core tenet of ZTA is **"Never Trust, Always Verify."**
- **Implicit Trust Zones Eliminated**: Every request, whether inside or outside the corporate network perimeter, must be authenticated, authorized, and encrypted.
- **Micro-Segmentation**: Isolating workloads and restricting east-west traffic between microservices.

---

## 5. Interview Deep-Dive Questions & Answers

### Q1: How would you design a scalable authorization system for a multi-tenant SaaS application with millions of users and hierarchical resources?
**Answer**:
- Adopt a ReBAC or advanced ABAC model inspired by Google Zanzibar.
- Represent access control as relation tuples (`object`, `relation`, `user`).
- Cache authorization checks aggressively at the API Gateway using signed caveats or short-lived tokens, while maintaining consistency via distributed caching and asynchronous invalidation streams.
