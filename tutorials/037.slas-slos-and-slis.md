# 037. SLAs, SLOs, and SLIs: Masterclass

## 1. Architectural Foundations of Site Reliability

Reliability is a feature. Without rigorous measurement, engineering teams optimize for velocity while accumulating silent technical and reliability debt. Site Reliability Engineering (SRE) establishes a rigorous quantitative framework using three core instruments: **SLIs**, **SLOs**, and **SLAs**.

### 1.1 The Reliability Hierarchy

```
+-----------------------------------------------------------------+
| SLAs (Business Contract + Financial Penalties)                  |
|   +-----------------------------------------------------------+ |
|   | SLOs (Internal Engineering Target / Error Budget)         | |
|   |   +-----------------------------------------------------+ | |
|   |   | SLIs (Raw Measurements: Latency, Error Rate, etc.)  | | |
|   |   +-----------------------------------------------------+ | |
|   +-----------------------------------------------------------+ |
+-----------------------------------------------------------------+
```

*   **Service Level Indicator (SLI):** A quantitatively measured metric of service performance over a rolling window. 
    *   *Examples:* HTTP request latency (percentage of requests completing under 200ms), error rate (percentage of non-5xx responses), data freshness (replication lag in seconds).
    *   *Formula:* $\text{SLI} = \frac{\text{Good Events}}{\text{Total Events}} \times 100$
*   **Service Level Objective (SLO):** The target reliability percentage set by engineering and product teams for an SLI over a specific time window (e.g., 30-day rolling window).
    *   *Example:* $99.9\%$ of all successful HTTP GET requests to `/checkout` must return in $< 250\text{ms}$ over a 30-day rolling window.
*   **Service Level Agreement (SLA):** A binding commercial contract between a service provider and a customer. It guarantees a specific SLO and specifies financial penalties (service credits, refunds) if the SLO is breached.
    *   *Key Rule:* **SLAs should never be stricter than SLOs.** Engineering internal targets (SLOs) must have a safety buffer before hitting the legal SLA threshold to prevent customer-facing contract breaches.

## 2. Defining Effective SLIs for Distributed Systems

Choosing the right SLIs determines whether monitoring accurately reflects user experience.

### 2.1 Request-Driven Systems SLIs
*   **Latency:** Measured at the load balancer or API gateway (edge-to-edge) rather than internal microservice CPU time. Distribution matters: p50, p95, p99, and p99.9.
*   **Availability (Success Rate):** Ratio of successful valid requests to total requests. Exclude client-side errors (HTTP 4xx) from availability SLIs, as they reflect client misuse rather than backend failure. Count HTTP 5xx errors and dropped connections as failures.
*   **Throughput & Durability:** For storage and messaging systems (e.g., Kafka, S3), SLIs measure successful write acknowledgments and durability guarantees.

## 3. Error Budgets and Burn Rate Alerting

An **Error Budget** is the inverse of your SLO. If your SLO is $99.9\%$ availability over 30 days, your error budget is $0.1\%$.

### 3.1 The Philosophy of Error Budgets
*   Error budgets align engineering velocity with reliability.
*   If the error budget is healthy, teams can ship features aggressively.
*   If the error budget is exhausted (consumed), feature deployments are frozen until stability is restored through bug fixes, performance profiling, and reliability engineering.

### 3.2 Burn Rate Alerting
Traditional threshold alerting (e.g., "Alert when error rate > 1%") generates alert fatigue and misses slow leaks. Modern SRE relies on **Burn Rate Alerting**—how fast is the error budget being consumed?

*   **Definition:** A burn rate of $1$ means you will consume exactly $100\%$ of your error budget in the allotted time window (e.g., 30 days).
*   **Google SRE Multi-Window, Multi-Burn-Rate Alerting Formula:**
    *   If you consume $2\%$ of your 30-day error budget in 1 hour (Burn rate = $14.4$), you will exhaust your entire monthly budget in ~50 hours. This warrants an immediate paging alert.
    *   If you consume $5\%$ of your budget in 6 hours (Burn rate = $6$), page within 2 hours.

## 4. Interview Deep Dive & Architectural Questions

### Q1: How do you establish SLOs for a complex microservices architecture where a single user request traverses 15 downstream services?
**Answer:**
1.  **Critical User Journeys (CUJs):** Identify core business transactions (e.g., "User completes checkout").
2.  **Dependency Cascading:** Set individual SLOs for downstream services based on their criticality. If a non-critical recommendation service fails, it should gracefully degrade rather than breaking the checkout SLI.
3.  **Client-Side SLIs:** Measure latency and success from the client application or edge API gateway to capture true end-user experience regardless of internal microservice topology.

### Q2: What happens when an engineering team exhausts its error budget, and how do you enforce the deployment freeze?
**Answer:**
When the error budget hits $0$, all non-reliability deployments (feature flags, new features) are halted. Engineering capacity shifts $100\%$ to refactoring, fixing flaky tests, optimizing bottlenecks, and enhancing monitoring until the rolling window replenishes the budget. CI/CD pipelines can enforce this programmatically by integrating SLO status checks into deployment gates.
