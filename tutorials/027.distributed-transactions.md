# 027. Distributed Transactions Masterclass

## 1. Architectural Foundations

In distributed microservices and polyglot persistence architectures, business operations frequently span multiple independent databases, services, and external APIs. Ensuring data integrity across these boundaries without sacrificing availability or latency is one of the most challenging problems in distributed systems engineering.

### 1.1 The CAP Theorem & ACID vs. BASE

*   **ACID (Atomicity, Consistency, Isolation, Durability):** Traditional guarantees provided by single-node relational databases (e.g., PostgreSQL, MySQL).
*   **BASE (Basically Available, Soft state, Eventual consistency):** The paradigm adopted by distributed data stores and microservices architectures to achieve high availability and partition tolerance (CAP Theorem).
*   **The Distributed Transaction Dilemma:** When trying to enforce strict ACID across multiple network nodes, systems must choose between consistency and availability (FLP Impossibility Theorem & Two-Phase Commit blocking nature).

## 2. Synchronous & Decentralized Coordination Protocols

### 2.1 Two-Phase Commit (2PC)

Two-Phase Commit is a classic atomic commitment protocol ensuring all participating nodes commit or abort together.

```
[ Coordinator ]
       |-- 1. Prepare Request ------------> [ Participant A & B ]
       |<-- 2. Votes (Prepared / Abort) --- [ Participant A & B ]
       |
       | (If all vote Yes)
       |-- 3. Commit / Abort Command ----> [ Participant A & B ]
       |<-- 4. Acknowledgment ------------ [ Participant A & B ]
```

*   **Phase 1 (Prepare):**
    1.  The coordinator sends a `PREPARE` message to all participants.
    2.  Participants execute transaction operations up to the commit point, write locks and undo/redo logs to disk, and reply with `VOTE_COMMIT` (Prepared) or `VOTE_ABORT`.
*   **Phase 2 (Commit/Abort):**
    *   If **all** participants vote `VOTE_COMMIT`, the coordinator writes a commit record to its log and broadcasts `GLOBAL_COMMIT`. Participants commit the transaction and release locks.
    *   If **any** participant votes `VOTE_ABORT` or fails to respond within a timeout, the coordinator broadcasts `GLOBAL_ABORT`. All participants roll back.
*   **Fatal Flaws of 2PC:**
    *   **Blocking:** If the coordinator crashes permanently after Phase 1 while participants are in the `PREPARED` state, participants hold locks indefinitely, freezing resources and causing cascading failures.
    *   **High Latency:** Requires multiple synchronous round-trips across the network.
    *   **Poor Scalability:** As the number of participants increases, the probability of failure increases exponentially.

### 2.2 Three-Phase Commit (3PC)

Three-Phase Commit introduces a non-blocking protocol by adding a `Pre-Commit` phase and using timeouts, but it remains impractical in real-world partitioned networks because network partitions can still lead to inconsistent states.

## 3. Asynchronous & Decentralized Patterns: The Saga Pattern

To avoid the blocking and latency bottlenecks of 2PC, modern microservices architectures rely heavily on the **Saga Pattern**.

### 3.1 Choreography-Based Saga
*   **Mechanism:** Services listen to events on a message broker and execute local transactions independently.
*   **Example (E-Commerce Checkout):**
    1.  `Order Service` creates an order (`OrderCreated`) -> `Payment Service` processes payment (`PaymentProcessed`).
    2.  If payment succeeds -> `Inventory Service` reserves stock (`StockReserved`).
    3.  If `Inventory Service` fails (out of stock) -> publishes `StockReservationFailed`.
    4.  `Payment Service` listens to `StockReservationFailed` and executes a **Compensating Transaction** (`RefundPayment`).
    5.  `Order Service` marks the order as cancelled.

```
[ Order Service ] --(OrderCreated)--> [ Payment Service ] --(PaymentProcessed)--> [ Inventory Service ]
       ^                                      |                                       |
       |--(CancelOrder)<---(RefundPayment)<---+<---(StockReservationFailed)-----------+
```

### 3.2 Orchestration-Based Saga
*   **Mechanism:** A central orchestrator (e.g., Temporal, AWS Step Functions, custom Saga engine) explicitly tells each service what transaction to execute and manages the state machine and compensation sequence.
*   **Advantages over Choreography:** Prevents cyclic dependencies, simplifies debugging, and centralizes business workflow logic.

## 4. Modern Distributed Consensus & Distributed SQL

Modern NewSQL databases (e.g., Google Spanner, CockroachDB, TiDB) solve distributed transactions without sagas by combining **Multi-Paxos / Raft consensus** with **TrueTime (atomic clocks/GPS)** or distributed locking.

*   **Distributed Two-Phase Locking (2PL) + Raft:** Transactions acquire distributed locks across Raft groups.
*   **Serializable Isolation:** Providing serializable ACID transactions across multiple geographic regions with minimal latency.

## 5. System Design Interview Blueprint: Designing a Distributed Payment Gateway

### Problem Statement
Design a payment gateway processing 5,000 transactions/sec interacting with external banking APIs, internal ledger services, and fraud detection.

### Key Architectural Patterns
1.  **Idempotency Keys:** Every payment request must include a client-generated UUID idempotency key stored in a distributed cache/DB with TTL to prevent double-charging on network retries.
2.  **Outbox Pattern:** Guarantee reliable event publishing. Write the transaction state and the outgoing event to the local database table in the exact same ACID transaction, then tail the outbox table (via Debezium/CDC) to publish to Kafka.
3.  **Compensating Workflows:** Use an orchestrator like Temporal to manage multi-step banking clearance, currency conversion, and ledger posting with automatic retries and compensation.
