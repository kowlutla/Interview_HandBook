# 029. Event-Driven Architecture (EDA) Masterclass

## 1. Architectural Foundations

Event-Driven Architecture (EDA) is a software design pattern where decoupled applications and services communicate asynchronously by producing and consuming domain events. Unlike traditional request-response architectures (REST/RPC) where clients tightly couple to servers and wait synchronously for execution, EDA decouples producers in time and space: producers emit events without knowing who consumes them, or even if any consumer is currently active.

### 1.1 Core Components of EDA
*   **Event Producer (Publisher):** A service that detects a state change or business occurrence (e.g., `OrderPlaced`, `UserRegistered`, `SensorReadingRecorded`) and emits an immutable event payload.
*   **Event Broker / Router:** The backbone infrastructure (e.g., Apache Kafka, RabbitMQ, AWS EventBridge, Apache Pulsar) that accepts events, routes them based on topics, keys, or filtering rules, and reliably stores/delivers them to consumers.
*   **Event Consumer (Subscriber):** A service that subscribes to specific event channels or topics, processes incoming events reactively, and updates its local state or triggers downstream workflows.

## 2. Advanced Design Patterns in EDA

### 2.1 Event Sourcing
Instead of storing only the current state of an entity in a relational table (e.g., `Balance = $100`), **Event Sourcing** persists every state-changing event as an immutable sequence in an **Event Store** (e.g., EventStoreDB, Kafka).
*   **How It Works:** Current state is derived by replaying the sequence of all historical events (`AccountCreated`, `DepositMade(+50)`, `WithdrawalMade(-20)`).
*   **Benefits:**
    *   **Absolute Auditability:** Complete, tamper-proof audit log of every operation.
    *   **Time-Travel Queries:** Ability to reconstruct system state at any exact timestamp in the past.
    *   **Event Replay:** Bug fixes or new analytical models can be built by replaying historical events through updated projection code.

### 2.2 CQRS (Command Query Responsibility Segregation)
Event Sourcing naturally pairs with **CQRS**, which splits the data architecture into two distinct models:
*   **Write Side (Command Model):** Handles write operations (`CreateOrder`, `UpdateUser`), validates business logic, and emits domain events into the event store.
*   **Read Side (Query Model):** Subscribes to events, updates denormalized read-optimized databases (e.g., Elasticsearch, Redis, PostgreSQL read replicas), and serves UI queries instantly without complex multi-table joins.

## 3. Topologies and Communication Styles

*   **Pub/Sub (Publish-Subscribe):** Events are broadcast to all interested subscribers. Ideal for notification systems and decoupled broadcasting.
*   **Event Streaming (Log-Based):** Events are stored in ordered, immutable partitions. Multiple consumer groups can read the same stream at different speeds and offsets (Kafka model).
*   **Event Notification vs. Event-Carried State Transfer:**
    *   *Event Notification:* Emits lightweight references (e.g., `OrderCreated { orderId: 123 }`). Consumers must callback via REST/RPC to fetch details.
    *   *Event-Carried State Transfer (ECST):* The event payload contains the complete state snapshot (e.g., `OrderCreated { orderId: 123, items: [...], customer: {...} }`). Consumers do not need to query the producer, eliminating network coupling.

---

## 4. Challenges and Mitigation Strategies

*   **Distributed Consistency & Ordering:** Events arriving out of order can corrupt state. Mitigated by partitioning streams by entity ID (e.g., `userId` or `orderId`) to guarantee strict in-order processing per partition.
*   **Idempotency:** Because networks drop acks and trigger retries, consumers must be fully idempotent (handling duplicate events gracefully).
*   **Debugging & Observability:** Tracing a single user request across asynchronous event chains requires robust **Distributed Tracing** (e.g., OpenTelemetry, Jaeger) injecting correlation IDs into event headers.

*   Understand when to choose Event-Driven Architecture over synchronous REST/gRPC.
*   Master Event Sourcing and CQRS concepts.
*   Know how Event-Carried State Transfer reduces inter-service dependency.
