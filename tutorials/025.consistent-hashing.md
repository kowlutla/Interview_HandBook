# 025. Consistent Hashing: Masterclass

## 1. Introduction & The Problem with Modulo Hashing

In distributed systems, caching clusters, and distributed databases, keys must be mapped across multiple physical servers. The naive approach uses modulo hashing:
$$\text{Server Index} = \text{hash}(\text{Key}) \pmod N$$
where $N$ is the number of servers.

### The Flaw of Modulo Hashing
If a server crashes ($N \to N-1$) or a new server is added ($N \to N+1$), almost every key hashes to a different server index. In a cache cluster, this causes a **cache stampede / cache collapse**, where nearly 100% of cache keys miss simultaneously, overwhelming downstream databases with sudden traffic spikes.

---

## 2. Consistent Hashing Architecture

**Consistent Hashing** (introduced by Karger et al. at MIT) solves this by ensuring that when a node is added or removed, **only $\frac{K}{N}$ keys need to be remapped** (where $K$ is the total number of keys and $N$ is the number of nodes), rather than nearly all keys.

### 2.1 The Hash Ring
1. Imagine the output range of a cryptographic hash function (e.g., MD5 or MurmurHash) mapped onto a circular ring ranging from $0$ to $2^{32}-1$ (or $2^{128}-1$).
2. **Node Placement:** Both physical servers and data keys are hashed using the same hash function and placed onto the ring.
3. **Key Assignment:** A key is stored on the **first physical node encountered moving clockwise** around the ring from the key's hash position.

```
       [ Server A: 10,000 ]
           /          \
          /            \
    [ Key 2 ]        [ Key 1 ]
        │              │
        ▼              ▼
     [ Server B: 200,000 ]
```

---

## 3. Handling Node Changes

### 3.1 Adding a Node
When a new server (Server C) is added to the ring:
- It occupies a specific position on the ring.
- It takes over keys that previously fell clockwise between Server C and its predecessor.
- **Data Movement:** Only the keys residing in that specific segment are migrated to Server C. All other keys on the ring remain untouched.

### 3.2 Removing a Node
When a server crashes or is decommissioned:
- Its assigned keys fall clockwise to the next available physical node.
- **Data Movement:** Only the keys owned by the removed server are reassigned; the rest of the cluster remains unaffected.

---

## 4. Virtual Nodes (Vnodes)

Pure consistent hashing with physical nodes suffers from two major flaws:
1. **Random Hotspots:** Random placement of physical nodes on the ring leads to uneven cluster load distribution (some nodes own massive arcs of the ring, others tiny arcs).
2. **Heterogeneous Hardware:** Powerful servers cannot be assigned proportionally more load than weaker servers.

### The Virtual Node Solution
Instead of mapping each physical server to a single point on the ring, each physical server is represented by **multiple virtual nodes (vnodes)** distributed across the ring (e.g., `ServerA_vnode1`, `ServerA_vnode2`, ..., `ServerA_vnode100`).

- **Benefits:**
  - **Uniform Distribution:** Higher number of vnodes ensures statistical randomness and balanced load across the ring.
  - **Weighted Capacity:** Powerful servers can be assigned 200 vnodes while weaker servers receive 50 vnodes, scaling storage and query load proportionally.
  - **Graceful Failure:** When a node fails, its virtual nodes are evenly distributed across all remaining surviving physical nodes, preventing cascading failures.

---

## 5. Real-World Applications
- **Distributed Caching (Memcached / Redis Cluster):** Client libraries or cluster proxies use consistent hashing to route key requests to the correct cache node.
- **NoSQL Datastores (Apache Cassandra / Amazon DynamoDB):** Uses consistent hashing rings with vnodes for decentralized token ring partitioning and replication across availability zones.
- **CDNs (Content Delivery Networks):** Edge caches route cache requests for static assets using consistent hashing.

---

## 6. Interview Deep Dive & Architectural Questions

### Q1: How do you handle replica placement on a consistent hashing ring for fault tolerance?
**Answer:** To ensure replicas reside on distinct physical servers (not just virtual nodes belonging to the same physical machine), the ring traversal continues clockwise until it finds $R$ distinct physical servers, ignoring subsequent vnodes belonging to servers already included in the replication set.

### Q2: What hash function is preferred for consistent hashing in distributed systems, and why?
**Answer:** Cryptographic hash functions like MD5 or non-cryptographic fast hash functions like MurmurHash3 or CityHash are preferred because they provide excellent avalanche effect and uniform distribution across the hash ring space, minimizing clustering.
