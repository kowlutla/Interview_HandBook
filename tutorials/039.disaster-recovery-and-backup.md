# 039. Disaster Recovery and Backup: Masterclass

## 1. Architectural Foundations of Disaster Recovery

Catastrophic failures—ranging from hardware disk corruption and software bugs to regional power grid outages, fiber cuts, and natural disasters—are statistical certainties at scale. **Disaster Recovery (DR)** and backup architecture ensure business continuity and data integrity when primary infrastructure fails.

### 1.1 Core Recovery Metrics
*   **Recovery Point Objective (RPO):** The maximum tolerable data loss measured in time. It defines how frequently you must take backups or replicate data. (e.g., An RPO of 1 hour means you can lose up to 1 hour of data transactions).
*   **Recovery Time Objective (RTO):** The maximum acceptable duration of downtime before services must be restored. (e.g., An RTO of 15 minutes means automated failover must complete within 15 minutes).

## 2. Backup Strategies & Storage Mechanics

Backups form the foundation of RPO compliance. Understanding backup types and their restoration trade-offs is essential for system designers.

### 2.1 Backup Types
*   **Full Backup:** Complete copy of all data files and metadata.
    *   *Pros:* Simplest and fastest restoration process (restore single backup file).
    *   *Cons:* High storage consumption and lengthy backup windows.
*   **Incremental Backup:** Copies only the blocks or files that have changed since the *most recent backup* (whether full or incremental).
    *   *Pros:* Extremely fast backup times, minimal storage overhead.
    *   *Cons:* Complex and slow restoration (must restore the last full backup plus every subsequent incremental backup in chronological order).
*   **Differential Backup:** Copies all changes made since the *last full backup*.
    *   *Pros:* Faster restoration than incremental (requires only the last full backup plus the most recent differential backup).
    *   *Cons:* Backup size grows larger over time as more changes accumulate between full backups.

### 2.2 Point-In-Time Recovery (PITR) & Write-Ahead Logs (WAL)
Modern databases achieve near-zero RPO (e.g., RPO < 5 seconds) using continuous archiving of Write-Ahead Logs (WAL) or binlogs combined with base snapshots. 
*   **Mechanism:** Every transaction is written to an immutable WAL before hitting storage. The WAL stream is continuously replicated to off-site cloud object storage (S3). To restore to 14:32:10 UTC, the system restores the nightly snapshot and replays WAL records up to the exact target timestamp.

## 3. Multi-Region Disaster Recovery Topologies

When disaster strikes an entire cloud availability zone (AZ) or cloud region, architectures must failover across geographic boundaries.

### 3.1 DR Topology Spectrum
1.  **Backup & Restore (Cold Standby):** Data is backed up to secondary region. Infrastructure is spun up manually upon disaster declaration. High RTO (hours), low cost.
2.  **Pilot Light:** Core database is synchronously or asynchronously replicated to secondary region. Application servers are scaled down or offline. Medium RTO (minutes to hours).
3.  **Warm Standby:** A scaled-down replica of the entire production stack runs continuously in the secondary region. Traffic is routed via DNS failover (Route 53). Low RTO (minutes).
4.  **Active-Active (Multi-Region):** Multiple datacenters actively serve traffic simultaneously. Uses distributed consensus or conflict-free replicated data types (CRDTs). Near-zero RTO and RPO, highest operational complexity and cost.

## 4. Interview Deep Dive & Architectural Questions

### Q1: Design a multi-region active-passive database failover system with an RPO of zero and an RTO under 30 seconds. How do you handle split-brain risks?
**Answer:**
1.  **Replication:** Use synchronous replication between primary and standby database instances within the same region, and asynchronous or semi-synchronous replication to the DR region to prevent write latency spikes.
2.  **Health Checking & Orchestration:** Deploy an automated health-checking agent (e.g., Consul or Kubernetes operator) that monitors primary database liveness.
3.  **Fencing (Split-Brain Prevention):** Before promoting the standby database in the secondary region to primary, the orchestration system must fence (isolate/terminate) the old primary using hardware fencing, API tokens, or STONITH (Shoot The Other Node In The Head) to prevent dual-master writes and data corruption.
4.  **DNS Routing:** Automatically update Global Traffic Management (GTM) or DNS records to point client traffic to the new primary cluster.
