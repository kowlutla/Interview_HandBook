# 026. Blob Storage and File Systems Architecture Masterclass

## 1. Architectural Foundations

Blob (Binary Large Object) storage and distributed file systems are the foundational tiers of unstructured and semi-structured data persistence in modern cloud-native architecture. While traditional relational databases handle structured, transactional data with strict ACID guarantees, blob storage and distributed file systems are optimized for scale, high throughput, cost-efficiency, and massive concurrency over unstructured assets (e.g., videos, high-resolution imagery, backup archives, data lake raw logs, container images, and large language model training checkpoints).

### 1.1 Object Storage vs. Distributed File Systems vs. Block Storage

Understanding the core abstractions is critical for designing scalable systems:

*   **Block Storage (e.g., AWS EBS, GCP Persistent Disk, SAN/NAS via iSCSI/Fibre Channel):**
    *   **Abstraction:** Exposes raw disk blocks (sectors) directly to the operating system. Formatted with filesystems like ext4, XFS, or NTFS.
    *   **Access Pattern:** Low-latency, random read/write access. Mounted directly to a single virtual machine instance (or shared via clustered filesystems with complex locking).
    *   **Use Cases:** Database storage engines, root volumes, transactional logs.
*   **Distributed File Systems (e.g., HDFS, CephFS, GlusterFS, NFS):**
    *   **Abstraction:** Exposes a traditional hierarchical directory and file tree accessed via POSIX-compliant APIs (`open`, `read`, `write`, `close`, `stat`, `chmod`).
    *   **Access Pattern:** File-level locking, random appends/writes, hierarchical path navigation.
    *   **Use Cases:** Big data analytics clusters (Hadoop/Spark), shared application code/asset directories, high-performance computing (HPC).
*   **Object Storage / Blob Storage (e.g., AWS S3, Google Cloud Storage, Azure Blob Storage, MinIO):**
    *   **Abstraction:** Flat namespace consisting of a globally unique bucket and an object key, accompanied by arbitrary metadata and a byte payload. No native POSIX hierarchical directory tree (though prefixes simulate directories).
    *   **Access Pattern:** Immutable objects. Operations are strictly `PUT`, `GET`, `DELETE`, and multipart uploads. Partial in-place updates are not supported; objects are replaced entirely.
    *   **Use Cases:** Data lakes, media streaming, backups, machine learning training datasets, static asset hosting.

```
+--------------------------------------------------------------------------+
|                       STORAGE TIER COMPARISON                            |
+--------------------------+-----------------------+-----------------------+
| Feature                  | Object Storage        | Distributed File Sys  | Block Storage         |
+--------------------------+-----------------------+-----------------------+-----------------------+
| Protocol/API             | REST / HTTP (S3 API)  | POSIX / NFS / SMB     | SCSI / NVMe over TCP  |
| Hierarchy                | Flat (Prefixes)       | Strict Tree (Directories) | Linear Blocks     |
| Mutability               | Append-only / Replace | In-place random write | In-place random write |
| Concurrency              | Massive (Millions QPS)| Moderate (File locks) | Single-node (usually) |
| Cost per GB              | Lowest                | Moderate              | Highest               |
+--------------------------+-----------------------+-----------------------+-----------------------+
```

## 2. Object Storage Deep Dive (S3-Style Architecture)

Modern hyperscale object storage systems are engineering masterpieces designed to achieve eleven 9s ($99.999999999\%$) of durability and four to six 9s of availability while serving tens of millions of requests per second globally.

### 2.1 Internal Architecture of Hyperscale Object Stores

An object storage service is architected into three primary planes:

1.  **Control Plane (Metadata & Namespace Service):**
    *   Manages bucket creation, IAM policies, access control lists (ACLs), bucket lifecycle rules, encryption configurations, and billing telemetry.
    *   Utilizes distributed consensus protocols (e.g., Paxos or Raft) stored across multi-region quorum databases to guarantee linearizable metadata operations.
2.  **Data Plane (Routing & Front-End Fleet):**
    *   A massive tier of stateless HTTP/HTTPS proxy and load-balancing nodes that terminate TLS, validate AWS Signature Version 4 (or equivalent HMAC tokens), parse REST requests, and route payloads to storage nodes.
3.  **Storage Engine / Storage Nodes:**
    *   Distributed clusters of commodity or custom hardware nodes running customized, high-performance storage engines (replacing heavy POSIX file systems with raw disk management or customized key-value stores like RocksDB over raw block devices).
    *   Handles erasure coding, bit-rot detection, checksum validation (MD5, SHA-256, CRC32C), and background data scrubbing.

```
[ Client App ] --HTTPS/REST--> [ API Gateway / Frontend Fleet ]
                                       |
                   +-------------------+-------------------+
                   |                                       |
        [ Control Plane / Metadata ]            [ Storage Nodes / Data Plane ]
        - Bucket Index (Paxos/Raft)             - Erasure Coding / Sharding
        - IAM & ACL Verification                - Disk Blocks / RocksDB Index
        - Lifecycle & Replication               - Checksums & Bit-Rot Scrubbing
```

### 2.2 Data Durability & Erasure Coding

Traditional replication (e.g., 3-way replication where data is copied across three distinct servers or racks) incurs a $200\%$ storage overhead ($3\times$ storage cost). Modern object storage relies heavily on **Erasure Coding (EC)** to achieve extreme durability with drastically lower overhead.

*   **Reed-Solomon Coding ($m+n$):** Data is split into $m$ data fragments and $n$ parity fragments. For example, in an $RS(12, 4)$ configuration:
    *   A 12MB object is split into twelve 1MB data chunks ($m=12$).
    *   Four parity chunks ($n=4$) are computed via polynomial matrix multiplication over Galois fields ($GF(2^8)$).
    *   Total 16 chunks are distributed across 16 independent failure domains (different servers, racks, power zones, or datacenters).
*   **Fault Tolerance:** The system can tolerate the simultaneous catastrophic failure of any $n$ fragments (in $RS(12,4)$, any 4 out of 16 nodes can fail) without data loss.
*   **Storage Overhead:** The storage overhead factor is $\frac{m+n}{m}$. For $RS(12,4)$, overhead is $\frac{16}{12} = 1.33$ ($33\%$ overhead compared to $200\%$ for 3-way replication).

### 2.3 Multipart Upload Architecture

Standard HTTP PUT requests are impractical for multi-gigabyte or terabyte files due to TCP connection drops, memory pressure, and retry storms. Object storage implements **Multipart Upload**:

1.  **Initiate Multipart Upload:** Client sends an HTTP request (`POST ?uploads`). The control plane allocates a unique upload ID and initializes a staging directory.
2.  **Upload Parts:** Client splits the large file into independent chunks (typically 5MB to 5GB) and issues concurrent `PUT ?partNumber=i&uploadId=...` requests. Each part is independently checksummed and written to storage nodes.
3.  **Complete Multipart Upload:** Client sends a `POST ?uploadId=...` containing an ordered manifest of part ETags. The coordinator verifies all parts exist, validates checksums, stitches metadata references atomically, and makes the object visible in the bucket namespace.
4.  **Abort/Cleanup:** If an upload fails or times out, lifecycle rules automatically garbage-collect orphaned part chunks from staging storage.

## 3. Distributed File Systems Architecture

When applications require POSIX compliance, directory hierarchies, and random in-place updates at scale, distributed file systems are deployed.

### 3.1 HDFS (Hadoop Distributed File System)

HDFS is designed for batch processing (MapReduce / Spark) with write-once, read-many workloads.

*   **NameNode (Master):** Maintains the entire filesystem namespace, directory tree, file-to-block mapping, and location of blocks on DataNodes. The NameNode stores metadata in memory (backed by an EditLog on disk and an FSImage checkpoint).
*   **DataNodes (Workers):** Store actual data blocks on local Linux filesystems. Periodically send block reports and heartbeats to the NameNode.
*   **Architecture Flow:**
    1. Client queries NameNode for file metadata and block locations.
    2. NameNode returns the list of DataNodes holding the requested blocks.
    3. Client streams data directly from the closest DataNode (rack-aware selection).

### 3.2 Ceph File System (CephFS)

Ceph is a unified, highly resilient distributed storage system providing object, block, and file storage on a single distributed cluster.

*   **RADOS (Reliable Autonomic Distributed Object Store):** The core engine that manages physical storage nodes as object storage.
*   **CRUSH Algorithm (Controlled Replication Under Scalable Hashing):** Unlike traditional centralized lookup tables, CRUSH is a deterministic pseudo-random placement algorithm. Given an object ID and cluster topology map, any client or storage node can compute precisely which OSD (Object Storage Daemon) holds the data without querying a central master. This eliminates centralized metadata bottlenecks.
*   **MDS (Metadata Servers):** CephFS uses a cluster of MDS daemons to manage the hierarchical directory namespace and POSIX metadata caching, while actual data is striped across RADOS OSDs.

## 4. Advanced Concepts & Challenges

### 4.1 Consistency Models

*   **Strong Read-After-Write Consistency:** After a successful `PUT` (create) or `DELETE` request for a new object, subsequent `GET` requests immediately return the new object or confirm deletion. (Modern cloud object stores like AWS S3 and GCS achieve read-after-write consistency globally for all operations).
*   **Eventual Consistency:** Older architectures exhibited a window where updates propagated asynchronously across replica nodes, causing stale reads.

### 4.2 Tiered Storage & Lifecycle Management

Managing petabytes or exabytes of data requires automated lifecycle policies to minimize costs:
*   **Hot Tier:** High-performance SSD-backed storage for active serving (frequent access).
*   **Cool/Warm Tier:** Standard HDD-backed storage for infrequent access (monthly queries).
*   **Cold / Archive Tier (e.g., AWS S3 Glacier):** Tape or high-density sharded disk storage with multi-hour retrieval latencies, optimized for long-term compliance retention.

### 4.3 Security, Encryption, and Access Control

*   **Server-Side Encryption (SSE-S3, SSE-KMS):** Data is encrypted at rest using keys managed by the cloud provider or customer-managed Hardware Security Modules (HSMs).
*   **Client-Side Encryption:** Applications encrypt data before transmitting it to the blob store.
*   **Presigned URLs:** Time-bounded cryptographic tokens granting temporary read/write access to specific objects without exposing permanent AWS IAM credentials.

## 5. System Design Interview Blueprint: Designing a Global Enterprise File Sync and Share Service (Dropbox / Google Drive style)

### Problem Statement
Design a cloud-hosted file synchronization service supporting 100 million active users, cross-device real-time sync, file versioning, sharing permissions, and delta-sync optimization.

### Step 1: Estimation & Requirements
*   **Scale:** 100M MAU, 10M DAU. Average user stores 5 GB. Total storage = 500 PB.
*   **Write Throughput:** 10M daily active users $\times$ 20 file changes/day = 200M changes/day $\approx$ 2,300 writes/sec.
*   **Read Bandwidth:** Peak read traffic equivalent to heavy streaming and syncing.

### Step 2: High-Level Architecture
```
[ Desktop / Mobile Client ] 
       |
       +---> (Chunking Engine: Rabin Fingerprinting) 
       |          |
       |          v
       |     [ Metadata Service ] <---> [ PostgreSQL / Spanner (Metadata DB) ]
       |          |
       |          v
       +---> [ Block Server / API Gateway ] 
                  |
                  v
       +---> [ Object Storage (S3 / Ceph) ] (Immutable Chunks)
```

### Step 3: Key Design Decisions
1.  **Chunking & Deduplication:** Files are broken into variable-sized chunks using **Rabin Fingerprinting** (content-defined chunking). Identical chunks across different files or users are stored only once (global deduplication), saving petabytes.
2.  **Delta Sync:** When a 100MB file has 2 lines modified, only the modified chunk hashes are transmitted to the server, rather than re-uploading the entire 100MB file.
3.  **Metadata vs Data Separation:** File metadata (path, owner, sharing ACLs, version tree, chunk hash manifest) is stored in a transactional relational database or distributed SQL store (e.g., CockroachDB / Google Spanner). Actual binary chunks are stored immutably in object storage.
4.  **Real-Time Notification & Sync:** Clients maintain a persistent WebSocket or gRPC bidirectional stream with a notification service (e.g., Redis Pub/Sub backed cluster) to receive instant sync triggers when another device updates a file.
