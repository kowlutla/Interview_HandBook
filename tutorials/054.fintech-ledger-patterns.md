# 054. FinTech Ledger & Payment Patterns

## Overview
Financial systems require absolute correctness, auditability, zero data loss, and strict adherence to accounting invariants. A **FinTech ledger** acts as the definitive source of truth for all monetary movements within an enterprise.

---

## 1. Core Principles of Financial Ledgers

### A. Double-Entry Bookkeeping
Invented by Luca Pacioli in 1494, double-entry bookkeeping mandates that every financial transaction has equal and opposite effects in at least two accounts.
- **Fundamental Equation**: $\text{Assets} + \text{Expenses} = \text{Liabilities} + \text{Equity} + \text{Revenue}$
- **Debits and Credits**: Every transaction consists of balanced journal entries where $\sum \text{Debits} = \sum \text{Credits}$.
- **Account Types**:
  - *Assets* (Cash, Accounts Receivable): Increased by Debits.
  - *Liabilities* (User Balances Owed): Increased by Credits.
  - *Equity* (Capital): Increased by Credits.
  - *Revenue* (Fees Earned): Increased by Credits.
  - *Expenses* (Operating Costs): Increased by Debits.

### B. Immutability & Append-Only Architecture
Financial ledgers are strictly **append-only**. 
- Historical records are never updated or deleted.
- If an error occurs, it is corrected by posting a **compensating transaction** (a reversing entry) that references the original transaction ID.
- This provides an unbroken, auditable chain of custody for every cent.

---

## 2. Concurrency & Race Conditions

In high-throughput payment systems, concurrent transactions targeting the same account can introduce race conditions (e.g., double-spending or negative balances).

### A. Pessimistic Locking
- Uses database row locks (`SELECT ... FOR UPDATE`) to serialize access to an account balance.
- *Pros*: Guarantees zero negative balances.
- *Cons*: High contention bottleneck under high concurrency.

### B. Optimistic Concurrency Control (OCC)
- Uses a `version` column on the account record. If the version changes between read and write, the transaction aborts and retries.
- *Pros*: High throughput when contention is low.
- *Cons*: Frequent retries under high contention on hot accounts.

---

## 3. Idempotency & Network Resiliency

Network timeouts can cause clients or payment gateways to retry requests. Without idempotency, a single charge request could execute multiple times.

### A. Idempotency Keys
- Clients generate a unique UUID (`Idempotency-Key`) for every payment request.
- The server stores the key alongside the request status and resulting transaction in a unique database constraint.
- Subsequent requests with the same key return the cached response without re-executing the financial transaction.

---

## 4. Distributed Transactions & Sagas

Modern payment workflows span multiple microservices and external payment gateways (Stripe, banks). Traditional ACID distributed transactions (Two-Phase Commit / 2PC) are too slow and brittle for web-scale FinTech.

### A. The Saga Pattern
- **Choreography**: Services listen to domain events and execute local transactions independently.
- **Orchestration**: A central Saga orchestrator explicitly commands each service to execute a step and invokes compensating transactions if any step fails.

---

## 5. End-of-Day Reconciliation

No financial system is infallible. **Reconciliation** processes compare internal ledger balances against external statement files provided by payment processors (Stripe, Visa, Mastercard, partner banks) to detect and flag discrepancies, missing payouts, or fraudulent adjustments.
