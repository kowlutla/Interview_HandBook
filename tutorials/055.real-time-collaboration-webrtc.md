# 055. Real-Time Collaboration & WebRTC

## Overview
Low-latency real-time collaboration powers modern productivity tools, multiplayer games, video conferencing, and document editors. Architecting these systems requires mastering peer-to-peer networking protocols, media routing topologies, and real-time state synchronization.

---

## 1. WebRTC Architecture & Protocols

**WebRTC (Web Real-Time Communication)** enables peer-to-peer audio, video, and arbitrary data streaming directly between browsers without intermediate proxy servers.

### A. Signaling
WebRTC requires a separate **signaling channel** (typically WebSockets or Server-Sent Events) to bootstrap a connection. Peers exchange three types of metadata during signaling:
1. **SDP Offers and Answers** (Session Description Protocol): Codec capabilities, encryption settings, and network address candidates.
2. **ICE Candidates** (Interactive Connectivity Establishment): Discovered IP addresses and ports for potential connection paths.

### B. NAT Traversal: STUN and TURN
Most clients sit behind Network Address Translators (NATs) and firewalls.
- **STUN (Session Traversal Utilities for NAT)**: Allows a client to discover its own public IP address and port as seen from the outside internet.
- **TURN (Traversal Using Relays around NAT)**: When direct peer-to-peer connection is impossible due to symmetric NAT restrictions, all traffic is relayed through a central TURN server.

## 2. Media Topologies (Video Conferencing)

When scaling video collaboration to multiple participants, choosing the right media topology is critical:

| Topology | Description | Bandwidth Cost (Client) | Server Compute Cost | Best Used For |
| :--- | :--- | :--- | :--- | :--- |
| **Mesh (P2P)** | Every peer connects directly to every other peer. | High ($N-1$ streams uploaded/downloaded) | Zero (No media server) | Small groups (2–4 participants) |
| **SFU (Selective Forwarding Unit)** | Peers upload one stream to a media server; server forwards streams to all participants. | Medium (1 upload, $N-1$ downloads) | Medium (Routing packets without heavy transcoding) | Standard video conferencing (Zoom, Google Meet) |
| **MCU (Multipoint Control Unit)** | Server receives all streams, mixes/transcodes them into a single composite video stream, and sends it to each client. | Low (1 upload, 1 download) | Extremely High (Heavy video mixing encoding) | Large webinars, resource-constrained clients |

## 3. WebRTC Data Channels

Beyond audio and video, WebRTC provides **Data Channels** running SCTP (Stream Control Transmission Protocol) over DTLS/UDP.
- **Reliability Modes**:
  - *Reliable*: Guarantees ordered, lossless delivery (like TCP).
  - *Unreliable / Unordered*: Drops old packets and allows out-of-order delivery (ideal for high-frequency cursor tracking or game state updates).

---

## 4. Real-Time Collaboration Stack

### A. Presence and Awareness
- **Heartbeats**: Clients send periodic ping/pong messages over WebSockets to maintain active presence and detect sudden disconnects.
- **Cursors & State**: Transmitting mouse coordinates, selection ranges, and user focus states with throttling/debouncing to prevent network saturation.

### B. Combining WebRTC with CRDTs
For zero-conflict collaborative editing (like Figma or Google Docs):
- **Transport**: WebRTC Data Channels provide ultra-low-latency peer-to-peer data transport.
- **Data Structure**: CRDTs (Yjs or Automerge) run over the Data Channels, ensuring that concurrent edits made by offline or connected peers merge deterministically without server locking.
