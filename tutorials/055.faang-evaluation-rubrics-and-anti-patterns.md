# 055. FAANG Evaluation Rubrics & Anti-Patterns

## Overview
Understanding how top-tier companies (FAANG/MAANG) evaluate system design interviews is key to structuring your responses effectively and avoiding common pitfalls.

## Core Evaluation Rubrics
Interviewers evaluate across four primary dimensions:

### 1. Requirements Clarification & Scoping
- **Goal**: Define the scope before jumping into design.
- **Key Actions**: Identify functional requirements (what the system does), non-functional requirements (latency, availability, consistency), and constraints (scale, QPS, data size, read/write ratio).

### 2. High-Level Architecture & Component Design
- **Goal**: Build a decoupled, scalable design.
- **Key Actions**: Select appropriate components (load balancers, API gateways, microservices, caches, databases, message queues) and explain their interactions clearly.

### 3. Deep Dives & Scalability Trade-offs
- **Goal**: Demonstrate depth of understanding.
- **Key Actions**: Address bottlenecks like database sharding, replication lag, cache invalidation, and consistency models (CAP theorem). Explicitly justify technical choices by weighing pros and cons.

### 4. Communication & Collaboration
- **Goal**: Structure the interview as a collaborative discussion.
- **Key Actions**: Organize the conversation, respond constructively to feedback, and manage time effectively.

## Common System Design Anti-Patterns
Avoiding these common mistakes is crucial for success:

- **Premature Optimization / Over-engineering**: Proposing complex distributed solutions (Kafka, Kubernetes, multi-region) for simple, low-scale problems.
- **The "Silver Bullet" Fallacy**: Forcing favorite technologies (e.g., MongoDB, Redis) regardless of the specific workload or access patterns.
- **Hand-Waving Bottlenecks**: Ignoring SPOFs (Single Points of Failure), database saturation, or network limitations without suggesting mitigations.
- **Skipping Clarification**: Rushing to draw architecture diagrams before establishing constraints or traffic estimates.
- **Poor Time Management**: Spending excessive time on high-level components, leaving insufficient time for deep-dive discussions on data schema or APIs.
- **Failing to Discuss Trade-offs**: Presenting a design as the only solution instead of evaluating trade-offs (e.g., strong vs. eventual consistency, latency vs. throughput).
