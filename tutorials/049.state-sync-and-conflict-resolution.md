# 049. State Synchronization and Conflict Resolution

## Overview
In distributed web architectures, clients maintain local state to ensure high responsiveness and offline resilience. However, when multiple clients or a client and server concurrently modify shared state, discrepancies arise. **State synchronization and conflict resolution** define the algorithms and protocols required to reconcile concurrent changes reliably and consistently.

---

## 1. Synchronization Paradigms

### A. Optimistic vs. Pessimistic UI Updates
- **Pessimistic Updates**: The UI waits for server confirmation before reflecting state changes. While safe against conflicts, this introduces network latency perceived as sluggishness.
- **Optimistic Updates**: The UI immediately applies state changes locally and assumes server success. If the server rejects the mutation, the client rolls back or applies compensation logic.

### B. Sync Triggers
- **Poll-based**: Periodic polling of server state (inefficient, high server load).
- **Event-driven (WebSockets / SSE)**: Real-time notification of state mutations.
- **Local-First Sync**: Continuous background synchronization of local databases (IndexedDB/SQLite) with remote servers via transactional logs.

---

## 2. Conflict Resolution Strategies

When two concurrent mutations modify the same resource before synchronization, a conflict occurs. Different architectures handle conflicts using distinct strategies:

### A. Last-Write-Wins (LWW)
- **Mechanism**: Attaches a timestamp to each mutation. When conflicts occur, the update with the latest timestamp overwrites the others.
- **Pitfalls**: Highly vulnerable to **clock skew** and NTP drift across client devices. Simultaneous user edits within clock resolution windows can result in silent data loss.

### B. Operational Transformation (OT)
- **Mechanism**: Primarily used in collaborative text editing (e.g., Google Docs). Operations (e.g., `insert(pos, char)`, `delete(pos)`) are transformed relative to concurrent operations that executed before them.
- **Topology**: Requires a **centralized server coordinator** that serializes operations, transforms them against concurrent past operations, and broadcasts them to all clients.

### C. Conflict-free Replicated Data Types (CRDTs)
- **Mechanism**: Decentralized mathematical data structures that guarantee convergence without requiring a central coordinator or locking.
- **Mathematical Foundation**: Formulated as a **join-semilattice** where the merge function ($\sqcup$) is:
  - **Commutative**: $a \sqcup b = b \sqcup a$ (order of delivery does not matter).
  - **Associative**: $(a \sqcup b) \sqcup c = a \sqcup (b \sqcup c)$ (grouping does not matter).
  - **Idempotent**: $a \sqcup a = a$ (duplicate delivery is harmless).

#### CRDT Variants:
1. **State-based CRDTs (CvRDT)**: Clients send their entire local state to peers; peers merge states using the join operator.
2. **Operation-based CRDTs (CmRDT)**: Clients broadcast individual operations; requires causal delivery guarantees.

---

## 3. Practical Architectural Patterns

### A. Vector Clocks and Version Vectors
To track causality without relying on wall-clock time, distributed systems use vector clocks $V(i)$ where each node maintains a vector of sequence numbers.
- If $V_A < V_B$, update $A$ causally preceded $B$.
- If neither $V_A < V_B$ nor $V_B < V_A$, a **concurrent conflict** exists and must be surfaced to the application or merged automatically.

### B. Local-First Stacks (Yjs / Automerge)
Modern local-first frameworks combine SQLite/IndexedDB with CRDT libraries (like Yjs or Automerge). Every keystroke or state change is recorded as a local CRDT fragment, synced over WebSockets or WebRTC data channels, and merged deterministically across all peers.
