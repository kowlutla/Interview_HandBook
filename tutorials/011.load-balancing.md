# 011. Load Balancing and Traffic Distribution

> **The Definitive, Comprehensive Masterclass on Load Balancing Topologies, Layer 4 vs. Layer 7 Routing, Algorithms, and High-Availability Architecture.**
> *Serving as a complete, authoritative reference covering load balancing algorithms, health checks, session persistence, global server load balancing (GSLB), and fault tolerance.*

---

## 1. Executive Summary & Philosophy

As web traffic scales beyond the capacity of a single server, horizontal scaling becomes mandatory. A cluster of application servers requires an intelligent traffic director to distribute incoming client requests across multiple backend instances.

A **Load Balancer (LB)** sits between clients and backend servers, acting as a reverse proxy to ensure high availability, fault tolerance, optimal resource utilization, and horizontal scalability. Without load balancing, systems suffer from single points of failure and resource exhaustion.

---

## 2. Load Balancer Placement & Topologies

```
[ Clients ] ---> [ DNS / GSLB ] ---> [ Layer 4 / 7 Load Balancer ]
                                            |
                       +--------------------+--------------------+
                       |                    |                    |
                       v                    v                    v
                 [ App Server 1 ]     [ App Server 2 ]     [ App Server 3 ]
```

*   **External / Edge Load Balancer**: Faces the public internet, handling SSL termination, DDoS protection, and initial traffic distribution.
*   **Internal Load Balancer**: Distributes traffic between microservices inside a private VPC (e.g., from API Gateway to internal service clusters).

## 3. Layer 4 vs. Layer 7 Load Balancing

Load balancers operate at different layers of the OSI stack, determining how deeply they inspect packet payloads.

### 3.1 Layer 4 (Transport Layer) Load Balancing
*   **Mechanism**: Operates at the transport layer (TCP/UDP). Routes traffic based on IP addresses and TCP/UDP ports without inspecting application payloads.
*   **Pros**: Extremely high throughput, low latency, minimal CPU overhead.
*   **Cons**: Lacks context about HTTP headers, URLs, or cookies; cannot make routing decisions based on application content.

### 3.2 Layer 7 (Application Layer) Load Balancing
*   **Mechanism**: Operates at the application layer (HTTP/HTTPS/gRPC). Terminates TCP connections, parses HTTP headers, cookies, query parameters, and URIs.
*   **Pros**: Intelligent routing (e.g., routing `/api/v1/users` to the User Service and `/api/v1/orders` to the Order Service), SSL termination, request rewriting, caching.
*   **Cons**: Higher CPU and memory overhead; requires maintaining TCP state.

## 4. Load Balancing Algorithms

| Algorithm | Description | Best Suited For |
| :--- | :--- | :--- |
| **Round Robin** | Sequentially distributes requests across servers in order. | Homogeneous server pools with equal capacity. |
| **Weighted Round Robin** | Assigns requests proportional to server weights (e.g., a server with weight 3 gets 3x more traffic). | Heterogeneous server fleets with mixed hardware specs. |
| **Least Connections** | Routes incoming requests to the server with the fewest active connections. | Long-lived connections (WebSockets, database queries). |
| **Weighted Least Connections** | Combines active connection count with server capacity weights. | Dynamic workloads with varying request processing times. |
| **IP Hash / Source IP** | Hashes the client's IP address to consistently map a client to the same backend server. | Basic session persistence without external state stores. |
| **Consistent Hashing** | Uses a consistent hashing ring to map keys/requests to backend nodes with minimal remapping upon node scaling. | Caching layers, distributed hash tables, stateful routing. |

## 5. Health Checks and Fault Tolerance

A load balancer continuously monitors backend server availability via active and passive health checks.

*   **Active Health Checks**: The load balancer periodically sends probe requests (e.g., HTTP `GET /healthz`) to backend servers at configured intervals. If a server fails $N$ consecutive checks, it is marked unhealthy and removed from the active routing pool.
*   **Passive Health Checks**: The load balancer monitors real client traffic. If a server returns multiple HTTP 5xx errors or connection timeouts, the load balancer temporarily ejects it.

---

## 6. Global Server Load Balancing (GSLB)

While traditional load balancers operate within a single data center or availability zone, **GSLB** distributes traffic across multiple geographically separated data centers worldwide, combining DNS resolution with continuous health monitoring of entire regions.

---

## 7. Common Pitfalls & Anti-Patterns

1.  **Sticky Sessions without State Replication**: Relying solely on IP Hash / cookie stickiness for session state without backing it with a shared Redis store, causing user data loss if a server restarts.
2.  **Load Balancer as a Single Point of Failure (SPoF)**: Deploying a single load balancer instance without active-passive or active-active redundancy (e.g., Keepalived / VRRP).
3.  **Ignoring Connection Drain**: Shutting down backend servers immediately during deployments without allowing active long-lived requests to complete gracefully.
