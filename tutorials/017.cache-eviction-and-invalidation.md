## 1. Executive Summary & Philosophy

Caching is a cornerstone of high-performance system design, bridging the speed gap between fast ephemeral storage (RAM/CPU cache) and slower persistent storage (SSDs, databases, network services). Because memory is finite and expensive, every caching layer must enforce strict capacity boundaries. When a cache reaches its capacity limit, **eviction policies** determine which items to discard to make room for new data. Simultaneously, **invalidation strategies** ensure that cached data remains synchronized with the underlying source of truth, preventing stale reads and data corruption.

Mastering cache eviction and invalidation requires balancing hit rates, computational overhead, memory footprints, and consistency guarantees under heavy concurrent workloads.

## 2. Cache Architecture & Memory Bounds

A cache is structured as a key-value store optimized for low-latency lookups $O(1)$. However, physical memory is bounded. Without proactive management, caches succumb to Out-Of-Memory (OOM) faults or thrashing.

```
+-------------------------------------------------------+
|                    CACHE STORAGE                      |
|                                                       |
|  [ Key 1 : Value ] -> Last Accessed: T-10s            |
|  [ Key 2 : Value ] -> Last Accessed: T-2s             |
|  [ Key 3 : Value ] -> Last Accessed: T-45s  <-- EVICT |
+-------------------------------------------------------+
                           |
                     Capacity Reached
                           |
                           v
              +--------------------------+
              |      Eviction Policy     |
              | (LRU, LFU, Clock, etc.)  |
              +--------------------------+
```

## 3. Cache Eviction Policies

When cache capacity is exhausted, the eviction policy selects victim items for removal. Different policies optimize for different access patterns.

### 3.1 Least Recently Used (LRU)
* **Mechanics**: Evicts the item that has not been accessed for the longest period of time. Based on the temporal locality principle (recently accessed items are likely to be accessed again soon).
* **Data Structure**: Typically implemented using a Hash Map combined with a Doubly Linked List ($O(1)$ lookups, insertions, and removals).
* **Limitations**: Vulnerable to "cache pollution" via one-off scans (e.g., a batch job reading all keys once flushes out hot operational data).

### 3.2 Least Frequently Used (LFU)
* **Mechanics**: Tracks access frequency and evicts items with the lowest access count.
* **Data Structure**: Min-heap combined with hash maps or frequency lists.
* **Limitations**: Stale hot items can linger indefinitely unless an aging mechanism (decay factor) is applied.

### 3.3 First-In, First-Out (FIFO)
* **Mechanics**: Evicts the oldest inserted item regardless of access frequency or recency.
* **Data Structure**: Queue / Circular buffer.
* **Limitations**: Suffers from Belady's Anomaly (increasing cache size can sometimes increase miss rates) and poor hit rates for skewed workloads.

### 3.4 Random Replacement (RR)
* **Mechanics**: Selects a random key for eviction when capacity is reached.
* **Advantages**: Zero metadata overhead, extremely fast, highly concurrent.
* **Disadvantages**: Suboptimal hit rates compared to LRU/LFU, but surprisingly effective when access patterns are uniform.

### 3.5 Advanced Replacement Policies
* **CLOCK / Second-Chance**: A lightweight approximation of LRU using a circular buffer and a reference bit per entry. Avoids the pointer-manipulation overhead of doubly linked lists.
* **ARC (Adaptive Replacement Cache)**: Dynamically balances between LRU (recency) and LFU (frequency) to self-tune based on workload characteristics.
* **TinyLFU**: Combines a frequency sketch (Count-Min Sketch) with an LRU window to maintain high hit rates with minimal memory overhead (used in Caffeine cache).

## 4. Invalidation Strategies

Invalidation ensures that when underlying data changes, stale cache entries are removed or updated.

### 4.1 Write-Through Cache
* **Workflow**: The application writes data to the cache, which synchronously writes to the primary database before returning success.
* **Pros**: Strong consistency; cache never contains stale data relative to the write path.
* **Cons**: Higher write latency due to synchronous database round-trips.

### 4.2 Write-Back / Write-Behind Cache
* **Workflow**: The application writes data to the cache, which immediately returns success. The cache asynchronously flushes writes to the database in batches.
* **Pros**: Extremely fast write performance.
* **Cons**: Risk of data loss if the cache node crashes before flushing to persistent storage.

### 4.3 Cache-Aside (Lazy Loading)
* **Workflow**: 
  1. Application checks cache.
  2. If hit, return data.
  3. If miss, query database, populate cache, and return data.
* **Pros**: Cache only stores requested data; resilient to cache node failures.
* **Cons**: First request for a key incurs a cache miss penalty; potential race conditions on concurrent invalidation.

### 4.4 Write-Around Cache
* **Workflow**: Writes go directly to the database, bypassing the cache. Cache is only populated on subsequent reads (cache miss).
* **Pros**: Prevents cache pollution from write-heavy, read-infrequent data.

### 4.5 Time-To-Live (TTL) & Expiration
* **Mechanics**: Every entry is assigned an absolute expiration timestamp or relative TTL.
* **Lazy Expiration**: Expired items are checked and purged upon access.
* **Active Expiration**: Background threads periodically sample keys and purge expired entries.

## 5. Distributed Concurrency & Failure Modes

In distributed systems, caching introduces complex synchronization challenges:

* **Cache Stampede / Dogpiling**: When a heavily requested hot key expires, thousands of concurrent requests miss the cache simultaneously and hammer the database.
  * *Mitigation*: Probabilistic Early Expiration (XFetch), mutex locks / request coalescing (single-flight pattern).
* **Cache Breakdown / Penetration**: Requests for non-existent keys (malicious or erroneous) always bypass the cache and hit the database.
  * *Mitigation*: Bloom filters, caching null/empty results with short TTLs.
* **Cache Avalanche**: A large batch of keys expire at the exact same time, causing a catastrophic spike in database load.
  * *Mitigation*: Add jitter (randomized offsets) to TTL expiration values.

## 6. Comparative Analysis / Trade-Off Matrix

| Eviction / Invalidation Strategy | Time Complexity | Space Overhead | Hit Rate Efficiency | Primary Vulnerability |
| :--- | :--- | :--- | :--- | :--- |
| **LRU** | $O(1)$ | Medium (Doubly Linked List pointers) | High for temporal workloads | Scan pollution (batch queries) |
| **LFU** | $O(1)$ | High (Frequency maps / heaps) | High for frequency workloads | Stale hot items lingering |

## 7. Real-World Case Studies

* **Redis Memory Management**: Redis supports configurable maxmemory policies (`volatile-lru`, `allkeys-lru`, `volatile-lfu`, `allkeys-lfu`, `volatile-random`, `allkeys-random`, `volatile-ttl`). Redis does not scan all keys for LRU; instead, it uses a randomized approximation algorithm by sampling a configurable number of keys and evicting the best candidate.
* **Facebook Memcached Scaling**: Facebook utilizes memcached clusters with client-side request routing and lease tokens to mitigate cache stampedes and stale writes caused by concurrent database updates.

---

## 8. Common Pitfalls & Anti-Patterns

1. **Ignoring Cache Invalidation**: Relying solely on TTLs for mutable data, leading to users seeing outdated states for extended periods.
2. **Unbounded Caching**: Allocating caches without a max capacity or eviction policy, inevitably leading to OOM crashes.
3. **Thundering Herd Ignorance**: Deploying high-traffic caches without mutex locks or probabilistic early expiration, risking cascading database failures.
