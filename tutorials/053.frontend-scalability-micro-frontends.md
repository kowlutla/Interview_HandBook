# 053. Frontend Scalability & Micro-Frontends

## Overview
As frontend applications grow in complexity and team size, monoliths become difficult to maintain, deploy, and scale. Micro-frontend architecture applies the principles of microservices to the frontend, enabling independent teams to develop, test, and deploy features autonomously.

## Core Concepts
- **Decomposition**: Breaking a large SPA into smaller, independently deployable pieces.
- **Autonomy**: Teams own the entire lifecycle of a feature (development, testing, deployment).
- **Technology Agnostic**: Different micro-frontends can theoretically use different frameworks (e.g., React, Vue, Svelte), though this increases complexity.

## Integration Strategies
1. **Build-Time Integration**: Micro-frontends are published as NPM packages. The host application installs them as dependencies. *Pros:* Consistent development experience. *Cons:* Tight coupling; requires a rebuild/redeploy of the host for any update.
2. **Run-Time Integration (Iframe)**: Simplest isolation mechanism. *Pros:* Complete CSS/JS isolation. *Cons:* Poor performance, difficult to share state or orchestrate communication.
3. **Run-Time Integration (Web Components)**: Native browser standard for encapsulating custom elements. *Pros:* Highly interoperable. *Cons:* Requires polyfills; state management and routing can be tricky.
4. **Module Federation (Webpack 5+)**: Shared runtime environment that allows dynamic loading of remote modules. *Pros:* Excellent performance, efficient dependency sharing. *Cons:* Higher configuration complexity.

## Challenges & Best Practices
- **CSS Isolation**: Use CSS Modules, BEM, or Shadow DOM to prevent global namespace collisions.
- **Shared State**: Avoid global state. Communicate through events, browser storage, or a lightweight shared message bus.
- **Routing**: The host application should maintain overall routing, delegating sub-routes to the active micro-frontend.
