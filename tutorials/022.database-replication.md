# 022. Database Replication: Masterclass

## 1. Introduction & Foundational Goals

Database replication involves copying data from a primary database instance to one or more replica instances. Replication is foundational for distributed systems, serving three core pillars:
1. **High Availability (HA):** If the primary node crashes, a replica can be promoted to take over with minimal downtime.
2. **Read Scalability:** Distributing read queries across multiple read-only replicas offloads CPU and I/O pressure from the primary.
3. **Geographic Distribution:** Placing replicas closer to regional users reduces network latency for read operations.

---

## 2. Replication Synchronization Models

The synchronization protocol determines *when* a write is considered successfully committed to the client relative to replica confirmation.

### 2.1 Synchronous Replication
- **Mechanism:** The primary node waits for all (or a quorum of) replicas to acknowledge that they have written the transaction to disk before returning success to the client.
- **Trade-offs:** 
  - *Pros:* Zero data loss (RPO = 0) upon primary failure; replicas are always fully up-to-date.
  - *Cons:* Higher write latency (bounded by the slowest replica/network round-trip); reduced availability (if one replica fails, writes block).

### 2.2 Asynchronous Replication
- **Mechanism:** The primary commits the transaction locally, writes to its WAL, returns success to the client immediately, and asynchronously streams the replication log to replicas in the background.
- **Trade-offs:**
  - *Pros:* Maximum write performance and lowest latency; primary continues functioning even if all replicas go offline.
  - *Cons:* Potential data loss (RPO > 0) if the primary crashes before log entries are replicated. Read replicas suffer from replication lag.

### 2.3 Semi-Synchronous Replication
- **Mechanism:** A compromise where the primary waits for *at least one* replica to acknowledge receipt of the write before confirming to the client.
- **Trade-offs:** Balances durability against latency. If the primary crashes, the acknowledged replica guarantees no data loss for committed transactions.

## 3. Replication Topologies

### 3.1 Single-Leader (Master-Slave / Primary-Replica)
- **Architecture:** Exactly one designated leader node accepts all writes (INSERT, UPDATE, DELETE). Leader streams change logs to one or more followers (replicas), which accept reads and replication updates.
- **Failover Mechanics:** 
  1. Detect leader failure via heartbeats/timeouts.
  2. Elect a new leader (via consensus or manual intervention).
  3. Reconfigure followers to replicate from the new leader.
- **Challenges:** Single point of failure for writes; failover can result in split-brain or lost un-replicated writes.

### 3.2 Multi-Leader (Master-Master)
- **Architecture:** Multiple nodes accept write operations and act as leaders, replicating their changes to each other and to followers.
- **Use Cases:** Multi-datacenter setups (each datacenter has a local leader for low-latency writes).
- **The Core Challenge: Write Conflicts:** If two clients update the same record concurrently on two different leaders, divergence occurs.
  - *Resolution Strategies:* Last-Write-Wins (LWW - prone to clock drift issues), Conflict-Free Replicated Data Types (CRDTs), Operational Transformation (OT), or custom application-level merge logic.

### 3.3 Leaderless (Quorum-Based / Dynamo-Style)
- **Architecture:** No leader node exists. Clients send writes and reads directly to multiple storage nodes simultaneously (e.g., Cassandra, DynamoDB).
- **Quorum Mechanics:** To guarantee strong consistency, the write and read sets must overlap:
  $$W + R > N$$
  - $N$ = Total number of replicas storing a key.
  - $W$ = Number of nodes that must acknowledge a write.
  - $R$ = Number of nodes that must respond to a read.
- **Anti-Entropy & Read Repair:** Background processes or on-read comparisons detect and heal stale replicas using vector clocks or timestamps.

## 4. Low-Level Replication Mechanisms

### 4.1 Statement-Based Replication
- Primary logs every SQL statement executed (`INSERT`, `UPDATE`).
- *Pitfall:* Non-deterministic functions (`NOW()`, `RAND()`, triggers) cause data divergence between primary and replicas.

### 4.2 Write-Ahead Log (WAL) / Binary Log (Binlog) Shipping
- Primary ships raw byte-level WAL or binlog records. Replicas replay the exact physical page or block modifications.
- *Pitfall:* Tightly couples storage engine format across primary and replicas.

### 4.3 Logical / Row-Based Replication (CDC - Change Data Capture)
- Primary streams logical events (e.g., "Row ID 5 column 'status' changed from 'pending' to 'active'").
- *Pros:* Engine-agnostic, allows replicating between different database versions or architectures (e.g., Postgres to Kafka/Elasticsearch via Debezium).

## 5. Replication Lag & Consistency Anomalies

Asynchronous replication introduces replication lag, leading to observable anomalies for clients:

1. **Read-Your-Writes Violation:** A user updates their profile picture, refreshes the page, and sees the old picture because their read hit a lagging replica.
   - *Solution:* Route user writes and immediate subsequent reads to the primary, or track client session state (monotonic read tokens).
2. **Monotonic Reads Violation:** A user refreshes a feed and sees comments disappear and reappear as requests hit different replicas with varying lag.
   - *Solution:* Ensure a given client always reads from the same replica or a replica guaranteed to be $\ge$ the timestamp of their previous read.
3. **Consistent Prefix Reads Violation:** Observing writes out of causal order (e.g., seeing an answer before the question).

## 6. The Split-Brain Problem & Fencing

### Split-Brain Scenario
Occurs when network partitioning isolates a primary node from its replicas. A replica assumes the primary is dead and promotes itself. Meanwhile, clients continue writing to the old isolated primary. When the network heals, two divergent data streams exist, resulting in catastrophic data corruption.

### Mitigation Strategies
- **Fencing Tokens / Generation Numbers:** Every time a new leader is elected, it receives an monotonically increasing epoch number. Storage nodes or downstream systems reject writes from any leader presenting an older epoch number.
- **Heartbeat Quorums / STONITH ("Shoot The Other Node In The Head"):** Automatically power off or fence off unresponsive nodes via hardware power control before promoting a replacement.

## 7. Interview Deep Dive & Architectural Questions

### Q1: How do you design a zero-data-loss failover pipeline in a PostgreSQL master-slave architecture?
**Answer:** Configure synchronous replication (`synchronous_commit = on` or `remote_apply`) with at least one sync replica, combined with an automated failover manager (e.g., Patroni with etcd/Consul consensus). If the primary fails, Patroni ensures the replica with the exact matching WAL LSN is promoted, and client connection pools are dynamically rerouted via DNS or smart proxies (PgBouncer/HAProxy).

### Q2: Why is Last-Write-Wins (LWW) dangerous in multi-leader or distributed key-value stores?
**Answer:** LWW relies on physical wall-clock timestamps (`gettimeofday()`). Due to clock drift across servers (even with NTP) and network delays, a write that occurred later in real-world time might be assigned an earlier timestamp than a concurrent write, causing silent, permanent data loss.
