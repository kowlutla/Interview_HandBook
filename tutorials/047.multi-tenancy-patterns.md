# 047. Multi-Tenancy Patterns

* **Domain**: Software Architecture & SaaS Design

## 1. Executive Summary & Core Definition

Multi-tenancy is an architectural pattern in which a single instance of a software application and its supporting infrastructure serves multiple distinct customer organizations (tenants). Each tenant operates in a logical sandbox where their data, configurations, user management, and custom behaviors remain completely isolated from other tenants, even though all tenants share the underlying physical infrastructure and application runtime.

In modern SaaS (Software as a Service) design, multi-tenancy is the foundational mechanism for achieving high resource utilization, predictable unit economics, and streamlined fleet-wide deployments. Conversely, single-tenant architectures (dedicated infrastructure per customer) are reserved for enterprise tiers requiring strict regulatory compliance or customized physical isolation.

## 2. Deep-Dive Architecture & Core Principles

### A. Core Tenant Isolation Models

Architects classify multi-tenant systems into three primary isolation models:

```
+-----------------------------------------------------------------+
|                       1. SILO MODEL                             |
|  [Tenant A App]  [Tenant A DB]                                  |
|  [Tenant B App]  [Tenant B DB]                                  |
|  (Maximum Isolation, High Cost, Zero Shared Compute/Storage)    |
+-----------------------------------------------------------------+
|                       2. POOL MODEL                             |
|  [Shared App Pool] ----> [Shared Database (Tenant ID Sharded)]  |
|  (Maximum Efficiency, Lowest Cost, Complex Isolation Logic)     |
+-----------------------------------------------------------------+
|                       3. BRIDGE MODEL                           |
|  [Shared App Pool] ----> [Tenant A DB]                          |
|                    ----> [Tenant B DB]                          |
|  (Hybrid: Shared Application, Isolated Storage)                 |
+-----------------------------------------------------------------+
```

1. **The Silo Model**: Every tenant receives a dedicated stack (compute instances, containers, databases, and network policies). 
   * *Pros*: Zero risk of cross-tenant data leaks, effortless compliance certification (SOC2, HIPAA), simple noisy-neighbor containment.
   * *Cons*: High operational and infrastructure cost; deployment pipelines require iterating across thousands of isolated environments.
2. **The Pool Model**: All tenants share the same application compute pools and database tables. Tenant distinction is enforced logically via a `tenant_id` column on every database table and strict JWT claims or context propagation in the application layer.
   * *Pros*: Lowest infrastructure cost per tenant, high resource efficiency, centralized maintenance.
   * *Cons*: High risk of data leakage via SQL injection or authorization bugs; severe "noisy neighbor" risks where one heavy tenant starves others.
3. **The Bridge Model**: The application tier is pooled (shared workers and API servers), but each tenant maintains a dedicated database or schema.
   * *Pros*: Balances security (isolated data storage) with infrastructure savings (shared application workers).
   * *Cons*: Connection pool exhaustion hazards when dealing with thousands of tenant databases.

### B. Database Multi-Tenancy Strategies

* **Database-per-Tenant**: Complete physical or logical database separation per customer. Ideal for enterprise tiers with strict backup/restore isolation requirements.
* **Schema-per-Tenant**: Shared database engine instance with isolated PostgreSQL schemas or MySQL logical groupings. Provides clean query separation while sharing database buffer pools and connection limits.
* **Shared Table (Row-Level Security - RLS)**: All tenant rows coexist in shared tables. Enforced at the database level via Postgres Row-Level Security policies (`CREATE POLICY tenant_isolation_policy ON orders FOR ALL USING (tenant_id = current_setting('app.current_tenant'))`).

## 3. Comparative Analysis / Trade-Off Matrix

| Dimension | Silo Model (Dedicated) | Pool Model (Shared) | Bridge Model (Hybrid) |
| :--- | :--- | :--- | :--- |
| **Infrastructure Cost** | High (Prohibitive for SMB tier) | Minimal (Optimal utilization) | Moderate |
| **Tenant Onboarding** | Slow (Requires automated provisioning) | Instant (Database insert / config flag) | Moderate (Schema/DB creation) |
| **Noisy Neighbor Risk** | None (Isolated hardware/compute) | High (Requires advanced rate limiting) | Moderate (Compute pooled, DB isolated) |
| **Security Blast Radius** | Low (Compromise affects single tenant) | High (Bug exposes all pooled tenants) | Medium (Data isolated, app shared) |
| **Backup & Restore** | Granular (Per-tenant point-in-time) | Complex (Logical subset extraction) | Granular per database |

## 4. Real-World Industry Use Cases

* **Salesforce (Multi-Tenant Metadata Architecture)**: Pioneer of multi-tenancy. Uses a pooled core database architecture driven by runtime metadata engines that translate tenant-specific customizations into universal database queries.
* **Shopify (Hybrid / Sharded Multi-Tenancy)**: Operates a massive multi-tenant platform where stores are sharded across dedicated database pods, ensuring that high-traffic flash sales on one merchant store do not impact neighboring storefronts.
* **Atlassian Jira / Confluence (Tenant Routing & Pods)**: Migrated from shared monoliths to tenant pods, grouping customers into isolated multi-tenant pods to contain blast radius and simplify geographic data residency compliance.

## 5. Common Pitfalls & Anti-Patterns

1. **Missing Tenant Context in Cache Keys**: Caching objects without prefixing the cache key with `tenant_id` (e.g., caching user profile as `user:123` instead of `tenant:456:user:123`), resulting in catastrophic cross-tenant data leaks.
2. **Unbounded Tenant Resource Consumption**: Failing to implement rate limiting, concurrency caps, or database query timeouts per tenant, allowing a single rogue scraping script or heavy report to degrade service for all other tenants.
3. **Hardcoded Database Connections in Monoliths**: Relying on static application database credentials rather than dynamic tenant lookup middleware that injects connection strings or sets session variables (`SET LOCAL`) per request.
4. **Complex Cross-Tenant Analytics**: Running heavy aggregation queries across pooled tables without proper indexing on `tenant_id`, causing table scans that lock out live transactional traffic.
