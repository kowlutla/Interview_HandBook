## 1. Executive Summary & Philosophy

System Design is the engineering discipline of defining the architecture, components, modules, interfaces, data flows, and infrastructure for a software system to satisfy specified functional and non-functional requirements. 

Unlike coding individual algorithms or micro-features, system design operates at the macro level. It asks:
* *How do we build software that survives hardware failure?*
* *How do we scale from 10 users to 100 million users without rewriting our stack?*
* *How do we balance consistency, availability, latency, and cost?*

This masterclass tutorial establishes the foundational mindset, structured frameworks, and mental models required to approach any complex architectural challenge with confidence.

## 2. Core Definitions & Fundamental Terminology

Before designing systems, you must master the vocabulary used by architects and interviewers.

| Term | Definition | Primary Objective |
| :--- | :--- | :--- |
| **High-Level Design (HLD)** | The overarching architectural blueprint showing major components, data stores, load balancers, and third-party services. | Define system macro-structure and integration boundaries. |
| **Functional Requirements** | What the system *must do* (features, user actions, API endpoints, core business logic). | Ensure product utility and user needs are met. |
| **Non-Functional Requirements (NFRs)** | How the system *behaves* under operational constraints (scalability, availability, latency, security, fault tolerance). | Ensure operational excellence and enterprise grade reliability. |
| **Scalability** | The capability of a system to handle growing amounts of work by adding resources to the system (Scale Up/Out). | Maintain performance under increasing load. |
| **Availability** | The percentage of time a system remains operational and accessible (`uptime`). | Minimize downtime (`99.999%` = ~5.26 minutes/year). |
| **Latency vs. Throughput** | Latency is the time taken to process a request (RTT); throughput is the number of requests processed per second (QPS/TPS). | Maximize throughput while minimizing tail latency (p99). |

## 3. The Anatomy of a System Design Problem

Every system design problem—whether in a FAANG interview or real-world production architecture—follows a rigorous lifecycle. Understanding this lifecycle prevents chaotic engineering and ensures holistic coverage.

```
+--------------------------------------------------------------------------+
|                        SYSTEM DESIGN LIFECYCLE                           |
+--------------------------------------------------------------------------+
  [Step 1: Clarify Requirements] --> Define scope, scale, constraints
        |
        v
  [Step 2: Estimation & Sizing] --> Back-of-the-envelope calculations (QPS, Storage)
        |
        v
  [Step 3: High-Level Architecture] --> Core components, API design, Data flow
        |
        v
  [Step 4: Deep Dive & Bottlenecks] --> Resolving failure modes, scaling specific services
        |
        v
  [Step 5: Trade-offs & Wrap-up] --> Justifying choices, identifying limitations
```

### 3.1 Step 1: Clarifying Requirements
Never jump straight into drawing boxes. Begin by separating requirements into two buckets:
* **Functional Requirements**: 
  * *Example (URL Shortener)*: Users enter a long URL and get a short alias; visiting the short alias redirects to the original URL.
* **Non-Functional Requirements (NFRs)**:
  * *Example*: Highly available (99.99%), low redirection latency (<100ms), fault-tolerant, secure.
* **Out-of-Scope**: Explicitly state what you are *not* building (e.g., "Analytics dashboard is out of scope for this MVP").

### 3.2 Step 2: Back-of-the-Envelope Estimations
Math is the architect's compass. You must quickly estimate storage, bandwidth, and QPS using standard hardware latency numbers and arithmetic approximations.
* *Example*: 100M daily active users (DAU), each writing 2 posts/day.
  * Write QPS = $\frac{200,000,000 \text{ posts}}{86,400 \text{ seconds}} \approx 2,315 \text{ writes/sec}$.
  * Peak QPS (typically 3x average) $\approx 7,000 \text{ QPS}$.

## 4. The Mindset of an Architect: Trade-offs Over Silver Bullets

In system design, **there are no correct answers—only trade-offs.** Every architectural decision incurs a cost:
* If you optimize for **Consistency**, you sacrifice **Availability** (CAP Theorem).
* If you optimize for **Write Throughput**, you sacrifice **Immediate Read Consistency**.
* If you optimize for **Cost**, you sacrifice **Ultra-low Latency**.

An elite engineer does not claim their design has zero flaws; instead, they articulate *why* a particular trade-off was chosen given the business domain and constraints.

---

## 5. Common Pitfalls & Anti-Patterns to Avoid

1. **Over-Engineering Early**: Proposing a 50-microservice Kubernetes mesh for a startup with 50 daily users.
2. **Single Point of Failure (SPOF)**: Relying on a single database instance or load balancer without hot standby or failover.
3. **Ignoring Bottlenecks**: Designing a system without identifying where the first bottleneck will occur (e.g., database locks, network bandwidth).
4. **Vague Estimates**: Guessing numbers instead of using logical approximations.

---

## 6. Best Practices Checklist for System Design

- [ ] Always start by clarifying scope, scale, and constraints.
- [ ] Perform back-of-the-envelope estimations to anchor your design in reality.
- [ ] Sketch the high-level architecture before diving into granular component details.
- [ ] Explicitly discuss trade-offs for every major component choice.
- [ ] Design for failure—assume every component will fail at some point.
