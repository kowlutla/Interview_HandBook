# 024. Database Sharding and Partitioning: Masterclass

## 1. Introduction & Definitions

When a single database instance exhausts vertical scaling limits (CPU, RAM, disk I/O, storage capacity), **Horizontal Partitioning (Sharding)** is required. 

- **Partitioning (Intra-Database):** Splitting a large table into smaller physical pieces within the *same* database instance (e.g., partitioning a massive `logs` table by date ranges).
- **Sharding (Inter-Database):** Distributing subsets of data across *multiple independent database instances* (nodes), which may reside on different physical servers or geographic regions.

---

## 2. Partitioning Types

### 2.1 Vertical Partitioning
Splitting a table by columns rather than rows.
- **Example:** A `users` table contains frequently accessed profile columns (`id`, `username`, `email`) and rarely accessed large columns (`bio`, `avatar_blob`, `settings_json`). Vertical partitioning splits this into `user_profiles` (hot storage) and `user_details` (cold/blob storage).
- **Benefits:** Better cache locality, reduced I/O footprint for common queries.

### 2.2 Horizontal Partitioning (Table Partitioning)
Splitting a table by rows within the same database instance.
- **Range Partitioning:** Rows are assigned to partitions based on ranges of a column value (e.g., orders partitioned by year: `orders_2024`, `orders_2025`).
- **List Partitioning:** Partitioned by explicit list membership (e.g., region: `users_eu`, `users_us`).
- **Hash Partitioning:** Uses a hash function on a partition key to distribute rows uniformly across partitions.

---

## 3. Sharding Strategies & Routing

Choosing the right **Shard Key** is the single most critical decision in sharding design; a poor shard key leads to data hotspots and unroutable queries.

### 3.1 Range-Based Sharding
- **Mechanism:** Data is partitioned based on continuous ranges of a key (e.g., User IDs 1-100,000 on Shard A; 100,001-200,000 on Shard B).
- **Pros:** Easy range queries (`WHERE user_id BETWEEN ...`).
- **Cons:** Hotspots. If most active users fall into a newly created range (e.g., recent user IDs), Shard B absorbs 90% of the traffic while Shard A sits idle.

### 3.2 Hash-Based Sharding
- **Mechanism:** Applies a hash function to the shard key and applies modulo arithmetic:
  $$\text{Shard ID} = \text{hash}(\text{ShardKey}) \pmod N$$
- **Pros:** Uniform data distribution across all shards.
- **Cons:** Resharding is painful. When adding a new shard ($N \to N+1$), almost every key must be rehashed and migrated to a new location (mitigated by **Consistent Hashing**). Range queries are impossible without querying all shards (scatter-gather).

### 3.3 Directory-Based (Lookup Service) Sharding
- **Mechanism:** Maintains a central lookup database or service that maps shard keys to physical shard locations (`user_id 1234 -> Shard_C`).
- **Pros:** Highly flexible; easy to rebalance data by updating routing tables.
- **Cons:** The lookup service becomes a single point of failure and adds network latency to every query.

---

## 4. Architectural Challenges & Solutions

### 4.1 Cross-Shard Joins & Scatter-Gather Queries
If a query requires joining `users` (sharded by `user_id`) and `orders` (sharded by `order_id`), a single database join is impossible.
- **Solution:** Denormalize data, enforce co-location (shard orders using `user_id` as part of the composite shard key), or perform application-level scatter-gather queries (query all shards in parallel and merge results).

### 4.2 Unique ID Generation in Sharded Systems
Auto-incrementing primary keys (`SERIAL` / `IDENTITY`) fail in sharded architectures because multiple independent databases would generate duplicate IDs.
- **Solutions:**
  - **UUID v4:** 128-bit random strings. *Consequence:* Poor B-Tree index locality due to random insertion patterns.
  - **UUID v7 / Snowflake IDs (Twitter Snowflake):** Time-ordered 64-bit integers composed of timestamp, worker/datacenter ID, and sequence counter. Preserves chronological insertion order while guaranteeing global uniqueness across shards.

### 4.3 Rebalancing & Resharding
When storage capacity is breached, adding new shards requires migrating terabytes of data with minimal downtime. Consistent hashing or virtual shard slots (e.g., MySQL Vitess keyspaces with 1024 virtual shards mapped to physical nodes) streamline slot migration without full dataset rehashes.

---

## 5. Sharding Middleware & Ecosystem
- **Vitess (MySQL):** Google's open-source sharding proxy for MySQL, handling connection pooling, query routing, and automated resharding.
- **Citus (PostgreSQL):** PostgreSQL extension that transforms Postgres into a distributed database via columnar and distributed tables.
- **Apache ShardingSphere:** Ecosystem providing distributed transaction and sharding middleware for Java/JDBC applications.

## 6. Interview Deep Dive & Architectural Questions

### Q1: How do you choose an optimal shard key for a global chat application?
**Answer:** For a chat app, sharding by `channel_id` or `conversation_id` is ideal because messages within a conversation are accessed together, avoiding cross-shard queries. Sharding by `user_id` would require scatter-gather queries for group chats involving multiple users.

### Q2: What happens during a resharding event in hash-based sharding without virtual nodes?
**Answer:** Without virtual nodes, changing the number of shards $N$ invalidates the modulo calculation (`hash % N`), requiring nearly 100% of data to be re-hashed and copied across physical nodes, causing massive network I/O and potential downtime.
