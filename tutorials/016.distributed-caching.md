# 016. Distributed Caching: Sharding, Replication, Consistency, and Memcached/Redis

> **The Definitive, Comprehensive Masterclass on Multi-Node Caching Topologies, Consistent Hashing, Data Partitioning, and Production Caching Clusters.**
> *Serving as a complete, authoritative reference covering Memcached vs. Redis, cluster sharding, replication strategies, persistence models, and high-availability caching.*

---

## 1. Executive Summary & Philosophy

Single-node caching systems have fundamental limits: maximum memory capacity, single point of failure (SPoF), and throughput constraints bounded by a single CPU and network interface. As applications scale to millions of users, distributed caching becomes essential to achieve horizontal scalability, fault tolerance, and geo-distributed low latency.

A **Distributed Cache** partitions cached data across multiple nodes in a cluster, enabling petabyte-scale caching capacity, automatic failover, and geographic replication.

---

## 2. Memcached vs. Redis: Technology Comparison

These are the two dominant distributed caching technologies, each with distinct design philosophies:

| Feature | **Memcached** | **Redis** |
| :--- | :--- | :--- |
| **Data Model** | Pure Key-Value (Strings, limited structures) | Rich Data Structures: Strings, Lists, Sets, Sorted Sets, Hashes, HyperLogLog, Bitmaps, Streams, Geospatial indexes. |
| **Persistence** | None (memory-only) | Optional: RDB (point-in-time snapshots), AOF (Append-Only File with configurable fsync policies). |
| **Clustering** | Distributed via client-side sharding (consistent hashing) | Native Cluster mode: Hash slots (16384 slots), automatic partitioning, master-replica replication. |
| **Replication** | None (replication must be implemented client-side or via third-party tools like repcached). | Master-Replica replication out-of-the-box; supports read replicas for read scalability. |
| **Use Case** | Simple, raw caching with maximal throughput. | Caching + Session store + Message queue + Rate limiting + Leaderboards + Pub/Sub. |
| **Language / Ecosystem** | C, libmemcached (C/C++, Python, PHP, Ruby clients). | C, official clients in virtually every language; rich module ecosystem (RediSearch, RedisJSON, RedisBloom). |

## 3. Sharding and Data Partitioning Strategies

Distributing keys across cache nodes is the core challenge of distributed caching:

### 3.1 Range-Based Sharding
*   **Mechanism**: Partition keys by key range (e.g., `user:0000-0999` → Node 1, `user:1000-1999` → Node 2).
*   **Pros**: Simple range scans (e.g., fetching all user IDs in a range).
*   **Cons**: Hotspots (e.g., celebrity user IDs concentrated in one range) cause uneven load distribution.

### 3.2 Consistent Hashing (Virtual Nodes / VNods)
*   **Mechanism**: Keys and nodes are placed on a hash ring (typically using MD5 or SHA-1). A key is assigned to the next node clockwise on the ring.
*   **Virtual Nodes**: Each physical node is assigned multiple virtual points on the ring to improve distribution and reduce rebalancing when nodes join/leave.
*   **Pros**: Minimal key remapping during scaling events (only keys between the joining node and its predecessor are moved).

## 4. Replication and High Availability

Distributed caches must survive node failures without service interruption.

*   **Master-Replica Architecture**: One master node handles all writes; one or more replicas asynchronously replicate data.
    *   On master failure: Failover promotes a replica to master (handled by Redis Sentinel for Redis, or client-side failover logic).
*   **Multi-Master / Active-Active**: Multiple masters accept writes simultaneously. Conflict resolution strategies (CRDTs, vector clocks, or last-write-wins) must be applied.

---

## 5. Persistence Trade-offs

While caching is traditionally in-memory, durability matters for session stores and data that cannot be recomputed from the primary database:

*   **Redis RDB**: Fork-based point-in-time snapshotting. Low overhead but incurs brief blocking during fork.
*   **Redis AOF**: Appends every write command to a log. Configurable fsync policies (`everysec`, `always`). Higher durability but larger file sizes.
*   **Memcached**: Pure memory-only. No persistence; if a node restarts, its cache is empty.

## 6. Real-World Industry Examples

*   **Twitter (Redis)**: Uses Redis heavily for timelines, social graphs, and engagement metrics, leveraging its rich data structures and high throughput.
*   **Instagram (Redis)**: Uses Redis for activity feeds and follower counts, storing sorted sets for efficient ranking and range queries.
*   **Netflix (Evcache / Memcached)**: Netflix developed Evcache (an extension of Memcached) for session data, recommendations, and metadata caching across AWS regions.

---

## 7. Common Pitfalls & Anti-Patterns

1.  **Network Partitions Causing Split-Brain**: In active-active clusters, network partitions can cause both sides to accept divergent writes, leading to data divergence.
2.  **Neglecting Cold Start / Cache Warm-Up**: When restarting a cache cluster, starting with an empty cache causes a thundering herd of database queries (the "cache miss storm").
3.  **Oversharding**: Creating too many small shards increases coordination overhead, latency, and operational complexity without meaningful throughput gains.
