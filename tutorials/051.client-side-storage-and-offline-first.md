# 051. Client-Side Storage & Offline-First Architecture

## Overview
Modern web applications must deliver high reliability, instant responsiveness, and seamless functionality regardless of network conditions. An **offline-first architecture** treats offline capability as a first-class citizen rather than an afterthought, leveraging robust client-side storage mechanisms, service workers, and local-first data synchronization patterns.

---

## 1. Storage Mechanisms Comparison

Choosing the correct storage mechanism depends on data size, structure, query complexity, and persistence guarantees.

| Mechanism | Storage Limit | Scope / Persistence | Access Model | Best Used For |
| :--- | :--- | :--- | :--- | :--- |
| **LocalStorage** | ~5MB per origin | Persistent until explicit removal | Synchronous (blocking) | Small user preferences, theme toggles, auth tokens |
| **SessionStorage** | ~5MB per origin | Tab session lifespan | Synchronous (blocking) | Transient form state, wizard step tracking |
| **IndexedDB** | GBs (depends on disk space) | Persistent (unless evicted under storage pressure) | Asynchronous (non-blocking) | Large relational datasets, cached API responses, offline mutations |
| **Cache API** | GBs (shared pool) | Persistent via Service Worker lifecycle | Asynchronous (Request/Response pairs) | Static assets, HTML shells, images, API asset caching |
| **Origin Private File System (OPFS)** | GBs (shared pool) | Persistent | High-performance synchronous/asynchronous file handles | Large binary assets, SQLite WASM databases, media editing buffers |

## 2. Deep Dive: Storage APIs

### A. IndexedDB Architecture
IndexedDB is a transactional, asynchronous, object-oriented database built into the browser.
- **Database & Object Stores**: Data is stored in Object Stores (analogous to tables), indexed by key paths or key generators.
- **Transactions**: All read/write operations require transactions (`readonly`, `readwrite`, `versionchange`). Transactions guarantee ACID compliance within the browser session.
- **Cursors**: For iterating over large datasets efficiently without loading all records into memory at once.

```javascript
// Example: Opening IndexedDB and storing an offline mutation
const openDB = () => {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open('OfflineAppDB', 1);
    
    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      if (!db.objectStoreNames.contains('outbox')) {
        db.createObjectStore('outbox', { keyPath: 'id', autoIncrement: true });
      }
    };
    
    request.onsuccess = (event) => resolve(event.target.result);
    request.onerror = (event) => reject(event.target.error);
  });
};
```

### B. Cache API & Service Workers
The Cache API stores pairs of `Request` and `Response` objects. It is designed to be used inside **Service Workers** to intercept network requests and serve cached assets instantaneously.

```javascript
// Service Worker Install Event: Pre-caching critical assets
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1-core-cache').then((cache) => {
      return cache.addAll([
        '/',
        '/index.html',
        '/styles.css',
        '/app.js',
        '/offline.html'
      ]);
    })
  );
});
```

## 3. Caching & Fetch Strategies

1. **Cache-First (Falling back to Network)**
   - *Use Case*: Static assets (fonts, images, CSS, JS bundles).
   - *Flow*: Check cache -> if found, return -> else fetch from network, store in cache, return.

2. **Network-First (Falling back to Cache)**
   - *Use Case*: Dynamic data (user feeds, dashboard metrics, real-time prices).
   - *Flow*: Fetch from network -> if successful, update cache and return -> else return cached response.

3. **Stale-While-Revalidate**
   - *Use Case*: Non-critical dynamic content where instant load is preferred over absolute freshness.
   - *Flow*: Return cached response immediately while simultaneously fetching fresh data from network in the background to update cache for next load.

## 4. Offline-First Architecture Patterns

### A. The Outbox Pattern (Client-Side)
When a user performs a mutation (e.g., creating a post, submitting an order) while offline:
1. **Capture**: The action is intercepted and written to a local IndexedDB `outbox` queue.
2. **Optimistic Update**: The local UI updates instantly to reflect success.
3. **Queue Processing**: When network connectivity is restored (detected via `navigator.onLine` or `online` event), the Service Worker or application layer processes the outbox sequentially or in parallel with idempotency keys.

### B. Background Sync API
Instead of relying solely on the main thread being active, applications use the **Background Synchronization API** to defer actions until the user has stable connectivity.

```javascript
// Registering a background sync task
navigator.serviceWorker.ready.then((registration) => {
  return registration.sync.register('sync-outbox-mutations');
});
```

## 5. Storage Management & Eviction

Browsers manage disk space under strict quotas. When disk space is low, the browser may evict data according to an **LRU (Least Recently Used)** policy under **Best-Effort** persistence.
- **Persistent Storage Request**: Applications can request persistent storage via `navigator.storage.persist()`, preventing automatic browser eviction unless explicitly triggered by user action.
- **Quota Estimation**: Always check available storage using `navigator.storage.estimate()` before large asset downloads.
