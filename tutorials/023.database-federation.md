# 023. Database Federation: Masterclass

## 1. Introduction & Core Concept

**Database Federation** (also known as **Functional Partitioning** or **Domain Splitting**) is an architectural pattern where a monolithic database is split into multiple distinct, independent databases based on business domains or functional boundaries.

### Federation vs. Sharding
- **Federation (Functional Partitioning):** Splits *different* tables/domains into separate databases (e.g., `User_DB` handles user profiles, `Product_DB` handles catalog items, `Order_DB` handles transactions). Each database stores a completely different schema and dataset.
- **Sharding (Horizontal Partitioning):** Splits the *same* table across multiple database instances based on a shard key (e.g., users 1-1,000,000 in Shard A, 1,000,001-2,000,000 in Shard B). Every shard shares the identical schema.

## 2. Domain-Driven Database Decomposition

In a federated architecture, boundaries align closely with Domain-Driven Design (DDD) Bounded Contexts.

### Example Architecture: E-Commerce Platform
Instead of a single monolithic database containing `users`, `products`, `orders`, `inventory`, and `payments`, the system decomposes into:
1. **User Service DB:** Manages authentication, profiles, addresses.
2. **Catalog Service DB:** Manages products, categories, search attributes.
3. **Order Service DB:** Manages cart checkouts, order lifecycles, and status.
4. **Payment Service DB:** Manages invoices, payment gateways, and ledger entries.

## 3. Challenges & Architectural Solutions

While federation eliminates single-point-of-contention bottlenecks and scales capacity, it introduces significant distributed systems challenges.

### 3.1 Cross-Database Joins & Queries
In a monolith, joining `Users` and `Orders` is a single SQL query (`SELECT * FROM users JOIN orders ON ...`). In a federated architecture, foreign key constraints across databases are **impossible** to enforce at the database engine level.

#### Solutions:
1. **Application-Level Joins:** Service A fetches user details, Service B fetches order details, and the application combines them in memory. (Prone to N+1 query problems; mitigated via batching/caching).
2. **Data Denormalization / Duplication:** Store a read-only copy of necessary user attributes (e.g., username, email) directly inside the Order record.
3. **CQRS & Data Sync (CDC):** Stream changes from User DB to Order DB using Change Data Capture (Debezium/Kafka) to maintain materialized views.

### 3.2 Distributed Transactions (ACID across Boundaries)
If an order placement requires updating `Order_DB`, decrementing stock in `Product_DB`, and debiting funds in `Payment_DB`, a local database transaction (`BEGIN ... COMMIT`) is insufficient because ACID transactions do not span multiple independent database instances.

#### Solutions:
1. **Two-Phase Commit (2PC):** A coordinator protocol (Prepare phase -> Commit phase). *Drawback:* Blocking protocol, prone to high latency and cascading failures during network partitions.
2. **Saga Pattern (Orchestration or Choreography):** A sequence of local transactions where each step updates a service DB and emits an event. If a step fails, compensating transactions (rollbacks) are executed sequentially in reverse.
3. **Transactional Outbox Pattern:** Ensures reliable message publishing alongside database updates to prevent dual-write failures between the DB and message broker.

## 4. Operational Benefits & Trade-offs

### Benefits
- **Independent Scaling & Tuning:** High-throughput order databases can run on high-performance SSD NVMe clusters, while infrequently accessed audit logs run on cheaper storage.
- **Blast Radius Isolation:** A runaway query or corruption in the Product DB does not take down User authentication or Payment processing.
- **Team Autonomy:** Microservices teams own their database schemas without locking shared database tables.

### Trade-offs
- **Operational Complexity:** Managing multiple database instances, backups, monitoring, connection pooling, and migrations.
- **Lack of ACID Guarantees:** Developers must handle eventual consistency and compensating logic in application code.

## 5. Interview Deep Dive & Architectural Questions

### Q1: When should you transition from a monolithic database to a federated database architecture?
**Answer:** Transition when table contention, locking overhead, and connection pool exhaustion on the single monolithic database bottleneck development velocity and database throughput, and when clear bounded business domains (e.g., billing vs. inventory) emerge that rarely require synchronous multi-domain joins.

### Q2: How do you handle referential integrity (foreign keys) when databases are federated?
**Answer:** Referential integrity must be enforced at the application layer or via asynchronous validation services. For example, the Order service must verify via a synchronous gRPC call or an asynchronous event message that the referenced `user_id` exists in the User service before inserting an order.
