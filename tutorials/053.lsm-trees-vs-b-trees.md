# 059. LSM-Trees vs. B-Trees

## Overview
Understanding storage engine indexing structures is fundamental to optimizing for read-heavy vs. write-heavy workloads.

## B-Tree (Balanced Tree)
A classical balanced tree structure used in traditional relational databases (e.g., MySQL/InnoDB).

- **Structure**: Data is stored in-place in fixed-size pages.
- **Reads**: Predictable, efficient $O(\log n)$ performance, ideal for point lookups and range scans.
- **Writes**: Slower, requiring in-place disk page updates, random I/O, and page splits/merges.

## LSM-Tree (Log-Structured Merge-Tree)
Optimized for high write throughput (e.g., Cassandra, RocksDB, LevelDB).

- **Structure**: Writes go to memory (MemTable) and are flushed to append-only immutable files (SSTables).
- **Writes**: Extremely fast due to sequential I/O and low write amplification.
- **Reads**: Requires checking multiple SSTables and MemTables; relies on **Bloom filters** and caching to reduce read amplification.
- **Background Overhead**: Compaction processes merge SSTables to reclaim space, remove tombstones, and optimize read paths, consuming significant CPU and I/O.

## Performance Trade-offs

| Feature | B-Tree | LSM-Tree |
| :--- | :--- | :--- |
| **Write Workload** | Moderate | High (Excellent) |
| **Read Workload** | High (Predictable) | Moderate (Variable) |
| **I/O Pattern** | Random | Sequential |
| **Space Efficiency** | Moderate (Fragmentation) | Low (Compaction overhead) |
