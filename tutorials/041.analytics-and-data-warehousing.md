# 041. Analytics and Data Warehousing Masterclass

## 1. Overview and Core Concepts

Modern data architecture separates operational databases (OLTP) optimized for fast transactional writes and point reads from analytical processing systems (OLAP) optimized for high-throughput scans, complex aggregations, and multi-dimensional analysis over petabyte-scale datasets.

### OLTP vs OLAP Comparison Matrix
| Dimension | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |
| :--- | :--- | :--- |
| **Primary Workload** | High concurrency, short CRUD operations | Low concurrency, complex multi-table joins, scans |
| **Data Schema** | Highly normalized (3NF/BCNF) | Denormalized (Star / Snowflake schema), columnar |
| **Access Pattern** | Row-oriented (B-Trees, LSM trees) | Column-oriented (Vectorized execution, compression) |
| **Latency SLA** | Milliseconds ($< 10\text{ms}$) | Seconds to minutes (depending on data volume) |
| **Storage Engine** | Row store (InnoDB, PostgreSQL Heap) | Column store (Parquet, ORC, proprietary columnar blobs) |

## 2. Storage Architectures: Row vs. Column Stores

### Row-Oriented Storage (OLTP)
Data is stored row by row on disk pages. When fetching a record, the entire row is loaded into memory.
- **Advantage**: Extremely efficient for single-row lookups and updates (`SELECT * FROM users WHERE id = 123`).
- **Disadvantage**: Inefficient for analytics. To compute the average age of users, the storage engine must scan entire rows, loading unnecessary columns (e.g., bio, password hash, profile settings) into memory and violating cache locality.

### Column-Oriented Storage (OLAP)
Data is stored column by column. All values for `column_a` are stored contiguously on disk, followed by `column_b`.
- **Advantage**: 
  - **I/O Reduction**: Only the columns referenced in the query are read from disk.
  - **Compression**: Data of the same type stored contiguously achieves massive compression ratios (e.g., Run-Length Encoding, Dictionary Encoding, Bit-Packing, Delta Encoding).
  - **Vectorized Execution**: Modern CPU SIMD (Single Instruction, Multiple Data) instructions process entire blocks of column values in a single CPU cycle.

## 3. Data Warehouse Modeling Techniques

### Dimensional Modeling (Ralph Kimball Approach)
- **Fact Tables**: Store quantitative measurements of business events (e.g., `sales_amount`, `quantity_sold`, `latency_ms`). Contain foreign keys to dimensions and additive/semi-additive/non-additive numerical metrics.
- **Dimension Tables**: Store descriptive context surrounding business processes (e.g., `customer_dim`, `product_dim`, `time_dim`).
- **Schemas**:
  - **Star Schema**: Fact table at the center directly linked to denormalized dimension tables. Faster query execution due to fewer joins.
  - **Snowflake Schema**: Dimension tables are normalized into sub-dimensions (e.g., `product_dim` links to `category_dim`). Reduces data redundancy at the cost of complex joins.

### Data Vault Modeling
Designed for enterprise-scale data integration, auditability, and historical tracking across disparate source systems.
- **Hubs**: Business keys with unique identifiers (e.g., `customer_id`).
- **Links**: Relationships between Hubs (e.g., `customer_places_order`).
- **Satellites**: Descriptive attributes attached to Hubs and Links with full temporal tracking (`valid_from`, `valid_to`, `hash_diff`).

## 4. Modern Data Architecture Paradigms

### ETL vs. ELT
- **ETL (Extract, Transform, Load)**:
  - Transformation happens before loading, typically in an external staging compute engine (e.g., Spark, Informatica).
  - Used when data must be scrubbed or anonymized before entering restricted storage.
- **ELT (Extract, Load, Transform)**:
  - Raw data is loaded directly into the data warehouse object store.
  - Transformations are executed inside the data warehouse using native distributed compute (e.g., dbt on Snowflake/BigQuery). Leverages cloud elasticity and massively parallel processing (MPP).

### Lakehouse Architecture
Combines the reliability, ACID transactions, and governance of data warehouses with the low-cost, flexible storage of data lakes (Object storage: AWS S3, Google Cloud Storage, Azure Blob).
- **Storage Formats**: Apache Iceberg, Apache Hudi, Delta Lake.
- **Key Features**:
  - **ACID Transactions**: Multiple concurrent readers and writers without corrupting data files.
  - **Time Travel & Rollback**: Query previous table snapshots via transaction logs.
  - **Schema Evolution**: Add, drop, or rename columns safely without rewriting entire datasets.
  - **Open Table Formats**: decoupling storage from compute engines (Trino, Spark, DuckDB, Snowflake).

## 5. Distributed Query Execution and MPP Engine Mechanics

Massively Parallel Processing (MPP) architectures distribute query execution across a cluster of independent nodes.

### Query Execution Phases
1. **Parser & Optimizer**: Converts SQL into an Abstract Syntax Tree (AST), applies cost-based optimization (CBO) to determine join orders, filter pushdowns, and aggregation strategies.
2. **Distributed Query Planner**: Splits the execution plan into stages separated by data exchange boundaries.
3. **Execution Operators**:
   - **Table Scan**: Reads columnar chunks from cloud storage with partition pruning and predicate pushdown.
   - **Hash Join**: Builds an in-memory hash table on the build side (smaller relation) and probes it with the stream side (larger relation). In distributed MPP, data is redistributed (shuffled) across nodes using a hash of the join key.
   - **Aggregation**: Two-phase aggregation (local partial aggregation followed by a shuffle and final global aggregation) to minimize network I/O.

## 6. Real-World Case Study: Petabyte-Scale Analytics Platform

### Architecture Requirements
- **Ingestion Volume**: 10 billion events/day ($~5\text{TB/day}$).
- **Query Latency**: Sub-second dashboard responses for operational analytics; $< 30\text{s}$ for heavy ad-hoc aggregations.
- **Storage**: Multi-tier storage with automatic cold-storage lifecycle policies.

### End-to-End Pipeline Design
```
[Client Apps / Clickstream]
       │
       ▼
  [Kafka / Kinesis]
       │
       ▼
 [Streaming Ingestion (Flink / Spark Streaming)]
       │
       ├─────────────────────────┐
       ▼                         ▼
[Real-Time OLAP]          [Cloud Object Store (S3)]
 (ClickHouse / Druid)             │
                          (Apache Iceberg)
                                 │
                                 ▼
                          [Cloud Data Warehouse]
                          (Snowflake / BigQuery)
```

1. **Ingestion Layer**: Events stream into Apache Kafka, buffered for fault tolerance.
2. **Real-Time Tier**: Apache Flink consumes Kafka streams and loads data into ClickHouse or Apache Pinot for ultra-low latency sub-second dashboard queries.
3. **Batch Tier**: Daily batch jobs persist raw partitioned Parquet/Iceberg files into AWS S3.
4. **Analytical Serving Tier**: Snowflake or BigQuery queries Iceberg tables directly via external catalogs, combining historical cold data with fresh hot partitions seamlessly.

## 7. Failure Modes, Edge Cases, and Mitigations

- **Data Skew**: Uneven distribution of partition or join keys overloading specific cluster nodes.
  - *Mitigation*: Salt join keys with random prefixes, or use broadcast joins for small dimension tables.
- **Small File Problem**: High frequency of streaming inserts creates millions of tiny Parquet files, degrading metadata performance and read throughput.
  - *Mitigation*: Implement scheduled compaction / compaction daemons (e.g., Iceberg compaction, Delta Optimize).
- **Concurrency Bottlenecks**: Heavy ad-hoc analytical queries starving high-priority executive dashboards.
  - *Mitigation*: Query acceleration services, warehouse compute clustering, virtual warehouse isolation, and workload management (WLM) query queuing rules.

## 8. Interview Deep-Dive Questions & Answers

### Q1: How would you design a real-time analytics system that handles 100,000 writes per second while supporting sub-second complex aggregations?
**Answer**: 
- **Storage Engine**: Use a column-oriented real-time OLAP database like ClickHouse or Apache Druid, which supports append-optimized immutable data parts merged in the background (LSM-tree inspired columnar storage).
- **Buffer & Partitioning**: Partition data by time (hourly/daily) and cluster by high-cardinality dimensions. Place Apache Kafka in front to smooth out traffic spikes and decouple producers from consumers.
- **Indexing**: Utilize primary index sparse sorting keys, skip indices (min-max indexes), and bloom filters to prune unnecessary data blocks during query execution without maintaining heavy traditional B-Tree indexes.

### Q2: Compare Apache Iceberg table format with traditional Hive-style partitioned tables.
**Answer**:
- **Hive Partitions**: Rely on directory structures (`/date=2026-10-17/region=us/`). Adding/dropping partitions requires directory renames or metadata repairs. Pruning relies on listing directory paths, which is slow on cloud object stores. Concurrent writes often corrupt partition directories.
- **Apache Iceberg**: Uses explicit file-level metadata tracked in JSON commit logs and Avro manifest files. Supports hidden partitioning (automatically computes derived columns), ACID snapshot isolation, time travel, schema evolution without rewriting data files, and atomic commits via optimistic concurrency control.
