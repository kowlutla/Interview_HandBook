# 021. Database Indexing and Storage: Masterclass

## 1. Introduction & Foundational Concepts

In modern distributed systems and relational/NoSQL databases, the choice of storage engine and indexing mechanism dictates query latency, throughput, write amplification, and durability. 

When data exceeds memory capacity (RAM), disk I/O becomes the primary bottleneck. Storage engines manage how data is structured on disk and in memory, balancing random vs. sequential I/O, CPU overhead, and space utilization.

### The Storage Hierarchy & I/O Costs
- **RAM (L1-L3 Cache & Main Memory):** Nanosecond access times. Volatile.
- **NVMe / SSD:** Microsecond access times. Block-based (typically 4KB blocks). Excellent random read performance; wear-leveling considerations for writes.
- **HDD:** Millisecond access times. Seek time and rotational latency dominate random I/O. Sequential I/O is orders of magnitude faster than random I/O.

## 2. Storage Engine Architectures

Database storage engines generally fall into two primary architectural paradigms: **B-Tree based engines** (Read-Optimized / In-Place Update) and **Log-Structured Merge-Tree (LSM-Tree) based engines** (Write-Optimized / Out-of-Place Update).

### 2.1 B-Tree (and B+ Tree) Storage Engines
Used by InnoDB (MySQL), PostgreSQL (Heap + B-Tree indexes), Oracle, and SQL Server.

#### Internal Structure
- **Pages (Blocks):** Data is read and written in fixed-size pages (e.g., 8KB or 16KB).
- **B+ Tree Variant:** Internal nodes store keys and child pointers acting as a routing guide. Leaf nodes store actual data records (Clustered Index) or pointers to heap files (Secondary Index) and are linked as a doubly linked list for efficient range scans.
- **Balanced Tree:** All leaf nodes reside at the same depth, guaranteeing $O(\log N)$ search, insert, and delete complexity.

```
       [ Root Node: 50 | 100 ]
           /       |       \
          /        |        \
    [10 | 30]   [60 | 80]  [110 | 130]  <- Internal Nodes
     /    \      /    \     /     \
   [Leaf] [Leaf][Leaf][Leaf][Leaf][Leaf] <- Linked List of Leaves
```

#### Mechanics of Writes and Updates
- **In-Place Updates:** When a record is updated, the database locates the page in the buffer pool (memory), modifies it in place, and marks the page as "dirty".
- **Write-Ahead Log (WAL):** To ensure atomicity and durability (ACID) against crashes, every modification is first appended to a sequential WAL on disk before the dirty page is written.
- **Buffer Pool Management:** Uses LRU (Least Recently Used) variants (such as 2Q or midpoint insertion policy) to cache disk pages in memory. Dirty pages are periodically flushed to disk by background checkpoints.

### 2.2 Log-Structured Merge-Tree (LSM-Tree) Storage Engines
Used by RocksDB, LevelDB, Cassandra, ScyllaDB, and SQLite (WITHOUT rowids in certain configurations / extensions, though SQLite is primarily B-Tree).

#### Internal Structure
- **MemTable:** In-memory buffer (typically Skiplist, Red-Black Tree, or Vector) where all writes (inserts, updates, deletes) are initially landed.
- **WAL (Commit Log):** Ensures durability of writes before they enter the MemTable.
- **SSTables (Sorted String Tables):** Immutable files on disk containing key-value pairs sorted by key, accompanied by an index and Bloom filters.
- **Compaction:** Background process that merges and sorts SSTables from level to level (Leveled Compaction or Size-Tiered Compaction) to remove stale versions and tombstones.

```
Incoming Write ──> [ WAL (Disk) ]
                        │
                        ▼
                   [ MemTable (RAM) ] ──(Flush)──> [ SSTable L0 (Disk) ]
                                                            │
                                                     (Compaction)
                                                            ▼
                                                   [ SSTable L1 (Disk) ]
```

### 2.3 Heap Files vs. Clustered Indexes
- **Heap File Architecture (PostgreSQL):** Tables are stored as unstructured heaps of pages. Indexes contain keys pointing to physical Tuple IDs (`CTID` - page number + item pointer). Secondary index lookups require an extra indirection step to fetch the heap tuple.
- **Clustered Index Architecture (MySQL InnoDB):** The primary key index *is* the table storage. Leaf nodes contain the full row data. Secondary indexes store the primary key value instead of physical disk addresses, requiring a secondary lookup on the primary key tree (unless covered by a covering index).

## 3. Index Types & Deep Dive

### 3.1 B-Tree Indexes
- **Best For:** Equality lookups (`WHERE id = 5`), range queries (`WHERE age BETWEEN 20 AND 30`), sorting (`ORDER BY`).
- **Cardinality:** Highly effective on columns with high cardinality (many unique values). Low cardinality columns (e.g., boolean `is_active`) degrade B-Tree effectiveness unless combined in composite indexes.

### 3.2 Composite (Multi-Column) Indexes & The Leftmost Prefix Rule
When creating an index on `(A, B, C)`, the B-Tree is sorted primarily by `A`, secondarily by `B`, and tertiarily by `C`.
- **Supported Queries:** Queries querying `A`, `A AND B`, or `A AND B AND C`.
- **Unsupported Queries (Index Skip / Miss):** Queries querying `B`, `C`, or `B AND C` cannot fully leverage the index because the tree branches on `A` first.

### 3.3 Covering Indexes
An index that contains all columns requested by a query (both in the `WHERE` clause and the `SELECT` clause). 
- **Benefit:** The database can satisfy the query entirely from the index structure without performing random I/O lookups to the underlying table or heap pages (Index-Only Scan).

### 3.4 Hash Indexes
- **Mechanism:** Maps keys to hash values pointing directly to data locations.
- **Complexity:** $O(1)$ for exact match lookups.
- **Limitations:** Completely useless for range queries (`>`,`<`,`BETWEEN`), sorting, or partial key matches. Used internally in memory hash joins and Redis key-value lookups.

### 3.5 Full-Text Indexes (Inverted Indexes)
Used for natural language search (e.g., Elasticsearch, Postgres `tsvector`).
- **Mechanism:** Parses documents into tokens (words), removing stop words, stemming, and mapping each term to a posting list of document IDs and positions.

### 3.6 Spatial (R-Tree) Indexes
Used for geospatial coordinates (latitude/longitude, polygons). Groups spatial objects into bounding boxes hierarchically.

### 3.7 Bitmap Indexes
Used in data warehouses and OLAP systems for low-cardinality columns (e.g., gender, status). Uses bit arrays where each bit corresponds to a row. Highly efficient for bitwise boolean operations (`AND`, `OR`, `NOT`).

## 4. Advanced Storage & Indexing Optimizations

### 4.1 Bloom Filters
Probabilistic data structures used in LSM-Tree engines and distributed databases to test whether a key *might* be in an SSTable or disk block.
- **False Positive Rate:** Can return "may be present" (with configurable probability, e.g., 1%), but *never* returns false negatives ("definitely not present"). Prevents expensive disk reads for non-existent keys.

### 4.2 Sparse vs. Dense Indexes
- **Dense Index:** Every search key in the data file has an entry in the index.
- **Sparse Index:** An index entry exists only for every block/page of data. Relies on data being sorted. Requires less memory/storage but requires linear scanning within the block.

### 4.3 Write Amplification Factor (WAF)
$$\text{WAF} = \frac{\text{Bytes written to storage}}{\text{Bytes written by application}}$$
- **B-Tree WAF:** High due to random writes, page splits, and WAL logging.
- **LSM-Tree WAF:** High due to background compaction reading and rewriting data multiple times across levels.

## 5. Comparative Trade-offs: B-Tree vs. LSM-Tree

| Dimension | B-Tree | LSM-Tree |
| :--- | :--- | :--- |
| **Write Performance** | Moderate (Random I/O, page splits, WAL) | Extremely High (Sequential append to WAL + MemTable) |
| **Read Performance** | Fast & Predictable ($O(\log N)$ point & range) | Slower (May require checking MemTable + multiple SSTables / Bloom filters) |
| **Space Amplification** | Moderate (Internal fragmentation, fill factor) | Higher during compaction spikes (requires extra disk overhead) |
| **Write Amplification** | Moderate-High (Page level updates) | High (Compaction rewriting) |
| **Primary Use Cases** | OLTP relational databases (MySQL/InnoDB, Postgres) | High-write ingestion, time-series, NoSQL (Cassandra, RocksDB) |

## 6. Interview Deep Dive & Architectural Questions

### Q1: Why do database indexes degrade range query performance when fragmented?
**Answer:** Over time, page splits in B-Trees cause logically sequential leaf nodes to be scattered across non-contiguous physical disk blocks. Range scans that should be sequential disk I/O degenerate into random disk seeks, reducing throughput. Reindexing or table defragmentation restores contiguous physical page layouts.

### Q2: How does MVCC (Multi-Version Concurrency Control) interact with storage and indexing?
**Answer:** MVCC allows multiple transactions to read a consistent snapshot of data without locking by maintaining multiple physical versions of rows (undo logs in InnoDB, tuple headers in Postgres). Indexes point to tuple versions, and background vacuuming processes clean up dead tuple versions no longer visible to any active transaction.
