# 030. Stream Processing Masterclass

## 1. Architectural Foundations

Historically, data processing was predominantly batch-oriented: data accumulated in storage over hours or days, and large batch jobs (e.g., nightly Hadoop MapReduce jobs) processed the backlog. While batch processing is powerful for deep historical analytics, modern business domains require **real-time intelligence**: detecting fraudulent credit card transactions in milliseconds, updating fraud models instantly, triggering dynamic surge pricing, or monitoring distributed system infrastructure health in real time.

**Stream Processing** is the continuous, real-time ingestion, transformation, and analysis of unbounded data streams as they flow through the system.

### 1.1 Batch vs. Stream Processing Paradigms
*   **Batch Processing:** Computes over a bounded, static dataset ($Data_{batch} = Finite$). High latency (hours/days), high throughput, easy to reason about failures (re-run the batch job).
*   **Stream Processing:** Computes over an unbounded, continuous dataset ($Data_{stream} = Infinite$). Sub-second latency, continuous execution, stateful computations requiring robust checkpointing and fault tolerance.

## 2. Core Concepts & Terminology

### 2.1 Stateful vs. Stateless Stream Processing
*   **Stateless Operations:** Each incoming event is processed independently without referencing past events (e.g., data sanitization, field projection, filtering out log levels). Easy to scale horizontally.
*   **Stateful Operations:** Processing an event requires maintaining accumulated state from previous events in the stream (e.g., calculating moving averages, counting active user sessions, detecting fraud patterns across multiple transactions). Requires distributed state backends (e.g., embedded RocksDB backed by distributed checkpoints).

### 2.2 Windowing Strategies
Because stream data is infinite, computations over aggregates (e.g., "count clicks per minute") must be bounded into finite subsets called **Windows**.
*   **Tumbling Windows:** Fixed-size, non-overlapping, contiguous time intervals (e.g., every 5 minutes: `[00:00-00:05], [00:05-00:10]`).
*   **Sliding Windows:** Fixed-size, overlapping windows defined by a window duration and a slide interval (e.g., 10-minute window sliding every 1 minute).
*   **Session Windows:** Dynamic windows bounded by periods of inactivity (gaps). If a user is active, the window expands; after 30 minutes of inactivity, the session closes.

```
Tumbling Windows: [ 0-5 ] [ 5-10 ] [ 10-15 ]  (Non-overlapping)

Sliding Windows:  [ 0-10 ]
                    [ 1-11 ]
                      [ 2-12 ]                 (Overlapping)
```

## 3. Handling Time & Out-of-Order Data

In distributed networks, events generated by clients or microservices frequently arrive out of order at the stream processor due to network latency, client offline buffering, or clock drift.

### 3.1 Event Time vs. Processing Time
*   **Processing Time:** The local wall-clock time of the stream processing machine when it receives the event. Vulnerable to network delays and infrastructure lag.
*   **Event Time:** The actual timestamp embedded in the event payload when it occurred on the client device. This is the correct time domain for accurate business analytics.

### 3.2 Watermarks
How does a stream processor know when it has received *all* events for a specific time window? 
*   **Watermarks** are special control markers injected into the event stream that declare: *"All events with an event timestamp less than time $T$ have now arrived."*
*   **Handling Late Data:** If an event arrives with an event time older than the current watermark (late data), stream processing frameworks provide mechanisms to drop, log, or route them to side-outputs for corrective aggregation.

## 4. Architectural Frameworks & Topologies

### 4.1 Apache Flink
*   **Design:** A distributed, high-performance stream processing framework built for continuous stateful computations over unbounded and bounded data streams.
*   **Chandy-Lamport Distributed Snapshots:** Flink achieves fault tolerance and exactly-once processing semantics without locking by periodically injecting barrier markers into data streams, snapshotting distributed state asynchronously to durable storage (S3/HDFS).

### 4.2 Apache Kafka Streams
*   **Design:** A lightweight, client-side Java library for building scalable stream processing applications where input and output data are stored in Kafka topics.
*   **Local State Stores:** Maintains state locally using embedded **RocksDB** instances, backed continuously by Kafka changelog topics for fault tolerance.

### 4.3 Lambda vs. Kappa Architecture
*   **Lambda Architecture:** Combines a **Batch Layer** (processes historical data accurately with Hadoop/Spark) and a **Speed Layer** (processes real-time streaming data with Flink/Storm), merged at a **Serving Layer**. *Drawback:* Maintaining two distinct codebases for batch and stream logic.
*   **Kappa Architecture:** Simplifies Lambda by eliminating the batch layer entirely. Everything is treated as an immutable stream. Reprocessing historical data is achieved by rewinding Kafka topic offsets and re-running the streaming pipeline at high speed.

## 5. System Design Interview Blueprint: Designing a Real-Time Credit Card Fraud Detection Engine

### Problem Statement
Design a stream processing system that ingests 50,000 credit card authorization transactions per second globally and flags fraudulent swipes within 100 milliseconds.

### Step 1: High-Level Architecture
```
[ POS Terminals / Mobile Apps ] 
       |
       v
[ API Gateway / Load Balancer ]
       |
       v
[ Kafka Ingestion Topic: `credit-card-txns` ] (Partitioned by `card_id`)
       |
       v
[ Stream Processing Engine (Apache Flink / Kafka Streams) ]
       |
       +---> [ Stateful Window: 5-minute Sliding Window of User Transactions ]
       |
       +---> [ Rule Engine / ML Model Scoring (Anomaly Detection) ]
       |
       +---> [ Alert Sink ] ---> (SMS / Risk Dashboard)
       |
       +---> [ Approved / Declined Output Topic ]
```

### Step 2: Key Design Decisions
1.  **Partitioning Strategy:** Transactions must be partitioned by `card_id` in Kafka. This guarantees that all transactions for a specific credit card are routed to the exact same Flink stream processing task, allowing local in-memory state tracking of recent geographic locations and spending velocity without distributed lock contention.
2.  **Stateful Velocity Check:** Flink maintains a sliding window state store holding the last 5 transactions for each card. If a transaction occurs in New York at 12:00 PM and another in Tokyo at 12:02 PM, the velocity check flags an impossible travel anomaly.
3.  **Low Latency SLA:** By processing data in-memory with embedded state stores (RocksDB), Flink evaluates fraud scoring rules and publishes authorization decisions within 50ms.
