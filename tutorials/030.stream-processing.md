# 030. Stream Processing Masterclass

## 1. Architectural Foundations

Traditional data processing was batch-oriented: data accumulated in files or databases over hours or days, and batch jobs (e.g., nightly Hadoop MapReduce or Spark jobs) processed the entire dataset at once. While efficient for large historical analysis, batch processing introduces high latency (hours of delay), making it inadequate for modern real-time use cases such as fraud detection, live anomaly monitoring, real-time bidding, and instant ride-sharing dispatch.

**Stream Processing** shifts the paradigm from *store-then-process* to *process-as-it-arrives*. Data flows continuously through computation engines in micro-batches or continuous event streams.

### 1.1 Key Terminology
*   **Event Time vs. Processing Time:**
    *   *Event Time:* The exact timestamp when the event actually occurred at the source (e.g., when a user clicked a button on their phone).
    *   *Processing Time:* The system clock time of the stream processing node when it evaluates the event. Network delays or backpressure can cause processing time to lag significantly behind event time.
*   **Stateful vs. Stateless Processing:**
    *   *Stateless:* Each incoming event is processed independently (e.g., data cleansing, filtering log levels).
    *   *Stateful:* Processing requires maintaining aggregations, joins, or windows across multiple events (e.g., counting user clicks per 5-minute window or tracking active user sessions).

## 2. Architectural Design Patterns: Lambda vs. Kappa

### 2.1 Lambda Architecture
Introduced by Nathan Marz, Lambda Architecture attempts to reconcile the latency limitations of batch processing with the speed of real-time processing by maintaining two parallel pipelines:
1.  **Batch Layer:** Ingests all raw data into a master immutable data store (e.g., HDFS, S3) and pre-computes batch views periodically. It is slow (high latency) but 100% accurate and fault-tolerant (handles late-arriving data and re-computes errors).
2.  **Speed Layer:** Processes incoming real-time streams with low latency (e.g., Apache Flink, Spark Streaming) to provide approximate or fast views of recent data.
3.  **Serving Layer:** Merges pre-computed batch views and real-time speed views to answer user queries.
*   **The Flaw of Lambda:** Maintaining two separate codebases (one in batch processing framework like Hadoop/Spark, another in streaming framework like Storm/Flink) creates massive operational complexity, code duplication, and synchronization bugs.

### 2.2 Kappa Architecture
Proposed by Jay Kreps, Kappa Architecture eliminates the batch layer entirely by treating **everything as a stream**.
*   **Mechanism:** Raw data is ingested into an append-only, durable log storage system with long retention (e.g., Apache Kafka or Apache Pulsar).
*   **Batch & Real-Time Unified:** When historical reprocessing or code updates are required, the stream processor simply rewinds consumer offsets to the beginning of the log and replays all historical data through the exact same stream processing engine at high speed.

```
[ Data Sources ] ---> [ Apache Kafka (Durable Append-Only Log) ]
                             |                           |
                 (Real-Time Path)                  (Reprocessing / Historical)
                             |                           |
                             v                           v
                      [ Stream Processor (Apache Flink) ]
                                     |
                                     v
                          [ Real-Time Serving DB ]
```

## 3. Windowing Strategies

Because streams are infinite, computations (like aggregations or joins) must be bounded into finite subsets called **Windows**.

*   **Tumbling Windows:** Fixed-size, non-overlapping, contiguous time intervals (e.g., every 5 minutes: [10:00-10:05], [10:05-10:10]).
*   **Sliding Windows:** Fixed-size, overlapping windows defined by a window duration and slide interval (e.g., 10-minute window sliding every 1 minute).
*   **Session Windows:** Dynamic windows bounded by periods of inactivity (e.g., group all user click events until the user stops clicking for 30 minutes).
*   **Watermarks:** A mechanism in stream processing engines (like Flink or Beam) that handles out-of-order events caused by network jitter. A watermark of time $T$ indicates that the system believes all events with event time $< T$ have arrived, safely triggering window computations.

## 4. Popular Stream Processing Engines

*   **Apache Flink:** A state-of-the-art stream processing framework designed for true event-by-event (low-latency) processing, robust event-time windowing, and distributed checkpoint-based fault tolerance.
*   **Apache Spark Streaming (Structured Streaming):** Uses a micro-batch processing model where continuous streams are broken into micro-batches (e.g., 100ms intervals), offering high throughput and unified batch/stream APIs.
*   **Kafka Streams:** A lightweight Java client library built directly on Apache Kafka that simplifies building microservices that process Kafka topics into other Kafka topics with local state stores (RocksDB).

## 5. System Design Interview Blueprint: Designing a Real-Time Trending Topics / Analytics Engine

### Problem Statement
Design a real-time analytics engine processing 1 million search queries per second to compute top 10 trending search keywords globally over rolling 1-hour windows.

### High-Level Architecture
1.  **Ingestion:** Client search requests are published to an **Apache Kafka** topic partitioned by keyword hash.
2.  **Stream Processing (Flink):**
    *   Flink application consumes events from Kafka.
    *   Applies a sliding window of 1 hour, sliding every 10 seconds.
    *   Maintains local state (aggregating counts of each keyword) backed by RocksDB.
    *   Emits top 10 keywords continuously to a downstream sink topic.
3.  **Serving Layer:** Real-time dashboards or search bars query a high-performance in-memory cache (Redis) updated continuously by the Flink sink.
