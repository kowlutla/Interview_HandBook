# 040. Search Systems: Masterclass

## 1. Architectural Foundations of Full-Text Search

Traditional relational databases excel at exact matches, range queries, and structured joins, but perform poorly on full-text search (e.g., finding documents containing semantic keywords, handling misspellings, ranking relevance, and processing natural language). Full-text search engines (e.g., Elasticsearch, Apache Solr, OpenSearch, Meilisearch) are purpose-built to index, score, and retrieve unstructured text at scale.

### 1.1 The Inverted Index
The fundamental data structure powering modern search systems is the **Inverted Index**. 
*   *Forward Index:* Maps document IDs to their contained words (document-centric).
*   *Inverted Index:* Maps individual terms (words) to the list of documents containing them, along with term frequency and positional offsets (term-centric).

```
Documents:
Doc 1: "system design masterclass scalable architecture"
Doc 2: "scalable system design patterns"

Inverted Index Structure:
  "architecture" -> [Doc 1 (offset 4)]
  "design"       -> [Doc 1 (offset 1), Doc 2 (offset 2)]
  "masterclass"  -> [Doc 1 (offset 2)]
  "patterns"     -> [Doc 2 (offset 3)]
  "scalable"     -> [Doc 1 (offset 3), Doc 2 (offset 0)]
  "system"       -> [Doc 1 (offset 0), Doc 2 (offset 1)]
```

## 2. Text Analysis & Tokenization Pipeline

Before text can be indexed or searched, raw text passes through an **Analyzer pipeline** consisting of three sequential stages:

1.  **Character Filters:** Cleanse the raw text stream (e.g., strip HTML tags, convert HTML entities like `&amp;` to `&`).
2.  **Tokenizer:** Splits the character stream into discrete tokens (words) based on whitespace, punctuation, or language grammars (e.g., Standard Tokenizer).
3.  **Token Filters:** Transform, normalize, or filter tokens:
    *   *Lowercase Filter:* Converts all tokens to lowercase ("System" -> "system").
    *   *Stop Word Filter:* Removes common insignificant words ("the", "and", "is").
    *   *Stemmer / Lemmatizer:* Reduces inflected words to their root form ("running", "runs", "ran" -> "run").
    *   *Synonym Filter:* Expands terms using a synonym dictionary ("laptop" -> matches "notebook", "laptop").

## 3. Relevance Scoring & Ranking Algorithms

When a user executes a search query with multiple terms, the search engine must rank matching documents by relevance.

### 3.1 TF-IDF (Term Frequency - Inverse Document Frequency)
*   **Term Frequency (TF):** Measures how frequently a term appears in a document. Higher frequency = higher relevance, with diminishing returns (using square root or log scaling).
*   **Inverse Document Frequency (IDF):** Measures how rare or common a term is across the entire corpus. Common words ("the", "is") have low IDF; rare domain-specific terms have high IDF.
*   *Formula:* $\text{TF-IDF} = \text{TF}(t, d) \times \text{IDF}(t, D)$

### 3.2 BM25 (Best Matching 25)
BM25 is the industry-standard probabilistic ranking function used by Elasticsearch and Lucene, improving upon TF-IDF by introducing **Term Frequency Saturation** and **Document Length Normalization**.
*   *Term Frequency Saturation:* In TF-IDF, an occurrence count of 100 contributes 10x more than 10. BM25 introduces a tuning parameter ($k_1$) that caps the contribution of term frequency, preventing documents with excessive repetition (keyword stuffing) from dominating results.
*   *Document Length Normalization:* Long documents naturally contain more words and higher term counts. BM25 penalizes documents longer than the average corpus length (parameter $b$) to prevent lengthy documents from unfairly ranking above concise, focused documents.

## 4. Vector Search & Hybrid Search in Modern Search Engines

Traditional keyword search struggles with semantic intent (e.g., searching for "automobile" might not match documents containing only "car"). Modern search engines combine lexical search with **Vector Search (Neural / Semantic Search)**.

*   **Embeddings:** Text documents and search queries are transformed into high-dimensional dense vectors (e.g., 768 or 1536 dimensions) using machine learning embedding models (e.g., BERT, OpenAI embeddings).
*   **Approximate Nearest Neighbor (ANN):** Algorithms such as **HNSW (Hierarchical Navigable Small World graphs)** or **IVF (Inverted File Index)** index vectors in high-dimensional space, enabling sub-millisecond similarity search (Cosine Similarity or Euclidean Distance) across billions of vectors.
*   **Hybrid Search:** Combines BM25 lexical search scores with HNSW vector search similarity scores using **Reciprocal Rank Fusion (RRF)**, yielding both precise keyword exact-matches and deep semantic understanding.

## 5. Interview Deep Dive & Architectural Questions

### Q1: How do search engines handle near real-time search indexing with high write throughput?
**Answer:**
Search engines built on Apache Lucene (like Elasticsearch) use immutable segments. 
1.  **Buffer & Refresh:** Inbound documents are written to an in-memory buffer and a transaction log (translog). Every 1s (configurable `refresh_interval`), the buffer is flushed into a new immutable Lucene **Segment** on disk.
2.  **Segment Merging (Compaction):** As writes continue, hundreds of small segments accumulate. A background thread performs **Segment Merging**, combining smaller segments into larger ones while purging deleted documents marked by tombstones, maintaining query performance and disk efficiency.

### Q2: How would you design a distributed auto-complete (type-ahead search) system supporting 50,000 QPS with sub-50ms latency?
**Answer:**
1.  **Data Structure:** Use an **N-gram Inverted Index** or a **Prefix Trie (Prefix Tree)** loaded directly into RAM across a distributed cluster of search nodes.
2.  **Caching:** Implement an edge caching layer (Redis / CDN) for top trending prefixes, as autocomplete queries follow a Zipfian distribution (a small fraction of prefixes account for $80\%$ of queries).
3.  **Asynchronous Indexing:** Decouple search log ingestion from index updates using an asynchronous worker queue.
