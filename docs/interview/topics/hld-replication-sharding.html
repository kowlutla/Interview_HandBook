How to use this page

Each question is a collapsible. Try to answer out loud first, then open it. Replication is about copies of the same data (availability, read scale, durability). Sharding is about splitting different data across machines (write scale, storage scale). Almost every interviewer follow-up is a trade-off between consistency, latency and operational pain, so practise naming the trade-off explicitly.

Replication basics

Why do we replicate data at all? Basic

Replication means keeping copies of the same data on several machines. Three reasons:

  • Availability: if one node dies, another still has the data and can serve it.
  • Durability: a disk failure does not lose data when a second copy exists on another machine or in another zone.
  • Read scalability and latency: reads can be spread over many copies, and a copy can sit near users in another region.

It does not increase write capacity: every copy must still apply every write. That is what sharding is for.

What is the difference between replication and sharding? Basic
ReplicationSharding (partitioning)
What is splitNothing. Same data on N nodesData is divided; each node holds a different slice
SolvesAvailability, durability, read scaleWrite scale, storage size, memory working set
CostReplication lag, failover complexityCross-shard queries and transactions, rebalancing

Real systems use both: the data is split into shards, and every shard is replicated (see the combining section).

How does leader-follower (primary-replica) replication work? Basic

One node, the leader, accepts all writes. It records each change in an ordered log. Followers connect to the leader, pull (or are pushed) that log and apply the changes in the same order. Reads can go to the leader or to followers.

Pros: simple, no write conflicts, well understood (MySQL, PostgreSQL, MongoDB replica sets, Redis). Cons: the leader is the write bottleneck and a single point of failure until failover completes.

Compare synchronous, asynchronous and semi-synchronous replication. Basic
ModeLeader acknowledges the client when...Trade-off
SynchronousAll (or the designated) followers have confirmed the writeNo data loss on leader crash, but one slow or dead follower blocks writes; higher write latency
AsynchronousThe leader alone has written itFast and tolerant of follower failure, but a leader crash can lose the last few acknowledged writes; followers lag
Semi-synchronousAt least one follower (not all) has confirmedCompromise: a copy exists on a second node, but one slow follower does not stall writes. Falls back to async if no follower answers (MySQL semi-sync), or needs a quorum (Raft-style)
Say: "Fully synchronous to every follower is fragile, since availability drops as you add replicas. In practice one synchronous follower plus the rest async, or a majority quorum, gives durability without letting one slow node block everything."
With async replication, exactly what can you lose, and how do you reason about it? Intermediate

Writes acknowledged to the client but not yet shipped to any follower. If the leader dies and a lagging follower is promoted, those writes are gone, and worse, if the old leader later returns holding them, they conflict with new writes taken by the new leader. The amount lost is bounded by the replication lag at the moment of the crash (often milliseconds, but can be seconds or more under load).

Mitigations: semi-sync or quorum commit for data you cannot lose (payments), monitoring lag, and discarding or manually reconciling the old leader's unreplicated tail. A famous example: GitHub's 2018 outage involved a brief network partition and a failover to a replica in another datacenter that was missing some writes, which led to many hours of reconciliation (details hedged; the headline is failover with unreplicated writes).

How do replication logs differ: statement-based, WAL shipping and logical (row-based)? Intermediate
Log typeWhat is shippedProblems / notes
Statement-basedThe SQL text (INSERT, UPDATE...)Non-deterministic functions (NOW(), RAND(), UUID()), auto-increment ordering, triggers and side effects can make replicas diverge. Largely abandoned as the default
WAL shipping (physical)Byte-level changes to disk pages, the same write-ahead log the engine uses for crash recoveryExact copy and efficient, but tied to the storage engine and version: leader and follower usually must run the same version, which complicates zero-downtime upgrades
Logical / row-basedPer-row events: "row with key K changed from A to B"Decoupled from the storage format, works across versions, and can be consumed by external systems (change data capture to Kafka, search indexes). MySQL binlog ROW format, PostgreSQL logical decoding

The write-ahead log (WAL) is an append-only file in which the database records each change before applying it to data pages, so it can recover after a crash. Reusing it for replication is cheap, which is why physical replication is so common.

How do you add a new follower to a running database without downtime? Intermediate
  1. Take a consistent snapshot of the leader (without locking writes) and note its exact position in the replication log (log sequence number, binlog coordinates).
  2. Copy the snapshot to the new node.
  3. The follower connects to the leader and requests all changes since that position.
  4. It applies the backlog until it has caught up, then follows the live stream.

The log position is the key detail: without it you cannot know where the snapshot ends and the stream begins.

Can you scale write throughput by adding more followers? What is the ceiling of read replicas? Basic

No. Every follower applies every write, so adding followers does not raise write capacity, and each one adds a little load on the leader (it must ship the log to each). Read replicas help read-heavy workloads (for example 95% reads) but have limits: replication lag makes reads stale, and a single-threaded apply process on a follower can fall behind a busy leader. When the leader itself saturates on writes or the dataset exceeds one node's disk, you need sharding.

How many replicas do you need? Why is three so common? Basic

Three copies tolerate one failure while still having a majority (2 of 3) for quorum decisions, and the usual layout is one per availability zone. Two copies cannot form a majority after one failure, so automatic election is unsafe. Five copies tolerate two failures at higher cost, used for critical metadata stores (etcd, ZooKeeper, often 3 or 5). A majority of N needs floor(N/2)+1, so even numbers buy nothing extra: 4 nodes still tolerate only 1 failure.

Replication lag and consistency anomalies

What is replication lag and why does it matter? Basic

The time (or number of log entries) a follower is behind the leader. With async replication, a read from a follower can return data that is already outdated. This is "eventual consistency": if writes stop, all followers eventually match. Normally lag is a fraction of a second, but a long-running query on the follower, a big batch write, a network issue or an overloaded follower can push it to minutes. Monitor it, and alert on it.

What is the read-your-writes anomaly and how do you fix it? Intermediate

A user posts a comment (write goes to the leader), refreshes the page (read goes to a lagging follower) and the comment is missing. They think it was lost. Read-your-writes (read-after-write) consistency guarantees that a user always sees their own writes, though not necessarily other users' latest writes.

Fixes:

  • Read things the user may have modified from the leader (for example their own profile), everything else from followers.
  • For a short window (say 1 minute) after a user's write, route all of that user's reads to the leader.
  • Track the log position of the user's last write (in the session or a token) and only read from a replica that has reached that position, else wait or use the leader.
  • Sticky routing to one replica helps monotonic reads but not this by itself.
Trap: with multiple devices (phone and laptop), session-based tricks break because the second device has no knowledge of the first device's last write timestamp. The position has to be stored server-side per user, and you may need to route all of a user's devices to the same region.
What are monotonic reads, and what goes wrong without them? Intermediate

Without them a user can see data move backwards in time. Example: refresh 1 hits a fresh follower and shows a new comment; refresh 2 hits a more lagging follower and the comment vanishes. Monotonic reads guarantee that once you have seen a value, you will not later read an older one. It is weaker than strong consistency but stronger than eventual.

Fix: pin each user to the same replica (hash of user id picks the replica). If that replica fails, the user moves to another and may see a one-time step back, which is usually acceptable.

What is the consistent-prefix-reads anomaly? Senior

Causally related writes are seen out of order. Classic example: Mr. A asks "How far into the future can you see?" and Mrs. B answers "About ten seconds." An observer reading from different shards might see the answer before the question, because the two writes live in different partitions with different lag. Guarantee: if a sequence of writes happens in some order, any reader sees them in that order. It is a problem mostly in sharded systems; fixes are to write causally related items to the same shard, or to track causality explicitly (version vectors, happens-before metadata).

Your analytics dashboard reads from a replica and numbers sometimes go down on refresh. What is happening and what do you do? Intermediate

This is a monotonic-reads violation: a load balancer sends consecutive requests to replicas with different lag. Options: route a user or session to one replica consistently; or if the dashboard needs fresh numbers, read from a replica but include a "data as of" timestamp from the replication position; or accept it and display the freshness. If it is a hard requirement that numbers never regress, track a high-water mark on the client and reject responses behind it.

Replica lag suddenly jumps from 100 ms to 10 minutes. What are the likely causes and what do you check? Senior
  1. Big transaction or bulk job on the leader (a huge UPDATE or index build) which a follower replays serially. Check the leader's recent big transactions.
  2. Single-threaded apply on the follower unable to keep up with a multi-core leader. Enable parallel apply where supported.
  3. Long-running read query on the follower blocking replay (in PostgreSQL, conflicts with recovery can pause apply or cancel the query).
  4. Follower resource problem: disk IO saturated, CPU, noisy neighbour, or a snapshot or backup running.
  5. Network: cross-region bandwidth or packet loss.

Short-term: take lagging replica out of the read pool so users do not see stale data. Long-term: break up large writes, throttle batch jobs, add apply parallelism, and alert on lag.

How do you decide which reads can go to a replica and which must hit the leader? Intermediate

Classify by staleness tolerance:

  • Must be current: reading a balance just before debiting, checking inventory before confirming an order, reading a value you are about to modify (read-modify-write), the user's own just-written data. Use the leader.
  • Tolerates seconds of staleness: product catalogue, feeds, search results, other people's profiles, reports. Use replicas.

Implement it as an explicit option in the data access layer (for example a "consistency=strong" flag) rather than letting each developer guess.

Failover, promotion and split brain

Walk through leader failover. What are the steps and what can go wrong? Intermediate
  1. Detect: followers or a monitor notice the leader is unreachable (heartbeat timeout, for example 30 seconds).
  2. Choose a new leader: by election among replicas, or appointed by a controller. The best candidate is the most up-to-date replica.
  3. Reconfigure: clients and the other followers start sending writes and replicating from the new leader.
  4. Handle the old leader: if it comes back it must realise it is no longer leader and become a follower (demote it, discard or reconcile its extra writes).

Things that go wrong: lost unreplicated writes (async); the timeout is too short so a brief GC pause or network blip triggers an unnecessary failover that makes load worse; too long and you have a long outage; two nodes both believing they are leader (split brain); stale primary keys reused (an out-of-date promoted replica reissues auto-increment ids that were already used and exposed in another system, a real GitHub incident type).

What is split brain and how do you prevent it? Intermediate

Two nodes both think they are the leader and both accept writes, so the data diverges and may be unmergeable. It typically happens in a network partition, or when the old leader is only slow (long GC pause), not dead.

Prevention:

  • Quorum / majority election: a leader needs votes from a majority; only one side of a partition can have a majority (Raft, Paxos, ZooKeeper-based election).
  • Epoch / term / fencing tokens: every leader has an increasing number; storage and followers reject requests carrying an older number, so a zombie old leader is harmless.
  • Fencing the old node (STONITH, "shoot the other node in the head"): power it off or revoke its storage access before promoting another.
  • Leases: leader holds a time-limited lease and stops serving when it cannot renew. Depends on bounded clock drift.
Why is a two-node primary-secondary setup with automatic failover dangerous? Senior

With two nodes, when they cannot talk to each other, neither can tell whether the other is dead or just unreachable. If both promote themselves you get split brain; if neither does you get an outage. A majority is impossible with 2 voters. The standard fix is a third vote: a witness/arbiter node (MongoDB arbiter, a tiebreaker in another zone) or a three-node cluster. If you must run two nodes, use an external lock service or manual failover.

Which replica should be promoted? Intermediate

The one with the most advanced position in the replication log (least data loss), subject to priorities (prefer same zone as clients, prefer bigger hardware, never promote a replica deliberately kept as a delayed or analytics replica). Raft handles this inherently: only a candidate whose log is at least as up to date as a majority can win the election, so committed entries are never lost.

How do clients find the new leader after failover? Intermediate
  • A proxy or virtual IP / DNS name that is repointed (watch out for DNS TTL caching).
  • A service discovery layer or cluster-aware driver that learns topology (MongoDB drivers, Redis Sentinel/Cluster clients, Kafka metadata requests).
  • Connection poolers such as ProxySQL or PgBouncer fronting the database.

Clients must retry with backoff, and writes must be idempotent, since a write timing out during failover may or may not have been applied.

Multi-leader and leaderless replication

What is multi-leader replication and when would you use it? Intermediate

More than one node accepts writes, and each leader replicates its changes to the others asynchronously. Use cases:

  • Multi-datacenter: one leader per region, so users write locally with low latency, and a region can keep working if the link between regions goes down.
  • Offline-capable clients: a phone calendar app is effectively a leader that syncs later; collaborative editors (Google Docs style) similar.

Cost: write conflicts. Two leaders can update the same row at the same time. Also trickier things such as auto-increment keys, triggers and constraints behave poorly. Many teams avoid multi-leader inside one datacenter because the complexity is not worth it.

How are write conflicts resolved in multi-leader or leaderless systems? Senior

Trap: saying "use timestamps" without mentioning that LWW loses data. A shopping cart done with LWW can drop an added item; a set-union merge keeps it, though it may resurrect a removed item (the Dynamo paper cart anomaly).
How does leaderless (Dynamo-style) replication work? Intermediate

There is no leader. A client (or a coordinator node) sends each write to all N replicas of the key and considers it successful once W of them acknowledge. A read asks R replicas and takes the newest version among the replies. Used by Cassandra, Riak, Voldemort and DynamoDB's original design.

It tolerates node failures and slow nodes without any failover step: you simply proceed with the others. Stale replicas are repaired by:

  • Read repair: when a read notices an outdated replica, the coordinator writes the fresh value back to it.
  • Anti-entropy: a background process compares replicas (often with Merkle trees, hash trees that quickly find the differing key ranges) and syncs them.
  • Hinted handoff: if a replica is down, another node stores the write as a "hint" and delivers it when the replica returns.
Explain quorum reads and writes with N, W and R. When is the system strongly consistent? Intermediate

N = number of replicas, W = acks needed for a write, R = replicas consulted for a read. If W + R > N, the set of nodes written and the set read must overlap in at least one node, so a read sees at least one replica with the latest write.

Config (N=3)Behaviour
W=2, R=2Balanced; tolerates one node down for both reads and writes
W=3, R=1Fast reads, writes fail if any node is down
W=1, R=3Fast writes, slow reads, writes may be lost if the single acking node dies
W=1, R=1Fastest, eventually consistent only

Even with W+R>N, edge cases remain: sloppy quorums (writes go to stand-in nodes outside the usual N), concurrent writes with unclear order, a write that succeeded on fewer than W nodes is not rolled back on the ones that did take it, clock-based LWW losing writes, and a node restored from a stale backup. So quorum gives "likely fresh", not linearizability, unless the system adds extra mechanisms.

Say: "W plus R greater than N guarantees overlap, but overlap alone is not linearizability."
What is a sloppy quorum? Senior

When some of the N home replicas for a key are unreachable, writes are accepted by other reachable nodes in the cluster, which hold them with a hint until the home nodes return (hinted handoff). It raises write availability during partitions but breaks the overlap guarantee: a read of R home nodes may miss the value stored on stand-ins, so it is weaker than a strict quorum.

How do Raft-style replicated state machines relate to leader-follower replication? Senior

They are leader-follower with a safe, automatic failover built in. The leader appends a command to its log, replicates it, and commits it once a majority has stored it, then replies. Elections need a majority, and a candidate with an incomplete log cannot win, so committed data is never lost and split brain is impossible (a minority side cannot commit). The price is latency for a majority round trip and unavailability when a majority is lost. Used by etcd, Consul, CockroachDB (per range), TiKV, and Spanner (Paxos groups).

Single-leader vs multi-leader vs leaderless: how do you choose? Intermediate

Default to single-leader unless a hard requirement (local writes in many regions, extreme availability) pushes you away.

Sharding basics

What is sharding and why would you do it? Basic

Sharding (horizontal partitioning) splits a large dataset into pieces called shards, each stored on a different node, so no single machine holds everything. "Partition" and "shard" are used almost interchangeably; strictly, a partition is the logical piece and a shard is often a separate database instance holding one or more partitions.

Reasons: the data no longer fits on one disk; the write rate exceeds what one primary can handle; the hot working set no longer fits in memory; you want to isolate tenants or place data in regions.

Example: 2 TB of orders growing 20% a month with 10k writes/s. Split by customer id into 16 shards, each about 125 GB and 600 writes/s.

Horizontal vs vertical partitioning: what is the difference? Basic

Horizontal splits rows: users 1 to 1M on shard A, the next million on shard B, same schema everywhere. Vertical splits columns or tables: a hot narrow table of frequently read fields separate from a wide table of rarely used blobs, or one service's tables in one database and another's elsewhere (functional partitioning). Vertical partitioning is often the cheaper first step, but it does not scale a single big table beyond one machine.

Compare range, hash and directory-based partitioning. Intermediate
SchemeHow the shard is chosenGood forWeakness
RangeKey ranges (A to F, F to M...; dates)Range scans and ordered access; easy to split a rangeHotspots: sequential keys (timestamps) send all new writes to the last range
Hashshard = hash(key) mod N, or hash ring positionEven distribution, spreads sequential keysRange queries scatter across all shards; naive mod N moves almost all keys when N changes
Directory / lookupA lookup service maps key (or tenant) to shardTotal flexibility: move one tenant, handle big tenants speciallyLookup is an extra hop and a critical component (cache it, replicate it); must be kept consistent

Hybrids are common: Cassandra and DynamoDB use hash partition key plus a sorted clustering/sort key inside the partition, so you get even spread plus range queries within one key's data.

Why is hash(key) mod N a bad scheme when the number of shards changes? Intermediate

Going from N=4 to N=5 changes the result for most keys (about 80% of keys move, in general a fraction of N/(N+1) or thereabouts), so nearly the whole dataset must be reshuffled, a huge copy storm, and caches keyed the same way all miss at once. Ways around it: consistent hashing, or a fixed large number of logical partitions (for example 1024) mapped to nodes, so adding a node only moves whole partitions.

What is the "fixed number of partitions" approach (pre-sharding) and why is it popular? Intermediate

Create many more logical partitions than nodes up front (say 1,000 partitions for 10 nodes). Key to partition mapping (hash mod 1000) never changes. Partitions are assigned to nodes; adding a node steals a few partitions from each existing node and copies only those. Used by Redis Cluster (16,384 hash slots), Elasticsearch (fixed primary shard count per index), Couchbase, Kafka partitions. Downside: the count is hard to change later (Elasticsearch needs split/shrink or reindex), so you must pick roughly right: too few limits scaling, too many adds overhead per partition.

What is dynamic partitioning (auto-splitting)? Intermediate

The system splits a partition when it grows past a size or load threshold (for example about 10 GB in HBase-style systems, or by load in DynamoDB and Spanner), and merges small ones. The number of partitions adapts to data volume. It starts with one partition, which is a bottleneck at first, so many systems support pre-splitting. Common with range partitioning (HBase, Bigtable, CockroachDB, MongoDB with ranges).

How does a request find the right shard (request routing)? Intermediate
  1. Any node routes: client contacts any node, which forwards if it does not own the key (Cassandra coordinator, Redis Cluster MOVED redirect).
  2. Routing tier / proxy: a stateless router knows the map (MongoDB mongos, Vitess vtgate, ProxySQL rules).
  3. Smart client: the client library holds the partition map and connects directly.

All need an agreed, up-to-date map of partitions to nodes: stored in a coordination service (ZooKeeper, etcd) or spread by gossip. During rebalancing the map changes, so stale routers must be redirected rather than serving wrong data.

Shard keys, hotspots and the celebrity problem

How do you choose a good shard key? Intermediate

A good key has:

  • High cardinality (many distinct values), so data can spread. Country code with 200 values is a poor key for 1,000 shards.
  • Even distribution of both data and traffic, not just of key values.
  • Matches the dominant access pattern, so most queries touch one shard (for example user_id for a per-user app).
  • Stable: changing a key value means moving the row to another shard.
  • Not monotonically increasing if you use range partitioning (timestamp, auto-increment).

The key choice is very hard to change later, so test it against realistic traffic.

Say: "I look at the top two or three queries and pick the key that lets them each hit one shard, then check it for skew."
Give an example where the shard key choice makes some queries easy and others painful. Intermediate

Orders table sharded by customer_id: "show my orders" hits one shard. But "all orders for seller X" or "all orders today" must query every shard (scatter-gather). If sharded by seller_id, the reverse. Options: pick the key for the dominant path and serve the other with a secondary index, a denormalised copy sharded the other way (written by events), or a search/analytics store fed by change data capture.

What is a hot shard (hotspot) and what causes it? Intermediate

One shard receives far more load than the rest, so it saturates while others are idle, and total capacity is limited by the hottest shard. Causes:

  • Monotonic keys under range partitioning (timestamps: all current writes go to one shard).
  • Skewed keys: a few huge tenants, popular products, celebrity users.
  • Low-cardinality keys (status, country).
  • Bad hash function or poor mod placement.
  • A time-based event (flash sale, breaking news) making one key hot.
How do you mitigate a hot key or hot shard? Senior
  • Hash the key (or add a hash prefix) so sequential keys spread. Trade-off: lose efficient range scans.
  • Key salting / write sharding: append a random suffix 0..k to a hot key (post:42#7) so writes spread over k sub-keys; reads must query all k and merge. Good for counters and write-heavy keys.
  • Cache hot reads in front (local cache plus Redis), with request coalescing.
  • Split the hot range or tenant out to its own shard (directory-based), or isolate big tenants on dedicated shards.
  • Replicate hot data for reads (more replicas of that shard).
  • Batch / aggregate writes (counters flushed periodically) so one hot row gets fewer writes.
  • Composite keys: (tenant, bucket of time) instead of just time.
Trap: hashing fixes skew from key patterns but not skew from one key being accessed a million times. A single hot key stays on one shard no matter how you hash it, which needs salting or caching.
What is the celebrity problem and how do you handle it? Senior

A few entities have vastly more activity than average: a user with 50 million followers, or a viral post with millions of likes or reads. Sharding by user id puts all of that load on one shard and one key, however many shards you have.

Handling:

  • Detect heavy hitters (by follower count, or live metrics) and treat them specially.
  • For writes (likes counter): salt the key into multiple sub-counters and sum on read, or aggregate in memory or a stream first.
  • For reads: cache aggressively, replicate the hot item more, serve it from CDN or edge.
  • For fan-out of a celebrity's posts: do fan-out on read (pull) for them and fan-out on write (push) for ordinary users.
For a multi-tenant SaaS, should you shard by tenant id? What goes wrong? Intermediate

Usually a good fit: nearly all queries are within one tenant, so they hit one shard, joins and transactions within the tenant stay local, and you can move a tenant, back it up or delete it (GDPR) as a unit. Problems: tenant sizes follow a power law, so one huge tenant overwhelms a shard (the "noisy neighbour"). Use a directory so big tenants get dedicated shards and small ones are packed together, and be able to split a tenant by a second key if it outgrows a shard. Cross-tenant analytics need a separate pipeline.

Consistent hashing and resharding

How does consistent hashing work and what problem does it solve? Intermediate

Both nodes and keys are hashed onto the same circular space (a ring, for example 0 to 2^32). A key is stored on the first node found going clockwise from its position. When a node joins, it takes over only the keys between its predecessor and itself; when a node leaves, only its keys move to the next node. On average only about K/N of K keys move when going from N to N+1 nodes, versus nearly all with mod N.

What are virtual nodes (vnodes) and why are they needed? Intermediate

With one ring position per physical node, random placement gives uneven arcs: one node may own 40% of the ring and another 10%. And when a node dies, its entire load falls on its single successor. Virtual nodes put each physical machine at many (for example 100 to 256) positions on the ring.

  • Load evens out statistically.
  • A failed node's keys scatter over many survivors, not one.
  • A new node takes small slices from many nodes, so rebalancing is parallel and cheap.
  • Heterogeneous hardware: give bigger machines more vnodes.

Cost: more metadata, and in some systems repair and streaming operations touch many ranges (Cassandra moved its default vnode count down, from 256 to 16 in version 4.0, for this reason).

How do you reshard (move data between shards) without downtime? Senior
  1. Prepare: provision target shards; record the new mapping but keep routing to the old one.
  2. Bulk copy: copy a consistent snapshot of the moving range/partition to the target.
  3. Catch up: tail the source's change log (CDC) and apply changes to the target until the lag is tiny. Alternative: dual-write from the application to both (needs care for failures and ordering).
  4. Verify: compare row counts and checksums, optionally shadow reads.
  5. Cut over: briefly pause writes to that range (seconds), drain the last changes, flip the routing map atomically, resume. Reads can be flipped first.
  6. Clean up: after a safe period, delete the data on the source. Keep the ability to roll back until then.

Tools that automate this: Vitess MoveTables/Reshard, MongoDB chunk migration, Citus shard rebalancer, CockroachDB and Spanner automatic range moves. Throttle copy traffic so it does not hurt production latency.

Trap: resharding "later when it hurts" means doing it while the system is already overloaded. Plan the partition count (many logical shards, fewer physical machines) early.
What are logical shards vs physical shards and why start with many logical ones? Senior

A logical shard is a unit of data placement (for example a database schema or a hash slot); a physical shard is a server hosting several logical ones. Start with, say, 256 logical shards on 4 servers. Scaling out then means moving whole logical shards to new servers (a copy and routing flip), never re-splitting rows. Instagram famously used many logical shards (PostgreSQL schemas) mapped onto fewer physical servers for this reason. The limit is the number of logical shards: you cannot exceed it without a real split.

Should rebalancing be automatic or manual? Senior

Fully automatic is convenient but risky: moving data is expensive, and rebalancing triggered by a node that is merely slow (not dead) adds load to an already struggling cluster, potentially cascading into more nodes being declared dead. A common compromise is automatic proposal with a human approval, or automatic with strict rate limits and delay before treating a node as permanently gone.

What alternatives to a hash ring exist? Senior
  • Rendezvous (highest random weight) hashing: for each key compute a score for every node, pick the highest. Node removal moves only its keys, no ring or vnodes needed, but lookup is O(N).
  • Jump consistent hash: tiny, fast, evenly distributed, but only supports growing or shrinking the node count at the end (numbered buckets).
  • Fixed slots (Redis Cluster) with an explicit slot-to-node table.

Cross-shard queries, joins, transactions and indexes

What is a scatter-gather query and why is it a problem? Intermediate

A query that does not include the shard key must be sent to every shard, and the results merged. Problems: latency is set by the slowest shard (tail latency amplification: if each shard has 1% slow requests and you query 100 shards, most requests hit at least one slow shard), load grows with shard count so adding shards does not help throughput, and sorting plus pagination across shards is awkward (to get page 3 sorted globally you need the top N from each shard). Mitigate by designing queries around the shard key, using secondary indexes, or sending such queries to a search or analytics system.

How do you handle joins across shards? Intermediate
  • Co-locate related data using the same shard key (orders and order_items both by customer_id), so joins stay on one shard.
  • Replicate small reference tables (countries, currencies, product categories) to every shard.
  • Denormalise: copy the needed fields into the row (customer name in the order).
  • Application-side join: fetch from one shard, then query the other by ids; fine for small result sets.
  • Ship to a warehouse or search index for cross-entity analytics.
  • Distributed SQL engines (Vitess, Citus, CockroachDB) can run distributed joins, but they are slow if large data must move over the network.
How do you do a transaction that spans shards? Senior

Best answer first: design so you do not need to (keep a transaction's data on one shard). If you must:

  • Two-phase commit (2PC): a coordinator asks all shards to prepare (and lock), then to commit. Gives atomicity, but blocks if the coordinator dies after prepare, holds locks across network round trips and lowers availability and throughput. Used inside distributed SQL databases (Spanner, CockroachDB, with consensus-replicated participants to reduce the blocking risk).
  • Saga: a sequence of local transactions, each with a compensating action to undo it (reserve inventory, charge card; if charge fails, release inventory). No global lock, but only eventual consistency and intermediate states are visible; compensations must be idempotent.
  • Outbox / events: write the state change and an outbox event in one local transaction; a relay delivers the event so the other shard applies its part at least once, with idempotent handling.
  • TCC (try-confirm-cancel): reserve resources first, then confirm or cancel.
Say: "2PC when I need hard atomicity and can accept the latency, sagas when services or shards are independent and eventual consistency with compensation is acceptable."
Why is two-phase commit called a blocking protocol? Senior

After a participant votes "yes" in the prepare phase, it has promised to commit if told to and must keep its locks. If the coordinator crashes before sending the decision, participants cannot decide alone (the others may have committed or aborted) and hold locks until the coordinator recovers. That can freeze rows for a long time. Mitigations: replicate the coordinator's decision log with consensus, use timeouts with manual resolution, or avoid 2PC with sagas.

Local vs global secondary indexes in a sharded database: what is the difference? Senior
Local (document-partitioned)Global (term-partitioned)
Index livesWith each shard, covering only that shard's rowsPartitioned by the indexed value, separate from the data shards
WriteCheap: one shard updates data and index togetherExpensive: one write touches the data shard and the index shard(s), often asynchronously (index lags) or via a distributed transaction

ExamplesMongoDB, Cassandra local indexes, Elasticsearch, Postgres per-shardDynamoDB GSI (eventually consistent), Spanner/CockroachDB indexes (transactional)

Pick local indexes for write-heavy workloads where reads can include the shard key, global for read-heavy lookups by a non-key attribute (find user by email).

How do you enforce a unique constraint (for example unique email) across shards? Senior

A per-shard unique index cannot see other shards. Options: shard by the unique attribute (then it is local, but other lookups suffer); a separate lookup table keyed by email (sharded by email) that you insert into first, as the arbiter, then create the user; a global unique index in a distributed SQL database; or a single small strongly consistent store for uniqueness claims. Handle failure between the claim and the insert (clean up orphaned claims).

How would you paginate globally sorted results across shards? Senior

Offset pagination is expensive: for page 100 of size 20 each shard must return its top 2,000 rows and the merger discards most. Use keyset (cursor) pagination: the client sends the last seen sort key and id; each shard returns the next page after that key; merge the sorted lists and take 20. Or serve the sorted listing from a dedicated search index or precomputed table, and be clear about whether the result is a consistent snapshot.

Unique ID generation across shards

Why does auto-increment not work across shards, and what are the options? Intermediate

Each shard's counter is independent, so shard A and shard B both hand out id 1001. Moving a row to another shard may also collide. Options:

  • Stride allocation: with N shards, shard k issues k, k+N, k+2N... Simple, but adding shards is awkward and ids are not time-ordered.
  • Ticket server / ID service: a central database or service hands out ids (Flickr's approach with two MySQL servers, odd and even). Single point of failure and bottleneck unless batched.
  • Range allocation: each app server asks a coordinator for a block of 1000 ids and uses them locally. Fast; ids have gaps after crashes, which is fine.
  • UUID: 128-bit random, no coordination. Large, poor index locality.
  • Snowflake-style: time plus machine plus sequence bits.
How does a Snowflake-style ID work and what are its failure modes? Intermediate

A 64-bit integer composed of: 1 unused sign bit, about 41 bits of millisecond timestamp (roughly 69 years from a custom epoch), about 10 bits of worker/machine id (1,024 workers), and about 12 bits of per-millisecond sequence (4,096 ids per ms per worker). The exact split varies by implementation.

  • Pros: no coordination on the hot path, roughly time-sortable (good B-tree insert locality), 64-bit fits in a long.
  • Cons / failure modes: clock going backwards (NTP step) can generate duplicates or force the generator to wait or refuse; worker ids must be unique (assign through ZooKeeper, etcd or config; duplicates cause collisions); more than the sequence limit in one ms must wait; ids leak creation time and rate; ordering is only approximate across workers.
UUID v4 vs UUID v7 / ULID vs Snowflake: how do you choose? Intermediate

UUID v7 / ULID128 bitYes (time prefix)NoneIndex-friendly like Snowflake, no worker id to manage

If the id is also the shard key, a time-sortable id under range partitioning creates a hot shard; hash it first.

Why do some systems embed the shard id inside the object id? Senior

Then the router can find the shard from the id alone with no lookup (Instagram's ids encoded timestamp, logical shard id and a per-shard sequence generated inside PostgreSQL; Pinterest-style ids similarly). Downside: the object is stuck to that shard in its id; moving it means changing the id, so use many logical shards and move whole logical shards instead.

Combining replication and sharding; multi-region

How are replication and sharding combined in a real cluster? Intermediate

Every shard is itself a small replication group with its own leader and followers, so the cluster has many leaders, each owning a slice of the keys (MongoDB sharded cluster of replica sets; Kafka partitions each with a leader and followers; HBase region servers over HDFS). Failure of one node triggers failover in just that shard group, leaving the others untouched. Spread a shard's replicas across racks and zones, and avoid placing too many leaders on one machine.

Active-passive vs active-active across regions: what is the difference? Intermediate
Active-passiveActive-active
WritesOne region serves; another is standbySeveral regions take writes
FailoverPromote standby (minutes, some data loss if async)Traffic shifts to remaining regions, little downtime
ComplexityLower: single writer, no conflictsHigh: conflict resolution or data ownership rules
CostStandby capacity often idle (hot, warm or cold)All capacity used, but needs headroom to absorb a lost region
MetricsRPO (data loss window) and RTO (time to recover) largerNear-zero RTO, RPO depends on replication

RPO (recovery point objective) is how much data you can afford to lose, RTO (recovery time objective) how long you can be down.

A practical active-active pattern avoids true conflicts: each user or tenant has a home region for writes and other regions only serve reads, so it is "active-active" at the service level but single-writer per record.

What is geo-partitioning and what does it buy you? Intermediate

Using a location attribute as part of the partition key, so each row lives in the region near its users (EU users' rows in Frankfurt, US users' in Virginia). Benefits: low latency because reads and writes are local, and compliance since data can be pinned to a jurisdiction. Costs: cross-region queries and transactions are slow and complex, a user who travels or moves needs data migration or remote access, and global features (search across all users) need a separate pipeline. CockroachDB (regional by row), Spanner (placement) and Azure Cosmos DB offer this natively.

How do data residency rules (for example GDPR) affect the architecture? Intermediate

Some laws restrict where personal data may be stored or transferred (GDPR limits transfers of EU residents' data outside approved jurisdictions; other countries require local storage). I am describing the concept, not giving legal advice. Design implications:

  • Classify data, and pin personal data to a region (geo-partitioning or per-region deployments, a "cell" per region).
  • Do not replicate regulated data to other regions as a backup or into a global analytics store, unless anonymised or permitted. Backups and logs count as copies.
  • Keep a global directory only with non-personal routing data (user id to region).
  • Support deletion (right to erasure) across replicas, caches, search indexes and backups, with a plan for backups (for example crypto-shredding: delete the per-user encryption key so remaining copies are unreadable).
  • Per-tenant keys and per-region key management.
How does cross-region replication change the latency and consistency trade-offs? Intermediate

Round trips between continents are on the order of 70 to 150 ms. Synchronous cross-region replication adds that to every write, so most systems replicate asynchronously across regions and synchronously within a region (across zones, a few milliseconds). Systems that give strong consistency globally (Spanner, with consensus across regions) pay the latency on writes, and place replicas deliberately. Reads can be served from nearby followers with a bounded staleness. Expect RPO above zero for regional disaster with async replication.

A whole region goes down. What do you need in place beforehand? Senior
  • Replicas of the data in another region, with known lag (that is your RPO).
  • Capacity headroom in survivors (N+1 regions: each must absorb the load of a failed one) or autoscaling that is actually tested.
  • Traffic steering (DNS, global load balancer, anycast) with sensible TTLs and health checks.
  • A decision process: automatic failover vs human (automatic failover on a flaky detection can cause a false-positive failover and data divergence).
  • A failback plan: how the recovered region catches up and how divergent writes are reconciled.
  • Regular game days that actually fail a region.

Backup and point-in-time recovery

Is a replica a backup? Basic

No. A replica faithfully copies mistakes: a bad DELETE, a buggy migration, corruption or ransomware encryption is replicated within moments. A backup is an independent, point-in-time copy you can restore from. You need both: replicas for availability, backups for recovery from logical errors. A delayed replica (intentionally applying changes an hour late) is a cheap extra safety net, but not a replacement for real backups.

What is point-in-time recovery (PITR) and how does it work? Intermediate

PITR lets you restore the database to any chosen moment (for example 14:31:59, just before the accidental delete). Mechanism: periodic full (base) backups plus continuous archiving of the write-ahead log or binlog. To recover: restore the most recent base backup before the target time, then replay the archived log up to the exact timestamp or log position.

  1. Detect the bad event and note its time or log position.
  2. Restore the latest base backup to a new instance (never over the live one).
  3. Replay logs up to just before the event.
  4. Verify, then either switch over or extract the lost rows and merge them into production.

Managed services offer it (for example about 5-minute granularity or continuous, retained for a configured window such as 7 to 35 days, vendor specific).

TypeContainsRestore

How do you take a consistent backup of a sharded database? Senior

Backing each shard up at a different moment can give an inconsistent whole (an order on shard A without the matching payment on shard B). Options: use a database with a global consistent snapshot (Spanner and CockroachDB timestamp-based backups); quiesce writes briefly; coordinate shards to a common logical timestamp or log position, then use PITR on each shard to that same instant; or accept per-shard consistency and design recovery with reconciliation (events replayed). Take backups from a follower so the leader is not loaded, and always test restores: an untested backup is not a backup.

What are RPO and RTO and how do they drive the replication and backup design? Basic

RPO: the maximum data loss you accept, measured in time. RTO: the maximum time to restore service. RPO of zero demands synchronous or quorum replication; RPO of minutes allows async plus log archiving; RPO of 24 h allows nightly backups. RTO of seconds needs hot standby with automatic failover; hours allows restoring from backup. Tighter targets cost more, so ask the business what each system actually needs.

When NOT to shard

Why should sharding be a last resort, and what do you try first? Intermediate

Sharding adds permanent complexity: you lose cross-shard joins, transactions and unique constraints, queries need the shard key, operations (schema changes, backups, resharding) multiply by the shard count, and bugs become harder to debug. Try in this order:

  1. Fix the queries and indexes: missing index, N+1 queries, full scans. Many "scale problems" are one slow query.
  2. Cache read-heavy data (Redis, CDN, application cache); a good hit ratio can remove 90% of the read load.
  3. Vertical scaling: a bigger machine, more RAM, faster NVMe. Modern single servers handle terabytes and tens of thousands of queries per second; it is the simplest scaling step.
  4. Read replicas for read-heavy load (accept lag).
  5. Functional / vertical partitioning: move a service's tables to its own database; split a hot table's cold columns.
  6. Archive or purge old data; partition tables by time inside one server (native table partitioning) to keep indexes small.
  7. Batch and queue writes to smooth bursts.
  8. Only then shard, or move to a distributed database that shards for you.
What signals tell you it really is time to shard? Intermediate
  • Write throughput on the primary is near its ceiling even after tuning, and cannot be batched away.
  • Dataset is approaching the largest practical node size (storage, backup and restore time becoming too long for your RTO).
  • The hot working set no longer fits in memory and the cache hit ratio falls.
  • Maintenance (vacuum, index builds, schema changes) takes unacceptably long on one huge table.
  • Regulatory or latency needs to place data in separate regions.
Say: "I would not shard at 100 GB. I would shard when measured write load or data size can no longer fit one machine after the cheaper options are used, and I would do it with a plan for the shard key and for resharding."
Instead of manual sharding, when would you use a distributed SQL or NoSQL database? Senior

If you expect to need horizontal scale and can accept the product's model: DynamoDB, Cassandra or Bigtable (partitioned key-value or wide column, limited queries), or Spanner, CockroachDB, YugabyteDB, TiDB (SQL with automatic range sharding and consensus replication). They handle splitting, rebalancing and failover for you, at the cost of higher write latency for cross-node transactions, learning curve, and cost. Middleware like Vitess or Citus keeps MySQL or PostgreSQL but automates sharding. Hand-rolled application-level sharding is the highest-effort option.

Scenarios and real-life problems

Your primary database is at 90% CPU, 80% of traffic is reads. What do you do? Intermediate
  1. Find the top queries (slow query log, pg_stat_statements); fix indexes and N+1 patterns.
  2. Add a cache for hot reads.
  3. Add read replicas and route tolerant reads there, with leader reads for read-your-writes paths.
  4. Watch replica lag, and add a replica health check in the router.
  5. Only if writes are the bottleneck after this, plan sharding.
You sharded a table by created_at range and the newest shard is melting while others are idle. Fix it. Intermediate

This is the monotonic key hotspot: all inserts hit the latest range. Change the shard key to a hash of a high-cardinality id (user or order id), or use a composite key (hash prefix, then time). If you need time-range queries, keep a time-ordered secondary structure (time-partitioned analytics store) fed from the main one. Migrate with the online resharding process (copy, CDC catch-up, cut over). A compromise: bucket keys as (hash(id) mod 16, timestamp) so inserts spread across 16 ranges and a time query asks 16 ranges.

You add a node to a modulo-hash cache cluster and the database melts. Why, and how do you prevent it? Intermediate

Going from N to N+1 with mod N remaps most keys, so most lookups miss simultaneously and fall through to the database (a cache stampede). Use consistent hashing so only about 1/(N+1) of keys move, add nodes gradually or warm them first, and protect the database with request coalescing and rate limits.

After a network partition, your cluster has two leaders that each accepted writes for 4 minutes. What now? Senior
  1. Stop the bleeding: fence one side (shut down or cut off the one you will discard), so only one leader remains.
  2. Pick the surviving side (usually the one with a majority or more valuable writes).
  3. Extract the writes from the losing side's log for the divergent window; compare to the surviving data.
  4. Reconcile: replay safe, non-conflicting writes (new rows); for conflicts apply business rules or manual review; notify affected customers if money is involved.
  5. Rebuild the losing node from the survivor.
  6. Postmortem: add quorum-based election, fencing tokens, and correct timeouts. GitHub's 2018 incident (a short network partition between datacenters leading to divergent writes and a long recovery) is a well-known example of this class of problem.
Users complain that after saving a setting the old value shows for a few seconds. Your reads go to replicas. What are your options? Intermediate

Classic read-your-writes problem. Quickest: after a write, read that user's data from the leader for the next 10 to 30 seconds (flag in session or cache). Better: return the new value in the write response and let the UI render it (optimistic update). Rigorous: pass the write's log position and let the router choose a replica that has applied it. Do not just make everything read from the leader; that gives up the scaling you added replicas for.

One tenant is 40% of your traffic and their shard is saturated. What do you do? Senior

Short term: move the other tenants off that shard (or give the whale its own dedicated shard and hardware), add replicas and cache for their reads, rate limit if needed. Medium term: if the tenant alone exceeds one shard, introduce a second-level shard key inside that tenant (for example tenant plus entity id hash). Use a directory-based mapping so such exceptions are possible. Long term: capacity plan per tenant and price accordingly.

After a failover, new rows reuse ids that had already been given to other systems. How can that happen? Senior

Async replication: the old leader had issued auto-increment ids up to 1,100 and shown them to clients or sent them to a cache or other services, but the promoted follower had only seen up to 1,050. It then issues 1,051 to 1,100 again for different rows, so downstream systems (cache, search, other services) mix up two entities. GitHub reported an issue of this type in 2012 with MySQL failover and Redis-held ids (hedged on details). Prevent with semi-sync replication, ids from a source not tied to a single replicated sequence (UUIDs, a separate ID service), or bumping the sequence ahead after failover.

Someone ran DELETE without a WHERE clause on production an hour ago. Replicas show the same. Recover. Intermediate

Replicas will not help (they replicated the delete); a delayed replica (if you have one) might, if it has not yet applied it: stop its replay immediately. Otherwise use PITR: restore the last base backup into a new instance, replay logs to just before the delete, then export the missing rows and merge into production (production has taken new writes since). Post-incident: restrict direct production access, require review for manual statements, use transactions with row-count checks, and run restore drills.

A viral post's like counter is a single row updated thousands of times per second and its shard is locking up. What do you do? Senior

Row-level lock contention on one hot row. Options: split the counter into k sub-counters (salted keys) and sum on read; buffer increments in memory or Redis and flush batched totals every second; use an append-only event stream and aggregate asynchronously; accept an approximate count for display while keeping exact data elsewhere. Use CRDT-style counters in leaderless stores.

Users in Asia see 300 ms page loads because your database is in the US. Options? Intermediate
  1. Cache and CDN for static and read-mostly content.
  2. Add an Asia read replica for reads; send writes to the US leader (writes stay slow) and handle read-your-writes for the writer.
  3. If writes also need to be local: home-region per user with geo-partitioning, or multi-leader with a conflict strategy.
  4. Keep the chatty parts (several sequential queries per page) in one region with the data to avoid many cross-ocean round trips.
