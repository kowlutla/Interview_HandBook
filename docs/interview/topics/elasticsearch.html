Mental model: the 8 ideas everything hangs on

One line: Elasticsearch is a distributed search engine built on Apache Lucene. You store JSON documents, it builds an inverted index (word to documents) at write time, and every search is fast because it looks words up instead of scanning documents. It is near real time, not transactional.
  1. An inverted index is the heart. At write time text is cut into terms. For each term ES stores the list of documents that contain it. A search looks up terms, it does not read documents.
  2. Analysis happens before indexing and before searching. The analyzer turns "Running Shoes!" into the terms run and shoe. If the two sides use different analysis, matches silently fail.
  3. Mapping is your schema. It decides which fields are searchable text (text), exact values (keyword), numbers, dates, or nested objects. Most existing fields cannot be changed in place. Plan the mapping, do not rely on guessing.
  4. An index is split into shards. A shard is a complete Lucene index. A document lives in exactly one primary shard, chosen by hashing. Each primary can have replica copies for safety and read speed.
  5. A shard is made of immutable segments. New data goes to a new small segment. Updates and deletes mark the old copy as deleted. Background merges clean up. This is why writes are fast and why updates are costly.
  6. Search is scatter and gather. Any node you call becomes the coordinating node. It asks one copy of every shard, merges the top hits, then fetches the documents.
  7. Near real time. A new document is searchable only after a refresh (default every 1 second). Get by id is real time; search is not.
  8. Elasticsearch is not your system of record. No multi-document transactions, no joins like SQL. Keep the truth in a database and feed ES from it.

1. Fundamentals and how search works

What is Elasticsearch, and what is it good at? Basic

What the interviewer is testing: whether you can place ES correctly: a search and analytics engine, not a general database.

Elasticsearch is a distributed search and analytics engine built on top of the Apache Lucene library. You send it JSON documents over a REST API, and it indexes every field so you can search them in milliseconds. It is very good at full-text search (find "red running shoes" with typos and ranking), filtering and sorting large data sets, aggregations such as counts per category or per day, and log or event analytics (the "ELK" or Elastic stack). It scales out by splitting an index into shards over many machines. It is not good as the only store for money or orders: it has no multi-document transactions, no foreign keys, and a write is visible in search only after about a second. I describe it as a very fast read-optimised view of data that lives somewhere else.

Likely follow-ups
  • Is it a NoSQL database? It is a document store with a search engine inside, so loosely yes, but treat it as a secondary index.
  • What is the ELK stack? Elasticsearch, Logstash (ingest) and Kibana (UI). Beats and Elastic Agent now often replace Logstash for shipping data.
Explain the vocabulary: cluster, node, index, document, shard, replica, segment. Basic

What the interviewer is testing: shared language. Everything else builds on it.

A cluster is a group of nodes that work together. A node is one running ES process (usually one per machine or container). A document is one JSON object, like a row. An index is a named collection of documents with the same kind of structure, like a table. An index is divided into shards so it can be spread over nodes. Each document lives in exactly one primary shard, and each primary can have replica shards, which are full copies on other nodes. Inside a shard, data is stored in segments, which are small immutable files written by Lucene. Every shard is a standalone Lucene index, which is why an ES index is really "many Lucene indexes behind one name".

Common mistakes: saying an ES index is the same as a database. A relational "database" maps better to a whole cluster or a set of indices; an ES index maps more closely to a table.
What is an inverted index and why does it make search fast? Basic

What the interviewer is testing: the single most important concept of the topic.

A normal index like a book's table of contents goes from page to words. An inverted index goes the other way: from each word to the pages (documents) that contain it. When a document is indexed, ES splits the text into terms, and for every term it keeps a sorted list of document ids, called a postings list. It also keeps how often the term appears in the document and where (positions), which is used for scoring and phrase search. The list of all terms is kept sorted in a dictionary, so finding a term is a quick lookup. To answer "quick AND fox", ES fetches the two postings lists and intersects them. It never reads the documents themselves. Cost depends on the size of the postings lists, not on the total number of documents, which is why a search over a billion documents can still take milliseconds.

Likely follow-ups
  • Why can ES not search for text in the middle of a word cheaply? The dictionary is sorted by the start of the term, so prefixes are cheap and "contains" needs to check many terms.
  • Does the inverted index also help sorting and aggregations? No. Those use doc values, a column-style structure (see the doc values question).
What happens inside the cluster when I send a search request? Intermediate

What the interviewer is testing: the distributed query model, and why deep pagination and big result sizes hurt.

The node that receives your request becomes the coordinating node. Search runs in two phases. In the query phase, the coordinator sends the query to one copy (primary or replica) of every shard of the index. Each shard runs the query locally and returns only a small list: document ids and scores for its top from + size hits. The coordinator merges these lists and picks the global top hits. In the fetch phase, the coordinator asks the owning shards for the full _source of only those winning documents, and returns the response. Because each shard must return from + size entries, asking for page 1000 makes every shard do heavy work. Replicas are used round-robin so reads spread over copies.

Likely follow-ups
  • What if one shard is down and has no replica? You get a partial result, and the response says how many shards failed. Check _shards.failed.
  • What is the "search_type"? Default query_then_fetch. dfs_query_then_fetch first gathers global term statistics for more accurate scores on tiny or skewed indices.
Why is Elasticsearch called near real time? Basic

What the interviewer is testing: the number one surprise for developers: "I wrote it, why can I not find it?".

When you index a document, ES writes it to memory and to a transaction log, but the document is not searchable yet. It becomes searchable at the next refresh, which by default runs every one second (index.refresh_interval). So search shows data with a delay of about a second. This is "near" real time. Fetching a document by id with GET index/_doc/id is real time, because it can read from the transaction log. If a test or a user flow needs read-your-own-write in search, you can pass refresh=wait_for on the write (it waits for the next scheduled refresh) or, rarely, refresh=true (forces a refresh now, expensive). Do not use a forced refresh after every write in production.

Likely follow-ups
  • Since 7.0, shards that got no search for 30 seconds ("search idle") skip scheduled refresh until a search arrives, to save work; the first search then triggers a refresh.
What are doc values, and how are they different from the inverted index? Intermediate

What the interviewer is testing: whether you know why sorting and aggregating work on some fields and fail on others.

The inverted index answers "which documents contain this term". That is the wrong direction for sorting or counting, where you need "what is the value of this field for document 17". For that, Lucene writes doc values: an on-disk, column-oriented structure per field, mapping each document to its value. Doc values are built at index time, stored on disk, and read through the OS file cache, so they do not live on the heap. They are on by default for keyword, numbers, dates, booleans and so on. They are not available for analysed text fields. If you try to sort or aggregate on a text field, ES refuses, because it would need fielddata, which loads all terms into heap. The normal fix is a keyword sub-field.

Likely follow-ups
  • Can I save disk by turning doc values off? Yes with doc_values: false on a field you never sort, aggregate or script on.
  • What is _source? The original JSON, stored as is and returned in hits. It is separate from the index and from doc values.
When would you use Elasticsearch instead of a relational database, and when not? Intermediate

What the interviewer is testing: sound judgement about using a tool for its strengths.

Use ES when the main need is searching text with ranking, typo tolerance, autocomplete, filtering on many fields at once, faceted counts (the "12 results in Shoes" side panel), or analysing large volumes of logs and events. A relational database can do LIKE '%word%', but it scans, has no relevance ranking and no stemming. Do not use ES as the main store for transactional data: there are no multi-document transactions, no joins as you know them, no foreign keys, a document change is visible after a refresh, and in rare failures acknowledged writes can be lost or diverge if you misconfigure. The common design is: database is the source of truth, ES is a search copy kept in sync. For small data and simple search, the database's own full-text (PostgreSQL tsvector, MySQL FULLTEXT) is often enough and avoids a second system.

How does Elasticsearch compare with Solr and OpenSearch? Intermediate

What the interviewer is testing: market awareness; the question is about trade-offs, not a winner.

Elasticsearch and Solr are both built on Lucene, so core indexing and scoring (BM25) are similar. Solr is older, an Apache project, configured by XML or the schema API, and clustered through SolrCloud with ZooKeeper. Elasticsearch is JSON and REST first, easier to start, with a very strong aggregation framework, a larger ecosystem (Kibana, Beats, ingest pipelines) and more built-in analytics, which is why it won log and observability use. OpenSearch is a fork of Elasticsearch 7.10.2 that AWS created in 2021 after Elastic changed its license (from Apache 2.0 to SSPL and the Elastic License, 7.11). Since then the two have drifted: APIs are almost the same for basic use, but newer features and client libraries differ, and the official Elastic clients from 7.14 onward refuse to talk to OpenSearch. Elastic added the AGPL as an extra license option in 2024. As a developer: match client libraries to the server product, and do not assume a feature from one exists in the other.

Likely follow-ups
  • Which would you choose for a new project? Usually what the company already runs or what the cloud provider offers managed. Features rarely decide it for ordinary search.
What is Lucene's role, and what does Elasticsearch add on top? Intermediate

What the interviewer is testing: layering. It helps you reason about limits that come from Lucene.

Lucene is a Java library that can build and search an index on one machine: analysis, inverted index, segments, scoring, doc values. It knows nothing about networks or JSON. Elasticsearch wraps many Lucene indexes (the shards) and adds the distributed parts: cluster state and master election, routing of documents to shards, replication, the REST API and Query DSL, aggregations framework, the transaction log, index lifecycle, security and so on. Several limits are inherited from Lucene: a segment is immutable, one shard can hold at most about 2.1 billion documents (the Lucene limit of 2^31 documents per index), and updates are really delete plus insert.

2. Analysis: analyzers, tokenizers and filters

What is an analyzer, and what are its parts? Basic

What the interviewer is testing: the pipeline that decides what words are stored and matched.

An analyzer turns a string into a list of terms. It has three stages, always in this order. Zero or more character filters clean the raw text first (for example strip HTML tags). Exactly one tokenizer splits the text into tokens (for example split on spaces and punctuation). Zero or more token filters change the tokens: lowercase them, remove stop words like "the", stem words ("running" becomes "run"), add synonyms, or cut them into n-grams. The result is what goes into the inverted index. The default standard analyzer uses the standard tokenizer (Unicode word splitting) and a lowercase filter, and does no stemming and, since 7.0, no stop word removal by default.

POST _analyze
{ "analyzer": "english", "text": "The Running Shoes" }
// tokens: run, shoe   (stop word "the" removed, stemmed)
Likely follow-ups
  • Which analyzers ship with ES? standard, simple, whitespace, stop, keyword, pattern, and language analyzers such as english.
Is the same analyzer used when indexing and when searching? What goes wrong if they differ? Intermediate

What the interviewer is testing: the classic "why does my search not match" root cause.

By default a text field uses the same analyzer at index time and at search time, and the match query analyses your query string with the field's analyzer. That is what makes "Shoes" match a stored "shoe": both become shoe. You can set a different search_analyzer on purpose. The standard use is autocomplete: at index time cut "laptop" into edge n-grams (l, la, lap, ...), and at search time use a plain analyzer so the typed "lap" is not cut again. If the two sides are mismatched by accident, for example you stored with stemming and query a term query (which does no analysis) with "Shoes", you get zero hits, since the stored term is shoe. The usual debugging step is to call _analyze on both the field and the query text and compare.

"title": { "type": "text",
           "analyzer": "autocomplete_index",
           "search_analyzer": "standard" }
Build autocomplete (search as you type). What options exist and what are the trade-offs? Senior

What the interviewer is testing: practical design of a very common feature.

Options, from simple to heavy. (1) A prefix query on a keyword or text field: no setup, but slow on large data because it expands to many terms. (2) Edge n-grams: a custom analyzer with the edge_ngram token filter (for example min 1, max 20) stores every prefix of each word at index time, so a lookup is an ordinary term match. It is fast at search but makes the index bigger. (3) The search_as_you_type field type (since 7.2) creates the n-gram sub-fields for you and works with multi_match of type bool_prefix. (4) The completion suggester: an in-memory finite-state structure, extremely fast, for prefix suggestions of known strings, but it matches prefixes only, and the data sits in heap-like memory structures. For typo-tolerant ranking of whole products I would use edge n-grams or search_as_you_type plus fuzziness, and keep completion suggester for query suggestions.

"settings": { "analysis": {
  "filter": { "edge": { "type": "edge_ngram", "min_gram": 1, "max_gram": 15 } },
  "analyzer": { "autocomplete_index": {
      "tokenizer": "standard", "filter": ["lowercase", "edge"] } } } }
Common mistakes: using the n-gram analyzer also at search time. The query "lap" is then cut into "l", "la", "lap" and matches everything.
How do stemming, stop words and synonyms work, and where should synonyms be applied? Intermediate

What the interviewer is testing: practical search-quality knowledge and awareness of reindex cost.

Stemming cuts words to a root ("running", "runs" to "run") so different forms match. It increases recall but can over-match ("university" and "universe"). Stop words are very common words (the, a, of) removed to save space; the standard analyzer no longer removes them (since 7.0), because modern scoring already handles common words and removing them breaks phrases like "to be or not to be". Synonyms make "tv" and "television" equal. If you expand synonyms at index time, changing the list needs a full reindex. If you apply them at search time (a search_analyzer with a synonym filter marked updateable), you can change the list and reload it without reindexing, so search-time is the usual advice. Newer versions (8.10 and later) also offer a synonyms API for managing sets, which I would mention only as "check your version".

A user searches "Müller" and the stored name is "Mueller". How do you think about this? Intermediate

What the interviewer is testing: handling accents and language-specific cases.

First I look at what the analyzer does with both words using _analyze. The default standard analyzer lowercases but keeps accents, so müller and mueller are different terms. To treat accented letters as plain, add the asciifolding token filter (so "ü" becomes "u") to a custom analyzer, which then matches "Muller" but still not "Mueller". The German-specific mapping "ü to ue" needs a character-level mapping filter or the german_normalization filter. The plan: pick the right language rules for the data, put them in the analyzer for both index and search, keep a keyword sub-field for exact display and sorting, and reindex, since changing an analyzer changes the stored terms.

3. Mappings

What is the difference between the text and keyword field types? Basic

What the interviewer is testing: the most common mapping decision, and the root of many bug reports.

A text field is analysed: the string is split into terms, lowercased and so on. Use it for content that people search by words, like a product description. It supports full-text queries and relevance scoring, but not sorting or aggregations. A keyword field is stored as one single term, exactly as given. Use it for exact values: ids, status codes, email addresses, country codes, tags. It supports term filters, sorting and aggregations, and has doc values. A text field is not good for exact matching because "Blue Shirt" was cut into blue and shirt, and a keyword field is not good for word search because only the full string matches. When you need both, use a multi-field: title as text plus title.keyword as a keyword sub-field.

"title": { "type": "text",
           "fields": { "raw": { "type": "keyword", "ignore_above": 256 } } }
Likely follow-ups
  • What does ignore_above do? Strings longer than that are not indexed into the keyword field (the dynamic default is 256), which protects against huge terms.
  • Should a numeric id such as an order number be a number or a keyword? If you never range-query it, keyword is usually better. Numeric types are optimised for ranges, keyword for exact lookups.
What is dynamic mapping, and what are its pitfalls? Intermediate

What the interviewer is testing: production hygiene. Many outages begin with "we let ES guess".

When a document has a field ES has not seen, dynamic mapping guesses the type from the first value: a string becomes text plus a keyword sub-field, a whole number becomes long, a decimal becomes float, a date-looking string becomes date, and so on. It is convenient but dangerous. The first value decides forever: if the first document has "price": 10 it becomes long, and a later 10.5 is truncated or rejected. A string like "2024-01-05" becomes a date, and the next value "N/A" fails to index. Every string gets two fields, doubling cost. And any new key creates a new field, so user-controlled keys can explode the mapping. The fix: define explicit mappings through an index template, and set dynamic to strict (unknown fields are rejected) or false (kept in _source but not indexed) for objects whose shape you do not control.

"mappings": { "dynamic": "strict",
  "properties": { "id": {"type":"keyword"}, "price": {"type":"scaled_float","scaling_factor":100} } }
What is a mapping explosion and how do you prevent it? Senior

What the interviewer is testing: whether you can spot a design that will fail at scale.

A mapping explosion means the index has far too many fields. It happens when the field names come from data, for example a map of {"attr_123": ...} per user, or a log line that uses an id or an IP address as a JSON key. Each unique key becomes a new field in the mapping, which is part of the cluster state. The cluster state is kept on every node and updated through the master, so thousands of fields slow down every mapping update, bloat memory, and can make the cluster unstable. ES protects you: index.mapping.total_fields.limit is 1000 by default, depth limit is 20, and the number of nested fields is limited to 50. Hitting the limit makes indexing fail with an error. The right fix is to change the data shape, not to raise the limit: turn the dynamic map into an array of key-value objects ([{"k":"attr_123","v":"red"}]) with a nested or plain mapping, or use the flattened field type, which indexes a whole object as one field of keywords. In 7.11 and later, runtime fields help with fields you only need sometimes.

Likely follow-ups
  • How do you find such an index? Look at the size of GET index/_mapping and at index settings; monitoring will also show cluster state size growing.
Can you change the mapping of an existing field? Intermediate

What the interviewer is testing: do you know that the answer is "mostly no, so plan reindexing".

You can add new fields at any time, and you can add a new multi-field or change a few parameters that do not alter stored data (like ignore_above, or adding a sub-field, though that only applies to documents indexed afterwards). You cannot change the type of an existing field, or its analyzer, because the terms already written in the segments were produced by the old settings and segments are immutable. The standard procedure is: create a new index with the corrected mapping, copy the data with the _reindex API, then switch an alias from the old index to the new one, and delete the old index. This is why applications should always read and write through an alias, not through a physical index name.

Likely follow-ups
  • Any shortcut? A runtime field (7.11 and later) lets you define a field computed at query time over existing data, with slower queries, as a bridge until you reindex.
What is the difference between object and nested fields? Why does it matter? Intermediate

What the interviewer is testing: a classic gotcha where queries return wrong results without any error.

Lucene has no notion of objects inside a document. ES flattens an array of objects into one list per field. Take comments: [{author: "alice", stars: 5}, {author: "bob", stars: 1}]. The object type stores comments.author = [alice, bob] and comments.stars = [5, 1], so the link between "alice" and "5" is lost. A query "author alice AND stars 1" wrongly matches this document. A nested field type fixes this: each object in the array is indexed as its own hidden Lucene document, next to the parent, so the fields inside one object stay together. You query it with the nested query, and aggregate with a nested aggregation. The price: each nested object is an extra Lucene document (so a doc with 100 comments is 101 internal documents), updating one comment reindexes the whole parent, and nested queries are slower. Use nested only when you need to match several fields of the same array element together.

GET posts/_search
{ "query": { "nested": { "path": "comments",
    "query": { "bool": { "must": [
      { "match": { "comments.author": "alice" } },
      { "term":  { "comments.stars": 1 } } ] } } } } }
Likely follow-ups
  • Limits? index.mapping.nested_fields.limit (default 50) and index.mapping.nested_objects.limit (default 10,000 nested objects per document).
How do you model relationships in Elasticsearch? Denormalise, nested or join? Senior

What the interviewer is testing: data modelling for a store without real joins.

The default and best answer is to denormalise: copy the data you search by into the document. An order document carries the customer name and city, so one query filters on them without a join. The cost is duplicated data: when the customer renames, you must update all orders that contain the name, with update_by_query or by re-indexing. Use nested when the child is a small array that belongs to one parent and you need element-level matching. Use the join field type (a parent-child relationship within one index) when children are numerous and change often, and you do not want to reindex the parent each time; the child and parent must be routed to the same shard, and has_child and has_parent queries are significantly slower and use more memory. A fourth option is to join in the application: two queries, the second with ids from the first. I pick denormalise first, nested second, join only when updates of the child dominate, and I say clearly that ES is not built for join-heavy queries.

Likely follow-ups
  • Can there be several joins? The join field allows one relation per index in practice; multiple levels are possible but strongly discouraged.
  • What about lookups across indices at query time? None natively for search. ES has an enrich processor for ingest-time lookups and (8.x) ES|QL joins are still limited, so verify your version.
Which field types would you choose for money, dates, ids, tags and geo? Intermediate

What the interviewer is testing: sound defaults that avoid rounding or format bugs.

Money: never float. Use scaled_float with a scaling factor (100 for cents), or store integer minor units in a long. Dates: use date and state the format (ISO 8601 is the default, plus epoch_millis); dates are stored as milliseconds in UTC. Use date_nanos only if you really need nanoseconds. Ids and codes: keyword. Tags and enums: keyword (arrays are fine, any field can hold several values). Booleans: boolean. IP addresses: ip supports CIDR queries. Coordinates: geo_point for distance and bounding-box queries, geo_shape for polygons. Embeddings: dense_vector with kNN search (8.0 and later). Long text blobs you only display: keep in _source and map with index: false.

What do the mapping options index, enabled, store, _source and norms control? Senior

What the interviewer is testing: practical disk and speed trade-offs in a mapping.

index: false means the field is not searchable but still in _source (and still has doc values for sort if enabled). enabled: false on an object means ES keeps the JSON in _source and ignores it completely: no parsing, no index. _source is the stored original JSON: it is needed for updates, reindex, highlighting and returning documents, so disabling it saves space but breaks _reindex and partial updates, which is rarely worth it. store: true stores a separate copy of a single field for retrieval, rarely needed. norms store field length data for scoring; turn them off (norms: false) on fields where you filter but never rank, to save memory and disk. A common tuning pass on a large index is: keyword where text is not needed, index: false for display-only fields, and no norms on filter-only fields.

What is an index template, and what changed in 7.8? Intermediate

What the interviewer is testing: that mappings are managed as code and applied automatically.

An index template holds settings, mappings and aliases that are applied automatically to any new index whose name matches a pattern, such as orders-*. This is how rolling indices (daily or monthly) get the same mapping without human steps. Before 7.8 there were legacy templates; since 7.8 there are composable index templates, built from reusable component templates (for example one for settings, one for common field mappings) and an index template that lists them. Legacy templates are deprecated. If several templates match, the one with the highest priority wins and they do not merge. A template applies only at index creation: changing the template does not change existing indices. I keep templates in source control and apply them through CI.

4. Query DSL

What is the difference between match and term queries? Basic

What the interviewer is testing: the famous "my term query finds nothing" bug.

A match query is for full-text search. It analyses your query text with the field's analyzer, then looks up the resulting terms. It is the default choice for text fields. A term query is not analysed at all: it looks up the exact value you give in the index. It is right for keyword, numbers, dates and booleans. The trap is a term query on a text field. If the document title is "Quick Brown Fox", the stored terms are lowercase quick, brown, fox. term: {title: "Quick"} finds nothing, because "Quick" with a capital Q is not in the index. Use match for text, or use the .keyword sub-field for an exact whole-string match.

{ "match": { "title": "quick fox" } }                // analysed, either word
{ "match": { "title": { "query": "quick fox", "operator": "and" } } }
{ "term":  { "status": "PAID" } }                      // keyword, exact
{ "terms": { "status": ["PAID", "SHIPPED"] } }         // any of
Likely follow-ups
  • What does a match with two words do by default? It uses OR between the terms, and ranks documents with more matching terms higher. Use operator: and or minimum_should_match to be stricter.
Explain the bool query: must, should, must_not and filter. Basic

What the interviewer is testing: the building block of almost every real query.

The bool query combines other queries. must: all clauses must match, and they add to the score. filter: all must match, but they do not affect the score and can be cached. must_not: none may match, no score, cached. should: optional extras that raise the score when they match; if there is no must or filter, at least one should must match (that is minimum_should_match defaulting to 1 in that case, and 0 otherwise). A typical product search is: must the user's text, filter on category, price range and in-stock, should a boost for promoted items.

{ "query": { "bool": {
    "must":     [ { "match": { "title": "running shoes" } } ],
    "filter":   [ { "term":  { "in_stock": true } },
                  { "range": { "price": { "lte": 100 } } } ],
    "must_not": [ { "term":  { "brand": "acme" } } ],
    "should":   [ { "term":  { "promoted": true } } ] } } }
Common mistakes: putting everything in must. Exact conditions then waste time on scoring and cannot use the filter cache.
What is the difference between query context and filter context, and why does it matter for speed? Intermediate

What the interviewer is testing: the main query-performance habit.

In query context a clause answers "how well does this document match?", so ES calculates a relevance score for it. In filter context a clause answers only "does it match, yes or no?". No score is computed, which is cheaper. In addition, ES can cache the set of matching documents of a filter per segment in the query cache (a bitset) and reuse it for later searches, so a repeated filter such as status = ACTIVE becomes almost free. Anything that is a yes or no condition, like a status, a date range, a tenant id or a category, belongs in filter. Only the text the user typed, where ranking matters, belongs in must or should. The cache applies to filters that are used often, and it is per segment, so heavy merging or constantly changing segments reduce its benefit.

Likely follow-ups
  • Where does constant_score fit? It wraps a filter and gives every match the same score, handy when you want filter behaviour inside a query slot.
How do range queries work, and what should you watch for with dates? Basic

What the interviewer is testing: everyday query writing and the date-math trap.

A range query takes gt, gte, lt, lte on numbers, dates or even keywords (sorted as strings). Numeric and date fields use the BKD tree structure in Lucene, which is fast for ranges. For dates you can use date math like now-7d/d (seven days ago, rounded down to the start of the day). Watch two points. First, time zone: dates are stored in UTC, and a time_zone parameter on the range converts your bounds, which matters for "today" for a user in another time zone. Second, a query with plain now is different every millisecond so it cannot be cached; rounding with /m or /d makes the filter reusable. A range on a text field compares terms alphabetically, which is almost never what you want.

{ "range": { "created": { "gte": "now-7d/d", "lt": "now/d", "time_zone": "+05:30" } } }
Why are wildcard, regexp and leading-wildcard queries slow? What are the alternatives? Intermediate

What the interviewer is testing: understanding of the term dictionary and the cost of "contains" searches.

The term dictionary is sorted from the start of each term. A query like shoe* (prefix) can jump to the right place and read forward, so it is cheap. A pattern like *shoe or *shoe* has no starting point: ES must test every term of the field against the pattern, and for a large field with millions of terms this can take seconds and heavy CPU. regexp has the same problem. By default ES also limits wildcard cost through search.allow_expensive_queries (true by default, but operators can turn it off, and then these queries are rejected). Alternatives: index the data in the shape you will query. Use edge n-grams for prefix and autocomplete, n-grams for "contains", a reversed copy of the field for suffix search, or the wildcard field type (since 7.9) made for log lines and code strings, which uses an n-gram index plus verification. Often the real answer is to use better analysis so a normal match works.

Likely follow-ups
  • Does a query_string query allow leading wildcards from users? It can, unless you set allow_leading_wildcard: false. Never expose raw user input to it unfiltered.
How do match_phrase, multi_match and fuzzy matching work? Intermediate

What the interviewer is testing: the standard search-box toolkit.

match_phrase requires the analysed terms to appear next to each other in the same order, using the positions stored in the index. slop allows some gap, for example slop: 2. multi_match runs one text over several fields, such as title and description. Its type decides scoring: best_fields (default) scores by the best single field, most_fields sums over fields, cross_fields treats the fields as one big field (good for first name and last name), and bool_prefix / phrase_prefix for typing-as-you-go. You can boost per field with title^3. Fuzziness accepts typos: fuzziness: "AUTO" allows 0 edits for 1 to 2 characters, 1 edit for 3 to 5, and 2 edits for longer words (edit distance = insert, delete, replace or swap a letter). Fuzzy is more expensive, so keep prefix_length at 1 or 2 to cut the candidate terms.

{ "multi_match": { "query": "runing shoes", "fields": ["title^3", "description"],
                   "fuzziness": "AUTO" } }
What are query_string and simple_query_string, and should you expose them to users? Intermediate

What the interviewer is testing: safety when a user-typed string goes into a query.

query_string parses a Lucene syntax mini-language: title:shoe AND (red OR blue) -cheap, wildcards, ranges, fuzzy. It is powerful, but invalid syntax raises an error (a user typing an unmatched quote or bracket gets a 400), and a user can write expensive queries such as *a*. simple_query_string supports a safe subset (+ | - " * ( ) ~) and never throws on bad syntax; it just treats it as text. For a public search box, use match or multi_match for the plain case, and simple_query_string if you want operators. Use query_string only for trusted internal users such as a log search tool. Also this is a query injection angle: build queries with the DSL objects, never by concatenating user strings into JSON.

How do you debug why a document matched, ranked high, or why a query is slow? Senior

What the interviewer is testing: a method, not guesswork.

I use four built-in tools. _analyze shows what terms the analyzer produces, which solves most "no match" bugs. GET index/_explain/id (or explain: true in a search) returns the score breakdown for one document: the BM25 parts, term frequency, document frequency, length normalisation and boosts. The _validate/query?explain=true API shows how a query is rewritten into Lucene queries. "profile": true in the search body returns, per shard and per query clause, the time spent in each phase, so you see which clause or which aggregation is slow. For slow queries in production I also read the slow log (index.search.slowlog.threshold.query.warn), which logs queries above a time limit, and I look at the number of shards hit and the size of the response.

GET shop/_search
{ "profile": true, "explain": true, "query": { "match": { "title": "shoes" } } }
How would you add highlighting, "did you mean", and filters with counts to a search page? Intermediate

What the interviewer is testing: can you assemble a real search results page from the features.

One request can return all three. Highlighting: add a highlight block naming the fields; ES returns fragments with the matched words wrapped in tags like <em>, which you then render. Escape the text first, or set encoder: html, to avoid injecting markup. Did you mean: the suggest section with a term or phrase suggester proposes corrections based on terms in the index, when the user's query gets few or no hits. Facets: aggs with a terms aggregation on brand.keyword and a range aggregation on price give the counts for the side panel. To keep the facets stable when the user selects a filter, apply the user's chosen filter with post_filter: the hits are narrowed by it, but the aggregations still see the wider set. All this is one round trip.

5. Relevance and scoring

How does Elasticsearch score documents? Explain BM25. Intermediate

What the interviewer is testing: intuition for ranking, not memorising the formula.

The default similarity is BM25 (default since Elasticsearch 5.0 and Lucene 6; before that it was TF-IDF). The score for a query term in a document is built from three ideas. Term frequency: the more often the word appears in the document, the better, but with diminishing returns: the tenth occurrence adds much less than the second (controlled by k1, default 1.2). Inverse document frequency: rare words matter more. A match on "kubernetes" says more than a match on "the", because few documents contain it. Field length normalisation: a match in a short field (a title) counts more than the same match in a long field (a book), controlled by b (default 0.75). The scores of each query term are summed. Scores are relative and meaningful only inside one query; do not compare them across queries, or treat them as percentages.

Likely follow-ups
  • How is BM25 different from TF-IDF in practice? TF saturates in BM25 instead of growing without limit, so keyword stuffing is less effective.
  • Why do scores look odd on a small index with several shards? IDF is computed per shard by default, so statistics differ. Use dfs_query_then_fetch in tests, or just use fewer shards.
How do you tune ranking: boosts, function_score, and business signals like popularity? Senior

What the interviewer is testing: can you move from pure text relevance to a product ranking.

The simplest tool is a boost on a field or clause: title^3 counts a title match three times as much as a description match. Use should clauses with a boost for soft preferences, such as "promoted" items. For business signals, wrap the query in function_score and combine the text score with a field such as sales count or rating using field_value_factor (with a log1p modifier, so a huge number does not dominate), a gauss decay on date or distance (newer or closer is better), or a script. In 8.x the rank_feature query is a cheaper way to add a stored numeric signal. For learning-to-rank beyond that, the specialised path is the Learning To Rank feature (8.x, licensed) or reranking in the application. My process: build a list of real queries with the expected best results, change one thing, measure with a metric like NDCG or a simple hit-rate on top 3, and keep what helps. Ranking by feel gets worse over time.

{ "function_score": { "query": { "match": { "title": "shoes" } },
    "field_value_factor": { "field": "sales", "modifier": "log1p", "factor": 1 },
    "boost_mode": "sum" } }
What happens to scoring when you add a sort? Intermediate

What the interviewer is testing: a detail that explains "why is _score null".

When you sort on a field such as price or created, results are ordered by that field and ES does not compute or return the score by default: _score is null in the hits. If you also want the score, set track_scores: true. You can sort on _score as one of several keys, for example score first, then date as tie-breaker. Always add a unique tie-breaker (such as _id, or better a keyword id field) at the end, especially with search_after, so that the order is deterministic. In filter-only queries (no relevance needed) it is cheaper to sort by field and skip scoring entirely.

6. Aggregations

What are aggregations, and what kinds are there? Basic

What the interviewer is testing: the analytics half of ES, and the vocabulary.

Aggregations compute summaries over the documents that match the query, in the same request. Think of SQL GROUP BY with functions. There are three families. Bucket aggregations group documents: terms (one bucket per value), date_histogram (per hour, day, month), range, histogram, filters, nested. Metric aggregations compute a number over a bucket: avg, sum, min, max, stats, cardinality (distinct count), percentiles. Pipeline aggregations work on the output of other aggregations: cumulative_sum, moving_avg style, bucket_sort. You nest them: a date_histogram by day, inside each bucket a terms on category, inside that a sum of revenue. They run on doc values, so fields must be keyword, number or date, not analysed text. Set "size": 0 when you want only the aggregation results and no hits.

GET orders/_search
{ "size": 0,
  "query": { "range": { "created": { "gte": "now-30d/d" } } },
  "aggs": { "per_day": { "date_histogram": { "field": "created", "calendar_interval": "day" },
      "aggs": { "revenue": { "sum": { "field": "amount" } } } } } }
Are terms aggregation counts exact? What is shard_size and doc_count_error_upper_bound? Senior

What the interviewer is testing: awareness that distributed top-N is approximate.

Not always. A terms aggregation asks each shard for its own top shard_size buckets, then the coordinator merges them. A term that is, say, 11th on every shard but would be 3rd overall can be missed, and the counts of some returned terms can be a little low, since a shard that did not list the term did not report its count. The response includes doc_count_error_upper_bound and sum_other_doc_count so you can see how big the possible error is. The default shard_size is size * 1.5 + 10; raising it improves accuracy at the cost of more memory and network. If the index has a single shard, or the data is routed so a term lives on one shard, counts are exact. Likewise cardinality is approximate (HyperLogLog++), accurate to a few percent, and the precision_threshold trades memory for accuracy. For a billing report that must be exact, compute it in the database, not from ES.

How do you page through all buckets of an aggregation, and what is too many buckets? Senior

What the interviewer is testing: you know the memory limits and the right tool for big group-bys.

A terms aggregation returns only the top size buckets and cannot be paged. To walk through all combinations (for example every customer and month) use the composite aggregation: it returns a page of buckets plus an after_key, which you pass back to get the next page, like a cursor. ES protects its memory with the search.max_buckets setting (65,535 by default since 7.0, and since 7.x a request that goes over fails with an error). High-cardinality terms aggregations on fields like user id are expensive because they build a hash map in heap for every shard. Also, eager_global_ordinals and execution_hint are tuning options, but the first fix is to filter with the query first to shrink the set, or to pre-aggregate into a summary index with a transform or rollup if the dashboard is read often.

You aggregate on a text field and get an error about fielddata. What does it mean and what do you do? Intermediate

What the interviewer is testing: link between mapping and aggregation behaviour.

The error says that text fields are not optimised for sorting or aggregations by default and that you can enable fielddata. Do not. Fielddata builds an uninverted structure of all terms of the field in the JVM heap, on first use, and keeps it. With big fields this fills the heap and can cause circuit-breaker errors or an out-of-memory crash. Moreover the result would be per analysed word, not per whole value ("new" and "york" instead of "new york"). The correct fix is to aggregate on a keyword field: use the .keyword sub-field if dynamic mapping created one, or add a keyword multi-field to the mapping and reindex.

7. Sorting and pagination

How does from/size pagination work and what is the 10,000 limit? Basic

What the interviewer is testing: the simple method, and why it breaks.

from is the number of hits to skip, size is how many to return (default 10). To return page 3 with 20 per page you send from: 40, size: 20. Under the hood every shard must produce its top from + size entries and the coordinator merges them all, then throws away the first from. The work and memory grow with depth and with the number of shards: page 500 of 20 per page means each of, say, 5 shards builds 10,000 entries. To protect the cluster, index.max_result_window limits from + size to 10,000 by default, and deeper requests fail. The total count is also capped: since 7.0 the response says only "at least 10,000" (relation: "gte") unless you set track_total_hits: true, which makes ES count everything and costs time. For normal user pages, going to page 50 is rare; I would limit the UI to the first few pages and encourage refining the query.

Likely follow-ups
  • Can I raise max_result_window? Yes, but you pay memory per request. It is a sign you need search_after instead.
What is search_after, and how does it differ from from/size and scroll? Intermediate

What the interviewer is testing: the modern answer for deep pagination.

search_after is cursor-based paging. You sort by some fields, and in the next request you pass the sort values of the last hit you received. ES then asks each shard only for documents after that sort position, so each page costs the same no matter how deep you are, and you do not need to hold state in the cluster. You need a deterministic sort with a unique tie-breaker, otherwise rows with equal sort values can be skipped or repeated. It supports "next page" but not "jump to page 40", and it does not by itself give a consistent snapshot: if documents change between requests, the pages shift. To get a stable view pair it with a point in time (PIT). scroll is older: it keeps a snapshot open for bulk export, but since 7.10 the guidance is to use search_after with PIT instead.

// first page
{ "size": 100, "sort": [ {"created":"asc"}, {"id":"asc"} ], "query": {...} }
// next page: pass the last hit's sort values
{ "size": 100, "sort": [ {"created":"asc"}, {"id":"asc"} ],
  "search_after": ["2024-05-01T10:00:00Z", "ord-9981"], "query": {...} }
What is a point in time (PIT) and when do you need it? Senior

What the interviewer is testing: consistency of long reads.

A PIT (added in 7.10) is a lightweight handle that keeps the set of segments as they were at one moment, so many searches see exactly the same data even while indexing continues. You open it with POST index/_pit?keep_alive=1m and get an id. You then search with "pit": {"id": "...", "keep_alive": "1m"}, no index name in the URL, and combine it with search_after. Each response returns an updated PIT id, which you use for the next call. At the end you close it with DELETE _pit. While a PIT is open, old segments cannot be deleted by merges, so keep the keep-alive short and close it. A PIT also gives an implicit tie-breaker field _shard_doc, so you may not need your own. Use it for exports, batch jobs, and "next page" lists where items must not appear twice or be skipped.

When is scroll still used, and what are its drawbacks? Intermediate

What the interviewer is testing: awareness of legacy code and its replacement.

The scroll API (?scroll=1m, then POST _search/scroll with the scroll id) gives a consistent snapshot to read a very large result in batches. It was the standard way to export or reindex data. The drawbacks: each open scroll keeps old segments alive (disk and file handles), there is a limit on open scroll contexts (search.max_open_scroll_context, default 500), the context is tied to one node's state, and it is forward only. If your code forgets to clear it with DELETE _search/scroll contexts remain until the timeout. Since 7.10 Elastic recommends search_after with PIT for deep paging, and scroll for bulk jobs is still accepted. _reindex and _update_by_query use scroll-like snapshots internally. You can also run a "sliced" scroll or PIT with several workers to parallelise an export.

The hit count says 10000 but I know there are more. Why, and should I fix it? Intermediate

What the interviewer is testing: the 7.0 behaviour change and cost awareness.

Since 7.0 the response's hits.total is a lower bound of 10,000 with "relation": "gte", because exact counting forces ES to visit every matching document, and with the bound it can stop early (it can skip documents using block-max techniques when sorting by score). To count everything, set "track_total_hits": true, or give a number such as 50,000 for a custom cap. If all you need is the count, use the _count API. In the UI, "10,000+ results" is accepted by users; showing exact page counts for a deep search is rarely worth the extra cost. Before 7.0 the total was always exact, which is why old code and old blog posts do not mention this.

8. The indexing path

What happens when I index a document? Explain translog, refresh, flush and segments. Senior

What the interviewer is testing: the model that explains NRT search, durability and write speed.

The write goes first to the primary shard. There the document is added to an in-memory buffer (not yet searchable) and appended to the translog, a write-ahead log on disk. By default the translog is fsynced to disk on every request (index.translog.durability: request), so an acknowledged write survives a crash. Then the request is sent to the replicas, which do the same, and only then is the client answered. Every second a refresh writes the memory buffer to a new small segment that lives in the OS file cache. A segment can be searched from that moment, which is why search is near real time. Refresh does not fsync the segment. A flush (automatic, when the translog gets large, about 512 MB by default, or on time) performs a Lucene commit: it fsyncs the segments to disk, and then the old translog can be cleared. On a crash, the shard restores the last commit and replays the translog, so no acknowledged data is lost. Over time many small segments are combined by background merges.

Likely follow-ups
  • What if I set translog durability to async? Fsync happens every 5 seconds (sync_interval), faster, but you can lose up to that window on a crash.
  • Does replication happen before or after the local write? The primary indexes locally first, then forwards the operation to in-sync replicas in parallel, and the client gets the answer after all of them acknowledged.
What are segments and merges, and why are updates and deletes expensive? Senior

What the interviewer is testing: immutability, and its consequences for design.

A segment is an immutable mini-index. Because it can never change, searches need no locks and caches stay valid, but it also means you cannot edit a document in place. A delete only sets a bit in a "live documents" file of that segment: the document is hidden from search, but the space stays. An update is a delete of the old version plus an index of the whole new document into a new segment, even if you changed one field. A merge picks several similar-sized segments (tiered merge policy), writes one new bigger segment without the deleted documents, and removes the old ones. Merging uses disk I/O and CPU in the background, and ES throttles it. Consequences for developers: heavy update workloads create many deleted docs and bigger indices; "partial update" saves network, not index work; and a counter that changes on every request (like page views on each product document) is a bad fit: aggregate it elsewhere or batch the updates.

Likely follow-ups
  • What is force merge? _forcemerge merges down to few segments. Use it only on read-only indices (for example yesterday's logs), never on an index still being written.
  • How does deleting an index differ from deleting documents? Deleting the whole index just drops the files, instantly; deleting many documents leaves work for merges. That is why time-based data uses one index per period.
How does refresh_interval affect indexing speed, and when would you change it? Intermediate

What the interviewer is testing: a basic and safe tuning lever.

Each refresh creates a new small segment. With a 1 second interval, a busy index produces many tiny segments, which merges then have to combine, so a lot of work is spent on that. If search freshness is not critical, raising the interval to 30 seconds, or even larger, greatly reduces segment churn and raises indexing throughput. For a large one-time load, set refresh_interval: -1 (disabled) and replicas to 0, load the data with bulk requests, then restore the settings, optionally force a refresh, and let replicas be created. For user-facing search that must feel instant, keep the 1 second default and accept the cost. If a single user flow needs to see its own write, use refresh=wait_for on that request instead of lowering the interval for everyone.

PUT shop/_settings { "index": { "refresh_interval": "30s" } }
PUT shop/_settings { "index": { "refresh_interval": "-1", "number_of_replicas": 0 } }  // initial load
What are the different ways to update documents? Intermediate

What the interviewer is testing: knowing which API to use and what it costs.

Index (PUT with id) replaces the whole document: you send the full new JSON. Update API (POST index/_update/id) takes a partial doc or a script; ES reads the current _source, merges, and reindexes the whole document, atomically on the shard. It saves network and avoids a race in your code on a read-modify-write, but it is not cheaper for Lucene. Upsert inserts if missing, doc_as_upsert merges. update_by_query applies a script to all documents matching a query, using a snapshot, and it can hit version conflicts (conflicts=proceed continues). delete_by_query removes matches. These "by query" jobs are heavy, run as tasks (use wait_for_completion=false and check the Tasks API), and can be throttled with requests_per_second. For many changes, prefer bulk with explicit ids.

9. Shards, replicas and the cluster

How does Elasticsearch decide which shard a document goes to? Intermediate

What the interviewer is testing: why the primary shard count is fixed, and how routing helps.

The formula is shard = hash(_routing) % number_of_primary_shards. By default _routing is the document id, which spreads documents evenly. Because the shard number depends on the number of primaries, you cannot change the number of primaries on an existing index by simply editing a setting: all documents would map to different shards and could not be found. To change it you use the split API (multiply by a factor), the shrink API (divide), or reindex. A custom routing value (for example a tenant id) keeps all documents of one tenant on one shard. Then a search that passes the same routing value goes to only that shard instead of all of them: much faster for multi-tenant data. Risks: a huge tenant makes a hot shard, and you must pass the routing value on every get, update and search or the document is not found.

How many shards should an index have, and what is over-sharding? Senior

What the interviewer is testing: the most common design mistake on ES projects.

Every shard has a fixed overhead: a Lucene index with its own memory structures, file handles, and an entry in the cluster state. Each search also has to touch every shard of the index. Over-sharding means too many small shards, for example a 5-shard-per-day default on tiny daily indices. Symptoms are high heap use, slow cluster state updates, slow searches (the work is spread over hundreds of tiny shards) and slow recoveries. A good rule of thumb from Elastic is shards of roughly 10 GB to 50 GB each for search workloads (and up to about 50 GB for logs), and no more than about 20 shards per GB of heap on a node (older guidance, still a useful ceiling), and fewer if possible. Under-sharding is the opposite problem: a single 600 GB shard cannot spread over nodes and is slow to recover and to merge. Start from expected data size at one year, divide by a target size, round to a multiple of the node count so shards balance, and, since 7.0, the default of 1 primary is fine for small indices. Use rollover and ILM so time-based indices get created at the right size, not a fixed schedule.

Likely follow-ups
  • Many tenants, each a tiny index? That is a classic over-sharding case. Use a shared index with a tenant id field (filter, plus routing), or filtered aliases.
  • Where does specialist depth start? Node sizing, shard allocation awareness and capacity planning belong to the platform or operations team.
What are replicas for, and how many should you have? Basic

What the interviewer is testing: two purposes of replicas, and the cost.

A replica is a full copy of a primary shard, always placed on a different node than its primary. It does two things. First, availability: if the node with a primary fails, a replica is promoted to primary and no data is lost. Second, read throughput: search requests are spread over primaries and replicas, so more replicas serve more concurrent searches. The default is 1 replica, which doubles the storage, and every write is done on both copies, so write cost goes up. Unlike the primary count, the replica count can be changed at any time with a settings call. With one replica you can survive the loss of one node. A single node cluster with replicas set to 1 will always be yellow, since the replica has no other node to live on. For a bulk load, set replicas to 0 and restore it after, since replicas can be copied faster by file than by re-indexing each document.

What do green, yellow and red mean, and what do you check first? Intermediate

What the interviewer is testing: basic cluster literacy for a developer on call.

Green: all primary and replica shards are assigned. Yellow: all primaries are assigned, but some replicas are not. Data is complete and searchable, but you have lost redundancy. Red: at least one primary shard is unassigned, so part of the data is unavailable, and searches on that index return partial results or errors. The first call is GET _cluster/health?level=indices to find the affected indices, then GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason, and for a specific shard GET _cluster/allocation/explain, which tells in plain text why it is not allocated. Common causes: a node left or restarted (wait for recovery), disk watermarks exceeded (a node with disk usage above the 85% low watermark gets no new shards; above 90% high it drains; 95% flood stage makes indices read-only), too few nodes for the replica count, or allocation filter settings. Deeper fixes such as manual reroute are for the platform team.

What node roles exist, and what should a developer know about them? Intermediate

What the interviewer is testing: enough cluster knowledge to talk to the platform team.

A master-eligible node can be elected as master, which manages the cluster state: which indices exist, their mappings, and where each shard lives. It does not touch your data per request. A data node stores shards and does indexing and search (and may be split into hot, warm, cold tiers for time-based data). An ingest node runs ingest pipelines that transform documents before indexing. A coordinating node (any node) takes the request, fans it out and merges the results. Dedicated master nodes (usually three) are the production standard so heavy searches cannot starve the master. Since 7.0 the cluster uses a new coordination layer with a voting quorum and no longer needs minimum_master_nodes; with 3 master-eligible nodes it tolerates losing one, which prevents split-brain (two halves each electing a master). As an application developer, your client should list several node addresses, or a load balancer, so it survives a node failure.

How does replication work, and what is the consistency guarantee? Senior

What the interviewer is testing: the model in one paragraph, and honest limits.

ES uses a primary-backup model. Each write goes to the primary, which assigns a sequence number, applies the operation, then forwards it to all replica copies in the in-sync set (copies the master knows are up to date). The write is acknowledged to the client when all in-sync copies have applied it. A copy that fails is removed from the in-sync set, so the guarantee stays "every acknowledged write is on all in-sync copies". If the primary fails, a replica from the in-sync set is promoted, and since 6.x, sequence numbers and checkpoints allow a recovering copy to replay only the missing operations. The setting wait_for_active_shards (default 1: just the primary) controls how many copies must be available before a write even starts; it does not change the acknowledgement rule. Reads are not linearizable: a search may hit a replica that has not refreshed yet, so two consecutive searches can return different views. For stronger read-your-write, use preference=_primary or a custom preference value per user so a user sticks to the same copy.

10. Indices, aliases, reindex and bulk

What is an alias and why should applications use aliases? Basic

What the interviewer is testing: the habit that makes reindexing painless.

An alias is a name that points to one or more indices. Your application reads from and writes to products, but behind it the real index is products-v3. When you need a new mapping, you build products-v4 beside it, fill it, and move the alias in a single atomic call, so no request sees a missing or half-built index and no deployment of the app is needed. An alias can also carry a filter (a "view" such as only one tenant's documents) and a routing value. For writes, an alias that points to several indices needs one of them marked is_write_index. Time-series setups use a write alias with rollover so the writer never changes its code.

POST _aliases
{ "actions": [
  { "remove": { "index": "products-v3", "alias": "products" } },
  { "add":    { "index": "products-v4", "alias": "products" } } ] }   // atomic
How do you change a mapping or analyzer with zero downtime? Senior

What the interviewer is testing: a full migration procedure that handles writes during the copy.

The steps: (1) Create products-v4 with the new mapping and settings (replicas 0 and refresh interval -1 to load fast). (2) Start sending new writes to both indices, or to the new one only, by pointing the write alias at v4 while the read alias stays on v3. (3) Run _reindex from v3 to v4 in the background (wait_for_completion=false, tune size and slices for speed). To avoid overwriting newer documents by older copies, set version_type: external and op_type: create or use the source's versions. (4) Compare counts and sample queries, restore replicas and refresh interval. (5) Switch the read alias from v3 to v4 atomically. (6) Keep v3 for a while for rollback, then delete it. If the source of truth is a database, an alternative is to rebuild v4 from the database and let CDC or the application keep both aligned; this avoids the copy-time race and also fixes any previous drift. Mention the one hard part: changes that happen during the reindex, which dual writing or a final catch-up reindex of "modified since start time" resolves.

How does the _reindex API work, and what should you watch? Intermediate

What the interviewer is testing: practical use of the copy tool.

_reindex reads documents from a source index (using a scroll snapshot internally) and writes them to a destination with bulk requests. It reads _source, so all fields you need must be in _source. It can filter with a query, rename or change fields with a script, route through an ingest pipeline, and even read from a remote cluster. It does not copy settings or mapping: create the destination first. Run it as a task (wait_for_completion=false) and check GET _tasks/id; use slices: auto to parallelise; throttle with requests_per_second so it does not starve live traffic. It is a snapshot at start, so changes made to the source afterwards are not included. Version conflicts can be handled with conflicts: proceed.

POST _reindex?wait_for_completion=false
{ "source": { "index": "products-v3", "size": 1000 },
  "dest":   { "index": "products-v4" } }
What are ILM, rollover and data streams? Intermediate

What the interviewer is testing: how time-series data (logs, events) is managed without a script.

Logs and events grow forever, and old data is rarely searched. The pattern is to write to a fresh index and retire old ones. Rollover creates a new index behind a write alias when the current one reaches a size, document count or age condition. Index Lifecycle Management (ILM), since 6.6 and GA in 7.0, is a policy that moves an index through phases: hot (being written), warm (read only, maybe shrunk and force-merged), cold (cheap storage), frozen, and delete after a retention time. A data stream (7.9 and later) packages this for append-only data: you write to one name, ES creates hidden backing indices, rolls them over and ILM manages them; documents need an @timestamp and can only be appended, not updated by id. For a developer, the benefits are: shards of healthy size, cheap retention (dropping an index is instant, unlike deleting documents), and the same mapping through a template.

How does the bulk API work, and how do you use it well? Intermediate

What the interviewer is testing: the main throughput tool, and error handling that people forget.

The bulk API sends many index, create, update and delete actions in one HTTP request, in newline-delimited JSON (an action line, then a source line). It saves round-trips and lets the shards batch their work. Good practice: batches of about 5 to 15 MB (not a fixed number of documents; test and pick the best point), several parallel workers, and a retry with exponential backoff when you get 429 Too Many Requests, which means the write thread pool queue is full. The most important point: bulk is not atomic and the HTTP status is 200 even if some items failed. You must read the response: errors: true means look at each item's own status and error. A mapping conflict on one document fails only that item. Send failed items to a dead-letter store or retry the retryable ones (429, 503), not the permanent ones (400 mapping errors). Use explicit ids for idempotent retries. Clients provide helpers, such as the BulkIngester in the Java API Client (it buffers by size, count and time) or BulkProcessor in the older client.

POST _bulk
{ "index":  { "_index": "shop", "_id": "1" } }
{ "name": "shoe", "price": 49 }
{ "update": { "_index": "shop", "_id": "2" } }
{ "doc": { "price": 55 } }
{ "delete": { "_index": "shop", "_id": "3" } }
Common mistakes: checking only the HTTP status; one huge bulk of 500 MB; no backoff on 429, which makes overload worse.
What is an ingest pipeline, and when would you use it instead of transforming in your code? Intermediate

What the interviewer is testing: where to place transformation logic.

An ingest pipeline is a series of processors that ES applies to a document before it is indexed: rename or remove fields, parse a date, split a string, grok a log line into fields, set a timestamp, look up data with the enrich processor, or call an inference model. You attach it by ?pipeline=name or as the index's default_pipeline. It is a good fit when many different producers write to the index and you want the clean-up in one place, or for log shipping where agents cannot run custom code. Keep it for light work, since it uses CPU on ingest or data nodes, and failures in a processor reject the document unless you set ignore_failure or an on_failure block. For complex business logic, versioned code and tests, I prefer to transform in the application or the stream processor before indexing.

11. Concurrency, durability and consistency

How does optimistic concurrency control work in Elasticsearch? Senior

What the interviewer is testing: safe concurrent updates without locks, and version-number knowledge.

Every document has a _seq_no (a number given by the primary shard to each change) and a _primary_term (a number that increases each time a new primary is elected). When you read a document you get both. When you write, you send them back as if_seq_no and if_primary_term. If another write changed the document since your read, the numbers no longer match and ES rejects your write with 409 version_conflict_engine_exception. You then read again, re-apply your change, and retry. This is optimistic locking: no lock is held; conflicts are rare and detected after the fact. This replaced the older use of the _version number for the same purpose (before 6.7). The _version field still exists, and with version_type=external you can supply your own number, such as a database row version or event timestamp, so ES keeps the newest and rejects stale writes. The update API retries conflicts on its own with retry_on_conflict.

PUT orders/_doc/42?if_seq_no=17&if_primary_term=3
{ "status": "SHIPPED" }
// 409 if another change happened in between
Likely follow-ups
  • Why external versioning for CDC? Events may arrive out of order or duplicated. With the database version as the external version, an older event can never overwrite a newer one.
Can Elasticsearch lose data? What is guaranteed after a write is acknowledged? Senior

What the interviewer is testing: honest understanding of durability and its edges.

With default settings, an acknowledged write has been fsynced to the translog on the primary and on all in-sync replicas. So a single node crash does not lose it. Data can still be lost in these cases: you set translog durability to async and a node crashes inside the sync window; you run with zero replicas and the disk or node is lost; you lose all nodes holding every copy of a shard; or a cluster-wide power loss on hardware that lies about fsync. Elastic's older versions (before 7.0, with the old election logic) could lose or diverge data in some partition cases; the new coordination in 7.0 and sequence numbers removed most of these. Also remember that a write acknowledged is not yet searchable. For real safety: keep at least one replica, run three master-eligible nodes, take regular snapshots (to a repository such as S3) and test restoring, and keep the source of truth in a database so ES can always be rebuilt.

Does Elasticsearch support transactions? How do you handle multi-document consistency? Intermediate

What the interviewer is testing: knowing the limits and the design workarounds.

No. A single document write is atomic (it is fully applied or not at all, and visible as a whole), but there is no transaction across documents or indices. A bulk request is not atomic: some items may succeed and others fail. There is no rollback. So I design so that no invariant depends on several documents changing together: put data that must change together into one document (denormalise or nested), keep the real invariants in the database where transactions exist, and treat ES as a derived view that is eventually consistent. If a workflow needs "all or nothing", write it to the database in one transaction, then publish the change to ES through an outbox, with retries that are idempotent.

12. Keeping Elasticsearch in sync with a database

Why is writing to the database and to Elasticsearch in the same request a problem? Senior

What the interviewer is testing: the dual-write problem, one of the most common design questions.

The database and ES have no shared transaction. If you save to the database and then call ES, there are two failure cases. ES is down or times out after the commit: the data exists only in the database, and the search is stale forever. Or you call ES first and the database transaction rolls back: search shows a record that does not exist. If you try retries in the request thread, you slow the user and still lose updates if the app crashes between the two calls. Even if both succeed, two concurrent updates to the same row can reach ES in the opposite order, and the older one wins. So the plain dual write gives silent, permanent inconsistency. The solutions are an outbox table or change data capture: let the database be the one and only write, and derive ES updates from its log.

What are the reliable ways to keep Elasticsearch in sync with a database? Senior

What the interviewer is testing: concrete architecture with trade-offs.

The options. (1) Change data capture (CDC): a tool such as Debezium reads the database's transaction log (binlog, WAL) and publishes every row change to Kafka. A consumer or the Kafka Connect Elasticsearch sink writes them to ES. No change to the application, nothing is missed, order per row is kept. The cost is more infrastructure, and the row shape has to be turned into the search document (often needing joins, which CDC gives only per table). (2) Transactional outbox: in the same database transaction as the business change, insert an event row in an outbox table. A relay (a poller or CDC on that table) publishes it, and a consumer indexes it. You control the event content, so you can publish a ready search document. (3) Periodic batch sync using an updated_at column: simple, but delays, and misses hard deletes unless you track them. (4) Application-level events after commit with retries: simpler than outbox but loses events on a crash between commit and publish. In all designs: make indexing idempotent (use the row id as the document id), use external versions (a row version or timestamp) so late events cannot overwrite newer ones, handle deletes explicitly, and keep a full-rebuild job and a reconciliation check for repair.

Likely follow-ups
  • How are deletes handled? CDC emits a delete event, which becomes a delete in ES (or a soft-delete flag first). In batch sync you need tombstones or a deleted flag.
  • What lag should I expect and is that acceptable? Typically seconds. Tell product that search is eventually consistent, and for a user's own just-saved item, read it from the database or show it optimistically.
Search returns ids from ES; should the app then load full rows from the database? Intermediate

What the interviewer is testing: a pragmatic read-path design choice.

Both patterns exist. If ES stores the full display data, return it straight from _source: one call, fast, but the data may be a second or seconds stale. If ES stores only searchable fields and ids, the app takes the ids and loads the rows from the database with one WHERE id IN (...): always fresh and permission-checked by the database, but two hops and the result may include ids that were deleted a moment ago, so the app must handle missing rows (skip them). I usually return the display fields in the index (a small, denormalised document) for list pages and load from the database for the detail page. Never let ES alone decide access rights unless the permission filter is part of the document and always applied in the query as a filter.

13. Performance tuning from the application side

Your searches are slow. What do you change in the query and the data model, before touching the cluster? Senior

What the interviewer is testing: a systematic, developer-owned list of fixes.

Query side: move yes-or-no conditions into filter; avoid leading wildcards and regexp; limit size and fetch only the fields you need with _source filtering (_source: ["name","price"]) so the fetch phase is small; avoid deep from; avoid scripts in queries and sorting (use a precomputed field); keep track_total_hits at default unless you need an exact number; round date math so filters can be cached; prefer keyword for exact conditions; use routing for tenant queries. Data side: denormalise instead of joins and nested where possible; map only what you search (index: false for display-only); split big mixed indices by use; use index sorting or time-based indices if queries always have a time range. Aggregation side: filter first to shrink the set, lower size, avoid high-cardinality terms. Then measure with profile and the slow log, and test with realistic data volume, since a query that is fast on 10,000 documents may not be on 100 million.

How do you make indexing faster from the application side? Intermediate

What the interviewer is testing: practical write throughput tuning.

Use the bulk API with batches of a few megabytes and several parallel workers; raise parallelism until you see 429 responses, then back off. Increase refresh_interval (for example 30 seconds, or -1 during an initial load). For a first load, set replicas to 0, then restore. Let ES generate ids if you do not need your own (an auto id avoids a lookup to check if the document exists). Keep documents small: map unused fields with index: false, avoid unneeded text + keyword doubling, and avoid huge nested arrays. Avoid per-document refresh=true. Avoid frequent updates of the same document. Keep the number of shards in line with data nodes so writes spread. Finally, put heavy transformations in the producer, not in ingest pipelines, if the cluster CPU is the limit. Measure documents per second before and after each change.

What uses the JVM heap and what uses the OS file cache? What should a developer avoid? Senior

What the interviewer is testing: a memory model that explains OOM incidents.

Lucene data (segments, doc values, the inverted index) is read through the OS file system cache, outside the heap, which is why ES guidelines say give the heap at most half of the machine RAM (and under about 30 to 31 GB so the JVM keeps compressed object pointers) and leave the rest to the cache. The heap holds: the cluster state and per-shard overhead (many shards means more heap), the query cache and request cache, fielddata if you enabled it, the in-memory indexing buffers, and per-request working memory, such as the priority queues for from+size and the bucket maps of aggregations. Developer habits that blow the heap: very large size, deep pagination, terms aggregations on high-cardinality fields, enabling fielddata on text, huge bulk requests, over-sharding, and mapping explosions. ES has circuit breakers (parent, request, fielddata) that reject a request with a 429 / circuit_breaking_exception before the node runs out of memory. Treat a circuit breaker error as a design signal, not something to disable.

What caches does Elasticsearch have? Intermediate

What the interviewer is testing: knowing which repeated work is free and why queries differ in cost.

Three main ones. The node query cache (filter cache) keeps the bitset of documents matching a filter clause, per segment, with a limit of 10% of the heap by default, and only for filters used often enough and on segments of reasonable size. The shard request cache caches the full result of a search with size: 0 (typically aggregations) for a shard, and it is cleared on each refresh that changes the shard, so it helps on indices that rarely change (old time-based indices). The OS file system cache keeps Lucene files in memory and is the most important one for speed. Queries that use now unrounded, scripts or non-deterministic functions are not cached. Because cache entries are per segment, a segment merge invalidates them, which is one more reason not to force-merge a live index.

14. Clients, Java and Spring

Which Java clients exist for Elasticsearch, and how did they change across versions? Intermediate

What the interviewer is testing: you will not use a removed client in a new project.

Timeline: the TransportClient (a binary protocol to the cluster) was deprecated in 7.0 and removed in 8.0. The Java Low Level REST Client sends raw HTTP; it still exists as the transport under the others. The Java High Level REST Client (RestHighLevelClient) gave typed requests, and is deprecated since 7.15. How does Spring Data Elasticsearch work, and what are its pitfalls? Intermediate

What the interviewer is testing: practical Spring usage and awareness of its abstraction limits.

You annotate a class with @Document(indexName = "products"), mark the id with @Id, and describe fields with @Field(type = FieldType.Text) or Keyword. Then you either extend ElasticsearchRepository<Product, String> and get save, findById and derived queries like findByCategory(String c), or you use ElasticsearchOperations (the successor of ElasticsearchRestTemplate) for full control with native queries and the DSL. Spring Data Elasticsearch 4.x used the High Level REST Client; 5.x (with Spring Boot 3) uses the new Java API Client. Pitfalls: (1) index creation from annotations happens only if createIndex is true and the index does not exist, and it will not update an existing mapping, so manage mappings with templates or migration scripts in production. (2) saveAll uses bulk, but save in a loop does a request per entity. (3) Derived repository queries are convenient but hide the real query; for ranking and aggregations use the native query builder. (4) Remember the NRT delay in tests: use a refresh policy or refresh call, or Testcontainers with an explicit refresh. (5) The version of Spring Data must match the client and the server version, so check the compatibility matrix.

@Document(indexName = "products")
public class Product {
  @Id private String id;
  @Field(type = FieldType.Text, analyzer = "english") private String title;
  @Field(type = FieldType.Keyword) private String category;
  @Field(type = FieldType.Double) private double price;
}
public interface ProductRepo extends ElasticsearchRepository<Product, String> {
  List<Product> findByCategoryAndPriceLessThan(String category, double max);

What should you configure in the client so it behaves well in production? Intermediate

What the interviewer is testing: operational awareness at the application edge.

List several nodes (or a load balancer address) so the client can fail over, and enable node sniffing only if the network allows direct node access. Set connection and socket timeouts so a slow cluster cannot hold your threads forever, and pair them with a bounded connection pool. Retry only safe operations: reads, and idempotent writes with explicit ids. Handle 429 and 503 with exponential backoff and jitter. Use TLS and an API key or user credentials (in 8.x security is on by default and the server certificate must be trusted). Reuse one client instance for the application, since it is thread safe and holds a pool; creating a client per request leaks connections. Put the request timeout also in the search body (timeout) so shards return partial results rather than wait, and log the took value of slow searches. Close the client on shutdown.

How do you test code that uses Elasticsearch? Intermediate

What the interviewer is testing: test practices that avoid flaky NRT tests.

Do not mock the ES client for search logic, as a mock cannot tell you whether the query returns the right documents. Use Testcontainers to run a real Elasticsearch container, the same version as production, with the real templates and mappings applied (security off for tests, one node, small heap). After indexing test data, call the refresh API (or use refresh=wait_for) before searching, otherwise tests fail randomly on timing. Use a fresh index name or delete between tests. Keep a small set of "relevance tests": fixed documents and queries with the expected top result, to catch regressions when a mapping or analyzer changes. Mock only the thin layer above, for example a service that calls your search repository.

What security basics should a developer know when exposing search? Intermediate

What the interviewer is testing: avoiding data leaks through search.

Never let a browser talk to ES directly; put a backend in front that builds the query. Enforce tenant and permission filters on the server, always as filter clauses added by your code, never from user input. Alternatively use filtered aliases per tenant, or document and field-level security (a paid feature in the Elastic license tiers). Use an API key with minimal privileges for the app (write role differs from read role). Do not build JSON by string concatenation with user text (query injection); use the client's builders. Avoid exposing query_string and scripts to users. Limit size and the depth of pagination. In 8.0 and later TLS and authentication are enabled by default; in older 7.x they were off unless you configured them, and many public data leaks came from open 9200 ports.

15. Real-life scenarios

A search that used to take 50 ms now takes 4 seconds. How do you find out why? Senior

What the interviewer is testing: a calm method that separates query, data and cluster causes.

Situation: a user-facing search became slow. It may be one query or all.

Check first: is it one query shape or everything? Look at the slow log and the application's timing: took in the response versus the total time at the client (a big gap points to network or a huge response). Check whether anything changed: a deploy, a new field, data growth, a new tenant, a merge storm, a new heavy aggregation. Check cluster health, the heap and the thread pool rejections of the node.

Steps:

  1. Capture the slow query and run it with "profile": true. The profile shows which clause or aggregation dominates, per shard.
  2. Typical findings: a leading wildcard or regexp; a scoring must that should be a filter; a script; a huge size or deep from; a terms aggregation on a high-cardinality field; a nested query over a growing array; now without rounding.
  3. Check shard count touched and shard sizes: hundreds of tiny shards or a few giant ones both hurt. Check the number of segments if heavy updates produced many deleted docs.
  4. Fix the query shape first (filter context, smaller _source, routing), then the mapping (keyword, n-gram index), then reindex if needed.

Prevent: keep a slow-log alert, load test with production-like volume, and review queries in pull requests as you review SQL.

Users save an item and immediately search, but it is not in the results. What is happening? Intermediate

What the interviewer is testing: NRT, async pipelines, and replica reads.

Situation: a write succeeded, and a search right after does not show it. Sometimes it appears a moment later.

Check first: how does the write reach ES? Directly with the client, or through Kafka, a CDC pipeline or a queue? Get the document by id: if GET index/_doc/id finds it, the data is there and only refresh is pending. If not, the write never arrived or failed (look at the bulk response errors).

Causes and fixes:

  • Refresh delay (up to 1 second, or more if refresh_interval was raised): use refresh=wait_for on that write if the flow needs it, or have the UI show the item from the write response.
  • Asynchronous sync lag (queue or CDC): expected eventual consistency. Show the saved record from the database, and explain in the UI.
  • Bulk partial failure ignored by the code (HTTP 200 with errors: true): read item statuses.
  • Different results on repeated search: reads alternate between primary and replica with different refresh timing. Use a preference value such as the user or session id so the same copy answers.
  • Wrong alias or index: the write went to the new index, the read alias still points to the old.
  • Mapping issue: the document is stored but a field was not indexed, so the query cannot match it.

Prevent: state the consistency model in the design, never use refresh=true on every write, and test through the real pipeline.

The monitoring dashboard shows the cluster as yellow, then red after a node restart. What do you do? Intermediate

What the interviewer is testing: the shard allocation basics for a developer on call.

Situation: a node restarted or crashed. Replicas were lost first (yellow), then a primary was unassigned (red).

Check first: do not restart more nodes. Run GET _cluster/health to see how many shards are unassigned, and whether the number is going down (shards recovering after a restart is normal and the status returns to green by itself).

GET _cluster/health?level=indices
GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason&s=state
GET _cluster/allocation/explain

Reading the result: NODE_LEFT means wait or bring the node back. DISK_USAGE or "disk watermark" means the nodes are too full: free space or add storage (and note that at the flood-stage 95% watermark indices become read-only, which makes writes fail with a 403 block error until the block is removed after space is freed). "No node can hold the shard" means a node-count or allocation-rule problem. A red index with no copy of a primary on any live node means data is only recoverable from a snapshot or the returning node.

What I tell the business: yellow means no redundancy and a second failure could lose data; red means some data is not available now. Deep recovery steps (manual reroute, snapshot restore) are for the platform team, and I make sure they are called early.

Prevent: three master-eligible nodes, at least one replica, disk alerts at the low watermark, and tested snapshots.

Indexing starts failing with "Limit of total fields [1000] has been exceeded". What happened and how do you fix it? Senior

What the interviewer is testing: root-cause thinking instead of raising a limit.

Situation: bulk requests fail for many documents, and the cluster state update times grow.

Check first: look at GET index/_mapping and count fields. Find the pattern in the field names: most often keys that carry data, such as labels.pod_a8f3..., an attribute per customer, an IP or id as a key, or an unbounded JSON from a third party indexed with dynamic mapping on.

Steps:

  1. Stop the immediate bleeding: reject or reshape the offending producer. Do not simply raise total_fields.limit to 10,000; it only delays the failure and loads the master.
  2. Change the shape: convert the dynamic map into an array of {key, value} objects, or map that sub-tree as flattened, or set dynamic: false (stored in _source, not indexed) or strict for the object.
  3. Create a new index with the corrected mapping and reindex through an alias switch, with a script or pipeline to convert old documents.

Prevent: explicit templates with dynamic: strict or false on free-form objects, a schema contract with producers, and an alert on mapping size.

Nodes are hitting circuit breaker errors and GC pauses, and searches return 429 or time out. What could be the application-side causes? Senior

What the interviewer is testing: linking heap symptoms to code and design choices.

Situation: heap use stays above 85%, long GC pauses, circuit_breaking_exception, search rejections.

Check first: which requests are heavy (the slow log, the tasks API: GET _tasks?detailed), whether the problem started with a deploy or a new feature, the number of shards per node, and whether fielddata or large aggregations are used (GET _nodes/stats/breaker, _cat/fielddata).

Common causes:

  • A new terms aggregation on a high-cardinality field, or many buckets per request.
  • Fielddata enabled on a text field to make a sort or aggregation work.
  • Very large size or deep from, for example an export loop done with a large from.
  • Huge bulk requests, or too many parallel bulk workers, filling the write queues.
  • Over-sharding (thousands of small shards) so the baseline heap use is already high.
  • A mapping explosion enlarging the cluster state.

Steps: cancel or throttle the heavy requests, put a limit on size and aggregation sizes in the API layer, replace fielddata with keyword fields, switch exports to search_after with PIT, reduce shard count by rollover or shrink, and lower client concurrency with backoff on 429. Asking for more heap is the last option; also the heap must stay below about 31 GB, so scaling out is the usual path (a platform decision).

You need to change a field from text to keyword and add a new analyzer on a live index with 200 million documents. How do you do it without downtime? Senior

What the interviewer is testing: the full migration plan, including writes that arrive during the copy.

Situation: the app reads and writes through the alias orders, which points to orders-v1.

Steps:

  1. Create orders-v2 with the new mapping and analysis settings. Set replicas: 0 and refresh_interval: -1 to speed the load.
  2. Decide how to catch writes made during the copy: have the application (or the sync pipeline) write every change to both indices from now on (use two aliases, orders-read and orders-write, or a dual-write consumer), using the same ids and external versions so duplicates are harmless.
  3. Start _reindex from v1 to v2 with slices: auto, a moderate requests_per_second, and version_type: external with op_type: create or equivalent so a newer document already written to v2 is not overwritten by an older copy. Alternatively rebuild v2 from the database.
  4. Verify: compare document counts, spot check queries, run the relevance test set against v2.
  5. Restore replicas and refresh interval. Wait for green.
  6. Switch the read alias to v2 atomically. Then switch the write alias, stop dual writes.
  7. Keep v1 for a rollback period, then delete it.

Prevent: use alias names in code from day one, keep the mapping in templates, and keep the rebuild job ready.

Product managers report that some deleted products still show up in search and some new ones are missing. How do you investigate and repair? Senior

What the interviewer is testing: drift between a database and its search copy, and a repeatable fix.

Situation: the database and the ES index disagree for some ids.

Check first: how is the data synced (dual write, outbox, CDC, batch)? Measure the size of the problem: compare counts, and compare id sets in chunks or with a checksum per id range between the two stores. Check the sync consumer for errors, the dead-letter topic, the lag, and the bulk responses (items with errors that were ignored).

Likely causes:

  • A dual write where the second call failed and nobody retried.
  • Hard deletes not propagated by a batch job that only looks at updated_at.
  • Out-of-order events overwriting newer data, with no external version.
  • A consumer that skipped poison messages (a mapping failure on one record).

Repair: first fix the cause so drift stops. Then run a reconciliation job: for each id range, compare and then index missing rows and delete orphans (ids in ES but not in the database). If drift is large, build a fresh index from the database and switch the alias. Prevent: move to outbox or CDC, idempotent writes with external versions, a dead-letter queue with an alert, and a scheduled reconciliation that reports drift as a metric.

Users complain that searching "iphone case" returns phones before cases, and "cases" returns nothing. What do you check and change? Senior

What the interviewer is testing: a methodical relevance investigation, not random boosts.

Situation: two separate problems: ranking (phones above cases) and recall (plural form finds nothing).

Check first: run _analyze with the field's analyzer on "cases" and on the stored titles. If the field uses the standard analyzer, there is no stemming, so "cases" and "case" are different terms; that explains the empty result. Then run the query with explain: true on one phone and one case to see the score parts.

Fixes:

  • Recall: use the english analyzer or a custom one with a stemmer (or a lemmatizing plugin) for the title and description; reindex.
  • Ranking: the match is probably an OR, so a phone that contains "iphone" many times outranks a case. Use operator: and or minimum_should_match: 75% so both words are needed. Add a match_phrase clause in should with a boost, so "iphone case" as a phrase wins. Boost the title field over the description with title^3. Consider a category signal: if the query contains "case", boost the case category.
  • Verify with a saved set of queries and expected top results before and after, so a fix for one query does not hurt others.

Prevent: own a relevance test set and review it when changing analyzers; collect click and "no result" logs to find the next problems.

An export screen asks for page 2,000 and the API fails with "Result window is too large". What do you do? Intermediate

What the interviewer is testing: choosing the right pagination tool for the use case.

Situation: from + size exceeds the 10,000 window.

Check first: what is the use case? A person browsing, or a job exporting everything? Nobody reads 2,000 pages, so for humans the answer is a UI limit and better filters. For a program that needs all the results, use a cursor.

Steps: open a PIT, search with a deterministic sort including a unique tie-breaker and search_after, page size around 1,000, and loop until a page is empty; close the PIT at the end (DELETE _pit). For parallelism, use slice on the PIT search. For "jump to page N" in a UI, either cap at 10,000 results or store an offset-to-sort-value mapping for common jumps. Do not just raise max_result_window to a million: memory per request grows with depth and shards.

Prevent: put a maximum page depth in the API contract and document it.

A nightly bulk load now fails with many 429 errors and some documents are missing. How do you fix it? Intermediate

What the interviewer is testing: backpressure, bulk error handling, and idempotency.

Situation: the loader sends too fast; the write thread pool queue is full and ES rejects work with 429. The job logs show success because the HTTP code was 200.

Check first: the bulk response: errors: true and the item statuses. Check _nodes/stats/thread_pool for write rejections and cluster CPU.

Steps:

  • Fix the loader: read each item result, retry only the 429 and 503 items with exponential backoff and jitter, send others to a dead-letter file.
  • Reduce pressure: smaller bulks (a few MB), fewer parallel workers, and a bounded queue in the loader. Increase concurrency slowly until you see the first 429.
  • Speed the target: raise refresh_interval or disable it during the load, set replicas to 0 and restore after (if downtime of redundancy is acceptable), and avoid per-document refresh.
  • Make the job idempotent with deterministic ids so a rerun is safe.
  • Re-run only the missing ids, found by comparing counts or ids with the source.

Prevent: use the client's bulk helper (BulkIngester) with backoff built in, and schedule heavy loads outside peak search hours.

You are designing search for 5,000 tenants, most of them small. How do you lay out indices? Senior

What the interviewer is testing: avoiding over-sharding and ensuring tenant isolation.

Situation: one index per tenant means 5,000 or more indices, and with the default one primary plus one replica that is 10,000 shards for tiny data. Cluster state and heap would suffer.

Options:

  • Shared index with a tenant_id keyword, always as a filter, with routing = tenant_id so a tenant's search touches one shard. Use a filtered alias per tenant to make it safe for the app code: the alias holds the filter and routing, so the app cannot forget it.
  • A few indices by size class: the big tenants get their own index, the many small ones share. Move a tenant when it grows, with reindex by query.
  • Index per tenant only for a small number of large, isolated tenants (compliance, different retention or very different mappings).

Trade-offs: shared indices give hot shard risk (one huge tenant with routing), shared mapping (all tenants must fit one schema), and harder per-tenant deletion (delete by query, not instant). Per-tenant indices give easy delete and isolation but cost heap. I choose a shared index with filtered aliases and routing, and I add a tenant filter at the server in code and in tests, since leaking data across tenants is the worst failure here.

Two services update the same document and you see occasional 409 version_conflict errors, or worse, lost updates. What do you do? Senior

What the interviewer is testing: optimistic concurrency in practice.

Situation: service A reads an order, changes the status, and indexes the full document; service B changes the amount at the same time. If both do read, modify, and full overwrite, the later one erases the earlier one's change (a lost update). If one uses if_seq_no it gets a 409.

Check first: which APIs are used: full index (overwrite), or the update API with a partial doc? Does the 409 appear on bulk updates?

Fixes:

  • Use the update API with a partial doc or a script, so each service touches only its own fields, atomically on the shard, with retry_on_conflict: 3.
  • If the logic needs the current value, use read, then write with if_seq_no and if_primary_term, and on 409 re-read and retry (a bounded loop).
  • If the source of truth is a database, use its row version as the external version (version_type=external), so an older update can never win.
  • Reduce write hotspots: do not update the same document many times per second (each update rewrites the whole document); aggregate counters elsewhere and flush them in batches.

Prevent: a single writer per document type where possible, and tests that run concurrent updates.

All writes suddenly fail with "index read-only / allow delete" (cluster_block_exception). What happened? Intermediate

What the interviewer is testing: knowing the disk watermark protection.

Situation: indexing returns 403 cluster_block_exception ... read-only-allow-delete though the cluster was healthy an hour ago.

Cause: a data node crossed the flood-stage disk watermark (95% by default). To protect the node, ES marks the indices that have a shard on it as read-only. Before that, at 85% (low watermark) it stops allocating new shards to the node, and at 90% (high) it moves shards away.

Steps: find the node with GET _cat/allocation?v; free space by deleting old indices (ILM retention that did not run, old logs), by adding disk or nodes, or by cutting replicas of non-critical indices. Since 7.4 (about) ES automatically releases the block once the disk falls under the high watermark; in older versions you had to clear it by hand with index.blocks.read_only_allow_delete: null. Verify writes work again. Then ask why the disk filled: a missing retention policy, a runaway log volume, or too few nodes for the growth.

Prevent: an ILM delete phase, disk alerts well below 85%, and a capacity review with the platform team. The app should treat 403 blocks and 429 as retryable with backoff and alert, not drop data.

A logs index has grown to 3 TB in one index with 5 shards, and searches over the last hour are slow. How do you restructure? Senior

What the interviewer is testing: time-based index design.

Situation: 600 GB shards, every query touches all of them, deleting old data requires delete-by-query, and merges are huge.

Plan: move to a data stream (or a write alias with rollover) backed by an ILM policy. Rollover when an index reaches about 30 to 50 GB per primary shard or one day, whichever comes first. A search on the last hour then reads only the newest backing index, because the query has a time range and ES can skip shards whose @timestamp range does not match (the "can match" phase). Retention is a delete phase that drops whole indices instantly. Older indices can be made read-only, shrunk and force-merged in the warm phase. Define the mapping in a composable template so every new index has it. Migrate with _reindex of the old index into the stream by time slices, or simply let the old index age out while new data goes to the stream and search both through an alias.

Prevent: time-based indices from the start for any append-only data, and a size-based rollover, not only a daily one, so busy days do not produce giant shards.
