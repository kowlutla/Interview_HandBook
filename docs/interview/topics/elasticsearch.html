Scope: this page is for the application developer who builds search on Elasticsearch (ES). About half of it is about writing and reading queries, because that is what interviews test. It does not cover cluster operations (node roles, ILM, snapshots, capacity planning). All examples use the Kibana Dev Tools style (GET index/_search plus a JSON body) and work on Elasticsearch 7.x and 8.x unless a note says otherwise.

Version notes: mapping types were removed in 8.0, so every index has the single type _doc. New indices get 1 primary shard by default since 7.0 (it was 5). Hit counts are capped at 10,000 by default since 7.0. Point in time (PIT) arrived in 7.10. search_as_you_type arrived in 7.2. OpenSearch is the fork of Elasticsearch 7.10.2 made by AWS in 2021; the Query DSL on this page works there too.

Mental model: the 7 ideas everything hangs on

One line: Elasticsearch is a distributed search engine on top of Apache Lucene. At write time it builds an inverted index (word to documents), so a search looks words up instead of scanning documents. It is fast, near real time, and not transactional.
  1. Inverted index. Text is cut into terms at write time. For each term ES stores the list of documents that contain it. A search looks terms up.
  2. Analysis runs on both sides. "Running Shoes!" becomes the terms running and shoes at index time, and the query text goes through the same process. If the two sides differ, matches silently fail.
  3. The mapping is your schema. It decides what is analysed text (text), an exact value (keyword), a number, a date or a nested object. You cannot change an existing field's type in place.
  4. Query context scores, filter context does not. "How well does it match?" is query context. "Does it match, yes or no?" is filter context, which is faster and cacheable.
  5. An index is split into shards. A shard is one complete Lucene index. A document lives in one primary shard, chosen by hashing its id. Replicas are copies for safety and read speed.
  6. Search is scatter and gather. The node you call asks every shard for its top hits, merges them, then fetches the documents.
  7. Near real time, not a database. New documents are searchable after a refresh (default 1 second). No multi-document transactions, no SQL-style joins. Keep the truth in a database and feed ES from it.

1. Fundamentals and how search works

What is Elasticsearch and what is it good at? Basic

Elasticsearch is a distributed search and analytics engine built on Apache Lucene. You store JSON documents, and it builds indexes that make full-text search, filtering and aggregations fast, usually in milliseconds even over hundreds of millions of documents. I use it for product or document search, log search, autocomplete and dashboard-style counts.

Lucene is the Java library that does the real indexing and searching inside one shard. Elasticsearch adds the parts around it: a REST API with JSON, distribution across nodes, replication and a query language (the Query DSL). The things it is bad at are what a relational database is good at: transactions, joins, strict consistency, and being the single source of truth. So the usual design is a database as the source of truth and Elasticsearch as a derived, searchable copy.

Remember: ES = Lucene + REST + distribution. Great at search and aggregations, not a system of record.

When would you use Elasticsearch instead of a relational database, and when not? Intermediate

I use Elasticsearch when users need full-text search with ranking, typo tolerance, filters with counts, or aggregations over a lot of data. I keep a relational database for the main data, because it gives transactions, joins and strict consistency, which Elasticsearch does not. In practice I use both: the database is the truth, and Elasticsearch is a search copy fed from it.

The reason for the split is the index structure. A B-tree in a database is great at "find the row with this id or range". It cannot do LIKE '%phone case%' fast, and it has no idea of relevance. An inverted index does exactly that. In return Elasticsearch gives up: no multi-document transactions, a new write is visible only after a refresh (about 1 second), no real joins, and updates are expensive because they rewrite the whole document.

Strengthtransactions, joins, constraintsfull-text, relevance, filters, aggregations
Read after writeimmediateafter refresh (about 1 s); get-by-id is immediate

Rolesource of truthderived search copy

Remember: DB for truth and transactions, ES for search and analytics. Never make ES your only copy.

What is an inverted index and why does it make search fast? Basic

An inverted index is like the index at the back of a book: for every word it lists the documents that contain that word. A search looks up the query words in a sorted dictionary and reads those lists, instead of scanning every document. That is why search time depends on how many documents match, not on how many documents exist.

It is "inverted" because a normal store maps document to words, and this maps word to documents. Each entry also keeps the positions of the word (needed for phrase search) and the term frequency (needed for scoring). To combine words, ES intersects or unions the sorted lists, which is quick. The cost is paid at write time: text is analysed and the index is built, which is why indexing is heavier than a plain insert.

Remember: word to documents, built at write time. Search cost follows matches, not total documents.

What happens inside the cluster when I send a search request? Intermediate

The node that receives the request becomes the coordinator. It sends the query to one copy (primary or replica) of every shard of the index. Each shard finds its own top hits and returns just ids and scores. The coordinator merges those lists into the global top N, then asks the right shards to fetch the full documents for only those N. Query then fetch, in two phases.

Two consequences matter for developers. First, a search with from: 0, size: 10 over 5 shards pulls 10 candidates from each, so cost grows with from + size (this is the deep paging problem). Second, relevance is computed per shard, so with very little data and many shards, scores can differ slightly from a single shard. The fix, if it matters, is search_type=dfs_query_then_fetch, which first collects global term statistics, at extra cost.

Remember: coordinator fans out, shards return top ids, coordinator merges, then fetches. Cost grows with from + size.

Why is Elasticsearch called near real time? Basic

Because a document I index is not searchable immediately. It becomes visible at the next refresh, which by default runs every second. So search sees data about a second late. Fetching a document by id is real time, because that reads from the transaction log if needed.

Why the delay: a refresh writes the in-memory buffer as a new small Lucene segment and opens it for search. That is cheap enough to do every second, but doing it per document would be very costly. For a user who saves and then immediately searches, I can pass ?refresh=wait_for on the write (waits for the next refresh, fine for occasional writes) or ?refresh=true (forces one now, harmful under load). For bulk loads I do the opposite: set refresh_interval to 30s or -1 while loading, then restore it, which makes indexing noticeably faster.

PUT products/_doc/1?refresh=wait_for
{ "name": "Red running shoes" }

PUT products/_settings
{ "index": { "refresh_interval": "30s" } }

Note that an idle shard (no search for 30 seconds by default) skips scheduled refreshes, and the next search triggers one, so this is invisible in practice.

Remember: searchable after refresh (about 1 s), get-by-id is instant. Use wait_for for read-your-write, slower refresh for bulk loads.

What are shards and replicas, and how many should an index have? Intermediate

An index is split into primary shards so data and work spread over nodes. Each document is routed to one primary by hashing its id. A replica is a copy of a primary on a different node: it keeps data safe if a node dies and also serves search requests. The number of primaries is fixed when the index is created, so I size it for the data and keep shards moderate, not tiny and not huge.

Routing is shard = hash(_routing) % number_of_primary_shards, where _routing defaults to the document id. That formula is why you cannot change the primary count in place: the modulus would change and documents would be looked up in the wrong shard. To change it you reindex, or use the split or shrink APIs. Replicas can be changed any time, and default to 1.

The common mistake is over-sharding. Every shard costs memory, file handles and a thread when searched, and a search touches all shards of the index. Hundreds of tiny shards are slower than a few well-sized ones. A rule of thumb many teams use is shards of roughly 10 to 50 GB, and since 7.0 the default is just one primary. If data grows over time (logs), use time-based indices instead of one giant index. Cluster-level planning is specialist territory beyond this page.

Remember: primaries are fixed at creation and chosen by hash(id); replicas are copies for safety and reads. Too many small shards hurt.

2. Analysis: how text becomes terms

What is an analyzer and what are its parts? Basic

An analyzer turns a piece of text into the list of terms that go into the inverted index. It has three stages: character filters clean the raw text, a tokenizer splits it into tokens, and token filters change the tokens (lowercase, stemming, stop words, synonyms). The default standard analyzer splits on word boundaries and lowercases.

The point is that I want "Running" and "run" to find the same documents, so both the stored text and the query text are normalised the same way. I debug analysis with the _analyze API, which shows the exact terms produced. Most "why does my search not match?" problems are solved by looking at that output.

POST _analyze
{ "analyzer": "standard", "text": "Running Shoes!" }
-- terms: running, shoes

Remember: char filter, tokenizer, token filters. When a match surprises you, run _analyze.

Is the same analyzer used when indexing and when searching? What goes wrong if they differ? Intermediate

By default yes: a text field uses its analyzer at index time and the same one at query time, so both sides produce the same terms. If they differ by accident, the query terms do not exist in the index and the search returns nothing, with no error. I only use a different search_analyzer on purpose, mainly for autocomplete.

A typical accident: the field was indexed with a stemming analyzer (stores run) but the query goes against a keyword field or a term query, which does not analyse, so searching Running finds nothing. The intended use is edge n-grams: index "laptop" as l, la, lap, ... but analyse the query "lap" only as lap, otherwise the query would also be cut into n-grams and match unrelated words.

Remember: same analysis on both sides, unless you chose a search_analyzer deliberately (autocomplete). A mismatch gives empty results, not errors.

How would you build autocomplete (search as you type)? Senior

For a normal "type three letters, see matching products" box I use the search_as_you_type field type, or an edge n-gram analyzer at index time with a plain analyzer at search time. If I only need fast prefix suggestions on a name list, I use the completion suggester. The trade-off is index size and flexibility: n-grams are flexible but larger, completion is fastest but matches only from the start.

  • edge_ngram: indexes every prefix of each word (l, la, lap, lapt...). A query for "lap" is a normal term lookup, so it is fast. Costs more disk and slower indexing.
  • search_as_you_type: built-in field type (7.2+) that creates the n-gram sub-fields for you; query it with multi_match of type bool_prefix.
  • completion suggester: an in-memory structure for prefix lookup, very fast, but prefix only, no typo tolerance by default and limited ranking control.
  • prefix / match_phrase_prefix: no extra setup, but expands terms at query time; fine for small data only.
PUT products
{ "mappings": { "properties": { "name": { "type": "search_as_you_type" } } } }

GET products/_search
{ "query": { "multi_match": {
    "query": "lap", "type": "bool_prefix",
    "fields": ["name", "name._2gram", "name._3gram"] } } }

Remember: n-grams at index time, plain terms at search time. search_as_you_type for most cases, completion suggester for pure prefix speed.

3. Mappings

What is the difference between the text and keyword field types? Basic

A text field is analysed: it is split into terms and lowercased, so I can do full-text search on it. A keyword field is stored as one exact value, so I use it for filtering, sorting and aggregations on things like status, email, id or country. For a string I need both ways, I map it as text with a keyword sub-field.

That is exactly what dynamic mapping does for strings: name becomes text, and name.keyword is a keyword (values longer than 256 characters are not indexed in it). Sorting and aggregating on a plain text field fails, with an error about "fielddata", because the index holds terms, not whole values. The right fix is to use the .keyword sub-field, not to enable fielddata, which loads every term into heap memory.

PUT products
{ "mappings": { "properties": {
    "name":   { "type": "text", "fields": { "raw": { "type": "keyword" } } },
    "status": { "type": "keyword" },
    "price":  { "type": "scaled_float", "scaling_factor": 100 }
} } }

GET products/_search
{ "sort": [ { "name.raw": "asc" } ],
  "aggs": { "by_status": { "terms": { "field": "status" } } } }

For money I use scaled_float or integer cents, not a plain float.

Remember: text = searched by words, keyword = exact value for filter, sort, aggregate. Use both via a sub-field.

What is dynamic mapping and what are its pitfalls? Intermediate

Dynamic mapping means that when a document has a field ES has not seen, it guesses the type and adds it to the mapping automatically. It is handy for a quick start, but risky in production: the first value decides the type forever, and unknown keys can bloat the mapping. For real systems I define the mapping explicitly and set dynamic to strict or false.

  • Wrong guess: the first document has "zip": "02134" (text) or "id": 7 (long). Later documents with a different shape get rejected, or are searched wrongly.
  • Strings become text plus keyword, which doubles the index cost for fields you only ever filter on.
  • Mapping explosion: if keys are data (for example user ids used as field names), the mapping grows without bound. The default limit is 1,000 fields per index, and past that indexing fails. Model such data as an array of {key, value} objects, or use the flattened type.
PUT products
{ "mappings": { "dynamic": "strict",
    "properties": { "name": { "type": "text" } } } }

strict rejects documents with unknown fields, false accepts them but does not index them, true (default) maps them.

Remember: first value fixes the type. Define mappings yourself, use dynamic strict or false, and never use data as field names.

Can I change the mapping of an existing field? Intermediate

No. I can add new fields and some harmless settings, but I cannot change a field's type or its analyzer on existing data, because the inverted index was already built that way. The fix is to create a new index with the right mapping, copy the data with the _reindex API, and switch an alias to the new index.

That is why applications should talk to an alias (products) and not to a concrete index (products_v1). The steps: create products_v2, run _reindex from v1 to v2, then switch the alias in one atomic call, so there is no downtime. For a live system, writes arriving during the copy must also go to the new index or be replayed afterwards (see the zero-downtime scenario below).

POST _aliases
{ "actions": [
  { "remove": { "index": "products_v1", "alias": "products" } },
  { "add":    { "index": "products_v2", "alias": "products" } } ] }

Remember: mappings are append-only. New index, reindex, flip the alias.

What is the difference between object and nested fields, and why does it matter? Intermediate

An array of objects is flattened by default, so the link between fields of the same object is lost. Searching "author first = John and last = Smith" can wrongly match a document with John Doe and Jane Smith. A nested field fixes this by indexing each object as its own hidden document, and I query it with a nested query. It is correct but costs more.

With a plain object, comments: [{user: "john", stars: 5}, {user: "amy", stars: 1}] is stored as comments.user: [john, amy] and comments.stars: [5, 1], so "john with 1 star" wrongly matches. With nested, each comment is a separate Lucene document linked to its parent. The price: more documents, slower queries and updates (changing one comment reindexes the whole parent and all its nested docs), and limits (50 nested fields and 10,000 nested objects per document by default). Use it only when you must query fields together inside one array element.

PUT posts
{ "mappings": { "properties": {
    "comments": { "type": "nested", "properties": {
        "user":  { "type": "keyword" },
        "stars": { "type": "integer" } } } } } }

Remember: arrays of objects flatten and mix up fields. Use nested when fields must match together, and pay for it.

How do you model relationships in Elasticsearch: denormalise, nested or join? Senior

I denormalise by default: copy the data I need for search into each document, so one query answers it with no join. If I must match fields together inside a list, I use nested. I use the join parent-child field only rarely, when the child data changes much more often than the parent and copying would be too costly. It is slower, and children must sit on the same shard as the parent.

Elasticsearch has no cheap general join across indices, so I model for the queries I need. Example: an order document stores the customer name and city inside it. The cost is duplicate data: when a customer's name changes, I must update (_update_by_query or a reindex) every order that copied it, so I accept that only for fields that rarely change or where slightly stale values are fine. Another option is to search for ids in ES and then load rows from the database in one batch query.

Denormalisefastestcopies must be refresheddefault choice

Remember: flatten for search; nested if fields must match together; join as a last resort.

4. Writing and reading queries

What is the difference between match, match_phrase and term queries? Basic

match is for full text: it analyses my query text and finds documents containing any of the resulting terms, ranked by relevance. match_phrase needs the terms to appear together and in order. term does no analysis: it looks up the exact value I give, so I use it on keyword, number and date fields, not on analysed text.

GET products/_search
{ "query": { "match": { "name": "red running shoes" } } }
-- terms red OR running OR shoes; more matching terms = higher score

{ "query": { "match": { "name": { "query": "red running shoes", "operator": "and" } } } }
-- all three terms must be present, any order

{ "query": { "match_phrase": { "name": "running shoes" } } }
-- "running" directly followed by "shoes"

{ "query": { "term": { "status": "ACTIVE" } } }
-- exact, case-sensitive value on a keyword field

The classic bug: term on a text field. The index holds lowercase terms (active), but term sends ACTIVE unchanged, so nothing matches. Fix it by using match on text, or term on a keyword field. terms is the "IN" version: {"terms": {"status": ["ACTIVE", "PENDING"]}}. match_phrase accepts a slop setting to allow some words in between.

Remember: match analyses and ORs the words, match_phrase wants order and adjacency, term is exact and only for keyword, number, date. terms = IN.

How do I search several fields at once, with one field more important than the others? Intermediate

I use multi_match with a list of fields and a boost on the important one, for example name^3 so a title match counts three times more than a description match. The type decides how field scores combine: best_fields (default) takes the best single field, most_fields adds them up, and cross_fields treats the fields as one big field.

GET products/_search
{ "query": { "multi_match": {
    "query": "running shoes",
    "fields": ["name^3", "brand^2", "description"],
    "type": "best_fields",
    "tie_breaker": 0.3 } } }

With best_fields, a document where both words are in the name beats one where one word is in the name and the other in the description. With tie_breaker, the other fields add a small share of their score. Use cross_fields when one logical value is split across fields, for example first_name and last_name with "operator": "and". If the same text is indexed several ways (stemmed, exact), most_fields makes sense. Setting fuzziness here also works (see the fuzzy question).

Remember: multi_match + field^boost. best_fields = best one wins, most_fields = sum, cross_fields = one virtual field.

Explain the bool query: must, should, must_not and filter. Basic

The bool query combines clauses. must means "has to match and contributes to the score". filter means "has to match" but does not score and can be cached. must_not excludes matches. should means "nice to have": it raises the score, and if there is no must or filter, at least one should has to match. It is the SQL AND, OR and NOT of Elasticsearch.

GET products/_search
{ "query": { "bool": {
    "must":     [ { "match": { "name": "running shoes" } } ],
    "filter":   [ { "term":  { "status": "ACTIVE" } },
                  { "range": { "price": { "lte": 100 } } } ],
    "must_not": [ { "term":  { "brand": "acme" } } ],
    "should":   [ { "term":  { "on_sale": true } } ],
    "minimum_should_match": 0
} } }

Reading it: text relevance comes from must; the yes/no conditions (active, price under 100) go in filter; excluded brand is must_not; on-sale items get a small bonus from should. The usual trap is should alone beside a must: it then does not filter, only boosts, so people think "OR" does not work. To require "A or B", put both in a should inside its own bool with minimum_should_match: 1. Clauses nest freely.

Remember: must scores, filter does not, must_not excludes, should is a bonus unless it is alone.

What is the difference between query context and filter context, and why does it matter for speed? Intermediate

Query context asks "how well does this document match?" and computes a relevance score. Filter context asks "does it match, yes or no?" and computes no score. Filters are cheaper, and Elasticsearch can cache their results, so I put every exact or yes/no condition (status, date range, category, tenant id) in a filter and keep only the real text search in must.

Scoring needs term frequencies and field lengths, which costs CPU. A filter only produces a set of matching documents, kept as a compact bit set per segment; frequently used filters are cached and reused across requests. Clauses inside filter, inside must_not and the filter parameter of constant_score all run in filter context. Do not filter on text relevance fields like "description contains ..." in filter context if you want ranking, since you would lose scores.

-- faster: text in must, exact conditions in filter
{ "bool": { "must":   [ { "match": { "title": "wireless headphones" } } ],
            "filter": [ { "term": { "tenant_id": "t-42" } },
                        { "range": { "created": { "gte": "now-30d/d" } } } ] } }

Remember: if it is not about relevance, put it in filter. No scoring, and it can be cached.

How do range queries work, and what should I watch for with dates? Basic

A range query takes gt, gte, lt, lte on numbers, dates or keywords. For dates I use date math such as now-7d/d, and I usually put the range in a filter. The main trap is rounding: /d rounds to the day, so be clear whether the upper bound should be inclusive.

GET orders/_search
{ "query": { "bool": { "filter": [
    { "range": { "created": { "gte": "now-7d/d", "lt": "now/d" } } },
    { "range": { "total":   { "gte": 100, "lte": 500 } } } ] } } }

Reading it: orders created from the start of the day 7 days ago up to (not including) the start of today, with a total between 100 and 500. Things to watch: a range on a text field compares terms as strings, so "9" > "10", which is almost never what you want, so use numeric or date fields. Dates are stored as UTC milliseconds, so pass time_zone if "today" means the user's day. A filter containing now cannot be cached well since the value changes constantly, which is why rounding with /d helps caching.

Remember: range goes in filter, use date math with rounding, never range over text fields, and mind time zones.

Why are wildcard, prefix and regexp queries slow? What do you use instead? Intermediate

The index is sorted by term, so a prefix like lap* can jump to one place and is fairly cheap. A wildcard that starts with *, like *top, or a regexp has to test every term in the field's dictionary, which gets slow and heavy on big fields. For autocomplete I use n-grams or search_as_you_type, and for "contains" search I use a proper analyzer or the wildcard field type.

{ "query": { "wildcard": { "sku": { "value": "*-2024-*" } } } }   // scans the dictionary
{ "query": { "prefix":   { "sku": "AB-" } } }                    // cheaper, still expands
{ "query": { "match":    { "name": "laptop" } } }                // best: normal term lookup

The better pattern is to change the data, not the query: index what you search for. For codes where you search parts, use an n-gram analyzer or split the code into separate fields. For genuine "contains" over log lines or ids, the wildcard field type (7.9+) is built for it. Also, never run wildcard on a big text field and never expose it directly to users, who will type *a*. The setting search.allow_expensive_queries: false blocks these query types cluster-wide.

Remember: leading wildcard and regexp scan the whole term dictionary. Index it the way you search (n-grams), do not wildcard it.

How do I make search tolerate typos? Intermediate

I add fuzziness to a match query. Elasticsearch then also accepts terms within a small edit distance (insert, delete, replace or swap a letter), so "runing shoos" still finds "running shoes". "fuzziness": "AUTO" is the sensible default. The cost is more terms to look up and some wrong matches, so I limit it with prefix_length.

GET products/_search
{ "query": { "match": { "name": {
    "query": "runing shoos",
    "fuzziness": "AUTO",
    "prefix_length": 1 } } } }

AUTO allows 0 edits for terms of 1 to 2 characters, 1 edit for 3 to 5, and 2 edits for longer terms (2 is the maximum). prefix_length: 1 means the first letter must be exact, which both speeds the query up and cuts silly matches, because most typos are not in the first letter. Fuzzy matches score lower than exact ones, so exact matches still rank first. For a "did you mean" hint instead of silently widening the query, use the term or phrase suggester. Fuzziness on very short terms or with an edit distance of 2 on large fields is expensive; do not turn it on blindly for every field.

Remember: match + fuzziness AUTO + prefix_length 1. Max 2 edits; exact matches still rank higher.

Show me a query on a nested field. What do I need to remember? Intermediate

A nested field has to be queried through a nested query that names the path. Inside it, I write normal queries using the full field names. A plain match on comments.user returns nothing, because the nested objects are hidden documents. If I also want to know which nested items matched, I add inner_hits.

GET posts/_search
{ "query": { "nested": {
    "path": "comments",
    "query": { "bool": { "must": [
        { "term":  { "comments.user": "john" } },
        { "range": { "comments.stars": { "lte": 2 } } } ] } },
    "inner_hits": {} } } }

This returns posts that have a comment by john with at most 2 stars, both conditions on the same comment, and inner_hits shows which comments matched. Aggregations on nested data need a nested aggregation first, then the inner aggregation, and reverse_nested to go back up to the parent level. Another thing to remember: score mode (score_mode: avg by default) decides how the scores of several matching nested items combine into the parent's score.

Remember: nested field = nested query with path. Same for aggregations. inner_hits shows which children matched.

How do I add highlighting and "did you mean" to a search page? Intermediate

For highlighting I add a highlight section with the fields to mark. ES returns snippets with the matched words wrapped in tags like <em>. For "did you mean" I add a suggest section with the term or phrase suggester, which looks for similar terms in the index. Both ride along in the same search request.

GET products/_search
{ "query": { "match": { "description": "runing shoes" } },
  "highlight": {
    "pre_tags": ["<mark>"], "post_tags": ["</mark>"],
    "fields": { "description": { "fragment_size": 120, "number_of_fragments": 2 } } },
  "suggest": { "did_you_mean": {
    "text": "runing shoes",
    "phrase": { "field": "description" } } } }

The response carries hits[].highlight.description (a list of snippets) and a suggest block with corrected phrases. Highlighting works from the stored text and the query terms, so highlight the same field you query. If the page shows user text as HTML, escape it: set "encoder": "html" so stored markup is not injected into the page. The default highlighter is fine for most cases.

Remember: highlight = marked snippets per hit; suggest = corrected spelling. Use the html encoder for safety.

Write the query behind a product search page: text search, filters, sort, page, highlight and facet counts. Senior

One request does it all: a bool query with the text in must and the filters in filter, a sort with a tie-breaker, from and size for the page, highlight for snippets and aggs for the facet counts. The detail that interviewers check is where each piece goes and why.

GET products/_search
{ "query": { "bool": {
    "must":   [ { "multi_match": { "query": "running shoes",
                   "fields": ["name^3", "description"], "fuzziness": "AUTO" } } ],
    "filter": [ { "term":  { "in_stock": true } },
                { "terms": { "brand": ["nike", "adidas"] } },
                { "range": { "price": { "gte": 50, "lte": 150 } } } ] } },
  "post_filter": { "term": { "color": "red" } },
  "aggs": {
    "brands": { "terms": { "field": "brand", "size": 10 } },
    "colors": { "terms": { "field": "color" } },
    "price_ranges": { "range": { "field": "price",
        "ranges": [ { "to": 50 }, { "from": 50, "to": 100 }, { "from": 100 } ] } } },
  "sort": [ { "_score": "desc" }, { "id": "asc" } ],
  "highlight": { "fields": { "name": {} } },
  "_source": ["id", "name", "price", "brand"],
  "from": 0, "size": 20 }
  • filter vs must: exact conditions in filter (no scoring, cached).
  • post_filter: the chosen colour narrows the results but not the facet counts, so the colour facet still shows all colours (explained in the facets question).
  • sort: score first, then a unique field as a tie-breaker so pages are stable.
  • _source filtering: return only the fields the page needs.

Remember: text in must, exact in filter, facets in aggs, selected facet in post_filter, sort with a tie-breaker, trim _source.

How do you find out why a document matched, why it ranked high, or why a query is slow? Senior

I use three tools. The _analyze API shows what terms my text produces, which explains most "why no match". explain shows how one document's score was computed. profile shows how long each part of a query took on each shard, which finds the slow clause.

POST _analyze  { "field": "name", "text": "Running Shoes" }

GET products/_explain/42
{ "query": { "match": { "name": "running shoes" } } }

GET products/_search
{ "profile": true, "query": { "bool": { "must": [ { "match": { "name": "shoes" } } ] } } }

_explain returns a tree: term frequency, inverse document frequency, field length factor, boost, and the final number, or tells me the document did not match and which clause failed. In the profile output I look for the clause with the largest time_in_nanos (often a wildcard, regexp or a script) and for breakdown phases such as advance or score. Beyond the query, the slow log (index.search.slowlog.threshold.query.warn) shows which queries are slow in production. Use profile in test, since it adds overhead itself.

Remember: _analyze for terms, _explain for score, profile for time, slow log for production.

5. Relevance and scoring

How does Elasticsearch score documents? Explain BM25 in plain words. Intermediate

The default scoring is BM25. A document scores higher when the query word appears more often in it, when the word is rare across all documents, and when the document (field) is short. Frequency helps but saturates, so repeating a word 50 times is not 50 times better.

  • Term frequency (tf): more occurrences means a higher score, with diminishing returns (controlled by k1, default 1.2).
  • Inverse document frequency (idf): a rare word like "ergonomic" is a stronger signal than "the". Rarer means a higher weight.
  • Field length: one match in a 3-word title beats one match in a 3,000-word body (controlled by b, default 0.75).

The score is only meaningful for ranking within one query; do not compare scores across queries or treat them as percentages. Two practical points. Statistics are per shard, so on small data with many shards the idf can differ and ordering looks odd; dfs_query_then_fetch fixes this at extra cost, but the real cure is fewer shards. And when you sort by a field instead of _score, scores are not computed at all (unless track_scores: true), which saves work. BM25 replaced the older TF-IDF default in Elasticsearch 5.0.

Remember: BM25 = frequent in doc (saturating) x rare overall x short field. Scores only rank, they are not percentages.

How do I tune ranking: boosts and business signals like popularity or recency? Senior

First the cheap tools: field boosts (name^3) and should clauses that add a bonus. When text relevance alone is not enough, I wrap the query in function_score to blend in signals like popularity or freshness. I keep the signal small enough that it adjusts the order but does not drown out the text match.

GET products/_search
{ "query": { "function_score": {
    "query": { "match": { "name": "running shoes" } },
    "functions": [
      { "field_value_factor": { "field": "sales", "modifier": "log1p", "factor": 0.5, "missing": 0 } },
      { "gauss": { "created": { "origin": "now", "scale": "30d", "decay": 0.5 } } } ],
    "score_mode": "multiply", "boost_mode": "multiply" } } }

Here log1p on sales means a product with 10,000 sales is better but not 10,000 times better, and the gauss decay halves the freshness boost every 30 days. Always use a damping function (log1p, sqrt) on counts, otherwise one hugely popular item wins every query. Keep it testable: collect example queries with the expected top results, and compare the ranking before and after a change. For a simple numeric signal, the rank_feature field type is a cheaper alternative. A pinned product list is done with the pinned query.

Remember: boost fields, then function_score with damped signals (log1p, decay). Always test with a fixed query set.

6. Aggregations

What are aggregations and what kinds exist? Show a simple example. Basic

Aggregations compute summaries over the documents that match a query, like SQL GROUP BY with counts and averages. There are three families: bucket aggregations group documents (terms, date_histogram, range), metric aggregations calculate a number (avg, sum, min, max, cardinality, percentiles), and pipeline aggregations calculate on the results of other aggregations.

GET orders/_search
{ "size": 0,
  "query": { "range": { "created": { "gte": "now-30d/d" } } },
  "aggs": {
    "by_status": { "terms": { "field": "status", "size": 5 } },
    "avg_total": { "avg": { "field": "total" } },
    "customers": { "cardinality": { "field": "customer_id" } } } }

"size": 0 skips returning hits, since I only want the numbers. Roughly the SQL equivalent: SELECT status, COUNT(*) ... GROUP BY status. Things to know: terms returns the top 10 buckets by default; cardinality and percentiles are approximate (they trade a little accuracy for low memory); aggregations run on doc values (a column-style structure), so the field must be keyword, number or date, not text.

Remember: bucket groups, metric calculates, pipeline works on results. size 0 when you only want numbers.

Write an aggregation for "monthly revenue by category, with the top product in each". Intermediate

I nest aggregations: a date_histogram by month, inside it a terms on category, inside that a sum on revenue and a top_hits for the best product. A sub-aggregation runs once for every bucket of its parent, so the results form a tree.

GET orders/_search
{ "size": 0,
  "aggs": { "per_month": {
    "date_histogram": { "field": "created", "calendar_interval": "month" },
    "aggs": { "per_category": {
      "terms": { "field": "category", "size": 5 },
      "aggs": {
        "revenue": { "sum": { "field": "total" } },
        "best":    { "top_hits": { "size": 1, "sort": [ { "total": "desc" } ],
                                    "_source": ["product"] } } } } } } } }

Use calendar_interval for month, quarter and year (they vary in length) and fixed_interval for fixed lengths like 30d or 1h; the older plain interval is deprecated. Cost multiplies with nesting: 12 months x 5 categories x top hits is fine, but a nested terms on a high-cardinality field explodes. Add "min_doc_count": 0 to a histogram to get empty months too.

Remember: aggregations nest as a tree. calendar_interval for months, and mind the multiplication of bucket counts.

On a search page, selecting a filter should keep the other facet counts correct. How do I do that? Senior

Filters that sit inside the query also shrink the aggregations, which is wrong for facets where I want to still see the counts of the other options. So for the facet the user just selected, I use post_filter. It filters the hits after the aggregations were computed. For several facets at once, I use a filter aggregation per facet that applies all the other filters except its own.

GET products/_search
{ "query": { "match": { "name": "shoes" } },
  "post_filter": { "term": { "color": "red" } },
  "aggs": {
    "colors": { "terms": { "field": "color" } },
    "brands": { "filter": { "term": { "color": "red" } },
                "aggs": { "b": { "terms": { "field": "brand" } } } } } }

Reading it: the hit list shows only red shoes (post_filter). The colors facet still counts all colours of "shoes", so the user can switch colour. The brands facet counts brands among red shoes only, because it applies the colour filter itself. The cost is that post_filter runs after the aggregations, so it does not make them cheaper and can slow the search. Use it only for facet-style filters, and put all other conditions in the normal bool filter.

Remember: filter in the query narrows everything. post_filter narrows hits only, so sibling facet counts stay full.

Are terms aggregation counts exact? Senior

Not always. Each shard returns only its own top terms (shard_size), and the coordinator adds them up. A term that is popular overall but just misses each shard's cut-off can be undercounted or missing. On a single shard it is exact. The response tells me the worst-case error in doc_count_error_upper_bound.

Example: with 3 shards, a term ranked 11th on every shard is cut from all three lists, yet its total could rank in the top 10. By default shard_size is about size * 1.5 + 10, which usually makes the error negligible. If I need better accuracy, I raise shard_size (more memory and network), or I route documents so each term lives on one shard. For fully exact grouping over very many values, the composite aggregation pages through all buckets, using after_key to continue, much like search_after. Remember the other approximations too: cardinality and percentiles are estimates by design.

{ "aggs": { "top": { "terms": { "field": "brand", "size": 10, "shard_size": 100 } } } }

Remember: terms aggs are per-shard top-N merged, so approximate with many shards. Raise shard_size, or use composite for exact paging.

7. Sorting and pagination

How does sorting work, and what should I watch for? Basic

I add a sort array with fields and directions. Sorting only works on fields that have doc values: keyword, numbers and dates, not analysed text. If I sort by a field, the relevance score is not used for ordering (and is not even computed unless I ask for it). I always add a unique tie-breaker, so pages are stable.

GET products/_search
{ "query": { "match": { "name": "shoes" } },
  "sort": [ { "price": "asc" },
            { "name.raw": "asc" },
            { "id": "asc" } ] }

Use "_score": "desc" as the first sort when relevance should lead, then break ties by a unique field. Without a tie-breaker, documents with equal values may switch order between requests, so a user paging through can see duplicates or miss items. Sorting by an analysed string fails with a fielddata error; use the keyword sub-field. Missing values can be controlled with "missing": "_last". Sorting on a field with doc values is cheap, since doc values are a column-style structure read straight from disk and the file cache.

Remember: sort on keyword, number or date only. Add a unique tie-breaker. Sorting by field skips scoring.

How does from/size pagination work and what is the 10,000 limit? Basic

With from and size, ES has to collect and sort from + size hits on every shard, then the coordinator merges them and throws away the first from. That cost grows with depth, so index.max_result_window defaults to 10,000 and a request beyond it fails. For deep paging I use search_after, not a bigger window.

Example: page 1,000 of 20 per page means from: 19980. With 5 shards, every shard builds a sorted list of 20,000 entries and the coordinator merges 100,000. That is the deep paging problem; it is slow and memory-hungry, and raising the limit only moves the problem. Separately, the hit count is capped too: hits.total reports at most 10,000 with "relation": "gte" (since 7.0) because exact counting is costly. If I truly need the exact total I set "track_total_hits": true; if I only need "more than 10,000", the default is faster.

GET products/_search
{ "from": 19980, "size": 20, "query": { "match_all": {} } }
-- error: Result window is too large, from + size must be less than or equal to 10000

Remember: from + size cost grows with depth, so the 10,000 cap. Deep paging means search_after. The total count is capped at 10,000 unless track_total_hits is true.

What is search_after, and how does it differ from from/size and scroll? Intermediate

search_after is cursor-style paging: I send the sort values of the last hit from the previous page, and ES returns the next hits after that point. No skipping, so every page costs the same. It needs a deterministic sort with a unique tie-breaker. To keep a consistent view while paging I pair it with a point in time (PIT), and for a full export it is the modern replacement for scroll.

POST products/_pit?keep_alive=1m            -- returns { "id": "..." }

GET _search
{ "size": 100,
  "query": { "match_all": {} },
  "pit": { "id": "46ToAwMD...", "keep_alive": "1m" },
  "sort": [ { "created": "asc" }, { "id": "asc" } ] }

-- next page: add the sort values of the last hit
  "search_after": [ 1731800000000, "p-981" ]
  • PIT (7.10+) freezes the view of the index so new writes do not shuffle pages. Without it, documents added or deleted between requests can cause duplicates or misses. Close it when done (DELETE _pit).
  • Scroll does a similar snapshot job with a server-side context, and still works, but Elastic recommends PIT with search_after for deep paging and exports.
  • UI "jump to page N" is not possible; infinite scroll and "next" buttons are.

Remember: from/size = skip and discard, search_after = continue from the last sort value. Add PIT for a stable view and a unique tie-breaker in the sort.

Is scroll still used? What are its drawbacks? Intermediate

Scroll still works and is common in older code for exporting or reindexing everything: the first call opens a snapshot and returns a scroll_id, and I keep calling with that id for the next batches. Its drawbacks are that it holds resources on the server until it expires, it is not meant for user-facing paging, and the recommended replacement is now PIT with search_after.

POST products/_search?scroll=1m
{ "size": 1000, "query": { "match_all": {} } }

POST _search/scroll
{ "scroll": "1m", "scroll_id": "DXF1ZXJ5..." }

DELETE _search/scroll   { "scroll_id": "DXF1ZXJ5..." }

The scroll keeps old segments alive while open (so merges cannot reclaim disk space) and counts against a limit of open contexts (500 by default). Always set a short keep-alive (renewed on each call) and clear the scroll when done. For parallel exports, sliced scroll splits the work into independent slices. Scroll results are a snapshot, so they do not show later writes, which is fine for exports.

Remember: scroll = snapshot cursor for bulk export; heavy on the server. Prefer PIT + search_after for new code.

8. Indexing, updates and keeping data in sync

What happens when I index a document? Explain translog, refresh, flush and segments. Senior

The coordinator hashes the id and sends the write to the right primary shard. The primary analyses the document, adds it to an in-memory buffer and appends it to the translog (a write-ahead log on disk, fsynced per request by default), then forwards it to the replicas and acknowledges once they have it. A refresh later turns the buffer into a searchable segment, and a flush commits segments to disk and trims the translog.

Why this design: segments are immutable files, so Elasticsearch never edits an index in place. A write must still survive a crash before it is flushed, so the translog records it first; after a crash, ES replays the translog. The immutability has a cost for updates and deletes: a delete only marks the old copy as deleted, and an update is a delete plus a full re-index of the document. Background merges combine small segments and finally drop the deleted copies. So an update-heavy workload creates garbage and merge work.

Remember: buffer + translog for durability, refresh for visibility, flush for committing. Update = delete + re-add, merges clean up later.

How does the bulk API work, and how do I use it well? Intermediate

Bulk sends many index, update and delete actions in one request, as lines of newline-delimited JSON (an action line, then a source line). It is much faster than one request per document. The key detail is that the response is HTTP 200 even when some items fail, so I must read the per-item results and retry the failed ones.

POST _bulk
{ "index":  { "_index": "products", "_id": "1" } }
{ "name": "Red running shoes", "price": 79 }
{ "update": { "_index": "products", "_id": "2" } }
{ "doc": { "price": 59 } }
{ "delete": { "_index": "products", "_id": "3" } }
  • Batch size: aim for roughly 5 to 15 MB per request and tune by measurement; huge batches stress memory and heap.
  • Check the response: if "errors": true, look at each item's status. A 429 (es_rejected_execution) means the cluster is overloaded: retry only those items, with exponential backoff, and slow the producer.
  • Bulk load tip: set refresh_interval to 30s or -1 and replicas to 0 during a huge initial load, then restore. In Java use the client's bulk helper (BulkIngester or BulkProcessor) which batches, retries and limits concurrency.
  • Use stable ids so retries are idempotent (a retried index with the same id overwrites, not duplicates).

Remember: bulk = fewer round trips. 200 does not mean success: check per-item status, retry 429 with backoff, use stable ids.

How do updates work, and how do I avoid lost updates from concurrent writers? Senior

A partial update reads the stored _source, merges my change and re-indexes the whole document, so there is no cheap in-place field update. To avoid two writers overwriting each other, I use optimistic concurrency control: read the document's _seq_no and _primary_term, send them back as if_seq_no and if_primary_term, and on a 409 version_conflict I re-read and retry.

GET products/_doc/1                      -- returns _seq_no: 12, _primary_term: 1

PUT products/_doc/1?if_seq_no=12&if_primary_term=1
{ "name": "Red running shoes", "stock": 4 }
-- 409 if someone else changed it meanwhile

POST products/_update/1?retry_on_conflict=3
{ "doc": { "price": 59 } }
-- partial update: ES retries by itself

POST products/_update_by_query
{ "query": { "term": { "brand": "acme" } },
  "script": { "source": "ctx._source.brand = 'ACME'" } }

Use if_seq_no when a read-modify-write in my app must not clobber another change. Use retry_on_conflict for simple partial updates that commute. For data coming from a database, the best approach is external versioning: version_type=external with the row's version, so an old event arriving late is rejected and never overwrites newer data. _update_by_query is a batch operation (it snapshots, then updates each match), not a transaction.

Remember: update = re-index whole doc. Use if_seq_no/if_primary_term to detect conflicts, retry_on_conflict for easy cases, external versions for DB-fed data.

Why is writing to the database and Elasticsearch in the same request a problem? Senior

Because there is no transaction across the two. If the database commit succeeds and the Elasticsearch call fails (or the app crashes between them), search is now missing data, and the opposite can also happen. Retries can apply old data after newer data. So I do not write to both in one request: I write to the database only and update Elasticsearch from there, asynchronously and with retries.

There are also timing problems: ES is near real time, so a user who saves and instantly searches may not see their change, and two concurrent requests can write to the two systems in opposite orders, leaving them different. The fix for all of it is a single source of truth (the database) and one-way, ordered, replayable data flow into ES (the next question).

Remember: no transaction across DB and ES. Write to the DB, feed ES from the DB.

What are the reliable ways to keep Elasticsearch in sync with a database? Senior

Two solid patterns. The transactional outbox: in the same database transaction as the business change, I insert an event row into an outbox table, and a separate process publishes it to a queue (for example Kafka) and a consumer indexes it. Or change data capture (CDC) such as Debezium, which reads the database log and streams changes without changing the app. Both are at-least-once, so the indexer must be idempotent.

  • Idempotent indexing: index by the entity id and use an external version (row version or updated timestamp), so duplicates and out-of-order events are harmless.
  • Deletes: propagate deletes as events, not only inserts and updates, or removed items keep showing in search.
  • Repair: keep a way to rebuild fully: reindex from the database into a fresh index and switch an alias, and run a periodic count or checksum comparison to detect drift.
  • Simple option: a polling job with an updated_at watermark works for small systems but misses hard deletes.

Remember: outbox or CDC, then an idempotent indexer with external versions. Handle deletes and keep a rebuild path.

9. Real-life scenarios

A search that used to take 50 ms now takes 4 seconds. How do you find out why? Senior

I find the exact slow query first, then use profile to see which clause is slow, and compare with what changed: the query, the data volume, or the load. In my experience the usual causes are a leading wildcard or regexp, deep from values, a large size, an aggregation on a high-cardinality field, a script, or a filter placed in must.

Situation: one endpoint got slow; other searches are fine.

Check first:

  • Is it slow for every request or only some inputs? Pull the slow log (index.search.slowlog.threshold.query.warn: 2s) and the response field took, to separate ES time from my app and network time.
  • Run the same body with "profile": true and look for the clause with the biggest time_in_nanos.
  • Look for: wildcard with a leading *, from in the thousands, size of 1,000+, terms aggregation on an id-like field, script queries, huge _source responses, many shards on the index.

Fix: move exact conditions into filter; replace wildcard with n-grams or search_as_you_type; use search_after instead of deep from; return only needed fields (_source filtering); cap aggregation sizes; precompute script values at index time.

Prevent: keep the slow log on, load-test new queries on production-size data, and review any new query shape before release.

Remember: slow log to find it, profile to localise it, then fix the query shape before touching the cluster.

Users save an item and immediately search, but it is not in the results. What is happening? Intermediate

Almost certainly the refresh delay: the document is stored but becomes searchable only after the next refresh, about a second later. If the app also writes via a queue or CDC pipeline, there is extra lag on top. I fix it for the user path with refresh=wait_for or by reading their own data from the database, not by forcing a refresh on every write.

Situation: create item, redirect to a list page backed by search, item is missing, appears on reload.

Check first: does GET index/_doc/id return it (yes means the write worked)? Does the item appear after a second? Is the write synchronous at all, or does it go through a queue? Compare the pipeline lag.

Fix:

PUT products/_doc/1?refresh=wait_for     -- returns when the next refresh made it visible
-- or: show the just-created item from the DB response, not from search

Avoid refresh=true on each write: it creates a tiny segment every time, floods merges and hurts throughput. For a write path that goes through a queue, tell the UI that the list updates shortly, or merge the new item into the displayed list locally.

Prevent: decide per screen whether it needs read-your-writes. Most search pages do not, and only edit screens do.

Remember: write is instant for get-by-id, visible to search after refresh. Use wait_for sparingly, never refresh=true in a loop.

Indexing fails with "Limit of total fields [1000] has been exceeded". What happened and how do you fix it? Senior

Dynamic mapping created too many fields, because some document key is used as a field name (user ids, dates, attribute names). Raising the limit hides the problem and makes the cluster state heavy. The fix is to change the data shape: store such data as a list of key/value items, or map it as flattened, and make the mapping explicit.

Situation: new documents are rejected; the field count keeps rising.

Check first: GET index/_mapping and see which object has hundreds of children, for example attributes.color_red, attributes.size_xl, or metrics.2024-05-01.

Fix:

-- bad: keys are data
{ "attrs": { "color": "red", "size": "xl", "u12345": "x" } }

-- better: fixed field names, data in values
{ "attrs": [ { "k": "color", "v": "red" }, { "k": "size", "v": "xl" } ] }

-- or one field that holds arbitrary keys without mapping each of them
"attrs": { "type": "flattened" }

Use a nested type for the key/value list if you must query key and value together. Raise index.mapping.total_fields.limit only as a temporary relief. The index must be rebuilt (reindex) with the fixed mapping.

Prevent: "dynamic": "strict" in production mappings, and a review of every new field.

Remember: keys must not be data. Key/value lists or flattened, strict mappings, reindex to repair.

You must change a field from text to keyword and add a new analyzer on a live index with 200 million documents. How do you do it without downtime? Senior

Create a new index with the new mapping, copy data into it with _reindex (while the app keeps using the old index through an alias), catch up on the changes made during the copy, then flip the alias atomically. Keep the old index for a while for rollback.

Situation: mapping cannot be edited in place; users keep searching and writing meanwhile.

Steps:

  1. App already uses aliases: products_read and products_write pointing at products_v1. If it does not, introducing aliases first is step zero.
  2. Create products_v2 with the new mapping and analyzer; set refresh_interval: -1 and replicas 0 for speed.
  3. Start _reindex as a background task (wait_for_completion=false), in slices for parallelism, throttled with requests_per_second.
  4. Make new writes go to both indices (dual-write to v1 and v2) or replay changes from the queue or DB after the copy, using external versions so older data never overwrites newer.
  5. Restore replicas and refresh, compare counts and spot-check queries, then flip the alias in one call.
POST _reindex?wait_for_completion=false&slices=auto
{ "source": { "index": "products_v1" }, "dest": { "index": "products_v2", "version_type": "external" } }

POST _aliases
{ "actions": [ { "remove": { "index": "products_v1", "alias": "products_read" } },
               { "add":    { "index": "products_v2", "alias": "products_read" } } ] }

Prevent: always code against aliases and keep a rebuild path from the source of truth.

Remember: new index, reindex in background, catch up on writes, atomic alias flip, keep the old index for rollback.

Users complain that "iphone case" returns phones before cases, and "cases" returns nothing. What do you check and change? Senior

Two separate problems. "Cases returns nothing" is an analysis problem: the field has no stemming or plural handling, so cases does not match case. "Phones before cases" is a ranking problem: the default OR matching and equal field weights let the word "iphone" in titles of phones win. I fix them with a better analyzer, a title boost and requiring all words.

Check first: run _analyze on the field with "cases" to see the stored terms; run _explain on a phone and a case document for the same query to see where the score comes from.

Fix:

"settings": { "analysis": { "analyzer": { "english_text": {
    "tokenizer": "standard", "filter": ["lowercase", "english_stemmer"] } },

An export screen asks for page 2,000 and the API fails with "Result window is too large". What do you do? Intermediate

The request has from + size above 10,000. I do not raise max_result_window, because deep paging makes every shard build huge sorted lists. For a UI I switch to search_after (next and previous only), and for a real export I stream with PIT plus search_after (or scroll on older versions).

Check first: who really needs page 2,000? Usually it is an export or a crawler, not a person. Users rarely go past page 5, so better filtering and sorting fix the real need.

Fix:

POST products/_pit?keep_alive=2m

GET _search
{ "size": 1000, "pit": { "id": "...", "keep_alive": "2m" },
  "sort": [ { "created": "asc" }, { "id": "asc" } ],
  "search_after": [ 1731800000000, "p-981" ] }

Loop until a page returns fewer than size hits, remember the last hit's sort values for the next call, and delete the PIT at the end. For a huge CSV export, run it as a background job and let the user download the file later, instead of holding an HTTP request open.

Prevent: cap the page number in the API, and give users filters and sorting instead of deep paging.

Remember: never raise max_result_window as a fix. UI = search_after, export = PIT + search_after in a background job.

A nightly bulk load now fails with many 429 errors and some documents are missing. How do you fix it? Intermediate

429 means the write queue on the cluster is full: I am sending faster than it can index. The missing documents are items the bulk response reported as failed while the request itself returned 200, and my code did not retry them. The fix is to retry only the failed items with exponential backoff, lower concurrency and batch size, and tune the index for loading.

Check first: does the code inspect "errors": true and each item's status? How many parallel bulk requests and what size? Is refresh_interval still 1 s, with replicas on?

Fix:

  • Parse the bulk response, collect items with status 429 (or 5xx), and resend just those after a growing delay.
  • Reduce parallel workers and keep batches near 5 to 15 MB. More concurrency past the cluster's limit only creates more rejections.
  • For a full reload into a new index: refresh_interval: -1 and number_of_replicas: 0 while loading, restore afterwards.
  • Use stable ids so a retry overwrites instead of duplicating.

Prevent: use the client's bulk helper with backpressure, alert on a non-zero failed-items count, and finish the run with a count check against the source.

Remember: bulk returns 200 with per-item failures. Retry 429 items with backoff, slow down, relax refresh and replicas during the load.

Product managers report deleted products still show in search and some new ones are missing. How do you investigate and repair? Senior

That is drift between the database and the index. Deleted products still showing means deletes are not reaching Elasticsearch; missing new ones means some index events were lost or failed. I measure the drift, fix the pipeline gap, and repair by reindexing from the database.

Check first: compare counts and ids between DB and ES for a sample period (_count versus the table count, or a checksum per id range). Look at how the data gets to ES: does the pipeline handle delete events, are failures in the indexer logged and retried, is there a dead-letter queue with unprocessed messages?

Fix: repair the gap by reindexing the affected range from the database (or a full rebuild into a new index and an alias flip). Send missing deletes explicitly (_delete_by_query on ids that no longer exist in the DB). Then fix the cause: handle deletes in the outbox or CDC flow, make the indexer idempotent with external versions, and add retries and a dead-letter queue.

POST products/_delete_by_query
{ "query": { "terms": { "id": ["p-17", "p-18", "p-19"] } } }

Prevent: a nightly reconciliation job that compares ids or counts between DB and ES and alerts on a difference, plus a tested full-rebuild path. Treat ES as a rebuildable cache of the database.

Remember: ES is a derived copy. Detect drift with reconciliation, repair by reindexing from the DB, and fix delete handling.
