Mental model: the 7 ideas everything hangs on

One line: Elasticsearch is a distributed search engine on top of Apache Lucene. At write time it builds an inverted index (word to documents), so a search looks words up instead of scanning documents. It is fast, near real time, and not transactional.
  1. Inverted index. Text is cut into terms at write time. For each term ES stores the list of documents that contain it. A search looks terms up.
  2. Analysis runs on both sides. "Running Shoes!" becomes the terms running and shoes at index time, and the query text goes through the same process. If the two sides differ, matches silently fail.
  3. The mapping is your schema. It decides what is analysed text (text), an exact value (keyword), a number, a date or a nested object. You cannot change an existing field's type in place.
  4. Query context scores, filter context does not. "How well does it match?" is query context. "Does it match, yes or no?" is filter context, which is faster and cacheable.
  5. An index is split into shards. A shard is one complete Lucene index. A document lives in one primary shard, chosen by hashing its id. Replicas are copies for safety and read speed.
  6. Search is scatter and gather. The node you call asks every shard for its top hits, merges them, then fetches the documents.
  7. Near real time, not a database. New documents are searchable after a refresh (default 1 second). No multi-document transactions, no SQL-style joins. Keep the truth in a database and feed ES from it.

1. Fundamentals and how search works

What is Elasticsearch and what is it good at? Basic

Elasticsearch is a distributed search and analytics engine built on Apache Lucene. You store JSON documents, and it builds indexes that make full-text search, filtering and aggregations fast, usually in milliseconds even over hundreds of millions of documents. I use it for product or document search, log search, autocomplete and dashboard-style counts.

Lucene is the Java library that does the real indexing and searching inside one shard. Elasticsearch adds the parts around it: a REST API with JSON, distribution across nodes, replication and a query language (the Query DSL). The things it is bad at are what a relational database is good at: transactions, joins, strict consistency, and being the single source of truth. So the usual design is a database as the source of truth and Elasticsearch as a derived, searchable copy.

Why it exists. A relational database answers "give me the row with id 42" very well, but it struggles with "find products about waterproof hiking boots, best match first, and tell me how many there are per brand". Doing that with LIKE '%boots%' scans every row, cannot rank, and cannot cope with plurals or typos. Search engines solve this by doing the hard work when data is written (cutting text into words and building an index), so that reading is cheap.

The vocabulary you need.

  • Document: one JSON object, the unit you store and find (like a row).
  • Index: a named collection of documents with a similar shape (like a table, roughly). Do not confuse it with a database index.
  • Mapping: the schema of an index (which field is text, which is a number).
  • Shard: a slice of an index; each shard is a complete Lucene index.
  • Node and cluster: a node is one running Elasticsearch process; a cluster is the group of nodes that share the work.

A tiny example. You store {"name": "Red running shoes", "price": 79} with PUT products/_doc/1. Then GET products/_search with {"query": {"match": {"name": "shoe"}}} returns it ranked by relevance, and an aggs block can add "count per brand" to the same response. One system does the search and the counts.

Where it is used: site and product search, document search, log and event analytics (the "ELK" stack: Elasticsearch, Logstash, Kibana), autocomplete, and metrics dashboards. Where it is weak: being the only copy of important data (it does not give you transactions), many-to-many joins, and workloads that update the same document many times per second. An interviewer who hears "ES is our database" will usually push back, so always say "derived, rebuildable copy".

Remember: ES = Lucene + REST + distribution. Great at search and aggregations, not a system of record.

When would you use Elasticsearch instead of a relational database, and when not? Intermediate

I use Elasticsearch when users need full-text search with ranking, typo tolerance, filters with counts, or aggregations over a lot of data. I keep a relational database for the main data, because it gives transactions, joins and strict consistency, which Elasticsearch does not. In practice I use both: the database is the truth, and Elasticsearch is a search copy fed from it.

The reason for the split is the index structure. A B-tree in a database is great at "find the row with this id or range". It cannot do LIKE '%phone case%' fast, and it has no idea of relevance. An inverted index does exactly that. In return Elasticsearch gives up: no multi-document transactions, a new write is visible only after a refresh (about 1 second), no real joins, and updates are expensive because they rewrite the whole document.

The core idea: two different index structures. A database index (a B-tree) is sorted by the column value. That is perfect for "id = 42" or "price between 10 and 20", because it can walk straight to the place. It is useless for "the word boots appears somewhere inside the description", because the sort order is by the whole string, not by the words inside it. An inverted index is sorted by word, so it answers that question directly and can also rank the matches.

A concrete comparison. Query: "waterproof boots under 100, newest first, plus a count per brand."

  • SQL way: WHERE description LIKE '%waterproof%' AND description LIKE '%boots%' AND price < 100 ORDER BY created DESC plus a second GROUP BY brand query. The LIKE conditions cannot use a normal index, so it scans the table. There is no concept of "best match first", no stemming ("boot" will not match "boots") and no typo tolerance.
  • Elasticsearch way: one request with a match on the text, a range filter on price and a terms aggregation on brand. The words are looked up in the inverted index and the counts come from column-style data (doc values). Results are ranked by relevance.

Decision rule I use. Does the user type free text or need ranking, facets and counts over a large data set? Add Elasticsearch. Is it "find by key, join a few tables, change several rows atomically"? Stay on the database. A table with 50,000 rows and a simple LIKE 'abc%' does not need a search cluster, and a database with built-in full-text search (for example PostgreSQL) can be enough for small needs. Adding ES also adds a new system to run, a sync pipeline to build and eventual consistency to explain to users.

What an interviewer probes next: "how do you keep the two in sync" (answer: the outbox/CDC question later on this page) and "what do you do when ES and the database disagree" (the database wins; rebuild the index).

Remember: DB for truth and transactions, ES for search and analytics. Never make ES your only copy.

What is an inverted index and why does it make search fast? Basic

An inverted index is like the index at the back of a book: for every word it lists the documents that contain that word. A search looks up the query words in a sorted dictionary and reads those lists, instead of scanning every document. That is why search time depends on how many documents match, not on how many documents exist.

It is "inverted" because a normal store maps document to words, and this maps word to documents. Each entry also keeps the positions of the word (needed for phrase search) and the term frequency (needed for scoring). To combine words, ES intersects or unions the sorted lists, which is quick. The cost is paid at write time: text is analysed and the index is built, which is why indexing is heavier than a plain insert.

How it is built, step by step. Take the three documents in the picture.

  1. Each text is analysed (cut into words and lowercased): doc 1 gives red, running, shoes.
  2. For every word, the engine records which documents contain it. The words are kept in a sorted dictionary, so a lookup is a quick binary-search-like jump, not a scan.
  3. Next to each document id it also stores how often the word occurs (term frequency, used for scoring) and the positions (used for phrase queries such as "running shoes").

How a query uses it. For match: "red jacket", ES analyses the query into red and jacket, looks both up (red = [1,3], jacket = [2,3]) and combines the lists. With AND it intersects them (only doc 3). With OR it unions them (docs 1, 2, 3) and scores doc 3 highest because it matched both words. Intersecting two sorted lists of ids is a fast linear merge, which is why even millions of documents answer in milliseconds.

The trade-off. The index is built at write time, so writing is heavier than a plain row insert, and updating a document means re-analysing it. Also, the structure answers "which documents contain this word" brilliantly but is not designed for "give me the whole value of field X for document 7". For that, ES keeps a second structure next to it:

  • Inverted index: term to documents. Used for searching and filtering.
  • Doc values: document to value, stored column by column on disk. Used for sorting and aggregations.
  • Stored _source: the original JSON, returned in the response.

Pitfall: the inverted index stores analysed terms, not your original text. If the analyzer lowercases and stems, the index contains run, not Running. That is exactly why an exact-value term query on an analysed field fails, a classic question in this chapter.

Remember: word to documents, built at write time. Search cost follows matches, not total documents.

What happens inside the cluster when I send a search request? Intermediate

The node that receives the request becomes the coordinator. It sends the query to one copy (primary or replica) of every shard of the index. Each shard finds its own top hits and returns just ids and scores. The coordinator merges those lists into the global top N, then asks the right shards to fetch the full documents for only those N. Query then fetch, in two phases.

Two consequences matter for developers. First, a search with from: 0, size: 10 over 5 shards pulls 10 candidates from each, so cost grows with from + size (this is the deep paging problem). Second, relevance is computed per shard, so with very little data and many shards, scores can differ slightly from a single shard. The fix, if it matters, is search_type=dfs_query_then_fetch, which first collects global term statistics, at extra cost.

Walk through one request. You run GET products/_search with from: 0, size: 10 on an index with 3 primary shards.

  1. Your request reaches any node. That node becomes the coordinating node for this request (every node can do this).
  2. Query phase. For each of the 3 shards, the coordinator picks one copy (primary or a replica, rotating so load is spread) and forwards the query. Each shard runs it against its local Lucene index and builds a priority queue of its own best 10 hits (from + size entries). It sends back only document ids and scores or sort values, which is tiny.
  3. The coordinator merges the 3 lists of 10 (30 candidates) and keeps the global top 10.
  4. Fetch phase. The coordinator asks only the shards that own those 10 winners to return the actual _source (and highlights). This is a multi-get by id, so it is cheap.
  5. The coordinator assembles the response with took, hits, and the merged aggs.

Why two phases? Shipping full documents from every shard would waste network: 30 documents travel to be thrown away. Sending ids and scores first means only the 10 winners are fetched in full.

Replicas help reads. Because any copy can answer, adding replicas raises search throughput, not just safety. Adding primaries raises the data and write capacity, but each search then has more shards to visit.

Pitfalls and probes.

  • If one shard is slow or down, the whole request waits for it or returns partial results. The response includes _shards.failed, and timed_out when a timeout was set. Always look at those fields in production code.
  • Scores come from per-shard statistics, so tiny indices with many shards can rank oddly. The better cure is fewer shards; dfs_query_then_fetch is the workaround.
  • Aggregations follow the same scatter and gather pattern, which is why some of them (terms, cardinality) are approximate when merged.

Remember: coordinator fans out, shards return top ids, coordinator merges, then fetches. Cost grows with from + size.

Why is Elasticsearch called near real time? Basic

Because a document I index is not searchable immediately. It becomes visible at the next refresh, which by default runs every second. So search sees data about a second late. Fetching a document by id is real time, because that reads from the transaction log if needed.

Why the delay: a refresh writes the in-memory buffer as a new small Lucene segment and opens it for search. That is cheap enough to do every second, but doing it per document would be very costly. For a user who saves and then immediately searches, I can pass ?refresh=wait_for on the write (waits for the next refresh, fine for occasional writes) or ?refresh=true (forces one now, harmful under load). For bulk loads I do the opposite: set refresh_interval to 30s or -1 while loading, then restore it, which makes indexing noticeably faster.

PUT products/_doc/1?refresh=wait_for
{ "name": "Red running shoes" }

PUT products/_settings
{ "index": { "refresh_interval": "30s" } }

Note that an idle shard (no search for 30 seconds by default) skips scheduled refreshes, and the next search triggers one, so this is invisible in practice.

What happens in the first second. A new document is first placed in an in-memory indexing buffer and appended to the translog (the safety log). At that point it is durable, but no search can see it, because searchers read only committed-to-searchable Lucene segments (small immutable index files). At the next refresh, the buffer is written as a new segment and the searcher is reopened to include it. From now on, search sees the document.

Timeline example.

  • t = 0.00 s: PUT products/_doc/1 returns 201. The document exists.
  • t = 0.20 s: GET products/_doc/1 works (real-time get, it can read from the translog). _search does not find it yet.
  • t = 1.00 s: refresh runs. _search finds it.

Why not refresh on every write? Each refresh creates a new tiny segment. Hundreds of tiny segments make every search slower (it has to look in each one) and force the background merger to work hard. A 1-second batch is the compromise between freshness and cost.

Pitfalls. Tests that index and then search without a refresh are flaky; call the refresh API in tests. A pipeline through a queue adds its own lag on top of the 1 s. And "near real time" is about searchability, not durability: the data is already safe in the translog before it is searchable.

Remember: searchable after refresh (about 1 s), get-by-id is instant. Use wait_for for read-your-write, slower refresh for bulk loads.

What are shards and replicas, and how many should an index have? Intermediate

An index is split into primary shards so data and work spread over nodes. Each document is routed to one primary by hashing its id. A replica is a copy of a primary on a different node: it keeps data safe if a node dies and also serves search requests. The number of primaries is fixed when the index is created, so I size it for the data and keep shards moderate, not tiny and not huge.

Routing is shard = hash(_routing) % number_of_primary_shards, where _routing defaults to the document id. That formula is why you cannot change the primary count in place: the modulus would change and documents would be looked up in the wrong shard. To change it you reindex, or use the split or shrink APIs. Replicas can be changed any time, and default to 1.

The common mistake is over-sharding. Every shard costs memory, file handles and a thread when searched, and a search touches all shards of the index. Hundreds of tiny shards are slower than a few well-sized ones. A rule of thumb many teams use is shards of roughly 10 to 50 GB, and since 7.0 the default is just one primary. If data grows over time (logs), use time-based indices instead of one giant index. Cluster-level planning is specialist territory beyond this page.

Worked example. Index orders with 3 primaries and 1 replica each means 6 shards in total, placed on at least 2 nodes (a replica never shares a node with its own primary). Write document order-77: hash("order-77") % 3 = 1, so it goes to primary P1 and is copied to P1's replica. A search touches one copy of each of the 3 shards.

Why not "as many shards as possible"?

  • Each shard is a full Lucene index with its own memory structures, file handles and cluster-state entry. Thousands of small shards waste heap and slow down the master node.
  • A search must visit every shard of the index (unless you route), so 100 shards of 100 MB each cost more than 2 shards of 5 GB.
  • Too few, very large shards make recovery and rebalancing slow (moving a 300 GB shard takes a long time).

How I would size it. Estimate the final index size, divide by a target shard size of roughly 10 to 50 GB (a common starting point, not a law; measure for your workload), and round to a small number. A 20 GB product index: 1 primary is fine today. For logs, use time-based indices (one per day or month, or rollover) so old indices can be dropped or shrunk without touching new ones.

Replica count. One replica gives you survival of a single node failure and doubles read capacity. Zero replicas is acceptable only during a bulk load or when data is easily rebuilt. More replicas help read-heavy workloads but multiply storage and write work.

What to watch. Hot shards: if one customer owns most of the data and you route by customer id, that shard grows far larger than the rest. Resizing later is possible with the _split (increase, in multiples) and _shrink (decrease) APIs, but both need a read-only index and planning.

Remember: primaries are fixed at creation and chosen by hash(id); replicas are copies for safety and reads. Too many small shards hurt.

What do green, yellow and red cluster health mean, and why is my index yellow? Intermediate

Green means all primary and replica shards are allocated. Yellow means all primaries are allocated, but at least one replica is not: searches and writes work, but there is no spare copy, so one more node failure could lose data. Red means at least one primary shard is not allocated, so part of the index is unavailable and searches on it return partial results or errors.

The most common yellow. A single-node cluster (a laptop or a dev container) with the default 1 replica. A replica is never placed on the same node as its primary, so with one node the replicas stay unassigned and the index stays yellow forever. That is normal. The fix is either to add a node or to set number_of_replicas: 0 in development.

How to investigate.

GET _cluster/health?level=indices
GET _cat/shards?v&h=index,shard,prirep,state,unassigned.reason
GET _cluster/allocation/explain

_cat/shards shows which shards are UNASSIGNED and the reason; _cluster/allocation/explain tells you in words why a particular shard cannot be placed. Typical reasons: not enough nodes for the replica count, a node left and the cluster is waiting before reallocating (a delay of about one minute by default), disk watermarks reached so no new shards are placed on a full node, or allocation filters that exclude every node.

What happens to my data and my writes when a node dies? Senior

If the dead node held a primary shard, the cluster promotes one of that shard's replicas to be the new primary, so no acknowledged write is lost as long as the write had reached the replica copies in sync. Then it rebuilds the missing replicas on the remaining nodes. Searches keep working from the surviving copies. This is why I run at least one replica and at least three master-eligible nodes in production.

Step by step, node 2 dies and it held primary P1.

  1. The master node notices (a missing heartbeat) and removes node 2 from the cluster state.
  2. For P1, an in-sync replica on another node is promoted to primary and the primary term is increased. Writes continue against the new primary. The index is yellow for a while.
  3. After a short delay (to avoid reshuffling if the node comes back right away), the master allocates new replica copies on other nodes and copies the data across. When done, the index is green again.
  4. If node 2 returns early, it can reuse its on-disk data and catch up from the translog instead of copying everything.

Why writes do not get lost. A write is acknowledged only after the primary and all in-sync replicas applied it. The index setting wait_for_active_shards (default 1, meaning just the primary) lets you require more active copies before a write is even attempted. Note that this protects availability and not durability by itself: durability comes from replicas holding the data plus the translog fsync.

When data can be lost.

  • Zero replicas: a dead node with a primary means a red index, and if its disk is gone, the data is gone. Restore from a snapshot.
  • All copies of a shard on failed nodes at once (for example both nodes in one availability zone, with no zone awareness).
  • Split brain was historically a problem with an even number of master-eligible nodes. Since 7.0 the cluster manages its voting configuration itself, but you still want 3 master-eligible nodes so a majority survives one failure.

What the app should do. Use the client's retry on connection failures and keep several node addresses in the client config. Make writes idempotent (stable ids) so a retry after an ambiguous failure is safe. Snapshots (backups) are still needed because replicas protect against a node failure, not against a bad delete or a bad deployment.

Remember: a replica is promoted to primary, then new replicas are rebuilt. Replicas are for availability, snapshots are for backup, and writes need stable ids so retries are safe.

2. Analysis: how text becomes terms

What is an analyzer and what are its parts? Basic

An analyzer turns a piece of text into the list of terms that go into the inverted index. It has three stages: character filters clean the raw text, a tokenizer splits it into tokens, and token filters change the tokens (lowercase, stemming, stop words, synonyms). The default standard analyzer splits on word boundaries and lowercases.

The point is that I want "Running" and "run" to find the same documents, so both the stored text and the query text are normalised the same way. I debug analysis with the _analyze API, which shows the exact terms produced. Most "why does my search not match?" problems are solved by looking at that output.

POST _analyze
{ "analyzer": "standard", "text": "Running Shoes!" }
-- terms: running, shoes

Why analysis exists. Computers compare strings exactly, but people do not search that way. A user types "running shoe", the product title says "Red Running Shoes!". Without analysis there is no match: different case, a plural, punctuation. Analysis rewrites both sides into a normal form so the comparison works.

The three stages with an example. Input: <p>The Quick Foxes</p>.

  1. Character filters (zero or more) rewrite the raw string before splitting. html_strip removes the tags: The Quick Foxes. A mapping char filter can replace characters.
  2. The tokenizer (exactly one) cuts the string into tokens: The, Quick, Foxes. The standard tokenizer follows Unicode word boundaries; whitespace splits only on spaces; keyword keeps the whole string as one token.
  3. Token filters (zero or more, in order) change the tokens: lowercase gives the, quick, foxes; a stop filter would drop the; a stemmer would turn foxes into fox; a synonym filter could add car beside automobile.

The resulting terms are what go into the inverted index, and the same pipeline (usually) is applied to the query text.

asciifolding makes "café" match "cafe". Pitfalls: the analyzer is fixed per field once data is indexed (changing it needs a reindex); language-specific stemming is lossy (it may conflate unrelated words); and stop word removal breaks searches such as "to be or not to be". Test with _analyze before you ship an analyzer.

Remember: char filter, tokenizer, token filters. When a match surprises you, run _analyze.

Is the same analyzer used when indexing and when searching? What goes wrong if they differ? Intermediate

By default yes: a text field uses its analyzer at index time and the same one at query time, so both sides produce the same terms. If they differ by accident, the query terms do not exist in the index and the search returns nothing, with no error. I only use a different search_analyzer on purpose, mainly for autocomplete.

A typical accident: the field was indexed with a stemming analyzer (stores run) but the query goes against a keyword field or a term query, which does not analyse, so searching Running finds nothing. The intended use is edge n-grams: index "laptop" as l, la, lap, ... but analyse the query "lap" only as lap, otherwise the query would also be cut into n-grams and match unrelated words.

Why the two sides must agree. The index stores the output of the index-time analyzer. The query text goes through the search-time analyzer and the resulting terms are looked up in the index. A match happens only if the two produce the same terms. Think of it as a key and a lock: the key must be cut the same way as the lock.

A failing example.

  • Field title uses an english analyzer. The document "Running Shoes" is stored as terms run, shoe.
  • A match query on title analyses "Running" with the same analyzer into run, and finds it. Good.
  • A term query on title for Running sends the raw string Running, which is not in the index (the index has run). Zero results, no error. Same effect if you query a different field that was analysed differently.

The one legitimate reason to split them: autocomplete. At index time, "laptop" is expanded by an edge n-gram filter into l, la, lap, lapt, lapto, laptop. A user who has typed "lap" should match, so the index must contain lap. But at search time you want "lap" to stay as the single term lap. If the same n-gram analyzer ran on the query, "lap" would become l, la, lap and match anything starting with "l", which is far too broad. So you set analyzer (index time) to the n-gram analyzer and search_analyzer to a plain one.

"name": { "type": "text",
          "analyzer": "autocomplete_ngram",
          "search_analyzer": "standard" }

Another legitimate case: synonyms applied only at search time, so you can change the synonym list without reindexing (search-time synonyms can be reloaded with the reload API in newer versions; check your version).

Debug routine. Run POST index/_analyze with "field": "title" and the query text, and compare with what the stored document produces. If the two term lists differ, you have found the problem.

Remember: same analysis on both sides, unless you chose a search_analyzer deliberately (autocomplete). A mismatch gives empty results, not errors.

How would you build autocomplete (search as you type)? Senior

For a normal "type three letters, see matching products" box I use the search_as_you_type field type, or an edge n-gram analyzer at index time with a plain analyzer at search time. If I only need fast prefix suggestions on a name list, I use the completion suggester. The trade-off is index size and flexibility: n-grams are flexible but larger, completion is fastest but matches only from the start.

  • edge_ngram: indexes every prefix of each word (l, la, lap, lapt...). A query for "lap" is a normal term lookup, so it is fast. Costs more disk and slower indexing.
  • search_as_you_type: built-in field type (7.2+) that creates the n-gram sub-fields for you; query it with multi_match of type bool_prefix.
  • completion suggester: an in-memory structure for prefix lookup, very fast, but prefix only, no typo tolerance by default and limited ranking control.
  • prefix / match_phrase_prefix: no extra setup, but expands terms at query time; fine for small data only.

First decide what "autocomplete" means. There are three different products hiding behind the word.

  1. Suggest query strings or names as the user types ("laptop stand", "laptop bag"): the completion suggester or search_as_you_type on a name field.
  2. Search results while typing (instant search): matches on words in titles, mid-phrase included. This is search_as_you_type or edge n-grams, with the normal search path.
  3. Typo-tolerant "did you mean": the phrase suggester or fuzziness.

How edge n-grams work, with numbers. The word "laptop" with edge n-grams of min 1 and max 10 is stored as l, la, lap, lapt, lapto, laptop. A query "lapt" is looked up as one term and found directly. No scan, no wildcard, so it stays fast, at the price of a bigger index (several terms per word) and slower indexing. Choose a sensible min_gram (often 2) and max_gram, otherwise the index grows for no gain.

What search_as_you_type builds for you. It creates sub-fields name._2gram, name._3gram (shingles of 2 and 3 words) and name._index_prefix (edge n-grams of the last word). A bool_prefix multi_match treats the last typed word as a prefix and the previous words as complete terms, so "red run" matches "Red running shoes" and "wireless head" matches "wireless headphones". The word order is free, and phrase-like ranking comes from the 2-gram and 3-gram fields.

Completion suggester. It uses a compact in-memory structure (an FST), so lookups take microseconds. Feed it explicit inputs and weights (for example popular searches) with the completion field type. It matches only from the start of the input (with fuzzy optional) and returns suggestions, not full documents with filters, though it supports contexts (such as category) for narrowing.

3. Mappings

What is the difference between the text and keyword field types? Basic

A text field is analysed: it is split into terms and lowercased, so I can do full-text search on it. A keyword field is stored as one exact value, so I use it for filtering, sorting and aggregations on things like status, email, id or country. For a string I need both ways, I map it as text with a keyword sub-field.

That is exactly what dynamic mapping does for strings: name becomes text, and name.keyword is a keyword (values longer than 256 characters are not indexed in it). Sorting and aggregating on a plain text field fails, with an error about "fielddata", because the index holds terms, not whole values. The right fix is to use the .keyword sub-field, not to enable fielddata, which loads every term into heap memory.

PUT products
{ "mappings": { "properties": {
    "name":   { "type": "text", "fields": { "raw": { "type": "keyword" } } },
    "status": { "type": "keyword" },
    "price":  { "type": "scaled_float", "scaling_factor": 100 }
} } }

GET products/_search
{ "sort": [ { "name.raw": "asc" } ],
  "aggs": { "by_status": { "terms": { "field": "status" } } } }

For money I use scaled_float or integer cents, not a plain float.

Choose by how you use the field. If humans search it in words (title, description, comments), use text. If a program compares it for equality, groups by it, or sorts by it (status, country, SKU, email, tenant id, enum values), use keyword. If both, use a multi-field: text on the main field and a keyword sub-field for the exact side. Numbers that you never do range queries on (zip codes, phone numbers, ids) are often better as keyword: term lookups on keywords are fast, and they keep leading zeros.

Useful keyword options. ignore_above skips very long values (the dynamic default is 256 for the sub-field). A normalizer (for example lowercase) lets you do case-insensitive exact matching while keeping a keyword. Newer versions also offer a case_insensitive option on the term query.

Why not just make everything text? Text fields cost more CPU and index space (analysis, positions, norms) and cannot be sorted or aggregated without loading fielddata into heap. Why not make everything keyword? Then no word-level search. The common bug is the reverse of what people expect: querying a text field with term and a capital letter. Look at the mapping first (GET index/_mapping) whenever a query surprises you.

Remember: text = searched by words, keyword = exact value for filter, sort, aggregate. Use both via a sub-field.

What are doc values and fielddata, and why can't I sort or aggregate on a text field? Senior

The inverted index maps term to documents, which is the wrong direction for sorting and aggregating, where I need document to value. For that Elasticsearch writes doc values, a column-style structure stored on disk at index time for keyword, numeric, date and most other non-text fields. Text fields have no doc values, so sorting or aggregating on them fails unless I enable fielddata, which builds the structure in JVM heap at query time and is risky. The normal fix is a keyword sub-field.

Why the direction matters. To sort by price you need, for each matching document, its price. The inverted index would force you to read every term and check whether the document is in its list. Doc values store, in document order, the value for each document, so a sort or a terms aggregation reads a compact column. It is kept on disk and relies on the operating system file cache rather than the JVM heap, so it scales to big data.

Why enabling fielddata on text is rarely what you want even if it works. A terms aggregation on an analysed field returns single words (red, running), not whole values, and it loads every unique term into heap. Use the .keyword sub-field and you get whole values with no heap cost.

If a field is never sorted, aggregated or used in scripts (for example a big keyword field you only filter on), you can set "doc_values": false to save disk. Conversely, if a field is only ever sorted or aggregated and never searched, you can set "index": false and keep only the column.

What is dynamic mapping and what are its pitfalls? Intermediate

Dynamic mapping means that when a document has a field ES has not seen, it guesses the type and adds it to the mapping automatically. It is handy for a quick start, but risky in production: the first value decides the type forever, and unknown keys can bloat the mapping. For real systems I define the mapping explicitly and set dynamic to strict or false.

  • Wrong guess: the first document has "zip": "02134" (text) or "id": 7 (long). Later documents with a different shape get rejected, or are searched wrongly.
  • Strings become text plus keyword, which doubles the index cost for fields you only ever filter on.
  • Mapping explosion: if keys are data (for example user ids used as field names), the mapping grows without bound. The default limit is 1,000 fields per index, and past that indexing fails. Model such data as an array of {key, value} objects, or use the flattened type.
PUT products
{ "mappings": { "dynamic": "strict",
    "properties": { "name": { "type": "text" } } } }

strict rejects documents with unknown fields, false accepts them but does not index them, true (default) maps them.

What dynamic mapping does, with the detection rules. When a new field appears, ES chooses a type from the JSON value: a string becomes text with a .keyword sub-field (unless it looks like a date, and date detection is on by default for common formats), integers become long, decimals become float, booleans become boolean, and objects become object. Numbers inside strings ("7") are not detected as numbers by default.

A pitfall in numbers. The first document has "price": 10, so the field becomes long. The second document has "price": 9.99. It is accepted, but the value is stored in the document's _source as 9.99 and indexed truncated into a long (the search index sees 9), so range queries are wrong. That silent loss is worse than an error. Defining price explicitly as scaled_float avoids it. And a first value of "N/A" in a field that later receives dates makes later documents fail.

Useful tools. dynamic_templates let you set rules ("every string whose name ends in _id is a keyword, all other strings are text only"), which fixes the doubled-index cost without losing flexibility. Index templates apply a mapping to every new index matching a pattern (daily log indices).

Why interviewers ask. It reveals whether you have run ES in production. The stories are always the same: a field mapped as the wrong type by the first document, an uncontrolled client sending random keys until the 1,000-field limit is reached, and an index that doubled in size because every string had both text and keyword. The answer: explicit mappings, strict or false for unknown fields, templates for the rest.

Remember: first value fixes the type. Define mappings yourself, use dynamic strict or false, and never use data as field names.

Can I change the mapping of an existing field? Intermediate

No. I can add new fields and some harmless settings, but I cannot change a field's type or its analyzer on existing data, because the inverted index was already built that way. The fix is to create a new index with the right mapping, copy the data with the _reindex API, and switch an alias to the new index.

That is why applications should talk to an alias (products) and not to a concrete index (products_v1). The steps: create products_v2, run _reindex from v1 to v2, then switch the alias in one atomic call, so there is no downtime. For a live system, writes arriving during the copy must also go to the new index or be replayed afterwards (see the zero-downtime scenario below).

POST _aliases
{ "actions": [
  { "remove": { "index": "products_v1", "alias": "products" } },
  { "add":    { "index": "products_v2", "alias": "products" } } ] }

Why it is impossible, not just forbidden. The inverted index for a field was written with one analyzer, as terms. If you switched a field from text to keyword, the old documents would still contain analysed terms and the new queries would look for whole values, so the same query would behave differently on old and new data. Segments are immutable and cannot be rewritten in place, so ES refuses and forces you to build a fresh index.

What you can change on a live index.

  • Add a new field (PUT index/_mapping).
  • Add a sub-field to an existing field (a new multi-field), but only documents indexed afterwards will have it; run _update_by_query to fill it for old documents.
  • A few parameters such as ignore_above on a keyword, or search_analyzer, can be updated.
  • Replica count and refresh_interval (these are settings, not mapping).

What needs a new index: changing a field's type, its analyzer, or index/doc_values options, and the number of primary shards (or use the split/shrink APIs for shards).

The full recipe with numbers. Suppose 200 million documents, 40 minutes per copy.

  1. Create products_v2 with the corrected mapping.
  2. Start _reindex from v1 to v2. It reads documents from the old index and writes them to the new one using the new analysis.
  3. Writes that happened during the copy are replayed or dual-written.
  4. One atomic _aliases call moves the alias. Clients using products never notice.
  5. Keep v1 until you are confident, then delete it.

Tips. Reindex reads _source, so fields that are not in _source are lost (do not disable _source casually). If the new mapping coerces data differently, test with a sample first. Where possible, rebuild from the database instead of from the old index, because it also repairs any drift.

Remember: mappings are append-only. New index, reindex, flip the alias.

What is the difference between object and nested fields, and why does it matter? Intermediate

An array of objects is flattened by default, so the link between fields of the same object is lost. Searching "author first = John and last = Smith" can wrongly match a document with John Doe and Jane Smith. A nested field fixes this by indexing each object as its own hidden document, and I query it with a nested query. It is correct but costs more.

With a plain object, comments: [{user: "john", stars: 5}, {user: "amy", stars: 1}] is stored as comments.user: [john, amy] and comments.stars: [5, 1], so "john with 1 star" wrongly matches. With nested, each comment is a separate Lucene document linked to its parent. The price: more documents, slower queries and updates (changing one comment reindexes the whole parent and all its nested docs), and limits (50 nested fields and 10,000 nested objects per document by default). Use it only when you must query fields together inside one array element.

PUT posts
{ "mappings": { "properties": {
    "comments": { "type": "nested", "properties": {
        "user":  { "type": "keyword" },
        "stars": { "type": "integer" } } } } } }

Why flattening happens. Lucene has no concept of objects: a document is a flat set of fields. ES maps comments.user and comments.stars to two flat multi-value fields. A document with 2 comments gets comments.user = [john, amy] and comments.stars = [5, 1]. Positions of values inside the arrays are not kept as a pair, so the pairing john-5 is gone.

The wrong result in a query. With a plain object, bool must: [comments.user = john, comments.stars = 1] matches this document, because john is somewhere in the user array and 1 is somewhere in the stars array, even though john gave 5 stars. This is a correctness bug, not a performance issue, and users will report it as "the filter shows wrong results".

How nested stores it. Each element becomes its own hidden Lucene document, stored right next to the parent in the same segment (so they are on the same shard and are "block joined"). The nested query runs its inner query against the hidden documents and then maps matches back to the parent. A document with 100 comments is stored as 101 Lucene documents.

The costs, concretely.

  • Memory and disk: more Lucene documents (the doc count in _cat/indices includes nested docs).
  • Updates: changing one comment reindexes the parent and all the comments, because the block must be written together.
  • Limits: index.mapping.nested_fields.limit (50) and index.mapping.nested_objects.limit (10,000 per document) protect against explosions.
  • Queries and aggregations need nested syntax.

Decision rule. Do you ever need two or more conditions to hold on the same array element? If not (for example just "any comment by john" or "any tag red"), keep a plain object or array, which is cheaper and simpler. If yes, use nested. If elements are numerous and change often, consider denormalising into a separate index instead. A third, lighter option, when fields are few, is to concatenate them into a single keyword like "john|5" and use a term query.

Remember: arrays of objects flatten and mix up fields. Use nested when fields must match together, and pay for it.

How do you model relationships in Elasticsearch: denormalise, nested or join? Senior

I denormalise by default: copy the data I need for search into each document, so one query answers it with no join. If I must match fields together inside a list, I use nested. I use the join parent-child field only rarely, when the child data changes much more often than the parent and copying would be too costly. It is slower, and children must sit on the same shard as the parent.

Elasticsearch has no cheap general join across indices, so I model for the queries I need. Example: an order document stores the customer name and city inside it. The cost is duplicate data: when a customer's name changes, I must update (_update_by_query or a reindex) every order that copied it, so I accept that only for fields that rarely change or where slightly stale values are fine. Another option is to search for ids in ES and then load rows from the database in one batch query.

The mindset change. In SQL you normalise data and join at query time. In Elasticsearch you precompute the answer shape: store the data the way it will be queried, even if it repeats. Writes get a little more work, reads become one fast lookup.

Example with an order system. You must search orders by customer name and city.

  • Denormalise: each order document includes customer: {id, name, city}. Search is one query. If a customer changes city, you update the orders you care about (for example with _update_by_query on customer.id), or accept that old orders keep the old city, which is often actually correct historically.
  • Nested: an order with line items [{sku, qty}, ...] where you need "sku = A and qty > 5 in the same line". Items are part of the order, so they change together.
  • Join field: a question with many answers where votes on answers change constantly, and you do not want to reindex the question on every vote. Parent and children are separate documents on the same shard, linked by a join mapping, and queried with has_child or has_parent.

Why join is the last resort. has_child queries must build a global lookup of parent ids in memory (global ordinals), they are noticeably slower than a flat query, and all related documents must share a routing value so they land on the same shard. They also complicate reindexing.

A fourth option: application-side join. Query ES for matching ids, then fetch details from the database or from another ES query (terms on ids). Fine for small result pages (20 ids), and it avoids copying volatile fields into ES. Another approach, for lookups in the other direction, is an enrich processor at ingest time, which copies values from a small lookup index into the incoming document.

How to answer in an interview. Ask "what are the queries and how often do the related fields change?" Then pick: rarely changing, queried together: denormalise. List items queried together: nested. Frequently changing children with a large parent: join. Never say "I would just use join like a foreign key".

Remember: flatten for search; nested if fields must match together; join as a last resort.

4. Writing and reading queries

What is the difference between match, match_phrase and term queries? Basic

match is for full text: it analyses my query text and finds documents containing any of the resulting terms, ranked by relevance. match_phrase needs the terms to appear together and in order. term does no analysis: it looks up the exact value I give, so I use it on keyword, number and date fields, not on analysed text.

GET products/_search
{ "query": { "match": { "name": "red running shoes" } } }
-- terms red OR running OR shoes; more matching terms = higher score

{ "query": { "match": { "name": { "query": "red running shoes", "operator": "and" } } } }
-- all three terms must be present, any order

{ "query": { "match_phrase": { "name": "running shoes" } } }
-- "running" directly followed by "shoes"

{ "query": { "term": { "status": "ACTIVE" } } }
-- exact, case-sensitive value on a keyword field

The classic bug: term on a text field. The index holds lowercase terms (active), but term sends ACTIVE unchanged, so nothing matches. Fix it by using match on text, or term on a keyword field. terms is the "IN" version: {"terms": {"status": ["ACTIVE", "PENDING"]}}. match_phrase accepts a slop setting to allow some words in between.

The mental model. There are two worlds. In the full-text world (match, match_phrase, multi_match) your query string is run through the field's analyzer, so it becomes the same kind of terms the index holds. In the exact world (term, terms, range, exists, prefix) the value you send is used as-is. Most mistakes come from using an exact-world query on a field that stores analysed terms.

One field, three queries. The document has name: "Red Running Shoes", mapped as text (stored terms: red, running, shoes).

Useful variants.

  • minimum_should_match in a match query is the middle ground between OR and AND: "minimum_should_match": "75%" requires three of four words.
  • match_phrase with slop: 1 allows one word in between or a swap.
  • match_phrase_prefix and match_bool_prefix treat the last word as a prefix (a cheap way to build autocomplete on small data).
  • match_all returns everything (score 1.0), exists finds documents that have a value for a field, and ids fetches by id.

Rule of thumb. Ask "is a human typing this?" Yes: match family on a text field. No, a program supplies a fixed value (status, id, enum, boolean): term or terms on a keyword, number or boolean, ideally inside filter.

Remember: match analyses and ORs the words, match_phrase wants order and adjacency, term is exact and only for keyword, number, date. terms = IN.

How do I search several fields at once, with one field more important than the others? Intermediate

I use multi_match with a list of fields and a boost on the important one, for example name^3 so a title match counts three times more than a description match. The type decides how field scores combine: best_fields (default) takes the best single field, most_fields adds them up, and cross_fields treats the fields as one big field.

GET products/_search
{ "query": { "multi_match": {
    "query": "running shoes",
    "fields": ["name^3", "brand^2", "description"],
    "type": "best_fields",
    "tie_breaker": 0.3 } } }

With best_fields, a document where both words are in the name beats one where one word is in the name and the other in the description. With tie_breaker, the other fields add a small share of their score. Use cross_fields when one logical value is split across fields, for example first_name and last_name with "operator": "and". If the same text is indexed several ways (stemmed, exact), most_fields makes sense. Setting fuzziness here also works (see the fuzzy question).

Why not three separate match queries in a bool? You can, and sometimes should, but multi_match is the short form and has smarter combinations. The question to answer is: how do scores of different fields combine into one document score?

Example with numbers. Query "running shoes", fields name^3, description. Document A: both words in the name. Document B: "running" in the name and "shoes" in the description.

When to pick which. Searching a title and a description: best_fields with a small tie_breaker (0.1 to 0.3), because the strongest field should lead. Searching the same text analysed in two ways, such as name (stemmed) and name.exact (not stemmed): most_fields, so an exact hit adds a bonus. Searching a person by "john smith" over first_name and last_name: cross_fields with operator: and, so each word may match in a different field but every word must match somewhere.

Boost syntax. name^3 multiplies that field's score by 3. Boosts are relative, so changing all of them by the same factor changes nothing. Do not guess the numbers: use _explain on a few queries and adjust, then keep your example query set as a regression test.

Pitfall. Do not mix a keyword field with analysed text fields in the same multi_match (a non-analysed field only matches the exact full value, which silently reduces recall); also remember that operator and minimum_should_match apply per field in best_fields but across all fields in cross_fields.

Remember: multi_match + field^boost. best_fields = best one wins, most_fields = sum, cross_fields = one virtual field.

Explain the bool query: must, should, must_not and filter. Basic

The bool query combines clauses. must means "has to match and contributes to the score". filter means "has to match" but does not score and can be cached. must_not excludes matches. should means "nice to have": it raises the score, and if there is no must or filter, at least one should has to match. It is the SQL AND, OR and NOT of Elasticsearch.

GET products/_search
{ "query": { "bool": {
    "must":     [ { "match": { "name": "running shoes" } } ],
    "filter":   [ { "term":  { "status": "ACTIVE" } },
                  { "range": { "price": { "lte": 100 } } } ],
    "must_not": [ { "term":  { "brand": "acme" } } ],
    "should":   [ { "term":  { "on_sale": true } } ],
    "minimum_should_match": 0
} } }

Reading it: text relevance comes from must; the yes/no conditions (active, price under 100) go in filter; excluded brand is must_not; on-sale items get a small bonus from should. The usual trap is should alone beside a must: it then does not filter, only boosts, so people think "OR" does not work. To require "A or B", put both in a should inside its own bool with minimum_should_match: 1. Clauses nest freely.

Mapping to everyday logic.

You wantWrite
A AND Bboth in filter (no score) or both in must (with score)
A OR Bboth in should with minimum_should_match: 1 (inside its own bool)
NOT Amust_not
(A OR B) AND Cbool with filter: [C, {bool: {should: [A, B], minimum_should_match: 1}}]

How should behaves, precisely. If the bool contains at least one must or filter, then minimum_should_match defaults to 0: the should clauses become optional bonuses. If the bool has only should clauses (and must_not), the default is 1, so at least one must match. Inside a filter context the default is 0 too. When in doubt, write minimum_should_match explicitly.

Score arithmetic. The bool score is the sum of the scores of the matching must and should clauses. A document that matches both a must and two shoulds gets a higher score than one that matches just the must. That is how "boost on-sale items" works without excluding others.

Nesting example: "(red or blue) shoes, in stock, not acme".

{ "bool": {
    "must":     [ { "match": { "name": "shoes" } } ],
    "filter":   [ { "term": { "in_stock": true } },
                  { "bool": { "should": [ { "term": { "color": "red" } },
                                          { "term": { "color": "blue" } } ],
                              "minimum_should_match": 1 } } ],
    "must_not": [ { "term": { "brand": "acme" } } ] } }

(For simple cases like this, "terms": {"color": ["red", "blue"]} is shorter than the inner bool.)

Pitfalls. Putting everything in must works but wastes scoring work and caching. A must_not alone with nothing else would return all documents except the matches (it is fine, but it is a very broad query). And an empty bool matches all documents, which has bitten people who build queries from optional user input: guard against empty condition lists.

Remember: must scores, filter does not, must_not excludes, should is a bonus unless it is alone.

What is the difference between query context and filter context, and why does it matter for speed? Intermediate

Query context asks "how well does this document match?" and computes a relevance score. Filter context asks "does it match, yes or no?" and computes no score. Filters are cheaper, and Elasticsearch can cache their results, so I put every exact or yes/no condition (status, date range, category, tenant id) in a filter and keep only the real text search in must.

Scoring needs term frequencies and field lengths, which costs CPU. A filter only produces a set of matching documents, kept as a compact bit set per segment; frequently used filters are cached and reused across requests. Clauses inside filter, inside must_not and the filter parameter of constant_score all run in filter context. Do not filter on text relevance fields like "description contains ..." in filter context if you want ranking, since you would lose scores.

-- faster: text in must, exact conditions in filter
{ "bool": { "must":   [ { "match": { "title": "wireless headphones" } } ],
            "filter": [ { "term": { "tenant_id": "t-42" } },
                        { "range": { "created": { "gte": "now-30d/d" } } } ] } }

Two questions, two costs. "How relevant is this document?" needs statistics from the index: how often the term appears in the document, how rare it is across all documents, the length of the field. "Is the status ACTIVE?" needs none. Filter context skips the first kind of work entirely, and gives a simple set of document ids.

What caching means here. For each segment, Lucene can keep a bitset (one bit per document: 1 = matches) for a filter such as tenant_id = t-42. The next request with the same filter reuses the bitset instead of recomputing it, and combining filters is a bit-wise AND, which is extremely cheap. Elasticsearch's query cache decides itself which filters are worth caching (it tracks usage and typically skips very small segments and rarely reused filters). You do not enable it manually; you just put your yes/no conditions in filter.

Example of the difference. Say must: [{term: {status: "ACTIVE"}}] and filter: [{term: {status: "ACTIVE"}}] return the same documents, but the first gives each a score of about 0.2 (a meaningless number, since every result has the same status) and recomputes each time, while the second gives score 0 and may be cached. If the same condition is in must and the order of results should come only from the text match, the extra constant scores add noise.

Where filter context applies. filter and must_not clauses of bool, the filter inside constant_score, and aggregation filters. Anything in must or should is query context.

Common patterns.

  • Multi-tenant isolation: filter: term tenant_id always, built by server code, never from user input.
  • Catalogue facets: category, brand, price range, in-stock as filters.
  • Pure filtering with a fixed score: wrap in constant_score with a boost.

Pitfall. A filter that contains now without rounding changes every millisecond and cannot be cached, so round date math (now/h, now/d). And remember filter context does not rank, so if "contains the word X" should affect ordering, keep it in must or should.

Remember: if it is not about relevance, put it in filter. No scoring, and it can be cached.

How do range queries work, and what should I watch for with dates? Basic

A range query takes gt, gte, lt, lte on numbers, dates or keywords. For dates I use date math such as now-7d/d, and I usually put the range in a filter. The main trap is rounding: /d rounds to the day, so be clear whether the upper bound should be inclusive.

GET orders/_search
{ "query": { "bool": { "filter": [
    { "range": { "created": { "gte": "now-7d/d", "lt": "now/d" } } },
    { "range": { "total":   { "gte": 100, "lte": 500 } } } ] } } }

Reading it: orders created from the start of the day 7 days ago up to (not including) the start of today, with a total between 100 and 500. Things to watch: a range on a text field compares terms as strings, so "9" > "10", which is almost never what you want, so use numeric or date fields. Dates are stored as UTC milliseconds, so pass time_zone if "today" means the user's day. A filter containing now cannot be cached well since the value changes constantly, which is why rounding with /d helps caching.

Operators and what they mean. gt (greater than), gte (greater or equal), lt, lte. You can use any combination, even just one bound. For dates, a string such as "2024-05-01" works, as does a format given explicitly with "format": "dd/MM/yyyy", and so does date math.

Date math explained by example. Suppose "now" is 2024-05-15 14:32 UTC.

  • now-7d = 2024-05-08 14:32 (exact moment, 7 days back).
  • now-7d/d = 2024-05-08 00:00 (rounded down to the start of the day).
  • now/d = 2024-05-15 00:00, start of today.
  • With lte and a rounded value, ES rounds up to the end of the unit: "lte": "2024-05-15||/d" means up to 2024-05-15 23:59:59.999. With lt it rounds down. This is a famous source of off-by-one-day bugs; test the boundary.

Example "yesterday's orders". {"gte": "now-1d/d", "lt": "now/d"} gives midnight yesterday up to (not including) midnight today. This half-open interval ([from, to)) is the safest way to make daily buckets that never overlap.

Time zones. Stored dates are UTC instants. now/d rounds on UTC day boundaries unless you pass "time_zone": "+05:30" (or a name like Asia/Kolkata), in which case "today" means the user's day. The now value itself is always the current UTC instant, but time_zone does change how date math rounding such as now/d is calculated, and how date strings without an offset are read.

Other range types. A range on ip fields supports CIDR; a range on keyword compares lexicographically (so "b" is between "a" and "c", and "10" < "9"); and there are range field types (date_range, integer_range) for storing an interval in a document, like a hotel room's availability.

Performance. Numeric and date ranges are fast: they use a structure called BKD trees (points), not term lists. A range on a very selective field combined with other filters is cheap. Keep ranges in filter.

Remember: range goes in filter, use date math with rounding, never range over text fields, and mind time zones.

Why are wildcard, prefix and regexp queries slow? What do you use instead? Intermediate

The index is sorted by term, so a prefix like lap* can jump to one place and is fairly cheap. A wildcard that starts with *, like *top, or a regexp has to test every term in the field's dictionary, which gets slow and heavy on big fields. For autocomplete I use n-grams or search_as_you_type, and for "contains" search I use a proper analyzer or the wildcard field type.

{ "query": { "wildcard": { "sku": { "value": "*-2024-*" } } } }   // scans the dictionary
{ "query": { "prefix":   { "sku": "AB-" } } }                    // cheaper, still expands
{ "query": { "match":    { "name": "laptop" } } }                // best: normal term lookup

The better pattern is to change the data, not the query: index what you search for. For codes where you search parts, use an n-gram analyzer or split the code into separate fields. For genuine "contains" over log lines or ids, the wildcard field type (7.9+) is built for it. Also, never run wildcard on a big text field and never expose it directly to users, who will type *a*. The setting search.allow_expensive_queries: false blocks these query types cluster-wide.

Why a leading star is expensive, in plain terms. The dictionary of terms is sorted alphabetically, like a phone book. To find names starting with "Smi" you flip straight to S-m-i. To find names ending with "son" there is no shortcut: you must read the whole book. ES does the same: for *top it goes through every unique term in the field, tests each against the pattern, and then collects the documents for the matches. On a field with millions of unique terms (ids, URLs, free text) that is slow and uses CPU and memory.

Rewriting the problem, with examples.

  • "Contains" search on a product name: it is words, not substrings. Use a text field and match. Users searching "top" probably want "laptop"? Then index n-grams.
  • Searching SKU parts like AB-2024-77: split into fields (prefix: AB, year: 2024, number: 77), or add a pattern tokenizer that splits on dashes.
  • Suffix search (*son): index a reversed copy of the field (using a reverse token filter) and run a prefix query on it.
  • Log lines, ids and free substring search: the wildcard field type, which uses n-gram-like structures internally and is built for this purpose.

Safety. Setting search.allow_expensive_queries: false makes the cluster reject wildcard, regexp, prefix (without index_prefixes), fuzzy, script and some other queries. If users type raw text into a search box, never pass their input into wildcard or query_string unescaped: someone can send *a*b*c* on a large index and burn CPU.

Remember: leading wildcard and regexp scan the whole term dictionary. Index it the way you search (n-grams), do not wildcard it.

How do I make search tolerate typos? Intermediate

I add fuzziness to a match query. Elasticsearch then also accepts terms within a small edit distance (insert, delete, replace or swap a letter), so "runing shoos" still finds "running shoes". "fuzziness": "AUTO" is the sensible default. The cost is more terms to look up and some wrong matches, so I limit it with prefix_length.

GET products/_search
{ "query": { "match": { "name": {
    "query": "runing shoos",
    "fuzziness": "AUTO",
    "prefix_length": 1 } } } }

AUTO allows 0 edits for terms of 1 to 2 characters, 1 edit for 3 to 5, and 2 edits for longer terms (2 is the maximum). prefix_length: 1 means the first letter must be exact, which both speeds the query up and cuts silly matches, because most typos are not in the first letter. Fuzzy matches score lower than exact ones, so exact matches still rank first. For a "did you mean" hint instead of silently widening the query, use the term or phrase suggester. Fuzziness on very short terms or with an edit distance of 2 on large fields is expensive; do not turn it on blindly for every field.

What "edit distance" means. The Levenshtein distance between two words is the number of single-letter changes needed to turn one into the other. "runing" to "running": insert one n, distance 1. "shoos" to "shoes": replace one letter, distance 1. ES also counts swapping two adjacent letters as one edit (transpositions: true by default), so "shose" to "shoes" is 1.

How it is done efficiently. ES does not compare your word with every document. It builds a small automaton for the query word (all strings within distance N) and intersects it with the term dictionary, collecting the matching terms. Then it looks them up like a multi-term query. The cost depends on the length of the word, the edit distance and how many unique terms the field has.

Knobs that matter.

  • prefix_length: letters at the start that must match exactly. Setting 1 to 2 shrinks the candidate set drastically.
  • max_expansions (default 50): the maximum number of terms the fuzzy part may expand to, to limit cost.
  • fuzzy_transpositions and operator: for multi-word queries, a typo in one word of an AND query still lets that word match its corrected form.

Fuzzy versus the alternatives. Fuzzy fixes typos in the index terms. Synonyms handle different words with the same meaning. Phonetic analyzers (for example Metaphone through a plugin) handle "sounds like" names. A "did you mean" suggestion shows the corrected phrase and lets the user confirm, which gives the user control and avoids surprising results.

Pitfalls. A fuzzy match scores lower than an exact one, but it can still outrank a weak exact match from another field; check ranking with _explain. Fuzziness on short product codes or numbers produces nonsense matches, so enable it only on the natural language fields (name, description), not on ids. Use keyword fields without fuzziness for codes.

Remember: match + fuzziness AUTO + prefix_length 1. Max 2 edits; exact matches still rank higher.

Show me a query on a nested field. What do I need to remember? Intermediate

A nested field has to be queried through a nested query that names the path. Inside it, I write normal queries using the full field names. A plain match on comments.user returns nothing, because the nested objects are hidden documents. If I also want to know which nested items matched, I add inner_hits.

GET posts/_search
{ "query": { "nested": {
    "path": "comments",
    "query": { "bool": { "must": [
        { "term":  { "comments.user": "john" } },
        { "range": { "comments.stars": { "lte": 2 } } } ] } },
    "inner_hits": {} } } }

This returns posts that have a comment by john with at most 2 stars, both conditions on the same comment, and inner_hits shows which comments matched. Aggregations on nested data need a nested aggregation first, then the inner aggregation, and reverse_nested to go back up to the parent level. Another thing to remember: score mode (score_mode: avg by default) decides how the scores of several matching nested items combine into the parent's score.

Why the plain query fails. The comments are hidden documents. A query match comments.user = john is run on the parent documents, and the parent has no such field in its own index, so it returns nothing and no error. The nested query temporarily switches into the hidden documents of the given path, runs the inner query there, and joins the result back to the parents.

A worked example. Index with two posts.

post 1: comments = [ {user: john, stars: 5}, {user: amy,  stars: 1} ]
post 2: comments = [ {user: john, stars: 1} ]

The query above (user john AND stars at most 2) matches only post 2, because only post 2 has one comment that satisfies both conditions at once. Post 1 has john and has a 1-star comment, but not in the same element. With an object field it would have matched.

Useful options.

  • inner_hits returns the matching comments inside each parent hit (with their own _nested.offset), so the UI can show "john: 1 star".
  • score_mode (avg, sum, max, min, none) decides how scores of several matching children produce the parent's score. Use none in filters when you do not need a score.
  • ignore_unmapped: true avoids an error when querying several indices where some lack the nested path.

Aggregations on nested data. To get the average stars per user over comments, wrap in a nested aggregation first, then run terms and avg inside it. To go back to a parent-level field (for example count distinct posts), use reverse_nested.

"aggs": { "c": { "nested": { "path": "comments" },
    "aggs": { "by_user": { "terms": { "field": "comments.user" },
        "aggs": { "avg_stars": { "avg": { "field": "comments.stars" } } } } } } }

Pitfall. Nested queries are noticeably slower than plain ones and cannot be combined across two different nested paths in a single clause: use two nested clauses inside a bool. Keep the number of nested elements per document small.

Remember: nested field = nested query with path. Same for aggregations. inner_hits shows which children matched.

How do I add highlighting and "did you mean" to a search page? Intermediate

For highlighting I add a highlight section with the fields to mark. ES returns snippets with the matched words wrapped in tags like <em>. For "did you mean" I add a suggest section with the term or phrase suggester, which looks for similar terms in the index. Both ride along in the same search request.

GET products/_search
{ "query": { "match": { "description": "runing shoes" } },
  "highlight": {
    "pre_tags": ["<mark>"], "post_tags": ["</mark>"],
    "fields": { "description": { "fragment_size": 120, "number_of_fragments": 2 } } },
  "suggest": { "did_you_mean": {
    "text": "runing shoes",
    "phrase": { "field": "description" } } } }

The response carries hits[].highlight.description (a list of snippets) and a suggest block with corrected phrases. Highlighting works from the stored text and the query terms, so highlight the same field you query. If the page shows user text as HTML, escape it: set "encoder": "html" so stored markup is not injected into the page. The default highlighter is fine for most cases.

How highlighting works. After the query decides which documents match, the highlighter takes the text of the requested field from _source, finds the places where the query terms occur (re-analysing the text, or using stored positions or offsets), cuts out short fragments around the best places, and wraps the matched words in tags. It is a display feature: it does not affect which documents match or their rank.

Example output. Query "runing shoes" with a fuzzy match, document "Red running shoes for trail": the response has "highlight": {"description": ["Red <mark>running</mark> <mark>shoes</mark> for trail"]}. The default tag is <em>.

Options worth knowing.

  • fragment_size and number_of_fragments: snippet length and count. Use number_of_fragments: 0 to return the whole field, highlighted (good for short titles).
  • require_field_match (default true): highlight only in the field that matched. Set false to highlight the same terms in other fields.
  • highlight_query: highlight with a different query than the one used to search (useful when the main query includes filters or rescoring).
  • Highlighters: unified (default, good all-round), plain (simple, slower on big text), and fvh (needs term vectors, fast on large fields, more disk).

"Did you mean". The term suggester corrects word by word using edit distance against terms in the index, and the phrase suggester scores whole corrected phrases using n-gram language models (it understands that "noble prize" should be "nobel prize" in context). Use suggest_mode: missing to suggest only for terms that are not found, which avoids suggestions for correct words. A common UI: if the search returns few or no results, show "Did you mean ...?".

Security. Highlighted fragments contain the original text, which may include user HTML. Use "encoder": "html" so markup in stored text is escaped and only your own highlight tags are real HTML, then render the snippet as HTML in the page. Skipping this is a cross-site scripting hole.

Remember: highlight = marked snippets per hit; suggest = corrected spelling. Use the html encoder for safety.

Write the query behind a product search page: text search, filters, sort, page, highlight and facet counts. Senior

One request does it all: a bool query with the text in must and the filters in filter, a sort with a tie-breaker, from and size for the page, highlight for snippets and aggs for the facet counts. The detail that interviewers check is where each piece goes and why.

GET products/_search
{ "query": { "bool": {
    "must":   [ { "multi_match": { "query": "running shoes",
                   "fields": ["name^3", "description"], "fuzziness": "AUTO" } } ],
    "filter": [ { "term":  { "in_stock": true } },
                { "terms": { "brand": ["nike", "adidas"] } },
                { "range": { "price": { "gte": 50, "lte": 150 } } } ] } },
  "post_filter": { "term": { "color": "red" } },
  "aggs": {
    "brands": { "terms": { "field": "brand", "size": 10 } },
    "colors": { "terms": { "field": "color" } },
    "price_ranges": { "range": { "field": "price",
        "ranges": [ { "to": 50 }, { "from": 50, "to": 100 }, { "from": 100 } ] } } },
  "sort": [ { "_score": "desc" }, { "id": "asc" } ],
  "highlight": { "fields": { "name": {} } },
  "_source": ["id", "name", "price", "brand"],
  "from": 0, "size": 20 }
  • filter vs must: exact conditions in filter (no scoring, cached).
  • post_filter: the chosen colour narrows the results but not the facet counts, so the colour facet still shows all colours (explained in the facets question).
  • sort: score first, then a unique field as a tie-breaker so pages are stable.
  • _source filtering: return only the fields the page needs.

Why each part is where it is. This question tests whether you know the request has distinct slots, each with a purpose.

  1. User text goes in must as multi_match: this is the only part that needs scoring. name^3 makes title hits matter more.
  2. Hard conditions go in filter: in-stock, selected brands, price range. They narrow results, are cacheable, and do not disturb ranking. Selected brands use terms (OR within one facet), while different facets are ANDed.
  3. The currently clicked facet goes in post_filter so that its own counts stay visible (see the facets question). Only the facet being selected is handled this way; other facets' selections stay in filter or are applied inside aggregation filters.
  4. aggs produce the facet counts the left sidebar shows: top brands, colours, and price buckets. size caps buckets.
  5. sort lets the user choose: relevance (_score), price, newest. Always end with a unique tie-breaker so pagination does not repeat or skip items.
  6. from/size for pages 1 to a few; if infinite scroll or exports are needed, switch to search_after.
  7. _source filtering returns only what the cards display, reducing transfer size.
  8. highlight for snippets, suggest when the result count is low.

Details that show experience.

  • Total count: the default stops counting at 10,000; use track_total_hits only if the UI shows exact totals, or show "10,000+" and avoid the cost.
  • Build the JSON on the server from a validated model of the request. Never forward raw user JSON, because it can run expensive queries or read other tenants' data. Always add the tenant filter on the server.
  • Empty search text: use match_all in must (or omit must) so browsing by filters works, and sort by something sensible, not by a meaningless constant score.
  • Facet value count and cost: aggregations over millions of documents add latency; cache facet results for the common unfiltered page and use shorter sizes.

What I would say if asked to improve it. Add synonyms and stemming for relevance, function_score or rank_feature for popularity, a "did you mean" suggester on empty results, and a query log to learn which searches fail (zero results) so I can fix them with synonyms or better data.

Remember: text in must, exact in filter, facets in aggs, selected facet in post_filter, sort with a tie-breaker, trim _source.

(3) Look at the response size and _source size, since fetch and transfer can dominate. (4) Check shard count and whether the index has many tiny segments. (5) Check whether the node is under heap or CPU pressure (the cluster's own monitoring). (6) Only then consider hardware.

5. Relevance and scoring

How does Elasticsearch score documents? Explain BM25 in plain words. Intermediate

The default scoring is BM25. A document scores higher when the query word appears more often in it, when the word is rare across all documents, and when the document (field) is short. Frequency helps but saturates, so repeating a word 50 times is not 50 times better.

  • Term frequency (tf): more occurrences means a higher score, with diminishing returns (controlled by k1, default 1.2).
  • Inverse document frequency (idf): a rare word like "ergonomic" is a stronger signal than "the". Rarer means a higher weight.
  • Field length: one match in a 3-word title beats one match in a 3,000-word body (controlled by b, default 0.75).

The score is only meaningful for ranking within one query; do not compare scores across queries or treat them as percentages. Two practical points. Statistics are per shard, so on small data with many shards the idf can differ and ordering looks odd; dfs_query_then_fetch fixes this at extra cost, but the real cure is fewer shards. And when you sort by a field instead of _score, scores are not computed at all (unless track_scores: true), which saves work. BM25 replaced the older TF-IDF default in Elasticsearch 5.0.

Why a scoring formula at all. Matching is yes or no. But a search for "shoes" can match 50,000 documents, and users only read the first few. Scoring orders them so the most likely helpful ones come first. BM25 is a well-tested formula from information retrieval that turns three simple intuitions into one number.

The three intuitions with a small example. Query: ergonomic chair. Two documents:

  • Doc A, title: "Ergonomic chair" (2 words).
  • Doc B, description: a 300-word text that mentions "chair" five times and "ergonomic" once.
  1. Rare words count more (idf). Suppose "chair" appears in 40% of documents and "ergonomic" in 1%. A match on "ergonomic" is a far stronger clue and adds more to the score.
  2. More occurrences help, but less and less (tf saturation). The 5th mention of "chair" adds much less than the 1st. This prevents keyword stuffing from winning. The parameter k1 (default 1.2) sets how fast it saturates.
  3. Short fields beat long fields (length normalisation). One "chair" in a 2-word title says "this is about chairs". One "chair" in a 300-word text says little. The parameter b (default 0.75) controls how strongly length matters; b: 0 disables it.

Doc A wins here, as it should. The final score of a document is the sum over the query terms (and clauses), each being roughly idf x (tf x (k1+1)) / (tf + k1 x (1 - b + b x fieldLength/avgFieldLength)). You do not need to memorise it, but you should be able to say what each part does.

Practical consequences.

  • Scores are not probabilities and are not comparable between different queries or even between indices. Never show "87% match" from _score, or set a global score threshold (min_score) without testing it.
  • Statistics are per shard. Very small indices spread over many shards can produce odd rankings; use one shard, or dfs_query_then_fetch.
  • Deleted documents still count in idf statistics until segments are merged, so scores can change slightly after merges.
  • Some fields should not use length normalisation (for example a tags field, where more tags is not worse). You can disable norms ("norms": false) on fields you only filter on, which also saves disk.

Is BM25 enough? It only knows about words. It does not know that a product is popular, new, or in stock. That is why a layer of business signals (next question) usually sits on top, and why relevance tuning is a testing job, not a one-time setting.

Remember: BM25 = frequent in doc (saturating) x rare overall x short field. Scores only rank, they are not percentages.

How do I tune ranking: boosts and business signals like popularity or recency? Senior

First the cheap tools: field boosts (name^3) and should clauses that add a bonus. When text relevance alone is not enough, I wrap the query in function_score to blend in signals like popularity or freshness. I keep the signal small enough that it adjusts the order but does not drown out the text match.

GET products/_search
{ "query": { "function_score": {
    "query": { "match": { "name": "running shoes" } },
    "functions": [
      { "field_value_factor": { "field": "sales", "modifier": "log1p", "factor": 0.5, "missing": 0 } },
      { "gauss": { "created": { "origin": "now", "scale": "30d", "decay": 0.5 } } } ],
    "score_mode": "multiply", "boost_mode": "multiply" } } }

Here log1p on sales means a product with 10,000 sales is better but not 10,000 times better, and the gauss decay halves the freshness boost every 30 days. Always use a damping function (log1p, sqrt) on counts, otherwise one hugely popular item wins every query. Keep it testable: collect example queries with the expected top results, and compare the ranking before and after a change. For a simple numeric signal, the rank_feature field type is a cheaper alternative. A pinned product list is done with the pinned query.

The tools, from simplest to most powerful.

  1. Field boost (name^3): "matches in the name count more". No code, easy to reason about.
  2. A should clause with a boost: add a bonus for exact phrase, in-stock, or a promoted brand without excluding other results.
  3. function_score: multiply or add a computed number (from a field, a decay, a script or a random seed) to the text score.
  4. rank_feature field (and rank_feature query): store a positive numeric signal such as popularity or a page-rank-like value; it is cheaper than function_score because it is designed for score contributions.
  5. rescore: run an expensive query only on the top N hits of a cheap first pass.
  6. Learning to rank (a machine-learned model that reorders the top results): the advanced option when you have click data. Available as a plugin or in some Elastic subscriptions; mention it, but do not go deep unless asked.

Why damping matters, with numbers. Suppose text score for a good match is about 8, and the best-seller has 100,000 sales while a normal product has 100.

  • Raw sales as a multiplier: 8 x 100,000 vs 8 x 100. The bestseller wins every query, even irrelevant ones.
  • With log1p: log10(100,001) is about 5 and log10(101) is about 2, so the bestseller gets about 2.5 times the boost, not 1,000 times. Popular items rise, but a much better text match can still win.

Decay functions. gauss, exp and linear reduce a score as a value moves away from an origin. For freshness, origin: now, scale: 30d, decay: 0.5 means a 30-day-old item gets half the boost. For geo, origin is the user's location and scale a distance. Add an offset to give everything within, say, 3 days the full boost.

How to combine. score_mode says how several functions combine with each other (multiply, sum, max, ...) and boost_mode says how the result combines with the text score (multiply is the usual, sum or replace when you want more control). Use max_boost to cap runaway values.

Process matters more than syntax. Collect 30 to 100 real queries with the products you expect at the top. After each change, replay them and compare. Check zero-result queries and "head" queries (the 20 most frequent), because those drive business value. Resist tuning for one complaint at the cost of the rest. Use pinned (or pinned ids) for editorial promotions rather than extreme boosts.

Remember: boost fields, then function_score with damped signals (log1p, decay). Always test with a fixed query set.

6. Aggregations

What are aggregations and what kinds exist? Show a simple example. Basic

Aggregations compute summaries over the documents that match a query, like SQL GROUP BY with counts and averages. There are three families: bucket aggregations group documents (terms, date_histogram, range), metric aggregations calculate a number (avg, sum, min, max, cardinality, percentiles), and pipeline aggregations calculate on the results of other aggregations.

GET orders/_search
{ "size": 0,
  "query": { "range": { "created": { "gte": "now-30d/d" } } },
  "aggs": {
    "by_status": { "terms": { "field": "status", "size": 5 } },
    "avg_total": { "avg": { "field": "total" } },
    "customers": { "cardinality": { "field": "customer_id" } } } }

"size": 0 skips returning hits, since I only want the numbers. Roughly the SQL equivalent: SELECT status, COUNT(*) ... GROUP BY status. Things to know: terms returns the top 10 buckets by default; cardinality and percentiles are approximate (they trade a little accuracy for low memory); aggregations run on doc values (a column-style structure), so the field must be keyword, number or date, not text.

Why not just run several queries? Aggregations run in the same pass over the matching documents as the search, using doc values, so they are cheaper than one extra query per number. They also run in parallel on all shards and are merged by the coordinator, so they scale with the cluster.

The three families, with real uses.

FamilyQuestion it answersExamples
Bucket"Which group does each document belong to?"terms (by category), date_histogram (by day), range (price bands), filters, histogram, geo_distance, composite
Metric"What single number describes these documents?"avg, sum, min, max, stats, value_count, cardinality (distinct count), percentiles, top_hits
Pipeline"What can I compute from other aggregations' outputs?"derivative (change per day), cumulative_sum, moving_avg (moving_fn), bucket_sort, avg_bucket

Reading the example response. For the query above, the response looks like:

"aggregations": {
  "by_status": { "buckets": [ { "key": "PAID", "doc_count": 912 },
                              { "key": "SHIPPED", "doc_count": 450 } ] },
  "avg_total": { "value": 63.4 },
  "customers": { "value": 701 } }

Buckets carry a key and a doc_count. Metrics carry a value.

Aggregations see the query's matches. The query decides which documents are aggregated: here, the last 30 days. To also see global numbers regardless of the query, use a global aggregation, and to filter just one aggregation use a filter aggregation.

Precision notes. cardinality uses HyperLogLog++ (approximate; very accurate below the precision threshold, which defaults to 3,000 and can be raised up to 40,000). percentiles uses TDigest (accurate at the extremes, approximate in between). terms merges per-shard top lists (see the accuracy question). Sums and averages are exact.

Memory and limits. Aggregations buffer results in heap on the coordinating node. A terms aggregation on a field with millions of values and a large size can trip the circuit breaker (search.max_buckets, default 65,536 in recent versions, limits total buckets in one response). Use composite to walk through large numbers of buckets in pages.

Remember: bucket groups, metric calculates, pipeline works on results. size 0 when you only want numbers.

Write an aggregation for "monthly revenue by category, with the top product in each". Intermediate

I nest aggregations: a date_histogram by month, inside it a terms on category, inside that a sum on revenue and a top_hits for the best product. A sub-aggregation runs once for every bucket of its parent, so the results form a tree.

GET orders/_search
{ "size": 0,
  "aggs": { "per_month": {
    "date_histogram": { "field": "created", "calendar_interval": "month" },
    "aggs": { "per_category": {
      "terms": { "field": "category", "size": 5 },
      "aggs": {
        "revenue": { "sum": { "field": "total" } },
        "best":    { "top_hits": { "size": 1, "sort": [ { "total": "desc" } ],
                                    "_source": ["product"] } } } } } } } }

Use calendar_interval for month, quarter and year (they vary in length) and fixed_interval for fixed lengths like 30d or 1h; the older plain interval is deprecated. Cost multiplies with nesting: 12 months x 5 categories x top hits is fine, but a nested terms on a high-cardinality field explodes. Add "min_doc_count": 0 to a histogram to get empty months too.

How to think about nesting. Read the request from the outside in as a sentence: "for each month, for each of the top categories in that month, sum the revenue and show the single best order." The response is a tree of the same shape: months contain categories contain numbers. Each level is computed once per parent bucket, so the number of work items multiplies: 12 months x 5 categories = 60 buckets, each with a sum and a top hit.

What the response looks like (shortened).

"per_month": { "buckets": [
  { "key_as_string": "2024-01", "doc_count": 1200,
    "per_category": { "buckets": [
      { "key": "shoes", "doc_count": 400,
        "revenue": { "value": 31250.0 },
        "best": { "hits": { "hits": [ { "_source": { "product": "Trail Pro" } } ] } } },
      { "key": "jackets", "doc_count": 310, "revenue": { "value": 28100.0 }, "best": { "...": "..." } } ] } },
  { "key_as_string": "2024-02", "...": "..." } ] }

Common variations.

  • Top N categories over the whole period, then monthly detail: reverse the nesting: terms on category outside, date_histogram inside. Choose the order by which dimension you want to be limited by size.
  • Order buckets by a sub-aggregation: "terms": {"field": "category", "order": {"revenue": "desc"}} sorts categories by revenue, not by document count. (Ordering by a sub-aggregation is also what makes top-N less accurate across shards.)
  • Month-over-month growth: add a derivative pipeline aggregation on the revenue inside the histogram.
  • Time zone: "time_zone": "Asia/Kolkata" on the histogram makes month boundaries follow the user's calendar.

Limits and costs. The total bucket count is capped by search.max_buckets. top_hits is expensive when used in many buckets, because it fetches documents per bucket, so keep size small. A terms inside a terms on two high-cardinality fields (customer and product) creates millions of buckets; compute those with composite or in a batch job. Empty months are returned by default only between the first and last bucket with data in the results; set min_doc_count: 0 with extended_bounds to force a continuous axis for charts.

Remember: aggregations nest as a tree. calendar_interval for months, and mind the multiplication of bucket counts.

On a search page, selecting a filter should keep the other facet counts correct. How do I do that? Senior

Filters that sit inside the query also shrink the aggregations, which is wrong for facets where I want to still see the counts of the other options. So for the facet the user just selected, I use post_filter. It filters the hits after the aggregations were computed. For several facets at once, I use a filter aggregation per facet that applies all the other filters except its own.

GET products/_search
{ "query": { "match": { "name": "shoes" } },
  "post_filter": { "term": { "color": "red" } },
  "aggs": {
    "colors": { "terms": { "field": "color" } },
    "brands": { "filter": { "term": { "color": "red" } },
                "aggs": { "b": { "terms": { "field": "brand" } } } } } }

Reading it: the hit list shows only red shoes (post_filter). The colors facet still counts all colours of "shoes", so the user can switch colour. The brands facet counts brands among red shoes only, because it applies the colour filter itself. The cost is that post_filter runs after the aggregations, so it does not make them cheaper and can slow the search. Use it only for facet-style filters, and put all other conditions in the normal bool filter.

The problem from the user's side. The sidebar shows colour: red (40), blue (25), black (60). The user clicks "red". What should the colour facet show next? Most shops keep showing red (40), blue (25), black (60) so the user can switch or add another colour. But the product grid must show only red items.

Why a normal filter gets it wrong. If the red filter is in the bool filter of the query, then the aggregations run only on red products, so blue and black counts drop to 0 and disappear. The user can no longer see alternatives.

The mechanism. A search runs in this order: (1) query selects documents, (2) aggregations compute on those documents, (3) post_filter narrows the hit list, which is what gets sorted and paged. So post_filter changes only what appears in hits, never the aggregation input.

Multiple facets: the standard solution. Assume the user chose colour = red and brand = nike. The full rule is: each facet counts the documents matched by all other selected filters, but not its own.

FacetCounts documents that match
colourtext query + brand = nike (not colour)
brandtext query + colour = red (not brand)
price rangetext query + colour = red + brand = nike
hits (grid)text query + colour = red + brand = nike (done with post_filter holding both)

Implementation: put the text query in query, both selections in post_filter, and give each aggregation a wrapper filter aggregation containing the other facets' selections. A common shortcut: put the filters that apply to every facet (like in-stock) in the query's bool filter, and use post_filter plus per-facet filter aggregations only for the interactive facets.

Cost. Because aggregations run over the larger, unfiltered-by-facet set, it is more work than a simple filter. Keep facet sizes small (10 to 20 buckets), only compute facets that are visible, and use "size": 0 style requests for refreshing facets only. For big catalogues, some teams precompute facet counts for the empty-query page and cache them.

Remember: filter in the query narrows everything. post_filter narrows hits only, so sibling facet counts stay full.

Are terms aggregation counts exact? Senior

Not always. Each shard returns only its own top terms (shard_size), and the coordinator adds them up. A term that is popular overall but just misses each shard's cut-off can be undercounted or missing. On a single shard it is exact. The response tells me the worst-case error in doc_count_error_upper_bound.

Example: with 3 shards, a term ranked 11th on every shard is cut from all three lists, yet its total could rank in the top 10. By default shard_size is about size * 1.5 + 10, which usually makes the error negligible. If I need better accuracy, I raise shard_size (more memory and network), or I route documents so each term lives on one shard. For fully exact grouping over very many values, the composite aggregation pages through all buckets, using after_key to continue, much like search_after. Remember the other approximations too: cardinality and percentiles are estimates by design.

{ "aggs": { "top": { "terms": { "field": "brand", "size": 10, "shard_size": 100 } } } }

Why it happens, with a small example. Three shards, and you ask for the top 2 brands (size: 2, imagine shard_size: 2 for simplicity).

BrandShard 1Shard 2Shard 3True total
nike50505105
adidas45550100
puma5454595
reebok404040120

Each shard returns only its top 2. Shard 1 sends nike and adidas, shard 2 sends nike and puma, shard 3 sends adidas and puma. Reebok never makes anyone's top 2, yet it has the highest true total (120). The merged answer misses it and undercounts others. With a larger shard_size, each shard would send more candidates and the error shrinks.

What the response tells you. doc_count_error_upper_bound is the largest possible error for the whole result, and each bucket may show its own bound when show_term_doc_count_error is true. A value of 0 means exact. sum_other_doc_count says how many documents fell into buckets that were not returned.

When it is a real problem. Reports, billing and anything that must reconcile with a database total. Analytics dashboards usually tolerate small errors. The error is most visible when: many shards, high cardinality, a long tail of near-equal counts, ordering by something other than doc_count (for example by a sub-aggregation or ascending count; ascending order is not reliable at all, and is discouraged).

Options for exact results.

  1. Raise shard_size (for example to 10x of size): more memory, more network, still not perfect.
  2. Use fewer shards. One shard is exact; many deployments of moderate size can use a single shard per index.
  3. Route by the term so each value lives on one shard (custom routing on the grouping key): then each shard's count for a term is complete.
  4. Use composite aggregation to enumerate all buckets exactly, page by page. Slower and sequential, but exact for the counts of each bucket.
  5. Pre-aggregate in a batch job or a transform (a rollup index) and query the result.

In an interview, the key sentence is: "terms is a distributed top-N, so it is approximate, and I either raise shard_size or switch to composite when exactness matters."

Remember: terms aggs are per-shard top-N merged, so approximate with many shards. Raise shard_size, or use composite for exact paging.

7. Sorting and pagination

How does sorting work, and what should I watch for? Basic

I add a sort array with fields and directions. Sorting only works on fields that have doc values: keyword, numbers and dates, not analysed text. If I sort by a field, the relevance score is not used for ordering (and is not even computed unless I ask for it). I always add a unique tie-breaker, so pages are stable.

GET products/_search
{ "query": { "match": { "name": "shoes" } },
  "sort": [ { "price": "asc" },
            { "name.raw": "asc" },
            { "id": "asc" } ] }

Use "_score": "desc" as the first sort when relevance should lead, then break ties by a unique field. Without a tie-breaker, documents with equal values may switch order between requests, so a user paging through can see duplicates or miss items. Sorting by an analysed string fails with a fielddata error; use the keyword sub-field. Missing values can be controlled with "missing": "_last". Sorting on a field with doc values is cheap, since doc values are a column-style structure read straight from disk and the file cache.

How a sort runs. For each matching document the shard reads the sort field from doc values (a column on disk, via the file cache), keeps a priority queue of the best from + size entries, and returns their sort values with the ids. The coordinator merges these. Because it uses doc values, sorting is only available for fields that have them: keyword, numbers, dates, booleans, ip. Analysed text has none, so Elasticsearch raises an error about fielddata.

Examples of sort options.

  • Multiple keys: the second key breaks ties of the first. [{"price": "asc"}, {"_score": "desc"}, {"id": "asc"}].
  • Missing values: {"price": {"order": "asc", "missing": "_last"}} puts documents without a price at the end.
  • Multi-valued fields (an array of prices): choose "mode": "min" or "max", avg, sum for which value to sort by.
  • Sorting by a nested field needs a nested section naming the path and optional filter.
  • Sort by distance: _geo_distance. Sort by a script: possible but slow; precompute the value instead.

Why a unique tie-breaker is essential. Imagine 30 products with the same price 49 and pages of 10. Without a further key, the order among equal values can differ from one request to the next (it depends on which shard copy answered and on segment internals). Page 1 could show products 1 to 10 and page 2 could repeat some of them and skip others. Adding a unique field (id, or a numeric sequence) makes the order total and stable. The tie-breaker must be a field with doc values and a unique value per document.

Do not sort by _id. The _id field has no doc values by default (sorting on it would load fielddata, which is discouraged and disabled by default in recent versions). Copy it into a keyword field instead. If you use PIT, ES provides an implicit tie-breaker called _shard_doc.

Relevance versus field sort. When sorted by a field, _score is null in the hits unless you set track_scores: true. If your product needs "sort by price but only among relevant documents", filter by relevance first (a min_score or a stricter query) rather than hoping the order will reflect it. Sort cost grows with the number of matching documents, so narrow the match set with filters first.

Remember: sort on keyword, number or date only. Add a unique tie-breaker. Sorting by field skips scoring.

How does from/size pagination work and what is the 10,000 limit? Basic

With from and size, ES has to collect and sort from + size hits on every shard, then the coordinator merges them and throws away the first from. That cost grows with depth, so index.max_result_window defaults to 10,000 and a request beyond it fails. For deep paging I use search_after, not a bigger window.

Example: page 1,000 of 20 per page means from: 19980. With 5 shards, every shard builds a sorted list of 20,000 entries and the coordinator merges 100,000. That is the deep paging problem; it is slow and memory-hungry, and raising the limit only moves the problem. Separately, the hit count is capped too: hits.total reports at most 10,000 with "relation": "gte" (since 7.0) because exact counting is costly. If I truly need the exact total I set "track_total_hits": true; if I only need "more than 10,000", the default is faster.

GET products/_search
{ "from": 19980, "size": 20, "query": { "match_all": {} } }
-- error: Result window is too large, from + size must be less than or equal to 10000

The numbers behind the limit. Each shard must produce a sorted list of its top from + size hits, because any of them might end up on the requested page after merging. With from: 9990, size: 10 and 5 shards, every shard keeps and sorts 10,000 entries and the coordinator merges 50,000 of them just to return 10. Memory and CPU grow linearly with depth, multiplied by the number of shards, and concurrent users multiply it again. The 10,000 default is a safety fuse. Raising index.max_result_window to 1,000,000 removes the fuse, not the danger: one crawler can then take down a node.

What the real fixes look like.

  • UI list: keep from/size for the first pages (people rarely pass page 10), and give more filters and a better sort.
  • Infinite scroll or "next page" API: search_after with a unique sort.
  • Export or batch job: PIT plus search_after in a loop (or scroll in older code).
  • "Jump to page 50": reconsider the requirement; if unavoidable, approximate it by sorting on a stable field and using a range filter as a cursor.

About the total hit count. hits.total looks like {"value": 10000, "relation": "gte"}: "at least 10,000". ES stops counting once it knows the result is above the threshold, which lets it skip documents (it can even avoid scoring them when the sort allows). Options: "track_total_hits": true counts exactly (can be slow on large result sets), or a number like 20000 counts up to that. A UI showing "about 10,000+ results" avoids the cost and is usually fine. For exact counts, use the _count API with the same query.

Pitfalls. With from/size and concurrent indexing, an item added between page 1 and page 2 shifts everything by one, so the user sees a duplicate or skips one. That is acceptable for browsing but not for exports. Also, ordering by _score alone with from/size has the tie problem described in the sorting question.

Remember: from + size cost grows with depth, so the 10,000 cap. Deep paging means search_after. The total count is capped at 10,000 unless track_total_hits is true.

What is search_after, and how does it differ from from/size and scroll? Intermediate

search_after is cursor-style paging: I send the sort values of the last hit from the previous page, and ES returns the next hits after that point. No skipping, so every page costs the same. It needs a deterministic sort with a unique tie-breaker. To keep a consistent view while paging I pair it with a point in time (PIT), and for a full export it is the modern replacement for scroll.

POST products/_pit?keep_alive=1m            -- returns { "id": "..." }

GET _search
{ "size": 100,
  "query": { "match_all": {} },
  "pit": { "id": "46ToAwMD...", "keep_alive": "1m" },
  "sort": [ { "created": "asc" }, { "id": "asc" } ] }

-- next page: add the sort values of the last hit
  "search_after": [ 1731800000000, "p-981" ]
  • PIT (7.10+) freezes the view of the index so new writes do not shuffle pages. Without it, documents added or deleted between requests can cause duplicates or misses. Close it when done (DELETE _pit).
  • Scroll does a similar snapshot job with a server-side context, and still works, but Elastic recommends PIT with search_after for deep paging and exports.
  • UI "jump to page N" is not possible; infinite scroll and "next" buttons are.

The idea in one picture. Imagine the result list sorted by (created, id). Page 1 ends with the item (1731800000000, "p-981"). Instead of saying "skip 20 items" (from/size), you say "give me the next items that sort after (1731800000000, p-981)". Each shard can use its sorted index structures to start right after that point and take only size items. The cost per page is constant (page 1 equals page 5,000).

The loop in an export job.

  1. Open a PIT: POST products/_pit?keep_alive=1m. Save the returned id.
  2. Search with pit.id, a stable sort, size 1,000 and no search_after.
  3. Process the hits. Take the sort array of the last hit.
  4. Search again with search_after = that array (use the pit.id returned by the previous response, as it can change).
  5. Stop when a page returns fewer than size hits. Close the PIT.

Why PIT is there. Without it, each request sees the index as it is at that instant. Between two requests a refresh may add, update or remove documents, so pages can have duplicates or gaps. A PIT keeps the segments as they were, so every page is consistent with the first. It is lightweight compared with scroll because it does not copy state per search, but it still holds old segments, so keep keep_alive short and renew it with each request. When using PIT, Elasticsearch adds a hidden tie-breaker (_shard_doc) to the sort, so exports without a natural unique field still work; for user-facing paging I still prefer an explicit unique field.

Pitfalls. The sort values must be passed back exactly (including types: dates as milliseconds, strings as they are). Previous-page navigation requires you to keep your own history of cursors or to reverse the sort.

Is scroll still used? What are its drawbacks? Intermediate

Scroll still works and is common in older code for exporting or reindexing everything: the first call opens a snapshot and returns a scroll_id, and I keep calling with that id for the next batches. Its drawbacks are that it holds resources on the server until it expires, it is not meant for user-facing paging, and the recommended replacement is now PIT with search_after.

POST products/_search?scroll=1m
{ "size": 1000, "query": { "match_all": {} } }

POST _search/scroll
{ "scroll": "1m", "scroll_id": "DXF1ZXJ5..." }

DELETE _search/scroll   { "scroll_id": "DXF1ZXJ5..." }

The scroll keeps old segments alive while open (so merges cannot reclaim disk space) and counts against a limit of open contexts (500 by default). Always set a short keep-alive (renewed on each call) and clear the scroll when done. For parallel exports, sliced scroll splits the work into independent slices. Scroll results are a snapshot, so they do not show later writes, which is fine for exports.

How scroll works. The first request with ?scroll=1m creates a search context that pins a snapshot of the index and returns the first batch and a _scroll_id. Each following request sends the id and gets the next batch. With every call you give a new scroll time (the keep-alive), which is the time to keep the context alive until the next call, not for the whole export. When done, delete the context with DELETE _search/scroll instead of waiting for expiry.

What it costs the server. While the context is open, the segments it needs cannot be deleted after merges, so heavy updating and merging while many scrolls are open increases disk usage. Each open context uses memory and file handles. There is a limit on open scroll contexts (search.max_open_scroll_context, 500 by default), and exceeding it gives an error. Each shard keeps its own context.

Typical correct usage.

1. POST products/_search?scroll=2m   { "size": 1000, "sort": ["_doc"] }
2. loop: POST _search/scroll { "scroll": "2m", "scroll_id": "..." }
3. until hits is empty
4. DELETE _search/scroll { "scroll_id": "..." }

Sorting by _doc (index order) is the cheapest order for a scroll and is what _reindex uses internally. Use slice to split one scroll into N parallel independent ones: "slice": {"id": 0, "max": 4} for the first of four workers.

Scroll versus PIT in one sentence. Scroll is a stateful cursor that must be advanced in order and cannot be resumed after you lose the id. PIT with search_after lets you retry a failed page, change the page size between calls and is the lighter, recommended approach.

When I still use scroll. Existing code or tools that depend on it (older client libraries, _reindex, _update_by_query and _delete_by_query use scroll or PIT internally), one-off scripts on an old cluster version before 7.10, and exports where order does not matter. Never use it for user-facing pagination, because every user session would hold a server context.

Remember: scroll = snapshot cursor for bulk export; heavy on the server. Prefer PIT + search_after for new code.

8. Indexing, updates and keeping data in sync

What happens when I index a document? Explain translog, refresh, flush and segments. Senior

The coordinator hashes the id and sends the write to the right primary shard. The primary analyses the document, adds it to an in-memory buffer and appends it to the translog (a write-ahead log on disk, fsynced per request by default), then forwards it to the replicas and acknowledges once they have it. A refresh later turns the buffer into a searchable segment, and a flush commits segments to disk and trims the translog.

Why this design: segments are immutable files, so Elasticsearch never edits an index in place. A write must still survive a crash before it is flushed, so the translog records it first; after a crash, ES replays the translog. The immutability has a cost for updates and deletes: a delete only marks the old copy as deleted, and an update is a delete plus a full re-index of the document. Background merges combine small segments and finally drop the deleted copies. So an update-heavy workload creates garbage and merge work.

Step by step, for PUT products/_doc/7.

  1. The coordinating node computes hash(7) % number_of_primaries and forwards the request to the node holding that primary.
  2. The primary validates the document against the mapping, analyses the text fields, and adds the document to the in-memory indexing buffer.
  3. It also appends the operation to the translog (a sequential file on disk). By default the translog is fsynced before the request is acknowledged (index.translog.durability: request), so an acknowledged write survives a crash of the process or machine.
  4. The primary sends the same operation, with a sequence number, to each in-sync replica in parallel. Each replica does steps 2 and 3 itself.
  5. When all in-sync replicas confirm, the primary acknowledges success to the client.
  6. Refresh (every second by default): the buffer is written out as a new immutable segment and searchers are reopened. Now the document is searchable. This segment may still live in the file system cache and is not yet fsynced.
  7. Flush (when the translog gets large, or at intervals): Lucene commits, meaning all segments are fsynced to disk, a commit point is written and old translog files are removed. After a crash, ES loads the last commit and replays the translog operations after it.

Why the translog is needed. Refresh does not fsync (fsyncing every second is costly), and a full Lucene commit is heavy. The translog gives cheap durability: appending to a sequential log is fast, and on restart it fills the gap between the last commit and the crash. It is the same idea as a database write-ahead log.

Segments and merges. Segments are write-once files. Deletes are recorded in a small "deleted" bitmap, and updates are "mark old as deleted, add new". A background merge process combines small segments into larger ones, physically dropping deleted documents. Merging uses I/O and CPU, which is why heavy bulk indexing or heavy updating makes the cluster work harder in the background. Searching many small segments is slower than searching a few large ones, so merges also help query speed.

How does the bulk API work, and how do I use it well? Intermediate

Bulk sends many index, update and delete actions in one request, as lines of newline-delimited JSON (an action line, then a source line). It is much faster than one request per document. The key detail is that the response is HTTP 200 even when some items fail, so I must read the per-item results and retry the failed ones.

POST _bulk
{ "index":  { "_index": "products", "_id": "1" } }
{ "name": "Red running shoes", "price": 79 }
{ "update": { "_index": "products", "_id": "2" } }
{ "doc": { "price": 59 } }
{ "delete": { "_index": "products", "_id": "3" } }
  • Batch size: aim for roughly 5 to 15 MB per request and tune by measurement; huge batches stress memory and heap.
  • Check the response: if "errors": true, look at each item's status. A 429 (es_rejected_execution) means the cluster is overloaded: retry only those items, with exponential backoff, and slow the producer.
  • Bulk load tip: set refresh_interval to 30s or -1 and replicas to 0 during a huge initial load, then restore. In Java use the client's bulk helper (BulkIngester or BulkProcessor) which batches, retries and limits concurrency.
  • Use stable ids so retries are idempotent (a retried index with the same id overwrites, not duplicates).

Why bulk is faster, with an example. Indexing 1 million documents one by one means 1 million HTTP round trips, each paying network latency (say 1 ms) and request parsing, which is at least 1,000 seconds of pure overhead. With bulk requests of 5,000 documents, there are 200 round trips. The shard also processes the batch together, which makes better use of its internal buffers.

The format. The body is newline-delimited JSON with a final newline: an action line (index, create, update, delete) and, except for delete, a source line. It is not a JSON array, because that format lets the server read it line by line without parsing a whole giant document. The content type is application/x-ndjson.

The response, and why 200 is misleading. The overall request is "accepted", and each item succeeds or fails on its own:

{ "took": 38, "errors": true, "items": [
  { "index":  { "_id": "1", "status": 201, "result": "created" } },
  { "update": { "_id": "2", "status": 404, "error": { "type": "document_missing_exception" } } },
  { "index":  { "_id": "9", "status": 429, "error": { "type": "es_rejected_execution_exception" } } } ] }

Item statuses mean different things. 429 and some 503: temporary, retry that item. 400 (mapping conflict, bad data): permanent, retrying will not help; send it to a dead-letter store and log it. 409: version conflict, usually fine if you used external versions, because it means a newer copy is already there. 404 on update: the document does not exist (use an upsert).

Retry loop. Collect only the retryable failed items, wait (exponential backoff with jitter, for example 200 ms, 400 ms, 800 ms), and resend; give up after a limit and dead-letter. Because ids are stable, resending is idempotent.

Sizing. The right batch size depends on document size, mapping and hardware. Start around 1,000 to 5,000 small documents or 5 to 15 MB and increase until throughput stops improving, then back off. Use a few concurrent workers (for example 2 to 4 per data node) instead of one giant request. A request that is too big wastes heap on the coordinating node, and ES has an HTTP size limit (100 MB by default).

Other levers for a big load. Disable or slow refresh, set replicas to 0 and restore it at the end, let ES generate ids if you do not need your own (it skips the check for existing ids and is faster), and use a client helper (BulkProcessor or BulkIngester in Java) that handles batching, concurrency and retries together.

Remember: bulk = fewer round trips. 200 does not mean success: check per-item status, retry 429 with backoff, use stable ids.

How do updates work, and how do I avoid lost updates from concurrent writers? Senior

A partial update reads the stored _source, merges my change and re-indexes the whole document, so there is no cheap in-place field update. To avoid two writers overwriting each other, I use optimistic concurrency control: read the document's _seq_no and _primary_term, send them back as if_seq_no and if_primary_term, and on a 409 version_conflict I re-read and retry.

GET products/_doc/1                      -- returns _seq_no: 12, _primary_term: 1

PUT products/_doc/1?if_seq_no=12&if_primary_term=1
{ "name": "Red running shoes", "stock": 4 }
-- 409 if someone else changed it meanwhile

POST products/_update/1?retry_on_conflict=3
{ "doc": { "price": 59 } }
-- partial update: ES retries by itself

POST products/_update_by_query
{ "query": { "term": { "brand": "acme" } },
  "script": { "source": "ctx._source.brand = 'ACME'" } }

Use if_seq_no when a read-modify-write in my app must not clobber another change. Use retry_on_conflict for simple partial updates that commute. For data coming from a database, the best approach is external versioning: version_type=external with the row's version, so an old event arriving late is rejected and never overwrites newer data. _update_by_query is a batch operation (it snapshots, then updates each match), not a transaction.

What happens inside an update. The Update API reads the current _source from the shard, applies your partial document or script, and indexes the result as a new document version, marking the old one as deleted. So a one-field change rewrites everything. For a document with large text, the cost is the size of the document, not the size of your change. That is why you avoid frequently updating counters or timestamps on big documents; keep volatile data in another index or in the database.

The lost-update problem with a timeline.

  1. Worker A reads product 1: stock 5.
  2. Worker B reads product 1: stock 5.
  3. A writes stock 4. B writes stock 4 (it also thought 5 minus 1). One sale is lost; the true stock should be 3.

The fix with optimistic concurrency. Every document operation gets a sequence number (_seq_no) and the shard has a _primary_term (which increases when a new primary is elected). You read the pair and write with if_seq_no and if_primary_term. If anything changed in between, ES answers 409 Conflict and writes nothing, and your code re-reads and retries. The pair together matters because after a failover the sequence numbers can restart on a new primary term.

Still, if you need strict stock control, the database should own the number, because Elasticsearch gives no multi-document transactions and the 1 s refresh delay means search shows slightly old values.

Upsert and bulk updates. doc_as_upsert: true (or an upsert block) creates the document if missing. _update_by_query and _delete_by_query work on a snapshot of the matching documents and update them in batches with version checks; if documents change during the run you get conflicts, which you can ignore with conflicts=proceed or retry. They are throttled and run as tasks (wait_for_completion=false), because a run over millions of documents takes a long time.

Remember: update = re-index whole doc. Use if_seq_no/if_primary_term to detect conflicts, retry_on_conflict for easy cases, external versions for DB-fed data.

Why is writing to the database and Elasticsearch in the same request a problem? Senior

Because there is no transaction across the two. If the database commit succeeds and the Elasticsearch call fails (or the app crashes between them), search is now missing data, and the opposite can also happen. Retries can apply old data after newer data. So I do not write to both in one request: I write to the database only and update Elasticsearch from there, asynchronously and with retries.

There are also timing problems: ES is near real time, so a user who saves and instantly searches may not see their change, and two concurrent requests can write to the two systems in opposite orders, leaving them different. The fix for all of it is a single source of truth (the database) and one-way, ordered, replayable data flow into ES (the next question).

The failure cases, concretely. Code: repo.save(order); esClient.index(order); inside one service call.

  • ES call fails after the DB commit (timeout, 429, node restart): the order exists but is invisible in search. If you roll back the DB instead, the user sees an error for something that mostly worked and a retry may duplicate side effects.
  • App crashes between the two calls: same result and no error is logged anywhere.
  • DB commit fails after the ES call: search shows an order that does not exist (a phantom).
  • Ordering race: request 1 updates the price to 10, request 2 updates it to 12. In the DB, 2 is the last. In ES, request 1's index call is delayed and arrives last, so the index says 10. The two stores disagree, and nothing ever corrects it.
  • Latency and availability: your write path is now only as available as the slower of two systems, and every save pays for both.

Why "try/catch and retry" does not fix it. You can retry the ES call, but the process can die during the retry, and a retry with older data can overwrite a newer update that reached ES first. Two-phase commit across a database and Elasticsearch is not supported. So the correct design removes the second write from the request path.

What to do instead. One system is the writer of record (the database). Everything else follows from its committed changes: either by reading its log (CDC) or an outbox table written in the same transaction. The indexer processes events in order per entity, uses the entity's version for idempotent writes, and retries safely. The cost is a few seconds of lag, which is acceptable for search, and you tell the UI to read the user's own just-saved data from the database.

When a simple dual write is "okay". A small internal tool where drift is tolerable and a full reindex runs nightly. Say that out loud: it shows judgement, not dogma. For anything customer-facing, say outbox or CDC.

Remember: no transaction across DB and ES. Write to the DB, feed ES from the DB.

What are the reliable ways to keep Elasticsearch in sync with a database? Senior

Two solid patterns. The transactional outbox: in the same database transaction as the business change, I insert an event row into an outbox table, and a separate process publishes it to a queue (for example Kafka) and a consumer indexes it. Or change data capture (CDC) such as Debezium, which reads the database log and streams changes without changing the app. Both are at-least-once, so the indexer must be idempotent.

  • Idempotent indexing: index by the entity id and use an external version (row version or updated timestamp), so duplicates and out-of-order events are harmless.
  • Deletes: propagate deletes as events, not only inserts and updates, or removed items keep showing in search.
  • Repair: keep a way to rebuild fully: reindex from the database into a fresh index and switch an alias, and run a periodic count or checksum comparison to detect drift.
  • Simple option: a polling job with an updated_at watermark works for small systems but misses hard deletes.

Outbox in detail. In one database transaction, the service writes the business row and inserts an event row into an outbox table (id, aggregate_id, type, payload, version, created_at). Either both commit or neither does. A relay process then reads unsent rows (by polling, or through the database log) and publishes them to a broker such as Kafka, then marks them sent (or deletes them). If the relay crashes after publishing but before marking, it republishes: that is the at-least-once behaviour.

CDC in detail. A tool such as Debezium reads the database's transaction log (the binlog in MySQL, the WAL in PostgreSQL), turns each committed row change into an event and publishes it. No application change is needed and no triggers are used, but the consumer gets table-shaped events, not business events, and schema changes must be handled. A common hybrid: Debezium reads the outbox table, which gives a clean event contract and reliable delivery.

The idempotent indexer. Events can arrive twice or out of order. The indexer turns each event into a full-document index (or delete) for entity id E, with version_type=external and the entity's version (or the event's source timestamp or log position). If an older event arrives after a newer one, ES rejects it with 409, and the indexer treats 409 as "already up to date" and moves on. Partition the Kafka topic by entity id so events for the same entity are processed in order by one consumer.

Index the data the search needs. If the search document is built from several tables (order plus customer plus items), the indexer should load the current state from the database when it handles the event (an event says "order 5 changed", then it reads the order aggregate and indexes it), rather than trusting stale event payloads. When the related customer changes, you also need an event that re-indexes the affected orders.

Operations. Monitor consumer lag and the dead-letter queue, run a periodic reconciliation (count and checksum per id range, or compare max version), and keep a full-rebuild path: create a new index, bulk-load from the database, replay events from a saved position, flip the alias.

Remember: outbox or CDC, then an idempotent indexer with external versions. Handle deletes and keep a rebuild path.

9. Real-life scenarios

A search that used to take 50 ms now takes 4 seconds. How do you find out why? Senior

I find the exact slow query first, then use profile to see which clause is slow, and compare with what changed: the query, the data volume, or the load. In my experience the usual causes are a leading wildcard or regexp, deep from values, a large size, an aggregation on a high-cardinality field, a script, or a filter placed in must.

Situation: one endpoint got slow; other searches are fine.

Check first:

  • Is it slow for every request or only some inputs? Pull the slow log (index.search.slowlog.threshold.query.warn: 2s) and the response field took, to separate ES time from my app and network time.
  • Run the same body with "profile": true and look for the clause with the biggest time_in_nanos.
  • Look for: wildcard with a leading *, from in the thousands, size of 1,000+, terms aggregation on an id-like field, script queries, huge _source responses, many shards on the index.

Fix: move exact conditions into filter; replace wildcard with n-grams or search_as_you_type; use search_after instead of deep from; return only needed fields (_source filtering); cap aggregation sizes; precompute script values at index time.

Prevent: keep the slow log on, load-test new queries on production-size data, and review any new query shape before release.

Triage order. Work from cheapest evidence to most expensive, and change one thing at a time.

  1. Is it really Elasticsearch? Compare the response field took (time inside ES) with the time your app measured. A big gap means the network, serialisation of a huge response, or the client library.
  2. What changed? A release with a new query shape, a data volume jump (the index doubled), a new aggregation, a traffic spike, or a cluster event (a node restarted, many shards relocating, a merge storm, heap pressure and long garbage collection).
  3. Which part? Run the slow query with "profile": true. If the time is in one WildcardQuery or a script, you have the cause. If time is spread across fetch, check the size of _source and number of hits. If aggregations dominate, look at the cardinality of the grouped field.
  4. Cluster side: if all queries are slower, check the hot threads (GET _nodes/hot_threads), search thread-pool queue and rejections (GET _cat/thread_pool/search?v), JVM heap and GC, disk I/O, and the shard count per node.

Example diagnosis. The product list endpoint got slow after "search by SKU contains" was added as wildcard: "*abc*" on a keyword field with 80 million unique values. Profile shows 3.8 s inside the wildcard query. The fix: index SKU n-grams (or the wildcard field type) and query a term; response drops to 40 ms.

Users save an item and immediately search, but it is not in the results. What is happening? Intermediate

Almost certainly the refresh delay: the document is stored but becomes searchable only after the next refresh, about a second later. If the app also writes via a queue or CDC pipeline, there is extra lag on top. I fix it for the user path with refresh=wait_for or by reading their own data from the database, not by forcing a refresh on every write.

Situation: create item, redirect to a list page backed by search, item is missing, appears on reload.

Check first: does GET index/_doc/id return it (yes means the write worked)? Does the item appear after a second? Is the write synchronous at all, or does it go through a queue? Compare the pipeline lag.

Fix:

PUT products/_doc/1?refresh=wait_for     -- returns when the next refresh made it visible
-- or: show the just-created item from the DB response, not from search

Avoid refresh=true on each write: it creates a tiny segment every time, floods merges and hurts throughput. For a write path that goes through a queue, tell the UI that the list updates shortly, or merge the new item into the displayed list locally.

Prevent: decide per screen whether it needs read-your-writes. Most search pages do not, and only edit screens do.

Why this scenario is a classic. The write path (database, queue, indexer, Elasticsearch) is asynchronous, and the page after the redirect reads from the search index. The user's save and the user's read use different systems at different times. Every extra hop adds lag: queue wait, indexer processing, bulk batching delay, and the 1-second refresh.

Options, with trade-offs.

  • Show the user's own change from the primary data. After the save, render the new item from the save response and merge it into the list (optimistic UI). Cheapest and always right.
  • Direct synchronous index for that one write with refresh=wait_for: the save returns after the document is searchable. Costs latency (up to the refresh interval) and re-introduces a dual write for this path, so use only if the rest of the pipeline can still repair failures.
  • Short polling or a "processing" state: the UI shows the item as pending and refreshes in a moment.
  • Sticky read: for a few seconds after a write by this user, route their list request to the database instead of search.

How to prove the cause. Take the id and call GET products/_doc/ID: found means indexing worked and the delay is refresh or pipeline lag. Not found for many seconds means the pipeline is behind or the event failed (look at consumer lag and the dead-letter queue). Compare _cat/indices doc counts with the source if you suspect lost events. Also check the index's refresh_interval; if someone set it to -1 or 30 s for a bulk load and forgot to restore it, you have found the real bug.

Not a fix: setting refresh_interval to 100 ms or refresh=true on every write. It creates a flood of tiny segments, slows searches, and does not fix pipeline lag at all.

Remember: write is instant for get-by-id, visible to search after refresh. Use wait_for sparingly, never refresh=true in a loop.

Indexing fails with "Limit of total fields [1000] has been exceeded". What happened and how do you fix it? Senior

Dynamic mapping created too many fields, because some document key is used as a field name (user ids, dates, attribute names). Raising the limit hides the problem and makes the cluster state heavy. The fix is to change the data shape: store such data as a list of key/value items, or map it as flattened, and make the mapping explicit.

Situation: new documents are rejected; the field count keeps rising.

Check first: GET index/_mapping and see which object has hundreds of children, for example attributes.color_red, attributes.size_xl, or metrics.2024-05-01.

Fix:

-- bad: keys are data
{ "attrs": { "color": "red", "size": "xl", "u12345": "x" } }

-- better: fixed field names, data in values
{ "attrs": [ { "k": "color", "v": "red" }, { "k": "size", "v": "xl" } ] }

-- or one field that holds arbitrary keys without mapping each of them
"attrs": { "type": "flattened" }

Use a nested type for the key/value list if you must query key and value together. Raise index.mapping.total_fields.limit only as a temporary relief. The index must be rebuilt (reindex) with the fixed mapping.

Prevent: "dynamic": "strict" in production mappings, and a review of every new field.

Why a field count limit exists. Every field is stored in the mapping, which is part of the cluster state sent to all nodes and held in memory. Thousands of fields make cluster state updates slow, bloat heap, and make searches (especially * field patterns and query_string over all fields) expensive. The default limit of 1,000 (index.mapping.total_fields.limit) is a guard rail, and it is almost always a symptom of a modelling mistake.

How it happens, with a typical example. A service stores user attributes as a JSON map {"attrs": {"color_pref": "red", "plan_2024_q1": "gold", "u12345_flag": true}}. Each new key becomes a new field. After enough tenants and months, there are tens of thousands of distinct keys.

You must change a field from text to keyword and add a new analyzer on a live index with 200 million documents. How do you do it without downtime? Senior

Create a new index with the new mapping, copy data into it with _reindex (while the app keeps using the old index through an alias), catch up on the changes made during the copy, then flip the alias atomically. Keep the old index for a while for rollback.

Situation: mapping cannot be edited in place; users keep searching and writing meanwhile.

Steps:

  1. App already uses aliases: products_read and products_write pointing at products_v1. If it does not, introducing aliases first is step zero.
  2. Create products_v2 with the new mapping and analyzer; set refresh_interval: -1 and replicas 0 for speed.
  3. Start _reindex as a background task (wait_for_completion=false), in slices for parallelism, throttled with requests_per_second.
  4. Make new writes go to both indices (dual-write to v1 and v2) or replay changes from the queue or DB after the copy, using external versions so older data never overwrites newer.
  5. Restore replicas and refresh, compare counts and spot-check queries, then flip the alias in one call.

Prevent: always code against aliases and keep a rebuild path from the source of truth.

The hard part is not the copy, it is the writes during the copy. A 200-million-document reindex can take hours. While it runs, the product team still edits products, and new products come in. If you copy a snapshot and flip the alias, everything written in those hours is missing from the new index. So the plan needs a way to capture changes.

Why version_type: external in the reindex. A document copied from v1 may be older than a document that the live indexer already wrote to v2 for the same id. With external versions (the document's version or updated_at as a number), the copy gets a 409 conflict for the stale one and does not overwrite the newer one. After the flip. Keep v1 read-only for a day or so. Delete when happy. If you changed analysis (a text field to keyword), also update the application queries (for example match to term) in the same release, ideally behind a feature flag that follows the alias flip.

Remember: new index, reindex in background, catch up on writes, atomic alias flip, keep the old index for rollback.

Users complain that "iphone case" returns phones before cases, and "cases" returns nothing. What do you check and change? Senior

Two separate problems. "Cases returns nothing" is an analysis problem: the field has no stemming or plural handling, so cases does not match case. I fix them with a better analyzer, a title boost and requiring all words.

Check first: run _analyze on the field with "cases" to see the stored terms; run _explain on a phone and a case document for the same query to see where the score comes from.

Fix:

Split the complaint into two different bugs. People often treat "search is bad" as one problem. Here there are two distinct causes and two kinds of fix.

Bug 1: "cases" returns nothing (recall problem). Use POST products/_analyze with the field and text "cases". With the standard analyzer the output is cases, but the document contains case. The terms differ, so there is no match. Fix with a stemmer or lemmatiser in the analyzer, so both become case (this also helps "cover", if you add a synonym case, cover carefully). Remember to reindex, since changing an analyzer needs new index data.

Bug 2: "iphone case" shows phones first (precision and ranking problem). Default match uses OR: a document matching only "iphone" (a phone) is a valid hit, and "iphone" is a rarer word than "case" so it carries a high idf weight. Phones, whose titles are short and contain "iphone", outscore cases whose titles are longer. Three changes help:

  1. Require both words (operator: and or minimum_should_match: 75%), so a plain phone no longer qualifies.
  2. Reward the phrase in a should (match_phrase), which lifts "iPhone 15 case" items above scattered matches.
  3. Use category signal: boost category matches, or classify the query ("case" is an accessory word) and add a filter or boost on category = Accessories. The best mature solutions detect product type from the query and use it as a strong signal.

How to verify without guessing. Run _explain for the top phone and the top case for the query and compare their score trees: you will see the idf and field length numbers. After changes, replay a fixed list of 50 to 100 queries and compare top-5 before and after. Track a metric such as the share of queries with a click in the top 3, and zero-result rate.

Cautions. Aggressive stemming can create false matches ("organization" and "organ"); test with real vocabulary. Stop words and synonyms should be curated (a synonym file under version control, with reload or reindex procedure). Do not tune boosts to fix one query: add it to the test list and look at the whole set.

Remember: no match = analysis, wrong order = scoring. Stemmer + AND + phrase bonus + field boosts, then test with real queries.

An export screen asks for page 2,000 and the API fails with "Result window is too large". What do you do? Intermediate

The request has from + size above 10,000. I do not raise max_result_window, because deep paging makes every shard build huge sorted lists. For a UI I switch to search_after (next and previous only), and for a real export I stream with PIT plus search_after (or scroll on older versions).

Check first: who really needs page 2,000? Usually it is an export or a crawler, not a person. Users rarely go past page 5, so better filtering and sorting fix the real need.

Prevent: cap the page number in the API, and give users filters and sorting instead of deep paging.

Understand who is calling. A request for page 2,000 is almost never a human. Typical sources: a nightly export or sync job written with a page loop, a web crawler or API client scraping all results, or a front end that lets the user type a page number. Ask who it is before choosing the fix, because the right answer differs.

Why raising max_result_window is wrong. You would allow a request that makes each shard collect and sort 100,000 or a million entries. One client doing this a few times concurrently can exhaust heap and trigger circuit breaker errors for everyone. The limit is protection, so an API should return a clear 400 for too-deep pages instead of passing the problem to ES.

Design of the cursor. The cursor given to the client is an opaque, signed or encoded string that contains the last hit's sort values (and, if you use PIT, the PIT id and its expiry). Clients cannot jump, but "next" is cheap. If the PIT expires, restart from the stored sort values with a fresh PIT, accepting that you may see small inconsistencies.

Export design. A background job writes pages of 1,000 to 5,000 to a file (CSV or Parquet) or a queue, reports progress, and stores a file link for download. HTTP requests are not held open for minutes. If the export is huge and has no query (everything), consider reading from the database or the data lake instead, since the search engine is not the best source for full dumps.

Verification. Test with a data set larger than 10,000 documents, and with concurrent writes while the export runs, checking count equality and no duplicate ids in the output.

Remember: never raise max_result_window as a fix. UI = search_after, export = PIT + search_after in a background job.

A nightly bulk load now fails with many 429 errors and some documents are missing. How do you fix it? Intermediate

429 means the write queue on the cluster is full: I am sending faster than it can index. The missing documents are items the bulk response reported as failed while the request itself returned 200, and my code did not retry them. The fix is to retry only the failed items with exponential backoff, lower concurrency and batch size, and tune the index for loading.

Check first: does the code inspect "errors": true and each item's status? How many parallel bulk requests and what size? Is refresh_interval still 1 s, with replicas on?

Fix:

  • Parse the bulk response, collect items with status 429 (or 5xx), and resend just those after a growing delay.
  • Reduce parallel workers and keep batches near 5 to 15 MB. More concurrency past the cluster's limit only creates more rejections.
  • For a full reload into a new index: refresh_interval: -1 and number_of_replicas: 0 while loading, restore afterwards.
  • Use stable ids so a retry overwrites instead of duplicating.

Prevent: use the client's bulk helper with backpressure, alert on a non-zero failed-items count, and finish the run with a count check against the source.

What a 429 means inside ES. Each node has thread pools with bounded queues (the write pool handles indexing, bulk and update requests). When the queue is full, new requests are rejected with es_rejected_execution_exception, HTTP 429. It is a back-pressure signal: "slow down". Recent versions also reject at the coordinating level when the in-flight indexing bytes exceed a memory limit (indexing_pressure), again with 429.

Why documents went missing. Many clients, when a bulk request returns HTTP 200, assume success. The 429 appears only inside the per-item results, so those documents were silently dropped. This is the single most common bulk bug. The fix is code, not cluster: inspect errors and item statuses every time.

Fix in order of impact.

  1. Handle the response: retry only the 429 and 5xx items, with backoff and a maximum attempt count; log or dead-letter permanent errors (400).
  2. Apply back-pressure: use a bounded number of concurrent bulk requests, and when you see 429s, reduce the rate (an adaptive producer). The client helpers (BulkIngester, BulkProcessor, Python's parallel_bulk, Logstash) already provide this; use them.
  3. Tune the target for loading: refresh_interval: -1 (or 30 s), replicas 0 during an initial load, a modest number of shards that spread across nodes, and let ES assign ids when you can.
  4. Check the cluster is healthy: a node with a slow disk, long GC pauses or too many shards will reject more. Look at _cat/thread_pool/write?v for queue and rejected counts, and node stats for heap and disk.

Do not just increase the write queue size. A longer queue only hides overload, uses heap, and increases latency until it fails more badly.

Verification at the end. After the job, compare the number of documents sent with _count (for a fresh index) and with the number of successful items your code tallied. Have the job fail loudly if there is any unresolved item.

Remember: bulk returns 200 with per-item failures. Retry 429 items with backoff, slow down, relax refresh and replicas during the load.

Product managers report deleted products still show in search and some new ones are missing. How do you investigate and repair? Senior

That is drift between the database and the index. Deleted products still showing means deletes are not reaching Elasticsearch; missing new ones means some index events were lost or failed. I measure the drift, fix the pipeline gap, and repair by reindexing from the database.

Check first: compare counts and ids between DB and ES for a sample period (_count versus the table count, or a checksum per id range). Look at how the data gets to ES: does the pipeline handle delete events, are failures in the indexer logged and retried, is there a dead-letter queue with unprocessed messages?

Fix: repair the gap by reindexing the affected range from the database (or a full rebuild into a new index and an alias flip). Send missing deletes explicitly (_delete_by_query on ids that no longer exist in the DB). Then fix the cause: handle deletes in the outbox or CDC flow, make the indexer idempotent with external versions, and add retries and a dead-letter queue.

POST products/_delete_by_query
{ "query": { "terms": { "id": ["p-17", "p-18", "p-19"] } } }

Prevent: a nightly reconciliation job that compares ids or counts between DB and ES and alerts on a difference, plus a tested full-rebuild path. Treat ES as a rebuildable cache of the database.

Why both symptoms point to the pipeline. Zombie documents (deleted in the DB, still in search) mean delete events are never applied: perhaps polling by updated_at only sees live rows, or the consumer ignores delete messages, or the delete event failed and was dropped. Missing new documents mean index events were lost, rejected (mapping error, 429), or stuck behind a poison message in the queue.

Investigation steps.

  1. Quantify. Take a stable slice (for example created last week) and compare DB ids to ES ids, using _search with only _id and "_source": false via search_after loops, or count per day on both sides. Note whether the gaps are random or clustered in time (an outage, a deployment, a schema change).
  2. Find the cause in the pipeline. Look for consumer lag, a dead-letter queue, bulk failures (400 mapping errors, 429), logs from the indexer in the gap period, and whether soft deletes are handled.
  3. Check the nature of the deletes. Hard deletes in the DB are the usual blind spot of polling jobs. Soft deletes (status = deleted) need the search query or the indexer to remove them.

Repair strategies.

  • Targeted: re-publish events for the affected id range, or _delete_by_query for ids found in ES but not in the DB.
  • Full rebuild: build a new index from the database, replay recent events, then flip the alias. Safest when the extent is unknown.

Permanent fixes. Delete events in the outbox or CDC stream, idempotent writes with external versions, retries with a dead-letter queue and alerts on it, and a nightly reconciliation job that compares counts per day or ids by range and posts a metric (drift count). Add a visible "last indexed" lag metric. A good closing line: "I treat the index as a rebuildable cache, so the first thing I make sure of is that a rebuild is a routine, tested button and not a heroic project."

Remember: ES is a derived copy. Detect drift with reconciliation, repair by reindexing from the DB, and fix delete handling.
