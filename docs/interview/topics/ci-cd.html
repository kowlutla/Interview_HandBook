Mental model: the 7 ideas everything hangs on

One line: a pipeline is an automated, repeatable path from a commit to production. Each stage is a question ("does it compile?", "do tests pass?", "is it safe to release?"), asked cheapest first, and the output is one artifact that is promoted unchanged through the environments.
  1. Integrate often. Small changes merged to the shared branch many times a day mean small, easy-to-find breakages. Big, rare merges mean big, painful ones.
  2. The pipeline is the only path. If a build or deploy works only from someone's laptop, you cannot trust or repeat it. Everything goes through the same automated steps.
  3. Build once, promote the same artifact. The thing tested in staging must be byte for byte the thing that runs in production. Only configuration changes between environments.
  4. Fail fast, cheap checks first. Lint and unit tests (seconds) before integration tests (minutes) before end-to-end (many minutes). A red result should arrive as early as possible.
  5. Deploy is not release. Putting code on servers (deploy) and turning a feature on for users (release) are different steps. Feature flags let you separate them.
  6. Every change must be reversible. Rollback, roll forward, flag off, or traffic switch back. Database changes are the hard part, so they are done in small compatible steps.
  7. Measure the flow. Lead time, deployment frequency, change failure rate and recovery time tell you whether the process is healthy. A slow or flaky pipeline is a product bug in your delivery system.

1. Fundamentals and pipeline design

What is continuous integration, and why does it matter? Basic

What the interviewer is testing: whether you see CI as a team habit, not just "a Jenkins job".

Continuous integration means every developer merges small changes into the shared main branch often, at least daily, and each merge is automatically built and tested. The point is early feedback. If two people break each other's code, you find out within minutes, while the change is still fresh in their heads, not three weeks later at release time. The tool (Jenkins, GitHub Actions, GitLab CI) only runs the checks. The practice is the habit of small changes plus a rule that a broken main is fixed first. A team that has a CI server but merges huge branches once a month is not really doing CI. A good sign of real CI: main is almost always green, and a failing build is treated as everyone's problem until it is fixed.

Likely follow-ups
  • What does CI check at minimum? Compile, unit tests, lint and static checks, and often a package step to prove the artifact can be built.
  • Does CI mean no feature branches? Short-lived ones are fine (a day or two). Long-lived ones defeat the idea.
What is the difference between continuous integration, continuous delivery and continuous deployment? Basic

What the interviewer is testing: the classic definition question. The trap is mixing the two "CD"s.

Continuous integration is merging and testing often. Continuous delivery means that every change that passes the pipeline is always in a releasable state: the artifact is built, tested and could go to production, but a human presses the button to release it, perhaps for business timing or approval. Continuous deployment goes one step further: if the checks pass, the change goes to production automatically with no human gate. So delivery is "ready at any time", deployment is "released automatically". Most teams do continuous delivery for regulated or customer-facing systems, and continuous deployment for services with strong automated tests, feature flags and good monitoring. Notice that deployment needs more trust in your tests and rollback than delivery does.

Likely follow-ups
  • Can a team do deployment to staging automatically and delivery to production? Yes, that is very common.
  • What makes continuous deployment safe? Fast reliable tests, small changes, progressive rollout, feature flags and automatic rollback on bad metrics.
What are the typical stages of a pipeline, and in what order? Basic

What the interviewer is testing: can you design a sensible pipeline and explain the order.

A common order is: checkout, build (compile, resolve dependencies), fast checks (lint, format, static analysis, unit tests), then package (jar, wheel, container image, with a version), then slower checks (integration tests against a real database, security scans), then publish the artifact to a repository or registry, deploy to a test or staging environment, run smoke and end-to-end tests there, and finally promote to production, often with an approval or an automatic gradual rollout. The order follows two rules. Put cheap, fast and likely-to-fail checks first so that feedback is quick. Do each expensive thing once, such as building the artifact. Independent checks, for example lint and unit tests, can run in parallel inside a stage to cut the total time.

Likely follow-ups
  • Where do you put slow end-to-end tests? After the artifact exists, against a deployed environment, and often only on main, not on every pull request.
  • What is a "gate"? A condition that must pass to continue: tests, approval, a security policy.
What does "pipeline as code" mean, and why is it better than clicking in a UI? Basic

What the interviewer is testing: knowledge of Jenkinsfile, workflow YAML and the reasons behind them.

Pipeline as code means the pipeline definition is a text file in the same repository as the application: a Jenkinsfile, a .github/workflows/*.yml, or a .gitlab-ci.yml. The benefits are the same as for any code. It is versioned, so you can see who changed the build and when, and revert it. It goes through pull-request review. It branches with the code, so an old release branch builds with its old pipeline, and a feature branch can change the build without breaking others. You can copy it to a new project. A pipeline configured only in a web UI is hidden, cannot be reviewed, and is lost when the server dies. The cost is that a mistake in the file can break everyone's builds, so treat it with care and test changes on a branch.

Likely follow-ups
  • How do you avoid copy-pasting pipelines across 50 repos? Shared libraries (Jenkins), reusable workflows and composite actions (GitHub), includes and templates (GitLab).
What does "build once, deploy many" mean, and why is rebuilding per environment a bad idea? Intermediate

What the interviewer is testing: the most important rule for trustworthy releases.

You build the artifact (a container image, jar, zip) one time, give it an immutable version such as the commit SHA, store it in a registry, and then deploy that same artifact to dev, staging and production. If you rebuild for production, you are no longer running what you tested. A different base image, a new transitive dependency, or a changed compiler flag can sneak in, and "it passed in staging" no longer means anything. What changes between environments is configuration only: database URLs, feature flags, secrets, resource limits. These are injected at deploy or start time, not baked into the artifact. A good check: can you take the exact image running in production and trace it to one commit and one pipeline run?

Likely follow-ups
  • Where does config come from? Environment variables, mounted config files, a config service or secret manager, injected at start.
  • Why tag images with the commit SHA and not only latest? latest moves, so you cannot tell what is running or roll back to a known version.
Common mistakes: a build step that runs per environment (for example npm run build:prod only in the deploy job), and baking secrets or URLs into the image.
What does "fail fast" mean in a pipeline, and how do you apply it? Basic

What the interviewer is testing: practical pipeline ordering and developer experience.

Fail fast means a broken change should be reported as early and as cheaply as possible. In practice you order the stages by cost: formatting, lint and compile take seconds, unit tests take a minute or two, integration tests longer, and end-to-end tests longest. If lint fails, there is no point spending ten minutes on the slow stages. You also stop the whole pipeline on the first failure (the default in most tools), cancel older runs when a new commit arrives on the same branch, and run the tests most likely to fail first. A developer who sees red in two minutes fixes it while the code is still in their head. A developer who waits forty minutes switches to other work and loses context.

Likely follow-ups
  • When would you NOT stop at the first failure? When you want a complete report, such as a test matrix where you want to see all failing platforms (fail-fast: false in GitHub Actions).
What makes a build reproducible, and why do builds that "work on my machine" fail in CI? Intermediate

What the interviewer is testing: debugging mindset for environment differences.

A reproducible build gives the same output from the same commit, anywhere. CI starts from a clean machine, so it exposes hidden assumptions. Typical causes of "works locally, fails in CI": a file that is git-ignored but needed (a local config), a dependency installed globally on your laptop, a different language or tool version, an unpinned dependency that resolved to a new version, test order or timing differences, a different time zone or locale, case-sensitive file names on Linux versus Windows or macOS, and environment variables or secrets that exist only on your machine. To make builds reproducible: pin tool versions (a .tool-versions file, the Node or Java version in the pipeline), commit lock files (package-lock.json, poetry.lock), build inside a container with a fixed image, and avoid reading from the network at test time. The fix for a mismatch is to reproduce CI locally: run the same container image and the same commands.

Likely follow-ups
  • What is a hermetic build? One that depends only on declared inputs, with no hidden network or machine state. Tools like Bazel enforce this.
How does an artifact move through environments, and what is an approval gate? Intermediate

What the interviewer is testing: promotion flow and where humans fit in.

After the build, the artifact is deployed to a first environment, often dev or an ephemeral preview, then to staging (a production-like copy), then to production. Each hop runs checks: smoke tests (does it start and answer basic requests?), end-to-end or contract tests, sometimes performance tests. A gate is a rule that blocks the next hop until satisfied. It can be automatic (all tests green, no critical vulnerabilities, error rate normal) or manual (a named person approves, a change ticket exists, it is outside a freeze window). GitHub Actions has "environments" with required reviewers, GitLab has protected environments and when: manual jobs, and Jenkins has the input step. Prefer automatic gates where possible, because manual approvals slow flow and often become a rubber stamp.

Likely follow-ups
  • Should staging be identical to production? As close as is affordable: same artifact, same deployment method, same kinds of dependencies. It is never fully identical in data volume and traffic, which is why progressive rollout in production still matters.

2. Jenkins

Many companies still run Jenkins. You need to read and write a Jenkinsfile and debug a failing job. Plugin internals and running the Jenkins cluster itself are platform-team topics and are not covered.

How is Jenkins structured: controller, agents, executors? Basic

What the interviewer is testing: basic understanding of where a build actually runs.

A Jenkins controller (older docs call it the master) holds the configuration, schedules jobs, shows the UI and stores build history. The real work should run on agents (older name: slaves, nodes): separate machines, VMs or containers that connect to the controller. An agent has one or more executors, which are slots, each running one build at a time. Jobs choose where to run using labels, for example agent { label 'linux && docker' }. Do not run builds on the controller: a heavy or malicious build then endangers the whole system and its credentials. Modern setups create agents on demand, for example as pods in Kubernetes, so each build gets a clean throwaway environment.

Likely follow-ups
  • Why throwaway agents? No leftover files from earlier builds, and no "it passed because of old state".
  • What is a workspace? The directory on the agent where the job checks out code and builds.
Show me a Declarative Jenkinsfile and explain its parts. Basic

What the interviewer is testing: can you actually write one.

A Declarative Pipeline has a fixed shape. pipeline is the root. agent says where to run. environment sets variables, and credentials() pulls secrets from the Jenkins credential store without printing them. stages contains stage blocks, each with steps. post runs at the end depending on the result (always, success, failure). options sets things like a timeout. when makes a stage conditional, for example only on the main branch.

pipeline {
  agent { docker { image 'maven:3.9-eclipse-temurin-17' } }
  options { timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }
  environment { REGISTRY = 'registry.example.com' }
  stages {
    stage('Build') { steps { sh 'mvn -B -DskipTests package' } }
    stage('Test')  {
      steps { sh 'mvn -B test' }
      post { always { junit 'target/surefire-reports/*.xml' } }
    }
    stage('Publish') {
      when { branch 'main' }
      environment { TOKEN = credentials('registry-token') }
      steps { sh './publish.sh' }
    }
  }
  post { failure { echo 'Build failed' } }
}
Likely follow-ups
  • Where does the file live? In the repo root as Jenkinsfile, picked up by a Multibranch Pipeline job that creates a job per branch and pull request.
  • How do you run stages in parallel? A parallel { stage('A') {...} stage('B') {...} } block inside a stage.
Declarative versus Scripted pipeline, and what are shared libraries? Intermediate

What the interviewer is testing: knowing the two styles and how teams avoid duplication.

Scripted Pipeline is plain Groovy code with node { ... } blocks. It is very flexible, with loops and functions, but easy to make messy and error-prone. Declarative is a structured, more restricted syntax that is easier to read, validate and support in the UI. You can still drop into Groovy with a script { ... } step when needed. Most teams start with Declarative. A shared library is a separate Git repository of Groovy code, loaded with @Library('my-lib'), that offers reusable steps such as deployToK8s(env: 'staging') so that fifty repos do not each copy the same logic. One caution: Groovy in Jenkins runs in a special way (it is made resumable, with a "CPS transform"), so some normal Groovy features behave oddly, and heavy computation belongs in a shell step, not in pipeline Groovy.

Likely follow-ups
  • Why can Groovy loops over big lists be slow or fail with "not serializable"? Pipeline state is saved to disk so builds survive a restart, which restricts what objects you can hold.
A Jenkins job fails. How do you find out why? Intermediate

What the interviewer is testing: a systematic approach to a red build.

I start with the console output and scroll up to the first error, because later errors are often consequences. I check which stage and which step failed, and whether it failed at once or after a long time (a timeout suggests a hang or a slow network call). Next I compare with the last green build: what changed, the code (the changes list shows the commits) or the environment (a new agent image, an updated plugin, an expired credential)? I check agent details: disk full, wrong tool version, missing label. For test failures I open the JUnit report. To reproduce, I run the same command in the same image locally or use the Jenkins "Replay" feature to re-run the pipeline with edits without committing. Adding set -x in shell steps, sh 'env | sort' (careful not to leak secrets) and sh 'pwd; ls -la' reveal hidden assumptions. If the same build fails on one agent only, I suspect that agent's state.

Likely follow-ups
  • Build hangs forever? Add a timeout, take a thread dump of the process, and look for a command waiting on input (a prompt).
  • "Permission denied" in a script? Often the file lost its executable bit, or the container user differs from the file owner.
How should secrets be used in Jenkins? Intermediate

What the interviewer is testing: safe handling in the most common legacy tool.

Store secrets in the Jenkins credential store (or better, in an external secret manager such as HashiCorp Vault that Jenkins reads at run time), never in the Jenkinsfile or the repo. Use them with withCredentials([string(credentialsId: 'api-token', variable: 'TOKEN')]) { sh 'curl -H "Authorization: Bearer $TOKEN" ...' }. Jenkins masks the value in the console log. Two warnings. Use single quotes around the shell command so the shell, not Groovy, expands the variable, since Groovy string interpolation can leak the secret into the process list and logs. And masking only matches the exact value: if a script prints it base64-encoded or split, masking will not catch it. Scope credentials to the folder or job that needs them, and rotate them.

Likely follow-ups
  • Can a pull request from a stranger steal secrets by editing the Jenkinsfile? Yes, if untrusted forks are built with credentials. Only run trusted code with secrets.

3. GitHub Actions

Explain the GitHub Actions model: workflow, event, job, step, runner, action. Basic

What the interviewer is testing: vocabulary and structure.

A workflow is a YAML file in .github/workflows/. It starts on an event: push, pull_request, a schedule (cron), a manual workflow_dispatch, a release, and more. A workflow has one or more jobs. Jobs run in parallel by default, and needs: makes one wait for another. Each job runs on a fresh runner, a virtual machine (GitHub-hosted, such as ubuntu-latest, or your own self-hosted one). A job has ordered steps, which share the machine's file system. A step either runs a shell command (run:) or uses an action (uses:), a reusable packaged step like actions/checkout. Because every job starts on a clean machine, files do not carry between jobs unless you upload and download them as artifacts or use a cache.

Likely follow-ups
  • How do jobs pass data? Small values through job outputs, files through artifacts.
  • What is ubuntu-latest? A label that points at a recent Ubuntu image, which GitHub moves forward over time. Pin a specific version if you need stability.
Write a simple GitHub Actions workflow that builds, tests and publishes on main. Basic

What the interviewer is testing: can you write one without looking it up.

This workflow runs on pull requests and on pushes to main. The test job runs always. The publish job needs the test job to succeed and runs only on main. Note the least-privilege permissions block, and the concurrency group that cancels outdated runs of the same branch.

name: ci
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm test
  publish:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/publish.sh
        env:
          TOKEN: ${{ secrets.REGISTRY_TOKEN }}
Likely follow-ups
  • Why npm ci and not npm install? It installs exactly what the lock file says and fails if they disagree. It is reproducible.
  • Why a timeout-minutes? The default is long (360 minutes), and a hung job would burn time and queue others.
What are matrix builds, concurrency groups and conditionals in Actions, and when do you use each? Intermediate

What the interviewer is testing: practical features you need for real pipelines.

A matrix runs the same job many times with different values, for example Java 17 and 21 on Linux and Windows, which is how a library proves it works on all supported versions. Add fail-fast: false if you want every combination to finish. Concurrency limits runs sharing a group key to one at a time and can cancel older runs. Cancel-in-progress is right for pull request builds (only the latest commit matters), but wrong for production deployments, where you want deploys to queue, not be cut in half. Conditionals use if: with expressions, such as if: github.event_name == 'push' or if: failure() to run a cleanup or notify step after a failure. Use paths: filters on the event to skip workflows when only docs changed.

strategy:
  fail-fast: false
  matrix:
    java: [17, 21]
    os: [ubuntu-latest, windows-latest]
runs-on: ${{ matrix.os }}
Likely follow-ups
  • How do you avoid two deploys to production racing? Give the deploy job a concurrency group such as deploy-prod with cancel-in-progress: false.
What are GITHUB_TOKEN permissions and OIDC, and why not store cloud keys as secrets? Senior

What the interviewer is testing: modern secure pipeline practice.

Each run gets an automatic GITHUB_TOKEN, a short-lived credential scoped to that repository. Set permissions: explicitly and minimally (for example contents: read) so a compromised step cannot push code or edit releases. For cloud access, long-lived access keys stored as repository secrets are risky: they leak, are rarely rotated, and work from anywhere. With OpenID Connect (OIDC) the workflow asks GitHub for a signed identity token (it needs permissions: id-token: write). The cloud provider is configured to trust tokens from that exact repository and branch or environment, and exchanges the token for temporary credentials valid for minutes. Nothing long-lived is stored. A cloud role can then say "only the main branch of repo X may deploy to production".

permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/deploy-prod
      aws-region: eu-west-1
Likely follow-ups
  • Same idea elsewhere? GitLab CI has id_tokens, and Jenkins can use OIDC plugins or workload identity on its agents.
What are the main security pitfalls in GitHub Actions workflows? Senior

What the interviewer is testing: supply-chain awareness beyond "use secrets".

First, third-party actions run with your token and secrets. A tag like @v3 can be moved by the action's owner (or an attacker who takes over the account), so for sensitive repos pin to a full commit SHA and let a bot update it. Second, pull_request_target and workflow_run triggers run with the base repository's secrets and write token. If such a workflow also checks out and runs the code from a fork's pull request, a stranger can steal secrets. Use plain pull_request for untrusted code (secrets are not given to forks). Third, script injection: putting ${{ github.event.pull_request.title }} directly inside a run: script lets a crafted title run commands. Pass it through an environment variable instead. Fourth, give each job the least permissions and do not echo secrets. Fifth, protect the workflow files themselves with code owners, since whoever can edit the workflow can change what runs.

# risky: title is pasted into the shell script
- run: echo "${{ github.event.pull_request.title }}"
# safer: value arrives as data in an environment variable
- run: echo "$TITLE"
  env:
    TITLE: ${{ github.event.pull_request.title }}
Likely follow-ups
  • Are secrets available to pull requests from forks? Not by default, which is why a fork PR build cannot publish or deploy.
How do you reuse pipeline logic across many repositories in GitHub Actions? Intermediate

What the interviewer is testing: avoiding copy-paste at scale.

There are two main tools. A reusable workflow is a whole workflow with on: workflow_call, which other workflows call as a job with uses: org/shared/.github/workflows/build.yml@v2, passing inputs and secrets. It suits a complete standard build-and-test flow. A composite action bundles several steps into one reusable step (an action.yml with runs: using: composite), good for a small repeated sequence such as "set up Java, restore cache, build". Version them with tags so that a change in the shared pipeline does not break all consumers at once. Organisations can also provide required workflows and starter templates. The trade-off of sharing is coupling: a bug in the shared piece hits everyone, so release it like a library with versions and a changelog.

Likely follow-ups
  • Reusable workflow versus composite action? A workflow is a whole job (or several) with its own runner; a composite action is steps inside your job on your runner.
A GitHub Actions run fails only in CI. How do you debug it? Intermediate

What the interviewer is testing: hands-on troubleshooting skills.

I open the failed step and read the first real error, not only the last line. Then I turn on debug logging by re-running the job with "Enable debug logging" (or setting the secret ACTIONS_STEP_DEBUG to true). I print context, such as the working directory, tool versions (node -v, java -version) and a safe subset of the environment. I compare with the last green run: did a dependency, the runner image or an action version change? Common causes are an unpinned @latest, a changed ubuntu-latest image, a stale or poisoned cache, a missing permission, a secret that is empty in a fork run, or a path filter that skipped a needed job. To reproduce locally, the tool act can run workflows in containers, though it is not identical to the real runner. For a stubborn problem you can add a temporary debug step or use an interactive session action on a branch, being careful with secrets. Once found, I fix the cause and add a guard (a pinned version, a check that fails early with a clear message).

Likely follow-ups
  • Re-running only failed jobs? The UI has "Re-run failed jobs". If it passes on retry with no change, that is flakiness, which should be tracked, not ignored.

4. GitLab CI and comparing tools

Explain how GitLab CI works: .gitlab-ci.yml, stages, jobs, runners. Basic

What the interviewer is testing: reading and writing a GitLab pipeline.

The pipeline is defined in .gitlab-ci.yml in the repo root. It has stages in order (for example build, test, deploy) and jobs that each belong to a stage. All jobs of one stage run in parallel; the next stage starts when the whole previous one succeeds. Jobs run on runners, agents that you register with the GitLab server, using an executor such as shell, Docker or Kubernetes. With the Docker executor each job runs in the container image you name with image:. script: holds the commands, artifacts: passes files forward and keeps reports, cache: speeds up dependency installs, variables: sets variables, and environment: links a job to a deployment target.

stages: [build, test, deploy]
build:
  stage: build
  image: golang:1.22
  script: [go build -o app ./...]
  artifacts: { paths: [app], expire_in: 1 week }
unit:
  stage: test
  image: golang:1.22
  script: [go test ./...]
deploy_prod:
  stage: deploy
  script: [./deploy.sh app]
  environment: production
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
Likely follow-ups
  • What are predefined variables? Values GitLab sets, such as CI_COMMIT_SHA, CI_COMMIT_BRANCH, CI_PIPELINE_ID.
What are rules, needs and merge request pipelines in GitLab? Intermediate

What the interviewer is testing: the features that make pipelines flexible and fast.

rules decide whether a job is added to a pipeline, using conditions on variables, changed files and the pipeline source, with when to make it manual or delayed. They replace the older only/except, which should not be mixed with them. needs builds a directed graph (DAG): a job can start as soon as the specific jobs it needs are done, without waiting for the entire previous stage. That removes idle waiting between stages. Merge request pipelines run for a merge request and can test the source branch; with merged results pipelines GitLab tests the result of merging into the target branch, which catches "green alone, red together" problems. A common pitfall is getting duplicate pipelines (one for the branch, one for the MR). Fix it with a workflow:rules block that picks one source.

integration:
  stage: test
  needs: [build]          # start when build is done, not when the stage ends
  rules:
    - changes: [src/**/*, pom.xml]
  script: [mvn -B verify]
Likely follow-ups
  • How to run a job N ways? parallel: matrix: or parallel: 4 for sharding tests.
  • Include shared config? include: with local files, other projects or templates.
What is a self-hosted runner or agent, and what should a developer care about? Intermediate

What the interviewer is testing: awareness of where code runs, without ops depth.

Hosted runners are machines the CI provider manages. Self-hosted runners are machines you run, used when you need special hardware, network access to private systems, bigger machines, or lower cost at scale. As a developer you should care about four things. Isolation: a persistent self-hosted runner keeps files and caches between jobs, so builds can pass or fail because of old state, and an untrusted pull request could plant something. Prefer ephemeral runners that are created per job and destroyed. Security: a runner can reach your internal network and may hold credentials, so do not run untrusted fork code on it. Capacity: queue time grows when there are too few runners. Consistency: the tools installed on the runner must match what the pipeline expects, which is why running jobs inside a pinned container image is safer than relying on the host's tools. Sizing, autoscaling and patching the fleet are platform-team work.

Jenkins versus GitHub Actions versus GitLab CI: how do you choose? Intermediate

What the interviewer is testing: balanced judgement, not tool fandom.

All three do the same job: run defined steps on events. Jenkins is self-hosted and very flexible, with a huge plugin ecosystem and Groovy pipelines. You can build almost anything, but you carry the maintenance: upgrades, plugins, agents, security. GitHub Actions is built into GitHub, with a large marketplace of reusable actions, hosted runners and a very low setup cost; pipelines are YAML. It fits best when the code is on GitHub. GitLab CI is built into GitLab, with an integrated experience (merge requests, registry, environments, security scans in one product) and a strong DAG and rules model. The usual deciding factors are where the code lives, whether the company wants to run the infrastructure, compliance needs, and the effort to migrate existing pipelines. The core concepts are the same everywhere, so a developer who understands stages, caching, artifacts and secrets can move between them in days.

Likely follow-ups
  • Is there a risk in the marketplace? Yes, third-party actions are code that runs in your pipeline, so vet and pin them.

5. Artifacts, caching and pipeline speed

What is the difference between an artifact and a cache? Basic

What the interviewer is testing: a very common confusion, and the answer shows pipeline literacy.

An artifact is an output that you want to keep or pass on: the compiled binary, a test report, a container image, a coverage file. It is the result of the build, it is versioned and tied to a run, and the next job or a human uses it. A cache is an optimisation: files that are expensive to fetch or compute again and can be rebuilt if missing, for example downloaded dependencies (~/.m2, node_modules, the pip cache). The pipeline must still work with an empty cache, only slower. Rule of thumb: if the pipeline breaks when it is missing, it is an artifact; if it just gets slower, it is a cache. Caches are shared best-effort and can be stale or evicted. Artifacts are expected to be there.

Likely follow-ups
  • Where do release artifacts live long term? In an artifact repository or registry (Nexus, Artifactory, a container registry, a package registry), not only as CI run attachments, which expire.
How do you design a good cache key, and what can go wrong? Intermediate

What the interviewer is testing: understanding invalidation, which is the hard part of caching.

The key should change exactly when the cached content should change. For dependencies, the key is usually the operating system plus a hash of the lock file, for example deps-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}. When the lock file changes, the key changes and a fresh cache is built. A fallback "restore key" such as the prefix deps-Linux- lets a new run start from the nearest older cache and only download the difference. What can go wrong: a key that never changes gives a stale cache and strange old behaviour; a key that changes every run (like the commit SHA) means it is never reused; caching build output as well as dependencies can hide real build errors; and caches shared across branches can be poisoned by an untrusted branch, so some systems isolate caches per branch or per trust level. If you suspect a bad cache, bump a version prefix in the key to start clean.

- uses: actions/cache@v4
  with:
    path: ~/.m2/repository
    key: m2-${{ runner.os }}-${{ hashFiles('**/pom.xml') }}
    restore-keys: m2-${{ runner.os }}-
Likely follow-ups
  • Cache size limits? Providers cap storage and evict old entries (GitHub's limit was about 10 GB per repository at the time of writing). Check current docs.
Common mistakes: caching the whole workspace; using the branch name as the only key; trusting a cache hit as proof the build is correct.
How do you make container image builds fast in CI? Intermediate

What the interviewer is testing: Docker layer awareness, which affects most pipelines.

Docker builds an image in layers, one per instruction, and reuses a layer if that instruction and everything before it is unchanged. So order the Dockerfile from least to most frequently changing. Copy only the dependency files first (package.json and the lock file), install dependencies, and only then copy the source code. A source change then reuses the dependency layer. Use a .dockerignore so the build context stays small. Use multi-stage builds: compile in a big builder image and copy only the result into a small runtime image, which is faster to push and pull and has fewer vulnerabilities. In CI the runner is clean, so the layer cache is empty. Use a remote cache: BuildKit can import and export cache to a registry or to the CI cache (--cache-from, --cache-to), so the next run starts warm.

FROM node:20 AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                 # cached until the lock file changes
COPY . .
RUN npm run build
FROM node:20-slim
COPY --from=build /app/dist /app/dist
CMD ["node", "/app/dist/server.js"]
Likely follow-ups
  • Why not tag production images only as latest? You cannot trace or roll back. Tag with the commit SHA or a version, and optionally also a moving tag.
How do you version and store build artifacts so a release is traceable? Intermediate

What the interviewer is testing: release hygiene.

Every artifact gets an immutable identifier tied to the source: the Git commit SHA, plus a human version such as 1.8.3 from semantic versioning (major.minor.patch: breaking change, new feature, bug fix). The pipeline pushes it to an artifact repository or registry and never overwrites a published version. Immutability matters: if 1.8.3 could change contents, nobody could say what is in production. Store metadata with the artifact: commit SHA, build number, pipeline URL, and ideally a software bill of materials (a list of the components inside) and a signature. A Git tag such as v1.8.3 marks the release commit. Then the question "what is running in production, and what changed since the last release?" is answered by comparing two SHAs. Also set retention rules so old snapshot builds are cleaned, while released versions are kept.

Likely follow-ups
  • Snapshot versus release? A snapshot (Maven -SNAPSHOT) is a moving development build, a release is fixed forever.
Your pipeline takes 40 minutes. How do you make it faster? Senior

What the interviewer is testing: measure first, then fix the biggest cost.

First I measure: look at the time per stage and per job, and the queue time before jobs start. Optimising without data wastes effort. Then the usual levers, roughly in order of payoff. Parallelise: independent jobs side by side, and split the test suite into shards. Cache dependencies and layers. Do less: path filters or affected-project detection in a monorepo so a docs change does not run everything, and cancel superseded runs. Reorder: put fast checks first so failures return early. Make tests faster: replace slow end-to-end tests with lower-level ones, share expensive setup, use in-memory or containerised databases that start quickly, and remove sleeps. Use bigger or more runners if the bottleneck is CPU or queueing. Trim the Docker image and the checkout (shallow clone with fetch-depth: 1). Move slow things off the critical path: run nightly full scans instead of per pull request. Finally, set a target (for example under 10 minutes for pull request feedback) and watch it, because pipelines slowly get slower.

Likely follow-ups
  • What if the time is queueing, not running? Add runners, use autoscaling, or reduce load by cancelling redundant runs.
  • Shallow clone risk? Anything that needs history (version from tags, git describe, changed-file detection) needs deeper fetch.

6. Testing in pipelines

What is the test pyramid, and how does it shape a pipeline? Basic

What the interviewer is testing: sound testing strategy, with speed and cost in mind.

The test pyramid says: have many fast, small unit tests at the bottom, fewer integration tests in the middle, and very few slow end-to-end (UI or full system) tests at the top. Unit tests check one class or function with no network or database, run in milliseconds and point to the exact failing line. Integration tests check that components work with real neighbours such as a database or message broker. End-to-end tests drive the whole system like a user: realistic but slow, fragile and hard to debug. The shape matters because cost and flakiness grow upward. In the pipeline, unit tests run on every commit and finish in a couple of minutes, integration tests run on every pull request, and a small set of end-to-end smoke tests run after deployment to staging. An "ice cream cone" (mostly end-to-end tests, few unit tests) gives slow, flaky pipelines.

Likely follow-ups
  • Where do contract tests fit? Between services, at the integration level: they check that a consumer and a provider agree on the API without deploying both.
  • What is the "testing trophy"? A variant that values integration tests more. The point is the same: be deliberate about cost versus confidence.
What is a flaky test, what causes it, and how do you handle it? Intermediate

What the interviewer is testing: mature handling of a problem that kills trust in CI.

A flaky test passes and fails on the same code. Common causes: timing and sleeps, async work not awaited, shared state between tests (a database row, a static variable, a file), test order dependence, reliance on the clock, random data without a fixed seed, real network calls, resource contention on a busy CI machine, and dates or time zones. Why it matters: when "just re-run" becomes normal, people stop believing red builds, and real bugs slip through. How I handle it: detect (track pass rate per test, re-run to confirm), then quarantine: move the test out of the blocking path into a separate non-blocking job so it stops hurting everyone, and open a ticket with an owner and deadline. Then fix the root cause: wait on conditions instead of fixed sleeps, isolate data per test, inject a fake clock, mock the network. Automatic retry hides the problem, so use it only as a stopgap and always report retried tests so the flakiness stays visible.

Likely follow-ups
  • How do you reproduce one? Run it in a loop, in random order, under CPU load, in the same container as CI.
  • Should the build retry failed tests automatically? Limited retries with a visible report can be acceptable. Silent unlimited retries are not.
Common mistakes: deleting a flaky test without understanding it (it might be a real race condition in the product code); adding a longer sleep.
How do you run tests in parallel and split a big suite across machines? Intermediate

What the interviewer is testing: practical speed-up and its pitfalls.

There are two levels. Inside one machine, test frameworks run tests across threads or processes (for example pytest -n auto, JUnit parallel execution, Jest workers). Across machines, you shard: split the suite into N groups and run each group as a separate parallel job, then merge the reports. Good splitting uses past timing data so each shard takes about the same time, since one slow shard decides the total. CI features help: parallel and matrix in GitLab and GitHub, or test-splitting tools. The big pitfall is shared state. Tests that were fine serially now collide on the same database table, port, temp file or environment variable. Fix by giving each worker its own database or schema, random ports and unique temp directories. Also collect all shard results and fail the pipeline if any fails.

strategy:
  matrix:
    shard: [1, 2, 3, 4]
steps:
  - run: pytest --shard-id=${{ matrix.shard }} --num-shards=4   # example plugin flags
Likely follow-ups
  • Why can parallel make flakiness appear? It exposes hidden order and shared-state dependencies.
How do integration tests get a real database or broker inside a pipeline? Intermediate

What the interviewer is testing: setting up realistic tests without a shared fragile environment.

The best approach is a throwaway dependency created for the test run. Service containers (GitHub Actions services:, GitLab services:) start, say, a PostgreSQL container next to your job. A library such as Testcontainers starts containers from inside the test code, so the same tests run on a laptop and in CI. Docker Compose can start a small stack. Advantages: a clean state every time, the same database engine and version as production (an in-memory substitute like H2 often behaves differently), and no shared test database that someone else might corrupt. Keep tests independent: run migrations at the start, roll back or clean after each test. For third-party services you cannot run, use a stub or mock server and add contract tests so the stub does not drift from reality.

services:
  postgres:
    image: postgres:16
    env: { POSTGRES_PASSWORD: test }
    ports: ['5432:5432']
    options: >-
      --health-cmd "pg_isready -U postgres" --health-interval 5s --health-retries 10
Likely follow-ups
  • Why the health check? The container may not be ready to accept connections when the first test starts, which is a classic flaky cause.
What are smoke tests, contract tests and post-deploy checks, and where do they run? Intermediate

What the interviewer is testing: knowing that tests continue after the build.

A smoke test is a tiny set of checks that proves a deployment is basically alive: the service starts, the health endpoint answers, a login and one key request work. It runs right after each deploy, in staging and production, and takes seconds. A contract test checks that two services agree on an API. With consumer-driven contracts (the Pact approach) the consumer records what it expects, and the provider's pipeline verifies it still satisfies those expectations. This catches breaking API changes without a full shared environment. Post-deploy checks compare real metrics with the previous version: error rate, latency, and business signals. A deployment is only "done" when these look healthy. This closes the loop: the pipeline does not end at "deployed", it ends at "verified".

Likely follow-ups
  • Should smoke tests write data in production? Only safe, clearly marked synthetic data, or read-only checks.
Should the pipeline enforce code coverage thresholds? Intermediate

What the interviewer is testing: judgement about metrics that can be gamed.

Coverage tells you which lines ran during tests, not whether the tests check anything meaningful. A test that calls a method and asserts nothing gives coverage but no safety. A hard global threshold, such as 80 percent, often leads to low-value tests written only to reach the number. What works better: report coverage on every pull request, enforce a gate on new or changed code (for example 80 percent of the lines in the diff), and prevent the overall number from dropping. Combine it with other signals: mutation testing for important modules (it changes the code and checks that tests notice), and reviewing risky paths by hand. So I would use coverage as a guide and a ratchet, not as a goal.

Likely follow-ups
  • What is mutation testing? A tool makes small bugs on purpose (flip a condition) and checks that at least one test fails. If none fails, your tests are weak there.

7. Deployment strategies and rollback

What is the difference between deploying and releasing? Intermediate

What the interviewer is testing: the idea that makes continuous deployment safe.

Deploying means putting a new version of the code on production machines. Releasing means making a feature available to users. They do not have to happen at the same moment. With feature flags you deploy code that is switched off (dark launch), verify it is healthy, and then turn it on for internal users, then 1 percent, then everyone, without another deployment. This reduces risk in two ways. A deployment becomes a boring technical event, because nothing visible changes. And a release becomes a quick configuration change you can undo in seconds by turning the flag off. It also decouples teams: engineering can deploy daily while product decides when users see the feature.

Likely follow-ups
  • Cost of flags? Extra code paths and tests, and old flags must be removed, or you build up "flag debt".
How does a rolling deployment work, and what are its trade-offs? Basic

What the interviewer is testing: the default strategy most developers meet first.

In a rolling deployment you replace instances of the old version with the new one a few at a time. At each step, a new instance starts, must pass its health check (readiness), and only then receives traffic, after which an old instance is stopped. At no moment is the whole service down, and you need little extra capacity. Kubernetes does this by default for a Deployment, controlled by maxSurge (how many extra pods may exist) and maxUnavailable (how many may be missing). The trade-offs: during the rollout both versions serve traffic at once, so they must be compatible with each other and with the same database schema. Rollback is itself another rolling update, so it is not instant. And if the new version is broken in a way that health checks do not catch, it gradually takes over before you notice.

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 0   # never drop below desired capacity
Likely follow-ups
  • Why does readiness matter? Without a proper readiness check, traffic is sent to an instance that has started but is not ready, and users get errors during the deploy.
  • What is graceful shutdown? Old instances stop accepting new requests and finish in-flight ones before exiting.
What is a blue-green deployment, and what are its pros and cons? Intermediate

What the interviewer is testing: can you explain an instant switch and its cost.

You keep two full production environments. Blue is live and serves all traffic. You deploy the new version to green, which is idle, and test it fully there (smoke tests, even a bit of internal traffic). When satisfied, you flip the router or load balancer so that all traffic goes to green in one step. Blue stays up, untouched, for a while. If something is wrong, you flip back, and rollback is nearly instant. Pros: no mixed versions serving users, fast rollback, a realistic pre-production test. Cons: you pay for double capacity during the switch, and the data layer is the hard part, because both environments usually share one database, so schema changes must work with both versions. Long-lived user sessions or in-flight work may also need care. It is an all-or-nothing switch, so it gives less gradual risk control than a canary.

Likely follow-ups
  • How do you reduce the double cost? Keep green only during the release, or scale it down after the soak period.
What is a canary release, and how do you decide to promote or abort it? Intermediate

What the interviewer is testing: progressive delivery and metric-driven decisions.

The name comes from the canary in the coal mine. You send a small slice of real traffic, say 1 or 5 percent, to the new version while everyone else stays on the old one. You watch signals that compare the two: error rate, latency percentiles, saturation (CPU, memory), and business metrics such as checkout success. If the canary is as healthy as the baseline, you increase the share in steps (5, 25, 50, 100 percent), pausing to watch at each step. If a metric breaches a threshold, you route all traffic back to the old version and the blast radius was only a few users. The skill is picking the right metrics and waiting long enough to see rare problems. Tools like Argo Rollouts, Flagger or a service mesh automate the analysis and the promotion. The trade-offs: more moving parts, you need good monitoring, and two versions run at once, so compatibility rules apply again.

Likely follow-ups
  • How is the canary chosen, randomly or by user? Either. Random is simple; sticky by user keeps one person on one version, which avoids confusing back-and-forth.
  • Low-traffic service? There may not be enough data to compare, so use a longer soak or synthetic tests.
Compare rolling, blue-green, canary and recreate deployments. When would you use each? Senior

What the interviewer is testing: trade-off thinking, matched to a situation.

Recreate stops the old version, then starts the new one. It is simple and avoids mixed versions, but it has downtime. It is acceptable for batch jobs, internal tools, or a change that cannot run side by side. Rolling is the cheap default: no downtime, little extra capacity, but mixed versions and slow rollback. Blue-green gives an instant switch and instant rollback and no mixed versions for users, at the cost of double capacity, and it suits releases where you want a full rehearsal first. Canary limits the blast radius with real traffic and metric checks, which suits high-traffic, high-risk services, at the cost of tooling and monitoring effort. They combine well: a canary stage followed by a rolling rest, with feature flags on top. In an interview, say how you would choose: how bad is a failed release, how fast can I detect it, can two versions coexist, and how much spare capacity do I have?

How do feature flags work in a delivery pipeline, and what are the risks? Intermediate

What the interviewer is testing: practical use of flags for safe, frequent releases.

A feature flag is a runtime switch in the code: if (flags.isOn("new-checkout", user)) { newFlow() } else { oldFlow() }. The value comes from a flag service or config, evaluated per request, so you can change behaviour without a deployment. Uses: dark launches, gradual percentage rollouts, targeting (staff first, one region, a beta group), an instant kill switch, and A/B experiments. They let unfinished work be merged to main safely in small steps, which supports trunk-based development. Risks: every flag doubles the code paths to test; stale flags pile up as clutter and hidden behaviour; a flag service outage must fall back to a safe default; flags can leak security-sensitive logic if evaluated on the client; and complex flag combinations are hard to reason about. Good practice: name an owner and expiry date for each flag, remove the flag after rollout, and keep defaults safe. Open standards such as OpenFeature give a common API across vendors.

Likely follow-ups
  • Types of flags? Release flags (short-lived), ops flags/kill switches (long-lived), experiment flags, and permission flags.
  • Do flags help database changes? Partly: they control which code path reads or writes, which is useful in expand-contract migrations.
What health checks should a service expose so deployments are safe? Intermediate

What the interviewer is testing: whether the application side of safe deployment is understood.

Rollouts and traffic switches depend on the application telling the platform its state honestly. Kubernetes uses three probes. Liveness: is the process stuck beyond repair? If it fails, restart it. Readiness: can it take traffic right now? If it fails, stop sending requests but do not restart. Rolling updates and canaries wait on readiness. Startup: gives slow-starting apps time before the other checks begin. A good readiness check confirms the app can really do its job (it loaded its config, can reach its main dependencies in a light way), but do not make liveness depend on downstream services, or one database blip will restart every pod and make things worse. Also support graceful shutdown: on a termination signal, stop being ready, finish in-flight requests, then exit.

Likely follow-ups
  • A deploy hangs with new pods never ready? Look at the pod logs and events, the readiness path, missing config or secrets, and whether the new version needs a schema that was not applied.
How do you roll back a bad release? Rollback versus roll forward? Senior

What the interviewer is testing: incident judgement. A senior answer says "it depends on state".

The safest first move is the one that restores users fastest and carries least risk. If the release is behind a flag, turn the flag off. If it is a canary, route back to 0 percent. For blue-green, switch the router back. For rolling deployments, redeploy the previous artifact version (kubectl rollout undo or re-run the pipeline pointing at the previous tag). Rollback works well when the previous version still works with the current data. It stops working when the release changed shared state: a database migration that dropped or reshaped something, messages written in a new format, or data already modified. Then you may need to roll forward: ship a quick fix on top instead. Rules that make rollback easy: keep old artifacts available, make deploys repeatable and one-click, make schema changes backward compatible, and rehearse the procedure. Decide the rollback trigger in advance (for example error rate above X for Y minutes) so nobody debates it during an incident.

kubectl rollout undo deployment/orders        # previous revision
kubectl rollout status deployment/orders      # watch it complete
kubectl rollout history deployment/orders
Likely follow-ups
  • Rollback in git terms? Revert the merge commit (a new commit that undoes the change) and let the pipeline redeploy, rather than rewriting main.
  • When is roll forward better? When the bug is small and well understood, or when rollback is unsafe because of data changes.
Common mistakes: a rollback plan that was never tested; assuming "undo" is safe after a destructive migration; debugging live in production before restoring service.

8. Database changes in a pipeline

How do you change a database schema without downtime and without breaking rollback? Senior

What the interviewer is testing: the key reason rollbacks fail, and the standard cure: expand and contract.

The problem: during a rolling or canary release, old and new application code run at the same time against one database, and after a rollback the old code meets the new schema. So every schema change must work with both the old and new code. The pattern is expand and contract (also called parallel change), done over several releases. Take renaming a column name to full_name. Step 1 expand: add the new nullable column, with no code change. Step 2: deploy code that writes to both columns and still reads the old one. Step 3: backfill old rows in batches. Step 4: deploy code that reads the new column. Step 5 contract: once nothing uses the old column and you are past the rollback window, drop it in a later release. Each step is safe to roll back, because the old code still finds what it needs. The cost is more steps and some patience, which is the price of zero downtime.

Likely follow-ups
  • What about adding a NOT NULL column? Add it nullable (or with a default), backfill, and only then add the constraint, because a big table rewrite can lock the table.
  • Why backfill in batches? One huge update can hold locks, fill the transaction log, and cause replication lag.
How are migrations run: Flyway, Liquibase, and in what order relative to the deploy? Intermediate

What the interviewer is testing: migration tooling and the ordering decision.

Tools such as Flyway and Liquibase (also Alembic for Python, Rails and Django migrations, Entity Framework migrations) keep schema changes as versioned files in the repo, for example V12__add_full_name.sql. A table in the database records which versions have been applied, so each runs once, in order, on every environment. This makes the database schema reviewable and repeatable like code. Never edit a migration that has already run anywhere: the tool checks a checksum and will refuse, and other environments would diverge. Add a new migration to fix a mistake instead. Order of operations: with a backward-compatible (expand) change, run the migration before the new code starts, because the old code still works with the new schema. Run it as a separate pipeline step or a one-off job, not by every instance at startup, otherwise several pods race to migrate. The tool's database lock helps, but a long migration then blocks the app start. Contract steps run after all old code is gone.

Likely follow-ups
  • Should every migration have a "down" script? Many teams skip them and rely on roll forward, since a down script is rarely tested and often cannot restore dropped data.
  • How do you test migrations? Run all of them on an empty database in CI, and try them against a copy of production-size data for timing and locks.
A release with a migration must be rolled back. What are the options? Senior

What the interviewer is testing: whether you know rollback is not symmetrical for data.

First look at what the migration did. If it only added things (a nullable column, a new table, an index), roll back the application and leave the schema alone. The old code ignores the extra column. This is the benefit of expand-only releases. If the migration also dropped or changed something that old code needs, the plain rollback fails, so the options are: roll forward with a fix; write and apply a new forward migration that restores compatibility (re-add the column and refill it from the new one); or in the worst case restore from a backup or point-in-time recovery, which loses data written since and is a major decision. Also consider data written by the new version in the new format: old code may not understand it. This is why teams ship destructive changes separately, late, and only after the new version has been stable for a while, and why they take a verified backup before a risky migration.

Likely follow-ups
  • Can the pipeline protect you? Yes: a lint step for migrations that flags destructive statements (DROP, RENAME, non-null without default) and requires explicit approval.
Which schema changes are dangerous on a large live table, and how do you make them safe? Senior

What the interviewer is testing: awareness of locking issues. Deep DBA topics are out of scope, but a developer should know the basics.

Dangerous: changes that rewrite the whole table or hold a lock that blocks reads and writes, such as adding a column with a volatile default on an older engine version, changing a column type, adding a constraint that checks every row, or creating a normal index while writes continue. Behaviour depends on the database and version (PostgreSQL 11 and later add a column with a constant default without a rewrite; MySQL online DDL varies), so check your engine's documentation. Safer habits: add columns as nullable; create indexes with the online option (CREATE INDEX CONCURRENTLY in PostgreSQL); add constraints in two steps (add as not validated, validate later); backfill in small batches with pauses; set a lock timeout so a migration gives up quickly instead of queueing behind a long query and blocking everything else; and run big changes off peak. Tools such as gh-ost or pt-online-schema-change exist for MySQL, which is DBA-level territory.

Likely follow-ups
  • Why can a "quick" ALTER take the site down? It waits for a lock behind a long-running query, and all new queries then queue behind the waiting ALTER.

9. GitOps, infrastructure as code and secrets

What is GitOps, and how is it different from a push-based pipeline? Intermediate

What the interviewer is testing: conceptual understanding, not tool operation.

In GitOps, a Git repository holds the desired state of the environment (for example Kubernetes manifests or Helm values): which image version, how many replicas, which settings. An agent running inside the cluster (Argo CD or Flux are the well-known ones) keeps comparing the cluster with the repository and pulls changes in, so the cluster converges to what Git says. This is the opposite of a push pipeline, where the CI job holds cluster credentials and runs kubectl apply from outside. Benefits: Git is the audit log (who changed what, when, and a review via pull request); rollback is a Git revert; drift is detected and corrected, since manual changes in the cluster get reverted or flagged; and cluster credentials stay inside the cluster, not in CI. Typical flow: CI builds and pushes the image, then opens a commit or pull request that bumps the image tag in the config repo, and the agent deploys it. The depth of running Argo CD itself belongs to the platform team.

Likely follow-ups
  • How do you roll back? Revert the commit in the config repo, and the agent applies the previous state.
  • What is drift? Live state that differs from Git, for example from a manual edit. GitOps tools show it and can auto-correct it.
What is infrastructure as code, and how does it fit into CI/CD? Intermediate

What the interviewer is testing: general awareness a developer should have, not operations depth.

Infrastructure as code (IaC) means describing servers, networks, databases and permissions in files (Terraform or OpenTofu, CloudFormation, Pulumi, Helm charts) instead of clicking in a console. The files live in Git, are reviewed, and are applied by a pipeline. This makes environments repeatable (create a staging copy from the same code), auditable, and reviewable. A typical pipeline for infrastructure: on a pull request run format and validate checks and a plan that shows what would change; after merge and approval run apply. The plan output in the review is the most important safety feature, because it shows if a change will destroy a database. Two cautions: state (Terraform's record of what exists) must be stored remotely and locked so two runs do not corrupt it, and secrets should not be written into state or code. Designing cloud platforms is a specialist topic.

Likely follow-ups
  • Declarative versus imperative? Declarative says what you want and the tool works out the steps (Terraform, Kubernetes manifests). Imperative lists the steps (a shell script).
How should secrets be handled in CI/CD? Intermediate

What the interviewer is testing: security habits that apply on every team.

Principles: never commit secrets to Git, never bake them into images, and give each secret the least scope and shortest life possible. Store them in the CI platform's secret store, or better in a dedicated secret manager (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, Google Secret Manager) and fetch them at run time. Prefer short-lived credentials over static keys: OIDC federation gives a pipeline a temporary cloud token, and applications can use workload identity. Expose a secret only to the single job and step that needs it, and not to builds from untrusted forks. Production secrets should live in the runtime environment of the application (injected at start from the secret manager), not pass through the build. Rotate them regularly, and have a tested way to rotate quickly after a leak. Add scanning (pre-commit hook and CI) to catch secrets before they land, and platform push protection to block them.

Likely follow-ups
  • Environment variable or mounted file? Both are used. Files avoid leaking through process listings and crash dumps in some cases, and make rotation easier; either way, never log them.
  • Is base64 encryption? No. It is only encoding, and Kubernetes Secret objects are base64 unless encryption at rest is configured.
CI masks secrets in logs. Is that enough? Intermediate

What the interviewer is testing: understanding the limits of a convenience feature.

No. Masking is a safety net that replaces the exact secret string in the log with stars. It does not stop a secret leaking in other forms. If a script prints it base64-encoded, URL-encoded, reversed, or split across lines, the match fails and it appears in clear text. A command such as env, set -x (shell trace), or a verbose HTTP client that prints headers can reveal it. Short or common values may not be masked reliably, and structured secrets like a JSON key file are only masked if each part is registered. Test output, error messages, build artifacts, and uploaded debug bundles can also contain a secret. And anyone who can change the workflow can exfiltrate a secret by sending it over the network, which no masking prevents. So treat a secret that appeared in any log as compromised: rotate it. The real defences are scope, short life, and not handing secrets to code you do not trust.

Likely follow-ups
  • How do you stop set -x leaks? Do not use it near secret use, or turn it off with set +x around those lines.
How do you manage configuration that differs between environments? Intermediate

What the interviewer is testing: the "config separate from code" rule from the Twelve-Factor App.

Anything that changes per environment (database host, feature flag defaults, replica count, log level) is configuration. It is kept outside the artifact and supplied at deploy or start time, so the same artifact runs everywhere. Common forms: environment variables, config files mounted into the container (a Kubernetes ConfigMap), Helm values files or Kustomize overlays per environment, or a central config service. Non-secret configuration can live in Git next to the manifests, which makes changes reviewable. Secrets are kept separately, in a secret manager. Keep the set of differences between environments small and explicit, and validate configuration at startup so a missing value fails fast with a clear message, not later at the first request. Also make production changes to configuration go through the same review and pipeline as code, because a config change can break production just as a code change can.

10. Dependency and security scanning

What are SAST, SCA, DAST and secret scanning, and where do they fit in a pipeline? Intermediate

What the interviewer is testing: a developer's working knowledge of security checks ("shift left").

SAST (static application security testing) reads your source code, without running it, to find risky patterns such as SQL built from strings; CodeQL and SonarQube are examples. It runs on pull requests. SCA (software composition analysis) checks the third-party libraries you depend on against databases of known vulnerabilities (CVEs); examples are Dependabot, Snyk, OWASP Dependency-Check, and npm audit. Most of your shipped code is other people's code, so this one finds the most. Container image scanning (Trivy, Grype) does the same for operating system packages in the image. DAST (dynamic testing) attacks a running test deployment from outside, like a scanner or a pen-tester would, and runs against staging. Secret scanning (gitleaks, GitHub secret scanning) finds committed keys. Put fast checks early and blocking, slower ones in a separate job or nightly, and tune the rules, because a tool that floods developers with false alarms gets ignored.

Likely follow-ups
  • What does "shift left" mean? Find problems earlier in the process, when they are cheaper to fix.
  • Should every finding block the build? No. Block on high-severity and exploitable issues, and track the rest with a deadline.
The scanner reports a critical CVE in a dependency. What do you do? Intermediate

What the interviewer is testing: sensible triage, not panic or ignoring.

First I check whether it really applies. Is the vulnerable library actually used, and is the vulnerable function reachable in our code? Is it in the runtime or only in test or build tooling? Is it a direct or a transitive dependency (one pulled in by another library)? Does the exploit need conditions we do not meet? Many "critical" reports are not exploitable in a given app, but I do not decide that alone for a serious one. If it applies, I upgrade to the fixed version, check the changelog for breaking changes, run the tests, and release. For a transitive dependency I can force a version through the build tool (dependency management or overrides in Maven, Gradle, npm) or ask the parent library to update. If no fix exists, I look for a mitigation (a config switch, a WAF rule, removing the feature) and record a time-limited exception with an owner. Everything is documented, and the pipeline keeps the gate so a new vulnerability cannot arrive unseen.

Likely follow-ups
  • How to keep dependencies fresh? A bot (Dependabot or Renovate) opens small update pull requests that CI tests, so updates are routine and not annual big-bang upgrades.
What is software supply chain security, and what can a developer do in the pipeline? Senior

What the interviewer is testing: awareness of attacks on the build itself, such as poisoned dependencies and compromised actions.

Attackers increasingly target what you depend on and how you build, not only your code: a malicious package with a typo-squatted name, a maintainer account takeover, a compromised CI action, or a tampered build. Practical measures at developer level: commit lock files and install from them; pin dependencies and actions (by digest or commit SHA where it matters); use a private proxy or artifact repository so internal package names cannot be hijacked from the public registry ("dependency confusion"); generate a software bill of materials (SBOM, a list of every component, in SPDX or CycloneDX format) so you can answer "are we affected?" quickly; sign artifacts and images (for example with Sigstore's cosign) and have the deploy step verify the signature; produce build provenance (a record of how and where the artifact was built, as in the SLSA framework); run builds on ephemeral runners with minimal permissions. Full programme design is a security-team task, but these are the pipeline parts developers own.

Likely follow-ups
  • What is dependency confusion? An attacker publishes a public package with the same name as your private one and a higher version, so the build fetches the attacker's.
How do you keep container images small and secure? Intermediate

What the interviewer is testing: practical image hygiene for developers.

A smaller image has fewer packages, so fewer vulnerabilities and faster pulls. Use a slim or distroless base image and a multi-stage build so compilers and build tools never reach the final image. Pin the base image by version or digest, and rebuild regularly to pick up patched base layers. Run the process as a non-root user, with a read-only file system where possible. Do not put secrets in layers: a deleted file is still in an earlier layer. Scan the image in CI (Trivy, Grype) and fail on severe findings with a fix available. Add a .dockerignore so .git, local env files and credentials are not copied in by accident. Tag images with the commit SHA, and make sure the scanned image is the same one that is deployed (scan by digest).

11. Branching, trunk-based development and release flow

What is trunk-based development, and why do high-performing teams use it? Intermediate

What the interviewer is testing: the branching model that best supports CI.

In trunk-based development everyone integrates into one main branch (the trunk), using very short-lived branches (hours to a couple of days) or committing directly in small steps. Main is always kept releasable. Unfinished features are merged hidden behind feature flags, or built in small safe steps (branch by abstraction), so the code is integrated even when the feature is not visible. Why it works: small changes are easy to review and easy to revert, merge conflicts are small, and the integration is truly continuous. The research behind DORA found that trunk-based development with few active branches correlates with better delivery performance. What it needs: fast reliable CI, good automated tests, a rule that a broken main is fixed immediately, and the discipline to keep pull requests small. It is hard for teams with long manual QA cycles or weak tests.

Likely follow-ups
  • How do you handle a feature that takes two weeks? Slice it into small safe pieces merged behind a flag, not a two-week branch.
  • What about code review? Small pull requests reviewed within hours. Some teams use pair programming instead.
Trunk-based development versus Git Flow: which would you choose? Intermediate

What the interviewer is testing: a reasoned opinion with trade-offs.

Git Flow has long-lived develop and main branches plus feature, release and hotfix branches. It fits software shipped in versioned releases that need parallel support (installed software, mobile apps with app-store delays, libraries with several supported versions). The cost is long-lived branches that diverge, painful merges, and a gap between "merged" and "released" that delays feedback. Trunk-based development fits web services and anything deployed continuously: one main branch, tiny branches, flags, quick releases. My default for a service is trunk-based with release tags. For products that must support several released versions, I use trunk plus short-lived release branches cut from main only when needed, where fixes are made on main first and cherry-picked back. That is simpler than full Git Flow and keeps CI meaningful. GitHub Flow (feature branch, pull request, merge to main, deploy) sits in between and works well for most teams.

How do you do hotfixes and maintenance of old versions with CI/CD? Senior

What the interviewer is testing: release flow beyond the happy path.

For a continuously deployed service, a hotfix is just a normal tiny change that goes through the same pipeline quickly: fix on main, let the pipeline run, deploy. You do not skip tests to go faster, because a rushed bad fix is how outages double. A well-tuned pipeline makes the normal path fast enough. For software with supported old versions, you cut a release/1.8 branch at release time. A bug is fixed on main first, then cherry-picked (with git cherry-pick -x, which records the source commit) onto the release branches that need it. The release branch has its own pipeline run and tag (v1.8.4). Fixing main first makes sure the bug does not come back in the next version. Keep the number of supported branches small, because every one multiplies the testing and release work.

Likely follow-ups
  • What if the hotfix cannot wait for the full pipeline? Have a pre-agreed, audited fast lane that still runs the essential tests and requires a second person. Not a bypass.
What are branch protection and merge queues, and what problem do they solve? Senior

What the interviewer is testing: how teams keep main green at scale.

Branch protection rules make main safe: require a pull request, at least one approval, passing status checks, an up-to-date branch, and no force-pushes. There is a subtle gap. Two pull requests can each pass CI against an older main, and both merge. Each was green alone, but together they conflict logically (one renames a function, another calls the old name), and main turns red. A merge queue (GitHub merge queue, GitLab merge trains) solves this: approved pull requests enter a queue, and the system tests each one on top of main plus the changes ahead of it in the queue, and merges only if that combined state passes. Main therefore only receives commits that were tested in their final position. The cost is extra CI capacity and a little waiting, which is worth it when many people merge to the same branch.

Likely follow-ups
  • Why not just require "branch up to date before merge"? It works but forces everyone to rebase and re-run CI after every other merge, so it does not scale. The queue automates that.
How do you version and tag releases in an automated pipeline? Intermediate

What the interviewer is testing: repeatable release naming.

Use semantic versioning: MAJOR.MINOR.PATCH, where MAJOR is a breaking change, MINOR is a backward-compatible feature, and PATCH is a bug fix. Automation can compute the next number from commit messages (Conventional Commits such as feat:, fix:, feat!:), using tools like semantic-release or release-please, which also write the changelog. A release is a Git tag on the exact commit, pushed to the remote, which triggers the release pipeline (on: push: tags: ['v*']) that publishes the artifact with that version. Every pipeline run should also embed the commit SHA in the artifact so you can trace it. For services that deploy continuously, a human-friendly version number matters less than the commit SHA, and you may use a date or build number.

Likely follow-ups
  • Should the pipeline commit back to main (for example to bump a version file)? Possible, but it can cause loops and conflicts. Deriving the version from tags avoids it.

12. Delivery metrics (DORA)

What are the DORA metrics, and what do they tell you? Intermediate

What the interviewer is testing: measuring delivery with outcomes, not activity.

DORA (DevOps Research and Assessment, a long-running research programme, now part of Google Cloud) found four metrics that predict software delivery performance. Two measure speed: deployment frequency (how often you release to production) and lead time for changes (from commit to running in production). Two measure stability: change failure rate (the percentage of deployments that cause a problem needing a fix or rollback) and time to restore service (how quickly you recover; newer reports call it failed deployment recovery time). Newer reports also look at rework rate. The important finding is that speed and stability go up together in good teams: shipping small changes often is safer, not riskier. You use the numbers to find bottlenecks, for example a long lead time with a short build time points at slow code review or manual approvals, not at the pipeline.

Likely follow-ups
  • How is lead time measured? From the first commit (or merge) to that change running in production. Define it clearly and use the same definition over time.
How can DORA metrics be misused, and what else do you watch? Senior

What the interviewer is testing: judgement about metrics and incentives.

Metrics turn into targets and then get gamed (Goodhart's law). If you reward deployment frequency, people split work into trivial deployments. If you punish change failure rate, people stop reporting failures or avoid risky but valuable changes. Comparing teams by these numbers ignores context: a firmware team and a web team are different. They are best used by a team to compare itself over time, find its own bottleneck, and start a discussion, not as a ranking or an individual performance measure. I also watch pipeline-level health: build duration, queue time, flaky test rate, mean time to repair a red main, and the share of deployments that were rolled back. And I pair the numbers with some human signals, such as developer satisfaction and how long a pull request waits for review.

Likely follow-ups
  • How do you get the data? From the pipeline and deploy events, the Git history, and the incident tracker. Automate it, because manual collection stops quickly.

13. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

The main branch build is red and ten people are blocked. What do you do? Senior

What the interviewer is testing: priorities during a team-wide blocker: restore green first, investigate second.

Situation: the latest builds on main fail, new pull requests cannot merge, and everyone's feedback is noise.

Check first: is it a real code break, a flaky test, or infrastructure (a registry outage, an expired credential, a full disk)? Compare the last green commit with the first red one. Read the first error in the log. Find out who merged in between.

Steps:

  1. Tell the team in the channel: "main is red, investigating, hold merges". One clear owner leads, to avoid five people fixing at once.
  2. If the cause is a commit, revert it first (git revert SHA through a pull request) and restore green within minutes. The author can re-land a corrected version afterwards. Do not spend an hour debugging forward while everyone waits.
  3. If it is infrastructure, fix or work around it (renew the credential, free the disk, rerun) and say so.
  4. If it is a flaky test, rerun to unblock and quarantine the test with a ticket.
  5. Confirm that main is green again and announce it.

Prevent: require checks before merge, use a merge queue so combined changes are tested together, and keep the rule "fixing a red main beats feature work". Track mean time to green. Do a short blameless review: why did the check not catch it before merge?

Likely follow-ups
  • Why revert and not "fix forward"? A revert is quick and low risk and clears the blockage. Fix forward is fine when the fix is obvious and small and takes minutes.
A test fails randomly about one run in ten and people keep clicking re-run. How do you deal with it? Senior

What the interviewer is testing: turning a nagging problem into a managed one without hiding real bugs.

Situation: a test fails intermittently. Each re-run costs ten minutes, and the team has begun to ignore red builds.

Check first: get the facts. Pull the history of that test: failure rate, which jobs, which runners, what time of day. Read the failure messages for a pattern (timeouts, connection refused, assertion on order). Check whether it fails more with parallel runs or under load.

Steps:

  1. Reproduce locally by running it in a loop with random test order, in the CI container, under CPU limits.
  2. Common root causes to look for: a fixed sleep, a shared database row or static state, an unawaited async call, real time or randomness, a service container not yet ready.
  3. Meanwhile, move the test to a non-blocking quarantine job so it stops blocking merges, with an owner and a date.
  4. Fix the cause (wait for a condition, isolate data, fake the clock) and move it back.
  5. If the flakiness turns out to be a real race condition in product code, that is a production bug, so raise it as one.

Prevent: dashboards of flaky tests, a policy that flaky tests are fixed or quarantined within a week, reports that show retried tests, and new tests reviewed for common flake patterns.

A release went out and error rates are climbing. What do you do in the first 15 minutes? Senior

What the interviewer is testing: incident reflexes: restore service first, find the cause after.

Situation: a deployment finished 10 minutes ago, and error rates and latency are up on the dashboard. Alerts are firing, and customers are affected.

Check first: confirm the link with the release. Does the metric jump line up with the deployment time? Is it the new version only (compare per-version metrics)? Was there another change at the same time, such as a flag, a config change or a dependency outage?

Steps:

  1. Declare an incident, name one incident lead, and post updates in one channel.
  2. Mitigate before diagnosing. Turn off the feature flag if the change is flagged. If it is a canary, send traffic back to 0 percent. Otherwise roll back to the last good artifact (kubectl rollout undo, or redeploy the previous tag).
  3. Before rolling back, check the database: was a migration included, and is the old code compatible with the new schema? If not, plan a roll forward.
  4. Confirm recovery in the metrics, not just "deploy finished".
  5. Collect evidence (logs, traces, the diff of the release) and only then investigate the root cause.

Prevent: progressive rollout with automatic rollback on error-rate thresholds, smaller releases, flags for risky features, and a blameless post-mortem with action items. Note that the "time to restore" is one of the DORA metrics, so a quick, practiced rollback is the best investment.

Common mistakes: debugging live while users keep failing; rolling back without checking the schema; having no agreed trigger for rollback.
A secret shows up in plain text in the CI logs. What do you do? Senior

What the interviewer is testing: correct order: treat as compromised, rotate, then clean.

Situation: someone notices an API token in a job log. Logs may be readable by many people, may be public if the repository is public, and may be copied to log search tools.

Check first: what is the secret, what can it do, and who could see the log? How did it get printed: shell trace, a debug flag, an error message that echoed a header, or a transformed value that masking missed?

Steps:

  1. Rotate or revoke the secret now. Assume it is already compromised, because log scrapers exist. Create the new one through the secret manager.
  2. Check the provider's audit logs for use of the old secret from unexpected places, and escalate to security if there is any.
  3. Delete the log (or the run) and any artifacts or copies, for example in log aggregation, and ask the CI admin to purge it. Deleting does not undo exposure, which is why rotation comes first.
  4. Fix the cause: remove set -x or verbose flags around secret use, stop printing the environment, pass the secret as an environment variable to only the step that needs it.
  5. Add detection: a secret scanner on logs or artifacts, and a test that fails if known patterns appear.

Prevent: short-lived credentials (OIDC), minimal scope per secret, masking as a safety net only, and awareness that base64 or split values escape masking.

The pipeline has grown from 8 to 45 minutes and developers are complaining. What is your plan? Senior

What the interviewer is testing: a data-driven approach to performance in the delivery system.

Situation: feedback is slow, people batch changes into bigger pull requests, and some push without waiting for results.

Check first: measure. Break the 45 minutes into queue time, checkout, dependency install, build, each test stage and publish. Look at the trend, since a single jump points to a specific change. Identify the critical path (the longest chain), because speeding up something off that path changes nothing.

Steps:

  1. Fix cheap wins on the critical path: dependency and Docker layer caches, shallow clone, removing duplicate builds.
  2. Parallelise: independent jobs side by side, and shard the largest test suite using timing data.
  3. Do less per pull request: path filters, affected-module detection in a monorepo, and move the slowest end-to-end and full security scans to main or nightly.
  4. Cancel superseded runs, and add runners if jobs sit in the queue.
  5. Attack the slowest tests themselves: remove sleeps, share setup, replace some end-to-end tests with lower-level ones.
  6. Set a target (for example pull request feedback under 10 minutes) and publish the chart.

Prevent: a budget with an alert when duration crosses a threshold, and an owner for pipeline health, since otherwise it degrades slowly with every added step.

You must roll back a release that included a database migration that dropped a column. What now? Senior

What the interviewer is testing: the hardest rollback case, and the prevention pattern.

Situation: release 2.4 renamed name to full_name by dropping and recreating the column in one migration. The new code has a bug. The old code expects name, which no longer exists, so a plain rollback of the application would crash.

Check first: how bad is the new bug, and can it be fixed forward quickly? What data was lost or changed? Is a backup or point-in-time restore available, and since when? How much new data has been written since the migration?

Steps:

  1. Mitigate users first if possible: turn off the broken feature with a flag, or take the affected function into a safe degraded mode.
  2. Prefer roll forward: fix the bug and ship quickly.
  3. If the old version is truly needed, write a new forward migration that re-adds name and fills it from full_name, apply it, and then roll back the application. Test this on a copy of production data first.
  4. Only as a last resort restore from backup, accepting the loss of data written after the backup, which needs business agreement.

Prevent: expand and contract: add full_name, dual write, backfill, switch reads, and drop name in a later release after the rollback window. Add a migration linter that blocks DROP and RENAME without explicit approval, and take a checked backup before any destructive step.

Tests pass on your laptop but fail in CI. How do you find out why? Intermediate

What the interviewer is testing: a method for environment differences, not guesswork.

Situation: a pull request is red in CI with an error you cannot reproduce locally.

Check first: read the first error and the exact command. List the differences between environments: operating system, language and tool versions, environment variables, file system case sensitivity, time zone and locale, available CPU and memory, network access, test order and parallelism, and files that are git-ignored but present on your machine.

Steps:

  1. Print versions and environment safely in the CI job and compare with local.
  2. Run the same container image CI uses, with the same command, on your machine. This reproduces most issues.
  3. Do a clean clone locally, install from the lock file, and run again. A missing committed file shows up at once.
  4. Try random test order and parallel mode, and run the failing test in a loop.
  5. Check for hidden state: a local database with leftover data, a cache directory, a global package.

Prevent: pin tool versions, commit lock files, use the same container for local and CI builds (dev containers or a build script that both call), and keep CI scripts runnable by hand as make test.

A rolling deployment is stuck halfway: new pods keep crashing and the old ones are still up. What do you do? Senior

What the interviewer is testing: debugging a failing rollout and knowing that the platform protects you.

Situation: the pipeline's deploy step has been waiting for a long time. Some pods run the new version and restart repeatedly. The old pods still serve traffic because the rollout waits for new ones to become ready.

Check first: users are mostly fine, since readiness stops broken pods from receiving traffic, so there is time to investigate. Look at the status and the logs of the failing pods.

Steps:

kubectl rollout status deployment/orders
kubectl get pods -l app=orders
kubectl describe pod orders-7d9f...      # events: image pull, probe failures, OOMKilled
kubectl logs orders-7d9f... --previous   # logs of the crashed container
  1. Common causes: missing or wrong config or secret, a failed database connection or migration not applied, an image tag that does not exist, a wrong readiness path, too little memory (OOMKilled), and a startup slower than the probe allows.
  2. If the fix is not quick, abort with kubectl rollout undo deployment/orders and set the pipeline job to fail so nobody believes it succeeded.
  3. Fix the cause and redeploy.

Prevent: deploy jobs that wait for rollout status and fail on timeout (progress deadline), a config validation step at startup, a smoke test after deploy, and a staging rollout with the same config shape.

A critical bug is in production on Friday afternoon and the full pipeline takes 40 minutes. May you skip it? Senior

What the interviewer is testing: discipline under pressure, and judgement about process.

Situation: customers are affected now. Someone suggests deploying from a laptop to skip the slow tests.

Check first: can you stop the harm without a code change: flag off, config change, rollback to the previous release? That is faster and safer than a new build.

Steps:

  1. Mitigate with the quickest reversible action first.
  2. If a code fix is needed, make the smallest possible change, in a normal pull request, with a second reviewer even if quick.
  3. Use the pipeline. If it is too slow, use a pre-agreed fast lane that still runs build, unit and smoke tests but skips long end-to-end or nightly suites, and is recorded and approved. Never deploy from a laptop: that artifact is untraceable and was not tested the same way.
  4. Deploy gradually (canary) and watch the metrics.
  5. Follow up with the full pipeline run and a note in the post-mortem.

Prevent: make the normal pipeline fast enough, have the fast lane defined before it is needed, and keep rollback one click away. Skipping checks to go faster is how a one-bug incident becomes two.

A new critical vulnerability is announced in a library used by many of your services. How do you respond? Senior

What the interviewer is testing: triage and fast, safe rollout across services.

Situation: a widely used library has a remote-code-execution flaw, with public exploits.

Check first: which of our services use the library, directly or through another dependency, and which versions? An SBOM or a dependency search across repositories answers this fast. Which services are internet-facing, and is the vulnerable code path reachable?

Steps:

  1. Rank services by exposure: public-facing first, internal later.
  2. Look for a quick mitigation while you patch (a config switch, a WAF rule, disabling the feature).
  3. Upgrade to the fixed version. For a transitive dependency, force the version in the build tool. Let a bot open the pull requests in all repos, and let CI test each one.
  4. Deploy with the normal pipeline, but prioritised. Verify the deployed version in production (check the image digest or the SBOM), not just the merge.
  5. Look in the logs for signs of exploitation before the fix.

Prevent: an SBOM for every build, automated dependency update pull requests, scanning gates in CI, and a regular habit of small upgrades so a big jump is not needed under pressure.

A build suddenly fails with a strange error, and a re-run on another branch passes. You suspect the cache. What do you do? Intermediate

What the interviewer is testing: diagnosing stale or corrupted cache, and safe invalidation.

Situation: after a dependency update, builds on one branch fail with missing classes or a version mismatch, while a fresh clone builds fine.

Check first: did the cache key change when the dependency file changed? Compare the logs: "cache restored from key X" and which restore-key fallback was used. A fallback to an older cache with a new lock file can leave old files behind.

Steps:

  1. Prove it: run the job with the cache disabled or with a changed key. If it passes, the cache is the cause.
  2. Bust it: bump a version prefix in the key (v2-deps-...), or delete the cache entry through the CI UI or API.
  3. Fix the key so it includes everything that affects the content: the lock file, the tool version, the operating system.
  4. Do not cache build outputs that the tool should rebuild itself, only downloaded dependencies.

Prevent: include a clean build on main nightly (no cache) to catch cache-masked problems, and limit cache sharing from untrusted branches.

A third-party action your pipelines use is reported as compromised. What do you do? Senior

What the interviewer is testing: supply-chain incident handling in CI.

Situation: a popular action had a malicious version published that dumps environment variables, including secrets, to an attacker. Your workflows used it by a moving tag.

Check first: which repositories use the action, in which workflows, and during what time window did runs fetch the bad version? What secrets and tokens were available to those runs?

Steps:

  1. Stop the exposure: disable the affected workflows, or pin to a known-good commit SHA or remove the action.
  2. Assume every secret that was available to runs in the window is stolen. Rotate them all, starting with cloud credentials and publishing tokens. Review the audit logs for use of those credentials.
  3. Check what the runs could write: were any releases, packages or images published with a tampered state? Verify and re-publish if needed.
  4. Communicate to the security team and, if required, to customers.

Prevent: pin third-party actions to full commit SHAs, use an allow-list of actions for the organisation, give jobs minimal permissions, prefer OIDC short-lived credentials so there is less to steal, and use a bot to review updates of pinned actions.

Two merges happen within a minute and the deploys overlap. Production ends up on the older version. How do you prevent that? Senior

What the interviewer is testing: race conditions in the delivery process itself.

Situation: commit A is merged, then commit B. Both pipelines deploy. The pipeline for A was slower and finished last, so production now runs A, although B is newer.

Check first: what version is really running (the image tag or digest in the cluster), and what does the deployment history say? Fix production first by redeploying B.

Steps:

  1. Redeploy the intended version (B) and verify it.
  2. Serialise deployments per environment: use a concurrency group such as deploy-prod with cancel-in-progress: false in GitHub Actions, resource_group in GitLab, or disableConcurrentBuilds in Jenkins.
  3. Make the deploy step refuse to deploy an older commit than what is live (compare the ancestry), or have the queue skip to the newest.
  4. Better still, use GitOps: the desired version is a single value in a Git file, and the agent applies the latest, so ordering is Git history.

Prevent: serialised deploys, a "currently deployed version" page or annotation on dashboards, and deployments that are idempotent (running the same deploy twice gives the same result).

In a monorepo, every pull request runs all tests for all 40 services. How do you fix it? Senior

What the interviewer is testing: scaling CI with repository size.

Situation: a one-line change in one service triggers a 50-minute pipeline for everything, and the CI bill is large.

Check first: understand the dependency graph between modules. Which services depend on shared libraries? A wrong "skip" is worse than a slow build.

Steps:

  1. Detect what changed against the merge base (git diff --name-only origin/main...HEAD) and map files to modules.
  2. Run only the affected modules and everything that depends on them. Use paths filters or rules:changes for simple cases, or a build tool that understands the graph (Bazel, Nx, Gradle with build caching, Turborepo).
  3. Use a remote build cache so unchanged modules are not rebuilt or retested.
  4. Run the complete suite on main or nightly as a safety net, and keep a merge queue so the combination is tested.
  5. Make sure a change to a shared library triggers its dependants.

Prevent: clear module ownership and boundaries, and a check that path filters stay in step with the real dependencies.
