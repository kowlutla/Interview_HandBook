How to use this page

Click a question to open the answer. Try to answer aloud first, in about 60 to 90 seconds. At senior level the interviewer is not testing whether you know the word "microservice"; they test whether you can say when NOT to use it, what it costs, and how you would move safely from one shape to another. Always tie a decision to a reason (team size, change rate, scaling shape, failure isolation) and name the trade-off. A separate page covers the developer-level mechanics (Spring, REST, resilience annotations); this one is about architecture decisions.

1. Monolith, modular monolith, microservices

What is a monolith, and is it always bad? Basic

A monolith is one deployable unit: all features are built, tested, released and scaled together, usually over one database. It is not "bad". It has simple local calls (a method call, not a network hop), simple transactions (one ACID database), easy debugging (one stack trace) and cheap operations (one thing to run).

It hurts when the codebase and the team outgrow it: builds take 40 minutes, any change risks everything, one team's bug blocks everyone's release, and you cannot scale the hot 5 percent of the code without scaling the other 95 percent.

Say: "A well-structured monolith is the right default for a new product. I would split only when I can name the pain: team contention, different scaling shapes, or failure isolation."
Compare monolith, modular monolith and microservices. When does each win? Intermediate

A modular monolith is often the best stepping stone: it gives you the boundaries of microservices without the distributed-systems tax, and each module can later be extracted along a seam you already enforce.

When should you actually choose microservices? Intermediate

Good reasons:

  • Many teams (rule of thumb: beyond roughly 30 to 50 engineers) stepping on each other in one codebase and release train.
  • Parts of the system have very different scaling shapes (image processing vs account settings) or different tech needs (a Python ML scorer next to a Java core).
  • Failure isolation: a recommendation outage must not take down checkout.
  • Regulatory isolation: payment or health data in a tightly controlled boundary.
  • Boundaries are well understood and stable.

Bad reasons: "it is modern", resume-driven design, a team of 6, or an unclear domain. Splitting before you know the boundaries freezes wrong boundaries into network contracts, which are far costlier to change than package boundaries.

A startup asks: monolith or microservices on day one? Senior

Start with a modular monolith. On day one you do not know where the real boundaries are, you have 3 to 8 engineers, and your biggest risk is product-market fit, not scale. Keep strict internal module boundaries (each module owns its tables, talks to others only via a public interface or domain events). Add architecture tests (ArchUnit or equivalent) that fail the build when a module reaches into another's internals. Extract a service only when a concrete trigger appears: a module needs independent scaling, a team needs independent release cadence, or a failure domain must be isolated.

Trap: Saying "monolith" and stopping. Interviewers want to hear that you keep the seams clean so extraction later is cheap.
What is a distributed monolith and how do you recognise one? Intermediate

A distributed monolith is a system split into many services that still must be changed, deployed and often failed together. You paid the full network and operations cost and got none of the independence.

Symptoms:

  • A feature change needs coordinated edits and a lock-step release of 4 services.
  • Services share one database or reach into each other's tables.
  • Long synchronous call chains: A calls B calls C calls D; one slow node stalls all.
  • A shared "common" library with domain objects forces everyone to upgrade together.
  • You need an environment with all services up to test anything.
  • A release needs a "deployment order" document.

Fixes: redraw boundaries around business capabilities (not technical layers), give each service its own data, replace chains with events or data replication where staleness is acceptable, and add consumer-driven contracts so services can ship independently. Sometimes the honest fix is to merge the services back into a modular monolith.

What are nanoservices and why are they a problem? Intermediate

Nanoservices are services so small that the overhead (deploy pipeline, network hop, monitoring, on-call, versioning) outweighs the logic inside. A "TaxCalculator service" with one function is the standard example. Each extra service adds latency, a failure point and operational load. Size by business capability and team ownership, not lines of code. A useful sanity test: can one team own it end to end, and does it change for a reason independent of its neighbours?

How big should a microservice be? Intermediate

No line-count rule works. Practical heuristics:

  • One bounded context or a coherent part of it, owned by one team ("two-pizza team" idea).
  • It can be rewritten in a few weeks if needed, not months.
  • It changes for one family of business reasons (single responsibility at service level).
  • It rarely needs to be changed in lock-step with another service.
  • One team can keep its full cognitive load: code, runbook, on-call.

2. Service boundaries and domain-driven design

How do you decide service boundaries? Senior

Split by business capability and bounded context, not by technical layer (no "database service", "UI service"). Practical methods:

  1. Event storming: workshop with domain experts; list domain events (OrderPlaced, PaymentCaptured) on a wall, cluster them, and the clusters hint at contexts.
  2. Look for language changes: when "customer" means something different (billing account vs shipping recipient vs support contact), you have crossed a context boundary.
  3. Follow change patterns: things that change together belong together; things that change independently can be apart.
  4. Follow data: who is the single writer of each fact? That owner is the service.
  5. Follow teams: boundaries should align with ownership (Conway's law, covered below).
  6. Measure coupling: if two candidate services chat constantly or need joint transactions, they are probably one service.
What is a bounded context? Give an example. Intermediate

A bounded context is an explicit boundary inside which a domain model and its vocabulary are consistent. The same word can mean different things in different contexts, and that is fine as long as each context has its own model.

Example in e-commerce: "Product" in Catalog has description, images, categories; in Inventory it is a SKU with stock counts per warehouse; in Pricing it is a price rule target; in Shipping it is weight and dimensions. Trying to make one giant shared Product class serves nobody. Each context holds its own small model and they exchange IDs and events. Contexts relate through patterns such as customer/supplier, anticorruption layer (translate the other model at the edge) and published language (an agreed event or API schema).

What is an aggregate, and why does it matter for service design? Intermediate

An aggregate is a cluster of objects treated as one consistency unit with a single root (for example Order with its OrderLines). All invariants inside it ("total equals sum of lines", "cannot add lines after shipping") are enforced in one transaction. Outside access goes through the root only, and other aggregates are referenced by ID, not by object link.

Architecture consequences:

  • An aggregate never spans services; a transaction boundary should not cross the network.
  • Keep aggregates small; large ones create contention and slow writes.
  • Consistency between aggregates is eventual (via events or sagas).
  • If two aggregates must always change atomically, that is a sign they are one aggregate (or one service).
What is a context map and the anticorruption layer? Senior

A context map documents how bounded contexts relate: shared kernel (a small co-owned model, risky), customer/supplier (upstream commits to downstream needs), conformist (downstream just accepts upstream's model), open host service with published language (stable public API), and anticorruption layer (ACL).

An ACL is a translation layer on the consuming side that converts a foreign or legacy model into your own, so the legacy concepts never leak into your domain. It is the key tool when integrating with a legacy monolith or a vendor API, and during strangler migrations.

Why is the "entity service" (one service per database table) an anti-pattern? Intermediate

A CustomerService, OrderService, AddressService that are just CRUD over tables push all real logic into callers, so every business operation becomes a multi-service orchestration with chatty calls and no transaction. Business capability services (Checkout, Fulfilment, Billing) own behaviour and the data needed for it. If your services' APIs look like GET /addresses/{id} and PUT /customers/{id} only, you probably cut by noun, not by capability.

Many services need the same data (country list, user profile name). Who owns it? Intermediate

One service owns it (single writer). Consumers choose among:

  • Call on demand (simple, but adds runtime dependency and latency).
  • Cache with TTL (good for slow-changing reference data).
  • Replicate via events: the owner publishes UserRenamed; consumers keep a local read copy with just the fields they need. Fast and resilient, eventually consistent.
  • Embed in tokens or messages (user id and display name in the JWT or event) when staleness is harmless.

Never let a consumer write into the owner's tables.

3. Data ownership and consistency

What is database per service and why is it the rule? Basic

Each service owns its data store privately; the only way to read or change its data is through its API or events. "Private" can be a separate schema with separate credentials; separate physical servers are optional and depend on scale and isolation needs.

Why: it lets each service change its schema freely, pick the right store (relational, document, search, cache), scale and fail independently, and prevents hidden coupling through tables. The cost: no cross-service joins or ACID transactions, so you use API composition, CQRS views, events and sagas.

Why is a shared database an anti-pattern? When might you tolerate it? Intermediate

When two services read or write the same tables, the schema becomes an unversioned public API. A column rename breaks another team silently; a slow query from one service locks rows the other needs; you cannot change the storage engine; ownership of invariants is unclear (who enforces "balance cannot go negative"?). It is the most common reason a split produces a distributed monolith.

Tolerable cases: a transitional phase during migration (both old monolith and new service use the table while you move writes), or read-only reporting access to a replica or warehouse copy. Even then, put a deadline on it.

Trap: "One database server with separate schemas" is not a shared database anti-pattern, as long as access is not crossed. The anti-pattern is shared access to the same tables.
How do you do a query that needs data from several services (for example an order page with customer, items and shipment status)? Intermediate

Three main approaches:

ApproachHowProsCons
API compositionA composer (gateway, BFF or aggregator service) calls each service in parallel and mergesSimple, always freshLatency is the slowest call; partial failure handling; no cross-service sort/filter on big sets
CQRS read modelA query service subscribes to events from all services and builds its own denormalised viewFast, can filter/sort/search, isolates read loadEventually consistent; more moving parts; rebuild logic
Data replication of small slicesEach service keeps the few fields it needs from othersNo runtime callStaleness and duplicate data

Pick composition for small, recent, per-entity views; CQRS views for search, lists, dashboards and large joins.

How do you keep data consistent across services without distributed transactions? Senior

Two-phase commit across services is avoided: it blocks on coordinator failure, holds locks across the network, and many stores and brokers do not support it. Instead use a saga: a sequence of local transactions, each publishing an event or command that triggers the next; if a step fails, run compensating actions that semantically undo previous steps (refund payment, release stock).

  • Choreography: services react to each other's events. No central brain, loosely coupled, but the flow is implicit and hard to see or debug as it grows.
  • Orchestration: a coordinator (saga orchestrator or workflow engine) tells each service what to do and tracks state. Flow is explicit and testable; the orchestrator is an extra component and risks absorbing business logic.

Rules of thumb: choreography for 2 to 4 steps, orchestration for longer or branching flows. Every step and compensation must be idempotent, because messages are delivered at least once. Design for visible intermediate states (order "PENDING"), because sagas are not isolated: other readers can see half-done work.

What if a saga step cannot be undone (an email was sent, a parcel shipped)? Senior

Order steps so the irreversible ones come last (the "pivot" step), after everything that can fail has succeeded. Use a reservation first (hold stock, authorise the card) and commit later (capture). For truly external effects, compensate semantically (send a correction email, create a return). Some failures need a human: route to a manual review queue with full saga state.

How do you atomically update your database and publish an event? Senior

Writing to the DB and then to the broker is two operations; a crash between them loses or duplicates the event (dual-write problem). Use the transactional outbox: in the same local transaction, write the business row and an "outbox" row; a relay (poller or change-data-capture reading the log, for example Debezium) publishes outbox rows to the broker and marks them sent. Delivery is at least once, so consumers must be idempotent (dedupe by event id). The mirror for inbound is an inbox table recording processed message ids.

Business says "the page must always be correct". How do you handle eventual consistency? Senior

First ask which screens truly need strong consistency; usually few do. Then:

  • Keep strongly related data in one aggregate/service so it is transactionally consistent.
  • Read-your-writes: after a user action, return the new state from the write response or route that user's next read to the source of truth for a short time.
  • Show honest intermediate states ("payment pending").
  • Version or timestamp events so consumers drop stale ones.
  • Reconciliation jobs that detect and repair drift.

4. Communication, gateway, mesh, discovery

What communication styles exist between services and how do you choose? Intermediate
StyleExamplesUse whenWatch out
Synchronous request/responseREST, gRPCCaller needs the answer now (price check, auth)Temporal coupling: callee down means caller degraded; latency adds up
Asynchronous messaging (commands)Queue (SQS, RabbitMQ)Work can be done later; load levellingNo immediate result; need status tracking
Event publish/subscribeKafka, SNS topicsMany consumers react to a fact; decouplingHard to trace flow; schema evolution; ordering
Streaming / bidirectionalgRPC streams, WebSocketContinuous dataConnection state, back-pressure

Rule: use sync for queries that need a fresh answer and for user-facing request paths with short chains (depth 1 to 2); use async for anything that crosses a consistency or availability boundary or fans out. Availability of a sync chain is the product of each hop: five services at 99.9 percent each give about 99.5 percent.

REST vs gRPC vs messaging between internal services? Intermediate
  • REST/JSON: universal, easy to debug and cache, good for public and cross-organisation APIs; text payload is bigger and slower to parse.
  • gRPC (HTTP/2, Protobuf): compact binary, strong typed contract generated into clients, streaming, deadlines built in; harder to call from a browser and to inspect by hand. Good for internal high-volume, low-latency calls.
  • Messaging: decouples in time; best for events and work queues.

Many systems use REST at the edge, gRPC inside, and events for propagation.

Event-driven vs request-driven architecture: when do you pick which? Senior

Request-driven: caller asks, waits, gets an answer. The flow is explicit and easy to follow. Event-driven: a service emits a fact ("OrderPlaced") and any number of others react, unknown to the producer.

AspectRequest-drivenEvent-driven
CouplingCaller knows calleeProducer does not know consumers
Adding a consumerChange the callerJust subscribe
AvailabilityBoth must be upBroker buffers while consumer is down
DebuggingStraight traceNeeds correlation ids, flow is emergent
ConsistencyImmediateEventual
Failure shapeErrors to the callerPoison messages, lag, duplicates, out-of-order

Choose events for notifications, fan-out, cross-context data propagation and integration; choose requests for queries and commands needing an immediate result. Most real systems are hybrid. Distinguish a command ("ChargeCard", addressed, one handler) from an event ("CardCharged", past tense, anyone may listen); sending commands disguised as events produces hidden coupling.

What kinds of events exist (notification, event-carried state transfer, event sourcing)? Senior
  • Event notification: thin event ("OrderPlaced id=42"); consumers call back for details. Small, but creates call-back coupling.
  • Event-carried state transfer: event contains the data consumers need, so they keep local copies and never call back. More resilient, bigger schema surface.
  • Event sourcing: the event log itself is the source of truth; state is derived by replay. Powerful audit and time travel, but heavy: schema evolution of old events, snapshots, learning curve. Do not adopt it just to publish events.
What are API composition and Backend for Frontend (BFF)? Intermediate

API composition: one component calls several services and combines results for a client, so the client does not make 8 calls. BFF: a dedicated backend per client type (mobile BFF, web BFF, partner API), owned by the frontend team. It shapes payloads for that client (mobile wants small responses, web wants rich ones), hides service topology, and lets the frontend team ship without waiting on a central API team.

Risks: BFFs duplicate logic if you put business rules in them (keep them thin: aggregate, translate, auth, no domain rules), and one big shared "gateway" owned by a central team becomes a bottleneck. Aggregation should call downstream in parallel with timeouts and return partial results when a non-critical dependency fails.

API gateway vs service mesh: what is the difference? Senior
API gatewayService mesh
TrafficNorth-south (clients into the system)East-west (service to service)
Typical jobsAuthentication, rate limiting, routing, TLS termination, request transformation, API keys, versioned public routesmTLS between services, retries, timeouts, circuit breaking, load balancing, traffic splitting (canary), telemetry
PlacementCentral edge componentProxy beside every service (sidecar) plus a control plane
OwnerAPI / platform teamPlatform team

They complement each other. A mesh adds latency (an extra hop on each side, typically sub-millisecond to a few ms), memory per pod and an operational learning curve; it pays off with many services and a need for uniform mTLS and policy without changing app code. With 5 services, library-level resilience and plain TLS is usually enough. Newer "ambient" or sidecar-less modes exist in some meshes to cut the per-pod cost.

Trap: Putting business logic in the gateway. It should be a thin edge, not an orchestration layer.
What is the sidecar pattern and why use it? Intermediate

A sidecar is a helper process deployed next to the main service in the same unit (same pod, shared network and lifecycle). It handles cross-cutting concerns outside the app code: proxying and mTLS (Envoy), log shipping, config reload, secrets fetch, metrics export. Benefits: language-agnostic (works for Java, Go and Python apps alike), upgradable independently of app code, consistent behaviour. Costs: extra CPU and memory per instance, startup ordering issues, more things to debug. Related shapes: ambassador (outbound proxy to a remote service) and adapter (normalises output, for example metrics format).

How does service discovery work? Client-side vs server-side? Intermediate

Instances come and go (autoscaling, deploys, crashes) with changing IPs, so callers need a way to find healthy ones.

  • Registry-based: instances register themselves (Eureka, Consul) and send heartbeats; the registry drops silent ones.
  • Client-side discovery: client fetches the instance list and load-balances itself (Ribbon-style). Flexible, but every language needs the library.
  • Server-side discovery: client calls a stable name or load balancer which picks an instance (cloud load balancers, Kubernetes Service). Simpler clients.
  • Platform-native: in Kubernetes, a Service gives a stable virtual IP and DNS name, and readiness probes decide which pods receive traffic; usually no separate registry is needed.

Pitfalls: stale entries (a dead instance still listed for a few seconds), DNS caching in the client runtime, and health checks that report "up" while dependencies are down. Pair discovery with timeouts and retries on idempotent calls.

Your checkout request goes through 6 services synchronously and p99 latency is 4 seconds. What do you do? Scenario
  1. Trace it (distributed tracing) to see which hop dominates and whether calls that could be parallel are serial.
  2. Parallelise independent calls; add per-call deadlines (budget the 4 seconds across hops).
  3. Remove calls from the critical path: pre-compute, cache slow-changing data, replicate small read copies via events.
  4. Move non-essential work (email, analytics, loyalty points) to async events.
  5. Question the boundaries: if two services always call each other for one user action, merge them.
  6. Add timeouts, circuit breakers and fallbacks so a slow non-critical hop degrades rather than blocks.

5. Migration and decomposition

What is the strangler fig pattern? Intermediate

Named after a vine that grows around a tree and eventually replaces it. You put a routing layer (proxy or gateway) in front of the legacy system. New or rewritten functionality is built as new services; the router sends that slice of traffic to the new code, everything else still goes to the monolith. Slice by slice the legacy shrinks until it can be switched off.

Why it works: small reversible steps, value delivered continuously, no big-bang cutover. Compare with a big-bang rewrite, which stops feature delivery for months, hits the "second system" trap and often never reaches parity.

How do you decompose a monolith safely? Give the steps. Senior
  1. Make it observable and tested first: you cannot compare old and new behaviour without metrics, logs and regression tests.
  2. Pick seams: choose modules with clear business meaning, low coupling and high business value or pain (a hot-scaling part, a part with churn). Start with an edge capability (notifications, search, reporting) rather than the tangled core; learn the process on something low-risk.
  3. Modularise inside the monolith first: enforce module boundaries and make the module talk to the rest via an interface; this is cheap to revert.
  4. Untangle data: find the tables the module uses; remove foreign keys and joins across the seam; replace with API calls or replicated data.
  5. Extract: build the service, add an anticorruption layer so legacy concepts do not leak, place the router in front.
  6. Migrate data and traffic gradually: shadow traffic (new service receives copies, results compared but discarded), then canary percentage, then full cutover. Use dual writes carefully or, better, change data capture to sync.
  7. Keep a rollback until the new path has run clean for a defined period; then delete the old code (do not leave dead code).
  8. Repeat; track progress by "routes or tables moved" and stop when the remaining monolith is small enough to be a service itself.
How do you split a shared database during extraction? Senior
  1. Map which code reads and writes which tables (static analysis plus query logs).
  2. Give each table one owner. For tables used by both sides, decide the owner and make the other side use the owner's API or a replicated copy.
  3. Replace cross-boundary foreign keys with IDs only and handle referential integrity in code or events.
  4. Temporary phase: new service has its own schema, kept in sync from the monolith via change data capture or a sync job; reads switch first, then writes, in that order.
  5. Verify with comparison jobs (row counts, checksums), then stop the sync and drop the old columns.

Hard parts: joins and reports that span the seam (move them to a read model or warehouse), and transactions that spanned both sides (become sagas or are redesigned).

What are branch by abstraction and parallel run? Senior

Branch by abstraction: when you cannot route at the network edge because the call is deep inside the monolith, introduce an interface in front of the functionality, implement it with the old code, then add a second implementation that calls the new service, and switch between them with a feature flag. Parallel run: run both implementations on the same input, return the old result, and compare outputs offline to find differences before trusting the new one. Together they allow safe, reversible, testable cutovers.

Management wants a full rewrite as microservices in 12 months. What do you say? Scenario

Explain the risks: the old system keeps changing while you rewrite, so you chase a moving target; hidden behaviour in old code (edge cases nobody documented) gets lost; no value ships until the end; the team runs two systems. Propose a strangler approach with milestones that each deliver value: for instance month 1 to 2 observability and routing layer; then extract the highest-pain module; measure improvements (deploy frequency, lead time, incident rate) to justify continuing. Define a stopping rule: it is fine if a stable core stays as a monolith.

6. Versioning, compatibility, contracts

How do you change an API or event between services without breaking consumers? Senior

Because services deploy independently, the producer and consumer versions overlap in production. So changes must be compatible in both directions during rollout.

  • Backward compatible (safe) changes: add optional fields, add new endpoints, add new enum values only if consumers ignore unknowns, loosen validation.
  • Breaking changes: remove or rename a field, change type or meaning, make an optional field required, tighten validation, change semantics silently.
  • Tolerant reader: consumers ignore unknown fields and do not depend on fields they do not need (Postel's law: be liberal in what you accept).
  • Expand and contract (parallel change): (1) expand: add the new field/endpoint, keep the old; (2) migrate consumers one by one; (3) contract: remove the old when metrics show zero use.
  • Versioning: when a break is unavoidable, introduce /v2 (or a new event type/schema version) and run v1 and v2 side by side with a published sunset date.

For events with Avro or Protobuf, use a schema registry with a compatibility mode (backward, forward or full) enforced in CI, and never reuse a Protobuf field number.

Rolling deploy: consumer needs a new field the producer is adding. In what order do you deploy? Senior

Producer first, adding the field as optional (old consumers ignore it). Then deploy the consumer that uses it, with a fallback if the field is missing (in case of rollback or lagging instances). Only later make it mandatory, if ever. The reverse for removal: stop consumers reading it, then remove from producer. If you ever need "deploy A then B within minutes" you have a coordination problem; redesign so each step is independently safe.

What is contract testing and why not just end-to-end tests? Intermediate

Consumer-driven contract testing (for example Pact) works like this: each consumer records what it expects from a provider (requests and the response fields it uses) as a contract; the provider's CI replays all consumer contracts against its real code and fails if any would break. Each side tests alone, fast, with no shared environment.

End-to-end tests across many services are slow, flaky, need everything deployed, and fail without telling you which service is at fault. Use a test pyramid: many unit tests, contract tests at service boundaries, a few integration tests per service with stubbed neighbours, and a very small number of end-to-end smoke tests on critical journeys. Contracts are not a substitute for behaviour tests of the provider's own logic; they check shape and the used subset.

Shared libraries vs duplication across services? Senior

Duplication of small, stable code is often better than coupling. A shared library that carries domain models or business rules couples release cycles: change it and every service must upgrade, which recreates the distributed monolith.

  • Fine to share: technical, stable, non-domain code (logging setup, tracing, auth token validation, HTTP client defaults), ideally thin and versioned semantically. Better still, move such concerns to the platform (sidecar, base image, mesh).
  • Avoid sharing: DTOs of other services, entity classes, validation of business rules. Generate client code from the owner's published API schema instead of sharing a hand-written jar.
  • If shared, treat it as a product: versioned, backward compatible, with an owner, and consumers may upgrade on their own schedule (never force lock-step).

"Don't repeat yourself" applies within a service; across services, the coupling cost often exceeds the duplication cost.

URL, header or media-type versioning: which and why? Intermediate

URL (/v2/orders): most visible, easy to route and cache, popular for public APIs. Header or media-type (Accept: application/vnd.x.v2+json): cleaner URLs, harder to test by hand. Query param: simple but easy to forget. The choice matters less than the discipline: version rarely, prefer additive evolution, support at most two or three versions, publish a deprecation policy and track per-consumer usage so you know who still calls v1.

7. Teams, Conway's law, platform engineering

What is Conway's law and how does it influence architecture? Intermediate

"Organisations design systems that mirror their communication structure." If you have separate frontend, backend and database teams, you get layered systems where every feature crosses three teams. If you have three teams you will likely end up with three components, whatever the diagram says.

The inverse Conway manoeuvre: shape the teams first to get the architecture you want. Create cross-functional, stream-aligned teams that own a business capability end to end (code, data, deploy, on-call), and the service boundaries follow. Practical rule: a service should have one owning team, and a team may own several services, but a service should never need three teams to change.

What are the team types in Team Topologies? Senior
  • Stream-aligned team: delivers a flow of business value (checkout, onboarding); owns services end to end.
  • Platform team: provides internal self-service capabilities that reduce the cognitive load of stream teams.
  • Enabling team: temporary coaches that help others adopt a skill (security, SRE practices).
  • Complicated-subsystem team: owns a part needing deep specialist knowledge (video codec, pricing engine).

Interaction modes: collaboration (short-term, high bandwidth), X-as-a-Service (consume via clear API), facilitating. The key idea is limiting each team's cognitive load, which is what ultimately caps how many services a team can own.

What is platform engineering and why do microservices need it? Intermediate

Each new service needs a repository, CI/CD pipeline, container build, monitoring, alerts, secrets, service discovery, access control. If every team builds this alone, you get 40 snowflake setups. A platform team builds an internal developer platform: self-service "golden paths" (templates, scaffolding that creates a service with pipeline, dashboards and security defaults in minutes), shared tooling (build, deploy, observability, secrets), and a service catalogue showing owners, dependencies and runbooks.

Principles: treat the platform as a product with internal customers; make the paved road the easiest road but allow opt-out for good reasons; measure adoption and time to first deploy. Without a platform, microservices cost grows linearly or worse with service count; with one, the marginal cost of a service drops sharply.

What does "you build it, you run it" mean and what does it require? Intermediate

The team that writes a service also operates it: on-call, incidents, capacity, cost. It aligns incentives (you feel the pain of fragile code). It requires good tooling (dashboards, alerts, runbooks), sustainable on-call rotations (a team of 2 cannot be on-call 24/7), blameless post-mortems and a platform that hides infrastructure toil.

How do you keep 50 services consistent without a central architecture committee slowing everyone? Senior

Standardise the few things that must be uniform (auth, logging format with trace ids, health endpoints, API style guide, deployment method) and let teams choose the rest. Enforce through templates and automated checks in CI, not documents. Use lightweight architecture decision records (ADRs) to capture decisions, and a guild or review forum for cross-cutting changes. Avoid "polyglot for fun": each additional language or database needs support, hiring and on-call skills, so require a justification for each new technology.

8. Multi-tenancy architecture

Pooled vs siloed multi-tenancy: explain and compare. Senior

A tenant is one customer organisation using your SaaS. Options for isolation:

Pooled (shared everything)Bridge (shared app, separate data)Siloed (dedicated stack)
ComputeSharedSharedPer tenant
DataShared tables with a tenant_id column (or row-level security)Schema or database per tenantOwn database and often own cluster
Cost per tenantLowestMediumHighest
Noisy neighbour riskHighMedium (shared compute)None
Data leak riskOne missing filter leaks dataLowerLowest

Common real-world answer: tiered. Small tenants pooled for cost; large or regulated enterprise tenants siloed (premium plan, data residency). The architecture must let a tenant be moved between tiers.

How do you make sure tenant data never leaks in a pooled design? Senior
  • Resolve the tenant once at the edge from the authenticated token (never from a client-supplied field) and propagate it as context (headers, async context) through every call and message.
  • Enforce at the data layer, not just in code: row-level security in the database, or a mandatory repository filter that adds tenant_id automatically; queries without tenant context fail.
  • Composite keys and indexes starting with tenant_id; cache keys and search indexes include the tenant.
  • Beware context loss in async paths: thread pools, scheduled jobs and message consumers that do not carry the tenant context are classic leak sources.
  • Automated tests with two tenants that assert cross-tenant access fails; periodic audits.
One tenant's bulk import slows down everyone. How do you handle noisy neighbours? Scenario

Per-tenant rate limits and quotas at the gateway; separate queues or partitions per tenant (or per tier) so one backlog does not block others (fair scheduling); bulkheads (separate thread or connection pools by tenant class); throttle heavy operations to off-peak; move the heavy tenant to a dedicated cell or silo; per-tenant metrics and alerts so you notice early. A cell-based architecture (many identical self-contained stacks, each serving a subset of tenants) limits blast radius: a bad deploy or overload affects one cell, not all tenants.

How do schema migrations work with schema-per-tenant at thousands of tenants? Senior

Run migrations as an orchestrated, resumable job over tenants in batches, tracking the version per tenant; make every migration backward compatible (expand and contract) so app versions can run against both old and new schema while the rollout is in progress; roll out first to internal and small tenants as canaries; keep the migration idempotent so failed tenants can be retried. Pooled schemas avoid this problem but concentrate the risk into one big migration.

9. Hexagonal architecture, serverless, deployment units

What is hexagonal (ports and adapters) or clean architecture, at concept level? Intermediate

The idea: keep business logic in the centre with no dependency on frameworks, databases or protocols. The core defines ports (interfaces it needs, such as OrderRepository, PaymentGateway, or that it offers, such as PlaceOrder). Adapters on the outside implement them: a REST controller, a Kafka consumer, a JPA repository, a call to a payment provider. Dependencies point inward only (dependency inversion).

Why it matters for microservices: the core is testable without a database or network; you can swap a transport (REST to gRPC to events) or store without touching rules; and when a module is extracted from a modular monolith, only the adapter changes (an in-process call becomes a remote call). Cost: more interfaces and mapping code; overkill for a trivial CRUD service.

What are the trade-offs of serverless (functions as a service) as an architecture? Senior
StrengthsWeaknesses
No server management; scale to zero and to thousands automaticallyCold starts add latency (tens of ms to seconds depending on runtime and size)
Pay per invocation: excellent for spiky or low trafficAt steady high load it can cost more than containers or VMs
Fast to build event-driven glue (file upload triggers a function)Execution time, memory and payload limits; not for long jobs
Built-in availability across zonesStateless: state must live elsewhere; connection pooling to databases is hard (many concurrent functions exhaust DB connections; use a proxy or HTTP data API)
Vendor lock-in; local testing and debugging are harder; many tiny functions create nanoservice sprawl and hard-to-trace flows

Good fits: webhooks, scheduled jobs, image or file processing, glue between managed services, unpredictable bursty APIs. Poor fits: latency-critical steady high-throughput services, long-running stateful processing. Mitigations: provisioned concurrency for cold starts, group related handlers into one function, set concurrency limits to protect downstream databases.

Real-world note: in 2023 Amazon Prime Video engineers described moving one video-quality monitoring component from a distributed serverless design back to a single process, cutting its infrastructure cost substantially (they reported about 90 percent). The lesson is that per-call overhead and data passing between stages can dominate; it was one component, not a verdict on serverless.

What deployment units exist (VM, container, function, pod) and how do you pick? Intermediate
  • VM: strong isolation, slow to start, heavier; suits legacy or special OS needs.
  • Container: process plus dependencies in an image; fast start, dense packing, same artefact from laptop to production; the default for microservices.
  • Pod (Kubernetes): one or more containers sharing network and lifecycle (app plus sidecar); the unit that is scheduled and scaled.
  • Function: code only, platform runs it per event; least control, most elasticity.
  • Independently deployable unit is the real test: if two things must always deploy together, they are one deployment unit regardless of how they are packaged.

Best practice: immutable images (never patch a running instance), one artefact promoted through environments, configuration injected at runtime.

Blue/green, canary and rolling deployments: how do they differ? Intermediate
  • Rolling: replace instances gradually; cheap, but old and new versions serve concurrently (needs compatibility) and rollback is another rollout.
  • Blue/green: run a full new environment, switch traffic at once; instant rollback by switching back; costs double capacity briefly and database changes still need to be compatible with both.
  • Canary: send 1, 5, 25 percent of traffic to the new version while watching error rate and latency, with automatic rollback on regression; best risk control for large systems.

All three depend on backward-compatible schemas and APIs and on good health signals.

10. 12-factor, config, feature flags, observability

What is the 12-factor app and which factors matter most for microservices? Intermediate

A methodology for building cloud-native services. The twelve: codebase (one repo per deployable, many deploys), dependencies (declared explicitly), config (in the environment), backing services (treated as attached resources), build/release/run (strictly separated stages), processes (stateless, share nothing), port binding (service exports itself over a port), concurrency (scale out via processes), disposability (fast start, graceful shutdown), dev/prod parity, logs (write to stdout as event streams), admin processes (one-off tasks as same code).

Most important in practice:

  • Stateless processes: so any instance can serve any request and you can scale and replace freely; keep sessions in a store, not in memory.
  • Config in environment: same image in every environment.
  • Disposability: handle SIGTERM by finishing in-flight work, deregistering, then exiting; start in seconds.
  • Logs as streams: the platform collects them; the app does not manage log files.
How do you manage configuration and secrets across many services and environments? Intermediate
  • Separate config from code and from the artefact: one build, config injected per environment (env vars, mounted files, or a config service).
  • Central config store with versioning, audit and per-environment overrides (Kubernetes ConfigMaps, Consul, Spring Cloud Config, cloud parameter stores) kept in Git (GitOps) so changes are reviewed and revertable.
  • Secrets in a dedicated vault (HashiCorp Vault, cloud secret manager), not in Git or images; short-lived, rotated credentials; access by service identity.
  • Dynamic reload for safe values (feature flags, rate limits), restart for risky ones (connection strings).
  • Validate config at startup and fail fast; avoid config drift by generating environment config from one source.

Incident pattern: a bad config push applied to all services at once is a common cause of large outages. Roll config out progressively like code.

What are feature flags and how do they help a microservice architecture? Intermediate

A feature flag is a runtime switch that turns behaviour on or off without a deploy. Uses: separate deploy from release (ship dark code, enable later); trunk-based development; gradual rollout by percentage, tenant or region; instant kill switch if a feature misbehaves; A/B experiments; branch by abstraction during migration (route to old or new implementation).

Risks: flag debt (hundreds of stale flags, combinatorial test states) so give each flag an owner and expiry and delete after rollout; flag service becomes a dependency (evaluate locally with cached rules and a safe default if the service is down); flags that must be consistent across services need a shared evaluation context. Keep permission flags and operational flags separate from release flags.

What observability do microservices need that a monolith does not? Senior

In a monolith a stack trace tells the story. In services, one user request touches many processes, so you need the three pillars plus correlation:

  • Distributed tracing: a trace id created at the edge and propagated on every call and message (W3C traceparent, OpenTelemetry); shows which hop is slow or failing.
  • Centralised structured logs: JSON, with trace id, tenant id, service, version; shipped to one searchable place.
  • Metrics: the RED method per service (Rate, Errors, Duration) for request paths and USE (Utilisation, Saturation, Errors) for resources; queue lag for async consumers.
  • Health checks: liveness (restart me) vs readiness (send me traffic); do not make liveness depend on downstream services or a dependency outage restarts everything.
  • SLOs and alerts on user-facing symptoms (error budget burn) rather than on every internal cause.
  • Service dependency map and a catalogue of owners and runbooks.
  • Deployment markers on dashboards to correlate regressions with releases.

Watch cost: tracing and logs at full volume are expensive; sample traces (head or tail-based, keep errors and slow ones) and set log retention tiers.

How do you keep a trace across asynchronous messaging? Senior

Put the trace context in message headers when producing; the consumer extracts it and starts a child span (or a linked span for batch consumers, since one batch may carry many traces). Log the trace id and message id on both sides. Without this, a trace dies at the broker and async flows become invisible. Also track consumer lag and dead-letter queue depth as first-class metrics.

Which resilience patterns are architecture-level for microservices? Senior
  • Timeouts everywhere with a deadline propagated down the chain; the single most important rule (no timeout means a slow dependency exhausts your threads).
  • Retries only for idempotent operations, with exponential backoff and jitter, and a retry budget to avoid a retry storm (3 layers each retrying 3 times means 27 times the load on the bottom).
  • Circuit breaker: stop calling a failing dependency, fail fast, probe for recovery.
  • Bulkhead: separate pools so one slow dependency cannot take all threads.
  • Fallbacks and graceful degradation: show cached recommendations if the recommender is down.
  • Load shedding and back-pressure: reject excess work early rather than collapse.
  • Idempotency keys on writes so a retried payment does not charge twice.

11. Cost, complexity and failure modes

What does microservices cost you? Be honest. Senior
  • Distributed-systems complexity: partial failures, latency, timeouts, eventual consistency, duplicates, ordering.
  • Operational overhead: many pipelines, many deployments, version matrix, certificates, on-call; needs a platform team.
  • Infrastructure cost: each service has baseline CPU and memory, replicas for availability, sidecars, log and trace volume, cross-zone network traffic (cloud data transfer between zones or regions is billed, and chatty services add up).
  • Testing and debugging difficulty: no single stack trace; integration environments are expensive.
  • Data challenges: no joins, no ACID across services, reporting needs a warehouse or CQRS.
  • Organisational load: skills, standards, ownership, documentation.
  • Slower start: much work before the first feature ships.

Benefits only repay this when the organisation is big enough that coordination in a monolith costs more. Some well-known companies have publicly described consolidating services back (Segment's 2018 write-up on moving from many per-destination services to one is a frequently cited example) because the overhead outweighed the benefit at their team size.

One non-critical service (recommendations) becomes slow and the whole site goes down. Explain and fix. Scenario

Mechanism: callers wait on the slow service with long or no timeouts, their request threads fill up, they stop serving other requests, and their callers in turn back up: a cascading failure. Retries then multiply the load on the already struggling service.

Fix in layers: a short timeout (for example 200 ms) on the optional call; a circuit breaker that opens after repeated failures; a bulkhead so this dependency has its own small pool; a fallback (cached or generic items) so the page renders without it; load shedding on the recommender; and an alert on dependency latency. Classify dependencies as critical or optional at design time, and test failure with chaos experiments in staging.

After a short database blip, all services keep failing for 20 minutes even though the database recovered. Why? Scenario

Typical cause is a retry storm and a thundering herd: when the dependency recovers, thousands of clients retry at once (and each layer multiplies retries), pushing it over again; connection pools are exhausted by queued work; caches that expired together all refill at once. Fixes: exponential backoff with jitter, a retry budget (cap retries as a percentage of traffic), circuit breakers with gradual half-open probing, request coalescing and staggered cache TTLs, and load shedding so the system sheds excess rather than queueing it. Published post-mortems from large cloud providers have described this class of feedback loop (retries and overload sustaining an outage after the original trigger passed), so it is a well-known failure mode.

Every release needs 5 teams to deploy together on a Saturday night. What is wrong and what do you do? Scenario

You have a distributed monolith: the services are coupled by schema or API shape. Steps: list the actual dependencies for the last 5 releases and find why each coordination was needed (usually a breaking API or schema change); introduce expand/contract and tolerant readers so each deploy is safe alone; add consumer-driven contract tests to CI so breaks are caught before merge; use feature flags to decouple deploy from release; remove shared database access; measure "percent of releases that were independent" as the key metric. If two services always release together, merge them.

An old service has no owner and still takes production traffic. What do you do? Scenario

Find consumers via traces and gateway logs, find the last committers and the business function, assign an owner (a team that depends on it most, or the nearest domain team), add it to the service catalogue with a runbook and alerts, upgrade dependencies for security, and decide: keep, merge into an owned service, or retire with a deprecation plan. Prevent recurrence by requiring an owner field for every service in the platform, and flagging services with no commits and no owner on a regular review.

How do you test a microservice architecture without an environment where everything runs? Senior
  • Unit tests on the domain core (cheap thanks to hexagonal design).
  • Component tests: the service with real own database (containers) and neighbours replaced by stubs or contract-verified mocks.
  • Consumer-driven contract tests at every boundary, in both directions.
  • A handful of end-to-end smoke tests on critical journeys only.
  • Testing in production safely: canaries, synthetic monitoring, feature flags, shadow traffic, and fast rollback; accept that some failure modes only appear at scale.
  • Resilience testing: fault injection and chaos experiments for timeouts, dead dependencies and slow responses.
Orchestration vs choreography for a long business process: which and what goes wrong? Senior

Choreography problems: nobody can answer "where is order 42 now?", cyclic event dependencies appear, and adding a step means editing several services. Orchestration problems: the orchestrator can become a god service containing all business logic and a single point of failure; services become anemic. Practical balance: use an orchestrator (or a workflow engine such as Temporal or a state-machine service) that only coordinates and tracks state, while each step's business rules stay inside the owning service; make it durable (state persisted, restart-safe) and highly available; expose process state for support and monitoring.

When would you NOT use an API gateway or mesh at all? Intermediate

If you have a handful of services, one team and one cluster, a simple load balancer or ingress with auth plus client libraries for timeouts and retries is enough. A gateway adds a hop, a component to run and a place where teams queue for changes; a mesh adds per-pod overhead and a steep operations curve. Adopt them when the problems appear: many public routes needing uniform auth and rate limits (gateway), or many services needing uniform mTLS, policy and traffic shifting without code changes (mesh).
