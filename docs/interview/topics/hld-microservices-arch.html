How to use this page

Click a question to open the answer. Try to answer aloud first, in about 60 to 90 seconds. At senior level the interviewer is not testing whether you know the word "microservice"; they test whether you can say when NOT to use it, what it costs, and how you would move safely from one shape to another. Always tie a decision to a reason (team size, change rate, scaling shape, failure isolation) and name the trade-off. A separate page covers the developer-level mechanics (Spring, REST, resilience annotations); this one is about architecture decisions.

1. Monolith, modular monolith, microservices

What is a monolith, and is it always bad? Basic
Say: "A monolith is one deployable unit over usually one database. It is not bad. It is the right default for a new product, and I split only when I can name the pain: team contention, different scaling shapes, or failure isolation."

What it is. A monolith is one program that is built, tested, released and scaled as a single unit, normally on top of one database. Everything (orders, payments, users, reports) lives in the same process. It says nothing about code quality: a monolith can be beautifully modular or a tangled ball of mud.

Why it is a good default. Every hard problem of distributed systems simply does not exist inside one process:

  • A call between two features is a method call: nanoseconds, cannot time out, cannot half-fail.
  • One database means one ACID transaction can update orders and stock together, so you never need sagas.
  • One stack trace shows the whole story, so debugging is cheap.
  • One thing to deploy, monitor and put on call.

When it starts to hurt. The pain is organisational more than technical:

  1. The build and test cycle grows (a 40-minute pipeline means people batch changes, which makes releases riskier).
  2. Many teams merge into one release train, so one team's bug blocks everybody.
  3. You cannot scale the hot 5 percent of the code (say image resizing) without cloning the other 95 percent.
  4. One memory leak or runaway query in a minor feature takes the whole app down (no failure isolation).

Decision rule. If you cannot name which of those four pains you have, you do not need to split. If you can, ask first whether a modular monolith (next question) fixes it before paying for a network.

Pitfall. Candidates who say "monolith bad, microservices good" look junior. The senior answer is that the monolith is a legitimate end state for many companies, and that the real skill is knowing the trigger for change.

Remember: Monolith = one deployable. Cheap and simple until team size, scaling shape or failure isolation says otherwise.

Compare monolith, modular monolith and microservices. When does each win? Intermediate
Say: "Big-ball monolith has no enforced boundaries. A modular monolith has the boundaries of microservices but runs as one process and one deploy. Microservices turn those boundaries into network contracts and independent deploys, which costs a lot. I pick by team count and how stable the boundaries are."

The idea behind the three. They differ along two separate axes that people often mix up: logical separation (are module boundaries enforced?) and physical separation (do modules run as separate processes with separate data?). A big-ball monolith has neither. A modular monolith has logical separation only. Microservices have both.

What "enforced boundary" looks like in a modular monolith. Take an orders module and a billing module in one codebase. Billing exposes a small public interface (BillingApi.chargeOrder(orderId)); everything else in the billing package is package-private. Billing owns the tables invoice and payment; the orders module is not allowed to join against them. An architecture test (ArchUnit in Java, for example) fails the build if orders imports a billing internal class. You get the discipline of services at the price of one deployment.

Why that matters. The expensive part of microservices is not the code split, it is the distributed-systems tax: partial failure, latency, eventual consistency, many pipelines. A modular monolith lets you find the right boundaries while changing them still costs a refactor, not a cross-team API migration. When a seam proves itself (needs its own scaling or team), you extract it, and only the adapter changes from an in-process call to a remote call.

Decision rule. Under roughly 20 to 30 engineers and a still-moving domain: modular monolith. Many autonomous teams, stable boundaries, and real differences in scaling or reliability: microservices. A big-ball monolith is only fine for a throwaway prototype.

Remember: Modular monolith = microservice-grade boundaries without the network. It is the usual best stepping stone.

When should you actually choose microservices? Intermediate
Say: "I choose microservices when organisational scale and real differences between parts justify the cost: many teams colliding in one release train, different scaling shapes, failure or compliance isolation, and boundaries I am confident are stable."

Why this question exists. Microservices solve a coordination problem between people and a few specific technical problems. They do not make code better by themselves. So the honest answer is a short list of conditions, each tied to a concrete pain.

Good reasons, with the pain behind each.

  • Many teams in one codebase. Rule of thumb: once you pass roughly 30 to 50 engineers, merge conflicts, a shared release train and "who broke the build" dominate. Independent deploy lets team A ship ten times a day without asking team B. (The number is a heuristic, not a law.)
  • Different scaling shapes. Image processing needs 200 CPU-heavy instances at peak, account settings needs 2. In a monolith you scale both together; as services you pay only for what is hot.
  • Different technology needs. A Python ML scorer beside a Java core, or a memory-hungry search component.
  • Failure isolation. A recommendation outage must not take down checkout. A separate process (plus timeouts and fallbacks) gives you a blast-radius wall.
  • Compliance isolation. Card data or health data in a small, tightly audited boundary shrinks the audit scope.
  • Stable, well-understood boundaries. You have already run the domain for a while and know where the seams are.

Bad reasons. "It is modern", resume-driven design, a team of six, or an unclear domain. The last one is the worst: splitting before you know the boundaries freezes the wrong boundaries into network contracts. Moving a function between two packages is a refactor; moving it between two services is a versioned, multi-team migration.

Checklist to say aloud. (1) Can I name the pain? (2) Would a modular monolith fix it? (3) Do I have the platform (CI/CD, tracing, on-call) to run N services? (4) Is the boundary stable? If any answer is no, wait.

Remember: Microservices are a response to team scale, scaling shape, isolation needs and stable boundaries, never to fashion.

A startup asks: monolith or microservices on day one? Senior
Say: "Modular monolith. On day one I do not know the real boundaries, the team is small and the biggest risk is product-market fit. I keep strict module seams so extraction is cheap later."

Why not microservices on day one. Three reasons stack up. First, your domain model is a guess: in the first six months the product changes direction, and every wrong boundary frozen into a network API is expensive to move. Second, 3 to 8 engineers cannot afford a platform: pipelines, service discovery, tracing and on-call per service eat the time you need for features. Third, the main startup risk is building the wrong thing, not failing to scale; scale problems are good problems you can solve later.

What "modular monolith" means in practice.

  1. One repo, one deployable, one database server.
  2. Split the code by business capability (catalog, orders, billing), not by layer (all controllers together).
  3. Each module owns its tables. No joins and no foreign keys across modules; refer to other modules by ID.
  4. Modules talk through a small public interface or through in-process domain events (OrderPlaced), never by reaching into another module's classes or tables.
  5. Add architecture tests (ArchUnit or equivalent) that fail the build when a module touches another's internals, so the boundary does not rot.

Triggers to extract a service later. One module needs independent scaling (video encoding), one team needs a separate release cadence, one failure domain must be isolated, or a compliance boundary appears. Because the seam is already clean, extraction means: put the module's interface behind an HTTP or message adapter, move its tables to their own schema, and route to it. It is a weeks-long task rather than a rewrite.

Trap: Saying "monolith" and stopping. The interviewer wants to hear that you keep the seams clean and tested, otherwise you end up with the big ball of mud that really cannot be split.

Remember: Day one = modular monolith with enforced seams; extract on evidence, not on hype.

What is a distributed monolith and how do you recognise one? Intermediate
Say: "A distributed monolith is many services that still have to be changed, deployed and failed together. You pay the full network and ops cost and get none of the independence. The tell is lock-step releases and a shared database."

How it happens. A team splits a monolith by technical layer or by guesswork, keeps one database "to save time", and shares a common library full of domain objects. Now every service depends on the others' internals, but the dependency has become a network call that can fail. It is the worst of both worlds.

Symptoms you can check in a review:

  • A single feature needs coordinated edits and a lock-step release across 4 services.
  • Services share one database or query each other's tables.
  • Long synchronous call chains (A calls B calls C calls D): one slow node stalls everything, and availability multiplies down (four services at 99.9 percent each give about 99.6 percent).
  • A shared "common" jar with domain classes forces everyone to upgrade together.
  • You need all services running to test anything.
  • Releases need a written "deployment order".

A quick diagnostic. Take the last ten changes. For each one, count how many services had to change and release together. If most touched more than one, the boundaries are wrong. A healthy system has most changes landing in exactly one service.

Fixes, in order of effort.

  1. Add expand/contract and tolerant readers so each deploy is safe on its own.
  2. Add consumer-driven contract tests so breaks are caught in CI.
  3. Give each service its own data; replace cross-service reads with APIs or replicated copies fed by events.
  4. Replace sync chains with events where staleness is acceptable.
  5. Redraw boundaries around business capabilities. If two services always change together, merge them (a modular monolith is a respectable destination).

Remember: If you cannot deploy one service alone, you do not have microservices; you have a distributed monolith.

What are nanoservices and why are they a problem? Intermediate
Say: "Nanoservices are so small that the overhead of running them (pipeline, network hop, monitoring, on-call, versioning) is bigger than the logic inside. I size services by business capability and team ownership, not lines of code."

The problem. Every service carries a fixed cost, regardless of how small it is: a repository and CI pipeline, a container image, health checks, dashboards and alerts, a version and API contract, an on-call rotation, a network hop on every call. If the code inside is one function, the fixed cost dwarfs the useful work.

Example. A "TaxCalculator service" with one function calculate(amount, region). Checkout now makes a network call to compute something that was a library method taking microseconds. You added roughly a millisecond or more of latency (plus tail latency), a new failure mode (what does checkout do if tax is down?), and a deployment to maintain. A library, or a module in the checkout service, would do the same job for free.

Why it happens. The slogan "each service does one thing" is taken to mean one function, and splitting is easy and feels productive. It also tends to produce the chatty, always-lock-step dependencies of a distributed monolith.

Sanity test for a candidate service.

  • Can one team own it end to end (code, data, deploy, on-call)?
  • Does it change for a reason independent of its neighbours?
  • Does it own data or behaviour a caller would be glad to not know about?
  • If I deleted the network between it and its main caller, would it make more sense as one thing? If yes, merge.

What to do if you already have them. Merge services that always change and deploy together, turning the network call back into an in-process one. Reducing the number of deployables is a legitimate architecture win.

Remember: Size by capability and ownership; a service whose overhead exceeds its logic should be a library or a module.

How big should a microservice be? Intermediate
Say: "No line count works. A service should be roughly one bounded context, or a coherent part of it, owned by one team that can hold all of it in their heads, and it should change independently of its neighbours."

Why line counts fail. Famous rules like "100 lines" or "rewrite in two weeks" are slogans. Two services with the same size can be perfectly drawn or terribly drawn. What matters is cohesion (things that change together live together) and coupling (little needs to change in lock-step with others).

Practical heuristics, each with the question to ask:

  • One team, one cognitive load. Can this team know the code, the runbook and the failure modes without notes? A team usually can own a handful of services, not thirty. Team Topologies calls this cognitive load.
  • Single reason to change. Does it change for one family of business reasons (pricing rules, shipping rates), not for five unrelated ones?
  • Rewritable. Could the team rewrite it in weeks rather than months if the design aged badly? That keeps it small enough to throw away.
  • Independent in releases. Does it rarely have to ship in lock-step with another service? If two always move together, they are one service wearing two hats.
  • Owns its data. It is the single writer of the facts it manages, so no one else needs its tables.

Too big versus too small. Too big: several teams edit it, deploys wait on each other, and one release carries unrelated risks (a mini monolith). Too small: calls between services outnumber useful work and every feature touches many services (nanoservices). The right size sits where a typical feature lands inside one service.

Remember: Size is set by ownership and cohesion (one bounded context, one team), not by lines of code.

2. Service boundaries and domain-driven design

How do you decide service boundaries? Senior
Say: "I split by business capability and bounded context, never by technical layer. I find the seams with event storming, language changes, change patterns, data ownership, team structure, and I merge candidates that chat constantly."

Why boundaries are the hard part. Code inside a service is easy to refactor; boundaries between services are not, because they are public contracts used by other teams and deployed separately. A wrong boundary produces a distributed monolith. So you invest time in discovering the seams before cutting.

Methods, and a tiny example for each (e-commerce).

  1. Event storming. Put domain experts and developers in a room and write domain events on sticky notes in time order: OrderPlaced, PaymentCaptured, StockReserved, ParcelShipped. Cluster them. Groups that talk about the same nouns and rules hint at contexts (Ordering, Payments, Inventory, Shipping).
  2. Language changes. When a word changes meaning you crossed a boundary: "customer" is a billing account in Finance, a delivery recipient in Shipping, a ticket requester in Support.
  3. Change patterns. Look at version history. Files that always change together belong together; things that change independently can separate.
  4. Data ownership. For each fact ask who is the single writer. "Stock level" has one writer (Inventory). That owner is the service; everyone else holds an ID or a replicated copy.
  5. Teams. Boundaries should match who owns what (Conway's law, covered later). A boundary that needs three teams to change is wrong.
  6. Coupling check. Prototype the calls. If two candidate services chat constantly, or need a joint transaction, they are probably one service.

Pitfalls. Cutting by layer ("data service", "UI service") puts every feature across all services. Cutting by noun (a service per table) gives entity services (a later question). Cutting too early, before the domain settles, is worse than starting inside a modular monolith.

Remember: Business capability plus bounded context, validated by change patterns, single-writer data and team ownership; chatty pairs merge.

What is a bounded context? Give an example. Intermediate
Say: "A bounded context is an explicit boundary inside which one domain model and one vocabulary are consistent. The same word can mean different things in different contexts, and each context keeps its own small model."

What it is. In domain-driven design, a model is only meaningful inside a context. Trying to build one universal model of "the business" produces a bloated class that serves nobody. A bounded context draws a line: inside it, terms have exactly one meaning; outside, a different model may use the same word differently.

Example: Product in e-commerce.

ContextWhat "Product" means thereFields it cares about
CatalogSomething to browse and describetitle, description, images, categories
InventoryA SKU in a warehousesku, quantity per warehouse, reorder level
PricingA target of price rulessku, base price, discounts
ShippingA parcel itemweight, dimensions, hazard class

A single shared Product class with all those fields forces every team to coordinate on every change. Instead each context holds a small model of its own and they exchange only a product ID and events such as PriceChanged.

How contexts relate. Through explicit patterns: customer/supplier (upstream commits to downstream needs), published language (an agreed event or API schema), and an anticorruption layer that translates a foreign model at the edge so it does not leak into yours.

Link to microservices. A bounded context is the best first guess for a service boundary (one context may become one or a few services, rarely the reverse). A service that spans two contexts has two vocabularies fighting inside it.

Remember: Same word, different model per context; exchange IDs and events, not one shared class.

What is an aggregate, and why does it matter for service design? Intermediate
Say: "An aggregate is a cluster of objects treated as one consistency unit with a single root. All its invariants are enforced in one transaction, other aggregates are referenced by ID, and an aggregate never spans services."

What it is. An aggregate groups objects that must be consistent together, behind one entry point called the aggregate root. Example: an Order (root) with its OrderLines. Rules that live inside: "order total equals sum of lines", "no lines can be added once shipped". Outside code may only call methods on Order; it never edits an OrderLine directly.

Why it matters. The aggregate answers "what must be changed atomically?". Everything inside is saved in one local transaction, so invariants always hold. Everything outside is allowed to be eventually consistent.

A small illustration.

  1. A client calls order.addLine(sku, qty).
  2. The root checks its rule (status is OPEN, quantity above 0) and updates total.
  3. The repository saves the whole order in one transaction.
  4. The order holds customerId as an ID, not a loaded Customer object, because Customer is another aggregate (maybe another service).

Architecture consequences.

  • A transaction boundary should not cross the network, so an aggregate never spans services.
  • Keep aggregates small. A giant "Customer with all orders" aggregate causes lock contention and slow writes; design for the invariant, not for the object graph.
  • Consistency between aggregates is eventual, through domain events or sagas.
  • If two aggregates must always change atomically, either they are one aggregate or you drew the boundary wrong.

Remember: Aggregate = transactional consistency boundary; reference others by ID; never across services.

What is a context map and the anticorruption layer? Senior
Say: "A context map shows how bounded contexts relate. An anticorruption layer is a translation layer on the consuming side so a legacy or foreign model never leaks into mine."

What a context map is. A diagram plus labels describing the relationship between each pair of contexts, so that teams know who depends on whom and how much power each side has. The common relationship types:

PatternMeaningRisk
Shared kernelTwo contexts co-own a small piece of model and codeTight coupling; changes need both teams
Customer / supplierUpstream (supplier) plans work to meet downstream needsNeeds real negotiation
ConformistDownstream accepts the upstream model as isUpstream quirks leak in
Open host service + published languageUpstream offers a stable public API with a documented schemaMust keep it compatible
Anticorruption layer (ACL)Downstream translates the foreign model into its ownExtra code to maintain

ACL, concretely. Suppose a legacy billing system returns {"CUST_STAT":"A","BAL_AMT":"00012050"}. Without an ACL, codes like "A" spread across your code. With an ACL, one adapter class maps this to your clean model: Customer(status=ACTIVE, balance=Money(120.50, "USD")). Your domain code never sees the legacy format, and if the legacy system is replaced, only the adapter changes.

When to use it. Integrating a vendor API, wrapping a legacy monolith, and especially during strangler migrations, where the new service and the old code co-exist and you must not let old concepts seep into the new design. The cost is extra mapping code and a place where bugs can hide, so test it thoroughly.

Remember: Context map = relationships between contexts; ACL = translation at your edge to protect your own model.

Why is the "entity service" (one service per database table) an anti-pattern? Intermediate
Say: "An entity service is CRUD over a table, so all the real logic moves into callers and every business operation becomes chatty multi-service orchestration. I cut by business capability, which owns behaviour and the data it needs."

What it looks like. CustomerService, OrderService, AddressService, each exposing only GET /x/{id}, PUT /x/{id}. It feels tidy because it mirrors the database tables, but it is cutting by noun.

Why it hurts. Walk through "place order":

  1. Some caller reads the customer from CustomerService.
  2. Reads the address from AddressService.
  3. Reads stock from a ProductService, checks it itself.
  4. Writes the order via OrderService, then updates stock via ProductService.

Where is the rule "do not sell below zero stock"? In the caller. Where is the transaction? Nowhere: if step 4 fails after the order was saved, you have an inconsistent state. And every caller must re-implement the same orchestration, so the logic is duplicated and drifts.

The better shape. A Checkout capability service owns the "place order" behaviour: validates, reserves stock, creates the order, all inside one boundary with one transaction for what must be atomic and events for the rest. Its API is verbs (POST /checkouts) rather than table CRUD. Data is held where the behaviour lives.

Smell test. If a service's API is only get/put/delete of one entity and every use case needs three or four of them, you cut by noun. Some CRUD services are fine for genuinely simple reference data, but they should not be the pattern for the whole system.

Remember: Services own behaviour for a capability, not rows of a table.

Many services need the same data (country list, user profile name). Who owns it? Intermediate
Say: "One service owns it as the single writer. Consumers either call it, cache it with a TTL, keep a local copy updated by events, or carry the few fields in tokens, depending on how stale they can tolerate. Nobody writes into the owner's tables."

Why a single owner. If two services can edit the same fact, you get conflicts and unclear rules. A single writer guarantees one place enforces the invariants and one place to fix bugs. Consumers hold copies, never the master.

Four ways for consumers to get the data, with trade-offs:

OptionHowGood forCost
Call on demandSync call to the owner each timeAlways-fresh needs, low volumeRuntime dependency, extra latency, owner outage hurts you
Cache with TTLCall, then keep for 5 minutesSlow-changing data like country listStale up to TTL
Replicate via eventsOwner publishes UserRenamed; consumers store the fields they needHot read paths, resilienceEventual consistency, duplicate data, backfill logic
Embed in token or messageUser id and display name in the JWT or eventHarmless stalenessCannot be updated until it expires

Example. Orders needs the customer's display name for an invoice. If the name changes, it is acceptable that old orders keep the name at purchase time. So Orders stores a snapshot at order time; no runtime call and no coupling. This is often the right modelling answer: the copy is not a stale mirror, it is a different fact ("name on the order").

Pitfalls. Replicated copies need an initial backfill and a way to repair drift. Do not store more fields than you use, or you create hidden coupling to the owner's schema.

Remember: Single writer; consumers choose call, cache, event-replicated copy or token, by tolerated staleness.

3. Data ownership and consistency

What is database per service and why is it the rule? Basic
Say: "Each service owns its data store privately. Others reach that data only through its API or its events. It lets each service evolve its schema, pick its store and fail independently, and the price is no cross-service joins or ACID transactions."

What it is. The service is the only code that reads or writes its tables (or documents, or index). "Private" means access control, not necessarily hardware: a separate schema with separate credentials on a shared database server already counts, as long as nobody else is granted access. Separate physical servers are a later decision driven by scale and isolation.

Why it is the rule. Think of the schema as part of the service's internal implementation. If other services read the tables, the schema becomes a public API nobody versioned, and you can no longer rename a column, change the index, or switch databases without a cross-team negotiation. With private data:

  • The team can change its schema freely behind a stable API.
  • Each service picks the right store: relational for orders, a document store for catalogue, a search index for queries, a cache for sessions.
  • Load and failures stay local: a heavy report query in one service cannot lock rows another service needs.
  • One clear owner enforces each invariant.

What you give up and what you do instead.

You loseYou use instead
Joins across servicesAPI composition, CQRS read models, small replicated copies
One ACID transaction across servicesSagas with compensations, outbox for reliable events
Foreign keys across servicesIDs only, referential checks in code or events
Ad hoc reporting over everythingEvent stream into a warehouse or data lake

Pitfall. Teams adopt it halfway: separate services but one shared schema "for now". That is the usual route to a distributed monolith (next question).

Remember: Private data, access only via API or events; trade joins and ACID for independence.

Why is a shared database an anti-pattern? When might you tolerate it? Intermediate
Say: "When services share tables, the schema becomes an unversioned public API. A rename breaks another team silently and nobody owns the invariants. I tolerate it only briefly during a migration, or as read-only access to a replica."

What goes wrong, with an example. Orders and Billing both read and write the orders table. Orders renames status values from PAID to CONFIRMED in a release. Billing, which filters on PAID, silently stops invoicing. No compiler, no contract test, no deploy dependency flagged it. Other failure modes of the same kind:

  • A slow query from one service holds locks or consumes I/O the other needs, so one team's report slows the other's checkout.
  • You cannot change the storage engine, shard it, or add a column type without coordinating everyone.
  • Invariants have no owner: who enforces "balance cannot go negative" when three services update the balance?
  • You cannot deploy independently, because schema changes must be applied for all at once.

This is the single most common reason a split ends up as a distributed monolith.

When it is tolerable.

  1. Transitional phase of a migration. The old monolith and the new service both touch a table while you move writes across. Put a deadline on it and an owner.
  2. Read-only reporting against a replica or warehouse copy, where a schema change only breaks a report, not a business flow.
Trap: "One database server with separate schemas per service" is not the anti-pattern, provided each service can only access its own schema. The anti-pattern is shared access to the same tables, not shared hardware.

Remember: Shared tables = hidden coupling. Shared server with private schemas is fine.

How do you do a query that needs data from several services (for example an order page with customer, items and shipment status)? Intermediate
Say: "For a small per-entity view I use API composition: a composer calls the services in parallel and merges. For lists, search or big joins I build a CQRS read model fed by events. For a few fields I replicate a slice locally."

The problem. With database per service you cannot write JOIN customers, orders, shipments. An order page needs the customer name (Customers), the items (Orders) and the delivery status (Shipping). Three owners, three stores.

ApproachHowProsCons
API compositionA composer (gateway, BFF or aggregator service) calls each service in parallel and mergesSimple, always freshLatency is the slowest call; partial failure handling; no cross-service sort/filter on big sets
CQRS read modelA query service subscribes to events from all services and builds its own denormalised viewFast, can filter/sort/search, isolates read loadEventually consistent; more moving parts; rebuild logic
Data replication of small slicesEach service keeps the few fields it needs from othersNo runtime callStaleness and duplicate data

Composition walked through. A request for order 42 arrives at the composer. It fires three calls at once (each with a 200 ms timeout): orders, customers, shipments. Total time is about the slowest call (say 120 ms), not the sum (say 300 ms). If shipments times out, the composer returns the page with "status unavailable" rather than failing the whole page.

Why composition breaks down. "Show all orders of customers in Germany sorted by value" would need the composer to pull everything from two services and sort in memory. That is where a CQRS read model wins: a query service consumes OrderPlaced and CustomerMoved events and stores one denormalised table or search index with exactly the columns that query needs, indexed for it.

Decision rule. Composition for small, recent, per-entity views. CQRS views for search, lists, dashboards and large joins. Replicated slices when a hot path cannot afford a runtime call. Expect to live with eventual consistency in the second and third.

Remember: No cross-service joins: compose at read time for small views, precompute a read model for big ones.

How do you keep data consistent across services without distributed transactions? Senior
Say: "I avoid two-phase commit across services and use a saga: a series of local transactions, each triggering the next, with compensating actions to undo earlier steps on failure. Choreography for short flows, orchestration for long or branching ones, and every step idempotent."

Why not two-phase commit. 2PC makes all participants lock their rows until a coordinator says commit. If the coordinator dies, participants stay blocked; locks are held across network round trips; and many brokers and stores do not support it. It trades availability for atomicity, which is the wrong deal for a service-per-database system.

How a saga works, with an example. Place an order:

  1. Order service creates the order as PENDING (local transaction).
  2. Payment service authorises the card.
  3. Inventory service reserves stock.
  4. Order service marks the order CONFIRMED.

If step 3 fails (out of stock), run compensations in reverse: refund the payment, cancel the order. A compensation is a semantic undo, not a database rollback: a refund is a new transaction, and it is visible in the ledger.

  • Choreography: each service listens for events and reacts (PaymentAuthorised triggers inventory). No central brain and loose coupling, but the flow is implicit; with many steps nobody can see it whole.
  • Orchestration: a coordinator (saga orchestrator or workflow engine) sends commands and tracks state. The flow is explicit, testable and observable; the cost is one more component and a temptation to put business logic in it.

Rule of thumb: choreography for 2 to 4 steps, orchestration for longer or branching flows.

Pitfalls. Messages arrive at least once, so every step and compensation must be idempotent (dedupe by a saga id and step). Sagas are not isolated: other readers can see the order half-done, so model visible intermediate states (PENDING) and never ship goods on a PENDING order. Persist saga state so a crashed orchestrator resumes.

Remember: Saga = local transactions plus compensations; idempotent steps; visible intermediate states.

What if a saga step cannot be undone (an email was sent, a parcel shipped)? Senior
Say: "I order the steps so irreversible ones come last, use reserve-then-commit for the rest, compensate semantically where I must, and route the leftovers to a human queue."

The problem. A compensation undoes a step, but some effects cannot be undone: an email already read, a parcel already on a truck, money already paid out to a third party.

Techniques, in order of preference:

  1. Put the pivot step last. Sequence the saga so that everything that can fail comes first and the irreversible step runs only after all of them succeeded. Once the pivot has run, the saga can only go forward (retry until it works), never back.
  2. Reserve first, commit later. Replace a final action by a two-part one: hold the stock, authorise the card (nothing leaves), and capture or ship only at the end. A reservation is cheap to release.
  3. Semantic compensation. If the effect is out, compensate in business terms: send a correction email, create a return, issue a credit note.
  4. Human fallback. When automation cannot decide, push the saga with its full state onto a manual review queue with an owner and an SLA.

Example. Order flow: validate, authorise card (hold), reserve stock, then at the end capture payment and create the shipment. If the stock reservation fails, only the card hold is released, which is free and invisible to the customer. If the shipment creation fails after capture, retry it (it is a forward-only step); after repeated failure, refund and alert a person.

Pitfall. Do not pretend a compensation is a perfect rollback; the customer may see the charge and the refund in their statement. Tell the business what they will see.

Remember: Irreversible steps last; reserve before commit; compensate semantically; humans for the rest.

How do you atomically update your database and publish an event? Senior
Say: "Writing to the database and then to the broker is two operations, so a crash between them loses or duplicates events. I use the transactional outbox: write the business row and an outbox row in one local transaction, and a relay publishes outbox rows to the broker, at least once, with idempotent consumers."

The dual-write problem. Code like this looks fine:

db.save(order);        // step 1
broker.publish(event); // step 2

If the process crashes between the two, the order exists but no event was sent (a lost event, downstream never learns). Reverse the order and you may publish an event for an order that then failed to save. There is no transaction spanning a database and a broker.

The outbox pattern.

  1. In one local database transaction, insert the order row and an outbox row (id, aggregate_id, type, payload). Either both commit or neither.
  2. A relay reads unsent outbox rows and publishes them to the broker. Two common ways: a poller that selects rows ordered by id, or change data capture (for example Debezium) that tails the database log.
  3. After a successful publish the relay marks the row sent (or deletes it).

If the relay crashes after publishing but before marking, it will publish again on restart. So delivery is at least once, and consumers must be idempotent: keep an inbox table of processed event ids and skip repeats (or make the handler naturally idempotent, such as "set status to X").

Trade-offs. The poller is simple but adds latency and load; CDC is faster and cleaner but needs infrastructure. Ordering is preserved per aggregate if you key messages by aggregate id. Clean up old outbox rows.

Remember: Outbox = atomic "state change plus intent to publish"; relay delivers at least once; consumers dedupe.

Business says "the page must always be correct". How do you handle eventual consistency? Senior
Say: "First I ask which screens truly need strong consistency; usually very few. I keep tightly related data in one aggregate, give users read-your-writes, show honest intermediate states, version events, and run reconciliation."

Why this arises. With data in several services and updates flowing by events, a read right after a write may still see old data for a moment (typically milliseconds to seconds, sometimes longer under lag). Business people hear "eventual" as "wrong". Your job is to separate where it truly matters from where it is invisible.

Step 1: classify. A bank balance shown right before a transfer needs strong consistency. A "recently viewed" list, a search index, a loyalty-points total can lag. Typically a handful of screens fall in the first group.

Step 2: techniques.

  • Keep strongly related data together in one aggregate or service so a local ACID transaction covers it.
  • Read-your-writes. After a user edits something, return the new state in the write response, or route that user's next reads to the source of truth for a few seconds (sticky read, or a version token the client sends back and the reader waits for).
  • Honest intermediate states. Show "Payment pending" instead of pretending it is done. This is also a better product.
  • Version or timestamp events so a consumer ignores an older event that arrives after a newer one.
  • Reconciliation jobs compare two stores periodically and repair drift.

Example. User changes address, the profile service saves it and returns the new address directly, the page shows it immediately. The order service receives AddressChanged a moment later and updates its copy; meanwhile any order created in that second uses the old address, which the business accepts or handles by reading the address from the profile at checkout.

Pitfall. Promising "always correct" and then adding distributed locks to deliver it: you trade correctness for outages. Negotiate the requirement instead.

Remember: Few screens need strong consistency; for the rest design for visible, bounded staleness.

4. Communication, gateway, mesh, discovery

What communication styles exist between services and how do you choose? Intermediate
Say: "I use synchronous calls where the caller needs the answer now and chains are short, and asynchronous commands or events where work can wait, load must be levelled, or the flow fans out."

The four styles.

Temporal coupling, explained. In a sync call the callee must be up at the exact moment the caller calls. Availability multiplies along the chain: five services at 99.9 percent each give about 99.5 percent for a request that needs all five. Latency also adds, and the slowest hop sets your tail latency.

Async example. Checkout accepts the order and returns 202 with an order id. It puts ProcessPayment on a queue. What each is. Event-driven vs request-driven architecture: when do you pick which? Senior
Say: "Request-driven is explicit and gives an immediate answer; event-driven decouples producers from consumers and buffers outages but is eventual and harder to trace. I choose events for notifications and fan-out, requests for queries and commands needing an immediate result."

Definitions. Request-driven: the caller asks a specific service and waits. Event-driven: a service announces a fact ("OrderPlaced") and any number of services react, without the producer knowing who they are.

AspectRequest-drivenEvent-driven
CouplingCaller knows calleeProducer does not know consumers

Example of the extensibility gain. Today OrderPlaced is consumed by Inventory. Next quarter Analytics and Loyalty want it. Request-driven: edit the Order service to call two more services (and redeploy it, and handle their failures). Event-driven: they subscribe, the Order service does not change.

Commands versus events. A command is an instruction to one handler ("ChargeCard"), named in the imperative. An event is a past-tense fact ("CardCharged") that anyone may hear. Sending commands dressed as events creates hidden coupling: the producer secretly expects a particular consumer to act.

Pitfalls of events. Flow becomes emergent (nobody can see "what happens after OrderPlaced"), duplicates and ordering must be handled, and schemas evolve. Invest in correlation ids, a schema registry and a dead-letter queue from the start.

Remember: Events for facts and fan-out, requests for answers now; most systems are hybrid.

What kinds of events exist (notification, event-carried state transfer, event sourcing)? Senior
Say: "Event notification is a thin ping, event-carried state transfer ships the data so consumers need not call back, and event sourcing stores the events themselves as the source of truth. They are different tools; I do not adopt event sourcing just to publish events."

Take the same fact, "customer 7 changed address", in three forms.

  • Event notification. {"type":"AddressChanged","customerId":7}. Tiny. Consumers who care must call the Customer service to learn the new address. Upside: small, the owner stays authoritative. Downside: a thundering herd of call-backs after each event, and a runtime dependency on the owner (which defeats part of the point of events).
  • Event-carried state transfer. {"type":"AddressChanged","customerId":7,"address":{...},"version":12}. The event contains the data consumers need, so each keeps a local copy and never calls back. Upside: resilient, fast reads. Downside: bigger schema surface (a change to the address shape is now a change to the event contract), duplicated data, and the need to handle ordering via the version number.
  • Event sourcing. The service does not store "current address"; it stores the full ordered log of events (AddressChanged and so on) and derives current state by replaying them, often with snapshots for speed. Upside: a complete audit trail, time travel ("what did we know on 1 March?"), and easy projections. Downside: heavy. Old events must stay readable forever (schema evolution), replays are slow without snapshots, queries need projections, and the team needs a real learning curve.

Do not confuse them. Publishing events from a normal database service (via outbox) is not event sourcing. Event sourcing is a persistence choice for one service. It is often paired with CQRS, but each can exist without the other.

Rule of thumb. Default to event-carried state transfer for data propagation between contexts; use thin notifications when the data is large or sensitive; use event sourcing only where audit and history are core to the domain (ledgers, trading).

Remember: Notification = ping, carried state = ping plus data, sourcing = the log is the database.

What are API composition and Backend for Frontend (BFF)? Intermediate
Say: "API composition is one component calling several services and merging results. A BFF is a thin backend per client type, owned by that frontend team, that shapes payloads for it. I keep business rules out of both."

The problem. A mobile home screen needs data from six services. If the app calls them directly, it makes six calls over a slow network, knows your internal topology, and has to merge and handle errors itself. Any service split ripples into the app.

API composition. One component (gateway, aggregator service or BFF) takes one client request, calls the downstream services, and returns a combined response. Done well, it calls downstream in parallel, each with its own timeout, and returns partial results if a non-critical dependency fails (show the page without recommendations).

Backend for Frontend (BFF). A separate backend per client type: a mobile BFF, a web BFF, a partner API. Why separate? Mobile wants small payloads and few round trips, web wants richer data, partners want stable versioned contracts. Each BFF is owned by its frontend team, so that team can change the shape of its API without queuing behind a central API team.

Example. Web BFF GET /home calls Catalog, Orders and Recommendations in parallel; the mobile BFF calls the same services but returns half the fields and a pre-resized image URL.

Risks.

  • Business rules creep into BFFs and get duplicated in several of them. Keep them to aggregate, translate and authenticate.
  • One big central gateway owned by one team turns into a bottleneck and a monolith in disguise.
  • Fan-out multiplies load: one client request becomes N backend requests, so cache and set limits.

Remember: Compose in parallel with timeouts and partial results; BFF per client type, thin and owned by the frontend team.

API gateway vs service mesh: what is the difference? Senior
Say: "A gateway handles north-south traffic, clients into the system: auth, rate limits, routing. A mesh handles east-west traffic between services: mTLS, retries, telemetry, traffic splitting. They complement each other, and a mesh only pays off at scale."

Picture it. North-south means traffic crossing the system boundary (browser to your backend). East-west means traffic inside (service to service). The gateway sits at the front door. The mesh is plumbing between rooms.

API gatewayService mesh
TrafficNorth-south (clients into the system)East-west (service to service)

How a mesh works. Each pod gets a proxy (commonly Envoy). All traffic in and out goes through it. A control plane pushes policy to the proxies: "service A may call B only with mTLS", "send 5 percent of B traffic to v2", "retry idempotent calls twice". Applications need no code change, in any language.

Costs. An extra hop on each side (typically sub-millisecond to a few milliseconds), CPU and memory per pod, and a real learning curve when debugging (is it the app or the proxy?). Newer sidecar-less ("ambient") modes in some meshes reduce the per-pod cost.

Decision rule. With 5 services, a load balancer plus client libraries for timeouts and plain TLS is enough. With dozens of services and a need for uniform mTLS, policy and canary routing without touching app code, a mesh earns its keep.

Trap: Putting business logic in the gateway. It should be a thin edge, not an orchestration layer.

Remember: Gateway = front door (north-south); mesh = plumbing between services (east-west).

What is the sidecar pattern and why use it? Intermediate
Say: "A sidecar is a helper process deployed beside the main service in the same pod, sharing network and lifecycle, that handles cross-cutting concerns like proxying, mTLS, log shipping or secrets, independent of the app's language."

What it is and why. Cross-cutting concerns (TLS, retries, metrics export, log shipping, config reload) are needed by every service. You could put them in a shared library, but then each language needs its own implementation and every service must rebuild to upgrade. A sidecar moves them into a separate container that runs next to the app in the same Kubernetes pod. They share localhost networking and start and stop together.

Example. Your Java service calls http://localhost:9000/payments. The Envoy sidecar on localhost accepts the call, opens an mTLS connection to the destination pod's sidecar, retries on connect errors, and emits metrics. The Java code has no TLS or retry code at all.

Benefits.

  • Language-agnostic: a Java, Go and Python service all behave the same.
  • Upgradable independently of app code (patch the proxy without rebuilding apps).
  • Consistent behaviour enforced by the platform team.

Costs. Extra CPU and memory for every instance, startup ordering issues (app starts before proxy is ready, or proxy shuts down before the app finishes), and one more thing to debug.

Related shapes. Ambassador: a sidecar that acts as the outbound proxy to a remote service (hides discovery, auth). Adapter: a sidecar that normalises output, for example converting an app's metrics into the format your monitoring expects.

Remember: Sidecar = cross-cutting helper in the same pod; language-agnostic, at the price of per-pod overhead.

How does service discovery work? Client-side vs server-side? Intermediate
Say: "Instances come and go with changing IPs, so callers need a way to find healthy ones. Either the client looks them up in a registry and balances itself, or a stable name or load balancer does it for them. On Kubernetes the platform already does this."

The problem. With autoscaling, rolling deploys and crashes, the set of IPs behind "payments" changes constantly. Hard-coded addresses break within minutes.

Options.

  • Registry-based. Instances register themselves (Eureka, Consul) and send heartbeats; the registry removes ones that go quiet. Callers query the registry.
  • Client-side discovery. The client fetches the instance list and load-balances itself (Ribbon style). Flexible (you can do smart routing), but every language needs the library and logic.
  • Server-side discovery. The client calls a stable name or load balancer that picks an instance (cloud load balancers, Kubernetes Service). Clients stay simple.
  • Platform-native. In Kubernetes a Service gives a stable virtual IP and DNS name (payments.shop.svc). Readiness probes decide which pods receive traffic. No separate registry is usually required.

Walk-through (Kubernetes).

  1. A new payments pod starts; its readiness probe fails until warm-up finishes.
  2. Once ready, it is added to the Service endpoints.
  3. Callers resolve payments by DNS, connect to the Service IP, and the cluster spreads connections across ready pods.
  4. On shutdown the pod is removed from endpoints first, then receives SIGTERM, drains and exits.

Pitfalls. Stale entries (a dead instance listed for a few seconds), DNS caching in the client runtime (a JVM that caches forever never sees new pods), and health checks that say "up" while the real dependency is down. Pair discovery with timeouts and retries on idempotent calls.

Remember: Registry with client-side balancing, or stable name with server-side balancing; on Kubernetes use Services and readiness probes.

Your checkout request goes through 6 services synchronously and p99 latency is 4 seconds. What do you do? Scenario
Say: "I trace first to find the dominant hops, then parallelise, budget deadlines, take non-essential work off the critical path, question the boundaries, and add timeouts, breakers and fallbacks."

Why 6 sync hops hurts. Latency adds along a serial chain, and tail latency is worse than the average: if each hop has a p99 of 600 ms, the chance that at least one of six is slow on a given request is much higher than for one hop. Availability also multiplies down (six at 99.9 percent give about 99.4 percent).

  1. Trace it. Use distributed tracing to draw the waterfall: which hop dominates, and which calls that could run in parallel run serially. Do not guess.
  2. Parallelise independent calls. If pricing, stock and shipping quote do not depend on each other, call them together. Latency becomes the max, not the sum.
  3. Budget deadlines. Give the whole request 1.5 s and propagate a deadline so each hop knows its share; a hop with 100 ms left should not start a 500 ms call.
  4. Take calls off the critical path. Cache slow-changing data, pre-compute, replicate small read copies via events so there is no runtime call.
  5. Move non-essential work to async events. Confirmation email, analytics and loyalty points do not need to block the response.
  6. Question the boundaries. If two services always call each other for one user action, merge them or move the data so one holds what it needs.
  7. Contain slowness. Per-call timeouts, circuit breakers and fallbacks so a slow optional hop degrades the page rather than blocks it.

Example result. Waterfall shows tax (900 ms) and recommendations (1,200 ms) running after stock check. Run them in parallel (saves about 900 ms), make recommendations optional with a 150 ms timeout and fallback (saves about 1 s), move the email to an event. p99 drops from 4 s to well under 1.5 s.

Remember: Trace, parallelise, budget, cut the critical path, fix boundaries, contain slowness.

5. Migration and decomposition

What is the strangler fig pattern? Intermediate
Say: "Strangler fig: put a routing layer in front of the legacy system, build new functionality as new services, and move routes to them one slice at a time until the legacy can be switched off. Each step is small and reversible."

Where the name comes from. A strangler fig is a vine that grows around a host tree and slowly replaces it. The migration works the same way: the new system grows around the old one.

Why it exists. The alternative is a big-bang rewrite: freeze features, rebuild everything, switch on one day. That fails often because the old system keeps changing during the rewrite (a moving target), undocumented edge cases in old code get lost, no value ships for a year, and the cutover is one huge risk. This is the "second system" trap.

How it works, step by step.

  1. Place a router, proxy or gateway (the facade) in front of the monolith. At first it forwards everything to legacy, so nothing changes for users.
  2. Pick one slice, for example /invoices. Build it as a new service.
  3. Test it, possibly with shadow traffic, then flip the route: /invoices goes to the new service, everything else still to legacy.
  4. If something is wrong, flip the route back (instant rollback).
  5. Repeat for the next slice. When the legacy serves nothing, retire it.

What makes it hard. The routing is easy; the data is hard (see database splitting), and legacy concepts must not leak into the new service (use an anticorruption layer). Some functionality is not reachable at the network edge because it is called deep inside the monolith; for that use branch by abstraction (a later question).

Pitfall. No stopping rule. Decide up front that the migration ends when the remaining monolith is small and stable; it may remain as a service.

Remember: Facade in front, move routes one by one, rollback is a route flip, value delivered at every step.

How do you decompose a monolith safely? Give the steps. Senior
Say: "Observe and test first, pick low-risk seams, modularise inside the monolith, untangle data, extract behind an anticorruption layer, shift traffic gradually with shadow then canary, keep rollback, delete the old code, repeat."

Why a procedure. Extraction fails when teams cut code first and discover data coupling later. The order below puts the cheap, reversible work first and the risky work last.

  1. Make it observable and tested. You cannot compare old and new behaviour without metrics, logs and regression tests. Capture baselines: latency, error rate, key business numbers.
  2. Pick seams. Choose modules with clear business meaning, low coupling and high payoff (a hot-scaling part, a high-churn part). Start with an edge capability such as notifications, search or reporting rather than the tangled core, so you learn the process on something forgiving.
  3. Modularise inside the monolith first. Introduce an interface between the module and the rest, and enforce it. This is cheap and trivially reversible.
  4. Untangle data. List the tables the module uses. Remove foreign keys and joins across the seam; replace with API calls or replicated data.
  5. Extract. Build the service with its own schema, an anticorruption layer toward legacy, and the router in front.
  6. Move data and traffic gradually. Shadow traffic first (the new service gets copies, its answers are compared and discarded), then a canary percentage (1, 10, 50), then full cutover. Keep data in sync with change data capture rather than risky dual writes.
  7. Keep a rollback until the new path has run clean for an agreed period, then delete the old code (dead code rots and confuses).
  8. Repeat. Track progress by routes or tables moved. Stop when what remains is small enough to be a service itself.

Example. Notifications module: wrap behind NotificationPort; move its three tables to a new schema; the monolith publishes NotificationRequested events (via outbox); the new service consumes them; compare sent counts for two weeks in shadow mode; flip; delete old code.

Pitfall. Extracting the biggest, most entangled part first because it hurts most. You will learn the process on your hardest case; start small.

Remember: Seams, data, then traffic, each reversible, with the old code deleted at the end.

How do you split a shared database during extraction? Senior
Say: "Map who touches which tables, give each table one owner, cut cross-boundary foreign keys down to IDs, sync the new schema via change data capture, switch reads first then writes, verify, then drop the old columns."

Why it is the hard part. Code can be moved in an afternoon; shared data holds the hidden coupling: joins, foreign keys, reports and transactions that spanned both sides.

  1. Map access. Use static analysis plus database query logs to find which code reads and writes which tables. The logs show real use, not just what the code says.
  2. Assign one owner per table. For tables used by both sides, decide the owner; the other side uses the owner's API or a replicated copy.
  3. Cut cross-boundary foreign keys down to plain IDs. Referential integrity moves from the database to code or events (for example, handle "customer deleted" by event).
  4. Temporary sync phase. The new service gets its own schema, kept in sync from the monolith by change data capture or a sync job. Reads switch first, then writes. Why this order: reads are harmless and reversible, and you can compare results; once reads are clean, a single write path is switched.
  5. Verify. Comparison jobs (row counts, checksums, sample diffs). When they stay clean, stop the sync and drop the old columns.

Example. Moving customer_address out: the monolith keeps writing it, CDC streams changes to the new Customer service's schema, Customer service serves reads, then the profile edit screen is switched to write via Customer service, and the CDC direction ends.

Hard parts. Joins and reports that cross the seam (move them to a read model or warehouse), and transactions that spanned both sides (become sagas or are redesigned). Also watch sequences and ID generation so new IDs do not collide.

Remember: One owner per table, IDs not foreign keys, sync via CDC, reads before writes, verify before dropping.

What are branch by abstraction and parallel run? Senior
Say: "When I cannot route at the network edge because the call is deep inside the monolith, I put an interface in front of it, add a second implementation that calls the new service, and switch with a flag. Parallel run executes both and compares."

The problem. The strangler works when a request enters through a URL. But sometimes the code to replace is called from ten places inside the monolith (a tax calculation, say). There is no network edge to route on.

Branch by abstraction, in steps.

  1. Introduce an interface TaxCalculator and make all ten callers use it. Implementation 1 is the existing code. Behaviour is unchanged, so this can be shipped safely.
  2. Write implementation 2 that calls the new Tax service.
  3. Choose between them with a feature flag (by tenant, percentage or environment).
  4. Ramp the flag up; if wrong, flip it back.
  5. When fully switched and stable, delete implementation 1 and the flag.

"Branch" here is not a version control branch; the code stays on trunk, so no long-lived branches or merge pain.

Parallel run. Run both implementations on the same input, return the old result to the user, and log the differences of the new one. Review mismatches offline. This finds hidden edge cases before you trust the new code. Cost: double work and duplicated side effects, so only run read-only or side-effect-free logic this way (never double-charge a card).

Together. Abstraction makes the switch possible, the flag makes it reversible and gradual, and parallel run makes it evidence-based.

Remember: Interface, two implementations, flag to switch; run both in parallel to compare before trusting.

Management wants a full rewrite as microservices in 12 months. What do you say? Scenario
Say: "I would not commit to a 12-month big-bang rewrite. I would propose a strangler approach with milestones that each deliver value, measured by deploy frequency, lead time and incident rate, and a clear stopping rule."

Explain the risks in business terms. Management responds to risk and money, not architecture slogans:

  • Moving target. The old system keeps getting features and fixes during the rewrite, so you chase it.
  • Lost knowledge. Old code encodes years of edge cases nobody documented. A rewrite quietly drops them and customers find out in production.
  • No value until the end. Twelve months of cost, zero releases; if the date slips (it will), you have nothing.
  • Two systems to run and staff during the transition.

The counter-proposal, with milestones.

  1. Months 1 to 2: observability, regression tests, a routing layer in front of the monolith.
  2. Months 3 to 5: extract the highest-pain module (say, the one that blocks releases or needs scaling) behind the router.
  3. Each following quarter: next slice, with measured outcomes.

Measure improvements to justify continuing: deployment frequency, lead time for changes, change failure rate, incident count, and cost. If the numbers do not improve, stop and reconsider.

Stopping rule. It is fine, and often best, for a stable core to remain a monolith. The goal is business outcomes, not an architecture diagram with no monolith.

When a rewrite is justified. The platform is unsupported or cannot be run, the domain has fundamentally changed, or the system is small enough to rewrite in a few months. State that to show balance.

Remember: Strangler with value at every step and measurable outcomes beats a 12-month big bang.

6. Versioning, compatibility, contracts

How do you change an API or event between services without breaking consumers? Senior
Say: "Services deploy independently so versions overlap in production. I make changes additive and backward compatible, keep consumers tolerant, use expand and contract for anything else, and version only when a break is unavoidable."

Why it matters. During a rolling deploy, old and new versions of producer and consumer run at the same time, and rollbacks put old versions back. So at any moment some consumer talks to a producer of a different version. Every change must survive that overlap.

Safe versus breaking changes.

Safe (backward compatible)Breaking
Add an optional fieldRemove or rename a field
Add a new endpointChange a field's type or meaning
Add an enum value (only if consumers ignore unknowns)Make an optional field required
Loosen validationTighten validation; change semantics silently

Tolerant reader. Consumers ignore fields they do not know and read only the fields they need. (Postel's law: be liberal in what you accept.) This is what makes additive changes safe.

Expand and contract (parallel change), example: rename phone to mobile.

  1. Expand. Producer returns both phone and mobile.
  2. Migrate. Consumers move to mobile one by one, at their own pace.
  3. Contract. When metrics show nobody reads phone, remove it.

When a break is unavoidable, add /v2 (or a new event type or schema version) and run both side by side with a published sunset date and per-consumer usage tracking.

Events. With Avro or Protobuf use a schema registry with a compatibility mode (backward, forward or full) enforced in CI. Never reuse a Protobuf field number; a deleted field's number should be reserved.

Remember: Additive, tolerant reader, expand then contract; version only when forced.

Rolling deploy: consumer needs a new field the producer is adding. In what order do you deploy? Senior
Say: "Producer first, adding the field as optional. Then the consumer, with a fallback if the field is missing. Make it mandatory only later, if ever. If I need 'deploy A then B within minutes', the design has a coordination problem."

Reasoning. During a rolling deploy you cannot guarantee both sides move together, so each intermediate state must work.

  1. Deploy the producer with the new field (optional). Old consumers ignore it (tolerant reader). Nothing breaks.
  2. Deploy the consumer that uses it. It must tolerate the field being absent, because some producer instances may be old during rollout or after a rollback.
  3. Later, optionally tighten (make required) once every producer and consumer version in production emits or handles it.

What if the consumer deploys first? It asks for a field no producer sends yet, so it fails or behaves incorrectly. That is why producer first for additions.

Removal is the mirror image. First stop consumers reading the field and deploy that; verify nothing reads it (metrics); then remove it from the producer.

Request versus response direction. If the new field is in a request (the consumer sends it to the provider), the order flips: the provider (receiver) must learn to accept it first, then clients start sending it. A useful rule: deploy whoever must understand the new thing before whoever sends it.

Red flag. If an instruction says "deploy A and then B within five minutes or errors occur", you have temporal coupling in releases. Redesign with expand and contract so each step is independently safe, and use feature flags to switch the behaviour on later.

Remember: Whoever must understand the new field deploys first; each step safe on its own.

What is contract testing and why not just end-to-end tests? Intermediate
Say: "Consumer-driven contract tests let each consumer record what it uses from a provider, and the provider's CI verifies it. Each side tests alone, fast, with no shared environment, which replaces most slow, flaky end-to-end tests."

The problem. Team A's service calls team B's. B renames a field. Unit tests on both sides pass. You find out in production (or in a shared test environment that is often broken). End-to-end tests across many services are slow, flaky, need everything deployed, and when one fails you do not know which service is at fault.

How consumer-driven contracts (for example Pact) work.

  1. The consumer's tests run against a mock provider. While doing so they record a contract: "when I send GET /orders/42 I expect 200 with id and status". Only fields the consumer actually uses appear.
  2. The contract is published to a broker.
  3. The provider's CI downloads all consumer contracts and replays them against the real provider code (with its dependencies stubbed). If any contract fails, the provider build fails.

Result: B learns in its own pipeline that removing status would break A, before merging. And because only the used subset is checked, B may freely change everything else.

The test pyramid for services. Many unit tests; contract tests at every service boundary; some component tests per service with a real own database and stubbed neighbours; very few end-to-end smoke tests for critical journeys.

Limits. Contracts check shape and the used subset, not business correctness of the provider's logic; that still needs the provider's own behaviour tests. They need discipline (publish contracts, keep the broker current) and work best with a "can I deploy?" gate in the pipeline.

Remember: Consumers publish expectations, providers verify them in CI; contracts replace most E2E tests.

Shared libraries vs duplication across services? Senior
Say: "Share only technical, stable, non-domain code, and treat it as a versioned product. Never share domain models or business rules across services, because that couples release cycles and recreates the distributed monolith. Duplication of small code beats coupling."

The tension. "Do not repeat yourself" is good advice inside one service. Across services, a shared library is a hidden dependency: change it, and every service must upgrade and redeploy, often in lock-step.

Example of harm. A common-domain.jar contains Order, Customer and validation rules. Billing needs a new field on Order. Now Orders, Shipping and Billing must all upgrade the jar, and their releases are coupled through it. Worse, different teams start depending on each other's internals through it.

Fine to shareAvoid sharing
Logging setup, tracing, auth token validation, HTTP client defaults (technical, stable)Other services' DTOs and entity classes
Thin, semantically versioned, backward compatible code with an ownerBusiness rules and validation of the domain
Generated clients from the owner's published API schemaHand-written shared client jars that the owner must keep in sync

Better alternatives. Move cross-cutting technical concerns to the platform: sidecar, mesh, base image. Generate clients from OpenAPI or Protobuf rather than sharing code.

If you share, treat it as a product. Backward-compatible releases, an owner, a changelog, and consumers may upgrade on their own schedule. A security fix may need a forced upgrade; plan for that.

Remember: Share technical plumbing, never domain; across services, coupling costs more than duplication.

URL, header or media-type versioning: which and why? Intermediate
Say: "URL versioning is the most visible and easiest to route, so it is the common choice for public APIs. Header or media-type versioning is cleaner but harder to test. The discipline matters more than the style: version rarely, evolve additively, support few versions, publish a deprecation policy."

Three styles.

StyleExampleProsCons
URL path/v2/ordersVisible, trivial to route, cache and test in a browser"Same resource" has two URLs; encourages whole-API versions
Header or media typeAccept: application/vnd.x.v2+jsonClean URLs, version per representationHarder to test by hand, easy for caches and proxies to mishandle
Query parameter/orders?version=2SimpleEasy to forget, mixes with filters

The real policy matters more.

  • Prefer additive evolution so you rarely need a new version at all.
  • Limit supported versions to two or three; every extra version multiplies testing and support.
  • Publish a deprecation policy: announcement, sunset date, Deprecation or Sunset headers.
  • Track per-consumer usage (by API key or client id) so you know exactly who still calls v1 and can contact them.

Internal APIs. Between teams that control both sides, expand and contract with contract tests often avoids versions entirely. Public and partner APIs, where you cannot force clients to move, need explicit versions.

Remember: URL versions for public APIs; the discipline (additive, few versions, sunset, usage tracking) is what counts.

7. Teams, Conway's law, platform engineering

What is Conway's law and how does it influence architecture? Intermediate
Say: "Conway's law says systems mirror the communication structure of the organisation that builds them. So I shape teams first, into cross-functional teams that own a capability end to end, and the service boundaries follow. That is the inverse Conway manoeuvre."

What the law says. Melvin Conway observed that organisations design systems that copy their own communication structure. It is not a rule you can opt out of; it is a force you either use or fight.

Examples.

  • Separate frontend, backend and database teams produce a layered system where every feature crosses three teams and three queues. Delivery is slow because every change needs hand-offs.
  • Three teams building a compiler tend to produce a three-pass compiler.
  • Two teams that do not talk to each other end up with an awkward, poorly defined interface exactly where they meet.

Why this matters for microservices. Drawing service boxes on a whiteboard does nothing if the teams that own them are organised differently. A service that needs three teams to change it will be changed slowly, or will rot with no owner.

Inverse Conway manoeuvre. Decide the architecture you want, then arrange teams to match. Create cross-functional, stream-aligned teams that own a business capability end to end (code, data, deploy, on-call). Their communication structure then produces the intended boundaries. Example: instead of a "database team", the Checkout team owns the checkout data store itself.

Practical rule. A service should have one owning team. A team may own several services, but one service should never need three teams to change. Draw boundaries where communication is naturally low and ownership is clear.

Pitfall. Reorganising the teams without changing the boundaries (or the reverse). Both must move together or the old structure will pull the system back.

Remember: Architecture mirrors team communication; reshape teams to get the architecture you want.

What are the team types in Team Topologies? Senior
Say: "Team Topologies defines four team types: stream-aligned, platform, enabling and complicated-subsystem, and three interaction modes. The goal is to limit each team's cognitive load, and that is what caps how many services a team can own."

The four types.

TypeJobExample
Stream-alignedDelivers a flow of business value end to end; owns its servicesCheckout team, Onboarding team
PlatformProvides internal self-service capabilities so stream teams carry less loadCI/CD, Kubernetes, observability, secrets
EnablingTemporary coaches that help others adopt a skill, then move onSecurity champions, SRE practice coaches
Complicated-subsystemOwns a part that needs deep specialist knowledgeVideo codec, pricing engine, ML ranking

Most teams (the book suggests the large majority) should be stream-aligned; the others exist to serve them.

Interaction modes.

  • Collaboration: two teams work closely for a short time to discover something. High bandwidth, costly, so keep it temporary.
  • X-as-a-Service: one team consumes another's output through a clear API or product, with little meeting. The normal mode for platform teams.
  • Facilitating: an enabling team helps another get better, then leaves.

Why cognitive load is the key idea. A team can only keep so much in its head: the code, the data, the runbooks, the dependencies. If you hand a team too many or too complex services, quality drops and on-call suffers. So the number and size of services a team owns should fit its capacity, and the platform team's job is to remove undifferentiated load (pipelines, infrastructure) so stream teams can focus on their domain.

Remember: Four team types, three interaction modes, one aim: bound each team's cognitive load.

What is platform engineering and why do microservices need it? Intermediate
Say: "Without a platform, every team builds its own pipelines, monitoring and secrets, and cost grows with each service. A platform team provides self-service golden paths and a service catalogue, run as a product with internal customers."

The problem. Every new service needs: a repository, a CI/CD pipeline, a container build, dashboards and alerts, secrets, service discovery, access control, security scanning. If each team builds these alone you end up with 40 snowflake setups, inconsistent security, and each new service costing days or weeks before the first line of business code.

What a platform team builds (an internal developer platform).

  • Golden paths: a template or scaffold that creates a new service with pipeline, dashboards, alerts, logging and security defaults in minutes. Example: run create-service orders-v2 and get a repo that deploys to staging on its first commit.
  • Shared tooling: build, deploy, observability stack, secrets management.
  • Service catalogue: who owns each service, its dependencies, runbook, SLOs, on-call.

Principles.

  1. Platform as a product: internal teams are customers; talk to them, measure satisfaction.
  2. Make the paved road the easiest road, but allow opt-out for good reasons rather than mandating it.
  3. Measure adoption and outcomes: time to first deploy for a new service, time to restore, percentage of services on the golden path.

Economics. Without a platform, the cost of microservices grows roughly linearly or worse with the number of services. With one, the marginal cost of one more service falls sharply. That is why a platform team is often a precondition for going beyond a handful of services, not an afterthought.

Pitfall. A platform built in isolation that nobody wants, or one that is mandatory but slow and becomes a ticket queue. Co-design it with its users.

Remember: Platform = self-service golden paths plus catalogue; it flattens the per-service cost.

What does "you build it, you run it" mean and what does it require? Intermediate
Say: "The team that writes a service also runs it: on-call, incidents, capacity, cost. It aligns incentives, and it only works with good tooling, sustainable rotations, blameless post-mortems and a platform that removes infrastructure toil."

What it means. No hand-off to a separate operations team. When the pager goes at 3 a.m., it goes to the developers who wrote the code. Werner Vogels of Amazon popularised the phrase.

Why it works. Incentives. If you are the one woken at night by fragile code, you add timeouts, alerts and graceful degradation. If someone else carries the pain, fragile code is cheap to write. It also shortens the feedback loop: production behaviour reaches the people who can fix the cause.

What it requires.

  • Tooling: dashboards, alerts tied to SLOs, runbooks, tracing, so on-call is diagnosis rather than guesswork.
  • Sustainable on-call: a team of two cannot cover 24/7 (leave and sickness make it unsafe); you typically need at least about five or six people in a rotation, or a follow-the-sun arrangement. Compensate and limit interruptions.
  • Blameless post-mortems that fix systems, not people, so incidents get reported honestly.
  • A platform that hides infrastructure toil, or the team spends its time on clusters instead of features.
  • Error budgets to balance feature speed against reliability.

Pitfall. Declaring it without the supporting pieces gives burnout. Also watch for services with no owner (a later scenario).

Remember: You build it, you run it: ownership aligns incentives but needs tooling, rotations and a platform.

How do you keep 50 services consistent without a central architecture committee slowing everyone? Senior
Say: "I standardise the few things that must be uniform and let teams choose the rest. I enforce through templates and automated checks, record decisions in ADRs, and require justification for each new technology."

The tension. A central architecture committee approving everything becomes a bottleneck and teams route around it. Total freedom produces 50 services in 12 languages with 6 ways to log. You want a middle path: aligned autonomy.

What must be uniform (the "must" list):

  • Authentication and authorisation approach.
  • Log format with trace id, tenant id, service name, version.
  • Health endpoints (liveness and readiness) and metrics naming.
  • API style guide: naming, error format, pagination, versioning policy.
  • Deployment method and artifact format.

Everything else (language within an approved set, internal design, datastore within reason) is the team's call.

How to enforce without a committee.

  1. Templates (golden paths): the default service already complies.
  2. Automated checks in CI: lint API specs against the style guide, fail the build for missing health endpoints or vulnerable dependencies. Policy as code beats a wiki page.
  3. Architecture decision records (ADRs): a short document per significant decision (context, options, decision, consequences) in the repo, so the "why" survives staff changes.
  4. A guild or review forum for cross-cutting changes, advisory rather than gatekeeping.

Avoid polyglot for fun. Each extra language or database needs hiring, support, security patching, build tooling and on-call knowledge. Require a written justification for a new technology and a named owner for its support.

Remember: Standardise the few essentials, automate enforcement, record decisions, justify new technology.

8. Multi-tenancy architecture

Pooled vs siloed multi-tenancy: explain and compare. Senior
Say: "Pooled shares everything and is cheapest but riskiest. Siloed gives each tenant a dedicated stack: strongest isolation and highest cost. Bridge shares the app but separates data. In practice I tier: small tenants pooled, large or regulated ones siloed."

What a tenant is. One customer organisation using your SaaS product, with its own users and data that must never mix with other tenants.

Pooled (shared everything)Bridge (shared app, separate data)Siloed (dedicated stack)
ComputeSharedSharedPer tenant
DataShared tables with a tenant_id column (or row-level security)Schema or database per tenantOwn database and often own cluster
Cost per tenantLowestMediumHighest
Noisy neighbour riskHighMedium (shared compute)None
Data leak riskOne missing filter leaks dataLowerLowest
Per-tenant customisation, backup, restore, residencyHardModerateEasy
Ops at 10,000 tenantsEasiestMany schemas to migrateVery heavy

Explaining the differences. In the pooled model, one table holds rows for every tenant and every query has WHERE tenant_id = ?. It is efficient because resources are shared and onboarding a tenant is just inserting a row, but one forgotten filter exposes data, and one tenant's heavy query slows everybody. In the siloed model, onboarding a tenant means provisioning a whole stack: great for isolation, per-tenant backups, data residency (data stays in a given country) and custom versions, but cost and operations grow with every tenant.

Real-world answer: tiered. A free or small tenant is pooled for cost. A large enterprise on a premium plan, or a regulated customer needing residency or dedicated encryption keys, gets a silo. So the architecture should let a tenant be moved between tiers (export and import tooling, tenant routing layer that maps tenant to the stack that serves it).

Decision rule. Choose by the strictest requirement among your customers (compliance, noisy-neighbour tolerance, customisation) weighed against cost per tenant and operational capacity.

Remember: Pooled = cheap, riskier; siloed = isolated, costly; tier by customer and keep tenants movable.

How do you make sure tenant data never leaks in a pooled design? Senior
Say: "I resolve the tenant once at the edge from the authenticated token, propagate it everywhere including async paths, and enforce it at the data layer with row-level security or a mandatory filter so a missing WHERE clause cannot leak data."

Why this is the central risk. In a pooled design, every table holds data for many customers. A single query missing the tenant filter is a data breach. Relying on every developer to remember it in every query is not a control; you need layers.

  1. Resolve tenant at the edge. Take the tenant id from the authenticated token (a claim), never from a client-supplied field or URL parameter that a user could change. Put it in a request context and pass it through every internal call (headers) and message (message headers).
  2. Enforce at the data layer. Row-level security in the database (for example, PostgreSQL policies keyed on a session setting for the tenant id), or a mandatory repository or ORM filter that adds tenant_id automatically. Queries without tenant context should fail, not return everything. This is the "fail closed" principle.
  3. Tenant-aware keys everywhere. Primary keys and indexes start with tenant_id; cache keys include tenant (t42:user:7); search indexes and object-storage paths include tenant.
  4. Guard async paths. Thread pools, scheduled jobs, message consumers and background workers lose the request context unless you carry it explicitly. This is the classic leak source: a consumer processes a message for tenant A, but its context still says tenant B from the previous message. Set and clear the context per message, and put the tenant id in the message.
  5. Test and audit. Automated tests with two tenants asserting that cross-tenant reads and writes fail; periodic scans of queries and logs for missing tenant predicates.

Example. A report endpoint takes ?tenantId=7 from the URL and uses it. An attacker changes it to 8 and reads another customer's data. The fix: ignore the parameter and use the tenant from the token.

Remember: Tenant from the token, carried in all contexts, enforced in the database, tested with two tenants.

One tenant's bulk import slows down everyone. How do you handle noisy neighbours? Scenario
Say: "I isolate the heavy tenant's load: per-tenant rate limits and quotas, separate queues or partitions so one backlog does not block others, bulkheads, throttling to off-peak, and if needed a dedicated cell. Per-tenant metrics tell me early."

The mechanism. A noisy neighbour is a tenant consuming a disproportionate share of a shared resource (CPU, database connections, queue throughput), degrading others. A bulk import of 5 million rows into a shared worker pool and queue means other tenants' small jobs wait behind it.

Layers of defence.

  • Rate limits and quotas per tenant at the gateway (requests per second, concurrent requests, daily imports). Reject or slow excess with a clear response (HTTP 429).
  • Fair scheduling. One shared queue is first come, first served, so a big tenant starves others. Use separate queues or partitions per tenant (or per tier), and a scheduler that round-robins across tenants.
  • Bulkheads. Separate thread or connection pools by tenant class so heavy tenants cannot exhaust the pool that everyone uses.
  • Throttle heavy operations: chunk the import into small batches with pauses, or run it off-peak.
  • Move the tenant to a dedicated cell or silo if their load is permanent.
  • Per-tenant metrics and alerts (requests, latency, queue depth per tenant) so you detect the problem before complaints.

Cell-based architecture. Run many identical, self-contained stacks (cells), each serving a subset of tenants, with a thin router assigning tenants to cells. A bad deploy, overload or noisy neighbour then affects one cell, not all tenants: the blast radius is bounded. Cells also scale by adding another cell instead of growing one giant system.

Example fix. Tenant X's import: limit to 2 concurrent import jobs per tenant, put imports on a per-tenant partitioned queue with a cap of 100 rows per second, alert at queue depth over 10,000. Other tenants are unaffected; X's import takes longer but completes.

Remember: Limit, separate queues, bulkhead, throttle, and use cells to bound blast radius.

How do schema migrations work with schema-per-tenant at thousands of tenants? Senior
Say: "I run migrations as an orchestrated, resumable, idempotent job over tenants in batches, tracking the schema version per tenant, make every migration backward compatible so app versions run against both schemas, and canary on small tenants first."

The problem. With schema per tenant and, say, 5,000 tenants, one ALTER TABLE becomes 5,000 of them. They will not all succeed at once: some tenants have huge tables, some time out, some run into locks. Meanwhile the application is live.

How to do it safely.

  1. Track version per tenant. A control table records each tenant's schema version (tenant 42: v37). Now you know exactly who is migrated.
  2. Orchestrated job in batches. A migration runner picks tenants (say 20 at a time), applies migration steps, records success or failure, and continues. It is resumable: if it dies, it restarts where it stopped.
  3. Idempotent migrations. Running the same migration twice on a tenant is harmless (use IF NOT EXISTS style guards or version checks), so failed tenants can simply be retried.
  4. Backward compatible (expand and contract). Because the rollout takes hours or days, the app must work with both old and new schema at once. Add the new column nullable first, deploy code that handles both, backfill, only later drop the old one.
  5. Canary order. Migrate internal and small tenants first, watch errors, then medium, then the largest.
  6. Handle new tenants: provisioning always starts from the latest schema.

Trade-off. Pooled schemas avoid this orchestration, but concentrate the risk into one large migration that, if it goes wrong, affects everyone, and may lock a very large table. Schema per tenant spreads and limits blast radius at the price of tooling.

Pitfall. Long migrations hold locks on large tenants during business hours; schedule or use online schema change tools.

Remember: Version per tenant, batched, resumable, idempotent, backward compatible, canary first.

9. Hexagonal architecture, serverless, deployment units

What is hexagonal (ports and adapters) or clean architecture, at concept level? Intermediate
Say: "Hexagonal architecture keeps business logic in the centre with no dependency on frameworks, databases or protocols. The core defines ports (interfaces), adapters implement them on the outside, and dependencies point inward."

The problem it solves. In a typical layered app, business rules call JPA entities, HTTP types and framework classes directly. You cannot test a rule without a database, switching from REST to messaging touches everything, and the framework leaks into the heart of the code.

The idea. The core (domain and use cases) depends on nothing technical. It defines ports:

  • Inbound ports (what the core offers): PlaceOrder.
  • Outbound ports (what the core needs): OrderRepository, PaymentGateway.

Adapters sit outside and implement or call the ports: a REST controller or Kafka consumer calls PlaceOrder; a JPA class implements OrderRepository; an HTTP client implements PaymentGateway. By the dependency inversion principle, source code dependencies point inward: adapters know the core, never the reverse.

Tiny example. A unit test creates PlaceOrder with an in-memory OrderRepository and a fake PaymentGateway: no database, no network, runs in milliseconds, tests the real rules.

Why it helps microservices.

  • Fast, isolated tests of the domain.
  • Swap transport (REST to gRPC to events) or store without touching rules.
  • When extracting a module from a modular monolith, only the adapter changes: an in-process call becomes a remote call.

Cost. More interfaces and mapping code; overkill for a trivial CRUD service. Use it where there are real business rules to protect.

Remember: Core defines ports, adapters implement them, dependencies point inward.

What are the trade-offs of serverless (functions as a service) as an architecture? Senior
Say: "Serverless gives scale-to-zero, per-invocation billing and no servers to run, which is great for spiky and event-driven work. The costs are cold starts, execution limits, statelessness, database connection pressure, lock-in and cost at steady high load."

What it is. Functions as a service (AWS Lambda, Azure Functions and similar): you upload code, the platform runs it per event, scales instances automatically and bills per invocation and duration. You manage no servers.

StrengthsWeaknesses
No server management; scale to zero and to thousands automaticallyCold starts add latency (tens of ms to seconds depending on runtime and size)
Pay per invocation: excellent for spiky or low trafficAt steady high load it can cost more than containers or VMs
Fast to build event-driven glue (file upload triggers a function)Execution time, memory and payload limits; not for long jobs
Built-in availability across zonesStateless: state must live elsewhere; connection pooling to databases is hard (many concurrent functions exhaust DB connections; use a proxy or HTTP data API)
Vendor lock-in; local testing and debugging are harder; many tiny functions create nanoservice sprawl and hard-to-trace flows

Two worked points.

  • Cold start. If no warm instance exists, the platform must start a runtime, load your code and initialise it before handling the request. A large Java function may take seconds; a small Go or Node function far less. Mitigate with provisioned concurrency (pre-warmed instances), smaller packages, and faster-starting runtimes.
  • Database connections. 1,000 concurrent invocations each opening a connection can exceed a relational database's connection limit, so use a connection proxy or a data API, and set function concurrency limits to protect downstream systems.

Good fits: webhooks, scheduled jobs, image or file processing, glue between managed services, unpredictable bursty APIs. Poor fits: latency-critical steady high-throughput services, long-running stateful processing.

Break-even thinking. Roughly, serverless wins when utilisation is low or spiky; a container that is busy most of the time is cheaper per request. Do the arithmetic with your own traffic.

Real-world note. In 2023 Amazon Prime Video engineers described moving one video-quality monitoring component from a distributed serverless design back to a single process, cutting its infrastructure cost substantially (they reported about 90 percent). The lesson is that per-call overhead and data passing between stages can dominate; it was one component, not a verdict on serverless.

Remember: Serverless for spiky, event-driven, glue work; watch cold starts, limits, connections and steady-load cost.

What deployment units exist (VM, container, function, pod) and how do you pick? Intermediate
Say: "Containers are the default deployable for microservices, a pod is the unit Kubernetes schedules, VMs suit legacy or special needs, and functions give most elasticity with least control. The real test is the independently deployable unit."

The options.

UnitWhat it isPick it when
VMFull virtual machine with its own OSStrong isolation, legacy software, special OS or licensing needs; slow to start, heavier
ContainerA process plus its dependencies in an imageDefault for microservices: fast start, dense packing, same artefact from laptop to production

The real test. Packaging does not decide independence. If two things must always deploy together, they are one deployment unit, however many containers they use. Conversely, two containers that must always ship together are still one unit. So the question to ask is "can I deploy this alone, safely, at any time?".

Good practices.

  • Immutable images: never patch a running instance; build a new image and replace it.
  • One artefact, promoted through environments: the exact image tested in staging is what runs in production.
  • Configuration injected at runtime (env vars, mounted files), not baked into the image.
  • Pin base images and scan them for vulnerabilities.

Remember: Containers by default, pods for app plus sidecar, and independent deployability is the real test.

Blue/green, canary and rolling deployments: how do they differ? Intermediate
Say: "Rolling replaces instances gradually, blue/green switches traffic between two full environments for instant rollback, and canary sends a small percentage to the new version while watching metrics. All three need backward-compatible schemas and APIs."

Why several strategies. They trade off cost, speed of rollback and how much real traffic sees a bad version.

Canary walk-through. Deploy v2 to 5 percent of traffic. An automated check compares error rate and p99 latency against v1 for 10 minutes. If fine, go to 25, then 100 percent. If error rate rises, traffic returns to v1 automatically and only 5 percent of users saw the problem.

Common limits.

  • Database changes must work with both versions at once (expand and contract); the database is usually not duplicated in blue/green.
  • Canary needs trustworthy health signals and enough traffic to be statistically meaningful.
  • Rolling and canary mean mixed versions: APIs and messages must be backward compatible.

Rule. Rolling for low-risk everyday changes, blue/green when you need instant rollback and can afford capacity, canary for large systems where limiting exposure matters most.

Remember: Rolling = cheap, blue/green = instant switch, canary = least exposure; all need compatibility.

10. 12-factor, config, feature flags, observability

What is the 12-factor app and which factors matter most for microservices? Intermediate
Say: "The 12-factor app is a methodology for cloud-native services. The factors that matter most are stateless processes, config in the environment, disposability with graceful shutdown, and logs as streams, which together let the platform scale and replace instances freely."

The twelve in one line each. Codebase (one repo per deployable, many deploys); dependencies (declared explicitly); config (in the environment); backing services (databases and queues as attached resources); build, release, run (strictly separate stages); processes (stateless, share nothing); port binding (the service exports itself over a port); concurrency (scale out by running more processes); disposability (fast start, graceful stop); dev/prod parity; logs (written to stdout as event streams); admin processes (one-off tasks run from the same code).

The four that matter most, with why.

  • Stateless processes. If a request's state lives in one instance's memory, the next request must reach that instance, so you cannot freely scale out, replace or restart. Keep sessions and caches shared in a store (Redis, database). Then any instance can serve any request.
  • Config in the environment. The same image runs in dev, staging and production; only environment variables or mounted files differ. This is what makes "promote one artefact" possible.
  • Disposability. Instances are started and stopped constantly (autoscaling, deploys, node failures). On SIGTERM the service should stop accepting new work, finish in-flight requests, deregister, then exit, within the platform's grace period (30 seconds is a common Kubernetes default). Startup should take seconds.
  • Logs as streams. The app writes events to stdout; the platform collects and ships them. The app does not manage log files, rotation or shipping.

Example of a violation. A service stores uploaded files on its local disk. Scale to two instances and half of the downloads return 404, and a restart loses data. Fix: use object storage as a backing service.

Caveat. The list was written around 2011 for web apps; modern practice adds items such as observability and API-first design, but the core remains valid.

Remember: Stateless, config in env, disposable, logs to stdout, one artefact for all environments.

How do you manage configuration and secrets across many services and environments? Intermediate
Say: "One build, config injected per environment, kept in versioned Git (GitOps) and a config store, secrets in a vault with short-lived rotated credentials, and config changes rolled out progressively like code."

Why it needs a plan. With 50 services and 4 environments you have hundreds of config sets. Ad hoc config leads to drift (staging differs from production in ways nobody knows), leaked secrets and outages from a bad change.

  • Separate config from code and from the artefact. One image, different config per environment, via environment variables, mounted files or a config service.
  • Versioned, audited, reviewed. Keep config in Git (GitOps) so each change has an author, a review and a revert. Platforms: Kubernetes ConfigMaps, Consul, Spring Cloud Config, cloud parameter stores.
  • Secrets in a vault (HashiCorp Vault, cloud secret manager), never in Git or images. Prefer short-lived, automatically rotated credentials, and access by service identity (the workload proves who it is) rather than a shared password.
  • Dynamic reload for safe values (feature flags, rate limits, log levels); restart for risky ones (connection strings).
  • Validate at startup and fail fast. A service with a missing or malformed setting should refuse to start rather than run half-configured.
  • Avoid drift by generating per-environment config from one source of truth with overrides.

Incident pattern. A bad config value pushed to every service at once is a classic cause of wide outages: there is no canary and no easy rollback. Roll config out progressively (one region or a small percentage first), watch health, and keep the previous version one command away.

Pitfall. Secrets in environment variables can leak through crash dumps or process listings; mounted secret files or direct vault fetch is safer for the most sensitive values.

Remember: One build, injected config, Git for config, vault for secrets, roll out config like code.

What are feature flags and how do they help a microservice architecture? Intermediate
Say: "A feature flag is a runtime switch that turns behaviour on or off without a deploy. It separates deploy from release, enables gradual rollout and kill switches, and supports migration. The price is flag debt, so every flag needs an owner and an expiry."

What it is. Code like if (flags.isOn("new-checkout", tenant)) { newFlow(); } else { oldFlow(); }, where the value comes from a flag service or config that can change at runtime.

Why it helps microservices.

  • Deploy is not release. Ship the code dark (off), then enable it when ready. This reduces the risk of every deploy and lets teams merge to trunk continuously.
  • Gradual rollout by percentage, tenant or region, watching metrics as you widen.
  • Kill switch. If a feature misbehaves, turn it off in seconds without rollback of the build.
  • A/B experiments.
  • Migration. Route to old or new implementation during a strangler migration (branch by abstraction).
  • Decoupled releases. A new producer behaviour can ship days before consumers are ready, enabled only when they are.

Kinds of flag. Release flags (short-lived), experiment flags (short-lived), operational flags or kill switches (long-lived), and permission flags (entitlements by plan). Keep them separate, since their lifecycles differ.

Risks and how to handle them.

  • Flag debt. Hundreds of stale flags, and a combinatorial explosion of states nobody tests. Give each flag an owner and an expiry date and delete it after full rollout.
  • The flag service is a dependency. Evaluate locally using cached rules, and define a safe default if the service is unreachable.
  • Cross-service consistency. If service A and B must agree on a flag for a user, give both the same evaluation context (user id, tenant) and rules, or pass the decision along in the request.

Remember: Flags decouple deploy from release; they need owner, expiry, local evaluation and safe defaults.

What observability do microservices need that a monolith does not? Senior
Say: "In a monolith a stack trace tells the story. With services one request spans many processes, so I need distributed tracing with propagated ids, centralised structured logs, RED and USE metrics, correct health checks, and SLO-based alerts."

Why it is different. A user clicks once; five services handle parts of it. Without correlation, each service's logs show only a fragment and you cannot tell which hop failed or was slow.

  • Distributed tracing. A trace id is created at the edge and propagated on every call and message (W3C traceparent header, OpenTelemetry). A trace shows a waterfall of spans so you see which hop is slow or failing.
  • Centralised structured logs. JSON, with trace id, tenant id, service, version, shipped to one searchable place. Searching the trace id returns the whole story.
  • Metrics. The RED method per service: Rate (requests per second), Errors, Duration (latency percentiles). The USE method for resources: Utilisation, Saturation, Errors. For async consumers add queue lag.
  • Health checks. Liveness answers "should I be restarted?" and readiness answers "should I receive traffic?". Do not make liveness depend on downstream services: if the database is down and every pod's liveness fails, the platform restarts them all and makes the outage worse.
  • SLOs and alerts. Alert on user-facing symptoms (error budget burn: "we are consuming the month's allowed errors at 10 times the sustainable rate") rather than on every internal cause, to avoid alert fatigue.
  • Service dependency map and a catalogue of owners and runbooks.
  • Deployment markers on dashboards to correlate regressions with releases.

Cost. Traces and logs at full volume are expensive. Sample traces (head-based decides at the start; tail-based decides after seeing the result, so you can keep errors and slow ones), and set log retention tiers (hot for days, cold for months).

Remember: Trace ids everywhere, structured logs, RED and USE, readiness versus liveness, SLO-based alerts.

How do you keep a trace across asynchronous messaging? Senior
Say: "I put the trace context in the message headers when producing, and the consumer extracts it and starts a child span, or a linked span for batches. I log the trace id and message id on both sides and track consumer lag and dead-letter depth."

The problem. In HTTP, the trace header travels with the request automatically (if your client library propagates it). A message broker breaks that chain: the producer sends and moves on, the consumer runs later, possibly on a different machine. If nothing carries the context, the trace ends at the broker and async flows are invisible.

How to keep it.

  1. Producer: when publishing, inject the current trace context (traceparent) into the message headers (for example Kafka record headers).
  2. Consumer: extract the context from the headers and start a new span as a child of the producer span. In the trace UI, the consumer work appears under the original request, with the queue wait time visible as the gap between spans.
  3. Batches: a consumer that reads 100 messages at once serves 100 different traces. A single parent does not fit, so create one span for the batch and add links to each message's context.
  4. Logs: include trace id and message id (and partition and offset) on both sides, so a search finds the full path.

Also measure the async-specific signals. Consumer lag (how far behind the consumer is), age of the oldest unprocessed message, dead-letter queue depth, and retry counts. Alert on lag growth because it is the async equivalent of latency.

Pitfall. Libraries that auto-instrument HTTP but not your broker client; check that headers are really propagated end to end with a test trace.

Remember: Trace context in message headers, child or linked spans, lag and DLQ as first-class metrics.

Which resilience patterns are architecture-level for microservices? Senior
Say: "Timeouts everywhere with deadline propagation, bounded retries with backoff and jitter on idempotent calls, circuit breakers, bulkheads, fallbacks, load shedding, and idempotency keys on writes."

Why architecture-level. In a distributed system, partial failure is normal. These patterns are policies applied across all services, not details of one.

  • Timeouts everywhere, with a deadline propagated down the chain. This is the single most important rule: with no timeout, one slow dependency holds your threads forever until you are down too.
  • Retries only for idempotent operations, with exponential backoff and jitter (randomness so clients do not retry in sync) and a retry budget. Retries multiply across layers: three layers each retrying three times means 27 times the load on the bottom service.
  • Circuit breaker. After repeated failures, stop calling the dependency and fail fast; after a cool-down, let a few probe calls through (half-open) to see if it recovered.
  • Bulkhead. Separate pools (threads, connections) per dependency so one slow dependency cannot use every thread.
  • Fallback and graceful degradation. If recommendations are down, show cached or generic items instead of an error page.
  • Load shedding and back-pressure. When overloaded, reject excess work early (with 503 or 429) rather than queueing until everything is slow.
  • Idempotency keys on writes: the client sends a unique key; the server stores the result and returns it on a repeat, so a retried payment does not charge twice.

How they combine. A call to the recommender: 200 ms timeout, one retry with jitter, breaker opens after 50 percent failures over 20 calls, small dedicated pool, fallback to cached items. Each layer handles a different failure shape.

Pitfall. Configuring them independently without thinking about the total: a 30 second timeout times three retries is 90 seconds of hanging for the user.

Remember: Timeouts first; bounded retries with jitter; breakers; bulkheads; fallbacks; shed load; idempotent writes.

11. Cost, complexity and failure modes

What does microservices cost you? Be honest. Senior
Say: "Microservices cost distributed-systems complexity, operational overhead, infrastructure spend, harder testing and debugging, data challenges, and organisational load. They repay this only when the organisation is large enough that monolith coordination costs more."

Where the costs come from.

  • Distributed-systems complexity. Partial failure, latency, timeouts, eventual consistency, duplicates and ordering all appear. A method call becomes a call that can fail in several ways.
  • Operational overhead. Many pipelines, deployments, version combinations, certificates and on-call rotations; it needs a platform team.
  • Infrastructure cost. Each service has baseline CPU and memory, replicas for availability, sidecars, log and trace volume, and cross-zone network traffic (cloud data transfer between zones or regions is billed, and chatty services add up). Ten services at 3 replicas each is 30 running processes before any traffic.
  • Testing and debugging. No single stack trace; integration environments are expensive and flaky.
  • Data challenges. No joins, no ACID across services, reporting needs a warehouse or CQRS.
  • Organisational load. Skills, standards, ownership, documentation.
  • Slower start. Much groundwork before the first feature ships.

When it pays. When the cost of many people coordinating in one codebase (merge conflicts, release trains, cross-team blocking) exceeds the above. This is a function of team size and boundary stability, not of the technology.

Evidence of consolidation. Some well-known companies have publicly described consolidating services back; Segment's 2018 write-up on moving from many per-destination services to one is a frequently cited example, because the overhead outweighed the benefit at their team size.

Remember: Be honest about the tax; microservices are a trade, justified at organisational scale.

One non-critical service (recommendations) becomes slow and the whole site goes down. Explain and fix. Scenario
Say: "Callers wait on the slow service with long or no timeouts, their threads fill up, they stop serving everything else, and their callers back up in turn. Fix in layers: short timeout, circuit breaker, bulkhead, fallback and load shedding, and classify dependencies as critical or optional."

The mechanism, step by step.

  1. The recommender slows from 50 ms to 20 s (a bad query, a GC pause, a noisy neighbour).
  2. The product page service calls it with a 30 s timeout (or none). Each request now holds a thread for 20 s.
  3. With, say, 200 threads and 100 requests per second, all threads are busy within two seconds.
  4. The page service can no longer serve even requests that do not need recommendations (checkout, search). It looks down.
  5. Its callers wait on it, so their threads fill up too. The failure propagates upward: a cascading failure.
  6. Clients and layers retry, multiplying load on the struggling recommender, so it cannot recover.

Fix in layers.

  • Short timeout on the optional call (for example 200 ms).
  • Circuit breaker that opens after repeated failures, so calls fail immediately without waiting.
  • Bulkhead: this dependency gets its own small pool (say 10 threads), so at worst 10 threads are wasted, not all 200.
  • Fallback: cached or generic recommendations so the page still renders.
  • Load shedding on the recommender so it rejects excess instead of queueing.
  • Alerts on dependency latency, not only on errors.

Prevent recurrence. At design time, mark each dependency as critical (checkout cannot proceed without payment) or optional (recommendations, loyalty badge). Optional dependencies must degrade, never block. Test with chaos experiments in staging: inject latency into the recommender and verify the page still works.

Remember: Slow is worse than down; timeouts, breaker, bulkhead and fallback turn a hard dependency into a soft one.

After a short database blip, all services keep failing for 20 minutes even though the database recovered. Why? Scenario
Say: "A retry storm and thundering herd: when the database recovers, thousands of clients retry at once, each layer multiplies retries, pools are exhausted and caches refill together, so the dependency falls over again. The fix is backoff with jitter, retry budgets, breakers with gradual probing, coalescing and load shedding."

The feedback loop.

  1. A 30 second database blip makes calls fail.
  2. Every client retries immediately, often at several layers (client, gateway, service, driver). Three layers with three retries each is up to 27 times the original load.
  3. When the database comes back, it faces a burst far above normal traffic, so it slows or fails again.
  4. Those failures trigger more retries. The system stays overloaded even though the original cause is gone: the failure is now self-sustaining.
  5. Other amplifiers: connection pools full of queued requests; caches whose entries expired together all refilling at once (a cache stampede); health checks failing and killing pods that then restart together.

Fixes.

  • Exponential backoff with jitter: wait 100 ms, 200, 400, each randomised, so clients spread out instead of hitting in unison.
  • Retry budget: cap retries at, say, 10 percent of normal traffic; beyond that, fail fast.
  • Retry at one layer only, typically the closest to the failure, not every layer.
  • Circuit breakers with gradual half-open probing: let a trickle through first, increase as success returns.
  • Request coalescing and staggered TTLs: one request refills a cache entry while others wait, and TTLs get random jitter.
  • Load shedding: reject excess requests early so the queue never grows beyond what the system can drain.

Context. Published post-mortems from large cloud providers have described this class of feedback loop (retries and overload sustaining an outage after the trigger passed), so it is a well-known failure mode and a common interview probe.

Remember: Recovery needs gentle ramp-up: jittered backoff, retry budgets, shedding, one retry layer.

Every release needs 5 teams to deploy together on a Saturday night. What is wrong and what do you do? Scenario
Say: "That is a distributed monolith: services coupled by schema or API shape. I find why each past release needed coordination, introduce expand and contract and tolerant readers, add contract tests, use feature flags, remove shared database access, and merge services that always release together."

Diagnose with evidence. Look at the last five coordinated releases and for each ask: why could the services not deploy separately? Typical answers: a renamed field, a mandatory new parameter, a shared database column, or a shared library bump.

Fixes mapped to causes.

CauseFix

Breaks discovered lateConsumer-driven contract tests in CI, a "can I deploy?" gate
New behaviour must start everywhere at onceFeature flags: deploy dark, enable later

Metric. Track "percent of releases that were independent" (deployed one service alone without coordinating). Set a target and review it. It shows progress objectively and keeps the effort funded.

Immediate relief. Reduce the Saturday-night risk now: rehearse the release in staging, automate the deploy order, add a rollback plan. But treat that as a stopgap, not the solution.

An old service has no owner and still takes production traffic. What do you do? Scenario
Say: "I find who depends on it from traces and gateway logs, find its business function, assign an owner, add it to the catalogue with a runbook and alerts, patch it, then decide keep, merge or retire. I prevent recurrence by making an owner mandatory."

Why it is dangerous. An unowned production service has nobody who patches dependencies, answers alerts or understands its behaviour. It will fail at the worst moment and nobody will know how to fix it.

  1. Discover the consumers. Use distributed traces and gateway or load balancer logs to see who calls it and how often. Also check scheduled jobs and message subscriptions.
  2. Discover the purpose. Last committers (version history), old tickets and documentation, and the business function it serves (billing? reports?). Ask the consumers.
  3. Assign an owner. The team that depends on it most, or the nearest domain team. Ownership means on-call, patching, a budget.
  4. Make it safe. Add it to the service catalogue with a runbook, alerts, dashboards, and a dependency upgrade for security issues (it is probably old).
  5. Decide its future. Keep as is, merge into an owned service, or retire with a deprecation plan (announce, migrate consumers, turn off traffic gradually, then delete).

Prevent recurrence. Require an owner field for every service in the platform, so deploys without one fail. Run regular reviews that flag services with no commits and no owner or no recent traffic. Include ownership transfer in team reorganisations.

Careful on retirement. "Zero traffic for a month" can miss quarterly or yearly jobs; check before deleting, and use a scream test (switch off briefly) with a rollback plan.

Remember: Find consumers and purpose, assign an owner, make it safe, then keep, merge or retire.

How do you test a microservice architecture without an environment where everything runs? Senior
Say: "Many unit tests on the domain core, component tests per service with stubbed neighbours, consumer-driven contract tests at every boundary, very few end-to-end smoke tests, plus safe testing in production and resilience experiments."

Why not one big environment. Running all services together for every test is slow, expensive, flaky and hard to diagnose. The aim is to test each service alone with confidence that the boundaries match.

  • Unit tests on the domain core. Cheap and fast, especially with a hexagonal design where the core has no framework or database dependency.
  • Component tests. Run one service with its real own database (a container) and replace neighbours with stubs or contract-verified mocks. This tests the service as deployed, minus the network to others.
  • Consumer-driven contract tests at every boundary, in both directions, so the stubs cannot silently drift from reality.
  • A handful of end-to-end smoke tests on critical journeys only (sign up, pay), run after deploy. Keep them few, because each is a flaky, slow liability.
  • Testing in production, safely. Canary releases, synthetic monitoring (a robot performs a purchase every minute), feature flags, shadow traffic, and fast rollback. Some failure modes only appear at real scale and real data.
  • Resilience testing. Fault injection and chaos experiments: kill a dependency, add latency, drop messages, and verify timeouts, breakers and fallbacks work.

Shape. A test pyramid: wide at the bottom with unit tests, narrow at the top with end-to-end. Contract tests sit at the service boundaries and replace most of what E2E tests used to do.

Pitfall. Mocks written by hand and never verified against the real provider; they pass while production breaks. Use contract verification to keep them honest.

Remember: Test each service alone, verify boundaries with contracts, keep E2E tiny, and learn from production safely.

Orchestration vs choreography for a long business process: which and what goes wrong? Senior
Say: "Choreography hides the process: nobody can say where order 42 is. Orchestration risks a god service with all the logic. I use a durable orchestrator or workflow engine that only coordinates and tracks state, while each step's business rules stay in the owning service."

Choreography problems. The business process exists only as a pattern of reactions, so:

  • Nobody can answer "where is order 42 now and why is it stuck?" without searching several services' logs.
  • Cyclic dependencies creep in (A reacts to B which reacts to A).
  • Adding or reordering a step means editing several services.
  • Testing the whole flow requires running them all.

Orchestration problems.

  • The orchestrator becomes a god service that knows every rule, so changing any business rule needs a change there; services become anemic (just CRUD).
  • It is a single point of failure if not made durable and highly available.
  • Teams queue behind the team that owns it.

The practical balance.

  1. Use an orchestrator or workflow engine (Temporal, a state machine service, or similar) that only sequences and tracks state: it says "now do payment", "now reserve stock".
  2. The business rules of each step (is this card valid? is this stock available?) stay inside the owning service. The orchestrator never decides those.
  3. Make it durable: process state persisted, restart-safe, retries and timers handled.
  4. Run it highly available.
  5. Expose process state for support and monitoring: a dashboard showing the step each order is at, with the ability to retry or cancel.

Rule of thumb. Short, simple reactions: choreography. Long-running, branching, time-sensitive processes with compensation: orchestration with the discipline above.

Remember: Orchestrator coordinates and tracks; owning services keep the rules; make it durable and visible.

When would you NOT use an API gateway or mesh at all? Intermediate
Say: "With a handful of services, one team and one cluster, a simple load balancer or ingress with auth plus client libraries is enough. I adopt a gateway or mesh when the problems it solves actually appear."

What each costs. An API gateway adds a network hop, a component to run, and a place where teams queue for changes. A service mesh adds a sidecar per pod (CPU, memory, startup time), a control plane to operate, and a steep debugging curve (is the failure in the app or in the proxy?).

When you do not need them.

  • 5 services, one team, one cluster: a managed load balancer or Kubernetes ingress handles routing and TLS; a small auth filter or the framework's security handles authentication; a resilience library (timeouts, retries, circuit breaker) handles east-west failures.
  • Few external routes, so there is no need for a central policy point.
  • No requirement for uniform mTLS between services, or the cluster network is already trusted and segmented.

Trigger conditions to adopt.

Problem that appearsAdopt
Many public routes needing uniform authentication, rate limits, API keys, versioned public APIsAPI gateway
Dozens of services needing uniform mTLS, policy, telemetry and traffic shifting without code changes, in several languagesService mesh

Principle. Add infrastructure to solve a named problem, not in advance. Each component you add must be run, upgraded, secured and understood by the on-call engineer at 3 a.m. Simplicity is an architectural feature.

Remember: Do not add a gateway or mesh until the problem exists; start with LB, ingress and libraries.
