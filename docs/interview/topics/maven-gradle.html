Mental model: the 8 ideas everything hangs on

One line: a build tool does three jobs: it decides what order to do things in (lifecycle or task graph), it finds the libraries you need (dependency resolution from repositories), and it avoids repeating work (caches). Maven does this by convention and a fixed lifecycle. Gradle does it with a flexible task graph and strong caching.
  1. Coordinates. Every library is named by group, artifact and version (GAV), for example org.slf4j:slf4j-api:2.0.13. Everything else (repositories, caches, conflicts) is about finding and choosing GAVs.
  2. Declarative versus programmable. Maven is an XML description plus a fixed lifecycle. Gradle is a real program (Groovy or Kotlin) that builds a graph of tasks.
  3. Lifecycle or task graph. Maven runs phases in a fixed order and plugins attach goals to phases. Gradle runs tasks in dependency order and skips the ones whose inputs did not change.
  4. Transitive dependencies. You declare 10 libraries and get 200 on the classpath. The tool must pick one version of each library. Maven picks the nearest to your project, Gradle picks the highest.
  5. Scopes and configurations. A library can be needed at compile time, at run time, only for tests, or only provided by the server. Maven calls this scope, Gradle calls it configuration.
  6. Repositories and caches. A local cache on your machine, then your company proxy (Nexus or Artifactory), then Maven Central. Most "works on my machine" bugs live in this chain.
  7. Reproducibility. Same input should give the same output. Fixed versions, wrappers, locked dependencies and no surprise SNAPSHOTs are how you get it.
  8. Fast feedback. Incremental builds, build caches, parallel module builds and daemons exist only to make the second build much faster than the first.

1. Maven core: lifecycle, POM and structure

What is Maven, and what problems does it solve? Basic

What the interviewer is testing: do you know that Maven is about convention, a standard lifecycle and dependency management, not just "a thing that downloads jars".

Maven is a build and dependency management tool for Java and other JVM projects. You describe the project in a pom.xml file (Project Object Model): what it is, which libraries it needs, how it is packaged. Maven then gives you a standard build: compile, test, package, install, deploy. It follows "convention over configuration". Sources go in src/main/java, tests in src/test/java, output in target/. If you follow the layout, you write almost no build logic. Maven also downloads libraries and their dependencies from repositories, so nobody has to copy jars into a lib folder. Before Maven, every project had its own Ant script and its own layout, so a new developer had to learn each one.

Likely follow-ups
  • What is the cost of the convention approach? It is rigid. Unusual builds need plugin configuration or a custom plugin, which is where Gradle is easier.
  • Is Maven only for Java? No. It builds Kotlin, Scala, and others through plugins, and packages many things, but Java is the home ground.
Explain the Maven lifecycles and phases. What happens when you run mvn package? Basic

What the interviewer is testing: the most asked Maven question. They want to hear that phases run in order, and that running a phase runs all earlier phases too.

Maven has three built-in lifecycles: clean (delete target/), default (build and deploy), and site (generate documentation). A lifecycle is an ordered list of phases. The main phases of the default lifecycle are: validate, compile, test, package, verify, install, deploy, with many small ones in between (generate-sources, process-resources, test-compile, integration-test and so on). When you run a phase, Maven runs every phase before it, in order, then that phase. So mvn package runs validate, compile, test, and package. It does not run install or deploy. mvn clean package runs the whole clean lifecycle up to clean, then the default one up to package. A phase itself does nothing. It is only a slot. Work is done by plugin goals that are bound to it.

Likely follow-ups
  • Difference between install and deploy? Install copies the artifact to your local ~/.m2. Deploy uploads it to a remote repository such as Nexus.
  • Can I run one phase without the earlier ones? No, but you can call a goal directly, for example mvn compiler:compile.
What is the difference between a phase, a goal and a plugin? Basic

What the interviewer is testing: the vocabulary. Many candidates mix these up.

A plugin is a package of related actions, for example maven-compiler-plugin. A goal is one action inside a plugin, written plugin:goal, for example compiler:compile or dependency:tree. A phase is a named step in a lifecycle. Goals are bound to phases. For jar packaging, compiler:compile is bound to the compile phase by default. You can run a phase (mvn test) which triggers all the bound goals, or run a goal directly (mvn dependency:tree) which skips the lifecycle. You can also mix them: mvn clean dependency:tree package runs in the order you typed. Some goals, such as dependency:tree, are not bound to any phase, so they only run when you ask.

mvn package                  # a phase: runs everything up to package
mvn dependency:tree          # a goal: just that action
mvn clean install -DskipTests
What is in a pom.xml? What are the Maven coordinates? Basic

What the interviewer is testing: basic fluency with the file you edit every week.

The coordinates identify an artifact: groupId (the organisation or product, like com.acme), artifactId (the module name), version, and optionally packaging (jar, war, pom) and a classifier (such as sources or linux-x86_64). The file also holds a parent, properties (values you reuse), dependencies, dependencyManagement (version control only), build (plugins, resources), profiles, modules (for multi-module projects), and distributionManagement (where to publish). On disk, a repository stores an artifact at a path made from its coordinates: com/acme/orders/1.2.0/orders-1.2.0.jar. Once you know that rule, you can find any artifact by hand.

<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.acme</groupId>
  <artifactId>orders</artifactId>
  <version>1.2.0-SNAPSHOT</version>
  <packaging>jar</packaging>
  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-api</artifactId>
      <version>2.0.13</version>
    </dependency>
  </dependencies>
</project>
Likely follow-ups
  • What is a classifier? An extra label so one version can have several files: -sources, -javadoc, -tests.
What is the Super POM and the effective POM, and why do I care? Intermediate

What the interviewer is testing: do you know where hidden configuration comes from, which is the key to debugging "why does Maven do this?".

Every POM silently inherits from the Super POM, which is built into Maven. It defines Central as the default repository, the default directory layout, and default plugin versions. Your POM, its parent POMs, active profiles, and settings are merged into the effective POM, which is what Maven really uses. When something behaves strangely, such as a plugin version you never set, a repository you never added, or a property with an odd value, ask Maven to show the result. It prints the merged XML, and you can see which parent or profile contributed each part.

mvn help:effective-pom -Doutput=effective.xml
mvn help:effective-settings
mvn help:active-profiles
mvn -X package        # debug log: classpath, plugin versions, repos
Likely follow-ups
  • Which plugin versions does Maven use if I set none? Versions bound by the Maven core for that packaging. They are old, so always pin plugin versions (the enforcer plugin can require it).
What packaging types exist, and what does packaging change? Intermediate

What the interviewer is testing: that packaging selects which goals are bound to phases.

The packaging element decides the default plugin bindings. jar is the default: compile, test, then jar:jar. war builds a web archive through the war plugin. pom produces no code, it only holds shared configuration, a BOM, or a parent, or aggregates modules. maven-plugin builds a Maven plugin. Others come from plugins: ear, bundle (OSGi), aar. For Spring Boot, packaging stays jar, and the Spring Boot plugin runs repackage after the jar goal to make an executable fat jar with nested libraries. So when somebody asks "where does the jar come from", the honest answer is: the packaging type bound jar:jar to the package phase.

What is the difference between inheritance and aggregation in Maven? Intermediate

What the interviewer is testing: parent POM versus multi-module POM, which many people treat as the same thing.

Inheritance is the <parent> element. A child POM gets the parent's properties, dependencies, dependencyManagement, plugin configuration and so on. It answers "what do these projects share". Aggregation is the <modules> element in a packaging-pom project. It answers "which projects do I build together with one command". They are independent. A parent does not need to list modules, and an aggregator does not need to be anyone's parent. In practice most multi-module projects use one POM for both roles. The parent link can also point to a POM that is not in your repository, for example spring-boot-starter-parent, which gives you ready-made dependency versions and plugin settings. A project can have only one parent, which is why Maven also offers BOM imports for sharing version lists.

Likely follow-ups
  • What is relativePath in the parent block? Where Maven looks for the parent on disk first (default ../pom.xml). If it is not found there, the parent is fetched from a repository.
How do properties and resource filtering work in Maven? Intermediate

What the interviewer is testing: everyday POM skill, and the trap of filtering the wrong files.

Properties are named values you define in <properties> and use as ${name} anywhere in the POM. Built-in ones are ${project.version}, ${project.basedir}, and environment variables as ${env.HOME}. System properties passed with -Dname=value override POM properties. Resource filtering goes one step further. If you set <filtering>true</filtering> on a resource directory, Maven replaces ${...} or @...@ placeholders inside those files during the process-resources phase, for example to put the version into application.properties. The classic trap is filtering binary files (images, keystores), which corrupts them, and filtering files that use ${...} for their own purposes, like shell scripts or Spring placeholders. Spring Boot's parent POM changes the delimiter to @...@ for exactly this reason.

What is the difference between -DskipTests and -Dmaven.test.skip=true? Basic

What the interviewer is testing: a small detail that breaks multi-module builds.

-DskipTests compiles the tests but does not run them. -Dmaven.test.skip=true skips both compiling and running the tests, and it also makes the jar plugin and others behave as if there are no test classes. The second one causes trouble when another module depends on the test-jar of this module, because that jar will not exist. Prefer -DskipTests for speed and keep tests compiling, so you notice broken tests early. Neither is a good habit on the main CI pipeline: skipping tests there defeats the build's purpose. They are fine for a quick local install of a library you are not changing.

2. Maven dependencies: scopes, transitive, conflicts, BOMs

Explain the Maven dependency scopes. Basic

What the interviewer is testing: where each library is visible: compile time, test time, run time.

A scope says in which classpaths a dependency is present, and whether it travels to projects that depend on yours.

ScopeCompileTestRunPassed on to users of your library?
compile (default)yesyesyesyes
providedyesyesnono (the container provides it, like the Servlet API)
runtimenoyesyesyes, as runtime (for example a JDBC driver)
testnoyesnono (JUnit, Mockito)
systemyesyesnodeprecated, points to a file path, avoid
importonly inside dependencyManagement with type pom, to import a BOM

A good habit is to use the narrowest scope: the JDBC driver as runtime so code cannot accidentally import its classes, Lombok or annotation APIs as provided, test libraries as test. This keeps the final package small and the API of your module honest.

Likely follow-ups
  • What happens to a transitive dependency's scope? A compile dependency of a compile dependency stays compile. A compile dependency of a runtime dependency becomes runtime. test and provided dependencies of a library are never passed on.
What are transitive dependencies, and how does Maven choose a version when two paths disagree? Intermediate

What the interviewer is testing: the "nearest wins" rule. It explains most surprising versions.

A transitive dependency is a library that your dependency needs, which Maven adds for you. Conflicts appear when two paths ask for different versions of the same library (same group and artifact). Maven uses dependency mediation: the version nearest to your project in the tree wins (fewest hops). If the depth is equal, the one declared first in the POM wins. Note that it is not "the newest wins". So a direct dependency always beats a transitive one, and an older version two hops away can beat a newer one three hops away. That is the cause of many NoSuchMethodError bugs: your code needs the new API, but Maven picked the old copy.

mvn dependency:tree -Dverbose -Dincludes=com.acme:util
# [INFO] +- lib-A:1.0
# [INFO] |  \- util:1.0
# [INFO] \- lib-B:1.0
# [INFO]    \- lib-C:1.0
# [INFO]       \- (util:2.0 - omitted for conflict with 1.0)
Likely follow-ups
  • How do I force a version? Put it in dependencyManagement (applies to the whole tree), or declare it directly (depth 1).
  • Is the same rule in Gradle? No. Gradle picks the highest version by default.
What is dependencyManagement and how is it different from dependencies? Intermediate

What the interviewer is testing: one of the top three Maven questions. The key point is that it declares versions but does not add anything to the classpath.

<dependencies> really adds libraries to this project's classpath. <dependencyManagement> only sets rules: "if anyone in this build uses this library, use this version, scope, and exclusions". It adds nothing by itself. Children then declare the dependency without a version. The rule also applies to transitive dependencies, and that is the strongest feature. If a library you use pulls in Jackson 2.9, a managed Jackson 2.17 overrides it everywhere, even though you never wrote Jackson in your own dependencies. The effect is one place to change a version for all modules.

<!-- parent pom -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.fasterxml.jackson.core</groupId>
      <artifactId>jackson-databind</artifactId>
      <version>2.17.1</version>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- child pom: no version needed -->
<dependency>
  <groupId>com.fasterxml.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
</dependency>
Common mistakes: thinking that putting a library under dependencyManagement makes it available; and forgetting that a child's own explicit version beats the managed one.
What is a BOM and how do you import one? Intermediate

What the interviewer is testing: you know how to share a tested set of versions without using single inheritance.

A BOM (Bill of Materials) is a POM with packaging pom whose main content is a dependencyManagement section. It lists versions of many related libraries that are known to work together, for example spring-boot-dependencies, jackson-bom, or aws-java-sdk-bom. You import it with scope import and type pom inside your own dependencyManagement. Maven copies its managed versions into yours. Unlike a parent, you can import many BOMs. If two BOMs manage the same library, the one that appears first wins, so order matters. Your own explicit entries beat imported ones. Gradle has the same idea with platform().

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.3.4</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
Likely follow-ups
  • Spring Boot BOM versus Spring Boot parent? The parent also configures plugins and resource filtering. The BOM gives only dependency versions, so use it when you already have your own parent.
What is the difference between exclusions and optional dependencies? Intermediate

What the interviewer is testing: who controls the cut: the consumer or the library author.

An exclusion is placed by the consumer: "I use library X, but do not bring in its dependency Y". It cuts one branch of the tree in my project only. Use it to remove an old logging binding, or a duplicate of a library I supply myself. An optional dependency is placed by the library author: "I need Z only for a feature, so do not pass it on". It is used in my build but is not transitive to my users. Typical example: a library that supports Jackson, Gson, or others, and wants you to pick one. Be careful: excluding a library that the code really needs leads to ClassNotFoundException at runtime, so after an exclusion run the tests and check the tree. A wildcard exclusion (*:*) is possible when you want a bare dependency and will provide everything yourself.

<dependency>
  <groupId>org.apache.hadoop</groupId>
  <artifactId>hadoop-client</artifactId>
  <version>3.3.6</version>
  <exclusions>
    <exclusion>
      <groupId>org.slf4j</groupId>
      <artifactId>slf4j-reload4j</artifactId>
    </exclusion>
  </exclusions>
</dependency>
Can you use version ranges, LATEST or RELEASE in Maven? Should you? Intermediate

What the interviewer is testing: reproducibility thinking.

Yes, Maven accepts ranges like [1.2,2.0) (at least 1.2, below 2.0). The meta-versions LATEST and RELEASE exist but are deprecated and not allowed in plugins in newer Maven. I would not use any of them in a real project. The build then depends on what the repository has today, so the same commit can build differently next week, a new upstream release can break production without any change in your code, and you cannot reproduce an old release. Maven must also fetch metadata files for each range on every check, so builds get slower. Better practice: fixed versions, updated on purpose using the versions-maven-plugin or Dependabot or Renovate, which open a pull request for each update that CI can test.

mvn versions:display-dependency-updates
mvn versions:display-plugin-updates
mvn versions:use-latest-releases    # edits POM, review the diff
What is the difference between a SNAPSHOT and a release version? Basic

What the interviewer is testing: mutability. A release must never change, a snapshot changes all the time.

A version ending in -SNAPSHOT means "work in progress, the latest build of this line". The same version string can point to different jars over time. Maven checks the remote repository for a newer snapshot based on an update policy, by default once a day, or every time with -U. A snapshot is stored with a timestamp (1.2.0-20241114.101500-7) in the remote repository, and a metadata file says which is the latest. A release version (1.2.0) is immutable: once published, it must never be replaced. If it is wrong, publish 1.2.1. Repositories normally enforce this: Nexus can be set to disallow redeploy of a release. Many teams also ban SNAPSHOT dependencies in release builds, with the enforcer rule requireReleaseDeps.

Likely follow-ups
  • Why can snapshots be dangerous? Two developers, or CI and local, may have different "same version" jars. This causes unrepeatable builds and "works on my machine".
  • How do I force an update? mvn -U, or delete the artifact folder in ~/.m2.
How do you inspect and clean up dependencies in a Maven project? Basic

What the interviewer is testing: practical debugging commands.

The first tool is mvn dependency:tree. It shows every library and who brought it. With -Dverbose it also shows the versions that were omitted because of conflicts, and -Dincludes=group:artifact filters to one library. The second is mvn dependency:analyze. It reports "used but undeclared" (you import it in code but only get it transitively, which is fragile) and "declared but unused" (safe candidates to remove). Treat the unused list with care, because it cannot see reflection, annotation processors, or runtime-only libraries such as drivers. Third, mvn dependency:resolve-sources and dependency:go-offline help for IDEs and offline builds. For a full view of classpath in a failing run, mvn -X prints the classpath given to the compiler and to the test runner.

mvn dependency:tree -Dverbose -Dincludes=com.google.guava
mvn dependency:analyze -DignoreNonCompile
mvn dependency:build-classpath -Dmdep.outputFile=cp.txt
You get NoSuchMethodError or ClassNotFoundException at runtime, though it compiled fine. How do you debug it? Senior

What the interviewer is testing: a systematic approach to classpath conflicts.

These errors mean that the class or method existed when compiling, but a different version, or none, is on the runtime classpath. My routine: first read the error to get the class name. Then ask which jar that class is loaded from. The JVM option -verbose:class or, for a test, Foo.class.getProtectionDomain().getCodeSource() prints the jar. Next, use mvn dependency:tree -Dverbose -Dincludes=... to see all versions of that library requested by different paths, and which one Maven kept. Typically the nearest-wins rule kept an old version. Then fix it by pinning the version in dependencyManagement, or by excluding the old copy. If the same class is in two different artifacts (for example a shaded copy inside a fat jar), the enforcer plugin's banDuplicateClasses rule finds it. Finally, add an enforcer rule so the problem cannot silently come back.

java -verbose:class -jar app.jar | grep com.google.common.base.Preconditions
mvn dependency:tree -Dverbose -Dincludes=com.google.guava:guava
unzip -l app.jar | grep guava
Likely follow-ups
  • Why does it compile but fail later? The compile classpath and the runtime classpath can differ (scope, provided, container libraries).
What does the Maven Enforcer plugin do, and which rules would you turn on? Senior

What the interviewer is testing: do you protect the build from drift, not only fix it.

The enforcer plugin fails the build when a rule is broken. It is a cheap guardrail that runs on every build. Useful rules: requireMavenVersion and requireJavaVersion (same tools for everybody), dependencyConvergence (fail if two paths bring different versions of the same library, strict but noisy), requireUpperBoundDeps (fail if the chosen version is lower than one asked for somewhere, which is the exact nearest-wins trap), banDuplicatePomDependencyVersions, requireReleaseDeps (no SNAPSHOT in a release), bannedDependencies (for example ban log4j:log4j 1.x or commons-logging), and requirePluginVersions. The extra-enforcer-rules module adds banDuplicateClasses, which finds the same class in two jars. Start with requireUpperBoundDeps, it gives high value with lower noise.

<plugin>
  <artifactId>maven-enforcer-plugin</artifactId>
  <version>3.5.0</version>
  <executions><execution>
    <id>enforce</id><goals><goal>enforce</goal></goals>
    <configuration><rules>
      <requireUpperBoundDeps/>
      <requireMavenVersion><version>[3.9.0,)</version></requireMavenVersion>
    </rules></configuration>
  </execution></executions>
</plugin>
How do you build a single executable jar (fat jar), and what can go wrong? Intermediate

What the interviewer is testing: the options and the typical traps in merging jars.

There are three common ways. The Spring Boot plugin (spring-boot-maven-plugin, goal repackage) keeps dependency jars intact inside BOOT-INF/lib and uses its own launcher. No class is copied, so there are few collisions. The shade plugin unpacks all dependency classes into one flat jar. It can relocate packages (rename com.google.common to shaded.com.google.common) to avoid clashes, and has transformers to merge files. The assembly plugin builds archives using a descriptor and is more general. With shading, the usual problems are: files with the same path in many jars where one overwrites another (META-INF/services/*, reference.conf), which needs the ServicesResourceTransformer or AppendingTransformer; signed jars whose signature files break the merged jar (exclude META-INF/*.SF); and a bigger jar with more security patching work, because you must track the copied libraries.

Likely follow-ups
  • Why relocate? Two libraries need different versions of the same dependency. Renaming one copy lets both live in the same JVM.

3. Maven plugins, profiles and tests

What is the difference between plugins and pluginManagement? Intermediate

What the interviewer is testing: same idea as dependencyManagement, applied to plugins.

<build><plugins> activates a plugin for this module: it will really run. <build><pluginManagement> only defines the default version and configuration for a plugin, and applies when a module uses that plugin, directly or because the packaging binds it. The parent POM usually puts the versions and settings of all plugins in pluginManagement, and a child lists a plugin in plugins without version only when it needs to turn it on. Note that plugins bound by packaging (the compiler, surefire, jar) are active even if you do not list them, and pluginManagement is the place where their versions and settings are pinned. Because Maven's default plugin versions are old, pin them. The enforcer rule requirePluginVersions checks it.

How do you run an extra action, for example code generation, at a certain phase? Intermediate

What the interviewer is testing: binding goals to phases with executions.

You add a plugin with an <execution> that names the goal and the phase. If the plugin goal has a default phase, you can leave the phase out. For example the build-helper-maven-plugin adds a generated source folder at generate-sources, and the exec-maven-plugin runs a script at process-resources. Several executions can use the same goal with different ids and configurations. Executions in the same phase run in the order they appear in the POM, with the plugins bound by packaging first. If you need heavy logic that repeats across projects, write a small custom plugin (a Java class with @Mojo, Maven plugin tools). In most application teams, an existing plugin is enough, and a custom plugin is a sign to ask whether Gradle suits that project better.

<plugin>
  <groupId>org.codehaus.mojo</groupId>
  <artifactId>build-helper-maven-plugin</artifactId>
  <version>3.6.0</version>
  <executions><execution>
    <id>add-gen-src</id>
    <phase>generate-sources</phase>
    <goals><goal>add-source</goal></goals>
    <configuration><sources><source>target/generated</source></sources></configuration>
  </execution></executions>
</plugin>
Surefire versus Failsafe: what is the difference, and why two plugins? Intermediate

What the interviewer is testing: unit versus integration test setup, and the lifecycle around integration tests.

Surefire runs unit tests in the test phase. By default it picks classes named *Test, Test*, *Tests, *TestCase. Failsafe runs integration tests in the integration-test phase and checks the results in the verify phase. It picks *IT, IT*, *ITCase. The split exists because integration tests often need setup and cleanup around them: pre-integration-test starts a server or container, post-integration-test stops it. If a test fails in integration-test, Failsafe does not fail the build right away, it waits for verify, so the cleanup still runs. That is why you run mvn verify and not mvn integration-test in CI. A modern alternative is Testcontainers inside the test itself, which reduces the need for phase-based setup.

Likely follow-ups
  • Why are my tests not running? Wrong name pattern, wrong JUnit engine for the Surefire version (JUnit 5 needs Surefire 2.22 or newer), or skipTests set in a profile.
  • Run one test? mvn test -Dtest=OrderServiceTest#shouldPay.
What are Maven profiles, how are they activated, and what are the risks? Intermediate

What the interviewer is testing: the power and the danger of conditional builds.

A profile is a named block of POM settings (properties, dependencies, plugins, repositories) that applies only when the profile is active. Activation: explicit with -P name, by default (activeByDefault, which switches off when another profile in the same POM is activated, so it surprises people), by JDK version, by operating system, by a property (-Denv=prod), or by the presence or absence of a file. Profiles are in the POM or in settings.xml (for machine-specific values). Use them for things like "skip slow tests", "run integration tests", "sign artifacts on release", or "add a vendor driver". The risk is that a profile changes what the artifact contains, so the jar built with -Pprod is not the one you tested. A safer pattern is: build one artifact once, and let the environment configuration come in at runtime (environment variables, config server), not at build time.

mvn -Pintegration verify
mvn help:active-profiles
mvn -P '!slow' test       # deactivate a profile
How do you set the Java version in Maven? What is the difference between source/target and release? Intermediate

What the interviewer is testing: a common reason for "builds on my JDK but fails on CI" or runtime errors on older JVMs.

maven.compiler.source says which language level to accept, and maven.compiler.target says which bytecode version to produce. The trouble is that the compiler still sees the API classes of the JDK that runs Maven. So you can compile with JDK 21 using target 11, accidentally call a method that exists only in Java 21, and it fails at runtime on Java 11 with NoSuchMethodError. The option maven.compiler.release (compiler plugin 3.6 and newer, JDK 9 and newer) fixes it. It sets language level, bytecode level and the API signatures together, so the compiler rejects APIs that are newer than the release. Use release. Also pin the JDK in CI and, if you want, enforce it with the enforcer plugin or toolchains.

<properties>
  <maven.compiler.release>17</maven.compiler.release>
</properties>

4. Repositories, settings.xml, releases and multi-module builds

What goes in settings.xml, and how is it different from the POM? Basic

What the interviewer is testing: the split between project definition (shared, committed) and machine or user configuration (private).

The POM describes the project and is committed to source control. settings.xml describes the machine and the user, and must not be committed with secrets. There are two files: the user file ~/.m2/settings.xml and the global one in $MAVEN_HOME/conf/settings.xml. The user file overrides it. Main content: servers (credentials, matched to a repository by id), mirrors (redirect repository requests to your company proxy), proxies (HTTP proxy for internet access), profiles (repositories and properties for this machine), activeProfiles, and localRepository (move the cache). The id match is the thing that bites: if the <id> in distributionManagement is company-releases but the server entry in settings has another id, the upload goes without credentials and gives a 401.

<settings>
  <servers>
    <server><id>company-releases</id>
      <username>${env.NEXUS_USER}</username>
      <password>${env.NEXUS_TOKEN}</password></server>
  </servers>
  <mirrors>
    <mirror><id>company-all</id><mirrorOf>*</mirrorOf>
      <url>https://nexus.example.com/repository/maven-public/</url></mirror>
  </mirrors>
</settings>
Likely follow-ups
  • How to avoid plain passwords? Use environment variables, CI secrets, or Maven's master-password encryption (mvn --encrypt-master-password), which is only light protection.
How does Maven find an artifact? Describe local, remote and Central repositories. Intermediate

What the interviewer is testing: the full resolution chain, so you can debug "could not resolve".

First Maven looks in the local repository (~/.m2/repository). If the artifact is there, it is used (for snapshots, Maven may still check remote based on the update policy). If not, it asks the remote repositories in order: those from the POM and active profiles, and the implicit Maven Central. If a mirror matches (for example mirrorOf *), the request goes to the mirror instead, so the real address is never contacted. In companies the mirror is a repository manager such as Nexus or Artifactory. It proxies Central (fetch once, cache), hosts your own releases and snapshots, and groups them under one URL. When a download fails, Maven writes a *.lastUpdated marker file in the local repo and will not retry until the update interval passes, which is why a fixed server problem still seems broken until you use -U or delete those markers.

What does mirrorOf mean, and what are the common values? Intermediate

What the interviewer is testing: a detail that explains "Maven ignores the repository I added".

mirrorOf lists which repository ids this mirror replaces. central replaces only Central. * replaces every repository, including those declared in project POMs, so everything goes through your proxy. external:* replaces everything except localhost and file-based repositories, which is useful when you also use a local repo on disk. *,!my-repo replaces all except my-repo. The side effect of * is that a POM with a custom repository, for example a vendor's repo, is also routed to your mirror. If the mirror does not proxy that vendor repository, the artifact cannot be found. The fix is to add that remote to the repository manager's group, not to disable the mirror. With Maven 3.8.1 and later, a built-in mirror also blocks http:// repositories, which is a safety measure after attacks on insecure repositories.

A build fails with "Blocked mirror for repositories ... http" after upgrading Maven. What happened? Intermediate

What the interviewer is testing: knowing a security change in Maven 3.8.1 and the right way to respond.

Since Maven 3.8.1 Maven ships a default mirror named maven-default-http-blocker that matches every repository using plain http:// (except localhost) and points it to a dummy blocked address. The reason: with plain HTTP, anyone on the network path can swap a jar for malicious code (man in the middle). Older POMs, especially old third-party libraries, still list http:// repositories. The right fix is to change the repository URL to https, or, better, to proxy it in your repository manager and let the build use only the manager. If the repository really has no HTTPS (a legacy internal host), you can add your own mirror entry with mirrorOf for that id and a URL, which overrides the blocker, but that is an accepted risk, so write it down.

How do you publish an artifact to Nexus or Artifactory with Maven? Intermediate

What the interviewer is testing: the pieces: distributionManagement, credentials and the deploy phase.

Three things are needed. First, distributionManagement in the POM names one repository for releases and one for snapshots, each with an id and URL. Second, settings.xml (or CI secrets) has a server entry with the same id and the credentials. Third, run mvn deploy. Maven decides snapshot or release from the version suffix and picks the matching repository. Deploy uploads the jar, the POM, and when configured, the sources and javadoc jars, plus checksums. Public publishing to Maven Central has extra rules: sources, javadoc, signatures with GPG, and complete POM metadata. Since mid-2025 the old OSSRH service is retired and publishing goes through the Central Portal, with its own plugin or an API token. The details change often, so check the current Central documentation before a release.

<distributionManagement>
  <repository><id>company-releases</id>
    <url>https://nexus.example.com/repository/maven-releases/</url></repository>
  <snapshotRepository><id>company-snapshots</id>
    <url>https://nexus.example.com/repository/maven-snapshots/</url></snapshotRepository>
</distributionManagement>
How do you do a release with Maven? Compare the release plugin with a CI-friendly version. Senior

What the interviewer is testing: release engineering at the developer level, with trade-offs.

The classic way is maven-release-plugin. release:prepare checks there are no uncommitted changes and no SNAPSHOT dependencies, changes 1.2.0-SNAPSHOT to 1.2.0, commits, tags, then sets the next development version (1.2.1-SNAPSHOT) and commits again. release:perform checks out the tag and deploys. It works, but it makes two commits per release, is slow, and fails halfway in awkward ways (then you need release:rollback and to delete the tag by hand). The modern approach is a CI-friendly version: since Maven 3.5 you can write <version>${revision}</version>, set <revision>1.2.0-SNAPSHOT</revision> as a property, and pass -Drevision=1.2.${BUILD_NUMBER} in CI. Add the flatten-maven-plugin so the published POM contains the real version, not the placeholder. Then the pipeline tags the commit, builds, and deploys. No commits are written back. A third option is a plugin that derives the version from the Git tag. Pick one and keep it simple.

mvn -B release:prepare release:perform
# CI-friendly alternative:
mvn -B -Drevision=1.2.7 clean deploy
How does a multi-module Maven build work? What is the reactor? Intermediate

What the interviewer is testing: how Maven orders modules, and why it matters for builds and CI.

A multi-module project has a root POM with packaging pom and a <modules> list. When you run Maven at the root, the reactor loads all module POMs, builds a graph from their dependencies on each other, and sorts them so a module is built after the modules it needs. The order is not the order in the modules list, but the dependency order, with the list order used to break ties. All modules run the same phase before the next module starts. Inside one reactor build, a module can use the output of a sibling directly from target/classes (with compile) or target/*.jar (with package), without installing it. A cycle between modules is an error. This is how you can build ten services and a shared library with one command.

Likely follow-ups
  • What if one module fails? Maven stops by default (--fail-fast). --fail-at-end continues with independent modules, and -rf :web resumes from a module.
How do you build only part of a multi-module project, and how do you speed Maven up? Intermediate

What the interviewer is testing: practical daily commands and knowing Maven's speed levers.

To select modules use -pl (projects list). -am (also make) adds the modules they depend on, and -amd (also make dependents) adds the modules that depend on them. -rf resumes from a module after a failure. For speed, -T 1C builds modules in parallel (one thread per CPU core), which works when modules are independent and plugins are thread safe. Skip work you do not need locally: -DskipTests, -Dmaven.javadoc.skip=true, -o (offline, avoids network checks). Keep the local repo on CI between runs (cache it). The Maven daemon mvnd keeps a warm JVM and parallel by default. Maven 4 adds a build cache and better parallelism. For huge codebases, a tool with a real build cache such as Gradle or Bazel gives more.

mvn -pl service,web -am -DskipTests package   # these two and what they need
mvn -T 1C -B verify
mvn -rf :web verify                           # continue from web
What are the Maven wrapper and toolchains for? Intermediate

What the interviewer is testing: do you make the build tool version and JDK part of the repository, not part of the laptop.

The Maven wrapper (mvnw, mvnw.cmd, and .mvn/wrapper) is a small script committed to the repo. When you run ./mvnw it downloads the Maven version named in .mvn/wrapper/maven-wrapper.properties and uses it. New developers and CI then need only a JDK. You create it with mvn wrapper:wrapper -Dmaven=3.9.9. Toolchains solve another problem: the JDK used to compile can differ from the JDK that runs Maven. You describe installed JDKs in ~/.m2/toolchains.xml and ask for "JDK 17" in the POM, so the compiler and test plugins use it. Gradle has the same idea built in with java.toolchain, which can even download the right JDK. Both exist to cut "works with my JDK" differences.

What is new in Maven 4? Senior

What the interviewer is testing: are you following the tool, and can you say what you are sure of.

Maven 4 has been in release-candidate stage, so check whether it is final when you read this. The main ideas, from the project's own announcements: a new POM model version 4.1.0 (the build POM and the consumer POM are separated, so the POM published to a repository can be cleaner than the one used to build), better multi-module support such as a built-in way to omit repeated parent versions, an improved build cache and parallelism, a new dependency resolver, and a new bom packaging. Maven 4 also needs a newer Java to run (Java 17). The practical advice for an interview: say that you would try it in a branch, because plugin compatibility is the usual risk, and that the day to day model of lifecycle, POM and dependencies stays the same.

5. Gradle core: DSL, phases, tasks, caching

What is Gradle, and why do many teams choose it over Maven? Basic

What the interviewer is testing: can you name the real differences: flexibility, speed and incremental work, not only "it uses Groovy".

Gradle is a general build tool for JVM projects, Android, and also other languages. A build is a script (build.gradle in Groovy, or build.gradle.kts in Kotlin) that describes tasks and their relationships. Gradle builds a graph of the needed tasks and runs them in order. The main advantages are: it skips tasks whose inputs and outputs did not change (incremental build), it can reuse outputs from earlier builds or other machines (build cache), it uses a long-lived background process (the daemon) for speed, and the build logic is real code, so unusual needs are easy. The costs are a steeper learning curve, more ways to do the same thing, and more freedom to write a messy build. It is the official build tool of Android, and Spring and many big open source projects use it.

Groovy DSL or Kotlin DSL? Which would you choose? Basic

What the interviewer is testing: a current, practical opinion.

Both describe the same model. Groovy (build.gradle) is dynamic and shorter, but the IDE cannot always check it. Kotlin (build.gradle.kts) is statically typed, so auto-complete, jump to definition, and compile errors in the build file work well in IntelliJ. Since Gradle 8.2, gradle init produces Kotlin DSL by default, and the Gradle team recommends it for new builds. Kotlin scripts are a bit slower to compile on first load and the error messages can be longer. Syntax differences are small but real: Kotlin needs parentheses and quotes (implementation("org.slf4j:slf4j-api:2.0.13"), tasks.register<Test>("x")). For a new project I choose Kotlin. For an old large Groovy build I keep Groovy until there is another reason to touch it, because a rewrite adds risk and no features.

// build.gradle.kts
plugins { java }
repositories { mavenCentral() }
dependencies {
    implementation("org.slf4j:slf4j-api:2.0.13")
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}
tasks.test { useJUnitPlatform() }
Explain the three phases of a Gradle build: initialization, configuration, execution. Intermediate

What the interviewer is testing: the most asked Gradle question. It explains slow builds and "why did my code run when I did not run the task".

Initialization: Gradle reads settings.gradle(.kts) to find which projects are in the build. Configuration: Gradle runs the build script of every project (unless on-demand configuration is used) to create the tasks and set their properties. This builds the task graph. No task action runs yet. Execution: Gradle runs only the tasks that are needed for the requested task, in dependency order, and skips the up-to-date ones. The big trap is code written directly in the build script body or in a configure block: it runs at configuration time on every build, even for gradle help. For example, an exec call or a network request placed there slows every command. Put work inside doLast { } or in a task class, which run only at execution time.

tasks.register("report") {
    println("CONFIG time: runs on every build")      // bad place for work
    doLast { println("EXECUTION time: only when task runs") }
}
What is a Gradle task, and how does the task graph decide the order? Intermediate

What the interviewer is testing: task relationships: dependsOn, mustRunAfter, finalizedBy, and why the graph has no cycles.

A task is a unit of work with inputs, outputs and actions: compile Java, run tests, build a jar. Tasks are linked by relationships. dependsOn means "this task needs that one to run first, and it will be added to the graph". mustRunAfter and shouldRunAfter only set an order if both tasks happen to be in the graph, they do not add the other one. finalizedBy says "run this cleanup task after me, even if I fail". Gradle collects all needed tasks into a directed acyclic graph (DAG), sorts it, and may run independent tasks in parallel. Most plugin tasks also connect through task inputs and outputs: if task B uses the output of task A as input, Gradle infers the dependency, so you do not need to write dependsOn by hand. A cycle is an error.

gradle build --dry-run        # show the tasks that would run, run none
gradle :app:test --tests '*OrderServiceTest'
gradle build -x test          # exclude a task
How do you write a custom task? What is the difference between tasks.create and tasks.register? Intermediate

What the interviewer is testing: modern, lazy task API and typed inputs.

The simple way is a script task with doLast. A better way is a class that extends DefaultTask with annotated inputs and outputs, because Gradle can then check up-to-date state and cache it. tasks.create builds the task immediately, during configuration, even if it will never run. tasks.register only records a recipe and builds the task when it is needed. This is called task configuration avoidance, and it keeps configuration time low in a large build, so always prefer register. Likewise, use named instead of getByName, and configureEach instead of all.

abstract class Greet : DefaultTask() {
    @get:Input abstract val name: Property<String>
    @get:OutputFile abstract val out: RegularFileProperty
    @TaskAction fun run() { out.get().asFile.writeText("Hello ${name.get()}") }
}
tasks.register<Greet>("greet") {
    name.set("team")
    out.set(layout.buildDirectory.file("greet.txt"))
}
How does Gradle know a task is UP-TO-DATE? Intermediate

What the interviewer is testing: the incremental build idea, which is the base for caching.

Before running a task, Gradle takes a fingerprint of its inputs (source files, properties, classpath, the task's own code) and its outputs (files it produced last time). It compares them with the stored fingerprint from the previous run. If the inputs are the same and the outputs are unchanged, the task is marked UP-TO-DATE and skipped. Fingerprints use file contents (and for classpath, the class contents and not only timestamps), so touching a file without changing it does not trigger a rebuild. If you write a custom task without declaring its inputs and outputs, Gradle has nothing to compare, so the task always runs. The common bug is the opposite: a task reads a file it did not declare as input, so Gradle thinks it is up to date and skips it with a stale result. Declare everything the task reads and writes. --info or --rerun-tasks help find which input changed.

Likely follow-ups
  • What are the usual statuses? UP-TO-DATE (local outputs fine), FROM-CACHE (outputs restored from the build cache), NO-SOURCE (no input files), SKIPPED (disabled).
What is the Gradle build cache, and how is it different from the up-to-date check? Senior

What the interviewer is testing: speed on CI and across branches, and the condition for it to work: reproducible tasks.

The up-to-date check only compares with the last run in the same workspace. The build cache stores task outputs under a key made from all inputs (a hash). When any build, on any branch or machine that can reach the cache, needs a task with the same key, Gradle downloads the outputs and marks the task FROM-CACHE. There is a local cache (~/.gradle/caches/build-cache-1) and an optional remote cache (an HTTP service, often read-only for developers and write-only for CI). It saves most when many builds share unchanged modules: switching branches, or CI running compile and tests for the modules a pull request did not touch. For it to work, tasks must be cacheable (@CacheableTask with declared inputs and outputs) and deterministic. If a task puts a timestamp or an absolute path into its output, or reads an undeclared input, the key does not match, or worse, a wrong output is shared. Enable it with org.gradle.caching=true in gradle.properties.

Likely follow-ups
  • Why does the cache not hit on CI? Absolute paths in inputs, timestamps in outputs, different JDK vendor or version, or environment variables as inputs. A build scan compares two builds and shows the differing input.
  • Is the remote cache a security risk? Anyone allowed to write could poison it, so only trusted CI writes.
What is the configuration cache, and how is it different from the build cache? Senior

What the interviewer is testing: that you understand two different caches that save different phases.

The build cache saves task outputs (execution phase work). The configuration cache saves the result of the configuration phase: the task graph itself. If the build scripts and their inputs did not change, Gradle loads the stored graph and goes straight to execution, which can cut seconds off every command in a big build. It also allows tasks to run in parallel more safely. The condition: build logic and tasks must not reach into the live project model at execution time (no project or gradle objects inside a task action), and must declare things they read, like environment variables, through providers. Plugins that break this rule fail with a clear report. It was stable from Gradle 8.1, and in Gradle 9 it is the recommended mode. Turn it on with org.gradle.configuration-cache=true.

# gradle.properties
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.parallel=true
org.gradle.jvmargs=-Xmx2g
What is the Gradle daemon, and when does it cause trouble? Basic

What the interviewer is testing: basics of why Gradle feels fast after the first run, and what to do when it misbehaves.

Starting a JVM and loading Gradle and plugins is slow. The daemon is a background JVM process that stays alive after a build (about three hours idle by default) and is reused by the next build. It keeps classes loaded and caches information in memory, so later builds start quickly. Since Gradle 3 it is on by default. Troubles: a daemon with a small heap runs out of memory (OutOfMemoryError: Metaspace or Java heap), so set org.gradle.jvmargs. Several daemons for different Gradle or JDK versions use a lot of RAM. A daemon can keep an old environment variable, or lock files on Windows, so a strange behaviour often goes away after ./gradlew --stop. On CI, short-lived containers get little from the daemon, so many teams run with --no-daemon or let the CI wrapper handle it, while keeping the Gradle caches between runs.

./gradlew --status       # list daemons
./gradlew --stop         # stop all of them
What is the Gradle wrapper, and why must it be in version control? Basic

What the interviewer is testing: reproducibility of the tool version.

The wrapper is gradlew, gradlew.bat and the folder gradle/wrapper with gradle-wrapper.properties and a small jar. The properties file names the Gradle version and distribution URL. When you run ./gradlew build, it downloads that Gradle (once, cached in ~/.gradle/wrapper) and runs it. Everyone and CI therefore use the same Gradle version, without installing anything. You upgrade by running ./gradlew wrapper --gradle-version 8.10.2 and committing the change. Good practice is to add distributionSha256Sum so a tampered download is rejected, and to validate the wrapper jar in CI (the gradle/actions/wrapper-validation action) because the committed jar is executable code. Do not commit it to .gitignore: the jar is needed.

What are lazy properties and providers in Gradle, and why were they introduced? Senior

What the interviewer is testing: modern Gradle authoring, linked to the configuration phase issue.

A Property<T> or Provider<T> is a value that is calculated later, when it is first needed, instead of at the moment you write the build script. Configuration happens before other parts of the build are known: the output folder of a task, a version read from a file, or a value set by another plugin. If you read these values eagerly, you can get a stale or wrong value, or force other work to happen early. With a provider you connect two things: task2.input.set(task1.output) and Gradle tracks the link, so it also knows that task2 depends on task1. This is also what makes configuration avoidance and the configuration cache possible. In day to day work: use .set() and .get() at execution time, use map { } to transform a value lazily, and avoid calling .get() in configuration code.

6. Gradle dependencies: configurations, conflicts, catalogs, locking

What is the difference between api and implementation in Gradle? Intermediate

What the interviewer is testing: the most asked Gradle dependency question. It is about leaking dependencies and recompilation.

These two come from the java-library plugin. implementation means "my code uses this library inside, but it is not part of my public API". Modules that depend on mine do not get it on their compile classpath (it is still on their runtime classpath). api means "this library appears in my public signatures (a parameter type, a return type, a superclass)", so consumers need it to compile and get it on the compile classpath. Why prefer implementation? First, it hides internals, so a consumer cannot accidentally depend on them. Second, builds are faster: if an implementation dependency changes, only my module recompiles, not every module that uses me. With api a change ripples through all consumers. Maven has no exact equivalent: a Maven compile dependency behaves like api for everybody downstream. Rule of thumb: start with implementation, switch to api only when a type of that library is visible in your public methods.

plugins { `java-library` }
dependencies {
    api("com.google.code.gson:gson:2.11.0")           // in public method signatures
    implementation("com.squareup.okhttp3:okhttp:4.12.0") // internal use only
    compileOnly("org.projectlombok:lombok:1.18.34")
    annotationProcessor("org.projectlombok:lombok:1.18.34")
    runtimeOnly("org.postgresql:postgresql:42.7.4")
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}
Likely follow-ups
  • Old names? compile and runtime were removed in Gradle 7. Use api/implementation/runtimeOnly.
  • Is api available in a plain java plugin project? No, only with java-library. An application does not need it.
What are Gradle configurations? How do compileClasspath and runtimeClasspath relate to implementation and runtimeOnly? Intermediate

What the interviewer is testing: the model behind the keywords.

A configuration is a named bucket of dependencies, with rules about how it can be used. Some are for declaring (implementation, api, compileOnly, runtimeOnly, testImplementation), and some are for resolving: compileClasspath and runtimeClasspath. The declaring ones extend each other, and the resolvable ones are built from them. compileClasspath gets api, implementation and compileOnly. runtimeClasspath gets api, implementation and runtimeOnly. Test classpaths add the test buckets. compileOnly libraries (servlet API, Lombok) are visible when compiling but are not in the runtime output. The word variant matters too: a library can publish several variants (for example a JVM jar and an Android aar, or different Java versions), and Gradle selects by attributes. For debugging use the report tasks, not guesses.

./gradlew dependencies --configuration runtimeClasspath
./gradlew :app:dependencyInsight --dependency jackson-databind --configuration runtimeClasspath
How does Gradle resolve version conflicts? How does it differ from Maven? Intermediate

What the interviewer is testing: the contrast that is asked in every comparison question.

Gradle builds the whole graph of requests first, then picks, for each module, the highest requested version. Maven picks the nearest to your project. Example: your app asks for util 1.0 directly, and a library asks for util 2.0. Maven keeps 1.0 (nearest), Gradle uses 2.0 (highest). Gradle's rule is usually safer for libraries that follow semantic versioning, since newer versions normally add features. It is not safe when a major version breaks the API, so you still need to test. To change the result: strictly in a version constraint (a hard rule, the build fails if impossible), a constraints { } block to set a minimum for transitive dependencies, force (works, but is a blunt tool and is discouraged), or substitution rules. If you want to fail on conflicts, set resolutionStrategy.failOnVersionConflict().

dependencies {
    implementation("com.acme:lib:1.0")        // brings util 2.0 transitively
    constraints {
        implementation("com.acme:util:2.1") { because("CVE fix, see SEC-123") }
    }
}
configurations.all {
    resolutionStrategy.failOnVersionConflict()
}
What are platforms, constraints, strictly and forced versions in Gradle? Senior

What the interviewer is testing: can you control versions without brittle hacks. This is the Gradle answer to dependencyManagement and BOM.

A constraint says "if this library shows up anywhere in the graph, it must be at least this version". It does not add the library. That is the equivalent of dependencyManagement. A platform (implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4"))) imports a BOM, so its versions act as constraints. enforcedPlatform makes them strict, which also overrides stronger requests from elsewhere, so it can break libraries that need something newer. Rich versions let you write strictly (hard limit and wins), require (minimum), prefer (soft choice), and reject. Force on a configuration was the old way, and it hides the reason, so a constraint with a because note is better. For publishing, your constraints become part of the metadata, so consumers inherit the safe versions.

dependencies {
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4"))
    implementation("org.springframework.boot:spring-boot-starter-web")   // no version
    implementation("com.fasterxml.jackson.core:jackson-databind") {
        version { strictly("[2.17.0, 2.18[") ; prefer("2.17.2") }
    }
}
What is a Gradle version catalog and why use one? Intermediate

What the interviewer is testing: managing versions in a multi-project build.

A version catalog is a file, gradle/libs.versions.toml, that lists versions, libraries, bundles and plugins in one place. Gradle generates type-safe accessors, so in a build file you write libs.jackson.databind and the IDE completes it. Benefits: one place to update a version for all modules, no copy-paste of version strings, and it can be shared across repositories as a published artifact. Sections: [versions], [libraries], [bundles] (a group used together, like test libraries) and [plugins]. It is stable since Gradle 7.4. A catalog only declares coordinates. It does not force versions in the graph, so conflict handling is still done with constraints or platforms. It is similar to a Maven parent with properties, but type safe, and not inherited through a POM.

# gradle/libs.versions.toml
[versions]
jackson = "2.17.2"
junit = "5.10.2"
[libraries]
jackson-databind = { module = "com.fasterxml.jackson.core:jackson-databind", version.ref = "jackson" }
junit-jupiter = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }
[bundles]
testing = ["junit-jupiter"]
[plugins]
spring-boot = { id = "org.springframework.boot", version = "3.3.4" }

// build.gradle.kts
dependencies {
    implementation(libs.jackson.databind)
    testImplementation(libs.bundles.testing)
}
What are dynamic and changing versions in Gradle, and how are they cached? Intermediate

What the interviewer is testing: Gradle's version of Maven's SNAPSHOT problem.

A dynamic version is a range or a wildcard such as 2.+, [2.0,3.0) or latest.release. Gradle asks the repository for the list of versions and picks the best. A changing module is a module whose content may change under the same version, for example a -SNAPSHOT. By default Gradle caches the answer to "what is the newest version" and the content of changing modules for 24 hours. You can change that with resolutionStrategy.cacheDynamicVersionsFor(10, "minutes") and cacheChangingModulesFor(0, "seconds"), or force a refresh with --refresh-dependencies. As in Maven, avoid dynamic versions for anything you ship, because the build is no longer repeatable. If you want some freshness without surprises, use dependency locking: dynamic versions during update, but a lock file during normal builds.

What is dependency locking and dependency verification in Gradle? Senior

What the interviewer is testing: repeatable builds and supply chain safety. They are two different features.

Locking records the exact resolved versions of every dependency in gradle.lockfile, which you commit. Later builds use exactly those versions, even if the build file contains ranges. You update on purpose with --write-locks. It answers "what versions did this build use". Verification is about integrity: gradle/verification-metadata.xml stores checksums (and optionally accepted PGP signing keys) of every artifact, and Gradle fails if a downloaded file does not match. It answers "is this the same file I approved". Together they protect against a surprise new version and against a tampered file. The costs are maintenance (every update changes the files) and noise in pull requests, but a bot can handle it. Maven's equivalents are a fixed version with no ranges, the maven-dependency-plugin checks, and a plugin such as checksum-maven-plugin, with less built-in support.

dependencyLocking { lockAllConfigurations() }
// ./gradlew dependencies --write-locks
// ./gradlew --write-verification-metadata sha256 help
How do repositories work in Gradle? Which repository is used first? Intermediate

What the interviewer is testing: order and scoping, which relates to supply-chain safety.

Repositories listed in repositories { } are searched in order. For a given module, Gradle goes through the list and takes the first repository that has the module. It is not the "best" or "highest" across all. So put your company repository first, and give it a content filter so other repositories cannot supply your internal groups. Content filtering (content { includeGroup("com.acme") }) also speeds up resolution, since Gradle skips pointless requests, and it reduces the chance of dependency confusion (an attacker publishes a public library with the same name as your internal one). Settings can also hold the repositories for all projects: dependencyResolutionManagement in settings.gradle.kts, with repositoriesMode set to FAIL_ON_PROJECT_REPOS to stop modules adding their own. Credentials go in ~/.gradle/gradle.properties or environment variables, not in the build file.

// settings.gradle.kts
dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        maven("https://nexus.example.com/repository/maven-public/") {
            credentials { username = providers.gradleProperty("nexusUser").get()
                          password = providers.gradleProperty("nexusToken").get() }
        }
    }
}
How do you find out why Gradle picked a certain version or pulled a library in? Basic

What the interviewer is testing: debugging tools, the Gradle counterpart of dependency:tree.

Use gradle dependencies to print the tree for each configuration, with arrows such as 1.0 -> 2.0 showing that a requested version was upgraded, and (*) marking already printed parts. For one library, gradle dependencyInsight --dependency name --configuration runtimeClasspath explains who asked for it, which versions were requested, and why one won (for example "by conflict resolution" or "by constraint"). Add --scan to publish a build scan (a web report) with a dependency view, timelines and cache information. For a multi-project build run the task for one project, as :app:dependencies. If you suspect a stale cache, add --refresh-dependencies.

./gradlew :app:dependencyInsight --dependency log4j-core --configuration runtimeClasspath
./gradlew build --scan

7. Gradle plugins, multi-project builds, toolchains and publishing

What kinds of Gradle plugins are there, and how do you apply them? Intermediate

What the interviewer is testing: plugin types and the plugins DSL.

There are core plugins shipped with Gradle (java, java-library, application, maven-publish, jacoco), community plugins from the Gradle Plugin Portal (Spring Boot, Shadow, Spotless), and your own local plugins. The recommended way to apply is the plugins { } block with the id and, for non-core plugins, a version. It is resolved early and is type safe. The older apply plugin: and buildscript { } style still works but is discouraged. A plugin usually adds tasks, adds configurations, and sets conventions (for example java adds compileJava and src/main/java). You can read a plugin's effect with ./gradlew tasks --all and ./gradlew properties.

plugins {
    java
    id("org.springframework.boot") version "3.3.4"
    id("com.diffplug.spotless") version "6.25.0"
}
How do you share build logic across many projects? Explain buildSrc and convention plugins. Senior

What the interviewer is testing: how a large Gradle build stays maintainable, instead of copy-pasting or using allprojects { }.

Old advice was allprojects { } or subprojects { } in the root script. It couples projects and makes configuration hard to follow. The current recommendation is convention plugins: small plugins, written as precompiled script plugins (java-conventions.gradle.kts), that set up Java version, test settings, static analysis, and publishing. Each module then says plugins { id("acme.java-conventions") }. Where do these live? In buildSrc (a special folder compiled before the build and put on the build classpath automatically; simple, but any change in it invalidates the cache of the whole build), or better in an included build such as build-logic (includeBuild("build-logic") in settings), which is more cache-friendly and can be shared. The effect is similar to a Maven parent POM, but composable: a module can apply several conventions.

// build-logic/src/main/kotlin/acme.java-conventions.gradle.kts
plugins { `java-library` }
java { toolchain { languageVersion.set(JavaLanguageVersion.of(21)) } }
tasks.withType<Test> { useJUnitPlatform() }
How does a multi-project Gradle build work? What is settings.gradle for? Intermediate

What the interviewer is testing: structure and project dependencies.

settings.gradle(.kts) is the entry point. It names the root project and lists subprojects with include("core", "service", "web"). Each subproject has its own build.gradle(.kts). Dependencies between projects are written implementation(project(":core")). Gradle sees them as task dependencies: when web needs core, it runs core:jar (or just the classes output) first. You can run a task on everything (./gradlew build) or for one project and what it needs (./gradlew :web:build, which builds core as needed, you do not need a flag like -am). Independent projects can run in parallel with org.gradle.parallel=true. Compared to Maven, Gradle is not limited to the build order of modules: it works at the task level, so it can run core:test while service:compileJava is running.

// settings.gradle.kts
rootProject.name = "shop"
include("core", "service", "web")

// web/build.gradle.kts
dependencies { implementation(project(":core")); implementation(project(":service")) }
What is a composite build (includeBuild) and when do you use it? Senior

What the interviewer is testing: how to work on a library and an app at the same time without publishing in between.

A composite build joins separate Gradle builds (often separate repositories) into one. In settings you write includeBuild("../shared-lib"). Gradle then substitutes the external dependency com.acme:shared-lib by the source project in that folder, so a change in the library is picked up by the app at once, with no publishing to a repository and no SNAPSHOT waiting. It is the clean Gradle answer to the Maven habit of mvn install in one project and building the other. It is also the recommended home for convention plugins (build-logic). Limits: all builds must be Gradle, and the included build's own settings are not shared, so it is not a way to merge two unrelated builds into one multi-project build.

How do you control the Java version in Gradle? What is a toolchain? Intermediate

What the interviewer is testing: the Gradle way to avoid "wrong JDK" problems.

Gradle itself runs on one JDK, but your code may be compiled and tested on another. A Java toolchain says which JDK the project needs, for example language version 21. Gradle then finds a matching JDK on the machine, or can download one when a resolver is configured (the foojay plugin), and uses it for compile, test, javadoc and run. This is how the build stays the same on a laptop and CI, even if each has a different default JDK. It is the Gradle version of Maven's release option plus toolchains. A related option is options.release.set(17) on the compile task, which restricts API use to that release, like Maven's maven.compiler.release. Remember that Gradle 9 itself needs Java 17 or higher to run.

java {
    toolchain { languageVersion.set(JavaLanguageVersion.of(21)) }
}
How do you publish a library from Gradle? Intermediate

What the interviewer is testing: the maven-publish plugin and the fact that Gradle publishes a POM too, so Maven users can consume your library.

Apply maven-publish (and often java-library with withSourcesJar() and withJavadocJar()). Define a publication from the java component, set the coordinates, and define the target repositories. Gradle writes a POM and also its own Gradle Module Metadata (.module file) that carries extra information such as variants and constraints. The POM maps api to compile scope and implementation to runtime scope, so a Maven consumer sees the correct classpath. Tasks are publishToMavenLocal and publish. Credentials come from properties or environment, never from the file. For public publishing, add the signing plugin and follow the Central requirements.

publishing {
    publications { create<MavenPublication>("lib") { from(components["java"]) } }
    repositories {
        maven {
            url = uri("https://nexus.example.com/repository/maven-releases/")
            credentials { username = findProperty("nexusUser") as String?
                          password = findProperty("nexusToken") as String? }
        }
    }
}
How do you run a single test, filter tests, and see why a Gradle test did not run? Basic

What the interviewer is testing: daily productivity, and the usual JUnit 5 setup mistake.

Use --tests with a class or method pattern: ./gradlew test --tests "com.acme.OrderServiceTest.shouldPay". With JUnit 5 you must call useJUnitPlatform() in the test task, or Gradle runs the old JUnit 4 engine and finds no tests. A task already UP-TO-DATE will not run again: use --rerun (Gradle 7.6 and newer) or cleanTest to force it, instead of a full clean. Results are in build/reports/tests/test/index.html and XML in build/test-results. Parallel test forks are set with maxParallelForks, and JVM flags with jvmArgs. Integration tests typically get their own source set and task, plus a check dependency, using the jvm-test-suite plugin.

8. Maven versus Gradle

Compare Maven and Gradle. When would you choose each? Basic

What the interviewer is testing: a balanced, experience-based opinion. Never say "one is bad".

Maven is declarative with a fixed lifecycle. The POM says what the project is, and every Maven project looks alike, so a new engineer is productive at once. It has huge plugin coverage and a very low chance of a clever, unreadable build. Gradle is programmable, with a task graph. It is faster for large builds, thanks to incremental work, the build cache, and the daemon, and it can express unusual builds (many source sets, code generation, Android). The cost is more complexity and more ways to write a bad build. I choose Maven for standard services and libraries, especially when the team values uniformity and many people touch the build. I choose Gradle for big multi-module repos where build time matters, for Android, for builds with custom steps, and when the team will invest in learning it. In both, the real determinant of quality is the discipline: pinned versions, convention-based sharing, no logic in the wrong place.

How would you migrate a Maven project to Gradle (or the reverse)? Senior

What the interviewer is testing: that you treat it as a project with risk, not a file conversion.

First answer "why": a concrete pain such as a 25-minute build, or a need for Android. If the reason is only taste, do not migrate. Then plan in steps. Run gradle init in the Maven project, which reads the POMs and generates a first build (modules, dependencies, some plugin settings). Treat the result as a draft. Compare the final artifacts: same jars, same classpath (mvn dependency:tree against gradle dependencies), same test counts. The usual differences: conflict resolution (nearest versus highest, so some versions change), resource filtering, profiles (no direct equivalent; use properties and conditions), and plugins that have no twin, which need a replacement or custom code. Move the shared parts to a version catalog and convention plugins early. Keep the old build working in parallel until the CI, release and deploy jobs produce identical outputs, and then switch. The reverse direction is rarer and mostly about simplicity and standardisation.

Likely follow-ups
  • What is the biggest risk? Silent differences in the dependency tree (version changes) and in packaging (a missing resource or manifest entry), which tests may not catch.
What are common Gradle mistakes you have seen or would review for? Senior

What the interviewer is testing: practical judgement on build quality.

The ones I look for: (1) heavy work in the configuration phase (shell calls, network, file scanning at the top of a script); (2) tasks without declared inputs and outputs, so they never get skipped or are wrongly skipped; (3) using tasks.create and getByName (eager) in a big build; (4) allprojects { } / subprojects { } blocks that hide where settings come from, instead of convention plugins; (5) using api everywhere, or compile-like leaks that destroy incremental benefit; (6) dynamic versions (+) in released code; (7) reading project inside task actions, which blocks the configuration cache; (8) passwords in build.gradle; (9) a huge buildSrc that invalidates everything; (10) not committing the wrapper or lock files. Each one is cheap to fix and shows up as slow or unreliable builds.

9. Dependency conflicts, vulnerabilities and supply chain

What is "jar hell", and how do you detect and fix it? Intermediate

What the interviewer is testing: whether you understand how the classpath really works at runtime.

Jar hell is the situation where the classpath holds several versions of the same library, or the same class in several jars. The JVM's class loader takes the first matching class it finds on the classpath, and ignores the others. So the behaviour depends on jar order. Typical symptoms: NoSuchMethodError, NoClassDefFoundError, AbstractMethodError, LinkageError, or a method that quietly behaves like the old version. Causes: transitive conflicts, a fat jar that includes a copy of a library which also appears normally, the same library under two names (javax.servlet and jakarta.servlet, or google-collections and guava), or an application server that ships its own copy. Detect with the dependency tree, with the enforcer rule banDuplicateClasses, or the Gradle dependencyInsight, and look at which jar a class is loaded from. Fix with one pinned version through dependencyManagement or a Gradle constraint, exclusions of the duplicate, relocation (shading) when two incompatible versions must live together, or a module system or classloader isolation as a last resort.

A scanner reports a CVE in a transitive dependency. How do you fix it? Senior

What the interviewer is testing: a calm, step by step process, and judgement about real risk.

Step 1, understand it. Read the advisory: which versions are affected, is there a fixed version, and how is it exploited (a certain feature, a certain input?). Is the vulnerable code even reachable in my service? Rate it by real risk, not only by the score. Step 2, find the path. Use mvn dependency:tree -Dincludes=... or gradle dependencyInsight to see who brings it. Step 3, upgrade the right thing. Best: upgrade the direct dependency that brings it, if a newer release has the fix. If the owner has not released one, override the transitive version: in Maven through dependencyManagement, in Gradle through a constraint with a because note. Check that the fixed version is compatible (patch and minor versions usually are, a major jump needs testing). Step 4, prove it. Re-run the tree and the scanner, run tests. Step 5, track it. Leave a comment in the POM or build file with the CVE id so that someone removes the override later when the parent catches up. If no fix exists, mitigate (disable a feature, add input validation, a WAF rule) and record an accepted risk with an expiry date.

<!-- pom.xml: override a transitive version, reason documented -->
<dependencyManagement><dependencies>
  <dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>2.17.1</version> <!-- CVE-2021-44228 and follow-ups -->
  </dependency>
</dependencies></dependencyManagement>
Likely follow-ups
  • The fix needs a new major version that breaks API. What now? Check if a patched backport exists, wrap or isolate the usage, or plan the upgrade as a proper task while mitigating.
  • How do you know you are not just hiding it? Re-scan the final built artifact (the fat jar or the image), not just the POM.
Which tools find vulnerable or outdated dependencies, and where do you run them? Intermediate

What the interviewer is testing: practical tooling, plus the point that scanning belongs in the pipeline.

Three groups. Software composition analysis: OWASP Dependency-Check (a Maven and Gradle plugin, uses the National Vulnerability Database), Snyk, Sonatype IQ, JFrog Xray, Trivy and Grype (also scan container images), and GitHub's dependency graph with Dependabot alerts. Update bots: Dependabot and Renovate open pull requests for new versions, with CI proving each one. Inventory: generate an SBOM (Software Bill of Materials) with CycloneDX or SPDX plugins, so when a new CVE appears you can answer "which of our services contain this library" within minutes. Run the scan on every pull request (fast, break on high severity with a documented suppression file for false positives), and on a schedule on the released artifacts, since new CVEs are published for old code. Expect false positives: scanners match by name and version string, so check before reacting.

mvn org.owasp:dependency-check-maven:check -DfailBuildOnCVSS=7
mvn org.cyclonedx:cyclonedx-maven-plugin:makeAggregateBom
./gradlew cyclonedxBom
What is dependency confusion, and how do you protect a build against supply chain attacks? Senior

What the interviewer is testing: security awareness at the developer level.

Dependency confusion: your company has an internal library com.acme:billing-core. An attacker publishes a library with the same coordinates to a public repository with a very high version number. If your build looks at both repositories and takes the highest version (or a repository listed earlier), it pulls the attacker's code. Protections that an application developer can do: resolve everything through one repository manager and route your own groups only to your hosted repository (routing rules in Nexus or Artifactory, or content filters in Gradle); own your group name on Central; avoid version ranges and dynamic versions; pin versions and use Gradle verification metadata or checksum checks; block http repositories (Maven does this since 3.8.1); review new dependencies in pull requests like code; keep the wrapper checksums; and do not run builds with production credentials in the environment. Other typosquatting attacks use a name that looks like a popular library, so check the group id of new dependencies.

What makes a build reproducible, and how can you check it? Senior

What the interviewer is testing: the same source and tools should always give the same artifact.

Sources of difference are: floating versions (ranges, SNAPSHOTs, latest), different tool versions (Maven, Gradle, JDK), different environments (OS, locale, time zone), and content inside the artifact that changes on each build (file timestamps, file order in a zip, build time or hostname written into the manifest). Fixes: wrappers, toolchains, locked or fixed versions, and for byte-for-byte equality: Maven's project.build.outputTimestamp property (supported by the standard plugins in recent versions) and Gradle's preserveFileTimestamps = false and reproducibleFileOrder = true on archive tasks. Check by building twice on different machines and comparing the checksums (the Maven artifact:compare goal from the buildinfo tooling, or a plain hash). Why care: you can verify that a released binary came from the claimed source, and caches (Gradle's build cache especially) work better.

How do you stop SNAPSHOT dependencies from reaching a release? Intermediate

What the interviewer is testing: a guardrail mindset.

A release that depends on a SNAPSHOT is not repeatable, because the snapshot can change or be deleted. In Maven use the enforcer rule requireReleaseDeps in the release profile (it also checks parents and plugins with other rules), and the release plugin already refuses SNAPSHOT dependencies at release:prepare. In Gradle use a small check in a task that runs before publish: iterate the resolved runtimeClasspath and fail if any version ends with -SNAPSHOT, or use dependency locking, which records exact versions. In both cases also configure the repository manager so the release repository rejects redeploys, and keep snapshots in a separate repository with a cleanup policy. The goal: a version number that was ever published is a promise.

10. More questions that come up

How do you build without network access (offline)? Intermediate

What the interviewer is testing: knowing the cache is the source of truth and how to fill it.

Maven: run mvn -o (offline). It will fail for anything missing from ~/.m2. To prefill, run mvn dependency:go-offline once online. It is not perfect, because some plugin dependencies are only discovered when the plugin runs, so a full mvn verify online is the most reliable warm-up. Gradle: --offline uses cached modules only. The Gradle cache has a different format and holds artifacts and metadata, and you can copy ~/.gradle/caches/modules-2 to a build machine, or better, point both tools at an internal repository manager so that "offline from the internet" still works. For air-gapped sites, mirror everything into the internal manager and block outbound traffic.

What are the *.lastUpdated files in ~/.m2, and what does "Could not transfer artifact" with a cached failure mean? Intermediate

What the interviewer is testing: practical local-cache troubleshooting.

When a download fails (timeout, 401, 404, a proxy problem), Maven records the failure in a file named like lib-1.0.jar.lastUpdated next to the artifact, and by default does not retry for a while, to avoid hammering a broken server. Even after you fix the cause (credentials, network, the artifact was just uploaded), Maven still says "was cached in the local repository, resolution will not be reattempted until the update interval of X has elapsed or updates are forced". The fix is mvn -U (force update), or delete the failing artifact folder or all *.lastUpdated files. Modern resolvers (Maven 3.9) keep that state in a separate "resolver status" file, but the idea is the same. Do not wipe the entire ~/.m2 as a first step: it costs a lot of re-download time and hides the real cause, which is usually the settings or the mirror.

mvn -U clean verify
find ~/.m2/repository -name "*.lastUpdated" -delete
Maven or Gradle fails with "PKIX path building failed" or SSL handshake errors against the company repository. What is going on? Senior

What the interviewer is testing: understanding that Java uses its own trust store, which is a very common corporate problem.

The message means the JVM does not trust the certificate chain that the server presented. In companies HTTPS traffic often goes through a proxy or a repository with a certificate signed by an internal certificate authority (CA). The operating system and browser trust that CA, but the JVM uses its own file, cacerts in the JDK folder. So the browser works and Maven does not. Check: which JDK is running the build (mvn -v, ./gradlew --version), and what certificate the server sends (openssl s_client -connect host:443 -showcerts). Fix: import the company CA certificate into the JDK trust store, or into a separate trust store file that you pass with -Djavax.net.ssl.trustStore=/path/file -Djavax.net.ssl.trustStorePassword=.... For Maven put it into MAVEN_OPTS or .mvn/jvm.config. For Gradle use org.gradle.jvmargs in gradle.properties. Note that the Gradle daemon may be a different JVM from the wrapper. Do not "fix" it by disabling certificate checks (-Dmaven.wagon.http.ssl.insecure=true) beyond a quick local experiment. That removes the protection that stops a man-in-the-middle. Specialist depth for managing company PKI and the repository server itself belongs to the platform team.

keytool -importcert -alias corp-ca -file corp-ca.pem \
        -keystore "$JAVA_HOME/lib/security/cacerts" -storepass changeit
# or per project: .mvn/jvm.config
-Djavax.net.ssl.trustStore=/etc/ssl/corp-truststore.jks
How do you make Maven and Gradle work behind a corporate HTTP proxy? Intermediate

What the interviewer is testing: where each tool reads proxy settings, since they differ.

Maven reads the proxy from settings.xml under <proxies> (host, port, user, password, and nonProxyHosts such as your internal Nexus). Gradle does not use that file. It reads JVM system properties: systemProp.http.proxyHost, systemProp.https.proxyHost, ports, and systemProp.http.nonProxyHosts in ~/.gradle/gradle.properties (or the project one). A mistake is to set only http and forget https, since repositories use HTTPS. Also, the wrapper download happens before Gradle properties are read, so the wrapper may need the proxy through environment or JVM settings. The simplest long-term answer is that the build talks only to the internal repository manager, which is reachable without a proxy and is the only machine allowed to talk to the internet. Then no developer needs a proxy for builds.

What is the standard directory layout, and how do you add extra source or resource folders? Basic

What the interviewer is testing: the shared convention; both tools use the same default layout.

Both tools use src/main/java, src/main/resources, src/test/java, src/test/resources. Maven writes to target/, Gradle to build/. Anything in resources is copied to the classpath root of the output (so src/main/resources/application.yml is found as application.yml). To add a generated source folder, Maven uses the build-helper-maven-plugin goal add-source, or the build/sourceDirectory setting for the main one. Gradle changes the source set: sourceSets.main { java.srcDir("build/generated/src") }, and better still, make the generating task's output the source directory so that the dependency is automatic. Keep generated code out of version control and make the compile step depend on the generator.

How do SNAPSHOTs work differently in Maven and Gradle builds? Intermediate

What the interviewer is testing: caching rules for moving versions, which cause stale-jar bugs.

In Maven, a snapshot is checked against the remote based on updatePolicy: daily by default, or always, never, or interval:N minutes, set per repository. The remote repository serves maven-metadata.xml telling the latest timestamped build, and Maven stores it locally. In Gradle, snapshots are "changing modules", cached for 24 hours by default (cacheChangingModulesFor), and --refresh-dependencies checks again. In both, a snapshot used inside the same multi-module reactor or multi-project build is taken from the local build and not from a repository, so there is no staleness inside the build. The stale case is a snapshot from another repository. For a team: either avoid cross-repository snapshots (use a Gradle composite build, or a release version built by CI for every merge), or set the update policy to always on CI.

How does Spring Boot's build plugin work, and how does it differ between Maven and Gradle? Intermediate

What the interviewer is testing: the most common real-life use of both tools in Java shops.

The Spring Boot plugin does three main things. It manages versions: in Maven through the spring-boot-starter-parent (or the BOM import), in Gradle through the Boot plugin and the io.spring.dependency-management plugin, or a platform() dependency. It repackages the jar into an executable jar, where dependency jars are nested in BOOT-INF/lib and a launcher starts the application: in Maven the repackage goal, in Gradle the bootJar task. It also offers run goals (mvn spring-boot:run, ./gradlew bootRun) and can build container images (bootBuildImage or spring-boot:build-image) using buildpacks. In Gradle the normal jar task still produces a plain, non-executable jar, unless you disable it, so a project can have two jars and the wrong one gets deployed. Check which file the Dockerfile or deploy script copies.

11. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

The build passes on your laptop but fails on CI. How do you find the cause? Senior

What the interviewer is testing: a systematic way to compare two environments.

Situation: same commit, green locally, red in the pipeline (compile error, test failure, or missing dependency).

Check first: read the first error in the CI log, not the last. Then list what could differ: tool versions (JDK, Maven, Gradle), operating system and case sensitivity of file names (Windows is case-insensitive, Linux is not), time zone and locale, your local ~/.m2 or ~/.gradle cache holding a SNAPSHOT or a hand-installed jar that CI does not have, a profile or property active locally (in your settings.xml), environment variables, test order and shared state, and files that exist locally but are git-ignored.

Steps:

  1. Print versions on CI (mvn -v, ./gradlew --version) and compare to local.
  2. Reproduce CI locally: clean clone, empty cache or a throwaway local repo (-Dmaven.repo.local=/tmp/m2, GRADLE_USER_HOME=/tmp/g), the same JDK, run the exact CI command.
  3. If a dependency is missing, check whether it came only from your local cache, for example a library you once ran mvn install for by hand.
  4. For a flaky test, run it with a random order and in parallel locally, and check time, locale and file paths.
  5. Fix the cause (declare the dependency in a repository, pin the JDK) and not the symptom.

Prevent: wrappers committed, toolchains or release set, a fresh clone and a clean cache in a nightly job, and the same container image for local and CI builds.

Common mistakes: clearing the CI cache and re-running until it turns green, which hides a dependency on local state.
After a deploy the service throws NoSuchMethodError, but all tests passed. What do you do? Senior

What the interviewer is testing: jar hell diagnosis under pressure, with a rollback first.

Situation: production logs show java.lang.NoSuchMethodError: com.google.common.base.Preconditions.checkArgument(...) right after startup or on one code path. Unit tests did not find it.

Check first: stop the damage: roll back to the last good version if users are affected. Then investigate. Why did the tests pass? Tests ran on the test classpath, which may have a different version from the packaged runtime (for example the application server or fat jar contains another copy).

Steps:

  1. Find the class and method in the stack trace and which library owns it.
  2. On the deployed artifact, list which jars contain that class: unzip -l app.jar | grep guava. More than one version means a conflict.
  3. Run the tree with the verbose flag for that library to see who asks for which version, and what Maven or Gradle selected. Remember Maven picks the nearest, Gradle the highest.
  4. Pin one compatible version through dependencyManagement or a Gradle constraint, or exclude the stale copy.
  5. Add a test that loads the packaged artifact (an integration test on the real jar) or at least an enforcer banDuplicateClasses or requireUpperBoundDeps rule.

Prevent: enforcer rules in CI, tests run against the final package, and no manual jars in the application server's shared library folder.

A teammate's local build uses a different version of a library than yours, with the same SNAPSHOT version number. How did that happen? Intermediate

What the interviewer is testing: SNAPSHOT behaviour and caches.

Situation: the module pricing-1.4.0-SNAPSHOT is used by your service. Your tests pass, your colleague's fail, same service commit.

Check first: where did each of you get the jar? Possibilities: you ran mvn install on your own checkout of pricing (so your ~/.m2 holds your local build, which wins over remote), your colleague has the CI-built snapshot downloaded yesterday, and the update policy is daily so nobody sees a newer one until tomorrow.

Steps: list the artifact folder in ~/.m2/repository/com/acme/pricing/1.4.0-SNAPSHOT on both machines and compare the timestamps and maven-metadata-*.xml. Run mvn -U or delete the folder to get a fresh copy from the repository. Compare checksums of the jars. Use mvn dependency:tree to confirm the resolved version string (a timestamped version shows in debug output).

Prevent: make CI publish every merge to the snapshot repository, tell developers to build the library through the multi-module reactor or a Gradle composite build rather than installing by hand, set the snapshot update policy to always where freshness matters, and use release versions (or ${revision} with a unique build number) for anything that crosses a team boundary.

The build takes 25 minutes and everyone complains. How do you make it faster? Senior

What the interviewer is testing: that you measure first, and know the main levers.

Situation: a multi-module project, CI and local builds are both slow. Developers wait for feedback and start skipping tests.

Check first: measure where time goes. With Gradle, --scan or --profile shows time per task and per phase. With Maven, use a build time extension or the log with timestamps (-Dorg.slf4j.simpleLogger.showDateTime=true), or the maven-build-time-extension. Typical culprits: tests (most often), dependency resolution over a slow network, no use of caches, running everything for every change, and a slow startup of the tool.

Steps:

  1. Tests: split fast unit tests from slow integration tests, run unit tests on each commit and integration tests in a later stage. Parallelise test forks (maxParallelForks, Surefire forkCount), and remove sleeps and heavy shared context setup.
  2. Parallel modules: Maven -T 1C, Gradle org.gradle.parallel=true.
  3. Caches: keep ~/.m2 and ~/.gradle between CI runs. Enable the Gradle build cache with a remote cache, and the configuration cache.
  4. Build only what changed: -pl ... -am (Maven) or just the project tasks (Gradle), driven by what files the pull request touched.
  5. Resolution: use the internal repository manager near the CI, content filters for repositories, no dynamic versions.
  6. Skip optional work on PRs: javadoc, sources jars, large reports, until release time.
  7. Tool: Maven daemon mvnd, bigger daemon heap, an SSD or RAM disk for the workspace.

Prevent: track the build time as a metric, and treat a slow build as a bug with an owner.

Maven deploy fails with 401 Unauthorized or 403 Forbidden against Nexus. What do you check? Intermediate

What the interviewer is testing: credentials wiring, and difference between 401 and 403.

Situation: mvn deploy fails with Return code is: 401 or 403 during upload.

Check first: 401 means "I do not know who you are" (credentials missing or wrong). 403 means "I know you, you are not allowed" (a permission, or a repository rule such as "release repository does not allow redeployment"). Read the URL in the message to see which repository was targeted.

Steps:

  1. Compare the <id> in distributionManagement with the <server><id> in settings.xml. They must be identical, and are case sensitive.
  2. Run mvn help:effective-settings to see whether the server entry is really loaded (the CI user may have a different home, so another settings.xml).
  3. Check the token or password has not expired, and has deploy rights on that repository. A user token may be read-only.
  4. For 403 on release: the version already exists and redeploy is disabled. This is intended. Bump the version.
  5. For SNAPSHOT versus release mixup: a SNAPSHOT version sent to the release repository (or the reverse) is rejected. The version suffix decides the target.
  6. Check whether a mirror mirrorOf * catches the deploy repository id and sends it to the read-only group URL. Deploy needs the hosted repository.

Prevent: keep credentials in CI secrets with a service account, and add a smoke test that deploys a dummy snapshot after a credential change.

On a new laptop every build fails with PKIX path building failed. How do you fix it properly? Intermediate

What the interviewer is testing: JVM trust store knowledge and not taking insecure shortcuts.

Situation: new machine, a fresh JDK, builds against the company Nexus fail with sun.security.provider.certpath.SunCertPathBuilderException: unable to find valid certification path to requested target. The browser opens Nexus without a warning.

Check first: the browser uses the operating system's trust store, where IT has installed the company root CA. The new JDK uses its own cacerts, which lacks it. Confirm the chain with openssl s_client -connect nexus.example.com:443 -showcerts and note the issuer.

Steps:

  1. Get the company root and intermediate CA certificates from the IT portal (not the server's leaf certificate, which will expire).
  2. Import into the JDK that runs the build with keytool -importcert, or, since JDK upgrades replace cacerts, create a separate trust store and pass it through MAVEN_OPTS or .mvn/jvm.config and org.gradle.jvmargs in ~/.gradle/gradle.properties.
  3. Stop old Gradle daemons (./gradlew --stop) so the new options apply.
  4. Re-run with -Djavax.net.debug=ssl:handshake if it still fails, to see which certificate is rejected.

Prevent: write the steps in the team's onboarding page, or ship a dev setup script. Never solve it with "trust all certificates" flags, since they are easy to leave in a CI configuration and switch off protection for the whole team.

A critical CVE (like Log4Shell) is announced on Friday. How do you find out which of your services are affected and fix them? Senior

What the interviewer is testing: speed with accuracy, and knowing that the library may arrive transitively and inside fat jars.

Situation: a widely used library has a remote code execution flaw. Management asks "are we affected?".

Check first: the advisory: affected versions, fixed versions, mitigation flags. Then the inventory: if you have SBOMs or a repository manager with a scanner (Xray, IQ), search for the library there. If not, search all repositories for the library name in POMs, lock files and gradle dependencies output, and also check deployed artifacts, since a fat jar may hide a copy: unzip -l app.jar | grep log4j-core.

Steps:

  1. Make a list of services, with the version found and who owns them. Include third-party software you run, which you cannot rebuild (apply the vendor mitigation).
  2. Apply the mitigation flag at once if it exists and the fix takes time (for Log4Shell, the mitigations changed as new CVEs followed, so read the current advisory).
  3. Fix each service: upgrade the direct dependency, or override the transitive one (dependencyManagement or a Gradle constraint), then rebuild, test and release. Use the Spring Boot BOM property when applicable (log4j2.version in older Boot versions).
  4. Verify on the built artifact with the scanner, not only on the POM, and check for shaded copies that your dependency tree cannot show.
  5. Roll out, watch the logs, and report status.

Prevent: an SBOM for each release, scheduled scans, a short path for a dependency-only release, and a team on-call who knows the process.

Builds fail with "invalid LOC header", "corrupted zip" or a missing POM for an artifact that clearly exists. What do you do? Intermediate

What the interviewer is testing: targeted cache repair instead of deleting everything.

Situation: after a network drop, a full disk, or two parallel builds writing the same cache, a jar in the local cache is truncated, or a POM is an HTML error page saved by a proxy.

Check first: the error names the file or the artifact. Open the file in ~/.m2/repository/... and check its size. A tiny jar, or a "pom" that starts with <html>, is a bad download. Also look at whether the proxy returned a login page.

Steps:

  1. Delete that artifact's folder (the version directory) and run with -U.
  2. If the cache is on a shared CI disk, check parallel jobs: use a separate local repo per job or a cache restore step that is atomic.
  3. For Gradle: --refresh-dependencies, and if needed delete the module from ~/.gradle/caches/modules-2/files-2.1/ and the matching metadata folder, then stop daemons.
  4. If the repository manager itself has a bad cached proxy copy, an admin should invalidate the proxy cache for that path.

Prevent: checksum validation on (-C in Maven fails on bad checksums, --strict-checksums in older versions), disk monitoring, and not sharing one mutable local repository between simultaneous builds.

The fat jar builds fine, but at runtime a framework cannot find its configuration, or a database driver is missing. Why? Senior

What the interviewer is testing: how merging many jars into one loses same-name files.

Situation: after switching to a shaded or assembled jar, one of these happens: No suitable driver, No ServiceProvider found, Akka/Typesafe config values missing, or Invalid signature file digest.

Check first: the Java service loader (ServiceLoader) finds implementations through files named META-INF/services/<interface>. Many libraries have such a file with the same path, and merging jars keeps only one of them, so the other implementations vanish. The same applies to reference.conf, spring.factories, and META-INF/spring/*.imports. Signed jars add .SF and .RSA files that no longer match the merged content.

Steps: compare the list of services in the fat jar with a dependency jar (unzip -p app.jar META-INF/services/java.sql.Driver). In the Maven shade plugin add ServicesResourceTransformer and AppendingTransformer for the config files, and a filter excluding META-INF/*.SF|*.DSA|*.RSA. In Gradle's Shadow plugin call mergeServiceFiles(). Or avoid the problem: use the Spring Boot nested-jar layout or a plain classpath directory with a start script and no merging.

Prevent: an integration test that starts the packaged jar, not the module's classes.

Your Maven release failed halfway: the tag exists and some artifacts were uploaded. What now? Senior

What the interviewer is testing: understanding that releases are immutable, so cleanup must be careful.

Situation: release:perform failed at the deploy step with a network or credential error. Git has the tag v1.4.0 and a "prepare release" commit, and the repository has part of the files for 1.4.0.

Check first: what exactly reached the repository, and did anyone already consume it? If the repository only holds part of the files, no one should use that version. Check whether the release repository allows redeploy (normally not).

Steps:

  1. Decide: if nothing consumed it, an admin deletes the partial 1.4.0 folder from the release repository. Then fix the cause and re-run the deploy from the tag (release:perform again, or a checkout of the tag and mvn deploy).
  2. If you cannot delete (policy, or someone may have pulled it), abandon 1.4.0: roll back git (release:rollback, delete the tag locally and remotely, revert the version commits), and release 1.4.1. A burned version number costs nothing.
  3. Never overwrite a published release with different content.

Prevent: test the credentials and a dry run (-DdryRun=true) before the real release, and move to a pipeline that deploys from a tag with a version supplied by CI, which has fewer moving parts.

You upgrade a dependency and the build is green, but production behaves strangely, with no errors. What could be happening? Senior

What the interviewer is testing: the dangers of silently changed transitive versions and behaviour changes.

Situation: after bumping a library (or the Spring Boot parent), JSON dates look different, a retry stopped working, or logging is gone. Nothing crashes.

Check first: compare the full resolved dependency list before and after, not only the library you changed. A bump can change many transitive versions. Save the tree from before (mvn dependency:tree -DoutputFile=before.txt, gradle dependencies > before.txt) and diff.

Steps:

  1. Diff the trees and read the release notes of every library that moved, especially defaults that changed (serialization settings, timeouts, pool sizes, logging bindings).
  2. Check logging: two SLF4J bindings give a warning and the loss of logs, or Log4j and Logback both present.
  3. Look for a library that changed from javax.* to jakarta.* packages, which silently disables scanning of old annotations.
  4. Bisect: revert half of the version changes and test to isolate the library.
  5. Add a test for the behaviour that broke, so the next bump catches it.

Prevent: update dependencies often and in small steps with a bot, instead of a yearly big bang, and review the tree diff in the pull request.

Gradle builds die with "OutOfMemoryError: Metaspace" or "Java heap space", or the daemon keeps being killed. What do you do? Intermediate

What the interviewer is testing: knowing there are two different JVMs: the Gradle daemon and the processes it starts for compile and tests.

Situation: a large build fails randomly with memory errors or "Gradle build daemon disappeared unexpectedly".

Check first: which JVM ran out? The stack trace and the message tell. The Gradle daemon runs the build logic and the plugins. Compilers (in-process or with a compiler daemon) and each test run in their own forked JVM with their own memory settings. Check ./gradlew --status for several daemons holding memory, and the CI container memory limit (a container killed by the operating system shows as "disappeared").

Steps:

  1. Daemon: set org.gradle.jvmargs=-Xmx3g -XX:MaxMetaspaceSize=1g in gradle.properties.
  2. Tests: set maxHeapSize = "1g" on the test task, and use forkEvery or fewer parallel forks if memory is tight.
  3. Kotlin compile has its own daemon with kotlin.daemon.jvmargs.
  4. Make sure the container limit is bigger than the sum of all JVMs, since both the daemon and the workers count.
  5. If metaspace keeps growing between builds, a plugin may leak classloaders. Update the plugin, or run with --no-daemon on CI.

Prevent: record peak memory in the CI job, and keep Gradle and plugins up to date.

A multi-module Maven build works with "mvn install" at the root but fails when you build one module alone. Why? Intermediate

What the interviewer is testing: how siblings are resolved in the reactor and outside of it.

Situation: mvn -f web/pom.xml package fails with "Could not resolve dependencies ... core:1.0-SNAPSHOT". Building from the root works.

Check first: in the root build, core is part of the reactor, so web uses its fresh output. Built alone, web needs core from a repository, and no one installed it into ~/.m2 or deployed it, or an old copy is there.

Steps: use mvn -pl web -am package from the root, which builds the needed siblings in the same reactor. Or install the dependency once (mvn -pl core install). Beware of stale copies in ~/.m2 when you use the install approach: another branch's core may be there, which produces odd results. Also check that the parent POM resolves (relativePath), and that all inter-module versions come from one property (${project.version} or ${revision}), not typed by hand.

Prevent: CI always builds from the root, with -pl -am for partial builds, and never keeps an unmanaged local repo between jobs.

The Gradle build cache works on your laptop but never hits on CI, so every build is a full build. How do you debug it? Senior

What the interviewer is testing: knowing that a cache key is a hash of every input, so a tiny change in any input is a miss.

Situation: remote cache is configured, but tasks show EXECUTED instead of FROM-CACHE across different CI machines or against the developers.

Check first: is the cache enabled (org.gradle.caching=true or --build-cache), is CI allowed to push and the developers to read, and are the tasks cacheable at all? The build output prints the reason a task was not cached ("Caching disabled for task ... because ...").

Steps:

  1. Run the same commit twice on CI with -Dorg.gradle.caching.debug=true, or better take two build scans and use the "build comparison" feature, which lists the input property that differs.
  2. Typical culprits: an absolute path as an input (different workspace folder per agent, so use relative paths with @PathSensitive(RELATIVE)), a timestamp or random value in an input or in a generated file, a different JDK vendor or minor version, an environment variable read in the build, and unnormalised line endings.
  3. Custom tasks: add @CacheableTask and declare inputs and outputs accurately.
  4. Check the remote cache itself: authentication, size limits and eviction, and network speed (a slow cache can cost more than it saves).

Prevent: a CI job that builds twice in different folders and asserts that the second build is fully cached. That test catches regressions early.

A security review says your build could download an internal library from the public internet. How do you close that gap? Senior

What the interviewer is testing: practical protection from dependency confusion.

Situation: the build has both the company repository and Central. An attacker could publish a package with the same coordinates as your internal com.acme:billing-core to Central with a higher version.

Check first: which repositories each project can reach, and in what order, including repositories declared inside third-party POMs (Maven follows those unless a mirror * catches them).

Steps:

  1. Route all builds through one repository manager group, using a Maven mirror mirrorOf *, and a Gradle settings repository set with FAIL_ON_PROJECT_REPOS.
  2. In the manager, add a routing rule: group com.acme.* is served only from the hosted repository, never from the Central proxy. Or in Gradle add a content filter with includeGroup("com.acme") on the internal repository and excludeGroup("com.acme") on the public one.
  3. Remove version ranges and latest for internal artifacts, and use checksum verification (Gradle verification metadata).
  4. Register your group id on Central if you publish there, so nobody else can.

Prevent: an automated test that tries to resolve a fake internal coordinate and expects a failure, plus periodic review of repository lists.

Logs disappeared after adding a new library, with a warning about multiple SLF4J bindings. What happened and how do you fix it? Intermediate

What the interviewer is testing: a classic transitive conflict that is not a version conflict, but two different implementations of the same API.

Situation: after you add a client library, the application prints SLF4J: Class path contains multiple SLF4J bindings and some or all logs vanish, or the format changes.

Check first: SLF4J is only a facade (an API). It needs exactly one backend on the classpath: Logback, Log4j2 binding, slf4j-simple, or slf4j-reload4j. The new library brought a second backend through its transitive dependencies. In SLF4J 2.x the warning text is slightly different, and it picks one provider.

Steps: find the backends in the tree (mvn dependency:tree | grep -i -E "slf4j|logback|log4j", or gradle dependencyInsight --dependency slf4j), pick the one you want, and exclude the others from the library that carries them (Maven exclusion, or Gradle exclude(group=..., module=...), or a capability rule). Also check for bridges such as log4j-over-slf4j and slf4j-log4j12 together, which create a loop. Libraries should only depend on slf4j-api, so the faulty library is a candidate for a bug report.

Prevent: an enforcer bannedDependencies rule for the backends you do not want.

Closing line for an interview: "A build tool finds the right libraries and does the least work needed. In Maven I rely on convention, pinned versions through dependencyManagement and a BOM, and I check conflicts with the dependency tree and the enforcer plugin. In Gradle I keep configuration light, use implementation over api, share logic through convention plugins and a version catalog, and lean on the build cache.
