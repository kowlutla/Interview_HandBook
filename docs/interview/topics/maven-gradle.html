Maven and Gradle interview questions

The build-tool questions a developer is really asked: Maven lifecycle, scopes, version conflicts, BOMs, multi-module builds, Gradle phases, caching, api versus implementation, and the build incidents you meet at work. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

Version notes: Maven 3.9.x is the long-running stable line. Since Maven 3.8.1, plain-HTTP repositories are blocked by default. Gradle 8.x is what most projects use, and the configuration cache became stable in 8.1. This page is for application developers: it stops before build-farm design and artifact-server administration.

Mental model: the 8 ideas everything hangs on

One line: a build tool does three jobs: it decides the order of work (lifecycle or task graph), it finds the libraries you need (dependency resolution), and it avoids repeating work (caches). Maven does this by convention and a fixed lifecycle. Gradle does it with a flexible task graph and strong caching.
  1. Coordinates. Every library is named by group, artifact and version (GAV), for example org.slf4j:slf4j-api:2.0.13. Repositories, caches and conflicts are all about finding and choosing GAVs.
  2. Declarative versus programmable. Maven is an XML description plus a fixed lifecycle. Gradle is a real program (Groovy or Kotlin) that builds a graph of tasks.
  3. Lifecycle or task graph. Maven runs phases in a fixed order, and plugin goals attach to phases. Gradle runs tasks in dependency order and skips the ones whose inputs did not change.
  4. Transitive dependencies. You declare 10 libraries and get 200 on the classpath. The tool must pick one version of each. Maven picks the nearest to your project, Gradle picks the highest.
  5. Scopes and configurations. A library may be needed at compile time, at run time, only for tests, or only provided by the server. Maven calls this scope, Gradle calls it configuration.
  6. Repositories and caches. A local cache on your machine, then your company proxy (Nexus or Artifactory), then Maven Central. Most "works on my machine" bugs live in this chain.
  7. Reproducibility. Same input should give the same output: fixed versions, wrappers, no surprise SNAPSHOTs.
  8. Fast feedback. Incremental builds, build caches and parallel modules exist to make the second build much faster than the first.

1. Maven core: lifecycle, goals and project structure

Explain the Maven lifecycle and phases. What happens when you run mvn package? Basic

Maven has three built-in lifecycles: clean, default and site. The default one is an ordered list of phases: validate, compile, test, package, verify, install, deploy. When I run a phase, Maven runs every earlier phase first and then that one, so mvn package runs validate, compile, test and package, and stops. It does not install or deploy.

A phase is only an empty slot. The real work is done by plugin goals bound to it: for jar packaging, compiler:compile sits on compile, surefire:test on test and jar:jar on package. There are also small phases in between (generate-sources, process-resources, test-compile). mvn clean package runs the clean lifecycle up to clean (delete target/), then the default lifecycle up to package. install copies the artifact into your local ~/.m2, and deploy uploads it to a remote repository like Nexus.

Remember: a phase runs all earlier phases; package stops before install and deploy. Phases are slots, goals do the work.

What is the difference between a phase, a goal and a plugin? Basic

A plugin is a package of related actions, like maven-compiler-plugin. A goal is one action inside a plugin, written plugin:goal, for example compiler:compile. A phase is a named step in the lifecycle, and goals are bound to phases. I can run a phase, which triggers all goals bound to it, or run a goal directly, which skips the lifecycle.

Some goals, such as dependency:tree, are not bound to any phase, so they run only when I name them. I can mix both in one command and Maven runs them in the order typed. To run extra work at a certain moment (for example code generation), I add a plugin with an <execution> naming the goal and the phase it should attach to.

mvn package                  # a phase: everything up to package
mvn dependency:tree          # a goal: just that action
mvn clean dependency:tree package   # mixed, runs left to right

Remember: plugin contains goals; phases are slots; a goal bound to a phase runs when that phase runs.

What are the Maven coordinates, and how do you see what Maven is really using? Basic

Coordinates identify an artifact: groupId (the organisation or product), artifactId (the module), version, plus optional packaging (jar, war, pom) and classifier (like sources). To see what Maven really uses, I run mvn help:effective-pom, which prints my POM merged with its parents, active profiles and Maven's built-in defaults.

A repository stores an artifact at a path built from the coordinates, like com/acme/orders/1.2.0/orders-1.2.0.jar, so you can find any jar by hand. Every POM silently inherits from the built-in Super POM, which sets Central as the default repository and the default directory layout. That is why a plugin version or repository you never wrote can still be in effect. Maven's default plugin versions are old, so I pin plugin versions in the POM.

mvn help:effective-pom -Doutput=effective.xml
mvn help:active-profiles
mvn -X package        # debug log: classpath, plugin versions, repos

Remember: GAV names the artifact; when behaviour is a mystery, read the effective POM.

What is the difference between inheritance and aggregation in Maven? Intermediate

Inheritance is the <parent> element: a child POM gets the parent's properties, dependencyManagement and plugin settings. It answers "what do these projects share". Aggregation is the <modules> list in a packaging-pom project. It answers "which projects do I build together with one command". They are independent ideas, though most multi-module projects use one POM for both.

A parent need not list modules, and an aggregator need not be anyone's parent. The parent can even live outside your repo, like spring-boot-starter-parent, which gives ready-made versions and plugin settings. Maven looks for the parent at ../pom.xml first (relativePath) and otherwise fetches it from a repository. A project has only one parent, which is exactly why BOM imports exist: they let you share version lists without using up your single parent.

Remember: parent = share config down; modules = build together. One parent only, many BOMs.

2. Maven dependencies: scopes, transitive, conflicts, BOMs

Explain the Maven dependency scopes. Basic

A scope says in which classpaths a dependency is present. compile (default) is everywhere and is passed on to users of my library. provided is for compile and test only, because the container supplies it at run time, like the Servlet API. runtime is not needed to compile but is on the run classpath, like a JDBC driver. test is for tests only, like JUnit.

ScopeCompileTestRunPassed to users of my library?
compileyesyesyesyes
providedyesyesnono
runtimenoyesyesyes, as runtime
testnoyesnono

There are two more: system (a file path on disk, deprecated, avoid) and import (only inside dependencyManagement to import a BOM). The habit I follow is to use the narrowest scope: the JDBC driver as runtime so code cannot import its classes by accident, Lombok as provided, test libraries as test. A transitive library's test and provided dependencies are never passed on.

Remember: compile = everywhere, provided = not at run time, runtime = not at compile time, test = tests only.

What are transitive dependencies, and how does Maven choose a version when two paths disagree? Intermediate

A transitive dependency is a library that my dependency needs, which Maven adds for me. When two paths ask for different versions of the same library, Maven uses dependency mediation: the version nearest to my project in the tree wins, and if the depth is equal, the one declared first wins. It is not "newest wins".

So a direct dependency always beats a transitive one, and an old version two hops away can beat a newer one three hops away. That is the cause of many NoSuchMethodError bugs: my code needs the new API, but Maven kept the old copy. To fix it I declare the version I want directly (depth 1), or pin it in dependencyManagement, which applies to the whole tree. Gradle uses a different rule (highest wins).

mvn dependency:tree -Dverbose -Dincludes=com.acme:util
# +- lib-A:1.0
# |  \- util:1.0
# \- lib-B:1.0
#    \- lib-C:1.0
#       \- (util:2.0 - omitted for conflict with 1.0)

Remember: Maven = nearest wins (then first declared), not newest. Gradle = highest wins.

What is dependencyManagement, and how is it different from dependencies? Intermediate

<dependencies> really adds libraries to the project's classpath. <dependencyManagement> only sets rules: "if anyone in this build uses this library, use this version, scope and exclusions". It adds nothing by itself. Children then declare the dependency without a version.

The strongest feature is that the rule also applies to transitive dependencies. If a library I use pulls in Jackson 2.9, a managed Jackson 2.17 overrides it everywhere, even though I never wrote Jackson myself. So there is one place to change a version for all modules. A child's own explicit version still beats the managed one.

<!-- parent pom -->
<dependencyManagement><dependencies>
  <dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.17.1</version>
  </dependency>
</dependencies></dependencyManagement>

<!-- child pom: no version needed -->
<dependency>
  <groupId>com.fasterxml.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
</dependency>
Watch out: putting a library only under dependencyManagement does not put it on the classpath.

Remember: dependencies = what I use; dependencyManagement = which version, including for transitives.

What is a BOM, and how do you import one? Intermediate

A BOM (Bill of Materials) is a POM with packaging pom whose content is a dependencyManagement list of versions that are known to work together, like spring-boot-dependencies. I import it inside my own dependencyManagement with type pom and scope import. Then I declare the libraries without versions.

Unlike a parent, I can import many BOMs. If two BOMs manage the same library, the one listed first wins, and my own explicit entries beat imported ones. The Spring Boot BOM only gives versions. The Spring Boot parent POM also configures plugins and resource filtering, so I use the BOM when I already have my own parent. Gradle has the same idea with platform().

<dependencyManagement><dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-dependencies</artifactId>
    <version>3.3.4</version>
    <type>pom</type>
    <scope>import</scope>
  </dependency>
</dependencies></dependencyManagement>

Remember: BOM = a shared version list you import (scope import, type pom); many allowed, unlike a parent.

What is the difference between exclusions and optional dependencies? Intermediate

An exclusion is set by the consumer: "I use library X, but do not bring in its dependency Y". It cuts one branch of the tree in my project only. An optional dependency is set by the library author: "I need Z only for a feature, so do not pass it on to my users". The first is the consumer's cut, the second is the author's.

I use an exclusion to remove an old logging backend or a duplicate of a library I supply myself. A typical optional case is a library that supports Jackson or Gson and wants me to pick one. After any exclusion I run the tests and check the tree, because cutting something the code really needs shows up as ClassNotFoundException at runtime. A wildcard exclusion (*:*) gives a bare dependency when I will supply everything myself.

<dependency>
  <groupId>org.apache.hadoop</groupId>
  <artifactId>hadoop-client</artifactId>
  <version>3.3.6</version>
  <exclusions><exclusion>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-reload4j</artifactId>
  </exclusion></exclusions>
</dependency>

Remember: exclusion = consumer cuts a branch; optional = author does not pass it on.

What is the difference between a SNAPSHOT and a release version? Basic

A version ending in -SNAPSHOT means work in progress: the same version string can point to different jars over time. A release version such as 1.2.0 is immutable. Once published it must never change, and if it is wrong I publish 1.2.1.

In the remote repository a snapshot is stored with a timestamp (like 1.2.0-20241114.101500-7), and a metadata file tells Maven which is the latest. Maven checks for a newer snapshot by an update policy, once a day by default, or every time with -U. The danger is that two developers, or CI and a laptop, can hold different jars under the "same" version, so builds are not repeatable. Repositories like Nexus normally refuse to redeploy a release. Many teams also ban SNAPSHOT dependencies in release builds with the enforcer rule requireReleaseDeps. Gradle caches snapshots (it calls them "changing modules") for 24 hours by default, and --refresh-dependencies checks again.

Remember: release never changes, SNAPSHOT always may. Force a fresh check with mvn -U.

What is "jar hell", and how do you detect and fix it? Intermediate

Jar hell is when the classpath holds several versions of the same library, or the same class in several jars. The JVM class loader takes the first matching class it finds and ignores the rest, so behaviour depends on jar order. The symptoms are NoSuchMethodError, NoClassDefFoundError or a method that quietly behaves like the old version.

To detect it, I print the dependency tree for that library, then ask which jar a class was really loaded from (-verbose:class, or Foo.class.getProtectionDomain().getCodeSource()). It compiled fine because the compile and runtime classpaths can differ. Causes are transitive conflicts, a fat jar with its own copy of a library, the same library under two names (google-collections and guava), or a server that ships its own copy. Fixes: pin one version through dependencyManagement, exclude the stale copy, or, only when two incompatible versions must coexist, relocate one by shading. To stop it coming back, the enforcer plugin has requireUpperBoundDeps and (in extra-enforcer-rules) banDuplicateClasses.

Remember: the JVM takes the first class it finds. Find who brought the old copy, pin one version.

3. Maven plugins, profiles, repositories and multi-module builds

Surefire versus Failsafe: what is the difference, and why two plugins? Intermediate

Surefire runs unit tests in the test phase, picking classes named *Test, Test* or *Tests. Failsafe runs integration tests in the integration-test phase and checks their result later in verify, picking *IT or IT*. They are split because integration tests need setup and cleanup around them, and the cleanup must run even when a test fails.

pre-integration-test starts a server or container and post-integration-test stops it. If an integration test fails, Failsafe does not fail the build at once. It waits for verify, after cleanup has run. That is why CI runs mvn verify, not mvn integration-test. Testcontainers inside the test itself is the modern way and reduces the need for phase-based setup. If tests silently do not run, suspect a wrong name pattern, or an old Surefire with JUnit 5 (it needs 2.22 or newer). To run one test: mvn test -Dtest=OrderServiceTest#shouldPay.

Remember: Surefire = unit (test), Failsafe = integration (*IT); run mvn verify so cleanup still happens.

What are Maven profiles, how are they activated, and what are the risks? Intermediate

A profile is a named block of POM settings (properties, dependencies, plugins, repositories) that applies only when the profile is active. I activate it with -P name, or automatically by JDK version, operating system, a property (-Denv=prod) or the presence of a file. The risk is that a profile changes what the artifact contains, so the jar built with -Pprod is not the one I tested.

I use profiles for things like "run slow integration tests" or "sign artifacts on release". The safer pattern for environments is to build one artifact once and give it configuration at runtime (environment variables, a config server). One trap: activeByDefault switches off as soon as any other profile in the same POM is activated, which surprises people. Profiles can also live in settings.xml for machine-specific values, which is a common reason why "it works only on my machine".

mvn -Pintegration verify
mvn help:active-profiles
mvn -P '!slow' test       # deactivate a profile

Remember: one artifact, many environments through runtime config, not through build profiles.

What goes in settings.xml, and how is it different from the POM? Basic

The POM describes the project and is committed to source control. settings.xml describes the machine and the user (~/.m2/settings.xml), and holds credentials, so it is never committed. It has servers (credentials), mirrors (redirect repository requests to the company proxy), proxies, and profiles for this machine.

A server entry is matched to a repository by id. If distributionManagement names the repository company-releases but the server id in settings differs, the upload goes with no credentials and fails with 401. A mirror with mirrorOf * sends every repository request, even ones declared in third-party POMs, to your proxy. That is good for control, but a vendor repository that the proxy does not know about then cannot be found, so add that remote to the repository manager. Since Maven 3.8.1 a built-in mirror also blocks plain http:// repositories, because anyone on the network path could swap a jar. The fix is to use https, not to disable the block.

<settings>
  <servers><server><id>company-releases</id>
    <username>${env.NEXUS_USER}</username>
    <password>${env.NEXUS_TOKEN}</password></server></servers>
  <mirrors><mirror><id>company-all</id><mirrorOf>*</mirrorOf>
    <url>https://nexus.example.com/repository/maven-public/</url></mirror></mirrors>
</settings>

Remember: POM = project (shared), settings.xml = machine and secrets. Server id must equal repository id.

How does Maven find an artifact? Describe the local repository, the mirror and Central. Intermediate

Maven first looks in the local repository (~/.m2/repository). If it is not there, Maven asks the remote repositories, and if a mirror matches, the request goes to the mirror instead. In companies the mirror is a repository manager such as Nexus or Artifactory that hosts our own releases and snapshots and proxies Maven Central, caching what it fetches.

Once downloaded, an artifact is reused with no network at all. When a download fails, Maven leaves a *.lastUpdated marker and will not retry until the update interval passes. That is why a server problem you already fixed still seems broken until you run mvn -U or delete the marker files. The first debugging step for "Could not resolve" is to check which URL it actually tried, because the mirror usually changed it.

Remember: local, then mirror (Nexus), then Central. A failed download is cached until -U.

How does a multi-module Maven build work? What is the reactor? Intermediate

A multi-module project has a root POM with packaging pom and a <modules> list. When I run Maven at the root, the reactor reads all module POMs, builds a graph from how they depend on each other, and builds them in dependency order, not in the order of the list. A cycle between modules is an error.

Inside one reactor build a module can use a sibling's output straight from target/classes (or the packaged jar), with nothing installed into ~/.m2. To build part of the project I use -pl (project list), with -am to also build what they need, or -amd to also build their dependents. -rf :web resumes after a failure and -T 1C builds independent modules in parallel, one thread per core. By default one failure stops the build, and --fail-at-end carries on with independent modules.

mvn -pl service,web -am -DskipTests package   # these two and what they need
mvn -T 1C -B verify                            # parallel
mvn -rf :web verify                            # resume from web

Remember: the reactor orders modules by dependencies. Partial build: -pl x -am.

4. Gradle core: phases, tasks, incremental build and caching

Explain the three phases of a Gradle build: initialization, configuration, execution. Intermediate

In initialization, Gradle reads settings.gradle(.kts) to find which projects are in the build. In configuration, it runs the build script of every project to create tasks and wire the task graph, but no task action runs yet. In execution, it runs only the tasks needed for the requested one, in dependency order, skipping the up-to-date ones.

The classic trap is code written straight in the build script body or a configure block. It runs at configuration time on every build, even for gradle help, so an exec call or a network request there slows every command. Work belongs inside doLast { } or a task class, which run only at execution time. The configuration cache can skip phase 2 completely when nothing in the build logic changed.

tasks.register("report") {
    println("CONFIG time: runs on every build")      // bad place for work
    doLast { println("EXECUTION time: only when task runs") }
}

Remember: initialize (which projects), configure (build the graph, no work), execute (run tasks). Keep work out of configuration.

What is a Gradle task, and how does the task graph decide the order? Intermediate

A task is a unit of work with inputs, outputs and an action, like compiling Java or running tests. Gradle collects the needed tasks into a directed acyclic graph (DAG: arrows with no cycles), sorts it, and runs independent tasks in parallel if allowed. If I ask for build, it pulls in everything build needs and nothing else.

Order comes from relationships. dependsOn means "run that first, and add it to the graph". mustRunAfter only sets an order when both tasks are already in the graph. finalizedBy runs a cleanup task after me, even if I fail. Most dependencies are inferred: if task B uses the output of task A as its input, Gradle links them without a hand-written dependsOn. Use tasks.register, not tasks.create: register builds the task only if it is needed (configuration avoidance), which keeps configuration fast in a big build.

gradle build --dry-run        # show the tasks that would run, run none
gradle :app:test --tests '*OrderServiceTest'
gradle build -x test          # exclude a task

Remember: tasks form a DAG. dependsOn adds and orders; mustRunAfter only orders. Prefer register.

How does Gradle know a task is UP-TO-DATE? Intermediate

Before running a task, Gradle fingerprints its inputs (source files, properties, classpath) and its outputs, and compares them with what it stored from the last run. If both are unchanged, the task is marked UP-TO-DATE and skipped. This is the incremental build, and the build cache is built on the same idea.

Fingerprints use file contents, not only timestamps, so touching a file without changing it triggers no rebuild. A custom task that declares no inputs and outputs always runs, because Gradle has nothing to compare. The opposite bug is worse: a task reads a file it did not declare as an input, so Gradle thinks nothing changed and keeps a stale result. So declare everything a task reads and writes. The statuses to know: UP-TO-DATE (local outputs are fine), FROM-CACHE (outputs restored from the build cache), NO-SOURCE (nothing to process). --info tells why a task re-ran.

Remember: same inputs and same outputs means skip. Undeclared inputs cause stale results.

What is the Gradle build cache, and how is it different from the up-to-date check? Senior

The up-to-date check compares only with the last run in the same workspace. The build cache stores task outputs under a key that is a hash of all the inputs, so any build on any branch or machine that reaches the cache can download the outputs instead of running the task. Gradle then marks the task FROM-CACHE. It pays off most on CI and when switching branches.

There is a local cache and an optional remote cache (an HTTP service, typically writable by CI only). For a hit, tasks must be cacheable and deterministic. If a task puts a timestamp or an absolute path into its output, or reads an undeclared input, the key differs, or worse, a wrong output is shared. When the cache never hits on CI, I compare two build scans, which show the input that differs. Usual culprits are absolute paths, timestamps, a different JDK, or environment variables. Enable it with org.gradle.caching=true.

The configuration cache is a different thing: it saves the result of the configuration phase (the task graph) so the next run skips straight to execution. It needs tasks not to touch the live project model at run time. It became stable in Gradle 8.1 and is switched on with org.gradle.configuration-cache=true.

# gradle.properties
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.parallel=true

Remember: up-to-date = same workspace; build cache = shared outputs by input hash; configuration cache = saves the task graph.

What are the Gradle and Maven wrappers, and why commit them? Basic

The wrapper is a small script (gradlew or mvnw) committed to the repo. It downloads the exact Gradle or Maven version named in a properties file and runs it. So every developer and CI use the same tool version and need only a JDK installed.

For Gradle the files are gradlew, gradlew.bat and gradle/wrapper/ (a properties file plus a small jar). I upgrade with ./gradlew wrapper --gradle-version <version> and commit the change. For Maven, mvn wrapper:wrapper creates mvnw and .mvn/wrapper. A safe practice is to add distributionSha256Sum so a tampered download is rejected, since the wrapper jar is executable code. A related point: Gradle runs a background JVM (the daemon) that stays alive for about three hours idle, so later builds start fast. If behaviour looks strange, ./gradlew --stop kills the daemons.

Remember: commit gradlew/mvnw so everyone builds with the same tool version. Strange Gradle behaviour: --stop.

5. Gradle dependencies, version control and multi-project builds

What is the difference between api and implementation in Gradle? Intermediate

Both come from the java-library plugin. implementation means "my code uses this library inside, it is not part of my public API", so modules that depend on mine do not get it on their compile classpath. api means "this library's types appear in my public signatures", so consumers need it to compile and do get it. I start with implementation and switch to api only when a type from that library is visible in my public methods.

Two reasons to prefer implementation. It hides internals, so consumers cannot depend on them by accident. And it makes builds faster: when an implementation dependency changes, only my module recompiles, while a change to an api dependency ripples through every consumer. Note the library is still on the consumers' runtime classpath. Maven has no direct equivalent: a Maven compile dependency leaks to all downstream modules like api. The other keywords map to Maven scopes: compileOnly to provided, runtimeOnly to runtime, testImplementation to test. The old compile and runtime configurations were removed in Gradle 7.

plugins { `java-library` }
dependencies {
    api("com.google.code.gson:gson:2.11.0")              // in public signatures
    implementation("com.squareup.okhttp3:okhttp:4.12.0") // internal only
    compileOnly("org.projectlombok:lombok:1.18.34")
    runtimeOnly("org.postgresql:postgresql:42.7.4")
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.2")
}

Remember: api = visible to consumers at compile time; implementation = private. Default to implementation.

How does Gradle resolve version conflicts, how is it different from Maven, and how do you override a version? Intermediate

Gradle builds the whole graph first, then picks the highest requested version of each module. Maven picks the nearest. If my app asks for util 1.0 and a library asks for util 2.0, Maven keeps 1.0 and Gradle uses 2.0. Gradle's rule is usually safer when libraries follow semantic versioning, but a major version can break the API, so I still test.

To override, I use a constraint: "if this library appears anywhere, it must be at least this version". It adds no dependency by itself, so it is Gradle's equivalent of dependencyManagement. A platform(...) imports a BOM as constraints, and strictly in a version is a hard rule that fails the build if it cannot be met. force works but hides the reason, so I prefer a constraint with a because note. To see why a version was chosen, gradle dependencyInsight --dependency name shows who asked for what and which rule won. In gradle dependencies output an arrow like 1.0 -> 2.0 means the request was upgraded.

dependencies {
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.3.4"))
    implementation("org.springframework.boot:spring-boot-starter-web")  // no version
    constraints {
        implementation("com.acme:util:2.1") { because("CVE fix, see SEC-123") }
    }
}
// ./gradlew :app:dependencyInsight --dependency util --configuration runtimeClasspath

Remember: Gradle highest wins, Maven nearest wins. Override with a constraint or platform, and explain why.

What is a Gradle version catalog, and why use one? Intermediate

A version catalog is a file, gradle/libs.versions.toml, that lists versions, libraries, bundles and plugins in one place. Gradle generates type-safe accessors, so a build file says libs.jackson.databind and the IDE autocompletes it. It gives one place to update a version for all modules and avoids copy-pasted version strings.

The sections are [versions], [libraries], [bundles] (libraries used together, like test libraries) and [plugins]. It has been stable since Gradle 7.4. A catalog only declares coordinates. It does not force versions in the dependency graph, so conflict handling is still done with constraints or platforms. It plays the role that properties in a Maven parent POM play, but type safe.

# gradle/libs.versions.toml
[versions]
jackson = "2.17.2"
[libraries]
jackson-databind = { module = "com.fasterxml.jackson.core:jackson-databind", version.ref = "jackson" }

// build.gradle.kts
dependencies { implementation(libs.jackson.databind) }

Remember: catalog = names and versions in one TOML file; constraints and platforms still decide the graph.

How does a multi-project Gradle build work, and how do you share build logic across projects? Intermediate

settings.gradle(.kts) names the root project and lists subprojects with include("core", "service", "web"). Each subproject has its own build file, and dependencies between them are written implementation(project(":core")). To share build logic I use convention plugins, not allprojects { } blocks.

Gradle works at the task level, so asking for :web:build builds what web needs from core automatically, with no flag like Maven's -am, and independent tasks can run in parallel (org.gradle.parallel=true). For shared logic, allprojects and subprojects blocks in the root script couple the projects and hide where settings come from. A convention plugin is a small precompiled script plugin (for example acme.java-conventions.gradle.kts) that sets the Java version, test settings and static analysis. Each module just says plugins { id("acme.java-conventions") }. It lives in an included build such as build-logic, or in buildSrc, which is simpler but invalidates caches of the whole build whenever it changes. It plays the role of a Maven parent POM, but a module can combine several conventions.

// settings.gradle.kts
rootProject.name = "shop"
includeBuild("build-logic")
include("core", "service", "web")

// web/build.gradle.kts
plugins { id("acme.java-conventions") }
dependencies { implementation(project(":core")); implementation(project(":service")) }

Remember: settings lists projects; share logic with convention plugins (build-logic), not allprojects.

6. Maven versus Gradle

Compare Maven and Gradle. When would you choose each? Basic

Maven is declarative with a fixed lifecycle: the POM says what the project is, so every Maven project looks alike and a new engineer is productive at once. Gradle is programmable with a task graph, and is faster on big builds because of incremental work, the build cache and the daemon. I choose Maven for standard services and libraries where uniformity matters, and Gradle for large multi-module repos where build time matters, for Android, and for builds with custom steps.

Gradle's cost is a steeper learning curve and more freedom to write a messy build. Maven's cost is rigidity: unusual builds need plugin configuration. In both, quality comes from discipline: pinned versions, shared conventions, a wrapper, and no heavy logic in the wrong place. The conflict rule is the favourite trap: Maven takes the nearest version, Gradle the highest.

Remember: Maven = convention and uniformity; Gradle = flexibility and speed. Nearest wins versus highest wins.

7. Vulnerable and conflicting dependencies

A scanner reports a CVE in a transitive dependency. How do you fix it? Senior

First I read the advisory: which versions are affected, whether a fix exists, and whether my service even uses the vulnerable code. Then I find who brings it with mvn dependency:tree -Dincludes=... or gradle dependencyInsight. Best fix is to upgrade the direct dependency that brings it. If the owner has no fix yet, I override the transitive version and write the CVE id next to it.

In Maven the override goes in dependencyManagement, in Gradle in a constraint with a because note. Patch and minor jumps are usually safe, a major jump needs real testing. Then I prove it: re-run the tree, the scanner and the tests, and scan the final artifact (the fat jar or image), not only the POM, because shaded copies are invisible to the tree. The comment lets someone remove the override later when the parent catches up. If no fixed version exists, I mitigate (disable the feature, validate input) and record an accepted risk with an expiry date. Tools: OWASP Dependency-Check, Snyk, Dependabot or Renovate for update pull requests, and an SBOM (a list of every component in a release) to answer "which services contain this library" quickly.

<!-- pom.xml: override a transitive version, reason documented -->
<dependencyManagement><dependencies>
  <dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>2.17.1</version> <!-- CVE-2021-44228 and follow-ups -->
  </dependency>
</dependencies></dependencyManagement>

Remember: understand it, trace it, upgrade the parent or override the version, re-scan the built artifact, document why.

8. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

The build passes on your laptop but fails on CI. How do you find the cause? Senior

Almost always the two environments differ: tool or JDK versions, or something that exists only in my local cache or settings. I read the first error in the CI log, then reproduce CI locally with a clean clone, an empty cache and the same JDK, and fix the cause rather than re-running until green.

Situation: same commit, green locally, red in the pipeline (compile error, test failure or missing dependency).

Check first: print mvn -v or ./gradlew --version on CI and compare. Then look for local-only state: a SNAPSHOT or a jar I once mvn installed by hand, a profile or mirror in my own settings.xml, environment variables, file name case (Windows ignores case, Linux does not), time zone, locale, and test order or shared state.

Fix: run the exact CI command in a clean clone with a throwaway cache (-Dmaven.repo.local=/tmp/m2 or GRADLE_USER_HOME=/tmp/g). If a dependency was only in my cache, publish it properly or declare it. Pin the JDK.

Prevent: commit the wrappers, set maven.compiler.release or a Gradle toolchain, and use the same container image locally and on CI.

Watch out: clearing the CI cache and re-running until it turns green hides a dependency on local state.

Remember: compare tool versions, then hunt local-only state (cache, settings, hand-installed jars).

After a deploy the service throws NoSuchMethodError, but all tests passed. What do you do? Senior

First I roll back if users are affected. Then I treat it as jar hell: the packaged app has a different version of a library than the one the code compiled against. I find who brings the old copy, pin one version, and add a guard so it cannot return.

Situation: production logs show NoSuchMethodError: com.google.common.base.Preconditions.checkArgument(...) on one code path. Unit tests were green.

Check first: tests ran on the test classpath, which can differ from the packaged runtime (for example the fat jar or application server carries another copy). List the jars that contain the class: unzip -l app.jar | grep guava. Run -verbose:class to see which jar actually loaded it.

Fix: print the verbose tree for that library (mvn dependency:tree -Dverbose -Dincludes=com.google.guava:guava or gradle dependencyInsight) and see who asks for what. Remember Maven keeps the nearest, Gradle the highest. Pin one compatible version in dependencyManagement or a Gradle constraint, or exclude the stale copy.

Prevent: enforcer rules requireUpperBoundDeps and banDuplicateClasses in CI, an integration test that starts the packaged artifact, and no hand-copied jars in the server's shared lib folder.

Remember: compiled against one version, ran on another. Find the loaded jar, then pin one version.

A teammate's build uses a different jar than yours, with the same SNAPSHOT version number. How did that happen? Intermediate

A SNAPSHOT is not one fixed jar. My ~/.m2 probably holds a build I did myself with mvn install, while my teammate has the CI snapshot downloaded yesterday, because snapshots are re-checked only once a day by default.

Situation: pricing-1.4.0-SNAPSHOT is used by your service. Same service commit, but tests pass for you and fail for your colleague.

Check first: where did each jar come from? List ~/.m2/repository/com/acme/pricing/1.4.0-SNAPSHOT on both machines and compare timestamps and the metadata files, then compare jar checksums.

Fix: run mvn -U (or delete that folder) to pull a fresh copy from the repository, so both use the same one.

Prevent: have CI publish every merge to the snapshot repository, build the library through the reactor (or a Gradle composite build) instead of installing by hand, and use real release versions for anything that crosses a team boundary.

Remember: same SNAPSHOT name does not mean same jar. Use -U, and prefer releases across teams.

The build takes 25 minutes and everyone complains. How do you make it faster? Senior

I measure first, because guessing wastes time. Then I go after the biggest cost, which is usually tests, then add parallelism, caches, and build-only-what-changed. Slow builds make people skip tests, so I treat it as a bug with an owner.

Situation: multi-module project, slow on both CI and laptops.

Check first: with Gradle, --scan or --profile shows time per task. With Maven, log timestamps or a build-time extension. Typical culprits: tests, slow dependency downloads, no caches, and building everything for every change.

Fix, in order of payoff:

  1. Tests: run fast unit tests on every commit, integration tests in a later stage, parallelise test forks, remove sleeps and heavy shared setup.
  2. Parallel modules: Maven -T 1C, Gradle org.gradle.parallel=true.
  3. Caches: keep ~/.m2 and ~/.gradle between CI runs. In Gradle enable the build cache (with a remote cache for CI) and the configuration cache.
  4. Build only what changed: -pl ... -am in Maven, project-level tasks in Gradle.
  5. Resolve through a nearby repository manager, with no dynamic versions. Skip javadoc and source jars on pull requests.

Prevent: track build time as a metric and review it regularly.

Remember: measure, then tests, parallel, caches, only what changed.

Maven says "Could not resolve dependencies" or "Could not transfer artifact" for a library that exists. What do you check? Intermediate

I read which URL Maven actually tried, then check the usual suspects in order: a cached failure (*.lastUpdated), the mirror and repository ids, credentials, and for certificate errors the JVM trust store. Most of the time it is the mirror or a cached earlier failure, not a missing library.

Situation: a build fails to download an artifact that you can see in Nexus.

Check first: the error text. was cached in the local repository ... until the update interval has elapsed means an earlier failure is remembered. A 401 means no or wrong credentials, a 403 means no permission (or "release already exists" on deploy), and a 404 usually means the mirror does not proxy the repository that has it.

Fix:

  1. Run mvn -U, or delete that artifact folder and the *.lastUpdated files. Do not wipe all of ~/.m2 first, it hides the real cause.
  2. Run mvn help:effective-settings to see the mirror and servers really loaded, and confirm the server id equals the repository id.
  3. If the mirror is mirrorOf *, add the vendor repository to the repository manager's group.
  4. PKIX path building failed means the JVM does not trust the company CA. The browser uses the operating system store, the JVM uses its own cacerts. Import the company CA into the JDK that runs the build, never disable certificate checks.
  5. If a jar is corrupted ("invalid LOC header"), delete that artifact folder and re-download.

Prevent: a documented dev setup for settings and CA, and build only through the company repository manager.

Remember: which URL, cached failure (-U), mirror and ids, credentials, trust store.

Closing line for an interview: "A build tool finds the right libraries and does the least work needed. In Maven I rely on convention, pinned versions through dependencyManagement and a BOM, and I check conflicts with the dependency tree and the enforcer plugin. In Gradle I keep configuration light, use implementation over api, share logic through convention plugins and a version catalog, and lean on the build cache. Trap to avoid: saying "Maven takes the newest version" or "Gradle takes the nearest". It is the other way round: Maven takes the nearest, Gradle takes the highest. Also do not say dependencyManagement adds a dependency. It only controls versions.
