Scaling the stateless tier

What is the difference between vertical and horizontal scaling, and when do you pick each? Basic
Say this: "Vertical scaling means a bigger box, horizontal means more boxes. I scale the stateless app tier out because it is cheap and gives availability too. I scale the database up first and protect it with caches and replicas before I think about sharding."

Vertical scaling (scale up) means giving one machine more CPU, RAM or faster disk. Horizontal scaling (scale out) means running more machines of the same kind behind a load balancer (a component that spreads incoming requests over the machines).

Why this choice matters. Every system eventually outgrows one machine. The question is how you grow. Vertical growth needs no code change, but you hit a ceiling (the biggest instance a cloud sells) and the price per unit of capacity rises steeply near that ceiling. Horizontal growth has almost no ceiling, but your software must be able to run as many copies, which is the real design work.

VerticalHorizontal
EffortTrivial, no code changeNeeds a stateless or partitioned design
CeilingHard limit (biggest instance size)Practically very high
Cost curveGets superlinear at the top endRoughly linear
FailureOne box is a single point of failureLose one of N, lose 1/N of capacity
DowntimeOften needs a restart to resizeAdd nodes with no downtime

A worked example. An API runs on one 8-core machine at 90 percent CPU. Going vertical: move to a 16-core machine, which takes a restart (a few minutes of downtime) and doubles the bill. Going horizontal: put 3 of the 8-core machines behind a load balancer. If one dies, you still have 2/3 of capacity and no outage. The second option is usually cheaper and safer, but only works if requests do not depend on which machine handled the previous one.

Decision rule. Pick vertical when the system is small, when the bottleneck is a single-node database (writes cannot simply be split across copies), or when the code is stateful and cannot yet be split. Pick horizontal for the web and API tier. In practice the order is: scale the stateless tier out, scale the database up as far as is sensible, then add read replicas and caches, and only then shard (split the data across several databases).

What an interviewer probes next: "Why not scale the database out too?" Because a database holds state; copies must agree with each other, which is exactly the hard part (see the replication and sharding page).

Remember: stateless tier scales out, stateful tier scales up first, then replicate, cache, shard.

What does "stateless service" mean and why is it the foundation of horizontal scaling? Basic
Say this: "A stateless service keeps nothing about a client between requests in its own memory or disk. Any instance can serve any request, so the load balancer can route freely and I can add or kill instances at will. The state did not vanish, it moved to a database, a cache or the client's token."

What it means. A stateless service treats each request as self-contained. Everything it needs arrives with the request (an auth token, parameters, a body) or is fetched from a shared store (database, cache, object storage). It does not remember "user 42 was on step 3" in local memory.

Why it is the foundation of horizontal scaling. Imagine a service that remembers your shopping cart in its own RAM. If your next request lands on a different copy, the cart is gone. To avoid that you would have to pin each user to one copy, and then you cannot freely add, remove or restart copies. Statelessness removes the pinning, which gives you four things at once:

  1. The load balancer can send each request anywhere, so load spreads evenly.
  2. Instances are interchangeable, so you can add, kill or replace them whenever you like.
  3. A crash loses only the requests in flight at that moment, not user data.
  4. Autoscaling and rolling deploys become safe, because removing an instance removes no unique information.

Example. Request 1: POST /cart/items hits node A; the item is written to a shared cart table (or Redis). Request 2: GET /cart hits node B; it reads the same table and sees the item. Node A could have been killed in between and nothing is lost.

Stateless does not mean "no state". The design question is always "where does the state live instead?" Typical homes: the database (durable truth), a cache (fast copy), the client (a signed token or cookie), a queue (work in progress), object storage (files).

Trap: answering "just put it in Redis" for everything. A shared store becomes the new bottleneck and the new single point of failure, so it needs its own scaling, replication and failure story.

Remember: stateless = state moved out of the process, not state removed.

What kinds of hidden state quietly break statelessness? Intermediate
Say this: "Anything held in one node's memory or disk that another node would need is hidden state: HTTP sessions, uploaded files, local caches that must agree, in-process schedulers, per-node rate-limit counters and WebSocket connections."

A service can look stateless on the architecture diagram and still break the moment you run two copies. Each item below is a common culprit, with the symptom you would see and the usual fix.

Hidden stateSymptom with N nodesFix
In-memory HTTP session (servlet session map)User is randomly logged out or sees an empty cartShared session store or signed token
Local file uploads or temp filesUpload went to node A, download lands on node B and returns 404Object storage (S3-like), or a shared file system
Local cache that must be consistent (permissions cache)Admin changes a permission, only the node that handled the call sees itShared cache or broadcast invalidation with a short TTL
In-process scheduler or cronThe nightly job runs 10 times with 10 instancesLeader election, or a distributed scheduler lock
In-memory rate-limit counterEach node counts alone, so the real limit is N times higherShared counter (Redis) or a gateway-level limiter
WebSocket or streaming connectionThe connection is pinned to one node; you cannot push to it from anotherRouting table or pub/sub layer (see the WebSocket question)
Singleton counters, sequence generators, local clock for orderingDuplicate ids, out-of-order eventsDatabase sequence, ID generator service, logical clocks
Big warm-up data (ML model, lookup table in heap)Not wrong, but a new node is slow and uses lots of memory for a whileReadiness gate, shared cache, slow start

How to find them. A practical test: run two copies behind a load balancer with round robin and click through the app. Anything that works with one copy but fails with two is hidden state. Another test: kill a random instance during a load test and look at what users lose.

Interviewer follow-up: "Is a local read-only cache of config acceptable?" Yes, if staleness for a few seconds is fine and nothing depends on all nodes agreeing at the same instant. The hidden-state problem is state that must be shared or must survive the node.

Remember: if it breaks when you run two copies, it is hidden state.

How does the load balancer choose among stateless instances, and which algorithm would you choose? Intermediate
Say this: "Default to least outstanding requests, or round robin when requests are uniform, with health checks and slow start for new nodes. I use hashing only when locality matters, such as a per-node cache for a key range."

What the load balancer does. It receives each request and picks one healthy instance to forward it to. The choice rule is the algorithm.

AlgorithmHowGood forWeak when
Round robinTake turns: A, B, C, A, B, CUniform, short requestsRequest costs vary, so a node can pile up slow ones
Weighted round robinBigger nodes get more turnsMixed instance sizes, canary traffic (5 percent to the new version)Weights are static and must be tuned
Least connections / least outstanding requestsSend to the node with the fewest in-flight requestsVariable cost, long callsNeeds the balancer to track state; many balancers each see only their own view
Power of two choicesPick 2 random nodes, send to the less loaded oneLarge fleets and many balancersSlightly less optimal than a perfect global view
IP or key hash, consistent hashSame key always goes to the same nodeCache affinity, sticky behaviourHot keys overload one node

Why "power of two choices" is interesting. If every balancer always picks "the least loaded node", they all see the same node as least loaded at the same moment and all send to it (herding). Picking two at random and taking the better one avoids this and gets close to optimal balance with almost no coordination.

Example of why round robin fails. Three nodes; 1 percent of requests take 5 s and the rest take 20 ms. Round robin is blind to this, so a node that got two slow requests in a row queues up while others sit idle. Least outstanding requests notices the queue and routes around it.

Decision rule. Uniform and cheap requests: round robin. Variable or long requests: least outstanding requests. Huge fleets: power of two choices. Local caches by key: consistent hashing. Always combine with health checks so dead nodes drop out.

Trap: round robin with a freshly started slow node. It gets the same share as everyone and falls behind. Least-connections plus slow start (ramp the weight up over 30 to 120 seconds) fixes this.

Remember: least outstanding requests by default; hash only for locality; add health checks and slow start.

You added more app servers but throughput barely improved. Why? Senior
Say this: "More app nodes only help if the app tier is the bottleneck. I would find the saturated resource first: usually a shared dependency like the database, a lock, the load balancer, or uneven traffic. Then fix that, not add more nodes."

The idea. Throughput is limited by the slowest stage that every request must pass through. Duplicating a stage that is not the slowest changes nothing. Think of a restaurant: hiring more waiters does nothing if there is one cook.

Checklist, with how to recognise each case:

  1. A shared dependency is saturated. Database CPU at 100 percent, connection limit reached, a single Redis maxed out, a slow third-party API. More app nodes push more load into the same limit. It often gets worse: each node opens its own connection pool, so 50 nodes x 20 connections is 1,000 connections to the database.
  2. Lock contention. Work is serialised on one hot row or a distributed lock, so ten nodes queue behind the same lock.
  3. Load balancer or network limit. Bandwidth, new connections per second, or a single LB instance.
  4. Uneven distribution. Sticky sessions or a hot key send most traffic to a few nodes while the rest idle.
  5. Coordination cost. Chatty node-to-node calls or cluster-wide cache invalidation broadcasts grow with N.
  6. A serial fraction of the work (Amdahl's law). If 10 percent of each request is inherently serial, speedup can never exceed 10x however many nodes you add. With 5 percent serial, the cap is 20x.

Method. Use the USE method for each component: Utilisation, Saturation, Errors. Find which resource is at its limit (CPU, memory, connections, queue length, lock wait), fix that, then move on to the next bottleneck. Caching in front of the database is often the cheapest fix because it removes load instead of adding capacity.

Interviewer follow-up: "How do you prove it?" Load test while watching per-tier metrics; the first resource that flatlines at a ceiling while latency climbs is the bottleneck.

Remember: scale the bottleneck, not the tier that is easy to scale.

How do clients find instances that come and go? Explain service discovery. Intermediate
Say this: "Service discovery keeps a live list of healthy instances so clients never hard-code addresses. Server-side discovery puts a load balancer or virtual IP in front. Client-side discovery has the client ask a registry. On Kubernetes, a Service plus DNS does it for you. Health checks decide who is in the list."

The problem. With autoscaling and restarts, instances get new IP addresses constantly. If service A has the IP of service B written in its config, the first restart breaks it. You need a lookup that is always current.

StyleHow it worksProsCons
Server-sideClient calls a stable address (cloud load balancer, Kubernetes Service virtual IP); the balancer consults the registrySimple clients, any languageOne extra hop, the balancer must be scaled and kept available
Client-sideClient asks a registry (Eureka, Consul, a gRPC resolver) and chooses an instance itselfNo extra hop, client can do smart balancingEvery language needs the logic, clients hold a cached view that can be stale
DNS-basedInstances published as DNS records with a short TTLEasy, universalResolvers and clients cache DNS, so changes spread slowly and unevenly
Service mesh sidecarA proxy next to each pod (Envoy-based meshes) handles discovery, retries, mTLS, balancingUniform behaviour, no app codeOperational complexity, extra resource use

How registration works. Self-registration: the instance tells the registry "I am here at 10.0.3.7:8080" and sends heartbeats; if heartbeats stop, the registry removes it. Third-party registration: the platform (Kubernetes) watches pods and updates the endpoint list itself, using readiness probes to decide who may receive traffic.

Walk-through. The orders service calls http://payments. DNS resolves that to a virtual IP; the cluster routes to one of three ready payment pods. A pod fails its readiness check, so it is removed from the list within seconds. Orders never changed anything.

Failure to mention. The registry can be stale for a few seconds, so a client may still send to a dead instance. That is why clients need timeouts, retries to a different instance (for idempotent calls) and circuit breakers.

Remember: a registry plus health checks; clients must still tolerate a stale view.

At a design level, what do containers and an orchestrator (such as Kubernetes) give you for scaling a stateless tier? Basic
Say this: "A container gives me an identical, immutable, fast-starting unit; an orchestrator like Kubernetes keeps a declared number of them running, replaces failures, does rolling updates, and gives stable names for discovery. Liveness and readiness probes are what make it safe."

Container. A package of your app plus its libraries and runtime in an immutable image. Every instance started from it is identical, and it starts in seconds rather than the minutes a VM can need. That identity is what makes "add 10 more copies" safe.

Orchestrator. You declare the desired state ("12 replicas of image v1.4, 500m CPU each") and a control loop continuously compares reality with it and fixes differences. What that gives you:

  • Scheduling: places containers on nodes with enough free CPU and memory.
  • Self-healing: restarts crashed containers and moves workloads off failed nodes.
  • Scaling: change the replica count by hand or with an autoscaler.
  • Rolling updates and rollback, gated by readiness.
  • Discovery and load balancing: a stable service name in front of changing pods.
  • Config and secrets injected from outside, which keeps the image stateless and reusable across environments.

Liveness vs readiness. A liveness probe asks "is this process stuck? If so, restart it". A readiness probe asks "can it take traffic right now?" If not, it is removed from the load balancer but not restarted. Mixing them up causes outages: if the liveness check calls the database, a short database blip makes every healthy pod fail liveness, and the orchestrator restarts all of them at once. Dependencies belong in readiness (or nowhere), not in liveness.

Two scaling layers. Pods scale first (seconds). If the cluster has no free node, new pods stay "Pending" until a node-level (cluster) autoscaler adds a machine, which takes minutes. So the pod autoscaler and node autoscaler must be sized to work together, and you keep some spare node capacity for sudden spikes.

Remember: immutable image + desired-state reconciliation; liveness restarts, readiness gates traffic.

Sessions and where state lives

Where can you keep user session state in a scaled-out system? Compare the options. Intermediate
Say this: "Four options: sticky sessions in server memory, a shared session store, a client-side signed token, or replicated sessions. Modern default: a short-lived signed token for authentication plus a small server-side store for what must be revocable or mutable."

The problem. HTTP is stateless, yet users expect "being logged in" and a persistent cart. Something must remember. With several servers, you must decide where that memory lives so that any server can answer the next request.

OptionHowProsCons
Server memory + sticky sessionsLB pins a user to one nodeFast, no extra systemUneven load, session lost on node death or deploy, blocks easy scale-in
Shared session store (Redis, Memcached, DB)Cookie holds a session id; the data lives in the storeAny node serves any user; easy revocationExtra network hop per request; the store is a critical dependency
Client-side token (signed JWT or encrypted cookie)Claims travel with every requestNo server lookup, scales triviallyHard to revoke, size limits, secrets must be encrypted, stale claims until expiry
Replicated sessions between nodesApp-server cluster copies sessions to peersNo external storeMemory and chatter grow with N; does not scale to large fleets

How the shared store works. Login: server creates a random session id, stores sess:ab12 -> {userId:42, cart:[...]} in Redis with a TTL of 30 minutes, and sets cookie sid=ab12. Each request: any node reads the cookie, fetches sess:ab12, refreshes the TTL. Logout: delete the key and the session is dead instantly on all nodes.

How a token works. The server signs {userId:42, role:"admin", exp:...} with a secret key; any node can verify the signature with no lookup. The cost is that you cannot "un-issue" it before it expires.

Decision rule. Need instant revocation or large mutable data: shared store. Need zero lookup on the hot path and can accept short staleness: token. Typically combine: a 5 to 15 minute access token plus a refresh token checked server-side. Keep the session small, give it a TTL, and decide up front what happens when the store is down (usually fail closed for auth).

Remember: avoid memory-only sessions; token for speed, store for control, often both.

JWT vs a server-side session in Redis: which is better for a high-scale API, and what is the catch? Senior
Say this: "A signed JWT removes the session store from the hot path because any node verifies it with a key. The catch is revocation and stale claims, so I use short expiry plus a server-checked refresh token, and keep a small deny-list for emergencies."

What a JWT is. A JSON Web Token has three parts: a header, a payload of claims (user id, roles, expiry) and a signature made with a secret or private key. Any service that has the key (or public key) can verify that the payload has not been tampered with, without calling anyone.

Why it scales. With a server-side session, every request needs a Redis read (about 1 ms plus a hard dependency). At 100,000 requests per second that is 100,000 reads per second you must serve and keep highly available. With a JWT, verification is a CPU-only signature check on the local node.

The catches, with a concrete example. A user is fired at 10:00. Their token, issued at 09:55 with a 1-hour expiry, is still cryptographically valid until 10:55. Nothing on the server knows to reject it.

  • Revocation. Mitigate with short expiry (5 to 15 minutes) plus a refresh token that is checked against server state, so access ends within minutes. For immediate cut-off, keep a small deny-list of revoked token ids in a cache; it is small because entries only need to live until the token's expiry.
  • Stale claims. A role change does not apply until the token is refreshed.
  • Size. It is sent on every request; large claims cost bandwidth.
  • Key management. Plan rotation, and always enforce the expected algorithm (never accept "alg: none" or switch from RSA to HMAC based on the header).
  • Storage in the browser. A token readable by scripts can be stolen via XSS; an HttpOnly cookie is safer.

Server-side session gives instant revocation and tiny cookies but adds one cache read per request and a dependency that must be highly available.

Decision rule. Many microservices verifying identity at the edge: JWT. Sensitive actions (change password, payments) or need to kill sessions immediately: check server state too. Many real systems use both.

Remember: JWT trades revocation for scalability; short expiry plus refresh recovers most of it.

What are sticky sessions, when are they acceptable, and what do they cost you? Intermediate
Say this: "Sticky sessions make the load balancer send one user to the same instance every time. They are acceptable for in-memory state like a WebSocket or as a bridge while migrating a legacy app, but they cause uneven load and lose sessions on node death, so stickiness should only ever be an optimisation, never a correctness requirement."

How it works. The balancer either sets a cookie naming the chosen node (AWSALB=node-3) or hashes the client IP or a key to pick the node. Later requests with that cookie or hash go to the same node.

Why people use it. The app keeps data in local memory (a session map, a game room, a large per-user working set). Sticky routing makes that work with several nodes without rewriting the app.

The costs, with an example. Six nodes; one customer runs a huge report that keeps one node at 100 percent CPU. Other users stuck to that node suffer, and the balancer cannot move them because they are pinned. Then:

  • Load is uneven; a few heavy users pile onto one node.
  • A node crash or a deploy drops every session pinned to it.
  • Scale-in kills live users; scale-out does not help existing users, who stay on old nodes while new nodes sit idle.
  • Canaries and blue-green switches get complicated because users are glued to the old version.

Acceptable when: state must be in memory for performance (WebSockets, a large per-user working set, a game room), or as a short-term bridge during migration to a stateless design.

Rule. Treat stickiness as a cache-locality hint. The system must still work, only slower, if a request lands elsewhere: the real state should be recoverable from a shared store.

Remember: sticky is a performance hint, not where truth lives.

How do you scale WebSocket or other long-lived connection servers, given the connection itself is state? Senior
Say this: "Terminate connections on a gateway fleet scaled on connection count and memory. Keep a user-to-node routing table or use pub/sub so any service can reach a user. Clients reconnect with backoff and jitter and resume from a last-seen id. Business logic stays in stateless services behind the gateway."

Why it is different. A WebSocket is a long-lived TCP connection used for push (chat, live prices, notifications). The connection lives on exactly one server, so the "pin to one node" rule is unavoidable. The goal is to keep that pinned state minimal and recoverable.

  1. Gateway tier. Dedicated nodes only hold sockets. One well-tuned node can hold tens to hundreds of thousands of mostly idle connections (limits: file descriptors, memory per connection, kernel settings). So scale on connection count and memory, not CPU.
  2. Reaching a user. Service X wants to push to user 42. Option A: a routing table in a shared store (user:42 -> gateway-7); X sends the message to gateway-7. Option B: publish to a pub/sub channel (Redis pub/sub, Kafka) that all gateways subscribe to; the gateway that holds user 42 delivers it and others ignore it.
  3. Reconnects. Deploys and scale-in will drop connections. Clients must reconnect with exponential backoff plus jitter and resume from the last message id they saw, so no messages are lost or duplicated.
  4. Draining. On shutdown, ask clients to reconnect elsewhere gradually. If 100,000 clients reconnect in the same second, they can overload the remaining nodes (a reconnect storm, also called thundering herd).
  5. Logic out of the gateway. The gateway authenticates, holds the socket and forwards; business rules run in stateless services. That keeps gateway deploys rare and fast.

Pitfall. A load balancer idle timeout shorter than the app's heartbeat will silently cut connections; use heartbeats (ping/pong) below that timeout.

Remember: scale sockets by count, route by table or pub/sub, reconnect with jitter.

Autoscaling

What signals do you use to autoscale a stateless service, and which are better than CPU? Intermediate
Say this: "CPU is the easy default but only works when CPU is the real limit. For APIs I prefer requests per second or in-flight concurrency per instance, for queue consumers queue depth or age, for IO-bound services thread-pool saturation, and I add scheduled scaling for known peaks."

What autoscaling does. A controller watches a metric and changes the number of instances to keep the metric near a target. The quality of the result depends almost entirely on whether the metric reflects real saturation.

Why CPU can mislead. Suppose a service spends 90 percent of each request waiting on a slow downstream. Its threads are all blocked, requests queue, latency explodes, yet CPU shows 20 percent. A CPU-based autoscaler sees no problem and does nothing. The metric must match the resource that actually runs out.

WorkloadBetter signalWhy
Request-serving APIRequests per second per instance, in-flight requests, or p95 latencyDirectly tied to how much work each instance is doing
Queue consumerQueue depth, or age of the oldest message, divided by per-worker throughputTells you how many workers are needed to catch up
IO-bound, waits on downstreamsConcurrency or thread-pool saturationCPU stays low while all threads are blocked
WebSocket gatewayConnection count, memoryEach connection costs memory, not CPU
Predictable daily peakScheduled scaling (for example scale up at 08:45 before the 09:00 rush)Reactive scaling is always late

Worked example, target tracking. Each instance handles 200 req/s comfortably. You set the target to 60 percent of that, 120 req/s per instance. At 1,200 req/s the controller wants 1,200 / 120 = 10 instances. If traffic goes to 2,400 it asks for 20. You pick a target below 100 percent so there is headroom to absorb a spike while the new instances boot.

Queue consumers. If 6,000 messages are waiting, each worker processes 10 per second, and you want to drain in 60 seconds, you need 6,000 / (10 x 60) = 10 workers.

Interviewer follow-up: "What if one signal is not enough?" Use several metrics and scale to whichever asks for the most instances (this is how Kubernetes HPA with multiple metrics behaves).

Remember: scale on the saturating resource, set a target below 100 percent, schedule known peaks.

What are the common autoscaling pitfalls? Senior
Say this: "Autoscaling is slow and can oscillate or amplify damage: metric and boot lag, flapping, scaling the app when the database is the bottleneck, cold-start death spirals, retry amplification and cost runaway. It handles gradual growth; for sudden spikes I rely on headroom, load shedding and rate limiting."

Each pitfall below is a thing that really happens, with its mitigation.

  • Lag. The chain is: metric collection (about a minute), decision, instance boot (VM minutes, container seconds to a minute), warm-up. A spike can double traffic in two minutes and hurt long before help arrives. Fix: headroom, scheduled or predictive scaling, small fast-starting images, pre-warmed pools.
  • Flapping (thrashing). Scale up, load per node drops, scale down, load rises again. Fix: a longer cooldown for scale-down than scale-up, and hysteresis (different up and down thresholds, for example up above 70 percent, down only below 40).
  • Scaling the wrong thing. Adding app nodes when the database is the bottleneck increases connections and load on it and makes the outage worse. Cap max replicas to what downstreams can bear.
  • Death spiral. New instances start cold, take traffic before they are ready, respond slowly, push the average up, trigger even more cold instances. Fix: readiness gating and slow start.
  • Retry amplification. When latency rises, clients retry, load rises further, and scale-up lags even more. Fix: retry budgets, backoff with jitter, circuit breakers.
  • Metric mismatch. CPU low while all threads are blocked, so nothing scales.
  • Cost runaway. A bug or an attack scales you to the maximum. Set a ceiling and a billing or instance-count alarm.
  • Per-instance resources that do not scale with N: connection pools, licence counts, rate limits to an upstream.

Timeline of why it is late. t=0 spike starts; t=60 s metric shows it; t=90 s decision made; t=150 s new instances booted; t=210 s warmed up. During those 3.5 minutes users see errors. That is why headroom (running at 50 to 65 percent rather than 90) is the real protection.

Say: "Autoscaling handles gradual growth. For sudden spikes I rely on headroom, load shedding and rate limiting, because new capacity arrives too late."

Remember: reactive scaling is always late; headroom and limits cover the gap.

What is instance warm-up and why does a freshly started instance often perform badly? Intermediate
Say this: "A new instance is slow at first because the JIT has not optimised hot paths, classes are lazily loaded, local caches are empty and pools are unfilled. I gate it with a readiness probe that runs a warm-up, use slow start at the load balancer, and shift deploy traffic gradually."

Why a fresh instance is slower.

  • JIT compilation. The JVM starts by interpreting bytecode and only compiles hot methods to fast native code after seeing them run many times. The first thousands of requests are slower.
  • Lazy class loading and initialisation add one-time latency to the first calls of each path.
  • Empty local caches. Every request misses and hits the database, so the new node is both slow and a source of extra database load.
  • Connection pools not filled. The first requests pay for opening TCP and TLS connections.
  • DNS and TLS session caches are cold.

Example. An old node answers in 20 ms. A new node answers its first minute at 200 ms. With round robin it still receives its full share, so its queue builds, it times out, and the average latency of the whole fleet jumps right after every scale-out or deploy.

What to do.

  1. Readiness probe returns success only after startup work finishes: load config, open pools, run a synthetic warm-up request set.
  2. Slow start at the load balancer: ramp the new node's share from a small weight up to full over 30 to 120 seconds.
  3. Start warm: pre-populate local caches or rely on a shared distributed cache.
  4. Gradual deploys (canary) instead of switching all traffic at once.
  5. Pre-scale ahead of known peaks, so warm-up happens before the load arrives.

Interviewer follow-up: "Why does this matter for autoscaling?" Because scale-out events happen exactly when the system is already stressed; cold nodes that take full traffic immediately can make the overload worse.

Remember: ready is not the same as started; ramp traffic in.

Why is scaling in (removing instances) harder than scaling out? Intermediate
Say this: "Adding a node is additive, but removing one can drop live work. So I deregister it, drain in-flight requests, hand back queue messages, close connections cleanly, and only then exit. I pick the victim carefully and scale in slowly."

Why scale-in is harder. A new node starts with nothing to lose. A node being removed may hold in-flight requests, a half-processed queue message, open WebSocket connections, a long-running job, and (if the design is sloppy) unique state.

Scale-in steps.

  1. Stop sending new requests: deregister from the load balancer or fail readiness.
  2. Let in-flight requests finish (connection draining).
  3. Finish or hand back queue messages so another consumer can take them.
  4. Close connections cleanly; for long-lived connections ask clients to reconnect elsewhere gradually.
  5. Exit before the platform's force-kill deadline.

Choosing the victim. Prefer the newest instance or the least loaded one. Do not pick a node that is 15 minutes into a 20-minute job. Some platforms support "scale-in protection" for instances marked busy.

Scaling in slowly. Remove about 10 percent of capacity at a time and wait a cooldown. A wrong decision to scale out is cheap (you pay a bit extra); a wrong decision to scale in causes an outage. That is why scale-down cooldowns are typically longer than scale-up cooldowns.

Example of a trap. Traffic dips at 14:00 for 3 minutes and the autoscaler removes half the fleet. Traffic returns, the remaining nodes are overwhelmed, and the new nodes need minutes to boot. A longer scale-in delay and a conservative step avoid this.

Remember: scale out fast, scale in slow and gracefully.

Deployment impact and graceful shutdown

How does a deployment affect capacity, and how do you avoid an outage during a rolling deploy? Senior
Say this: "A rolling deploy temporarily removes capacity and adds cold instances. I control max unavailable and max surge, keep headroom for the batch plus losing a zone, gate on readiness, use canary or blue-green, and do database changes in backward-compatible steps."

The capacity arithmetic. You run 10 nodes at 80 percent utilisation. A rolling deploy takes 3 out at once. The remaining 7 must carry the same load: 80 x 10 / 7 = about 114 percent. They overload and fall over, and now the deploy has caused the outage. Also the replacement instances start cold and are slower than the old ones.

Controls.

  • Max unavailable (how many may be down) and max surge (how many extra to start first). Surge-first (start new before removing old) keeps capacity constant, at the price of briefly using more resources.
  • Headroom covering the batch size plus losing one availability zone.
  • Readiness gates on each step, then a small bake time and health metrics checks before continuing.
  • Canary: send 1 to 5 percent of traffic to the new version, watch error rate and latency, then expand. Limits the blast radius.
  • Blue-green: a full parallel environment; switch the router; keep the old one for instant rollback. Costs double capacity during the switch.
  • Backward-compatible database changes (expand, migrate, contract): old and new code run side by side during the deploy, so a new column must be added first (expand), code that handles both runs (migrate), and the old column is removed only later (contract).
  • Avoid deploying at peak, and avoid all services deploying simultaneously.

Interviewer follow-up: "How do you roll back?" Keep the previous image and config; rollback is just redeploying it, which only works if the database change was backward compatible. That is why destructive schema changes are never in the same release as the code that needs them.

Remember: deploys are a planned partial outage; budget capacity for them.

Walk through a graceful shutdown of a stateless service and explain connection draining. Intermediate
Say this: "On SIGTERM the instance goes unready so the balancer stops sending new requests, keeps serving in-flight ones until done or a timeout, stops queue consumers after the current message, flushes and closes resources, then exits within the grace period. Connection draining is the balancer side of the same idea."

Definition. Connection draining (also called deregistration delay) means a node leaving the pool stops receiving new requests but is given time to finish the ones already in flight.

  1. The orchestrator or scaler decides to stop the instance and sends a termination signal (SIGTERM).
  2. The instance fails its readiness check (or is deregistered), so the load balancer stops routing new requests. This propagates with a delay, so a few more requests may still arrive.
  3. The app stops accepting new connections but keeps serving in-flight requests until done, bounded by a timeout.
  4. Queue consumers stop polling, finish the current message and ack it (or let it return to the queue).
  5. Flush buffers, close database pools, deregister from discovery.
  6. Exit. If it has not exited within the grace period, the platform force-kills it (SIGKILL), so the grace period must be longer than the longest normal request.

Common bug 1. The process dies instantly on SIGTERM while the load balancer still sends it traffic for several seconds, producing a burst of 502 errors on every deploy. Fix: after going unready, wait a few seconds before closing the listener.

Common bug 2. Keep-alive connections that clients reuse keep pointing at the old instance. Send Connection: close or close idle connections once draining begins.

Because clients can still see failures (crash, forced kill), design for idempotent operations and client retries. Graceful shutdown reduces errors but cannot eliminate them.

Remember: unready, drain, stop consumers, close, exit before SIGKILL.

How much spare capacity should a stateless tier carry, and why? Senior
Say this: "Plan for failure, not just load. With three zones and a need to survive losing one, peak utilisation should be near 65 percent, then add margin for deploys and autoscaling lag. Running at 90 percent causes a latency cliff on any spike."

The arithmetic. You run across 3 availability zones (AZ, separate data-centre groups in one region). If one fails, the other two must carry everything. Total traffic T is normally split T/3 per zone; after a failure it is T/2 per zone, which is 1.5x the normal per-zone load. If those two zones can safely run at 100 percent, then before the failure each zone must have been at most 66 percent. So total peak utilisation should be around 65 percent for N+1 zone safety.

A small spike, a deploy or a lost node pushes latency off a cliff. Running hot looks efficient on a cost report but is fragile.

Caching basics: why and where

Why do we cache? Give a concrete example with numbers. Basic
Say this: "A cache keeps a copy of expensive-to-get data somewhere faster. It lowers latency, takes load off the source of truth, and saves cost. It works because access is skewed and reads outnumber writes."

What it is. A cache is a fast, usually smaller, usually temporary store placed in front of a slower or more expensive source (a database, a remote API, a computation). On a read, you check the cache first.

Why it exists. Databases are slow relative to memory, and they are hard to scale because they hold state. Without a cache, every page view runs the same queries again. With a cache, the answer is computed once and reused until it changes.

Worked example. A product page needs data that takes 40 ms and one database query. A cache lookup takes about 1 ms. At a 95 percent hit ratio:

  • Average read time: 0.95 x 1 ms + 0.05 x (1 + 40) ms = 0.95 + 2.05 = about 3 ms (vs 40 ms).
  • Database load: at 20,000 reads per second, only 5 percent miss, so the database sees 1,000 queries per second instead of 20,000.

The load reduction is the real win: a database that could not scale now has 20x headroom, which is often worth more than the latency gain.

Why caching works at all. Two properties of real traffic. First, access is skewed (roughly a power law): a small set of items gets most of the traffic, so a small cache captures most reads (the "80/20" intuition). Second, data is read far more often than it changes, so a copy stays valid for a useful time. If neither is true (uniform random access, constantly changing data), a cache helps little.

The price. Staleness (the copy can be out of date), extra complexity (invalidation, failure modes), extra infrastructure, and memory cost.

Remember: caches buy speed and database headroom, and cost you freshness and simplicity.

How does HTTP caching work for clients and CDNs (Cache-Control, ETag, versioned URLs)? Intermediate
Say this: "Cache-Control says how long a response can be reused, ETag lets the client revalidate cheaply with a 304, stale-while-revalidate hides refresh latency, and Vary controls variants. For static assets I put a content hash in the filename and cache them forever."

The mechanism. HTTP has a built-in caching protocol that browsers, CDNs and proxies all understand. The server sends headers describing how long the response may be reused; caches follow them.

  • Cache-Control: max-age=N lets the browser and shared caches reuse the response for N seconds with no request at all. s-maxage applies only to shared caches such as a CDN. private means only the browser may store it; no-store means store nowhere; no-cache (confusingly) means store but revalidate before each use.
  • Validators. The server sends an ETag (content fingerprint) or Last-Modified. When the copy expires, the client asks If-None-Match: "abc"; if unchanged the server replies 304 Not Modified with no body. That saves bandwidth, not the round trip.
  • stale-while-revalidate serves the stale copy immediately and refreshes in the background; stale-if-error serves stale when the origin is failing.
  • Vary names the request headers that change the response (Accept-Encoding, Accept-Language). A wrong Vary either fragments the cache or leaks one user's variant to another.

Example flow.

GET /app.3f9a1c.js
-> 200, Cache-Control: public, max-age=31536000, immutable   (cached for a year)

GET /api/products/42
-> 200, ETag: "v17", Cache-Control: max-age=30
... 30 s later ...
GET /api/products/42  If-None-Match: "v17"
-> 304 Not Modified (no body)

Best practice for static assets. Put a content hash in the file name (app.3f9a1c.js), serve it with a very long max-age and immutable, and deploy a new file name whenever the content changes. This sidesteps invalidation completely: the HTML that references the new name is short-lived, the assets are forever.

Trap: caching a personalised response (account page keyed by a session cookie) at a CDN without private or a correct Vary. One user's data gets served to another. This class of incident is real and is a security issue.

Remember: hashed filenames for assets, short TTL plus validators for APIs, private for personal data.

What does a CDN actually do, and when is it not enough? Basic
Say this: "A CDN is a global fleet of edge servers that cache copies and answer from the nearest location. It cuts latency, offloads the origin and absorbs spikes and some attacks. It is not enough for highly personalised or constantly changing content."

What it is. A content delivery network has points of presence in many cities. A user's request is routed (by DNS or anycast) to a nearby edge. The edge returns a cached copy if it has one; otherwise it fetches from your origin, stores it per the cache headers and returns it.

Why it exists. Distance costs time: a round trip from Mumbai to a US-East origin may be 200 ms; to a Mumbai edge, 10 ms. And your origin cannot serve every image and script for millions of users. The CDN turns millions of origin requests into a handful.

What it gives you.

  • Lower latency (shorter distance, optimised connections, TLS terminated nearby).
  • Origin offload: a 95 percent edge hit ratio means the origin sees 5 percent of the traffic.
  • Spike absorption: a viral image costs the origin one fetch, not a million.
  • Protection: DDoS absorption and a WAF at the edge.
  • Origin shield: an extra tier so many edge misses collapse into one request to the origin (request coalescing at CDN level).

When it is not enough. Content that is highly personalised, changes every second, or is write-heavy. Then cache what you can (static parts, shared fragments, a short-TTL public version of an API), compute the rest at the origin, or run light logic at the edge (edge functions).

Pitfalls. Purge delay (invalidations take seconds to minutes to reach all edges), cache-key mistakes that fragment or leak variants, and treating the CDN as a security boundary for private data.

Remember: CDN = geographic cache plus origin shield; best for public, cacheable content.

Local (in-process) cache vs distributed cache: how do you choose? Intermediate
Say this: "Local caches are nanosecond fast but each node has its own copy, so they can disagree. Distributed caches are one shared copy, bigger, but cost a network hop and a new dependency. I use local for tiny hot slow-changing data and often both together, with a short-TTL local cache in front."
Local (for example Caffeine, Guava)Distributed (Redis, Memcached)

Why the hit ratio differs. With 10 app nodes and a local cache each, a key must be loaded once per node: 10 database reads for the same data. With one shared cache, it is loaded once. Local caches also make rolling deploys expensive: every restart wipes its cache.

Why consistency differs. If product 42 changes, a shared cache is updated in one place. With 10 local caches you must reach all 10, or wait for each TTL.

Decision rule.

  • Tiny, hot, rarely changing, staleness-tolerant (feature flags, config, country lists): local.
  • Large working set, tighter consistency, shared across nodes (product catalogue, sessions): distributed.
  • Very hot keys: both. A local cache with a short TTL (1 to 10 seconds) in front of the distributed cache removes the network hop and protects the shared cache from hot keys.

Remember: local is faster but inconsistent; distributed is shared but costs a hop.

What is a multi-level (L1/L2) cache, and what new problems does it bring? Senior
Say this: "L1 is a small in-process cache with a short TTL, L2 is the shared distributed cache, and the database is the truth. It protects against hot keys and removes network hops, but invalidation has to reach every L1, and staleness stacks up."

How a read works. Check L1 (in-process). On a miss, check L2 (Redis). On a miss, read the database. Fill L2, then L1 on the way back. Most reads end at L1 and cost microseconds.

Why add L1. Even a fast Redis has limits: about one network round trip per read and a single node owning each key. For a hot key read 100,000 times per second, a 2-second L1 TTL on each of 50 app nodes cuts Redis traffic for that key to about 50 / 2 = 25 reads per second.

Problems it brings.

  • Invalidation fan-out. A delete in L2 does not clear L1 on other nodes. Options: a very short L1 TTL (accept bounded staleness), or broadcast invalidation messages over pub/sub (if a message is lost, data stays stale until the TTL, so always keep a TTL as a safety net).
  • Staleness stacks. If L1 is filled from L2, worst-case staleness is L1 TTL plus L2 TTL (for example 2 s + 60 s).
  • Memory duplication across nodes, and more places to look when debugging "why do I see old data on only some requests".
  • Different users see different versions for a moment, depending on the node they hit.

When to use. Only for the hot subset. Do not put everything in L1; give it a small size limit and let admission policies keep the hot items.

Remember: L1 for speed and hot keys, L2 for sharing, TTL as the safety net.

What should you not cache? Intermediate
Say this: "I cache reads that are hot, expensive and tolerant of seconds of staleness. I do not cache data that must be strongly correct at read time, low-reuse data, quickly changing write-heavy data, sensitive data in shared caches, or things cheaper to compute than to fetch."
  • Data that must be correct at decision time. An account balance used to authorise a payment, inventory at the final checkout step: a stale read can lose money. Cache for display, but read the source of truth for the decision.
  • Data with a very low hit ratio. Unique per request (search with random filters, huge scans). You pay memory and write cost and never get a hit. Test: will this key be read again before it expires or is evicted?
  • Write-heavy, quickly changing data. If it is invalidated before it is read again, the cache just adds work.
  • Personalised or sensitive data in shared caches without a correct key and access control (tokens, personal data in a CDN).
  • Very large objects that crowd out many small hot ones; cache them in a separate tier or cache a pointer.
  • Cheap-to-compute values where the lookup costs about as much as the work.

Example. A bank app shows "balance: 1,204" from cache (fine if 5 seconds old). The "transfer 1,000" action re-checks the balance with a locking read in the database inside the transaction. The cache serves speed; the database serves correctness.

Say: "I cache reads that are hot, expensive and tolerant of seconds of staleness, and I do the final correctness check against the source of truth."

Remember: cache for display and speed, not for the final authoritative decision.

Cache patterns: read and write strategies

Explain cache-aside (lazy loading). What are its strengths and weaknesses? Basic
Say this: "Cache-aside means the application owns the logic. Read: check cache, on a miss read the database and fill the cache with a TTL. Write: update the database, then delete the cache entry. It is simple and degrades gracefully when the cache is down, so it is my default."

Why it exists. You want a cache that is easy to add to existing code and that never makes the system less correct or less available than the database alone. Cache-aside (also called lazy loading) gives you that: the cache is optional and holds only what has been asked for.

  1. Read: look in the cache. If hit, return.
  2. On a miss, read the database.
  3. Put the result in the cache with a TTL, return it.
  4. Write: update the database, then delete (or update) the cache entry.
def get_product(id):
    v = cache.get("product:" + id)
    if v is not None:
        return v
    v = db.query("select * from product where id = ?", id)
    cache.set("product:" + id, v, ttl=300 + random(0, 60))
    return v

def update_product(id, data):
    db.update(id, data)          # truth first
    cache.delete("product:" + id) # then invalidate

Strengths. Simple; only requested data is cached (no wasted memory); a cache outage degrades to slower, not broken, because the app can fall back to the database; the cache can hold a different shape than the table (a joined, rendered object).

Weaknesses. The first request for each key is a miss; stale data is possible in the window between a write and the invalidation (and the race covered in the consistency section); every application instance carries the caching code (put it in a shared library); popular misses cause stampedes.

Interviewer follow-up: "Why delete rather than update on write?" See the delete-vs-update question: it avoids a write-ordering race.

Remember: read: cache, then DB, then fill. Write: DB, then delete.

What is read-through, and how does it differ from cache-aside? Intermediate

Example. In an in-process loading cache you write cache = Caffeine.newBuilder().maximumSize(10000).expireAfterWrite(5, MINUTES).build(key -> db.load(key)), then just call cache.get(key). If 100 threads ask for the same missing key at once, the loader runs once and all 100 get the result. That built-in single-flight behaviour is the practical advantage.

Why plain Redis is used cache-aside. Redis does not know how to talk to your database, so the application supplies the loading logic.

Trade-off. Read-through centralises logic and makes behaviour uniform, but couples the cache layer to the data source and is harder to customise per call site.

Remember: same data flow as cache-aside, different owner of the miss logic.

What is write-through caching, and what does it cost? Intermediate
Say this: "On a write, the app writes to the cache, which synchronously writes to the database before acknowledging. The cache is always fresh after a write, but every write pays two writes and unread data fills the cache."

How it flows. Write request, then cache layer updates its entry, then it writes to the database, then acknowledges only after the database confirms. A later read is a guaranteed hit with current data.

ProsCons
Consistent reads right after writes; no stale window from the write path; simple mental modelHigher write latency (two synchronous writes); data written but never read wastes memory (mitigate with TTL)

Failure handling. If the cache update succeeds but the database write fails, the cache holds a value that does not exist in truth. The database is the source of truth, so fail the write and remove the cache entry (or write the database first, then the cache).

When to use. Data that is read right after it is written and read often (user profile after an edit, settings). It pairs naturally with read-through: one layer handles both directions.

Not to be confused with write-behind (async). Write-through waits for the database; write-behind does not.

Remember: synchronous double write: fresh cache, slower writes.

What is write-behind (write-back), and when would you accept its risks? Senior
Say this: "Write-behind (write-back) acknowledges after the cache write and flushes to the database later, often batched. It gives very low write latency and coalesces repeated writes, but acknowledged writes can be lost if the cache node dies before flushing. I only use it for loss-tolerant high-volume data like counters."

How it works. The app writes to the cache and returns immediately. A background worker collects dirty entries and writes them to the database in batches every few seconds, or when a buffer fills.

Example of the gain. A video gets 10,000 views per second. Writing each view to the database is 10,000 writes per second. With write-behind, the cache increments an in-memory counter and flushes the total once per second: 1 database write per second instead of 10,000. That is a 10,000x reduction.

Pros. Very low write latency; repeated writes to the same key coalesce; absorbs write spikes; shields a slow database.

Cons.

  • If the cache node dies before flushing, acknowledged writes are lost. Mitigate with replication or by writing to a durable log first.
  • The database is behind, so any reader that bypasses the cache (reports, other services) sees old data.
  • Ordering and failure handling in the flusher is complex: what if the database rejects a batch?
  • Hard to debug and reason about.

Decision rule. Accept it where losing a few seconds of data is tolerable and the volume is high: view counters, likes, analytics events, last-seen timestamps. Never for payments, orders or anything with legal or financial meaning.

Remember: fast and coalescing, but durability moves into the cache.

What is refresh-ahead? Intermediate
Say this: "Refresh-ahead reloads a hot entry in the background before it expires, so readers keep getting a value with no miss latency and no stampede at expiry. It suits predictable hot keys with expensive loads."

The problem it solves. With a plain TTL of 60 seconds, the first reader after expiry pays the full load time (say 800 ms) and many concurrent readers may all miss at once. For a hot key that is a periodic latency spike and a stampede risk.

How it works. The cache stores the value and its load time. When an entry has used some fraction of its TTL (for example 75 percent) and is read again, the cache returns the current value and starts a background reload. By the time the TTL ends, a fresh value is already in place.

t=0     load, ttl=60
t=45    read: value returned, background refresh starts
t=46    refreshed, ttl reset to 60 (no reader ever missed)

Strengths. No miss latency for hot keys; no expiry stampede.

Weaknesses. Wasted work on keys that will not be read again; it needs the loader to know how to reload; if refresh fails you must keep serving the old value up to a hard limit and alert.

Variants. A scheduled job that recomputes a known set of hot keys (homepage, leaderboard), and HTTP-style stale-while-revalidate.

Remember: refresh before expiry on hot keys; serve the old value meanwhile.

What is write-around, and when is it useful? Intermediate
Say this: "Write-around sends writes straight to the database and skips the cache; an entry is cached only when it is later read. It keeps write-once, rarely-read data out of the cache."

Why it exists. If every write goes into the cache (write-through), data that is written once and rarely read (log entries, bulk imports, uploads, order history of old orders) takes up memory and evicts data that is actually hot. Write-around avoids that pollution.

How it works.

  1. Write: go to the database only.
  2. Read: normal cache-aside. The first read after a write is a miss and populates the cache.
  3. If an older copy of that key may be in the cache, you must still delete it on write; otherwise readers see stale data.

Trade-off. The first read after a write is slower (a miss), so it is a poor fit when data is read immediately after writing. Good fit when most written items are never read soon (data ingestion, audit logs).

Relation to cache-aside. Cache-aside with delete-on-write is effectively write-around plus invalidation, which is why the names get blurred in practice.

Remember: write to the DB only; let reads decide what is worth caching.

On a write, should you update the cache or delete the entry? Senior
Say this: "On a write I delete the cache entry instead of updating it. Updating from the writer has an ordering race that can leave an old value cached until TTL, and derived values are easier to delete than to recompute. Delete has its own smaller race, covered by TTL, delayed double delete, versioning or leases."

The race with updating. Two concurrent writers change the same row:

  1. Writer A sets the database value to 1.
  2. Writer B sets the database value to 2.
  3. B updates the cache to 2.
  4. A (delayed) updates the cache to 1.

Final state: the database says 2, the cache says 1, and it stays that way until the TTL. The database order was A then B, but the cache order was B then A, because the two systems are not updated atomically.

Why delete is safer. A delete does not carry a value, so it cannot write the wrong value. The next reader loads the latest row and fills the cache. Deleting twice is harmless (idempotent).

Other reasons to delete. Derived values (a rendered page, an aggregate, a joined view) are hard to recompute inside the writer, and updating a cache entry on every write wastes work if it is never read before the next write (lazy refill is cheaper).

When updating is OK. Single writer per key, or values carrying a version number and a compare-and-set that rejects older versions.

The remaining race. A slow reader can repopulate with an old value right after the delete (see the stale-race question). Mitigations: short TTL, delayed double delete, versioned values, leases.

Remember: invalidate, do not update, unless you have versions.

Eviction, expiry and invalidation

What are LRU, LFU, FIFO and TTL, and how do you choose an eviction policy? Basic
Say this: "Eviction decides what to drop when the cache is full: LRU drops the least recently used, LFU the least frequently used. TTL is separate: it expires entries by age regardless of space. In practice I use LRU or a modern hybrid like TinyLFU, plus a TTL on every key."

Why eviction exists. Memory is finite and the dataset is larger than the cache. When a new entry arrives and the cache is full, something must go. A good policy keeps the items most likely to be read again.

PolicyEvictsGood whenWeak when
LRU (least recently used)The entry unused for the longest timeRecent access predicts near-future access (most workloads)A big one-time scan flushes the hot set
LFU (least frequently used)The entry with the fewest accessesStable popularity (a hot catalogue)Old popular items linger; needs frequency aging
FIFOThe oldest insertedSimple, rarely bestIgnores usage
RandomA random entryVery cheap approximationNo intelligence
TTLAnything past its time limitBounding stalenessDoes not manage size alone

LRU example. Capacity 3. Access A, B, C (cache: A B C). Access A again (A becomes most recent: B C A). Insert D: evict B, the least recently used. Result: C A D.

The scan problem. A crawler reads 1 million items once each. With LRU they all enter and push out your genuinely hot items. A policy with an admission filter (TinyLFU, used by W-TinyLFU in Caffeine) only admits a new item if it looks more valuable than the one it would evict, so one-hit scans do not pollute.

Practical advice. Large caches often use sampled (approximate) LRU or LFU, because exact LRU needs a global linked list updated on every read, which is costly. Redis, for example, samples a few keys and evicts the best candidate among them. Always combine eviction with a TTL.

Trap: a very common coding question: implement an LRU cache. Hash map plus doubly linked list gives O(1) get and put.

Remember: eviction handles space, TTL handles age; use both.

How do you choose a TTL? Intermediate
Say this: "TTL is the upper bound on staleness and the safety net when explicit invalidation fails. I choose it from the business tolerance for stale data, add jitter, and keep it short for security-sensitive and negative entries."

The trade-off. A longer TTL means a higher hit ratio and less database load, but data can be wrong for longer. A shorter TTL is safer but loads the database more. The right number comes from the question "how stale can this data be before a user or the business is harmed?" not from habit.

DataTypical TTLWhy
Static or reference (country list)Hours to daysAlmost never changes
Product details1 to 10 minutesChanges occasionally; a short delay is OK
Counts, feeds, search resultsSeconds to a minuteChanges constantly, freshness visible
Per-user permissionsSeconds to a minuteStale permissions are a security problem
Negative results ("not found")Seconds to a minuteThe thing may be created right after

Jitter. If 100,000 keys are loaded in the same minute with TTL 600 s, they all expire in the same second and cause an avalanche. Use TTL = base x random(0.9, 1.1), which spreads expiry over a window.

With explicit invalidation. Even if you delete on write, keep a TTL as the backstop for the case where the delete is lost. In that setup the TTL can be longer, because it covers only failures.

Sizing the effect. If a key is read 10 times per second and the TTL is 60 s, one load serves 600 reads (hit ratio about 99.8 percent). With TTL 5 s it serves 50 reads (98 percent). The database cost is 12x higher for the shorter TTL, which is the price of 12x fresher data.

Remember: TTL = acceptable staleness; add jitter; keep it as a backstop.

What are the strategies for cache invalidation? Why is it called one of the hard problems? Intermediate
Say this: "Options: TTL only, delete on write, event-driven or CDC invalidation, versioned keys, tag-based purge. It is hard because one write can affect many derived keys, writes race with readers, multiple cache layers hold copies and a missed invalidation is silent. I combine explicit invalidation with a TTL backstop."
  1. TTL only: do nothing on writes; accept staleness up to the TTL. Simplest and most robust.
  2. Delete on write: the writer deletes the key after committing. Fresh data soon after, but you must know every key affected.
  3. Event-driven invalidation: publish change events (from the application, or from the database change log via change data capture, CDC) and a consumer deletes or updates keys. Decouples writers from caches and covers writes from any source.
  4. Versioned keys: put a version in the key (user:42:v7); bumping the version makes old entries unreachable, and they age out through eviction. No delete, no race.
  5. Tag or group invalidation: attach tags (all pages that include product 42) so one call purges the group; CDNs call this "surrogate keys".
  6. Purge API or soft purge: at CDNs, mark content stale and serve it while refetching.

Why it is hard, with an example. Product 42's price changes. Which cached values include that price? The product page, the category listing page 1 to 20, search results, a "recommended for you" fragment, and a cart total. A single database row changed, but ten cache keys are now wrong, and they live in a CDN, in Redis and in three apps' local caches. You must find them all, delete them in an order that does not allow a stale refill, and handle the case where one delete fails silently.

Pragmatic answer. Design keys so affected keys are easy to enumerate (or use versions or tags), always set a TTL, and invalidate by event rather than from each code path.

Remember: explicit invalidation for freshness plus TTL for safety.

Why use change data capture (CDC) for cache invalidation instead of invalidating in application code? Senior
Say this: "CDC reads the database commit log, so every committed change, from any writer, becomes an ordered event that a consumer uses to delete the right cache keys, with retries. It fixes the missed-delete and failed-delete gaps of application-level invalidation."

The problem with application-level invalidation. Code that does "update DB then delete key" misses: a batch job that updates rows directly, an admin running manual SQL, another service writing the same table, a code path someone forgot, and the case where the DB commit succeeds but the process crashes before the delete.

What CDC (change data capture) does. A tool reads the database's own transaction log (binlog, WAL, redo log) and publishes a record for every committed row change to a message bus. A consumer maps "row product:42 changed" to the cache keys affected and deletes or refreshes them.

DB commit -> transaction log -> CDC reader -> Kafka topic
          -> invalidation consumer -> DEL product:42, DEL listing:books:p1

Benefits.

  • Catches every writer, because the log is the single record of truth.
  • Events are in commit order, which avoids out-of-order invalidation.
  • Reliable: the event is retried until the consumer succeeds, so a transient cache outage does not leave stale data forever (deletes are idempotent).
  • Decouples cache logic from the write path.

Costs. More infrastructure to run, a small delay (typically sub-second to a few seconds), and the consumer must contain the mapping from rows to cache keys. Facebook's published memcache design uses a similar idea: a daemon reads the database commit log and issues deletes.

Alternative. The transactional outbox: write an invalidation event row in the same transaction as the data, and a relay publishes it. Same reliability without reading the log, but only for writers that use the outbox.

Remember: invalidate from the log, not from each code path.

How do you design good cache keys? Intermediate
Say this: "A key must include everything that changes the result: entity id, tenant, locale, version, relevant parameters, role if output depends on it. Keep it consistent, normalised and short, include a schema version, and bound its cardinality."
  • Include every dimension that changes the value. A missing tenant in the key is a data-leak bug: tenant A reads tenant B's cached object. Same for locale (a French page served to an English user) and for user role.
  • Structured, readable format: app:entity:id:variant, for example shop:product:42:en. Easier to debug and to delete by pattern in the right tooling.
  • Normalise inputs. ?a=1&b=2 and ?b=2&a=1 are the same request; sort parameters, lowercase, trim, so equal requests share one entry. Otherwise hit ratio collapses.
  • Keep keys short. In a cache with hundreds of millions of keys, a 100-byte key versus a 40-byte key is gigabytes of memory.
  • Include a schema or code version when the serialised format changes (v3: prefix), so a rolling deploy does not read objects written in an old shape.
  • Avoid unbounded cardinality. A key per free-text search string fills the cache with one-hit entries that evict useful data.
  • Never put secrets or personal data in the key itself since keys show up in logs and monitoring.

Example of a bad key and its fix. search:{query}:{timestamp} never hits (the timestamp differs every time). Fix: search:v2:{tenant}:{normalised-query}:{page} with a short TTL.

Remember: key = everything that affects the answer, nothing that does not.

What is cache warming, and when do you need it? Intermediate
Say this: "A cold cache sends all traffic to the database. Warming pre-loads the hot keys before live traffic, using a top-N list, a background loader, mirrored reads or gradual traffic ramp, rate-limited so it does not overload the database itself."

When you need it. A new cache cluster or node, a restart or failover (cache comes back empty), a planned high-traffic event (a sale at noon), or a deploy that changes the key format (all old keys become misses).

Why it matters, with numbers. A database sized for a 95 percent hit ratio at 20,000 reads per second sees 1,000 qps. With a cold cache it sees up to 20,000 qps, 20 times more, exactly when the system is least healthy.

Methods.

  • Replay a hot-key list from access logs, or from the previous cache's statistics.
  • Background loader that queries the most popular entities (top 10,000 products) and fills them, rate limited.
  • Shadow or mirror reads: send a copy of live reads to the new cache so it fills with real traffic before it takes responsibility.
  • Gradual traffic ramp onto a new node, or populate new keys while the old format still serves.
  • Persistence reload: restore from a snapshot after a restart (for caches that support it).

Without warming, rely on graceful degradation: request coalescing, per-database concurrency limits, and load shedding so a cold start slows the system rather than killing the database.

Remember: warm before taking traffic, and rate-limit the warmer.

Cache failure modes: stampede, hot keys, penetration, avalanche

What is a cache stampede (thundering herd) and how do you prevent it? Intermediate
Say this: "A stampede is when a popular key expires and thousands of requests all miss and hit the database with the same query at once. I coalesce misses so one request reloads, serve stale while refreshing, add TTL jitter, refresh hot keys ahead of time, and cap database concurrency."

What happens. Key home:feed takes 800 ms to compute and is read 5,000 times per second. At 12:00:00 it expires. During the next 800 ms, about 4,000 requests all see a miss and all start the 800 ms query. The database suddenly runs 4,000 identical queries, slows to several seconds, so the refill takes even longer, which makes even more requests pile up. A feedback loop that can take the database down.

DefenceHow it works
Request coalescing (single flight)Within a node, the first miss runs the loader; others for the same key wait for its result. Built into loading caches.
Distributed lock or leaseThe first requester sets a short-lived lock key (SET NX with a TTL); others wait briefly and re-read, or serve stale. The lock needs a TTL so a crash does not block forever.
Serve stale while revalidatingKeep a soft TTL (when to refresh) and a hard TTL (when to drop). After the soft TTL, one caller refreshes while others get the old value.
TTL jitterRandomise expiry so keys do not expire together.
Refresh-ahead / background recomputeHot keys never expire in the foreground.
Probabilistic early expirationEach reader has a small, growing chance of refreshing before the TTL, higher when the load is slow. Spreads refreshes over time with no lock.

Why local coalescing is not enough alone. With 100 app nodes, each node's single flight still sends 100 queries. Add a distributed lock or serve-stale for the hottest keys, and a database-side concurrency limit as the last line of defence.

Say: "Coalesce misses, serve stale for a bit, add jitter, and cap database concurrency so a stampede cannot take the database down."

Remember: one key, many concurrent misses: make only one of them do the work.

What is a hot key problem, and how do you handle it? Senior
Say this: "A hot key is one key with a huge share of traffic. In a sharded cache it lives on one node, which saturates while others idle, and adding nodes does not help. The fixes are a short-TTL local cache in every app node, replicating the key under several names, detecting hot keys automatically, and edge caching."

Why it happens. Sharded caches decide the node by hashing the key. All requests for product:777 (the flash-sale item, the celebrity's profile) hash to the same node. If that key gets 300,000 reads per second and a node handles perhaps 100,000, the node is overloaded while the other nine are bored. A tenfold bigger cluster still has exactly one owner for that key.

Fixes, cheapest first.

  • Local (L1) cache with a short TTL on every app node for the hot key. Reads never leave the app node. 50 nodes with a 2 s TTL turn 300,000 reads per second into about 25 per second at the cache. Most effective and cheapest.
  • Replicate the key under several names (hot:777#1 to hot:777#8), read a random one, write or invalidate all of them. The 8 copies land on different nodes, spreading load 8 ways.
  • Detect hot keys automatically (client-side counters, proxy sampling, or server statistics) and promote them to L1 or replication dynamically, so you do not need to predict them.
  • Edge caching by a CDN for public content.
  • Split the value: a heavily updated counter can be sharded into many sub-counters (likes:777:0..15) and summed on read.
  • Rate limit or coalesce requests for that key.

Interviewer follow-up: "What about writes to a hot key?" Writes cannot be served locally: batch them (write-behind with coalescing) or use sub-counters.

Remember: hot key problems are about a single owner, so replicate or push the key to the clients.

What is cache penetration, and how do you defend against it? Intermediate
Say this: "Penetration is when requests ask for keys that exist nowhere, so every one misses the cache and then the database, and the cache gives no protection. I defend with negative caching, a Bloom filter in front, input validation and rate limiting."

What happens. A normal miss gets filled, so the next read hits. But a request for user id -1, or a random id an attacker scans, finds nothing in the database either, so there is nothing to cache. Every repeat goes all the way to the database. An attacker (or a bug) can send 50,000 such requests per second at almost no cost and your database absorbs all of it.

  • Negative caching: cache the "not found" result with a short TTL (30 to 60 seconds). Repeated lookups of the same missing key now hit the cache.
  • Bloom filter in front: a compact probabilistic set of all valid ids. If it says "definitely not present", return immediately without touching cache or database. It can give false positives (a few wasted lookups) but never false negatives. It must be updated as new ids are created. This also helps against random-id scans where negative caching would just fill memory with one-hit entries.
  • Input validation (id format and range), authentication, and per-client rate limiting.
  • Monitoring: a high cache miss rate combined with a high database "no rows" rate is the attack signature.

Example. Valid product ids are 1 to 10 million. A Bloom filter of 10 million ids at 1 percent false positive rate takes roughly 12 MB (about 10 bits per id). A request for id 99,999,999 is rejected in microseconds, with no cache or database call.

Compare: penetration = keys that never exist; stampede = one hot key that does exist but expired; avalanche = many keys or the whole cache gone.

Remember: if the miss cannot be cached as a hit, cache the miss or filter it out.

What is negative caching and what are its risks? Intermediate
Say this: "Negative caching stores the fact that something does not exist, so repeated lookups skip the source. The risk is that the thing gets created right after and the cache still says not found until the TTL ends, so I use short TTLs, delete the negative entry on creation, and never cache transient errors as not found."

Where you already see it. DNS caches NXDOMAIN answers; CDNs cache 404s; an app caches a null for a missing user id.

Why use it. It stops repeated lookups for missing items from reaching the database (the penetration defence).

The risk, with an example. A user visits a page for username "alice", which does not exist yet, so user:alice -> NOT_FOUND is cached for 5 minutes. Alice signs up one minute later. For the next 4 minutes, every lookup says she does not exist, so she cannot log in.

  • Short TTL for negatives (seconds to a minute), shorter than for positives.
  • Delete the negative entry when the entity is created (part of the create path or event).
  • Use a distinct sentinel so an intentionally empty value (a user with no orders) is not confused with a miss, and so a cached "not found" is not mistaken for a real object.
  • Never negatively cache transient errors (timeout, a 500, a connection failure) as "not found". That turns a 10-second outage into a multi-minute wrong answer.

Remember: cache real absence briefly, never cache errors as absence.

What is a cache avalanche and how do you prevent it? Intermediate
Say this: "An avalanche is when a large part of the cache disappears at once, because many keys expire together or the cache cluster dies, and the database takes the whole read load. I use TTL jitter, a highly available cache, multi-level caching, database protection and warm-up. Stampede is one hot key; avalanche is many keys or the whole cache."

Two causes.

  1. Mass expiry. A batch loaded 500,000 keys at 03:00 with the same 1-hour TTL, so at 04:00 they all vanish in the same second.
  2. Cache outage. The cache cluster crashes or restarts empty; the hit ratio drops from 97 percent to 0, and the database sees about 33x its normal read load.

Defences.

  • Jitter on TTLs so expiry spreads over a window.
  • High availability for the cache: replicas, multiple zones, consistent hashing so losing one node loses only its share of keys.
  • Multi-level caching: a local cache absorbs some load during an outage.
  • Protect the database: concurrency limits, circuit breakers, load shedding and request coalescing, so it degrades rather than collapses.
  • Warm the cache before returning a replacement node to service.
  • Serve stale data when the loader is failing.
  • Staggered rollout and refresh-ahead for known big batches.

What should happen when the cache is down? Fail open or fail closed? Senior
Say this: "I decide per use case before the incident. A pure read cache fails open to the database, protected by a concurrency limit, circuit breaker and short cache timeouts. A cache that holds real state (sessions, counters, locks) has no fallback and needs replication and an explicit degraded mode."
  • Pure read cache: fail open. Go to the database, but protect it with a concurrency limit, a circuit breaker and load shedding. Use short timeouts on the cache call (a few ms to tens of ms), so a slow cache does not become slower than no cache at all.
  • Cache that carries real state (sessions, rate-limit counters, locks): there is no database fallback. Either replicate and accept degraded behaviour (rate limiting often fails open with a coarse local limit; security checks usually fail closed), or keep that data in a durable store.
  • Do not retry aggressively against a struggling cache; use jittered backoff and a circuit breaker.
  • Test the cold-cache case. Many databases are sized assuming a 95 percent hit ratio and cannot survive 0 percent. Run game days where the cache is emptied.

Fail-open vs fail-closed examples.

UseCache down behaviour

Session lookupFail closed: cannot authenticate, ask the user to log in again
Distributed lockFail closed for correctness; skip work rather than risk double execution
Trap: saying "the cache is just an optimisation" while the system silently depends on it for capacity. If the database cannot serve the miss load, the cache is effectively mandatory and must be treated as a tier-one dependency.

Remember: classify caches as disposable or stateful before they fail.

What goes wrong with very large cache values or huge collections? Intermediate
Say this: "Very large values or huge collections are slow to transfer, can block a single-threaded cache server while read or deleted, crowd out many small hot keys, and make a miss expensive. Split them, compress, cache only the needed fields, or store blobs elsewhere and cache a pointer."

What goes wrong.

  • Transfer time and bandwidth. A 5 MB value fetched 1,000 times per second is 5 GB per second of network traffic, enough to saturate the cache node's link.
  • Blocking. In a single-threaded server like Redis, one command that reads, serialises or deletes a huge value (or iterates a huge list or set) stalls every other client for its duration. Deleting a multi-million-element collection can freeze the node for a noticeable time.
  • Eviction pressure. One big entry may evict thousands of small hot ones.
  • Expensive miss. When it expires, every reader reloads a big object, which is a stampede with heavy payload.
  • Uneven shards. A node holding a few giant keys is overloaded compared with peers.

Fixes.

  • Break it into smaller keys or pages (a list of 1 million items stored as 1,000 chunks).
  • Cache only the fields you need (a hash with selective reads rather than a whole serialised object).
  • Compress (watch CPU cost).
  • Store large blobs in object storage and cache only the pointer or metadata.
  • Enforce a maximum value size at the client and monitor the biggest keys regularly.
  • Use incremental or asynchronous deletion where the store supports it.

Remember: keep cache values small and bounded.

Consistency between cache and database

Describe a race condition in cache-aside that leaves stale data in the cache. How do you reduce it? Senior
Say this: "A slow reader can read the old row, a writer then updates the database and deletes the key, and then the reader writes its old value into the cache. The cache stays stale until TTL. I reduce it with TTL, delayed double delete, versioned values, leases or CDC-driven invalidation."

The interleaving, step by step.

  1. Reader R misses the cache and reads the old row (v1) from the database.
  2. Writer W updates the row to v2 and deletes the cache key.
  3. R, which was slow (a GC pause, a slow network), now writes v1 into the cache.
  4. The cache holds v1 although the database holds v2, until the TTL expires.

It is rare (the reader must be delayed between its read and its fill by longer than the writer takes) but real at scale, where rare events happen every day. Mitigations, from simplest:

  • TTL as a backstop, the minimum defence: the stale value dies on its own.
  • Delayed double delete: delete after the write, then delete again after a short delay (longer than a typical read-and-fill time, for example 500 ms to 1 s) to remove a late stale fill. Cheap but heuristic.
  • Versioned values: store a version or timestamp with the data and use a compare-and-set that refuses to overwrite a newer version.
  • Leases (from Facebook's memcache paper): a miss returns a token; a delete invalidates outstanding tokens, so R's late set with an old token is rejected.
  • CDC-driven invalidation from the commit log, which orders events properly and delivers a delete after the commit of v2 whatever the readers did.

Remember: the problem is a late fill after a delete; version or lease the fill.

In a write, do you update the database first or the cache first? What if one step fails? Senior
Say this: "Write the database first, then delete the cache entry. If the delete fails, the cache is stale only until TTL, and I retry it through a queue or outbox. Other orders are worse. Two systems cannot be made atomic cheaply, so I design for bounded inconsistency."

Compare all four orders.

OrderWhat can go wrongVerdict
Update cache, then DBDB write fails; cache holds data that never existedBad
Delete cache, then update DBA reader loads the old value between the two steps and re-caches it, stale until TTLBad (and common)
Update DB, then update cacheConcurrent writers can leave the older value in the cacheRisky
Update DB, then delete cacheIf the delete fails, stale until TTL; tiny race with a slow readerBest standard choice

Handling a failed delete. Put the delete on a retry queue, or write an invalidation record to an outbox table in the same database transaction as the data. A relay process reads the outbox and issues the deletes, retrying until success. This gives reliable at-least-once invalidation; deletes are idempotent, so duplicates are harmless.

BEGIN;
  UPDATE product SET price = 99 WHERE id = 42;
  INSERT INTO outbox(event) VALUES ('invalidate product:42');
COMMIT;
-- relay: read outbox, DEL product:42, mark done (retry on failure)

Why not a distributed transaction. Two-phase commit between a database and a cache is slow, complex and the cache usually does not support it. Bounded staleness plus retries is cheaper and good enough for caches.

What you can promise. "After a successful write, the cache is stale for at most the time to retry the delete plus the TTL."

Remember: DB first, delete second, retry reliably, TTL as the net.

A user updates their profile and then sees the old one. How do you fix read-your-writes with a cache and replicas? Senior
Say this: "A user who just updated their profile must see the new one. Delete the key on write, and for a short window after the write route that user's reads to the primary (not a lagging replica), or return the new object in the write response, or use write-through for that entity. Other users can see stale data briefly."

Why it breaks. There are three places a stale copy can come from after a write:

  1. A stale cache entry that was not invalidated yet.
  2. A read replica that has not applied the write yet (replication lag, often ms to seconds). Worse: after you delete the cache key, the next read goes to the lagging replica, reads the old row, and puts the old value back in the cache for everyone.
  3. A different region's cache that has not received the invalidation.

Options.

  • Delete the key on write so the next read reloads. To avoid the lagging-replica refill, for a short window after a write (say 5 to 10 seconds, tracked with a cookie or a last-write timestamp in the session) route that user's reads to the primary.
  • Write-through for that entity so the cache already holds the new value.
  • Return the new object in the write response and let the client display it instead of re-fetching immediately.
  • Versioned reads: the write returns version N; the client sends "at least version N" and the server refuses to answer from anything older (waits or goes to the primary).

Scope. Only the writer needs this guarantee. Other users seeing the old profile for a few seconds is usually acceptable. Solving read-your-writes for one user is much cheaper than global strong consistency.

Remember: give the writer a consistent view; let others be eventually consistent.

How do you explain the consistency you offer when a cache sits in front of a database? Intermediate
Say this: "With a cache in front of a database I offer bounded staleness: typically milliseconds to seconds after a write when invalidation works, and at worst the TTL when it fails. That is eventual consistency. Flows that need strong consistency bypass the cache."

How to say it in an interview. Give a concrete bound: "A product price change appears everywhere within about 1 second normally, and never later than 5 minutes, because every entry has a 5 minute TTL." Interviewers like numbers and a clear failure bound more than the words "eventually consistent".

Strong consistency flows. A payment check, a stock decrement, a permission check for a sensitive action: bypass the cache and read or write the source of truth, ideally in a transaction or with a conditional update (UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0).

Framing. Present it as a deliberate trade: freshness against latency, load and availability. Cache for display and discovery paths; go to the source of truth at decision points.

Remember: state the staleness bound as a number, and name the flows that bypass the cache.

How do caches behave across multiple regions? Senior
Say this: "Each region has its own cache cluster, because a cross-region round trip would defeat the cache. Writes must invalidate entries in other regions, usually via replicated invalidation events or the database replication stream, with TTL as a bound. Pinning users to a home region reduces cross-region traffic."

Why not one global cache. A cache hit should be about 1 ms. A call from Singapore to a Virginia cache costs well over 150 ms, which is as slow as or slower than the data you were trying to avoid fetching. So every region gets its own cache next to its apps.

The new problem. A write in region A updates the database and deletes the key in A's cache. Region B's cache still holds the old value. Options:

  • Replicate invalidation events over a message bus (or reuse the database replication stream). When region B sees the change, it deletes its key. This also ensures B deletes only after its local replica has the new data, so B does not refill from a lagging replica.
  • Accept TTL-bounded staleness where that is fine (catalogue data).
  • Home region per user or tenant: most reads and writes of a user happen in one region, so there is little cross-region inconsistency to manage.
  • Global database with synchronous replication when you need strong global consistency, at the price of write latency.

Pitfall. Refilling a remote cache from a lagging replica right after an invalidation can re-cache stale data. Order matters: the invalidation should reach B after, or together with, the data.

Failure case. If the inter-region link is cut, invalidations are queued; TTLs bound how stale the far region can get meanwhile.

Remember: local cache per region, replicated invalidation, TTL bound.

Sizing, hit ratio and technology choice

What is the hit ratio, and how does it change your average latency and database load? Basic
Say this: "Hit ratio is hits divided by total lookups. Average latency is h times cache time plus (1 minus h) times cache plus database time, and database load is (1 minus h) times reads. Think in miss ratio: going from 95 to 99 percent cuts database load five times."

Formulas. Hit ratio h = hits / (hits + misses). Average latency = h x t_cache + (1 - h) x (t_cache + t_db), because a miss still pays the cache lookup first. Database load = (1 - h) x total reads.

Hit ratioAvg latency (1 ms cache, 40 ms db)DB load at 50,000 reads/s
80%9 ms10,000/s
90%5 ms5,000/s
95%3 ms2,500/s
99%1.4 ms500/s

The insight. Latency barely changes between 95 and 99 percent (3 ms to 1.4 ms), but database load drops 5x (2,500 to 500 per second). That is why you reason about the miss ratio when protecting the database: 1 percent misses versus 5 percent is a 5x difference in what the database must survive.

Other things to remember.

  • A miss is slower than having no cache at all, by exactly one lookup.
  • Tail latency (p99) is dominated by misses, because they are 40x slower than hits. If 5 percent of requests miss, p95 is already a miss.
  • Hit ratio has diminishing returns as the cache grows; the long tail of rarely read items costs a lot of memory for little gain.
  • Measure it per key type (products, sessions) rather than one overall number, and watch the eviction rate beside it.

Remember: database load = miss ratio x reads; focus on the misses.

How do you size a cache? Walk through an estimate. Senior
Say this: "Size for the hot working set, not the whole dataset. Multiply the hot item count by entry size plus overhead, add headroom and replicas, then check throughput and network separately, and validate with the hit-ratio curve."

Worked estimate.

  1. Working set. 100 million products, but access is skewed so that 5 percent of items take about 90 percent of reads. Hot set = 5 million items.
  2. Entry size. 2 KB value plus about 100 bytes of key and metadata = about 2.2 KB. Real overhead depends on the store; add 30 to 50 percent for fragmentation and metadata to be safe.
  3. Memory. 5 million x 2.2 KB = 11 GB. With the overhead allowance and headroom, plan for about 16 to 20 GB. Add a replica per shard for availability (doubling the total memory).
  4. Throughput. If peak is 100,000 cache operations per second and a node safely handles about 50,000 to 100,000 simple operations per second (hedge: it depends on payload size and hardware), you need several nodes for throughput even if memory fits on one.
  5. Network. 100,000 ops/s x 2 KB = 200 MB/s, about 1.6 Gbit/s. Check NICs on the cache nodes and the app side can carry it.
  6. Validate. Track hit ratio versus cache size. Many evictions with a falling hit ratio means it is too small; a flat hit ratio when you add memory means it is already big enough.

Why check three limits. A cache can run out of memory (capacity), CPU (operations per second) or network (bandwidth). The binding one decides the node count. In the example, memory says 1 to 2 nodes, throughput says 2 or more, so throughput decides.

Sanity check on the skew assumption. If access is closer to uniform, the working set is the whole dataset and you cannot get a high hit ratio from a small cache. Check real access logs rather than assuming a power law.

Say: "I size for the hot working set, then check throughput and network separately, and verify with the hit-ratio curve instead of guessing."

Remember: working set x entry size, then memory, ops and bandwidth.

Redis vs Memcached at design level: how do you choose? Intermediate
Say this: "Redis by default, because it has richer data types, optional persistence, replication, failover and cluster mode. Memcached for plain, large, multi-core, ephemeral object caching where simplicity matters. Either way a cache of copies is disposable."
MemcachedRedis

What the differences mean in practice. If you need a leaderboard (sorted set), a rate limiter (atomic increment with expiry) or a lock, Redis does it natively; with Memcached you would build it yourself. If you only need to cache serialised objects on a machine with 32 cores, Memcached's multi-threading uses the hardware more simply, while Redis scales by running more shard processes. Decision rule. Features, HA or data structures: Redis (or a compatible managed service). Plain, large, ephemeral key-value caching at maximum simplicity: Memcached. How is a distributed cache spread over many nodes, and what happens when you add or remove one? Intermediate
Say this: "Naive hash mod N remaps almost every key when N changes, which makes everything miss at once. Consistent hashing, or fixed hash slots as in Redis Cluster, moves only about 1/N of the keys when a node is added or removed."

The naive approach and its flaw. Pick the node as hash(key) mod N. With 4 nodes, key 10 goes to node 2 (10 mod 4). Add a fifth node: 10 mod 5 = 0, a different node. Almost all keys now map elsewhere (roughly N/(N+1), here 80 percent), so nearly everything misses together, an instant self-inflicted avalanche.

Consistent hashing. Place nodes at points on a ring (the hash space). A key goes to the first node clockwise from its hash. Add a node: it takes over only the keys between it and its predecessor, about 1/N of all keys. Remove a node: only its keys move to the next node. Virtual nodes (each physical node appears at many ring points) even out the load.

Redis Cluster uses 16,384 fixed hash slots assigned to nodes; adding a node means moving some slots (and their keys) to it. Same effect, simpler bookkeeping.

Operational advice. Resize during low traffic, warm the new node, and expect a temporary dip in hit ratio while keys migrate. Moving slots gradually keeps the effect small.

Remember: change the node count without reshuffling everything.

What design choices about serialisation and value shape affect a cache? Intermediate
Say this: "Value format and shape change cost and safety: JSON is readable but bulky, binary formats are compact, compress large values, version the key or value so a rolling deploy can share the cache, choose entry granularity deliberately, and cache plain data, not ORM entities."
  • Format. JSON is readable and debuggable but bulky and slower to parse. Binary formats (protobuf, MessagePack, Avro) are smaller and faster. A 2 KB JSON object may be 600 bytes in protobuf; across 100 million entries that is a large memory saving. Compress large values, remembering CPU cost.
  • Schema evolution during deploys. During a rolling deploy old and new code share the cache. If v2 code adds a field and v1 code reads it (or vice versa), deserialisation can fail. Include a version in the key or value, and make readers tolerate unknown fields. Otherwise each deploy produces a burst of errors or poisoned entries.
  • Granularity. Cache the object, a page of results, or the rendered fragment? Bigger entries save more work per hit but are invalidated more often and hold more redundant data (the same product inside many listings). Smaller entries reuse better but need more lookups, so use batch gets.
  • Do not cache ORM entities with lazy references. They drag session state, proxies and lazily loaded relations. Cache plain data objects (DTOs).
  • Never use language-native serialisation across services or for untrusted data (Java serialisation has a history of security problems and breaks on class changes).

Remember: small, versioned, plain data objects.

Scenarios and real-life problems

Scenario: right after a Redis restart the database CPU hits 100 percent and the site is slow for 20 minutes. What happened and what do you do? Senior
Say this: "The cache came back empty, so the hit ratio fell from about 97 percent to near zero and the database saw roughly 30 times its normal read load, plus stampedes on popular keys. Shed load and warm hot keys first, then fix the architecture."

Diagnosis with numbers. Before: 97 percent hits means the database saw 3 percent of reads, say 600 per second out of 20,000. After the restart: 0 percent hits, so 20,000 per second, about 33x more. The database had never been sized for that, so latency rose, requests timed out, and retries made it worse. Refilling is slow because the database is slow, which is why it took 20 minutes.

Immediate actions.

  • Shed load: rate limit, serve degraded or stale pages, disable expensive features (recommendations, personalisation).
  • Cap database concurrency and enable request coalescing so identical queries run once.
  • Warm the hottest keys first (top-N list) so the biggest slice of traffic hits quickly.
  • Ramp traffic back gradually if you can.

Long-term fixes.

  • Replicas with automatic failover instead of a single node, so a restart does not empty the cache.
  • Persistence (snapshot reload) if restart time is the issue.
  • A warm-up routine and multi-level caching.
  • Jittered TTLs.
  • A game-day that runs with an empty cache to learn what the database can really handle, and to find out how long recovery takes.

Remember: a cold cache is an outage for a database sized on the hit ratio.

Scenario: a flash sale for one product, the product page and stock count are read 200,000 times a second. How do you cope? Senior
Say this: "Cache the public page at the CDN with a few seconds TTL and stale-while-revalidate. Use a short-TTL L1 cache for the hot product record. Show stock slightly stale, but decrement stock in the source of truth with an atomic conditional update. Pre-warm and pre-scale, and protect checkout with rate limiting or a waiting room."

Break it by component. 200,000 reads per second for one product is a hot key problem plus a correctness problem on stock.

  • Page body (public). Serve from the CDN with a TTL of a few seconds plus stale-while-revalidate. The origin sees about one request per edge location per few seconds instead of 200,000 per second.
  • Product record (hot key). An L1 cache in each app node with a 1 to 5 second TTL, so the distributed cache sees a trickle and no single Redis node is overloaded.
  • Stock display. Can be slightly stale ("only a few left"), cached separately with a short TTL, so the page does not depend on exact numbers.
  • Stock decrement (correctness). Goes to the source of truth with an atomic conditional update: UPDATE stock SET qty = qty - 1 WHERE sku = ? AND qty > 0, checking the affected-row count. For extreme contention, put purchase attempts in a queue to serialise them for that sku, or pre-allocate stock tokens.
  • Capacity. Pre-warm the cache before the sale starts and pre-scale the app tier on a schedule, instead of waiting for autoscaling lag.
  • Protection. Rate limiting, bot protection and a waiting-room queue in front of checkout, so only a manageable number of buyers reach the database.

The principle. Separate what can be stale (display) from what cannot (the decrement), and put the cache and CDN in front of everything on the first side.

Remember: cache display, protect the decision.

Scenario: an admin removes a user's access, but the user keeps access for 10 minutes. Why, and how do you fix it? Intermediate
Say this: "Permissions were cached, or baked into a long-lived token, with a 10 minute TTL and nothing invalidated them on change. Delete the key on change, use short TTLs or short-lived tokens for security data, check a revocation list, and ask the source of truth for sensitive actions."

Why it happens. For speed, the auth layer caches "user 42 may access resource R" for 10 minutes, or embeds roles in a JWT valid for an hour. The admin's change updates the database only. Until the cache entry or token expires, the old permission is used.

Fixes, layered.

  • Event-driven invalidation: on a permission change, publish an event; a consumer deletes perm:user:42 (and any L1 copies).
  • Short TTL for security data (seconds to a minute), accepting more database load for that small dataset.
  • Revocation list checked on each request: a small set of revoked users or token ids, cheap to hold in memory and update by broadcast.
  • Short-lived access tokens (5 to 15 minutes) with server-side refresh, so a change takes effect at the next refresh.
  • Separate "show" from "authorise". The UI can render from cache; the sensitive action (delete data, export, payment) asks the source of truth or a fresh cache.

Say it as a requirement. Choose the maximum acceptable delay for revocation (for example 30 seconds) from the security requirement, then pick TTL and mechanism to meet it. This is the case where a bounded-staleness answer must be tied explicitly to a security rule.

Remember: permissions need short, event-invalidated caching, and sensitive actions recheck.

Scenario: every deployment produces a short burst of 502 and 504 errors, though the new version is healthy. What do you check? Intermediate
Say this: "A deploy-time burst of 502 and 504 almost always means requests are still routed to instances that are shutting down, or to new instances that are not ready. I check signal handling and draining, balancer deregistration timing, readiness strength, max unavailable, keep-alive timeouts and the grace period."

Checklist, with the reason each one causes errors.

  1. Does the app handle SIGTERM and drain, or die at once? Instant exit drops in-flight requests (502 or connection reset).
  2. Deregistration delay versus drain time. The balancer keeps sending traffic for several seconds after the instance goes unready. The app should wait a few seconds after going unready, before closing its listener.
  3. Are new pods ready too early? A weak readiness probe lets cold instances (cold JIT, empty caches) take traffic and time out (504).
  4. Is max unavailable too high? Capacity dips below the peak load and the remaining nodes overload.
  5. Keep-alive mismatch. If the balancer's idle timeout is longer than the app's, the app closes an idle connection just as the balancer reuses it, producing a 502. Rule: the app's idle timeout must be longer than the balancer's.
  6. Grace period shorter than the slowest request. The platform force-kills requests that were still running.

Fixing these usually removes the errors; client-side retries on idempotent requests cover the remainder. Verify by deploying under a steady load test and watching the error count.

Remember: unready, wait, drain, then exit; and make the ready signal honest.

Scenario: traffic doubles in two minutes during a TV ad, and autoscaling adds nodes after the site is already failing. What would you change? Senior
Say this: "For a known event, schedule capacity ahead. For unknown spikes, add headroom, scale faster on a leading signal like requests per second, and cover the gap with load shedding, rate limits, cached fallbacks and a CDN. Also check that downstream limits will hold when the app tier doubles."

Why autoscaling failed here. Traffic doubled in 2 minutes, but the metric lag (about 1 minute), decision time and instance boot and warm-up (a few minutes) are all longer than the spike. The site was failing for minutes before new capacity helped.

  • Known event (a TV ad is scheduled): scheduled scale-up before it, or a higher minimum capacity during the window; pre-warm caches.
  • Unknown spikes: more headroom (lower the target utilisation, for example 50 percent instead of 70), faster scale-up (larger step sizes, shorter cooldown), small images with pre-pulled layers, a warm pool of pre-initialised instances, and scale on a leading signal (requests per second or queue depth instead of CPU).
  • While capacity arrives: load shedding (return 503 with Retry-After for low-priority traffic), per-client rate limits, cached or static fallbacks, and a CDN in front to serve most of the traffic.
  • Downstream limits: make sure database connections and third-party API quotas hold when the app tier doubles; otherwise scaling the app tier simply moves the failure.

Priority. Protect the critical path (checkout, login) and shed the rest, so partial failure is controlled rather than random.

Remember: autoscaling is for ramps; spikes need headroom and shedding.

Scenario: users are logged out randomly after you scale from 2 to 6 servers. What is the likely cause? Basic
Say this: "Sessions are stored in each server's memory and the balancer is not sticky, so a request that lands on a different server finds no session. With 2 servers it happened to work often; with 6 it rarely does. Move sessions to a shared store or signed tokens."

Why scaling exposed it. With 2 servers, a random request lands on the same server as the previous one about half the time. With 6 servers, about one in six. So users appear logged out roughly 83 percent of the time instead of 50 percent: the bug was always there; more servers made it visible.

Fix.

  • Move sessions to a shared store (Redis) or use signed tokens, so any server can serve any request.
  • As a stopgap, enable sticky sessions, knowing their limits (lost on node death or deploy, uneven load).
  • Check that every node uses the same signing or encryption key for cookies and tokens. A mismatched secret on some nodes produces the same symptom: a cookie valid on one node is rejected on another.
  • Check that the cookie domain, path and secure flags are consistent across nodes and the load balancer.

Remember: more nodes expose hidden state; fix the state, not the symptom.

Real-life: what is a well-known example of a cache-related outage? Senior
Say this: "Facebook's 2010 outage is a commonly cited case: an invalid configuration value caused every client to query the database to fix it, which created a feedback loop that overloaded the database cluster. The lesson is about self-made stampedes and protecting the database from client-driven retries. I would stick to the lesson, not exact figures."

The story (as publicly described at the time; details hedged). A configuration value held in a persistent store was judged invalid by clients. Each client tried to repair it by querying the database. As more clients saw the invalid value, the number of queries grew until the database cluster was overloaded, which made it harder to fix the value, and the site was effectively down for hours. Engineers had to cut traffic to the database and restore gradually.

Lessons usually drawn.

  • A bad value that every client reacts to by hitting the database is a self-made stampede.
  • Protect the database from client-driven retries and fix-up logic: rate limits, circuit breakers, single-flight on the repair path.
  • Have a way to cut traffic and restore gradually (a kill switch, load shedding).
  • Avoid designs where the recovery action multiplies load when the system is already failing.

Facebook's later published memcache design (the 2013 NSDI paper "Scaling Memcache at Facebook") describes leases against stampedes and stale sets, and cluster-level protection for the same class of problem.

Trap: in an interview, stick to the lesson, not exact figures, if you do not remember them.

Remember: recovery logic that hits the database from every client can turn a small fault into an outage.

Scenario: hit ratio is only 40 percent although the data seems cacheable. How do you investigate? Senior
Say this: "I would check whether the cache is too small (high evictions), whether keys are too specific, whether TTLs are shorter than the reuse gap, whether scans flush hot items, whether invalidation is too broad, whether the workload has little reuse, and whether per-node caches warm separately. I measure per key type, not one overall ratio."
  • Cache too small. High eviction rate, and the hit ratio climbs when you add memory. Fix: more memory or smaller entries.
  • Keys too specific. Timestamps, request ids or unsorted parameters in the key, so equal requests do not share an entry. Normalise keys.
  • TTL too short compared with the time between repeated reads. Example: an item is read every 90 seconds but the TTL is 60, so every read is a miss. Lengthen the TTL or use event invalidation.
  • Scans or one-hit traffic (crawlers, bulk exports) flushing hot items. Use an admission policy (TinyLFU) or exclude that traffic from the cache.
  • Frequent invalidation because writes touch broad keys (one price change deletes whole listing pages). Narrow the invalidation.
  • Low reuse in the workload (long-tail access); consider whether the cache is worth it at all.
  • Per-node local caches that each warm separately; add a shared level.

Method. Break the hit ratio down by key type and endpoint; check eviction counts, TTL distribution and key cardinality; replay a sample of traffic against different sizes and TTLs to find the knee of the curve. A single overall number hides that, say, products hit at 95 percent while search at 5 percent drags the average down.

Remember: measure by key type; check size, key shape, TTL, scans, invalidation.

Scenario: after scaling the app from 20 to 200 pods, the database and cache start refusing connections. Why, and what do you do? Senior
Say this: "Each pod has its own connection pool, so 200 pods times 20 connections is 4,000 connections, far above what a database handles well. I shrink the per-pod pools, put a connection pooler or proxy in front that multiplexes many clients over few server connections, and cap the autoscaler maximum."

Why it breaks. A database connection is not free: each takes memory and (in some databases) a process or thread. Past a few hundred active connections, performance usually degrades, because of context switching and lock contention, and then hits the connection limit and refuses new ones. Most pool connections sit idle most of the time, so the app holds far more than it needs.

The arithmetic. 20 pods x 20 = 400 connections (fine). 200 pods x 20 = 4,000 (too many). The same multiplication applies to the cache cluster if every pod connects to every node.

Fixes.

  • Smaller per-pod pools. A pool of 5 is often enough; measure real concurrent usage. Total = pods x pool size.
  • Connection pooler or proxy between the app and the database (such as PgBouncer or ProxySQL, or a cloud database proxy) that multiplexes thousands of client connections over a few dozen server connections. Mind transaction versus session pooling modes and features that need session state.
  • Proxy in front of the cache cluster to cut the node-by-pod connection fan-out.
  • Cap the autoscaler maximum to what the dependency can accept.
  • Reduce database calls with caching so fewer connections are needed at all.

Rule of thumb for the design discussion. Compute total connections as pods x pool size for every shared dependency before you set autoscaling limits.

Remember: scale-out multiplies connections; budget them.
