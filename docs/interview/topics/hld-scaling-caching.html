Click a question to open the answer. Try to answer out loud first, then compare. The page has two halves: how to scale the stateless service tier, and how to use caches without hurting correctness. Scaling the stateless tier

What is the difference between vertical and horizontal scaling, and when do you pick each? Basic

Vertical scaling (scale up) means a bigger machine: more CPU, RAM, faster disk. Horizontal scaling (scale out) means more machines behind a load balancer.

VerticalHorizontal
EffortTrivial, no code changeNeeds a stateless or partitioned design
CeilingHard limit (biggest instance size)Practically very high
Cost curveGets superlinear at the top endRoughly linear
FailureOne box is a single point of failureLose one of N, lose 1/N of capacity
DowntimeOften needs a restart to resizeAdd nodes with no downtime

Pick vertical first when the system is small, the bottleneck is a single-node database, or the code is stateful and cannot be split yet. Pick horizontal for the web or API tier, because it is the cheapest path to both capacity and availability. In practice: scale the stateless tier out, scale the database up as far as is sane, then add replicas, caches, and finally sharding.

Say: "The app tier scales out because it holds no state; the data tier is where scaling gets hard, so I protect it with caching and read replicas before I shard."
What does "stateless service" mean and why is it the foundation of horizontal scaling? Basic

A stateless service keeps no per-client or per-request data in its own memory or local disk between requests. Any instance can serve any request because everything needed arrives with the request (token, parameters) or is fetched from a shared store (database, cache).

That gives you: (1) a load balancer can route freely, no affinity needed; (2) instances are interchangeable, so you can add, kill or replace them at will; (3) a crash loses nothing but in-flight requests; (4) autoscaling and rolling deploys become safe.

Stateless does not mean "no state exists". The state moved: into a database, a cache, a token the client holds, or a queue. The design question is always "where does the state live instead?"

Trap: Saying "just put it in Redis" for everything. A shared store becomes the new bottleneck and the new single point of failure, so it needs its own scaling and failure story.
What kinds of hidden state quietly break statelessness? Intermediate
  • In-memory HTTP sessions (a servlet session map). A second request on a different node sees an empty session.
  • Local file uploads or temp files. Upload goes to node A, the download lands on node B. Use object storage.
  • Local caches that must be consistent, such as a permissions cache updated by an admin call that only hit one node.
  • In-process schedulers and cron. With 10 instances the job runs 10 times. Use leader election or a distributed scheduler lock.
  • In-memory rate-limit counters. Each node counts alone so the effective limit is N times higher.
  • WebSocket connections. The connection itself is state pinned to one node. You need a pub/sub or routing layer to reach it.
  • Singletons with counters or sequence generators, and local clocks used for ordering.
  • Warm-up data (a big model or lookup table loaded in memory). Not wrong, but it affects how fast a new node becomes useful.
How does the load balancer choose among stateless instances, and which algorithm would you choose? Intermediate
AlgorithmHowGood for
Round robinTake turnsUniform, short requests
Weighted round robinBigger nodes get more turnsMixed instance sizes, canary traffic
Least connections / least outstanding requestsSend to the least busy nodeVariable request cost, long calls
Power of two choicesPick 2 random nodes, take the less loadedLarge fleets, avoids herding on one "least loaded" node
IP or key hash / consistent hashSame key goes to same nodeCache affinity, sticky behaviour

Default answer: least outstanding requests (or round robin if requests are uniform), with health checks so dead nodes drop out. Use consistent hashing only when locality really matters, for example when each node keeps a local cache for a subset of keys.

Trap: Round robin with a slow new node: it gets the same share as everyone and falls behind. Least-connections plus slow-start (ramp weight up over time) fixes this.
You added more app servers but throughput barely improved. Why? Senior

Horizontal scaling only helps if the bottleneck is the thing you duplicated. Look for:

  1. Shared dependency saturated. Database CPU or connections, a single Redis, a downstream API. More app nodes simply push more load into the same limit. (Often worse: each node opens its own connection pool, so 50 nodes times 20 connections is 1000 connections to the database.)
  2. Lock contention on a shared row or a distributed lock; work is serialized no matter how many nodes.
  3. Load balancer or network limit (bandwidth, connections per second, a single LB instance).
  4. Uneven distribution: sticky sessions or a hot key send most traffic to a few nodes.
  5. Coordination cost: chatty calls between nodes, cluster-wide cache invalidation broadcasts.
  6. Serial portion of the work (Amdahl's law): if 10 percent of each request is serialized, the speedup can never exceed 10x however many nodes you add.

Method: find the saturated resource first (utilisation, saturation, errors per component), fix that, then scale the next tier. Caching in front of the database is often the cheapest fix.

How do clients find instances that come and go? Explain service discovery. Intermediate

When instances autoscale, restart and get new IPs, hard-coded addresses fail. Service discovery keeps a live registry of healthy instances.

  • Server-side discovery: clients call a stable address (a load balancer or virtual IP); the LB consults the registry. Simple clients, one extra hop. Example: cloud load balancers, a Kubernetes Service.
  • Client-side discovery: the client queries the registry and picks an instance itself (Eureka with a client library, gRPC with a resolver). No extra hop, but every language needs the logic.
  • DNS-based: instances published as DNS records with a short TTL. Easy, but clients and resolvers cache DNS, so changes propagate slowly and unevenly.
  • Service mesh sidecar: a proxy next to each pod handles discovery, retries, mTLS and load balancing (Envoy-based meshes).

Registration is either self-registration (the instance announces itself and sends heartbeats) or third-party (the platform, for example Kubernetes, registers it). Health checks decide who is in the registry. Key failure to mention: a stale registry sends traffic to dead nodes, so clients need timeouts, retries to another instance and circuit breakers.

At a design level, what do containers and an orchestrator (such as Kubernetes) give you for scaling a stateless tier? Basic

A container packages the app and its dependencies into an immutable image, so every instance is identical and starts in seconds rather than minutes. An orchestrator runs a declared desired state ("keep 12 replicas of this image") and continuously reconciles reality with it.

  • Scheduling: places containers on nodes with enough CPU and memory.
  • Self-healing: restarts crashed containers, replaces failed nodes' workloads.
  • Scaling: change the replica count by hand or by an autoscaler.
  • Rolling updates and rollback with readiness gates.
  • Discovery and load balancing: a stable service name in front of changing pods.
  • Config and secrets injected from outside the image, keeping the image stateless.

Two health concepts interviewers like: a liveness probe ("is it stuck, restart it") and a readiness probe ("can it take traffic now"). Mixing them up causes outages: a liveness check that depends on the database will restart every healthy pod when the database blips.

Two scaling layers: pods scale first, but if the cluster has no free nodes pods stay pending, so a node-level (cluster) autoscaler must also exist, and it is slower (minutes).

Sessions and where state lives

Where can you keep user session state in a scaled-out system? Compare the options. Intermediate
OptionHowProsCons
Server memory + sticky sessionsLB pins a user to one nodeFast, no extra systemUneven load, session lost on node death or deploy, blocks easy scale-in
Shared session store (Redis, Memcached, DB)Cookie holds a session id, data is in the storeAny node serves any user; easy revocationExtra network hop per request; store is a critical dependency
Client-side token (signed JWT or encrypted cookie)Claims travel with the requestNo server lookup, scales triviallyHard to revoke, size limits, secrets in tokens must be encrypted, stale claims until expiry
Replicated sessions between nodesApp server clusters copy sessionsNo external storeMemory and chatter grow with N; does not scale to large fleets

Typical modern answer: a short-lived signed access token for authentication plus a small server-side store for things that must be revocable or mutable (shopping cart, refresh tokens). Keep the session small, give it a TTL, and decide what happens if the store is down.

JWT vs a server-side session in Redis: which is better for a high-scale API, and what is the catch? Senior

A signed JWT (JSON Web Token) lets any node verify identity with a key and no lookup. It removes the session store from the hot path. Catches:

  • Revocation. A logout or a banned user stays valid until the token expires. Mitigate with short expiry (5 to 15 minutes) plus a refresh token that is checked server-side, or a small deny-list of revoked ids kept in a cache.
  • Stale claims. Role changes do not apply until refresh.
  • Size. Every request carries it; big tokens cost bandwidth.
  • Key management. Key rotation and the algorithm choice must be handled carefully (never accept an "alg: none" token).

A server-side session gives instant revocation and tiny cookies but adds one cache read per request and a hard dependency. Many systems use both: JWT for edge verification, server state for sensitive actions.

What are sticky sessions, when are they acceptable, and what do they cost you? Intermediate

Sticky sessions (session affinity) make the load balancer send all of one user's requests to the same instance, using a cookie or an IP or key hash.

Acceptable when: state must live in memory for performance (WebSocket connection, a large per-user working set, a game room), or as a short-term bridge while you migrate a legacy app to stateless.

Costs:

  • Uneven load: a few heavy users pile on one node, and the balancer cannot rebalance them.
  • Node loss or deploy drops all sessions pinned there.
  • Scale-in kills live users; scale-out does not help existing users because they stay on old nodes.
  • Complicates canaries and blue-green switches.

Rule: stickiness is an optimisation (a cache-locality hint), never a correctness requirement. The system must still work, just slower, if a request lands elsewhere.

How do you scale WebSocket or other long-lived connection servers, given the connection itself is state? Senior
  • Terminate connections on a fleet of gateway nodes; one node can hold tens to hundreds of thousands of mostly idle connections if tuned (file descriptors, memory per connection). Scale on connection count and memory, not CPU.
  • Keep a routing table (user id to gateway node) in a shared store, or publish messages on a pub/sub channel that every gateway subscribes to and filters.
  • Clients must reconnect with backoff and jitter and resume from a last-seen id, since deploys and scale-in will drop connections.
  • Drain gradually on shutdown: tell clients to reconnect elsewhere in a staggered way so you avoid a reconnect storm that knocks over the remaining nodes.
  • Keep business logic in stateless services behind the gateway; the gateway only holds sockets.

Autoscaling

What signals do you use to autoscale a stateless service, and which are better than CPU? Intermediate

CPU utilisation is the default because it is easy, but it only works when CPU is truly the limiting resource. Better signals depend on the workload:

WorkloadBetter signal
Request-serving APIRequests per second per instance, or concurrent in-flight requests, or p95 latency
Queue consumerQueue depth or age of the oldest message, divided by per-worker throughput
IO-bound / waits on downstreamsConcurrency or thread-pool saturation (CPU stays low while threads are all blocked)
WebSocket gatewayConnection count, memory
Predictable daily peakScheduled scaling (scale up at 08:45 before the 09:00 rush)

Target-tracking is the usual policy: "keep average at 60 percent of capacity" and the platform computes the instance count. Pick a target below 100 percent so there is headroom to absorb a spike while new instances boot.

What are the common autoscaling pitfalls? Senior
  • Lag. Metric collection (about a minute), decision, instance boot (VM: minutes; container: seconds to a minute), warm-up. A sudden spike hurts before help arrives. Fixes: headroom, scheduled or predictive scaling, faster images, pre-warmed pools.
  • Flapping (thrashing). Scale up, load drops, scale down, load rises. Use a longer scale-down cooldown than scale-up, and hysteresis (different up and down thresholds).
  • Scaling the wrong thing. Adding app nodes when the database is the bottleneck increases the damage. Cap max replicas to what downstreams can bear.
  • Death spiral. New instances start cold, take traffic before ready, are slow, push the average up, trigger more instances that all start cold. Needs readiness gating and slow-start.
  • Retry amplification. When latency rises, clients retry, load rises, scale-up lags further.
  • Metric mismatch (CPU low while all threads are blocked on a slow dependency, so no scale-out).
  • Cost runaway. A bug or an attack scales to the max limit; set a ceiling and alarms.
  • Per-instance resources (connection pool limits, licence counts, rate limits to an upstream) that do not scale with N.
Say: "Autoscaling handles gradual growth. For sudden spikes I rely on headroom, load shedding and rate limiting, because new capacity arrives too late."
What is instance warm-up and why does a freshly started instance often perform badly? Intermediate

A new instance is not instantly as fast as an old one. Causes: JIT (just-in-time) compilation in the JVM has not optimised hot paths yet; classes are lazily loaded; local caches are empty so every request misses and hits the database; connection pools are not yet filled; DNS and TLS sessions are not cached.

What to do:

  • Readiness probe only passes after startup tasks finish (preload config, open pools, run a synthetic warm-up request set).
  • Slow start at the load balancer: ramp a new node's share from a small weight up over 30 to 120 seconds.
  • Pre-populate local caches or rely on a shared distributed cache so new nodes start warm.
  • For deploys, shift traffic gradually (canary) rather than all at once.
  • Ahead of known peaks, pre-scale rather than react.
Why is scaling in (removing instances) harder than scaling out? Intermediate

Adding a node is additive; removing one can drop live work. On scale-in you must: stop sending new requests (deregister from the LB), let in-flight requests finish (drain), finish or hand back queue messages, close connections cleanly, then exit. Long-lived connections (WebSocket, streaming) and long jobs make this slow. Choose a victim carefully: prefer the newest or the least loaded node, not one mid-way through a 20-minute job. Also scale in slowly (for example remove 10 percent at a time) so a wrong decision is cheap to reverse.

Deployment impact and graceful shutdown

How does a deployment affect capacity, and how do you avoid an outage during a rolling deploy? Senior

A rolling deploy takes instances out of service while they are replaced. If you run at 80 percent utilisation with 10 nodes and take 3 out at once, the remaining 7 face about 114 percent and fall over. Also, new instances start cold (see warm-up).

  • Control the batch with max unavailable (how many may be down) and max surge (how many extra to start first). Surge-first keeps capacity constant.
  • Keep steady-state headroom that covers the batch size plus the failure of one availability zone.
  • Gate each step on a readiness probe, then on a small bake time and health metrics.
  • Prefer canary (1 to 5 percent traffic, watch errors and latency, then expand) or blue-green (a full parallel environment, switch the router, keep the old one for fast rollback).
  • Do database changes in backward-compatible steps (expand, migrate, contract), because old and new code run side by side during the deploy.
  • Avoid deploying at peak traffic, and avoid all services deploying simultaneously.
Walk through a graceful shutdown of a stateless service and explain connection draining. Intermediate

Connection draining (deregistration delay) means a node leaving the pool stops receiving new requests but is given time to finish the ones in flight.

  1. The orchestrator or scaler decides to stop the instance and sends a termination signal (for example SIGTERM).
  2. The instance fails its readiness check (or is deregistered) so the load balancer stops routing new requests. This propagates with a delay, so a few more requests may still arrive.
  3. The app stops accepting new connections but keeps serving in-flight requests until done, bounded by a timeout.
  4. Queue consumers stop polling, finish the current message and ack (or let the message return to the queue).
  5. Flush buffers, close database pools, deregister from discovery.
  6. Exit. If it has not exited within the grace period, the platform force-kills it (SIGKILL), so the grace period must be longer than the longest normal request.

Common bug: the process dies instantly on SIGTERM while the LB still sends it traffic for several seconds, producing a burst of 502 errors on every deploy. Fix: wait a few seconds after going unready before closing the listener. Another: keep-alive connections that clients reuse; send "Connection: close" or close idle connections once draining begins.

Because clients can still see failures (crash, forced kill), the design also needs idempotent operations and client retries; graceful shutdown reduces errors but does not eliminate them.

How much spare capacity should a stateless tier carry, and why? Senior

Plan for failure, not just load. With 3 availability zones and a requirement to survive losing one, each zone must be able to take 50 percent more traffic, so total utilisation at peak should stay near 65 percent (2 zones at 100 percent carry what 3 zones carry at 66 percent). Add the deployment batch and autoscaling lag margin on top. Running hot at 90 percent looks efficient but any spike, deploy or node loss causes a latency cliff, because queueing delay grows sharply as utilisation approaches 100 percent.

Caching basics: why and where

Why do we cache? Give a concrete example with numbers. Basic

A cache stores a copy of data that is expensive to fetch or compute in a place that is faster to read. It buys three things: lower latency, lower load on the source of truth, and lower cost.

Example: a product page needs data that takes 40 ms and one database query. A cache lookup takes about 1 ms. At 95 percent hit ratio the average read is about 0.95 x 1 + 0.05 x 41 = 3 ms, and the database sees 5 percent of the traffic. If the site gets 20,000 reads per second, the database goes from 20,000 qps to 1,000 qps. That is the real win: a database that could not scale now has 20x headroom.

Caching works because access patterns are skewed (a small set of items gets most traffic, roughly a power law) and because data is read far more often than it changes. If neither is true, a cache helps little.

At which layers can you cache, and what does each layer give? Basic
LayerWhat it cachesStrengthWeakness

CDN / edgeImages, JS, video, cacheable API responsesClose to the user, absorbs huge trafficPurge propagation delay, privacy of personalised data
Reverse proxy / API gatewayWhole responsesShields all app serversKey must include variants (language, auth)

Rule of thumb: cache as close to the user as correctness allows, because every layer closer removes work from every layer behind it.

How does HTTP caching work for clients and CDNs (Cache-Control, ETag, versioned URLs)? Intermediate
  • Cache-Control: max-age=N lets the browser and shared caches reuse the response for N seconds with no request at all. s-maxage applies only to shared caches (CDN). private means only the browser may store it; no-store means store nowhere; no-cache means store but revalidate before use.
  • Validators: an ETag (content fingerprint) or Last-Modified. The client sends If-None-Match; the server answers 304 Not Modified with no body when unchanged. This saves bandwidth, not the round trip.
  • stale-while-revalidate serves stale content immediately and refreshes in the background; stale-if-error serves stale content when the origin is failing.
  • Vary tells caches which request headers change the response (Accept-Encoding, Accept-Language). A wrong Vary either fragments the cache or leaks one user's variant to another.

Best practice for static assets: put a content hash in the filename (app.3f9a1c.js), serve with a very long max-age and "immutable", and deploy a new filename when content changes. That sidesteps invalidation entirely.

Trap: Caching a personalised response (account page with a session cookie) at a CDN without Vary or private. One user's data gets served to another. This is a real class of security incident.
What does a CDN actually do, and when is it not enough? Basic

A CDN (content delivery network) is a fleet of edge servers around the world that cache copies of your content and answer users from the nearest location. It cuts latency (shorter distance), offloads the origin (most requests never reach it), and absorbs traffic spikes and some attacks. Many CDNs add an "origin shield" tier so many edge misses collapse into one origin request.

It is not enough when content is highly personalised, changes every second, or is write-heavy. Then you cache what you can (static parts, shared fragments) and compute the rest at the origin, or move compute to the edge for light logic.

Local (in-process) cache vs distributed cache: how do you choose? Intermediate
Local (for example Caffeine, Guava)Distributed (Redis, Memcached)
LatencyNanoseconds to microsecondsAbout 0.2 to 2 ms network round trip
CapacityA slice of each node's heapAggregate memory of the cluster
ConsistencyN copies can disagree for a whileOne logical copy
Hit ratioLower: each node warms independentlyHigher: shared across all nodes
FailureDies with the processSurvives app restarts (but is itself a dependency)
GC impactLarge caches add GC pressure (JVM)None on the app

Use local for tiny, hot, rarely changing data (feature flags, config, country lists) and where a few seconds of staleness is fine. Use distributed when you need a large shared working set or tighter consistency. Use both (a two-level cache) for the hottest keys: local with a short TTL (1 to 10 seconds) in front of a distributed cache.

What is a multi-level (L1/L2) cache, and what new problems does it bring? Senior

L1 is a small in-process cache with a short TTL; L2 is the shared distributed cache; the database is the source of truth. A read checks L1, then L2, then the database, filling each level on the way back.

Benefits: the hottest keys never leave the app node, so you take load off the distributed cache and remove the network hop. It also defends against hot keys.

Problems:

  • Invalidation fan-out. A delete in L2 does not clear L1 on other nodes. Options: very short L1 TTL (accept bounded staleness), or broadcast invalidation messages over pub/sub (a lost message means stale data until TTL, so always keep a TTL as a safety net).
  • Staleness stacks up. Worst case staleness is L1 TTL plus L2 TTL if both are filled from each other.
  • Memory duplication across nodes and more places to debug.
What should you not cache? Intermediate
  • Data that must be strongly correct at read time: account balances used to authorise a payment, inventory at the final checkout step, anything where a stale read causes money or safety loss. Read from the source of truth there (you can still cache for display).
  • Data with a very low hit ratio: unique per request (search with random filters), huge scans. You pay memory and write cost for nothing.
  • Write-heavy, quickly changing data that is invalidated before it is read again.
  • Personalised or sensitive data in shared caches without a correct key and access control (tokens, personal data in a CDN).
  • Very large objects that crowd out many small hot ones (or cache them in a separate tier).
  • Cheap-to-compute values where the cache lookup costs about as much as the work.
Say: "I cache reads that are hot, expensive and tolerant of seconds of staleness, and I do the final correctness check against the source of truth."

Cache patterns: read and write strategies

Explain cache-aside (lazy loading). What are its strengths and weaknesses? Basic
  1. Read: look in the cache. If hit, return.
  2. On miss, read the database.
  3. Put the result in the cache with a TTL, return it.
  4. Write: update the database, then delete (or update) the cache entry.

Strengths: simple, only requested data is cached, a cache outage degrades to slower (the app can fall back to the database), the cache can have a different data shape than the database. Weaknesses: first request is always a miss; stale data is possible in the window between a write and an invalidation; every app instance carries the caching logic; stampedes on popular misses.

It is the default answer in most interviews.

What is read-through, and how does it differ from cache-aside? Intermediate

In read-through the application talks only to the cache. On a miss the cache itself loads the value from the database through a loader and stores it. The caller sees a single interface.

Difference: with cache-aside the app contains the miss logic; with read-through the cache layer or library does. Read-through centralises logic, and makes it easy to add request coalescing (see stampede). The cost: the cache must know how to talk to the database, which usually means a library (a loading cache in-process) or a caching product that supports loaders. Most plain Redis or Memcached deployments are used cache-aside for this reason.

What is write-through caching, and what does it cost? Intermediate

On a write, the application writes to the cache, and the cache synchronously writes to the database before acknowledging. The cache is always up to date after a write, so later reads are hits.

Pros: consistent reads right after writes, no stale window from the write path. Cons: every write pays two writes of latency; data that is written but never read wastes cache space (mitigate with a TTL); still needs a decision on what happens if the cache write succeeds and the database write fails (the database is the truth, so fail the write and drop the cache entry). It pairs naturally with read-through.

What is write-behind (write-back), and when would you accept its risks? Senior

The application writes to the cache, which acknowledges immediately and persists to the database asynchronously later, often batched.

Pros: very low write latency, writes to the same key can be coalesced (1000 counter increments become one database write), absorbs write spikes, shields a slow database.

Cons: if the cache node dies before flushing, acknowledged writes are lost (mitigate with replication or a durable log); the database is stale, so other readers that bypass the cache see old data; ordering and failure handling in the flusher is complex; hard to debug.

Accept it for data where loss of a few seconds is tolerable and volume is high: view counters, likes, analytics events, last-seen timestamps. Do not use it for payments or orders.

What is refresh-ahead? Intermediate

The cache refreshes a hot entry in the background before it expires, typically when it has used some fraction of its TTL (for example 75 percent) and is accessed again. Readers keep getting the old value with no miss latency, so no stampede at expiry.

It suits predictable, hot keys with expensive loads (a homepage query). It wastes work on keys that will not be read again, and if the refresh fails you must serve stale up to a hard limit. Variants: a scheduled job that recomputes a few known-hot keys, and "stale-while-revalidate" semantics.

What is write-around, and when is it useful? Intermediate

Writes go straight to the database and skip the cache; the entry is only cached when later read. It avoids filling the cache with data that is written once and rarely read (logs, bulk imports, uploads). Reads right after a write will miss, and any older cached copy must still be invalidated.

On a write, should you update the cache or delete the entry? Senior

Delete (invalidate) is usually safer. Updating the cache from the writer has a race: two concurrent writers update the database in order A then B, but the cache updates land B then A, leaving the cache holding the older value A forever (until TTL). Deleting avoids stale values being written; the next reader reloads the latest row. Also, derived values (a rendered page, an aggregate) are easier to delete than to recompute in the writer.

Even delete has a race, covered in the consistency section: a slow reader can repopulate the cache with an old value right after the delete. Mitigations: short TTLs, delayed double delete, or versioned values.

Eviction, expiry and invalidation

What are LRU, LFU, FIFO and TTL, and how do you choose an eviction policy? Basic

Eviction decides what to throw out when the cache is full. TTL (time to live) is separate: it expires an entry after a fixed time regardless of space.

PolicyEvictsGood whenWeak when
LRU (least recently used)The entry unused for longestRecent access predicts near-future access (most workloads)A big one-time scan flushes the hot set
LFU (least frequently used)The entry with fewest accessesStable popularity (a hot catalogue)Old popular items linger; needs frequency aging
FIFOThe oldest insertedSimple, rarely bestIgnores usage
RandomA random entryVery cheap approximationNo intelligence
TTLAnything past its time limitBounding stalenessDoes not manage size alone

Practical: LRU or an approximate LRU plus a TTL on every key. Modern in-process caches (for example W-TinyLFU as used in Caffeine) combine recency and frequency, with a small admission filter so scans do not pollute the cache. Large caches often use sampled (approximate) LRU because exact LRU needs a global linked list that is costly.

Trap: Implementing an LRU cache is a common coding question: a hash map plus a doubly linked list gives O(1) get and put.
How do you choose a TTL? Intermediate

TTL is the upper bound on staleness, and your safety net when explicit invalidation fails. Choose it from the business tolerance, not from habit:

  • Static or reference data (country list): hours to days.
  • Product details: 1 to 10 minutes.
  • Counts, feeds, search results: seconds to a minute.
  • Per-user permissions: short (seconds to a minute) because stale permissions are a security issue.
  • Negative results ("not found"): short (seconds to a minute).

Always add jitter (a random plus or minus 10 to 20 percent) so entries filled together do not all expire together. A longer TTL gives a higher hit ratio but more staleness; a shorter TTL is safer but loads the database more.

What are the strategies for cache invalidation? Why is it called one of the hard problems? Intermediate
  1. TTL only: do nothing on writes; accept staleness up to the TTL. Simplest and robust.
  2. Delete on write: the writer deletes the cache key after committing. Fresh data soon after, but you must know every key affected.
  3. Event-driven invalidation: publish change events (from the application, or from the database change log via change data capture, CDC) and a consumer deletes or updates keys. Decouples writers from caches, covers writes from any source (batch jobs, admin tools).
  4. Versioned keys: put a version number in the key (user:42:v7); bumping the version makes old entries unreachable, and they age out by eviction. No race, no delete needed.
  5. Tag or group invalidation: attach tags (all pages that include product 42) so one call purges a group; CDNs offer "surrogate keys".
  6. Purge API / soft purge: at CDNs, mark content stale and serve it while refetching.

Why hard: a cached value can be derived from many rows, so a single write affects many keys; you must know which; updates and deletes race with readers; multiple cache layers each hold copies; and a missed invalidation is silent. The pragmatic answer: always combine explicit invalidation with a TTL as a backstop.

Why use change data capture (CDC) for cache invalidation instead of invalidating in application code? Senior

Application-level deletes miss writers: a batch job, a manual SQL fix, another service, or a code path someone forgot. CDC reads the database commit log (for example via a log-reader tool streaming to a message bus), so every committed change produces an event, in commit order. A consumer then deletes or refreshes the right keys. It also fixes the "database commit succeeded, cache delete failed" gap, because the event is retried until processed. Costs: extra infrastructure, a small delay (typically sub-second to seconds), and the consumer must map row changes to cache keys. Facebook's published memcache design uses a similar idea (a daemon reading the database commit log and issuing deletes).

How do you design good cache keys? Intermediate
  • Include everything that changes the result: entity id, tenant, locale, API version, relevant query parameters, and user role where output depends on it. A missing tenant in the key is a data-leak bug.
  • Use a consistent, readable structure: app:entity:id:variant, for example shop:product:42:en.
  • Normalise inputs (sort query parameters, lowercase) so equivalent requests share one entry.
  • Keep keys short, since in a big cache key bytes cost memory.
  • Add a schema or code version in the key when the serialised format changes, so a deploy does not read objects in an old shape.
  • Avoid unbounded key cardinality (a key per search string) that fills the cache with one-hit entries.
What is cache warming, and when do you need it? Intermediate

A cold cache has no entries, so all traffic falls to the database. Warming pre-loads the cache before it takes live traffic. Needed when: a new cache cluster or node is added, after a restart or failover, before a planned high-traffic event (a sale), or after a deploy that changes key format.

Methods: replay a list of the top N hot keys (from access logs or the previous cache's stats); run a background loader that queries popular entities; shadow or mirror a slice of live reads to the new cache; ramp traffic gradually onto the new node. Do it with rate limits so the warm-up itself does not overload the database. Without warming, the cure is request coalescing and rate-limited database access so that a cold start degrades gracefully.

Cache failure modes: stampede, hot keys, penetration, avalanche

What is a cache stampede (thundering herd) and how do you prevent it? Intermediate

A popular key expires. In the next few milliseconds, thousands of requests all miss, and all of them run the same expensive database query at once. The database slows or falls over, which makes the refill slower, which makes more requests pile up.

DefenceHow
Request coalescing (single flight)Within a node, only the first miss runs the loader; others wait for its result. Built into loading caches.
Distributed lock / leaseThe first requester sets a short-lived lock key; others wait briefly and re-read, or serve stale. Give the lock a TTL so a crash does not block forever.
Serve stale while revalidatingKeep a soft TTL (when to refresh) and a hard TTL (when to drop). After the soft TTL, one caller refreshes while others get the old value.
TTL jitterRandomise expiry so keys do not expire together.
Refresh-ahead / background recomputeHot keys never expire in the foreground.
Probabilistic early expirationEach reader has a small, growing chance of refreshing before the TTL, more likely when the load is slow. Spreads refresh over time with no lock.
Say: "Coalesce misses, serve stale for a bit, add jitter, and cap database concurrency so a stampede cannot take the database down."
What is a hot key problem, and how do you handle it? Senior

One key gets a disproportionate share of traffic (a celebrity profile, a flash-sale product). In a sharded cache, hashing maps that key to one node, so that node's CPU or network saturates while others are idle. Adding nodes does not help, because the key still lives on exactly one.

  • Local (L1) cache with a short TTL on every app node for the hot key. Reads never leave the app node. Most effective and cheapest.
  • Replicate the key under several names (hot:42#1 to hot:42#N), read a random one, write/invalidate all. Spreads load over N cache nodes.
  • Detect hot keys automatically (client-side counters, proxy sampling, or cache server stats) and promote them to L1 or replication dynamically.
  • Edge caching via CDN for public content.
  • Split the value: a heavily updated counter can be sharded into many sub-counters and summed on read.
  • Rate limit or coalesce requests for that key.
What is cache penetration, and how do you defend against it? Intermediate

Penetration (or cache bypass) is when requests ask for keys that do not exist anywhere (user id -1, random ids, or an attacker scanning). Every request misses the cache, then misses the database, so the cache gives no protection and the database takes the whole load.

  • Negative caching: cache the "not found" result with a short TTL (30 to 60 seconds).
  • Bloom filter in front: a compact set of all valid ids; if the filter says "definitely not present", return at once without touching cache or database. Allows false positives (a few wasted lookups) but never false negatives. Needs updating as new ids are created.
  • Input validation (id format and ranges), authentication, and per-client rate limiting.
  • Monitor for a high miss ratio paired with a high database miss rate as an attack signal.
What is negative caching and what are its risks? Intermediate

Negative caching stores the fact that something does not exist (or a lookup failed) so repeated lookups do not hit the source. Examples: DNS NXDOMAIN caching, caching a 404 at a CDN, caching a null for a missing user.

Risk: the thing gets created right after, but the cache still says "not found" until the TTL ends. A user signs up and cannot log in for a minute. Mitigations: short TTLs for negatives, and delete the negative entry when the entity is created. Also store negatives with a distinct sentinel so a legitimately empty value is not confused with a miss. Do not negatively cache transient errors (a timeout, a 500) as if they were "not found".

What is a cache avalanche and how do you prevent it? Intermediate

A large part of the cache becomes unavailable at once, so a flood of requests hits the database. Two causes: (1) many keys expire at the same instant (loaded together with the same TTL), (2) the cache cluster itself crashes or restarts empty.

  • Jitter on TTLs.
  • High availability for the cache: replicas, multiple zones, consistent hashing so losing one node loses only its share.
  • Multi-level caching, so a local cache absorbs some load during an outage.
  • Protect the database: concurrency limits, circuit breakers, load shedding, and request coalescing so it degrades rather than collapses.
  • Warm the cache before returning a replacement node to service.
  • Serve stale data when the loader is failing.

Stampede is one hot key; avalanche is many keys or the whole cache. Interviewers like candidates who separate them.

What should happen when the cache is down? Fail open or fail closed? Senior

Decide per use case, before the incident:

  • Pure read cache: fail open, go to the database, but protect it with a concurrency limit, a circuit breaker and load shedding. Short timeouts on the cache call (a few ms to tens of ms) so a slow cache does not become slower than no cache.
  • Cache that carries real state (sessions, rate-limit counters, locks): there is no database fallback. Either replicate and accept degraded behaviour (for rate limiting, often fail open with a coarse local limit; for security checks, fail closed), or keep that data in a durable store.
  • Do not retry aggressively against a struggling cache; use jittered backoff and a circuit breaker.
  • Run capacity tests that simulate a cold cache. Many databases are sized assuming a 95 percent hit ratio and cannot survive a 0 percent one.
Trap: Saying "the cache is just an optimisation" while the system silently depends on it for capacity. If the database cannot serve the miss load, the cache is effectively mandatory and needs to be treated as a tier-one dependency.
What goes wrong with very large cache values or huge collections? Intermediate

A single multi-megabyte value takes long to transfer and (on a single-threaded server) blocks other requests while it is read, serialised or deleted; it uses network bandwidth, evicts many small hot keys, and when it expires every reader reloads a big object. Fixes: break it into smaller keys or pages, compress, cache only the fields you need, store big blobs in object storage and cache the pointer, and set size limits on values.

Consistency between cache and database

Describe a race condition in cache-aside that leaves stale data in the cache. How do you reduce it? Senior
  1. Reader R misses the cache and reads the old row (v1) from the database.
  2. Writer W updates the row to v2 and deletes the cache key.
  3. R, which was slow, now writes v1 into the cache.
  4. The cache holds v1 although the database holds v2, until TTL expires.

It is rare (the reader has to be delayed between its read and its fill, longer than the write) but real at scale. Mitigations:

  • TTL as a backstop, the minimum defence.
  • Delayed double delete: delete after the write, then delete again after a short delay (longer than a typical read-and-fill time) to remove a late stale fill.
  • Versioned values: store a version or timestamp with the data and use a compare-and-set that refuses to overwrite a newer version.
  • Leases (as in Facebook's memcache paper): a miss returns a token; a delete invalidates outstanding tokens, so a stale fill is rejected.
  • CDC-driven invalidation from the commit log, which orders events properly.
In a write, do you update the database first or the cache first? What if one step fails? Senior

Standard: write the database first (source of truth), then delete the cache entry.

  • Cache first, then database: if the database write fails, the cache holds data that never existed. Bad.
  • Delete the cache first, then write the database: a concurrent reader can reload the old value between the two steps and re-cache it. Bad.
  • Database then delete: if the delete fails, the cache is stale until TTL. Fix with retry (a queue or outbox that retries deletes) and with TTL. The window of staleness is small and bounded.

You cannot make two separate systems atomic without distributed transactions, so you design for bounded inconsistency and retries instead. An outbox table (written in the same transaction as the data) plus a relay that issues cache deletes gives reliable, at-least-once invalidation. Deletes are idempotent, so duplicates are harmless.

A user updates their profile and then sees the old one. How do you fix read-your-writes with a cache and replicas? Senior

Causes: stale cache entry, or a read replica that has not caught up yet, or a different region's cache. Options:

  • Delete the cache key on write so the next read reloads. If that read goes to a lagging replica it can re-cache old data, so for a short window after a write route that user's reads to the primary (for example for 5 to 10 seconds, tracked by a cookie or by a last-write timestamp).
  • Write-through for that entity so the cache is updated with the new value.
  • Return the new object in the write response and have the client use it instead of re-fetching.
  • Version the value and let the client send "at least version N".

Other users may see stale data for a while; that is usually acceptable. Only the writer needs the guarantee.

How do you explain the consistency you offer when a cache sits in front of a database? Intermediate

Say it as bounded staleness: "Reads may be up to TTL seconds stale in the worst case when invalidation fails, and typically milliseconds to seconds stale after a write when invalidation works." This is eventual consistency, not strong consistency. If a flow needs strong consistency (a payment check, a stock decrement), it bypasses the cache and reads or writes the source of truth, ideally in a transaction or with a conditional update. Present it as a deliberate trade: freshness against latency, load and availability.

How do caches behave across multiple regions? Senior

Each region usually has its own cache cluster, because a cross-region round trip (tens to over a hundred ms) would defeat the purpose. A write in region A must invalidate entries in region B. Options: replicate invalidation events over a message bus or the database's replication stream (so B deletes after it sees the change; this also avoids B refilling from a replica that has not received the write yet); accept TTL-bounded staleness for data where that is fine; or pin each user or tenant to a home region so most reads and writes stay local. Beware refilling a remote cache from a lagging replica, which can cache stale data right after a delete.

Sizing, hit ratio and technology choice

What is the hit ratio, and how does it change your average latency and database load? Basic

Hit ratio = hits / (hits + misses). Average latency = h x t_cache + (1 - h) x (t_cache + t_db) (the miss still pays the cache lookup). Database load = (1 - h) x total reads.

Hit ratioAvg latency (1 ms cache, 40 ms db)DB load at 50,000 reads/s
80%9 ms10,000/s
90%5 ms5,000/s
95%3 ms2,500/s
99%1.4 ms500/s

Insight: going from 95 to 99 percent cuts database load by 5x, though latency barely moves. So think of the miss ratio, not the hit ratio, for protecting the database: 1 percent misses versus 5 percent is a 5x difference. Also remember that a miss path is slower than no cache by one lookup, and tail latency (p99) is dominated by misses.

How do you size a cache? Walk through an estimate. Senior

Steps:

  1. Estimate the working set, not the whole dataset. Suppose 100 million products but access follows a skew where 5 percent of items take 90 percent of reads: hot set is 5 million items.
  2. Per-entry size: 2 KB value plus about 100 bytes key and overhead, call it 2.2 KB (real overhead depends on the store; add 30 to 50 percent for fragmentation and metadata to be safe).
  3. Memory: 5 million x 2.2 KB = 11 GB, plus headroom, call it about 16 GB. Add replicas for availability (a copy per shard).
  4. Throughput: if peak is 100,000 cache ops/s and a node safely handles about 50,000 to 100,000 simple ops/s (hedge: depends on payload and hardware), you need several nodes for throughput even if memory fits on one.
  5. Check network: 100,000 ops/s x 2 KB = 200 MB/s, which is 1.6 Gbit/s; make sure NICs and the app side can carry it.
  6. Validate with measurements: track hit ratio against cache size (a larger cache has diminishing returns), and eviction rate. Many evictions with a falling hit ratio means it is too small.
Say: "I size for the hot working set, then check throughput and network separately, and verify with the hit-ratio curve instead of guessing."
Redis vs Memcached at design level: how do you choose? Intermediate
MemcachedRedis

Default choice today is Redis (or a compatible managed service) because it does more and offers HA. Memcached is chosen for plain, large, multi-core, ephemeral caching where simplicity matters. Whatever you choose, treat a cache holding only copies as disposable and keep durable data elsewhere. For internals of Redis, see the separate Redis page.

How is a distributed cache spread over many nodes, and what happens when you add or remove one? Intermediate

Naive hashing (key hash mod N) remaps almost every key when N changes, so adding a node makes nearly everything miss: an instant self-inflicted avalanche. Consistent hashing places nodes and keys on a ring so adding or removing a node only moves about 1/N of the keys (with virtual nodes to even out the load). Redis Cluster uses fixed hash slots (16384) that are moved between nodes, with similar effect. Do resizing during low traffic, warm the new node, and expect a temporary dip in hit ratio.

Where does the sharding logic live: client library or a proxy? Intermediate

Smart client: the library knows the node map and routes directly (fewest hops, but every language needs a good client, and topology changes must be pushed to all clients). Proxy: clients talk to a stable endpoint; the proxy routes, pools connections and hides topology (one more hop and one more thing to scale and keep available, but simpler clients and easier failover, and connection counts to the cache are far lower). A managed service typically offers one of these for you.

What design choices about serialisation and value shape affect a cache? Intermediate
  • Format: JSON is readable but bulky; binary formats (protobuf, MessagePack) are smaller and faster. Compress large values (watch CPU).
  • Schema evolution: during a rolling deploy old and new code share the cache. Include a version in the key or value, and make readers tolerate unknown fields, or the deploy causes deserialisation errors.
  • Granularity: cache the object, a page of results, or the rendered fragment? Bigger entries save more work per hit but are invalidated more often and hold more redundant data.
  • Do not cache ORM entities with lazy references; cache plain data objects.

Scenarios and real-life problems

Scenario: right after a Redis restart the database CPU hits 100 percent and the site is slow for 20 minutes. What happened and what do you do? Senior

The cache came back empty (cold), so hit ratio went from 97 percent to near zero and the database got about 30x its normal read load. Misses also trigger stampedes on popular keys.

Immediate: shed load (rate limit, serve degraded or stale pages, disable expensive features), cap database concurrency, enable request coalescing, and warm the hottest keys first.

Long term: replicas with automatic failover instead of a single node, persistence (snapshot reload) if restart time is the issue, a warm-up routine, multi-level caching, jittered TTLs, and a game-day test that runs with an empty cache to find out what the database can really handle.

Scenario: a flash sale for one product, the product page and stock count are read 200,000 times a second. How do you cope? Senior
  • The page body is public and cacheable: serve it from the CDN with a short TTL (a few seconds) plus stale-while-revalidate.
  • The product record is a hot key: use an L1 cache in each app node with a 1 to 5 second TTL, so the distributed cache sees a trickle.
  • Stock display can be slightly stale (show "low stock"), cached separately with a short TTL. The final decrement goes to the source of truth with an atomic conditional update (decrement only if stock is above zero), maybe through a queue to serialise contention.
  • Pre-warm before the sale starts and pre-scale the app tier on a schedule rather than waiting for autoscaling lag.
  • Add rate limiting and a waiting-room queue to protect checkout.
Scenario: an admin removes a user's access, but the user keeps access for 10 minutes. Why, and how do you fix it? Intermediate

Permissions were cached (or put into a long-lived token) with a 10 minute TTL, and nothing invalidated the entry on change. Fixes: delete the permission key on change (event-driven), shorten TTL for security data to seconds, use a revocation list checked on each request, short-lived access tokens with server-side refresh, and separate "show in the UI" from "authorise the action" so the sensitive path asks the source of truth or a fresh cache. This is a case where a bounded-staleness answer must be tied to a security requirement.

Scenario: every deployment produces a short burst of 502 and 504 errors, though the new version is healthy. What do you check? Intermediate
  1. Does the app handle the termination signal and drain, or does it die at once?
  2. Does the load balancer's deregistration delay exceed the app's drain time, and is there a short wait between going unready and closing the listener?
  3. Are new pods marked ready before they are really ready (readiness probe too weak, cold JIT and empty caches)?
  4. Is max unavailable too high, so capacity dips under peak load?
  5. Do keep-alive connections from clients or the LB stay pointed at terminated instances (idle timeout mismatch: LB idle timeout longer than the app's)?
  6. Is the grace period longer than the slowest request?

Fixing these usually removes the errors; client-side retries for idempotent requests cover the rest.

Scenario: traffic doubles in two minutes during a TV ad, and autoscaling adds nodes after the site is already failing. What would you change? Senior
  • Known event: schedule scale-up before it, or use a higher minimum capacity.
  • Unknown spikes: more headroom (lower the target utilisation), faster scale-up (larger step sizes, shorter cooldown, small fast-starting images, pre-pulled images and a warm pool), and scale on a leading signal (requests per second or queue depth instead of CPU).
  • While capacity arrives: load shedding (return 503 with Retry-After for low-priority traffic), rate limits per client, serve cached or static fallbacks, and a CDN in front.
  • Make sure downstream limits (database connections, third-party APIs) will hold when the app tier doubles.
Scenario: users are logged out randomly after you scale from 2 to 6 servers. What is the likely cause? Basic

Sessions are stored in each server's memory and the load balancer is not sticky (or the sticky cookie is ignored). With 2 servers, many requests happened to hit the same one; with 6 the chance is lower. Fix: move sessions to a shared store or use signed tokens; as a stopgap enable sticky sessions, knowing the limits. Also check each node uses the same signing or encryption key for cookies, since mismatched secrets cause the same symptom.

Real-life: what is a well-known example of a cache-related outage? Senior

Facebook's 2010 outage is a commonly cited case (publicly described by Facebook at the time, details hedged here): a configuration value stored in a persistent store was found invalid by clients, and each client tried to fix it by querying the database, which created a feedback loop of queries that overloaded the database cluster; the site was effectively taken down for hours. The lessons usually drawn: a bad value that every client reacts to by hitting the database is a self-made stampede; protect the database from client-driven retries; and have a way to cut traffic and restore gradually. Facebook's later published memcache design (the 2013 NSDI paper "Scaling Memcache at Facebook") describes leases against stampedes and stale sets, and cluster-level protection for the same class of problem.

Trap: In an interview, stick to the lesson, not exact figures, if you do not remember them.
Scenario: hit ratio is only 40 percent although the data seems cacheable. How do you investigate? Senior
  • Cache too small: high eviction rate and a hit ratio that climbs when you add memory.
  • Keys too specific: timestamps, request ids or unsorted parameters in the key, so equal requests do not share an entry. Normalise keys.
  • TTL too short compared with the time between repeated reads.
  • Scans or one-hit traffic (crawlers, bulk exports) flushing hot items; use admission policies (TinyLFU) or exclude that traffic.
  • Frequent invalidation because writes touch broad keys.
  • Low reuse in the workload (long-tail access); consider whether the cache is worth it at all.
  • Per-node local caches that each warm separately; add a shared level.

Measure per key-type hit ratios, eviction counts, and TTL distribution rather than one overall number.

Scenario: after scaling the app from 20 to 200 pods, the database and cache start refusing connections. Why, and what do you do? Senior

Each pod has its own connection pool: 200 pods x 20 connections is 4,000 connections, far above what a database typically handles well (often a few hundred active connections is the sweet spot). Fixes: smaller per-pod pools (most of the time connections sit idle), a connection pooler or proxy between the app and database that multiplexes many clients over few server connections, and a proxy in front of the cache cluster. Cap the autoscaler maximum to what the dependency can accept, and reduce database calls with caching so fewer connections are needed.
