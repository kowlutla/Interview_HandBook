Version notes used on this page: the idempotent producer is on by default and acks=all is the default since Kafka 3.0. KRaft mode (Kafka without ZooKeeper) became production ready in 3.3, ZooKeeper mode was deprecated in 3.5, and ZooKeeper support was removed in Kafka 4.0 (released 2025). The cooperative rebalance protocol arrived in 2.4. The new server-side consumer group protocol (KIP-848) became generally available in 4.0. The default linger.ms is 0 up to 3.x and was raised to 5 in 4.0. Share groups (queue-like consumption, KIP-932) are early work in 4.x, so treat them as new. Where a default may differ in your version, check the docs.

Mental model: the 8 ideas everything hangs on

One line: Kafka is a distributed, replicated, append-only log. Producers append records to the end of a partition. Consumers read at their own pace by remembering an offset. Nothing is removed when it is read, only when retention says so.
  1. It is a log, not a queue. Records are appended and kept. Reading does not delete. Many readers can read the same data independently.
  2. A topic is split into partitions. A partition is one ordered log. Order is guaranteed only inside a partition, never across the whole topic.
  3. The offset is the position. Each record in a partition has a number: 0, 1, 2... The consumer's "progress" is just a stored offset.
  4. Partitions are the unit of parallelism. In one consumer group, a partition is read by at most one consumer at a time. More partitions means more possible parallel consumers.
  5. Replication gives durability. Each partition has a leader and followers on other brokers. The in-sync replica set (ISR) plus acks and min.insync.replicas decide what "safely written" means.
  6. The key chooses the partition. Same key goes to the same partition, so records of one key stay in order.
  7. Delivery guarantees are built by you. Kafka gives at-least-once by default. Exactly-once needs idempotent producers, transactions, and consumers that tolerate duplicates.
  8. Consumers pull. The consumer asks for data, so a slow consumer does not break the broker. It just falls behind (lag).

1. Why Kafka, the log, topics, partitions and offsets

What is Kafka and what problem does it solve? Basic

What the interviewer is testing: can you describe Kafka beyond "a message queue".

Kafka is a distributed event streaming platform. At its heart it stores streams of records in an append-only, replicated log, and lets many programs write to it and read from it independently. It was built at LinkedIn to move huge volumes of events (page views, logs, metrics) between many systems without every pair of systems needing its own connection. Before it, teams wired each producer to each consumer, which became a tangle. With Kafka, a producer writes once to a topic and any number of consumers read it later, at their own speed. It is used for event-driven microservices, data pipelines, change data capture, stream processing and audit trails. Its strengths are high throughput, durability through replication, replay of old data, and loose coupling between teams.

Likely follow-ups
  • Is it a database? It stores data durably and can be replayed, but it has no query by field and no joins. Use it as a log and a pipe, not as your main query store.
  • How fast is it? Often hundreds of thousands to millions of records per second per cluster, because it does sequential disk writes and batches.
Explain the log abstraction. Why is Kafka a log and not a queue? Intermediate

What the interviewer is testing: the key design idea behind Kafka's speed and replay.

A log is the simplest data structure: you only add to the end, and every entry gets a growing number. In a classic queue, the broker tracks each message and removes it when a consumer acknowledges it. Kafka does not track messages. It just keeps the log, and each consumer remembers one number: the offset of what it read last. That makes reads and writes sequential, which disks do very fast, and makes the broker cheap, because it does not keep per-message, per-consumer state. It also gives you things a queue cannot: replay from any offset, many independent readers, and a new consumer that starts from the beginning. The price is that you cannot delete or reorder one message, and there is no per-message routing or priority. Old data goes away only by retention (time or size) or by compaction.

Likely follow-ups
  • Can a consumer re-read? Yes: seek to an earlier offset or timestamp, or reset the group's offsets.
  • Why is disk not slow? Sequential writes, the OS page cache, batching, and zero-copy sends from page cache to the network.
What are topics and partitions, and why do partitions exist? Basic

What the interviewer is testing: the basic vocabulary and the link between partitions, order and parallelism.

A topic is a named stream of records, like "orders". A topic is split into partitions. Each partition is its own ordered log, stored on one broker as the leader (with copies on others). Partitions exist for two reasons. First, scale: one machine cannot hold or serve all the data, so the topic is spread over many brokers. Second, parallelism: in one consumer group, each partition is read by one consumer, so ten partitions allow up to ten consumers working at once. The cost is that Kafka only promises order inside a partition. Two records in different partitions have no guaranteed order. So you choose a key (like orderId) so that records that must stay in order land in the same partition.

Likely follow-ups
  • Can I reduce partitions later? No, only increase. To shrink you create a new topic and migrate.
  • How many partitions does a topic have by default? Whatever the broker setting num.partitions says, often 1 on a plain install, so set it deliberately.
What is an offset? Who owns it? Basic

What the interviewer is testing: the difference between the record position and the consumer progress.

An offset is a sequence number of a record inside one partition. The broker assigns it when the record is appended. It is unique only within that partition, so the real address of a record is topic, partition, offset. A consumer group keeps its progress as the "committed offset": the offset of the next record it will read. That progress is stored by Kafka in an internal topic called __consumer_offsets, keyed by group, topic and partition. The offset belongs to the group, not the consumer instance, so if a consumer dies, another one in the group continues from the last committed offset. Offsets are not reused and are not guaranteed to be gap-free: transaction markers and compaction can leave holes.

Likely follow-ups
  • What if there is no committed offset? auto.offset.reset decides: latest (default) or earliest or none (throw an error).
  • What if the committed offset has been deleted by retention? The same reset policy applies, because the position is "out of range".
How is a partition stored on disk? What are segments? Intermediate

What the interviewer is testing: storage basics that explain retention, compaction and fast lookup.

A partition is a directory on the broker. Inside, the log is cut into segment files. The newest one is the "active" segment where writes go. When it reaches a size (segment.bytes, default 1 GB) or an age (segment.ms, default 7 days), Kafka closes it and opens a new one. Each segment has a data file (.log), a sparse offset index (.index) and a time index (.timeindex). The file name is the first offset in that segment. To find offset N, Kafka picks the segment by name, uses the index to jump near the position, then scans a little. Retention and compaction work on whole closed segments: Kafka deletes an old segment file in one cheap operation instead of removing records one by one. The active segment is never deleted or compacted, which surprises people who see data "not deleted" after the retention time.

Likely follow-ups
  • Why was my data not deleted after 7 days? The segment must close first and the whole segment must be older than retention (by its newest record).
What is inside a Kafka record? Basic

What the interviewer is testing: practical knowledge of what you can send.

A record has an optional key, a value (the payload, as bytes), a timestamp, and optional headers (small key and value pairs, good for trace ids or schema ids). Kafka itself only sees bytes. Your serializers turn objects to bytes (String, JSON, Avro, Protobuf) and deserializers do the reverse. The key does two jobs: it picks the partition, and it is the identity of the record for log compaction. The timestamp is either the time the producer created the record (CreateTime, default) or the time the broker appended it (LogAppendTime). The default maximum record batch size is about 1 MB (message.max.bytes on the broker, max.request.size on the producer). Big files should go to object storage with only a link in the record.

Likely follow-ups
  • Can a value be null? Yes. A null value on a compacted topic is a "tombstone" meaning delete this key.
Why is Kafka fast even though it writes to disk? Intermediate

What the interviewer is testing: understanding of the performance design, not just a slogan.

There are four main reasons. One: it only does sequential appends, and sequential disk access is far faster than random access, even on spinning disks. Two: it leans on the operating system page cache. A write goes to memory and the OS flushes it later, so recent data is read from memory, not from disk. Replication, not fsync on every message, is what gives durability. Three: batching. Producers send batches, brokers store batches as they are, and consumers fetch batches, so the per-message cost is tiny. Compression is applied on the batch too. Four: zero-copy. For a consumer fetch the broker can send file data from the page cache to the network socket with sendfile, without copying it through the application. One catch: zero-copy does not work when TLS encryption is on, because the data must pass through user space to be encrypted, so TLS costs some throughput.

How does retention work? What controls how long data is kept? Basic

What the interviewer is testing: that data lifetime is a topic setting, not tied to consumption.

By default Kafka keeps records for 7 days (retention.ms, from the broker default log.retention.hours=168), whether or not anyone read them. You can also limit by size with retention.bytes (per partition). Whichever limit is hit first causes old closed segments to be deleted. You can set retention to -1 to keep forever, which is fine for small event-sourcing topics but needs disk planning. The cleanup policy is delete (the default, remove old data) or compact (keep the latest value per key), or both together. Remember the consequence for consumers: if a consumer is down longer than retention, the data it needed is gone and it will hit an out-of-range offset and fall back to auto.offset.reset.

kafka-configs.sh --bootstrap-server b1:9092 --alter \
  --entity-type topics --entity-name orders \
  --add-config retention.ms=259200000      # 3 days
Likely follow-ups
  • Does reading shorten retention? No. Consumption never deletes data.

2. Brokers, replication, ISR and leader election

What is a broker, and how does a cluster spread a topic's partitions? Basic

What the interviewer is testing: the cluster picture, and the idea of leaders per partition.

A broker is one Kafka server process. A cluster is several brokers working together. Each partition has one leader broker and zero or more follower brokers that hold copies. All reads and writes for a partition go to its leader (followers do not serve clients by default; since Kafka 2.4 a consumer can fetch from the closest replica if configured, mostly to save cross-zone traffic). Leaders are spread across brokers so load is balanced: broker 1 may lead partition 0, broker 2 partition 1, and so on. Any broker can answer a metadata request that says who leads what, so clients connect to a few "bootstrap" addresses, learn the full map, then talk straight to the right leaders. A client does not need to know all brokers up front.

Likely follow-ups
  • What is the replication factor? The number of copies of each partition, including the leader. Three is the usual production value.
  • What happens if the leader moves? The client gets a "not leader" error, refreshes metadata and retries, usually automatically.
How does replication work in Kafka? Intermediate

What the interviewer is testing: leader-follower pull replication and the high watermark.

Followers copy data from the leader by sending fetch requests, just like consumers do. The leader appends the record to its log first. Followers fetch it and append it to their own logs, then the next fetch tells the leader how far they have got. The leader tracks the smallest offset that all in-sync replicas have: the high watermark. Consumers can only read records below the high watermark, so they never see a record that could still be lost if the leader failed. A producer with acks=all gets its acknowledgement only when the in-sync replicas have the record. This design means a record is "committed" once every in-sync replica has it, and a committed record survives the loss of the leader as long as one in-sync replica lives.

Likely follow-ups
  • Do followers serve reads? Not by default. Fetch from follower (KIP-392, 2.4+) is optional.
What is the ISR? When does a replica drop out of it? Intermediate

What the interviewer is testing: the core durability concept.

ISR means in-sync replicas: the leader plus the followers that are keeping up. A follower is in sync if it has fetched from the leader recently enough, controlled by replica.lag.time.max.ms (default 30 seconds). If a follower is slow, stuck in a long garbage collection pause, or its broker is down, the leader removes it from the ISR. When it catches up again it is added back. The ISR shrinks and expands automatically. This matters because only ISR members can become the new leader (by default), and because acks=all waits for the ISR, not for all replicas. So if the ISR shrinks to just the leader, acks=all alone means the same as acks=1. That is the reason min.insync.replicas exists.

Likely follow-ups
  • What does an under-replicated partition mean? Its ISR is smaller than its replication factor. It is a warning sign to watch.
Explain acks and min.insync.replicas together. How do you get "no data loss"? Senior

What the interviewer is testing: the most asked Kafka durability question. Many answer only half.

acks is set on the producer and says when the broker answers success. acks=0: the producer does not wait at all, fastest, you may lose data silently. acks=1: the leader answers after writing to its own log; if the leader dies before followers copy the record, it is lost. acks=all (or -1): the leader answers when all current ISR members have the record. min.insync.replicas is set on the topic or broker and says the smallest ISR size for which a write is accepted. If the ISR is smaller, the broker rejects acks=all writes with NotEnoughReplicas. The classic safe setup is replication factor 3, min.insync.replicas=2, acks=all. Then a write is on at least two brokers before you get success. You survive one broker loss with no data loss and still accept writes. If two brokers go, writes stop, which is the right choice if loss is worse than downtime. Also disable unclean leader election, and make the producer retry and be idempotent.

# topic level
kafka-configs.sh --bootstrap-server b1:9092 --alter --entity-type topics \
  --entity-name payments --add-config min.insync.replicas=2

# producer
acks=all
enable.idempotence=true
retries=2147483647
delivery.timeout.ms=120000
Likely follow-ups
  • What if min.insync.replicas equals the replication factor? One broker down stops all writes. Usually a bad trade.
  • Does acks=all with min ISR 2 guarantee no loss in every case? Almost: it can still lose data if all ISR members fail together before flush to disk, or if unclean election is on.
Common mistakes: saying acks=all means "all replicas" (it means all in-sync replicas); forgetting min.insync.replicas; leaving it at the default of 1.
What happens when a partition leader broker dies? Intermediate

What the interviewer is testing: failover flow and what clients see.

The cluster controller (one broker elected to manage metadata; in KRaft mode it is the active quorum controller) notices that the broker is gone. For each partition that the broker led, it chooses a new leader from the ISR, usually the first live replica in the replica list, and publishes the new metadata. Followers start fetching from the new leader. Clients that were talking to the old leader get errors like NotLeaderOrFollower or a timeout, refresh their metadata, and retry against the new leader. With idempotent producers the retry does not create duplicates. The failover typically takes from a fraction of a second to a few seconds. Because the new leader is an ISR member, it has all committed records, so no committed data is lost. When the dead broker returns, it becomes a follower, truncates any records beyond what the leader has, and catches up. Later, preferred leader election can move leadership back so load is balanced again.

Likely follow-ups
  • What if the ISR is empty? Then no leader can be elected and the partition is offline, unless unclean election is enabled.
What is unclean leader election and when would you allow it? Senior

What the interviewer is testing: the consistency versus availability trade-off.

Normally only an in-sync replica can become leader. Suppose all ISR members are down and only an out-of-sync follower is alive. The partition has no valid leader, so it is unavailable. With unclean.leader.election.enable=true Kafka lets that stale follower become leader. The partition comes back at once, but any records the stale replica did not have are lost, and consumers may even see offsets rewind in unusual cases. The default is false (since 0.11). You choose it by what you value. For payments, orders or audit data, keep it false and accept downtime. For metrics or click logs where freshness matters more than a few lost points, true can be acceptable. It is a topic-level setting, so you can set it per topic.

What is the controller, and what is the high watermark versus the log end offset? Senior

What the interviewer is testing: two vocabulary items that senior engineers use during incident calls.

The controller is the part of the cluster that makes metadata decisions: which broker is alive, who leads each partition, when topics are created. In old ZooKeeper clusters one broker was elected controller through ZooKeeper. In KRaft clusters a small quorum of controller nodes holds the metadata in a Raft-replicated log, and one is the active leader. The log end offset (LEO) is the offset of the next record to be written on a given replica, so it shows how far that replica has copied. The high watermark (HW) is the lowest LEO across the in-sync replicas. Consumers read only below the HW. The gap between leader LEO and HW is data that exists but is not yet committed. When you hear "the follower lag is growing", it means the follower's LEO is falling behind the leader's.

How many brokers and what replication factor would you pick, and why does rack or zone awareness matter? Intermediate

What the interviewer is testing: sensible production defaults, from a developer view.

A common production choice is three brokers or more, replication factor 3 and min.insync.replicas=2. With replication factor 3 you can lose one broker and keep writing and reading with no data loss. You cannot have a replication factor above the number of brokers. Rack awareness (broker.rack) tells Kafka which zone each broker is in so that the replicas of a partition are placed in different zones. Without it, all three copies could sit in one zone and one zone outage would take the partition down. Across three availability zones with replication factor 3, one zone can fail and the topic stays fully available. A developer's job is to ask for a replication factor of 3 and a sensible min ISR when creating topics, and not to leave topics at the default of 1 copy. Cluster sizing and tuning belong to the platform team.

3. Producers: batching, keys, idempotence, ordering

What happens inside the producer when you call send()? Intermediate

What the interviewer is testing: do you know that send is asynchronous and batched, which explains latency and loss questions.

send() does not write to the network at once. First the record is serialized (key and value) and the partitioner picks a partition. The record is then put into a per-partition batch in a memory buffer (buffer.memory, default 32 MB). A background sender thread collects ready batches, groups them per broker, and sends them. A batch is sent when it is full (batch.size, default 16 KB) or when it has waited linger.ms. When the broker answers, the producer completes the future or calls your callback. If the buffer is full, send() blocks up to max.block.ms (default 60 seconds) and then throws. Because it is asynchronous, a process crash right after send() returns can lose records still in the buffer unless you call flush() or close().

Likely follow-ups
  • Is send() blocking? Mostly not, except when metadata is missing or the buffer is full.
  • How do I make it synchronous? Call get() on the returned future. This kills throughput, so avoid it for bulk data.
How do batch.size, linger.ms and compression affect throughput and latency? Intermediate

What the interviewer is testing: the throughput versus latency trade-off, which you tune daily.

Sending one record per network request is wasteful. A batch groups many records for one partition into one request. batch.size is the maximum bytes of one batch (default 16 KB). linger.ms is how long the sender waits for more records before sending a not-yet-full batch. With linger.ms=0 (the default up to Kafka 3.x) records go out as soon as the sender is free, so batches are still formed under load but are small under light traffic. Setting linger.ms to 5 to 20 ms and a larger batch.size (64 KB or more) gives bigger batches, better compression, fewer requests, and much higher throughput, at the cost of a few milliseconds of latency. compression.type (lz4, snappy, zstd, gzip) compresses the whole batch, so bigger batches compress better. Typically lz4 is a fast choice and zstd gives the best ratio. Compression saves network and disk, and the broker stores the batch compressed unless the topic uses a different codec.

Likely follow-ups
  • Does a larger batch.size waste memory? Only as needed: a batch buffer is allocated per active partition, so many partitions times a large batch uses more memory.
  • Where is compression done? On the producer. Consumers decompress.
How does a producer choose the partition? Basic

What the interviewer is testing: keys, ordering and hot partitions all start here.

There are three cases. If you set a partition number on the record, that is used. If the record has a key, the default partitioner hashes the key bytes with murmur2 and takes it modulo the number of partitions, so the same key always goes to the same partition. If there is no key, the producer uses a "sticky" approach (since 2.4, improved in 3.3): it fills a batch for one partition, then switches to another. This gives even spread with large batches. Because the formula uses the partition count, adding partitions later changes where keys go, which can break ordering for existing keys. You can write a custom Partitioner if you need special routing, for example to send one big tenant to a dedicated set of partitions.

Likely follow-ups
  • What if the key is null? The records spread across partitions with no ordering link between them.
What is an idempotent producer and what exactly does it protect against? Senior

What the interviewer is testing: the difference between producer retry duplicates and application duplicates.

Imagine the producer sends a batch, the broker writes it, but the acknowledgement is lost in the network. The producer times out and retries. Without protection the batch is written twice. With enable.idempotence=true the broker gives the producer a unique producer id (PID), and each batch carries a per-partition sequence number. The broker remembers the last sequences for each PID and partition, and drops a batch it has already stored, but still acknowledges it. It also rejects out-of-order sequences. The result: no duplicates and no reordering caused by retries, within one producer session and one partition. It is on by default since Kafka 3.0 (needs acks=all, and up to 5 in-flight requests). What it does NOT cover: a crash and restart of your application gives a new PID, so your code re-sending the same business event twice still produces two records. For that you need transactions, or consumer-side deduplication by a business id.

enable.idempotence=true            # default since 3.0
acks=all
max.in.flight.requests.per.connection=5   # up to 5 is safe with idempotence
Likely follow-ups
  • Does it work across partitions? The guarantee is per partition and per producer session.
  • Does it cost much? Very little: a few bytes of sequence data per batch.
Common mistakes: saying idempotence gives exactly-once end to end. It only removes duplicates caused by the producer's own retries.
Does retrying a failed send break ordering? What about max.in.flight.requests? Senior

What the interviewer is testing: an old, well-known gotcha.

The producer may have several unacknowledged requests "in flight" to one broker (max.in.flight.requests.per.connection, default 5). Suppose batch 1 fails and batch 2 succeeds. If batch 1 is retried, it now lands after batch 2, so the order is wrong. In old setups the advice was to set in-flight to 1, which hurts throughput. With the idempotent producer, the broker checks sequence numbers, so it rejects batch 2 until batch 1 arrives, and the producer keeps the correct order, even with up to 5 in flight. So the modern answer: turn on idempotence (default now), keep in-flight at 5 or lower, and ordering within a partition is kept even under retries. If you disable idempotence and still need order, set in-flight to 1.

Which producer errors are retried, and what do retries and delivery.timeout.ms do? Intermediate

What the interviewer is testing: modern timeout semantics, instead of fiddling with a retry count.

Retriable errors are temporary: leader changed, network failure, NotEnoughReplicas, request timeout. Non-retriable errors are permanent: record too large, invalid topic, serialization failure, authorization failure. The producer retries retriable errors by itself. Since Kafka 2.1 the real limit is delivery.timeout.ms (default 2 minutes): the total time from send() returning until success or failure is reported. retries defaults to a huge number (Integer.MAX_VALUE), so time, not count, ends it. Related: request.timeout.ms (default 30 s) is the wait for one request, and retry.backoff.ms is the pause between tries. When the delivery timeout expires, your callback gets an exception, and your code must decide: log, retry at application level, store it for later, or fail the business operation. Never ignore the callback.

producer.send(record, (meta, ex) -> {
    if (ex != null) {
        log.error("send failed key={}", record.key(), ex);
        // store in outbox / alert / fail the request
    }
});
What are serializers and why do they matter in practice? Basic

What the interviewer is testing: awareness that Kafka stores bytes and the contract lives in your code.

Kafka only moves bytes. A serializer turns your key or value object into bytes on the producer, and a deserializer turns it back on the consumer. Built in: String, Integer, Long, ByteArray. For objects you pick JSON, Avro or Protobuf. Plain JSON is easy but has no enforced schema, so a producer can change a field name and silently break every consumer. Avro and Protobuf with a Schema Registry give a checked contract and smaller payloads. A real incident cause: a consumer's deserializer throws on one bad record, and because it fails inside poll(), the consumer loops forever on the same offset. Always plan for deserialization failure (see poison pill).

Which producer settings would you set for a reliable, fast service? Intermediate

What the interviewer is testing: practical config sense, not memorised defaults only.

For a durable pipeline I set: acks=all, enable.idempotence=true, a topic with replication factor 3 and min.insync.replicas=2, and keep the default huge retries with a clear delivery.timeout.ms. For throughput I add linger.ms of 5 to 20, batch.size of 64 KB to 256 KB, and compression.type=lz4 or zstd. I set client.id so brokers' logs and quotas show who is who. I always handle the send callback. For very small low-latency flows I keep linger at 0. I also check max.request.size against my biggest record. I do not tune the buffer memory until I see "buffer exhausted" errors, which signal that the producer produces faster than brokers can accept.

When would you write a custom partitioner, or avoid keys altogether? Senior

What the interviewer is testing: design judgment around skew and ordering needs.

I would write one when the default hash gives a bad spread or when I need business routing. Example: one huge tenant produces 60 percent of traffic and one partition cannot keep up. A custom partitioner can spread that tenant over several partitions by using tenant plus a sub-key (like customer id), accepting that order is kept only per sub-key. Another case is sending priority traffic to specific partitions. I would avoid keys when no record depends on another one, such as independent click events: a null key gives the best spread and batching. The rule: use a key only if there is a real ordering or grouping requirement, and pick the smallest key that gives the order you need, because a broader key means bigger hot spots.

4. Consumers, consumer groups, rebalancing and offset commits

What is a consumer group and how are partitions assigned? Basic

What the interviewer is testing: the scaling model on the consumer side.

A consumer group is a set of consumers that share one group.id and work together to read a topic. Kafka gives each partition to exactly one consumer in the group at a time. So with 6 partitions and 3 consumers, each gets 2. With 6 consumers each gets 1. With 8 consumers, 2 sit idle, because a partition cannot be split. So the partition count is the upper limit of parallelism. Different groups are independent: a "billing" group and a "search" group each get every record and keep their own offsets. This one design gives both queue behaviour (one group, work shared) and publish and subscribe behaviour (many groups, each gets all).

Likely follow-ups
  • Can two consumers in a group read one partition? No. If you need that, use more partitions or a different design.
  • How do I read without a group? assign() partitions manually; no rebalancing and no group management.
How does the consumer poll loop work, and what are max.poll.interval.ms and session.timeout.ms? Intermediate

What the interviewer is testing: the two liveness checks, which cause most rebalance trouble.

A consumer runs a loop: call poll(timeout), process the returned records, commit offsets, repeat. There are two separate liveness checks. A background heartbeat thread sends heartbeats to the group coordinator every heartbeat.interval.ms (default 3 s). If the coordinator hears nothing for session.timeout.ms (default 45 s since 3.0, earlier 10 s), it declares the consumer dead and rebalances. Separately, the consumer must call poll() again within max.poll.interval.ms (default 5 minutes). If your processing of a batch takes longer, the consumer is considered stuck, leaves the group, and a rebalance starts, even though heartbeats were fine. max.poll.records (default 500) limits how many records one poll returns, so you can shrink the batch so processing fits inside the interval.

while (running) {
    ConsumerRecords<String,String> recs = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String,String> r : recs) process(r);
    consumer.commitSync();     // after processing = at-least-once
}
Likely follow-ups
  • Why two checks? Heartbeat detects a dead process. The poll interval detects a live but stuck processing thread.
  • Is the consumer thread-safe? No. One consumer per thread. Hand work to workers carefully, and commit only after they finish.
What is a rebalance, and why can it hurt? Eager versus cooperative? Senior

What the interviewer is testing: the most common source of production consumer problems.

A rebalance is the group re-deciding who owns which partitions. It happens when a consumer joins, leaves, crashes, misses the poll interval, or when topic partitions change. In the classic eager protocol, every consumer first gives up all its partitions ("stop the world"), then all rejoin and receive a new assignment. During that pause nobody processes, lag builds up, and consumers lose in-memory state or caches. In the cooperative incremental protocol (CooperativeStickyAssignor, since 2.4), only the partitions that must move are revoked, over two short rounds; the other consumers keep working. Since Kafka 3.0 the default assignor list is Range plus CooperativeSticky, so a rolling upgrade to cooperative is possible. Kafka 4.0 brings the new consumer group protocol (KIP-848, set group.protocol=consumer) where the broker computes the assignment and there is no global barrier, so rebalances are much smoother. To reduce pain: use cooperative or the new protocol, use static membership (group.instance.id) so a restart does not trigger a rebalance, keep processing within max.poll.interval.ms, and do rolling restarts slowly.

Likely follow-ups
  • What is static membership? A fixed group.instance.id lets a consumer restart within session.timeout.ms and get its partitions back without a rebalance.
  • What does a "rebalance storm" look like? Repeated rebalances, lag growing, logs full of "rebalance in progress" and "commit failed". See the scenarios.
What partition assignment strategies exist? Intermediate

What the interviewer is testing: breadth, and why "sticky" matters.

Range assigns consecutive partitions of each topic to consumers; with several topics it can give the first consumers more work. RoundRobin spreads all partitions evenly. Sticky is even like round robin but tries to keep existing assignments when the group changes, so fewer partitions move. CooperativeSticky is the same but uses the incremental protocol, avoiding stop-the-world. You set them with partition.assignment.strategy. Moving a group from eager to cooperative needs two rolling restarts: first add the cooperative assignor alongside the old one, then remove the old one. With the new KIP-848 protocol in 4.0 the broker does the assignment with server-side assignors (uniform or range) and the client setting is no longer used.

How do offset commits work? Auto commit versus manual, sync versus async. Intermediate

What the interviewer is testing: where duplicates and losses come from on the consumer side.

Committing an offset tells Kafka "this group has processed everything before this offset". After a crash the group restarts from the last commit. With enable.auto.commit=true (default) the consumer commits the offsets returned by the last poll() every 5 seconds, inside the next poll call. The risk: it can commit records you have fetched but not finished processing, so a crash loses them (at-most-once), or you can crash after processing but before the commit, so they are processed again (duplicates). For control, turn auto commit off and commit yourself after processing succeeds. commitSync() blocks and retries until success, simplest and safest. commitAsync() is faster but does not retry (a retry could commit an older offset over a newer one), so a common pattern is async in the loop and one sync commit on shutdown. You can commit exact offsets per partition for fine control. Commit the offset of the next record to read, which is last processed offset plus 1.

consumer.commitSync(Map.of(
    new TopicPartition("orders", 0),
    new OffsetAndMetadata(lastProcessedOffset + 1)));
Likely follow-ups
  • Commit per record or per batch? Per batch is cheaper. Per record is safer for slow, side-effect-heavy work but costs more requests.
  • Where are commits stored? In the __consumer_offsets topic (50 partitions by default).
Common mistakes: committing offset N instead of N+1 (re-reads one record); committing before processing; leaving auto commit on with slow async processing.
What do you do in a ConsumerRebalanceListener? Senior

What the interviewer is testing: safe handling of ownership change.

The listener has two callbacks. onPartitionsRevoked runs before partitions are taken away. This is the last chance to finish or flush in-flight work and commit the offsets for exactly those partitions, so the next owner does not redo them. onPartitionsAssigned runs after you receive partitions; here you can load state or seek to a position stored in your own database. With the cooperative protocol the callbacks are about only the moved partitions, and there is also onPartitionsLost for the case where the group already took them away (for example after a session timeout), where committing is no longer possible and you should just drop local state. If you process asynchronously with a thread pool, you must wait for in-flight tasks of the revoked partitions in this callback, otherwise the new owner and the old worker both process the same records.

How can a consumer rewind, replay or skip data? Intermediate

What the interviewer is testing: practical use of the log for recovery and backfill.

In code you can call seek(partition, offset), seekToBeginning, seekToEnd, or offsetsForTimes to find the offset for a timestamp and seek there. From the command line, with the group stopped, kafka-consumer-groups.sh --reset-offsets can move a group to earliest, latest, a timestamp, a shift, or a specific offset. Use --dry-run first, then --execute. Typical uses: replay the last 2 hours after a bug fix, skip a poison record by moving one offset forward, or start a new consumer group from the beginning for a backfill. Replaying means side effects happen again, so the consumer must be idempotent.

kafka-consumer-groups.sh --bootstrap-server b1:9092 --group billing \
  --topic orders --reset-offsets --to-datetime 2026-11-17T08:00:00.000 --dry-run
What is consumer lag and how do you measure it? Basic

What the interviewer is testing: the number every Kafka dashboard shows, and whether you read it correctly.

Lag for one partition is the log end offset minus the group's committed offset: how many records are waiting that the group has not yet processed. Total lag is the sum across partitions. You see it with kafka-consumer-groups.sh --describe --group X, or through monitoring tools (Burrow, the consumer's own records-lag-max metric, or exporters to Prometheus). A small steady lag is normal. What matters is the trend: growing lag means consumers are slower than producers. Lag in records is not the same as delay in time, so some teams also track "time lag", the age of the oldest unprocessed record. Also look per partition: one partition with big lag and others at zero points to a hot partition or one stuck consumer.

5. Delivery semantics, exactly-once and transactions

Explain at-most-once, at-least-once and exactly-once delivery in Kafka. Intermediate

What the interviewer is testing: one of the top three Kafka questions. A clear, honest answer stands out.

At-most-once: a record is processed zero or one time. You commit the offset before processing; if you crash in between, the record is lost. Fine for non-critical metrics. At-least-once: a record is processed one or more times. You process, then commit; if you crash in between, the record is read again, so you may see duplicates. This is the normal default and what most systems use, with idempotent handling. Exactly-once: the effect happens once. Kafka offers this inside Kafka (read from topic, write to topic, commit offset, all atomically with transactions). For side effects outside Kafka (email, a database, a payment API), true exactly-once is not possible by the broker alone. You get the same result by making the operation idempotent, or by storing the offset and the result in one database transaction. The honest summary: exactly-once is "at-least-once delivery plus idempotent processing".

Likely follow-ups
  • Which is the default behaviour? At-least-once, if you commit after processing.
  • Why can the broker not give exactly-once to my REST call? Because the call and the commit are two systems and Kafka cannot make them one atomic step.
How do Kafka transactions work, and what do isolation.level and transactional.id do? Senior

What the interviewer is testing: do you really know how exactly-once is built, including its limits.

A transactional producer has a stable transactional.id. It calls initTransactions(), then beginTransaction(), sends records to one or more topics and partitions, can call sendOffsetsToTransaction() to include the consumer's input offsets, then commitTransaction() or abortTransaction(). A transaction coordinator on a broker tracks its state in an internal topic, __transaction_state. On commit it writes a commit marker into every partition touched, so the writes become visible together. The same transactional.id after a restart bumps an epoch, which fences out the old "zombie" instance, so two copies cannot both commit. Consumers choose isolation.level: read_uncommitted (default) sees everything including aborted records; read_committed sees only committed transactional records, and it waits at the "last stable offset", so one long open transaction can delay readers. Limits: it covers only Kafka reads and writes; it adds some latency; and aborted data still occupies the log until retention.

producer.initTransactions();
while (true) {
  var recs = consumer.poll(Duration.ofMillis(500));
  producer.beginTransaction();
  try {
    for (var r : recs) producer.send(new ProducerRecord<>("out", r.key(), transform(r.value())));
    producer.sendOffsetsToTransaction(offsetsOf(recs), consumer.groupMetadata());
    producer.commitTransaction();
  } catch (Exception e) { producer.abortTransaction(); }
}
Likely follow-ups
  • What are zombies? An old instance that is paused or partitioned from the cluster and wakes up later. The epoch makes its writes fail with ProducerFencedException.
  • What does Kafka Streams use? processing.guarantee=exactly_once_v2 (since 3.0), which is built on this.
Is "exactly-once" in Kafka really exactly once? Where does it stop? Senior

What the interviewer is testing: honesty about guarantees and awareness of the external side effect problem.

It is exactly-once for the pipeline that lives entirely inside Kafka: read from topics, compute, write to topics, with offsets committed in the same transaction. Each input record affects the output exactly once, even across crashes. It stops at the edge of Kafka. If your code calls a payment API, writes to a database or sends an email inside the loop, that action is not part of the Kafka transaction. If the transaction aborts and the record is processed again, the action happens twice. For those cases you make the external operation idempotent: pass an idempotency key to the API, use an upsert or a unique constraint in the database, or store the processed id. For database sinks you can also store the consumer offset in the same database transaction as the result, and on restart seek to that stored offset, which gives exactly-once effect without Kafka transactions.

How do you build an idempotent consumer? Senior

What the interviewer is testing: the practical answer to "how do you avoid duplicate processing".

Assume every record can arrive twice, because rebalances, retries and restarts will cause it. The goal is that handling it twice has the same effect as once. There are four common techniques. First, natural idempotence: operations like "set status to SHIPPED" or an upsert by primary key are safe to repeat. Second, a dedup table: each record has a unique business id (or topic, partition and offset); in the same database transaction as the business change, insert that id into a processed_events table with a unique constraint. A duplicate hits the constraint and is skipped. Third, version checks: only apply an event if its version is higher than the stored one. Fourth, idempotency keys when calling other services. The key point is atomicity: the dedup check and the effect must be in one transaction, otherwise a crash between them reopens the gap. Keep the dedup table small by expiring old ids after a window longer than your maximum replay time.

@Transactional
void handle(OrderEvent e) {
  if (!processedRepo.insertIfAbsent(e.eventId())) return;  // unique key, duplicate skipped
  orderRepo.apply(e);
}
Likely follow-ups
  • Can I use offset as the dedup key? Yes within one topic and partition, if the producer does not re-publish duplicates. A business id also protects against producer-side duplicates.
Where can a Kafka message be lost end to end? Senior

What the interviewer is testing: systematic thinking across producer, broker and consumer.

I walk the path in three places. Producer: acks=0 or 1; no callback checking; the process exits before flush(); retry budget exhausted with the error ignored; a non-retriable error such as record too large. Broker: replication factor 1; min.insync.replicas=1 with acks=all, so only one copy exists; unclean leader election; losing all ISR brokers at once; retention that deletes data before slow consumers read it. Consumer: auto commit marks records done before they are processed; manual commit placed before processing; processing handed to a thread pool and offsets committed before the threads finish; swallowing an exception and moving on; skipping a failed record without a dead-letter topic. A good answer ends with a safe recipe: acks=all, replication 3, min ISR 2, no unclean election, handle callbacks, commit after processing.

Where do duplicates come from in a Kafka system? Intermediate

What the interviewer is testing: root cause thinking before fixes.

Duplicates have a few common causes. On the producer: an acknowledgement was lost and the producer retried (fixed by idempotence); the application itself sent the same event twice after a crash or a user double-click (needs a business id). On the consumer: a rebalance happened after processing but before the commit, so the next owner re-reads those records; a crash in the same gap; max.poll.interval.ms exceeded so the group kicked the consumer, whose uncommitted work is redone elsewhere; an offset reset or replay by an operator. Upstream, a source connector can re-deliver after a restart. The answer is rarely "stop duplicates at the source". It is "make the consumers idempotent", and reduce the gap by committing promptly and handling rebalances in the listener.

6. Retries, dead-letter topics, poison pills, lag and backpressure

What is a poison pill message and how do you handle it? Intermediate

What the interviewer is testing: resilience: one bad record must not stop a whole partition.

A poison pill is a record that always fails: a broken payload that cannot be deserialized, a value that triggers a bug, or a business rule violation. Because a partition is processed in order, the consumer cannot skip it unless you tell it to. Without handling, it throws, the offset is not committed, the consumer polls again, gets the same record, and loops forever. The partition is stuck and lag climbs. The fix has layers. For deserialization errors, wrap the real deserializer in an error-handling one (Spring's ErrorHandlingDeserializer) so the failure becomes a value you can route, not an exception inside poll(). For processing errors, retry a few times with backoff for temporary problems, then publish the record, with the error reason in headers, to a dead-letter topic (DLT), commit the offset, and move on. Alert on DLT traffic and keep a way to inspect and replay.

Likely follow-ups
  • Skip or send to DLT? Skipping silently loses data. A DLT keeps it for analysis and replay.
  • Which errors should not be retried? Permanent ones: bad schema, validation failure, not found.
Design a retry and dead-letter strategy for a consumer. Senior

What the interviewer is testing: the trade-off between blocking retries and non-blocking retry topics.

First split errors into temporary (database down, timeout from another service) and permanent (bad data). Permanent errors go straight to the DLT. For temporary errors there are two styles. Blocking retry: retry in place with a backoff (for example 1 s, 2 s, 4 s, 5 attempts) before moving on. It keeps order, but it stalls the whole partition while waiting, and a long backoff risks max.poll.interval.ms. Non-blocking retry topics: on failure, publish the record to orders-retry-1 (delay 1 min), then orders-retry-2 (10 min), and finally orders-dlt. The main topic keeps flowing. The cost is that order is lost for the retried records, and you need separate consumers or delayed handling. I choose blocking retries for short blips where order matters, and retry topics for slower recovery where throughput matters. Always include in headers the original topic, partition, offset, exception text and attempt count, and keep a runbook for replaying the DLT after a fix.

Likely follow-ups
  • How do you "delay" in a retry topic? The consumer reads the record's timestamp, and pauses the partition until the delay has passed (Spring Kafka's @RetryableTopic does this for you).
Consumer lag keeps growing. How do you approach it? Senior

What the interviewer is testing: structured diagnosis, rather than "add consumers".

First, find out whether lag is on all partitions or a few. All partitions growing means the group is too slow or producers spiked. One partition means a hot key or one stuck consumer. Second, check whether the consumers are alive and stable, or are in a rebalance loop (see group state with --describe --state). Third, find the bottleneck in processing time per record: a slow database call, a blocking HTTP call, a lock. Add timing metrics around the handler. Then act. If processing is I/O bound, use more consumers up to the partition count, or process records of one batch in parallel with a worker pool (keeping per-key order and commits correct). If partitions are fewer than needed, increase partitions (with the key-order caveat). Tune fetch.min.bytes, max.poll.records and batch the database writes. Last, if the spike is short, lag may drain by itself. Never just raise consumer count beyond partitions: extras stay idle.

Kafka consumers pull. How do you handle backpressure and slow downstream systems? Senior

What the interviewer is testing: flow control without losing data or getting kicked out of the group.

Because consumers pull, Kafka gives natural backpressure: a slow consumer simply reads less and lag grows, while the broker is unaffected. The danger is inside your process. If you poll fast and push records into an unbounded in-memory queue for worker threads, memory grows and you may crash. So bound the queue. If the downstream (a database or an API) is slow or down, use consumer.pause(partitions): keep calling poll() so heartbeats and the poll interval stay healthy, but get no new records. Resume with resume() when the downstream recovers. Spring Kafka's listener container does this for you in its container-level pause. Also cap max.poll.records and fetch.max.bytes, add a circuit breaker around the downstream call, and set rate limits. On the producing side, a full producer buffer makes send() block, which also slows the producer naturally; quotas on brokers can throttle noisy clients.

One consumer thread is too slow for one partition. How do you process faster without breaking order? Senior

What the interviewer is testing: how to get parallelism beyond the partition count safely.

The first option is simply more partitions and consumers, which is the cleanest. If that is not possible, parallelize inside the consumer. Poll a batch, split records by key (or by key hash into N lanes) and give each lane to a worker, so records of the same key run in order on the same lane, and different keys run in parallel. Then wait for all lanes of that batch to finish before committing the highest offsets that are fully done. The hard parts are partial failures (commit only up to the lowest unfinished offset) and rebalances (finish or drop work in onPartitionsRevoked). Libraries like Confluent's Parallel Consumer implement this model. Another approach is to make each record cheaper: batch database inserts, make calls asynchronous with bounded concurrency. Say the trade-off clearly: more complexity and more duplicates after a crash, so the handler must be idempotent.

Which consumer settings affect throughput and latency? Intermediate

What the interviewer is testing: practical knobs and what they trade.

fetch.min.bytes (default 1) and fetch.max.wait.ms (default 500) say how much data the broker should gather before answering a fetch. Raising min bytes gives bigger, more efficient fetches but adds latency. max.partition.fetch.bytes (default 1 MB) and fetch.max.bytes (default 50 MB) cap the size. max.poll.records (default 500) caps the records per poll, which you tune to fit processing time inside the poll interval. auto.offset.reset sets what to do with no valid offset. isolation.level sets whether to see uncommitted transactional data. session.timeout.ms, heartbeat.interval.ms and max.poll.interval.ms control liveness. Start with defaults, then change one thing at a time while watching lag and processing time.

7. Ordering, partition-count design, compaction, hot partitions

What ordering does Kafka guarantee, and how do you design for "process orders in order"? Intermediate

What the interviewer is testing: the exact wording of the guarantee, and design from it.

Kafka guarantees that records sent by one producer to the same partition are appended in the order sent, and consumers read a partition in offset order. It does not guarantee order across partitions, and it does not order records from different producers except by arrival. So to keep order for one entity, make sure all of its records go to one partition by using the entity id as the key (for example orderId or accountId). Then a single consumer processes that partition in order. You need three things to hold together: the same key, an idempotent producer (so retries do not reorder), and sequential processing per partition on the consumer side (no free-for-all thread pool). If you truly need global order for a whole topic, you need one partition, which caps throughput to one consumer. Most designs avoid global order and settle for per-key order.

Likely follow-ups
  • Two services produce events about the same order. Order between them? Only arrival order at the leader. If order matters, route both through one producer or add a version number and let the consumer ignore stale ones.
How do you decide how many partitions a topic needs? Senior

What the interviewer is testing: capacity thinking and awareness that you cannot easily undo the choice.

Start from the target throughput. Measure what one consumer can handle per partition (say 10 MB/s or 2,000 records/s of your real work) and what one producer partition can take. Partitions needed is about target throughput divided by the smaller of those, then add headroom (often 2x to 3x) for growth, because you can add partitions later but doing so breaks key placement. Also consider the maximum consumer parallelism you want to allow later, since consumers cannot exceed partitions. The costs of too many partitions: more open files and memory on brokers, longer leader election and recovery, more replication traffic, bigger end-to-end latency with many small batches, and more rebalance work. Typical sensible topic sizes are 6 to 50 partitions; thousands per topic is rare. For ordering-sensitive topics, pick the number up front and plan to never change it.

What happens to ordering if you add partitions to a topic that uses keys? Senior

What the interviewer is testing: a classic trap tied to the key hash formula.

The default partitioner computes hash(key) mod partitionCount. When the count changes from 6 to 12, many keys now map to a different partition. Old records for key K are still in the old partition, and new records for K go to a new partition. Two consumers may now process K at the same time, and the new records can be processed before older ones that are still sitting in lag in the old partition. Order for that key is broken during the transition, and stateful consumers (Kafka Streams state, caches keyed by partition) may need rebuilding. Ways to handle it: plan enough partitions at the start; add partitions only when the topic is drained (lag zero) and producers paused if order matters; or create a new topic with the larger count, dual-write or migrate with a mirror, and switch consumers over. Also, a compacted topic can end up with the same key in two partitions, so compaction no longer keeps just one latest record across the topic.

What is a hot partition and how do you fix it? Senior

What the interviewer is testing: data skew awareness.

A hot partition gets much more traffic than the others, usually because of key skew: one customer, one tenant or one popular product generates most events, or a bad key (like a country code with a few values) hashes unevenly. Symptoms: one partition's lag grows while others are near zero, one broker has high CPU or disk, and one consumer is always busy. Fixes, from cheapest: choose a higher-cardinality key (orderId instead of customerId) if you do not need per-customer order. Add a salt for a known heavy key (key = tenant + "-" + (hash(entity) mod 8)) and accept order only per sub-key. Use a custom partitioner that spreads the heavy key. Split the heavy tenant into its own topic with more partitions. For the consumer side, process one partition's records in parallel by key lanes. Measure first with per-partition bytes-in and lag, because the guess is often wrong.

What is log compaction, and when would you use it? Intermediate

What the interviewer is testing: the second cleanup mode, and the "latest value per key" idea.

With cleanup.policy=compact, Kafka does not delete by age. A cleaner thread rewrites closed segments and keeps only the most recent record for each key, removing older ones. The topic becomes a changelog that always holds at least the last value of every key, so a new consumer can read it from the start and rebuild the full current state (a table). Typical uses: current state of entities (user profile, product price), a cache or lookup table topic, Kafka's own __consumer_offsets, and Kafka Streams changelog topics. Compaction is eventual, not instant: the active segment is not compacted, and old duplicates stay until the cleaner runs (tunable with min.cleanable.dirty.ratio and min.compaction.lag.ms). Records need a key; a record without a key cannot go to a compacted topic. Order of the surviving records is kept, and offsets do not change, so gaps appear.

Likely follow-ups
  • How do I delete a key? Send a record with that key and a null value (a tombstone). It stays for delete.retention.ms (default 24 h) so consumers can see it, then is removed.
  • Can a topic use both policies? Yes: compact,delete, which compacts and also deletes by age.
How do you design topics for a new domain: one topic per event type or one big topic? Senior

What the interviewer is testing: design thinking about ordering, schemas and consumers.

The deciding question is ordering. Events that must be processed in order relative to each other (OrderCreated, OrderPaid, OrderShipped for the same order) belong in one topic keyed by the order id, because order exists only inside one partition. Putting them in separate topics loses that order. Events of unrelated types, with different consumers, different volume and different retention, go in separate topics. A topic per entity type ("orders", "payments") keyed by entity id is a good default. Name topics clearly (domain.entity.event.v1 style conventions). Choose the key, partition count and retention deliberately. Decide whether the topic is an event stream (delete by time) or entity state (compacted). Keep payloads self-describing with a schema and a version, and plan for evolution rather than one topic per schema version. Avoid "one topic for everything", which forces every consumer to read and discard what it does not need.

8. Schema Registry, Avro and schema evolution

What is the Schema Registry and why use Avro or Protobuf instead of plain JSON? Intermediate

What the interviewer is testing: contract management between teams.

The Schema Registry is a separate service that stores versions of schemas and gives each a numeric id. A producer registers (or looks up) its schema, then writes each record as a magic byte, the 4-byte schema id, and the compact binary body. The consumer reads the id, fetches the schema from the registry once (and caches it), and decodes. Benefits: records are small because field names are not repeated; every record can be decoded; and the registry can check that a new schema is compatible with older versions before it is accepted, so a bad change is rejected at deploy time instead of breaking consumers at 3 a.m. Plain JSON has no such contract: any producer can rename a field silently. The cost is an extra service to run, a dependency at start-up, and some tooling friction. Avro, Protobuf and JSON Schema are all supported by the Confluent registry (and compatible registries).

Explain schema compatibility modes: backward, forward, full. Senior

What the interviewer is testing: safe evolution and the correct upgrade order.

Backward compatible (the registry default): consumers using the new schema can read data written with the old schema. So you can upgrade consumers first. Allowed changes: delete a field, or add a field with a default. Forward compatible: consumers using the old schema can read data written with the new schema. So you can upgrade producers first. Allowed: add a field, or delete a field that had a default. Full: both directions; allowed changes are adding or deleting fields that have defaults. Each has a "transitive" version that checks against all older versions, not only the previous one (use it when old data stays in the topic for a long time, or for replay). None turns checks off. For Kafka, with retention and replay, backward transitive or full transitive is the safest choice. Practical rules: always give new fields a default, never rename a field (add a new one, migrate, then drop the old one), never change a type incompatibly, and use aliases when a rename is needed.

Common mistakes: mixing up backward and forward; adding a required field without a default; renaming fields.
What is a subject naming strategy, and how do you roll out a breaking schema change? Senior

What the interviewer is testing: the registry mechanics and a migration plan.

A subject is the name under which versions of a schema are stored, and compatibility is checked per subject. The default TopicNameStrategy uses topic-value and topic-key, so one topic has one value schema lineage. RecordNameStrategy uses the record's full name, which allows several event types in one topic (good when order across types matters). TopicRecordNameStrategy combines both. For a truly breaking change (type change, removal of a field consumers rely on), do not force it. Create a new topic or a new major version (orders.v2), have producers write to both for a while, move consumers to v2, then retire v1. Use a transformation job (Kafka Streams or Connect) to translate between versions if needed. Plan the change with the consumer teams, because the registry only checks structure, not meaning: changing "amount" from dollars to cents passes every compatibility check and still breaks everyone.

9. Kafka Streams, ksqlDB, Kafka Connect, CDC and the outbox pattern

What is Kafka Streams and how is it different from a plain consumer or from Spark and Flink? Intermediate

What the interviewer is testing: do you know when a library is enough and when a cluster framework is needed.

Kafka Streams is a Java library, not a cluster. You add it to your normal application, define a topology (read topics, filter, map, join, aggregate, write topics), and run as many instances of your app as you like. Instances share the work by the same partition assignment as a consumer group, and state is kept in local stores (RocksDB) backed by compacted changelog topics, so a replacement instance can rebuild state. It gives you windowing, joins, aggregation and exactly-once (processing.guarantee=exactly_once_v2) with little code. Compared with a hand-written consumer, you do not manage offsets, state or rebalancing yourself. Compared with Spark or Flink: those run on their own cluster, handle many sources and sinks and heavier analytics, while Kafka Streams is Kafka in, Kafka out, simple to deploy and scale. It is limited to JVM languages and to Kafka as source.

Likely follow-ups
  • What is a KStream versus a KTable? A KStream is an unbounded series of events. A KTable is the latest value per key (a changelog turned into a table).
  • What is a GlobalKTable? A table fully copied to every instance, good for small lookup data and joins without co-partitioning.
What are windows and joins in Kafka Streams, and what do you need to watch for? Senior

What the interviewer is testing: stateful stream processing basics.

Windows cut an endless stream into time buckets for aggregation: tumbling (fixed, no overlap, for example per 5 minutes), hopping (fixed size, overlapping), sliding (continuous), and session windows (grouped by activity gaps). Time is usually event time taken from the record, so late data can arrive; the grace period says how long a window stays open for late records. Joins combine streams: stream to stream joins need a time window, stream to table joins enrich events with the latest table value, table to table joins keep two tables in sync. For key-based joins both topics must be co-partitioned: same number of partitions and same partitioning rule, so matching keys land on the same instance. A mismatch causes wrong or missing joins. Watch for state size, repartition topics created by re-keying, and the cost of rebuilding state after a restart.

What is ksqlDB and when would you pick it? Basic

What the interviewer is testing: basic awareness of the SQL layer and its trade-offs.

ksqlDB is a streaming database by Confluent that lets you write SQL on Kafka topics. You define a stream or a table over a topic and write continuous queries: they keep running and update their results as new records arrive. Under the hood it runs Kafka Streams. Example: CREATE TABLE orders_per_min AS SELECT customer, COUNT(*) FROM orders WINDOW TUMBLING (SIZE 1 MINUTE) GROUP BY customer;. It is quick for filters, enrichment, simple aggregates and prototypes, and non-Java teams can use it. For complex logic, custom code, unit tests, or strict deployment control, Kafka Streams in code is easier to test and version. Note that ksqlDB is a Confluent-licensed product, not part of Apache Kafka, so check whether your platform offers it.

What is Kafka Connect and why use it instead of writing producers and consumers? Intermediate

What the interviewer is testing: use of the integration framework.

Kafka Connect is a runtime for moving data between Kafka and other systems using ready-made connectors, configured with JSON and no code. A source connector pulls data into Kafka (a database, files, a queue, a SaaS API). A sink connector pushes data out (to Elasticsearch, S3, a data warehouse, JDBC databases). Connect runs as a cluster of workers (distributed mode), spreads connector tasks over workers, stores connector offsets in internal topics, restarts failed tasks, and scales out. Single Message Transforms (SMTs) apply small changes such as renaming fields, masking, or routing to topics. It handles tricky concerns for you: batching, retries, offset tracking, schema integration, and converters (JSON, Avro, Protobuf). You write custom code only when no connector exists or logic is complex. Sink connectors can send bad records to a dead-letter topic (errors.tolerance=all, errors.deadletterqueue.topic.name).

What is change data capture (CDC) and how does Debezium use Kafka? Intermediate

What the interviewer is testing: how to stream database changes reliably without dual writes.

CDC means turning every insert, update and delete in a database into an event. Debezium is a popular open source set of source connectors that does this by reading the database's own transaction log (the MySQL binlog, the PostgreSQL write-ahead log via logical replication) instead of querying tables. That is light on the database, captures deletes, and keeps commit order. Each table becomes a topic, keyed by primary key, and each event carries the "before" and "after" row and metadata. Consumers can then update caches, search indexes, or other services. First it takes a consistent snapshot of existing rows, then it streams ongoing changes. Things to know: it is at-least-once, so consumers must be idempotent; schema changes in the source table flow through to events; large transactions and long-running snapshots need care; and the replication slot in PostgreSQL holds log files until the connector reads them, so a stopped connector can fill the database disk.

What is the outbox pattern and why do we need it? Senior

What the interviewer is testing: solving the dual-write problem in microservices. It is a favourite senior question.

The problem: a service must save an order in its database and publish "OrderCreated" to Kafka. These are two systems. If you write the database, then send to Kafka, a crash between them saves the order but never publishes (a lost event). If you publish first, a rollback leaves an event about an order that does not exist. A distributed transaction between the two is not available. The outbox pattern fixes it: in the same local database transaction that saves the order, also insert a row into an outbox table with the event payload. Because it is one database transaction, both happen or neither. A separate process then publishes the outbox rows to Kafka: either a poller that reads unsent rows, or, better, Debezium reading the outbox table's log and publishing with the Outbox Event Router transform. Delivery is at-least-once, so consumers are idempotent, and the event id doubles as the dedup key. Key the event by the aggregate id to keep per-entity order.

Likely follow-ups
  • Poller or CDC? Polling is simple but adds database load and delay and can reorder under concurrency. Log-based CDC is cleaner.
  • How do you clean the outbox table? Delete rows after publish or on a schedule; with CDC you can even delete the row at once since the log already has it.
How does Kafka fit with event sourcing, CQRS and sagas? Senior

What the interviewer is testing: architectural use, and awareness of the limits.

Event sourcing stores state as a sequence of events. Kafka's retained, replayable log, with compacted topics for snapshots, suits it as the event transport and for rebuilding read models, but it is not a good primary event store by itself: it has no per-entity read by key, no optimistic concurrency check ("append only if version is N"), and per-entity streams need one partition each or filtering. Many teams keep the authoritative events in a database and publish them to Kafka. CQRS (separate read models) fits well: services consume events and build their own query stores (search index, cache). For sagas (long business flows across services), Kafka carries commands and events between steps, with a compensating event if a step fails. Choreography (services react to each other's events) is simple for short flows; an orchestrator service with its own state is clearer for long ones. In every case, events are idempotent and carry ids and versions.

10. KRaft, security and Spring Kafka

What is KRaft and why did Kafka remove ZooKeeper? Intermediate

What the interviewer is testing: up-to-date knowledge of the biggest architecture change in Kafka.

Older Kafka kept its cluster metadata (brokers, topics, partition leaders, configs, ACLs) in a separate ZooKeeper cluster, and one broker acted as controller, loading all that state from ZooKeeper. KRaft (Kafka Raft) replaces this: a set of controller nodes run Kafka's own Raft-based quorum and store metadata in an internal log, __cluster_metadata, and brokers read it like any log. Reasons for the change: one system to run and secure instead of two; metadata is a log that brokers replay, so controller failover is fast (seconds, not minutes on big clusters); and it scales to millions of partitions instead of hitting ZooKeeper limits. Timeline: early access in 2.8; production ready in 3.3; ZooKeeper mode deprecated in 3.5; migration tooling for ZooKeeper clusters in 3.6 and later; ZooKeeper support removed in Kafka 4.0, so 4.0 clusters are KRaft only. A node can be a broker, a controller, or both (combined mode, fine for dev, not advised for production). As an application developer, your client code does not change.

Likely follow-ups
  • Do clients need changes? No. Clients never talked to ZooKeeper. Old consumers that stored offsets in ZooKeeper stopped being supported long ago.
What are the security basics in Kafka: authentication, authorization, encryption? Intermediate

What the interviewer is testing: the developer's view: what to configure on clients and what to ask the platform team.

Three layers. Encryption in transit: TLS on listeners (security.protocol=SSL or SASL_SSL), so data on the network is encrypted. It costs some CPU and disables zero-copy reads. Authentication (who are you): TLS client certificates (mTLS), or SASL with a mechanism: SCRAM-SHA-256/512 (username and password stored in the cluster), PLAIN (only over TLS), GSSAPI (Kerberos), or OAUTHBEARER (tokens from an identity provider, common in cloud). Authorization (what may you do): ACLs that grant a principal operations (READ, WRITE, CREATE, DESCRIBE) on resources (topic, group, transactional id, cluster). A consumer needs READ on the topic and READ on its group. A transactional producer needs WRITE on its transactional.id. Data at rest is usually handled by disk or cloud volume encryption, and sensitive fields can be encrypted by the application before producing. As a developer, keep credentials out of code (secret store), use least-privilege principals per service, and never log full records with personal data.

  username="orders-svc" password="${KAFKA_PASSWORD}";

How do you use Kafka with Spring Boot? What does @KafkaListener do? Intermediate

What the interviewer is testing: hands-on use. What happens behind the annotations.

Spring for Apache Kafka gives you KafkaTemplate to send and @KafkaListener to receive. Behind a listener sits a listener container (a ConcurrentMessageListenerContainer) that owns one or more real KafkaConsumer threads, runs the poll loop, calls your method for each record (or batch), and handles commits according to an AckMode. The default AckMode.BATCH commits after the whole poll batch was handled successfully, and Spring sets auto commit off. concurrency sets how many consumer threads per container; each thread is one consumer in the group, so it cannot usefully exceed the partition count. Configuration is by spring.kafka.* properties or by defining ConsumerFactory and ProducerFactory beans. Error handling is done by a DefaultErrorHandler with a back-off and a DeadLetterPublishingRecoverer.

@Component
class OrderListener {
  @KafkaListener(topics = "orders", groupId = "billing", concurrency = "3")
  void on(ConsumerRecord<String, OrderEvent> rec) {
     billingService.charge(rec.value());   // exception triggers the error handler
  }
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object,Object> t) {
  var recoverer = new DeadLetterPublishingRecoverer(t);
  return new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));
}
Likely follow-ups
  • What does @RetryableTopic do? Creates delayed retry topics and a DLT automatically (non-blocking retry).
  • How to commit manually? Use AckMode.MANUAL and take an Acknowledgment parameter, then call ack.acknowledge().
How do you handle deserialization errors and bad messages in Spring Kafka? Senior

What the interviewer is testing: concrete poison pill handling in the stack you use.

If the value deserializer throws inside poll(), the container never even sees a record, and the consumer can loop on the same offset. Wrap the real deserializer in ErrorHandlingDeserializer: it catches the exception and delivers a record with the failure stored in a header. The container's DefaultErrorHandler then sees it as a normal failure. Configure it with a BackOff and a DeadLetterPublishingRecoverer to publish the bad record (with exception headers) to topic.DLT. Mark errors that are not worth retrying (for example IllegalArgumentException, or a custom validation error) as not retryable with addNotRetryableExceptions, so they go to the DLT at once. For JSON, restrict trusted packages so a header cannot make you deserialize arbitrary classes. For batch listeners, throw a BatchListenerFailedException with the index of the bad record so only that one is retried or dead-lettered.

spring.kafka.consumer.value-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.properties.spring.deserializer.value.delegate.class=io.confluent.kafka.serializers.KafkaAvroDeserializer
How do you test Kafka code? Intermediate

What the interviewer is testing: engineering practice, not only theory.

I use layers. Unit tests keep the business logic free of Kafka types, so a handler is a plain method tested with plain inputs. For the integration layer I run a real broker: Testcontainers starts a Kafka container (a KRaft-mode image) for the test, and the test produces a record and waits (with a timeout, using something like Awaitility) for the effect. Spring has @EmbeddedKafka for a lighter in-JVM broker. Kafka Streams has TopologyTestDriver to test topologies with no broker at all. I test the unhappy paths on purpose: duplicate delivery of the same record, a poison record going to the DLT, an out-of-order event, and a consumer restart in the middle. For contracts between teams, schema compatibility checks in the build (the registry's compatibility test, or a Pact style contract) catch breaking changes before deploy.

What would you monitor for a Kafka-based service you own? Intermediate

What the interviewer is testing: operational ownership at the application level.

For the consumer side: consumer lag per partition (and its trend), time since last successful processing, rebalance count and duration, records processed per second, handler latency, error and DLT counts, and the poll interval margin (how close you are to max.poll.interval.ms). For the producer side: send error rate, request latency, batch size average, record retry rate, buffer pool wait time, and delivery callbacks failing. For the platform (watch, but usually platform team owns): under-replicated partitions, offline partitions, ISR shrink events, request handler idle ratio, disk usage. Alerts should be on symptoms with business meaning: "lag older than 5 minutes" or "DLT received messages", not on raw CPU. 11. Kafka versus RabbitMQ, SQS, Pulsar and others

Kafka versus RabbitMQ: how do you choose? Intermediate

What the interviewer is testing: reasoning from requirements, not brand loyalty.

RabbitMQ is a traditional message broker. It has smart routing (exchanges, bindings, topic and header routing), per-message acknowledgement, priorities, TTLs and delayed messages. The broker pushes messages to consumers and removes them once acknowledged, so it is great for task queues and request or reply, with moderate throughput. Kafka is a distributed log: the broker is simple, consumers pull, data is retained and replayable, many independent consumer groups can read the same data, and throughput is far higher with strong per-partition ordering. So I choose Kafka for event streaming, data pipelines, event sourcing and CDC, replay, and many readers of the same events. I choose RabbitMQ for job queues with per-message handling, complex routing, priorities, and work that should be consumed and forgotten. Pitfalls: using Kafka as a task queue with per-message retry and delay is awkward (one slow record blocks its partition), and using RabbitMQ for huge replayable streams is the wrong tool.

When should you NOT use Kafka? Senior

What the interviewer is testing: judgment. Seniors know where a tool does not fit.

Do not use it when you have a low volume of simple jobs and want a managed queue with delay, visibility timeout and per-message retry (SQS or RabbitMQ is simpler). Do not use it when you need synchronous request and response (HTTP or gRPC is better; a Kafka reply topic works but is clumsy). Do not use it as a database for random lookups by key or for ad hoc queries. Do not use it when you need per-message priority or complex routing. Do not choose it for tiny teams with no platform support, because a self-run cluster has real operational cost; use a managed service or something simpler. Also be careful when the data is huge per message (large files), or when you need global ordering of all events. The honest answer shows you pick tools from requirements.

What are the options besides running your own Kafka, and what changes for developers? Intermediate

What the interviewer is testing: practical awareness of the managed ecosystem.

Options include Confluent Cloud, Amazon MSK, Azure Event Hubs (which offers a Kafka-compatible endpoint), Aiven, and Redpanda (a Kafka API compatible broker written in C++). For a developer the client code stays the same, because they all speak the Kafka protocol. What changes is configuration: bootstrap addresses, SASL and TLS settings, quotas on throughput and partitions, topic creation policies (sometimes topics cannot be auto-created), and which features exist (for example not all support every transaction or compaction setting, or the same Connect plugins). Always check the limits of the managed service: maximum partitions, message size, retention caps, and cost per partition and per GB. I would also keep the topic and ACL definitions as code (Terraform or a topic operator), not created by hand.

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

After a release, consumer lag on the orders topic grows every minute. What do you do? Senior

What the interviewer is testing: structured diagnosis under pressure.

Situation: producers write about the same rate as before, but the billing group falls behind and the alert for lag fires.

Check first: is it all partitions or a few? Is the group stable or rebalancing? What changed in the release (a new database call, a bigger payload, a lower max.poll.records, fewer pods)? Look at handler latency metrics and logs for timeouts.

kafka-consumer-groups.sh --bootstrap-server b1:9092 --describe --group billing
kafka-consumer-groups.sh --bootstrap-server b1:9092 --describe --group billing --state

Steps: if the new code is slow, roll back or fix the call (batch inserts, add an index, cache a lookup). If pods were reduced, scale back up, but only to the partition count. If one partition is the problem, find the hot key or the stuck instance. While recovering, protect downstream systems with a rate limit. After the fix, the lag drains at (consume rate minus produce rate), so estimate the time and tell stakeholders.

Prevent: load test the consumer after changes, alert on lag trend and on time lag, not only absolute numbers, and track handler p99 latency in the dashboard.

Customers were charged twice. The payment consumer processed some Kafka messages two times. Why, and how do you fix it? Senior

What the interviewer is testing: understanding at-least-once and idempotency in a money flow.

Situation: a few payments appear twice, mostly around deployments and slow periods.

Check first: match duplicates to times of rebalances, restarts, and long processing. Check whether offsets are committed before or after the charge, whether max.poll.interval.ms was exceeded, and whether the producer sometimes publishes the same event twice (compare event ids and offsets).

Cause: usually at-least-once working as designed: a pod was killed after charging but before committing, or a rebalance moved the partition and the new owner re-read uncommitted records.

Steps: make the handler idempotent. Use the event id as an idempotency key: insert into a processed_events table (unique key) in the same transaction as the payment record, and pass the same key to the payment provider as its idempotency key. Commit offsets after processing, commit in onPartitionsRevoked, stop consumers gracefully on shutdown. Refund the duplicates found by a reconciliation query.

Prevent: idempotency by design for any side effect, tests that deliver the same message twice, and graceful shutdown (wakeup() then close()).

The consumer group keeps rebalancing every few minutes and almost no work gets done. What is going on? Senior

What the interviewer is testing: knowing the causes of a rebalance storm and the fixes.

Situation: logs show "Revoking previously assigned partitions", "Attempt to heartbeat failed since group is rebalancing" and "commit failed, the group has already rebalanced". Lag rises and falls in waves.

Check first: why do members leave? There are three usual causes. One: processing a poll batch takes longer than max.poll.interval.ms. Two: long garbage collection pauses or CPU starvation (common with tight container CPU limits) cause missed heartbeats beyond session.timeout.ms. Three: pods restart again and again (crash loops, failing health probes, autoscaler flapping), each time triggering a rebalance.

Steps: lower max.poll.records or raise max.poll.interval.ms so a batch always finishes in time; move slow calls off the poll thread carefully; add static membership (group.instance.id) so restarts do not rebalance; use the cooperative assignor or the new group protocol; give pods proper CPU and memory and tune GC; stop crash loops; slow down rolling updates (one pod at a time with readiness).

Prevent: alert on rebalance rate, and test with realistic slow downstream responses.

A producer team says they sent an event but the consumer never got it. Where do you look? Senior

What the interviewer is testing: end-to-end checking before blaming anyone.

Situation: one business event is missing downstream.

Check first: prove which side is wrong. Search the topic for the key and time window with a console consumer (--from-beginning or a timestamp), or by offset. If the record is in the topic, the problem is the consumer: it skipped it (error swallowed, filter, wrong group, offset reset to latest, retention passed while the group was down), or it is in the DLT. If the record is not in the topic, the producer never delivered: callback errors ignored, acks=0/1 with a failover, process killed before flush(), wrong topic or key, a transaction that aborted (and the reader uses read_committed), or the event never left the service because of a dual-write crash.

kafka-console-consumer.sh --bootstrap-server b1:9092 --topic orders \
  --partition 3 --offset 120000 --max-messages 50 --property print.key=true --property print.offset=true

Prevent: producer config for durability (acks=all, idempotence, min ISR 2), always handle callbacks, use the outbox pattern for database-triggered events, log topic, partition and offset on send and receive, and alert on DLT and on "sent versus received" count drift.

A single bad record has stopped a partition for an hour. How do you unblock and prevent it? Senior

What the interviewer is testing: unblocking safely and fixing the design.

Situation: one partition shows lag growing and the same stack trace repeats in logs, always at the same offset. Other partitions are fine.

Check first: find the offset in the log message and read it with a console consumer to see what is wrong (bad JSON, wrong schema id, null where a field is required, a data value that triggers a bug).

Steps (now): if the cause is data, move the group past it: stop the group, then kafka-consumer-groups.sh --reset-offsets --to-offset BAD+1 --topic orders:3 --execute. Copy the bad record to a quarantine topic first so it is not lost. If the cause is a bug in your code, fix and redeploy, no skip needed.

Prevent (design): ErrorHandlingDeserializer, a DefaultErrorHandler with limited retries and a DeadLetterPublishingRecoverer, a rule that permanent errors skip retries, validation at the producer side, a schema registry with compatibility checks, and an alert on DLT traffic.

One partition has ten times the lag of the others and one broker is at 90 percent CPU. What is happening? Senior

What the interviewer is testing: data skew diagnosis and a fix that respects ordering.

Situation: the topic has 12 partitions, keyed by tenantId. Dashboards show partition 7 receiving most of the bytes.

Check first: per-partition bytes-in and record counts; sample the keys on partition 7 with a console consumer (--property print.key=true). You will likely find one big tenant producing most of the traffic.

Steps: short term, give that partition's consumer more room (faster hardware, key-lane parallelism inside the consumer). Medium term, change the key for heavy tenants to tenantId + ":" + (customerId hash mod N) so they spread over N partitions. Per-tenant order then turns into per-customer order, so check that is acceptable. If the hot tenant is truly special, send it to its own topic with more partitions. Changing keys affects ordering at the cut-over, so drain the topic or switch at a clean point.

Prevent: choose keys with high cardinality and uniform spread, load test with realistic skew, and monitor per-partition metrics rather than topic totals.

After the team added partitions to scale, events for the same customer are being processed out of order. Why? Senior

What the interviewer is testing: the key-hash-modulo trap in a real incident.

Situation: the topic went from 6 to 12 partitions. Since then, "AccountClosed" is sometimes processed before the "PaymentPosted" that came earlier.

Cause: hash(key) mod 12 differs from hash(key) mod 6 for about half of the keys. Older events of a customer sit unconsumed in the old partition, while newer ones go to a new partition that is read by another consumer at the same time.

Steps: for the damage, find affected entities (compare event timestamps or versions with processing order) and re-apply in the right order using versions. To stop it, make the consumer version-aware: ignore or re-queue events older than the stored version, so order is protected at the application level. Going forward: if strict order is needed, follow the safe procedure: stop producers, let lag drain to zero, add partitions, restart. Or create a new topic with the right count and migrate.

Prevent: size partitions with headroom at creation, treat the partition count as a fixed contract for keyed topics, and carry a version or sequence in events.

A broker crashes in production at peak time. What do you expect to happen and what do you check? Senior

What the interviewer is testing: knowing the failover behavior and what the application should show.

Situation: one of three brokers disappears. Replication factor is 3, min ISR is 2, producers use acks=all.

What should happen: the controller moves leadership of the partitions that broker led to ISR members within seconds. Clients get NotLeaderOrFollower errors, refresh metadata, and retry. Producers briefly slow down; idempotence prevents duplicates. Writes continue because ISR is still 2. No committed data is lost. Under-replicated partitions go up until the broker returns.

Check: offline partition count should be zero; under-replicated partitions should be only those that had a replica on the dead broker; producer error rate spikes then recovers; consumer rebalances may occur if consumer processes also lived on the failed host. Look at client logs for retriable errors versus delivery timeouts.

If things go wrong: if a second broker fails, ISR drops to 1, acks=all writes fail with NotEnoughReplicas (by design) and producers must buffer, retry, or alert. Never switch on unclean election in a hurry for important data.

Prevent: replication 3 across zones, rack awareness, client timeouts that allow a failover (delivery.timeout.ms well above 30 seconds), and regular failure drills.

Producers suddenly throw NotEnoughReplicasException. What does it mean and what do you do? Intermediate

What the interviewer is testing: connecting the error to ISR and min.insync.replicas.

Situation: sends to topic payments fail, while other topics work.

Meaning: the ISR of at least one partition has fewer members than min.insync.replicas, and the producer uses acks=all. The broker refuses the write on purpose, to protect durability.

Check: ask the platform team or run kafka-topics.sh --describe --under-min-isr-partitions. See which broker is out (down, overloaded, slow disk, network trouble) and why followers fell behind.

Steps: restore the lagging or dead broker. In the meantime the application should retry for the delivery timeout, queue the events locally (outbox), or return a clear "try later" instead of losing data. Do not lower min ISR to 1 just to make the errors stop unless the business accepts the risk.

Prevent: alert on under-replicated partitions before it reaches under-min-ISR, and size replication to survive one failure.

A consumer was down over a long weekend and, after restart, it silently skipped a large chunk of data. Why? Senior

What the interviewer is testing: retention versus consumer downtime, and auto.offset.reset.

Situation: the topic has 3 day retention and the consumer was off for 4 days. After restart, the committed offset no longer exists (the segments were deleted), so the consumer sees an out-of-range position. With auto.offset.reset=latest it jumps to the end and drops all missing data without any error. With earliest it starts from the oldest remaining record, so records that were already deleted are gone but it reads everything still present.

Another variant: a consumer group that had no committed offsets (it was new, or its offsets expired after offsets.retention.minutes, default 7 days of an empty group) starts from latest and misses earlier data.

Steps: find the gap (compare offsets, event times), recover from another source (the producer system, a database, a mirrored cluster, or archived topic data in S3 via a sink connector), and replay. Set auto.offset.reset=earliest for consumers that must not miss data, or none so it fails loudly.

Prevent: retention longer than your worst outage and weekend, alerts on lag before data expires (compare lag age to retention), and an archive sink for critical topics.

The producer logs "Expiring N record(s) ... has passed since batch creation" and "buffer exhausted". How do you debug? Senior

What the interviewer is testing: reading producer timeout messages.

Situation: sends fail with TimeoutException after about two minutes, or send() blocks and then throws "Failed to allocate memory within max.block.ms".

Meaning: a batch waited in the buffer longer than delivery.timeout.ms because the broker was not accepting data fast enough or was not reachable, and meanwhile the buffer filled up because the application kept producing.

Check: network and DNS to the brokers (advertised listeners wrong is a classic: the client connects to the bootstrap but cannot reach the advertised hostnames), broker health and leader changes, request latency metrics, batch and record size versus max.request.size, and whether the app produces faster than the cluster can take (quotas can throttle).

Steps: fix connectivity, give a clear backpressure path (bounded queue before the producer, reject or slow incoming requests), increase linger.ms and compression to cut request count, and do not just raise buffer.memory, which only delays the failure.

A producer team deployed a schema change and three consumers crashed. How do you respond and prevent it? Senior

What the interviewer is testing: schema governance and incident handling.

Situation: after a deploy, consumers throw deserialization errors or null pointer exceptions. The field amount changed from int to string, or a field was renamed.

Steps now: stop the bleeding: roll back the producer. Records already written with the new schema remain in the topic, so consumers hit them again. Decide: skip those offsets with a DLT, or release a consumer fix that understands both. Check which schema version produced which offsets (the schema id is in each record) so you can bound the damage and replay or repair those records.

Prevent: a Schema Registry with compatibility set to backward (or full) transitive and a CI step that runs a compatibility check before deploy, so the change is rejected; a rule never to rename or retype fields (add a new field, migrate, remove the old); consumer-driven contract tests; and a deprecation process. Remember the registry checks structure, not meaning.

Two services publish events about the same order and consumers see "shipped" before "paid" sometimes. How do you fix it? Senior

What the interviewer is testing: ordering across producers and defensive consumers.

Situation: the payment service and the shipping service each publish to order-events keyed by orderId, so they share a partition, but their producers are different processes with their own clocks and network delays. Arrival order at the broker is not the business order.

Steps: same key keeps both on the same partition, but there is no promise of business order. Fix at the design level: shipping should only act after it has seen "paid" (a state machine in the consumer that parks or ignores out-of-order events until the prerequisite arrives), or the services should chain through events (shipping starts only when it receives PaymentCompleted). Add a version or sequence number per order, and let consumers drop stale events. A saga orchestrator can own the order of steps.

Prevent: do not rely on cross-producer ordering. Model the legal state transitions and make consumers tolerant to reordering and duplicates.

Producers fail with RecordTooLargeException for some documents. What are your options? Intermediate

What the interviewer is testing: knowing the limits and the claim-check pattern.

Situation: a few payloads are 5 MB; the default limit is about 1 MB.

Option one, raise limits: it must be raised in several places that must agree: broker or topic message.max.bytes (or topic max.message.bytes), producer max.request.size, replica replica.fetch.max.bytes, and consumer max.partition.fetch.bytes and fetch.max.bytes. It works but large records hurt memory, batching and latency.

Option two, compression: compress the batch or the payload; fine if the data compresses well.

Option three (preferred): the claim-check pattern. Store the big payload in object storage (S3, blob storage) and send a small event with the link, size and checksum. Consumers fetch the file only if they need it. Take care of the lifecycle: delete the object after retention, and secure the link.

The dead-letter topic suddenly receives thousands of messages per minute. What now? Senior

What the interviewer is testing: distinguishing a systemic failure from bad data, and replaying safely.

Situation: alerts fire on DLT volume right after a deploy of a downstream dependency.

Check first: look at the exception headers on a sample of DLT records. If they all share one exception (connection refused, 503, timeout), it is a systemic outage that got treated as permanent, not bad data. If they are validation errors, a producer sent bad data.

Steps: for a systemic failure, fix the dependency, then replay the DLT back into the main topic (a small tool or the same code with a rate limit), and make sure the handler is idempotent because some records may already have partly worked. For bad data, tell the producer team, fix, and decide per record. Also review the retry design: temporary errors like 503 should be retried with backoff, and a circuit breaker should pause the consumer instead of sending everything to the DLT.

Prevent: classify exceptions into retryable and permanent, use pause on downstream outage, and keep a tested replay tool with rate limiting.

Consumers using read_committed stop seeing new records even though producers keep writing. What could be wrong? Senior

What the interviewer is testing: the last stable offset behavior with transactions.

Situation: lag grows on one partition for read_committed consumers only; read_uncommitted consumers see the data.

Cause: a transactional producer began a transaction and neither committed nor aborted it (a hung or crashed app with a long transaction.timeout.ms). A read_committed consumer can only read up to the last stable offset: the first offset belonging to a still-open transaction. All records after it, even from other committed producers, are held back until that transaction finishes or the coordinator times it out (default transaction.timeout.ms is 60 seconds on the producer; the broker caps it with transaction.max.timeout.ms, 15 minutes by default).

Steps: find the owner (the transactional.id) and fix or restart it; the restart with the same id will fence and abort the old transaction. Make sure transactions are short: do not hold one open while calling slow external services.

Prevent: small transactions, sensible timeouts, and alerts on last stable offset lag.

A sink connector task has FAILED and data is not reaching the database. How do you handle it? Intermediate

What the interviewer is testing: basic Kafka Connect operations that a developer meets.

Situation: the connector status shows RUNNING, but one task is FAILED and lag for the connector's group grows.

Check first: the Connect REST API shows the trace of the failed task: GET /connectors/orders-sink/status. Typical causes: a record that cannot be converted (schema mismatch), a constraint error in the database, an unreachable database, or an expired credential.

Steps: fix the cause (credentials, database, schema). Restart the task with POST /connectors/orders-sink/tasks/0/restart (or restart the connector with failed tasks, newer versions have query options for that). For bad records, set errors.tolerance=all with a dead-letter queue topic and errors.deadletterqueue.context.headers.enable=true, so bad records are parked and good ones continue. Remember the connector's offsets are kept in Kafka, so after restart it continues from where it stopped, with at-least-once delivery, so the sink must be idempotent (upsert mode).

Prevent: alert on task status and connector lag, and use upsert mode for sinks.

The PostgreSQL database disk is filling up after a Debezium connector was stopped. Why? Senior

What the interviewer is testing: CDC operational side effects that surprise application teams.

Situation: WAL files keep growing and the database is close to a full disk.

Cause: Debezium uses a logical replication slot. PostgreSQL keeps all WAL segments that the slot has not yet confirmed, so a stopped, failed or very slow connector makes the WAL pile up without limit.

Steps: first restart or fix the connector so that it consumes and confirms the log. If it cannot be fixed quickly and the disk is nearly full, drop the replication slot to release the WAL (SELECT pg_drop_replication_slot('slot_name')), then accept that you must re-snapshot or re-sync the downstream data afterwards. Coordinate with the database owners before dropping.

Prevent: monitor the slot lag and WAL size, alert early, set max_slot_wal_keep_size (PostgreSQL 13 and later) to cap the damage, and add a heartbeat so the slot advances even when tables are quiet.

A new service was deployed with a new consumer group but it processes only new events, not the history it needs. What happened? Intermediate

What the interviewer is testing: the default offset reset behavior.

Situation: a new "search-indexer" service starts and indexes only events that arrive after deploy; older ones are missing.

Cause: a new group id has no committed offsets, so auto.offset.reset applies, and its default is latest. The group starts at the end of the log.

Steps: stop the group, reset its offsets to the earliest (or a timestamp) with kafka-consumer-groups.sh --reset-offsets --to-earliest --execute, and start again; or set auto.offset.reset=earliest before the first start. Make sure the old data is still in retention; if it is not, use the source system or a compacted topic or archive. Watch for the load: reading months of history can overwhelm downstream systems, so throttle.

Prevent: decide the reset policy deliberately for each new consumer, and keep a compacted topic for state that new services need to bootstrap.

Every deployment causes duplicate processing and a burst of lag. How do you make deployments quiet? Senior

What the interviewer is testing: shutdown and rollout hygiene for stateful consumers.

Situation: a rolling update of 10 pods triggers many rebalances; pods are killed in the middle of processing batches.

Steps: handle SIGTERM: call consumer.wakeup() from the shutdown hook, finish the current batch, commit offsets, then close() so the member leaves the group cleanly (Spring Kafka does this on context close if the termination grace period is long enough). Set the Kubernetes terminationGracePeriodSeconds above your longest batch time. Use static membership (group.instance.id based on the pod name of a StatefulSet) with a session.timeout.ms long enough to cover a restart, so partitions stay with the instance and no rebalance happens. Use the cooperative assignor, and set maxSurge and maxUnavailable so pods roll one or two at a time. Keep the handler idempotent for the leftover duplicates.

Prevent: include a "deploy while under load" test in staging and watch rebalance count as a release metric.
