Kafka interview questions

What Kafka really is (a distributed commit log), how producers and consumers behave, how to get reliability and ordering, and how to answer the production incident questions. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

Mental model: the 8 ideas everything hangs on

One line: Kafka is a distributed, replicated, append-only log. Producers append records to the end of a partition. Consumers read at their own pace by remembering an offset. Nothing is removed when it is read, only when retention says so.
  1. It is a log, not a queue. Records are appended and kept. Reading does not delete. Many readers can read the same data independently.
  2. A topic is split into partitions. A partition is one ordered log. Order is guaranteed only inside a partition, never across the whole topic.
  3. The offset is the position. Each record in a partition has a number: 0, 1, 2... A consumer's "progress" is just a stored offset.
  4. Partitions are the unit of parallelism. In one consumer group, a partition is read by at most one consumer at a time. More partitions means more possible parallel consumers.
  5. Replication gives durability. Each partition has a leader and followers on other brokers. The in-sync replica set (ISR) plus acks and min.insync.replicas decide what "safely written" means.
  6. The key chooses the partition. Same key goes to the same partition, so records of one key stay in order.
  7. Delivery guarantees are built by you. Kafka gives at-least-once by default. Exactly-once needs idempotent producers, transactions, and consumers that tolerate duplicates.
  8. Consumers pull. The consumer asks for data, so a slow consumer does not hurt the broker. It just falls behind (lag).

1. Why Kafka, the log, topics, partitions and offsets

What is Kafka and what problem does it solve? Basic

Kafka is a distributed event streaming platform. It stores streams of records in a replicated, append-only log, so many programs can write to it and many others can read from it later, each at its own speed. It solves the tangle of point-to-point connections between systems: a producer writes once to a topic, and any number of consumers pick it up.

It was built at LinkedIn to move huge volumes of events (page views, logs, metrics) between many systems. Typical uses are event-driven microservices, data pipelines, change data capture, stream processing and audit trails. The strengths are high throughput, durability through replication, replay of old data, and loose coupling between teams. It is not a database: you cannot query by field or join, so use it as a durable pipe and log, not as your main query store.

Remember: Kafka is a durable, replayable log that decouples producers from consumers.

Why is Kafka a log and not a queue? Intermediate

A classic queue tracks each message and deletes it once a consumer acknowledges it. Kafka does not track messages at all. It only appends to a log, and each consumer remembers one number, its offset. That makes the broker cheap and fast, and gives replay, many independent readers, and new consumers that can start from the beginning.

The log is the simplest data structure: add to the end, every entry gets a growing number. Writes and reads are sequential, which disks do very well, and the broker keeps no per-message, per-consumer state. The price: you cannot delete or reorder one message, and there is no per-message priority or routing. Old data goes away only by retention (time or size) or by compaction.

Remember: a queue deletes on read, a log keeps data and the consumer just moves its offset.

What are topics and partitions, and why do partitions exist? Basic

A topic is a named stream of records, like "orders". It is split into partitions, and each partition is one ordered log living on one broker (with copies on others). Partitions exist for scale, because one machine cannot hold or serve everything, and for parallelism, because each partition can be read by one consumer in a group. The cost is that Kafka only promises order inside a partition.

So ten partitions allow up to ten consumers working at once in one group. Two records in different partitions have no guaranteed order, which is why you choose a key (like orderId): records with the same key land in the same partition and stay in order. You can add partitions later but never remove them, and adding moves keys (see the partition questions in section 7). num.partitions defaults to 1 on a plain install, so set it on purpose.

Remember: partition = one ordered log = one unit of parallelism. Order exists only inside it.

What is an offset, and who owns it? Basic

An offset is the sequence number of a record inside one partition, assigned by the broker when it appends the record. The real address of a record is topic, partition, offset. The consumer group owns its progress: the committed offset, which is the offset of the next record it will read.

Committed offsets are stored by Kafka in an internal topic called __consumer_offsets, keyed by group, topic and partition. Because the offset belongs to the group and not to one consumer instance, a replacement consumer continues from the last commit when another dies. Offsets are never reused but can have gaps (transaction markers and compaction leave holes), so do not assume they are consecutive.

If a group has no valid committed offset, auto.offset.reset decides where to start (see its own question below).

Remember: offset = position in one partition. The group stores "next offset to read".

Why is Kafka fast even though it writes to disk? Intermediate

Four things. It only appends sequentially, which is much faster than random disk access. It leans on the operating system page cache, so recent data is served from memory. It batches records and compresses whole batches. And for plain reads it can use zero-copy, sending data from the page cache to the network socket without copying it through the application.

Durability comes from replication, not from calling fsync on every message: the OS flushes pages later, and other brokers hold copies. One catch is that zero-copy does not work with TLS, because the data has to pass through user space to be encrypted, so TLS costs some throughput.

Remember: sequential writes + page cache + batching + zero-copy.

How does retention work, and why was my data not deleted after 7 days? Basic

Retention is a topic setting, not tied to consumption. By default Kafka keeps records for 7 days (retention.ms) and optionally up to a size per partition (retention.bytes), whether or not anyone read them. Whichever limit is hit first causes old data to be deleted. Reading never deletes anything.

Deletion works on whole segment files, not on single records. A partition is stored as a series of segment files; the newest one is "active" and takes writes. Kafka only deletes closed segments, and a segment goes only when its newest record is older than the retention time. So data can live a bit longer than 7 days until the active segment rolls (by size, default 1 GB, or age). The cleanup policy is delete (default), compact, or both.

The consequence for consumers: if a group is down longer than retention, the offsets it needs are gone and it falls back to auto.offset.reset. Set retention longer than your worst outage.

Remember: retention is by time or size, in whole segments, and independent of who has read what.

2. Replication, ISR and durability

How does replication work in Kafka? Intermediate

Each partition has one leader broker and some follower brokers. All reads and writes go to the leader. Followers copy the data by sending fetch requests to the leader, just like consumers do. A record counts as committed once every in-sync replica has it, and consumers only see committed records, up to the high watermark.

The leader tracks how far each follower has copied. The high watermark is the smallest end offset among the in-sync replicas. Consumers cannot read above it, so they never see a record that could still vanish if the leader died. The replication factor is the number of copies including the leader; three is the usual production value. Leaders are spread across brokers to balance load. Clients connect to a bootstrap address, fetch metadata that says who leads what, then talk straight to the right leaders.

Remember: followers pull from the leader; committed = on all in-sync replicas; consumers read below the high watermark.

What is the ISR, and when does a replica drop out of it? Intermediate

The ISR is the set of in-sync replicas: the leader plus the followers that are keeping up. A follower is dropped when it has not fetched up to the leader's end within replica.lag.time.max.ms (default 30 seconds), for example because it is slow, paused in a long garbage collection, or its broker is down. It is added back when it catches up.

The ISR matters for two reasons. Only ISR members can become the new leader by default, so they hold every committed record. And acks=all waits for the ISR, not for all replicas. So if the ISR shrinks to just the leader, acks=all alone is as weak as acks=1. That is the reason min.insync.replicas exists. A partition whose ISR is smaller than its replication factor is "under-replicated", a warning sign worth alerting on.

Remember: ISR = leader + followers that are caught up. It shrinks and grows by itself.

Explain acks and min.insync.replicas together. How do you get no data loss? Senior

I use replication factor 3, min.insync.replicas=2 and producer acks=all. acks says when the broker answers success; min.insync.replicas says the smallest ISR size for which a write is accepted. With these settings a write is on at least two brokers before I get success, I survive one broker loss with no data loss, and writes stop (with an error) rather than being "safe" on one broker.

acks=0 does not wait at all and can lose data silently. acks=1 waits for the leader's own write only, so a leader crash before followers copy it loses the record. acks=all waits for the whole current ISR. If the ISR is below min.insync.replicas, the broker rejects the write with NotEnoughReplicas. If two brokers die, writes stop, which is the right choice when loss is worse than downtime. Also keep unclean leader election off, keep idempotence on, and always check the send callback.

# topic level
kafka-configs.sh --bootstrap-server b1:9092 --alter --entity-type topics \
  --entity-name payments --add-config min.insync.replicas=2

# producer
acks=all
enable.idempotence=true
delivery.timeout.ms=120000
Watch out: acks=all means all in-sync replicas, not all replicas. And min.insync.replicas defaults to 1, so without setting it, acks=all can end up on one broker. Setting it equal to the replication factor means one broker down stops all writes.

Remember: RF 3, min ISR 2, acks=all. acks says who confirms, min ISR says how few is acceptable.

What happens when a partition leader broker dies? Intermediate

The cluster controller notices the broker is gone and picks a new leader for each of its partitions from the ISR, then publishes the new metadata. Clients get a "not leader" error or a timeout, refresh metadata and retry against the new leader, usually within a few seconds. Because the new leader was in the ISR, no committed data is lost.

With the idempotent producer the retry does not create duplicates. When the dead broker comes back it becomes a follower, drops any records beyond what the leader has, and catches up. If the ISR is empty (every in-sync replica is down), the partition is offline and writes fail. For a developer the practical point is client timeouts: delivery.timeout.ms must be comfortably longer than a failover.

Remember: new leader comes from the ISR, so committed data survives; clients just refresh metadata and retry.

What is unclean leader election, and when would you allow it? Senior

It lets an out-of-sync follower become leader when no in-sync replica is alive. The partition comes back immediately, but records the stale replica did not have are lost. It is off by default. I keep it off for payments, orders and audit data and accept downtime, and consider it only for data like metrics where freshness beats completeness.

It is the pure consistency versus availability trade-off. Setting is unclean.leader.election.enable, which can be set per topic. Turning it on in a hurry during an incident is a classic mistake: you get availability back and silently lose data.

Remember: unclean election trades data for availability. Default is off, keep it off for important data.

3. Producers: batching, keys, idempotence, ordering

What happens inside the producer when you call send()? Intermediate

send() does not write to the network. It serializes the key and value, picks a partition, and puts the record into a per-partition batch in a memory buffer. A background sender thread later groups ready batches per broker and sends them. When the broker answers, the returned future completes and my callback runs. So send is asynchronous and a crash right after it returns can lose buffered records.

A batch is sent when it is full (batch.size, default 16 KB) or has waited linger.ms. The buffer is buffer.memory (default 32 MB); if it is full, send() blocks up to max.block.ms (60 s) and then throws. Call flush() or close() before exiting. To make a send synchronous, call get() on the future, but that kills throughput.

Remember: send() = buffer, not network. Always handle the callback and flush on exit.

How do batch.size, linger.ms and compression affect throughput and latency? Intermediate

Bigger batches mean fewer requests and better compression, so higher throughput, but each record may wait a little longer. linger.ms is how long the sender waits for a batch to fill before sending it anyway. Setting it to about 5 to 20 ms with a larger batch.size (64 KB or more) and lz4 or zstd compression usually gives a big throughput gain for a few milliseconds of latency.

With linger.ms=0 (the default in 3.x) records go out as soon as the sender is free; under load batches still form, but under light traffic they are tiny. Compression is applied to the whole batch on the producer, stored compressed by the broker, and decompressed by the consumer, so bigger batches compress better. lz4 is a fast choice, zstd gives the best ratio. For a very latency-sensitive flow, keep linger at 0.

Remember: linger a few ms + bigger batches + lz4/zstd = throughput. Linger 0 = lowest latency.

How does a producer choose the partition? Basic

If I set a partition on the record, that is used. If the record has a key, the default partitioner hashes the key bytes (murmur2) and takes it modulo the partition count, so the same key always goes to the same partition. With no key, the producer spreads records across partitions in a "sticky" way: it fills a batch for one partition, then moves to the next.

The key does two jobs: it keeps records of one entity in order, and it is the identity of a record for compaction. Because the formula uses the partition count, adding partitions changes where keys go. You can plug in a custom Partitioner for special routing, for example spreading one very large tenant over several partitions. Use a key only if there is a real ordering or grouping need; for independent events a null key gives the best spread.

Remember: hash(key) mod partitions. Same key, same partition, same order. No key, even spread.

What is an idempotent producer, and what does it protect against? Senior

It protects against duplicates caused by the producer's own retries. If a batch is written but the acknowledgement is lost, the producer retries, and without idempotence the batch is stored twice. With enable.idempotence=true each batch carries a producer id and a sequence number per partition, and the broker drops a batch it has already stored while still acknowledging it. It also stops retries from reordering records.

It is on by default since Kafka 3.0 (it needs acks=all and at most 5 in-flight requests). The cost is a few bytes per batch. What it does not cover: the guarantee holds per partition and per producer session. If my application crashes and restarts, it gets a new producer id, and if my code sends the same business event twice, that is two records. For those cases I need transactions or consumer-side deduplication by a business id.

Watch out: idempotence is not end-to-end exactly-once. It only removes duplicates caused by the producer's own retries.

Remember: producer id + sequence number kills retry duplicates, within one session and partition only.

Does retrying a failed send break ordering? What about max.in.flight.requests? Senior

Without idempotence, yes: if batch 1 fails and batch 2 succeeds, batch 1 is retried and lands after batch 2. With the idempotent producer, no. The broker checks sequence numbers and rejects out-of-order batches, so order within a partition is kept even with up to 5 requests in flight.

max.in.flight.requests.per.connection (default 5) is how many unacknowledged requests the producer may have outstanding per broker. The old advice was to set it to 1 for ordering, which hurts throughput. The modern answer: leave idempotence on (the default), keep in-flight at 5 or less, and ordering is preserved under retries. If you disable idempotence and still need order, set in-flight to 1.

Remember: idempotence on + in-flight at most 5 = ordered and no duplicates under retries.

Which producer errors are retried, and what do retries and delivery.timeout.ms do? Intermediate

The producer retries temporary errors by itself: leader change, network failure, NotEnoughReplicas, request timeout. It does not retry permanent ones: record too large, serialization failure, authorization failure. The real limit is delivery.timeout.ms (default 2 minutes), the total time from send() until success or failure is reported. retries defaults to a huge number, so time, not count, ends it.

Related timers: request.timeout.ms (30 s) is the wait for one request, retry.backoff.ms is the pause between tries. When the delivery timeout expires, my callback gets an exception and my code must decide what to do: log, store in an outbox, alert, or fail the business operation. The worst mistake is ignoring the callback, because that is how messages get lost silently.

producer.send(record, (meta, ex) -> {
    if (ex != null) {
        log.error("send failed key={}", record.key(), ex);
        // store in outbox / alert / fail the request
    }
});

Remember: temporary errors retry until delivery.timeout.ms; permanent ones fail at once; always check the callback.

Which producer settings would you set for a reliable, fast service? Intermediate

For reliability: acks=all, enable.idempotence=true, a topic with replication factor 3 and min.insync.replicas=2, default retries with a clear delivery.timeout.ms, and a send callback that handles errors. For throughput: linger.ms 5 to 20, batch.size 64 to 256 KB, and compression.type of lz4 or zstd.

I also set client.id so broker logs and quotas show who is who, and check max.request.size against my biggest record. I leave buffer.memory alone until I see "buffer exhausted" errors, which mean I produce faster than the brokers accept. Start from defaults and change one thing at a time.

Remember: safe = acks=all + idempotence + RF3/minISR2. Fast = linger + batch + compression.

4. Consumers, consumer groups, rebalancing and offset commits

What is a consumer group and how are partitions assigned? Basic

A consumer group is a set of consumers sharing one group.id that split a topic's partitions between them. Each partition is owned by exactly one consumer in the group at a time. With 6 partitions and 3 consumers, each gets 2; with 8 consumers, 2 sit idle. So the partition count is the upper limit of parallelism. Different groups are independent and each gets every record.

This one design gives both queue behaviour (one group, work shared) and publish-subscribe behaviour (many groups, each gets all). If I need to read without group management, I can use assign() to pick partitions manually, but then there is no rebalancing or failover. Two consumers in one group can never share a partition; if I need more parallelism I need more partitions.

Remember: in a group, one partition has one owner. Extra consumers beyond the partition count idle.

How does the consumer poll loop work, and what are max.poll.interval.ms and session.timeout.ms? Intermediate

A consumer runs a loop: poll(), process the records, commit, repeat. There are two separate liveness checks. A background thread sends heartbeats, and if the group coordinator hears nothing for session.timeout.ms (45 s default since 3.0) the consumer is declared dead. Separately, I must call poll() again within max.poll.interval.ms (5 minutes default), or the consumer is considered stuck and leaves the group, even though heartbeats were fine.

So the heartbeat detects a dead process, and the poll interval detects a live process with stuck processing. Heartbeats go every heartbeat.interval.ms (3 s). If a batch takes too long, lower max.poll.records (default 500) so each batch finishes inside the interval. The consumer object is not thread-safe: one consumer per thread.

while (running) {
    ConsumerRecords<String,String> recs = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String,String> r : recs) process(r);
    consumer.commitSync();     // after processing = at-least-once
}

Remember: heartbeat = "process alive", poll interval = "processing not stuck". Slow batch means rebalance.

What is a rebalance, and why can it hurt? Eager versus cooperative? Senior

A rebalance is the group re-deciding who owns which partitions. It happens when a consumer joins, leaves, crashes, misses the poll interval, or partitions change. In the classic eager protocol everyone gives up all partitions, then rejoins, so the whole group pauses and lag builds up. The cooperative protocol moves only the partitions that must move, and the others keep working.

Cooperative (CooperativeStickyAssignor, since Kafka 2.4) revokes only the moving partitions, over two short rounds. In Kafka 4.0 the new group protocol (KIP-848, group.protocol=consumer) lets the broker compute assignments with no global barrier, which is smoother still. Ways to reduce pain: use cooperative or the new protocol, use static membership (next question), keep processing within max.poll.interval.ms, and roll restarts slowly. Moving an existing group from eager to cooperative takes two rolling restarts: add the cooperative assignor alongside the old one, then remove the old one.

Remember: eager = stop the world; cooperative = move only what must move.

How do you stop restarts and deploys from triggering rebalances? Senior

I use static membership: give each consumer a stable group.instance.id (for example the pod name of a StatefulSet) and a session.timeout.ms longer than a restart. When that consumer restarts within the timeout, it gets its old partitions back and no rebalance happens. I also use the cooperative assignor, shut down gracefully, and roll pods one or two at a time.

The trade-off: a really dead static member keeps its partitions until the session timeout expires, so failover is slower. Graceful shutdown means catching SIGTERM, calling consumer.wakeup(), finishing the batch, committing, then close(). Without a graceful close the group waits for the session timeout. Set the Kubernetes termination grace period longer than your longest batch.

Remember: static id + longer session timeout + graceful close = quiet deploys.

How do offset commits work? Auto versus manual, sync versus async. Intermediate

Committing an offset tells Kafka "this group has processed everything before this offset", and after a crash the group restarts from there. Auto commit (the plain-consumer default) commits every 5 seconds inside poll() and can mark records done before I finished them, so a crash loses them. I turn it off and commit manually after processing succeeds, which gives at-least-once.

commitSync() blocks and retries, so it is the simplest and safest. commitAsync() is faster but does not retry, because a retry could overwrite a newer commit with an older one. A common pattern is async in the loop and one sync commit on shutdown. I commit the offset of the next record to read, which is the last processed offset plus 1. Per batch is cheaper; per record is safer for slow, side-effect-heavy work but costs more requests.

consumer.commitSync(Map.of(
    new TopicPartition("orders", 0),
    new OffsetAndMetadata(lastProcessedOffset + 1)));
Watch out: committing N instead of N+1 re-reads one record; committing before processing loses records on a crash.

Remember: process, then commit last offset + 1. Auto commit off for anything important.

What do you do in a ConsumerRebalanceListener? Senior

In onPartitionsRevoked I finish or flush in-flight work for those partitions and commit their offsets, so the next owner does not redo them. In onPartitionsAssigned I can load state or seek to a position stored in my own database. onPartitionsLost is called when the group already took the partitions away, where committing is impossible, so I just drop local state.

It matters most when work is handed to a thread pool: the revoke callback must wait for in-flight tasks of the revoked partitions, otherwise the new owner and the old worker both process the same records. With cooperative rebalancing the callbacks cover only the moved partitions.

Remember: revoked = finish and commit; assigned = load state; lost = just drop.

How can a consumer rewind, replay or skip data? Intermediate

In code I call seek(partition, offset), seekToBeginning, seekToEnd, or offsetsForTimes to find the offset for a timestamp and seek there. From the command line, with the group stopped, kafka-consumer-groups.sh --reset-offsets moves the group to earliest, latest, a timestamp, a shift, or a specific offset. I always run --dry-run first, then --execute.

Typical uses: replay the last 2 hours after a bug fix, skip one poison record by moving one offset forward, or start a new group from the beginning for a backfill. Replay repeats side effects, so the handler must be idempotent.

kafka-consumer-groups.sh --bootstrap-server b1:9092 --group billing \
  --topic orders --reset-offsets --to-datetime 2026-11-17T08:00:00.000 --dry-run

Remember: stop the group, dry-run the reset, execute. Replays need idempotent handlers.

What is consumer lag and how do you measure it? Basic

Lag for a partition is the log end offset minus the group's committed offset: how many records are waiting that the group has not processed. Total lag is the sum across partitions. A small steady lag is normal. What matters is the trend: growing lag means consumers are slower than producers.

I read it with kafka-consumer-groups.sh --describe --group X or via monitoring (the consumer's records-lag-max metric, Burrow, Prometheus exporters). Look per partition: one partition with big lag and the rest at zero means a hot key or one stuck consumer. Lag in records is not delay in time, so also track the age of the oldest unprocessed record.

GROUP   TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
billing orders  0          1500            1520            20
billing orders  1          900             5900            5000   <- problem

Remember: lag = log end offset minus committed offset. Watch the trend and the per-partition shape.

What does auto.offset.reset do, and what goes wrong with the default? Intermediate

It decides where a consumer starts when its group has no valid committed offset: latest (the default) jumps to the end, earliest starts from the oldest available record, and none throws an error. The danger of latest is silent data skipping: a brand-new group misses all history, and an old group whose offsets were deleted skips everything it missed.

It applies in two cases: a new group id, and an offset that is out of range, for example because retention deleted it while the group was down, or the committed offsets of an idle group expired (offsets.retention.minutes, default 7 days). For consumers that must not miss data I set earliest, or none so it fails loudly. A new service that needs history must also check that the history is still within retention.

Remember: no offset means auto.offset.reset applies. Default latest silently skips data; choose it on purpose.

5. Delivery semantics, exactly-once and transactions

Explain at-most-once, at-least-once and exactly-once delivery in Kafka. Intermediate

At-most-once means a record is processed zero or one time: commit the offset before processing, and a crash loses the record. At-least-once means one or more times: process first, then commit, and a crash between them causes a re-read, so duplicates. Exactly-once means the effect happens once. Kafka can do that inside Kafka with transactions; for outside side effects I use at-least-once plus idempotent processing.

At-least-once is the normal default and what most systems use. Exactly-once inside Kafka means read from a topic, write to a topic and commit the input offset atomically. For an email, a REST call or a payment, the broker cannot make the call and the commit one atomic step, so the honest summary is: exactly-once effect = at-least-once delivery + idempotent processing.

Remember: commit first = may lose, process first = may duplicate. Exactly-once = at-least-once + idempotence.

How do Kafka transactions work, and what do isolation.level and transactional.id do? Senior

A transactional producer, identified by a stable transactional.id, begins a transaction, writes to one or more topics, adds the consumer's input offsets to the same transaction, and commits. Either all writes and the offset commit become visible, or none do. Consumers with isolation.level=read_committed only see committed data. This is how Kafka Streams gets exactly-once.

A transaction coordinator on a broker tracks state in __transaction_state, and on commit writes a marker into every partition touched. After a restart, the same transactional.id bumps an epoch, which fences the old "zombie" instance so two copies cannot both commit (ProducerFencedException). The default isolation.level is read_uncommitted. A read_committed reader waits at the last stable offset, so one long-open transaction (a hung producer) holds back everything after it until it commits, aborts or times out (transaction.timeout.ms, 60 s by default). Limits: it covers only Kafka reads and writes, and it adds some latency.

producer.initTransactions();
while (true) {
  var recs = consumer.poll(Duration.ofMillis(500));
  producer.beginTransaction();
  try {
    for (var r : recs) producer.send(new ProducerRecord<>("out", r.key(), transform(r.value())));
    producer.sendOffsetsToTransaction(offsetsOf(recs), consumer.groupMetadata());
    producer.commitTransaction();
  } catch (Exception e) { producer.abortTransaction(); }
}

Remember: output + offsets commit atomically; transactional.id plus epoch fences zombies; readers use read_committed.

Is Kafka's exactly-once really exactly once? Where does it stop? Senior

It is exactly-once for a pipeline that lives entirely inside Kafka: read topics, compute, write topics, with offsets committed in the same transaction. It stops at the edge of Kafka. If my code calls a payment API, writes to a database or sends an email inside the loop, that action is not part of the Kafka transaction, so after an abort and reprocess it can happen twice.

For those side effects I make the operation idempotent: pass an idempotency key to the API, use an upsert or a unique constraint, or store the processed id. For database sinks there is another route: store the consumer offset in the same database transaction as the result, and on restart seek to that stored offset. That gives an exactly-once effect without Kafka transactions.

Remember: exactly-once holds inside Kafka only. Outside, use idempotent writes or offset-in-the-same-DB-transaction.

How do you build an idempotent consumer? Senior

I assume every record can arrive twice, then make handling it twice have the same effect as once. The most robust way is a dedup table: in the same database transaction as the business change, insert the event's unique id into a processed_events table with a unique constraint. A duplicate hits the constraint and is skipped.

Other techniques: natural idempotence (set status to SHIPPED, upsert by primary key), version checks (apply an event only if its version is higher than stored), and passing idempotency keys to other services. The key point is atomicity: the dedup check and the effect must be in one transaction, or a crash between them reopens the gap. Expire old ids after a window longer than your longest replay. Topic, partition and offset can be the dedup key, but a business id also protects against duplicates created by the producer.

@Transactional
void handle(OrderEvent e) {
  if (!processedRepo.insertIfAbsent(e.eventId())) return;  // unique key, duplicate skipped
  orderRepo.apply(e);
}

Remember: the dedup check and the effect must commit together, in one transaction.

Where can a Kafka message be lost end to end? Senior

I walk the path in three places. Producer: acks=0 or 1, an ignored callback, a crash before flush(). Broker: replication factor 1, min ISR 1, unclean leader election, or retention deleting data before a slow consumer read it. Consumer: committing before processing, auto commit, handing work to threads and committing early, or swallowing an exception and moving on.

The safe recipe: acks=all, replication 3, min ISR 2, unclean election off, handle the producer callback, commit only after processing, and send failures to a dead-letter topic instead of skipping. A good debugging first step is to check whether the record is in the topic: if yes, the consumer lost it; if no, the producer never delivered it.

Remember: producer acks and callbacks, broker replication and retention, consumer commit order and swallowed errors.

Where do duplicates come from in a Kafka system? Intermediate

Mostly from at-least-once working as designed. On the consumer side: a crash or rebalance after processing but before the commit, a consumer kicked out for exceeding max.poll.interval.ms whose work is redone elsewhere, or an operator replaying offsets. On the producer side: a lost acknowledgement causing a retry (fixed by idempotence), or my application sending the same event twice after a crash or double click.

A source connector can also re-deliver after a restart. The answer is rarely "stop duplicates at the source"; it is "make consumers idempotent", and shrink the window by committing promptly and handling rebalances in the listener.

Remember: duplicates are normal in at-least-once. Fix them with idempotent consumers, not hope.

6. Retries, dead-letter topics, poison pills and backpressure

What is a poison pill message and how do you handle it? Intermediate

A poison pill is a record that always fails: a payload that cannot be deserialized, a value that triggers a bug, or a rule violation. Because a partition is processed in order, the consumer cannot skip it on its own. It throws, the offset is not committed, the next poll returns the same record, and the partition is stuck while lag climbs. I retry a few times for temporary problems, then publish the record to a dead-letter topic with the error in headers, commit the offset and move on.

Deserialization failures need extra care because they happen inside poll(), before my code sees a record. Wrap the real deserializer in an error-handling one (Spring's ErrorHandlingDeserializer) so the failure becomes a value I can route. Skipping silently loses data, while a dead-letter topic keeps it for inspection and replay. Permanent errors (bad schema, validation failure) should not be retried at all. Alert on dead-letter traffic.

Remember: retry briefly, then dead-letter and commit. Never loop forever, never skip silently.

Design a retry and dead-letter strategy for a consumer. Senior

First I split errors into temporary (database down, timeout) and permanent (bad data). Permanent errors go straight to the dead-letter topic. For temporary ones I choose between blocking retry, which retries in place with backoff and keeps order but stalls the partition, and non-blocking retry topics, which publish the failed record to orders-retry-1, orders-retry-2 and finally orders-dlt so the main topic keeps flowing at the cost of order.

Blocking retry fits short blips where order matters, but a long backoff risks max.poll.interval.ms. Retry topics fit slower recovery where throughput matters; the delay is done by pausing the partition until the record's timestamp plus the delay has passed (Spring's @RetryableTopic automates this). In headers I keep the original topic, partition, offset, exception text and attempt count, and I keep a tested runbook for replaying the dead-letter topic after a fix.

Remember: permanent = dead-letter now; temporary = blocking retry (keeps order) or retry topics (keeps flow).

How do you handle bad messages and deserialization errors in Spring Kafka? Senior

I wrap the value deserializer in ErrorHandlingDeserializer, so a bad payload becomes a record carrying the failure instead of an exception inside poll(). Then I configure a DefaultErrorHandler with a back-off and a DeadLetterPublishingRecoverer, which publishes failed records, with exception headers, to topic.DLT.

I mark exceptions that are not worth retrying (validation errors, IllegalArgumentException) as not retryable with addNotRetryableExceptions, so they go to the dead-letter topic at once. For batch listeners I throw BatchListenerFailedException with the index of the bad record, so only that record is retried or dead-lettered. For JSON, restrict trusted packages so a header cannot make you deserialize arbitrary classes. The default back-off and retry count differ by Spring Kafka version, so set it explicitly.

spring.kafka.consumer.value-deserializer=org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
spring.kafka.consumer.properties.spring.deserializer.value.delegate.class=io.confluent.kafka.serializers.KafkaAvroDeserializer

Remember: ErrorHandlingDeserializer + DefaultErrorHandler + DeadLetterPublishingRecoverer, and mark permanent errors non-retryable.

Consumers pull. How do you handle backpressure and a slow downstream system? Senior

Kafka gives natural backpressure: a slow consumer just reads less and lag grows, while the broker is unaffected. The danger is inside my process: polling fast into an unbounded in-memory queue, which ends in an out-of-memory crash. So I bound the queue, and when the downstream is slow or down I use consumer.pause(partitions), which keeps calling poll() (so heartbeats and the poll interval stay healthy) but returns no records, then resume() when it recovers.

Spring Kafka's listener container supports pausing too. I also cap max.poll.records, wrap the downstream call in a circuit breaker with timeouts, and rate-limit. On the producer side a full buffer makes send() block, which slows the producer naturally.

Remember: bounded queue, pause() while downstream is down, keep polling so you are not kicked out.

One consumer thread is too slow for a partition. How do you go faster without breaking order? Senior

The cleanest answer is more partitions and more consumers. If that is not possible, I parallelize inside the consumer: poll a batch, split records by key into lanes, give each lane to a worker so one key stays in order on one lane, and commit only up to the highest offset that is fully done below all unfinished ones.

The hard parts are partial failures (commit only up to the lowest unfinished offset), rebalances (finish or drop work in onPartitionsRevoked), and more duplicates after a crash, so the handler must be idempotent. Confluent's Parallel Consumer library implements this model. Cheaper alternatives: batch the database inserts, and use asynchronous calls with bounded concurrency.

Remember: parallel by key lanes, commit only the contiguous finished prefix, handler idempotent.

7. Ordering, partition count, compaction, hot partitions

What ordering does Kafka guarantee, and how do you design for "process orders in order"? Intermediate

Kafka guarantees that records one producer sends to one partition are appended in the order sent, and consumers read a partition in offset order. There is no order across partitions. So to keep order for one entity I use the entity id (orderId, accountId) as the key, so all its records land in one partition, and one consumer processes that partition sequentially.

Three things must hold together: same key, idempotent producer (so retries do not reorder), and sequential processing per partition on the consumer (no free-for-all thread pool). Global order for a whole topic needs one partition, which caps throughput to one consumer, so most designs settle for per-key order. If two services publish events about the same order, only arrival order at the broker is kept, not business order. Route them through one producer, or add a version number so the consumer ignores stale events, or model the state machine so a consumer parks "shipped" until "paid" arrives.

Remember: order = same key, same partition, idempotent producer, sequential consumer. No global order.

How do you decide how many partitions a topic needs? Senior

I work from throughput. I measure what one consumer can handle per partition for my real work, divide the target throughput by that, and add headroom, often 2x to 3x, because the count is hard to change later. I also think about the maximum consumer parallelism I may want, since consumers cannot exceed partitions.

Too few partitions cap parallelism and create hot spots. Too many cost more open files and memory on brokers, longer leader election and recovery, more replication traffic and more rebalance work. Sensible sizes are often 6 to 50 for a busy topic. For key-ordered topics treat the number as a fixed contract, because adding partitions moves keys.

Remember: partitions = target throughput / per-partition rate, plus headroom. Easy to add, impossible to remove.

And what happens to ordering if you add partitions to a keyed topic? Senior

Ordering breaks for existing keys during the change. The partitioner computes hash(key) mod partitionCount, so going from 6 to 12 partitions sends many keys to a different partition. Old records of a key sit in the old partition, new ones go to the new one, and two consumers can process the same key at once, with new records overtaking older ones still in lag.

Safe options: pick enough partitions up front; or add partitions only when lag is zero and producers are paused; or create a new topic with the larger count and migrate consumers over. Also make consumers version-aware so stale events are ignored. A compacted topic can end up with the same key in two partitions, so compaction no longer keeps one latest record per key across the whole topic.

Remember: hash(key) mod N changes when N changes, so keys move and order breaks. Drain first or use a new topic.

What is a hot partition and how do you fix it? Senior

A hot partition receives far more traffic than the others, usually from key skew: one big tenant or popular product generates most events, or the key has few distinct values. I see one partition's lag growing while others are near zero. I fix it by choosing a higher-cardinality key, or salting a known heavy key (tenant plus a sub-key hash), or giving the heavy tenant its own topic.

Salting like tenantId + ":" + (customerId hash mod 8) spreads the tenant over 8 partitions but keeps order only per sub-key, so check that is acceptable. You can do this with a custom Partitioner or simply by building the key. On the consumer side, key-lane parallelism can speed a single hot partition. Measure first with per-partition bytes and lag, because guesses are often wrong. Use the smallest key that gives the order you need: a broader key means bigger hot spots.

Remember: hot partition = skewed key. Higher-cardinality key or salt the heavy key, and accept weaker order.

What is log compaction, and when would you use it? Intermediate

With cleanup.policy=compact Kafka does not delete by age. A cleaner keeps only the most recent record for each key and drops older ones, so the topic always holds at least the latest value of every key. A new consumer reads it from the start and rebuilds the current state, like a table. I use it for entity state, lookup tables, and changelogs.

Examples: user profiles, product prices, Kafka's own __consumer_offsets, and Kafka Streams changelog topics. Compaction is eventual: the active segment is not compacted and old duplicates stay until the cleaner runs. Records must have a key. To delete a key, send a record with a null value (a tombstone); it is kept for delete.retention.ms (24 h by default) so readers can see it, then removed. Offsets of survivors do not change, so gaps appear. You can combine both: compact,delete.

Remember: compaction = latest value per key, null value = delete. Good for state, not for event history.

How do you design topics for a new domain: one topic per event type or one big topic? Senior

The deciding question is ordering. Events that must stay in order relative to each other (OrderCreated, OrderPaid, OrderShipped for one order) go in one topic keyed by the order id, because order exists only inside a partition. Unrelated event types with different consumers, volumes and retention go in separate topics. A topic per entity type, keyed by entity id, is a good default.

I also decide whether the topic is an event stream (delete by time) or entity state (compacted), choose key, partitions and retention deliberately, use clear names (such as domain.entity.event.v1), and put a schema and version on every payload rather than one topic per schema version. Avoid "one topic for everything", which forces every consumer to read and discard what it does not need.

Remember: same-order events share a topic and a key; unrelated streams get their own topic.

8. Schema Registry, Avro and schema evolution

What is the Schema Registry, and why use Avro or Protobuf instead of plain JSON? Intermediate

Kafka only moves bytes, so the contract lives in my serializers. The Schema Registry is a service that stores schema versions and gives each an id. The producer writes each record as a magic byte, the 4-byte schema id and a compact binary body, and the consumer fetches the schema by id (cached) to decode it. The registry also rejects a new schema that is incompatible with the old ones, so a breaking change fails at deploy time instead of breaking consumers at night.

Plain JSON has no enforced contract: any producer can rename a field silently. Avro and Protobuf give smaller messages because field names are not repeated, plus checked evolution. The cost is an extra service to run and a start-up dependency. Another common failure with any serializer is a bad record whose deserialization throws inside poll(), so plan for poison pills.

Remember: schema id in every record, schema in the registry, compatibility checked before deploy.

Explain schema compatibility: backward, forward, full. How do you roll out a breaking change? Senior

Backward compatible means consumers on the new schema can read old data, so I upgrade consumers first; allowed changes are adding a field with a default or deleting a field. Forward compatible means consumers on the old schema can read new data, so I upgrade producers first. Full means both directions. The registry default is backward. For a truly breaking change I do not force it: I create a new topic or version, dual-write for a while, move consumers over, then retire the old one.

The "transitive" variants check against all earlier versions, not just the last one; with retention and replay, backward-transitive or full-transitive is safest. Practical rules: always give new fields a default, never rename or retype a field (add a new one, migrate, drop the old one). The registry checks structure, not meaning: changing "amount" from dollars to cents passes every check and still breaks everyone, so coordinate with consumer teams.

Watch out: people mix up backward and forward, and add required fields without a default.

Remember: backward = upgrade consumers first, forward = producers first. New fields need defaults; never rename.

9. Kafka Streams, Connect, CDC and the outbox pattern

What is Kafka Streams, and how is it different from a plain consumer or from Spark and Flink? Intermediate

Kafka Streams is a Java library, not a cluster. I add it to my normal application, define a topology (read topics, filter, map, join, aggregate, write topics), and run as many app instances as I like; they share the work using the same partition assignment as a consumer group. State lives in local stores (RocksDB) backed by compacted changelog topics, so a replacement instance can rebuild it.

Compared with a hand-written consumer, I do not manage offsets, state or rebalancing myself, and I get windowing, joins, aggregations and exactly-once (processing.guarantee=exactly_once_v2). Compared with Spark or Flink, which run on their own cluster and handle many sources, Streams is simpler to deploy but limited to JVM languages with Kafka in and Kafka out. A KStream is an unbounded series of events; a KTable is the latest value per key. Key joins need both topics co-partitioned: same partition count and same partitioning rule.

Remember: Streams = a library in your app, state in RocksDB + changelog topic. No separate cluster.

What is Kafka Connect, and why use it instead of writing producers and consumers? Intermediate

Kafka Connect is a runtime for moving data between Kafka and other systems using ready-made connectors configured in JSON, with no code. A source connector pulls data into Kafka (a database, files, an API); a sink connector pushes it out (Elasticsearch, S3, a warehouse, JDBC). It handles batching, retries, offset tracking, scaling across workers and restarting failed tasks, so I write code only when no connector fits.

Offsets of connectors are stored in internal Kafka topics, delivery is at-least-once, so sinks should be idempotent (upsert mode). Single Message Transforms (SMTs) apply small changes like renaming or masking fields. Bad records can be parked in a dead-letter topic with errors.tolerance=all and errors.deadletterqueue.topic.name. When a task shows FAILED, I read its trace from the Connect REST status endpoint, fix the cause (credentials, schema, constraint), and restart the task.

{ "name": "orders-sink",
  "config": {
    "connector.class": "io.confluent.connect.jdbc.JdbcSinkConnector",
    "topics": "orders",
    "insert.mode": "upsert",
    "pk.mode": "record_key",
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "orders-sink-dlq" } }

Remember: source in, sink out, config not code. At-least-once, so upsert on sinks.

What is change data capture (CDC) and how does Debezium use Kafka? Intermediate

CDC turns every insert, update and delete in a database into an event. Debezium does it by reading the database's own transaction log (MySQL binlog, PostgreSQL write-ahead log) instead of querying tables. That is light on the database, captures deletes, and keeps commit order. Each table becomes a topic keyed by primary key, with before and after rows in each event.

It first takes a snapshot of existing rows, then streams changes. Delivery is at-least-once, so consumers must be idempotent. In PostgreSQL the replication slot keeps log files until the connector confirms them, so a stopped connector can slowly fill the database disk. Monitor slot lag, and cap it with max_slot_wal_keep_size (PostgreSQL 13 and later).

Remember: CDC reads the DB log, not the tables. Watch the replication slot if the connector stops.

What is the outbox pattern and why do we need it? Senior

It solves the dual-write problem: a service must save to its database and publish an event to Kafka, and those are two systems. If it writes the database then crashes before sending, the event is lost; if it sends first and the database rolls back, the event describes something that never happened. With the outbox, I insert the event into an outbox table in the same local database transaction as the business change, and a separate process publishes outbox rows to Kafka afterwards.

Because the database transaction is atomic, both rows commit or neither does. The publisher is either a poller reading unsent rows (simple, but adds load and delay) or, better, Debezium reading the outbox table's log with the Outbox Event Router. Delivery is at-least-once, so consumers dedupe by the event id. Key the event by aggregate id to keep per-entity order. Clean old outbox rows on a schedule.

Remember: one DB transaction writes data and event; a relay publishes later, at-least-once.

10. Spring Kafka, testing and monitoring

How do you use Kafka with Spring Boot? What does @KafkaListener do? Intermediate

Spring for Apache Kafka gives me KafkaTemplate to send and @KafkaListener to receive. Behind a listener is a listener container that owns one or more real KafkaConsumer threads, runs the poll loop, calls my method per record (or batch) and commits according to an ack mode. concurrency sets the number of consumer threads, so it is useless above the partition count.

The default ack mode is BATCH: offsets are committed after the whole poll batch was handled successfully, and Spring turns off the client's auto commit. My method runs on the consumer thread, so a slow method blocks its partition and can exceed max.poll.interval.ms. Errors go to a DefaultErrorHandler with a back-off and an optional DeadLetterPublishingRecoverer. @RetryableTopic creates delayed retry topics and a dead-letter topic automatically. For manual commits use AckMode.MANUAL and call ack.acknowledge().

@KafkaListener(topics = "orders", groupId = "billing", concurrency = "3")
void on(ConsumerRecord<String, OrderEvent> rec) {
   billingService.charge(rec.value());   // exception triggers the error handler
}

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object,Object> t) {
  var recoverer = new DeadLetterPublishingRecoverer(t);
  return new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));
}

Remember: listener = container + real consumer threads. concurrency up to partitions; failures go to the error handler.

How do you test Kafka code? Intermediate

In layers. I keep business logic free of Kafka types so handlers are plain methods with unit tests. For integration I run a real broker with Testcontainers (a Kafka container), produce a record and wait with a timeout (Awaitility) for the effect. Spring's @EmbeddedKafka is a lighter in-JVM alternative, and Kafka Streams has TopologyTestDriver that needs no broker.

I test unhappy paths on purpose: the same record delivered twice, a poison record landing in the dead-letter topic, an out-of-order event, and a consumer restart mid-batch. For contracts between teams I add a schema compatibility check to the build, so breaking changes fail before deploy.

Remember: unit-test the handler, integration-test with Testcontainers, and test duplicates and poison records.

What would you monitor for a Kafka-based service you own? Intermediate

On the consumer side: lag per partition and its trend, the age of the oldest unprocessed record, rebalance count, handler latency, error and dead-letter counts, and how close I am to max.poll.interval.ms. On the producer side: send error rate, request latency, retries, and buffer wait time. The platform team usually owns under-replicated and offline partitions, but I should know to watch them.

I alert on symptoms with business meaning, such as "lag older than 5 minutes" or "records arrived in the dead-letter topic", not on raw CPU. I log topic, partition, offset and a trace id on each send and receive so one record can be followed end to end.

Remember: lag trend, rebalances, dead-letter counts and handler latency. Log topic-partition-offset.

11. Kafka versus RabbitMQ and others

Kafka versus RabbitMQ (or SQS): how do you choose? Intermediate

I choose Kafka for event streaming, data pipelines, event sourcing, CDC, replay, and many independent readers of the same events, with high throughput and per-key ordering. I choose RabbitMQ or SQS for job queues where each message is handled once and forgotten, with per-message acknowledgement, retries, delays, priorities or complex routing.

RabbitMQ is a smart broker: exchanges and bindings route messages, the broker pushes to consumers and deletes after ack. Kafka is a simple log: consumers pull, data is retained and replayable, fan-out is just another consumer group. SQS is a managed queue: no replay, delay and dead-letter built in, nothing to run. Pitfalls: using Kafka as a task queue is awkward because one slow record blocks its partition and there is no per-message delay or retry; using RabbitMQ for huge replayable streams is the wrong tool. Pulsar is another log-style option with built-in multi-tenancy but a smaller ecosystem. Kafka is also adding queue-like "share groups" (KIP-932, new in recent 4.x releases), which narrows this gap.

AspectKafkaRabbitMQSQS
ModelReplicated log, pullBroker with routing, pushManaged queue, polling
ReplayYes, by offset or timeNo (streams feature aside)No
OrderingPer partitionPer queue, weaker with many consumersFIFO queues per group
Best forStreams, pipelines, many readersTask queues, rich routingSimple managed queue in AWS

Remember: need history and many readers, pick Kafka. Need a task queue with per-message features, pick RabbitMQ or SQS.

When should you NOT use Kafka? Senior

I would not use Kafka for a small number of simple jobs that need delay, per-message retry or priority (use SQS or RabbitMQ), for synchronous request and response (use HTTP or gRPC), as a database for lookups by key or ad hoc queries, or when a small team has no platform support to run a cluster and no managed option.

Also be careful with very large payloads (use the claim-check pattern: store the file in object storage and send a link) and with requirements for global ordering across all events. Naming these limits shows I pick tools from requirements, not habit.

Remember: not for task queues, request-reply, random lookups, or huge payloads.

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

After a release, consumer lag on the orders topic grows every minute. What do you do? Senior

I look at the shape of the lag first. All partitions growing means the handler got slower or traffic spiked; one partition means a hot key or a stuck consumer; lag in waves means a rebalance loop. Then I find the bottleneck, usually a slow call added in the release, and roll back or fix it before scaling anything.

Situation: producers write at the same rate as before, but the billing group falls behind and the lag alert fires.

Check first: per-partition lag and group state, then what changed in the release (a new database call, a bigger payload, a lower max.poll.records, fewer pods), then handler latency metrics.

kafka-consumer-groups.sh --bootstrap-server b1:9092 --describe --group billing
kafka-consumer-groups.sh --bootstrap-server b1:9092 --describe --group billing --state

Fix: fix the slow call (batch inserts, an index, a cache). If pods were cut, scale back up but only to the partition count, because extra consumers sit idle. Rate-limit to protect downstream while catching up. Lag drains at consume rate minus produce rate, so estimate the time for stakeholders.

Prevent: load test the consumer after changes, alert on lag trend and age, track handler p99 latency.

Remember: read the lag shape first (all, one, or waves), then find the slow step. Never add consumers beyond partitions.

Customers were charged twice because the payment consumer processed some messages two times. Why, and how do you fix it? Senior

It is almost always at-least-once working as designed: a pod was killed or a partition moved after the charge but before the offset commit, so the next owner re-read the record. The fix is an idempotent handler: dedupe by event id in the same database transaction as the payment, and pass the same id to the payment provider as its idempotency key.

Situation: a few payments appear twice, mostly around deployments and slow periods.

Check first: match duplicates to rebalances, restarts and long processing; check whether offsets are committed before or after the charge, whether max.poll.interval.ms was exceeded, and whether the producer published the same event twice (compare event ids).

Fix: insert the event id into a processed_events table with a unique key in the same transaction as the payment record. Commit offsets after processing, commit in onPartitionsRevoked, and stop gracefully. Refund the duplicates found by a reconciliation query.

Prevent: idempotency by design for any side effect, and a test that delivers the same message twice.

Remember: at-least-once means duplicates happen. Dedupe by event id inside the same transaction as the effect.

The consumer group keeps rebalancing every few minutes and almost no work gets done. What is going on? Senior

Members keep leaving the group, usually because a poll batch takes longer than max.poll.interval.ms, because GC or CPU starvation misses heartbeats, or because pods keep restarting. The fix is to make each batch fit the interval (lower max.poll.records), use cooperative rebalancing and static membership, and stop the crash loops.

Situation: logs show "Revoking previously assigned partitions", "Attempt to heartbeat failed since group is rebalancing" and "commit failed, the group has already rebalanced". Lag rises and falls in waves.

Check first: why do members leave? Slow batch over the poll interval, long GC pauses or tight container CPU limits beyond session.timeout.ms, or crash loops and autoscaler flapping.

Fix: lower max.poll.records or raise max.poll.interval.ms; move slow calls off the poll thread carefully; add static membership (group.instance.id); use the cooperative assignor or the new group protocol; give pods proper CPU and memory and tune GC; fix crash loops; roll one pod at a time.

Prevent: alert on rebalance rate and test with realistic slow downstream responses.

Remember: slow batch causes rebalance causes redo causes slow batch. Break the loop with smaller batches and stable members.

A producer team says they sent an event but the consumer never got it. Where do you look? Senior

I first prove which side is wrong by looking for the record in the topic by key and time window with a console consumer. If it is there, the consumer skipped it or it went to a dead-letter topic. If it is not there, the producer never delivered it.

Situation: one business event is missing downstream.

Check first: search the topic by partition and offset or timestamp. Record present: look for a swallowed error, a filter, the wrong group, offset reset to latest, retention passing while the group was down, or the dead-letter topic. Record absent: look for ignored callback errors, acks=0/1 with a failover, a process killed before flush(), wrong topic or key, an aborted transaction (the reader uses read_committed), or a dual-write crash.

kafka-console-consumer.sh --bootstrap-server b1:9092 --topic orders \
  --partition 3 --offset 120000 --max-messages 50 --property print.key=true --property print.offset=true

Prevent: durable producer config, always handle callbacks, the outbox pattern for database-triggered events, logging topic-partition-offset on send and receive, and alerts on dead-letter traffic.

Remember: in the topic = consumer problem. Not in the topic = producer problem.

A single bad record has stopped a partition for an hour. How do you unblock and prevent it? Senior

I read the bad offset with a console consumer to see why it fails. If it is bad data, I copy it to a quarantine topic, stop the group and reset its offset to just past the bad record. If it is a bug in my code, I fix and redeploy. Then I add a dead-letter flow so it never blocks again.

Situation: one partition shows growing lag and the same stack trace at the same offset. Other partitions are fine.

Check first: the offset in the log message, then the record itself (bad JSON, wrong schema id, null where a field is required).

Fix now: kafka-consumer-groups.sh --reset-offsets --to-offset BAD+1 --topic orders:3 --execute with the group stopped, after saving the record.

Prevent: ErrorHandlingDeserializer, a DefaultErrorHandler with limited retries and a DeadLetterPublishingRecoverer, no retries for permanent errors, validation at the producer, schema compatibility checks, and an alert on dead-letter traffic.

Remember: quarantine, skip one offset, then add dead-letter handling so one record cannot block a partition.

One partition has ten times the lag of the others and one broker is at 90 percent CPU. What is happening? Senior

Key skew: one key, often a big tenant, produces most of the traffic and all of it lands in one partition. I confirm by sampling the keys on that partition, then spread the heavy key by salting it with a sub-key, or give that tenant its own topic.

Situation: 12 partitions, keyed by tenantId, and partition 7 receives most of the bytes.

Check first: per-partition bytes-in and counts, then a console consumer with print.key=true on partition 7.

Fix: short term, give that consumer more room (faster hardware, key-lane parallelism). Medium term, key heavy tenants as tenantId + ":" + (customerId hash mod N) so they spread over N partitions; per-tenant order becomes per-customer order, so check that is acceptable. Switch keys at a clean point (drain the topic) because changing keys affects order at cut-over.

Prevent: high-cardinality keys, load tests with realistic skew, per-partition dashboards.

Remember: one partition lagging = skewed key. Salt the heavy key and accept weaker order.

After the team added partitions to scale, events for the same customer are processed out of order. Why? Senior

Because the key-to-partition formula, hash(key) mod partitionCount, changed. For roughly half of the keys, new events go to a new partition while older events still wait in the old one, so two consumers handle the same customer at once. I make consumers version-aware to protect order, and in future drain the topic before adding partitions, or migrate to a new topic.

Situation: the topic went from 6 to 12 partitions. Since then "AccountClosed" is sometimes processed before the earlier "PaymentPosted".

Fix: find affected entities by comparing event timestamps or versions with processing order and re-apply in the right order. Make the consumer ignore or re-queue events older than the stored version. For strict order going forward: stop producers, let lag drain to zero, add partitions, restart; or create a new topic with the right count and migrate.

Prevent: size partitions with headroom, treat the count as fixed for keyed topics, and carry a version or sequence in events.

Remember: change N and keys move. Version your events so consumers can survive it.

Producers suddenly throw NotEnoughReplicasException. What does it mean and what do you do? Intermediate

It means at least one partition's in-sync replica set has fewer members than min.insync.replicas, and the producer uses acks=all, so the broker refuses the write on purpose to protect durability. The cause is usually a broker that is down or lagging. I restore it, and meanwhile retry or queue events instead of lowering min ISR.

Situation: sends to payments fail while other topics work.

Check first: kafka-topics.sh --describe --under-min-isr-partitions, then which broker is out (down, slow disk, network) and why followers fell behind. Usually the platform team owns the fix.

Application side: the producer retries for delivery.timeout.ms; beyond that, store events locally (outbox) or return a clear "try later" instead of losing data. Do not set min ISR to 1 just to stop the errors unless the business accepts the risk.

Prevent: alert on under-replicated partitions early, and use replication factor 3 across zones.

Remember: ISR below min.insync.replicas = writes refused by design. Fix the broker, do not lower the guard.

A consumer was down over a long weekend and, after restart, it silently skipped a large chunk of data. Why? Senior

The data it needed aged out of retention while it was down, so its committed offset no longer existed. With auto.offset.reset=latest it jumped to the end and silently dropped everything it missed. I recover the gap from another source and set the reset policy to earliest or none.

Situation: topic retention is 3 days, the consumer was off for 4. With earliest it would start from the oldest remaining record, which is still a gap but at least reads what is left.

Same trap for a new group: a group with no committed offsets (new, or its offsets expired after 7 days idle) starts at latest and misses older data.

Fix: find the gap (compare offsets and event times), recover from the source system, a database, a mirrored cluster or a sink archive in S3, and replay. Prevent: retention longer than your worst outage, alerts when lag age approaches retention, an archive sink for critical topics.

Remember: retention shorter than downtime plus latest equals silent data loss.

A producer team deployed a schema change and three consumers crashed. How do you respond and prevent it? Senior

I roll the producer back to stop new bad records, then deal with the records already written: skip them to a dead-letter topic or ship a consumer fix that reads both shapes. To prevent it, enforce schema compatibility checks in the registry and in CI so an incompatible change is rejected before deploy.

Situation: after a deploy consumers throw deserialization errors or null pointer exceptions; amount changed from int to string, or a field was renamed.

Steps now: each record carries its schema id, so I can bound which offsets were written with the new schema and then replay or repair them.

Prevent: registry compatibility set to backward (or full) transitive, a CI compatibility check, a rule never to rename or retype fields (add new, migrate, remove old), and consumer-driven contract tests. The registry checks structure, not meaning, so talk to consumers about semantic changes.

Remember: roll back, bound the bad offsets, then make compatibility checks a deploy gate.

Every deployment causes duplicate processing and a burst of lag. How do you make deployments quiet? Senior

Pods are being killed mid-batch, so offsets are not committed and each restart triggers rebalances. I make shutdown graceful (catch SIGTERM, finish the batch, commit, close), use static membership with the cooperative assignor, and roll pods one or two at a time. The handler stays idempotent for leftover duplicates.

Situation: a rolling update of 10 pods triggers many rebalances, and pods die in the middle of processing.

Steps: in the shutdown hook call consumer.wakeup(), finish, commit, then close() so the member leaves cleanly (Spring Kafka does this on context close if the grace period is long enough). Set terminationGracePeriodSeconds above your longest batch. Use group.instance.id from a StatefulSet pod name and a session timeout that covers a restart. Set maxSurge and maxUnavailable low.

Prevent: a "deploy under load" test in staging, and rebalance count as a release metric.

Remember: wakeup, finish, commit, close. Static ids and slow rolling updates.

Producers fail with RecordTooLargeException for some documents. What are your options? Intermediate

The default limit is about 1 MB. My preferred fix is the claim-check pattern: store the large payload in object storage and send a small event with the link, size and checksum. Raising the limits works but must be done consistently in several places and large records hurt memory and latency. Compression helps only if the data compresses well.

Situation: a few payloads are 5 MB.

Raising limits: broker or topic message.max.bytes (topic max.message.bytes), producer max.request.size, replica.fetch.max.bytes, and consumer max.partition.fetch.bytes and fetch.max.bytes. If any one is missed, producers or consumers fail.

Claim check: consumers fetch the file only when needed. Delete the object after retention and secure the link.

Remember: keep Kafka records small. Big payload goes to object storage, Kafka carries the link.

13. Rapid-fire round

Short answers to say in one breath. If the interviewer wants more, point to the full question above.

QuestionOne-line answer
What is a Kafka topic?A named, partitioned, append-only log. Records are kept by retention, not deleted on read.
Where is order guaranteed?Inside one partition only.
How does a key pick a partition?hash(key) mod partitionCount (murmur2 in the default partitioner).
What is an offset?A record's position in one partition. It is unique only per partition.
Max consumers working in one group?The partition count. Extra consumers sit idle.
Two groups on one topic?Each group gets every record, independently.
Why is Kafka fast?Sequential disk writes, batching, page cache, zero-copy sends.
What does acks=all mean?Wait for all in-sync replicas, with at least min.insync.replicas of them.
Durable setup?Replication factor 3, min.insync.replicas=2, acks=all, idempotence on.
What does the idempotent producer prevent?Duplicates and reordering from producer retries, per partition and per producer session.
Is idempotence on by default?Yes in current clients (3.0 and later), together with acks=all.
What does linger.ms do?Waits a bit so more records fill a batch. More throughput, a little more latency.
What is the ISR?The replicas that are caught up with the leader.
Unclean leader election?Choosing an out-of-sync replica as leader. Availability up, data loss risk. Off by default.
What makes a consumer leave a group?No heartbeats within session.timeout.ms, or no poll() within max.poll.interval.ms.
Eager versus cooperative rebalance?Eager revokes everything first; cooperative moves only the partitions that must move.
Static membership?group.instance.id: a restarted member keeps its partitions without a rebalance, within the session timeout.
Which offset do you commit?The next one to read, so last processed plus 1.
Auto commit risk?It can commit before processing finishes, so a crash loses work. Prefer committing after processing.
auto.offset.reset applies when?Only when there is no valid committed offset. Default is latest.
Default delivery guarantee?At-least-once when you commit after processing.
Exactly-once in Kafka?Idempotent producer plus transactions, within Kafka. Outside effects still need idempotent handlers.
What does read_committed do?Hides records from open or aborted transactions.
What is a poison pill?A record that always fails and blocks its partition. Retry briefly, then dead-letter.
Which errors should not be retried?Permanent ones: bad schema, validation failures.
What is a tombstone?A record with a key and null value. It deletes that key during compaction.
Can you reduce partitions?No. You can only add them, and adding them moves keys.
Hot partition cause?Skewed key. Fix with a better key or salting.
Which schema compatibility is default?Backward (upgrade consumers first).
What does Debezium read?The database's transaction log, not the tables.
Why the outbox pattern?To avoid the dual write: data and event commit in one database transaction.
Default max record size?About 1 MB. Use claim check for big payloads.
Kafka or RabbitMQ?Kafka for streams and replay; RabbitMQ for task queues and routing.
