What an application developer must know to package, ship, run and debug a service on containers and Kubernetes: images, Dockerfiles, Pods, Deployments, Services, probes, limits, Helm, and the failures you meet at 2 a.m. Basic, Intermediate and Senior, with model answers you can say aloud.

Mental model: the 8 ideas everything hangs on

One line: a container is an ordinary Linux process with a private view of the machine. An image is its read-only starting filesystem. Kubernetes is a control loop that keeps comparing "what you declared" with "what is running", and fixes the difference. Helm is a templating and release tool on top.
  1. A container is not a small VM. It is a normal process on the host kernel, isolated by namespaces (what it can see) and cgroups (how much it can use).
  2. An image is layers. Each Dockerfile step adds a read-only layer. A running container adds one thin writable layer on top, which is thrown away when the container is removed.
  3. Containers are disposable. Anything that must survive goes to a volume or an external store. Config comes from the environment, not from the image.
  4. Declarative, not imperative. You write YAML that says "3 replicas of this image". Controllers keep working until reality matches.
  5. The Pod is the unit of scheduling. One or more containers sharing a network address and volumes. You almost never create bare Pods; a Deployment or similar owns them.
  6. Pods are mortal and their IPs change. A Service gives a stable name and virtual IP in front of a changing set of Pods, chosen by labels.
  7. Requests and limits drive everything. Requests decide where a Pod is placed. Limits decide when it is throttled (CPU) or killed (memory).
  8. Probes tell Kubernetes the truth about your app. Liveness restarts it, readiness gates traffic, startup protects slow boots. Wrong probes cause most self-inflicted outages.

1. Containers and images

What is a container, and how is it different from a virtual machine? Basic

What the interviewer is testing: whether you know a container is a process on a shared kernel, not a small VM.

A virtual machine includes a full guest operating system with its own kernel, running on virtual hardware that a hypervisor provides. A container has no kernel of its own. It is a normal process on the host's kernel, which the kernel isolates in two ways. Namespaces limit what the process can see: its own process list, network interfaces, mount points, hostname and users. Cgroups (control groups) limit what it can use: CPU, memory and disk I/O. Because there is no guest operating system to boot, a container starts in well under a second, uses megabytes instead of gigabytes, and you can pack many more on one machine. The price is weaker isolation. All containers share the host kernel, so a kernel bug can affect all of them, and a Linux container cannot run a different kernel (a Linux image on a Windows or Mac laptop actually runs inside a hidden Linux VM).

Likely follow-ups
  • When would you still pick a VM? When you need strong isolation between untrusted tenants, a different kernel, or a legacy app that expects a full OS.
  • Is a container secure by default? Reasonably, but not like a VM. Run as non-root, drop capabilities, and keep the host kernel patched.
What do namespaces and cgroups actually do? Intermediate

What the interviewer is testing: the two kernel features behind every container, and how they explain real symptoms like OOMKilled.

A Linux namespace wraps a global resource so a process sees its own private copy. The main kinds are PID (the container sees its app as process 1), network (its own interfaces and IP), mount (its own filesystem view), UTS (its own hostname), IPC and user. A cgroup is an accounting and limiting group in the kernel. You put processes in it and set caps: "at most 512 MB of memory and 1 CPU worth of time". If the group goes over its memory cap, the kernel's out-of-memory killer ends a process in that group. That is exactly what you see as OOMKilled. For CPU, going over the cap does not kill anything; the kernel just pauses the process for part of each scheduling period, which is called throttling. When someone says "Docker is just a wrapper", this is what they mean: the runtime sets up namespaces and cgroups and then starts your process.

# see the container's view vs the host's view
docker run --rm alpine ps          # PID 1 is the command itself
docker run --rm --memory=64m --cpus=0.5 alpine sh -c 'echo limited'
Likely follow-ups
  • Is there a "container" object in the kernel? No. "Container" is a user-space idea built from namespaces and cgroups.
  • What is a seccomp profile? A filter that blocks risky system calls for the container.
What is the difference between an image, a container and a registry? Basic

What the interviewer is testing: the basic vocabulary, said precisely.

An image is a read-only package: a stack of filesystem layers plus metadata such as the default command, environment variables and exposed ports. Think of it as a class, or a recipe result that does not change. A container is a running (or stopped) instance of an image, like an object created from a class. You can start many containers from one image. A registry is a server that stores and serves images, for example Docker Hub, GitHub Container Registry, or a private registry in your company. An image name looks like registry.example.com/team/orders:1.4.2: the host, the repository path, and a tag. Tags are labels that can be moved. A digest (@sha256:...) is the exact content hash and never changes.

docker build -t registry.example.com/team/orders:1.4.2 .
docker push registry.example.com/team/orders:1.4.2
docker run -d --name orders -p 8080:8080 registry.example.com/team/orders:1.4.2
Likely follow-ups
  • What is the difference between docker run and docker start? Run creates a new container from an image and starts it. Start restarts an existing stopped container.
How do image layers work, and what is copy-on-write? Intermediate

What the interviewer is testing: understanding of why builds are cached and why deleting a file in a later layer does not shrink the image.

Most Dockerfile instructions (FROM, COPY, RUN) produce a layer: a set of file changes on top of the previous one. Layers are read-only and identified by a content hash, so two images that start from the same base share those layers on disk and during download. When a container starts, the runtime stacks the layers with a union filesystem (usually overlayfs) and adds one thin writable layer on top. If the container changes a file that lives in a lower layer, the file is first copied up into the writable layer and changed there. This is copy-on-write. When the container is deleted, the writable layer goes with it.

Two practical effects. First, layers only add. If one step downloads a 500 MB archive and a later step deletes it, the image still carries 500 MB, because the earlier layer is unchanged. You must download and delete in the same RUN step, or use a multi-stage build. Second, writing a lot of data into the container's writable layer is slow and lost on restart; use a volume.

Likely follow-ups
  • Why do later layers not shrink an image? Layers only add. A delete is recorded as a "whiteout" marker, the old bytes stay.
  • How can I look inside? docker history IMAGE shows layers and sizes; dive is a popular tool.
Why is the latest tag a bad idea in production, and what should you use? Intermediate

What the interviewer is testing: reproducibility and release hygiene.

A tag is a movable pointer. latest is just the tag you get when you give none, and it does not mean "newest" in any enforced way. If production runs orders:latest, you cannot tell which code is running, two nodes can pull different content depending on when they pulled, and a rollback is impossible because the old content has no name. In Kubernetes there is an extra trap: a tag of latest (or no tag) makes imagePullPolicy default to Always, while any other tag defaults to IfNotPresent. I would tag every build with an immutable version, often the Git commit SHA or a semantic version (1.4.2, or 1.4.2-3f9c2ab). For the strongest guarantee, deploy by digest (orders@sha256:...), which cannot change. Many registries can also enforce tag immutability so a tag can never be overwritten.

Likely follow-ups
  • Is a digest readable? No, so pipelines usually keep both: a version tag for humans and the digest recorded in the deployment.
Common mistakes: reusing the same tag for new builds (for example dev or v1) and expecting nodes to refresh it.
What is the difference between Docker, containerd, runc and OCI? Senior

What the interviewer is testing: whether you know what actually runs your container on a cluster node.

The OCI (Open Container Initiative) defines open standards: the image format and the runtime specification. Because of that, an image built by any tool runs on any compliant runtime. runc is the small low-level program that follows the runtime spec: it creates the namespaces and cgroups and starts the process. containerd is a daemon that manages images and container lifecycle and calls runc. Docker is a whole developer toolset (CLI, build, Compose, desktop app) that uses containerd underneath. Kubernetes talks to a runtime through the Container Runtime Interface (CRI). Since Kubernetes 1.24 it no longer has built-in Docker support (dockershim), so nodes use containerd or CRI-O directly. For you as a developer nothing changes: images built with Docker run fine on those nodes. What changes is that docker ps on a node shows nothing; use crictl there.

Likely follow-ups
  • Are there alternatives to Docker for building images? Yes: Buildah, Kaniko, BuildKit directly, Jib for Java. They produce the same OCI images.
What is the difference between CMD and ENTRYPOINT, and between shell form and exec form? Basic

What the interviewer is testing: a classic question that also hides the signal-handling trap.

ENTRYPOINT is the program the container always runs. CMD provides the default arguments, and anything you pass after the image name in docker run replaces CMD but not ENTRYPOINT. A common pattern is ENTRYPOINT ["java","-jar","app.jar"] with CMD ["--spring.profiles.active=prod"]. There are two syntaxes. Exec form is a JSON array: CMD ["java","-jar","app.jar"]. The process starts directly and becomes PID 1. Shell form is plain text: CMD java -jar app.jar. Docker wraps it as /bin/sh -c "...", so the shell is PID 1 and your app is its child. The shell does not forward stop signals, so on docker stop or a Kubernetes pod shutdown your app never gets SIGTERM, waits out the grace period, and is killed hard. Always use exec form for the main process. If you need environment variable expansion, use a tiny start script that ends with exec java ..., which replaces the shell with your process.

ENTRYPOINT ["java", "-jar", "/app/app.jar"]
CMD ["--server.port=8080"]
# docker run orders --server.port=9090   replaces CMD only
Likely follow-ups
  • How do I override ENTRYPOINT? docker run --entrypoint sh image, handy for debugging.
  • In Kubernetes, which fields map to these? command replaces ENTRYPOINT and args replaces CMD.
Why does PID 1 matter in a container? Senior

What the interviewer is testing: graceful shutdown and zombie processes, which show up as slow rollouts and stuck pods.

The first process in a container is PID 1, and Linux treats it specially in two ways. First, the kernel does not apply the default signal action to PID 1: if your app has not installed a handler for SIGTERM, the signal is ignored. Many runtimes (like the JVM and Node.js, when set up with handlers) do handle it, but a shell script does not. Second, PID 1 is responsible for reaping orphaned child processes. If it never calls wait, zombie processes pile up. The fix is to run your app directly in exec form, and if your app spawns children, add a small init process. Docker has --init, which injects tini, and many base images ship tini or dumb-init. In Kubernetes the symptom is a pod that always takes the full 30 seconds (the default terminationGracePeriodSeconds) to stop, and then ends with exit code 137 (killed).

Likely follow-ups
  • How do I prove it? kubectl exec pod -- ps -ef shows PID 1. If it is sh -c, the shell is the problem.
What is a .dockerignore file and why does it matter? Basic

What the interviewer is testing: practical build hygiene: speed and secrets.

When you run docker build ., the CLI first sends the whole build context (the directory) to the builder. .dockerignore lists paths that are left out, in the same spirit as .gitignore. It matters for three reasons. Speed: without it, .git, node_modules or target folders get uploaded on every build. Cache: any change to a file that a COPY . . step includes breaks the cache for that layer, and ignored files cannot do that. Safety: it keeps .env files, private keys and local credentials from being copied into an image by a broad COPY. A typical file lists .git, target/, node_modules/, *.log, .env and Dockerfile itself.

2. Writing good Dockerfiles

How does the Docker build cache work, and how do you order a Dockerfile for fast builds? Intermediate

What the interviewer is testing: whether you know the one rule that makes builds fast: put slow, rarely changing steps first.

For each instruction Docker checks whether it has already built this exact step on top of this exact previous layer. For RUN it compares the command text. For COPY and ADD it compares the checksum of the files. If it matches, the cached layer is reused. The moment one step misses the cache, every step after it is rebuilt. So order matters. Copy the files that change rarely (the dependency list) first, install the dependencies, and only then copy the source code that changes on every commit. For a Maven project, copy pom.xml, download dependencies, then copy src. A code change then reuses the expensive dependency layer.

# slow: any source change re-downloads all dependencies
COPY . .
RUN mvn package

# fast: dependency layer is cached until pom.xml changes
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B package -DskipTests

With BuildKit you can also use a cache mount (RUN --mount=type=cache,target=/root/.m2 mvn package) so the Maven repository survives between builds even when the layer is rebuilt. In CI, where each build starts on a clean machine, you need a shared cache (registry cache with --cache-from and --cache-to), or the cache is empty every time.

Likely follow-ups
  • How do I force a rebuild? docker build --no-cache.
  • Why does apt-get update on its own line cause stale packages? It is cached forever. Put update and install in the same RUN.
What is a multi-stage build, and why use it? Basic

What the interviewer is testing: the single most useful Dockerfile technique.

A multi-stage build uses several FROM lines in one Dockerfile. Early stages have everything needed to compile (JDK, Maven, compilers, source code). The final stage starts from a small runtime image and copies only the finished artifact from the earlier stage with COPY --from=build. Everything else is left behind. The result is a much smaller image, faster to pull and with fewer packages that can have security holes. It also keeps your build tools and source out of production, and you do not need a separate "build on the CI box, then copy the jar" step: the Dockerfile builds in a clean, repeatable environment.

# ---- build stage ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B package -DskipTests

# ---- runtime stage ----
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S app -G app
WORKDIR /app
COPY --from=build /src/target/orders.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
Likely follow-ups
  • Can I stop at a stage? Yes: docker build --target build ., useful to run tests in CI.
  • Can a stage use an external image? Yes: COPY --from=nginx:1.27 /etc/nginx/nginx.conf ..
How do you make an image small and safe? Alpine, slim, distroless, scratch? Intermediate

What the interviewer is testing: trade-offs, not a single answer.

Smaller images pull faster, start faster on a new node, and have fewer packages to patch. The usual options from biggest to smallest: a full OS image like ubuntu (familiar tools, large); -slim variants (Debian with fewer packages, a good default); Alpine (very small, but it uses musl instead of glibc, which can break native libraries or change performance in some cases; for Java use a glibc-based or well-tested Alpine JRE build); distroless (Google images with only the runtime and your app, no shell or package manager, so little to attack, but harder to debug); and scratch (empty, good for a single static Go binary). Beyond choosing a base: use multi-stage builds, combine install-and-clean in one RUN (apt-get install --no-install-recommends ... && rm -rf /var/lib/apt/lists/*), use .dockerignore, and install only runtime needs. For Java, jlink can build a trimmed JRE, and Jib or Spring Boot layered jars split dependencies from your code so the small, frequently changing layer is the only one that moves.

Likely follow-ups
  • How do I debug a distroless pod with no shell? kubectl debug -it pod --image=busybox --target=app attaches an ephemeral debug container.
  • Pin the base image? Yes, by version, ideally by digest, and rebuild regularly to pick up security patches.
Why should containers not run as root, and how do you do it? Intermediate

What the interviewer is testing: basic container security that application teams own.

By default a process in a container is root (user ID 0) inside it. Root in a container is not the same as root on the host, but it is a weaker barrier than people think: if the app has a vulnerability, or a misconfiguration mounts a host path or leaves extra capabilities, a root process can do much more damage and has a better chance of escaping to the host. Running as a non-root user limits what an attacker can do after breaking in. In the Dockerfile create a user and switch with USER. Prefer a numeric ID (USER 10001) so Kubernetes can verify it is not root. In Kubernetes enforce it in the Pod spec, and make the filesystem read-only where possible. Then writes go only to explicit volumes such as an emptyDir for /tmp. Many clusters also enforce this with Pod Security Standards (the "restricted" level requires non-root and no privilege escalation).

securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
Likely follow-ups
  • My app fails with "permission denied" after switching users. Why? Files copied in are owned by root, or the app writes into a directory the user cannot write. Use COPY --chown and create writable directories.
  • Can a non-root user bind port 80? Not by default. Use a port above 1024 (such as 8080) and let the Service map it.
How do you handle secrets during a build and at run time? Intermediate

What the interviewer is testing: a common leak: credentials baked into layers.

Anything written into a layer stays in the image forever, even if a later step deletes it, because anyone who can pull the image can unpack the earlier layer. So never use COPY .env, never ENV API_KEY=..., and never pass secrets with ARG (build args appear in docker history). For build-time secrets, such as a token to fetch a private dependency, use BuildKit secret mounts: the secret is available only during that RUN step and is not stored in any layer. For run time, inject secrets from outside the image: environment variables or files from a Kubernetes Secret, or better, pulled from a vault or cloud secret manager at start-up. If a secret ever reached an image, treat it as leaked and rotate it, because deleting the image tag does not delete copies others pulled.

# Dockerfile
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci

# build
docker build --secret id=npm_token,src=./npm_token.txt .
Likely follow-ups
  • How do I scan images for leaks and CVEs? Tools such as Trivy, Grype or Docker Scout, run in CI.
How do you run a JVM application well in a container? Senior

What the interviewer is testing: the most common source of "works on my laptop, OOMKilled in the cluster" for Java developers.

The JVM must know the container's limits. Modern JVMs are container aware (since JDK 10, and backported to 8u191), so they read the cgroup memory and CPU limits instead of the host's. But the defaults are not great: the maximum heap defaults to only 25% of the container memory, which wastes memory. A common setting is -XX:MaxRAMPercentage=70 (about 60 to 75), so the heap is most of the limit but leaves room for everything else. That "everything else" is large: metaspace (class data), thread stacks (about 1 MB each by default), code cache, direct and native buffers, and the garbage collector's own structures. If heap plus all of that exceeds the memory limit, the kernel kills the container with OOMKilled, even though the Java heap itself never threw OutOfMemoryError. That is the key distinction: a Java OutOfMemoryError is the JVM complaining about the heap; OOMKilled (exit code 137) is the kernel complaining about the whole process.

Other points. CPU: the JVM sizes thread pools and GC threads from the CPU count it sees. With a CPU limit below 1, it may pick the serial GC and one processor; set requests/limits knowingly and consider -XX:ActiveProcessorCount. Startup: JIT warm-up uses extra CPU, so a tight CPU limit makes cold starts slow; consider a startup probe, CDS/AppCDS, or GraalVM native image if start time matters. Shutdown: handle SIGTERM (Spring Boot has graceful shutdown) and use exec form. Diagnostics: enable -XX:+ExitOnOutOfMemoryError (so a broken JVM restarts instead of limping), and heap dumps to a volume if needed.

ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError"
# k8s: memory limit 1Gi  -> heap max about 700Mi, rest for non-heap
Likely follow-ups
  • Should memory request equal memory limit for a JVM? Usually yes or close, since the JVM tends to grow to its heap size and does not shrink well.
  • What does the number "exit code 137" mean? 128 plus signal 9 (SIGKILL), which is what the OOM killer sends.
Common mistakes: setting -Xmx equal to the container limit; leaving the default 25% heap; forgetting thread stacks and metaspace.
What is the difference between COPY and ADD, and between ARG and ENV? Basic

What the interviewer is testing: small instruction details that interviewers use to check real Dockerfile experience.

COPY copies files from the build context into the image, nothing more. ADD also extracts local tar archives and can fetch a URL, which makes it less predictable, so the guidance is to use COPY unless you specifically want tar extraction. ARG is a build-time variable: available only while building (set with --build-arg), gone in the running container, but still visible in the image history. ENV sets an environment variable that is stored in the image and present in every container started from it. Use ARG for things like a version number used during the build, and ENV for defaults that the running app reads. Neither is a safe place for secrets. Related: EXPOSE only documents a port and publishes nothing; WORKDIR sets the working directory and creates it if missing (prefer it to RUN cd).

Likely follow-ups
  • Does EXPOSE 8080 open the port? No. You publish with -p in Docker or declare containerPort and a Service in Kubernetes.
Review this Dockerfile: what is wrong with it? Intermediate

What the interviewer is testing: practical review skill, spotting several problems quickly.

FROM ubuntu:latest
RUN apt-get update
RUN apt-get install -y openjdk-17-jdk maven
COPY . /app
WORKDIR /app
RUN mvn package
ENV DB_PASSWORD=secret123
EXPOSE 8080
CMD java -jar target/app.jar

Here is how I would review it. (1) ubuntu:latest is unpinned, so builds change over time and are not reproducible. (2) apt-get update on its own line gets cached and goes stale; combine it with install and clean the lists. (3) It installs a JDK and Maven into the final image: large, with many extra packages. Use a multi-stage build with a JRE-only runtime. (4) COPY . /app comes before the build, so any file change rebuilds everything, and without a .dockerignore it copies .git and possibly secrets. Copy pom.xml first. (5) The password in ENV is baked into the image. Inject it at run time. (6) It runs as root: add a non-root user. (7) CMD in shell form means PID 1 is a shell that will not pass SIGTERM: use exec form. (8) There is no HEALTHCHECK and no JVM memory flags. Fixing these turns a 900 MB image into one near 200 MB that builds in seconds on small changes.

Dockerfile or Jib/buildpacks for a Java service? Senior

What the interviewer is testing: pragmatism and knowing the alternatives.

A Dockerfile gives full control and every engineer understands it, but each team writes it slightly differently and must keep base images patched. Jib (a Maven or Gradle plugin) builds an optimized image straight from the build, with no Docker daemon and no Dockerfile: it layers dependencies, resources and classes separately, so a code change only pushes a tiny layer, and builds are reproducible. Cloud Native Buildpacks (for example spring-boot:build-image) detect the app type, pick a patched base and a memory-aware JVM configuration for you, which gives consistency across many teams. I would pick a Dockerfile when I need special OS packages or tight control, and Jib or buildpacks when I want standardized, fast, low-maintenance builds for plain JVM services. In all cases the base image still needs regular rebuilds for security patches.

3. Networking, volumes and Compose

How does container networking work in Docker? What are bridge, host and none? Intermediate

What the interviewer is testing: whether you can explain how containers reach each other and the outside world.

By default a container joins the bridge network: a virtual switch on the host. Each container gets a private IP on it, and outgoing traffic is translated (NAT) to the host's address. To reach a container from outside you publish a port with -p 8080:80, meaning host port 8080 forwards to container port 80. On the default bridge, containers can only find each other by IP. On a user-defined bridge network (and in Compose), Docker runs a small DNS server so containers reach each other by container or service name, for example jdbc:postgresql://db:5432/app. With host networking the container shares the host's network stack, with no isolation and no port mapping; it is fast but can clash with host ports (and on Docker Desktop it behaves differently). none gives only a loopback interface. A frequent beginner mistake is using localhost to reach another container: inside a container, localhost means that same container.

Likely follow-ups
  • How does a container reach a service running on my laptop? Docker Desktop provides host.docker.internal.
  • What does Kubernetes change? Every Pod gets its own IP, and all Pods can reach all Pods without NAT. Service names replace Docker DNS names.
What are volumes, bind mounts and tmpfs, and when do you use each? Basic

What the interviewer is testing: where data lives, since container storage is temporary.

The container's own writable layer disappears with the container, so data that matters must live outside it. A named volume is storage managed by Docker (a directory under Docker's area on the host). It survives container removal, is easy to back up, and is the right choice for databases and any data the app owns. A bind mount maps an exact host path into the container. It is perfect in development (mount your source code so changes appear at once, or mount a config file), but it ties the container to a host layout and can have permission problems. A tmpfs mount lives in memory only, good for sensitive or temporary data that should never touch disk. In Kubernetes the same ideas become emptyDir (scratch space that lives as long as the Pod), hostPath (a host directory, avoid), ConfigMap and Secret volumes, and PersistentVolumeClaims for real durable storage.

docker run -v pgdata:/var/lib/postgresql/data postgres:16     # named volume
docker run -v "$PWD/conf:/etc/app:ro" myapp                    # bind mount, read-only
docker run --tmpfs /tmp myapp                                  # in-memory
Likely follow-ups
  • I removed the container and lost my data. Why? You wrote into the writable layer, not a volume.
  • Does docker rm -v delete named volumes? Only anonymous ones; named volumes stay until removed explicitly.
What is Docker Compose, and how would you use it for local development? Basic

What the interviewer is testing: daily developer workflow with multi-service apps.

Compose describes a group of containers (services), their networks and volumes in one YAML file, so docker compose up starts the whole stack: your app, a database, a cache, a message broker. All services share a default network where they reach each other by service name. It is mainly a development and test tool: it runs on a single machine, with no scheduling across nodes, no rolling updates and no self-healing across hosts. Production on many nodes is the job of Kubernetes. A good local file uses a health check on the database and depends_on with condition: service_healthy, because "started" does not mean "ready". It also uses a named volume for data, an env file for config, and a bind mount for live code reload.

services:
  app:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_URL: jdbc:postgresql://db:5432/orders
    depends_on:
      db: { condition: service_healthy }
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: dev }
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
volumes:
  pgdata:
Likely follow-ups
  • down versus stop? stop keeps the containers. down removes containers and networks; add -v to remove volumes as well.
  • Can I use Compose files in Kubernetes? Tools like Kompose convert them, but hand-written manifests or Helm are better for real use.
My app starts before the database is ready and crashes. How do you fix it properly? Intermediate

What the interviewer is testing: resilience thinking. Start order is not readiness, in Compose or Kubernetes.

Plain depends_on only controls the order in which containers are started, not whether the dependency is ready to accept connections. In Compose, add a health check to the database and use condition: service_healthy. That fixes local development. But the same problem exists in Kubernetes, where there is no start order between Deployments at all. The robust fix is in the application: retry connections with backoff when starting up, and do not crash the whole process on the first failure. In Kubernetes, a readiness probe that includes the database makes the Pod unready until it can serve, and a restarting container with backoff is acceptable as a last resort. An init container that waits for a dependency (pg_isready loop) is common, but it is a crutch: the database can also restart later, while the app is running, and the app must survive that too.

4. Kubernetes core: architecture, Pods and workloads

Describe Kubernetes architecture at a high level. Basic

What the interviewer is testing: can you name the parts and follow one request through them. No need for operator-level depth.

A cluster has a control plane and worker nodes. In the control plane, the API server is the front door: every tool (kubectl, controllers, kubelets) talks to it, and it validates and stores objects in etcd, the cluster's key-value database. The scheduler watches for Pods with no node and picks a node for each. The controller manager runs many control loops (Deployment, ReplicaSet, Node, Job controllers) that keep real state equal to desired state. On each worker node, the kubelet is the agent that makes the node run the Pods assigned to it, by calling the container runtime (containerd). kube-proxy (or an equivalent network plugin) programs the rules that make Services work. When you apply a Deployment: the API server stores it; the Deployment controller creates a ReplicaSet; the ReplicaSet controller creates Pods; the scheduler assigns nodes; the kubelets start containers. Nothing "calls" anything directly. Each component watches the API server and reacts. How to run and upgrade the control plane is cluster-operations depth; most teams use a managed service (EKS, GKE, AKS) for that.

Likely follow-ups
  • What happens if the control plane is down? Running Pods keep running on the nodes, but nothing can be changed, scheduled or healed.
  • What is the only component that talks to etcd? The API server.
What does "declarative" and "control loop" mean in Kubernetes, and what is the difference between kubectl apply and create? Intermediate

What the interviewer is testing: the philosophy behind the whole system.

You do not tell Kubernetes the steps ("start 3 containers"). You write the desired state ("3 replicas of this image") and store it. Controllers run endless loops: observe the real state, compare with the desired state, take an action to reduce the difference, repeat. If a Pod dies, the loop notices 2 of 3 and creates one more. This is why Kubernetes is self-healing and why you edit the YAML, not the running things. kubectl create is imperative: it fails if the object exists. kubectl apply is declarative: it creates the object or updates it to match the file, by computing the change since the last applied version. That is what you want in Git-based workflows, as you can re-run the same command safely. Also useful: kubectl diff -f file.yaml shows the change before you apply it, and --dry-run=server validates against the real API without saving.

Likely follow-ups
  • What is "server-side apply"? The server tracks which manager owns which field and reports conflicts, which is safer when several tools (Helm, an autoscaler, you) touch one object.
What is a Pod, and why is the Pod the smallest unit rather than a container? Basic

What the interviewer is testing: the most basic Kubernetes object, and the multi-container patterns.

A Pod is a group of one or more containers that always run together on the same node. They share one network address (so they talk over localhost and share the port space), and they can share volumes. Most Pods have one container. The Pod is the unit because some helpers are tightly tied to the main app: a log shipper reading the app's log files, a proxy that handles TLS, or a process that refreshes config. Those need to be scheduled together and share files or network. Pods are meant to be disposable: if a Pod dies it is not repaired, a controller creates a new one, with a new name and a new IP. That is why you do not create Pods directly. A bare Pod that is deleted, or whose node fails, is simply gone.

apiVersion: v1
kind: Pod
metadata: { name: demo, labels: { app: demo } }
spec:
  containers:
  - name: app
    image: registry.example.com/team/orders:1.4.2
    ports: [{ containerPort: 8080 }]
Likely follow-ups
  • How do containers in a Pod share the network? A hidden "pause" container holds the network namespace and the others join it.
What are init containers and sidecars, and when do you use them? Intermediate

What the interviewer is testing: multi-container patterns and the startup order of a Pod.

Init containers run one at a time, in order, before the main containers start. Each must finish successfully, or the Pod restarts it. Use them for one-off setup: wait for a service, run a schema migration (carefully), download files into a shared volume, set file permissions. A sidecar runs next to the main container for the whole life of the Pod: a service-mesh proxy, a log forwarder, a certificate refresher. A long-standing problem was that sidecars started in no guaranteed order and did not stop cleanly in Jobs (the Job never finished because the sidecar kept running). Since Kubernetes 1.29 (stable in 1.33) you declare a native sidecar as an init container with restartPolicy: Always: it starts before the app, keeps running, and is stopped after the app. Other patterns are the ambassador (a local proxy to the outside world) and the adapter (translate the app's output into a standard format, such as metrics).

initContainers:
- name: wait-db
  image: busybox:1.36
  command: ["sh","-c","until nc -z db 5432; do sleep 2; done"]
containers:
- name: app
  image: orders:1.4.2
Likely follow-ups
  • Pod stuck in Init:0/1? The init container is still running or failing; use kubectl logs pod -c wait-db.
  • Why not run migrations in an init container? With many replicas, they all try at once. A Job or a Helm hook is usually safer.
Walk me through a Pod's life: phases, container states, and what happens on shutdown. Intermediate

What the interviewer is testing: the knowledge needed for graceful shutdown and for reading kubectl get pods.

A Pod's phase is a coarse summary: Pending (accepted, but not all containers running yet: waiting for a node or an image pull), Running, Succeeded or Failed (all containers ended, used by Jobs), and Unknown. Each container has a state: Waiting (with a reason such as ContainerCreating, ImagePullBackOff, CrashLoopBackOff), Running, or Terminated (with an exit code and a reason such as OOMKilled). Many statuses you see in kubectl get pods, like CrashLoopBackOff, are not phases but container reasons.

On shutdown (a rolling update, a scale-down, a node drain) these things happen: the Pod is marked terminating and removed from Service endpoints; a preStop hook runs if you have one; the container gets SIGTERM; Kubernetes waits up to terminationGracePeriodSeconds (30 s by default); then sends SIGKILL. Removing from endpoints and sending SIGTERM happen at about the same time, and endpoint removal takes a moment to reach every node. So some requests can still arrive after SIGTERM. A good app keeps serving for a few seconds (a small preStop sleep), then stops accepting new work, finishes in-flight requests, and exits.

Likely follow-ups
  • How do you avoid 502s during a rolling update? A short preStop sleep, SIGTERM handling, a readiness probe, and a grace period longer than your slowest request.
What is a Deployment, and how does it relate to ReplicaSets and Pods? Basic

What the interviewer is testing: the ownership chain, which explains rollouts and rollbacks.

A Deployment manages stateless apps. You declare the Pod template and a replica count. The Deployment controller creates a ReplicaSet for that exact template, and the ReplicaSet makes sure the right number of Pods exist. When you change the template (a new image, new env vars), the Deployment creates a new ReplicaSet for the new template and gradually scales it up while scaling the old one down. That is a rolling update. The old ReplicaSets stay around with zero Pods, which is what makes rollback quick: scale the old one back up. The number kept is revisionHistoryLimit (10 by default). Changing only the replica count does not create a new ReplicaSet. If you delete a Pod, the ReplicaSet replaces it. If you edit a Pod's labels so it no longer matches, the ReplicaSet creates a new one and the old Pod is orphaned.

apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders } }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 25%, maxUnavailable: 0 }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
      - name: orders
        image: registry.example.com/team/orders:1.4.2
Likely follow-ups
  • How does the ReplicaSet know which Pods are its own? By the label selector plus owner references.
  • Can the selector be changed later? No, it is immutable in apps/v1.
What is a StatefulSet, and how is it different from a Deployment? Intermediate

What the interviewer is testing: whether you know what "state" requires: stable identity and stable storage.

A Deployment treats Pods as identical and interchangeable: random names, any order, shared or no storage. A StatefulSet is for apps where each member has an identity: databases, Kafka, ZooKeeper, Elasticsearch. It gives each Pod (1) a stable, predictable name with an ordinal: db-0, db-1, db-2; (2) a stable network name through a headless Service (db-0.db.prod.svc.cluster.local), which survives rescheduling; (3) its own PersistentVolumeClaim from volumeClaimTemplates, which is re-attached when that Pod is re-created; and (4) ordered start and stop by default (0 first, then 1, and so on; deleted in reverse), which suits systems that need a primary first. Data volumes are not deleted when you scale down or delete the StatefulSet, by default, to protect data. Important honesty point: a StatefulSet does not make a database highly available by itself. It gives you the building blocks; replication and failover still come from the database or an operator. For many teams a managed database outside the cluster is the better choice.

Likely follow-ups
  • What is a headless Service? One with clusterIP: None. DNS returns the Pod IPs directly instead of one virtual IP.
  • Can I start Pods in parallel? Yes, podManagementPolicy: Parallel.
What are DaemonSets, Jobs and CronJobs, and when do you use each? Basic

What the interviewer is testing: choosing the right workload type.

A DaemonSet runs one Pod on every node (or on selected nodes): log collectors, node monitoring agents, network and storage plugins. A Job runs Pods until a task finishes successfully, then stops: a database migration, a report, a data import. It retries failed Pods up to backoffLimit (6 by default) and can run several in parallel using completions and parallelism. For Jobs the Pod's restartPolicy must be OnFailure or Never. A CronJob creates Jobs on a schedule written in cron format. Things to know: concurrencyPolicy (Allow, Forbid or Replace) decides what happens if the last run is still going, startingDeadlineSeconds limits how late a missed run may start, and times are in UTC unless you set timeZone (stable since 1.27). Jobs must be idempotent, because a retry or an overlapping run can happen. Use ttlSecondsAfterFinished to clean up finished Jobs automatically.

Likely follow-ups
  • Cron job did not run for days? Possibly more than 100 missed schedules while it was suspended or failing; the controller then stops scheduling it.
How do labels, selectors, namespaces and annotations work together? Basic

What the interviewer is testing: the glue of Kubernetes. Most "it does not work" problems are a label mismatch.

Labels are key-value tags on objects (app: orders, tier: backend). They are how things find each other: a Service picks its Pods with a selector on labels, a ReplicaSet counts its Pods with a selector, and you filter with kubectl get pods -l app=orders. Annotations are also key-value, but not used for selection. They hold extra information for tools (ingress settings, Helm hooks, checksums, build info). Namespaces split one cluster into virtual areas: names only need to be unique within one, and quotas, access rules (RBAC) and network policies can be set per namespace. They are for organisation and access control, not hard security isolation. Some objects are cluster-wide (Nodes, PersistentVolumes, StorageClasses, Namespaces themselves). Service DNS names include the namespace, which matters when one app calls another across namespaces.

kubectl get pods -n prod -l app=orders,tier=backend
kubectl label pod orders-abc env=test
kubectl config set-context --current --namespace=prod

5. Services, Ingress and configuration

What is a Service and how does it find Pods? What are the types? Basic

What the interviewer is testing: the stable-endpoint idea and the four types.

Pods come and go and their IPs change, so clients need a stable address. A Service gives a fixed virtual IP (ClusterIP) and a DNS name in front of a set of Pods, chosen by a label selector. Kubernetes keeps a list of the ready Pod IPs behind it (EndpointSlices) and spreads connections across them. Only Pods that pass their readiness probe are in that list. Types: ClusterIP (default): reachable only inside the cluster. NodePort: also opens a high port (30000 to 32767 by default) on every node. LoadBalancer: asks the cloud for an external load balancer in front of it. ExternalName: a DNS alias to an outside host, with no proxying. There is also the headless Service (clusterIP: None) with no virtual IP, used with StatefulSets and for client-side discovery.

apiVersion: v1
kind: Service
metadata: { name: orders }
spec:
  selector: { app: orders }
  ports:
  - port: 80          # port clients use on the Service
    targetPort: 8080  # port the container listens on
Likely follow-ups
  • Service has no endpoints? The selector does not match any Pod labels, or no Pod is ready. Check with kubectl get endpoints orders.
  • Does a Service do round-robin? Roughly random or round-robin per connection, not per request. Long-lived HTTP/2 or gRPC connections stick to one Pod, so you may need client-side balancing, a headless Service, or a mesh.
How do Pods find each other by name? What is the DNS name of a Service? Intermediate

What the interviewer is testing: in-cluster service discovery, which you use in every config file.

The cluster runs a DNS server (CoreDNS). Every Service gets a record: <service>.<namespace>.svc.cluster.local. Inside the same namespace you can use just orders. From another namespace use orders.prod (or the full name). Pods get a search path in /etc/resolv.conf that makes the short names work. A headless Service returns the individual Pod IPs, and StatefulSet Pods also get per-Pod names. Kubernetes also injects environment variables like ORDERS_SERVICE_HOST for services that existed when the Pod started, but DNS is the better way because it works for Services created later. One more detail: the default ndots:5 setting makes lookups of names with fewer than 5 dots try the search domains first, so external names like api.example.com cause several useless queries. Writing a trailing dot (api.example.com.) or tuning ndots speeds that up.

kubectl run -it --rm dns --image=busybox:1.36 --restart=Never -- nslookup orders.prod
Likely follow-ups
  • Intermittent DNS timeouts under load? Look at CoreDNS pod health and CPU, the ndots effect, and consider NodeLocal DNSCache. That tuning is platform-team territory.
What is an Ingress, and how is it different from a LoadBalancer Service? Intermediate

What the interviewer is testing: how HTTP traffic from the internet reaches Pods, and cost and routing trade-offs.

A LoadBalancer Service gives one external IP per Service and works at layer 4 (TCP/UDP). With 30 services that is 30 cloud load balancers, which is expensive. An Ingress is a set of HTTP routing rules (host and path to Service) that one shared entry point applies. The rules do nothing alone: you must install an Ingress controller (NGINX, Traefik, HAProxy, or a cloud one such as the AWS Load Balancer Controller), which watches Ingress objects and configures a proxy. One controller behind one load balancer then routes shop.example.com/orders to the orders Service and /payments to another. It also usually terminates TLS using a certificate stored in a Secret (cert-manager can obtain and renew those automatically) and can add redirects and rewrites, mostly through controller-specific annotations. The Ingress API is frozen, and the newer Gateway API (Gateway, HTTPRoute, stable since v1.0 in late 2023) is the more expressive, role-oriented successor: platform teams own the Gateway, app teams own their routes. Note that the community ingress-nginx project announced its retirement for around March 2026, so check which controller your platform uses.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop }
spec:
  ingressClassName: nginx
  tls: [{ hosts: [shop.example.com], secretName: shop-tls }]
  rules:
  - host: shop.example.com
    http:
      paths:
      - { path: /orders,   pathType: Prefix, backend: { service: { name: orders,   port: { number: 80 } } } }
      - { path: /payments, pathType: Prefix, backend: { service: { name: payments, port: { number: 80 } } } }
Likely follow-ups
  • Ingress shows no address? No controller installed, wrong ingressClassName, or the cloud LB is still provisioning.
  • Does Ingress handle non-HTTP traffic? Not well. Use a LoadBalancer Service or Gateway API TCP routes.
How do ConfigMaps and Secrets work, and how do you consume them? Basic

What the interviewer is testing: the twelve-factor idea (config outside the image) and the honest limits of Secrets.

A ConfigMap holds non-sensitive settings as key-value pairs or whole files. A Secret holds sensitive values in the same shape. You can use either in a Pod in three ways: as environment variables (env.valueFrom for single keys, or envFrom for all keys), as files in a mounted volume, or read through the API (rare). The difference that matters: environment variables are fixed when the container starts, so changing the ConfigMap does not change running Pods; a mounted volume is refreshed by the kubelet after a short delay (about a minute) so the app can re-read the file, but a variable inserted by subPath mount is never updated. To roll out a config change reliably, change the Pod template (Helm adds a checksum annotation of the config for this), or use a tool that restarts Deployments on config change.

A Secret is base64 encoded, which is not encryption: anyone who can read the Secret object, or who can create a Pod in that namespace, can read the value. By default it is stored unencrypted in etcd. Good practice is to enable encryption at rest (platform team), restrict read access with RBAC, avoid committing Secret YAML to Git (use Sealed Secrets, SOPS, or the External Secrets Operator syncing from a vault or cloud secret manager), and prefer files over environment variables, since env vars leak easily into logs, crash dumps and child processes. Very large values are limited to 1 MiB.

env:
- name: DB_HOST
  valueFrom: { configMapKeyRef: { name: orders-config, key: dbHost } }
- name: DB_PASSWORD
  valueFrom: { secretKeyRef: { name: orders-secret, key: password } }
volumeMounts:
- { name: cfg, mountPath: /etc/orders }
volumes:
- { name: cfg, configMap: { name: orders-config } }
Likely follow-ups
  • Can I make a ConfigMap immutable? Yes, immutable: true; safer and lighter on the API server, and you roll out by creating a new name.
  • Pod stuck in CreateContainerConfigError? A referenced ConfigMap, Secret or key does not exist.
Common mistakes: saying "Secrets are encrypted"; expecting env vars to update live; committing base64 secrets to Git.
What is a NetworkPolicy, and what happens when you create none? Intermediate

What the interviewer is testing: awareness that Kubernetes networking is open by default.

By default every Pod can talk to every other Pod in the cluster, across namespaces. A NetworkPolicy restricts that: it selects Pods by label and lists which sources are allowed in (ingress) and which destinations are allowed out (egress). Once any policy selects a Pod for a direction, everything not explicitly allowed in that direction is denied. A common secure pattern is a default-deny policy per namespace, plus small policies that allow only needed paths, such as "orders may reach the database on 5432", and do not forget DNS egress to CoreDNS. One important catch: NetworkPolicy objects are only enforced if the cluster's network plugin supports them (Calico and Cilium do; some basic setups do not). Writing a policy on an unsupporting cluster silently does nothing. How the plugin enforces it is network-specialist depth.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-allow-orders }
spec:
  podSelector: { matchLabels: { app: db } }
  policyTypes: [Ingress]
  ingress:
  - from: [{ podSelector: { matchLabels: { app: orders } } }]
    ports: [{ port: 5432 }]

6. Probes, resources, scaling and rollouts

Explain liveness, readiness and startup probes. How do they differ and what goes wrong with them? Intermediate

What the interviewer is testing: one of the most common real questions. Bad probes cause cascading outages.

A readiness probe asks "can this Pod take traffic now?" If it fails, the Pod stays running but is removed from Service endpoints. If it passes again, traffic returns. It is the right place to check things the app needs to serve: started up, cache loaded, the database reachable. A liveness probe asks "is this process stuck beyond recovery?" If it fails enough times, the kubelet restarts the container. It should check only the app itself, such as "the event loop answers", never external dependencies. A startup probe covers slow boots: while it has not yet succeeded, liveness and readiness are held off. Once it succeeds, they take over. Give it a generous limit (for example 30 checks of 10 s) so a slow Java boot is not killed in a restart loop.

Failure patterns I have seen: (1) A liveness probe that calls the database. The database blips, all Pods fail liveness at the same time, and all restart together, turning a small blip into a full outage. (2) A readiness probe so strict (or so slow) that no Pod is ever ready, so a rollout hangs. (3) A liveness probe with a 1-second timeout on a JVM during a long GC pause or a CPU-throttled start: restart, slow start, restart, in a loop. (4) No readiness probe at all, so a new Pod gets traffic as soon as the container starts, before the app listens, and users see errors during every deploy. Probe types: HTTP GET, TCP socket, exec command, and gRPC (stable since 1.27). Spring Boot Actuator provides /actuator/health/liveness and /readiness groups made for this.

startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 30        # up to 5 minutes to boot
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 3
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
Likely follow-ups
  • Should a Pod become unready when a downstream is down? Debated: it removes capacity and can cascade. Many teams keep readiness for the Pod itself and use timeouts, retries and circuit breakers for dependencies.
  • Do probes affect rollouts? Yes: a rolling update only proceeds when new Pods are ready.
What are resource requests and limits, and how do they differ for CPU and memory? Intermediate

What the interviewer is testing: whether you size workloads and understand throttling versus killing.

A request is what the container is guaranteed, and the scheduler uses the sum of requests to decide whether a Pod fits on a node. A limit is the maximum it may use. CPU is measured in cores or millicores (500m is half a core) and memory in bytes (512Mi). They behave differently when exceeded. CPU is a "compressible" resource: over the limit, the process is throttled, which means it gets paused for part of each 100 ms period. It slows down (and latency spikes) but is not killed. Memory is "incompressible": over the limit, the kernel kills the container with OOMKilled. When a node itself runs short of memory, Pods using more than they requested are the first to be evicted.

The requests and limits also set the Pod's QoS class: Guaranteed (every container has requests equal to limits for CPU and memory), Burstable (some requests or limits set, not equal), and BestEffort (none set). Under pressure BestEffort goes first, then Burstable, and Guaranteed last. A sound starting policy for services: memory request equal to memory limit (predictable, no surprise eviction); CPU request set from measured typical use; and either a generous CPU limit or none, because tight CPU limits cause throttling that is hard to see (many teams, and some platform guidance, avoid CPU limits for latency-sensitive services but keep requests). Without any requests the scheduler thinks Pods are free and packs a node until it falls over. Many clusters add a LimitRange (defaults per namespace) and a ResourceQuota (a namespace total).

resources:
  requests: { cpu: "250m", memory: "512Mi" }
  limits:   { memory: "512Mi" }      # CPU limit deliberately omitted
Likely follow-ups
  • How do I choose numbers? Measure real usage under load (metrics, kubectl top, the Vertical Pod Autoscaler in recommend mode), then add headroom.
  • Pod resizing without restart? In-place resize went beta around 1.33; check your version.
A Pod keeps restarting with OOMKilled. How do you investigate? Intermediate

What the interviewer is testing: a structured debugging approach for the most common runtime failure.

First confirm it is OOM: kubectl describe pod shows Last State: Terminated, Reason: OOMKilled, Exit Code: 137. Exit code 137 means killed by SIGKILL. Next ask what is using memory. For a JVM remember the whole process counts, not only the heap: heap, metaspace, thread stacks, direct buffers and code cache. Compare kubectl top pod over time with the limit. A steady climb to the limit means a leak (cache without a bound, unclosed resources, listeners). A sudden spike during a request means a big payload, a big query result held in memory, or a burst of threads. A flat usage a little above the limit means the limit is simply too low, or the heap percentage is too high. Then fix the cause: bound caches and queues, stream big data instead of loading it, tune MaxRAMPercentage, raise the limit with evidence, and add a heap dump on error to a volume for analysis. Also check whether it is the container limit or the node under pressure: the latter shows as the Pod being Evicted instead, with a message about node memory.

kubectl describe pod orders-7d9 | grep -A5 "Last State"
kubectl top pod orders-7d9 --containers
kubectl get pod orders-7d9 -o jsonpath='{.status.containerStatuses[0].lastState}'
Likely follow-ups
  • Will increasing the limit fix it? Only if the app is actually under-provisioned. If it is a leak, it just takes longer to die.
  • Why is OOMKilled not visible in logs? The kernel kills the process instantly, so the app logs nothing. Look at the pod status and events.
How does the Horizontal Pod Autoscaler work, and what are its pitfalls? Intermediate

What the interviewer is testing: whether you understand scaling based on requests, and the lag.

The HPA is a control loop (checks about every 15 seconds) that adjusts the replica count of a Deployment (or StatefulSet). It reads metrics, usually CPU or memory from the metrics-server, and computes desired = ceil(current replicas * current metric / target metric). For example 4 Pods at 90% CPU with a 60% target gives ceil(4 * 90 / 60) = 6. Key points: utilisation is measured relative to the container's request, so a Pod with no CPU request cannot be scaled on CPU, and a wrong request gives wrong scaling. It has built-in calm-down: scale-up reacts quickly but scale-down waits for a stabilization window (5 minutes by default) to avoid flapping. The autoscaling/v2 API supports memory, custom metrics (such as requests per second or queue length through a metrics adapter), and behavior rules for the pace. For event-driven queue consumers, KEDA is a popular add-on that can scale from queue depth and even to zero.

Pitfalls: a slow-starting app means new Pods help late, so use readiness and startup probes properly; JVM apps rarely release memory, so scaling on memory is awkward; HPA and a fixed replicas in your Helm values fight each other (remove replicas from the Deployment when HPA is on); the node pool must have room, which needs a cluster autoscaler (platform scope). Scaling out also does not help if the bottleneck is a database or a single-threaded part.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: orders }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders }
  minReplicas: 3
  maxReplicas: 12
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
Likely follow-ups
  • HPA shows <unknown> for the metric? The metrics server is missing or the Pod has no resource request.
  • HPA versus VPA? HPA changes the number of Pods, VPA changes the size of each. Do not let both act on the same metric.
How does a rolling update work, and how do maxSurge and maxUnavailable change it? Intermediate

What the interviewer is testing: zero-downtime deployment mechanics.

With the default RollingUpdate strategy, the Deployment creates a new ReplicaSet and moves Pods across in steps. maxSurge is how many extra Pods above the desired count may exist during the update, and maxUnavailable is how many Pods may be missing. Both default to 25%. With 4 replicas, maxSurge: 1, maxUnavailable: 0 means: start 1 new Pod, wait until it is Ready, then stop 1 old Pod, and repeat. Capacity never drops, which is what I want for production, at the cost of needing room for one extra Pod and a slower rollout. Readiness probes are what make this safe: a new Pod only counts once Ready. If the new version never becomes ready, the rollout stalls with the old Pods still serving, so a bad release does not take you down. progressDeadlineSeconds (600 s by default) marks the Deployment as failed if it makes no progress, though it does not roll back by itself. The other strategy is Recreate: kill all old Pods, then start new ones. That means downtime, but it is needed when two versions must never run at once (for example an exclusive volume or a breaking schema).

Likely follow-ups
  • What about database schema changes? Use expand-and-contract: add new columns first, deploy code that works with both, then remove the old ones later.
  • How do I do canary or blue-green? Plain Deployments do not. Use two Deployments behind one Service, an ingress or mesh traffic split, or Argo Rollouts and Flagger.
How do you roll back a bad release in Kubernetes? Basic

What the interviewer is testing: incident response basics, and the limits of rollback.

Check how the rollout is going with kubectl rollout status deploy/orders. If it is bad, kubectl rollout undo deploy/orders goes back to the previous ReplicaSet (or --to-revision=N for a specific one; kubectl rollout history lists them). This is fast, because the old ReplicaSet and its template still exist. Limits to remember. It only reverts the Pod template, not ConfigMaps, Secrets, or other resources that changed with the release. It cannot undo a database migration that already ran. And if you deploy through Git or Helm, an imperative undo makes the live state differ from the repository, so the next deploy brings the bad version back. In a GitOps team the real rollback is reverting the commit (or helm rollback for Helm-managed releases). Set kubernetes.io/change-cause annotations (or use CI release names) so history is readable.

kubectl rollout status deploy/orders
kubectl rollout history deploy/orders
kubectl rollout undo deploy/orders --to-revision=3
kubectl rollout pause deploy/orders      # also: resume, restart
Likely follow-ups
  • What does rollout restart do? Recreates all Pods one by one with the same template (it adds an annotation with a timestamp). Useful to pick up a changed ConfigMap or a re-pushed tag.
How does the scheduler place Pods? What are nodeSelector, affinity, taints and tolerations? Intermediate

What the interviewer is testing: the knobs a developer uses to spread a service and to keep it off (or on) certain nodes.

The scheduler does two steps for each new Pod: filter out nodes that cannot run it (not enough requested CPU or memory, taints not tolerated, selectors do not match), then score the remaining nodes and pick the best. The tools: nodeSelector is the simple "node must have this label" rule. Node affinity is a richer version with required and preferred rules. Pod affinity and anti-affinity place Pods relative to other Pods: "not on the same node as another orders Pod". Taints are marks on a node that repel Pods (for example "dedicated for GPU work"), and tolerations on a Pod allow it to land there. Taints repel, they do not attract; to also attract, combine a taint with a node selector or affinity. For spreading replicas across failure domains, the modern tool is topologySpreadConstraints: "at most 1 more Pod in any zone than in another". Without this, the scheduler may put all your replicas on one node, and one node failure takes the service down.

Also relevant: a PodDisruptionBudget (PDB) says how many Pods may be down during voluntary events such as a node drain for upgrades (minAvailable: 2), which protects you during cluster maintenance. And priorityClassName decides who is evicted first when the cluster is full.

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: ScheduleAnyway
  labelSelector: { matchLabels: { app: orders } }
Likely follow-ups
  • Pod stuck Pending with "0/5 nodes available"? The event lists the reasons: insufficient CPU or memory, untolerated taints, unmatched affinity, or unbound volumes.
  • Does a PDB stop a node crash? No, only voluntary evictions.
What do you need for truly zero-downtime deploys? Senior

What the interviewer is testing: putting probes, shutdown, spreading and compatibility into one checklist.

It is a chain, and one weak link causes errors. (1) At least 2 replicas, spread across nodes or zones. (2) A readiness probe that is true only when the app can serve, so new Pods get no traffic early. (3) maxUnavailable: 0 with a surge of at least 1. (4) Graceful shutdown in the app: handle SIGTERM, stop accepting new connections, finish in-flight work, close the pool. (5) A short preStop sleep (a few seconds), because endpoint removal propagates a little after SIGTERM, so the load balancer may still send requests. (6) A terminationGracePeriodSeconds longer than your longest normal request plus the sleep. (7) A PodDisruptionBudget so node drains cannot remove all replicas. (8) Backward compatible changes: during the rollout old and new versions run together, so APIs, messages and database schema must work for both. (9) Clients that retry idempotent calls on connection errors. When a team says "we get a few 502s on every deploy", it is nearly always items 4, 5 or 2 missing.

lifecycle:
  preStop: { exec: { command: ["sleep", "10"] } }
terminationGracePeriodSeconds: 45

7. Storage, security and access

Explain PersistentVolume, PersistentVolumeClaim and StorageClass. Intermediate

What the interviewer is testing: how a Pod gets durable disk, in the developer's terms.

A PersistentVolume (PV) is a piece of real storage in the cluster (a cloud disk, an NFS share). A PersistentVolumeClaim (PVC) is a request for storage by an app: "10 GiB, read-write by one node". A Pod references the PVC, never the PV. A StorageClass describes a kind of storage ("fast SSD", "standard") and the provisioner that makes it. With dynamic provisioning, which is normal in the cloud, you create a PVC naming a StorageClass, and the cluster creates the disk and PV for you and binds them. Important details: access modes (ReadWriteOnce means one node at a time, ReadWriteMany many nodes, which needs a file system such as NFS or EFS, ReadWriteOncePod one Pod); the reclaim policy (Delete removes the disk when the PVC goes, Retain keeps it); and volumeBindingMode: WaitForFirstConsumer, which delays creating a zonal disk until the Pod is scheduled, so the disk and the Pod end up in the same zone. A classic problem: a cloud disk lives in one zone, so a Pod that needs it can only run in that zone, and node loss in that zone leaves the Pod Pending.

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data }
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: standard-ssd
  resources: { requests: { storage: 10Gi } }
Likely follow-ups
  • Can I grow a volume? Yes if the StorageClass sets allowVolumeExpansion: true; you edit the PVC size. Shrinking is not supported.
  • PVC stuck in Pending? No matching StorageClass or provisioner, or WaitForFirstConsumer waiting for a Pod.
Explain RBAC in Kubernetes: Role, ClusterRole, bindings and ServiceAccounts. Intermediate

What the interviewer is testing: least privilege for the people and Pods you deploy. Basics, not cluster-admin design.

RBAC (role-based access control) answers "who may do what to which resources". A Role lists permissions inside one namespace: verbs (get, list, create, delete) on resources (pods, secrets). A ClusterRole is the same but cluster-wide, or for cluster-scoped objects. Permissions are only granted, never denied, and nothing is allowed by default. A RoleBinding attaches a Role (or a ClusterRole, limited to that namespace) to a subject: a user, a group or a ServiceAccount. A ClusterRoleBinding grants cluster-wide. A ServiceAccount is the identity of a Pod: if your app needs to call the Kubernetes API (for example a controller listing Pods, or leader election using a Lease), you create a ServiceAccount, a Role with only those verbs, and a RoleBinding. Good habits: do not use the default ServiceAccount for apps that need access; set automountServiceAccountToken: false for Pods that never call the API; never give cluster-admin to an app; and be careful with secrets and pods/exec permissions, since they are effectively broad access. In cloud clusters, map ServiceAccounts to cloud identities (IRSA on AWS, Workload Identity on GKE) rather than putting cloud keys in Secrets.

kubectl auth can-i list pods --as=system:serviceaccount:prod:orders -n prod
kubectl create role pod-reader --verb=get,list --resource=pods -n prod
kubectl create rolebinding orders-read --role=pod-reader --serviceaccount=prod:orders -n prod
Likely follow-ups
  • Pod gets "forbidden" calling the API? Check the ServiceAccount of the Pod and its bindings with auth can-i.
  • What replaced PodSecurityPolicy? Pod Security Admission with the privileged, baseline and restricted levels (since 1.25).
What would you put in a Pod spec to harden an application? Senior

What the interviewer is testing: practical security that an application team can own.

The things I would set by default: run as a non-root numeric user; allowPrivilegeEscalation: false; drop all Linux capabilities and add back only what is truly needed; readOnlyRootFilesystem: true with an emptyDir for temp files; the RuntimeDefault seccomp profile; no privileged mode, no host network, host PID, or hostPath mounts; resource limits so one Pod cannot starve the node; a dedicated ServiceAccount with minimum rights and the token not mounted unless needed; secrets from a manager and not baked into images; a NetworkPolicy so the Pod can only talk to what it needs; images from a trusted registry, pinned by tag or digest and scanned in CI. These settings together are roughly what the "restricted" Pod Security Standard demands, and many clusters reject Pods that do not comply, so it is easier to build them in from day one.

Which kubectl commands do you use every day, and what does each tell you? Basic

What the interviewer is testing: hands-on fluency; they will often ask you to "debug live".

kubectl get lists objects (add -o wide for node and IP, -o yaml for the full object, -w to watch). kubectl describe shows one object in detail and, most useful, its Events at the bottom: scheduling errors, image pull errors, probe failures. kubectl logs shows container output (-f to follow, --previous for the last crashed instance, -c to choose a container, -l to select by label). kubectl exec -it pod -- sh runs a shell inside. kubectl port-forward tunnels a local port to a Pod or Service for testing. kubectl apply -f and delete -f manage manifests. kubectl rollout status/undo track and revert deployments. kubectl top shows live CPU and memory (needs metrics-server). kubectl get events --sort-by=.lastTimestamp shows recent cluster events. kubectl explain pod.spec.containers documents any field right in the terminal. Finally kubectl config get-contexts and use-context switch clusters; always check which one you are on before deleting anything.

kubectl get pods -n prod -o wide
kubectl describe pod orders-7d9-abcde -n prod
kubectl logs orders-7d9-abcde -n prod --previous
kubectl port-forward svc/orders 8080:80 -n prod

8. Helm

What is Helm, and what problem does it solve? Basic

What the interviewer is testing: the "package manager" idea and why raw YAML copying does not scale.

A real application needs a Deployment, Service, Ingress, ConfigMap, ServiceAccount, HPA and more, and you need versions of it for dev, test and prod that differ only in some values (replica count, image tag, hostnames). Copying YAML files per environment drifts and is error-prone. Helm is the package manager for Kubernetes. A chart is a package: a folder of templated YAML plus a values.yaml of defaults. You install a chart with some values, and the result is a release: one named, versioned instance of the chart in a cluster. Helm renders the templates with the values into plain YAML, sends it to the API server, and records the release (with its revision number and the rendered manifest) as a Secret in the namespace. That record is what enables upgrades, diffs and rollbacks. You can also install third-party software, for example a database or an ingress controller, from public chart repositories or OCI registries. Since Helm 3 (2019) there is no Tiller server; Helm is a client-side tool using your own kubeconfig permissions.

helm install orders ./orders-chart -n prod --create-namespace -f values-prod.yaml
helm list -n prod
helm upgrade orders ./orders-chart -n prod -f values-prod.yaml --set image.tag=1.4.3
Likely follow-ups
  • Where does Helm store release data? As Secrets (type helm.sh/release.v1) in the release namespace by default.
  • Helm 4? Released in late 2025. It keeps charts v2 compatible and changes internals such as server-side apply; check release notes for your version.
What is inside a Helm chart, and how do values and templates work? Intermediate

What the interviewer is testing: can you read and write a chart, not just run helm install.

A chart folder has Chart.yaml (name, chart version, app version, dependencies), values.yaml (default settings), templates/ (the YAML templates and a _helpers.tpl with reusable snippets), optionally charts/ (sub-chart dependencies), a values.schema.json to validate values, and templates/NOTES.txt shown after install. Templates use Go template syntax. {{ .Values.image.tag }} reads a value, {{ .Release.Name }} and {{ .Chart.Name }} are built-in objects, {{- if .Values.ingress.enabled }} adds conditions, range loops, and pipelines such as | quote, | default "x", | toYaml | nindent 4 transform values. Values come from layers; later ones win: chart defaults, then -f file.yaml files in order, then --set flags. Typical practice is one values.yaml of safe defaults plus a values-prod.yaml with only the differences. Keep chart version (changes when the chart changes) separate from appVersion (the version of the application).

# templates/deployment.yaml (excerpt)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
        resources:
          {{- toYaml .Values.resources | nindent 10 }}
Likely follow-ups
  • What is the checksum annotation for? When the ConfigMap changes, the Pod template changes too, so the Deployment rolls its Pods.
  • YAML indentation bugs in templates? Use nindent and check with helm template and helm lint.
How do helm upgrade and helm rollback work, and what are the flags you actually use? Intermediate

What the interviewer is testing: safe releases through Helm and knowing what rollback does and does not do.

On helm upgrade, Helm renders the chart, compares the new manifest with the previous release and with the live cluster state (a three-way merge in Helm 3), applies the changes, and stores a new revision. helm rollback orders 2 re-applies the manifest of revision 2 and stores it as a new revision (so history only grows). Useful flags: --install (upgrade or install if missing, perfect for CI), --atomic (if the upgrade fails or times out, roll back automatically; implies --wait), --wait (wait until Pods are ready, Jobs complete), --timeout, --history-max (limit stored revisions, default 10), --reuse-values (reuse last values; risky because new chart defaults are ignored, so many teams prefer passing the full values file every time), and --dry-run. Before deploying, helm template renders locally, helm lint checks the chart, and the helm diff upgrade plugin shows what will change. After deploying, helm history, helm status and helm get values/manifest show what is live.

Limits of rollback: it does not undo database migrations or data changes, it does not roll back resources Helm does not manage, and objects created by hooks are not reverted. A release stuck in pending-upgrade (after a killed CI job) must be fixed with helm rollback to the last good revision, or by cleaning the stuck release record, before the next upgrade will run.

helm upgrade --install orders ./chart -n prod -f values-prod.yaml \
  --set image.tag=$GIT_SHA --atomic --timeout 5m
helm history orders -n prod
helm rollback orders 3 -n prod --wait
Likely follow-ups
  • CRDs and Helm? CRDs in the crds/ folder are installed once and never upgraded or deleted by Helm; manage them separately.
  • Why does helm upgrade say "another operation in progress"? A previous run left the release in a pending state.
What are Helm hooks and when would you use them? Intermediate

What the interviewer is testing: how to run one-off tasks such as database migrations around a release.

A hook is an ordinary manifest (usually a Job) with an annotation such as "helm.sh/hook": pre-upgrade. Helm runs it at that point in the release life cycle instead of treating it as a normal resource: pre-install, post-install, pre-upgrade, post-upgrade, pre-delete, pre-rollback and test. A typical use is a schema migration Job as a pre-upgrade hook: Helm waits for it to finish, and if it fails the upgrade stops before new code goes out. Use helm.sh/hook-weight to order hooks and helm.sh/hook-delete-policy (for example before-hook-creation,hook-succeeded) to clean old Jobs, so a re-run does not clash with the old Job name. Cautions: hooks are not part of the release, so Helm does not track them for uninstall; they delay the release; and a hook that is not idempotent will hurt on retries. If you use GitOps with Argo CD, it has its own hook system, and Helm hooks are mapped to it.

Helm or Kustomize? How would you choose? Intermediate

What the interviewer is testing: balanced judgment, not tool loyalty.

Helm is a templating system plus a package and release manager. It is strong when you distribute an app to many users who need a few knobs (public charts), when you want versioned releases with history, rollback and hooks, or when many environments differ by many parameters. Its weak points are the Go templates inside YAML (hard to read and indent correctly, difficult to debug), and that chart authors decide which settings are exposed, so a missing value means forking the chart. Kustomize (built into kubectl apply -k) has no templating. You keep plain valid YAML as a base, and write overlays per environment that patch it (change replicas, add labels, swap image tags, merge patches). It is easy to read and any field can be patched, but it has no release history or rollback of its own, no packaging or versioning, and complex logic is awkward. In practice many teams use both: Helm to install third-party charts, and Kustomize overlays to adjust them (or a "helm template, then Kustomize" pipeline). Pure in-house services with a few environments often do fine with Kustomize; products shipped to customers usually need Helm. GitOps tools such as Argo CD and Flux support both.

Likely follow-ups
  • Where do secrets go? Neither tool solves it; pair with Sealed Secrets, SOPS or External Secrets.
How do chart dependencies, library charts and OCI registries work? Senior

What the interviewer is testing: managing charts at team scale.

A chart can depend on other charts, declared in Chart.yaml under dependencies with a name, version range and repository. helm dependency update downloads them into charts/ and writes Chart.lock, which pins exact versions for repeatable builds. Sub-chart values are set under a key with the sub-chart's name in your values.yaml, and a condition field lets you switch a dependency off (use an external database in prod, an embedded one in dev). When many services share the same shape, a library chart (type: library) contains only named templates and no resources of its own, so each service has a tiny chart that includes the common Deployment, Service and probe templates. This gives consistency, and a fix in one place reaches all services on their next release. For distribution, Helm supports OCI registries (stable since Helm 3.8): helm push chart.tgz oci://registry.example.com/charts and helm install x oci://..., so charts live next to images with the same access control. Sign and verify charts if your supply chain requires it.

How should secrets and environment-specific values be handled with Helm? Senior

What the interviewer is testing: the standard trap of passwords in values.yaml committed to Git.

Anything you pass to Helm ends up in the release record, which is stored in the cluster, and in CI logs if you use --debug. Plain secrets in a values file in Git is the common mistake. Better options: keep the chart referencing an existing Secret by name (existingSecret value) which is created by another path; sync secrets from a vault or cloud secret manager with External Secrets Operator or the CSI secret store driver, so Helm never sees the value; or encrypt the values file in Git with SOPS (the helm-secrets plugin) or Sealed Secrets. For environment differences, keep one values file per environment and change only what differs, keep image tags in the CD pipeline (--set image.tag=$SHA) rather than hand-edited, and use values.schema.json so a typo in a values key is caught at lint time instead of being silently ignored.

9. Troubleshooting a failing app

A deployed app is not working. What is your step-by-step approach? Intermediate

What the interviewer is testing: a calm routine that goes from the outside in: object, Pod, container, network.

I follow the request path and the object chain. (1) kubectl get pods: what is the status and restart count? (2) kubectl describe pod: read the Events at the bottom, they name most problems (cannot schedule, image pull failed, probe failed, OOMKilled). (3) kubectl logs, with --previous if it restarted. (4) If Pods are fine, check the Service: kubectl get endpoints, are there IPs? If not, the selector does not match or no Pod is ready. (5) Test from inside the cluster: kubectl run -it --rm tmp --image=curlimages/curl -- sh, then curl the Service name, and test DNS. (6) kubectl port-forward to the Pod itself to separate "app broken" from "network broken". (7) Check the Ingress and its controller logs. (8) Check config: ConfigMaps, Secrets, env variables and the image tag actually deployed (kubectl get deploy -o yaml). (9) Check recent changes: kubectl rollout history, Helm history, Git log. Most failures are in Events or the previous logs, and the order saves time.

A Pod is in CrashLoopBackOff. What does that mean and how do you fix it? Basic

What the interviewer is testing: the most-asked Kubernetes debugging question.

It means the container starts, exits, Kubernetes restarts it, it exits again, and the kubelet now waits longer between restarts (10 s, 20 s, 40 s, up to 5 minutes) so it does not spin. The status is a symptom, not a cause. Find the cause from the last run: kubectl logs pod --previous shows the output of the crashed container, and kubectl describe pod shows the exit code and reason. Meaning of common exits: 1 app error (exception on start, bad config, cannot connect to a required service); 137 killed (OOMKilled, or killed after liveness failures); 139 segmentation fault; 143 terminated by SIGTERM; 126 or 127 the command is not executable or not found (wrong ENTRYPOINT, missing shell, wrong architecture). Common causes: missing or wrong environment variable or Secret; the database not reachable; wrong command; a liveness probe that kills a slow-starting app; a permission error after switching to a non-root user; an image built for another CPU architecture (ARM image on x86 nodes gives exec format error). If logs are empty, the process died before writing: override the command with sleep and exec in to test by hand, or use kubectl debug.

kubectl logs orders-7d9 --previous
kubectl describe pod orders-7d9 | grep -A6 "Last State"
kubectl debug orders-7d9 -it --copy-to=orders-debug --container=orders -- sh
Likely follow-ups
  • Is it "Error" or "CrashLoopBackOff"? Error is a single failed run, and CrashLoopBackOff is the waiting between repeated failures.
What causes ImagePullBackOff or ErrImagePull? Basic

What the interviewer is testing: the short list of real causes.

The kubelet on the node could not download the image and is retrying with backoff. kubectl describe pod shows the exact message in Events. The usual causes: a typo in the image name or tag, or a tag that was never pushed (CI did not finish); a private registry and no credentials: create a docker-registry Secret and reference it in imagePullSecrets (or attach it to the ServiceAccount), and check it is in the same namespace as the Pod; expired registry tokens (cloud registries often use short-lived tokens, so a Pod that used to pull fine suddenly fails on a new node); the node cannot reach the registry (firewall, proxy, DNS); registry rate limits (Docker Hub limits anonymous pulls, so mirror images into your own registry); and a wrong architecture where the manifest has no variant for the node's CPU ("no matching manifest"). To test it, try docker pull of the same name from a similar machine, or run a debug Pod on the same node.

kubectl create secret docker-registry regcred \
  --docker-server=registry.example.com --docker-username=ci --docker-password="$TOKEN"
# then in the Pod spec:  imagePullSecrets: [{ name: regcred }]
A Pod stays Pending. What are the possible reasons? Intermediate

What the interviewer is testing: scheduling knowledge. Pending means "no node yet" or "not started yet".

Run kubectl describe pod and read the event from the scheduler: for example 0/6 nodes are available: 3 Insufficient memory, 3 node(s) had untolerated taint. Reasons: (1) Not enough resources: your requests are larger than what any node has free; lower the requests or add capacity. (2) Taints the Pod does not tolerate. (3) Node selector or affinity that matches no node, or an anti-affinity rule that cannot be satisfied with the current node count. (4) Unbound PVC: no StorageClass, provisioner failed, or the disk is in another zone than the available nodes. (5) ResourceQuota reached in the namespace (then the Pod is not even created; look at the ReplicaSet events). (6) Topology spread rules with DoNotSchedule that cannot be met. (7) A waiting cluster autoscaler that is adding a node (it takes minutes). If the Pod is scheduled but shows ContainerCreating, then the problem is on the node: image pull, a missing ConfigMap or Secret volume, or a volume attach problem.

kubectl describe pod orders-7d9 | tail -20
kubectl describe nodes | grep -A8 "Allocated resources"
kubectl get pvc,resourcequota -n prod
The Pod is Running but 0/1 Ready, or the Service gives no response. What do you check? Intermediate

What the interviewer is testing: separating a probe problem, a selector problem and an app problem.

Start with describe pod: events like Readiness probe failed: HTTP probe failed with statuscode: 503 or connection refused tell you what the probe saw. Then check things in order. Is the probe path and port right? A common error is a probe on port 8080 while the app listens on 8081, or on localhost only (the app must bind 0.0.0.0, not 127.0.0.1, or the kubelet and Services cannot reach it). Does the endpoint need authentication, so the probe gets 401? Is the app simply slow (raise initialDelay/use a startup probe)? Is a dependency down (the readiness probe checks the database)? If the Pod is Ready but the Service still does not work: kubectl get endpoints svc empty means the Service selector does not match the Pod labels, or the Pods are not ready. targetPort must match the container's real port. A named port mismatch gives the same symptom. Use kubectl port-forward pod/x 8080 and curl locally to prove the app works, which cuts the problem in half.

Likely follow-ups
  • App works via port-forward but not via the Service? Selector, targetPort, NetworkPolicy, or the app bound to loopback only.
Common mistakes: binding to 127.0.0.1 inside the container; confusing port and targetPort.
An app cannot resolve a service name, or cannot connect to another service. How do you debug it? Intermediate

What the interviewer is testing: layered thinking: name, then address, then port, then policy.

I test one layer at a time from a Pod in the same namespace as the failing app (use kubectl debug or a temporary Pod with nslookup and curl). (1) Name: nslookup orders and the full name orders.prod.svc.cluster.local. If the short name fails but the full name works, check namespaces and search paths. If nothing resolves, look at the CoreDNS Pods in kube-system (running? errors in logs?) and the Pod's dnsPolicy. (2) Address: does the Service exist and have endpoints? (3) Port: curl -v orders:80; "connection refused" means nobody listens on that port (wrong targetPort); a timeout means the traffic is dropped (a NetworkPolicy, a security group or the Pod is on another network) or the Pod IP is dead. (4) Policy: list NetworkPolicies in both namespaces; a default-deny egress without a DNS rule breaks all name lookups. (5) Application side: Java caches DNS results (the JVM can cache successful lookups for a long time if a security manager is on, or with a configured networkaddress.cache.ttl), so a client may keep using an old IP after a Pod moved; use short TTLs or a client that re-resolves.

kubectl run -it --rm net --image=nicolaka/netshoot --restart=Never -- bash
# inside: nslookup orders ; curl -sv http://orders:80/health ; cat /etc/resolv.conf
Why do Pods get Evicted, and how is it different from OOMKilled? Intermediate

What the interviewer is testing: node-level versus container-level resource problems.

OOMKilled is the kernel killing one container because it went over its own memory limit. Eviction is the kubelet removing a whole Pod because the node is running out of something: memory, disk space, or inode count. The Pod ends up in Failed with reason Evicted and a message such as "The node was low on resource: ephemeral-storage". The kubelet chooses victims by QoS class and by how far usage is above the request, so BestEffort and heavy Burstable Pods go first. Typical developer-caused reasons: writing lots of logs or temp files into the container filesystem or an emptyDir (use an ephemeral-storage limit and ship logs out), no memory requests so the Pod looks free to the scheduler, or too many Pods packed on a node. Fixes: set realistic requests (ideally equal to limits for critical services), cap ephemeral storage, rotate logs, and clean up the leftover Evicted Pods (they are just records). Another separate cause is node-pressure from a node drain or a spot instance reclaim, which is "disruption" and is handled with PDBs and graceful shutdown.

How do you debug a Pod that has no shell, or that keeps crashing too fast to exec into? Senior

What the interviewer is testing: modern tooling for minimal and distroless images.

Use kubectl debug. An ephemeral container (stable since 1.25) is added into a running Pod with its own image of tools (busybox, netshoot), sharing the Pod's network and, with --target, the process namespace of the app container, so you can see its processes and files through /proc/PID/root. For a Pod that crashes at once, --copy-to makes a copy of the Pod where you can change the command (for example to sleep 3600) or the image, and then exec in to run the start command by hand and see the error. You can also debug a node by starting a privileged Pod on it (kubectl debug node/name), though that is mostly for the platform team. Other tools: kubectl logs --previous, kubectl get events, and kubectl port-forward to reach the app from your laptop with a normal debugger or profiler (for Java, a remote JMX or a JFR recording to a volume). Remember to delete debug copies afterwards, because they still hold resources.

kubectl debug -it orders-7d9 --image=nicolaka/netshoot --target=orders
kubectl debug orders-7d9 -it --copy-to=orders-dbg --container=orders -- sh

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

Your Java service is OOMKilled every few hours in Kubernetes, but the heap looks fine in monitoring. What do you do? Senior

What the interviewer is testing: JVM versus container memory accounting.

Situation: restarts with exit code 137, no Java OutOfMemoryError in logs. The kernel is killing the whole process, not the JVM complaining about its heap.

Check first: kubectl describe pod for OOMKilled and the time pattern. Compare container memory (kubectl top or the metrics dashboard, working set) with the limit, and the JVM's own numbers: heap, metaspace, thread count, direct buffers. Check flags: is -Xmx near the limit, or is MaxRAMPercentage very high (like 90)?

Steps: list what is outside the heap: thread count (each thread stack about 1 MB), Netty or NIO direct buffers, metaspace growth from class loading, native libraries. Turn on Native Memory Tracking in a test (-XX:NativeMemoryTracking=summary) and use jcmd VM.native_memory. Set heap to about 60 to 70% of the limit so there is headroom, add ExitOnOutOfMemoryError and a heap dump path on a volume, and reproduce under load. If memory grows steadily, take two heap dumps hours apart and compare for a leak. Only then raise the limit, with the data to justify it.

Prevent: a documented sizing rule (heap percentage, request equal to limit), load tests in a container with the real limits, alerts on working-set memory at 85% of the limit, and dashboards for non-heap memory.

After a deploy, the new Pods are in CrashLoopBackOff, but the old ones are still serving. What do you do? Intermediate

What the interviewer is testing: triage under a stalled rollout, and the safety of rolling updates.

Situation: a rolling update with a readiness probe is protecting you: the new Pods never became Ready, so the old ones were not removed. Users are fine, but the rollout is stuck.

Check first: kubectl rollout status, then the logs of a failing new Pod with --previous and its describe events. Look at what changed: the image tag, a new environment variable or Secret key, a new config the code requires, or a changed probe.

kubectl rollout status deploy/orders -n prod
kubectl logs orders-6c4f8-xk2 -n prod --previous | tail -50
kubectl rollout undo deploy/orders -n prod      # if no quick fix

Steps: if the cause is clear and small (a missing config key), fix and re-roll. If not, undo, since the old version is healthy, and investigate on the side with kubectl debug, or in a lower environment. Tell the team, and note the exact failing version.

Prevent: run the same container with prod-like config in CI, a smoke test in the pipeline, --atomic or automated rollback on a failed rollout, and a progress deadline alert.

Users see a burst of 502 errors on every deployment, even though the rollout is "zero downtime". Why, and how do you fix it? Senior

What the interviewer is testing: the shutdown race between endpoints, SIGTERM and the load balancer.

Situation: errors only for a few seconds around each release, matching Pods being terminated or started.

Check first: correlate error timestamps with Pod start and stop times. Is there a readiness probe? Does the app handle SIGTERM (PID 1 a shell?) and how long does shutdown take? What do the ingress or load balancer logs show: connection reset or upstream refused?

Steps and fixes: (1) During termination the Pod is removed from endpoints and gets SIGTERM at the same time, but the ingress controller or cloud load balancer needs a few seconds to stop sending new requests. Add a preStop sleep of 5 to 15 seconds so the Pod keeps serving while that propagates. (2) Make the app stop accepting new connections on SIGTERM and finish in-flight requests (Spring Boot: server.shutdown=graceful). (3) Use exec form so the signal reaches the app. (4) Set the grace period longer than the sleep plus the longest request. (5) Make sure new Pods have a real readiness probe, so they do not get traffic before the server listens. (6) Use maxUnavailable: 0. (7) For keep-alive connections, the proxy may reuse a connection to a Pod that closed it, so make the app's idle timeout longer than the proxy's.

Prevent: a shared chart template with these defaults, and a test that runs a load while rolling out in staging.

You changed a ConfigMap but the application still uses the old values. What happened? Intermediate

What the interviewer is testing: how config reaches a running container.

Situation: kubectl apply succeeded, the ConfigMap shows new data, the app behaves as before.

Check first: how the app consumes the config. Environment variables are read once at container start, so they never change in a running Pod. A mounted file is updated by the kubelet after a delay (up to about a minute), but only if mounted as a whole volume: a subPath mount never updates. And even if the file changes, the app may read it only at startup.

Steps: run kubectl exec pod -- cat /etc/orders/app.properties to see what the Pod sees. Then restart: kubectl rollout restart deploy/orders. For the long term: in Helm add a checksum/config annotation to the Pod template so any config change triggers a rolling restart; or make ConfigMaps immutable with a hash in the name; or use an app that watches the file (Spring Cloud Kubernetes reload).

Prevent: treat config changes as releases (version them, roll them out the same way), and document how each setting is loaded.

The Service exists, the Pods are Running and Ready, but calls to the Service time out. What do you check? Intermediate

What the interviewer is testing: selector, port and policy checks in the right order.

Situation: Pods are healthy, but nothing is reachable by the Service name or IP.

Check first: kubectl get endpoints orders (or get endpointslices). Empty means the Service selector does not match the Pod labels. Compare kubectl get svc orders -o yaml selector with kubectl get pods --show-labels. A single typo (app: order versus orders) is enough.

Steps: if endpoints exist, compare targetPort with the port the app really listens on, and check the app binds to 0.0.0.0. Test the Pod IP directly from a debug Pod: if the Pod IP works but the Service does not, it is the Service config; if neither works, a NetworkPolicy or the app. Check NetworkPolicies in the namespace, especially default-deny. If the call comes from a different namespace, use the namespaced name.

Prevent: template labels and selectors from the same helper in Helm so they cannot drift, and add a post-deploy smoke test that calls the Service.

You scale a Deployment from 3 to 10 and only 4 Pods come up; the rest are Pending. What now? Intermediate

What the interviewer is testing: capacity and scheduling diagnosis.

Situation: the new Pods exist but cannot be scheduled.

Check first: kubectl describe pod on a Pending one. The scheduler message tells the reason, like Insufficient cpu. Then kubectl describe nodes to compare allocated requests with allocatable. If the Pods do not even exist (fewer than 10 in the ReplicaSet), look at ReplicaSet events for a ResourceQuota error.

Steps: the usual root cause is that the requests are large (for example 2 CPU per Pod set "to be safe") while real use is small, so nodes look full. Fix by right-sizing requests from real metrics. If the load truly needs it, the platform has to add nodes (cluster autoscaler may already be doing that, taking some minutes), or the namespace quota needs raising. Anti-affinity or zone spread rules can also block, if you ask for one Pod per node and have fewer nodes.

Prevent: requests based on measured use, a VPA recommendation review, a quota alert, and load tests that include scale-out.

A new node joined the cluster and Pods placed there get ImagePullBackOff, while other nodes work. Why? Intermediate

What the interviewer is testing: node-specific causes versus Pod-specific ones.

Situation: same image, same Secret, works on old nodes only.

Check first: describe pod for the exact pull error (unauthorized, timeout, no such host). Note that old nodes may simply have the image cached already, which hides the real problem: IfNotPresent means they never pulled it.

Steps: if "unauthorized", the pull secret is missing in that namespace or the node's cloud registry permission (an instance role) is missing on the new node group. If "timeout" or DNS failure, the new node pool is in a subnet with no route or proxy access to the registry. If "no matching manifest", the new node is a different CPU architecture (for example ARM nodes) and the image is only built for x86; build multi-architecture images with docker buildx --platform linux/amd64,linux/arm64. Confirm by running a test Pod pinned to the new node with nodeName.

Prevent: multi-arch builds or node selectors by architecture, pull permissions in the node group template, and a pre-pull test when adding node pools.

A short database outage turned into a 30-minute full outage of your service. The Pods kept restarting. What went wrong? Senior

What the interviewer is testing: cascading failure from a badly chosen liveness probe, and recovery thinking.

Situation: the database was unreachable for 2 minutes. After it came back, the service stayed down for a long time.

Check first: the probe config. If the liveness endpoint checks the database (a "deep health check"), all Pods failed liveness together and restarted. Restarts reset caches and connection pools, all Pods start at once, hammer the database with new connections and slow it down further, so the probes fail again. The restart backoff made the recovery even longer. Look at restart counts and the database connection graph.

Steps (now): stop the loop: temporarily remove or loosen the liveness probe, scale to a few Pods, let them connect gradually. Fix: liveness must check only the process itself, never dependencies. Keep dependencies in readiness at most, and make the app retry with backoff and jitter. Use a startup probe to protect slow boots, a connection pool with a sane maximum so a restart storm cannot exhaust the database, and a circuit breaker so the app degrades instead of dying.

Prevent: a probe review as part of the chart template, a game-day test that takes the database away, and an alert on restart counts.

A database password turns up inside a container image in the registry. What do you do? Senior

What the interviewer is testing: calm incident response and understanding that layers are permanent.

Situation: a secret was baked into a layer (an ENV, a COPY .env, or a build arg) and the image has been pulled by CI and nodes.

Check first: how many tags and digests contain it, who can pull them, how long it has been there, and whether the password is for prod. Deleting the tag is not enough, because any machine that pulled it still has the layers.

Steps: (1) Rotate the secret immediately: new password in the database and in the secret store. This is the real fix. (2) Roll out the new value to all consumers. (3) Delete the affected images and tags from the registry, and purge caches in CI. (4) Check database access logs for use by unknown clients. (5) Fix the build: remove the secret from the Dockerfile and use BuildKit secret mounts for build time and injected Secrets for run time, add .dockerignore entries for .env. (6) Run docker history or an image scanner for secrets.

Prevent: secret scanning in CI (image and Git), push protection, short-lived credentials from a vault, and no static database passwords where workload identity can replace them.

Traffic doubled but the HPA did not add Pods, and the service was slow. Why? Intermediate

What the interviewer is testing: HPA mechanics and the boundaries of autoscaling.

Situation: latency rose, replicas stayed at the minimum.

Check first: kubectl describe hpa orders. Look at the current metric (is it <unknown>?), the conditions (ScalingActive, AbleToScale), and events. Then kubectl top pods.

Steps: possible causes: (1) metrics-server missing or unhealthy, or the Pod has no CPU request, so utilisation cannot be computed. (2) The load is not CPU-bound: the app waits on a database or downstream call, CPU stays low, so a CPU target never triggers; scale on a better metric such as requests per second, in-flight requests, or queue length. (3) maxReplicas already reached. (4) New Pods were added but Pending because the nodes were full. (5) The target is too high (90%) or stabilization windows are too long. (6) The bottleneck is a shared resource (database connections), so more Pods do not help and may make it worse. After fixing, load test with a ramp to prove scale-out time end to end.

Prevent: define the scaling metric from the real bottleneck, set min replicas for the expected base load, and alert when HPA is at max.

The CI pipeline was cancelled in the middle of helm upgrade, and now every upgrade fails with "another operation is in progress". What do you do? Intermediate

What the interviewer is testing: Helm release state handling.

Situation: the release status is pending-upgrade (or pending-install), and Helm refuses to start a new operation.

Check first: helm status orders -n prod and helm history orders -n prod show the stuck revision. Check whether any live Pods are in a bad state, and whether another pipeline is truly still running (do not break a live lock).

helm history orders -n prod
helm rollback orders 7 -n prod --wait      # to the last good revision
# last resort for a stuck pending-install: remove the stuck release record
kubectl get secret -n prod -l owner=helm,name=orders
helm upgrade --install orders ./chart -n prod -f values-prod.yaml --atomic

Steps: roll back to the last deployed revision, which clears the pending state. If it was a first install that never completed, uninstall the failed release (helm uninstall) and install again. Only delete the release Secret by hand when nothing else works.

Prevent: use --atomic --timeout, run Helm in non-cancellable pipeline stages or with a lock, and do not run two deploys of one release at once.

A release needs a database migration, and you want zero downtime. How do you do it with Kubernetes? Senior

What the interviewer is testing: sequencing schema and code changes during a rolling update.

Situation: new code needs a new column, while for a few minutes old and new Pods run together.

Approach: use the expand and contract pattern across at least two releases. Release 1 (expand): migration only adds nullable columns or new tables, and the code is written to work with both. Release 2: code starts using the new column. Release 3 (contract), later: remove the old column once no running version needs it. Never ship a migration that renames or drops something the previous version still reads, because a rollback or the overlap during the rollout would break.

Mechanics: run the migration once, not from every Pod. Options: a Helm pre-upgrade hook Job, a separate Job in the pipeline before the Deployment changes, or a tool like Flyway or Liquibase that locks, so replicas starting together are safe. Give the Job its own limited database account, backoffLimit small, and make migrations idempotent and quick (avoid long table locks; for huge tables use online techniques). If the migration fails, the Deployment is not changed, which is what you want.

Prevent: test migration on a prod-sized copy, and keep rollback in mind: every change must be safe with the previous app version.

A nightly CronJob sometimes runs twice at once and corrupts data. How do you prevent that? Intermediate

What the interviewer is testing: CronJob semantics: at least once, not exactly once.

Situation: two Pods of the same job are processing the same data.

Check first: the CronJob concurrencyPolicy (default Allow): if last night's run was still going, a new run starts anyway. Also check the Job's backoffLimit and restartPolicy, as a retry after a failure can overlap with other work, and node failures can cause a Pod to be started again while the old one may still be alive on a partitioned node.

Steps: set concurrencyPolicy: Forbid (skip a run if the previous is running), set activeDeadlineSeconds so a stuck job is stopped, and set startingDeadlineSeconds. But the platform only gives "at least once" in rare cases, so make the work itself safe: idempotent processing, a database lock or lease (for example a row-level lock or a unique run key), and a record of processed batches. Use successfulJobsHistoryLimit and ttlSecondsAfterFinished to keep history tidy for debugging.

Prevent: alerts on job duration and failure, and a review rule that every scheduled job is idempotent.

Your Spring Boot app takes 90 seconds to start, and Kubernetes keeps killing it. How do you fix it? Intermediate

What the interviewer is testing: startup probes and why liveness alone is dangerous.

Situation: Pods restart repeatedly before they ever become Ready, often with exit code 137 and event "Liveness probe failed".

Check first: describe pod events and the time between container start and the first liveness failure. The liveness probe probably starts after a short initialDelaySeconds and fails three times before the app is up.

Steps: add a startup probe with failureThreshold * periodSeconds larger than the worst start time (for example 30 x 10 s = 5 minutes). Until it passes, liveness and readiness do not run. Then keep a normal tight liveness probe. Also look at why it is slow: a very low CPU limit throttles the JVM during start-up (give the start more CPU, or no CPU limit), too many beans or classpath scanning, slow remote calls at start. Options to speed up: Class Data Sharing, Spring AOT or a native image, lazy initialisation for rarely used beans, and a bigger CPU request. Do not solve it with a giant initialDelaySeconds on liveness, since it also delays detection of a real deadlock for every later restart.

Prevent: chart defaults with a startup probe, and measuring startup time in CI.

An image built on a developer's Apple Silicon laptop fails on the cluster with "exec format error". What happened? Intermediate

What the interviewer is testing: CPU architecture is part of an image.

Situation: the Pod crashes immediately, with exec /app/start.sh: exec format error or exec format error in the logs.

Cause: an image contains binaries for one CPU architecture. The laptop is ARM64, so docker build produced linux/arm64, and the cluster nodes are amd64. The same happens in reverse. A missing shebang or Windows line endings (CRLF) in a script gives a similar error, so check both.

Steps: confirm with docker image inspect --format '{{.Architecture}}' image and kubectl get nodes -o wide (or the node architecture label). Build for the right target: docker buildx build --platform linux/amd64 -t image --push ., or build multi-architecture images that serve both. Best of all, build only in CI on a runner with the target architecture so laptops never push production images.

Prevent: CI-only image publishing, and a multi-arch manifest if the fleet is mixed (for example Graviton nodes).

Pods are being Evicted with "ephemeral-storage" messages, and the node shows disk pressure. What is going on? Intermediate

What the interviewer is testing: hidden disk consumers inside containers.

Situation: Pods disappear as Evicted, and nodes report DiskPressure.

Check first: which Pods get evicted and which write the most. The node's local disk holds container logs, the writable layers, emptyDir volumes and images. An app writing big log files to a file inside the container, a temp-file directory that is never cleaned, or an emptyDir used as a cache that grows are the typical sources. Many images also pile up on the node.

Steps: find the heavy writer (kubectl exec pod -- du -sh /tmp /var/log). Fix the app: log to stdout (the runtime rotates it), clean temp files, and bound caches. Add resources.limits.ephemeral-storage so one Pod is evicted alone instead of hurting the node. For emptyDir caches set sizeLimit. Use a PVC for large working data. Platform teams tune log rotation and image garbage collection, which is their part.

Prevent: ephemeral-storage requests and limits as standard in the chart and monitoring on filesystem use.

You ran a destructive kubectl command and realise you were in the production context. What now, and how do you stop it happening again? Senior

What the interviewer is testing: honesty, blast-radius thinking and safe tooling habits.

Situation: for example kubectl delete deploy orders or helm uninstall ran against prod instead of staging.

Check first: say so right away and tell the on-call channel. Then see what the command removed. Deleting a Deployment removes its ReplicaSets and Pods; Services, ConfigMaps, and PVCs usually stay. PVCs are deleted only if you deleted the namespace or a StatefulSet's claims by policy, and the PV reclaim policy (Delete or Retain) decides if the disk survives.

Steps: restore the objects from the source of truth: re-run the pipeline for the last good version, or helm rollback/helm install of the last revision (the Helm history shows values), or kubectl apply from Git. In a GitOps setup, the controller usually re-creates the deleted object itself within minutes. Verify the Pods are Ready and the Service has endpoints. Check data: for a deleted PVC with Retain, the disk still exists and can be re-bound.

Prevent: read-only prod access for developers by default (RBAC), separate kubeconfig files or shell prompts that show the cluster, kubectl --context in scripts, deployments only through the pipeline or GitOps, namespaces and PVs with Retain for important data, and admission policies that block deleting protected resources.

CI builds the Docker image in 12 minutes for a one-line code change. How do you speed it up? Intermediate

What the interviewer is testing: practical build-cache work.

Situation: every CI run downloads all dependencies and rebuilds all layers.

Check first: read the build log for which step takes the time and whether any step says CACHED. Two causes are common: instruction order (source copied before the dependency step, so every change invalidates it) and an empty cache on every CI runner.

Steps: (1) Reorder: copy dependency manifests first and install, then copy source. (2) Add .dockerignore so unrelated changes (docs, .git) do not invalidate COPY .. (3) Use BuildKit cache mounts for the Maven or npm cache. (4) Persist the layer cache between CI runs with --cache-from/--cache-to type=registry (or the CI provider's cache). (5) Use multi-stage builds and build only the needed target. (6) Pull a slim base. (7) Consider Jib, which pushes only changed layers without a Docker daemon. (8) Run unit tests once outside the image, not twice.

Prevent: a shared Dockerfile template, and a build-time metric tracked in CI.

A StatefulSet Pod db-1 is stuck Terminating after its node died, and its replacement will not start. What do you do? Senior

What the interviewer is testing: the at-most-one guarantee of StatefulSets and the risk of forcing.

Situation: node NotReady, the Pod is stuck in Terminating or Unknown, and the StatefulSet does not start db-1 elsewhere.

Why: StatefulSets promise at most one Pod with that identity and that volume. Kubernetes cannot be sure the old Pod is really stopped, because the node may just be cut off from the network and still running it and writing to the disk. Starting a second one could corrupt data, so it waits.

Check first: is the node really dead (check with the cloud console or platform team)? Is the volume ReadWriteOnce still attached to the dead node (a multi-attach error in events)?

Steps: if the node is confirmed gone, the platform team removes or powers off the node object (the cloud provider controller then cleans up), and the Pod is then replaced. Only as a last resort, kubectl delete pod db-1 --force --grace-period=0, and only after being sure the old process is not running, since it removes the record without proof. Newer Kubernetes has a non-graceful node shutdown feature (stable in 1.28) using an out-of-service taint to help here. Then verify replication health in the database itself.

Prevent: use managed databases or a mature operator, test failover, and keep replicas in different zones.
