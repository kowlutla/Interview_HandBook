Mental model: the 8 ideas everything hangs on

One line: an entity is a Java object that is being watched. Inside a transaction, the watcher (the persistence context) remembers every entity it loaded, notices what you changed, and writes the SQL when it flushes. Most bugs come from forgetting the watcher exists.
  1. JPA is a spec, Hibernate is an implementation, Spring Data is a convenience layer. You code against JPA, Hibernate runs it, Spring Data JPA removes repository boilerplate.
  2. An entity is always in a state: new, managed, detached or removed. Only managed entities are watched.
  3. The persistence context is a per-transaction identity map. Load row 5 twice and you get the same Java object. This is the first-level cache.
  4. Dirty checking. Change a managed entity and you do not call save. At flush, Hibernate compares it with the snapshot taken at load and writes an UPDATE.
  5. Writes are delayed. SQL is queued and sent at flush: before a query that could be affected, and at commit. SQL order is Hibernate's, not your code's.
  6. Laziness is a proxy. A lazy association is a placeholder that loads on first touch, and only while the context is open. That is the source of LazyInitializationException and of N+1.
  7. The owning side decides the foreign key. In a two-way relationship only the side without mappedBy writes the column.
  8. Concurrency is your job. The persistence context does not stop two users overwriting each other. @Version (optimistic) or row locks (pessimistic) do.

1. Basics and the entity lifecycle

What is the difference between JPA, Hibernate and Spring Data JPA? Basic

JPA is only a specification: annotations and interfaces such as @Entity, EntityManager and JPQL. Hibernate is the most popular implementation that actually generates SQL. Spring Data JPA sits on top and writes the repository boilerplate for me, so findByEmail becomes a query without any code.

In practice I write against the JPA API and Hibernate does the work, so I can still use Hibernate extras (batch fetch size, filters, Envers) when I need them. Hibernate's Session extends JPA's EntityManager, and SessionFactory extends EntityManagerFactory. unwrap(Session.class) gives the Hibernate object. The factory is thread-safe and built once; an EntityManager is cheap, not thread-safe, and lives for one unit of work (in Spring, one transaction). Spring Data JPA is not part of JPA: it generates repository implementations at startup and delegates to the EntityManager.

Remember: JPA = rules, Hibernate = engine, Spring Data = shortcuts. The factory is shared, the EntityManager is not.

Why use an ORM at all, and what does it cost you? Basic

An ORM (object-relational mapper) removes the repetitive code that turns rows into objects and back, and gives me dirty checking, relationships, caching and database portability. The cost is that SQL becomes indirect: it is easy to create N+1 queries, load too much data, or hit surprises at flush time. I use JPA for normal CRUD on aggregates and drop to SQL or jOOQ for reports and heavy bulk work.

The root problem is the "impedance mismatch": objects form graphs and use inheritance, while tables have rows, foreign keys and joins. Hibernate bridges that, but you still have to know what SQL it produces. The rule I follow is to log the SQL in development, watch the statement count per request, and never treat the ORM as magic.

Remember: ORM saves typing, not thinking. Always look at the SQL it generates.

What does a class need to be a JPA entity? Why should it not be final? Basic

It needs @Entity, an @Id field, and a no-argument constructor that is at least protected. The class and its persistent methods should not be final, because Hibernate creates proxy subclasses for lazy loading and a final class cannot be subclassed.

Hibernate also reads and writes fields reflectively and needs to instantiate the object itself when loading rows, hence the empty constructor (I make it protected and keep a real constructor for my own code). Whether Hibernate uses fields or getters is decided by where I put @Id: on the field means field access, which I prefer, because setters with logic then do not run during loading. Records cannot be entities in Hibernate 6 (they are final and immutable), though they work well as DTOs and as embeddables in recent versions.

@Entity
public class Customer {
    @Id @GeneratedValue private Long id;
    private String name;
    protected Customer() {}                // for Hibernate
    public Customer(String name) { this.name = name; }
}

Remember: entity = annotation + id + protected no-arg constructor + non-final, so proxies can work.

Explain the entity lifecycle states and what moves an entity between them. Basic

There are four states. New (transient) is a plain object with no row. Managed (persistent) is attached to a persistence context, so changes are tracked. Detached has an id but its context is closed, so changes are ignored. Removed is scheduled for deletion at flush. persist makes new into managed, find and queries return managed, remove makes removed, and merge copies a detached object onto a managed one.

The state that matters most in practice is detached. After the transaction ends, an entity you return from a service is detached: you can still read it, but a setter on it changes nothing in the database, and untouched lazy fields cannot load. Detached happens through detach, clear, closing the EntityManager, or simply the end of a Spring transaction.

Remember: new, managed, detached, removed. Only managed entities get UPDATEs for free.

What is the difference between persist, merge, save and update? Intermediate

In JPA, persist takes a new object and makes that same object managed. merge takes an object that may be detached, copies its state onto a managed instance (loading it first if needed) and returns that managed copy; the object I passed stays detached. Hibernate's old save, update and saveOrUpdate are Hibernate-specific and were removed in Hibernate 6, so I use the JPA calls, or Spring Data's save which picks between them.

The classic mistake is to call merge(x) and keep using x: further changes go to a copy nobody tracks. Always use the return value. persist on a detached object throws "detached entity passed to persist". Merge costs a SELECT when the entity is not already in the context, because it must load the current state to copy onto.

Order managed = em.merge(detachedOrder);   // use 'managed' from here on
managed.setStatus(PAID);                   // tracked

Remember: persist attaches this object, merge returns a different managed copy. Use the return value.

find versus getReference: when would you use the lazy one? Intermediate

find loads the row now and returns null if it does not exist. getReference returns a lazy proxy holding only the id and does not hit the database until I touch a field. I use getReference when I only need to set a foreign key, for example order.setCustomer(em.getReference(Customer.class, id)), so I save a pointless SELECT.

The trade-off is that a missing row only shows up later as EntityNotFoundException (or at the foreign key on flush), and touching it after the context closes throws LazyInitializationException. In Spring Data the same idea is repository.getReferenceById(id) (called getOne in old versions). If I need the data or a clean "not found" answer, I use find.

Remember: find = load now or null. getReference = cheap placeholder, just to link by id.

How do Hibernate proxies work, and what traps do they create? Senior

For a lazy association Hibernate puts a generated subclass of my entity in the field. It holds the id, and on the first call of any method (other than getId) it loads the real row through the open session and delegates to it. The traps are that the proxy is a different class than my entity, so getClass(), instanceof with final classes and some equals implementations break, and that it only loads while the session is open.

Concrete traps: obj.getClass() == Customer.class is false for a proxy, so I compare with Hibernate.getClass(obj) or instanceof. Accessing a field directly (not through a getter) on a proxy returns null, because the proxy's own fields are empty. A lazy @ManyToOne to a class in an inheritance tree can give a proxy of the base type that cannot be cast to the subtype. To check if something is loaded use Hibernate.isInitialized(x); to force loading inside a transaction use Hibernate.initialize(x).

Remember: a lazy field is a proxy subclass. Use getters, instanceof, and stay inside the session.

2. Persistence context, flush and dirty checking

What is the persistence context, and what is the first-level cache? Basic

The persistence context is the set of managed entities that one EntityManager (one Session) keeps in memory. It works as an identity map: asking for the same entity id twice gives me the same Java object, and the second find costs no SQL. That is the first-level cache. It is always on, and it is scoped to one transaction in a normal Spring service.

The context also keeps a snapshot of each entity's values at load time, which is what dirty checking later compares against. Two consequences. First, it is not a shared cache: another transaction has its own context and may see different data. Second, it grows with every entity I load, so a loop over a million rows without clear() ends in OutOfMemoryError. A JPQL query always goes to the database, but the rows it returns are matched with entities already in the context, so I get the existing object back and my in-memory changes are not overwritten.

Remember: one transaction, one context, one object per id. Huge loops need clear().

How does automatic dirty checking work, and what does it cost? Intermediate

When Hibernate loads an entity it keeps a copy of its field values. At flush time it compares every managed entity with its copy, and for each one that differs it queues an UPDATE. So inside a transaction I just call a setter, and I never call save. Nothing happens for detached objects.

The cost is proportional to the number of managed entities times their fields, on every flush, so a context with 50,000 entities makes each flush slow even if only one changed. For read-only code I avoid the cost with @Transactional(readOnly = true), read-only queries, or DTO projections. By default the UPDATE includes all columns, not only the changed ones (@DynamicUpdate changes that, at the price of more distinct statements that cannot be reused or batched as well). Bytecode enhancement can track dirty fields without comparing, but few teams enable it.

@Transactional
public void pay(Long id) {
    Order o = repo.findById(id).orElseThrow();
    o.setStatus(PAID);       // no save() needed: UPDATE happens at commit
}

Remember: managed + changed = UPDATE at flush. No save needed, and none helps a detached object.

When does Hibernate flush, and what is the difference between flush and commit? Intermediate

Flush means "send the queued SQL to the database inside the open transaction"; commit means "make it permanent". With the default AUTO flush mode Hibernate flushes at commit and also before a query that might read data I changed, so my own queries see my own changes. A flush can still be rolled back; a commit cannot.

Flush modes are AUTO (default), COMMIT (only at commit, so queries may miss my pending changes), ALWAYS and, in Hibernate, MANUAL (only when I call flush()). I call flush() myself when I need constraint errors early (to catch a duplicate key inside the try block) or before native SQL, because Hibernate cannot tell which tables a native query reads. Through the JPA EntityManager it typically flushes everything first, but the Hibernate-native Session API may not, so I flush explicitly to be safe. Because flush runs at commit, a constraint failure often surfaces in the transaction proxy after my method returned, which confuses people reading the stack trace.

Remember: flush sends SQL, commit finalises it. Flush is automatic before affected queries and at commit.

In what order does Hibernate execute SQL at flush, and why does it matter? Senior

Hibernate does not run statements in the order I wrote the code. At flush it runs, roughly, all inserts, then all updates, then collection changes, then all deletes. This matters when my logic depends on order, for example deleting a row and re-inserting the same unique key: the insert runs first and fails with a duplicate key.

The reason is that Hibernate collects an action queue and sorts it to respect foreign keys and to allow batching. When order matters I call em.flush() right after the delete so it goes out before the insert. Better, I update the existing row instead of delete and insert. The same ordering can cause deadlocks when two transactions touch the same rows in different order: hibernate.order_updates=true and order_inserts=true sort statements by entity and id to make that more consistent.

Remember: inserts, then updates, then deletes. Need another order? Call flush() between the steps.

What do detach, clear, refresh and flush each do, and when do you use them? Intermediate

flush writes pending changes to the database. clear empties the whole persistence context, detaching everything, and detach(e) does it for one entity. refresh(e) reloads one entity from the database and overwrites my in-memory changes. I use flush plus clear in batch loops, clear after a bulk update, and refresh after a database trigger or a native update changed a row.

Order matters: always flush() before clear(), otherwise pending changes are thrown away silently. After clear(), every entity I still hold is detached, so touching its lazy fields fails. refresh on an entity with unflushed changes throws those changes away, so I use it carefully.

Remember: flush writes, clear forgets, refresh re-reads. Flush before you clear.

What does @Transactional(readOnly = true) really do? Intermediate

It is mainly a hint. With Spring and Hibernate it switches the flush mode to MANUAL, so there is no dirty checking and no automatic flush, and it tells the JDBC driver and database the connection is read-only, which some databases use to optimise or route to a replica. It does not make the database refuse writes in every case, and it still opens a transaction with a consistent snapshot.

I use it on every query-only service method: it saves the dirty-check pass and documents intent. If someone changes an entity inside it, the change is simply not flushed, which can look like "my update was ignored". Whether the read-only flag is enforced depends on the driver and database (PostgreSQL rejects writes, MySQL typically does too with InnoDB, others only treat it as a hint). A small trap is that a readOnly method called from an existing read-write transaction does not change that transaction.

Remember: readOnly = no flush, no dirty check, driver hint. It is a performance and intent flag, not a security feature.

3. Mappings: relationships, cascades, inheritance, ids

What is the owning side of a relationship, and what does mappedBy do? Basic

In a two-way relationship, only one side controls the foreign key column. That is the owning side, normally the "many" side with @ManyToOne and @JoinColumn. The other side uses mappedBy = "fieldName", which means "I am just a mirror of that field". Hibernate ignores changes made only to the mirror side.

So if I do order.getItems().add(item) but never call item.setOrder(order), the order_id column stays null, even though the Java objects look right in memory. The foreign key always lives in the table of the many side, which is why that side is the natural owner.

Remember: the side without mappedBy writes the foreign key. Always set the owning side.

How do you map a bidirectional one-to-many safely? Intermediate

I put @ManyToOne(fetch = LAZY) on the child as the owner, @OneToMany(mappedBy = ..., cascade = ALL, orphanRemoval = true) on the parent, and I add helper methods addItem and removeItem on the parent that update both sides. I never expose the raw collection to be modified from outside.

@Entity class Order {
  @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
  private List<OrderItem> items = new ArrayList<>();

  public void addItem(OrderItem i)    { items.add(i);    i.setOrder(this); }
  public void removeItem(OrderItem i) { items.remove(i); i.setOrder(null); }
}
@Entity class OrderItem {
  @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id")
  private Order order;
}

Why this shape: the helper keeps memory and database in step, so the object graph does not lie within the same transaction. Cascade ALL plus orphanRemoval makes the parent own the children's lifecycle, which is right for true parts of an aggregate (order items) and wrong for independent entities (a customer). Initialise the collection in the field so it is never null, and avoid replacing it with setItems(new list) when orphanRemoval is on: Hibernate complains about a dereferenced collection.

Remember: child owns the FK and is LAZY, parent has mappedBy, and helper methods update both sides.

What is wrong with a unidirectional @OneToMany? Senior

Without @JoinColumn, Hibernate invents an extra join table for it, which means extra writes and extra joins. With @JoinColumn it works on the child's table, but the child row is inserted first with a null foreign key and then updated, which needs a nullable column and doubles the statements. A bidirectional mapping with the owner on the child is cheaper.

A List (a "bag", with no index column) makes it worse: removing one element often deletes all rows of that collection from the join table and re-inserts the rest. Using a Set, or @OrderColumn for ordered lists, reduces this. My default is to map the many side with @ManyToOne, and add the @OneToMany(mappedBy) only if I really navigate that direction.

Remember: unidirectional one-to-many means a join table or insert-then-update. Prefer a @ManyToOne owner.

How do you map many-to-many, and why do people avoid it? Intermediate

With @ManyToMany and @JoinTable on the owning side, using a Set. I avoid it for real domain data because a join table never stays "just two ids": soon I need a created date, a role or a status, and then I have to remodel it as an entity. So I usually create the link entity from the start, for example Enrollment between Student and Course.

Two more problems. First, with a List, removing one link deletes and re-inserts the whole set of links for that owner, so use Set with a good equals/hashCode. Second, never use CascadeType.REMOVE or ALL on many-to-many: deleting one student would delete courses that other students share. Cascade PERSIST and MERGE at most, and keep helper methods that update both sides.

Remember: many-to-many hides a table you will need to extend. Use a link entity, and never cascade remove.

What does cascade mean, and which cascade types exist? Intermediate

Cascade makes an entity operation on the parent automatically apply to the related child entities. The JPA types are PERSIST, MERGE, REMOVE, REFRESH, DETACH and ALL (all of them). I use ALL only where the child cannot live without the parent, like order items, and never between independent entities.

Example: with cascade = PERSIST, persisting an order also persists new items added to it; without it, I get "object references an unsaved transient instance" at flush. Cascade is about operations, not about the foreign key: the foreign key is still decided by the owning side. Dangerous case: REMOVE on a @ManyToOne would delete the shared parent when one child is deleted. Remember that cascade runs when the operation is called, so a child added to a managed parent after persist is still saved at flush, because PERSIST cascades at flush time too.

Remember: cascade follows the lifecycle, so use ALL for parts of an aggregate and never for shared entities.

What is orphanRemoval, and how is it different from CascadeType.REMOVE? Intermediate

CascadeType.REMOVE deletes the children when the parent is deleted. orphanRemoval = true also deletes a child when I simply take it out of the parent's collection, because a child without a parent (an orphan) is considered meaningless. It is the right tool for "this list owns its elements".

It works only for one-to-one and one-to-many, and only for true parts of an aggregate. Gotchas: the collection must be modified in place with remove or clear, not replaced with a new instance; and if the same child is moved to another parent in the same transaction, it can get deleted by mistake. Each orphan removal is a separate DELETE by id, so removing 1,000 items from a list is 1,000 deletes. For bulk deletes use a JPQL delete.

Remember: REMOVE reacts to deleting the parent, orphanRemoval also reacts to removing a child from the list.

How do you map a one-to-one, and why is lazy loading a problem there? Senior

The owning side has the foreign key (or shares the primary key with @MapsId). On the owning side, @OneToOne(fetch = LAZY) works. On the inverse side (mappedBy) Hibernate usually cannot be lazy, because it cannot know whether the other row exists without querying, and a proxy cannot represent "null". So it loads that side eagerly with an extra query.

That produces a hidden N+1 when loading a list of parents. Options: (1) make the child the owner so the parent side holds the key, (2) share the primary key with @MapsId so the child can be loaded by the parent's id, (3) make the relation a unidirectional pointer from the child only, or (4) use bytecode enhancement for lazy inverse-side proxies (works but adds build complexity). My default is a shared primary key and navigating from the dependent side only.

@Entity class UserProfile {
  @Id private Long id;
  @OneToOne(fetch = LAZY) @MapsId @JoinColumn(name = "id")
  private User user;
}

Remember: a lazy one-to-one works only on the side that owns the key. The inverse side loads eagerly.

What inheritance mapping strategies does JPA have, and how do you choose? Intermediate

There are three entity strategies. SINGLE_TABLE (the default) puts the whole hierarchy in one table with a discriminator column: fastest, no joins, but subclass columns must be nullable. JOINED has one table per class joined by id: clean schema, but reads need joins. TABLE_PER_CLASS has a full table per concrete class: polymorphic queries become UNIONs, so I avoid it. For just sharing fields, @MappedSuperclass is simpler.

My choice: single table when the subclasses differ by a few columns and I query the base type a lot; joined when subclasses have many columns and need not-null constraints. Whatever I choose, polymorphic queries and polymorphic associations (a field of the base type) are where cost appears. For common fields like id, createdAt, version I use @MappedSuperclass, which is not an entity and cannot be queried.

Remember: single table is fast, joined is clean, table-per-class is rarely right. Shared fields: MappedSuperclass.

Explain the id generation strategies: IDENTITY, SEQUENCE, AUTO and UUID. Which do you pick? Intermediate

I pick SEQUENCE where the database has sequences (PostgreSQL, Oracle, SQL Server; MySQL has none, so it uses IDENTITY). With a sequence Hibernate gets a block of ids at once (allocation size 50 by default) and assigns ids in memory, so inserts can be batched. IDENTITY uses an auto-increment column, so Hibernate must run the INSERT immediately to learn the id, which disables JDBC insert batching.

AUTO lets the provider choose; in Hibernate 6 that is a sequence per entity named like order_seq, in Hibernate 5 a shared hibernate_sequence, which is a common upgrade surprise. If the database sequence increments by 1 but allocationSize is 50, ids collide, so the INCREMENT BY of the sequence must equal the allocation size. TABLE is slow and rarely used. A random UUID is easy to generate in the app and good for distributed inserts, but a random primary key scatters inserts across a B-tree index and is bigger; time-ordered UUIDs (v7) or a sequence for the clustered key reduce that.

Remember: SEQUENCE batches, IDENTITY does not. The sequence increment must equal allocationSize.

How should you implement equals and hashCode on JPA entities? Senior

Never include all fields or lazy associations, and do not rely on a database-generated id alone. I use either a natural business key (an email, an order number), or a constant hashCode with an equals that compares ids only when both are non-null. And I never put Lombok @Data on an entity.

Why it is tricky: the generated id is null until persist, so a hash based on it changes after saving, and an entity stored in a HashSet before that is lost in the wrong bucket. Using all fields breaks as soon as one field changes, and a lazy association in equals or toString triggers loading, or a LazyInitializationException, or an infinite loop through a bidirectional link. Also compare with instanceof (or Hibernate.getClass), not getClass(), because proxies are subclasses.

@Override public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Order other)) return false;
  return id != null && id.equals(other.getId());
}
@Override public int hashCode() { return Order.class.hashCode(); } // constant

Remember: equals on a stable key, hashCode must not change when the id is assigned, and no @Data on entities.

4. Fetching, N+1 and projections

What is the difference between lazy and eager loading, and what are the JPA defaults? Basic

Eager loads the related data together with the owner. Lazy loads it only when I first touch it. The JPA defaults are EAGER for @ManyToOne and @OneToOne, and LAZY for @OneToMany, @ManyToMany and @ElementCollection. I set every association to LAZY explicitly and fetch what I need per use case.

Eager is a trap because it is fixed in the mapping: every query on that entity pays for it, whether the screen needs it or not. A JPQL query does not honour EAGER as a join, so it loads the parents first and then runs a second select per parent, which is N+1 again. Lazy is not free either: touching it outside the transaction throws LazyInitializationException, and touching it in a loop causes N+1. In JPA, FetchType on the mapping is only the default plan; a query or entity graph can override it per use case, and that is the right place to decide.

Remember: ToOne is EAGER by default, ToMany is LAZY. Make all LAZY and fetch per query.

What is the N+1 select problem, and how does it happen? Basic

N+1 means one query loads N parent rows, and then N more queries run, one per parent, to load a lazy or eager association. For 10,000 orders that is 10,001 round trips. It happens because the loop touches order.getCustomer().getName() and each touch triggers its own SELECT.

It hides well: the code looks innocent, tests with 3 rows are fast, and production with 5,000 rows takes seconds. The fix is to tell Hibernate up front what the use case needs, instead of letting it discover it one row at a time. The usual tools are join fetch, an entity graph, batch fetching, or a projection (next question). The unit of measure is statements per request, so I count queries in tests rather than trust timing.

Remember: 1 query for the list plus 1 per row for the association. Count SQL statements, not milliseconds.

How do you fix N+1? List your options and pick one. Intermediate

For a screen that reads data, my first choice is a DTO projection with exactly the columns needed. If I need entities, I use join fetch or an entity graph for ToOne associations, and batch fetching (@BatchSize or default_batch_fetch_size) for collections, especially when paging. Whatever I pick, I make the mapping LAZY first.

OptionGood forWatch out
Projection (DTO)read-only lists, reportsno managed entity, so no updates
join fetch / entity graphToOne, or one small collectionnever page a collection fetch
@BatchSize / default_batch_fetch_sizecollections, paged listsstill 1 + N/batch queries
Second-level cacherarely changing lookupsnot a real fix, hides the cost

Do not "fix" it by switching to EAGER: that makes the cost permanent everywhere. After fixing, I add a test that asserts the statement count, so the problem cannot come back unseen.

Remember: LAZY first, then projection, join fetch or graph for ToOne, batch size for collections.

What is the difference between join fetch and an entity graph? Intermediate

Both load an association in the same query as the owner. join fetch is written inside the JPQL text. An entity graph (@EntityGraph or @NamedEntityGraph) is declared separately and attached to a query or repository method, so the same query can be reused with different fetch plans, and it works with derived queries like findByStatus where I cannot write JPQL.

In Spring Data I write @EntityGraph(attributePaths = {"customer", "items"}) on a repository method. Graph hints come in two flavours: fetch graph (attributes not listed are treated as lazy) and load graph (listed attributes are eager, others keep their mapping default). Under the hood both run a left join. The rules do not change: a collection join still multiplies rows, and a collection graph with paging is still done in memory.

@EntityGraph(attributePaths = {"customer"})
List<Order> findByStatus(Status status);

@Query("select o from Order o join fetch o.customer where o.status = :s")
List<Order> findWithCustomer(@Param("s") Status s);

Remember: join fetch lives in the query text, a graph lives beside it. Same SQL idea, graph works on derived queries.

How does @BatchSize work, and when is it better than join fetch? Intermediate

With batch fetching, when I touch the first lazy association, Hibernate loads it for up to a batch (say 50) of parents from the context at once, with where parent_id in (?, ?, ...). So 1 + N queries become 1 + N/50. It is better than join fetch for collections, especially with paging, because it does not multiply the parent rows.

I set it globally with hibernate.default_batch_fetch_size=50 (or per mapping with @BatchSize). It is a safety net more than a perfect fix: the queries are still lazy, so an access outside a transaction still throws, and I still pay more round trips than a single join. Its big strength is that it needs no change in the queries, and that it fixes ToOne and collections at once. It is not enough when I know exactly what I need: then a projection or fetch join is faster.

Remember: batch size turns N lazy selects into N/50 IN selects. Great default, safe with paging.

What is MultipleBagFetchException and how do you handle it? Senior

It is thrown when one query tries to join fetch two or more List collections (bags, unordered lists with duplicates allowed). The fix is not to change them to Set, which hides the error but creates a huge cartesian product. The fix is to load one collection per query: fetch the parents with the first collection, then a second query for the second collection, and let the persistence context merge them.

Why the product is the real problem: an order with 10 items and 5 payments becomes 50 rows in a double join, and with real data this explodes memory and bandwidth. Hibernate cannot tell which duplicate rows are real duplicates in a bag, which is why it refuses. Running two simple queries (select o from Order o join fetch o.items where o.id in :ids then the same for payments) uses the first-level cache to fill the same entities. Batch fetching is the other clean solution.

Remember: never fetch two collections in one query. One collection per query, or use batch size.

Why is pagination with a collection join fetch dangerous? Senior

Because joining a collection returns one row per child, so a SQL LIMIT would cut children, not parents. Hibernate cannot apply the limit in SQL, so it loads the whole joined result into memory and cuts the page in Java. The log shows HHH000104: firstResult/maxResults specified with collection fetch; applying in memory (the warning code differs in Hibernate 6, but the behaviour is typically the same). With a big table, that is an out-of-memory incident waiting to happen.

The correct approach is two steps: first query only the ids of the page (no collection join, with LIMIT), then load those parents with their children using where id in :ids. Alternatives are batch fetching (page the parents, children load in batches) or a DTO projection. Fetching a ToOne association together with a page is safe, because it does not multiply rows.

Remember: never page a collection fetch join. Page the ids first, then fetch children for those ids.

Why do I get duplicate parents with a join fetch, and what does distinct do? Intermediate

A join on a collection returns one SQL row per child, so a parent with 3 children appears 3 times in the result list. In Hibernate 5, I add select distinct in JPQL to de-duplicate the entities in memory. In Hibernate 6 the duplicates are removed automatically for entity results, so distinct is no longer needed for that purpose.

In Hibernate 5, distinct was sent to SQL as well, which can slow down the query; the hint hibernate.query.passDistinctThrough=false keeps it in Java only. When counting parents with a collection join, use count(distinct o), since a plain count counts rows.

Remember: collection join gives one row per child. Hibernate 5 needs distinct to collapse parents, Hibernate 6 does it for you.

When should you use a projection or DTO instead of loading entities? Intermediate

Whenever the use case is read-only, such as a list screen, an API response or a report. A projection selects just the columns I need into a DTO, so there are no proxies, no snapshots for dirty checking, no lazy loading surprises and less data on the wire. I load entities only when I am going to modify them.

In JPQL I use a constructor expression, in Spring Data an interface or a record/class projection:

select new com.acme.OrderRow(o.id, o.total, c.name)
from Order o join o.customer c where o.status = :s

interface OrderRow { Long getId(); BigDecimal getTotal(); String getCustomerName(); }
List<OrderRow> findByStatus(Status s);

A trap in Spring Data: a closed interface projection (only simple getters) selects only those columns, but an open projection (with @Value("#{...}")) loads the whole entity first. Also, one big projection with a collection inside is awkward; usually I run a second query for the collection.

Remember: read = DTO projection, write = entity. Open projections load the full entity.

How do you detect N+1 and other query problems before production? Intermediate

I count the SQL statements per request. In development I turn on SQL logging and Hibernate statistics, and in tests I assert the number of queries with a datasource proxy (datasource-proxy, or Hibernate's statistics bean), so a regression fails the build. In production, an APM or tracing tool shows the number of DB calls per request and flags the repeated same-shape statement.

Signs to look for: the same SELECT repeated with different ids, a request with hundreds of statements, HHH000104 pagination warnings, and long transactions. Test with realistic data volumes, since N+1 is invisible with 3 rows. Practical setup: spring.jpa.properties.hibernate.generate_statistics=true in a profile, plus a test helper that resets and reads the prepared-statement count.

Remember: you cannot see N+1 in one query's timing. Count statements per request, in tests and in APM.

5. Transactions with Spring, and lazy loading errors

How does @Transactional work inside Spring? Intermediate

Spring wraps my bean in a proxy. When someone calls a @Transactional method through that proxy, the proxy starts a transaction (gets a connection and binds an EntityManager to the thread), calls my method, then commits if it returns normally or rolls back on a runtime exception. My code never calls begin or commit.

The proxy is the whole trick, so anything that bypasses it gets no transaction: a call from another method in the same class, a private method, a bean created with new. The transaction is stored in a thread-local, so work on another thread (an @Async method, a parallel stream, a CompletableFuture) is outside it. At commit, Spring flushes the persistence context first, and that is when most SQL and most constraint errors actually appear.

Remember: @Transactional = a proxy around the call. No proxy, no transaction.

Why might @Transactional not work? Give the usual causes. Intermediate

The usual causes are: self-invocation (a method calling another method of the same class skips the proxy), a non-public or final method or class where the proxy cannot intercept, an object created with new instead of injected, a checked exception that by default does not roll back, a caught exception that never reaches the proxy, and work on another thread.

  • Self-invocation: this.save() from the same class. Fix: move it to another bean, or inject a self-reference, or use TransactionTemplate.
  • Checked exception: the default rule rolls back on unchecked exceptions and Error only. Use rollbackFor = Exception.class when needed.
  • Swallowed exception: a try/catch that logs and continues means the proxy sees success and commits.
  • Wrong annotation or config: a different Transactional import still works (both are supported), but a missing @EnableTransactionManagement outside Spring Boot, or a bean not managed by Spring, does not.
  • Another thread: @Async methods and executors get their own, separate (or no) transaction.

Remember: self-call, private, checked exception, swallowed exception, another thread.

Explain transaction propagation: REQUIRED, REQUIRES_NEW, NESTED and the rest. Intermediate

Propagation says what a method does when a transaction already exists. REQUIRED (default) joins it, or starts one if none. REQUIRES_NEW suspends the current one and runs in a completely separate transaction with its own commit. NESTED runs inside the same transaction but with a savepoint, so only the inner part can roll back. The rest: SUPPORTS, NOT_SUPPORTED, MANDATORY (fail if none) and NEVER.

I use REQUIRES_NEW for things that must commit even if the caller fails, such as an audit record, and I accept the cost: it takes a second connection from the pool while the first is held, so in a busy system a pool of 10 can deadlock itself. NESTED needs JDBC savepoint support and is rarely used with JPA. The most common surprise is with REQUIRED: if the inner method throws, it marks the shared transaction as rollback-only, so the outer caller cannot rescue it just by catching (see the scenario on UnexpectedRollbackException).

Remember: REQUIRED joins, REQUIRES_NEW is separate (and needs a second connection), NESTED is a savepoint.

What are the isolation levels, and which problems does each prevent? Intermediate

Isolation controls what a transaction can see of other transactions' work. READ_UNCOMMITTED allows dirty reads. READ_COMMITTED prevents dirty reads but allows non-repeatable reads and phantoms. REPEATABLE_READ also prevents non-repeatable reads. SERIALIZABLE prevents all anomalies, at a high cost. The default of @Transactional is the database default: typically READ_COMMITTED on PostgreSQL, Oracle and SQL Server, and REPEATABLE_READ on MySQL InnoDB.

The exact behaviour differs by database (PostgreSQL's repeatable read is snapshot isolation and also prevents phantoms; it does not have a real read-uncommitted). I rarely raise the level in application code: for "check then update" I use a version column or a row lock, which is cheaper and more explicit than serializable. Note also that isolation protects database reads, not the persistence context: a repeated find returns the cached object anyway.

Remember: default is READ_COMMITTED (MySQL: REPEATABLE_READ). Use @Version or locks for conflicts, not higher isolation.

What are the rollback rules, and what is UnexpectedRollbackException? Intermediate

By default Spring rolls back for RuntimeException and Error, and commits for checked exceptions. I change this with rollbackFor and noRollbackFor. UnexpectedRollbackException appears when an inner method that joined my transaction threw an exception, which marked the shared transaction rollback-only, and I caught it and carried on; at the end Spring refuses to commit and throws it.

The reason is that there is only one physical transaction under REQUIRED, and the inner proxy has already decided "this transaction must roll back". Catching the exception in the outer method does not undo that mark. Fixes: let the exception propagate, call the risky part with REQUIRES_NEW (accepting its separate transaction), or do not use an exception for an expected case (check first, return a result). A related trap: after any exception from the persistence context, the entities may be in an unknown state, so the Hibernate session should be treated as unusable.

Remember: unchecked rolls back, checked commits. Catching an inner exception does not clear the rollback-only mark.

What is LazyInitializationException and how do you fix it properly? Basic

It means I touched a lazy association (a proxy or lazy collection) after the session was closed, so Hibernate had no connection to load it. The proper fix is to load what I need while the transaction is still open: use a join fetch, an entity graph or a DTO projection, and map to the DTO inside the service method. I do not fix it with EAGER or with enable_lazy_load_no_trans.

The usual place it happens is in the controller or JSON serialiser, after the service method returned a detached entity. EAGER fixes the symptom by making every query pay for the data, forever. hibernate.enable_lazy_load_no_trans=true opens a new session for each lazy touch, so each lazy access gets its own connection and transaction: it hides the problem and turns N+1 into N+1 connections. The clean design is that services return DTOs, and controllers never see entities.

Remember: fetch inside the transaction and return DTOs. EAGER and no-trans lazy loading only hide the bug.

What is Open Session In View (OSIV), and should you leave it on? Intermediate

OSIV keeps the EntityManager open for the whole web request, until the response is rendered, so lazy loading works in controllers and in JSON serialisation. Spring Boot enables it by default (spring.jpa.open-in-view=true, with a startup warning). For a serious service I turn it off, because it hides lazy-loading and N+1 bugs and holds a database connection while the controller does slow work.

The details: the session is open, but each lazy load outside a transaction runs in autocommit mode on a connection that is held until the request ends. So a slow remote call in the controller, or serialising a big response to a slow client, keeps a pool connection busy; under load this exhausts the pool. With OSIV off, all loading must happen inside the service transaction, which forces explicit fetching and DTOs. That is the design I want, though the migration finds many hidden lazy accesses.

Remember: OSIV on = convenient but leaks connections and hides N+1. Set open-in-view=false and return DTOs.

Why should you not call remote services inside a transaction? Senior

Because the transaction holds a database connection and often row locks for as long as the remote call takes, and the remote call is slow or can hang. Under load the connection pool empties, and other requests wait or fail. I keep transactions short and database-only, and call remote services outside them.

There is also a correctness problem: if I call an external API or send a message inside the transaction and then the commit fails, the outside world has already seen the effect, and I cannot roll it back. Patterns: do the remote call first and the database write after; use TransactionTemplate for a small, explicit transactional block; or use a transactional outbox (write an event row in the same transaction, and a separate publisher sends it after commit). @TransactionalEventListener(phase = AFTER_COMMIT) is a lightweight option inside one service.

Remember: short DB-only transactions. Remote calls go outside, or through an outbox.

6. Concurrency and locking

What is a lost update, and how does optimistic locking prevent it? Intermediate

A lost update happens when two users read the same row, both change it, and the second save silently overwrites the first. Optimistic locking prevents it by adding a @Version column. Every UPDATE includes where id = ? and version = ? and increments the version; if another transaction already changed the row, zero rows match and Hibernate throws an OptimisticLockException instead of overwriting.

"Optimistic" means I do not lock anything while the user thinks; I assume conflicts are rare and detect them at write time. The caller then retries (for automatic work) or tells the user "this record was changed by someone else" (HTTP 409 in a REST API). In Spring the exception arrives as ObjectOptimisticLockingFailureException. For this to protect a web form, the version must travel with the data: send it to the client and send it back in the update request, otherwise I re-read the latest version in the update call and the check protects nothing.

@Entity class Customer {
  @Id @GeneratedValue Long id;
  @Version Long version;     // Integer, Long or Timestamp
  String name;
}
-- generated: update customer set name=?, version=2 where id=? and version=1

Remember: @Version turns a silent overwrite into an exception. Retry or return 409, and send the version with the form.

How does pessimistic locking work in JPA? Intermediate

Pessimistic locking locks the database row when I read it, so nobody else can change it until my transaction ends. I ask for it with LockModeType.PESSIMISTIC_WRITE (or @Lock on a Spring Data query), and Hibernate issues SELECT ... FOR UPDATE. I use it for short, high-contention work like decrementing stock, and always with a lock timeout.

The costs: other writers wait, so throughput drops and deadlocks become possible if two transactions lock rows in a different order. So keep the transaction short, lock rows in a consistent order, and set jakarta.persistence.lock.timeout so waiting ends. PESSIMISTIC_READ (shared lock) is less used. A useful variant is skip-locked (SELECT ... FOR UPDATE SKIP LOCKED, via Hibernate's lock timeout hint -2) for job queues, where each worker takes rows nobody else holds. Plain atomic SQL like update stock set qty = qty - 1 where id = ? and qty > 0 often beats both.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
Optional<Account> findById(Long id);

Remember: pessimistic = FOR UPDATE, short transaction, fixed lock order, always a timeout.

Optimistic or pessimistic: how do you choose? Senior

I default to optimistic: it needs no database locks, scales well and fits web apps where users take time between read and save. I choose pessimistic when conflicts on the same row are frequent and a failed retry is expensive or not possible, such as a hot account balance or a job queue. And when the update can be a single atomic SQL statement, I use that instead of both.

Remember: rare conflicts = optimistic, hot rows = lock or atomic SQL. Add @Version by default.

7. Caching

What is the difference between the first-level and second-level cache? Intermediate

The first-level cache is the persistence context: per session, always on, and it cannot be turned off. The second-level cache is optional, shared by all sessions of the same SessionFactory, and needs a provider like Ehcache, Infinispan or Hazelcast. A lookup by id checks L1, then L2, then the database.

L2 stores entity data in a "dehydrated" form (column values, not objects) and is used by find and lazy loading by id, not by ordinary queries. I enable it per entity (@Cacheable with @Cache(usage = ...)) for data that is read often and changes rarely, such as countries or product categories. Strategies are READ_ONLY, NONSTRICT_READ_WRITE, READ_WRITE and TRANSACTIONAL, in increasing consistency and cost. The main risk is staleness: if another application, a SQL script or another node writes the row, a local cache does not know.

Remember: L1 is per transaction and automatic. L2 is shared, opt-in, and only good for read-mostly data.

How do you enable the second-level cache, and when is it a bad idea? Senior

I add a cache provider (usually through JCache, with Ehcache or Infinispan), set hibernate.cache.use_second_level_cache=true and the region factory, and annotate only the chosen entities with @Cacheable and @Cache(usage = READ_WRITE). I also size and expire the regions. It is a bad idea for data that changes often, is written by other systems, or runs on many nodes without a cluster-aware provider.

Collections need their own annotation (@Cache on the collection) and are cached as id lists. Reality check before I enable it: most "slow read" problems are N+1 or missing indexes, which a cache hides rather than fixes, and a stale cache creates bugs that are hard to reproduce. In a multi-node deployment I would rather use an application-level cache (Spring Cache with Redis) where I control keys and expiry, and keep Hibernate L2 for small static reference data. Bulk JPQL updates evict the affected entity regions, but native SQL may not, so be careful there.

Remember: L2 is opt-in per entity, for read-mostly data. Measure first, and expect staleness across nodes.

What is the query cache, and why is it rarely worth it? Senior

The query cache stores the result of a query (the list of ids) keyed by the query text and parameters. It must be switched on globally and per query. It is rarely worth it because any write to a table involved invalidates every cached query that touched that table, so on busy tables the hit rate is poor and the cache only adds overhead.

It stores ids only, and the entities themselves must come from L1, L2 or the database, so without L2 for those entities, a cached query can even lead to N queries by id. It fits queries over read-mostly data with a small result set and repeating parameters, like "all active currencies". For everything else, a good index, a projection, or an application cache is better.

Remember: query cache = ids per query, wiped by any write to its tables. Use only on static data.

8. Queries: JPQL, Criteria and native SQL

What is JPQL, and how is it different from SQL and HQL? Basic

JPQL (Java Persistence Query Language) is an object-oriented query language: I query entities and their fields (select o from Order o where o.status = :s), not tables and columns, and Hibernate translates it to SQL for the database in use. HQL is Hibernate's own, richer language, and JPQL is effectively a subset of it.

The benefit is portability and refactoring safety: I use entity names, joins follow mapped associations (join o.customer c), and results come back as managed entities or projections. The limit is that it cannot use database-specific features, so I use native SQL for window functions, recursive queries or vendor hints. Hibernate 6 added many functions and made HQL stricter and closer to SQL (for example, better support for subqueries in from and set operations), so some sloppy queries from Hibernate 5 may need small fixes after an upgrade.

Remember: JPQL queries entities, not tables. Native SQL is the escape hatch.

How do you pass parameters safely, and what is the injection risk? Basic

I always use bind parameters, either named (:email) or positional (?1), and never concatenate user input into the query string. Bound values are sent separately from the SQL text, so they cannot change the query structure, which prevents SQL injection and also lets the database reuse the execution plan.

The same rule applies to JPQL, native queries and Spring Data @Query with @Param. Injection is still possible if I build a query string from a column name or sort field that comes from the request. For dynamic sorting I allow-list the field names, or use Spring Data's Sort with validated properties. A like filter needs the wildcard added to the parameter value ("%" + text + "%"), not to the query string, and I escape % and _ in the user's text if needed.

// unsafe: "select u from User u where u.email = '" + email + "'"
em.createQuery("select u from User u where u.email = :email", User.class)
  .setParameter("email", email)
  .getResultList();

Remember: bind parameters always. Allow-list anything dynamic like column names.

What is the Criteria API, and when would you use it instead of JPQL? Intermediate

The Criteria API builds a query from Java objects instead of a string, so it is type-checked by the compiler and can be assembled dynamically. I use it when the query shape changes at runtime, such as a search form with many optional filters. For fixed queries I prefer JPQL because it is much easier to read.

In Spring Data this usually appears as Specification objects (see the Spring Data section), which wrap Criteria predicates into small reusable pieces that I combine with and / or. Plain Criteria is verbose, and many teams use Querydsl or jOOQ for a nicer type-safe API. The real danger of dynamic queries is not the API but performance: a flexible filter produces many different SQL shapes, so I make sure each common combination has an index.

Remember: fixed query = JPQL, dynamic filters = Criteria or Specifications.

When do you use native queries, and what do they cost you? Intermediate

I use a native query when JPQL cannot express it or when I need database features: window functions, recursive CTEs, JSON operators, upserts (on conflict), or tuned hints. The cost is losing portability and some safety: the result mapping is manual, and Hibernate cannot always tell which tables the query touches.

That last point has practical effects. Pending changes may not be flushed before a native query (through the JPA EntityManager Hibernate typically flushes everything, but I call flush() myself to be safe), and a native update does not update the persistence context or the second-level cache. For results I can map to an entity (createNativeQuery(sql, Order.class)), to an interface projection in Spring Data, or to a DTO via a result mapping. With paging, a native @Query in Spring Data needs an explicit countQuery.

Remember: native for power features. Flush before it, and clear or refresh after a native write.

Offset or keyset pagination? What goes wrong with deep pages? Senior

Offset pagination (limit 20 offset 100000) is simple, but the database must read and discard all earlier rows, so deep pages get slower and slower, and concurrent inserts can shift rows so items appear twice or are skipped. Keyset pagination remembers the last seen key and asks for rows after it (where id < :last order by id desc limit 20), which uses the index and costs the same on page 1 and page 10,000.

The price of keyset is that I cannot jump to "page 57" directly, so it fits "load more" and infinite scroll, and exports. The sort must be on a unique, indexed key (add the id as a tie-breaker when sorting by a non-unique field like date). Spring Data offers Window / ScrollPosition support for keyset scrolling in recent versions (3.1 and later, typically). Also remember that Page runs an extra count(*), which can be slow on big tables; Slice avoids it.

select o from Order o
where (o.createdAt < :ts or (o.createdAt = :ts and o.id < :id))
order by o.createdAt desc, o.id desc

Remember: offset gets slower with depth. Keyset stays fast, but no random page jumps.

9. Spring Data JPA

How do derived query methods work, and what are their limits? Basic

Spring Data parses the method name at startup and builds the query from it: findByStatusAndCreatedAtAfter(status, date) becomes a JPQL query with two conditions. It saves a lot of code for simple lookups, and an invalid property name fails at startup instead of at runtime.

The limits: long names become unreadable, joins and fetch joins are awkward, and complex conditions or aggregates are better as @Query. Keywords include And, Or, Between, In, Like, OrderBy, IsNull, Top5, exists and count. Derived methods work on entities, so a read-only list should still use a projection (List<OrderRow> findByStatus(...)) or an @EntityGraph to avoid N+1. As a rule, when a method name has more than about three conditions, I switch to @Query.

Remember: the method name is the query. Keep it short, otherwise use @Query.

How do @Query and @Modifying work, and what is clearAutomatically for? Intermediate

@Query lets me write the JPQL or native SQL myself. For an update or delete query I must add @Modifying, and the method needs a transaction. The statement runs directly in the database and does not touch the persistence context, so @Modifying(clearAutomatically = true) clears the context afterwards, and flushAutomatically = true flushes pending changes first.

@Modifying(flushAutomatically = true, clearAutomatically = true)
@Transactional
@Query("update Order o set o.status = 'EXPIRED' where o.createdAt < :limit")
int expireOld(@Param("limit") Instant limit);

Why clear: otherwise entities already loaded in the same transaction keep their old values, and a later find returns stale data (see the bulk update question). The downside of clearAutomatically is that it detaches all other entities I hold, which may break later lazy access, so I run bulk updates early or in their own transaction. The method returns the number of rows changed; check it when it matters.

Remember: @Modifying for update and delete queries. Flush first, clear after, or you read stale entities.

What does repository.save() actually do? Intermediate

save checks whether the entity is "new". If it is new, it calls persist; otherwise it calls merge. "New" means the id is null, or, when there is a @Version field of a wrapper type, the version is null. So with a generated id it behaves as I expect, but with an id I assign myself (for example a UUID created in code), save thinks it is not new and calls merge, which first runs a SELECT and then the INSERT.

That is the extra SELECT before each INSERT that slows imports. Fixes: add a @Version field (null means new), or implement Persistable<ID> with an isNew() method (for example a transient flag set in a @PostLoad / @PostPersist callback). Also, inside a transaction I do not need save for changes to a managed entity: dirty checking writes them at flush. And save returns the managed instance, so I use the return value, as with merge.

Remember: save = persist if new, else merge. Assigned ids need @Version or Persistable to avoid the extra SELECT.

What are Specifications, and how do you build a dynamic search with them? Intermediate

A Specification<T> is a small reusable piece of a Criteria query (one predicate). I make the repository extend JpaSpecificationExecutor, write one specification per filter, and combine only the filters the user actually sent with Specification.where(...).and(...). This gives a dynamic search without string building.

static Specification<Order> hasStatus(Status s) {
  return (root, q, cb) -> s == null ? null : cb.equal(root.get("status"), s);
}
static Specification<Order> placedAfter(Instant t) {
  return (root, q, cb) -> t == null ? null : cb.greaterThan(root.get("createdAt"), t);
}
repo.findAll(where(hasStatus(s)).and(placedAfter(t)), pageable);

A null predicate is ignored, which makes optional filters simple. Watch the performance side: each combination needs a supporting index, a collection join inside a specification brings back the paging problem, and for list screens I still want a projection instead of full entities (specifications return entities). Paging with a specification also runs a count query.

Remember: one Specification per filter, combine with and/or, null means "skip". Index the common combinations.

How do you set up auditing (created and modified timestamps and users)? Intermediate

I enable it with @EnableJpaAuditing, add @EntityListeners(AuditingEntityListener.class) to a @MappedSuperclass, and annotate fields with @CreatedDate, @LastModifiedDate, @CreatedBy and @LastModifiedBy. For the user fields I provide an AuditorAware bean that returns the current user, usually from the security context.

The listener runs on persist and update callbacks, so the fields are filled at flush time. Limits: it only sees changes made through the persistence context, so a bulk JPQL update or native SQL does not update lastModified, and it records who and when, not what changed. For a full change history (old and new values) use Hibernate Envers or database-level audit tables.

Remember: enable auditing, add the listener, give an AuditorAware. Bulk updates bypass it.

Why is deleteBy or deleteAll slow, and what is a better way? Intermediate

Derived deletes such as deleteByStatus and deleteAll(entities) first load every matching entity, then delete them one by one so that cascades and callbacks run. For 100,000 rows that is 100,000 loaded objects and 100,000 DELETE statements. For a bulk removal I use @Modifying @Query("delete from X where ..."), or deleteAllInBatch, which issue a single statement.

The trade-off is that a bulk delete skips cascades, orphanRemoval, entity listeners and the persistence context, so child rows must be handled by database cascade or by deleting them first, and the context should be cleared. For very large deletes I delete in chunks (limit by ids) to avoid long locks and a giant transaction.

Remember: deleteBy loads and deletes row by row. Use a bulk delete query for volume, and handle children yourself.

Page, Slice and List: what is the difference in the SQL they run? Intermediate

Page runs the data query plus a count(*) query to know the total pages. Slice runs only the data query, but asks for one extra row to learn whether a next page exists, so it has no total. List with a Pageable just applies the limit and returns nothing about totals. I use Slice for infinite scroll and when the count is expensive.

The count query can be the slowest part on a large filtered table, so options are: Slice, a cached or approximate total, or a custom countQuery that skips the joins. Always include a stable ORDER BY with a unique tie-breaker, or pages can overlap. Also remember that Pageable sort properties come from the client and should be validated.

Remember: Page = data + count, Slice = data + 1 peek row, List = just the limit.

10. Performance, bulk work and large data

What is the problem with bulk updates in JPA? Intermediate

A bulk JPQL or native update (update Order set status = 'EXPIRED' where ...) goes straight to the database and bypasses the persistence context. Entities already loaded keep their old values, so a later find in the same transaction returns stale data. Bulk updates also skip @Version increments, entity listeners and auditing, unless I set those columns myself.

The rules I follow: flush before the bulk update, clear (or refresh) after it, and keep it in its own short transaction when possible. I also bump the version in the statement (set version = version + 1) if other code relies on optimistic locking. The benefit is huge: one statement instead of loading and updating thousands of entities, so for mass changes it is the right tool, as long as I respect its side effects.

Remember: bulk SQL skips the context. Flush before, clear after, and set the version yourself.

How do you make Hibernate insert 100,000 rows quickly? Senior

I turn on JDBC batching with hibernate.jdbc.batch_size=50 and order_inserts=true, use a sequence id (not IDENTITY), and in the loop I flush() and clear() every 50 rows so the persistence context stays small. Without this, each insert is its own round trip, and 100,000 entities pile up in memory.

spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
# PostgreSQL JDBC url: ...?reWriteBatchedInserts=true  (MySQL: rewriteBatchedStatements=true)

for (int i = 0; i < rows.size(); i++) {
    em.persist(rows.get(i));
    if (i % 50 == 49) { em.flush(); em.clear(); }
}

Checks I make: IDENTITY ids disable batching, so switch to SEQUENCE with a matching allocation size; assigned ids make save run a SELECT first (use persist or Persistable); the driver option rewrites batches into multi-row inserts and gives a further large speed-up; and I split a huge import into several transactions of a few thousand rows, so a failure does not roll back everything. For truly big loads, a database bulk loader or JdbcTemplate.batchUpdate is faster than any ORM.

Remember: batch size + sequence ids + flush and clear every batch. IDENTITY silently kills batching.

You must process 1 million rows. How do you avoid running out of memory? Senior

I never load them all with findAll(). I read in chunks, using keyset paging (where id > :last order by id limit 1000), or stream with a database cursor, and I clear the persistence context after each chunk so the managed entities can be garbage collected. If I only read, I use projections or a read-only query so no snapshots are kept.

Streaming with a Spring Data Stream<T> return type needs an open transaction, must be closed (try-with-resources), and the driver must really use a cursor: PostgreSQL needs autocommit off and a fetch size, MySQL needs Integer.MIN_VALUE or useCursorFetch. Without the fetch size, the driver loads the whole result set first and I get the same memory error. Chunked keyset reads are simpler and more predictable; they also allow commit per chunk and resuming after a crash. Hibernate's StatelessSession (no context, no dirty checking, no cache) is another option for pure processing.

Remember: chunk by key or stream with a real fetch size, and clear the context. Never findAll() a big table.

How do you see the SQL Hibernate runs, including parameter values? Basic

Set the logger org.hibernate.SQL=DEBUG for the statements, and for the bound values use org.hibernate.orm.jdbc.bind=TRACE on Hibernate 6 (org.hibernate.type.descriptor.sql.BasicBinder=TRACE on Hibernate 5). Do not use spring.jpa.show-sql in real code, since it prints to standard output and without values.

These loggers are for development only, because they are noisy and slow. For a view that shows the final SQL with values, and counts per request, a datasource proxy (datasource-proxy, p6spy) is more practical, and it is also what I use to assert statement counts in tests. In production I rely on slow-query logs from the database and tracing from an APM tool.

Remember: org.hibernate.SQL for text, bind logger for values. Dev only. Count statements with a datasource proxy.

How does the connection pool relate to JPA performance? Intermediate

Every transaction takes one connection from the pool (HikariCP in Spring Boot, default size 10) and holds it until the transaction ends, or with OSIV until the request ends. So throughput depends on how short the transactions are, not on how many threads I have. When the pool is empty, requests wait and then fail with "Connection is not available, request timed out after 30000ms".

Making the pool bigger is usually the wrong fix: the database can only do so much parallel work, and a larger pool adds contention. The right fixes are shorter transactions (no remote calls or slow work inside), OSIV off, fewer queries per request, and watching for REQUIRES_NEW, which needs a second connection while holding the first. A rough starting size is small (about 10 to 20 per instance); multiply by the number of instances and check it against the database's connection limit. Hikari can warn about leaks with leakDetectionThreshold.

Remember: a transaction equals a held connection. Fix pool exhaustion with shorter transactions, not a bigger pool.

11. Schema management and testing

What does ddl-auto do, and what should you use in production? Basic

spring.jpa.hibernate.ddl-auto lets Hibernate create or change the schema from the entities. Values: none, validate, update, create, create-drop. In production I use none or validate, and manage the schema with versioned migrations in Flyway or Liquibase. update is not safe for production.

Why not update: it only adds missing tables and columns. It never drops or renames, cannot do data migrations, behaves differently per database, and runs at startup on every node, so with several nodes starting together it races. Migrations are versioned SQL files, reviewed in pull requests and run once, in order, with a history table that records what ran (Flyway: file names like V12__add_status.sql; Liquibase: changelogs). With validate, the application refuses to start if the entities and the schema do not match, which catches a forgotten migration. For schema changes with no downtime, I use expand and contract: add the new column first (old code ignores it), deploy code that uses both, backfill, then remove the old column in a later release.

Remember: production = migrations (Flyway or Liquibase) plus validate. Never update or create.

How do you test the persistence layer? Intermediate

I use @DataJpaTest with a real database in Testcontainers (the same engine as production), not H2, whenever behaviour matters: native queries, locking, JSON columns, constraints and collations all differ between databases. I test repositories and queries with real data and assert the statement count to catch N+1.

Traps: @DataJpaTest wraps each test in a transaction that rolls back, and the persistence context hides what the database really does. So in a test I call flush() and clear() before asserting, to prove that the SQL runs and that data is read back from the database, not from the context. To use a real database, I add @AutoConfigureTestDatabase(replace = NONE). Rolled-back tests cannot check commit-time behaviour (a constraint checked at commit, an AFTER_COMMIT listener, optimistic lock conflicts between two transactions); for those I use a test without the wrapping transaction.

Remember: test against the real engine, flush and clear before asserting, and assert query counts.

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say that shape aloud in the interview. It shows you work calmly under pressure.

The orders page was fast in test and now takes 12 seconds in production. APM shows 800 SQL calls. What happened? Senior

It is almost certainly N+1: one query for the page of orders, then hundreds of tiny SELECTs because lazy (or eager ToOne) associations are touched in a loop or by the JSON mapper. I confirm it from the statements, then give the list its own query with a projection or fetch join, and add a test that counts statements.

Situation: test data had five rows, production has 200 per page, so one extra query per row became hundreds.

Check first: open one slow trace. Many identical statements that differ only by the id value is the signature, and the table name tells me which association is touched. Count statements per request in staging.

Fix:

  1. Give the screen a read use case: a DTO projection, or join fetch or an entity graph for the ToOne parts.
  2. For collections, never join them into a paged query. Use @BatchSize or default_batch_fetch_size=50, or a second query by parent ids.
  3. Make all associations LAZY (ToOne defaults to EAGER).

Prevent: a statement-count assertion in tests of the main endpoints, a global batch fetch size as a safety net, open-in-view=false, and test data of realistic size. Adding a cache is not a fix: it hides the first request and adds invalidation problems.

Remember: many identical SELECTs = N+1. Fix the query shape, then lock it in with a statement-count test.

Two support agents edit the same customer, and one agent's change disappears. How do you find and fix it? Senior

This is a lost update: both agents loaded the same row, both saved, and the second save silently overwrote the first. I add a @Version column so the second save fails, return HTTP 409, and make the screen show the conflict. I also send the version to the client and back.

Situation: last write wins, with no error anywhere.

Check first: look for a @Version field. Check whether the update API re-reads the entity by id and copies all fields from the request (this overwrites even fields the agent never touched), and whether the request carries the version the agent saw.

Fix: add @Version (a numeric column with a migration, default 0). Include version in the response and require it in the update request, then copy it onto the loaded entity (or compare) so Hibernate's check uses the agent's version, not the fresh one. Map ObjectOptimisticLockingFailureException to 409 with a message. Where partial updates are the real need, use a PATCH that changes only the sent fields.

Prevent: a version column on every mutable table, and a concurrency test with two threads or two transactions.

Remember: silent overwrite means no version check. Add @Version, pass it through the API, answer 409.

Production logs show "Deadlock found when trying to get lock" a few times per hour during order processing. What do you do? Senior

A deadlock means two transactions each hold a row the other needs, in opposite order. The database kills one of them. I find the two statements in the database's deadlock report, make all code lock rows in the same order, shorten the transactions, and add a retry for the victim.

Situation: for example transaction A updates order 1 then order 2, while B updates order 2 then order 1.

Check first: read the deadlock detail from the database (SHOW ENGINE INNODB STATUS in MySQL, the server log in PostgreSQL). It lists the statements and the locked rows. Then map them to code paths. Remember that Hibernate orders statements itself at flush (inserts, updates, deletes), so the actual order differs from the order in my code.

Fix:

  • Process rows in a stable order (sort ids before updating or locking), and set hibernate.order_updates=true.
  • Keep transactions short, and move remote calls out.
  • Replace read-then-write with one atomic update ... where, or lock with FOR UPDATE in id order.
  • Retry the failed transaction a couple of times (deadlock victims are safe to retry).

Prevent: a documented lock order, missing foreign-key indexes added (they widen locks), and load tests with concurrent writers.

Remember: deadlock = opposite lock order. Same order, short transactions, retry the victim.

The product list endpoint with filters and paging is slow and the database CPU is high. Walk me through it. Senior

I measure first, in this order: how many statements run, what the slowest statement is and its execution plan, and then whether I load more than I show. The usual culprits are N+1, a collection join with paging, a slow count(*), a missing index, and loading full entities for a list.

Check first: SQL log or APM for statement count per request; EXPLAIN on the slowest query; look for the in-memory pagination warning (HHH000104) and for offset with big numbers.

Fix, in order of payoff:

  1. Return a DTO projection with only the displayed columns, with ToOne data joined in the same query.
  2. Index the filter and sort columns for the common combinations; avoid leading-wildcard like.
  3. Page ids first when a collection is involved; use Slice or a cheaper count if the total is expensive; use keyset paging for deep pages.
  4. Only then consider caching.

Prevent: an endpoint-level performance test with production-sized data, and statement-count assertions.

Remember: count statements, read the plan, project only what is shown, index filters. Cache last.

After disabling Open Session In View, the API returns LazyInitializationException on several endpoints. How do you handle it? Intermediate

That is the bug OSIV was hiding: controllers or serialisers were touching lazy data after the transaction ended. I go endpoint by endpoint: load what the response needs inside the service transaction (fetch join, entity graph or projection) and return DTOs, so nothing lazy leaves the service.

Check first: the stack trace names the lazy field and the serialiser or controller line that touched it. List the endpoints that return entities directly.

Fix: for each endpoint, decide what the response needs, fetch exactly that in a read-only transaction, map to a DTO inside the service. Use default_batch_fetch_size to soften the remaining cases. Do not go back to OSIV, EAGER, or enable_lazy_load_no_trans: they bring the same hidden costs back.

Prevent: a rule that controllers never return entities, and integration tests that call the real endpoints with OSIV off.

Remember: LazyInit after turning OSIV off is a good sign: the hidden lazy loads are now visible. Fetch in the service, return DTOs.

After a bulk update the API still returns the old status for some records. Why? Senior

The bulk update ran in the database but the persistence context still holds the old entities, so later reads in the same transaction answer from memory. I flush before the bulk update and clear (or refresh) after it, or use @Modifying(flushAutomatically = true, clearAutomatically = true). If the stale value is on another server, I also check a second-level cache.

Check first: is the stale read in the same transaction as the update? If yes, it is the context. If it is in a later request, look at L2 or query caches, or an application cache that the bulk update did not evict. Native SQL updates are the usual cache bypass.

Prevent: a convention that bulk updates run in their own method and transaction, and the version column updated in the statement (set version = version + 1) so optimistic locking still sees the change.

Remember: bulk SQL skips the context and the version. Flush before, clear after.

Under load the service logs "Connection is not available, request timed out after 30000ms", though the database CPU is low. What is going on? Senior

The pool is empty because connections are held too long, not because the database is busy. Threads wait for a free connection and time out. I look for what runs while a connection is held: remote calls inside transactions, OSIV keeping the session open during slow work, REQUIRES_NEW needing a second connection, or leaks. Then I shorten those, instead of just raising the pool size.

Check first: HikariCP metrics (active, idle, pending threads) and a thread dump: are many threads waiting for a connection while others sit in a remote call or a long loop with a connection held? Check whether OSIV is on. Enable leakDetectionThreshold to find code that holds a connection too long.

Fix: move remote calls out of transactions, turn OSIV off, avoid nested REQUIRES_NEW in a pool-limited path (or make sure the pool is bigger than the maximum nesting times concurrent requests), split long transactions into chunks, and size the pool deliberately.

Prevent: pool metrics and alerts, and a load test that includes the slowest downstream.

Remember: empty pool with idle database = connections held too long. Shorten transactions, do not just grow the pool.

A transaction deletes a row and inserts a replacement with the same unique key, and fails with a duplicate key error even though the delete comes first in the code. Why? Senior

Hibernate runs inserts before deletes at flush, so the new row hits the unique constraint while the old row still exists. I either call em.flush() right after the delete so it is sent first, or, better, change the existing row instead of deleting and inserting.

Situation: in the code, repo.delete(old); repo.save(new) with the same unique value, and the log shows INSERT before DELETE.

Check first: the SQL log order. It confirms the action-queue order (inserts, updates, collection changes, deletes).

Fix: update the row in place when the intent is "replace". If a delete plus insert is really needed, flush between them (deleteAndFlush in Spring Data, or em.flush()). For collections of children with a unique key, the same ordering applies to orphanRemoval.

Prevent: remember that code order is not SQL order, and add an integration test for the replace case.

Remember: flush order is insert, update, delete. Need delete first? Flush after it, or just update.

Users report old prices after an admin updated them, but only on some servers. What do you check? Senior

"Only on some servers" points to a node-local cache. Each node has its own second-level or application cache, and the update on one node did not invalidate the others. I check which cache holds prices, whether the provider is cluster-aware, and whether the price was changed outside Hibernate (SQL script, another service, a bulk or native update).

Check first: is the Hibernate L2 cache or query cache enabled for the price entity? Is the provider local (default Ehcache) or distributed? Does an application cache (Spring Cache) hold price DTOs without expiry?

Fix: give the data a time-to-live as a safety net, use a distributed cache with invalidation (Redis, Hazelcast, Infinispan) or evict by event, and make every writer go through the same path. If prices change often, do not cache them in L2 at all.

Prevent: decide per data type how stale it may be, and write a test that updates on node A and reads on node B.

Remember: some servers stale = a local cache per node. Add expiry, shared invalidation, or no cache.

A developer says "I put @Transactional, but half the changes were saved and half were not". How do you debug it? Intermediate

Either there was no transaction around the whole method, or it committed even though an error happened. I check the usual four: self-invocation (the call never went through the proxy), a swallowed exception, a checked exception that does not roll back by default, and a REQUIRES_NEW or async call that ran in a different transaction.

Check first: turn on logging.level.org.springframework.transaction.interceptor=TRACE (or org.springframework.orm.jpa) to see "Getting transaction for ..." and "Completing transaction". Does the log show one transaction or several? Was the annotated method called from another bean?

Fix: move the method to another bean or use TransactionTemplate; let the exception propagate or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(); add rollbackFor = Exception.class if checked exceptions are expected; keep async work in its own transaction by design.

Prevent: an integration test that forces a failure in the middle and asserts that nothing was saved.

Remember: partial saves mean the transaction did not span the work. Check proxy bypass, swallowed and checked exceptions.

We catch an exception from an inner service call and continue, but the request ends with UnexpectedRollbackException. Explain and fix. Senior

The inner method is @Transactional(REQUIRED), so it joined the outer transaction. When it threw, the proxy marked the whole shared transaction rollback-only. My catch block swallowed the exception, but the mark stays, and at the end Spring cannot commit and throws UnexpectedRollbackException. To keep going after an inner failure, the inner work must run in its own transaction or not throw.

Check first: find which inner call threw (the log shows "Participating transaction failed - marking existing transaction as rollback-only").

Fix:

  • If the inner step is optional, run it with REQUIRES_NEW, so its rollback is separate. Watch the second connection.
  • Or do not use an exception for expected cases: check first and return a result.
  • Or use noRollbackFor for an exception that is really harmless.
  • Do not catch and continue after a persistence exception in the same context: the session may be in an inconsistent state.

Prevent: test the failure path of each inner call, and keep transaction boundaries visible in the design.

Remember: inner REQUIRED failure poisons the shared transaction. Use REQUIRES_NEW or avoid the exception.

You are asked to upgrade a service from Spring Boot 2.7 (Hibernate 5) to Spring Boot 3 (Hibernate 6). How do you plan the persistence part? Senior

I treat it as a behaviour change, not only a rename. Step one is javax.persistence to jakarta.persistence (mechanical, with a migration tool). Step two is to check what Hibernate 6 does differently: id generation naming, stricter HQL, some type mappings, and SQL it generates. Then I run the full integration test suite on a real database and compare statements and schema.

Check first (known areas of change, typically):

  • Ids: AUTO and sequences now use one sequence per entity (entity_seq) instead of the shared hibernate_sequence, so existing databases break unless I set the legacy naming strategy or add the sequences.
  • HQL: stricter parsing and some different semantics; a few queries need fixing. distinct for fetch joins is no longer needed.
  • Types: date, time, enum and JSON mappings changed in places; check with ddl-auto=validate against the real schema.
  • Config: remove a hand-set dialect (it is detected), and check logging names (the bind logger moved to org.hibernate.orm.jdbc.bind).
  • Java 17 minimum, and Spring Data JPA 3.

Prevent surprises: upgrade on a branch with Testcontainers against the production database engine, run validate, diff the SQL of key flows before and after, and roll out gradually.

Remember: javax to jakarta is the easy part. Watch id sequences, HQL strictness and type mappings, and validate against a real schema.
