Version notes used on this page. JPA (Java Persistence API) is the specification. Up to JPA 2.2 the package was javax.persistence. Since JPA 3.0 (after the move to the Eclipse Foundation) it is jakarta.persistence; only the package name changed, not the ideas. Hibernate 5.x (5.6 is the last) uses javax and is what Spring Boot 2.x ships with. Hibernate 6.x uses jakarta, needs Java 11 or newer (Java 17 for the Spring Boot 3 stack), rewrote the query engine, and is what Spring Boot 3.x ships with. Hibernate 7 follows JPA 3.2. Where behaviour differs between 5 and 6, the answer says so. Spring Data JPA 3.x goes with Spring Boot 3.

Mental model: the 8 ideas everything hangs on

One line: an entity is a Java object that is being watched. Inside a transaction, the watcher (the persistence context) remembers every entity it loaded, notices what you changed, and writes the SQL for it when it flushes. Most bugs come from forgetting that the watcher exists, or that it is closed.
  1. JPA is a spec, Hibernate is an implementation, Spring Data is a convenience layer. You write against JPA, Hibernate runs it, Spring Data JPA removes the repository boilerplate.
  2. An entity is in a state. New (transient), managed (persistent), detached, removed. Only managed entities are watched.
  3. The persistence context is a per-transaction identity map. Load row 5 twice in the same context and you get the same Java object. This is the first-level cache.
  4. Dirty checking. Change a managed entity and you do not call save. At flush time Hibernate compares it with the snapshot it took at load and writes an UPDATE.
  5. Writes are delayed. SQL is queued and sent at flush: before a query that could be affected, and at commit. SQL order is Hibernate's, not your code's.
  6. Laziness is a proxy. A lazy association is a placeholder that loads on first touch. It only works while the context is open. That is the source of LazyInitializationException and of N+1.
  7. The owning side decides the foreign key. In a two-way relationship, only the side without mappedBy writes the column.
  8. Concurrency is your job. The persistence context does not stop two users overwriting each other. @Version (optimistic) or row locks (pessimistic) do.

1. Basics and the entity lifecycle

What is the difference between JPA, Hibernate and Spring Data JPA? Basic

What the interviewer is testing: whether you know which layer does what, so you can debug the right one.

JPA is only a specification: a set of interfaces and annotations such as @Entity, EntityManager and the query language JPQL. It does nothing alone. Hibernate is the most popular implementation (a "JPA provider"). It generates the SQL, manages the persistence context, caches, and adds extra features of its own. EclipseLink is another provider. Spring Data JPA sits on top: you declare an interface like OrderRepository extends JpaRepository<Order, Long> and Spring builds the implementation at runtime. Inside, that implementation just calls the EntityManager. So when a query is slow, you look at Hibernate and the database. When a method name does not work, you look at Spring Data. When an annotation is not found, check whether it is from JPA or from Hibernate.

Likely follow-ups
  • Can you use JPA without Hibernate? Yes, with EclipseLink or OpenJPA, but Hibernate is the default choice almost everywhere.
  • Does Spring Data JPA replace the EntityManager? No, it wraps it. You can still inject the EntityManager for custom code.
What changed between Hibernate 5 and 6, and between javax and jakarta? Intermediate

What the interviewer is testing: do you know your upgrade path, since many companies are mid-migration.

The javax.persistence to jakarta.persistence change is a pure rename of the package. It happened when Java EE moved to the Eclipse Foundation and became Jakarta EE 9. Hibernate 5.x stays on javax. Hibernate 6.0 and later use jakarta, and so do Spring Boot 3 and Spring Data JPA 3. That is why upgrading to Spring Boot 3 breaks every import in your entities. Besides the rename, Hibernate 6 rewrote the query engine (it builds a semantic query model, SQM, and then SQL), changed some defaults and removed or deprecated older APIs. Examples: results of a join fetch are de-duplicated for you, so distinct is no longer needed just for that; the legacy Hibernate Criteria API is gone; @Where was superseded by @SQLRestriction (6.3); and a @TenantId annotation was added for discriminator multi-tenancy. Sequence-based id generation also changed in naming: each entity gets its own sequence named like order_seq by default, instead of one shared hibernate_sequence.

Likely follow-ups
  • How do you migrate? Upgrade to the latest 5.6 first, fix deprecation warnings, switch the imports (OpenRewrite recipes do it), then move to Spring Boot 3 and run the tests with SQL logging to spot changed queries.
  • What is the most common surprise? Id generator names, so new inserts fail or collide. Keep the old strategy explicitly if the schema already exists.
Why use an ORM at all? What are its costs? Basic

What the interviewer is testing: balanced judgement, not fan-boy or hater.

An ORM (object-relational mapper) turns rows into objects and back. It removes a lot of repetitive JDBC code: opening statements, binding parameters, reading result sets, writing basic inserts and updates. It also gives you dirty checking, relationships as object references, caching, portability between databases, and optimistic locking nearly for free. The cost is that the mapping is not simple. Objects form graphs and tables form sets, and this "impedance mismatch" produces surprises: the N+1 query problem, lazy loading errors, hidden flushes, large memory use. A good rule I use: JPA is excellent for ordinary create, read, update and delete on aggregates. For heavy reporting, big bulk work or very complex SQL, drop to native SQL, jOOQ or JDBC in the same application. You do not have to pick only one.

Likely follow-ups
  • Name the "object-relational impedance mismatch". Inheritance, identity (== versus primary key), associations (references versus foreign keys) and graph navigation do not map one to one.
What does a class need to be a JPA entity? Why can it not be final? Basic

What the interviewer is testing: basics, plus awareness of proxies.

It must have @Entity, an identifier marked with @Id, and a no-argument constructor that is public or protected. The class must not be final, and persistent methods and fields must not be final either. The reason is that Hibernate creates subclasses at runtime, called proxies, to support lazy loading. A final class cannot be subclassed, so lazy loading silently turns off or fails. Fields should be private, and Hibernate usually reads and writes them directly if you put @Id on the field (field access). If you put it on the getter, it uses property access. Do not mix them. Java records cannot be entities because they are final and immutable, although a record can be used as an embeddable in recent Hibernate versions (about 6.2 and later) and is a fine DTO.

@Entity
@Table(name = "orders")
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    protected Order() { }          // required by JPA, hidden from callers
    public Order(String customer) { this.customer = customer; }
    private String customer;
}
Likely follow-ups
  • Can an entity have a constructor with arguments? Yes, as long as the no-arg one also exists.
  • Why avoid Lombok @Data on entities? It generates equals, hashCode and toString over all fields, which touch lazy associations and can loop forever.
What is the difference between EntityManager and Session, and EntityManagerFactory and SessionFactory? Intermediate

What the interviewer is testing: the JPA-versus-Hibernate vocabulary.

EntityManager is the JPA interface: persist, find, merge, remove, createQuery. Session is Hibernate's own, older interface, and it extends EntityManager (since Hibernate 5.2). So every Session is an EntityManager, and the Session adds Hibernate-only features such as setJdbcBatchSize, stateless sessions, byMultipleIds, and the old save and saveOrUpdate. In the same way SessionFactory extends EntityManagerFactory. The factory is built once at startup. It is heavy, thread-safe, and holds mapping metadata and the second-level cache. The EntityManager or Session is light, not thread-safe, and represents one unit of work with one persistence context. When you need a Hibernate feature, you can unwrap it: entityManager.unwrap(Session.class).

Session session = entityManager.unwrap(Session.class);
session.setJdbcBatchSize(50);
SessionFactory sf = entityManagerFactory.unwrap(SessionFactory.class);
sf.getStatistics();
Likely follow-ups
  • Is the EntityManager thread-safe? No. In Spring you inject a shared proxy that hands out one real EntityManager per transaction and thread.
Common mistakes: creating an EntityManager per request by hand and forgetting to close it, or sharing one across threads.
Explain the entity lifecycle states and what moves an entity between them. Basic

What the interviewer is testing: the single most asked JPA concept; everything else builds on it.

An entity is in one of four states. New (transient): you created it with new; it has no row and nobody watches it. Managed (persistent): it is attached to a persistence context. Hibernate watches it, and any change will be written at flush. You get this state with persist or by loading with find or a query. Detached: it has an id and maybe a row, but its context is closed or you called detach or clear. Changes are no longer tracked. Removed: you called remove; the row will be deleted at flush. merge takes a detached (or new) object, copies its state onto a managed instance and returns that managed instance. The object you passed in stays detached. The word "persistent" in the Hibernate docs equals "managed" in JPA.

Likely follow-ups
  • Can a removed entity come back? Yes, call persist on it again before flush.
  • What is a "transient" entity in Hibernate error messages? The same as new. "TransientObjectException" means you point to an unsaved entity.
What is the difference between persist, merge, save, saveOrUpdate and update? Intermediate

What the interviewer is testing: precise knowledge of what each call does to the object you hold.

persist(entity) is for a new entity. The same object you passed becomes managed, and the INSERT happens at flush (immediately only when the id is IDENTITY). Calling it on a detached entity throws. merge(entity) works for new or detached objects: it loads the row (or a managed copy), copies your values onto it and returns the managed copy. Your object stays detached, so you must keep using the returned one. Merge usually costs an extra SELECT. save, update and saveOrUpdate are old Hibernate-only methods. update re-attaches a detached instance itself, without a copy. They are deprecated in Hibernate 6 and I would not use them in new code. In Spring Data, repository.save() is not a Hibernate call: it checks "is this new?" and calls persist if yes or merge if no.

Order saved = em.merge(detachedOrder);   // use 'saved', not detachedOrder
saved.setStatus(PAID);                   // tracked
detachedOrder.setStatus(PAID);           // NOT tracked, silently lost
Likely follow-ups
  • Why can merge hurt? It overwrites every field, including ones the user never edited, which can wipe out other people's changes. A version column protects you.
  • Do you call save on a managed entity to update it? No. Dirty checking does that. The call is harmless but noise.
Common mistakes: modifying the argument of merge after the call, and expecting save() to be needed for every change inside a transaction.
find versus getReference (get versus load). When would you use the lazy one? Intermediate

What the interviewer is testing: proxies and avoiding useless SELECTs.

find(Order.class, 5L) runs a SELECT right away (unless the entity is already in the persistence context) and returns the entity, or null if the row does not exist. getReference(Order.class, 5L) returns a proxy, a stand-in object that only knows its id. No SQL runs until you call a method other than getId. If the row does not exist you get an EntityNotFoundException at that later moment. The best use is setting a foreign key without loading the other side. For example, to create a comment for post 5 you do comment.setPost(em.getReference(Post.class, 5L)), and Hibernate writes post_id = 5 with no SELECT on the post. Spring Data offers this as getReferenceById (earlier getById, deprecated).

Likely follow-ups
  • What happens if you touch a proxy after the session closed? LazyInitializationException.
  • Hibernate names? session.get is like find, session.load is like getReference.
How do Hibernate proxies work, and what traps do they create? Senior

What the interviewer is testing: deeper understanding of lazy loading and why instanceof, equals and getClass sometimes misbehave.

When Hibernate needs a placeholder for an entity it has not loaded, it generates a subclass at runtime with ByteBuddy (the default since Hibernate 5.3; older versions used Javassist). Every method call on the proxy first checks "is the real object loaded?". If not, it runs a SELECT using the session, stores the real entity inside the proxy, and delegates. Traps: (1) proxy.getClass() is the generated subclass, not your class, so getClass() == other.getClass() in equals breaks. Use Hibernate.getClass(obj) or instanceof. (2) With inheritance, a proxy of the base type is not an instance of the subclass, so instanceof Dog fails even though the row is a Dog. Use Hibernate.unproxy. (3) Final classes and methods cannot be proxied. (4) Accessing fields directly instead of getters on another object skips the proxy and returns null. (5) @OneToOne on the side that has no foreign key cannot be lazy by proxy, because Hibernate must query to know if the value is null.

Likely follow-ups
  • How do you check if a proxy is loaded without loading it? Hibernate.isInitialized(obj) or PersistenceUnitUtil.isLoaded.
  • What is bytecode enhancement? A build-time option that changes the entity class itself to support lazy fields and cheaper dirty tracking, so proxies are less needed.

2. Persistence context, flush and dirty checking

What is the persistence context, and what is the first-level cache? Basic

What the interviewer is testing: the core concept. Without it you cannot explain dirty checking, N+1 or stale data.

The persistence context is the set of managed entities for one EntityManager. Think of it as a map keyed by entity type plus id. It lives inside the Session and by default is created when a transaction starts and ends when it finishes. It does three jobs. First, identity guarantee: asking for the same id twice returns the same Java instance, so find(1) twice gives == objects and only one SELECT. That is the first-level (L1) cache, and it cannot be turned off. Second, change tracking: it keeps a snapshot of each entity's loaded values. Third, write-behind: it queues INSERT, UPDATE and DELETE and sends them at flush. The L1 cache is per transaction and per thread, so it never shares data between users.

Likely follow-ups
  • Does a JPQL query hit the L1 cache? The SQL always runs. But for each returned row, if that id is already in the context, you get the existing object and its in-memory state, not fresh column values.
  • Is the cache shared between threads? No.
When does Hibernate flush, and what are the flush modes? Intermediate

What the interviewer is testing: do you understand that SQL is delayed and why "my change is not in the database yet" happens.

Flush means "send the queued changes to the database", but it does not commit. Under the default mode AUTO, Hibernate flushes (1) before a transaction commits, (2) before running a query when pending changes might affect its result (it looks at which tables the query touches), and (3) when you call flush() yourself. With a JPA EntityManager, a native SQL query normally flushes everything first, since Hibernate cannot know which tables it reads. COMMIT mode flushes only at commit, so a query may not see your pending changes. Hibernate also has ALWAYS (flush before every query) and MANUAL (only when you call flush). MANUAL is what Spring sets for @Transactional(readOnly = true), which saves the dirty-check work. After a flush the data is in the database inside your open transaction. Other transactions cannot see it until commit, and a rollback removes it.

em.setFlushMode(FlushModeType.COMMIT);          // JPA
session.setHibernateFlushMode(FlushMode.MANUAL); // Hibernate only
em.flush();      // force now, still not committed
Likely follow-ups
  • Why do constraint violations appear at commit time, far from the line that caused them? Because the INSERT or UPDATE only ran at flush. Call flush() to fail early where you can handle it.
  • Does persist run an INSERT? Only immediately for IDENTITY ids, because the database must produce the id.
How does automatic dirty checking work, and what does it cost? Intermediate

What the interviewer is testing: inner workings and performance awareness.

When Hibernate loads an entity, it stores a copy of its property values, called the snapshot or loaded state. At flush time it goes through every managed entity, compares current values with the snapshot, and for each entity that differs it queues an UPDATE. By default the UPDATE sets all columns, not just the changed ones, so the same prepared statement can be reused. @DynamicUpdate changes this to only changed columns, which helps with wide tables or triggers, but builds new SQL each time. The cost is proportional to the number of managed entities times their properties, on every flush. Loading 50,000 entities and flushing three times can burn a lot of CPU. Fixes: read-only transactions, read-only queries (setReadOnly(true) hint) or projections for data you will not modify, clear() in batches, or bytecode enhancement, which lets the entity say "I changed".

Likely follow-ups
  • If I change a field and then change it back? No UPDATE, since the value equals the snapshot.
  • Does dirty checking work on a detached entity? No. Merge it first or load it in the transaction.
  • Does a mutable collection of embeddables or a Date field confuse it? Mutating a mutable value type in place can be detected by deep comparison, but immutable types like LocalDate are cheaper and safer.
In what order does Hibernate execute SQL at flush? Why does it matter? Senior

What the interviewer is testing: depth on write-behind and unique-constraint surprises.

Hibernate does not run SQL in the order your code called the methods. At flush it runs, in this order: entity inserts, entity updates, collection removals, collection element updates and inserts, then collection inserts, then entity deletes. A well-known surprise: you delete a row and insert a new row with the same unique value in one transaction. The insert runs before the delete, so the unique constraint fails. The fix is to call em.flush() right after the delete, or to update the existing row instead. Another effect: a business rule that depends on the order of two statements will not work unless you flush between them. This is also why hibernate.order_inserts and order_updates exist: they sort statements of the same type by entity so JDBC batching can group them.

repo.delete(oldBadge);
repo.flush();                 // push the DELETE out first
repo.save(new Badge(user, "GOLD"));  // unique (user, name) is now safe
Likely follow-ups
  • Why the order "inserts first"? So that parent rows exist before children that reference them, and deletes last so children go before parents are touched.
What do detach, clear, refresh and flush do, and when do you use each? Intermediate

What the interviewer is testing: control over the persistence context in long jobs.

flush() writes pending changes to the database, keeps everything managed. detach(entity) removes one entity from the context, so it is no longer tracked. clear() detaches everything. refresh(entity) reloads the row from the database and overwrites the in-memory state, which is how you pick up changes made by a bulk update or another transaction. The classic batch pattern is: process a chunk, flush(), then clear(), so memory stays flat. Important: if you call clear() without flushing first, the pending changes are thrown away. Also remember that after clear() every entity you still hold is detached, and lazy fields on them may fail.

for (int i = 0; i < items.size(); i++) {
    em.persist(items.get(i));
    if (i % 50 == 49) { em.flush(); em.clear(); }
}
Likely follow-ups
  • What happens to unflushed changes on clear? They are lost.
What is a transaction-scoped versus an extended persistence context? Senior

What the interviewer is testing: how the context lifetime ties to the transaction, and why a long-lived context is risky.

A transaction-scoped context (the default in Spring and Jakarta EE) is created when the first EntityManager call happens inside a transaction and is closed at the end of that transaction. After that, entities are detached. An extended context outlives a transaction. In Jakarta EE stateful beans you can mark an EntityManager as EXTENDED; in Hibernate terms this is the "session-per-conversation" pattern. It lets a multi-step wizard keep entities managed across several requests, with flush mode set to manual until the last step. The price is memory held per user, stale data (the context never refreshes), and a risk of huge, slow flushes. Almost every modern REST service stays stateless and uses a short, transaction-scoped context. Open Session In View stretches the context across a web request, which is a milder form of the same idea.

Likely follow-ups
  • Which would you pick for a REST API? Transaction-scoped. Pass ids and DTOs between requests, not entities.
How does Spring give you an EntityManager, and what does @PersistenceContext inject? Senior

What the interviewer is testing: how a singleton bean can use a non-thread-safe object.

The injected EntityManager is not a real one. It is a shared proxy, a thin wrapper that works like a thread-local lookup. Each call on it asks Spring "which EntityManager is bound to the current transaction and thread?". If a @Transactional method started a transaction, JpaTransactionManager has already created an EntityManager and bound it, so you get that one. If there is no transaction, the proxy creates a short-lived EntityManager for that single call, and queries still work but results come back detached and writes may not happen. That is why a repository method outside a transaction can behave differently than inside one. With @PersistenceContext or plain @Autowired or constructor injection of EntityManager, you get the same proxy. This design is what lets singleton services and repositories share it safely.

Likely follow-ups
  • Why does my modification not save when I call a service method without @Transactional? There is no managed context at flush time, so nothing writes it. Spring Data repository methods have their own small transaction, but your own setter calls on a returned entity do not.
What does @Transactional(readOnly = true) really do? Intermediate

What the interviewer is testing: separating real effects from folklore.

It is a hint, not a lock. With Spring and Hibernate it does a few concrete things. Spring sets the Hibernate flush mode to MANUAL, so there is no dirty checking at the end and no accidental writes. Hibernate can skip taking snapshots for entities loaded in a read-only session, saving memory. Spring also calls connection.setReadOnly(true), which some drivers or pools use to route to a replica or to optimise (PostgreSQL then rejects writes, MySQL can too). It does not stop you calling repository.save() on a database that ignores the hint, and it does not give a consistent snapshot unless your isolation level does. I use it on every query-only service method: it is cheap, it documents intent, and it gives the performance win on large reads.

Likely follow-ups
  • Can a read-only method call a write method with REQUIRED propagation? It joins the outer read-only transaction, so the write may be silently dropped or rejected. Use REQUIRES_NEW if the write must happen.
What are JPA lifecycle callbacks and entity listeners, and what are the limits? Intermediate

What the interviewer is testing: how to hook into persistence for auditing or validation, and the restrictions.

Callbacks are methods annotated @PrePersist, @PostPersist, @PreUpdate, @PostUpdate, @PreRemove, @PostRemove and @PostLoad. You can put them on the entity itself or on a separate listener class registered with @EntityListeners. They are good for setting created and modified timestamps, normalising a field, or computing a transient value after load. Rules to remember: they run inside the persistence operation, so inside them you must not call EntityManager operations, query other entities or change relationships, because the context is mid-flush. @PreUpdate runs only when Hibernate found the entity dirty, at flush. And bulk JPQL updates, native queries and plain JDBC bypass callbacks completely. For cross-service reactions, do not send messages from a callback: the transaction may still roll back. Publish after commit instead (the outbox pattern or @TransactionalEventListener).

Likely follow-ups
  • Callback versus Hibernate Interceptor or Envers? Interceptors and event listeners are Hibernate-specific and can see more detail; Envers is a full history-tracking module.

3. Mappings: relationships, inheritance, ids

What is the owning side of a relationship, and what does mappedBy do? Basic

What the interviewer is testing: the most common source of "my relationship is not saved" bugs.

In the database a relationship is one foreign key column on one table. In Java a two-way relationship is two references, one on each object. JPA needs to know which Java field controls the column. That field is the owning side. It is the side without mappedBy, and for one-to-many it is always the @ManyToOne side, because the foreign key lives in the "many" table. The other side, the inverse side, has mappedBy = "fieldNameOnOwner", and Hibernate ignores it when writing. So if you only add a child to parent.getChildren() and never set child.setParent(parent), the foreign key is null and nothing is saved. The rule: always set the owning side, and keep both sides in sync with a helper method.

Likely follow-ups
  • Which side owns a many-to-many? Whichever side has no mappedBy; it owns the join table.
  • What if both sides have a JoinColumn? Two writers for one column, a bug that creates duplicate or conflicting SQL.
How do you map a bidirectional one-to-many safely? Intermediate

What the interviewer is testing: practical mapping habits that avoid known pitfalls.

Make the child own the relationship with @ManyToOne(fetch = LAZY), and put mappedBy on the parent's collection. Initialise the collection (new ArrayList<>()) so it is never null. Add addItem and removeItem helper methods on the parent that update both sides together. Do not expose the raw list for callers to modify, return an unmodifiable view. Add cascade = ALL and orphanRemoval = true only if the child cannot live without the parent, as in order and order lines. Use a join on a foreign key column, not a join table, because the join table adds an extra table and extra SQL for no reason.

@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    public void addItem(OrderItem i)    { items.add(i); i.setOrder(this); }
    public void removeItem(OrderItem i) { items.remove(i); i.setOrder(null); }
}
@Entity
public class OrderItem {
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id")
    private Order order;
}
Likely follow-ups
  • Why LAZY on ManyToOne? The default is EAGER, which loads the parent for every child and fuels N+1.
What is wrong with a unidirectional @OneToMany? Senior

What the interviewer is testing: knowing that a mapping that "looks simpler" produces worse SQL.

A unidirectional @OneToMany with no @JoinColumn makes Hibernate create a hidden join table with two foreign keys. Every add or remove touches that extra table. With a List (a "bag", with no index column), removing one element deletes all join rows for the parent and re-inserts the remaining ones, which is very wasteful. If you add @JoinColumn(name = "parent_id") on the one side, it uses the child's table, but then the child row is inserted with a null foreign key first and an extra UPDATE sets it later, and the column cannot be NOT NULL unless you also say nullable = false. The clean answer is to make it bidirectional with the many side as owner, or to avoid the collection altogether and query children by parent id with a repository method. A parent that holds a collection of thousands of children is a design smell anyway, since loading it is expensive.

Likely follow-ups
  • When is a collection mapping not needed? When you can always say itemRepo.findByOrderId(id). Fewer mapped collections means fewer accidents.
How do you map many-to-many, and why do people avoid it? Intermediate

What the interviewer is testing: practical judgement about join tables.

A many-to-many uses a join table with two foreign keys. You annotate one side with @ManyToMany and @JoinTable (the owner) and the other with @ManyToMany(mappedBy = ...). Three rules. Use a Set, not a List: removal from a bag rewrites the whole join table for that owner, while a set deletes exactly one row. Do not use CascadeType.REMOVE or ALL, because deleting one student would delete courses shared with others. Write helper methods that update both sides. And the main reason people avoid it: the moment the relationship needs its own data (enrolled date, grade, role), a pure many-to-many cannot hold it. So you model a join entity such as Enrollment with two @ManyToOne fields and extra columns. Many real systems start with the join entity right away.

@ManyToMany
@JoinTable(name = "student_course",
    joinColumns = @JoinColumn(name = "student_id"),
    inverseJoinColumns = @JoinColumn(name = "course_id"))
private Set<Course> courses = new HashSet<>();
Likely follow-ups
  • Why does a Set need good equals and hashCode? Otherwise duplicates and lookups misbehave. See the equals/hashCode question.
What does cascade mean, and which cascade types exist? Intermediate

What the interviewer is testing: when to propagate operations, and the danger of cascading too far.

Cascade means "when I do an operation on this entity, also do it on the related entities". The JPA types are PERSIST, MERGE, REMOVE, REFRESH, DETACH and ALL (all of them). Hibernate adds its own, such as SAVE_UPDATE and REPLICATE. Example: with cascade = PERSIST on Order.items, calling persist(order) also persists the items. Without it, persisting an order that points to an unsaved item fails at flush with "object references an unsaved transient instance". Cascade should follow ownership: use it from a parent to the children it owns (order to lines), never to a shared or independent entity (order to customer). REMOVE on a @ManyToOne would delete the customer when you delete one order. Also, cascade is not the same as the database's ON DELETE CASCADE. The JPA one runs in Java by loading each child, the database one runs in the engine and is faster, but the persistence context will not know about it.

Likely follow-ups
  • How does cascade REMOVE delete 1,000 children? One DELETE per child after loading them. For many children use a bulk delete or a database cascade.
Common mistakes: CascadeType.ALL on every relationship by habit, especially on @ManyToOne and @ManyToMany.
What is orphanRemoval, and how is it different from CascadeType.REMOVE? Intermediate

What the interviewer is testing: a classic subtle difference.

CascadeType.REMOVE says: when I delete the parent, delete its children. orphanRemoval = true says: if a child is removed from the parent's collection (or the reference is set to null), delete that child row, because it has become an orphan with no parent. So order.getItems().remove(item) deletes the item row at flush with orphanRemoval, but with only cascade REMOVE it would just try to null the foreign key (or do nothing, for a mappedBy side). Orphan removal also implies a remove when the parent is deleted. Use it only for true parent-owned children (composition), never for entities other aggregates also use. Trap: if you replace the collection object with a new list (order.setItems(newList)), Hibernate throws "A collection with cascade all-delete-orphan was no longer referenced by the owning entity instance". Keep the original collection and call clear() and addAll().

Likely follow-ups
  • Does orphanRemoval work on @ManyToOne? No, only on @OneToOne and @OneToMany.
How do you map a one-to-one, and why is the lazy loading problem there? Senior

What the interviewer is testing: knowledge of the shared-key mapping and the lazy limitation.

The most efficient mapping shares the primary key: the child's id is also the foreign key to the parent. In JPA 2 you write @OneToOne @MapsId on the child, and the child's table needs no separate id column. Reading the child by the parent's id needs no join. For lazy loading: the side that holds the foreign key (the owner) can be lazy, because Hibernate knows from the column whether the other side exists, so it can create a proxy. The inverse side (mappedBy) cannot, because Hibernate cannot tell whether a row exists without querying. So it loads the other side eagerly with an extra SELECT, even when you ask for LAZY. Solutions: make the dependent side own the key, use bytecode enhancement with lazy-group support, change it to a @OneToMany you treat as optional, or fetch the data you need with a query and a DTO. This is a known N+1 source.

@Entity
class UserProfile {
    @Id private Long id;
    @OneToOne(fetch = FetchType.LAZY) @MapsId
    @JoinColumn(name = "id")
    private User user;
}
What is an embeddable, and when would you use one? Basic

What the interviewer is testing: value objects in JPA.

An @Embeddable class is a group of fields that has no identity of its own and is stored in the same table as the owning entity. A typical example is Address (street, city, zip) or Money (amount, currency). In the entity you declare @Embedded Address address. It keeps the domain model clean, because you can put validation and methods on the value type, and the table stays flat with columns such as address_city. When you need the same embeddable twice in one entity (billing and shipping address), rename the columns with @AttributeOverrides. If all columns of an embeddable are null, Hibernate gives you a null embedded object, which surprises people who expect an empty object. Make embeddables immutable where possible. Do not give them @Id and do not point other entities at them.

@Embeddable
public class Address { private String street; private String city; }

@Embedded
@AttributeOverride(name = "city", column = @Column(name = "ship_city"))
private Address shipping;
Likely follow-ups
  • Embeddable versus separate entity? Use an entity when it has its own lifecycle or is shared. Use an embeddable for a value that always belongs to one owner.
What is @ElementCollection, and when is it a bad idea? Intermediate

What the interviewer is testing: the difference between a collection of values and a collection of entities.

@ElementCollection maps a collection of basic values or embeddables (for example a set of tags or phone numbers) to a separate table with a foreign key back to the owner. The elements have no identity of their own. This is convenient for small, simple lists that are always loaded and saved with the owner. The downsides: the collection is replaced as a whole when it changes in some cases (for a bag, delete everything and re-insert), you cannot query the elements as independent rows without a join, you cannot add more columns of metadata later without changing to an entity, and a large collection loads slowly. If elements need an id, auditing, their own queries, or could grow large, use a real entity with @OneToMany instead. Collections are lazy by default, which means a LazyInitializationException if touched outside the session.

Likely follow-ups
  • How do you get a stable order? @OrderColumn or @OrderBy; the first stores an index column and makes updates cheaper than a bag.
What inheritance mapping strategies does JPA have, and how do you choose? Intermediate

What the interviewer is testing: the trade-offs, not only the names.

First, @MappedSuperclass: a base class (for example with id, createdAt, version) whose fields are copied into each child's table. It is not an entity and cannot be queried. Then, for real entity hierarchies, three strategies via @Inheritance. SINGLE_TABLE (the default): one table for the whole tree with a discriminator column. It is the fastest, with no joins, and polymorphic queries are simple. The cost: columns of subclasses must be nullable, and the table can get wide. JOINED: one table per class, linked by primary key. It is normalised and allows NOT NULL on subclass columns, but reads need joins, so deep trees are slower. TABLE_PER_CLASS: one full table per concrete class, no shared table. Polymorphic queries become UNIONs and it cannot use IDENTITY ids, so I almost never use it. My default is single table for small hierarchies with a few subclass fields, and joined when subclass data is large and constraints matter.

Likely follow-ups
  • Does Hibernate offer a fourth style? Yes, the @Embeddable composition, plus @DiscriminatorFormula. Many teams also prefer composition over inheritance for domain reasons.
Explain the id generation strategies: IDENTITY, SEQUENCE, TABLE, AUTO, UUID. Intermediate

What the interviewer is testing: the link between id strategy and batching performance.

IDENTITY uses an auto-increment column. The database makes the id, so Hibernate must run the INSERT immediately to know it, which breaks JDBC insert batching. SEQUENCE asks a database sequence for the id before the insert, so inserts can wait until flush and be batched. With the default allocationSize = 50, Hibernate reads one sequence value and hands out 50 ids from memory (the "pooled" optimiser), so the sequence must be defined with INCREMENT BY 50 or ids collide. It is the best choice on PostgreSQL and Oracle. TABLE simulates a sequence with a table and row locks; slow, avoid. AUTO lets Hibernate pick: usually a sequence where the dialect supports it, otherwise identity or table. UUID: generated in Java, no round trip, good for distributed systems and client-generated ids, but random v4 UUIDs scatter inserts across a B-tree index and enlarge indexes. Time-ordered UUIDs (Hibernate 6.x has @UuidGenerator(style = TIME); UUIDv7) keep inserts roughly ordered.

@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
@SequenceGenerator(name = "order_seq", sequenceName = "order_seq", allocationSize = 50)
private Long id;
Likely follow-ups
  • What if allocationSize is 50 but the DB sequence increments by 1? Two instances get overlapping ranges and you see duplicate key errors.
  • Can you batch with IDENTITY? Not insert batching; MySQL users often use a sequence-like table or accept it.
How do you map a composite primary key? Intermediate

What the interviewer is testing: JPA's two ways to do it, and the equals/hashCode rule.

There are two styles. With @EmbeddedId you create an @Embeddable class holding the key fields and put one field of that type on the entity. With @IdClass you write a plain class with the same field names and annotate the entity's multiple @Id fields. I prefer @EmbeddedId: it is a single object you can pass around, and it reads clearly in queries (e.id.orderId). In both cases the key class must implement Serializable, have a public or protected no-arg constructor, and implement equals and hashCode using all key fields, because Hibernate uses it as a key in the persistence context map. A composite key makes foreign keys and joins larger and verbose, so unless the table is a legacy table or a pure join table, a surrogate single-column id plus a unique constraint is easier.

@Embeddable
public class EnrollmentId implements Serializable {
    private Long studentId; private Long courseId;
    // equals and hashCode on both fields
}
@Entity
public class Enrollment {
    @EmbeddedId private EnrollmentId id;
    @ManyToOne @MapsId("studentId") private Student student;
    @ManyToOne @MapsId("courseId")  private Course course;
}
How do you map enums, dates and custom types correctly? Basic

What the interviewer is testing: small mistakes that corrupt data later.

For enums always use @Enumerated(EnumType.STRING). The default is ORDINAL, which stores the position (0, 1, 2). If anyone later inserts or reorders a constant, all old rows silently change meaning. The string form is safe but a bit larger; for compact storage use an AttributeConverter with a stable code. For dates and times use java.time types (LocalDate, Instant, LocalDateTime). They are supported since JPA 2.2 and Hibernate 5.2. Store timestamps as UTC Instant, and avoid the old java.util.Date plus @Temporal. For money use BigDecimal with a declared precision and scale. For a value that is stored differently from how Java sees it (a JSON string, a comma list, a custom wrapper) write an @Converter implementing AttributeConverter<X, Y>. Hibernate 6 also has native JSON mapping support.

Likely follow-ups
  • Which time zone does LocalDateTime use? None. It has no zone, so decide a convention (UTC) or use Instant or OffsetDateTime.
How should you implement equals and hashCode on JPA entities? Senior

What the interviewer is testing: a very frequent senior question with a real trade-off.

The trouble: the id is often null until the entity is persisted, and entities can be proxies. If hashCode uses the id, it changes after persist, so an entity put in a HashSet before saving is "lost" afterwards. If you use all fields, you may touch lazy collections and recurse. Options. (1) Use a natural business key that is stable and unique (an ISBN, an email, a UUID assigned at construction). Best when you have one. (2) Use a UUID assigned in the constructor as a surrogate business key. (3) Use the database id in equals only when it is not null, and return a constant hashCode such as getClass().hashCode(). This is stable across persist, and only costs when huge sets are in memory. (4) Do not override at all, and accept identity equality, which is correct inside one persistence context because it guarantees one instance per row. In every variant: compare with instanceof or Hibernate.getClass (proxy-safe), and call getters, not fields, so a proxy answers correctly. Never include collections or lazy associations, and do not let Lombok generate it.

@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Book other)) return false;
    return isbn != null && isbn.equals(other.getIsbn());
}
@Override public int hashCode() { return Objects.hashCode(isbn); }
Likely follow-ups
  • Why does this matter in practice? Sets in @ManyToMany and detached entities in collections break without it. Also removeItem from a list uses equals.
Common mistakes: generated Lombok @EqualsAndHashCode over all fields, getClass() != o.getClass() which fails for proxies.
How do you do soft delete, and what are the pitfalls? Intermediate

What the interviewer is testing: Hibernate-specific features and their limits.

Soft delete means the row stays and a flag marks it deleted. In Hibernate you combine @SQLDelete(sql = "UPDATE book SET deleted = true WHERE id = ?") so remove turns into an UPDATE, and a filter on reads: @Where(clause = "deleted = false") in Hibernate 5 and 6.0 to 6.2, or @SQLRestriction in 6.3 and later. The filter applies to entity loads and to joins from other entities. Pitfalls: native queries ignore it, so they must add the condition themselves; unique constraints clash when a "deleted" row blocks a new row with the same value (use a partial unique index where the database supports it); cascades through the tree behave in surprising ways; and a tombstone table grows forever, so plan archiving. A newer Hibernate has dedicated soft delete support, but verify your version. An alternative is a database view or a separate archive table filled by a trigger.

Likely follow-ups
  • How do you read deleted rows for support tools? A separate native query or a second entity mapped on the same table without the restriction. A parameterised @Filter can be enabled or disabled per session.

4. Fetching, N+1 and projections

What is the difference between lazy and eager loading, and what are the JPA defaults? Basic

What the interviewer is testing: basic mapping knowledge plus a known default trap.

Eager loading fetches the association together with the owner, at the same time. Lazy loading puts a proxy (or an uninitialised collection wrapper) in its place and loads the real data only when you first use it. JPA defaults: @ManyToOne and @OneToOne are EAGER, @OneToMany, @ManyToMany and @ElementCollection are LAZY. The ToOne defaults are widely considered a mistake. In my own code I set every association to LAZY explicitly and then load what I need per use case with join fetch or an entity graph. A global EAGER cannot be undone in a single query: JPQL does not respect it, so Hibernate runs a second query for each eager row, which creates N+1. Lazy errs on the safe side, but needs an open session when you touch the data.

Likely follow-ups
  • Is FetchType.LAZY a guarantee? It is only a hint to the provider. Hibernate honours it for collections and for ToOne with proxies, with the OneToOne exception.
What is the N+1 select problem, and how does it happen? Basic

What the interviewer is testing: the most important performance pitfall of ORMs. Expect it in every interview.

You run one query to load N parents (for example 100 orders). Then in a loop you touch a lazy association on each one (order.getCustomer().getName()). Each touch fires one more SELECT. That is 1 query plus N queries. With 100 orders you run 101 statements, with 10,000 you run 10,001, and the endpoint is fast in development with five rows but crawls in production. The same happens with eager ToOne associations when you load a list by a JPQL query, because Hibernate loads the list first and then fills each eager association with separate selects. It also hides in JSON serialisation, in toString() and in mapper libraries that walk the whole object graph. You find it by counting statements per request, not by reading the code.

Likely follow-ups
  • Why is a round trip costly even if each query is fast? Network latency, pool connection time and parsing add up. 10,000 queries of 1 ms is 10 seconds.
How do you fix N+1? List your options and pick one. Intermediate

What the interviewer is testing: a toolbox, and judgement about which fix suits which case.

First make the associations lazy. Then choose per use case. (1) join fetch in JPQL: loads parent and association in one query. Best for ToOne and for one collection when you do not paginate. (2) Entity graph (@EntityGraph in Spring Data): the same effect, declared outside the query text, so you can reuse one query with different graphs. (3) Batch fetching: @BatchSize(size = 50) or the global hibernate.default_batch_fetch_size. Lazy loads are grouped, so 100 lazy customers load in 2 queries using where id in (?, ?, ...). It is a very cheap, safe default and works with pagination. (4) Subselect fetch (@Fetch(SUBSELECT)) loads a collection for all parents of the original query at once. (5) Projection or DTO that selects only the columns you need, with joins in the query, so no entities and no lazy loading at all. For read endpoints I prefer projections; for write flows I prefer fetch joins on the aggregate; and I set a global batch size as a safety net.

@Query("select o from Order o join fetch o.customer where o.status = :s")
List<Order> findWithCustomer(@Param("s") Status s);

@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findByStatus(Status s);
Likely follow-ups
  • Is batch fetching a fix or a bandage? It reduces N+1 to about N/50+1, which is usually enough, but a join or a projection gives the minimum.
What is the difference between join fetch and an entity graph? Intermediate

What the interviewer is testing: precise understanding of a feature you probably use.

Both tell Hibernate to load an association in the same SQL as the parent. A join fetch is written inside the JPQL string, so the query and the fetch plan are tied together. An entity graph is defined separately, with @NamedEntityGraph on the entity or @EntityGraph on a repository method, or built in code, and applied to a query or to find as a hint. That lets one query be used with different graphs, and it works with derived Spring Data methods, where you cannot write a join fetch. A graph has two modes. fetchgraph: attributes in the graph are eager, everything else is treated as lazy. loadgraph: attributes in the graph are eager, the rest keep their mapped fetch type. Spring Data's default is fetchgraph semantics (EntityGraphType.FETCH). A join fetch can also have conditions in the query, and an entity graph cannot filter the fetched rows.

@NamedEntityGraph(name = "Order.full",
  attributeNodes = { @NamedAttributeNode("customer"),
                     @NamedAttributeNode(value = "items", subgraph = "item") },
  subgraphs = @NamedSubgraph(name = "item", attributeNodes = @NamedAttributeNode("product")))
Likely follow-ups
  • Do graphs fix pagination problems with collections? No. A collection in the graph has the same in-memory pagination problem as a join fetch.
How does @BatchSize work, and when is it better than join fetch? Intermediate

What the interviewer is testing: knowing a fix that works with pagination and with several collections.

When Hibernate has to load a lazy association for one entity and it knows that more entities of the same type are waiting uninitialised in the persistence context, it fetches them together: where id in (?, ?, ..., ?) for ToOne proxies, or where order_id in (...) for collections. The group size is the batch size. You set it per class or per collection with @BatchSize(size = 25), or globally with hibernate.default_batch_fetch_size=25. It is better than join fetch in three cases: (1) when you paginate a parent list, because the main query stays row-per-parent; (2) when several collections must be loaded, since no cartesian product appears; (3) when you cannot know which associations a caller will use. The cost is a few small extra queries instead of one big one. Hibernate 6 also pads the IN list to powers of two with in_clause_parameter_padding, so the number of distinct statement shapes stays small and plan caches stay effective.

Likely follow-ups
  • Does batch size fix N+1 completely? It cuts N to N/size. It is a mitigation. For a hot endpoint tune the query itself.
What is MultipleBagFetchException and how do you handle it? Senior

What the interviewer is testing: what really happens when you join two collections.

A "bag" is a List without an index column. If you join fetch two bags in the same query, Hibernate throws MultipleBagFetchException: cannot simultaneously fetch multiple bags. The reason is that the join returns a cartesian product. An order with 10 items and 5 payments produces 50 rows, and from those rows Hibernate cannot tell which duplicate belongs where for a bag. The tempting wrong fix is to change List to Set. It removes the exception, but the database still sends the whole cartesian product, so 50 rows (or 5 million, for bigger numbers) cross the wire each time. The correct fix is to load one collection per query. First, select o from Order o join fetch o.items where .... Second, another query in the same transaction, select o from Order o join fetch o.payments where o in :orders, which fills the payments of the same managed objects. Or use batch fetching for the second collection. Or use a DTO query.

Likely follow-ups
  • Why does the second query fill the same entities? The persistence context gives back the same instances, and Hibernate initialises their payments collections.
Common mistakes: switching to Set just to silence the error, or using FetchType.EAGER on both lists.
Why is pagination with a collection join fetch dangerous? Senior

What the interviewer is testing: a real production memory problem with a log warning that people ignore.

A join with a collection returns one row per child, not per parent. If you ask for page one of 20 orders, the database cannot just apply LIMIT 20 to the joined rows, because that would cut an order's items in half. So Hibernate does something else. It logs HHH000104: firstResult/maxResults specified with collection fetch; applying in memory. It loads all matching orders with all their items, from the database into the JVM, and then slices out the 20 in Java. On a table of a million orders that is an out-of-memory incident hiding behind a small page size. Fixes: (1) a two-step query: first select o.id from Order o where ... order by ... with the page limit, then select o from Order o join fetch o.items where o.id in :ids and sort in Java by the first list; (2) paginate the parents without fetching, and set @BatchSize so the collections load in a few grouped queries; (3) use a DTO query or a window function in native SQL. Joining ToOne associations with pagination is fine, because it does not multiply rows.

Likely follow-ups
  • Does Hibernate 6 fix it? No. Hibernate 6 still warns and applies the limit in memory for collection fetches.
Why do I get duplicate parents with join fetch, and what does distinct do? Intermediate

What the interviewer is testing: the result-set shape behind fetch joins, and the 5 versus 6 difference.

A join fetch on a collection returns one SQL row per child, with the parent columns repeated. In Hibernate 5, the list returned from JPQL then contained the same parent several times: an order with 3 items showed up three times. You added select distinct o from Order o join fetch o.items so that Hibernate removed duplicate parents in memory. In Hibernate 5 that distinct was also sent to the database as SQL DISTINCT, which costs a sort; the hint hibernate.query.passDistinctThrough=false stops that. In Hibernate 6 the de-duplication of entity results happens automatically, so you do not need distinct for this reason any more. Keep it only if you really want SQL distinct. Still remember: the SQL result is still large (rows times children), so a big collection fetch is expensive even if the Java list is clean.

Likely follow-ups
  • Does distinct help with MultipleBagFetchException? No.
When should you use a projection or DTO instead of loading entities? Intermediate

What the interviewer is testing: knowing that entities are for writing, DTOs for reading.

When a request only needs a few columns, loading full entities wastes memory, creates snapshots for dirty checking, and risks lazy loading. A projection selects just the columns and returns a lightweight object. In JPQL you use a constructor expression: select new com.app.OrderRow(o.id, o.total, c.name) from Order o join o.customer c. You can also select a Tuple, or in Spring Data return an interface (closed projection) or a record. DTO queries are not managed, so there is no dirty checking, no L1 cache entry and no lazy surprises. For read-heavy list pages, search and reports, they are usually the fastest and the most predictable choice. For a write flow (load, change, save) use entities. A good team rule: controllers never return entities, they return DTOs that are built from a projection or mapped inside the transaction.

public record OrderRow(Long id, BigDecimal total, String customerName) {}

@Query("select new com.app.OrderRow(o.id, o.total, c.name) " +
       "from Order o join o.customer c where o.status = :s")
List<OrderRow> rows(@Param("s") Status s);
Likely follow-ups
  • Constructor expression versus Tuple? The constructor is type-safe but needs a matching constructor; a Tuple is flexible for dynamic queries.
How do you detect N+1 and other query problems before production? Intermediate

What the interviewer is testing: whether you have a process, not only knowledge.

Turn on SQL logging in development and count what one request does. Better, make it automatic: in integration tests, wrap the DataSource with a statement counter (datasource-proxy or Hibernate Statistics) and assert "this endpoint runs at most 3 statements", so a new lazy access fails the build. Hibernate's statistics (hibernate.generate_statistics=true) report query counts, entity loads and cache hits per session. In production, watch APM traces: a request with 400 near-identical SELECT spans is N+1. Use a realistic data size in test, because with two rows nothing looks wrong. The Hibernate log also shows the warning HHH000104 for pagination with fetch. Tools like the Hypersistence Optimizer (commercial) find mapping smells. Finally, read the slow-query log of the database, to see which statements take time and which are cheap but very frequent.

Likely follow-ups
  • Why does it not show in unit tests? Mocks never run SQL. You need a real database, usually Testcontainers.
Can you make a basic column lazy, like a big text or image column? Senior

What the interviewer is testing: the real behaviour of @Basic(fetch = LAZY).

Normally no. @Basic(fetch = LAZY) on a String or byte[] is ignored unless bytecode enhancement with lazy loading is enabled in the build (the Hibernate Maven or Gradle plugin). Without it, every load of the entity also reads the huge column. Options: (1) enable enhancement; (2) move the big column to a separate entity with a one-to-one on the shared primary key, and load it only when needed; (3) use projections that do not include it; (4) for large binary content, store it in object storage (S3 or a file store) and keep only a URL in the row. Option 4 is what I choose for anything over a few hundred KB: databases and connection pools are poor places for big blobs. If you do use @Lob, remember that on PostgreSQL @Lob maps to large objects requiring a transaction, which has surprised many people.

5. Transactions, propagation and lazy loading errors

How does @Transactional work inside Spring? Intermediate

What the interviewer is testing: proxies and the reasons @Transactional "does not work".

Spring wraps your bean in a proxy (a generated subclass or a JDK interface proxy). When another bean calls orderService.pay(), the call goes to the proxy first. The proxy asks the PlatformTransactionManager (for JPA, JpaTransactionManager) to begin a transaction, which opens an EntityManager, binds it to the current thread, and takes a connection from the pool. Then it calls your real method. On a normal return it commits, which flushes the persistence context first. On a runtime exception it rolls back. Then the EntityManager is closed and the connection returns to the pool. Everything between begin and end shares one connection and one persistence context, bound to the thread. That is why a transaction does not flow into another thread, and why @Async or a parallel stream loses it.

Likely follow-ups
  • Which proxy type? Spring Boot uses CGLIB class proxies by default (proxyTargetClass=true).
  • Where should @Transactional go? On service methods that represent a use case, not on controllers or repositories.
Why might @Transactional not work? Give the usual causes. Intermediate

What the interviewer is testing: debugging skills on the most common Spring bug.

The common reasons: (1) Self-invocation: this.save() inside the same class skips the proxy. Move the method to another bean or inject self. (2) The method is private, final or static, so the proxy cannot intercept it. Public methods of a proxied class are the safe choice. (3) The class is not a Spring bean, you created it with new. (4) Checked exceptions do not roll back by default. Only RuntimeException and Error do. Use rollbackFor = Exception.class when you need it. (5) Swallowed exceptions: a try-catch inside the method hides the error from the proxy, so it commits. (6) Wrong import: javax.transaction.Transactional or jakarta versus Spring's own annotation. Both work, but the rollback rules differ slightly. (7) The call happens on another thread. (8) A rollback-only inner call: an inner REQUIRED method threw and marked the shared transaction rollback-only, and the outer method caught the exception and tried to commit, which gives UnexpectedRollbackException.

Likely follow-ups
  • How to check if a transaction is active? TransactionSynchronizationManager.isActualTransactionActive(), or enable logging.level.org.springframework.transaction.interceptor=TRACE.
Explain transaction propagation: REQUIRED, REQUIRES_NEW, NESTED and the rest. Intermediate

What the interviewer is testing: whether you know what happens when one transactional method calls another.

Propagation says what to do if a transaction already exists when the method is called. REQUIRED (default): join the existing one, or start one if none. One commit, one rollback for all. REQUIRES_NEW: suspend the current transaction and start a separate one with its own connection. It commits or rolls back on its own; use it for audit logs or outbox rows that must survive an outer rollback. Beware: it needs a second connection at the same time, so under pool pressure it can deadlock the pool. NESTED: runs inside the outer transaction using a savepoint, so only the inner part can roll back. It works with JDBC-based transaction managers, and with JPA only on drivers that support savepoints; the commit still happens only with the outer one. SUPPORTS: use one if present, else run without. NOT_SUPPORTED: suspend and run without a transaction. MANDATORY: must already be in one, else throw. NEVER: must not be in one.

Likely follow-ups
  • REQUIRES_NEW inside a loop of 1,000 items? One commit and one connection acquisition each, which is slow. Only use it for the part that must be independent.
What are the isolation levels, and which anomalies does each prevent? Intermediate

What the interviewer is testing: database-level concurrency basics every backend engineer needs.

Isolation says how much one transaction sees of another's work. READ UNCOMMITTED: can see uncommitted data (dirty reads); almost never used. READ COMMITTED: sees only committed data, but the same query can return different rows later in the same transaction (non-repeatable read, phantom rows). It is the default in PostgreSQL, Oracle and SQL Server. REPEATABLE READ: rows you have read do not change; this is the default in MySQL InnoDB. In PostgreSQL it is snapshot isolation, so phantoms are also hidden, but write skew is still possible. SERIALIZABLE: behaves as if transactions ran one after another; safe but you must retry on serialisation failures. The default @Transactional isolation is DEFAULT, meaning "whatever the database uses". Isolation does not stop the lost update on its own at READ COMMITTED, which is why we add versioning or locks. Raise isolation only for a specific need, and handle the retry.

Likely follow-ups
  • Does Hibernate's first-level cache affect repeatable reads? Yes: reading a row twice in one context returns the cached instance, which looks like repeatable read at the Java level even under READ COMMITTED.
What are the rollback rules, and what is UnexpectedRollbackException? Intermediate

What the interviewer is testing: exception semantics inside transactions.

By default Spring rolls back on unchecked exceptions (RuntimeException, Error) and commits on checked exceptions, copying the old EJB rule. You can change that with rollbackFor and noRollbackFor. Another important detail: in a JPA transaction, when a persistence exception is thrown (such as a constraint violation or an optimistic lock failure), the JPA spec says the transaction is marked for rollback and the persistence context state is no longer reliable. If an outer method calls an inner REQUIRED method that fails, the inner proxy marks the shared transaction rollback-only. If the outer method catches the exception and carries on, at commit Spring throws UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only. The honest fix is either to not catch it, or to run the risky part in REQUIRES_NEW so its failure is isolated, or validate before the call.

Likely follow-ups
  • Can I catch a unique constraint violation and continue? Not in the same persistence context safely. Start a new transaction or check existence first.
What is LazyInitializationException and how do you fix it properly? Basic

What the interviewer is testing: an everyday error; the interviewer also wants to hear which fixes are bad.

It means "could not initialize proxy - no Session". You touched a lazy association (a proxy or a collection) after the persistence context was closed. The usual flow: a service method with @Transactional loads an order and returns the entity; the transaction ends and the session closes; then a controller or the JSON serialiser calls order.getItems(), and Hibernate cannot run the SELECT. Good fixes: (1) fetch what the use case needs inside the service with a join fetch or an entity graph; (2) map entities to DTOs inside the transaction and return DTOs only; (3) use a projection query; (4) Hibernate.initialize(order.getItems()) inside the transaction for a small, rare case. Bad fixes: making everything EAGER, which creates N+1 and loads the world; hibernate.enable_lazy_load_no_trans=true, which opens a new connection for every lazy access (an anti-pattern); and relying on Open Session In View.

Likely follow-ups
  • What if I only need the id of a lazy ToOne? order.getCustomer().getId() normally does not trigger loading, because the proxy already knows its id. Treat this as typical behaviour and test it with your access type.
Common mistakes: changing the mapping to EAGER globally just to stop the exception.
What is Open Session In View (OSIV), and should you leave it on? Intermediate

What the interviewer is testing: a Spring Boot default with real trade-offs.

OSIV keeps one EntityManager open for the whole web request, from the filter or interceptor until the response is written, even after the service's transaction has finished. That is why lazy loading still works in the controller and during JSON rendering. Spring Boot turns it on by default (spring.jpa.open-in-view=true) and prints a warning at startup. The problems: queries can happen at any time in the view layer, so N+1 hides in serialisation; the database connection can be held or taken again for the whole request including slow rendering, which starves the pool under load; and business logic gets mixed with presentation, with no clear transaction around the lazy reads, so data may be read without the isolation you expect. My rule: switch it off (spring.jpa.open-in-view=false), have services return DTOs built inside the transaction, and fix the LazyInitializationException errors that appear by fetching correctly. It is a small migration that pays back quickly.

Likely follow-ups
  • What breaks when you disable it? Code that touches lazy data in controllers or serialisers. That is the point: you find the hidden queries.
Why should you not call remote services inside a transaction? Senior

What the interviewer is testing: connection pool and lock thinking, a common production failure.

A transaction holds a database connection, and often row locks, from the first statement to the commit. If you call a payment API, send an email or wait for Kafka inside the transaction, the connection is held for the full network time, maybe seconds. With a Hikari pool of 10 connections and 50 concurrent requests, requests queue for connections and then fail with "Connection is not available, request timed out". Locks taken earlier by updates also stay for that time, so other requests block. The better design: do the database work in a short transaction, commit, then call the remote service. If the two must stay consistent, use an outbox table (write the event in the same transaction, a separate publisher sends it after commit) or a saga with compensation. Keep the transaction as small as the data rule needs: read, decide, write, commit.

Likely follow-ups
  • How do you find it? Pool metrics (active versus pending), long transaction alerts in the database, and thread dumps with many threads waiting on HikariPool.getConnection.
JpaTransactionManager or JTA? And what about two databases? Senior

What the interviewer is testing: distributed transaction awareness.

JpaTransactionManager is a local, resource-level transaction manager. It manages the transaction of one EntityManagerFactory and its DataSource. It is what Spring Boot uses by default and is enough for almost all services. JTA (Java Transaction API with an XA transaction manager such as Atomikos or Narayana) coordinates a two-phase commit across several resources, for example two databases or a database plus a JMS broker. It is slower, more complex to run, and many cloud databases or drivers do not support XA well. With two databases, most teams avoid distributed transactions: they keep each service's data in its own database, use separate transaction managers explicitly (@Transactional("ordersTm")), and make cross-system consistency eventual through events and the outbox pattern. Pick JTA only when you really need atomic commit across resources and your platform supports it.

Likely follow-ups
  • What is "best effort one-phase commit"? Chain two local transactions and commit them in reverse order; if the second fails after the first commits you can get inconsistency, so design for it.

6. Concurrency and locking

What is a lost update, and how does optimistic locking prevent it? Intermediate

What the interviewer is testing: the most important concurrency feature in JPA.

A lost update happens when two users read the same row, both change it, and both write back; the second write silently overwrites the first. Example: two clerks open the same customer, one changes the phone, one changes the address, and the later save sets the old phone back. With optimistic locking you add a @Version column. Hibernate includes it in every UPDATE and DELETE: update customer set phone=?, version=2 where id=? and version=1. If another transaction already moved the version to 2, the update matches zero rows. Hibernate detects the zero count and throws OptimisticLockException (Spring translates it to ObjectOptimisticLockingFailureException; the Hibernate class is StaleObjectStateException). The second user then reloads and retries, or is told "someone else changed this". It is "optimistic" because it assumes conflicts are rare, takes no database lock while reading, and checks only at write time.

@Entity
public class Customer {
    @Id private Long id;
    @Version private long version;   // never set it yourself
    private String phone;
}
Likely follow-ups
  • What types can a version have? int, long, short and their wrappers, or Timestamp. A number is safer than a timestamp.
  • How do you retry? Catch the exception outside the transaction (so a fresh one starts), reload, reapply, with a limit on attempts. Spring Retry has @Retryable.
What details about @Version should a senior engineer know? Senior

What the interviewer is testing: the edge cases that appear in real APIs.

First, the version protects only what went through Hibernate. A JPQL bulk update or native SQL does not bump it unless you write update versioned in HQL or set it yourself. Second, in a REST API the version must travel with the user's view of the data: return it in the GET response (or as an ETag), and require it back in the PUT (or If-Match). If the server just loads the row fresh and applies the DTO, the check compares the new version with itself and always passes, so the protection is lost. When you do merge with a detached entity carrying the old version, Hibernate does compare and throws if it is stale. Third, a version increment happens only when the entity is dirty. To lock a parent when only a child changes (aggregate-wide consistency), use LockModeType.OPTIMISTIC_FORCE_INCREMENT. Fourth, collections owned by the entity (non-inverse) also bump the version when they change; @OptimisticLock(excluded = true) stops that for a field. Fifth, you do not set the field yourself, and a null version means the entity is new.

Likely follow-ups
  • Can you do optimistic locking without a version column? @OptimisticLocking(type = DIRTY) with @DynamicUpdate compares changed columns, a Hibernate feature that is more fragile.
Common mistakes: loading the row by id inside the update call and copying DTO fields into it, which throws away the version the client saw.
How does pessimistic locking work in JPA? Intermediate

What the interviewer is testing: when to take database row locks and how.

Pessimistic locking assumes conflicts are likely, and takes a lock in the database while reading. In JPA you pass a lock mode: PESSIMISTIC_WRITE issues SELECT ... FOR UPDATE, so other transactions that want to update or lock the same row wait. PESSIMISTIC_READ is a shared lock (FOR SHARE, or LOCK IN SHARE MODE in MySQL); several readers can hold it but writers wait. The lock lasts until the transaction ends. You set it in em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE), in a query with setLockMode, or on a Spring Data method with @Lock(LockModeType.PESSIMISTIC_WRITE). Always set a wait limit with the hint jakarta.persistence.lock.timeout (in ms; javax. in older versions), or you wait on the database's own timeout. Use it for short critical sections like "decrement stock" or "take the next job from a queue", and keep the transaction tiny.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
@Query("select a from Account a where a.id = :id")
Optional<Account> findForUpdate(@Param("id") Long id);
Likely follow-ups
  • How do you implement a job queue without workers clashing? FOR UPDATE SKIP LOCKED: in Hibernate set lock timeout -2 (or use @Lock with the skip-locked option); each worker takes different rows.
  • Does it work across microservice instances? Yes, because the lock is in the database, not in Java memory.
Optimistic or pessimistic: how do you choose? Senior

What the interviewer is testing: engineering judgement based on contention.

I look at three things: how likely two writers touch the same row, how costly a retry is, and how long the work takes. If conflicts are rare (profile edits, most CRUD screens), optimistic is cheaper: no locks held, nothing blocks, and a conflict only costs a retry or a message to the user. It also fits long "read, think, submit" user flows, since the user can take minutes and you cannot hold a row lock for that. If conflicts are frequent and a failed attempt is expensive or must never be visible (hot counters, inventory on a flash sale, a balance transfer, picking jobs from a queue), pessimistic is better, because the loser waits and then proceeds instead of failing and retrying in a storm. A third option for simple counters is an atomic SQL statement: update stock set qty = qty - 1 where id = ? and qty > 0, checking the affected-row count. It needs no lock mode and no read, and often beats both. Pessimistic locks bring the risk of deadlocks and pool exhaustion, so lock rows in a consistent order and keep transactions short.

Likely follow-ups
  • Can you use both? Yes. A version column as a safety net everywhere, and pessimistic locking only on the few hot paths.
What are the JPA lock modes, including OPTIMISTIC and FORCE_INCREMENT? Senior

What the interviewer is testing: the full list, and the aggregate use case.

NONE is the default. OPTIMISTIC (old name READ): at commit, Hibernate re-checks that the version of an entity you only read has not changed, which protects a decision that was based on that data. OPTIMISTIC_FORCE_INCREMENT (old WRITE): bumps the version at commit even if the entity was not modified, and is the way to say "this whole aggregate changed" when only a child changed. PESSIMISTIC_READ, PESSIMISTIC_WRITE, and PESSIMISTIC_FORCE_INCREMENT (lock the row and also bump the version). A typical use of OPTIMISTIC: you read a product price while saving an order line. If someone changes the price before you commit, you want to fail rather than save an order with a wrong price. You can also apply entityManager.lock(entity, mode) to an entity that is already loaded.

Likely follow-ups
  • Which lock mode for "two users add items to the same cart"? FORCE_INCREMENT on the cart root, so concurrent changes to different items still conflict.
How do database deadlocks happen with JPA, and how do you prevent them? Senior

What the interviewer is testing: reasoning about lock order, and about the hidden SQL order from flush.

A deadlock is a cycle: transaction A holds row 1 and waits for row 2, while B holds row 2 and waits for row 1. The database detects it, kills one transaction and gives you an error (CannotAcquireLockException, PessimisticLockException, or a deadlock message from the driver). With JPA it is common because Hibernate decides the order of statements at flush, and two code paths can update the same rows in different orders. Prevention: always touch rows in a consistent order (for example sort ids ascending before a bulk locking read); keep transactions short; lock the rows you will change early with PESSIMISTIC_WRITE in a fixed order; use hibernate.order_updates=true so batched updates follow a primary key order; avoid user interaction or remote calls in transactions; index the columns used in WHERE so fewer rows are locked (MySQL gap locks make it worse). Because a deadlock is not a bug you can fully remove, catch it at the service boundary and retry the whole transaction a few times with a small random delay.

Likely follow-ups
  • How do you diagnose? The database deadlock log (SHOW ENGINE INNODB STATUS in MySQL, the server log in PostgreSQL) shows both statements and the rows.

7. Caching

What is the difference between the first-level and second-level cache? Intermediate

What the interviewer is testing: scope and lifetime of each cache.

The first-level (L1) cache is the persistence context itself. It is always on, belongs to one session, lives for one transaction, and is never shared between users. The second-level (L2) cache belongs to the SessionFactory, so it is shared by all sessions of the application, and it survives across transactions. It is off by default and you opt in per entity and per collection. When Hibernate looks up an entity by id, it checks L1 first, then L2, and only then the database. L2 stores the entity's data as "dehydrated" arrays of values, not as live objects, so every read builds a fresh instance. The L2 cache needs a provider such as Ehcache, Infinispan or Hazelcast (through JCache), or Caffeine via JCache. It helps for read-mostly reference data (countries, product categories) that is read by id often. It does nothing for queries unless you also turn on the query cache.

Likely follow-ups
  • Is L2 safe in a cluster? Only with a provider that replicates or invalidates across nodes, or with short expiry. Otherwise nodes read stale data.
How do you enable and tune the second-level cache? Senior

What the interviewer is testing: real hands-on use and the concurrency strategies.

Steps: add a JCache provider (Ehcache 3, Infinispan, Hazelcast), set hibernate.cache.use_second_level_cache=true and the region factory (hibernate.cache.region.factory_class, for JCache jcache), then mark entities with @Cacheable (JPA) and Hibernate's @Cache(usage = ...). The JPA shared cache mode usually must be ENABLE_SELECTIVE so only annotated entities are cached. The strategy: READ_ONLY for data that never changes (fastest, error on update); NONSTRICT_READ_WRITE for rarely changed data, accepting a short stale window; READ_WRITE with soft locks to keep consistency for entities that change; TRANSACTIONAL for full JTA support, rarely used. Configure size and time-to-live per region, since an unbounded cache is a memory leak. Cache collections separately with @Cache on the collection field: only ids of elements are stored, so the elements must be cached too or you get one SELECT per element. Turn on statistics and measure hit ratio; if it is below about 80 percent for a region, remove the cache.

Likely follow-ups
  • Why not just cache with Redis in the service layer? Often better: you control keys, TTL and invalidation, and cache DTOs. L2 is invisible and tied to entity ids.
What is the query cache, and why is it rarely worth it? Senior

What the interviewer is testing: knowing when a feature is a trap.

The query cache (hibernate.cache.use_query_cache=true, plus setCacheable(true) on each query) stores the list of ids a query returned, keyed by the query text and its parameter values. Then Hibernate loads each entity by id, from the L2 cache if possible, and from the database if not. A hidden bug is that if the entities are not in L2, a cached query still produces N queries (one per id). The cache is invalidated by a timestamp for the tables: any insert, update or delete on a table in the query clears all cached results that touch that table. So on write-heavy tables the hit rate is close to zero, and you pay the cost of storing and invalidating. It pays off only for queries over read-mostly tables, with few distinct parameter combinations, such as "all active countries". For most cases an application-level cache of a DTO list is simpler and more predictable.

Likely follow-ups
  • What are "update timestamps" caches? A region holding the last-modified time per table; a query result is valid only if it is newer than that timestamp.
What can go wrong with Hibernate caching in production? Senior

What the interviewer is testing: awareness of staleness and invalidation holes.

The main risks: (1) Stale data from writes that bypass Hibernate. Native SQL updates, other applications, database triggers and batch jobs change rows while L2 still holds old values. Hibernate invalidates the regions of entities it knows about for HQL bulk statements, but a native query invalidates everything unless you declare which tables it touches. (2) Clustered nodes. A local-only cache on each node gives different answers per node. (3) Memory. Without size limits and expiry, the cache grows; a collection cache without an entity cache gives N+1. (4) Cached object mutability. L2 stores copies of the state, but if you cache a mutable entity that changes often, the invalidation cost beats the saving. (5) Multi-tenancy. Cache keys must include the tenant id; Hibernate does this for its multi-tenancy modes, but custom caches might not. (6) Hidden behaviour: nobody sees the cache in the SQL log, so debugging "why is old data shown" is slow. Rule: cache only reference data you control, set a TTL, and measure.

Likely follow-ups
  • How do you evict programmatically? sessionFactory.getCache().evictEntityData(Product.class, id) or evictAllRegions().

8. Queries: JPQL, Criteria and native SQL

What is JPQL, and how is it different from SQL and HQL? Basic

What the interviewer is testing: basics of the query language.

JPQL (Jakarta Persistence Query Language) is an object-oriented query language. You write it against entity classes and their fields, not against tables and columns: select o from Order o where o.customer.name = :name. The provider translates it into SQL for your database dialect, so the same query works on PostgreSQL and Oracle. HQL is Hibernate's own language. It is a superset of JPQL with extra features such as more functions, and in Hibernate 6 it supports things like limit, offset, set operations and window functions. SQL (native) is written against tables, and has all the power of your database, but is not portable and returns rows, not managed entities, unless you map them. Use JPQL for ordinary queries, and native SQL when you need database-specific features (window functions on older Hibernate, recursive CTEs, JSON operators, hints).

Likely follow-ups
  • Can a JPQL query return entities from native SQL? Yes, createNativeQuery(sql, Order.class) maps columns to the entity, which then becomes managed.
How do you pass parameters safely, and what is the injection risk? Basic

What the interviewer is testing: security basics in the data layer.

Always use bind parameters: named (:status) or positional (?1). The provider sends the SQL with placeholders and the values separately through JDBC, so the database never parses the value as SQL. If you build the query by joining strings ("... where name = '" + name + "'") then a user can send ' or '1'='1 and change the query. That is SQL injection, and JPQL is not immune, because it is translated to SQL. Parameters also help performance: the same statement text is reused, so the database and Hibernate can cache plans. What cannot be a parameter is an identifier, such as a sort column name or a table name. For those, validate against a whitelist of allowed names. Spring Data's Sort built from user input can also be abused, so map the user's sort key to a known property first.

em.createQuery("select o from Order o where o.status = :s", Order.class)
  .setParameter("s", Status.PAID)
  .getResultList();
getSingleResult, getResultList, getResultStream: what are the differences? Basic

What the interviewer is testing: exceptions and memory behaviour of the Query API.

getResultList() returns all rows as a list, in memory, and an empty list when nothing matches. getSingleResult() expects exactly one row: zero rows throws NoResultException, more than one throws NonUniqueResultException. Because both are runtime exceptions, many teams prefer a list plus a check, or Spring Data's Optional. getResultStream() (JPA 2.2) returns a Stream. In Hibernate it reads through a scrollable result, so rows can be processed as they come, but you must close it (use try-with-resources) and stay inside the transaction. For very large results also set a fetch size, because many JDBC drivers load the whole result into memory otherwise (PostgreSQL needs auto-commit off and a fetch size; MySQL needs a special setting). Use setMaxResults for "top N" or "first" queries, instead of loading all rows and taking the first one.

Likely follow-ups
  • The query returned one row but getSingleResult throws NonUnique? A join multiplied rows, a collection fetch without distinct in Hibernate 5, or data that violates your assumption.
What is the Criteria API, and when would you use it instead of JPQL? Intermediate

What the interviewer is testing: dynamic queries and type safety.

The Criteria API builds a query in Java objects instead of a string: CriteriaBuilder, CriteriaQuery, Root, and Predicate. Its value is dynamic queries: a search screen with ten optional filters, where you add a predicate only when the filter is set. With JPQL you would concatenate strings, which is error prone. Together with the generated static metamodel (Order_.status, produced by the hibernate-jpamodelgen annotation processor) the compiler checks property names, so a rename breaks the build instead of production. The downside is verbose, hard-to-read code. So: JPQL (or @Query) for fixed queries, Criteria or Spring Data Specification for dynamic filters, and sometimes QueryDSL or jOOQ for a fluent, type-safe alternative. Note that the old Hibernate Criteria API (session.createCriteria) was removed in Hibernate 6; it is not the same as JPA Criteria.

CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<Order> cq = cb.createQuery(Order.class);
Root<Order> o = cq.from(Order.class);
List<Predicate> ps = new ArrayList<>();
if (status != null) ps.add(cb.equal(o.get(Order_.status), status));
if (min != null)    ps.add(cb.ge(o.get(Order_.total), min));
cq.select(o).where(ps.toArray(new Predicate[0]));
List<Order> result = em.createQuery(cq).getResultList();
When do you use native queries, and what do they cost you? Intermediate

What the interviewer is testing: pragmatism and awareness of side effects with the persistence context.

I use native SQL for things JPQL cannot express or does poorly: complex reporting with window functions, recursive CTEs, database-specific JSON or full-text operators, INSERT ... SELECT, upserts (ON CONFLICT), and very performance-critical statements. It can return entities (createNativeQuery(sql, Order.class)), a DTO via @SqlResultSetMapping or constructor mapping, or a plain Object[] or Tuple. The costs: it ties you to one database, it is not checked at compile time (a typo shows up at runtime), and a native update does not update the persistence context or the second-level cache. With an entity manager, Hibernate normally flushes pending changes before a native query to be safe, but entities already loaded stay stale after a native update, so call clear() or refresh(). Tell Hibernate which tables the statement touches (query spaces) if you want fine-grained cache invalidation. Always bind parameters.

Likely follow-ups
  • Spring Data pagination with a native query? You must supply a countQuery yourself, and make sure the sort is written into the SQL.
Offset pagination or keyset pagination? What goes wrong with deep pages? Senior

What the interviewer is testing: performance thinking on list endpoints.

Offset pagination (limit 20 offset 100000) makes the database read and throw away 100,000 rows before it returns 20, so page 5,000 is slow, and the result shifts if rows are inserted while the user pages. Spring Data's Page also runs an extra count(*) query for every request, which can be as costly as the data query on a big table. Slice skips the count and only checks "is there a next page" by fetching size+1 rows. Keyset (seek) pagination remembers the last row's sort key: where (created_at, id) < (:lastCreated, :lastId) order by created_at desc, id desc limit 20. The database jumps in the index to that point, so every page costs the same, and results are stable. The cost: no jump to "page 37", and you need a deterministic unique sort (add the id as tiebreaker) and an index. Spring Data 3.1 and later has a ScrollPosition API for it. For infinite scroll feeds and exports, keyset; for small admin tables, offset is fine.

Likely follow-ups
  • How do you cut the count cost? Skip it (use Slice), cache it, approximate it, or cap the maximum page.
Hibernate 6 changed HQL. What should I watch for when upgrading? Senior

What the interviewer is testing: practical upgrade experience.

Hibernate 6 parses HQL into a semantic query model and checks it more strictly, so some sloppy queries that used to run now fail at startup or first use. Things I have seen or that are documented: implicit joins and some ambiguous aliases are validated harder; positional parameters in the old ? JDBC style are no longer supported, use ?1 or names; the default id generator names and sequence behaviour changed; select distinct no longer needed for fetch join de-duplication; some functions return different types (an int division or sum of integers may return a different Java type, so a cast fails); the legacy Criteria, some @Type usages and @TypeDef were replaced; date and time and timezone handling got new options (hibernate.timezone.default_storage); and @Where and @Filter changed. Also dialect classes were simplified, and hibernate.dialect is often best left unset so it is detected. The safe approach is to run the whole integration test suite on the new version and compare the SQL for hot queries.

9. Spring Data JPA

How do derived query methods work, and what are their limits? Basic

What the interviewer is testing: daily fluency with repositories.

Spring Data parses the method name at startup. findByLastNameAndAgeGreaterThanOrderByAgeDesc is split into a subject (find, exists, count, delete), the properties (LastName, Age), keywords (And, GreaterThan, In, Like, IsNull, Between), and ordering. Spring builds the JPQL for it, and a typo in a property name fails at application startup, which is good. Special parameters: Pageable, Sort, and Limit in newer versions; return types: entity, Optional, List, Stream, Page, Slice, a projection. Limits: names become unreadable past two or three conditions; joins and fetch plans cannot be expressed; there is no OR-heavy logic or subqueries. Then switch to @Query, a Specification, or a custom repository method.

List<Order> findTop10ByStatusOrderByCreatedAtDesc(Status s);
boolean existsByEmail(String email);
long countByCustomerId(Long id);
Page<Order> findByCustomerNameContainingIgnoreCase(String n, Pageable p);
Likely follow-ups
  • existsBy or count to check existence? existsBy; it can stop at the first row.
How do @Query and @Modifying work, and what is clearAutomatically for? Intermediate

What the interviewer is testing: bulk updates and persistence context staleness.

@Query lets you write JPQL (or native SQL with nativeQuery = true) on the method, with named parameters from @Param. For INSERT-less statements that change data (UPDATE or DELETE) you must add @Modifying, and the method needs a transaction (the calling service usually has one; otherwise add @Transactional). The return value is the number of rows affected. Such statements go straight to the database and do not touch the persistence context, so entities you already loaded keep their old values. @Modifying(clearAutomatically = true) clears the context after the statement, so later reads load fresh rows, and flushAutomatically = true flushes pending changes before the statement, so it does not run against old data. Without them, you can read stale entities in the same transaction.

@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("update Order o set o.status = :to where o.status = :from and o.createdAt < :cutoff")
int expire(@Param("from") Status from, @Param("to") Status to, @Param("cutoff") Instant cutoff);
Likely follow-ups
  • Does a bulk update fire @PreUpdate or bump @Version? No, unless you write update versioned in HQL.
What does repository.save() actually do? Intermediate

What the interviewer is testing: whether you know about the hidden SELECT and the isNew rule.

SimpleJpaRepository.save is transactional. It asks the entity "are you new?". By default, an entity is new when its id is null (for a primitive id, when it is 0), or, if there is a @Version wrapper field, when the version is null. If new, it calls em.persist. If not, it calls em.merge. The trap: when you assign the id yourself (for example a UUID you create, or a business key) the id is never null, so Spring treats the entity as not new and calls merge. Merge runs a SELECT first to see if the row exists, and then inserts, so each insert costs two statements. Fixes: add a @Version field (null at creation), or implement Persistable<ID> with an isNew() method (often backed by a transient flag set by @PostPersist and @PostLoad). Also, save returns the managed instance; with merge it is a different object than the one you passed, so always use the returned value.

Likely follow-ups
  • Is saveAll batched? It calls save in a loop inside one transaction; real JDBC batching depends on your Hibernate batch settings and id strategy.
What are Specifications, and how do you build a dynamic search with them? Intermediate

What the interviewer is testing: a clean approach for many optional filters.

A Specification<T> is a small reusable predicate, built on the Criteria API. A repository that extends JpaSpecificationExecutor<T> gets findAll(Specification, Pageable). You write one static method per filter, returning null or a conjunction when the input is empty, and then combine them with and and or. This keeps each rule testable and named, and avoids a method with 12 optional parameters or string-built JPQL. Beware of the same problems as any Criteria query: joins inside a specification can multiply rows (use distinct or a subquery), fetch joins in specifications break the count query used for paging, and sorting on joined fields needs care. For huge or very flexible search (full text, facets), a search engine such as Elasticsearch is better than ever more complex specifications.

static Specification<Order> hasStatus(Status s) {
    return (root, q, cb) -> s == null ? null : cb.equal(root.get("status"), s);
}
static Specification<Order> totalAtLeast(BigDecimal m) {
    return (root, q, cb) -> m == null ? null : cb.ge(root.get("total"), m);
}
repo.findAll(Specification.where(hasStatus(s)).and(totalAtLeast(m)), pageable);
How do projections work in Spring Data, and what is an open projection trap? Intermediate

What the interviewer is testing: knowing when a projection really reduces the SELECT.

Spring Data supports three kinds. An interface projection is an interface with getters: interface OrderView { Long getId(); BigDecimal getTotal(); }. If every getter maps to a property (a closed projection), Spring selects only those columns. A class-based projection (a DTO class or record) uses a constructor, and also selects only the needed columns. A dynamic projection lets the caller pass the type: <T> List<T> findByStatus(Status s, Class<T> type). The trap is the open projection: if any getter uses @Value("#{target.firstName + ' ' + target.lastName}"), Spring cannot know which columns are needed, so it loads the whole entity and evaluates the expression in memory. You lose the benefit and you may get lazy loads. Also, nested interface projections over collections may produce extra queries. Check the SQL log once for each projection.

How do you set up auditing (created and modified timestamps and users)? Intermediate

What the interviewer is testing: a common feature and its small details.

Add @EnableJpaAuditing on a configuration class. On a base class marked @MappedSuperclass with @EntityListeners(AuditingEntityListener.class), add fields annotated @CreatedDate, @LastModifiedDate, @CreatedBy and @LastModifiedBy. The dates are filled automatically on persist and on update. For the user fields you provide a bean of type AuditorAware<String> that reads the current user, usually from Spring Security's context. Remember: auditing runs through JPA callbacks, so bulk updates and native SQL do not update these fields. Make createdAt updatable = false. If you need the full history of changes (what the value was before, who changed it, restore a version), use Hibernate Envers, which creates an audit table per entity and a revision record per transaction. Or use database triggers or CDC (change data capture) when many applications write to the same tables.

@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class Auditable {
    @CreatedDate @Column(updatable = false) private Instant createdAt;
    @LastModifiedDate private Instant updatedAt;
    @CreatedBy @Column(updatable = false) private String createdBy;
}
Why is deleteBy or deleteAll slow, and what is a better way? Intermediate

What the interviewer is testing: hidden per-row work in convenient repository methods.

A derived deleteByStatus(...) first SELECTs all matching entities, then calls remove on each one, which means one DELETE statement per row, plus cascade and lifecycle callbacks. deleteAll() does the same for the entire table, and deleteAllInBatch() issues one delete from table statement. deleteAllById loads rows too. For 100,000 rows the first style is a long, memory-hungry job. When you only need rows gone and have no cascade logic, use a single statement: @Modifying @Query("delete from Event e where e.createdAt < :cutoff"). For huge tables, delete in chunks (for example 5,000 rows each in its own short transaction) so locks and undo logs stay small, or use table partitioning and drop whole partitions. Remember that bulk delete skips orphan removal and JPA cascades; the database ON DELETE CASCADE or manual deletes must clean the children.

Page, Slice and List: what is the difference in the SQL they run? Intermediate

What the interviewer is testing: the hidden count query.

A repository method returning Page<T> runs two statements: the data query with limit and offset, and a select count(...) to know the total number of pages. The count is derived from your query, and it can be expensive on big tables or when joins are involved. For a custom @Query you may provide a cheaper countQuery (without joins and order by). Slice<T> runs only the data query for size + 1 rows to find out if there is a next page, so it is cheaper, but gives no total. List<T> with a Pageable argument applies limit and offset without any count. Spring skips the count query automatically when the first page has fewer rows than the page size. A common design: use Slice for infinite scroll, Page only where a total is really shown.

How do you add custom logic to a Spring Data repository? Intermediate

What the interviewer is testing: the fragment mechanism.

Create an interface with your method (OrderRepositoryCustom), a class implementing it (the class name ends with Impl, or you use the fragment's own name plus Impl), and let your main repository interface extend both. Spring Data finds the implementation and merges it into the repository proxy. Inside the implementation you inject the EntityManager or JPAQueryFactory (QueryDSL) and write the code you want: Criteria, native SQL, batch inserts with flush and clear, or a call to a stored procedure. Fragments are the modern approach: many small interfaces, each with its own implementation, so you can compose them. Good uses: complex dynamic reports, bulk operations, and calling database functions.

public interface OrderRepository extends JpaRepository<Order, Long>, OrderRepositoryCustom { }
public interface OrderRepositoryCustom { List<OrderRow> search(SearchCriteria c); }
class OrderRepositoryCustomImpl implements OrderRepositoryCustom {
    @PersistenceContext private EntityManager em;
    public List<OrderRow> search(SearchCriteria c) { /* ... */ return List.of(); }
}

10. Performance, bulk work and large data

What is the problem with bulk updates in JPA? Intermediate

What the interviewer is testing: the gap between the database and the persistence context.

A JPQL or native update ... where ... runs directly in the database and changes many rows at once, which is very fast compared to loading entities one by one. But the persistence context is not told. Entities already loaded in the session still hold the old values, and a later read of them in the same transaction (by find or by a query that returns the same ids) returns the old, now wrong, in-memory objects. The version column is not incremented, lifecycle callbacks do not run, cascades are skipped, and with the second-level cache on, Hibernate invalidates the affected region for HQL, but not for native SQL unless you tell it. The safe pattern: flush before, run the bulk statement, then clear() (or refresh specific entities), or keep the bulk update at the very start of the transaction before loading anything. Also add version = version + 1 to the statement if other code relies on optimistic locking.

Likely follow-ups
  • When is looping with entities better? When you need callbacks, cascades, auditing or optimistic locking per row, and the volume is small.
How do you make Hibernate insert 100,000 rows quickly? Senior

What the interviewer is testing: JDBC batching, id strategy, and memory control together.

Four things must be right. (1) JDBC batching on: hibernate.jdbc.batch_size=50, so Hibernate groups statements into one JDBC batch. (2) Order the statements: hibernate.order_inserts=true (and order_updates), otherwise inserts for different entity types interleave and break the batches. (3) A batch-friendly id: SEQUENCE with a pooled allocation size. IDENTITY disables insert batching. (4) Control the persistence context: every 50 entities call flush() and clear(), or the context grows with 100,000 entities and dirty checking becomes slower each time. On top, for MySQL add rewriteBatchedStatements=true to the JDBC URL (otherwise the driver sends statements one by one), and for PostgreSQL reWriteBatchedInserts=true. Do it in chunked transactions so a failure at row 90,000 does not roll back everything, and disable second-level cache writes for the load. If it is still too slow, use a JdbcTemplate.batchUpdate, or the database's bulk loader (COPY, LOAD DATA), because JPA is not a bulk-loading tool.

spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
spring.jpa.properties.hibernate.batch_versioned_data=true
Likely follow-ups
  • How do you verify batching works? Turn on hibernate.generate_statistics and look at the "JDBC batches executed" count, or use a datasource proxy that logs batch sizes.
You must process 1 million rows. How do you avoid running out of memory? Senior

What the interviewer is testing: streaming, chunking and the persistence context memory trap.

The mistake is repo.findAll(), which loads every row into a list, and every entity also gets a snapshot in the persistence context, so memory use doubles. Options: (1) Chunked keyset reads: where id > :lastId order by id limit 1000 in a loop, one short transaction per chunk, with clear() after each. Simple, restartable, safe. (2) Streaming with a repository method returning Stream<T> (needs a transaction and close()), or Hibernate's scroll, plus a fetchSize hint (jakarta.persistence.query.fetchSize or @QueryHints), and a driver mode that really streams (PostgreSQL: auto-commit off and fetch size; MySQL: useCursorFetch or fetch size Integer.MIN_VALUE). (3) Read-only and projections: use readOnly queries or select only the columns you need into DTOs, so no snapshots are kept. (4) StatelessSession: no persistence context, no dirty checking, no cache. (5) Move heavy export work to SQL, a database job, or Spring Batch with chunk-oriented steps, which handles restart and skip. Always process in the database when you can: an insert ... select beats any loop in Java.

@QueryHints(@QueryHint(name = "org.hibernate.fetchSize", value = "1000"))
@Query("select e from Event e")
Stream<Event> streamAll();   // call inside @Transactional(readOnly=true), try-with-resources
Likely follow-ups
  • Why does a Stream still run out of memory? You are still holding the entities in the persistence context. Detach each one (em.detach) or clear every N items, and verify the driver streams.
What is a StatelessSession, and when would you use it? Senior

What the interviewer is testing: Hibernate-specific tools for batch jobs.

A StatelessSession is a Hibernate session without a persistence context. There is no first-level cache, no dirty checking, no automatic cascading, no lazy-loading proxies and no interceptors or entity callbacks (it runs very close to JDBC). Calls like insert, update and delete act immediately on the database. It is useful for bulk imports and for scrolling over large result sets where you do not want entities held in memory. The trade-off: you give up the conveniences. Associations are not loaded for you, you must manage versions and relationships by hand, and the same entity loaded twice gives two different objects. It is Hibernate-only (not in JPA). In Hibernate 6 and later there are also bulk "insert multiple" helpers on it. For many teams, JdbcTemplate batch updates or Spring Batch are simpler for this kind of job.

How do you see the SQL Hibernate runs, with parameter values? Basic

What the interviewer is testing: debugging habits.

The quick but weak way is spring.jpa.show-sql=true, which prints to standard output with ? instead of values and bypasses the logging framework. The better way is the logger: logging.level.org.hibernate.SQL=DEBUG prints the statements, and for the bound values, in Hibernate 6 use logging.level.org.hibernate.orm.jdbc.bind=TRACE (in Hibernate 5 it was org.hibernate.type.descriptor.sql.BasicBinder=TRACE). Add hibernate.format_sql=true for readability and hibernate.use_sql_comments=true to see the HQL that produced each statement. For a full picture with timings and batch information use a JDBC proxy: datasource-proxy or p6spy. To measure, enable hibernate.generate_statistics, which logs counts and the slow queries when you set hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS. Never leave full SQL and parameter logging on in production: it is slow and can leak personal data into logs.

logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE      # Hibernate 6
spring.jpa.properties.hibernate.format_sql=true
spring.jpa.properties.hibernate.generate_statistics=true
How does the connection pool relate to JPA performance? Intermediate

What the interviewer is testing: the link between transaction length, pool size and throughput.

Spring Boot uses HikariCP by default. A transaction borrows a connection and returns it at the end. With OSIV on it may hold or re-borrow connections longer. The number of connections that can do real work is small: more connections than the database can serve in parallel just add queueing and context switching. A common starting point is a pool of about 10 to 20 per application instance, calculated from the database cores, not from the number of web threads. If requests are many and transactions are slow, threads wait for a connection and you see Connection is not available, request timed out after 30000ms. Fix the cause: shorter transactions, no remote calls inside them, fewer queries per request, then maybe a larger pool. Watch the Hikari metrics: active, idle, pending and the connection acquire time. Remember total connections equals pool size times the number of instances, which must stay below the database limit.

Likely follow-ups
  • What happens with REQUIRES_NEW and a tiny pool? The thread holds one connection and waits for a second one, which may never come if all threads do the same: a pool deadlock.
A list endpoint is slow. How do you investigate from the JPA side? Intermediate

What the interviewer is testing: a structured process.

Measure first. (1) Count statements for the request with SQL logging or a proxy. Many near-identical queries means N+1. (2) For the main query, copy the SQL and run EXPLAIN (ANALYZE) in the database: look for sequential scans on big tables, missing indexes, sorting without an index, and a large count(*). (3) Check payload: do you load entire entities when the screen needs five columns? Switch to a projection. (4) Check pagination: offset on a deep page, a collection fetch with a limit (HHH000104 in the log), a Page doing an expensive count. (5) Check the JSON side: serialising a large graph, or lazy loading inside the serialiser. (6) Check transaction and pool metrics for waiting. (7) Only then think about caching. Fix the biggest item first, then measure again. I keep a before and after number so the change is proven.

11. Schema management, multi-tenancy and testing

What does spring.jpa.hibernate.ddl-auto do, and what should you use in production? Basic

What the interviewer is testing: a classic production-safety question.

It tells Hibernate whether to touch the schema at startup. none: do nothing. validate: check that tables and columns match the entities, and fail startup if not; it changes nothing. update: add missing tables and columns (it never drops or renames anything, never changes types safely, and cannot handle data migrations). create: drop and create at startup. create-drop: create at startup, drop at shutdown. Spring Boot's default is create-drop for embedded databases like H2 and none for others. In production use none or validate, and manage the schema with migration tools. update is risky: it is unreviewed, not repeatable across environments, can run at the same time on several instances, and gives no history. create in production would erase your data.

Likely follow-ups
  • Is it OK in tests? Yes for throwaway in-memory databases, but better to run the same migrations in tests as in production.
Flyway or Liquibase? How do versioned migrations work? Intermediate

What the interviewer is testing: migration discipline.

Both keep a history table in the database listing which migrations ran, with a checksum, and apply new ones in order at startup (or from a pipeline step). Flyway is simple: plain SQL files named like V12__add_order_index.sql, run once, in version order. Optional R__ files are repeatable. Changing an already-applied file fails the checksum check, so you add a new file instead. Liquibase uses changelogs in XML, YAML, JSON or SQL with changeSet entries identified by id and author. It can express changes in a database-neutral way, supports rollback definitions, contexts and labels. Flyway is easier for teams that think in SQL; Liquibase is stronger when you target several databases or want rollback metadata. Both integrate with Spring Boot: put the files in the classpath folder and set ddl-auto=validate. A good practice: migrations are reviewed with the code, never edited after release, and tested against a copy of production data size.

Likely follow-ups
  • Two app instances start together? Both tools take a lock on the history table, so only one runs the migration.
How do you change the schema without downtime while old and new code both run? Senior

What the interviewer is testing: expand and contract, the standard safe pattern.

During a rolling deploy, version N and N+1 of the application run against the same schema, so every migration must work for both. The pattern is expand, migrate, contract. Example: rename column name to full_name. Release 1 (expand): add the new nullable column, and the code writes both columns and reads the old one. Then a backfill job copies old data in small batches. Release 2: code reads the new column and still writes both. Release 3 (contract): stop writing the old column, and later drop it in a separate migration. Other rules: add new columns nullable or with a default; do not add NOT NULL until backfilled; create indexes concurrently (CREATE INDEX CONCURRENTLY in PostgreSQL) so the table is not locked; avoid long table rewrites during peak; and never drop or rename something the previous version still uses. JPA validate will fail startup if the new entity expects a column that is not there yet, so migrate first, deploy code second.

What are the multi-tenancy approaches in Hibernate? Senior

What the interviewer is testing: basics of tenant isolation in a data layer.

Multi-tenancy means one application serves many customers (tenants) with their data kept apart. Three approaches. Separate database per tenant: strongest isolation, easy backup and restore per customer, but costly with many tenants, and many connection pools. Separate schema per tenant: good isolation in one database, cheaper, but migrations must run for every schema. Shared schema with a discriminator column (tenant_id on every table): cheapest and scales to thousands of tenants, but one bug in a query can leak data, so you must enforce the filter centrally. Hibernate supports the first two through MultiTenantConnectionProvider (picks a database or schema) and CurrentTenantIdentifierResolver (supplies the tenant id, e.g. from the request token). For the discriminator style, Hibernate 6 adds @TenantId, which adds the column to every query and insert automatically; in Hibernate 5 you build it with @Filter and discipline, or use database row-level security (PostgreSQL RLS). Cache keys and native queries need extra care, since they might skip the tenant filter.

Likely follow-ups
  • How do you stop a developer from forgetting the tenant filter? Central enforcement (@TenantId, RLS), plus tests that query as tenant A and assert nothing from B appears.
How do you test the persistence layer? Intermediate

What the interviewer is testing: practical test strategy.

Use @DataJpaTest: it loads only JPA components, wraps each test in a transaction that rolls back, and by default swaps your database for an embedded one. I prefer to run tests against the real database engine with Testcontainers (@AutoConfigureTestDatabase(replace = NONE)), because H2 behaves differently in dialect, locking, JSON, sequences and case rules, so tests may pass while production fails. Important detail: because the test transaction rolls back and never commits, Hibernate may not even flush, so constraint violations and generated SQL do not run. Call entityManager.flush() and clear() before asserting, so you read fresh data and see real SQL behaviour. Also test the things that bite in production: statement counts for key endpoints, optimistic locking conflicts with two threads, and migrations running from scratch with ddl-auto=validate. Keep a few end-to-end tests with real commits for transaction-boundary behaviour.

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

The orders page was fast in test and now takes 12 seconds in production. APM shows 800 SQL calls. What happened? Senior

What the interviewer is testing: recognising N+1 from symptoms and fixing it without making things worse.

Situation: one request makes one query for the orders and then hundreds of tiny SELECTs for customers, items and products, because lazy associations are touched in a loop or in the JSON mapper. Test data had five rows, production has 200 per page.

Check first: open one slow trace and look at the span list: many identical statements that differ only in the id value is the signature. Turn on SQL logging in a staging copy and count statements per request. Find which association is touched (the SQL says which table).

Steps:

  1. Make the list a read use case with its own query: a DTO projection with the joins in the SQL, or a join fetch or an entity graph for the ToOne parts.
  2. For collections, do not join them into a paginated query. Use @BatchSize or default_batch_fetch_size=50, or a second query by parent ids.
  3. Set associations to LAZY if some are eager by default (@ManyToOne).
  4. Add a test asserting the statement count with a datasource proxy.

Prevent: a statement-count assertion in the integration tests of the main endpoints, a global batch fetch size as a safety net, open-in-view=false, and test data of realistic size.

Likely follow-ups
  • Why not just add a cache? It hides the first request's cost and adds invalidation problems. Fix the query shape first.
Two support agents edit the same customer, and one agent's change disappears. How do you find and fix it? Senior

What the interviewer is testing: lost update and where a version check really gets lost in a REST design.

Situation: agent A saves a new phone number, then agent B saves a new address, and the phone goes back to the old value, because B's form carried the old phone and the service wrote all fields.

Check first: is there a @Version on the entity? Does the update API accept the version from the client? Check the update code: if it does findById and then copies the DTO onto the entity, the version in the entity is the current one, not the one the user saw, so the check always passes.

Steps:

  1. Add a @Version column through a migration (default 0).
  2. Return the version in the GET response (or as an ETag), require it in the PUT (or If-Match), and compare it with the loaded entity's version before applying changes. Or call merge on a detached object carrying the old version.
  3. Translate ObjectOptimisticLockingFailureException into HTTP 409 Conflict with a message, so the client reloads and re-applies.
  4. For partial updates (PATCH) apply only the changed fields, so unrelated edits do not collide.

Prevent: a concurrent test with two threads and a latch that must produce exactly one conflict, plus a rule that every mutable aggregate root has a version.

Common mistakes: adding @Version and thinking the work is finished, while the service still overwrites the whole row from the latest data.
Production logs show "Deadlock found when trying to get lock" a few times per hour during order processing. What do you do? Senior

What the interviewer is testing: diagnosing lock order problems and designing a retry.

Situation: two order transactions each update the same two rows (for example stock for product A and product B), but in opposite orders. The database detects the cycle and kills one transaction.

Check first: the database deadlock report (InnoDB status or the PostgreSQL log) names the two statements and the rows. Find the code paths for both. Check whether the order of updates is driven by user input (the order of the items in the cart) or by Hibernate's flush order.

Steps:

  1. Make the lock order deterministic: sort the product ids ascending before touching stock, and lock them up front with PESSIMISTIC_WRITE in that order.
  2. Use hibernate.order_updates=true so batched updates follow primary key order.
  3. Shrink the transaction: no remote calls, no heavy reads after the first write.
  4. Check indexes on the WHERE columns, since a table scan locks more rows.
  5. Add a bounded retry (2 or 3 attempts, small random delay) around the whole transaction at the service boundary, because some deadlocks always remain. The operation must be idempotent.

Prevent: a documented rule "lock in id order", and a load test with concurrent orders on the same hot products.

The product list endpoint with filters and paging is slow and the database CPU is high. Walk me through it. Senior

What the interviewer is testing: a layered investigation from query shape to SQL plan.

Situation: a Spring Data endpoint using Page<Product> with a Specification and a few joins takes seconds on a table of 5 million rows.

Check first: the generated SQL (data query and count query). Then EXPLAIN ANALYZE on both.

Steps:

  1. Look at the count query: it often does the same joins and no index helps. Cut it with Slice, a simpler countQuery, a cached or approximate total, or a capped total.
  2. Look at the data query: add composite indexes that match the filter plus sort columns (status, created_at desc, id), and remove leading wildcards in LIKE '%x%' (use full text or a search engine).
  3. Look at the payload: return a DTO projection, not entities with lazy children.
  4. Check for N+1 in mapping, and for a collection join with paging (HHH000104).
  5. For deep pages switch to keyset pagination.
  6. Check the pool and any lock waits, in case time is spent waiting, not working.

Prevent: a performance test with production-size data, index review during code review, and a slow query alert.

After disabling Open Session In View, the API returns LazyInitializationException on several endpoints. How do you handle it? Intermediate

What the interviewer is testing: fixing the cause, not the symptom.

Situation: controllers returned entities and Jackson walked lazy associations after the transaction was gone. With OSIV off the session is closed, so every access fails.

Check first: the stack trace shows the entity and the property (failed to lazily initialize a collection of role: Order.items), and the serialiser or mapper that touched it.

Steps:

  1. For each endpoint decide exactly what the response needs.
  2. Build that data inside a @Transactional(readOnly = true) service method: a DTO projection, or a fetch join or entity graph followed by mapping to a DTO in the same method.
  3. Return DTOs from the controller, not entities. That also stops leaking internal fields and ends infinite JSON loops from two-way relationships.
  4. Do not "fix" it with EAGER mappings or enable_lazy_load_no_trans.
  5. Run the tests with SQL logging to confirm the statement count did not rise.

Prevent: an architecture rule (ArchUnit) that controllers must not depend on entity classes, and OSIV disabled by default in the shared service template.

After a bulk update the API still returns the old status for some records. Why? Senior

What the interviewer is testing: persistence context and cache staleness after a statement that bypasses them.

Situation: a method loads orders, then runs update Order set status = 'EXPIRED' where ..., then returns the same orders (or loads them again). The response shows old values. Another symptom: a different node shows old values for minutes.

Check first: is the read in the same transaction as the bulk update? Then the persistence context answered from memory. Is second-level or an application cache involved? Check the SQL log: the update ran, but there was no second SELECT, or the SELECT returned a row that Hibernate ignored because the id was already managed.

Steps:

  1. Use @Modifying(flushAutomatically = true, clearAutomatically = true), or call em.flush() before and em.clear() after the bulk statement.
  2. Or move the bulk statement before loading, or refresh the entities you need.
  3. Evict the entity cache regions (HQL does it, native SQL needs the table declared) and any service-level cache keys.
  4. If optimistic locking matters, add version = version + 1 to the statement.

Prevent: a team rule that bulk statements live in a dedicated repository method with the clear option, and a test that loads, bulk-updates, and reloads.

A nightly export job loads 1 million rows and the service dies with OutOfMemoryError. What do you change? Senior

What the interviewer is testing: streaming and persistence context memory.

Situation: the job calls findAll() or a query returning List<Entity>. Each row becomes an entity plus a snapshot copy in the persistence context, so 1 million rows can mean several GB.

Check first: the heap dump (most memory in entity classes and EntityEntry objects), and the query: is it one big SELECT in one transaction?

Steps:

  1. Read in chunks by key: where id > :last order by id limit 2000, each chunk in its own short transaction, and call clear() after each chunk.
  2. Select only the columns the export needs, as a DTO projection, so no snapshots are kept.
  3. If streaming, use Stream or scroll in a read-only transaction with a fetch size, make sure the driver streams, and detach as you go. Close the stream.
  4. Write the output as you read (to a file or object storage), do not collect a list.
  5. Consider Spring Batch (chunk steps, restart after failure) or let the database do the work with a native COPY or export.

Prevent: code review rule against findAll() on big tables, and a memory test with a larger data set.

Under load the service logs "Connection is not available, request timed out after 30000ms", though the database CPU is low. What is going on? Senior

What the interviewer is testing: connection pool starvation caused by long transactions.

Situation: all pool connections are checked out, and new requests wait. The database is idle because the connections are held by code that is waiting on something else.

Check first: Hikari metrics (active equals max, pending rising), a thread dump (many threads blocked in HikariPool.getConnection, and others stuck in an HTTP client or Kafka call while inside a transaction), and the database's session list for "idle in transaction" sessions.

Steps:

  1. Find the transaction that wraps a remote call and move the call outside it. Commit first, call after, or use an outbox table.
  2. Look for REQUIRES_NEW in a loop or under pool pressure: it needs a second connection while the first is held.
  3. Turn off OSIV so a connection is not held through JSON rendering.
  4. Set sane timeouts on remote calls, and Hikari leak-detection-threshold to find forgotten connections.
  5. Only after that consider a bigger pool, within the database limit multiplied by the instance count.

Prevent: alerts on pending connections and on "idle in transaction" age.

An import of 200,000 rows takes two hours with Spring Data saveAll. How do you speed it up? Senior

What the interviewer is testing: the four conditions of real batching.

Situation: every entity is inserted with a separate round trip, and the persistence context grows with every row, so each flush gets slower.

Check first: the id strategy (IDENTITY disables insert batching), the batch settings, and a statement counter. Look at whether save issues a SELECT for each row (a manually assigned id makes Spring call merge).

Steps:

  1. Switch to a SEQUENCE with matching allocation size (or accept a different tool if the database is MySQL with identity ids).
  2. Set hibernate.jdbc.batch_size=50, order_inserts=true, and the driver option (rewriteBatchedStatements=true for MySQL, reWriteBatchedInserts=true for PostgreSQL).
  3. Process in chunks of 50 to 500 with flush() and clear(), and commit per chunk.
  4. Make new entities really new: a @Version field or Persistable, to avoid the merge SELECT.
  5. If still too slow, use JdbcTemplate.batchUpdate or the database loader. A 200,000 row import should take minutes, not hours.

Prevent: a performance test for import jobs and a check of "JDBC batches executed" in statistics.

The log shows "HHH000104: firstResult/maxResults specified with collection fetch; applying in memory" and the memory spikes on one endpoint. Why, and what is the fix? Senior

What the interviewer is testing: the pagination with fetch join trap in a real incident.

Situation: a query does join fetch o.items and also sets Pageable or setMaxResults. The database returns all matching orders with all items, and Hibernate cuts the page in the JVM.

Check first: the SQL: no limit or fetch first, and a row count that looks like a full table. Check how big the table is (the larger it is, the larger the spike).

Steps:

  1. Split it in two. Query 1: select o.id from Order o where ... order by ... with the page limit. Query 2: select distinct o from Order o left join fetch o.items where o.id in :ids. Restore the order in Java.
  2. Or drop the fetch join, paginate only the parents, and set @BatchSize on the collection so it loads in a few grouped queries.
  3. Or return a DTO built by a query with aggregation, if the screen only needs counts or sums.
  4. Add a test that fails if the warning is logged.

Prevent: a rule "no collection fetch together with paging", enforced by a log pattern check in CI.

A transaction deletes a row and inserts a replacement with the same unique key, and fails with a duplicate key error even though the delete comes first in the code. Why? Senior

What the interviewer is testing: flush ordering.

Situation: code does repo.delete(old); repo.save(new Item(sameKey)); in one transaction. At commit, the unique index rejects the insert.

Check first: the SQL log order. You will see the INSERT before the DELETE, because Hibernate runs inserts, then updates, then deletes at flush.

Steps:

  1. Call repo.flush() (or em.flush()) right after the delete, so the DELETE reaches the database first.
  2. Better: avoid delete and insert. Update the existing row's fields, which expresses the intent and keeps the id and history.
  3. For a replace-all of a collection, with orphan removal and a unique constraint on the child, flush between the removal and the additions, or use a bulk delete before the inserts.

Prevent: unit tests with a real database for operations that replace rows with the same key.

A release with ddl-auto=update dropped nothing but left the database in a wrong state and one node failed on startup. What is your advice? Intermediate

What the interviewer is testing: the danger of automatic schema changes in production.

Situation: update added a new NOT NULL column with no default on a table with data, or two instances tried to alter the same table at once. Or a renamed field produced a new empty column while the old data stayed behind.

Check first: which statements Hibernate ran (the startup SQL log), the current schema versus the expected one, and which instances saw which state.

Steps:

  1. Repair the schema by hand with a reviewed SQL script, backfill data, and restart.
  2. Set ddl-auto=validate (or none) in production profiles.
  3. Introduce Flyway or Liquibase. Baseline the current schema so history starts at the real state.
  4. Follow expand and contract for later changes, so old and new code both work during the rollout.
  5. Run migrations as a separate pipeline step or an init job, before the application pods start.

Prevent: block the update value in production profiles through a config check, and test migrations on a copy of production data.

Users report old prices after an admin updated them, but only on some servers. What do you check? Senior

What the interviewer is testing: cache invalidation across nodes and bypassing writes.

Situation: prices are cached in the Hibernate second-level cache with a local-only provider on each node, or the prices are updated by a native SQL job. The node that handled the update has fresh data, others serve old data until expiry.

Check first: is use_second_level_cache on, which provider, is it clustered or local? Was the change made through Hibernate or through SQL or another service? What are the TTL and eviction settings of the region?

Steps:

  1. If the write came from SQL or a script, evict the region (sessionFactory.getCache().evictEntityData(...)) or restart nodes as a quick fix.
  2. Use a distributed provider (Infinispan, Hazelcast) or a short TTL, or drop L2 for this entity.
  3. Better: cache at the service level, with Redis or Caffeine, publish an invalidation event after commit, and keep price reads for checkout always from the database.
  4. For consistency-critical values (price at checkout), never trust a cache: read the committed row and use @Version.

Prevent: cache only reference data, document each cache's staleness budget, and add metrics for hit ratio and age.

A developer says "I put @Transactional, but half the changes were saved and half were not". How do you debug it? Intermediate

What the interviewer is testing: proxy behaviour and rollback rules.

Situation: method process() calls this.step1() and this.step2(), each marked @Transactional(REQUIRES_NEW). Also an exception is caught and logged inside.

Check first: turn on logging.level.org.springframework.transaction.interceptor=TRACE or org.springframework.orm.jpa=DEBUG to see where transactions start and end. Check whether the call crosses a Spring proxy, which exception type was thrown, and whether it was swallowed.

Steps:

  1. Self-invocation: the annotation on step1 is ignored because the call does not go through the proxy. Move it to another bean, or restructure.
  2. A checked exception does not roll back by default; add rollbackFor or throw an unchecked one.
  3. A swallowed exception means a normal commit. Rethrow after logging, or mark rollback with TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().
  4. Check that the method is public and the class is a Spring bean (not created with new).
  5. Write a test that triggers the failure and asserts that nothing was saved.

Prevent: keep the transaction on one clear service method per use case.

We catch an exception from an inner service call and continue, but the request ends with UnexpectedRollbackException. Explain and fix. Senior

What the interviewer is testing: shared transaction state under REQUIRED.

Situation: an outer @Transactional method calls auditService.record() (REQUIRED), which throws a runtime exception. The inner proxy marks the shared transaction rollback-only before the exception reaches the outer code. The outer method catches the exception and goes on, but at commit Spring sees the flag and throws.

Check first: the stack trace has "Transaction silently rolled back because it has been marked as rollback-only". Look for a try-catch around a call to another transactional bean.

Steps:

  1. Decide what you want. If the inner failure should not affect the main work, put the inner method on REQUIRES_NEW, so it fails in its own transaction.
  2. If it must be all or nothing, do not catch the exception; let it roll back everything and handle it at the top.
  3. If the failure can be predicted (duplicate, missing record), check first instead of using exceptions as control flow. A persistence exception also leaves the persistence context unreliable.

Prevent: clear propagation choices in code reviews, and tests of the failure path.

Inserts with client-generated UUIDs run a SELECT before each INSERT and the import is twice as slow as expected. Why? Senior

What the interviewer is testing: the isNew rule in Spring Data.

Situation: the entity gets its UUID in the constructor. repository.save() sees a non-null id and no version, decides it is not new, and calls merge. Merge cannot know the row is absent, so it SELECTs first, finds nothing, then INSERTs.

Check first: the SQL log shows select ... where id=? immediately before each insert.

Steps:

  1. Add a @Version field. It is null on a fresh object, so Spring treats the entity as new, and you also get optimistic locking.
  2. Or implement Persistable<UUID>: keep a transient isNew flag set to true in the constructor and cleared in @PostLoad and @PostPersist.
  3. Or call entityManager.persist yourself in a custom repository fragment.

Prevent: a base class for all entities with client-assigned ids that already includes the isNew logic.

A customer sees another customer's records in a shared-schema multi-tenant app. How do you investigate and prevent it? Senior

What the interviewer is testing: data isolation thinking, which matters a lot to security teams.

Situation: every table has a tenant_id, and repositories rely on developers adding the filter. One native query, or one new repository method, skipped it. Or a cache key lacked the tenant.

Check first: treat it as a security incident: stop the leak (disable the endpoint or the feature), preserve logs, find which tenant ids appeared in which queries, and find the query that returned them. Check native queries, specifications, caches (L2 and application), and background jobs that run without a tenant context.

Steps:

  1. Fix the query and notify the security and legal contacts according to your process.
  2. Move enforcement away from developer discipline: Hibernate 6 @TenantId, or an @Filter enabled for every session by an aspect, or PostgreSQL row-level security, which protects even raw SQL.
  3. Include the tenant id in every cache key and every thread-local context, and clear it at request end.
  4. Add automated tests: create data for tenants A and B, call every endpoint as A, and assert that no B data appears.

Prevent: central enforcement plus tests, and a review checklist that every native query includes the tenant condition.

You are asked to upgrade a service from Spring Boot 2.7 (Hibernate 5) to Spring Boot 3 (Hibernate 6). How do you plan the persistence part? Senior

What the interviewer is testing: practical migration planning.

Situation: the app has many entities, native queries and a production database that cannot change shape.

Check first: the list of libraries that use javax.persistence (Envers, QueryDSL, MapStruct, validators, Spring Data extensions), the Java version (17 needed), and the test coverage on repositories.

Steps:

  1. First upgrade to the latest Spring Boot 2.7 and fix all deprecations. Add integration tests with Testcontainers against the real database.
  2. Run an automated rename of javax.* to jakarta.* (OpenRewrite). Upgrade dependent libraries to their jakarta versions.
  3. Check the id generation: set the sequence names and allocation size explicitly, so inserts continue with the existing sequences and no duplicates appear.
  4. Compare SQL for hot queries before and after, and run the tests for the result types of aggregate functions, enum, date and time zone mapping, and the removed Criteria or @Type usage.
  5. Roll out to a canary instance with SQL and error monitoring.

Prevent: keep dependency upgrades small and regular, so the next jump is smaller.
