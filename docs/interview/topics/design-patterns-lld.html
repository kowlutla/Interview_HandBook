Mental model: the 7 ideas everything hangs on

One line: good design makes the next change cheap. Patterns are names for proven ways to keep parts independent, so a new requirement means adding code, not editing and breaking old code.
  1. Change is the real enemy. Requirements always grow. Ask "what will vary?" and hide that behind an interface.
  2. Depend on abstractions. Business code should not know which database, payment provider or algorithm is used. It talks to an interface, and details are plugged in from outside.
  3. Composition over inheritance. Inheritance is a fixed, compile-time, tight link. Holding another object and delegating is flexible and can change at runtime.
  4. High cohesion, low coupling. Things that change together live together. Things that change independently know little about each other.
  5. Patterns are vocabulary, not goals. Use one when the problem is real. Over-engineering is a bug.
  6. Keep it simple (KISS, YAGNI). Add a pattern when the second or third variation appears, not before.
  7. Testability is design feedback. If a class needs a real database or static calls to be tested, it is too coupled.

1. Principles: SOLID, composition, coupling, simplicity

What are the SOLID principles? One line for each. Basic

SOLID is five guidelines for classes that are easy to change. S: a class has one reason to change. O: add behaviour by adding code, not by editing old code. L: a subclass must work wherever its parent is expected. I: prefer small, focused interfaces. D: high-level code depends on abstractions, not on concrete classes.

  • S, Single Responsibility: an Invoice class should not also print PDFs and send emails.
  • O, Open/Closed: a new discount type is a new class, not another else if.
  • L, Liskov Substitution: if code works with Bird, it must still work with any subclass of it.
  • I, Interface Segregation: do not force a read-only client to implement save() and delete().
  • D, Dependency Inversion: the service owns an OrderRepository interface, the MySQL class implements it.

They are guidelines, not laws. Applied blindly they produce a forest of tiny classes, so I use them when a real change hurts.

Why these five exist. Software rarely fails because the first version was wrong. It fails because the tenth change is painful: you edit one class and three unrelated features break, or you cannot test a class without a database. SOLID (a mnemonic coined by Robert Martin) is a checklist of the habits that keep the tenth change as cheap as the first. Each letter attacks one specific kind of pain.

A tiny story that touches all five. You build checkout. At first OrderService prices, saves and emails (breaks S). Marketing adds a festival discount and you add another else if (breaks O). Someone adds a GiftCard subclass of Payment whose refund() throws (breaks L). The Payment interface has twelve methods and the new cash-on-delivery class implements six as no-ops (breaks I). And the service calls new StripeClient(), so no test can run offline (breaks D). Fixing them in that order gives you small classes, a strategy for discounts, a cleaner payment hierarchy, narrow interfaces and an injected gateway.

How to use this in an interview. Do not recite definitions only. Name the principle, then give the smell you would see in code and the one-line fix. Interviewers probe the last two letters hardest: L (the Square and Rectangle trap) and D (how it differs from dependency injection). Also be honest that these are guidelines: a 40-line script does not need an interface per class, and over-applying S and O creates a maze of tiny classes that nobody can follow.

Remember: S one reason to change, O extend do not edit, L subclass keeps the promise, I small interfaces, D depend on interfaces.

Explain the Single Responsibility Principle with a real violation and the fix. Basic

SRP says a class should have one reason to change, meaning one stakeholder or concern drives its changes. If a class handles business rules, database access and email, three different kinds of change all hit the same file. I fix it by splitting each concern into its own class and letting a thin coordinator call them.

// Violation: pricing rules, SQL and email in one class
class OrderService {
    void place(Order o) {
        o.setTotal(o.items().stream().mapToDouble(Item::price).sum() * 0.9); // pricing
        jdbc.update("insert into orders ...", o);                          // persistence
        mailer.send(o.customerEmail(), "Order placed");                    // notification
    }
}
// Fix: PricingService, OrderRepository, NotificationService.
// OrderService only coordinates them.

The test for a violation: "and" in the class description ("it calculates tax and saves orders"), or two unrelated edits in the same class in one sprint. The opposite mistake is splitting by method count. One responsibility is not one method.

What "responsibility" really means. It is not "does one thing" in the loose sense. It is "has one reason to change", and a reason to change usually maps to a person or team who asks for it. In the example above, the finance team changes discount rules, the DBA team changes the schema, and marketing changes the email text. With all three inside one class, three people edit the same file, merge conflicts grow, and a mistake in the email text can break pricing because they share fields and helper methods.

How to spot a violation, step by step.

  1. Write one sentence describing the class. If you need "and" or "also", you probably have two responsibilities.
  2. List who would ask for a change: business analyst, DBA, UX, security. More than one name means more than one reason.
  3. Look at imports: a class importing both a JDBC package and a mail package is touching two worlds.
  4. Look at the test: if testing a pricing rule needs a mocked mailer and a mocked database, the rule is trapped inside a class that does too much.

After the fix the flow reads naturally: OrderService.place() calls pricing.total(order), then repo.save(order), then notifier.orderPlaced(order). Each collaborator can be tested alone, replaced alone, and edited by its own owner. Pricing becomes a plain function of an order, so a test is three lines with no mocks.

Common over-correction. Do not create OrderPriceCalculatorFactoryImpl for every method. A class with five tightly related methods that all change for the same reason is perfectly SRP-compliant. A good smell test for "too split" is that to change one business rule you now have to open six files.

What an interviewer probes next: "Is a Spring @Service with ten methods a violation?" Not by count. If all ten serve one use case area (say order lifecycle) and change together, it is fine. If half deal with reporting, it should be split.

Remember: one reason to change means one concern. If the description needs "and", split it.

Explain the Open/Closed Principle. Show a violation and the fix. Basic

Open/Closed means code is open for extension but closed for modification: I add new behaviour by writing a new class, without editing code that already works and is tested. The usual tool is an interface with several implementations, which is the Strategy pattern. The classic violation is an if/else or switch on a type that grows with every feature.

// Violation: every new customer type edits this method
double discount(Customer c, double amt) {
    if (c.type() == REGULAR) return amt * 0.05;
    else if (c.type() == PREMIUM) return amt * 0.10;
    return 0;
}
// Fix: new type = new class, calculator never changes
interface DiscountPolicy { double apply(double amt); }
class PremiumDiscount implements DiscountPolicy { public double apply(double a) { return a * 0.10; } }

Why it matters: every edit to old code risks breaking it and forces retesting. The trade-off is indirection, so I do not abstract on the first requirement. I wait until the second or third variation shows up, then refactor to the interface.

The idea from scratch. "Closed for modification" means once a class works and is tested, you try not to edit it. "Open for extension" means you can still add new behaviour. These sound contradictory until you see the trick: put the part that varies behind an interface, and let new behaviour arrive as a new class that implements it. The existing class is untouched, yet the system can do something new.

Walk through the example. Suppose the business adds a GOLD customer with a 15 percent discount.

  1. Before: you open discount(), add a third else if, retest REGULAR and PREMIUM as well (because you touched their method), and hope the merge with a colleague's edit is clean.
  2. After: you add class GoldDiscount implements DiscountPolicy and register it. REGULAR and PREMIUM code is byte-for-byte unchanged, so its tests need no rerun beyond the normal suite. The only new test is for the new class.
// Wiring: the calculator never mentions concrete policies
class CheckoutService {
    private final Map<CustomerType, DiscountPolicy> policies;   // Spring injects this map
    double finalPrice(Customer c, double amt) {
        return amt - policies.get(c.type()).apply(amt);
    }
}

Honest caveat. Something still has to know the list of policies (here the map, or a registry). OCP does not remove all edits, it moves them to one boring place (configuration or registration) instead of the business logic. Also, you can only be closed against changes you predicted. You cannot design for every change, so the practical advice is: write the straightforward code first, and when the second variation appears, refactor to an interface. The third variation then costs one class.

Related tools: Strategy for algorithms, Decorator for stackable add-ons, and plug-in lookups like Java's ServiceLoader. In Java 17+ with sealed types you can go the other way and deliberately keep the set of variants closed so the compiler checks every switch is exhaustive. That is a conscious trade, not a violation: it suits cases where the variants truly are fixed.

Remember: new requirement should mean new class. A growing if/else on type is the smell.

Explain the Liskov Substitution Principle. What is the Square and Rectangle problem? Intermediate

LSP says that anywhere code uses a parent type, I must be able to pass any subclass and the code still behaves correctly. A subclass may not break the promises of the parent: it cannot demand more from callers, deliver less, or throw surprises. In the Square and Rectangle example, a Square that extends Rectangle breaks the promise that width and height change independently.

void grow(Rectangle r) {
    r.setWidth(5); r.setHeight(4);
    assert r.area() == 20;   // fails for Square: setHeight also changes width
}

Maths says a square is a rectangle, but in code the behaviour must match. Common real violations: an override that throws UnsupportedOperationException (ImmutableList.add where the parent type is List), an override that quietly does nothing, or a subclass that adds stricter preconditions. Fixes: do not inherit, use a common interface (Shape.area()), or use composition. A signal that LSP is broken is instanceof checks in client code.

What it is, plainly. Barbara Liskov's rule: if S is a subtype of T, then code written for T must keep working, with no surprises, when handed an S. The compiler only checks signatures. LSP is about behaviour: what callers expect from the method in terms of inputs it accepts, results it returns, and side effects.

The three contract rules, with a quick example each.

  • Preconditions cannot be strengthened. Parent withdraw(amount) accepts any positive amount. A subclass that suddenly requires "amount must be a multiple of 100" rejects calls the parent would accept.
  • Postconditions cannot be weakened. Parent save() guarantees the record is persisted. A ReadOnlyRepo.save() that silently does nothing breaks the promise.
  • Invariants must be preserved. A Rectangle promises width and height are independent. Square ties them together and breaks that promise.

Why Square and Rectangle fails, in a timeline. A client holds a Rectangle r that is secretly a Square. It calls r.setWidth(5), so the square sets both sides to 5. It then calls r.setHeight(4), so both sides become 4. It expects area 5 times 4 equals 20 and gets 16. The code was correct for every real Rectangle and wrong for the subtype.

How to fix such designs. Ask whether the hierarchy models behaviour or just real-world words. Options: (1) two unrelated classes sharing a Shape interface with area(); (2) make both immutable, so there are no setters to break (a Square that is a Rectangle with equal sides is then fine); (3) composition instead of inheritance.

Java examples worth citing. Collections.unmodifiableList(...).add() throws UnsupportedOperationException, which strictly violates LSP for List; the JDK accepts it by documenting the "optional operation" in the Collection contract. A classic textbook failure is Stack extends Vector, which exposes insertElementAt and breaks stack discipline (inheritance used for reuse, not for substitutability).

Practical test: if a caller needs if (x instanceof Special) to behave correctly, or a subclass method body is throw new UnsupportedOperationException(), suspect LSP. Contract tests that run the same test suite against every implementation of an interface catch violations early.

Remember: a subclass must keep the parent's promises. "Is-a" in the real world is not "is-a" in behaviour.

Explain the Interface Segregation Principle with an example. Basic

ISP says no client should be forced to depend on methods it does not use. Instead of one fat interface, I make several small, role-based ones. A fat Worker interface with work() and eat() forces a Robot class to implement a meaningless eat().

// Fat: forces every implementor to support everything
interface Repository<T> { T find(long id); void save(T t); void delete(long id); }

// Segregated: a read-only report depends only on what it needs
interface ReadRepository<T>  { T find(long id); }
interface WriteRepository<T> { void save(T t); void delete(long id); }

Why it matters: with a fat interface, a change in delete() recompiles and retests every client, and implementors are tempted to throw "not supported", which also breaks LSP. In Java, a class can implement many small interfaces, so splitting is cheap. Do not overdo it: one-method interfaces for everything adds noise.

The problem it solves. An interface is a promise a class must keep. If the interface is large, every implementor must keep promises it has no reason to make, and every client sees methods it should never call. Both directions create coupling to things you do not use.

Three concrete costs of a fat interface:

  1. Forced fake implementations. A CachedReportRepo only reads, but the fat Repository makes it write save() as throw new UnsupportedOperationException(). That is a landmine and an LSP violation.
  2. Needless recompilation and risk. Adding bulkDelete() to the fat interface forces every implementor and every mock to change, even a reporting module that will never delete.
  3. Harder testing. A fake for a 12-method interface is 12 methods long. A fake for ReadRepository is one.

Before and after, with a client. A ReportService needs to read orders only. Before: it takes Repository<Order> and could, by mistake, call delete. After: it takes ReadRepository<Order>, so the type system documents and enforces "this service never writes". The same JpaOrderRepository class can implement both small interfaces, so there is no duplication.

class JpaOrderRepository implements ReadRepository<Order>, WriteRepository<Order> { ... }
class ReportService { ReportService(ReadRepository<Order> reads) { ... } }   // cannot write

Where this shows in real Java. java.util.Collection versus RandomAccess (a marker), Comparable and Comparator being separate, and the many small functional interfaces in java.util.function. Spring Data splits CrudRepository, PagingAndSortingRepository and ListCrudRepository, and lets you declare a custom base interface with only the methods you want to expose.

Balance. The test is who calls the methods, not how many there are. An interface with ten methods that every client uses together (List) is fine. Split when different clients use different slices. Java 8 default methods let you add a method to an interface without breaking implementors, which softens the maintenance cost, but does not fix the design smell.

Remember: many small, role-based interfaces beat one fat one. If you write "not supported", the interface is too fat.

What is the Dependency Inversion Principle, and how is it different from dependency injection? Intermediate

DIP is a design rule: high-level business code and low-level details should both depend on an abstraction, and the abstraction is owned by the high-level side. Dependency injection (DI) is a technique for supplying the concrete object from outside, for example through the constructor. DIP says what to depend on, DI is how the object arrives.

"Inversion" refers to the arrows. Normally business code calls the database class directly, so it depends on it. With DIP, the service declares an OrderRepository interface, and the MySQL class implements it, so the source-code arrow points from the detail up to the abstraction.

In a test I pass a fake repository. In production, Spring injects the real one. You can do DI without DIP (injecting a concrete class), which gives you little benefit.

The two halves of the rule. (1) High-level modules (business rules) should not depend on low-level modules (database, HTTP client, file system). Both should depend on abstractions. (2) The abstraction belongs to the high-level side: it is shaped by what the business needs, not by what the database offers.

Why it matters, with a story. Without DIP, OrderService imports MySqlOrderDao. Moving to PostgreSQL, adding a cache layer or testing the service all require editing or faking a concrete class that drags a JDBC driver along. With DIP the service says "I need something that can save(Order) and findPending()", and that sentence is the interface. The database package then depends on the service's package to implement it. The compile-time arrow is flipped (inverted) compared with the runtime call direction, hence the name.

DIP versus DI versus IoC, in one table.

TermWhat it isLevel
DIPPrinciple: depend on abstractions, abstraction owned by the clientDesign rule
IoC (Inversion of Control)A framework or container calls your code and controls object creation, not your own mainGeneral idea
DI (Dependency Injection)Technique: dependencies are passed in (constructor, setter) by someone elseMechanism

Example that has DI but not DIP: OrderService(MySqlOrderRepo repo), injected by Spring. The service still depends on the concrete class and its package, so swapping it needs a code change. Example that has DIP but no container: a hand-written main that does new OrderService(new MySqlOrderRepo()). The service depends only on the interface, and wiring is manual. You get the benefit with no framework.

Where to put the interface. A frequent mistake is placing OrderRepository in the persistence package next to its implementation. Then the service still imports from the persistence package. In hexagonal or clean architecture, the interface lives in the domain package, the implementation in an infrastructure package that depends on the domain.

Pitfall: inventing an interface for every class "for DIP" produces one-implementation interfaces with no value. Apply it at real boundaries: persistence, external services, clock, messaging, anything slow or volatile.

Remember: DIP is depend on interfaces. DI is pass them in from outside. DIP is the why, DI is the how.

Composition vs inheritance: why do people say "favour composition"? Basic

Inheritance ties a subclass to its parent's implementation at compile time, so a change in the parent can break every child, and you cannot swap behaviour at runtime. Composition means holding another object and delegating to it, so I can swap parts, test them with fakes, and combine behaviours freely. I use inheritance only for a true is-a relationship with stable behaviour, and composition for everything else.

Example: a Duck with fly and quack behaviours. With inheritance you get RubberDuck overriding fly() to do nothing (an LSP smell), and a class explosion for every combination. With composition, Duck holds a FlyBehavior and a QuackBehavior that can be changed even at runtime.

Java also has single inheritance only, so burning your one parent slot on code reuse is costly. The classic warning is HashSet extended to count additions: addAll internally calls add, so the count doubles. That is the fragile base class problem.

Why inheritance is more dangerous than it looks. A subclass inherits every method, including ones the author of the parent never intended to be overridden, and relies on the parent's internal calls staying the same. If the parent changes how its methods call each other, the child may break even though nothing in the child changed. This is the fragile base class problem.

The HashSet counting example, step by step.

class CountingSet<E> extends HashSet<E> {
    int added = 0;
    @Override public boolean add(E e)  { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { added += c.size(); return super.addAll(c); }
}
new CountingSet<String>().addAll(List.of("a", "b", "c"));   // added == 6, not 3

The subclass counted three in addAll, then the parent's addAll called add three times (an internal implementation detail), and each call counted again. The fix with composition: hold a Set in a field and forward calls, counting only once (this is the "forwarding class" approach recommended in Effective Java).

Decision rule.

Use inheritance whenUse composition when
True is-a relationship that holds in behaviour (LSP safe)You want to reuse code or behaviour
Parent is designed and documented for extension (abstract template, framework base class)Behaviour must change at runtime or be mixed in combination
You control both classes and they change togetherParent is a third-party or JDK class you do not control

Practical forms of composition: hold a collaborator and delegate (Strategy, Decorator, State), pass behaviour as a lambda, or implement several small interfaces. Java 8 default methods give some multiple-inheritance-of-behaviour, but without state, so they are safer than class inheritance.

Pitfall: "composition over inheritance" does not mean "never inherit". Frameworks need it (a JPA entity, HttpServlet, test base classes). The advice is about the default choice when the only reason to inherit is to avoid typing delegation code. Also mark classes final or document them for extension (Effective Java: "design and document for inheritance or else prohibit it").

Remember: inheritance is "is-a" and fixed at compile time. Composition is "has-a" and swappable. Default to composition.

What are coupling and cohesion? What is good design aiming for? Basic

Coupling is how much one class knows about and depends on another. Cohesion is how closely the things inside one class belong together. Good design aims for low coupling and high cohesion: a change stays inside one class, and each class has one clear purpose.

High coupling looks like reaching deep into other objects (order.getCustomer().getAddress().getCity(), a Law of Demeter violation: talk only to your direct neighbours, so write order.shippingCity()), sharing mutable global state, or depending on concrete classes. Low cohesion looks like a Utils or Manager class with unrelated methods. The two are linked: splitting a low-cohesion class often reduces coupling too.

Practical tools to cut coupling: depend on interfaces, inject dependencies, pass small immutable values, and publish events instead of calling many services directly.

Coupling, in levels. Not all coupling is equally bad. From worst to best:

  1. Content coupling: one class reads or modifies another's internals (public mutable fields, reflection hacks).
  2. Common/global coupling: many classes share global mutable state (a static map, a singleton with setters).
  3. Stamp/data coupling: passing a whole big object when you need two fields, so the callee depends on its structure.
  4. Interface coupling: depending on a small, stable interface. This is the healthy kind and cannot be avoided entirely.

Why you care: ripple effect. If class A depends on B's internals, a change to B has to be checked in A, and in everything that depends on A. Low coupling shrinks that blast radius. In an interview a good illustration is: "if I rename a database column, how many files change?" In a loosely coupled design the answer is one mapping class. In a tightly coupled one it is the whole codebase.

Cohesion, in levels. The best form is functional cohesion: every member helps with one well-defined task (an EmailAddress value type that validates and normalises). Weaker: logical cohesion (a StringUtils with unrelated helpers) and coincidental cohesion (a Misc class). Signs of low cohesion: methods that use disjoint subsets of the fields (you could split the class along the lines of field usage), and class names ending in Manager, Helper, Util, Processor that hide a vague purpose.

Law of Demeter in one example. Instead of invoice.getCustomer().getAddress().getCountry().equals("IN"), ask the object that owns the knowledge: invoice.isDomestic(). The caller no longer depends on three classes' shapes. Do not apply it mechanically: a fluent builder or a stream pipeline chain is fine, since it is the same object type returned each time.

Trade-off: the cheapest way to reduce coupling is often adding an interface or an event, which adds indirection. Cut coupling at boundaries that change (vendors, modules, teams) and leave tightly related classes in one package.

Remember: low coupling between classes, high cohesion inside a class. A Utils class is a cohesion smell.

Explain DRY, KISS and YAGNI. When can following DRY hurt? Basic

DRY, Don't Repeat Yourself, means each piece of knowledge lives in one place. KISS means keep the solution as simple as it can be. YAGNI, "You Aren't Gonna Need It", means do not build features or abstractions for needs that do not exist yet. DRY hurts when I merge code that only looks alike but changes for different reasons.

DRY is about duplicated knowledge (a business rule, a constant), not duplicated text. If two teams' validation rules look the same today but belong to different business rules, one shared function couples them. Every change by team A then risks team B, and the shared code grows flags and if branches. A little duplication is cheaper than the wrong abstraction. A good rule is the "rule of three": copy once, abstract on the third time, when the real shape of the variation is visible.

YAGNI and KISS fight speculative generality: interfaces with one implementation "just in case", plug-in frameworks nobody asked for.

Three rules, three different failure modes they prevent.

RulePreventsExample of obeyingExample of overdoing
DRYSame rule copied in five places, fixed in only threeOne TaxCalculator used by cart and invoiceMerging two look-alike validators that serve different teams
KISSClever code nobody can debugA plain loop instead of a three-level generic frameworkRefusing to use a well-known pattern because it is "complex"
YAGNIFeatures and flexibility built for a future that never comesHard-code one payment provider until the second is realNo interface even at a database boundary that obviously needs a test seam

The "wrong abstraction" story. Two classes have similar loops, so you extract a shared helper process(items, flag1, flag2). A month later a third caller needs a slight difference, so you add a flag. Then a fourth. Soon the helper is an unreadable switchboard, and each caller uses only part of it. The cheapest fix is often to inline the helper back into each caller and let them diverge. As Sandi Metz put it, duplication is far cheaper than the wrong abstraction.

How to decide whether to extract.

  1. Are these the same business knowledge (one tax rule) or only the same shape (two loops)?
  2. Will they always change together? If a change for A should not affect B, keep them apart.
  3. Have I seen it three times? Two occurrences are not enough to know the real axis of variation.

Where DRY is genuinely strict: constants and rules with legal or financial meaning, schema definitions, configuration keys, and API contracts. A tax rate in four places is a bug waiting to happen. Generate code from one source (OpenAPI to clients) rather than hand-copying.

Relation to patterns: YAGNI is why you do not start with a Strategy for a single algorithm, and DRY is why you extract one when the second copy appears. They pull in opposite directions, and judgment about the real rate of change decides.

Remember: duplicate knowledge is bad, similar-looking code is not. The wrong abstraction costs more than duplication.

What is a design pattern, and what are the risks of using patterns? Basic

A design pattern is a named, proven solution to a problem that keeps recurring in object-oriented design, described by its intent, structure and trade-offs. The value is a shared vocabulary ("use a Decorator here") and not having to reinvent known solutions. The risk is over-engineering: forcing a pattern onto a simple problem makes code harder to read.

A pattern is not code to copy. It is a template you adapt, and the same class diagram can serve different intents (Strategy and State look alike). Common misuse: Singleton for everything (hidden global state), Factory for a class that is created in one place, or five patterns in a 50-line feature. Good use is driven by a pain: a growing if/else asks for Strategy, many constructor parameters ask for Builder, a need for cross-cutting behaviour asks for Decorator or Proxy. In modern Java, lambdas and records replace several patterns' boilerplate.

Where patterns came from. In 1994 four authors (the Gang of Four, GoF) catalogued 23 recurring solutions found in good object-oriented code, in the book Design Patterns. They did not invent them. They named them, so a team can say "wrap it in a Decorator" and everyone pictures the same structure. A pattern entry has a name, the problem and context, the solution structure, and the consequences (trade-offs).

The three families. Creational (how objects are made: Singleton, Factory, Builder), Structural (how objects are assembled: Adapter, Decorator, Facade, Proxy, Composite), Behavioral (how objects collaborate: Strategy, Observer, Command, State, Template Method, Chain of Responsibility).

How to learn each pattern so it sticks, in four questions:

  1. What painful situation makes me want it? (growing if/else, constructor with ten parameters)
  2. What are the two or three classes and who holds whom?
  3. Where have I already seen it? (Comparator, BufferedReader, @Transactional)
  4. When would it be wrong? (one variant only, performance-critical hot loop, simpler language feature exists)

Patterns versus language features. Some GoF patterns exist to patch weaknesses of 1990s languages. Java 8 lambdas make Strategy and Command a one-liner, Iterator is built into the for-each loop, records reduce Builder and Value Object boilerplate, and sealed types with pattern matching reduce the need for Visitor. Knowing this shows maturity: the pattern's idea remains, the ceremony shrinks.

Patterns versus principles versus architecture. Principles (SOLID) tell you what a good design looks like. Patterns are small reusable recipes at class level. Architectural patterns (layered, hexagonal, event-driven, CQRS) work at system level. Interviewers often start with one and drift into the next, so be ready to connect them: "Strategy is how I satisfy Open/Closed, and hexagonal is Dependency Inversion applied to the whole app."

Red flags in interviews: naming a pattern before describing the problem, using three patterns for a 20-line exercise, or claiming Singleton is "always fine". Say what pain the pattern removes and what it costs.

Remember: a pattern is a name for a solution to a real pain. No pain, no pattern.

2. Creational patterns

What is the Singleton pattern, and when is it a good or bad idea? Basic

Singleton guarantees one instance of a class per JVM (strictly, per class loader) and gives a global access point to it. It is fine for genuinely single, stateless or read-only things like a configuration holder or a metrics registry. It is a bad idea as a convenient global: hidden shared state makes tests order-dependent and code hard to change.

Problems: callers hide their dependency (Config.getInstance() inside a method), you cannot swap it for a fake in tests, mutable state is shared across threads, and it is different per class loader. The better answer in real code is to let a DI container (Spring) create one instance and inject it. You get one instance without the global static. Java's Runtime.getRuntime() is a real example.

What the pattern really consists of. Two things: (1) the class controls its own construction (private constructor), so only one instance can exist, and (2) it offers a well-known way to reach it (getInstance()). The intent is to guarantee a single instance. The risky half is the "global access point".

Where one instance is genuinely right. A resource that is physically unique or expensive to build and holds no per-request state: a thread pool, a connection pool, a metrics registry, a read-only configuration holder, a logger factory. JDK examples: Runtime.getRuntime(), Desktop.getDesktop().

Why it is called an anti-pattern so often. Walk through what goes wrong in a normal codebase:

  1. Hidden dependency. A method signature says process(Order o), but inside it calls Config.getInstance().taxRate(). You cannot see from the signature that it needs configuration, and you cannot change what it gets.
  2. Untestable. A test cannot replace the singleton with a fake, and state from one test leaks into the next (see the scenario on tests that pass alone and fail together).
  3. Hidden global mutable state. Any code can change it, so a bug in module A appears as a failure in module B.
  4. Concurrency. If it has mutable fields, every access needs synchronisation.
  5. Class loaders and clusters. "One per JVM" is really one per class loader (an app server can have several copies), and it is one per process, not one per cluster. Never rely on a singleton for a cluster-wide guarantee such as a global counter or lock; that needs a database or a coordination service.

The modern alternative, in code.

@Configuration class AppConfig {
    @Bean AppSettings settings() { return AppSettings.load(); }   // one instance per container
}
@Service class TaxService {
    private final AppSettings settings;                           // visible, replaceable
    TaxService(AppSettings s) { this.settings = s; }
}

You still get a single shared instance, but the class itself is an ordinary class (public constructor, no static access), so tests can create their own. In an interview, say "the single-instance idea is fine, the static global is the smell", and mention that Spring's default bean scope is exactly this idea (but singleton per container, not per class loader).

Remember: one instance is fine, a global static is the problem. Let the container own the single instance and inject it.

How do you write a thread-safe Singleton in Java? Compare the options, including double-checked locking and enum. Intermediate

My first choice is an enum singleton, or the initialization-on-demand holder idiom when I need a normal class. Both are lazy or safe by JVM class-loading guarantees, with no locking code. Double-checked locking also works, but only if the field is volatile, and it is easy to get wrong.

// 1. Enum: simplest, safe against reflection and serialization
enum Registry { INSTANCE; void register(String s) { ... } }

// 2. Holder idiom: lazy, thread-safe, no synchronized
class Config {
    private Config() {}
    private static class Holder { static final Config I = new Config(); }
    static Config get() { return Holder.I; }   // Holder loads on first call
}

// 3. Double-checked locking: volatile is mandatory
class Cache {
    private static volatile Cache inst;
    static Cache get() {
        if (inst == null) {                       // first check, no lock
            synchronized (Cache.class) {
                if (inst == null) inst = new Cache();   // second check
            }
        }
        return inst;
    }
}

Why volatile: new Cache() is allocate, construct, then assign. Without volatile, the JIT or CPU may reorder so another thread sees a non-null but half-built object. The class-loading guarantee used by options 1 and 2 is that a class initializer runs exactly once, under a lock held by the JVM. A plain private constructor can still be broken by reflection or by deserialization (add readResolve). Enums are immune to both. The enum cannot extend another class, and it is eager.

First, what can go wrong without protection. Naive lazy code is if (inst == null) inst = new Cache();. Two threads can both see null at the same moment and both create an instance, so you get two singletons, and one thread may keep using an object others have dropped. That is the race we must prevent.

Option-by-option, with when to choose which.

OptionLazy?Locks on each call?Reflection / serialization safe?When
Eager static fieldNoNoNo (needs readResolve)Cheap to build, always needed
synchronized getInstance()YesYes, every callNoRarely hot, simplest correct lazy

Why the holder idiom is lazy and safe. The nested Holder class is not loaded until get() touches Holder.I. When the JVM first initialises a class it holds an internal lock and runs the static initialiser exactly once; other threads wait, then see the finished value. The Java Memory Model guarantees that this initialisation happens-before any use, so no volatile is needed.

Why double-checked locking needs volatile, in a timeline. inst = new Cache() is really three steps: (a) allocate memory, (b) run the constructor to fill fields, (c) publish the reference into inst. The compiler or CPU may reorder (b) and (c). Thread 1 does (a), then (c), and is paused before (b). Thread 2 runs the first if (inst == null) check without a lock, sees a non-null reference and returns it, and uses an object whose fields are still default values. volatile forbids the reordering and gives the happens-before edge. This bug was real and is why pre-Java-5 double-checked locking was broken.

Breaking a singleton, and defences. Reflection can call the private constructor (guard by throwing if inst != null, or use an enum). Serialization creates a new object on read (add readResolve() returning the instance, or use an enum). Cloning can copy it (do not implement Cloneable). Different class loaders each get their own copy.

What to say: "In real services I would not write any of these. I would register a Spring bean, which is a singleton per container and thread-safe to create. I write one by hand only for a library or a plain-Java context."

Remember: enum or holder idiom first. Double-checked locking needs volatile. A lazy synchronized getter works but locks on every call.

Explain the Factory Method pattern and the "simple factory". When do you use them? Basic

A factory hides which concrete class gets created, so the caller asks for a thing by a key or by a method and receives an interface. A simple factory is one class with a method that picks the implementation, usually with a switch or a map. Factory Method proper is when a base class declares an abstract create() and subclasses decide the concrete product. I use a factory when creation logic is non-trivial or chosen at runtime.

interface Notifier { void send(String to, String msg); }

class NotifierFactory {                       // simple factory
    private final Map<String, Notifier> byChannel;   // Spring can inject this map
    NotifierFactory(Map<String, Notifier> m) { this.byChannel = m; }
    Notifier get(String channel) {
        Notifier n = byChannel.get(channel);
        if (n == null) throw new IllegalArgumentException("Unknown channel " + channel);
        return n;
    }
}

Why it helps: adding a channel touches the factory (or just registers a new bean), not every caller. JDK examples: List.of, Calendar.getInstance, Integer.valueOf. A plain new is better when the class is simple and has one variant.

The problem a factory solves. If code calls new SmsNotifier() in twenty places, every place knows the concrete class, its constructor arguments and its setup. Adding a push channel, or changing how SMS is built (credentials, a retry wrapper), means editing twenty places. A factory puts "which class, and how to build it" in one place and hands out an interface.

Three related things that get mixed up.

Why static factory methods are often better than constructors (Effective Java, Item 1): they have names (Money.ofPaise(500) reads better than new Money(500)), they may return a cached instance or a subtype (List.of() returns a compact immutable list type that you never see), and they do not have to create a new object each call.

Walk-through of the simple factory. A request arrives: factory.get("sms"). The factory looks up "sms" in its map, returns the registered SmsNotifier, and the caller calls send() against the Notifier interface without ever naming SmsNotifier. In Spring, every Notifier bean is put into that map automatically with the bean name as key, so adding a channel means adding one annotated class and no edit to the factory. That makes it Open/Closed friendly, unlike a switch inside the factory, which would still need editing.

Pitfalls. A factory with a giant switch grows into the same if/else problem it was meant to hide (prefer a registry map). A factory that returns null for unknown keys moves the failure far from the cause (throw a clear exception). A factory for a class with only one implementation is noise. Also remember that the factory does not make the products interchangeable by itself: the products must honour the same interface contract (LSP).

Remember: factory = the caller asks for an interface and does not know the class. Do not add one for a class that has a single implementation.

What is Abstract Factory, and how is it different from Factory Method? Intermediate

Factory Method creates one kind of product and lets subclasses choose the class. Abstract Factory creates a whole family of related products that must be used together, and swapping the factory swaps the whole family. Think of a UI toolkit: a DarkThemeFactory makes a dark button, dark checkbox and dark menu, and you never mix themes.

interface UiFactory { Button button(); Checkbox checkbox(); }
class DarkUiFactory  implements UiFactory { ... returns DarkButton, DarkCheckbox }
class LightUiFactory implements UiFactory { ... returns LightButton, LightCheckbox }

void render(UiFactory f) { f.button().draw(); f.checkbox().draw(); }  // consistent family

The trade-off: adding a new product type (say Slider) means changing the factory interface and every factory, so it fits when families vary but product types are stable. Real examples: JDBC (Connection makes matching Statement and ResultSet for one driver), DocumentBuilderFactory. In practice, a Spring configuration profile often plays this role.

The problem. Sometimes the objects you create must be consistent with each other. A dark-theme button next to a light-theme checkbox looks broken; a Postgres Connection paired with an Oracle Statement does not even work. Creating each with its own factory lets you accidentally mix them. Abstract Factory fixes that by making a single factory object responsible for the whole matching set.

How it fits together, step by step.

  1. Define an interface per product type (Button, Checkbox).
  2. Define an abstract factory interface with one creation method per product (button(), checkbox()).
  3. Write one concrete factory per family (DarkUiFactory, LightUiFactory), each returning products of its own family.
  4. Client code receives a factory (usually once, at start-up) and only calls the interface methods. Choosing the family happens in one place: UiFactory f = darkMode ? new DarkUiFactory() : new LightUiFactory();

Modern forms. In Spring Boot you rarely write this by hand. A profile or a conditional configuration (@Profile("aws") versus @Profile("local")) swaps a whole family of beans (blob store, queue client, secrets reader) together. A cross-platform example is a database dialect: one dialect object produces SQL fragments for pagination, identity columns and date functions that fit one database.

Pitfalls. Many products and many families means many classes (families times products). Do not use it when you have one family. And the "adding a product type is painful" cost is real, so use it when product types are stable but families change.

Remember: Factory Method = one product, subclass decides. Abstract Factory = a family of matching products, swap them together.

What is the Builder pattern? Why is it better than a telescoping constructor? Basic

Builder constructs a complex object step by step with named setters and a final build(). It beats a telescoping constructor (one with many parameters, several of the same type) because call sites read clearly, optional fields are simply left out, and the finished object can be immutable and validated once in build().

HttpRequest r = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/orders"))
        .timeout(Duration.ofSeconds(5))
        .header("Accept", "application/json")
        .build();                               // validate here, return immutable object

// Hand-written
class Pizza {
    private final String size; private final boolean cheese;
    private Pizza(Builder b) { size = b.size; cheese = b.cheese; }
    static class Builder {
        private String size; private boolean cheese;
        Builder size(String s) { size = s; return this; }
        Builder cheese(boolean c) { cheese = c; return this; }
        Pizza build() { if (size == null) throw new IllegalStateException("size"); return new Pizza(this); }
    }
}

new Pizza("L", true, false, false) is unreadable and the order is easy to swap by mistake. Builder also avoids JavaBean-style setters, which leave the object half-built and mutable. In real projects, I use Lombok @Builder or, for a few fields, a Java record with a static factory. Builder is worth it from about four or five parameters, or when several are optional. JDK examples: StringBuilder, Stream.builder(), HttpRequest.newBuilder().

The problem, shown with numbers. A User has 3 required fields and 6 optional ones. Constructor overloads for every useful combination explode, and a call like new User("a", "b", null, null, true, false, 30, null, "IN") is unreadable: which null is which? Swapping two boolean arguments compiles and silently produces a wrong object. The JavaBean alternative (empty constructor, then setters) is readable but leaves the object half-built and mutable between calls, so it cannot be immutable and can be seen in an invalid state by another thread.

How a Builder works, step by step.

  1. The builder is a separate mutable object collecting values with chained setters that return this.
  2. Required values go in the builder's constructor (or are checked at the end).
  3. build() validates the combination ("size is required", "end date after start date") in one place and calls the target's private constructor.
  4. The product's fields are final, so the result is immutable and thread-safe once built.

Variations you should know.

  • Lombok @Builder: generates the code. Use @Builder(toBuilder = true) to copy-and-modify an immutable object.
  • Records: good for a handful of components with all required values; add a static factory or a small builder when there are many optional ones.
  • Step builder / fluent interface: the types guide you so you cannot call build() before setting required fields (compile-time safety, more code).
  • GoF Builder with a Director: a director class knows the recipe (buildSpicyPizza(builder)). Rarely seen in application code.

Builder versus Factory. A factory decides which class to make and usually returns it in one call. A builder assembles one complex object piece by piece. They combine well: a factory can return a pre-configured builder.

Pitfalls. A builder for a class with two fields is overkill. Mutable builder reuse across threads is unsafe. Forgetting to validate in build() brings back the half-built object problem. With Lombok on JPA entities, a builder bypasses the no-argument constructor rules, so check the framework needs. Builders also create an extra object, which only matters in extremely hot code.

Remember: many or optional parameters means Builder. Validate in build() and return an immutable object.

3. Structural patterns

What is the Adapter pattern? Give an example. Basic

Adapter converts one interface into another that the client expects, so two classes that were not designed together can work together. I use it to wrap a third-party or legacy API behind my own interface, which also protects my code if the vendor changes.

interface PaymentGateway { PaymentResult charge(String customerId, long paise); }

class StripeAdapter implements PaymentGateway {        // adapts Stripe's SDK to my interface
    private final StripeClient stripe;
    StripeAdapter(StripeClient s) { this.stripe = s; }
    public PaymentResult charge(String id, long paise) {
        StripeCharge c = stripe.createCharge(id, paise / 100.0, "INR");   // vendor-specific call
        return new PaymentResult(c.getId(), "succeeded".equals(c.getStatus()));
    }
}

The adapter holds the vendor object (composition) and translates calls and data types. JDK examples: InputStreamReader adapts a byte stream to a character reader, Arrays.asList adapts an array to a List, and Spring's HandlerAdapter. In hexagonal architecture, adapters are exactly this at the system boundary. The cost is one more class per vendor, which is small compared with a vendor SDK scattered over 200 files.

Analogy. A travel plug adapter: the laptop (client) expects one socket shape, the wall (vendor) offers another, and the adapter sits in between and changes the shape without changing the electricity.

Why it exists. You usually cannot change the thing on the other side: a vendor SDK, a legacy class, a generated client. Your code, meanwhile, wants an interface in your own language and types. If your code calls the SDK directly, vendor names, exception types and quirks leak everywhere, and a vendor change is a codebase-wide edit.

How it works, step by step, using the payment example.

  1. Define the target interface PaymentGateway in terms the business uses: charge(customerId, paise) returning your own PaymentResult.
  2. Write StripeAdapter implements PaymentGateway, holding a StripeClient.
  3. Inside charge, translate: convert paise to the unit Stripe wants, call the vendor method, then translate the vendor's response and exceptions back into your types.
  4. The rest of the code only sees PaymentGateway. Add RazorpayAdapter later with zero change in checkout.

Two forms. Object adapter (shown above): holds the adaptee as a field, uses composition, works with the adaptee's subclasses, and is the normal choice in Java. Class adapter: extends the adaptee and implements the target, which needs multiple inheritance and is rare in Java.

Adapter versus the lookalikes. Adapter only changes the interface and adds no new behaviour. If it also adds logging or caching it starts to be a Decorator or Proxy. If it simplifies many classes into one call it is a Facade. When the adapter shields your whole domain from a foreign model (translating concepts, not only method names) it is often called an anti-corruption layer.

Pitfalls. Leaky adapters that expose vendor types in method signatures defeat the purpose. A "thin" adapter that still lets the vendor's checked exceptions escape is not isolating anything. And do not wrap what you control: if you own both sides, change the interface instead.

Remember: Adapter changes the interface so incompatible things fit. It does not add behaviour.

Explain the Decorator pattern. Why not just use inheritance? Basic

Decorator wraps an object that has the same interface and adds behaviour before or after delegating to it. Because decorators can be stacked in any order at runtime, I avoid the class explosion of inheritance, where every combination of features would need its own subclass.

interface Coffee { double cost(); }
class Espresso implements Coffee { public double cost() { return 80; } }
abstract class CoffeeDecorator implements Coffee {
    protected final Coffee inner;
    CoffeeDecorator(Coffee c) { inner = c; }
}
class Milk extends CoffeeDecorator { Milk(Coffee c){super(c);} public double cost(){ return inner.cost() + 20; } }
class Sugar extends CoffeeDecorator { Sugar(Coffee c){super(c);} public double cost(){ return inner.cost() + 5; } }

Coffee c = new Sugar(new Milk(new Espresso()));   // cost() = 105

The classic JDK example is java.io: new BufferedReader(new InputStreamReader(new FileInputStream(f))). Others: Collections.unmodifiableList and synchronizedList. Servlet filters and Spring's HttpServletRequestWrapper are decorators too. The downside is many small objects and a stack trace that is harder to read.

The problem, with a count. You have a data stream and three optional features: buffering, compression, encryption. With inheritance you need a class per combination: Buffered, Compressed, Encrypted, BufferedCompressed, BufferedEncrypted, CompressedEncrypted, all three, which is 2 to the power 3, minus 1 equals 7 classes, and the count doubles with every new feature. With decorators you write three small classes and stack whichever you want at runtime.

How it works, step by step, using the coffee example.

  1. Everything implements the same interface: Coffee.cost().
  2. The base object (Espresso) does the real work and returns 80.
  3. Milk holds a Coffee. Its cost() asks the inner coffee first, then adds 20.
  4. Sugar wraps Milk. Calling sugar.cost() goes inward: Sugar asks Milk, Milk asks Espresso (80), Milk returns 100, Sugar returns 105.
  5. The caller holds just a Coffee, and does not know or care how many wrappers surround the base.

Key properties. Same interface in and out (so decorators are transparent and stackable). Added behaviour happens before, after, or instead of the delegated call. Order can matter: encrypt-then-compress is much worse than compress-then-encrypt, because encrypted data does not compress.

Decorator versus Proxy. Same structure, different intent. A decorator adds responsibilities and is stacked by the caller. A proxy controls access to one object and often creates or finds it itself. In practice the line blurs, so explain the intent.

Real-world uses beyond java.io. Spring's BeanPostProcessors and AOP wrap beans; Collections.synchronizedMap adds locking; Servlet filters and middleware add logging and auth around a handler; in a REST client you wrap the HTTP client with retry, then with metrics, then with caching.

Pitfalls. Identity breaks: a decorated object is not == or equals to the original, and instanceof against a concrete class fails. Many tiny classes and deep stacks make debugging harder. If the interface is large, writing forwarding methods in every decorator is tedious (a base decorator class that forwards everything helps). If you only ever need one fixed combination, a plain class is simpler.

Remember: Decorator = same interface, wraps, adds behaviour, stackable at runtime. Use it instead of subclass-per-combination.

What is the Facade pattern? Is a service class a facade? Basic

A Facade gives one simple entry point to a complicated subsystem, so callers use one method instead of coordinating five classes. It does not remove the subsystem, it just hides it. A service method like checkout(cart) that calls inventory, payment and shipping is a facade in spirit.

class CheckoutFacade {
    private final Inventory inventory; private final Payment payment; private final Shipping shipping;
    Receipt checkout(Cart cart) {
        inventory.reserve(cart);
        Charge c = payment.charge(cart.total());
        shipping.schedule(cart, c);
        return new Receipt(c.id());
    }
}

Difference from Adapter: Adapter changes one interface to match another, Facade simplifies many classes into one easy interface. A facade does not forbid direct access to the subsystem for advanced users. Risk: a facade that grows business rules becomes a god class.

The problem. A feature such as "place an order" needs inventory, payment, shipping, tax and loyalty points, each with its own API and ordering rules (reserve stock before charging, charge before scheduling shipping). If every controller repeats this choreography, the sequence is duplicated and drifts out of sync. A facade owns the choreography once and offers one intent-revealing method.

Walk through the example. The controller calls checkout.checkout(cart). Inside: (1) inventory.reserve(cart) to hold stock, (2) payment.charge(total), (3) shipping.schedule(...), (4) return a receipt. The controller knows nothing about those three subsystems. If shipping gets a new required parameter, only the facade changes.

What a facade is not.

  • It is not a place for business rules. If the facade starts deciding discounts and eligibility it becomes a god class. It should orchestrate calls, not own the rules (which stay in the subsystem classes).
  • It does not hide the subsystem from everyone. Advanced callers may still use the parts directly. That is the difference from encapsulation by access modifiers.
  • It is not an Adapter: an adapter makes one interface fit another expected one, a facade invents a new simpler interface.

Failure handling is the real work. In the example, what if payment succeeds and shipping fails? A real facade must define compensation (refund, release stock) or a saga across services. Mention this in an interview: the facade is the natural place where the "all or nothing" decision lives. In a single database it is a transaction; across services it becomes the orchestrator of a saga.

Where you see it. SLF4J as a facade over logging frameworks, Spring's JdbcTemplate over raw JDBC, and an API gateway or "backend for frontend" as a facade over microservices. A Spring @Service that orchestrates other services is a facade in spirit, though people rarely call it that.

Remember: Facade = one easy front door to a messy subsystem. Adapter = translate one interface.

What is the Proxy pattern? Name the types, and give real examples. Intermediate

A Proxy stands in for a real object with the same interface and controls access to it. The caller thinks it talks to the real thing. The main types are virtual (lazy creation), protection (access checks), remote (a local stand-in for a remote call) and caching or logging. In Spring and Hibernate, proxies are everywhere: @Transactional, @Cacheable, and lazy-loaded entities are all proxies.

In Java, a proxy is created in one of two ways. A JDK dynamic proxy (java.lang.reflect.Proxy) needs the target to implement an interface. CGLIB-style proxies subclass the target class, so a final class or final method cannot be proxied. Spring Boot uses class-based proxies by default. This design is why calling a @Transactional method from another method of the same class skips the proxy (see the scenario on it).

The four classic reasons to put something in front of an object.

TypeWhat the proxy doesExample
Virtual (lazy)Delays creating or loading the expensive real object until first useHibernate lazy association: order.getItems() is a proxy that runs SQL only when you touch it

How Spring makes @Transactional work, step by step.

  1. At start-up Spring sees OrderService has a @Transactional method and creates a subclass (CGLIB) or interface-based proxy object.
  2. The proxy, not the real object, is what gets injected into other beans.
  3. When a controller calls orderService.place(), the call enters the proxy. It opens a transaction, then calls the real place().
  4. On normal return it commits; on a runtime exception it rolls back; then it hands the result back to the caller.

Consequences you must know. (a) Only calls that cross the proxy are intercepted, so this.other() inside the same class is not (self-invocation). (b) A class-based proxy needs a non-final class and non-final methods, because the proxy overrides them. (c) The injected object's class name is something like OrderService$$SpringCGLIB$$0, which surprises people in logs and in getClass() comparisons. (d) Since Spring Boot 2.0, class-based proxies are the default, and since Spring 6 non-public methods can in some setups be intercepted, so check the version if asked, but public methods called from another bean are always safe.

JDK dynamic proxy in 6 lines.

Service real = new RealService();
Service logged = (Service) Proxy.newProxyInstance(
    Service.class.getClassLoader(), new Class<?>[] { Service.class },
    (proxy, method, args) -> {
        System.out.println("calling " + method.getName());
        return method.invoke(real, args);       // forward to the real object
    });

Proxy versus Decorator in words. Both implement the same interface and forward calls. A Decorator is about adding functionality that the caller composes. A Proxy is about being a stand-in that decides whether, when and how the real object gets used. If you can list the real reason as "lazy, security, remote, transaction, cache", it is a Proxy.

Remember: Proxy = same interface, controls access to the real object. Decorator adds behaviour. Proxy gates or defers it.

Adapter, Decorator, Proxy and Facade all "wrap" something. How do you tell them apart? Intermediate

I tell them apart by intent and by the interface they present. Adapter presents a different interface than the wrapped object. Decorator presents the same interface and adds behaviour. Proxy presents the same interface and controls access. Facade presents a new, simpler interface over many objects.

Decorator and Proxy have the same shape, so the difference is purpose. A proxy usually creates or manages the real object itself and the client does not stack proxies. Decorators are given the object by the caller and are meant to be stacked.

A memory trick. Ask two questions about the wrapper: (1) is its interface the same as the wrapped object's? (2) how many objects does it wrap?

  • Different interface, one object: Adapter (translate).
  • Same interface, one object, adds behaviour you choose to stack: Decorator (enhance).
  • Same interface, one object, stands in and gates or defers access: Proxy (control).
  • New simpler interface, many objects: Facade (simplify).

The same scenario seen four ways: calling a payment vendor.

  • Adapter: turns the vendor's createCharge(double, String) into your charge(long paise).
  • Decorator: LoggingGateway(MetricsGateway(RazorpayAdapter)): each layer adds a concern and you choose the stack.
  • Proxy: a lazy proxy that opens the vendor connection only on the first call, or a protection proxy that rejects calls from users without the right role.
  • Facade: CheckoutFacade.checkout(cart) which uses payment, stock and shipping together.

Edge cases that cause confusion. A decorator that only logs is also a "smart reference" proxy, so the line is intent and who creates it: a proxy usually creates or locates the real object itself and the client cannot swap or stack it, whereas a decorator is given its inner object and is designed to nest. An adapter that also caches begins to act like a decorator. In real code, combine them freely and name each class by what it does. In an interview, state intent first and structure second.

Related pair worth adding: Bridge looks like Adapter structurally but is designed up front to let an abstraction and its implementation vary independently, whereas Adapter is applied after the fact to make existing incompatible pieces fit.

Remember: different interface = Adapter, same + add = Decorator, same + gate = Proxy, many + simplify = Facade.

What is the Composite pattern? Where is it used? Intermediate

Composite lets me treat a single object and a group of objects through the same interface, so a tree of parts and wholes can be handled with one call. A file system is the classic case: a File and a Folder both have size(), and a folder's size is the sum of its children.

interface Node { long size(); }
class FileNode implements Node { long bytes; public long size() { return bytes; } }
class Folder implements Node {
    private final List<Node> children = new ArrayList<>();
    void add(Node n) { children.add(n); }
    public long size() { return children.stream().mapToLong(Node::size).sum(); }   // recursion
}

Use it for UI component trees, organisation charts, menus, expression trees and permission groups. The trade-off: the shared interface can end up with methods that make no sense for a leaf (add() on a file), so keep child management only on the composite.

The problem. You have things that can contain other things of the same kind: a folder with files and folders, a menu with items and sub-menus, an order with line items and bundles of items, an organisation with employees and teams. Without Composite the client code is full of if (x instanceof Folder) { loop } else { ... } at every place, and each new operation repeats that branching.

The three roles.

  • Component: the common interface (Node.size()).
  • Leaf: an item with no children (FileNode), does the real work.
  • Composite: holds child components and implements the operation by delegating to children and combining results (Folder.size() sums them).

Walk through the diagram. Calling root.size(): the root folder asks a.txt (say 10 bytes), then asks the src folder. src asks A.java (30) and B.java (20), returns 50. The root adds 10 plus 50 and returns 60. The caller wrote one line and never knew the tree's shape. Depth does not matter because recursion handles it.

Design choice: where do add() and remove() live?

ChoiceProCon
On the common interface (transparency)Client treats all nodes identicallyLeaf has methods that make no sense; they throw errors at runtime
Only on the Composite (safety)Type-safe, a leaf cannot be asked to addClient must know whether it holds a composite to add children

Most Java code picks safety.

Other uses and tips. Expression trees (Add(Num, Mul(Num, Num))), permission groups containing users and other groups, and UI hierarchies such as Swing's Container and Component. Combine with Visitor or a streaming flatten() when you need many different operations over the tree. Watch for cycles (a folder that contains itself), which cause infinite recursion, and for very deep trees, which can overflow the stack if you recurse (use an explicit stack). Cache aggregates like size() only if you also invalidate them when children change.

Remember: Composite = tree where a leaf and a group share one interface, so one call recurses over everything.

4. Behavioral patterns

Explain the Strategy pattern with an example. How does it relate to Open/Closed? Basic

Strategy puts a family of interchangeable algorithms behind one interface, and the caller picks which one to use. It replaces a big if/else or switch over "which way to do it", and it is the standard way to satisfy Open/Closed: a new algorithm is a new class, and the calling code does not change.

interface PricingStrategy { double price(Order o); }
class RegularPricing implements PricingStrategy { public double price(Order o) { return o.subtotal(); } }
class FestivalPricing implements PricingStrategy { public double price(Order o) { return o.subtotal() * 0.8; } }

class Checkout {
    private final PricingStrategy pricing;               // injected, swappable
    Checkout(PricingStrategy p) { this.pricing = p; }
    double total(Order o) { return pricing.price(o); }
}
// With lambdas, a one-method strategy needs no class: new Checkout(o -> o.subtotal() * 0.8)

JDK examples: Comparator passed to sort, and ThreadPoolExecutor's rejection policy. In Spring, I inject a Map<String, PricingStrategy> and pick by key. Do not use it for two fixed branches that never change.

The problem. A piece of code must do "the same job" in different ways: price an order, compress a file, choose a route, sort records. The naive version has a method with if (type == A) ... else if (type == B) .... Every new way means editing that method, retesting every old way, and the method becomes a magnet for merge conflicts.

How Strategy fixes it, step by step.

  1. Pull the varying part into an interface with one method: PricingStrategy.price(Order).
  2. Write one small class per way: RegularPricing, FestivalPricing.
  3. The class that needs the job done (the context, here Checkout) holds a strategy field and calls it. It does not know which one it has.
  4. Something outside the context chooses the strategy: a constructor argument, a factory keyed by customer type, a configuration property, or Spring injecting a Map<String, PricingStrategy>.

Numbers. An order has subtotal 1,000. Regular returns 1,000; festival returns 800. Next month marketing wants "buy one get one": one new class, BogoPricing. Checkout and the existing two strategies are untouched and their tests still pass. That is Open/Closed made concrete.

Strategy with lambdas. A functional interface turns it into a one-liner, so you only need a named class when the strategy has state or is reused: Comparator<Order> byTotal = Comparator.comparing(Order::total); and list.sort(byTotal.reversed()). Here the lambda is the strategy and sort is the context.

Strategy versus the neighbours. State has the same shape but the object changes it by itself over time. Template Method varies steps through inheritance and fixes the order. A plain switch is perfectly fine when the cases are few, closed and unlikely to grow, for example a two-value enum.

Pitfalls. Clients must know enough to choose a strategy (that knowledge has to live somewhere). Strategies that need lots of context data tempt you to pass the whole context object, which couples them to it (pass only what is needed, or a small parameter object). Too many tiny strategies for trivial differences can be harder to read than a table of rates. And if two strategies share most code, factor the shared part into a helper instead of inheriting from each other.

Remember: Strategy = swap the algorithm behind an interface. It is the cure for a growing if/else.

What is the Template Method pattern, and how is it different from Strategy? Intermediate

Template Method defines the skeleton of an algorithm in a base class, with fixed steps in a fixed order, and lets subclasses fill in specific steps. Strategy swaps the whole algorithm by composition, Template Method varies only some steps by inheritance. I prefer Strategy when I need runtime flexibility, and Template Method when the order must be locked.

abstract class DataImporter {
    public final void run(String path) {          // final: subclasses cannot change the order
        List<String> raw = read(path);            // step 1: varies
        List<Record> recs = parse(raw);           // step 2: varies
        validate(recs);                           // fixed step
        save(recs);                               // fixed step
    }
    protected abstract List<String> read(String p);
    protected abstract List<Record> parse(List<String> raw);
    private void validate(List<Record> r) { ... }
    private void save(List<Record> r) { ... }
}
class CsvImporter extends DataImporter { ... }

It follows the "Hollywood principle": the base class calls the subclass, not the other way round. JDK and framework examples: HttpServlet.service calling doGet/doPost, AbstractList, and JUnit's setup and teardown. The downside is that inheritance ties you to the base class, so Spring's JdbcTemplate uses the callback (Strategy) form of the same idea instead.

The problem. Several jobs follow the same recipe but differ in a few steps. A CSV importer and an XML importer both: open, parse, validate, save, log. If each is written separately, the common steps (validate, save, log) are copied, and a fix to the recipe has to be repeated in each copy. Template Method keeps the recipe in one place.

How it works, step by step.

  1. The base class has a public final method (the template) that calls a fixed sequence of steps. final stops subclasses from reordering the recipe.
  2. Some steps are implemented in the base class (the shared ones).
  3. Some steps are abstract: subclasses must provide them (read, parse).
  4. Some steps are hooks: a default empty or default implementation that subclasses may override (onFinished()).
  5. A client calls new CsvImporter().run(path). The base class drives, and calls back into the subclass at the right moments (the Hollywood principle: do not call us, we call you).
Template MethodStrategy
MechanismInheritanceComposition

Modern alternative. Instead of subclassing, pass the varying steps as lambdas into one method: importer.run(path, this::read, this::parse). This is the callback form, used by Spring's JdbcTemplate.query(sql, rowMapper), where the template handles connection, statement, exceptions and cleanup and you only supply the row mapping. Same intent, no inheritance.

Pitfalls. Calling an overridable method from a constructor in the base class runs before the subclass fields are initialised, a classic bug. Too many hooks make the template impossible to follow. And if every subclass overrides almost everything, Template Method was the wrong choice and Strategy would be cleaner.

Remember: Template Method = base class owns the order, subclasses fill the steps (inheritance). Strategy = pass in the whole algorithm (composition).

Explain the Observer pattern. What are its pitfalls? Basic

Observer lets one object (the subject) notify many others (observers) when something happens, without knowing who they are. The subject keeps a list of listeners and calls each when its state changes. It decouples the producer from the consumers, so I can add a new reaction without touching the producer. The pitfalls are memory leaks from listeners that are never removed, surprising call order, and a slow or failing listener hurting the producer.

interface OrderListener { void onPlaced(Order o); }
class OrderService {
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>();
    void subscribe(OrderListener l) { listeners.add(l); }
    void place(Order o) {
        save(o);
        listeners.forEach(l -> l.onPlaced(o));     // email, analytics, inventory...
    }
}
  • Leak: a long-lived subject holds strong references to short-lived listeners (a closed UI screen), so they are never garbage collected. Always unsubscribe, or use weak references.
  • Synchronous by default: a slow listener slows the producer and an exception can stop the rest. Isolate each call with try/catch, or dispatch through an executor or a message queue.
  • Order and cascades: listeners that trigger more events are hard to debug.

JDK's java.util.Observable is deprecated since Java 9, so use listener interfaces, PropertyChangeListener, or Spring's ApplicationEventPublisher. Across services, the same idea is publish-subscribe on Kafka or a similar broker.

The problem. When an order is placed you must send an email, update analytics, reserve inventory, notify a warehouse. If OrderService.place() calls each one directly, it depends on all of them, and adding the fifth reaction means editing the order code. Observer inverts this: the service only announces "order placed", and anyone interested has already registered.

Lifecycle, step by step.

  1. A listener implements a small interface (OrderListener.onPlaced).
  2. At start-up each listener registers itself with the subject (subscribe).
  3. The subject finishes its own work (save the order), then loops over the list calling each listener.
  4. When a listener is no longer needed, it unsubscribes.

Push versus pull. In the push model the subject sends the data (onPlaced(order)); in the pull model it sends only a signal and the listener queries for what it needs. Push is simpler and common. Pull avoids sending data some listeners do not need.

In-process Observer versus messaging.

Spring specifics. ApplicationEventPublisher.publishEvent(new OrderPlaced(o)) and @EventListener methods implement Observer inside the app. Events are synchronous by default and run in the publisher's transaction. @TransactionalEventListener(phase = AFTER_COMMIT) delays the listener until the transaction has committed, so a listener never announces an order that later rolls back.

The leak in detail ("lapsed listener"). A long-lived subject holds a strong reference to each listener. If a short-lived screen registers itself and is closed without unsubscribing, the subject still references it, so the garbage collector cannot free it, and the screen keeps receiving events. Over time memory grows. Fixes: always unsubscribe in a finally or lifecycle hook, or store listeners in a WeakReference collection.

Other pitfalls. Iterating a listener list while a listener unsubscribes throws ConcurrentModificationException (hence CopyOnWriteArrayList above). Cascading events (listener A fires event 2, which triggers listener B...) create hard-to-trace flows, and circular chains can loop forever. Order of listeners should not matter; if it does, make the dependency explicit.

Remember: Observer = subject notifies unknown listeners. Watch for leaks (unsubscribe) and slow or failing listeners.

What is the Command pattern, and what do you use it for? Intermediate

Command turns a request into an object, so I can queue it, log it, retry it, schedule it, or undo it. The caller (invoker) just calls execute() and does not know what the command does or who receives it. I use it for undo/redo, job queues, task schedulers, and macro or batch operations.

interface Command { void execute(); void undo(); }
class AddText implements Command {
    private final Editor ed; private final String text;
    AddText(Editor e, String t) { ed = e; text = t; }
    public void execute() { ed.append(text); }
    public void undo()    { ed.deleteLast(text.length()); }
}
class History {
    private final Deque<Command> done = new ArrayDeque<>();
    void run(Command c) { c.execute(); done.push(c); }
    void undo() { if (!done.isEmpty()) done.pop().undo(); }
}

JDK example: Runnable and Callable submitted to an ExecutorService are commands. Event sourcing and database write-ahead logs are the same idea at system scale. In modern Java, a lambda is often enough for commands without undo.

The idea from scratch. Normally to do something you just call a method. Command turns "do this thing with these arguments" into an object. Once an action is an object you can store it in a list, send it to another thread, write it to a file, schedule it for later, run it again, or call its opposite. That is exactly what a plain method call cannot do.

The four roles.

  • Command: interface with execute() (and optionally undo()).
  • Concrete command: holds the receiver and the arguments (AddText holds the editor and the text).
  • Receiver: the object that really does the work (Editor).
  • Invoker: triggers commands and manages them (a button, a scheduler, the History class). It never knows what the commands do.

Undo, walked through with real values. The editor holds "Hello". The user types " world": History.run(new AddText(ed, " world")) calls execute() (text becomes "Hello world") and pushes the command on the stack. The user presses undo: History.undo() pops it and calls undo(), which deletes the last 6 characters, returning "Hello". A redo stack works the same way, in reverse. For commands where reversing is hard, store a snapshot (Memento) of the state before the command.

Uses beyond the editor.

  • Work queues and thread pools: executor.submit(Callable). The task is a command.
  • Transactions and audit: log every command to replay after a crash or to show who did what (event sourcing: the stored commands or events are the source of truth).
  • Retry with backoff: the retry loop re-executes the same command object.
  • Macro commands: a CompositeCommand that runs a list of commands (and undoes them in reverse order).
  • CQRS "command" side: PlaceOrderCommand carries the intent, a handler executes it. A related but different use of the word.

Pitfalls. One class per action creates many small classes (lambdas help). Commands that capture mutable state may execute later against changed data, so capture immutable values. Undo must be exact: a command that cannot be reversed (sending an email) needs a compensating action, not a true undo. Also make long-running or queued commands idempotent, so a retry does not charge twice.

Remember: Command = a request as an object, so it can be queued, logged, retried or undone.

Explain the State pattern. How would you model an order or a vending machine with it? Intermediate

State lets an object change its behaviour when its internal state changes, by delegating to a separate state object per state. It replaces a pile of if (state == X) checks in every method. For an order, each state (Created, Paid, Shipped, Cancelled) knows which actions are legal and which state comes next.

interface OrderState {
    OrderState pay();
    OrderState ship();
    OrderState cancel();
}
class Created implements OrderState {
    public OrderState pay()    { return new Paid(); }
    public OrderState ship()   { throw new IllegalStateException("pay first"); }
    public OrderState cancel() { return new Cancelled(); }
}
class Shipped implements OrderState {
    public OrderState pay()    { throw new IllegalStateException("already paid"); }
    public OrderState ship()   { throw new IllegalStateException("already shipped"); }
    public OrderState cancel() { throw new IllegalStateException("too late"); }
}
class Order { private OrderState state = new Created();
    void pay() { state = state.pay(); }  void ship() { state = state.ship(); } }

For a small machine with a few states and rare change, an enum with a transition table is simpler than a class per state. Use full State classes when each state has real behaviour. Vending machines and ATMs are classic uses (see those exercises).

The problem. An order behaves differently depending on its status. Without State, every method starts with checks: pay() says "if status is CREATED do this, else if PAID throw, else if SHIPPED throw...", and ship() and cancel() repeat the same kind of ladder. Each new status edits every method, and it is easy to forget one, leaving an illegal transition possible (shipping a cancelled order).

How State flips the structure. Instead of "method, then check state", it becomes "state, then method". The rules for being in the Paid state live together in one class: which actions are allowed and which state follows. The order object (the context) just forwards each call to its current state object and stores the state that comes back.

Walk through a timeline.

  1. new Order() starts in Created.
  2. order.pay(): Created.pay() returns a Paid object, so the order is now Paid.
  3. order.ship(): Paid.ship() returns Shipped.
  4. order.cancel(): Shipped.cancel() throws "too late". The illegal move is rejected by the very structure, with no central if-chain.

Who decides the next state? Either the state objects (as above, flexible, states know each other) or the context using a transition table. States that hold no data can be shared single instances (enum constants, flyweights); states that carry per-context data are created per transition.

Enum-based version, often enough.

enum OrderStatus {
    CREATED, PAID, SHIPPED, CANCELLED;
    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
        CREATED, Set.of(PAID, CANCELLED), PAID, Set.of(SHIPPED, CANCELLED),
        SHIPPED, Set.of(), CANCELLED, Set.of());
    boolean canMoveTo(OrderStatus next) { return ALLOWED.get(this).contains(next); }
}

Use this when states differ only in which transitions are legal. Move to State classes when each state has different behaviour (different pricing, different side effects). For long-lived or very complex workflows, a state machine library or workflow engine and a persisted state column with an audit history are better.

Persistence and concurrency. The state must be stored (a status column), and a transition should be an atomic conditional update (UPDATE orders SET status='PAID' WHERE id=? AND status='CREATED') so two concurrent payments cannot both succeed.

Remember: State = behaviour changes with state, each state is a class that handles actions and names the next state.

State and Strategy have the same class diagram. What is the difference? Intermediate

The shape is the same, the intent differs. In Strategy, the client chooses an algorithm from outside and it usually stays the same. In State, the object changes its own state object as it runs, and the states know about each other because they trigger the transitions.

A quick test: who switches it, and does it change over time? A sorting comparator chosen by a caller is Strategy. An order that moves from Created to Paid to Shipped is State. Strategies are independent of one another and usually stateless. States often reference the next state.

What is the Chain of Responsibility pattern? Give a real example. Intermediate

Chain of Responsibility passes a request along a line of handlers. Each handler either handles it, changes it, or passes it to the next one. The sender does not know which handler will act, and I can add, remove or reorder handlers without changing the others. Servlet filters and Spring Security's filter chain are the everyday examples.

abstract class Handler {
    private Handler next;
    Handler then(Handler n) { this.next = n; return n; }
    void handle(Request r) {
        if (!process(r) && next != null) next.handle(r);   // process returns true if it stops the chain
    }
    protected abstract boolean process(Request r);
}
auth.then(rateLimit).then(validation).then(businessLogic);

Other examples: Java exception handling (catch blocks), logging levels, approval workflows (manager, then director, then VP), and middleware in web frameworks. The downside: a request might not be handled at all, and debugging means following the whole chain.

The problem. A request must pass several independent checks or transformations: authenticate, rate limit, validate, log, authorise, then handle. If one big method does all of that with nested ifs, you cannot reorder, reuse or test the pieces separately. And if a new check is needed for some routes only, you duplicate code.

How a chain works, step by step.

  1. Every handler implements the same interface (handle(request)) and keeps a reference to the next handler.
  2. The chain is assembled once, by wiring auth.then(rateLimit).then(validation).then(business).
  3. A request goes to the first handler. It does its job and then either calls next.handle(request) to continue, or stops by returning a response or an error (a 401 stops at Auth).
  4. Reordering, adding or removing a link is a wiring change only.

Two flavours. First-match wins (classic GoF): exactly one handler handles it and the rest are skipped. Example: approval limits, where a manager approves up to 10,000, a director up to 100,000, and a VP the rest. Pipeline (every handler does something and passes on): servlet filters, middleware. Most real uses are the pipeline form. A filter can act before the rest of the chain, after it (post-processing the response), or both, like an onion.

In Java and Spring. The servlet Filter.doFilter(req, res, chain) where you call chain.doFilter(...) to continue. Spring Security is a list of filters (SecurityFilterChain), each with a single job (CSRF, authentication, authorisation). HandlerInterceptor has preHandle and postHandle. The Java catch clauses and logging frameworks' appender chains are also chains.

Pitfalls. The order is behaviour: putting authorisation before authentication is a bug, so define and test the order. A handler that forgets to call next silently swallows requests. If no handler handles a first-match request, you need a default. Debugging requires following the whole path, so log which handler stopped the request. A very long chain adds latency, and shared mutable request state passed along can cause surprising interactions.

Remember: Chain = handlers in a line, each handles or passes on. Servlet filters are the example to name.

What are Visitor and Mediator, and when would you pick each over a simpler design? Senior

Visitor lets me add a new operation over a stable set of classes without editing those classes, by moving the operation into a separate visitor object and using double dispatch. Mediator puts the interaction logic between several peer objects into one coordinator, so the peers talk to the mediator and never to each other. I rarely hand-write Visitor in modern Java, because sealed types plus pattern matching for switch give the same result with less code.

Visitor, in plain steps. Suppose you have an expression tree with Num and Add nodes, and want to compute it, print it, and later optimise it. Without Visitor each new operation means editing every node class. With Visitor:

  1. Each node has one method, accept(Visitor v), which calls v.visit(this). This is double dispatch: the method run depends on both the node's type and the visitor's type.
  2. Each operation is a class implementing Visitor with one visit overload per node type (SumVisitor, PrintVisitor).
  3. Adding an operation is a new visitor class and touches no node.

The trade-off is the mirror image of Open/Closed: it is easy to add operations, but adding a new node type forces you to change every visitor. So it fits when the class hierarchy is stable and operations change, such as compilers, syntax-tree processing, and tax rules over document types.

// Modern Java 21 alternative: sealed interface + exhaustive switch
sealed interface Expr permits Num, Add {}
record Num(int v) implements Expr {}
record Add(Expr l, Expr r) implements Expr {}
static int compute(Expr e) {
    return switch (e) {
        case Num n -> n.v();
        case Add a -> compute(a.l()) + compute(a.r());     // compiler checks that all cases are covered
    };
}

Here a new operation is a new method, and adding a new subtype makes the compiler flag every switch that needs updating, which gives Visitor's safety with no ceremony.

Mediator, in plain steps. In a chat room with N users, if every user holds references to every other, there are about N squared links. With a ChatRoom mediator, each user knows only the room, and the room decides who receives a message (N links). Another classic: a dialog box where the checkbox, text field and OK button enable or disable each other. The dialog class holds that logic, and the widgets stay reusable. Air-traffic control is the usual real-life comparison.

Mediator versus Observer. Observer is a one-way broadcast from a subject to listeners who register themselves. Mediator is a two-way hub that owns the coordination rules. The risk of Mediator is that it grows into a god class holding all the logic, so keep it focused. A message bus or event bus (Spring events, Guava EventBus) is a mediator that decouples senders from receivers but, unlike a classic mediator, contains no business rules itself.

Remember: Visitor adds operations to a stable hierarchy (use sealed types and switch today). Mediator centralises peer-to-peer coordination in one object.

Why this question is asked. It tests whether you see patterns as living structures in code you already use, not as textbook diagrams. A strong answer picks three examples and explains the mechanism rather than reciting the whole table.

Three worked examples.

  1. Decorator in java.io. new BufferedReader(new InputStreamReader(new FileInputStream(f))). FileInputStream reads raw bytes. InputStreamReader is an Adapter that turns bytes into characters using a charset. BufferedReader is a Decorator that adds an in-memory buffer and readLine(). Each layer is swappable, which is why the same BufferedReader can read from a file, a socket or a string.
  2. Strategy in Comparator. Collections.sort is the fixed algorithm. The Comparator argument is the interchangeable strategy. Passing a different comparator changes ordering with no change to the sort code.
  3. Template Method plus Proxy in Spring. JdbcTemplate.query(sql, rowMapper) fixes the sequence (get connection, prepare statement, run, map rows, close, translate exceptions) and lets you vary only the row mapping. And @Transactional works because Spring wraps your bean in a Proxy that starts and commits the transaction around your method.

More examples worth knowing. Iterator: Collection.iterator() and the enhanced for loop. Observer: PropertyChangeListener, Swing listeners, Spring events. Flyweight: Integer.valueOf caches -128 to 127, and String interning. Factory: Executors.newFixedThreadPool, Charset.forName. Builder: StringBuilder, Stream.Builder, HttpClient.newBuilder(). Front Controller: Spring MVC's DispatcherServlet receives every request and routes it to a controller. Dependency Injection and IoC: the whole Spring container. Prototype: Object.clone(), and Spring's prototype scope. Singleton: Runtime and default Spring beans.

Caveat on accuracy. Some textbook labels are loose: Collections.unmodifiableList is a wrapper that blocks mutation (decorator or proxy depending on your reading), and Spring's BeanFactory is more a registry and factory than a pure Factory Method. In an interview, pick the cleanest examples and be ready to say "it is close to X" instead of overclaiming.

What are the types of dependency injection, and which one do you prefer? Why? Basic

There are three: constructor, setter and field injection. I prefer constructor injection because dependencies are required and visible, fields can be final, the object can never exist half-wired, and I can create it in a plain unit test with new and fakes. The container (IoC, Inversion of Control) creates beans and passes them in, instead of each class creating its own collaborators.

@Service
class OrderService {
    private final OrderRepository repo;           // final: set once, never null
    private final PaymentGateway gateway;
    OrderService(OrderRepository repo, PaymentGateway gateway) {   // single constructor: no @Autowired needed
        this.repo = repo; this.gateway = gateway;
    }
}
  • Constructor: required dependencies, immutable, easy to test. A constructor with many parameters is a useful warning that the class does too much.
  • Setter: optional or changeable dependencies, though it allows a half-built object.
  • Field (@Autowired on a field): short, but hides dependencies, cannot be final, and needs reflection or the Spring container to test. Avoid it in new code.

Constructor injection also fails fast on a circular dependency at start-up, which is a good thing: it tells you the design is tangled.

What IoC and DI are, simply. Normally a class builds what it needs: this.repo = new MySqlRepo(). With Inversion of Control, control of creation and wiring moves to a container (Spring): the class just declares what it needs, and the container creates the objects and supplies them. Dependency Injection is the way supplies arrive: through the constructor, a setter, or a field.

What the container does at start-up, step by step.

  1. It scans for beans (@Component, @Service, @Bean methods) and records their definitions.
  2. It works out a dependency graph from constructor parameters.
  3. It instantiates beans in the order required: repository first, then the service that needs it, passing the repository in.
  4. If it finds a cycle with constructor injection, it cannot satisfy it and fails with a clear error.

Is a Spring singleton bean thread-safe? What are the bean scopes? Intermediate

No. "Singleton" in Spring means one instance per container, shared by all request threads, and Spring does nothing to make its fields safe. So singleton beans must be stateless, or hold only immutable or thread-safe state. A mutable field like private Order current; in a service is a race condition.

Scopes: singleton (default), prototype (new instance on each injection or lookup), and web scopes request, session, application. Spring's singleton differs from the GoF one: GoF is one per class loader, Spring is one per bean definition per container, so you can have two beans of the same class.

A common trap: injecting a prototype or request-scoped bean into a singleton gives you only one instance, created at wiring time. The fix is ObjectProvider<T> or a scoped proxy (@Scope(proxyMode = TARGET_CLASS)), which creates a fresh target on each call. Keep request-specific data in method parameters, not in fields.

Why "singleton" does not mean "safe". A singleton bean is one object shared by every request thread at the same time. Think of a Tomcat with 200 worker threads all calling orderService.place() on the same instance. Any non-final field they write is shared, and writes race with each other.

A bug in slow motion.

@Service class ReportService {
    private User currentUser;                       // shared by all threads: bug
    String build(User u) { this.currentUser = u; return render(); }   // render() reads currentUser
}
  1. Thread A sets currentUser = alice and starts rendering.
  2. Thread B sets currentUser = bob before A finishes.
  3. A's report now contains Bob's data. It happens only under concurrent load, so unit tests and a single-user dev run are fine.

Fix: pass the user as a parameter (render(u)), so each thread has its own copy on its own stack.

What is safe inside a singleton. Other singleton beans injected as dependencies (they are shared but stateless), final immutable configuration, and thread-safe components such as ConcurrentHashMap, AtomicLong or an injected DataSource. Be careful with caches inside beans: a HashMap used as a cache is not safe.

A singleton is built once, at start-up, so its constructor runs once and receives one request-scoped object, and that same object is then used forever. Why is immutability valuable, and how do you make a Java class truly immutable? Intermediate

An immutable object cannot change after construction, so it is automatically thread-safe, safe to share and cache, safe as a HashMap key, and easy to reason about. To make a class immutable: make it final, make all fields private final, have no setters, and defensively copy any mutable object that comes in or goes out.

public final class Booking {
    private final String id;
    private final List<String> seats;
    public Booking(String id, List<String> seats) {
        this.id = id;
        this.seats = List.copyOf(seats);       // copy in: caller cannot change it later
    }
    public List<String> seats() { return seats; }   // already unmodifiable
}
// Java 16+: record Booking(String id, List<String> seats) { Booking { seats = List.copyOf(seats); } }

The common mistake is a final field holding a mutable object (final List still lets callers add to it), or returning the internal Date or array. The cost of immutability is a new object per change, which the JVM handles well. For "modify", return a new copy (withSeat(...)). String, Integer and LocalDate are immutable.

Why threads care. Concurrency bugs come from two threads touching the same changing data. If the data can never change after it is built, there is nothing to race on. An immutable object needs no locks, can be handed to any thread, cached forever, and used as a key in a map or element of a set (its hashCode never changes while it sits in the collection). That is why String is immutable.

Checklist, with the reason for each rule.

  1. final class (or private constructor): a subclass could add mutable state or override getters and break the guarantee.
  2. private final fields: final also gives a Java Memory Model guarantee that other threads see the fully constructed values, even if the object was shared through a data race (safe publication of final fields).
  3. No setters and no method that mutates internal state.
  4. Defensive copy on the way in for mutable parameters (List.copyOf(seats)). Otherwise the caller keeps a reference and can change your internals later.
  5. Defensive copy or unmodifiable view on the way out (List.copyOf inside the getter, or store an unmodifiable list once).
  6. Do not leak this from the constructor (for example by registering as a listener) before it finishes.

A failing example and the fix.

// Looks immutable but is not
public final class Booking {
    private final List<String> seats;
    public Booking(List<String> seats) { this.seats = seats; }       // keeps caller's list
    public List<String> seats() { return seats; }                    // hands out internals
}
List<String> mine = new ArrayList<>(List.of("A1"));
Booking b = new Booking(mine);
mine.add("A2");                 // b now has two seats; the "immutable" object changed

The fix is the List.copyOf version above. Note the List.of and List.copyOf collections are unmodifiable and also reject null elements. Collections.unmodifiableList(list) is only a read-only view: it still changes if the original list changes, so copy first.

Records and "with" methods. A record gives you final fields, constructor, equals, hashCode and toString for free, but it is only shallowly immutable: a record holding a List still needs the copy in its compact constructor. To "change" an immutable object you create a new one: b.withSeat("A2") returns a new Booking. For frequently changed big structures, persistent data structures or builders reduce copying.

Trade-offs. Extra allocation on every change (the JIT and garbage collector make short-lived objects cheap, so only measure in a genuinely hot path); awkward with frameworks that want setters and a no-arg constructor (JPA entities are usually mutable, but value objects embedded in them can be immutable); and deep copies of large collections can be expensive, so prefer immutable collections that share structure.

Remember: final class, private final fields, no setters, copy mutable inputs and outputs. A final reference does not mean a frozen object.

How do you design a class to be thread-safe? What are your options, in order of preference? Senior

I prefer, in order: no shared state (stateless), immutable state, thread confinement (each thread has its own copy), then existing thread-safe building blocks (ConcurrentHashMap, AtomicLong), and only last explicit locking. Locks are the most error-prone, so I keep them small and hide them inside one class.

  1. Stateless: a method that uses only its parameters. Nothing to protect.
  2. Immutable: share freely, no locks.
  3. Confinement: local variables, or a ThreadLocal (careful with thread pools: always remove()).
  4. Concurrent classes: ConcurrentHashMap.merge, LongAdder, AtomicReference.compareAndSet.
  5. Locks: synchronized or ReentrantLock, guarding every access to the shared fields with the same lock.

The classic bug is check-then-act: if (!map.containsKey(k)) map.put(k, v) is not atomic even on a thread-safe map. Use putIfAbsent or computeIfAbsent. Another is compound state, such as two fields that must change together under one lock. In an interview LLD (parking lot, ticket booking), say where the shared state is and which lock protects it.

First principle. A class is thread-safe if it behaves correctly when accessed from several threads at once, with no extra coordination by callers. Trouble needs three ingredients together: shared, mutable state, accessed by multiple threads. Remove any one and the problem vanishes. So the ladder of preference is about removing ingredients.

Three classic bugs, each with a small example.

  1. Check-then-act race. if (!map.containsKey(k)) map.put(k, load(k)). Two threads both see "absent" and both load. Use map.computeIfAbsent(k, this::load), which does the check and the put atomically for a ConcurrentHashMap.
  2. Read-modify-write on a counter. count++ is read, add, write; two threads can lose an update. Use AtomicLong.incrementAndGet(), or LongAdder under heavy contention.
  3. Visibility. Without volatile or a lock, a thread may never see another thread's write to a flag. volatile boolean running fixes visibility but not compound actions.

Locking rules that keep you safe.

  • Guard every access (reads too) to a shared variable with the same lock.
  • One lock per invariant: if two fields must change together (balance and lastUpdated), they share one lock.
  • Keep critical sections short, and never call unknown code (callbacks, I/O) while holding a lock.
  • Take multiple locks in a fixed global order to avoid deadlock (transfer from A to B: lock lower account id first).
  • Do not expose the lock (synchronized(this) lets outsiders interfere). Prefer a private lock object.

Document the policy. Mark classes with an annotation or Javadoc: "immutable", "thread-safe", "not thread-safe, confined to the request thread", "guarded by lock". In a design interview, say where the shared state is and which mechanism protects it. Mention higher-level options too: a single-writer thread with a queue, or optimistic concurrency with a version column when the shared state is in a database.

Remember: avoid shared mutable state first. If you must share it, use one lock or one atomic operation per invariant.

What is an anemic domain model, and what is the alternative? Senior

An anemic model has entities that are only data (fields, getters, setters) while all the business rules live in service classes. The alternative is a rich domain model, where the entity owns its rules and protects its own invariants, so an Account refuses a withdrawal that overdraws it. The anemic version works for simple CRUD, but rules spread across services and anyone can put an object into an invalid state.

// Anemic: any caller can set a negative balance
account.setBalance(account.getBalance() - amt);

// Rich: the rule lives with the data
class Account {
    private long balance;
    void withdraw(long amt) {
        if (amt > balance) throw new InsufficientFundsException();
        balance -= amt;
    }
}

The rich model matches the object-oriented idea of data plus behaviour and makes rules easy to unit test without a database. Anemic is not always wrong: for thin CRUD APIs it is simple and fine. Persistence frameworks like JPA make rich models a little harder because they want a no-argument constructor and mutable fields.

What "anemic" means. The term (Martin Fowler) describes domain objects that look like data holders: fields plus getters and setters, with the logic in OrderService, AccountService and so on. It resembles procedural programming with objects used as data structures. The object has no ability to defend itself.

The practical consequences, with the banking example. Suppose "balance cannot go below zero" is a rule. In the anemic style, the rule lives in AccountService.withdraw(). But five other places also call setBalance() directly (a batch job, an admin screen, an import). Only one of them checks the rule, so invalid state is reachable. In the rich style, the only way to change the balance is account.withdraw(amt), so the rule can never be bypassed, and the setter does not exist.

Characteristics of a rich model.

  • Methods named after business intents (order.cancel(), account.withdraw()), not setStatus(...).
  • Constructors or factories that only create valid objects (no half-built objects).
  • Invariants checked inside the entity, state changes through methods.
  • Services stay thin: load the aggregate, call a method, save, publish events, handle the transaction.

Rich domain model and Domain-Driven Design (DDD) vocabulary. An entity has identity and lifecycle (Order). A value object is immutable and compared by value (Money, Address). An aggregate is a cluster treated as one unit with a root (Order plus its OrderLines), and outsiders may only change it through the root. A domain service holds logic that does not naturally belong to one entity (transfer between two accounts).

When anemic is acceptable. Simple CRUD screens, reporting, integration code, or when the logic is a thin pass-through. Forcing rich models onto a form-over-database app adds ceremony. Choose rich when business rules are many and change often.

Practical friction with JPA. Hibernate wants a no-argument constructor (can be protected) and often field access. Keep setters private or absent, use the protected constructor for the framework, and expose business methods. Keep persistence annotations off your domain model only if you are following hexagonal architecture strictly (then you need mapping code).

Remember: put behaviour with the data it protects. Setters on everything means no invariants.

How do you read a UML class diagram? What do the arrows mean? Basic

A class is a box with three parts: name, fields, methods. The line style tells the relationship. A solid line with a hollow triangle is inheritance (extends). A dashed line with a hollow triangle is implementing an interface. A plain arrow is association (has a reference). A hollow diamond is aggregation (a whole with parts that can live on their own), a filled diamond is composition (parts die with the whole). A dashed open arrow is a dependency (uses temporarily).

Also note visibility signs: + public, - private, # protected. Multiplicity such as 1 or * sits near the line ends. In an interview, a simple sketch with boxes, key fields and these arrows is enough.

Why UML shows up. In design interviews you rarely need strict UML. You need a quick diagram that communicates which classes exist, what they hold, and how they relate. The six relationships cover almost everything, and the interviewer wants to see whether you can tell them apart, especially association versus aggregation versus composition.

How to distinguish the relationships by asking two questions.

  1. Is it a type relationship or an object relationship? Type: inheritance ("is-a") or realization (implements). Objects: association, aggregation, composition, dependency.
  2. For objects, how long does the part live relative to the whole? If the part cannot exist without the whole (a room without its house), it is composition. If it can (a player without a team), aggregation. If it just holds a reference without ownership, association. If it only appears as a parameter or local variable inside one method, dependency.

Explain hexagonal (ports and adapters) architecture. How is it different from classic layered architecture? Senior

In classic layers (controller, service, repository), the dependency arrow goes down, so business logic ends up depending on the database layer. In hexagonal architecture the business core sits in the middle and defines ports (interfaces) for what it needs and offers. Adapters on the outside (REST controller, JPA, Kafka, an HTTP client) implement or call these ports, so every dependency points inward to the domain. This is Dependency Inversion applied to the whole application.

Benefit: the core is tested with plain unit tests and fakes, and a technology change (swap the database or add a message queue) touches only an adapter. Cost: more interfaces and mapping between domain and persistence objects. It is worth it for long-lived business-heavy services, not for a small CRUD app. Clean architecture and onion architecture are close relatives with the same inward dependency rule.

Start with the problem in classic layers. Controller calls Service calls Repository calls Database. Sources depend downward, so the service imports repository classes, which import JPA entities, which carry persistence annotations. The business core is now tied to the persistence technology. To test a business rule you need the persistence layer (or heavy mocking), and to switch databases or expose the same logic through Kafka instead of REST, you touch the middle of the application.

How hexagonal changes it, step by step.

  1. Domain core: entities, value objects and use cases written in plain Java, with no framework imports.
  2. Ports: interfaces the core defines. Inbound (driving) ports say what the app can do (PlaceOrderUseCase). Outbound (driven) ports say what it needs from the world (OrderRepository, PaymentGateway, Clock).
  3. Adapters: technology-specific code on the outside. Inbound adapters (REST controller, Kafka listener, CLI) call inbound ports. Outbound adapters (JPA repository, HTTP client) implement outbound ports.
  4. Wiring: the Spring configuration (or a hand-written main) connects adapters to ports at start-up.

A request traced through. POST /orders hits OrderController (inbound adapter), which maps the JSON DTO to a command and calls PlaceOrderUseCase.place(cmd). The use case loads and creates the domain Order, applies rules, calls the outbound port OrderRepository.save(order). At runtime that is JpaOrderRepositoryAdapter, which maps the domain order to a JPA entity and saves it. The core never saw JSON or SQL.

Practical Spring approach: keep packages domain, application, adapter.in, adapter.out and add an ArchUnit test that fails when the domain imports Spring or JPA.

When not to use it. A small CRUD service, a prototype, or a team unfamiliar with it. The mapping layers add code and can be mistaken for bureaucracy. A pragmatic middle path: layered architecture, but with repository interfaces defined in the service layer's package (DIP only where it matters).

What are Repository, DAO, DTO and Service Layer? How do they differ? Intermediate

A DAO (Data Access Object) wraps database operations for a table, in a technical style such as insert and findById. A Repository is similar but speaks the domain's language, as a collection of aggregates: orders.findPendingFor(customer). A DTO (Data Transfer Object) is a plain data carrier shaped for the API or a call across a boundary. The service layer holds the use-case logic and coordinates repositories, with the transaction boundary.

  • Entity: the domain or persistence object (has identity).
  • DTO: what goes over the wire, so API shape can change without changing the entity, and internal fields (password hash) are not leaked. Java records suit this well.
  • Repository vs DAO: in practice Spring Data's JpaRepository plays both roles. The conceptual difference is domain-oriented collection (Repository) versus table-oriented gateway (DAO).
  • Service: placeOrder() with @Transactional: load, apply rules, save. Controllers stay thin.

Why there are so many words. They each answer "where does this kind of code live?" so that SQL does not appear in controllers and JSON shapes do not leak into the database model. Think of a request going down and back up: DTO arrives from the client, the controller maps it and calls the service, the service loads an entity through a repository, applies rules, saves it, and a DTO goes back out.

Why not return entities from controllers? Four reasons. (1) Leaking: sensitive fields (password hash, internal flags) can slip into JSON. (2) Coupling: renaming a column changes your public API and breaks clients. (3) Lazy loading: a lazy collection serialised outside the transaction throws LazyInitializationException or triggers N+1 queries. With Spring Data JPA the interface OrderRepository extends JpaRepository<Order, Long> is generated at runtime, and most teams use the word "repository" for it.

Transaction placement. Put @Transactional on service methods that represent one business operation, not on controllers or on every repository call. Keep controllers thin: parse, validate, call, map.

Pitfall. A "service layer" that just forwards each call to the repository adds noise. If a service method has no rule or orchestration, question why it exists, but keep it if it marks a clean transaction or security boundary.

Remember: Controller maps DTOs, Service runs the use case, Repository stores entities.

What makes code easy to unit test, in terms of design? Intermediate

Code is easy to test when its dependencies are passed in, not created inside, and when it does little hidden work. That means constructor injection, interfaces for slow or external things (database, clock, HTTP), no static calls to those things, and small classes with one job. If a test needs a real database or 11 mocks, the design is telling me something is wrong.

// Hard to test: hidden new, hidden clock
class TokenService { boolean valid(Token t) { return t.expiry().isAfter(Instant.now()); } }

// Easy: the clock is injected, the test fixes the time
class TokenService {
    private final Clock clock;
    TokenService(Clock c) { clock = c; }
    boolean valid(Token t) { return t.expiry().isAfter(clock.instant()); }
}

Typical blockers: new inside business methods, Singleton.getInstance(), static utility calls with side effects, LocalDateTime.now() and Random inside logic, and long methods mixing I/O with decisions. A useful split: pure logic in one class (tested with plain inputs), I/O in another (tested lightly or with integration tests). Mock only what you own across a boundary. Too many mocks means too much coupling.

What a unit test needs. To test a class alone you must be able to (1) construct it cheaply, (2) replace everything it talks to with a fake, (3) control inputs such as time and randomness, and (4) observe the result. Design that blocks any of the four makes tests slow, flaky or impossible.

The seams, one by one.

  • Constructor injection: lets a test pass fakes. Hidden new inside a method removes the seam.
  • Interfaces at I/O boundaries: a PaymentGateway interface lets a test return "declined" on demand, which a real vendor sandbox cannot do reliably.
  • Injected Clock: Clock.fixed(Instant.parse("2025-01-01T00:00:00Z"), ZoneOffset.UTC) makes expiry logic deterministic. Same for a Supplier<UUID> or Random seed.
  • Small methods returning values (pure functions): inputs in, output out, no mocks needed.

Functional core, imperative shell. Keep decisions in pure code (Decision decide(Order o, Stock s)) and put I/O at the edges (read stock, call decide, write the result). The core is tested with a table of inputs; the shell with a few integration tests.

Test doubles, named properly. A stub returns canned answers. A fake is a simple working implementation (an in-memory repository). A mock records calls and verifies them (Mockito). A spy wraps a real object. Prefer stubs and fakes for state-based tests: assert on outcomes, not on which methods were called, because over-verified mocks break whenever you refactor. Count of mocks needed is a design metric: more than three or four suggests too many dependencies.

Static and final traps. Static helpers with side effects (EmailUtil.send) cannot be replaced without special tools. Mockito can mock statics and final classes in newer versions, but needing it is a smell, not a goal. Wrap statics behind an injected interface.

Do not damage design for tests. Do not make private methods public just to test them: test through the public behaviour, or extract the logic into its own class and test that. And remember the test pyramid: many fast unit tests, fewer integration tests (real database via Testcontainers), and few end-to-end tests.

Remember: inject dependencies, including the clock and randomness. Hard-to-test code is a design smell, not a testing problem.

7. LLD exercises

What is your step-by-step approach in a low-level design interview? Basic

I go in five steps, out loud. First clarify requirements and scope with questions. Then list the core entities (nouns) and the actions (verbs). Then draw classes with relationships, and pick patterns only where something will vary. Then write the key class and the main flow in code. Finally I discuss concurrency, extensibility and what I would change for scale.

  1. Requirements (3 to 5 minutes): who uses it, what are the must-have features, what is out of scope, rough scale, concurrency needs. State assumptions.
  2. Entities and APIs: nouns become classes (Vehicle, Ticket), verbs become methods (park(), exit()). Define the main public interface first.
  3. Class design: relationships (has-a, is-a), interfaces for parts that vary (pricing, allocation), enums for fixed sets.
  4. Code the core: clean, small classes, no giant methods. Show the one hard algorithm (LRU eviction, seat locking).
  5. Discuss: thread safety, edge cases (full, duplicate, failure), and extensions ("add a new vehicle type", "dynamic pricing") to show Open/Closed in action.

Common mistakes: jumping to code without clarifying, using a pattern for every box, ignoring concurrency, and money in double (use long paise or BigDecimal).

What the interviewer is actually grading. Not whether you remember the "official" parking lot. They watch: do you ask before building, do you model the nouns sensibly, do you isolate what will change, do you notice concurrency and failure, and can you explain trade-offs while coding. A clean small design that you can extend live beats a sprawling one.

The five steps in more detail, with a worked mini example ("design a parking lot").

  1. Clarify (write answers on the board). Questions: single building or many? Vehicle types? Fixed rate or by time? Do we need payment? Multiple entrances? Reservations? Expected size and concurrency? Write the agreed list as "in scope" and "out of scope" so you cannot be accused of missing something later.
  2. Entities and verbs. From the requirements pull nouns: ParkingLot, Floor, Slot, Vehicle, Ticket. Verbs: park, exit, pay, find free slot. Decide who owns each verb: ParkingLot.park() orchestrates, Slot.occupy() changes slot state, PricingStrategy.fee() computes money.
  3. Relationships and variation points. Draw the class diagram. For each box ask: "will this vary?" Pricing yes (hourly now, flat on weekends later) so make it an interface. Vehicle types are a small fixed set, so an enum is fine. Avoid inheritance for things that differ only by data.
  4. Code the heart. Write the public method signatures first, then the one interesting algorithm in full. Do not write every getter. Narrate decisions: "I use a map here for O(1) lookup".
  5. Stress it. Walk through three scenarios: the happy path, an edge case (lot is full, exit with a lost ticket), and a concurrency case (two cars, one free slot). Then offer extensions and say what you would change at scale (database, caching, distributed locks).

Handy checklists.

  • Edge cases: null or empty input, duplicates, full or empty capacity, invalid state transitions, timeouts, partial failure in the middle of a multi-step operation.
  • Concurrency: what is shared, which operation must be atomic, which lock or atomic variable protects it, and how to avoid holding it while doing slow work.
  • Money and time: integer minor units or BigDecimal, an injected Clock, and time zones.
  • Extensibility: "How would you add X?" should be answered with "add a class, no edit to existing code" at least once.

Time budget for a 45-minute round: about 5 clarifying, 10 design and diagram, 20 code, 10 discussion. If the interviewer interrupts with a different direction, follow them: they are showing you what they care about.

Remember: clarify, entities, classes, code the core, then concurrency and extension. Talk throughout.

Design a parking lot. Senior

I model a ParkingLot with floors, each with typed slots (bike, car, truck), plus Ticket, Vehicle, and two replaceable policies: a SlotAllocationStrategy (nearest to entrance) and a PricingStrategy (hourly rate). park(vehicle) finds a free slot of the right type and issues a ticket. exit(ticket) computes the fee and frees the slot. The hard part to call out is that two entry gates must not allocate the same slot.

Ticket park(Vehicle v) {
    synchronized (allocationLock) {                       // two gates must not pick the same slot
        Slot s = allocation.find(floors, v.type())        // strategy
                 .orElseThrow(() -> new LotFullException(v.type()));
        s.occupy(v);
        return new Ticket(UUID.randomUUID().toString(), s, Instant.now());
    }
}
long exit(Ticket t) {
    long fee = pricing.fee(t.entryTime(), Instant.now(), t.slot().type());   // strategy
    t.slot().free();
    return fee;
}

Concurrency: a single lock is simplest, but it serialises all gates. Better: per-slot compare-and-set (AtomicBoolean.compareAndSet) or a lock per slot type. Extensions I would mention: EV charging slots (a new slot type), reserved slots, a payment step on exit, a display board (Observer on slot count changes). Keep the fee as long paise, not double.

Requirements I would confirm first. Multiple floors; vehicle types bike, car, truck mapped to slot types; one or more entry and exit gates; ticket on entry; fee on exit based on duration and vehicle type; display of free slots per floor. Out of scope unless asked: reservations, payment gateway details, license-plate recognition.

Walk through a day in the life.

  1. A car arrives at gate 1. park(car) asks the SlotAllocationStrategy for a free CAR slot (say nearest to the entrance, floor 0 slot 12).
  2. The slot is marked occupied, a Ticket(id, slot, entryTime) is created and handed back.
  3. Later the driver reaches the exit. exit(ticket) computes duration, asks PricingStrategy.fee(...), frees the slot and returns the fee. Example: entry 10:00, exit 12:30, rate 20 per hour with a part-hour rounded up: 3 hours times 20 equals 60.

Making the allocation fast. Scanning all slots is O(slots). Keep a structure of free slots per type: for the "nearest" policy, a PriorityQueue or TreeSet ordered by (floor, slot number) per slot type. Allocation is then pollFirst(), O(log n), and freeing is add. This is also a natural lock scope: one lock per slot-type structure instead of one for the entire lot.

A bigger vehicle in a smaller slot (policy: car in a truck slot allowed? ask). Double exit with the same ticket (mark ticket used; make exit idempotent or reject). Remember: entities plus two strategies (allocation, pricing). The interview trap is concurrent allocation of the same slot.

Design an LRU cache with O(1) get and put. Intermediate

I combine a hash map for O(1) lookup with a doubly linked list that keeps entries in order of recent use. The map goes from key to list node. On get or put I move the node to the head, and when the cache is over capacity I remove the tail, the least recently used. Both pieces are needed: the map alone has no order, and the list alone has O(n) lookup.

class LRUCache<K, V> {
    private class Node { K k; V v; Node prev, next; Node(K k, V v){this.k=k;this.v=v;} }
    private final int cap;
    private final Map<K, Node> map = new HashMap<>();
    private final Node head = new Node(null, null), tail = new Node(null, null);   // sentinels
    LRUCache(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }

    synchronized V get(K k) {
        Node n = map.get(k); if (n == null) return null;
        unlink(n); addFirst(n); return n.v;
    }
    synchronized void put(K k, V v) {
        Node n = map.get(k);
        if (n != null) { n.v = v; unlink(n); addFirst(n); return; }
        if (map.size() == cap) { Node lru = tail.prev; unlink(lru); map.remove(lru.k); }
        n = new Node(k, v); map.put(k, n); addFirst(n);
    }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFirst(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}

The dummy head and tail nodes remove all null checks. Shortcut worth naming: LinkedHashMap with accessOrder=true and an overridden removeEldestEntry is a ready-made LRU. Thread safety: synchronized is fine to start, because even get mutates the list. For high concurrency use a production library such as Caffeine. Add TTL by storing an expiry time per node.

Why the combination is needed, in a table.

NeedHashMap aloneLinked list aloneBoth together
Find a key fastO(1)O(n) scanO(1)
Know the least recently usedNo orderTail of the listTail of the list
Move an item to "most recent"no conceptO(1) only if you hold the node (and it is doubly linked)O(1): map gives the node

Why the list must be doubly linked. To remove a node from the middle in O(1) you must update its neighbours' pointers, so you need the predecessor. A singly linked list would need an O(n) walk to find it. That is the key insight to say aloud.

A trace with capacity 2.

  1. put(A,1): list is head, A, tail.
  2. put(B,2): list is B, A (B newest). Cache is full.
  3. get(A): map finds node A, we unlink and re-insert it at the front: list is A, B.
  4. put(C,3): size equals capacity, so evict the tail node B (remove from list and from map by lru.k), then add C: list is C, A.
  5. get(B): miss, returns null.

Remember to store the key in the node. When evicting the tail node you must also delete it from the map, so the node needs its key. Forgetting this is the most common bug.

The shortcut.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int cap;
    LruCache(int cap) { super(16, 0.75f, true); this.cap = cap; }      // true = access order
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) { return size() > cap; }
}

Say "I would use this in production, but the interviewer asked me to build it, so here is how it works inside." Wrap with Collections.synchronizedMap for basic thread safety.

Concurrency and scale. Because get reorders the list, even reads write, so a read-write lock does not help. Options: a single lock (fine for modest load), lock striping across several smaller LRU segments by key hash (how some caches shard), or approximate LRU with sampling or a clock algorithm (used when exact order is not required). Caffeine uses a different design (Window TinyLFU with buffered access recording) to scale reads, so mention it as the production answer.

Extensions. TTL (store expiry in the node, drop on access and with a sweeper), LFU (needs frequency buckets: a map from frequency to list), write-through or write-back to a database, and cache statistics (hit rate). Cache stampede (many threads miss the same key at once) is solved by computing per key under a lock or with computeIfAbsent.

Remember: HashMap plus doubly linked list gives O(1). Map finds the node, list gives order. get also changes order.

Design a rate limiter (class level). Which algorithms exist? Senior

I would expose one interface, boolean allow(String key), and keep the algorithm behind it as a Strategy. The one I implement by default is the token bucket: each key has a bucket that refills at a fixed rate, each request takes one token, and an empty bucket means reject. It allows short bursts but enforces the average rate, and needs only two numbers of state per key.

AlgorithmHowTrade-off
Fixed window countercount per time window, reset at the boundarysimple, but up to 2x the limit can pass around a boundary
Sliding window logstore a timestamp per requestexact, but memory per request
Sliding window counterweighted blend of current and previous windowcheap, close enough

Leaky bucketqueue drained at a fixed ratesmooths output, delays requests
class TokenBucket {
    private final long capacity; private final double refillPerNano;
    private double tokens; private long last = System.nanoTime();
    TokenBucket(long capacity, double perSecond) { this.capacity = capacity; this.tokens = capacity; this.refillPerNano = perSecond / 1e9; }
    synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) * refillPerNano);   // lazy refill, no timer thread
        last = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
class RateLimiter { private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    boolean allow(String key) { return buckets.computeIfAbsent(key, k -> new TokenBucket(10, 5)).tryAcquire(); } }

Key design points: refill lazily on each call (no background thread), lock per bucket not globally, and evict idle keys so the map does not grow without bound. Across many servers the state must be shared, usually in Redis with an atomic Lua script, trading a network hop for a global limit. Return HTTP 429 with a Retry-After header.

What the problem is. Limit how often a client (user id, API key or IP) may call something, for example 100 requests per minute, to protect a service from abuse and overload. The class must answer "may this request go through right now?" very quickly, for many keys at once, from many threads.

Clarify first. Per user, per IP, or global? Hard limit or just shaping? Single node or distributed? What should the caller see when blocked (reject with HTTP 429, queue, or delay)? What burst is acceptable?

Token bucket, walked through with numbers. Bucket capacity 10, refill rate 5 tokens per second, starting full.

  1. t = 0: a client sends 10 requests at once. They take 10 tokens and all pass. Bucket is empty. This is the allowed burst.
  2. t = 0.1 s: request 11 arrives. Lazy refill adds 0.1 times 5 = 0.5 tokens, which is less than 1, so it is rejected.
  3. t = 0.2 s: refill brings it to 1.0 token, so one request passes.
  4. Long-run average cannot exceed 5 per second, whatever the pattern.

Sliding window counter, in one example. Limit 100 per minute. At second 15 of the current minute, the previous minute had 80 requests and the current has 30. Weighted estimate: 80 times (45/60) plus 30 equals 90. Under 100, so allow. It needs only two counters per key and smooths the boundary problem, at the cost of being approximate.

Choosing.

NeedPick

Simplest thing, boundary spikes acceptableFixed window counter

Distributed version. Local buckets are enough when traffic is sticky to one node or the limit is per node. For a global limit across N servers, keep the state in Redis. A check-and-decrement must be atomic, so run a Lua script (or use INCR with EXPIRE for fixed window). The cost is one network round trip per request. A common compromise: each node takes a batch of tokens from Redis and spends locally (less accuracy, much less traffic).

Design details. Make the algorithm a Strategy behind RateLimiter.allow(key), with limits looked up per plan (free versus paid) from configuration. Use a monotonic clock (System.nanoTime), not wall-clock time, so clock changes do not break refills. Evict idle buckets (a cache with expire-after-access) so a flood of unique keys cannot exhaust memory. Return headers such as Retry-After and the remaining count. Decide fail-open (let traffic through if the limiter store is down) or fail-closed, and say why.

Remember: token bucket = bursts allowed, average enforced, lazy refill. Fixed window leaks 2x at the boundary.

Design an elevator system. Senior

I model an ElevatorController that receives hall calls (floor and direction) and assigns each to the best Elevator. Each elevator is a state machine (IDLE, MOVING_UP, MOVING_DOWN, doors open) with a set of stops. The scheduling idea is SCAN (the "LOOK" variant): keep going in the current direction, serving stops on the way, reverse only when nothing is left ahead.

class Elevator {
    private int floor; private Direction dir = Direction.IDLE;
    private final TreeSet<Integer> up = new TreeSet<>(), down = new TreeSet<>(Comparator.reverseOrder());
    synchronized void addStop(int f) { if (f > floor) up.add(f); else if (f < floor) down.add(f); }
    synchronized void step() {                          // called each tick
        if (dir == Direction.UP || (dir == Direction.IDLE && !up.isEmpty())) {
            Integer next = up.ceiling(floor);
            if (next == null) { dir = down.isEmpty() ? Direction.IDLE : Direction.DOWN; return; }
            floor++; if (floor == next) { up.remove(next); openDoors(); }
        } else { /* mirror image for DOWN */ }
    }
}

Why SCAN: it avoids starvation and is efficient, like a disk head. Plain FCFS zig-zags. Interview extras: separate inside-car button presses from hall calls, an overload sensor, maintenance mode, and priority or express elevators (a new dispatch strategy). The controller can notify displays through Observer. I would run one thread per elevator or a single scheduler tick, with the stop sets protected by the elevator's lock.

Clarify the problem first. How many elevators and floors? Is there one hall call button per floor with up and down, or destination dispatch (you enter the target floor in the lobby)? Capacity limits? Express or service elevators? Out of scope usually: real-time physics, door safety hardware.

Entities. ElevatorController (scheduler), Elevator (state, floor, stops), Request (floor, direction), Direction and ElevatorState enums, and a DispatchStrategy interface.

SCAN walked through. Elevator at floor 3 moving up with up-stops {5, 8} and down-stops {2}.

  1. It moves 3 to 4 to 5, opens doors at 5, removes 5 from the up set.
  2. It continues to 8, stops, removes 8. Up set is empty.
  3. Now it reverses to DOWN and serves 2.
  4. If a new request for floor 6 (going up) arrives while at 4, it is added to the up set and served on the way. A request for floor 3 while moving up goes to the down set and waits for the return trip.

This is the disk-scheduling idea (SCAN, "LOOK" variant that reverses at the last request, not at the building end). FCFS (first come first served) would zig-zag between floors, and nearest-first can starve far floors.

Choosing which elevator takes a hall call. Simple cost function: for each elevator compute a score, then pick the lowest. Examples: idle elevator, cost = distance. Elevator moving toward the caller in the same direction, cost = distance. Moving away or in the opposite direction, cost = distance to its last stop plus the return distance. Plug this in as a DispatchStrategy, so you can swap in zoning or load balancing later.

Two kinds of input. Hall calls (outside buttons: floor plus direction) go through the controller. Cabin calls (inside buttons: target floor) go straight to that elevator's stop sets. Mixing them up is a common design slip.

State machine. IDLE, MOVING_UP, MOVING_DOWN, DOORS_OPEN, plus MAINTENANCE and EMERGENCY. Illegal moves (opening doors while moving) are excluded by the state design (State pattern). Door timers, overload sensors and a fire mode that overrides the schedule are good extension points.

Concurrency. Requests arrive from many threads (buttons) while a tick thread moves the elevators. Protect each elevator's stop sets with its lock (or funnel all events into one scheduler thread through a queue, so the model is single-threaded and lock-free). The second is easier to reason about. Mention that the controller must not hold its own lock while calling into an elevator, to avoid deadlock.

Remember: controller dispatches, each elevator is a state machine with sorted up and down stops. SCAN means finish the direction, then reverse.

Design a vending machine (or an ATM). Intermediate

It is a textbook State pattern problem. The machine has states Idle, HasMoney, Dispensing and OutOfService, and each state decides what insertCoin, selectItem, cancel and dispense do. Separate classes hold the inventory (item to slot, price, quantity) and the cash handling. An ATM has the same shape: Idle, CardInserted, PinVerified, Transaction.

interface MachineState { void insertCoin(Machine m, int amt); void select(Machine m, String code); void cancel(Machine m); }
class IdleState implements MachineState {
    public void insertCoin(Machine m, int amt) { m.addBalance(amt); m.setState(new HasMoneyState()); }
    public void select(Machine m, String c)  { throw new IllegalStateException("Insert money first"); }
    public void cancel(Machine m)            { /* nothing to refund */ }
}

Points to add: check stock and balance before dispensing, return change using a greedy coin algorithm (fine for standard denominations), make dispensing atomic with the stock update, and keep money in integer paise. Extensions: new payment types (Strategy), restock and admin mode (a new state), low-stock alerts (Observer).

Why State and not an if-chain. Four actions (insert coin, select item, cancel, dispense) times four states gives sixteen combinations to reason about. With an if-chain, each action method has to check the state and every new state edits every method. With State objects, each state class answers all four actions in one place, and the illegal combinations are explicit (select in Idle throws "insert money first").

A full purchase, walked through. Item A1 costs 30 (tracked in paise as 3000).

  1. State Idle. User inserts 20 (2000). Idle.insertCoin adds to balance and moves to HasMoney.
  2. User inserts another 20, balance 4000. HasMoney.insertCoin adds to balance, stays in HasMoney.
  3. User selects A1. HasMoney.select checks stock (quantity above 0) and price (balance at least 3000). Both fine, so move to Dispensing.
  4. Dispensing decrements stock, releases the item and returns change of 1000, then goes back to Idle and resets the balance.
  5. If the user pressed cancel instead of select in step 3, HasMoney.cancel refunds 4000 and returns to Idle.

Other classes. Inventory (item code to ItemSlot with item, price, quantity), CoinChanger (what denominations are available for change), Machine (context holding current state, balance, inventory). If the machine cannot make exact change, refuse the sale before dispensing, which is the case people forget. The greedy coin algorithm is correct for standard denominations (1, 2, 5, 10...) but not for arbitrary ones, where dynamic programming is needed.

ATM variation. States: Idle, CardInserted, PinVerified, SelectingTransaction, Dispensing, plus OutOfService. Extra rules: lock the card after three wrong PINs, never log the PIN, cash dispenser has denominations and a limit, and the debit plus dispense must be consistent: debit first with a pending marker, dispense, then confirm, and reverse the debit if dispensing fails. Talk to the bank through an interface (Adapter) and make bank calls idempotent with a transaction id.

Concurrency. A single physical machine handles one user at a time, so a lock around the machine's methods is enough. For a networked ATM backend, concurrency moves to the account (database transaction with a row lock or optimistic version check).

Remember: vending machine and ATM mean State pattern. Each state class handles the actions and picks the next state.

Design tic-tac-toe, and then explain how you would extend the design to chess. Intermediate

For tic-tac-toe I use Game, Board, Player and a WinChecker. The trick that shows depth is O(1) win detection: keep a counter per row, column and both diagonals, and after each move check if one reaches N. For chess, the board grid stays, but each piece type becomes a class that knows its own legal moves (polymorphism), and rules like check and turn order live in the game.

class Board {
    private final int n; private final int[] rows, cols; private int diag, anti;
    Board(int n) { this.n = n; rows = new int[n]; cols = new int[n]; }
    boolean move(int r, int c, int player) {          // player is +1 or -1, returns true if this move wins
        int d = player;
        rows[r] += d; cols[c] += d;
        if (r == c) diag += d;
        if (r + c == n - 1) anti += d;
        return Math.abs(rows[r]) == n || Math.abs(cols[c]) == n || Math.abs(diag) == n || Math.abs(anti) == n;
    }
}

Checking every row, column and diagonal after every move is O(n) or O(n squared), the counter trick is O(1). Also validate the cell is empty and the game is not already over.

For chess: an abstract Piece with List<Move> legalMoves(Board), implemented by Knight, Bishop and so on (each is a small Strategy for movement). A Move object records from, to and captured piece, which also makes undo (Command) and move history easy. Check, checkmate, castling and en passant are rules in a Game or RulesEngine class, because they need knowledge of the whole board, not one piece.

Tic-tac-toe, in order.

  1. Requirements: NxN board (default 3), two players alternate, win by N in a row, column or diagonal, draw when the board is full.
  2. Classes: Game (turn order, status), Board (cells, move validation), Player (name, symbol), Move, GameStatus enum (IN_PROGRESS, WON, DRAW).
  3. Flow of play(r, c): reject if game over, cell outside the board, or cell not empty. Place the symbol. Check for win. If board full and no win, draw. Otherwise switch player.

Why the counter trick works. Give player X the value +1 and O the value -1. Keep running sums for each row, each column and the two diagonals. A line is complete only if all N cells have the same player, which means its sum is exactly +N or -N. Example 3x3: X plays (0,0), (0,1), (0,2). rows[0] goes 1, 2, 3. When it hits 3, X wins. If O had played (0,1), rows[0] would have been 1, 0, 1 and never reaches 3. Each move updates at most four counters and checks four values, which is O(1) per move instead of scanning N cells.

Extensions to mention: a bot player (Strategy: random, or minimax with alpha-beta for 3x3), undo (Command), spectators and score board (Observer), and a game over state that rejects further moves (State).

Chess, how to think about it.

  • Entities: Game, Board (8x8 of Cell or a map of position to Piece), Piece (abstract, with colour), six subclasses, Player, Move.
  • Responsibility split: a piece knows its geometry (a bishop moves diagonally, stops at blockers). The game or RulesEngine knows whole-board rules: you cannot make a move that leaves your own king in check, castling needs an unmoved king and rook and no attacked squares in between, en passant needs the previous move, promotion, stalemate, draw by repetition.
  • Legal move generation, two-stage: pieces return pseudo-legal moves, then the engine filters out the ones that leave the king in check by applying the move on a copy and testing for attack.
  • Undo and history: store each Move with captured piece and flags, so undo is applying it in reverse (Command or Memento).

Is polymorphic Piece the best design? It is the expected answer and reads well. Alternatives like data-driven movement tables work too. Say that you start with polymorphism for clarity and optimise (bitboards) only if a chess engine's speed is required, which is far beyond a LLD interview.

Remember: tic-tac-toe wins in O(1) with row, column and diagonal counters. Chess pieces are polymorphic classes that each generate their own moves.

Design a notification service (email, SMS, push). Senior

I define a Channel interface with one implementation per medium (email, SMS, push), a template service to build the message, a user-preference check, and a dispatcher that sends through the right channels. Sending is asynchronous: the caller puts a notification on a queue and a worker delivers it, with retries and a dead-letter queue for failures. New channel means a new class, nothing else changes (Open/Closed).

interface Channel { ChannelType type(); void send(Notification n) throws DeliveryException; }
class Dispatcher {
    void handle(Notification n) {
        for (ChannelType t : prefs.enabledFor(n.userId(), n.category())) {   // user preferences, quiet hours
            try { channels.get(t).send(n); }
            catch (DeliveryException e) { retry.schedule(n, t, backoff(n.attempt())); }   // exponential backoff
        }
    }
}

Points that make it senior-level: idempotency key so a retry does not send twice, per-channel rate limits, templates with localisation, priority (OTP before marketing), delivery status tracking, and a circuit breaker per vendor. Strategy for channels, Factory or a map for lookup, Observer or events to trigger sends.

Requirements to confirm. Channels (email, SMS, push, maybe in-app, WhatsApp). Triggered by events (order shipped) or by a campaign? Volume (thousands per minute or millions per hour)? User preferences and opt-out? Templates and languages? Delivery guarantees (at least once is typical)? Priority (OTP versus promotion)?

The flow end to end, step by step.

  1. A service calls notificationApi.send(userId, "ORDER_SHIPPED", params). This only validates and enqueues, then returns immediately (so business flows are never slowed by a vendor).
  2. A worker takes the message from the queue (separate queues or priority per channel).
  3. It loads user preferences (channels enabled, quiet hours, opt-outs, regulatory rules). Marketing messages obey opt-out; transactional ones such as OTP bypass it.
  4. It renders the template for the user's language with the parameters.
  5. It applies per-user and per-vendor rate limits (do not send 20 pushes in a minute).
  6. It calls the channel adapter (EmailChannel wraps an SMTP or vendor API). On a transient error it retries with exponential backoff and jitter. After N attempts the message goes to a dead-letter queue for inspection.
  7. It records status (QUEUED, SENT, DELIVERED, FAILED) from vendor callbacks, for tracking and support.

Idempotency, explained. Queues and retries are at-least-once, so a worker may process the same message twice (crash after sending but before acknowledging). Give each notification a unique key (userId + eventId + channel), store it in a table or Redis with a unique constraint before sending, and skip duplicates. For vendors that accept an idempotency key, pass it along. Without this, customers get duplicate OTPs and receipts.

Design choices to state. Channel as Strategy (and Adapter around each vendor). A fallback chain (push first, then SMS if undelivered) as a Chain of Responsibility. Priority queues so OTPs jump marketing traffic. Circuit breaker per vendor so a failing SMS provider does not fill your threads, with failover to a second provider. Bulk campaigns processed through a separate pipeline so they cannot starve transactional messages.

Class sketch. NotificationService (API), Notification (immutable message), Channel interface plus three implementations, TemplateEngine, PreferenceService, Dispatcher worker, RetryPolicy, DeliveryStatusRepository.

Scale answer. Kafka or a managed queue partitioned by user id (keeps order per user), stateless workers scaled horizontally, and database writes for status batched. Never send inside the request thread of the business service.

Remember: channel interface, async queue, retry with backoff and dead-letter, idempotency key to avoid duplicates.

Design BookMyShow (a movie ticket booking system). Senior

The entities are City, Theatre, Screen, Movie, Show, Seat, Booking and Payment. The real problem is that two users must never book the same seat. I solve it with a two-step flow: temporarily hold the seats for a few minutes with an expiry, then confirm the booking after payment. The hold-then-confirm step must be atomic per show and seat.

boolean holdSeats(Show show, List<String> seatIds, String userId) {
    synchronized (show) {                                         // one lock per show, not global
        for (String id : seatIds) if (!show.seat(id).isAvailable()) return false;   // all or nothing
        Instant until = Instant.now().plus(Duration.ofMinutes(5));
        seatIds.forEach(id -> show.seat(id).hold(userId, until));
        return true;
    }
}

Treat an expired hold as available when checking (lazy expiry), plus a cleanup job. In a real multi-server system the lock is not a Java synchronized: use a database row lock or an optimistic version check (UPDATE seat SET status='HELD' WHERE id=? AND status='AVAILABLE', success only if 1 row changed), or a Redis lock with TTL. Search and browse are read-heavy and cacheable. Seat selection and booking need strong consistency. Pricing per seat type is a Strategy, and booking confirmation is an event that triggers notifications (Observer).

The domain model, briefly. A City has Theatres; a theatre has Screens; a screen has fixed Seat layout. A Show is a movie playing on a screen at a time, and the availability lives per show: ShowSeat(show, seat, status, price). Do not store "booked" on the physical Seat, because the same seat is free for the 6 pm show and taken for the 9 pm one. This split of physical seat and seat in a show is a classic point interviewers listen for.

The booking flow, step by step.

  1. User browses shows (read-heavy, cached, no locking).
  2. User picks seats: holdSeats(show, seats, user). Atomically check every seat is AVAILABLE (or its hold has expired) and mark all HELD with an expiry, say 5 minutes. All or nothing: if one seat is gone, none are held and the user is told.
  3. User pays. The payment flow runs outside the lock, because it is slow.
  4. On payment success: confirm(bookingId) moves the seats HELD to BOOKED, but only if the hold still belongs to this user and has not expired. Then issue the ticket and notify.
  5. On failure or timeout: release the seats back to AVAILABLE (the cleanup job or lazy expiry).

Making the hold atomic in a real system. A single conditional SQL statement is the most robust approach:

UPDATE show_seat
   SET status = 'HELD', held_by = :user, hold_until = now() + interval '5 minutes'
 WHERE show_id = :show AND seat_id IN (:seats)
   AND (status = 'AVAILABLE' OR hold_until < now());
-- success only if affected rows == number of seats; otherwise roll back

It relies on the database to arbitrate between concurrent users (row locks). Alternatives: SELECT ... FOR UPDATE on the seat rows (pessimistic), a version column (optimistic, retry on conflict), or a Redis SET key value NX EX 300 per seat (fast, but you must also keep the database authoritative). To avoid deadlock when users select overlapping seats, lock seats in a consistent order (sorted by seat id).

Payment edge cases. The hold expires while the payment is in flight: the money was charged but the seat is gone. Handle by extending the hold when payment starts, and by an automatic refund path if confirm fails. Payment callbacks can be duplicated, so make confirm idempotent by booking id.

Scale and fairness. A hot release (a big film opening) makes thousands of users fight for the same seats. A virtual waiting room or queue in front of the seat map, rate limiting, and sharding by show id help. Seat map reads can be served from cache with a short TTL, while holds always go to the source of truth.

Patterns. Strategy for pricing (weekend, seat tier), State for seat or booking status, Observer for post-booking notifications, Facade as BookingService, Factory for payment methods.

Remember: hold seats with a timeout, confirm after payment, and make the hold atomic (lock per show or conditional DB update).

Design Splitwise (shared expenses). Senior

The core model is User, Group, Expense and a balance table that stores who owes whom. An expense has a payer and a split rule, so I make the split a Strategy: equal, exact amounts, or percentage. After each expense, I update the pairwise balances. "Simplify debts" then reduces many small debts to few transfers.

interface SplitStrategy { Map<String, Long> split(long totalPaise, List<String> users, Map<String, Long> params); }
class EqualSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<String> users, Map<String, Long> p) {
        long share = total / users.size(), rem = total % users.size();
        Map<String, Long> out = new LinkedHashMap<>();
        for (String u : users) out.put(u, share + (rem-- > 0 ? 1 : 0));   // spread leftover paise, so sum is exact
        return out;
    }
}
void addExpense(String payer, long total, SplitStrategy s, ...) {
    s.split(...).forEach((user, owed) -> { if (!user.equals(payer)) balances.add(user, payer, owed); });
}

Details that matter: store money as long paise (never double) and distribute rounding leftovers so the shares sum to the total. Balances can be a map per user pair, or just net per user for simplification. Concurrency: expenses in a group touch shared balances, so lock per group or use DB transactions. Extras: settle up as a negative expense, expense history (immutable records), multi-currency, and notifications through Observer.

Requirements. Users, groups, add an expense paid by one or more people and shared by some, three split types (equal, exact, percent), show balances ("you owe X 300"), settle up, and simplify debts within a group.

The data model. Balances can be stored as a pairwise map (owes[A][B]) or, more simply, as a net balance per user in the group: positive means others owe you, negative means you owe. The expense is also stored immutably (payer, total, splits, date, description) so the history can be shown and corrected.

Walk through a trip. Alice pays 900 for dinner for Alice, Bob and Carol, split equally.

  1. Equal split: 300 each.
  2. Alice paid 900 but only owes 300, so net +600. Bob owes 300 (net -300). Carol owes 300 (net -300).
  3. Next, Bob pays 300 for a cab shared equally: each share 100. Bob net becomes -300 + 300 - 100 = -100. Alice net 600 - 100 = +500. Carol -300 - 100 = -400.
  4. Simplification: the largest debtor Carol (-400) pays the largest creditor Alice (+500) 400. Then Bob (-100) pays Alice 100. Two transfers settle everything instead of tracking each expense.

Why the heaps approach works. Net balances always sum to zero. Repeatedly matching the largest creditor with the largest debtor settles at least one person completely each round, so at most (n - 1) transfers. It is not guaranteed to be the minimum possible (that problem is NP-hard in general, equivalent to a subset-sum style partition), but it is good and simple. Say that you would not claim optimality.

Rounding. 100.00 split three ways is 33.33 + 33.33 + 33.34. Work in minor units (paise) with long, give the remainder to the first few people as in the code, so the shares always add to the total. For percentage splits, validate that percentages sum to 100, and for exact splits that amounts sum to the total.

Other design points. The payer is also a participant who may owe themselves part of the total (skip self-debt). Multiple payers are supported by treating each contribution as a credit. Expenses should be append-only; to edit one, add a reversing entry (an accounting habit that keeps the audit trail). Settlements are simply expenses where one person pays another directly. Concurrency: updates to a group's balances must be atomic (database transaction per expense, or a lock per group), otherwise two simultaneous expenses can lose an update.

Patterns. Strategy for splits, Factory to pick a split by type, Observer for notifications ("Bob added an expense"), Facade ExpenseService.

Remember: split rule as Strategy, money in integer paise with remainder handling, and simplify debts with two heaps on net balances.

A pricing method has grown into a 400-line if-else chain, and every release adds more branches. What do you do? Intermediate

This is the Strategy refactor: each branch becomes a small class behind a PricingRule interface, and a lookup picks the right one. I do it in small, test-protected steps, not in one rewrite.

Situation: one method branches on customer type, region, season and coupon. Each release edits it, and bugs appear in unrelated branches.

Check first: are the branches really independent? Is there test coverage? If not, write characterization tests that pin down today's outputs for many inputs, before touching anything.

Fix: extract one branch at a time into a class that implements PricingRule. Register them in a Map<Type, PricingRule> (Spring can inject the map). Replace the chain with rules.get(type).price(order). Run the tests after every extraction. If rules combine rather than exclude each other, use a list of rules applied in order (a Chain).

Prevent: the rule "new pricing case equals new class" in code review. Do not pre-build the abstraction for the first case. Extract when the second variation arrives.

Why a big-bang rewrite fails here. A 400-line pricing method encodes years of business rules, many of them undocumented. A rewrite will silently drop some, and customers find out through wrong invoices. So the safest path preserves behaviour at every step and proves it with tests.

Step by step, with a small example. Suppose the method looks like:

double price(Order o) {
    double p = o.subtotal();
    if (o.customer().type() == GOLD) p *= 0.90;
    if (o.region().equals("IN") && isFestival(o.date())) p *= 0.85;
    if (o.coupon() != null) p -= o.coupon().value();
    return Math.max(p, 0);
}
  1. Characterisation tests. Feed a few hundred real or generated orders (or replayed production samples) through the current code and record outputs as the expected values. These tests assert "what it does now", not "what it should do". They are your safety net.
  2. Name the rules. Each branch becomes a rule: GoldDiscount, FestivalDiscount, CouponRule. Extract each one into its own class behind interface PricingRule { double apply(double price, Order o); }, one commit per rule, tests green after each.
  3. Decide the composition. If rules are exclusive (only one applies), a map keyed by type is enough. If they stack (as above), keep a list and apply them in a defined order, since 10 percent then 15 percent differs from the reverse once a flat coupon is involved. The order must be explicit and tested.
  4. Make the old method a thin loop over the rule list. Delete the dead branches.
  5. Release behind a flag or shadow mode: run old and new code side by side in production, log differences, switch when they match.

Trade-offs to mention. More classes and a bit more indirection, in exchange for isolated tests per rule and no merge conflicts between teams. If only two rules exist and they rarely change, leave the if statement alone (YAGNI). Business-owned rules that change monthly could go to a rules table or a rules engine, but only if non-developers truly need to edit them.

Remember: growing if/else on type means Strategy. Pin behaviour with tests first, then extract one branch at a time.

How do you add a new payment provider (say Razorpay) without touching existing code? Intermediate

If the design is right, I add one new class that implements the PaymentGateway interface and register it as a bean. The checkout code, which only knows the interface, does not change. If I am forced to edit if (provider.equals(...)) chains, the design needs the Open/Closed refactor first.

Check first: does checkout depend on the interface or on provider classes? Is there a switch on provider name anywhere?

Fix: create RazorpayGateway implements PaymentGateway (an Adapter around the vendor SDK that maps requests, responses and errors to my own types). Annotate it as a Spring component with its key, "razorpay". A GatewayRegistry built from Map<String, PaymentGateway> finds it. Add contract tests that every gateway must pass, so a new one is checked against the same expectations.

Prevent: keep vendor types out of the domain, and map vendor errors to a few of my own exceptions (declined, timeout, invalid), so retry logic is provider-independent.

The litmus test. "How many files do I touch to add Razorpay?" With a clean design the answer is two: the new adapter class, and a configuration entry. If the answer includes the checkout service, an enum, a switch and three tests of old providers, the abstraction is leaking.

Step-by-step plan.

  1. Look at the contract. The interface should speak in domain terms: authorize, capture, refund, returning your own result type, not the vendor's. If it currently has vendor-only fields (Stripe's paymentIntentId), generalise with an opaque providerReference string.
  2. Write the adapter. RazorpayGateway implements PaymentGateway. Translate amounts (paise versus rupees), currencies, statuses (captured maps to your SUCCESS), and errors (a vendor timeout maps to your GatewayTimeoutException, a declined card to PaymentDeclinedException).
  3. Register it. A Spring @Component("razorpay"); the registry (Map<String, PaymentGateway>) now contains it. Decide how the right gateway is chosen: by merchant configuration, by customer country, or by a routing rule (also a Strategy).
  4. Contract tests. One abstract test class run against every implementation (against sandboxes or recorded stubs): successful charge, declined card, timeout, duplicate request with the same idempotency key, refund of a partial amount.
  5. Roll out gradually. Feature-flag the provider, route 1 percent of traffic, compare success rates and latency, then increase.

Things that commonly bite. Webhooks: every provider calls back in its own format, so you need an inbound adapter per provider that converts callbacks to your internal events. Idempotency keys: every provider has a different mechanism, so hide it behind the interface. Reconciliation and refunds are provider-specific and often forgotten. Secrets and per-environment credentials belong in configuration, never in the adapter code. And resilience (timeouts, retries only on safe operations, circuit breaker) can be added as a Decorator around any gateway, so it is written once.

Remember: new provider means a new Adapter class plus registration. If you must edit old code, fix the abstraction first.

You inherit a 3,000-line OrderManager god class that everyone is afraid to change. How do you refactor it? Senior

I would not rewrite it. I add tests around the behaviour first, then peel responsibilities out one by one into focused classes, keeping the old class as a thin facade until callers have moved. Each step is small, shipped and reversible.

Situation: one class handles pricing, stock, payments, emails and persistence. Merge conflicts are constant and a change in one area breaks another.

Check first: find the clusters of methods that use the same fields (low cohesion shows as groups). Use change history to see which parts change most. Check what tests exist.

Fix: 1) write characterization tests through the public API. 2) Extract the least tangled cluster (say notifications) into OrderNotifier and delegate from OrderManager. 3) Repeat for pricing, stock, payments. 4) Inject the new classes. 5) When callers use the new classes directly, delete the delegating methods. Prefer many small safe commits over a big-bang branch.

Prevent: a size or complexity limit in the build, and "one reason to change" in code review.

Why not rewrite. A 3,000-line class has absorbed years of fixes and edge cases. A rewrite resets that knowledge and takes months in which the old class still needs bug fixes (so you maintain both). Incremental extraction is slower to start but never breaks production.

The technique in detail (a version of "strangler" at class level).

  1. Find seams. Group methods by the fields they use and by what they call. Tools: IDE "find usages", a cohesion metric (LCOM), and a graph of method to field access. Clusters usually appear: pricing, stock, notifications, persistence.
  2. Freeze behaviour. Add characterisation tests through the public methods (and the database, using Testcontainers if needed). Aim for coverage of the cluster you will extract first, not the whole class.
  3. Extract the safest cluster. Move methods plus the fields they own into a new class (IDE "Extract Class" or "Move Method"). In OrderManager keep a field notifier and delegate calls. Callers still use OrderManager, so nothing outside changes. Run tests, commit.
  4. Break hidden dependencies. A god class often shares mutable state between clusters (the same currentOrder field). Pass the data explicitly as parameters while extracting, so each new class has a clear input and output.
  5. Introduce interfaces only at real boundaries (payment, persistence) as you go.
  6. Move callers to the new classes in small PRs. When no caller uses a delegating method, delete it. OrderManager shrinks until it is a thin facade or vanishes.

Order of extraction. Start with pure logic and leaf dependencies (formatting, pricing calculations), which are easiest to test, then the I/O-heavy clusters. Extract what changes most often first, to see the benefit sooner and win support from the team.

Social side. Agree a short rule with the team: "no new code goes into the god class; every bug fix in it extracts the touched method first" (the boy-scout rule). Track size over time to show progress. Avoid freezing the whole team for a refactoring sprint, since the code changes underneath you.

Remember: tests first, extract one cluster at a time, keep the old class as a facade until callers move.

Services A, B and C all call each other, and the app fails at start-up with a circular dependency. How do you untangle it? Senior

The cycle means responsibilities are in the wrong place, so I do not silence it with @Lazy. I find the shared logic that A, B and C each need and pull it into a new lower-level class that all three depend on, or break one edge with an event or an interface.

Check first: read the stack trace for the cycle (A to B to C to A). Constructor injection fails fast at start-up with a circular reference error. Since Spring Boot 2.6, circular references are prohibited by default even with field or setter injection, unless you set spring.main.allow-circular-references=true.

Fix, in order of preference: 1) Extract the shared piece into class D, so A, B and C depend on D and not on one another. 2) Invert one dependency: A publishes an event that B listens to (Observer). 3) Introduce an interface owned by the lower layer (Dependency Inversion). 4) Last resort: @Lazy on one injection point, or setter injection, which hides the problem and risks half-wired beans.

Prevent: keep dependencies flowing one way (web, service, repository), and add an architecture test (ArchUnit) that fails the build on cycles.

Read the message first. The error looks like "The dependencies of some of the beans in the application context form a cycle: A to B to C to A". It tells you exactly which beans are involved. Draw that triangle on paper, and for each arrow write the actual method call that causes it. Often one of those calls is the odd one out.

A worked example. OrderService calls CustomerService.isVip(). CustomerService calls InvoiceService.unpaidCount(). InvoiceService calls OrderService.findOpenOrders(). Each service wanted "just one little method" from another. Fixes:

  • Extract shared logic. The three need customer and order read data. Create OrderQueries (or a repository method) that all three use. Now the arrows point down to a shared low-level class: no cycle.
  • Move the method to the right owner. unpaidCount is really a query over invoices by customer: put it on InvoiceRepository, and let CustomerService use the repository, not the other service.
  • Replace a call with an event. When OrderService places an order, publish OrderPlaced. InvoiceService listens. OrderService no longer depends on it at all.
  • Invert with an interface owned by the lower layer (OrderLookup), implemented by the higher one, so the compile-time arrow points the other way.

Why @Lazy is risky. It injects a proxy resolved on first use, so start-up passes, but the cycle is still there. Bugs now show up later (a half-initialised bean used during start-up callbacks, such as @PostConstruct), initialisation order becomes accidental, and the cycle can also surface as an infinite recursion at runtime. It is a patch to buy time, with a ticket to fix properly.

Prevention. An ArchUnit rule such as "slices matching com.app.(*).. should be free of cycles" and package-by-feature with a dependency direction that is documented. Also notice when constructors are growing: many injected services usually signal a class that does too much and invites cycles.

Remember: a cycle is a design smell. Extract the shared part or break an edge with an event. @Lazy is a patch.

Unit tests pass alone but fail when run together, and the culprit is a Singleton holding state. How do you fix it? Intermediate

The tests share one global object, so state from one test leaks into the next, and the result depends on test order. The proper fix is to stop using a static singleton and inject the dependency, so each test gets a fresh instance. The quick fix is a reset method used in test setup.

Situation: CacheManager.getInstance() keeps entries between tests, so test B sees data from test A. It passes alone and fails in the suite, sometimes only on CI where order differs.

Check first: run the failing test alone, then with the previous test. Search for static mutable fields and getInstance() calls.

Fix: change the class under test to take the cache through its constructor. In production, Spring supplies one shared bean (still a single instance, no static). In tests, create a new cache each time. If the singleton is legacy and widely used, add a package-private reset() and call it in @BeforeEach, then migrate step by step.

Prevent: avoid static mutable state, and run tests in random order on CI to expose hidden coupling.

How to prove it is order-dependent. Run the failing test alone (passes). Run the whole class (fails). Run the pair: previous test then the failing one. Most runners can randomise order (JUnit 5 supports a random method orderer through configuration, and Maven Surefire has a runOrder setting). Once you find the pair, search for what both touch: a static field, a singleton, a system property, a static cache, a shared temp file, or a time-based value.

The mechanism in one picture. Test A runs CacheManager.getInstance().put("user:1", alice). The test ends, but the JVM and the singleton live on. Test B asserts the cache is empty on first call, or expects a database read, but finds Alice. Surefire reuses one JVM for all tests in a module by default, which is why this only appears when running together.

Fix options, in order of quality.

  1. Inject the dependency. UserService(CacheManager cache). Production wiring passes the shared instance, the test creates new CacheManager() per test. No global state remains.
  2. Keep the singleton but add a seam. Add static void setInstance(CacheManager c) or a reset(), annotate it as test-only, and call it in @BeforeEach and @AfterEach. It works, but it is a crutch, and parallel tests will still collide.
  3. Run tests in isolated JVMs (Surefire reuseForks=false). It hides the problem at a heavy time cost, so only as a stop-gap.

Do not forget the Spring variant. Spring caches the application context across tests, and singleton beans keep their state between test classes. Use @DirtiesContext sparingly (it is slow), or better, reset the state in the bean for test, or use @MockBean or fresh fakes. Also consider the same bug for statics like Locale.setDefault, System.setProperty, and mutable static final collections.

Lesson to state. A test that depends on order is a design report: the code under test has hidden global state. Fixing the design fixes the tests, and also removes the production risk of one request affecting another.

Remember: static state is shared between tests. Inject it so each test has its own.

A @Transactional method is not rolling back or not starting a transaction. The code looks correct. What do you check? Senior

Nearly always the cause is the proxy. Spring applies @Transactional through a proxy around the bean, so the annotation only works when the call goes through the proxy from another bean. A call from one method to another in the same class, a private method, or an object created with new skips it.

Check first, in this order:

  • Self-invocation: this.save() inside the same class bypasses the proxy, so there is no new transaction or propagation. Fix by moving the method to another bean, or by injecting the bean itself (less pretty).
  • Visibility: the method must be public to be intercepted by the default proxy mode. A final or private method cannot be proxied the class-based way.
  • Exception type: by default only unchecked exceptions (RuntimeException, Error) roll back. A checked exception commits unless you set rollbackFor.
  • Swallowed exception: a catch that logs and continues means the proxy never sees the failure.
  • Bean created by hand, not by Spring, or the wrong @Transactional import, or threads: a new thread (@Async or an executor) does not share the transaction.

Prevent: integration tests that check rollback, and keep transaction boundaries on service methods called from outside.

Mental model that makes every symptom obvious. Spring does not change your class. It builds a second object (the proxy) that has the same methods and wraps your bean. Other beans get the proxy injected. The proxy begins the transaction, calls your real method, then commits or rolls back. Anything that reaches your real object without passing through the proxy gets no transaction.

Self-invocation, with a concrete trace.

@Service class OrderService {
    public void checkout(Cart c) { save(c); }              // no transaction on checkout
    @Transactional public void save(Cart c) { ... }        // annotation ignored: called via this
}
  1. A controller calls orderService.checkout(c). It enters the proxy, which sees no annotation on checkout and forwards to the real object.
  2. Inside the real object, save(c) means this.save(c). this is the raw object, not the proxy, so the interceptor never runs.
  3. Result: save runs with no transaction (or, if checkout were transactional, without its own propagation settings such as REQUIRES_NEW).

Fixes for self-invocation. Move save to another bean (cleanest), or put the annotation on the entry point (checkout) if one transaction is what you wanted, or inject a self reference or use AopContext.currentProxy() (works but ugly), or use AspectJ weaving mode (no proxy, so it works on self calls but needs more setup).

Rollback rules, in a table.

Exception thrownDefault resultTo change
RuntimeException or ErrorRollbacknoRollbackFor
Checked exception (IOException)CommitrollbackFor = Exception.class
Exception caught inside the methodCommit (proxy sees normal return)Rethrow, or mark the current transaction rollback-only through TransactionAspectSupport

Other causes to scan for. Wrong import (javax.transaction.Transactional versus Spring's; both usually work but have slightly different rollback options). Bean created by new. The method is final or private; visibility rules differ by Spring version, so check the reference for your version, and make transactional methods public to be safe. A thread switch (@Async, parallel stream, executor) moves work to a thread with no transaction, because the transaction is bound to the thread. A REQUIRES_NEW inner transaction that commits even though the outer one rolls back. Read-only transactions that still try to write. Debug by turning on logging for org.springframework.transaction and org.springframework.orm.jpa at DEBUG: it prints "Creating new transaction" or "Participating in existing transaction".

Remember: proxy-based, so only external public calls are intercepted. Checked exceptions do not roll back by default.

A third-party SDK is used directly in 200 files, and the vendor just released an incompatible version. How do you get out of this, and how do you stop it happening again? Senior

I put my own interface between my code and the vendor (an Adapter, also called an anti-corruption layer), then migrate callers to it gradually. Once the vendor appears in only one adapter class, upgrading or replacing it is a change in one file.

Check first: what do we actually use? Often only five calls out of the SDK's hundreds. List them with a code search.

Fix: 1) Define PaymentClient (or similar) with just the operations we need, in our own types. 2) Write an adapter implementing it with the old SDK. 3) Move callers over in batches, using IDE refactoring or automated migration, with tests. 4) Write a second adapter for the new SDK version, and switch with a config flag. 5) Delete the old one. Do the migration over several small releases, not one large one.

Prevent: a lint or architecture rule that only the adapter package may import the vendor package, and never let vendor types appear in public method signatures or entities.

Why this keeps happening. Using the SDK directly is the fastest way to ship the first feature, so it spreads by copy-paste. Years later the vendor's types (StripeCharge, its exceptions, its enums) are in method signatures, database mappings and JSON classes across the codebase. This is vendor lock-in at the code level, and an incompatible upgrade becomes a project instead of a version bump.

The migration, with the order that keeps you safe.

  1. Inventory. Use a code search to list SDK classes and methods actually used, counted by number of files. Usually a small set dominates (charge, refund, fetch). Note any SDK types stored in your database or serialised to messages, which are the hardest to change.
  2. Define your port. Create PaymentClient with exactly those operations and your own result types and exceptions. Name things in business terms.
  3. Adapter for the current SDK version. Wrap the existing behaviour first. No new vendor version yet, so this step is a pure refactor and must change nothing.
  4. Migrate callers in batches. Mechanical changes can use IDE structural search and replace or an automated recipe (OpenRewrite). Each batch is a PR with tests. Ban new direct uses immediately (see prevention), otherwise you chase a moving target.
  5. Second adapter for the new version. Implement the same interface. Run both against the same contract tests. Select between them by a feature flag or configuration, then move traffic gradually, keeping the ability to roll back.
  6. Remove the old adapter and the old dependency.

Dealing with old data. If vendor types were persisted (for example JSON blobs of SDK objects), add a mapper and migrate lazily on read, or write a one-time migration. If you cannot upgrade both at once, the adapter can run two SDK versions side by side only with shading or separate class loaders, which is painful, so prefer a short window.

Prevention. Enforce the boundary: an ArchUnit or Gradle/Maven module rule that only payments-adapter may depend on the vendor library, plus a lint on imports. Translate vendor exceptions at the boundary. Keep SDK objects out of entities and events. This is the same idea as an anti-corruption layer in Domain-Driven Design: your model should not be shaped by someone else's API.

Remember: wrap the vendor behind your own interface. One adapter file is the only place that knows the SDK.

Placing an order takes 8 seconds because one "OrderPlaced" listener (analytics) is slow, and sometimes its failure fails the order. How do you fix it? Senior

The listeners run synchronously in the same thread and transaction as the order, so the slowest one sets the response time and any exception propagates. I make non-critical listeners asynchronous and isolated, and for important side effects I use a reliable queue.

Check first: which listener is slow (a thread dump or timing log per listener) and which ones must succeed for the order to be valid (payment, stock) versus nice to have (analytics, email).

Fix: keep only essential steps synchronous. Run analytics through an executor (@Async with a bounded pool) or publish a message to Kafka or a queue, and consume it separately. Wrap each listener call in try/catch so one failure cannot stop the others. In Spring, @TransactionalEventListener(phase = AFTER_COMMIT) makes sure side effects run only after the order is saved. If the event must not be lost, write it to an outbox table in the same transaction and publish from there.

Prevent: timeouts and a bounded queue on async work, and monitoring of listener latency.

Why this happens. In-process Observer is just a loop of method calls. publishEvent in Spring runs listeners on the caller's thread, one after another, inside the caller's transaction unless told otherwise. So total latency is the sum of all listeners, an exception from the third listener propagates back through place() and rolls back the order, and a listener that calls a remote service holds a database transaction open while it waits.

Diagnosis. Add timing around each listener (or use a tracing tool such as a span per listener) and look at the distribution, not only the average. A thread dump taken during a slow request shows which listener the thread is stuck in (for example waiting on an HTTP call or a lock). Also check whether the analytics listener makes a network call inside the transaction.

Classify each reaction.

TypeExamplesTreatment
Must succeed with the order, same atomic unitReserve stock, create payment recordKeep synchronous in the same transaction (or part of the use case itself, not an event)
Must happen, but can be a little lateSend confirmation email, notify warehouseOutbox plus a queue; retry until done
Nice to haveAnalytics, recommendationsAsynchronous, best effort, failure only logged

Implementation, concretely.

  1. Switch the analytics listener to @Async with a named, bounded ThreadPoolTaskExecutor (set queue capacity and a rejection policy such as caller-runs or drop with a metric). Never use an unbounded queue, or a slow vendor fills memory.
  2. Use @TransactionalEventListener(phase = AFTER_COMMIT) so the listener runs only if the order really committed. Note that work done after commit must start its own transaction if it needs one (REQUIRES_NEW).
  3. For things that must not be lost, write an outbox row in the same transaction as the order. A relay process (or a CDC tool) publishes it to Kafka. The consumer is idempotent, because delivery is at least once.
  4. Wrap remote calls with a timeout and a circuit breaker so one slow dependency cannot stall threads.

Pitfalls after the fix. Async means the order response no longer implies the side effect has happened, so UIs and tests must not assume it. Errors are no longer visible to the caller, so add alerts on the failure rate and a dead-letter queue. Ordering between events for the same order is no longer guaranteed unless you key the queue by order id.

Remember: Observer is synchronous by default. Move non-critical listeners off the request thread, and isolate their failures.

An intermittent bug: a request sometimes shows another user's data or a changing total. The code shares a mutable object. How do you find and fix it? Senior

This is shared mutable state across threads: typically a singleton bean (service, formatter, helper) with an instance field that holds per-request data. The fix is to remove the field: pass data as method parameters, or make the shared thing immutable or thread-safe.

Check first: look for non-final instance fields in singleton beans, static mutable fields, shared SimpleDateFormat (not thread-safe), shared HashMap, and ThreadLocal values not cleared on pooled threads (a classic cross-user leak). Reproduce with a concurrent test (many threads calling the same bean), because the bug hides under single-thread load.

Fix: turn the field into a local variable or parameter; use DateTimeFormatter (immutable, thread-safe); use ConcurrentHashMap or immutable value objects; if a ThreadLocal is used, clear it in a finally. Do not "fix" it by adding synchronized everywhere, which hides the design problem and hurts throughput.

Prevent: make singleton beans stateless by convention, code review for non-final fields, and concurrency tests for shared components.

What the symptom tells you. "Sometimes another user's data" and "a total that changes" mean two threads touched the same variable at the same time. It is intermittent because it needs overlapping requests, which dev machines and single-user tests rarely produce. It tends to show up in production under load or right after a deploy when many users hit the system.

Hunt, step by step.

  1. Static analysis first. Find fields that are non-final in Spring singletons (@Service, @Component, @Controller). Static analysis tools and IDE inspections flag them. Also search for static non-final fields and static collections.
  2. Known thread-unsafe classes. SimpleDateFormat and DecimalFormat as shared fields, HashMap or ArrayList written from several threads, StringBuilder shared as a field, and Calendar.
  3. Thread-bound state that outlives the request. A ThreadLocal set in a filter and not cleared leaks into the next request served by that pooled thread (a security bug when it holds the user identity). Always clear in finally.
  4. Reproduce. Write a test that calls the suspect bean from 50 threads with different inputs and asserts each result matches its own input (use ExecutorService and a CountDownLatch start gate). A tool like jcstress or a stress run helps for subtle visibility bugs.

The shape of a typical bug and its fix.

// Bug: one formatter and one total shared by all requests
@Service class InvoiceService {
    private final SimpleDateFormat fmt = new SimpleDateFormat("yyyy-MM-dd");   // not thread-safe
    private double total;                                                      // shared state
    String render(Invoice i) { total = 0; for (Line l : i.lines()) total += l.amount(); return fmt.format(i.date()) + total; }
}
// Fix: immutable formatter, local variable
private static final DateTimeFormatter FMT = DateTimeFormatter.ISO_LOCAL_DATE;   // immutable
String render(Invoice i) { double total = i.lines().stream().mapToDouble(Line::amount).sum(); return FMT.format(i.date()) + total; }

Why not just add synchronized. It makes the symptom disappear but turns the service into a single-lane road (one request at a time), and remaining shared state may still leak through other paths. Locks are a last resort after eliminating shared state.

Longer-term prevention. A rule that singleton beans have only final fields, injected collaborators and constants; request data flows through parameters or a request-scoped holder; code review checks; and a concurrency test for any bean that has to keep state.

Remember: a singleton must be stateless. Per-request data goes in parameters, not in fields.

Two teams want to share one "common" validation module, but their rules keep diverging, and every change breaks the other team. What do you advise? Senior

I advise splitting it. The shared code was a premature DRY: the rules look the same but belong to different business contexts and change for different reasons. Each team should own its copy, and only truly shared, stable pieces (like a format check) stay common.

Check first: how many flags and if (teamA) branches have been added to the shared module? How often do changes need a cross-team release? Are the rules really the same business rule?

Fix: copy the module into each team's codebase (duplication is acceptable here), delete the branches each team does not need, and keep a small shared library for genuinely common stable utilities. If one rule truly must be identical (a legal rule), keep that one piece shared with clear ownership and versioning.

Prevent: follow the rule of three (abstract after the third use), and share through a versioned library with a deprecation policy, never by editing shared code in place.

How the situation develops. A year ago two teams had similar validation, so someone extracted a shared module (DRY applied well on paper). Since then Team A needs a stricter phone format, Team B an optional field, and flags and branches (if (tenant == A)) have appeared. Now any change needs both teams' review, a shared release, and regression testing of both. The module's cost exceeds the duplication it saved. This is coupling through shared code, and it is the main danger of a shared library across team boundaries.

A decision framework. For each piece of shared logic ask:

  1. Same reason to change? If both teams always change it for the same business or legal reason (a tax identifier format defined by law), keep it shared.
  2. Same rate of change? A stable utility (an email regex, IBAN checksum) can be shared. Fast-moving business rules usually should not.
  3. How much does divergence already cost? Count flags, cross-team PRs and incidents. If these exceed a couple per quarter, split.

The split, step by step.

  1. Freeze the shared module and publish its current version as a stable release (so nobody is surprised).
  2. Each team copies it into its own repo or module, deletes the other team's branches, and adds its own tests. Because the code started identical, the copy is a safe, mechanical step.
  3. Keep a small shared artefact only for truly common, stable parts (formats, constants), with a named owner, semantic versioning and a deprecation policy.
  4. Switch each team's dependency over, and retire the old combined module.

Alternatives to a hard split. A shared library with extension points (a validation rule interface; each team supplies its rules) lets them share the framework but own the rules. A shared service via API makes sense when the rule must be identical for all callers and you want one deployment to change it, at the cost of a network call and a runtime dependency.

How to explain it diplomatically. It is not "the shared code was a mistake". It was a reasonable choice that no longer fits as the teams' needs diverged. The cost of a little duplication is lower than the cost of coordinating every change. Revisit later: if the two copies converge again, they can be re-merged with evidence.

Remember: a shared module with team flags is the wrong abstraction. Duplication is cheaper than coupling.

A junior has applied five design patterns to a 50-line feature, and now nobody can follow it. How do you handle the review? Senior

I ask which problem each pattern solves today, and if there is no real pain I ask to simplify it. I praise that they learned the patterns, then explain YAGNI: add structure when a second variation exists, not before. The goal is code the team can read, with a pattern only where change is likely.

Check first: is there more than one implementation of each interface? Is a variation actually planned? How many classes and files would a new teammate open to follow one request?

Fix: pair on a simpler version: a plain class or method, maybe with one interface at the real boundary (the database or an external call). Show that adding the pattern later is a small refactor, backed by tests, so there is no loss in waiting. Frame it as a learning point and not a failure.

Prevent: team guidelines such as "no interface with a single implementation unless it is a boundary", and design discussion before large structures.

Approach the person, not just the code. The junior probably studied the patterns recently and did what the books suggest. The goal of the review is that they understand the principle, and that you do not discourage them. Start with what is good (they know the patterns, the code is tidy and tested), then move to the question that opens the discussion.

Questions that guide without lecturing.

  • "What change are we protecting this feature against?" If there is no concrete answer, the pattern is speculative.
  • "How many implementations does this interface have today? In the next quarter?"
  • "If a new teammate had to find where the discount is applied, how many files would they open?"
  • "Could we get the same result with a method and a lambda?"

A before and after, concretely. The feature: apply a 10 percent discount for premium users. The over-engineered version has DiscountStrategy, DiscountStrategyFactory, DiscountContext, PremiumDiscountStrategy, and an AbstractDiscountHandler: five files, one behaviour. The simple version:

double discount(User u, double amount) { return u.isPremium() ? amount * 0.10 : 0; }

When a second and third rule appear, promote it to an interface plus a list of rules. The refactoring is a few minutes with tests, so nothing is lost by waiting. In fact, you now know the true shape of the variation, so the abstraction fits better.

What to keep. Not all structure is bad. A single interface at a real boundary (payment gateway, repository, clock) is justified even with one implementation because it enables fakes in tests and protects against vendor change. So the rule of thumb is: boundaries yes, speculative variation no.

Making it stick. Pair on the simplification so they see the result. Write the team principle down (for example "prefer the simplest design that passes the tests, and refactor to a pattern when the second variation arrives"). Praise good restraint publicly. And model it yourself: when you add a pattern in your own PRs, state which problem it solves in the description.

Remember: patterns solve pain you have, not pain you might have. Simple first, refactor when the second case arrives.
