Mental model: the 7 ideas everything hangs on

One line: good design is about making the next change cheap. Patterns are names for proven ways to keep parts independent, so that a new requirement means adding code, not editing and breaking old code.
  1. Change is the real enemy. Requirements always grow. A design is good when a likely change touches one small place. Ask "what will vary?" and put that behind an interface.
  2. Depend on abstractions, not on concrete classes. High-level code (business rules) should not know which database, payment provider or sorting algorithm is used. It talks to an interface; details are plugged in from outside.
  3. Prefer composition over inheritance. Inheritance is a fixed, compile-time, tight link. Composition (holding another object and delegating) is flexible and can change at runtime.
  4. High cohesion, low coupling. Things that change together live together (cohesion). Things that change independently should know as little as possible about each other (coupling).
  5. Patterns are vocabulary, not goals. A pattern is a named solution to a recurring problem. You use one when the problem is real, not to look clever. Over-engineering is a bug.
  6. Keep it small and simple. KISS and YAGNI: build what is needed now, in the simplest form that is still easy to change. Add a pattern when the second or third variation appears, not before.
  7. Testability is design feedback. If a class is hard to unit test (needs a real database, static calls, hidden new), the design is too coupled. Good LLD makes a class testable with simple fakes.

1. Principles: SOLID, composition, coupling, simplicity

What is low-level design (LLD), and how is it different from high-level design? Basic

What the interviewer is testing: whether you know the scope of the round before you start drawing.

High-level design (HLD) is about the whole system: services, databases, queues, caches, how traffic flows and how it scales. Low-level design is about the code inside one service or module: classes, interfaces, their relationships, and the key methods. In an LLD round you are given a small problem like a parking lot or an elevator. You clarify the requirements, find the objects (nouns) and their behaviour (verbs), draw a class diagram, decide where to use interfaces and patterns, write the key classes, and then explain how the design would handle new requirements. The interviewer cares about clean responsibilities, sensible abstractions, thread safety where it matters, and your ability to defend trade-offs. They do not care about getters, setters or a database schema unless asked.

Likely follow-ups
  • What steps do you follow? Requirements, entities, relationships, behaviours and interfaces, patterns where the variation is, code for the core flow, then extensions.
  • Do you design persistence? Only a repository interface, unless the interviewer asks for the schema.
What are the SOLID principles? Give one line for each. Basic

What the interviewer is testing: a clean, correct definition of each, with no mixing of letters.

S, Single Responsibility: a class should have one reason to change. O, Open/Closed: classes should be open for extension but closed for modification, so a new case is added by writing new code, not by editing tested code. L, Liskov Substitution: anywhere you use a base type, you must be able to use a subtype without surprises. I, Interface Segregation: many small, focused interfaces are better than one fat one, so no class is forced to implement methods it does not need. D, Dependency Inversion: high-level code and low-level code should both depend on an abstraction, and the abstraction should be owned by the high-level side. Together they say: split by reason to change, add behaviour by plugging in, keep promises of types, keep interfaces small, and point dependencies at abstractions.

Likely follow-ups
  • Are these laws? No, they are guidelines. Following them blindly creates too many tiny classes. Use them to explain pain, not to start the design.
  • Who named them? Robert C. Martin (Uncle Bob) collected them in the early 2000s.
Explain the Single Responsibility Principle with a real violation and the fix. Basic

What the interviewer is testing: do you understand "reason to change", not "does one thing".

SRP does not mean a class has one method. It means a class should have one reason to change, usually one stakeholder or one concern. Here is a typical violation. InvoiceService calculates tax (finance rules), saves to the database (storage concern), builds a PDF (presentation) and sends an email (delivery). If the tax law changes, the database changes, the PDF layout changes or the email provider changes, this same class changes, and every change risks breaking the other three. It is also hard to test, because calculating a total needs a database and a mail server. The fix is to split by concern: a pure TaxCalculator, an InvoiceRepository, an InvoicePdfRenderer and a Notifier, with a thin InvoiceService that coordinates them.

// violation: four reasons to change
class InvoiceService {
    double total(Invoice i) { /* tax rules */ return 0; }
    void save(Invoice i)    { /* JDBC code */ }
    byte[] toPdf(Invoice i) { /* layout */ return null; }
    void email(Invoice i)   { /* SMTP */ }
}

// fix: one reason each, coordinated by a thin class
class InvoiceService {
    private final TaxCalculator tax;
    private final InvoiceRepository repo;
    private final Notifier notifier;
    InvoiceService(TaxCalculator t, InvoiceRepository r, Notifier n) { tax = t; repo = r; notifier = n; }
    void finalizeInvoice(Invoice i) {
        i.setTotal(tax.total(i));
        repo.save(i);
        notifier.send(i);
    }
}
Likely follow-ups
  • How do I know a class has too many responsibilities? Its name has "And" or "Manager", it needs many unrelated imports, or different features change the same file in every pull request.
  • Can you go too far? Yes: ten classes of three lines each, with no real reason to change separately, is just noise.
Common mistakes: saying "one class, one method"; splitting by technical layer only, when the real axis is the reason to change.
Explain the Open/Closed Principle. Show a violation and the fix. Basic

What the interviewer is testing: can you remove a growing if-else or switch with polymorphism, the most common practical use of OCP.

Open for extension, closed for modification means: when a new variation arrives, you add a new class instead of editing a working one. The classic violation is a method with a switch on type. Every new customer type needs a new case in the same method, which has to be retested and can break the old cases. The fix is to hide the variation behind an interface. Each customer type gets its own implementation, and the calculator simply calls the interface. To add a new type you write one new class and register it. Nothing old is touched. The price is a few more classes, so use it when the variation is real and has already appeared twice or three times.

// violation
double discount(String type, double amount) {
    switch (type) {
        case "REGULAR": return amount * 0.0;
        case "GOLD":    return amount * 0.10;
        case "PLATINUM":return amount * 0.20;   // each new type edits this method
        default: throw new IllegalArgumentException(type);
    }
}

// fix
interface DiscountPolicy { double apply(double amount); }
class GoldDiscount implements DiscountPolicy { public double apply(double a) { return a * 0.10; } }
class PlatinumDiscount implements DiscountPolicy { public double apply(double a) { return a * 0.20; } }

class PriceCalculator {
    private final Map<String, DiscountPolicy> policies;   // injected, e.g. by Spring
    PriceCalculator(Map<String, DiscountPolicy> p) { policies = p; }
    double finalPrice(String type, double amount) {
        return amount - policies.getOrDefault(type, a -> 0).apply(amount);
    }
}
Likely follow-ups
  • Is OCP only about inheritance? No. You can also reach it with composition, lambdas, plug-in registries or configuration.
  • Is OCP ever fully achieved? No. You choose which change to protect against, based on what is likely to change.
Explain the Liskov Substitution Principle. What is the Square and Rectangle problem? Intermediate

What the interviewer is testing: whether you understand behavioural contracts, not just "is-a" in English.

LSP says that if code works with a base type, it must keep working when you pass any subtype. The subtype may do more, but it must not break the promises the base type made. A square is a rectangle in maths, but a mutable Square that extends Rectangle breaks the promise that width and height are independent. Code that sets width to 5 and height to 4 and expects area 20 gets 16 on a square, because setting one side changed the other. The "is-a" relation was right in the real world and wrong in code. Other signs of an LSP break are: a subclass that throws UnsupportedOperationException for an inherited method, a subclass that makes preconditions stricter, a subclass that returns weaker results, or code that checks instanceof to treat some subtypes specially. The fix is usually to stop inheriting: use a shared smaller interface (Shape with area()) or make the types immutable.

class Rectangle { protected int w, h;
    void setW(int w) { this.w = w; }  void setH(int h) { this.h = h; }
    int area() { return w * h; } }
class Square extends Rectangle {
    @Override void setW(int w) { this.w = w; this.h = w; }   // surprise
    @Override void setH(int h) { this.w = h; this.h = h; }
}
// test written for Rectangle:
r.setW(5); r.setH(4); assert r.area() == 20;   // fails for Square (16)
Likely follow-ups
  • A JDK example? Collections.unmodifiableList returns a List that throws on add. It is a known compromise: the type says it can add, the object cannot.
  • Another famous one? A Bird with fly() and a Penguin subclass. Fix by splitting FlyingBird from Bird.
Explain the Interface Segregation Principle with an example. Basic

What the interviewer is testing: can you spot a fat interface and its cost.

A client should not be forced to depend on methods it does not use. If an interface has ten methods and a class needs only two, it has to either implement eight pointless methods (often throwing exceptions, which also breaks LSP) or it gets recompiled and affected when those unused methods change. Example: a MultiFunctionMachine interface with print, scan and fax. A basic printer is forced to implement scan and fax. Split it into Printer, Scanner and Fax, and let a multi-function device implement all three. A real-life version: a UserRepository with read, write, delete and bulk-import methods being used by a read-only reporting job. Give the reporting job a small UserReader interface instead.

interface Printer { void print(Document d); }
interface Scanner { Document scan(); }
class BasicPrinter implements Printer { public void print(Document d) { /* ... */ } }
class OfficeMachine implements Printer, Scanner { /* both */ }
Likely follow-ups
  • Is a very small interface always better? A one-method interface is fine (functional interface), but splitting a cohesive concept into many pieces makes it hard to use.
What is the Dependency Inversion Principle, and how is it different from dependency injection? Intermediate

What the interviewer is testing: these three terms (DIP, DI, IoC) are mixed up constantly. Be precise.

DIP is a design rule: high-level modules (business logic) must not depend on low-level modules (database, HTTP client). Both should depend on an abstraction, and the high-level side should own that abstraction. Normally the dependency arrow points from business code down to the database code. After inversion the business code defines OrderRepository, and the database class implements it, so the arrow from the database now points up to the business code. That is the "inversion". Dependency injection is a technique: a class does not create its dependencies with new; they are passed in, usually through the constructor. DI is the common way to achieve DIP, but you can do one without the other: injecting a concrete MySqlOrderRepository is DI without DIP.

class OrderService {
    private final OrderRepository repo;            // abstraction
    OrderService(OrderRepository repo) { this.repo = repo; }   // injected
    void place(Order o) { repo.save(o); }
}
// test: new OrderService(new InMemoryOrderRepository())
Likely follow-ups
  • And IoC? Inversion of Control is the wider idea that a framework calls your code (and creates your objects) rather than you calling it. DI is one form of IoC.
Composition vs inheritance: why do people say "favour composition"? Basic

What the interviewer is testing: a real trade-off view, not a slogan.

Inheritance reuses code by making a subclass a kind of the parent. It is a static link set at compile time, and the child knows the internals of the parent, so a change in the parent can silently break children (the fragile base class problem). It also has only one parent in Java, and deep hierarchies become hard to follow. Composition reuses code by holding another object and calling it. The link can be changed at runtime, each part can be tested alone, and you can combine many behaviours. Example: instead of FlyingDuck, SwimmingFlyingDuck, RubberDuck subclasses, give Duck a FlyBehavior field (that is the Strategy pattern). Use inheritance when there is a true is-a relation with a stable contract that follows LSP, for example ArrayList is a List. Use composition when you just want to reuse behaviour.

Likely follow-ups
  • What is the fragile base class problem? A subclass depends on how a parent method calls other overridable methods. If the parent changes that, the subclass breaks. Joshua Bloch's example is HashSet.addAll calling add, which breaks a counting subclass.
  • What is "design for inheritance or prohibit it"? Make classes final unless you wrote documentation and tests for subclassing.
What are coupling and cohesion? What is good design aiming for? Basic

What the interviewer is testing: the two quality measures behind almost every design choice.

Coupling is how much one class knows about and depends on another. Tight coupling means a change in one forces changes in the other: using a concrete class, reaching into its fields, sharing global state, or knowing the order of calls. Cohesion is how well the parts inside one class belong together. A class with high cohesion has methods all working on the same data and goal (for example Money with add, subtract, compare). Low cohesion is a Utils or Manager class with unrelated methods. We want high cohesion and low coupling. Low coupling is gained by depending on interfaces, passing data not objects, and using events. Tools to reduce coupling: dependency injection, interfaces, Observer, Mediator, Facade. A quick test: how many files must I touch for one small business change? If the answer is many, coupling is high or cohesion is low.

Likely follow-ups
  • Types of coupling, weakest to strongest? Data (pass simple values), stamp (pass a big object but use part), control (pass a flag that steers behaviour), common (shared globals), content (reach into another's internals).
  • Can coupling be zero? No. Systems must talk. Make it explicit and narrow.
Explain DRY, KISS and YAGNI. When can following DRY hurt? Basic

What the interviewer is testing: judgement. DRY followed blindly is a well-known trap.

DRY (Don't Repeat Yourself) says every piece of knowledge should live in one place. If a tax rate or a validation rule is copied in five places, one change needs five edits and one will be missed. KISS (Keep It Simple) says choose the simplest design that works; clever code costs every future reader. YAGNI (You Aren't Gonna Need It) says do not build features or extension points for needs you only imagine. DRY can hurt when two pieces of code look the same by accident but change for different reasons. If you merge them into one shared function with flags, then every change has to satisfy both callers and the function fills with if branches. A good rule is the "rule of three": tolerate duplication twice, extract on the third time, when the real shape of the shared part is clear. DRY is about duplicated knowledge, not duplicated lines of text.

Likely follow-ups
  • How do YAGNI and OCP fit together? Do not build the extension point today. Write clean code so that adding it later is easy. When the second variation arrives, refactor to a pattern.
Common mistakes: creating a shared "common" module for two things that only look alike; adding a plug-in framework for one implementation.
What is the Law of Demeter? Show a violation. Intermediate

What the interviewer is testing: encapsulation at the call-chain level.

The Law of Demeter, or "principle of least knowledge", says a method should only talk to its direct friends: itself, its parameters, objects it creates, and its own fields. It should not reach through an object to get another object and call that. The famous smell is a long chain like order.getCustomer().getAddress().getCity(). The caller now knows that an order has a customer, that a customer has an address, and that an address has a city. If any of those structures change, this caller breaks. The fix is to ask the nearest object to do the work: order.shippingCity(). This is also called "tell, don't ask": tell the object what you need, do not pull its data out and decide for it. Not every dot is a violation. Fluent builders and streams (list.stream().filter(...).map(...)) return the same kind of object and are fine. Plain data structures with no behaviour are also usually fine.

// violation: caller knows the whole structure
String city = order.getCustomer().getAddress().getCity();

// better: Order hides how it finds the city
class Order {
    String shippingCity() { return customer.cityForShipping(); }
}
Likely follow-ups
  • Downside of the law? You may write many small delegating methods. Apply it at module boundaries, where it protects most.
What is a design pattern, and what are the risks of using patterns? Basic

What the interviewer is testing: maturity. Juniors worship patterns; seniors know when to skip them.

A design pattern is a named, reusable solution to a common design problem, described by its intent, structure, participants and trade-offs. It is not code you copy; it is an idea you adapt. The value is a shared vocabulary: saying "this is an observer" tells a teammate a lot in two words. It also records experience of what works. The risks are over-engineering (an abstract factory for one product), forcing a pattern where a function would do, and making code harder to read for people who do not know the pattern. Many classic patterns are also built into modern languages: Strategy and Command become lambdas, Iterator is a for-each, Singleton is often a Spring bean scope. Use a pattern when the problem is real, and be able to explain what pain it removes.

Likely follow-ups
  • What is a pattern language vs an idiom? An idiom is language-specific (try-with-resources), a pattern is language-independent.
  • Which patterns do you use most? Be honest: Strategy, Factory, Builder, Observer, Decorator and Adapter come up daily.

2. Creational patterns

What is the Singleton pattern, and when is it a good or bad idea? Basic

What the interviewer is testing: the definition, plus awareness that it is the most abused pattern.

Singleton makes sure a class has only one instance in the process and gives a global access point to it. Typical uses are things that are naturally single: a configuration holder, a connection pool, a logger factory, an in-memory cache. To build one you make the constructor private, keep a static field with the instance, and expose a static method to get it. The problems: it is global state in disguise, so any code can reach it and change it, which hides dependencies. It is hard to unit test, because you cannot replace it with a fake, and tests leak state into each other. It couples every caller to a concrete class. In modern code the better answer is usually "one instance, but managed by a container": a Spring bean with the default singleton scope gives you a single shared instance, still injected through the constructor, still replaceable in tests. Remember that a Spring singleton is one per container, while the GoF singleton is one per class loader.

Likely follow-ups
  • Why is "one instance" not enough reason? Most things only need to be shared, not enforced as unique. Enforcing uniqueness in the class itself makes testing hard.
  • Is a class with only static methods the same? It is similar in effect, but cannot implement an interface or be injected.
How do you write a thread-safe Singleton in Java? Compare the options, including double-checked locking and enum. Intermediate

What the interviewer is testing: the Java memory model: why double-checked locking needs volatile, and which options are simplest.

There are four common ways. Eager static field: the instance is created when the class loads. It is thread-safe because the JVM guarantees class initialization happens once, and it is the simplest, but it is created even if never used. Synchronized getter: correct but takes a lock on every call, which is slow if called often. Double-checked locking: check without a lock, then lock and check again. It must declare the field volatile. Without it, the compiler or CPU may reorder the steps of new (allocate memory, assign the reference, run the constructor), so another thread can see a non-null reference to a half-built object. Holder idiom: a private static nested class holds the instance; it loads only on first use, and the JVM's class-init lock makes it thread-safe with no explicit locking. Enum singleton is recommended by Joshua Bloch in Effective Java: it is thread-safe, and safe against serialization (the enum constant is always the same) and against reflection (you cannot build another enum instance). Its limit: it cannot extend another class, and it loads eagerly like any enum.

// double-checked locking (volatile is mandatory)
class Config {
    private static volatile Config instance;
    private Config() {}
    static Config get() {
        Config local = instance;
        if (local == null) {
            synchronized (Config.class) {
                local = instance;
                if (local == null) instance = local = new Config();
            }
        }
        return local;
    }
}

// holder idiom: lazy and lock-free
class Registry {
    private Registry() {}
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    static Registry get() { return Holder.INSTANCE; }
}

// enum singleton
enum AppSettings { INSTANCE; private int timeout = 30; int timeout() { return timeout; } }
Likely follow-ups
  • Which would you pick? The holder idiom for a lazy singleton, an enum when you also need serialization safety, or just a Spring bean.
  • Can a singleton be broken? Yes, by reflection (calling the private constructor), by serialization (a new instance on deserialize unless you add readResolve), by cloning, and by several class loaders.
Common mistakes: double-checked locking without volatile; claiming synchronized on the method is "wrong" (it is correct, only slower).
Explain the Factory Method pattern and the "simple factory". When do you use them? Basic

What the interviewer is testing: can you separate "creating" from "using", and name the difference between the idiom and the GoF pattern.

The problem: code that does new EmailSender() everywhere is welded to that class, and adding SmsSender means editing all those places. A simple factory is one static method that decides which class to create, based on input. It centralises the switch, but it still has to change when a new type is added, and it is not an official GoF pattern. The Factory Method pattern is different: a base class declares an abstract method that creates the product, and subclasses decide which concrete product to create. The base class holds the common algorithm that uses the product through its interface. For example an abstract Dialog has createButton(); WindowsDialog returns a Windows button and WebDialog an HTML button, while render() in the base class works for both. Use a factory when the exact type is decided by configuration or input, when creation is complex, or when you want callers to depend only on an interface.

interface Notification { void send(String to, String msg); }
class Email implements Notification { public void send(String t, String m) { /* SMTP */ } }
class Sms implements Notification { public void send(String t, String m) { /* gateway */ } }

abstract class Alert {                        // creator
    protected abstract Notification create(); // factory method
    void raise(String to, String msg) { create().send(to, "ALERT: " + msg); }
}
class EmailAlert extends Alert { protected Notification create() { return new Email(); } }
Likely follow-ups
  • Factory method vs static factory method (List.of, Integer.valueOf)? A static factory is only a named constructor. Factory Method relies on subclassing.
  • How to avoid editing the factory when adding a type? Keep a registry map from key to supplier, filled at start-up or by Spring.
What is Abstract Factory, and how is it different from Factory Method? Intermediate

What the interviewer is testing: families of related objects, the key idea that separates it from Factory Method.

Abstract Factory is an interface with several creation methods that together produce a family of related products which must be used together. Classic example: a UI toolkit with a WidgetFactory that makes Button, Checkbox and Menu. A DarkThemeFactory makes dark versions of all three, a LightThemeFactory makes light ones. The client gets one factory and cannot accidentally mix a dark button with a light checkbox. A backend example: a CloudFactory with createStorage(), createQueue(), createSecretStore() for AWS, Azure or in-memory test mode. The difference: Factory Method creates one product and uses inheritance (subclasses override one method). Abstract Factory creates several related products and uses composition (you pass a factory object in). Its weakness: adding a new product type (say Slider) means changing the interface and every factory.

interface CloudFactory {
    BlobStore blobStore();
    MessageQueue queue();
}
class AwsFactory implements CloudFactory {
    public BlobStore blobStore() { return new S3Store(); }
    public MessageQueue queue()  { return new SqsQueue(); }
}
class LocalFactory implements CloudFactory {      // for tests and laptops
    public BlobStore blobStore() { return new InMemoryStore(); }
    public MessageQueue queue()  { return new InMemoryQueue(); }
}
Likely follow-ups
  • Real use? JDBC: a Connection makes matching Statement and PreparedStatement objects for the same driver. DocumentBuilderFactory is another.
What is the Builder pattern? Why is it better than a telescoping constructor? Basic

What the interviewer is testing: practical object construction, immutability and validation.

When a class has many fields and some are optional, constructors get ugly. With a "telescoping constructor" you write new Pizza(12, true, false, true, null, 2) and nobody knows what each argument means. JavaBean setters fix readability but leave the object half-built and mutable. A Builder collects values step by step with named methods, then build() validates and creates the final immutable object in one go. The object is never visible in a partial state, so it is safe to share across threads. Builders also let you enforce rules such as "if delivery is true then address is required" in one place. Java has no named parameters, so builders are the standard way. Lombok's @Builder generates one. Examples in the JDK: StringBuilder (a related idea), HttpRequest.newBuilder(), Stream.Builder, and in Spring UriComponentsBuilder.

public final class Pizza {
    private final int size; private final boolean cheese; private final String sauce;
    private Pizza(Builder b) { size = b.size; cheese = b.cheese; sauce = b.sauce; }
    public static Builder builder(int size) { return new Builder(size); }
    public static final class Builder {
        private final int size;                 // required
        private boolean cheese; private String sauce = "tomato";   // optional
        private Builder(int size) { this.size = size; }
        public Builder cheese(boolean c) { cheese = c; return this; }
        public Builder sauce(String s)   { sauce = s; return this; }
        public Pizza build() {
            if (size <= 0) throw new IllegalStateException("size");
            return new Pizza(this);
        }
    }
}
Pizza p = Pizza.builder(12).cheese(true).sauce("pesto").build();
Likely follow-ups
  • Builder vs a record with many fields? A record is fine up to a few fields. Past that, or with optional fields and validation, builders read better.
  • What is the "Director"? In the GoF form, an optional class that knows the order of build steps. Rarely used in practice.
  • Is a Builder thread-safe? Usually not. Use one builder per thread; the built object is the thread-safe part.
What is the Prototype pattern? What are shallow and deep copies? Intermediate

What the interviewer is testing: copy semantics and the problems with Cloneable.

Prototype creates new objects by copying an existing one, instead of building from scratch. It is useful when creation is expensive (loading data, complex setup) and you need many similar objects, or when you want to copy an object whose exact class you do not know. A shallow copy copies the fields, but references to other objects are shared: change a shared list in the copy and the original changes too. A deep copy also copies the objects they point to. In Java, Object.clone() with Cloneable is considered broken: Cloneable has no method, clone() is protected, it makes a shallow copy by default and bypasses constructors. Effective Java suggests a copy constructor or a static copy factory instead. Deep copy can also be done via serialization, but that is slow. Typical uses: game units spawned from a template, document templates, test fixtures.

class Shape {
    private final String color; private final List<Point> points;
    Shape(Shape other) {                        // copy constructor
        this.color = other.color;
        this.points = new ArrayList<>(other.points);   // copy the list (Point must be immutable)
    }
}
Likely follow-ups
  • How is it different from Factory? A factory builds a new thing from rules, Prototype copies a configured instance.
  • Is it used in Spring? Yes: bean scope prototype makes a new bean per request (a different meaning, "new each time", not "copied").
How do you choose between Factory Method, Abstract Factory, Builder and Prototype? Intermediate

What the interviewer is testing: can you pick by problem, not by name.

Ask what hurts. If callers must not know the concrete class, and there is one product that varies, use Factory Method (or a plain static factory). If several related products must change together (a "family"), use Abstract Factory. If one object has many parts or options and you need readable, validated, immutable construction, use Builder. If creating from scratch is expensive or complicated and you can copy a configured one, use Prototype. If you just need one shared instance, prefer a container-managed singleton. All of them move the new keyword out of business code, so the business code depends on interfaces.

Likely follow-ups
  • Can they combine? Yes. An abstract factory is often implemented with factory methods; a factory can return builders.

3. Structural patterns

What is the Adapter pattern? Give an example. Basic

What the interviewer is testing: integration with code you cannot change.

An adapter wraps an object with one interface and presents it as another interface that the client expects, like a travel plug adapter. You use it when you have a useful class (a third-party library, a legacy service) that does not match the interface your code uses, and you cannot or should not modify it. Example: your code uses PaymentGateway.pay(Money), but a provider SDK has charge(String currency, long cents, String card). You write StripeAdapter implements PaymentGateway, which converts arguments and calls the SDK. Your business code only sees PaymentGateway. Adapters also protect you from vendor lock-in and let you add a new provider without touching old code. JDK examples: Arrays.asList adapts an array to a List; InputStreamReader adapts a byte stream to a character reader; Collections.enumeration.

interface PaymentGateway { Receipt pay(Money amount, CardToken card); }

class StripeAdapter implements PaymentGateway {
    private final StripeClient sdk;                 // third-party, cannot change
    StripeAdapter(StripeClient sdk) { this.sdk = sdk; }
    public Receipt pay(Money amount, CardToken card) {
        var r = sdk.charge(amount.currency().code(), amount.minorUnits(), card.value());
        return new Receipt(r.id(), r.status().equals("succeeded"));
    }
}
Likely follow-ups
  • Adapter vs Facade? Adapter changes an interface to match another one; Facade gives a simpler interface to a whole subsystem.
  • Class adapter vs object adapter? Class adapter uses inheritance, object adapter holds the adaptee (composition). Prefer the object adapter.
Explain the Decorator pattern. Why not just use inheritance? Basic

What the interviewer is testing: adding behaviour dynamically, and the JDK I/O example.

A decorator wraps an object that has the same interface and adds behaviour before or after delegating to it. Because decorators have the same interface, you can stack them in any order. Take a coffee shop: Espresso costs 2. With inheritance you would need EspressoWithMilk, EspressoWithMilkAndSugar and so on; the classes multiply. With decorators, new Sugar(new Milk(new Espresso())) costs the sum, and each add-on is one small class. The JDK I/O library is the standard example: new BufferedInputStream(new GZIPInputStream(new FileInputStream(f))); each layer adds buffering or decompression on top of a plain stream. In web code, servlet filters and Spring's HandlerInterceptor are similar in spirit. Caching, retry and logging wrappers around a service are decorators too. The cost: many small objects, and harder debugging because a call passes through many layers.

interface Beverage { double cost(); }
class Espresso implements Beverage { public double cost() { return 2.0; } }
abstract class AddOn implements Beverage {
    protected final Beverage inner;
    AddOn(Beverage inner) { this.inner = inner; }
}
class Milk extends AddOn { Milk(Beverage b) { super(b); } public double cost() { return inner.cost() + 0.5; } }
class Sugar extends AddOn { Sugar(Beverage b) { super(b); } public double cost() { return inner.cost() + 0.2; } }
// new Sugar(new Milk(new Espresso())).cost() == 2.7
Likely follow-ups
  • Does order matter? Sometimes: compress then encrypt is not the same as encrypt then compress.
  • Decorator vs subclassing? Decorators are chosen at runtime, subclasses at compile time.
What is the Facade pattern? Is a service class a facade? Basic

What the interviewer is testing: simplifying a subsystem, and not confusing it with Adapter.

A facade is a class that offers one simple, high-level interface over a group of classes that are complex to use directly. The client calls orderFacade.placeOrder(request), and inside, the facade talks to inventory, pricing, payment and shipping in the right order. The client no longer needs to know those classes or the order of calls. This lowers coupling, and gives you one place to change when the subsystem changes. A facade does not hide the subsystem completely; advanced users can still reach the parts. It adds no new behaviour, only convenience and a stable entry point. An application service layer in a web app often plays the role of a facade for the domain. The risk is a facade that grows into a "god class" with all the logic. Keep it as coordination only.

class OrderFacade {
    private final Inventory inventory; private final Payment payment; private final Shipping shipping;
    OrderFacade(Inventory i, Payment p, Shipping s) { inventory = i; payment = p; shipping = s; }
    Confirmation placeOrder(OrderRequest r) {
        inventory.reserve(r.items());
        var receipt = payment.charge(r.card(), r.total());
        var tracking = shipping.schedule(r.address(), r.items());
        return new Confirmation(receipt, tracking);
    }
}
Likely follow-ups
  • Facade vs Mediator? A facade is one-way (client to subsystem) and the subsystem does not know it. A mediator is two-way: the colleagues talk through it.
What is the Proxy pattern? Name the types, and give real examples. Intermediate

What the interviewer is testing: control of access, and links to Spring AOP and Hibernate.

A proxy has the same interface as the real object and stands in front of it to control access. The client does not know it is talking to a stand-in. Types: a virtual proxy delays creating an expensive object until first use (lazy loading); a protection proxy checks permissions before calling; a remote proxy hides network calls (RMI stub, a generated REST client such as a Feign interface); a caching proxy returns saved results; a logging or smart proxy adds counting, retries or transactions. Java has built-in support: java.lang.reflect.Proxy creates a proxy for an interface at runtime, and libraries such as CGLIB or ByteBuddy create subclasses to proxy classes. Spring AOP uses these: when you put @Transactional or @Cacheable on a bean, Spring gives callers a proxy that starts the transaction, calls your method, then commits or rolls back. Hibernate uses proxies for lazy-loaded entities.

interface Report { String content(); }
class RealReport implements Report { /* loads 50 MB */ public String content() { return "..."; } }
class LazyReport implements Report {                 // virtual proxy
    private RealReport real;
    public String content() {
        if (real == null) real = new RealReport();   // load on first use
        return real.content();
    }
}
Likely follow-ups
  • Why does a Spring @Transactional method not work when called from another method in the same class? The call is this.method(), so it skips the proxy. The proxy only wraps calls that come from outside.
  • Why can a CGLIB proxy not wrap a final class or method? It works by subclassing, and final cannot be overridden.
Adapter, Decorator, Proxy and Facade all "wrap" something. How do you tell them apart? Intermediate

What the interviewer is testing: intent. The structure looks alike; the purpose differs. This is a favourite comparison question.

Look at the interface and the intent. Adapter gives a different interface from the one it wraps, to make incompatible things work together. Decorator keeps the same interface and adds new behaviour, and you can stack several. Proxy keeps the same interface and controls access to the object (lazy create, permission, remote, cache); it usually manages the real object's lifetime itself. Facade gives a new, simpler interface over many objects. A one-line memory: adapter changes the plug, decorator adds a feature, proxy guards the door, facade is a front desk.

What is the Composite pattern? Where is it used? Intermediate

What the interviewer is testing: tree structures and uniform treatment of one and many.

Composite lets you treat a single object and a group of objects in the same way. You define one interface (FileSystemNode with size()). A leaf (File) implements it directly. A composite (Folder) implements it by holding a list of children and combining their results. The client just calls size() on whatever it has, with no if (isFolder) checks, and the recursion happens inside. This fits any part-whole tree: file systems, UI components (a panel contains buttons and other panels), organisation charts, menus with sub-menus, expression trees, a shopping bundle that contains products and other bundles. The trade-off: the interface can become too general, since a leaf has to decide what add(child) means. Many designs keep child management only in the composite.

interface Node { long size(); }
record FileNode(String name, long bytes) implements Node { public long size() { return bytes; } }
class Folder implements Node {
    private final List<Node> children = new ArrayList<>();
    void add(Node n) { children.add(n); }
    public long size() { return children.stream().mapToLong(Node::size).sum(); }
}
Likely follow-ups
  • Cycles? A folder inside itself would recurse forever. Guard in add.
  • JDK example? java.awt.Container holds Components; a JPanel is both.
What is the Bridge pattern, and how is it different from Strategy and Adapter? Senior

What the interviewer is testing: a pattern that is often misunderstood. It solves two independent dimensions of variation.

Bridge splits one class hierarchy that varies in two directions into two separate hierarchies connected by composition. Suppose you have notifications of kinds Alert and Reminder, and channels Email and Sms. With inheritance you need four classes (EmailAlert, SmsAlert, ...) and each new kind or channel multiplies them. With Bridge you have an abstraction side (Notification and subclasses Alert, Reminder) which holds a reference to an implementor side (Channel with EmailChannel, SmsChannel). Now 2 kinds plus 2 channels is 4 classes, and adding a channel costs one class. Structurally it looks like Strategy (an object holds an interface). The intent differs: Strategy swaps an algorithm inside one class, while Bridge is planned up front to let two whole hierarchies evolve separately. Adapter is applied after the fact to make existing classes fit; Bridge is designed in from the start. JDBC is the textbook example: java.sql API is the abstraction, drivers are implementors; also JDK's java.util.logging front with handlers, and SLF4J with backends.

Likely follow-ups
  • When not to use it? When only one dimension varies. Then plain Strategy or an interface is enough.
What is the Flyweight pattern? Give a Java example. Senior

What the interviewer is testing: memory optimisation through sharing, and the idea of intrinsic vs extrinsic state.

When you need huge numbers of similar objects, flyweight shares the parts that are the same and passes the parts that differ from outside. The shared, unchanging part is the intrinsic state (a character's glyph shape, a tree's mesh and texture). The per-use part is the extrinsic state (the position on screen). A text editor does not create one object with font data for every letter; it keeps one Glyph per character and font, and the document stores positions. A game with a million trees keeps a few TreeType objects. Flyweights must be immutable, since many users share them, and usually come from a factory with a cache. Java examples: the String pool, Integer.valueOf caching values from -128 to 127, and Boolean.TRUE. It trades CPU and complexity for memory, so use it only when profiling shows a memory problem.

Likely follow-ups
  • Why does new Integer(5) == new Integer(5) give false but Integer.valueOf(5) == Integer.valueOf(5) give true? The second returns a cached flyweight. Compare boxed values with equals anyway.

4. Behavioral patterns

Explain the Strategy pattern with an example. How does it relate to Open/Closed? Basic

What the interviewer is testing: the single most useful pattern, and the standard cure for if-else chains.

Strategy puts a family of interchangeable algorithms behind one interface, and lets the caller (the "context") pick one and use it. The context does not know how the algorithm works, only the interface. Example: a checkout that can compute shipping by weight, by flat rate, or free over a limit. Instead of a switch inside Checkout, you write a ShippingStrategy interface and three implementations, and pass one to the checkout. Adding a fourth costs one class and no edit to Checkout, which is Open/Closed in action. You can also change the strategy at runtime (for example by customer plan). In Java 8 and later, a strategy with one method is often just a lambda or a method reference, so there is no class at all. JDK example: Comparator passed to Collections.sort; ThreadPoolExecutor's RejectedExecutionHandler.

interface ShippingStrategy { Money cost(Order o); }
class Checkout {
    private ShippingStrategy shipping;
    Checkout(ShippingStrategy s) { shipping = s; }
    Money total(Order o) { return o.subtotal().plus(shipping.cost(o)); }
}
new Checkout(o -> Money.of(5));                 // flat rate as a lambda
new Checkout(new ByWeight(0.8));
Likely follow-ups
  • How does the right strategy get chosen? A factory or a map from key to strategy, often injected by Spring as Map<String, ShippingStrategy>.
What is the Template Method pattern, and how is it different from Strategy? Intermediate

What the interviewer is testing: inheritance-based versus composition-based variation.

Template Method defines the skeleton of an algorithm in a base class, in a final method that calls steps in a fixed order. Some steps are abstract or have default behaviour, and subclasses fill them in. The base class controls the flow ("don't call us, we'll call you"). Example: a data exporter always does writeHeader(), writeRow() for each row, then writeFooter(); the CSV and JSON subclasses only supply the format-specific steps. JDK examples: AbstractList, InputStream.read(byte[]) built on read(), and in Spring JdbcTemplate (the same idea with callbacks, not inheritance). The difference from Strategy is how the variation is plugged in: Template Method varies parts of an algorithm via subclassing (fixed at compile time, strong coupling to the base), while Strategy varies the whole algorithm through composition (changeable at runtime). Prefer Strategy or callbacks when you can; use Template Method when the order of steps must be strictly controlled.

abstract class Exporter {
    public final void export(List<Row> rows, OutputStream out) throws IOException {   // the template
        writeHeader(out);
        for (Row r : rows) writeRow(r, out);
        writeFooter(out);
    }
    protected abstract void writeHeader(OutputStream o) throws IOException;
    protected abstract void writeRow(Row r, OutputStream o) throws IOException;
    protected void writeFooter(OutputStream o) throws IOException { }   // optional hook
}
Likely follow-ups
  • What is a hook? An optional step with an empty default that a subclass may override.
  • Why make the template method final? So no subclass can change the order of steps.
Explain the Observer pattern. What are its pitfalls? Basic

What the interviewer is testing: event-driven design, and real problems like memory leaks and ordering.

Observer defines a one-to-many link: a subject keeps a list of observers and notifies them when its state changes. The subject does not know what the observers do, which keeps coupling low. Examples: a stock price feed notifying many dashboards, a UI button notifying click listeners, an order service publishing "OrderPlaced" so that email, inventory and analytics react. In the JDK there is the java.util.EventListener style (Swing listeners), PropertyChangeListener, and Flow.Publisher/Subscriber in Java 9 (reactive streams). java.util.Observable is deprecated since Java 9: it is a class (not an interface), not type-safe and not thread-safe. In Spring you use ApplicationEventPublisher with @EventListener. Pitfalls: (1) memory leaks, the "lapsed listener": the subject holds a strong reference, so an observer you forgot to unregister is never garbage collected. (2) Order and exceptions: one slow or failing observer can block or break the others if notification is synchronous. (3) Thread safety: modifying the list while notifying causes ConcurrentModificationException; use CopyOnWriteArrayList. (4) Cascades and cycles, where an observer changes the subject again. (5) Hard to follow control flow when debugging.

interface OrderListener { void onPlaced(Order o); }
class OrderService {
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>();
    void subscribe(OrderListener l)   { listeners.add(l); }
    void unsubscribe(OrderListener l) { listeners.remove(l); }
    void place(Order o) {
        /* save order */
        for (OrderListener l : listeners) {
            try { l.onPlaced(o); } catch (RuntimeException e) { /* log, do not stop the rest */ }
        }
    }
}
Likely follow-ups
  • Observer vs Pub/Sub? In Observer the subject knows its observers directly (in one process). In Pub/Sub a broker sits between, and the two sides do not know each other (Kafka, SNS).
  • Push vs pull? Push sends the data in the call; pull sends only a signal and the observer asks for what it needs.
What is the Command pattern, and what do you use it for? Intermediate

What the interviewer is testing: turning a request into an object, and the undo/queue use cases.

Command wraps a request (what to do, on which receiver, with which arguments) into an object with an execute() method. Because the request is now an object, you can pass it around, store it in a queue, log it, run it later, retry it, or keep a history to undo it by adding an undo() method. The sender (a button, a scheduler) only calls execute() and does not know what happens. Examples: text editor actions with undo and redo, a job queue where each task is a command, a remote control with button slots, macro recording, transactional scripts. In the JDK, Runnable and Callable are commands, and an ExecutorService is the invoker. For an undo stack: perform the command and push it on a stack; undo pops it and calls undo(). A command that needs to be undone must save enough state (the old text, the old value) when it executes.

interface Command { void execute(); void undo(); }
class InsertText implements Command {
    private final Document doc; private final String text; private final int pos;
    InsertText(Document d, int p, String t) { doc = d; pos = p; text = t; }
    public void execute() { doc.insert(pos, text); }
    public void undo()    { doc.delete(pos, text.length()); }
}
Deque<Command> history = new ArrayDeque<>();
Command c = new InsertText(doc, 0, "Hi"); c.execute(); history.push(c);
history.pop().undo();
Likely follow-ups
  • Command vs Strategy? A command is a request ("do this now or later"), a strategy is a way of doing a job. Commands are usually one-shot and carry their data.
Explain the State pattern. How would you model an order or a vending machine with it? Intermediate

What the interviewer is testing: replacing state flags and big switches with polymorphism.

State lets an object change its behaviour when its internal state changes, so it looks as if it changed class. The naive way keeps a field like status and every method starts with if (status == PAID) ... else if (status == SHIPPED) .... With many states and many actions the code becomes a tangle that is easy to get wrong. With State, each state is a class that implements the same interface (pay(), ship(), cancel()). The context (the order) holds a current state object and forwards calls to it. Each state decides what is allowed and which state comes next, so invalid moves are simple to handle (throw or ignore) and each file is small. Adding a state is adding a class. Cost: more classes, and the transitions are spread across them, so keep a diagram of the state machine. For simple machines with few states an enum with abstract methods or a transition table is enough.

interface OrderState { OrderState pay(); OrderState ship(); OrderState cancel(); }
final class NewState implements OrderState {
    public OrderState pay()    { return new PaidState(); }
    public OrderState ship()   { throw new IllegalStateException("pay first"); }
    public OrderState cancel() { return new CancelledState(); }
}
final class PaidState implements OrderState {
    public OrderState pay()    { throw new IllegalStateException("already paid"); }
    public OrderState ship()   { return new ShippedState(); }
    public OrderState cancel() { return new CancelledState(); }
}
class Order {
    private OrderState state = new NewState();
    void pay()  { state = state.pay(); }
    void ship() { state = state.ship(); }
}
Likely follow-ups
  • Who triggers transitions: context or state? Both work. States returning the next state keep the rules in one place.
  • Persisted state? Store the state name in the database, and rebuild the state object from it.
State and Strategy have the same class diagram. What is the difference? Intermediate

What the interviewer is testing: intent over structure again.

Both hold a reference to an interface and delegate to it. The difference is who changes it and why. In Strategy, the client chooses the algorithm from outside, usually once, and the strategies do not know about each other. They are alternatives for the same job (sort by price or by name). In State, the object changes its own state object as it works, and the states often know the next state (Paid goes to Shipped). The behaviours are not alternatives for the same job but phases in the life of the object. A simple test: if the choice comes from the caller or configuration, it is Strategy. If the choice follows from what has already happened to the object, it is State.

What is the Chain of Responsibility pattern? Give a real example. Intermediate

What the interviewer is testing: pipelines and filters. This is how most web frameworks work.

A request passes along a chain of handlers. Each handler decides to handle it, to change it and pass it on, or to stop the chain. The sender does not know which handler will do the work. The handlers are linked by a "next" reference, or are held in a list. Real examples: servlet Filter chains and Spring Security's filter chain (authentication, then authorization, then CSRF, then the controller), an expense approval flow (manager up to 1,000, director up to 10,000, else VP), support escalation, and validation pipelines. It is a good fit when the set of steps changes, or when different requests need different steps. Risks: a request may fall off the end with no handler, so decide on a default; the order is important and implicit; and debugging needs good logging of which handler did what. Variants: in the "pure" form exactly one handler handles it; in the "pipeline" form every handler gets a turn (servlet filters).

interface Handler { void handle(Request r, Chain next); }
class Chain {
    private final List<Handler> handlers; private int i = 0;
    Chain(List<Handler> h) { handlers = h; }
    void proceed(Request r) { if (i < handlers.size()) handlers.get(i++).handle(r, this); }
}
class AuthHandler implements Handler {
    public void handle(Request r, Chain next) {
        if (!r.hasValidToken()) throw new UnauthorizedException();
        next.proceed(r);
    }
}
Likely follow-ups
  • Chain vs Decorator? Both wrap in layers. In a chain a handler may stop the flow and the request is the thing passing through; in a decorator every layer adds to a result.
What is the Iterator pattern, and how does it work in Java (including fail-fast)? Basic

What the interviewer is testing: the pattern you use every day, and what really happens under for-each.

Iterator gives a way to walk through the elements of a collection one by one without exposing how the collection stores them. In Java, a class that implements Iterable<T> returns an Iterator<T> with hasNext() and next() (and optionally remove()), and the enhanced for loop calls those for you. The benefit is that the loop code is the same for an ArrayList, a HashSet or your own tree. Most JDK collections have fail-fast iterators: the collection counts its structural changes in a modCount field, the iterator remembers the count when created, and if the collection is changed by anything other than the iterator itself, the next call throws ConcurrentModificationException. It is a best-effort bug detector, not a thread-safety guarantee. Concurrent collections such as CopyOnWriteArrayList and ConcurrentHashMap have weakly consistent iterators that never throw it. To write your own, implement Iterable and return an iterator, possibly a lazy one.

class Range implements Iterable<Integer> {
    private final int from, to;
    Range(int from, int to) { this.from = from; this.to = to; }
    public Iterator<Integer> iterator() {
        return new Iterator<>() {
            private int cur = from;
            public boolean hasNext() { return cur < to; }
            public Integer next() { return cur++; }
        };
    }
}
for (int x : new Range(0, 3)) System.out.println(x);   // 0 1 2
Likely follow-ups
  • How to remove while iterating? Use iterator.remove() or list.removeIf(...).
  • Internal vs external iteration? for is external (you control). forEach and streams are internal (the collection controls).
What is the Mediator pattern, and how is it different from Observer? Senior

What the interviewer is testing: managing many-to-many dependencies.

When many objects need to talk to many others, direct links produce a spaghetti of dependencies: N objects can have N times N links. Mediator puts a central object in the middle. Colleagues only talk to the mediator, and the mediator knows the rules about who needs to hear what. Examples: an air-traffic control tower (planes talk to the tower, never to each other), a chat room (users send to the room, the room delivers), a dialog box where the form controls enable and disable each other through the dialog class, and in Spring MVC the DispatcherServlet that coordinates handlers, view resolvers and converters. The difference from Observer: Observer is one-way and broadcast, the subject does not care who listens. Mediator has the interaction logic inside it, and colleagues report to it and get directed responses. The risk: the mediator can become a god class that knows everything. Keep it focused on coordination.

interface ChatRoom { void send(String from, String msg); void join(User u); }
class SimpleRoom implements ChatRoom {
    private final List<User> users = new ArrayList<>();
    public void join(User u) { users.add(u); }
    public void send(String from, String msg) {
        for (User u : users) if (!u.name().equals(from)) u.receive(from, msg);
    }
}
Likely follow-ups
  • Mediator vs event bus? An event bus is a loose, generic mediator. A true mediator has explicit rules for each interaction.
Explain the Visitor pattern. When is it a good fit, and what is double dispatch? Senior

What the interviewer is testing: adding operations to a stable class hierarchy, and a deep understanding of dispatch.

Visitor lets you add new operations to a set of classes without changing them. Take a stable tree of node types: Num, Add, Mul (an expression tree). You want to compute it, print it, and later optimise it. Instead of adding each operation as a method in every node class, you write one Visitor interface with visitNum, visitAdd, visitMul, and each node has accept(Visitor v) that calls the matching method on the visitor. A new operation means a new visitor class; the node classes do not change. Double dispatch: Java picks a method by the runtime type of only one object (the receiver). To choose by the types of two objects (node and visitor), the node calls v.visitAdd(this) inside accept: the first dispatch selects Add.accept, the second selects visitAdd on the concrete visitor. The pattern fits when the types are stable but operations change (compilers, syntax trees, tax rules over a fixed set of products). It is a poor fit when new node types are added often, since every visitor must change. Java has examples in FileVisitor (Files.walkFileTree) and javax.lang.model. With Java 21 sealed interfaces and pattern matching for switch, many visitors can be replaced by a plain switch that the compiler checks for completeness.

interface Expr { <R> R accept(Visitor<R> v); }
record Num(int v) implements Expr { public <R> R accept(Visitor<R> vis) { return vis.visitNum(this); } }
record Add(Expr l, Expr r) implements Expr { public <R> R accept(Visitor<R> vis) { return vis.visitAdd(this); } }
interface Visitor<R> { R visitNum(Num n); R visitAdd(Add a); }
class Calc implements Visitor<Integer> {
    public Integer visitNum(Num n) { return n.v(); }
    public Integer visitAdd(Add a) { return a.l().accept(this) + a.r().accept(this); }
}

// Java 21 alternative with a sealed interface
sealed interface Node permits Lit, Plus {}
record Lit(int v) implements Node {}
record Plus(Node l, Node r) implements Node {}
static int calc(Node n) {
    return switch (n) { case Lit x -> x.v(); case Plus p -> calc(p.l()) + calc(p.r()); };
}
Likely follow-ups
  • Downside? It breaks encapsulation a bit (visitors need access to node data) and it is verbose.
What are the Null Object and Memento patterns, in short? Intermediate

What the interviewer is testing: two smaller patterns that remove null checks and support undo.

Null Object replaces null with an object that does nothing, so callers do not need if (x != null). For example a NoOpLogger that implements Logger with empty methods, or Collections.emptyList(). It removes a whole class of NullPointerException and keeps the calling code clean. Use it only when "do nothing" is a sensible default; if a missing value is an error, fail instead. Optional is the other tool for return values that may be absent. Memento captures an object's internal state in a separate snapshot object, so the object can be restored later, without exposing its internals. The editor (originator) creates a memento, a caretaker (the history stack) stores it, and undo asks the originator to restore from it. It is the state-saving approach to undo, while Command undoes by applying the inverse action. It uses more memory but is simpler for complex states. Serialization based checkpoints and "save game" use the same idea.

class NoOpLogger implements Logger { public void info(String m) { } public void error(String m) { } }
record Snapshot(String text, int cursor) {}      // memento (immutable)
class Editor {
    private String text = ""; private int cursor;
    Snapshot save() { return new Snapshot(text, cursor); }
    void restore(Snapshot s) { text = s.text(); cursor = s.cursor(); }
}
Your app slowly runs out of memory and a heap dump shows many old listeners. What is the pattern problem, and how do you fix it? Senior

What the interviewer is testing: can you connect a design pattern to a production memory leak.

This is the lapsed listener problem in Observer. A long-lived subject (a singleton event bus, a static registry, an application-wide service) keeps a strong reference to every listener in its list. A short-lived object, such as a screen, a request handler, or a session component, registers itself and is later dropped, but never unregisters. The subject still points to it, so the garbage collector cannot free it or the object graph behind it, and the list grows forever. How to confirm: in the heap dump follow "path to GC roots" for a leaked listener, and you will see the subject's list. Fixes: always pair subscribe with unsubscribe in a lifecycle method (close(), @PreDestroy); return an AutoCloseable subscription token from subscribe so it works with try-with-resources; hold listeners through WeakReference (or a WeakHashMap keyed by listener) when you cannot control the lifetime, accepting that the listener may disappear if nothing else holds it; and monitor the listener count with a metric.

Likely follow-ups
  • Any other leak form? Anonymous inner classes and lambdas capture the enclosing object, so registering this::onEvent keeps the whole outer object alive.

What are the types of dependency injection, and which one do you prefer? Why? Basic

What the interviewer is testing: practical DI sense, immutability and testability.

There are three forms. Constructor injection passes dependencies as constructor arguments. Setter injection uses setter methods after construction. Field injection puts @Autowired on a private field and lets the container set it by reflection. I prefer constructor injection. The dependencies can be final, so the object is immutable and always fully built; required dependencies are visible in the constructor, and a class with ten arguments warns you that it does too much (an SRP smell). You can create the class in a plain unit test with new and fakes, with no Spring needed. Field injection hides dependencies, cannot be final, needs reflection or a container in tests, and allows a half-initialized object. Setter injection is acceptable for truly optional dependencies or those that can change. Since Spring 4.3 a class with a single constructor does not even need @Autowired.

@Service
class OrderService {
    private final OrderRepository repo;
    private final PaymentGateway payments;
    OrderService(OrderRepository repo, PaymentGateway payments) {   // single constructor: no @Autowired needed
        this.repo = repo; this.payments = payments;
    }
}
Likely follow-ups
  • Circular dependencies? Constructor injection cannot resolve A needs B needs A (Spring throws, and Spring Boot 2.6 and later forbids cycles by default). That is a useful signal: break the cycle with an interface, an event, or move shared logic to a third class.
What is IoC, and how does the Spring container create and wire beans? Intermediate

What the interviewer is testing: that you know what the container does, not just the annotations.

Inversion of Control means the flow of control is reversed: instead of your code creating objects and calling libraries, a framework creates your objects, wires them and calls your code. The Spring container reads configuration (component scanning of @Component classes, @Bean methods, or XML) and builds bean definitions, which are recipes: class, scope, dependencies, init and destroy methods. Then it instantiates beans (in dependency order, singletons at start-up by default), injects dependencies, and runs lifecycle callbacks. The main order is: instantiate, inject dependencies, BeanPostProcessor before-init, @PostConstruct, afterPropertiesSet, BeanPostProcessor after-init (this is where AOP proxies are created), then the bean is ready; on shutdown @PreDestroy runs. The benefit: object creation and lifetime are in one place, so swapping implementations, adding cross-cutting behaviour, or using fakes in tests needs no change in business code.

Likely follow-ups
  • BeanFactory vs ApplicationContext? ApplicationContext extends BeanFactory with events, message resources, and eager singleton creation. Use it.
  • What if two beans match an interface? Use @Primary or @Qualifier, or inject a List or Map of all of them.
Is a Spring singleton bean thread-safe? What are the bean scopes? Intermediate

What the interviewer is testing: shared mutable state, the most common bug in Spring code.

No. Spring only creates one instance and shares it; it does nothing to make the instance thread-safe. A singleton service that is called by many request threads must be stateless (only final fields pointing to other thread-safe beans) or protect its mutable state. The classic bug is storing per-request data in a field of a singleton controller or service (the current user, a running total); two requests overwrite each other's data. Scopes: singleton (default, one per container), prototype (a new instance each time it is requested; Spring does not manage its destruction), and in web apps request, session, application and websocket. Injecting a shorter-lived bean into a singleton needs a scoped proxy (@Scope(proxyMode = TARGET_CLASS)) or ObjectProvider, otherwise the singleton gets one instance at start-up and keeps it forever.

Likely follow-ups
  • Prototype injected into a singleton? It is created once, at wiring time. Use ObjectProvider<T>.getObject() for a fresh one each call.

6. Anti-patterns, immutability, thread-safe design, UML and architecture

What are the common design anti-patterns and code smells you look for in a review? Intermediate

What the interviewer is testing: can you name the problem you see, and suggest the fix.

An anti-pattern is a common solution that looks fine at first but causes trouble later. The ones I meet most: God class (one class that knows and does everything; fix by splitting by responsibility). Spaghetti code (no structure, tangled control flow). Shotgun surgery (one change forces edits in many classes; a sign the concept is spread too thin, so gather it). Divergent change (one class changed for many unrelated reasons; an SRP violation). Feature envy (a method uses another class's data more than its own; move it there). Primitive obsession (using String and double for emails and money; make small value types such as Money and Email). Anemic domain model (entities are only getters and setters, and all logic sits in services). Singleton abuse and global state. Service locator (code asks a global registry for its dependencies; they are hidden, unlike injection). Golden hammer (using the same favourite pattern or tool for every problem). Premature abstraction (interfaces with one implementation "just in case"). Copy-paste programming. Magic numbers and strings. Long parameter lists and long methods (extract method, parameter object). Switch on type (use polymorphism). For each one, I name the smell, say what change it makes harder, and refactor in small steps with tests.

Likely follow-ups
  • How do you refactor safely? Write characterization tests first, change in small steps, run tests after each, and avoid mixing refactoring and new features in the same commit.
What is an anemic domain model, and what is the alternative? Senior

What the interviewer is testing: object-oriented thinking versus data-plus-scripts thinking.

An anemic model has entity classes with only fields, getters and setters, while all business rules live in *Service classes that read and write those fields. It looks object-oriented but it is procedural: the data and the rules that protect it are apart, so any code can put an entity into an invalid state (set an order to SHIPPED with no items). Rules also get duplicated across services. A rich domain model puts behaviour with the data. Order.addItem() checks the rules, Order.ship() checks the state, and setters are replaced by methods named after business actions. The object protects its own invariants (rules that must always be true). Services stay thin: load, call the domain method, save. That follows "tell, don't ask" and encapsulation. Be fair about it: for simple CRUD apps, an anemic model is fine and cheaper. A rich model pays off when there are many rules and states.

class Order {
    private final List<Item> items = new ArrayList<>();
    private Status status = Status.NEW;
    void addItem(Item i) {
        if (status != Status.NEW) throw new IllegalStateException("order is closed");
        items.add(i);
    }
    void ship() {
        if (items.isEmpty()) throw new IllegalStateException("empty order");
        status = Status.SHIPPED;
    }
}
Why is immutability valuable, and how do you make a Java class truly immutable? Intermediate

What the interviewer is testing: concurrency safety by design, and the details people forget (defensive copies).

An immutable object never changes after it is built. That gives you: automatic thread safety (no locks needed, since nobody can write), safe sharing and caching, safe use as a HashMap key, easier reasoning (no hidden changes), and no need for defensive copying by callers. The costs are more object creation when values change often, and builders or "with" methods for big objects. To make a class immutable: declare it final (or make the constructor private) so no subclass can add mutability; make all fields private final; provide no setters; defensively copy mutable inputs in the constructor and mutable outputs in getters (arrays, Date, lists); do not let this escape from the constructor. Since Java 16 a record gives most of that, but a record holding a List is shallow-immutable: the list can still change unless you copy it with List.copyOf. String, Integer and the java.time classes are immutable.

public final class Booking {
    private final String id;
    private final List<String> seats;
    public Booking(String id, List<String> seats) {
        this.id = id;
        this.seats = List.copyOf(seats);       // defensive copy, unmodifiable
    }
    public List<String> seats() { return seats; }     // safe: already unmodifiable
    public Booking withSeat(String s) {                // "modify" by creating a new one
        var n = new ArrayList<>(seats); n.add(s);
        return new Booking(id, n);
    }
}
Likely follow-ups
  • Is final on a field enough? No. final List only fixes the reference; the list can still change.
  • What is "effectively immutable"? An object that is not changed after safe publication, even if its class allows changes. Risky, so prefer real immutability.
Common mistakes: returning the internal array or list from a getter; copying in the constructor but not in the getter; non-final class that a subclass can make mutable.
How do you design a class to be thread-safe? What are your options, in order of preference? Senior

What the interviewer is testing: a layered approach to shared state, and knowing that locks are the last resort.

First, avoid shared mutable state: if no state is shared or nothing changes, there is nothing to protect. Prefer, in this order. (1) Stateless classes: only local variables and method parameters, as in a good service class. (2) Immutable objects, with safe publication through final fields. (3) Thread confinement: each thread uses its own copy (local variables, ThreadLocal, one object per request); remember to clean up ThreadLocal in thread pools. (4) Concurrent building blocks from java.util.concurrent: ConcurrentHashMap, AtomicInteger, LongAdder, BlockingQueue, Semaphore. (5) Locks: synchronized or ReentrantLock around the smallest critical section, always locking the same object, with a consistent lock order to avoid deadlock. Document the thread-safety policy in the class (immutable, thread-safe, or not thread-safe). Do not forget compound actions: two thread-safe calls in a row are not atomic (if (!map.containsKey(k)) map.put(k, v) is a race; use putIfAbsent or computeIfAbsent). Also avoid calling unknown code (callbacks) while holding a lock.

class HitCounter {
    private final ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();
    void hit(String page) { hits.computeIfAbsent(page, k -> new LongAdder()).increment(); }
    long count(String page) { LongAdder a = hits.get(page); return a == null ? 0 : a.sum(); }
}
Likely follow-ups
  • volatile vs synchronized? volatile only gives visibility and ordering for one variable; it does not make count++ atomic.
  • Atomic vs lock? Atomics are lock-free for single variables; locks are needed to keep several variables consistent together.
How do you read a UML class diagram? What do the arrows mean? Basic

What the interviewer is testing: can you read and draw the notation quickly on a whiteboard.

A class is a box with three parts: name, fields, methods. A + means public, - private, # protected. Italic names or <<interface>> mark abstract types. The relationships, from weakest to strongest: Dependency (dashed arrow): one class uses another briefly, as a parameter or local variable. Association (plain line or arrow): one class holds a reference to another as a field. Aggregation (hollow diamond on the whole side): "has-a" where the part can live without the whole (a Team has Players; players exist if the team is deleted). Composition (filled diamond): "owns-a" where the part dies with the whole (an Order owns its OrderLines). Inheritance (solid line, hollow triangle at the parent): "is-a" for classes. Realization (dashed line, hollow triangle): a class implements an interface. Numbers at the line ends are multiplicity: 1, 0..1, * or 1..*. In an interview, draw boxes with names and the key methods, label arrows with multiplicity, and skip anything that does not help the discussion.

Likely follow-ups
  • How do I tell aggregation from composition in code? Ask: if the whole is deleted, should the part go too? Yes means composition (the whole creates and owns the part). In code, both are usually just a field; the difference is lifetime.
Explain clean architecture or hexagonal architecture (ports and adapters). How is it different from classic layered architecture? Senior

What the interviewer is testing: DIP applied to a whole application.

In a classic layered app (controller, service, repository), dependencies point downward, so business logic ends up depending on the database layer, and often on the framework types. In hexagonal architecture (Alistair Cockburn) you put the business logic (domain and use cases) in the centre. The centre defines ports, interfaces for what it needs (OrderRepository, PaymentGateway) and for what it offers (PlaceOrderUseCase). Outside the centre are adapters that plug into those ports: a REST controller or a Kafka consumer drives the app (inbound adapters), and a JPA repository or Stripe client is driven by the app (outbound adapters). All dependencies point inwards, to the domain. Clean architecture (Robert Martin) is the same idea in rings: entities, use cases, interface adapters, frameworks, with the "dependency rule": source code dependencies only point inward. The gains: domain logic is testable without a database or a web server, frameworks and databases are replaceable details, and the core stays clean. The cost: more interfaces and mapping between models. It pays off for long-lived business-heavy systems, less so for small CRUD services.

Likely follow-ups
  • Where do JPA annotations go? Ideally in the adapter's own entity classes, mapped to and from the domain objects. Many teams accept annotated entities as a practical compromise.
  • Is this over-engineering for microservices? For a thin CRUD service, yes. Use it where domain rules are rich.
What are Repository, DAO, DTO and Service Layer? How do they differ? Intermediate

What the interviewer is testing: the enterprise application vocabulary used in every Java codebase.

A DAO (Data Access Object) wraps one table or data source: findById, insert, update, close to the database shape. A Repository (from Domain-Driven Design) looks like an in-memory collection of domain aggregates: orders.add(o), orders.findByCustomer(c). It speaks in domain terms and hides persistence completely. In practice Spring Data's JpaRepository is used for both. A DTO (Data Transfer Object) is a plain data carrier for crossing a boundary, such as a JSON body or a message, so you do not expose entities, and can shape the data for the client. Records are a good fit. A Service layer holds use-case logic and transaction boundaries and coordinates repositories and domain objects. A Mapper converts between entity and DTO (MapStruct is common). Keep entities out of controllers: exposing them couples your API to your tables and risks lazy-loading errors and accidental over-exposure of fields.

Likely follow-ups
  • Where does validation go? Format checks on the DTO at the edge, business rules in the domain.
How have lambdas, records and sealed types changed the classic patterns in modern Java? Senior

What the interviewer is testing: do you use patterns with judgement in modern code, rather than copy 1994 diagrams.

Many patterns existed to work around missing language features. Strategy and Command and Observer callbacks are lambdas: Comparator.comparing(User::age) is a strategy with no class. Template Method often becomes a method taking a function argument (executeInTransaction(tx -> ...)). Iterator is built into for-each and Stream. Builder is reduced for small data by records with compact constructors for validation, though large objects still use builders. Visitor is mostly replaced by sealed interfaces plus pattern matching for switch (Java 21), which gives completeness checking: if you add a new subtype, the compiler flags every switch that misses it. Singleton is usually a container bean or an enum. Decorator can be done with function composition (Function.andThen). The main ideas, separate what varies, program to interfaces, prefer composition, still apply; only the amount of ceremony shrinks. Patterns that still need classes: State with real behaviour, Composite, Proxy, Adapter, Facade, and Chain when handlers hold state.

record Card(String number) implements Payment {}
record Upi(String vpa) implements Payment {}
record Wallet(String id) implements Payment {}
String describe(Payment p) {
    return switch (p) {            // compiler checks all cases are covered
        case Card c   -> "card ending " + c.number().substring(c.number().length() - 4);

Service Locator vs Dependency Injection: why is injection preferred? Intermediate

What the interviewer is testing: hidden dependencies and their cost.

With a service locator, a class asks a global registry for what it needs inside its methods: ServiceLocator.get(PaymentGateway.class). With dependency injection, the dependencies are given to it from outside. The locator works and is simple, but the dependencies are hidden: from the constructor you cannot tell what the class needs, so you find out at runtime with a failure. Tests must set up the global registry, which is shared mutable state and leaks between tests. The class is coupled to the locator itself. With DI the class declares what it needs in its constructor, tests pass fakes with no global setup, and wiring problems appear at start-up. A locator can still be fine at the edge of a system, for code the container cannot construct (for example a legacy class or a plugin loaded by name). The JDK's ServiceLoader is a locator for plug-ins.

What makes code easy to unit test, in terms of design? Intermediate

What the interviewer is testing: that you see testing as a design tool.

Code is easy to test when its collaborators can be replaced and its results are visible. Concretely: dependencies are injected through constructors, so a test can pass a fake. Time, random numbers and IDs come from small interfaces (Clock, IdGenerator), not from LocalDateTime.now() and UUID.randomUUID() in the middle of logic. There are few static calls and no hidden singletons. Business rules are in plain classes (no framework types), and I/O sits at the edge, behind interfaces, which is the hexagonal idea. Methods return values or have clear observable effects, rather than only changing hidden state. Classes are small and follow SRP, so a test needs little setup. If a test needs ten mocks, the class has too many dependencies; if a test needs to mock a mock of a mock, there is a Law of Demeter problem. Use real objects for simple value types, fakes for repositories, and mocks mainly to verify an important interaction.

Likely follow-ups
  • Mock vs fake vs stub? A stub returns canned answers, a mock verifies calls, a fake is a working simple version (in-memory repository).

7. LLD exercises with full worked designs

What is your step-by-step approach in a low-level design interview? Basic

What the interviewer is testing: structure and communication. Most failed LLD rounds fail on approach, not on knowledge.

I follow the same steps every time and say them aloud. 1. Clarify requirements (3 to 5 minutes): what must it do, what is out of scope, how many users, is it concurrent, do we need persistence. Write the list down. 2. Find the entities: nouns in the requirements become candidate classes (Vehicle, Ticket, Spot), verbs become methods. 3. Define relationships: who owns whom, one-to-many, and which are interfaces. 4. Find what varies: pricing rules, matching rules, channels. Put those behind an interface (Strategy), and say which pattern and why. 5. Draw the class diagram, small, with only the important methods. 6. Write the core flow in code: the main method (park a car, place a bet, send a notification) and the one tricky class. 7. Handle concurrency and errors: where two threads can collide, and what happens on failure. 8. Discuss extensions: "what if we add X?", and show that the design absorbs it with a new class, not an edit. Do not start with patterns; start with requirements. Keep it simple and name the trade-offs.

Likely follow-ups
  • How much code should I write? The interfaces and core classes, not getters, setters, or main methods that wire up examples.
  • What if requirements are vague? Ask, then state your assumptions clearly and move on.
Design a parking lot. Senior

What the interviewer is testing: the most common LLD question: entities, Strategy for pricing and allocation, and a concurrency edge case.

Requirements. Multiple levels, each with spots of types (motorcycle, compact, large, EV). Vehicles of types car, bike, truck. On entry the gate issues a ticket and assigns a spot. On exit the system computes a fee by time and vehicle type, takes payment, and frees the spot. Several entry and exit gates work at the same time. Out of scope: reservations, physical sensors.

Classes. ParkingLot (the entry point, holds levels and strategies), Level (a list of spots), ParkingSpot (id, type, occupied), Vehicle (plate, type), Ticket (id, vehicle, spot, entry time), plus two interfaces for what varies: SpotAllocationStrategy (nearest to the gate, lowest level first) and PricingStrategy (hourly, flat, per vehicle type). A spot can fit a vehicle if its type is the same or larger, which is a method on the spot, not a switch in the lot.

enum SpotType { MOTORCYCLE, COMPACT, LARGE }
class ParkingSpot {
    private final String id; private final SpotType type;
    private final AtomicBoolean occupied = new AtomicBoolean(false);
    boolean tryOccupy() { return occupied.compareAndSet(false, true); }   // atomic claim
    void release()      { occupied.set(false); }
    boolean fits(Vehicle v) { return type.ordinal() >= v.type().minSpot().ordinal(); }
}
class ParkingLot {
    private final List<Level> levels; private final SpotAllocationStrategy allocator; private final PricingStrategy pricing;
    Ticket enter(Vehicle v) {
        for (int attempt = 0; attempt < 3; attempt++) {
            ParkingSpot s = allocator.find(levels, v).orElseThrow(LotFullException::new);
            if (s.tryOccupy()) return new Ticket(UUID.randomUUID().toString(), v, s, Instant.now());
        }                                              // lost the race to another gate: try again
        throw new LotFullException();
    }
    Money exit(Ticket t) {
        Money fee = pricing.fee(t, Instant.now());
        t.spot().release();
        return fee;
    }
}

Concurrency. Two gates may pick the same free spot at the same moment. The atomic compareAndSet in tryOccupy decides the winner; the loser picks another spot. This is cheaper than locking the whole lot. Extension questions. (1) Add EV charging spots: a new SpotType, with charging as a separate ChargingService, no change to the flow. (2) Dynamic pricing at peak hours: a new PricingStrategy, or a decorator around the base one. (3) Display board with free spots per level: Observer, spots publish occupy and release events. (4) Reservations: a spot gets a RESERVED state with an expiry. (5) Lost ticket: look up by plate and charge the maximum fee. (6) Make it distributed: the atomic claim becomes a database update with a condition (where occupied = false) or a Redis lock.

Design an elevator system. Senior

What the interviewer is testing: State pattern, a scheduling algorithm, and separation between dispatching and movement.

Requirements. A building with N floors and M elevators. Passengers press a hall button (up or down) on a floor, then press a destination button inside the car. The system chooses which elevator serves each hall call. Each elevator moves, stops at requested floors, opens and closes doors. Emergency stop and overload are extras. Out of scope: physical motor control.

Classes. ElevatorController (receives hall requests, picks a car with a DispatchStrategy), Elevator (current floor, direction, state, and two sorted sets of stops), Request (floor, direction), Direction (UP, DOWN, IDLE), Door, Button classes. For movement use the SCAN (elevator) algorithm: keep going in the current direction, serving stops on the way, and only reverse when there are none ahead. Keep upStops and downStops in TreeSets so the next stop is always the nearest in the direction of travel. The dispatcher scores each car, for example "idle and closest" or "moving towards the floor and the request is on its path".

class Elevator {
    private int floor = 0; private Direction dir = Direction.IDLE;
    private final TreeSet<Integer> up = new TreeSet<>(), down = new TreeSet<>();
    synchronized void addStop(int target) {
        if (target > floor) up.add(target); else if (target < floor) down.add(target);
        if (dir == Direction.IDLE) dir = target > floor ? Direction.UP : Direction.DOWN;
    }
    synchronized void step() {                         // called by a timer, one floor per tick
        if (dir == Direction.UP) {
            if (up.isEmpty()) { dir = down.isEmpty() ? Direction.IDLE : Direction.DOWN; return; }
            floor++;
            if (up.first() == floor) { up.pollFirst(); openDoor(); }
        } else if (dir == Direction.DOWN) {
            if (down.isEmpty()) { dir = up.isEmpty() ? Direction.IDLE : Direction.UP; return; }
            floor--;
            if (down.last() == floor) { down.pollLast(); openDoor(); }
        }
    }
    int cost(int target) { return Math.abs(floor - target) + (dir == Direction.IDLE ? 0 : 5); }   // simple score
}

Extension questions. (1) Peak hours (everyone goes to the lobby): a different dispatch strategy that parks idle cars at the ground floor. (2) Express and service lifts: an Elevator has allowed floors, and the dispatcher filters on it. (3) Overload: a weight sensor puts the state in Overloaded, and doors stay open. (4) Destination dispatch (the passenger enters the floor in the hall): the request carries the destination, and the dispatcher groups passengers. (5) Fault of one car: mark it out of service and reassign its pending requests. (6) Thread safety: one scheduler thread per car, or one lock per elevator; the controller never holds a lock while calling into cars.

Design an LRU cache with O(1) get and put. Intermediate

What the interviewer is testing: data structure design, and thread safety.

Requirements. Fixed capacity. get(key) returns the value or null and marks the key as most recently used. put(key, value) adds or updates, and when the cache is full, it removes the least recently used entry. Both in O(1).

Design. One structure cannot do both jobs. A HashMap gives O(1) lookup, but no order. A doubly linked list gives O(1) move and remove when you hold the node, but needs O(n) to find it. Combine them: the map goes from key to list node, and the list keeps entries from most recent (head) to least recent (tail). On get, find the node by the map and move it to the head. On put, if the key exists, update and move to head; otherwise add a new node at the head, and if the size is over capacity, remove the tail node and its map entry. Use dummy head and tail nodes to avoid null checks. The shortcut in Java is LinkedHashMap with accessOrder=true and an overridden removeEldestEntry; say you know it, then show the manual version if asked.

class LRUCache<K, V> {
    private class Node { K k; V v; Node prev, next; Node(K k, V v) { this.k = k; this.v = v; } }
    private final int capacity;
    private final Map<K, Node> map = new HashMap<>();
    private final Node head = new Node(null, null), tail = new Node(null, null);
    LRUCache(int capacity) { this.capacity = capacity; head.next = tail; tail.prev = head; }

    synchronized V get(K k) {
        Node n = map.get(k);
        if (n == null) return null;
        unlink(n); addFirst(n);
        return n.v;
    }
    synchronized void put(K k, V v) {
        Node n = map.get(k);
        if (n != null) { n.v = v; unlink(n); addFirst(n); return; }
        if (map.size() == capacity) { Node lru = tail.prev; unlink(lru); map.remove(lru.k); }
        n = new Node(k, v); map.put(k, n); addFirst(n);
    }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }

Design a rate limiter (class level). Which algorithms exist? Senior

What the interviewer is testing: Strategy for algorithms, per-key state, and race conditions.

Requirements. Limit each client (user id or API key) to a number of requests per period, for example 100 per minute. allow(clientId) returns true or false, in constant time and safe under many threads. Rules can differ by client tier. Algorithms. Fixed window: a counter per window; simple, but allows a burst of 2x the limit around a window edge. Sliding window log: store each timestamp; exact but uses memory. Sliding window counter: weighs the current and previous window counts; cheap and close to exact. Token bucket: a bucket holds up to capacity tokens, refilled at a steady rate; each request takes one token. It allows short bursts up to the capacity while keeping the average rate; it is the most common choice. Leaky bucket: requests queue and leave at a fixed rate, which smooths the output.

Classes. RateLimiter (interface: allow(key)), TokenBucketLimiter, FixedWindowLimiter as implementations (Strategy), RateLimitConfig (capacity, refill rate), a LimiterRegistry that holds one bucket per key in a ConcurrentHashMap, and a factory that picks the config by tier. A servlet filter or an interceptor calls it (Chain of Responsibility).

class TokenBucketLimiter implements RateLimiter {
    private final long capacity; private final double refillPerNano;
    private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();
    TokenBucketLimiter(long capacity, double refillPerSecond) { this.capacity = capacity; this.refillPerNano = refillPerSecond / 1e9; }

    public boolean allow(String key) {
        Bucket b = buckets.computeIfAbsent(key, k -> new Bucket(capacity, System.nanoTime()));
        synchronized (b) {                              // per-key lock: no global contention
            long now = System.nanoTime();
            b.tokens = Math.min(capacity, b.tokens + (now - b.last) * refillPerNano);   // lazy refill
            b.last = now;
            if (b.tokens >= 1) { b.tokens -= 1; return true; }
            return false;
        }
    }
    private static class Bucket { double tokens; long last; Bucket(double t, long l) { tokens = t; last = l; } }
}

No background thread is needed: the bucket is topped up lazily from the elapsed time on each call. Extension questions. (1) Distributed across many app servers: keep the counter in Redis, and do the check and update atomically with a Lua script or INCR plus EXPIRE. (2) Different limits per tier or per endpoint: key includes the endpoint, and config comes from a LimitPolicy lookup. (3) Memory growth with millions of keys: evict idle buckets (an LRU or a time-based sweep). (4) What to return: HTTP 429 with a Retry-After header. (5) Fail open or closed if the limiter store is down? Usually fail open for availability, closed for abuse-critical paths.

Design tic-tac-toe, and then explain how you would extend the design to chess. Intermediate

What the interviewer is testing: a clean small design, a smart win-check, and polymorphism for chess pieces.

Tic-tac-toe requirements. N by N board (default 3), two players alternate, the first with N in a row, column or diagonal wins, a full board with no winner is a draw. Classes. Game (players, board, turn, status), Board (grid of cells), Player (name, Symbol), Symbol enum, GameStatus enum. A naive win check scans the whole board, O(N squared) per move. The better trick: keep a counter per row, per column and for the two diagonals, for each player. A move adds one to the counters it touches, and a player wins when any counter reaches N. That is O(1) per move.

class Board {
    private final int n; private final Symbol[][] cells;
    private final int[] rows, cols; private int diag, anti, moves;   // +1 for X, -1 for O
    Board(int n) { this.n = n; cells = new Symbol[n][n]; rows = new int[n]; cols = new int[n]; }
    boolean place(int r, int c, Symbol s) {              // returns true if this move wins
        if (cells[r][c] != null) throw new IllegalStateException("cell taken");
        cells[r][c] = s; moves++;
        int d = (s == Symbol.X) ? 1 : -1;
        rows[r] += d; cols[c] += d;
        if (r == c) diag += d;
        if (r + c == n - 1) anti += d;
        return Math.abs(rows[r]) == n || Math.abs(cols[c]) == n || Math.abs(diag) == n || Math.abs(anti) == n;
    }
    boolean full() { return moves == n * n; }
}

enum Level { DEBUG, INFO, WARN, ERROR }
record LogEvent(Instant time, Level level, String logger, String thread, String message) {}

class Logger {
    private final String name; private volatile Level min = Level.INFO;
    private final List<Appender> appenders = new CopyOnWriteArrayList<>();
    void log(Level l, String msg) {
        if (l.ordinal() < min.ordinal()) return;                    // cheap early exit
        LogEvent e = new LogEvent(Instant.now(), l, name, Thread.currentThread().getName(), msg);
        for (Appender a : appenders) a.append(e);
    }
}
class AsyncAppender implements Appender {
    private final BlockingQueue<LogEvent> q = new ArrayBlockingQueue<>(10_000);
    private final Appender target;
    AsyncAppender(Appender target) {
        this.target = target;
        Thread t = new Thread(() -> { try { while (true) target.append(q.take()); } catch (InterruptedException ignored) { } });
        t.setDaemon(true); t.start();
    }
    public void append(LogEvent e) { q.offer(e); }                 // drop when full, never block the app
}

class SeatLockService {
    boolean lock(Show show, List<ShowSeat> seats, String userId, Duration ttl) {
        List<ShowSeat> taken = new ArrayList<>();
        for (ShowSeat s : sorted(seats)) {
            if (s.tryLock(userId, Instant.now().plus(ttl))) taken.add(s);
            else { taken.forEach(t -> t.unlock(userId)); return false; }   // all or nothing
        }
        return true;
    }
}
class ShowSeat {
    private Status status = Status.AVAILABLE; private String owner; private Instant until;
    synchronized boolean tryLock(String user, Instant expiry) {
        boolean free = status == Status.AVAILABLE || (status == Status.LOCKED && until.isBefore(Instant.now()));
        if (!free) return false;
        status = Status.LOCKED; owner = user; until = expiry;
        return true;
    }
    synchronized boolean confirm(String user) {
        if (status == Status.LOCKED && user.equals(owner) && until.isAfter(Instant.now())) { status = Status.BOOKED; return true; }
        return false;
    }
    synchronized void unlock(String user) { if (status == Status.LOCKED && user.equals(owner)) status = Status.AVAILABLE; }
}

interface SplitStrategy { List<Split> split(long totalCents, List<User> users, double[] args); }
class EqualSplit implements SplitStrategy {
    public List<Split> split(long total, List<User> users, double[] ignored) {
        long share = total / users.size(), rem = total % users.size();
        List<Split> out = new ArrayList<>();
        for (int i = 0; i < users.size(); i++) out.add(new Split(users.get(i), share + (i < rem ? 1 : 0)));  // spread leftover cents
        return out;
    }

class BalanceSheet {
    private final Map<String, Long> net = new HashMap<>();       // positive = is owed, negative = owes
    void record(String payer, List<Split> splits) {
        for (Split s : splits) {
            if (s.user().id().equals(payer)) continue;
            net.merge(payer, s.cents(), Long::sum);
            net.merge(s.user().id(), -s.cents(), Long::sum);
        }
    }
    List<Payment> simplify() {                                    // greedy: biggest debtor pays biggest creditor
        PriorityQueue<Map.Entry<String, Long>> owed = new PriorityQueue<>((a, b) -> Long.compare(b.getValue(), a.getValue()));
        PriorityQueue<Map.Entry<String, Long>> debt = new PriorityQueue<>(Comparator.comparingLong(Map.Entry::getValue));
        net.entrySet().forEach(e -> { if (e.getValue() > 0) owed.add(Map.entry(e.getKey(), e.getValue())); else if (e.getValue() < 0) debt.add(Map.entry(e.getKey(), e.getValue())); });
        List<Payment> out = new ArrayList<>();
        while (!owed.isEmpty() && !debt.isEmpty()) {
            var c = owed.poll(); var d = debt.poll();
            long pay = Math.min(c.getValue(), -d.getValue());
            out.add(new Payment(d.getKey(), c.getKey(), pay));
            if (c.getValue() > pay) owed.add(Map.entry(c.getKey(), c.getValue() - pay));
            if (-d.getValue() > pay) debt.add(Map.entry(d.getKey(), d.getValue() + pay));
        }
        return out;
    }
}

How do you add a new payment provider (say Razorpay) without touching existing code? Intermediate

What the interviewer is testing: Open/Closed in a real flow: Adapter plus Strategy plus a registry.

Situation. Today CheckoutService has if (provider.equals("STRIPE")) ... else if (provider.equals("PAYPAL")) .... Product wants Razorpay next week, and Adyen next month. Design. Define a port owned by your business code: PaymentProvider with id(), charge(request), refund(paymentId), using your own request and result types (no vendor types leak out). Each vendor gets one adapter class that translates between your types and the vendor SDK, and handles vendor error codes by mapping them to your exceptions. The checkout service receives all providers as a collection, builds a map by id() in its constructor (Strategy by key), and looks up the provider named in the request. In Spring, List<PaymentProvider> is injected automatically, so a new @Component class is picked up with no change to checkout. Then adding Razorpay means: one new adapter class, its config and its own tests; nothing old is edited, so nothing old can break. Details that matter. Idempotency keys on charge so retries do not charge twice; timeouts and a circuit breaker around each vendor; vendor-specific features go behind capability methods, not into the common interface; contract tests that every adapter must pass.

interface PaymentProvider { String id(); ChargeResult charge(ChargeRequest r); }
@Component class RazorpayProvider implements PaymentProvider {
    public String id() { return "RAZORPAY"; }
    public ChargeResult charge(ChargeRequest r) { /* call the SDK, map the response */ return null; }
}
@Service class CheckoutService {
    private final Map<String, PaymentProvider> providers;
    CheckoutService(List<PaymentProvider> list) {
        providers = list.stream().collect(Collectors.toMap(PaymentProvider::id, p -> p));
    }
    ChargeResult pay(String providerId, ChargeRequest r) {
        PaymentProvider p = providers.get(providerId);
        if (p == null) throw new UnsupportedProviderException(providerId);
        return p.charge(r);
    }
}
You inherit a 3,000-line OrderManager god class that everyone is afraid to change. How do you refactor it? Senior

What the interviewer is testing: a safe, incremental plan, not "rewrite it".

Situation. One class does validation, pricing, stock, payment, emails, persistence and reporting. Merge conflicts are daily, and changes cause surprising bugs. First checks. Look at the change history and find which parts change together and which change alone (the version control log is the best map of responsibilities). List the responsibilities and the fields each method group uses. A group of methods using the same few fields is a class waiting to be extracted. Check test coverage. Plan. (1) Add characterization tests around the public behaviour so I can detect breakage. (2) Extract the easiest, most independent part first (for example email sending) into its own class, and make OrderManager delegate to it. Keep the public API unchanged. Run tests, merge to main, repeat. Small steps in production beat a long-lived refactoring branch. (3) Extract by responsibility: PricingService, StockService, PaymentService, OrderRepository. Introduce interfaces where a second implementation or a fake is useful. (4) Replace static calls and new with injected dependencies as you go. (5) When only a thin coordinator is left, rename it to what it is (PlaceOrderUseCase). (6) For code that cannot be extracted yet, wrap it behind an interface (the "strangler" approach) and move gradually. Prevention. Add a rule in review for class size and the number of dependencies, track ownership by module, and write new features as new classes, not new methods on the god class.

  • Business wants features meanwhile? Do the refactoring on the code you touch for the feature (the boy-scout rule), so it improves with delivery.
Services A, B and C all call each other, and the app fails at start-up with a circular dependency. How do you untangle it? Senior

What the interviewer is testing: dependency direction, DIP and events.

Situation. OrderService calls InventoryService, which calls PricingService, which calls back into OrderService for the order history. Spring reports a cycle (Boot 2.6 and later refuses it by default). The quick fix, @Lazy or setting allow-circular-references, only hides the problem. What I check. Draw the dependency graph and find why the back edge exists. Usually one of two reasons: (a) a shared piece of logic lives in the wrong place, and both need it; or (b) a lower-level class needs to notify a higher-level one. Fixes. For (a): extract the shared logic into a third class that both depend on (so the arrows point one way), or move the method to the class that owns the data. For (b): invert the dependency. The low-level class defines a small interface (OrderHistoryProvider) and the high-level class implements it (DIP), or the low-level class publishes an event and the high-level class listens (Observer). Where possible, pass the data needed as a method argument instead of calling back. Prevention. Define layers and check them automatically (ArchUnit tests can fail the build on cycles and on wrong-direction imports). Prefer constructor injection, since it makes cycles fail early and loudly.

Unit tests pass alone, but fail when run together, and the culprit is a Singleton holding state. How do you fix it? Intermediate

What the interviewer is testing: global state, test isolation and the cost of the Singleton pattern.

Situation. A ConfigManager.getInstance() or CacheManager.getInstance() is used all over the code. Tests set values in it, and the next test sees them. Run order changes, and the CI fails randomly. What I check. Find the shared static state (singletons, static caches, static counters). Run the failing tests in a different order to confirm the leak. Short-term fix. Add a package-private reset() or clear in @BeforeEach/@AfterEach, so tests do not leak. That is a bandage. Real fix. Remove the global access: make the class a normal class with a normal constructor, create exactly one instance at the application root (or let Spring manage it as a singleton bean), and inject it into whoever needs it through constructors. Tests then create their own fresh instance or a fake. Do this one caller at a time: first extract an interface, make the old getInstance() return the one shared instance, move callers to injection gradually, and finally delete getInstance(). Prevention. No static mutable state without a very good reason; run tests in random order in CI so such leaks show up early; use Clock, not System.currentTimeMillis().

A @Transactional method is not rolling back or not starting a transaction. The code looks correct. What do you check? Senior

What the interviewer is testing: that you understand the Proxy pattern behind Spring annotations.

Situation. OrderService.process() (not transactional) calls this.saveAll(), which is annotated @Transactional. Data is written, an exception happens, but nothing is rolled back. What I check, in order. (1) Self-invocation: a call inside the same class goes straight to this, not through the Spring proxy, so the transaction advice never runs. (2) Visibility: with proxy-based AOP the method must be public and the class must not be final (for CGLIB). (3) Exception type: by default Spring rolls back on unchecked exceptions (RuntimeException and Error) only, not on checked exceptions; use rollbackFor. (4) The exception is caught and swallowed inside the method, so the proxy never sees it. (5) The bean was created with new, not by Spring, so it is not proxied at all. (6) The transaction runs on a different thread (@Async or a parallel stream); transaction context is bound to the thread. (7) Wrong propagation, for example REQUIRES_NEW committing independently. Fixes. Move the transactional method to another bean and call it from outside (the cleanest), or put @Transactional on the outer public method, or use TransactionTemplate for explicit control. Prevention. Know that annotations are implemented by proxies; keep transaction boundaries on service-layer entry methods; add an integration test that forces a failure and checks the rollback.

A change to a parent class broke three subclasses in other modules. How do you prevent this class of problem? Senior

What the interviewer is testing: the fragile base class problem and the move to composition.

Situation. A base class BaseReportJob had a protected run() that called prepare() then execute(). Someone changed it to call execute() before validate() and also added a new call to an overridable method. Subclasses that relied on the old order or overrode that method broke, and the base team had no idea who depended on what. What I check. Which subclasses override which methods, and what each assumes about the call order (hidden coupling through inheritance). Short-term. Revert or fix forward with a compatibility path, then agree on a documented contract of which methods are for overriding, and make the rest final. Long-term. (1) Replace "extend and override" by "compose and plug in": the job holds a ReportStep or Exporter strategy that is passed in. The base flow is then a normal class with a small public interface, and subclasses become small implementations of that interface. (2) Where inheritance stays (Template Method), make the template method final, keep the number of hooks small, and document the order. (3) Make classes final by default ("design for inheritance, or forbid it"). (4) Add contract tests that every subclass must pass. Prevention. Treat inheritance as a public API with a stability promise; do not use it merely to share code.

A third-party SDK is used directly in 200 files, and the vendor just released an incompatible version. How do you get out of this, and how do you stop it happening again? Senior

What the interviewer is testing: Adapter, anti-corruption layer and the cost of letting a vendor shape your domain.

Situation. Vendor types (com.vendor.Customer, their exceptions, their builders) appear in the controllers, services and tests. The upgrade changes names and behaviour, so 200 files need edits. Plan. (1) Introduce an interface in your own words (CustomerDirectory with your own Customer type) that offers only what you use. List actual uses first, which is usually a small subset of the SDK. (2) Write an adapter that implements it with the old SDK version, so behaviour stays the same. (3) Migrate callers to the interface in small batches, module by module; each batch is a safe, reviewable change; use IDE refactoring and a lint rule (ArchUnit or a banned-import check) to stop new direct uses. (4) When the last direct use is gone, upgrade the SDK. Only the adapter changes, with contract tests that run against both the fake and the real vendor sandbox. This is an anti-corruption layer: vendor models stop at the boundary, and the rest of the code uses your model. Cost. Some mapping code, and the temptation to make the interface too wide. Keep it narrow and shaped by your needs, not by the vendor's API. Prevention. Treat every external library with a large API surface (cloud SDKs, payment, messaging) as something to wrap, but not small utilities such as Guava or Jackson.

A constructor has 14 parameters, and several are optional or of the same type, so mistakes are common. What do you do? Intermediate

What the interviewer is testing: telling apart two causes: too many responsibilities, or just a configuration object.

Situation. new Report("Q3", true, false, 10, null, "UTC", 5, ...). Callers pass arguments in the wrong order, and the compiler cannot help since many are String or boolean. What I check first. Why are there 14 values? Case 1: the class depends on 14 collaborators (services, repositories). That is an SRP problem: the class does too much, and I split it by responsibility. Case 2: the values are data and options of one concept. Then I use a better way to build it. Fixes for case 2. Group values that belong together into small value types (DateRange, PageOptions), which also removes same-type confusion (parameter object). Use a Builder for the optional ones, with defaults and validation in build(). For immutable data, a record with a builder. Use enums or small types instead of boolean flags (Format.PDF instead of true). Prevention. Lint rule for the maximum number of parameters, and look at long parameter lists in review as a design smell, not a style issue.

Placing an order takes 8 seconds because one of the "OrderPlaced" listeners (analytics) is slow, and sometimes its failure fails the order. How do you fix it? Senior

What the interviewer is testing: the hidden cost of synchronous Observer and a path to reliable events.

Situation. The order service publishes a Spring event, and the listeners run in the same thread and the same transaction by default. The analytics listener calls an external service, so the order request waits for it, and an exception in it rolls back the order. What I check. Thread dump or trace to confirm the wait is inside publishEvent; which listeners are critical (inventory reserve) and which are best effort (analytics, email). Fixes. (1) Separate the two kinds. Critical work stays in the transaction. Best-effort work runs after commit with @TransactionalEventListener(phase = AFTER_COMMIT), so a failure cannot undo the order. (2) Make slow listeners asynchronous (@Async with a bounded executor), and catch and log their exceptions, with a timeout on the external call. (3) For reliability across restarts, write the event to an outbox table in the same transaction as the order, and let a publisher send it to Kafka; consumers do their work at their own pace and are idempotent. (4) Add a metric for listener duration and failure count. Trade-off. Async means the effect is not instant and may be lost on a crash unless you use the outbox. Prevention. Every event handler declares whether it is critical, and nothing slow and external is called inside a transaction.

An intermittent bug: a request sometimes shows another user's data or a changing total. The code shares a mutable object. How do you find and fix it? Senior

What the interviewer is testing: thread safety through design: singleton state, shared mutable objects, and immutability.

Situation. Rare, hard-to-reproduce wrong values under load. What I check first. Look for state held in fields of singleton beans (services, controllers, utility classes): private Order currentOrder;, a shared SimpleDateFormat (not thread-safe), a mutable static cache, a HashMap used from several threads, a ThreadLocal not cleared in a thread pool (the next request on the same thread sees the old user), or a shared mutable DTO returned from a cache. Reproduce by hammering the endpoint with many parallel requests, and use a thread dump or tools such as the JFR lock view. Fixes. Make services stateless: pass data as parameters and return values. Replace shared mutable objects with immutable ones (records, List.copyOf, java.time classes instead of SimpleDateFormat). Where sharing is needed, use ConcurrentHashMap, atomics, or defensive copies when returning cached objects. Clear ThreadLocals in a finally or filter. Prevention. A convention: singleton beans have only final fields; mark thread-safety policy in class docs; a concurrency stress test for shared components; static analysis rules for mutable static fields.

A method has five boolean flags (process(order, true, false, true, ...)) and each new feature adds one more. How do you clean it up? Intermediate

What the interviewer is testing: spotting "control coupling" and replacing flags by types.

Situation. Flags such as sendEmail, skipValidation, isRetry, isBulk steer the behaviour inside one big method. Callers cannot read the call, flags interact in ways nobody tested (2 to the power 5 combinations), and every branch is another place for bugs. What I check. Which combinations are really used in production (search callers), and whether flags are independent options or select one of a few modes. Fixes. If the flags choose a mode (retry vs bulk vs normal), replace them with an enum or, better, with Strategy objects: separate implementations of the flow, sharing common steps through small methods or Template Method. If they are independent options, move them to an options object with a builder and named methods (ProcessOptions.defaults().withoutEmail()). If a flag switches a side effect (sendEmail), take it out of the method entirely: the method returns a result and the caller, or a listener, decides what happens next. Replace flag-based branching with state or polymorphism when flags describe the object's condition. Prevention. Treat any boolean parameter as a design question in review: "can this be two methods or a type?"

Two teams want you to share one "common" validation module, but their rules keep diverging, and every change breaks the other team. What do you advise? Senior

What the interviewer is testing: judgement on DRY and coupling between teams.

Situation. The shared module started as 200 lines of "the same" validation. Now it has flags and special cases for each team, releases are coordinated, and each change needs both teams to review. Analysis. The code looked the same, but the two uses change for different reasons (different business owners). That is accidental duplication, and merging it created coupling that costs more than the duplication did. DRY is about duplicated knowledge, not about similar-looking lines. Options. (1) If a rule really is one business fact (the format of a tax id, set by law), keep it in one small, stable library with a clear owner and semantic versioning. (2) For rules that belong to each domain, split again. Each team copies the code it needs and owns it, so they can change independently. A little duplication is cheaper than the wrong abstraction. (3) If they share a skeleton but differ in rules, keep only the skeleton (the validation framework: Rule interface, a runner) in the shared module, and let each team write its own rules (Strategy). Prevention. Use the "rule of three" before extracting, and share things that change together and have a single owner. Never allow a shared module to grow flags for each client.

A unit test needs 11 mocks and 40 lines of setup to test one method. What does that tell you, and what do you do? Intermediate

What the interviewer is testing: using test pain as design feedback.

Situation. The class under test has many dependencies, and the method calls chains like a.getB().getC().doIt(), so the test has to mock a mock of a mock. What it tells me. One or both: the class has too many responsibilities (SRP), or it breaks the Law of Demeter and is coupled to the inner structure of its collaborators. The difficulty of the test is not a testing problem; it is a design problem showing up in the test. What I do. (1) Count real responsibilities and split the class; each part then needs 2 or 3 collaborators. (2) Move pure logic (calculations, decisions) into small classes or functions with no dependencies, which can be tested with plain inputs and outputs, no mocks at all. Keep the orchestration thin and test it with a few mocks or an integration test. (3) Fix the chains: ask the direct collaborator for what you need (order.shippingCity()) so the test mocks one object. (4) Prefer simple fakes (an in-memory repository) over many strict mocks, since fakes keep tests resistant to refactoring. (5) Remove hidden dependencies on time, random and statics by injecting a Clock and similar. Prevention. Write tests while designing (or TDD for new code), and discuss "this is painful to test" in review.

A junior has applied five design patterns to a 50-line feature, and now nobody can follow it. How do you handle the review? Senior

What the interviewer is testing: engineering judgement, mentoring, and not worshipping patterns.

Situation. The pull request has an abstract factory, a builder, a strategy with one implementation, an observer for a single listener, and a facade over one class. The feature itself is a loop and two ifs. How I respond. First, I ask the author what problem each pattern solves right now. If the answer is "in case we need it later", that is YAGNI: one implementation behind an interface is just indirection. Then I show the simple version: for 50 lines, a small class with clear names is easier to read, test and change. I give a concrete rule: introduce a pattern when there are two real variations today or the change is clearly coming (a ticket exists), and when the pain of the simple code is visible, such as a growing switch or a duplicated block. I point out that refactoring to a pattern later is cheap when the code is clean and tested, so waiting is safe. I also keep it kind: the instinct to design for change is good, and the skill is to know when. For the PR, I suggest removing the speculative layers, keeping one interface only where tests need a fake, and adding the pattern when the second requirement shows up. Prevention. A team habit: "name the force" in the PR description (what hurts today), and prefer deleting code over adding layers.
