Mental model: the 8 ideas everything hangs on

One line: data engineering is "put bytes in files in a layout that is cheap to scan, add a table layer so many writers and readers stay consistent, then move data with pipelines that can safely be run twice."
  1. Format is how bytes are laid out; table format is how files become a table. Avro, Parquet and ORC are file formats. Iceberg, Delta and Hudi are table formats: they track which files make up the table right now.
  2. Row formats are good for writing and whole-record reads; column formats are good for analytics. Avro is row based (streams, messages). Parquet is columnar (analytics).
  3. A schema is a contract. Who can change it, and in which direction, decides who breaks. Compatibility rules (backward, forward, full) are the vocabulary.
  4. Object storage is cheap and immutable. You cannot edit a file in S3. You write new files and swap a pointer. That one fact explains snapshots, delete files and compaction.
  5. Metadata makes queries cheap. Min and max values per column, file lists and partition values let an engine skip most files without opening them.
  6. Files must be the right size. Many tiny files kill speed (too many opens, too much metadata). A few giant files kill parallelism. Aim for 128 MB to 1 GB.
  7. Delivery is at-least-once, so pipelines must be idempotent. Running a step twice must give the same result as once.
  8. Time has two meanings. Event time (when it happened) and processing time (when you saw it). Late data lives in the gap.

1. Row versus columnar storage

What is the difference between row-oriented and column-oriented storage, and when do you pick each? Basic

What the interviewer is testing: the most basic data engineering idea, and whether you can link it to a workload.

In a row format, all the fields of one record are stored next to each other: row 1 (id, name, city, amount), then row 2, and so on. In a columnar format, all values of one column are stored together: all ids, then all names, then all cities. Think of a spreadsheet: row storage is reading across a line, columnar storage is reading down a column. Row storage is great when you read or write whole records, for example "get order 42" or "append this event to a stream". Columnar storage is great for analytics such as "sum of amount per city for last month", because the engine reads only the two columns it needs and skips the other fifty. Columns also compress very well, because values in one column look alike (many repeated cities, ids that grow steadily). So the rule I use: row formats (Avro, JSON, Protobuf, a normal OLTP database) for transactions and messages; columnar (Parquet, ORC) for scans and aggregations over many rows.

Likely follow-ups
  • Why is a single-row insert slow in columnar files? You must touch every column block. That is why writes are batched (a file per batch) and why streaming uses a row format first.
  • Why do columns compress better? Similar neighbours: repeated values use dictionary or run-length encoding, sorted numbers use deltas.
Give three concrete reasons a columnar scan is faster than a row scan. Intermediate

What the interviewer is testing: can you go beyond "it reads fewer columns".

First, column pruning: you read only the columns the query mentions, so I/O drops from the whole table to a fraction of it. Second, compression and encoding: a column holds one data type with similar values, so dictionary, run-length and delta encodings shrink it a lot, and less data means less disk and network time. Third, skipping with statistics: every column chunk stores min, max and null count, so a filter like amount > 1000 can skip whole blocks whose max is below 1000 without reading them. A fourth reason is CPU: engines process a column as a tight array in batches (vectorised execution), which uses CPU caches and SIMD instructions well. The honest downside is point lookups and small updates, which are poor, and that you need a decent file size for the tricks to work.

Likely follow-ups
  • Does columnar always win? No. For "SELECT *" of one row, or write-heavy tiny inserts, a row store is better.
Name the common data formats (CSV, JSON, Avro, Protobuf, Parquet, ORC) and say where each fits. Basic

What the interviewer is testing: practical judgement, not memorised lists.

CSV is plain text with no types and no nesting: fine for small exports and humans, bad for pipelines (quoting bugs, no schema). JSON is self-describing text with nesting: great for APIs and logs, but big and slow, and field types are loose. Avro is a compact binary row format that carries or references a schema: the usual choice for Kafka messages and for ingestion files where you want schema evolution. Protobuf is a binary row format from Google where fields are identified by numbers: the usual choice for RPC (gRPC) and also used on Kafka. Parquet and ORC are binary columnar formats for analytics tables: Parquet is the default across Spark, Trino, Snowflake, DuckDB, and Iceberg; ORC is strongest in the Hive world. A common pipeline therefore reads JSON or Avro events from Kafka, and writes Parquet tables for analysts.

Likely follow-ups
  • Why not keep everything in JSON? It repeats field names in every record and parses slowly, so storage and CPU cost are several times higher.

2. Avro, schemas and schema evolution

What is Apache Avro and what does an Avro schema look like? Basic

What the interviewer is testing: you have really used it, not only heard of it.

Avro is a row-oriented binary serialization format from the Hadoop world. Its key idea is that data is always described by a schema, and the schema is written in JSON. The data itself carries no field names or type tags, only values, so it is very compact. Primitive types are null, boolean, int, long, float, double, bytes and string. Complex types are record, enum, array, map, union and fixed. Avro is the usual format for Kafka messages and for event files that must evolve over time. Code generation is optional: you can use a generic record (a map-like object) or generate Java classes from the schema.

{
  "type": "record",
  "name": "Order",
  "namespace": "com.shop.events",
  "fields": [
    {"name": "orderId", "type": "long"},
    {"name": "customer", "type": "string"},
    {"name": "coupon", "type": ["null", "string"], "default": null},
    {"name": "createdAt", "type": {"type": "long", "logicalType": "timestamp-millis"}}
  ]
}
Likely follow-ups
  • What is a union? A list of allowed types. ["null","string"] is the Avro way to say "optional string".
  • Where is the schema stored? Either inside the file (the object container file header) or outside, in a registry, with only an id sent per message.
How does Avro encode data in binary? Why is it so compact? Intermediate

What the interviewer is testing: internals, and the reason a reader must have the writer's schema.

Avro writes values one after another in the order the schema lists the fields. There are no field names, no field numbers and no type markers. An int or long uses a variable-length zigzag encoding: zigzag maps small signed numbers to small unsigned numbers (0, -1, 1, -2 become 0, 1, 2, 3), then the number is written in 7-bit groups, so small values take one byte. A string is its length (as a long) followed by UTF-8 bytes. A boolean is one byte. A float is 4 bytes, a double 8 bytes, little-endian. A union is the zero-based index of the chosen branch (as a long), then the value. An array is written in blocks: a count, the items, and a final zero count. Because the bytes have no self-description, you cannot decode them without the exact schema they were written with. That is the price of compactness, and the reason schema management (registry or file header) is central to Avro.

Likely follow-ups
  • Why zigzag? Plain two's complement makes negative numbers huge in varint form (10 bytes); zigzag keeps small negatives small.
  • Is the field order important? Yes, for the binary encoding the order in the writer schema defines the byte order. Resolution matches by name, not position.
Explain reader schema versus writer schema and how Avro schema resolution works. Intermediate

What the interviewer is testing: the mechanism behind safe evolution. Most candidates only know the word "evolution".

The writer schema is the one used when the bytes were produced. The reader schema is the one your code wants the data in today. Avro needs both at read time. The library decodes bytes using the writer schema, then maps the result to the reader schema using fixed resolution rules. Fields are matched by name (or by an alias). If the writer has a field the reader does not know, it is skipped. If the reader has a field the writer did not have, the reader's default value fills it, and if there is no default, resolution fails with an error. Some type promotions are allowed: int to long, float, double; long to float, double; float to double; string and bytes to each other. This is why adding a field with a default and removing a field are the standard safe changes, and why a field rename needs an alias. Old files stay readable forever, because you keep the writer schema with the data.

Common mistakes: thinking the reader can guess the writer schema from the bytes. It cannot. Another one: adding a field without a default and then being surprised that old data cannot be read.
What are backward, forward and full compatibility? Which changes are safe in each? Intermediate

What the interviewer is testing: the direction confusion trap. Many people mix up backward and forward.

Use this memory trick: the words say what the new schema can do. Backward compatible: a consumer using the NEW schema can read data written with the OLD schema. This is what you need when you upgrade consumers first and must still read old data (for example when replaying a Kafka topic from the start). Forward compatible: a consumer using the OLD schema can read data written with the NEW schema. You need this when producers upgrade first and old consumers are still running. Full: both directions. For safe changes: adding a field WITH a default is backward and forward safe (new readers use the default for old data; old readers ignore the new field). Deleting a field that HAS a default is both too. Adding a field without a default is forward compatible only (old readers ignore it) but not backward (a new reader cannot fill it for old data). Deleting a field without a default is backward compatible only. Renaming and changing a type incompatibly are breaking unless you use aliases or allowed promotions. So the practical rule is: every field you add or remove should have a default, and then you are full compatible.

Likely follow-ups
  • Why does widening int to long only work backward? A new reader (long) can read old ints, but an old reader (int) cannot read a long.
  • What about the transitive modes? See the schema registry question.
List the evolution rules for Avro you would put in a team guideline. Intermediate

What the interviewer is testing: can you turn theory into practice that a team follows.

My guideline has seven lines. One: every new field must have a default (usually null through a union with null first, or a sensible value). Two: only remove fields that have defaults. Three: never reuse a field name with a new meaning, add a new field instead. Four: never change a field type except through allowed promotions (int to long, float to double) and only after all readers are upgraded. Five: renames use aliases on the new name, or better, do not rename at all. Six: for enums, add new symbols only at the end, and give the enum a default symbol (supported since Avro 1.9) so old readers do not fail on an unknown symbol. Seven: a union with null should list "null" first when the default is null, because a default must match the first branch of the union. A registry compatibility check in CI enforces these rules automatically, so a human does not have to remember them.

{"name": "country", "type": "string", "default": "unknown"}
{"name": "fullName", "type": "string", "aliases": ["name"]}   // rename with alias
{"type": "enum", "name": "Status", "symbols": ["NEW","PAID","SHIPPED"], "default": "NEW"}
Common mistakes: writing ["string","null"] with "default": null. That is an invalid default, because it must match the first union branch.
What are Avro logical types, and what are the usual traps with them? Intermediate

What the interviewer is testing: real-world data typing: dates, times, money, ids.

A logical type is an annotation on a primitive type that tells readers how to interpret the stored value. Avro has no native date or decimal type, so it stores an int, a long, bytes or fixed, plus a logicalType label. Examples: date (int, days since 1970-01-01), time-millis (int), timestamp-millis and timestamp-micros (long, UTC instant), local-timestamp-millis (no timezone, added in 1.10), decimal (bytes or fixed, with precision and scale), and uuid (string, and fixed in newer versions). If a reader does not know a logical type, it just sees the underlying primitive, so old readers do not break. Traps: money as double loses precision, so use decimal with a declared scale. A decimal's scale is fixed by the schema, so changing it is a breaking change. Timestamps without a clear time zone meaning cause off-by-hours bugs, so store instants in UTC. And converters must be registered for logical types in the Java library, otherwise you get raw longs instead of Instant.

{"name": "amount", "type": {"type": "bytes", "logicalType": "decimal", "precision": 12, "scale": 2}}
Likely follow-ups
  • Is timestamp-millis vs micros change breaking? Yes: same long, 1000 times different meaning.
What is a Schema Registry and how does it work with Kafka and Avro? Intermediate

What the interviewer is testing: the end-to-end picture of how a message becomes readable, and where compatibility is enforced.

A schema registry is a small service that stores schemas, gives each one a numeric id, and keeps versions per subject. For Kafka the default subject name is <topic>-value (and -key). The producer serializer registers (or looks up) the schema, gets an id, and writes each message as: one magic byte (0), four bytes of schema id, then the Avro bytes. The consumer reads the id, fetches the schema from the registry once, caches it, and decodes. So each message carries 5 extra bytes instead of a full schema. The registry also enforces compatibility: before a producer can register a new version, the registry checks it against earlier versions using the subject's mode, and rejects an incompatible schema. That moves schema breakage from "consumers crash at 3 am" to "the producer deploy fails". Confluent Schema Registry is the best known; AWS Glue Schema Registry, Apicurio and others do the same job. Most also support Protobuf and JSON Schema.

Likely follow-ups
  • What if the registry is down? Clients with cached ids keep working; a new producer or new schema id fails. Run it highly available.
  • What are the subject naming strategies? TopicNameStrategy (default), RecordNameStrategy (one topic with many event types), TopicRecordNameStrategy.
Name the Schema Registry compatibility modes. What is the difference between BACKWARD and BACKWARD_TRANSITIVE, and which would you choose? Senior

What the interviewer is testing: the transitive detail, and the link to upgrade order.

The modes are NONE, BACKWARD, BACKWARD_TRANSITIVE, FORWARD, FORWARD_TRANSITIVE, FULL, FULL_TRANSITIVE. The non-transitive modes check a new schema only against the latest registered version. The transitive modes check against all earlier versions. The default in Confluent Schema Registry is BACKWARD. Why does transitive matter? Imagine v1 has no country, v2 adds it as required with a default, and v3 removes the default. v3 might be compatible with v2 but not with v1 data, and if your topic still holds v1 messages and you replay it, a v3 consumer fails. If your retention is long, or you re-read topics from the start (event sourcing, data lake loads), you want BACKWARD_TRANSITIVE. For topics with short retention where all readers move forward together, plain BACKWARD is enough. Upgrade order follows the mode: with BACKWARD, upgrade consumers first, then producers. With FORWARD, upgrade producers first. With FULL, order does not matter, which is why FULL is the safest default in multi-team organisations, even if it limits you to add and remove fields with defaults.

  • Can I change the mode per subject? Yes, there is a global setting and a per-subject override.
  • How do I make a truly breaking change? Create a new topic (or a new subject) with a new major version, dual-write for a while, migrate consumers, then retire the old one.
What is the Avro object container file, and why is it splittable? Senior

What the interviewer is testing: file-level structure, relevant for Avro files in a lake.

An Avro data file starts with a header: the magic bytes Obj plus version 1, a metadata map that holds the JSON schema and the codec (null, deflate, snappy, zstd, and others), and a random 16-byte sync marker. After the header come data blocks. Each block has the count of records, its byte size, the (optionally compressed) serialized records, and the same sync marker again. Because the sync marker is a known random value repeated between blocks, a reader that starts at any byte offset can scan forward to the next marker and start decoding cleanly. That makes Avro files splittable even when compressed (compression is per block), so a big file can be processed by many parallel tasks. The schema is stored once per file, so the file is self-describing, unlike a Kafka message where only an id is stored.

Likely follow-ups
  • Why is gzip-compressed CSV not splittable but compressed Avro is? Gzip must be read from the start; Avro compresses per block with markers.
Compare Avro, Protobuf, JSON and Parquet. How do you choose? Intermediate

What the interviewer is testing: trade-off thinking across layers, since people often compare Avro to Parquet wrongly.

First separate the roles. Avro and Protobuf are row-based serialization formats, best for messages and records in motion. Parquet is a columnar file format for data at rest and analytics. JSON is a text format that fits anywhere but is big and loosely typed. Between Avro and Protobuf: Protobuf identifies fields by number, so the reader does not need the writer schema to skip unknown fields, and it is the standard for gRPC and strongly typed code generation. Avro needs the writer schema at read time but then supports richer schema resolution (defaults, unions, aliases), and fits the Hadoop and Kafka ecosystem and schemaless storage in files. For Kafka I pick Avro if the data ends up in a lake, and Protobuf if services already use gRPC and want one schema language. For analytics tables I pick Parquet. For public APIs, JSON.

How does schema evolution in Protobuf differ from Avro? Senior

What the interviewer is testing: depth of comparison, and the "reserved field number" idea.

In Protobuf every field has a stable number on the wire, and the number is the identity. So you can rename a field freely, add new fields with new numbers, and old readers simply skip numbers they do not know. There are no required defaults: a missing field decodes to the type's zero value (proto3), which can hide "not set" versus "zero" unless you mark it optional. What breaks: reusing a field number for a different meaning, changing a field's wire type, or removing a field and later reusing its number. The cure is reserved 5; for deleted numbers. In Avro, by contrast, the name is the identity and defaults make a missing field explicit and safe, but renames need aliases and the reader needs the writer's schema. In short: Protobuf evolves by number discipline, Avro evolves by schema resolution rules.

Likely follow-ups
  • Which one is easier for many independent consumers? Protobuf, since readers need not fetch the exact writer schema. Avro with a registry is also fine.
In Java, what is the difference between GenericRecord and SpecificRecord, and where do people get burnt? Intermediate

What the interviewer is testing: hands-on experience with the library.

GenericRecord is a runtime map-like object: you read fields by name and the schema is supplied at runtime. It is flexible and good for generic tools (a data copier, a Kafka Connect transform). SpecificRecord is a class generated from the schema (with the Avro Maven or Gradle plugin): fields are typed getters, the code is faster and safer to write, but you must regenerate and redeploy when schemas change. Burn points: Avro string comes back as Utf8 (a CharSequence) unless you configure String type, so equals with a Java String fails and map lookups miss. Logical types need conversions registered, otherwise you get raw longs. When using a registry, the deserializer needs specific.avro.reader=true to return generated classes, otherwise it hands back GenericRecord. Also: generated classes using different schema versions on producer and consumer sides are exactly the writer/reader schema pair, which is how evolution works in practice.

Likely follow-ups
  • When do you choose Generic? Generic pipelines handling many schemas, schema-driven routing, or when you do not want deploys per schema change.

3. Parquet internals

How is a Parquet file organised inside? Explain row groups, column chunks, pages and the footer. Intermediate

What the interviewer is testing: the structure that makes pruning and parallel reads possible.

A Parquet file is cut horizontally into row groups: a few hundred thousand to millions of rows each, typically 128 MB uncompressed by default in many writers (some use up to 1 GB). Inside a row group, each column is stored as a column chunk, all values of that column for those rows. A column chunk is split into pages (default about 1 MB): usually one optional dictionary page, then data pages, and each page is encoded and compressed on its own. At the very end is the footer: the schema, and for each row group and column chunk the offsets, sizes, compression codec, encodings and statistics (min, max, null count). The file starts and ends with the magic bytes PAR1. A reader first reads the last few bytes to find the footer length, reads the footer, decides which row groups and columns it needs using the statistics, and then reads only those byte ranges. This is why Parquet works well on S3 with range requests. A row group is the unit of parallelism: one task can handle one row group.

Likely follow-ups
  • Why read the footer first? It is at the end because a writer streams data and only knows sizes after finishing.
  • Why not make row groups very small? More footer metadata, worse compression, and less I/O efficiency. Very large ones need lots of writer memory.
What is predicate pushdown and projection pushdown, and how does Parquet support them? Intermediate

What the interviewer is testing: why "sorted data and good stats" matter for speed.

Projection pushdown means the engine tells the file reader which columns it needs, so only those column chunks are read. Predicate pushdown means the filter is pushed down into the reader so it can skip data that cannot match. Parquet helps at several levels. File and partition level: table metadata (for example Iceberg manifests) can skip whole files. Row group level: the footer min and max skip row groups. Page level: since Parquet 1.11 the optional page index (column index and offset index) holds min and max per page, so pages are skipped too. Value level: dictionary pages and, since 1.12, bloom filters can say "this value is definitely not here", which helps for equality filters on high-cardinality columns such as ids. All of these only help when the data is arranged so that min and max ranges are narrow. If every file contains a bit of every customer, min and max span everything and nothing is skipped. That is why sorting or clustering data on the common filter column matters so much.

Likely follow-ups
  • Does a filter on a function, like lower(name) = 'x', push down? Usually not, because the stats are on the raw value. Filter on the raw column or store a derived column.
  • Do stats help with a LIKE '%abc%'? No. Only prefix patterns can use min and max.
Which encodings and compression codecs does Parquet use, and how do they differ? Senior

What the interviewer is testing: the difference between encoding (shape the data) and compression (squeeze the bytes).

Encoding is a data-aware step that rearranges values to be smaller, and compression is a general byte-level step applied after encoding. Main encodings: dictionary (store each distinct value once, then small integer codes; the writer falls back to plain when the dictionary grows too big), run-length and bit-packing hybrid (for repeated codes, booleans and levels), delta binary packed (store differences, great for timestamps and increasing ids), delta byte array (shared prefixes of strings), and byte stream split (helps floats compress). Compression codecs per column chunk: snappy (fast, moderate, the long-time default), zstd (better ratio at good speed, increasingly the default choice), gzip (smaller but slow), lz4, brotli. My rule: zstd for cold or large tables where storage and I/O matter, snappy or lz4 where CPU is the bottleneck. Low-cardinality columns such as country or status shrink the most, nearly random strings such as UUIDs shrink little, and sorting the data before writing often shrinks a file noticeably.

Likely follow-ups
  • Why does sorting reduce size? Equal values sit together, so run-length and dictionary codes repeat.
How does Parquet store nested and optional data, such as arrays and structs? Senior

What the interviewer is testing: awareness of repetition and definition levels, which explain why nested columns can be read independently.

Parquet uses the approach from Google's Dremel paper. A nested record is flattened into one column per leaf field (for example order.items.price). To rebuild the structure, each value gets two small numbers. The definition level says how many optional or repeated parts on the path are actually present, so it separates a null from an empty list. The repetition level says at which list level a new element starts, so the reader knows where one array ends and the next record begins. Both are stored compactly with run-length encoding. The practical result: you can read just items.price without touching the other fields of the struct, and nulls are cheap. The cost: deeply nested data with long lists is slower to assemble back into objects, so for heavy analytics people flatten the hot fields into top-level columns.

Likely follow-ups
  • Is a map column supported? Yes, as a repeated group of key and value.
Parquet versus ORC: how would you decide? Intermediate

What the interviewer is testing: avoiding dogma; knowing the ecosystem.

Both are columnar, compressed and carry statistics. ORC (from Hive) stores data in stripes (about 64 MB to 256 MB), with lightweight indexes and optional bloom filters, and has strong support for ACID tables in Hive. Parquet is the broader standard: it is the default in Spark, Trino, Presto, Snowflake, BigQuery, DuckDB, pandas and Arrow, and it handles nested data very well. For a new platform I choose Parquet, because every tool reads it and Iceberg and Delta default to it. I choose ORC only if the company's stack is deeply Hive-centred. Benchmarks vary by workload and by version, so the difference is usually small compared to the effect of good file sizes and sorting.

Can you update a row inside a Parquet file? Why is this hard, and how do table formats work around it? Intermediate

What the interviewer is testing: the immutability idea that motivates Iceberg and Delta.

No, not in place. Parquet files are written once, compressed in blocks, with the footer holding offsets and stats. Changing one value would shift bytes and invalidate the footer. Object stores such as S3 also cannot modify part of an object; you can only write a whole new object. So an "update" is always a rewrite. Table formats offer two strategies. Copy-on-write: rewrite every data file that contains an affected row, producing new files without the old row version. Merge-on-read: leave the data files alone, write a small delete file (listing removed rows) and a small file with the new rows, and make readers combine them. Then the table metadata is switched atomically from the old file list to the new one. The old files are not touched, so readers that started earlier still see a consistent view.

Likely follow-ups
  • So is a delete cheap? With merge-on-read, yes; the cost moves to every read until compaction.

4. Data lake, warehouse and lakehouse

What are a data warehouse, a data lake and a lakehouse? Why did the lakehouse appear? Basic

What the interviewer is testing: can you explain architecture history in a sentence and the real trade-off.

A data warehouse (Teradata, Redshift, Snowflake, BigQuery) stores structured, modelled data in its own managed storage, with strong SQL, transactions, and good performance. It is easy to use, but storage can be costly and it fits semi-structured data and machine learning less well. A data lake is cheap object storage (S3, ADLS, GCS) full of files in open formats such as Parquet, JSON, images. It is cheap, flexible and handles any data, but it historically had no transactions, no schema enforcement, and no safe updates, so many lakes turned into "data swamps" with half-written files and broken readers. The lakehouse adds a table format layer (Iceberg, Delta, Hudi) on top of the lake files. That gives ACID transactions, schema evolution, time travel, and row-level updates on cheap open storage, and any engine can read the same tables. So one copy of data serves BI, data science and streaming. The honest trade-off: you now own more moving parts (catalog, compaction, maintenance) than with a fully managed warehouse.

What is the medallion (bronze, silver, gold) architecture? Intermediate

What the interviewer is testing: practical layering of a lakehouse and where quality checks go.

It is a naming pattern for stages of refinement. Bronze holds raw data exactly as received, append-only, with ingestion metadata (source, load time). It lets you replay and reprocess anything. Silver holds cleaned and conformed data: types fixed, duplicates removed, bad rows quarantined, keys joined, often one table per business entity. Gold holds business-ready, aggregated or dimensionally modelled tables for dashboards and ML features. The value is that each layer has a clear job and a clear owner, bugs are fixed by re-running from the layer below, and raw data is never lost. It is a convention, not a technology, so do not over-engineer it: sometimes two layers are enough.

OLTP versus OLAP: why not run analytics directly on the production database? Basic

What the interviewer is testing: the reason a data platform exists at all.

OLTP (online transaction processing) systems such as PostgreSQL or MySQL serve the application: many small reads and writes, row at a time, low latency, strong consistency, normalised tables. OLAP (online analytical processing) systems answer questions over huge history: few big queries that scan millions of rows and aggregate a few columns. If you run a heavy report on the production database, it competes for CPU, memory and locks with customer requests and can slow the app down. The data is also shaped for transactions, not analysis, and has no long history. So we copy data out (CDC or batch) into an analytical store, columnar and scalable, shaped for questions. A read replica is a quick fix for light reporting, but it does not scale to history, joins across systems, or heavy aggregation.

5. Apache Iceberg

What is Apache Iceberg? What problem does a table format solve? Basic

What the interviewer is testing: the key distinction: Iceberg is not a file format and not a storage engine.

Iceberg is an open table format: a specification and library for tracking a large set of data files as one reliable table. The data files are normal Parquet (or ORC or Avro) files in object storage. Iceberg adds a metadata layer that says exactly which files belong to the table at each moment, with the schema, partitioning, and per-file statistics. Before table formats, a "table" on a lake was just a folder, and the engine listed the folder. Listing is slow on object stores. Worse, a reader could see half-written files, two writers could overwrite each other, and renaming a column meant rewriting data. Iceberg solves this with an atomic commit (swap one pointer to a new metadata file), so readers always see a complete snapshot, writers do not corrupt one another, and the file list is known without listing. It gives you ACID transactions, schema and partition evolution, time travel, and engine independence (Spark, Flink, Trino, Snowflake, Athena and others can all read and write the same table).

Likely follow-ups
  • Is Iceberg a database? No. It has no server. It is a spec plus client libraries; engines do the work.
  • Who created it? Netflix, to fix slow and unsafe Hive tables on S3; it is now an Apache top-level project.
Walk through the Iceberg metadata layers from catalog down to data files. Intermediate

What the interviewer is testing: this is the most common Iceberg question. You must be able to draw it.

Start at the top. The catalog maps a table name to the location of the current metadata file. The metadata file (metadata.json) is a JSON file with the table schema (with column ids), partition specs, table properties, the list of snapshots, and which snapshot is current. Each snapshot points to one manifest list (an Avro file). The manifest list has one entry per manifest file, with summary stats such as the partition value range and counts of added or deleted files. Each manifest file (also Avro) lists data files (and delete files), and for each file stores its path, format, partition values, record count, size, and per-column statistics (min, max, null counts). At the bottom are the data files, Parquet normally. To plan a query the engine reads the metadata JSON, one manifest list, prunes manifests by their partition ranges, reads only the useful manifests, prunes data files by column stats, and finally opens only those Parquet files. It never lists a directory.

Likely follow-ups
  • Why two levels (list and manifest)? A new commit can reuse old manifests unchanged and only add one new manifest, so commits stay small and cheap.
  • Why Avro for manifests? Compact, schema-evolving, splittable; it fits row-like metadata records.
What is an Iceberg snapshot, and how does time travel work? Intermediate

What the interviewer is testing: immutability in practice, and the cost of keeping history.

A snapshot is the complete state of the table at one point in time: the set of data files that made up the table after one commit. Every write (append, overwrite, delete, compaction) creates a new snapshot with a new id and timestamp. It does not copy data. The new snapshot reuses existing manifests and files and adds only what changed. The metadata file keeps the list of snapshots, so to read the past, the engine simply starts from an older snapshot instead of the current one. Time travel is therefore free to implement: it only needs that the old files still exist. It is useful for reproducing a report, auditing, debugging a bad load ("what did the table look like before the job?"), and quick rollback. The cost: old data files stay on storage until you expire the snapshots that reference them.

-- Spark SQL
SELECT * FROM prod.orders TIMESTAMP AS OF '2026-11-01 00:00:00';
SELECT * FROM prod.orders VERSION AS OF 4928374982374;   -- snapshot id
SELECT * FROM prod.orders.snapshots;                      -- metadata table
CALL prod.system.rollback_to_snapshot('orders', 4928374982374);
Likely follow-ups
  • Does time travel use the old schema? A timestamp query uses the schema of that snapshot in recent versions; check your engine version.
  • Branches and tags? You can name a snapshot with a tag (keep it for audit) or branch (write on it, like a staging area, then fast-forward main). Available since Iceberg 1.2 for Spark.
How does Iceberg give ACID transactions on object storage with no lock server? Senior

What the interviewer is testing: optimistic concurrency, which is the heart of the design.

A writer works in four steps. It reads the current metadata (say version 12). It writes its new data files, new manifests, a new manifest list and a new metadata file (version 13) to storage; none of these is visible yet, because no one points to them. Then it asks the catalog to do a compare-and-swap: "change the pointer from v12 to v13, only if it is still v12". That one atomic step in the catalog is the commit. If another writer committed first, the pointer is now v13 and the swap fails. The loser does not give up: it re-reads the new state, checks whether its change conflicts with what changed (for example, did the other commit delete files that mine also modified?), and if not, it rebuilds its metadata on top of the new version and retries (the default number of retries is 4, configurable). If there is a real conflict it fails with a validation error. This is optimistic concurrency control: no locks, cheap when conflicts are rare. Atomicity comes from the single pointer swap, isolation from snapshots (readers hold a snapshot and are never affected), consistency from validation, and durability from object storage. Appends rarely conflict with each other. Overlapping updates or deletes can.

Likely follow-ups
  • What isolation level? Serializable by default for deletes and overwrites, snapshot isolation optional (write.delete.isolation-level and friends).
  • What about a catalog that cannot swap atomically? The plain file-system (Hadoop) catalog is unsafe on S3 for concurrent writers. Use Glue, JDBC, REST or Hive catalogs.
Common mistakes: saying Iceberg uses S3 locking. It does not; the atomic step is in the catalog.
How does Iceberg handle schema evolution without rewriting data? Intermediate

What the interviewer is testing: the column-id idea, and why Iceberg avoids Hive's name or position bugs.

Iceberg gives every column a unique, permanent field id and stores that id in the metadata and in the data files. The engine maps columns by id, not by name or position. So you can add a column (old files simply return null for it), drop a column (the id is retired and never reused), rename a column (only the name changes, the id stays, so old files still match), and reorder columns, all as metadata-only changes with no rewrite. Type changes are allowed only when safe: int to long, float to double, and decimal precision widening. Compare with plain Parquet or Hive tables, where a name or position mapping can silently return the wrong column's data after a drop and re-add. Iceberg's id model prevents that "zombie column" problem. Each schema version is kept in the metadata, so time travel and old snapshots remain readable.

ALTER TABLE prod.orders ADD COLUMN coupon string;
ALTER TABLE prod.orders RENAME COLUMN cust TO customer;
ALTER TABLE prod.orders ALTER COLUMN qty TYPE bigint;
ALTER TABLE prod.orders DROP COLUMN legacy_flag;
Likely follow-ups
  • Can I change string to int? No, not as a metadata change; that needs a new column and a backfill.
What is hidden partitioning in Iceberg, and what problem does it solve compared with Hive-style partitioning? Intermediate

What the interviewer is testing: why many production lake queries were silently slow before Iceberg.

In Hive-style partitioning, the partition is a physical folder and a separate column, for example dt=2026-11-17. The user must add that extra column on write and put a filter on dt in every query. If an analyst filters only on event_time, the engine does not know the link, so it scans everything. In Iceberg, you declare a transform of a source column: day(event_time), month, hour, bucket(16, user_id), truncate(4, code), or identity. Iceberg computes the partition value itself on write and stores it in the metadata. When a query says WHERE event_time >= '2026-11-01', Iceberg knows how to turn that into a partition filter automatically. Users do not see or manage a partition column, so no one can forget it or fill it wrongly, and the physical layout is free to change.

CREATE TABLE prod.events (
  id bigint, user_id bigint, event_time timestamp, payload string)
USING iceberg
PARTITIONED BY (day(event_time), bucket(16, user_id));
Likely follow-ups
  • When use bucket? To spread a high-cardinality key evenly and support equality filters and joins on it.
What is partition evolution, and what happens to existing data when you change the partitioning? Senior

What the interviewer is testing: the table keeps several partition specs at once, and queries still work.

Say a table is partitioned by month and data volume grows, so you want daily partitions. In Hive this means creating a new table and rewriting everything. In Iceberg you run one metadata command that adds a new partition spec. Old data files keep their old spec (month), and new files use the new spec (day). Each manifest records which spec its files were written with. At query time the planner splits the filter by spec: it prunes monthly-partitioned files using month rules and daily ones using day rules, and combines the results. No data is rewritten and nothing breaks. If you later want the old data in the new layout, you can run a rewrite (compaction) job on selected ranges, when convenient. The same works for adding a bucket column or removing a partition field.

Likely follow-ups
  • Any catch? Queries over a mix of specs plan a bit slower, and joins that rely on a single partitioning cannot use it across specs.
Explain copy-on-write versus merge-on-read in Iceberg, including position and equality deletes. Senior

What the interviewer is testing: the central write versus read trade-off, and the delete file vocabulary.

Both strategies exist because data files are immutable. With copy-on-write (COW), an update or delete rewrites each data file that contains an affected row, writing a new file without or with the changed rows. Reads stay fast and simple (just data files), but writes are heavy: changing one row rewrites a whole 512 MB file. With merge-on-read (MOR), the writer leaves data files untouched and writes delete files. A position delete file says "in file X, row positions 17 and 902 are deleted". An equality delete file says "any row where order_id = 42 is deleted" (common in streaming upserts from Flink, since the writer does not know file positions). Updated rows are written as a delete plus a new row in a small new file. Writes are cheap, but readers must merge delete files with data on every read, so reads slow down until a compaction rewrites files and drops the deletes. Rule of thumb: COW for read-heavy tables with infrequent, batch updates; MOR for write-heavy, frequent small updates and CDC. In spec v2 these row-level deletes are supported; spec v3 adds deletion vectors (a compact bitmap per data file stored in a Puffin file), which replace position deletes and make MOR reads cheaper. Modes are set with write.delete.mode, write.update.mode, write.merge.mode (copy-on-write is the default).

Likely follow-ups
  • Which would you use for a nightly MERGE of 2% of rows? Likely COW if partitions are well aligned; MOR if the 2% is scattered across all files.
  • Why equality deletes for Flink? It streams upserts by key without reading the table to find positions.
What table maintenance does an Iceberg table need? Explain compaction, expire snapshots, orphan files and manifest rewrite. Senior

What the interviewer is testing: you know that Iceberg is not "set and forget", and what each job does.

Compaction (rewrite_data_files) merges many small files into files near the target size (default 512 MB for write.target-file-size-bytes), can sort or z-order data to improve skipping, and applies pending delete files. It creates a new snapshot. Expire snapshots (expire_snapshots) removes old snapshots from metadata and deletes data and manifest files only they reference. Without it, storage and metadata grow forever, because every commit keeps old files for time travel. It also removes your ability to time travel to those snapshots, so you choose retention (for example 7 days, minimum 1 snapshot kept). Remove orphan files (remove_orphan_files) deletes files in the table folder that no metadata knows about, left over by failed or aborted jobs; use an age threshold (default 3 days) so you do not delete files of a write still in progress. Rewrite manifests (rewrite_manifests) regroups manifest files when streaming commits made thousands of tiny ones, which slows query planning. A typical schedule: compaction hourly or daily on hot partitions, expire and orphan cleanup daily or weekly. Many managed platforms (Glue, Snowflake, Tabular, Databricks) can do this automatically.

CALL prod.system.rewrite_data_files(table => 'db.events',
  strategy => 'sort', sort_order => 'user_id',
  where => 'event_time >= current_date - 2');
CALL prod.system.expire_snapshots('db.events', TIMESTAMP '2026-11-10 00:00:00', 10);
CALL prod.system.remove_orphan_files(table => 'db.events');
CALL prod.system.rewrite_manifests('db.events');
Likely follow-ups
  • Does expire snapshots break running readers? A reader on an expired snapshot may fail with "file not found", so keep retention longer than your longest query.
  • Why an age limit on orphan removal? A running writer has files not yet committed; deleting them would corrupt its commit.
What is an Iceberg catalog, and which kinds exist? Intermediate

What the interviewer is testing: the catalog is the one component that must be atomic and shared.

The catalog does two jobs: it maps table names to the current metadata file, and it makes the commit swap atomic. Common types: the Hive Metastore (old but everywhere), AWS Glue Data Catalog (managed on AWS), JDBC catalog (a table in any SQL database; simple and atomic), Nessie (git-like branches and commits across tables), and the REST catalog (an open HTTP specification; implementations include Apache Polaris, Unity Catalog, Lakekeeper, Gravitino and vendor services). REST is the direction of the project, because it lets one server handle auth, credential vending, and multi-table work for every engine. The Hadoop (file system) catalog uses only the folder and needs an atomic rename; it is not safe on S3 for concurrent writers. The choice matters for governance, multi-engine access and who can run commits.

Likely follow-ups
  • Can two catalogs point at the same table? Dangerous: each can accept a commit, and they will overwrite each other. One table, one catalog.
Compare Iceberg, Delta Lake and Hudi. How would you choose? Senior

What the interviewer is testing: balanced, current view without vendor bias.

All three add transactions, schema evolution and time travel to Parquet files. Delta Lake (Databricks, now Linux Foundation) tracks changes in a _delta_log folder: ordered JSON commit files and periodic Parquet checkpoints. It is tightly integrated with Spark and Databricks, and its commit step relies on atomic put-if-absent of the next log file (needs special handling on some stores). Hudi (from Uber) has a timeline of actions, two table types (copy-on-write and merge-on-read), record-level indexes and strong incremental pulls, so it fits heavy upsert and CDC ingestion. Iceberg uses the tree of metadata, manifests and a catalog pointer; it is the most engine-neutral, has hidden partitioning and partition evolution built in, and by 2024-2025 has the widest vendor support (Snowflake, BigQuery, Athena, Trino, Flink, Databricks reading and writing). My practical choice: Iceberg for a multi-engine or vendor-neutral platform; Delta if you are all-in on Databricks; Hudi if upsert-heavy streaming ingestion is the core need. Interop tools (Delta UniForm, Apache XTable) can expose one table in several formats, which lowers the cost of the choice.

You run SELECT ... WHERE event_time = '2026-11-17' AND user_id = 7 on an Iceberg table. Describe what the engine does. Senior

What the interviewer is testing: end to end understanding, in order, with pruning at each level.

First the engine asks the catalog for the current metadata file and loads it (one small JSON read). It picks the current snapshot and reads its manifest list. The manifest list stores a partition range summary per manifest, so the engine drops all manifests that cannot contain that day. For the remaining manifests, it reads the entries. Each entry has the partition value and the column min and max. The filter on event_time turns into a partition filter on day(event_time) (hidden partitioning) and the filter on user_id is checked against the min and max, or against the bucket value if the table uses a bucket transform. Files that fail are skipped. The result is a small list of data files, which become scan tasks of about 128 MB each (split size). Each task opens its Parquet file, reads the footer, skips row groups and pages by stats (and bloom filters), reads only the needed columns, applies any delete files, and filters rows. No directory listing is done at any point.

Likely follow-ups
  • How can I see what was pruned? Query the metadata tables (files, manifests, partitions) or use EXPLAIN and the scan metrics.
What are Iceberg metadata tables and how do you use them to debug? Intermediate

What the interviewer is testing: practical debugging tools.

Iceberg exposes its own metadata as queryable tables that you reach by adding a suffix to the table name. .snapshots lists commits with operation type and summary. .history shows how the current pointer moved. .files lists every live data file with size, record count, and column stats. .manifests lists manifest files. .partitions gives counts and sizes per partition. .refs lists branches and tags. I use .files to find small-file problems (files under 32 MB, count per partition), .snapshots to see which job wrote what and when, and .partitions to spot skew. This is a very fast way to answer "why is this table slow" without scanning data.

SELECT partition, count(*) AS files, avg(file_size_in_bytes)/1048576 AS avg_mb
FROM prod.db.events.files
GROUP BY partition ORDER BY files DESC LIMIT 20;
Why is Iceberg better than a plain Hive-style table on S3? Intermediate

What the interviewer is testing: can you list the concrete failures that motivated table formats.

A Hive table is a folder structure plus a metastore listing partitions. Problems: listing thousands of folders and files on S3 is slow (and was eventually consistent in the early days). There is no atomic multi-file commit, so a reader can see half a job, and a failed job leaves partial files. Two concurrent writers can overwrite the same partition. Schema changes are fragile because columns are matched by name or position. Partitioning is exposed to users and cannot change without a rewrite. Updates and deletes mean rewriting an entire partition. Statistics are coarse, so little file skipping. Iceberg fixes each: the file list is in metadata (no listing), commits are atomic, concurrency is controlled, columns use ids, partitioning is hidden and evolvable, row-level changes are supported, and per-file statistics enable skipping. The data files themselves stay in the same open Parquet format, so migration can be done in place with add-files style procedures.

How do you write to an Iceberg table safely from Spark and from a stream? Give the main write operations. Intermediate

What the interviewer is testing: hands-on write paths and idempotency.

Batch writes with Spark SQL or the DataFrame v2 API: INSERT INTO appends, INSERT OVERWRITE replaces matching partitions (dynamic overwrite is safer than a static full overwrite), and MERGE INTO performs upserts using a join on keys. For idempotent loads I prefer MERGE INTO on a business key or a "replace this partition" overwrite, because a retry gives the same result; a plain append retried twice makes duplicates. For streaming, Flink has an Iceberg sink that commits on each checkpoint (so commit frequency equals checkpoint interval, and short intervals make many small files). Spark Structured Streaming can append with a checkpoint location; it records the batch id so a restarted batch is not committed twice. Remember each commit creates a snapshot and at least one small file per task, so choose commit intervals of minutes, not seconds, and plan compaction.

MERGE INTO prod.db.customers t
USING staging.customers_delta s ON t.id = s.id
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
Likely follow-ups
  • What if the source batch has two rows for one key? MERGE fails ("multiple matches"), so deduplicate the source first, keeping the latest per key.

6. Pipelines, streaming, CDC and data quality

Batch versus streaming processing: how do you decide? Basic

What the interviewer is testing: choosing by need, not by fashion.

Batch processes a bounded chunk of data on a schedule: "every night, process yesterday". It is simple, cheap, easy to re-run and test, and works well when a delay of hours is fine, such as finance reports. Streaming processes an unbounded flow of events continuously, with seconds or less of delay, for things like fraud alerts, live dashboards, or keeping a search index fresh. Streaming costs more in complexity: you must handle state, ordering, late events, restarts and exactly-once effects, and you pay to keep jobs running all day. I start from the business question "what is the cost of data being one hour old?". If the answer is "nothing", use batch (or micro-batch every few minutes). Many systems use both: streaming for the freshest slice, batch to reprocess and correct. Modern engines (Spark Structured Streaming, Flink) use almost the same API for both, which reduces the gap. Iceberg and Delta tables can be the sink for both modes.

Likely follow-ups
  • What are lambda and kappa architectures? Lambda runs a batch layer and a speed layer and merges them (two code paths, painful). Kappa uses one streaming path and replays the log to reprocess.
ETL versus ELT: what is the difference and why did ELT become popular? Basic

What the interviewer is testing: where the transform runs and the consequences.

ETL means Extract, Transform, Load: data is cleaned and reshaped on a separate processing server, and only the final result is loaded into the warehouse. ELT means Extract, Load, Transform: raw data is loaded first into the lake or warehouse, and transformations run there using its own scalable engine (SQL, Spark, dbt). ELT became popular because storage and compute in the cloud are cheap and elastic, so there is no need for a separate transform server. Raw data is kept, so you can change the business logic later and re-run from raw without re-extracting from the source. It also lets analysts own transformations in SQL. ETL is still right when data must be masked or filtered before it may land (privacy rules), when the target is small or fixed, or when you must reduce huge volumes before loading. A good pipeline often does a little "T" before load (remove PII, validate types) and the main modelling after.

What is Change Data Capture (CDC), and what are the ways to do it? Intermediate

What the interviewer is testing: you know log-based CDC and why polling is weaker.

CDC means capturing every insert, update and delete from a source database as a stream of change events, so a lake, search index or cache can follow it. There are three ways. Query-based: poll the table for rows with updated_at greater than the last seen time. It is simple but misses hard deletes, can miss rows updated in the same millisecond, and loads the database. Trigger-based: database triggers write changes to a shadow table; it works but slows down every write. Log-based: read the database's transaction log (MySQL binlog, PostgreSQL WAL through a replication slot, Oracle redo log). It sees every change in commit order, including deletes, with almost no load on the tables. Debezium is the best-known open source tool (it runs on Kafka Connect). A Debezium event has before and after row images, an op code (c, u, d, r for snapshot read), and source position (log offset). Downstream you apply events to the target with upserts and deletes in order, usually per key, using MERGE.

Likely follow-ups
  • What is the initial snapshot? Before streaming the log, the connector reads the existing table (op = r), then switches to the log, with a consistent position.
  • Risk with PostgreSQL slots? An unconsumed replication slot makes the database keep WAL forever and fill the disk. Monitor lag.
What is the transactional outbox pattern, and what problem does it solve? Senior

What the interviewer is testing: the dual-write problem, which is a classic design trap.

The problem: a service must update its database AND publish an event to Kafka. These are two systems, so there is no shared transaction. If you write the DB and then publish, a crash in between loses the event. If you publish first and the DB write fails, you announce something that never happened. The outbox fixes it: in the same local database transaction, write the business row and also insert an event row into an outbox table. Either both commit or neither does. A separate relay then reads the outbox and publishes to Kafka. The best relay is log-based CDC (Debezium reads the outbox inserts from the WAL, often with its outbox event router), or a poller. The relay gives at-least-once delivery: it may publish an event twice after a crash. So consumers must be idempotent, usually by tracking the event id. Ordering per aggregate is kept by using the aggregate id as the Kafka key. Old outbox rows are deleted or the table is partitioned and dropped periodically.

Likely follow-ups
  • Why not use Kafka transactions across DB and Kafka? Kafka transactions cover only Kafka; they cannot include your SQL database.
  • Alternative? "Listen to yourself" or event sourcing. Outbox is simpler for existing CRUD services.
Explain at-most-once, at-least-once and exactly-once. Is exactly-once real? Intermediate

What the interviewer is testing: precise vocabulary and skepticism about marketing.

At-most-once: a message is delivered zero or one time; you may lose data (commit the offset before processing). At-least-once: delivered one or more times; no loss, but duplicates after retries (process first, then commit the offset). Exactly-once means the effect happens once. Over an unreliable network you cannot guarantee a message is delivered exactly once, so real systems get exactly-once effects by combining at-least-once delivery with deduplication or idempotent or transactional writes. Examples: Kafka's idempotent producer (sequence numbers per partition) and transactions (atomic write to several partitions plus the consumer offsets, for Kafka-to-Kafka flows); Flink checkpoints with a two-phase commit sink; Spark Structured Streaming with a checkpointed, idempotent sink; and an Iceberg MERGE on a key. Outside the system (calling an API or sending an email) there is no such guarantee, so you need an idempotency key. My answer: "exactly-once is at-least-once plus idempotence, inside a boundary where I control both sides".

Likely follow-ups
  • Where does it break? At the edge: the sink that is not transactional and has no key, for example appending to a plain file.
What is an idempotent data pipeline, and how do you build one? Intermediate

What the interviewer is testing: the most important property of a production pipeline. Almost every incident story links to it.

A pipeline is idempotent if running it twice with the same input gives the same final data as running it once. Pipelines are re-run all the time: a task is retried after a timeout, an operator backfills, an orchestrator replays a day. If a re-run adds the rows again, you get duplicates and wrong totals. Techniques: (1) Overwrite by partition: the job for 2026-11-17 replaces exactly that day's partition, never appends to it. (2) Upsert with a natural key: MERGE INTO on the business key, so the same row updates itself. (3) Deterministic output: avoid now(), random ids and unordered "pick any row"; take the run date as a parameter, not the wall clock. (4) Write to a temporary location, then atomically swap/commit: a half-finished run leaves nothing visible; Iceberg and Delta commits do this. (5) Track processed inputs (file names, offsets, event ids) in a ledger written in the same transaction as the output. (6) Delete-then-insert for a batch id in a single transaction. The test is simple: run the job twice and compare the output.

-- re-runnable: only touches the day it owns
INSERT OVERWRITE prod.sales_daily PARTITION (dt = '2026-11-17')
SELECT ... FROM raw.sales WHERE sale_date = '2026-11-17';
Common mistakes: an append-only job scheduled with "retry 3 times". Also using current_date inside the query, so a backfill reads today's data instead of the run date.
How do you remove duplicates in a stream or a table? Which key and which row do you keep? Intermediate

What the interviewer is testing: practical dedup, state limits, and picking a winner deterministically.

First define identity: what makes two records "the same"? Usually a business key or a unique event id created at the source (a UUID made by the producer, not by the pipeline). Then define which to keep: normally the latest by event time or by source log position (sequence number), not by arrival order. In a batch table: use a window function with row_number() over (partition by key order by updated_at desc, offset desc) and keep rank 1, or MERGE into the target. In a stream: keep state of seen ids for a bounded time (Spark dropDuplicatesWithinWatermark, Flink keyed state with a time-to-live), because unbounded state grows without limit. The retention of that state must be longer than the longest expected duplicate gap. Always add a tie-breaker to the ordering, otherwise two rows with the same timestamp make the output non-deterministic and a re-run can pick a different one.

SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY order_id
         ORDER BY updated_at DESC, source_offset DESC) AS rn
  FROM bronze.orders) WHERE rn = 1;
What are event time, processing time and watermarks? How do you handle late data? Senior

What the interviewer is testing: the core streaming concept that most candidates only half know.

Event time is when the thing happened (a phone taps "buy" on a train with no signal). Processing time is when your system sees it, maybe ten minutes later. If you count orders per minute using processing time, results depend on network delays, and replays give different answers. So we group by event time. But then the engine must decide: "when can I finalise the window 10:00 to 10:01, since a late event might still arrive?" A watermark is the engine's moving estimate of "I have probably seen all events up to time T". It is usually the highest event time seen so far minus an allowed lateness (say 10 minutes). When the watermark passes the end of a window, the window is closed and its result emitted; state for it is dropped, which keeps memory bounded. Events older than the watermark are late. Options: drop them (simple, but counts are slightly off), route them to a side output or a "late" table for repair, allow a longer lateness (more delay and state), or emit updated results (retractions or upserts) when a late event arrives. The trade-off is always latency versus completeness. A batch correction job that recomputes yesterday from the raw log is a common safety net.

Likely follow-ups
  • What if one Kafka partition is idle? Its watermark does not advance, and the whole job stalls. Configure an idle timeout.
  • Tumbling, sliding, session windows? Fixed non-overlapping, overlapping, and gap-based per user.
How do you design a pipeline so that backfills are safe? Senior

What the interviewer is testing: operational maturity: re-running history without hurting production.

A backfill means re-computing data for a past period, because of a bug, new logic, or a late source. To make it safe: the job takes the date range as parameters and never uses the current time. It writes by partition overwrite or merge (idempotent), so running it again is harmless. It reads from immutable raw data (bronze) that was kept long enough. It runs in parallel by partition (one task per day) with a concurrency limit, so it does not starve the daily load. Output goes to a staging table or an Iceberg branch first; you compare row counts and totals with the old data, then publish by swapping or fast-forwarding. Downstream tables are re-run in dependency order (orchestrators such as Airflow can clear and re-run a date range with downstream tasks). Tell consumers beforehand if numbers will change. Keep the old snapshot for a few days so you can roll back (Iceberg time travel is useful here). Watch the cost: a backfill of three years can use more compute than a month of normal work.

Likely follow-ups
  • What about SCD2 dimensions in a backfill? Point-in-time joins must use the version valid at the event date, so rebuild history from change logs, not from today's snapshot.
How does an orchestrator such as Airflow fit in, and what makes a good task design? Intermediate

What the interviewer is testing: do you separate scheduling from processing.

An orchestrator (Airflow, Dagster, Prefect, Argo) runs a dag (graph) of tasks in order, retries failures, tracks state, and lets you re-run a range. It should not move the data itself; it triggers Spark, SQL or dbt jobs that do. Good task design: small tasks with one clear output; each task idempotent (so retries are safe); the logical date passed as a parameter (Airflow's data_interval_start), so a re-run for 2026-11-10 reads that day's data; dependencies expressed by data availability (sensors on the partition or dataset triggers), not by "run at 3 am and hope"; no big data passed through the scheduler (pass paths, not rows); and alerts on failure and on delay (SLA). Avoid huge dags that mix hundreds of tasks, and avoid hidden dependencies between dags. Treat pipeline code like any other code: version control, tests, and code review.

How do you assure data quality in a pipeline? What checks, where, and what happens when they fail? Intermediate

What the interviewer is testing: engineering approach to correctness, not "we look at the dashboard".

I use layers of checks. At ingestion: schema validation (does the record match the contract, are the types right), required fields, and format. Row-level: not null, ranges (age between 0 and 120), allowed values, referential integrity (every order has a customer), uniqueness of keys. Table-level: row count within the expected range versus yesterday, freshness (the latest event is not older than N hours), and volume anomalies. Business-level: reconciliation, such as the revenue total in the lake matches the source system within a small tolerance. Tools include dbt tests, Great Expectations, Soda, Deequ, and Iceberg or Delta constraints. When a check fails, decide by severity: a critical failure stops the pipeline so bad data does not reach gold (a "circuit breaker"); a minor failure sends the bad rows to a quarantine table with the reason and lets good rows continue, and always raises an alert. Write-Audit-Publish is a good pattern: write to a staging branch, audit it, and publish only if it passes. Never silently drop bad rows; count them and report.

Likely follow-ups
  • What is Write-Audit-Publish? Write new data where consumers cannot see it (an Iceberg branch or staging table), run checks, then make it visible atomically.
What is a data contract, and how does it differ from a schema? Senior

What the interviewer is testing: the people and process side of data quality at scale.

A schema describes the structure: field names and types. A data contract is a wider, explicit agreement between a data producer (a service team) and consumers (analytics, ML, other services). It includes the schema, plus semantics (what "amount" means: tax included, in which currency), quality rules (not null, unique, ranges), freshness and delivery expectations (an SLA), ownership and a contact, how breaking changes are announced (versioning and a deprecation period), and rules for sensitive fields such as PII. The key move is that the contract is machine-checkable and lives in version control next to the producer code. The producer's CI runs the compatibility check (for example the registry rules), and a breaking change fails the build. This stops the typical failure: an upstream team renames a column in the application database, and a dashboard silently breaks two weeks later. Contracts shift responsibility "left", to the team that makes the data, and replace direct reading of internal service tables with a published interface (an event stream or a curated table).

Likely follow-ups
  • Should analysts read the production DB tables directly via CDC? It couples them to internal design. Better to publish an event or an outbox with a stable contract.
How do you handle schema drift from a source you do not control? Senior

What the interviewer is testing: defensive pipeline design.

First, land raw data without enforcing a strict structure (bronze keeps the original payload, or a variant or string column, plus metadata), so a new field never causes data loss. Second, detect drift: compare the incoming schema with the expected one at ingestion and raise an alert, or record it in a schema history table. Third, apply a policy by change type. A new optional column: add it automatically to bronze, and decide on silver deliberately. A removed or renamed column: fail the silver step and alert, because the business meaning changed. A type change: quarantine rows that no longer fit. Use the table format features: Iceberg and Delta allow safe additive evolution, and Spark can merge schemas on write. Keep a stable curated layer so consumers see only intentional changes. And talk to the source owner: drift tolerance is a stopgap, a contract is the real fix.

7. File layout, partitioning, and dimensional modelling

How do you choose a partitioning strategy for a lake table? Intermediate

What the interviewer is testing: balanced trade-offs, and awareness of over-partitioning.

Partitioning splits a table into groups of files by a column value, so queries that filter on it can skip whole groups. Pick the column that most queries filter on, and that gives partitions that are big enough. Time (day) is the most common choice for event data. Targets: each partition should hold at least a few hundred MB to many GB of data (so files are near the target size), and the total number of partitions should stay in the thousands, not millions. Too fine (for example partition by user_id, or by hour for a tiny table) produces millions of tiny files, a huge metadata load and slow planning. Too coarse (partition by year) means every query scans lots of data. For high-cardinality columns like user_id, do not partition by value; use a bucket transform or sort the data inside files so min and max stats work. In Iceberg, day(ts) plus bucket(N, id) is a typical pairing, and you can change it later (partition evolution), so start simple and measure. Data skew matters too: a country partition where one country has 80% of the data does not balance work.

Likely follow-ups
  • Partition column versus sort column? Partition prunes folders, sort order narrows min and max within files; use both.
What is the small files problem? Why does it hurt and how do you fix it? Intermediate

What the interviewer is testing: the most common real performance problem on a lake.

Small files are data files far below the useful size (say under 32 MB when the target is 256 to 512 MB). Every file costs a fixed amount: an object-store request (S3 GET with latency about tens of milliseconds), a footer read, a task launch, and an entry in the metadata. Reading a million 1 MB files is much slower than reading one 1 TB-sized set of 500 files, even if total bytes are the same. Compression and column stats also work worse on tiny files. Query planning slows too, since the metadata list is huge. Where do they come from? Streaming writes that commit every few seconds; too many Spark shuffle partitions (200 default tasks each writing a file per partition); over-partitioning; many small incremental loads. Fixes: write fewer, larger files (repartition or coalesce before write, adaptive query execution in Spark 3, or Iceberg write distribution mode hash), commit less often, choose coarser partitions, and run compaction (rewrite_data_files, or Delta OPTIMIZE) as scheduled maintenance. Prevention is cheaper than cure, but you need the compaction job anyway.

Likely follow-ups
  • Does compaction block writers? Not in Iceberg: it commits optimistically, but can conflict with concurrent deletes in the same partitions and retry. Compact cold partitions, not the one currently being written.
How does sorting or z-ordering data help query speed? Senior

What the interviewer is testing: why layout inside files matters beyond partitions.

File statistics only help when each file covers a narrow range of the filter column. If rows are in random order, every file holds a bit of every user, so min and max span everything and no file can be skipped. If you sort rows by user_id during compaction, each file covers a small range, and a query for one user opens one or two files. Sorting by one column is excellent for that column but weak for others. Z-ordering (and Hilbert curves) interleaves the bits of several columns so that rows close in several dimensions at once are stored together, giving decent skipping for filters on any of them. The cost is a more expensive rewrite and slightly weaker skipping than a pure sort for the first column. Iceberg supports sort orders on the table and rewrite_data_files with sort or zorder strategy; Delta has Z-order and liquid clustering. Use it for columns with many different queries and high selectivity, after you fix file sizes.

What are slowly changing dimensions (SCD)? Explain types 1, 2 and 3, and how you implement type 2. Intermediate

What the interviewer is testing: a classic modelling question: how to keep history of changing attributes such as a customer's city.

A dimension is a descriptive table (customer, product). Its attributes change slowly: a customer moves city. SCD describes what to do with old values. Type 0: never change (e.g. original signup date). Type 1: overwrite the old value; simple, no history, old reports change retroactively. Type 2: add a new row for each change and keep the old row, with valid_from, valid_to and an is_current flag; full history, so a fact that happened while the customer lived in Pune is still reported under Pune. Each version has its own surrogate key, and facts store that key. Type 3: keep the previous value in an extra column (previous_city); only one step of history. Type 4 puts history in a separate table, and type 6 combines 1, 2 and 3. To implement type 2 in a lake: compare incoming records with current rows by business key and a hash of the tracked columns; for changed ones, close the current row (set valid_to and is_current false) and insert a new row with valid_from = change time. A single MERGE can do both when the source rows are staged twice (one to close, one to insert).

Likely follow-ups
  • Why a surrogate key and not the customer id? Because the same customer id now appears in several rows, one per version.
  • Problem with SCD2 on a big dimension? Rows grow with each change; do not track fast-changing attributes (use a mini-dimension).
Explain dimensional modelling: facts, dimensions, grain, star versus snowflake. Intermediate

What the interviewer is testing: analytics modelling basics (Kimball).

A fact table records measurable events: a sale, a click, a payment. Each row has numeric measures (quantity, amount) and foreign keys to dimensions. A dimension table describes the context: who (customer), what (product), where (store), when (date). The most important step is to declare the grain: exactly what one fact row means, for example "one line item on one order". Mixing grains in one table gives wrong sums. In a star schema, the fact sits in the middle and dimensions around it are denormalised (flat), so queries need few joins and are fast and easy to understand. In a snowflake schema, dimensions are normalised into sub-tables (product, category, department), which saves a little space and removes redundancy, but needs more joins. In modern columnar warehouses, storage is cheap and joins are well optimised, so the star is the usual choice. Measures can be additive (amount: can be summed across all dimensions), semi-additive (account balance: not across time), or non-additive (ratios: recompute from parts). A date dimension table is nearly always included.

Likely follow-ups
  • What is a degenerate dimension? An identifier such as order number kept in the fact table, with no separate dimension.
  • What is a factless fact table? Records that an event happened with no measure, such as student attendance.
Normalised versus denormalised: what do you choose for analytics, and why do big-data engines like wide tables? Intermediate

What the interviewer is testing: can you flip the OLTP reflex.

In OLTP, normalisation (3NF) avoids update anomalies: each fact is stored once, and joins rebuild the whole picture. In analytics the data is mostly written once and read many times, so we trade space and some redundancy for speed and simplicity. Denormalised, wide tables avoid big distributed joins, which are the most expensive step in Spark or Trino because they move data across the network (shuffle). With columnar storage, extra columns cost almost nothing when not read. The downside: if a dimension attribute changes, you must update many rows (hence SCD thinking), and a wide table can hide the grain. A balanced answer is: keep clean, normalised or star-modelled core tables, and build wide denormalised tables or views for the hot dashboards on top.

A join in Spark is very slow and one task runs much longer than the rest. What is happening? Senior

What the interviewer is testing: data skew, one of the most common causes of "my job is stuck at 99%".

The join key is skewed: one key (a null, "unknown" or a very popular customer) holds a huge share of the rows. A shuffle sends all rows with the same key to one task, so that task is overloaded while the others finish and wait. Check the Spark UI: one task has far more input bytes and time than the median. Fixes, in order: filter out null or junk keys before the join (null never matches in an inner join anyway). Use a broadcast join when one side is small (under about 10 MB by default threshold, can be raised), which avoids the shuffle entirely. Turn on Spark 3 adaptive query execution with skew join handling, which splits big partitions automatically. Use salting: add a random suffix to the hot key on the big side and replicate the small side across suffixes. Or pre-aggregate before the join to cut the row count. Also confirm that the number of shuffle partitions suits the data volume.

8. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview.

A producer team removed a field from the Avro schema on a Kafka topic and the consumer jobs crashed in production. What do you do? Senior

What the interviewer is testing: incident handling plus the registry and contract lessons.

Situation: consumers fail with a decoding or "missing field" error right after a producer deploy. Messages with the new schema are now mixed in the topic with older ones.

Check first: read the registry history for the subject: what changed between the last good version and the new one? Was the field required (no default)? What compatibility mode was set (NONE would explain how it got through)? Check how many messages with the new schema exist and which consumer groups are failing.

Steps: (1) Stop the bleeding: roll back the producer to the previous version, so new messages use the old schema again. (2) Consumers that are stuck: pause them. For the already written bad-schema messages, either deploy a consumer that handles the new schema, or skip them to a dead letter topic after copying them for later replay. Do not just reset offsets blindly; you lose data. (3) Restore the missing field in a compatible way: add it back with a default, or release the removal in two steps: first make the field optional with a default and upgrade all consumers, then remove it. (4) Replay from the saved offset once fixed.

Prevent: set the subject to BACKWARD or FULL (transitive if you replay), run the registry compatibility check in the producer's CI so incompatible schemas fail the build, add consumer-driven contract tests, and agree a deprecation process (announce, dual write, remove).

Likely follow-ups
  • How do you make a real breaking change? New topic or new subject version, dual-publish, move consumers one by one, retire the old.
A daily report on an Iceberg table went from 2 minutes to 40 minutes after streaming ingestion was added. What do you check? Senior

What the interviewer is testing: the small files and metadata growth diagnosis.

Situation: the query itself did not change, only the ingestion did: a Flink job now commits every 10 seconds.

Check first: query the metadata tables. SELECT count(*), avg(file_size_in_bytes)/1048576 FROM t.files per partition: expect tens of thousands of files averaging 1 to 5 MB. Count rows in .snapshots (thousands of snapshots per day) and in .manifests (thousands of tiny manifests). The Spark UI will show a huge number of tiny tasks and a long planning time before the first task starts.

Steps: run compaction on the affected partitions now (rewrite_data_files with the target size and a sort order, limited to old partitions to avoid conflicts with streaming), then rewrite_manifests, then expire_snapshots to cut metadata and storage. The query should return to normal speed. For the cause: increase the commit interval to 1 to 5 minutes, or write to a staging table and merge hourly, and schedule compaction every hour or day.

Prevent: a data-layout monitoring job that alerts when average file size drops under a threshold, and ingestion that treats commit frequency as a cost parameter.

After a job retry, the daily revenue is double what the source system says. Find and fix it. Senior

What the interviewer is testing: idempotency, and a calm reconciliation approach.

Situation: a task failed halfway on a timeout, the orchestrator retried it, and the second attempt appended all the rows again. Some rows from the first attempt were already written.

Check first: compare counts with the source for that date and see whether duplicates are exact copies (same key, same values). Query SELECT order_id, count(*) ... GROUP BY order_id HAVING count(*) > 1. Look at the table's snapshot history (.snapshots): two append commits from the same job run id confirm the double write.

Steps: for an Iceberg table, the fastest safe fix is to roll back or overwrite: rollback_to_snapshot to the one before the bad commits if nothing else wrote since, or re-run the day with a partition overwrite from raw data. If rollback is not possible, deduplicate with row_number by business key into a new table, validate totals, then swap. Rebuild downstream tables for the date, and tell consumers that the numbers were wrong for a period.

Prevent: make the task idempotent: overwrite by partition or MERGE on the business key; pass the logical date as a parameter; add a unique-key test and a reconciliation check (row count and sum against the source) that fails the pipeline before publish.

Finance found a bug in a transformation. You must recompute 18 months of a gold table without disturbing the daily load. How? Senior

What the interviewer is testing: safe large backfill design.

Situation: the bug affected revenue classification since June last year. Dashboards read the gold table every morning.

Check first: is raw (bronze) data still available for all 18 months, and was the source changed meanwhile (late updates, corrected records)? What is the compute budget and what is downstream (other gold tables, extracts)?

Steps: (1) Fix and unit-test the transformation, with fixed sample inputs and expected outputs. (2) Create a branch or a shadow table of the gold table. (3) Run the backfill by month or day partitions in parallel, with a concurrency cap, on a separate cluster or queue, using the date parameter (never the wall clock), with idempotent partition overwrite. (4) Compare old and new: row counts, totals per month and the differences, and let finance confirm the delta matches the bug. (5) Publish: fast-forward the branch to main, or swap the table in one atomic step. Keep the previous snapshot for rollback for a week. (6) Re-run the downstream tables and notify consumers that history has changed.

Prevent: keep raw data immutable and long enough, keep transformation code versioned, and have a standing backfill runbook.

A user asks to be deleted (GDPR "right to erasure"). Their data is in an Iceberg lake with years of history. How do you actually delete it? Senior

What the interviewer is testing: understanding that delete in an immutable table is logical first, physical later.

Situation: events, orders and profile rows for the user are spread across bronze, silver, gold and some derived extracts and backups.

Check first: find all places that hold that user id: use a data catalog and lineage, or a PII inventory. Check whether a legal basis requires keeping some records (invoices for tax), which may need to be anonymised, not deleted.

Steps: (1) Run DELETE FROM t WHERE user_id = X on each table. In Iceberg this creates a new snapshot. With copy-on-write, files holding that user are rewritten without the rows. With merge-on-read, delete files only hide the rows, so the data is still in the old files. (2) Compact (rewrite_data_files) so delete files are applied and the data files are physically rewritten. (3) Expire old snapshots (expire_snapshots) and remove orphan files, because old snapshots and time travel still reference the original files with the user's data. Also remove old metadata files per your settings. (4) Handle other copies: derived tables, search index, caches, ML feature stores, and backups (document the retention period of backups, or use crypto methods). (5) Record proof that it was done, within the legal deadline (30 days under GDPR).

Prevent: design for deletion: keep PII in a small separate table keyed by a surrogate id so erasure touches one place (the rest stays as anonymous data); partition or sort by user bucket to make deletes cheap; or use per-user encryption keys and delete the key ("crypto-shredding"). Batch many requests into one weekly delete job.

Common mistakes: running DELETE and saying "done". The old snapshots still contain the data until they are expired.
An analyst says a query on a big lake table is "slow and expensive". How do you investigate? Senior

What the interviewer is testing: a method: bytes scanned, pruning, file layout, then query shape.

Situation: a dashboard query scans the whole 8 TB table to answer a question about one week.

Check first: look at the query plan and the scan metrics: how many files and bytes were read versus the table total? If nearly all, pruning is not working. Check the filter: is it on the partition source column, directly (not wrapped in a function such as date_format(ts) or cast that blocks pruning)? Does the table partition on that column at all? Check file sizes and counts in the .files metadata table (small files?), and whether the data is sorted on the filter column. Check SELECT * usage on a wide table (column pruning lost), non-selective joins or skew, and whether the engine collected statistics.

Steps: rewrite the filter so it can be pushed down (ts >= '2026-11-10' AND ts < '2026-11-17'); select only needed columns; compact small files; sort or z-order by the common filter columns; add or change partitioning (Iceberg lets you evolve it); for repeated dashboards create a pre-aggregated gold table or materialised view; cache or use result caching for identical queries.

Prevent: table-level documentation of the intended filters, a query cost dashboard, and guard rails such as required partition filters on huge tables.

Mobile events arrive up to two days late and your hourly streaming counts keep changing. What do you design? Senior

What the interviewer is testing: event time, lateness trade-offs, and correction.

Situation: devices buffer events offline and upload later. A job with a 10-minute watermark drops them, and a job with unbounded lateness never finalises.

Check first: measure the lateness distribution: what percent of events arrive within 1 minute, 1 hour, 1 day, 2 days? That tells you the cost of each choice. Also ask the business: which numbers must be exact, and when?

Steps: keep the streaming job simple and fast with a short watermark (say 15 minutes) for a "fresh, approximate" view. Write every event, including late ones, to the bronze table with event time and arrival time. Run a batch job (hourly for the last 3 days, and a final one after 48 hours) that recomputes the aggregates from bronze using idempotent partition overwrite or merge. Dashboards read the corrected table and label the newest hours as "provisional". Late events beyond the cutoff go to a late table and an alert if their rate is unusual.

Prevent: record both event time and ingestion time on every record; agree on a data-completeness SLA with consumers.

The PostgreSQL primary's disk is filling up and the cause is WAL growth after you added a Debezium CDC connector. What happened? Senior

What the interviewer is testing: operational knowledge of log-based CDC from an application developer's view.

Situation: the connector had a problem (crashed, paused, or Kafka was down) a few days ago.

Check first: in PostgreSQL, look at pg_replication_slots and find the slot used by Debezium: is it inactive, and how far behind is its restart_lsn? A slot makes PostgreSQL keep every WAL segment until the consumer confirms it.

Steps: fix the connector first if you can, so it catches up and the slot advances; the WAL is then released. If the disk is about to be full and you cannot recover in time, drop the slot to protect the primary (you will have to re-snapshot the tables afterwards). Then verify downstream: the Kafka topic and the lake table may have a gap, so run a reconciliation and, if needed, a fresh snapshot with an idempotent merge.

Prevent: alert on slot lag and on WAL disk usage, set max_slot_wal_keep_size (PostgreSQL 13 and later) so a stuck slot cannot take down the primary, enable Debezium heartbeats for low-traffic databases, and monitor connector status.

CDC events for the same order arrive out of order in the lake and the table shows an old status. How do you fix it? Senior

What the interviewer is testing: ordering, keys, and applying changes by version, not by arrival.

Situation: the order shows PENDING in the lake, but the source says SHIPPED. Two updates were processed in the wrong order, for example by parallel tasks or by a replay.

Check first: is the Kafka topic keyed by the order id (so all changes for one order stay in one partition and keep order)? Does the job apply events in micro-batches in parallel, or does a MERGE use whichever row it sees last? Does each event carry a version, such as the log position (LSN) or source timestamp?

Steps: key the topic by primary key. In each batch, first deduplicate by key, keeping the event with the highest source log position (use ts_ms plus offset as a tie-breaker), then MERGE. Make the MERGE conditional so it never moves backwards: WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE. Then repair the existing wrong rows by replaying from bronze or by re-snapshotting the affected keys.

Prevent: store the source version on every row, and include an ordering column in the contract.

Your nightly MERGE job fails with a commit conflict while a compaction job is running on the same Iceberg table. What now? Senior

What the interviewer is testing: optimistic concurrency in daily life.

Situation: a ValidationException says files that the MERGE read or planned to replace were already removed by another commit: compaction rewrote the data files the MERGE was updating.

Check first: the table snapshot history shows the replace commit from compaction between your read snapshot and your commit time. The conflict is real because both operations touched the same files (a rewrite and a row-level change).

Steps: just re-run the MERGE: it will start from the new snapshot and normally succeed. If it keeps failing, separate the schedules so they do not overlap, or restrict compaction to partitions that the MERGE does not touch (for example only partitions older than 2 days). Raise the commit retry settings only for append-like conflicts; true conflicts need a re-run. Check the isolation level: snapshot isolation tolerates more concurrent operations than serializable, if your data model permits it.

Prevent: an orchestrator dependency that serialises maintenance and heavy updates on one table, and automatic retry in the job with the full re-plan.

Queries on a new events table always scan everything even though they filter by date. What is wrong? Intermediate

What the interviewer is testing: practical partition pruning pitfalls.

Situation: the table was created in Hive style with a dt string partition column, but analysts filter on event_time.

Check first: EXPLAIN the query: does it list partition filters? In Hive-style tables, the engine only prunes if the query filters the partition column dt itself. Also check whether the filter uses a function, such as to_date(event_time) = ... on a table partitioned by something else.

Steps: on Iceberg, partition by day(event_time) with a hidden partition transform, so a filter on event_time prunes by itself. If you must stay with Hive tables, add dt in the filter or put a view in front that derives it. Rewrite filters as direct range comparisons on the raw column. For an existing Iceberg table, add the partition field (partition evolution) and compact old data when convenient.

Prevent: review the table design with the query patterns before choosing partitions, and test with EXPLAIN on the first real query.

The cloud bill shows the lake storage doubling every month though the data volume is steady. What is going on? Senior

What the interviewer is testing: the hidden cost of immutable tables.

Situation: frequent upserts and compactions write new files each time, and old ones are never deleted.

Check first: compare the live table size (sum of .files) with the actual bytes under the table folder in object storage. A large difference means retained old files from snapshots or orphans. Check the snapshot count and the retention settings (history.expire.max-snapshot-age-ms), and look for failed jobs that left partial files.

Steps: run expire_snapshots with a sensible retention (for example 7 days), then remove_orphan_files with the age limit, then check storage again. Also confirm the object-store versioning and lifecycle rules, because bucket versioning keeps deleted objects too; add a lifecycle rule for noncurrent versions. If data is rewritten constantly, review the write pattern (MERGE frequency, copy-on-write on a hot table might better be merge-on-read).

Prevent: automate table maintenance for every table, with ownership, and graph storage per table over time.

Reports show sales shifted by one day for some regions after moving to a new pipeline. How do you debug? Intermediate

What the interviewer is testing: time zone and logical type pitfalls, common in real data work.

Situation: late-evening sales in India appear on the next day's report in one table and on the correct day in another.

Check first: the type of each timestamp column: is it a UTC instant (timestamp-millis or Spark TIMESTAMP, an absolute time) or a local timestamp without zone? What is the session time zone of the Spark job, and how is the "day" computed? A day bucket derived from a UTC instant differs from the local business date. Also check whether an int-based timestamp changed units (seconds versus milliseconds) between systems.

Steps: store instants in UTC, and add an explicit local business date column computed with the region's time zone when business reporting needs it. Set the time zone of the engine explicitly in the job configuration. Fix the Avro or Parquet logical types so the same meaning is carried across systems, and backfill the affected range.

Prevent: a data contract that names the time zone and unit of every time field, and tests with boundary-time samples (23:30 local on the last day of a month).

One bad record keeps crashing your streaming consumer in a restart loop. What do you do? Senior

What the interviewer is testing: poison pill handling and dead letter queues.

Situation: the consumer fails on one message (invalid bytes, schema not found, null in a required field), the offset is not committed, it restarts and fails again. All the partition's later messages are blocked, and lag grows.

Check first: the stack trace and the partition and offset of the failing message. Read that message with a console consumer to see the raw bytes and schema id.

Steps: short term: move past the message deliberately. Copy it to a dead letter topic (with the error, original topic, partition, offset), then skip it or reset the offset by one for that partition. Fix the underlying cause (missing schema, producer bug) and later replay from the dead letter topic. Long term: wrap deserialisation and validation in a try-catch that routes bad records to the dead letter topic and continues; use retry topics with backoff for transient errors, but send permanent errors straight to the dead letter queue. Alert on dead letter volume.

Prevent: schema validation at the producer, registry checks, and a rule that nothing is silently dropped: bad data goes to quarantine with a reason.

You must rebuild a downstream table from a Kafka topic with 6 months of retention, but the consumer logic changed. How do you do it without double-counting? Senior

What the interviewer is testing: replay design: new consumer group, new target, then switch.

Situation: a new version of the aggregation must be applied to all history, while the current one keeps serving traffic.

Check first: is the earliest offset still available, or has retention removed data? Is the topic compacted or time-retained? Is the old and new schema readable (BACKWARD_TRANSITIVE needed)?

Steps: start a new consumer group at the earliest offset, writing to a new table (not the live one), with idempotent writes (merge on key, or partition overwrite). Let it catch up while the old one still runs. Verify the new table against the old for an overlap period. Then switch consumers to the new table (rename or point views at it) and stop the old job. If Kafka retention is too short, rebuild from bronze files in the lake and then continue from the stream, using the offsets stored in the files to avoid gaps or overlaps.

Prevent: keep the raw stream landed in the lake (bronze), so the log is not the only source of history.
