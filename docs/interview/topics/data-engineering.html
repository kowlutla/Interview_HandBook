How data is stored and moved: row and column formats, Avro schemas and evolution, Parquet, lakes and lakehouses, Apache Iceberg at concept level, and pipelines that survive retries, late data and schema change. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

Depth: this page is for an application developer who works with data pipelines. It covers how you design with and debug these tools, not how to run a data platform. Version notes: Iceberg table spec v2 added row-level deletes; v3 (deletion vectors and more) is newer and engine support is still spreading, so check your engine. Mental model: the 7 ideas everything hangs on

One line: put bytes in files in a layout that is cheap to scan, add a table layer so many writers and readers stay consistent, then move data with pipelines that can safely run twice.
  1. File format is how bytes are laid out; table format is how files become a table. Avro, Parquet and ORC are file formats. Iceberg, Delta and Hudi are table formats: they track which files make up the table right now.
  2. Row formats suit writing and whole-record reads; column formats suit analytics. Avro is row based (messages). Parquet is columnar (analytics).
  3. A schema is a contract. Who may change it, and in which direction, decides who breaks. Backward, forward and full compatibility are the vocabulary.
  4. Object storage is cheap and immutable. You cannot edit a file in S3. You write new files and swap a pointer. This one fact explains snapshots, delete files and compaction.
  5. Metadata makes queries cheap. Min and max per column, file lists and partition values let an engine skip most files without opening them.
  6. Delivery is at-least-once, so pipelines must be idempotent. Running a step twice must give the same result as running it once.
  7. Time has two meanings. Event time (when it happened) and processing time (when you saw it). Late data lives in the gap.

1. File formats and Parquet

What is the difference between row-oriented and column-oriented storage, and when do you pick each? Basic

A row format stores all fields of one record together; a columnar format stores all values of one column together. I use row formats (Avro, JSON, a normal database) for transactions and messages, where I read or write whole records. I use columnar formats (Parquet, ORC) for analytics, where a query touches a few columns of millions of rows.

Columnar wins on scans for three reasons. First, column pruning: "sum of amount per city" reads two columns and skips the other fifty. Second, compression: one column holds one type and similar values (repeated cities, steadily growing ids), so dictionary, run-length and delta encodings shrink it a lot. Third, statistics: each column chunk stores min and max, so a filter like amount > 1000 can skip whole blocks without reading them. The cost is point work: reading one full row touches every column block, and a single-row insert is expensive, so columnar files are written in big batches.

Remember: rows for transactions and messages, columns for scans and aggregates. Columnar is fast because it reads less, not because it reads faster.

Compare CSV, JSON, Avro, Protobuf and Parquet. How do you choose? Basic

I pick by role. JSON for public APIs and logs, Avro (or Protobuf) for messages on Kafka and ingestion files, and Parquet for analytics tables. CSV only for small human exports. A normal pipeline reads Avro or JSON events from Kafka and writes Parquet tables for analysts.

CSV has no types and no nesting, and quoting bugs are common. JSON is self-describing text with nesting, but it repeats field names in every record, is slow to parse and loosely typed. Avro is a compact binary row format where a schema is required, which gives safe evolution. Protobuf is also binary rows, but fields are identified by number, which makes it the usual choice for gRPC; for Kafka I pick Avro if the data ends up in a lake, and Protobuf if services already use gRPC. Parquet is columnar, so it gives the best scan speed and size for analytics but is poor for row writes and point updates.

How is a Parquet file organised inside? Intermediate

A Parquet file is split into row groups (horizontal slices of rows). Inside a row group each column is stored as a column chunk, and each chunk is cut into pages. At the end of the file is a footer with the schema and, for every column chunk, offsets and min, max and null-count statistics. A reader reads the footer first, decides which row groups and columns it needs, and reads only those byte ranges.

Row groups are typically around 128 MB by default in common writers, and a row group is the unit of parallelism: one task can take one row group. Pages are about 1 MB by default and are encoded and compressed on their own. The footer is at the end because the writer streams data and only knows sizes when it finishes; the file starts and ends with the magic bytes PAR1. This layout works well on S3, because the reader can fetch just the footer and just the needed column chunks with range requests.

Remember: file, row groups, column chunks, pages; the footer holds the stats that let you skip.

What are predicate and projection pushdown, and why does sorting the data matter? Intermediate

Projection pushdown means the engine tells the reader which columns it needs, so only those column chunks are read. Predicate pushdown means the filter goes into the reader, which uses min and max statistics to skip files, row groups and pages that cannot match. It only works well when the data is clustered: if every file holds a bit of every customer, min and max span everything and nothing can be skipped.

Skipping happens at several levels: table metadata skips whole files (Iceberg manifests hold per-file stats), the footer skips row groups, and the optional page index skips pages. For equality filters on high-cardinality columns such as ids, newer Parquet versions also support bloom filters ("this value is definitely not here"). So I sort or cluster data on the column that queries filter on, usually during compaction: then each file covers a narrow range and a lookup opens one or two files. Filters that wrap the column in a function (lower(name) = 'x') usually cannot use the stats, so filter on the raw column.

Remember: stats only skip what is clustered. Sort on the filter column and keep filters on the raw column.

Can you update a row inside a Parquet file? How do table formats get around that? Intermediate

No, not in place. Parquet files are written once, compressed in blocks, and the footer holds offsets, so changing a value would shift bytes. Object stores such as S3 also cannot modify part of an object. So every update is a rewrite: table formats either rewrite the affected files (copy-on-write) or write small delete files and merge them at read time (merge-on-read), and then switch the table metadata to the new file list atomically.

Old files are not touched, so readers that started earlier still see a consistent view. That immutability is the root of snapshots, time travel and compaction later on this page.

Remember: immutable files mean "update" is write new files, then swap the pointer.

2. Avro, schemas and schema evolution

What is Apache Avro, and what does a schema look like? Basic

Avro is a compact, row-oriented binary format where every piece of data is described by a schema written in JSON. The data itself has no field names or type tags, only the values in schema order, so it is small. It is the usual choice for Kafka messages and for event files that must change over time.

Because the bytes carry no description, you cannot decode them without the schema they were written with. A string is a length plus UTF-8 bytes; an int uses a variable-length encoding so small numbers take one byte. The schema lives either in the file header (Avro data files) or in a registry with only a small id sent per message. Types: primitives (null, boolean, int, long, float, double, bytes, string) and complex ones (record, enum, array, map, union, fixed). An optional field is a union with null. Code generation is optional: you can use a generic record or generate Java classes.

{
  "type": "record", "name": "Order", "namespace": "com.shop.events",
  "fields": [
    {"name": "orderId", "type": "long"},
    {"name": "customer", "type": "string"},
    {"name": "coupon", "type": ["null", "string"], "default": null}
  ]
}
Watch out: a union default must match the FIRST branch. ["string","null"] with "default": null is invalid; put "null" first. For money use the decimal logical type with precision and scale, never double.

Remember: Avro = values only plus a separate schema. Lose the schema and the bytes are meaningless.

Explain reader schema versus writer schema. How does Avro schema resolution work? Intermediate

The writer schema is the one the bytes were written with. The reader schema is the one my code wants today. Avro needs both: it decodes using the writer schema, then maps the result to the reader schema by field name. Fields the reader does not know are skipped; fields the writer did not have get the reader's default, and if there is no default the read fails.

That is why adding a field with a default is the standard safe change, and why old files stay readable forever as long as you keep the writer schema with the data. A rename needs an aliases entry on the new name. A few type promotions are allowed (int to long, float or double; float to double; string and bytes to each other).

Remember: match by name, fill from the reader default, skip the extras. No default means no read.

What are backward, forward and full compatibility? Which changes are safe? Intermediate

The words describe what the new schema can do. Backward compatible: consumers on the NEW schema can read data written with the OLD one. Forward compatible: consumers on the OLD schema can read data written with the NEW one. Full is both. In practice, if every field I add or remove has a default, the change is full compatible.

Backward is what you need when you upgrade consumers first or replay old data from a topic. Forward is what you need when producers upgrade first and old consumers still run. Adding a field without a default is forward only (old readers ignore it, but a new reader cannot fill it for old data). Removing a field without a default is backward only. Renames and incompatible type changes are breaking unless you use aliases or allowed promotions. For enums, add new symbols at the end and give the enum a default symbol so old readers do not fail on an unknown one.

ChangeBackwardForwardFull
Add field with defaultYesYesYes

Remove field without defaultYesNoNo
Rename field (no alias)NoNoNo
Widen int to longYesNoNo

Remember: backward = new reads old, forward = old reads new. Always give added or removed fields a default.

What is a Schema Registry and how does it work with Kafka and Avro? Intermediate

A schema registry is a small service that stores schemas, gives each one a numeric id, and keeps versions per subject (for Kafka, normally <topic>-value). The producer registers its schema, gets an id, and writes each message as a magic byte, a 4-byte schema id and the Avro bytes. The consumer reads the id, fetches the schema once, caches it, and decodes. The registry also rejects a new schema that breaks the subject's compatibility rule, so breakage fails the producer deploy instead of crashing consumers at night.

Each message carries only 5 extra bytes instead of a whole schema, and clients cache by id, so the registry is called once per new id, not per message. If the registry is down, already-cached clients keep working; new schemas fail, so run it highly available. Confluent Schema Registry is the best known; others (Apicurio, AWS Glue) do the same job, and most also handle Protobuf and JSON Schema.

Remember: the message carries an id, the registry holds the schema and enforces compatibility at register time.

What is the difference between BACKWARD and BACKWARD_TRANSITIVE, and which would you choose? Senior

Plain BACKWARD checks a new schema only against the latest registered version. BACKWARD_TRANSITIVE checks it against every earlier version. I use the transitive mode when old data stays around or gets replayed (long retention, event sourcing, loading a lake from the start of a topic), because then a consumer must be able to read all versions. BACKWARD is the Confluent default.

Example: v1 has no country, v2 adds it with a default, v3 drops that default. v3 is compatible with v2, but it cannot read v1 data, and a replay will crash it. Upgrade order follows the mode: with BACKWARD upgrade consumers first, with FORWARD producers first, with FULL any order. In a multi-team company I prefer FULL (or FULL_TRANSITIVE) because nobody has to coordinate upgrade order. For a truly breaking change, create a new topic or subject, dual-write for a while, migrate consumers, then retire the old one.

Remember: transitive means "against all history". Use it whenever old messages can be re-read.

3. Lakehouse, Iceberg and partitioning

What are a data warehouse, a data lake and a lakehouse? Why did the lakehouse appear? Basic

A warehouse is managed, structured, SQL-first storage with transactions and good speed, but costly and awkward for raw or unstructured data. A lake is cheap object storage full of open files (Parquet, JSON, images): flexible and cheap, but historically with no transactions, no schema enforcement and no safe updates. A lakehouse puts a table format (Iceberg, Delta, Hudi) on top of the lake files, so you get ACID, schema evolution and time travel on cheap open storage, and many engines can read the same tables.

Lakes turned into "data swamps" because a table was just a folder: readers saw half-written files, two writers overwrote each other, and nobody knew which files were current. The table format fixes that with a metadata layer. The honest trade-off is that you now own more moving parts (catalog, compaction, cleanup) than with a fully managed warehouse. Many companies run both, and major warehouses can read Iceberg tables too.

Remember: lakehouse = lake files + table format. Cheap storage, warehouse-like guarantees.

What is Apache Iceberg, and why use it instead of plain Parquet files in a folder? Basic

Iceberg is an open table format: a specification and library that tracks a set of data files (usually Parquet) as one reliable table. It stores exactly which files make up the table at each moment, plus schema, partitioning and per-file statistics. Compared with a folder of Parquet files, it gives atomic commits, safe concurrent writers, schema and partition evolution, row-level updates, time travel, and no slow directory listing.

With a plain folder, a reader can see half a job, a failed job leaves partial files, two writers can overwrite the same partition, columns are matched by name or position (renames go wrong), and every query lists thousands of objects on S3. Iceberg fixes each of these with metadata and one atomic pointer swap. It is not a file format and not a database: there is no server, just the spec plus client libraries, and engines (Spark, Flink, Trino and others) do the work. The data files stay in open Parquet, so you can migrate an existing table in place.

Delta Lake and Hudi solve the same problem. Delta is closely tied to Spark and Databricks, Hudi is strong at record-level upserts and incremental pulls, and Iceberg is the most engine-neutral. I choose Iceberg for a multi-engine platform; the details of the others are specialist knowledge.

Remember: Iceberg = metadata that says which files are the table. Not a file format, not a server.

Walk me through the Iceberg metadata layers, from catalog down to data files. Intermediate

The catalog maps a table name to the current metadata file. That metadata JSON holds the schema, partition specs and the list of snapshots. Each snapshot points to a manifest list, which points to manifest files, and each manifest lists data files with their partition values and column statistics. To plan a query the engine walks down this tree, pruning at each level, so it opens only a few Parquet files and never lists a directory.

Two levels (manifest list, then manifests) are there so a new commit can reuse old manifests unchanged and add just one new manifest, which keeps commits small. The manifest list stores partition range summaries, so whole manifests are dropped without opening them. Manifests and the manifest list are Avro files; data files are normally Parquet.

Remember: catalog, metadata.json, manifest list, manifests, data files. Prune at every level, never list a folder.

What is an Iceberg snapshot, and how does time travel work? Intermediate

A snapshot is the complete state of the table after one commit: the set of data files that made up the table at that moment. Every write (append, overwrite, delete, compaction) creates a new snapshot without copying data, because it reuses existing files and manifests. Time travel just starts reading from an older snapshot, so it only needs the old files to still exist.

It is useful for reproducing a report, auditing, debugging a bad load ("what did the table look like before the job?") and quick rollback. The cost is storage: old data files stay until you expire the snapshots that reference them. Snapshots can also be named: a tag keeps one for audit, and a branch lets you write to a staging copy, check it, and then publish (the write-audit-publish pattern).

-- Spark SQL
SELECT * FROM prod.orders TIMESTAMP AS OF '2026-11-01 00:00:00';
SELECT * FROM prod.orders VERSION AS OF 4928374982374;   -- snapshot id
CALL prod.system.rollback_to_snapshot('orders', 4928374982374);

Remember: snapshot = list of files at one commit. Time travel is free until you expire snapshots.

How does Iceberg give ACID transactions on object storage with no lock server? Senior

Through optimistic concurrency. A writer reads the current metadata, writes its new data files, manifests and a new metadata file, and none of that is visible yet. The commit is one atomic compare-and-swap in the catalog: "move the pointer from v12 to v13, only if it is still v12". If another writer got there first, the swap fails, and the loser re-reads the new state, checks for real conflicts, rebuilds on top of it and retries.

Atomicity comes from the single pointer swap, isolation from snapshots (a reader keeps the snapshot it started with and is never disturbed), and durability from object storage. Appends rarely conflict with each other, but two jobs that rewrite or delete the same files can: that fails with a validation error. Retries default to a small number (about 4) and are configurable. The atomic step lives in the catalog, not in S3, so use a catalog that supports it (Hive, Glue, JDBC, REST, and similar); a plain file-system catalog is unsafe for concurrent writers on S3.

Remember: write files invisibly, then one atomic pointer swap commits. Lose the race, validate, retry.

How does Iceberg handle schema evolution without rewriting data? Intermediate

Every column gets a unique, permanent field id, stored in the metadata and in the data files, and the engine maps columns by id, not by name or position. So add, drop, rename and reorder are metadata-only changes and no data is rewritten. Old files simply return null for a newly added column.

This avoids the classic bug in plain Parquet or Hive tables, where a name or position mapping returns the wrong column's data after a drop and re-add. Ids are never reused. Type changes are allowed only when safe (int to long, float to double, wider decimal precision); string to int needs a new column and a backfill. Each schema version is kept, so old snapshots stay readable.

ALTER TABLE prod.orders ADD COLUMN coupon string;
ALTER TABLE prod.orders RENAME COLUMN cust TO customer;
ALTER TABLE prod.orders ALTER COLUMN qty TYPE bigint;

Remember: columns are tracked by id, so rename and reorder are free and a dropped column never "comes back".

How do you choose a partitioning strategy for a lake table? Intermediate

I partition on the column most queries filter on, usually a time column such as day for event data, and I check that each partition is big enough. Partitions let a query skip whole groups of files. The mistakes are going too fine (partition by user id, or by hour on a small table), which creates millions of tiny files, and too coarse (by year), where every query scans a lot.

Rough targets: each partition holds at least a few hundred MB to many GB, and the total number of partitions stays in the thousands, not millions. For a high-cardinality column like user_id do not partition by value: use a bucket transform (hash into N buckets) or sort data inside files so min and max stats work. Watch for skew too: if one country has 80% of the data, partitioning by country does not balance the work. Partitioning prunes folders; sorting narrows min and max within files; use both. In Iceberg you can change the partitioning later, so start simple and measure.

Remember: partition by what queries filter on, in chunks big enough to be worth skipping. Never by an id.

What is hidden partitioning in Iceberg, and what is partition evolution? Intermediate

In Hive-style tables the partition is a folder and an extra column like dt=2026-11-17, and users must filter on it or the query scans everything. In Iceberg you declare a transform of a real column, such as day(event_time), and Iceberg computes and tracks the partition value itself. A filter on event_time is automatically turned into partition pruning, and nobody can forget or mis-fill a partition column.

Transforms include year, month, day, hour, bucket(N, col) and truncate(W, col). Because layout is metadata, you can also change it: move from monthly to daily partitions with one command. Old files keep the old spec and new files use the new one; each manifest remembers its spec, and the planner prunes each group with its own rules. Nothing is rewritten, though queries spanning both layouts plan a little slower, and you can compact old data into the new layout when convenient.

CREATE TABLE prod.events (id bigint, user_id bigint, event_time timestamp)
USING iceberg
PARTITIONED BY (day(event_time), bucket(16, user_id));

Remember: partition by a transform of a real column. Users filter on the column, Iceberg handles the folders, and the layout can change later.

Explain copy-on-write versus merge-on-read in Iceberg. Senior

Both exist because data files are immutable. Copy-on-write rewrites each data file that holds an affected row: reads stay fast, but one changed row rewrites a whole large file. Merge-on-read leaves data files alone and writes small delete files; writes are cheap, but readers must merge deletes with data until a compaction cleans up. I use copy-on-write for read-heavy tables with infrequent batch updates, and merge-on-read for frequent small updates and CDC.

Delete files come in two kinds. A position delete says "in file X, rows 17 and 902 are deleted". An equality delete says "any row with order_id = 42 is deleted", which suits streaming upserts, where the writer does not know file positions. An update is a delete plus a new row. Newer table spec versions replace position deletes with compact deletion vectors, which make merge-on-read reads cheaper. Copy-on-write is typically the default and the mode is a table property.

Remember: COW pays on write, MOR pays on read. Merge-on-read needs compaction.

What is the small files problem, and what maintenance does an Iceberg table need? Intermediate

Small files are data files far below a useful size (say a few MB when the target is a few hundred MB). Every file costs a fixed amount: an object-store request, a footer read, a task launch and a metadata entry, so reading a million 1 MB files is far slower than reading 500 big ones holding the same bytes. The fix is compaction: rewrite many small files into few well-sized ones, on a schedule, plus cleanup of old snapshots.

They come from streaming writes that commit every few seconds, too many shuffle partitions in Spark, and over-partitioning. Prevention: commit every few minutes, not seconds, and choose coarser partitions. Maintenance jobs for an Iceberg table:

  • Compaction (rewrite_data_files): merge small files toward the target size (default about 512 MB), optionally sort, and apply delete files.
  • Expire snapshots (expire_snapshots): drop old snapshots and the files only they use; without it storage and metadata grow forever. It also ends time travel to those snapshots, so keep retention longer than your longest query.
  • Remove orphan files: delete files no metadata knows about (from failed jobs), with an age threshold so a running write is not harmed.
  • Rewrite manifests: regroup thousands of tiny manifests left by frequent commits.

Remember: few big files beat many small ones. Compact often, expire snapshots, clear orphans.

4. Pipelines, streaming and data quality

Batch versus streaming processing: how do you decide? Basic

I ask "what does it cost the business if this data is one hour old?". If the answer is "nothing", I use batch (or micro-batch every few minutes): it is simpler, cheaper and easy to re-run and test. I use streaming when seconds matter, for things like fraud alerts, live dashboards or keeping a search index fresh.

Batch processes a bounded chunk on a schedule ("every night, process yesterday"). Streaming processes an unbounded flow of events continuously. Streaming costs more in complexity: state, ordering, late events, restarts and exactly-once effects, plus jobs that run all day. Many systems use both: streaming for the freshest slice, batch to reprocess and correct. Engines like Spark and Flink use nearly the same API for both, which narrows the gap. A lambda architecture runs both paths and merges them (two code bases, painful); a kappa architecture uses one streaming path and replays the log to reprocess.

Remember: batch unless freshness really pays for the extra complexity.

ETL versus ELT: what is the difference and why did ELT become popular? Basic

ETL transforms data on a separate processing server before loading only the result into the warehouse. ELT loads raw data first and transforms it inside the lake or warehouse with its own scalable engine (SQL, Spark, dbt). ELT won because cloud storage and compute are cheap and elastic, and keeping raw data means I can change business logic later and re-run without re-extracting from the source.

ETL is still right when data must be masked or filtered before it may land (privacy rules), or when you must shrink huge volumes before loading. A common practical mix: a little "T" before load (drop PII, validate types), and the main modelling after.

Remember: ETL = shape then load. ELT = load raw, shape later where the compute is.

What is Change Data Capture (CDC), and how do you do it? Intermediate

CDC captures every insert, update and delete from a source database as a stream of change events, so a lake, cache or search index can follow it. I prefer log-based CDC: it reads the database transaction log (MySQL binlog, PostgreSQL WAL), sees every change in commit order including deletes, and puts almost no load on the tables. Debezium on Kafka Connect is the best-known tool.

The alternatives are weaker. Query-based CDC polls for updated_at greater than the last seen time: it misses hard deletes, can miss rows updated at the same moment, and loads the database. Trigger-based CDC slows every write. A Debezium event has before and after row images, an op code (create, update, delete, snapshot read) and the log position. Downstream, apply events per key in order with upserts and deletes (MERGE). One operational risk to know: in PostgreSQL an unconsumed replication slot makes the database keep WAL forever and can fill its disk, so monitor slot lag.

Remember: log-based CDC = read the DB log, not the tables. Apply per key in order, and watch the lag.

Explain at-most-once, at-least-once and exactly-once. Is exactly-once real? Intermediate

At-most-once means delivered zero or one time: you can lose data (commit the offset before processing). At-least-once means one or more times: no loss but duplicates after retries (process, then commit). Exactly-once is really exactly-once effect: at-least-once delivery combined with deduplication or idempotent or transactional writes, inside a boundary where I control both sides.

Over an unreliable network you cannot guarantee a message arrives exactly once, because a lost acknowledgement looks the same as a lost message. Real mechanisms: Kafka's idempotent producer (sequence numbers per partition) and transactions (atomic writes to several partitions plus consumer offsets, for Kafka-to-Kafka flows); Flink checkpoints with a two-phase-commit sink; a checkpointed, idempotent sink in Spark; and an Iceberg MERGE on a key. It breaks at the edge: calling an external API or appending to a plain file has no such guarantee, so use an idempotency key.

Remember: exactly-once = at-least-once + idempotent write.

What is an idempotent data pipeline, and how do you build one? Intermediate

A pipeline is idempotent if running it twice with the same input gives the same final data as running it once. Pipelines are re-run all the time (retries, backfills, replays), so an append-only job turns every retry into duplicates and wrong totals. I make jobs idempotent by overwriting the partition they own, or by upserting with MERGE on a business key, and by passing the run date as a parameter instead of using the wall clock.

Other techniques: write to a temporary location and commit atomically (Iceberg and Delta do this), so a half-finished run is invisible; track processed inputs (file names, offsets, event ids) in the same transaction as the output; avoid now(), random ids and "pick any row". For deduplication, define what identifies a record (a producer-generated event id or a business key), keep the latest by event time or source offset, and add a tie-breaker so a re-run picks the same row. In a stream, keep seen ids only for a bounded time, longer than the longest expected duplicate gap. The test is simple: run the job twice and compare the output.

-- re-runnable: only touches the day it owns
INSERT OVERWRITE prod.sales_daily PARTITION (dt = '2026-11-17')
SELECT ... FROM raw.sales WHERE sale_date = '2026-11-17';

-- dedup: latest per key, deterministic tie-break
SELECT * FROM (SELECT *, row_number() OVER (PARTITION BY order_id
       ORDER BY updated_at DESC, source_offset DESC) rn FROM bronze.orders) WHERE rn = 1;
Watch out: an append-only task with "retry 3 times", and current_date inside the query so a backfill reads today instead of the run date.

Remember: overwrite the partition or merge on a key. Run it twice and the result must not change.

What are event time, processing time and watermarks? How do you handle late data? Senior

Event time is when something happened; processing time is when my system saw it, maybe minutes later. I group by event time, so results do not depend on network delay and replays give the same answer. A watermark is the engine's moving estimate "I have probably seen all events up to time T" (highest event time seen minus an allowed lateness). When it passes the end of a window, the window is closed and its state dropped; events older than the watermark are late.

For late events I choose among: drop them (simple, counts slightly off), send them to a side output or "late" table for repair, allow more lateness (more delay and more state), or emit corrected results. The trade-off is always latency versus completeness. A batch job that recomputes recent windows from the raw log is a common safety net. One practical trap: an idle Kafka partition does not advance its watermark and can stall the whole job, so configure an idle timeout.

Remember: group by event time, let the watermark close windows, and repair very late data in batch.

How do you assure data quality in a pipeline? What happens when a check fails? Intermediate

I use layers of automated checks and decide the failure action by severity. At ingestion I validate schema, types and required fields. On rows I check not-null, ranges, allowed values, key uniqueness and referential integrity. On the table I check row count versus the usual, freshness and totals reconciled with the source. A critical failure stops the pipeline so bad data never reaches consumers; a minor failure sends the bad rows to a quarantine table with a reason and alerts. I never silently drop rows.

Tools such as dbt tests, Great Expectations or Soda run these checks. A good pattern is write-audit-publish: write new data where consumers cannot see it (a staging table or an Iceberg branch), run the checks, and publish atomically only if they pass. The people side matters as much: a data contract is an explicit, machine-checkable agreement between the producing team and consumers, covering schema, meaning (currency, tax included?), quality rules, freshness, ownership and how breaking changes are announced. Checked in the producer's CI, it stops "an upstream team renamed a column and a dashboard broke two weeks later".

Remember: check early, stop on critical failures, quarantine the rest, and never drop silently.

5. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview.

A producer team removed a field from the Avro schema on a Kafka topic and consumer jobs crashed in production. What do you do? Senior

Roll the producer back so new messages use the old schema again, then fix the removal in a compatible way. The root cause is a breaking schema change that got through, so I then enforce compatibility in the registry and the producer's CI.

Situation: consumers fail with a decoding or "missing field" error right after a producer deploy, and messages with the new schema are mixed in the topic with old ones.

Check first: the registry history for the subject (what changed, did the removed field have a default, what compatibility mode was set; NONE would explain how it got through), which consumer groups fail, and how many bad-schema messages exist.

Fix: (1) roll back the producer. (2) Pause stuck consumers; for messages already written, deploy a consumer that handles the new schema or move them to a dead-letter topic after copying them for replay. Do not blindly reset offsets, that loses data. (3) Re-release the change in two steps: make the field optional with a default and upgrade all consumers, then remove it. (4) Replay from the saved offset.

Prevent: BACKWARD or FULL (transitive if you replay) on the subject, a registry compatibility check in the producer's CI, consumer contract tests, and a deprecation process (announce, dual write, remove).

Remember: never remove a field in one step. Make it optional first, upgrade readers, then remove.

After a job retry, the daily revenue is double what the source system says. Find and fix it. Senior

A failed task was retried and appended the rows again, so the job is not idempotent. I would roll the table back to the snapshot before the bad commits, or re-run that day with a partition overwrite from raw data, and then make the job idempotent so it cannot happen again.

Situation: a task timed out halfway, the orchestrator retried, and the second attempt appended all rows again.

Check first: compare counts with the source for that date; run SELECT order_id, count(*) ... HAVING count(*) > 1 to confirm exact duplicates; look at the table's snapshot history for two append commits from the same run id.

Fix: on an Iceberg table, rollback_to_snapshot to the one before the bad commits if nothing else has written since, or re-run the day with partition overwrite. If neither works, deduplicate with row_number by business key into a new table, validate totals, then swap. Rebuild downstream tables for the date and tell consumers the numbers were wrong for a period.

Prevent: partition overwrite or MERGE on a key, the logical date as a parameter, a unique-key test, and a reconciliation check (row count and sum versus source) that fails the pipeline before publish.

Remember: retries are normal, so the job must be safe to run twice.

Mobile events arrive up to two days late and your hourly streaming counts keep changing. What do you design? Senior

I run two paths: a streaming job with a short watermark for a fresh but provisional view, and a batch job that recomputes the last few days from the raw table for the final numbers. Every event, including late ones, is kept in the raw layer with both event time and arrival time.

Situation: devices buffer events offline and upload later. A 10-minute watermark drops them; an unbounded one never finalises.

Check first: measure the lateness distribution (what percent arrive within 1 minute, 1 hour, 1 day, 2 days) and ask the business which numbers must be exact and when.

Fix: short watermark (say 15 minutes) for the "fresh, approximate" view; write all events to the raw table; an hourly batch recompute for the last 3 days and a final one after 48 hours, using idempotent partition overwrite or merge. Dashboards read the corrected table and label the newest hours "provisional". Events beyond the cutoff go to a late table, with an alert if their rate is unusual.

Prevent: record event time and ingestion time on every record, and agree a completeness SLA with consumers.

Remember: fast and approximate in streaming, correct in batch, and keep the raw log.

A daily report on an Iceberg table went from 2 minutes to 40 minutes after streaming ingestion was added. What do you check? Senior

Almost certainly small files and metadata growth from frequent streaming commits. I check the table's file and snapshot metadata, compact the hot partitions, rewrite manifests and expire snapshots, then lower the commit frequency and schedule compaction.

Situation: the query did not change, only the ingestion: a Flink job now commits every 10 seconds.

Check first: query the metadata tables: file count and average size per partition (expect thousands of files of 1 to 5 MB), the number of snapshots per day, and the number of manifests. The engine UI shows many tiny tasks and long planning time.

Fix: run rewrite_data_files on the affected partitions (old ones, to avoid conflicts with streaming), then rewrite_manifests and expire_snapshots. For the cause, raise the commit interval to a few minutes or stage and merge hourly, and schedule compaction.

Prevent: a layout monitor that alerts when average file size drops below a threshold.

Remember: commit frequency is a cost knob. More commits means more small files.

A user asks to be deleted (GDPR erasure). Their data is in an Iceberg lake with years of history. How do you actually delete it? Senior

A DELETE alone is not enough, because in an immutable table it only hides the rows. I delete the rows, compact so data files are physically rewritten, expire the old snapshots and remove orphans so time travel cannot bring the data back, and then handle every other copy (derived tables, indexes, backups).

Situation: the user's events, orders and profile are spread across raw, cleaned and gold layers, plus extracts.

Check first: find every place that holds the user id (data catalog, lineage, PII inventory), and check whether the law requires keeping some records, such as invoices, which may need anonymising instead.

Fix: (1) DELETE FROM t WHERE user_id = X on each table: this creates a new snapshot. With copy-on-write the files are rewritten; with merge-on-read only delete files hide the rows. (2) Compact so the data files are rewritten. (3) Expire old snapshots and remove orphan files, since old snapshots still reference the original files. (4) Handle other copies and document backup retention. (5) Keep proof, within the legal deadline.

Prevent: keep PII in a small separate table keyed by a surrogate id, batch deletions into a regular job, or use per-user encryption keys and delete the key.

Watch out: running DELETE and saying "done". The data is still in old snapshots until they are expired.

Remember: delete, compact, expire snapshots, remove orphans. Then the other copies.

CDC events for the same order arrive out of order and the lake table shows an old status. How do you fix it? Senior

Apply changes by source version, not by arrival order. I key the topic by the primary key, dedupe each batch keeping the event with the highest log position, and make the merge conditional so it never moves backwards.

Situation: the lake shows PENDING while the source says SHIPPED, because two updates were applied in the wrong order (parallel tasks, or a replay).

Check first: is the topic keyed by order id, so all changes for one order sit in one partition in order? Does the merge take whichever row it sees last? Does each event carry a version such as the log position or source timestamp?

Fix: in each batch deduplicate by key, keeping the highest log position (timestamp plus offset as tie-breaker), then MERGE ... WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE. Repair the wrong rows by replaying from raw or re-snapshotting the affected keys.

Prevent: store the source version on every row.

Remember: order by the source version, and never let an older event overwrite a newer one.
