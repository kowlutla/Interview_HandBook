Mental model: the 7 ideas everything hangs on

One line: Spring Boot is Spring plus opinions. It looks at your classpath and your properties, and registers the beans you would probably have written yourself. You override any of it by defining your own bean or setting a property.
  1. Boot is not a new framework. It sits on Spring Framework. Every Boot feature ends up as normal Spring beans and normal Spring configuration. Nothing is hidden bytecode magic.
  2. Starters pull in the right jars. One dependency such as spring-boot-starter-web brings Spring MVC, Jackson, Tomcat and logging, all at versions that are known to work together (the BOM, a bill of materials).
  3. Auto-configuration is "conditional configuration classes". Each one says "if this class is on the classpath and the user has not defined their own bean, create this bean". It is read from a list file in each jar.
  4. User beans always win. Auto-configuration is processed after your own configuration, and most of its beans are @ConditionalOnMissingBean. Define your own and the default backs off.
  5. Externalized configuration with a strict order. The same app runs everywhere because properties come from many sources (files, environment variables, command line) and the higher source wins.
  6. The app is a plain main method. SpringApplication.run builds the context, starts an embedded web server inside the same process, and runs your runners. Deploy is "run one jar".
  7. Production features are opt-in add-ons. Actuator (health, metrics), graceful shutdown, structured logging, tracing and native image are modules you switch on, not code you write.

1. Boot basics, starters and the BOM

What does Spring Boot give you that plain Spring does not? Basic

What the interviewer is testing: do you see Boot as a set of conventions on top of Spring, not as a replacement.

With plain Spring you had to choose and align many jars, write XML or Java configuration for the DataSource, the transaction manager, the view resolver, the Jackson converter, and then build a WAR and deploy it into an external Tomcat. Boot removes that work in five ways. First, starters give you one dependency per feature, with compatible versions. Second, auto-configuration creates sensible beans for what is on the classpath. Third, embedded server: Tomcat runs inside your jar, so you start the app with java -jar. Fourth, externalized configuration with profiles and environment variables, which fits containers well. Fifth, production features such as Actuator health and metrics. Boot generates no code and needs no XML. It is the same Spring underneath, so everything you learned about beans, proxies and transactions still applies.

Likely follow-ups
  • Can you use Spring without Boot? Yes. Boot is optional, and some teams still do it on old stacks.
  • Is Boot slower because of auto-configuration? A little at startup, since it evaluates many conditions. Runtime speed is the same as hand-written configuration.
What is inside @SpringBootApplication? Basic

What the interviewer is testing: whether you know the annotation is a shortcut for three real ones.

@SpringBootApplication is a meta-annotation, which means an annotation made of other annotations. It combines three. @SpringBootConfiguration is a specialised @Configuration, so the class can declare @Bean methods and tests can find it. @EnableAutoConfiguration turns on auto-configuration: it imports a selector that reads the list of auto-configuration classes from every jar. @ComponentScan scans the package of the annotated class and all sub-packages for @Component, @Service, @Repository and @Controller classes. It also adds filters so that auto-configuration classes are not found by accident through scanning. Inside @EnableAutoConfiguration there is also @AutoConfigurationPackage, which records your base package. JPA uses it to find your @Entity classes and Spring Data uses it to find repositories.

Common mistakes: putting the main class in the default (root) package, or in a package that is not a parent of your other packages. Then component scan misses your beans and you get NoSuchBeanDefinitionException.
Your @Service in another package is not found. How does Boot decide where to scan, and how do you change it? Basic

What the interviewer is testing: the most common beginner startup failure.

Boot scans from the package of the class that carries @SpringBootApplication, downwards. A class in com.acme.shared is not found if the main class is in com.acme.orders. There are three clean fixes. The best is to move the main class to a parent package such as com.acme. Second, list packages with @SpringBootApplication(scanBasePackages = {"com.acme.orders","com.acme.shared"}). Third, add @Import or a @Bean for the specific class. Entities and repositories have their own scan roots: use @EntityScan and @EnableJpaRepositories(basePackages=...) when they live outside the main package. Careful: when you add @EnableJpaRepositories yourself, Boot's repository auto-configuration backs off, so give it all the packages it needs.

What is a starter? What is inside one? Basic

What the interviewer is testing: do you know a starter is mostly a dependency list, not code.

A starter is a small module with almost no code. It is a POM (or Gradle module) that lists the dependencies you need for one feature. spring-boot-starter-web pulls in Spring MVC, Jackson, embedded Tomcat, validation hints and the base starter (logging, YAML, Spring core). spring-boot-starter-data-jpa brings Hibernate, Spring Data JPA, JDBC and the Hikari connection pool. The versions are not written in the starter, they come from the Boot BOM. The actual behaviour, creating beans, lives in the spring-boot-autoconfigure jar, which is triggered by what the starter put on the classpath. Naming rule: official starters are spring-boot-starter-*. Third parties should use acme-spring-boot-starter, so they do not look official.

Likely follow-ups
  • Does a starter bring auto-configuration code? Official ones rely on the one shared spring-boot-autoconfigure jar (before Boot 4). Third-party starters usually have a separate autoconfigure module.
How does Boot manage dependency versions? How do you override one? Intermediate

What the interviewer is testing: knowledge of the BOM, and the real-life need to patch a library (for example for a security fix).

Boot ships a BOM (bill of materials) called spring-boot-dependencies. It is a list of hundreds of libraries with versions that were tested together. You get it by using spring-boot-starter-parent as the Maven parent, or by importing the BOM in dependencyManagement (when you already have another parent), or in Gradle with the Spring Boot plugin and dependency management. After that you write dependencies without versions. To override one version, set the version property that the BOM uses, for example <jackson-bom.version>2.17.2</jackson-bom.version> in Maven properties, or ext['jackson-bom.version'] = '2.17.2' in Gradle. This changes all related artifacts at once. Only override for a reason (a CVE fix), and re-run the tests, because Boot's auto-configuration was tested against its own version.

<!-- Maven: use the BOM without the parent -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>3.4.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
Likely follow-ups
  • Where do I find the property name? In the Boot reference appendix "Dependency versions", or open the spring-boot-dependencies POM.
  • Parent versus import? The parent also sets Java level, resource filtering and plugin defaults. The import only gives versions.
Common mistakes: hard-coding a version on a library the BOM already manages and then wondering why two versions of it are on the classpath.

How do you start a new Boot project, and what is the Initializr? Basic

What the interviewer is testing: basic fluency.

Spring Initializr (start.spring.io) is a web service that generates a project skeleton: build file (Maven or Gradle), Java version, Boot version, the dependencies you tick, and a main class with a test. IDEs (IntelliJ, VS Code) call the same service, and you can use it with curl from a script. It creates one main class annotated with @SpringBootApplication, an empty application.properties and a context-loads test. The generated build includes the Boot plugin, which gives you spring-boot:run (or bootRun), the executable repackaging and build-image. Many companies run an internal Initializr, or a template repository, so every new service starts with the same logging, security and observability setup.

Spring Boot, Spring Framework, Spring Cloud: how are they related? Basic

What the interviewer is testing: terminology that candidates mix up.

Spring Framework is the base: the container (IoC and DI), AOP, transactions, MVC and so on. Spring Boot is a layer that makes using the Framework quick: starters, auto-configuration, embedded server. Spring Cloud is a family of libraries for distributed systems: config server, service discovery, load balancing, circuit breakers, gateway, and so on. Spring Cloud builds on Boot, and each Spring Cloud release train is matched to specific Boot versions (the "release train" names are like 2023.0.x, 2024.0.x). So you pick your Boot version first, then the Spring Cloud train that supports it. Using a mismatched pair is a classic cause of startup errors after an upgrade. In Kubernetes, many teams skip parts of Spring Cloud (discovery, config) and use platform features instead.

How can you customise how the application starts (banner, profiles, web type)? Intermediate

What the interviewer is testing: that SpringApplication is an object you can configure, not only a static call.

The static SpringApplication.run(App.class, args) is a shortcut. You can build the object yourself: new SpringApplication(App.class), then set options and call run. Or use SpringApplicationBuilder for a fluent style. Typical options: setBannerMode(Banner.Mode.OFF), setAdditionalProfiles("local"), setDefaultProperties(map), setWebApplicationType(WebApplicationType.NONE) (a batch job with no web server), addListeners(...), setLazyInitialization(true), and setApplicationStartup(new BufferingApplicationStartup(2048)) to record startup steps. Most of these also exist as properties (spring.main.*), and properties are usually better because they change without a rebuild. The same options work in tests through @SpringBootTest(properties=...).

public static void main(String[] args) {
    SpringApplication app = new SpringApplication(App.class);
    app.setBannerMode(Banner.Mode.OFF);
    app.setWebApplicationType(WebApplicationType.NONE);   // batch / worker
    app.run(args);
}

2. The startup sequence

What happens when you call SpringApplication.run()? Senior

What the interviewer is testing: can you walk through the real start, which helps debugging every startup problem.

In order: (1) Boot creates a SpringApplication and detects the web type from the classpath: servlet (MVC), reactive (WebFlux) or none. It loads ApplicationContextInitializer and ApplicationListener objects from the jar metadata. (2) It starts the run listeners and publishes ApplicationStartingEvent. (3) It prepares the Environment: reads command-line args, system properties, environment variables and application.yml, activates profiles, and publishes ApplicationEnvironmentPreparedEvent. The banner prints here. (4) It creates the ApplicationContext of the right type (for servlet apps an AnnotationConfigServletWebServerApplicationContext), runs the initializers, and publishes ApplicationContextInitializedEvent. (5) It registers your main class as a bean source, and publishes ApplicationPreparedEvent. (6) It calls refresh(), the normal Spring start: bean definitions are loaded (component scan, auto-configuration), the web server is created, singleton beans are made, and the server begins accepting requests. (7) It publishes ApplicationStartedEvent, then calls the ApplicationRunner and CommandLineRunner beans. (8) It publishes ApplicationReadyEvent and the readiness state becomes ACCEPTING_TRAFFIC. If anything throws, ApplicationFailedEvent fires and failure analyzers print a friendly message.

Likely follow-ups
  • When does the port start accepting connections? The web server starts while the context finishes refresh, and Boot makes sure it only opens after beans are ready in modern versions.
  • Where would you hook code that must run before the context? An EnvironmentPostProcessor or an ApplicationListener registered in META-INF/spring.factories.
Which startup events are there, and how do you listen for them? Intermediate

What the interviewer is testing: that you pick the right hook for the job.

The events, in order, are ApplicationStartingEvent, ApplicationEnvironmentPreparedEvent, ApplicationContextInitializedEvent, ApplicationPreparedEvent, then (after the context refreshes) ApplicationStartedEvent, AvailabilityChangeEvent for liveness, runners are called, ApplicationReadyEvent, and AvailabilityChangeEvent for readiness. On failure you get ApplicationFailedEvent. The first few happen before the context exists, so an @EventListener bean cannot receive them. Use SpringApplication.addListeners or the spring.factories file. For normal work, use @EventListener(ApplicationReadyEvent.class) on a bean: it runs after everything is started, which is where you warm caches or announce "I am up". Use ApplicationReadyEvent rather than @PostConstruct for work that needs the whole app, since @PostConstruct runs while the context is still being built.

@Component
class WarmUp {
    @EventListener(ApplicationReadyEvent.class)
    void onReady() { cache.preload(); }
}
CommandLineRunner versus ApplicationRunner versus @PostConstruct versus ApplicationReadyEvent: when do you use which? Intermediate

What the interviewer is testing: startup ordering and failure behaviour.

@PostConstruct (or InitializingBean) runs for one bean, when that bean is created, so other beans may not be ready. Keep it for small internal setup. CommandLineRunner and ApplicationRunner run once, after the context is fully refreshed, just before ApplicationReadyEvent. The first gets raw String[] args; the second gets parsed ApplicationArguments, so you can ask for --name=value options. You can order several runners with @Order. If a runner throws, the application fails to start and the process exits. That is useful for "must-have" checks and for batch-style jobs. ApplicationReadyEvent comes after runners, and an exception inside a listener does not stop the app the same way. Important: runners run on the main thread, so a slow runner delays readiness. For long work, hand it to an executor.

@Component @Order(1)
class SeedData implements ApplicationRunner {
    public void run(ApplicationArguments args) { /* load reference data */ }
}
Common mistakes: calling a slow remote service in a runner on every pod start, so a restart storm hits that service.
How does Boot decide whether the app is servlet, reactive or non-web? Intermediate

What the interviewer is testing: classpath-driven decisions, and what happens when both stacks are present.

Boot checks the classpath. If Spring MVC and the Servlet API classes are present, it is SERVLET. If only Spring WebFlux is present, it is REACTIVE. If neither, it is NONE and no web server starts. If both MVC and WebFlux are present, MVC wins. This is a common surprise when someone adds spring-boot-starter-webflux only to use WebClient: the app stays a servlet app, which is fine. You can force it with spring.main.web-application-type=reactive or none. The type decides the context class, which server is created (Tomcat or Netty), and which auto-configurations apply, since many are @ConditionalOnWebApplication(type=...).

Startup fails with a long stack trace. How does Boot turn it into the readable "APPLICATION FAILED TO START" message? Intermediate

What the interviewer is testing: that you read the Description and Action lines first.

When startup throws, Boot asks a list of FailureAnalyzer objects whether they understand the exception. Each analyzer looks for one cause, for example "port already in use", "no qualifying bean", "circular dependency", "cannot bind property", "failed to configure a DataSource". The first match produces two parts: Description (what went wrong) and Action (what to try). So the real first step in debugging is to read those two lines, not the 200-line trace. If no analyzer matches, you see the plain trace; then read the bottom-most "Caused by". You can add your own analyzer: implement FailureAnalyzer and register it in META-INF/spring.factories (this file still exists for these extension types, even though auto-configuration moved to the imports file). Libraries do this to turn their own misconfiguration into a short helpful message.

***************************
APPLICATION FAILED TO START
***************************
Description:
Web server failed to start. Port 8080 was already in use.
Action:
Identify and stop the process that's listening on port 8080 or configure this application to listen on another port.
What does spring.main.lazy-initialization do, and what are the risks? Intermediate

What the interviewer is testing: trade-offs of faster startup.

Normally Spring creates all singleton beans at startup. With lazy initialization on, beans are created the first time something asks for them. Startup is faster and uses less memory at the start, which helps in local development, tests, and serverless-like workloads. The costs are real: misconfigured beans are found only when first used, so a bad connection string might fail on the first customer request instead of at deploy time. The first request to each path is slower, which hurts latency and can look like a performance bug. Health checks might report "up" while parts of the app are broken. In production most teams keep eager startup, since "fail fast" is worth the seconds. A middle path: make only specific heavy beans @Lazy, or turn on global lazy only for local and test profiles.

Boot 2.6 and later refuse circular dependencies. What changed, and how do you fix a cycle? Intermediate

What the interviewer is testing: design sense, not just the flag.

A cycle is when bean A needs B and B needs A. With constructor injection Spring cannot build either first, so it fails with "The dependencies of some of the beans in the application context form a cycle". Field or setter injection used to hide the problem, since Spring could create a half-built bean and fill it later. From Boot 2.6 that is off by default (spring.main.allow-circular-references=false). Setting it to true makes the error go away but keeps the bad design. Better fixes: (1) extract the shared part into a third bean that both use; (2) invert one side with an event (ApplicationEventPublisher) so A does not call B directly; (3) pass a value instead of a bean; (4) as a last resort, inject one side as @Lazy (a proxy that resolves later) or through ObjectProvider. A cycle is nearly always a sign that two classes share a responsibility that belongs in one place.

Your Boot app takes 90 seconds to start. How do you find out why? Senior

What the interviewer is testing: a method to measure, not guess.

First measure. Boot can record steps through BufferingApplicationStartup: set it on the application, add Actuator, and read /actuator/startup for a list of steps with durations (bean creation, auto-configuration processing). Also run once with --debug or log level DEBUG for org.springframework.boot and look at timestamps. The usual causes: a huge component scan or classpath scan; Hibernate scanning many entities or ddl-auto=update reading the whole schema; Flyway or Liquibase running many migrations; a bean that calls a remote service in @PostConstruct (config server, vault, a slow DNS or a remote health check); Kafka or other clients that connect eagerly; too many auto-configurations loaded because of fat classpath; and CPU limits in containers (a pod with 0.5 CPU starts several times slower). Fixes by cause: move slow work out of startup or make it async, trim classpath and exclude unused auto-configurations, give startup more CPU (or use a startup probe), enable spring.main.lazy-initialization where safe, use CDS (class data sharing) or AOT, and in the extreme a native image.

SpringApplication app = new SpringApplication(App.class);
app.setApplicationStartup(new BufferingApplicationStartup(4096));
// management.endpoints.web.exposure.include=startup
// curl localhost:8080/actuator/startup

3. Auto-configuration in depth

How does auto-configuration work internally? Senior

What the interviewer is testing: the most famous Boot question. A senior answer names the file, the selector, and the conditions.

Every jar that offers auto-configuration lists its configuration classes in a file: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. @EnableAutoConfiguration imports an AutoConfigurationImportSelector. It reads that file from every jar on the classpath, removes any class you excluded, and hands the rest to Spring as configuration classes. Because it is a deferred import selector, these classes are processed after your own configuration, so your beans are already registered. Then each auto-configuration class is checked against its conditions, such as @ConditionalOnClass(DataSource.class) and @ConditionalOnMissingBean(DataSource.class). If all conditions pass, its @Bean methods run. If not, the class is skipped completely. Nothing is scanned at runtime; it is a list read at startup plus fast checks. Class-presence checks use ASM (reading bytes) so classes are not even loaded when the answer is "no".

spring.factories versus AutoConfiguration.imports: what is the difference? Intermediate

What the interviewer is testing: migration awareness for libraries and starters.

In Boot 2.6 and earlier, auto-configuration classes were registered in META-INF/spring.factories under the key org.springframework.boot.autoconfigure.EnableAutoConfiguration. That file is a generic key-value file used for many extension points, so it was slow to scan and mixed unrelated things. Boot 2.7 introduced a dedicated file, META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, which simply lists one fully qualified class name per line. It is faster to read and easier to tool. Boot 2.7 supported both (the old way deprecated), and Boot 3.0 removed support for the old key: a library that only has the spring.factories entry silently stops auto-configuring on Boot 3. The factories file is still used for other extension points (listeners, initializers, environment post-processors, failure analyzers). The new @AutoConfiguration annotation (2.7) marks these classes and has before and after attributes for ordering.

# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.audit.AuditAutoConfiguration
com.acme.audit.AuditWebAutoConfiguration
Common mistakes: upgrading to Boot 3 and finding that an old internal starter "does nothing". The cause is almost always the missing imports file.
Name the common @Conditional annotations and what each is for. Intermediate

What the interviewer is testing: breadth, and that you understand each one has a purpose.

  • @ConditionalOnClass / @ConditionalOnMissingClass: a class is (or is not) on the classpath. This is how "add the jar and it turns on" works.
  • @ConditionalOnBean / @ConditionalOnMissingBean: a bean of that type exists or not. The second one makes defaults back off.
  • @ConditionalOnSingleCandidate: exactly one bean (or one primary) of that type exists.
  • @ConditionalOnProperty: a property has a given value. Typical for feature flags, for example my.feature.enabled=true, with matchIfMissing to say what happens when it is absent.
  • @ConditionalOnResource: a file is present.
  • @ConditionalOnWebApplication / @ConditionalOnNotWebApplication: servlet, reactive or none.
  • @ConditionalOnExpression: a SpEL expression (Spring Expression Language) is true.
  • @ConditionalOnCloudPlatform, @ConditionalOnJava, @ConditionalOnWarDeployment: environment checks.
  • @Profile: a profile is active (it is itself a condition).

Two rules matter. Class-based conditions are safe on an annotation of the class itself, because they are checked without loading the class. And @ConditionalOnBean and @ConditionalOnMissingBean depend on the order in which bean definitions are registered, so they are reliable only in auto-configuration classes, which run last. Using them in your own normal configuration can give surprising results.

Likely follow-ups
  • How do I write my own condition? Implement Condition (or extend SpringBootCondition) and use @Conditional(MyCondition.class).
How does @ConditionalOnMissingBean let your bean replace a default, and what can go wrong? Senior

What the interviewer is testing: the back-off mechanism and its side effects.

Auto-configuration classes are processed after yours. Boot's default ObjectMapper bean is declared with @ConditionalOnMissingBean. If you define your own ObjectMapper bean, the condition sees yours and skips the default. This is the whole "your code wins" rule. The danger is that replacing a bean also drops everything that default setup did. If you create your own ObjectMapper with new ObjectMapper(), you lose Boot's settings (spring.jackson.* properties, modules, date format defaults). A frequent bug is that dates suddenly become numbers or unknown JSON fields start causing failures. Better: customise rather than replace. Boot exposes customizer beans for this, such as Jackson2ObjectMapperBuilderCustomizer, WebServerFactoryCustomizer, RestTemplateCustomizer and MeterRegistryCustomizer. They adjust the default and keep everything else. The same happens with DataSource: defining one yourself turns off Hikari property binding unless you bind it yourself.

@Bean
Jackson2ObjectMapperBuilderCustomizer jsonCustomizer() {
    return b -> b.featuresToDisable(SerializationFeature.FAIL_ON_EMPTY_BEANS)
                 .simpleDateFormat("yyyy-MM-dd'T'HH:mm:ss");
}
How do you control the order of auto-configurations? Senior

What the interviewer is testing: know that order matters for conditions on beans.

Order matters because @ConditionalOnBean and @ConditionalOnMissingBean look at what has been registered so far. If A needs a DataSource that B creates, A must run after B. Use the attributes of @AutoConfiguration: @AutoConfiguration(after = DataSourceAutoConfiguration.class) or before = .... The older equivalents are @AutoConfigureAfter and @AutoConfigureBefore. A coarse global order can be set with @AutoConfigureOrder. Ordering only works between auto-configuration classes. It does not change the order between your own configuration and auto-configuration (yours is always first), and it does not control the order in which beans are created at runtime. For runtime creation order use @DependsOn or, better, express the real dependency through constructor parameters. Do not use ordering to hide a design problem.

How do you turn off an auto-configuration you do not want? Basic

What the interviewer is testing: practical control, and the usual "DataSource" error.

Three ways. In code: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class), or excludeName with a string when the class is not on your compile classpath. In properties: spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration, handy because you can set it per profile or by environment variable. Or remove the dependency that triggered it. A classic case: a service that has a JDBC library on the classpath through some other dependency but no database. It fails with "Failed to configure a DataSource: 'url' attribute is not specified". Excluding DataSourceAutoConfiguration (and the JPA or transaction ones that follow) fixes it. Excluding is a sign to ask why the library is on the classpath at all: if you do not need it, remove it. If the excluded class is not an auto-configuration, Boot fails with an error telling you so.

An auto-configuration is not kicking in, or one you did not expect is. How do you debug it? Intermediate

What the interviewer is testing: the standard tool: the conditions evaluation report.

Start the app with --debug (or debug=true in properties). Boot prints a CONDITIONS EVALUATION REPORT with four groups: Positive matches (auto-configs that were applied and which conditions passed), Negative matches (skipped, with the exact failed condition, for example "did not find required class" or "found beans of type X"), Exclusions, and Unconditional classes. For a running app, the Actuator /actuator/conditions endpoint shows the same data as JSON, and /actuator/beans lists every bean with its origin. For one specific bean you can also set logging.level.org.springframework.boot.autoconfigure=DEBUG. Then read the negative match for your class. Typical findings: a missing property, the wrong profile, a class that is not on the classpath (a missing dependency), or another bean of the same type that made your default back off. Together with mvn dependency:tree, this solves most "why did it (not) turn on" questions.

java -jar app.jar --debug
# Negative matches:
#   RedisAutoConfiguration:
#     Did not match: @ConditionalOnClass did not find required class 'RedisOperations'
Show how you would write your own auto-configuration. Senior

What the interviewer is testing: can you build a shared library that behaves like a Boot starter, a common senior task in a company with many services.

Example: a shared audit client that every service should get. Steps: (1) a properties class bound to acme.audit.*; (2) an auto-configuration class with @AutoConfiguration, conditions, and the beans; (3) register it in the imports file; (4) optionally add the configuration processor so IDEs show hints. The key habits: guard with @ConditionalOnClass so it does not fail if an optional dependency is missing, add @ConditionalOnMissingBean on every bean so the user can override, and offer an off switch with @ConditionalOnProperty. Do not component-scan inside an auto-configuration. Use @Bean methods or explicit @Import, because scanning would pick up unrelated classes and is slow.

@ConfigurationProperties("acme.audit")
public record AuditProperties(String url, @DefaultValue("5s") Duration timeout) {}

@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@ConditionalOnProperty(prefix = "acme.audit", name = "enabled", matchIfMissing = true)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    AuditClient auditClient(AuditProperties p) {
        return new AuditClient(p.url(), p.timeout());
    }
}

How do you structure a custom starter for your company? Senior

What the interviewer is testing: packaging discipline.

The usual layout is two modules. acme-audit-spring-boot-autoconfigure holds the properties class, the auto-configuration and the imports file. Its dependencies on libraries are marked optional, so they do not leak to every user. acme-audit-spring-boot-starter is an empty module whose only job is to depend on the autoconfigure module and on the libraries the feature really needs. Small teams often merge both into one module to keep it simple, which is fine. Rules: name it acme-...-spring-boot-starter, never spring-boot-starter-...; add spring-boot-configuration-processor as an optional annotation processor so that META-INF/spring-configuration-metadata.json is generated (this gives IDE auto-complete and documentation for your properties); use sensible defaults so zero configuration works; version it with a BOM of your own; and write an ApplicationContextRunner test for each condition. A shared starter is a contract across many teams, so be careful with breaking changes, and be careful about what you put on every classpath (it is a common source of the "transitive dependency surprise" scenario below).

What does @Configuration(proxyBeanMethods = false) mean, and why do Boot's classes use it? Senior

What the interviewer is testing: understanding of "full" versus "lite" configuration.

A normal @Configuration class is wrapped in a CGLIB subclass. When one @Bean method calls another, the proxy intercepts the call and returns the existing singleton rather than running the method again. This is "full" mode. It costs a generated class per configuration and some startup time, and it needs the class to be non-final. With proxyBeanMethods = false ("lite" mode) there is no proxy: calling another @Bean method is an ordinary Java call and creates a new object each time. So lite mode is safe only when bean methods do not call each other. Pass dependencies as method parameters instead, which Spring injects. Boot's auto-configurations all use lite mode for faster startup, lower memory, and because it is friendlier to native image. For your own application configuration, the default is fine unless you care about startup time. This is the same idea as the self-invocation trap with @Transactional, covered on the Spring Framework page.

4. Externalized configuration

Where can Boot read properties from, and which source wins? Intermediate

What the interviewer is testing: the precedence order, which explains every "my property is ignored" bug.

Later (higher) sources override earlier (lower) ones. From the highest down, the ones you meet in real life are: (1) test properties (@TestPropertySource, @SpringBootTest(properties=...)); (2) command-line arguments (--server.port=9000); (3) SPRING_APPLICATION_JSON; (4) Java system properties (-Dserver.port=9000); (5) OS environment variables; (6) profile-specific files outside the jar, then inside the jar (application-prod.yml); (7) general application.yml or .properties outside the jar, then inside the jar; (8) @PropertySource annotations; (9) default properties from setDefaultProperties. Easy way to remember it: the closer the source is to the running process and the later it is decided, the higher it wins. Command line beats environment, environment beats files, an external file beats the one packed in the jar, and profile-specific beats general. So the same jar can be reconfigured by the platform with no rebuild. Within one location, .properties wins over .yml if both define the same key.

Likely follow-ups
  • How can I see where a value came from? /actuator/env/{property} shows each source that defines it and which one won (Actuator env must be exposed and secured).
YAML or .properties: any real differences? Basic

What the interviewer is testing: whether you know the sharp edges, not only the syntax.

Both bind to the same keys. YAML is hierarchical, so repeated prefixes are written once, and a single file can hold several "documents" separated by ---, each with its own profile condition. Lists are easy. The sharp edges: YAML indentation mistakes are silent (a key at the wrong level just becomes a different key); the values yes, no, on, off may be read as booleans by some parsers (quote strings); a leading zero or a colon in a value needs quotes; and you cannot use @PropertySource to load YAML. Properties files are flat and harder to read when nested, but harder to break. If both files exist, .properties wins over .yml at the same location. Pick one per project. For environment variables and the command line, dotted keys are used no matter which file format you chose.

How do profiles work? How do you activate and combine them? Basic

What the interviewer is testing: daily usage and the traps around it.

A profile is a named switch. It does two things: files named application-{profile}.yml are loaded when that profile is active and override the base file, and beans marked @Profile("name") (or @Profile("!prod")) exist only when it is active. Activate with spring.profiles.active=prod, the environment variable SPRING_PROFILES_ACTIVE=prod, or --spring.profiles.active=prod. You can have several, comma separated, and later ones win on conflict. spring.profiles.include adds profiles always on, and spring.profiles.group.prod=proddb,prodmq (Boot 2.4+) makes one name activate many. With no profile active, Boot uses the default profile. Rules of thumb: keep profiles for environment types (local, test, prod), not for every feature flag; use environment variables for per-deployment values; never put real secrets in a profile file in the repo. Setting spring.profiles.active inside a profile-specific file is not allowed, and Boot 2.4+ rejects it.

Common mistakes: a production pod that quietly runs with the default profile because the variable was misspelled, so it connects to the local H2 database or the wrong URL. Log the active profiles at startup (Boot does: "The following profiles are active") and check it.
Boot 2.4 changed how config files are loaded. What is spring.config.import and how do config locations work? Senior

What the interviewer is testing: knowledge of the "Config Data API" that replaced the bootstrap context.

Boot looks for application.yml and .properties in these places, in increasing priority: classpath root, classpath /config, the current directory, ./config/, and its immediate subdirectories. Locations can be changed with spring.config.location (this replaces the defaults, which is easy to forget) or spring.config.additional-location (this is added on top and wins). The name can change with spring.config.name. Since 2.4, a file can pull more configuration with spring.config.import: for example optional:file:/etc/app/extra.yml, configtree:/etc/secrets/ (a directory where each file is a property, the shape Kubernetes mounts secrets in), or optional:configserver:http://config:8888. The word optional: means a missing target is not an error. This replaced the old bootstrap.yml and the bootstrap context from Spring Cloud; the legacy way still works only if you add the bootstrap starter. Profile-specific activation moved to spring.config.activate.on-profile, replacing spring.profiles inside multi-document files.

spring:
  config:
    import:
      - optional:configtree:/etc/secrets/
      - optional:file:/etc/app/overrides.yml
How does @ConfigurationProperties work, and why is it better than @Value? Intermediate

What the interviewer is testing: type-safe, validated configuration.

@ConfigurationProperties(prefix = "acme.payment") on a class (or a record) binds a whole group of properties to fields. Nested objects, lists, maps, enums, Duration (5s, PT5S), DataSize (10MB) are converted for you. You register it with @EnableConfigurationProperties(Cls.class), or @ConfigurationPropertiesScan, or @Component on it. Add @Validated and Jakarta Validation annotations (@NotBlank, @Min, @Valid on nested objects) and a bad value stops the startup with a clear message: fail fast, instead of a surprise at 3 a.m. In Boot 3, a class with a single constructor is bound by constructor automatically (immutable records are great), and @DefaultValue gives defaults. @Value("${...}") is fine for one-off values, but it is stringly typed, does not group, has no validation, no IDE metadata, and spreads key names across the code. Also, SpEL in @Value is powerful but easy to misuse.

@ConfigurationProperties("acme.payment")
@Validated
public record PaymentProperties(
    @NotBlank String baseUrl,
    @DefaultValue("3s") Duration timeout,
    @Min(1) @DefaultValue("3") int retries,
    @Valid Pool pool) {
    public record Pool(@DefaultValue("20") int size) {}
}

What is relaxed binding? How do property names map to environment variables? Intermediate

What the interviewer is testing: why the same property can be written four ways, and the rule for containers.

Boot accepts several spellings of one property name when binding to @ConfigurationProperties: acme.max-retries (kebab-case, the recommended form in files), acme.maxRetries (camel case), acme.max_retries (underscore), and ACME_MAXRETRIES (upper case, for environment variables). For environment variables the rule is: upper case, replace dots and dashes with underscores. So spring.datasource.url becomes SPRING_DATASOURCE_URL and acme.max-retries becomes ACME_MAXRETRIES (dashes are removed). Lists use an index: ACME_HOSTS_0=a, ACME_HOSTS_1=b. Map keys with special characters are awkward in env vars, so use a file or SPRING_APPLICATION_JSON for those. The relaxation is for @ConfigurationProperties and the Environment lookup; @Value is stricter, so write the canonical kebab-case form there. In Kubernetes, one of the most common mistakes is setting SPRING_DATASOURCE_URL correctly in the manifest but typing a dash or dot in the variable name.

How do you pass configuration and secrets to a Boot app on Kubernetes? Intermediate

What the interviewer is testing: twelve-factor configuration in practice, and safe handling of secrets.

The image contains only defaults. The environment supplies the rest. Options: (1) Environment variables from a ConfigMap or Secret (envFrom or valueFrom). Simple, but visible in the pod spec and in the process environment, and changes need a restart. (2) Mounted files: a ConfigMap as an application.yml placed in ./config/ or mounted at a path you point to with spring.config.additional-location. A Secret mounted as a directory works well with spring.config.import=optional:configtree:/etc/secrets/: each file name becomes the key and the file content the value, and no secret appears in env vars. (3) Spring Cloud Config Server or HashiCorp Vault when you need central config, history and dynamic secrets. (4) A cloud secrets manager through a Spring Cloud integration or a sidecar. Do not bake secrets into the image or commit them in a profile file. Kubernetes Secrets are only base64, not encrypted by themselves, so enable encryption at rest and tight RBAC (role-based access control), or use an external store. A mounted file change reaches the pod after a short delay, but Boot does not re-read it unless you wire up a refresh, so plan a rolling restart for secret rotation.

What does Spring Cloud Config Server give you, and how does a client refresh? Senior

What the interviewer is testing: central configuration and its operational trade-offs.

A Config Server is a small Boot app that serves properties from a Git repository (or Vault, a database, a filesystem), organised by application name and profile. Clients ask for /{application}/{profile} at startup. Since Boot 2.4 the client enables it with spring.config.import=optional:configserver:http://host:8888. Benefits: one place for shared settings, a Git history of every change, per-environment values, encryption of values. Costs: another service that must be highly available (use optional: and sensible fail-fast settings); a startup dependency; network latency at start. To change a value without restart, annotate beans with @RefreshScope and call POST /actuator/refresh on each instance (or broadcast through Spring Cloud Bus). Beware: refresh rebuilds only the beans in refresh scope, so a connection pool or thread pool created at startup keeps the old values. Many Kubernetes teams skip Config Server and use ConfigMaps plus a rolling restart because it is simpler and visible in the cluster.

How do you find out which value an app is really using, and from where? Intermediate

What the interviewer is testing: debugging method for configuration surprises.

Use Actuator. /actuator/env lists all property sources in order, and /actuator/env/some.key shows which source supplies the winning value and which others also define it. /actuator/configprops shows each @ConfigurationProperties bean with its bound values. /actuator/conditions and /actuator/beans show what was created. Since Boot 3.0 values are masked by default (management.endpoint.env.show-values controls it), so you may see ****** and need to set it to WHEN_AUTHORIZED for an authorised user. Without Actuator, log the values at startup in a controlled way, or run with --debug and logging.level.org.springframework.boot.context.config=TRACE, which prints which config files were looked for and loaded. These endpoints expose sensitive data, so never leave them open to the internet. Section "Actuator" below covers how to secure them.

What are property placeholders and how do defaults work? Basic

What the interviewer is testing: small syntax that appears in every config file.

A value can refer to another property with ${name}, and a default with a colon: ${DB_HOST:localhost}. Placeholders work inside config files (url: jdbc:postgresql://${DB_HOST:localhost}:5432/app) and in @Value("${acme.timeout:5s}"). They are resolved against the whole Environment, so an OS variable DB_HOST feeds it. A special random.* source gives ${random.uuid} or ${random.int(1000,9000)}, useful for a random port. If the placeholder has no value and no default, startup fails with "Could not resolve placeholder", which is good: it is fail-fast. A default hides mistakes, though: ${DB_HOST:localhost} in production would silently point to localhost if the variable is missing. For required settings in production, prefer no default.

5. Embedded servers and threads

How does the embedded server work, and how do you switch from Tomcat to Jetty or Undertow? Basic

What the interviewer is testing: you understand the app and the server are one process, and how auto-configuration picks the server.

The embedded server is just a library. A ServletWebServerFactory bean (TomcatServletWebServerFactory by default) creates and starts a Tomcat object inside your JVM during the context refresh, registers Spring's DispatcherServlet in it, and your main thread keeps the process alive. This is why you deploy a jar and not a WAR. spring-boot-starter-web brings spring-boot-starter-tomcat. To switch, exclude that starter and add another one: spring-boot-starter-jetty or spring-boot-starter-undertow. Auto-configuration sees which server classes are present and picks the factory. For reactive apps the default is Netty. Boot 4 dropped Undertow support, as far as I know, so check before choosing it for new work. Reasons to switch are rare: Tomcat is the best-tested default. Pick Jetty for certain async features or existing Jetty expertise, and measure before you believe a claim that one is faster. Configuration of any server goes through server.* properties, or a WebServerFactoryCustomizer bean for things properties do not cover.

How does Tomcat handle a request, and which settings control capacity? Intermediate

What the interviewer is testing: thread-per-request model and the queues in front of it.

Tomcat (NIO connector) uses a small number of acceptor and poller threads to accept connections and detect which have data. Each ready request is given to a worker thread from a pool. That one thread runs the whole request: filters, controller, service, database call, response. While it waits on the database, that thread is blocked. Capacity is therefore bounded by the pool. Key properties and defaults: server.tomcat.threads.max = 200 workers, threads.min-spare = 10, server.tomcat.max-connections = 8192 (open sockets Tomcat will accept), server.tomcat.accept-count = 100 (the OS queue of waiting connections once max-connections is reached). Beyond all that, new connections are refused or time out. So: 200 threads and 200 slow requests means request 201 waits in line, and the whole service looks slow while CPU stays low. The fix is not simply a bigger pool, since each thread also needs a DB connection or downstream capacity. Size the pool from measured concurrency, look at the downstream limits, and set timeouts everywhere.

Which server settings do you actually tune in production? Intermediate

What the interviewer is testing: practical knobs, not a memorised list.

Timeouts first: server.tomcat.connection-timeout (how long Tomcat waits for the request to arrive, default 20s) and server.tomcat.keep-alive-timeout. Keep-alive must be longer on the app than on the load balancer in front of it, or the LB sends a request on a socket the app just closed and you see random 502 errors. Then limits: server.max-http-request-header-size (default 8KB; large cookies or JWTs can exceed it and give 400), spring.servlet.multipart.max-file-size (default 1MB) and max-request-size (default 10MB), and server.tomcat.max-swallow-size. Then efficiency: server.compression.enabled=true (off by default; often better done at the proxy), server.http2.enabled=true (needs TLS in most setups), and server.forward-headers-strategy=framework or native so the app trusts X-Forwarded-* headers behind a proxy, otherwise redirects and generated URLs use http and the internal host. TLS: since Boot 3.1 use SSL bundles (spring.ssl.bundle.*) which also support certificate reload. Access logs: server.tomcat.accesslog.enabled. Only change threads after measuring.

What are virtual threads, and how do you use them in Boot 3.2 and later? Senior

What the interviewer is testing: modern concurrency, and honest knowledge of the limits.

Virtual threads (Java 21) are very cheap threads managed by the JVM, not the OS. When code blocks on I/O (a DB call or HTTP call), the JVM parks the virtual thread and reuses the carrier OS thread for other work. So you can write simple blocking code and still serve many thousands of concurrent requests, without the pool-of-200 limit. In Boot 3.2 and later, with Java 21, you set spring.threads.virtual.enabled=true. Tomcat then handles each request on a virtual thread, and the auto-configured task executor (for @Async) and scheduler also use them. Things to know: (1) it helps I/O-bound services, not CPU-bound work; (2) the real limit moves to downstream resources: a Hikari pool of 10 now has thousands of virtual threads waiting, so protect the DB and remote services with pool sizes, timeouts and bulkheads (a limit on concurrent calls); (3) in Java 21 to 23, blocking inside a synchronized block pins the carrier thread, which can starve the app, and Java 24 removed most of that problem; (4) ThreadLocal still works but each virtual thread has its own copy, so heavy use costs memory; (5) thread dumps and metrics look different, so test and monitor. Do not pool virtual threads.

Likely follow-ups
  • Does it replace WebFlux? For many teams it removes the main reason to use reactive code, since blocking style is simpler. WebFlux still fits streaming and back-pressure use cases.
  • What property turns it on? spring.threads.virtual.enabled=true with Java 21 or newer.
Spring MVC or WebFlux in a Boot app: how do you choose? Intermediate

What the interviewer is testing: a reasoned choice, not fashion.

MVC is blocking and thread-per-request: simple to write, simple to debug (clear stack traces, thread-bound transactions, ThreadLocal security context), and works with JDBC and JPA, which are blocking. WebFlux is non-blocking and runs on a few event-loop threads (Netty by default), using Mono and Flux. It shines when you have many concurrent, slow I/O calls, streaming, server-sent events, or you need back-pressure. The price is a different programming model, harder debugging, and the rule that one blocking call on an event-loop thread hurts everyone. JPA does not fit; you would need R2DBC or a reactive driver. My default for a business service on a relational database is MVC, and with virtual threads on Java 21 it scales far better than before. I choose WebFlux for gateways, streaming APIs, or a team already fluent in reactive code. Boot can also include WebClient in an MVC app for outbound calls, without turning the app reactive.

Can you still deploy a Boot app as a WAR to an external Tomcat? Basic

What the interviewer is testing: legacy deployment knowledge.

Yes. Change the packaging to war, extend SpringBootServletInitializer in the main class (it lets the external container start your app), and mark the embedded Tomcat starter as provided so it is not in the WAR. The external container must match the Servlet version Boot expects: Boot 3 needs a Servlet 6 container with jakarta.* (Tomcat 10.1 or newer), and a Boot 2 WAR needs javax.* (Tomcat 9). You lose some conveniences: the server settings under server.* no longer apply, because the container owns them. Today a jar run in a container is the normal choice, and WAR is for organisations with a mandatory shared application server.

6. Logging, Actuator and observability

How does logging work in Boot, and how do you configure it? Basic

What the interviewer is testing: SLF4J versus the implementation, and where config lives.

Your code logs to SLF4J, which is the interface (a facade). Boot's default implementation behind it is Logback, brought in by spring-boot-starter-logging. Output defaults to the console at INFO level. Simple settings go in properties: logging.level.root=WARN, logging.level.com.acme.orders=DEBUG, logging.file.name=app.log, logging.pattern.console=..., and size-based rolling with logging.logback.rollingpolicy.*. logging.group.* lets you set one level for a named set of packages. For anything more, add logback-spring.xml, with the -spring suffix. That suffix lets Boot process it, so you can use <springProfile name="prod"> blocks and <springProperty>. A plain logback.xml is read too early for those features. To use Log4j2, exclude spring-boot-starter-logging and add spring-boot-starter-log4j2. In containers, log to stdout and let the platform collect it, rather than writing files inside the container.

Likely follow-ups
  • Change a log level without restart? POST /actuator/loggers/com.acme with {"configuredLevel":"DEBUG"}.
  • Why do I see two logging implementations warnings? Another dependency brought a second SLF4J binding. Exclude it.
How do you get JSON logs and correlation ids across services? Intermediate

What the interviewer is testing: logs that a log platform can search.

Plain text lines are hard to query. In Boot 3.4 and later you can switch on structured logging with a property: logging.structured.format.console=ecs (Elastic Common Schema), logstash or gelf. Before 3.4 teams used the Logstash Logback encoder with a logback-spring.xml. For correlation, use the MDC (mapped diagnostic context), a per-thread map that the logger prints in every line. With Micrometer Tracing on the classpath, Boot puts traceId and spanId into the MDC automatically and adds them to the default log pattern (Boot 3.2 added a correlation pattern property). Incoming traceparent headers (W3C trace context standard) are continued, and outgoing calls made through Boot's auto-configured RestTemplate, RestClient or WebClient builders add them. So one request can be followed from gateway to every service by searching one id. Three cautions: do not log secrets or personal data; MDC values do not cross threads by themselves, so for your own executors wrap tasks or use the context-propagating decorators; and with virtual threads each request has its own thread, so MDC still works.

What is Actuator, and which endpoints matter most? Basic

What the interviewer is testing: production readiness basics.

Actuator (spring-boot-starter-actuator) adds operational endpoints under /actuator. The ones you use: health (is the app and its dependencies okay), info (build and git details), metrics and prometheus (numbers for monitoring), loggers (read and change log levels), env and configprops (configuration), beans and conditions (what the context built), threaddump and heapdump (diagnostics), httpexchanges (recent requests, needs a repository bean), scheduledtasks, mappings, and startup. Since Boot 2, over HTTP only health is exposed by default. You choose others with management.endpoints.web.exposure.include=health,info,prometheus. Exposed and enabled are different: an endpoint can exist but not be exposed. Because several of these endpoints leak sensitive data, treat exposure as a security decision.

How do you secure Actuator endpoints? Intermediate

What the interviewer is testing: the classic security mistake: leaving env or heapdump open.

Layers, from simplest. (1) Expose the minimum: only health, info and your metrics endpoint. Never expose env, heapdump, threaddump, configprops to the public. A heap dump contains passwords and tokens held in memory. (2) Separate port: management.server.port=9090, reachable only inside the cluster or by the monitoring system, with the main port public. Kubernetes probes and Prometheus scrape the internal port. (3) Spring Security rules for Actuator, using EndpointRequest: permit health to the platform, require a role for the rest. (4) Mask values: Boot 3 hides values in env and configprops by default (show-values). (5) management.endpoint.health.show-details=when-authorized so dependency details are not shown to anonymous callers. Also remember that adding Spring Security to the classpath secures all endpoints by default, which is why probes suddenly return 401 after someone adds the security starter.

@Bean
SecurityFilterChain actuator(HttpSecurity http) throws Exception {
    http.securityMatcher(EndpointRequest.toAnyEndpoint())
        .authorizeHttpRequests(a -> a
            .requestMatchers(EndpointRequest.to("health", "info")).permitAll()
            .anyRequest().hasRole("OPS"))
        .httpBasic(Customizer.withDefaults());
    return http.build();
}
How does the health endpoint work, and how do you write a custom health indicator? Intermediate

What the interviewer is testing: aggregation, and what a good health check should and should not do.

The health endpoint asks every HealthIndicator bean for a status (UP, DOWN, OUT_OF_SERVICE, UNKNOWN) and combines them: the worst status wins, and DOWN returns HTTP 503. Boot auto-registers indicators for what it finds: database, disk space, Redis, RabbitMQ, Kafka and others. A custom one is a bean implementing HealthIndicator (or extending AbstractHealthIndicator). The name in the output is the class name without "HealthIndicator". Keep the check cheap and fast, with its own short timeout, because the probe calls it often. A health check that runs a heavy query, or calls a slow third party, can itself bring the service down or make it flap. And decide carefully what counts for liveness and readiness (next question). You can turn off an indicator with management.health.redis.enabled=false.

@Component
class PaymentGatewayHealth implements HealthIndicator {
    private final PaymentClient client;
    PaymentGatewayHealth(PaymentClient c) { this.client = c; }
    @Override public Health health() {
        try {
            client.ping(Duration.ofSeconds(1));
            return Health.up().withDetail("gateway", "reachable").build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}
What are liveness and readiness probes in Boot, and how do they map to Kubernetes? Senior

What the interviewer is testing: the difference that prevents restart storms.

Liveness answers "is the process broken beyond repair?". If it fails, Kubernetes restarts the container. Readiness answers "can I take traffic right now?". If it fails, Kubernetes only removes the pod from the Service endpoints; it is not restarted. Boot supports both through ApplicationAvailability: LivenessState (CORRECT or BROKEN) and ReadinessState (ACCEPTING_TRAFFIC or REFUSING_TRAFFIC). Endpoints: /actuator/health/liveness and /actuator/health/readiness. They are on automatically when Boot detects Kubernetes, or set management.endpoint.health.probes.enabled=true. Readiness turns to refusing at the start of graceful shutdown. The key rule: liveness must not depend on external systems. If the database is down and your liveness check includes it, Kubernetes restarts every pod, which cannot fix the database and makes the outage worse. Put dependencies in readiness (and only those you cannot serve without), or leave them to metrics and alerts. Add a startup probe for slow starts, so liveness does not kill a pod that is still starting. You can change what each group contains with management.endpoint.health.group.readiness.include=readinessState,db.

What is Micrometer, and how do metrics reach Prometheus? Intermediate

What the interviewer is testing: metrics model and how it is wired.

Micrometer is a vendor-neutral metrics facade, like SLF4J but for metrics. Your code records to a MeterRegistry, and a registry implementation sends it to a backend: Prometheus, Datadog, CloudWatch, and so on. Boot auto-configures the registry for whatever backend jar is on the classpath, and registers many built-in metrics: JVM memory and GC, threads, CPU, http.server.requests (latency and count by URI, method, status), hikaricp.connections.*, Tomcat sessions, Kafka consumer lag, cache statistics. For Prometheus, add micrometer-registry-prometheus and expose /actuator/prometheus. Prometheus then scrapes that URL on a schedule (pull model). Meter types: Counter (only goes up), Gauge (current value, like queue size), Timer (count and duration), DistributionSummary (sizes), and histograms or percentiles for latency. Add common tags with management.metrics.tags.application=orders so dashboards can filter by service.

Likely follow-ups
  • Why alert on percentiles and not the average? Averages hide slow tails. Use histograms and compute p95 or p99 in the backend.
How do you add a custom business metric, and what is "cardinality"? Intermediate

What the interviewer is testing: practical use and the cardinality trap.

Inject MeterRegistry and create meters, with tags to slice the data. A counter for orders by payment type, a timer around a call. The annotation @Timed works only if you register a TimedAspect bean; @Observed (Boot 3) creates both a metric and a trace span, and needs an ObservedAspect. Cardinality is the number of different tag value combinations. Each combination is a separate time series stored by the monitoring system. If you tag with userId, orderId or a raw URL with ids in it, you create millions of series, the metrics backend runs out of memory or the bill explodes. Tags must come from a small, fixed set: payment type, status, region. Boot's HTTP metrics use the URI template (/orders/{id}), not the real path, for this reason. Put high-cardinality data in logs or traces instead.

private final Counter paid;
OrderService(MeterRegistry reg) {
    this.paid = Counter.builder("orders.paid")
        .tag("method", "card").register(reg);
}
void pay() { /* ... */ paid.increment(); }
How does distributed tracing work in Boot 3 (Micrometer Tracing)? Senior

What the interviewer is testing: knowing that Sleuth is gone and what replaced it.

Spring Cloud Sleuth does not exist for Boot 3. Boot 3 uses the Micrometer Observation API: instrumented code (HTTP server, RestClient, JDBC, Kafka, your @Observed methods) creates an "observation", and handlers turn it into a metric, a trace span, or a log entry. For tracing you add a bridge: micrometer-tracing-bridge-otel (OpenTelemetry) or -brave (Zipkin Brave), plus an exporter such as opentelemetry-exporter-otlp or Zipkin. A trace is the whole request journey, made of spans (one step each), tied by a trace id passed in the traceparent header. Boot auto-instruments only clients built from Boot's builders (RestTemplateBuilder, RestClient.Builder, WebClient.Builder): if you create new RestTemplate() yourself, propagation silently stops. Default sampling is 10 percent (management.tracing.sampling.probability=0.1), so for a dev check set it to 1.0. Messaging needs spring.kafka.template.observation-enabled=true (and the listener one) in many versions.

A pod is slow or leaking memory. Which Actuator and JVM tools do you use first? Senior

What the interviewer is testing: a diagnostic routine.

Look at metrics first: jvm.memory.used by area, GC pause time, jvm.threads.live, hikaricp.connections.pending, and http.server.requests p99. Then get evidence. /actuator/threaddump (or jcmd PID Thread.print) shows what threads are doing: many threads waiting on the same lock or on a socket tells you the bottleneck. Take two or three dumps a few seconds apart. For memory, /actuator/heapdump (or jcmd PID GC.heap_dump) and open it in a heap analyser to see what holds the memory, such as an unbounded cache, a static map, or a ThreadLocal. Start the JVM with -XX:+HeapDumpOnOutOfMemoryError and a writable path so you get a dump at the moment of failure. Remember: heap dumps are large, pause the app, and contain secrets. In locked-down production, you often do this with a temporary debug container or JFR (Java Flight Recorder) rather than an open endpoint.

What does Spring Boot DevTools do, and is it safe in production? Basic

What the interviewer is testing: developer tooling and its safety limits.

DevTools speeds up local development. Automatic restart: it watches the classpath and, when a class changes, restarts the app using two classloaders: one for unchanging library jars and one for your code, so only your code is reloaded, which is much faster than a cold start. LiveReload: a browser extension refreshes the page. Development property defaults: it switches template caching off and enables more web logging. It also supports remote restart over HTTP (rarely used and risky). It is automatically disabled when the app runs from a fully packaged jar (java -jar), and the repackaged jar excludes it by default, so it should not reach production. Mark it optional or developmentOnly in the build. Classloader tricks sometimes cause odd ClassCastExceptions on the same class loaded twice; if so, exclude that library from the restart classloader with restart.include or exclude settings, or disable restart. In IDEs, the restart triggers after a build, not on save.

7. Testing Boot applications

What does @SpringBootTest do, and what are its web environment modes? Basic

What the interviewer is testing: the full-context test, and its cost.

@SpringBootTest starts the complete application context, the same configuration as the real app, found by searching up from the test class for the @SpringBootConfiguration. It is an integration test: slow, but the closest to production. The webEnvironment choices: MOCK (default) uses a mock servlet environment, no real port, and you use MockMvc. RANDOM_PORT starts a real embedded server on a random free port, and you call it with TestRestTemplate, WebTestClient or RestTestClient (Spring 7). DEFINED_PORT uses the configured port (can clash). NONE loads the context with no web at all. Use @LocalServerPort to get the random port. Use properties = {...} or @TestPropertySource to override settings, and @ActiveProfiles("test") to pick a profile. Use it for a small number of end-to-end checks and use the faster slices (next) for most tests.

What are test slices? Name the main ones. Intermediate

What the interviewer is testing: fast, focused tests, and knowing what each slice loads.

A slice loads only the part of the context for one layer, so the test starts in a second or two. @WebMvcTest(OrderController.class) loads controllers, @ControllerAdvice, converters, filters, and MockMvc, but not services or repositories: you provide those as mocks. @DataJpaTest loads entities, repositories, Hibernate and a transaction manager, rolls back after each test, and by default swaps your database for an embedded one. @JsonTest checks JSON serialisation. @DataJdbcTest, @JdbcTest, @DataMongoTest, @DataRedisTest, @RestClientTest and @WebFluxTest do the same for other layers. Slices use special test auto-configuration lists, so only matching auto-configurations run. Components such as @Service are not scanned in a slice. A trap: if your main class has extra annotations (@EnableScheduling, @EnableJpaRepositories), a slice picks them up too and can break; keep such annotations on separate configuration classes.

How do you test a controller with @WebMvcTest and MockMvc? Intermediate

What the interviewer is testing: you can test the HTTP contract without starting a server.

@WebMvcTest builds the MVC layer and gives you an auto-wired MockMvc, which sends fake requests straight through the DispatcherServlet (no network). You mock the service with @MockitoBean (Boot 3.4+ with Spring 6.2) or @MockBean (older). You then check status, headers, JSON body, validation errors, and your error handler. This tests routing, request binding, validation annotations, JSON mapping, exception handling and (if you include it) security rules. It does not test the service or database. If Spring Security is on the classpath, requests are secured, so add spring-security-test and use @WithMockUser or .with(csrf()), or you will see 401 and 403 and wonder why.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test void returns404WhenMissing() throws Exception {
        when(service.find(7L)).thenThrow(new OrderNotFound(7L));
        mvc.perform(get("/orders/7"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.title").value("Order not found"));
    }
}
What does @DataJpaTest do, and why should you not rely on H2 alone? Intermediate

What the interviewer is testing: repository tests that mean something.

@DataJpaTest starts only the JPA parts, runs each test in a transaction that is rolled back at the end, and by default replaces your DataSource with an embedded database. You get a TestEntityManager to set up data. This is a good, fast way to test derived queries, @Query and mappings. The trouble with H2 (the embedded database) is that it is not your production database. SQL dialects, JSON columns, sequences, locking, collation and functions differ, so a test can pass on H2 and fail on PostgreSQL. Best practice is to use a real PostgreSQL (or whatever you run) in a Testcontainers container, and tell Boot not to replace it with @AutoConfigureTestDatabase(replace = NONE). Also remember that the rollback means the SQL may never flush: call entityManager.flush() before asserting on constraint violations or generated SQL.

@MockBean versus @MockitoBean (and @SpyBean): what changed? Intermediate

What the interviewer is testing: up-to-date test API knowledge.

@MockBean and @SpyBean are Boot annotations that replace a bean in the context with a Mockito mock or spy. Spring Framework 6.2 added the same capability in the core framework as @MockitoBean and @MockitoSpyBean (also @TestBean for a bean made by a factory method). Boot 3.4 deprecated the Boot ones in favour of them, and Boot 4 removes them, as far as I know. Differences worth knowing: the new ones are part of the Spring test context framework, they work on fields in test classes and also on a class level for sharing, and they do not create a bean if none exists unless you ask. Mocks are reset after each test by default. Be aware that every different combination of mocked beans creates a different context, which cannot be shared with other tests, so many different mock sets mean many slow context startups. Prefer constructor injection and plain unit tests where possible, and share one mock configuration through a base class or a @TestConfiguration.

How do you use Testcontainers in a Boot test? What is @ServiceConnection? Senior

What the interviewer is testing: integration tests against real dependencies.

Testcontainers starts real Docker containers (PostgreSQL, Kafka, Redis) for a test. Before Boot 3.1 you had to start the container and push its random URL into Spring with @DynamicPropertySource. Boot 3.1 added @ServiceConnection: put it on a container field or a @Bean and Boot reads the container's host, port and credentials and configures the matching auto-configuration (datasource, Kafka, Redis) by itself. Mark the container static so it is reused across the tests in a class, and use singleton containers or the reuse option to avoid starting one per class. Boot 3.1 also lets you run the same containers during development with SpringApplication.from(App::main).with(TestcontainersConfig.class).run(args). Requirements: Docker available in CI. Tests become slower but far more honest. Keep their number small and make the unit tests cover the logic.

@SpringBootTest
@Testcontainers
class RepoIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");

    @Autowired OrderRepository repo;
    @Test void saves() { /* real PostgreSQL */ }
}
Why does our Boot test suite take 20 minutes, and how do you speed it up? Senior

What the interviewer is testing: understanding of the test context cache.

Spring caches the ApplicationContext between test classes, keyed by the full configuration: configuration classes, active profiles, properties, mocked beans, @TestPropertySource, and more. If two test classes have exactly the same key, the second reuses the first context. Any difference creates a new context, which takes many seconds. Common causes of cache misses: each class has a different @MockBean set, different @ActiveProfiles, per-class properties = ..., and @DirtiesContext sprinkled around "to be safe". Fixes: put mocks and properties into a few shared base classes; avoid @DirtiesContext unless the test really changes global state; use slices for most tests; use constructor-injected plain unit tests for logic; make Testcontainers singleton. Also check log output for the number of times the banner prints during a build: each banner is a new context. Run tests in parallel at the class level only if the contexts and databases are isolated.

How do you override a bean or property only for tests? Intermediate

What the interviewer is testing: test configuration hygiene.

For properties: @SpringBootTest(properties = "acme.payment.base-url=http://localhost:9999"), @TestPropertySource, or a file application-test.yml with @ActiveProfiles("test"). These sit at the top of the precedence order. For beans: a nested static class or a separate class annotated @TestConfiguration declares replacement beans. Unlike a normal @Configuration, it is not found by component scanning, so you import it with @Import on the test (a nested one is picked up automatically). To replace an existing bean of the same name you may need spring.main.allow-bean-definition-overriding=true, or better, use @MockitoBean or @Primary on the test bean. For external services, use a fake server (WireMock, MockWebServer) and point the base URL at it, so the real HTTP client and JSON mapping are exercised.

8. Data access configuration

How does Boot configure a DataSource? What if there is no URL? Basic

What the interviewer is testing: understanding of the defaults and the famous "Failed to configure a DataSource" error.

DataSourceAutoConfiguration runs when a DataSource class and a JDBC driver are on the classpath and you have not defined your own DataSource bean. It reads spring.datasource.url, username, password, and picks the connection pool by what it finds: HikariCP first (it comes with the JDBC and JPA starters), then Tomcat JDBC, then Commons DBCP2. The driver class is guessed from the URL. If no URL is set and an embedded database (H2, HSQLDB, Derby) is on the classpath, Boot starts an in-memory one, which is handy in tests but a trap if it happens in production by accident. If no URL is set and no embedded database exists, startup fails with "Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured". That usually means a missing property (wrong profile or env variable name) or a JDBC library you do not use. Pool-specific settings live under spring.datasource.hikari.*.

spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:5432/orders
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 15
How do you size and tune HikariCP? What are the key settings? Senior

What the interviewer is testing: the connection pool is the usual real bottleneck in Boot services.

Hikari's defaults: maximum-pool-size 10, minimum-idle equal to the maximum (a fixed-size pool, which Hikari recommends), connection-timeout 30 seconds (how long a caller waits for a connection), idle-timeout 10 minutes, max-lifetime 30 minutes. Set max-lifetime a few minutes shorter than any timeout in the database or network device (a firewall or proxy that closes idle connections), or you will get "connection reset" errors from dead connections. Pool size: smaller than people think. A database serves a limited number of queries at once; a pool of 10 to 20 per instance is often right, and more connections can make everything slower. A rough rule from Hikari's own guide is (core count x 2) plus disk spindles, applied to the database server, divided across all app instances. Remember the total: 20 pods x 20 connections = 400 on the database, which may exceed its limit. Lower connection-timeout to something like 2 to 5 seconds so an overloaded service fails fast. Turn on leak-detection-threshold (for example 20000 ms) to log a stack trace for connections held too long. Watch hikaricp.connections.active, .pending and .timeout metrics.

Likely follow-ups
  • Should I just raise the pool size? Only after you prove connections are short-lived and the database has headroom. Otherwise find the slow query or the leak.
Which JPA and Hibernate properties matter in a Boot app? Intermediate

What the interviewer is testing: settings that bite in production.

spring.jpa.hibernate.ddl-auto: values are none, validate, update, create, create-drop. The default is create-drop for an embedded database and none otherwise. Use validate or none in production, with a migration tool (Flyway or Liquibase) owning the schema; update can silently make bad changes and never drops anything. spring.jpa.open-in-view (OSIV) is true by default and Boot logs a warning about it: it keeps a database connection (the persistence context) open for the whole HTTP request, including the view rendering and slow remote calls, which is a common cause of pool exhaustion. Set it to false and load what you need inside the service transaction. spring.jpa.show-sql prints SQL to stdout (use the logger org.hibernate.SQL at DEBUG instead). Batching: spring.jpa.properties.hibernate.jdbc.batch_size=50, plus order_inserts and order_updates; note that IDENTITY id generation turns off insert batching. hibernate.default_batch_fetch_size helps with N+1 loads. Set spring.jpa.properties.hibernate.jdbc.time_zone=UTC to avoid time-zone surprises. Deeper JPA topics are on the Spring Framework page and the data pages of this book.

How do Flyway and Liquibase work with Boot? What goes wrong with them? Intermediate

What the interviewer is testing: schema change discipline.

Add the Flyway (or Liquibase) dependency and Boot runs the migrations automatically at startup, before the JPA EntityManagerFactory is created, so Hibernate sees the up-to-date schema. Flyway reads files from classpath:db/migration named V1__create_orders.sql, V2__add_index.sql (version, two underscores, description). It records each applied file with a checksum in the table flyway_schema_history. Liquibase reads a changelog (default db/changelog/db.changelog-master.yaml) and records changesets in DATABASECHANGELOG. Rules: never edit an applied migration (the checksum check fails startup); only add new ones; keep each migration small and backward compatible (add a nullable column first, backfill, then add the constraint in a later release) so old and new app versions can run at the same time during a rolling deploy. Both tools take a lock so only one instance migrates at once, but a long migration blocks startup and probes may kill the pod; consider running migrations as a separate job before the rollout. Newer Flyway versions (10 and later) need a database-specific module, for example flyway-database-postgresql, which is a common surprise after an upgrade. For an existing database use baseline-on-migrate.

How do you use two databases in one Boot app? Senior

What the interviewer is testing: what auto-configuration does when you take over.

Once you declare your own DataSource bean, Boot's one backs off (@ConditionalOnMissingBean). With two, you must tell Spring which one is the default: mark one @Primary. Create a DataSourceProperties bean per database bound with @ConfigurationProperties("app.db.orders"), build each pool from it, and for JPA create a LocalContainerEntityManagerFactoryBean and a JpaTransactionManager for each, pointing to its own entity package. Each repository package gets its own @EnableJpaRepositories(entityManagerFactoryRef=..., transactionManagerRef=...). In services, name the transaction manager in @Transactional("ordersTx"). The big warning: a transaction is not shared across two databases. A @Transactional block commits one of them, and a failure on the second leaves them inconsistent. If you need both to agree, use a saga or the outbox pattern, not a distributed (XA) transaction unless there is no alternative. Often a better design is two services, each owning one database.

What are JdbcClient and the other newer data features in Boot 3.2+? Intermediate

What the interviewer is testing: awareness of recent APIs.

JdbcClient (Spring 6.1 and Boot 3.2) is a fluent wrapper over JdbcTemplate and NamedParameterJdbcTemplate: jdbc.sql("select * from orders where id = :id").param("id", 7).query(Order.class).single(). It is easier to read than the older template and maps rows to records. Boot 3.2 also added the RestClient (a modern synchronous HTTP client with a fluent API, replacing most RestTemplate use), and virtual threads support. Boot 3.1 added @ServiceConnection and Docker Compose support: put a compose.yaml in the project and, in development, Boot starts the services and wires the connection details for you. Boot 3.3 added Class Data Sharing helpers; Boot 3.4 added structured logging and improved @MockitoBean support. I would mention one or two of these, show I know where they help, and be clear which Boot version brought them.

9. Building REST APIs

How do you validate request input in Boot, and what exceptions can you get? Basic

What the interviewer is testing: the standard approach and the often-missed starter.

Add spring-boot-starter-validation. Since Boot 2.3 the web starter no longer includes it. Put Jakarta Validation annotations on the request class (@NotBlank, @Size, @Email, @Min, @Valid on nested objects) and add @Valid before the @RequestBody parameter. If validation fails Spring throws MethodArgumentNotValidException for a body, HandlerMethodValidationException in Spring 6.1 and later, or ConstraintViolationException when you put @Validated on the class and validate a path variable or request parameter. By default these become a plain 400 response. You make the response useful with a @RestControllerAdvice (next question). Validation checks the shape (not blank, in range). Business rules ("stock available", "email unique") belong in the service, with their own exceptions, since they need data and can race with other requests: also enforce uniqueness with a database constraint.

public record CreateOrder(@NotBlank String sku, @Min(1) int qty) {}

@PostMapping("/orders")
ResponseEntity<Order> create(@Valid @RequestBody CreateOrder req) { ... }
How do you build consistent error responses? What is ProblemDetail? Intermediate

What the interviewer is testing: API design and the Spring 6 standard error type.

ProblemDetail (Spring 6, so Boot 3) is a built-in class for the standard error format of RFC 7807 (updated by RFC 9457), media type application/problem+json, with fields type, title, status, detail, instance, and room for extra properties. To use it everywhere, write a @RestControllerAdvice that extends ResponseEntityExceptionHandler: it already turns standard Spring MVC exceptions (bad body, missing parameter, unsupported media type) into ProblemDetail. Add @ExceptionHandler methods for your own exceptions. Or set spring.mvc.problemdetails.enabled=true to get this for the built-in exceptions with no code. Without any of this, Boot's BasicErrorController returns its older default JSON (timestamp, status, error, path). Since Boot 2.3 that default hides the message and the stack trace (server.error.include-message=never), which is correct for security: never return stack traces to clients, but do log them with a correlation id.

@RestControllerAdvice
class ApiErrors extends ResponseEntityExceptionHandler {
    @ExceptionHandler(OrderNotFound.class)
    ProblemDetail notFound(OrderNotFound e) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        p.setTitle("Order not found");
        p.setProperty("orderId", e.id());
        return p;
    }
}
How is Jackson configured in Boot, and what are the usual JSON problems? Intermediate

What the interviewer is testing: where the defaults come from and how not to break them.

Boot builds one ObjectMapper using Jackson2ObjectMapperBuilder, and registers modules found on the classpath (Java time, parameter names, JDK8 types). It also changes some Jackson defaults: FAIL_ON_UNKNOWN_PROPERTIES is off (extra JSON fields are ignored) and WRITE_DATES_AS_TIMESTAMPS is off (dates are ISO strings like 2025-03-01T10:15:30Z, not numbers). You tune it with spring.jackson.* properties (default-property-inclusion=non_null, serialization.indent-output, time-zone) or a customizer bean. The pitfall is defining your own ObjectMapper bean with new ObjectMapper(): it replaces Boot's, losing those defaults and the modules. Other usual problems: LocalDate fails without the Java time module (Boot adds it); infinite recursion on bidirectional JPA entities (return DTOs, never entities); lazy-loading proxies serialised by mistake; and money as double instead of BigDecimal. In Boot 4 with Jackson 3 the package and some defaults change, so check the migration guide.

How do you document a Boot REST API with OpenAPI? Intermediate

What the interviewer is testing: the library choice that changed with Boot 3, and design-first versus code-first.

Spring itself has no OpenAPI generator. The common library is springdoc-openapi. For Boot 3 use springdoc-openapi-starter-webmvc-ui version 2.x (for WebFlux the webflux variant). It reads your controllers and models at runtime, exposes the spec at /v3/api-docs and Swagger UI at /swagger-ui.html, and you enrich it with annotations such as @Operation, @Schema and @ApiResponse. The old Springfox library does not work on Boot 3, and springdoc 1.x is for Boot 2. Two approaches: code-first (generate the spec from the code, simple, but the spec drifts with every code change and is easy to break by accident) and contract-first (write the OpenAPI file first, generate interfaces and models with the OpenAPI Generator, and implement them: better for public APIs and for teams who need to agree before coding). Protect the docs endpoints in production, or switch them off with springdoc.api-docs.enabled=false.

How do you call another service from Boot? What are the traps with timeouts? Intermediate

What the interviewer is testing: outbound calls are the main cause of cascading failures.

Options: RestTemplate (older, in maintenance mode), RestClient (Boot 3.2, synchronous, fluent, the new default for blocking code), WebClient (reactive, also usable from MVC), and declarative HTTP interface clients (@HttpExchange interfaces, Spring 6) which generate the client from an interface. Inject Boot's RestClient.Builder or RestTemplateBuilder instead of calling new, so you inherit message converters, observability and tracing. The big trap: no timeout by default in many underlying clients. A call to a slow service then holds your worker thread forever, threads fill up, and your service is down too. Always set connect and read timeouts (through the request factory settings, or spring.http.client.* properties in newer Boot versions), add retries only for safe (idempotent) calls with backoff, and add a circuit breaker (Resilience4j) so a failing dependency is skipped quickly. Return a fallback or fail fast with a clear error.

@Bean
RestClient paymentClient(RestClient.Builder b, PaymentProperties p) {
    var factory = ClientHttpRequestFactories.get(
        ClientHttpRequestFactorySettings.DEFAULTS
            .withConnectTimeout(Duration.ofSeconds(1))
            .withReadTimeout(p.timeout()));
    return b.baseUrl(p.baseUrl()).requestFactory(factory).build();
}
What is BasicErrorController, and what does /error do? Intermediate

What the interviewer is testing: what happens to errors that never reach your handlers.

Some errors happen outside Spring MVC's handler chain: a 404 for an unknown path, an exception in a filter, a servlet container error. The container forwards those to the path /error, and Boot's BasicErrorController handles it. For a browser (Accept: text/html) it renders the "Whitelabel Error Page" or your error/404.html template; for other clients it returns JSON with timestamp, status, error, path. The contents are built by an ErrorAttributes bean, so you can customise them. Exceptions thrown from a controller are first offered to your @ExceptionHandler and @ControllerAdvice, and only if unhandled do they reach /error. A subtle point: exceptions in a servlet Filter do not pass through @ControllerAdvice, so they come out as the generic error response, which is why security filter errors look different from your API errors. If Spring Security is present, /error itself must be permitted, otherwise every error shows as 401.

10. Messaging, caching and scheduling

How does Boot support Kafka? What do you configure? Intermediate

What the interviewer is testing: the basic wiring and the common reliability settings.

With spring-kafka on the classpath, Boot auto-configures a KafkaTemplate for sending, a producer factory, a consumer factory and a listener container factory for @KafkaListener methods. Settings are under spring.kafka.*: bootstrap-servers, consumer.group-id, consumer.auto-offset-reset, key and value (de)serializers, producer.acks, producer.properties.enable.idempotence. A listener is just an annotated method. For reliability: choose the ack mode (spring.kafka.listener.ack-mode), do not commit before processing, handle failures with a DefaultErrorHandler that retries with backoff and then sends the record to a dead letter topic (DeadLetterPublishingRecoverer), make processing idempotent (a message can arrive twice), and mind max.poll.interval.ms: a listener that works too long causes a consumer group rebalance. Deserialisation errors need ErrorHandlingDeserializer, otherwise one bad message blocks the partition forever. The messaging design questions themselves (partitions, ordering, exactly-once) are on the Kafka page of this book.

@KafkaListener(topics = "orders", groupId = "billing")
void on(OrderCreated event) { billing.handle(event); }

kafkaTemplate.send("orders", order.id(), event);
And RabbitMQ with Boot: what is auto-configured, and what are the common problems? Intermediate

What the interviewer is testing: the AMQP basics in a Boot setting.

With spring-boot-starter-amqp, Boot creates the connection factory, a RabbitTemplate to send, a RabbitAdmin to declare queues, exchanges and bindings you define as beans, and a listener container for @RabbitListener. Properties: spring.rabbitmq.host, username, password, listener.simple.acknowledge-mode, listener.simple.prefetch, and listener.simple.retry.*. Typical problems: (1) by default a listener that throws is requeued forever, so one poison message loops at full speed. Configure a dead-letter exchange and limit retries, or set default-requeue-rejected=false. (2) With the default Java serialisation (or a mismatched JSON converter), producer and consumer cannot read each other's messages; set a Jackson2JsonMessageConverter bean. (3) Publisher confirms and returns are needed if you must know a message reached the broker. (4) Declare queues once, in code, so the app creates what it needs on startup. Both brokers need idempotent consumers, because at-least-once delivery means duplicates happen.

How does caching work in Boot? Which providers? What can go wrong? Intermediate

What the interviewer is testing: the abstraction, and its stale-data and proxy traps.

Add spring-boot-starter-cache and put @EnableCaching on a configuration class. Then @Cacheable("products") on a method stores the result by the method arguments, @CacheEvict removes entries, and @CachePut always runs the method and updates the cache. Boot picks a CacheManager by what is on the classpath: Caffeine (fast, in-process, with size and expiry), Redis, Hazelcast, Ehcache, or a simple ConcurrentHashMap fallback with no expiry. Choose with spring.cache.type and configure Caffeine using spring.cache.caffeine.spec=maximumSize=10000,expireAfterWrite=10m. Things that go wrong: it is proxy-based, so a call from another method in the same class is not cached (the self-invocation problem, same as @Transactional); the default key is built from all arguments, so large objects need a deliberate key; null results may be cached; no expiry means stale data and memory growth; and with several instances, an in-process cache is different on each pod, so use Redis if they must agree. For concurrent misses set sync = true to avoid a stampede. Detailed cache design is on the Redis page.

How do @Scheduled tasks work, and what are the traps in a multi-instance deployment? Intermediate

What the interviewer is testing: a classic production bug: every pod runs the job.

Add @EnableScheduling and annotate a no-argument method with @Scheduled(fixedRate = ...), fixedDelay (wait after the previous run ends), or cron = "0 0 2 * * *" (Spring cron has six fields, with seconds first). Boot configures a task scheduler with a pool of one thread by default (spring.task.scheduling.pool.size=1), so two jobs share one thread and a long job delays the others. Raise the pool size for several jobs. Exceptions are logged and the schedule continues. The big trap: in Kubernetes with three replicas, the job runs three times. Solutions: a distributed lock (ShedLock with a table or Redis), a Kubernetes CronJob for work that should run once, or a leader election. Also make the job idempotent and set time zones explicitly (zone = "UTC"). Do not do hours of work in a scheduled method that holds a request-like resource; hand off to a queue. For virtual threads (Boot 3.2+) the scheduler can use them when enabled.

What does @Async do in Boot, and what executor does it use? Intermediate

What the interviewer is testing: hidden thread pools and lost context.

With @EnableAsync, a method marked @Async runs on another thread and returns at once (return void or CompletableFuture). Boot auto-configures a ThreadPoolTaskExecutor named applicationTaskExecutor, with settings under spring.task.execution.*: pool.core-size (8 by default), pool.max-size (effectively unbounded unless you set a queue limit), and pool.queue-capacity (also effectively unbounded by default). That default can hide trouble: an unbounded queue grows without limit when work arrives faster than it finishes, until memory runs out. Set explicit bounds and a rejection policy. Because it is proxy-based, self-calls do not run async, and the caller's SecurityContext, MDC and transaction do not carry over to the new thread unless you add a task decorator or use the delegating security executor. Exceptions in a void async method are lost unless you register an AsyncUncaughtExceptionHandler. With Boot 3.2 and virtual threads on, it uses a virtual-thread-per-task executor instead.

11. Packaging, containers, native image and shutdown

What is a "fat jar" (executable jar)? How is it different from a normal jar? Basic

What the interviewer is testing: how java -jar works with nested jars.

The Boot Maven or Gradle plugin repackages your build into one executable jar. Inside BOOT-INF/classes are your classes and BOOT-INF/lib holds all dependency jars, as nested jars. A normal JVM cannot load classes from a jar inside a jar, so Boot adds its own launcher (org.springframework.boot.loader.launch.JarLauncher; in Boot 3.2 and earlier, loader.JarLauncher), which is the Main-Class. It creates a special classloader that reads nested jars, then calls your real main class (named in Start-Class). So java -jar app.jar just works with no classpath to manage. Benefits: one artifact, no server install. Drawbacks: the whole jar is rebuilt on each change (large layer for Docker, see layered jars), and startup unpacks nothing but does scan jar entries. The original plain jar can be kept with the .original suffix or a classifier.

How do you build a good Docker image for a Boot app? Intermediate

What the interviewer is testing: image size, build speed, and safe defaults.

Three ways. (1) Buildpacks: ./mvnw spring-boot:build-image (or bootBuildImage) builds an OCI image with Paketo buildpacks, no Dockerfile, with sensible layers, a non-root user, a memory calculator for the JVM, and regular base image patches. (2) Layered jars with your own Dockerfile. Since Boot 2.4 the jar is split into layers in order of change frequency: dependencies, spring-boot-loader, snapshot-dependencies, application. Dependencies rarely change, so Docker reuses that layer and a code change pushes only a few KB. Extract with java -Djarmode=tools -jar app.jar extract --layers (Boot 3.3 and later; older: -Djarmode=layertools ... extract). (3) A simple COPY app.jar: works but every build uploads the whole jar. Good habits: use a small JRE base image, a multi-stage build, run as non-root, do not put secrets in layers, and pass settings through environment variables. Set JVM memory flags for containers (next question).

FROM eclipse-temurin:21-jre AS runtime
WORKDIR /app
COPY --from=build /build/dependencies/ ./
COPY --from=build /build/spring-boot-loader/ ./
COPY --from=build /build/snapshot-dependencies/ ./
COPY --from=build /build/application/ ./
USER 10001
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","org.springframework.boot.loader.launch.JarLauncher"]
How do you set JVM memory and CPU for a Boot app in a container? Senior

What the interviewer is testing: the main cause of OOMKilled pods.

Modern JVMs (Java 11 and later, and 8u191 and later) read the container limit, not the host memory. By default the max heap is only a quarter of the container memory, which wastes memory on small pods. A common setting is -XX:MaxRAMPercentage=70 to 75. Do not set heap equal to the limit: the JVM also uses non-heap memory: metaspace (class data), thread stacks (about 1 MB each by default, so 200 threads is 200 MB), direct buffers (Netty and NIO), code cache and GC structures. If heap plus non-heap exceeds the limit, the kernel kills the container with OOMKilled (exit code 137), and you get no Java OutOfMemoryError. This looks like a "random restart" with nothing in the logs. Paketo buildpacks calculate these settings for you. CPU: the JVM sizes its GC and thread pools from the visible CPU count. With a limit under 2 CPUs it may pick the serial GC and fewer compiler threads. Also, startup is CPU hungry (class loading and JIT compile), and a low CPU limit makes it several times slower, so give extra CPU while starting, or avoid tight CPU limits and rely on requests. Watch for CPU throttling in metrics. Always enable -XX:+HeapDumpOnOutOfMemoryError to a mounted volume.

What is a GraalVM native image, how does Boot support it, and what are the trade-offs? Senior

What the interviewer is testing: realistic judgement about when native is worth it.

GraalVM Native Image compiles your application ahead of time (AOT) into a standalone native executable, with no JVM and no JIT. Results: startup in tens of milliseconds, lower memory at rest, small container. Boot 3 supports it officially. During the build, Boot's AOT engine runs the application context setup at build time and generates plain Java code for the bean definitions and the runtime hints (reflection, resources, proxies) that the native compiler needs, because native image uses a closed world: anything not seen at build time (reflection, dynamic proxies, resource loading, classpath scanning) is missing at run time unless registered with RuntimeHints, @RegisterReflectionForBinding or a configuration file. Consequences: the set of beans, profiles and many @Conditional results are fixed at build time; builds are slow (minutes) and need lots of RAM; peak throughput can be lower than a warmed-up JIT JVM; debugging is harder; some libraries do not work. Build with ./mvnw -Pnative native:compile or spring-boot:build-image with native enabled. Good fits: serverless, scale-to-zero, CLI tools, many small instances. For a long-running, busy service, a JVM with CDS, virtual threads and correct sizing is usually simpler.

Likely follow-ups
  • What is the AOT processing without native? Boot 3 can also use the generated code on a normal JVM (-Dspring.aot.enabled=true) for some startup gain.
  • Alternative to speed up JVM startup? CDS or AppCDS archives (supported with Boot 3.3 tooling), and checkpoint/restore (CRaC) with a supporting JDK.
How does graceful shutdown work in Boot, and how does it fit with Kubernetes? Senior

What the interviewer is testing: zero-error deployments.

By default a Boot web server stops immediately on shutdown and cuts requests in progress. Set server.shutdown=graceful and on SIGTERM Boot does this: the readiness state becomes REFUSING_TRAFFIC, the server stops accepting new connections, and waits for active requests to finish, up to spring.lifecycle.timeout-per-shutdown-phase (30 seconds by default). Then the context closes (beans destroyed, pools closed). Kubernetes adds a twist: when a pod is deleted it sends SIGTERM and, at the same moment, removes the pod from Service endpoints, but that removal takes a moment to reach every load balancer and kube-proxy. If the app stops accepting at once, a few requests still arrive and fail with connection refused. The common fix is a short preStop sleep (about 5 to 10 seconds) so the endpoint removal propagates before SIGTERM reaches the app. Then make sure terminationGracePeriodSeconds is larger than the preStop sleep plus the Boot timeout, or the pod gets SIGKILL. Also stop consuming messages (Kafka listeners stop on context close), finish scheduled tasks, and close executors.

12. Migrating from Boot 2 to 3 (and looking at 4)

What is the javax to jakarta change and why does it hurt? Intermediate

What the interviewer is testing: the biggest practical break in Boot 3.

Java EE moved to the Eclipse Foundation, which could not use the javax name, so it was renamed Jakarta EE and the packages became jakarta.* from Jakarta EE 9. Spring Framework 6 and Boot 3 require them: jakarta.servlet, jakarta.persistence, jakarta.validation, jakarta.annotation (@PostConstruct), jakarta.transaction, jakarta.mail. It hurts for three reasons: all your imports change; every library you depend on must have a Jakarta version (a library still on javax will fail at runtime with NoClassDefFoundError or ClassNotFoundException for javax.servlet.Filter, for instance); and a mix of both on the classpath is a source of odd errors. Note that javax.sql, javax.crypto, and other JDK packages are not renamed: only the Java EE ones. Tools: OpenRewrite recipes and IDE migration helpers do the import changes, then you chase down old libraries (older Swagger, some commons modules, vendor SDKs, internal shared libs) and upgrade or replace them. Internal shared libraries are often the real blocker: they need to publish a Boot 3 version before the services can move.

How would you plan a Boot 2.7 to 3.x upgrade for 40 services? Senior

What the interviewer is testing: a staged, low-risk plan rather than a big bang.

First, go to Boot 2.7.x latest on each service. It has the closest behaviour to 3.0, and its deprecation warnings point to what to change. Move to Java 17 while still on 2.7 (it runs there), so the JDK change is a separate step. Fix deprecations and run the full tests. Second, upgrade shared libraries and internal starters first (publish versions for Boot 3, move auto-configuration to the imports file, jakarta packages), because services depend on them. Third, per service: run an OpenRewrite recipe (UpgradeSpringBoot_3_x) to change imports and properties, add spring-boot-properties-migrator temporarily so renamed properties are reported at startup, fix Security (next question), then compile and test. Fourth, check things that tests do not catch: Hibernate 6 query and id generation behaviour changes, metric and tracing names (Sleuth to Micrometer), trailing slash matching (off by default in Spring 6: /orders/ is no longer the same route), property renames (for example server.max-http-header-size became server.max-http-request-header-size), and the Actuator env masking. Roll out with canaries and watch error rate, latency and memory. Go minor by minor (3.0, then 3.1 and so on) rather than jumping, since each has its own deprecations. Then repeat the idea for 3.5 to 4.0 later.

What changed in Spring Security configuration with Boot 3? Intermediate

What the interviewer is testing: the most visible code change after the package rename. Basics of Security are on the Spring Framework page.

Boot 3 uses Spring Security 6. The main changes you hit: WebSecurityConfigurerAdapter is removed. You declare a SecurityFilterChain bean instead (the component style began in 5.4 and is now the only way). authorizeRequests() became authorizeHttpRequests(), and antMatchers, mvcMatchers, regexMatchers were replaced by requestMatchers. The lambda DSL (http.csrf(c -> c.disable())) is the preferred style and the old chained .and() style is deprecated. @EnableGlobalMethodSecurity became @EnableMethodSecurity (with @PreAuthorize on by default). Authorization was reworked around AuthorizationManager. Some defaults are stricter: the security filter now applies to all dispatcher types, so error dispatches (/error) need permitAll; SecurityContextHolder context must be saved explicitly in custom filters (requireExplicitSave); and the @Configuration for the filter chain no longer needs to extend anything. With the OAuth2 resource server, the JWT converter setup is mostly the same, with new package names.

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(c -> c.disable())
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health/**").permitAll()
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}
What other Boot 3 and Spring 6 changes commonly break apps? Intermediate

What the interviewer is testing: breadth of real migration experience.

  • Java 17 minimum. Java 8 and 11 do not run Boot 3. Strong encapsulation of JDK internals can break libraries using reflection into java.base.
  • Auto-configuration registration: the old spring.factories key for auto-configuration is no longer read.
  • Sleuth removed: use Micrometer Tracing. Trace propagation, log pattern and metric names change.
  • Hibernate 6: changed id generation defaults for sequences, query parsing is stricter, some HQL breaks, and the dialect settings are different.
  • Trailing slash match is off by default in Spring MVC.
  • Constructor binding for @ConfigurationProperties is automatic for a single constructor; @ConstructorBinding only needed at class level in rare cases.
  • HTTP client: Apache HttpClient 5 replaces 4 for RestTemplate; Tomcat 10.1; Jetty 11 or 12; Undertow needed an update.
  • Spring Cloud must be a matching release train (2022.0.x or later for Boot 3).
  • Actuator: the env and configprops values are masked by default; the httptrace endpoint became httpexchanges.
  • Removed deprecated 2.x APIs. Compile errors tell you most of it.

The properties migrator and the "Upgrading to Boot 3" wiki page together catch most of these.

What should an engineer know about Spring Boot 4? Senior

What the interviewer is testing: that you follow the platform. Be honest about what you have used.

Boot 4.0 (November 2025) builds on Spring Framework 7. As far as I know, the headline points are: the code base is modularised, so the single big spring-boot-autoconfigure jar is split into smaller modules with their own auto-configuration and dedicated starters, which gives smaller classpaths, faster startup and more precise conditions; Jackson 3 becomes the default JSON library (with a new package name tools.jackson) and Jackson 2 support is deprecated; Jakarta EE 11 and newer servers (Tomcat 11, Servlet 6.1); null-safety through JSpecify annotations; first-class API versioning support in Spring MVC; HTTP service clients become easier to register; the deprecated pieces from 3.x (for example @MockBean and Undertow) are removed; Java 17 stays the minimum with support for newer Java versions. Migration advice: be on the latest 3.5 first, clear every deprecation warning, then upgrade, and read the official migration guide, as exact details can differ from my summary. In the interview, saying "I would verify against the release notes" is a stronger answer than guessing.

13. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

After a refactor the app will not start: "NoSuchBeanDefinitionException: No qualifying bean of type OrderService". What do you do? Intermediate

What the interviewer is testing: a systematic way to read a startup failure.

Situation: startup fails with an "APPLICATION FAILED TO START" block saying a bean of some type was required but not found.

Check first: read the Description and Action lines, and the name of the class that needed the bean. Then ask the four usual questions. Is the class annotated (@Service, @Component) or declared by a @Bean? Is it in a package below the main class, or covered by scanBasePackages (a package move in a refactor is the most common cause)? Is it hidden by a condition: @Profile, @ConditionalOnProperty, a property that is now missing? Is it from a library whose auto-configuration did not run (missing starter, or the class is not on the classpath)? Is there another type involved, such as an interface with no implementation after a rename, or two implementations (that gives a different error, "expected single matching bean but found 2")?

Steps:

java -jar app.jar --debug          # conditions report: look in Negative matches
curl localhost:8080/actuator/beans # if it starts partly in another profile
mvn dependency:tree | grep -i the-library

Fix the package or annotation, enable the missing property or profile, or add the missing dependency. Use @Qualifier or @Primary when there are several candidates.

Prevent: keep the main class in the root package, have one @SpringBootTest context-loads test in CI so the failure shows on the pull request, and avoid moving packages without running the app.

"Web server failed to start. Port 8080 was already in use." It works on your colleague's machine. What do you do? Basic

What the interviewer is testing: simple operational debugging, and test hygiene.

Situation: the embedded server could not bind to its port.

Check first: who owns the port? On Linux or macOS use lsof -i :8080 (or ss -ltnp), on Windows netstat -ano | findstr :8080 and then the task list for that process id. Often it is a previous run of the same app that was not stopped, an IDE run, a Docker container that maps the port, or another service. In a container, two processes in the same pod cannot share a port either (an app plus a sidecar, or a second server such as a management port set to the same number).

Steps: stop the other process, or change this app's port with --server.port=8081 or SERVER_PORT=8081. For integration tests never use a fixed port: use webEnvironment = RANDOM_PORT, or server.port=0 to let the OS pick a free one. If management.server.port equals server.port by accident, change it.

Prevent: random ports in tests, a documented port per service in local setups, and containers for local dependencies so ports stay mapped explicitly.

After upgrading Boot, the app fails with "The dependencies of some of the beans in the application context form a cycle". It worked before. Why, and what do you do? Intermediate

What the interviewer is testing: knowing the behaviour change, and resisting the quick flag.

Situation: the app ran for years on Boot 2.5 or earlier and now stops at startup on 2.6 or later.

Check first: read the cycle printed in the error: it lists the beans in a loop, for example orderService -> paymentService -> orderService. Boot 2.6 turned circular references off by default (spring.main.allow-circular-references=false). Before that, field or setter injection tolerated a cycle by building half-ready beans.

Steps: the quick, temporary fix is spring.main.allow-circular-references=true to unblock a release. The real fix is to remove the loop: move the shared logic into a third service; replace one direction with an application event; pass a value instead of the bean; or inject one side with @Lazy or ObjectProvider as a last resort. After the fix, remove the flag.

Prevent: constructor injection everywhere (cycles then fail early and loudly), and an architecture rule test (ArchUnit) that forbids cycles between packages.

The production pod connects to the dev database. You suspect the wrong profile. How do you confirm and fix it? Intermediate

What the interviewer is testing: configuration debugging under pressure.

Situation: an instance is using values from another environment, or the default profile.

Check first: stop traffic to it if data is at risk (scale down or cordon it from the Service). Read the first lines of the startup log: Boot prints "The following 1 profile is active: dev" or "No active profile set, falling back to 1 default profile: default". Then ask the running app: /actuator/env shows spring.profiles.active and which property source it came from, and /actuator/env/spring.datasource.url shows the winning source. Look at the pod spec: is the variable named exactly SPRING_PROFILES_ACTIVE (a dash or a typo makes it ignored silently)? Is a baked-in application.yml setting spring.profiles.active? Does a command-line argument in the entrypoint override it? Remember command line and system properties beat the environment variable.

Steps: correct the variable in the deployment manifest, roll out, verify in the log and in /actuator/env, and check what data the wrong instance wrote.

Prevent: fail fast: validate required properties with @ConfigurationProperties and no defaults for environment-specific values, so a missing production value stops the startup; separate network access so non-prod and prod databases are unreachable from the other side; and a smoke test after each deployment that prints the active profile.

The service now takes 3 minutes to become ready after a deployment, and Kubernetes keeps killing it. What do you do? Senior

What the interviewer is testing: measure first, then fix the cause, and protect the rollout while you work.

Situation: liveness probes fail during startup, so the pod restarts in a loop (CrashLoopBackOff), and the rollout stalls.

Check first: stop the bleeding: add or raise a startup probe (for example failureThreshold: 30, periodSeconds: 10), so liveness does not run until boot ends. Then find out why it is slow. Compare with the last good version: what changed (dependency, new auto-configuration, new migration, new remote call at startup)? Look at log timestamps between steps. Check the CPU limit: a pod with 250m CPU can start 5 times slower than with 1 CPU, and throttling shows in metrics.

Steps:

  1. Record startup: BufferingApplicationStartup and /actuator/startup, or start locally with DEBUG for org.springframework.
  2. Typical findings: a Flyway migration that rebuilds a big index; Hibernate ddl-auto=update reading metadata; a remote config server or secret store with a slow timeout; @PostConstruct that loads a big dataset; Kafka or Redis clients connecting eagerly with long retries; component scanning a large classpath.
  3. Fix by cause: run migrations as a separate job; move data loading after readiness and make it async; shorten timeouts; trim dependencies; raise CPU requests at startup.

Prevent: an alert on startup time, a startup probe by default in the service template, CDS or AOT for large services, and a rule that nothing slow runs on the main thread during boot.

At peak the API returns 500s: "HikariPool-1 - Connection is not available, request timed out after 30000ms". What do you do? Senior

What the interviewer is testing: do you find the cause, or just raise the pool size.

Situation: requests wait 30 seconds for a database connection and then fail. Latency is up, the database may look idle or busy.

Check first: metrics hikaricp.connections.active (equals max?), .pending (growing?), and .usage/.acquire times. On the database side, look for long-running queries, lock waits, and the number of sessions. Take a thread dump: many threads in HikariPool.getConnection confirm the pool is the bottleneck, while threads holding connections show what they are doing (waiting on a lock, a slow remote HTTP call inside a transaction, a stuck query).

Steps: mitigate: restart or scale out if the database has capacity; kill the blocking query. Then find the cause: (1) slow queries (missing index, N+1 loops) hold connections long; (2) a transaction wrapping a remote call, or open-in-view=true keeping the connection through the whole request; (3) a leak, a connection not returned: turn on leak-detection-threshold=20000 to see the stack trace; (4) a traffic spike bigger than the pool (a real capacity issue); (5) pool size times replicas exceeds the database limit, so each instance starves the others. Only after that adjust the pool, and reduce connection-timeout to fail fast.

Prevent: open-in-view=false, short transactions with no I/O inside, a pool alert on pending greater than 0 for some minutes, query timeouts, load tests that include the pool, and a circuit breaker or rate limit in front of heavy endpoints.

The pod restarts every few hours with exit code 137, and there is no OutOfMemoryError in the logs. What is happening? Senior

What the interviewer is testing: the difference between a Java heap error and a container kill.

Situation: kubectl describe pod shows OOMKilled, exit code 137. The JVM never got the chance to throw anything.

Check first: the kernel killed the process because total memory of the container passed its limit. That total is heap plus non-heap. Compare the limit with the JVM settings: if -Xmx or MaxRAMPercentage is close to the limit, there is no room for metaspace, thread stacks (about 1 MB each), direct buffers, code cache and the JVM itself. Check metrics: jvm.memory.used by area and process.resident.memory if available, thread count, and Native Memory Tracking (-XX:NativeMemoryTracking=summary and jcmd PID VM.native_memory).

Steps: lower the heap to about 70 percent of the limit (-XX:MaxRAMPercentage=70); raise the container limit if the real need is higher; bound thread pools and direct memory (-XX:MaxDirectMemorySize, Netty settings); look for a real leak by watching heap after full GC over time: if it climbs, take a heap dump and find the retained objects (an unbounded cache, a map keyed by request data, a ThreadLocal). Add -XX:+HeapDumpOnOutOfMemoryError, and alert on memory working set near the limit.

Prevent: use buildpacks or a standard memory template for all services, set limits equal to requests for memory, and run a soak test before release.

The service is slow only in Kubernetes. CPU graphs look low but latency is high, and startup is slow. Why? Senior

What the interviewer is testing: CPU throttling and JVM sizing in containers.

Situation: the same jar runs fast on a laptop, and slow in a pod with a CPU limit of, say, 500m.

Check first: the metric container_cpu_cfs_throttled_periods_total (or "CPU throttling" in your dashboard). A CPU limit is enforced in short time slices: a multi-threaded JVM can use its whole quota in the first part of a slice and then be frozen for the rest, so requests stall even though average CPU looks low. GC threads, JIT compiler threads and many worker threads all compete for the small quota. Also check how many CPUs the JVM thinks it has (Runtime.availableProcessors(), logged by -Xlog:os+container): with a limit under 2 CPUs, JVM may choose the serial GC and size pools small.

Steps: raise the CPU limit (or remove the limit and keep a request, a common practice for latency-sensitive services); right-size thread pools to the CPUs you really have; choose G1 explicitly with at least 2 CPUs if the app needs it, or keep serial for tiny pods; add CPU during startup; consider CDS and AOT to cut start-up work.

Prevent: load test in the same resource shape as production, alert on throttling, and keep a startup probe so slow starts are not killed.

The database had a 2 minute outage and every pod was restarted, which made the recovery slower. What went wrong? Senior

What the interviewer is testing: liveness versus readiness design.

Situation: during a short outage of a shared dependency, Kubernetes restarted the whole fleet. When the database returned, all pods started at once and overloaded it with connections and migrations.

Check first: what the liveness probe calls. If it points to /actuator/health (the full health including the db indicator), then a database failure returns 503, liveness fails, and the kubelet kills the pod. That does nothing useful: restarting a healthy JVM does not fix the database. Check the pod events and the probe settings (thresholds, timeouts) in the manifest.

Steps: point liveness to /actuator/health/liveness, which reflects only the internal state of the app (it turns BROKEN only when the app decides it cannot recover). Point readiness to /actuator/health/readiness and decide which dependencies belong there: a pod that cannot reach its only database should be taken out of rotation, but be careful: if every pod goes unready at once you serve nothing, so consider degrading gracefully instead. Give the probes sensible timeouts and failure thresholds, add a startup probe, add retry with backoff and jitter for connections, and limit the connection pool so a restart wave does not flood the database. A Pod Disruption Budget and slow rollouts help too.

Prevent: a service template with the three probes done correctly, and a game day that switches off a dependency to prove the fleet does not restart.

After adding one library, every endpoint returns 401 and the log shows "Using generated security password". How did that happen? Senior

What the interviewer is testing: the "auto-configuration surprise from a transitive dependency" problem.

Situation: nobody added Spring Security, yet the app now asks for a login. A new internal client library was added.

Check first: the log line "Using generated security password: ..." means UserDetailsServiceAutoConfiguration ran, so Spring Security is on the classpath. Run mvn dependency:tree -Dincludes=org.springframework.security (or gradle dependencies) to see which dependency brought it. Also run with --debug and read Positive matches for SecurityAutoConfiguration and SpringBootWebSecurityConfiguration.

Steps: decide if you want security. If yes, define your own SecurityFilterChain with the rules you want (this makes the default back off). If no, remove or exclude the dependency from the library, or exclude the auto-configurations with spring.autoconfigure.exclude. The same pattern appears with other libraries: adding a JDBC or JPA jar causes "Failed to configure a DataSource", adding Flyway runs migrations on startup, adding Hazelcast or Redis starts a client, adding actuator exposes health, adding a second JSON library changes message converters, and adding both Tomcat and Jetty jars picks one by order.

Prevent: keep libraries (especially shared company jars) free of starters they do not need: mark them optional or provided; review the dependency tree and the conditions report on every upgrade; and have a context-loads test and a basic security test (anonymous request returns what you expect) in CI.

You set a property in a ConfigMap and the app ignores it. How do you find out why? Intermediate

What the interviewer is testing: property precedence and naming rules in practice.

Situation: you changed acme.payment.timeout but behaviour did not change.

Check first: ask the app what it sees: /actuator/env/acme.payment.timeout shows every source defining the key and the winner, and /actuator/configprops shows the bound object. Then walk the common causes in order: (1) Precedence: a command-line argument or system property in the container entrypoint (-Dacme.payment.timeout=...) beats the environment and files. (2) Name mismatch: environment variables must be upper case with underscores, ACME_PAYMENT_TIMEOUT; a dot or dash in the variable name does not work. (3) File not loaded: the ConfigMap is mounted somewhere Boot does not look. Check spring.config.additional-location or spring.config.import. Setting spring.config.location replaces the defaults, so the packaged file vanishes. (4) No restart: values are read at startup; a ConfigMap change needs a pod restart (env vars never update in a running pod). (5) Profile: the key is in a profile file that is not active, or a profile-specific file overrides your general one. (6) Typo or wrong type: acme.payment.timout; or binding to @Value with a different name. (7) A @Value("${key:default}") default hides the missing value. (8) .properties beats .yml in the same place.

Prevent: bind with @ConfigurationProperties plus validation so unknown or missing keys are visible (ignore-unknown-fields=false for strict mode), log effective values for non-secret settings at startup, and use one configuration method per setting.

A small worker service that never uses a database now fails with "Failed to configure a DataSource". What happened? Basic

What the interviewer is testing: the most common auto-configuration surprise.

Situation: startup stops with "'url' attribute is not specified and no embedded datasource could be configured".

Check first: a JDBC-related class is on the classpath, so DataSourceAutoConfiguration tried to create a pool. Find which dependency added it (spring-boot-starter-jdbc, a JPA starter, or a transitive library such as a batch or workflow framework). Check the conditions report for DataSourceAutoConfiguration.

Steps: if the service really needs no database, remove the dependency, or exclude the auto-configurations: @SpringBootApplication(exclude = {DataSourceAutoConfiguration.class, HibernateJpaAutoConfiguration.class}). If it should have one, the URL is missing: check the profile, the environment variable name (SPRING_DATASOURCE_URL) and the mounted config. If you wanted an embedded test database, add H2 to the test scope.

Prevent: do not add starters "just in case", and run the app (not only unit tests) in CI so this kind of failure appears in the pull request.

Every deployment causes a few seconds of 502 and 503 errors. How do you get zero-error rollouts? Senior

What the interviewer is testing: graceful shutdown plus Kubernetes timing.

Situation: during a rolling update, clients see errors for a short time, especially connection resets and 502 from the ingress.

Check first: time sequence. When a pod terminates, SIGTERM and endpoint removal start together, but the ingress and kube-proxy take a few seconds to forget the pod. Does the app stop at once on SIGTERM (default server.shutdown=immediate)? Is there a preStop hook? Is terminationGracePeriodSeconds large enough? Also look at the start side: does the new pod receive traffic before it is ready (a readiness probe that is too optimistic, or none)? And check keep-alive: if the app closes an idle connection a little before the load balancer does, the next request on that connection fails; the app's keep-alive timeout must be longer than the load balancer's.

Steps: set server.shutdown=graceful and spring.lifecycle.timeout-per-shutdown-phase=30s; add a preStop sleep of 5 to 10 seconds; set the grace period to more than the sleep plus 30 seconds; use a correct readiness probe; set rolling update maxUnavailable: 0; and align keep-alive timeouts. Make sure message consumers stop cleanly and in-flight messages are acknowledged or safely retried.

Prevent: put all of this in the shared deployment template, and test it with a load generator running during a rollout.

A deployment fails at startup with "Migration checksum mismatch". Production data is in that database. What do you do? Senior

What the interviewer is testing: safe schema management, and not reaching for the destructive fix.

Situation: Flyway refuses to start because an already-applied migration file differs from what was recorded.

Check first: do not run flyway clean (it drops everything, and it is disabled by default in recent versions for this reason). Find what changed: git log on the migration file. Someone edited an applied script (even whitespace or a comment, or a line-ending change from the editor changes the checksum). Compare with the table flyway_schema_history (checksum, installed time). Are other environments fine?

Steps: revert the file to the exact original content (the safest fix) and put the intended change in a new versioned migration. If the original change really was needed and is already applied manually, use flyway repair to update the recorded checksum after you have confirmed the database state matches. A failed migration (half applied, in a database without transactional DDL) needs a manual fix to the schema, then repair. Take a backup first.

Prevent: a CI check that rejects changes to existing migration files, validate-on-migrate on, backward-compatible steps (expand, then contract), running migrations in a pre-deploy job against a copy of production data, and never giving the app user rights to drop tables.

Heap usage climbs for days until the service becomes slow and restarts. How do you find the leak? Senior

What the interviewer is testing: a method for memory problems, not guessing.

Situation: the saw-tooth GC pattern slowly shifts upward. Full GCs happen more often and free less memory. Latency grows. Eventually OutOfMemoryError: Java heap space or GC overhead limit exceeded.

Check first: confirm it is a leak, not just a big working set: look at the heap used after full GC over days. If it only goes up, it is a leak. Check which area (heap, metaspace) and the class counts. Also see whether it correlates with a feature or traffic type.

Steps: take a heap dump when the heap is high (jcmd PID GC.heap_dump file, or the Actuator endpoint if secured), and ideally a second one later, then open them in a heap analyser (Eclipse MAT or VisualVM). Look at the "dominator tree" and "leak suspects", and follow the path to GC roots to see who holds the objects. Usual culprits in Boot services: an in-memory cache with no size limit or expiry (a plain ConcurrentMapCacheManager, or a hand-made static map); a metric tag with unbounded values (a new meter object per user id); listeners or scheduled tasks registered again and again; a ThreadLocal never cleared in a thread pool; large result sets loaded fully; session or request data stored in a static; Hibernate first-level cache growth in a long loop. Fix the cause, for example bound the cache with Caffeine maximumSize and expireAfterWrite.

Prevent: soak tests, alerts on after-GC heap trend, -XX:+HeapDumpOnOutOfMemoryError, and code review that asks "what removes this entry?" for each cache or map.

The nightly report e-mail was sent three times, once per pod. How do you fix the @Scheduled job? Intermediate

What the interviewer is testing: scheduling in a horizontally scaled setup.

Situation: the service has three replicas, each with its own scheduler. Each runs the cron method at 02:00.

Check first: confirm in the logs that all three pods ran it at nearly the same time. Spring's @Scheduled knows nothing about other instances.

Steps: choose by need. (1) ShedLock (or Quartz clustered mode): a lock row in the database or Redis, so only the instance that gets the lock runs the task; set lockAtMostFor longer than the job and lockAtLeastFor to cover clock differences. (2) A Kubernetes CronJob that runs the work once as a separate pod: clean for heavy or rare work. (3) Leader election. In every case make the job idempotent (a "report sent" record per day), because locks can still fail, and a retry can repeat a send. Check time zones with zone on the cron expression, and the scheduler pool size, since the default is one thread.

Prevent: a rule in code review that every scheduled method is lock protected or idempotent, and a test with two instances.

After moving to Boot 3, a shared internal library "does nothing", and some URLs with a trailing slash return 404. What is going on? Senior

What the interviewer is testing: migration traps that do not produce compile errors.

Situation: the app starts, tests pass, but behaviour differs in production.

Check first: two classic silent changes. First: the library registers its auto-configuration in META-INF/spring.factories under EnableAutoConfiguration. Boot 3 no longer reads that key, so the library's beans are never created. The conditions report shows no entry for it. Second: Spring Framework 6 turned off trailing slash matching, so /orders/ no longer maps to /orders.

Steps: for the library, add META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports and republish (or, short term, import the configuration class explicitly with @Import). For URLs: change clients and gateways to the canonical path; as a bridge, register a redirect or re-enable matching for specific paths via PathMatchConfigurer (not recommended long term). Review other silent items: renamed or removed properties (use the properties migrator), changed Hibernate behaviour, metric and tracing names, and the Actuator env masking.

Prevent: contract tests for shared libraries on the new Boot version, a canary rollout with dashboards, and a migration checklist that includes a comparison of the conditions report before and after the upgrade.

A security scan finds /actuator/env and /actuator/heapdump open on the public internet. What do you do? Senior

What the interviewer is testing: incident priority: contain, assess, rotate, prevent.

Situation: someone set management.endpoints.web.exposure.include=* to debug something and shipped it.

Check first: contain right now: block the path at the ingress or gateway (deny /actuator/** except health) while you fix the app. Then assess: check access logs for requests to these endpoints from outside. A heap dump holds passwords, tokens and personal data; env can show connection strings and keys (masked by default in Boot 3, but not in Boot 2, and masking does not cover everything).

Steps: deploy a fix that exposes only health, info and the metrics endpoint; move management to a separate internal port (management.server.port) and add Security rules with EndpointRequest. If logs show access, treat all secrets as leaked: rotate database passwords, API keys, signing keys, and invalidate sessions and tokens. Inform the security team and follow the incident process.

Prevent: default-deny at the ingress for management paths, a build test that fails when exposure is * in production profiles, an external scan in CI, and secrets from a store with short lifetimes.

You enabled virtual threads on Java 21 and under load the service stopped responding while CPU was idle. What happened? Senior

What the interviewer is testing: honest knowledge of virtual thread limits.

Situation: after setting spring.threads.virtual.enabled=true, throughput first rose, then requests hung under heavy load, with almost no CPU use.

Check first: take a thread dump (for virtual threads use jcmd PID Thread.dump_to_file -format=json file, the ordinary dump hides them). Look for pinned threads: virtual threads blocked inside a synchronized block or a native call keep their carrier thread. In Java 21 to 23, if enough carriers are pinned (the pool is about the number of CPUs), everything else cannot run. Run with -Djdk.tracePinnedThreads=full to print the stack where pinning happens. Check also the downstream: Hikari pool pending count, remote client limits. With virtual threads, thousands of requests can now wait at the pool at the same time, and each holds memory.

Steps: update libraries that use synchronized around I/O (some JDBC drivers, older clients) or replace the locks with ReentrantLock in your own code; move to Java 24 or later where most pinning in synchronized is gone; add explicit limits (a semaphore or bulkhead) in front of scarce resources; set timeouts; keep the pool sizes. If it cannot be fixed, switch the property off and go back to platform threads.

Prevent: load test before enabling it, monitor pinning events with JFR, and roll it out to one service first.
