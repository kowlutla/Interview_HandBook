Mental model: the 7 ideas everything hangs on

One line: Spring Boot is Spring plus opinions. It looks at your classpath and your properties, and registers the beans you would probably have written yourself. You override any of it by defining your own bean or setting a property.
  1. Boot is not a new framework. It sits on Spring Framework. Every Boot feature ends up as ordinary Spring beans and ordinary configuration.
  2. Starters pull in the right jars. One dependency such as spring-boot-starter-web brings Spring MVC, Jackson, Tomcat and logging, at versions known to work together (the BOM, a bill of materials).
  3. Auto-configuration is conditional configuration. Each class says: "if this library is on the classpath and the user has not defined their own bean, create this bean".
  4. User beans always win. Auto-configuration is processed after your own configuration, and most of its beans are @ConditionalOnMissingBean.
  5. Configuration has a strict order. The same jar runs everywhere because properties come from many sources (files, environment variables, command line) and the higher source wins.
  6. The app is a plain main method. SpringApplication.run builds the context and starts an embedded web server in the same process. Deploying means running one jar.
  7. Production features are opt-in. Actuator (health, metrics), graceful shutdown and tracing are modules you switch on, not code you write.

1. Boot basics, starters and the BOM

What does Spring Boot give you that plain Spring does not? Basic

Boot removes the setup work. Starters give me a working set of dependencies in one line, auto-configuration creates the usual beans (DataSource, Jackson, MVC) from what is on the classpath, and an embedded server lets me run the app as a plain jar. On top of that I get externalized configuration and production features like Actuator.

Plain Spring is powerful but you wire it yourself: pick compatible library versions, declare the DataSource, the transaction manager, the view resolver, package a WAR, deploy it to a server. Boot does the common 80 percent for you and steps aside when you define your own bean. It is still just Spring underneath, so anything Boot creates can be inspected, overridden or switched off. The trade-off is "magic": when something is auto-configured that you did not expect, you need to know how to find out why (see the debug question later).

Remember: Boot = Spring + starters + auto-configuration + embedded server + production add-ons. Same Spring underneath.

What is inside @SpringBootApplication? Basic

It is three annotations in one. @SpringBootConfiguration marks the class as a configuration class (it is a @Configuration). @EnableAutoConfiguration turns on auto-configuration. @ComponentScan scans the package of this class and everything below it for my components.

That is why the main class should sit in the root package of the project: the scan starts there. I can replace the one annotation with the three separate ones, and I can tune it, for example @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) or scanBasePackages = {"com.acme.a", "com.acme.b"}. Inside @EnableAutoConfiguration, an import selector reads the auto-configuration list from every jar on the classpath, and @AutoConfigurationPackage records the root package so that JPA and others know where to look for entities.

Remember: configuration class + auto-configuration + component scan, all starting at the main class's package.

My @Service in another package is not found. How does Boot decide where to scan, and how do I fix it? Basic

Boot scans only the package of the @SpringBootApplication class and its sub-packages. If my bean lives in a sibling package like com.other.service, it is simply not seen. The cleanest fix is to move the main class up to the common root package; otherwise I set scanBasePackages or add @Import.

The symptom is NoSuchBeanDefinitionException at startup (for constructor injection) or a 404 for a controller that exists. Check first: is the class annotated (@Service, @Component), is it in a scanned package, and is a @Profile or @Conditional turning it off? Be careful with @ComponentScan placed on another class: it replaces the default scan base instead of adding to it, so the main class's own package may stop being scanned. A shared library that ships beans should use auto-configuration or an explicit @Import, not rely on the app scanning its packages.

@SpringBootApplication(scanBasePackages = {"com.acme.orders", "com.acme.shared"})
public class OrdersApp { ... }

Remember: scan starts at the main class's package. Move the main class up, or list the packages.

What is a starter, and what is inside one? Basic

A starter is a dependency descriptor: a tiny jar with no code that pulls in a curated set of libraries for one purpose. spring-boot-starter-web brings Spring MVC, Jackson, embedded Tomcat and logging. It saves me from choosing libraries and matching their versions.

The starter itself only has a pom listing dependencies. The logic that creates beans lives in the separate spring-boot-autoconfigure jar. The two work together: the starter puts libraries on the classpath, and auto-configuration notices them and builds the beans. That is why adding spring-boot-starter-data-jpa is enough to get a DataSource, an EntityManagerFactory and a transaction manager. A consequence to remember: adding a starter can change app behaviour, because new classes on the classpath switch on new auto-configurations (security is the famous one).

Remember: a starter is a dependency list. Auto-configuration is what reacts to it.

How does Boot manage dependency versions, and how do I override one? Intermediate

Boot ships a BOM (bill of materials) called spring-boot-dependencies that fixes the version of hundreds of libraries, so I declare them without a version. With the Boot parent POM or the Gradle plugin that is automatic. To override one library I set its version property, for example jackson-bom.version in Maven.

The managed versions are tested together, which avoids the "works on my machine" jar conflicts. Overriding is allowed, but I do it deliberately: usually to pick up a security fix before the next Boot release. In Maven I set a property in <properties>; in Gradle with the dependency-management plugin I set ext['jackson-bom.version']. If my company already has a parent POM, I import the Boot BOM with <scope>import</scope> instead. To see what version was actually picked, run mvn dependency:tree or gradle dependencies. Overriding a core library such as Hibernate to a different major version is risky, because Boot's auto-configuration is tested against its managed one.

Remember: leave versions out, let the BOM choose; override with the BOM's property name, not by hard-coding a version.

2. Startup and context problems

What happens when you call SpringApplication.run()? Senior

Boot first prepares the environment: it detects the app type (servlet, reactive or none), loads properties and activates profiles. Then it creates the ApplicationContext, loads bean definitions including auto-configuration, and calls refresh(), which creates the singleton beans and starts the embedded web server. At the end it runs CommandLineRunner and ApplicationRunner beans, and the app is ready.

Along the way Boot publishes events (starting, environment prepared, started, ready, failed) so listeners can hook in. The two events I actually use are ApplicationReadyEvent (app can take traffic) and ApplicationFailedEvent. If anything throws, Boot prints a failure analysis and exits with a non-zero code, which is what makes a Kubernetes pod crash loop visibly. The web server starts near the end of refresh(), so a slow bean delays the port opening, and anything done in a runner delays "ready".

Remember: environment first, then context and beans, then the web server, then runners, then ready.

CommandLineRunner, ApplicationRunner, @PostConstruct, ApplicationReadyEvent: which one do I use for startup work? Intermediate

For work that needs the whole application up, such as warming a cache or a one-off task, I use a runner or an ApplicationReadyEvent listener. @PostConstruct is only for initialising that one bean, because it runs while other beans may not be ready yet. Between the two runners, ApplicationRunner gives me parsed arguments, CommandLineRunner gives raw strings.

  • @PostConstruct: runs per bean, during creation. Keep it quick and local. Slow work here delays context start and can deadlock with circular setups.
  • Runners: run after the context is refreshed, before the app reports ready. Ordered with @Order. An exception here fails the startup. A slow runner delays readiness, which is fine for must-have setup and bad for optional warming.
  • ApplicationReadyEvent: published after runners finish. Use it for optional work that should not block start.

Anything long (data load, remote calls) should be asynchronous or in a Kubernetes init step, with a startup probe protecting it from being killed.

Remember: @PostConstruct = this bean only; runner = needs the whole app; ready event = optional, non-blocking.

What does spring.main.lazy-initialization do, and what are the risks? Intermediate

It tells Spring to create beans only when they are first needed, instead of all at startup. Startup gets faster and uses less memory, but problems that used to fail at boot (missing beans, bad configuration) now fail on the first request instead. I use it for local development and tests, and I am careful in production.

The first request that touches a lazy bean pays its creation cost, so p99 latency spikes right after a deploy. Readiness says "ready" before the app is really warmed up. A better production approach is to find which beans are slow and make only those lazy with @Lazy, or to fix the slow startup itself. Eager startup has a real benefit: configuration errors kill the pod during rollout, before it receives traffic, so a bad deploy is caught by the platform and not by users.

Remember: lazy init moves errors and cost from startup to first use. Fail fast is usually what you want in production.

Boot refuses circular dependencies. Why, and how do you fix a cycle? Intermediate

Since Boot 2.6 circular references are not allowed by default, so a cycle fails at startup with "The dependencies of some of the beans in the application context form a cycle". A cycle (A needs B and B needs A) is a design smell, so I fix it by breaking the loop, not by switching it back on with spring.main.allow-circular-references=true.

With constructor injection a cycle can never work, because neither object can be built first. Field or setter injection hid the problem by injecting half-built objects. The usual fixes, best first: move the shared logic into a third bean that both use; replace a direct call with an application event; or make the dependency lazy, either @Lazy on the constructor parameter (Spring injects a proxy) or ObjectProvider<B>. If I ever see a cycle between two services, the real question is which one owns the behaviour.

// A needs B, B needs A  ->  extract the shared part
class PricingRules { ... }          // used by both OrderService and DiscountService

Remember: a cycle means the design is wrong. Extract a third bean first, use @Lazy as a last resort.

Your Boot app takes 90 seconds to start. How do you find out why? Senior

I measure first, then fix the biggest item. I turn on Boot's startup tracking (BufferingApplicationStartup and the /actuator/startup endpoint) to see which beans took longest. Then I look at logs for gaps, because the usual causes are slow beans (remote calls or cache warming in constructors), database migrations, classpath scanning of a huge package, and a remote config server.

Typical findings: a bean calling a remote service in @PostConstruct with no timeout; Flyway running many migrations on every start; Hibernate validating the schema against a slow database; component scan over a very wide package; too little CPU in the container (Java starts slowly on 0.5 CPU, JIT compiles use CPU). Fixes: move remote or warm-up work after startup (ready event or async), narrow the scan, give the pod more CPU at startup, make a few heavy beans @Lazy, and add a Kubernetes startup probe so slow starts are not killed. For extreme cases there is CDS or native image, but measure before reaching for them.

SpringApplication app = new SpringApplication(App.class);
app.setApplicationStartup(new BufferingApplicationStartup(4096));
// management.endpoints.web.exposure.include=startup

Remember: measure with /actuator/startup, find the slow bean, move its work out of startup.

3. Auto-configuration

How does auto-configuration work internally? Senior

Every Boot jar lists its auto-configuration classes in a file, META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. At startup @EnableAutoConfiguration reads those files from the whole classpath, then each class is checked against its @Conditional rules. If all conditions pass, its beans are registered; if one fails, the whole class is skipped. These classes run after my own configuration, so my beans take precedence.

A typical one looks like this: DataSourceAutoConfiguration is active only if DataSource is on the classpath, and its beans are guarded by @ConditionalOnMissingBean, so defining my own DataSource switches the default off. Settings are bound from properties by @EnableConfigurationProperties classes. The file replaced the old spring.factories key in Boot 2.7, and Boot 3 no longer reads the old key for auto-configuration. Boot also ships a pre-filter that reads a generated metadata file, so classes whose required jars are missing are discarded without even being loaded, which keeps startup quick.

Remember: list in imports file, filter by conditions, run after user config, back off when the user defines the bean.

Name the common @Conditional annotations and what each is for. Intermediate

The ones I use most: @ConditionalOnClass (a library is on the classpath), @ConditionalOnMissingBean (back off if the user defined one), @ConditionalOnProperty (a property has a value, good for feature flags), and @ConditionalOnBean. Together they let a configuration say "create this if the library is present and the user has not already provided one".

Remember: class = is the library there, missing bean = can the user override, property = feature switch.

How does @ConditionalOnMissingBean let my bean replace a default, and what can go wrong? Senior

Auto-configuration is processed after my configuration. By the time Boot's @ConditionalOnMissingBean is evaluated, my bean is already registered, so the condition fails and the default is skipped. That is the whole override mechanism: I define a bean of the same type, and the default backs off.

What goes wrong: if my bean has a different type than the one the condition checks (for example I define a MyObjectMapper that does not extend ObjectMapper), the default still appears and I get two. If I define a bean in a class that is itself conditional or in a later-loaded place, order can bite. Overriding wholesale also loses Boot's extras: defining my own ObjectMapper drops the Jackson properties and modules Boot would have applied. So before replacing, check for a customizer: Jackson2ObjectMapperBuilderCustomizer, WebMvcConfigurer, RestClientCustomizer adjust the default without replacing it. Use a customizer to tweak, and a full bean to replace.

@Bean
Jackson2ObjectMapperBuilderCustomizer jsonTweaks() {
    return b -> b.featuresToEnable(SerializationFeature.INDENT_OUTPUT);
}

Remember: tweak with a customizer, replace with your own bean of the same type. Replacing loses Boot's extras.

How do you turn off an auto-configuration you do not want? Basic

Add it to exclude on @SpringBootApplication (or @EnableAutoConfiguration), or list it in spring.autoconfigure.exclude in properties. The property form is handy because it can differ per profile and needs no code change.

@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)

# application.yml (no code change, per profile)
spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

Use excludeName with a string if the class is not on the compile classpath. Excluding is a last resort. Often a property is cleaner (spring.jpa.hibernate.ddl-auto, spring.main.web-application-type=none), or the cause is a library on the classpath that the app does not need, in which case removing that dependency is better. When an excluded config is something other beans depend on, expect a "no bean of type" error next.

Remember: exclude via annotation or spring.autoconfigure.exclude, but first ask if a property or a dependency removal is cleaner.

An auto-configuration is not kicking in, or one I did not expect is. How do I debug it? Intermediate

I ask Boot for the condition evaluation report. Start the app with --debug (or debug=true), or call /actuator/conditions on a running one. It lists every auto-configuration as "positive matches" or "negative matches" with the exact condition that failed or passed.

The report is split into positive matches (with the reason, for example "@ConditionalOnClass found DataSource"), negative matches ("@ConditionalOnMissingBean found existing bean 'dataSource'"), exclusions, and unconditional classes. Typical findings: a property is spelled differently than the condition expects; a class is missing because the starter is not on the classpath; my own bean of that type already exists and made the default back off; or a @Profile is not active. For one specific bean, /actuator/beans tells me which configuration class created it, and /actuator/env or /actuator/configprops shows the values.

Remember: --debug or /actuator/conditions tells you which condition failed, so never guess.

How would you write your own auto-configuration or starter for a shared company library? Senior

I write a normal @AutoConfiguration class with conditional beans, bind its settings with a @ConfigurationProperties class, and register it in META-INF/spring/...AutoConfiguration.imports. Every bean is @ConditionalOnMissingBean so the app can override it. Then I publish it as a library, and optionally add a thin starter that just depends on it.

@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    AuditClient auditClient(AuditProperties p) {
        return new AuditClient(p.getUrl(), p.getTimeout());
    }
}
// src/main/resources/META-INF/spring/
//   org.springframework.boot.autoconfigure.AutoConfiguration.imports
// contains: com.acme.audit.AuditAutoConfiguration

Good practice: do not rely on component scanning, because the app will not scan my package; use @ConditionalOnProperty for an on/off switch (acme.audit.enabled); add spring-boot-configuration-processor so IDEs autocomplete my properties; test with ApplicationContextRunner, which is fast and needs no full app. Naming: Boot reserves spring-boot-starter-*, so mine is acme-spring-boot-starter. The starter holds no code, only dependencies, and the auto-configuration module holds the beans.

Remember: @AutoConfiguration + conditions + imports file + @ConditionalOnMissingBean on every bean.

4. Configuration, properties and profiles

Where can Boot read properties from, and which source wins? Intermediate

From many places, and the rule is that the more specific, more external source wins. From highest to lowest: test properties, command-line arguments, Java system properties, OS environment variables, profile-specific config files, application.yml or .properties (outside the jar beats inside), then @PropertySource and defaults. So the platform can always override what is packaged in the jar.

That is why one image runs in every environment: the file inside the jar carries safe defaults, and Kubernetes sets environment variables (SPRING_DATASOURCE_URL) that win. Properties are merged by key, so a profile file overrides only the keys it defines. Config files are looked up in classpath:/, the current directory, and /config; extra files can be pulled in with spring.config.import (for example a mounted secrets folder or a config server). If a value looks ignored, it is nearly always a higher source overriding it, and /actuator/env shows which one.

Remember: command line beats env vars, env vars beat files, profile files beat the base file, outside the jar beats inside.

How do profiles work? How do you activate and combine them? Basic

A profile is a named set of configuration, such as dev or prod. I put environment-specific values in application-prod.yml and beans in @Profile("prod") classes, and activate the profile with spring.profiles.active. In deployment I set it as an environment variable: SPRING_PROFILES_ACTIVE=prod.

Profile files override only the keys they define, on top of application.yml. Several profiles can be active at once (prod,eu) and the later one wins when they set the same key. Profile groups (spring.profiles.group.prod=proddb,prodmq) switch on a bundle with one name. @Profile("!prod") means "everything except". In one multi-document YAML file, a section can be limited with spring.config.activate.on-profile. Common mistakes: putting secrets in a committed profile file, creating so many profiles that nobody knows what runs in prod, and forgetting that an active profile can silently switch off a bean (a typical cause of "bean not found" in only one environment). Good practice is few profiles, differences only in values, and logging the active profiles at startup (Boot already does).

Remember: profile = overlay of config and beans. Activate with SPRING_PROFILES_ACTIVE, keep profiles few.

How does @ConfigurationProperties work, and why is it better than @Value? Intermediate

@ConfigurationProperties binds a whole prefix of properties (for example app.mail.*) into a typed class, with nested objects, lists, durations and validation. @Value injects one value at a time as a string expression. For anything beyond one or two settings I prefer @ConfigurationProperties: it is type-safe, grouped in one place, supports relaxed binding and can fail startup if values are wrong.

@ConfigurationProperties("app.mail")
public record MailProperties(String host, int port, Duration timeout, List<String> bcc) {}

// activate: @EnableConfigurationProperties(MailProperties.class)
// or @ConfigurationPropertiesScan on the main class

A record (or a class with a single constructor) uses constructor binding, so the object is immutable; in Boot 3 no extra annotation is needed for that. Types like Duration ("5s"), DataSize ("10MB") and enums convert automatically. @Value still fits a single simple value or a SpEL expression, but it does no relaxed binding of names, has no IDE metadata, and scatters keys around the code, which makes renaming a property painful.

Remember: group settings in a typed @ConfigurationProperties record; use @Value only for one-off values.

How do I make the app fail at startup if a required setting is missing or invalid? Intermediate

I put @Validated on the @ConfigurationProperties class and add Bean Validation constraints such as @NotBlank or @Min. If a value is missing or wrong, binding fails and the app refuses to start with a message naming the property. That is much better than a NullPointerException at 3 a.m. from a value nobody set.

@ConfigurationProperties("app.payment")
@Validated
public record PaymentProperties(
    @NotBlank String apiUrl,
    @Min(1) @Max(10) int retries,
    @DefaultValue("3s") Duration timeout) {}

This needs spring-boot-starter-validation on the classpath. Fail-fast at startup is the goal: a pod with bad config should crash during rollout, not after it receives traffic. Nested objects need @Valid on the field to be checked too. For @Value, a missing key without a default also fails at startup with "Could not resolve placeholder", but a present-yet-wrong value is not validated at all.

Remember: @Validated + constraints on @ConfigurationProperties = bad config stops the deploy, not production.

How do property placeholders and defaults work with @Value? Basic

A placeholder ${key} is replaced with the property value. I give a default after a colon: ${app.timeout:5s}. Without a default, a missing key fails startup with "Could not resolve placeholder". For SpEL expressions I use #{...}.

@Value("${app.region:eu-west-1}") String region;
@Value("${app.hosts:}") List<String> hosts;     // empty default, comma list
@Value("#{systemProperties['user.home']}") String home;

Placeholders also work inside property files (app.url=http://${app.host}:${app.port}), and Boot has a random.* source for tests (${random.uuid}, ${random.int(1000,2000)}). Remember @Value is resolved when the bean is created; it does not update later without a refresh mechanism.

Remember: ${key:default} for properties, #{...} for expressions. No default means fail-fast.

What is relaxed binding? How do property names map to environment variables? Intermediate

Relaxed binding means one property can be written in several styles and still bind to the same field. In files I use kebab-case (my.app.read-timeout); the same value can be set as an environment variable by upper-casing, turning dots into underscores and dropping dashes: MY_APP_READTIMEOUT. That makes it easy to override any property from Kubernetes without editing files.

Rules for environment variables: uppercase, dots become underscores, and dashes are simply removed (so read-timeout becomes READTIMEOUT). A list element uses a number: MY_APP_HOSTS_0=a. This works for @ConfigurationProperties and for known Boot properties. Using @Value("${...}") with an exact key does not get all variants, so prefer kebab-case in files with @ConfigurationProperties. A map key or value that contains a dot or a dash is awkward to set through an environment variable, which is the usual place this trips people up.

Remember: files use kebab-case, env vars use UPPER_SNAKE: spring.datasource.url becomes SPRING_DATASOURCE_URL.

How do you pass configuration and secrets to a Boot app on Kubernetes? Intermediate

Non-secret settings come from a ConfigMap and secrets from a Secret, both exposed to the pod either as environment variables or as mounted files. Boot reads env vars automatically through relaxed binding, and can read a mounted directory with spring.config.import=optional:configtree:/etc/secrets/, where each file name becomes a key and its content the value.

Environment variables are simple but visible in process listings, in crash dumps and /actuator/env (Boot masks values for keys like password and secret by default, and recent versions hide all values unless you opt in). Mounted files are safer and can be updated without a restart of the image, but a running Boot app does not re-read them unless you restart or use a refresh mechanism. Never bake secrets into the image or commit them in application-prod.yml. For stricter needs use a secret manager (Vault, a cloud secret store) through a Spring Cloud integration or a sidecar. Config changes in a ConfigMap require a rollout for env vars to change.

Remember: ConfigMap for settings, Secret for secrets, env var or mounted configtree; secrets never in the image or Git.

How do I find out which value the app is really using, and where it came from? Intermediate

I use the Actuator /actuator/env/<property> endpoint: it shows the final value and every source that defined it, in priority order, with the winning one first. /actuator/configprops shows the bound @ConfigurationProperties objects. If Actuator is not exposed, starting with --debug or logging the property gives a quick check.

This answers the classic "I set it in the ConfigMap and nothing changed": the endpoint shows that a command-line argument or system property is overriding it, or that my variable name was wrong (a typo or a missing underscore), or that the active profile is not the one I thought. Both endpoints are sensitive: they must be secured and are not exposed over HTTP by default. In Boot 3 values are masked by default and you opt in to show them (management.endpoint.env.show-values), which is sensible in production.

Remember: /actuator/env/<key> shows the winner and the losers. Secure it.

5. REST controllers, validation and error handling

What is the difference between @Controller and @RestController, and how does a request reach my method? Basic

@RestController is @Controller plus @ResponseBody: the return value is written straight into the HTTP response (as JSON by default) instead of being treated as a view name. In Boot a request goes through the servlet filters, then the DispatcherServlet, which finds the handler method by URL and HTTP method, converts the input, calls my method, and converts the result back.

In detail: HandlerMapping picks the method from @RequestMapping / @GetMapping rules; argument resolvers fill @PathVariable, @RequestParam and @RequestBody; for @RequestBody an HttpMessageConverter (Jackson) turns the JSON into an object; after my method returns, a converter writes the response. Exceptions are routed to @ExceptionHandler methods. Boot auto-configures all of this when spring-boot-starter-web is present. The full MVC internals are on the Spring Framework page.

Remember: @RestController = @Controller + @ResponseBody. The DispatcherServlet does mapping, conversion and error routing.

@PathVariable, @RequestParam, @RequestBody, @RequestHeader: when do I use each? Basic

@PathVariable is for the identity of a resource in the URL (/orders/42). @RequestParam is for optional filters and paging in the query string (?status=OPEN&page=2). @RequestBody is for the JSON payload of POST, PUT and PATCH. @RequestHeader reads a header such as Authorization or an idempotency key.

@GetMapping("/orders/{id}")
Order get(@PathVariable long id) { ... }

@GetMapping("/orders")
Page<OrderDto> list(@RequestParam(defaultValue = "OPEN") String status, Pageable page) { ... }

@PostMapping("/orders")
ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrder body) { ... }

Details that matter: parameters are required unless I give required = false or a default; a type mismatch (/orders/abc for a long) gives 400; a missing body gives 400; a wrong Content-Type gives 415. A body can be read only once, so do not combine two @RequestBody parameters. Parameter names are bound by name, which works in Boot because the Boot Maven and Gradle plugins compile with -parameters.

Remember: path = which resource, query = filters, body = payload, header = metadata.

How do I return the right HTTP status and headers from a controller? Basic

For the normal case I return the object and annotate the method with @ResponseStatus, or I return ResponseEntity when status or headers depend on the logic. A create returns 201 with a Location header, a delete returns 204, a missing resource gives 404, invalid input 400, a conflict 409.

@PostMapping("/orders")
ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrder in) {
    OrderDto out = service.create(in);
    URI uri = URI.create("/orders/" + out.id());
    return ResponseEntity.created(uri).body(out);          // 201 + Location
}

@DeleteMapping("/orders/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)                     // 204
void delete(@PathVariable long id) { service.delete(id); }

For errors I do not build ResponseEntity by hand in every method. The service throws a domain exception (OrderNotFoundException) and one global handler maps it to 404 (next questions). A common mistake is returning 200 with an error message in the body, or returning null and getting an empty 200. Also use 401 for "not authenticated" and 403 for "authenticated but not allowed", and 422 or 400 for validation failures (be consistent across the API).

Remember: 201 + Location on create, 204 on delete, throw exceptions for errors and map them in one place.

Why not return JPA entities directly from a controller? Intermediate

Because the API contract and the database model should change independently. If I return an entity, any column rename breaks clients, internal fields (password hash, audit columns) leak by accident, and lazy relations can trigger extra queries or a LazyInitializationException during JSON serialisation. So I map entities to small DTOs (records) and accept DTOs in, not entities.

Specific problems with entities as request bodies: mass assignment (a client sends "role":"ADMIN" or "id" and it is bound to the entity), and bidirectional relations that cause infinite recursion in Jackson. A DTO lets me expose exactly the fields I choose, version the API, and attach validation to the input model. Mapping can be done by hand, or with MapStruct to avoid boilerplate. The cost is a bit of mapping code, which is worth it; for simple internal tools some teams accept entities, but then I would at least use @JsonIgnore and open-in-view off.

public record OrderDto(long id, String status, BigDecimal total) {
    static OrderDto from(Order o) { return new OrderDto(o.getId(), o.getStatus().name(), o.getTotal()); }
}

Remember: entity = database shape, DTO = API shape. Never let one leak into the other.

How do you do pagination and sorting in a Boot REST API? Intermediate

With Spring Data I accept a Pageable parameter and return a Page<T>. Boot resolves ?page=0&size=20&sort=createdAt,desc into the Pageable automatically, and the repository turns it into LIMIT/OFFSET plus ORDER BY and a count query.

@GetMapping("/orders")
Page<OrderDto> list(Pageable pageable) {
    return repo.findAll(pageable).map(OrderDto::from);
}

Things to say next: set a maximum page size (spring.data.web.pageable.max-page-size, default 2000) so a client cannot ask for a million rows; whitelist sort fields so clients cannot sort by an unindexed column; return a small response type (content, page, total) rather than the whole Page if I want a stable JSON contract. Offset paging gets slow on deep pages (the database still walks the skipped rows) and can skip or repeat rows when data changes, so for large or fast-changing data I use keyset (seek) pagination: "give me 20 rows after id 5000". Use Slice instead of Page to skip the count query when the total is not needed.

Remember: Pageable in, Page out; cap the size; for deep or live lists use keyset paging.

How do you validate request input in Boot, and what happens when it fails? Basic

I add spring-boot-starter-validation, put constraints like @NotBlank, @Email, @Positive on the DTO fields, and mark the controller parameter with @Valid. If validation fails, Spring throws MethodArgumentNotValidException, which gives a 400 response. I normally catch it in a global handler to return a clean list of field errors.

public record CreateUser(
    @NotBlank @Size(max = 50) String name,
    @Email String email,
    @Min(18) int age) {}

@PostMapping("/users")
ResponseEntity<?> create(@Valid @RequestBody CreateUser in) { ... }

Two classic mistakes: the starter is missing (since Boot 2.3 it is no longer included in the web starter), so nothing is validated and no error is raised; and @Valid is forgotten on the parameter. For nested objects, add @Valid on the nested field too. Validation is only a first line of defence for shape and format: business rules (does this email already exist?) belong in the service layer and the database (unique constraint), because a check-then-insert has a race.

Remember: starter + constraints on the DTO + @Valid on the parameter. Missing starter means silent no-validation.

How do I validate path variables and request parameters, and which exception do I get? Intermediate

For simple parameters I put constraints directly on them, for example @PathVariable @Min(1) long id, and add @Validated on the controller class. A failure throws ConstraintViolationException (a different exception from the body case, which throws MethodArgumentNotValidException). So a good global handler covers both.

@RestController
@Validated                         // needed for parameter-level constraints
class OrderController {
    @GetMapping("/orders/{id}")
    OrderDto get(@PathVariable @Min(1) long id) { ... }
}

Without @Validated on the class, parameter constraints are silently ignored. In newer Spring versions (6.1 and later) built-in method validation can handle this without the class annotation and throws HandlerMethodValidationException, so the exact exception depends on the version; I would say "check which one your version throws, and handle all three in the advice". Rule of thumb: @Valid on a body validates its fields; @Validated on the class enables validation of simple parameters (and groups).

Remember: body fails with MethodArgumentNotValid, plain parameters fail with ConstraintViolation (or HandlerMethodValidation in newer Spring). Handle all.

How do you write a custom validation rule, for example a password or unique-email check? Intermediate

I create my own constraint annotation and a ConstraintValidator class that implements the rule. The validator is a Spring bean-aware class, so it can inject a repository. I use this for format rules (strong password, valid country code) and avoid it for rules that need a race-free guarantee, like uniqueness.

@Target(FIELD) @Retention(RUNTIME)
@Constraint(validatedBy = StrongPasswordValidator.class)
public @interface StrongPassword {
    String message() default "password too weak";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {
    public boolean isValid(String v, ConstraintValidatorContext c) {
        return v != null && v.length() >= 12 && v.chars().anyMatch(Character::isDigit);
    }
}

A uniqueness validator that queries the database looks fine but is not safe: two concurrent requests both pass the check, then both insert. The real guarantee is a unique constraint in the database; the validator only gives a friendlier early message, and the service should still handle DataIntegrityViolationException and return 409. For rules that involve several fields (end date after start date), put a class-level constraint.

Remember: annotation + ConstraintValidator for format rules; uniqueness is guaranteed by the database, not by the validator.

How do you handle exceptions globally in a Boot REST API? Basic

I write one class annotated with @RestControllerAdvice that has @ExceptionHandler methods. Each method maps an exception type to an HTTP status and a consistent JSON error body. Controllers and services just throw domain exceptions and never build error responses themselves.

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ApiError> notFound(OrderNotFoundException e) {
        return ResponseEntity.status(404).body(new ApiError("ORDER_NOT_FOUND", e.getMessage()));
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ApiError> invalid(MethodArgumentNotValidException e) { /* list field errors, 400 */ }
    @ExceptionHandler(Exception.class)
    ResponseEntity<ApiError> unexpected(Exception e) {
        log.error("Unhandled", e);                       // log once, with stack trace
        return ResponseEntity.status(500).body(new ApiError("INTERNAL", "Something went wrong"));
    }
}

Rules I follow: the most specific handler wins; the catch-all handler logs the stack trace but returns a generic message (never leak internals or SQL); client errors (4xx) are logged at low level, server errors (5xx) at error. Extending ResponseEntityExceptionHandler gives me ready-made handlers for Spring's own exceptions (missing parameter, wrong media type, validation) so I only add my domain ones. A @ExceptionHandler inside one controller only covers that controller.

Remember: throw domain exceptions, map them once in @RestControllerAdvice, and never leak internals in the 500.

What is ProblemDetail, and should I use it for error responses? Intermediate

ProblemDetail is Spring's built-in class for the standard "problem details" error format (RFC 7807, updated by RFC 9457). It gives every error the same fields: type, title, status, detail, instance, plus any custom ones. Yes, I would use it, because clients get one predictable error shape and I do not invent my own.

@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail notFound(OrderNotFoundException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    pd.setTitle("Order not found");
    pd.setProperty("orderId", e.getId());          // custom field
    return pd;                                     // content type application/problem+json
}

Support arrived in Spring 6 / Boot 3. Setting spring.mvc.problemdetails.enabled=true makes Spring's own exceptions (validation, 405, 415) render as ProblemDetail automatically. Keep the detail safe for clients, and add a stable machine-readable code (a custom property) so clients do not parse the message text. If clients already depend on an older custom error format, change it with a versioned API, not silently.

Remember: ProblemDetail = the standard error body (application/problem+json). One shape for all errors.

What is the /error endpoint and BasicErrorController? Intermediate

It is Boot's fallback for errors that nobody handled. When an exception escapes the controllers, or a request has no handler (404), the servlet container forwards to /error, where BasicErrorController produces a JSON body (timestamp, status, error, path) for API clients or the "Whitelabel Error Page" for browsers.

Two things matter in practice. First, a @RestControllerAdvice handles exceptions thrown by controllers before they reach /error, but errors that happen outside the MVC layer (a 404 for an unknown URL, a failure in a filter) still use the fallback unless I handle them. Second, the default body can leak details: server.error.include-message, include-stacktrace and include-binding-errors default to "never", and I keep them that way in production. To customise the output I can provide my own ErrorAttributes bean, or enable ProblemDetail so fallback errors use the same format as my handlers.

Remember: /error is the safety net for unhandled errors. Keep message and stack trace off in production.

How is Jackson configured in Boot, and what are the usual JSON problems? Intermediate

Boot auto-configures one shared ObjectMapper with sensible defaults, and I tune it through spring.jackson.* properties or a Jackson2ObjectMapperBuilderCustomizer rather than creating my own mapper. Boot's defaults include ignoring unknown JSON properties and writing dates as ISO strings, not numbers.

Frequent problems: a date field coming out as [2025,1,15] or a number (the Java time module is missing, or write-dates-as-timestamps is on; Boot normally handles it, so a hand-built new ObjectMapper() is the usual culprit); a failure for an unknown field (the default for a plain Jackson mapper, but Boot turns it off); infinite recursion on two-way entity relations (use DTOs); money as double (use BigDecimal, and consider sending it as a string). Common properties: spring.jackson.default-property-inclusion=non_null, spring.jackson.property-naming-strategy=SNAKE_CASE, spring.jackson.time-zone=UTC. Always inject the Boot mapper (ObjectMapper bean) instead of calling new ObjectMapper(), so the same rules apply everywhere. In Boot 4 the Jackson major version changes, so check the migration notes there.

Remember: inject Boot's ObjectMapper, tune with spring.jackson.* or a customizer, never `new ObjectMapper()`.

How do I call another service from Boot, and what are the traps with timeouts? Intermediate

In Boot 3.2 and later I use RestClient (blocking, fluent) built from the auto-configured RestClient.Builder; WebClient is for reactive code and RestTemplate is in maintenance mode. The main trap is timeouts: by default there are none, so one slow downstream can hold all my threads.

@Bean
RestClient inventory(RestClient.Builder b) {
    var f = ClientHttpRequestFactoryBuilder.detect().build(
        ClientHttpRequestFactorySettings.defaults()
            .withConnectTimeout(Duration.ofSeconds(1))
            .withReadTimeout(Duration.ofSeconds(3)));
    return b.baseUrl("http://inventory").requestFactory(f).build();
}

Rules: always set a connect and a read timeout (in 3.4 and later there are also spring.http.client.* properties for this); inject the Boot builder so metrics, tracing and message converters are applied; retry only idempotent calls, with backoff, never on a 4xx; add a circuit breaker (Resilience4j) when a failing dependency can take the whole service down. Wrapped exceptions like HttpClientErrorException expose the status, so translate them into my domain exceptions at one boundary. For declarative clients, @HttpExchange interfaces work on top of RestClient.

Remember: RestClient from the Boot builder, always a timeout, retry only idempotent calls.

What does Boot do for security by default, and how do I configure my own rules? Intermediate

As soon as spring-boot-starter-security is on the classpath, Boot protects every endpoint with HTTP basic and a form login, using a generated password printed in the log. To configure real rules I define a SecurityFilterChain bean. The old WebSecurityConfigurerAdapter was removed in Spring Security 6 (Boot 3).

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())                      // stateless token API only
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .build();
}

Notes: rules are checked in order, first match wins, so put specific rules first and anyRequest() last. Disable CSRF only for stateless APIs with a token in a header, not for browser sessions with cookies. Because security is auto-configured, merely adding a library that brings the security starter transitively can suddenly make every endpoint return 401, which is a classic surprise. Authentication internals and method security (@PreAuthorize) are covered on the Spring Framework page.

Remember: add the starter and everything is locked; define a SecurityFilterChain bean to set your own rules.

6. Data access configuration

How does Boot configure a DataSource, and what happens if there is no URL? Basic

If a JDBC driver is on the classpath, Boot creates a DataSource from spring.datasource.url, username and password, and picks the connection pool it finds, HikariCP by default. Only for an embedded database (H2, HSQL, Derby) can it work without a URL. For anything else, a missing URL fails startup with "Failed to configure a DataSource: 'url' attribute is not specified".

The failure often surprises people who never wanted a database: a library brought spring-jdbc or a JPA starter transitively, so Boot tried to set one up. Fix it by removing the dependency, or by excluding DataSourceAutoConfiguration. The driver class is detected from the URL, so driver-class-name is rarely needed. Pool settings live under spring.datasource.hikari.*. Boot also wires JdbcTemplate, the transaction manager and (with JPA) the EntityManagerFactory on top of this one DataSource. If I define my own DataSource bean, the default backs off.

Remember: JDBC on classpath + no URL = startup failure, unless it is an embedded DB. Unwanted? Remove the dependency or exclude it.

How do you size and tune HikariCP? What are the key settings? Senior

I keep the pool small, because the database can only do so much in parallel. The default maximum-pool-size is 10 and it is often enough. A good starting rule is roughly (number of DB cores x 2) plus the disk spindles, then I measure. Raising the pool to hundreds usually makes the database slower, not faster. Multiply by the number of pods: 20 pods x 10 connections is already 200 connections on the database.

The settings I know: maximum-pool-size (10), minimum-idle (same as max by default, so a fixed-size pool), connection-timeout (30 s: how long a caller waits for a free connection before the exception), max-lifetime (30 min: must be shorter than any firewall or database idle timeout), idle-timeout (10 min, used only if minimum-idle is lower), leak-detection-threshold (log a stack trace when a connection is held longer than this). When the pool is exhausted the cause is usually not "pool too small" but someone holding a connection too long: a slow query, a transaction that includes an HTTP call, or a leak.

Remember: small pool x number of pods must fit the database. Exhaustion means find who holds connections, before you raise the maximum.

Which JPA and Hibernate properties matter in a Boot app, especially ddl-auto? Intermediate

The important one is spring.jpa.hibernate.ddl-auto. For embedded databases Boot defaults to create-drop, for real databases to none. In production I use none or validate and manage the schema with Flyway or Liquibase. update is tempting but unsafe: it only adds, never drops or renames, and can run unreviewed changes against production.

  • spring.jpa.show-sql / org.hibernate.SQL logger: see the SQL. Use the logger in dev, not in production (noisy).
  • spring.jpa.open-in-view: default true, I turn it off (next question).
  • spring.jpa.properties.hibernate.jdbc.batch_size plus order_inserts: needed for real JDBC batching of inserts.
  • spring.jpa.properties.hibernate.default_batch_fetch_size: softens N+1 on lazy collections.
  • spring.jpa.hibernate.naming.physical-strategy: Boot uses snake_case column names by default (firstName becomes first_name).

Hibernate itself (N+1, lazy loading, fetch joins, locking) is covered on the Hibernate and JPA page.

Remember: production ddl-auto = none or validate; schema changes go through migrations.

What is open-in-view, and why do people turn it off? Intermediate

Open Session in View keeps the JPA EntityManager (and its database connection) open for the whole web request, until the response is written. That lets lazy relations load in the controller or during JSON serialisation without error. It is on by default in Boot (with a warning at startup), and I turn it off with spring.jpa.open-in-view=false.

Why off: a database connection is held for the full request, including time spent calling other services or rendering the response, so under load the pool runs dry. It also hides N+1 queries, because lazy loading happens quietly in the web layer, and it blurs the layer boundary: queries run from places that are not transactional. With it off, accessing a lazy field outside the transaction throws LazyInitializationException. That is a good thing: it forces me to load what I need in the service (fetch join, entity graph, or a DTO projection) and return DTOs. So: off, load explicitly in the service, return DTOs.

Remember: open-in-view holds a connection for the whole request and hides N+1. Turn it off, fetch in the service.

How do Flyway and Liquibase work with Boot, and what goes wrong? Intermediate

Add the Flyway or Liquibase dependency and Boot runs the migrations automatically at startup, before the JPA layer uses the schema. Each migration runs once, in order, and the tool records it in a history table (flyway_schema_history). Flyway migrations are versioned SQL files such as db/migration/V3__add_index.sql.

What goes wrong: editing a migration that was already applied gives a "checksum mismatch" error, because the tool compares the stored hash with the file. The rule is that applied migrations are immutable: add a new one (V4) that fixes things. Two developers both adding V5 on different branches causes a clash, so teams use timestamps or agree an order. With several pods starting at once, Flyway takes a lock so only one migrates. Long, locking migrations on a big table can block the application during deploy, so for large tables use an expand-and-contract approach (add column, deploy, backfill, switch, drop later). Rolling back means a new forward migration. Use validate for Hibernate so a mismatch between entities and the schema is caught at startup.

Remember: never edit an applied migration. Fix forward with a new version.

How do you use two databases in one Boot app? Senior

Boot only auto-configures one DataSource, so for two databases I define both myself: two DataSource beans (one marked @Primary), and for JPA a separate EntityManagerFactory and transaction manager each. Then each set of repositories is pointed at its own factory with @EnableJpaRepositories and its own package.

@Configuration
@EnableJpaRepositories(basePackages = "com.acme.orders",
    entityManagerFactoryRef = "ordersEmf", transactionManagerRef = "ordersTx")
class OrdersDbConfig {
    @Bean @Primary @ConfigurationProperties("app.orders.datasource")
    DataSource ordersDataSource() { return DataSourceBuilder.create().build(); }
    // ordersEmf and ordersTx built from it; same pattern for the second DB
}

Pitfalls: @Transactional uses the primary transaction manager unless I name another (@Transactional("ordersTx")); there is no transaction across two databases, so a cross-DB update can leave them out of sync (use an outbox or a saga, not a hand-made two-phase commit); the entity packages must be separated; and when I define my own DataSource Boot's properties under spring.datasource.* no longer apply, so I bind my own prefix. For plain reads, a read replica is usually a routing DataSource instead.

Remember: two DBs = two of everything (DataSource, EMF, tx manager), one @Primary, and no shared transaction.

7. Actuator, logging and observability

How does logging work in Boot, and how do you configure it? Basic

Boot logs through SLF4J with Logback as the default implementation, so my code uses LoggerFactory.getLogger(...) or Lombok's @Slf4j. The default level is INFO to the console. I set levels in properties, for example logging.level.com.acme=DEBUG or logging.level.org.hibernate.SQL=DEBUG, and for anything more I add logback-spring.xml.

Use the name logback-spring.xml, not logback.xml: the -spring variant is processed by Boot after the environment is ready, so it can use <springProfile> blocks and Spring properties. In containers I log to the console (stdout), as one line per event, and let the platform collect it, not write rotating files. Since Boot 3.4 there is built-in structured logging (logging.structured.format.console=ecs or logstash) for JSON output without extra libraries; on older versions use a Logback JSON encoder. Log levels can be changed at runtime through /actuator/loggers (secure it). For correlation, put a trace id in the log pattern (with Micrometer Tracing it is added to the MDC automatically) so one request can be followed across services.

Remember: SLF4J + Logback, levels in properties, logback-spring.xml for more, JSON to stdout in containers.

What is Actuator, and which endpoints matter most? Basic

Actuator adds production endpoints to the app: health, metrics, info, loggers, environment and more, under /actuator. I add spring-boot-starter-actuator. Over HTTP only health is exposed by default; others must be listed in management.endpoints.web.exposure.include.

  • health (and health/liveness, health/readiness): status for the load balancer and Kubernetes.
  • metrics and prometheus: numbers for dashboards and alerts.
  • loggers: read and change log levels at runtime.
  • info: build and git details (version, commit).
  • env, configprops, beans, conditions, mappings: what the context really contains. Useful for debugging.
  • threaddump, heapdump: diagnosis; heapdump contains secrets from memory.

Keep actuator on a separate management port (management.server.port) that is not exposed through the public ingress, and expose only what I need. See the cheat sheet for the full table.

Remember: only /health is public by default. Expose the minimum, secure the rest.

How do you secure Actuator endpoints? Intermediate

Three layers: expose only the endpoints I need, move them to a separate management port that the public ingress does not route, and require authentication (with an admin role) for anything sensitive. Health and the probes may stay open to the platform; env, heapdump, loggers and threaddump must never be public.

management:
  server.port: 9090                          # not routed by the public ingress
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health.show-details: when_authorized

// Security: restrict the rest
.requestMatchers(EndpointRequest.to("health", "info")).permitAll()
.requestMatchers(EndpointRequest.toAnyEndpoint()).hasRole("OPS")

Why it matters: /actuator/env and /configprops can reveal connection strings (values are masked by default in Boot 3, but do not rely on that), heapdump hands over everything in memory including tokens, and loggers with write access can be used to flood logs. Real-world data leaks often come from an exposed heapdump or env. Network policy helps too: only the monitoring system can reach the management port.

Remember: minimum exposure + separate port + auth. Never expose heapdump or env publicly.

How does the health endpoint work, and how do you write a custom health indicator? Intermediate

The health endpoint asks every HealthIndicator bean (database, disk, Redis, Kafka and so on, auto-detected from the classpath) and combines the results into one status: the worst one wins (DOWN beats UP). To add my own, I implement HealthIndicator or extend AbstractHealthIndicator, and the bean name becomes the key in the output.

@Component
class PaymentGatewayHealth implements HealthIndicator {
    public Health health() {
        try {
            gateway.ping();                       // must be fast, with a timeout
            return Health.up().withDetail("latencyMs", 12).build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}

Important judgment: a health check runs often and on a request thread, so it must be fast and have a timeout. Do not put every downstream dependency into the health that Kubernetes uses for liveness: if the database is down, restarting every pod does not help. Use groups to decide which indicators feed which probe (management.endpoint.health.group.readiness.include=db). By default details are hidden; show-details: when_authorized reveals them to logged-in users.

Remember: worst status wins. Keep checks fast, and choose carefully what feeds liveness versus readiness.

What are liveness and readiness probes in Boot, and how do they map to Kubernetes? Senior

Liveness answers "is the process stuck beyond repair, should Kubernetes restart it?". Readiness answers "can this pod take traffic right now?". Boot exposes both as /actuator/health/liveness and /actuator/health/readiness (enabled automatically on Kubernetes). A failing readiness removes the pod from the Service; a failing liveness restarts the container.

The key rule: liveness must not depend on external systems. If it checks the database and the database goes down, every pod fails liveness and is restarted together, which makes the recovery slower (a restart storm). Readiness may include dependencies that the pod truly needs, but be careful with shared ones for the same reason: all pods become unready at once and the service has zero endpoints. Boot flips readiness to REFUSING_TRAFFIC during graceful shutdown, so the load balancer stops sending new requests while in-flight ones finish. Use a startup probe for slow starts, so liveness does not kill a pod that is still booting. Typical settings: startupProbe with a generous failureThreshold, readiness every 5 to 10 s, liveness with a longer period.

Remember: readiness failing = pause traffic, liveness failing = restart. Never put shared dependencies in liveness.

What is Micrometer, and how do metrics reach Prometheus? Intermediate

Micrometer is the metrics facade of Boot, like SLF4J for metrics: my code records counters, timers and gauges once, and a registry for the chosen backend exports them. For Prometheus I add micrometer-registry-prometheus, expose /actuator/prometheus, and Prometheus scrapes (pulls) that URL every 15 to 30 seconds.

Boot already records a lot without code: JVM memory, GC, threads, CPU, HTTP server request timings (http.server.requests), Hikari pool, cache and Kafka metrics. The ones I alert on: HTTP error rate and p95 or p99 latency, pool usage (hikaricp.connections.active/pending), JVM heap and GC pause, thread counts. Percentiles and histograms are opt-in (management.metrics.distribution.percentiles-histogram.http.server.requests=true). Add common tags such as the application name with management.metrics.tags.application=orders so dashboards can filter. Prometheus is pull-based, so short-lived batch jobs need a push gateway.

Remember: Micrometer records, a registry exports, Prometheus scrapes /actuator/prometheus.

How do you add a custom business metric, and what is "cardinality"? Intermediate

I inject the MeterRegistry and create a counter, timer or gauge with a name and a few tags. Cardinality is the number of distinct tag-value combinations: each combination is a separate time series stored by the metrics system, so a tag with unbounded values (user id, order id, URL with ids) can blow up memory and cost.

@Service
class OrderService {
    private final Counter placed;
    private final Timer payTimer;
    OrderService(MeterRegistry r) {
        placed = Counter.builder("orders.placed").tag("channel", "web").register(r);
        payTimer = Timer.builder("orders.payment").publishPercentileHistogram().register(r);
    }
    void place(Order o) { payTimer.record(() -> pay(o)); placed.increment(); }
}

Rules: tags must be a small fixed set (status, channel, region), never ids or free text; count events with counters, measure durations with timers, current values (queue size) with gauges; name with dots (orders.placed), and the Prometheus registry converts to orders_placed_total. Use @Timed or the Observation API when I want a metric plus a trace span from one instrumentation point. A tag like userId with a million values is the classic mistake that takes down a Prometheus server.

Remember: few, bounded tag values. High-cardinality tags (ids) kill the metrics backend.

How does distributed tracing work in Boot 3? Senior

Spring Cloud Sleuth is gone in Boot 3; tracing is now Micrometer Tracing with a bridge to OpenTelemetry (or Brave). A request gets a trace id when it enters the system, each unit of work is a span with its own id, and the ids travel to the next service in HTTP headers (W3C traceparent). The ids are also put in the log context, so I can search all logs for one request.

To use it I add micrometer-tracing-bridge-otel plus an exporter (OTLP) and set management.tracing.sampling.probability (default 0.1, meaning 10 percent of requests; use 1.0 in dev). Propagation works automatically when I call other services with the Boot-provided RestClient.Builder, RestTemplateBuilder or WebClient.Builder, but it does not survive a plain new RestTemplate(), and it is lost across threads unless the executor is context-aware. For messaging, the trace context rides in Kafka record headers when the observation support is enabled. The practical value: a slow request is found by trace id, and the span tree shows which downstream call cost the time.

Remember: trace id travels in headers, spans form the tree, sampling is 10 percent by default. Use Boot's builders so propagation works.

8. Testing Boot applications

What does @SpringBootTest do, and what are its web environment modes? Basic

@SpringBootTest starts the full application context, with auto-configuration and all my beans, so I can test components wired together. By default (MOCK) there is no real server: MockMvc is used. With RANDOM_PORT it starts a real embedded server on a free port, and I call it with TestRestTemplate or WebTestClient.

The four modes: MOCK (default, mock servlet environment), RANDOM_PORT (real server, free port), DEFINED_PORT (the configured port, rarely wanted) and NONE (no web environment). The full context is slow to start, so I use it for a few end-to-end tests, not for every class. Properties can be overridden per test: @SpringBootTest(properties = "app.feature=true") or @TestPropertySource, and profiles with @ActiveProfiles("test"). @Transactional on a test rolls back after the test, but with RANDOM_PORT the server runs on another thread, so that rollback does not cover what the server did.

Remember: full context = slow. Few @SpringBootTest, many unit tests and slices.

What are test slices? Name the main ones. Intermediate

A slice test loads only the part of the application one layer needs, so it starts in a second or two instead of loading everything. The main ones: @WebMvcTest (controllers, with MockMvc), @DataJpaTest (repositories and an in-memory or container database), @JsonTest (serialisation), @RestClientTest (a client with a mock server), and @DataJdbcTest.

Each slice applies only the auto-configurations for its layer and scans only matching beans (a @WebMvcTest sees controllers, advice and filters but not services or repositories). Missing collaborators are provided with @MockitoBean. The benefit is speed and focus: a controller test checks mapping, validation and error codes without a database. The trap is a slice that fails with "no qualifying bean" because a service the controller needs was not loaded: mock it. Another trap is custom configuration with @Configuration on the main class, which leaks into every slice and slows them; keep the main class clean.

Remember: slice = one layer's auto-configuration only. Mock what that layer calls.

How do you test a controller with @WebMvcTest and MockMvc? Intermediate

I use @WebMvcTest(OrderController.class), inject MockMvc, mock the service with @MockitoBean, and send fake requests. I assert on status, headers and JSON. It tests URL mapping, validation, serialisation and error handling without a server or database.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test void returns404WhenMissing() throws Exception {
        when(service.find(42L)).thenThrow(new OrderNotFoundException(42L));
        mvc.perform(get("/orders/42"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.code").value("ORDER_NOT_FOUND"));
    }

    @Test void rejectsInvalidBody() throws Exception {
        mvc.perform(post("/orders").contentType(APPLICATION_JSON).content("{}"))
           .andExpect(status().isBadRequest());
    }
}

If Spring Security is on the classpath, requests return 401 unless I add @WithMockUser or a security test configuration, which is the most common reason a fresh controller test "fails". Methods that return the same JSON must be checked in a field-by-field way (jsonPath or JSONAssert), not by comparing raw strings.

Remember: @WebMvcTest + MockMvc + @MockitoBean for the service; add @WithMockUser when security is present.

What does @DataJpaTest do, and why should I not rely on H2 alone? Intermediate

@DataJpaTest starts only the JPA layer: entities, repositories and a DataSource, each test in a transaction that is rolled back at the end. By default it swaps my database for an embedded one (H2). I prefer running it against the same database engine as production using Testcontainers, because H2 behaves differently.

H2 differs from PostgreSQL or MySQL in SQL dialect, JSON and array types, locking, case sensitivity, and function names, so a test can pass on H2 and fail in production, or the reverse. With H2 in "mode" settings it is closer but never the same. Native queries, migrations and constraints are exactly what I want to test on the real engine. To keep the real database, add @AutoConfigureTestDatabase(replace = NONE) and a container:

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class OrderRepositoryTest {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");
    @Autowired OrderRepository repo;
}

Remember the test transaction rolls back, so it hides problems that appear only on commit (such as a deferred constraint), and a flush is needed to force the SQL to run.

Remember: @DataJpaTest = JPA layer in a rolled-back transaction. Use the real DB engine via Testcontainers.

@MockBean versus @MockitoBean: what is the difference? Intermediate

They do the same job: replace a bean in the Spring test context with a Mockito mock (or spy). @MockBean and @SpyBean are Boot annotations that were deprecated in Boot 3.4. @MockitoBean and @MockitoSpyBean come from Spring Framework 6.2 and are the recommended replacement. For new code I use the new ones.

Both change the context definition, which has a cost: each different combination of mocks creates a new cached context, so sprinkling different mocks across many test classes makes the suite slow (next question). The older annotation was tied to Boot's test module; the new one lives in the core test framework, so it works the same in plain Spring tests and can be placed on test fields and on configuration classes. Use a real bean wherever it is cheap (an in-memory fake), and mock only the boundaries: remote clients, clocks, slow dependencies. Mocking everything makes tests that pass while production breaks.

Remember: @MockitoBean is the new @MockBean (Boot 3.4+). Each distinct mock set creates another context.

How do you use Testcontainers in a Boot test? What is @ServiceConnection? Senior

Testcontainers starts a real database, broker or cache in Docker for the test, so I test against the real thing. @ServiceConnection (Boot 3.1+) connects the app to the container automatically: Boot reads the container's host and port and configures the DataSource or Kafka client, so I no longer write @DynamicPropertySource boilerplate.

@SpringBootTest
@Testcontainers
class OrderFlowIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");
    // Boot sets spring.datasource.url/username/password from the container
}

For older versions (or unsupported services) use @DynamicPropertySource to register the URL. To keep the suite fast: make the container static so one container serves the whole class; share one container across classes with a singleton base class or reusable containers; and keep Docker available in CI (a Docker-in-Docker or remote Docker host is a common CI problem). Boot 3.1 also lets me run an application locally with the same containers via SpringApplication.from(App::main).with(ContainersConfig.class).

Remember: static container + @ServiceConnection = real DB in tests with no manual property wiring.

Why does our Boot test suite take 20 minutes, and how do you speed it up? Senior

Almost always because many tests each start a new Spring context. Spring caches a context and reuses it for tests with the same configuration, but any difference (a different mock, property, profile, or @DirtiesContext) makes a new one. I speed up by making configurations identical across tests, using slices instead of full contexts, and testing logic as plain unit tests.

What creates a new context: a different set of @MockitoBeans, different @TestPropertySource or @ActiveProfiles, @DirtiesContext (throws the cache away, use rarely), and different web environment. Practical steps: move business logic tests out of Spring entirely (JUnit + Mockito, milliseconds); use one shared abstract base class with the same annotations for integration tests; use slices for controllers and repositories; share Testcontainers; run test classes in parallel only if they are isolated; and watch the log for repeated "Started ... in x seconds" lines to count contexts. Also avoid sleeping in tests: use Awaitility.

Remember: same configuration = cached context. Different mocks or properties = new, slow context.

9. Server, threads and background work

How does the embedded server work, and how do you switch from Tomcat to Jetty or Undertow? Basic

The web starter includes Tomcat as a library. Boot creates the server inside my application's process, registers the DispatcherServlet, and starts listening on server.port (8080). There is no external server to install, so deployment is "run the jar". To switch, I exclude the Tomcat starter from spring-boot-starter-web and add spring-boot-starter-jetty (or Undertow).

<dependency>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions><exclusion>
    <artifactId>spring-boot-starter-tomcat</artifactId>
  </exclusion></exclusions>
</dependency>
<dependency><artifactId>spring-boot-starter-jetty</artifactId></dependency>

Reasons to switch are rare: a team standard, or a specific feature. Tomcat is the best-known and the default, so I switch only for a clear reason. Server settings are in server.* properties (server.port, server.compression.enabled, server.servlet.context-path, server.tomcat.*). Setting server.port=0 picks a random free port, useful in tests. Undertow support has changed between Boot versions (it was not compatible with newer Servlet APIs), so check that your Boot version supports it before choosing it.

Remember: the server is just a library inside the jar. Switch by excluding Tomcat and adding another starter.

How does Tomcat handle a request, and which settings control capacity? Intermediate

Tomcat uses a worker thread pool: one thread handles one request from start to finish, and blocks while waiting for the database or another service. The default maximum is 200 threads (server.tomcat.threads.max). When all 200 are busy, new connections wait in the accept queue (accept-count, 100), and beyond that they are refused.

The settings I know: threads.max (200), threads.min-spare (10), max-connections (8192: connections Tomcat holds open), accept-count (100), connection-timeout (20 s), and for body size server.tomcat.max-http-form-post-size and spring.servlet.multipart.max-file-size. The key insight is that the smallest limit in the chain decides throughput. 200 request threads sharing a 10-connection Hikari pool means most threads just wait for a connection. More threads do not help if the bottleneck is the database; they only add memory (each thread has a stack, about 1 MB reserved) and context switching. Tune from measurements: if threads are saturated while CPU is low, requests are blocked on I/O and the fix is shorter downstream calls, timeouts, or virtual threads, not 2000 threads.

Remember: one request = one thread. The narrowest limit in the chain (often the DB pool) decides throughput.

What are virtual threads, and how do you use them in Boot? Senior

Virtual threads (Java 21) are very cheap threads managed by the JVM: when one blocks on I/O, the JVM parks it and lets the OS thread (the carrier) run something else. In Boot 3.2 and later with Java 21 I turn them on with spring.threads.virtual.enabled=true, and Tomcat then handles each request on a virtual thread, so blocking code scales without the 200-thread ceiling.

What they do not do: make the database or downstream services faster. The limit moves from thread count to the DB pool and remote capacity, so keep pool sizes, rate limits and timeouts, otherwise a flood of virtual threads overwhelms the database. Known risks: synchronized blocks that hold a lock while doing I/O can pin the carrier thread (improved in Java 24, so check your JDK), long CPU-bound work gets no benefit, and ThreadLocal-heavy code uses more memory with millions of threads. If the service stops responding with idle CPU after switching, suspect pinning or an exhausted pool that is now being hit by many more concurrent requests. Benefits are largest for I/O-heavy services that call several others.

Remember: virtual threads remove the thread ceiling, not the DB or downstream ceilings. Keep pools and timeouts.

Spring MVC or WebFlux in a Boot app: how do you choose? Intermediate

I choose MVC by default: simple blocking code, easy to debug, and the whole ecosystem (JPA, JDBC) is blocking anyway. I choose WebFlux when the service is mostly I/O waiting with a very high number of concurrent connections (streaming, gateways, server-sent events) and the whole stack, including the database driver, can be non-blocking. With virtual threads in Java 21, MVC covers most of the cases where people used to pick WebFlux.

WebFlux uses a few event-loop threads and reactive types (Mono, Flux). The cost is a steeper learning curve, harder stack traces, and the risk that one blocking call on an event-loop thread stalls everything. It only helps if everything is non-blocking end to end (R2DBC instead of JDBC, WebClient). If a team mixes blocking JPA inside WebFlux, they get the complexity without the benefit. Boot decides the web type from the classpath: if both are present, MVC wins, unless I set spring.main.web-application-type.

Remember: MVC (plus virtual threads) by default; WebFlux only when the whole chain is non-blocking and you need huge concurrency or streaming.

How does caching work in Boot, and what can go wrong? Intermediate

I add @EnableCaching, annotate methods with @Cacheable, @CacheEvict and @CachePut, and Boot picks a cache provider from the classpath (Caffeine, Redis, or a simple in-memory map if nothing else). The result of the method is stored under a key built from the arguments, and a later call with the same arguments returns the stored value without running the method.

@Cacheable(cacheNames = "products", key = "#id")
public Product find(long id) { ... }

@CacheEvict(cacheNames = "products", key = "#p.id")
public void update(Product p) { ... }

Things that go wrong: the default in-memory map has no size limit or expiry, so use Caffeine (maximumSize, expireAfterWrite) or Redis with a TTL; caching works through a proxy, so a call from another method of the same class (self-invocation) bypasses it; objects must be serialisable for Redis; a mutable cached object can be changed by one caller and seen by all; and with several pods a local cache gives stale data per pod, so use Redis or accept short TTLs. Also, cached null results and "cache stampede" (many requests rebuilding the same expired key) need thought. Always decide what invalidates the entry.

Remember: proxy-based, so no self-invocation. Always set size and TTL, and plan invalidation.

How does @Scheduled work, and what are the traps in a multi-instance deployment? Intermediate

With @EnableScheduling, a method annotated @Scheduled(cron = "..."), fixedRate or fixedDelay runs on a scheduler thread. Two traps: the default scheduler has one thread, so a slow job delays all others; and every pod runs its own copy, so in a three-pod deployment the job runs three times.

Fix the first with spring.task.scheduling.pool.size. For the second, make the job run once: use a distributed lock (ShedLock, which stores a lock row in the database or Redis), a Kubernetes CronJob that runs separately from the web pods, or leader election. Whichever I choose, the job must also be idempotent (safe to run twice), because a lock can expire or a pod can die midway. Other points: fixedRate starts every N ms regardless of the last run, fixedDelay waits N ms after the last run finished; cron uses the server time zone unless I set zone; exceptions are logged and the schedule continues; and for long work, hand it to an executor so the scheduler thread is free. For heavy or critical batch processing, Spring Batch or a dedicated job is better than @Scheduled.

Remember: one scheduler thread by default, and one run per pod. Use ShedLock or a CronJob, and make jobs idempotent.

What does @Async do in Boot, and what executor does it use? Intermediate

With @EnableAsync, a method annotated @Async runs on another thread, and the caller returns immediately (void, or a CompletableFuture for the result). Boot auto-configures a ThreadPoolTaskExecutor for it, with 8 core threads and an unbounded queue by default; I tune it with spring.task.execution.pool.*.

Traps: it works through a proxy, so self-invocation and non-public methods are not async. An unbounded queue means that under overload the work piles up in memory silently, so I set a queue capacity and a rejection policy, and name the threads (spring.task.execution.thread-name-prefix) to read thread dumps. Exceptions in a void method vanish unless I register an AsyncUncaughtExceptionHandler. Context such as the security principal, MDC logging data, and transactions do not move to the new thread automatically (a TaskDecorator can copy them). And if the work must not be lost (send an invoice), a thread pool is not enough: a crash loses queued tasks, so use a message queue or an outbox table.

Remember: @Async = proxy + thread pool. Bound the queue, handle exceptions, and use a real queue for work you cannot lose.

10. Packaging, containers and shutdown

What is a "fat jar" (executable jar), and how is it different from a normal jar? Basic

A fat jar contains my compiled classes and all dependency jars nested inside one file, plus Boot's launcher, so java -jar app.jar just works. A normal jar has only my classes and needs a classpath for the rest. The Maven or Gradle Boot plugin builds it in the repackage step.

Java cannot load jars nested inside a jar by default, so Boot ships its own class loader (JarLauncher) that does it. The manifest's Main-Class points at the launcher, which then starts my Start-Class. For containers a fat jar has a downside: any code change makes a new multi-megabyte layer, so Docker cannot reuse the dependency layer. The fix is the layered jar (next question). A fat jar also differs from a WAR: Boot can still build a WAR for an external server, but the embedded server style is the standard.

Remember: fat jar = my classes + dependency jars + launcher. Great for running, poor for Docker layer caching unless layered.

How do you build a good Docker image for a Boot app? Intermediate

I use the layered jar so that dependencies (large, rarely changing) and my code (small, changes every build) go into separate image layers; Docker reuses the cached dependency layers and only pushes the tiny application layer. Alternatively ./mvnw spring-boot:build-image builds an optimised image with Cloud Native Buildpacks, no Dockerfile needed.

FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY app.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/extracted/dependencies/ ./
COPY --from=builder /app/extracted/spring-boot-loader/ ./
COPY --from=builder /app/extracted/snapshot-dependencies/ ./
COPY --from=builder /app/extracted/application/ ./
USER 1000
ENTRYPOINT ["java", "-jar", "app.jar"]

Good practice: a JRE-only base image (smaller), a non-root user, put the layers from least to most changing, no secrets in the image, a pinned base image version, and container-aware JVM settings. The layer tool is -Djarmode=tools from Boot 3.3 (earlier versions used -Djarmode=layertools), so adjust to your version.

Remember: layer by change frequency: dependencies low, your code on top. Run as non-root.

How do you set JVM memory and CPU for a Boot app in a container? Senior

Modern JVMs read the container limits, so I set the container memory limit and tell the JVM what share to use: -XX:MaxRAMPercentage=75 instead of a fixed -Xmx. I leave room outside the heap, because the JVM also uses memory for metaspace, thread stacks, direct buffers and code cache. If I give the heap 100 percent, the pod is killed with exit code 137 (OOMKilled) even though Java reported no OutOfMemoryError.

Rules of thumb: heap at 60 to 75 percent of the limit; set requests close to limits for memory (memory is not compressible, CPU is); be careful with CPU limits, because a low limit throttles the JVM (GC and JIT threads included), which shows up as high latency and slow start with low reported CPU usage. Use at least 1 full CPU for a normal service and check the throttling metric. The JVM sizes its GC and thread pools from the visible CPU count, so a 0.5 CPU limit may select a single-threaded GC. Check with -XX:+PrintFlagsFinal or the actuator metrics jvm.memory.*, and start by setting -XX:+ExitOnOutOfMemoryError so a real OOM restarts the pod cleanly.

Remember: MaxRAMPercentage ~75, leave non-heap room, and watch CPU throttling. Exit 137 = killed by the container limit.

How does graceful shutdown work in Boot, and how does it fit with Kubernetes? Senior

With server.shutdown=graceful, on SIGTERM Boot stops accepting new requests, lets in-flight requests finish for up to spring.lifecycle.timeout-per-shutdown-phase (30 s default), and then closes the context. Without it the server stops immediately and running requests are cut. The default is immediate, so I must turn graceful on.

Kubernetes adds a race: when a pod is deleted, it is removed from the Service endpoints and sent SIGTERM at about the same time, but endpoint removal takes a moment to reach every proxy, so traffic can still arrive after SIGTERM. That produces the few 502 or 503 errors at each deploy. The fix is a preStop sleep of 5 to 10 seconds so the pod keeps serving while endpoints update, then the graceful drain. Also, terminationGracePeriodSeconds must be longer than preStop plus the drain timeout, or Kubernetes sends SIGKILL in the middle of a request. Background work (consumers, schedulers) must also stop cleanly, and requests longer than the timeout are cut, so long jobs belong in a queue.

Remember: graceful on, preStop sleep, and grace period greater than preStop plus drain timeout.

11. Real-life scenarios

Every answer follows the same shape: the diagnosis first, then situation, what you check first, the fix, and how you prevent it. Say this shape aloud in the interview. It shows you work calmly under pressure.

After a refactor the app will not start: "No qualifying bean of type OrderService". What do you do? Intermediate

The bean is not registered, and after a refactor the usual reason is that the class moved outside the scanned package, lost its annotation, or is switched off by a profile or condition. I read the failure message, run with --debug to see the conditions report, and fix the package or annotation.

Situation: startup prints "APPLICATION FAILED TO START" saying a bean of some type was required but not found.

Check first: the Description line names the class that needed the bean. Then the four questions: is the class annotated or declared with @Bean; is it in a package below the main class (or in scanBasePackages); is a @Profile or @ConditionalOn... turning it off; is the library that provides it on the classpath?

java -jar app.jar --debug            # look at "Negative matches"
mvn dependency:tree | grep -i the-library

Fix: correct the package or annotation, enable the profile or property, or add the dependency. If there are several candidates, @Primary or @Qualifier.

Prevent: keep the main class in the root package, and keep one context-loads @SpringBootTest in CI so this fails on the pull request, not at deploy.

Remember: not found = not scanned, not annotated, switched off, or library missing. --debug tells which.

"Web server failed to start. Port 8080 was already in use." It works on a colleague's machine. What do you do? Basic

Another process is already listening on that port, often a previous run of the same app that did not stop. I find and stop that process, or run this one on another port with --server.port=8081. In tests I use server.port=0 so a free port is chosen.

Check first: who owns the port.

netstat -ano | findstr :8080        # Windows (last column is the PID)
lsof -i :8080                       # macOS / Linux
kill <pid>

Fix: stop the old process, or change server.port. In Kubernetes this error means two containers in one pod want the same port (a sidecar), or the app binds a fixed port that clashes with the management port.

Prevent: random ports in tests, a separate management.server.port on purpose, and stop dev runs cleanly from the IDE.

Remember: port in use = find the owner. Tests use port 0.

The production pod connects to the dev database. You suspect the wrong profile. How do you confirm and fix it? Intermediate

I confirm which profile is active and which source supplies the datasource URL, then fix the source. Boot logs "The following profiles are active: ..." at startup, and /actuator/env/spring.datasource.url shows the winning value and where it came from. Then I correct the profile variable or remove the override.

Check first: the startup log line for active profiles, then the property source list for the URL. Typical causes: SPRING_PROFILES_ACTIVE not set in the Deployment (so the default profile applies and application.yml holds the dev URL); a higher-priority source (a command-line argument or a system property in the image's entrypoint) overriding the ConfigMap; or a wrong variable name, so relaxed binding did not match.

Fix: set SPRING_PROFILES_ACTIVE=prod and the URL through a Secret or ConfigMap, then roll out and verify with the env endpoint.

Prevent: never keep a real environment URL as the default in the packaged application.yml. A default that points to a harmless local database fails safely; a default that points to dev connects silently. Add a startup check that logs the host (not the password) of the database in use.

Remember: check the log for active profiles, then /actuator/env for the winning source. Defaults must fail safe.

At peak the API returns 500s: "HikariPool-1 - Connection is not available, request timed out after 30000ms". What do you do? Senior

The pool is exhausted: all connections are in use and callers wait 30 seconds, then fail. Raising the pool is usually the wrong first move. I find who holds connections too long (slow query, a transaction that includes a remote call, or a leak), fix that, and only then size the pool.

Check first: metrics hikaricp.connections.active, pending and usage time; a thread dump to see where threads wait and what holds connections; the database's own view of slow or idle-in-transaction sessions. Turn on leak-detection-threshold (for example 20 s) to get a stack trace of code that keeps a connection.

Fix: move HTTP calls out of @Transactional methods, fix the slow query or add the missing index, turn off open-in-view, close resources that leak. Then, if load is really higher, raise the pool carefully, checking that pods x pool size fits the database limit. Lower connection-timeout to fail fast rather than pile up requests.

Prevent: alert on pending connections, keep transactions short, load-test with realistic concurrency.

Remember: exhausted pool = connections held too long. Find the holder, then resize.

The pod restarts every few hours with exit code 137, and there is no OutOfMemoryError in the logs. What is happening? Senior

Exit code 137 means the container was killed (SIGKILL), almost always OOMKilled: total process memory exceeded the container limit. The Java heap is only part of it, so the JVM never saw an OutOfMemoryError. I check kubectl describe pod for "OOMKilled", then compare the heap setting with the limit and look for non-heap growth.

Check first: the last state in kubectl describe pod; the JVM flags (a fixed -Xmx equal to the limit leaves nothing for metaspace, thread stacks and direct buffers); metrics for heap and non-heap, thread count and direct buffers; whether memory grows steadily (a leak) or in steps (traffic, large responses, many threads).

Fix: use -XX:MaxRAMPercentage=70 or so, not heap equal to the limit; limit thread pools; cap direct memory when using Netty; fix a leak if memory only grows. Add -XX:+ExitOnOutOfMemoryError and, in a controlled setup, a heap dump on OOM to a volume.

Prevent: dashboards for heap, non-heap and container working set; load tests that run long enough to show the slope.

Remember: 137 with no Java error = killed by the container limit. Heap is not the whole process.

After adding one library, every endpoint returns 401 and the log shows "Using generated security password". How did that happen? Senior

The new library pulled in spring-boot-starter-security (or Spring Security) transitively, and Boot's security auto-configuration switched on: every endpoint now needs basic auth with a generated password. I confirm with the dependency tree and the conditions report, then either define my own SecurityFilterChain or remove the unwanted dependency.

Check first: mvn dependency:tree (or gradle dependencies) to see who brought it, and --debug to see SecurityAutoConfiguration in the positive matches.

Fix: if the app should have security, write a proper SecurityFilterChain bean (the default backs off). If not, exclude the dependency from the library, or exclude the auto-configuration classes. Never fix it by disabling all authorization on a service that is exposed.

Prevent: review the dependency tree on every new library, and have a test that loads the context and calls one endpoint, so a changed security posture is noticed in CI. This is the general lesson of auto-configuration: classpath changes behaviour.

Remember: classpath drives auto-configuration. A new transitive jar can switch on security, a DataSource, and more.

You set a property in a ConfigMap and the app ignores it. How do you find out why? Intermediate

Either the value never reached the process, or a higher-priority source overrides it. I look at the resolved value with /actuator/env/<key>, which lists every source in priority order, and check the pod's environment directly.

Check first: (1) did it reach the pod: kubectl exec pod -- env | grep NAME, or the mounted file; (2) is the name right: spring.datasource.url becomes SPRING_DATASOURCE_URL, and a typo or a dash left in place silently does nothing; (3) is something higher overriding: a command-line argument in the container args, a -D system property, or a profile file; (4) is the pod restarted: environment variables from a ConfigMap are read only at container start, so changing the ConfigMap does not change running pods.

Fix: correct the name, remove the override, and roll the deployment (kubectl rollout restart).

Prevent: a checksum annotation of the ConfigMap in the Deployment (so a change triggers a rollout), validated @ConfigurationProperties, and one documented place for each setting.

Remember: check that it arrived, check the name, check who overrides it, and restart the pod.

A small worker service that never uses a database now fails with "Failed to configure a DataSource". What happened? Basic

Something on the classpath, usually a new dependency, brought JDBC or JPA, so Boot tried to create a DataSource and found no URL. I find which dependency added it and remove it, or exclude DataSourceAutoConfiguration if the app really does not need a database.

Check first: the failure message names the cause ("'url' attribute is not specified and no embedded datasource could be configured"). Then dependency:tree for spring-jdbc, spring-boot-starter-data-jpa or a driver that came in with a shared internal library.

Fix: remove or exclude the dependency; or spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration (and the JPA/Hibernate one if present).

Prevent: shared libraries should not drag in JPA or JDBC for everyone; mark such dependencies optional or split the module. Check the dependency diff on upgrades.

Remember: JDBC on the classpath without a URL = startup failure. Remove the cause, do not just add a fake URL.

A deployment fails at startup with "Migration checksum mismatch". Production data is in that database. What do you do? Senior

Someone changed a migration file that was already applied, so its stored checksum no longer matches. I do not touch production data. I restore the original file exactly as it was applied, and put the intended change into a new migration. Only if the old file really must change do I use Flyway's repair, carefully, after confirming that the database state matches.

Check first: in Git, what changed in that file (even whitespace or line endings change the checksum); in the flyway_schema_history table, which version and checksum are recorded; whether the change was only formatting.

Fix: revert the file and add V(next)__fix.sql. If the edit was harmless and has to stay, run flyway repair to update the checksum, as a deliberate and reviewed step, never on autopilot. Roll forward rather than trying to undo production.

Prevent: a CI check that fails if an existing migration file changes, a lock on the migration folder in code review, and running migrations against a copy of production data before release.

Remember: applied migrations are immutable. Revert the file, add a new migration.

The nightly report e-mail was sent three times, once per pod. How do you fix the @Scheduled job? Intermediate

Every pod runs its own scheduler, so three pods run the job three times. I make the job run once: a distributed lock with ShedLock, or move it to a Kubernetes CronJob. Either way I also make it idempotent, so a repeat does no harm.

Check first: the log shows three runs at the same time from three pod names; confirm that only the scheduler is the cause and not a retry.

Fix: with ShedLock, annotate the job with @SchedulerLock(name = "nightlyReport", lockAtMostFor = "30m", lockAtLeastFor = "5m") backed by a database table or Redis; the first pod takes the lock and the others skip. A CronJob is cleaner for heavy jobs: they run once, in their own resources, and do not slow the web pods. Add idempotence: record "report for date X was sent" and skip if it exists.

Prevent: treat every @Scheduled method as "runs on every instance" during design review, and keep lockAtMostFor longer than the job but short enough to recover after a crash.

Remember: @Scheduled runs on every pod. Lock it or move it, and make it idempotent.
