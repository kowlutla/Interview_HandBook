Mental model: the 7 ideas everything hangs on

One line: Spring Boot is Spring plus opinions. It looks at your classpath and your properties, and registers the beans you would probably have written yourself. You override any of it by defining your own bean or setting a property.
  1. Boot is not a new framework. It sits on Spring Framework. Every Boot feature ends up as ordinary Spring beans and ordinary configuration.
  2. Starters pull in the right jars. One dependency such as spring-boot-starter-web brings Spring MVC, Jackson, Tomcat and logging, at versions known to work together (the BOM, a bill of materials).
  3. Auto-configuration is conditional configuration. Each class says: "if this library is on the classpath and the user has not defined their own bean, create this bean".
  4. User beans always win. Auto-configuration is processed after your own configuration, and most of its beans are @ConditionalOnMissingBean.
  5. Configuration has a strict order. The same jar runs everywhere because properties come from many sources (files, environment variables, command line) and the higher source wins.
  6. The app is a plain main method. SpringApplication.run builds the context and starts an embedded web server in the same process. Deploying means running one jar.
  7. Production features are opt-in. Actuator (health, metrics), graceful shutdown and tracing are modules you switch on, not code you write.

1. Boot basics, starters and the BOM

What does Spring Boot give you that plain Spring does not? Basic

Boot removes the setup work. Starters give me a working set of dependencies in one line, auto-configuration creates the usual beans (DataSource, Jackson, MVC) from what is on the classpath, and an embedded server lets me run the app as a plain jar. On top of that I get externalized configuration and production features like Actuator.

Start with the problem. Plain Spring Framework is a toolkit: it gives you dependency injection, MVC, transactions and so on, but you assemble the application yourself. For a simple REST service with a database you would, without Boot, do all of this by hand:

  1. Choose compatible versions of Spring MVC, Jackson, Hibernate, a connection pool and a logging library (a mismatch gives NoSuchMethodError at runtime).
  2. Declare the beans: DataSource, EntityManagerFactory, TransactionManager, DispatcherServlet, message converters.
  3. Package a WAR and deploy it into a Tomcat that somebody installed and configured.

Boot automates exactly those three chores, using four mechanisms:

MechanismWhat it does for you
Starters + BOMOne dependency pulls a tested set of libraries with matching versions.
Auto-configurationLooks at the classpath and properties, then registers the usual beans for you.
Embedded serverTomcat runs inside your process, so java -jar app.jar is the whole deployment.
Externalized config + ActuatorThe same jar reads different settings per environment, and exposes health and metrics endpoints.

A tiny example: this class plus spring-boot-starter-web is a running web server on port 8080.

@SpringBootApplication
@RestController
public class App {
    @GetMapping("/hello") String hello() { return "hi"; }
    public static void main(String[] a) { SpringApplication.run(App.class, a); }
}

Boot does not replace Spring and adds no new programming model. Every auto-configured thing is an ordinary bean, so you can inspect it, override it by defining your own bean of the same type, or switch it off. The cost is "magic": when a bean appears that you did not expect, you must know how to ask why (the conditions report, covered later). Interviewers often probe this: "is Boot a framework?" The honest answer is that it is a convention layer over Spring, not a competitor to it.

Remember: Boot = Spring + starters + auto-configuration + embedded server + production add-ons. Same Spring underneath, and your own bean always wins.

What is inside @SpringBootApplication? Basic

It is three annotations in one. @SpringBootConfiguration marks the class as a configuration class (it is a @Configuration). @EnableAutoConfiguration turns on auto-configuration. @ComponentScan scans the package of this class and everything below it for my components.

Before Boot you wrote three separate things on your main class. @SpringBootApplication is a shortcut (a meta-annotation) that bundles them:

Inner annotationJob
@SpringBootConfigurationSpecialisation of @Configuration. The class can declare @Bean methods, and tests can find this class to start the app.
@EnableAutoConfigurationTurns on the auto-configuration machinery (the conditional config classes listed in jar metadata).
@ComponentScanFinds @Component, @Service, @Repository, @RestController in this package and below.

The scan starts at the package of the annotated class. So if the main class is com.acme.orders.App, then com.acme.orders.web.OrderController is found, but com.acme.billing.X is not. This is why the main class belongs in the root package of the project.

How @EnableAutoConfiguration works in two steps: first @AutoConfigurationPackage records your root package (JPA uses it as the default place to look for @Entity classes and Spring Data uses it for repositories). Then an import selector reads the file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports from every jar and registers those candidate classes, each of which then decides via conditions whether to apply.

You can tune it without giving it up:

@SpringBootApplication(
    exclude = DataSourceAutoConfiguration.class,        // switch one off
    scanBasePackages = {"com.acme.a", "com.acme.b"})    // widen the scan

Pitfalls: putting the main class in the default (empty) package makes the scan walk the whole classpath and is flagged with a warning; and a second @SpringBootApplication in the same module causes duplicate-bean surprises.

Remember: configuration class + auto-configuration + component scan, all starting at the main class's package.

My @Service in another package is not found. How does Boot decide where to scan, and how do I fix it? Basic

Boot scans only the package of the @SpringBootApplication class and its sub-packages. If my bean lives in a sibling package like com.other.service, it is simply not seen. The cleanest fix is to move the main class up to the common root package; otherwise I set scanBasePackages or add @Import.

Think of component scanning as a search with a starting folder. Boot's starting folder is the package of the class annotated with @SpringBootApplication. Everything in that package and its sub-packages is searched for stereotype annotations. A class in a sibling or parent package is never looked at, so no bean definition is created for it.

Example of the failure:

com.acme.orders.OrdersApp          // @SpringBootApplication, scan starts here
com.acme.orders.web.OrderController // found
com.acme.shared.PricingService      // NOT found -> NoSuchBeanDefinitionException

Typical symptoms: with constructor injection, startup fails with "No qualifying bean of type PricingService"; for a controller, the app starts fine but its URL returns 404 because nothing registered the mapping.

Debug checklist, in order:

  1. Does the class have a stereotype annotation (@Service, @Component...)? An interface or a plain class is not enough.
  2. Is its package at or below the main class's package?
  3. Is something switching it off: @Profile, @ConditionalOnProperty?
  4. Did someone add a second @ComponentScan on another class? That replaces the default base package instead of adding to it, so the main class's own package may stop being scanned.

Fixes, from best to worst: move the main class up to the common root (com.acme); list packages with scanBasePackages; or @Import(PricingService.class) / @Import(SharedConfig.class) for one-off cases. For a shared library that ships beans to many apps, do not make every app scan the library's package. Give the library an auto-configuration class instead, so adding the jar is enough.

Remember: scan starts at the main class's package. Move the main class up, or list the packages. Libraries should use auto-configuration, not rely on scanning.

What is a starter, and what is inside one? Basic

A starter is a dependency descriptor: a tiny jar with no code that pulls in a curated set of libraries for one purpose. spring-boot-starter-web brings Spring MVC, Jackson, embedded Tomcat and logging. It saves me from choosing libraries and matching their versions.

Compare it with shopping lists. Without a starter, to build a web app you write six dependencies in your pom and choose a version for each. With spring-boot-starter-web you write one line and the starter pulls the rest.

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>   <!-- no version: the BOM supplies it -->
</dependency>

What is physically inside: a starter jar contains essentially no classes, only a pom listing dependencies. For starter-web those are spring-webmvc, jackson, spring-boot-starter-tomcat and spring-boot-starter-logging (Logback), plus the core spring-boot-starter.

The starter and the behaviour are separate. The starter puts jars on the classpath. The beans come from the spring-boot-autoconfigure jar, whose classes are guarded by conditions like "if DataSource.class is on the classpath". So adding starter-data-jpa brings Hibernate and Hikari, and auto-configuration then sees them and builds a DataSource, an EntityManagerFactory and a transaction manager.

Naming rule: official starters are spring-boot-starter-*. Third parties name theirs acme-spring-boot-starter, because the spring-boot-starter prefix is reserved.

Useful swaps: exclude Tomcat and add starter-jetty or starter-undertow to change the server; exclude Logback and add starter-log4j2 to change logging.

Pitfall: adding a starter changes behaviour, not just the classpath. Adding starter-security locks every endpoint behind a generated login at once; adding a JDBC driver without a URL fails startup because a DataSource is now expected. The same effect is why a leftover unused starter can break an app.

Remember: a starter is a dependency list. Auto-configuration is what reacts to it, and the reaction can change behaviour.

How does Boot manage dependency versions, and how do I override one? Intermediate

Boot ships a BOM (bill of materials) called spring-boot-dependencies that fixes the version of hundreds of libraries, so I declare them without a version. With the Boot parent POM or the Gradle plugin that is automatic. To override one library I set its version property, for example jackson-bom.version in Maven.

The problem: Spring, Jackson, Hibernate, Netty, Tomcat and hundreds of others each release independently, and not every combination works. Boot's team tests one combination per release and publishes it as a BOM, a pom named spring-boot-dependencies that only contains a dependencyManagement section (a table of "library to version"). When your project inherits that table, you write a dependency with no version and Maven or Gradle fills it in.

How you get the table:

  • Maven, normal case: use spring-boot-starter-parent as the parent.
  • Maven, you already have a company parent: import the BOM instead.
  • Gradle: the Spring Boot plugin plus io.spring.dependency-management, or Gradle's native platform(...).
<!-- override one version (property name comes from the BOM) -->
<properties>
  <jackson-bom.version>2.17.2</jackson-bom.version>
</properties>

<!-- or import the BOM when you cannot use the parent -->
<dependencyManagement><dependencies><dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-dependencies</artifactId>
  <version>3.3.0</version><type>pom</type><scope>import</scope>
</dependency></dependencies></dependencyManagement>

In Gradle with the dependency-management plugin the equivalent is ext['jackson-bom.version'] = '2.17.2'.

When to override: mostly to take a security fix (a CVE in a library) before the next Boot patch release. Check what you actually got with mvn dependency:tree or gradle dependencies.

Risks: overriding a core piece (Hibernate, Spring Framework itself) to another major or minor line can break auto-configuration because Boot was tested against its managed version. Hard-coding a version on the dependency also hides the override from the rest of the team; the property approach is visible and also affects other artifacts of the same family.

Remember: leave versions out, let the BOM choose; override with the BOM's property name, and re-run your tests.

2. Startup and context problems

What happens when you call SpringApplication.run()? Senior

Boot first prepares the environment: it detects the app type (servlet, reactive or none), loads properties and activates profiles. Then it creates the ApplicationContext, loads bean definitions including auto-configuration, and calls refresh(), which creates the singleton beans and starts the embedded web server. At the end it runs CommandLineRunner and ApplicationRunner beans, and the app is ready.

Think of startup as five phases. The numbers below are the order things happen.

  1. Prepare. Boot reads SpringApplication settings, decides the app type from the classpath (servlet if Spring MVC and a servlet API exist, reactive if WebFlux, otherwise none), and finds listeners registered in META-INF/spring.factories. It fires ApplicationStartingEvent.
  2. Environment. It builds the Environment: system properties, env vars, command-line args, application.yml, and activates profiles. ApplicationEnvironmentPreparedEvent fires. Then the banner prints.
  3. Create context. It creates the right ApplicationContext type, applies initializers, loads the bean definitions from your configuration and the auto-configuration imports.
  4. refresh(). This is core Spring: bean factory post-processors run, then all non-lazy singletons are created and wired, and the embedded web server is created and started near the end (WebServerStartStopLifecycle). ApplicationStartedEvent fires after.
  5. Runners and ready. ApplicationRunner and CommandLineRunner beans run, then ApplicationReadyEvent fires, and the availability state moves to ACCEPTING_TRAFFIC.

If an exception occurs at any phase, Boot publishes ApplicationFailedEvent, runs a FailureAnalyzer to turn the stack trace into a readable "Description / Action" message, and the JVM exits non-zero. That visible exit is what makes Kubernetes show CrashLoopBackOff for a bad config.

Practical consequences: (a) a slow bean delays the moment the port opens; (b) work in a runner delays "ready" but not the port; (c) listeners for the earliest events cannot be normal beans, since no context exists yet, so they are registered in spring.factories or with SpringApplication.addListeners; (d) the liveness state becomes CORRECT at started and readiness at ready, which is what Kubernetes probes read.

Remember: environment first, then context and beans, then the web server, then runners, then ready. Failures exit non-zero with an analysis.

CommandLineRunner, ApplicationRunner, @PostConstruct, ApplicationReadyEvent: which one do I use for startup work? Intermediate

For work that needs the whole application up, such as warming a cache or a one-off task, I use a runner or an ApplicationReadyEvent listener. @PostConstruct is only for initialising that one bean, because it runs while other beans may not be ready yet. Between the two runners, ApplicationRunner gives me parsed arguments, CommandLineRunner gives raw strings.

The core question is: how much of the application must be alive when my code runs? Boot offers four hook points, in the order they fire:

  1. @PostConstruct (or InitializingBean): per bean, right after that bean's dependencies are injected. The rest of the context is probably not finished.
  2. Context refreshed: all singletons exist and the web server has started listening.
  3. Runners: CommandLineRunner.run(String... args) and ApplicationRunner.run(ApplicationArguments args).
  4. ApplicationReadyEvent: published after runners; the app reports ready for traffic.
@Component
@Order(1)
class WarmUp implements ApplicationRunner {
    public void run(ApplicationArguments args) {
        // args.containsOption("reload"), args.getOptionValues("env")
        cache.preload();
    }
}

@EventListener(ApplicationReadyEvent.class)
void afterReady() { metrics.record("startup-done"); }

Choosing:

  • Initialising one bean (open a file, build a lookup map from its own config): @PostConstruct. Keep it fast and local; slow work here delays the entire context, and calling other beans that are not initialised yet is a classic bug (and a deadlock risk with circular setups).
  • Mandatory setup needing the whole app (schema check, loading reference data the app cannot serve without): a runner. An exception stops startup, which is what you want.
  • Optional work (cache warming, announcing to a registry): a ready-event listener, ideally asynchronous so it does not hold anything.

Pitfalls: runners run before readiness, so a 5 minute runner means 5 minutes of not-ready (use a startup probe so Kubernetes does not kill the pod). Multiple runners are ordered by @Order; without it, order is unspecified. For long data loads prefer a Kubernetes init job or an async task.

Remember: @PostConstruct = this bean only; runner = needs the whole app, failure aborts; ready event = optional, non-blocking.

What does spring.main.lazy-initialization do, and what are the risks? Intermediate

It tells Spring to create beans only when they are first needed, instead of all at startup. Startup gets faster and uses less memory, but problems that used to fail at boot (missing beans, bad configuration) now fail on the first request instead. I use it for local development and tests, and I am careful in production.

Normally Spring creates every singleton bean at startup ("eager"), which is why a typo in configuration crashes the app on boot, not later. With spring.main.lazy-initialization=true, Spring only registers the definitions and creates each bean the first time something asks for it.

What you gain: faster startup and lower initial memory, because beans never used (or not used yet) are never built. In a big app with hundreds of beans this can cut startup noticeably, which helps local development and slice tests.

What you lose, with a concrete timeline:

  1. Deploy at 12:00. Readiness turns green at 12:00:20 because few beans exist.
  2. The load balancer sends the first request. It triggers creation of the controller, service, repository, maybe a Hibernate session factory: this one request takes 4 seconds, and a concurrent burst all pays the cost.
  3. A misconfigured bean (wrong URL, missing property) is only discovered when a user hits it, as a 500, instead of a failed rollout.

So lazy init moves both cost and errors from deploy time to request time. In production, fail-fast eager startup is usually the safer property: the orchestrator sees the crash and rolls back before users are affected.

Middle path: keep global eager, and mark only genuinely heavy, rarely-used beans @Lazy; or keep lazy globally and force critical beans eager with @Lazy(false). Note: @Lazy on an injection point injects a proxy that resolves the real bean on first call. Also note that lazy init does not remove the cost of auto-configuration condition evaluation or classpath scanning, so measure before assuming a big win.

Remember: lazy init moves errors and cost from startup to first use. Good for dev and tests, careful in production.

Boot refuses circular dependencies. Why, and how do you fix a cycle? Intermediate

Since Boot 2.6 circular references are not allowed by default, so a cycle fails at startup with "The dependencies of some of the beans in the application context form a cycle". A cycle (A needs B and B needs A) is a design smell, so I fix it by breaking the loop, not by switching it back on with spring.main.allow-circular-references=true.

A cycle means bean A needs B to be constructed and B needs A. Spring cannot finish either: with constructor injection it throws BeanCurrentlyInCreationException. Older Spring tolerated cycles for field and setter injection by exposing an early, half-built reference ("early singleton reference"). That hid a design flaw and caused hard-to-find bugs (a bean used before it was fully initialised, proxies not applied). Since Boot 2.6 this tolerance is off by default, and startup fails with an explicit list of the beans in the cycle.

@Service class OrderService    { OrderService(DiscountService d) {} }
@Service class DiscountService { DiscountService(OrderService o) {} }  // cycle

Treat the error as feedback: two classes that need each other usually share a hidden third concept. Fixes, in order of preference:

  1. Extract the shared logic into a third bean (PricingRules) that both depend on. The dependency graph becomes a tree again.
  2. Invert with events. Instead of A calling B directly, A publishes an application event and B listens. A no longer knows B.
  3. Break at the injection point. @Lazy on one constructor parameter injects a proxy that resolves the real bean on first call; or inject an ObjectProvider<B> and call getObject() when needed.
  4. Last resort: spring.main.allow-circular-references=true. It restores the old behaviour for setter and field injection only, and just hides the smell.

What an interviewer may probe: why constructor injection makes cycles visible (it is a real compile-time-like dependency, immutable fields cannot be half-set); and the question "which service owns this behaviour?" which is usually the real answer.

Remember: a cycle means the design is wrong. Extract a third bean first, use @Lazy as a last resort, avoid the allow flag.

Your Boot app takes 90 seconds to start. How do you find out why? Senior

I measure first, then fix the biggest item. I turn on Boot's startup tracking (BufferingApplicationStartup and the /actuator/startup endpoint) to see which beans took longest. Then I look at logs for gaps, because the usual causes are slow beans (remote calls or cache warming in constructors), database migrations, classpath scanning of a huge package, and a remote config server.

The rule is measure, do not guess. A 90 second start has one or two dominant causes, and removing them matters far more than tuning everything.

Step 1: get data. Turn on startup tracking so Boot records the time of each phase and bean creation.

SpringApplication app = new SpringApplication(App.class);
app.setApplicationStartup(new BufferingApplicationStartup(4096));
app.run(args);
# application.properties
management.endpoints.web.exposure.include=startup
# then GET /actuator/startup and sort steps by duration

Also read the log timestamps: a long gap between two lines points at the culprit. Run with --debug to see the conditions report if the scan or auto-configuration is suspect. A thread dump taken at second 30 shows what the main thread is blocked on.

Step 2: match to the usual suspects.

FindingFix
Bean calls a remote service in constructor or @PostConstruct, no timeoutMove to ready event or async; add timeouts
Flyway/Liquibase runs many migrations every startRun migrations as a separate job, or baseline
Hibernate ddl-auto=validate on a slow or remote DBValidate in CI, not at every start

Step 3: protect rollouts. Add a Kubernetes startup probe so a legitimately slow start is not killed by the liveness probe. For extreme cases consider AppCDS (class data sharing), Spring AOT, or a GraalVM native image, but only after you have found that class loading and bean creation dominate; they bring build complexity and reflection limits.

Remember: measure with /actuator/startup, find the slow bean, move its work out of startup, then protect the rollout with a startup probe.

3. Auto-configuration

How does auto-configuration work internally? Senior

Every Boot jar lists its auto-configuration classes in a file, META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. At startup @EnableAutoConfiguration reads those files from the whole classpath, then each class is checked against its @Conditional rules. If all conditions pass, its beans are registered; if one fails, the whole class is skipped. These classes run after my own configuration, so my beans take precedence.

Why it exists: Boot cannot know your project at build time, so it ships a large pool of "maybe" configuration classes, one per technology (DataSource, Jackson, MVC, Kafka, and so on), and decides at startup which ones to apply. The decision is made by conditions, so the same Boot jar behaves differently in an app with JPA and one without.

The mechanism in five steps:

  1. Discover. Each library jar lists its auto-configuration classes in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, one class name per line. @EnableAutoConfiguration reads this file from every jar on the classpath.
  2. Exclude. Classes named in exclude or spring.autoconfigure.exclude are removed.
  3. Pre-filter. A generated metadata file lets Boot discard classes whose required jars are absent without loading them, which keeps startup fast.
  4. Order. Classes are sorted using @AutoConfiguration(before=..., after=...). All of them are processed after your own configuration.
  5. Evaluate conditions. Each class and each of its @Bean methods carries @Conditional... checks. If a class-level condition fails, the whole class is skipped; if a method-level one fails, just that bean is.

Simplified example of what DataSourceAutoConfiguration does:

@AutoConfiguration
@ConditionalOnClass(DataSource.class)                 // is JDBC on the classpath?
@EnableConfigurationProperties(DataSourceProperties.class)  // bind spring.datasource.*
class DataSourceAutoConfiguration {
    @Bean @ConditionalOnMissingBean(DataSource.class)  // back off if the user made one
    HikariDataSource dataSource(DataSourceProperties p) { ... }
}

"After your own configuration" is the crucial point: when @ConditionalOnMissingBean is checked, your beans are already registered, so yours wins.

Version detail: the .imports file arrived in Boot 2.7, and Boot 3 no longer reads auto-configuration entries from the old spring.factories key. Interview probe: "how do I see what happened?" Answer: the conditions report (next questions).

Remember: list in the imports file, filter by conditions, run after user config, back off when the user defines the bean.

Name the common @Conditional annotations and what each is for. Intermediate

The ones I use most: @ConditionalOnClass (a library is on the classpath), @ConditionalOnMissingBean (back off if the user defined one), @ConditionalOnProperty (a property has a value, good for feature flags), and @ConditionalOnBean. Together they let a configuration say "create this if the library is present and the user has not already provided one".

A condition is a yes/no test evaluated while Spring registers bean definitions. Boot gives ready-made ones so a configuration reads like a sentence.

AnnotationPasses whenTypical use
@ConditionalOnClass / OnMissingClassclass is / is not on classpathactivate when a library is present
@ConditionalOnBean / OnMissingBeana bean of that type exists / does notdefault bean the user can replace
@ConditionalOnPropertyproperty has a value (havingValue, matchIfMissing)feature toggle
@ConditionalOnResourcea file existsoptional config file
@ConditionalOnWebApplicationservlet or reactive web appweb-only beans
@ConditionalOnExpressionSpEL expression is truerare, complex rules

Combined, they express "create this if the library is present and the user has not provided one, unless switched off":

@Configuration
@ConditionalOnClass(KafkaTemplate.class)
@ConditionalOnProperty(name = "acme.audit.enabled", havingValue = "true", matchIfMissing = true)
class AuditConfig {
    @Bean @ConditionalOnMissingBean AuditSender sender() { return new AuditSender(); }
}

Note matchIfMissing=true: with it the feature is on unless someone sets the property to false; without it, a missing property means off. That choice decides whether the feature is opt-in or opt-out.

Traps:

  • @ConditionalOnBean depends on registration order. It is reliable only in auto-configuration classes (processed last). In ordinary configuration it may run before the bean it checks for exists.
  • @ConditionalOnClass on a @Bean method can still fail at class-loading time if the signature mentions the missing class. Boot puts it on the configuration class, or uses the name attribute with a string.

Remember: class = is the library there, missing bean = can the user override, property = feature switch.

How does @ConditionalOnMissingBean let my bean replace a default, and what can go wrong? Senior

Auto-configuration is processed after my configuration. By the time Boot's @ConditionalOnMissingBean is evaluated, my bean is already registered, so the condition fails and the default is skipped. That is the whole override mechanism: I define a bean of the same type, and the default backs off.

The mechanism is just ordering. Spring registers bean definitions in this order: your @Configuration and scanned components first, then auto-configuration. When Boot evaluates @ConditionalOnMissingBean(DataSource.class), it asks "is there already a definition of type DataSource?". If you defined one, the answer is yes, the condition fails, and Boot's default is not registered. There is no special override API.

@Bean DataSource dataSource() { return myCustomPool(); }   // yours
// Boot's own: @Bean @ConditionalOnMissingBean DataSource ...  -> skipped

What can go wrong:

  1. Different type. If you define MyObjectMapper that does not extend ObjectMapper, Boot's condition (on ObjectMapper) still passes and you now have two, or injection becomes ambiguous.
  2. Replacing loses Boot's extras. Boot's default ObjectMapper is built by a builder that applies the spring.jackson.* properties and registers modules (Java time, etc.). A hand-made new ObjectMapper() drops all that, which is a common cause of "dates suddenly serialise as numbers".
  3. Order inside your own config. A bean defined in a conditional or late-loaded place may not be visible yet.

So the rule: to tweak, use the customizer hooks Boot provides (Jackson2ObjectMapperBuilderCustomizer, WebMvcConfigurer, RestClientCustomizer, HikariConfig properties); to replace, define your own bean of the same type and accept responsibility for everything the default did.

@Bean
Jackson2ObjectMapperBuilderCustomizer jsonTweaks() {
    return b -> b.featuresToEnable(SerializationFeature.INDENT_OUTPUT);

How do you turn off an auto-configuration you do not want? Basic

Add it to exclude on @SpringBootApplication (or @EnableAutoConfiguration), or list it in spring.autoconfigure.exclude in properties. The property form is handy because it can differ per profile and needs no code change.

Sometimes auto-configuration does something you do not want: it tries to create a DataSource when you have a JDBC driver but no database, or it secures endpoints you wanted open. You then tell Boot to skip that class. There are two places to do it.

// in code
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
// string form when the class is not on the compile classpath
@SpringBootApplication(excludeName = "org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration")

# application.yml (no code change, can vary by profile)
spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

The property form is handy for ops: a profile or an environment variable can switch the class off with no rebuild.

Before excluding, ask whether a lighter lever exists:

  • A property: spring.main.web-application-type=none for a non-web app, spring.jpa.hibernate.ddl-auto=none, management.endpoint.x.enabled=false.
  • Removing the dependency that caused the auto-configuration (cleanest: the code is gone, startup is faster).
  • Defining your own bean so the default backs off (keeps the rest of the configuration working).

Pitfall: exclusion is blunt. If you exclude DataSourceAutoConfiguration but a repository still needs a DataSource, startup now fails with "no bean of type DataSource". Also the exclude must name the exact auto-configuration class; a typo is reported as an error for classes that are not auto-configurations, which helps catch it.

Remember: exclude via annotation or spring.autoconfigure.exclude, but first ask if a property or a dependency removal is cleaner.

How would you write your own auto-configuration or starter for a shared company library? Senior

I write a normal @AutoConfiguration class with conditional beans, bind its settings with a @ConfigurationProperties class, and register it in META-INF/spring/...AutoConfiguration.imports. Every bean is @ConditionalOnMissingBean so the app can override it. Then I publish it as a library, and optionally add a thin starter that just depends on it.

The goal: a team ships a shared library (say an audit client) and any app gets it working just by adding the dependency, with sensible defaults and the right to override. You build it as a Boot-style auto-configuration, in these pieces.

  1. Properties class bound from a prefix, so users configure it in application.yml.
  2. Auto-configuration class with conditional beans.
  3. Imports file that registers the class.
  4. Optional starter that only holds dependencies.
@ConfigurationProperties("acme.audit")
public record AuditProperties(String url, @DefaultValue("2s") Duration timeout) {}

@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@ConditionalOnProperty(name = "acme.audit.enabled", matchIfMissing = true)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {
    @Bean @ConditionalOnMissingBean
    AuditClient auditClient(AuditProperties p) { return new AuditClient(p.url(), p.timeout()); }
}
# src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.audit.AuditAutoConfiguration

Why each choice:

  • Imports file, not scanning. The consuming app only scans its own package, so a @Configuration in your jar would never be seen.
  • @ConditionalOnMissingBean on every bean so teams can replace the client with their own.
  • An enabled property gives a kill switch without removing the jar.
  • spring-boot-configuration-processor generates metadata so IDEs autocomplete acme.audit.* and show descriptions.

Naming and structure: the spring-boot-starter-* prefix is reserved for Spring, so use acme-spring-boot-starter. The starter has no code; the acme-spring-boot-autoconfigure module has the beans. Test it with ApplicationContextRunner: it builds a tiny context in milliseconds, lets you add or remove classes and properties, and asserts which beans exist.

Remember: @AutoConfiguration + conditions + imports file + @ConditionalOnMissingBean on every bean.

4. Configuration, properties and profiles

Where can Boot read properties from, and which source wins? Intermediate

From many places, and the rule is that the more specific, more external source wins. From highest to lowest: test properties, command-line arguments, Java system properties, OS environment variables, profile-specific config files, application.yml or .properties (outside the jar beats inside), then @PropertySource and defaults. So the platform can always override what is packaged in the jar.

Why a precedence list exists: the same jar must run on a laptop, in CI and in production with different settings, and an operator must be able to change a value without rebuilding. Boot solves this by reading many sources and stacking them; when two define the same key, the higher one wins. The principle: the more specific and more external the source, the higher it ranks.

Worked example. Suppose the jar contains server.port=8080 and the pod sets an env var SERVER_PORT=9090:

application.yml (inside jar):   server.port=8080
SERVER_PORT=9090   (env var):   server.port=9090   <- wins
java -jar app.jar --server.port=7070 <- wins over both

Useful details:

  • Merge by key. A profile file or an external file does not replace the whole base file. It overrides only the keys it defines; others fall through to the lower file.
  • Where files are searched. classpath:/, classpath:/config/, the current directory, and ./config/; later (more external) locations override earlier ones.
  • Extra files: spring.config.import=optional:file:/etc/app/extra.yml, or a config tree for mounted secrets, or a config server.
  • Profile files beat the base file: application-prod.yml wins over application.yml.

Debugging rule: "my value is ignored" almost always means a higher source is overriding it. Look at /actuator/env/<key>, which lists all sources in priority order. Pitfall: an old -D system property in a startup script quietly beats the ConfigMap env var you just changed.

Remember: command line beats env vars, env vars beat files, profile files beat the base file, outside the jar beats inside.

How do profiles work? How do you activate and combine them? Basic

A profile is a named set of configuration, such as dev or prod. I put environment-specific values in application-prod.yml and beans in @Profile("prod") classes, and activate the profile with spring.profiles.active. In deployment I set it as an environment variable: SPRING_PROFILES_ACTIVE=prod.

A profile is a label that switches groups of configuration and beans on or off. The need: development uses an in-memory DB and verbose logs, production uses a real cluster. Profiles let one codebase carry both without if-statements.

Two uses:

# 1) config files: application-prod.yml overlays application.yml
spring:
  datasource:
    url: jdbc:postgresql://db.prod/orders

// 2) beans only for a profile
@Configuration @Profile("prod")
class ProdMailConfig { ... }
@Bean @Profile("!prod") MailSender fakeSender() { ... }   // everything except prod

Activating:

  • Property or env var: spring.profiles.active=prod or SPRING_PROFILES_ACTIVE=prod (the usual way in containers).
  • Several at once: prod,eu. If both set the same key, the later one wins.
  • Always-on: spring.profiles.include (cannot be set inside a profile-specific document in current versions).
  • Groups: spring.profiles.group.prod=proddb,prodmq turns on a bundle with one name.
  • One multi-document YAML file, with a section scoped by spring.config.activate.on-profile: prod.

Profile files override only the keys they define; everything else falls through to application.yml.

Pitfalls and good practice:

  • A profile can silently switch off a bean, a classic reason for "bean not found" in only one environment.
  • Do not multiply profiles (dev, qa, uat, perf, prod-eu...). Keep few, and let the platform supply differing values by env var.
  • Never commit secrets in a profile file.
  • Do not put the active profile inside the packaged application.yml for prod; set it from the environment.

Remember: profile = overlay of config and beans. Activate with SPRING_PROFILES_ACTIVE, keep profiles few.

How does @ConfigurationProperties work, and why is it better than @Value? Intermediate

@ConfigurationProperties binds a whole prefix of properties (for example app.mail.*) into a typed class, with nested objects, lists, durations and validation. @Value injects one value at a time as a string expression. For anything beyond one or two settings I prefer @ConfigurationProperties: it is type-safe, grouped in one place, supports relaxed binding and can fail startup if values are wrong.

The two tools solve the same need, reading settings, at different scales.

@Value("${app.mail.host}") injects one value into a field or parameter. It works, but with ten settings you get ten annotations scattered around the code, each a string key that a typo can break and an IDE cannot check.

@ConfigurationProperties("app.mail") binds a whole prefix into one typed object:

app:
  mail:
    host: smtp.acme.com
    port: 587
    timeout: 5s
    bcc: [a@x.com, b@x.com]

@ConfigurationProperties("app.mail")
public record MailProperties(String host, int port, Duration timeout, List<String> bcc) {}

// register: @EnableConfigurationProperties(MailProperties.class)
// or @ConfigurationPropertiesScan on the main class

A record or a class with a single constructor is bound through the constructor, giving an immutable object (no extra annotation is needed in Boot 3; in Boot 2 you needed @ConstructorBinding). A class with setters is bound by calling them.

Use @Value for a single value or a SpEL computation. Everything else belongs in a properties class, which also makes tests easy: build the record by hand. Pitfall: forgetting to register the class means it silently never binds (it is not a component by itself).

Remember: group settings in a typed @ConfigurationProperties record; use @Value only for one-off values.

How do I make the app fail at startup if a required setting is missing or invalid? Intermediate

I put @Validated on the @ConfigurationProperties class and add Bean Validation constraints such as @NotBlank or @Min. If a value is missing or wrong, binding fails and the app refuses to start with a message naming the property. That is much better than a NullPointerException at 3 a.m. from a value nobody set.

The idea is "fail fast". A missing database URL should stop the pod at deploy, where the rollout fails and nobody is affected, and not produce a NullPointerException hours later in a rarely used code path.

How: add @Validated to the properties class and put Bean Validation constraints on the fields. Binding then validates the object, and a violation aborts startup with a message that names the property.

@ConfigurationProperties("app.payment")
@Validated
public record PaymentProperties(
    @NotBlank String apiUrl,
    @Min(1) @Max(10) int retries,
    @DefaultValue("3s") Duration timeout,
    @Valid Retry retry) {                       // @Valid needed to check nested object
    public record Retry(@Positive int attempts) {}
}

Failure looks like:

Binding to target ... failed:
    Property: app.payment.apiUrl
    Value: ""
    Reason: must not be blank

Requirements and details:

  • Add spring-boot-starter-validation (a validator implementation, Hibernate Validator, must be on the classpath).
  • Nested objects need @Valid on the field, otherwise they are skipped.
  • A required property with no default and no constraint simply binds as null (or 0), so the constraint is what makes it required. With a record you can also give defaults via @DefaultValue.
  • With @Value, a missing key without a default also fails ("Could not resolve placeholder"), but a present-and-wrong value is never validated.

Combine this with a Kubernetes readiness probe and rolling update: the new pods crash, the old ones keep serving, and the bad config never reaches users.

Remember: @Validated + constraints on @ConfigurationProperties = bad config stops the deploy, not production.

How do property placeholders and defaults work with @Value? Basic

A placeholder ${key} is replaced with the property value. I give a default after a colon: ${app.timeout:5s}. Without a default, a missing key fails startup with "Could not resolve placeholder". For SpEL expressions I use #{...}.

A placeholder ${key} is text replaced by a property value when the bean is created. You can add a fallback after a colon, and you can nest them.

@Value("${app.region:eu-west-1}")  String region;     // default if key missing
@Value("${app.hosts:}")            List<String> hosts;   // empty default; "a,b" splits into a list
@Value("${app.timeout}")           Duration t;          // no default: missing key = startup failure
@Value("#{systemProperties['user.home']}") String home;  // #{...} = SpEL expression
@Value("#{${app.limit} * 2}")      int doubled;          // placeholder inside SpEL

The two syntaxes are different things. ${...} is "look up a property". #{...} is the Spring Expression Language, which can call methods, read beans (#{@myBean.x}) and do arithmetic. People mix them up in interviews.

Placeholders also work inside property files, which avoids repeating values:

app.host=api.acme.com
app.url=https://${app.host}:${app.port:443}/v1

Boot has a random.* property source that is useful for tests and local runs: ${random.uuid}, ${random.int(1000,2000)}, ${random.value}. It generates a new value each time it is read, so it is not suitable for something that must stay stable.

Behaviours to know: no default means a missing key fails fast with "Could not resolve placeholder 'x' in value ${x}", which is usually what you want; and @Value is resolved once when the bean is created, so changes later (even if the file changes) do not show up without a restart or a refresh mechanism such as Spring Cloud's @RefreshScope.

Remember: ${key:default} for properties, #{...} for expressions. No default means fail-fast.

What is relaxed binding? How do property names map to environment variables? Intermediate

Relaxed binding means one property can be written in several styles and still bind to the same field. In files I use kebab-case (my.app.read-timeout); the same value can be set as an environment variable by upper-casing, turning dots into underscores and dropping dashes: MY_APP_READTIMEOUT. That makes it easy to override any property from Kubernetes without editing files.

Property names are written differently in different places: Java fields use camelCase, YAML files prefer kebab-case, environment variables cannot contain dots or dashes. Relaxed binding means Boot treats these spellings as the same key so each place can use its natural style.

For a field readTimeout under prefix my.app, all of these bind to it:

WhereSpelling
properties/yaml (recommended)my.app.read-timeout
camelCasemy.app.readTimeout
underscoremy.app.read_timeout
environment variableMY_APP_READTIMEOUT

The environment-variable rule: take the canonical kebab-case name, replace dots with underscores, drop the dashes, uppercase. So spring.datasource.url is SPRING_DATASOURCE_URL, and my.app.read-timeout is MY_APP_READTIMEOUT. Lists and maps use indexes or keys: MY_APP_HOSTS_0=a, MY_APP_HOSTS_1=b.

This is the reason a Kubernetes manifest can override any setting without editing a file in the image:

env:
  - name: SPRING_DATASOURCE_URL
    value: jdbc:postgresql://db/orders

Caveats:

  • Relaxed binding is full-strength for @ConfigurationProperties. For @Value the key must match closely, so kebab-case in the file is the safest form.
  • Map keys that contain dots or dashes are awkward to set from an environment variable (they lose the characters). Use a file or the SPRING_APPLICATION_JSON variable for those.
  • A typo in an env var name is silent: nothing binds, the default is used. Check with /actuator/env.

Remember: files use kebab-case, env vars use UPPER_SNAKE: spring.datasource.url becomes SPRING_DATASOURCE_URL.

How do you pass configuration and secrets to a Boot app on Kubernetes? Intermediate

Non-secret settings come from a ConfigMap and secrets from a Secret, both exposed to the pod either as environment variables or as mounted files. Boot reads env vars automatically through relaxed binding, and can read a mounted directory with spring.config.import=optional:configtree:/etc/secrets/, where each file name becomes a key and its content the value.

Split what you pass by sensitivity. Plain settings (URLs, feature flags, pool sizes) go in a Kubernetes ConfigMap. Credentials and keys go in a Secret. Both reach the pod in one of two ways.

1) As environment variables. Boot's relaxed binding picks them up with no code:

env:
  - name: SPRING_DATASOURCE_URL
    valueFrom: { configMapKeyRef: { name: orders-cfg, key: db-url } }
  - name: SPRING_DATASOURCE_PASSWORD
    valueFrom: { secretKeyRef: { name: orders-secret, key: db-pass } }

2) As mounted files. Mount the Secret at /etc/secrets; each key becomes a file. Tell Boot to read the folder as a config tree:

spring.config.import=optional:configtree:/etc/secrets/

5. REST controllers, validation and error handling

What is the difference between @Controller and @RestController, and how does a request reach my method? Basic

@RestController is @Controller plus @ResponseBody: the return value is written straight into the HTTP response (as JSON by default) instead of being treated as a view name. In Boot a request goes through the servlet filters, then the DispatcherServlet, which finds the handler method by URL and HTTP method, converts the input, calls my method, and converts the result back.

Two layers of the question. First the annotations. A class marked @Controller is a web handler whose methods usually return a view name (such as "orders") that a template engine renders to HTML. @ResponseBody says "do not look for a view; write the return value into the response body". @RestController simply carries both, so every method returns data, normally JSON.

@RestController                      // = @Controller + @ResponseBody on every method
@RequestMapping("/orders")
class OrderController {
    @GetMapping("/{id}")
    OrderDto get(@PathVariable long id) { return service.find(id); }   // becomes JSON
}

Second, how a request travels. Take GET /orders/42:

  1. The embedded Tomcat accepts the connection and runs the servlet filters (security, logging, CORS).
  2. The DispatcherServlet, the single front controller, asks the HandlerMapping which method matches path and HTTP verb. It finds get(long).
  3. Argument resolvers prepare parameters: 42 from the path is converted to long; @RequestBody would use an HttpMessageConverter (Jackson) to read JSON.
  4. Interceptors run, then your method is called.
  5. The return value goes through a converter again (object to JSON) and is written with a status code.
  6. If anything throws, the exception is routed to a matching @ExceptionHandler; if none matches, the fallback /error handling takes over.

Boot auto-configures all of this when spring-boot-starter-web is present: the DispatcherServlet, Jackson converters, static resources, error handling. For reactive apps (WebFlux) the same annotations work but the pipeline is non-blocking. Interviewers like "where does a filter differ from an interceptor": filters are servlet-level and see every request; interceptors are MVC-level and see only requests mapped to a handler. Deeper MVC internals are on the Spring Framework page.

Remember: @RestController = @Controller + @ResponseBody. The DispatcherServlet does mapping, conversion and error routing.

@PathVariable, @RequestParam, @RequestBody, @RequestHeader: when do I use each? Basic

@PathVariable is for the identity of a resource in the URL (/orders/42). @RequestParam is for optional filters and paging in the query string (?status=OPEN&page=2). @RequestBody is for the JSON payload of POST, PUT and PATCH. @RequestHeader reads a header such as Authorization or an idempotency key.

HTTP gives a request four places to carry data, and Spring has one annotation for each. Choosing the right place is part of good REST design.

Defaults and errors worth knowing:

  • Parameters are required. Missing required one gives 400; make it optional with required=false, a default, or Optional<T>.
  • A type mismatch (/orders/abc where a long is expected) gives 400 (MethodArgumentTypeMismatchException).
  • A body that is not valid JSON or is missing gives 400; a wrong Content-Type gives 415; an unacceptable Accept gives 406.
  • The body stream can be read only once, so one @RequestBody per method.

Design rule of thumb: path identifies, query narrows, body carries. Putting a filter in the path (/orders/open) or an id in the query is allowed but muddles the contract. Parameter names are bound by name, which works in Boot because its build plugins compile with -parameters; when you build with a plain compiler setup, name them explicitly (@PathVariable("id")).

Remember: path = which resource, query = filters, body = payload, header = metadata.

How do I return the right HTTP status and headers from a controller? Basic

For the normal case I return the object and annotate the method with @ResponseStatus, or I return ResponseEntity when status or headers depend on the logic. A create returns 201 with a Location header, a delete returns 204, a missing resource gives 404, invalid input 400, a conflict 409.

The status code is part of the API contract: clients, caches and retries act on it. So the controller must send the right one, not a blanket 200.

SituationStatus
Read ok200
Created, return the new resource and its URL201 + Location header
Done, nothing to return (delete, update without body)204
Bad input / validation400 (some teams use 422)
Not logged in / not allowed401 / 403

Conflict (duplicate, version clash)409

Two ways to set it. A fixed status goes on the method with @ResponseStatus. A status or headers that depend on logic go through ResponseEntity.

@PostMapping("/orders")
ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrder in) {
    OrderDto out = service.create(in);
    URI uri = URI.create("/orders/" + out.id());
    return ResponseEntity.created(uri).body(out);          // 201 + Location
}

@DeleteMapping("/orders/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)                     // 204
void delete(@PathVariable long id) { service.delete(id); }

For error statuses do not hand-build ResponseEntity in every method. The service throws a domain exception (OrderNotFoundException) and one global advice maps it to 404 (see the exception-handler question). Alternatively ResponseStatusException throws with a status inline for small cases.

Common mistakes: returning 200 with {"error": ...} (breaks monitoring and client retry logic); returning null for "not found" (gives an empty 200); mixing 401 and 403 (401 = identity unknown, 403 = known but forbidden); using 500 for client mistakes. Also remember idempotence: a repeated PUT or DELETE should not change outcome.

Remember: 201 + Location on create, 204 on delete, throw exceptions for errors and map them in one place.

Why not return JPA entities directly from a controller? Intermediate

Because the API contract and the database model should change independently. If I return an entity, any column rename breaks clients, internal fields (password hash, audit columns) leak by accident, and lazy relations can trigger extra queries or a LazyInitializationException during JSON serialisation. So I map entities to small DTOs (records) and accept DTOs in, not entities.

An entity models a database table; a DTO (data transfer object) models what the API sends or receives. They change for different reasons and at different speeds, so tying them together causes pain.

What goes wrong when an entity is the API:

  1. Contract breaks with schema changes. Rename a column or field and every client breaks, though nothing about the business changed.
  2. Accidental leaks. The User entity has passwordHash, internalNotes, audit columns; they are serialised unless someone remembers to hide each.
  3. Mass assignment. If the entity is the request body, a client can send {"role":"ADMIN","id":1} and Jackson sets those fields.
  4. Lazy loading surprises. Jackson walking a lazy collection triggers extra SQL (the N+1 problem) or a LazyInitializationException if the session is closed. With open-in-view on, queries silently run during rendering.
  5. Infinite recursion with two-way relations (Order.items and Item.order).

With DTOs you choose the exact fields, can version the API, and can attach input validation to the request model without polluting the entity.

public record OrderDto(long id, String status, BigDecimal total) {
    static OrderDto from(Order o) { return new OrderDto(o.getId(), o.getStatus().name(), o.getTotal()); }
}
public record CreateOrder(@NotNull Long customerId, @NotEmpty List<Line> lines) {}

Mapping options: by hand (clear, small), MapStruct (generated at compile time, fast, no reflection), or a Spring Data projection that makes the query return only the DTO fields, avoiding loading whole entities.

Trade-off: DTOs mean extra classes and mapping code. For a quick internal tool some teams accept entities; if you do, at least use @JsonIgnore/views, and set spring.jpa.open-in-view=false. For anything public, use DTOs.

Remember: entity = database shape, DTO = API shape. Never let one leak into the other.

How do you do pagination and sorting in a Boot REST API? Intermediate

With Spring Data I accept a Pageable parameter and return a Page<T>. Boot resolves ?page=0&size=20&sort=createdAt,desc into the Pageable automatically, and the repository turns it into LIMIT/OFFSET plus ORDER BY and a count query.

Returning "all orders" works in a demo and fails with a million rows: memory, latency and bandwidth explode. Pagination returns the data in slices.

Spring Data does most of the work. A Pageable parameter is filled from query parameters, and the repository turns it into SQL.

GET /orders?page=2&size=20&sort=createdAt,desc

@GetMapping("/orders")
Page<OrderDto> list(Pageable pageable) {
    return repo.findAll(pageable).map(OrderDto::from);
}
-- generated: SELECT ... ORDER BY created_at DESC LIMIT 20 OFFSET 40
--            SELECT count(*) FROM orders          (for total elements)

A Page carries the content, total elements, total pages. A Slice skips the count query and only knows "is there a next page", which is cheaper when you do not need the total.

Guard rails to mention:

  • Cap the size. spring.data.web.pageable.max-page-size (default 2000) and a lower default default-page-size.
  • Whitelist sort fields. Sorting by an unindexed column on a large table is a self-inflicted slow query, and arbitrary property names leak your model.
  • Stable JSON. Return your own small response type (items, page, size, total) rather than serialising Spring's Page directly.

Offset vs keyset. Offset paging makes the database walk and discard the skipped rows, so page 50,000 is slow; and if rows are inserted while a user pages, rows shift and get repeated or skipped. Keyset (seek) paging fixes both: remember the last item's sort key and ask for the next ones.

SELECT * FROM orders WHERE (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC LIMIT 20

The price: no jump to arbitrary page number, and the sort key must be unique (add the id as a tie breaker) and indexed.

Remember: Pageable in, Page out; cap the size; for deep or live lists use keyset paging.

How do you validate request input in Boot, and what happens when it fails? Basic

I add spring-boot-starter-validation, put constraints like @NotBlank, @Email, @Positive on the DTO fields, and mark the controller parameter with @Valid. If validation fails, Spring throws MethodArgumentNotValidException, which gives a 400 response. I normally catch it in a global handler to return a clean list of field errors.

Never trust input. Validation checks shape and format at the door so bad data never reaches your logic. Boot uses Bean Validation (Jakarta Validation) with Hibernate Validator as the implementation.

Three steps:

  1. Add the dependency spring-boot-starter-validation.
  2. Put constraints on the DTO.
  3. Put @Valid on the controller parameter.
public record CreateUser(
    @NotBlank @Size(max = 50) String name,
    @Email String email,
    @Min(18) int age,
    @Valid Address address) {}                 // @Valid cascades into the nested object

@PostMapping("/users")
ResponseEntity<?> create(@Valid @RequestBody CreateUser in) { ... }

If a rule fails, Spring throws MethodArgumentNotValidException before your method runs; by default the response is 400. A global handler turns it into a friendly body:

{ "errors": [ {"field":"email","message":"must be a well-formed email address"} ] }

Pitfalls interviewers like:

  • The starter is missing (it was removed from the web starter in Boot 2.3). Nothing is validated and no error is raised: a silent bug.
  • @Valid forgotten, or not placed on the nested field.
  • @NotNull vs @NotEmpty vs @NotBlank: null; null or empty; null, empty or only spaces (strings only).
  • Validation is a first line for shape. Business rules ("does this email already exist?") belong in the service, and uniqueness belongs to a database constraint, because check-then-insert races.

Validation groups (@Validated(OnCreate.class)) let one DTO have different rules for create and update, though separate DTOs are usually clearer.

Remember: starter + constraints on the DTO + @Valid on the parameter. Missing starter means silent no-validation.

How do I validate path variables and request parameters, and which exception do I get? Intermediate

For simple parameters I put constraints directly on them, for example @PathVariable @Min(1) long id, and add @Validated on the controller class. A failure throws ConstraintViolationException (a different exception from the body case, which throws MethodArgumentNotValidException). So a good global handler covers both.

Body validation and parameter validation use different machinery, which is why they throw different exceptions. When a body DTO is annotated with @Valid, Spring MVC validates it while resolving the argument and throws MethodArgumentNotValidException. For simple parameters (a path variable, a query parameter) there is no object to validate, so the constraint sits on the parameter itself and is applied by a method-validation proxy.

@RestController
@Validated                                     // enables parameter constraints (needed before Spring 6.1)
class OrderController {
    @GetMapping("/orders/{id}")
    OrderDto get(@PathVariable @Min(1) long id,
                 @RequestParam @Max(100) int size) { ... }
}

How do you write a custom validation rule, for example a password or unique-email check? Intermediate

I create my own constraint annotation and a ConstraintValidator class that implements the rule. The validator is a Spring bean-aware class, so it can inject a repository. I use this for format rules (strong password, valid country code) and avoid it for rules that need a race-free guarantee, like uniqueness.

Built-in constraints cover common cases. When your rule is domain-specific (strong password, valid country code, end date after start date) you write a reusable constraint in two parts: an annotation that declares it, and a validator class that implements the check.

@Target(FIELD) @Retention(RUNTIME)
@Constraint(validatedBy = StrongPasswordValidator.class)
public @interface StrongPassword {
    String message() default "password too weak";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {
    public boolean isValid(String v, ConstraintValidatorContext c) {
        return v != null && v.length() >= 12 && v.chars().anyMatch(Character::isDigit);
    }
}
// use: record Signup(@StrongPassword String password) {}

Spring creates validators as beans through its own factory, so a validator can inject dependencies (a repository, a clock). That makes a "unique email" validator tempting:

class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {
    UniqueEmailValidator(UserRepository r) {...}
    public boolean isValid(String e, ConstraintValidatorContext c) { return !r.existsByEmail(e); }
}

It reads well but is not a guarantee. Two concurrent signups both see "not exists" and both insert. The correct design is: a unique index in the database as the real rule; the validator only gives an early, friendly message; the service catches DataIntegrityViolationException and returns 409 for the race loser.

Other tips: treat null as valid inside the validator and add @NotNull separately (keeps rules composable); for cross-field rules put the annotation on the class and read both fields; keep validators free of slow I/O, because they run on the request thread for every call; and give errors a stable message key so clients and translations do not depend on English text.

Remember: annotation + ConstraintValidator for format rules; uniqueness is guaranteed by the database, not by the validator.

How do you handle exceptions globally in a Boot REST API? Basic

I write one class annotated with @RestControllerAdvice that has @ExceptionHandler methods. Each method maps an exception type to an HTTP status and a consistent JSON error body. Controllers and services just throw domain exceptions and never build error responses themselves.

Without a plan, every controller catches exceptions and builds its own error JSON, so formats differ and code repeats. The fix is to centralise: services throw meaningful exceptions, and one class translates them to HTTP.

@RestControllerAdvice is a class whose @ExceptionHandler methods apply to all controllers (it is @ControllerAdvice + @ResponseBody). When an exception escapes a controller, Spring looks for the handler whose declared type is closest to the thrown one.

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ApiError> notFound(OrderNotFoundException e) {
        return ResponseEntity.status(404).body(new ApiError("ORDER_NOT_FOUND", e.getMessage()));
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ApiError> invalid(MethodArgumentNotValidException e) { /* field errors, 400 */ }
    @ExceptionHandler(Exception.class)
    ResponseEntity<ApiError> unexpected(Exception e) {
        log.error("Unhandled", e);                       // log once, with stack trace
        return ResponseEntity.status(500).body(new ApiError("INTERNAL", "Something went wrong"));
    }
}

Walk-through: service.find(42) throws OrderNotFoundException; no catch in the controller; the advice maps it to 404 with code ORDER_NOT_FOUND; the client gets a predictable body.

Rules of good practice:

  • Most specific handler wins; the Exception.class catch-all is the safety net.
  • Log once, at the place that decides (the advice), at the right level: 4xx are caller mistakes (info/warn at most), 5xx are our bugs (error with stack trace). Do not log and rethrow at every layer.
  • Never leak internals (SQL, class names, stack traces) in the response; use a correlation/trace id so support can find the log.
  • Extend ResponseEntityExceptionHandler to get tested handlers for Spring's own exceptions (missing parameter, 405, 415, body not readable) and override only the ones you need.

Scope: an @ExceptionHandler inside a single controller only covers that controller, and @RestControllerAdvice(basePackages=...) narrows an advice. It does not catch exceptions from servlet filters (such as security), which are handled elsewhere.

Remember: throw domain exceptions, map them once in @RestControllerAdvice, and never leak internals in the 500.

What is ProblemDetail, and should I use it for error responses? Intermediate

ProblemDetail is Spring's built-in class for the standard "problem details" error format (RFC 7807, updated by RFC 9457). It gives every error the same fields: type, title, status, detail, instance, plus any custom ones. Yes, I would use it, because clients get one predictable error shape and I do not invent my own.

Every team used to invent its own error JSON ({"error":...}, {"message":...}, {"code":...}), so every client wrote custom parsing. RFC 7807 (updated by RFC 9457) defines one standard shape, media type application/problem+json, and Spring 6 / Boot 3 added a class for it, ProblemDetail.

The standard members:

FieldMeaning
typeURI identifying the kind of problem (defaults to about:blank)
titleshort, human-readable summary of the type
statusthe HTTP status
detailexplanation for this particular occurrence
instanceURI of this occurrence (often the request path)

Any extra members are allowed; you add them with setProperty.

@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail notFound(OrderNotFoundException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    pd.setTitle("Order not found");
    pd.setType(URI.create("https://errors.acme.com/order-not-found"));   // stable id
    pd.setProperty("orderId", e.getId());                                // custom member
    return pd;
}
// response: 404, Content-Type: application/problem+json
// {"type":"...","title":"Order not found","status":404,"detail":"...","orderId":42}

To make Spring's built-in exceptions (validation errors, 405, 415, unreadable body) also use this format, set spring.mvc.problemdetails.enabled=true (or extend ResponseEntityExceptionHandler, which produces ProblemDetail).

Guidance: yes, adopt it for new APIs, because tooling and clients understand it. Keep detail safe for outsiders, give clients a stable machine-readable code (the type or a property) so nobody parses message text, and add a trace id. If clients already depend on an old format, do not silently switch: version the API or support both for a while.

Remember: ProblemDetail = the standard error body (application/problem+json). One shape for all errors.

What is the /error endpoint and BasicErrorController? Intermediate

It is Boot's fallback for errors that nobody handled. When an exception escapes the controllers, or a request has no handler (404), the servlet container forwards to /error, where BasicErrorController produces a JSON body (timestamp, status, error, path) for API clients or the "Whitelabel Error Page" for browsers.

Not every error passes through your controllers. A request for a URL that has no handler (404), an exception in a servlet filter, or a failure after you wrote part of the response happens outside MVC's exception handling. The servlet container still has to answer, so Boot registers an error page pointing at /error, and BasicErrorController handles that path.

Flow for an unknown URL:

  1. No handler found, so the container (or Spring) marks the response as an error with status 404.
  2. The container forwards internally to /error.
  3. BasicErrorController checks the Accept header: for JSON clients it returns a map, for browsers it renders the "Whitelabel Error Page" (or error.html / error/404.html if you provide one).
{ "timestamp": "...", "status": 404, "error": "Not Found", "path": "/nope" }

How this interacts with your advice: @RestControllerAdvice handles exceptions thrown from controller methods first, so only unhandled ones reach /error. To make 404s for unknown paths also pass through your advice, set spring.mvc.throw-exception-if-no-handler-found=true and spring.web.resources.add-mappings=false; in Spring 6.1+ unmatched requests raise NoResourceFoundException, which your advice can map.

Security of the fallback: attributes that may leak internals are controlled by server.error.include-message, include-stacktrace, include-binding-errors and include-exception. Defaults are "never" for message, stack trace and binding errors; keep them so in production, and use logs for detail. To change the output globally, provide your own ErrorAttributes bean or extend BasicErrorController; or enable ProblemDetail so fallback and handled errors share one format.

Pitfall: with Spring Security, errors can be forwarded to /error and then blocked as unauthenticated, turning a 500 into a confusing 401/403; permit /error in your security rules.

Remember: /error is the safety net for unhandled errors. Keep message and stack trace off in production.

How is Jackson configured in Boot, and what are the usual JSON problems? Intermediate

Boot auto-configures one shared ObjectMapper with sensible defaults, and I tune it through spring.jackson.* properties or a Jackson2ObjectMapperBuilderCustomizer rather than creating my own mapper. Boot's defaults include ignoring unknown JSON properties and writing dates as ISO strings, not numbers.

Jackson is the library that converts Java objects to JSON and back. In Boot the web layer, RestClient, Actuator and Spring Data REST all use one shared ObjectMapper bean that Boot builds for you. Boot starts from a few opinionated defaults (it differs from a raw Jackson mapper): it registers modules found on the classpath (Java time, Jdk8, parameter names), writes dates as ISO-8601 strings instead of numbers, and does not fail on unknown JSON properties.

You adjust it in two ways, and neither requires building your own mapper:

# application.yml
spring:
  jackson:
    default-property-inclusion: non_null      # omit nulls
    property-naming-strategy: SNAKE_CASE
    time-zone: UTC
    deserialization:
      fail-on-unknown-properties: false

// or programmatically
@Bean Jackson2ObjectMapperBuilderCustomizer c() { return b -> b.simpleDateFormat("yyyy-MM-dd"); }

Rule: always inject the Boot ObjectMapper (or the builder), so every part of the app obeys the same rules. Per-class tweaks use annotations such as @JsonIgnore, @JsonFormat, @JsonProperty. Security note: do not enable Jackson default typing for untrusted input (deserialisation gadgets). Versions: Jackson 2 in Boot 3; Boot 4 is expected to move to Jackson 3, so check its migration notes.

Remember: inject Boot's ObjectMapper, tune with spring.jackson.* or a customizer, never `new ObjectMapper()`.

How do I call another service from Boot, and what are the traps with timeouts? Intermediate

In Boot 3.2 and later I use RestClient (blocking, fluent) built from the auto-configured RestClient.Builder; WebClient is for reactive code and RestTemplate is in maintenance mode. The main trap is timeouts: by default there are none, so one slow downstream can hold all my threads.

Calling another HTTP service is the most common source of production incidents in microservices, because a slow dependency can use up all your threads. Three decisions: which client, timeouts, and failure policy.

Which client. RestClient (Spring 6.1 / Boot 3.2) is the modern blocking, fluent client and the default choice for servlet apps. WebClient is for reactive code (it also works in servlet apps but is non-blocking by design). RestTemplate still works but is in maintenance mode. Declarative interfaces (@HttpExchange) sit on top of RestClient.

@Bean
RestClient inventory(RestClient.Builder b) {
    var f = ClientHttpRequestFactoryBuilder.detect().build(
        ClientHttpRequestFactorySettings.defaults()
            .withConnectTimeout(Duration.ofSeconds(1))
            .withReadTimeout(Duration.ofSeconds(3)));
    return b.baseUrl("http://inventory").requestFactory(f).build();
}
// use
Stock s = inventory.get().uri("/stock/{sku}", sku).retrieve().body(Stock.class);

(The request-factory builder classes are from Boot 3.4; in 3.2/3.3 you set the timeouts on the ClientHttpRequestFactory directly. Newer versions also expose spring.http.client.* properties. Check your version.)

Timeouts. Many underlying clients have no timeout by default (or a very long one). Picture 200 Tomcat threads, a downstream that hangs, and each request waiting forever: after 200 requests your whole service is frozen even though it is healthy. Always set a connect timeout (about a second) and a read timeout (just above the downstream's normal p99).

Failure policy.

  • Retry only idempotent calls (GET, or PUT with an idempotency key), with exponential backoff and jitter, never on 4xx, and cap attempts.
  • Add a circuit breaker and bulkhead (Resilience4j) so a failing dependency fails fast.
  • Translate HttpClientErrorException/HttpServerErrorException into your domain exceptions at one boundary so callers do not see HTTP details.

Inject the Boot-provided builder, not RestClient.create(), so metrics, tracing headers and message converters are applied. For service-to-service calls, propagate the trace id.

Remember: RestClient from the Boot builder, always a timeout, retry only idempotent calls.

What does Boot do for security by default, and how do I configure my own rules? Intermediate

As soon as spring-boot-starter-security is on the classpath, Boot protects every endpoint with HTTP basic and a form login, using a generated password printed in the log. To configure real rules I define a SecurityFilterChain bean. The old WebSecurityConfigurerAdapter was removed in Spring Security 6 (Boot 3).

Boot is "secure by default" the moment Spring Security is on the classpath. Adding spring-boot-starter-security triggers auto-configuration that: requires authentication for every request, enables form login and HTTP basic, enables CSRF protection and security headers, and creates a user named user with a random password printed at startup ("Using generated security password: ..."). It is deliberately restrictive so you cannot forget to secure something.

To define real rules, publish a SecurityFilterChain bean. Because your bean exists, Boot's default chain backs off (the same override pattern as everywhere). Since Spring Security 6 (Boot 3) the old WebSecurityConfigurerAdapter is gone; configuration is component-based with lambdas.

@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())                      // stateless token API only
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))   // validate bearer JWTs
        .build();
}

Key points:

  • Order matters. Matchers are checked top to bottom and the first match wins; put specific rules first and anyRequest() last. Deny by default.
  • CSRF. Needed when the browser sends credentials automatically (cookies, sessions). For a stateless API using a bearer token in a header, it can be disabled. Disabling it on a cookie-based app is a vulnerability.
  • Several chains. You can publish multiple SecurityFilterChain beans with securityMatcher and @Order, for example one for /api/** (JWT) and one for the admin UI (form login).
  • Actuator. Secure it; allow only health/info to the platform's probes.

Classic surprise: a library that pulls in the security starter transitively makes every endpoint answer 401 after an innocent dependency change. In tests use spring-security-test (@WithMockUser, jwt()). Authentication internals and method security are on the Spring Framework page.

Remember: add the starter and everything is locked; define a SecurityFilterChain bean to set your own rules.

How does Boot configure a DataSource, and what happens if there is no URL? Basic

If a JDBC driver is on the classpath, Boot creates a DataSource from spring.datasource.url, username and password, and picks the connection pool it finds, HikariCP by default. Only for an embedded database (H2, HSQL, Derby) can it work without a URL. For anything else, a missing URL fails startup with "Failed to configure a DataSource: 'url' attribute is not specified".

A DataSource is the object that hands out database connections. Boot creates one for you by following a short decision chain at startup:

  1. Is a JDBC DataSource class and a driver or an embedded DB on the classpath? If not, nothing happens.
  2. Is spring.datasource.url set? If yes, build a DataSource from it (plus username, password). The driver class is guessed from the URL.
  3. If there is no URL, but an embedded database (H2, HSQL, Derby) is on the classpath, create an in-memory one with default settings.
  4. Otherwise fail.
spring.datasource.url=jdbc:postgresql://db:5432/orders
spring.datasource.username=app
spring.datasource.password=${DB_PASSWORD}
spring.datasource.hikari.maximum-pool-size=10

Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.

Pool choice: Boot picks the first it finds, in this order of preference: HikariCP, Tomcat JDBC, Commons DBCP2. starter-jdbc and starter-data-jpa bring Hikari, so it is the default.

On top of the DataSource, Boot wires JdbcTemplate, the transaction manager and, with JPA, the EntityManagerFactory. All use this one DataSource. If you define your own DataSource bean the default backs off, and then the spring.datasource.url properties no longer apply unless you bind them yourself.

The classic surprise: "my app does not use a database but fails with this message". Cause: something transitive added spring-jdbc or a JPA starter. Fixes in order: remove the unneeded dependency; or set spring.autoconfigure.exclude for DataSourceAutoConfiguration. The opposite surprise: an embedded H2 is silently used in production because the URL property was misspelled or missing in that environment, so data vanishes on restart. Failing fast on a missing URL is therefore a feature; in tests, H2 or Testcontainers are chosen deliberately.

Remember: JDBC on classpath + no URL = startup failure, unless it is an embedded DB. Unwanted? Remove the dependency or exclude it.

How do you size and tune HikariCP? What are the key settings? Senior

I keep the pool small, because the database can only do so much in parallel. The default maximum-pool-size is 10 and it is often enough. A good starting rule is roughly (number of DB cores x 2) plus the disk spindles, then I measure. Raising the pool to hundreds usually makes the database slower, not faster. Multiply by the number of pods: 20 pods x 10 connections is already 200 connections on the database.

A connection pool keeps a fixed set of open database connections and lends them to request threads, because opening a connection is slow (tens of milliseconds, plus authentication). HikariCP is Boot's default pool.

Why small is better. A database server has a limited number of cores and disks. Once enough queries are running to keep them busy, extra concurrent queries only fight for CPU, locks and cache and make everything slower. The classic starting formula from the HikariCP wiki is roughly connections = (core_count x 2) + effective_spindle_count for the database server, then measure. A 4-core DB is happy with about 10 active connections. Another 190 threads should wait in line for a connection, which is cheap, not hammer the database.

Do the multiplication. The pool is per pod. 20 pods x 10 connections = 200 connections, and each Postgres connection is a process using memory. During autoscaling the total grows. Size for maxPods x pool and consider a proxy (PgBouncer, RDS Proxy) if the number gets large.

When the pool is exhausted you see Connection is not available, request timed out after 30000ms. Check the metrics hikaricp.connections.active, pending and acquire time. "Increase the pool" is usually the wrong answer; ask who holds connections for too long. Causes: a slow query, a transaction that includes an HTTP call or file I/O, a missing index, a leak (connection not returned), or open-in-view keeping the connection through the whole request. Fix the holder; maybe lower connection-timeout so callers fail fast (30 s of waiting threads is itself an outage).

Remember: small pool x number of pods must fit the database. Exhaustion means find who holds connections, before you raise the maximum.

Which JPA and Hibernate properties matter in a Boot app, especially ddl-auto? Intermediate

The important one is spring.jpa.hibernate.ddl-auto. For embedded databases Boot defaults to create-drop, for real databases to none. In production I use none or validate and manage the schema with Flyway or Liquibase. update is tempting but unsafe: it only adds, never drops or renames, and can run unreviewed changes against production.

Most JPA problems in Boot come from a handful of settings. The first one decides who owns the schema.

ddl-auto tells Hibernate what to do with the schema at startup:

ValueEffectUse
nonenothingproduction default for real DBs
validatecheck the schema matches entities, fail if notproduction with migrations: catches drift
updateadd missing tables and columns, never drops or renamesquick prototypes only
create / create-dropdrop and rebuild (create-drop also drops at shutdown)tests, embedded DB (Boot's default for embedded)

update is dangerous in production: changes are not reviewed or versioned, a rename becomes "new column, old data stays behind", and it runs against live data on whichever pod boots first. Use Flyway or Liquibase for schema changes and validate to prove entities and schema agree.

Other properties worth knowing:

  • spring.jpa.open-in-view=false (next question).
  • logging.level.org.hibernate.SQL=DEBUG shows the SQL through the logger (better than show-sql, which prints to stdout); add org.hibernate.orm.jdbc.bind=TRACE to see parameters in Hibernate 6. Dev only.
  • spring.jpa.properties.hibernate.jdbc.batch_size=50 plus order_inserts=true, order_updates=true: needed for real JDBC batching. Note that identity (auto-increment) keys disable insert batching in Hibernate; use a sequence.
  • spring.jpa.properties.hibernate.default_batch_fetch_size=50: turns N+1 lazy loads into "IN (...)" batches; a cheap mitigation.
  • Naming: Boot's default strategy converts firstName to column first_name (snake_case), which surprises people expecting the literal name.

Entity-level problems (N+1, lazy loading, fetch joins, locking) belong to the Hibernate and JPA page.

Remember: production ddl-auto = none or validate; schema changes go through migrations.

What is open-in-view, and why do people turn it off? Intermediate

Open Session in View keeps the JPA EntityManager (and its database connection) open for the whole web request, until the response is written. That lets lazy relations load in the controller or during JSON serialisation without error. It is on by default in Boot (with a warning at startup), and I turn it off with spring.jpa.open-in-view=false.

A lazy relation (say order.getItems()) is loaded on first access, which needs an open Hibernate session. Normally the session lives only inside the @Transactional service method. If you return an entity from the service and the controller or Jackson touches items afterwards, the session is already closed and you get LazyInitializationException.

Open Session in View (OSIV) is a web filter/interceptor that keeps the EntityManager open for the whole HTTP request, until the response is written. Lazy loading then works anywhere. Boot enables it by default (spring.jpa.open-in-view=true) and logs a warning at startup, because it is controversial.

Timeline of one request with OSIV on:

  1. Request arrives; the session opens (a DB connection is taken from the pool on first use and, in default mode, kept).
  2. Service runs a transaction and returns an entity.
  3. Controller calls a remote service for 500 ms.
  4. Jackson serialises the entity and lazy-loads items: extra queries (N+1), outside any transaction.
  5. Response sent; the connection is released only now.

Why teams turn it off:

  • Connections held too long. Slow remote calls and serialisation keep a pooled connection busy, exhausting the pool under load.
  • Hidden N+1. Queries fire from the web layer, unnoticed in code review.
  • Blurred layers. Data access happens outside transactions, with surprising isolation and read-after-write behaviour.

With spring.jpa.open-in-view=false, lazy access outside the service throws. That is the point: load what you need inside the service with a fetch join, an entity graph or a DTO projection, and return DTOs.

@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(long id);

Switching an existing app off may reveal hidden lazy loads; fix them one by one. For tiny apps with templates (server-side pages) OSIV is tolerable, but for REST APIs prefer off.

Remember: open-in-view holds a connection for the whole request and hides N+1. Turn it off, fetch in the service.

How do Flyway and Liquibase work with Boot, and what goes wrong? Intermediate

Add the Flyway or Liquibase dependency and Boot runs the migrations automatically at startup, before the JPA layer uses the schema. Each migration runs once, in order, and the tool records it in a history table (flyway_schema_history). Flyway migrations are versioned SQL files such as db/migration/V3__add_index.sql.

Database schemas change over time, and every environment (your laptop, test, production) must reach the same schema in the same order. Flyway and Liquibase are migration tools: you write numbered change scripts, and the tool applies the ones that have not run yet and records them in a history table.

With Boot you just add the dependency (flyway-core, plus the database-specific module for some databases in newer Flyway versions, or liquibase-core). Boot's auto-configuration runs the migration at startup, before the JPA EntityManagerFactory is used.

src/main/resources/db/migration/
  V1__create_orders.sql
  V2__add_status.sql
  V3__add_index.sql

-- flyway_schema_history records version, description, checksum, success, time

Flyway uses plain SQL files named V<version>__<description>.sql (repeatable ones use R__). Liquibase uses changelogs (XML/YAML/SQL) with changesets, which is more database-neutral and supports rollbacks.

What goes wrong:

  • Checksum mismatch. Someone edits V2 after it ran. Flyway compares the stored hash and refuses to start. Rule: an applied migration is immutable; fix forward with V4.
  • Two branches both add V5. Conflict at merge or out-of-order error. Agree numbering, use timestamps, or allow out-of-order for dev only.
  • Several pods start together. The tool takes a lock (on the history table or a DB advisory lock) so one migrates and others wait.
  • Long, locking migration on a big table blocks traffic during deploy. Use expand and contract: add a nullable column, deploy code that writes both, backfill in batches, switch reads, drop the old column in a later release. Also keep old and new app versions compatible with the schema during a rolling deploy.
  • Rollback. Do not rely on undo scripts; plan forward fixes.

Pair it with ddl-auto=validate so a mismatch between entities and schema fails fast. In tests, run the real migrations against a Testcontainers database to catch SQL differences from H2.

Remember: never edit an applied migration. Fix forward with a new version.

How do you use two databases in one Boot app? Senior

Boot only auto-configures one DataSource, so for two databases I define both myself: two DataSource beans (one marked @Primary), and for JPA a separate EntityManagerFactory and transaction manager each. Then each set of repositories is pointed at its own factory with @EnableJpaRepositories and its own package.

Boot's data auto-configuration assumes exactly one DataSource and backs off as soon as it finds your own. So when you need two databases (orders and reporting, or two schemas), you take over and build each stack yourself. "A stack" means: DataSource, and for JPA an EntityManagerFactory and a transaction manager. Each set of repositories must point at its own stack.

@Configuration
@EnableJpaRepositories(basePackages = "com.acme.orders",
    entityManagerFactoryRef = "ordersEmf", transactionManagerRef = "ordersTx")
class OrdersDbConfig {
    @Bean @Primary @ConfigurationProperties("app.orders.datasource")
    DataSource ordersDataSource() { return DataSourceBuilder.create().build(); }

    @Bean @Primary
    LocalContainerEntityManagerFactoryBean ordersEmf(EntityManagerFactoryBuilder b, DataSource ordersDataSource) {
        return b.dataSource(ordersDataSource).packages("com.acme.orders.model").persistenceUnit("orders").build();
    }
    @Bean @Primary
    PlatformTransactionManager ordersTx(@Qualifier("ordersEmf") EntityManagerFactory emf) {
        return new JpaTransactionManager(emf);
    }
}
// BillingDbConfig: same pattern, other package, no @Primary, own property prefix

Properties then use your own prefixes (app.orders.datasource.url, app.billing.datasource.url), because spring.datasource.* is bound only for Boot's default one.

Pitfalls to mention:

  • Which transaction manager? @Transactional uses the @Primary one; for the other, write @Transactional("billingTx"). A wrong choice silently runs without the transaction you thought.
  • No cross-database atomicity. Updating both in one method can commit one and fail the other. Do not fake two-phase commit by hand; use the outbox pattern or a saga, or accept eventual consistency. (XA/JTA exists but is heavy and rarely worth it.)
  • Separate entity and repository packages per database, otherwise repositories bind to the wrong factory.
  • Flyway needs a configuration per DataSource too.
  • Two pools means pool-size math doubles.

If the second database is only a read replica of the same data, a routing AbstractRoutingDataSource (choose by read-only transaction) is simpler than two full stacks. For plain JDBC, two JdbcTemplate beans are enough.

Remember: two DBs = two of everything (DataSource, EMF, tx manager), one @Primary, and no shared transaction.

7. Actuator, logging and observability

How does logging work in Boot, and how do you configure it? Basic

Boot logs through SLF4J with Logback as the default implementation, so my code uses LoggerFactory.getLogger(...) or Lombok's @Slf4j. The default level is INFO to the console. I set levels in properties, for example logging.level.com.acme=DEBUG or logging.level.org.hibernate.SQL=DEBUG, and for anything more I add logback-spring.xml.

Boot logging has three layers. SLF4J is the API your code calls (log.info(...)). Logback is the implementation Boot chooses by default. Spring Boot's logging system glues it up: console output, colours, level properties, and a hook for your own config. Libraries that use other APIs (Commons Logging, Log4j2 API, java.util.logging) are redirected to SLF4J, so everything ends in one place.

Configuration, from simple to full:

logging.level.root=INFO
logging.level.com.acme.orders=DEBUG
logging.level.org.hibernate.SQL=DEBUG            # package or class based
logging.pattern.console=%d %-5level [%X{traceId:-}] %logger{36} - %msg%n
logging.group.db=org.hibernate.SQL,org.hibernate.orm.jdbc.bind   # name a group of loggers
logging.level.db=DEBUG

<!-- logback-spring.xml: profile-aware, can use Spring properties -->
<springProfile name="prod"><root level="INFO"><appender-ref ref="JSON"/></root></springProfile>

Why logback-spring.xml and not logback.xml: plain logback.xml is read by Logback very early, before Boot's environment is ready, so <springProfile> and <springProperty> do not work. The -spring name is picked up by Boot at the right moment.

Container practice: write to the console (stdout), one event per line, and let the platform (Kubernetes, a log agent) collect and ship it. Rotating files inside a container are lost with the pod and add disk concerns. Structured JSON logs are searchable: Boot 3.4 added built-in support (logging.structured.format.console=ecs, also logstash and gelf); on older versions use a Logback JSON encoder.

Runtime and correlation: change levels live through POST /actuator/loggers/com.acme (secure it) to debug a live issue without redeploy, then put it back. With Micrometer Tracing the trace and span ids go into the MDC, so one request can be followed across services. Do not log secrets or personal data, and avoid logging inside tight loops. To switch to Log4j2, exclude spring-boot-starter-logging and add spring-boot-starter-log4j2.

Remember: SLF4J + Logback, levels in properties, logback-spring.xml for more, JSON to stdout in containers.

What is Actuator, and which endpoints matter most? Basic

How do you secure Actuator endpoints? Intermediate

Three layers: expose only the endpoints I need, move them to a separate management port that the public ingress does not route, and require authentication (with an admin role) for anything sensitive. Health and the probes may stay open to the platform; env, heapdump, loggers and threaddump must never be public.

Actuator endpoints are an operator's back door into the app, so treat them like an admin interface. The right model is defence in depth: three independent layers, so one mistake does not expose you.

  1. Expose less. List only the endpoints you need in management.endpoints.web.exposure.include. Never use * in production.
  2. Separate the network path. Set management.server.port (and optionally management.server.address) so actuator is on its own port. The public Ingress or load balancer routes only the application port; a network policy lets only the monitoring system reach the management port.
  3. Authenticate. With Spring Security, allow the probe endpoints and require a role for the rest.
management:
  server.port: 9090
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health.show-details: when_authorized

@Bean SecurityFilterChain actuator(HttpSecurity http) throws Exception {
    return http.securityMatcher(EndpointRequest.toAnyEndpoint())
        .authorizeHttpRequests(a -> a
            .requestMatchers(EndpointRequest.to("health", "info")).permitAll()
            .anyRequest().hasRole("OPS"))
        .httpBasic(Customizer.withDefaults()).build();
}

What an attacker or leak gets from unsecured endpoints:

  • heapdump: the whole memory, including session tokens, passwords and keys. Real breaches have started here.
  • env / configprops: connection strings and keys (Boot 3 masks all values by default, and you opt in to show them; do not rely on masking).
  • loggers (write): turn on TRACE everywhere, flooding disks and leaking data to logs.
  • shutdown (disabled by default): stop the app.
  • mappings, beans: a map of your attack surface.

Also hide health details from anonymous users (show-details), because a detailed health page tells which database and version you run. Test it: from outside the cluster, request /actuator/env and confirm a 404 or 401.

Remember: minimum exposure + separate port + auth. Never expose heapdump or env publicly.

How does the health endpoint work, and how do you write a custom health indicator? Intermediate

The health endpoint asks every HealthIndicator bean (database, disk, Redis, Kafka and so on, auto-detected from the classpath) and combines the results into one status: the worst one wins (DOWN beats UP). To add my own, I implement HealthIndicator or extend AbstractHealthIndicator, and the bean name becomes the key in the output.

The /actuator/health response is the combination of many small checks. Each check is a bean implementing HealthIndicator. Boot auto-registers indicators for what it finds on the classpath: db (runs a validation query), diskSpace, redis, mongo, kafka, and more. The HealthEndpoint asks each, then a StatusAggregator combines them: by default the worst status wins, in the order DOWN, OUT_OF_SERVICE, UP, UNKNOWN. One DOWN makes the whole thing DOWN (HTTP 503).

{ "status": "DOWN",
  "components": { "db": {"status":"UP"},
                  "paymentGateway": {"status":"DOWN","details":{"error":"timeout"}} } }

Writing your own:

@Component
class PaymentGatewayHealth implements HealthIndicator {     // bean name "paymentGatewayHealth" -> key "paymentGateway"
    public Health health() {
        try {
            gateway.ping();                                  // must be fast, with a timeout
            return Health.up().withDetail("latencyMs", 12).build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}

The key is the bean name with the "HealthIndicator" suffix removed. AbstractHealthIndicator handles try/catch for you. For reactive apps use ReactiveHealthIndicator.

Design judgment, the part interviewers care about:

  • Be cheap and bounded. Probes run every few seconds from several callers on a request thread. A slow check ties up threads, and a check that hangs makes the probe time out. Use short timeouts or cache results.
  • Choose what the platform sees. If every dependency feeds liveness, a database outage restarts all pods for nothing. Use health groups: management.endpoint.health.group.readiness.include=readinessState,db and keep liveness to the process state only.
  • Optional dependencies should not turn the whole app DOWN; report them as a detail, or map to a custom status with management.endpoint.health.status.order.
  • Details are hidden by default; show-details=when_authorized reveals them to authenticated users.

Remember: worst status wins. Keep checks fast, and choose carefully what feeds liveness versus readiness.

What are liveness and readiness probes in Boot, and how do they map to Kubernetes? Senior

Liveness answers "is the process stuck beyond repair, should Kubernetes restart it?". Readiness answers "can this pod take traffic right now?". Boot exposes both as /actuator/health/liveness and /actuator/health/readiness (enabled automatically on Kubernetes). A failing readiness removes the pod from the Service; a failing liveness restarts the container.

Kubernetes needs two separate answers about a pod, because the right reaction differs:

ProbeQuestionIf it failsBoot endpoint
LivenessIs the process broken beyond self-repair (deadlock, corrupted state)?kubelet restarts the container/actuator/health/liveness
ReadinessCan this pod serve requests right now?pod removed from Service endpoints; no restart/actuator/health/readiness
StartupHas the app finished booting?keeps liveness and readiness off until it passes, restarts after too many failuresusually the liveness URL

Boot supports these through availability state: LivenessState (CORRECT/BROKEN) and ReadinessState (ACCEPTING_TRAFFIC/REFUSING_TRAFFIC). The groups are on automatically on Kubernetes (or with management.endpoint.health.probes.enabled=true). Your code can mark itself unready or broken by publishing an AvailabilityChangeEvent.

livenessProbe:  { httpGet: {path: /actuator/health/liveness,  port: 9090}, periodSeconds: 10, failureThreshold: 3 }
readinessProbe: { httpGet: {path: /actuator/health/readiness, port: 9090}, periodSeconds: 5 }
startupProbe:   { httpGet: {path: /actuator/health/liveness,  port: 9090}, periodSeconds: 5, failureThreshold: 30 }

The big rule: liveness must not depend on external systems. Scenario: liveness includes the database check; the database has a 2 minute outage; all 20 pods fail liveness together and get restarted in a loop; when the database returns, the pods are still booting and the service is down longer than the outage. The fix is that liveness reflects only "this JVM can still respond".

Readiness can include a dependency the pod truly cannot work without, but a shared dependency again makes every pod unready at the same time (zero endpoints, hard errors instead of degraded service). Often it is better to stay ready and return errors or fallback for the affected features.

Graceful shutdown ties in: on SIGTERM Boot sets readiness to REFUSING_TRAFFIC, the load balancer stops sending new requests, in-flight ones finish within the shutdown timeout, and then the app stops. Add a short preStop sleep because endpoint removal takes a moment to propagate. Use the startup probe for slow starts so a long migration is not killed by liveness.

Remember: readiness failing = pause traffic, liveness failing = restart. Never put shared dependencies in liveness.

What is Micrometer, and how do metrics reach Prometheus? Intermediate

Micrometer is the metrics facade of Boot, like SLF4J for metrics: my code records counters, timers and gauges once, and a registry for the chosen backend exports them. For Prometheus I add micrometer-registry-prometheus, expose /actuator/prometheus, and Prometheus scrapes (pulls) that URL every 15 to 30 seconds.

Micrometer is a vendor-neutral metrics API, "SLF4J for metrics". Your code records measurements once against Micrometer's types; a registry for the chosen monitoring system (Prometheus, Datadog, CloudWatch, OTLP) turns them into that system's format. Switching vendors means swapping a dependency, not code.

The three basic meter types:

  • Counter: only goes up (orders placed, errors). Query it as a rate.
  • Gauge: a current value that goes up and down (queue size, active connections).
  • Timer / DistributionSummary: durations and sizes with count, sum, max and optional percentiles/histograms.

Prometheus path:

  1. Add micrometer-registry-prometheus and expose the endpoint: management.endpoints.web.exposure.include=prometheus.
  2. Prometheus pulls GET /actuator/prometheus every 15 to 30 s (scrape config or a Kubernetes ServiceMonitor).
  3. Grafana queries Prometheus; Alertmanager alerts on expressions.
# HELP http_server_requests_seconds
http_server_requests_seconds_count{method="GET",status="200",uri="/orders/{id}"} 1532
http_server_requests_seconds_sum{...} 61.4

Boot instruments a lot for free: JVM memory, GC, threads, CPU, class loading, Tomcat, http.server.requests (with the URI template, not the raw URL), hikaricp.*, cache, Kafka, RestClient timings. Alerts that pay off: HTTP 5xx rate, p95/p99 latency, Hikari pending above zero, heap after GC trending up, GC pause time, thread pool saturation.

Tuning: percentiles and histograms are off by default (management.metrics.distribution.percentiles-histogram.http.server.requests=true enables histogram buckets so Prometheus can compute p99 across pods; avoid client-side percentiles, which cannot be aggregated). Add a common tag management.metrics.tags.application=orders so dashboards can filter. Because Prometheus pulls, short-lived batch jobs need a push gateway or an OTLP push registry.

Remember: Micrometer records, a registry exports, Prometheus scrapes /actuator/prometheus.

How do you add a custom business metric, and what is "cardinality"? Intermediate

I inject the MeterRegistry and create a counter, timer or gauge with a name and a few tags. Cardinality is the number of distinct tag-value combinations: each combination is a separate time series stored by the metrics system, so a tag with unbounded values (user id, order id, URL with ids) can blow up memory and cost.

Technical metrics tell you the app is alive; business metrics tell you whether it is doing its job (orders per minute, payment failures, queue backlog). You create them with the auto-configured MeterRegistry.

@Service
class OrderService {
    private final Counter placed;
    private final Timer payTimer;
    OrderService(MeterRegistry r, OrderQueue queue) {
        placed   = Counter.builder("orders.placed").tag("channel", "web").register(r);
        payTimer = Timer.builder("orders.payment").publishPercentileHistogram().register(r);
        Gauge.builder("orders.queue.size", queue, OrderQueue::size).register(r);   // sampled value
    }
    void place(Order o) { payTimer.record(() -> pay(o)); placed.increment(); }
}

Pick the type by the question: "how many times" is a counter, "how long" is a timer, "what is it now" is a gauge. Naming: dotted lowercase (orders.placed); the Prometheus registry renders orders_placed_total. Convenience: @Timed on a method, or the Observation API when one instrumentation point should give both a metric and a trace span.

Cardinality is the number of distinct time series. Every unique combination of metric name and tag values is stored as its own series in the backend.

Example: orders.placed with tag channel (web, app, partner) is 3 series. Add region (10 values) and it is 30. Add userId with a million users and it is 30 million series: Prometheus memory and storage explode, queries slow down, and a managed vendor sends a huge bill. The same happens with raw URLs containing ids, exception messages, or timestamps.

Rules: tags are small, bounded sets known at design time (status, channel, region, outcome). Put identifiers in logs and traces, which are made for high-cardinality detail. Boot's http.server.requests uses the URI template (/orders/{id}) for exactly this reason, which is also why you should avoid manually tagging raw paths. Register meters once (in the constructor), not on every call, to avoid lookup cost and accidental new tags.

Remember: few, bounded tag values. High-cardinality tags (ids) kill the metrics backend.

How does distributed tracing work in Boot 3? Senior

Spring Cloud Sleuth is gone in Boot 3; tracing is now Micrometer Tracing with a bridge to OpenTelemetry (or Brave). A request gets a trace id when it enters the system, each unit of work is a span with its own id, and the ids travel to the next service in HTTP headers (W3C traceparent). The ids are also put in the log context, so I can search all logs for one request.

In a microservice system one user click fans out into many calls. Logs from each service are separate, so "why was this slow?" needs a thread connecting them: that is distributed tracing.

The vocabulary:

  • Trace: the whole journey of one request, identified by a trace id created at the entry point.
  • Span: one unit of work within it (the controller, a DB query, an outgoing HTTP call), with its own span id, a parent span id, start time and duration.
  • Context propagation: the trace id and parent span id are passed to the next service in a header, standardised as W3C traceparent (00-<traceId>-<spanId>-01).
Trace 4bf9...  gateway(120 ms)
                +- orders(95 ms)
                     +- inventory(20 ms)
                     +- payments(60 ms)   <- the slow one
                          +- psp-call(55 ms)

Boot 3 setup: Spring Cloud Sleuth is gone; tracing is Micrometer Tracing (an API, built on the Observation API) with a bridge to a tracer. Typical dependencies: micrometer-tracing-bridge-otel and opentelemetry-exporter-otlp, sending to a collector or backend such as Tempo, Jaeger or Zipkin.

management.tracing.sampling.probability=1.0     # default 0.1 (10 percent); 1.0 for dev/test
management.otlp.tracing.endpoint=http://collector:4318/v1/traces
logging.pattern.level=%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]

The trace and span ids go into the logging MDC, so you can search logs by trace id.

What breaks propagation, the usual interview probe:

  • new RestTemplate() or RestClient.create(): not instrumented. Use the Boot-provided builders (RestClient.Builder, RestTemplateBuilder, WebClient.Builder).
  • Thread hops: @Async or custom executors lose the context unless wrapped (context-propagating task decorator; Boot's auto-configured executors can be set to propagate).
  • Messaging: Kafka needs observation enabled (spring.kafka.template.observation-enabled, and the listener one) so the context travels in record headers.

Sampling trades cost against completeness: 100 percent traces at high traffic are expensive, so sample (head sampling) or use tail sampling in the collector to keep slow and failed traces. Never put personal data in span attributes.

Remember: trace id travels in headers, spans form the tree, sampling is 10 percent by default. Use Boot's builders so propagation works.

8. Testing Boot applications

What does @SpringBootTest do, and what are its web environment modes? Basic

@SpringBootTest starts the full application context, with auto-configuration and all my beans, so I can test components wired together. By default (MOCK) there is no real server: MockMvc is used. With RANDOM_PORT it starts a real embedded server on a free port, and I call it with TestRestTemplate or WebTestClient.

Unit tests check one class with its collaborators faked. But many Boot bugs live in the wiring: a missing bean, a wrong property name, a filter in the wrong order, a JSON mapping. @SpringBootTest catches those because it starts the real application context for the test: component scan, auto-configuration, properties and all your beans, the same way main would.

The cost: startup in seconds, and a different configuration means a new context (see the context cache question). So use it for a handful of end-to-end tests of the main paths, and test logic as plain unit tests and wiring per layer with slices.

Gotcha: with RANDOM_PORT a test-method @Transactional does not help, because the HTTP call is handled by a server thread with its own transaction; the data it committed is not rolled back, so clean up explicitly or use unique data.

Remember: full context = slow. Few @SpringBootTest, many unit tests and slices.

What are test slices? Name the main ones. Intermediate

A slice test loads only the part of the application one layer needs, so it starts in a second or two instead of loading everything. The main ones: @WebMvcTest (controllers, with MockMvc), @DataJpaTest (repositories and an in-memory or container database), @JsonTest (serialisation), @RestClientTest (a client with a mock server), and @DataJdbcTest.

The full context is slow because it creates everything. But a controller test does not need a database, and a repository test does not need controllers. A slice loads only the beans and auto-configurations of one layer.

AnnotationLoadsTypical use
@WebMvcTestcontrollers, advice, filters, converters (not services or repos)mapping, validation, status codes, JSON
@DataJpaTestentities, repositories, DataSource, rolled-back transactionsqueries, mappings

How they work: each is a meta-annotation that applies an include-filter on component scan (only matching bean types, such as @Controller) and imports just the auto-configurations listed for that layer. Everything else is absent, so a missing collaborator must be supplied:

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @MockitoBean OrderService service;   // the service is not in the slice
    @Autowired MockMvc mvc;
}

Why use them: a slice starts in about a second or two, fails with a message pointing to one layer, and keeps the test honest about what the layer depends on.

Traps: "No qualifying bean of type ..." means your layer needs a bean the slice does not load; mock it or @Import it. Putting extra annotations (@EnableScheduling, component scans, @Bean methods) on the main class leaks them into every slice and slows or breaks them; keep the main class thin and put such configuration in separate classes. Different slices and mocks produce different cached contexts, so keep them consistent.

Remember: slice = one layer's auto-configuration only. Mock what that layer calls.

How do you test a controller with @WebMvcTest and MockMvc? Intermediate

I use @WebMvcTest(OrderController.class), inject MockMvc, mock the service with @MockitoBean, and send fake requests. I assert on status, headers and JSON. It tests URL mapping, validation, serialisation and error handling without a server or database.

A controller has little logic but lots of contract: URL, verb, status code, validation, JSON shape, error mapping. @WebMvcTest checks all of that quickly because it loads only the web layer, and MockMvc sends requests straight into the DispatcherServlet without a network or a port.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test void returns404WhenMissing() throws Exception {
        when(service.find(42L)).thenThrow(new OrderNotFoundException(42L));
        mvc.perform(get("/orders/42"))
           .andExpect(status().isNotFound())
           .andExpect(jsonPath("$.code").value("ORDER_NOT_FOUND"));
    }

    @Test void rejectsInvalidBody() throws Exception {
        mvc.perform(post("/orders").contentType(APPLICATION_JSON).content("{}"))
           .andExpect(status().isBadRequest());
    }

    @Test @WithMockUser(roles = "ADMIN")
    void adminCanDelete() throws Exception {
        mvc.perform(delete("/orders/1").with(csrf())).andExpect(status().isNoContent());
        verify(service).delete(1L);
    }
}

What this exercises that a plain unit test of the controller class would not: path variable binding, @Valid, @RestControllerAdvice mapping, Jackson serialisation, content negotiation. What it does not: the service logic (mocked) or the database.

Tips and traps:

  • With Spring Security on the classpath, every request is 401 or 403 unless you add @WithMockUser or a test security config; for POST/PUT/DELETE also .with(csrf()) if CSRF is on. This is the number one reason "a new controller test fails".
  • Prefer jsonPath or JSONAssert to compare JSON field by field rather than raw strings, since field order and whitespace differ.
  • Build the request body from an object with an injected ObjectMapper instead of hand-typed JSON.
  • Boot 3.4 and later also supports MockMvcTester with AssertJ-style assertions (version dependent).

Remember: @WebMvcTest + MockMvc + @MockitoBean for the service; add @WithMockUser when security is present.

What does @DataJpaTest do, and why should I not rely on H2 alone? Intermediate

@DataJpaTest starts only the JPA layer: entities, repositories and a DataSource, each test in a transaction that is rolled back at the end. By default it swaps my database for an embedded one (H2). I prefer running it against the same database engine as production using Testcontainers, because H2 behaves differently.

@DataJpaTest is the slice for repositories. It loads entities, Spring Data repositories, Hibernate and a DataSource. Each test method runs in a transaction that is rolled back at the end, so tests do not leave data behind or affect each other. By default it also replaces your configured database with an embedded one (H2).

@DataJpaTest
class OrderRepositoryTest {
    @Autowired OrderRepository repo;
    @Autowired TestEntityManager em;

    @Test void findsOpenOrdersForCustomer() {
        em.persist(new Order(7L, OPEN));
        em.flush(); em.clear();                  // force SQL out, drop first-level cache
        assertThat(repo.findByCustomerIdAndStatus(7L, OPEN)).hasSize(1);
    }
}

Why not H2 alone. H2 is a different database from production. Differences that bite:

  • SQL dialect and functions, JSONB, arrays, enums, window functions, upsert syntax.
  • Case sensitivity of names and strings, default collation, null ordering.
  • Locking and isolation behaviour, so concurrency bugs and deadlocks do not reproduce.
  • Your Flyway scripts are written for Postgres or MySQL and may not run on H2 at all (H2 "compatibility modes" are partial).

So a test can be green on H2 and the query fail in production, or the reverse. Use the same engine through Testcontainers, and turn off the replacement:

@DataJpaTest
@AutoConfigureTestDatabase(replace = Replace.NONE)
@Testcontainers
class OrderRepositoryTest {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> db = new PostgreSQLContainer<>("postgres:16");
}

Caveats: because the transaction rolls back, nothing is actually committed, so commit-time checks (deferred constraints, triggers on commit) do not run; and without flush() Hibernate may not send the SQL, so a test that "passes" never touched the database. H2 remains fine for very simple, portable tests and quick feedback, as long as a real-engine integration test also exists.

Remember: @DataJpaTest = JPA layer in a rolled-back transaction. Use the real DB engine via Testcontainers.

@MockBean versus @MockitoBean: what is the difference? Intermediate

They do the same job: replace a bean in the Spring test context with a Mockito mock (or spy). @MockBean and @SpyBean are Boot annotations that were deprecated in Boot 3.4. @MockitoBean and @MockitoSpyBean come from Spring Framework 6.2 and are the recommended replacement. For new code I use the new ones.

Both annotations answer the same need: "in this test, replace a bean in the Spring context with a Mockito mock (or wrap the real bean in a spy)". Without it you would need a test configuration class for every fake.

The cost you must know: the set of overrides is part of the context cache key. Test class A with a mocked OrderService and test class B with a mocked PaymentClient cannot share a context, so each starts its own. Many small variations make the suite slow.

Judgement: mock the boundaries (remote clients, clock, email sender), use real beans or in-memory fakes inside the app, and do not mock what you are testing. A suite that mocks every collaborator passes while real wiring is broken.

Remember: @MockitoBean is the new @MockBean (Boot 3.4+). Each distinct mock set creates another context.

How do you use Testcontainers in a Boot test? What is @ServiceConnection? Senior

Testcontainers starts a real database, broker or cache in Docker for the test, so I test against the real thing. @ServiceConnection (Boot 3.1+) connects the app to the container automatically: Boot reads the container's host and port and configures the DataSource or Kafka client, so I no longer write @DynamicPropertySource boilerplate.

Testcontainers is a library that starts Docker containers from test code (Postgres, Kafka, Redis, a mock server) and stops them afterwards. Tests then run against the same engine as production, which finds issues H2 and in-memory fakes hide.

The problem it used to leave: the container gets a random port, and the app needs to be told. Before, you wrote:

@DynamicPropertySource
static void props(DynamicPropertyRegistry r) {
    r.add("spring.datasource.url", pg::getJdbcUrl);
    r.add("spring.datasource.username", pg::getUsername);
    r.add("spring.datasource.password", pg::getPassword);
}

@ServiceConnection (Boot 3.1) removes that. Boot has a ConnectionDetails abstraction; for known container types (Postgres, MySQL, Kafka, Redis, MongoDB, RabbitMQ and others) it reads host, port and credentials from the container and configures the matching auto-configuration for you:

@SpringBootTest
@Testcontainers
class OrderFlowIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16");
    @Container @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.6.0"));
}

For services Boot does not know, keep @DynamicPropertySource. You can also declare containers as @Bean @ServiceConnection methods in a @TestConfiguration.

Keeping the suite fast:

  • Make containers static so one is shared by all tests of the class, not one per test.
  • Share one container across classes with a singleton holder or a base class; or enable container reuse for local development.
  • Pin image tags; pull-through cache registry in CI.
  • Avoid @DirtiesContext; reset data with truncation or per-test transactions.

Boot 3.1 also supports development-time containers: SpringApplication.from(App::main).with(ContainersConfig.class).run(args) starts your app locally with the same containers (no docker-compose needed). CI caveat: Docker must be reachable (Docker-in-Docker or a remote daemon), and this is the usual reason these tests pass locally and fail in a pipeline.

Remember: static container + @ServiceConnection = real DB in tests with no manual property wiring.

Why does our Boot test suite take 20 minutes, and how do you speed it up? Senior

Almost always because many tests each start a new Spring context. Spring caches a context and reuses it for tests with the same configuration, but any difference (a different mock, property, profile, or @DirtiesContext) makes a new one. I speed up by making configurations identical across tests, using slices instead of full contexts, and testing logic as plain unit tests.

Starting a Spring context for tests costs seconds. To avoid paying it for every test class, Spring's test framework caches contexts. The cache key is the full configuration: the configuration classes, active profiles, property sources and test properties, context initializers, the set of @MockitoBean and @MockitoSpyBean definitions, and the web environment. Two test classes with exactly the same key share one context. Any difference creates a new one.

So a slow suite is usually a "context explosion". Example: 100 integration tests, each class with its own mix of mocks and properties: roughly 60 distinct keys, 60 startups at 15 seconds each, which is 15 minutes before a single test body runs.

Find it. Count how many times the log prints the Boot banner or "Started ... in x seconds"; or enable debug logging for org.springframework.test.context.cache to see cache hits and misses (and the size statistics).

Reduce it:

  1. Move logic out of Spring. Business rules as plain JUnit and Mockito tests run in milliseconds. This is the biggest win.
  2. Use slices (@WebMvcTest, @DataJpaTest) for layers; they start much faster than the full context.
  3. Standardise integration tests. One abstract base class carrying the shared annotations (profile, properties, containers); put mocks in one place or avoid them.
  4. Avoid @DirtiesContext; it discards the cached context. Clean data in the test instead.
  5. Share Testcontainers so you do not start a database per class.
  6. Replace sleep with Awaitility polling.
  7. Parallelise carefully: JUnit parallel execution and Maven/Gradle parallel forks help only for isolated tests; shared databases and ports cause flakiness.
  8. Optionally lazy initialisation in tests (spring.main.lazy-initialization=true) to cut startup, accepting that errors show up later.

Also consider: Gradle build cache and test selection, only running affected modules, and CI hardware. The principle for a senior answer: first measure (count contexts, find the slowest classes), then pick the cheapest fix, which is nearly always fewer, more similar contexts.

Remember: same configuration = cached context. Different mocks or properties = new, slow context.

9. Server, threads and background work

How does the embedded server work, and how do you switch from Tomcat to Jetty or Undertow? Basic

The web starter includes Tomcat as a library. Boot creates the server inside my application's process, registers the DispatcherServlet, and starts listening on server.port (8080). There is no external server to install, so deployment is "run the jar". To switch, I exclude the Tomcat starter from spring-boot-starter-web and add spring-boot-starter-jetty (or Undertow).

Traditionally you built a WAR and deployed it into an application server (Tomcat) that someone installed and configured. Boot flips this: the server is a library inside your app. At startup, ServletWebServerApplicationContext asks an auto-configured ServletWebServerFactory (Tomcat by default) to create a server, registers the DispatcherServlet and filters, and starts listening on server.port (8080). So java -jar app.jar is the deployment, every environment runs the same artifact, and you can tune the server with properties.

Switching servers is a dependency swap, because the web starter pulls spring-boot-starter-tomcat as a separate starter:

<dependency>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions><exclusion>
    <artifactId>spring-boot-starter-tomcat</artifactId>
  </exclusion></exclusions>
</dependency>
<dependency><artifactId>spring-boot-starter-jetty</artifactId></dependency>

Auto-configuration then sees Jetty on the classpath and builds it instead. Your controllers do not change.

How does Tomcat handle a request, and which settings control capacity? Intermediate

Tomcat uses a worker thread pool: one thread handles one request from start to finish, and blocks while waiting for the database or another service. The default maximum is 200 threads (server.tomcat.threads.max). When all 200 are busy, new connections wait in the accept queue (accept-count, 100), and beyond that they are refused.

Tomcat's model (blocking, "thread per request"): a connector accepts the connection, hands the request to a worker thread, and that same thread runs your controller, service and database calls. While it waits for the database or a remote service, the thread is blocked and cannot serve anyone else. Capacity is therefore about how many threads you have and how long each is held (Little's law: concurrent requests = arrival rate x time per request).

Example: 200 threads and 100 ms per request gives roughly 2,000 requests per second. If the downstream slows to 2 seconds per request, the same 200 threads handle only about 100 per second, and the queue grows.

PropertyDefaultMeaning
server.tomcat.threads.max200worker threads (max concurrent requests)
server.tomcat.threads.min-spare10kept ready
server.tomcat.max-connections8192sockets Tomcat holds open (NIO)
server.tomcat.accept-count100OS accept queue when all connections are in use; beyond it connections are refused
server.tomcat.connection-timeout20 stime to wait for the request line/data

The key insight is that the chain of pools has a narrowest point. 200 request threads in front of a 10-connection Hikari pool means at most 10 requests make progress in the database; the other threads queue for a connection. Raising Tomcat to 1000 threads only adds memory (each stack reserves around 1 MB of address space), more context switching, and more load on a database that is already the limit.

How to reason when it is slow: look at tomcat.threads.busy against tomcat.threads.config.max, the Hikari pending, and CPU. Busy threads at max with low CPU means threads are blocked on I/O: find the slow downstream call, add timeouts, cache, or reduce time per request. High CPU means compute-bound: optimise or scale out. Virtual threads help the "blocked on I/O" case by removing the thread ceiling (see the next question), but the DB pool remains the limit.

Other limits that bite: max header size, max-http-form-post-size, multipart limits (spring.servlet.multipart.max-file-size) and proxy timeouts that are shorter than your slowest endpoint.

Remember: one request = one thread. The narrowest limit in the chain (often the DB pool) decides throughput.

What are virtual threads, and how do you use them in Boot? Senior

Virtual threads (Java 21) are very cheap threads managed by the JVM: when one blocks on I/O, the JVM parks it and lets the OS thread (the carrier) run something else. In Boot 3.2 and later with Java 21 I turn them on with spring.threads.virtual.enabled=true, and Tomcat then handles each request on a virtual thread, so blocking code scales without the 200-thread ceiling.

The pain: with platform threads each request holds an OS thread while it waits on I/O, so concurrency is capped by the thread count (about 200 in Tomcat by default). OS threads are expensive (memory, scheduling), so you cannot just have 100,000 of them.

A virtual thread (final in Java 21) is a thread object managed by the JVM, not the OS. It is mounted on a small pool of carrier OS threads. When the code blocks on I/O (a JDBC call, an HTTP call), the JVM unmounts the virtual thread, saving its stack on the heap, and the carrier runs another virtual thread. When the I/O completes, the virtual thread is scheduled again. You keep the simple blocking code style but get scalability close to reactive.

# Boot 3.2+ on Java 21
spring.threads.virtual.enabled=true
# Tomcat/Jetty request handling, @Async, @Scheduled tasks and others then use virtual threads

// or by hand
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) { ex.submit(() -> callRemote()); }

What it does not change:

  • It does not make the database or remote services faster. The limit moves to the DB pool and downstream capacity. With 10,000 virtual threads and a 10-connection pool, 9,990 wait for a connection. Keep pool sizes, rate limits, timeouts and bulkheads, or you can overwhelm a dependency with far more concurrent calls than before.
  • CPU-bound work gets no benefit.

Risks to name:

  • Pinning. A virtual thread inside a synchronized block (or native call) that blocks cannot unmount, so it holds its carrier. Java 24 removed most synchronized pinning; on Java 21 prefer ReentrantLock in your own hot paths and check libraries (older JDBC drivers). Diagnose with -Djdk.tracePinnedThreads=full or JFR.
  • ThreadLocal caches multiply when you have a huge number of threads.
  • Unbounded concurrency is now easy; use semaphores to cap concurrent calls to a limited resource.
  • Thread dumps look different (use jcmd Thread.dump_to_file for virtual threads).

Symptom after enabling: service stalls with idle CPU. Suspect pinning or exhausted DB pool under the larger concurrency. It is best for I/O-heavy services that fan out to several others; measure before and after.

Remember: virtual threads remove the thread ceiling, not the DB or downstream ceilings. Keep pools and timeouts.

Spring MVC or WebFlux in a Boot app: how do you choose? Intermediate

I choose MVC by default: simple blocking code, easy to debug, and the whole ecosystem (JPA, JDBC) is blocking anyway. I choose WebFlux when the service is mostly I/O waiting with a very high number of concurrent connections (streaming, gateways, server-sent events) and the whole stack, including the database driver, can be non-blocking. With virtual threads in Java 21, MVC covers most of the cases where people used to pick WebFlux.

The two stacks differ in the threading model, not in the annotations.

The reason for WebFlux: with a few threads you can hold tens of thousands of open connections, because a waiting request costs a callback, not a thread. That fits API gateways, streaming responses, server-sent events, WebSockets, and services that mostly wait for many remote calls.

The catch: it only pays off if the whole path is non-blocking. A single blocking call (JDBC, Thread.sleep, a blocking HTTP client) on an event-loop thread stalls every request on that thread. Tools like BlockHound can detect it. Mixing JPA inside WebFlux gives you the complexity of reactive with none of the benefit.

// MVC
Order get(long id) { return repo.findById(id).orElseThrow(); }
// WebFlux
Mono<Order> get(long id) { return repo.findById(id).switchIfEmpty(Mono.error(new NotFound())); }

Decision rule: default to MVC. With Java 21 virtual threads, blocking MVC scales to high concurrency with simple code, which removes most reasons people picked WebFlux. Choose WebFlux when you need streaming/backpressure, you already have a reactive stack (R2DBC, reactive drivers), or the team is skilled in reactive.

Boot decides automatically: if both starters are on the classpath, MVC wins; force it with spring.main.web-application-type=reactive|servlet|none. A servlet app may use WebClient for its client features without becoming reactive.

Remember: MVC (plus virtual threads) by default; WebFlux only when the whole chain is non-blocking and you need huge concurrency or streaming.

How does caching work in Boot, and what can go wrong? Intermediate

I add @EnableCaching, annotate methods with @Cacheable, @CacheEvict and @CachePut, and Boot picks a cache provider from the classpath (Caffeine, Redis, or a simple in-memory map if nothing else). The result of the method is stored under a key built from the arguments, and a later call with the same arguments returns the stored value without running the method.

Caching stores the result of an expensive call so the next identical call is fast. Spring's cache abstraction lets you do it declaratively and swap the store without changing code.

Setup: @EnableCaching plus a provider. Boot's CacheAutoConfiguration picks one from the classpath in order (Redis, Caffeine, Hazelcast, JCache, and so on, ending with a simple concurrent map). You can force it with spring.cache.type.

@Cacheable(cacheNames = "products", key = "#id", unless = "#result == null")
public Product find(long id) { ... }            // 1st call runs and stores; later calls skip the method

@CachePut(cacheNames = "products", key = "#p.id")  // always runs, refreshes the entry
public Product update(Product p) { ... }

@CacheEvict(cacheNames = "products", key = "#id")  // remove after change
public void delete(long id) { ... }

spring.cache.cache-names=products
spring.cache.caffeine.spec=maximumSize=10000,expireAfterWrite=10m

Mechanism: a proxy around the bean intercepts the call, builds the key from the arguments, checks the cache, and either returns the stored value or calls the method and stores the result.

What goes wrong:

  • Self-invocation. A call from another method in the same class bypasses the proxy, so nothing is cached.
  • Unbounded default. The simple map has no size limit or expiry: a memory leak. Use Caffeine (maximumSize, expireAfterWrite) or Redis with a TTL.
  • Stale data across pods. A local cache differs per pod; after an update, other pods serve old values until TTL. Use Redis (shared) or short TTLs plus eviction events.
  • Mutable cached objects. A caller changes the shared object and everyone sees it; cache immutable values or copy.
  • Serialisation. Redis needs serialisable values; changing the class shape between deploys can break reading old entries.
  • Stampede. When a hot key expires, many requests recompute it at once; use sync=true (per-key lock locally) or refresh-ahead.
  • Null and key design. Decide whether to cache misses; keys must be stable and include the tenant or locale if results depend on them.

Most important: decide what invalidates an entry before you add a cache. "There are only two hard things: cache invalidation..." is a fair answer if followed by your plan.

Remember: proxy-based, so no self-invocation. Always set size and TTL, and plan invalidation.

How does @Scheduled work, and what are the traps in a multi-instance deployment? Intermediate

With @EnableScheduling, a method annotated @Scheduled(cron = "..."), fixedRate or fixedDelay runs on a scheduler thread. Two traps: the default scheduler has one thread, so a slow job delays all others; and every pod runs its own copy, so in a three-pod deployment the job runs three times.

Scheduling runs a method on a timer. Add @EnableScheduling and annotate a method:

@Scheduled(fixedRate = 60_000)                    // every 60s from start to start
void poll() { ... }
@Scheduled(fixedDelay = 30_000, initialDelay = 10_000)   // 30s AFTER the previous run ends
void cleanup() { ... }
@Scheduled(cron = "0 0 2 * * *", zone = "UTC")    // second minute hour day month weekday
void nightly() { ... }

fixedRate measures between starts (runs can overlap or queue if one takes longer); fixedDelay measures from the end of the previous run, so runs never overlap. Cron uses the JVM time zone unless you set zone, a source of "ran at the wrong hour" after moving to UTC containers. An exception is logged and the schedule continues.

Trap 1: one scheduler thread. The default scheduler pool has a single thread, so a 5-minute job delays every other scheduled method. Set spring.task.scheduling.pool.size=5, and hand heavy work to an executor. (With virtual threads enabled, Boot can use a virtual-thread scheduler.)

Trap 2: every pod runs it. Scale to 3 pods and the "send daily report" job fires 3 times: duplicate emails, double charges. Options:

ApproachHowNote
ShedLocklock row in DB/Redis; @SchedulerLock(name="report", lockAtMostFor=...)simple, works in same codebase
Kubernetes CronJobseparate pod runs the job onceclean separation, own resources
Leader electionone pod is leadermore moving parts
Quartz clusteredjobs stored in DBheavier, rich features

Whatever you pick, make jobs idempotent (safe if run twice or partly): locks can expire (lockAtMostFor), a pod can die midway, and clocks skew. Use a "processed" marker or unique constraint.

Other points: set a time-out and monitor jobs (a metric for last success time and an alert when it is stale); graceful shutdown should wait for running jobs; for heavy, critical or restartable batch work use Spring Batch or a dedicated job rather than @Scheduled.

Remember: one scheduler thread by default, and one run per pod. Use ShedLock or a CronJob, and make jobs idempotent.

What does @Async do in Boot, and what executor does it use? Intermediate

With @EnableAsync, a method annotated @Async runs on another thread, and the caller returns immediately (void, or a CompletableFuture for the result). Boot auto-configures a ThreadPoolTaskExecutor for it, with 8 core threads and an unbounded queue by default; I tune it with spring.task.execution.pool.*.

@Async lets a call return immediately while the work runs on another thread. Enable it with @EnableAsync, annotate a method, and return void (fire and forget) or CompletableFuture<T> (to get a result).

@Async
public CompletableFuture<Report> build(long id) {
    return CompletableFuture.completedFuture(heavyWork(id));   // runs on the executor
}
// caller: CompletableFuture<Report> f = reports.build(5);  ... f.get()/thenAccept(...)

spring.task.execution.pool.core-size=8
spring.task.execution.pool.max-size=16
spring.task.execution.pool.queue-capacity=200
spring.task.execution.thread-name-prefix=app-async-

The executor: Boot auto-configures applicationTaskExecutor (a ThreadPoolTaskExecutor, 8 core threads, unbounded queue by default) and uses it for @Async. Important detail: the pool only grows beyond core size after the queue is full, so with the default unbounded queue it never grows past 8, and a burst simply queues in memory.

Traps:

  • Proxy. Self-invocation (calling this.build()) or a non-public/final method runs synchronously.
  • Unbounded queue hides overload as growing memory and latency; set queue-capacity and a rejection policy (caller-runs gives natural back-pressure).
  • Lost exceptions. A void async method's exception goes nowhere; register an AsyncUncaughtExceptionHandler (via AsyncConfigurer), or return a future and handle it.
  • Lost context. Security principal, MDC log fields, trace ids and the transaction do not follow the new thread. Copy them with a TaskDecorator; @Transactional in the async method starts a fresh transaction.
  • Lost work. The queue is in memory; a crash or deploy loses queued tasks. For work that must happen (invoice email, payment), use a durable queue or an outbox table, not a thread pool.
  • Shutdown. Set spring.task.execution.shutdown.await-termination=true so tasks finish during graceful shutdown.

Remember: @Async = proxy + thread pool. Bound the queue, handle exceptions, and use a real queue for work you cannot lose.

10. Packaging, containers and shutdown

What is a "fat jar" (executable jar), and how is it different from a normal jar? Basic

A fat jar contains my compiled classes and all dependency jars nested inside one file, plus Boot's launcher, so java -jar app.jar just works. A normal jar has only my classes and needs a classpath for the rest. The Maven or Gradle Boot plugin builds it in the repackage step.

Java's default class loader cannot load classes from a jar inside another jar, so a plain build gives you your own small jar and a pile of separate dependency jars you must put on the classpath yourself. A "fat" (also "uber" or executable) jar bundles everything in one file so java -jar app.jar is the entire run command.

Layout of a Boot executable jar:

app.jar
  META-INF/MANIFEST.MF        Main-Class: org.springframework.boot.loader.launch.JarLauncher
                              Start-Class: com.acme.OrdersApp
  BOOT-INF/classes/           your compiled code and resources
  BOOT-INF/lib/               dependency jars, nested as they are
  BOOT-INF/layers.idx         layer list (for Docker)
  org/springframework/boot/loader/   the launcher classes

On start, the JVM runs JarLauncher (the manifest's Main-Class). It builds a class loader that understands the nested BOOT-INF/lib jars and then invokes your Start-Class. The Boot Maven plugin (spring-boot-maven-plugin, goal repackage) or the Gradle bootJar task produces it.

Compare with the alternatives:

Normal jaronly your classesneeds a classpath for the rest
Shaded jar (Maven shade)all classes unpacked and mergedcan clash on resource files; different mechanism

Downside for containers: every code change rewrites a big file, so the Docker layer holding the jar is rebuilt and pushed in full, even if only your tiny code changed (a typical jar is 30 to 80 MB). The layered jar and layered Docker image fix that (next question). Also note: a fat jar is the artifact, but extracting it (-Djarmode=tools extract) and running it as an exploded directory starts a little faster and is what Boot suggests for production containers.

Remember: fat jar = my classes + dependency jars + launcher. Great for running, poor for Docker layer caching unless layered.

How do you build a good Docker image for a Boot app? Intermediate

I use the layered jar so that dependencies (large, rarely changing) and my code (small, changes every build) go into separate image layers; Docker reuses the cached dependency layers and only pushes the tiny application layer. Alternatively ./mvnw spring-boot:build-image builds an optimised image with Cloud Native Buildpacks, no Dockerfile needed.

A Docker image is a stack of layers, and each layer is cached by content. If you copy the whole fat jar into one layer, then every build, even a one-line change, produces a new 50 MB layer to build, push and pull. But 95 percent of that jar is dependencies that did not change. Layer by how often things change, and the registry and nodes only move the small changed layer.

Boot's layered jar already splits its content into four layers (listed in layers.idx), from least to most changing: dependencies, spring-boot-loader, snapshot-dependencies, application. A multi-stage Dockerfile extracts them:

FROM eclipse-temurin:21-jre AS builder
WORKDIR /app
COPY app.jar app.jar
RUN java -Djarmode=tools -jar app.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=builder /app/extracted/dependencies/ ./
COPY --from=builder /app/extracted/spring-boot-loader/ ./
COPY --from=builder /app/extracted/snapshot-dependencies/ ./
COPY --from=builder /app/extracted/application/ ./
USER 1000
ENTRYPOINT ["java", "-jar", "app.jar"]

Version note: -Djarmode=tools arrived in Boot 3.3 (earlier versions use -Djarmode=layertools extract and a JarLauncher entry point). Check your version.

Two alternatives that need no Dockerfile: ./mvnw spring-boot:build-image (Gradle bootBuildImage) uses Cloud Native Buildpacks, which layers the image, sets memory flags for the JVM and runs as non-root; and Jib (a Maven/Gradle plugin) builds layered images without a Docker daemon.

Image hygiene:

  • JRE-only (or distroless/slim) base image: smaller and fewer vulnerabilities to patch.
  • Run as a non-root user; read-only root filesystem where possible.
  • Pin base image versions (and digests) and rebuild regularly for security fixes.
  • No secrets baked in; pass configuration at runtime.
  • Add container-aware JVM flags (see the memory question) and a health check path for the orchestrator.
  • Use .dockerignore to keep the build context small.

Remember: layer by change frequency: dependencies low, your code on top. Run as non-root.

How do you set JVM memory and CPU for a Boot app in a container? Senior

Modern JVMs read the container limits, so I set the container memory limit and tell the JVM what share to use: -XX:MaxRAMPercentage=75 instead of a fixed -Xmx. I leave room outside the heap, because the JVM also uses memory for metaspace, thread stacks, direct buffers and code cache. If I give the heap 100 percent, the pod is killed with exit code 137 (OOMKilled) even though Java reported no OutOfMemoryError.

Inside a container the JVM must respect the cgroup limits. Modern JVMs (Java 10 and later, and 8u191+) detect the container's memory and CPU limits, so you size relative to the limit instead of the host.

Memory. The container limit covers more than the heap. A JVM process also uses metaspace (class metadata), thread stacks (about 1 MB each x threads), direct buffers (Netty, NIO), the code cache, GC structures and native libraries. So if the limit is 1 GB and the heap may grow to 1 GB, the kernel kills the process: exit code 137 (OOMKilled), and no Java OutOfMemoryError appears in the log, which confuses people.

resources:
  requests: { memory: 1Gi, cpu: "1" }
  limits:   { memory: 1Gi }              # memory request = limit
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"

Rules of thumb: MaxRAMPercentage 60 to 75 percent (lower for apps with many threads or large direct buffers); set memory request equal to the limit (memory cannot be squeezed back, unlike CPU); use -XX:+ExitOnOutOfMemoryError so a real OOM restarts the pod cleanly instead of limping. Observe with jvm.memory.used, jvm.buffer.* and Native Memory Tracking (-XX:NativeMemoryTracking=summary) when the process grows beyond the heap.

CPU. A CPU limit is enforced by throttling (CFS quota): when the pod uses its quota within each 100 ms period it is paused until the next. For a JVM this hurts, because garbage collection, JIT compilation and request threads all burn CPU in parallel, so latency spikes and startup is slow while reported CPU usage looks low. Check container_cpu_cfs_throttled_seconds_total. Many teams set a CPU request but no (or a generous) limit. Also the JVM derives its GC choice and thread counts from the visible CPUs: under 2 CPUs or about 1.8 GB memory it picks the Serial GC instead of G1; set -XX:ActiveProcessorCount or the GC explicitly if you need to. Startup needs extra CPU (JIT warm-up), so slow starts often just need a higher limit or a startup boost.

Remember: MaxRAMPercentage ~75, leave non-heap room, and watch CPU throttling. Exit 137 = killed by the container limit.

How does graceful shutdown work in Boot, and how does it fit with Kubernetes? Senior

With server.shutdown=graceful, on SIGTERM Boot stops accepting new requests, lets in-flight requests finish for up to spring.lifecycle.timeout-per-shutdown-phase (30 s default), and then closes the context. Without it the server stops immediately and running requests are cut. The default is immediate, so I must turn graceful on.

Every deploy stops old pods. Without graceful handling, requests that are mid-flight get cut and clients see errors during every rollout.

With server.shutdown=graceful, when Boot receives SIGTERM it:

  1. sets readiness to REFUSING_TRAFFIC and stops accepting new connections/requests (the web server pauses);
  2. waits for in-flight requests to finish, up to spring.lifecycle.timeout-per-shutdown-phase (default 30 s);
  3. closes the rest of the context in order (executors, pools, message listeners, then the DataSource).

The default, unless you set it, is immediate shutdown (check your version's reference), so you must enable it deliberately.

server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=25s

# Kubernetes pod spec
terminationGracePeriodSeconds: 45
lifecycle:
  preStop: { exec: { command: ["sleep","10"] } }

The Kubernetes race. On pod deletion two things start at the same time: the pod is removed from Service endpoints (asynchronously, kube-proxy, ingress controllers and load balancers update on their own schedule), and the kubelet sends SIGTERM. For a few seconds traffic may still be routed to a pod that has begun to shut down: you see 502/503 or connection resets on each deploy. The standard fix is a preStop sleep (5 to 10 s) so the pod keeps serving normally while endpoints propagate; then SIGTERM runs the Boot drain.

Three clocks must agree: terminationGracePeriodSeconds must be greater than preStop sleep plus Boot's drain timeout. Otherwise Kubernetes sends SIGKILL in the middle of a request. Example: 10 s + 25 s = 35 s, so 45 s is safe.

Other things to shut down cleanly: Kafka/RabbitMQ listeners (stop consuming, finish and commit the current message), @Scheduled and @Async executors (await-termination), and long requests (anything longer than the timeout is cut, so very long operations belong on a queue). Test it: run a load test during a rolling restart and count non-2xx responses.

Remember: graceful on, preStop sleep, and grace period greater than preStop plus drain timeout.

After a refactor the app will not start: "No qualifying bean of type OrderService". What do you do? Intermediate

The bean is not registered, and after a refactor the usual reason is that the class moved outside the scanned package, lost its annotation, or is switched off by a profile or condition. I read the failure message, run with --debug to see the conditions report, and fix the package or annotation.

Situation. You moved classes around in a refactor. The app no longer starts and prints:

APPLICATION FAILED TO START
Description: Parameter 0 of constructor in com.acme.web.OrderController required a bean of type 'com.acme.service.OrderService' that could not be found.
Action: Consider defining a bean of type 'com.acme.service.OrderService' in your configuration.

Read the message first: "Description" names who needed the bean and which type. That tells you the consumer and the missing type, not why it is missing. A bean can be missing for exactly four reasons, so check them in this order.

  1. Not annotated or declared. Does OrderService have @Service/@Component, or is there a @Bean method? A refactor that turned a class into an interface or dropped the annotation produces this.
  2. Not scanned. Is the class in the main class's package or below, or listed in scanBasePackages? Moving it to a sibling package such as com.other hides it.
  3. Switched off. A @Profile, @ConditionalOnProperty or @ConditionalOnClass may exclude it in this environment.
  4. Library missing. If the bean comes from auto-configuration (a starter), the jar or the property that enables it is gone.
java -jar app.jar --debug                 # conditions report: look at "Negative matches"
mvn dependency:tree | grep -i the-library

Fix. Restore the annotation or package, enable the profile or property, add the dependency. If the opposite error appears ("expected single matching bean but found 2"), use @Primary or @Qualifier.

Prevent. Keep the main class in the root package. Keep at least one @SpringBootTest that only loads the context (contextLoads()) so this fails in the pull request build, not at deploy time; slices catch the same class of error for one layer.

Remember: not found = not scanned, not annotated, switched off, or library missing. --debug tells which.

"Web server failed to start. Port 8080 was already in use." It works on a colleague's machine. What do you do? Basic

Another process is already listening on that port, often a previous run of the same app that did not stop. I find and stop that process, or run this one on another port with --server.port=8081. In tests I use server.port=0 so a free port is chosen.

Situation. Startup fails with:

Web server failed to start. Port 8080 was already in use.
Action: Identify and stop the process that's listening on port 8080 or configure this application to listen on another port.

It works for a colleague because nothing else listens on 8080 on their machine. The cause is always the same: the port is a single resource, and another socket already owns it.

Check first. Find who owns it.

netstat -ano | findstr :8080        # Windows; last column = PID, then: tasklist /fi "pid eq 1234"
lsof -i :8080                       # macOS / Linux
kill <pid>  (taskkill /pid 1234 /f on Windows)

Common owners on a dev machine: the same app from an earlier run that never stopped (a zombie from the IDE or a terminal), another service like a local Jenkins or another project, or a Docker container publishing 8080.

Fix. Stop the old process, or run on a different port: --server.port=8081, or SERVER_PORT=8081. In tests use server.port=0 (a random free port, then inject it with @LocalServerPort).

Kubernetes variant. If a pod loops with this error, two containers in the same pod are trying to bind the same port (the pod shares one network namespace; a sidecar or a second copy of the app is the usual culprit), or the application and management port are accidentally set equal. Check the container ports and management.server.port.

Prevent. Random ports in integration tests (parallel runs will not collide), a deliberately different management port, and stopping dev runs cleanly. Do not "fix" it by killing random processes on a shared server without looking at the PID.

Remember: port in use = find the owner. Tests use port 0.

The production pod connects to the dev database. You suspect the wrong profile. How do you confirm and fix it? Intermediate

I confirm which profile is active and which source supplies the datasource URL, then fix the source. Boot logs "The following profiles are active: ..." at startup, and /actuator/env/spring.datasource.url shows the winning value and where it came from. Then I correct the profile variable or remove the override.

Situation. Production traffic is writing to the dev database, or a pod shows dev data. This is a configuration incident, so confirm facts before changing anything.

Check first, in this order:

  1. Which profile is active? Boot logs it at startup: The following 1 profile is active: "dev" (or "No active profile set, falling back to 1 default profile: default"). Read it with kubectl logs.
  2. Which value won, and from where? 
    GET /actuator/env/spring.datasource.url      # shows the winning value and the ordered list of sources
kubectl exec pod -- env | grep -i -E "spring|datasource"
  3. Why that source? Typical causes:
    • SPRING_PROFILES_ACTIVE is missing from the Deployment, so the default profile applies and the packaged application.yml holds the dev URL.
    • A command-line argument or -D option in the image entrypoint overrides the ConfigMap (higher priority than env vars).
    • The variable name is wrong (SPRING_DATASOURCE_URI, missing underscore), so relaxed binding never matched and the default stayed.
    • The wrong ConfigMap or namespace is mounted.

Fix. Set SPRING_PROFILES_ACTIVE=prod and provide the URL and password from the prod Secret/ConfigMap, roll the Deployment (kubectl rollout restart), then verify through /actuator/env again and check the database's connection list. Treat the data written to the wrong database as a separate recovery task (stop writes first).

Prevent.

  • Never put a real environment's URL as the default in the packaged file. A default that points to a harmless local DB fails safely; one that points to dev connects silently.
  • Use @Validated properties that reject obviously wrong values (for example a hostname containing "dev" when profile is prod).
  • Log the DB host (never the password) at startup; add a deployment check on it.
  • Network policy so prod pods cannot reach the dev database at all.

Remember: check the log for active profiles, then /actuator/env for the winning source. Defaults must fail safe.

At peak the API returns 500s: "HikariPool-1 - Connection is not available, request timed out after 30000ms". What do you do? Senior

The pool is exhausted: all connections are in use and callers wait 30 seconds, then fail. Raising the pool is usually the wrong first move. I find who holds connections too long (slow query, a transaction that includes a remote call, or a leak), fix that, and only then size the pool.

Situation. At peak, requests fail with SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out after 30000ms. Latency was already high for 30 s before each failure, because every caller waited that long for a connection.

The tempting reaction is "raise the pool size". Resist it: if the database was already the bottleneck, more connections make it slower and can crash it. First learn why connections are held, not whether there are enough.

Check first.

  • Hikari metrics: hikaricp.connections.active at max and pending above zero confirm exhaustion; hikaricp.connections.usage shows how long each is held.
  • Thread dump (/actuator/threaddump or jstack): where are the threads that hold connections? In a socket read to another service (a remote call inside a transaction), or waiting in a JDBC call (slow query or lock)?
  • Database side: pg_stat_activity (or equivalent): long-running queries, "idle in transaction" sessions (a connection held but not working), lock waits.
  • Leak detection: set spring.datasource.hikari.leak-detection-threshold=20000 to log a stack trace for code that holds a connection too long.
  • Did traffic, pod count (pods x pool size vs DB max connections) or a deploy change just before?

Typical causes and fixes:

CauseFix
HTTP/remote call inside @TransactionalMove the call outside the transaction; keep transactions short
Slow query or missing indexExplain plan, add index, paginate
Open-in-view holds the connection during renderingspring.jpa.open-in-view=false
Connection leak (manual JDBC not closed)try-with-resources
Lock contention on hot rowsShorter transactions, different locking
Real load growthScale pods and raise the pool only within DB capacity

Also lower connection-timeout (for example 2 to 5 s) so callers fail fast instead of piling up 200 threads waiting 30 s, and add a circuit breaker/bulkhead for the endpoints involved.

Prevent. Alert on pending > 0 and acquire time (before errors), keep transactions short by review rule, load-test with realistic concurrency, and size pods x pool against the database limit.

Remember: exhausted pool = connections held too long. Find the holder, then resize.

The pod restarts every few hours with exit code 137, and there is no OutOfMemoryError in the logs. What is happening? Senior

Exit code 137 means the container was killed (SIGKILL), almost always OOMKilled: total process memory exceeded the container limit. The Java heap is only part of it, so the JVM never saw an OutOfMemoryError. I check kubectl describe pod for "OOMKilled", then compare the heap setting with the limit and look for non-heap growth.

Situation. A pod restarts every few hours. kubectl get pod shows restarts; the app log ends without any stack trace, and there is no OutOfMemoryError.

What the clue means. Exit code 137 = 128 + 9: the process received SIGKILL. In Kubernetes the usual sender is the kernel's OOM killer, because the container's memory use exceeded its limit. A Java OutOfMemoryError is raised when the heap is full. If the process dies from outside, the JVM never gets to log anything. So the total process memory (heap + metaspace + thread stacks + direct buffers + code cache + native allocations) crossed the limit.

Check first.

kubectl describe pod X       # Last State: Terminated, Reason: OOMKilled, Exit Code: 137
kubectl top pod X --containers
# JVM flags in effect:
-XX:+PrintFlagsFinal | grep -E "MaxHeapSize|MaxRAMPercentage"
  • Is -Xmx equal (or close) to the container limit? Then non-heap memory has no room.
  • Metrics: jvm.memory.used (heap vs non-heap), jvm.threads.live, jvm.buffer.memory.used (direct buffers), and the container working set. Does memory climb steadily (leak), or step up with traffic (large payloads, many threads, caching)?
  • Native memory tracking if needed: -XX:NativeMemoryTracking=summary and jcmd <pid> VM.native_memory summary.

Fix.

  • Use -XX:MaxRAMPercentage=70 (or a fixed -Xmx well below the limit) so there is headroom for non-heap.
  • Cap thread pools and stack sizes; bound caches; cap Netty direct memory (-XX:MaxDirectMemorySize) if used; stream large responses instead of buffering them.
  • If heap grows forever, take a heap dump (on -XX:+HeapDumpOnOutOfMemoryError to a volume) and find the retained objects.
  • Raise the limit only when measurements show the working set is legitimate.
  • Add -XX:+ExitOnOutOfMemoryError so a genuine heap OOM exits cleanly with a log line, easy to distinguish from a kernel kill.

Prevent. Dashboards for heap, non-heap and container working set against the limit, an alert at 85 percent, and soak tests that run long enough to show a slope.

Remember: 137 with no Java error = killed by the container limit. Heap is not the whole process.

After adding one library, every endpoint returns 401 and the log shows "Using generated security password". How did that happen? Senior

The new library pulled in spring-boot-starter-security (or Spring Security) transitively, and Boot's security auto-configuration switched on: every endpoint now needs basic auth with a generated password. I confirm with the dependency tree and the conditions report, then either define my own SecurityFilterChain or remove the unwanted dependency.

Situation. You added a library to the pom (say an internal shared module). After deploy every endpoint answers 401, and the startup log shows Using generated security password: 7c1f.... You did not touch security code.

What happened. Boot's auto-configuration reacts to the classpath. The new library depends (maybe transitively, as a compile dependency) on Spring Security. Now SecurityAutoConfiguration and the web security configuration find Spring Security on the classpath and no SecurityFilterChain bean of yours, so they apply the secure default: authenticate every request and create a user with a random password. Nothing in your code changed, but the classpath did.

Check first.

mvn dependency:tree -Dincludes=org.springframework.security     # who brought it
java -jar app.jar --debug   # "Positive matches": SecurityAutoConfiguration, SpringBootWebSecurityConfiguration

Fix (decide intent first).

  • The service should be secured: define a real SecurityFilterChain bean (the default backs off). Add the correct rules, authentication (JWT, OAuth2) and permit the health probes.
  • It should not use security: exclude the transitive dependency in the pom (<exclusions>) or fix the library so Spring Security is optional/provided. As a last resort exclude the auto-configuration classes.
  • Do not "fix" it by permitAll() on everything for a service that is reachable from outside; that quietly removes protection.

Related surprises from the same mechanism: a driver jar activates a DataSource and fails startup; spring-boot-starter-actuator exposes new endpoints; a Redis client activates the Redis health indicator and makes readiness DOWN when Redis is unreachable.

Prevent. Review the dependency tree (and diff it) when adding or upgrading libraries; make shared libraries keep heavy dependencies optional; have a CI test that boots the context and calls one real endpoint with the expected status, so a change in security posture fails the pull request.

Remember: classpath drives auto-configuration. A new transitive jar can switch on security, a DataSource, and more.

You set a property in a ConfigMap and the app ignores it. How do you find out why? Intermediate

Either the value never reached the process, or a higher-priority source overrides it. I look at the resolved value with /actuator/env/<key>, which lists every source in priority order, and check the pod's environment directly.

Situation. You edited the ConfigMap (say FEATURE_X_ENABLED=true or a timeout) and the application behaves as before. There are only a few places the change can get lost, so walk the path from Kubernetes to the Java object.

  1. Did the pod restart? Environment variables from a ConfigMap are read when the container starts. Editing the ConfigMap does not change a running pod (mounted files do refresh eventually, but Boot does not re-read them). Check pod age; run kubectl rollout restart deployment/x.
  2. Did it reach the container? 
    kubectl exec pod -- env | grep FEATURE
kubectl get configmap x -o yaml
    Wrong namespace, wrong ConfigMap name, or a missing envFrom/valueFrom mapping are common.
  3. Is the name right? Environment variable names must follow the relaxed-binding rule: spring.datasource.url is SPRING_DATASOURCE_URL; my.app.read-timeout is MY_APP_READTIMEOUT. A typo, or a dash or dot left in, is silently ignored.
  4. Does something outrank it? Look at the sources: 
    GET /actuator/env/my.app.read-timeout     # winner + all sources in priority order
    Command-line args in the container args, a -D in JAVA_TOOL_OPTIONS, or a profile-specific file can override an env var. Also check a duplicate key defined twice in the Deployment.
  5. Is the code reading it? A @Value is resolved at bean creation, and a @ConfigurationProperties record is built once; both need a restart. A property the code never reads, or one bound under a different prefix, appears in env but changes nothing: check /actuator/configprops.

Fix. Correct the name or remove the overriding source, then roll the Deployment.

Prevent. Put a checksum of the ConfigMap into a pod annotation (Helm checksum/config) so any change triggers a rollout; use @Validated @ConfigurationProperties so missing or wrong values fail at startup; document one place for each setting.

Remember: check that it arrived, check the name, check who overrides it, and restart the pod.

A small worker service that never uses a database now fails with "Failed to configure a DataSource". What happened? Basic

Something on the classpath, usually a new dependency, brought JDBC or JPA, so Boot tried to create a DataSource and found no URL. I find which dependency added it and remove it, or exclude DataSourceAutoConfiguration if the app really does not need a database.

Situation. A small worker (queue consumer, batch task) starts failing after a routine dependency change:

Failed to configure a DataSource: 'url' attribute is not specified and no embedded datasource could be configured.
Reason: Failed to determine a suitable driver class

Why. Boot's DataSourceAutoConfiguration is active whenever the DataSource class (from spring-jdbc) is on the classpath. It then insists on a URL, unless it can start an embedded database. Your worker never wanted a database, but some dependency now brought JDBC onto the classpath: a shared internal library that includes starter-data-jpa, a metrics or audit library using JdbcTemplate, or Spring Batch (which needs a JobRepository DataSource).

Check first.

mvn dependency:tree | grep -E "spring-jdbc|data-jpa|hikari|postgresql|h2"
# compare against the dependency tree of the last working build

Fix, in order of preference.

  1. Remove the dependency (or exclude it from the library that drags it in). This also removes dead code and speeds startup.
  2. If the app genuinely never needs a database but the jar must stay: spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration (and HibernateJpaAutoConfiguration when JPA is present).
  3. If it should use a database after all, set spring.datasource.url and the credentials.

Do not paper over it by adding a fake URL or letting an embedded H2 silently start: the app then runs with a throwaway database and the real problem remains.

Prevent. Shared libraries should not force JPA/JDBC on every consumer: split into modules, mark such dependencies optional, or provide auto-configuration that is conditional. Review the dependency diff on every upgrade.

Remember: JDBC on the classpath without a URL = startup failure. Remove the cause, do not just add a fake URL.

A deployment fails at startup with "Migration checksum mismatch". Production data is in that database. What do you do? Senior

Someone changed a migration file that was already applied, so its stored checksum no longer matches. I do not touch production data. I restore the original file exactly as it was applied, and put the intended change into a new migration. Only if the old file really must change do I use Flyway's repair, carefully, after confirming that the database state matches.

Situation. A release fails to start and the log says:

FlywayValidateException: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 12
-> Applied to database : 1865538265
-> Resolved locally    : 913044113

Flyway stores a checksum of each migration file when it runs it. At every start it recomputes checksums of the files and compares. A mismatch means the file for version 12 differs from what was executed in production. Boot's startup fails on purpose, because applying new migrations on top of an unknown history is dangerous. The application has not changed the data; the database is still in the state it was.

Check first (read-only).

  • git log -p -- db/migration/V12__*.sql: what changed and who changed it? Even whitespace, comments or line endings (CRLF versus LF) alter the checksum, so a formatter or editor setting is a frequent innocent cause.
  • select version, description, checksum, success, installed_on from flyway_schema_history order by installed_rank; to see what really ran. Also check for rows with success=false (a half-applied migration, a separate problem).
  • Compare environments: did staging apply the original and production too, or did the edited file already run somewhere?

Fix.

  1. Revert V12 to the exact applied content (from the git revision that was released) and ship the intended change as V13__fix.sql. Fix forward, never backward.
  2. If the edit was purely cosmetic and must stay, run flyway repair (or mvn flyway:repair), which rewrites the stored checksum to the file's. Do this as a deliberate, reviewed step after confirming that the database state really equals what the new file describes, not on autopilot and not from application startup.
  3. Do not delete rows from the history table by hand or set validate-on-migrate=false to "get it started"; that hides drift.

Prevent. A CI check that fails if an already-released migration file is modified (compare with the main branch), a code-owner rule on the migration folder, consistent line endings (.gitattributes), and rehearsing migrations on a copy of production data.

Remember: applied migrations are immutable. Revert the file, add a new migration.

The nightly report e-mail was sent three times, once per pod. How do you fix the @Scheduled job? Intermediate

Every pod runs its own scheduler, so three pods run the job three times. I make the job run once: a distributed lock with ShedLock, or move it to a Kubernetes CronJob. Either way I also make it idempotent, so a repeat does no harm.

Situation. The nightly report mail reached customers three times. You scaled the service to three pods, and @Scheduled runs inside each JVM: it has no idea other instances exist. So all three fire at 02:00.

Check first. The logs show three executions within the same second from three different pod names, not one run retried. Confirm that nothing else (a duplicate trigger, a retry in the mail client) produced the extra sends.

Fix. Two good choices:

OptionHowWhen
ShedLockA lock row in a DB table or Redis; first pod gets it, others skiplight jobs that can stay in the web app
Kubernetes CronJobA separate pod runs the job once on scheduleheavy or long jobs; isolates resources
@Scheduled(cron = "0 0 2 * * *", zone = "UTC")
@SchedulerLock(name = "nightlyReport", lockAtMostFor = "30m", lockAtLeastFor = "5m")
void nightlyReport() { ... }

lockAtMostFor is the safety release if the holder dies: longer than the job takes, but short enough to recover. lockAtLeastFor prevents a second pod from running it again immediately if clocks differ slightly or the job finishes very quickly.

A lock alone is not enough. Locks can expire while a slow job still runs, a pod can crash after sending half the mails, and a manual re-run happens. So make the job idempotent: record "report for 2026-11-18 sent" with a unique key and skip if it exists; send each mail with an idempotency key.

Prevent. In design review treat every @Scheduled as "runs on every instance". Monitor jobs with a "last successful run" metric and alert when stale, so you notice both missing and duplicate runs.

Remember: @Scheduled runs on every pod. Lock it or move it, and make it idempotent.

Turn on virtual threads?spring.threads.virtual.enabled=true (Boot 3.2+, Java 21+).
Which Actuator endpoints are on the web by default?Only health.
Should liveness check the database?No. It causes restart storms.
Default Hikari pool size and timeout?10 connections, 30 s connection timeout.
Is open-in-view on by default?Yes. Turn it off for most services.
Safe ddl-auto in production?none or validate, with Flyway or Liquibase.
Why is validation not working?Missing spring-boot-starter-validation or missing @Valid.
Exception for a failed @Valid body?MethodArgumentNotValidException (400).
Standard error body type?ProblemDetail (RFC 7807 / 9457).
Default test web environment?MOCK (no real server).
Test only the controller layer?@WebMvcTest with MockMvc and @MockitoBean.
Wire a Testcontainer into Boot?@ServiceConnection (Boot 3.1+).
Scheduler thread pool default?One thread.
Make a scheduled job run once across pods?ShedLock, a CronJob or leader election, plus idempotence.
Enable graceful shutdown?server.shutdown=graceful (30 s default drain).
Exit code 137 in Kubernetes?OOMKilled: memory above the container limit.
WebSecurityConfigurerAdapter in Boot 3?Removed. Declare a SecurityFilterChain bean.
