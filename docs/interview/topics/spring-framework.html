Version notes used on this page: Spring Framework 5.3 (Java 8 or newer, javax.* packages) and Spring Framework 6.x (Java 17 or newer, jakarta.* packages; Spring Boot 3 is built on it). So javax.annotation.PostConstruct, javax.servlet, javax.persistence and javax.validation became jakarta.* in Spring 6. Spring Framework 7 (late 2025) continues the line with a Jakarta EE 11 baseline; the concepts below do not change.

Mental model: the 7 ideas everything hangs on

One line: Spring is a container that builds your objects, wires them together, and then wraps many of them in proxies that add behaviour such as transactions, security and caching. Most Spring bugs are either "the container did not create or wire what I thought" or "the proxy was not in the call path".
  1. Inversion of control. You do not call new for your services. You declare what you need, and the container creates and supplies it. This is what makes swapping, mocking and wrapping possible.
  2. Bean definition first, object later. The container first reads recipes (bean definitions) from annotations and config, and only then builds the objects in the right order.
  3. Post-processors are the extension points. BeanFactoryPostProcessor changes recipes. BeanPostProcessor changes or replaces finished objects. Almost every "magic" annotation is implemented by one of these.
  4. Annotations such as @Transactional, @Async, @Cacheable, @PreAuthorize work through proxies. The caller gets a wrapper object. The wrapper does the extra work, then calls your real object. A call that does not go through the wrapper gets no magic.
  5. The bean graph is mostly singletons shared by all threads. So beans must be stateless or thread-safe. Anything per-request or per-user must live in a scope, a method variable, or a ThreadLocal you clean up.
  6. Per-thread context. Transactions, security context and request attributes are stored in ThreadLocal variables. A new thread (async, executor, reactive) does not see them unless you pass them on.
  7. Web requests go through a chain. Servlet filters, then the DispatcherServlet, then interceptors, then your controller, and the same way back. Knowing where each piece sits explains most MVC and Security bugs.

1. IoC, dependency injection, container and scopes

What is Inversion of Control, and what is dependency injection? How are they related? Basic

What the interviewer is testing: can you explain the idea in plain words, not just recite "IoC container".

Normally your class decides which collaborators it uses and creates them with new. With Inversion of Control, that decision moves out: somebody else (the framework) builds the objects and hands them in. Dependency injection is the most common way to do that. The class only says "I need a PaymentGateway" and the container supplies one. The benefit is loose coupling: the class depends on an interface, not on a concrete class or on how it is configured. In tests you pass a fake. In production you pass the real thing, or a proxy that adds transactions or caching. IoC is the broad principle (the framework calls you); DI is one technique to achieve it. Others are the service locator and template-method callbacks.

@Service
class OrderService {
    private final PaymentGateway gateway;          // an interface
    OrderService(PaymentGateway gateway) {         // container supplies it
        this.gateway = gateway;
    }
}
Likely follow-ups
  • Is a service locator IoC too? Yes, but the class still asks for its dependency, so it is harder to test and hides what it needs.
  • Do I need Spring for DI? No. Passing arguments to a constructor by hand is DI. Spring just automates the wiring for big graphs.
Constructor, setter and field injection: what are the differences, and which do you prefer? Basic

What the interviewer is testing: a clear, reasoned preference, with the testing and design arguments.

Constructor injection passes dependencies as constructor arguments. Setter injection calls setter methods after the object is created. Field injection puts @Autowired on a private field and Spring sets it with reflection. I prefer constructor injection for required dependencies. The fields can be final, so the object is immutable and always fully built. You cannot create it half-wired, which means no NullPointerException from a forgotten dependency. A class with eight constructor arguments is also a visible smell that it does too much; field injection hides that. Unit tests can use new OrderService(fakeGateway) with no Spring and no reflection. Setter injection is fine for truly optional dependencies or ones that may be re-configured. Field injection is short, but it makes testing harder, hides the dependency count, and allows circular dependencies to slip through. Since Spring 4.3, a class with one constructor does not need @Autowired at all.

Likely follow-ups
  • Does constructor injection solve circular dependencies? It exposes them, loudly: startup fails with BeanCurrentlyInCreationException. That is the point; fix the design.
  • When is field injection acceptable? In test classes, and in framework glue where nobody else will construct the class.
Common mistakes: saying "field injection is bad because it is slow" (it is not). The real reasons are testability, immutability and hidden coupling.
What is the difference between BeanFactory and ApplicationContext? Basic

What the interviewer is testing: basic container knowledge beyond the textbook line.

BeanFactory is the root interface of the container: it can create beans by name or type and manage their dependencies. ApplicationContext extends it and adds the features real applications need: it automatically detects and applies BeanPostProcessor and BeanFactoryPostProcessor beans, so annotations, AOP and transactions work; it publishes application events; it resolves messages for internationalisation (MessageSource); it loads resources (ResourceLoader); it exposes the Environment with profiles and properties; and it creates all non-lazy singletons at startup, so wiring errors appear when the app starts instead of at the first request. A raw DefaultListableBeanFactory creates beans lazily and applies none of the post-processors unless you add them by hand. In practice you always use an ApplicationContext (for example AnnotationConfigApplicationContext, or the web variants).

Likely follow-ups
  • Why is eager singleton creation useful? Fail fast: a missing bean or bad config stops the deploy, not the first user.
  • Can there be several contexts? Yes. Classic Spring MVC has a parent root context (services) and a child DispatcherServlet context (controllers). Boot normally uses one.
What happens when an ApplicationContext starts? Walk me through refresh(). Senior

What the interviewer is testing: do you know the order, so you can explain why some things work before others (for example why a BeanPostProcessor cannot be proxied by itself).

The central method is AbstractApplicationContext.refresh(). In plain words: first it prepares the environment and property sources. It creates the bean factory and loads bean definitions (from component scanning, @Configuration classes, XML). Then it runs the BeanFactoryPostProcessor beans, which may add or change definitions; this is where @Configuration classes are parsed, @ComponentScan, @Import and @Bean methods are turned into definitions, and ${...} placeholders are resolved. Next it registers all BeanPostProcessor beans, so they can see every ordinary bean made later. It then initialises the message source and event multicaster, lets web contexts start their embedded server (in Boot), registers listeners, and finally instantiates all remaining non-lazy singletons, running the full bean lifecycle on each. The last step publishes ContextRefreshedEvent. Because post-processors are created before ordinary beans, a bean that a post-processor depends on may be created "too early" to be proxied, and Spring logs that such a bean is "not eligible for getting processed by all BeanPostProcessors".

Likely follow-ups
  • Where does @Configuration get processed? In ConfigurationClassPostProcessor, a BeanFactoryPostProcessor.
  • Where do @PostConstruct and @Autowired get handled? In bean post-processors (CommonAnnotationBeanPostProcessor, AutowiredAnnotationBeanPostProcessor).
What is a BeanDefinition, and how does Spring choose which bean to inject? Intermediate

What the interviewer is testing: the resolution rules behind "No qualifying bean" and "expected single matching bean" errors.

A BeanDefinition is the recipe for a bean: class, scope, lazy flag, constructor arguments, property values, init and destroy method names, dependencies. The container keeps these in a map by bean name before it creates any object. To fill an injection point, Spring does this. First it finds all beans whose type matches. If there is exactly one, done. If there are several, it looks for one marked @Primary. Otherwise it applies @Qualifier if present. As a last fallback it compares the injection point's field or parameter name to the bean names. If still ambiguous, you get NoUniqueBeanDefinitionException. If none match, NoSuchBeanDefinitionException (the message "No qualifying bean of type..."). If the type is List<T>, Set<T> or Map<String,T>, Spring injects all matching beans; use @Order to sort the list.

@Bean @Primary DataSource mainDs() {...}
@Bean DataSource reportDs() {...}

@Autowired                       DataSource ds;       // mainDs (primary)
@Autowired @Qualifier("reportDs") DataSource rds;     // by qualifier
Likely follow-ups
  • What if a dependency is optional? @Autowired(required = false), Optional<T>, or ObjectProvider<T>.
  • Difference between @Autowired, @Resource and @Inject? @Autowired is Spring's and matches by type first. @Resource (jakarta.annotation) matches by name first. @Inject (jakarta.inject) is the standard twin of @Autowired without the required flag.
What bean scopes does Spring have, and which is the default? Basic

What the interviewer is testing: scope basics plus the awareness that singleton means shared across threads.

The default is singleton: one instance per container (not per JVM, and not the GoF pattern), shared by all threads. Prototype creates a new instance every time the bean is requested from the container. In a web application there are also request (one per HTTP request), session (one per HTTP session), application (one per ServletContext) and websocket. You can register custom scopes (Spring Batch uses step, Spring Cloud uses refresh). Because singletons are shared, they must not keep per-request state in fields. A service with a field currentUser will mix data between concurrent users, one of the most expensive classic bugs. Stateless singletons plus method-local state is the usual design.

@Component @Scope("prototype")                       class ReportBuilder {}
@Component @RequestScope                             class RequestInfo {}   // proxied
@Component @SessionScope                             class Cart {}
Likely follow-ups
  • Is a singleton bean thread-safe? Only if you make it so. Spring does not synchronise anything for you.
  • When is a singleton created? At startup, unless @Lazy is set.
What happens if you inject a prototype bean into a singleton? How do you fix it? Intermediate

What the interviewer is testing: the classic scope-mismatch trap, and whether you know the standard fixes.

Injection happens once, when the singleton is created. So the singleton gets exactly one prototype instance and keeps it forever. The "new instance per use" you expected never happens, and that one instance is now shared by all threads. The same trap applies to request or session scoped beans injected into a singleton, except there Spring fails at startup with "Scope 'request' is not active" unless a proxy is used. There are four fixes. (1) Inject ObjectProvider<T> (or jakarta.inject.Provider) and call getObject() each time you need a fresh instance. (2) Use @Lookup on an abstract or overridable method; Spring generates a subclass that asks the container each time. (3) Declare the scope with a proxy: @Scope(value="prototype", proxyMode=ScopedProxyMode.TARGET_CLASS); the singleton holds a small proxy that looks up the real target on every call. (4) Inject the ApplicationContext and call getBean, which works but couples you to Spring, so avoid it. I prefer ObjectProvider for its clarity.

Common mistakes: thinking prototype scope means a new object per injection point per call. It means a new object per container lookup. Also forgetting that Spring does not call destroy callbacks on prototypes.
How can a singleton controller use a request scoped bean? Intermediate

What the interviewer is testing: scoped proxies in practice.

When the singleton is created at startup there is no request, so the container cannot create a real request bean. The fix is a scoped proxy. @RequestScope and @SessionScope already set proxyMode = TARGET_CLASS. The singleton receives a CGLIB proxy that looks like the bean. On every method call, the proxy finds the current request (through a ThreadLocal holder, RequestContextHolder), fetches or creates the real request bean from the request attributes, and delegates. That also explains the error "No thread-bound request found": you used the request scoped bean on a thread that is not handling a request, for example inside @Async or a scheduled job. The fix is to pass the needed values as plain arguments instead.

Likely follow-ups
  • Why not just inject a field in the controller? Controllers are singletons; per-request data in a field is shared between users.
  • Is it good style? Sparingly. Often simpler: read the value in the controller and pass it down as a parameter.
What does @Lazy do, and when would you use it? Intermediate

What the interviewer is testing: knowing both meanings, as a bean flag and as an injection-point flag.

On a bean (@Component @Lazy or @Bean @Lazy) it means "do not create this singleton at startup; create it on first use". This speeds start-up and avoids paying for rarely used beans, but it moves errors from startup to runtime, so a wiring problem shows up under load. On an injection point (@Autowired @Lazy Service s) Spring injects a lazy-resolution proxy and only builds the target when you first call a method. This is a common way to break a circular dependency and to inject a heavy bean only when needed. There is also a global switch, spring.main.lazy-initialization=true in Boot, which I use only in local development or tests, since it hides startup failures.

Likely follow-ups
  • Does lazy make a request slower? Yes, the first one that touches the bean pays the creation cost.
What is the difference between @Component and @Bean? Basic

What the interviewer is testing: when to use each way to declare a bean.

@Component (and its specialisations) goes on your own class. Spring finds it by scanning the classpath and creates the bean by calling a constructor. @Bean goes on a method inside a @Configuration class; the method body builds and returns the object, and Spring registers the return value as a bean. Use @Bean when you cannot annotate the class (a third-party class such as ObjectMapper, RestTemplate, a DataSource), when construction needs logic, or when you want several differently configured beans of the same type. Use @Component for your own application classes because it is shorter and keeps the class self-describing.

@Component, @Service, @Repository, @Controller: is there a real difference? Basic

What the interviewer is testing: whether you know the technical differences and not only "they are all the same".

All are stereotype annotations; @Service, @Repository and @Controller are meta-annotated with @Component, so scanning treats them alike. The extra meaning: @Service is documentation only (marks business logic) today. @Repository adds real behaviour: a post-processor wraps the bean to translate persistence exceptions (such as SQLException or Hibernate exceptions) into Spring's unchecked DataAccessException hierarchy. @Controller tells RequestMappingHandlerMapping to look for request mapping methods on it; @RestController is @Controller plus @ResponseBody. Choosing the right stereotype also helps tools, AOP pointcuts (for example "all @Service classes") and readers.

How does component scanning work, and why might a bean not be found? Intermediate

What the interviewer is testing: practical debugging of missing beans.

@ComponentScan tells Spring to look through a base package and its sub-packages for classes carrying @Component or a stereotype, read their class files (without loading them), and register definitions. If no base package is given, it uses the package of the annotated configuration class. The common reasons a bean is "not found": the class lives in a package outside the scanned tree (for example the main class is in com.acme.app but the bean is in com.acme.shared); the annotation is missing; the class is an interface or abstract; a conditional (@Profile, @ConditionalOnProperty) switched it off; or the class was created with new by hand. The fix is to move the class, widen scanBasePackages, or declare it with @Import or @Bean. Scanning cost grows with the number of classes, which matters for startup time (see the slow-startup scenario).

@Configuration
@ComponentScan(basePackages = {"com.acme.app", "com.acme.shared"})
class AppConfig {}
When do you use @Primary and when @Qualifier? Basic

What the interviewer is testing: picking among several beans of one type.

Use @Primary on the bean that should win by default when there are several candidates, for example your main DataSource. Callers do nothing special. Use @Qualifier("name") at the injection point when a particular consumer needs a specific one. When both exist, the qualifier wins over primary, because it is more specific. You can create your own qualifier annotation (meta-annotated with @Qualifier) to avoid magic strings. Injecting List<PaymentStrategy> or Map<String, PaymentStrategy> is a nice way to implement the strategy pattern without any if chain: the map key is the bean name.

What is ObjectProvider, and why use it instead of injecting the bean directly? Intermediate

What the interviewer is testing: modern, flexible injection.

ObjectProvider<T> is a handle that resolves the bean later and on demand. getObject() returns it (a fresh one for prototypes), getIfAvailable() returns null when the bean does not exist, getIfUnique() tolerates multiple candidates, stream() and orderedStream() give all matches. I use it for four things: optional dependencies, prototype or request scoped beans inside singletons, deferring a heavy bean, and breaking a circular dependency without a hard failure. It keeps the dependency visible in the constructor signature and is easier to test than ApplicationContext.getBean.

Is a Spring singleton the same as the Singleton design pattern? Intermediate

What the interviewer is testing: a favourite trick question.

No. The GoF Singleton guarantees one instance per class loader (or JVM) and enforces it in code with a private constructor. A Spring singleton means one instance per bean definition per container. If you define two beans of the same class with different names, you get two instances, both "singleton scoped". If you run two application contexts, you get two instances again. Spring does not stop you from also calling new on the class. Because of that, thread safety is a design concern for you, not something the scope gives you.

2. Bean lifecycle and post-processors

Describe the full lifecycle of a singleton bean, with all the hooks. Intermediate

What the interviewer is testing: the exact order, which is asked in almost every Spring interview.

The steps for one singleton: (1) Spring instantiates it by calling the constructor (or factory method). (2) It populates dependencies: setter and field injection. (3) Aware callbacks run: BeanNameAware, BeanFactoryAware, ApplicationContextAware. (4) Every BeanPostProcessor.postProcessBeforeInitialization runs; this is where @PostConstruct is called, because that annotation is handled by a post-processor. (5) InitializingBean.afterPropertiesSet(). (6) The custom init-method (@Bean(initMethod="...")). (7) Every BeanPostProcessor.postProcessAfterInitialization runs; this is where AOP proxies for @Transactional, @Async and so on are created, and the proxy replaces the raw bean in the container. The bean is now ready. On shutdown: (8) @PreDestroy, (9) DisposableBean.destroy(), (10) custom destroy-method. Remember "annotation, interface, custom method" for both start and end. Prototypes get steps 1 to 7 but Spring never calls their destroy callbacks.

Likely follow-ups
  • Which hook would you choose for new code? @PostConstruct and @PreDestroy; they do not couple your class to Spring interfaces.
  • In Spring 6 which package? jakarta.annotation.PostConstruct. In Spring 5 it was javax.annotation.
What is the difference between BeanPostProcessor and BeanFactoryPostProcessor? Intermediate

What the interviewer is testing: the two main extension points and their timing.

A BeanFactoryPostProcessor works on bean definitions after they are loaded and before any ordinary bean exists. It can add definitions or change property values in them. Examples: ConfigurationClassPostProcessor (reads @Configuration, @Bean, @ComponentScan) and the placeholder resolver for ${...}. A BeanPostProcessor works on bean instances, for each bean, before and after its init methods. It can modify the object or return a different one, such as a proxy. Examples: AutowiredAnnotationBeanPostProcessor (does @Autowired and @Value), CommonAnnotationBeanPostProcessor (@PostConstruct, @Resource), and AbstractAutoProxyCreator (AOP proxies). A practical consequence: declare a BeanFactoryPostProcessor @Bean method as static, so the containing configuration class need not be created early.

@Component
class TimingBpp implements BeanPostProcessor {
    public Object postProcessAfterInitialization(Object bean, String name) {
        // return the bean itself or a wrapper
        return bean;
    }
}
Likely follow-ups
  • Can a BeanPostProcessor use @Autowired? Its dependencies get created early and are not post-processed themselves; keep BPPs light and free of dependencies.
What should and should not go into @PostConstruct? Intermediate

What the interviewer is testing: awareness that the bean is not fully "ready" when the init hook runs.

@PostConstruct is good for cheap, local set-up that needs injected fields: build a cache, validate configuration, start a lightweight resource. It runs once, per bean, in the thread that creates the bean, and a failure aborts startup. Things to avoid: calling your own @Transactional or @Cacheable methods. At that moment the proxy does not exist yet (it is created in step 7, after init), so this.save() runs with no transaction. Do not do slow remote calls or big queries, since they block startup and delay readiness probes. Do not start request handling that depends on beans not yet created. For "run after everything is up", use ApplicationReadyEvent or SmartInitializingSingleton, or in Boot an ApplicationRunner. For data loading that needs a transaction, call a separate bean's transactional method from such a late hook.

Common mistakes: an unhandled exception in @PostConstruct kills the whole application start-up; wrap optional work in a try/catch with a log, or move it to a background task.
What is a FactoryBean, and how is it different from a BeanFactory? Senior

What the interviewer is testing: a known confusing pair of names.

A BeanFactory is the container. A FactoryBean<T> is a special bean that acts as a factory for another object: the container calls its getObject() to produce the bean registered under that name. It is used when creating the object needs complex logic that a constructor cannot express. Spring's own examples: LocalContainerEntityManagerFactoryBean, ProxyFactoryBean, and the factory that creates Spring Data repository proxies. If you ask for the bean by name, you receive the product. If you prefix the name with & (getBean("&myFactory")) you receive the factory itself. In new code, a plain @Bean method does the same job with less ceremony, so FactoryBean is mostly framework territory today.

Does Spring always call @PreDestroy? When might it not run? Intermediate

What the interviewer is testing: graceful shutdown awareness.

Destroy callbacks run when the context is closed, which happens on a normal JVM shutdown (a shutdown hook is registered; Boot does that by default) or when you call close(). They do not run if the JVM is killed hard (kill -9, out-of-memory kill, power loss). They also do not run for prototype beans, because the container hands the object over and forgets it. They run in reverse order of dependency, so a bean is destroyed before the beans it depends on. For @Bean methods, Spring infers a public close() or shutdown() method as the destroy method unless you disable it. In production, pair this with a graceful shutdown (stop accepting new requests, finish in-flight ones, then close). Boot supports server.shutdown=graceful for that.

3. Configuration, profiles and properties

What does @Configuration do? Explain "full" versus "lite" mode and proxyBeanMethods. Senior

What the interviewer is testing: understanding that @Configuration classes are CGLIB-proxied for inter-bean calls.

A @Configuration class holds @Bean methods. In full mode (the default, proxyBeanMethods = true) Spring creates a CGLIB subclass of your configuration class. When one @Bean method calls another (return new A(b());), the subclass intercepts the call and returns the existing singleton b from the container instead of running the method again. That keeps singleton semantics and honours scopes even when you write plain Java calls. In lite mode the class is not proxied: this applies to @Bean methods declared in a @Component, or in a @Configuration(proxyBeanMethods = false) class. There, calling another @Bean method is an ordinary Java call, which creates a new object each time, so the singleton rule is broken. Lite mode starts faster, uses less memory and works with GraalVM native images, so Spring Boot uses it for its own auto-configurations. Use proxyBeanMethods = false when your @Bean methods never call each other, and pass dependencies as method parameters instead.

@Configuration(proxyBeanMethods = false)
class Cfg {
    @Bean B b() { return new B(); }
    @Bean A a(B b) { return new A(b); }   // dependency as parameter: safe in both modes
}
Likely follow-ups
  • Why must a @Configuration class not be final? CGLIB must subclass it. Spring checks and fails fast.
  • Why prefer method parameters? They work in both modes and make the dependency explicit.
Java config, XML config, annotation config: how has configuration style changed? Basic

What the interviewer is testing: whether you can still read legacy code, and know the modern default.

Early Spring (2004 to 2008) used XML files listing every bean. Spring 2.5 added annotations such as @Autowired and @Component with component scanning, so most beans needed no listing. Spring 3 added Java config (@Configuration and @Bean), which is type-safe, refactorable and debuggable. Today, the normal approach is: stereotype annotations with scanning for your own classes, plus Java config (@Bean) for third-party objects, and Boot auto-configuration for infrastructure. XML is still read in legacy systems; it can be mixed with Java config using @ImportResource. The benefits of Java config: compile-time checking, easy navigation, conditionals written in plain code.

How do profiles work, and how do you make config differ per environment? Basic

What the interviewer is testing: practical environment handling, and the common ways it breaks.

A profile is a named group of beans and properties that is active only when you ask for it. Mark a bean with @Profile("dev") (also "!prod" or expressions like "dev & local") and it is registered only if the profile is active. Choose active profiles with the spring.profiles.active property, environment variable SPRING_PROFILES_ACTIVE, a JVM argument -Dspring.profiles.active=prod, or @ActiveProfiles in tests. In Boot, files named application-{profile}.yml are loaded in addition to application.yml when that profile is active, and the profile file overrides the base file. Practical rules: keep the same code in all environments and vary only configuration; keep secrets out of the repository and supply them through the environment or a secret store; do not use @Profile("prod") to hide business logic that is untested elsewhere. If no profile is set, the default profile is active.

Likely follow-ups
  • Can I activate several? Yes, comma separated; later ones override earlier ones.
  • What is the Boot 2.4 change? Inside a multi-document file you now use spring.config.activate.on-profile instead of spring.profiles. See the Spring Boot page for config loading order.
@Value versus @ConfigurationProperties: which and when? Intermediate

What the interviewer is testing: type-safe configuration habits.

@Value("${app.timeout:30}") injects one value, with an optional default after the colon, and also supports SpEL such as #{...}. It is fine for one or two simple values. @ConfigurationProperties(prefix = "app.payment") binds a whole group of properties to a typed class: lists, maps, nested objects, durations (30s), data sizes. It uses relaxed binding (max-retries, maxRetries and MAX_RETRIES all map to maxRetries), supports bean validation with @Validated, and gives IDE metadata. With records or a single constructor, Boot 3 binds through the constructor, which makes the config immutable. I use it for anything beyond two values, because a wrong property then fails at startup with a clear message. With @Value, a missing key with no default also fails at startup, but a typo in a default-valued key silently uses the default.

@ConfigurationProperties(prefix = "app.payment")
@Validated
record PaymentProps(@NotBlank String url, Duration timeout, int maxRetries) {}
Likely follow-ups
  • Why is @Value null in my class? The object was created with new, not by Spring, or the field is static, or the placeholder was not resolved.
What is the Environment, and how are property sources ordered? Intermediate

What the interviewer is testing: which value wins when the same key is set in many places.

The Environment is the container's view of two things: the active profiles and a stack of PropertySource objects (system properties, OS environment variables, config files, @PropertySource files). When you ask for a key, Spring searches the stack top to bottom and returns the first hit. So the order decides the winner. In a typical Boot app, from highest to lowest priority: command line arguments, Java system properties (-D), OS environment variables, profile specific config files, then the main config file, then @PropertySource classpath files, then defaults set in code. The consequence for operations: an environment variable or command line flag beats the file packaged inside the jar, which is how you override settings per deployment without rebuilding. Note that @PropertySource does not support YAML files by default and sits low in the order. Details of Boot's full order are on the Spring Boot page.

@Autowired Environment env;
String v = env.getProperty("app.mode", "default");
boolean prod = env.acceptsProfiles(Profiles.of("prod"));
What do @Conditional, @Import and @ImportResource do? Senior

What the interviewer is testing: the building blocks behind modular configuration (and, indirectly, Boot auto-configuration).

@Conditional takes a Condition class with a matches method; the bean or configuration is registered only when it returns true. @Profile is itself implemented as a condition. Boot adds many: @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty. @Import pulls other configuration classes (or an ImportSelector or ImportBeanDefinitionRegistrar) into the current one, without scanning. That is how a library can offer @EnableXyz annotations: the annotation is meta-annotated with @Import(XyzConfiguration.class). @ImportResource loads legacy XML definitions. Together these give a module system: libraries expose opt-in configuration, and applications turn it on explicitly.

What is a circular dependency in Spring, and how does Spring handle it? Senior

What the interviewer is testing: the three-level cache and an opinion about design.

A circular dependency means A needs B and B needs A. With constructor injection, neither can be created first, so Spring fails with BeanCurrentlyInCreationException. With setter or field injection on singletons, Spring used to resolve it with three caches: singletonObjects (finished beans), earlySingletonObjects (early references), and singletonFactories (factories that can produce an early reference). It creates A, but before filling A's fields it stores a factory for A's early reference. While injecting A's fields, it needs B, creates B, and B needs A, which is found through that factory as an early (not yet finished) reference. B finishes, then A finishes. The factory exists so that, if A is going to be proxied, B gets the proxy and not the raw A. Since Spring Boot 2.6, circular references are disallowed by default (spring.main.allow-circular-references=false). I treat a cycle as a design smell: split a third class that holds the shared logic, use events, or invert one dependency to an interface. If you must, use @Lazy on one injection point.

Likely follow-ups
  • Why can an early reference be wrong? The early A may be the raw object while the final A becomes a proxy; Spring detects this and fails with "has been injected into other beans in its raw version".
  • Fix without redesign? @Lazy on the constructor parameter, or ObjectProvider.
How does Spring make unit testing easier, and how do you test a service with no Spring at all? Basic

What the interviewer is testing: that you keep fast unit tests free of the container.

Because dependencies come in through the constructor, a unit test can build the class with new and pass in mocks or hand-written fakes. No Spring context starts, so the test runs in milliseconds. A Spring context test (@SpringBootTest, @ContextConfiguration) is for checking wiring, configuration and integration, and costs seconds. A healthy suite is mostly plain unit tests, some slice tests (web layer or data layer only), and a few full-context tests. If your service needs reflection or a context just to be tested, that is usually a sign of field injection or static calls that you should refactor.

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock PaymentGateway gateway;
    @Test void pays() {
        var svc = new OrderService(gateway);       // no Spring
        // ...
    }
}

4. Proxies and AOP

Why does Spring use proxies, and which features rely on them? Intermediate

What the interviewer is testing: the key to understanding every "annotation does nothing" bug.

Spring wants to add behaviour (start a transaction, check security, cache a result, run on another thread) without you writing that code in each method, and without changing your class. The trick is a proxy: an object that looks like your bean, wraps the real one, and adds the extra steps around each call. The container puts the proxy into the bean map instead of the real object, so anyone who injects the bean gets the proxy. Features built this way include @Transactional, @Async, @Cacheable and the other cache annotations, @PreAuthorize and method security, @Validated method validation, @Retryable (Spring Retry), scoped proxies and your own aspects. The big rule that follows: the extra behaviour happens only on calls that arrive through the proxy. A call from inside the same object (this.other()) skips it.

What is the difference between JDK dynamic proxies and CGLIB proxies? Intermediate

What the interviewer is testing: how the proxy is built, and the limits that follow.

A JDK dynamic proxy is created with java.lang.reflect.Proxy. It implements the interfaces of the target, so it can only be used where the bean is injected as that interface. If you inject the concrete class, it fails with a "cannot be cast" error. A CGLIB proxy generates a subclass of the target class at runtime, overriding its methods. It works without interfaces. Its limits come from subclassing: the class and the advised methods cannot be final, a private method cannot be overridden so it cannot be advised, and the class needs a visible constructor (modern Spring uses Objenesis, so the constructor is not even called). Which one is chosen? Plain Spring picks JDK proxies when the target implements an interface and CGLIB otherwise. Spring Boot sets spring.aop.proxy-target-class=true by default, so Boot uses CGLIB almost everywhere, which avoids the cast problem. In both cases the proxy is a different object from the target, so this inside the target is the target, not the proxy.

Likely follow-ups
  • Why does getClass() print $$SpringCGLIB$$? You are looking at the proxy subclass. Use AopUtils.getTargetClass(bean) for the real class.
  • Does final on a Kotlin class matter? Yes, Kotlin classes are final by default; use the Kotlin allopen plugin for Spring.
Explain AOP terms: aspect, join point, pointcut, advice, weaving. Basic

What the interviewer is testing: vocabulary with a concrete example.

AOP (aspect-oriented programming) handles cross-cutting concerns: logic needed in many places that is not core business logic, such as logging, timing, security and transactions. An aspect is the module holding it (a class with @Aspect). A join point is a point in the program where it could apply; in Spring AOP that is always a method execution. A pointcut is an expression that selects which join points to apply to, for example "all public methods in the service package". An advice is the code to run there, and its type says when. Weaving is the act of linking aspects to targets; Spring does it at runtime by creating proxies, while AspectJ can do it at compile time or class load time. A target is the object being advised.

@Aspect @Component
class TimingAspect {
    @Around("execution(* com.acme.service..*(..))")
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        long t = System.nanoTime();
        try { return pjp.proceed(); }
        finally { log.info("{} took {} ms", pjp.getSignature(), (System.nanoTime() - t) / 1_000_000); }
    }
}
What are the advice types, and in what order do they run? Intermediate

What the interviewer is testing: precise behaviour of each advice and when it fires.

@Before runs before the method and cannot stop it (unless it throws). @AfterReturning runs only when the method returns normally and can see the result. @AfterThrowing runs only when it throws, and can see the exception. @After (finally) always runs, success or failure. @Around is the most powerful: it wraps the call, decides whether to call proceed() at all, may change arguments and the result, and may catch exceptions. For one aspect, the flow is: Around (before part), Before, the method, then AfterReturning or AfterThrowing, then After, then Around (after part). When several aspects apply, order them with @Order (lower number is outer, runs first on the way in, last on the way out). Use the weakest advice that does the job; an @Around that forgets to call proceed() or swallows exceptions silently breaks the application.

How do you write pointcut expressions? Give examples of execution, within, @annotation and bean. Intermediate

What the interviewer is testing: can you actually write one.

The most used designator is execution(modifiers? return-type declaring-type? name(params) throws?). execution(* com.acme.service.*.*(..)) means any return type, any class directly in the package, any method, any arguments. .. after a package means "and sub-packages". within(com.acme.service..*) matches all methods in the types in that package tree. @annotation(com.acme.Audited) matches methods carrying that annotation, which is the cleanest way to opt in: you mark methods and the aspect finds them. @within(...) matches classes with an annotation. bean(*Service) is Spring-specific and matches by bean name. args(..) and this/target bind arguments and objects. Combine with &&, ||, !. Name reusable pointcuts with an empty @Pointcut method. Prefer annotation-based pointcuts for custom aspects, since package-based ones break silently when classes move.

@Pointcut("within(@org.springframework.stereotype.Service *)")
void services() {}

@Around("services() && @annotation(audited)")
Object audit(ProceedingJoinPoint pjp, Audited audited) throws Throwable {...}
Why does @Transactional (or @Async, @Cacheable) not work when a method calls another method in the same class? Intermediate

What the interviewer is testing: the most common Spring gotcha, explained from first principles.

Because the advice lives in the proxy and the call never touches the proxy. Another bean that injects OrderService really gets OrderService$$Proxy. When it calls placeOrder(), the proxy starts a transaction and then calls the real object. Inside the real object, this is the real object, not the proxy. So when placeOrder() calls this.audit(), that is a direct Java call and the proxy is bypassed, so audit()'s @Transactional(REQUIRES_NEW) or @Async is ignored. The fixes, in order of preference: (1) move the method into another bean and inject it, which is clean and usually a better design; (2) inject a self reference (@Lazy self-injection) or fetch the proxy through AopContext.currentProxy() with exposeProxy = true, which works but is ugly; (3) switch to AspectJ weaving, which changes the bytecode so the advice applies to internal calls too, at the price of build setup; (4) use TransactionTemplate programmatically inside the method.

Likely follow-ups
  • Does the same hold for private methods? Yes, and they cannot be advised at all.
  • Does the same hold for @PostConstruct calling a transactional method? Yes, the proxy is not created yet.
What are the limitations of Spring AOP, and when would you use AspectJ instead? Senior

What the interviewer is testing: knowing where proxy-based AOP stops.

Spring AOP is proxy-based and only on Spring beans. So it only advises public (and for class proxies in Spring 6, protected and package-visible) method calls that come through the proxy on container-managed beans. It cannot advise: private methods, calls inside the same object, final classes or methods with CGLIB, objects created with new, field access, constructors, or static methods. It also adds a small cost per call. AspectJ modifies bytecode (compile-time, post-compile or load-time weaving), so it can advise any join point on any object, including constructors, field reads, and self calls, and has no proxy overhead. The price is build-tool setup (ajc compiler or a Java agent), longer builds and harder debugging. In 95 percent of apps Spring AOP is enough. Choose AspectJ when you need to advise non-Spring objects such as domain entities (@Configurable), or when self-invocation must be covered, or the proxy overhead is measured to matter.

Where have you used AOP in a real project, and what would you avoid doing with it? Intermediate

What the interviewer is testing: judgement, not just definitions.

Good uses: audit logging of selected operations (a custom @Audited annotation), timing and metrics around service calls, retry and circuit-breaker annotations, tenant or correlation-id context set-up and clean-up, permission checks, idempotency guards, and translating exceptions at a module boundary. What I avoid: putting core business rules in aspects, since the flow is invisible when reading the service code; aspects with side effects that change return values in surprising ways; broad pointcuts such as "every method of every bean", which hurt performance and create startup surprises; and swallowing exceptions in @Around advice. Keep aspects small, tested, and opt-in through an annotation so a reader of the service can see that something extra happens. Mention that logging every argument can leak personal data into logs.

5. Transactions with @Transactional

How does @Transactional work internally? Intermediate

What the interviewer is testing: that you can describe the proxy, the interceptor, the transaction manager and the thread binding.

Spring creates a proxy around the bean (as explained in the AOP section). When a transactional method is called through the proxy, a TransactionInterceptor runs. It reads the @Transactional attributes (propagation, isolation, timeout, read-only, rollback rules) and asks the configured PlatformTransactionManager (for example JpaTransactionManager or DataSourceTransactionManager) to start or join a transaction. The manager gets a database connection from the pool, turns off auto-commit, and binds the connection (and the JPA EntityManager) to the current thread using TransactionSynchronizationManager, which is a set of ThreadLocals. Any repository or JdbcTemplate call on that thread then finds the same connection, so all work is in one transaction. The interceptor calls your method. If it returns, the manager commits. If it throws an exception that matches the rollback rules, the manager rolls back. Then it unbinds and returns the connection to the pool. Everything depends on the thread: a new thread has no transaction.

Likely follow-ups
  • What if there are two data sources? Define two transaction managers and name one in @Transactional("orderTm").
  • When does the JPA flush happen? At commit, or earlier before a query that needs it. That is why constraint violations often appear at commit time, outside your try/catch.
Explain the transaction propagation levels. Intermediate

What the interviewer is testing: real understanding of REQUIRED versus REQUIRES_NEW and when others matter.

Propagation says what to do when a transactional method is called while a transaction may already exist. REQUIRED (default): join the existing one, or create one if none. REQUIRES_NEW: suspend the current one and start a fully separate transaction; it commits or rolls back independently. SUPPORTS: join if there is one, otherwise run without. NOT_SUPPORTED: suspend the current one and run without a transaction. MANDATORY: must already be inside one, else throw. NEVER: must not be inside one, else throw. NESTED: run in a savepoint inside the current transaction; if the inner part fails, only the savepoint is rolled back and the outer transaction can continue. NESTED needs a JDBC savepoint-capable setup (it works with DataSourceTransactionManager; with JPA it generally does not). Real uses: REQUIRES_NEW for writing an audit record that must survive even if the main work rolls back; NOT_SUPPORTED for a slow report that should not hold a transaction open; MANDATORY on methods that must never be called alone.

  • What risk does REQUIRES_NEW add? Pool exhaustion and deadlocks: each in-flight request can hold two connections, and the inner one may wait on a row locked by the outer one.
  • REQUIRED inside REQUIRED, the inner throws and the outer catches it. What happens? The shared transaction is already marked rollback-only, so the outer commit throws UnexpectedRollbackException.
For which exceptions does @Transactional roll back? What about checked exceptions? Intermediate

What the interviewer is testing: a favourite pitfall, with the reasoning behind the default.

By default Spring rolls back on unchecked exceptions (RuntimeException and its subclasses) and on Error. It does not roll back for checked exceptions such as IOException or your own extends Exception; the transaction commits. The rule copies the EJB convention: a checked exception was thought of as a recoverable business outcome, not a system failure. Many teams are surprised by it. Fix it per method with @Transactional(rollbackFor = Exception.class) or rollbackFor = PaymentException.class, and use noRollbackFor for the opposite. Another cause of "no rollback": you catch the exception inside the method and swallow it, so the proxy never sees an exception. Then either rethrow, or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(). Many teams make their domain exceptions unchecked to avoid the problem altogether.

@Transactional(rollbackFor = Exception.class)
public void pay(Order o) throws PaymentException { ... }

// swallowed exception: no rollback
@Transactional
public void bad() {
    try { repo.save(x); } catch (Exception e) { log.warn("ignored", e); }
}
Common mistakes: believing "any exception rolls back". Also forgetting that a caught exception from a REQUIRED inner call still marks the shared transaction rollback-only.
What are the isolation levels and the problems they prevent? Intermediate

What the interviewer is testing: can you connect isolation levels to concrete anomalies, and know the defaults.

Isolation controls what a transaction can see from other concurrent transactions. Dirty read: reading data another transaction has not committed. Non-repeatable read: reading the same row twice and getting different values because someone committed in between. Phantom read: running the same range query twice and getting different sets of rows. READ_UNCOMMITTED allows all three. READ_COMMITTED prevents dirty reads (the default in PostgreSQL, Oracle and SQL Server). REPEATABLE_READ also prevents non-repeatable reads (the default in MySQL InnoDB; in PostgreSQL it uses snapshots and also prevents phantoms). SERIALIZABLE prevents all, by behaving as if transactions ran one at a time, at a high cost in locks or retries. In Spring, @Transactional(isolation = Isolation.X) asks the database for that level when a new transaction begins; it is ignored when you join an existing one. DEFAULT means "use the database default". For most business code I stay on the default and protect specific updates with optimistic locking (@Version) or SELECT ... FOR UPDATE. The SQL databases page goes deeper into locking.

What does @Transactional(readOnly = true) actually do? Intermediate

What the interviewer is testing: the fact that it is an optimisation hint, not a guard.

It is a hint passed down to the transaction manager and the persistence provider. With Hibernate, Spring sets the session flush mode to MANUAL, so Hibernate skips dirty checking and does not flush at the end. That saves CPU and memory in read-heavy methods. Spring also asks the JDBC connection to be read-only (Connection.setReadOnly(true)), which some drivers and databases use to reject writes or to route the query to a read replica (for example through a routing DataSource). It does not make the code safe by itself: with some databases, writes still succeed, and a read-only flag on a method that joins an outer read-write transaction is ignored. It also does not change visibility; for a consistent snapshot across several reads you still need the right isolation. Good practice: put readOnly = true at class level on query services and override with plain @Transactional on write methods. Spring Data's SimpleJpaRepository does just that.

Where should @Transactional go: interface or class, controller or service, public or private methods? Intermediate

What the interviewer is testing: layering sense and awareness of the proxy rules.

Put it on the service layer method (or class) that represents one business operation: one use case, one transaction. Not on controllers, because the transaction would then stay open during JSON serialisation and view rendering, and not on repositories, because separate repository calls would then not share one unit of work. Annotate the concrete class; Spring documents that annotations on interfaces work only with interface-based proxies, so class-level annotations are safer. It works on public methods; for class-based proxies Spring 6 also honours protected and package-visible methods, but it never works on private methods. Keep transactions short: do remote calls, file uploads and long computation outside the transaction, since the database connection and any row locks are held for the whole method. Do not mix several unrelated business operations in one huge transaction.

How do @Transactional and @Async or other threads interact? Senior

What the interviewer is testing: the ThreadLocal nature of transactions.

A transaction belongs to one thread. If a transactional method hands work to another thread (@Async, an ExecutorService, CompletableFuture.supplyAsync, a parallel stream) that work runs outside the caller's transaction. It gets its own connection and transaction if its own method is transactional, or none at all. Consequences: the async code cannot see uncommitted data from the caller, so it may fail to find a row the caller has just inserted but not yet committed; a rollback of the caller does not undo what the async code did; and lazy loaded entities from the caller's persistence context are not usable in the other thread. Fix by making the async step start only after commit, using @TransactionalEventListener(phase = AFTER_COMMIT) that triggers the async work, and by passing IDs or immutable DTOs to the other thread, never managed entities. The same holds for security context and request attributes, which are also ThreadLocal.

How do you run code only after a transaction commits, for example sending an email or a Kafka message? Senior

What the interviewer is testing: avoiding the "message sent but transaction rolled back" bug.

If you send the email or message inside the transactional method and the transaction later rolls back (or fails at commit), the outside world already got a lie. Publish a Spring event inside the transaction and handle it with @TransactionalEventListener whose default phase is AFTER_COMMIT. The listener runs only if the commit succeeded. Alternatively register a callback directly with TransactionSynchronizationManager.registerSynchronization(...). Remember that at AFTER_COMMIT the original transaction is complete, so any database write in the listener needs its own transaction (@Transactional(propagation = REQUIRES_NEW)), otherwise it is silently not committed. For truly reliable delivery (a crash between commit and send loses the message) use the transactional outbox pattern: write the message to an outbox table in the same transaction, and let a poller or CDC publish it. See the microservices page and the Kafka page.

@Service class OrderService {
    @Transactional void place(Order o) {
        repo.save(o);
        events.publishEvent(new OrderPlaced(o.getId()));   // plain data
    }
}
@Component class Mailer {
    @TransactionalEventListener   // AFTER_COMMIT by default
    void on(OrderPlaced e) { send(e.id()); }
}
When would you use TransactionTemplate instead of the annotation? Intermediate

What the interviewer is testing: alternatives and when the annotation is the wrong tool.

TransactionTemplate lets you wrap just a block of code in a transaction, in plain Java. It avoids the proxy limits, so it works for self-invocation and for private methods. It is better when only part of a method should be transactional, for example: call a remote API first, then open a short transaction for the database write. It also makes the boundaries visible and lets you decide the rollback logic in code (status.setRollbackOnly()). The cost is more verbose code, and the transaction code mixes with the business code. I use the annotation for most services, and the template for batch loops that commit every N items, and for the "avoid holding a transaction across a remote call" case.

Result r = http.call();                          // no transaction yet
tx.executeWithoutResult(status -> {              // short transaction
    repo.save(map(r));
});
What is Open Session In View, and why is it controversial? Senior

What the interviewer is testing: knowing a default that affects performance and connection use.

With Open Session In View (OSIV) the JPA EntityManager (Hibernate session) stays open for the whole web request, including rendering the response. Because of that, lazy associations can be loaded in the controller or in JSON serialisation without a LazyInitializationException. In Spring Boot this is on by default (spring.jpa.open-in-view=true) and Boot prints a warning at startup. The problems: the database connection is held for the whole request (it is released only at the end), so slow clients or slow serialisation use up your connection pool; lazy loading in the view hides N+1 queries, each running in autocommit-like mode outside your service's transaction boundary; and data access leaks into the web layer. Most teams I trust turn it off, then fetch exactly what the use case needs in the service (fetch join, @EntityGraph, or a DTO projection) and return DTOs. See the Hibernate and JPA page for fetching strategy.

How do you handle a transaction that spans a database and a message broker, or two services? Senior

What the interviewer is testing: whether you reach for 2PC blindly or choose a practical pattern.

A Spring @Transactional covers one resource manager, usually one database. Two resources need either a distributed (XA, two-phase commit) transaction through a JTA manager, which is slow, hard to operate, and unsupported by many modern brokers and cloud databases, or an eventual-consistency pattern. I choose by case. Database plus message broker: transactional outbox as above. Several services: a saga, a sequence of local transactions, each followed by an event, with a compensating action for each step if a later step fails. Make every consumer idempotent (safe to process the same message twice), because delivery is at least once. If you only need "best effort", chained transaction managers are possible but give no real atomicity. State this trade-off clearly; interviewers want to hear "I avoid XA and design for idempotency".

What goes wrong with long transactions, and how do you spot them? Senior

What the interviewer is testing: production thinking about transaction size.

A long transaction holds a pooled connection and probably row locks. Symptoms: the connection pool runs out (threads wait for getConnection, then time out with "Connection is not available"), other requests block on locked rows or deadlock, the database keeps old row versions and bloats, and replicas lag. Typical causes: a remote HTTP call or file operation inside the transaction, processing a million rows in one transaction, a missing index causing a slow update, or OSIV plus slow clients. Detect it with pool metrics (active versus pending connections), the database's view of long-running transactions (pg_stat_activity in PostgreSQL, information_schema.innodb_trx in MySQL), and slow query logs. Remedies: shrink the scope, move remote calls outside, process in batches with a commit per chunk, set @Transactional(timeout = n) as a safety net, and set sensible pool timeouts. Also keep the pool size modest; a bigger pool usually shifts the pain to the database.

6. Spring MVC

Walk me through what happens to an HTTP request in Spring MVC. Intermediate

What the interviewer is testing: the single most-asked MVC question. Name the components in order.

The servlet container (Tomcat) receives the request and runs it through the servlet filters. The request reaches the DispatcherServlet, the front controller. It asks the HandlerMapping (mainly RequestMappingHandlerMapping) which handler method matches the URL, HTTP method, headers and content type; the result is a HandlerExecutionChain: the handler plus the matching interceptors. It then finds a HandlerAdapter (RequestMappingHandlerAdapter) that knows how to call that kind of handler. The interceptors' preHandle methods run. The adapter uses argument resolvers to build the method arguments (path variables, @RequestBody via an HttpMessageConverter, validation, Principal), invokes your controller method, and uses return value handlers to process the result. For a @RestController, the return value is written to the response by a message converter (usually Jackson to JSON). For a view-based controller, a ViewResolver picks a template. Then postHandle and afterCompletion of the interceptors run, and the response travels back out through the filters. If any step throws, HandlerExceptionResolvers (including @ExceptionHandler methods and @ControllerAdvice) turn the exception into a response.

Likely follow-ups
  • What thread runs it? One container thread per request (thread-per-request), unless you return an async type.
  • Is DispatcherServlet a singleton? Yes, one servlet instance handles all requests concurrently.
What is the difference between @Controller and @RestController? Basic

What the interviewer is testing: basics, plus the meaning of @ResponseBody.

@Controller is for classic server-side rendered pages. A handler method returns a view name (a string such as "orders/list"), and a ViewResolver finds the template (Thymeleaf, JSP) and renders it with the model data. @RestController is @Controller plus @ResponseBody on every method. That tells Spring not to look for a view: the returned object is serialised by an HttpMessageConverter (JSON by Jackson) straight into the response body. Use ResponseEntity<T> as the return type when you need to control the status code and headers (201 Created with a Location header, 304, 404). For a plain object, the default status is 200.

@RestController
@RequestMapping("/api/orders")
class OrderController {
    @GetMapping("/{id}")
    OrderDto get(@PathVariable long id) {...}

    @PostMapping
    ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrder req) {
        var dto = service.create(req);
        return ResponseEntity.created(URI.create("/api/orders/" + dto.id())).body(dto);
    }
}
@RequestParam, @PathVariable, @RequestBody, @ModelAttribute, @RequestHeader: what is each for? Basic

What the interviewer is testing: daily MVC fluency.

@PathVariable reads a part of the URL path (/orders/{id}). @RequestParam reads a query string or form field (?page=2); it is required by default, and you can give defaultValue or required=false. @RequestBody reads the whole request body and converts it, usually from JSON, to an object with a message converter. @ModelAttribute binds form fields or query parameters onto an object by property name (data binding); it is the default for a complex type with no annotation. @RequestHeader and @CookieValue read headers and cookies. Also available without annotation: HttpServletRequest, Principal, Locale, Pageable. Conversion of strings to types such as LocalDate or enums is done by the ConversionService and @DateTimeFormat. A conversion failure becomes a 400 response.

How does request mapping choose a handler? What are consumes, produces and params? Intermediate

What the interviewer is testing: precise routing rules and the 404, 405, 406 and 415 codes.

@RequestMapping (and shortcuts @GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping) match on path, HTTP method, and optionally consumes (the request Content-Type), produces (what the client may Accept), params and headers. If several match, the most specific one wins. Misses give useful status codes: no path match gives 404; path matches but method does not gives 405 Method Not Allowed; the request body type is not accepted by consumes gives 415 Unsupported Media Type; the client's Accept header cannot be satisfied gives 406 Not Acceptable. Two handlers that map to exactly the same request cause Ambiguous mapping at startup. Since Spring 6 (and Boot 3) a trailing slash no longer matches by default (/orders/ is not /orders), and Spring 5.3 already switched the default path matcher to PathPatternParser.

How does validation work in Spring MVC with Bean Validation? Intermediate

What the interviewer is testing: validate at the boundary, and handle the failure in one place.

Bean Validation (Jakarta Validation, with Hibernate Validator as the implementation) lets you put constraints on fields: @NotNull, @NotBlank, @Size, @Email, @Min, @Pattern. In a controller, add @Valid (or Spring's @Validated) on the @RequestBody parameter. Spring runs the validator after binding and, if there are violations, throws MethodArgumentNotValidException (for a body), which is by default a 400. For simple @RequestParam and @PathVariable constraints, put @Validated on the class and the constraints on the parameters; you get a ConstraintViolationException in Spring 5 and Boot 2, and from Spring 6.1 a HandlerMethodValidationException. @Valid is the standard annotation and cascades into nested objects; @Validated is Spring's, adds validation groups and enables method-level validation on any bean. In Boot you must add spring-boot-starter-validation, as it is no longer part of the web starter since Boot 2.3. Validation of input formats belongs on the DTO; rules that need the database (is this email unique?) belong in the service, protected by a database unique constraint.

record CreateUser(@NotBlank String name, @Email String email, @Min(18) int age) {}

@PostMapping("/users")
ResponseEntity<?> create(@Valid @RequestBody CreateUser req) {...}
Likely follow-ups
  • Why does validation of a nested list not run? Add @Valid on the nested field to cascade.
  • Do the javax and jakarta packages matter? Yes: Spring 6 and Boot 3 use jakarta.validation.*.
How do you handle exceptions globally in Spring MVC? Intermediate

What the interviewer is testing: a clean error contract, not stack traces to clients.

Define one class annotated @RestControllerAdvice (or @ControllerAdvice) with @ExceptionHandler methods. Each method names the exception types it handles and returns the response, typically with a status and an error body. The most specific exception type wins. A handler inside a controller overrides the global ones for that controller only. For a consistent error format, use ProblemDetail (RFC 7807, built into Spring 6; spring.mvc.problemdetails.enabled in Boot 3) or extend ResponseEntityExceptionHandler, which already maps the standard MVC exceptions (400, 404, 405, 415 and more). Map your domain exceptions to proper HTTP codes: not found to 404, rule violation to 409 or 422, and everything unexpected to a generic 500 that logs the details but returns only a correlation id. You can also annotate an exception with @ResponseStatus for a quick mapping. Important limit: @ControllerAdvice only sees exceptions thrown from inside the DispatcherServlet (controllers, interceptors). Exceptions thrown in a servlet filter, including most Spring Security failures, never reach it.

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFound.class)
    ProblemDetail notFound(OrderNotFound e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
}
What is the difference between a servlet Filter, a HandlerInterceptor and AOP? Intermediate

What the interviewer is testing: choosing the right layer, and understanding order.

A servlet Filter belongs to the servlet container, runs before the DispatcherServlet, and sees the raw request and response. It knows nothing about Spring MVC handlers. Use it for cross-cutting web concerns that apply to everything: authentication (Spring Security is a filter chain), CORS, compression, request logging, correlation ids, wrapping the body. A HandlerInterceptor belongs to Spring MVC, runs inside the DispatcherServlet, and knows which handler method is about to run (you can read its annotations). It has three callbacks: preHandle (can stop the chain by returning false), postHandle (after the handler, before rendering; not called on exceptions) and afterCompletion (always, for clean-up). Use it for per-handler logic such as locale, rate limiting by annotation, or timing. AOP works on bean method calls at any layer, not just web, and sees Java arguments and results. Exceptions from filters are not handled by @ControllerAdvice, but those from interceptors are. Rule of thumb: raw HTTP concern means filter; needs the handler means interceptor; needs a service method means AOP.

Likely follow-ups
  • How do you set filter order? @Order on a filter bean, or FilterRegistrationBean.setOrder. Lower runs first.
  • Why extend OncePerRequestFilter? It guarantees one run per request even with forwards and error dispatches.
What are HandlerMethodArgumentResolver and HttpMessageConverter? When would you write your own? Senior

What the interviewer is testing: knowing the machinery behind controller method signatures.

A HandlerMethodArgumentResolver turns the HTTP request into one controller method argument. Spring has resolvers for each annotation and type; the first one that supportsParameter wins. You write your own to inject something domain-specific without repeated code: for example a CurrentTenant parameter read from a header, or the logged-in user object. An HttpMessageConverter converts between the body bytes and Java objects for @RequestBody and @ResponseBody: Jackson for JSON, a String converter, byte array, form data, and optionally XML or Protobuf. Register extra ones by WebMvcConfigurer.extendMessageConverters. The converter chosen depends on the content type and the Java type. Customise Jackson (date format, unknown properties) through the ObjectMapper bean, not by creating a second one inside a class. Other extension points: Converter and Formatter for simple types, HandlerInterceptor, and WebMvcConfigurer to hook everything in one class.

How does content negotiation work in Spring MVC? Intermediate

What the interviewer is testing: how one endpoint can return JSON or XML and what the status codes mean.

The client says what it wants in the Accept header (application/json, application/xml). Spring compares it with the produces types of the matching handler and with the message converters available for the return type, and picks the best match. If none fits, it returns 406. For the request side, the Content-Type header is matched against consumes and the converters that can read that type; no match gives 415. Older strategies such as a file extension (/orders.json) or a ?format=json parameter are off by default since Spring 5.3 for security and simplicity. XML needs an extra library on the classpath (Jackson XML), otherwise the XML converter is not registered. In an API, I usually support JSON only and declare it with produces = MediaType.APPLICATION_JSON_VALUE so the contract is explicit.

How do asynchronous requests work in Spring MVC (Callable, DeferredResult, CompletableFuture)? Senior

What the interviewer is testing: understanding of servlet threads and when async really helps.

In the normal model, one container thread is held for the full request. If the work is a slow call to another system, that thread just waits. When a controller returns Callable<T>, DeferredResult<T>, CompletableFuture<T>, SseEmitter or StreamingResponseBody, Spring starts servlet asynchronous processing: it releases the container thread and keeps the response open. Callable runs the work on a thread from Spring's task executor. DeferredResult lets any other thread (for example a message listener) complete the result later. When the value arrives, the request is dispatched back to the container to write the response. Async helps when many requests wait on slow I/O and you want to limit container threads, but it still blocks some thread unless the work is truly non-blocking, so it is not the same as reactive. Remember context: the security context and request attributes are carried by Spring's async support in these cases, but arbitrary executors you create yourself do not carry them. With Java 21 virtual threads (Spring 6.1 with Boot 3.2, spring.threads.virtual.enabled=true), the simple blocking style becomes cheap again, which lowers the need for these patterns.

How do you design a good REST endpoint in Spring MVC regarding status codes, idempotency and pagination? Intermediate

What the interviewer is testing: practical API design in the Spring idiom.

Use nouns in paths and the HTTP verb for the action. GET is safe and idempotent; PUT replaces a resource and is idempotent; DELETE is idempotent; POST creates and is not idempotent, so for payments accept an Idempotency-Key header and store the result. PATCH is a partial update. Return 201 with a Location header on create, 204 for success with no body, 400 for bad input, 401 or 403 for security, 404 for missing, 409 for conflict (including optimistic-lock failures), 422 for semantic validation errors. Never return a JPA entity directly: use DTOs (records are ideal), so schema changes do not leak and lazy proxies do not get serialised. For lists use pagination with Pageable (page, size, sort parameters) and cap the maximum page size. Version the API (path or header) before the first external consumer. More on design is in the microservices and REST page.

7. HTTP clients and reactive basics

RestTemplate, WebClient and RestClient: how do they differ, and which should I use? Intermediate

What the interviewer is testing: current knowledge of the HTTP client options and their blocking model.

RestTemplate is the classic synchronous, blocking client with a template-style API. It is in maintenance mode: it still works and is widely used, but it gets no new features. WebClient (Spring 5, from the WebFlux module) is a fluent, non-blocking client built on Reactor; it returns Mono and Flux, supports streaming and composes parallel calls well. You can also call .block() to use it from ordinary blocking code, but then you lose the benefit and must not do that on a reactive thread. RestClient arrived in Spring 6.1 (Boot 3.2): a synchronous, fluent client with the same style as WebClient, meant as the modern replacement for RestTemplate in blocking applications. My rule: a blocking Spring MVC application uses RestClient (or RestTemplate on older versions); a reactive application uses WebClient; use WebClient in MVC only if you need streaming or want to fan out several calls concurrently. For declarative clients, Spring 6 has @HttpExchange interfaces; Spring Cloud OpenFeign is the older alternative.

RestClient client = RestClient.builder().baseUrl("https://api.example.com").build();
Order o = client.get().uri("/orders/{id}", id).retrieve().body(Order.class);

Mono<Order> m = webClient.get().uri("/orders/{id}", id).retrieve().bodyToMono(Order.class);
Likely follow-ups
  • What timeouts does RestTemplate have by default? With the simple JDK request factory, effectively none (it can wait forever). Always configure connect and read timeouts.
  • How do you handle 4xx and 5xx? retrieve().onStatus(...) in WebClient and RestClient; an error handler in RestTemplate (which throws HttpClientErrorException by default).
What must you configure on an outgoing HTTP client for production? Senior

What the interviewer is testing: that remote calls are the usual cause of thread starvation and cascading failure.

Always set a connect timeout and a read (response) timeout; without them, a slow dependency holds your threads and the whole service stalls. Use a pooled HTTP client (Apache HttpClient, Jetty, or Reactor Netty for WebClient) and size the pool, with a limit per route. Add retries only for idempotent calls, with exponential backoff and jitter, and a retry budget, or you will multiply load on an already struggling dependency. Add a circuit breaker (Resilience4j) so you fail fast while the dependency is down, and a bulkhead so one slow dependency cannot use all your threads. Propagate a correlation id and the trace context. Never call remote services inside a database transaction. Log and measure latency per dependency. Define a fallback or a clear error. See the microservices page for the patterns.

What is reactive programming and Spring WebFlux? When would you pick it over Spring MVC? Intermediate

What the interviewer is testing: a balanced view, not hype.

In the MVC model, one thread handles one request from start to end and blocks while waiting for I/O. In the reactive model, a small number of event-loop threads handle many requests; each step that needs I/O returns immediately with a description of the future result, and the framework continues when the data arrives. Spring WebFlux is the reactive web stack, running on Netty (or Servlet 3.1 containers), using Project Reactor: Mono<T> is a stream of zero or one item, Flux<T> a stream of zero to many. Nothing happens until someone subscribes. Backpressure lets a slow consumer tell a fast producer how many items it can take. Pick WebFlux when you have very high concurrency with mostly I/O waiting, streaming, or an end-to-end non-blocking stack (reactive drivers: R2DBC, reactive Mongo, Redis, WebClient). Do not pick it just for speed: a single request is not faster, debugging is harder, stack traces are less helpful, and one blocking call (JDBC, Thread.sleep) on an event-loop thread can freeze everything. With JDBC/JPA in the stack, MVC (optionally with virtual threads on Java 21) is the simpler choice.

What are the common mistakes when working with Mono and Flux? Senior

What the interviewer is testing: real experience with the model.

(1) Not subscribing: building a chain and discarding it does nothing, since streams are lazy. In WebFlux, return the Mono and the framework subscribes. (2) Blocking inside the chain: JDBC calls, block(), Thread.sleep, or big CPU work. If you must, wrap it with subscribeOn(Schedulers.boundedElastic()). Tools such as BlockHound find these. (3) Losing ThreadLocal context: security context, MDC logging ids and transactions do not follow a reactive chain across threads; use the Reactor Context (Spring Security and Micrometer have helpers), and use R2dbc reactive transactions, because @Transactional over JDBC does not work here. (4) Swallowing errors: forgetting onErrorResume or logging, so failures disappear. (5) Using flatMap for sequence: flatMap runs inner calls concurrently and does not preserve order; concatMap keeps order. (6) Unbounded collectList() on a huge stream, which defeats backpressure.

8. Data access: JdbcTemplate and Spring Data

What does JdbcTemplate give you over raw JDBC? Basic

What the interviewer is testing: the template pattern, and safe query habits.

Raw JDBC needs boilerplate: get a connection, create a statement, set parameters, loop over the result set, close everything in a finally block, and handle checked SQLException. JdbcTemplate does all the resource handling for you (acquire, release, always), converts checked SQL exceptions into Spring's unchecked DataAccessException hierarchy, and gives short methods: query with a RowMapper, queryForObject, update, batchUpdate. NamedParameterJdbcTemplate allows :name parameters, which are easier to read. Always pass values as parameters (? or :name) and never concatenate user input into the SQL string, which would allow SQL injection. It takes its connection from the transaction-bound one, so it joins @Transactional automatically. It is a good fit for reporting queries, bulk operations, and cases where an ORM is too heavy.

List<User> users = jdbc.query(
    "select id, name from users where status = :s",
    Map.of("s", "ACTIVE"),
    (rs, i) -> new User(rs.getLong("id"), rs.getString("name")));
What is DataAccessException and why does Spring translate exceptions? Intermediate

What the interviewer is testing: understanding of the portable, unchecked exception hierarchy.

Every persistence technology throws its own exceptions: SQLException with vendor codes in JDBC, PersistenceException in JPA, Hibernate specific ones. Spring translates them into one unchecked hierarchy under DataAccessException: for example DuplicateKeyException, DataIntegrityViolationException, EmptyResultDataAccessException, OptimisticLockingFailureException, CannotAcquireLockException, TransientDataAccessException (worth retrying). Translation happens in JdbcTemplate directly, and for other code, in a post-processor that wraps beans marked @Repository. The benefit: the service code can catch a meaningful type (for instance map DuplicateKeyException to a 409 conflict) without knowing the database or the ORM, and being unchecked, these exceptions also trigger transaction rollback by default.

How do Spring Data repositories work? Where does the implementation come from? Intermediate

What the interviewer is testing: the proxy-generated repository model, and query options.

You declare an interface that extends JpaRepository<Entity, Id> (or CrudRepository). At startup Spring Data scans for such interfaces and, for each, creates a proxy backed by SimpleJpaRepository, which holds the standard CRUD code. For your own methods, it builds queries from the method name (findByEmailAndStatus), or from @Query with JPQL or native SQL, or named queries, or Specification and Querydsl for dynamic filters. The proxy is also where @Repository exception translation and transactions come in: SimpleJpaRepository is read-only transactional at class level, with write methods marked as read-write, so a single save is atomic even without your own annotation. Paging and sorting come from Pageable parameters: return Page (with a count query), Slice (no count, cheaper) or List. Use projections (interfaces or records) to fetch only needed columns. The JPA side (entities, fetching, N+1) is covered on the Hibernate and JPA page.

interface UserRepo extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
    Page<User> findByStatus(Status s, Pageable p);
    @Query("select u from User u where u.lastLogin < :t")
    List<User> stale(@Param("t") Instant t);
}
Likely follow-ups
  • Does save() always insert? It calls persist for a new entity and merge for a detached one (decided by id or @Version), which can cost an extra select.
  • Why can a derived method name get silly? Long names are hard to read; switch to @Query.
What is the difference between Page, Slice and keyset pagination? Senior

What the interviewer is testing: performance awareness on large tables.

A Page carries the items plus the total count, so Spring runs a second count(*) query; that is expensive on big tables and rarely needed by infinite-scroll UIs. A Slice only knows whether there is a next slice (it fetches size+1 rows) and skips the count. Both use offset pagination (LIMIT 20 OFFSET 100000), where the database must walk and discard all the skipped rows, so deep pages get slower, and rows inserted between requests cause duplicates or gaps. Keyset (seek) pagination asks for rows after the last seen sort key (where id > :lastId order by id limit 20), which stays fast with an index and is stable; Spring Data supports it through ScrollPosition and Window in recent versions (3.1 and later). Always sort by a unique, indexed column, and cap the page size on the server.

How does a connection pool relate to Spring, and how do you size it? Intermediate

What the interviewer is testing: that you know pool exhaustion is a top production issue.

Spring does not pool connections itself; it uses a DataSource, typically HikariCP (the Boot default). A transaction takes one connection from the pool and gives it back at commit or rollback. When all connections are busy, new requests wait up to connectionTimeout (30 seconds by default in Hikari) and then fail with "Connection is not available, request timed out". A good starting point for size is small: the pool only needs enough connections to keep the database busy, usually about (cores x 2) + disks as a rough starting rule, or 10 to 20 in many services; a huge pool just moves the queue into the database. Pool exhaustion usually comes from long transactions, leaked connections (code that never returns one), REQUIRES_NEW nesting, or a slow query. Monitor active, idle and pending connections, and set leakDetectionThreshold in non-production to find leaks. Total connections across all your service instances must stay under the database limit.

How do you insert or update a million rows efficiently with Spring? Senior

What the interviewer is testing: batching and transaction chunking.

Avoid one giant transaction and avoid one statement per round trip. Process in chunks (for example 1,000 rows), committing per chunk with TransactionTemplate, so locks and memory stay small and a failure loses only one chunk. Use JdbcTemplate.batchUpdate (or JDBC batching with rewriteBatchedStatements=true on MySQL, reWriteBatchedInserts=true on PostgreSQL), which sends many rows in one network round trip. With JPA, enable hibernate.jdbc.batch_size and order_inserts, flush and clear the persistence context after each chunk, and note that IDENTITY id generation disables insert batching, so use a sequence. For file loads that are repeatable and restartable with skip and retry rules, use Spring Batch instead of hand-written loops. Make the job idempotent so a restart does not duplicate rows.

9. Events, @Async, @Scheduled and caching

How do Spring application events work? Are they asynchronous? Intermediate

What the interviewer is testing: the default synchronous behaviour that surprises people.

Publish with ApplicationEventPublisher.publishEvent(obj); any object can be an event (since Spring 4.2). Subscribe with @EventListener on a method whose parameter is the event type. By default, publication is synchronous: the listeners run one after another in the same thread, and inside the same transaction as the publisher. So a slow listener slows the publisher, and an exception in a listener propagates to the publisher and can roll back its transaction. For async, add @Async to the listener (with @EnableAsync), or configure an executor on the multicaster; then it runs in another thread, outside the transaction and security context. Use @TransactionalEventListener to run after commit. Events decouple modules inside one application (an order module announces OrderPlaced, a mail module listens). They are not a message queue: no persistence, no retry, nothing survives a crash. For reliability across restarts or services, use a broker and an outbox.

Likely follow-ups
  • Can a listener return an event? Yes, the returned object is published as a new event.
  • Ordering? @Order on listeners.
How does @Async work, and what are its pitfalls? Intermediate

What the interviewer is testing: the proxy, the executor and the lost context.

Add @EnableAsync, then annotate a public method of a Spring bean with @Async. A proxy intercepts the call and submits the method body to a TaskExecutor, and the caller continues at once. The return type should be void, Future or CompletableFuture<T>. The pitfalls are many. (1) Self-invocation and private methods are not async, as with all proxies. (2) The default executor: in plain Spring without a bean, SimpleAsyncTaskExecutor creates a new thread for each task, with no limit; Boot auto-configures a bounded ThreadPoolTaskExecutor, but you should define your own with named threads, queue size, a rejection policy and a graceful shutdown. An unbounded queue hides overload and can cause out-of-memory errors. (3) Exceptions in a void method are lost to the caller; register an AsyncUncaughtExceptionHandler. (4) Thread-bound context (transaction, security context, MDC, request attributes) is not propagated. (5) The caller's transaction does not include it. (6) The caller must not depend on completion order. Wrap your executor with Spring Security's DelegatingSecurityContextExecutor and a TaskDecorator to copy MDC.

@Bean TaskExecutor mailExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4); ex.setMaxPoolSize(8); ex.setQueueCapacity(200);
    ex.setThreadNamePrefix("mail-");
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    return ex;
}
@Async("mailExecutor") public CompletableFuture<Void> send(Mail m) {...}
How does @Scheduled work, and what goes wrong with it? Intermediate

What the interviewer is testing: single-thread default and multi-instance duplication.

Add @EnableScheduling and annotate a no-argument method with @Scheduled(fixedRate = ...) (start to start), fixedDelay (end of one run to start of the next), or cron. Spring's cron has six fields with seconds first (0 0 2 * * * is 02:00 every day), unlike the five-field Unix cron, and a zone attribute. By default, all scheduled tasks share a single thread (Boot's pool size is 1 unless you set spring.task.scheduling.pool.size), so one slow job delays every other job. Runs of the same task do not overlap in that setup, but they can when the pool is larger and you use fixedRate. Exceptions are logged and the schedule continues. The biggest production problem: with several instances of the service, every instance runs the job, so it runs several times. Solutions: a distributed lock such as ShedLock (database or Redis based), a leader election, running the job in a single dedicated instance, or a Kubernetes CronJob. Make jobs idempotent and time-bounded. Add logging and metrics so you notice when a job stops. For complex, restartable batch work use Spring Batch or Quartz.

How does the Spring cache abstraction work? Intermediate

What the interviewer is testing: annotation semantics, key design and the proxy limit.

Add @EnableCaching and a CacheManager (Boot picks one from the classpath: Caffeine, Redis, simple in-memory map). @Cacheable("users") on a method: before calling, the proxy looks up the key (by default built from all arguments); on a hit it returns the cached value and your method does not run; on a miss it runs, stores and returns. @CachePut always runs the method and updates the cache. @CacheEvict removes an entry (or allEntries = true). Useful attributes: key (a SpEL expression), condition and unless (for example unless = "#result == null"), and sync = true so only one thread loads a missing key (preventing a stampede, for a single JVM). Pitfalls: self-invocation bypasses the cache; keys and values must be correct and serialisable (Redis); cached mutable objects can be changed by callers; no time to live by default (set expiry in Caffeine or Redis config, or data goes stale forever); with several instances, an in-memory cache is per instance and becomes inconsistent after writes, so use Redis or accept staleness. More caching design is on the Redis and Caching page.

@Cacheable(cacheNames = "products", key = "#id", unless = "#result == null")
public Product find(long id) {...}

@CacheEvict(cacheNames = "products", key = "#p.id")
public void update(Product p) {...}
How do you add retries to a Spring service call? Intermediate

What the interviewer is testing: safe retry rules, and that it is proxy-based too.

Spring Retry offers @Retryable(retryFor = IOException.class, maxAttempts = 3, backoff = @Backoff(delay = 200, multiplier = 2)) with @Recover for a fallback and @EnableRetry to switch it on; Spring Framework 7 also includes core retry support. Resilience4j offers @Retry, @CircuitBreaker and @Bulkhead. Both are proxy-based, so self-invocation does not work, and the order of advices matters when combined with @Transactional: a retry placed inside a transaction retries within the same, probably failed, transaction, so the retry advice should be outside the transactional one. Retry only transient failures (timeouts, connection resets, 503) and only idempotent operations, with backoff and jitter. Never retry a validation error.

What is SpEL, and where is it used? Intermediate

What the interviewer is testing: the difference between ${} and #{}.

The Spring Expression Language is a small expression language evaluated at runtime. ${app.name} is a property placeholder: it is replaced by the property value, nothing more. #{...} is SpEL: it can call methods, do maths, read beans (#{@myBean.limit}), and use conditions (#{systemProperties['os.name']}). You can combine them: @Value("#{${app.limit} * 2}"). It is used in @Value, @Cacheable keys and conditions, @PreAuthorize rules, @ConditionalOnExpression, and @Scheduled placeholders. Keep expressions short, since they are strings that are not checked at compile time; never evaluate SpEL built from user input, as it can execute arbitrary methods.

10. Spring Security essentials

How does Spring Security work? Explain the filter chain. Intermediate

What the interviewer is testing: that Security is a set of servlet filters, in a known order, before MVC.

Spring Security is built on servlet filters. A single filter registered with the container, DelegatingFilterProxy (in Boot, FilterChainProxy is registered), forwards each request to a SecurityFilterChain: an ordered list of filters chosen by matching the request path. You can define several chains, for example one for /api/** (stateless, JWT) and one for the web UI (session, form login). The important filters in order are roughly: the one that loads and saves the SecurityContext, header writers, CORS, CSRF, logout, an authentication filter (username and password, or bearer token, or basic), request cache, anonymous authentication, session management, the ExceptionTranslationFilter, and last the AuthorizationFilter which decides if the now-authenticated user may access the URL. The ExceptionTranslationFilter turns AuthenticationException into a call to the AuthenticationEntryPoint (401 or redirect to login) and AccessDeniedException into the AccessDeniedHandler (403). The result of authentication is an Authentication object stored in the SecurityContext, held in a SecurityContextHolder which is ThreadLocal based. Because all this happens before the DispatcherServlet, @ControllerAdvice never sees these errors.

What is the difference between authentication and authorization, and between 401 and 403? Basic

What the interviewer is testing: a basic distinction that is often mixed up in real APIs.

Authentication answers "who are you?": checking a password, a token or a certificate. Authorization answers "what are you allowed to do?": checking roles, permissions or ownership. HTTP status codes follow this. 401 Unauthorized really means "unauthenticated": no valid credentials were given (missing or expired token), and the client may retry with proper ones. 403 Forbidden means "authenticated, but not allowed": the server knows who you are and still refuses; sending credentials again will not help. A typical bug is returning 403 for a missing token (in older Spring Security setups without an entry point, Http403ForbiddenEntryPoint was used) or 401 for a role problem. Some teams return 404 instead of 403 for resources a user should not even know exist. In Spring Security: AuthenticationEntryPoint produces 401, AccessDeniedHandler produces 403.

Likely follow-ups
  • How do I customise the JSON body of a 401? Implement AuthenticationEntryPoint and register it with exceptionHandling.
  • Where does an anonymous user denied access go? To the entry point (401 or login redirect), since anonymous users are treated as not authenticated.
How do you configure Spring Security in Security 5.7 and in Security 6? Intermediate

What the interviewer is testing: knowing the version change, since much code on the web is old.

Before 5.7, you extended WebSecurityConfigurerAdapter and overrode configure(HttpSecurity). From 5.7 that class is deprecated, and 6.0 removed it. Now you declare a SecurityFilterChain bean. Also in Security 6: authorizeRequests() is replaced by authorizeHttpRequests(); antMatchers, mvcMatchers and regexMatchers are replaced by requestMatchers; @EnableGlobalMethodSecurity is replaced by @EnableMethodSecurity; and the lambda DSL (http.csrf(c -> c.disable())) is the style to use, replacing the old .and() chaining (the chained style is removed in Security 7). Security 6 also requires you to save the SecurityContext explicitly in custom login code, and loads the CSRF token lazily. Security 6 needs Spring Framework 6, Java 17 and jakarta. Because many tutorials show the old adapter, check the version first.

@Configuration @EnableMethodSecurity
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http.csrf(c -> c.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a
                .requestMatchers("/public/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
        return http.build();
    }
}
Common mistakes: order of matchers: the first match wins, so put specific rules first and anyRequest() last. Another: hasRole("ADMIN") checks authority ROLE_ADMIN; hasAuthority("ADMIN") checks exactly ADMIN.
What happens inside Spring Security when a user logs in with username and password? Senior

What the interviewer is testing: the roles of AuthenticationManager, provider, UserDetailsService and PasswordEncoder.

The UsernamePasswordAuthenticationFilter (or your own controller) builds an unauthenticated UsernamePasswordAuthenticationToken and passes it to the AuthenticationManager (normally a ProviderManager). The manager tries each AuthenticationProvider that supports that token type. The DaoAuthenticationProvider calls UserDetailsService.loadUserByUsername to load the stored user with the password hash and authorities, then uses the PasswordEncoder to compare the submitted password with the stored hash, then checks account flags (locked, disabled, expired). On success it returns a fully populated Authentication with authorities. The filter stores that in the SecurityContext; for session-based login the context is saved in the HTTP session, so the next requests are recognised by the session cookie. On failure an AuthenticationException leads to the failure handler or entry point. To add multi-factor or a custom user store, implement your own UserDetailsService or AuthenticationProvider.

How should you store passwords, and what is PasswordEncoder? Intermediate

What the interviewer is testing: modern password storage, with slow salted hashes.

Never store plain text, and never use a fast hash such as MD5 or SHA-256 alone, since attackers can try billions per second. Use a slow, adaptive hash with a built-in random salt: BCrypt (the common default, with a cost factor, 10 by default), Argon2 (preferred by many for new systems, memory hard), SCrypt or PBKDF2 (for FIPS needs). Spring Security's PasswordEncoder interface has encode and matches. PasswordEncoderFactories.createDelegatingPasswordEncoder() stores hashes with a prefix like {bcrypt}, so you can upgrade the algorithm over time and old hashes still verify; upgradeEncoding lets you re-hash on next login. Tune the cost so one check takes roughly 100 to 300 ms on your hardware. Salt makes identical passwords produce different hashes. Do not log passwords, and limit login attempts to slow guessing.

How do you secure a REST API with JWT, using Spring as an OAuth2 resource server? Senior

What the interviewer is testing: the split between authorization server and resource server, and how validation works.

A JWT (JSON Web Token) is three base64 parts: header, claims (payload) and a signature. The client logs in with an authorization server (Keycloak, Okta, Azure AD, Spring Authorization Server) and gets an access token. It sends Authorization: Bearer <token> on each API call. Your API is the resource server: it does not log anyone in. With oauth2ResourceServer(o -> o.jwt(...)), the BearerTokenAuthenticationFilter extracts the token and a JwtDecoder validates it: signature (using the issuer's public keys fetched from its JWK set URI, found from issuer-uri config), expiry, issuer, and optionally audience. A JwtAuthenticationConverter turns the claims into authorities: by default the scope claim becomes SCOPE_xxx authorities; map roles from a custom claim yourself. The API is stateless: no session, so no CSRF issue. Because the token is self-contained, the API needs no call to the auth server per request, which scales, but you cannot revoke a token before expiry, so keep access tokens short (minutes) and use refresh tokens at the client. Use opaque tokens with introspection if instant revocation matters.

Likely follow-ups
  • Where should a SPA store tokens? Preferably in memory or in an HttpOnly cookie via a backend-for-frontend; storing in localStorage exposes them to script injection.
  • Which OAuth2 flow for a browser app? Authorization Code with PKCE. The implicit and password grants are discouraged.
Which OAuth2 grant types matter, and what are the roles? Intermediate

What the interviewer is testing: basic OAuth2 fluency.

Roles: the resource owner (the user), the client (the app acting on their behalf), the authorization server (issues tokens) and the resource server (API). Authorization Code with PKCE is the standard for web, mobile and single page apps: the user logs in at the auth server, the client gets a one-time code, and swaps it for tokens; PKCE protects the code from interception. Client Credentials is for service to service calls with no user: the client authenticates with its own id and secret. Refresh token gets a new access token without asking the user again. The implicit and resource owner password grants are deprecated. OpenID Connect (OIDC) adds an ID token on top of OAuth2 to say who the user is (login), while OAuth2 alone is about delegated access. In Spring: oauth2Login() for a client doing login, oauth2Client for calling other APIs with a token, oauth2ResourceServer for your API.

What is method security, and how does @PreAuthorize work? Intermediate

What the interviewer is testing: fine-grained rules, and the fact that it is a proxy too.

URL rules (requestMatchers) protect paths. Method security protects service methods with rules that can use arguments and results. Enable it with @EnableMethodSecurity (Security 5.6 and later; it turns on @PreAuthorize and @PostAuthorize by default and replaces @EnableGlobalMethodSecurity). @PreAuthorize("hasRole('ADMIN')") is checked before the call. @PreAuthorize("#userId == authentication.principal.id") compares an argument to the current user, which is how you enforce ownership. @PostAuthorize("returnObject.owner == authentication.name") checks after the call, and @PostFilter or @PreFilter filter collections. Since it is implemented by an AOP proxy, it has all the proxy limits: no effect on self-invocation or private methods. It is the right place for business-level authorisation, since a URL rule alone cannot tell whose order it is. Always combine both: URL rules as the broad gate and method rules for object-level checks. Missing ownership checks are the most common real vulnerability in APIs (broken object-level authorization, or IDOR).

What is CSRF, and when do you turn it off? Intermediate

What the interviewer is testing: that you understand why it exists, instead of disabling it blindly.

Cross-Site Request Forgery tricks a logged-in user's browser into sending a request to your site from another site. It works because browsers attach cookies automatically, including the session cookie, so the request looks authenticated. Spring Security's defence is a CSRF token: a secret value your page includes in each state-changing request (POST, PUT, DELETE) as a header or hidden field, which a malicious site cannot read. Spring enables this by default. You can safely disable CSRF for a stateless API that authenticates with a bearer token in the Authorization header, since the browser does not add that header automatically, so there is nothing to forge. If you use cookies for authentication (a session cookie, or a JWT stored in a cookie), keep CSRF protection on, or use SameSite=Lax/Strict cookies plus a token. For a single page app with cookies, CookieCsrfTokenRepository.withHttpOnlyFalse() lets the script read the token. Saying "I disabled CSRF because POST returned 403" is a red flag in an interview; the cause is usually a missing token.

What is CORS, and why does a preflight request fail with 401 or 403? Intermediate

What the interviewer is testing: the same-origin policy, and the interplay of CORS with Security.

Browsers block a page from reading responses from a different origin (scheme, host, port) unless the server allows it with CORS headers such as Access-Control-Allow-Origin. For "non-simple" requests (JSON Content-Type, custom headers like Authorization, or methods like PUT or DELETE) the browser first sends an OPTIONS preflight without credentials, asks whether the real request is allowed, and only then sends it. CORS is a browser protection; curl and server-to-server calls ignore it. In Spring MVC you can use @CrossOrigin or a WebMvcConfigurer. But with Spring Security, the preflight reaches the security filters first, and it has no token, so it gets 401 or 403 before MVC adds the CORS headers. The fix is to enable CORS in the security chain (http.cors(Customizer.withDefaults()) with a CorsConfigurationSource bean) so the CORS filter answers the preflight early. Rules: do not use allowedOrigins("*") together with allowCredentials(true) (the browser rejects it); list exact origins.

How does Spring Security know the current user, and what happens in other threads? Senior

What the interviewer is testing: the ThreadLocal model and its consequences with async code.

The authenticated Authentication object is kept in a SecurityContext, which is stored by SecurityContextHolder in a ThreadLocal by default. In a controller you can read it through a Principal or @AuthenticationPrincipal parameter, or SecurityContextHolder.getContext().getAuthentication(). The filter chain clears it at the end of the request, so a pooled thread does not leak the previous user. In a new thread (@Async, CompletableFuture, an executor, a parallel stream) the holder is empty, so the code sees no user (often "anonymous", or a null pointer), and method security fails with an authentication error. Fixes: wrap the executor with DelegatingSecurityContextExecutorService (or DelegatingSecurityContextAsyncTaskExecutor) so the context is copied into the task; or set the strategy MODE_INHERITABLETHREADLOCAL (only helps for threads created by the request thread, not for pooled ones); or pass the user id as an argument. Spring MVC's own Callable and DeferredResult support propagates it. In reactive code the context travels in the Reactor context instead.

Session-based security versus stateless token security: trade-offs? Intermediate

What the interviewer is testing: architecture choices, not a slogan.

With sessions, the server stores the login in memory or a shared store, and the browser keeps a session id cookie. Logout and revocation are instant; the server controls everything; CSRF protection is needed. With several instances you need sticky sessions or a shared store (Spring Session with Redis). With stateless tokens (JWT), the client holds the proof; any instance can verify it, so horizontal scaling is easy and no session store is needed; mobile and service clients fit well. The costs: a token cannot be revoked before it expires unless you keep a deny-list (which brings state back), tokens grow big with claims, and storing them safely in a browser is tricky. For a server-rendered website, sessions are usually simpler and safer. For a public API serving many clients, tokens are the norm. A hybrid is common: a backend-for-frontend keeps tokens server-side and gives the browser only an HttpOnly session cookie.

What common security mistakes do you look for in a Spring application? Senior

What the interviewer is testing: practical security habits.

(1) Missing object-level checks: an endpoint that takes an id and returns the record without checking that the user owns it. (2) Mass assignment: binding request JSON directly onto an entity so a user can set role or admin; use DTOs. (3) Exposing entities or internal exceptions and stack traces. (4) SQL built by string concatenation instead of parameters. (5) Turning off CSRF while using cookie authentication. (6) Wildcard CORS with credentials. (7) Secrets in the repository or logs, and logging personal data or tokens. (8) Weak password hashing. (9) Actuator endpoints exposed without protection (details on the Spring Boot page). (10) Unvalidated redirects, and deserialisation of untrusted data. (11) Outdated dependencies with known CVEs (Spring4Shell in 2022 is the well-known Framework example), so keep Spring patched and scan dependencies. (12) Relying on client side checks. Security should be deny by default: anyRequest().authenticated() as the last rule.

11. Testing Spring applications

@SpringBootTest versus test slices versus plain unit tests: how do you choose? Intermediate

What the interviewer is testing: a sensible, fast test strategy.

A plain unit test (JUnit and Mockito, no Spring) tests business logic in a class. It is the fastest, so most tests should be this. A slice test starts only a part of the context: @WebMvcTest loads controllers, JSON conversion, validation, security filters and MockMvc, with services replaced by mocks; @DataJpaTest loads only JPA, repositories and an embedded or container database, rolling back each test; there are similar slices for JSON and REST clients. Slices are quick and focused: they check mappings, status codes, queries and serialisation. @SpringBootTest starts the whole application context (optionally with a real random port) to check that wiring, configuration and layers work together; it is the slowest, so write a few. Spring caches contexts between test classes that have the same configuration, so avoid unnecessary variations (different @MockBean sets, @DirtiesContext), each of which forces a new context. For databases, prefer a real engine in a container (Testcontainers) over H2 when you use database-specific features. Details of Boot's test annotations are on the Spring Boot page.

What is the difference between Mockito's @Mock and Spring's @MockBean or @MockitoBean? Intermediate

What the interviewer is testing: where a mock lives.

@Mock (Mockito) creates a mock object that only exists inside the test class; you pass it into your class by constructor, or with @InjectMocks. No Spring context is involved. @MockBean (Spring Boot test) creates a mock and puts it into the Spring context, replacing any existing bean of that type, so that other beans (for example the controller under @WebMvcTest) receive the mock. It forces the context to be re-created for each distinct combination, which slows down large suites. In Spring Framework 6.2 and Boot 3.4, @MockBean and @SpyBean are deprecated in favour of @MockitoBean and @MockitoSpyBean from the core test framework. Use @Mock when you can build the object yourself; use the Spring variants when a bean in the context must be swapped. Prefer faking at your own boundaries (a repository or gateway interface) and not mocking everything: a test with ten mocks only proves the mocks.

How do you test a controller? Intermediate

What the interviewer is testing: test through the HTTP contract without a real server.

Use @WebMvcTest(OrderController.class), which loads the MVC infrastructure and your controller, and inject MockMvc. Mock the service with a mock bean. Then perform a request and assert the status, headers and JSON body (jsonPath). This checks mapping, binding, validation, error handling advice and serialisation without starting Tomcat. If Spring Security is on the classpath, the slice includes the filter chain, so add @WithMockUser (or a JWT post-processor like jwt()) and, for POST, csrf(). An unexpected 401, 403 or 404 in these tests is almost always a security or configuration issue, which is useful feedback. For a true end-to-end HTTP check including the real server, use @SpringBootTest(webEnvironment = RANDOM_PORT) with TestRestTemplate or WebTestClient.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean OrderService service;

    @Test @WithMockUser
    void notFound() throws Exception {
        given(service.get(9L)).willThrow(new OrderNotFound(9L));
        mvc.perform(get("/api/orders/9")).andExpect(status().isNotFound());
    }
}
Tests marked @Transactional roll back by default. Is that good, and what does it hide? Senior

What the interviewer is testing: awareness that test transactions differ from production.

Spring's test framework wraps each @Transactional test method in a transaction and rolls it back at the end, so tests do not leave data behind and need no clean-up. That is convenient for repository tests. What it hides: the data never really commits, so commit-time problems do not appear (deferred constraint checks, a flush that fails only at commit, @TransactionalEventListener(AFTER_COMMIT) listeners that never fire); the persistence context stays open for the whole test, so lazy loading works even when production code would throw LazyInitializationException; and any code on another thread (@Async, a server on a random port handling the request) does not see the uncommitted data. For such tests, do not use @Transactional on the test; commit real data and clean up in @AfterEach or use a fresh container per class. Also call entityManager.flush() and clear() in a repository test to force the SQL to run and reload from the database.

Why use Testcontainers instead of H2 for repository tests? Intermediate

What the interviewer is testing: test fidelity.

H2 and HSQLDB are fast and need no set-up, but they are not your production database. SQL dialect, locking behaviour, JSON columns, window functions, sequences, collation and index rules differ. A query that works in H2 can fail in PostgreSQL, and the reverse. Testcontainers starts a real PostgreSQL, MySQL, Kafka or Redis in a Docker container for the test run, so the test uses the same engine and the same migration scripts (Flyway or Liquibase) as production. The costs are Docker availability in CI and a few seconds of start-up, which you reduce by sharing one container across test classes and using the container reuse features. A good split: plain unit tests for logic, and Testcontainers for anything that touches SQL or messaging. Boot 3.1 and later makes this simpler with @ServiceConnection.

Why is our Spring test suite so slow, and how do you speed it up? Senior

What the interviewer is testing: practical test engineering.

The usual cause is too many full application contexts. Spring caches a context under a key made of the configuration, active profiles, property overrides and mock bean definitions. Every new combination, and every @DirtiesContext, makes a new context with a new set of beans, database connections, maybe an embedded server. Fixes: keep a base test class with one standard configuration and reuse it; avoid per-class @MockBean sets or move them into one shared config; replace @SpringBootTest with slices where possible; use @DirtiesContext only when the test truly corrupts the context; turn on lazy initialisation in tests; start containers once per JVM; run tests in parallel at class level only if they do not share data. Measure first: the log lines "Started ... in N seconds" show how many contexts were built.

12. Real-life scenarios

Each scenario is answered the same way: situation, what you check first, the fix, and how to stop it happening again.

A payment fails and throws an exception, but the order row is still in the database. @Transactional "did not roll back". What do you do? Intermediate

What the interviewer is testing: a systematic check of the usual causes.

Situation: a service method annotated @Transactional saves an order, calls the payment code, which throws, yet the order is committed. Check in this order. (1) Is the exception checked? The default rolls back only for RuntimeException and Error. (2) Is the exception caught and swallowed inside, so the proxy sees a normal return? (3) Is the method called from another method of the same class (self-invocation), or is it private, so there is no proxy? (4) Is the bean really a Spring bean, or created with new? (5) Is the import right: org.springframework.transaction.annotation.Transactional or jakarta.transaction.Transactional (which has different rollback rules: it does not roll back on checked exceptions either, but uses rollbackOn)? (6) Does the work run on a different thread (async)? (7) Is there a transaction manager for this data source, and does the storage engine support transactions (MyISAM does not)? (8) Is @EnableTransactionManagement or Boot auto-configuration active? Confirm by setting logging.level.org.springframework.transaction.interceptor=TRACE and org.springframework.orm.jpa=DEBUG: you will see "Getting transaction for" and "Completing transaction" lines, or not. Fix the actual cause (rollbackFor, rethrow, move the method to another bean). Prevent: an integration test that forces the failure and asserts that the row is absent.

The app fails to start with "No qualifying bean of type X" or "required a bean of type X that could not be found". How do you debug it? Basic

What the interviewer is testing: the missing bean checklist.

Situation: startup stops with UnsatisfiedDependencyException or NoSuchBeanDefinitionException. Read the message: it names the class that needs the bean, the injection point and the type. Check: is the class annotated with a stereotype, or is there a @Bean method for it? Is its package inside the component-scan root of the main class? Is it an interface with no implementation bean? Is a @Profile or @Conditional turning it off in this environment (a very common difference between local and server)? Is the dependency a library whose auto-configuration is not on the classpath? Was the class created by new? Is it the wrong generic type (List<String> vs List<Integer>)? Tools: run with --debug to print the Boot conditions report; use the /actuator/beans endpoint locally. Fix by adding the stereotype, widening the scan, or declaring a @Bean. Prevent: a context-loading smoke test in CI for each profile.

After adding a second implementation of an interface, startup fails with NoUniqueBeanDefinitionException. What now? Basic

What the interviewer is testing: disambiguation options and design sense.

Situation: expected single matching bean but found 2: stripePay, paypalPay. The container found two beans of the type and does not know which one the injection point wants. Options: mark the default one @Primary; name the exact one with @Qualifier("stripePay") at the injection point; or, if the code is meant to use both, inject List<PaymentGateway> or a Map<String,PaymentGateway> and pick one at runtime (the strategy pattern). Matching by parameter name works as a last resort but is fragile. If only one should exist per environment, use @Profile or @ConditionalOnProperty. Prevent: avoid relying on parameter-name matching; create a custom qualifier annotation; add a test that starts the context.

After upgrading to Boot 2.6 or 3, the app fails with "The dependencies of some of the beans in the application context form a cycle". What do you do? Senior

What the interviewer is testing: fixing the design and not only the symptom.

Situation: OrderService uses CustomerService, which uses OrderService. It used to work because field injection plus the early-reference cache hid it, and Boot 2.6 turned that off by default. First: read the cycle printed in the error (A to B to C to A). Fix options, best first: (1) Break the cycle by design: extract the shared part into a third class that both depend on; or make one side publish an event instead of calling the other; or move a method to where it belongs. (2) Replace one dependency with a narrower interface or a callback. (3) Use @Lazy on one constructor parameter, or inject an ObjectProvider; this is a quick patch. (4) The wrong fix is spring.main.allow-circular-references=true: it hides the problem and keeps risks such as the "raw version" proxy error. Prevent: constructor injection everywhere (cycles then fail early), and an architecture test (ArchUnit) that forbids package cycles.

The heap grows slowly in production until the service is killed for out of memory. You suspect Spring beans or ThreadLocals. What do you check? Senior

What the interviewer is testing: connecting scopes and thread pools to leaks.

Situation: old generation grows between full GCs; restart "fixes" it for a day. Capture: a heap dump (-XX:+HeapDumpOnOutOfMemoryError or jcmd GC.heap_dump) and open it in a tool such as Eclipse MAT, looking at the dominator tree and "path to GC roots". Spring-specific suspects: (1) ThreadLocal values never removed on container threads: a ThreadLocal set in a filter or interceptor (user context, MDC, a request cache) without remove() in a finally block keeps the object, and also the class loader on redeploy, alive as long as the pooled thread lives. (2) Prototype beans that hold resources (connections, listeners, executors): Spring creates them but never calls @PreDestroy, so they are never cleaned up, and if registered as a listener or scheduled task they are retained forever. (3) Singleton fields that accumulate: an unbounded HashMap used as a cache, a list of listeners, per-user maps. Replace with Caffeine with a size and time limit. (4) Unbounded @Async queues (LinkedBlockingQueue with no capacity). (5) Lots of @Scope("request") proxies is not usually a leak. (6) Hibernate second-level or query caches without limits. Fix the root holder, add try/finally clean-up, bound every cache and queue. Prevent: a heap-after-GC metric alert, and code review rule "every ThreadLocal.set has a remove in finally".

A client reports 403 where they expected 401 (or the other way round), and a browser shows a login page for an API call. How do you sort it out? Intermediate

What the interviewer is testing: the difference between the entry point and the denied handler.

Situation: an API call with no token returns a 302 redirect to /login or a 403; an expired token returns 403 instead of 401. Check: is the chain configured for form login (which redirects) while the API should be stateless? For an API chain, use httpBasic or oauth2ResourceServer (which sets a BearerTokenAuthenticationEntryPoint returning 401 with a WWW-Authenticate header), not formLogin. If you have a custom JWT filter and no entry point, anonymous users who get denied are sent to the default entry point, which in some setups (Http403ForbiddenEntryPoint) answers 403. Register one explicitly with http.exceptionHandling(e -> e.authenticationEntryPoint(...).accessDeniedHandler(...)). Meaning to hold: 401 = we do not know who you are; 403 = we know and you may not. Also check that a /error dispatch is permitted: when your app throws a 4xx error, the servlet container forwards to /error, and if that path requires authentication, the real status gets masked as 401 or 403. Prevent: MockMvc security tests for "no token", "bad token" and "wrong role".

Startup takes 90 seconds and Kubernetes keeps killing the pod. How do you find out why and speed it up? Senior

What the interviewer is testing: measuring first, then fixing the biggest contributor.

Situation: the readiness probe fails because the context is not up in time. Measure: turn on the startup tracker (new BufferingApplicationStartup(...) and the /actuator/startup endpoint), or log at debug level to see bean creation times. Look at what dominates: (1) classpath scanning of a very wide base package or scanning dependencies; restrict scanBasePackages. (2) Slow @PostConstruct or init code: remote calls, loading big caches, running migrations. Move to a background task or ApplicationReadyEvent. (3) JPA/Hibernate: ddl-auto=validate or update on a big schema, building metadata, many entities; initialise in parallel with spring.data.jpa.repositories.bootstrap-mode=deferred. (4) Many auto-configurations you do not need; exclude them. (5) Connection checks to slow dependencies at startup (health checks, eager clients). (6) Disk and CPU limits in the pod: a CPU limit of 0.5 cores slows class loading a lot. Options: spring.main.lazy-initialization=true (with the risk of late failures), class data sharing (CDS/AppCDS), Spring AOT and GraalVM native image, and a startup probe with a generous failure threshold so Kubernetes does not kill a slow starter. Prevent: track startup time in CI and fail the build when it doubles.

An @Async method fails with "An Authentication object was not found in the SecurityContext" or logs show user "anonymous". Why, and how do you fix it? Senior

What the interviewer is testing: ThreadLocal propagation.

Situation: the controller is secured and works, but a method it calls with @Async that uses @PreAuthorize or reads the current user fails or acts as anonymous. Cause: the security context lives in a ThreadLocal of the request thread; the async task runs on an executor thread where it is empty. The same happens to the MDC logging context and to request-scope beans, and the transaction. Fix: (1) Prefer to pass what you need explicitly: the user id or a small immutable object as a method argument, so the async code does not depend on thread context at all. (2) If it must have the full context, wrap the executor in DelegatingSecurityContextAsyncTaskExecutor (or define a TaskDecorator that copies the context and MDC and clears them after). (3) Avoid MODE_INHERITABLETHREADLOCAL with pools; it copies only at thread creation, so reused threads keep the first user's context, which is a data leak. Prevent: an integration test with @WithMockUser that calls the async path and checks the principal.

A controller returns an entity and the response fails with LazyInitializationException (or sends hundreds of SQL queries). What is going on? Intermediate

What the interviewer is testing: fetch boundaries and DTO discipline.

Situation: GET /orders/5 works in a test but in production throws could not initialize proxy - no Session, or works but runs one query per line item. Cause: the service method (and its transaction) ended, the persistence context closed, and the entity returned still has lazy associations. When Jackson walks the object and touches order.getItems(), either the session is closed (exception) or, with Open Session In View on, each access fires a separate query (N+1). Fix: do not return entities from controllers. Map to a DTO inside the transactional service method, after loading what is needed with one query: a fetch join, @EntityGraph, or a DTO projection. Do not "fix" it by switching associations to EAGER (that makes every query heavier) or by relying on OSIV. Check with SQL logging or Hibernate statistics for the number of queries per request. Prevent: a test that asserts the query count for key endpoints. See the Hibernate and JPA page.

A custom logging or tenant filter sees no authenticated user, or runs twice. How do you debug filter order problems? Senior

What the interviewer is testing: how container filters and the security chain interact.

Situation 1: your @Component filter reads SecurityContextHolder and finds nothing. In Boot the security chain is registered with order -100, so a plain @Component filter with a default order (lowest priority) runs after it and should see the user, but a filter with @Order(Ordered.HIGHEST_PRECEDENCE) runs before and sees nothing. Situation 2: the filter runs twice: you registered it as a bean (so Boot adds it to the container chain) and also in the security chain with addFilterBefore. Disable the automatic registration with a FilterRegistrationBean whose setEnabled(false), or do not make it a bean. Situation 3: a filter needing the user should be placed inside the security chain, after the authentication filter: http.addFilterAfter(f, BearerTokenAuthenticationFilter.class). Debug: turn on logging.level.org.springframework.security=DEBUG; Security prints the filter list for each chain at startup and at request time. Extend OncePerRequestFilter to avoid duplicate runs on forwards. Prevent: document the order, and test with MockMvc including security.

The production config is not being picked up: the app uses dev values in production, or application-prod.yml seems ignored. How do you find out why? Intermediate

What the interviewer is testing: property source order and profile activation.

Situation: a property still has the default value in prod. Check: (1) Is the profile actually active? Look at the startup log line "The following 1 profile is active" (or "No active profile set, falling back to default"). The variable name must be SPRING_PROFILES_ACTIVE (with underscores) or spring.profiles.active. (2) File name must be exactly application-prod.yml, in src/main/resources or the config path, and be inside the jar. A typo like application-production.yml will not match profile prod. (3) YAML indentation or a property key typo, or a duplicate key; keys are case sensitive in YAML but relaxed for env variables (APP_PAYMENT_URL). (4) A higher-priority source overrides it: an environment variable, a command line argument, or a config server value wins over a file. (5) @Value on a bean created without Spring. @Cacheable seems to do nothing: the method is called every time. What do you check? Intermediate

What the interviewer is testing: the same proxy discipline in another feature.

Situation: database load did not drop after adding @Cacheable. Check: (1) @EnableCaching present (Boot does not turn it on by itself) and a CacheManager exists. (2) The call comes from another bean, not from this. (3) The method is public and the class is a Spring bean. (4) The key: arguments with no proper equals and hashCode (a new object each call) always miss; use an explicit key = "#id". (5) unless or condition excludes the result; results of null may not be cached. (6) The cache name has no configuration and expiry is zero, or entries are evicted at once by size or TTL. A nightly @Scheduled job started sending every customer two emails after we scaled to two instances. Fix it. Senior

What the interviewer is testing: distributed scheduling.

Situation: both instances run the scheduler at 02:00. Immediate fix: introduce a lock so that only one instance does the work: ShedLock with @SchedulerLock(name = "nightlyMail", lockAtMostFor = "10m", lockAtLeastFor = "1m") backed by the existing database table or Redis. lockAtMostFor protects against a crashed holder; lockAtLeastFor protects against clock skew running it again right away. Better design: make the job idempotent: mark each customer row as "mail sent for date X" in the same transaction as selecting it (SELECT ... FOR UPDATE SKIP LOCKED or an update-then-select pattern), so even a duplicate run does no harm. For heavy or critical jobs, move scheduling out of the app: a Kubernetes CronJob or a workflow scheduler triggers one run. Prevent: a rule that every scheduled method must say how it behaves with N instances, and metrics for last success time with an alert if it does not run.

Under load, requests hang and the log shows "HikariPool-1 - Connection is not available, request timed out after 30000ms". What is your approach? Senior

What the interviewer is testing: a calm diagnosis of a classic incident.

Situation: the pool (say 10 connections) is fully used and threads wait. Do not just raise the pool size first. Check: (1) Thread dump: how many threads wait in getConnection, and what are the threads that hold connections doing? If they wait on an HTTP call inside a transaction, you found it. (2) Database side: long-running transactions and locks (pg_stat_activity or the InnoDB transaction table); a lock wait caused by a stuck transaction or missing index. (3) REQUIRES_NEW nesting: each request holds two connections, and with a pool of 10 and 10 concurrent requests all 10 hold one and wait for a second: a deadlock-like stall. (4) Connection leaks (manual getConnection not closed; streams not closed); Hikari's leakDetectionThreshold prints the stack of the leaker. (5) OSIV holding connections during rendering. (6) A sudden slow query after a data growth. Fix: shorten transactions (remote calls outside), avoid nested new transactions, add timeouts (@Transactional(timeout), statement timeout, query timeout), fix the slow query. Size the pool by what the database can handle. Prevent: dashboards for active, pending and timeout counts, with an alert on pending above zero for a minute.

A method called from @PostConstruct throws "no transaction in progress" or writes data that is never committed. Why? Senior

What the interviewer is testing: bean lifecycle timing and proxies.

Situation: at startup a bean seeds reference data from its @PostConstruct method by calling its own @Transactional method, and either a "TransactionRequiredException: no transaction is in progress" appears or data silently does not persist. Cause: the transactional proxy is created in postProcessAfterInitialization, which runs after @PostConstruct; and anyway the call is on this, not the proxy. So no transaction exists. Fix: move the seeding to another bean's transactional method and call it from a late hook: an ApplicationReadyEvent listener, an ApplicationRunner, or a SmartInitializingSingleton (called after all singletons, and with proxies, are ready). Or use TransactionTemplate in the init code. For schema and reference data, a migration tool (Flyway or Liquibase) is the correct place. Prevent: a rule that init callbacks must not use proxy-based features.

A field annotated @Autowired or @Value is null at runtime with no startup error. What happened? Basic

What the interviewer is testing: the "not a Spring-managed object" family of bugs.

Situation: a NullPointerException on an injected field. Causes, most common first: (1) The object was created with new MyClass(), so the container never injected it, including objects created inside another class by hand or deserialised by a library. (2) The field is static; Spring does not inject static fields. (3) The annotated class is not a bean (no stereotype, outside the scan). (4) The field is used in the constructor of the same class, before injection has run: field injection happens after construction. Use constructor injection to avoid it. (5) A final or private method on a CGLIB proxy: the proxy subclass instance has null fields (the proxy's own fields are not injected), so a call to a final method runs on the proxy and sees nulls. (6) A @Value("${x}") placeholder not resolved because PropertySourcesPlaceholderConfigurer is missing in a plain Spring setup. Fix by getting the object from the container, or injecting it, or making the class a bean; for objects you must create yourself, pass dependencies in explicitly. Prevent: constructor injection and final fields.

Using a request scoped bean fails with "Scope 'request' is not active for the current thread". What are the causes? Intermediate

What the interviewer is testing: scope and thread awareness.

Situation: an exception No thread-bound request found or Scope 'request' is not active. Causes: the code runs outside an HTTP request thread: an @Async method, a scheduled job, a message listener, a startup hook, or a thread pool you started. Or a singleton injects the request bean without a proxy (fixed by @RequestScope, which uses a proxy). Or the app is not a web application context. Fix: read what you need from the request on the request thread and pass it as an argument. If you really must carry request data into another thread, copy it explicitly (a TaskDecorator that copies RequestContextHolder attributes, with great care to clear it afterwards). Do not keep request objects after the response completes. Prevent: keep request-specific data in method parameters or small immutable context objects.

A list endpoint is fast with 10 rows in dev but takes 8 seconds in production with 5,000 rows. What do you look at in the Spring layer? Senior

What the interviewer is testing: end-to-end performance thinking.

Situation: latency grows with data size. Check: (1) The number of SQL statements per request (N+1): enable SQL logging, or Hibernate statistics, or a datasource proxy such as datasource-proxy. (2) Missing pagination: the endpoint returns the whole table; add Pageable with a maximum size. (3) Loading entities when only three columns are needed: use projections. (4) JSON serialisation cost of a large graph; return a lean DTO. (5) A missing index for the filter or sort (look at the query plan). (6) Work done per row that calls another service or the database (a loop of remote calls); batch it. (7) Slow queries hidden by the cache that is cold in production. (8) Thread pool or connection pool saturation under concurrency. Tools: a profiler or flame graph, http.server.requests timing, slow query logs, and a trace through the layers. Prevent: load test with production-sized data, and enforce paging on every list endpoint by code review or a base class.

The front end gets a CORS error only for POST requests with an Authorization header, although @CrossOrigin is on the controller. What is wrong? Intermediate

What the interviewer is testing: preflight handling together with Security.

Situation: GET works, but POST with JSON or a bearer token fails in the browser with "Response to preflight request doesn't pass access control check". Cause: the browser sends an OPTIONS preflight with no Authorization header. Spring Security's filters run first, find no credentials, and answer 401 or 403 without CORS headers. @CrossOrigin is evaluated later by MVC, which the request never reaches. Fix: add http.cors(Customizer.withDefaults()) and a CorsConfigurationSource bean listing the exact origins, methods (GET, POST, PUT, DELETE, OPTIONS) and headers (Authorization, Content-Type), and allowCredentials only if cookies are needed (then origins must not be *). Cache the preflight with maxAge. Verify with curl by sending an OPTIONS request with Origin and Access-Control-Request-Method headers. Prevent: a MockMvc test of an OPTIONS request against the secured chain.

After adding @Transactional to a class you get "class $Proxy123 cannot be cast to class MyServiceImpl". Why? Intermediate

What the interviewer is testing: JDK versus CGLIB proxies in practice.

Situation: a field of type MyServiceImpl is injected and, since the class now has a transactional annotation, the context fails or throws ClassCastException. Cause: the class implements an interface, and the context chose a JDK proxy, which implements the interface but is not a MyServiceImpl. Fix: inject the interface type (the cleaner design), or force class-based proxies with @EnableAspectJAutoProxy(proxyTargetClass = true) or spring.aop.proxy-target-class=true (already the default in Boot). For CGLIB the class must not be final and the advised methods not final. Prevent: depend on interfaces, or at least be consistent, and test the wiring with a context test.

An outer transaction fails at commit with UnexpectedRollbackException, although the inner exception was caught and handled. Why? Senior

What the interviewer is testing: the shared rollback-only flag with REQUIRED propagation.

Situation: importAll() loops over items and calls itemService.importOne() (@Transactional, REQUIRED) inside a try/catch so that one bad item should not stop the rest. After the loop the commit throws "Transaction silently rolled back because it has been marked as rollback-only". Cause: the inner method joined the outer transaction. When it threw a runtime exception, the proxy marked the shared transaction rollback-only. Catching the exception in the outer method does not clear that flag. So the outer commit is refused. Fix options: make the inner call REQUIRES_NEW, so each item has an independent transaction (watch pool usage); or use NESTED with savepoints on a JDBC transaction manager; or do not use an outer transaction at all and commit per item with TransactionTemplate; or validate before and avoid throwing. Prevent: a test that imports a batch with one bad record and asserts the good records are saved.

A security review found that a user can promote themselves to admin by adding "role": "ADMIN" to a profile-update request. What happened and how do you fix it? Senior

What the interviewer is testing: DTO discipline and server-side authorization.

Situation: the controller takes @RequestBody User user (the JPA entity) and calls repo.save(user). Jackson binds every property in the JSON onto the entity, including role and enabled. This is mass assignment. It was also missing an ownership check (the id came from the body). Fix: (1) Take a dedicated request DTO that has only the fields the user may change (name, phone), and copy those onto the loaded entity. (2) Take the user id from the authenticated principal, never from the body or path when it means "me". (3) Add @PreAuthorize for object-level checks, and keep role changes in an admin-only endpoint. (4) Configure Jackson to fail on unknown properties for strict contracts. Prevent: a rule that entities never appear in controller signatures, plus a security test that tries to send forbidden fields.

Closing line for an interview: "Spring is a container that builds and wires my objects, then wraps some of them in proxies. Transactions, async, caching and method security all work through those proxies, on one thread, so I design with that in mind: constructor injection, small services as transaction boundaries, no self-calls, and explicit context passing when work leaves the thread."
