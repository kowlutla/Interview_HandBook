Mental model: the 6 ideas everything hangs on

One line: Spring is a container that builds your objects, wires them together, and then wraps many of them in proxies that add transactions, security, caching and so on. Most Spring bugs are either "the container did not create or wire what I thought" or "the proxy was not in the call path".
  1. Inversion of control. You do not call new for your services. You declare what you need and the container supplies it. That is what makes swapping, mocking and wrapping possible.
  2. Recipe first, object later. The container first reads bean definitions (recipes) from annotations and config, and only then builds the objects in dependency order.
  3. Post-processors are the extension points. BeanFactoryPostProcessor edits recipes. BeanPostProcessor edits or replaces finished objects. Nearly every "magic" annotation is built on one of them.
  4. @Transactional, @Async, @Cacheable and @PreAuthorize work through proxies. The caller gets a wrapper that does the extra work and then calls your real object. A call that does not go through the wrapper gets no magic.
  5. Beans are mostly singletons shared by all threads. So they must be stateless or thread-safe. Per-request state lives in method variables, a scope, or a ThreadLocal you clean up.
  6. Per-thread context. Transactions, the security context and request attributes sit in ThreadLocals. A new thread (async, executor) does not see them unless you pass them on.

1. IoC, dependency injection, container and scopes

What is Inversion of Control, and what is dependency injection? How are they related? Basic

Normally a class creates its own collaborators with new. With Inversion of Control that decision moves out: the framework builds the objects and hands them in. Dependency injection (DI) is the most common way to do it. My class says "I need a PaymentGateway" and the container supplies one.

The payoff is loose coupling. The class depends on an interface, not on a concrete class or on how it is configured. In a test I pass a fake. In production the container passes the real one, or a proxy that adds transactions or caching. IoC is the broad idea (the framework calls you); DI is one technique for it. A service locator is another, but there the class still asks for its dependency, so it is harder to test and hides what it needs. You do not need Spring for DI: passing arguments to a constructor by hand is DI. Spring automates the wiring for big object graphs.

@Service
class OrderService {
    private final PaymentGateway gateway;        // an interface
    OrderService(PaymentGateway gateway) {       // the container supplies it
        this.gateway = gateway;
    }
}

Why it exists

Without IoC, a class decides which implementation it uses, how to build it and when to throw it away. Look at what that costs you:

class OrderService {
    // hard-wired: which gateway, which URL, which credentials?
    private final PaymentGateway gateway =
        new StripeGateway("https://api.stripe.com", System.getenv("KEY"));
}

To unit test OrderService you would call the real Stripe. To switch to another provider you edit the class. If StripeGateway needs three collaborators of its own, OrderService must build those too. The knowledge of "how the object graph is assembled" leaks into every class.

How the container does it

  1. At startup Spring scans for classes (@Service, @Component) and @Bean methods and records a bean definition for each: type, scope, constructor arguments.
  2. It works out the dependency graph: OrderService needs a PaymentGateway, which needs an HttpClient.
  3. It creates objects in dependency order (HttpClient first, then the gateway, then the service), passing each one into the constructor of the next.
  4. It keeps them in the container, so every class that asks for a PaymentGateway gets the same configured instance.

The "inversion" is who is in control. Before, your code called new. Now the framework calls your constructor. It is the Hollywood principle: "don't call us, we'll call you".

Same idea by hand, no Spring

// DI without any framework: you wire manually in main()
var gateway = new StripeGateway(config);
var service = new OrderService(gateway);

// in a test
var service = new OrderService(new FakeGateway());

Spring is just an automatic version of that wiring code. When the graph has hundreds of classes, nobody wants to maintain it by hand, and the container can also wrap beans in proxies (transactions, caching, security) without the class knowing.

Pitfall: DI makes dependencies easy to add, so classes quietly grow ten collaborators. A long constructor is the signal that the class has too many responsibilities.

Remember: IoC is the principle (do not build your own collaborators), DI is how the container hands them in.

Constructor, setter and field injection: what are the differences, and which do you prefer? Basic

I prefer constructor injection for required dependencies. The fields can be final, the object can never exist half-wired, and a unit test can just call new OrderService(fakeGateway) with no Spring and no reflection. Setter injection is fine for truly optional dependencies. I avoid field injection (@Autowired on a private field) in application code.

Field injection is short, but it hides how many dependencies a class has, needs reflection or a Spring context to test, and lets circular dependencies slip through quietly. A constructor with eight arguments is a visible smell that the class does too much. Since Spring 4.3, a class with a single constructor needs no @Autowired at all. Do not argue that field injection is "slow"; it is not. The real reasons are testability, immutability and honest coupling.

A constructor cycle (A needs B, B needs A) fails loudly at startup with BeanCurrentlyInCreationException. That is a feature: it forces you to fix the design.

The three styles side by side

    private Clock clock = Clock.systemUTC();      // sensible default

}

// 3. Field injection (avoid)
@Service

    @Autowired private PaymentGateway gateway;    // hidden, not final
}

What each one really buys you

Immutability and safe publication. A final field set in the constructor is visible to every thread without extra synchronisation (Java memory model guarantee for final fields). Setter and field injection give you a mutable field that Spring writes after construction.

Honest design. If the constructor has seven parameters you feel it, and you split the class. With field injection the class looks tiny while secretly needing seven beans.

Circular dependencies. With constructors A-needs-B-needs-A cannot be built at all, so Spring fails at startup. Setter or field injection let Spring create A first, then B with a reference to the half-built A. Since Spring Boot 2.6, circular references are prohibited by default (spring.main.allow-circular-references is false), so this "quietly works" trap is mostly gone, but the right fix is still to redesign: extract a third class or use an event.

Say in the interview: field injection is not wrong because of speed, it is wrong because it makes classes hard to test and hides coupling.

Remember: constructor for required, setter for optional, field only in tests and glue code.

What is the difference between BeanFactory and ApplicationContext? Basic

BeanFactory is the basic container: it creates beans and wires dependencies. ApplicationContext extends it with what real applications need: automatic registration of post-processors (so annotations, AOP and transactions work), application events, internationalised messages, resource loading, the Environment with profiles and properties, and eager creation of singletons at startup. In practice you always use an ApplicationContext.

The eager creation matters most in practice: a missing bean or bad config fails the application at startup, not on the first user request. A bare DefaultListableBeanFactory creates beans lazily and applies no post-processors unless you add them by hand. Classic Spring MVC can have two contexts: a parent root context (services) and a child DispatcherServlet context (controllers). Boot normally uses a single one.

What a container is, from scratch

A container is an object that holds bean definitions ("recipes") and builds and stores bean instances on demand. BeanFactory is the minimal interface: getBean(name), getBean(Class), containsBean. That is all.

The practical rule: you never choose BeanFactory directly. It is the base interface; every real container (AnnotationConfigApplicationContext, the web contexts, Boot's SpringApplication context) is an ApplicationContext. Knowing the split explains why a hand-built DefaultListableBeanFactory in a test "ignores my annotations".

Follow-up to expect: "Is the context thread-safe?" Reading beans (getBean) is; refresh and close are guarded by a lock, and you should not refresh concurrently.

Remember: ApplicationContext = BeanFactory + post-processors, events, i18n, environment, eager singletons.

What happens when an ApplicationContext starts? Walk me through refresh(). Senior

The work happens in AbstractApplicationContext.refresh(). Spring loads bean definitions (scanning, @Configuration classes), runs the BeanFactoryPostProcessors that may change those definitions, registers the BeanPostProcessors, then creates all non-lazy singletons through the full bean lifecycle, and finally publishes ContextRefreshedEvent. Recipes first, extension points second, real objects last.

Details that help in an interview. @Configuration, @ComponentScan, @Import and @Bean are processed by ConfigurationClassPostProcessor, which is a BeanFactoryPostProcessor. @Autowired and @PostConstruct are handled by bean post-processors. Because post-processors are created before ordinary beans, a bean that a post-processor itself depends on gets created too early to be proxied, and Spring logs "not eligible for getting processed by all BeanPostProcessors". Any error in these steps aborts startup, which is why wiring problems show at boot.

Walk-through with a tiny config

@Configuration
@ComponentScan("com.acme")
class AppConfig {
    @Bean DataSource ds() { return new HikariDataSource(); }
}
var ctx = new AnnotationConfigApplicationContext(AppConfig.class);   // refresh() runs here
  1. Prepare and get a fresh bean factory. The context sets up the Environment, creates the empty factory and registers some built-in beans.
  2. Load bean definitions. The AppConfig class is registered. Nothing is instantiated, only definitions (type, scope, dependencies) are stored.
  3. Invoke BeanFactoryPostProcessors. ConfigurationClassPostProcessor reads @ComponentScan, @Import, @Bean and adds many more definitions. PropertySourcesPlaceholderConfigurer resolves ${...} placeholders. This is the last chance to change a definition.
  4. Register BeanPostProcessors. They are instantiated now (before ordinary beans) so they can wrap every later bean: autowiring, @PostConstruct, AOP auto-proxy creator.
  5. Init infrastructure: message source, event multicaster, and in web apps the embedded server is created at the "onRefresh" hook (Boot creates the server here but starts accepting requests only after refresh completes in current versions).
  6. Instantiate all non-lazy singletons through the full bean lifecycle (see the next chapter).
  7. Finish: start Lifecycle beans, publish ContextRefreshedEvent.

Why this order matters

Definitions must be final before beans are built, otherwise a placeholder could resolve too late. Bean post-processors must exist before application beans so they can proxy them. If a normal bean is needed by a post-processor, it gets created too early, skips later post-processors and is not proxied. That causes the confusing case "my @Transactional doesn't work on a bean used by a BeanPostProcessor".

Failure behaviour: any exception in these steps aborts refresh(); the context destroys the beans it already created and rethrows, so the app exits at boot with a clear stack trace. This is the "fail fast" design.

A good interview line: "BeanFactoryPostProcessors change recipes, BeanPostProcessors change finished objects."

Remember: definitions, then factory post-processors, then bean post-processors, then singletons, then the refreshed event.

How does Spring decide which bean to inject when there are several of the same type? Intermediate

Spring first collects all beans whose type matches. If exactly one matches, it is injected. If several match, it prefers the one marked @Primary, then applies an @Qualifier if the injection point has one, and as a last fallback it compares the field or parameter name with bean names. If it is still ambiguous you get NoUniqueBeanDefinitionException. If nothing matches you get NoSuchBeanDefinitionException, the "No qualifying bean of type" message.

Use @Primary on the bean that should win by default (your main DataSource). Use @Qualifier("name") at the injection point when one consumer needs a specific bean. A qualifier beats primary because it is more specific. If the injected type is List<T> or Map<String,T>, Spring injects all matches; that is a neat way to do the strategy pattern with no if chain. Order a list with @Order. For optional dependencies use Optional<T>, ObjectProvider<T> or @Autowired(required = false).

@Bean @Primary DataSource mainDs() {...}
@Bean DataSource reportDs() {...}

@Autowired DataSource ds;                         // mainDs (primary)
@Autowired @Qualifier("reportDs") DataSource rds; // by qualifier

A worked example

Suppose there are three implementations of one interface:

interface Notifier { void send(String msg); }
@Component class EmailNotifier implements Notifier {...}
@Component @Primary class SmsNotifier implements Notifier {...}
@Component class PushNotifier implements Notifier {...}

// Three alternative constructors (use ONE per class):
@Service class AlertA { AlertA(Notifier n) {} }                          // gets SmsNotifier (primary)
@Service class AlertB { AlertB(@Qualifier("pushNotifier") Notifier n) {} } // gets PushNotifier
@Service class AlertC { AlertC(Notifier emailNotifier) {} }              // EmailNotifier by param name*

* Name fallback only works if parameter names are available (compile with -parameters; Boot's Maven and Gradle plugins do this) and there is no @Primary, since primary is checked first.

Default bean names come from the class name with a lowercase first letter (PushNotifier becomes pushNotifier) or from the @Bean method name.

Injecting all of them: the strategy pattern

@Service
class AlertService {
    private final List<Notifier> all;          // every Notifier bean
    private final Map<String, Notifier> byName;// key = bean name
    AlertService(List<Notifier> all, Map<String, Notifier> byName) {...}
    void broadcast(String m) { all.forEach(n -> n.send(m)); }
}

Adding a new Notifier class needs no change to AlertService: the open/closed principle done by the container. Order with @Order(1) or by implementing Ordered; lower numbers come first.

Custom qualifiers and pitfalls

  • You can define your own annotation meta-annotated with @Qualifier (for example @Fast) for type-safe selection rather than magic strings.
  • @Qualifier on a @Bean method or class labels the bean; on the injection point it selects. Two @Primary beans of the same type still cause a NoUniqueBeanDefinitionException.
  • Generic types act as qualifiers too: Repository<Order> and Repository<User> are different candidates.
  • Do not rely on name matching in shared code: renaming a parameter then changes behaviour. Prefer an explicit @Qualifier.

Remember: type, then @Primary, then @Qualifier, then name. Several candidates and no winner means NoUniqueBeanDefinition.

What is the difference between @Autowired, @Resource and @Inject? Intermediate

@Autowired is Spring's own annotation and resolves by type first, then narrows by qualifier or name. @Inject (jakarta.inject) is the standard equivalent and behaves the same, except it has no required flag. @Resource (jakarta.annotation) is the reverse: it resolves by name first and falls back to type.

Because they are processed by different post-processors, behaviour can differ slightly, but for application code the choice is mostly style. I use constructor injection, which needs no annotation at all. @Resource is handy when you want to pick a bean strictly by name, and it works on fields and setters but not on constructors.

Why there are three

@Autowired came first and is Spring-specific. @Inject was added so code can move between DI frameworks (Spring, Guice, CDI). @Resource comes from Java EE and is name-based because JNDI lookups are name-based. Note that since Spring 6 / Boot 3 the packages are jakarta.*; on Boot 2 they are javax.*, a common migration pitfall.

Practical advice: pick one convention for the team. The most robust is constructor injection (annotation optional), with @Qualifier for the rare disambiguation. An interviewer asking this wants to hear "type-based vs name-based" and that you know constructor injection avoids the question.

Remember: Autowired and Inject go by type; Resource goes by name first.

What bean scopes does Spring have, and which is the default? Basic

The default is singleton: one instance per container, shared by every thread. Prototype creates a new instance each time the bean is requested from the container. In a web app there are also request, session, application and websocket scopes. Because singletons are shared, they must not keep per-request state in fields.

A service with a field currentUser mixes data between concurrent users, which is one of the costliest classic bugs. The usual design is stateless singletons with state in method variables. Spring does not synchronise anything for you, so a singleton is thread-safe only if you make it so. Singletons are created at startup unless marked @Lazy. You can also register custom scopes (Spring Batch has step, Spring Cloud has refresh).

@Component @Scope("prototype") class ReportBuilder {}
@Component @RequestScope       class RequestInfo {}   // scoped proxy
@Component @SessionScope       class Cart {}

The key point: shared means thread-safe or stateless

@Service
class PriceService {
    private BigDecimal lastPrice;               // BUG: shared by all threads
    BigDecimal quote(Item i) {
        lastPrice = lookup(i);                  // thread A writes...
        return lastPrice.multiply(taxRate());   // ...thread B overwrote it
    }
}

Fix: use a local variable (var price = lookup(i)), or make the state immutable or thread-safe (AtomicLong, ConcurrentHashMap). Per-request state belongs in method parameters, a request-scoped bean or a ThreadLocal that you clean up.

Lifecycle differences you should know

  • The container does not manage destruction of prototypes: @PreDestroy is never called for them. The caller owns cleanup.
  • Singletons are created eagerly at startup (fail fast); prototypes and request/session beans are created lazily when needed.
  • Web scopes need an active web request. Injecting them into a singleton needs a scoped proxy (see the prototype question).
  • Session-scoped beans must be Serializable if sessions are replicated or persisted.

Interview probe: "Is a singleton controller thread-safe?" It is shared, so it is thread-safe exactly when it has no mutable state.

Remember: singleton by default means shared by all threads, so keep it stateless.

Is a Spring singleton the same as the Singleton design pattern? Intermediate

No. The GoF Singleton guarantees one instance per class loader and enforces it in code with a private constructor. A Spring singleton means one instance per bean definition per container. Define two beans of the same class with different names and you get two instances, both singleton scoped. Run two application contexts and you get two more.

Spring also does nothing to stop someone calling new on the class. So thread safety stays your design responsibility; the scope does not give it to you.

What happens if you inject a prototype (or request-scoped) bean into a singleton? How do you fix it? Intermediate

Injection happens only once, when the singleton is created. So the singleton gets one prototype instance and keeps it forever, shared by all threads. The fresh-instance-per-use you expected never happens. The fix is to ask the container each time: inject an ObjectProvider<T> and call getObject(), or use a scoped proxy.

The four options. (1) ObjectProvider<T> (or jakarta.inject.Provider): my preferred choice, explicit and easy to test. (2) @Lookup on a method: Spring generates a subclass that asks the container on each call. (3) A scoped proxy: @Scope(value = "prototype", proxyMode = TARGET_CLASS); the singleton holds a small proxy that looks up the real target on every call. (4) Injecting ApplicationContext and calling getBean works, but couples you to Spring.

The same trap with request or session scope is how a singleton controller uses a request-scoped bean. @RequestScope and @SessionScope already set a scoped proxy. On each call the proxy finds the current request through a ThreadLocal (RequestContextHolder) and delegates to that request's real bean. That is also why using it from an @Async thread fails with "Scope 'request' is not active": there is no request on that thread.

Reproduce the bug first

@Component @Scope("prototype")
class ShoppingBasket { final List<Item> items = new ArrayList<>(); }

@Service
class CheckoutService {
    private final ShoppingBasket basket;                   // injected ONCE
    CheckoutService(ShoppingBasket basket) { this.basket = basket; }
    void add(Item i) { basket.items.add(i); }              // everyone shares one basket!
}

User A and user B both add to the same list. The annotation says prototype, but nothing asks the container for a new one after startup.

The fixes in code

// 1. ObjectProvider: explicit, my default
CheckoutService(ObjectProvider<ShoppingBasket> baskets) { this.baskets = baskets; }
void add(Item i) { baskets.getObject().items.add(i); }   // new basket per call

// 2. @Lookup: Spring overrides the method in a generated subclass
@Lookup ShoppingBasket newBasket() { return null; }       // body ignored

// 3. Scoped proxy: injection point stays plain
@Component @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
class ShoppingBasket {...}

Beware of option 3 for prototypes: each method call on the proxy creates a fresh target, so a sequence basket.add(a); basket.add(b); acts on two different instances. A scoped proxy fits request and session scope, where "the current one" is well-defined, but rarely a prototype. For prototypes prefer ObjectProvider and keep the instance in a local variable for the whole operation.

How the request-scope proxy works

  1. Singleton gets a CGLIB proxy (same type as the target) at startup.
  2. On each call the proxy asks RequestContextHolder (a ThreadLocal) for the current request attributes.
  3. It finds or creates the real bean stored in that request and delegates.

With no request on the thread (an @Async method, a scheduled job, a plain new thread) you get IllegalStateException: No thread-bound request found or "Scope 'request' is not active". Pass the needed data as arguments instead.

Remember: injection time is the moment of choice. A direct reference freezes it; a provider or scoped proxy asks again on every use.

What does @Lazy do, and when would you use it? Intermediate

On a bean, @Lazy means "do not create this singleton at startup, create it on first use". On an injection point, Spring injects a lazy proxy and builds the real bean only when a method is first called. I use it to skip a heavy, rarely used bean, or to break a circular dependency without a redesign.

The trade-off is that errors move from startup to runtime, so a wiring problem shows up under load, and the first request that touches the bean pays the creation cost. A global switch exists in Boot (spring.main.lazy-initialization=true); I use it only in local development, since it hides startup failures.

Eager versus lazy, with an example

@Component
@Lazy                                // not created at startup
class ReportEngine { ReportEngine() { /* loads 200 MB of templates */ } }

@Service
class Controller {
    Controller(@Lazy ReportEngine engine) {}   // injects a proxy; real bean built on first call
}

Normal singletons are built during refresh(). With @Lazy the definition exists but nothing is built until someone calls getBean or, for a lazy injection point, until the first method call on the proxy.

Two main uses

  • Startup speed and memory. Skip beans most runs never touch (admin tools, rarely used clients). Boot's global lazy-init does this for the whole app, which can cut startup time but spreads cost to first requests.
  • Breaking a cycle. If A needs B and B needs A through constructors, marking one injection point @Lazy lets A get a proxy of B now and a real B later. It works, but it is a patch. Prefer fixing the design.

What goes wrong

  • A misconfigured lazy bean passes startup and blows up on a user request. Health checks and readiness probes can report "up" while the app is broken.
  • First-call latency spikes in production, which hurts p99 and can trip timeouts after a deploy. Warm-up calls or eager mode in production avoid that.
  • @Lazy on a @Configuration class or component scan makes all its beans lazy.

Remember: lazy trades fail-fast startup for a faster start. Use it sparingly.

What is the difference between @Component and @Bean? Basic

@Component goes on your own class, and Spring finds it by scanning and calls its constructor. @Bean goes on a method inside a @Configuration class: the method builds and returns the object and Spring registers that return value as a bean. I use @Bean for third-party classes I cannot annotate (ObjectMapper, DataSource), when construction needs logic, or when I want several differently configured beans of one type. @Component is for my own classes.

Same result, different mechanism

// @Component: Spring instantiates my class by scanning
@Component
class PriceCalculator {
    PriceCalculator(TaxService tax) {...}
}

@Component, @Service, @Repository, @Controller: is there a real difference? Basic

All are stereotype annotations and @Service, @Repository and @Controller are meta-annotated with @Component, so scanning treats them the same. The real differences: @Repository makes Spring translate persistence exceptions (SQLException, Hibernate errors) into its unchecked DataAccessException hierarchy. @Controller tells MVC to look for request-mapping methods. @Service is documentation only today.

Using the right one still helps readers, tools and AOP pointcuts such as "every @Service class". @RestController is @Controller plus @ResponseBody.

How does component scanning work, and why might a bean not be found? Intermediate

@ComponentScan walks a base package and its sub-packages, reads class files looking for @Component or a stereotype, and registers a definition for each. With no base package given, it uses the package of the annotated class. The most common reason a bean is "not found" is that it sits in a package outside the scanned tree.

Other causes: the annotation is missing, the class is an interface or abstract, a condition switched it off (@Profile, @ConditionalOnProperty), or someone created it with new. Fix by moving the class, widening scanBasePackages, or declaring it with @Import or @Bean. In Boot the main class sits at the root package, so everything below it is scanned.

@Configuration
@ComponentScan(basePackages = {"com.acme.app", "com.acme.shared"})
class AppConfig {}

What happens during scanning

  1. Spring takes the base package(s), for example com.acme.app.
  2. It lists .class files under that path on the classpath and reads their metadata with ASM (without loading the classes into the JVM).
  3. If a class has @Component or a meta-annotation of it, and passes the filters and conditions, it registers a bean definition. The default name is the decapitalised simple class name.

2. Bean lifecycle and post-processors

Describe the lifecycle of a singleton bean, with all the hooks. Intermediate

Spring constructs the bean, injects dependencies, runs the Aware callbacks, then BeanPostProcessor before-init (which runs @PostConstruct), afterPropertiesSet(), the custom init method, and finally BeanPostProcessor after-init, where AOP proxies are created. The bean is then ready. On shutdown it runs @PreDestroy, DisposableBean.destroy(), then the custom destroy method.

A way to remember it: at both start and end the order is "annotation, interface, custom method". Two points interviewers like. First, the proxy appears only in the last init step, so inside @PostConstruct the bean is still the raw object and @Transactional on its own methods does nothing. Second, prototype beans go through creation but Spring never calls their destroy callbacks. Destroy callbacks also do not run if the JVM is killed hard (kill -9); on a normal shutdown the context closes through a shutdown hook, which Boot registers. For new code use @PostConstruct and @PreDestroy, since they do not tie your class to Spring interfaces.

Watch it happen

This tiny bean prints each hook, so you can see the order yourself:

@Component
class Demo implements BeanNameAware, InitializingBean, DisposableBean {
    Demo()                                   { log("1 constructor"); }
    @Autowired void setDep(Dep d)            { log("2 inject"); }
    public void setBeanName(String n)        { log("3 aware"); }
    @PostConstruct void pc()                 { log("4 @PostConstruct"); }
    public void afterPropertiesSet()         { log("5 afterPropertiesSet"); }
    // @Bean(initMethod="start") would run here  -> 6
    @PreDestroy void pd()                    { log("8 @PreDestroy"); }
    public void destroy()                    { log("9 destroy"); }
}

Which hook for which job

  • Constructor: only assign fields; dependencies are passed in, so this is where required state becomes valid.
  • @PostConstruct: work that needs all injected fields, e.g. build an index from an injected config.
  • InitializingBean / initMethod: the same idea without annotations; initMethod is useful on third-party classes via @Bean(initMethod = "start").
  • @PreDestroy / destroy / destroyMethod: close pools, flush buffers, stop threads. Note that @Bean methods returning Closeable or having a public close() or shutdown() get that method called automatically ("inferred" destroy method).

Why the proxy comes last

The auto-proxy creator is a BeanPostProcessor. Its "after initialization" hook wraps the finished bean. So the object @PostConstruct sees is raw: a call to this.someTransactionalMethod() there has no transaction. The container then stores the proxy under the bean name.

SmartLifecycle is a separate, later mechanism: beans start in phases after all singletons exist (Kafka listeners, schedulers), and stop in reverse phase order on shutdown. That is the right hook for "start consuming only when the app is fully ready".

Shutdown depends on the context closing: Boot registers a JVM shutdown hook, so SIGTERM runs destroy callbacks and gives in-flight work a chance to finish (graceful shutdown). kill -9 skips everything.

Remember: construct, inject, aware, @PostConstruct, afterPropertiesSet, init-method, proxy. Destroy mirrors it: annotation, interface, method.

What is the difference between BeanPostProcessor and BeanFactoryPostProcessor? Intermediate

A BeanFactoryPostProcessor works on bean definitions (the recipes) after they are loaded and before any ordinary bean is created. A BeanPostProcessor works on bean instances, around each bean's init methods, and may modify the object or return a different one such as a proxy.

Examples of the first: ConfigurationClassPostProcessor (reads @Configuration, @Bean, @ComponentScan) and the ${...} placeholder resolver. Examples of the second: AutowiredAnnotationBeanPostProcessor (does @Autowired and @Value), CommonAnnotationBeanPostProcessor (@PostConstruct) and the auto-proxy creator for AOP. Practical rule: declare a BeanFactoryPostProcessor @Bean method as static so its configuration class need not be created early, and keep post-processors free of dependencies, since those dependencies are created before the processors can touch them.

@Component
class TimingBpp implements BeanPostProcessor {
    public Object postProcessAfterInitialization(Object bean, String name) {
        return bean;   // the bean itself, or a wrapper/proxy
    }
}

Two moments, two kinds of object

Think of baking. The bean definition is the recipe card; the bean is the finished cake.

  • BeanFactoryPostProcessor edits recipe cards before baking starts. It can add a definition, change a scope or fill in a ${...} placeholder.
  • BeanPostProcessor inspects each cake as it comes out of the oven, before and after the "init" step, and can swap it for another (a proxy).
// Changes a recipe: make every bean in a package lazy
@Bean static BeanFactoryPostProcessor makeLazy() {          // static!
    return bf -> {
        for (String n : bf.getBeanDefinitionNames()) {
            BeanDefinition d = bf.getBeanDefinition(n);
            if (d.getBeanClassName() != null && d.getBeanClassName().startsWith("com.acme.report"))
                d.setLazyInit(true);
        }
    };
}

// Changes objects: wrap every @Service in a timing proxy (simplified)
@Component class Timing implements BeanPostProcessor {
    public Object postProcessAfterInitialization(Object bean, String name) {
        return bean.getClass().isAnnotationPresent(Service.class) ? wrapWithTimer(bean) : bean;
    }
}

Why "static" and "no dependencies"

A BeanFactoryPostProcessor is created before regular beans. If it is declared as an instance @Bean method, Spring must instantiate the whole @Configuration class first, which triggers early creation of other beans that the config class needs (autowired fields), and they miss @Autowired or proxying. A static method needs no instance. The same logic means a BeanPostProcessor with injected dependencies forces those dependencies to be built early, and Spring logs "is not eligible for getting processed by all BeanPostProcessors".

What should and should not go into @PostConstruct? Intermediate

Use it for cheap local set-up that needs injected fields: build a lookup map, validate configuration. Avoid calling your own @Transactional or @Cacheable methods from it, because the proxy does not exist yet, and avoid slow remote calls, because they block startup.

An exception in @PostConstruct aborts the whole application start, so wrap optional work in a try/catch or move it to a background task. For "run after everything is up" use ApplicationReadyEvent, SmartInitializingSingleton, or in Boot an ApplicationRunner. If data loading needs a transaction, call another bean's transactional method from such a late hook; that call goes through a proxy.

Why people trip on it

It looks like "run this once the bean is ready", but at that moment the bean is only half of the story: dependencies are injected, yet the bean is not yet wrapped in its proxy and the rest of the context may still be starting.

    @Autowired CatalogRepo repo;

    @PostConstruct
    void init() {
        warmCache();              // @Cacheable on warmCache: IGNORED, no proxy yet
        loadFromRemote();         // slow HTTP call: blocks startup, and if it throws, app does not start
    }
    @Cacheable("items") List<Item> warmCache() { ... }
}

What is a FactoryBean, and how is it different from a BeanFactory? Senior

A BeanFactory is the container itself. A FactoryBean<T> is a special bean that produces another object: the container calls its getObject() and registers that product under the bean name. Spring uses it for complex creation, such as LocalContainerEntityManagerFactoryBean and ProxyFactoryBean.

Asking for the bean by name gives you the product. Prefix the name with & (getBean("&myFactory")) to get the factory itself. In new code a plain @Bean method does the same job with less ceremony.

The problem it solves

Some objects cannot be created by "call a constructor": a JPA EntityManagerFactory needs a data source, a persistence unit and vendor adapter; a proxy needs interfaces and interceptors; a JNDI lookup needs a name. A FactoryBean wraps that creation logic and registers the product under the bean name.

class ClockFactory implements FactoryBean<Clock> {
    public Clock getObject()        { return Clock.systemUTC(); }  // the product
    public Class<?> getObjectType() { return Clock.class; }
    public boolean isSingleton()    { return true; }
}
// register: @Bean ClockFactory clock() ...
ctx.getBean("clock");    // a Clock (the product)
ctx.getBean("&clock");   // the ClockFactory itself

3. Configuration, profiles and properties

What does @Configuration do? Explain "full" versus "lite" mode and proxyBeanMethods. Senior

A @Configuration class holds @Bean methods. In full mode (the default) Spring creates a CGLIB subclass of it, so when one @Bean method calls another, the call is intercepted and returns the existing singleton instead of running the method again. In lite mode (proxyBeanMethods = false, or @Bean methods in a plain @Component) there is no proxy, so such a call is an ordinary Java call and creates a new object each time.

Lite mode starts faster, uses less memory and suits GraalVM native images, which is why Boot's own auto-configurations use it. The safe habit in both modes is to pass dependencies as method parameters, not to call another @Bean method. A full configuration class cannot be final, because CGLIB must subclass it.

@Configuration(proxyBeanMethods = false)
class Cfg {
    @Bean B b() { return new B(); }
    @Bean A a(B b) { return new A(b); }   // parameter: correct in both modes
}

The effect, in code

@Configuration                       // full mode (CGLIB subclass)
class Full {
    @Bean Repo repo()       { return new Repo(); }
    @Bean ServiceA a()      { return new ServiceA(repo()); }   // intercepted: same singleton
    @Bean ServiceB b()      { return new ServiceB(repo()); }   // same Repo as A
}

@Configuration(proxyBeanMethods = false)       // lite mode
class Lite {
    @Bean Repo repo()       { return new Repo(); }
    @Bean ServiceA a()      { return new ServiceA(repo()); }   // plain call: NEW Repo!
    @Bean ServiceB b(Repo r){ return new ServiceB(r); }        // parameter: correct
}

In Lite, a() gets a private Repo that is not the registered bean, so two different "singleton" repos exist. That is a quiet bug that shows up as inconsistent state or double connections.

How full mode works

  1. ConfigurationClassPostProcessor replaces the class definition with a CGLIB subclass.
  2. Every @Bean method in the subclass first checks the container: "is there already a bean named repo?" If yes, return it; if not, run the real method and register the result.

Rule of thumb: always write @Bean methods with dependencies as parameters, then proxyBeanMethods=false is free to use. Framework and library configurations (Boot auto-configs) do exactly that.

Remember: full mode proxies inter-bean calls to keep singletons; lite is faster but needs dependencies as parameters.

How do profiles work, and how do you make config differ per environment? Basic

A profile is a named group of beans and properties that is active only when you ask for it. I mark beans with @Profile("dev") and activate profiles with spring.profiles.active, the SPRING_PROFILES_ACTIVE environment variable, or @ActiveProfiles in tests. In Boot, application-prod.yml is loaded on top of application.yml when prod is active and overrides it.

Rules I follow: the same code runs in every environment and only configuration varies; secrets come from the environment or a secret store, never the repository; and I do not hide untested business logic behind @Profile("prod"). Expressions like "!prod" and "dev & local" work. With no profile set, default is active. You can activate several, comma separated. A common failure is a typo in the profile name, so the expected file is silently not loaded.

Profiles in practice

@Configuration
class StorageConfig {
    @Bean @Profile("dev")  FileStore localStore() { return new LocalDiskStore("/tmp/x"); }
    @Bean @Profile("prod") FileStore s3Store()    { return new S3Store(bucket); }
}

app.mail.from: noreply@acme.test
---
# application-prod.yml (loaded when profile "prod" is active, overrides the above)

How to activate

  • Environment variable: SPRING_PROFILES_ACTIVE=prod (my choice for containers).
  • Command line: java -jar app.jar --spring.profiles.active=prod.
  • Tests: @ActiveProfiles("test").
  • Programmatically: SpringApplication.setAdditionalProfiles("x"), or spring.profiles.include to add profiles on top.

Good and bad use

Good: swapping an infrastructure implementation (local disk vs S3, fake vs real payment sandbox), or toggling dev tooling. Bad: if profile is prod branches inside business code, or "prod only" features that no test ever exercises, because the code that ships is then different from the code that was tested. For feature toggles use feature flags, not profiles.

In Boot 2.4 and later, profile-specific documents can also live inside one multi-document YAML using spring.config.activate.on-profile. Never commit prod secrets to application-prod.yml; read them from env variables or a secret manager.

Remember: same artifact everywhere, only the active profile and external config change.

What is the Environment, and which value wins when the same property is set in several places? Intermediate

The Environment holds the active profiles and an ordered stack of property sources. A lookup returns the first hit from the top. In a typical Boot app the order from highest to lowest is: command-line arguments, system properties (-D), OS environment variables, profile-specific config files, the main config file, then defaults in code.

The operational meaning: an environment variable or command-line flag beats the file packaged in the jar, so you can override settings per deployment without rebuilding. Note that @PropertySource sits low in the order and does not load YAML by default. The exact full order is on the Spring Boot page.

String v = env.getProperty("app.mode", "default");
boolean prod = env.acceptsProfiles(Profiles.of("prod"));

The mental model: a stack of maps

Each property source is a named key-value map. The Environment keeps them in a list; getProperty(key) walks the list from the top and returns the first match. That is why the same key can be set in many places safely.

Example: where does server.port come from?

# application.yml (inside jar)           server.port: 8080
# application-prod.yml (inside jar)      server.port: 8081
# environment variable on the host       SERVER_PORT=9090
# command line                           java -jar app.jar --server.port=7070

# active profile = prod. Result: 7070 (command line wins)
# remove the command-line flag:     9090 (env var beats files)
# remove the env var:               8081 (profile file beats main file)
# remove the profile file:          8080

Simplified order, high to low

  1. Command-line arguments
  2. SPRING_APPLICATION_JSON, system properties (-Dkey=value)
  3. OS environment variables (MY_APP_KEY is mapped to my.app.key)
  4. External config files next to the jar, then those inside the jar; profile-specific before general
  5. @PropertySource classes and default properties

The ops value: the same image is promoted from test to prod, and each environment injects its own values from outside. Never rebuild for a config change.

Pitfalls: a stale environment variable silently overriding the file you edit; @PropertySource does not support YAML without a custom factory; and relaxed binding for env vars (uppercase with underscores) applies to @ConfigurationProperties but not always to @Value with a hyphenated name, so use the canonical lowercase key in @Value.

Remember: command line beats system property beats env var beats config file. Override outside, do not rebuild.

What is a circular dependency in Spring, and how does Spring handle it? Senior

It means A needs B and B needs A. With constructor injection neither can be built first, so startup fails with BeanCurrentlyInCreationException. With setter or field injection on singletons, Spring can resolve it by exposing a half-built A early. Since Spring Boot 2.6 this is disabled by default, so cycles show up as startup errors, and I treat a cycle as a design smell to fix.

The mechanism uses three caches: finished singletons, early references, and singleton factories. Spring creates A, registers a factory for its early reference, then injects A's fields. That needs B, which needs A, and B gets A's early reference from the factory. B finishes, then A finishes. The factory exists so that if A will become a proxy, B receives the proxy and not the raw A. If it ends up with the raw version, Spring fails with "has been injected into other beans in its raw version".

Fixes: extract a third class that holds the shared logic, use events, or invert one side to an interface. As a quick patch, put @Lazy on one constructor parameter or inject an ObjectProvider.

A concrete cycle

@Service class OrderService   { @Autowired InvoiceService invoices; }
@Service class InvoiceService { @Autowired OrderService orders; }   // cycle

On Boot 2.6+ this fails at startup with a message listing the cycle ("The dependencies of some of the beans in the application context form a cycle"). The message is helpful: read it, it prints A, B, A.

Why a cycle is a design smell, not just a wiring problem

If OrderService and InvoiceService need each other, they probably share a concept that wants its own class, or one of them is doing a job that belongs to the other. Cycles also make initialisation order fragile and unit tests awkward.

Ways to break the cycle (in order of preference)

  1. Extract: move the shared logic into a third bean both depend on. The graph becomes a tree.
  2. Events: OrderService publishes OrderPlaced; InvoiceService listens. Neither knows the other.
  3. Invert: make one side depend on an interface or callback it receives as a method argument.
  4. Patch: @Lazy on one constructor parameter, or ObjectProvider<OrderService>, resolved on first use. Works, but hides the problem.
  5. Last resort: set spring.main.allow-circular-references=true to restore the old behaviour.

Why constructors cannot be saved by early references: to expose an early reference Spring needs the instance to exist; with constructor injection the instance does not exist until all arguments are available, which is the circular wait.

Remember: constructor cycles cannot work; setter cycles used to be patched by early references. Redesign instead.

4. Proxies and AOP

Why does Spring use proxies, and which features rely on them? Intermediate

Spring wants to add behaviour such as starting a transaction, checking security or caching a result without me writing it in every method. A proxy is an object that looks like my bean, wraps the real one, and adds those steps around each call. The container stores the proxy in place of the real object, so everyone who injects the bean gets the proxy.

Features built this way: @Transactional, @Async, @Cacheable, @PreAuthorize, @Validated method validation, @Retryable, scoped proxies and my own aspects. The proxy is created by a BeanPostProcessor after the bean is initialised. The big consequence: the extra behaviour happens only on calls that arrive through the proxy. A call from inside the same object skips it.

The problem: cross-cutting code everywhere

Imagine writing transaction code by hand in every service method:

void placeOrder(Order o) {
    Connection c = ds.getConnection();
    try { c.setAutoCommit(false);
          orders.save(o); stock.reserve(o);
          c.commit();
    } catch (Exception e) { c.rollback(); throw e; }
    finally { c.close(); }
}

Business logic is buried in plumbing, and forgetting one rollback corrupts data. A proxy moves that plumbing into one place.

What the proxy does, step by step

  1. You annotate placeOrder with @Transactional and write only the business lines.
  2. At startup the auto-proxy creator sees the annotation and replaces the bean with a proxy.
  3. A caller invokes orderService.placeOrder(o): it really calls the proxy.
  4. The proxy runs its interceptor chain: begin transaction, then call the real method, then commit, or roll back if a runtime exception escaped.
// roughly what the generated proxy does
Object invoke(Method m, Object[] args) {
    TransactionStatus tx = txManager.getTransaction(def);
    try { Object r = target.placeOrder(args); txManager.commit(tx); return r; }
    catch (RuntimeException e) { txManager.rollback(tx); throw e; }
}

Because one mechanism serves many features, the same pattern appears everywhere: @Cacheable checks a cache before calling, @Async submits the call to an executor and returns immediately, @PreAuthorize checks permissions first.

Consequences to remember: final classes and methods (CGLIB), private methods, self-calls and objects not created by Spring are not advised; and getClass() on an injected bean returns the proxy class. Debug trick: AopUtils.isAopProxy(bean) or look at the class name containing $$.

Remember: the annotation is not magic on my class; a proxy around it does the work, and only calls through the proxy count.

What is the difference between JDK dynamic proxies and CGLIB proxies? Intermediate

A JDK dynamic proxy implements the interfaces of the target and forwards calls, so it needs at least one interface. CGLIB creates a subclass of the target class at runtime, so it needs no interface but cannot proxy final classes or final methods. Spring Boot defaults to CGLIB (spring.aop.proxy-target-class=true); plain Spring uses a JDK proxy when the bean has interfaces.

The type consequence is the classic error: with a JDK proxy, injecting the concrete class (OrderServiceImpl) fails with "class $Proxy123 cannot be cast to ...Impl", because the proxy is an interface implementation, not a subclass. Inject the interface, or use CGLIB. CGLIB proxies also need a non-private, non-final target, and since Spring 4 they do not call the constructor twice. In both cases only calls through the proxy are advised.

How each is built

JDK proxy: java.lang.reflect.Proxy.newProxyInstance(loader, new Class[]{Pay.class}, handler) generates a class at runtime that implements Pay; every method call goes to handler.invoke(...), which adds advice and forwards to the target.

CGLIB: generates a subclass of the target (class name like PayService$$SpringCGLIB$$0) and overrides every non-final public/protected/package method to call the interceptors first. Spring repackages CGLIB inside spring-core, and uses Objenesis to create the instance without running the constructor again.

Why Boot defaults to CGLIB

With JDK proxies, injecting the concrete class fails, which confused many users. CGLIB works whether or not an interface exists, so behaviour is consistent. If you want JDK proxies, set spring.aop.proxy-target-class=false and inject interfaces.

Classic failure modes

  • class jdk.proxy2.$Proxy45 cannot be cast to ...Impl: JDK proxy plus concrete-class injection.
  • Kotlin classes are final by default; use the kotlin-spring (allopen) plugin so CGLIB can subclass them.
  • A final method on a CGLIB proxy runs on the proxy object itself with its fields uninitialised, so it may see null dependencies. This is a nasty NPE that only shows with proxies.

Remember: JDK proxy = implements the interface; CGLIB = subclasses the class. Final breaks CGLIB; the missing interface breaks JDK.

Explain the AOP terms: aspect, join point, pointcut, advice, weaving. Give a pointcut example. Basic

An aspect is a module holding cross-cutting logic such as logging or auditing. A join point is a place where it can apply (in Spring AOP, always a method call). A pointcut is the expression that selects which join points. Advice is the code that runs there. Weaving is linking the aspect to the target, which Spring does at runtime with proxies.

Pointcut designators I use: execution (by method signature), within (by type), @annotation (methods carrying an annotation) and bean (by bean name). I prefer annotation-based pointcuts, since the code that gets extra behaviour is visibly marked. Good uses are audit logging, timing and metrics, tenant or correlation-id context, and permission checks. I keep business rules out of aspects, because the flow becomes invisible to a reader. Avoid pointcuts like "every method of every bean": they cost performance, and logging every argument may leak personal data.

@Aspect @Component
class AuditAspect {
    @Around("@annotation(audited)")
    Object audit(ProceedingJoinPoint pjp, Audited audited) throws Throwable {
        long t = System.nanoTime();
        try { return pjp.proceed(); }
        finally { log.info("{} took {} ns", pjp.getSignature(), System.nanoTime() - t); }
    }
}

Judgement

What are the advice types, and in what order do they run? Intermediate

There are five: @Before, @AfterReturning, @AfterThrowing, @After (always, like finally) and @Around, which wraps the call and decides whether to proceed. When several aspects apply, @Order decides: the lower number is the outer layer, so it runs first on the way in and last on the way out.

Within one aspect, since Spring 5.2.7 the precedence is Around, Before, After, AfterReturning, AfterThrowing. So on the way out, AfterReturning or AfterThrowing run before After. @Around is the most powerful but easy to misuse: forget to call proceed() and the target never runs; catch and swallow an exception and the caller never sees it. This ordering matters in practice: a transaction aspect must sit outside a retry aspect, or each retry would reuse an already broken transaction.

@Around("@annotation(Retry)")

    for (int i = 0; ; i++) {

        catch (TransientException e) { if (i == 2) throw e; }
    }
}

Choosing: use the weakest advice that works. @Before for a check, @AfterReturning to publish a metric, @Around only when you must control the call (timing, retry, caching, try/catch). Weak advice cannot break the call by accident.

Order, concretely

With @Order(1) Security and @Order(2) Tx, a call runs: Security-before, Tx-before, method, Tx-after, Security-after. The transaction opens after the security check, and closes before security's "after" code. Getting this wrong has real effects: if retry is inside the transaction aspect, a retry reuses a transaction that is already marked rollback-only; if the transaction is inside retry, each attempt gets a fresh one. For @Transactional the order is set via @EnableTransactionManagement(order = ...); the default is lowest precedence (innermost).

Without @Order, the order between different aspects is undefined, so never rely on it.

Remember: lower @Order is the outer layer. Around wraps everything and must call proceed().

Why does @Transactional (or @Async, @Cacheable) not work when a method calls another method in the same class? Intermediate

Because the advice lives in the proxy, and a call from inside the class never goes through the proxy. Other beans hold OrderService$$Proxy. When placeOrder() runs, this is the real object, so this.audit() is a plain Java call and the annotation on audit() is ignored. The best fix is to move the method into another bean and inject it.

Other fixes, in order of preference: use TransactionTemplate in the method; inject a self-reference (with @Lazy) or use AopContext.currentProxy() with exposeProxy = true, which works but is ugly; or switch to AspectJ weaving, which changes the bytecode so internal calls are advised too, at the price of build setup. The same applies to private methods (they cannot be advised), to @PostConstruct (the proxy is not created yet), and to objects created with new.

Reproduce it

@Service
class OrderService {
    public void placeOrder(Order o) {       // no @Transactional here
        save(o);                            // this.save(o): NO transaction!
    }
    @Transactional
    public void save(Order o) { repo.save(o); ... }
}

A controller calls orderService.placeOrder(o) via the proxy, but there is nothing to advise on placeOrder, so the call just reaches the real object. Inside, save is called on this (the raw target), and the proxy is bypassed. The failure is silent: no error, but no transaction, no cache, and it runs on the same thread for @Async.

Fixes in code

// 1. Split into two beans (best): the call now crosses a proxy
@Service class OrderService {
    private final OrderWriter writer;
    public void placeOrder(Order o) { writer.save(o); }
}
@Service class OrderWriter { @Transactional public void save(Order o) {...} }

// 3. Annotate the entry method instead: put @Transactional on placeOrder itself
// 4. Self-injection (works, smells)

The simplest honest fix is often option 3: put the annotation on the public method that outsiders call, because the boundary of a business operation is usually that method anyway.

Related silent failures: @Transactional on a private or package-private method under certain proxy modes, on a method of a bean created with new, or on a final method with CGLIB. Detect them with a test that asserts rollback behaviour, or enable logging.level.org.springframework.transaction.interceptor=TRACE to see whether a transaction is actually created.

Remember: the proxy guards the front door only. this.method() uses the side door.

What are the limits of Spring AOP, and when would you use AspectJ instead? Senior

Spring AOP is proxy-based, so it advises only method calls that arrive through a proxy on Spring beans. It cannot advise private methods, self-calls, final classes or methods under CGLIB, objects created with new, constructors, field access or static methods. AspectJ changes the bytecode (at compile time, post-compile, or load time), so it can advise any join point on any object.

I stay with Spring AOP in nearly all applications. I would move to AspectJ only to advise non-Spring objects such as domain entities, to cover self-invocation, or when a measured proxy overhead matters. The price is a special compiler or Java agent, longer builds and harder debugging.

5. Transactions with @Transactional

How does @Transactional work internally? Intermediate

Spring wraps the bean in a proxy. When a transactional method is called through the proxy, a TransactionInterceptor asks the PlatformTransactionManager to begin a transaction: it takes a connection from the pool, turns off auto-commit and binds the connection to the current thread. My method then runs, and every repository or JdbcTemplate call on that thread reuses the same connection. On normal return it commits; on a matching exception it rolls back; then it releases the connection.

The binding is done with ThreadLocals in TransactionSynchronizationManager, so a transaction belongs to one thread, and a new thread has no transaction. The interceptor reads the attributes (propagation, isolation, timeout, read-only, rollback rules). With JPA, flush happens at commit or before a query that needs it, which is why constraint violations often appear at commit time, outside my try/catch. With two data sources, define two transaction managers and name one: @Transactional("orderTm").

What a transaction is, and what problem this solves

A transaction groups several database changes into "all or nothing". Moving 100 from account A to B is two updates; if the second fails, the first must be undone. In plain JDBC you do setAutoCommit(false), run the statements on one connection, then commit() or rollback(). The hard part in layered code is making the repository calls inside a service all use that same connection without passing it around as a parameter.

Step by step

  1. A caller calls service.transfer(a, b, 100); it reaches the proxy.
  2. TransactionInterceptor reads the @Transactional attributes and asks the transaction manager: getTransaction(definition).
  3. The manager (for JDBC, DataSourceTransactionManager; for JPA, JpaTransactionManager) borrows a connection from the pool, sets auto-commit to false and stores it in a ThreadLocal via TransactionSynchronizationManager, keyed by the DataSource.
  4. Your method runs. JdbcTemplate, JPA and Spring Data call DataSourceUtils.getConnection(ds), which first checks that ThreadLocal and returns the same connection.
  5. Normal return: the manager commits (for JPA, flushes first). Exception matching the rollback rules: rollback. Either way the connection is unbound and returned to the pool.
@Transactional
public void transfer(long from, long to, BigDecimal amt) {
    accounts.debit(from, amt);     // same connection
    accounts.credit(to, amt);      // same connection; if this throws, debit is undone
}

Consequences worth stating

  • One thread, one transaction. Another thread (an executor, @Async) has no binding, so it does its own thing.
  • Constraint violations may surface at commit. JPA batches SQL until flush, so the exception can be thrown when the proxy commits, after your try/catch has exited. Call flush() if you need it earlier.
  • The connection is held for the whole method. Long methods drain the pool.
  • Multiple databases need a named manager per datasource: @Transactional("ordersTm"). One @Transactional does not span two databases.

Interviewers often follow with: "What if I call the method from the same class?" (no proxy, see the proxy chapter) and "which exceptions roll back?" (next questions).

Remember: proxy, interceptor, transaction manager, connection in a ThreadLocal. Commit on return, rollback on matching exception.

Explain the transaction propagation levels. Intermediate

Propagation says what to do when a transactional method is called and a transaction may already exist. The default is REQUIRED: join the current one, or create one if none exists. REQUIRES_NEW suspends the current transaction and starts an independent one. The others are rare: SUPPORTS, NOT_SUPPORTED, MANDATORY, NEVER and NESTED.

Real uses: REQUIRES_NEW for an audit record that must survive even if the main work rolls back; NOT_SUPPORTED for a slow report that should not hold a transaction open; MANDATORY on a method that must never be called alone. Danger with REQUIRES_NEW: the inner transaction takes a second pooled connection while the outer still holds one, so under load it can exhaust the pool or deadlock on a row the outer transaction locked.

The question propagation answers

Service A is transactional and calls service B, which is also transactional. Should B be part of A's transaction, or separate? That choice is propagation.

The two you must know

REQUIRED (default). B joins A's transaction. There is one real transaction; if B throws a runtime exception, it marks the shared transaction rollback-only, so A cannot commit even if it catches the exception. A later commit attempt gives UnexpectedRollbackException.

REQUIRES_NEW. B suspends A's transaction (unbinds A's connection), opens a second connection and transaction, commits it, and then A resumes. Use it when B's outcome must not depend on A:

@Service class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String event) { auditRepo.save(new Audit(event)); }  // survives A's rollback
}

@Service class PaymentService {
    @Transactional
    public void pay(Order o) {
        audit.record("pay started");   // committed immediately
        charge(o);                      // throws -> pay() rolls back, audit row stays
    }
}

Remember self-invocation: if record is in the same class, the annotation is ignored. It must be another bean.

The rest, in one sentence each

  • SUPPORTS: use a transaction if there is one, otherwise run without (read-only helpers).
  • NOT_SUPPORTED: always run without a transaction, suspending any existing one (long report that should not hold locks).
  • MANDATORY: must be called inside a transaction, else exception (a method that is wrong to call alone).
  • NEVER: must not be in a transaction, else exception.
  • NESTED: savepoint inside the current transaction (see next question).

Production pitfalls

REQUIRES_NEW in a loop or deep in call chains needs one extra connection per level. With a pool of 10 and 10 requests that each hold an outer connection and wait for a second one, every thread waits and none can progress: a pool-exhaustion deadlock. Keep pool size above (max concurrent requests x connections per request), or avoid REQUIRES_NEW on hot paths. Also, propagation is applied by the proxy, so it follows the same "only through the proxy" rule.

Remember: REQUIRED joins, REQUIRES_NEW is independent (and needs a second connection).

What is the difference between REQUIRES_NEW and NESTED? Senior

REQUIRES_NEW is a completely separate transaction on its own connection. It commits or rolls back independently, even if the outer transaction later rolls back. NESTED runs inside the outer transaction using a database savepoint: if the inner part fails, only the work since the savepoint is undone and the outer can continue, but if the outer rolls back, the nested work goes too.

So REQUIRES_NEW is for "this must survive no matter what" (an audit row). NESTED is for "try this part, and fall back if it fails" within one unit of work. NESTED needs savepoint support through JDBC, so it works cleanly with DataSourceTransactionManager. With JPA it is shaky, because the persistence context can still hold entities from the failed part, so I would not rely on it.

A savepoint, explained

A savepoint is a bookmark inside one database transaction. ROLLBACK TO sp1 undoes only the statements after the bookmark; everything before it stays pending in the same transaction.

BEGIN;
INSERT order ...;
SAVEPOINT sp1;                 -- NESTED begins
INSERT loyalty_points ...;     -- fails
ROLLBACK TO sp1;               -- only the loyalty insert is undone
COMMIT;                        -- order insert still commits

For which exceptions does @Transactional roll back? What about checked exceptions? Intermediate

By default only for unchecked exceptions (RuntimeException and subclasses) and Error. A checked exception such as IOException or my own extends Exception does not roll back, and the transaction commits. I change this with rollbackFor = Exception.class on the annotation, or make my domain exceptions unchecked.

The default copies the old EJB idea that a checked exception is a recoverable business outcome. A second common reason for "no rollback": I caught the exception inside the method and swallowed it, so the proxy never saw an exception. Rethrow it, or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly(). And even a caught exception from a joined (REQUIRED) inner call has already marked the shared transaction rollback-only.

@Transactional(rollbackFor = Exception.class)
public void pay(Order o) throws PaymentException { ... }

@Transactional
public void bad() {
    try { repo.save(x); } catch (Exception e) { log.warn("ignored", e); } // commits
}

Why checked exceptions commit

The default follows the EJB convention: an unchecked exception means "the system broke, give up", whereas a checked exception is part of the method's contract, a business outcome the caller may handle ("insufficient funds"). Many teams disagree and make everything roll back.

Three ways it bites in practice

// 1. Checked exception: row stays committed
@Transactional
void a() throws IOException { repo.save(x); throw new IOException(); }   // COMMITS

// 2. Swallowed exception: proxy never sees it
@Transactional
void b() { try { repo.save(x); riskyCall(); } catch (Exception e) { log.error("x", e); } }  // COMMITS

// 3. Joined inner call threw: outer is poisoned
@Transactional void outer() {
    try { inner.work(); }           // inner is REQUIRED, throws RuntimeException
    catch (RuntimeException e) {}   // outer thinks it is fine...
}                                   // ...commit fails: UnexpectedRollbackException

Controlling the rules

  • rollbackFor = Exception.class: roll back on any exception.
  • noRollbackFor = NotFoundException.class: commit even though it is a RuntimeException.
  • Set a module-wide habit: make business exceptions extend RuntimeException, and keep rollbackFor only for exceptions you do not control.
  • Programmatic: TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() when you handled the error but still want a rollback.

Also note: rollback happens only when the exception leaves the transactional method. A test that does @Transactional on the test class rolls back at the end by default, which can hide commit-time failures (deferred constraints, flush errors); use @Commit or flush explicitly when you test that.

Remember: rolls back on RuntimeException and Error only. Checked or swallowed exceptions commit.

What are the isolation levels and the problems they prevent? Intermediate

Isolation controls what a transaction sees from concurrent ones. A dirty read sees uncommitted data. A non-repeatable read gets different values for the same row on two reads. A phantom read gets a different set of rows for the same range query. READ_COMMITTED stops dirty reads, REPEATABLE_READ also stops non-repeatable reads, and SERIALIZABLE stops all three at a high cost.

The default is the database's own: typically READ_COMMITTED in PostgreSQL, Oracle and SQL Server, and REPEATABLE_READ in MySQL InnoDB. In Spring, @Transactional(isolation = ...) applies only when a new transaction begins and is ignored when joining an existing one. For most business code I stay on the default and protect specific updates with optimistic locking (@Version) or SELECT ... FOR UPDATE. See the SQL databases page for locking.

What does @Transactional(readOnly = true) actually do? Intermediate

It is an optimisation hint, not a guard. With Hibernate, Spring sets the flush mode to manual, so Hibernate skips dirty checking and the final flush, which saves CPU and memory. Spring also marks the JDBC connection read-only, which some drivers and databases use to reject writes or to route the query to a read replica.

It does not reliably block writes, and it is ignored if the method joins an outer read-write transaction. It also does not change visibility; for a consistent snapshot across several reads you need the right isolation. My habit: readOnly = true at class level on query services, overridden by plain @Transactional on write methods. Spring Data's repositories do the same.

What happens, layer by layer

  1. Spring: marks the transaction definition read-only and exposes it via TransactionSynchronizationManager.isCurrentTransactionReadOnly().
  2. JPA/Hibernate: Spring sets FlushMode.MANUAL (or the equivalent), so no automatic flush at commit and no dirty-check pass over every loaded entity. With thousands of loaded entities this is a measurable saving. Hibernate may also skip snapshot copies of read-only entities, saving memory.
  3. JDBC: calls connection.setReadOnly(true). Drivers react differently: PostgreSQL sends SET TRANSACTION READ ONLY (writes fail); MySQL Connector/J can route to a replica when configured; some drivers ignore it.

Use it for what it is

@Service
@Transactional(readOnly = true)          // default for the class: queries
class OrderQueries {
    List<OrderDto> recent() {...}

    @Transactional                       // override for the one write method
    void markSeen(long id) {...}
}

Pitfalls: (a) a readOnly method that calls a write method in the same transaction sees a read-only connection, so the write may fail or silently not flush; (b) readOnly on an inner method that joins an outer read-write transaction is ignored; (c) with a read replica and replication lag, a read-only call right after a write may not see that write, so route carefully; (d) it does not provide a stable snapshot across statements: that depends on isolation, not on read-only.

Remember: readOnly is a performance hint (no dirty checking), not a security feature.

Where should @Transactional go: interface or class, controller or service, public or private? Intermediate

On the service layer: one business use case, one transaction. Not on controllers, because the transaction would then stay open during JSON serialisation and rendering. Not on repositories, because separate repository calls would not share a unit of work. Put it on the concrete class, on public methods; it never works on private methods.

Annotations on an interface only work with interface-based proxies, so the class is safer. For class-based proxies Spring 6 also honours protected and package-visible methods; I would still use public to stay portable. Keep transactions short. A remote call, file upload or long computation inside the transaction holds a database connection and row locks the whole time. Do the slow work first, then open a short transaction for the write.

The rule: a transaction is a business operation

"Place order" = save order + reserve stock + record payment: all or nothing. That operation is a service method, so the transaction boundary is the service method. Everything below (repositories) joins it; everything above (controller) stays outside.

When would you use TransactionTemplate instead of the annotation? Intermediate

When only part of a method should be transactional, or when the proxy limits get in the way. TransactionTemplate wraps a block of code in a transaction in plain Java, so it works for self-invocation and private methods, and it lets me decide rollback in code with status.setRollbackOnly().

Typical cases: call a remote API first, then open a short transaction for the database write; or a batch loop that commits every N items. The cost is more verbose code with transaction handling mixed into business logic. I use the annotation for ordinary services and the template for these two cases.

Result r = http.call();                       // no transaction yet

How do @Transactional and @Async or other threads interact? Senior

A transaction belongs to one thread. If a transactional method hands work to another thread (@Async, an executor, CompletableFuture.supplyAsync), that work runs outside the caller's transaction. It cannot see the caller's uncommitted rows, a rollback of the caller does not undo it, and it gets its own transaction only if its own method is transactional.

A typical bug: the caller inserts a row and fires an async task, which looks the row up and does not find it because the caller has not committed yet. Fix it by starting the async work only after commit, using @TransactionalEventListener(phase = AFTER_COMMIT) that triggers it, and pass IDs or immutable DTOs to the other thread, never managed entities. The security context and request attributes are ThreadLocal too and are not carried over.

Why: the connection lives in a ThreadLocal

The transaction state is stored per thread. A pool thread running an @Async method starts with an empty ThreadLocal, so it has no transaction, no security context and no request attributes, unless something copies them over (like DelegatingSecurityContextExecutor, or a TaskDecorator).

The race condition, step by step

@Transactional
public void register(User u) {
    users.save(u);                       // INSERT not yet committed
    notifier.sendWelcomeAsync(u.getId());// runs on another thread NOW
}                                        // commit happens only here

@Async
public void sendWelcomeAsync(long id) {
    User u = users.findById(id).orElseThrow();   // may fail: row not committed yet
}

Timeline: T0 save, T1 async thread starts, T2 async thread queries (row invisible to its connection), T3 caller commits. The async thread can win the race, so the bug appears only under load. The mirror problem: caller rolls back at T3, but the email was already sent.

Correct designs

  1. Publish an event and handle it with @TransactionalEventListener(phase = AFTER_COMMIT), which then calls the async method.
  2. Pass IDs or immutable DTOs, not entity objects. A managed entity is tied to a persistence context that belongs to the first thread; using it from another thread causes lazy-loading failures and races.
  3. Give the async method its own transaction (@Transactional on it, in another bean) if it writes data.
  4. For parallel work inside one transaction (rare), you cannot share the connection safely across threads; redesign.

Same issue for parallel streams, CompletableFuture and @Scheduled: no inherited transaction or request context. Java 21 virtual threads do not change this; they are still separate threads.

Remember: new thread, new world: no transaction, no security context, no request. Trigger it after commit and pass plain data.

How do you run code only after a transaction commits, for example sending an email or a Kafka message? Senior

I publish a Spring event inside the transaction and handle it with @TransactionalEventListener, whose default phase is AFTER_COMMIT. The listener runs only if the commit succeeded. If I sent the email inside the transactional method and the transaction later rolled back, the outside world would already have a lie.

At AFTER_COMMIT the original transaction is finished, so a database write in the listener needs its own transaction (REQUIRES_NEW), otherwise it is not committed. There is still a gap: a crash between commit and send loses the message. For reliable delivery I use the transactional outbox: write the message to an outbox table in the same transaction, and let a poller or CDC publish it. See the microservices page.

@Transactional void place(Order o) {
    repo.save(o);
    events.publishEvent(new OrderPlaced(o.getId()));   // plain data
}
@TransactionalEventListener          // AFTER_COMMIT by default
void on(OrderPlaced e) { mailer.send(e.id()); }

The problem: side effects are not rolled back

A database change can be undone, an email or a Kafka message cannot. If you send them before the commit, there are two bad outcomes: the transaction rolls back and customers have an email for an order that does not exist, or the consumer receives the message and queries the database before the commit and finds nothing.

@TransactionalEventListener phases

Details: if there is no active transaction when the event is published, the listener does not run at all (unless fallbackExecution = true). In AFTER_COMMIT, the transaction is complete but its resources may still be bound, so a repository write there will not be committed; mark the listener method @Transactional(propagation = REQUIRES_NEW) if it must write. Exceptions in an AFTER_COMMIT listener cannot roll back the finished transaction; they are logged.

The remaining gap, and the outbox

If the process crashes after commit but before the listener runs, the message is lost. The outbox pattern closes that gap:

  1. In the same transaction, insert the business row and an outbox row ("OrderPlaced", payload).
  2. A relay (a scheduled poller, or CDC like Debezium) reads unsent outbox rows, publishes them and marks them sent.
  3. Delivery is at least once, so consumers de-duplicate by message ID.

Choose AFTER_COMMIT for low-stakes notifications, the outbox when losing a message is not acceptable.

Remember: side effects after commit. For no lost messages, use the outbox.

What is Open Session In View, and why is it controversial? Senior

With Open Session In View (OSIV) the JPA session stays open for the whole web request, including JSON rendering, so lazy associations load in the controller or serializer without LazyInitializationException. Spring Boot turns it on by default (spring.jpa.open-in-view=true) and logs a warning. I turn it off and fetch exactly what each use case needs in the service.

The problems: the database connection is held until the response is written, so slow clients or serialisation drain the pool; lazy loading in the view hides N+1 queries running outside the service's transaction; and persistence concerns leak into the web layer. With it off, use fetch joins, @EntityGraph or DTO projections, and return DTOs. See the Hibernate and JPA page.

What goes wrong without it

@Transactional(readOnly = true)
public Order load(long id) { return orders.findById(id).get(); }   // tx ends here

// controller serialises it:
order.getItems().size();     // items are LAZY -> LazyInitializationException: no Session

Once the service method returns, the transaction and, without OSIV, the Hibernate session close. Touching a lazy collection after that fails. OSIV is a request-wide interceptor (OpenEntityManagerInViewInterceptor) that keeps the EntityManager open until the response is complete, so lazy loads still work outside the service. It is on by default in Boot, which logs "spring.jpa.open-in-view is enabled by default".

Why it is a trap

  • Connection held longer than needed. Lazy loading in the view takes a connection from the pool during rendering; a slow client keeps it. Under load: pool exhausted, requests queue.
  • Hidden N+1. Serialising 100 orders each lazy-loading its items runs 101 queries in the web layer, each in auto-commit mode, outside any service transaction.
  • Unclear boundaries. Data access happens in the controller or in Jackson, so you cannot reason about which queries a use case triggers.

Doing it without OSIV

spring.jpa.open-in-view=false

@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(long id);             // fetch what the use case needs
// or @EntityGraph, or a DTO projection: select new OrderDto(o.id, o.total) ...

Return DTOs from services. Then the controller cannot trigger any database access at all. Trade-off: you must think about fetching up front; the benefit is predictable queries and connection use.

Remember: OSIV hides lazy-loading bugs and holds connections. Turn it off, return DTOs.

How do you handle a transaction that spans a database and a message broker, or two services? Senior

I avoid distributed (XA, two-phase commit) transactions and design for eventual consistency instead. Database plus broker: the transactional outbox. Several services: a saga, which is a sequence of local transactions, each followed by an event, with a compensating action per step if a later step fails. Every consumer must be idempotent, since delivery is at least once.

A Spring @Transactional covers one resource manager, usually one database. XA through a JTA manager is slow, hard to operate and unsupported by many modern brokers and cloud databases. State the trade-off clearly in an interview: you give up atomicity across systems and accept temporary inconsistency in return for availability and simpler operations.

Why one @Transactional cannot do it

Spring commits one resource manager. With a database plus Kafka there are two systems: whichever commits first can succeed while the other fails, leaving them inconsistent ("dual write problem").

@Transactional
void placeOrder(Order o) {
    repo.save(o);                 // DB commit happens after the method returns...
    kafka.send("orders", o);      // ...so Kafka may have the message, DB may roll back (or reverse)
}

Option 1: transactional outbox (DB + broker)

Write the order and an outbox row in one local transaction. A relay publishes outbox rows to the broker. Atomicity comes from the database only; the broker publish is retried until it succeeds (at-least-once).

Option 2: saga (several services)

A business process is split into local transactions, each publishing an event that triggers the next step. If a step fails, previously completed steps are undone by compensating actions (not rollbacks): cancel the reservation, refund the payment.

StyleHow steps are triggeredGood forDrawback
Choreographyeach service reacts to eventsfew steps, loose couplingflow is hard to see
Orchestrationa coordinator tells each service what to domany steps, clear statecoordinator is a new component

Example: Order created, Payment charged, Stock reserved. If stock fails, Payment gets "refund". Between steps, the system is visibly inconsistent (order "pending"), so design the UI and states for that.

Why not XA / two-phase commit

2PC makes all participants lock resources until a coordinator decides; if the coordinator dies in between, locks stay held ("in doubt" transactions). It lowers availability and throughput, and many brokers and cloud databases do not support it. It is acceptable in a closed system with two XA-capable resources (a JMS broker and a DB under a JTA manager like Atomikos or Narayana), but it is rarely the right default.

Always make consumers idempotent: store processed message IDs, or use natural idempotency (upsert by key).

Remember: outbox for DB plus broker, saga for services, idempotent consumers. Avoid XA.

6. Spring MVC

Walk me through what happens to an HTTP request in Spring MVC. Intermediate

The servlet container passes the request through the filters, then to the single DispatcherServlet, the front controller. It asks the HandlerMapping which controller method matches the URL and HTTP method. Interceptors run preHandle, a HandlerAdapter resolves the method arguments (path variables, @RequestBody through a message converter, @Valid) and calls my method. The return value is written out, as JSON by Jackson for a @RestController, or as a view for a classic @Controller.

On the way back: interceptor postHandle and afterCompletion, then the filters, then the client. If anything throws, HandlerExceptionResolvers take over, which is where @ExceptionHandler and @ControllerAdvice live. Knowing this order explains most bugs: security filters reject before the DispatcherServlet, so @ControllerAdvice never sees those errors.

One request, numbered, with a concrete call

Example: POST /orders with JSON, handled by @PostMapping("/orders") create(@Valid @RequestBody CreateOrder b).

  1. Tomcat parses HTTP and runs the filter chain (security, CORS, request logging).
  2. DispatcherServlet.doDispatch receives it. It asks each HandlerMapping (RequestMappingHandlerMapping) "who handles POST /orders?" and gets a HandlerExecutionChain: the controller method plus the matching interceptors.
  3. Interceptors' preHandle run in order. Returning false stops the request.
  4. The RequestMappingHandlerAdapter prepares arguments with HandlerMethodArgumentResolvers: @RequestBody uses a message converter (Jackson) to build CreateOrder, @Valid triggers validation. A failure here throws before your code runs.
  5. Your method runs and returns a value.
  6. A HandlerMethodReturnValueHandler handles it: for @ResponseBody, a message converter writes JSON and sets Content-Type; for a view name, a ViewResolver renders a template.
  7. postHandle, then afterCompletion (always, even on error), then the filters unwind in reverse and the response is sent.
  8. If any step throws, HandlerExceptionResolvers try @ExceptionHandler methods, @ResponseStatus, then the default resolver; if unhandled, the container's error page (/error in Boot).

What is the difference between @Controller and @RestController? Basic

@RestController is @Controller plus @ResponseBody on every method. With plain @Controller, a returned String is treated as a view name (for Thymeleaf or JSP). With @RestController, the return value is written straight into the response body by an HttpMessageConverter, usually as JSON.

Use @RestController for APIs and @Controller for server-rendered pages. Return ResponseEntity<T> when you need to control status code and headers.

Two return-value behaviours

@Controller
class PageController {
    @GetMapping("/home") String home(Model m) { m.addAttribute("user", u); return "home"; } // renders template home.html
    @GetMapping("/api/ping") @ResponseBody String ping() { return "pong"; }                  // body text "pong"
}

@RestController                  // = @Controller + @ResponseBody on every method
class OrderApi {
    @GetMapping("/orders/{id}") Order get(@PathVariable long id) {...}                      // JSON body
    @PostMapping("/orders") ResponseEntity<Order> create(@RequestBody CreateOrder b) {
        Order o = service.create(b);
        return ResponseEntity.created(URI.create("/orders/" + o.id())).body(o);             // 201 + Location
    }
}

What ResponseEntity adds

Returning a plain object gives 200 and the body. ResponseEntity<T> lets you set the status, headers (Location, ETag, Cache-Control) and body together. For fixed statuses you can instead annotate with @ResponseStatus(HttpStatus.CREATED).

A typical bug: a @Controller method returning a String or object for an API call, which makes Spring try to find a view called that string and fails with a 404 or "Circular view path". Switching to @RestController fixes it.

Return DTOs, not JPA entities, from either, so a database change does not silently change the API and lazy fields do not get serialised by accident.

Remember: RestController = Controller + ResponseBody. Return value is the body, not a view name.

@RequestParam, @PathVariable, @RequestBody, @ModelAttribute, @RequestHeader: what is each for? Basic

@PathVariable reads a part of the URL path (/orders/{id}). @RequestParam reads a query string or form parameter (?page=2). @RequestBody converts the request body, usually JSON, into an object. @RequestHeader reads a header. @ModelAttribute binds form fields or query parameters onto an object field by field.

Details that get asked: @RequestParam is required by default and accepts required = false or defaultValue. @RequestBody can be used once per method, because the body stream is read once. Add @Valid next to it to trigger validation. Binding errors give 400 Bad Request: a wrong type becomes MethodArgumentTypeMismatchException, unreadable JSON becomes HttpMessageNotReadableException.

How does Spring MVC turn JSON into objects and back, and how does content negotiation work? Intermediate

It uses HttpMessageConverters. For @RequestBody, Spring looks at the request Content-Type and picks a converter that can read it, for JSON a Jackson converter. For the response it looks at the Accept header and the types the method can produce, and picks a converter that can write it. If nothing fits you get 415 Unsupported Media Type (cannot read the body) or 406 Not Acceptable (cannot produce what the client wants).

Mappings can narrow this with consumes and produces. The Jackson ObjectMapper can be customised, in Boot through Jackson2ObjectMapperBuilderCustomizer or spring.jackson.* properties, for date formats and unknown-field behaviour. A class that cannot be deserialised (no default constructor, wrong field names) gives a 400, not a 500.

Two directions, two headers

  • Reading a request body: Content-Type: application/json tells Spring the body's format. It walks the list of HttpMessageConverters and uses the first whose canRead(type, mediaType) is true (MappingJackson2HttpMessageConverter for JSON). No match: 415.
  • Writing the response: Accept: application/json says what the client wants. Spring computes the producible types for the return value, intersects with Accept (with quality values like q=0.8) and picks a converter. No overlap: 406.
@PostMapping(value = "/orders", consumes = "application/json", produces = "application/json")
Order create(@RequestBody CreateOrder b) {...}

// Typical failures
// Content-Type: text/plain on a JSON endpoint           -> 415
// Accept: application/xml but only Jackson JSON present -> 406
// Body {"qty": "abc"} for int qty                       -> 400 (HttpMessageNotReadableException)

How does validation work in Spring MVC with Bean Validation? Intermediate

I put constraint annotations (@NotBlank, @Size, @Email) on the request object and add @Valid on the controller parameter. Before my method runs, Spring validates it and, on failure, throws MethodArgumentNotValidException, which I turn into a 400 with field messages in a @RestControllerAdvice.

For path variables and request parameters, put @Validated on the controller class and constraints on the parameters; this throws ConstraintViolationException (Spring 6.1 adds built-in method validation that reports HandlerMethodValidationException). Use @Validated with groups for different rules on create and update, and write custom constraints for business rules. Validation of the shape belongs at the edge; rules that need the database (is this email unique?) belong in the service. Never trust the client-side check.

record CreateUser(@NotBlank String name, @Email String email, @Min(18) int age) {}

@PostMapping("/users")
User create(@Valid @RequestBody CreateUser body) {...}

The flow

  1. Constraints on the object describe valid data.
  2. @Valid on @RequestBody makes the argument resolver run the Validator after deserialising.
  3. Violations produce MethodArgumentNotValidException holding a BindingResult with one FieldError per problem.
  4. Your advice converts it to a response.
record CreateUser(@NotBlank @Size(max = 50) String name,
                  @Email String email,
                  @Min(18) @Max(120) int age) {}

@RestControllerAdvice
class Errors extends ResponseEntityExceptionHandler {          // handles it as a 400 by default
    @Override protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders h, HttpStatusCode s, WebRequest r) {
        Map<String,String> fields = new LinkedHashMap<>();
        ex.getFieldErrors().forEach(f -> fields.put(f.getField(), f.getDefaultMessage()));
        return ResponseEntity.badRequest().body(Map.of("errors", fields));
    }
}

How do you handle exceptions globally in Spring MVC? Intermediate

I write one @RestControllerAdvice class with @ExceptionHandler methods. Each maps an exception type to a status and a consistent error body. That keeps controllers free of try/catch and gives every client the same error shape. Since Spring 6, ProblemDetail gives a standard error body (the RFC 7807 problem format; newer versions follow its successor, RFC 9457).

The most specific handler wins. A catch-all Exception handler returns 500 and logs the stack trace, without leaking internals to the client. For my own exceptions I can also use @ResponseStatus on the class. Remember that this machinery only sees exceptions thrown inside the DispatcherServlet. Errors from security filters (401, 403) or from earlier filters never reach @ControllerAdvice; for those use the security entry point and access-denied handler.

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(OrderNotFound.class)
    ProblemDetail notFound(OrderNotFound e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
}

Without it, and with it

    try { return ok(service.get(id)); }
    catch (OrderNotFound e) { return status(404).body("not found"); }
}

// With: controllers just throw
@GetMapping("/orders/{id}") Order get(@PathVariable long id) { return service.get(id); }
@RestControllerAdvice
class GlobalErrors {
    @ExceptionHandler(OrderNotFound.class)
    ProblemDetail notFound(OrderNotFound e) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        p.setTitle("Order not found");
        return p;
    }
    @ExceptionHandler(DataIntegrityViolationException.class)
    ResponseEntity<ProblemDetail> conflict(...) { ... 409 ... }

    @ExceptionHandler(Exception.class)                       // safety net

        log.error("Unhandled", e);                            // full detail in logs
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");
    }
}

How Spring picks a handler

  1. First the controller's own @ExceptionHandler methods, then the advice classes (ordered by @Order).
  2. Within them, the closest match in the exception class hierarchy wins.
  3. If none, ResponseStatusExceptionResolver (for @ResponseStatus or ResponseStatusException) and then DefaultHandlerExceptionResolver (maps standard MVC exceptions to 400, 404, 405, 415...).
  4. Still unhandled: the servlet container's error handling, in Boot BasicErrorController at /error.

Practical points: extend ResponseEntityExceptionHandler to get consistent handling of Spring's own exceptions; enable spring.mvc.problemdetails.enabled=true in Boot for RFC format on those; log once at the handler, with a correlation ID, and return the same ID in the body so support can find it; never put stack traces or SQL messages in the response (information leak); and in the 5xx case do not echo exception messages.

Remember: one @RestControllerAdvice, specific handlers, no stack traces to clients. Filters bypass it.

What is the difference between a servlet Filter, a HandlerInterceptor and AOP? Intermediate

They sit at different layers. A servlet Filter works on the raw HTTP request, before the DispatcherServlet, and knows nothing about controllers. A HandlerInterceptor runs inside Spring MVC around the chosen controller method, so it knows which handler will run. AOP wraps any Spring bean method call and has no idea about HTTP at all.

Use a filter for things that must apply to every request, such as security, request-ID logging, compression and rate limiting (OncePerRequestFilter guarantees one run per request). Use an interceptor for per-handler web logic, such as locale or tenant resolution. Use AOP for service-layer concerns such as audit and timing. Filter order is set by @Order or a registration bean; interceptors run in registration order.

How do you design a good REST endpoint in Spring MVC: status codes, idempotency, pagination? Intermediate

Use nouns in URLs and HTTP methods for the action. Return the right status: 201 Created with a Location header for a new resource, 204 when there is nothing to return, 400 for bad input, 404 for unknown, 409 for conflicts. GET, PUT and DELETE are idempotent (repeating them has the same effect), POST is not, so I support an Idempotency-Key header for payments and similar. Large lists are paged with a size limit.

Pagination: offset paging (page and size, Spring Data Pageable) is simple but slows down on deep pages and shifts when data changes. Keyset (cursor) paging, which asks for rows after the last seen key, is stable and fast for big or fast-changing data. Never return entities directly; return DTOs so the API does not change when the database model does. Version the API and use one error format for all failures. More on API design is on the microservices page.

7. HTTP clients and reactive basics

RestTemplate, WebClient and RestClient: how do they differ, and which should I use? Intermediate

RestTemplate is the older blocking client, now in maintenance mode. WebClient (from Spring WebFlux) is non-blocking and reactive, though it can also be used blockingly. RestClient (Spring 6.1) is the modern blocking client with a fluent API like WebClient. For new blocking code I use RestClient; I use WebClient when the code is reactive or I need streaming or many parallel calls.

Whatever the client, production needs configuration. Always set connect and read timeouts: the defaults can wait forever, and one slow downstream then ties up all my threads. Add retries only for idempotent calls and with backoff and a cap, and consider a circuit breaker (Resilience4j) so a failing dependency fails fast. Build the client from a shared builder bean so tracing, metrics and auth headers are applied consistently. Declarative @HttpExchange interfaces (Spring 6) can replace hand-written client code.

RestClient client = RestClient.builder().baseUrl("https://pay.example.com").build();
Payment p = client.get().uri("/payments/{id}", id).retrieve().body(Payment.class);

// RestClient (blocking, Spring 6.1+, fluent)

// WebClient (non-blocking, returns a Mono; nothing happens until subscribed)
Mono<Payment> m = webClient.get().uri("/payments/{id}", id).retrieve().bodyToMono(Payment.class);

What is reactive programming and Spring WebFlux? When would you pick it over Spring MVC? Intermediate

Spring MVC uses one thread per request, and that thread waits (blocks) while it does I/O. WebFlux uses a few event-loop threads that never block: when a call waits for I/O, the thread moves on to other requests and comes back when the data is ready. Code is written with Mono (zero or one value) and Flux (a stream of values). I pick WebFlux for very high concurrency with mostly waiting, streaming, or fully non-blocking stacks. For ordinary CRUD services I stay on MVC.

The catch: the whole path must be non-blocking, including the database driver (R2DBC, not JDBC), or one blocking call stalls the event loop for everyone. Reactive code is also harder to write, read and debug, and stack traces are less helpful. Since Java 21, virtual threads let plain blocking MVC code scale to many concurrent requests, which removes much of the reason to go reactive (Boot 3.2 and later can switch them on with spring.threads.virtual.enabled=true). Nothing runs until something subscribes, and calling .block() on an event-loop thread is a classic mistake.

The idea: do not park a thread while waiting

A blocking request spends most of its life waiting: for the database, a remote service, a disk. With 200 threads, only 200 requests can be waiting at once. In an event-loop model, a thread starts the I/O, registers a callback, and goes to serve something else. When data arrives, any free thread continues the work. So a handful of threads can juggle thousands of idle-waiting connections.

Mono and Flux in practice

// Mono<T>: 0 or 1 item. Flux<T>: 0..N items. They are recipes, not results.
Mono<OrderView> view(long id) {
    return orders.findById(id)                                  // R2DBC, returns Mono<Order>
        .zipWith(customers.findByOrder(id))                     // both lookups run concurrently
        .map(t -> new OrderView(t.getT1(), t.getT2()))
        .timeout(Duration.ofSeconds(2))
        .switchIfEmpty(Mono.error(new OrderNotFound(id)));
}
// Nothing ran yet. The framework subscribes when the HTTP response is written.

Costs you pay

  • Whole chain non-blocking. JDBC, JPA/Hibernate, Thread.sleep, blocking file I/O all block the event loop. Wrap unavoidable blocking in Schedulers.boundedElastic(). Tools like BlockHound detect accidental blocking calls in tests.
  • Context loss. ThreadLocals (security context, MDC, transactions) do not follow a reactive pipeline; you use the Reactor Context.
  • Harder debugging. Stack traces show operators, not your call chain; Hooks.onOperatorDebug() or checkpoints help.
  • Back-pressure: subscribers tell the publisher how much they can take, which prevents a fast producer overwhelming a slow consumer. That is a real benefit for streaming.

When to pick which, honestly

Do not choose it for speed on CPU-bound work: reactive does not make a single request faster; it increases how many wait concurrently on few threads.

Remember: MVC = a thread per request, WebFlux = few threads and no blocking. Do not mix blocking calls into reactive code.

8. Data access: exceptions, Spring Data and pools

What is DataAccessException, and why does Spring translate exceptions? Intermediate

Spring wraps technology-specific errors (SQLException, Hibernate and JPA exceptions) into its own unchecked DataAccessException hierarchy. That means my service code does not depend on JDBC or Hibernate, I do not need try/catch for checked exceptions, and I can handle meaningful cases such as DuplicateKeyException or DataIntegrityViolationException the same way on any database.

The translation is done for @Repository beans (a post-processor adds it), for JdbcTemplate, and for Spring Data repositories. Also remember that being unchecked, these exceptions trigger rollback by default. With JPA, many constraint errors only appear at flush or commit, not at save().

The problem it solves

Different technologies report the same failure differently. A duplicate email gives SQLException with SQLState 23505 on PostgreSQL, error code 1062 on MySQL, a ConstraintViolationException in Hibernate, a PersistenceException in JPA. Without translation, your service code would test vendor codes.

How it works

  • JdbcTemplate maps the SQLException using a SQLExceptionTranslator (checks SQLState, then vendor error code tables).
  • For JPA/Hibernate, a PersistenceExceptionTranslationPostProcessor wraps @Repository beans in a proxy that translates after each call.
  • Spring Data repositories are covered automatically.
try {
    users.save(new User(email));
    users.flush();                              // forces the INSERT now (see below)
} catch (DataIntegrityViolationException e) {   // same type on Postgres, MySQL, Oracle
    throw new EmailAlreadyUsed(email);
}

How do Spring Data repositories work? Where does the implementation come from? Intermediate

I declare an interface that extends JpaRepository<Entity, Id> and write no implementation. At startup Spring Data creates a proxy for it. Basic methods (save, findById) are delegated to a shared implementation, SimpleJpaRepository. For methods like findByEmailAndStatus it parses the method name into a query when the application starts, and a name it cannot parse fails the startup.

For anything more complex I use @Query (JPQL or native), the Specification API for dynamic filters, or projections to fetch only the columns I need. Repository methods are transactional by default (reads are read-only), but calling several of them from a service is not one transaction unless the service is transactional. A common trap is returning entities from a service with lazy fields into the web layer; return DTOs.

interface OrderRepo extends JpaRepository<Order, Long> {
    List<Order> findByCustomerIdAndStatus(long customerId, Status status);
    @Query("select o from Order o where o.total > :min")
    List<Order> big(@Param("min") BigDecimal min);
}

What Spring Data does at startup

  1. It scans for interfaces extending Repository (@EnableJpaRepositories, auto-on in Boot).
  2. For each, a RepositoryFactoryBean creates a JDK proxy that implements the interface.
  3. The proxy's target is SimpleJpaRepository (CRUD, paging, sorting), plus interceptors for query methods.
  4. For every declared method, a QueryLookupStrategy finds a query: first an explicit @Query or named query, else it parses the method name.

How does a connection pool relate to Spring, and how do you size it? Intermediate

Opening a database connection is expensive, so a pool (HikariCP is the Boot default) keeps a set of open connections and lends them out. A @Transactional method borrows one connection for its whole duration. So the number of requests doing database work at once is capped by the pool size, and the rest wait up to the connection timeout (30 seconds by default in Hikari).

I keep the pool small. Hikari's default maximum is 10, and a few dozen is usually enough. A bigger pool often just moves the queue to the database and makes things worse. The sizing guidance from Hikari's wiki is roughly cores times two plus the number of disks, then tune with a load test. Watch active versus pending connections as metrics. The common pool-exhaustion causes are long transactions (a remote call inside @Transactional), leaked connections and REQUIRES_NEW holding two connections.

Why a pool, and what a borrow looks like

Opening a connection means TCP, TLS and authentication: tens of milliseconds. A pool does it once and reuses connections.

  1. @Transactional method starts: the manager calls dataSource.getConnection(), which hands out an idle pooled connection (or waits).
  2. All repository calls in the method reuse it.
  3. On commit/rollback the connection returns to the pool (it is not closed).

Without @Transactional, a repository call borrows a connection for just that statement (auto-commit). With Open Session In View, a connection can be held across the web request.

Sizing: why bigger is often worse

The database can do real work on only about as many connections as it has cores and disks; more just fight for CPU, locks and cache. If the app has 50 instances x 20 connections, the database sees 1000 connections and thrashes.

Capacity math: if an average transaction holds a connection for 20 ms, one connection supports about 50 transactions per second; a pool of 10 supports roughly 500 per second. If a transaction wrongly holds a connection for 500 ms because of a remote call inside it, the same pool supports only 20 per second.

spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=10          # fixed-size pool is recommended
spring.datasource.hikari.connection-timeout=3000  # fail fast instead of waiting 30s
spring.datasource.hikari.max-lifetime=1740000     # a bit less than DB/infra timeout
spring.datasource.hikari.leak-detection-threshold=20000   # log stack of borrowers held 20s

Diagnosing exhaustion

Symptom: Connection is not available, request timed out after 30000ms and rising response times. Check metrics hikaricp.connections.active, .pending, .usage. Causes, in order of likelihood: long transactions or remote calls inside them, connection leaks (manual JDBC not closed), REQUIRES_NEW nesting, a traffic spike with a pool too small, a slow query. A thread dump shows many threads waiting in HikariPool.getConnection while others sit in your transactional code.

Remember: pool size caps concurrent database work. Keep it small and keep transactions short.

9. Events, @Async, @Scheduled and caching

How do Spring application events work? Are they asynchronous? Intermediate

A component calls ApplicationEventPublisher.publishEvent(event) and any bean with an @EventListener method for that type receives it. By default this is synchronous: the listener runs on the publisher's thread, inside the publisher's transaction, and an exception in the listener propagates back to the publisher.

That makes events a good way to decouple modules (order placed, then send mail, update stats) while keeping one thread and one transaction. To run asynchronously, annotate the listener with @Async (needs @EnableAsync) and remember it then loses the transaction and security context. To run only after a successful commit, use @TransactionalEventListener. Events are in-process only; they are not a message broker and are lost on a crash.

What it looks like

record OrderPlaced(long orderId) {}                    // any object can be an event

@Service class OrderService {
    private final ApplicationEventPublisher events;
    @Transactional public void place(Order o) {
        repo.save(o);
        events.publishEvent(new OrderPlaced(o.getId()));   // returns after ALL listeners ran
    }
}

@Component class MailListener {
    @EventListener void on(OrderPlaced e) { mail.sendConfirmation(e.orderId()); }
}
@Component class StatsListener {
    @EventListener @Async void on(OrderPlaced e) { stats.increment(); }   // other thread
}

Why use events

Without events, OrderService would call the mailer, the stats service and the loyalty service directly, so it depends on all of them and grows each time you add a reaction. With events the publisher knows nothing about the listeners (open/closed principle), and modules can be separated.

Behaviour you must know

Built-in lifecycle events are useful hooks too: ContextRefreshedEvent, ApplicationReadyEvent (Boot, app ready for traffic), ContextClosedEvent.

Choosing: in-process decoupling, same transaction: plain events. Side effects only if the data was committed: @TransactionalEventListener. Cross-service or must survive crashes: a broker plus an outbox.

Remember: events are synchronous by default and in-process. For after-commit use @TransactionalEventListener; for durability use a broker.

How does @Async work, and what are its pitfalls? Intermediate

With @EnableAsync, a proxy intercepts calls to @Async methods and runs them on a TaskExecutor thread, returning immediately. The method should return void or a CompletableFuture. I always configure a bounded ThreadPoolTaskExecutor explicitly, because without one the fallback may create an unbounded number of threads (plain Spring's default is SimpleAsyncTaskExecutor, which starts a new thread per task).

Pitfalls: it is proxy-based, so calling an async method from the same class runs synchronously. Exceptions from a void method are lost unless I set an AsyncUncaughtExceptionHandler; with a CompletableFuture they surface in the future. The new thread has no transaction, no security context and no request scope. A full queue and pool lead to rejected tasks, so choose the queue size and rejection policy deliberately.

@Bean TaskExecutor mailExecutor() {
    var ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4); ex.setMaxPoolSize(8); ex.setQueueCapacity(100);
    ex.setThreadNamePrefix("mail-"); return ex;
}
@Async("mailExecutor") public CompletableFuture<Void> send(Mail m) {...}

What happens on a call

  1. @EnableAsync registers a post-processor that wraps beans having @Async methods in a proxy.
  2. A caller invokes mailer.send(m) on the proxy.
  3. The proxy packages the call as a task and submits it to the executor, then returns at once (null for void, or an incomplete CompletableFuture).
  4. A pool thread later runs the real method; the result completes the future.
@Async("mailExecutor")
public CompletableFuture<SendResult> send(Mail m) {
    return CompletableFuture.completedFuture(client.deliver(m));   // runs on mail-1, mail-2 ...
}
// caller
var f = mailer.send(m);              // returns immediately
f.thenAccept(r -> log.info("sent {}", r)).exceptionally(t -> { log.error("fail", t); return null; });

The executor decides everything

A ThreadPoolTaskExecutor works like ThreadPoolExecutor: it first fills core threads, then queues tasks, and only when the queue is full does it add threads up to max; beyond that it rejects. Hence with core=4, max=8, queue=100 the pool stays at 4 threads until 100 tasks wait. Common mistake: expecting max threads to grow before the queue fills.

SettingWhy it matters

Pitfalls, each with its fix

  • Self-invocation: same proxy rule as transactions; move the method to another bean.
  • Lost exceptions in void methods: implement AsyncConfigurer.getAsyncUncaughtExceptionHandler(), or return a future.
  • No context in the new thread: transaction, security context, MDC, request attributes. Use a TaskDecorator to copy MDC and security context, or pass the data in arguments.
  • Race with the caller's transaction: start it after commit (see the after-commit question).
  • Boot defaults: Boot auto-configures an applicationTaskExecutor, but a named, bounded one of your own is clearer. With virtual threads enabled, it uses them.
  • Ordering: tasks do not run in submit order across several threads.

Remember: own bounded executor, no self-calls, no lost exceptions, and no transaction or security context in the new thread.

How does @Scheduled work, and what goes wrong with it? Intermediate

With @EnableScheduling, Spring runs annotated methods on a scheduler by fixedRate (every N ms from start), fixedDelay (N ms after the last run ends) or cron. By default there is a single scheduler thread, so a slow job delays every other scheduled job. And in a cluster, every instance runs the job, so a nightly job runs twice with two instances.

For one run across a cluster I use a lock such as ShedLock (a lock row in the database or Redis) or an external scheduler, and make the job idempotent. An exception in a task is logged and the schedule continues, but it may go unnoticed, so I add alerting. Give the scheduler a bigger pool if there are several long jobs, and give cron an explicit time zone.

The three timing modes

@Scheduled(fixedRate = 60_000)                       // start every 60 s (overlap possible if slow, single thread: queues)
@Scheduled(fixedDelay = 60_000, initialDelay = 5000) // wait 60 s after the previous run ENDS
@Scheduled(cron = "0 30 2 * * *", zone = "UTC")      // sec min hour day month weekday: 02:30 UTC daily

Time line for fixedRate=10s with a 4 s job: starts at 0, 10, 20. For fixedDelay=10s: 0 to 4, then 14 to 18, then 28... Use fixedDelay when runs must never overlap.

Three production problems

1. One thread. Boot uses a scheduler with a pool size of one by default. A 10-minute job blocks a 1-second heartbeat job. Configure spring.task.scheduling.pool.size or a ThreadPoolTaskScheduler.

2. Every instance runs it. With 3 pods, an invoice job generates 3 invoices. Options:

ApproachNotes
ShedLockLibrary: before running, take a named lock row (DB, Redis, ZooKeeper) with lockAtMostFor and lockAtLeastFor. Simple. Needs tuning so a crashed pod does not hold the lock for too long.
Leader electionOnly the leader schedules (Kubernetes lease, ZooKeeper).
External schedulerKubernetes CronJob, Quartz in clustered mode, or a workflow engine. Better for heavy or critical jobs.
Idempotent job bodySafe even if it runs twice: process "unbilled" rows with a status update, using SELECT ... FOR UPDATE SKIP LOCKED.

3. Silent failure. Exceptions are logged and the next run proceeds; nobody notices a job that fails nightly. Add metrics (last success timestamp) and alerts.

Other gotchas: @Scheduled methods take no arguments and return void; cron is evaluated in the server's time zone unless you set zone (daylight-saving shifts can skip or repeat a run); long jobs should respect shutdown (check an interrupt flag). For anything needing persistence, retries or a UI, use Quartz or Spring Batch rather than @Scheduled.

Remember: one thread by default, and every instance runs the job. Lock it with ShedLock.

How does the Spring cache abstraction work? Intermediate

With @EnableCaching, a proxy intercepts calls to @Cacheable methods. It builds a key from the arguments, returns the cached value if present and otherwise calls the method and stores the result. @CacheEvict removes entries and @CachePut always runs the method and updates the cache. The actual store (Caffeine, Redis, ConcurrentMap) is plugged in behind a CacheManager.

Points to know. Being proxy-based, self-invocation and private methods are not cached. The default key is built from all arguments, so write a custom key when the arguments include large or unstable objects. The default simple in-memory store has no expiry or size limit; use Caffeine or Redis with a TTL. Several instances with a local cache can hold different values, so a shared cache or short TTLs are needed. Use unless to skip caching nulls and sync = true to stop many threads computing the same missing key. Caching and consistency are covered on the Redis and caching page.

@Cacheable(cacheNames = "customer", key = "#id", unless = "#result == null")
public Customer find(long id) {...}
@CacheEvict(cacheNames = "customer", key = "#c.id")
public void update(Customer c) {...}

How a call flows

@Service class CustomerService {
    @Cacheable(cacheNames = "customer", key = "#id", unless = "#result == null", sync = true)
    public Customer find(long id) { return repo.findById(id).orElse(null); }   // runs only on a miss

    @CachePut(cacheNames = "customer", key = "#result.id")      // always runs, stores result
    public Customer update(Customer c) { return repo.save(c); }

    @CacheEvict(cacheNames = "customer", key = "#id")           // removes the entry
    public void delete(long id) { repo.deleteById(id); }
}
  1. Call hits the proxy; the cache interceptor builds the key (SpEL or default from arguments).
  2. Look up key in the cache from the CacheManager.
  3. Hit: return, the method body is skipped. Miss: call the method, store the result, return it.

Choosing a provider

StoreGood forNotes
Caffeine (local)fast per-instance cachesize and TTL via spring.cache.caffeine.spec=maximumSize=10000,expireAfterWrite=10m; each instance has its own copy
Redis (shared)consistent across instancesnetwork hop; set TTL (spring.cache.redis.time-to-live); values must be serialisable
ConcurrentMap (default fallback)testsunbounded, no expiry: memory leak in production

Pitfalls an interviewer expects

  • Stale data: any update path that bypasses the annotated methods (a SQL script, another service) leaves old values. TTLs bound the staleness.
  • Self-invocation: no proxy, no caching.
  • Caching entities or mutable objects: a caller mutates the cached object in place, and everyone sees it (local caches). Cache immutable DTOs.
  • Cache stampede: many threads miss at once and all hit the database; sync = true serialises per key within one instance.
  • Caching null or errors: use unless; decide deliberately about negative caching.
  • Transactions: a cache write can happen and then the transaction rolls back; evicting after commit or using TransactionAwareCacheManagerProxy avoids that.
  • Key design: default key uses all params; include tenant ID in the key in multi-tenant code, or entries leak across tenants.

Remember: proxy plus key plus CacheManager. Set a TTL, and self-calls bypass the cache.

10. Spring Security essentials

How does Spring Security work? Explain the filter chain. Intermediate

Spring Security is a chain of servlet filters that runs before the DispatcherServlet. A single entry filter (DelegatingFilterProxy, then FilterChainProxy) picks the SecurityFilterChain whose matcher fits the request, and the filters in it do the work in order: load the security context, CORS, CSRF, authenticate (form, basic, bearer token), turn on anonymous access, translate security exceptions, and finally check authorization.

Because all of this happens in filters, a rejected request never reaches my controller, and @ControllerAdvice never sees the error. The ExceptionTranslationFilter decides the response: not authenticated leads to the AuthenticationEntryPoint (401, or a redirect to the login page), authenticated but not allowed leads to the AccessDeniedHandler (403). I can define several SecurityFilterChain beans, for example one stateless chain for /api/** and one session-based chain for the web UI. To see the exact filter list, turn on debug logging for org.springframework.security.

How the chain gets into the servlet container

The servlet container only knows servlet filters. Spring Security registers one filter, springSecurityFilterChain (DelegatingFilterProxy in plain Spring, registered by Boot automatically), which forwards to FilterChainProxy. That object owns a list of SecurityFilterChains, each with a request matcher. The first chain that matches the request runs its filters.

A request walked through

GET /api/orders   Authorization: Bearer eyJ...

1. SecurityContextHolderFilter       load/empty context (stateless: always empty)
2. CorsFilter                        answer preflight, add CORS headers
3. CsrfFilter                        (disabled for this stateless chain)
4. BearerTokenAuthenticationFilter   validate JWT -> Authentication stored in the SecurityContext
5. AnonymousAuthenticationFilter     only if nobody authenticated
6. ExceptionTranslationFilter        wraps the next one: turns exceptions into 401 / 403
7. AuthorizationFilter               "/api/orders" requires authenticated -> ok
-> DispatcherServlet -> controller

If step 4 finds no token and step 7 refuses an anonymous user, it throws AccessDeniedException. Step 6 catches it, sees the user is anonymous, and calls the AuthenticationEntryPoint: 401 (or a redirect to /login for form login). If the user was authenticated but lacked a role, it calls the AccessDeniedHandler: 403.

Practical uses

  • Multiple chains: annotate with @Order and give each a securityMatcher: stateless JWT for /api/**, form login + sessions for the rest.
  • Custom filter: add with http.addFilterBefore(apiKeyFilter, UsernamePasswordAuthenticationFilter.class). Watch out: if your filter is also a @Component, Boot registers it a second time in the servlet chain; either do not make it a bean or add a FilterRegistrationBean that disables it.
  • Debug: @EnableWebSecurity(debug = true) (never in prod) or logging.level.org.springframework.security=DEBUG prints which filters ran and why a request was denied.
  • Static resources / health checks: prefer permitAll() in the chain over ignoring them completely.

Pitfall: custom JSON error bodies for 401/403 must be produced by the entry point and denied handler, since @ControllerAdvice is not involved.

Remember: filters in front of MVC. Entry point gives 401, access-denied handler gives 403. Controller advice never sees them.

What is the difference between authentication and authorization, and between 401 and 403? Basic

Authentication is proving who you are (password, token). Authorization is deciding what you may do once known. Failed authentication gives 401 Unauthorized, which really means "unauthenticated". Authenticated but not allowed gives 403 Forbidden. I remember it as: 401, I do not know you; 403, I know you and the answer is no.

In Spring terms, the principal is the logged-in user, authorities are the permissions, and roles are authorities with a ROLE_ prefix. hasRole("ADMIN") checks the authority ROLE_ADMIN, while hasAuthority("ADMIN") checks exactly ADMIN, a common mix-up. Note also that an anonymous user hitting a protected URL gets 401 (or a login redirect) and not 403.

Definitions with a movie-theatre picture

Authentication is showing your ticket at the door (who are you, and is it valid). Authorization is which rooms the ticket lets you into (VIP lounge or not). One happens first; the other depends on it.

What happens inside Spring Security when a user logs in with username and password? Senior

The login filter (UsernamePasswordAuthenticationFilter for forms) builds an unauthenticated Authentication token and hands it to the AuthenticationManager. The manager (a ProviderManager) asks its AuthenticationProviders. The usual DaoAuthenticationProvider calls my UserDetailsService to load the user, checks the password with the PasswordEncoder, and returns a fully authenticated token with authorities. The result is stored in the SecurityContext, which is kept in the HTTP session for session-based apps.

On later requests, the SecurityContext is restored from the session (or rebuilt from the token on stateless APIs), and it lives in a ThreadLocal via SecurityContextHolder for that request. To plug in my own user store I implement UserDetailsService. To support a different credential, such as an API key, I add a custom filter or provider. Failures throw AuthenticationException subclasses, which become a 401 or redirect.

How should you store passwords, and what is PasswordEncoder? Intermediate

Never store plain text, and never use a fast hash such as MD5 or plain SHA. Store a slow, salted, one-way hash made by a PasswordEncoder: BCryptPasswordEncoder is the common choice, with Argon2 and SCrypt as alternatives. At login the encoder hashes the supplied password and compares, using matches().

A slow hash makes brute-forcing stolen hashes expensive, and a per-password random salt, built into the stored string, stops rainbow tables. PasswordEncoderFactories.createDelegatingPasswordEncoder() stores the algorithm as a prefix like {bcrypt}, so I can upgrade the algorithm later without breaking existing users. Add rate limiting or lockout on the login endpoint, and never log passwords.

Why plain hashes are not enough

  • Plain text: one database leak exposes every password, and users reuse them elsewhere.
  • Fast hash (MD5, SHA-256): a GPU computes billions per second, so common passwords fall in minutes.
  • Unsalted hash: identical passwords give identical hashes, and precomputed "rainbow tables" crack them in bulk.

The fix is a deliberately slow function with a built-in random salt and a tunable work factor.

How do you secure a REST API with JWT, using Spring as an OAuth2 resource server? Senior

The user logs in at an authorization server (Keycloak, Okta and so on) and gets a signed JWT. The client sends it as Authorization: Bearer .... My Spring API is the resource server: it validates the signature using the server's public keys (fetched from a JWKS URL and cached), plus expiry and issuer, and turns the token's claims into an Authentication. The API keeps no session and never sees the password.

Configuration is one property, spring.security.oauth2.resourceserver.jwt.issuer-uri, plus oauth2ResourceServer(o -> o.jwt(...)) in the chain. I map claims such as scope or roles to authorities with a JwtAuthenticationConverter. Typical answers a senior should give: keep access tokens short-lived and use refresh tokens; JWTs cannot be revoked before expiry (so use short lifetimes or a deny list); never put sensitive data in a JWT, since it is only signed, not encrypted; and check the aud (audience) and iss claims. The response codes: 401 for a missing or invalid token, 403 for a valid token lacking scope or role.

What a JWT is

A JSON Web Token has three base64 parts: header.payload.signature. The payload holds claims such as sub (user id), iss (issuer), aud (intended audience), exp (expiry), scope. The authorization server signs header+payload with its private key. Anyone with the public key can verify that nobody changed it, but the payload is only encoded, not encrypted: anyone can read it.

What the Spring resource server does on each request

  1. BearerTokenAuthenticationFilter extracts the token from the Authorization header.
  2. JwtDecoder parses it, verifies the signature using a key from the JWKS endpoint (fetched once, cached, refreshed when an unknown kid appears), and validates exp, nbf and iss.
  3. A JwtAuthenticationConverter turns claims into authorities. By default scope becomes SCOPE_....
  4. An Authentication is placed in the context and authorization rules run as usual.
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://idp.example.com/realms/acme

@Bean JwtAuthenticationConverter jwtAuthConverter() {
    var gr = new JwtGrantedAuthoritiesConverter();
    gr.setAuthoritiesClaimName("roles");     // Keycloak/Okta custom claim
    gr.setAuthorityPrefix("ROLE_");
    var c = new JwtAuthenticationConverter();
    c.setJwtGrantedAuthoritiesConverter(gr);
    return c;
}

@Bean JwtDecoder decoder() {                 // add audience check
    var d = (NimbusJwtDecoder) JwtDecoders.fromIssuerLocation(issuer);
    d.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        JwtValidators.createDefaultWithIssuer(issuer), audienceValidator("orders-api")));
    return d;
}

Opaque tokens versus JWT

If you need instant revocation, use opaque tokens and let the resource server call the authorization server's introspection endpoint on each request (or cache it briefly); the price is a network call. JWTs trade revocation for speed.

Things that go wrong

  • Accepting alg: none or the wrong algorithm; use the library decoder, never hand-parse.
  • Skipping the audience check, so a token for another API is accepted here.
  • Clock skew between servers (the default tolerance is 60 seconds).
  • Storing JWTs in browser local storage, where an XSS bug can steal them.
  • Using the ID token as an access token; they have different audiences and purposes.

Remember: verify signature, expiry, issuer and audience. Stateless, short-lived tokens, no secrets inside.

Which OAuth2 grant types matter, and what are the roles? Intermediate

The roles are: the resource owner (the user), the client (the app), the authorization server (issues tokens) and the resource server (my API). The grant I use for user logins in web and mobile apps is the authorization code flow with PKCE. For service-to-service calls with no user, I use client credentials. The old implicit and password grants are deprecated and should be avoided.

In the authorization code flow the user logs in at the authorization server, which redirects back with a short-lived code. The client exchanges that code for tokens on a back channel; PKCE adds a one-time secret so a stolen code is useless, which makes it safe for public clients such as single-page and mobile apps. OAuth2 is about authorization (delegated access); OpenID Connect adds an ID token on top for authentication, i.e. "who is this user".

The roles with a concrete example

"Print my photos" app wants to read photos from "PhotoCloud". You (resource owner) allow it. Print app = client. PhotoCloud's login/consent server = authorization server. PhotoCloud's photo API = resource server. The client never sees your PhotoCloud password.

Authorization code flow with PKCE, step by step

  1. Client generates a random code_verifier and sends code_challenge = SHA256(verifier) in the redirect to the authorization server.
  2. User logs in and consents on the authorization server's own page.
  3. Server redirects back to the client with a short-lived code.
  4. Client calls the token endpoint over a back channel with the code and the original code_verifier.
  5. Server checks the verifier matches the earlier challenge, then issues an access token (and optionally a refresh token and an OIDC ID token).

PKCE (Proof Key for Code Exchange) means a thief who steals the code in the redirect cannot redeem it without the verifier. It is now recommended even for confidential clients.

In Spring: oauth2Login() for a client app, oauth2ResourceServer() for an API, and WebClient with an OAuth2 filter for client-credentials calls.

What is method security, and how does @PreAuthorize work? Intermediate

Method security puts access rules on service methods, not only on URLs. With @EnableMethodSecurity, @PreAuthorize("...") is checked before the method runs, using a SpEL expression that can use roles, the logged-in user and the method arguments. If the check fails, it throws AccessDeniedException, which becomes a 403. It works through a proxy, like @Transactional.

The strength over URL rules is checking ownership: the URL says which user, the expression compares with the current principal, which prevents users reading each other's data (broken object-level authorization is a top API risk). Because it is proxy-based, self-invocation skips it, and private methods are not covered. Use @PostAuthorize to check the returned object. I still keep coarse rules at the URL level as a first layer.

@PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")
public Profile load(long userId) {...}

Why URL rules are not enough

A URL rule says "authenticated users may call GET /accounts/{id}". It cannot say "only the owner of account {id}". If user 7 requests /accounts/8, the URL rule passes. Checking the object's owner is the real defence against broken object-level authorization (IDOR), consistently in the top API risks.

The annotations

@EnableMethodSecurity                      // enables @PreAuthorize, @PostAuthorize, @PreFilter, @PostFilter

@PreAuthorize("hasAuthority('orders:read')")
List<Order> all() {...}

@PreAuthorize("#userId == authentication.principal.id or hasRole('ADMIN')")
Profile load(long userId) {...}

@PostAuthorize("returnObject.owner == authentication.name")      // check after loading
Order get(long id) {...}

@PreAuthorize("@perm.canEdit(authentication, #docId)")           // call your own bean for complex rules
void edit(long docId) {...}

How it works

A proxy (like transactions) invokes an AuthorizationManager before the method. It evaluates the SpEL expression with authentication, the method arguments (#name, compile with -parameters) and, for post-checks, returnObject. A false result throws AccessDeniedException, handled like any other 403. The security context must be present on the calling thread.

Use it well

  • Layer it: coarse URL rules at the edge, @PreAuthorize on service methods that touch sensitive data.
  • Keep expressions short; move logic into a named bean method so it is unit-testable.
  • Put it on the service layer, since the same service may be called by controllers, jobs or messaging.
  • Pitfalls: self-invocation, private methods and classes without a proxy are not protected; @PostAuthorize runs after side effects, so do not use it on write methods; and test with at least a wrong-user case.
  • Better for collections: query by owner in SQL (where owner = :user) instead of loading everything and filtering with @PostFilter.

Remember: URL rules for coarse access, @PreAuthorize for per-object rules. It is proxy-based, so no self-calls.

What is CSRF, and when do you turn it off? Intermediate

Cross-Site Request Forgery tricks a logged-in user's browser into sending a request to my site from a malicious page, and the browser attaches the session cookie automatically. Spring Security defends with a CSRF token that must come back with each state-changing request, which a forged page cannot read. I turn CSRF off only for stateless APIs that authenticate with a header token (such as a bearer JWT), because the browser does not attach that header by itself.

If the app uses cookie-based sessions (or a token in a cookie), keep CSRF on. A SameSite cookie attribute is a useful extra layer but not a full replacement. Disabling CSRF "to make POST work" on a session-based app is a real vulnerability, so first find out why the POST fails (usually the token is missing in the request).

The attack, step by step

  1. You are logged in at bank.com; your browser stores a session cookie.
  2. You open evil.com, which has a hidden form: POST https://bank.com/transfer?to=attacker&amount=1000, submitted by script.
  3. The browser sends that POST with your bank.com cookie attached automatically.
  4. The bank sees a valid session and executes the transfer.

The attacker cannot read the response, but does not need to: the side effect is the goal.

The defence: a token the attacker cannot know

The server issues a random CSRF token tied to the session. The page includes it in forms or a header (X-CSRF-TOKEN). On each POST/PUT/DELETE/PATCH the server compares. evil.com cannot read the token from bank.com (same-origin policy), so its forged request lacks it and is rejected with 403. Safe methods (GET, HEAD, OPTIONS) are not checked, which is why a state-changing GET is a bug.

// Stateless API using Authorization: Bearer: no ambient credential, so CSRF can be disabled

    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));

What is CORS, and why does a preflight request fail with 401 or 403? Intermediate

CORS (Cross-Origin Resource Sharing) is a browser rule: a page from one origin may call another origin only if that server allows it with response headers. For "non-simple" requests (JSON POST, an Authorization header) the browser first sends an OPTIONS preflight, with no credentials. If Spring Security rejects that OPTIONS request before CORS headers are added, the browser reports a CORS error even though the real cause is 401 or 403.

The fix is to enable CORS in the security chain, http.cors(Customizer.withDefaults()), with a CorsConfigurationSource bean that lists allowed origins, methods and headers, so the CORS filter answers the preflight before authentication. @CrossOrigin on a controller alone is not enough, because the request is rejected earlier in the filter chain. Do not combine allowCredentials(true) with a * origin; list the origins. Also note CORS is enforced by browsers only: it is no protection against curl or other servers.

The same-origin policy, and what CORS relaxes

An origin is scheme + host + port. A page from https://app.example.com cannot read responses from https://api.example.com unless the API says it may. The API says so with Access-Control-Allow-Origin and related headers. This protects users' browsers, not your server: the request still reaches the server and curl ignores CORS.

Simple versus preflighted requests

A "simple" request (GET/POST with basic headers and form content types) is sent directly. A JSON POST, a PUT/DELETE, or any request with Authorization triggers a preflight:

OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type
   -> must answer 200 with Access-Control-Allow-Origin / -Methods / -Headers, no auth needed

POST /orders   (the real call, only sent if the preflight allowed it)

If the preflight returns 401/403 or lacks headers, the browser console shows "blocked by CORS policy". People then wrongly hunt in CORS config, when the real problem is the security chain rejecting the unauthenticated OPTIONS.

Fix in Spring Security

http.cors(Customizer.withDefaults());       // uses the CorsConfigurationSource bean

@Bean CorsConfigurationSource cors() {
    var c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("https://app.example.com"));
    c.setAllowedMethods(List.of("GET","POST","PUT","DELETE"));
    c.setAllowedHeaders(List.of("Authorization","Content-Type"));
    c.setAllowCredentials(true);            // cookies; then origin must NOT be "*"
    c.setMaxAge(3600L);                     // browser caches the preflight
    var s = new UrlBasedCorsConfigurationSource();
    s.registerCorsConfiguration("/api/**", c);
    return s;
}

Pitfalls: @CrossOrigin or MVC addCorsMappings alone fail if Security rejects first; duplicated CORS headers when a gateway also adds them; and exposing custom response headers needs setExposedHeaders. Better still, serve the front end and API from the same origin (reverse proxy) and avoid CORS entirely.

Remember: the preflight carries no token, so CORS must be handled in the security chain before authentication.

How does Spring Security know the current user, and what happens in other threads? Senior

The authenticated user is stored in a SecurityContext held by SecurityContextHolder, which by default is a ThreadLocal. So SecurityContextHolder.getContext().getAuthentication() works anywhere on the request thread. A new thread (@Async, an executor) starts with an empty context, so the user appears as anonymous or missing.

Fixes: set the holder strategy to MODE_INHERITABLETHREADLOCAL (works only for threads created from the request thread, not pooled ones), or better, wrap the executor with DelegatingSecurityContextExecutor or DelegatingSecurityContextAsyncTaskExecutor, which copy the context into each task. Often the cleanest design is to read the user once and pass the user id into the async method explicitly. The request thread's context is cleared at the end of the request, so never keep it in a static field.

Where the "current user" lives

SecurityContextHolder uses a ThreadLocal strategy by default. At the start of a request, a filter puts the SecurityContext (holding the Authentication) into it; at the end, it is cleared. Everything on that thread, controllers, services, @PreAuthorize, auditing code, can call SecurityContextHolder.getContext().getAuthentication(). In controllers you can also simply take Authentication, Principal or @AuthenticationPrincipal as a parameter, which is easier to test.

Session-based security versus stateless token security: what are the trade-offs? Intermediate

Session-based: the server stores the logged-in state and the browser holds a session id cookie. My rule: server-rendered web app with a browser, use sessions; public API, mobile clients or many services, use short-lived tokens with refresh tokens. Where to keep a token in a browser is its own trade-off: a cookie is exposed to CSRF, local storage to cross-site scripting.

A short-lived access token (5 to 15 minutes) plus a longer refresh token kept in a secure, HttpOnly cookie or stored server-side. Logout and "revoke all sessions" then take effect within the access-token lifetime. Some teams use a Backend-for-Frontend (BFF): the SPA talks to its own backend with a session cookie, and the BFF holds the tokens and calls the APIs; browsers never see a token.

Say it back plainly: "stateless" does not mean "no state": the state moves into the token, and the cost is that you cannot easily take it back.

Remember: sessions are easy to revoke but stateful; tokens scale but are hard to revoke. Match the choice to the client type.

What is the difference between Mockito's @Mock and Spring's @MockBean or @MockitoBean? Intermediate

How do you test a controller? Intermediate

I use @WebMvcTest(OrderController.class) with MockMvc, and mock the service with @MockitoBean (or @MockBean on older versions). MockMvc runs the real request mapping, binding, validation, converters, exception handlers and Security filters, but without a real HTTP server, so it is fast. I assert on status, headers and JSON body.

I test the unhappy paths too: a bad body gives 400, an unknown id gives 404, no token gives 401, wrong role gives 403. 12. Real-life scenarios

Each scenario starts with the one-sentence diagnosis, then goes through the situation, what to check first, the fix, and how to prevent it.

A payment fails and throws an exception, but the order row is still in the database. @Transactional "did not roll back". What do you do? Intermediate

Almost always one of four causes: the exception is checked, it was caught and swallowed, the call was a self-invocation so there was no proxy, or the annotation is on a private method or a non-bean. I check them in that order and fix the one I find.

Situation: a method annotated @Transactional saves an order, calls payment code that throws, and the order is committed anyway.

Check first:

  • Is the exception checked? The default rolls back only for RuntimeException and Error.
  • Is it caught inside the method, so the proxy sees a normal return?
  • Is the method called from the same class (this.pay()), or private? Then no proxy was involved.
  • Is the bean created with new? Is the import org.springframework.transaction.annotation.Transactional and not the javax/jakarta one?
  • Is the payment done on another thread (@Async)? That is a different transaction.

Fix: use rollbackFor = Exception.class or an unchecked exception; rethrow or call setRollbackOnly(); move the method to another bean. Turn on logging.level.org.springframework.transaction.interceptor=TRACE to see whether a transaction even started.

Prevent: a test that forces the failure and asserts that no row was saved, and unchecked domain exceptions by convention.

Reproduce each cause in 3 lines

// 1 checked exception           2 swallowed                      3 self-call
@Transactional                   @Transactional                   public void checkout(Order o) {
void pay(Order o)                void pay(Order o) {                  this.pay(o);          // no proxy
   throws PaymentException {         try { gateway.charge(o); }   }
   repo.save(o);                     catch (Exception e) { log... } @Transactional void pay(Order o) {...}
   throw new PaymentException();     repo.save(o);
}   // COMMITS                    }   // COMMITS

A fast way to prove which one it is

  1. Set logging.level.org.springframework.transaction.interceptor=TRACE. You should see "Getting transaction for [OrderService.pay]" and, at the end, either "Completing transaction" (commit) or "Completing transaction ... after exception" (rollback). No "Getting transaction" line means no proxy was involved: self-call, private, or not a bean.
  2. "Completing transaction" despite an exception in your logs means the exception was caught or was a checked one (the log shows "Applying rules to determine whether transaction should rollback on ...: commit").
  3. Log TransactionSynchronizationManager.isActualTransactionActive() inside the method for a quick check.

Fix choices

  • Business exception: make it extend RuntimeException, or add rollbackFor.
  • You must catch it: log and rethrow, or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().
  • Wrong layer: move @Transactional to the public service method that the controller calls.

A related variant: the payment is a separate system (an HTTP call). A rollback cannot undo a charge that already happened. Order the work so the irreversible step comes last (or is compensated), or use an outbox plus saga. Note on imports: Spring also honours jakarta.transaction.Transactional, with the same default rollback rules, so the import rarely is the cause; check it only if you use a different library's annotation.

Remember: checked, swallowed, self-call, not a bean, other thread. Turn on transaction TRACE logging.

The app fails to start with "No qualifying bean of type X" or with NoUniqueBeanDefinitionException. How do you debug it? Basic

"No qualifying bean" means the container found zero candidates, so I find out why the class is not registered. "NoUnique" means it found several and has no rule to pick one, so I add @Primary or @Qualifier. The message names the type and the injection point, which tells me where to look.

Check first (no bean):

  • Is the class annotated, and is it inside the scanned package tree?
  • Was it switched off by @Profile or a conditional?
  • Is it declared as an interface only, or created manually with new?
  • In a test slice such as @WebMvcTest, the service bean simply is not loaded: mock it with @MockitoBean.

Fix (several beans): mark the default @Primary, qualify the injection point, or inject List<T> if you want all. A new second implementation of an interface is the typical trigger.

Prevent: a context-load test in CI that catches wiring errors before deploy.

Reading the error message

Parameter 0 of constructor in com.acme.OrderService required a bean of type 'com.acme.PaymentGateway' that could not be found.
Action: Consider defining a bean of type 'com.acme.PaymentGateway' in your configuration.

It names the consumer (OrderService), the injection point (constructor parameter 0), and the missing type. Start from there.

Decision path for "no bean"

  1. Is there an implementation, and does it carry @Component/@Service or a @Bean method?
  2. Is it under the package of your @SpringBootApplication class? If not, add @ComponentScan or @Import.
  3. Does it have @Profile, @ConditionalOnProperty, @ConditionalOnMissingBean that is false? Run with --debug and read "Negative matches".
  4. Is it a test? Slice tests load a subset of beans: add @Import(MyService.class) or @MockitoBean.
  5. Is a library supposed to supply it (Boot starter missing, auto-configuration excluded)? Add the dependency.

Decision path for "NoUniqueBeanDefinition"

expected single matching bean but found 2: stripeGateway, paypalGateway
fix: @Primary on the default, or @Qualifier("stripeGateway") at the injection point,
     or inject List<PaymentGateway> if all are wanted

The shortcut is a CI test @SpringBootTest class ContextLoadsTest { @Test void loads() {} } that fails the build on any wiring error, so these never reach a deploy.

Remember: zero candidates means a scanning, profile or slice problem; several candidates means @Primary or @Qualifier.

After upgrading to Boot 2.6 or 3, the app fails with "The dependencies of some of the beans in the application context form a cycle". What do you do? Senior

Since Boot 2.6 circular references are not allowed by default, so a cycle that was silently patched before now fails at startup. The right fix is to break the cycle in the design; flipping spring.main.allow-circular-references=true is only a short-term bridge.

Check first: the error prints the cycle (A to B to A). Look for the dependency that should not exist: often a service calling back into the service that called it.

Fix:

  • Extract the shared logic into a third bean that both use.
  • Replace one direction with an event, or an interface owned by the caller.
  • If urgent, put @Lazy on one constructor parameter or inject an ObjectProvider.

Prevent: constructor injection everywhere, which exposes cycles immediately, and a layering rule that dependencies point one way.

Reading the failure

The dependencies of some of the beans in the application context form a cycle:
┌─────┐
|  orderService defined in file [.../OrderService.class]
↑     ↓
|  invoiceService defined in file [.../InvoiceService.class]
└─────┘

Treat it like a design review: draw the arrows. Usually one arrow is a convenience call that put "how invoices work" inside the order service or the reverse.

Refactor example: extract the shared part

// Before: Order -> Invoice -> Order
class OrderService   { InvoiceService invoices; Order find(long id){...} void ship(Order o){ invoices.issue(o);} }
class InvoiceService { OrderService orders;     void issue(Order o){ ... orders.find(o.id()) ... } }

// After: both depend on a repository / lookup class, not on each other
class OrderLookup    { Order find(long id) {...} }
class OrderService   { OrderLookup lookup; InvoiceService invoices; ... }
class InvoiceService { OrderLookup lookup; ... }          // cycle gone

// Or: decouple with an event
class OrderService { void ship(Order o){ events.publishEvent(new OrderShipped(o.id())); } }
class InvoiceService { @EventListener void on(OrderShipped e){ issue(e.orderId()); } }

Why the upgrade surfaced it: previously Spring resolved setter/field cycles using early references; Boot 2.6 turned this off because it hid design problems and caused subtle issues (a bean might receive a raw, not proxied, reference). The temporary flag spring.main.allow-circular-references=true buys time, but plan to remove it. Libraries you do not own that form a cycle may need @Lazy on one injection point.

Remember: a cycle is a design smell. Extract, use events, or @Lazy as a patch. Do not re-enable the old behaviour for good.

A client reports 403 where they expected 401 (or the other way round), and a browser shows a login page for an API call. How do you sort it out? Intermediate

401 comes from the AuthenticationEntryPoint (not logged in or bad token), and 403 comes from the AccessDeniedHandler (logged in but not allowed). A login page for an API call means the chain is still using the default form-login entry point, which redirects, so I configure the API chain to return 401 JSON instead.

Check first: which chain handled the request (debug log for org.springframework.security), whether the request was authenticated at all, and the actual role: hasRole("ADMIN") needs the authority ROLE_ADMIN. A 403 on a POST with a valid login is often a missing CSRF token.

Fix: for a stateless API, disable form login, set a bearer or basic entry point that returns 401, and register a custom AccessDeniedHandler for a JSON 403. Fix role-prefix mix-ups. Remember that @ControllerAdvice does not see these errors, because they happen in filters.

Prevent: @WebMvcTest security tests for 401 and 403 on each protected endpoint.

An @Async method fails with "An Authentication object was not found in the SecurityContext" or logs show the user as "anonymous". Why, and how do you fix it? Senior

The security context is a ThreadLocal, and the async method runs on a different thread that starts with an empty context. I either pass the user id into the method explicitly, or make the executor copy the context into each task.

Check first: confirm the call crosses a thread boundary (@Async, CompletableFuture, an executor, a parallel stream). The same applies to MDC log fields and request-scoped beans.

Fix:

  • Cleanest: read the user in the caller and pass the id or a small user object as an argument.
  • Otherwise wrap the executor in DelegatingSecurityContextAsyncTaskExecutor, or use DelegatingSecurityContextRunnable for single tasks.
  • For method security on the async method, the context must be present, so use the wrapping option.

Prevent: define the shared executor once, wrapped, and have a test that runs an async call as a logged-in user.

What exactly happens

@PreAuthorize("hasRole('USER')")
@Async
public void exportReport(long id) {...}
// request thread: SecurityContext = alice (ThreadLocal)
// executor thread "task-3": SecurityContext = empty -> AuthenticationCredentialsNotFoundException

The caller's context is stored in a ThreadLocal. A pool thread has its own, which is empty. The annotation check then finds no Authentication and throws. In logs, an audit field "user" may show "anonymous" for the same reason.

Fix 1: pass the data (preferred)

String user = SecurityContextHolder.getContext().getAuthentication().getName();
async.exportReport(id, user);          // method takes the user id; no security needed inside
// secure the entry method (on the request thread), not the async worker

Fix 2: propagate the context with the executor

@Bean(name = "taskExecutor")
Executor taskExecutor() {
    var pool = new ThreadPoolTaskExecutor();
    pool.setCorePoolSize(4); pool.setMaxPoolSize(8); pool.setQueueCapacity(100);
    pool.initialize();
    return new DelegatingSecurityContextAsyncTaskExecutor(pool);   // copies context per task
}
// MDC (log fields) needs a TaskDecorator: copy MDC.getCopyOfContextMap() at submit, set/clear in worker

Delegating wrappers capture the context at submit time and clear it after the task, preventing a leak to the next task on a reused thread. Do not use MODE_INHERITABLETHREADLOCAL with pools: threads are created once, so they keep the context of whoever triggered their creation. Same cure for CompletableFuture.supplyAsync(..., wrappedExecutor); parallel streams use the common pool and cannot be wrapped, so avoid them for secured code.

Remember: new thread, empty context. Pass the user or use the delegating executor.

A controller returns an entity and the response fails with LazyInitializationException (or sends hundreds of SQL queries). What is going on? Intermediate

The entity has lazy associations and JSON serialisation touches them after the transaction (and, with OSIV off, the session) has closed, which throws LazyInitializationException. With OSIV on, the lazy loads work but fire one query per row, the N+1 problem. The fix is the same: do not return entities, return DTOs built from queries that fetch exactly what is needed.

Check first: is spring.jpa.open-in-view on (it is the Boot default)? Count queries with SQL logging. Look at the serialised object graph: does it include collections or back-references?

Fix: map to DTOs inside the service transaction; load with a fetch join, @EntityGraph or a projection query; turn OSIV off so the problem shows up in testing, not production. Do not "fix" it by switching associations to eager, which usually makes the N+1 worse elsewhere.

Prevent: a rule that controllers return DTOs, and a test that asserts the number of queries.

Two symptoms, one root cause

@GetMapping("/orders/{id}")
Order get(@PathVariable long id) { return service.find(id); }   // entity returned

class Order { @OneToMany(fetch = LAZY) List<Item> items; }
// OSIV off: Jackson touches items after the service transaction ended -> LazyInitializationException
// OSIV on:  Jackson touches items -> a query. For a list of 100 orders -> 1 + 100 queries (N+1)

How to see it

Turn on SQL logging (spring.jpa.show-sql=true in dev, or Hibernate statistics): you will see the same select ... from item where order_id=? repeating per order. A test using Hibernate's statistics or a datasource proxy lib can assert "at most 2 queries".

The fix, with code

// 1. fetch what is needed in one query
@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(long id);

// 2. or fetch only the DTO columns
@Query("select new com.acme.OrderDto(o.id, o.total) from Order o")
List<OrderDto> summaries();

// 3. map inside the transaction and return the DTO
@Transactional(readOnly = true)
public OrderDto get(long id) { return OrderDto.from(repo.findWithItems(id).orElseThrow()); }

Caveats: join-fetching two collections at once causes a Cartesian product (and Hibernate refuses with MultipleBagFetchException for Lists); use a second query or @BatchSize. Paging with a collection join fetch happens in memory with a warning (HHH90003004); page the parent IDs first. Returning entities also leaks internal fields, causes infinite recursion with bidirectional links and couples the API to the schema.

Remember: never return entities from controllers. Fetch what you need in the service and map to a DTO.

A nightly @Scheduled job started sending every customer two emails after we scaled to two instances. Fix it. Senior

Every instance runs its own @Scheduled timer, so two instances run the job twice. I make sure only one runs at a time with a distributed lock such as ShedLock, or move the trigger out to a single scheduler, and I make the job idempotent so a double run is harmless.

Check first: confirm from logs that both instance ids ran the job at the same time.

Fix:

  • ShedLock: a lock row in the database or Redis, taken per job name for a set duration; only the instance holding it runs.
  • Or trigger the job from an external scheduler or a Kubernetes CronJob that calls it once.
  • Make the job safe to repeat: record "email sent for customer X on date D" with a unique constraint and skip duplicates.

Prevent: treat every scheduled job as "runs on N instances" at design time, and set the lock duration longer than a normal run but shorter than the interval.

Confirm, then fix in layers

Logs show two entries with different host names at 02:00:00. That proves "one scheduler per instance". Three layers of defence:

  1. Lock so only one instance runs the job.
  2. Idempotent body so a double run (lock failure, retry, manual rerun) does no harm.
  3. Monitoring to notice when it did not run at all.
@Scheduled(cron = "0 0 2 * * *", zone = "UTC")
@SchedulerLock(name = "nightlyEmails", lockAtMostFor = "30m", lockAtLeastFor = "1m")
public void sendNightlyEmails() {
    for (Customer c : customers.findNotNotifiedToday()) {            // SELECT ... WHERE notified_on < today
        if (notifications.tryMarkSent(c.id(), LocalDate.now())) {     // INSERT with unique(customer_id, day)
            mailer.send(c);
        }
    }
}

Choosing the lock times

  • lockAtMostFor: safety release if the holder crashes; must exceed the longest normal run, else a second instance starts mid-run.
  • lockAtLeastFor: stops a fast job being re-run by another instance whose clock is slightly ahead.

Why mark-then-send is better than send-then-mark

If the process crashes between sending and recording, a retry sends again (duplicate). If you record first with a unique constraint and then send, a crash means a missed email, which you can detect and re-drive. Pick based on whether duplicates or misses are worse; for high-stakes messages use an outbox with a sender that tracks status.

Alternatives when the job is heavy or important: a Kubernetes CronJob (one pod per run, built-in history and retries), Quartz clustered mode, or a queue where the schedule only enqueues one message.

Remember: a scheduler per instance means N runs. Lock it and make it idempotent.

Under load, requests hang and the log shows "HikariPool-1 - Connection is not available, request timed out after 30000ms". What is your approach? Senior

All pooled connections are checked out and new requests waited 30 seconds for one. The cause is usually connections held too long, not a pool that is too small, so I look for long transactions and leaks before I touch the pool size.

Check first: Hikari metrics (active, pending, timeouts); a thread dump to see what the holding threads are doing; and the database's list of long-running transactions or idle-in-transaction sessions. Typical culprits: a remote HTTP call or file operation inside @Transactional, REQUIRES_NEW taking a second connection while the outer holds one, open-session-in-view with slow clients, a missing index making queries slow, and manual JDBC code that does not close connections.

Fix: shrink the transaction scope, move slow calls outside it, add the missing index, close resources, and set a Hikari leakDetectionThreshold to find leaks. Raise the pool size only after that, and modestly.

Prevent: alert on pending connections, and review any use of REQUIRES_NEW.

The investigation order

  1. Measure. Hikari JMX/Micrometer: hikaricp.connections.active pinned at max, .pending above zero, .acquire time rising. That confirms a pool problem, not a database outage.
  2. Who holds the connections? Take 2 or 3 thread dumps 10 seconds apart. Threads in HikariPool.getConnection are waiting; threads holding connections are elsewhere, for example in SocketInputStream.read inside your own RestTemplate call, inside a @Transactional method.
  3. What does the DB say? pg_stat_activity (state "idle in transaction" with old xact_start) or the MySQL process list: sessions that are open but idle mean the app holds the transaction while doing other things.
  4. Turn on leak detection: leak-detection-threshold=15000 prints the stack trace of code that held a connection longer than 15 s.

Typical culprits and the concrete fix

CulpritFix
HTTP call inside @Transactionalcall first, then open a short transaction
REQUIRES_NEW inside a loop or deep callrestructure; pool must exceed concurrent outer plus inner
OSIV on, slow client or heavy serialisationturn OSIV off; return DTOs
Slow query (missing index, big scan)explain plan, add index, add query timeout
Manual JDBC without try-with-resourcesclose connections
Traffic spike, downstream slownesstimeouts and bulkheads; shed load; then consider more capacity

Fail fast instead of hanging: connection-timeout=3000 and a request timeout at the gateway return errors in 3 s instead of piling up 30 s waiters that exhaust the server's own threads. Raising the pool from 10 to 100 usually moves the queue into the database, where it hurts more, so do it last and with a load test.

Remember: exhaustion is mostly held connections: long transactions, leaks, REQUIRES_NEW. Find the holders first.

@Cacheable seems to do nothing: the method is called every time. What do you check? Intermediate

Caching is proxy-based, so the usual causes are that the method is called from the same class, is private, or that @EnableCaching is missing. After those, I check the key and the cache manager.

Check first:

  • Is @EnableCaching present, and is a CacheManager configured?
  • Is the call coming from another bean through the proxy, not from this?
  • Is the cache name right, and does the key differ each time (an argument object without equals and hashCode, or a timestamp)?
  • Does unless or condition exclude the result, or is the entry expiring immediately (TTL)?

Fix: move the method to another bean, add equals and hashCode or a SpEL key (key = "#id"), and check the cache contents through the CacheManager or logging at TRACE for org.springframework.cache.

Prevent: a test that calls the method twice and verifies the repository was hit once.

A conceptual trap: caching returns the same object instance for local caches, so a caller that mutates the result changes the cache; return immutable DTOs.

Remember: proxy rules apply: no self-calls. Then check @EnableCaching, key and TTL.

An outer transaction fails at commit with UnexpectedRollbackException, although the inner exception was caught and handled. Why? Senior

The inner method joined the outer transaction (REQUIRED), and when it threw a runtime exception through its own proxy, the shared transaction was marked rollback-only. Catching the exception in the outer method does not clear that mark, so at commit Spring refuses and throws UnexpectedRollbackException.

Check first: find the inner @Transactional call that throws, and confirm it shares the outer transaction (default propagation).

Fix: decide what you want. If the inner failure should not affect the outer, run the inner in REQUIRES_NEW (own transaction, mind the extra connection), or NESTED with savepoints on JDBC. If the failure is fatal, let it propagate instead of catching. Another option: validate first so the inner call is not expected to fail.

Prevent: avoid catching exceptions from transactional calls inside a transaction unless the propagation allows recovery.

Timeline of what happens

@Transactional void outer() {                // T1 begins (physical transaction)
    try {
        inner.work();                        // joins T1; throws RuntimeException;
                                             //   the proxy sees it and marks T1 rollback-only
    } catch (RuntimeException e) {
        log.warn("ignored", e);              // you handled it, but the mark stays
    }
    repo.save(x);                            // works, but...
}                                            // commit: T1 is rollback-only -> rolls back,
                                             //   throws UnexpectedRollbackException:
                                             //   "Transaction silently rolled back because it has been marked as rollback-only"

Why: a transaction is one unit in the database. The inner proxy cannot roll back "only the inner part" (no separate transaction exists), so it records "this whole transaction can no longer commit". The outer proxy checks that flag at commit and rejects, rather than silently committing half-failed work.

The choices, and when

IntentionDo
Inner failure is fatal for the whole operationdo not catch it; let the outer roll back; map the exception to a 4xx/5xx at the edge
Inner is optional and must not affect the outerREQUIRES_NEW (separate commit, extra connection)
Inner is a retryable sub-step within the same unitNESTED (JDBC savepoint) and catch; outer continues
Inner is "try and see"check preconditions first (exists? valid?) so it does not throw; use noRollbackFor on the inner for expected business exceptions

Also look for it in test code: an inner @Transactional(readOnly=true) method throwing EmptyResultDataAccessException that the caller treats as "not found" is a classic source. Use Optional returns for expected absences instead of exceptions.

Remember: a joined transaction cannot be half-failed. The inner throw marks the whole thing rollback-only.

The front end gets a CORS error only for POST requests with an Authorization header, although @CrossOrigin is on the controller. What is wrong? Intermediate

A POST with an Authorization header triggers a preflight OPTIONS request that carries no credentials. Spring Security rejects it with 401 or 403 before the controller and its @CrossOrigin are ever reached, so no CORS headers are returned and the browser reports a CORS error.

Check first: open the browser network tab and look at the OPTIONS request status and response headers. If it is 401 or 403 with no Access-Control-Allow-* headers, that confirms it.

Fix: enable CORS in the security chain with http.cors(...) and a CorsConfigurationSource bean that lists the exact origins, methods and headers (including Authorization), so the CORS filter answers the preflight before authentication. Do not use a * origin together with credentials.

Prevent: keep CORS config in one place, and test the preflight with MockMvc.

What the browser actually does

1. OPTIONS /api/orders   Origin: https://app.example.com
                         Access-Control-Request-Method: POST
                         Access-Control-Request-Headers: authorization,content-type
   no cookies, no Authorization header
   -> Spring Security: unauthenticated -> 401/403, NO CORS headers
2. Browser: "preflight failed" -> never sends the POST
3. Console: "blocked by CORS policy: Response to preflight request doesn't pass access control check"

So the POST never reaches your controller, and @CrossOrigin there is irrelevant. GET without custom headers works because it is a "simple" request with no preflight, which explains "only POST with Authorization fails".

Fix and verify

http.cors(Customizer.withDefaults())
    .authorizeHttpRequests(a -> a.anyRequest().authenticated());

@Bean CorsConfigurationSource corsConfigurationSource() {
    var c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("https://app.example.com"));
    c.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS"));
    c.setAllowedHeaders(List.of("Authorization","Content-Type"));
    var src = new UrlBasedCorsConfigurationSource();
    src.registerCorsConfiguration("/**", c);
    return src;
}

// test the preflight
mvc.perform(options("/api/orders").header("Origin","https://app.example.com")
        .header("Access-Control-Request-Method","POST")
        .header("Access-Control-Request-Headers","authorization"))
   .andExpect(status().isOk())
   .andExpect(header().exists("Access-Control-Allow-Origin"));

Other causes to rule out: a reverse proxy or API gateway also adding CORS headers (duplicate Access-Control-Allow-Origin values are rejected by browsers); allowed origin with a trailing slash or wrong scheme/port (match must be exact); using * with credentials. Remember that CORS is a browser protection: curl working does not prove your CORS config is right.

Remember: a preflight has no token. Configure CORS in the security chain, not only on the controller.

A field annotated @Autowired or @Value is null at runtime with no startup error. What happened? Basic

The object was not created by Spring. If I called new MyClass() myself, the container never injected anything into it. The other usual causes are a static field, or an injection that Spring skipped because the class is not a bean.

Check first:

  • Search for new on that class, including in a test or a utility method.
  • Is the field static, or is the injection used inside the constructor before fields are set? Fields are injected after the constructor runs; use constructor injection.
  • Is the class annotated and scanned, and is it the bean that gets used, not a second instance?

Fix: get the object from the container (inject it), use constructor injection so a null is impossible, and pass dependencies explicitly in tests. A @Value that is not null but wrong usually means the property name or profile file is off.

Prevent: constructor injection and final fields: the compiler then forbids a half-built object.

Why new bypasses injection

Injection is done by the container on the instances it creates (post-processors run on beans). A manually created object is just a plain Java object, so its @Autowired fields stay null.

@Component class Mailer { @Autowired Client client; @Value("${mail.from}") String from; }

class Job {
    void run() {
        Mailer m = new Mailer();     // not a bean: client == null, from == null
        m.send();                    // NullPointerException
    }
}
// fix: inject it
@Component class Job { private final Mailer mailer; Job(Mailer mailer) { this.mailer = mailer; } }

If you really must create objects yourself and still need Spring's injection, use AutowireCapableBeanFactory.autowireBean(obj), or ObjectProvider/@Lookup for prototypes, or AspectJ @Configurable. In tests, a missing Spring context is a common reason: with @ExtendWith(MockitoExtension.class) use @InjectMocks, or build the object with its constructor.

Remember: only objects Spring creates get injected. new bypasses the container.
