Mental model: the 7 ideas everything hangs on

One line: modern Java lets you pass behaviour as a value (lambda), process data as a lazy pipeline (stream), describe data with small immutable types (records, sealed types) and take them apart safely (pattern matching), while the platform moves toward cheap threads and strong encapsulation.
  1. A lambda is an instance of a functional interface. Java did not add a "function type". Any interface with one abstract method can be written as a lambda.
  2. A stream is a pipeline, not a collection. It stores no data. It describes steps from a source to one result, and nothing runs until a terminal operation is called.
  3. Elements flow one at a time. Each element goes through the whole chain before the next starts. That is why limit and infinite streams work.
  4. Immutability is the direction. List.of, records, java.time and Stream.toList() give values you cannot change. Fewer shared-state bugs.
  5. "Maybe no result" is a type. Optional belongs in return types, not in fields or parameters.
  6. Types describe the data. Records carry data, sealed types list every allowed subtype, and a pattern-matching switch makes the compiler check you handled all of them.
  7. Upgrades break on removed things, not new things. Removed Java EE modules, locked-down JDK internals and old libraries hurt. New syntax is optional.

1. Lambdas, functional interfaces and interface methods

What is a lambda, why was it added in Java 8, and how is it different from an anonymous class? Basic

A lambda is a short, nameless piece of code that I can pass around, and it implements a functional interface (an interface with one abstract method). Java 8 added it so that streams and callbacks could be written in one line instead of a five-line anonymous class. It is not just shorter syntax: inside a lambda this means the enclosing object, and it does not create its own class file.

list.sort(new Comparator<String>() {                  // before Java 8
    public int compare(String a, String b) { return a.length() - b.length(); }
});
list.sort(Comparator.comparingInt(String::length));      // Java 8

Differences that matter: an anonymous class is a real class, with its own this, its own fields and one class file per use. A lambda compiles to a private method plus an invokedynamic call, and the JVM builds the interface object at first use. A lambda also needs a target type from context, so var f = x -> x; does not compile. The same lambda text can become a Function or a custom interface, depending on where it is used.

Why it exists

Before Java 8, the only way to hand "a piece of behaviour" to a method (sort this way, run this when done) was an anonymous inner class. Five lines of ceremony carried one line of logic, so APIs like streams, which take many small behaviours, would have been unusable. A lambda removes the ceremony. The compiler already knows from the context which interface is needed and which method to implement, so you only write the parameters and the body.

What the compiler does, step by step

  1. It looks at where the lambda is used (the target type), for example the parameter of list.sort(Comparator<? super T>).
  2. It checks that the target is a functional interface and finds its single abstract method (compare(T, T)), so it knows the parameter types and the return type.
  3. It compiles the lambda body into a private (synthetic) method of the enclosing class. No separate .class file is written.
  4. At the place of use it emits an invokedynamic instruction. The first time that line runs, the JVM links it and generates an object that implements the interface and calls the private method. Later runs reuse it. A lambda that captures nothing is typically created once and reused.

The this difference, shown

class Demo {
    String name = "Demo";
    void run() {
        Runnable anon = new Runnable() {
            String name = "anon";
            public void run() { System.out.println(this.name); }   // the anonymous object
        };
        Runnable lam = () -> System.out.println(this.name);        // the Demo object
        anon.run();   // prints: anon
        lam.run();    // prints: Demo
    }
}

Inside an anonymous class, this is the new anonymous object and it can shadow outer names. Inside a lambda there is no new scope for this, and a lambda parameter cannot reuse the name of a local variable that is already in scope (the compiler rejects it).

Pitfall: because a lambda has no name, stack traces show it as something like lambda$run$0, and a very large lambda body is hard to debug. If the body is more than three or four lines, move it into a named method and use a method reference.

Remember: a lambda is an object of a functional interface, with this from the enclosing class and no class file of its own.

What is a functional interface? Do I need @FunctionalInterface? Basic

It is an interface with exactly one abstract method. Default methods, static methods and methods that match Object (like equals) do not count. @FunctionalInterface is optional, but I add it because the compiler then refuses to compile if someone adds a second abstract method and breaks every lambda that used it.

@FunctionalInterface
interface Validator<T> {
    boolean validate(T t);                       // the one abstract method
    default Validator<T> and(Validator<T> o) { return x -> validate(x) && o.validate(x); }
}
Validator<String> notEmpty = s -> !s.isEmpty();

Old interfaces such as Runnable, Comparator and Callable already qualify, which is why lambdas work with old APIs. Comparator declares equals as well, but that matches Object, so it still has one abstract method.

What counts, and what does not

The rule is "exactly one abstract method". Three kinds of methods do not count against that limit, and this is the part people get wrong:

  • default methods (they have a body),
  • static methods (they belong to the interface, not to an implementation),
  • abstract methods that match a public method of Object (equals, hashCode, toString), because every class already has them.
interface Ok1  { void run(); default void log() {} static Ok1 noop() { return () -> {}; } }   // functional
interface Ok2  { int compare(String a, String b); boolean equals(Object o); }                  // functional
interface Bad1 { void a(); void b(); }                                                         // two abstract: NOT
interface Bad2 { }                                                                             // zero abstract: NOT

What the annotation actually does

@FunctionalInterface changes nothing at run time. It only asks the compiler to verify the rule. Picture a teammate adding a second abstract method to Validator a year from now. Without the annotation the error appears in the 40 places that use a lambda for it, far from the cause. With the annotation the error appears on the interface itself, immediately. That is why it is worth the one line, much like @Override.

Why the single-method rule exists

When you write s -> !s.isEmpty() there is no method name. The compiler needs to know which method this body implements. With exactly one abstract method the answer is never ambiguous. That is the whole reason for the rule.

Pitfall: a generic method cannot be implemented by a lambda (<T> T pick(T a) in an interface), and a lambda does not work for an abstract class even if it has a single abstract method. Use an anonymous class there.

Remember: one abstract method = lambda-ready. The annotation is a compile-time guard, not a requirement.

Name the core interfaces in java.util.function and how you compose them. Basic

Four are the base: Predicate<T> takes T and returns boolean, Function<T,R> turns T into R, Consumer<T> takes T and returns nothing, and Supplier<T> takes nothing and returns T. Variants add two arguments (BiFunction), same input and output type (UnaryOperator, BinaryOperator) or primitives (IntPredicate, ToIntFunction) to avoid boxing.

They compose through default methods. Predicate has and, or, negate. Function has andThen and compose, and the difference is only the order:

Function<Integer,Integer> plus1 = x -> x + 1, times2 = x -> x * 2;
plus1.andThen(times2).apply(5);   // (5+1)*2 = 12   first, then second
plus1.compose(times2).apply(5);   // (5*2)+1 = 11   second, then first

Supplier is how you pass "compute this only if needed", for example a lazy log message or orElseGet. Callable looks like a Supplier but may throw a checked exception.

The four shapes, as a table

InterfaceMethodShapeTypical use
Predicate<T>boolean test(T)T to booleanfilter, removeIf
Function<T,R>R apply(T)T to Rmap, computeIfAbsent
Consumer<T>void accept(T)T to nothingforEach, ifPresent

Variants follow a naming pattern: Bi means two inputs (BiFunction<T,U,R>, BiConsumer), Unary/Binary operators mean input and output are the same type (UnaryOperator<T> is a Function<T,T>), and Int/Long/Double prefixes mean primitives, which avoid boxing (IntPredicate, ToIntFunction<T>, IntBinaryOperator).

Composition with output

Predicate<String> longer = s -> s.length() > 3;
Predicate<String> startsA = s -> s.startsWith("a");
Predicate<String> both = longer.and(startsA.negate());
both.test("bank");    // true  (long, does not start with a)
both.test("apple");   // false (starts with a)

Function<String,Integer> len = String::length;
Function<Integer,String> stars = n -> "*".repeat(n);
len.andThen(stars).apply("java");   // "****"

Why composition matters: you build small tested rules (isAdult, isActive) and combine them at the call site, instead of writing a new if-chain each time. Predicate.not(...) (Java 11) is handy with method references: filter(Predicate.not(String::isBlank)).

Pitfall: do not mix up Callable (returns a value, may throw a checked exception, used with executors) and Supplier (no checked exception, used in functional code).

Remember: Predicate tests, Function maps, Consumer eats, Supplier gives. a.andThen(b) runs a first; a.compose(b) runs b first.

What are the four kinds of method reference? Intermediate

A method reference is a lambda that only calls one existing method, written with ::. The four kinds are a static method (Integer::parseInt), a method on a specific object (System.out::println), a method on an arbitrary object of a type, where the stream element becomes the receiver (String::length), and a constructor (ArrayList::new).

x -> Integer.parseInt(x)     ==  Integer::parseInt        // static
x -> out.println(x)          ==  out::println             // bound to out
s -> s.length()              ==  String::length           // first arg is the receiver
() -> new ArrayList<>()      ==  ArrayList::new           // constructor

The third kind confuses people. String::compareToIgnoreCase as a Comparator means (a, b) -> a.compareToIgnoreCase(b): the first argument is the object and the rest are arguments. If a method is overloaded, the target type picks the version, and sometimes the call is ambiguous. Then write the lambda.

Why method references exist

Many lambdas do nothing but forward their arguments to an existing method, like s -> s.length(). A method reference says the same thing with the name only, so the reader sees the intent ("get the length") without the plumbing. It is not faster, it is just clearer.

How to tell the four kinds apart

Ask: who is the receiver of the call, and where does it come from?

KindWrittenEquivalent lambdaReceiver

The constructor form adapts to the interface: as a Supplier it calls the no-arg constructor, as a Function<String,Person> it calls Person(String). Array constructors work too: stream.toArray(String[]::new).

List<String> words = List.of("b", "A", "c");
words.stream().sorted(String::compareToIgnoreCase).toList();   // [A, b, c]  unbound: (x, y) -> x.compareToIgnoreCase(y)
words.stream().map(String::toUpperCase).forEach(System.out::println);  // B A C, bound println

Pitfall: with a bound reference, obj::method evaluates obj immediately. If obj is null you get a NullPointerException when the reference is created, not when it runs. When a method is overloaded (for example Integer::toString has both static and instance forms) the compiler may report ambiguity, and a lambda is the clear fix.

Remember: static, bound instance, unbound instance (first argument is the receiver), constructor.

Why must variables captured by a lambda be effectively final? Intermediate

A lambda copies the value of a captured local variable, and that copy can be used later, even on another thread, after the method has returned. If the original could change, the copy and the original would disagree, and local variables are not safe to share between threads. So the compiler requires that the variable is never reassigned. That is what "effectively final" means.

int count = 0;
list.forEach(x -> count++);          // does not compile
AtomicInteger c = new AtomicInteger();
list.forEach(x -> c.incrementAndGet());   // works, but a stream reduce/count is better

The rule applies to local variables and parameters only. Fields, static fields and array elements can be changed from a lambda, because the lambda holds the reference to the object, not a copy of a local. That is a loophole, not a recommendation: mutating outside state from a lambda is a bug waiting in parallel code. A classic form of the error is a loop variable for (int i...) used inside the lambda. Copy it to a final int j = i; first, or use an enhanced for loop.

The problem the rule prevents

A local variable lives on the stack of the method that created it. When that method returns, the variable is gone. But a lambda can outlive the method (it may be stored, or run later on another thread). So Java does not let the lambda reach back to the variable. It copies the value into the lambda when the lambda is created. If the original could change afterwards, there would be two diverging versions of "the same" variable, which would be very confusing. So the language forbids it: captured locals must be effectively final, meaning they could be declared final without a compile error (assigned once, never changed).

What it looks like, step by step

int base = 10;                      // assigned once: effectively final
Function<Integer,Integer> add = x -> x + base;   // copies 10 into the lambda
// base = 20;                       // if you add this line, the lambda above stops compiling

for (int i = 0; i < 3; i++) {
    // tasks.add(() -> System.out.println(i));    // error: i changes every loop
    int j = i;                                       // a fresh variable per iteration
    tasks.add(() -> System.out.println(j));          // ok, prints 0, 1, 2 when run
}

The same rule applies to anonymous inner classes (it was explicit final in Java 7 and "effectively final" since Java 8).

Ways to get a changing result out

  • Let the stream produce it: long n = list.stream().filter(...).count(); instead of a counter.
  • Use a thread-safe holder when mutation is really needed: AtomicInteger, LongAdder. This works, but only in the sense that the compiler is happy. Mutating from a parallel stream still needs the holder to be thread-safe.
  • Use a plain for loop when state across iterations is the point.

A one-element array (int[] c = {0}; list.forEach(x -> c[0]++);) compiles, but it is a hack that hides state and breaks in parallel. Interviewers often use it as a trap question.

Remember: lambdas capture values, not variables. Need a changing result? Return it from a stream operation instead.

How do you handle checked exceptions inside a lambda? Intermediate

The standard functional interfaces do not declare checked exceptions, so a lambda body that throws one will not compile. I either catch it inside the lambda and wrap it in an unchecked exception, or I move the risky call into a small helper method that does the wrapping.

paths.stream().map(p -> {
    try { return Files.readString(p); }
    catch (IOException e) { throw new UncheckedIOException(e); }
}).toList();

If this repeats, define my own interface ThrowingFunction<T,R> { R apply(T t) throws Exception; } and a wrapper static <T,R> Function<T,R> unchecked(ThrowingFunction<T,R> f) that catches and rethrows unchecked. The real design question is what a failure should mean for the pipeline: stop everything (rethrow), skip the element (return empty or Optional), or collect the errors (return a result object). Do not swallow it silently.

Why it does not compile

Function.apply, Consumer.accept and the others declare no throws. A lambda is the body of that method, so it may not throw a checked exception (IOException, SQLException) either. Runtime exceptions are fine.

// does not compile: unreported exception IOException
List<String> texts = paths.stream().map(p -> Files.readString(p)).toList();

Three practical fixes

1. Wrap inline (shown above). Fine for one use.

2. Reusable wrapper, so the pipeline stays clean:

@FunctionalInterface interface ThrowingFunction<T,R> { R apply(T t) throws Exception; }

static <T,R> Function<T,R> unchecked(ThrowingFunction<T,R> f) {
    return t -> {
        try { return f.apply(t); }
        catch (RuntimeException e) { throw e; }
        catch (Exception e) { throw new RuntimeException(e); }
    };
}
paths.stream().map(unchecked(Files::readString)).toList();

3. Do not throw at all. Return a result that says what happened, so one bad file does not kill the whole run:

record Result(Path p, String text, Exception error) {}
paths.stream().map(p -> { try { return new Result(p, Files.readString(p), null); }
                         catch (IOException e) { return new Result(p, null, e); } })
     .toList();      // later: partition into successes and failures

The design question behind it

Which behaviour do you want? Fail fast (rethrow unchecked), skip and log, or collect all errors. Pick on purpose. Another known pitfall: the "sneaky throw" trick that rethrows a checked exception without declaring it compiles, but the caller will not expect it, so I avoid it in application code.

Remember: wrap in the lambda, or wrap once in a helper. Decide first whether one failure should stop the whole stream.

What are default and static methods in interfaces, and why were they added? Basic

A default method is an interface method with a body, so implementing classes get it for free and may override it. They were added so Java could extend old interfaces, such as adding stream() to Collection or sort() to List, without breaking every class that already implemented them. Static methods in interfaces hold helpers that belong with the interface, like Comparator.comparing.

Defaults cannot hold state: no instance fields. Java 9 added private interface methods so several defaults can share code. Static interface methods are not inherited by implementing classes; you call them as Interface.method(). An abstract class is still the right tool when you need fields, constructors or protected helpers. A good pattern is an interface with defaults plus an optional abstract skeleton, like List and AbstractList.

The problem default methods solved

Imagine Java 8 wants to add stream() to Collection. Before Java 8, adding a method to an interface broke every class in the world that implemented it (they would no longer compile). Adding it as a default method gives existing classes a working version automatically. That is the whole reason: interface evolution. It is how List.sort, Map.getOrDefault, Iterable.forEach and Collection.removeIf arrived without breaking ArrayList or third-party lists.

Before and after

// Java 7: each implementing class needs its own code, or a helper class like Collections
Collections.sort(list, cmp);
// Java 8: the behaviour lives on the interface
list.sort(cmp);

interface Greeter {
    String name();
    default String greet() { return "Hello " + name(); }         // Java 8, inherited by implementors
    static Greeter of(String n) { return () -> n; }              // Java 8 static factory
    private String shout() { return greet().toUpperCase(); }     // Java 9: private helper, not visible outside
    default String loud() { return shout() + "!"; }
}
Greeter.of("Asha").loud();    // HELLO ASHA!

Remember: default methods exist for interface evolution, not as a replacement for abstract classes.

A class implements two interfaces that have the same default method. What happens? Intermediate

The class does not compile until I resolve the clash. I override the method in the class and, if I want one of the originals, call it with InterfaceName.super.method(). There are only two simple rules before that: a method in the class (or superclass) always wins over an interface default, and a more specific interface wins over its parent.

interface A { default String hi() { return "A"; } }
interface B { default String hi() { return "B"; } }
class C implements A, B {
    public String hi() { return A.super.hi() + B.super.hi(); }   // forced to choose
}

If one interface declares the method abstract and the other gives a default, it is still a clash and the class must implement it. This is Java's version of the "diamond problem", solved by making the developer decide. It is safe because interfaces have no state.

The three resolution rules, in order

  1. Class wins. A method declared in the class or inherited from a superclass beats any interface default.
  2. Most specific interface wins. If B extends A and both have hi(), then B's is used.
  3. Otherwise it is a compile error and you must override and say which one you want, with A.super.hi().
interface A { default String hi() { return "A"; } }
interface B extends A { default String hi() { return "B"; } }
class D implements A, B { }
new D().hi();            // "B": rule 2, B is more specific than A

class Base { public String hi() { return "Base"; } }
class E extends Base implements A { }
new E().hi();            // "Base": rule 1, class wins over interface default

Why this is a safe design

In C++ multiple inheritance of state causes the real diamond problem: which copy of a field do you have? Java sidesteps this because interfaces carry no instance state, only behaviour. If two behaviours clash, the compiler asks you instead of guessing. The error message looks like "class C inherits unrelated defaults for hi() from types A and B".

Pitfall: adding a default method to a library interface can silently create this clash for users who implement two interfaces. Library authors should be careful, which is one reason Java adds defaults only when there is a strong need.

Remember: class wins, then the most specific interface, otherwise you must override and use X.super.m().

How do you write a multi-field sort with the modern Comparator API? Basic

I chain the factory methods: Comparator.comparing(...) for the first key, then thenComparing(...) for tie-breakers, and reversed() or Comparator.reverseOrder() for descending. It is shorter and safer than a hand-written compare with subtraction.

people.sort(Comparator.comparing(Person::city)
        .thenComparing(Person::age, Comparator.reverseOrder())
        .thenComparing(Person::name));
// nulls: Comparator.nullsLast(Comparator.naturalOrder())
// primitives: comparingInt(Person::age) avoids boxing

Two traps. First, a.age - b.age overflows for large values, so never do it; use Integer.compare or the factories. Second, comparing(Person::age).reversed() works, but after a lambda such as comparing(p -> p.age()).reversed() type inference can fail; use a method reference or write Comparator.comparing(Person::age, Comparator.reverseOrder()).

Old way vs new way, with output

record Person(String name, String city, int age) {}
var ps = new ArrayList<>(List.of(
    new Person("Zoe", "Pune", 30), new Person("Amy", "Pune", 41), new Person("Bob", "Delhi", 30)));

// Java 7 style: easy to get wrong
ps.sort(new Comparator<Person>() {
    public int compare(Person a, Person b) {
        int c = a.city().compareTo(b.city());
        if (c != 0) return c;
        return Integer.compare(b.age(), a.age());     // age descending
    }
});
// Java 8 style: reads like the requirement
ps.sort(Comparator.comparing(Person::city)
                  .thenComparing(Person::age, Comparator.reverseOrder()));
// result: Bob(Delhi), Amy(Pune, 41), Zoe(Pune, 30)

How the chain works

comparing(keyExtractor) builds a Comparator that extracts a key from each side and compares the keys (which must be Comparable, or you pass a second argument with a key comparator). thenComparing returns a new comparator that only consults the next rule when the earlier ones say "equal". reversed() flips the whole comparator built so far, so put it where you mean it: comparing(A).thenComparing(B).reversed() reverses both.

Null and overflow

  • A null key throws NPE. Wrap it: comparing(Person::city, Comparator.nullsFirst(Comparator.naturalOrder())).
  • The subtraction trick fails: Integer.MIN_VALUE - 1 overflows to a large positive number, so the order is wrong for extreme values. Always use Integer.compare or the factories.

The comparator contract is also something an interviewer may probe: it must be consistent (if a<b then b>a, and transitive), or TimSort may throw "Comparison method violates its general contract".

Remember: comparing, thenComparing, reversed, nullsLast. Never subtract to compare.

2. Stream API

What is a Stream, and how is it different from a Collection? Basic

A collection stores data. A stream does not store anything: it is a one-time pipeline of operations over a source such as a list, array or file. A collection can be read many times and changed. A stream is consumed once, never modifies its source and can even be infinite.

A pipeline has three parts: a source (list.stream()), zero or more intermediate operations that return a new stream and only describe work (filter, map, sorted), and one terminal operation that produces a result or a side effect (collect, count, forEach, findFirst). Because the work is described first and run later, the library can fuse the steps into a single pass and stop early.

List<String> top = names.stream()
    .filter(n -> n.length() > 3)    // intermediate
    .map(String::toUpperCase)       // intermediate
    .limit(5)                       // intermediate, short-circuiting
    .toList();                      // terminal: now it runs

From scratch

Think of a stream as a recipe on a conveyor belt, not a box of ingredients. The collection is the box. The stream says "take items from the box, drop the short ones, shout the rest, give me the first five". Nothing is cooked until someone asks for the result.

Why it exists

Before Java 8 you wrote a loop with a temporary list, an if, and an add. The loop mixes how (indexes, temporary variables) with what (the filter rule). Streams let you state the what and let the library handle the how, including running in parallel later by changing one word. It also makes it natural to chain steps.

Before and after, with output

List<String> names = List.of("Amy", "Bob", "Christine", "Dave", "Elizabeth", "Fay");

// Java 7: imperative
List<String> result = new ArrayList<>();
for (String n : names) {
    if (n.length() > 3) {
        result.add(n.toUpperCase());
        if (result.size() == 2) break;
    }
}

// Java 8+: declarative
List<String> result2 = names.stream().filter(n -> n.length() > 3).map(String::toUpperCase).limit(2).toList();
// [CHRISTINE, DAVE]   (toList() is Java 16)

What does "lazy" mean for streams? In what order do elements move through the pipeline? Intermediate

Lazy means intermediate operations do nothing until a terminal operation starts the pipeline. Then elements go through one at a time: the first element passes all stages before the second element starts. That is why findFirst or limit can stop early and why infinite streams are possible.

Stream.of("a","bb","ccc","dd")
  .filter(s -> { System.out.println("filter " + s); return s.length() > 1; })
  .map(s -> { System.out.println("map " + s); return s.toUpperCase(); })
  .findFirst();
// filter a, filter bb, map bb  -> then stops. "ccc" and "dd" are never touched.

Not everything is one-at-a-time. Stateful operations such as sorted and distinct must see (or remember) many elements first, so sorted buffers the whole input before passing anything on.

Why laziness is useful

If every filter and map ran immediately, each would build a whole new list in memory: three steps over a million items means three million-item lists. Laziness avoids that. The library first collects the whole recipe, and only then runs it as one pass, pushing each element through every step. It can also stop as soon as the answer is known.

Walk through the example, step by step

  1. findFirst() starts the pipeline and asks for one element.
  2. Element "a" reaches filter. Its length is 1, so it is rejected. Nothing downstream sees it. Output so far: filter a.
  3. Element "bb" reaches filter and passes. Output: filter bb. It then reaches map. Output: map bb.
  4. findFirst has its answer (Optional["BB"]), so the pipeline stops. "ccc" and "dd" are never read.

Compare this with the eager mental model, which would print filter a, filter bb, filter ccc, filter dd, map bb, map ccc, map dd. The printed order is the proof that elements are processed vertically (one element through all stages), not horizontally (one stage over all elements).

Stateful and short-circuit operations

  • Stateless (filter, map, peek): decide per element, no memory.
  • Stateful (sorted, distinct, skip, limit): need to see or remember other elements. sorted is the extreme: it must read the entire input before emitting the first output, so sorted().limit(1) on a large source still sorts everything (or uses a bounded buffer in some cases, but do not rely on that).
  • Short-circuit (limit, findFirst, anyMatch, allMatch, noneMatch): can finish before the source is exhausted. This is what makes an infinite stream like Stream.iterate(1, x -> x * 2).limit(5) work. Without a short-circuit step, an infinite stream runs forever.

Pitfall: a pipeline with no terminal operation does nothing, silently. list.stream().map(x -> {log(x); return x;}); prints nothing. This is a common bug.

Remember: nothing runs without a terminal operation, and each element travels the whole chain before the next one starts (except sorted, which waits for all).

What is the difference between map and flatMap? Basic

map turns each element into exactly one new element. flatMap turns each element into a stream of zero or more elements and then joins all those streams into one flat stream. I use flatMap whenever my function returns a collection or stream and I want the items, not the boxes.

orders.stream().map(Order::getItems)            // Stream<List<Item>>  (nested)
orders.stream().flatMap(o -> o.getItems().stream())  // Stream<Item>  (flat)

"hello world".chars()... // words: Arrays.stream(text.split(" "))
lines.stream().flatMap(l -> Arrays.stream(l.split(" ")))  // all words

An element can map to an empty stream, so flatMap also works as "filter and map in one step". On Optional, flatMap does the same job: it avoids Optional<Optional<T>>.

The problem it solves

Suppose each order contains a list of items and you want all items in one stream. With map(Order::getItems) you get a Stream<List<Item>>, a stream of boxes. You would then need a second loop to open every box. flatMap does the opening for you.

Concrete example with numbers

List<List<Integer>> nested = List.of(List.of(1, 2), List.of(3), List.of());

nested.stream().map(l -> l.size()).toList();             // [2, 1, 0]       one output per input
nested.stream().flatMap(List::stream).toList();           // [1, 2, 3]       lists opened and joined; empty list adds nothing
nested.stream().flatMap(List::stream).map(n -> n * n).toList();   // [1, 4, 9]

Think of flatMap(f) as "map each element with f to a stream, then concatenate all those streams". The function must return a Stream (not a List), hence List::stream or l -> l.stream().

More uses

  • Words from lines: lines.stream().flatMap(l -> Arrays.stream(l.split("\\s+"))).
  • Skip some elements: return Stream.empty() for an element to drop it, or Stream.of(x) to keep it. Since Java 16, mapMulti does this with less allocation.
  • Optional inside a stream: optionals.stream().flatMap(Optional::stream) (Java 9) keeps only the present values.
  • Pairs: xs.stream().flatMap(x -> ys.stream().map(y -> List.of(x, y))) gives all combinations.

Pitfall: if the function returns null instead of an empty stream, you get a NullPointerException. Return Stream.empty().

Remember: map is one-to-one, flatMap is one-to-many and flattens.

How does reduce work, and what rules must it follow? Intermediate

reduce folds all elements into one value by repeatedly applying a combining function. With an identity value, reduce(0, Integer::sum) returns a plain value (0 for an empty stream). Without it, reduce(Integer::sum) returns an Optional, because an empty stream has no result. The function must be associative and stateless, otherwise parallel streams give wrong answers.

int total = nums.stream().reduce(0, Integer::sum);
Optional<Integer> max = nums.stream().reduce(Integer::max);
// three-argument form: type changes, parallel-safe
int len = words.stream().reduce(0, (sum, w) -> sum + w.length(), Integer::sum);

Associative means (a op b) op c == a op (b op c), so any split into chunks gives the same answer. Subtraction is not associative, so reduce(0, (a,b) -> a-b) is wrong in parallel. The identity must be neutral (0 for add, 1 for multiply). For building a mutable result such as a list or string, do not use reduce (it would copy over and over). Use collect, which is built for mutable containers, or Collectors.joining. For sums, mapToInt(...).sum() is clearer and avoids boxing.

What reduce does, as a fold

Reduce takes a list and collapses it to a single value. With reduce(0, Integer::sum) over [3, 5, 2], it behaves like: start with identity 0, then 0+3=3, then 3+5=8, then 8+2=10. The identity is the starting value and also the answer for an empty stream.

Why associativity matters (parallel picture)

In a parallel stream the data is split, for example [3, 5] and [2, 7]. Each chunk is reduced separately starting from the identity (8 and 9), and then the partial results are combined (8+9 = 17). That only equals the sequential answer if the operation is associative. Check with subtraction:

[10, 3, 2], operation (a, b) -> a - b, identity 0
sequential:              ((0-10)-3)-2        = -15
parallel [10] | [3, 2]:  (0-10) = -10 and (0-3)-2 = -5, combined: -10 - (-5) = -5
two different answers, so subtraction is not a valid reduce function

The identity rule: combine(identity, x) must equal x. For addition the identity is 0, for multiplication 1, for max it is Integer.MIN_VALUE (or use the Optional form).

The three overloads

reduce(U identity, BiFunction accumulator, BinaryOperator combiner)Uresult type differs from element type (sum of lengths)

The classic mistake is using reduce to build a list or a string with +: each step copies the container, which is O(n squared). Use collect(Collectors.toList()) or joining.

Remember: reduce for values (associative, with a neutral identity), collect for containers.

What happens if you use a stream twice? Basic

The second use throws IllegalStateException: stream has already been operated upon or closed. A stream is a one-shot pipeline: once a terminal operation runs, it is finished. If I need to run it again, I create a new stream from the source, usually by keeping a Supplier<Stream<T>> or the original collection.

Stream<String> s = list.stream().filter(x -> x.length() > 2);
s.count();
s.forEach(System.out::println);          // IllegalStateException

Supplier<Stream<String>> src = () -> list.stream().filter(x -> x.length() > 2);
src.get().count();  src.get().forEach(System.out::println);   // fine

The same error appears if you store a stream in a field or cache it. Cache the collected result instead. Also remember that IntStream and other streams over I/O (Files.lines) hold resources and should be closed with try-with-resources.

Why a stream is one-shot

A stream is not data. It is a single traversal that is wired to a source with a "linked" flag. When the terminal operation runs, the stream is marked as consumed. The library does this on purpose: some sources (a socket, a file, a random generator) cannot be replayed at all, so the API treats all streams the same way.

What you see

Stream<String> s = Stream.of("a", "b");
s.forEach(System.out::println);      // prints a, b
s.forEach(System.out::println);      // java.lang.IllegalStateException: stream has already been operated upon or closed

Stream<String> t = Stream.of("a", "b");
Stream<String> u = t.filter(x -> true);
t.map(x -> x);                       // also throws: t was already used to build u (can't branch a stream)

The second example is the less obvious one: even an intermediate operation counts as using the stream, so you cannot "fork" one stream into two pipelines.

Fixes, from simple to heavy

  1. Build a fresh stream from the collection each time (list.stream() is cheap).
  2. Hold a Supplier<Stream<T>> if the pipeline setup is long or comes from a method.
  3. If the source is expensive (I/O), collect once into a list, then stream the list as many times as needed.
  4. Need two results from one pass (sum and count)? Use summaryStatistics(), a teeing collector (Java 12), or a loop.

Pitfall: returning a Stream from a repository method and consuming it after the transaction or connection is closed. The stream may fail then, so collect inside the transaction.

Remember: store the data or a Supplier, never the stream.

Why are there IntStream, LongStream and DoubleStream? Intermediate

They avoid boxing. A Stream<Integer> wraps every number in an object, which costs memory, garbage collection and a pointer lookup per element. IntStream works on raw ints and also gives numeric helpers like sum(), average(), max() and summaryStatistics().

int total = orders.stream().mapToInt(Order::qty).sum();        // no boxing
IntStream.rangeClosed(1, 5).sum();                              // 15
List<Integer> boxed = IntStream.range(0, 3).boxed().toList();  // back to objects
OptionalDouble avg = scores.stream().mapToInt(i -> i).average();

Convert with mapToInt, mapToObj, boxed, asLongStream. In hot loops over millions of numbers the difference is large; in business code over small lists it is noise, so choose the readable form first. average() and max() return OptionalDouble / OptionalInt, since an empty stream has no average.

The cost of boxing, in concrete terms

A primitive int is 4 bytes, stored inline. An Integer is an object on the heap (typically 16 bytes with the header) that the stream refers to by pointer. For one million numbers that is roughly 4 MB versus around 16 MB of objects plus 4 to 8 MB of references (exact numbers depend on the JVM and settings), and more garbage-collection work and cache misses. Small values (about -128 to 127) are cached by Integer.valueOf but most are not.

Example: one problem, three ways

List<Integer> xs = List.of(4, 9, 7);

int s1 = xs.stream().reduce(0, Integer::sum);          // boxes: unbox, add, box, every step
int s2 = xs.stream().mapToInt(Integer::intValue).sum();// unboxes once, then adds raw ints
IntSummaryStatistics st = xs.stream().mapToInt(i -> i).summaryStatistics();
// st.getMin()=4, getMax()=9, getAverage()=6.666..., getSum()=20, getCount()=3

Useful factory methods

  • IntStream.range(0, 5) gives 0..4, rangeClosed(1, 5) gives 1..5. This replaces a counting for loop: IntStream.range(0, n).forEach(i -> ...).
  • "hello".chars() returns an IntStream of char codes: "hello".chars().filter(c -> c == 'l').count() is 2.
  • Arrays.stream(int[]) avoids boxing an int array.

Pitfall: IntStream.sum() overflows silently at the int range. For big totals use mapToLong or asLongStream. And average() on an empty stream returns OptionalDouble.empty(), not 0 and not NaN.

Remember: mapToInt for numbers: faster (no boxing) and gets sum, average and statistics.

3. Collectors

How does groupingBy work, and what are downstream collectors? Intermediate

Collectors.groupingBy(classifier) sorts elements into a Map where the key is what the classifier returns and the value is a list of the elements with that key. A downstream collector as the second argument says what to do with each group instead of making a list, for example counting(), summingInt, mapping or averagingDouble.

Map<String, List<Emp>> byDept   = emps.stream().collect(groupingBy(Emp::dept));
Map<String, Long>       count     = emps.stream().collect(groupingBy(Emp::dept, counting()));
Map<String, Double>     avgSalary = emps.stream().collect(groupingBy(Emp::dept, averagingDouble(Emp::salary)));
Map<String, Set<String>> names     = emps.stream().collect(groupingBy(Emp::dept, mapping(Emp::name, toSet())));
// sorted keys: groupingBy(Emp::dept, TreeMap::new, counting())

The default map is a HashMap (no ordering guarantee), so pass TreeMap::new or LinkedHashMap::new when order matters. The classifier must not return null (NPE).

What it does, with data

Start with five employees: Ann (HR), Bob (IT), Cy (IT), Di (HR), Ed (IT). groupingBy(Emp::dept) calls the classifier on each one and puts it in the bucket of the returned key, so the result is {HR=[Ann, Di], IT=[Bob, Cy, Ed]}. That is the same as the SQL idea GROUP BY dept.

Downstream collectors: SQL aggregates

The one-argument form fills each bucket with a list. A downstream collector replaces that with an aggregate, like the SQL functions after GROUP BY:

Map<String, Map<String, Long>> byDeptAndCity = emps.stream()

Because the three-argument form takes a map supplier, you can choose TreeMap::new for sorted keys. Without it the order is whatever a HashMap gives. Java 12 added teeing for computing two aggregates in one pass.

Pitfall: values inside groups keep encounter order from the stream, but the map itself does not. A key returning null throws NPE ("element cannot be mapped to a null key"). Fix with a default: e -> Objects.requireNonNullElse(e.dept(), "NONE").

Remember: groupingBy(key, downstream): the key makes the buckets, the downstream collector shapes each bucket.

What is partitioningBy, and how is it different from groupingBy? Basic

partitioningBy(predicate) splits a stream into exactly two groups, true and false, and the result map always has both keys, even if one list is empty. groupingBy can make any number of groups and only has keys that actually occurred.

Map<Boolean, List<Integer>> p = nums.stream().collect(partitioningBy(n -> n % 2 == 0));
p.get(true);    // evens
p.get(false);   // odds, an empty list if there are none (never null)
// with downstream: partitioningBy(n -> n > 50, counting())

Use partitioningBy for a yes/no split, where the always-present keys save you null checks. Use groupingBy for categories.

Why a separate collector for two buckets

Splitting into pass/fail is such a common need (valid vs invalid rows, adults vs minors) that the library gives a specialised collector. Its advantage over groupingBy(x -> predicate(x)) is that you always get both keys, so result.get(false) is safe even when nothing failed.

List<Integer> nums = List.of(2, 4, 6);
nums.stream().collect(groupingBy(n -> n % 2 == 0));        // {true=[2, 4, 6]}   no false key at all
nums.stream().collect(partitioningBy(n -> n % 2 == 0));    // {false=[], true=[2, 4, 6]}   both keys

Map<Boolean, Long> counts = nums.stream().collect(partitioningBy(n -> n > 3, counting()));
// {false=1, true=2}

How does Collectors.toMap behave with duplicate keys and nulls? Intermediate

With duplicate keys, toMap throws IllegalStateException: Duplicate key ... unless I pass a third argument, a merge function that decides what to do with two values for the same key. A null value throws a NullPointerException because it uses HashMap.merge internally.

Map<String,Integer> m = words.stream()
    .collect(Collectors.toMap(w -> w, w -> 1, Integer::sum));       // counts duplicates
// keep insertion order:
.collect(toMap(Emp::id, e -> e, (a, b) -> a, LinkedHashMap::new));  // keep first

This is a production-incident classic: code works on test data and then fails when real data has a duplicate. Decide the rule on purpose (keep first, keep last, sum, or collect into a list with groupingBy). If you want all values per key, groupingBy is the right tool, not toMap. The map type is HashMap unless you pass a supplier as the fourth argument.

What goes wrong, as an example

record Emp(int id, String name) {}
List<Emp> es = List.of(new Emp(1, "Ann"), new Emp(2, "Bob"), new Emp(1, "Ann2"));

es.stream().collect(Collectors.toMap(Emp::id, Emp::name));
// IllegalStateException: Duplicate key 1 (attempted merging values Ann and Ann2)

es.stream().collect(Collectors.toMap(Emp::id, Emp::name, (a, b) -> b));   // {1=Ann2, 2=Bob}  keep last
es.stream().collect(Collectors.toMap(Emp::id, Emp::name, (a, b) -> a));   // {1=Ann, 2=Bob}   keep first

The merge function gets the old value and the new value and returns what to store. Typical choices: keep one of them, add them (Integer::sum, a word-count), concatenate ((a, b) -> a + "," + b), or take the max.

Null values and keys

toMap is implemented with HashMap.merge, which does not allow a null value, so a null value gives a NullPointerException (a null key is allowed by HashMap but is not usually what you want). The fix is to filter nulls first, or use a plain loop with put, or Optional as the value.

Map type and ordering

The four-argument form lets you choose the map: LinkedHashMap::new to keep encounter order, TreeMap::new for sorted keys, or ConcurrentHashMap::new. There is also Collectors.toUnmodifiableMap (Java 10) and toConcurrentMap for parallel streams.

When to choose: toMap if the key is guaranteed unique (an id), with a merge function if not sure. groupingBy if many values per key are expected. Pitfall: the message says "Duplicate key" but not which stream element is to blame in older versions, so log the data when you see it in production.

Remember: toMap needs a merge function unless keys are guaranteed unique, and null values blow up.

Stream.toList() versus Collectors.toList(): what is the difference? Intermediate

Stream.toList() (Java 16) returns an unmodifiable list and allows null elements. Collectors.toList() returns a list whose type and mutability are not promised: in practice an ArrayList that you can change. If code later calls add on the result, replacing one with the other causes UnsupportedOperationException.

The other options: Collectors.toUnmodifiableList() (Java 10) is also unmodifiable but throws on null elements, and Collectors.toCollection(ArrayList::new) is how you ask for a specific mutable type. My default is toList() because most results are never edited, and an immutable result is safer to share. Note that "unmodifiable" is a shallow guarantee: the objects inside can still change.

var a = Stream.of(1, 2, 3).collect(Collectors.toList());     // ArrayList in practice, mutable, allows null

4. Parallel streams and performance

How does a parallel stream work? Intermediate

Calling parallelStream() or .parallel() splits the source into chunks, processes the chunks on several threads and then merges the partial results. By default it uses the shared common ForkJoinPool, whose size is about the number of cores minus one, plus the calling thread.

How well the source splits matters. ArrayList, arrays and IntStream.range split cheaply in halves. LinkedList, Stream.iterate and I/O sources split badly. Parallel only wins when there are many elements, each costs real CPU time, and the operations are independent and stateless. For ordinary business code it is usually slower or no better.

What happens, step by step

  1. Split. The source's Spliterator is asked to split itself in half, repeatedly, until the pieces are small enough (the library aims for several pieces per core so work can be balanced).
  2. Fork. Each piece becomes a task in the ForkJoinPool. Idle worker threads steal tasks from busy ones (work stealing).
  3. Process. Each task runs the same pipeline (filter, map, ...) on its own piece, sequentially.
  4. Join and combine. Partial results are merged: sums are added, lists are concatenated, maps are merged.

The calling thread joins in as a worker too, which is why the pool size is cores minus one.

A tiny example

long count = IntStream.rangeClosed(1, 5_000_000)
        .parallel()
        .filter(PrimeCheck::isPrime)      // CPU heavy, independent per number
        .count();

System.out.println(ForkJoinPool.commonPool().getParallelism());   // e.g. 7 on an 8-core machine
// change the size (JVM option): -Djava.util.concurrent.ForkJoinPool.common.parallelism=4

Splitting and merging are not free. If each element costs a few nanoseconds (adding numbers), the overhead of tasks and handing work between threads exceeds the gain. A rough rule often quoted is that the work should be at least tens of microseconds in total per chunk, but measure rather than trust a number.

Order

A parallel stream over an ordered source (List, array) still gives collect, toList, findFirst and forEachOrdered results in the original order. It is only forEach that runs in no defined order. Keeping the order costs extra coordination. If the order is not needed, unordered() can make distinct, limit and findAny cheaper.

Source quality

Remember: parallel = split, run on the shared common pool, combine. It pays only for big, CPU-heavy, independent work.

When should you NOT use a parallel stream? Senior

I avoid it for blocking work (database, HTTP, files), for small data, for poorly splittable sources, for anything that writes to shared state, and inside servers where other requests share the same common pool. In a service, a parallel stream running slow I/O can starve unrelated endpoints, because all of them share the same few threads.

  • Blocking calls: the pool has only about cores-1 threads, so a handful of slow calls block everything using the pool.
  • Shared state: adding to an ArrayList or incrementing a counter from the lambda is a race (lost rows, exceptions).
  • Ordering and short-circuit costs: findFirst, limit and sorted on ordered parallel streams need extra coordination.
  • Small work: thread handoff costs more than the work.

If I really need parallel I/O, I use an explicit executor (or virtual threads on Java 21) with a sensible size and timeouts, so the failure stays inside my own pool. If I do use a parallel stream for CPU work, I measure first with a realistic data size, for example with JMH, not guess.

The core danger: one shared pool

All parallel streams in a JVM use the same common pool unless you do something special. Suppose a REST service has 8 cores, so the pool has 7 workers. Request A runs a parallel stream where each element makes a 500 ms HTTP call. Those 7 workers are now blocked. Request B, which only wants to do a quick parallel sum, waits in the queue behind them. Latency of unrelated code goes up, and nothing in the stack trace says why. This is called pool starvation, and it is the classic production story.

Two failure modes, shown

// 1. Race on shared state: results are wrong or an exception is thrown
List<Integer> out = new ArrayList<>();
IntStream.range(0, 100_000).parallel().forEach(out::add);
System.out.println(out.size());       // often less than 100000, or ArrayIndexOutOfBoundsException

// 2. Correct and parallel-safe: let the collector merge per-thread results
List<Integer> ok = IntStream.range(0, 100_000).parallel().boxed().toList();     // always 100000

Decision checklist before using parallel

  • Is the work CPU-bound (not waiting on I/O)? If not, stop.
  • Is the data big (many thousands of elements, or few elements but each very expensive)?
  • Does the source split well (ArrayList, array, range)?
  • Are all lambdas stateless and free of shared mutation?
  • Did I measure with a benchmark on realistic data, and is the gain worth the risk?
  • Is this code on a busy server that shares the common pool with other work?

If you do need a different pool

There is a widely used trick of submitting the parallel stream from inside your own ForkJoinPool so it uses that pool, but it relies on implementation behaviour and is not guaranteed by the specification. A cleaner way is to use an explicit ExecutorService with CompletableFuture, or virtual threads (Java 21) for blocking I/O.

Remember: parallel streams are for CPU-bound, independent work on big, splittable data. Never for I/O, never with shared mutable state.

Why are side effects in stream lambdas a problem, and are streams faster than loops? Senior

Stream lambdas should be stateless and free of side effects, because the library may run them in any order, on any thread, or skip them. A lambda that adds to an outside list or updates a counter works in a sequential test and breaks under parallel, or when someone later reorders the pipeline. Streams are also not automatically faster than loops: they are about clarity, and for simple loops over small data a plain for is as fast or faster.

// bad: side effect on outside state
List<String> out = new ArrayList<>();
names.stream().filter(n -> n.length() > 3).forEach(out::add);
// good: let the stream build the result
List<String> out2 = names.stream().filter(n -> n.length() > 3).toList();

Performance myths: streams add a little overhead per pipeline (object creation, indirect calls), the JIT often inlines it away on hot paths, and boxing (Stream<Integer>) is the real cost, so use IntStream for numeric loops. Also be careful with peek: it is for debugging only, and the library may skip it (since Java 9, count() on a sized source skips map and peek because the size is already known). When debugging, peek with a log line or the IDE's stream debugger is fine, but keep it out of committed logic.

What "stateless and side-effect free" means

A side effect is anything a lambda does besides computing a result from its input: changing a variable outside, adding to a list, writing a file. The stream contract says behavioural parameters must not interfere with the source and should be stateless. Why? Because the library may call them from many threads, in a different order than you imagine, more or fewer times than you expect, or lazily at a later time.

Seeing the surprise

List<Integer> seen = new ArrayList<>();
long n = Stream.of(1, 2, 3, 4).peek(seen::add).count();     // Java 9+: count is 4, peek may never run
System.out.println(n + " " + seen);                           // prints "4 []" on Java 9 and later

// order surprise with unordered terminal on a parallel stream
Stream.of("a","b","c","d").parallel().forEach(System.out::print);   // for example "cdab"

In the first example, since the size (4) is known from the source without running the pipeline, count() may skip the whole pipeline, including peek. If your logic lived in the peek, it silently vanished after an upgrade to Java 9. Do not put logic in peek.

Are streams faster than loops?

Not by themselves. A well-written loop over an ArrayList is usually equal or a bit faster for simple work, since the stream creates a few objects and goes through lambda calls (which the JIT frequently inlines on hot code, but not always). Streams win in readability, and in parallel for large CPU-bound work. Typical measured rules: boxing costs more than the stream overhead, so use primitive streams for numbers; very short pipelines in cold code are dominated by warm-up. Do not quote numbers without a JMH benchmark.

Bad (side effect)Good (result from the pipeline)

Remember: build results with collectors, not by mutating outside state. Use streams for clarity, and measure before claiming speed.

When would you choose a for loop over a stream? Intermediate

I use a plain loop when the logic needs early break or continue with several conditions, mutable state across iterations, checked exceptions, or index access, and when a stream version would be harder to read. I use a stream for filter, map, group and aggregate pipelines, where it describes what I want.

Rule of thumb: if the stream needs a multi-line lambda, an outside variable, or peek, it has stopped helping. Stack traces from deep streams are also harder to read than from loops, and debugging is harder. Long chains of more than about five steps become hard to follow, so extract named methods or Predicate variables to document intent. Mixed style is fine: a loop outside, streams inside for the data transformation.

Same task two ways

// Stream wins: filter, transform, collect
List<String> emails = users.stream()
        .filter(User::isActive)
        .map(User::email)
        .sorted()
        .toList();

// Loop wins: early exit, state across iterations, checked exception
double balance = 0;
for (Txn t : txns) {
    if (t.isReversal()) continue;
    balance += t.amount();
    if (balance < 0) throw new InsufficientFundsException(t.id());   // checked exception, early stop
}

Why the loop wins in the second case

The running balance is state that changes per element. A stream would need a mutable outside variable, which is exactly the thing streams avoid, or a clever reduce that is harder to read. The checked exception cannot be thrown from a lambda cleanly. And break logic is awkward (takeWhile (Java 9) helps in simple cases).

Pitfall: do not turn a simple loop into a ten-line stream just to look modern. In a code review, ask "which one would I understand in six months?" Also be careful when debugging: a stack trace inside a stream shows many library frames, whereas a loop shows only your own code.

Remember: streams for transformations, loops for control flow and state. Pick the one a teammate reads fastest.

5. Optional

What is Optional for, and how should you use it? Basic

Optional<T> is a container that holds either one value or nothing. It is meant for method return types, to say in the signature "this may have no result" so the caller cannot forget to handle it. I do not use it for fields, method parameters, collections elements or JSON/entity properties.

Optional<User> findByEmail(String email);        // good: return type

String city = findByEmail(e)
    .map(User::address).map(Address::city)         // transform if present
    .filter(c -> !c.isBlank())
    .orElse("unknown");                            // default if empty
findByEmail(e).ifPresentOrElse(this::welcome, this::register);   // Java 9

Main methods: map, flatMap, filter, orElse, orElseGet, orElseThrow, ifPresent, isPresent/isEmpty. Optional is not Serializable, adds an object allocation, and is not designed for fields. For a method returning a collection, return an empty collection, never an Optional<List>.

The problem it solves

Tony Hoare called null his "billion-dollar mistake". The trouble is that a method returning User does not tell you in its type whether it can return null, so the null pointer shows up far away, at run time. With Optional<User> the signature itself warns the caller: "there may be nothing here", and the compiler forces you to unwrap it before using it as a User.

Before and after

// before: nested null checks
String city = null;
User u = repo.findByEmail(email);
if (u != null) {
    Address a = u.getAddress();
    if (a != null) { city = a.getCity(); }
}
if (city == null) city = "unknown";

// after: one chain, no null checks
String city2 = repo.findByEmail(email)               // Optional<User>
        .map(User::getAddress).map(Address::getCity)
        .orElse("unknown");

Creating one

Optional.of(x)x is definitely not null (NPE otherwise)
Optional.ofNullable(x)x may be null, then empty
Optional.empty()no value

Why not for fields and parameters

  • Fields: Optional is not serializable, adds an extra object per field, and the Optional reference itself could still be null.
  • Parameters: callers must wrap values, and a caller can still pass null for the Optional. Use two overloads, or accept a nullable value and document it.
  • Collections: an empty list already means "nothing". An Optional<List<T>> has two ways to say "none".
  • Primitives: use OptionalInt, OptionalDouble to avoid boxing.

Java's own guidance (from the JDK architects) is that Optional is "limited to use as a return type". Method isEmpty() arrived in Java 11, or(), stream() and ifPresentOrElse() in Java 9.

Remember: Optional is a return type that says "may be empty". Not a field, not a parameter.

What are the common Optional anti-patterns? Intermediate

The big ones are calling get() without checking (it throws NoSuchElementException and is just a hidden null pointer), writing if (opt.isPresent()) opt.get() instead of using map/orElse, passing Optional as a parameter or field, and returning null from a method that returns Optional.

// bad
if (opt.isPresent()) { return opt.get().getName(); } else { return "none"; }
// good
return opt.map(User::getName).orElse("none");

// bad: Optional.of(null) throws, and null Optional is worse
Optional<User> find() { return null; }
// good
Optional<User> find() { return Optional.ofNullable(lookup()); }

Other smells: Optional.of(x) when x may be null (NPE; use ofNullable), wrapping just to unwrap, and using orElseThrow() (Java 10, no-arg) where a meaningful exception with a message is better. If you need the exception, orElseThrow(() -> new NotFound(id)) is the idiom.

Why these are anti-patterns

Each of them throws away the point of Optional, which is to avoid forgetting the empty case. Using get() without a check makes the Optional just a slower null. isPresent() followed by get() is the old null check written in new clothing, and it is easy to forget the else branch.

Outputs of the common mistakes

Remember: prefer map, orElse and orElseThrow over isPresent plus get. Never return null from an Optional method.

What is the difference between orElse and orElseGet? Basic

orElse(x) takes a ready value, so the argument is always evaluated, even when the Optional has a value. orElseGet(supplier) only runs the supplier when the Optional is empty. If the default is expensive or has side effects (database call, creating an object, logging), use orElseGet.

User u = repo.findById(id).orElse(createDefaultUser());       // createDefaultUser() runs EVERY time
User u = repo.findById(id).orElseGet(() -> createDefaultUser()); // only when missing
User u = repo.findById(id).orElseGet(this::createDefaultUser);

With a constant such as orElse("n/a") there is no difference worth caring about. The bug shows up when the "default" saves a row: with orElse, a duplicate row is created on every call, even when the user exists. That is a real production bug (see scenarios).

Why the argument is evaluated always

It is plain Java evaluation order. opt.orElse(expr) is a method call, and before any method is called, Java computes its arguments. So expr runs first, whether or not opt has a value, and its result is then thrown away if not needed. orElseGet(supplier) instead receives a recipe (a lambda). The method decides whether to run the recipe.

Proof with printed output

static String fallback() { System.out.println("fallback called"); return "default"; }

Optional.of("value").orElse(fallback());       // prints "fallback called", returns "value"
Optional.of("value").orElseGet(() -> fallback());   // prints nothing,         returns "value"
Optional.empty().orElseGet(() -> fallback());       // prints "fallback called", returns "default"

The real production bug

// Looks innocent. If the account exists, a NEW row is still created on every call.
Account a = accounts.findByUser(id).orElse(accounts.save(new Account(id)));

// Correct
Account b = accounts.findByUser(id).orElseGet(() -> accounts.save(new Account(id)));

Rule of thumb

Default is...Use
a constant or an existing variable ("n/a", 0, DEFAULT)orElse
a method call, new of something costly, I/O, loggingorElseGet
an errororElseThrow(...)
another Optionalor(() -> other) (Java 9)

The same lazy-versus-eager pattern appears in logging (log.debug(() -> expensive()) with a Supplier) and in Objects.requireNonNull(x, () -> message).

Remember: orElse runs always, orElseGet runs only when empty. Anything with a cost or side effect goes in orElseGet.

Optional.map versus flatMap, and how do you chain nullable getters safely? Intermediate

map applies a function that returns a plain value and wraps the result. flatMap is for functions that already return an Optional, so you do not end up with Optional<Optional<T>>. I use these to replace nested null checks.

// getAddress() may be null; Address.getCity() returns Optional<String>
String city = Optional.ofNullable(user)
    .map(User::getAddress)          // plain value or null -> empty
    .flatMap(Address::getCity)      // already an Optional
    .orElse("unknown");

map treats a null result as empty, so a chain stops quietly at the first missing link. Better still, make the model honest: have findX methods return Optional and keep fields non-null where possible, so the null checks are not needed at all.

The type problem, shown

class User    { Address getAddress() { ... } }                 // may return null
class Address { Optional<String> getCity() { ... } }           // honest: may be absent

Optional<User> ou = Optional.of(user);

Optional<Optional<String>> nested = ou.map(User::getAddress).map(Address::getCity);   // map wraps again: Optional of Optional
Optional<String> flat = ou.map(User::getAddress).flatMap(Address::getCity);        // flatMap does not wrap again

Rule: map(f) wraps whatever f returns. flatMap(f) assumes f already returns an Optional and does not wrap it. This is exactly how Stream.flatMap works too: one level of container is removed.

What happens at each link of a chain

  1. If the Optional is empty, map and flatMap skip the function and stay empty.
  2. If it has a value, the function runs. For map a null result becomes empty. For flatMap the function must return a non-null Optional (null gives a NullPointerException).
  3. The chain ends with orElse, orElseGet, orElseThrow or ifPresent.

Combining two Optionals

Optional<String> name = ..., Optional<Integer> age = ...;
Optional<String> label = name.flatMap(n -> age.map(a -> n + " (" + a + ")"));   // present only if both are present

Also useful: filter to turn a present value into empty if it fails a test, and or (Java 9) to fall back to another Optional-producing source.

Remember: map for value-returning functions, flatMap for Optional-returning ones.

6. java.time (date and time API)

What was wrong with Date and Calendar, and what does java.time fix? Basic

java.util.Date and Calendar are mutable, not thread-safe, have confusing design (months start at 0, years offset from 1900) and mix a point in time with a calendar view. java.time (Java 8) fixes this with immutable, thread-safe types that each say exactly what they hold, and a clear API.

Immutability means every change returns a new object (date.plusDays(1) does not change date), so they are safe to share and cache. DateTimeFormatter is thread-safe, unlike SimpleDateFormat, which causes famous random bugs in shared static fields. Time zones, durations and calendar math are first-class instead of hacks. When old code needs a Date, convert with Date.from(instant) and date.toInstant().

The concrete problems with the old API

  • Mutable and not thread-safe: Date.setTime changes the object in place. Pass one to a method and it can change under you.
  • Confusing numbering: in the deprecated new Date(2024, 1, 15) the year is an offset from 1900, so it means year 3924, and month 0 is January, so 1 means February. Almost nobody got this right the first time.
  • One class for everything: a Date is an instant, but prints as a date in the default zone, and has no time zone field inside.
  • SimpleDateFormat is not thread-safe. A shared static formatter produces corrupted strings or random exceptions under load.
  • Lenient parsing: Calendar accepts month 13 and rolls over to next year silently.

Before and after

// old
Calendar c = Calendar.getInstance();
c.set(2024, Calendar.JANUARY, 31);
c.add(Calendar.MONTH, 1);                 // c is changed in place
SimpleDateFormat f = new SimpleDateFormat("yyyy-MM-dd");   // not thread-safe
String s = f.format(c.getTime());         // 2024-02-29

// new (Java 8)
LocalDate d = LocalDate.of(2024, 1, 31);
LocalDate next = d.plusMonths(1);         // d unchanged; next = 2024-02-29
String s2 = next.format(DateTimeFormatter.ISO_LOCAL_DATE);   // formatter is immutable and thread-safe

The type vocabulary

java.time gives a separate type per idea (date only, time only, instant, zone, duration), so a method signature says what it needs. It is also based on ISO-8601 and uses sensible numbering: January is 1 (and the Month enum exists). Parsing is strict by default, so a bad date throws DateTimeParseException instead of being silently corrected. For legacy code and old libraries, convert at the boundary (Timestamp.toInstant(), Date.from(instant)) and keep java.time inside.

Remember: java.time = immutable, thread-safe, explicit types. Never share a SimpleDateFormat.

Explain LocalDate, LocalDateTime, Instant, ZonedDateTime and OffsetDateTime. When do you use which? Intermediate

I pick by the question "is it a point on the global timeline, or a calendar reading on a wall clock?". Instant is a point in time (UTC), the right choice for timestamps, logs and storage. LocalDate and LocalDateTime are wall-clock values with no time zone, good for birthdays, due dates, or "9 am every day". ZonedDateTime is a local date-time plus a zone such as Asia/Kolkata, used when daylight-saving rules matter. OffsetDateTime is a local date-time plus a fixed offset like +05:30, handy for APIs and databases.

Typical design: store and transport Instant (or UTC), convert to ZonedDateTime only at the edge to show it to a user in their zone. A "meeting every day at 9:00 in London" is a LocalTime plus a ZoneId, not a fixed instant, because the instant shifts with daylight saving.

The deciding question

Ask: "Would two people in different countries agree on the exact moment this refers to?" If yes (a payment time, a log line), it is a point on the global timeline: use Instant. If no (a birthday, "closing time is 18:00", an invoice due date), it is a calendar reading: use LocalDate or LocalDateTime, and add a zone only when you must turn it into a moment.

Same moment, different types

Instant now = Instant.parse("2025-03-10T08:30:00Z");                 // 08:30 UTC
ZonedDateTime kolkata = now.atZone(ZoneId.of("Asia/Kolkata"));       // 2025-03-10T14:00+05:30[Asia/Kolkata]
ZonedDateTime london  = now.atZone(ZoneId.of("Europe/London"));      // 2025-03-10T08:30Z[Europe/London]
LocalDateTime wall    = kolkata.toLocalDateTime();                   // 2025-03-10T14:00   (zone information is gone)
OffsetDateTime odt    = kolkata.toOffsetDateTime();                  // 2025-03-10T14:00+05:30
wall.atZone(ZoneId.of("Asia/Kolkata")).toInstant().equals(now);      // true, if we put the zone back

Notice that LocalDateTime alone cannot be turned back into a moment without being told the zone. That is the main trap: storing a LocalDateTime for "when something happened" loses information, and breaks when servers move or daylight saving changes.

Choosing, as a table

NeedType

Why not just OffsetDateTime everywhere? An offset like +01:00 does not know the region's daylight-saving rules, so adding six months may land at the wrong wall-clock time. A zone id does know.

Remember: Instant = when it happened. Local = what the clock says. Zoned = the clock in a place, with DST.

What is the difference between Duration and Period? Intermediate

Duration is an exact amount of time in seconds and nanoseconds (hours, minutes), used between two instants. Period is a calendar amount in years, months and days, used between two dates. A day in a Period is "one calendar day", which can be 23 or 25 hours long on a daylight-saving change, while a Duration of 24 hours is always 86,400 seconds.

Duration.between(startInstant, endInstant).toMinutes();
Period.between(LocalDate.of(2024,1,31), LocalDate.of(2024,3,1));   // P1M1D
ChronoUnit.DAYS.between(d1, d2);                                    // total days
zdt.plusDays(1)    // same clock time next day (calendar)
zdt.plus(Duration.ofHours(24))   // exactly 24 hours later (may shift the clock)

Month arithmetic clamps: Jan 31 plus one month is Feb 29 (leap year) or Feb 28, not an error.

Why two classes

"One day" has two meanings. A physical day is always 24 hours (86,400 seconds). A calendar day is "the same clock time tomorrow", which is 23 or 25 hours long on daylight-saving change days. The same holds for a month: 28, 29, 30 or 31 days. Duration captures the first meaning (exact seconds), Period the second (calendar fields).

A daylight-saving example with real values

ZoneId ny = ZoneId.of("America/New_York");
ZonedDateTime start = ZonedDateTime.of(2025, 3, 8, 12, 0, 0, 0, ny);   // the day before spring-forward (Mar 9, 2025)

start.plusDays(1);                    // 2025-03-09T12:00-04:00  same clock time (only 23 hours passed)
start.plus(Duration.ofHours(24));     // 2025-03-09T13:00-04:00  exactly 24 hours (clock shows 13:00)

Duration d = Duration.between(start, start.plusDays(1));    // PT23H
d.toMinutes();                                              // 1380

Period arithmetic

LocalDate a = LocalDate.of(2024, 1, 31), b = LocalDate.of(2024, 3, 1);
Period p = Period.between(a, b);            // P1M1D  (one month and one day)
p.getMonths();                              // 1
ChronoUnit.DAYS.between(a, b);              // 30  total days: use this for "days between"
a.plusMonths(1);                            // 2024-02-29  (clamps to the last valid day)

Pitfall: Period.getDays() returns only the days part (1 above), not the total, which surprises people who expect 30. Also, Duration does not accept a date-only type (LocalDate has no time), so Duration.between(date1, date2) throws UnsupportedTemporalTypeException. Use Period or ChronoUnit.DAYS.

Remember: Duration = machine time (seconds). Period = calendar time (years, months, days).

How does java.time handle time zones and daylight saving gaps and overlaps? Senior

A ZoneId carries the region's rules, including every offset change. Two local times are troublesome around the change: a gap (spring forward) when some local times do not exist, and an overlap (fall back) when some local times happen twice. ZonedDateTime resolves both for you in a documented way: gap times are shifted forward by the length of the gap, and overlap times use the earlier offset by default (withLaterOffsetAtOverlap() selects the later one).

Practical rules: store Instant or UTC, so no ambiguity; do calendar math (plusDays) on ZonedDateTime and not on raw seconds; schedule jobs in UTC or use a scheduler that understands zones, because a "daily at 02:30 local" job is skipped once a year and may run twice another day. Never hard-code offsets like +01:00 for a region. Use zone ids like Europe/Paris, and keep the JDK's tz data updated, since governments change rules.

The two odd moments, with real clock numbers

In a zone like Europe/Paris, on the last Sunday of March the clock jumps from 02:00 to 03:00 (spring forward). The local times 02:00 to 02:59 never happen. On the last Sunday of October the clock goes from 03:00 back to 02:00 (fall back), so 02:00 to 02:59 occurs twice. (Exact dates and hours depend on the region and year, since they come from the tz database.)

ZoneId paris = ZoneId.of("Europe/Paris");
// Gap: 2025-03-30 02:30 does not exist in Paris
ZonedDateTime gap = ZonedDateTime.of(LocalDateTime.of(2025, 3, 30, 2, 30), paris);
System.out.println(gap);          // 2025-03-30T03:30+02:00[Europe/Paris]   shifted forward by the gap length

// Overlap: 2025-10-26 02:30 happens twice
LocalDateTime amb = LocalDateTime.of(2025, 10, 26, 2, 30);
ZonedDateTime first  = ZonedDateTime.of(amb, paris);                       // 02:30+02:00 (earlier offset)
ZonedDateTime second = first.withLaterOffsetAtOverlap();                   // 02:30+01:00
Duration.between(first, second);                                           // PT1H

If you want to see the raw possibilities, paris.getRules().getValidOffsets(ldt) returns zero offsets in a gap, two in an overlap and one normally.

What goes wrong in production

  • A local-time cron/scheduler job at 02:30: skipped on the spring day (or run at 03:30), run twice on the fall day. Schedule in UTC for system tasks, and only use local time for user-facing ones, with a scheduler that handles zones.
  • Storing LocalDateTime for events: the 02:30 that happened twice is indistinguishable, so ordering by the stored value is wrong.
  • Adding hours across the change: plusHours(24) and plusDays(1) give different clock times (see the Period answer).
  • Outdated tz data: governments change rules (a country scrapping DST, or shifting the date). Keep the JDK patched, since the tz database ships inside it.
  • Fixed offsets for a region: +01:00 is not Paris; Paris is +01:00 in winter and +02:00 in summer.

Remember: store UTC (Instant), show in a zone, and never trust a plain local time around a clock change.

How do you make time-dependent code testable? Intermediate

I inject a java.time.Clock instead of calling Instant.now() or LocalDate.now() directly. In production I pass Clock.systemUTC(), and in tests a fixed clock, so the result does not depend on when the test runs.

class TokenService {
    private final Clock clock;
    TokenService(Clock clock) { this.clock = clock; }
    boolean isExpired(Instant expiry) { return Instant.now(clock).isAfter(expiry); }
}
// test
Clock fixed = Clock.fixed(Instant.parse("2025-01-01T10:00:00Z"), ZoneOffset.UTC);
new TokenService(fixed).isExpired(Instant.parse("2025-01-01T09:00:00Z"));  // true

All now() methods have an overload that takes a Clock. This avoids static mocking and sleeping in tests, and makes tests for expiry, DST or month-end easy to write. For a clock that moves, Clock.offset or a small mutable test clock works.

Why a direct call to now() is a problem

Instant.now() is a hidden input: it reads the system clock. A test for "token is expired" would pass or fail depending on the day it runs, or would need Thread.sleep, which is slow and flaky. Making the clock an explicit dependency (dependency injection) means the test controls time.

How Clock works

Clock is an abstract class with a source of "current instant" plus a zone. All the now() methods have an overload that takes one: Instant.now(clock), LocalDate.now(clock), ZonedDateTime.now(clock). The factories:

FactoryBehaviour
Clock.systemUTC() / systemDefaultZone()real time, for production
Clock.fixed(instant, zone)always returns the same instant, for deterministic tests
Clock.offset(base, duration)base clock shifted by a duration ("30 minutes from now")
Clock.tick(base, duration) (and tickSeconds, tickMinutes)rounds the time to whole units

Simulating time passing

class MutableClock extends Clock {
    private Instant now; private final ZoneId zone;
    MutableClock(Instant start, ZoneId zone) { this.now = start; this.zone = zone; }
    void advance(Duration d) { now = now.plus(d); }
    @Override public Instant instant() { return now; }
    @Override public ZoneId getZone() { return zone; }
    @Override public Clock withZone(ZoneId z) { return new MutableClock(now, z); }
}
// test: create token at 10:00, advance 61 minutes, assert expired (token lifetime 60 minutes)

In Spring, expose a Clock bean. Pitfall: one stray LocalDate.now() inside a deep helper makes a test flaky only near midnight or at the end of the month, a very hard bug to reproduce. A code search for .now() calls with no arguments helps find them.

Remember: inject Clock, don't call now() directly.

7. Language features: var, factories, records, sealed, patterns, switch

What do var and text blocks do, and what are their rules? Basic

var (Java 10) lets the compiler infer a local variable's type from the right-hand side. It is still static typing, just less typing. Text blocks (final in Java 15) are multi-line string literals between triple quotes, great for JSON, SQL and HTML without escape noise.

var users = new ArrayList<User>();           // inferred ArrayList<User>
String json = """
    {
      "name": "Asha",
      "age": 30
    }
    """;                                        // closing quotes position sets the indent

var rules: only for local variables (and for-loop variables, lambda parameters from Java 11), always needs an initializer, cannot be null, a lambda or an array initializer alone, and is not allowed for fields, parameters or return types. Use it when the type is obvious from the right side, not when it hides information (var x = process(); tells the reader nothing). Text blocks strip the common leading indentation, so the closing delimiter's position controls it, and a trailing backslash joins lines. Handy String methods from 11 on: isBlank(), strip(), lines(), repeat(n), and formatted() (15).

var: what it is and is not

var is not dynamic typing like JavaScript. The compiler works out the type once, at compile time, from the right-hand side, and the variable keeps that fixed type. It was added in Java 10 to cut noise like Map<String, List<Order>> m = new HashMap<String, List<Order>>();.

var n = 10;                    // int
var list = new ArrayList<String>();   // ArrayList<String>, not List<String>
list.add("x");                 // fine
// list.add(5);                // still a compile error: static typing is unchanged
// var x;                      // error: cannot infer type (no initializer)
// var y = null;               // error: null has no type
// var f = () -> 1;            // error: a lambda needs a target type

Two gotchas: the inferred type is the exact right-hand type, so var list = new ArrayList<>() is an ArrayList<Object>, and a variable declared var x = 1; cannot later hold a long. Use var when the type is obvious from the right side (new, a constructor, a clear factory) and avoid it when the reader must guess (var r = service.process();).

Text blocks: how the indentation works

  1. The opening triple quote must be followed by a line break. Content starts on the next line.
  2. The compiler finds the smallest indentation among all content lines and the closing delimiter line, and removes that much from every line.
  3. Trailing spaces on each line are stripped, and line breaks become a newline character.
String sql = """
        SELECT id, name
          FROM users
         WHERE active = true
        """;
// value: "SELECT id, name\n  FROM users\n WHERE active = true\n"
// closing quotes further left keep extra indentation; closing quotes on the last text line remove the final newline

Escapes still work. A backslash at the end of a line joins it with the next (no newline), and \s keeps a trailing space. Use .formatted(args) (Java 15) for placeholders. Never paste user input into a text block to build SQL: it is still string concatenation, so use prepared statements.

Remember: var = inferred, still strongly typed, locals only. Text blocks = multi-line strings that strip common indentation.

How do List.of, Set.of and Map.of work, and how do they differ from Arrays.asList? Intermediate

List.of, Set.of and Map.of (Java 9) create truly immutable collections: any change throws UnsupportedOperationException, and null elements are not allowed. Arrays.asList is only fixed-size: you can set elements, and writes go through to the backing array, but you cannot add or remove.

  • List.of(1, null) throws NPE. Even List.of(...).contains(null) throws NPE.
  • Set.of and Map.of reject duplicates with IllegalArgumentException, and their iteration order is randomised per JVM run, so never depend on it.
  • List.copyOf(c) (Java 10) makes an immutable copy, and returns the same list if it is already immutable.
  • Collections.unmodifiableList(c) is only a read-only view: if someone changes the original, the view changes.

Immutable collections are safe to share between threads and to return from a method. They are shallow: the objects inside can still be mutable.

Why the factories were added

Before Java 9, a small constant list took three lines (create, add, wrap) or the "double-brace" hack, which creates an extra anonymous class. List.of gives a short, safe, immutable and compact collection.

What is a record, what do you get for free, and what are its limits? Basic

A record (final in Java 16) is a short way to declare an immutable data carrier. From one line the compiler generates the private final fields, a canonical constructor, accessors named after the fields (name(), not getName()), and equals, hashCode and toString based on all components. I use records for DTOs, value objects, map keys and results returned from methods.

public record Point(int x, int y) {
    public Point {                                   // compact constructor: validate
        if (x < 0 || y < 0) throw new IllegalArgumentException("negative");
    }
    double distance() { return Math.sqrt(x * x + y * y); }   // extra methods allowed
    static Point origin() { return new Point(0, 0); }
}

Limits: a record is implicitly final, cannot extend a class (it can implement interfaces), cannot declare extra instance fields, and its fields are shallowly immutable, so a List component can still be changed unless you copy it with List.copyOf in the compact constructor. Records do not suit JPA/Hibernate entities, which need a no-argument constructor, mutability and proxies. They are fine for projections and API objects. Modern Jackson (2.12+) and Spring support them.

The problem

A plain "data class" in old Java takes about 40 lines for two fields: private final fields, a constructor, getters, equals, hashCode, toString. It is boring and easy to get wrong (forgetting one field in hashCode). Libraries like Lombok hid this with annotation processing. A record makes the language do it in one line.

Before and after

// Java 8: a value class
public final class Point {
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public int getX() { return x; }  public int getY() { return y; }
    @Override public boolean equals(Object o) { /* 6 lines */ }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point[x=" + x + ", y=" + y + "]"; }
}

// Java 16
public record Point(int x, int y) {}

var p = new Point(3, 4);
p.x();                                   // 3 (accessor has no "get")
p.equals(new Point(3, 4));               // true, compared field by field
System.out.println(p);                   // Point[x=3, y=4]

Customising a record

  • Compact constructor (no parameter list) runs before the fields are assigned: validate or normalise the parameters there, for example name = name.trim();.
  • Defensive copy for collections: public Order { items = List.copyOf(items); } makes the record deeply immutable for that field.
  • Extra constructors must delegate to the canonical one: Point() { this(0, 0); }.
  • Static fields and methods are allowed. Extra instance fields are not.
  • Records may be nested, local (inside a method, handy for intermediate stream results) and generic: record Pair<A,B>(A first, B second) {}.

A subtle point: an array component is compared by reference in the generated equals, which is almost never what you want, so avoid arrays as components.

Remember: record = final fields + constructor + accessors + equals/hashCode/toString. For data, not entities. Immutable only as deep as its components.

What are sealed classes and interfaces, and why are they useful? Intermediate

A sealed type (final in Java 17) lists exactly which classes may extend or implement it, using permits. That gives me a closed hierarchy: the compiler knows every subtype, so a switch over it can be checked for completeness and I need no default branch. Each permitted subclass must be final, sealed or non-sealed.

sealed interface Shape permits Circle, Square, Rect {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}
record Rect(double w, double h) implements Shape {}

double area(Shape s) {
    return switch (s) {                       // Java 21: no default needed
        case Circle c -> Math.PI * c.r() * c.r();
        case Square q -> q.side() * q.side();
        case Rect r   -> r.w() * r.h();
    };
}

Permitted subclasses must be in the same module (or the same package if no modules). Compared with an enum, a sealed hierarchy lets each case carry different data. Compared with the visitor pattern, it is much less code.

The problem: open hierarchies cannot be checked

With a normal interface anyone can add a new implementation tomorrow, so a method that handles "all kinds of Shape" can never be sure it covered them all. You end up with a default branch that hides new cases, or an else throw that fails at run time. Enums solve this for fixed values, but each enum constant has the same shape. A sealed type solves it for types that carry different data.

How to declare one

public sealed interface Payment permits Card, Upi, Cash {}                 // Java 17
public record Card(String number, String holder) implements Payment {}    // records are final automatically
public record Upi(String vpa) implements Payment {}
public final class Cash implements Payment {}

public sealed class Account permits Savings, Current {}                    // classes too
public final class Savings extends Account {}
public non-sealed class Current extends Account {}                         // non-sealed: opens the hierarchy again below this class

Each permitted subclass must say one of three things: final (no more subclasses), sealed (with its own permits list), or non-sealed (anyone may extend it). If all subclasses are in the same source file you may omit permits and the compiler infers them.

What you gain

  • Exhaustive switch: no default, and adding Wallet to the permits list breaks every switch that forgot it, at compile time. This is the main benefit: missing cases become compile errors.
  • Domain modelling as "one of these": Result = Success | Failure, Event = Created | Updated | Deleted, an expression tree, a parser's tokens.
  • Replaces the visitor pattern in most cases, with far less code.

Trade-offs: the library author controls the list. Adding a subtype is a source-breaking change for callers that switch exhaustively (that is intended, but plan for it in a public API). Tools that create runtime subclasses of your types (some mocking tools) cannot extend final or sealed types the usual way.

Remember: sealed = a closed list of subtypes, so the compiler can check a switch is exhaustive.

What is pattern matching for instanceof? Basic

It combines the type check and the cast in one step (final in Java 16). If the check succeeds, a new variable of that type is already available, so I do not cast manually.

// before
if (obj instanceof String) { String s = (String) obj; use(s.length()); }
// Java 16+
if (obj instanceof String s && s.length() > 3) { use(s); }
if (!(obj instanceof String s)) return;   // s is in scope after this line
use(s);

The pattern variable is only in scope where the compiler can prove the match succeeded, which includes the right side of && and code after an early return. This is also why equals methods get shorter: return o instanceof Point p && x == p.x && y == p.y;. Java 21 extends the idea to record patterns, such as o instanceof Point(int x, int y), which takes a record apart.

The repetition it removes

The old idiom writes the type three times and invites mistakes: check, cast, and declare. If the check and the cast ever disagree after a refactor, you get a ClassCastException at run time. The pattern form makes this impossible, because the variable only exists where the check succeeded.

// before: type written 3 times
if (shape instanceof Circle) {
    Circle c = (Circle) shape;
    return Math.PI * c.r() * c.r();
}
// Java 16
if (shape instanceof Circle c) {
    return Math.PI * c.r() * c.r();
}

Scope rules, the part interviewers probe

The binding variable is in scope only where the compiler can prove the match succeeded (called flow scoping).

if (o instanceof String s && s.length() > 3) { ... }     // ok: right side of && only runs when matched
if (o instanceof String s || s.isEmpty()) { ... }       // compile error: s is not definitely matched here
if (!(o instanceof String s)) { return; }               // s is in scope AFTER the if, since we returned otherwise
System.out.println(s.length());

A real use: equals

@Override public boolean equals(Object o) {
    return this == o || (o instanceof Point p && x == p.x && y == p.y);
}

If the object is null, instanceof is false, so null never matches. In Java 21 you can also nest patterns for records: if (o instanceof Line(Point(var x1, var y1), var end)). The feature was preview in 14 and 15 and final in 16.

Remember: x instanceof T t checks, casts and names it in one go.

What is the difference between the old switch statement and a switch expression? Intermediate

A switch expression (final in Java 14) produces a value, uses -> arms with no fall-through and no break, and must cover every case. The old statement falls through to the next label unless you write break, which is a classic bug source.

int days = switch (month) {
    case FEB -> 28;
    case APR, JUN, SEP, NOV -> 30;
    default -> 31;
};
String label = switch (code) {
    case 1 -> "low";
    case 2 -> { log(code); yield "high"; }     // block arm: use yield to return a value
    default -> "unknown";
};

Because it is an expression, the compiler checks that every possible input yields a value: an enum switch without default must list all constants, or the code does not compile. That makes adding a new enum constant a compile error in the places you forgot. yield returns a value from a block arm. The old colon form with yield also exists, but is rarely used.

The old switch and its traps

// Old statement: falls through unless you break
switch (day) {
    case SAT:
    case SUN: type = "weekend"; break;
    case MON: type = "start";               // missing break: also runs the next line
    default:  type = "mid";                 // so MON ends as "mid"
}

The old switch had four problems: fall-through by default (a classic bug source), one shared variable scope for all cases, a value had to be assigned from inside each branch, and nothing checked that every case was handled.

The new form fixes all four

String type = switch (day) {                       // an expression: produces a value
    case SAT, SUN -> "weekend";                    // several labels per arm
    case MON      -> "start";
    case TUE, WED, THU, FRI -> {                   // block arm
        log.debug("weekday " + day);
        yield "mid";                               // yield returns the value of the block
    }
};                                                 // enum with all 7 days covered: no default needed
  • No fall-through: only the matching arm runs.
  • Exhaustive: for an enum, listing all constants is enough, and if someone adds a constant later the switch stops compiling. For int and String selectors a default is required.
  • Each arm has its own scope.
  • Can throw: default -> throw new IllegalArgumentException("bad " + code); is a good idiom.

The arrow form can also be used as a statement (no value needed, still no fall-through). The colon form with yield exists and still falls through, and the compiler forbids mixing the two styles in one switch. History: preview in 12 and 13, final in 14.

Pitfall: when an enum switch is exhaustive without default, the compiler adds a hidden throwing branch (an error type, MatchException in Java 21) in case a new constant appears in a separately compiled library. Recompile everything that switches over a changed enum.

Remember: arrow arms mean no fall-through. A switch expression returns a value and must be exhaustive.

Explain pattern matching for switch, guards with when, record patterns and case null. Senior

Since Java 21, a switch can match on the type of its selector, not only on constants. Each case declares a type pattern with a variable, may add a guard with when, can take records apart (record patterns), and can handle null explicitly. On a sealed type the compiler checks the switch is complete.

String describe(Object o) {
    return switch (o) {
        case null                          -> "nothing";
        case Integer i when i > 100        -> "big int " + i;
        case Integer i                     -> "int " + i;
        case String s                      -> "text of length " + s.length();
        case Point(int x, int y) when x == y -> "diagonal point";
        case Point(int x, int y)           -> "point " + x + "," + y;
        default                            -> "something else";
    };
}

Rules to remember. Order matters: a more general case before a specific one is a compile error ("dominated"), and guarded cases must come before the unguarded one of the same type. Without case null, a null selector throws NullPointerException as it always did. Record patterns can nest, case Line(Point(var x1, var y1), Point p2), to destructure deeply. This replaces long if instanceof chains and the visitor pattern. Pattern switch and record patterns became final in Java 21, after previews from 17 to 20.

From scratch: what changed in Java 21

Until Java 20, case labels could only be constants (numbers, strings, enum values). To branch on the type of an object you wrote an if-else chain of instanceof with casts. Pattern-matching switch lets each case say "if the object is a Type, call it name and run this arm".

Before and after

// before
static String fmt(Object o) {
    if (o instanceof Integer) { return "int " + (Integer) o; }
    else if (o instanceof String) { return "str " + ((String) o).length(); }
    else if (o == null) { return "null"; }
    else { return "other"; }
}
// Java 21
static String fmt(Object o) {
    return switch (o) {
        case null       -> "null";
        case Integer i  -> "int " + i;
        case String s   -> "str " + s.length();
        default         -> "other";
    };
}
fmt(42); fmt("abc"); fmt(null);     // "int 42", "str 3", "null"

Record patterns: taking data apart

sealed interface Expr permits Num, Add, Mul {}
record Num(int v) implements Expr {}
record Add(Expr l, Expr r) implements Expr {}
record Mul(Expr l, Expr r) implements Expr {}

static int calc(Expr e) {
    return switch (e) {                                   // sealed + all cases = no default
        case Num(int v)          -> v;
        case Add(Expr l, Expr r) -> calc(l) + calc(r);
        case Mul(Num(var a), Num(var b)) -> a * b;       // nested pattern: both sides are Num
        case Mul(Expr l, Expr r) -> calc(l) * calc(r);
    };
}
calc(new Add(new Num(2), new Mul(new Num(3), new Num(4))));   // 14

The pattern Add(Expr l, Expr r) checks the type and extracts the fields in one step. No casts and no getters.

Rules that cause compile errors

  • Dominance: a case that can never be reached because an earlier, more general case already matches is an error. Put guarded and more specific cases first. case Integer i before case Integer i when i > 100 will not compile.
  • Exhaustiveness: the switch must cover all values. For Object you need a default or a total pattern. For a sealed type, covering all permitted subtypes is enough.
  • Null: a pattern switch without case null still throws NullPointerException on a null selector. With case null you choose what happens (and may write case null, default -> ...).
  • Guards: when follows the pattern, is a boolean expression and can use the bound variable.

History: instanceof patterns final in 16; switch patterns previewed in 17 to 20 and final in 21; record patterns previewed in 19 and 20 and final in 21; unnamed patterns (_) final in 22.

Remember: specific cases first, guard with when, add case null if null is possible, and let sealed types remove the default.

What are virtual threads (Java 21), and when do they help? Senior

Virtual threads are lightweight threads managed by the JVM, not the operating system. I can create millions of them, one per task, and write plain blocking code. When a virtual thread blocks on I/O, the JVM unmounts it from its carrier (a real OS thread) and runs another one, so the carrier is never wasted waiting. They help for I/O-bound servers with many concurrent requests. They do not help CPU-bound work.

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var url : urls) ex.submit(() -> fetch(url));    // one VT per task
}                                                         // close() waits for tasks

Rules: do not pool virtual threads (they are cheap; create one per task), and limit concurrency to protected resources such as a database with a Semaphore or a bounded connection pool, otherwise a million VTs flood it. A virtual thread can get pinned to its carrier while inside synchronized (before Java 24) or a native call, which hurts scalability; prefer ReentrantLock. Use ThreadLocal sparingly, because there will be millions. Spring Boot 3.2+ enables them with spring.threads.virtual.enabled=true.

The problem they solve

A classic server uses one OS thread per request. An OS thread reserves on the order of a megabyte of stack (depends on settings) and the OS scheduler struggles with tens of thousands of them. Most of the time those threads just wait on a database or HTTP call, so you can serve only a few thousand concurrent requests while the CPU is idle. The earlier fix was asynchronous or reactive code, which scales but is harder to write and debug.

How virtual threads fix it, step by step

  1. You start a virtual thread with ordinary code, including normal blocking calls.
  2. The JVM mounts it on a carrier thread (a platform thread from a small pool, about the number of cores) and runs it.
  3. When the code blocks on I/O, a sleep or a java.util.concurrent lock, the JVM saves the virtual thread's stack to the heap (unmounting) and the carrier is free to run another virtual thread.
  4. When the I/O completes, the virtual thread is scheduled again, possibly on a different carrier.

A virtual thread starts with a tiny stack that grows on the heap as needed, so hundreds of thousands are practical. It is "waiting made cheap".

Creating them

Thread.startVirtualThread(() -> handle(req));
Thread t = Thread.ofVirtual().name("worker-", 0).start(task);
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {       // one new VT per submitted task
    List<Future<String>> fs = urls.stream().map(u -> ex.submit(() -> fetch(u))).toList();
}   // close() waits for all tasks

What to watch for

CPU-bound work gets no speed-up (cores are the limit)keep a normal pool sized to cores

Virtual threads were previewed in Java 19 and 20 and final in 21 (JEP 444). They are daemon threads, so they do not keep the JVM alive.

Remember: virtual threads make blocking I/O cheap. They scale waiting, not CPU. Don't pool them, do limit what they hit.

Do virtual threads replace reactive programming and CompletableFuture? Senior

For most request-per-thread services, yes: virtual threads give the same scalability for I/O-bound work with simple blocking code that is easy to read, debug and profile. Reactive and CompletableFuture still make sense when I need streaming with back-pressure (flow control from the consumer), or I am composing many parallel calls explicitly.

Why the difference: reactive code splits logic into callbacks and operators, which loses readable stack traces and makes debugging hard. A virtual thread keeps the normal call stack. What virtual threads do not give: back-pressure, event streams, or a faster CPU. Existing reactive codebases do not need to be rewritten just because of Java 21. For new blocking-style services on Java 21, start with virtual threads. Structured concurrency (StructuredTaskScope) for managing groups of sub-tasks was still a preview feature in Java 21 and later releases, so check the current status before relying on it.

Compare the two styles on one task

Task: load a user, then their orders, then their prices, with three blocking calls.

// Blocking style on a virtual thread: reads top to bottom, normal try/catch, normal stack trace
User u = users.load(id);
List<Order> os = orders.forUser(u);
Prices p = pricing.price(os);

// Reactive style (for example Reactor): same logic as a chain of operators
users.load(id)
     .flatMap(orders::forUser)
     .flatMap(pricing::price)
     .onErrorResume(...);

Both let one JVM handle many concurrent requests, since neither holds an OS thread while waiting. The difference is how you write and debug it. Reactive code is a pipeline of callbacks: stack traces show library frames, a debugger steps through operators, and every library in the chain must be non-blocking. Virtual threads keep the ordinary call stack.

Where each is the better tool

CompletableFuture remains a good tool for composing a few asynchronous steps and works fine with virtual threads. What goes away is the need to use async style merely to avoid blocking a scarce thread. Decision rule: new service with blocking drivers, use virtual threads; need back-pressure or event streams, reactive.

Remember: virtual threads win on simplicity for I/O-bound work. Reactive still wins for streams with back-pressure.

What are sequenced collections (Java 21)? Intermediate

Java 21 added new interfaces (SequencedCollection, SequencedSet, SequencedMap) for collections with a defined order, giving one standard way to get the first and last element and to reverse the view. Before that, "last element of a list" and "last of a LinkedHashSet" had completely different code.

list.getFirst();   list.getLast();    list.addFirst(x);   list.removeLast();
list.reversed();                         // a reverse-ordered VIEW, not a copy
linkedHashSet.getLast();                 // finally possible without iterating
linkedHashMap.firstEntry();  linkedHashMap.pollLastEntry();

List, Deque, LinkedHashSet, SortedSet and LinkedHashMap now implement them. getFirst() on an empty list throws NoSuchElementException. reversed() is a live view, so changes show through. HashSet and HashMap are not sequenced.

The inconsistency it fixes

Getting the last element had a different spelling for each collection type, and some had none:

// Before Java 21
list.get(list.size() - 1);                           // List
deque.getLast();                                     // Deque
sortedSet.last();                                    // SortedSet
linkedHashSet.stream().reduce((a, b) -> b).get();    // LinkedHashSet: walk the whole set!

// Java 21: one vocabulary
list.getLast();  deque.getLast();  sortedSet.getLast();  linkedHashSet.getLast();

The new interfaces

  • SequencedCollection: getFirst, getLast, addFirst, addLast, removeFirst, removeLast, reversed. Implemented by List and Deque.
  • SequencedSet: for sets with an order, such as LinkedHashSet and SortedSet.
  • SequencedMap: firstEntry, lastEntry, pollFirstEntry, putFirst, putLast, reversed. For LinkedHashMap and SortedMap.

Example with output

var list = new ArrayList<>(List.of("a", "b", "c"));
list.getFirst();         // "a"
list.getLast();          // "c"
var rev = list.reversed();     // a view: [c, b, a]
list.add("d");
rev.getFirst();          // "d"   the view saw the change
new ArrayList<String>().getFirst();   // NoSuchElementException

Watch for: List.of(...) results implement the interface but throw on the mutating methods. A small compatibility trap: because List got new default methods, a custom class or library that already had a method with the same name and a different return type can stop compiling on Java 21, so run your build on 21 before calling the upgrade done. HashSet and HashMap are intentionally excluded, as they have no encounter order.

Remember: ordered collections got getFirst, getLast and reversed(). Java 21.

Walk me through the LTS releases (8, 11, 17, 21, 25) and what each brought. Senior

9. Migration from Java 8 to 11, 17 and 21

You are asked to upgrade a Java 8 application to 17 or 21. How do you approach it? Senior

I upgrade in steps, not one jump. First get the build and tests green on the new JDK (Java 11 first, then 17, then 21), fix what the compiler and tests report, upgrade libraries and build plugins, and only then roll out gradually with monitoring. I keep the language level unchanged at first so each change can be blamed on one thing.

  • Audit: jdeps --jdk-internals lists use of internal JDK APIs, jdeprscan lists removed APIs.
  • Removed in 11: Java EE modules (JAXB, JAX-WS, javax.annotation), now separate dependencies.
  • Locked in 17: reflection into java.* internals fails, so upgrade libraries (Lombok, Mockito, Spring, Hibernate, ByteBuddy, Jackson) first, then use --add-opens only as a stop-gap.
  • Flags: remove old JVM flags (CMS, PermGen sizes, old GC logging options) that make the JVM refuse to start.
  • Watch for silent changes: default charset UTF-8 (Java 18), different default GC (G1 from 9), container memory awareness, Locale data changes (CLDR default from 9) that alter date and number formatting, and tighter security defaults.
  • Rollout: canary instance, compare GC and latency dashboards, quick rollback.

First question: why not jump straight to 21?

You can, but when 40 things break at once you cannot tell which change caused which failure. Each step removes a different category of problem: 11 removes Java EE modules, 17 locks down internals and removes old flags, 21 mostly adds. Doing them one at a time turns one unbounded debugging session into three small ones. Some teams jump 8 to 17 directly when their dependencies are modern, but they still triage errors by category.

A concrete plan

  1. Inventory. List the JDK, build tool, frameworks and agents (APM, Jacoco, Lombok). Run jdeps --jdk-internals and jdeprscan to catch internal and removed API use before changing anything.
  2. Update the build, not the code. Move Maven or Gradle and their plugins (compiler, surefire, Jacoco, shade) to versions that understand new class files. Keep the language level at 8 (--release 8) so only the toolchain changes first.
  3. Run on JDK 11. Typical fixes: add JAXB and annotation API jars back for the removed EE modules, bump libraries, replace sun.misc.* usage.
  4. Run on JDK 17. Typical fixes: library upgrades for reflection errors (InaccessibleObjectException), delete obsolete JVM flags, review the GC choice.
  5. Raise the language level (--release 17) once the runtime is stable, then adopt features gradually (records, var, text blocks), not in a mass rewrite.
  6. Go to 21 and decide about virtual threads.
  7. Roll out. Canary first, compare GC pauses, heap, startup, p99 latency and error rate. Keep a rollback.

Why does "illegal reflective access" fail on Java 17? Senior

Java 9 introduced modules and started restricting deep reflection into JDK internals, but kept the old behaviour with a warning so old code kept running. Java 16 made it fail by default, and Java 17 removed the --illegal-access switch. Now code or a library that calls setAccessible(true) on a private JDK field gets InaccessibleObjectException.

The fix, in order of preference: upgrade the library (the cause is nearly always an old version of Lombok, Spring, Hibernate, Mockito, ByteBuddy, Jackson, Guice or a serialisation or mapping tool), remove my own reflection hacks, and only as a temporary patch add --add-opens java.base/java.lang=ALL-UNNAMED to the JVM flags. The error message names the exact module, package and flag to open. jdeps --jdk-internals finds many problems before runtime. Strong encapsulation is a security and stability gain, since the JDK can then change internals freely.

Background

Before Java 9 any code on the classpath could reflectively read and modify any private field of the JDK with setAccessible(true). Libraries used this for speed and convenience (serialization, mocking, bytecode tools). It also made the JDK impossible to change safely, since someone always depended on a private field. Java 9 modules introduced strong encapsulation: a module only exposes packages it explicitly exports, and only allows deep reflection into packages it explicitly "opens".

Timeline of enforcement

16denied by default; you could still re-enable with --illegal-access=permit

What you see and how to fix it

java.lang.reflect.InaccessibleObjectException:
  Unable to make field private final byte[] java.lang.String.value accessible:
  module java.base does not "opens java.lang" to unnamed module @1b2c3d

// temporary patch in the JVM options (name the module and package from the message)

  1. Find who caused it. The stack trace shows the library that called setAccessible.
  2. Upgrade that library. Most mainstream libraries fixed this years ago by using public APIs or method handles.
  3. Remove your own reflection into JDK classes; use a public alternative.
  4. Only then use --add-opens, and record it as technical debt, in the launch script or JAVA_TOOL_OPTIONS (for tests, in the surefire argLine).

This applies only to JDK packages. Reflection into your own classes and third-party jars on the classpath still works normally. Related: sun.misc.Unsafe memory methods are being phased out gradually, with warnings added in recent releases (check the release notes for the exact version).

Remember: upgrade the library first, --add-opens is a temporary patch.

What is the javax to jakarta change, and how does it relate to the Java upgrade? Senior

It is a separate migration from the JDK upgrade. Java EE moved to the Eclipse Foundation as Jakarta EE, and from Jakarta EE 9 the packages were renamed from javax.* to jakarta.* (servlet, persistence, validation, annotation and so on). Spring Boot 3 and Spring Framework 6 use jakarta.* and need Java 17 or newer.

I do the JDK upgrade first on the old framework, ship it, and then do the Spring Boot 3 jump as its own step. Note that javax.* packages that are part of the JDK itself (javax.sql, javax.crypto, javax.net) are not renamed.

Java EE (enterprise Java: servlets, JPA, JAX-RS, bean validation) was handed from Oracle to the Eclipse Foundation, which could not reuse the javax namespace for new versions. Which behaviour changes can silently change results after an upgrade? Senior

10. Functional style and immutability

How functional is Java, and what are the trade-offs of the functional style? Senior

Java is object-oriented with functional features on top: lambdas, streams, Optional and immutable values. I use the functional style for transformations of data (filter, map, group), pure helper functions and immutable records, because it is declarative, easier to test and safe to run in parallel. I keep objects and loops for state, I/O and control flow.

Trade-offs: functional code reads well for short pipelines and badly for long ones with nested lambdas; stack traces are deeper and harder to read; boxing and object creation add overhead; and Java has no tail-call optimisation, tuples, or pattern-friendly types like Either, so some functional idioms feel clumsy. Records, sealed interfaces and pattern switch (Java 17 to 21) give Java a proper way to model data as "sum types" and to process it with pure functions, which is the practical centre of modern Java: immutable data in, new data out.

What "functional" means here

Functional style rests on three habits: use pure functions (same input gives the same output, no side effects), prefer immutable data, and treat functions as values you can pass around. Java supports these partly: lambdas and streams for the third, records and List.of for the second, and discipline for the first, since the language cannot enforce purity.

Imperative vs functional on the same problem

// Imperative: mutates state, how-oriented
double total = 0;
for (Order o : orders) {
    if (o.status() == PAID) total += o.amount() * (1 - o.discount());
}

// Functional: describes the what, nothing is mutated
double total2 = orders.stream()
        .filter(o -> o.status() == PAID)
        .mapToDouble(o -> o.amount() * (1 - o.discount()))
        .sum();

Immutable update, the functional way

record Account(String id, long balance) {
    Account deposit(long amt) { return new Account(id, balance + amt); }   // returns a NEW value
}
var a = new Account("A1", 100);
var b = a.deposit(50);          // a.balance() is still 100, b.balance() is 150

Why it helps: an immutable value can be shared among threads with no locks and cached safely. A pure function is easy to test (no mocks) and to reason about.

Honest limits of functional style in Java

  • Readability: three or four pipeline steps read well; nested lambdas and very long chains do not. Pull lambdas out into small named methods.
  • Performance: each immutable update allocates. Usually fine, and the JIT can remove some of it (escape analysis), but in a very hot loop or with huge collections the copy cost is real.
  • No tail-call optimisation, so deep recursion in place of loops risks StackOverflowError.
  • Debugging and stack traces through stream internals are harder.
  • Missing features: no built-in tuples, no persistent (structural-sharing) collections, no Either type. Records and sealed interfaces fill part of that gap, for example sealed interface Result<T> permits Ok, Err.

Decision rule: pure, immutable transformations in the core (parse, validate, compute), and effects (database, network, logging) at the edges. That separation gives most of the benefit without fighting the language.

Remember: functional for transforming data, objects for state and I/O. Keep lambdas small, pure and named.

How do immutable types (records, List.of, java.time) change how you design code? Intermediate

Immutable objects can be shared freely between threads and used as map keys without defensive copies, so a whole class of bugs disappears: no locks for read-only data, no "who changed this?", no surprise changes while iterating. To "change" one, I build a new one: date.plusDays(1), a record withX method, or List.copyOf.

Costs: more small objects (the JIT and GC handle this well) and a bit more code to copy with changes. The common trap is shallow immutability: a record with a List component is only immutable if the list is also immutable, so copy it in the compact constructor: this.items = List.copyOf(items). Also do not return internal mutable collections from getters, return unmodifiable views or copies.

What immutable means, and why it helps

An immutable object cannot change after construction. Because nothing can change, there is nothing to protect: any number of threads can read it with no locks, it is safe as a HashMap key (its hash never changes), and no method can alter it behind your back. This removes whole categories of bugs ("who modified this list?", "why did my key disappear from the map?").

Bug it prevents, shown

// Mutable: the caller changes your internal state through the getter
class Team { private final List<String> members = new ArrayList<>(); List<String> members() { return members; } }
team.members().clear();                  // team is now empty, and Team had no say

// Immutable
record Team(List<String> members) {
    Team { members = List.copyOf(members); }       // copy on the way in
}
// team.members().clear();                          // UnsupportedOperationException

The "change" pattern: build a new one

LocalDate d = LocalDate.of(2025, 1, 31);
LocalDate e = d.plusDays(1);                // d is still 2025-01-31
record User(String name, int age) { User withAge(int a) { return new User(name, a); } }
var older = new User("Asha", 30).withAge(31);

Shallow versus deep

A record or final field only freezes the reference. If the field points to a mutable object (a List, a Date, an array), that object can still change. For real immutability: copy mutable inputs in the constructor, do not hand out internal mutable objects (return copies, or unmodifiable collections), and prefer immutable types for components (java.time, String, List.copyOf).

Costs and when not to

  • More small objects per update. This is typically cheap, since the JVM allocates quickly and short-lived objects die young, but huge structures updated in a hot loop (a million-element list copied per step) are a real cost. Use a mutable builder inside, and freeze at the end.
  • JPA entities and some frameworks need mutable beans.

Rule of thumb: make values immutable by default (records, final fields), and allow mutability only where measured or required, and keep it inside one object.

Remember: immutable = thread-safe by default. It must be deep: copy the collections you accept.

11. Coding questions solved with streams

Count the frequency of each word in a sentence, and find the top 3. Basic

I split the text into words, group by the word and count each group. For the top 3, I sort the map entries by count descending and take three.

Map<String, Long> freq = Arrays.stream(text.toLowerCase().split("\\W+"))
    .filter(w -> !w.isEmpty())
    .collect(Collectors.groupingBy(Function.identity(), Collectors.counting()));

List<String> top3 = freq.entrySet().stream()
    .sorted(Map.Entry.<String, Long>comparingByValue().reversed()
            .thenComparing(Map.Entry.comparingByKey()))      // stable tie-break
    .limit(3).map(Map.Entry::getKey).toList();

Points to mention: lower-casing and splitting on \W+ handle punctuation; counting() returns Long; the tie-breaker makes the result deterministic. To keep a sorted map, collect to a LinkedHashMap using the four-argument toMap with a merge function. For a huge input, a single pass with HashMap.merge(w, 1, Integer::sum) is simple and fast too.

Step by step with real data

Input: "the cat and the hat and the bat".

  1. toLowerCase() so "The" and "the" count together.
  2. split("\\W+") splits on any run of non-word characters (spaces, commas, dots). Result: [the, cat, and, the, hat, and, the, bat]. A leading punctuation mark can leave an empty first string, hence the filter(w -> !w.isEmpty()).
  3. groupingBy(identity, counting()) makes one bucket per distinct word and counts it: {the=3, and=2, cat=1, hat=1, bat=1} (the map order is not defined).
  4. Sort entries by count descending, then by word ascending as a tie-break, so the answer is repeatable: the(3), and(2), bat(1), cat(1), hat(1).
  5. limit(3), then map(Entry::getKey): [the, and, bat].

Why the tie-break matters

Without it, cat, hat and bat all have count 1 and the third place depends on the HashMap order, which can change between runs or JDK versions. A deterministic answer is what a test and a customer need.

The loop version, for comparison

Map<String,Integer> m = new HashMap<>();
for (String w : text.toLowerCase().split("\\W+")) {
    if (!w.isEmpty()) m.merge(w, 1, Integer::sum);     // put 1 or add 1
}

It is just as good and faster for huge inputs. Mention both. Follow-ups: use TreeMap for alphabetical output, a PriorityQueue of size 3 for top-k in O(n log k) if the number of distinct words is huge, and \p{L}+ instead of \W+ to handle non-English letters properly.

Remember: groupingBy(identity, counting()), then sort entries by value and limit.

Find the second highest distinct number in a list. Basic

Take the distinct values, sort them in descending order, skip the first and take the next. The result is an Optional, because the list may not have two distinct values.

Optional<Integer> second = nums.stream()
    .distinct()
    .sorted(Comparator.reverseOrder())
    .skip(1)
    .findFirst();

This is O(n log n) because of the sort. If the interviewer asks for O(n), do one pass with two variables, max and second, updating them as you go. Say the edge cases aloud: empty list, one element, all equal (no second highest) and negative numbers (do not initialise with 0).

Step by step

Input: [10, 40, 40, 20, 30].

  1. distinct() removes duplicates: [10, 40, 20, 30]. This matters because the "second highest" of [40, 40, 20] should be 20, not 40.
  2. sorted(Comparator.reverseOrder()): [40, 30, 20, 10].
  3. skip(1) drops the highest: [30, 20, 10].
  4. findFirst() gives Optional[30]. For [5, 5] or an empty list the stream is empty after the skip, so the result is Optional.empty, which is the honest answer.

The O(n) version, in one pass

Integer max = null, second = null;
for (int n : nums) {
    if (max == null || n > max)            { second = max; max = n; }
    else if (n != max && (second == null || n > second)) { second = n; }
}
// second is null when there is no second distinct value

Trace for [10, 40, 40, 20, 30]: 10 gives max=10; 40 gives second=10, max=40; the second 40 is equal to max, ignored; 20 gives second=20; 30 gives second=30. Result 30.

Variations an interviewer may ask

  • k-th highest: keep a min-heap of size k, or sort distinct values and use skip(k-1).
  • Per group: group by key, then apply the above to each list.
  • Using primitives: IntStream.of(...).distinct().boxed().sorted(reverseOrder()).skip(1).findFirst().

Pitfall: initialising max with 0 or Integer.MIN_VALUE gives wrong results with negative numbers or with a real Integer.MIN_VALUE in the data; using null or a boolean flag avoids that.

Remember: distinct, sorted descending, skip 1, findFirst. Mention the O(n) two-variable version.

Find the highest-paid employee in each department. Intermediate

Group by department and use maxBy as the downstream collector. Each value is an Optional, so I wrap it in collectingAndThen to unwrap it.

Map<String, Emp> best = emps.stream().collect(
    Collectors.groupingBy(Emp::dept,
        Collectors.collectingAndThen(
            Collectors.maxBy(Comparator.comparingDouble(Emp::salary)),
            Optional::get)));       // safe: a group always has at least one element

// alternative: toMap with a merge function
emps.stream().collect(Collectors.toMap(Emp::dept, e -> e,
    BinaryOperator.maxBy(Comparator.comparingDouble(Emp::salary))));

Optional::get is safe here only because a group exists only if it has at least one member. The toMap version is shorter and avoids the Optional. For the second highest per department, group into lists and sort each, or use mapping then post-process.

Step by step with data

Employees: Ann (HR, 50), Di (HR, 70), Bob (IT, 90), Cy (IT, 60).

  1. groupingBy(Emp::dept, ...) creates buckets: HR has Ann and Di, IT has Bob and Cy.
  2. The downstream maxBy(comparingDouble(Emp::salary)) is applied to each bucket and returns an Optional<Emp> (it is Optional because a general stream could be empty): HR gives Optional[Di], IT gives Optional[Bob].
  3. collectingAndThen(..., Optional::get) applies a finishing function to each bucket result and unwraps the Optional. Result: {HR=Di, IT=Bob}.

The shorter alternative

toMap(Emp::dept, e -> e, BinaryOperator.maxBy(cmp)) uses the merge function: whenever two employees share a dept key, it keeps the better one. It builds the result in one pass and has no Optional. Both give the same answer; the first is more "standard", the second is shorter.

Variations

// the highest salary VALUE only
groupingBy(Emp::dept, collectingAndThen(mapping(Emp::salary, maxBy(naturalOrder())), Optional::get))
// or summarizingDouble for min, max, avg in one go
groupingBy(Emp::dept, summarizingDouble(Emp::salary))      // each value has getMax(), getMin(), getAverage()
// top 2 per department
groupingBy(Emp::dept, collectingAndThen(toList(),
    l -> l.stream().sorted(comparingDouble(Emp::salary).reversed()).limit(2).toList()))

Pitfall: if there is a tie at the top salary, maxBy returns one of them (the first encountered in a sequential stream), so state the tie rule if asked. And remember that a department with no employees will not appear at all, because groups only exist if at least one element was seen.

Remember: groupingBy + maxBy + collectingAndThen(Optional::get), or toMap with BinaryOperator.maxBy.

How do you sort a map by value and keep that order? Intermediate

Stream the entries, sort them with Map.Entry.comparingByValue(), and collect into a LinkedHashMap, because only a linked map remembers insertion order. A plain HashMap would throw the sorting away.

Map<String, Integer> sorted = scores.entrySet().stream()
    .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
    .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue,
             (a, b) -> a, LinkedHashMap::new));

The explicit type witness <String, Integer> is needed before .reversed() because inference cannot see through the chain. Alternatively use Map.Entry.comparingByValue(Comparator.reverseOrder()), which needs no witness. If the map must stay sorted on every insert, use a TreeMap sorted by key instead, since a TreeMap cannot sort by value.

Why a plain collect loses the order

A HashMap stores entries by hash, not by the order you insert them. So sorting the entries and collecting into a default map (or Collectors.toMap without a supplier) puts them back in hash order, and your sorting is thrown away. A LinkedHashMap remembers insertion order, so it keeps the sorted sequence.

Step by step with data

scores = {amy=70, bob=90, cy=80}.

  1. entrySet().stream() gives three Map.Entry objects.
  2. Sort by value descending: bob=90, cy=80, amy=70.
  3. toMap(key, value, merge, LinkedHashMap::new) inserts them in that order. The merge function is required in this four-argument form but never actually runs because keys from a map are unique, so (a, b) -> a is fine.
  4. Result printed: {bob=90, cy=80, amy=70}.

Cleaner ways to write it

// no type witness needed
.sorted(Map.Entry.comparingByValue(Comparator.reverseOrder()))
// sort by value descending, then key ascending
.sorted(Map.Entry.<String,Integer>comparingByValue().reversed().thenComparing(Map.Entry.comparingByKey()))
// only the keys in order
List<String> keys = scores.entrySet().stream().sorted(...).map(Map.Entry::getKey).toList();

If you only need the ordered list for display, skip the map and keep a List<Map.Entry>. If you need a map that stays sorted as you add, no JDK map sorts by value, so keep a separate structure (for example a TreeSet of entries with a comparator that includes the key as a tie-breaker). Since Java 21, the result of LinkedHashMap also supports firstEntry() and reversed().

Remember: sort the entries, collect into LinkedHashMap. TreeMap sorts by key only.

Real-life scenarios

Each scenario starts with the diagnosis and fix, then shows the situation, what to check first, the fix and how to prevent it.

A report built with a parallel stream sometimes has missing rows and once threw ArrayIndexOutOfBoundsException. What happened? Intermediate

The lambda adds to a plain ArrayList from several threads. ArrayList.add is not thread-safe, so two threads can write the same slot (a lost row) or resize during a write (the exception). Replace the side effect with collect or toList().

Situation: orders.parallelStream().filter(...).forEach(o -> result.add(o)). It fails randomly, so tests pass most of the time. Check first: search the pipeline for any lambda that writes to an outside list, map, counter or field, and check whether the stream is parallel. Fix: let the stream build the result, .collect(toList()) or .toList(), which gives each thread its own container and merges safely. Prevent: a team rule of no side effects in stream lambdas, and a regression test with a large input run repeatedly.

Why this fails, in slow motion

ArrayList.add does two things: write the element at elementData[size], then increase size. These are not atomic. Two threads can both read size = 5, both write to slot 5 (one row overwrites the other, a lost row) and both set size to 6 (the count is also off). If a resize happens in between (the array is copied into a bigger one), one thread may write into an old array, or index beyond the length, which is the ArrayIndexOutOfBoundsException.

Reproduce and fix

List<Integer> bad = new ArrayList<>();
IntStream.range(0, 100_000).parallel().forEach(bad::add);
bad.size();   // for example 98_431, or an exception; different every run

List<Integer> good = IntStream.range(0, 100_000).parallel().boxed().toList();
good.size();  // always 100000
// if a mutable collection is truly needed: collect(Collectors.toCollection(ArrayList::new))

A nightly job scheduled for 02:30 local time did not run once a year and ran twice in autumn. Explain and fix. Senior

What the letters mean

yyyy is the calendar year of the date. YYYY is the week-based year: the year that the date's ISO week belongs to. You enabled virtual threads on Java 21 and the database falls over, or throughput does not improve. Why? Senior

Virtual threads remove the thread limit, so nothing slows the requests down before the database anymore: thousands of concurrent queries hit a pool or server that was only ever sized for a few hundred. And if the work is CPU-bound, or threads are pinned inside synchronized blocks, there is no gain. I cap concurrency at the resource and fix the pinning.

Check first: connection pool wait time and DB active sessions, CPU usage (is it CPU bound?), and thread dumps with -Djdk.tracePinnedThreads=full (or JFR pinned-thread events) to find pinned virtual threads. Fix: keep a bounded connection pool (requests wait for a connection, which is the intended back-pressure), use a Semaphore for other limited resources, replace long synchronized sections with ReentrantLock, and upgrade libraries (JDBC drivers) that pin. Java 24 removes most synchronized pinning. Prevent: load test with the setting on, and monitor pool wait time.

Two different failure modes

Failure 1: the database falls over. Previously a platform-thread pool of 200 acted as an accidental throttle: no more than 200 requests were ever in flight, so the database saw at most 200 queries. With virtual threads there is no such cap, and 5,000 concurrent requests all try to run queries. With a bounded connection pool (say 30), 4,970 virtual threads wait for a connection. That is actually fine (they are cheap), and is the right back-pressure. The failure happens when there is no bound, for example each task opens its own connection, calls an external API with a rate limit, or a downstream has no queue. Then the thousands of concurrent calls overwhelm that dependency.

Failure 2: no improvement. The work was CPU-bound, so there is nothing to un-block, or the virtual threads are pinned: blocking inside a synchronized block (on Java 21 to 23) or a native frame keeps the carrier thread blocked too, so the few carriers get exhausted and throughput looks like a small thread pool again.

Diagnose and fix

// find pinning
java -Djdk.tracePinnedThreads=full -jar app.jar      // prints a stack when a VT blocks while pinned
// or JFR event jdk.VirtualThreadPinned

// cap concurrency at the scarce resource, not at the thread count
private final Semaphore limit = new Semaphore(50);
Result call() throws InterruptedException {
    limit.acquire();
    try { return client.call(); } finally { limit.release(); }
}
  • Keep the connection pool at its right size; do not enlarge it just because threads are cheap.
  • Replace long synchronized sections that contain blocking calls with ReentrantLock, or upgrade libraries (JDBC drivers) that pin. Java 24 removes most synchronized pinning.
  • Load test with virtual threads on and compare pool wait time, DB sessions, p99 latency.

Remember: virtual threads move the bottleneck to your database. Limit concurrency at the resource, not at the thread.
