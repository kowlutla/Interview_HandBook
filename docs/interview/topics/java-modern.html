Scope: this page covers the language and library features added from Java 8 to Java 21 (with a look at 22 to 25), and the migration pain. Sibling pages cover the rest of Java: Java fundamentals, collections internals, concurrency (threads, executors, CompletableFuture in depth), JVM, memory and GC, and exceptions and I/O.

Version words used on this page: preview means the feature is in the JDK but you must pass --enable-preview, and it may still change. Incubator means a separate module that may change. Final (or standard) means it is permanent and supported. A feature that was preview in one release becomes final in a later one, so always name the release where it became final. LTS (long term support) releases are 8, 11, 17, 21 and 25.

Mental model: the 8 ideas everything hangs on

One line: modern Java lets you pass behaviour as a value (lambda), process data as a lazy pipeline (stream), describe data with small immutable types (records, sealed types) and take them apart safely (pattern matching), while the platform moves toward cheap threads and strong encapsulation.
  1. A lambda is an instance of a functional interface. It is not a new "function type". Java kept its type system and said: any interface with one abstract method can be written as a lambda.
  2. Streams are pipelines, not collections. A stream holds no data. It describes steps from a source to one final result. Nothing runs until a terminal operation is called.
  3. Processing is element by element. Each element goes through the whole chain (filter, map, limit) before the next element starts. This is why short-circuiting and infinite streams work.
  4. Immutability is the default direction. List.of, records, java.time, Stream.toList() all return values you cannot change. Fewer shared-state bugs.
  5. Absence and failure are values. Optional says "maybe no result" in a method signature. It is for return types, not for fields or parameters.
  6. Types describe the data model. Records are data carriers, sealed types list every allowed subtype, and a pattern-matching switch checks that you handled them all.
  7. Java releases every 6 months, LTS every 2 years. Since Java 9 the cadence is fixed (Java 8 to 17 was 3 years, now 2). Companies run an LTS; features arrive as preview first.
  8. Upgrades break on removed things, not on new things. Removed Java EE modules, strong encapsulation of JDK internals, and library versions are what hurt. The new syntax is optional.

1. Lambdas, functional interfaces and interface methods

What is a lambda expression, and why was it added in Java 8? Basic

What the interviewer is testing: do you see a lambda as "a short way to pass behaviour", and do you know it has a type.

A lambda is a short block of code you can pass around, like a method without a name. Before Java 8 you had to write an anonymous inner class just to say "sort by length" or "run this later", which was five lines of noise for one line of logic. A lambda writes only the parameters, an arrow, and the body. The compiler works out the type from the place where you use it. That type must be a functional interface: an interface with exactly one abstract method. So (a, b) -> a.length() - b.length() is simply an object that implements Comparator. The big reason for the feature was streams: without lambdas, the Stream API would be unreadable.

// before Java 8
list.sort(new Comparator<String>() {
    public int compare(String a, String b) { return a.length() - b.length(); }
});
// Java 8
list.sort((a, b) -> Integer.compare(a.length(), b.length()));
list.sort(Comparator.comparingInt(String::length));   // best
Likely follow-ups
  • Can a lambda exist without a target type? No. var f = x -> x; does not compile because there is no interface to implement.
  • Does a lambda have its own type? No. The same lambda text can be a Function or a custom interface, depending on context.
What is a functional interface? Do I need @FunctionalInterface? Basic

What the interviewer is testing: the exact rule, including what does not count as abstract.

A functional interface has exactly one abstract method. Default methods, static methods, and methods that match public methods of Object (like equals) do not count. That is why Comparator is functional even though it declares equals. The annotation @FunctionalInterface is optional. It does not change behaviour. It only makes the compiler complain if someone later adds a second abstract method, which would silently break every lambda that uses your interface. I always add it on interfaces meant for lambdas, as documentation and as a guard.

@FunctionalInterface
interface Validator<T> {
    boolean validate(T value);                       // the one abstract method
    default Validator<T> and(Validator<T> o) {      // default does not count
        return v -> validate(v) && o.validate(v);
    }
}
Validator<String> notEmpty = s -> !s.isEmpty();
Likely follow-ups
  • Is Runnable a functional interface? Yes. So are Callable, Comparator and Iterable (one abstract method, iterator()).
  • Can a functional interface extend another? Yes, if the total abstract methods stay at one.
Name the core functional interfaces in java.util.function and when you use each. Basic

What the interviewer is testing: daily vocabulary. You must know them without thinking.

Function<T,R> turns a T into an R (apply). Predicate<T> answers yes or no about a T (test); it drives filter. Supplier<T> takes nothing and gives a T (get); it is for lazy creation, like orElseGet. Consumer<T> takes a T and returns nothing (accept); it is for side effects like forEach. BiFunction<T,U,R> takes two inputs. UnaryOperator<T> is a Function<T,T> (same type in and out), and BinaryOperator<T> is a BiFunction<T,T,T>, used in reduce and merge. There are also primitive versions (IntPredicate, ToIntFunction, IntSupplier, IntBinaryOperator) that avoid boxing.

Likely follow-ups
  • Why primitive variants? Function<Integer,Integer> boxes every value; IntUnaryOperator does not.
  • Which interface for "run something, no input, no output"? Runnable. For a result and a checked exception, Callable.
How do you compose functions and predicates? What is the difference between andThen and compose? Intermediate

What the interviewer is testing: small but classic. People mix up the order.

f.andThen(g) means "run f first, then g", so it is g(f(x)). f.compose(g) means "run g first, then f", so it is f(g(x)). For predicates, and, or and negate build bigger conditions, and they short-circuit like && and ||. Predicate.not(String::isBlank) (Java 11) lets you negate a method reference without writing a lambda. Predicate.isEqual(x) gives a null-safe equality check. Function.identity() returns its input, common in toMap and groupingBy.

Function<Integer,Integer> plus1  = x -> x + 1;
Function<Integer,Integer> times10 = x -> x * 10;
plus1.andThen(times10).apply(2);   // (2+1)*10 = 30
plus1.compose(times10).apply(2);   // (2*10)+1 = 21

Predicate<String> longWord = s -> s.length() > 5;
words.stream().filter(longWord.and(Predicate.not(String::isBlank)))...
What are the four kinds of method reference? Intermediate

What the interviewer is testing: can you tell them apart, especially the "unbound instance" one that confuses people.

A method reference is a shorter lambda that only calls one method. There are four kinds. Static: Integer::parseInt is s -> Integer.parseInt(s). Bound instance: System.out::println uses one specific object, fixed when the reference is created. Unbound instance: String::length means s -> s.length(); the first parameter becomes the object the method is called on. Constructor: ArrayList::new or Person::new, and int[]::new for arrays. Use them when they read better. If you must squint to see which method is called, or arguments are rearranged, a lambda is clearer.

names.stream().map(String::toUpperCase)      // unbound instance
names.forEach(System.out::println)           // bound instance
numbers.stream().map(Integer::valueOf)       // static
Supplier<List<String>> s = ArrayList::new;   // constructor
Likely follow-ups
  • When is a method reference ambiguous? Integer::toString has both a static toString(int) and an instance toString(), so the compiler rejects it for Function<Integer,String>.
Why must variables captured by a lambda be effectively final? Intermediate

What the interviewer is testing: do you understand where local variables live and what a lambda really captures.

A local variable lives on the stack of the method that created it. A lambda can outlive that method, and it may run later or on another thread. So the lambda does not point to the variable; it gets a copy of its value. If you could change the variable after the copy, the lambda and the method would disagree about its value, and with threads you would get visibility bugs. Java avoids the whole problem by a rule: a captured local must be final or effectively final (never reassigned after its first assignment, even without the keyword). Fields are different: a lambda captures this, and reads the field at run time, so it can change fields. That is legal, but it is shared mutable state, and it is exactly where thread-safety bugs come from.

Likely follow-ups
  • People bypass it with a one-element array or AtomicInteger. Is that fine? It compiles, but in a stream it hides state mutation. Use reduce, count or collect instead.
Common mistakes: saying "because Java does not support closures". It does; it just captures values, not variables.
How is a lambda different from an anonymous inner class? Intermediate

What the interviewer is testing: meaning of this, and how lambdas are compiled.

The first difference is this. Inside an anonymous class, this is the anonymous object itself. Inside a lambda, this is the enclosing class, because a lambda body is just part of the surrounding method. Second, an anonymous class can implement any interface or extend any class and can have fields and several methods; a lambda only implements one functional interface. Third, compilation: an anonymous class creates a real .class file and a new object on each use. A lambda is compiled to a private method plus an invokedynamic instruction, and at the first call the JVM builds the lambda object through LambdaMetafactory. A lambda that captures nothing can be created once and reused. This gives smaller jars and faster startup than many anonymous classes. Lambdas also cannot shadow local variables of the enclosing method.

Likely follow-ups
  • Do lambdas have a stable toString or equals? No. Do not compare them or use them as map keys.
  • Can a lambda be serialized? Only if the target interface is Serializable, and it is fragile across compiler versions. Avoid it.
How do you handle checked exceptions inside a lambda? Intermediate

What the interviewer is testing: a real annoyance with streams and an honest trade-off answer.

The standard functional interfaces do not declare checked exceptions, so a lambda body cannot throw an IOException unless the interface allows it. Options: first, catch inside the lambda and wrap it in an unchecked exception (UncheckedIOException). Second, write a small helper that wraps a throwing function once, so call sites stay clean. Third, define your own functional interface whose method throws Exception. Fourth, step out of the stream and use a normal loop, which is often the cleanest when the body is mostly error handling. Do not hide failures by returning null from the catch block.

@FunctionalInterface interface ThrowingFn<T,R> { R apply(T t) throws Exception; }

static <T,R> Function<T,R> unchecked(ThrowingFn<T,R> f) {
    return t -> {
        try { return f.apply(t); }
        catch (Exception e) { throw new RuntimeException(e); }
    };
}
paths.stream().map(unchecked(Files::readString)).toList();
Likely follow-ups
  • Why not make the stream interfaces throw checked exceptions? The designers judged that generic exception types in the stream API would be too hard to use. Exceptions in the exceptions page covers the wider design.
What are default and static methods in interfaces, and why were they added? Basic

What the interviewer is testing: can you explain interface evolution, not just syntax.

Before Java 8, adding a method to an interface broke every class that implemented it. To add stream() to Collection and sort() to List without breaking millions of classes, Java allowed a default method: an interface method with a body that implementers inherit unless they override it. A static method in an interface is a helper that belongs to the interface itself, like Comparator.comparing or List.of. Static interface methods are not inherited and you call them as InterfaceName.method(). Java 9 added private interface methods so default methods can share code without exposing it. Interfaces still have no instance state (fields are constants), which is the main difference from abstract classes.

interface Greeter {
    String name();
    default String greet() { return prefix() + name(); }
    private String prefix() { return "Hello, "; }     // Java 9
    static Greeter of(String n) { return () -> n; }   // static factory
}
Likely follow-ups
  • Interface with default methods versus abstract class? Interfaces allow multiple inheritance of behaviour but no state. Abstract classes allow fields and constructors, but only one parent.
Two interfaces have the same default method and a class implements both. What happens? Intermediate

What the interviewer is testing: the three resolution rules for the "diamond problem".

Java applies three rules in order. First, a class wins: if the class or a superclass defines the method, that one is used. Second, the most specific interface wins: if one interface extends the other and overrides the method, the sub-interface version is used. Third, if neither rule decides, the code does not compile, and you must override the method yourself. In that override you can pick one parent with the syntax A.super.hello(). Because state is not allowed in interfaces, the classic C++ diamond problem of duplicate fields does not exist. Only the behaviour choice remains, and Java makes you decide it explicitly.

How do you write a multi-field sort with the modern Comparator API? Basic

What the interviewer is testing: fluent comparator use and null handling.

Use Comparator.comparing(keyExtractor), then chain thenComparing for tie-breakers and reversed() for descending order. Primitive versions comparingInt, comparingLong, comparingDouble avoid boxing. For nullable keys, wrap with Comparator.nullsFirst or nullsLast. A common trap: reversed() reverses the whole chain built so far, not only the last step, so put a descending key inside comparing(..., Comparator.reverseOrder()) when only one field is descending. Never write a.x - b.x as a comparator, because subtraction overflows for large values.

people.sort(Comparator.comparing(Person::city)
        .thenComparing(Person::age, Comparator.reverseOrder())
        .thenComparing(Person::name, Comparator.nullsLast(Comparator.naturalOrder())));

2. Stream API in depth

What is a Stream? How is it different from a Collection? Basic

What the interviewer is testing: the basic idea that a stream is not a data structure.

A collection stores data. A stream does not store anything; it is a one-time description of a computation over a source (a collection, array, file, generator). Three differences matter. A stream is lazy: intermediate steps do nothing until a terminal operation runs. A stream is single use: once consumed, it cannot be reused. A stream does not change its source: filtering a list gives a new result and leaves the list alone. A stream can also be infinite (Stream.iterate), which a collection cannot. Think of a collection as a bucket of water and a stream as a pipe the water flows through once.

Likely follow-ups
  • Is Stream the same as InputStream? No, they are unrelated. java.util.stream.Stream is for data processing; InputStream is for bytes.
  • Does a stream close? Streams from files (Files.lines) hold a resource, so use try-with-resources. Normal streams do not need closing.
Explain the stream pipeline: source, intermediate and terminal operations. Basic

What the interviewer is testing: the three-part structure and which operations are which.

Every pipeline has three parts. A source creates the stream: list.stream(), Arrays.stream(arr), Stream.of(...), IntStream.range, Files.lines. Then zero or more intermediate operations, each returning a new stream: filter, map, flatMap, sorted, distinct, limit, skip, peek, takeWhile. Finally exactly one terminal operation, which starts the work and returns a value or nothing: collect, forEach, reduce, count, min, max, anyMatch, findFirst, toList. If you forget the terminal operation, nothing runs, and a common bug is a peek or map that "does not execute" for that reason.

long n = orders.stream()                 // source
    .filter(o -> o.total() > 100)        // intermediate
    .map(Order::customerId)              // intermediate
    .distinct()                          // intermediate
    .count();                            // terminal: now it runs
What does "lazy" mean for streams? How does element-by-element processing work? Intermediate

What the interviewer is testing: the "vertical" processing model, which explains short-circuiting and the output order of peek.

Intermediate operations only build the pipeline. When the terminal operation starts, it pulls one element at a time from the source and pushes it through every step before taking the next. This is called vertical (or fused) processing, not "do all filter, then all map". It has two big benefits. No temporary lists are created between steps, so memory stays small. And the pipeline can stop early: with limit(3) or findFirst, the source is not read further once the answer is known. That is why Stream.iterate(1, x -> x + 1).filter(...).limit(5) finishes even though the source is infinite. The exceptions are stateful steps like sorted, which must see all elements before passing any on.

Likely follow-ups
  • What does sorted() do to this model? It is a barrier: it must collect everything, sort, then release elements. Putting it before limit on an infinite stream never finishes.
What is the difference between map and flatMap? Basic

What the interviewer is testing: one of the most asked stream questions. You need a clear picture, not a definition.

map transforms each element into exactly one new element: one in, one out. flatMap transforms each element into a stream of elements and then joins all those little streams into one flat stream: one in, zero or many out. Use map when your function returns a plain value. Use flatMap when your function returns a collection, an array, an Optional or a stream, and you want to work with the inner items. If you used map there, you would get a Stream<List<X>>, a stream of lists, which is rarely what you want. The same idea exists in Optional: flatMap avoids an Optional<Optional<T>>.

List<String> allWords = lines.stream()
    .flatMap(line -> Arrays.stream(line.split("\\s+")))
    .toList();
List<Item> items = orders.stream().flatMap(o -> o.items().stream()).toList();
Likely follow-ups
  • What is mapMulti (Java 16)? A push-style alternative to flatMap that avoids creating a small stream per element. Use it when each element produces few outputs.
  • How do I flatten Optional values in a stream? flatMap(Optional::stream) (Java 9).
How does reduce work, and what are its rules? Intermediate

What the interviewer is testing: understanding of identity, associativity, and why reduce is not for building collections.

reduce folds all elements into one value. The simple form is reduce(identity, accumulator): start from the identity value and combine each element into it. Example: reduce(0, Integer::sum). The form without identity returns an Optional, because an empty stream has no result. Rules: the accumulator must be associative (grouping does not matter, like addition) and stateless, and the identity must be neutral (0 for sum, 1 for product). These rules matter because with parallel streams the work is split into chunks and combined in any grouping. The three-argument form adds a combiner to merge partial results when the result type differs from the element type. Do not use reduce to build a list or string by appending: it creates many objects and breaks the rules for mutable containers; use collect.

int total = nums.stream().reduce(0, Integer::sum);
Optional<Integer> max = nums.stream().reduce(Integer::max);
int totalLen = words.stream().reduce(0, (acc, w) -> acc + w.length(), Integer::sum);
Common mistakes: subtraction or a non-neutral identity in a parallel reduce gives wrong, unpredictable results.
Which operations are short-circuiting, and which are stateful? Intermediate

What the interviewer is testing: can you reason about cost and infinite streams.

Short-circuiting operations can finish without reading all elements: anyMatch, allMatch, noneMatch, findFirst, findAny, and the intermediate limit and takeWhile. They are the only way to finish an infinite stream. Stateless operations (filter, map, flatMap, peek) look at one element at a time and need no memory of the others. Stateful operations (sorted, distinct, skip, limit) need to remember something about other elements. sorted must buffer everything. distinct keeps a set of seen values, which can grow large. Stateful operations also hurt parallel performance because they need coordination.

Likely follow-ups
  • What does allMatch return on an empty stream? true. anyMatch returns false, and noneMatch returns true.
  • Is limit cheap in parallel on an ordered stream? Not really; it has to respect the encounter order, so it can be costly. Use unordered() if order does not matter.
How do sorted, distinct, limit, skip and takeWhile behave? Any traps? Intermediate

What the interviewer is testing: practical details that decide whether a pipeline is correct and fast.

sorted() uses natural order (elements must be Comparable, otherwise ClassCastException at run time), or you pass a Comparator. It is stable for ordered streams. distinct() uses equals and hashCode, so your class needs both. limit(n) keeps the first n, skip(n) drops the first n; together they give simple paging, though for large offsets a database query is better. takeWhile(p) (Java 9) takes elements while the condition is true and stops at the first failure; dropWhile does the opposite. They are different from filter: on 1,2,5,1 with x < 3, filter gives 1,2,1 but takeWhile gives 1,2. The traps: sorted before limit on a huge stream sorts everything (for top N, consider a bounded heap), and takeWhile on an unordered stream has unpredictable results.

Stream.of(1, 2, 5, 1).takeWhile(x -> x < 3).toList();   // [1, 2]
Stream.of(1, 2, 5, 1).dropWhile(x -> x < 3).toList();   // [5, 1]
Stream.iterate(1, x -> x < 100, x -> x * 2).toList();   // 1,2,4,...,64 (Java 9)
What is peek for, and why is it dangerous? Intermediate

What the interviewer is testing: knowing the documented purpose and the laziness trap.

peek(consumer) passes each element through unchanged and runs your consumer on the way. The Javadoc says it exists mainly "to support debugging", for example to print the elements at one point in the pipeline. It is dangerous for two reasons. First, it only runs if the element reaches that point and a terminal operation pulls it; with short-circuiting or an optimised terminal it may run less than you expect. In particular, since Java 9, count() can skip the whole pipeline when the size can be computed directly from the source, so list.stream().peek(print).count() prints nothing. Second, people put real logic in it (saving, updating counters), and that is a side effect inside something that may be reordered, skipped or run in parallel. Use forEach for a real action.

Likely follow-ups
  • How do you debug a pipeline then? See the debugging question: split into steps, use peek temporarily, or use the IDE stream debugger.
Why are there IntStream, LongStream and DoubleStream? Intermediate

What the interviewer is testing: boxing cost and the convenience methods.

A Stream<Integer> holds boxed objects: every number is an Integer on the heap, so large numeric work creates garbage and loses cache locality. IntStream, LongStream and DoubleStream hold raw primitives. They also have numeric methods that object streams lack: sum, average (returns OptionalDouble), min, max, summaryStatistics, and range factories IntStream.range(0, n) and rangeClosed. Convert with mapToInt, mapToObj, boxed() and asLongStream. chars() on a String gives an IntStream of UTF-16 code units (use codePoints() for full Unicode). There is no CharStream or FloatStream. Also watch sum() on IntStream: it silently overflows, so use mapToLong for big totals.

double avg = people.stream().mapToInt(Person::age).average().orElse(0);
IntSummaryStatistics st = nums.stream().mapToInt(i -> i).summaryStatistics();
int[] squares = IntStream.rangeClosed(1, 5).map(i -> i * i).toArray();
What happens if you use a stream twice? Basic

What the interviewer is testing: knowing the exact exception and the usual fixes.

After a terminal operation, the stream is consumed. Any second use throws IllegalStateException: stream has already been operated upon or closed. The same happens if you call two operations on the same intermediate stream reference (branching). A stream is a one-shot pipe, not a collection. Fix by creating a new stream from the source each time, by keeping the source (the list) and calling stream() where needed, or by keeping a Supplier<Stream<T>> that builds a fresh stream on demand. If you need two results from one pass, use Collectors.teeing or collect once and derive both. Do not store streams in fields or return them from caching methods.

Stream<String> s = names.stream().filter(n -> n.length() > 3);
s.count();
s.toList();                       // IllegalStateException

Supplier<Stream<String>> sup = () -> names.stream().filter(n -> n.length() > 3);
sup.get().count();  sup.get().toList();   // fine
How do you create streams, including infinite ones? Basic

What the interviewer is testing: breadth of the API, and the safe way to bound infinite streams.

From collections: list.stream(). From arrays: Arrays.stream(arr) or Stream.of(a, b). From numbers: IntStream.range. From files: Files.lines(path) (close it) and Files.walk. From text: string.lines() (Java 11) and chars(). Generators: Stream.generate(supplier) is infinite and unordered; Stream.iterate(seed, f) is infinite, and Java 9 added iterate(seed, hasNext, next) as a stream-style for loop that stops. Stream.ofNullable(x) (Java 9) gives an empty or single-element stream. Stream.concat(a, b) joins two. Always bound an infinite stream with limit, takeWhile or a short-circuiting terminal operation.

Stream.iterate(1, n -> n * 2).limit(5).toList();          // 1,2,4,8,16
Stream.generate(UUID::randomUUID).limit(3).toList();
try (Stream<String> lines = Files.lines(Path.of("a.txt"))) {
    lines.filter(l -> l.contains("ERROR")).forEach(System.out::println);
}
I need a custom intermediate operation, like a sliding window. Is that possible? Senior

What the interviewer is testing: awareness of newer releases and the limits of the stream API.

Before Java 22, you could not add your own intermediate operation. You could write a custom Collector (a terminal step) or a custom Spliterator, which is advanced and rare. Java 22 introduced Stream Gatherers as a preview (JEP 461), second preview in 23, and they became final in Java 24 (JEP 485). A Gatherer is a custom intermediate operation that can keep state and emit zero or more outputs per input. Java ships built-ins in java.util.stream.Gatherers: windowFixed, windowSliding, fold, scan, mapConcurrent. This is beyond Java 21, so in a Java 21 shop the answer is: write a loop, use a library, or write a custom collector.

// Java 24+
Stream.of(1,2,3,4,5).gather(Gatherers.windowSliding(3)).toList();
// [[1,2,3],[2,3,4],[3,4,5]]

3. Collectors

What does collect do, and what is the difference between collect and reduce? Intermediate

What the interviewer is testing: mutable reduction versus immutable reduction.

collect is a mutable reduction: it uses a mutable container (a list, a map, a StringBuilder) and adds elements into it. A Collector has four parts: a supplier that creates an empty container, an accumulator that adds one element, a combiner that merges two containers (for parallel runs), and an optional finisher that converts to the final result. reduce combines values into a new immutable value each time, which is right for sums and max, but wasteful for building collections. That is why you write collect(Collectors.toList()) and not reduce(new ArrayList<>(), ...). The Collectors class has ready-made collectors, and you can build your own with Collector.of(...).

Collector<String, StringBuilder, String> joiner = Collector.of(
    StringBuilder::new, StringBuilder::append, StringBuilder::append, StringBuilder::toString);
How does groupingBy work, with downstream collectors? Intermediate

What the interviewer is testing: the most used collector. Can you do group-and-count, group-and-sum, and group-and-map.

groupingBy(classifier) puts each element into a bucket named by the classifier's result, and returns a Map<K, List<T>>. The second argument is a downstream collector that decides what each bucket becomes: counting() gives a Long count, summingInt, averagingDouble, mapping(f, toList()) to keep only a field, maxBy(comparator), joining, or even another groupingBy for two-level grouping. The three-argument form takes a map factory, for example TreeMap::new for sorted keys. By default the map is a HashMap, so order is not guaranteed. A null key throws NullPointerException ("element cannot be mapped to a null key"). Java 9 added filtering and flatMapping downstream collectors.

Map<String, Long> count = emps.stream().collect(groupingBy(Emp::dept, counting()));
Map<String, Double> avg = emps.stream().collect(groupingBy(Emp::dept, averagingDouble(Emp::salary)));
Map<String, List<String>> names = emps.stream()
    .collect(groupingBy(Emp::dept, TreeMap::new, mapping(Emp::name, toList())));
What is partitioningBy, and how is it different from groupingBy? Basic

What the interviewer is testing: the special two-bucket collector and its guarantee.

partitioningBy(predicate) splits elements into two groups: those where the predicate is true and those where it is false. The result is a Map<Boolean, List<T>> that always contains both keys, even if one list is empty. With groupingBy, a key that has no elements is simply missing, so you must handle absence. Partitioning also accepts a downstream collector, so partitioningBy(p, counting()) counts both sides in one pass. Use it for "pass or fail", "even or odd", "valid or invalid" splits.

Map<Boolean, List<Integer>> parts = nums.stream().collect(partitioningBy(n -> n % 2 == 0));
List<Integer> evens = parts.get(true);
Map<Boolean, Long> counts = nums.stream().collect(partitioningBy(n -> n > 10, counting()));
How does Collectors.toMap behave with duplicate keys and nulls? Intermediate

What the interviewer is testing: a classic production bug, and the three-argument fix.

The two-argument toMap(keyFn, valueFn) throws IllegalStateException: Duplicate key X (attempted merging values A and B) if two elements give the same key. Fix it with the three-argument form, which takes a merge function that says what to do on a clash: keep the first, keep the last, add them, or concatenate. The four-argument form adds a map supplier, for example LinkedHashMap::new to keep encounter order, because the default is a HashMap. Also know that toMap throws NullPointerException when a value is null (it uses HashMap.merge internally), even though HashMap allows null values. If you only need grouping, groupingBy is usually the better tool because duplicates are expected there.

Map<String, Integer> byName = people.stream()
    .collect(Collectors.toMap(Person::name, Person::age, (a, b) -> a));   // keep first
Map<String, Integer> sum = items.stream()
    .collect(Collectors.toMap(Item::sku, Item::qty, Integer::sum, LinkedHashMap::new));
Likely follow-ups
  • Which key does the merge function see first? The existing value is the first argument, the new one is the second.
How do you join strings, and what are the other handy collectors? Basic

What the interviewer is testing: daily fluency with Collectors.

Collectors.joining() concatenates CharSequence elements; joining(", ") adds a separator and joining(", ", "[", "]") adds a prefix and suffix. Elements must already be strings, so map(String::valueOf) first. Other handy ones: counting(), summingInt/Long/Double, averagingInt, minBy/maxBy (return Optional), summarizingInt (count, sum, min, avg, max in one pass), toSet(), toCollection(TreeSet::new) to choose the container, collectingAndThen(downstream, finisher) to post-process (for example make an unmodifiable list), mapping, filtering, flatMapping, and reducing. Since Java 10, toUnmodifiableList/Set/Map give immutable results.

String csv = ids.stream().map(String::valueOf).collect(joining(",", "(", ")"));
IntSummaryStatistics s = emps.stream().collect(summarizingInt(Emp::age));
List<String> ro = names.stream().collect(collectingAndThen(toList(), Collections::unmodifiableList));
What is Collectors.teeing? Intermediate

What the interviewer is testing: knowing the Java 12 addition, and the "two results in one pass" idea.

teeing (Java 12) sends every element to two collectors at the same time, and then merges their two results with a function you give. It solves the stream-reuse problem: you want, say, both the minimum and the maximum, or the sum and the count, but a stream can only be read once. Without it you would traverse twice or write a custom accumulator class. The name comes from the Unix tee command that splits a pipe.

double avg = Stream.of(4, 8, 6).collect(
    Collectors.teeing(summingInt(i -> i), counting(), (sum, n) -> (double) sum / n));
record MinMax(int min, int max) {}
MinMax mm = nums.stream().collect(teeing(minBy(naturalOrder()), maxBy(naturalOrder()),
    (a, b) -> new MinMax(a.get(), b.get())));
Stream.toList() versus Collectors.toList(): what is the difference? Intermediate

What the interviewer is testing: a small Java 16 detail that breaks code during upgrades.

Stream.toList() (Java 16) is a shortcut that returns an unmodifiable list. Calling add or remove throws UnsupportedOperationException. Collectors.toList() returns an ArrayList in practice, but the Javadoc promises nothing about type, mutability or thread-safety. Another difference: Stream.toList() allows null elements, while Collectors.toUnmodifiableList() (Java 10) and List.of reject them with NullPointerException. So a mechanical search-and-replace from collect(Collectors.toList()) to toList() can break code that later mutates the list. My rule: use toList() by default, and collect(toCollection(ArrayList::new)) when I really need a mutable list.

Likely follow-ups
  • Is the result of Stream.toList() a copy? It is a list built from the stream's elements, and it is unmodifiable, but the objects in it are the same objects, so they can still be changed.
How do you sort a map by value, and keep that order? Intermediate

What the interviewer is testing: a very common coding question that checks if you know a HashMap has no order.

A HashMap has no order, so sorting must produce an ordered structure. Stream over entrySet(), sort entries with Map.Entry.comparingByValue() (add Comparator.reverseOrder() for descending), and collect into a LinkedHashMap, which keeps insertion order. You need the four-argument toMap with a merge function and LinkedHashMap::new. If you only need the keys in order, map to the keys and collect into a list; that is simpler. Collecting back to a plain HashMap silently loses the order, a classic mistake.

Map<String, Long> sorted = counts.entrySet().stream()
    .sorted(Map.Entry.<String, Long>comparingByValue().reversed())
    .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue,
             (a, b) -> a, LinkedHashMap::new));

4. Parallel streams, performance and debugging

How does a parallel stream work? Intermediate

What the interviewer is testing: the fork/join model under the hood and the shared pool.

Calling parallelStream() or .parallel() marks the pipeline as parallel. At the terminal operation, the source's Spliterator splits the data into smaller chunks again and again (like a binary tree). Chunks run as tasks in the common ForkJoinPool, which is one pool shared by the whole JVM, with about cores - 1 worker threads, and the calling thread helps. Each chunk produces a partial result, and the combiner merges them back up the tree. This works well when the source splits cheaply and evenly (ArrayList, arrays, IntStream.range), the operation is CPU-bound, and the pieces are independent.

Likely follow-ups
  • How do I change the pool size? -Djava.util.concurrent.ForkJoinPool.common.parallelism=N, or run the stream inside your own ForkJoinPool (a known trick, but not officially guaranteed). More in the concurrency page.
When should you NOT use a parallel stream? Senior

What the interviewer is testing: judgement. Most good answers are "almost never, unless measured".

Avoid it when: the data is small (the split and merge cost is larger than the work); the source splits badly (LinkedList, Stream.iterate, Files.lines in older versions); the operations are cheap (a sum of ints is usually faster sequentially); the work blocks on I/O, database or HTTP calls (blocked workers in the common pool starve everything else in the JVM, including other parallel streams and CompletableFuture.supplyAsync without an executor); the lambdas have side effects or touch shared mutable state; the pipeline has stateful or order-dependent steps (sorted, limit, findFirst, forEachOrdered); or you run inside a web server where many requests already use all cores. A usable rule: you need a large collection (tens of thousands of elements), CPU-heavy per-element work, independent elements, and a benchmark that shows a gain. In server code I prefer explicit executors where I control the pool size.

Common mistakes: adding .parallel() "to make it faster" without measuring, or calling a remote service inside a parallel map.
Does a parallel stream keep order? What about forEach versus forEachOrdered? Intermediate

What the interviewer is testing: encounter order and its cost.

It depends on the stream's encounter order: lists and arrays are ordered, HashSet streams are not. For an ordered source, operations like collect(toList()), findFirst and limit still return results in encounter order, even in parallel; Java merges chunks back in order, which costs some performance. But forEach in parallel runs on many threads, in any order, so output can look scrambled. forEachOrdered respects the order but gives up much of the parallel gain. If order does not matter, call unordered() or use findAny and the library can do less work. The practical lesson: never rely on forEach order in a parallel stream, and never mutate a shared list from it.

Are streams faster than for loops? What performance myths should I avoid? Senior

What the interviewer is testing: engineering maturity: measure, do not guess.

Streams are not faster than a plain loop. For simple work a loop is the same or faster, because it has no pipeline objects, no lambdas to inline and no boxing. Streams win on readability and composition, and the JIT compiler often inlines the lambdas so the difference is small. Myths: "parallel is always faster" (false, see above); "streams are slow" (usually false for normal business code, where the database call dominates); "a stream avoids creating objects" (it creates several small objects, and boxed numbers if you use Stream<Integer>); "chain order does not matter" (it does: filter before map, and filter before sorted, to reduce work). For hot numeric code, use primitive streams or loops. Always measure with a proper tool like JMH (the Java microbenchmark harness), not with System.currentTimeMillis around one run, because of JIT warm-up.

Likely follow-ups
  • One concrete tuning tip? Put cheap, selective filter steps first, avoid sorted before limit when you can, and avoid repeated boxing.
Why are side effects in stream lambdas a problem? What should lambdas be? Senior

What the interviewer is testing: the Stream contract: non-interfering, stateless, preferably side-effect-free.

The stream Javadoc asks for lambdas that are non-interfering (do not change the source while the stream runs), stateless (result does not depend on anything that may change during the run) and free of harmful side effects. If you break this, three things go wrong. In a sequential stream, modifying the source list during a pipeline throws ConcurrentModificationException or gives undefined results. In a parallel stream, adding to a shared ArrayList from many threads loses elements or throws ArrayIndexOutOfBoundsException, because the list is not thread-safe. Even in a sequential stream, a side effect inside map or filter may run a surprising number of times, or never, because of laziness and short-circuiting. The fix is to return the result and let a collector build it, not to push into an outside list.

// bad
List<String> out = new ArrayList<>();
names.parallelStream().filter(n -> n.length() > 3).forEach(out::add);   // race!
// good
List<String> out = names.stream().filter(n -> n.length() > 3).toList();
How do you debug a stream pipeline? Intermediate

What the interviewer is testing: practical habits, since stack traces from streams are noisy.

First, split a long chain into named steps (not always as streams, sometimes as variables after a collect), so you can inspect each stage. Second, use peek(x -> log.debug("after filter: {}", x)) temporarily between steps, remembering it is lazy and only runs when elements flow. Third, use the IDE: IntelliJ has "Trace Current Stream Chain" in the debugger that shows what each step received and produced; Eclipse and others have a similar view. Fourth, put a breakpoint inside the lambda body, which works fine once you use a block lambda or a method reference to a named method. Fifth, read the stack trace from the bottom: exceptions inside lambdas appear with many frames of java.util.stream internals, and the useful frame is your lambda (named like lambda$main$0). A named private method instead of a long inline lambda gives a readable frame and is easy to unit test.

5. Optional

What is Optional for, and how should you use it correctly? Basic

What the interviewer is testing: the design intent: a return type that says "there may be no result".

Optional<T> is a small box that holds either one value or nothing. It was added in Java 8 for return types of methods that may legitimately have no result, such as findById. It forces the caller to think about the empty case, instead of getting a surprise NullPointerException. Create with Optional.of(x) (throws if x is null), Optional.ofNullable(x) (empty if null) and Optional.empty(). Consume with map, flatMap, filter, orElse, orElseGet, orElseThrow, ifPresent, ifPresentOrElse (Java 9), or (Java 9), stream (Java 9). Chain these instead of calling isPresent() and get().

String city = findUser(id)                      // Optional<User>
    .map(User::address)                         // may be null: use flatMap if it returns Optional
    .map(Address::city)
    .orElse("unknown");
findUser(id).ifPresentOrElse(u -> log(u), () -> log("no user"));
What are the common Optional anti-patterns? Intermediate

What the interviewer is testing: do you know where Optional should not appear.

First: opt.get() without checking. It throws NoSuchElementException, which is just a NullPointerException in a new coat. Prefer orElseThrow() (no-argument, Java 10) which says clearly that absence is an error. Second: if (opt.isPresent()) { opt.get() }, which is a null check in disguise; use map or ifPresent. Third: Optional as a field, a method parameter or inside a collection. It is not Serializable, adds an object, and the caller can still pass null as the Optional itself. Use overloads or a nullable parameter. Fourth: Optional.of(x) with a value that can be null. Fifth: returning null from a method that returns Optional. Sixth: orElse(expensiveCall()), which always runs the call; use orElseGet(() -> ...). Seventh: Optional of a collection; return an empty collection instead. And never use it for performance-critical inner loops, or for primitives (use OptionalInt).

Likely follow-ups
  • Is Optional a monad? Loosely: it has of, map and flatMap. Do not worry about the word in interviews, just show the chaining.
Common mistakes: wrapping every nullable thing in Optional, including entity fields. It makes JPA mapping and JSON binding awkward.
What is the difference between orElse and orElseGet? Basic

What the interviewer is testing: eager versus lazy arguments. A very common question.

orElse(value) takes a value, so Java computes that value before the call, whether or not the Optional is empty. orElseGet(supplier) takes a Supplier and only calls it when the Optional is empty. If the fallback is a constant like "N/A", both are the same. If the fallback creates an object, hits the database, or has a side effect, use orElseGet, otherwise you pay the cost (or cause the side effect) every time, even when a value exists. orElseThrow(supplier) is also lazy: the exception is only built when needed.

User u = repo.find(id).orElse(createDefaultUser());        // createDefaultUser() ALWAYS runs
User v = repo.find(id).orElseGet(() -> createDefaultUser()); // runs only if empty
User w = repo.find(id).orElseThrow(() -> new NotFoundException(id));
Optional.map versus flatMap, and how do you chain nullable getters safely? Intermediate

What the interviewer is testing: the same map/flatMap idea as streams, applied to a single value.

map(f) applies f to the value if present and wraps the result; if f returns null the result becomes empty, which is handy for legacy getters that can return null. flatMap(f) is for a function that already returns an Optional; it avoids an Optional<Optional<T>>. The pattern Optional.ofNullable(order).map(Order::customer).map(Customer::address).map(Address::zip).orElse("none") replaces three nested null checks. Keep chains short. If a chain is longer than three or four steps, the domain model probably needs a better shape.

Optional<Address> addr = findUser(id).flatMap(User::primaryAddress); // returns Optional
String zip = findUser(id).map(User::legacyAddress).map(Address::zip).orElse("");
Optional.of or ofNullable? And how do you treat null in the first place? Basic

What the interviewer is testing: practical null discipline.

Optional.of(x) throws NPE immediately if x is null; use it when you know the value exists, so a bug fails loudly. Optional.ofNullable(x) turns a possible null into empty; use it at the boundary with legacy code. Beyond Optional, good null discipline: return empty collections instead of null, use Objects.requireNonNull(x, "msg") to fail fast in constructors, use Objects.requireNonNullElse(x, def) (Java 9) for defaults, and annotate nullability (@Nullable) so tools can warn. Since Java 14 (on by default from 15), "helpful NullPointerException" messages tell you exactly which variable or method call was null, for example Cannot invoke "String.length()" because "user.name" is null, which makes the old "NPE with no clue" mostly a problem of the past.

6. java.time (date and time API)

What was wrong with java.util.Date and Calendar, and what does java.time fix? Basic

What the interviewer is testing: can you name concrete problems, not just "it was bad".

Date is misnamed: it is really a timestamp (milliseconds since the epoch) and has no time zone, yet its toString prints in the JVM's default zone, which confuses people. It is mutable, so passing one around lets others change it. Its deprecated constructor has years counted from 1900 and months from 0. Calendar also counts months from 0, is mutable, verbose and not thread-safe. SimpleDateFormat is not thread-safe: sharing one instance gives corrupt output under load. java.sql.Date and Timestamp extend Date in awkward ways. The java.time package (Java 8, JSR-310, designed by the Joda-Time author) fixes this: types are immutable and thread-safe, months are 1 to 12 (with a Month enum), there are separate types for date, time, instant and zoned time, and DateTimeFormatter is thread-safe.

Likely follow-ups
  • How do I convert? date.toInstant() and Date.from(instant); calendar.toInstant(); GregorianCalendar.toZonedDateTime().
Explain LocalDate, LocalDateTime, Instant, ZonedDateTime and OffsetDateTime. When do you use which? Intermediate

What the interviewer is testing: choosing the right type is 80 percent of avoiding time bugs.

Instant is a point on the global timeline (nanoseconds since 1970-01-01T00:00Z), with no zone. Use it for "when did this happen" such as audit times, event times and database timestamps. LocalDate is a calendar date with no time or zone (a birthday, an invoice date). LocalTime is a time of day. LocalDateTime is date plus time with no zone: it does not identify a real moment, it is only a "wall clock reading", good for "the shop opens at 09:00 local". ZonedDateTime is a local date-time plus a ZoneId such as Europe/Berlin, so it knows DST rules. OffsetDateTime is date-time with a fixed offset like +02:00 and no rules; it suits APIs and databases. A good habit: store and transfer Instant (or UTC), convert to ZonedDateTime only for display or for calendar arithmetic in the user's zone.

What is the difference between Duration and Period? Intermediate

What the interviewer is testing: machine time versus human calendar time.

Duration is an exact amount of time in seconds and nanoseconds, like 36 hours. It is machine time. Period is an amount of calendar in years, months and days, like "1 month and 3 days". It is human time, and its real length depends on the date: one month from January 31 is not the same number of seconds as one month from February 1. Use Duration.between(instantA, instantB) for elapsed time and timeouts, and Period.between(dateA, dateB) for age or "3 months from now". Across a DST change, plus(Period.ofDays(1)) on a ZonedDateTime keeps the same local clock time (so the day may be 23 or 25 hours), while plus(Duration.ofHours(24)) adds exactly 24 hours of real time.

Duration d = Duration.between(start, end);            // Instants or LocalDateTimes
long mins = d.toMinutes();
Period age = Period.between(birthDate, LocalDate.now());
int years = age.getYears();
How does java.time handle time zones and DST? What are gaps and overlaps? Senior

What the interviewer is testing: real knowledge of the hardest part of time handling.

A ZoneId such as America/New_York carries rules from the IANA time-zone database: when the offset changes and by how much. Twice a year in many zones a local clock changes. In spring there is a gap: for example 02:00 to 03:00 does not exist, so a local time of 02:30 is invalid. ZonedDateTime.of resolves it by moving forward by the gap length (to 03:30). In autumn there is an overlap: 01:00 to 02:00 happens twice, so a local time like 01:30 is ambiguous. By default Java picks the earlier offset (the summer one), and you can choose with withEarlierOffsetAtOverlap() or withLaterOffsetAtOverlap(). Also, zone rules are data that changes: governments change DST rules, and the JDK tzdata is updated by patch releases (or the tzupdater tool), so old JDKs get dates wrong. For future events such as a meeting next year, store the local date-time plus the zone ID, not a computed UTC instant, because the offset may change before the event.

Likely follow-ups
  • Offset versus zone? +01:00 is a fixed number; Europe/Paris is a set of rules, giving +01:00 in winter and +02:00 in summer.
How do you parse and format dates, and what are the common pattern mistakes? Intermediate

What the interviewer is testing: thread-safe formatting and the famous YYYY bug.

Use DateTimeFormatter. It is immutable and thread-safe, so keep it as a static final constant; that is the opposite of SimpleDateFormat. Predefined ones like ISO_LOCAL_DATE and ISO_INSTANT cover most APIs. For custom patterns use ofPattern("dd/MM/yyyy"). Pattern traps: lowercase yyyy is the year; uppercase YYYY is the week-based year, which makes 2024-12-30 print as 2025 in many locales (a real end-of-year bug). MM is month and mm is minutes. HH is 24-hour and hh is 12-hour (needs a for AM/PM). Parsing a string with only a date into LocalDateTime fails; use the matching type, or LocalDate.parse. Always pass a Locale when month names are involved. A parse failure throws DateTimeParseException.

static final DateTimeFormatter F = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm");
LocalDateTime t = LocalDateTime.parse("2025-03-09 14:30", F);
String s = ZonedDateTime.now(ZoneId.of("Asia/Kolkata")).format(DateTimeFormatter.ISO_OFFSET_DATE_TIME);
How do you make time-dependent code testable? Intermediate

What the interviewer is testing: design habit: inject the clock.

Do not call LocalDate.now() or Instant.now() deep inside business code, because tests then depend on the real date and break on the 31st or at midnight. All now() methods have an overload taking a Clock. Inject a Clock into the class (in Spring, define a Clock bean with Clock.systemUTC()). In tests use Clock.fixed(instant, zone) for a frozen time or a small custom clock you can advance. This also fixes the "which zone is the server in" confusion, because the zone is explicit in the clock. For measuring elapsed time, use System.nanoTime() or Instant with a monotonic source, not wall-clock differences, since wall clocks can jump.

class Expiry {
    private final Clock clock;
    Expiry(Clock clock) { this.clock = clock; }
    boolean isExpired(Instant t) { return Instant.now(clock).isAfter(t); }
}
new Expiry(Clock.fixed(Instant.parse("2025-01-01T00:00:00Z"), ZoneOffset.UTC));
How do you store dates and times in a database and pass them in JSON? Intermediate

What the interviewer is testing: end-to-end consistency, where most time bugs live.

For events: store UTC. In SQL use TIMESTAMP WITH TIME ZONE where it exists (or a UTC TIMESTAMP by convention) and read as Instant or OffsetDateTime. JDBC 4.2 (Java 8) lets you use java.time types directly via setObject and getObject; JPA 2.2 and Hibernate 5.2 or newer support them too. For pure calendar facts like birthdays, use DATE and LocalDate. In JSON, send ISO-8601 strings (2025-03-09T14:30:00Z) and not epoch numbers or custom formats. With Jackson you need the jackson-datatype-jsr310 module, and you should disable WRITE_DATES_AS_TIMESTAMPS. Set the JVM and DB session time zone explicitly (UTC on servers), so that behaviour does not depend on the machine.

7. Language features: String, var, factories, records, sealed, patterns, switch

What did Java 11 to 15 add to String? Basic

What the interviewer is testing: small but handy methods, with the right version and the whitespace subtlety.

Java 11 added isBlank() (true if empty or only whitespace), strip(), stripLeading(), stripTrailing(), lines() (a stream of lines) and repeat(n). The difference between strip and trim: trim removes only characters up to U+0020 (ASCII control and space), while strip uses Character.isWhitespace and so also removes Unicode spaces. Java 12 added indent and transform. Java 15 added formatted(args), an instance version of String.format, plus stripIndent and translateEscapes (supporting text blocks). Java 21 added indexOf(ch, from, to), splitWithDelimiters and StringBuilder.repeat. Behind the scenes, Java 9 stored strings as compact byte arrays (Latin-1 when possible), saving memory, and string concatenation with + uses invokedynamic since Java 9.

"  ".isBlank();                    // true
"  hi  ".strip();              // "hi" (trim would keep the Unicode space)
"ab".repeat(3);                    // "ababab"
"a\nb\nc".lines().count();         // 3
"Hi %s, you are %d".formatted("Ann", 30);
What are text blocks, and what are their rules? Basic

What the interviewer is testing: version (final in Java 15) and the indentation rule.

A text block is a multi-line string literal between triple quotes. It was a preview in 13 and 14 and became final in Java 15. It removes the need for \n and escaping quotes in JSON, SQL, HTML or XML snippets. The opening """ must be followed by a line break. The compiler removes the common leading indentation (it takes the least-indented line, including the closing delimiter line, as the baseline), and strips trailing spaces on each line. The closing delimiter's position controls whether the string ends with a newline. \ at the end of a line joins it with the next, and \s keeps a trailing space. You can use formatted for placeholders. It is the same type as any String, so there is no run-time difference.

String json = """
    {
      "name": "%s",
      "active": true
    }
    """.formatted(name);
What are the rules and the good style for var? Intermediate

What the interviewer is testing: know it is compile-time inference, not dynamic typing, and its limits.

var (Java 10) lets the compiler infer the type of a local variable from its initializer. The variable is still statically typed: var x = "a" is a String forever. Allowed: local variables with an initializer, for loop variables, and try-with-resources. Not allowed: fields, method parameters, return types, a variable without an initializer, var x = null, array initializer shorthand var a = {1,2}, and a lambda or method reference with no target type. Java 11 allows var in lambda parameters, mainly to attach annotations. var is a reserved type name, not a keyword, so a variable named var still compiles. Style: use it when the type is obvious from the right side (var users = new ArrayList<User>()) and avoid it when it hides information (var result = service.process()). A subtle trap: var list = new ArrayList<>() infers ArrayList<Object>, because the diamond has no target type. And var on an integer literal gives int, not long.

Likely follow-ups
  • Is var a performance feature? No. The bytecode is the same as with the explicit type.
  • Why can var help? It can infer types you cannot write, such as an anonymous class type or intersection types.
How do List.of, Set.of and Map.of work, and how do they differ from Arrays.asList? Intermediate

What the interviewer is testing: Java 9 factories and the many ways "unmodifiable" can differ.

The factories List.of(...), Set.of(...) and Map.of(k1, v1, ...) (up to 10 pairs; use Map.ofEntries for more) arrived in Java 9. They return truly immutable collections: add, remove and even sort throw UnsupportedOperationException. They reject null with NullPointerException, even in contains(null). Set.of and Map.of throw IllegalArgumentException on duplicates. The iteration order of Set.of and Map.of is deliberately randomised per JVM run, so never depend on it. List.copyOf, Set.copyOf, Map.copyOf (Java 10) make immutable copies. Arrays.asList is different: a fixed-size list backed by the array, so set works and writes through to the array but add fails. Collections.unmodifiableList is only a read-only view: if the original changes, the view changes too.

List<String> a = List.of("x", "y");
a.add("z");                                  // UnsupportedOperationException
List<String> b = Arrays.asList("x", "y");
b.set(0, "q");                               // ok, writes through
b.add("z");                                  // UnsupportedOperationException
Map<String,Integer> m = Map.of("a", 1, "b", 2);
Likely follow-ups
  • Are the elements of an immutable list immutable? No, only the list structure is. See the collections page.
What is a record, and what do you get for free? What are its limits? Basic

What the interviewer is testing: version (final in Java 16) and honest limits.

A record is a compact way to declare an immutable data carrier. Preview in 14 and 15, final in Java 16. You write record Point(int x, int y) {} and the compiler generates a private final field per component, a canonical constructor, accessor methods x() and y() (not getX), and equals, hashCode and toString based on all components. A record is implicitly final, cannot extend a class (it extends java.lang.Record), may implement interfaces, and may have static fields and methods, extra constructors and instance methods, but no extra instance fields. A compact constructor lets you validate or normalise without repeating field assignments. Limits: it is only shallowly immutable (a List component can still be changed unless you copy it), it does not follow JavaBean naming (older tools expect getX), and it is a poor JPA entity because entities need a no-argument constructor and mutability, though records work well as DTOs and query projections. Jackson supports records from 2.12.

record Money(BigDecimal amount, String currency) {
    Money {                                       // compact constructor
        Objects.requireNonNull(amount);
        if (amount.signum() < 0) throw new IllegalArgumentException("negative");
        currency = currency.toUpperCase();
    }
    Money add(Money o) { return new Money(amount.add(o.amount), currency); }
}
Likely follow-ups
  • Record versus Lombok @Value? Record is a language feature without a build plugin, but Lombok also gives builders and withers.
  • Can a record be serialized? Yes, with Java serialization it is rebuilt using the canonical constructor, which is safer than for normal classes.
What are sealed classes and interfaces, and why are they useful? Intermediate

What the interviewer is testing: version (final in Java 17) and the link to exhaustive switch.

A sealed type restricts which classes may extend or implement it. You write sealed interface Shape permits Circle, Square. Preview in 15 and 16, final in Java 17. Each permitted subtype must be declared final (or a record, which is final), sealed again, or non-sealed (opens the branch up again). The subtypes must be in the same module (or same package if no module). If the subtypes are in the same file you can omit permits. The point is a closed set of cases that the compiler knows, so a switch over a sealed type can be checked for exhaustiveness: add a new subtype, and every switch without a default fails to compile until you handle it. This models "algebraic data types", for example Result = Success | Failure or PaymentMethod = Card | Wallet | Bank, better than an enum (cases with different data) or an open interface (can be extended anywhere).

sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}

double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.r() * c.r();
        case Square q -> q.side() * q.side();
    };   // exhaustive: no default
}
What is pattern matching for instanceof? Basic

What the interviewer is testing: the flow-scoping rule of the binding variable.

Before Java 16 you wrote an instanceof check and then a separate cast. The pattern form (final in Java 16, preview in 14 and 15) does both: if (obj instanceof String s) tests the type and gives you a variable s already cast. The binding variable is available only where the compiler can prove the test succeeded (flow scoping): inside the if block, to the right of &&, and after an early return when the test is negated. It is not in scope in an || branch or after the if when the test may fail. It removes cast noise and cast mistakes, and it is the base for the switch patterns of Java 21. It is especially nice in equals methods.

if (o instanceof String s && s.length() > 3) { use(s); }
if (!(o instanceof Integer n)) return;
use(n + 1);                                   // n is in scope here

@Override public boolean equals(Object o) {
    return o instanceof Point p && x == p.x && y == p.y;
}
What is the difference between the old switch statement and a switch expression? Intermediate

What the interviewer is testing: version (final in Java 14) and the safety gains.

The classic switch statement uses colons, falls through from one case to the next unless you write break, and is a statement (no value). The switch expression (preview in 12 and 13, final in Java 14) uses arrows case A -> value, has no fall-through, can list several labels (case MON, TUE -> ...), and produces a value you can assign or return. For a block, use yield to return the value. It must be exhaustive: for an enum, either all constants are covered or you add default; the compiler errors otherwise. That is a real safety win: add a new enum constant and the compiler shows you every switch that needs updating. A missing break was a classic bug source, and now it cannot happen with arrows. An arrow case may be an expression, a block, or a throw.

int days = switch (month) {
    case FEB -> 28;
    case APR, JUN, SEP, NOV -> 30;
    default -> {
        log.debug("long month");
        yield 31;
    }
};
Explain pattern matching for switch, guards with when, record patterns and case null. Senior

What the interviewer is testing: Java 21 features and the ordering rules. Be exact about preview history.

Pattern matching for switch lets a switch test the type of the selector: case Circle c -> .... It was preview in 17 to 20 and final in Java 21 (JEP 441). A guard adds a condition with when: case Integer i when i > 10 -> .... Record patterns (preview in 19 and 20, final in Java 21, JEP 440) take a record apart in the pattern itself, including nested ones: case Line(Point(var x1, var y1), Point p2) -> .... case null is allowed in Java 21; without it, a null selector throws NullPointerException as before. Rules: the compiler checks dominance: a more general case before a more specific one is a compile error ("this case label is dominated"), so put guarded and specific cases first. The switch must be exhaustive, which is easy with a sealed type. Java 22 made unnamed patterns and variables (_) final, for when you do not need a component.

String describe(Object o) {
    return switch (o) {
        case null -> "nothing";
        case Integer i when i > 100 -> "big int " + i;
        case Integer i -> "int " + i;
        case String s -> "text of " + s.length();
        case int[] arr -> "ints: " + arr.length;
        case Point(int x, int y) when x == y -> "diagonal point";
        case Point(var x, var y) -> "point " + x + "," + y;
        default -> "other";
    };
}
Likely follow-ups
  • What if I reverse Integer i and Integer i when i > 100? Compile error: the general case dominates the guarded one.
  • Does it replace polymorphism? No. Use virtual methods when you own the types and the behaviour belongs to them; use switch patterns for operations on closed data (sealed hierarchies, records), especially when you do not want to add methods to those types.
When do you pick an enum, a sealed interface with records, or a normal polymorphic class? Senior

What the interviewer is testing: design judgement with the new tools.

Use an enum when the cases are a fixed set of constants that carry the same shape of data (days, status codes). Use a sealed interface with records when the cases are fixed but each carries different data (a payment is a card number, or a wallet id, or a bank account). That gives you exhaustive switches and immutable data. Use a normal polymorphic class hierarchy when the set of types is open (plugins, user extensions) or when behaviour belongs inside the type and callers should not care about the concrete type. The trade-off is the classic "expression problem": adding a new type is easy with polymorphism but adding a new operation touches every class; with sealed types and switches, adding a new operation is easy (one new switch) but adding a new type touches every switch (and the compiler lists them for you). Pick the axis that changes more often.

8. Platform: sequenced collections, virtual threads, HttpClient, modules, GC, LTS

What are sequenced collections (Java 21)? Intermediate

What the interviewer is testing: a Java 21 API change that fixes a long-standing inconsistency.

Before 21, "get the last element" was different for each collection: list.get(list.size() - 1), deque.getLast(), linkedHashSet had no way except iterating, and SortedSet.last(). Java 21 (JEP 431) added three interfaces: SequencedCollection, SequencedSet and SequencedMap, for collections that have a defined encounter order. They give getFirst(), getLast(), addFirst, addLast, removeFirst, removeLast, and reversed(), which returns a live reversed view (not a copy). SequencedMap adds firstEntry, lastEntry, pollFirstEntry, putFirst, sequencedKeySet and so on. List, Deque, LinkedHashSet, LinkedHashMap, SortedSet and SortedMap now implement these. HashSet and HashMap do not, because they have no order. Calling getFirst() on an empty list throws NoSuchElementException, and on an immutable list the add and remove methods throw UnsupportedOperationException.

List<String> l = new ArrayList<>(List.of("a", "b", "c"));
l.getFirst();            // "a"   (Java 21)
l.getLast();             // "c"
l.reversed();            // view: c, b, a
LinkedHashMap<String,Integer> m = new LinkedHashMap<>();
m.putFirst("x", 1);      // new in 21
What are virtual threads (Java 21), and when do they help? Senior

What the interviewer is testing: the model, the limits, and not overselling it. Details of concurrency belong in the sibling page.

A virtual thread is a lightweight thread managed by the JVM, not the OS. Preview in 19 and 20, final in Java 21 (JEP 444, Project Loom). A normal platform thread is a thin wrapper over an OS thread: about a megabyte of stack reserved and slow to create, so you pool and limit them. Virtual threads cost very little (a few KB, growing on the heap), so you can have millions. The JVM runs them on a small pool of carrier threads. When a virtual thread blocks on I/O (a socket read, a sleep, a lock from java.util.concurrent), it is unmounted from its carrier, which is then free to run another virtual thread. This lets you write simple blocking code, one thread per request, yet scale like async code. They help with I/O-bound work with many concurrent waits. They do not help CPU-bound work (still limited by cores). Rules: do not pool them (create one per task, for example Executors.newVirtualThreadPerTaskExecutor()); limit concurrency to downstream resources with a semaphore, because 10,000 virtual threads will happily open 10,000 database connections; be careful with ThreadLocal (millions of copies); and know pinning: in Java 21, a virtual thread blocked inside a synchronized block or a native call keeps its carrier thread pinned. Java 24 (JEP 491) removed the synchronized pinning. Deep coverage: the concurrency page.

Likely follow-ups
  • Do they replace reactive programming? For most business services, they remove the need for it, since you keep a simple blocking style. Reactive still helps with back-pressure-driven streaming.
  • Structured concurrency and scoped values? In Java 21 both were preview (still preview or evolving in later releases, with scoped values final in Java 25 and structured concurrency still in preview then; check the release you target).
How does the java.net.http HttpClient work, and how is it better than HttpURLConnection? Intermediate

What the interviewer is testing: modern HTTP without a library, and correct reuse.

Java 9 introduced a new HTTP client as an incubator module, and it became standard in Java 11 as java.net.http. Compared with the old HttpURLConnection it has a fluent builder API, HTTP/2 support with fallback to HTTP/1.1, WebSocket support, synchronous send and asynchronous sendAsync (returning a CompletableFuture, see concurrency), and body handlers for strings, files and streams. The client is immutable and thread-safe, and holds a connection pool, so create one and share it. Set a connectTimeout on the client and a per-request timeout, because by default there is no timeout. It does not throw for 4xx or 5xx responses: you must check statusCode(). In Java 21 HttpClient became AutoCloseable. For heavy needs (retries, interceptors, metrics) people still use libraries such as OkHttp, or the Spring clients.

HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(3)).build();
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com/items"))
    .timeout(Duration.ofSeconds(5)).header("Accept", "application/json").GET().build();
HttpResponse<String> res = client.send(req, HttpResponse.BodyHandlers.ofString());
if (res.statusCode() != 200) throw new IllegalStateException("HTTP " + res.statusCode());
client.sendAsync(req, HttpResponse.BodyHandlers.ofString()).thenApply(HttpResponse::body);
What is the Java module system (JPMS) in simple terms, and do application developers need it? Intermediate

What the interviewer is testing: the basics, and honesty about practical use.

JPMS (Java 9, project Jigsaw) adds a level above packages: the module. A module has a module-info.java that says what it requires and which packages it exports. Two big ideas. Reliable configuration: the JVM checks at startup that required modules exist, so a missing dependency fails early instead of as a NoClassDefFoundError in production. Strong encapsulation: a public class in a package that is not exported is not accessible to other modules, even by reflection (unless the module opens it). The JDK itself was split into modules (java.base, java.sql, java.xml), and jlink can build a small custom runtime with only the modules you need, and jdeps shows dependencies. In practice most business applications still run on the classpath (the "unnamed module"), where everything is readable. Plain jars on the module path become "automatic modules". As an app developer you mostly feel JPMS through strong encapsulation of JDK internals during upgrades (--add-opens), and through library authors who ship module-info.

What are the default garbage collectors and JVM defaults across versions? Senior

9. Migration from Java 8 to 11, 17 and 21

You are asked to upgrade a Java 8 application to 17 or 21. How do you approach it? Senior

What the interviewer is testing: a calm, staged plan, not "change the version in pom.xml".

I upgrade in stages and keep the app releasable at each stage. First, inventory: build tools (Maven or Gradle plugin versions), frameworks (Spring, Hibernate), libraries that use bytecode tricks (Lombok, Mockito, ByteBuddy, cglib, ASM, Jacoco, Jackson modules), and JVM flags in startup scripts. Second, run jdeps --jdk-internals to find uses of JDK internals, and jdeprscan for removed APIs. Third, upgrade libraries and build plugins first, while still on Java 8 where they allow it. Fourth, compile and test on 11 first (the big break: removed Java EE modules and the module system), then 17 (strong encapsulation, no --illegal-access), then 21 (mostly smooth). Fifth, fix runtime flags: remove obsolete GC and logging flags, switch to -Xlog. Sixth, run the whole test suite, performance tests and a canary in production with GC logs on. Do not adopt new language features in the same change; do that afterwards.

Which APIs were removed between Java 8 and 17, and what broke because of that? Senior

What the interviewer is testing: concrete, remembered migration knowledge.

The biggest: Java EE and CORBA modules, deprecated in 9 and removed in Java 11 (JEP 320): java.xml.bind (JAXB), java.xml.ws (JAX-WS), java.activation, java.xml.ws.annotation (that is javax.annotation.PostConstruct and friends), java.corba and java.transaction. What is "illegal reflective access", and why does it fail on Java 17? Senior

What the interviewer is testing: the most common upgrade failure and the right way to handle it.

Many libraries used reflection with setAccessible(true) to touch private parts of JDK classes (for example java.lang or java.util internals). With the module system in Java 9, the JDK's internal packages are encapsulated. For compatibility, Java 9 to 15 defaulted to --illegal-access=permit: it still worked and printed a warning. Java 16 changed the default to deny (JEP 396), and Java 17 removed the flag completely (JEP 403), so such access throws InaccessibleObjectException: Unable to make field ... accessible: module java.base does not "opens java.lang" to unnamed module. Real fixes, in order of preference: upgrade the library (most have fixed it: newer Lombok, Mockito, ByteBuddy, Jackson, Hibernate, Spring), replace the code that pokes into JDK internals, and only as a last resort add --add-opens java.base/java.lang=ALL-UNNAMED to the JVM arguments (also in test runner arguments such as Surefire's argLine). The --add-opens flag is a workaround you track as technical debt.

java --add-opens java.base/java.lang=ALL-UNNAMED \
     --add-opens java.base/java.util=ALL-UNNAMED -jar app.jar
What is the javax to jakarta change, and how does it relate to the Java upgrade? Senior

What the interviewer is testing: it is a separate change from the JDK upgrade that teams often confuse with it.

Oracle handed Java EE to the Eclipse Foundation, which renamed it Jakarta EE. Jakarta EE 8 kept the javax.* package names. From Jakarta EE 9 the packages were renamed to jakarta.* (javax.servlet to jakarta.servlet, javax.persistence to jakarta.persistence, javax.validation to jakarta.validation, javax.annotation to jakarta.annotation). This is not a JDK change. But it lands on the same upgrade projects: Spring Boot 3 and Spring Framework 6 (late 2022) require Java 17 and Jakarta EE 9+, so moving to Boot 3 means both a JDK upgrade and a mass rename of imports. Also Tomcat 10+, Hibernate 6 and Jetty 11+ use jakarta. Note that javax.* packages that belong to the JDK itself (javax.net.ssl, javax.crypto, javax.swing) are not renamed. Why did Java 8 behave badly in containers, and what changed? Senior

What the interviewer is testing: a real production issue related to upgrading. The JVM page goes deeper.

The early Java 8 builds read CPU count and memory from the host machine, not from the container's cgroup limits. In a pod limited to 1 CPU and 1 GB on a 64 GB, 32 core node, the JVM sized the default heap as a quarter of the host's RAM, created GC and compiler threads for 32 cores, and the common ForkJoinPool had 31 workers. Result: the container got killed by the kernel (OOMKilled) or ran with heavy thread contention. Java 8u191 backported container support, and Java 10 has it from the start (-XX:+UseContainerSupport is on by default). Use -XX:MaxRAMPercentage=75 instead of fixed -Xmx where you can, and set CPU limits knowingly because they decide the active processor count (and the parallel stream pool size). That is another reason a plain upgrade often helps resource use.

10. Functional style in Java and its trade-offs

How functional is Java, and what are the trade-offs of the functional style? Senior

What the interviewer is testing: balanced judgement, not enthusiasm.

Java is an object-oriented language that borrowed useful functional tools: first-class behaviour through lambdas, immutable value types, higher-order functions (map, filter), and now algebraic data types (sealed types plus records plus pattern matching). It is not a pure functional language: no tail-call optimisation, no persistent data structures in the JDK, no native currying, and checked exceptions fit poorly. Benefits: declarative code that says what, not how; fewer mutable variables and loops with indices; easy composition; code that is simpler to reason about and to test when functions are pure (same input gives same output, no side effects); and better thread-safety with immutable data. Costs: long chains become hard to read and debug; stack traces are noisy; allocation overhead in hot paths; checked exceptions are awkward; and teams less used to it write clever, unreadable pipelines. My guideline: use streams for transforming and aggregating data in a few clear steps, keep lambdas short (extract a named method if more than three lines), keep side effects at the edges (I/O at the boundary, pure logic in the middle), and use a plain loop when the logic has early exits, multiple accumulators, or lots of state.

Likely follow-ups
  • What is a pure function? Output depends only on its inputs and it has no side effects. That makes it trivially testable and safe to run in parallel.
  • What is currying? Turning a function of two arguments into a function that returns a function. You can write Function<Integer, Function<Integer,Integer>>, but it is not idiomatic in Java.
When would you choose a for loop over a stream? Intermediate

What the interviewer is testing: pragmatism.

A loop is better when: you need to break, continue or return early in complex ways; you update several variables in one pass; you need the index; the body throws checked exceptions; you mutate state on purpose; the code is on a measured hot path; or the logic is simple and a stream would be longer. A stream is better when the job is a transformation: filter, map, group, aggregate, with no outside state. A good check: if you find yourself using AtomicInteger, a one-element array or an external list inside a lambda, you are forcing a loop's job into a stream. For index-based work, IntStream.range(0, n) is a middle ground, but a normal loop is often clearer.

How do immutable types (records, List.of, java.time) change how you design code? Intermediate

What the interviewer is testing: link between modern features and robust design.

Immutable objects cannot change after creation, so they can be shared freely between threads and cached without locks, and you never worry about "someone changed my object". Modern Java makes this cheap: records for data carriers, List.of/copyOf for collections, java.time types for dates, String for text. Design habits: make fields final, copy mutable inputs in the constructor (List.copyOf(items)), return immutable views or copies from getters, and model change as "new value" (withName style methods or a record that creates a new record). Remember that immutability is shallow by default: a record holding a Date or a mutable ArrayList is not safe until you copy. The cost is more small objects, usually cheap for the JVM, but real in a very hot loop.

11. Coding questions solved with streams

Count the frequency of each word in a sentence. Basic

What the interviewer is testing: groupingBy with counting, and normalising input.

Split on whitespace, normalise case, drop empty strings, and group. Function.identity() means "use the word itself as key". The result is Map<String, Long> because counting() returns a Long. If you want the order of first appearance, pass LinkedHashMap::new; for sorted keys use TreeMap::new.

Map<String, Long> freq = Arrays.stream(text.toLowerCase().split("\\W+"))
    .filter(w -> !w.isEmpty())
    .collect(Collectors.groupingBy(Function.identity(), LinkedHashMap::new, Collectors.counting()));
Find the second highest number in a list. Basic

What the interviewer is testing: handling duplicates and "not enough elements".

The stream answer: take distinct values, sort descending, skip one, take the first, and return an Optional because the list might have fewer than two distinct values. Without distinct() the answer is wrong for [5, 5, 3]. This is O(n log n). If the interviewer pushes for O(n), do a single pass keeping max and second, in a loop; a stream is not a natural fit for that.

Optional<Integer> second = nums.stream()
    .distinct()
    .sorted(Comparator.reverseOrder())
    .skip(1)
    .findFirst();
Flatten a list of lists, and get the unique sorted values. Basic

What the interviewer is testing: flatMap.

Use flatMap(List::stream) to join the inner lists into one stream, then distinct and sorted. For a list of arrays, flatMap(Arrays::stream). For a deeper nesting, apply flatMap again, or use a recursive helper. For primitives, flatMapToInt gives an IntStream.

List<List<Integer>> nested = List.of(List.of(3, 1), List.of(2, 3), List.of());
List<Integer> flat = nested.stream().flatMap(List::stream).distinct().sorted().toList();  // [1, 2, 3]
Split numbers into even and odd, and strings by length, in one pass. Basic

What the interviewer is testing: partitioningBy versus groupingBy.

For a yes/no split use partitioningBy; for many classes use groupingBy. Both can take a downstream collector. With partitioningBy you always get both keys, so get(true) is safe even when empty.

Map<Boolean, List<Integer>> eo = nums.stream().collect(partitioningBy(n -> n % 2 == 0));
Map<Integer, List<String>> byLen = words.stream().collect(groupingBy(String::length));
Map<Boolean, Long> cnt = nums.stream().collect(partitioningBy(n -> n % 2 == 0, counting()));
Find the top 3 most frequent words. Intermediate

What the interviewer is testing: combining group-and-count with sorting entries, and tie-breaking.

First count with groupingBy and counting. Then stream the entries, sort by count descending, add a tie-breaker (alphabetical) so the result is deterministic, and limit(3). For very large inputs, sorting all entries is wasteful: keep a bounded min-heap (PriorityQueue) of size N, which is O(n log N). Mention that trade-off.

List<String> top3 = words.stream()
    .collect(groupingBy(Function.identity(), counting()))
    .entrySet().stream()
    .sorted(Map.Entry.<String, Long>comparingByValue(Comparator.reverseOrder())
            .thenComparing(Map.Entry.comparingByKey()))
    .limit(3)
    .map(Map.Entry::getKey)
    .toList();

What is Stream.mapMulti, and when is it better than flatMap? Senior

What the interviewer is testing: knowing a Java 16 addition and its niche.

mapMulti (Java 16) gives each element a Consumer to which you push zero, one or many output values. With flatMap you must build a small Stream for each input, which has a cost when most inputs produce 0 or 1 outputs. mapMulti skips that allocation, and it is also easier when the logic is imperative (loops, conditions) or recursive. For normal code, flatMap is clearer, so I use mapMulti only after measuring. Type inference needs a hint when the output type is not obvious, as in Stream.<String>mapMulti(...).

List<Object> out = Stream.of(1, 2, 3).<Object>mapMulti((n, sink) -> {
    if (n % 2 == 1) { sink.accept(n); sink.accept("odd"); }
}).toList();
Why do Collectors.filtering and flatMapping exist, when I can filter before grouping? Senior

What the interviewer is testing: subtle correctness: filtering before grouping removes groups, filtering inside a group keeps them.

If you filter the stream first and then call groupingBy, a department with no matching employee disappears from the map. If you use groupingBy(dept, filtering(pred, toList())) (Java 9), every department still appears, and its list may be empty. Pick based on whether you need the empty groups in the report. flatMapping (Java 9) does the same for the one-to-many case, for example grouping orders by customer and collecting all item names in one flat set per customer.

Map<String, List<Emp>> rich = emps.stream()
    .collect(groupingBy(Emp::dept, filtering(e -> e.salary() > 100_000, toList())));
// HR still appears with [] if nobody there earns more
What are helpful NullPointerException messages? Basic

What the interviewer is testing: a small quality-of-life change that helps debugging.

Before, an NPE said only the line number, and in a chain like a.getB().getC().name() you could not tell which part was null. Java 14 added detailed messages behind a flag (-XX:+ShowCodeDetailsInExceptionMessages), and from Java 15 they are on by default. The message now reads like Cannot invoke "String.length()" because "order.customer.name" is null. Local variable names show only if the class was compiled with -g; otherwise you see "<local1>". It does not replace null discipline, but it makes production logs much more useful, and it is one more reason to upgrade.

With default methods, do abstract classes still have a place? Intermediate

What the interviewer is testing: design thinking, not syntax.

Yes. An interface describes a capability and cannot hold instance state: no instance fields, no constructors, and default methods can only call other interface methods. An abstract class describes a partial implementation: it can hold fields, enforce construction rules, offer protected helpers, and share state across subclasses. A class can implement many interfaces but extend only one class. A good design: expose behaviour as an interface (maybe with defaults), and optionally supply an abstract skeleton class that implements it, like List and AbstractList in the JDK. Defaults are best for evolving old interfaces and for small convenience methods, not for building a deep hierarchy of behaviour.

Real-life scenarios

Each scenario is answered as: the situation, what to check first, the steps, and how to prevent it next time.

A report built with a parallel stream sometimes has missing rows and once threw ArrayIndexOutOfBoundsException. What happened? Intermediate

What the interviewer is testing: thread-safety of side effects in streams.

Situation: the code does orders.parallelStream().filter(...).forEach(o -> result.add(o)), where result is a plain ArrayList. The failure is random, so tests pass most of the time.

Check first: search the pipeline for any lambda that writes to an outside variable: a list, a map, a counter, a field. Check whether the stream is parallel.

Steps: ArrayList.add is not thread-safe: two threads can write to the same slot (a lost row) or resize while another writes (the exception). Replace the side effect with a collector: .collect(toList()) or .toList(), which gives each thread its own container and merges them safely. Add a regression test with a large input run several times.

Prevent: a team rule that stream lambdas do not mutate outside state; code review checks for forEach that adds to a collection; static analysis rules (Sonar has one) for this pattern.

After someone added parallelStream() to a service call loop, the whole app slowed down and other endpoints started timing out. Why? Senior

What the interviewer is testing: the common ForkJoinPool is shared and sized for CPU work.

Situation: a method calls a remote pricing service for every item using items.parallelStream().map(client::price). In testing it was faster. In production under load, latency of unrelated features rose.

Check first: thread dump: how many ForkJoinPool.commonPool-worker threads are blocked in socket reads? Check the container CPU limit, because the pool is about cores - 1, perhaps just 1 or 3 threads. Check whether other code also uses the common pool (other parallel streams, CompletableFuture.supplyAsync with no executor).

Steps: the blocking I/O calls occupy the few common-pool workers, so everything else that needs the pool queues up. Remove parallel(). If you really need concurrent calls, use a dedicated bounded executor (or virtual threads on Java 21 with a semaphore to limit calls to the remote service), and set timeouts. Check the concurrency page for the executor options.

Prevent: a rule that parallel streams are for CPU-bound work on large in-memory data, backed by a benchmark; no I/O inside them; load tests that include a concurrent mix of endpoints.

A job hangs forever. The thread dump shows common-pool workers all waiting inside a parallel stream. Is it a deadlock? Senior

What the interviewer is testing: pool starvation and lock misuse inside parallel tasks.

Situation: a parallel forEach body takes a lock (synchronized on a shared object) and also calls future.join() on a CompletableFuture that was submitted to the same common pool. All workers are waiting for results that need a free worker.

Check first: take a thread dump (jcmd PID Thread.print or jstack) and look for workers blocked on the same monitor, or parked in join/get. Look for a lock held by the thread that called the stream (the main thread also helps run tasks).

Steps: it is pool starvation, a kind of deadlock: tasks wait for other tasks that can never start. Remove the blocking dependency: do not wait for async tasks inside a parallel stream, do not hold locks across stream tasks, run the async work on a separate executor, or make the stream sequential. Break the circular wait, and add timeouts to every get.

Prevent: avoid parallel streams for anything that blocks or locks; use dedicated executors for async work; deadlock detection in thread dumps during load tests.

Production logs show NoSuchElementException: No value present and NullPointerException from code that "uses Optional everywhere". Find the misuse. Intermediate

What the interviewer is testing: Optional anti-patterns in real code.

Situation: a service has repo.findByEmail(e).get().getAddress().getCity() and a method that returns null for an Optional return type.

Check first: grep for .get() on Optionals, for methods returning Optional that can return null, and for Optional parameters and fields. Read the stack trace to find which call was empty.

Steps: replace get() with orElseThrow(() -> new UserNotFoundException(e)) so the failure has a clear message and a proper HTTP status. Chain with map and flatMap for nested values. Fix the method that returns null to return Optional.empty(). Use orElseGet for expensive defaults. Remove Optional from parameters and fields.

Prevent: lint rules against Optional.get() and against null returns in Optional methods; a convention: Optional only as a return type.

Every request creates a duplicate "default" row in the database even though the user exists. Why? Intermediate

What the interviewer is testing: eager evaluation of orElse arguments.

Situation: code reads repo.find(id).orElse(repo.save(new Settings(id))). The inner save runs on every call, because Java evaluates arguments before the call.

Check first: look for method calls with side effects (save, send, log, network) inside orElse(...). Check the database for duplicate rows with the same defaults.

Steps: change to orElseGet(() -> repo.save(new Settings(id))), which runs only when empty. Clean up duplicates with a script, and add a unique constraint so the data layer protects itself. Add a test that counts saves when the value exists.

Prevent: the rule "constants in orElse, everything else in orElseGet"; a static check; unique constraints on natural keys.

A nightly job scheduled for 02:30 local time did not run once a year and ran twice in autumn. Explain and fix. Senior

What the interviewer is testing: DST gap and overlap, and the right storage types.

Situation: the job computes the next run with LocalDateTime plus 24 hours and stores local times with no zone. On the spring change day, 02:30 does not exist. In autumn, 01:30 happens twice.

Check first: what time zone does the server JVM use (user.timezone), what type is stored (LocalDateTime versus Instant), and how "next run" is computed (add hours or add days).

Steps: decide what the business wants. For "every 24 hours exactly", schedule in UTC using Instant and Duration; DST is irrelevant. For "every day at local 02:30", use ZonedDateTime with the business zone and add days (plusDays(1)), letting Java resolve gaps (moves forward) and overlaps (earlier offset). Or move the job to a time that never falls in a change window. Run the servers in UTC. Write tests that use Clock.fixed around the change dates for the zone, for example Europe/Berlin in late March and October.

Prevent: a team convention: persist Instant; LocalDateTime never crosses a service boundary; test DST dates; keep tzdata updated.

Invoices created on 30 December show next year's date on the PDF. What is wrong? Intermediate

What the interviewer is testing: the YYYY versus yyyy pattern letter trap.

Situation: the format string is dd-MM-YYYY. Uppercase Y is the week-based year, and the week containing 30 December 2024 belongs to week 1 of 2025 in many locales (ISO weeks).

Check first: grep all format patterns for Y. Reproduce with the exact date and the production locale.

Steps: change to yyyy. Add a unit test for 28 December to 4 January. Check other places with the same bug, such as logging formats and file names.

Prevent: use predefined formatters (ISO_LOCAL_DATE) where possible; a shared constants class for patterns; tests at year boundaries every December.

An endpoint that worked for months now returns 500 with "Duplicate key" IllegalStateException. What do you do? Intermediate

What the interviewer is testing: toMap assumptions, and handling data you do not control.

Situation: users.stream().collect(toMap(User::email, Function.identity())). A new import created two users with the same email in different case, or a legacy duplicate appeared. The message names the key and both values.

Check first: read the exception message (it prints the duplicate key and both values), query the data for duplicates, and decide whether duplicates are valid.

Steps: short term: add a merge function, choosing the rule explicitly (keep the newest by updatedAt, or keep the first), and normalise the key (toLowerCase). If duplicates mean a data bug, fix the data and add a unique constraint, and log a warning when the merge function runs. If you need all values, use groupingBy instead.

Prevent: always ask "can the key repeat?" when writing toMap; prefer the three-argument form for external data; database constraints.

A loop starts tasks with lambdas, and they all print the same value or a compile error says the variable must be effectively final. How do you reason about it? Basic

What the interviewer is testing: variable capture and shared mutable state.

Situation: a developer wants a counter incremented inside a lambda, and works around the compiler error with a one-element array int[] count = {0} or a shared field, then runs it in parallel and gets wrong totals. Or tasks capture a mutable object that changes later, so they see the final state.

Check first: what is captured: a local (copy, fixed), a field (shared), or a mutable object (shared by reference)? Is the lambda run on another thread?

Steps: do not force mutation into a lambda. Use stream.count(), reduce, sum or a collector for totals. If you really need a thread-safe counter, use AtomicInteger or LongAdder. In a loop, copy the loop variable into a new final local per iteration, and pass immutable data (records) into tasks. A shared SimpleDateFormat captured by many tasks is another classic: replace it with the immutable DateTimeFormatter.

Prevent: pass values, not shared objects; prefer immutable captured data; review lambdas that touch fields.

A cached Stream field causes "stream has already been operated upon or closed" on the second request. Fix it. Basic

What the interviewer is testing: the one-shot nature of streams.

Situation: a class builds Stream<Rule> rules = loadRules().stream().filter(Rule::enabled) in the constructor and uses it per request. The first request works, the next fails.

Check first: find any stream stored in a field, returned from a cache, or used twice in one method.

Steps: store the result, not the stream: List<Rule> rules = loadRules().stream().filter(Rule::enabled).toList(), and call rules.stream() where needed. If building is costly and must stay lazy, keep a Supplier<Stream<Rule>>. For two results from one pass, use teeing.

After a "modernise collectors" refactor, a service throws UnsupportedOperationException on add. What changed? Intermediate

What the interviewer is testing: immutable results from newer APIs.

Situation: a bulk edit replaced collect(Collectors.toList()) with .toList(). Downstream code adds to or sorts the returned list in place. Stream.toList() returns an unmodifiable list. The same appears with List.of, Collectors.toUnmodifiableList, and Arrays.asList(...).add.

Check first: the stack trace shows the call to ImmutableCollections methods; find where the list was created and who mutates it.

After moving to Java 11, the app fails at startup with NoClassDefFoundError: javax/xml/bind/JAXBException. Senior

What the interviewer is testing: the removal of Java EE modules.

Situation: code or a library uses JAXB, JAX-WS, javax.annotation.PostConstruct or javax.activation. They were in the JDK through Java 8, deprecated in 9 and removed in 11.

Check first: run jdeps on the jars, read the missing class name, and check which library needs it (mvn dependency:tree).

The app starts on Java 11 with warnings but crashes on 17 with InaccessibleObjectException. What now? Senior

What the interviewer is testing: strong encapsulation and the right order of fixes.

Situation: startup logs on Java 11 said "WARNING: An illegal reflective access operation has occurred". On 17 the same code throws java.lang.reflect.InaccessibleObjectException: Unable to make field private final byte[] java.lang.String.value accessible.

Check first: the stack trace shows which library calls setAccessible. The warning on 11 names the package (for example java.base/java.lang).

After upgrading Spring Boot 2.7 to 3.x, the build fails with "package javax.servlet does not exist" and a third-party filter stops working. Senior

You enabled virtual threads on Java 21 and the database falls over, or throughput does not improve. Why? Senior

What the interviewer is testing: realistic expectations of virtual threads.

Situation: the web server now creates a virtual thread per request. With thousands of concurrent requests, the connection pool (say 20 connections) becomes the queue; requests wait on it, or without a pool limit the database gets thousands of connections. In another case latency stays the same because the work is CPU-bound, or because carrier threads are pinned inside synchronized blocks that do blocking I/O (Java 21 to 23).

Check first: the downstream limits (database pool, remote API rate limits), CPU usage, and pinning: run with -Djdk.tracePinnedThreads=full in Java 21 and look at the JFR event jdk.VirtualThreadPinned.

Steps: keep concurrency bounded with a Semaphore or a bounded pool in front of scarce resources. Replace synchronized around blocking calls with ReentrantLock (or upgrade to Java 24+ where that pinning is fixed). Replace pooled ThreadLocal caches that assume few threads. Do not pool virtual threads. For CPU-bound work keep a normal pool sized to cores.

Prevent: load test before the switch; set limits explicitly instead of relying on thread count as backpressure. See concurrency.

After moving from Java 11 to 21, non-English characters in exported files look different. Why? Senior

What the interviewer is testing: silent behaviour change: default charset.

Situation: code uses new FileWriter(path) or String.getBytes() without charset. On Java 11 on Windows the default was windows-1252 (or ASCII on a Linux container with POSIX locale). Since Java 18 (JEP 400), the default charset is UTF-8 on all platforms, so the files written earlier and files written now use different encodings.

Check first: which APIs omit charset; what Charset.defaultCharset() and file.encoding were in the old setup; how old files were encoded.

Steps: make charset explicit everywhere (StandardCharsets.UTF_8, Files.readString(path, UTF_8)); for legacy files read them with their real charset; decide one standard and convert. Prevent: a lint rule forbidding charset-less constructors; golden file tests with non-ASCII content.

A Java 8 service in Kubernetes is OOMKilled although -Xmx is "small". Upgrading to 17 changed it. Explain. Senior

What the interviewer is testing: JVM memory beyond heap, and container awareness.

Situation: old Java 8 (before 8u191) ignored the cgroup limit, so with no -Xmx it sized heap from the node's memory. Even with -Xmx set, total memory is heap plus Metaspace, thread stacks, code cache, direct buffers and GC structures, which can exceed the pod limit.

Check first: pod limit versus -Xmx; JVM version; -XX:+PrintFlagsFinal output for MaxHeapSize; Native Memory Tracking (-XX:NativeMemoryTracking=summary) for off-heap use.
