What happens when you type a URL

What happens when you type https://shop.example.com/cart in a browser and press Enter? Basic
  1. Parse and check caches. Browser splits scheme, host, path. It checks HSTS (forces https), the HTTP cache and any open connection to that host.
  2. DNS lookup. Browser cache, OS cache, then the recursive resolver (ISP or 8.8.8.8), which walks root, .com TLD and the authoritative server if it has no cached answer. Result: an IP (A or AAAA record).
  3. TCP handshake. SYN, SYN-ACK, ACK: 1 round trip (RTT). (HTTP/3 skips TCP and uses QUIC over UDP.)
  4. TLS handshake. TLS 1.3 takes 1 RTT (0 RTT on resumption): server presents certificate, both sides derive session keys.
  5. HTTP request. GET /cart goes over the encrypted channel, usually to a CDN or load balancer first, then a reverse proxy or API gateway, then an app server.
  6. Response and render. HTML comes back, browser parses it, discovers CSS/JS/images and fetches them (often over the same HTTP/2 connection), then renders.
Say: I would then add the production details: anycast or geo DNS picks a nearby edge, the CDN may answer from cache, the L7 load balancer terminates TLS and routes to a healthy backend, and connection reuse means repeat visits skip steps 2 to 4.
Where does the latency go on a cold first request, and how do you cut it? Intermediate

A cold request pays DNS (0 to 100+ ms), TCP (1 RTT), TLS (1 RTT on 1.3, 2 on 1.2), then the request itself (1 RTT plus server time). With a 100 ms RTT that is roughly 300 to 400 ms before the first byte of HTML.

  • Put content near users (CDN, multi-region) to shrink the RTT itself.
  • Reuse connections (keep-alive, HTTP/2 multiplexing) so later requests pay none of the setup.
  • TLS 1.3 and session resumption, OCSP stapling, HTTP/3 (QUIC merges transport and crypto handshakes into 1 RTT).
  • DNS: sensible TTLs, dns-prefetch and preconnect hints for third-party hosts.
  • Terminate TLS at an edge close to the user, then use a long-lived warm connection from edge to origin.
The same URL, but the site is behind a CDN and a load balancer. Draw the path. Intermediate

DNS (often CNAME to the CDN) decides which edge you reach. The edge serves cacheable content directly and forwards misses to the origin load balancer, which spreads requests across gateway or service instances.

DNS

What is DNS and what are the main record types? Basic

DNS is the distributed, hierarchical name-to-address database of the internet.

RecordMeaning
A / AAAAName to IPv4 / IPv6 address
CNAMEAlias to another name (cannot sit at the zone apex; vendors offer ALIAS/ANAME to work around)
NSWhich servers are authoritative for the zone

TXTFree text: SPF, domain verification

Walk through recursive DNS resolution. Who are the resolver, root, TLD and authoritative servers? Intermediate
  1. Your stub resolver asks the recursive resolver (ISP, corporate, or public like 1.1.1.1) for shop.example.com.
  2. If not cached, the resolver asks a root server, which replies "ask the .com servers".
  3. The TLD server for .com replies "example.com is served by these NS".
  4. The authoritative server for example.com returns the A record with a TTL.
  5. The resolver caches it for the TTL and answers the client.

Most lookups never reach steps 2 to 4 because the resolver already has the NS and A records cached.

How does TTL affect failover and what TTL would you choose? Intermediate

TTL (time to live) tells caches how long to keep an answer. Low TTL (30 to 60 s) means changes propagate quickly but resolvers query you more and lookups are slower more often. High TTL (hours) is cheap and fast but a failover change can take hours to be seen.

  • Use 30 to 60 s for records you may need to fail over; 5 min to 1 hour for stable ones.
  • Lower the TTL before a planned migration (at least one old-TTL ago), then restore it.
  • Some resolvers and client libraries ignore TTL (the JVM historically cached DNS indefinitely with a security manager; many apps pin resolved IPs). So DNS failover is never instant and never total.
Trap: saying "set TTL to 0 and failover is instant". Clients and intermediaries misbehave, and you create a huge query load on authoritative servers.
What are DNS routing policies: round robin, weighted, latency, geo, failover? Intermediate
  • Round robin: return several A records, clients pick one. Simple, no health awareness.
  • Weighted: 90/10 split, good for canary or gradual migration.
  • Latency-based: answer with the region that has lowest measured latency to the resolver.
  • Geo-based: answer by the resolver's country or region. Useful for data residency and localised content.
  • Failover: health checks on the primary; if it fails, answer with the secondary.

Caveat: the authoritative server sees the resolver's IP, not the user's, so geo decisions can be wrong (a user on a distant public resolver). EDNS Client Subnet partly fixes this.

DNS-based global load balancing vs anycast: what is the difference? Senior

DNS GSLB returns different IPs to different users; failover speed is bounded by TTL and resolver behaviour. Anycast announces the same IP from many locations via BGP; the network routes each user to the topologically nearest one, and if a site dies its route is withdrawn and traffic shifts in seconds, with no client change. Anycast works very well for UDP and short flows (DNS itself, CDNs); long TCP connections can break if routes shift mid-connection, which is why operators design for that. Large CDNs and DNS providers typically use anycast; many setups combine both.

Your DNS provider has an outage. What happens, and how do you defend? Senior

Everything that depends on cold lookups of your name fails even though your servers are healthy. A well-known example: the Dyn DDoS in October 2016 made many major sites unreachable for hours for users whose resolvers had no cached answer. Facebook's October 2021 outage also involved DNS: their authoritative name servers withdrew their BGP routes after a backbone configuration change, so the names stopped resolving (and internal tools relying on the same network were hit too).

  • Use two independent DNS providers, with NS records at both (multi-provider).
  • Keep reasonable TTLs so caches ride out short outages.
  • Make internal tooling and out-of-band access not depend on the same DNS and network you are fixing.
You must move a service to a new IP with no downtime. What is the plan? Intermediate
  1. Lower TTL to 60 s a day ahead (wait out the old TTL).
  2. Bring up the new endpoint and verify it directly.
  3. Shift with weighted records 5%, 25%, 100% while watching errors.
  4. Keep the old endpoint serving (or proxying) until traffic drains; clients with stale caches still arrive for a while.
  5. Raise TTL back afterwards.

TCP, UDP, HTTP and TLS

TCP vs UDP: when do you pick each? Basic
TCPUDP
ConnectionHandshake, statefulNone
DeliveryReliable, ordered, retransmitsBest effort, may drop or reorder
ControlFlow control and congestion controlNone built in
OverheadHigherLow
Typical useHTTP, databases, file transferDNS, live video/voice, games, QUIC

Pick UDP when a late packet is worthless (a voice sample 2 s late), or when you want to build your own reliability (QUIC). Otherwise TCP.

Explain the TCP handshake, and what head-of-line blocking is. Intermediate

Client sends SYN, server replies SYN-ACK, client sends ACK; then data flows. Closing uses FIN/ACK in each direction, and the closer may sit in TIME_WAIT for a while (can exhaust ports on busy clients that open and close many short connections, another reason to pool).

Head-of-line (HOL) blocking: TCP delivers bytes strictly in order. If one packet is lost, every later byte on that connection waits for the retransmit, even if it belongs to a different HTTP/2 stream. This is the core motivation for HTTP/3.

Compare HTTP/1.1, HTTP/2 and HTTP/3. Intermediate
HTTP/1.1HTTP/2HTTP/3
TransportTCPTCP (+TLS in practice)QUIC over UDP (TLS 1.3 built in)
FormatTextBinary framesBinary frames
ConcurrencyOne request at a time per connection; browsers open about 6 connections per hostMany multiplexed streams on one connectionSame, with independent streams

HTTP/2 also had server push, which has largely been abandoned in practice. HTTP/3 helps most on lossy mobile networks. Some corporate firewalls block UDP 443, so clients fall back to HTTP/2.

Why does HTTP/2 make "bundle everything into one file" and "domain sharding" less useful? Senior

Those were HTTP/1.1 workarounds for the one-request-per-connection limit. With HTTP/2 multiplexing, many small requests share one connection cheaply, and sharding across hosts hurts (more handshakes, no shared compression state, congestion windows start small on each). Still, extremely high request counts cost scheduling and server CPU, so moderate bundling remains reasonable.

Explain the TLS handshake in plain terms. Intermediate

TLS gives confidentiality, integrity and server authentication. In TLS 1.3:

  1. Client Hello: supported ciphers, a key share (its half of a Diffie-Hellman exchange), and SNI (the hostname wanted).
  2. Server Hello: picks the cipher, sends its key share, certificate chain and a signature proving it owns the private key. Both sides now derive the same session keys without ever sending the key.
  3. Client validates the chain up to a trusted CA, the hostname and expiry, then both switch to symmetric encryption (fast, e.g. AES-GCM).

Asymmetric crypto is used only to authenticate and agree on keys; bulk data uses symmetric crypto. Ephemeral keys give forward secrecy: stealing the server key later does not decrypt recorded traffic. TLS 1.2 needed 2 RTTs; 1.3 needs 1, and 0-RTT resumption exists but is replayable, so allow it only for idempotent requests.

Where do you terminate TLS, and what are the trade-offs? Intermediate
OptionProsCons
At the load balancer or edge (offload)Certs managed in one place, backends save CPU, L7 routing possibleTraffic is plaintext inside the network unless re-encrypted
Passthrough (L4 LB, backend terminates)End-to-end encryption, LB never sees dataNo L7 routing, certs on every backend
Re-encrypt (terminate, then new TLS to backend)L7 features and encrypted internal hopsDouble crypto cost, two cert sets

For zero-trust or compliance setups, use mTLS between services (often via a service mesh sidecar) so each side proves its identity.

A certificate expired in production and all calls fail. What is the lesson? Senior

Expired certificates are a classic cause of large outages (for example, Microsoft Teams in 2020 and many internal service-to-service failures). Prevention: automate issuance and renewal (ACME or an internal PKI), short-lived certs, monitor days-to-expiry with alerts well ahead, and test renewal paths. During an incident, check clock skew too, since a wrong clock looks like an expired or not-yet-valid cert.

What are keep-alive and connection pooling, and why do they matter? Basic

Keep-alive leaves a TCP (and TLS) connection open after a response so the next request reuses it. A connection pool is the client-side manager that holds a bounded set of such connections and hands them out.

Without reuse, each call pays TCP + TLS setup (2 to 3 RTTs) and burns ports in TIME_WAIT. With 1 ms inside a datacentre this is small, but across regions at 80 ms it triples latency. Pools also protect the server by capping concurrent connections.

How do you size and configure a connection pool, and what bugs happen? Senior
  • Size by Little's law: connections needed = request rate x average latency (100 rps x 0.05 s = 5 in flight, then add headroom). Too small queues requests; too large overloads the downstream (a database has limited connections, so total across all app instances matters).
  • Idle timeout mismatch: if the server or LB closes idle connections after 60 s and the client keeps them for 120 s, the client sends on a dead connection and gets a reset. Set client idle timeout lower than the server's, and enable retry on stale-connection errors for idempotent calls. (Known AWS ALB tip: keep backend keep-alive longer than the ALB idle timeout, which defaults to 60 s.)
  • Pool exhaustion: a slow downstream holds connections, the pool empties, callers wait, threads pile up. Use acquire timeouts and bulkheads.
  • DNS staleness: a long-lived pool keeps talking to old IPs; set max connection lifetime so it rebalances after deploys.
Users see random 502s right after a quiet period. Where do you look? Senior

Random failures on the first request after idle smell like the idle-timeout race above: the LB or proxy closed a connection that the client or upstream pool still believed open. Check the idle timeout at each hop (client, LB, proxy, app server), make each hop's timeout longer than the one in front of it on the caller side, and look for connection reset or "upstream prematurely closed" in logs.

Load balancing

What does a load balancer do and why do you need one? Basic

It presents one address and spreads requests over many backends. You get horizontal scaling, availability (dead backends are skipped), zero-downtime deploys (drain a node, replace it), and a place for TLS termination and rate limiting. Example: 10 stateless app servers behind one LB; losing one costs 10% capacity, not an outage.

L4 vs L7 load balancing: what is the difference and when do you pick each? Intermediate

Typical layered design: an L4 tier at the edge for scale and DDoS absorption, an L7 tier behind it for smart routing. Pick L4 for non-HTTP protocols or extreme throughput; L7 for microservice path routing.

Trap: with HTTP/2 or gRPC, an L4 balancer balances connections, and since one long-lived connection carries many requests, load becomes badly skewed. Use an L7 balancer (or client-side balancing) for gRPC.

How do health checks work and what makes them go wrong? Intermediate

Active checks: the LB probes (TCP connect or HTTP GET /health) every few seconds and marks a node unhealthy after N consecutive failures and healthy after M successes. Passive checks: the LB watches real traffic and ejects a node returning errors or timing out (outlier detection).

  • Shallow vs deep: a shallow check (process is up) misses a broken database link; a deep check that tests the DB can take every node out at once when the DB is slow, causing a full outage. Typical compromise: liveness (shallow, restart if dead) vs readiness (can serve traffic), and avoid failing readiness on shared dependencies without a panic threshold.
  • Panic mode: if too many backends look unhealthy, many LBs (Envoy, for example) route to all of them anyway rather than none.
  • Slow start: new nodes with cold caches should ramp up traffic.
  • Connection draining: on removal, finish in-flight requests before closing.
What are sticky sessions, how are they implemented, and why avoid them? Intermediate

Sticky (session affinity) routes one user to the same backend each time, via an LB-set cookie, source-IP hash, or a session id in the URL or header. It is used when the server keeps user state in local memory.

Problems: uneven load (one heavy user pins a node), the user loses state if that node dies or is scaled in, deploys are harder, and NAT'd offices behind one IP all hash to one node. Better: stateless servers with session data in Redis or a signed token (JWT), so any node can serve any request. Stickiness remains legit for websockets (the connection itself is sticky) and for cache locality.

Global vs local load balancing: how do they fit together? Senior

Global (GSLB) chooses the region or datacentre: DNS policies, anycast, or a global proxy like a cloud global LB. Local chooses the instance inside that region: L4/L7 LBs, or client-side/mesh balancing. Flow: user, DNS or anycast, nearest healthy region, regional LB, instance.

Design points: health-check regions and fail traffic over with capacity headroom (if region A dies and B is already 70% full, you cascade; plan N+1 regions); keep data locality in mind (failing over a user to a region that lacks their data); and ensure failover is tested regularly.

The load balancer is a single point of failure. How do you make it highly available? Senior
  • Active-passive pair sharing a virtual IP (VRRP/keepalived): standby takes the IP on failure. Simple, but the standby sits idle and failover takes seconds.
  • Active-active with several LB nodes behind DNS round robin, anycast/ECMP routing (routers spread flows across LB nodes by hash), or a cloud-managed LB that scales across zones.
  • Spread LB nodes over availability zones; share config via automation, not manual edits.
  • Large providers use a layered approach: ECMP spreads flows to many L4 nodes (consistent hashing so the same flow lands on the same node even as nodes change), which hand off to L7 proxies.
  • Plan for LB capacity: connection tables, TLS CPU, and bandwidth are the limits; also protect against SYN floods.
What is client-side load balancing and when would you use it over a central LB? Senior

The client (or a sidecar like Envoy in a service mesh) gets the list of instances from service discovery and picks one itself. It removes a hop and a central bottleneck, balances gRPC per request, and allows smarter policies. Costs: every client needs the logic and fresh instance lists, and library upgrades across many languages are painful (a reason meshes moved it into sidecars). Use central LBs at the edge and for simple setups; client-side or mesh for east-west internal traffic.

One backend is at 95% CPU while the other nine sit at 30%. Why, and what do you do? Senior

Likely causes: sticky sessions or hash-based routing with a hot key; long-lived connections (websocket, HTTP/2, gRPC) balanced at L4 so some nodes got the heavy ones; a mix of cheap and expensive requests with round robin; a slow node accumulating work; new node cold-start. Fixes: least-connections or power-of-two-choices, L7 per-request balancing, remove stickiness, set max connection age so clients rebalance, add slow start, and check that one tenant is not the hot key (then shard or rate-limit that tenant).

How do you deploy with zero downtime behind a load balancer? Intermediate

Rolling, blue-green or canary, all relying on the LB: start new instances, wait until readiness passes, add to the pool (slow start), then mark an old instance as draining (no new requests, in-flight ones finish up to a drain timeout), then terminate. Ensure the app handles SIGTERM by finishing requests, and that DB schema changes are backward compatible so old and new versions coexist.

Proxies, API gateway and CDN

Forward proxy vs reverse proxy? Basic

A forward proxy sits in front of clients and speaks for them to the internet: corporate egress filtering, anonymity, caching, VPN-like access. The server sees the proxy, not the client. A reverse proxy sits in front of servers and speaks for them: the client thinks it talks to the real site. It provides load balancing, TLS termination, caching, compression, WAF, and hides internal topology. NGINX, HAProxy and Envoy are commonly used in the reverse role. A load balancer is essentially a reverse proxy focused on distribution.

What is an API gateway, and how is it different from a load balancer or reverse proxy? Intermediate

An API gateway is the single entry point for API clients and handles cross-cutting concerns so each service does not have to: authentication and authorisation, rate limiting and quotas, request routing, protocol translation (REST to gRPC), request/response transformation, API key management, usage metering, caching, observability, and sometimes aggregation of several backend calls.

A load balancer focuses on spreading traffic and health. A reverse proxy is the generic building block. A gateway is a reverse proxy with API-management features and awareness of consumers and policies. In practice the pieces overlap (Envoy-based gateways, Kong, cloud API gateways).

Risks: it is a critical path and a potential bottleneck/SPOF (run it replicated), it can become a "god" layer full of business logic (keep it thin), and it adds a hop of latency.

What is the Backend for Frontend (BFF) pattern and when is it useful? Senior

A BFF is a gateway-like service tailored per client type (mobile, web, partner). Mobile may need one aggregated, small payload to save round trips on a slow network; web wants something else. Each BFF is owned by the client team, avoids a one-size-fits-all API, and reduces over-fetching. The cost is more services to maintain and some duplicated logic. GraphQL is an alternative way to let each client shape responses.

What is a CDN and what problem does it solve? Basic

A content delivery network is a globally distributed set of edge servers that cache and serve content near users. It cuts latency (shorter distance), offloads the origin (a viral image is served once from origin, millions of times from the edge), absorbs DDoS traffic, and terminates TLS close to the user. It suits static assets (images, JS, video segments) and increasingly cacheable API responses and dynamic acceleration (persistent optimised connections to origin).

CDN push vs pull: what is the difference? Intermediate
Pull (origin pull)Push
HowEdge fetches from origin on first miss and caches by TTLYou upload content to the CDN ahead of time
ProsSimple, only popular content is cachedNo first-request miss, full control, origin may be offline
ConsFirst user per edge pays the miss; stampede on cold startYou manage uploads and storage; unused content costs space

Pull is the default. Many CDNs add a mid-tier "origin shield" so misses from many edges collapse into one request to the origin, and request coalescing so concurrent misses for one object trigger one fetch.

How do you update content that is cached on a CDN (invalidation)? Intermediate
  1. Versioned URLs (best): app.3f9c1.js or ?v=42. New content gets a new URL, so there is nothing to invalidate; set long Cache-Control: max-age=31536000, immutable.
  2. TTL expiry: short TTL for things that change (max-age=60), plus stale-while-revalidate so users never wait on refresh.
  3. Explicit purge: API call to purge a path, a wildcard or a surrogate key/tag (purge all pages tagged "product-42"). Works, but propagation takes seconds to minutes and is rate-limited or billed by some vendors.
  4. Conditional requests: ETag / Last-Modified so revalidation returns 304 with no body.
Trap: caching personalised responses. Always set Cache-Control: private or no-store for per-user data, and use Vary carefully (Vary: Cookie makes the cache nearly useless). A famously damaging class of bug is a CDN serving one user's page to another because auth responses were cached.
Which HTTP caching headers matter? Intermediate
  • Cache-Control: max-age=N browser and shared caches; s-maxage for shared caches (CDN) only; public/private; no-cache (store but revalidate before use); no-store (never store).
  • ETag and If-None-Match; Last-Modified and If-Modified-Since: revalidation returns 304 Not Modified.
  • Vary: which request headers form part of the cache key (Accept-Encoding, Accept-Language).
  • stale-while-revalidate, stale-if-error: serve stale while refreshing or when origin is down.
What can you do at the edge besides caching? Senior

Edge compute (Workers, Lambda@Edge style): A/B routing, auth token checks, redirects, header rewriting, image resizing and format conversion (WebP/AVIF by Accept header), geo-based content, bot filtering and WAF, rate limiting. Keep it small and stateless; edge functions have tight CPU/time limits and consistency is hard across hundreds of locations.

You push a new release at midnight, cache is cold and the origin falls over. Why, and how do you prevent it? Senior

A cold cache sends every request to the origin: a cache stampede (thundering herd). Mitigation: origin shield tier, request coalescing (collapse concurrent misses on one key), pre-warm hot objects (a push or scripted fetch), serve stale during revalidation, stagger purges rather than purging everything, and rate-limit/autoscale the origin. Versioned asset URLs mean you only ever warm new files, not everything.

API styles: REST, gRPC, GraphQL, real-time

What makes an API RESTful, and what are the HTTP method semantics? Basic

REST models resources (nouns identified by URLs) manipulated through uniform HTTP methods, stateless (each request has all it needs), with cacheable responses.

MethodMeaningSafeIdempotent
GETReadYesYes
POSTCreate / actionNoNo
PUTReplace whole resourceNoYes
PATCHPartial updateNoNot guaranteed
DELETERemoveNoYes

Idempotent means repeating the call has the same effect as doing it once (the response may differ, e.g. second DELETE returns 404).

What production problems come with GraphQL? Senior
  • N+1 queries: resolving a list of 50 posts then each author issues 50 DB calls; fix with batching (DataLoader pattern).
  • Expensive queries: a client can request deeply nested data. Use depth and complexity limits, persisted/allow-listed queries, timeouts.
  • Caching: no URL-per-resource, so HTTP/CDN caching is weak; use persisted queries via GET or application-level caching.
  • Errors: usually HTTP 200 with an errors array, which confuses monitoring; track errors in the body.
  • Authorisation must be applied per field, not just per endpoint.
Why is gRPC faster than JSON over REST, and what are its pitfalls? Intermediate

Protobuf is a compact binary format (smaller payloads, faster to parse than JSON), HTTP/2 gives multiplexing and header compression, and generated clients remove hand-written glue. It supports four modes: unary, server streaming, client streaming and bidirectional streaming. It has built-in deadlines that propagate across calls.

Pitfalls: L4 balancers skew load (see earlier question), browsers need gRPC-Web, you must evolve .proto files carefully (never reuse or renumber field tags; adding optional fields is safe), and binary payloads are harder to inspect.

What makes WebSockets hard to scale? Senior
  • Each connection is long-lived state on a node (memory plus a file descriptor); one box handles tens to hundreds of thousands with tuning, but deploys disconnect everyone, so clients must reconnect with jittered backoff to avoid a reconnect storm.
  • To message user B who is connected to a different node, you need a pub/sub backplane (Redis pub/sub, Kafka) or a connection registry mapping user to node.
  • Load balancer idle timeouts kill quiet sockets: send heartbeats (ping/pong).
  • Use least-connections balancing and drain gracefully.
  • Authenticate at connect, and re-validate tokens that expire mid-connection.
What are webhooks and how do you design them reliably? Intermediate

A webhook is an HTTP callback: when an event happens, the provider POSTs it to a URL the consumer registered (payment succeeded, repo pushed). It avoids consumers polling.

  • At-least-once delivery: retry with exponential backoff and jitter on non-2xx or timeout, for hours or days, then dead-letter. Consumers must therefore be idempotent: include a unique event id.
  • Security: sign the payload with an HMAC and a timestamp (receiver verifies and rejects old ones to stop replays); use HTTPS; protect against SSRF when users supply URLs (block internal IP ranges).
  • Ordering is not guaranteed; carry a version or timestamp, or let consumers fetch the current state by id.
  • Consumer side: respond 2xx fast, enqueue, process asynchronously; provide a replay or event log API for missed events.
  • Disable endpoints that fail for days and notify the owner.

API design

What are good practices for REST resource naming and URL design? Basic
  • Plural nouns, not verbs: GET /orders/42, not /getOrder?id=42.
  • Hierarchy for ownership, shallow: /users/7/orders; avoid nesting more than two levels (/orders/42 is enough once you have the id).
  • Methods carry the action; for non-CRUD actions use a sub-resource or custom verb: POST /orders/42/cancel.
  • Consistent casing, lowercase hyphenated paths, stable ids (opaque, not sequential if enumeration is a concern).
  • Correct status codes: 200 OK, 201 Created (with Location), 204 No Content, 400 bad input, 401 unauthenticated, 403 forbidden, 404 not found, 409 conflict, 422 validation, 429 too many requests, 5xx server fault.

Choose cursors for feeds, large or fast-changing data, and APIs consumed by machines. Offset is fine for small admin tables where page numbers matter. The cursor should be opaque (base64 of the sort key plus a tiebreaker such as id), so you can change internals. Sorting on a non-unique column (created_at) needs the tiebreaker, or rows get lost across pages. Return a next_cursor and put an upper bound on limit.

How do you design filtering, sorting and field selection? Intermediate

Use query parameters: ?status=open&created_after=2026-01-01&sort=-created_at&fields=id,title. Whitelist sortable and filterable fields (each must have an index, otherwise a client can issue slow scans), validate values, cap result size, and document defaults. Sparse field selection and expansion (?expand=customer) reduce over-fetching without needing GraphQL. For complex search, use a dedicated search endpoint or a search engine rather than bending the list endpoint.

How do you version an API, and how do you keep backward compatibility? Intermediate

Common schemes: URL path (/v2/orders, most visible and cache friendly), header or media type (Accept: application/vnd.x.v2+json, cleaner URLs), or date-based versions pinned per account (Stripe-style).

Non-breaking (safe) changes: adding optional fields, new endpoints, new optional parameters, new enum values only if clients are told to tolerate unknowns. Breaking: removing or renaming fields, changing types or meaning, making a field required, tightening validation, changing error formats.

  • Follow the robustness principle: clients ignore unknown fields; servers ignore unknown optional input.
  • Deprecate with notice: Deprecation and Sunset headers, docs, usage metrics per version, and direct contact with remaining heavy users before removal.
  • Avoid running many versions: translate old versions to the new core at the edge.
  • Use consumer-driven contract tests to detect breaks before release.
What are idempotency keys and how do you implement them? Senior

Problem: a client calls POST /payments, the connection times out, and it does not know whether the charge happened. Retrying may charge twice. Solution: the client sends a unique Idempotency-Key header (a UUID) per logical operation, and the server guarantees one effect per key.

  1. On request, atomically insert (key, request hash, status=in_progress) with a unique constraint.
  2. If the insert fails because the key exists: if completed, return the stored response; if in progress, return 409 (or wait); if the request body differs from the original, return an error (key reuse).
  3. Do the work, then store the response with the key in the same transaction as the business write where possible.
  4. Expire keys after a window (for example 24 hours).

The same technique makes webhook consumers and message consumers safe under at-least-once delivery. Naturally idempotent operations (PUT, DELETE) need no key.

Trap: checking "does key exist" then writing, as two steps without a lock or unique constraint. Two concurrent retries both pass the check.
How should an API report errors? Intermediate

Use the right HTTP status plus a consistent machine-readable body (for example RFC 7807 "problem details"):

HTTP/1.1 422 Unprocessable Entity
{ "type": "validation_error",
  "title": "Invalid request",
  "status": 422,
  "detail": "email must be a valid address",
  "errors": [{"field": "email", "code": "invalid_format"}],
  "request_id": "req_8f3a" }
  • 4xx means the client should fix the request; 5xx means the server failed and a retry may help. Do not return 200 with an error inside.
  • Stable error codes for programs, human messages for people; never leak stack traces or internals.
  • Include a request id for support and tracing.
  • Mark retryability: 429 and 503 carry Retry-After.
How do you do rate limiting at the API edge, and what do you tell clients? Intermediate

Enforce at the gateway or edge before requests reach services, keyed by API key, user, tenant or IP. Common algorithms:

  • Token bucket: a bucket refills at rate r up to burst size b; each request takes a token. Allows bursts, most popular.
  • Leaky bucket: requests drain at a fixed rate, smoothing output.
  • Fixed window counter: simple, but allows 2x burst at window boundaries.
  • Sliding window (log or counter): accurate, more memory or approximation.

With several gateway nodes, the counters live in a shared store (Redis with atomic Lua or INCR + expiry), or each node enforces a share of the limit locally for lower latency at some accuracy cost. Respond with 429, Retry-After, and headers showing limit and remaining (the RateLimit-* or vendor X-RateLimit-* conventions). Use tiers per plan, tighter limits on expensive endpoints, and separate protection of the system (load shedding) from fairness between tenants.

Trap: decide up front what happens if the limiter store is down. Fail open protects availability; fail closed protects the backend. Many choose fail open with local fallback limits.
How do you design bulk or batch APIs? Senior

Batching cuts round trips and per-request overhead (for example create 500 records in one call). Design choices:

  • Partial failure: return 207-style per-item results (item id, status, error) rather than all-or-nothing, unless atomicity is required, in which case say so and use a transaction.
  • Limits: cap batch size and payload bytes; reject oversized with 413.
  • Idempotency: a client-supplied id per item so a retry of the whole batch does not duplicate.
  • Large work: make it asynchronous: POST /imports returns 202 Accepted with a job URL; client polls GET /imports/9 or receives a webhook. Upload big files to object storage with a pre-signed URL rather than through the API.
  • Rate-limit by items, not just by requests, or one batch call bypasses your limits.
An operation takes 2 minutes. How should the API expose it? Intermediate

Do not hold the HTTP request open (gateways and browsers time out at 30 to 60 s). Return 202 Accepted with a Location of a status resource. The client polls it (with Retry-After) or gets a webhook/SSE notification. The status shows pending, running, succeeded (with result link) or failed (with error). Persist the job so a restart does not lose it.

How do APIs authenticate clients, briefly? Intermediate
  • API keys: simple identification for server-to-server; rotate, never put in URLs.
  • OAuth 2.0 bearer tokens: delegated access with scopes and expiry; short-lived access token plus refresh token.
  • JWT: signed, self-contained, validated at the gateway without a lookup; cannot be revoked before expiry unless you add a deny-list, so keep lifetimes short.
  • mTLS: both sides present certificates; common service to service.
  • Gateways validate once at the edge, then pass a trusted identity downstream; internal services must still authorise, not assume the edge did everything.
How do you make GET requests cacheable and conditional in your API? Intermediate

Return ETag (hash or version) and Cache-Control. Clients send If-None-Match and get 304 with no body if unchanged. For writes, use If-Match with the ETag as optimistic concurrency control: if someone else changed the resource, return 412 Precondition Failed instead of silently overwriting (lost update).

Availability math: if a request synchronously depends on 5 services each at 99.9%, the chain is about 99.5%. Moving non-critical steps behind a queue keeps the critical path short.

What patterns keep synchronous calls from taking the whole system down? Senior
  • Timeouts on every call (never infinite) and a deadline for the whole request.
  • Retries only for idempotent operations, with exponential backoff and jitter, a retry budget (for example at most 10% extra traffic) and only at one layer; otherwise retries multiply across layers (3 layers x 3 tries = 27x load on the bottom).
  • Circuit breaker: after repeated failures, fail fast for a cooldown, then probe (half-open), so a sick dependency gets room to recover.
  • Bulkheads: separate pools per dependency so one slow service cannot consume all threads.
  • Load shedding and backpressure: reject early when overloaded instead of queueing forever.
  • Fallbacks: cached or default data when optional dependencies fail.
How do services find each other (service discovery)? Intermediate

Instances register with a registry (Consul, etcd, Eureka, or Kubernetes Services with DNS) and heartbeat; callers look up healthy instances by name. Options: DNS names with a load balancer or cluster IP in front (simple), client-side lookup (library queries registry and balances), or a mesh sidecar that gets endpoints from a control plane. Watch for stale entries: use health checks and short TTLs.

What is a service mesh and is it worth it? Senior

A mesh puts a proxy sidecar (for example Envoy) next to every service, managed by a control plane. It gives mTLS, retries, timeouts, circuit breaking, traffic splitting and telemetry uniformly, without library code in each language. Costs: extra hop latency (typically a millisecond or so), resource overhead per pod, operational complexity and debugging difficulty. It pays off with many services and polyglot teams; for a handful of services, a shared client library is usually enough.

Service C becomes slow (not down). Why does that take down A and B, and how do you stop it? Senior

A slow dependency is worse than a dead one: a dead one fails fast, a slow one holds threads and connections. B's threads all wait on C, B's pool fills, B stops answering A, and A's threads fill: a cascading failure. Controls: tight timeouts, circuit breakers, bulkheads, bounded queues with shedding, and no retry storms (budget retries and use jitter). A well-known pattern in many AWS and other large-scale post-mortems is that retries from healthy callers keep an already struggling service from recovering.

Timeouts at the network level

What kinds of timeouts exist on a network call? Intermediate
  • Connect timeout: time to establish TCP (and TLS). Keep short (hundreds of ms to a few seconds), since a host that does not answer SYN is probably down.
  • Read (socket) timeout: maximum silence waiting for data after sending. Set from the callee's latency profile (a bit above p99).
  • Write timeout for sending large bodies.
  • Pool acquire timeout: waiting for a free connection from the pool.
  • Request or total deadline: end to end cap, including retries.
  • Idle timeout: how long LBs, proxies, NATs keep silent connections (AWS ALB defaults to 60 s; some NAT or firewalls drop idle flows after minutes).
Trap: many HTTP clients default to no timeout, or very long ones. Always set them explicitly.
How should timeouts be set across a call chain (deadline propagation)? Senior

Each downstream timeout must be smaller than the caller's, and ideally the remaining time budget is passed along (gRPC deadlines do this automatically; for HTTP use a header). Example: the user-facing request has 2 s. The gateway gives service A 1.8 s; A spends 100 ms, then calls B with 1.5 s left; and so on. If B is configured with 5 s while A gives up at 1.8 s, B keeps working for nobody, wasting capacity. Also compare to retries: total worst case is (timeout x attempts) plus backoff, and it must still fit in the deadline.

How do you pick a timeout value? Intermediate

Measure the callee's latency distribution. Set the timeout near p99 or p99.9 plus margin, so you cut off real outliers without failing normal slow requests. Too low causes false failures and retry storms; too high ties up resources while the dependency is sick. Revisit after changes, and alert on timeout rate.

Clients get 504 Gateway Timeout from the gateway, but the backend logs show the request succeeded. What happened? Senior

The gateway's upstream timeout (say 30 s) fired before the backend finished; the backend carried on and completed the work, but nobody was listening. Dangers: clients retry and the operation runs twice (hence idempotency keys), and the backend wastes work. Fixes: align timeouts (backend deadline below the gateway's), make long operations asynchronous (202 plus polling), have the backend honour cancellation when the client disconnects, and add idempotency for writes. Also distinguish 502 (bad response or connection reset from upstream), 503 (no healthy upstream or overloaded) and 504 (upstream too slow).

A brief database blip causes a long outage afterward. What may have gone wrong at the network layer? Senior

Likely a retry storm plus a reconnect stampede: when the DB came back, thousands of clients retried at once with no jitter and re-opened connections simultaneously, overloading it again (a metastable failure, where the system stays broken even after the trigger is gone). Mitigation: exponential backoff with full jitter, circuit breakers, connection pool limits and slow ramp-up, load shedding at the entry point, and the ability to temporarily reduce incoming traffic to let the system recover.
