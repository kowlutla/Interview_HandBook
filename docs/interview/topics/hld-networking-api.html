What happens when you type a URL

What happens when you type https://shop.example.com/cart in a browser and press Enter? Basic

In one line: the browser turns the name into an IP (DNS), opens a reliable connection (TCP), secures it (TLS), sends an HTTP request, and renders what comes back. Every step costs at least one network round trip (RTT), which is why caching and connection reuse matter so much.

Why interviewers ask it: it is a tour of the whole stack. A good answer shows you know where latency comes from and where each production component (CDN, load balancer, gateway) plugs in.

  1. Parse and check local caches. The browser splits https://shop.example.com/cart into scheme (https), host (shop.example.com) and path (/cart). Before touching the network it checks: HSTS (a remembered rule "this host is https only"), its HTTP cache (maybe /cart is cached and fresh, so no request at all), and whether it already has an open connection to this host.
  2. DNS lookup. The browser needs an IP address. It asks its own cache, then the OS cache, then the recursive resolver (your ISP, office network, or 8.8.8.8). If the resolver has no cached answer it walks root, then .com TLD, then the authoritative server for example.com. The answer is an A (IPv4) or AAAA (IPv6) record with a TTL.
  3. TCP handshake. SYN, SYN-ACK, ACK: 1 RTT before any data can flow. (HTTP/3 skips TCP and uses QUIC over UDP.)
  4. TLS handshake. The client says which hostname it wants (SNI), the server presents its certificate, both sides agree on session keys. TLS 1.3 costs 1 RTT (0 RTT when resuming a previous session); TLS 1.2 costs 2.
  5. HTTP request. GET /cart travels over the encrypted channel, usually hitting a CDN or load balancer first, then a reverse proxy or API gateway, then an app server, which may query a cache and a database.
  6. Response and render. HTML comes back. The browser parses it, discovers CSS, JS and images, and fetches them (typically multiplexed over the same HTTP/2 connection), builds the page and paints it.

Tiny timeline with a 100 ms RTT, cold start: DNS about 50 ms, TCP 100 ms, TLS 100 ms, request plus server time 100 ms + 30 ms. That is about 380 ms before the first byte arrives. A repeat visit with a warm connection pays only the last 130 ms.

Say this: I would then add the production details: anycast or geo DNS picks a nearby edge, the CDN may answer from cache without ever reaching the origin, the L7 load balancer terminates TLS and routes to a healthy backend, and connection reuse means repeat requests skip steps 2 to 4.

What an interviewer probes next: "which of those steps can you remove?" (answer: DNS via caching and preconnect, TCP and TLS via keep-alive and HTTP/3, the whole trip via CDN caching) and "what changes for an API client rather than a browser?" (no render step, but connection pooling matters even more).

Where does the latency go on a cold first request, and how do you cut it? Intermediate

In one line: a cold request is a stack of sequential round trips, so you cut latency by removing round trips (reuse, caching, HTTP/3) or by shortening each one (move content closer to the user).

Where the time goes. Nothing can be sent in parallel at the start because each step depends on the previous one: you cannot open a TCP connection without the IP, and you cannot negotiate TLS without the TCP connection.

StepCostAt 100 ms RTT
DNS (cache miss)0 to several RTTs to resolver and authoritative servers0 to 100+ ms
TCP handshake1 RTT100 ms
TLS 1.3 handshake1 RTT (TLS 1.2: 2)100 ms (200 ms)
HTTP request/response1 RTT + server time100 ms + server time

So a user 100 ms away sees roughly 300 to 400 ms before the first byte of HTML, and the server's own speed barely matters yet. That is why a fast app can still feel slow to far-away users: distance dominates.

How to cut it, by what each fix removes:

  • Shorten the RTT itself: CDN and multi-region deployments put an edge within about 10 to 30 ms of the user. This is the biggest single win.
  • Skip the setup: keep-alive and HTTP/2 multiplexing let later requests reuse the open, already-encrypted connection, so they pay none of steps 2 to 4.
  • Merge or shrink the handshakes: TLS 1.3 and session resumption, OCSP stapling (server includes the certificate-revocation proof so the client does not make an extra lookup), and HTTP/3 (QUIC combines transport and crypto setup into 1 RTT, 0 on resume).
  • Do the setup early: dns-prefetch and preconnect hints let the browser resolve and connect to third-party hosts (fonts, analytics) while it is still parsing HTML.
  • Split the distance: terminate TLS at an edge near the user (a short, cheap handshake), then use a long-lived warm connection from edge to origin, so the long-haul cost is paid once, not per user.

Pitfall: quoting server-side tuning (indexes, caching) as the answer to a cold-start latency question. It only helps the last slice.

The same URL, but the site is behind a CDN and a load balancer. Draw the path. Intermediate

In one line: the user's DNS lookup resolves to the CDN edge, the edge answers if it has a fresh copy, and only a miss continues through the load balancer, gateway and service to the database.

  1. DNS for shop.example.com returns a CNAME to the CDN, which returns an IP of an edge near the user (via geo DNS or anycast).
  2. CDN edge terminates TLS close to the user. For a static asset or cacheable response it answers immediately (hit). For anything else it forwards to the origin over a warm, long-lived connection (miss).
  3. L7 load balancer in front of the origin terminates (or re-encrypts) TLS, checks backend health, and spreads requests across gateway instances.
  4. API gateway authenticates the caller, rate-limits, and routes /cart to the cart service.
  5. Service and database do the real work. The response travels back the same path, and the CDN may store it if its Cache-Control headers allow.

Which requests stop where: images, JS, CSS and public pages usually stop at the edge (95%+ of bytes in many sites). Personalised calls like /cart for a logged-in user are normally not cacheable, so they pass through the whole chain; the CDN still helps with TLS termination and a fast edge-to-origin connection.

Pitfall: forgetting that the origin sees the CDN's IP, not the user's. The real client IP arrives in X-Forwarded-For (or the PROXY protocol), and you should only trust it from known proxy addresses.

DNS

What is DNS and what are the main record types? Basic

In one line: DNS is the internet's phone book: it maps human names like shop.example.com to the numbers machines need, and also stores a few other facts about a domain (mail servers, verification text).

Why it exists. IP addresses change and are hard to remember. A name gives you a stable handle: you can move the service to a new IP, add servers, or point at a CDN by changing a record, with no change on the client side. It is distributed and hierarchical (root, then .com, then example.com) so no single server holds everything, and heavily cached so most lookups never leave your local network.

A zone is a set of records. Each record has a name, a type, a value and a TTL (how long caches may keep it).

RecordMeaning
A / AAAAName to IPv4 / IPv6 address
CNAMEAlias to another name (cannot sit at the zone apex; vendors offer ALIAS/ANAME to work around)
NSWhich servers are authoritative for the zone
MXMail servers
TXTFree text: SPF, domain verification
SRVHost and port for a service (used by service discovery)
SOAZone metadata and negative-cache TTL

Example zone fragment:

shop.example.com.   300  A      203.0.113.10
www.example.com.    300  CNAME  shop.example.com.
example.com.       3600  MX 10  mail.example.com.
example.com.       3600  TXT    "v=spf1 include:mailer.example -all"
_grpc._tcp.cart     60   SRV    10 5 8443 cart-1.internal.

The CNAME rules people trip on: a CNAME says "this name is just another name for that one", so it cannot coexist with other records at the same name. At the zone apex (example.com itself) you must already have SOA and NS records, so a CNAME there is illegal. Providers add a non-standard ALIAS/ANAME record that behaves like a CNAME but is flattened to A records on the server side. Each CNAME hop also costs an extra lookup, so long CNAME chains slow cold resolution.

Pitfall: TXT and MX changes look instantaneous in a console but are still bound by old TTLs in caches around the world.

Walk through recursive DNS resolution. Who are the resolver, root, TLD and authoritative servers? Intermediate

In one line: your machine asks a recursive resolver, which does the legwork by asking root, then the TLD, then the authoritative server, and caches every answer by TTL.

Cast of characters:

  • Stub resolver: the tiny client in your OS or browser; it just forwards the question to the recursive resolver.
  • Recursive resolver: run by your ISP, company, or a public service (1.1.1.1, 8.8.8.8). It does the full lookup on your behalf and caches the results for everybody using it.
  • Root servers: know only who runs each top-level domain (.com, .org, .in). 13 named root addresses, each served by many anycast machines.
  • TLD servers: know which name servers are responsible for each domain under them (example.com).
  • Authoritative server: holds the real records for example.com. This is the only one that gives the final answer, and it is the server you control (via Route 53, Cloudflare, etc.).

Worked example (cold cache): the resolver asks root for shop.example.com; root answers "I do not know, but .com is served by these NS addresses". The resolver asks a .com server; it answers "example.com is served by ns1.dns-host.net". The resolver asks ns1.dns-host.net and gets A 203.0.113.10, TTL 300. It returns that to the client and keeps it for 300 s. The NS records for .com and example.com are cached too (their own TTLs are much longer, often a day or more), so the next lookup for api.example.com goes straight to the authoritative server.

That is why most lookups never reach steps 2 to 4: the popular parts of the hierarchy are always cached. It also explains why DNS outages for your authoritative servers only hurt as caches expire.

Pitfall / probe: "recursive vs iterative". The client-to-resolver leg is recursive (do all the work), while resolver-to-servers legs are iterative (each server only gives a referral).

How does TTL affect failover and what TTL would you choose? Intermediate

In one line: TTL is how long a cached DNS answer may be reused, so it directly sets how fast a change (like failover) reaches clients. Lower TTL means faster change but more DNS load; and no TTL makes failover instant.

What TTL does. Every DNS answer comes with a TTL in seconds. Resolvers and clients keep the answer until it expires and do not ask again. If you change a record at 12:00 with a 1 hour TTL, some users keep the old IP until 13:00, because their resolver cached it at 11:59.

TTLProsCons
Low (30 to 60 s)Changes and failover visible within about a minute or twoMore queries to your authoritative servers (cost, load); more cold lookups, so slightly slower pages; bigger outage if DNS provider fails (caches empty fast)
High (hours)Cheap, fast (mostly cached), rides out short DNS outagesA failover or migration takes hours to be seen

Practical rules:

  • Use 30 to 60 s for records you may need to flip quickly (a primary endpoint with a standby), 5 minutes to 1 hour for stable ones.
  • Before a planned migration, lower the TTL at least one old-TTL ahead of time. If the TTL is 24 h, lower it 24 h or more before the cut, because the old long-lived answers are still sitting in caches. After the cut is stable, raise it again.
  • Expect rule-breakers. Some resolvers enforce a minimum TTL, some home routers and clients cache longer, and many applications resolve once and keep the IP in a long-lived connection pool. The JVM, for instance, has its own cache controlled by networkaddress.cache.ttl whose default depends on whether a security manager is present, so a Java service may ignore your 60 s TTL unless configured.

Timeline example: the primary dies at 12:00:00, health check fails after 30 s, DNS flips at 12:00:30, TTL 60 s. Clients are healed between 12:00:30 and 12:01:30 if they respect TTL; long-lived pools only heal when their connection breaks and they re-resolve. So a realistic recovery is minutes, not seconds.

Trap: saying "set TTL to 0 and failover is instant". Many caches treat 0 as "use a default" or ignore it, clients still hold connections, and you create a huge query load on authoritative servers. For fast failover use anycast or a load balancer with health checks and a stable IP.
What are DNS routing policies: round robin, weighted, latency, geo, failover? Intermediate

In one line: the authoritative server can choose different answers for different queries, which turns DNS into a coarse traffic director: spread (round robin), split by percentage (weighted), send to nearest (latency or geo), or fail away from a sick endpoint (failover).

PolicyWhat the server returnsTypical use
Round robinAll A records, order rotated; client picks (usually the first)Cheap spreading over equal servers; no health awareness
WeightedAnswer chosen by weight, e.g. 90% old / 10% newCanary release, gradual migration, A/B between regions
Latency-basedThe region with the lowest measured latency to the resolver's networkMulti-region apps wanting fastest region
Geo-basedAnswer by the resolver's country or continentData residency (EU users to EU), localised content, licensing
FailoverPrimary while its health check passes, else secondaryActive-passive regions, disaster recovery

How health-aware policies work: the DNS provider runs probes against each endpoint from several places. If an endpoint fails N checks in a row it is removed from answers. This is only as fast as probe interval times N plus the TTL, so you should expect a minute or more.

The big caveat: DNS sees the resolver, not the user. The authoritative server receives the query from the user's recursive resolver, so its geo decision is made from the resolver's IP. A user in Mumbai using a public resolver whose egress is in Singapore gets "Singapore" answers. EDNS Client Subnet (ECS) lets the resolver pass a truncated prefix of the client's network so the authoritative side can decide more accurately, but not every resolver sends it (some privacy-focused ones deliberately do not).

Another limit: DNS cannot see load. Weighted records are static, so a hot region keeps receiving its share. For load-aware, per-request decisions use a load balancer behind the DNS name.

Pitfall: using round robin as "load balancing": a dead server stays in the rotation, and clients that cache one IP all hit the same box.

DNS-based global load balancing vs anycast: what is the difference? Senior

In one line: DNS GSLB changes the answer (different IP per user) and is limited by TTL; anycast keeps the same IP everywhere and lets internet routing (BGP) deliver each packet to the nearest announcing site, so failover is as fast as route withdrawal.

DNS-based global load balancing. Each region has its own IP. The DNS service returns the IP of the best region for the asker. To move users away from a failed region, DNS has to stop returning that IP, and then every cache must expire. Speed is bounded by TTL and by clients that ignore it.

Anycast. The same IP (say 198.51.100.1) is announced via BGP from many locations. Routers send each packet along the shortest path to whichever location announces it, so each user lands at a nearby site without any DNS trick. If a site dies or is drained, it withdraws its announcement; routers converge in seconds to tens of seconds and traffic shifts to the next-nearest site. The client is unaware: same IP, same connection target.

DNS GSLBAnycast
Failover speedTTL plus resolver behaviour (minutes)BGP convergence (seconds)
Awareness of userResolver IP only (ECS helps)Network topology (nearest in routing terms, not always geographic)
Load / health smartsWeighted, health-checkedCoarse: you steer by announcing or withdrawing
Long TCP flowsFine, IP stays fixed per clientRisky if routes shift mid-connection (packets land on a site without that connection's state)
Best forRegion choice, data residency, canariesDNS itself, CDNs, DDoS absorption, short flows

Why anycast works well for DNS and CDN: DNS queries are single UDP packets, so any site can answer. CDN edges terminate each connection locally and routes rarely flip during a short request. Operators handle the occasional mid-connection shift with consistent hashing across sites or with QUIC connection IDs.

What to say: large CDNs and DNS providers use anycast for the front door, then DNS or application logic for fine decisions (which region has the data), so the answer is usually "both".

Your DNS provider has an outage. What happens, and how do you defend? Senior

In one line: if your authoritative DNS is unreachable, nobody can find you even though your servers are fine. Defence is redundancy at the DNS layer, sensible TTLs, and not letting your recovery tools depend on the thing that broke.

What actually happens. Resolvers with a cached answer keep serving it until the TTL expires. Resolvers with no cached answer (new users, rarely queried names, caches that expired) get SERVFAIL or timeouts. So an outage ramps up as TTLs run out: small at first, then full once most caches have expired. Short TTLs make you fall over faster; long TTLs buy time but slow your own changes.

Real examples (as commonly reported).

  • October 2016, Dyn, a large DNS provider, was hit by a DDoS; customers that used only Dyn (many well-known sites) were unreachable for many users for hours.
  • October 2021, Facebook's DNS name servers withdrew their BGP routes after a backbone configuration change, so the names stopped resolving globally. Internal tooling that relied on the same network was also affected, which slowed recovery.

Defence, in order of value:

  1. Two independent DNS providers. Put NS records for both in the zone and keep the zone synced (tools like OctoDNS or Terraform). If one provider is attacked or fails, resolvers retry the other. Independent means different networks and companies, not two products of one vendor.
  2. Sensible TTLs. A few minutes to an hour on stable records gives caches time to ride out short incidents.
  3. Serve stale: some resolvers can return an expired answer when authoritative servers are down (RFC 8767). You can't control that, but it helps.
  4. Break the dependency loop. Out-of-band access (separate network, separate DNS or hard-coded IPs for the admin path, break-glass accounts) so you can fix DNS when DNS is broken.
  5. Protect and monitor: anycast and DDoS protection on the provider, alerts on NXDOMAIN or SERVFAIL rate and on authoritative response time from several places.

Probe: "can you avoid DNS altogether?" Mobile or internal clients can hold a fallback list of IPs, but you lose flexibility, so most keep DNS and add the redundancy above.

You must move a service to a new IP with no downtime. What is the plan? Intermediate

In one line: make the change reversible and gradual: lower the TTL early, run old and new side by side, shift traffic in steps, and keep the old endpoint alive until stragglers drain.

  1. Lower the TTL ahead of time. If the current TTL is 1 hour, lower it to 60 s at least 1 hour before the move, so by cutover every cache holds a short-lived answer. Doing it at the last minute changes nothing for caches that already hold the old record for another 59 minutes.
  2. Bring up the new endpoint and verify directly. Call it by IP or via a host-file override: health checks, TLS certificate valid for the hostname, data and config in place, capacity sized for 100% of traffic.
  3. Shift gradually with weighted records. For example 5% to new for 15 minutes while watching error rate and latency, then 25%, 50%, 100%. At any step, set the weight back to 0 to roll back; with a 60 s TTL that completes in a couple of minutes.
  4. Keep the old endpoint serving (or proxying to new) for a while. Clients that ignore TTL, long-lived connections, hard-coded IPs, and misbehaving resolvers keep arriving for hours or days. Watch old-endpoint traffic fall off before turning it down. If state is involved (sessions, a database), make sure both sides read and write the same data, or the split causes inconsistencies.
  5. Restore a normal TTL once the new endpoint is stable.

If the IP must not change for clients (partners whitelist your IP), use a load balancer or anycast IP in front, and change what is behind it. That removes DNS from the cutover entirely.

Pitfall: forgetting other things keyed to the old IP: firewall allow-lists, TLS certs, CDN origin settings, and the reverse DNS (PTR) for mail servers.

TCP, UDP, HTTP and TLS

TCP vs UDP: when do you pick each? Basic

In one line: TCP gives you a reliable, ordered byte stream and pays for it with a handshake, retransmissions and waiting; UDP just fires independent packets with no guarantees. Pick UDP when a late packet is worthless or when you want to build your own reliability.

The problem each solves. The internet underneath (IP) is best effort: packets can be lost, duplicated, reordered or delayed. Most applications (web pages, databases, file transfer) cannot tolerate a missing byte, so TCP hides the chaos. It numbers every byte, the receiver acknowledges what arrived, the sender retransmits what did not, and the receiver reassembles in order. It also does flow control (do not overrun the receiver) and congestion control (do not overload the network).

UDP adds almost nothing on top of IP: ports and a checksum. Each datagram stands alone. There is no connection, no retransmit, no ordering, no throttling.

TCPUDP
ConnectionHandshake, statefulNone
DeliveryReliable, ordered, retransmitsBest effort, may drop or reorder
ControlFlow control and congestion controlNone built in
OverheadHigherLow
Typical useHTTP, databases, file transferDNS, live video/voice, games, QUIC

Examples that make the choice clear.

  • Live voice call: a 20 ms audio chunk that arrives 2 seconds late is useless. With TCP, one lost packet would stall all later audio while it is retransmitted (head-of-line blocking), producing a freeze. With UDP you drop it and move on (conceal the gap).
  • DNS: one small question, one small answer. A TCP handshake would triple the cost, so DNS uses UDP and retries itself (it falls back to TCP for large answers).
  • Online games: the latest position matters, the old position does not.
  • QUIC / HTTP/3: built on UDP so it can implement reliability, multiple independent streams, and encryption in user space and evolve faster than the kernel's TCP.

Decision rule: default to TCP. Choose UDP when latency matters more than completeness, when you broadcast or multicast, or when you are deliberately building your own transport.

Pitfall: UDP needs the application to handle loss, duplicates, ordering, congestion and (for amplification attacks) source address spoofing; naive UDP services can be abused for DDoS reflection.

What are the network layers (OSI / TCP-IP), and what do "L4" and "L7" mean? Basic

In one line: networking is split into layers, each solving one problem and relying on the one below. "L4" means the transport layer (TCP/UDP, ports) and "L7" means the application layer (HTTP and friends).

Why layers. Without layers every application would need to know about cables, routing and retransmission. With layers, the web server only speaks HTTP and trusts everything below, and an engineer can swap Wi-Fi for fibre without touching the application.

Layer (OSI number)JobExampleAddressing unit
L7 ApplicationMeaning of the messagesHTTP, gRPC, DNS, SMTPURL, header, method
L6/L5 Presentation, sessionEncoding, encryption, sessions (in practice folded into L7 or TLS)TLS
L4 TransportDelivery between processes, reliability or notTCP, UDP, QUICPort
L3 NetworkRouting between networksIP, ICMPIP address
L2 Data linkDelivery on one local networkEthernet, Wi-FiMAC address
L1 PhysicalBits on the wireCable, radio

Encapsulation, one example. Your GET /cart (L7) is wrapped in a TCP segment with source and destination ports (L4), wrapped in an IP packet with source and destination addresses (L3), wrapped in an Ethernet frame (L2). Each router peels the outer layers it needs and forwards.

Why interviewers care. The layer a device works at defines what it can see and do. An L4 load balancer sees IPs and ports, so it can only balance whole connections. An L7 load balancer reads the HTTP request, so it can route by path or header, but it needs more CPU. Firewalls, NAT (L3/L4), WAF (L7) and gateways are all described this way.

Pitfall: the OSI model is a teaching model; the real internet follows the 4-layer TCP/IP model (link, internet, transport, application). Say that, and nobody will argue about where TLS sits (it does not map cleanly).

Explain the TCP handshake, and what head-of-line blocking is. Intermediate

In one line: TCP opens with a three-step handshake so both sides agree on starting sequence numbers, and its strict in-order delivery means one lost packet stalls everything behind it (head-of-line blocking).

The handshake, step by step.

  1. SYN: client says "I want to talk; my starting sequence number is x".
  2. SYN-ACK: server replies "OK; mine is y, and I expect x+1 next".
  3. ACK: client confirms "expecting y+1". Data can now flow (the client can even put data in this third packet).

That costs 1 RTT before the first byte. The numbers matter because TCP labels every byte: the receiver acknowledges "I have everything up to N", and the sender resends whatever was not acknowledged.

Closing. Each side sends FIN and gets an ACK, so it is a four-step teardown (either side may close first; a RST aborts immediately). The side that closes first sits in TIME_WAIT for about 1 to 2 minutes (kernel dependent) so late duplicate packets cannot be mistaken for a new connection. A client that opens and closes thousands of short connections per second to the same server can run out of local ports (about 28k to 64k ephemeral ports), seeing "cannot assign requested address". Fixes: connection pooling and keep-alive (the real fix), widening the port range, spreading over more server IPs.

Head-of-line blocking, with an example. TCP guarantees the app sees bytes strictly in order. Suppose packets 1 to 5 are sent and packet 2 is lost. Packets 3, 4, 5 arrive but the receiver cannot hand them to the application until 2 is retransmitted (which takes at least one RTT plus detection time). Everything behind packet 2 waits, even if packets 3 to 5 belong to a completely unrelated HTTP/2 stream on the same connection. HTTP/2 solved HOL at the HTTP level (many streams on one connection) but they all share one TCP byte stream, so a single loss still stalls all streams. HTTP/3 moves to QUIC where each stream has independent ordering, so a loss only delays its own stream.

Pitfall: do not claim "HTTP/2 removed head-of-line blocking"; it removed it at the HTTP layer only.

What are TCP flow control and congestion control, and why does a new connection start slow? Intermediate

In one line: flow control stops a fast sender from overwhelming a slow receiver; congestion control stops senders from overwhelming the network. Both limit how much unacknowledged data can be in flight, which is why a fresh connection starts slow and speeds up.

Flow control (receiver protection). In every ACK the receiver advertises a receive window: how many more bytes it has buffer space for. The sender never has more unacknowledged data in flight than that window. If the application reads slowly, the window shrinks toward zero and the sender pauses. Example: the receiver advertises 64 KB; the sender may send 64 KB without waiting for acknowledgements, then must wait.

Congestion control (network protection). The sender also keeps a congestion window (cwnd) and sends at most min(receive window, cwnd). It does not know the network capacity, so it probes:

  1. Slow start: cwnd begins small (commonly 10 packets, about 14 KB) and roughly doubles every RTT while ACKs return cleanly. Despite the name, growth is exponential.
  2. Congestion avoidance: after a threshold (or the first loss) growth becomes linear: add about one packet per RTT.
  3. On loss (timeout or duplicate ACKs, a sign that queues overflowed) cwnd is cut, e.g. halved, and the cycle continues. Modern algorithms differ: CUBIC (common default on Linux) grows by a cubic curve, BBR estimates bandwidth and RTT instead of reacting to loss.

Why it matters to system design.

  • A new connection needs several RTTs to reach full speed, so a short transfer on a fresh connection never reaches it. This is another reason to reuse connections (a pooled connection keeps its grown window) and to avoid domain sharding.
  • Throughput per connection is limited by window / RTT. With a 64 KB window and 100 ms RTT the cap is about 5 Mbit/s no matter how fat the pipe is, which is why long-distance transfers need window scaling, tuned buffers or multiple streams.
  • After an idle period some stacks reset cwnd (slow-start restart), so a bursty client can be slow on the first request after a pause.

Pitfall: confusing the two. Flow control is end-to-end and about the receiver's memory; congestion control is about shared network capacity and is inferred from loss or delay.

Compare HTTP/1.1, HTTP/2 and HTTP/3. Intermediate

In one line: HTTP/1.1 sends one request at a time per connection, HTTP/2 multiplexes many streams over one TCP connection but suffers TCP head-of-line blocking, and HTTP/3 runs the same ideas over QUIC (UDP) so streams are truly independent and connection setup is faster.

The story of why each exists.

  • HTTP/1.1: text based. A connection handles one request-response at a time (pipelining existed but was never reliably usable). So a page with 80 assets was fetched with about 6 parallel connections per host, and developers worked around the limit with bundling, sprites and domain sharding. Headers (cookies, user-agent) were resent in full each time.
  • HTTP/2: same semantics (methods, headers, status) but binary framing. Many request/response streams are interleaved on one connection, so 80 assets need one connection and one TLS handshake. HPACK compresses headers, which matters because repeated cookies dominate small requests. Remaining flaw: all streams ride one TCP stream, so a single lost packet freezes all of them.
  • HTTP/3: same semantics over QUIC, a transport built on UDP with TLS 1.3 inside. Each stream is delivered independently, so loss on one stream does not stall others. Setup is 1 RTT (transport and crypto together), 0 RTT on resumption. A connection is identified by a connection ID, not the IP:port tuple, so it survives a phone switching from Wi-Fi to cellular.

Why does HTTP/2 make "bundle everything into one file" and "domain sharding" less useful? Senior

In one line: bundling and domain sharding were tricks to get around HTTP/1.1's "one request per connection" limit; HTTP/2 removes that limit, so those tricks become neutral or harmful.

What the old tricks did. With HTTP/1.1 a browser opens about 6 connections per host, each carrying one request at a time. To load 60 small files you waited in line, so teams (1) bundled files into one big JS/CSS file and used image sprites, and (2) sharded domains (img1.cdn.com, img2.cdn.com) to get 6 connections per hostname, i.e. more parallelism.

Why they stop helping under HTTP/2.

  • Many streams share one connection, so 60 small requests are cheap. There is no queue to jump.
  • Sharding hurts: each extra hostname means another DNS lookup, TCP and TLS handshake, and a fresh TCP congestion window that starts small (slow start). You also split header-compression state across connections and defeat HTTP/2 prioritisation, which only works within a connection.
  • Bundling hurts caching: change one line in a 1 MB bundle and users re-download the whole thing. Many small files cache independently, so only the changed file is fetched. Large bundles also delay execution until the entire file arrives.

The nuance (what makes the answer senior). Do not swing to the opposite extreme: thousands of tiny requests still cost per-request header processing, scheduling and server CPU, and compression works better on larger files. The modern practice is moderate bundling (a handful of chunks split by route, with content-hashed filenames for long caching), and serving everything from one host. If you must support HTTP/1.1 clients (old proxies), a bit of bundling still helps them.

Explain the TLS handshake in plain terms. Intermediate

In one line: TLS lets the client and server agree on a secret key over an open network and prove the server is who it claims to be, then encrypt everything with fast symmetric crypto. In TLS 1.3 this takes one round trip.

What TLS provides. Three things: confidentiality (nobody on the path can read it), integrity (nobody can alter it undetected) and authentication (the server is really shop.example.com, not an impostor), proven with a certificate signed by a trusted Certificate Authority (CA).

The core trick: Diffie-Hellman key exchange. Each side picks a random private number and sends the other a derived public "key share". Combining my private number with your public share produces the same secret on both sides, yet an eavesdropper who sees both public shares cannot compute it. Colour-mixing is the classic analogy: mixing a secret colour into a public one is easy; un-mixing is not.

TLS 1.3 handshake, step by step:

  1. ClientHello: supported cipher suites, the client's key share, SNI (the hostname, so one IP can host many sites), and ALPN (which protocols it speaks, e.g. h2, http/1.1).
  2. ServerHello and the rest, in one flight: chosen cipher, the server's key share, then (already encrypted) its certificate chain and a signature over the handshake with its private key. That signature proves it owns the certificate. Both sides now derive the same session keys, which are never transmitted.
  3. Client verifies: certificate chain leads to a trusted CA, the name matches, it is not expired or revoked, and the signature checks out. It sends its Finished message; encrypted application data starts (the client's first request rides the same flight).

TLS 1.2 needed two round trips; 1.3 needs one. On a resumed session, 1.3 allows 0-RTT data (client sends the request with its first packet using a pre-shared key).

Key ideas to be able to state:

  • Asymmetric crypto (certificate signature, key agreement) is used only to authenticate and agree on a key; bulk data uses symmetric ciphers like AES-GCM or ChaCha20, which are thousands of times cheaper.
  • Forward secrecy: keys are ephemeral per session, so stealing the server's long-term private key later does not let an attacker decrypt traffic they recorded earlier.
  • 0-RTT is replayable: an attacker can resend the captured first flight. Allow it only for safe, idempotent requests (a GET), never for "transfer money".

Pitfall: mixing up the two "keys": the certificate's key pair proves identity; the session key encrypts data.

A certificate expired in production and all calls fail. What is the lesson? Senior

In one line: certificates have a hard expiry date, so certificate renewal must be automated and monitored; otherwise a quiet date on a calendar becomes a total outage.

Why it breaks everything. A TLS client refuses to talk to a server whose certificate is expired (or not yet valid, or for the wrong name). There is no graceful degradation, so every request fails at once, including service-to-service calls if internal certificates expire. Often there are many certs (edge, load balancer, internal mTLS, database, client certs, intermediate CAs) and the one forgotten is the one that expires. Reported examples include Microsoft Teams in February 2020 (an authentication certificate expired) and many internal incidents where an intermediate or root CA expired and cascaded.

Prevention checklist.

  1. Automate issue and renewal: ACME (the protocol behind Let's Encrypt and many cloud certificate managers) or an internal PKI such as Vault, cert-manager in Kubernetes, or a service mesh CA. No human calendar reminders.
  2. Short lifetimes: short-lived certs (days to a few months) force automation to work constantly, so a broken renewal is noticed early and a leaked key has limited value. Public CAs are moving to shorter maximum lifetimes.
  3. Monitor days-to-expiry from the outside (probe each endpoint), alert at 30, 14, 7 days, and inventory every certificate including intermediate CAs.
  4. Test the renewal path and the reload: renewal that writes a file but never makes the server reload it still expires. Consider a game day.

During the incident. Replace or renew the cert, reload every terminator, and clear caches. Also check clock skew: a server whose clock is wrong sees valid certs as expired or not yet valid, producing the same symptom. NTP drift, a VM restored from a snapshot, or a container with a wrong clock are classic causes.

Probe: "what about revocation?" Mention OCSP stapling and short-lived certs as the practical approach, since CRLs and live OCSP checks are unreliable.

What are keep-alive and connection pooling, and why do they matter? Basic

In one line: keep-alive keeps a TCP/TLS connection open after a response so the next request skips the handshake; a connection pool is the client-side manager that holds a bounded set of those open connections and lends them out.

Why it matters, with numbers. A brand new HTTPS connection costs TCP (1 RTT) plus TLS (1 to 2 RTT) before the first byte of the request is sent, so 2 to 3 RTTs of pure setup. Inside one datacentre (RTT about 1 ms) that is small, though it still burns CPU on the crypto. Across regions (RTT 80 ms) it is 160 to 240 ms added to every call, tripling the latency of a quick request. Also, closing and reopening floods the client with sockets in TIME_WAIT (possible port exhaustion).

How a pool works.

  1. The app asks the pool for a connection to host H.
  2. If an idle connection exists, it is handed over (no setup). Otherwise, if the pool is below its max size, a new one is opened. Otherwise the caller waits until one is returned or an acquire timeout fires.
  3. After the request completes, the connection returns to the pool and sits idle until reused or evicted (idle timeout or max lifetime).

The pool also acts as a safety valve: it caps how many concurrent connections a client can open to a downstream, protecting it from a stampede. HTTP/2 changes the shape: one connection carries many concurrent streams, so a pool needs only a few connections per host.

Pitfall: creating a new HTTP client per request (a very common bug) bypasses the pool entirely. Build one client, reuse it app-wide.

How do you size and configure a connection pool, and what bugs happen? Senior

In one line: size the pool from Little's law, make idle timeouts consistent across every hop, and guard against pool exhaustion and stale connections.

1. Sizing with Little's law. Connections in use on average = arrival rate x time each is held. If an instance makes 200 calls/s and each takes 50 ms: 200 x 0.05 = 10 connections busy on average. Add headroom for bursts and p99 latency (say 2x, so 20). Too small: callers queue for a free connection and latency rises. Too big: with 50 instances x 20 = 1000 connections hitting a database that supports 200 total, you overload the downstream. So compute the sum across all instances, not per instance (this is why databases use a proxy such as PgBouncer or RDS Proxy).

2. Idle-timeout mismatch (most common prod bug). Say a load balancer closes idle connections after 60 s, but the client pool keeps them for 120 s. At second 90 the client picks a connection that the LB silently closed and gets a reset or a 502 on its first write. Rule: the connection owner that is calling must drop idle connections sooner than the server side would. Set client idle timeout below the server's. For the opposite direction (an ALB calling your app), keep your app's keep-alive timeout longer than the ALB's idle timeout (60 s by default on AWS ALB), or your server closes a connection the ALB is about to reuse. Add a retry for idempotent requests that fail on a stale reused connection.

3. Pool exhaustion. A slow downstream holds connections longer (Little's law again: same rate x longer time = more connections). The pool empties, callers block waiting, threads pile up, and one slow dependency freezes the service. Guard with an acquire timeout (fail fast rather than wait forever), a separate pool per dependency (bulkhead), and a circuit breaker.

4. Staleness after deploys or DNS changes. A long-lived pool keeps talking to old IPs, so new instances stay idle while old ones are overloaded. Set a max connection lifetime (for example 5 to 30 minutes with jitter) so connections rotate and re-resolve DNS.

5. Validate on borrow or test idle ones (cheap ping) when the network between you and the server is flaky (NAT or firewalls drop idle flows silently).

Users see random 502s right after a quiet period. Where do you look? Senior

In one line: errors on the first request after a quiet period point to a stale connection: some hop closed an idle connection that another hop still believed was open, and the next request is sent into the void.

The race, spelled out. Suppose the load balancer's idle timeout is 60 s and your app server's keep-alive timeout is 30 s. After 30 s of silence the app closes the connection (sends FIN). The LB may not have processed that yet, or sees it a moment later. If a request arrives exactly in that window, the LB writes it on a connection that the app is closing, and the app answers with a reset. The LB reports 502 Bad Gateway to the user. Busy periods do not show it (connections are constantly reused, never idle); quiet periods do, which is why "random 502s after a quiet period" is a signature.

How to investigate.

  1. List the idle timeout at every hop: CDN, load balancer, reverse proxy (NGINX keepalive_timeout), app server (Tomcat, Node), client pool, and any NAT or firewall in between.
  2. Look in logs for "connection reset by peer", "upstream prematurely closed connection", or 502 with zero upstream response time.
  3. Correlate: do the failures happen roughly one idle-timeout after the last request?

Fix. Make the timeouts monotonic: the party that sends the request should give up on an idle connection first. The backend's keep-alive timeout must be longer than the proxy's idle timeout in front of it (e.g. ALB 60 s, app 75 s). Enable retry for idempotent requests on connection reset, enable TCP keepalive probes to stop NATs forgetting flows, and cap connection lifetime.

Do not forget the alternatives if the idle theory does not fit: a backend crashing and restarting (check restarts), a deploy without draining, or health checks marking nodes down and up.

Load balancing

What does a load balancer do and why do you need one? Basic

In one line: a load balancer (LB) gives clients one stable address and spreads their requests across many identical backends, so you can scale out, survive failures and deploy without downtime.

The problem. One server has a ceiling (CPU, memory, connections) and is a single point of failure. You can buy a bigger machine (vertical scaling) only up to a point. Running several servers (horizontal scaling) solves capacity but raises new questions: which one does the client call, and what if one is dead? The LB answers both.

What it does.

  1. Distributes each connection or request over healthy backends using an algorithm (round robin, least connections, ...).
  2. Health checks backends and stops sending to ones that fail, so a crashed node costs capacity, not an outage.
  3. Enables zero-downtime changes: mark a node as draining so it finishes in-flight work, replace it, put it back. Deploys, scaling in and out, and canaries all rely on this.
  4. Central place for cross-cutting features: TLS termination, connection limits, rate limiting, WAF, access logs and metrics.

Example. 10 stateless app servers, each good for 1000 req/s, behind one LB: total 10,000 req/s. One server dies; the health check notices in about 10 s and removes it. Capacity drops to 9,000 req/s (10 percent), not zero. Traffic that was in flight to the dead node fails and must be retried.

Important precondition: backends should be stateless (or share state through a DB or cache), otherwise "any server can handle any request" is false and you need sticky sessions.

Pitfall: the LB itself becomes a single point of failure and a possible bottleneck, so it must be redundant (see the HA question).

L4 vs L7 load balancing: what is the difference and when do you pick each? Intermediate

In one line: an L4 balancer forwards connections by looking only at IPs and ports (fast, protocol agnostic); an L7 balancer understands HTTP and can route each request by URL, host, header or cookie (smarter, costlier).

How each works.

  • L4: sees the TCP/UDP packet headers. It picks a backend when a connection starts (hash of the 5-tuple or similar) and then just relays the bytes for that connection. It never decrypts or parses HTTP. It can run in the kernel or in hardware and handle millions of connections.
  • L7: terminates the client connection (including TLS), reads each HTTP request, decides the backend for that request, and sends it over its own pooled connection to the backend. Because it has the full request it can do path routing (/api to service A, /img to service B), host-based routing, header or cookie rules, retries, response caching, compression, authentication, canary splits (5 percent to v2), and WAF.

How to think about each.

  • Round robin / weighted: server 1, 2, 3, 1, 2, 3. Zero state, perfect when every request costs about the same.   • Least connections: send to the backend with the fewest in-flight requests. Naturally adapts to slow requests (uploads, reports, websockets). Cost: needs live counts; with many LB nodes each only knows its own counts.
  • Least response time: combines connection count with observed latency, so a degraded node gets less traffic. Sensitive to noisy measurement.
  • Hash of IP or key (hash mod N): same key always goes to the same server: cheap stickiness and cache affinity. Problem: change N (add a server) and almost every key moves, wrecking caches. Fix: consistent hashing.
  • Consistent hashing: servers and keys are placed on a ring; a key goes to the next server clockwise. Adding or removing a server moves only about 1/N of keys. Used for cache tiers and sharded stateful backends (see the dedicated question).
  • Power of two choices: pick two backends at random and send to the less loaded. Surprisingly near-optimal and avoids the "herd effect" where many LBs all pick the same momentarily least-loaded node based on stale info. Used in large fleets and in proxies like Envoy and NGINX.
  • Random: trivially simple and, with many requests, close to even.

Decision rule: start with round robin or least connections. Add hashing only when you need locality (cache hit rate, per-user state). Verify with metrics: per-backend request count and CPU should be close; if one stands out, the algorithm or a hot key is the cause.

What is consistent hashing, and why does it beat "hash mod N"? Senior

In one line: consistent hashing maps keys and servers onto a ring so that adding or removing a server moves only about 1/N of the keys, instead of nearly all of them as with hash(key) mod N.

The problem with mod N. Suppose 4 cache servers and you pick the server by hash(key) % 4. It is cheap and spreads evenly. But go from 4 to 5 servers and almost every key maps to a different server (a key moves unless hash mod 4 equals hash mod 5, about 20 percent stay). Every cache entry is suddenly on the "wrong" server, hit rate collapses to near 0, and the database behind it is flooded. The same happens when a server dies.

How the ring works.

  1. Imagine a circle of hash values from 0 to 2^32-1.
  2. Hash each server's name onto the circle (e.g. A at 10, B at 40, C at 70, D at 90).
  3. To place a key, hash it onto the circle and walk clockwise to the first server. Key at 55 goes to C; key at 95 wraps around to A.

Now add server E at 60. Only keys between 40 and 60 (previously C's) move to E. Everything else stays. Remove B: only B's keys move to the next clockwise server C. So about 1/N of keys move per change.

Virtual nodes (vnodes). With only a few points on the ring, the arc lengths are uneven, so some servers get a lot more keys. Each server is therefore placed at many points (100 to several hundred "virtual nodes"). This evens the load, and when a server leaves, its keys spread over many neighbours rather than dumping on one. Heterogeneous servers get more vnodes for more share.

Where it is used. Cache clusters (memcached client libraries), sharded stores (Dynamo-style systems, Cassandra), CDN request routing, and load balancers that need affinity (Envoy's ring hash, Maglev hashing is a related table-based variant giving more even load and fast lookup).

Pitfalls. Hot keys still land on one node (hashing spreads keys, not popularity), so add replicas or local caches for very hot keys. Ring changes must be seen consistently by all clients, or two clients disagree about the owner. Replication places copies on the next few distinct servers clockwise.

How do health checks work and what makes them go wrong? Intermediate

In one line: health checks let the LB stop sending traffic to broken backends. The art is checking the right depth: too shallow misses real failures, too deep can take your whole fleet out when a shared dependency hiccups.

Two kinds.

  • Active: the LB probes each backend every few seconds (TCP connect, or HTTP GET /health expecting 200). It marks the node unhealthy after N consecutive failures (say 3) and healthy again after M successes (say 2). Detection time is roughly interval x N, so 5 s x 3 = 15 s of traffic still going to a dead node.
  • Passive (outlier detection): the LB watches real traffic. A node returning five 5xx in a row, or timing out, is ejected for a while. Faster to react and based on real behaviour, but needs traffic.

Use both: active catches idle failures, passive catches subtle ones.

Shallow vs deep checks. A shallow check (process answers) says nothing about the database link. A deep check that queries the database sounds smarter, but if the database slows down, every app node fails its check simultaneously and the LB removes all of them: the dependency's partial problem becomes a total outage. Common compromise: Kubernetes-style liveness (shallow: is the process alive, otherwise restart it) and readiness (can this node serve right now). Make readiness depend on local conditions (started, warmed up, not overloaded), not on shared downstream health, unless you have a fallback.

Other behaviours worth naming.

  • Panic mode: when more than a threshold (Envoy default about 50 percent) of backends look unhealthy, send to all of them anyway; routing to none guarantees failure, while routing to all may succeed partially.
  • Slow start: ramp a newly healthy node's share over 30 to 60 s while JIT and caches warm up.
  • Connection draining: when removing a node (deploy, scale in), stop new requests but let in-flight ones finish up to a timeout.
  • Flapping: a node that oscillates healthy/unhealthy; require several successes before re-adding and add hysteresis.
What are sticky sessions, how are they implemented, and why avoid them? Intermediate

In one line: sticky sessions pin each user to one backend. They are a workaround for servers that keep user state in local memory; the better fix is to make servers stateless.

Why people use them. A login session stored in server 3's memory means a request landing on server 5 looks logged out. Stickiness makes every request from that user go to server 3.

How it is implemented.

  • LB-issued cookie (most common): the LB sets e.g. AWSALB=server3, and later requests with it go to server 3. Works for L7 only.
  • Source IP hash: hash the client IP to pick the backend. Works at L4, but many users behind one NAT or corporate proxy all hash to the same node.
  • Application session id in a cookie, header or URL, hashed or looked up by the LB.

Why to avoid them.

  1. Uneven load: a heavy user or a big NAT'd office pins a node while others idle; autoscaling does not help the hot node.
  2. Failure loses state: node dies or is scaled in and every pinned user loses their session.
  3. Deploys are harder: draining takes long because sessions are tied to the node.
  4. Weakens the LB's job: least-connections and health decisions fight the pinning.

Better design: keep servers stateless. Put session data in a shared store (Redis, a database) keyed by a session id, or use a signed token (JWT) that carries the state so any node can verify and serve. Then plain round robin works and nodes are interchangeable.

When stickiness is legit: WebSocket connections (the connection itself is pinned for its life), cache locality (route a user to the node holding their warm cache, accepting a miss if the node changes), and temporary use during a migration of a legacy app.

Global vs local load balancing: how do they fit together? Senior

In one line: global load balancing picks which region serves a user; local load balancing picks which instance in that region. They are two tiers working together.

The two tiers.

  • Global (GSLB): decides between regions or datacentres (US-East, EU-West, Mumbai). Mechanisms: DNS policies (geo, latency, weighted, failover), anycast IPs, or a cloud global load balancer / global proxy that terminates the user connection at the nearest edge and forwards to the best region.
  • Local: inside the region, L4/L7 load balancers spread across instances in several availability zones, or client-side/mesh balancing for internal calls.

Request flow: user, then DNS or anycast, then nearest healthy region, then regional L7 LB, then an instance (in a healthy AZ), then the data store.

Design points that interviewers look for.

  1. Capacity headroom for failover. If region A dies and its traffic goes to B, B must absorb it. With two regions each at 70 percent, one failure sends B to 140 percent and you cascade into a second outage. Plan N+1: e.g. three regions each at about 60 to 65 percent so any two can carry the load, or autoscaling plus load shedding for the surge.
  2. Data locality. Sending a user to a different region is useless if their data lives elsewhere, or it adds cross-region latency on every query. Decide: replicate data (active-active, with its conflict problems), or home each user to a region and fail over with a replica promoted, or accept degraded read-only mode.
  3. Health checks at region level: check an end-to-end synthetic transaction, not only that the LB IP responds, from multiple vantage points, and avoid flip-flopping (hysteresis).
  4. Failover speed: DNS is TTL-bound; anycast and global proxies are faster. Decide acceptable RTO.
  5. Test it regularly (game days, evacuate a region on purpose); untested failover usually fails.
The load balancer is a single point of failure. How do you make it highly available? Senior

In one line: never run a single LB; run several, in different failure domains, and make the "front door" address survive any one of them dying.

Why it is a real risk. Every request goes through the LB, so if it dies, everything behind it is unreachable even though the backends are healthy.

Common designs.

  • Active-passive pair with a virtual IP (VRRP, keepalived). Two LBs; one holds the virtual IP and answers. They exchange heartbeats; if the active stops, the standby takes over the IP (and sends a gratuitous ARP so switches learn the new location). Simple, but half the hardware sits idle and failover takes seconds, during which connections are dropped unless state is synced.
  • Active-active: several LB nodes all serve. Ways to spread clients across them: DNS returning multiple IPs; anycast or ECMP (the upstream router hashes each flow to one of N LB nodes, so adding nodes adds capacity); or a managed cloud LB, which is itself a distributed fleet across availability zones (this is what AWS ALB/NLB or GCP's LB are doing for you).
  • Layered approach at large scale (Maglev, Katran style): routers use ECMP to spread flows over a fleet of L4 nodes; those use consistent hashing so a flow keeps landing on the same node even when nodes join or leave, and they forward to L7 proxies that do routing. Because the L4 layer is stateless-ish and replicated, any node can fail without losing most connections.

Operational checklist.

  • Spread LB nodes across availability zones, never put both in one rack or one AZ.
  • Configuration as code and automated rollout; a bad LB config pushed to all nodes is a classic whole-site outage, so roll out gradually.
  • Capacity: watch connection table size, TLS handshakes per second (CPU), bandwidth, and ephemeral ports towards backends; protect against SYN floods and other DDoS (SYN cookies, upstream scrubbing, rate limits).
  • Monitor the LB from outside (synthetic probes), not only its own metrics.

Pitfall: making the DNS or the VIP the new single point of failure; ask "what is the next layer up, and is that redundant too?"

What is client-side load balancing and when would you use it over a central LB? Senior

In one line: in client-side load balancing the caller itself picks which instance to send each request to, using a list from service discovery; there is no central balancer in the data path.

How it works. The client library (or a sidecar proxy such as Envoy in a service mesh) asks a registry (Consul, Eureka, Kubernetes endpoints, a mesh control plane) for the current healthy instances of "cart-service", caches the list, refreshes it as it changes, and applies its own algorithm (round robin, least requests, power of two choices) per request. It can also track failures and eject bad instances.

One backend is at 95% CPU while the other nine sit at 30%. Why, and what do you do? Senior

In one line: uneven load means the balancer is not actually spreading work, only requests or connections. Find what is pinning work to one node, then fix the pinning rather than just adding servers.

Likely causes, with how each shows up.

  1. Sticky sessions or hash routing with a hot key. One huge tenant or user maps to node 7. Check: do requests on the hot node share a key or cookie?
  2. Long-lived connections balanced at L4. WebSocket, HTTP/2 or gRPC clients opened connections at startup (or after a deploy) and keep them; the first nodes up got most. Check: connection counts per node and age.
  3. Uniform algorithm, non-uniform requests. Round robin sends equal request counts, but some endpoints (export, search) cost 100x more. Check: CPU versus request count per node.
  4. A slow node accumulating work. Noisy neighbour, GC pauses, a bad disk: it processes slowly, so requests queue on it. With round robin it keeps receiving its full share.
  5. Cold start. A node that just joined and receives full traffic immediately while its JIT and caches are cold.
  6. Deploy imbalance: after a rolling deploy all clients reconnect to the first available node.

Fixes.

  • Switch to least connections or power-of-two-choices so slow or loaded nodes receive less.
  • Use an L7 balancer for per-request distribution of HTTP/2/gRPC; set a max connection age (say 5 minutes with jitter) so clients reconnect and rebalance.
  • Remove stickiness (externalise state), or shard the hot key (split a big tenant), or rate-limit it.
  • Add slow start for new nodes, outlier detection to eject slow ones, and separate pools for expensive endpoints.

First step in an interview: say you would look at per-node request rate, connection count, CPU and latency to see whether the skew is in requests, connections, or request cost, because the fix differs.

How do you deploy with zero downtime behind a load balancer? Intermediate

In one line: never kill a node that is serving; add the new one only when ready, stop sending new work to the old one, let in-flight work finish, then terminate. Compatibility of data and APIs between old and new versions makes it safe.

The rolling deploy, step by step.

  1. Start a new instance (version N+1). It is not in the pool yet.
  2. Wait for readiness: the readiness probe passes only once the app has started, loaded config and warmed up connections.
  3. Add to the pool with slow start (ramp 10 percent to 100 percent over a minute) so a cold node is not hit with full load.
  4. Drain an old instance: mark it "draining". The LB stops sending new requests but keeps existing connections open until they finish, up to a drain timeout (for example 30 s).
  5. Graceful shutdown: on SIGTERM the app stops accepting new connections, finishes in-flight requests, closes pools, then exits. If it exits immediately, drained or not, users see errors. Kubernetes tip: pods get SIGTERM and are removed from endpoints concurrently, so add a short preStop sleep so the LB stops sending before the app stops accepting.
  6. Repeat in small batches (maxSurge / maxUnavailable) while watching error rate; roll back automatically on a bad signal.

Strategies compared.

  • Rolling: replace gradually in place; cheapest, brief mixed-version period.
  • Blue-green: run a full second environment, then switch the LB (or DNS) to it; instant rollback by switching back; costs double capacity.
  • Canary: send 1 to 5 percent to the new version (weighted routing), compare metrics, then ramp. Best risk control.

The part people forget: compatibility. During the roll, both versions serve at once and share the database and queues. So schema changes must be backward compatible (expand, migrate, contract: add a nullable column first, deploy code that uses it, drop the old one later), and message formats and APIs must tolerate both versions.

Pitfall: long-lived connections (WebSocket, streams) make draining slow; set a max drain time and have clients reconnect with jitter.

Proxies, API gateway and CDN

Forward proxy vs reverse proxy? Basic

In one line: a forward proxy represents clients to the outside world; a reverse proxy represents servers to the outside world. Same machine type, opposite side of the conversation.

Forward proxy (in front of clients). Clients are configured to send their requests through it, and it makes the requests to the internet for them. The destination server sees the proxy's address, not the client's. Uses: corporate egress control and filtering (block sites, scan downloads), caching shared downloads, anonymity or geo-shifting (VPN-like), auditing, giving a private network a single controlled exit. Example: employees' browsers send all traffic through proxy.corp:3128.

Reverse proxy (in front of servers). Clients believe they talk directly to the site, but their requests arrive at the proxy, which forwards them to backend servers. The client sees only the proxy. Uses: load balancing, TLS termination, caching and compression, WAF and DDoS shielding, routing by path, hiding internal topology, and a single place for logs and rate limits. NGINX, HAProxy, Envoy and Apache are all commonly used this way.

Relationships to remember. A load balancer is essentially a reverse proxy focused on distribution; a CDN edge is a geographically distributed caching reverse proxy; an API gateway is a reverse proxy with API-management features. A transparent proxy intercepts traffic without client configuration.

Pitfall: behind a reverse proxy, the app sees the proxy's IP. Read the real client address from X-Forwarded-For or the PROXY protocol, and trust it only when the request came from your proxy.

What is an API gateway, and how is it different from a load balancer or reverse proxy? Intermediate

In one line: an API gateway is the single front door for API clients: a reverse proxy that also handles the cross-cutting API concerns (auth, rate limits, routing, metering) so each service does not re-implement them.

Why it exists. With 30 microservices, every team would otherwise implement authentication, throttling, logging and TLS themselves, inconsistently, and clients would need to know every service's address. The gateway centralises these.

What a gateway typically does.

  1. Route by path, host or header to the right service (/orders/* to the orders service) and handle versions.
  2. Authenticate and authorise: validate API keys, OAuth tokens or JWTs once at the edge, then pass a trusted identity (headers) downstream.
  3. Rate limit and quota per key, user or plan.
  4. Transform: protocol translation (REST to gRPC), header or payload changes, response shaping, sometimes aggregating several backend calls into one response.
  5. Resilience and observability: timeouts, retries, circuit breaking, request ids, metrics, access logs, usage billing.
  6. Cache responses where allowed.

What is the Backend for Frontend (BFF) pattern and when is it useful? Senior

In one line: a Backend for Frontend is a thin server layer built for one specific client type (mobile, web, partner), shaping and aggregating backend data exactly how that client needs it.

The problem. One general API serves everyone poorly. A mobile app on a slow network wants a single small payload (one round trip, few fields, compressed images). A desktop web app can afford several calls and wants more fields. A partner needs a stable, documented contract. If one API tries to satisfy all, it either bloats (over-fetching) or forces some clients into many round trips (under-fetching), and every client change needs backend team coordination.

How it works. Each client has its own BFF, usually owned by the same team that builds the client (so they can evolve it together). The BFF calls the downstream microservices, merges and trims the results, handles client-specific auth flows and caching, and returns the shape the UI needs.

Example. The mobile home screen needs the user's name, 3 recent orders and a cart count. Without a BFF the app makes three calls over 4G (3 x 200 ms). With a BFF it makes one call; the BFF calls the three services in parallel inside the datacentre (3 x 5 ms in parallel) and returns a 2 KB response.

Trade-offs.

  • Pro: smaller payloads, fewer round trips, client teams move independently, backend services stay clean and generic.
  • Con: more services to build, deploy and secure; logic duplicated across BFFs (keep business rules in the domain services, not in BFFs); a BFF owned by a different team than the client reintroduces coordination delays.

Alternatives. GraphQL lets each client ask for exactly the fields it needs through one endpoint (with its own operational costs). A gateway with aggregation features covers simple cases. Choose a BFF when clients differ a lot in needs or in network characteristics.

What is a CDN and what problem does it solve? Basic

In one line: a CDN is a worldwide network of caching servers (edges) that serve content from close to the user, so pages load faster and your origin handles far less traffic.

Why it exists. The speed of light sets a floor on latency: a user in Sydney fetching from a US server pays about 150 to 200 ms per round trip, and a page needing many round trips feels slow. And without caching, a viral image requested a million times hits your origin a million times.

How it works. You point your domain (DNS CNAME) at the CDN. The user's request reaches the nearest edge (chosen by anycast or DNS). If the edge has the object and it is still fresh (per Cache-Control), it responds immediately: a cache hit. If not, it fetches from your origin, stores the response, and serves it: a miss. The next user nearby gets a hit. The cache hit ratio is the key metric; a good static site is above 90 percent.

What it gives you.

  • Lower latency: shorter distance, and TLS terminated close to the user.
  • Origin offload: one origin fetch can serve millions of users, so you need far less origin capacity and bandwidth cost.
  • Resilience: absorbs traffic spikes and DDoS (huge distributed capacity, often with WAF and bot filtering), and with stale-if-error can keep serving if the origin is down.
  • Dynamic acceleration: even uncacheable requests benefit from the edge keeping warm, optimised connections to the origin.

What suits it. Static assets (images, JS, CSS, fonts), video segments, downloads, public pages and public API responses. Per-user content generally must not be cached at shared edges (or must be keyed per user carefully).

Cost and trade-offs. Invalidation is hard (see the next questions), stale content risks, vendor pricing per GB and per request, and an extra moving part to debug ("is this from the edge or the origin?" the Age and vendor cache-status headers tell you).

CDN push vs pull: what is the difference? Intermediate

In one line: in pull mode the CDN fetches content from your origin the first time it is asked and caches it; in push mode you upload content to the CDN in advance. Pull is the default.

Pull (origin pull). You configure the CDN with your origin URL. A request that misses at the edge makes the edge fetch from origin, store by TTL, and serve. Little to manage and only popular content takes up cache space. Downsides: the first user per edge location pays the miss (slower), and a cold cache after a release sends a burst of requests to the origin (stampede).

Push. You upload files to the CDN's storage (or the CDN's distribution) when you publish them. Edges serve them from there, so there is no first-request penalty and your origin can even be offline. Downsides: you own the upload and cleanup logic, content is stored whether anyone requests it or not, and you must remember to update/remove.

How do you update content that is cached on a CDN (invalidation)? Intermediate

In one line: the best invalidation is not needing it: give changed content a new URL. For things that must keep their URL, use a short TTL with stale-while-revalidate, and keep explicit purge for emergencies.

Why it is hard. A CDN may hold copies in hundreds of locations, each with its own timer. You cannot reach in and change all of them instantly, and browsers hold copies too, which the CDN cannot purge at all.

  1. Versioned (fingerprinted) URLs, the best option. Build tools put a content hash in the name: app.3f9c1.js, or you add ?v=42. New content means a new URL, so nothing has to be invalidated, and old and new coexist during a rollout. Serve these with Cache-Control: public, max-age=31536000, immutable (a year, never revalidate). Only the HTML that references them (short TTL) changes.
  2. Short TTL plus stale-while-revalidate for content that keeps its URL but changes (a product page): max-age=60, stale-while-revalidate=300. Users always get an instant response; the edge refreshes in the background. Accept up to a minute of staleness.
  3. Explicit purge via the CDN's API: purge one URL, a prefix or wildcard, or a surrogate key / cache tag (tag every page showing product-42 with Surrogate-Key: product-42; one call purges them all). Propagation takes seconds to minutes (some CDNs are near-instant), calls may be rate-limited or billed, and a mass purge empties the cache and triggers a stampede on the origin.
  4. Conditional revalidation: when TTL expires, the cache sends If-None-Match: "etag"; if unchanged the origin replies 304 with no body, saving bandwidth.
Trap: caching personalised responses. Responses with per-user data need Cache-Control: private or no-store; a shared cache must never store a response that included Set-Cookie or auth-dependent content under a shared key. Vary: Cookie makes the cache key include the cookie, so hit rate collapses to nearly zero. Real incidents have shown one user's page served to another because an authenticated response was cached.
Which HTTP caching headers matter? Intermediate

In one line: Cache-Control says who may cache and for how long; ETag and Last-Modified let caches check cheaply whether their copy is still valid; Vary says what makes two requests different.

Freshness: Cache-Control directives.

  • max-age=N: the response is fresh for N seconds, in browsers and shared caches alike. During that time no request is made at all.
  • s-maxage=N: same, but for shared caches (CDN, proxies) only; lets the CDN keep it for an hour while browsers keep it for a minute.
  • public / private: private means only the user's browser may store it (per-user data); public allows shared caches too.
  • no-cache: may be stored, but must be revalidated with the origin before each use. (Common confusion: it does not mean "do not cache".)
  • no-store: never store anywhere. Use for sensitive data.
  • immutable: will never change during its freshness lifetime; skip revalidation on reload.

Revalidation (cheap checks). The origin sends ETag: "v7" and/or Last-Modified. When the copy is stale the cache asks with If-None-Match: "v7" (or If-Modified-Since). If unchanged, the origin returns 304 Not Modified with no body: one small round trip instead of a full download.

Cache key: Vary. Vary: Accept-Encoding tells caches to store separate copies for gzip and brotli. Every header in Vary multiplies variants, so avoid Vary: Cookie or User-Agent on cacheable content.

Resilience extensions: stale-while-revalidate=N (serve stale instantly, refresh in the background), stale-if-error=N (serve stale if the origin returns errors or is down).

Example for a fingerprinted JS file: Cache-Control: public, max-age=31536000, immutable. For an API list: Cache-Control: public, s-maxage=30, stale-while-revalidate=60 plus an ETag. For an account page: Cache-Control: private, no-store.

What can you do at the edge besides caching? Senior

In one line: modern CDNs run your code at the edge, so you can make small decisions close to the user without a trip to the origin, as long as that code stays light, stateless and tolerant of eventual consistency.

What edge compute is. Platforms like Cloudflare Workers, Lambda@Edge, Fastly Compute or Akamai EdgeWorkers run short functions in the CDN's points of presence, on request and response events.

Typical uses.

  • Routing and experiments: A/B tests and feature flags decided at the edge (and cache keyed by variant), redirects and rewrites, canary routing to a different origin.
  • Security: validate JWTs or API keys and reject bad requests before they cost origin capacity; WAF rules, bot filtering, geo-blocking, rate limiting by IP.
  • Content adaptation: image resizing and format conversion (serve WebP or AVIF if the Accept header says so), device-specific variants, geo-localised content or currency.
  • Request shaping: normalise the cache key (drop tracking query parameters so hit rate rises), add or remove headers, and assemble pages from cached fragments.
  • Static plus dynamic: render an API response at the edge from cached data.

Constraints (and why). Functions have tight CPU time and memory limits (milliseconds, tens of MB), restricted runtimes, and cold starts in some platforms. State is the hard part: hundreds of locations cannot share strong consistency cheaply, so edge KV stores are eventually consistent and reads of a recently written value can be stale; strongly consistent state needs a single-region object or a coordination service. Also debugging and observability across many locations are harder, and vendor lock-in is real.

Rule of thumb: use the edge for decisions based on the request itself (headers, cookies, URL, geography) and cacheable data; use the origin for anything needing transactions or fresh shared state.

You push a new release at midnight, cache is cold and the origin falls over. Why, and how do you prevent it? Senior

In one line: a cold cache turns every request into an origin request at once (a cache stampede or thundering herd). Prevent it by warming the cache, collapsing duplicate misses, adding a shield tier, and releasing changes gradually.

What happens. Normally 95 percent of requests hit the CDN and the origin sees 5 percent. A release that purges everything (or a new region, new CDN config, changed cache key) sends 100 percent of traffic to the origin. If your origin is sized for 5 percent of peak, it is overwhelmed: slow responses cause timeouts, timeouts cause retries, and the edges cannot refill because the origin never completes. This is a metastable failure: the cache cannot warm because the origin is down, and the origin is down because the cache is cold.

Numbers example. 50,000 req/s at the edge with 95 percent hit ratio means the origin sees 2,500 req/s. After a full purge the first seconds send up to 50,000 req/s for the same hot objects.

Mitigations, in order of effect.

  1. Request coalescing at the edge: 1000 simultaneous requests for the same object produce one origin fetch; the others wait for it. This alone removes most duplicate load on hot items.
  2. Origin shield: a mid-tier cache means 200 edges ask the shield, and only the shield asks the origin.
  3. Prewarm: before cutover, a script fetches the top N URLs (from yesterday's logs) through the CDN, or push the new assets.
  4. Serve stale: stale-while-revalidate and stale-if-error let edges keep serving old content while refreshing.
  5. Versioned URLs: new asset names mean you warm only the new files, and you never mass-purge.
  6. Stagger and target purges: purge by tag or in waves rather than everything at once; do releases off-peak, region by region.
  7. Protect the origin: rate limit and load-shed (return 503 with Retry-After for low-priority requests), autoscale ahead of the release, and make sure timeouts and retries have backoff and jitter.

API styles: REST, gRPC, GraphQL, real-time

What makes an API RESTful, and what are the HTTP method semantics? Basic

In one line: a REST API exposes resources (things, named by URLs) and lets clients act on them with the standard HTTP methods; each request is self-contained (stateless) and responses say whether they can be cached.

The ideas behind it.

  • Resources, not actions: /orders/42 is a thing; the method says what to do to it.
  • Uniform interface: everyone uses the same small verb set, so tools, proxies and caches understand your API without custom knowledge.
  • Stateless: the server stores no client session between requests; each request carries identity (token) and context. That is what lets any server instance answer and makes horizontal scaling easy.
  • Cacheable: GET responses can be cached by browsers and CDNs, given the right headers.

Safe and idempotent, defined. Safe means it does not change server state (GET only), so crawlers and caches can call it freely. Idempotent means doing it N times leaves the same state as doing it once; this is what makes automatic retry safe.

Examples.

  • PUT /users/7 with the full user: calling it twice leaves the same user. Idempotent.
  • DELETE /orders/42: first call deletes (200/204), the second returns 404, but the server state is the same, so it is still idempotent (the response may differ, the effect does not).
  • POST /orders: twice creates two orders. Not idempotent, which is why payment APIs add an Idempotency-Key.
  • PATCH /users/7 {"age": 31} is idempotent as a "set" operation, but {"op":"increment","field":"age"} style patches are not; hence "not guaranteed".

Pitfalls. "REST" in everyday use usually means "JSON over HTTP with resource URLs"; strict REST (hypermedia links, HATEOAS) is rare. Do not use GET for actions with side effects (prefetchers and crawlers will trigger them), and do not tunnel everything through POST.

Compare REST, gRPC and GraphQL. When do you choose each? Intermediate

In one line: REST is the simple, universal default for public APIs; gRPC is a fast, strongly typed RPC for internal service-to-service calls; GraphQL lets each client ask for exactly the data shape it wants, useful in front of many backends.

What each really is.

  • REST: resources and HTTP methods, usually JSON. Every tool understands it (browsers, curl, CDNs, proxies).
  • gRPC: you define services and messages in a .proto file; code generators produce client and server stubs in many languages. Calls look like local function calls, travel as compact Protocol Buffers over HTTP/2, and support streaming and deadlines.
  • GraphQL: one endpoint and a typed schema; the client sends a query naming the fields it wants, including nested relations, and gets exactly that.

  • Internal east-west calls, latency or throughput matters, many languages, streaming: gRPC. The generated contract also stops teams from drifting apart.
  • Many different clients (mobile, web, TV) pulling overlapping data from many services, with frontend teams wanting independence: GraphQL, usually as a gateway or BFF over REST/gRPC backends.

What production problems come with GraphQL? Senior

In one line: GraphQL moves control to the client, which is powerful but pushes risks to the server: N+1 database calls, unbounded query cost, poor HTTP caching, confusing error semantics, and field-level authorisation.

  • N+1 queries. Query: posts { title author { name } }. A naive resolver fetches 50 posts (1 query), then runs one author query per post (50 queries) = 51 round trips. Fix: batching with the DataLoader pattern: collect all author ids requested during one request tick and issue a single WHERE id IN (...), then hand results back per resolver. Also cache per-request.
  • Expensive or abusive queries. Clients can nest arbitrarily (user { friends { friends { friends ... } } }) or request huge lists. Defences: query depth limits, complexity scoring (assign cost per field and list size, reject above budget), pagination required on lists, timeouts, and persisted queries (only pre-registered query ids allowed in production, so unknown queries are rejected).
  • Caching. Everything is usually POST to one URL, so CDNs and browsers cannot cache by URL. Mitigate with persisted queries over GET (cacheable), response caching keyed by query plus variables, and normalised client caches (Apollo, Relay).
  • Errors and monitoring. A GraphQL request commonly returns HTTP 200 with {"data":..., "errors":[...]} even on partial failure, so a dashboard based on HTTP status shows green during an outage. Track error counts in the body and instrument per operation name.
  • Authorisation. There is no endpoint-per-resource gate; the same type is reachable by many paths, so authorise at the field or object level in resolvers (or in a shared policy layer), not only at the entry.
  • Introspection and schema exposure: disable or restrict introspection in production for public APIs, and watch for batching attacks (many aliased operations in one request bypassing a naive request-count rate limit).

Say: I would still pick GraphQL when client diversity is the pain, but I budget for DataLoader, cost limits and operation-level observability from day one.

Why is gRPC faster than JSON over REST, and what are its pitfalls? Intermediate

In one line: gRPC is faster than JSON over REST mainly because of its compact binary format (Protocol Buffers), HTTP/2 multiplexing and generated code; its pitfalls are L4 load balancing skew, browser support, and careful schema evolution.

Why it is faster (and how much to claim).

  • Protobuf encoding: fields are sent as numbered tags with varint or fixed binary values, with no field names and no quotes or braces. {"id":1234,"name":"Ana"} (about 25 bytes of JSON) is around 10 bytes in protobuf, and parsing binary is cheaper than parsing text. Typically a few times smaller and faster than JSON, though real gains depend on payload shape.
  • HTTP/2: one long-lived connection with many multiplexed calls and header compression, so no per-call connection setup.
  • Generated clients and servers from the .proto: no hand-written serialisation, strong typing, same contract in every language.

Four call modes. Unary (request, response); server streaming (one request, a stream of responses, e.g. a feed); client streaming (stream of uploads, one response); bidirectional streaming (both sides send independently, e.g. chat). It also has deadlines that propagate: the caller sets "finish within 500 ms" and every downstream call inherits the remaining time.

Schema example:

message User { int64 id = 1; string name = 2; string email = 3; }
service Users { rpc GetUser(GetUserRequest) returns (User); }

Pitfalls.

  • Load balancing: a long-lived HTTP/2 connection makes L4 balancers pin all calls from a client to one backend; use L7/mesh balancing or client-side balancing with max connection age.
  • Browsers cannot speak raw gRPC (no access to HTTP/2 trailers and framing); use gRPC-Web through a proxy, or expose REST at the edge.
  • Schema evolution: field numbers are the identity on the wire. Never reuse or renumber a tag; mark removed ones reserved. Adding new optional fields is safe; changing a type is not. Old clients ignore unknown fields.
  • Debugging: binary payloads need tools (grpcurl, reflection), and caching at HTTP level is not available.
Compare polling, long polling, SSE and WebSockets. Intermediate

In one line: these are four ways to get fresh data to a client. Polling asks repeatedly, long polling asks and waits, SSE is a one-way server stream over HTTP, WebSocket is a two-way channel. Pick the simplest one that meets your direction and latency needs.

How each one behaves.

  • Short polling: the client calls GET /status every 5 seconds. Dead simple, works everywhere, but wasteful (most responses are "no change") and updates arrive up to 5 s late.
  • Long polling: the client sends a request, the server holds it open until there is data or a timeout (say 30 s), replies, and the client immediately asks again. Near real time, works through any proxy, but each wait ties up a connection and each update costs a full request cycle.
  • Server-Sent Events (SSE): one ordinary HTTP response that never ends; the server writes lines data: ... as events occur. The browser's EventSource reconnects automatically and sends Last-Event-ID so you can resume without gaps. Text only, one direction (server to client).
  • WebSocket: starts as an HTTP request with Upgrade: websocket; after a 101 response the connection switches to a separate framed protocol where either side sends messages any time, text or binary.

What makes WebSockets hard to scale? Senior

In one line: every WebSocket is a long-lived connection held in memory on one specific server, so scaling is about connection capacity, cross-node message delivery, reconnect storms and graceful deploys.

Why they are harder than normal HTTP. A normal request is short and any server can handle it. A WebSocket stays open for hours and the server holds its state (user, subscriptions, buffers). The fleet is no longer interchangeable.

  1. Connection capacity. Each connection consumes a file descriptor, kernel socket buffers and application memory (tens of KB). One tuned box (raised ulimit, epoll/NIO event loop, small buffers) can hold 100k+ idle connections, but CPU is spent on the active ones. Plan per-node connection limits and scale on connection count, not only CPU.
  2. Delivering to a user on another node. User A is connected to node 1, user B to node 3. When A sends B a message, node 1 does not hold B's socket. Two standard solutions: a pub/sub backplane (every node subscribes to channels in Redis pub/sub, NATS or Kafka and forwards to local sockets), or a connection registry (a store mapping userId to node id, so you route the message to the right node directly).
  3. Deploys and restarts disconnect everyone. Restarting a node drops, say, 100,000 clients, who all reconnect at once to the remaining nodes: a reconnect storm that can topple them. Clients must reconnect with exponential backoff plus random jitter, servers should drain gradually (close connections in batches with a "reconnect later" hint), and capacity should leave headroom for this surge.
  4. Idle timeouts. Load balancers, proxies and NATs kill silent connections (often 60 s). Send application pings or protocol ping/pong every 20 to 30 s, and detect dead peers (no pong, close).
  5. Load balancing. Use least-connections so new connections go to emptier nodes; the connection itself is pinned once open, so stickiness is not needed per message, though the initial HTTP upgrade must reach a node that can serve it.
  6. Auth and security. Authenticate at connect (token in the handshake), re-validate or refresh tokens that expire mid-connection, check the Origin header, and rate limit per-connection messages.
  7. Delivery guarantees. The socket gives no durable delivery: a message sent while the client is reconnecting is lost, so give messages ids and sequence numbers, and let the client resume from the last id (or fetch missed events via REST).
What are webhooks and how do you design them reliably? Intermediate

In one line: a webhook is the provider calling you: when something happens, it sends an HTTP POST to a URL you registered. Reliable webhook design is about at-least-once delivery, signatures, idempotent consumers and replay.

Why it exists. Without webhooks you poll ("did the payment succeed yet?" every few seconds), which is wasteful and slow. Webhooks push the event the moment it occurs: Stripe tells you a charge succeeded, GitHub tells you a push happened.

Flow: event occurs, provider stores it, a delivery worker POSTs JSON to the consumer's URL, consumer returns 2xx quickly to acknowledge, provider retries on anything else.

Designing the provider side.

  • At-least-once delivery. Retry on timeout or non-2xx with exponential backoff and jitter (for example 1 min, 5 min, 30 min, 2 h, up to a day or three), then move to a dead-letter store and alert. Because retries and network ambiguity mean duplicates, the payload carries a unique event id.
  • Security: sign the body with an HMAC using a shared secret, include a timestamp in the signed data, and have receivers reject old timestamps (stops replay). Use HTTPS only. Guard against SSRF: when users can register arbitrary URLs, a malicious user may point you at http://169.254.169.254/ or internal services; resolve the host, block private and link-local IP ranges, and disallow redirects to them.
  • Ordering is not guaranteed (retries reorder events). Include a version or timestamp, or send a thin event ("order 42 changed") that the consumer uses to fetch the current state.
  • Operations: per-endpoint health, auto-disable endpoints failing for days and notify the owner, a dashboard of delivery attempts, and a "resend" button.

Designing the consumer side.

  • Verify the signature, then respond 2xx immediately, put the event on a queue, and process asynchronously. Doing slow work inline causes provider timeouts and duplicate retries.
  • Be idempotent: record processed event ids (unique constraint) and skip repeats.
  • Reconcile: provide or use an events API so you can recover anything missed during your own downtime.

API design

What are good practices for REST resource naming and URL design? Basic

In one line: name things with plural nouns, let the HTTP method carry the verb, keep URLs shallow and consistent, and return the right status code so clients can react without guessing.

Why it matters. An API is a contract used by people who cannot read your code. Predictable names let a developer guess the next endpoint correctly, and consistent status codes let generic client code, proxies and monitoring behave properly.

  • Nouns, plural, no verbs in the path. GET /orders/42, not /getOrder?id=42. POST /orders creates; DELETE /orders/42 removes.
  • Hierarchy shows ownership, but stay shallow. /users/7/orders lists user 7's orders. Once an order has its own id, address it directly as /orders/42 instead of /users/7/orders/42/items/3/options; deep nesting couples URLs to the parent chain and is awkward to evolve.
  • Actions that are not CRUD become a sub-resource or a custom action: POST /orders/42/cancel, POST /payments/9/refunds (a refund is a thing you create).
  • Consistency: lowercase, hyphenated paths (/purchase-orders), one casing for JSON fields, ISO 8601 timestamps in UTC, and opaque stable ids. If enumeration is a concern use random ids (UUID/ULID) instead of sequential integers.
  • Query parameters for filter, sort, paging, not for identifying the resource.

Offset vs cursor pagination: how do they differ and which do you choose? Intermediate

In one line: offset pagination says "skip N rows"; cursor (keyset) pagination says "give me rows after this one". Offset is simple but slow and unstable for deep or changing data; cursors stay fast and consistent.

Why offset breaks down. OFFSET 100000 LIMIT 20 forces the database to find and throw away 100,000 rows before returning 20, so page 5000 is 5000 times more work than page 1. And data moves under you. Example: you read page 1 (items 1 to 20); meanwhile 3 new items are inserted at the top; page 2 (offset 20) now starts at what used to be item 18, so you see items 18, 19, 20 twice. With deletions you skip rows instead.

How cursors work. Return a pointer to the last item you gave, and ask for items strictly after it:

GET /posts?limit=20
-> { "items": [...], "next_cursor": "eyJ0IjoiMjAyNi0wMS0wNVQxMDoyMDowMCIsImlkIjo5MDEyfQ" }

-- server decodes cursor to (created_at='2026-01-05 10:20:00', id=9012)
SELECT * FROM posts
WHERE (created_at, id) < ('2026-01-05 10:20:00', 9012)
ORDER BY created_at DESC, id DESC
LIMIT 20;      -- uses an index on (created_at, id): constant time at any depth

The tiebreaker (id) matters: if many rows share one created_at, using only that column would skip or repeat rows at page boundaries. The sort key must be unique in combination.

Choosing. Feeds, timelines, exports, large or fast-changing tables, and machine consumers: cursors. Small, stable admin tables where users jump to "page 7" and need a total count: offset is fine (set a maximum offset). If you need both, offer the cursor for sequential reads and a capped offset for UI paging.

Good practice. Make the cursor opaque (base64 of the sort key plus id, ideally signed) so you can change internals without breaking clients; cap limit (say 100) with a sensible default; return next_cursor (null at the end) rather than making the client compute it; avoid exact total counts on huge tables since COUNT(*) is itself slow (return "has_more" or an approximate count).

How do you design filtering, sorting and field selection? Intermediate

In one line: expose filters, sorts and field selection as query parameters, but only on fields you have deliberately allowed and indexed, with caps, so clients cannot turn your list endpoint into a full-table scan.

A typical request.

GET /tickets?status=open&assignee=7&created_after=2026-01-01
            &sort=-created_at&fields=id,title,status&expand=assignee&limit=50
  • Filtering: simple equality as field=value; ranges as created_after/created_before or operator syntax (price[gte]=10); multiple values as status=open,pending. Keep to a small documented set.
  • Sorting: sort=-created_at,title where a leading minus means descending. Always add a unique tiebreaker internally so pagination is stable.
  • Field selection (sparse fieldsets): fields=id,title trims payload size and DB columns read; helpful for mobile.
  • Expansion: expand=assignee embeds the related object in the same response, saving a round trip, without needing GraphQL.

Rules that prevent production pain.

  1. Whitelist filterable and sortable fields; each must be backed by an index. If a client can sort by an unindexed column on a 100-million-row table, one request can cause a full scan and an outage.
  2. Validate and bound everything: parse types, reject unknown parameters or ignore them consistently, cap limit, cap number of expansions and the total size of IN lists.
  3. Never build SQL by concatenating parameters (injection); map them to bound parameters and a fixed set of column names.
  4. Document defaults (default sort, default limit) and keep them stable, since changing defaults is a breaking change.

When filtering is too rich for query strings: full-text search, faceting, fuzzy matching, many combined conditions. Provide a dedicated search endpoint (POST /tickets/search with a JSON body) backed by a search engine (Elasticsearch, OpenSearch) rather than endlessly bending the list endpoint.

How do you version an API, and how do you keep backward compatibility? Intermediate

In one line: make changes additive so most never need a new version; when a break is unavoidable, version explicitly, run old and new together, and retire the old one with notice and usage data.

Why it matters. Once clients exist, you cannot change the API in place without breaking some of them, and you do not control when they upgrade (mobile apps stay installed for years).

Versioning schemes.

SchemeExampleNotes
URL path/v2/ordersMost visible, easy to route and cache and to test in a browser; changes the URL of every resource
Header / media typeAccept: application/vnd.acme.v2+jsonClean URLs, same resource identity; harder to try by hand and to cache correctly (needs Vary)
Date-pinned per accountAcme-Version: 2026-03-01Account is pinned to the version it first used; lets you ship many small breaking changes without a big-bang v2 (Stripe style); needs compatibility layers

Breaking vs non-breaking.

  • Safe: new endpoints, new optional request fields, new response fields, new optional query parameters. (New enum values are safe only if clients were told to tolerate unknown values.)
  • Breaking: removing or renaming a field, changing a type or unit (cents to dollars), making an optional field required, tightening validation, changing error formats or status codes, changing default sort or page size, changing meaning with the same name.

Practices that keep it manageable.

  • Tolerant reader: clients ignore unknown response fields; servers ignore unknown optional input. This is what makes additive changes safe.
  • Deprecation process: announce, add Deprecation and Sunset response headers (dates), log which API keys still use the old version, contact heavy users, publish a migration guide, then remove. Do not remove blind.
  • Limit live versions: keep one core implementation and translate old versions to it at the edge (adapters), instead of forking the codebase.
  • Contract tests: consumer-driven contracts (Pact) or OpenAPI diff checks in CI to catch accidental breaks before release.
What are idempotency keys and how do you implement them? Senior

In one line: an idempotency key is a unique token the client attaches to a write; the server remembers it, so a retry returns the original result instead of doing the work again. It makes retries safe for non-idempotent operations like creating a payment.

The problem, as a story. A client calls POST /payments for $100. The server charges the card, but the response is lost (timeout, dropped connection). The client cannot tell whether the charge happened. If it retries, the customer may be charged twice; if it does not, they may not be charged at all. Retrying is only safe if repeats do not repeat the effect.

The mechanism. The client generates a unique id (a UUID) once per logical operation and sends it on the first attempt and on every retry: Idempotency-Key: 6b1c.... The server guarantees at most one effect per key.

  1. On a request, atomically insert a row (key, request_hash, status='in_progress') into a table with a unique constraint on key (or a Redis SET NX).
  2. If the insert succeeds, you are the first: do the work. If it fails because the key exists, branch on the stored state:
    • completed: return the saved response (same status and body) without redoing anything;
    • in progress: another attempt is running; return 409 (or wait briefly) so the client retries later;
    • request hash differs: the client reused a key for a different request; return an error (422).
  3. On finish, save the response with the key, in the same database transaction as the business write whenever possible, so you can never have "money moved but key not recorded".
  4. Expire old keys after a window (commonly 24 hours or more) to bound storage.

Timeline: attempt 1 inserts key K (in progress), charges, response lost. Attempt 2 (retry) finds K completed with stored response "payment 981, success" and returns it. One charge, client happy.

The same idea makes webhook consumers and queue consumers safe under at-least-once delivery: record the event id in a unique-constrained table and skip duplicates. PUT and DELETE are naturally idempotent and need no key.

Trap: implementing it as "SELECT to see whether the key exists, then INSERT" as two separate steps. Two concurrent retries both see "not found" and both perform the charge. The unique constraint (or an atomic set-if-absent) must do the check and the claim in one step. Also note crash recovery: if the server dies while "in progress", you need a timeout or recovery rule to avoid blocking that key forever.
How should an API report errors? Intermediate

In one line: use the correct HTTP status for the class of failure, plus a consistent machine-readable body with a stable error code, a human message and a request id.

Why it matters. Clients, SDKs, retry logic, gateways and dashboards all react to the status code first. A client must know in one glance: should I fix my request (4xx), retry later (5xx, 429), or re-authenticate (401)? A consistent body lets programs act on the cause without parsing prose.

A good error response (modelled on RFC 7807/9457 "problem details"):

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json
{ "type": "https://api.example.com/errors/validation",
  "title": "Invalid request",
  "status": 422,
  "detail": "email must be a valid address",
  "errors": [{"field": "email", "code": "invalid_format"}],
  "request_id": "req_8f3a" }
  • 4xx = the client should change something; 5xx = the server failed and a retry may succeed. Never return 200 with an error inside: it breaks retries, monitoring, caches and SLO calculations.
  • Stable error codes (invalid_format, insufficient_funds) are for programs and must not change casually; messages are for people and can be reworded or localised.
  • Request id in every response (and logged) lets support find the exact trace. It is the most useful single field.
  • Safe disclosure: never leak stack traces, SQL, internal hostnames or whether a username exists on login errors. Log details server-side.
  • Signal retryability: 429 and 503 should carry Retry-After; consider a retryable flag. Distinguish 401 (no or bad credentials) from 403 (not allowed).
  • Validation errors: report all field problems at once, not one per round trip.

Pitfall: inconsistent shapes across services (each team invents its own), which forces every client to special-case. Standardise in the gateway or a shared library.

How do you do rate limiting at the API edge, and what do you tell clients? Intermediate

In one line: rate limiting caps how many requests a caller can make in a time window, to protect the system and share capacity fairly. The usual tool is a token bucket enforced at the gateway with shared counters, answering 429 with Retry-After.

Why. Without limits, one buggy client in a retry loop, one abusive scraper, or one noisy tenant can consume all capacity and cause an outage for everyone. Limits also enforce commercial plans (free: 60/min, paid: 6000/min).

Algorithms.

  • Token bucket (most common): a bucket holds up to b tokens and refills at r tokens per second; each request removes one, and with an empty bucket the request is rejected. Example: r = 10/s, b = 50: a client may burst 50 at once, then sustain 10/s. Allows natural bursts while enforcing the long-run average. Stores just (tokens, last_refill_time) per key.
  • Leaky bucket: requests enter a queue and drain at a fixed rate; smooths output, good for protecting a fragile downstream; adds queueing delay.
  • Fixed window counter: count per minute window. Simple (INCR with expiry), but a client can send 100 at 12:00:59 and 100 at 12:01:00, i.e. 2x the limit within two seconds.
  • Sliding window log or counter: accurate over any interval; the log stores a timestamp per request (memory heavy), the counter blends the previous and current window (approximate, cheap).

Distributed enforcement. With many gateway nodes, a per-node counter lets a client get N times the limit. Options: a shared store (Redis with an atomic Lua script or INCR+EXPIRE; accurate, but adds a network call and a dependency); or local counters with periodic sync or each node getting a fraction of the quota (fast, slightly inaccurate). Pick based on how strict the limit must be.

What to tell the client. Reply 429 Too Many Requests with Retry-After: 30 and headers showing the limit, what remains, and reset time (the RateLimit-* draft headers or the widespread X-RateLimit-*). Well-behaved clients back off.

Design choices. Key by API key, user, tenant or IP (IP alone punishes NAT'd offices). Different limits per plan and tighter ones for expensive endpoints (search, export). Count cost, not just calls, for batch endpoints. Separate fairness (per-tenant quotas) from self-protection (global load shedding when the system is saturated).

Trap: decide up front what happens if the limiter store is down. Fail open (allow) protects availability but loses protection; fail closed (deny) protects the backend but turns a Redis blip into an API outage. Many choose fail open with conservative local fallback limits.
How do you design bulk or batch APIs? Senior

In one line: batch endpoints cut round trips but create new questions: what if some items fail, how big can a batch be, how do retries avoid duplicates, and when should the work be asynchronous.

Why batch. Creating 500 records with 500 requests costs 500 round trips and 500 sets of auth, parsing and logging. One request with 500 items is far cheaper, especially over a high-latency link.

Design decisions.

  • Partial failure. Decide all-or-nothing (one transaction, any failure rolls back everything, return 4xx for the batch) or per-item results. Per-item is most useful: return 200 (or the WebDAV-style 207 Multi-Status) with an array like [{"id":"a","status":201},{"id":"b","status":422,"error":"invalid email"}] so the client retries only the failed items. State clearly which you chose.
  • Limits. Cap items per batch (say 1000) and bytes per payload; reject larger with 413. Without a cap, one request can hold a thread, memory and a DB transaction for minutes.
  • Idempotency. Require a client-supplied id per item (or one idempotency key for the batch) so a timed-out batch can be resent without duplicating records.
  • Asynchronous for big jobs. For tens of thousands of items, accept the job and process in the background: POST /imports returns 202 Accepted and a job URL; the client polls GET /imports/9 (or gets a webhook) to see progress and a result report. For big files, the client uploads straight to object storage (S3 pre-signed URL) and passes the object key, keeping large bodies off your API servers.
  • Fair rate limiting. Count items, not just requests, otherwise a single batch call bypasses limits meant to be per-record.
  • Ordering and dependencies: say whether items are processed in order and whether later items may refer to earlier ones.

Pitfall: a synchronous batch that holds a DB transaction open for 30 seconds locks rows and times out at the gateway; split into chunks or go async.

An operation takes 2 minutes. How should the API expose it? Intermediate

In one line: do not hold the request open. Return 202 Accepted with a status URL right away, run the work in the background, and let the client poll (or be notified) for the result.

Why not wait synchronously. Browsers, gateways and load balancers cut requests at 30 to 60 seconds; the client may disconnect; a held connection occupies a thread; and a timeout leaves the client not knowing whether the work finished.

The pattern.

  1. POST /reports with the parameters. The server validates, stores a job record (id, state=pending, owner), enqueues the work, and replies immediately: 
    HTTP/1.1 202 Accepted
Location: /reports/jobs/9f2c
Retry-After: 5
  2. A worker picks the job from the queue, updates state to running (with progress if available), and stores the result (often in object storage).
  3. The client polls GET /reports/jobs/9f2c: {"state":"running","progress":40} then {"state":"succeeded","result_url":"/reports/9f2c/file"} or {"state":"failed","error":{...}}. A common variant: the status resource returns 303 See Other pointing to the finished result.
  4. Instead of polling, offer a webhook callback or SSE/WebSocket notification, with polling as the fallback.

Details that make it production-ready. Persist the job (a restart must not lose it); make creation idempotent (idempotency key, so a retried POST does not start two reports); give polling a sensible Retry-After and rate limit it; let clients cancel (DELETE on the job); expire results; and have workers retry safe steps and record failures with a clear reason.

Pitfall: using a long-lived request and "just raising the timeout"; it hides the problem until a deploy or network blip kills the in-flight work.

How do APIs authenticate clients, briefly? Intermediate

In one line: authentication proves who is calling; the API picks a credential type by who the client is: API keys for simple server-to-server, OAuth 2.0 tokens for delegated user access, JWTs for self-contained verifiable identity, and mTLS for strong service identity.

  • API keys. A long random string identifying the calling application. Simple and good for server-to-server and metering. Weaknesses: it is a bearer secret with no user context, and leaked keys work until revoked. Send it in a header (never in URLs, which end up in logs), store it hashed, support rotation and per-key scopes, and allow multiple keys per client for rollover.
  • OAuth 2.0 bearer tokens. A framework for delegated access: a user authorises app X to act on their behalf with limited scopes (read:orders), and X receives a short-lived access token plus a longer-lived refresh token to get new ones. The API checks the token and its scopes. Use authorization code with PKCE for apps with users, and client credentials for machine-to-machine.
  • JWT (JSON Web Token). A signed, self-contained token (header, claims such as sub, exp, scope, signature). The gateway verifies the signature with the issuer's public key (no database lookup), so it scales well. The catch: it cannot be revoked before it expires unless you keep a deny-list or check a version, so keep lifetimes short (minutes), and keep secrets out of the payload (it is encoded, not encrypted).
  • mTLS. Both sides present certificates during the TLS handshake. Strong identity for service-to-service and B2B; certificate lifecycle (issue, rotate, revoke) is the cost, usually automated by a mesh or internal PKI.

Where to enforce. Validate once at the gateway (cheap, centralised), then pass a trusted identity to services (signed header or internal token). Internal services must still authorise (is this caller allowed this action on this object?) rather than assuming the edge did everything; many breaches come from services that trust the network (zero-trust says do not).

Authentication vs authorisation: who you are vs what you may do. A valid token for user A must not allow reading user B's order (object-level authorisation, the top OWASP API risk).

How do you make GET requests cacheable and conditional in your API? Intermediate

In one line: use ETags to make reads cheap (304 Not Modified) and to make writes safe (If-Match to prevent lost updates).

Conditional reads (saves bandwidth and time). The server returns ETag: "v17" (a hash or version of the representation) with Cache-Control. The next time the client wants the resource it sends If-None-Match: "v17". If unchanged, the server replies 304 Not Modified with no body (a few hundred bytes instead of the whole payload); if changed, it returns 200 with the new body and ETag. The server still does a check, but can make it cheap (compare a version column without building the whole response).

Conditional writes (prevents lost updates). Scenario: two users open the same document at version 17. User A saves changes; user B, still editing the old copy, saves later and silently overwrites A's work. With optimistic concurrency:

GET  /docs/5            -> 200  ETag: "v17"
PUT  /docs/5            If-Match: "v17"   -> 200  ETag: "v18"     (A succeeds)
PUT  /docs/5            If-Match: "v17"   -> 412 Precondition Failed  (B is told it is stale)

B must re-fetch, merge and retry. Many APIs require If-Match on updates and return 428 Precondition Required if it is missing. It maps to a version column or a hash in the database (UPDATE ... WHERE id=5 AND version=17, check rows affected).

Which validator. Strong ETags (exact bytes) vs weak (W/"...", semantically equal); Last-Modified has one-second granularity, so ETags are better for fast-changing resources. Note that gzip and other encodings may need different ETags per variant.

Pitfall: relying on last-write-wins when concurrent edits are plausible. ETags are the HTTP-native fix, and unlike pessimistic locks they never block.

Service-to-service communication

Synchronous vs asynchronous service communication: how do you choose? Intermediate

In one line: use synchronous calls when the caller needs the answer to continue; use asynchronous messaging when the work can happen later, may fan out, or must not tie the caller's availability to the callee's.

The core difference. In a synchronous call (REST, gRPC) the caller waits for the callee. In an asynchronous exchange the caller hands a message or event to a broker (queue, log) and moves on; the callee processes it when it can.

Examples.

  • Sync: checkout asks the pricing service for the current price and the auth service whether the token is valid. The answer is needed to respond to the user, so wait.
  • Async: after the order is stored, publish OrderPlaced; the email service, inventory service, analytics and search indexer each consume it independently. The order API does not care if email is slow or down, and adding a new consumer needs no change to the producer.

Availability arithmetic. If a request needs 5 services in series, each 99.9 percent available, the chain is 0.999^5 = about 99.5 percent (roughly 3.6 hours down per month instead of 43 minutes). Every synchronous dependency multiplies in. Moving non-critical steps behind a queue shortens the critical path and raises availability.

Costs of async. Eventual consistency (the user may not see the effect immediately), duplicates (design for at-least-once and idempotent consumers), ordering challenges, dead-letter handling, and harder debugging and tracing across hops. You also need a broker to operate.

Decision rule. Sync for queries and for steps whose result decides the response; async for notifications, side effects, workflows that can complete later, and spikes needing buffering. A common hybrid: accept synchronously, store, return 202 or the id, and process the rest asynchronously (the outbox pattern ensures the DB write and the event publish do not diverge).

What patterns keep synchronous calls from taking the whole system down? Senior

In one line: assume every remote call can hang or fail; contain the damage with timeouts, careful retries, circuit breakers, bulkheads, load shedding and fallbacks, used together.

Why. A slow dependency is more dangerous than a dead one: callers hold threads and connections while waiting, exhaust their own capacity, and the failure spreads upstream (cascading failure).

  • Timeouts everywhere. Every outbound call gets a connect and read timeout, plus an overall deadline for the whole user request. No call waits forever.
  • Retries, carefully. Retry only idempotent operations (or those with idempotency keys), only on retryable errors (timeouts, 503, connection reset, not 400), with exponential backoff and jitter (random spread) so clients do not retry in sync. Use a retry budget (retries limited to, say, 10 percent of normal traffic) and retry at one layer only. Otherwise it multiplies: 3 layers each making 3 attempts means 27 calls reach the bottom service during an incident, finishing off a service that was only struggling.
  • Circuit breaker. Wraps calls and tracks failures. States: closed (normal), open (after e.g. 50 percent failures in a window, fail immediately without calling for a cooldown, giving the dependency room to recover and freeing the caller's threads), half-open (let a few trial requests through; success closes, failure re-opens).
  • Bulkheads. Separate thread or connection pools per dependency (like watertight ship compartments), so a slow recommendations service can exhaust only its own pool, not the pool used for payments.
  • Load shedding and backpressure. When overloaded, reject early (fast 503) rather than queue until everything times out. Bounded queues, concurrency limits, and prioritising critical requests keep goodput up.
  • Fallbacks and graceful degradation. Serve cached or default data if the optional dependency fails (no recommendations, but the page works).
How do services find each other (service discovery)? Intermediate

In one line: service discovery is how a caller turns "the cart service" into the current IP addresses of healthy instances, when instances come and go constantly.

Why it exists. In a cloud or Kubernetes setup, instances are created and destroyed by autoscaling and deploys, and their IPs change. Hard-coding addresses breaks immediately; a human-maintained list is always out of date.

The mechanism.

  1. Register: each instance announces itself (name, IP, port, metadata) to a registry on start-up, either itself (self-registration) or via a platform component (Kubernetes does it from pod state).
  2. Keep alive: the instance heartbeats, or the registry health-checks it; failing instances are removed after a timeout.
  3. Lookup: callers query the registry for healthy instances by name and refresh as it changes.

Common implementations.

  • DNS plus a stable virtual IP: in Kubernetes, cart.shop.svc.cluster.local resolves to a Service ClusterIP; kube-proxy or the mesh spreads traffic over healthy pods. Simplest for callers, the default choice.
  • Registry plus client-side lookup: Consul, Eureka, etcd/ZooKeeper-based. The client library queries the registry and balances itself (also gives metadata, zone awareness).
  • Mesh control plane: sidecars receive endpoint lists pushed from the control plane (xDS in Envoy/Istio); apps just call a name.
  • Headless services / SRV records return the individual instance IPs and ports for clients that balance themselves (gRPC, databases).

Failure modes. Stale entries (instance dead but still listed) cause errors until health checks catch up, so use short TTLs, active health checks, and client-side retry on another instance. The registry itself must be highly available (it is a critical dependency); clients should cache the last known list so a registry outage does not stop calls. DNS caching in clients (the JVM, long TTLs) can hide updates.

What is a service mesh and is it worth it? Senior

In one line: a service mesh moves networking features (mTLS, retries, timeouts, traffic splitting, telemetry) out of application code into a sidecar proxy beside each service, configured centrally. It is worth it at scale, not for a handful of services.

How it works. Each pod runs your app plus a sidecar proxy (Envoy in Istio, linkerd2-proxy in Linkerd). All inbound and outbound traffic of the app passes through the sidecar (traffic is redirected transparently). A control plane pushes configuration (routes, policies, certificates, endpoint lists) to all the sidecars. (Newer "ambient" or node-level modes aim to drop per-pod sidecars to cut overhead.)

What you get uniformly across languages.

  • mTLS between services with automatic certificate issue and rotation, and identity-based authorisation policies ("only checkout may call payments").
  • Resilience policies as config: timeouts, retries with budgets, circuit breaking, outlier ejection, rate limits.
  • Traffic management: canary and weighted splits (5 percent to v2), traffic mirroring, fault injection for testing, locality-aware routing.
  • Observability: golden metrics (rate, errors, latency) and traces for every hop without instrumenting each app.
  • Per-request balancing for gRPC and HTTP/2.

Costs. An extra proxy hop on each side (typically around a millisecond or less per hop, workload dependent), CPU and memory per sidecar (adds up across thousands of pods), operational complexity (upgrades, control plane availability, certificate trust), and harder debugging ("is the app or the proxy dropping this?"). Misconfigured retries in the mesh stack with app retries and amplify load.

When. Worth it with many services, many languages, strict security (mTLS everywhere) or complex rollout needs. For a few services, a shared client library plus a gateway and Kubernetes-native features is usually enough.

Service C becomes slow (not down). Why does that take down A and B, and how do you stop it? Senior

In one line: a slow dependency is worse than a dead one, because callers keep waiting on it and exhaust their own threads and connections, which spreads the failure upstream. Stop it with deadlines, circuit breakers, bulkheads, shedding and disciplined retries.

The chain reaction, step by step. A calls B, B calls C. C becomes slow (a bad query, GC, saturated DB), say responses go from 20 ms to 10 s.

  1. Each B request now holds a thread and an outbound connection for 10 s. By Little's law, with 200 requests/s that is 2000 busy threads; B's pool (say 200) fills within a second.
  2. B's new requests queue or are rejected; B's own latency spikes. Health checks on B may even fail, taking B out of rotation and sending its load to fewer B nodes, which fall over faster.
  3. A's calls to B now hang, so A's threads fill the same way. The outage has climbed from C to A and the user sees errors, though only C was sick.
  4. Callers time out and retry, adding load to the already-struggling C, so it cannot recover even after the original cause passes.

Controls (each breaks a link in the chain).

  • Tight timeouts and deadlines so waits are bounded (a 500 ms timeout holds a thread for 0.5 s, not 10 s).
  • Circuit breakers on B→C so B fails fast after a few failures and frees its threads, giving C room to recover.
  • Bulkheads: a dedicated, limited pool for C calls, so a slow C cannot starve B's other work.
  • Bounded queues and load shedding: reject excess early with 503 rather than queueing until everything times out.
  • Retry discipline: backoff with jitter, a retry budget, and retries at a single layer only.
  • Fallbacks / graceful degradation (cached or default data) and async decoupling for non-critical calls.
  • Autoscaling alone is not the answer: adding B instances just moves more threads onto a slow C.

Retry storms preventing recovery are a recurring theme in published outage post-mortems from large cloud and internet companies, which is why retry budgets and circuit breakers are standard practice.

Timeouts at the network level

What kinds of timeouts exist on a network call? Intermediate

In one line: a network call has several different clocks that can each expire; you need to set each one, not rely on one vague "timeout".

The timeline of one call, with a timeout for each phase.

  1. Pool acquire timeout: how long to wait for a free connection from the client pool. If the pool is exhausted you want to fail quickly (tens to hundreds of ms), not queue forever.
  2. Connect timeout: time to establish TCP (and often TLS). A healthy host answers in a round trip or two; if the SYN gets no reply the host is probably down, so keep this short (hundreds of ms to a few seconds). It lets you fail over to another instance quickly.
  3. Write timeout: time to send the request, mainly matters for large bodies and slow receivers.
  4. Read (socket) timeout: maximum silence while waiting for response bytes. Set from the callee's latency profile (a bit above p99). Note it is per read, not for the whole response: a server drip-feeding one byte every few seconds never trips it, which is why you also need the next one.
  5. Total request deadline: hard cap on the whole operation, including retries and backoff. This is the number that must fit your user-facing SLA.

Plus infrastructure timeouts you do not control from the client. Idle timeouts in load balancers, proxies, NATs and firewalls: how long they keep a silent connection before dropping it (AWS ALB defaults to 60 s; some NATs and firewalls forget idle flows after a few minutes). Also server-side request timeouts and gateway upstream timeouts. These cause the "dead connection" bugs discussed earlier; mitigate with keep-alive probes and shorter client idle timeouts.

Example Java-style config (conceptual): acquire 200 ms, connect 1 s, read 800 ms, total deadline 2 s with at most one retry.

Trap: many HTTP clients default to no timeout, or to very long ones (minutes). A hung dependency then holds threads indefinitely. Always set them explicitly, and test by simulating a slow server.
How should timeouts be set across a call chain (deadline propagation)? Senior

In one line: every hop's timeout must be shorter than its caller's, and the remaining time should be passed downstream, so nobody works on a request whose caller has already given up.

The problem. Suppose the user's request has a 2 s budget. The gateway calls A, A calls B, B calls C. If each layer has its own independent timeout (gateway 2 s, A 5 s, B 5 s), then when C is slow, the gateway gives up at 2 s and tells the user "error", but A and B keep working for up to 5 more seconds, holding threads and DB connections for a result nobody will read. At scale that wasted work is a large share of load, precisely when the system is already stressed.

Deadline propagation. Instead of fixed per-hop timeouts, pass the absolute deadline (or remaining time) with the request, and each service uses remaining time minus a margin.

user budget 2000 ms
gateway -> A       timeout 1900 ms
  A spends 100 ms, calls B with 1800 - 100 = 1700 ms left
    B spends 200 ms, calls C with 1400 ms left
      C sees "1400 ms left"; if it can't finish, it fails fast or skips optional work

gRPC does this automatically (a deadline travels in the call metadata, and cancellation propagates). For HTTP, send a header (for example X-Request-Deadline or a remaining-ms value) and have your client library read it. Also honour cancellation: when the caller disconnects, stop working (cancel the DB query).

Account for retries. Worst-case time for one dependency = attempts x timeout + backoff delays. With 3 attempts of 1 s plus backoff you already spend over 3 s, exceeding a 2 s budget. So either reduce per-attempt timeouts, retry only if enough budget remains, or limit attempts. Inner layers should have smaller timeouts than outer ones, and retries should happen at one layer.

How do you pick a timeout value? Intermediate

In one line: set the timeout from measured latency (around p99 to p99.9 plus margin), not from a guess, and monitor the timeout rate to re-tune it.

The trade-off. A timeout is a bet: wait long enough that healthy-but-slow requests succeed, short enough that sick dependencies do not hold your resources.

  • Too low: normal slow requests (the slowest 1 percent) fail. Callers retry, which adds load, which slows things further: false failures and retry storms.
  • Too high: when the dependency is unhealthy you hold threads, connections and memory for the whole duration, producing cascading failure.

How to pick.

  1. Measure the callee's latency distribution under realistic load (p50, p99, p99.9), from the caller's side, since that includes network and queueing.
  2. Set the read timeout slightly above the latency you consider acceptable, often p99 or p99.9 times a small factor. Example: p99 = 120 ms, p99.9 = 300 ms, so choose 400 to 500 ms.
  3. Make sure it fits the caller's overall deadline once retries are considered.
  4. Use different values per endpoint: a search call and a report export have different shapes.
  5. Keep connect timeout much lower than read timeout.

Revisit after traffic or code changes. Alert on timeout rate, and watch for timeouts clustering near the limit (a sign the real latency is creeping up). Adaptive approaches (concurrency limits that follow measured latency, hedged requests for tail latency) exist but start from solid fixed timeouts.

Clients get 504 Gateway Timeout from the gateway, but the backend logs show the request succeeded. What happened? Senior

In one line: the gateway gave up waiting before the backend finished, but the backend kept going and committed the work. The client sees failure for something that actually succeeded, which makes retries dangerous.

What happened, on a timeline. Gateway upstream timeout is 30 s. At t=0 the client sends POST /orders. The backend takes 35 s (a slow DB lock, a heavy report). At t=30 s the gateway returns 504 Gateway Timeout to the client and closes the upstream connection. At t=35 s the backend finishes and writes the order, then tries to respond to a connection nobody is reading. The logs show success; the user saw an error.

Consequences. The client (or user) retries and the order is created twice unless writes are idempotent; backend capacity is wasted on abandoned work; and metrics disagree (gateway says failed, service says OK).

Fixes.

  1. Align timeouts: the backend's own deadline must be shorter than the gateway's, so it fails (or cancels) before the gateway gives up, and the failure is reported honestly.
  2. Make long work asynchronous: return 202 plus a status URL, so no request lives 30 s.
  3. Idempotency keys on writes so a retry after 504 returns the original result.
  4. Honour cancellation: stop work (and roll back or skip) when the client disconnects or the deadline passes.
  5. Find and fix why it is slow (profile the DB lock or query), since timeouts only bound the damage.

A brief database blip causes a long outage afterward. What may have gone wrong at the network layer? Senior

In one line: the outage outlasted the trigger because clients' own recovery behaviour (synchronised retries and reconnects) kept overloading the database: a retry storm leading to a metastable failure.

The sequence.

  1. The database stalls for 30 seconds (failover, maintenance, a slow query). Requests time out.
  2. Thousands of clients retry immediately, many layers retry, and pools open new connections. Demand on the database becomes several times normal.
  3. The database comes back, but it faces the accumulated backlog plus the retry traffic plus a flood of new connections (each costs memory and auth work), so it stays overloaded and keeps timing out, causing more retries.

This is a metastable failure: the system is stuck in a bad state sustained by its own feedback loop, even after the original trigger has gone. It will not heal on its own.

Mitigations.

  • Exponential backoff with full jitter (sleep = random(0, min(cap, base * 2^attempt))) so retries spread out instead of arriving in waves.
  • Retry budgets and a single retry layer, plus circuit breakers so clients stop hammering a sick dependency.
  • Limit connection counts (pool max sizes, a DB proxy such as PgBouncer or RDS Proxy) and ramp pools back up slowly, not all at once.
  • Load shedding at the front door (reject or prioritise requests) so total demand stays below capacity while the backlog clears; drop work that is already expired (deadline passed).
  • Operational lever: the ability to shed or pause a large share of traffic temporarily (feature flags, rate-limit tightening, taking a region out) and let the system recover, then restore gradually.
  • Capacity headroom and testing recovery (chaos tests that stall the database) so you know it recovers rather than hoping.
