HLD: Security, Observability and Operations interview questions

The cross-cutting topics of every system design interview: authentication and authorization, tokens, OAuth2/OIDC, encryption, common attacks, privacy and multi-tenancy; logs, metrics, traces, SLOs and incident response; CI/CD, rollouts, migrations, cost, capacity and infrastructure as code.

How to use this page

Interviewers rarely ask these topics on their own. They show up as follow-ups inside a design: "how do users log in?", "how would you know it is broken?", "how do you roll this out safely?". Click a question, answer it aloud first, then open the answer. Questions marked Basic are vocabulary, Intermediate are the usual follow-ups, Senior are trade-off and judgment questions. Scenario questions (orange) are the "your service sees X, what do you do" type. Where an incident is quoted, only the headline is given and details are hedged.

Authentication, sessions and tokens

What is the difference between authentication and authorization? Basic

Authentication (AuthN) answers "who are you?". Authorization (AuthZ) answers "what are you allowed to do?". AuthN comes first and produces an identity; AuthZ takes that identity plus the requested action and resource and says yes or no.

AuthNAuthZ
QuestionWho is this?May they do this?
InputsPassword, passkey, OTP, certificate, tokenIdentity, roles/attributes, resource, action
Failure code401 Unauthorized (really "unauthenticated")403 Forbidden
WhereUsually once, at the edge or identity providerOn every request, close to the data
Trap: authenticating at the gateway and then trusting every internal call. A valid login says nothing about whether user A may read user B's order. Always check ownership in the service that owns the data (otherwise you get the classic IDOR / broken object level authorization bug).
Server-side sessions versus tokens: how do they differ and when do you pick each? Intermediate

Session: after login the server stores state (user id, roles) in a store such as Redis and gives the browser an opaque random session id in a cookie. Each request looks the id up.

Token (for example JWT): the server signs a small document with claims (user id, roles, expiry) and the client sends it back. Any service holding the verification key can check it without calling a central store.

Session idSelf-contained token
StateServer holds itClient holds it
RevocationEasy: delete the recordHard: valid until expiry unless extra machinery
Per-request costOne store lookupSignature check, no network
Cross-service useEvery service needs the storeNatural fit for microservices and third parties
SizeTiny cookieHundreds of bytes to KBs

Pick sessions for a classic browser web app with one backend, where instant logout and "kill all sessions" matter. Pick tokens when many independent services or mobile/third-party clients must verify identity with no shared store. Many real systems combine them: a short-lived token for APIs plus a server-side refresh record that can be revoked.

What is a JWT and how is it structured? Basic

A JSON Web Token has three base64url parts joined by dots: header.payload.signature.

  • Header: algorithm and key id, e.g. {"alg":"RS256","kid":"2026-11"}.
  • Payload (claims): sub (subject), iss (issuer), aud (audience), exp (expiry), iat, plus custom claims such as roles or tenant id.
  • Signature: HMAC with a shared secret (HS256) or a private-key signature (RS256/ES256) over header and payload.

The payload is encoded, not encrypted: anyone holding the token can read it. Never put secrets or sensitive PII in it. The signature only proves it was not altered and who issued it.

What are the pros and cons of JWTs? Intermediate
ProsCons
Stateless verification: no lookup, scales horizontally, no shared session storeCannot be revoked before expiry without extra state
Carries claims so services avoid a user-service callClaims go stale (role removed, but token still says admin until expiry)

One-line verdict: JWTs trade easy revocation for easy verification. Keep them short-lived (5 to 15 minutes) so the weakness is bounded.

How do you revoke or invalidate a JWT? Senior

A pure stateless JWT cannot be revoked; the options all add some state or shorten the window:

  1. Short expiry + refresh token. Access token lives about 10 minutes; revoke the refresh token server-side (a DB row) and the user is out within 10 minutes. This is the default answer.
  2. Denylist. Store revoked token ids (jti) or "user X tokens issued before time T are invalid" in Redis with a TTL equal to the token's remaining life. The list stays tiny because entries expire. Costs a lookup per request, which gives up some statelessness.
  3. Token versioning. Put a ver claim in the token and a version counter on the user; bump it to invalidate all tokens. Needs a (cacheable) read.
  4. Key rotation. Rotate the signing key to kill everything. A nuclear option for a compromise.
  5. Token introspection. Use opaque tokens and have resources call the identity provider (RFC 7662). Full control, one extra hop (cache it for seconds).
Say: "Short-lived access tokens, rotating refresh tokens that I can revoke, and a small TTL-bounded denylist for emergencies like a stolen device."
Where should a browser app store tokens, and why? Intermediate
  • localStorage / sessionStorage: readable by any script on the page, so one XSS bug leaks the token.
  • HttpOnly, Secure, SameSite cookie: scripts cannot read it, so XSS cannot steal it directly (it can still make requests as the user). But cookies are sent automatically, which brings CSRF, so pair with SameSite=Lax/Strict and CSRF tokens for state-changing calls.

Common recommendation: keep the refresh/session credential in an HttpOnly cookie and keep any access token in memory only. Mobile apps use the OS secure store (Keychain, Keystore).

What is refresh token rotation and why use it? Senior

Each time a client uses a refresh token, the server returns a new access token and a new refresh token and invalidates the old one. If an attacker steals a refresh token and uses it, then the real client later presents the already-used token: the server sees reuse, concludes theft, and revokes the whole token family so both parties must log in again. This turns a silent long-lived theft into a detectable event. Handle the race where a flaky network makes the real client retry: allow a short grace window or tie refresh tokens to the device.

How should passwords be stored? Why not SHA-256 or encryption? Basic

Store a slow, salted, adaptive hash: argon2id (preferred), bcrypt or scrypt, or PBKDF2 where required for compliance.

  • Hash, not encrypt: encryption is reversible; if the key leaks, all passwords leak. You never need the original password, only to compare.
  • Slow on purpose: plain SHA-256 does billions of guesses per second on a GPU. A tuned argon2id/bcrypt makes each guess cost tens to hundreds of milliseconds and, for argon2, lots of memory.
  • Salt: a unique random value per user, stored beside the hash, so identical passwords hash differently and precomputed rainbow tables are useless.
  • Pepper (optional): a secret kept outside the database (in an HSM or secrets manager) mixed in, so a DB-only leak is not enough.

Also: rate limit logins, check against breached-password lists, support MFA/passkeys, and tune the cost so login takes roughly 100 to 500 ms on your hardware. Mind DoS: expensive hashing is a CPU target, so rate limit it.

What is MFA and what are passkeys? Intermediate

MFA requires two or more factor types: something you know (password), have (phone, hardware key) or are (biometric). Strength ranks roughly: SMS code (weak: SIM swap, phishable) < TOTP app (phishable by a real-time proxy) < push with number matching < FIDO2/WebAuthn hardware key or passkey (phishing resistant).

Passkeys (WebAuthn) replace the password with a public/private key pair per site. The private key stays in the device's secure hardware; the server stores only the public key and verifies a signed challenge. Because the signature is bound to the real origin, a look-alike phishing site gets nothing usable, and there is no shared secret to leak from your database.

When do you use API keys, and how do you design them safely? Intermediate

An API key is a long random string identifying a calling application or project (not a human). Good for server-to-server, developer platforms, simple metering and per-key rate limits.

  • Generate 128+ bits from a secure random source; show it to the user once.
  • Store only a hash (SHA-256 is fine here since the key is high entropy) plus a short visible prefix (sk_live_ab12...) for lookup and support.
  • Send in a header, never in URLs (they end up in logs and browser history).
  • Scope them (read-only, per-resource), allow several keys per account for rotation, support expiry and instant revoke, and watch for leaks (secret scanning in repos).

Limits: a key is a bearer secret with no user identity, no built-in expiry and coarse permissions. For delegated access on behalf of users, use OAuth2 instead.

What is mTLS and where is it used? Intermediate

Normal TLS authenticates only the server: the client checks the server's certificate. In mutual TLS the client also presents a certificate and the server verifies it, so both sides are cryptographically identified during the handshake.

Use it for service-to-service traffic inside a mesh (Istio, Linkerd issue short-lived certificates per workload, often from a SPIFFE identity), for B2B APIs and for IoT devices. It gives encryption plus strong workload identity without passing tokens around.

Costs: you need a certificate authority, automated issuance and rotation (lifetimes of hours are common in meshes), and debugging is harder. Expired certificates are a classic outage cause, so monitor expiry. mTLS proves which service is calling; you still need AuthZ (which calls that service may make) and usually a user token for which end user.

OAuth2, OIDC and SSO

What problem does OAuth2 solve, in plain words? Basic

OAuth2 is a delegated authorization framework. Example: a photo-printing app wants your photos from a cloud drive. Without OAuth you would hand it your drive password. With OAuth you are sent to the drive's own login page, you approve "allow printing app to read photos", and the app receives a limited, revocable access token. The app never sees your password and cannot do more than the granted scopes.

Four roles: resource owner (you), client (printing app), authorization server (issues tokens), resource server (the API).

Trap: OAuth2 by itself is not authentication. An access token says "the bearer may do X", not "this person is user 42". That is what OIDC adds.
Walk through the Authorization Code flow with PKCE. Senior
  1. Client creates a random code_verifier, sends its hash (code_challenge) and a random state in the redirect to the authorization server.
  2. User logs in at the authorization server and consents; the server redirects back with a one-time code.
  3. Client posts the code plus the original code_verifier to the token endpoint. The server hashes the verifier and compares.
  4. Server returns the access token (and refresh token, and an ID token if OIDC).

Why PKCE: if an attacker intercepts the code (a malicious app on the phone, a leaked redirect), they lack the verifier, so the code is useless. PKCE is now recommended for all clients, not just public ones. Why state: ties the response to the request, defeating CSRF on the callback.

What does OpenID Connect add on top of OAuth2? Intermediate

OIDC is an identity layer on OAuth2. When the client asks for the openid scope it also gets an ID token, a JWT that states who authenticated (sub, iss, aud, exp, nonce, often email and name), plus a standard /userinfo endpoint and a discovery document (/.well-known/openid-configuration) listing endpoints and signing keys (JWKS).

Rule of thumb: the ID token is for the client to learn who the user is; the access token is for the API. Do not send ID tokens to APIs as credentials. The client must validate signature, issuer, audience, expiry and nonce.

What is SSO and how does it work? Compare SAML and OIDC. Intermediate

Single sign-on: the user logs in once at a central identity provider (IdP: Okta, Entra ID, Google) and every connected app (service providers) trusts the IdP's assertion, so no per-app passwords. The IdP keeps its own session; when app B redirects the user there, the IdP sees the live session and bounces straight back with a token or assertion, no second login.

SAML 2.0OIDC
FormatXML assertionsJSON/JWT
Typical useEnterprise web apps, older workforce SSOModern web, mobile, APIs
Mobile/SPA fitPoorGood

Design points: SSO is a single point of failure and a high-value target, so require MFA at the IdP. Logout is hard: single logout across apps is unreliable, so keep app sessions short. For enterprise customers also support SCIM so the IdP can provision and deprovision users automatically (offboarding in one place).

How should an API validate an incoming access token? Intermediate
  1. If it is a JWT: verify the signature against the issuer's public keys (JWKS, cached, selected by kid). Pin the allowed algorithms; reject none.
  2. Check iss is your trusted issuer, aud is this API, exp/nbf with small clock skew.
  3. Check scopes/roles against the endpoint.
  4. Do object-level checks (does this user own this record?).
  5. If the token is opaque: call the introspection endpoint and cache the result briefly.

Where it runs: often at the API gateway for coarse checks, with services re-checking fine-grained rules. Pass the verified identity internally in a signed header or a downscoped token, not the raw user token to every hop (confused-deputy risk).

How do microservices authenticate to each other and carry the end user's identity? Senior
  • Workload identity: mTLS with per-service certificates (mesh) or cloud IAM roles/service accounts. Answers "which service is calling".
  • User context: propagate a short-lived, narrowly scoped token (token exchange, RFC 8693) or a signed internal assertion with the user id. Answers "on whose behalf".
  • AuthZ at each service: a policy such as "orders-service may call payments-service charge only" (mesh authorization policies), plus the user permission check.

Avoid a shared static internal API key: it cannot be traced, rotated easily or scoped. Avoid "inside the network means trusted": that is exactly what zero trust rejects.

Authorization models, secrets and zero trust

Compare RBAC and ABAC. When would you choose each? Intermediate

RBAC (role-based): users get roles (admin, editor, viewer); roles hold permissions. Simple to explain, audit and implement. ABAC (attribute-based): a policy evaluates attributes of the user, resource, action and context: "a doctor may read a record if record.hospital == user.hospital and it is during a shift and the request comes from a managed device".

RBACABAC
ExpressivenessCoarseFine-grained, contextual
ComplexityLow; fails with role explosion (editor-for-team-A, editor-for-team-B...)Higher; harder to audit "who can access X?"
PerformanceLookupPolicy engine evaluation (OPA, Cedar)

Pick RBAC for most internal tools and as a starting point. Add ABAC conditions (tenant, ownership, time, risk) when roles multiply or rules depend on data. Relationship-based access control (ReBAC, Google Zanzibar style: "user is editor of folder, doc inherits folder") fits sharing models like documents and drives. In practice: RBAC for coarse capability, attribute/relationship checks for object level.

Where should authorization logic live: gateway, each service, or a central service? Senior
  • Gateway: coarse checks (valid token, scope, rate limit). Cheap and uniform, but it cannot know object ownership.
  • In each service (library + local rules): has the data and context; fastest; risk of inconsistent implementations.
  • Central policy service or sidecar (OPA/Cedar, Zanzibar-like): one policy language, consistent audit, decisions as code; adds latency and a dependency, so evaluate locally (sidecar/embedded) with policy and data pushed to the edge, and decide fail-closed on error.

A balanced design: gateway for authN and coarse scope, shared policy library or sidecar for decisions, object-level enforcement in the owning service. Always default deny, enforce on the server (never rely on a hidden button), and log decisions.

How do you manage secrets (passwords, API keys, certificates)? Intermediate

Principles: secrets never live in source control, container images, logs or plain environment dumps; they are fetched at runtime from a dedicated store; access is identity-based and audited; they rotate.

  • Store: a secrets manager (HashiCorp Vault, AWS Secrets Manager, cloud KMS-backed stores). Kubernetes Secrets are only base64 unless you enable encryption at rest and tight RBAC; many teams sync from an external manager.
  • Access: the workload proves its identity (IAM role, service account token), gets only the secrets it needs, ideally short-lived dynamic credentials (Vault mints a database user valid for one hour).
  • Rotate: automate, support two valid versions during the changeover so there is no downtime.
  • Detect: pre-commit and CI secret scanning; treat any leaked secret as compromised and rotate, deleting the commit is not enough.
Trap: the "secret zero" problem: something must authenticate to the vault first. Answer: use platform identity (cloud instance role, Kubernetes service account) instead of a stored bootstrap password.
What is zero trust? Intermediate

"Never trust, always verify." The old model was a hard perimeter (firewall/VPN) with a soft trusted inside; once an attacker was in, they moved freely. Zero trust assumes the network is hostile and decides per request using identity and context.

  • Strong identity for users (MFA, device posture) and for workloads (mTLS, workload identity).
  • Least privilege and short-lived credentials; per-request authorization at every service.
  • Micro-segmentation: network policies that allow only the needed service-to-service paths.
  • Encrypt all internal traffic; log and monitor everything; assume breach and limit blast radius.

It is a direction, not a product. A concrete example: replacing a corporate VPN with an identity-aware proxy that checks user, device health and app before each access.

What is least privilege and how do you apply it to a cloud service? Basic

Each identity gets only the permissions needed for its job, for only as long as needed. Examples: the thumbnail worker can read the uploads bucket and write the thumbnails prefix, not delete or read other buckets; humans get time-boxed break-glass admin with approval and audit instead of standing admin; databases have separate users for the app (DML only), migrations (DDL) and analytics (read replica). Review permissions regularly and remove unused ones (access analyzers help).

Encryption and key management

Explain encryption in transit versus at rest and what each protects against. Basic
In transitAt rest
HowTLS (HTTPS, mTLS, TLS to the DB and broker)Disk/volume, database (TDE) or object-store encryption, usually AES-256
Protects againstEavesdropping and tampering on the networkStolen disks/backups, snapshots exposed, a curious infrastructure operator
Does not protect againstA compromised endpointA compromised running app (it can read decrypted data), SQL injection, stolen app credentials

Also mention application-level (field) encryption for the most sensitive columns (card numbers, national ids) so even DBAs or a leaked database dump see ciphertext, and end-to-end encryption where only the users' devices hold keys, which prevents the provider reading content (at the cost of server-side search and recovery features).

How does TLS work at a high level, and why asymmetric plus symmetric crypto? Intermediate
  1. Client says hello with supported versions and ciphers.
  2. Server presents its certificate chain; client verifies it chains to a trusted CA, the name matches and it has not expired.
  3. They run a key exchange (ephemeral Diffie-Hellman) to agree a shared session key; the server proves possession of its private key by signing.
  4. Both switch to fast symmetric encryption (AES-GCM or ChaCha20) with that session key.

Asymmetric crypto solves "agree on a key with a stranger" but is slow; symmetric is fast but needs a shared key. Using both gets the best of each. Ephemeral keys give forward secrecy: stealing the server's long-term key later cannot decrypt recorded old traffic. TLS 1.3 needs one round trip (and zero on resumption, with replay caveats). Terminate TLS at the load balancer for convenience but re-encrypt to backends in a zero-trust design.

What is envelope encryption and why is it used? Senior

Instead of sending big data to a key service, you use two layers of keys:

  1. A data encryption key (DEK) is generated per object/file/tenant and encrypts the data locally (fast, AES).
  2. A key encryption key (KEK) held in a KMS/HSM encrypts the DEK. The encrypted DEK is stored beside the ciphertext.
  3. To read: ask the KMS to decrypt the small DEK (authorized and audited), then decrypt the data locally.

Benefits: the master key never leaves the HSM; only small payloads cross the network; rotating the KEK means re-wrapping DEKs (cheap) instead of re-encrypting terabytes; per-tenant DEKs allow crypto-shredding. Cloud object stores and databases use exactly this internally.

How do you manage and rotate encryption keys? Senior
  • Generate and keep keys in a KMS/HSM (cloud KMS, Vault transit, hardware module); the application asks it to encrypt/decrypt or to unwrap DEKs, and never holds the root key.
  • Separate duties: who can administer keys differs from who can use them; log every use.
  • Rotate on a schedule and on suspicion. Tag ciphertext with a key version so old data stays readable; new writes use the new version; lazily or in batch re-encrypt old data when policy demands.
  • Backup and DR: losing the key means losing the data; replicate keys across regions in a controlled way.
  • Customer-managed keys (BYOK/HYOK): enterprise customers hold or can revoke the key; revoking it makes their data unreadable. Costs availability dependency on the customer's key service.

Crypto-shredding: to "delete" data in backups and replicas, destroy the per-user or per-tenant key. The ciphertext that remains is unreadable. Useful for GDPR erasure.

Common attacks and design-level defences

What is injection (SQL and others) and how do you design against it? Basic

Untrusted input is interpreted as code. Example: "SELECT * FROM users WHERE name = '" + input + "'" with input ' OR '1'='1 returns every row. Same family: NoSQL, OS command, LDAP, template and log injection.

  • Parameterized queries / prepared statements keep data and code separate. ORMs do this by default, but raw string concatenation inside them is still vulnerable.
  • Validate input against an allowlist (type, length, format) as defence in depth, not as the main defence.
  • Least privilege DB accounts (no DROP, no access to other schemas), so a successful injection has limited impact.
  • Never build shell commands from user input; use library calls with argument arrays.
What is XSS, and what are the defences? Intermediate

Cross-site scripting: attacker-supplied script runs in a victim's browser in your site's origin, so it can read the page, act as the user and steal non-HttpOnly tokens. Types: stored (a comment saved in the DB and shown to others), reflected (in a link parameter echoed back), DOM-based (client code writes untrusted data into the page).

  • Output encoding in the right context (HTML, attribute, JS, URL); modern frameworks (React, Angular) escape by default, so be wary of their "render raw HTML" escape hatches.
  • Content Security Policy to restrict which scripts may run (no inline scripts, nonce-based).
  • HttpOnly cookies; sanitize rich text with a vetted library using an allowlist.
  • Treat user-uploaded HTML/SVG as hostile; serve user content from a separate domain.
What is CSRF and how do you prevent it? Intermediate

Cross-site request forgery: the victim is logged into bank.com; a malicious page makes their browser send POST bank.com/transfer. The browser attaches the cookie automatically, so the server thinks the user did it. It exploits automatic credential sending, so it matters for cookie-based auth (not for tokens in an Authorization header set by your own JS).

  • SameSite cookies (Lax or Strict) stop cookies on most cross-site requests.
  • Anti-CSRF token (random value in the page or double-submit cookie) required on state-changing requests.
  • Check Origin/Referer; use non-GET for changes (GET must be safe); require re-authentication for sensitive actions.

Contrast with XSS: CSRF abuses the browser's trust in the user's cookies; XSS abuses the user's trust in the site.

What is SSRF and why is it dangerous in cloud systems? Senior

Server-side request forgery: the attacker makes your server fetch a URL of their choosing (an image-from-URL feature, a webhook, a PDF renderer, an import-from-link). The server sits inside the network, so the attacker can reach internal services and, notably, the cloud metadata endpoint (169.254.169.254) which can hand out the instance role's credentials. The 2019 Capital One breach is widely reported to have involved SSRF against a misconfigured web application firewall to obtain cloud credentials (details per public reporting).

  • Allowlist destination hosts where possible; otherwise resolve DNS yourself, block private, loopback and link-local ranges, and connect to the resolved IP (defeats DNS rebinding); do not follow redirects blindly.
  • Run fetchers in an isolated network segment with egress controls and no sensitive IAM role.
  • Use the hardened metadata version (IMDSv2 on AWS requires a session token header) and minimal instance roles.
How do you defend a system against DDoS? Senior

Layers of attack, layers of defence:

  • Volumetric (L3/L4: SYN floods, UDP/amplification): absorb at a huge edge: CDN or anycast network and a scrubbing provider; your own servers cannot out-bandwidth it. Hide origin IPs and accept traffic only from the CDN.
  • Protocol: SYN cookies, connection limits, timeouts (slowloris defence).
  • Application (L7: expensive endpoints, login, search): WAF rules, bot detection and challenges, per-IP/per-key/per-user rate limits, caching, request cost limits, queueing and load shedding.
  • Resilience: autoscaling (with a ceiling so an attack cannot bankrupt you), graceful degradation (serve cached or read-only), runbook and a way to contact upstream providers fast.

Autoscaling alone is a trap: you pay for the attacker's traffic and may overload the database behind it. Protect the shared, hard-to-scale resource.

What is a replay attack and how do you defend against it? Intermediate

The attacker captures a valid request (a signed payment webhook, an auth message) and sends it again. The signature is still valid, so naive verification accepts it.

  • Timestamp + short validity window inside the signed data (reject if older than, say, 5 minutes).
  • Nonce / unique id remembered for the window (Redis set with TTL); reject duplicates.
  • Idempotency keys on payments so a replay (or a genuine retry) does not double-charge.
  • TLS prevents capture on the wire; short-lived tokens limit reuse; sequence numbers in protocols; OIDC nonce binds an ID token to one login.

Example: Stripe-style webhooks sign the timestamp together with the body for exactly this reason.

How do rate limiting and abuse prevention work, and what do you key the limit on? Intermediate

Goals: protect capacity (fairness, noisy neighbour), cost and security (brute force, scraping). Common algorithms: token bucket (allows bursts: bucket of N tokens refilled at R per second, each request takes one), leaky bucket (smooths to a steady rate), fixed window (simple, but a 2x burst at window edges), sliding window (accurate, more memory).

Key choice: per IP (cheap, but shared NATs punish many users and attackers rotate IPs), per user or API key (accurate once authenticated), per tenant (fair multi-tenancy), per endpoint (tighter on login and expensive search). Use several layers: coarse IP limits at the edge, finer per-key limits in the service.

Implementation: counters in Redis with atomic scripts, or local approximate limits synced periodically for speed. Return 429 Too Many Requests with Retry-After, and fail open or closed deliberately if the limiter store is down (open for general APIs, closed for login). Beyond limits: CAPTCHA, proof-of-work, account lockout with care (lockout itself becomes a DoS lever), anomaly detection, and tiered quotas.

Scenario: login traffic spikes 50x at 3 a.m. and many accounts report suspicious activity. What do you do? Senior
  1. Confirm: failure ratio on /login, distinct IPs and user agents, passwords tried per account. Many accounts, one or two tries each, from many IPs, is credential stuffing (not brute force on one account).
  2. Contain: tighten per-IP and per-account rate limits, turn on bot challenges for suspicious clients, block known bad ASNs/IPs at the WAF, temporarily require MFA or step-up for logins from new devices.
  3. Protect victims: force reset for accounts with successful logins from the attack pattern, revoke their sessions and refresh tokens, notify users.
  4. Prevent: breached-password screening, MFA/passkeys, device fingerprint risk scoring, uniform error messages (do not reveal which accounts exist).
  5. Review: post-mortem and alerts on login failure rate.
Scenario: an engineer pushed a cloud access key to a public repository an hour ago. What now? Intermediate
  1. Revoke or rotate the key immediately. Do this before cleaning history; bots scrape new commits within minutes.
  2. Audit what the key did since the push (cloud audit logs): unknown instances, new users, data reads, unusual regions.
  3. Remove any resources or persistence the attacker created, rotate anything the key could read.
  4. Clean the repository (history rewrite helps but assume the secret is burned).
  5. Prevent: pre-commit and CI secret scanning, short-lived credentials via roles so there is no long-lived key to leak, least privilege, billing alerts.

Privacy, compliance and multi-tenancy

What is PII and what does GDPR mean for system design? Intermediate

PII is data that identifies a person alone or combined: name, email, phone, IP address, device id, location, government id; special categories (health, biometrics, religion) get stricter rules. GDPR (EU) applies when you handle data of people in the EU, wherever you are.

Design consequences:

  • Know where PII lives: a data inventory/catalog; classify fields; keep it in few well-guarded places and reference by internal id elsewhere (pseudonymization).
  • Data minimization and retention: collect only what you need; give every dataset a retention period and an automated purge.
  • User rights: access/export, rectification, erasure ("right to be forgotten"), restriction, portability, objection; usually within about one month.
  • Lawful basis and consent: store consent records and honour withdrawal.
  • Security and breach notification: encryption, access control, and notify the authority within 72 hours of becoming aware of a qualifying breach.
  • Privacy by design: default to the most private setting; keep PII out of logs, analytics and URLs.
How do you implement "delete my data" across a distributed system? Senior

Hard part: the user's data is in the primary DB, caches, search index, data warehouse, event logs (Kafka), backups, logs, third-party processors and ML features.

  1. Map the data (inventory) and give each store an owner and a delete handler.
  2. Orchestrate: a deletion request becomes an event or workflow; each service deletes or anonymizes its data and acks; track status and retry until all complete, with an audit record (which stores a deletion hit, without keeping the PII itself).
  3. Soft delete with a grace period (e.g. 30 days to allow account recovery), then hard delete.
  4. Immutable stores: append-only logs and backups cannot be edited cheaply. Use crypto-shredding (per-user key destroyed), short retention, tombstone events plus compaction, and let backups age out, with documentation that restored backups must re-apply the deletion list.
  5. Exceptions: legal retention (tax records, fraud) may override erasure; keep only what the law requires and restrict it.
What is data residency and how does it affect architecture? Senior

Some laws or customer contracts require that data about citizens or tenants stays in a country or region (EU, Germany, India, and so on), or restrict transfers abroad. Architecture implications:

  • Regional cells/stacks: a tenant is pinned to a home region at signup; its database, object storage, search index, queues and backups all live there. A thin global layer holds only non-personal routing data (tenant to region map).
  • Routing: the edge/global router sends each request to the tenant's region; avoid cross-region calls that carry PII.
  • Hidden leaks: logs, metrics, traces, analytics pipelines, support tools, CDN caches, backups and DR replicas that quietly copy data to another region. Plan DR inside the allowed geography.
  • Trade-offs: more operational cost (N deployments), harder global features (cross-region search, global analytics must use aggregated or anonymized data), and moving a tenant between regions becomes a migration project.
What makes a good audit log, and how does it differ from application logging? Intermediate

An audit log records who did what to which resource, when, from where, and with what outcome for security and compliance, e.g. "user 42 exported customer list 9 from IP x at T, success". Application logs are for debugging and may be sampled or dropped; audit logs must be complete.

  • Content: actor (user and service identity), action, target, before/after for changes, result, request/trace id, source IP and device. No secrets or full PII payloads.
  • Integrity: append-only, write-once (WORM) storage, hash chaining or signing, separate permissions so admins cannot silently edit; ship to a separate account.
  • Reliability: write transactionally with the action (or via an outbox) so an action cannot happen without its record; no sampling.
  • Retention and access: retention per regulation (often one to seven years), searchable, access to the log itself is audited.

Common answer: a tiered approach, pooled for small tenants and dedicated for big/regulated ones, with the same code and a tenant router.

Defence in depth for the shared model: take tenant id from the verified token, never from the request body; apply it automatically in the data layer (ORM filter, or database row-level security policies) instead of in each query; tenant-scoped cache keys and queue topics; per-tenant encryption keys; automated tests that try cross-tenant access; per-tenant audit logs.

What is the noisy neighbour problem and how do you handle it? Intermediate

One tenant's heavy use (a bulk import, an expensive report, a viral customer) consumes shared CPU, DB connections, cache or queue throughput, and every other tenant slows down. It is the main operational risk of shared infrastructure.

  • Per-tenant quotas and rate limits on API calls, concurrent requests, storage and job size.
  • Bulkheads: separate thread pools, connection pools and queues per tier or tenant so one cannot exhaust the shared pool.
  • Fair scheduling: weighted fair queues, per-tenant concurrency caps for background jobs; shuffle sharding limits how many tenants one bad actor can hit.
  • Isolate heavy tenants: move them to dedicated shards or cells.
  • Observe per tenant: metrics and top-N dashboards by tenant id (careful with cardinality, see below), alerts on a tenant exceeding its share.
  • Throttle gracefully with 429 and backoff hints; shed low-priority work first.
Scenario: a customer reports seeing another customer's data in your multi-tenant app. What do you do? Senior
  1. Treat as a security incident (Sev1): assemble incident team, involve security and legal early since it may be a reportable breach.
  2. Contain: disable the affected feature or endpoint with a feature flag or roll back the last deploy; if unknown, restrict the suspect path. Preserve evidence (logs, request ids) before they rotate.
  3. Find the cause: common culprits are a cache key without the tenant id, a missing tenant filter in a new query, a thread-local tenant context not cleared in a reused thread, a shared mutable singleton, or an async job that lost its tenant context.
  4. Scope: use audit logs to find which tenants and records were exposed and for how long.
  5. Notify affected customers and regulators per obligations (GDPR 72 hours).
  6. Prevent: central enforcement (row-level security, mandatory tenant scope in the data layer), cross-tenant tests in CI, tenant id in every cache key, and a post-mortem.

Observability: logs, metrics, traces

What is observability and how is it different from monitoring? Basic

Monitoring checks known failure modes: "is CPU above 90%?", "is the health check passing?". Observability is the ability to ask new questions about a running system from its outputs, without shipping new code: "why are requests from tenant X in region Y slow only on Tuesdays?". You need rich, high-detail telemetry (logs, metrics, traces) and the means to slice it. Monitoring tells you something is wrong; observability helps you work out why, especially for unknown-unknowns in distributed systems.

What is structured logging and why does it matter? Basic

Write logs as machine-readable key/value records (usually JSON) instead of free text.

{"ts":"2026-11-17T10:02:11Z","level":"ERROR","service":"checkout","env":"prod",
 "trace_id":"4bf92f35...","tenant":"t-81","order_id":"o-9912",
 "msg":"payment declined","err_code":"CARD_DECLINED","latency_ms":412}

Benefits: filter and aggregate by field ("count by err_code"), join with traces, consistent schema across services, no brittle regex parsing. Rules: stable field names, levels used consistently (ERROR means someone should look), one event per line, no secrets or PII, log at boundaries (request in/out, external calls, failures) rather than in tight loops, include enough context to act, and log an error once at the place it is handled instead of at every layer.

What are correlation ids and trace ids, and how do they propagate? Intermediate

A unique id created at the edge for each request and passed to every downstream call, so all logs and spans of one user request can be found together.

  • Propagation: HTTP header (W3C Trace Context traceparent: 00-<trace-id>-<span-id>-01, or X-Request-Id), message headers in Kafka/queues, gRPC metadata. Each service reads it, adds it to its log context (MDC in Java) and forwards it.
  • Async gaps: thread pools, queues and scheduled jobs lose context unless you copy it explicitly. Instrumentation libraries (OpenTelemetry) handle most of it.
  • Return it to the user in error responses or a header so support can quote "request id abc" and engineers find the exact trace.

Trace id is the whole journey; span id is one hop within it; a business correlation id (order id) may also be logged to join across several separate requests.

How does distributed tracing work? Intermediate

Each unit of work is a span with a name, start, duration, status, attributes and a parent span id. The trace id and parent id travel in headers; every service reports its spans (usually asynchronously through an agent or collector) to a backend (Jaeger, Tempo, Zipkin, vendor APM) which assembles the tree. Uses: find the critical path, spot sequential calls that could be parallel, N+1 calls, retries, and which dependency causes errors. OpenTelemetry is the vendor-neutral standard for the APIs, SDKs, wire format (OTLP) and collector.

Why sample traces, and what are head-based and tail-based sampling? Senior

Tracing every request at high traffic is costly in CPU, network and storage. Sampling keeps a fraction.

  • Head-based: decide at the first span (e.g. keep 1%); the decision is propagated so a trace is whole or absent. Cheap and simple; but you may drop exactly the rare slow or failing requests you care about.
  • Tail-based: collect all spans temporarily in a collector, then decide once the trace completes: keep all errors, all traces slower than a threshold, plus a small random baseline. Much better signal; needs a stateful collector layer that buffers spans (memory) and routes all spans of a trace to the same instance.
  • Other tools: always sample specific tenants or debug flags, lower rates for health checks and noisy endpoints, and use exemplars (a trace id attached to a metric bucket) so a latency spike links to a real trace.

Say what you give up: statistics from sampled traces must be scaled; accurate counts and rates come from metrics, not traces.

What types of metrics exist (counter, gauge, histogram) and why are percentiles better than averages? Intermediate
  • Counter: only goes up (requests_total, errors_total); you graph its rate.
  • Gauge: goes up and down (queue depth, memory in use, active connections).
  • Histogram: counts observations in buckets (latency) so you can compute p50/p95/p99 and aggregate across instances. Summaries computed per instance cannot be averaged correctly.

Why percentiles: averages hide the tail. If 99 requests take 100 ms and one takes 10 s, the mean is 199 ms, which looks fine, while 1% of users wait 10 s. With fan-out, tail latency amplifies: if a page makes 100 backend calls, about 63% of pages hit at least one p99 slow call (1 minus 0.99 to the power of 100). Alert and set SLOs on p95/p99, not the average. Measure at the client or load balancer too, to avoid coordinated omission (a stalled server not recording the requests it never received).

What are the RED and USE methods? Intermediate
MethodForMeasures

RED describes the experience of the callers; USE finds the bottleneck resource behind it. Start from RED ("checkout p99 is up"), drill down with USE ("DB connection pool saturated: 50 of 50 busy, 200 waiting"). Saturation is the early warning that utilization alone misses.

What are the four golden signals? Basic

From Google's SRE book: latency (time to serve, tracking successful and failed requests separately, since a fast error hides in the average), traffic (demand: requests/s, sessions), errors (explicit 5xx, wrong content, and policy errors such as "slower than 1 s counts as failed"), saturation (how full the most constrained resource is). If you can only watch four things per service, watch these. They are RED plus saturation.

What is the cardinality problem in metrics? Senior

A metric's cost is the number of unique label combinations (time series). http_requests{service, route, status} with 20 services, 50 routes and 5 statuses is 5,000 series: fine. Add user_id (10 million values) and you ask for billions of series: the metrics server runs out of memory, queries crawl, and vendors bill per series.

  • Never use unbounded values as labels: user id, email, request id, full URL with ids, error message text, trace id. Use the route template /orders/{id}, not /orders/123.
  • Bound label sets (status class, region, tier); put high-cardinality detail in logs or traces, which are designed for it.
  • Per-tenant metrics for the top N tenants only, or tiers, or use an events/columnar store built for high cardinality.
  • Watch the series count itself and alert on growth; drop or relabel at the collector; histograms multiply series by bucket count, so keep buckets modest.
Log volume is exploding and the logging bill doubled. How do you reduce cost without going blind? Senior
  1. Find the biggest producers (volume by service, level and message pattern). Usually a few lines produce most of it.
  2. Fix levels: DEBUG off in production by default (dynamic switch per service for troubleshooting); remove per-item loop logging and log-and-rethrow duplicates; health check access logs excluded.
  3. Sample successful, repetitive events (log 1 in 100 normal requests, keep 100% of errors and slow requests).
  4. Convert to metrics: if you only count or aggregate something, emit a counter instead of millions of lines.
  5. Tier storage: 7 to 14 days hot and searchable, then cheap object storage with slower query, then delete per retention policy; compress and drop unused fields.
  6. Route by value: audit and security logs retained long; debug logs short; do not send everything to the most expensive index.
  7. Guardrails: per-service volume quotas and alerts on sudden growth.

Keep in mind that the failure you need to debug is often the one you sampled away, so keep errors and tail-latency events unsampled.

How do you keep sensitive data out of logs and telemetry? Intermediate

Logs are copied widely, retained long and read by many people, so a password or card number in a log is a breach. Controls: never log request bodies or auth headers by default; allowlist what is logged rather than blocklist; mask or tokenize at the logger (field-level redaction for known keys: password, token, authorization, ssn); use ids not names or emails; scrub at the collector as a second net; scan logs for patterns in CI or periodically; restrict access to production logs and audit it; set short retention for anything that may contain personal data.

What makes a good dashboard? Intermediate
  • Answer a question. A service overview dashboard answers "is it healthy right now?": the golden signals at the top, then dependencies, then resources. A separate one for deep dives.
  • Hierarchy: top-level business and SLO view (orders per minute, error budget left), then per-service, then per-component, with links between them.
  • Show percentiles, rates and ratios, not just raw counts; add deploy markers and feature flag changes as annotations so you can see cause and effect.
  • Compare to the past (same time last week) since many metrics are seasonal.
  • Avoid walls of 60 graphs, unlabeled axes, averages only, and dashboards no one owns. A dashboard that nobody opens during incidents should be deleted.
Scenario: users say checkout got slow. Walk through how you investigate using observability data. Senior
  1. Scope it: RED dashboard for checkout: since when, which percentile, which endpoints, region, tenant or client version. Check deploy and feature flag markers around the start time.
  2. Find the hop: open a few slow traces (or tail-sampled ones). Which span grew? Suppose payment-svc to the external processor went from 240 ms to 3 s.
  3. Check the dependency and resources with USE: connection pool saturation, thread pool queue, CPU throttling, GC pauses, DB slow query log, replication lag.
  4. Read logs for the affected trace ids: timeouts, retries (a retry storm can multiply load), circuit breaker state.
  5. Mitigate before root cause: roll back the suspect change, flip the flag, fail over, scale out, or shed load; announce status.
  6. Confirm recovery in the SLI, then write the timeline for the post-mortem.
Say: "Mitigate first, diagnose second: the goal during an incident is to restore the user experience, not to find the elegant root cause."

SLIs, SLOs and alerting

What are SLI, SLO and SLA? Give a concrete example. Basic
  • SLI (indicator): a measured number about user experience, e.g. "fraction of checkout requests that return success in under 500 ms".
  • SLO (objective): the internal target for the SLI over a window, e.g. "99.9% over 30 days".
  • SLA (agreement): the contract with customers, with consequences (credits) if missed, e.g. 99.5%. SLA is looser than the SLO so you notice trouble before you owe money.
SLOAllowed downtime per 30 days
99%about 7.2 hours
99.9%about 43 minutes
99.99%about 4.3 minutes

Pick SLIs from the user's view (availability, latency, correctness, freshness, durability), measured at the edge, not CPU. Each extra nine costs far more and is limited by your dependencies: if you call three services at 99.9% in series, you are capped near 99.7%.

What is an error budget and how does it change behaviour? Intermediate

Budget = 100% minus the SLO. A 99.9% monthly SLO leaves 0.1% (about 43 minutes, or 1 in 1,000 requests) that may fail. It makes reliability a shared, measurable resource: while budget remains, the team ships features and takes calculated risks; when it is spent, the team slows releases and works on reliability until it recovers. This replaces arguments between "ship faster" and "be safe" with data. Budgets also justify pausing risky experiments and decide which toil to automate.

How do you design alerting that does not page for noise? Senior
  • Page on symptoms, not causes. Page when users are hurt or the error budget is burning ("checkout error rate above SLO"), not when CPU is 85% or one pod restarts. Causes go on dashboards or tickets.
  • Every page must be urgent, actionable and needs a human now. If the answer is "wait and see", make it a ticket or a daily report.
  • Multi-window, multi-burn-rate alerts on the SLO. Burn rate is how fast you consume the budget (1x = exactly on target for the window). A common recipe from the SRE workbook: page when burn rate is about 14x over both 1 hour and 5 minutes (about 2% of a 30-day budget gone in an hour), ticket for about 6x over 6 hours, and so on. The long window avoids flapping; the short window makes the alert clear quickly after recovery.
  • Duration/"for" clauses, hysteresis and aggregation so a single blip or one bad host does not page.
  • Dedupe and group: one incident should produce one page, not 200 (alert grouping, dependency-aware suppression: do not page about 50 services when the database is down).
  • Runbook link and context in every alert; severity levels with different routes (page, chat, ticket).
  • Hygiene: review alerts after each on-call week; delete or fix any that fired without action; track pages per shift (a common target is at most about two incidents per 12-hour shift).
  • Alert on absence of data (dead-man's switch) so a broken pipeline is not read as "all green".
Why is "CPU above 80% for 5 minutes" often a bad page? Intermediate

High CPU may be perfectly healthy (efficient use, autoscaler will react) and users see nothing wrong. Conversely, an outage can occur with low CPU (a deadlock, a bad dependency, a full connection pool). It pages on a cause that may not matter and misses ones that do. Use it as a diagnostic graph or a low-urgency capacity ticket, and page on the SLI instead. Exception: resources with hard cliffs that give no warning and no automatic remedy, such as disk filling up in two hours or certificate expiry in 7 days, deserve predictive alerts.

Black-box versus white-box monitoring, and what are synthetic checks? Intermediate

White-box: uses internal metrics the service exposes (queue depth, error counters); finds impending problems and causes. Black-box: tests from outside like a user would; finds what is actually broken as users see it, including DNS, CDN, certificates and network problems your internal metrics cannot see. Synthetic checks (probes) run scripted user journeys (log in, add to cart, check out) from several regions every minute; essential for low-traffic paths and off-peak hours, where no real traffic exists to reveal a break. Use both: black-box to detect, white-box to diagnose.

On-call, incident response and post-mortems

How is a well-run incident handled from page to resolution? Intermediate
  1. Detect and acknowledge: alert reaches on-call; ack within minutes.
  2. Triage and declare: set severity (Sev1 = major user impact). Open an incident channel and name roles.
  3. Roles: incident commander (coordinates, decides, does not debug), operations/tech lead (hands on), communications lead (status page, stakeholders), scribe (timeline).
  4. Mitigate first: roll back, flip a flag, fail over, scale, shed load, block bad traffic. Fix root cause later.
  5. Communicate on a regular cadence (every 15 to 30 minutes) even if nothing changed.
  6. Resolve and verify against the SLI; stand down.
  7. Post-mortem within days; track action items to completion.
What is a blameless post-mortem and what goes in it? Intermediate

A written review focused on how the system and process allowed the failure, not on who made the mistake. People who fear blame hide information; people who are safe tell the truth, so you learn more and the same class of failure is prevented. Typical contents: summary and impact (duration, users, money, SLO budget used), timeline with timestamps, detection (how long until we knew?), root cause and contributing factors (a "five whys" style analysis or a causal chain, rarely a single cause), what went well and badly, where we got lucky, and action items with owners and due dates, split into prevent, detect and mitigate. If actions are not tracked and done, the post-mortem is theatre.

Key time metrics: MTTD (detect), MTTA (acknowledge), MTTR (restore). Improving detection and mitigation speed usually pays more than chasing zero failures.

How do you keep on-call sustainable? Intermediate
  • Weekly rotation with a primary and a secondary; follow-the-sun across time zones where possible so nobody is paged at 3 a.m. routinely; compensation or time off in lieu.
  • A runbook per alert and a clear escalation path; handover notes between shifts.
  • Limit noise (see alert design) and measure it: pages per shift, off-hours pages, repeated alerts. Dedicate engineering time to removing toil and recurring pages.
  • Rotation size of about 6 to 8 people so each is on call roughly every 6 to 8 weeks; "you build it, you run it" keeps developers close to the pain.
  • Game days and drills for new joiners (shadow, then reverse-shadow).
Name real outages that teach design lessons. Senior

Hedged to the headline of public post-mortems:

  • AWS S3, US-East-1, February 2017: an operator command during debugging removed more servers than intended; dependent subsystems had to restart and took hours; many sites that relied on S3 (and even the AWS status page's own assets) were affected. Lessons: guardrails and minimum-capacity limits on dangerous commands, blast-radius limits, do not host your status page on the thing that is down.
  • GitLab database incident, January 2017: an engineer removed the wrong database directory while repairing replication; several backup mechanisms turned out not to work. Lessons: test restores, not just backups; careful operations during stress; transparent post-mortem.
  • Cloudflare, July 2019: a regular-expression in a WAF rule caused catastrophic backtracking and pegged CPUs worldwide. Lessons: staged rollouts for config too, resource limits on rule evaluation, a global kill switch.
  • Facebook, October 2021: a routine backbone configuration change withdrew the BGP routes to its DNS servers, taking apps offline for hours; internal tools and badge access depended on the same network, which slowed recovery. Lessons: out-of-band access, audit tooling that validates changes, avoid recovery depending on the thing that is broken.
  • CrowdStrike, July 2024: a faulty content update to a security agent crashed a large number of Windows machines worldwide. Lessons: staged/canary rollout even for "content" updates, validation, and the ability to recover without per-machine manual work.
  • Knight Capital, 2012: a partially deployed trading software update left old code active on one server and caused large losses in under an hour. Lessons: consistent, automated deployments, removing dead flags, kill switches.

Common themes: config changes are as dangerous as code, rollouts need to be gradual, recovery paths must not share failure domains with the system, and untested backups are not backups.

CI/CD, configuration and safe rollouts

What does a CI/CD pipeline for a service look like? Basic

Continuous integration: every commit is built and tested automatically and merged to trunk often (small changes, short-lived branches). Continuous delivery: every merged change produces a deployable artifact and can go to production at the push of a button. Continuous deployment: it goes to production automatically when checks pass.

  1. Commit and review; lint, unit tests, static analysis, dependency and secret scans.
  2. Build one immutable artifact (container image tagged with the commit sha), sign it, push to a registry. Build once, promote the same artifact through environments.
  3. Deploy to staging; integration and contract tests, smoke tests.
  4. Progressive production rollout (canary), automated health checks against SLIs, automatic rollback on regression.
  5. Post-deploy verification and a deploy marker on dashboards.

Principles: fast feedback (under about 10 minutes for the main checks), reproducible builds, the pipeline as code, deploys that are boring and frequent (small diffs are easier to debug and roll back). Track the DORA metrics: deployment frequency, lead time for changes, change failure rate, time to restore.

How do you manage configuration across environments? Intermediate
  • Separate config from code (twelve-factor): the same artifact runs everywhere; environment supplies values (env vars, mounted files, a config service).
  • Versioned and reviewed: config in git (GitOps) with code review, history and rollback. Secrets go to a secrets manager, not git.
  • Validate: typed schema, validation at startup (fail fast on a bad value), and in CI.
  • Dynamic vs static: values that need no restart (timeouts, flags, limits) are watched from a config service; structural ones (ports, DB URLs) change with a deploy.
  • Roll out config like code: staged, with canary and a quick revert. Many large outages (see incidents above) come from config pushes, not code.
  • Keep environment differences small and explicit to avoid "works in staging".
What are feature flags and what are the pitfalls? Intermediate

A flag is a runtime switch that turns behaviour on or off without a deploy, evaluated per user, tenant, percentage or region. It decouples deploy from release: code ships dark, then is exposed gradually.

Uses: gradual rollout (1%, 10%, 50%, 100%), kill switch for a risky feature, A/B tests, per-customer entitlements, trunk-based development of unfinished work, ops flags to shed load (turn off recommendations in an incident).

Pitfalls:

  • Flag debt: old flags left in code multiply paths and bugs; give each release flag an owner and an expiry and delete after rollout. (Knight Capital is the cautionary tale of repurposed old flags.)
  • Combinatorial testing of flag states; keep the number of live flags small and independent.
  • Flag service as a dependency: evaluate locally from a cached ruleset with a safe default when the service is down.
  • Consistency: a user should see a stable variant (hash of user id), and flags in distributed calls must agree across services.
  • Audit who changed which flag and when; changing a flag is a production change.

When should you roll back versus roll forward? Intermediate

Default to rollback during an incident if the deploy is the likely cause and it is reversible: it is the fastest, best-understood action. Roll forward (a quick fix) when rollback is unsafe: a database migration already dropped or reshaped data the old code needs, new data has been written in a format the old code cannot read, or the fix is a one-line trivial change that can ship through the fast pipeline. To keep rollback possible, make changes backward compatible, keep migrations expand/contract, use flags to disable behaviour without redeploying, and rehearse rollbacks. Automated canary analysis that rolls back on SLI regression removes the human delay.

How do you change a database schema with zero downtime? Senior

Use the expand and contract (parallel change) pattern so old and new code both work at every step. Example: rename column name to full_name.

  1. Expand: add nullable full_name (no data rewrite, no long lock).
  2. Deploy code that writes both columns and still reads the old one.
  3. Backfill old rows in small batches (throttled, resumable) so you do not saturate the primary or replication.
  4. Deploy code that reads the new column (compare results with shadow reads if risky).
  5. Stop writing the old column, deploy, wait through a safe period.
  6. Contract: drop the old column in a later release.
  • Dangerous operations: adding a column with a default, creating an index, or adding a constraint can lock a big table in some engines; use online or concurrent variants (for example CREATE INDEX CONCURRENTLY in PostgreSQL, online schema change tools such as gh-ost or pt-online-schema-change for MySQL) and check your engine version's behaviour.
  • Run migrations as a separate step from app deploy, version them (Flyway, Liquibase) and keep them forward-only in prod.
  • Never combine a breaking schema change and the code change in one deploy; always ensure N and N+1 are compatible.
  • Test on production-sized data, take a backup or snapshot first, and set lock timeouts so a stuck migration fails fast instead of blocking everything.
How do you keep services and messages compatible during rolling deploys? Senior

During a rollout (and rollback) old and new versions talk to each other. Rules: add, never remove or repurpose fields; make new fields optional with defaults; consumers ignore unknown fields (tolerant reader); deploy consumers before producers when adding a field, and stop producing a field before removing it from consumers; version APIs and events (schema registry with compatibility checks for Avro/Protobuf in CI); use consumer-driven contract tests; for breaking changes publish a new version and run both until traffic drains. The same discipline applies to cache entry formats and queued messages that outlive a deploy.

Scenario: 10 minutes after a deploy the error rate climbs from 0.1% to 4%. What do you do? Intermediate
  1. Check the deploy marker against the start of the climb. Correlated? Roll back immediately (or flip the new feature's flag off) and post in the incident channel; do not wait to understand.
  2. Confirm the SLI recovers. If not, the deploy was not the cause: widen the search (dependency, traffic spike, expired certificate, config push, cloud provider status).
  3. Collect evidence from the bad version (logs, a heap dump, a canary instance kept out of rotation) before it vanishes.
  4. Find the cause offline, add a test that would have caught it, and ask why the canary or pre-prod did not (not enough traffic? different data? config drift?).
  5. Improve: automated canary analysis with auto-rollback so the next one is stopped at 1% of traffic.
Trunk-based development versus long-lived branches, and why does it matter for delivery? Intermediate

Trunk-based: engineers merge small changes to the main branch at least daily, hiding unfinished work behind flags. Merge conflicts stay small, integration problems show up early, and main is always releasable. Long-lived feature or release branches delay integration; the "big bang" merge is risky and the time between writing code and learning it fails grows. High-performing teams in the DORA research tend to practise trunk-based development with a fast pipeline.

Capacity, autoscaling, cost and infrastructure as code

How do you do capacity planning? Intermediate
  1. Model demand: current peak and average rates, growth trend, seasonality and known events (sales, launches); use peak, not average, with headroom (often 30 to 50%).
  2. Know per-unit capacity: load test one instance to its knee (the point where latency rises sharply), e.g. 800 req/s per instance at p99 under 200 ms. Run at 60 to 70% of that, not 100%.
  3. Compute: peak 20,000 req/s with 70% target of 800 gives about 36 instances, plus N+1 or N+2 for failures and a zone failure (if losing one of three zones must be survivable, you need 50% over-provisioning of the remaining two to hold the whole load, so run each zone at no more than about 66% of what it can take).
  4. Find the next bottleneck: database connections, IOPS, cache memory, network, third-party limits and quotas.
  5. Review regularly, alert on saturation trends, and run load and failure tests (including a regional failover) before the big event.

Back-of-envelope numbers (QPS, storage per day, bandwidth) are what interviewers expect; state assumptions.

How does autoscaling work and what can go wrong? Intermediate

Reactive: add or remove instances based on a metric: CPU, memory, request rate per instance, queue depth, or a custom SLI (Kubernetes HPA, cloud auto scaling groups, KEDA for event-driven). Scheduled: scale ahead of known peaks. Predictive: forecast from history. Scale-out is usually quick and eager, scale-in slow and cautious (cooldowns) to avoid flapping.

Failure modes:

  • Too slow: a new instance takes minutes to boot and warm caches; a spike hits before capacity arrives. Fixes: scale on leading indicators (queue depth, rate), keep headroom, pre-warm, smaller images, fast startup.
  • Wrong metric: CPU is meaningless for an IO-bound service waiting on a database.
  • Scaling the wrong tier: adding web nodes floods an unscalable database; scale-out of the front moves the bottleneck down and can cause a cascading failure. Use connection pooling limits, backpressure and load shedding.
  • Flapping from tight thresholds; cost blow-ups from runaway scale (set max limits, budgets and alerts), and attack traffic triggering scale (see DDoS).
  • Stateful services scale poorly: they need rebalancing, shard moves or leader election.
  • Also scale vertically where sensible, and remember quotas and capacity availability in the cloud zone.
What are load shedding and backpressure, and how do they protect a service? Senior

When demand exceeds capacity, a service that accepts everything gets slower for everyone, then collapses (queues grow, timeouts cause retries, retries add load: a metastable failure). Load shedding deliberately rejects some requests early and cheaply (503/429) so the rest succeed: prefer dropping low-priority, expensive or already-late work (a request that has waited longer than the client timeout is worthless). Backpressure pushes the limit upstream: bounded queues, blocking or rejecting producers, and clients that slow down with exponential backoff plus jitter. Pair with timeouts, circuit breakers and retry budgets so retries cannot exceed, say, 10% extra load.

What is FinOps and how do you reduce cloud cost? Intermediate

FinOps is the practice of making cloud spend visible and a shared engineering responsibility: inform (who spends what), optimize, operate (continuous). The unit that matters is cost per unit of value (per 1,000 requests, per tenant, per order), not the total bill.

  • Visibility: tag or label resources by team, service and environment; show cost per service and per tenant; budgets and anomaly alerts.
  • Rightsize: many instances run at under 20% utilization; match size to the load. Turn off dev and test environments overnight; delete orphaned volumes, snapshots and idle load balancers.
  • Pricing models: on-demand for spiky work; commitments (reserved capacity, savings plans) for the steady baseline; spot/preemptible instances for fault-tolerant batch and stateless workers (at large discounts, but they can be reclaimed on short notice).
  • Architecture: cache and CDN to cut compute and egress; storage tiering and lifecycle rules (hot to cold to archive); compress; avoid cross-zone and cross-region data transfer, which is billed; use ARM or newer instance generations where compatible; sample and tier logs.
  • Trade-off: cost versus reliability and engineer time. Spending an engineer-month to save a few hundred dollars is a bad trade; multi-region active-active doubles cost, justify it with the SLO.
Scenario: the cloud bill jumped 40% this month with no traffic growth. How do you find out why? Intermediate
  1. Break the bill down by service type and by tag/team/day with the cost explorer: when did it start, which line item grew (compute, storage, data transfer, logging, NAT gateway)?
  2. Correlate the start date with deploys and changes: a new debug log level (log ingest), a retry loop, a job that scans too much, a cache that stopped working (more DB and compute), missing lifecycle rules on a bucket, forgotten test clusters, autoscaler stuck at high count, cross-region replication turned on.
  3. Check untagged resources: those are the usual orphans.
  4. Fix and add guardrails: budgets and anomaly alerts, per-team cost dashboards, quotas, policy that forbids untagged resources.
What is infrastructure as code and why use it? Basic

Define servers, networks, databases, permissions and so on in versioned files (Terraform/OpenTofu, Pulumi, CloudFormation, Kubernetes manifests with Helm/Kustomize) and apply them with tools, instead of clicking in a console.

  • Declarative: you describe the desired end state; the tool computes the plan (diff) and makes reality match. Review the plan like a code diff.
  • Benefits: reproducible environments (staging equals prod), code review and audit trail, fast disaster recovery (rebuild a region from code), consistent security baselines, fewer snowflake servers.
  • Practices: remote, locked state (state tells the tool what it already manages); small modules; separate state per environment/blast radius; run plan in CI and apply through a pipeline; policy-as-code checks (no public buckets); detect and fix drift (manual changes that diverge from code); never put secrets in code or state in plain text.
  • GitOps: git is the source of truth and a controller (Argo CD, Flux) continuously reconciles the cluster to it.
  • Immutable infrastructure: replace servers with new images rather than patching them in place.
What are RPO and RTO, and how do backup and DR strategies map to them? Intermediate

RPO (recovery point objective): how much data you can afford to lose, as time (RPO 5 minutes means restore to within 5 minutes before the failure). RTO (recovery time objective): how long you can be down.

StrategyRTOCost
Backup and restoreHoursLowest
Pilot light (data replicated, minimal compute)Tens of minutesLow
Warm standby (scaled-down copy running)MinutesMedium
Active-active multi-regionNear zeroHighest, plus data consistency complexity

Backups must be tested by actually restoring (a backup never restored is a hope), stored in a separate account/region and protected from deletion (immutable, protects against ransomware and operator error). Run failover drills.

What is chaos engineering and game days? Intermediate

Deliberately injecting failures (kill instances, add latency, drop a dependency, fail a zone) in a controlled way to check that the system degrades as designed and that alerts and runbooks work. Method: define steady state (SLI), form a hypothesis ("losing one cache node costs under 1% availability"), limit the blast radius, run it (staging first, then production in a small scope with a stop button), observe, fix. A game day is a scheduled team exercise of a realistic incident. It finds weak timeouts, missing retries, hidden shared dependencies and unrealistic runbooks before a real outage does.

What is the difference between liveness, readiness and startup checks, and what goes wrong with them? Intermediate
  • Liveness: is the process stuck and in need of a restart? Keep it cheap and independent of dependencies.
  • Readiness: can it serve traffic now? Fail during warm-up or when overloaded; the load balancer then stops sending requests.
  • Startup: gives slow-starting apps time before liveness begins.
Trap: a liveness check that calls the database. When the database is slow, every pod fails liveness, all restart at once, and a partial problem becomes a full outage. Likewise a readiness check that depends on a shared downstream can remove all pods simultaneously. Check local health, not the world.
