Mental model: the ideas everything hangs on

One line: security is deciding, on every request and at every layer, who is calling, what they may do, to which data, and then proving later that you decided correctly.
  1. Authenticate, then authorize. Identity is cheap to centralize; permission needs the data, so it lives in the service that owns it.
  2. Never trust input, including tokens. A token is untrusted until verified with configuration you control (algorithm, key, issuer, audience).
  3. Short-lived and narrow beats long-lived and broad. Credentials will leak; limit the window and the reach.
  4. Tenant is part of every key and every query. Isolation bugs are silent until a customer sees someone else's data.
  5. Fail closed, deny by default. New endpoints, new versions and missing context should be rejected, not allowed.
  6. Contracts are promises. Only add inside a version; retire old versions with data, not hope.
  7. Retries happen. Idempotency keys, rate limits with clear signals, and signed, replay-safe callbacks keep retries harmless.

1. Authentication, sessions, tokens and bearer credentials

What is the difference between authentication and authorization? Basic

Authentication answers "who are you?" and authorization answers "what are you allowed to do?". Authentication happens first and produces an identity. Authorization takes that identity plus the action and the resource, and returns allow or deny.

They fail differently, and that matters for status codes. A missing, expired or invalid credential is an authentication failure: return 401 Unauthorized (the name is misleading, it really means "unauthenticated") with a WWW-Authenticate header. A valid identity that lacks permission is an authorization failure: return 403 Forbidden.

A third case people forget: when a user asks for an object that belongs to someone else, you may return 404 instead of 403 so you do not confirm that the object exists. Pick one policy and apply it everywhere, otherwise the difference itself leaks information.

The practical rule: authentication can be centralized (one gateway or identity provider), but authorization needs knowledge of the data, so the service that owns the data must enforce it. A gateway can check "does this token have the scope orders:read", but only the order service knows whether order 42 belongs to this tenant.

Remember: authentication proves identity (401), authorization decides permission (403); the data owner must enforce the second.

Server-side sessions versus tokens: how do you choose? Basic

A session stores state on the server and gives the browser an opaque id in a cookie. A token carries the state inside itself, signed, so any server can verify it without a lookup. Sessions are easy to revoke; self-contained tokens scale across services but are hard to revoke before expiry.

Session: after login the server creates a record (user, roles, expiry) in memory or a store like Redis and returns a random id in a Set-Cookie header. Each request sends the cookie, and the server looks the record up. Logging out or banning a user is a delete. The cost is a lookup on every request and a shared store so any instance can serve the user.

Token (for example a JWT): the server signs a small document of claims. Any service holding the verification key can check it offline. The cost is that you cannot easily take it back: until it expires, it is valid.

My rule: browser apps on one site are well served by sessions (HttpOnly, Secure, SameSite cookie). APIs called by other services or many clients use short-lived tokens. Many real systems mix: a short access token plus a server-tracked refresh token gives most of the scale and most of the revocation.

Remember: sessions are stateful and revocable; tokens are stateless and portable, so keep them short-lived.

What is a bearer token and what are the risks of using one? Basic

A bearer token is a credential where possession is enough: whoever holds it can use it, like cash. It is sent in the header Authorization: Bearer <token>. The risk is theft, so you protect it with TLS, short lifetime, narrow scope, and never put it in URLs or logs.

The server does not check who is presenting the token, only that the token is valid. If an attacker copies it from a log file, a browser history, a proxy cache or a crash report, they are the user until it expires.

  • TLS everywhere, so it cannot be sniffed on the wire.
  • Header, not query string. URLs end up in access logs, referrer headers and browser history.
  • Short expiry (minutes) so a stolen token dies quickly, with a refresh token for longevity.
  • Narrow scope and audience, so a token stolen from one API is useless on another.
  • Redact the Authorization header in request logging and error reports.
  • Sender-constrained tokens when the risk justifies it: mTLS-bound tokens (RFC 8705) or DPoP (RFC 9449) tie the token to a key the client holds, so a copy is useless.

In a browser, where you store it matters: an in-memory variable is safer against persistent theft but lost on refresh; localStorage is readable by any script on the page (XSS); an HttpOnly cookie cannot be read by script but brings CSRF concerns.

Remember: a bearer token is cash: protect it in transit, in logs, and by keeping it short-lived and narrow.

Where should a browser app keep its tokens, and what changes between a cookie and the Authorization header? Intermediate

There is no perfect place. An HttpOnly, Secure, SameSite cookie cannot be read by JavaScript, which defends against XSS theft, but it is sent automatically so you must defend against CSRF. A token in memory or localStorage is immune to CSRF but exposed to XSS.

The two attacks are mirror images. XSS means attacker script runs on your page; it can read anything JavaScript can read, so localStorage tokens are stolen, while HttpOnly cookies cannot be read (though the script can still make requests as the user). CSRF means another site makes the browser send your cookie to your API; it needs the credential to be automatic, which header-based tokens are not.

StorageXSSCSRF
localStorage / sessionStorageToken readable, badNot affected
JS memory onlyHarder to steal, still abusable while the page livesNot affected
HttpOnly cookieCannot be readAffected: needs SameSite and a CSRF token

A common modern pattern is the backend-for-frontend: the browser holds only an HttpOnly session cookie, and a small server component holds the real access and refresh tokens and calls the APIs on its behalf. That removes tokens from the browser entirely. Whatever you pick, fix XSS with output encoding and a strict Content-Security-Policy, because XSS defeats every option in some way.

Remember: cookies trade XSS safety for CSRF risk; a backend-for-frontend keeps tokens out of the browser.

When are API keys acceptable, and how are they different from tokens? Intermediate

An API key identifies a calling application, usually with a long life and no user identity. It is acceptable for low-risk, server-to-server or quota use if it is stored hashed, scoped, rotatable and sent only over TLS. It is not a substitute for user authentication.

An API key is a long random string the provider issues to a client. It answers "which app is this?" for quota and billing, not "which user is this?". Tokens usually carry identity, scope and expiry; keys usually carry none of these, so the server looks everything up.

  • Generate with a secure random source, at least 128 bits.
  • Store only a hash on the server (plain SHA-256 is fine because the key is high-entropy; you do not need bcrypt for random keys). Show the key once at creation.
  • Give each key a scope, an owner and an expiry, and support two active keys per client so rotation has no downtime.
  • Add a visible prefix so secret scanners can find leaked keys.
  • Never put keys in URLs, mobile app binaries or front-end code.

For anything sensitive or multi-user I prefer OAuth client credentials: the client holds a secret only to obtain short-lived tokens, so a leaked access token dies in minutes rather than staying valid for years.

Remember: an API key names an application; keep it hashed, scoped and rotatable, and prefer short-lived tokens for sensitive work.

2. JWT: structure, signing, validation, refresh and attacks

What is inside a JWT and how is it verified? Basic

A JWT is three base64url parts joined by dots: header, payload (claims) and signature. The signature covers the first two parts, so any change is detected. Anyone can read a JWT; only the key holder can create a valid one. Signed does not mean encrypted.

header   = {"alg":"RS256","kid":"2026-01","typ":"JWT"}
payload  = {"iss":"https://idp.example","sub":"u-123","aud":"orders-api",
            "exp":1767225600,"iat":1767225000,"nbf":1767225000,
            "jti":"b7f...","scope":"orders:read","tenant":"t-42"}
token     = b64url(header) + "." + b64url(payload) + "." + b64url(signature)
signature = Sign(key, b64url(header) + "." + b64url(payload))

Registered claims: iss issuer, sub subject (the user or client), aud audience (who the token is for), exp expiry, nbf not-before, iat issued-at, jti unique id. Anything else (roles, tenant) is a private claim.

The payload is only encoded, not secret. Never put passwords, card numbers or personal data in it. If you need confidentiality there is JWE (encrypted JWT), but most systems keep tokens small and put sensitive data behind an API call.

Decoding a token and trusting its contents without checking the signature is the single most common JWT bug. The checks are in the next questions.

Remember: a JWT is signed, not encrypted: readable by anyone, forgeable by no one without the key.

HS256 versus RS256 and ES256: which should you use and why? Intermediate

HS256 is symmetric: one shared secret both signs and verifies. RS256 (RSA) and ES256 (ECDSA P-256) are asymmetric: a private key signs, a public key verifies. Use asymmetric whenever the verifier is a different party than the issuer, because verifiers then never hold a secret that could mint tokens.

Rule of thumb: HS256 is fine when one service both issues and verifies its own tokens and the secret is long and random (at least 256 bits). The moment a second service needs to verify, sharing an HS256 secret means that service can also forge tokens for everyone. With many microservices, use RS256 or ES256 and publish the public keys.

ES256 gives smaller tokens, which matters when tokens ride in every request header. RS256 has the widest library support. Ed25519 (EdDSA) is a modern option where supported. Whatever you choose, pin the allowed algorithm in configuration.

Remember: symmetric when one party does both jobs, asymmetric when others verify; pin the algorithm either way.

List every check you perform when validating an incoming JWT. Intermediate

Parse, check the algorithm against an allow-list, verify the signature with the right key (found by kid), then check iss, aud, exp and nbf with small clock skew, then check scopes or roles for the operation. Skipping any one creates a known attack.

  1. Structure: exactly three parts, valid base64url, valid JSON.
  2. Algorithm: compare the header alg to your configured allow-list. Never let the token choose.
  3. Signature: pick the key by kid from your trusted key set and verify.
  4. Issuer: iss must equal the one issuer you trust.
  5. Audience: aud must contain this API. Otherwise a token meant for service A works on service B.
  6. Time: exp in the future, nbf not in the future, allowing about 30 to 60 seconds of clock skew.
  7. Authorization: required scope, role and tenant for this exact operation.

Use a maintained library for all of this and configure it, rather than hand-writing parsers. In Spring this is the resource server support, which does the signature, issuer and time checks once you set the issuer or key set; you typically add an audience validator yourself because it is not enforced by default.

Remember: verify algorithm, signature, issuer, audience and time, using a maintained library.

What are the common JWT attacks and how do you prevent each? Senior

The classics are alg none, algorithm confusion, missing exp or aud checks, weak HS256 secrets, kid injection, and trusting jku or x5u URLs. All are prevented by pinning algorithms and keys in your own configuration and never letting token content decide how it is verified.

How do access tokens, refresh tokens and expiry work together? Intermediate

The access token is short-lived (minutes) and sent to APIs. The refresh token is long-lived, kept only by the client, and sent only to the authorization server to get a new access token. A leaked access token is a small window; a leaked refresh token is serious, so it is rotated and revocable.

Flow: the client logs in and gets an access token (for example 5 to 15 minutes) and a refresh token. When the access token expires, the client posts the refresh token to the token endpoint and receives a new access token, and usually a new refresh token.

Refresh token rotation. Each refresh returns a new refresh token and invalidates the old one. If an old one is ever used again, it was copied, so the server revokes the whole token family and forces a re-login. This detects theft because two parties end up racing on one token.

Why not one long access token? Because APIs verify it without a lookup, there is no revocation. Short life bounds the damage. The refresh step is a server-side check, so that is where you apply bans, password changes and session limits.

Details to state: refresh tokens should be opaque random strings stored hashed on the server, bound to a client, with an absolute lifetime and an idle timeout. Clients should refresh a little before expiry and handle the race where two tabs refresh at the same moment (a short grace window for the old token avoids false theft alarms).

Remember: short access plus rotating, server-tracked refresh tokens bounds damage and keeps revocation possible.

How do you revoke JWTs when they are stateless? Senior

You cannot unsend a signed token, so you shorten its life, keep a small deny list checked by verifiers, or ask the identity provider (introspection). In practice: short expiry plus revoking refresh tokens, plus a deny list keyed by jti or by user for emergencies.

  1. Short expiry only. Revoke the refresh token; the access token dies within minutes. Often enough.
  2. Deny list of jti or subject. Store revoked token ids (or "all tokens for user X issued before time T") in Redis with a TTL equal to the token's remaining life. Every verifier does one cache lookup. This gives immediate revocation at the cost of a dependency.
  3. Introspection (RFC 7662). Use opaque tokens and have the gateway ask the authorization server on each request, usually behind a short cache. Immediate, but adds latency and a dependency.
  4. Per-user token version. Put a ver claim in the token and keep the current version per user; bump it to revoke everything. Needs a lookup, like the deny list.

The deny list stays small because entries only need to live until the token's natural exp. Decide the failure mode up front: if Redis is down, do you fail open (accept tokens) or closed (reject)? For high-risk APIs fail closed; for low-risk accept the risk and alert.

Key rotation is a separate emergency lever: if a signing key is compromised, remove it from the JWKS and every token it signed becomes invalid at once.

Remember: revoking stateless tokens is a trade: short life plus a small deny list, or a lookup per call.

What is a JWKS and how do you rotate signing keys without downtime? Senior

A JWKS (JSON Web Key Set) is a JSON document of the issuer's public keys, each with a kid. Verifiers fetch it from a well-known URL and cache it. Rotation works by publishing the new key first, signing with it later, and removing the old one only after the last old token has expired.

Verifier side: read the token's kid, find that key in the cached JWKS, verify. If the kid is unknown, refetch the JWKS once (rate limited, so an attacker cannot force a fetch on every request with random kids), then fail if still missing. Cache with a sensible TTL, respecting cache headers.

  1. Generate key B and add it to the JWKS next to key A. The issuer still signs with A. Verifiers now know B.
  2. Wait longer than the verifiers' cache TTL so every verifier has seen B.
  3. Switch the issuer to sign with B. Tokens signed with A are still valid.
  4. After the longest token lifetime has passed, remove A.

Skipping step 2 causes a burst of 401s from verifiers that have not refreshed. Emergency rotation (compromised key) skips the waiting and accepts that some valid tokens fail; clients recover by refreshing.

The JWKS URL itself must be fetched over TLS from a configured location, never from a URL given in the token. Private keys live in a KMS or HSM, with signing done through it, so key material is not copied to disk or into app config.

Remember: publish the new key first, sign with it later, remove the old key only after old tokens expire.

JWT or opaque token: how do you decide? Intermediate

Use JWT when many services must verify tokens offline and the claims are small and low-sensitivity. Use opaque tokens when you need instant revocation, want to hide claims from clients, or need large or changing authorization data, accepting an introspection call.

An opaque token is a random string; its meaning lives only at the authorization server. The API calls the introspection endpoint to learn who it is, which gives live status but adds a network hop. A common compromise is for the gateway to introspect opaque external tokens once, then pass an internal short-lived JWT to the services behind it.

What is a JWT bearer assertion (RFC 7523) and when is it used for system-to-system calls? Senior

Instead of a client secret, the calling system signs a short-lived JWT (the assertion) with its own private key and sends it to the token endpoint. The server verifies it with the client's registered public key and returns an access token. No shared secret ever crosses the network.

The RFC covers two uses: client authentication (the JWT proves the client's identity in place of a secret, called private_key_jwt) and an authorization grant (the JWT states that a subject authorizes the access).

POST /oauth/token
grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
assertion=<signed JWT>
scope=orders:write

assertion claims:
  iss = client id        (who signed)
  sub = client id or user
  aud = token endpoint URL
  exp = now + 60 seconds
  jti = unique id        (server stores it to block replay)

The server must check: signature against the registered public key for that iss; aud equals its own token endpoint; exp is short and not far in the future; and jti has not been seen within the lifetime. Short life plus a jti store stops replay.

Why it beats a client secret: the private key never leaves the caller, so a breach of the server leaks no credentials; keys rotate by publishing a new public key; and each assertion is single-purpose and short-lived. The result is a normal bearer access token, used against the API (often through a gateway).

Make it yours: your resume mentions an API gateway with zero-trust, bearer tokens and JWT assertions for system-to-system auth. State plainly what you did yourself (for example configuring or consuming the flow, validating claims, key handling) and what the platform provided. [name the actual gateway feature or library you used]

Remember: a signed, short-lived, single-use JWT replaces the client secret; the server holds only the public key.

How do you keep tokens and claims from leaking into logs and errors? Intermediate

Redact the Authorization header at the logging layer, never log whole tokens (log the jti or a short hash instead), keep tokens out of URLs, and make error responses generic. Review exception messages, because a library may include the token in them.

  • Access logs and proxies: configure header allow-lists rather than deny-lists, so a new sensitive header is hidden by default.
  • Debug request logging: request-logging filters often dump all headers. Wrap them to mask Authorization, Cookie and custom auth headers.
  • Exception messages: a parse failure may echo the raw token. Log a fixed message plus the failure category.
  • Query strings: if a client put the token in a URL, it is now in every log. Reject such requests.
  • Tracing and APM: span attributes can capture headers; disable or scrub.
  • Correlation: log sub, tenant and jti so incident response can trace a token without holding the token.

Add an automated test: send a request with a recognizable fake token, capture the log output, and assert the fake token string is absent. This catches regressions when someone adds a logging line.

Remember: log identifiers, never credentials, and test that redaction really works.

3. OAuth 2.0, OIDC, mTLS, zero trust and the API gateway

Name the OAuth 2.0 grant types and when each is used. Basic

Authorization code with PKCE is for users signing in through a browser or mobile app. Client credentials is for service-to-service with no user. Refresh token renews access. Implicit and password grants are deprecated and should not be used in new systems.

GrantUsed forNotes

OAuth 2.0 is an authorization framework: it lets an app get limited access on a user's behalf without the user giving it their password. It says nothing by itself about who the user is; OpenID Connect adds that.

Remember: code plus PKCE for people, client credentials for machines; forget implicit and password.

Walk through authorization code with PKCE and explain what PKCE protects against. Intermediate

The client creates a random code_verifier, sends its hash as code_challenge in the authorization request, and later proves it holds the original verifier when redeeming the code. A stolen authorization code is then useless to an attacker, who lacks the verifier.

Steps: the client generates code_verifier (43 to 128 random characters), computes code_challenge = BASE64URL(SHA256(verifier)) (method S256) and starts the redirect. After login the server stores the challenge against the code it issues. At the token endpoint the client sends the verifier; the server hashes it and compares.

Attack prevented: on mobile or in browsers, a malicious app or a leaked redirect URL can capture the authorization code. Without PKCE the attacker could redeem it. With PKCE the code is bound to the starter. PKCE is now recommended for all clients.

Also validate the state parameter (CSRF protection on the redirect), use exact redirect URI matching, and keep codes single-use and short-lived (about a minute).

Remember: PKCE proves the redeemer is the starter, so a stolen code is worthless.

How does the client credentials grant work and what are its limits? Basic

The client authenticates directly to the token endpoint and receives an access token for itself, with no user involved. It suits batch jobs and service-to-service calls. Its limit is that the token represents the application, so end-user identity and per-user permissions are not present.

POST /oauth/token
Authorization: Basic base64(client_id:client_secret)   // or private_key_jwt / mTLS
grant_type=client_credentials&scope=orders:read

200 { "access_token":"...", "token_type":"Bearer", "expires_in":300 }

The client should cache the token until shortly before expiry rather than request one per call (that overloads the authorization server and adds latency). Scopes should be the minimum for each client. Client secrets belong in a secret manager and get rotated; better still use key-based client authentication so there is no shared secret.

The user-propagation problem: if service A calls B on behalf of a user and uses only A's client token, B cannot tell which user is acting, so it cannot apply per-user rules and audit logs lose the actor. Solutions: forward the user's token (watching audience rules), use token exchange (RFC 8693) to get a token for B that carries both the user and the acting service, or pass a signed internal identity header that only trusted callers can set.

Remember: client credentials proves which app is calling, not which user; propagate user identity deliberately.

What are OAuth scopes and how do they differ from roles and permissions? Intermediate

A scope is a limit on what a token may do, granted to a client, such as orders:read. A role is a label attached to a user, such as admin. Effective access should be the intersection: the user must have the permission and the token must carry the scope.

Scopes describe what the client may do on the user's behalf. Roles describe what the user may do in the system. Take a user with the admin role who logs into a reporting app that was only granted orders:read. That app should not be able to delete orders even though the user could. Enforce both:

allowed = user.hasPermission("orders:delete") && token.hasScope("orders:delete")

Design tips: name scopes as resource:action; keep them coarse (a handful per API) since they travel in tokens; keep fine-grained rules (this customer's records only) in the service. Scopes arrive in the scope claim (space-separated string) or scp (array) depending on the provider, so check how yours encodes them and map them to authorities.

Avoid putting every permission in the token. A token with 200 permissions is big and goes stale when roles change.

Remember: a scope limits the client, a role describes the user; enforce the intersection.

What does OpenID Connect add to OAuth 2.0? Intermediate

OAuth 2.0 gives access to APIs; OIDC adds identity. It defines an ID token (a JWT about the authentication event), the openid scope, a userinfo endpoint, discovery metadata and standard claims. The ID token is for the client app; the access token is for the API.

  • ID token: a signed JWT with sub, iss, aud (the client id), exp, nonce and often auth_time. The client validates it to learn who logged in.
  • openid scope: asking for it turns an OAuth request into an OIDC login.
  • Discovery: /.well-known/openid-configuration lists endpoints and the JWKS URI, so clients configure from the issuer URL alone.
  • UserInfo endpoint: returns profile claims for a valid access token.
Trap to avoid: sending the ID token to an API as if it were an access token. Its audience is the client app, not the API. APIs should accept access tokens whose aud is the API.

The nonce ties the ID token to the login request and prevents replay of an old token into a new session.

Remember: OIDC is identity on top of OAuth: ID token for the app, access token for the API.

What is mutual TLS, and where does it fit for service-to-service security? Intermediate

In normal TLS only the server proves its identity with a certificate. In mutual TLS the client also presents a certificate, so both sides authenticate at the connection level. It gives strong machine identity without secrets in headers, and is common inside a service mesh.

How it works: during the TLS handshake the server requests a client certificate; the client sends one signed by a CA the server trusts and proves it owns the private key. The server then knows the peer identity, for example from the certificate subject or a URI in the SAN field.

Strengths: identity is established before any HTTP bytes are exchanged; there is no bearer secret to copy from a log; it works for any protocol.

Costs: certificate issuance and rotation at scale is the real work. Short-lived certificates (hours) issued automatically by an internal CA or a mesh (Istio, Linkerd, SPIRE) make this manageable. Manual certificates that expire after a year cause outages when someone forgets to renew.

mTLS versus tokens: mTLS authenticates the workload; tokens carry the user and permissions. They complement each other. Also note TLS termination: if a gateway terminates TLS and forwards plain HTTP, the client identity is lost unless you re-establish mTLS on the next hop or forward verified identity.

Remember: mTLS authenticates workloads at the connection; tokens carry user and scope; use both.

What does zero trust mean for a microservice platform in practical terms? Intermediate

Zero trust means no request is trusted just because it comes from inside the network. Every call is authenticated, authorized and encrypted, access is least-privilege, and you assume a breach has already happened somewhere.

The older model was a hard perimeter with a soft inside: once past the firewall, services trusted each other, so one compromised pod could reach everything. Zero trust moves the checks to every hop.

  • Authenticate every caller: mTLS between services and tokens for users and clients.
  • Authorize at the service, not only at the edge: check scope, tenant and resource ownership in each service.
  • Least privilege: narrow scopes per client, network policies that allow only the calls that should exist, separate credentials per service.
  • Short-lived credentials: minutes for tokens, hours for certificates, automatic rotation.
  • Encrypt in transit everywhere, including internal traffic.
  • Log and monitor every decision, so an unexpected caller stands out.
  • Limit blast radius: one compromised service should not reveal the secrets of others.

Explain CORS and CSRF. How are they different and how do you configure each? Intermediate

CORS is a browser rule that blocks a page from reading responses from another origin unless the server allows it. CSRF is an attack where another site makes the victim's browser send an authenticated request. CORS does not stop CSRF, and CSRF defenses do not replace CORS.

CORS (Cross-Origin Resource Sharing). Browsers apply the same-origin policy. A server opts in to other origins with headers such as Access-Control-Allow-Origin. For non-simple requests (JSON with custom headers, PUT, DELETE) the browser first sends a preflight OPTIONS request and proceeds only if the response approves. Configure an explicit allow-list of origins; never reflect the request's Origin blindly; a wildcard cannot be combined with credentials. CORS is a browser protection only: curl ignores it, so it is not authentication.

CSRF. A malicious page triggers a form post to your site; the browser attaches the user's cookies; the server sees a valid session and acts. Defenses: SameSite=Lax or Strict cookies, anti-CSRF tokens (synchronizer or double-submit), checking Origin and Referer, and requiring a custom header.

When CSRF protection can be off. For a stateless API that takes tokens only in the Authorization header (no cookie auth), CSRF is not a risk, because the browser does not attach that header by itself. That is why Spring Security configs for pure token APIs often disable CSRF, and why people get into trouble when they disable it on an app that does use cookies.

Remember: CORS controls who can read responses; CSRF is forged requests with ambient cookies; header tokens avoid CSRF.

4. Spring Security essentials

How does the Spring Security filter chain work for one request? Intermediate

Spring Security is a chain of servlet filters in front of your controllers. Each filter does one job (read credentials, authenticate, check authorization, handle exceptions). Authentication results are stored in the SecurityContext, which later code reads through the SecurityContextHolder.

A request passes through a SecurityFilterChain chosen by matching the request path. The order is fixed. In a typical token API the important filters are:

  1. Context and header filters: security headers, CORS, CSRF (if enabled).
  2. Authentication filter (for resource servers, the bearer token filter): extracts the token, passes an unauthenticated Authentication object to the AuthenticationManager, which delegates to providers. On success the filter stores an authenticated object (with GrantedAuthority list) in the SecurityContext.
  3. ExceptionTranslationFilter: turns an AuthenticationException into 401 (via the entry point) and an AccessDeniedException into 403 (via the access-denied handler).
  4. Authorization filter: evaluates URL rules such as requestMatchers("/admin/**").hasRole("ADMIN").
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    http.csrf(c -> c.disable())                       // header tokens only, no cookie auth
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers(HttpMethod.GET, "/v1/orders/**").hasAuthority("SCOPE_orders:read")
            .anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
    return http.build();
}

Good habits: end with anyRequest().authenticated() so new endpoints are closed by default, and order matchers from most to least specific, because the first match wins. Debug with logging.level.org.springframework.security=DEBUG, which prints the chain and the matcher that decided.

Remember: a request walks an ordered filter chain; authentication fills the SecurityContext, then rules decide; default deny.

What is the SecurityContext and why does it break across threads? Intermediate

The SecurityContext holds the current Authentication. By default it is stored in a ThreadLocal, so it is visible only to the thread that handled the request. Work moved to another thread (async, executors, reactive) loses it unless you propagate it explicitly.

SecurityContextHolder.getContext().getAuthentication() returns the caller in the request thread. Because the default strategy is MODE_THREADLOCAL, these things lose the identity:

  • @Async methods and any ExecutorService you submit to.
  • CompletableFuture.supplyAsync on the common pool.
  • Parallel streams, scheduled tasks, Kafka listener threads.
  • Reactive code (WebFlux uses the reactive context instead).

Fixes: wrap the executor with DelegatingSecurityContextExecutorService (or DelegatingSecurityContextRunnable), or configure a task decorator for @Async so the context is copied into the worker thread. Another option is to avoid reading the context in the worker at all: capture the needed values (user id, tenant) in the request thread and pass them as parameters. That is clearer and safer.

The opposite bug is also dangerous: a pooled thread that keeps a stale context from a previous request would run work as the wrong user. The framework clears the context at the end of each request, and so should your own wrappers (clear in a finally block).

Remember: ThreadLocal context is per thread: copy it to workers deliberately, and always clear it afterwards.

How does method security work (@PreAuthorize) and when do you use it instead of URL rules? Intermediate

Method security puts authorization annotations on service methods, evaluated by an interceptor through a proxy before the method runs. Use it when the rule depends on method arguments or the loaded object, not just the URL, and to protect code paths reachable from more than one entry point.

@EnableMethodSecurity            // on a configuration class

@PreAuthorize("hasAuthority('SCOPE_orders:write') and #tenantId == authentication.token.claims['tenant']")
public Order update(String tenantId, Order o) { ... }

@PostAuthorize("returnObject.ownerId == authentication.name")
public Order get(String id) { ... }

URL rules are coarse and sit at the edge: "only authenticated callers reach /v1/*". Method rules are close to the logic and can use arguments (#id), the returned object (returnObject), and custom beans (@perm.canEdit(#id)). Use both: URLs for broad gates, methods for resource-level rules.

Pitfalls: it is proxy-based (same-class calls skip it, see the AOP section); private methods are not protected; and @PostAuthorize runs after the method, so side effects already happened. Test with security-aware tests (@WithMockUser or a mock JWT) and include denied cases, not just allowed ones.

Remember: URL rules gate the edge, method rules decide on arguments and results; both rely on proxies.

How do you configure a Spring Boot service as an OAuth2 resource server, and what is not validated by default? Intermediate

Add the resource server starter and point it at the issuer or JWKS URI. Spring then verifies signature, expiry and issuer and builds authorities from the scope claim. You must add audience validation and map custom role or tenant claims yourself.

spring.security.oauth2.resourceserver.jwt.issuer-uri=https://idp.example
# or: ...jwt.jwk-set-uri=https://idp.example/.well-known/jwks.json

What common Spring Security mistakes lead to real vulnerabilities? Senior

Open-by-default rules, wrong matcher order, permitting actuator endpoints, disabling CSRF on cookie apps, trusting client-sent headers for identity, and checking roles in the controller but not on the service that other paths also call.

  • No final deny rule. A new endpoint is public until someone remembers to secure it. End with anyRequest().authenticated() or denyAll().
  • Matcher order and path forms. A broad permitAll placed before a specific rule wins. Trailing slashes and path variants can differ between the matcher and the controller mapping; test the variants.
  • Actuator and docs exposed. /actuator/env, heap dumps and Swagger UI can leak configuration. Expose only health and info publicly and put the rest behind authentication or a management port.
  • Trusting identity headers. If the service reads X-User-Id set by the gateway, make sure clients cannot send it directly: strip it at the edge and accept it only over mTLS from the gateway.
  • Authorization only at the controller. A scheduled job, message listener or another service reaching the same service method bypasses it. Enforce in the service layer too.
  • Verbose errors. Stack traces and "user not found" versus "wrong password" differences help attackers.
  • Unsafe CORS with reflected origins plus credentials.
  • Old dependencies with known security-framework CVEs; keep Spring Boot patch versions current.

A useful review habit is to list every entry point (HTTP, Kafka listener, scheduled job, admin endpoint) and ask which identity it runs as and which check protects it.

Remember: default deny, test path variants, and enforce at every entry point, not just the controller.

5. Spring AOP for declarative authorization

How would you build declarative privilege enforcement with a custom annotation and Spring AOP? Intermediate

Define an annotation that names the required privilege, write an @Aspect with @Around advice that reads the current identity, checks the privilege and either proceeds or throws an access-denied exception. Spring applies it through a proxy, so callers get checks without any code in the business method.

@Target(METHOD) @Retention(RUNTIME)
public @interface RequiresPrivilege {
    String value();                  // e.g. "PREFERENCE_WRITE"
}

@Aspect @Component @Order(Ordered.HIGHEST_PRECEDENCE + 10)
public class PrivilegeAspect {
    private final PrivilegeService privileges;
    private final CurrentUser current;                 // resolves tenant and user

    @Around("@annotation(req)")
    public Object check(ProceedingJoinPoint pjp, RequiresPrivilege req) throws Throwable {
        Principal p = current.require();               // 401 if missing
        if (!privileges.has(p.tenantId(), p.userId(), req.value())) {
            audit.denied(p, req.value(), pjp.getSignature().toShortString());
            throw new AccessDeniedException("missing privilege");
        }
        return pjp.proceed();
    }
}

@RequiresPrivilege("PREFERENCE_WRITE")
public void savePreference(String tenantId, Pref p) { ... }

Why this design: the rule is visible on the method (readable and greppable), the check is written once, and developers cannot forget it in the method body. It also lets you log every denial in one place.

Design points to mention: deny by default when the annotation is present but the principal is unresolved; keep the privilege lookup fast (cache per tenant and user, with a short TTL or event-based invalidation); put argument-dependent checks (does this user own record X) in the aspect only if the argument is reachable cleanly, otherwise do them in the service.

How does Spring AOP work internally, and what is the difference between JDK and CGLIB proxies? Intermediate

Spring AOP wraps a bean in a proxy object at startup. Calls from other beans go to the proxy, which runs the advice (aspect code) and then delegates to the real object. A JDK proxy implements the bean's interfaces; a CGLIB proxy subclasses the bean class.

MechanismImplements the interfaces of the beanGenerates a subclass of the bean class
RequiresThe bean implements an interfaceClass and methods not final (and a usable constructor)
Inject byThe interface type onlyClass or interface

Limits that follow from proxies: only public (and in CGLIB, non-private, non-final) method calls through the proxy are advised; final classes and methods cannot be overridden; calls inside the same object are not intercepted; and only Spring-managed beans are proxied. AspectJ with compile-time or load-time weaving removes these limits by changing the bytecode itself, at the cost of build or agent complexity.

Remember: AOP is a proxy in front of the bean; only calls that go through the proxy get the advice.

What is the self-invocation pitfall and how do you fix it? Intermediate

When a method calls another method on the same object (this.other()), the call does not pass through the proxy, so annotations like your privilege check, @Transactional or @Cacheable on the second method are silently ignored. Fix it by restructuring so the call crosses a bean boundary.

@Service
class PrefService {
    public void import(List<Pref> list) {
        for (Pref p : list) save(p);      // this.save(): NO privilege check, NO transaction
    }
    @RequiresPrivilege("PREF_WRITE")
    @Transactional
    public void save(Pref p) { ... }
}

This is dangerous for security: the method looks protected, tests of the outer call may pass, and the bypass is invisible. Fixes, best first:

  1. Move the advised method to another bean and inject it. The call crosses the proxy. This is the cleanest and the one I use.
  2. Put the annotation on the outer (entry) method too, so the external call is checked.
  3. Inject the proxy of itself (self-injection with @Lazy) and call through it. Works but is a code smell.
  4. Use AspectJ weaving so advice is woven into the class itself.

Prevention: write a test that calls the entry point as an unauthorized user and expects a denial; a self-invocation bug shows up as a test that unexpectedly passes.

Remember: a this-call skips the proxy and therefore the check; move the advised method to a different bean.

How is the order of aspects and other interceptors controlled, and why does it matter for security? Senior

Order is set with @Order or the Ordered interface (lower value runs first on the way in). It matters because the authorization check must run before anything with side effects, and the transaction, cache and tenant-context interceptors have to wrap each other in the right sequence.

Advice from several aspects around one method form a nested chain: the first-ordered aspect is outermost. A sensible stack, outermost first:

  1. Tenant and identity context (so everything below knows who is calling).
  2. Authorization / privilege check (reject before doing any work).
  3. Caching (@Cacheable), so a denied caller never reads cached data.
  4. Transaction, closest to the method, so denied calls never open a transaction.

Real bugs from bad ordering: a cache aspect outside the authorization aspect returns a cached value to a caller who should be denied; a transaction opened before the check holds a database connection for denied requests (a cheap denial-of-service); a logging aspect inside the check never logs denials. Set explicit orders instead of relying on defaults, and note that @EnableTransactionManagement, @EnableMethodSecurity and @EnableCaching each take an order attribute.

Verify ordering in a test or with debug logs listing the advisors on the bean. Exact default orders differ between Spring versions, so do not rely on memory.

Remember: authorization goes outside cache and transaction so a denied caller does no work and sees no cached data.

6. Role, scope and tenant-scoped authorization, multi-tenant isolation

How does a request get its tenant, and what must you never trust? Intermediate

The tenant should come from the verified credential (a claim in the validated token, or the mTLS identity), not from a request parameter or header the caller controls. Resolve it once at the edge into a request-scoped context and use that everywhere downstream.

Sources, from most to least trustworthy: a signed claim in a verified token; the identity bound to the mTLS certificate; a gateway-injected header that clients cannot forge; a subdomain or path segment that you cross-check against the token; a plain client header or body field (never trust alone).

The classic mistake is an endpoint like GET /tenants/{tenantId}/prefs that uses the path tenant without comparing it to the token tenant. A caller changes the number and reads someone else's data. The rule: if the path carries a tenant, assert path.tenant == token.tenant (or that the caller is a platform admin with an explicit cross-tenant right).

TenantContext.set(jwt.getClaimAsString("tenant"));   // in a filter, after authentication
try { chain.doFilter(req, res); } finally { TenantContext.clear(); }

Make the tenant a required part of every data access method signature or read it from the single context object, so a developer cannot forget it. Add logging and metrics fields for tenant on every request, which also helps support and per-tenant rate limiting.

Remember: derive the tenant from the verified token, cross-check any tenant in the URL, and set it once per request.

What are the options for isolating tenant data, and how do you enforce a row-level tenant filter? Senior

Isolation can be a database per tenant, a schema per tenant, or shared tables with a tenant_id column. The shared model is cheapest but needs the filter on every query, enforced centrally (ORM filter, database row-level security, or a repository base class) rather than by developer discipline.

How do cache keys and ThreadLocals leak data between tenants? Senior

A cache key without the tenant id lets tenant B read tenant A's cached value. A ThreadLocal that is not cleared lets the next request on a pooled thread inherit the previous tenant. Both are silent until a customer sees someone else's data.

Cache key leak. Suppose the key is pref:{userId} and two tenants both have user id 7. Whoever caches first wins. Fix: always include the tenant and a version, pref:v2:{tenantId}:{userId}. Do the same for local in-memory caches (Caffeine or a map) and for Spring @Cacheable keys: build the key from an expression that includes the tenant, or use a custom KeyGenerator that adds it automatically. Per-tenant eviction then becomes a prefix delete or a tenant-version counter in the key.

ThreadLocal leak. Servlet containers reuse threads. If the filter sets TenantContext and an exception path skips the clear, the next request on that thread (possibly with no tenant header, or a failed authentication) reads the previous tenant. Always clear in a finally block, and fail closed when the tenant is missing instead of defaulting to something.

Other leak spots: static mutable fields and singleton beans holding per-request state; shared SimpleDateFormat-style caches of tenant settings; message-listener threads reusing context; connection-level session variables (for row-level security) not reset when a pooled connection is returned.

How do you keep tenant and security context across async work, Kafka consumers and scheduled jobs? Senior

Treat the context as data, not as ambient state. Capture tenant and user ids in the request thread, put them in the task or message, and re-establish the context at the start of the worker inside a try/finally. Never assume the worker thread inherits anything.

  • Executors and @Async: use a task decorator (or DelegatingSecurityContext* wrappers) that copies the tenant and security context into the worker and clears it afterwards. A decorator is applied in one place so no task forgets.
  • Kafka or JMS messages: there is no thread inheritance at all; the producer must write the tenant (and a correlation id) into a message header or the payload. The consumer reads it, validates it against what it is allowed to process, sets the context, processes, clears. Never let a consumer default to some tenant when the header is missing: dead-letter the message instead.
  • Scheduled and batch jobs: iterate over tenants explicitly, setting the context per tenant, so a failure for one tenant is isolated and logged with its id.
  • Reactive code: use the Reactor context, not ThreadLocal, or a library bridge; context can hop threads between operators.
  • Retries and delayed work: a retry runs later on another thread, so the tenant has to be stored with the retry record.

Test it: run two tenants' requests concurrently through the async path with a tiny thread pool (one or two threads) so thread reuse is forced, and assert that each result carries the correct tenant. Small pools make hidden leaks appear quickly.

Remember: pass tenant and user as data, restore it in the worker, clear it in finally, and test with a tiny thread pool.

RBAC grants permissions to roles and roles to users. Scopes limit what a client token can do. ABAC decides from attributes of the user, resource and context (owner, tenant, time). Real systems combine them: role for what you may do, attributes for which records, scopes for which client.

What is BOLA (broken object level authorization) and how do you prevent it systematically? Senior

BOLA (also called IDOR) is when an authenticated caller changes an object id in the request and gets or modifies someone else's object because the server never checks ownership. It is the number one risk in the OWASP API Security list. Prevent it by checking ownership or tenant on every object access, in a central place.

Example: GET /v1/prefs/9001 returns the preference with id 9001 for any logged-in user. The attacker loops over ids. Random UUIDs make guessing hard but are not authorization; a leaked id still works.

Systematic prevention:

  • Query by owner: load with WHERE id = ? AND tenant_id = ? AND (owner_id = ? OR :canSeeAll), so a foreign id behaves like a missing one. This removes the need for a separate check that someone may forget.
  • Central policy: one method such as access.require(principal, resource, action) used by every handler, or an aspect on the repository or service layer.
  • Test automatically: for each endpoint with an id, call it with another user's token and expect 403 or 404. Add this to the integration suite as a generic loop over routes.
  • Bulk and nested paths: check list filters, batch endpoints (an array of ids), and child resources (/orders/1/items/5 must verify that item 5 belongs to order 1 and order 1 to the caller).
  • Same for writes: PUT, PATCH and DELETE, not just GET.

How would you design multi-step customer authentication with a registration id, passcode, OTP and security questions? Intermediate

  1. Identify: the user submits a registration id. Respond the same way whether it exists or not (avoid account enumeration).
  2. Knowledge factor: passcode (stored hashed, compared in constant time).
  3. Possession factor: an OTP sent to a registered phone or email, or generated by an app.
  4. Step-up or recovery factor: security questions for lower-trust situations such as a reset, ideally as one signal among several rather than the sole proof.

Server state machine: after step 1 the server creates a short-lived "pending login" record with a random id and a status (ID_OK, PASSCODE_OK, OTP_OK). Each endpoint accepts only the next status. The client holds just the pending id. Only the last step issues the session or token. Without this, an attacker calls the final endpoint directly.

How do you generate, store and verify one-time passcodes safely? Intermediate

Generate with a cryptographically secure random source, keep it short-lived (a few minutes) and single-use, store only a hash with the expiry and an attempt counter, verify in constant time, and invalidate on success, on expiry, and on too many failures.

SecureRandom rnd = new SecureRandom();              // never java.util.Random
String otp = String.format("%06d", rnd.nextInt(1_000_000));
store(userId, purpose, sha256(otp + pepper), now + 5min, attempts = 0);

verify: record = load(userId, purpose)
  - missing or expired       -> fail
  - attempts >= max          -> fail, lock
  - attempts++               (before comparing)
  - MessageDigest.isEqual(hash(input), record.hash) -> success: delete record
  • Entropy math: a 6-digit code has a million values. With 5 attempts per code, the chance of a random guess succeeding is 5 in a million, which is acceptable only because attempts are capped. Without the cap it falls quickly.
  • Hashing: OTPs are short-lived and rate limited, so a fast hash with a server-side pepper is acceptable; the key point is not storing them in plain text or logs.
  • Single use and binding: bind to user, purpose (login, reset) and ideally to the pending-login id, so a code from one flow cannot complete another.
  • Resend limits: cap sends per hour, since SMS costs money and floods annoy users. A resend should invalidate the earlier code.
  • Delivery channel risks: SMS can be intercepted or SIM-swapped; prefer app-based TOTP (RFC 6238) or push approval for higher risk.

Remember: secure random, short TTL, single use, hashed, capped attempts, constant-time compare.

How do you defend against brute force and credential stuffing without locking out real users? Intermediate

Combine per-account and per-IP rate limits, progressive delays, short temporary lockouts rather than permanent ones, breached-password checks, CAPTCHA or step-up after suspicious patterns, and monitoring. Pure hard lockout is itself a denial-of-service weapon.

Two different attacks. Brute force hammers one account with many guesses. Credential stuffing tries leaked username and password pairs across many accounts, each only once or twice, so per-account counters never trigger. Defend against both:

  • Per-account counter with exponential backoff: 1, 2, 4 seconds and so on, or a temporary lock of 15 minutes after N failures, with automatic unlock. Permanent lockouts let an attacker lock out any victim.
  • Per-IP and per-device limits, plus global limits on the login endpoint.
  • Same response and timing for unknown user and wrong password.
  • Breached-password screening when users set passwords, and MFA to make a stolen password insufficient.
  • Challenge on risk: new device, unusual location or high failure rate triggers CAPTCHA or an extra factor.
  • Notify the user of lockouts and unusual logins, and log events for detection.

Counters live in Redis with TTL (atomic increment with expiry), so they work across instances. Choose the failure mode if Redis is down: for login, fail closed or fall back to a conservative in-memory limit.

Remember: throttle by account and by IP, lock temporarily, and add MFA, because stuffing evades per-account counters.

How should passwords and passcodes be stored: bcrypt, Argon2, salting and peppering? Intermediate

Never store passwords reversibly or with a fast hash. Use a deliberately slow, salted, adaptive algorithm: Argon2id (preferred), bcrypt or scrypt. Each password gets a unique random salt, stored with the hash, and the cost is tuned so one check takes roughly 100 to 500 ms on your hardware.

ApproachVerdict
Plain text, or reversible encryptionNever. A database leak exposes every password

Salt: a unique random value per password, stored next to the hash. It makes identical passwords hash differently and kills precomputed tables. It is not secret. Pepper: an extra secret kept outside the database (in a KMS or secret store) mixed into the hash, so a database-only leak is not enough to crack hashes. Optional but useful.

Tune the cost by measuring on production-like hardware and raise it over time; store the algorithm and parameters in the hash string so you can detect old hashes and re-hash at the next successful login. Are security questions a good idea? How do you implement them if required? Intermediate

They are weak: answers are often guessable or findable on social media and do not change. If a product requires them, treat them as a low-grade supplementary factor, store the answers hashed like passwords, normalize input, throttle attempts, and never use them alone for high-risk actions.

  • Store hashed: normalize first (trim, lowercase, collapse spaces) so "New York " and "new york" match, then hash with a slow salted algorithm. Do not store them reversibly just for support convenience.
  • Let the user write or choose from a well-designed list; avoid questions with a small answer space (favorite color) or public answers (high school).
  • Throttle and lock exactly like passwords. A question has far less entropy, so limits matter even more.
  • Do not leak: do not reveal which question the user has before identification; do not say which answer was wrong when several are asked.
  • Combine: use them together with a possession factor such as an OTP, so guessing the answers is not enough.
  • Encourage better: allow replacing them with an authenticator app or passkey.

Standards guidance (for example NIST) discourages knowledge-based questions as a sole authenticator. Saying that shows you know the trade-off, even if the product still has the feature.

Remember: security questions are guessable: hash them, throttle them, and pair them with a stronger factor.

8. Input validation, OWASP API risks, secrets, dependencies and data leakage

How do you prevent injection and handle input validation in a REST service? Basic

Validate input at the boundary against an allow-list (type, length, format, range), and never build SQL, shell commands, or queries by concatenating user input. Use parameterized queries and bound parameters; encode output for its context.

  • SQL: prepared statements or named parameters. In JPA, @Query("... where e.tenantId = :t") with bound parameters. Be careful with dynamic ORDER BY and column names, which cannot be parameters: map the client's value to a fixed allow-list of columns.
  • NoSQL and search queries: the same idea applies to Elasticsearch JSON, MongoDB filters and LDAP. Build queries with the client's builder objects and bind values; never paste raw user text into a query string or script. A configuration-driven query builder should treat user input as values, never as field names or operators unless checked against the registry.
  • OS commands and file paths: avoid shell calls; for file names reject path separators and .., and resolve against a base directory then verify the result is still inside it.
  • Bean Validation: @NotNull @Size @Pattern @Min on DTOs plus @Valid; limit collection sizes and request body size.
  • Deserialization: do not enable default typing or deserialize untrusted data into arbitrary classes. Use explicit DTOs.
  • Output encoding: HTML-escape in HTML contexts; set Content-Type correctly and X-Content-Type-Options: nosniff.

Validation is a quality filter, not the main defense. The main defense against injection is that data and code never share a channel: parameters stay parameters.

Remember: allow-list validate at the edge, and keep data out of the code channel with parameters.

What are mass assignment and excessive data exposure, and how do you stop them? Intermediate

Mass assignment is binding a request body straight onto an entity, so a caller can set fields they should not (role, tenantId, price). Excessive data exposure is returning the whole entity and trusting the client to ignore sensitive fields. Both are fixed by explicit request and response DTOs.

// Vulnerable: entity bound directly
@PutMapping("/users/{id}") User update(@RequestBody User u) { return repo.save(u); }
// attacker sends {"name":"x","role":"ADMIN","tenantId":"other"}

// Safe: dedicated input type with only editable fields
record UpdateProfile(@Size(max=80) String name, @Email String email) {}
@PutMapping("/users/{id}")
UserView update(@PathVariable String id, @Valid @RequestBody UpdateProfile in) {
    User u = users.loadOwned(id);          // ownership checked
    u.setName(in.name()); u.setEmail(in.email());
    return UserView.of(u);                 // response DTO, no internal fields
}
  • Never expose entities directly in controllers. Mapping layers (MapStruct or manual) make the allowed fields explicit.
  • Jackson settings: FAIL_ON_UNKNOWN_PROPERTIES can surface unexpected input, and @JsonIgnore or @JsonProperty(access = READ_ONLY) protects sensitive fields. DTOs are still the more robust fix.
  • Different views per role: an admin view may add fields; build separate DTOs rather than conditionally nulling fields in one.
  • Contract tests that compare the response schema to the OpenAPI document catch new fields appearing without review.

Remember: bind to purpose-built DTOs both ways, so only reviewed fields ever go in or out.

How should secrets be managed in services and pipelines? Intermediate

Keep secrets out of source, images and plain config. Inject them at runtime from a secret manager (Vault, a cloud secret store, or Kubernetes secrets with encryption), give each service its own least-privilege access, rotate regularly, and scan repositories for leaks.

  • Where not to put them: source control, Docker image layers, build logs, plain application.yml, or environment variables printed by diagnostics. Environment variables are visible in process listings and crash dumps; mounted files or an API fetch at startup are better.
  • Kubernetes: Secrets are only base64-encoded by default. Enable encryption at rest, restrict RBAC to them, prefer an external store with a CSI driver or operator, and avoid giving every pod access to every secret.
  • Rotation: design for it: read the secret on each use or on a refresh schedule, support two valid values during overlap, and automate. A secret you cannot rotate without downtime will never be rotated.
  • Prefer identity over secrets: workload identity and short-lived tokens beat static database passwords.
  • Detection: pre-commit and CI secret scanning; treat any committed secret as compromised and rotate it, since deleting the commit does not remove it from clones.
  • Access: separate secrets per environment; audit who read what.

Remember: inject secrets at runtime, rotate them without downtime, and treat any leaked one as compromised.

How do you upgrade a vulnerable transitive dependency in Maven or Gradle, and what can go wrong? Senior

First find which direct dependency pulls it in, then prefer upgrading that parent. If no parent update exists, force a safe version with dependency management (Maven) or constraints (Gradle), then run the full test suite and check for binary incompatibility, because you are running a library version its consumer was not built against.

Find the path: mvn dependency:tree -Dincludes=group:artifact or gradle dependencyInsight --dependency name --configuration runtimeClasspath. Check both compile and runtime classpaths and the final packaged artifact (a fat jar may bundle a copy).

Options in order of preference:

  1. Upgrade the direct dependency or the framework BOM (for example the Spring Boot version) which brings a patched transitive version.
  2. Override the version: Maven <dependencyManagement> entry, or a Gradle constraints { implementation("x:y:fixed") { because "CVE-..." } } block. Document the reason in a comment so it is removed when no longer needed.
  3. Exclude and replace when the library is abandoned, or when the vulnerable module is unused.
  4. Shade or patch only as a last resort.

What is contract testing and how does it differ from integration tests? Senior

How do V1, V2 and V3 of an API coexist in one codebase, and how do you deprecate old versions? Senior

  • Separate packages per version (api.v1, api.v2). No version-specific logic in the service layer; if V3 needs different behavior, express it as a parameter or new method, not an if (version == 3) scattered around.

  • Each version has its own OpenAPI file and contract tests, so a V3 change cannot silently alter V1.
  • Prefer additive evolution inside a version and cut a new one only for real breaks.

What are your rules for keeping an API backward compatible? Intermediate

Be conservative in what you send and liberal in what you accept: only add, never remove or reinterpret. Clients must ignore unknown fields, servers must treat new fields as optional, and any change that could make a working client fail needs a new version.

  • Add, do not change: new optional fields, new endpoints, new optional query parameters are safe. Renames are a remove plus an add, so keep both for a deprecation period.
  • Never repurpose a field: a field that used to hold seconds must not start holding milliseconds.
  • Enums: adding a value can break clients with a strict switch. Document that clients must tolerate unknown values, and consider whether a new value affects older versions' behavior.
  • Defaults: a new optional input must default to the old behavior.
  • Validation: do not tighten rules on existing inputs (for example a shorter max length) without a version.
  • Error contract: status codes and error codes are part of the contract.
  • Ordering and pagination defaults are also relied on by clients.
  • Mechanics: a spec-diff tool in CI, contract tests, and Jackson set to ignore unknown properties on inputs from other services (while still validating your own public inputs).

Also think about rolling deployments: during a rollout old and new service versions run together, so a message or database format change must be readable by both. The same expand-then-contract approach applies: deploy readers first, then writers, then remove the old form.

Remember: only add; if a working client could fail, it is a new version.

How do idempotency keys make POST requests safe to retry? Senior

The client sends a unique Idempotency-Key header with a POST. The server stores the key with the result of the first processing. If the same key arrives again, the server returns the stored result instead of doing the work twice. This makes retries after timeouts safe.

Why needed: GET, PUT and DELETE are idempotent by definition, but POST is not. If a client times out on a payment POST, it does not know whether it succeeded. A blind retry could charge twice.

POST /v1/payments
Idempotency-Key: 6c1f6e2a-...
{ "amount": 1200, ... }

server:
  1. INSERT key + request fingerprint with status IN_PROGRESS   (unique constraint on key + client)
     - duplicate and COMPLETED -> return the stored response (same status and body)
     - duplicate and IN_PROGRESS -> 409 (or wait), do not run twice
     - duplicate but different request body -> 422 (key reuse with a different payload)
  2. do the work
  3. store response, mark COMPLETED   (ideally in the same transaction as the work)
  4. keep keys for a retention window, such as 24 hours

Details that matter: scope the key by client or tenant so one tenant cannot replay another's; the unique constraint (not a read-then-write) is what prevents a race between two simultaneous retries; store the fingerprint of the request to detect misuse; and make side effects (events, downstream calls) part of the same atomic unit or themselves idempotent.

Same idea in messaging: consumers with at-least-once delivery de-duplicate by a message id, writing the processed id and the effect in one transaction. That is how idempotent processing from a JMS or Kafka queue works, and the dead-letter queue holds messages that keep failing.

Remember: a unique key plus a stored result turns a retried POST into a replay, not a duplicate.

Offset versus cursor (keyset) pagination: how do they differ and which do you use? Intermediate

Offset pagination (page and size) is simple but slow on deep pages and unstable when data changes between requests. Cursor (keyset) pagination continues after the last seen sort key, so it is fast at any depth and stable, but you cannot jump to an arbitrary page.

Offset / limitCursor / keyset
QueryORDER BY id LIMIT 50 OFFSET 100000WHERE id > :last ORDER BY id LIMIT 50

Concurrent insertsItems repeat or are skipped between pagesStable

Total countEasy but costs a count queryUsually omitted

Cursor details: the cursor is an opaque token (base64 of the last sort key values) so clients do not depend on its structure and so you can change it. The sort must be total and stable, so add a unique tiebreaker such as the id (ORDER BY created_at, id with a compound comparison). Response includes nextCursor.

Search backends: Elasticsearch deep paging with from + size is limited (a default window of 10,000) and expensive; use search_after with a sort that includes a tiebreaker, plus a point-in-time context for consistency if needed. Always enforce a maximum page size server-side; an unbounded size parameter is an easy denial-of-service and data-scraping route.

Remember: keyset for large or changing data, offset for small admin lists, and always cap the page size.

How do HTTP caching headers and ETags work for an API? Intermediate

The server marks responses with Cache-Control (how long they may be reused) and an ETag (a version fingerprint). Clients and proxies can revalidate with If-None-Match and get a cheap 304 Not Modified. The same ETag with If-Match gives optimistic locking on updates.

GET /v2/prefs/42
200 OK
ETag: "v17"
Cache-Control: private, max-age=30

GET /v2/prefs/42
If-None-Match: "v17"
304 Not Modified          (no body: saves bandwidth and serialization)

PUT /v2/prefs/42
If-Match: "v17"
412 Precondition Failed    (someone changed it since you read it)
  • private vs public: data that depends on the user or tenant must be private (or no-store for sensitive data). Marking per-tenant data public lets a shared cache serve one tenant's response to another, a real data leak.
  • Vary: if the response differs by a header (Accept-Language, Authorization, a version header) list it in Vary so caches key correctly.
  • no-cache means "revalidate before reuse", while no-store means "do not keep it at all". People confuse them.
  • ETag source: a version column or a hash of the representation. A weak ETag (W/) is enough for GET revalidation; use a strong one with If-Match.
  • Lost-update protection: If-Match with ETag maps neatly to JPA @Version, giving 412 or 409 on conflicts without locks.

Remember: ETag plus If-None-Match saves work; ETag plus If-Match prevents lost updates; never mark tenant data public.

What makes a good client SDK library for an API, and what are the pitfalls of generating it? Intermediate

A good client library hides the HTTP details but not the semantics: typed models, built-in authentication and token refresh, sensible timeouts, retries with backoff only for safe cases, idempotency keys, clear exceptions, and version alignment with the API contract. Generated from the OpenAPI spec so it cannot drift.

  • Generated models and operations from the same spec the server uses, so a field change appears as a compile error rather than a runtime surprise.
  • Auth built in: obtain and cache tokens, refresh before expiry, handle 401 once by refreshing then retrying.
  • Timeouts always set: connect and read timeouts; never an infinite default.
  • Retries with care: retry on connection failures, 429 (honoring Retry-After) and 503, with exponential backoff and jitter. Retry unsafe methods like POST only with an idempotency key.
  • Error mapping: parse problem details into a typed exception with status, code and trace id.
  • Tenant and correlation headers added automatically so callers cannot forget them.
  • Small dependency footprint: an SDK that drags in a heavy framework or conflicting library versions causes classpath conflicts for every consumer; this is a real, common pain.
  • Versioning: the SDK version tracks the API version; keep SDK changes additive and publish release notes.

Pitfalls: generated code overwritten by hand edits (put customizations in a wrapper, not in generated files); forgetting to run the contract tests against the SDK; and unbounded retries from many clients multiplying load during an outage (a retry storm). Use a circuit breaker and cap retries.

10. Rate limiting, async APIs and webhooks

How should an API respond when a client is rate limited? Basic

Return 429 Too Many Requests with a Retry-After header telling the client how long to wait, plus problem-details body. Include the limit headers so well-behaved clients can slow down before hitting the wall.

HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 12
Content-Type: application/problem+json

{ "type": "https://api.example/problems/rate-limited", "title": "Too many requests",
  "status": 429, "code": "RATE_LIMITED", "detail": "Retry after 12 seconds." }
  • 429 versus 503: 429 means this client sent too much; 503 means the server is overloaded or unavailable for everyone. Both may carry Retry-After.
  • Header names: the older de-facto names are X-RateLimit-*; an IETF draft standardizes RateLimit-*. Say which you use and stay consistent.
  • Client behavior: wait at least Retry-After, then retry with jitter, so many clients released at the same moment do not all return together.
  • Limit what you count: limit per client or tenant, and apply tighter limits on expensive or sensitive endpoints (login, search, export).
  • Fairness: a 429 must be cheap to produce, so check the limit early in the pipeline, before authentication cost where feasible or right after identification.

Remember: 429 plus Retry-After, with limit headers; make the rejection cheap and tell clients how to back off.

Token bucket versus sliding window versus fixed window: how do they work and differ? Intermediate

A fixed window counts requests per clock interval and is simple but allows double bursts at the boundary. A sliding window smooths that by looking at the last N seconds. A token bucket refills tokens at a steady rate up to a capacity, allowing controlled bursts while enforcing an average rate.

Leaky bucketQueue draining at fixed rateSmooths outputAdds queueing delay

Choosing: token bucket is the common default for public APIs because real clients are bursty. Use a sliding window when strict "N per minute" fairness matters (login attempts). Use a concurrency limit (in-flight requests) in addition to a rate, since slow requests are what actually exhaust a server.

Remember: token bucket allows bursts at a steady average; sliding window is stricter; fixed window is cheap but leaky at the edges.

How do you implement per-tenant rate limiting with Redis atomically? Senior

Keep the state per tenant key in Redis and update it in a single Lua script, so the read, compute and write happen atomically. Doing GET then SET from the application races between instances and lets bursts through. The script returns allowed or denied plus the wait time.

-- KEYS[1] = rl:{tenant}:{api}
-- ARGV: rate (tokens/sec), capacity, now_ms, cost
local d = redis.call('HMGET', KEYS[1], 't', 'ts')
local tokens = tonumber(d[1]) or tonumber(ARGV[2])
local ts     = tonumber(d[2]) or tonumber(ARGV[3])
local delta  = math.max(0, tonumber(ARGV[3]) - ts) / 1000
tokens = math.min(tonumber(ARGV[2]), tokens + delta * tonumber(ARGV[1]))
local allowed = tokens >= tonumber(ARGV[4])
if allowed then tokens = tokens - tonumber(ARGV[4]) end
redis.call('HMSET', KEYS[1], 't', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], math.ceil(tonumber(ARGV[2]) / tonumber(ARGV[1]) * 1000) * 2)
return { allowed and 1 or 0, math.floor(tokens) }

Why a script: Redis runs a script as one uninterrupted unit, so two gateway instances cannot interleave. For a simple fixed window, INCR plus EXPIRE on first increment is enough, but set the expiry atomically (or in a script) so a crash between the two commands does not leave an immortal key.

Time source: pass now from one place, or use Redis TIME inside the script (version behavior around non-deterministic commands in scripts has changed, so check yours), to avoid clock skew between app servers.

  • Per-tenant configuration: look up each tenant's plan limits (cached) and pass them as arguments, so one script serves all tenants.
  • Cluster: the key must be in one slot; one key per tenant and API keeps it in one slot automatically.
  • Failure mode: if Redis is down, decide: fail open (accept traffic, protecting availability) with a coarse local in-memory fallback limit, or fail closed for sensitive endpoints. Set a short timeout on the Redis call so rate limiting never becomes the slowest part of a request.
  • Hot tenants: one very busy tenant means one hot key; that is usually fine, but consider local pre-limiting if the key becomes a bottleneck.

How do you design an asynchronous API with 202 Accepted and a status resource? Intermediate

For long-running work, accept the request, return 202 Accepted with a Location header pointing to a status resource, and let the client poll (or receive a callback). The status resource reports pending, running, succeeded or failed, and links to the result when ready.

POST /v2/exports                 Idempotency-Key: ...
202 Accepted
Location: /v2/exports/9a1/status
Retry-After: 5

GET /v2/exports/9a1/status
200 { "state": "RUNNING", "progress": 40 }

GET /v2/exports/9a1/status       (when finished)
303 See Other   Location: /v2/exports/9a1/result
  or 200 { "state": "SUCCEEDED", "resultUrl": "..." }
  or 200 { "state": "FAILED", "error": { problem details } }
  • Authorize the status resource like any object: only the owner or tenant may read it (BOLA applies, and job ids are guessable surprisingly often).
  • Persist the job before returning 202, so an instance crash does not lose accepted work; process from a queue with retries and a dead-letter path.
  • Idempotency key on the POST so a retried submission does not create two jobs.
  • Expiry: keep results for a limited time and say so.
  • Webhooks as an alternative to polling: the server calls the client when done (next question), but offer polling as well since not every client can receive callbacks.
  • Sync versus async dual mode: small requests can be handled inline and large ones queued, with the same payload shape. The client then needs to handle both 200 and 202 responses.

Remember: 202 with a Location status resource, persisted jobs, an idempotency key, and the same authorization on the status.

How do you design and secure webhooks? Senior

A webhook is the provider calling the consumer's URL when an event happens. Secure it by signing each payload with an HMAC and a timestamp so the consumer can verify origin and freshness, delivering over TLS, retrying with backoff, and making consumers idempotent by event id.

POST https://consumer.example/hooks/orders
X-Event-Id: evt_81f2
X-Timestamp: 1767225600
X-Signature: v1=hex(HMAC_SHA256(secret, timestamp + "." + rawBody))

consumer verifies:
  1. timestamp within 5 minutes (stops replay of captured requests)
  2. recompute HMAC over the RAW body bytes, compare in constant time
  3. event id not processed before (dedupe; delivery is at-least-once)
  4. respond 2xx quickly, process asynchronously
  • Use the raw body for the signature; parsing and re-serializing changes bytes and breaks verification.
  • Per-subscription secrets, rotatable, with two valid secrets during rotation.
  • Provider side retries: exponential backoff for a day or so on non-2xx or timeouts, then mark the endpoint failing and notify the owner; disable endpoints that fail for long.
  • SSRF risk on the provider: since customers supply URLs, the provider must block private and metadata addresses (169.254.x.x, internal ranges), re-resolve after DNS to defeat rebinding, and limit redirects.
  • Ordering is not guaranteed: include a sequence or timestamp and let consumers fetch current state if needed.
  • Payload minimization: send the event type and ids, and let the consumer fetch the details with authenticated API calls, so a leaked webhook exposes little.

Remember: sign timestamp plus raw body, verify in constant time, dedupe by event id, and guard the sender against SSRF.

11. Real-life scenarios

Scenario: an access token (or refresh token) was found in a log file or pasted in a public ticket. What do you do? Senior

Treat it as compromised. Contain first (revoke it and the refresh family), then scope the damage from audit logs, then fix the leak source, then rotate anything else exposed alongside it, and finally write down what changed so it cannot recur.

  1. Contain (minutes): revoke the token: add its jti or the user's token version to the deny list, revoke the refresh token family at the authorization server, and if it was a client credential or API key, rotate the secret. Remove or redact the exposed log or ticket (and know that copies may exist in log shippers and backups).
  2. Assess: what could the token do? Check its scope, audience, tenant and expiry; a 5-minute token that has already expired is low risk, a long-lived service token is not. Query access logs for that jti or subject and look for use from unexpected IPs, user agents or odd hours, and for reads of other tenants' data.
  3. Notify: follow the incident process: security team, and the data owner or customer if data may have been accessed. Do not decide alone whether it is reportable.
  4. Find the root cause: which code or config logged the header or URL (debug request logging, an exception message, a query-string token)? Fix it and add the redaction test described earlier.
  5. Prevent: shorten lifetimes, add sender-constrained tokens for sensitive APIs, add secret scanning on logs and tickets, and add an alert for token use from new locations.
  6. Review afterwards: a blameless write-up with timeline, impact, fix, and follow-ups with owners.

What interviewers want to hear: speed of containment, honest scoping from evidence rather than assumption, and a systemic fix instead of only deleting the log line.

Remember: revoke first, scope from audit logs, fix the leak source, and make the fix testable.

Scenario: a critical CVE is announced in a library that your service only pulls in transitively. What do you do? Senior

Confirm whether you are really affected (version, feature, reachability), find which dependency brings it, apply the least risky fix (upgrade the parent, otherwise a constrained override), test, deploy within the SLA, and verify that the shipped artifact no longer contains the bad version.

  1. Affected? Search the SBOMs or run the dependency tree on every service and batch job. Read the advisory: which versions, which class or feature, which conditions (for example "only when parsing untrusted XML with option X").
  2. Exploitable here? Is the vulnerable path reachable from untrusted input in our code? A server processing user uploads is very different from a library used only by an offline test. Record the reasoning. Even if unlikely, plan the fix, because scanners and auditors will still flag it.
  3. Locate: mvn dependency:tree or gradle dependencyInsight to see the path.
  4. Choose the fix: bump the direct dependency or framework BOM if a patched release exists; otherwise add a dependency constraint to the fixed version with a comment naming the CVE; as a last resort exclude the module or apply a mitigation (disable the feature, a WAF rule).
  5. Verify: run unit and integration tests, check for runtime binary incompatibility (NoSuchMethodError), rebuild and rescan the image, and confirm the fixed version is on the final classpath.
  6. Roll out: by risk. Critical and internet-facing first, via the normal pipeline with a rollback ready. Track in the ticket against the SLA.
  7. Close the loop: if you could not answer step 1 quickly, improve the SBOM process; if the fix needed an override, set a reminder to remove it when the parent catches up.

Scenario: a customer reports seeing another tenant's preferences in their UI. How do you investigate and fix it? Senior

Treat it as a severity-one data exposure. Stop the bleeding (feature flag, cache flush or isolating the path), reproduce with two tenants, find the leak layer (cache key, ThreadLocal, query filter, or response caching), fix it centrally, then add the two-tenant regression test and assess who else was affected.

  1. Contain: if a cache is suspected, flush the affected keys or disable the cache for that path through a flag; this is cheap and reversible. Notify security and the incident owner.
  2. Gather facts: exact request, tenant id and user id of the victim, time, endpoint, response headers (was it served by a shared HTTP cache? check Cache-Control, Age, Vary), and the correlation id to trace logs across services.
  3. Hypotheses in order of likelihood:
    • Cache key without tenant (Redis, local cache, or HTTP cache): compare the key format to the code; look for two tenants sharing the same user ids.
    • Context leakage: a ThreadLocal not cleared, a pool thread reused, async work running without the tenant, or a singleton bean holding last-request state. Check logs: does the logged tenant for that thread change mid-request?
    • Query without tenant filter: a new native query, a repository method missing the predicate, or a batch job.
    • Trusting a client-sent tenant header or path value.
  4. Reproduce: two tenants, same ids, concurrent requests with a small thread pool. Reproduction in a test is the proof of the fix.
  5. Fix at the right layer: include the tenant in every cache key through a shared key builder, clear contexts in finally blocks in a single filter, enforce the tenant predicate via ORM filter or row-level policy so one missed query cannot leak.
  6. Scope the impact: from access logs determine which responses may have served the wrong tenant's data and to whom; give that to security and customer teams for notification decisions.
  7. Prevent: two-tenant integration test for every endpoint, code review checklist item, static checks for static mutable state.

Remember: contain with a flag or flush, reproduce with two tenants, fix at the shared layer, and assess exposure.

Scenario: after a signing key rotation, many clients suddenly get 401. What happened and what do you check? Intermediate

Almost certainly verifiers do not have the new key (stale JWKS cache) or the issuer started signing before the new key was published and cached everywhere. Check the kid in a failing token against the JWKS served and cached by each verifier, and the order of the rotation steps.

  1. Get one failing token and decode the header (not the secret parts): note kid and alg. Check the logs of the verifier for the exact error (unknown kid, signature mismatch, expired, bad issuer).
  2. Compare with the JWKS: does the public JWKS endpoint include that kid? If not, the key was removed or never published. If yes, the verifier's cache is stale or it cannot reach the endpoint (network policy, certificate problem).
  3. Check the rotation order: the correct order is publish new key, wait for caches, switch signing, wait for old tokens to expire, remove old. If the old key was removed early, tokens still in flight fail.
  4. Mixed environments: a canary or region that still holds an old key set; gateways with their own longer cache.
  5. Mitigate: restore the removed key to the JWKS (fastest), restart or refresh verifiers' key caches, and clients that refresh will recover on their own with new tokens.
  6. Prevent: a runbook with the four-step order, a cache TTL shorter than the wait time, a refetch-on-unknown-kid behavior with rate limiting, and a synthetic check that verifies a fresh token end to end after rotation.

Remember: unknown-kid 401s after rotation mean key publication or cache order was wrong; restore the key, then fix the runbook.

Scenario: the OTP endpoint shows a spike of failures from thousands of IPs, each with a few attempts. What is happening and what do you do? Intermediate

It looks like a distributed guessing or credential-stuffing attack, built to stay under per-IP limits. Add per-account and global limits, challenge suspicious traffic, and make sure OTP attempts are capped per code so success is statistically unreachable.

  • Confirm: group failures by account id, not IP. If many different accounts get one or two failures each, it is stuffing; if the same few accounts are hit from many IPs, it is distributed brute force on specific targets.
  • Immediate controls: per-account attempt limit and lock (temporary), global rate limit on the endpoint, CAPTCHA or an extra challenge for high-risk patterns, block or challenge known bad networks at the edge, and temporarily raise logging at the gateway for the endpoint.
  • Check the math: if each code allows only 5 attempts and expires in a few minutes, the chance to guess a 6-digit code is about 5 in a million per code. The danger is any path that lets the attempt counter reset (for example requesting a new code resets the counter, allowing endless fresh attempts at the same account). Also check there is a limit on code requests.
  • Look for success: were any of these accounts successfully logged in after failures? Force a re-verification for those and notify owners.
  • Follow up: alerting on failure ratio, device and location signals, and a review of whether the response differs between valid and invalid accounts (enumeration).

Remember: count by account as well as IP, cap attempts per code and per account, and never let a resend reset the counter.

Scenario: you want to retire V1 of your API but are unsure who still uses it. How do you proceed? Senior

Measure first. Add per-client usage metrics for V1, announce a sunset date with response headers and direct outreach, run brown-outs to flush out silent callers, and remove only when traffic is zero or the remaining callers have signed off.

  1. Inventory: add a metric on every V1 request tagged with client id (from the token or API key), endpoint and tenant; build a dashboard and an alert for new V1 callers. Look at logs for several weeks to catch monthly or quarterly batch callers.
  2. Announce: publish the deprecation date and migration guide; add Deprecation and Sunset response headers to V1; email owners found in the metrics.
  3. Help migrate: a diff of V1 versus V2 behavior, updated client library, and a compatibility note for any breaking semantic changes.
  4. Brown-out: in the final weeks, return errors for a short window (for example an hour) on a schedule, which reveals callers who ignored mail. Use a clear error with a link to the migration doc.
  5. Shut off: after zero or accepted traffic, return 410 Gone for a period, then delete code, specs, tests and generated clients.
  6. Meanwhile: keep security fixes applied to V1, since an old version is still attack surface, and make sure the shared service layer means a fix applies to all versions.

Remember: measure real usage per client, announce with headers, brown-out to find stragglers, and keep V1 patched until it is gone.

Scenario: a penetration test shows a service can be called directly inside the cluster without going through the gateway, and it trusted an X-User-Id header. What do you fix? Senior

The service must not trust identity just because a request arrived from inside the network. Make the service verify credentials itself (validate the JWT), or accept identity only over mTLS from the gateway, strip identity headers at the edge, and add network policies so only the gateway can reach it.

  1. Severity: any pod that can reach the service can impersonate any user or tenant by setting a header. Treat it as high.
  2. Fix in layers:
    • Service verifies the token as a resource server (signature, issuer, audience), and takes the user and tenant from verified claims, not headers.
    • If the design needs gateway-injected headers, require mTLS from the gateway's identity and ignore the headers otherwise; the gateway removes any client-supplied copy before injecting its own.
    • Network policy: only the gateway namespace or service account may reach the service ports; deny all other ingress.
    • Service mesh authorization policy (if used) restricting callers by identity.
  3. Check siblings: other services copying the same pattern; actuator and admin ports; message consumers that read identity from message bodies.
  4. Test: an integration test that calls the service with a forged header and no token and expects 401, and another with a token for tenant A and a header for tenant B expecting the token to win.

This is the practical meaning of zero trust: the gateway is a convenience for common checks, not the only gate.

Remember: never trust an identity header by network location; verify tokens or mTLS in the service and restrict who can reach it.

Scenario: customers report duplicate charges or duplicate orders after a gateway timeout. How do you diagnose and fix it? Senior

The client timed out, retried a non-idempotent POST, and the first request had in fact succeeded. Confirm from logs, then make the operation idempotent with an idempotency key and a unique constraint, and align timeouts and retry rules across client, gateway and service.

  1. Confirm: for a duplicated pair, find both requests by customer and time. Look at their correlation ids: was the first one logged as completed after the client gave up (a timeout at the gateway, while the service kept working)? Different request ids with the same payload a few seconds apart is the signature.
  2. Find who retried: the mobile app, the SDK, the gateway (many gateways retry upstream failures by default; retrying POST is dangerous), or a message redelivery after a slow consumer ack.
  3. Timeout mismatch: if the gateway timeout (say shorter) is below the service's real processing time, the client sees a failure while work completes. Align: client timeout greater than gateway greater than service budget, with the work itself bounded.
  4. Fix: accept an idempotency key on the POST and enforce it with a unique constraint plus stored response; add a business-level uniqueness rule where one exists (for example one order per client reference); disable automatic gateway retries for non-idempotent routes.
  5. For queues: consumers de-duplicate by message id inside the same transaction as the side effect, because at-least-once delivery will produce duplicates sooner or later.
  6. Clean up: identify and reverse duplicates already created, and monitor the duplicate rate afterwards.

Remember: a retried POST after a timeout duplicates work unless an idempotency key and a unique constraint stop it.
