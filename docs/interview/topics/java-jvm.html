Java JVM, memory and GC interview questions

How a Java program really runs, where its memory goes, how garbage collection works, how to pick a collector, and how to debug leaks, OutOfMemoryError, slow starts and container kills. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

This page covers the runtime side of Java. For language basics see Java fundamentals, for threads and the memory model Java concurrency, and for newer language features Modern Java.

Version notes. Long-term-support (LTS) releases are 8, 11, 17, 21 and 25. The default collector is Parallel GC in Java 8 and G1 from Java 9 on (when the JVM sees at least 2 CPUs and about 1.8 GB of memory, otherwise Serial). Metaspace replaced PermGen in Java 8. CMS was removed in Java 14. ZGC became production-ready in 15, and its generational mode arrived in 21. Details of flags can change between versions, so check java -XX:+PrintFlagsFinal on your own JDK.

Mental model: the 8 ideas everything hangs on

One line: your code is compiled to portable bytecode, loaded by class loaders, run first by an interpreter and then by a JIT compiler, and every object lives on a garbage-collected heap that the JVM cleans by finding what is still reachable.
  1. Write once, run on a JVM. javac turns source into bytecode in .class files. The JVM, not the CPU, runs bytecode.
  2. Classes load lazily. A class loader finds the bytes, the JVM verifies them, and static initializers run only on first use.
  3. Memory is split by purpose. Heap (objects, shared), thread stacks (method calls, one per thread), metaspace (class metadata, native), plus code cache and direct buffers. The heap is only part of what the process uses.
  4. Garbage means unreachable. The collector asks "can I still reach it from a root?" (thread stacks, static fields), never "will the code use it?". So a forgotten reference is a leak.
  5. Most objects die young. The heap has a small young area collected often and cheaply, and a large old area collected rarely.
  6. Every collector trades three things: throughput, pause time and memory footprint. You cannot maximise all three.
  7. The JIT makes Java fast after warm-up. Hot methods become machine code using runtime knowledge. The first minutes are slower.
  8. In a container the process budget is bigger than the heap. The limit must also cover metaspace, stacks, code cache and direct memory.

1. Platform and startup

What is the difference between the JDK, the JRE and the JVM? Basic

The JVM is the engine that runs bytecode. The JRE is the JVM plus the standard class library, which is what you need to run a program. The JDK is the JRE plus developer tools like javac, jar, jcmd and jfr, which you need to build and diagnose one.

Bytecode is the portable instruction set that javac produces in .class files. The same jar runs on any OS because each OS has its own JVM that understands bytecode. Since Java 11 Oracle and OpenJDK no longer ship a separate JRE download; you either install a JDK or build a trimmed runtime with jlink. In production images I still want a JDK (or at least jcmd), because without it I cannot take a thread dump or heap dump from a running process.

Remember: JDK = JRE + tools, JRE = JVM + libraries. JVM runs bytecode, javac makes it.

What happens when you run java Main? Walk me through it. Intermediate

The launcher starts a JVM process, which sets up the heap and other memory areas, loads core classes, then uses a class loader to find Main. The class is loaded, verified and initialized, and the JVM calls main. The method first runs in the interpreter, and the JIT compiler turns it into machine code once it proves hot.

Class loading is lazy: other classes are loaded the first time code touches them, not at startup. The garbage collector threads and JIT compiler threads start with the JVM, in the background. That is why a Java program starts slowly and then speeds up: the first calls run as slow interpreted code while the JVM profiles them. The program ends when main returns and all non-daemon threads have finished, or on System.exit.

java -cp app.jar com.acme.Main
# 1 start JVM, reserve heap  2 load Main  3 verify, init statics
# 4 run main() interpreted   5 JIT compiles hot methods

Remember: start JVM, load classes lazily, interpret first, JIT the hot parts. The JVM exits when the last non-daemon thread ends.

Which garbage collector is the default in each Java version? Intermediate

Java 8 defaults to Parallel GC. From Java 9 onwards the default is G1, but only if the JVM sees at least 2 CPUs and about 1.8 GB of memory. On a smaller machine or container it silently falls back to Serial GC.

This matters because a tiny pod (1 CPU, 1 GB) quietly gets the single-threaded Serial collector with no warning, and teams then wonder why GC behaves differently than on their laptop. The GC log first line shows which collector is really in use: Using G1 or Using Serial. For the LTS releases: 8 (Parallel), 11 and 17 (G1, with CMS removed in 14), 21 (G1, with generational ZGC available), 25 (G1; ZGC is generational only). I always set the collector explicitly in production so it never depends on the machine size.

Remember: Parallel in 8, G1 from 9, but Serial on a machine under 2 CPUs or about 1.8 GB. Pin it with a flag.

2. Class loading

What is a class loader, and what are the built-in ones? Basic

A class loader finds the bytes of a class by name and turns them into a Class object in the JVM. There are three built in: the bootstrap loader for core JDK classes, the platform loader for other JDK modules, and the application loader for my classpath.

The bootstrap loader is written in native code, so String.class.getClassLoader() returns null. Before Java 9 the middle one was called the extension loader. A class's identity in the JVM is its name plus the loader that defined it. The same class file loaded by two different loaders gives two unrelated types, and casting between them fails with ClassCastException. App servers, plugin systems and frameworks use this on purpose to isolate applications.

Remember: bootstrap, platform, application, then custom. Class identity = name + loader.

Explain the parent delegation model. Why does it exist? Intermediate

Before a loader loads a class itself, it asks its parent to try first, all the way up to bootstrap. Only if every parent fails does the child load it. This guarantees that core classes like java.lang.String always come from the JDK, so nobody can slip in a fake one by putting it on the classpath.

It also avoids loading the same class twice, since a shared parent loads it once for everyone below. The cost is that a parent can never see classes only a child knows about. That is the reason for the context class loader, which libraries like JNDI or JDBC use to look down at application classes. Web containers such as Tomcat deliberately break the rule: a webapp loader looks in its own WEB-INF/lib first, so each app can ship its own library versions.

Remember: ask the parent first. It protects core classes and loads shared classes once. Web containers reverse it for webapps.

What are the phases of loading a class: loading, linking and initialization? Intermediate

Loading reads the class bytes and creates the Class object. Linking has three steps: verify the bytecode is safe, prepare static fields with default values (0, null), and resolve references. Initialization then runs static initializers and sets static fields to their real values, and it happens only on first active use.

First active use means new, calling a static method, reading a non-constant static field, or Class.forName. Using a static final compile-time constant does not trigger it, because the value is inlined at compile time. Initialization is thread-safe: the JVM holds a lock per class, so a static initializer runs exactly once. If it throws, the class is marked broken, and later uses throw NoClassDefFoundError: Could not initialize class. Two threads whose static initializers wait on each other's class can deadlock.

Remember: load, link (verify, prepare, resolve), then initialize lazily and once. A failed initializer poisons the class.

ClassNotFoundException versus NoClassDefFoundError: what is the difference and how do you debug each? Intermediate

ClassNotFoundException is a checked exception thrown when code asks for a class by name at runtime, for example Class.forName("x.Y"), and the loader cannot find it. NoClassDefFoundError is an error: the class was there when the code was compiled, but the JVM cannot find or initialize it now. The first is a "wrong name or classpath" problem. The second is usually a packaging, version or static-initializer problem.

For ClassNotFoundException I check the class name, the classpath and, for plugin or reflection code, which loader is being used. For NoClassDefFoundError I look at the message. If it says Could not initialize class X, an earlier static initializer of X failed, so I find that first exception higher in the logs. Otherwise the jar is missing at runtime, often a dependency that was provided or optional at build time, or two versions of a library on the classpath. mvn dependency:tree and -verbose:class show what really loaded.

Remember: Exception = I asked by name and it is not there. Error = it was there at compile time but is missing or broken now.

What is a class loader leak, and how does it show up on redeploys? Senior

When an app is undeployed, its class loader and every class it loaded can only be freed if nothing outside still references any of them. If something does, for example a thread, a ThreadLocal or a driver registered in a parent-loader singleton, the whole old app stays in memory. After a few hot redeploys OutOfMemoryError: Metaspace appears.

A class keeps a reference to its loader, and a loader to all its classes. So one stray reference to one class pins everything. Classic culprits: a JDBC driver registered in DriverManager (a parent-loader object) and never deregistered, a non-daemon thread started by the app, a ThreadLocal value on a pooled server thread whose class came from the webapp, and a shutdown hook. The proof is in a heap dump: count instances of the loader class (WebappClassLoader) and trace the GC root path of an old one. The fix is cleanup in the context-destroyed callback, or simply restarting the server instead of hot redeploying.

Remember: one reference into the old loader keeps the whole old app alive. Restart instead of hot redeploy.

3. Memory areas, objects and allocation

What are the JVM runtime memory areas? Basic

The heap holds all objects and is shared by all threads. Each thread has its own stack with one frame per method call. Class metadata (the structure of each loaded class) lives in metaspace, which is native memory. On top of that the process uses the code cache for JIT-compiled code, and direct buffers and other native memory.

The heap is the area I tune with -Xmx, but it is only part of the process footprint. A service with -Xmx2g can easily use 3 GB in total. That gap is the root of most container kills. Each thread stack is about 1 MB by default on 64-bit Linux (-Xss), so 500 threads cost around 500 MB outside the heap.

Remember: heap shared, stacks per thread, metaspace for classes. Process memory is more than heap.

What lives on the stack and what lives on the heap? Basic

Local variables and method call frames live on the thread's stack: primitives directly, and for objects only the reference. The objects themselves are on the heap. So Order o = new Order() puts the reference o on the stack and the Order object on the heap.

The stack is private to a thread, which is why locals are naturally thread-safe, and it is freed automatically when the method returns, with no GC involved. Heap objects are shared and need the garbage collector. Fields of an object, including its primitive fields, sit inside the object on the heap. One nuance: the JIT can use escape analysis to avoid allocating an object at all if it never leaves the method, so "all objects are on the heap" is the language model, not always the machine reality.

Remember: references and primitives in locals go on the stack, objects go on the heap.

How is the heap organised into generations? Explain Eden, Survivor and Old. Intermediate

The heap is split into a young generation and an old generation, because most objects die very young. New objects are allocated in Eden. A young GC copies the survivors into one of two small Survivor spaces, and objects that survive enough rounds are promoted to the old generation, which is collected rarely.

The idea is cost: a young collection only touches live objects, and most of Eden is already dead, so it is fast. Each survivor of a young GC gets its age incremented. When the age reaches a threshold (up to 15, adjusted by the JVM), or when the survivor space is too full, the object is promoted. Old-generation collections are more expensive, so I want only long-lived data to end up there. Note that G1, ZGC and Shenandoah split the heap into many regions instead of fixed contiguous areas, but they still keep the young and old idea.

Remember: allocate in Eden, copy survivors, promote the old ones. Keep short-lived garbage out of Old.

What happened to PermGen, and what is Metaspace? Intermediate

PermGen was a fixed-size area inside the heap that held class metadata and was a common source of OutOfMemoryError. Java 8 removed it. Metaspace replaces it, stores the same class metadata in native memory, and grows on demand by default, up to the OS or container limit.

Because it is not capped by default, a class-loader leak or heavy runtime class generation (proxies, scripting) no longer fails fast: it quietly eats native memory until the container is killed. So I set -XX:MaxMetaspaceSize (for example 256m) to get a clear OutOfMemoryError: Metaspace instead. Interned strings and static fields moved to the normal heap already in Java 7. Metaspace is freed only when the class loader that defined the classes becomes unreachable and a GC runs.

Remember: Metaspace = class metadata in native memory, uncapped by default. Cap it to fail fast.

How much memory does an object take, and why does it matter? Senior

Every object carries a header of about 12 bytes on a typical 64-bit JVM with compressed pointers (16 bytes without), and its total size is rounded up to a multiple of 8. So an Integer holding 4 bytes of data takes 16 bytes, and an empty Object takes 16. Many tiny objects waste far more memory than the data inside them.

A String of 10 characters is the String object plus a separate byte array, about 56 bytes in total. A HashMap<Integer,Integer> entry costs roughly 60 to 80 bytes counting the entry node and two boxed integers, for 8 bytes of real data. This is why a "small" 100 MB dataset can take 1 GB in a Java collection, and why primitive arrays or specialised collections win for big data. Newer JDKs can shrink the header to 8 bytes with compact object headers (a feature that became standard only in recent releases, so check your version). To measure real sizes I use the JOL tool or a heap dump, not guesses.

Remember: header plus padding makes small objects expensive. Fewer objects, more primitives.

Trace the life of an object from new to being freed. Intermediate

The JVM allocates the object in Eden, from a thread-private slice so no locking is needed. If it dies before the next young GC it costs almost nothing, because the collector only copies live objects. If it survives it is copied between survivor spaces, getting older each time, and is finally promoted to old, where only a less frequent old collection frees it.

The fast allocation is a pointer bump inside a per-thread buffer (a TLAB, thread-local allocation buffer), so new is a handful of instructions. Objects larger than the TLAB are allocated more slowly, and in G1 very big ones go straight to special humongous regions. An object becomes garbage the moment no root can reach it, but memory is only reclaimed at the next collection that covers its area. The cheap path (die young) is the one to aim for: lower allocation rate and short object lifetimes mean fewer promotions.

Remember: allocation is a pointer bump, dying young is free, surviving is what costs.

The heap is 2 GB but the process uses 3.5 GB. Where does the rest go? Senior

The rest is everything outside the heap: metaspace, thread stacks, the JIT code cache, direct buffers, GC bookkeeping structures and native libraries. A typical service easily adds 25 to 50 percent on top of -Xmx, and more with many threads or heavy NIO.

The way to see it is Native Memory Tracking: start with -XX:NativeMemoryTracking=summary, then run jcmd PID VM.native_memory summary. It lists each category in MB. If the numbers add up to the process size, the breakdown tells me which area to tune. If they do not, the gap is native code outside the JVM's accounting, for example a JNI library, or glibc malloc arena fragmentation. On Linux, many threads can create many malloc arenas, and setting MALLOC_ARENA_MAX=2 can reduce this.

java -XX:NativeMemoryTracking=summary -jar app.jar
jcmd PID VM.native_memory summary

Remember: RSS = heap + metaspace + stacks + code cache + direct + native. Use NMT to see which.

What causes StackOverflowError and how do you fix it? Basic

Each method call pushes a frame on the thread's stack, and the stack has a fixed size (about 1 MB by default). If calls nest too deeply, usually through unbounded or accidental recursion, the stack runs out and the JVM throws StackOverflowError. The real fix is to correct the recursion, not to raise the stack size.

In a stack trace I look for a repeating pattern of the same few methods. Typical production causes: a cyclic object graph with a toString, equals or hashCode that walks both directions (parent to child to parent), a JSON serializer on a bidirectional JPA relationship, or recursion on deeply nested data (a very deep linked list or user-supplied nested JSON). Fixes: break the cycle (@JsonIgnore, exclude the back reference), convert recursion to a loop with an explicit stack or queue, or limit input depth. -Xss is a last resort, because it is multiplied by every thread. Note this is an Error, but it only kills the current thread's work, not the JVM.

Remember: stack overflow = runaway recursion. Find the repeating frames and break the cycle.

4. References, strings and cleanup

Explain strong, soft, weak and phantom references. When would you use each? Intermediate

A strong reference is the normal one and keeps its object alive. A soft reference is cleared only when the JVM is short on memory, so it suits caches. A weak reference is cleared at the next GC once nothing strong refers to the object, so it suits canonical maps like WeakHashMap. A phantom reference is for cleanup actions after an object is collected, and you can never get the object back from it.

All three weaker kinds can be registered with a ReferenceQueue, so I get notified when the target is cleared. In practice: I avoid SoftReference caches in servers, since their behaviour depends on GC and heap size, and use a bounded cache like Caffeine instead. Weak references are used by ThreadLocal map keys and WeakHashMap keys. Phantom references power java.lang.ref.Cleaner, the modern replacement for finalizers.

Remember: strong keeps, soft = low-memory cache, weak = next GC, phantom = cleanup hook.

What is the String pool, and what is the difference between new String("a") and "a"? Basic

The string pool is a cache of unique string values that lives in the heap. A literal like "a" is taken from the pool, so two identical literals are the same object. new String("a") always creates a new separate object on the heap, so == between it and the literal is false.

That is why strings must be compared with equals, not ==. s.intern() returns the pooled instance, adding it if missing. I do not use intern in application code: the pool is a hash table with a fixed bucket count that can become slow when it holds millions of strings, and it hides the real fix. For memory savings on many duplicate strings I would use G1's string deduplication (-XX:+UseStringDeduplication), which shares the underlying character arrays. The pool was moved from PermGen to the normal heap in Java 7, so it is garbage collected like other objects.

String a = "hi", b = "hi", c = new String("hi");
a == b            // true  (same pooled object)
a == c            // false (new object)
a.equals(c)       // true
a == c.intern()   // true

Remember: literals are pooled, new String is not. Compare with equals.

Why are finalize() and finalizers discouraged, and what replaces them? Intermediate

A finalizer runs at some unpredictable time after the object is unreachable, maybe never, on a special thread. It slows GC, can resurrect the object and hides bugs. Finalization is deprecated for removal (since Java 18). I use try-with-resources for anything that must be closed, and java.lang.ref.Cleaner as a safety net.

Objects with finalizers need extra GC passes: the first finds them unreachable and queues them, the finalizer thread runs them later, and only a following GC can free the memory. A slow or blocked finalizer then causes a pile of unreclaimed objects and eventually OutOfMemoryError. The right pattern is an AutoCloseable class used with try-with-resources, so cleanup is deterministic. If a leaked resource must still be released, register a Cleaner action that does not reference the object itself.

Remember: never rely on finalize. Close explicitly with try-with-resources, Cleaner as backup.

5. Garbage collection fundamentals

How does the JVM decide something is garbage? What are GC roots? Basic

An object is garbage if it cannot be reached from any GC root by following references. Roots are things that are always alive: local variables and parameters on thread stacks, static fields, active threads, JNI references and class loaders. The collector marks everything reachable from roots and treats the rest as free space.

This is tracing, not reference counting. Java does not count references, so two objects pointing at each other with no outside reference are both garbage: cycles are no problem. The flip side is the source of Java leaks: an object that is still reachable, for example from a static map, is never collected even if the code will never use it again. "Reachable" is not the same as "needed".

Remember: garbage = unreachable from roots. A forgotten reference is a leak, a cycle is not.

Explain mark-sweep, mark-compact and copying collection. What are the trade-offs? Intermediate

Mark-sweep marks live objects then frees the dead ones in place, which is simple but leaves holes (fragmentation). Mark-compact marks, then slides the live objects together, which removes holes but costs time moving them. Copying collection copies live objects into an empty space and discards the old one in one go, which is fast and compact but needs spare room.

Copying is perfect for the young generation: most objects are dead, so only the few survivors are copied, and cost is proportional to live data, not to the area size. Old generations hold mostly live data, so copying everything would be wasteful, and they use mark-compact (or region-based evacuation in G1). Compaction matters because without it a big array may not fit in free memory even when total free space is large. This is the reason CMS, which only swept, eventually hit slow full GCs when fragmentation built up.

Remember: sweep is cheap but fragments, compact is tidy but moves, copy is fast but needs spare space. Copy for young, compact for old.

Why are generational collectors a good idea, and what are minor, major, mixed and full GC? Intermediate

Because most objects die young (the weak generational hypothesis), collecting a small young area often is cheap and reclaims most garbage, while the large old area needs collecting rarely. A minor GC collects only young. A mixed GC (G1) collects young plus some old regions. A full GC collects the whole heap and is the slow one I want to avoid.

"Major GC" is a loose term; people mean an old-generation collection. In Parallel and Serial, a full GC stops the world for the whole heap and compacts. G1 only does a full GC when it falls behind, and the full GC is then single-threaded in older JDKs, so it can last many seconds. In logs, any "Pause Full" line is a red flag. Triggers include old being full, metaspace threshold, System.gc(), or a failed promotion.

TypeCollectsPause
Minor (young)Eden and survivorsShort, frequent
Mixed (G1)Young plus chosen old regionsBounded by the pause goal
FullEntire heap, with compactionLong, avoid

Remember: most objects die young, so collect young often. A full GC in the log means trouble.

What is a stop-the-world pause and what is a safepoint? Senior

A stop-the-world pause is a moment when the JVM freezes all application threads so it can do work that needs a stable heap, such as moving objects. A safepoint is the state the threads must reach first: each thread runs until it hits a safe spot, parks there, and then the JVM does its job.

Threads check for a safepoint request at safe locations such as method returns and loop back-edges. The pause is therefore time to reach the safepoint plus the work itself. One thread stuck in a long loop without such a check delays everyone (time-to-safepoint). Not only GC uses safepoints: biased-lock revocation in old JDKs, deoptimisation and some diagnostic operations do too. In a GC log, -Xlog:safepoint shows time spent reaching safepoints separately from the GC work. Concurrent collectors like ZGC and Shenandoah keep the stop-the-world parts tiny, and do most work while the app runs.

Remember: pause = time to bring all threads to a safepoint + the work done there.

What is premature promotion, and why does it hurt? Senior

Premature promotion is when short-lived objects get moved into the old generation too early, because the survivor space was too small or the young generation was too small for a burst of live data. They then die in old, where only an expensive old collection can remove them, so old fills up and full GCs start.

It looks like this in a GC log: the old generation after each young GC rises quickly and does not fall, and old collections become frequent even though the real long-lived set is small. Typical triggers are a young generation that is too small, a request burst holding many objects alive across a young GC, or big temporary buffers. Remedies: give the heap more room, stop pinning the young size too small, reduce how long request data stays alive (for example do not hold whole result sets in memory), and with G1 let it size the young generation instead of forcing -Xmn.

Remember: if old grows from short-lived data, fix the young size or the object lifetime, not the old collector.

6. The collectors: Serial, Parallel, G1, ZGC

Name the HotSpot garbage collectors and what each one is for. Basic

Serial is single-threaded, for tiny heaps and single-CPU containers. Parallel uses many threads to maximise throughput, good for batch jobs that tolerate pauses. G1 is the balanced default, with pause-time goals for most services. ZGC (and Shenandoah) aim at very short pauses on large heaps. CMS was an older low-pause collector and was removed in Java 14.

All the stop-the-world collectors freeze the app while they work, but Parallel uses many threads to do it faster. G1 splits the heap into regions and collects the ones with most garbage first. ZGC does nearly all its work concurrently, so its pauses stay below about a millisecond regardless of heap size, at the cost of some CPU and memory overhead. Shenandoah is a similar low-pause collector available in OpenJDK builds from Red Hat and others, but not in every vendor build.

CollectorGoalUse when
SerialSmall footprintTiny heaps, 1 CPU, small tools
ParallelThroughputBatch jobs, pauses are fine
G1Balance, pause goalMost services (the default)
ZGCVery low pauseBig heaps, strict latency

Remember: Serial small, Parallel throughput, G1 balanced default, ZGC low latency.

How does G1 work? Explain regions and the pause-time goal. Intermediate

G1 divides the heap into equal-sized regions (1 to 32 MB each). Any region can play the role of Eden, Survivor, Old or Humongous. It tracks how much garbage each region holds and, per collection, picks the regions that give the most space back within the pause goal (-XX:MaxGCPauseMillis, default 200 ms). That goal is a target G1 aims for, not a guarantee.

Because it works region by region, G1 can collect a chosen subset of the heap instead of everything, and it evacuates (copies) live objects out of the chosen regions into fresh ones, which compacts as a side effect. It adapts the size of the young generation to meet the pause goal. Lower the goal and young collections get smaller and more frequent, costing throughput. The name "Garbage First" means it picks the regions with the most garbage first.

Remember: G1 = regions, collect the most garbage first, aim at the pause goal. The goal is a target, not a promise.

Describe the phases of a G1 cycle: young, concurrent marking and mixed collections. Senior

G1 does normal young collections (stop-the-world, copy live objects). When the old generation passes a threshold of the heap (the initiating occupancy, 45 percent by default and adaptive in recent versions), it runs a concurrent marking cycle beside the app to find which old regions are mostly garbage. After that it runs several mixed collections that clean young plus those old regions. If marking cannot finish before the heap fills, G1 falls back to a full GC.

The concurrent part has short stop-the-world steps at the start (piggybacked on a young GC) and at the remark. Marking uses a snapshot-at-the-beginning technique so objects changed meanwhile are handled safely. A full GC is the failure case, caused by allocation outpacing marking, by humongous allocations, or by too small a heap. Typical fixes are more headroom, a lower initiating threshold, or more concurrent threads, but first I check that the live set is not simply too large for the heap.

Remember: young, then concurrent mark, then mixed. Full GC means marking lost the race.

What are humongous objects in G1, and why can they hurt? Senior

In G1 an object bigger than half a region is humongous. It is allocated directly into its own contiguous regions, outside the normal young path. These are expensive: they need contiguous free space, they fragment the heap, and they used to be reclaimed only after concurrent marking, so many of them cause early marking cycles and even full GCs.

With the default region size chosen from the heap, humongous starts at typically 512 KB to a few MB. Common sources are big byte arrays or buffers, large ArrayList backing arrays that grow by copy, large JSON or file contents read into a single array. How I confirm it: GC logs show "Humongous Allocation" as the cause of a GC. Fixes: allocate smaller chunks or stream the data, presize or avoid giant arrays, or increase the region size with -XX:G1HeapRegionSize (up to 32 MB) so fewer objects qualify. Newer G1 versions can reclaim humongous objects earlier, so the pain is lower in recent JDKs.

Remember: an object over half a region is humongous. Stream data instead of building giant arrays, or raise the region size.

How does ZGC achieve sub-millisecond pauses, and what does it cost? Senior

ZGC does almost all its work, including moving objects, concurrently while the application runs. The only stop-the-world steps are tiny ones that do not depend on heap size, so pauses stay around a millisecond or less even on multi-terabyte heaps. The price is some extra CPU, a bit more memory headroom, and a small cost on each object reference read.

The trick is the load barrier: a small check the JIT adds whenever the app loads an object reference. ZGC keeps metadata bits in the pointer itself (coloured pointers), so the barrier can notice that an object has moved and fix the pointer on the fly. That lets objects be relocated while threads are running. ZGC became production-ready in Java 15. Generational ZGC arrived in Java 21 (-XX:+UseZGC -XX:+ZGenerational) and from Java 23 is the default ZGC mode, with the single-generation mode removed in 24. The generational version handles high allocation rates much better because it collects young objects separately. ZGC needs spare heap, because it allocates while collecting: if allocation outruns collection, the app stalls ("allocation stall").

Remember: ZGC moves objects while the app runs, using load barriers. Pauses are tiny, you pay CPU and headroom.

How would you choose a garbage collector for a service? Senior

I start from the goal. For a normal web or microservice, G1 (the default) is fine. For a batch or offline job where only total time matters, Parallel. For a small container with 1 CPU or a tiny heap, Serial. If I have large heaps and strict tail-latency targets and G1 still shows pauses that hurt, I try generational ZGC. Then I confirm by measuring pauses and throughput under realistic load, not by assumption.

The trade-off triangle is throughput, pause time and memory. Parallel gives the best throughput but long pauses that grow with heap size. G1 trades a little throughput for bounded pauses. ZGC gives the shortest pauses but uses more CPU and memory. Before switching collectors I check that the problem is not really my allocation rate or a leak, because no collector fixes those. And I never decide from one benchmark: I compare p99 latency, GC pause totals and CPU on a production-like load test.

Remember: default G1, Parallel for batch, Serial for tiny, ZGC for strict latency. Measure, do not guess.

7. Tuning flags and reading GC logs

Which heap flags matter (-Xms, -Xmx, MaxRAMPercentage) and how do you set them? Basic

-Xmx is the maximum heap and -Xms the initial size. In production I set them equal, so the heap does not resize under load. In containers I prefer -XX:MaxRAMPercentage=70 (or about 60 to 75) over a fixed number, so the heap follows the container limit. The default is only 25 percent, which wastes memory.

Equal Xms and Xmx avoids the pause and cost of growing the heap and makes memory use predictable, at the price of committing it up front. I never set the heap equal to the container limit, since metaspace, stacks and direct buffers also need room. A rule of thumb is a heap of 60 to 75 percent of the limit, less if the service uses many threads or off-heap memory. -Xmn or NewSize pin the young size and stop G1 from tuning itself, so I avoid them with G1.

Remember: Xms = Xmx, and in a container use MaxRAMPercentage around 70, never 100.

Which other JVM flags would you put on every production service? Intermediate

Enough to get evidence and fail clearly: heap dump on OOM, GC logging, an exit on OOM so the orchestrator restarts a broken process, and a metaspace cap. I would add native memory tracking only when investigating.

-XX:MaxRAMPercentage=70
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/dumps          # a mounted volume, with space
-XX:+ExitOnOutOfMemoryError      # a half-dead JVM is worse than a restart
-XX:MaxMetaspaceSize=256m        # fail fast on class loader leaks
-Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m

Why exit on OOM: after an OutOfMemoryError some threads die and the service is often in a broken half-working state, and a restart is safer. The heap dump path must be on a volume that survives the restart and has enough space (a dump is about the size of the used heap). -Xlog is the unified logging flag from Java 9; Java 8 used -XX:+PrintGCDetails -Xloggc. I keep the flags in one place (a JAVA_TOOL_OPTIONS variable or the image entrypoint) so every service has them.

Remember: heap dump, GC log, exit on OOM, metaspace cap. Evidence first, tuning later.

How do you tune G1 to meet a latency target? Senior

First I measure where pauses come from in the GC log, then change one thing at a time. Usually the best step is not a flag but giving G1 more heap headroom and reducing allocation. After that I adjust MaxGCPauseMillis and look at young pause times and any full GCs, and I avoid pinning the young size.

  • Pauses long because a young GC copies a lot: lower the goal a little so G1 shrinks the young generation, or cut the allocation rate and survivor volume.
  • Full GCs or "to-space exhausted": not enough free space to evacuate. More heap, lower the initiating threshold (InitiatingHeapOccupancyPercent) or fix humongous allocations.
  • Long pauses with high system time: often the OS, such as swapping or a container with a CPU limit throttling GC threads, not G1.

The trap is a tuning spree: ten flags copied from a blog make behaviour worse and unexplained. If G1 cannot meet a strict target after sensible headroom, that is the signal to try ZGC rather than to tune further.

Remember: read the log, add headroom, cut allocation, change one flag at a time. If G1 still cannot meet the target, try ZGC.

How do you read a GC log? What numbers do you look at first? Intermediate

I look at four things: pause durations, how often collections happen, the heap occupancy after each collection, and any Full GC or evacuation failure lines. The "heap after GC" number is the most useful: if it keeps rising over hours, there is a leak or a too-small heap.

[12.345s][info][gc] GC(41) Pause Young (Normal) (G1 Evacuation Pause) 512M->180M(1024M) 8.2ms
[98.001s][info][gc] GC(97) Pause Full (G1 Compaction Pause) 1020M->700M(1024M) 2400ms

Reading the first line: before 512 MB, after 180 MB, total heap 1024 MB, pause 8.2 ms. The second is trouble: a Full GC of 2.4 seconds that only freed 320 MB, so the live set is about 700 MB in a 1 GB heap. Plotting the after-GC occupancy over time gives a sawtooth: the floor of the teeth is the live data. A rising floor means a leak. Then I check the total GC time share, which should be a few percent. Tools such as GCeasy or GCViewer turn logs into graphs.

Remember: watch pause time, frequency, and the after-GC floor. A rising floor is a leak, a Full GC is a warning.

How do you decide how big the heap should be? Senior

I measure the live set: the heap occupancy right after full or mixed collections under realistic load. Then I size the heap at about 3 to 4 times the live set, so the collector has room to work and does not run constantly. I check the result by looking at GC time share and pause times.

A small heap makes GC run often, with high CPU and more promotion. A very large heap makes each full GC (if it happens) long, wastes memory and, when above about 32 GB, loses compressed object pointers, which can make you worse off than at 31 GB. In containers the heap must also fit the memory budget with the non-heap parts. So the rule is: measure the live set, multiply, then check against the container limit, and re-measure after changes. Capacity needs change as data grows, so I watch the after-GC floor over weeks.

Remember: heap is about 3 to 4 times the live set. Measure it, do not guess.

8. Memory leaks and OutOfMemoryError

Java has a garbage collector. How can it still have memory leaks? Basic

A Java leak is an object that is no longer needed but is still reachable, so the GC cannot free it. Typical case: items added to a static or long-lived collection and never removed. The heap grows slowly until OutOfMemoryError, even though no memory was "lost" in the C sense.

The symptom is a rising floor in heap-after-GC and more and more frequent full GCs. The cause is nearly always a reference chain from a root, such as a static map, a cache without a limit, a listener never unregistered, a ThreadLocal on a pooled thread, or an unclosed resource. GC cannot know what the code intends. The fix is to find the chain in a heap dump and remove the reference at the right time, or to bound the structure.

Remember: a leak in Java = still reachable but no longer needed. Find the chain from a root.

What are the most common causes of memory leaks in real Java services? Intermediate

The usual suspects are unbounded caches or static maps, listeners and callbacks registered but never removed, ThreadLocal values on pooled threads that are never cleared, unclosed resources (streams, connections, sessions), and inner classes holding a hidden reference to their outer object.

  • Static or long-lived collections: a Map used as a cache with no size limit or expiry. Use Caffeine with a maximum size and TTL.
  • Listeners and event buses: register without unregister. Object lives as long as the bus does.
  • ThreadLocal: thread pool threads live forever, so a value set per request stays unless I call remove() in a finally.
  • Bad keys: mutable keys or missing hashCode and equals make map entries pile up as duplicates.
  • Class loaders: redeploys that keep the old loader alive (see the class loader leak question).
  • Inner classes and lambdas: capture this and keep the whole outer object alive.

Remember: unbounded cache, un-removed listener, uncleared ThreadLocal. Bound it, unregister it, remove it in finally.

How do you find a memory leak in a running production service? Senior

First confirm it is a leak: heap-after-GC keeps rising over time. Then compare two heap histograms taken some time apart to see which class count grows, take a heap dump, and open it in Eclipse MAT or VisualVM to find what holds those objects. The GC root path shows the exact reference chain to cut.

  1. Confirm: GC log or metrics show a rising floor (not just a high heap, which can be normal).
  2. Narrow down: jcmd PID GC.class_histogram twice, 10 minutes apart. The class whose count and bytes grow is the suspect.
  3. Capture: jcmd PID GC.heap_dump /dumps/h.hprof, or rely on -XX:+HeapDumpOnOutOfMemoryError. Take it off the hot path (see the heap dump scenario).
  4. Analyse: in MAT use the leak suspects report and the dominator tree, then "path to GC roots, excluding weak references" for one suspect object.
  5. Fix and verify: remove or bound the reference, deploy, and confirm the floor is flat.

Remember: rising floor, then histogram diff, then heap dump, then GC root path. Fix and re-measure.

In a heap dump, what are shallow size, retained size, the dominator tree and the GC root path? Senior

Shallow size is the memory of the object itself. Retained size is the memory that would be freed if that object were removed, meaning the object plus everything reachable only through it. The dominator tree orders objects by retained size, so the biggest holders of memory are at the top. The GC root path shows the chain of references that keeps an object alive.

Shallow size is misleading: a HashMap object itself is small, but it may retain gigabytes through its entries. So I sort the dominator tree by retained size and look for one object that retains a surprising amount, such as a cache or a session store. Then I take one instance of the leaking type and choose "path to GC roots, exclude weak and soft references" in MAT. The first strong link out of a root, such as a static field, tells me which line of code to fix.

Remember: sort by retained size, then follow the root path. Shallow size alone misleads.

What kinds of OutOfMemoryError are there, and what do you do for each? Intermediate

The message after OutOfMemoryError: tells the area that ran out. Each one points to a different fix, so I read the message first.

MessageMeaningFirst step
Java heap spaceHeap full of live dataHeap dump: leak or just too small?
GC overhead limit exceededOver 98% of time in GC, under 2% freed (mostly Parallel GC)Same as heap space. Do not disable the check.
MetaspaceToo many classesClass loader leak or runaway class generation
Unable to create native threadOS or container refused a new threadToo many threads, check limits
Direct buffer memoryOff-heap buffers over limitLeaked or unreleased buffers
Requested array size exceeds VM limitOne huge arrayFix the code that sizes it

"GC overhead limit exceeded" is only a symptom of a nearly full heap: turning the check off just makes the app crawl for longer before it fails with plain heap space. The first response for any heap OOM is the heap dump captured by -XX:+HeapDumpOnOutOfMemoryError. Raising the heap is only right when the live set is legitimately bigger than the heap.

Remember: read the message after OutOfMemoryError. It names the area, and each area has its own fix.

What is the difference between a Java OutOfMemoryError and the Linux OOM killer? Senior

An OutOfMemoryError is raised inside the JVM when a JVM-managed area is full, usually the heap, and I get a stack trace and possibly a heap dump. The OOM killer (or Kubernetes OOMKilled) is the operating system killing the whole process with SIGKILL (exit code 137) when total memory use goes over the limit. The JVM gets no chance to log anything.

So a killed pod with a healthy-looking heap graph means the non-heap memory grew: threads, metaspace, direct buffers, native libraries, or the heap simply set too close to the limit. The investigation is different: use Native Memory Tracking, check kubectl describe pod for the OOMKilled reason, and compare container memory against heap. Fix by lowering the heap share, capping the off-heap areas, or raising the limit.

Remember: OutOfMemoryError is the JVM complaining. Exit 137 is the OS killing it, usually from non-heap growth or a heap set too big.

What causes "OutOfMemoryError: unable to create native thread"? Senior

The JVM asked the OS for a new thread and the OS said no. It is not about the heap. Typical reasons are an unbounded number of threads (a thread per request, or leaked thread pools), an OS or container limit on processes or PIDs, or not enough native memory left for another stack.

Each thread reserves its stack (about 1 MB by default) outside the heap, so thousands of threads use gigabytes. Diagnose with a thread dump: count threads and group them by name to see which pool is exploding. Then check ulimit -u and the container PID limit. Fixes: bound the pools (use a fixed or bounded executor, not newCachedThreadPool for unbounded work), fix code that creates a pool per request, reduce -Xss if safe, or on Java 21 use virtual threads for blocking I/O work, which need no OS thread each.

Remember: too many threads, not too little heap. Count and bound them.

What are direct buffers, and how can they cause an OutOfMemoryError while the heap looks fine? Senior

A direct buffer (ByteBuffer.allocateDirect) is memory outside the heap, used by NIO and Netty to avoid a copy when talking to the OS. The small Java object on the heap owns a large native block. The native block is freed only when that heap object is garbage collected, so if the heap is quiet, GC does not run, the native memory is not released, and I can hit the direct limit with a healthy heap.

The limit is -XX:MaxDirectMemorySize, which defaults to roughly the max heap size. The message is OutOfMemoryError: Direct buffer memory. Causes: buffers not released (Netty ByteBuf without release() is the classic leak), or allocating a new direct buffer per request instead of pooling. Fixes: pool and reuse buffers, release reference-counted buffers in finally, enable Netty's leak detector in test, and set the direct memory limit deliberately. Never call System.gc() to hide it.

Remember: direct buffers live off-heap but are freed by heap GC. Pool them, release them, and budget for them.

9. JIT, warm-up and native image

What is the JIT compiler, and why does Java need it? Basic

The JIT (just-in-time) compiler turns hot bytecode into optimised machine code while the program runs. Interpreting bytecode is slow, and compiling everything upfront would waste time on code that rarely runs. So the JVM starts by interpreting, counts how often methods and loops execute, and compiles only the hot ones.

Because it compiles at run time, it knows facts a static compiler cannot: which classes are actually loaded, which branch is taken 99.9 percent of the time, which method calls are always on the same type. It uses these to optimise aggressively, with a safety net: if an assumption later breaks, the JVM throws away the compiled code and falls back to the interpreter (deoptimisation). That is how Java can approach the speed of C++ for long-running code.

Remember: interpret first, compile the hot parts with runtime knowledge, deoptimise if a guess breaks.

Explain tiered compilation, C1 and C2, and inlining. Intermediate

HotSpot has two JIT compilers. C1 compiles quickly with light optimisation, so code gets faster soon. C2 compiles slowly with heavy optimisation for the hottest code. Tiered compilation uses both: interpreter first, then C1 (collecting profile data), then C2 for what stays hot. The most valuable optimisation C2 does is inlining.

Inlining means pasting a small called method's body into the caller. It removes call overhead, but more importantly it lets the compiler see across method boundaries, which enables other optimisations such as escape analysis (an object that never leaves the method may not be allocated on the heap at all) and dead code removal. This is why many small, simple methods and getters cost nothing in Java. Inlining is limited by method size and depth, so a giant method may not be inlined or even compiled well.

Remember: interpreter, C1, C2. Inlining is the big win because it unlocks the other optimisations.

Why is a Java service slow right after start, and what can you do about it? Intermediate

Right after start the code runs in the interpreter and the JIT has not compiled it yet, classes are still loading, and caches are cold. It is normally slow for seconds to minutes until hot paths are compiled. To reduce it, I warm up the instance before sending real traffic, ramp traffic up gradually, and consider class data sharing or native image for startup.

Practical steps: a readiness probe that only turns ready after a warm-up phase (call the main endpoints a few thousand times with synthetic requests), slow-start or ramp-up in the load balancer so a new pod gets a trickle first, and avoiding CPU limits so tight that the JIT compiler threads starve. Application Class Data Sharing (AppCDS) speeds up class loading, and checkpoint-restore (CRaC) or GraalVM native image address startup more radically. Also remember a rolling deployment replaces fast instances with cold ones, so a latency spike after each deploy is expected without these.

Remember: cold JVM = interpreter plus cold caches. Warm up before taking traffic, and ramp it slowly.

What is GraalVM native image, and what are the trade-offs? Intermediate

Native image compiles a Java application ahead of time into a standalone native executable. It starts in milliseconds and uses much less memory, which is great for serverless and short-lived or scale-to-zero services. The trade-offs are a longer, heavier build, usually lower peak throughput than a warmed-up JIT, and restrictions around reflection, dynamic proxies and dynamic class loading.

It works with a closed-world assumption: at build time it analyses what is reachable and drops the rest, so anything found only at runtime (reflection, resources, JNI) must be declared in configuration files or hints. Spring and Quarkus generate much of this for you. The GC in native image is simpler than HotSpot's, and there is no runtime profiling, so very long-running, CPU-heavy services often run faster on the normal JVM. I choose native image when startup time and memory matter more than peak speed, and stay on the JVM for steady, long-running services.

Remember: native image = fast start, small memory, lower peak, closed world. JVM = slow start, best peak.

10. The JVM in containers

Is the JVM aware of container limits? What does it do with them? Intermediate

Yes. Modern JVMs (8u191 and later, and 10 and later) read the container's cgroup limits for memory and CPU. The default heap is then 25 percent of the container memory, and the number of CPUs it sees (which drives GC threads, JIT threads and availableProcessors()) comes from the CPU limit, rounded up.

Two consequences matter. First, the default 25 percent is too low for most services, so set -XX:MaxRAMPercentage explicitly. Second, a CPU limit below 2 makes the JVM think it is on a tiny machine and choose Serial GC, and a limit of 1 CPU gives one GC thread and a slow JIT. Older JVMs (before 8u191) ignored cgroups and sized themselves from the host's memory, which led to instant OOM kills. Check what the JVM sees with java -XX:+PrintFlagsFinal -version | grep -E "MaxHeapSize|UseG1|ActiveProcessorCount".

Remember: the JVM reads the cgroup limit. Set MaxRAMPercentage yourself, and mind a CPU limit under 2.

How do you size container memory for a Java service? Senior

I add up everything the process uses, not just the heap: heap, metaspace, thread stacks, code cache, direct memory and some native overhead, plus a safety margin. As a starting rule the heap is 60 to 75 percent of the limit. Then I confirm by watching the real resident memory under load, and set the limit with headroom above it.

Example for a 2 GB limit: heap 1.3 GB, metaspace about 100 MB, 100 threads at 1 MB is 100 MB, code cache 50 to 100 MB, direct buffers 100 MB, plus about 100 MB for GC structures and native libraries. That is about 1.9 GB, which is too close. So either I raise the limit to 2.5 GB or lower the heap to 1.1 GB. For memory, I set the request equal to the limit, since memory is not compressible: if the pod exceeds the limit, it is killed. Heavy NIO or many threads push the non-heap share higher, so a service with Netty and 400 threads needs a lower heap percentage.

Remember: limit = heap + metaspace + stacks + code + direct + native + margin. Heap about 60 to 75 percent.

How do CPU limits in Kubernetes affect a JVM? Senior

A CPU limit is enforced by throttling: when the container uses its quota within a 100 ms period, all its threads are paused until the next period. A JVM burns CPU in bursts, from GC threads and JIT compilation, so a tight limit causes throttling that shows up as latency spikes, long GC pauses and slow warm-up, even when average CPU looks low.

Also, the JVM sizes its thread pools from the CPU count it sees, so a limit of 1 CPU means one GC thread, Serial GC, and fewer JIT threads. Common practice for latency-sensitive Java services is a CPU request that matches normal use, and either a generous limit or no CPU limit at all, while always setting a memory limit. If a limit is needed, I give at least 2 CPUs, and check container_cpu_cfs_throttled_seconds_total in metrics. -XX:ActiveProcessorCount can override what the JVM sees.

Remember: tight CPU limits throttle GC and JIT bursts. Prefer a generous limit and at least 2 CPUs.

11. Tools and performance pitfalls

Which JDK tools do you use to inspect a running JVM, and for what? Basic

I mostly use jcmd, which is the Swiss army knife: thread dumps, heap dumps, class histograms, flags and Flight Recorder. Beyond that, jstat for live GC numbers, jstack and jmap as older single-purpose tools, and VisualVM or Mission Control for a GUI.

jcmd                              # list JVM processes
jcmd PID Thread.print             # thread dump (same as jstack PID)
jcmd PID GC.class_histogram       # which classes use the heap
jcmd PID GC.heap_dump /tmp/h.hprof
jcmd PID VM.flags                 # flags actually in effect
jcmd PID JFR.start duration=60s filename=/tmp/r.jfr
jstat -gcutil PID 1000            # GC occupancy and counts every second

These tools attach to the JVM from the same machine and user, so in a container I run them inside it (kubectl exec), and the image needs a JDK, not just a JRE. A distroless runtime image without jcmd is a common reason that a diagnosis cannot start; the usual workaround is an ephemeral debug container sharing the process namespace.

Remember: jcmd for almost everything, jstat for live GC, JFR for deeper recordings.

How do you take and read a thread dump? What patterns do you look for? Intermediate

I take one with jcmd PID Thread.print (or kill -3 PID), and always take three, a few seconds apart, because one snapshot cannot show what is stuck versus just busy. I look at thread states: many BLOCKED threads waiting on one lock, many threads waiting on the same I/O or connection pool, or the same stack frame hot across dumps.

Each thread shows a name, state and stack. RUNNABLE threads are on CPU or doing I/O, BLOCKED means waiting to enter a synchronized block, and WAITING or TIMED_WAITING means parked or sleeping. The dump also reports a detected deadlock at the bottom, with the lock cycle. Patterns: 200 threads BLOCKED on the same monitor means lock contention, with the owner thread visible in the dump; all pool threads stuck in a socket read means a slow downstream service; threads piling up in HikariPool.getConnection means connection pool exhaustion. Naming threads and pools makes dumps readable.

Remember: take three dumps, group by state and top frame. Many threads on one lock or one wait is your answer.

The service has 100% CPU. How do you find out whether it is your code, the JIT or the GC? Senior

I find which threads burn the CPU first. Per-thread CPU from top -H -p PID gives a thread id; I convert it to hex and match it with nid in a thread dump. If those threads are named "GC Thread" or "G1 Conc", it is GC. If they are "C2 CompilerThread", it is JIT, usually just warm-up. If they are application threads, I read their stack, or sample with a profiler.

For application threads, a few thread dumps often show the same hot frame (a regex, a loop, serialization). For a precise answer I use a sampling profiler such as async-profiler or Java Flight Recorder (JFR), and read the flame graph: width is time, so the widest frame near the top is the best fix. JFR is built in, has low overhead (typically 1 to 2 percent) and is safe to run in production. A classic cause is an infinite or very long loop, a regex with catastrophic backtracking, or a hot lock spinning.

Remember: hot thread id, then hex, then thread dump. GC thread, compiler thread or app thread decides the path.

How does autoboxing affect memory and speed? Intermediate

Autoboxing wraps a primitive in an object (int to Integer). Each box is a heap object of 16 bytes for a 4-byte value, plus a reference to it, and it creates garbage. In a hot loop or a big collection like List<Integer> this multiplies memory use and allocation, and slows the code through cache misses and GC.

Long sum = 0L;                       // boxed: each += allocates a new Long
for (long i = 0; i < 1_000_000; i++) sum += i;

long sum2 = 0L;                      // primitive: no objects
for (long i = 0; i < 1_000_000; i++) sum2 += i;

Small values from -128 to 127 are cached by Integer.valueOf, which is why == on boxed numbers works for small values and fails for bigger ones: another reason to compare with equals. For large numeric data I use primitive arrays, primitive streams (IntStream), or specialised collections, and the JIT's escape analysis removes only some of the boxes, not all.

Remember: a boxed value is an object. Use primitives in hot loops and big collections.

What is allocation rate, and how does reducing it help GC? Senior

Allocation rate is how many MB per second the app creates objects. Every young GC is triggered by Eden filling up, so a high rate means more frequent collections, more objects caught alive mid-flight and promoted early, and more CPU spent on GC. Cutting the rate is often a bigger win than any GC flag.

I measure it from the GC log (heap before the GC minus heap after the previous one, divided by time) or JFR's allocation profiling, which names the code that allocates the most. Typical savings: stop building throwaway strings and collections in hot paths, reuse a StringBuilder, avoid boxing, stream results instead of building a large list, cache immutable objects, and avoid logging strings built eagerly with concatenation when the level is disabled (use parameterised messages). Reduce first the biggest allocators found by profiling, not guessed ones.

Remember: less allocation means fewer GCs and less promotion. Profile allocations, fix the top allocators.

12. Real-life scenarios

Each scenario starts with the one-sentence diagnosis and fix you can say first. Then it follows the same shape: situation, what you check first, the fix, and how you prevent it next time.

The pod is OOMKilled (exit code 137) again and again, but the heap graph never reaches the limit. What is going on? Senior

The heap is not the only memory the process uses. Native memory (threads, metaspace, direct buffers, code cache) or a heap set too close to the container limit pushes the total over, and the kernel kills the process. I find which area grew with Native Memory Tracking, then lower the heap share or cap that area.

Situation: restarts every few hours, kubectl describe pod shows OOMKilled, no OutOfMemoryError in the logs, heap graph looks healthy.

Check first: compare container memory (RSS) against heap used. Check the flags: is -Xmx or MaxRAMPercentage close to the limit? Count threads. Restart with -XX:NativeMemoryTracking=summary and diff jcmd PID VM.native_memory summary.diff over time to see which category grows.

Fix: lower the heap to 60 to 70 percent of the limit, cap metaspace, direct memory and thread count, or raise the limit. If one native category keeps growing, that is a leak to fix (for example unreleased direct buffers or a thread-pool leak).

Prevent: a memory budget per service (heap plus non-heap), alerts on container working-set memory and not only heap, and a load test that checks RSS over hours.

Remember: OOMKilled with a fine heap means non-heap growth or a heap set too big. Use NMT to see which.

Users report random freezes of 2 to 5 seconds in production. How do you investigate the GC? Senior

First prove whether the freezes are GC pauses. I turn on GC logging, line the freeze times up with "Pause" lines, and then fix the cause: a Full GC means too little headroom or a leak, long young pauses mean too much live data to copy, and pauses with high system time point to swapping or CPU throttling outside the GC.

Check first: GC log with -Xlog:gc*,safepoint. If there is no GC pause at the freeze time, look elsewhere: a safepoint delay, a thread dump showing a lock or slow downstream call, a noisy neighbour, or container CPU throttling.

  • Pause Full: the old generation is full or humongous allocations are failing. Add headroom, find leak or giant arrays.
  • Long young pause: too many survivors (large live data per request). Reduce allocation retained per request.
  • High sys time in the log (user=0.1 sys=2.5): the OS is the problem, often swap or throttled CPU.

Fix: depends on the cause above. If G1 cannot meet the target even after headroom, try generational ZGC.

Prevent: keep GC logs on always, alert on pause p99 and any Full GC.

Remember: match freeze time to GC log lines. Full GC, long copy or OS stall each has its own fix.

After each deployment the new pods are very slow for a few minutes, then fine. What is happening and what do you do? Intermediate

The new JVMs are cold: code runs in the interpreter, classes are still loading, connection pools and caches are empty, and the JIT has not compiled the hot paths. The fix is to warm each pod up before it gets real traffic and then ramp traffic in gradually.

Check first: compare latency per pod age. Look at JIT activity (jcmd PID Compiler.queue or JFR) and CPU in the first minutes, and check whether a CPU limit is starving the compiler threads.

Fix: make the readiness probe pass only after a warm-up routine (call key endpoints with synthetic requests, open the connection pool). Use slow-start in the load balancer or service mesh. Give the pod enough CPU during startup (a startup CPU boost where supported). Consider AppCDS for faster class loading, or GraalVM native image or CRaC if startup is the main issue.

Prevent: include a warm-up phase in the standard service template, and watch p99 latency during rollouts so a bad one is stopped early.

Remember: cold JVM is slow. Warm it before readiness, then ramp traffic.

The heap grows slowly until the service dies after about 3 days, and the heap dump shows many instances of a request-context class. How do you find the cause? Senior

Something still holds every request context. I open the dump, pick one instance of the context class, and look at its path to the GC roots. A very common answer is a ThreadLocal on a pooled thread that is set per request and never removed, so each thread keeps its last context alive, or a static collection or listener that accumulates them.

Check first: in Eclipse MAT, run "path to GC roots, excluding weak and soft references" on one context object. If it ends at Thread.threadLocals, it is a ThreadLocal. If it ends at a static field, it is a collection. Note that one leaked context may drag along a large object graph (the request body, the session), so retained size explains why the heap grows fast.

// the fix: always clear in finally
CONTEXT.set(ctx);
try {
    chain.doFilter(req, res);
} finally {
    CONTEXT.remove();   // pooled threads live forever
}

Fix: clear in finally, or move to a request-scoped design. Prevent: wrap ThreadLocal use in one helper or filter, and add a soak test that watches the heap-after-GC floor.

Remember: a growing request-scoped class usually means a ThreadLocal never removed on a pooled thread. Remove in finally.

An in-memory cache was added to speed up a lookup and a week later the service has OutOfMemoryError. What went wrong and how do you fix it? Intermediate

The cache has no size bound or expiry, so it grows with every new key until the heap is full. A cache without an eviction policy is a memory leak with a nice name. I replace it with a bounded cache (maximum size plus time to live), such as Caffeine, and measure the hit rate.

Check first: in a heap dump, the dominator tree shows one map retaining most of the heap. Check the key space: user ids, request ids and timestamps give nearly unbounded keys. Also check whether values hold large objects and whether keys have correct equals and hashCode (otherwise duplicates pile up).

Cache<String, Product> cache = Caffeine.newBuilder()
    .maximumSize(50_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .recordStats()
    .build();

Fix: bound by size or weight and add expiry. Prefer an external cache (Redis) when the data set is big or must be shared. Soft references are not a good bound, because they behave unpredictably. Prevent: review every static or singleton map in code review, and expose cache size and hit-rate metrics.

Remember: every cache needs a maximum size and a TTL, and metrics.

After a few hot redeploys on Tomcat, the app server throws OutOfMemoryError: Metaspace. How do you handle it? Senior

Each redeploy creates a new class loader, and the old one is not being freed, so old copies of all classes pile up in metaspace. That is a class loader leak: something outside the webapp still points to it. Short term I restart the server instead of hot redeploying. Long term I find the reference in a heap dump and remove it.

Check first: after a redeploy, take a heap dump and search for multiple instances of the webapp class loader (WebappClassLoaderBase). For an old one, find the path to GC roots. Usual blockers: a JDBC driver registered in DriverManager, a non-daemon thread or timer started by the app and never stopped, a ThreadLocal on a container thread, a shutdown hook or a logging framework holding an appender.

Fix: clean up in a ServletContextListener.contextDestroyed: deregister drivers, stop threads and executors, clear thread locals. Tomcat's leak prevention listener reports many of these in its logs. Setting -XX:MaxMetaspaceSize makes the failure explicit and early. Prevent: deploy by restarting or replacing containers, which is the normal practice now.

Remember: one reference into the old class loader keeps the whole old app. Clean up on shutdown, or restart instead.

After a traffic spike the service enters a loop of full GCs and never recovers until restarted. What happened and how do you prevent it? Senior

The spike pushed the live data (queued requests, buffers, big result sets) close to the heap size, and each Full GC then frees almost nothing, so the next one starts at once. The JVM is thrashing: it spends nearly all its time in GC, requests time out and pile up even more, and it cannot recover. The fix is to bound the work in flight and give the heap headroom.

Check first: the GC log shows back-to-back Pause Full lines where the heap after GC stays near the maximum. The heap dump of that moment shows what is retained: usually in-flight request data, unbounded queues or caches.

Fix: bound the queues and thread pools, apply backpressure or load shedding (reject early with 429 or 503 rather than accepting everything), stream big results, and raise the heap if the legitimate live set is large. As a safety net, -XX:+ExitOnOutOfMemoryError with a restart policy is better than a zombie that never recovers. Also make the health probe fail when the process is in GC trouble, so the orchestrator replaces it.

Prevent: load test beyond the expected peak, and alert on GC time share and Full GC count.

Remember: a full GC loop is thrashing near the heap limit. Bound the work, shed load, add headroom.

After a dependency upgrade, a service throws NoClassDefFoundError and NoSuchMethodError in production, but all unit tests pass. What do you check? Intermediate

This is almost always a dependency version conflict: the classpath at runtime holds a different version of a library than the one the code was compiled and tested against. I inspect the resolved dependency tree of the real artifact, find the duplicate or wrong-version jar, and pin one version.

Check first: read the exact class or method in the error. Run mvn dependency:tree -Dverbose (or gradle dependencies) and look for the library with two versions or a transitive dependency that the new version dropped. Check the packaged fat jar or WAR contents too, since the test classpath differs from the runtime one. -verbose:class or -Xlog:class+load shows which jar each class was loaded from. Also look for a shaded copy of the same library.

Fix: align versions with dependency management (BOM or constraints), exclude the stray transitive dependency, or relocate it. For NoClassDefFoundError: Could not initialize class, look higher in the logs for the first failure of the static initializer. Prevent: an integration test that runs against the packaged artifact, and a dependency convergence check in CI.

Remember: works in tests but fails in production means a different classpath. Read the dependency tree and see which jar loaded.

You need a heap dump from a 24 GB production heap, but taking it freezes the pod and the liveness probe kills it. What do you do? Senior

A heap dump pauses the JVM while it writes about as many gigabytes as the used heap, so on a big heap it can last minutes and the probe kills the pod mid-dump. I take the dump from one instance that is pulled out of the load balancer and has its liveness check relaxed, onto a volume with enough space, or I avoid a full dump by using histograms and a smaller target.

Steps: pick one affected replica, remove it from traffic, and temporarily raise or disable the liveness probe (or use a debug sidecar). Run jcmd PID GC.heap_dump -all /dumps/h.hprof to a mounted volume (default is live objects only, which also triggers a full GC first). Compress and copy it out with kubectl cp. Open it on a machine with RAM larger than the dump, or use a tool that streams.

Cheaper options first: jcmd PID GC.class_histogram twice takes seconds and often names the leaking class. Flight Recorder's old-object sample can point to the leak path with low overhead. And -XX:+HeapDumpOnOutOfMemoryError captures the dump at the failing moment so no manual one is needed.

Prevent: have a volume and a runbook ready, and test the procedure before an incident.

Remember: a heap dump freezes the JVM. Use one pulled-out replica, a big volume, and try the histogram first.

A nightly batch job fails with "Java heap space" after the data grew. The team wants to raise -Xmx to 32 GB. What do you say? Intermediate

I would not just raise the heap. I first check why memory depends on data size: most likely the job loads everything into memory before processing. A heap that grows with the data size only delays the next failure. I would change the job to stream or process in chunks so memory stays constant, and raise the heap only as a short-term bridge.

Check first: the heap dump (or histogram) at the failure shows what holds the memory: a giant List of rows, a whole file read into a string, or an ORM loading entities into one persistence context. Count how it grows with input size.

Fix: read in pages or with a cursor or stream, process and write per chunk (for example batch size 1000), clear the persistence context between chunks, and never collect the full result in a list. Where it is truly needed, use primitive arrays or compact structures. Note that going past about 32 GB loses compressed object pointers, so a 32 GB heap can hold less than a 31 GB one. And a bigger heap makes any full GC pause longer.

Prevent: test batch jobs with a data volume well above production, and monitor peak heap per run.

Remember: if memory grows with the data, stream it. More heap just moves the failure date.
