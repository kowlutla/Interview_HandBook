This page covers the runtime side of Java: the JVM, memory and garbage collection. For language basics see Java fundamentals, for collections Java collections, for threads and the memory model in depth Java concurrency, for newer language features Modern Java, and for exceptions and I/O Exceptions and I/O.

Version notes used on this page. Long-term-support (LTS) releases are 8, 11, 17, 21 and 25 (September 2025). The default collector is Parallel GC in Java 8 and G1 from Java 9 onwards (only when the JVM sees at least 2 CPUs and about 1.8 GB of memory; otherwise it falls back to Serial). Metaspace replaced PermGen in Java 8. CMS was deprecated in 9 and removed in 14. ZGC and Shenandoah became production-ready in 15. Generational ZGC arrived in 21 and became the only ZGC mode in 24. The unified logging switch -Xlog arrived in 9. Flight Recorder is free in OpenJDK from 11 (backported to later 8 updates). Finalization is deprecated for removal since 18.

Mental model: the 8 ideas everything hangs on

One line: your code is compiled to portable bytecode, loaded by class loaders into the JVM, run first by an interpreter and then by a JIT compiler, and every object lives on a garbage-collected heap that the JVM cleans by finding what is still reachable.
  1. Write once, run on a JVM. javac turns source into bytecode in .class files. The JVM, not the CPU, runs bytecode. That is why the same jar runs on Windows, Linux and Mac.
  2. Classes are loaded lazily and by name. A class loader finds the bytes, the JVM checks them, prepares statics, and runs static initializers only when the class is first used.
  3. Memory is split by purpose. Heap (all objects, shared), thread stacks (method calls, one per thread), metaspace (class metadata, native memory), plus code cache and direct buffers. The heap is only a part of what the process uses.
  4. Garbage means unreachable. The collector never asks "is this used?". It asks "can I still reach it from a root?" (thread stacks, static fields). So a forgotten reference is a leak even though the code never touches it again.
  5. Most objects die young. The heap is split into young and old areas so the cheap, frequent collection works only on the small young area.
  6. Every collector trades three things: throughput (work done per second), pause time (how long your app stops) and memory footprint. You cannot have all three.
  7. The JIT makes Java fast after warm-up. Hot methods are compiled to machine code using runtime knowledge. The first minutes of a process are slower than later.
  8. In containers the process budget is bigger than the heap. The container limit must cover heap, metaspace, thread stacks, code cache and direct memory. Heap equal to the limit means the process is killed.

1. Platform, bytecode and how a program runs

What is the difference between the JDK, the JRE and the JVM? Basic

What the interviewer is testing: basic vocabulary, and whether you know what you install on a build machine versus a server.

The JVM (Java Virtual Machine) is the engine that loads bytecode and runs it. It includes the class loader, the interpreter, the JIT compiler and the garbage collector. The JRE (Java Runtime Environment) was the JVM plus the standard class library (java.lang, java.util and so on), enough to run programs. The JDK (Java Development Kit) is the JRE plus development tools: javac, jar, javap, jcmd, jfr and more. In practice, since Java 11 there is no separate JRE download. You install a JDK, or you build a small custom runtime with jlink that contains only the modules your app needs. Also remember that "JVM" is a specification; HotSpot (in OpenJDK, Oracle JDK, Temurin, Corretto) is the most common implementation, and others exist such as Eclipse OpenJ9 and GraalVM.

Likely follow-ups
  • Is Java compiled or interpreted? Both. Source is compiled to bytecode, then the JVM interprets it and compiles hot parts to machine code at run time.
  • Why do production images still often ship a full JDK? Because tools like jcmd and jstack are needed for troubleshooting. A jlink runtime is smaller but you give those up unless you include them.
What is bytecode, and what is inside a .class file? Basic

What the interviewer is testing: do you understand what "platform independent" really means.

Bytecode is a compact instruction set for an imaginary stack machine. Each instruction is one byte (the opcode) with optional operands, for example iload_1 pushes a local int on the operand stack and iadd adds the top two values. A class file starts with the magic number 0xCAFEBABE, then the version, a constant pool (names, strings, numbers, method references), access flags, the class and its parents, fields, methods with their bytecode, and attributes such as line numbers and annotations. The JVM verifies it, then runs it. Because the instruction set does not depend on a real CPU, the same class file works anywhere a JVM exists. You can read it with javap.

javap -c -p Foo.class      # disassemble methods, including private ones
javap -v Foo.class         # also shows constant pool and class version
Likely follow-ups
  • Which invoke instructions exist? invokevirtual (normal instance call), invokeinterface, invokespecial (constructors, super, private), invokestatic, and invokedynamic (used for lambdas and string concatenation).
  • What does "class file version 61" mean? It was produced for Java 17 (52 is Java 8, 55 is 11, 61 is 17, 65 is 21). An older JVM refuses newer versions with UnsupportedClassVersionError.
What happens when you run java Main? Walk me through it. Intermediate

What the interviewer is testing: can you connect loading, memory, interpreting and compiling into one story.

The launcher starts a native process and creates the JVM. The JVM reserves memory for the heap, sets up metaspace and the code cache, and starts helper threads (GC, JIT compiler, signal handling). The bootstrap loader loads core classes from the JDK. Then the application class loader finds Main on the class path, the JVM loads, verifies, prepares and initializes it, and calls public static void main(String[]) on a new "main" thread. Code starts in the interpreter, which is slow but starts immediately. The JVM counts how often methods and loops run. Hot ones are queued for the JIT compiler, which produces machine code and stores it in the code cache. As you create objects they go in the heap; when it fills, the garbage collector runs. When main returns and no non-daemon threads remain, the JVM runs shutdown hooks and exits.

Likely follow-ups
  • What keeps the JVM alive? Any running non-daemon thread. Daemon threads (GC, timers you mark as daemon) do not.
  • What runs on exit? Shutdown hooks added with Runtime.addShutdownHook, in no guaranteed order. A kill -9 skips them.
HotSpot, OpenJ9, GraalVM: what are they, and does the choice matter to an application developer? Intermediate

What the interviewer is testing: awareness that the JVM is a specification with several implementations, and the distribution landscape.

HotSpot is the reference implementation in OpenJDK. Oracle JDK, Eclipse Temurin, Amazon Corretto, Azul Zulu and Microsoft Build of OpenJDK are all builds of it, so they behave the same for almost all purposes; the differences are licence, support and extras. OpenJ9 (IBM, now Eclipse) is a different JVM with lower memory footprint and faster start, and its own GC policies and flags. GraalVM is a JDK distribution with the Graal JIT compiler, and a tool called native image that compiles a Java app ahead of time to a standalone executable. For most application developers the practical choice is a HotSpot-based build from a vendor you can get security updates from. Flags such as -XX:+UseG1GC are HotSpot flags and mean nothing to OpenJ9.

Likely follow-ups
  • Is Oracle JDK still different from OpenJDK? Since Java 17 the code is essentially the same; the difference is mainly licensing terms.
Which Java versions matter, and what is the default garbage collector in each? Intermediate

What the interviewer is testing: you know the platform you actually run, and that a JDK upgrade can change GC behaviour.

Java 8 (2014) is still in use; its default collector is Parallel GC and it has PermGen replaced by Metaspace, and container awareness only from 8u191. Java 9 made G1 the default (on machines with 2 or more CPUs and about 1.8 GB or more; otherwise Serial). Java 11 (LTS) added Epsilon (no-op GC) and experimental ZGC, plus free Flight Recorder. Java 14 removed CMS. Java 15 made ZGC and Shenandoah production-ready. Java 17 (LTS) is the common baseline today. Java 21 (LTS) adds Generational ZGC (opt-in with -XX:+UseZGC -XX:+ZGenerational) and virtual threads. Java 24 removed non-generational ZGC, so -XX:+UseZGC alone gives the generational one. Java 25 (LTS) makes compact object headers a product feature (opt-in with -XX:+UseCompactObjectHeaders), which shrinks every object by up to 4 bytes. G1 itself keeps getting faster in each release, so upgrading often gives free improvements.

What do modules (JPMS), jlink and jdeps give an application developer? Senior

What the interviewer is testing: can you reason about runtime size and about "illegal reflective access" failures after upgrading Java.

Since Java 9 the JDK itself is split into modules (java.base, java.sql, java.logging and so on). A module declares what it exports and what it needs, and the JVM enforces that. Two practical effects. First, jdeps can list which JDK modules your jar uses and jlink can build a trimmed runtime image with only those, which makes container images smaller. Second, the JDK now blocks deep reflection into its internal packages (strong encapsulation, enforced from Java 17). Old libraries that reflect into java.base then fail with InaccessibleObjectException, and the stop-gap is flags such as --add-opens java.base/java.lang=ALL-UNNAMED. The real fix is upgrading the library. Most apps still run on the class path (the "unnamed module") and never write a module-info file.

Likely follow-ups
  • Do I need module-info for my service? No, almost never; it matters for libraries that want strong boundaries and for jlink-based images.

2. Class loading and initialization

What is a class loader, and what are the built-in ones? Basic

What the interviewer is testing: the base vocabulary for all class loading questions.

A class loader is an object that finds the bytes of a class by name and asks the JVM to define a class from them. There are three built-in loaders. The bootstrap loader is built into the JVM, written in native code, and loads the core JDK classes (java.base: Object, String, collections). In code it appears as null. The platform loader (called the extension loader before Java 9) loads other JDK modules. The application (system) loader loads classes from your class path or module path, which is your code and your libraries. Frameworks add their own: web servers give each web application its own loader, and OSGi and plugin systems do the same. A class is identified by its name and its loader, so the same class file loaded by two loaders gives two different, incompatible classes.

System.out.println(String.class.getClassLoader());      // null (bootstrap)
System.out.println(Main.class.getClassLoader());        // jdk.internal.loader.ClassLoaders$AppClassLoader
System.out.println(Thread.currentThread().getContextClassLoader());
Likely follow-ups
  • Why is String's loader null? The bootstrap loader is not a Java object, so there is nothing to return.
Explain the parent delegation model. Why does it exist? Intermediate

What the interviewer is testing: a classic. They want the flow, the reason (security and uniqueness), and when it is broken.

When a loader is asked for a class, it does not look itself first. It asks its parent, the parent asks its own parent, up to the bootstrap loader. Only if every ancestor fails does the loader try its own search. So the path is application, then platform, then bootstrap on the way up, and the first one that finds the class wins. This has two benefits. First, safety: you cannot replace java.lang.String by putting your own copy on the class path, because bootstrap always finds the real one first. Second, uniqueness: shared classes are loaded once, by the highest loader, so every part of the program sees the same String class. Some systems deliberately break the rule: a web server loads the web application's own classes first (child first), so each app can bring its own library versions.

Likely follow-ups
  • Which method do I override to write a custom loader that keeps delegation? findClass. Overriding loadClass is what breaks delegation.
  • What is the thread context class loader? A loader stored on the thread so framework code in a high loader (like JDBC or JNDI) can load classes that only a lower loader can see.
What are the phases of loading a class: loading, linking and initialization? Intermediate

What the interviewer is testing: precise knowledge of what happens when, especially the difference between "loaded" and "initialized".

Loading: a loader reads the bytes and the JVM builds the class metadata in metaspace plus a Class object on the heap. Linking has three steps. Verification checks that the bytecode is well-formed and safe (types match, stack does not overflow). Preparation allocates the static fields and sets them to default values (0, false, null), not to the values you wrote. Resolution turns symbolic references in the constant pool into direct ones; it may be done lazily, the first time a reference is used. Initialization runs the static initializers and static field assignments, in source order, as one synthetic method called <clinit>. The JVM guarantees <clinit> runs once and is thread-safe: other threads wait while one runs it. That guarantee is exactly why the "initialization-on-demand holder" singleton works.

Likely follow-ups
  • When does initialization trigger? First new, first call of a static method, first read or write of a non-constant static field, initializing a subclass, Class.forName(name), and for the main class at startup.
  • Does reading a static final int X = 5 trigger it? No. Compile-time constants are copied into the caller's bytecode.
What is the difference between Class.forName, ClassLoader.loadClass and new? Intermediate

What the interviewer is testing: the initialization distinction, and the old JDBC driver story.

Class.forName("com.acme.Foo") loads the class through the caller's class loader and initializes it, so its static blocks run. classLoader.loadClass("com.acme.Foo") only loads (and maybe links) it and does not initialize. Class.forName(name, false, loader) lets you choose a loader and skip initialization. new Foo() needs Foo to be known at compile time; the other two work with a string chosen at run time, which is what plugin systems and frameworks use. The old JDBC pattern Class.forName("com.mysql.jdbc.Driver") worked because the driver's static block registered itself with DriverManager. Since JDBC 4 (Java 6) drivers are found by the service loader, so that line is no longer needed.

Class<?> a = Class.forName("com.acme.Foo");                 // loads and runs static init
Class<?> b = loader.loadClass("com.acme.Foo");              // loaded only
Object o = a.getDeclaredConstructor().newInstance();       // instance via reflection
ClassNotFoundException versus NoClassDefFoundError: what is the difference and how do you debug each? Intermediate

What the interviewer is testing: a favourite question. It checks if you can reason about class path problems rather than memorise.

ClassNotFoundException is a checked exception thrown when your code asks for a class by name at run time (Class.forName, loadClass, reflection, a framework reading a config string) and no loader can find it. The usual cause is a missing jar or a typo in a name. NoClassDefFoundError is an Error thrown by the JVM when a class that was present at compile time cannot be loaded at run time, for example because code compiled against a library that is not on the runtime class path, a transitive dependency was excluded, or the jar is visible to a different loader. It has a second, trickier cause: the message Could not initialize class X means X was found, but its static initializer failed earlier (that first failure was an ExceptionInInitializerError). Every later use throws NoClassDefFoundError, and the real cause is only in the first stack trace in the logs.

java.lang.NoClassDefFoundError: Could not initialize class com.acme.Config
    ... earlier in the log ...
java.lang.ExceptionInInitializerError
Caused by: java.lang.IllegalStateException: DB_URL not set

To debug: print the class path or dependency tree (mvn dependency:tree, gradle dependencies), look for a missing or excluded jar, check whether two different versions of a library are present, and search the logs backwards for the first ExceptionInInitializerError.

Likely follow-ups
  • NoSuchMethodError at run time? Binary incompatibility: you compiled against one version and run with another that lacks the method.
  • ClassCastException between the "same" class? Two class loaders each loaded their own copy.
When would you write a custom class loader, and how? Senior

What the interviewer is testing: whether you know where loaders are used in real software, not only the theory.

Real reasons: loading plugins from a folder at run time, isolating tenants or apps so their library versions do not clash (application servers), loading classes from a database or network, hot reloading during development, or decrypting classes. The simple recipe is to extend ClassLoader, override findClass(String name), read the bytes and call defineClass. Keeping loadClass untouched keeps parent-first delegation. For jar-based plugins, URLClassLoader already does the work. The risks are memory and identity: a class loader holds every class it loaded, so if anything keeps a reference to one class or one instance, the whole loader and all its classes stay in metaspace. Also, interfaces shared between host and plugin must come from the common parent loader, or you get ClassCastException on identical-looking types.

class DirLoader extends ClassLoader {
    private final Path dir;
    DirLoader(Path dir, ClassLoader parent) { super(parent); this.dir = dir; }
    @Override protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            byte[] b = Files.readAllBytes(dir.resolve(name.replace('.', '/') + ".class"));
            return defineClass(name, b, 0, b.length);
        } catch (IOException e) { throw new ClassNotFoundException(name, e); }
    }
}
Likely follow-ups
  • How does a loader get unloaded? Only when the loader, all its classes and all their instances become unreachable. Then metaspace for them is freed at a GC.
What is a class loader leak, and how does it show up on redeploys? Senior

What the interviewer is testing: experience with application servers and a real source of Metaspace OutOfMemoryError.

When you redeploy a web app in Tomcat or a similar container without restarting the JVM, the server drops the old web-app class loader and creates a new one. The old loader, and every class it loaded, should then be garbage collected. A class loader leak means something outside the web app still points to a class or object from the old loader. Common culprits: a thread created by the app and never stopped (its context class loader is the old one), a ThreadLocal value on a server thread-pool thread, a JDBC driver registered with the shared DriverManager, a shutdown hook or a static field in a shared library that holds an app object, and a logging library keeping a reference. The old loader then stays, with all its classes in metaspace. Each redeploy adds another copy, so metaspace grows until OutOfMemoryError: Metaspace. To prove it, take a heap dump after a few redeploys and look for several instances of the web-app class loader in MAT, then follow the path to GC roots.

Likely follow-ups
  • Quick mitigation? Restart instead of hot redeploy; in container-based deployments it is the default anyway.

3. Runtime memory areas, objects and allocation

What are the JVM runtime data areas? Basic

What the interviewer is testing: the standard JVM memory question. A clear picture matters more than names.

Some areas are shared by all threads and some belong to one thread. Shared: the heap, where all objects and arrays live and where garbage collection happens; and metaspace, where class metadata lives (method bytecode, constant pools, field layouts), which is in native memory, not the heap. Per thread: the JVM stack, holding one frame per method call with its local variables and operand stack; the program counter (PC) register, which points to the bytecode instruction being run; and the native method stack for calls into C code through JNI. Outside the spec but real: the code cache (JIT-compiled machine code), direct byte buffers, and the GC's own data structures, all in native memory.

Likely follow-ups
  • Which areas can throw OutOfMemoryError? Heap, metaspace, direct memory, and "unable to create native thread" when stacks cannot be allocated.
  • Which area is per thread? Stack, PC register, native stack. Thread-local allocation buffers are carved from the heap.
What lives on the stack and what lives on the heap? Basic

What the interviewer is testing: the foundation for pass-by-value, escape analysis and leaks.

Each method call gets a frame on the calling thread's stack. The frame holds the local variables (primitives and references) and a small working area for expressions. When the method returns the frame is popped and everything in it disappears instantly, with no GC. Every object and every array lives on the heap, whether you made it in a method or in a field. A local variable of type Person is only a reference (4 or 8 bytes) on the stack pointing to the object on the heap. Fields of an object, including primitives, sit inside the object on the heap. Static fields live with the class (the mirror Class object on the heap, metadata in metaspace). One twist: the JIT may avoid allocating an object at all if it can prove it never escapes the method (escape analysis), but that is an optimisation, not something you can rely on in code.

void run() {
    int count = 3;                  // stack: the int itself
    Person p = new Person("Asha");  // stack: reference p; heap: the Person object
}
Likely follow-ups
  • Is Java pass by value or by reference? Always by value; for objects the value is the reference. See Java fundamentals.
What is inside a stack frame, and what controls how deep recursion can go? Intermediate

What the interviewer is testing: link between frames, thread stack size and StackOverflowError.

A frame has an array of local variables (parameters first, with this at slot 0 for instance methods), an operand stack where bytecode instructions push and pop values, and a link to the constant pool of the method's class plus the return address. The size of each frame is known at compile time. Total depth depends on the thread stack size, set with -Xss (default 1 MB on 64-bit Linux, 512 KB to 1 MB on other platforms) divided by frame size. A simple recursive method might reach 10,000 to 20,000 calls before the stack is full; a method with many locals gets fewer. The main thread's size may come from the OS. Bigger -Xss multiplies across every thread: 1,000 threads at 1 MB reserve 1 GB of address space, though pages are committed only as they are used.

Likely follow-ups
  • Does the JVM do tail-call optimisation? No. Recursion in Java uses a frame per call, so convert deep recursion to a loop.
How is the heap organised into generations? Explain Eden, Survivor and Old. Intermediate

What the interviewer is testing: the standard heap layout and the idea of promotion.

The classic layout (Serial, Parallel, and the logical view in G1) splits the heap into a young generation and an old generation. New objects are created in Eden. When Eden fills, a young collection (a minor GC) copies the live objects out of Eden and the current survivor space into the empty survivor space (S0 or S1; they swap roles each time) and the dead ones are simply left behind. Each time an object survives, its age goes up by one. When the age passes a threshold (up to 15, adaptive), or when the survivor space is too full, the object is promoted to the old generation. The old generation is collected less often because it holds long-lived data like caches and connection pools. Eden is typically about 80% of young, and each survivor space about 10%.

Likely follow-ups
  • What tunes the layout? -XX:NewRatio, -XX:SurvivorRatio, -XX:MaxTenuringThreshold. With G1 or ZGC avoid fixing young size, the collector adapts it.
  • What is premature promotion? Short-lived objects pushed to old because survivor space is too small. They then wait for the expensive old collection.
What happened to PermGen, and what is Metaspace? Intermediate

What the interviewer is testing: a Java 8 migration classic.

Before Java 8, class metadata lived in a fixed-size area of the heap called the Permanent Generation. Its size had to be guessed with -XX:MaxPermSize, and apps with many classes or many redeploys died with OutOfMemoryError: PermGen space. Java 8 removed it. Class metadata now lives in Metaspace, which is allocated from native memory and grows on demand. By default it is not capped, only the machine limits it. That is why it is wise to set -XX:MaxMetaspaceSize in production: a class loader leak then fails fast with OutOfMemoryError: Metaspace instead of eating all RAM. Interned strings and static variables moved to the heap in Java 7. The metaspace size triggers a GC when it crosses a high-water mark (-XX:MetaspaceSize) so unused classes get unloaded. Compressed class pointers use a separate area limited by -XX:CompressedClassSpaceSize (1 GB default).

Likely follow-ups
  • What fills metaspace? Many classes: big frameworks, generated proxies (Hibernate, CGLIB, Groovy), repeated redeploys, and heavy use of dynamic class generation or reflection inflation.
How much memory does an object take? Describe the layout of an object in memory. Senior

What the interviewer is testing: can you estimate memory cost, which drives data structure choices.

A HotSpot object has a header, then the fields, then padding so the total is a multiple of 8 bytes. On a 64-bit JVM with compressed pointers (the default for heaps below about 32 GB) the header is 12 bytes: an 8-byte mark word (identity hash code, lock state, GC age) and a 4-byte class pointer. Arrays add a 4-byte length, making 16 bytes. References are 4 bytes with compressed oops, 8 bytes without. So an empty Object is 16 bytes (12 plus 4 padding). An Integer holds a 4-byte int, so 12 + 4 = 16 bytes, plus the 4-byte reference that points to it. A boolean field takes a full byte. Therefore a List<Integer> with one million entries costs about 4 MB of references plus 16 MB of Integer objects, around 20 MB, whereas an int[] of the same size is 4 MB. Compact object headers (Java 24 experimental, Java 25 product) cut the header to 8 bytes.

Likely follow-ups
  • How can I measure it? The JOL tool (Java Object Layout) prints layouts; a heap dump histogram shows shallow size per class.
  • What is shallow versus retained size? Shallow is the object itself. Retained is everything that would be freed if this object vanished (its exclusive sub-graph).
What are compressed oops, and why is a 32 GB heap often worse than a 31 GB heap? Senior

What the interviewer is testing: a known sizing trap that surprises people.

An "oop" is an ordinary object pointer. A 64-bit pointer would be 8 bytes. Because objects are aligned to 8 bytes, the JVM can store a 32-bit number that is shifted left by 3 bits when used, and so address 32 GB (4 billion times 8) with only 4 bytes per reference. That is compressed oops. It saves a lot of memory since references are everywhere in objects, arrays and collections. Cross 32 GB (the practical limit is a little under, about 32 GB minus a bit) and the JVM must switch to full 8-byte references. All reference fields double in size, so a 33 GB heap can hold less data than a 31 GB one. The CPU caches also hold fewer objects. Rule of thumb: stay at or under about 31 GB, or go well beyond (60 GB plus). Check it with -XX:+PrintFlagsFinal | grep UseCompressedOops. Larger heaps use ZGC or Shenandoah, which handle them with short pauses.

How does the JVM allocate objects so fast? What is a TLAB? Senior

What the interviewer is testing: allocation internals and why short-lived objects are cheap.

Allocation in Eden is a bump-the-pointer: the JVM keeps a pointer to the free start of Eden, and allocating an object means adding its size to that pointer. That is a few machine instructions, faster than malloc. With many threads, the pointer would need a lock or an atomic update for every object. To avoid that, each thread gets its own private chunk of Eden called a TLAB (Thread-Local Allocation Buffer). A thread bumps its own pointer inside its TLAB without any locking. When the TLAB is full, the thread asks for a new one (this one step is synchronised). Very big objects skip the TLAB and are allocated directly in Eden, or in old/humongous space in G1. TLAB is on by default (-XX:+UseTLAB) and its size adapts. After a young GC, Eden is empty again, so "freeing" dead objects costs nothing: only live objects are copied. This is why many short-lived small objects are cheap in Java, and why allocation rate matters mostly through how often it triggers a young GC.

Likely follow-ups
  • Does a larger allocation rate make Java slow? Only through more frequent young GCs and cache pressure. A pause happens when the live set is big, not when garbage is big.
Trace the life of an object from new to being freed. Intermediate

What the interviewer is testing: a full story that ties together allocation, generations and reachability.

The class is loaded and initialised if needed. new allocates the object in a TLAB inside Eden, zeroes its fields, then the constructor runs and fills them in. While something reachable refers to it, it stays. If it becomes unreachable (the method returned and nothing stored it) it is simply ignored in the next young GC: nothing is done to it, the space is reused. If it is still reachable at the young GC, it is copied to a survivor space and its age becomes 1. Each later survival copies it again and raises the age. At the tenuring threshold, or if survivor space is full, it is promoted to old. Once there, it is only removed by an old or mixed collection after it becomes unreachable. A large array or object may go straight to old (or to a humongous region in G1). If the class has a finalizer, extra steps apply (see the finalizer question), which is one more reason to avoid them.

The heap is 2 GB but the process uses 3.5 GB. Where does the rest go? Senior

What the interviewer is testing: do you know the JVM is more than the heap, which is the root of most container kills.

Several parts live outside the heap. Metaspace (class metadata, 50 to 300 MB for a typical Spring service). Thread stacks (each thread reserves up to -Xss, 1 MB by default, and 500 threads can add several hundred MB). Code cache (JIT output, up to 240 MB reserved). Direct buffers (NIO, Netty, some database drivers). GC overhead (G1 remembered sets and card tables can be 5 to 20% of heap). JIT compiler working memory and native libraries (zip inflaters, JNI, TLS). Also, glibc malloc can fragment arenas, making native memory look larger than it is. To see it, start the JVM with -XX:NativeMemoryTracking=summary and run jcmd PID VM.native_memory summary. It prints committed memory per category: Java Heap, Class, Thread, Code, GC, Internal, Symbol and so on. A fair budget is: container limit equals heap plus 25 to 40% headroom.

java -XX:NativeMemoryTracking=summary -jar app.jar
jcmd <pid> VM.native_memory summary
jcmd <pid> VM.native_memory baseline        # then later:
jcmd <pid> VM.native_memory summary.diff
Likely follow-ups
  • NMT does not show something that RSS has. What is it? Memory allocated by native libraries and by glibc fragmentation. Try MALLOC_ARENA_MAX=2 or jemalloc.
What causes StackOverflowError and how do you fix it? Basic

What the interviewer is testing: can you find the actual cause, not just "increase -Xss".

It happens when a thread has too many nested calls and its stack runs out. Almost always it is unbounded recursion: a missing or wrong base case, two methods calling each other, or a cycle in an object graph. Typical real examples: toString, equals or hashCode on two entities that reference each other (parent and child in JPA); a JSON serializer following a bidirectional relation; a proxy calling itself; getX() that calls getX(). The stack trace is long and shows the same few frames repeating, which tells you where the loop is. The fix is to repair the logic: add the base case, break the cycle (@JsonIgnore, exclude a field from toString), or turn deep recursion into a loop or an explicit stack. Raising -Xss is only a workaround for legitimately deep but finite recursion (a deep parser tree). Note it is an Error, so you rarely should catch it, and heap is not affected: it is thread memory.

Likely follow-ups
  • Can StackOverflowError happen without recursion? Yes, with very deep but finite call chains such as long chains of decorators or very deep expression trees.

4. References, strings and cleanup

Explain strong, soft, weak and phantom references. Intermediate

What the interviewer is testing: can you choose the right reference for caches and cleanup.

A strong reference (a normal variable) always keeps the object alive. A soft reference (SoftReference) keeps it alive until the JVM is short of memory; the collector clears soft references before throwing OutOfMemoryError, so they suit memory-sensitive caches, but their timing is hard to predict. A weak reference (WeakReference) does not keep an object alive: at the next GC, if only weak references remain, the object is collected. It is used by WeakHashMap (keys) and for canonical-instance maps, and for listeners that should not prevent cleanup. A phantom reference (PhantomReference) is only a notification: get() always returns null, and it is put on a ReferenceQueue after the object is finalised, so you can do cleanup of related native resources safely. java.lang.ref.Cleaner is the modern way to use it. Strong is the default, and the other three are about letting the GC reclaim things.

WeakReference<Image> ref = new WeakReference<>(image);
image = null;
System.gc();
System.out.println(ref.get());   // probably null
Likely follow-ups
  • Is SoftReference a good cache today? Usually no. Behaviour depends on heap size and GC, and it can cause erratic latency. Use a real cache (Caffeine) with size or time limits.
How does WeakHashMap work, and when does it fail to clean up? Intermediate

What the interviewer is testing: practical use of weak references and the classic mistake of the value pointing to the key.

A WeakHashMap holds each key through a weak reference. When no one else holds the key strongly, the GC clears it, and on later map operations the map drops that entry (using a reference queue). So it is useful for metadata attached to objects you do not own, like "extra info per object, which should disappear with the object". Two traps. First, if the value strongly refers to its key, the entry can never be cleared, because the map keeps the value, the value keeps the key. Second, keys such as interned strings, small boxed numbers or enum constants are always strongly reachable elsewhere, so they never vanish. Also it is not thread safe, and removal depends on GC timing, so size can shrink at unpredictable moments. For a real cache with expiry, use Caffeine, which can use weak keys or values if needed.

What is the String pool, and what is the difference between new String("a") and "a"? Basic

What the interviewer is testing: a basic but frequent memory-and-identity question.

The string pool (string intern table) is a cache of unique String objects held by the JVM. String literals in source code, like "a", are put in it when the class is loaded, so every use of "a" anywhere in the program refers to the same single object. new String("a") always creates a new object on the heap, separate from the pooled one (the literal still goes in the pool). So "a" == "a" is true, and new String("a") == "a" is false, but .equals is true in both cases. Since Java 7 the pool lives in the heap (before that, in PermGen), so pooled strings can be garbage collected when unreferenced. Compile-time constant expressions such as "a" + "b" are folded into the literal "ab" by the compiler, while a concatenation with a variable is built at run time and is not pooled.

String a = "java";
String b = "java";
String c = new String("java");
System.out.println(a == b);          // true  (same pooled object)
System.out.println(a == c);          // false (c is a separate heap object)
System.out.println(a == c.intern()); // true
Common mistakes: comparing strings with == in business code. It "works" for literals and breaks for strings from input, JSON or a database.
What does String.intern() do, and is it a good idea to use it? Senior

What the interviewer is testing: judgement: do you know a tool that sounds clever but has traps.

intern() looks the string up in the pool. If an equal string is there, it returns that pooled instance, otherwise it adds this string and returns it. The goal is to save memory when the same string value repeats millions of times (country codes, enum-like values read from files). The costs are real: the pool is a hash table with a fixed bucket count (-XX:StringTableSize, 65,536 by default in recent versions), so heavy use causes long chains and slowness; every intern call does a lookup; and interning unbounded unique values (user IDs, URLs) simply fills the pool. Pooled strings are collected when unreachable, so it is not a classic leak, but it is pressure. Better alternatives: if you use G1, turn on -XX:+UseStringDeduplication, which lets the GC share the underlying character arrays of equal strings in the background. Or use your own bounded map or an enum for a small value set. Java 9 added compact strings (one byte per char for Latin-1 text), which halves memory for most strings.

Likely follow-ups
  • Is String immutability related? Yes. Sharing one object is only safe because it cannot change, and the hash code can be cached.
Why are finalize() and finalizers discouraged, and what replaces them? Intermediate

What the interviewer is testing: do you know the cost, and what to use instead for resource cleanup.

finalize() is a method the GC calls once, some time after the object becomes unreachable. Problems: there is no guarantee when, or even whether, it runs (the JVM may exit first). An object with a finalizer needs at least two GC cycles to free: the first finds it, queues it for the finalizer thread, and only a later cycle reclaims the memory, so objects survive longer and may be promoted to old. A single finalizer thread can fall behind and the queue then grows until OutOfMemoryError. Finalizers can "resurrect" the object, swallow exceptions silently, and they are a security risk for subclassing. It has been deprecated since Java 9 and deprecated for removal since Java 18. Instead: close resources deterministically with try-with-resources and AutoCloseable. As a safety net for forgotten native resources use java.lang.ref.Cleaner (it uses phantom references and a dedicated thread, and the cleanup action must not refer to the object itself).

try (var in = Files.newInputStream(path)) {
    // used, then closed even on exception
}

5. Garbage collection fundamentals

What does "garbage" mean in Java, and how does the JVM decide something is garbage? Basic

What the interviewer is testing: reachability, which explains leaks later.

An object is garbage when no live part of the program can reach it any more. The JVM does not count references like reference counting; it traces. It starts at a set of GC roots, follows every reference from them to find all reachable objects, and treats everything else as dead. Reference counting cannot free a cycle (A points to B and B points to A, nothing else points to them) but tracing does, because neither is reachable from a root. The roots are: local variables and parameters on the stacks of all live threads, static fields of loaded classes, JNI references, active monitors, and a few internal references. An object kept in a long-lived static map is reachable, therefore not garbage, even if your code will never read it again. That is exactly what a Java "memory leak" is.

Likely follow-ups
  • Can I force GC? System.gc() is only a request and on most collectors triggers a full GC. Avoid it in production; -XX:+DisableExplicitGC ignores it (but be careful if you use direct buffers).
Explain mark-sweep, mark-compact and copying collection. What are the trade-offs? Intermediate

What the interviewer is testing: the three basic algorithms behind every collector.

Mark-sweep: first mark every reachable object, then sweep through the heap and free the unmarked ones. It is simple, but the freed space is scattered in small holes (fragmentation), so allocating a big object may fail even with enough total free memory, and allocation needs free-list searching. Mark-compact: mark, then slide all live objects to one end, so free space is one big block and allocation can use a fast bump pointer. Moving objects costs time and requires updating every reference to them. Copying: split space in two halves, copy live objects from one into the other, then wipe the old half. Cost is proportional to live data only, not to garbage, and the result is compact. But it needs spare room (up to double), which suits the young generation where few objects survive. Real collectors combine them: young generation uses copying, old uses mark-compact (Parallel, Serial) or region-by-region copying (G1).

Why are generational collectors a good idea? Intermediate

What the interviewer is testing: the reasoning behind the heap layout, and when it breaks.

Measurements of real programs show the weak generational hypothesis: most objects die very young (temporary strings, request objects, iterators, boxed numbers), and few objects live long. So the heap is split. A young collection touches only the small young area, and since most things there are dead, copying the few survivors is quick, typically a few milliseconds to tens of milliseconds. The big old area, which is costly to scan, is left alone most of the time. The result is higher throughput and shorter pauses than collecting the whole heap each time. The price is bookkeeping: old objects may refer to young ones, so the JVM keeps a card table (a bitmap of dirty old-area memory) updated by a small write barrier on every reference store, and young collection uses those cards as extra roots. The hypothesis breaks for workloads where many objects live medium-long, like a cache churning in a time-limited window or a batch holding a big working set: then objects get promoted and old collections become the bottleneck.

Likely follow-ups
  • Are all modern collectors generational? G1 yes, Parallel and Serial yes, Generational ZGC yes (since 21), Shenandoah's generational mode is experimental in recent releases.
What are minor, major, mixed and full GC? Intermediate

What the interviewer is testing: precise vocabulary used in GC log reading.

A minor GC (young GC) collects only the young generation. It is frequent and short, and always stops the application (stop-the-world, in all collectors except fully concurrent ones). A major GC collects the old generation; the word is used loosely and different people mean different things. A full GC collects the whole heap (young, old) and also metaspace, usually with a stop-the-world compaction. It is the most expensive event and a sign of trouble in G1 and CMS. In G1 the picture differs: it does young collections, then a concurrent marking cycle to find mostly-garbage old regions, then mixed collections that clean young regions plus some old ones. A full GC in G1 is a fallback when the collector cannot keep up. In logs, G1 shows "Pause Young (Normal)", "Pause Young (Mixed)", "Pause Full (Allocation Failure)" or "(System.gc())". Triggers for a full GC: promotion failure, old generation full, metaspace limit, System.gc(), a heap dump with live, or evacuation failure in G1.

What is a stop-the-world pause and what is a safepoint? Senior

What the interviewer is testing: why pauses exist at all and why a pause can be longer than the GC work itself.

During some GC phases the JVM must be sure that no thread is changing object references, since the collector is tracing or moving objects. So it pauses every Java thread: this is stop-the-world (STW). Threads cannot stop at any instruction. The JIT places safepoint polls at points such as method returns and loop back edges, and when the JVM requests a safepoint, each thread continues until its next poll and then parks. The delay until the last thread arrives is the time to safepoint. A thread running a long counted loop, or doing a slow native call or memory-mapped file page fault, can hold up everyone. Safepoints are used for more than GC: thread dumps, heap dumps, deoptimisation, biased lock revocation (removed in 21), class redefinition. So an application pause may exceed the "pause" in the GC log. Diagnose with -Xlog:safepoint to see "reaching safepoint" times.

Likely follow-ups
  • How do ZGC and Shenandoah get tiny pauses? They do the heavy work (marking, relocating) concurrently while threads run, and only pause briefly for root scanning and synchronisation. Pauses no longer grow with heap size.
How can a young collection find old-to-young references without scanning the old generation? Senior

What the interviewer is testing: write barriers and remembered sets, the hidden cost of generational GC.

If the young collection had to scan the whole old generation to see which young objects it points to, the young collection would be as slow as a full one. So the JVM tracks old-to-young pointers as they are created. The heap is divided into small cards (512 bytes) with a card table, one byte per card. Every time the program stores a reference into a field, a tiny piece of code called a write barrier marks the card containing that field as dirty. At a young GC, only dirty cards in old are scanned and used as extra roots. G1 keeps a more detailed structure per region, the remembered set (which other regions point into me), and refines dirty cards in background threads. This costs some CPU on every reference write and some memory (G1: often 5 to 20% of heap). It also explains why a large, heavily mutated old graph raises young pause times, and why a tiny young generation with plenty of old pointers into it is slow.

What is premature promotion, and why does it hurt? Senior

What the interviewer is testing: do you understand the usual hidden reason that old gen fills up.

Premature promotion means short-lived objects are promoted to old because survivors do not fit in survivor space, or because a young GC happens while they are still in use. Imagine an HTTP request takes 300 ms, and the young generation fills every 100 ms. The request's objects are still live during the young GC, get copied to survivor, and after a few more GCs are promoted, even though they die a moment later. They now sit in old as garbage until an old collection. Old fills, concurrent cycles or full GCs increase, and throughput drops. Signs: the old generation grows steadily after each young GC, and the log shows survivor "to-space overflow" or age distributions that drop off at age 1. Fixes: a larger young generation (or a larger total heap, since G1 sizes young from total), reduce allocation per request, and avoid holding large per-request structures. With G1 do not set -Xmn; give it more heap or a looser pause goal.

6. The collectors: Serial, Parallel, CMS, G1, ZGC, Shenandoah

Name the HotSpot garbage collectors and what each one is for. Basic

What the interviewer is testing: a map of the options before the detail questions.

Serial: one thread does all GC work, with stop-the-world pauses. It has the least overhead, so it fits tiny heaps, single CPU containers and short-lived tools. Parallel (the throughput collector): the same generational design, but many threads do the work during pauses. It maximises total work done and suits batch jobs where a pause of a second does not matter. CMS (Concurrent Mark Sweep): the old low-pause collector, removed in Java 14. G1 (Garbage-First): splits the heap into many regions and collects the ones with most garbage first, aiming at a pause-time goal. It is the default since Java 9 and a good all-rounder. ZGC: a concurrent collector with pauses well under a millisecond (typically), independent of heap size, for large heaps and strict latency. Shenandoah: similar goals, concurrent compaction, from Red Hat, in OpenJDK builds from 12 and production from 15 (not in Oracle JDK builds). Epsilon: collects nothing, for tests and very short runs.

Serial versus Parallel collector: how do they differ, and when would you still use them? Intermediate

What the interviewer is testing: that "old" collectors still have a place, and the throughput versus pause trade-off.

Both use the same classic layout: young generation collected by copying, old generation by mark-compact, both stop-the-world. Serial uses one thread. For a small heap, its pauses are short and there is no thread coordination overhead, no extra background threads, and the smallest memory footprint. That is why the JVM picks it automatically when it sees fewer than 2 CPUs or less than about 1.8 GB. It is a good choice for small containers or CLI tools. Parallel uses many GC threads (by default about one per CPU up to 8, then a fraction of the rest). The pause is shorter than Serial on a big heap but still proportional to live data. Its goal is throughput: the share of time spent running your code rather than GC. It has no concurrent phase and so no background overhead. For a nightly batch job, ETL or a build tool, it often finishes faster than G1. For an interactive service, a full GC under Parallel on a 16 GB heap can take several seconds, which usually violates latency goals.

Likely follow-ups
  • Knobs for Parallel? -XX:ParallelGCThreads, -XX:GCTimeRatio (target throughput), -XX:MaxGCPauseMillis (soft goal).
What was CMS, and why was it removed? Intermediate

What the interviewer is testing: historical awareness, since many older services still carry CMS flags, and why the replacement is better.

CMS (Concurrent Mark Sweep, Java 1.4 era onward) was the first mainstream low-pause collector. It collected the old generation concurrently with the application: a short initial mark pause, concurrent marking and cleaning while threads run, a short remark pause, then concurrent sweep. Young collection was done with a parallel copying collector (ParNew). Weaknesses: it did not compact, so old gen got fragmented. When a large object could not fit, or when promotion outran the concurrent cycle ("concurrent mode failure"), it fell back to a long, single-threaded full GC, the nightmare pause CMS users knew. It left "floating garbage" till the next cycle, needed 20 to 30% spare headroom, used many tuning flags, and burned extra CPU. G1 solved these with region-based compaction and predictable pauses. CMS was deprecated in Java 9 and removed in Java 14. If you see -XX:+UseConcMarkSweepGC in an old config, then on Java 14 and later it just prints a warning and the JVM uses the default collector, which silently changes behaviour.

How does G1 work? Explain regions and the pause-time goal. Intermediate

What the interviewer is testing: the default collector, so you should be able to describe it clearly.

G1 divides the heap into about 2,048 equal regions (1 MB to 32 MB each, computed from heap size; set with -XX:G1HeapRegionSize). There is no fixed memory layout for Eden, Survivor and Old. Instead any region can currently play the role of Eden, Survivor, Old or Humongous (for large objects), and roles change at each collection. A young collection picks all Eden and Survivor regions and evacuates (copies) their live objects into free regions, which compacts as a side effect. The collector knows how much garbage is in every region, and chooses regions with the most garbage first, hence the name. It uses measured copy speed to pick as many regions as fit within the pause goal (-XX:MaxGCPauseMillis, default 200 ms), and resizes the young generation to hit that goal. The goal is a target, not a guarantee. To avoid scanning the whole old gen, each region has a remembered set of incoming references.

Likely follow-ups
  • Should I set -Xmn with G1? No. Fixing young size removes G1's main way of meeting the goal.
  • Is 200 ms goal strict? No. It is a best effort target. Lower goals mean more frequent, smaller collections and lower throughput.
Describe the phases of a G1 cycle: young, concurrent marking and mixed collections. Senior

What the interviewer is testing: can you read a G1 log and know what is normal versus a warning sign.

G1 mostly does young collections (STW). When the old generation occupancy crosses the initiating heap occupancy threshold (-XX:InitiatingHeapOccupancyPercent, default 45%, adaptive since Java 9), it starts a concurrent marking cycle alongside the next young collection: an initial mark (piggy-backed on a young pause), a concurrent root-region scan, a concurrent mark while the app runs (using snapshot-at-the-beginning barriers to cope with changes), a short remark pause, and a cleanup that frees completely empty regions and ranks the rest by garbage amount. Then comes the mixed collection phase: the next several pauses (up to 8 by default) collect young regions plus a slice of the old regions with the most garbage, until the reclaimable amount falls below the waste threshold. Then it goes back to young-only. Healthy: marking cycles end before the heap fills, and mixed pauses stay near the goal.

Likely follow-ups
  • What is SATB? Snapshot-at-the-beginning: the collector marks everything that was reachable when marking started, using a barrier that records overwritten references, so concurrent changes do not hide live objects.
  • How do I fix frequent concurrent cycles? More heap, lower allocation rate, or a larger IHOP if the heap is mostly stable.
What are humongous objects in G1, and why can they hurt? Senior

What the interviewer is testing: a real G1 production gotcha tied to big arrays and batch loading.

An object that is at least half a region in size is called humongous. G1 allocates it directly in old space in one or more contiguous regions, skipping the young generation. For a 4 MB region size, anything of 2 MB or more qualifies, such as a big byte array for a file upload, a large StringBuilder or a big ArrayList backing array growing past that point. Problems: it needs contiguous free regions, which may fail on a fragmented heap and cause a full GC even with plenty of total free space; and it was only freed at marking or cleanup time (newer JDKs can reclaim dead humongous objects eagerly during young pauses, which helps). Too many humongous allocations also trigger early concurrent cycles. Remedies: stream data instead of loading it whole, use chunked buffers, raise -XX:G1HeapRegionSize (for example 16m or 32m) so fewer objects count as humongous, and look for "Humongous" in GC logs (-Xlog:gc+humongous or in a JFR recording).

-XX:G1HeapRegionSize=16m
-Xlog:gc*,gc+humongous=debug:file=gc.log:time,uptime
What do "to-space exhausted" and "evacuation failure" in a G1 log mean? Senior

What the interviewer is testing: can you read the words that signal G1 is in trouble.

During evacuation G1 copies live objects into free regions. If there is not enough free space to copy them (to-space), the pause cannot finish normally. G1 then marks those regions as "evacuation failed", leaves the objects where they are and fixes up pointers; this is slow, and often followed by a Full GC. The log shows To-space exhausted or Evacuation Failure. The usual reasons: the heap is too small for the live set plus promotion spikes; allocation is too fast compared to concurrent marking; the old generation is full of garbage that marking has not yet reclaimed (IHOP too high); too many humongous objects; or -XX:G1ReservePercent (default 10% reserve) is too small for the load. Fixes in order: give more heap, lower the allocation rate or humongous allocations, reduce IHOP so marking starts earlier (or leave adaptive IHOP on), and look at the survivor size. Raising pause goal usually does not help; it is a space problem, not a time problem.

How does ZGC achieve sub-millisecond pauses? Senior

What the interviewer is testing: a developer-level understanding of concurrent compaction, and honesty about trade-offs.

ZGC does almost everything while your threads run: marking, relocating objects (which is compaction) and fixing references. The only stop-the-world steps are very short synchronisations to scan thread stacks (roots), so pause time does not grow with heap size or with live set size, and is typically well below 1 ms (up to 16 TB heaps are supported). How can it move an object while the program uses it? ZGC uses load barriers: a small piece of code the JIT adds whenever a reference is loaded from the heap. The reference carries a few colored bits telling the phase. If the reference is stale, the barrier fixes it on the spot (looks up the new address, or helps relocate the object). So the application heals pointers itself as it touches them. The costs are about 5 to 15% more CPU than G1 in many workloads, a bit more memory, and the need for spare headroom: if allocation outruns the collector, threads stall ("allocation stall"). Generational ZGC (Java 21; the only mode from 24) collects young objects separately, which greatly lowers CPU cost and headroom needs. Enable it with -XX:+UseZGC (in 21, add -XX:+ZGenerational).

Likely follow-ups
  • Is ZGC always better than G1? No. For throughput batch jobs and small heaps G1 or Parallel are more efficient. ZGC wins when tail latency matters or heaps are large.
  • Memory use? Multi-mapped memory shows odd numbers in some tools, so trust the container metrics, not naive RSS reads.
What is Shenandoah, and how does it compare to ZGC? Senior

What the interviewer is testing: knowing both low-pause options and a sound way to choose.

Shenandoah is a region-based, mostly concurrent collector developed at Red Hat, aiming at short pauses regardless of heap size, like ZGC. Its key idea is concurrent compaction: objects are moved while the application runs, with a barrier on reads and writes so every access finds the right copy (older versions used a forwarding pointer in each object, newer use a load-reference barrier). Pauses are usually a few milliseconds or less. It supports compressed oops and works on smaller heaps and 32-bit-style settings, where ZGC historically did not. It ships in OpenJDK builds such as Red Hat, Temurin, Corretto and others, but not in Oracle JDK builds, so check your vendor. Differences from ZGC in practice are minor to a developer: both give far lower pauses than G1, both cost some throughput, and both need headroom. Pick by what your JDK vendor supports and what your own load test shows. A generational mode is available in newer releases.

Likely follow-ups
  • How to enable? -XX:+UseShenandoahGC, on Java 11 and 12 you also needed the experimental unlock flag.
How would you choose a garbage collector for a service? Senior

What the interviewer is testing: a method, driven by goals and measurements, not by habit.

I start with the goal: throughput (batch, ETL, nightly jobs), latency (p99 of an API) or footprint (many tiny containers). Then the facts: heap size, CPU count, JDK version. My default is to stay on the JDK's default, G1, and to measure before changing anything. If the heap is under a few hundred MB or the container has 1 CPU, Serial is often best, because the JVM would pick it anyway. For throughput-only batch with no latency target, Parallel often completes the same work sooner. If the app is latency sensitive and G1 pauses are still too long after tuning (say p99 pauses above 100 to 200 ms), or heaps exceed 30 to 100 GB, try ZGC (generational) or Shenandoah. Test with realistic load for hours, not minutes, watching p99 latency, GC CPU, and memory. Change one thing at a time. Also say that the best "tuning" is often to allocate less (fewer temporary objects, reuse buffers) and fix leaks, because every collector gets faster when there is less garbage and a smaller live set.

When would you use Epsilon or turn GC logging up to debug a collector choice? Intermediate

What the interviewer is testing: awareness of niche tools and of how to compare collectors on your own app.

Epsilon (-XX:+UseEpsilonGC, Java 11) allocates memory but never reclaims it. When the heap is full, the JVM exits with OutOfMemoryError. That sounds useless, but it is valuable for: performance tests that must exclude GC noise, measuring an app's raw allocation, and extremely short-lived jobs (a function that runs for 200 ms and exits) where GC work is wasted. To compare real collectors, run the same load test with each, with the same heap, and capture -Xlog:gc* plus latency percentiles from the application. Compare p50, p99 and p99.9 latency, throughput, total CPU and peak memory. A common trap is judging only by average pause. Another is testing on a laptop with different CPU counts from production, which changes the thread counts and even picks Serial.

7. Tuning flags and reading GC logs

Which heap flags matter: -Xms, -Xmx, -XX:MaxRAMPercentage, and how should you set them? Basic

What the interviewer is testing: the flags everyone has to touch, and the sizing logic.

-Xms is the initial heap size and -Xmx the maximum. The heap can grow from one to the other. In production on a fixed-size host or container, set them equal: no resize pauses, and no surprise when the OS cannot give you the memory later. -XX:+AlwaysPreTouch additionally touches all pages at startup so the first request does not pay page faults (it slows startup). In containers, instead of a fixed megabyte count, use -XX:MaxRAMPercentage=70 (and -XX:InitialRAMPercentage), which sizes the heap as a percent of the container memory limit. The default is only 25% of limit, which wastes memory in a dedicated container. Do not go much past 75%: the rest of the process (metaspace, stacks, code cache, direct memory) needs room. -Xmx overrides percentages if both are given. Size the heap from data: the live set after a full GC (from GC log or JFR), then set max to about 2 to 4 times that.

java -Xms2g -Xmx2g -XX:MaxMetaspaceSize=256m -jar app.jar        # fixed host
java -XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError -jar app.jar   # container
Likely follow-ups
  • Why not just set the heap huge? Longer full GCs, a bigger memory bill, and a leak takes longer to appear, then gives a bigger heap dump.
Which other JVM flags would you put on every production service? Intermediate

What the interviewer is testing: practical operational habits, not flag trivia.

A sensible baseline: heap sizing (above); -XX:+HeapDumpOnOutOfMemoryError with -XX:HeapDumpPath=/dumps so the first OOM leaves evidence (make sure the path has disk space and is a mounted volume in containers); -XX:+ExitOnOutOfMemoryError (or CrashOnOutOfMemoryError) so a half-dead JVM is restarted by the orchestrator instead of limping; unified GC logging -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20m, which costs almost nothing; -XX:MaxMetaspaceSize to cap class metadata; and optionally -XX:NativeMemoryTracking=summary (about 5 to 10% overhead, so some teams enable it only when investigating), -XX:+UseStringDeduplication with G1 for string-heavy apps, and -Xss only if you know you need it. Also keep JFR available: -XX:StartFlightRecording can run continuously with low overhead (about 1 to 2%). Avoid copying huge flag lists from the internet; each flag is a risk across JDK upgrades.

How do you tune G1 to meet a latency target? Senior

What the interviewer is testing: disciplined tuning: measure, change one lever, and know which levers exist.

First, read the GC log and identify the problem. Is it long young pauses, long mixed pauses, concurrent cycles that cannot keep up, or full GCs? Then pick levers. Pause goal: -XX:MaxGCPauseMillis=100 makes G1 collect less per pause and so pauses are shorter but more frequent, costing throughput. More heap usually fixes most problems, because it gives G1 room to finish marking. Reduce allocation rate and promotion in the code. For mixed pauses that are too long, G1 can reclaim fewer old regions per pause: -XX:G1MixedGCCountTarget (more mixed pauses with less work each) and -XX:G1MixedGCLiveThresholdPercent. For early marking: -XX:InitiatingHeapOccupancyPercent, or leave adaptive IHOP alone. For humongous: larger region size. For time spent in GC threads: -XX:ParallelGCThreads and -XX:ConcGCThreads (most important in containers where the JVM sees fewer CPUs). Avoid -Xmn, -XX:NewSize and SurvivorRatio, which switch off its adaptive sizing. Re-test after every change under the same load.

Common mistakes: setting a pause goal of 10 ms on G1 with a heavy allocation rate; G1 then spends most CPU in GC and throughput collapses, and the pause goal is still missed.
How do you read a GC log? What lines and numbers do you look at first? Intermediate

What the interviewer is testing: hands-on skill. Many candidates know the theory but have never opened a log.

Turn it on with -Xlog:gc*:file=gc.log:time,uptime,level,tags (Java 9 or later; on Java 8 use -XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log). A basic G1 line looks like this: pause type and cause, then heap before, after (and total), then the pause time. Tools: GCeasy, GCViewer, or the JFR GC views.

How do you decide how big the heap should be? Senior

What the interviewer is testing: evidence-based sizing instead of copying numbers.

Measure the live set: the heap used right after a full or concluding mixed collection under real, peak-like load (the "heap after" numbers in the log, or jcmd PID GC.heap_info after GC.run in a test). The max heap should be about 2 to 4 times the live set for G1 and Parallel, which leaves room for young allocation, promotion bursts and marking to finish. Too small: frequent GCs and full GCs. Too big: wasted memory, longer full GCs, and more expensive containers. Then check headroom: container limit should be heap plus metaspace, stacks, code cache, direct memory and GC overhead (usually heap divided by 0.7 to 0.75). Plan for both normal and peak: a batch import that doubles the live set once a day defines the maximum. Re-measure after every big release, because live sets drift as caches and features grow. If the service autoscales horizontally, remember each pod pays its own overhead, so many small pods cost more total memory than a few larger ones.

What is "GC overhead" and how can you tell the JVM spends too much time in GC? Intermediate

What the interviewer is testing: a quick health measurement and the matching symptoms.

GC overhead is the fraction of wall-clock time where the application is paused or where GC threads steal CPU. How to see it: from GC logs add the pause times over a window and divide by the window length; with jstat -gcutil PID 1000 look at YGCT and FGCT (total time spent) rising per second; or in JFR/APM dashboards chart "GC time". A healthy service spends under 1 to 5% of time in GC. Over 10% is a problem, and if GC occupies 90% or more of the time while freeing almost nothing, the JVM may throw OutOfMemoryError: GC overhead limit exceeded (the Parallel collector does this: more than 98% time in GC and less than 2% heap recovered). Symptoms of a GC-bound app: high CPU with low throughput, latency spikes that line up with pauses, full GCs back to back, and the heap after each GC staying near max.

8. Memory leaks and OutOfMemoryError

Java has a garbage collector. How can it still have memory leaks? Basic

What the interviewer is testing: the correct definition of a leak in a managed language.

The GC only frees objects that are unreachable. A leak in Java is an object that is still reachable, so it cannot be collected, but the program will never use it again. The code just forgot to remove the last reference. Over time these pile up, the heap after each GC rises, GC runs more and more, and finally you get OutOfMemoryError. The leaked data is not special; the problem is a lifetime mismatch: a short-lived thing is stored in something long-lived (a static map, a cache, a thread, a listener list, a class loader). Example: a static Map<String, Session> where you add sessions on login and forget to remove them on logout. The map is a GC root path to every session ever created.

class SessionRegistry {
    private static final Map<String, Session> ALL = new HashMap<>();
    static void onLogin(Session s)  { ALL.put(s.id(), s); }
    // onLogout never removes it  -> leak
}
What are the most common causes of memory leaks in real Java services? Intermediate

What the interviewer is testing: pattern recognition from experience.

The usual suspects, in rough order of how often I see them:

  • Unbounded caches and maps: a static or singleton HashMap used as a cache with no size limit or expiry. Fix with Caffeine or Guava Cache with a maximum size and time-to-live.
  • ThreadLocal values on pooled threads: server threads live forever, so a value set per request and never removed (remove() in a finally block) lives forever, and may pin a class loader.
  • Listeners and callbacks not unregistered: event buses, addListener without removeListener, observers, Spring application event listeners created per request.
  • Unclosed resources: streams, connections, ResultSet, HTTP responses, ExecutorService never shut down (each holds native memory or threads).
  • Collections that only grow: queues where the consumer is slower than the producer (unbounded LinkedBlockingQueue), a list of "recent events" never trimmed.
  • Inner classes and lambdas capturing this: a long-lived task holds the whole outer object.
  • Class loader leaks at redeploy, and String.intern or generated classes without limit.
  • Bad equals/hashCode on map keys: entries are added again and again but never found for removal.
  • Metrics with unbounded labels (a tag per user id or URL), common with Micrometer and Prometheus.
Likely follow-ups
  • Does a mutable key in a HashMap leak? Yes, if you change a field used in hashCode after inserting, the entry cannot be found or removed.
How do you find a memory leak in a running production service? Senior

What the interviewer is testing: a calm, step-by-step method that uses the right tools without hurting production.

1. Confirm it is a leak. Chart the heap used after GC over hours. A sawtooth with a rising floor is a leak. A flat floor at a high value is an undersized heap. 2. Find which class grows. Cheap and live: jcmd PID GC.class_histogram (or jmap -histo:live PID) twice, some time apart, and compare; the leaking class count rises. 3. Capture a heap dump when memory is high: jcmd PID GC.heap_dump /tmp/h.hprof. This pauses the JVM for seconds on a big heap and writes a file about the heap size, so do it on one instance taken out of the load balancer. 4. Analyse in Eclipse MAT (or VisualVM, IntelliJ profiler): open the Leak Suspects report, then the dominator tree (what holds the most retained memory), and use "path to GC roots, excluding weak references" on a suspicious object. The path reads like a story: static field, map, entry, your object. 5. For low-overhead continuous detection use JFR with the jdk.OldObjectSample event, which records allocation stack traces and root paths of old objects with minimal cost. 6. Fix, redeploy, and confirm the floor is now flat.

jcmd <pid> GC.class_histogram | head -20
jcmd <pid> GC.heap_dump /tmp/h.hprof          # add -all to include unreachable objects
jfr print --events jdk.OldObjectSample rec.jfr
Common mistakes: dumping a heap on the busiest pod without draining it; opening a 20 GB dump on a laptop (give MAT more memory, or analyse on a server); trusting shallow size instead of retained size.
In a heap dump analysis, what are shallow size, retained size, dominator tree and GC root path? Senior

What the interviewer is testing: fluency with the vocabulary of heap analysis tools.

Shallow size is the memory of the object itself (header and fields, not what it points to). A HashMap object is about 48 bytes shallow, even if it holds a million entries. Retained size is the memory that would be freed if this object were collected: itself plus everything reachable only through it. That tells you what a suspect really costs. The dominator tree is a tree where object X dominates Y if every path from a GC root to Y goes through X. Sorting it by retained size puts the real culprit on top, for example one cache object retaining 600 MB. A path to GC roots shows the exact chain of references that keeps one object alive, starting at a root such as a static field of a class, a thread (by its name), or a JNI global. Reading this chain tells you what code to fix. MAT also offers "histogram" (counts per class), "duplicate classes" (class loader leaks), "OQL" queries, and a "compare to baseline snapshot" feature for before and after dumps.

What is the difference between a Java OutOfMemoryError and the Linux OOM killer? Senior

What the interviewer is testing: distinguishing the JVM's own limit from the operating system's, which decides where you look.

An OutOfMemoryError is thrown by the JVM when one of its own limits is hit: the maximum heap, metaspace limit, direct buffer limit. It is an exception: your logs show it, a heap dump can be written, and the process may even survive. The Linux OOM killer (or a container runtime enforcing a cgroup memory limit) is outside the JVM: when the total process memory (RSS: heap, metaspace, stacks, native) exceeds the machine or container limit, the kernel kills the process with SIGKILL. There is no stack trace, no heap dump, no shutdown hook; the evidence is outside. In Kubernetes the pod shows OOMKilled with exit code 137, and on a plain host dmesg shows "Out of memory: Killed process". If the JVM threw an OOME, tune the JVM area named in the message. If the container was killed with a healthy heap, the heap is probably set too close to the limit, or native memory (direct buffers, threads, metaspace) grew. Compare heap max plus other areas to the container limit, and use NMT.

What causes "OutOfMemoryError: unable to create native thread"? Senior

What the interviewer is testing: that this error is not about the heap, and ties to thread design.

Each Java platform thread is a real OS thread with its own stack (default 1 MB reserved) and kernel structures. This error means the OS refused to make another one. Reasons: the app has too many threads (a thread leak, an unbounded pool such as Executors.newCachedThreadPool() under load, a new thread per request); a limit was reached (ulimit -u for the user, /proc/sys/kernel/threads-max, the container pids.max limit); or the machine has no memory left for another stack, which can be made worse by a huge -Xss or an oversized heap that leaves too little native memory. Counterintuitively, giving the JVM more heap makes it worse, since it takes memory away from native allocations. Diagnose with a thread dump: group threads by name prefix (jstack PID | grep '^"' | sed 's/-[0-9]*"//' | sort | uniq -c) and find which pool exploded. Fix by bounding pools, using a queue, fixing the leak of threads that never finish, or on Java 21 and later moving to virtual threads for lots of blocking tasks (see Java concurrency).

What are direct buffers, and how can they cause an OutOfMemoryError while the heap looks fine? Senior

What the interviewer is testing: understanding that off-heap memory is freed only through heap objects.

ByteBuffer.allocateDirect(n) allocates memory outside the heap, in native memory. It is faster for I/O because the OS can read or write straight into it without an extra copy. NIO, Netty, Kafka clients, gRPC and many database drivers use it heavily. The limit is -XX:MaxDirectMemorySize (defaults to about the max heap size). The trap: the small Java ByteBuffer object sits on the heap, and the native block is freed only when that object is garbage collected (through a cleaner). If the heap has plenty of room, young GCs are rare, so the tiny heap objects are not collected soon, while the native memory is already full. Result: OutOfMemoryError: Direct buffer memory although the heap is nearly empty. Worse, if code calls allocateDirect in a loop, or Netty buffers are not released (reference counted release() forgotten), it is a true leak. Check with JMX BufferPool MXBeans (the "direct" pool count and used bytes), Netty's leak detector, and NMT. Fixes: release buffers, pool and reuse them, size MaxDirectMemorySize explicitly, and avoid -XX:+DisableExplicitGC when relying on System.gc() to free them.

What does "GC overhead limit exceeded" mean, and should I disable it? Intermediate

What the interviewer is testing: do not mask a symptom.

The Parallel collector throws it when more than 98% of the time is spent in GC and less than 2% of heap is freed, repeated over several consecutive collections. It means the JVM is about to run out of heap, and is just failing early rather than crawling for hours. You can switch the check off with -XX:-UseGCOverheadLimit, but that only trades a quick failure for a very slow death, with the application near-frozen. The right response is the same as for "Java heap space": find what fills the heap (leak, a query loading millions of rows, a giant cache), or increase the heap if the live data is truly that large. G1 does not have this check; it just runs full GCs and then throws "Java heap space".

9. JIT, AOT, warm-up and the memory model

What is the JIT compiler, and why does Java need it? Basic

What the interviewer is testing: why Java can be as fast as compiled languages and what that implies for startup.

Interpreting bytecode is slow: each instruction is decoded and executed by software. The JIT (Just-In-Time) compiler translates bytecode to native machine code while the program runs, so the CPU executes it directly. The JVM first interprets everything, counting how often each method is called and how many times each loop iterates. When a method is "hot", it is compiled. Because it compiles at run time, it knows facts a static compiler does not: which classes are actually loaded, which branch is taken 99.9% of the time, which type is really behind an interface call. It uses these facts for optimisations, and if a guess turns out wrong it discards the code and falls back to the interpreter. This is why a long-running Java service can match C++ in many workloads, but also why a Java process starts slowly: it needs time to find and compile hot code (warm-up).

Explain tiered compilation, C1 and C2. Intermediate

What the interviewer is testing: the structure behind warm-up behaviour.

HotSpot has two JIT compilers. C1 (client compiler) compiles quickly and applies cheap optimisations. C2 (server compiler) takes longer and applies aggressive optimisations, producing the fastest code. Since Java 8 tiered compilation is on by default and uses both. Code starts in the interpreter (level 0). When a method is called often enough (on the order of a couple of hundred calls or loop iterations), C1 compiles it with profiling code included (levels 2 and 3), which collects the type and branch statistics. When it becomes really hot (thousands of invocations), C2 recompiles it at level 4 using those statistics. Meanwhile compilation runs on background compiler threads, so your thread keeps running the older code. Very hot loops can even be swapped in while running, called on-stack replacement (OSR). The result is quick start from C1 and top speed from C2.

Likely follow-ups
  • See what is compiled? -XX:+PrintCompilation. See inlining? -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining.
  • Code cache full? The JIT stops compiling and performance falls. Raise -XX:ReservedCodeCacheSize.
What is method inlining, and why is it the most important JIT optimisation? Intermediate

What the interviewer is testing: why small methods and clean code do not cost performance in Java, and where the limits are.

Inlining means the compiler copies a small method's body into the caller, removing the call overhead. The gain is bigger than the call cost: after inlining, the compiler sees the combined code and can apply more optimisations (remove dead branches, reuse values, eliminate allocations, hoist checks out of loops). That is why getters and tiny helper methods are free in compiled code. By default, methods under about 35 bytecode bytes are inlined, and hot methods up to about 325 bytes (-XX:MaxInlineSize, -XX:FreqInlineSize). It even inlines virtual and interface calls when profiling shows one dominant type (monomorphic), with a guard that deoptimises if another type shows up. Calls with two types are bimorphic and still handled; megamorphic call sites (many types) are not inlined and cost more. A very large method that exceeds the huge-method limit (8000 bytes) is never compiled, which is a reason to avoid giant methods.

What is escape analysis, and how does it reduce garbage? Senior

What the interviewer is testing: the "objects are always on the heap" caveat, and not over-trusting it.

After inlining, C2 can prove that an object never leaves the current method, so no other thread or caller can see it. It then applies scalar replacement: the object is never allocated; its fields become plain local variables (in registers). A temporary Point created, used and discarded in a loop then costs nothing. It can also do lock elision (remove synchronized on an object that does not escape, so a local StringBuffer loses its lock cost) and lock coarsening. These are optimisations that appear only in C2-compiled code, only if everything is inlined, and the analysis gives up for large methods, objects stored in fields or arrays, or objects passed to a non-inlined method. So write natural code with small objects, but do not assume "it will be optimised away" in a hot path without measuring (JMH, allocation profiling). For example, boxing an int into an Integer inside a loop may or may not be eliminated.

What is deoptimisation? Why would compiled code be thrown away? Senior

What the interviewer is testing: understanding that JIT code is speculative, which explains performance cliffs.

The JIT optimises on assumptions learned from profiling: "this branch never runs", "this call site only ever sees ArrayList", "no subclass of this class is loaded", "this value is never null". It puts a cheap guard where the assumption matters, called an uncommon trap. If the guard fails, the JVM deoptimises: it abandons the compiled code for that method, rebuilds the interpreter's state from the machine state, and continues in the interpreter. The method is then profiled again and recompiled with new knowledge. Typical triggers: a new class loaded that breaks a class hierarchy assumption, a rare branch finally taken (for instance the first error in an hour), a type profile change. In production a burst of deoptimisations looks like a latency spike after a rare event; traffic shape changes can cause it. You can see it with -XX:+PrintCompilation ("made not entrant") or JFR compilation events. One mitigation is warming up with representative traffic, including error paths, before taking real load.

Why is a Java service slow right after start, and what can you do about it? Intermediate

What the interviewer is testing: a classic production symptom (slow after deploy, fast later) with a toolbox of fixes.

In the first seconds to minutes: classes are still being loaded and initialised, code runs in the interpreter, hot code is not yet compiled, caches (application and CPU) are cold, connection pools are empty, and the heap is still growing. All of this adds up to higher latency and CPU, often bad enough that a rolling deploy sends full traffic to a new pod that cannot cope, and health checks or timeouts fail. Remedies, from simple to heavy: (1) a proper readiness probe that waits until the app has done a warm-up routine, sending synthetic requests that cover the main paths; (2) slow-start / ramp-up in the load balancer so traffic increases gradually; (3) give the pod enough CPU during startup (CPU limits throttle the JIT threads and make warm-up much longer; some teams allow a startup CPU boost); (4) Class Data Sharing (AppCDS) archives to speed class loading; (5) newer options: JDK 24+ ahead-of-time class loading and linking cache (Project Leyden), CRaC (checkpoint and restore of a warmed process), or GraalVM native image for fast start at the cost of peak throughput. Also lazily initialised beans and heavy Spring component scanning slow startup; measure it.

Likely follow-ups
  • Why benchmarks lie without warm-up: first iterations include interpreter time. Use JMH, which handles warm-up, forks and dead-code elimination.
What is GraalVM native image, and what are the trade-offs? Intermediate

What the interviewer is testing: informed view on AOT, not hype.

Native image compiles your Java application ahead of time into a standalone native executable. During the build it analyses the code under a "closed world" assumption: everything that can run must be known at build time. It then compiles only reachable code and includes a small runtime (a minimal GC and thread support). Benefits: start in tens of milliseconds, small memory footprint, no JIT warm-up, nice for serverless functions, CLI tools and scale-to-zero services. Costs: long build times (minutes) and high build memory; features that are dynamic (reflection, dynamic proxies, resource loading, JNI, serialisation) need configuration hints at build time, though frameworks like Spring Boot 3, Quarkus and Micronaut generate them for you; fewer GC choices; peak throughput is often lower than a JIT-warmed JVM, since there is no run-time profiling (PGO can help); debugging and tooling are different (no jcmd heap dumps in the same way, unless supported). For long-running, high-throughput services the plain JVM is normally the better choice; for short-lived or cold-start sensitive ones, native image shines.

Likely follow-ups
  • Other ways to get faster start without native image? AppCDS, CRaC, Leyden AOT cache, trimming Spring auto-configuration, lazy init.
How is the Java Memory Model related to all this? Intermediate

What the interviewer is testing: that you separate "memory areas" (this page) from the "memory model" (visibility and ordering between threads).

Two different things share the word "memory". The runtime data areas above describe where data lives. The Java Memory Model (JMM) describes when one thread is guaranteed to see another thread's writes. Because CPUs have caches and compilers reorder instructions, without a rule thread B may not see what thread A wrote, or may see writes in a different order. The JMM defines happens-before rules: an unlock happens before a later lock of the same monitor, a write to a volatile field happens before a later read of it, Thread.start() happens before the thread's actions, and a thread's actions happen before another thread's join() returns. If there is a happens-before edge, the reader sees the writer's data. The JIT is allowed to optimise anything that does not break these rules, such as hoisting a non-volatile field read out of a loop (making a "stop flag" loop run forever). The JMM also protects final fields after construction. Full coverage, including volatile, atomics and locks, is in Java concurrency.

10. The JVM in containers

Is the JVM aware of container limits? What changed over the versions? Intermediate

What the interviewer is testing: a very common production issue. Old JVMs saw the whole host, not the container.

A container is a normal Linux process limited by cgroups (control groups): the kernel enforces a memory limit and a CPU quota. A JVM that does not read those limits sees the host machine, for example 64 GB and 32 CPUs, and sizes the heap to a quarter of 64 GB and creates 32 GC threads, then the container is killed for exceeding its real limit. Java 8 before update 191 behaved that way. From Java 10 (and 8u191) the JVM reads cgroup v1 limits, and later versions (Java 15 and updates of 11 and 8) understand cgroup v2 too. Container support is on by default (-XX:+UseContainerSupport). The JVM then uses the memory limit for default heap sizing (a quarter of it, MaxRAMPercentage=25) and the CPU quota to compute how many CPUs it has (Runtime.availableProcessors()), which in turn sizes GC thread counts, the common fork-join pool, and the choice of collector. If the limit is under 2 CPUs or 1.8 GB, the JVM picks Serial GC instead of G1, which surprises people. Check what the JVM sees with -Xlog:os+container or java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|UseG1GC|UseSerialGC'.

Likely follow-ups
  • How do I override the CPU count? -XX:ActiveProcessorCount=N.
  • Does requests matter or only limits? The JVM reads limits. A request without a limit means the JVM sees the whole node.
How do you size container memory for a Java service? Senior

What the interviewer is testing: the key rule that heap is not the whole process.

Think of the container limit as a budget that must cover every area the process uses: heap (max) + metaspace (100 to 300 MB) + code cache (up to 240 MB, usually 50 to 100 used) + thread stacks (threads times stack size, say 200 threads times 1 MB) + direct buffers and native libraries + GC overhead (G1 structures) + some slack for the OS page cache accounting. A practical rule: set -XX:MaxRAMPercentage between 60 and 75, not 90 or 100; smaller containers (under 1 GB) need a lower percentage because the fixed overheads are a bigger share. Example: limit 2 GB, MaxRAMPercentage=70 gives a 1.4 GB heap and leaves about 600 MB for everything else. Validate with NMT or by watching the container working-set memory under peak load, and leave 10 to 20% free. If the pod keeps getting OOMKilled while the heap is fine, you are exceeding the budget in a non-heap area, and lowering the heap percentage is a legitimate fix.

How do CPU limits in Kubernetes affect a JVM? Senior

What the interviewer is testing: the hidden cost of CPU throttling on pause times and warm-up.

A CPU limit (say 2 cores) is enforced as a quota per 100 ms period: once all your threads together use 200 ms of CPU in that period, all of them are frozen until the next period. This is called throttling. The JVM has many busy threads beyond your request threads: GC workers, JIT compiler threads, and at startup lots of work. A parallel young collection with 4 GC threads on a 2-core quota can burn the quota in 50 ms and then the whole process, including the application, stalls for the rest of the period. The visible effect is latency spikes of tens to hundreds of milliseconds that do not appear in GC logs. Warm-up also takes far longer. Mitigations: set CPU limits higher than the average need (or remove limits and keep only requests, which many teams do for latency-sensitive services), match ParallelGCThreads and ConcGCThreads to the quota, watch the container_cpu_cfs_throttled metric, and remember JVM defaults use the quota to pick the number of processors, so 1 CPU means Serial GC.

Which JVM settings do you use in a Kubernetes deployment? Intermediate

What the interviewer is testing: practical, minimal configuration instead of a flag dump.

I keep it small. Pass them through JAVA_TOOL_OPTIONS or JAVA_OPTS in the deployment. Typical baseline: -XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps with an emptyDir or volume mounted at /dumps (otherwise the dump is lost when the container restarts), and GC logging to stdout so the log system collects it: -Xlog:gc*:stdout:time,uptime,level,tags. Set requests equal to limits for memory (avoids eviction surprises). Keep a decent CPU limit, and pin -XX:ActiveProcessorCount only if you have a reason. Add a startup or readiness probe long enough for warm-up. Ensure the JDK in the image includes jcmd or use an ephemeral debug container. For graceful shutdown, handle SIGTERM (the JVM runs shutdown hooks) and make terminationGracePeriodSeconds larger than your drain time.

Which JDK tools do you use to inspect a running JVM, and for what? Basic

What the interviewer is testing: practical diagnostics vocabulary.

How do you take and read a thread dump? What patterns do you look for? Intermediate

What the interviewer is testing: the number one tool for hangs, high CPU and stuck pools.

Take 3 dumps, 5 to 10 seconds apart (jcmd PID Thread.print or kill -3 PID, which prints to the process output). One dump is a photo, a few dumps show movement. Each thread shows a name, state (RUNNABLE, BLOCKED, WAITING, TIMED_WAITING), and its stack. Patterns: many threads BLOCKED on the same lock ("waiting to lock <0x...>" with one owner thread) is lock contention; find the owner and what it is doing. Deadlock: the dump ends with "Found one Java-level deadlock" and names the cycle. All pool threads WAITING on the same I/O call (database, HTTP client) means a slow downstream. Threads stuck in the same method in all dumps shows a hotspot or infinite loop. Thousands of threads with similar names means a thread leak. For high CPU, map the hot OS thread id (top -H -p PID) to the hex nid in the dump. Names matter: always name your thread pools with a thread factory so dumps are readable.

top -H -p <pid>              # find hottest thread id, e.g. 4321
printf '%x\n' 4321           # 10e1
jcmd <pid> Thread.print | grep -A 20 'nid=0x10e1'
The service has 100% CPU. How do you find out whether it is your code, the JIT or the GC? Senior

What the interviewer is testing: structured triage by thread type.

Look at which threads are using CPU: top -H -p PID. In a thread dump, GC threads are named like "GC Thread#3" or "G1 Conc#1" and JIT threads "C2 CompilerThread0". If GC threads are hot, check jstat -gcutil or the GC log: frequent young GCs mean a high allocation rate, and back-to-back full GCs mean the heap is too small or leaking. If compiler threads are hot, it is warm-up, or a deoptimisation loop (rare), or code cache problems; it normally calms down within minutes after start. If application threads are hot, take thread dumps and a CPU profile: JFR or async-profiler for 30 to 60 seconds gives a flame graph that shows which methods burn CPU (regexes, JSON serialisation, a tight retry loop, a hash collision storm, an endless loop on a corrupted structure). Also compare to traffic: did request rate change, did a new release go out, did a cache expire so everything recomputes? Fix the biggest box in the flame graph first.

What is Java Flight Recorder, and when do you use it instead of a profiler? Intermediate

What the interviewer is testing: knowing the safe, built-in production profiler.

JFR is an event recorder built into the JVM. It records low-level events (GC pauses, allocations, thread parking, lock contention, I/O, method samples, JIT compilations, exceptions) into a compact binary file with about 1 to 2% overhead, so it is safe to leave on in production. It was a commercial feature until Java 11 where it became part of OpenJDK. You start it at launch (-XX:StartFlightRecording=duration=1h,filename=app.jfr) or on a live process (jcmd PID JFR.start), and open the file in JDK Mission Control or read it with the jfr command. It samples the Java stack about every 10 to 20 ms, so it finds hot methods without the big bias of instrumenting profilers. It also gives allocation hot spots, GC phases and the OldObjectSample leak events. Use JFR first for most "why is it slow" questions in production. Use a heavier tool (async-profiler) when you need native frames, kernel time, or accurate allocation and lock flame graphs.

jcmd <pid> JFR.start name=r settings=profile duration=120s filename=/tmp/r.jfr
jfr summary /tmp/r.jfr
jfr print --events jdk.GarbageCollection /tmp/r.jfr | head
What is async-profiler, what is a flame graph, and what is "safepoint bias"? Senior

What the interviewer is testing: modern profiling concepts rather than a specific tool command.

async-profiler is an open source sampling profiler that uses OS features (perf_events on Linux) and the JVM's AsyncGetCallTrace to take stack samples at any instruction, not only at safepoints. Many older profilers (and parts of JVMTI) only see threads when they reach a safepoint, so the samples are biased to places where the JIT put polls (loop ends, method returns), blaming the wrong code. This is the safepoint bias. async-profiler avoids it, sees native and kernel frames, and can profile CPU, wall-clock time, allocations, and lock contention. The output is a flame graph: each box is a method, its width is the share of samples where that method was on the stack, the stack grows upward (callers below). You look for the widest boxes at the top: that is where time is actually spent. A plateau of width is a hot method; a wide tower is a hot call path. Wall-clock mode shows where threads wait, such as on a database call, whereas CPU mode shows only on-CPU time. Run it with asprof -d 30 -f flame.html PID.

What is the impact of taking a heap dump or a thread dump on a production JVM? Senior

What the interviewer is testing: responsible operations: diagnostics have a cost.

A thread dump needs a safepoint, so it pauses the application briefly (milliseconds to a few hundred ms with thousands of threads). It is cheap enough to take several. A heap dump stops the world while it writes the file; for a 8 GB heap it can mean 10 to 60 seconds of freeze and an 8 GB file, so health checks fail and the pod may be killed in the middle. jmap -dump:live and jcmd GC.heap_dump first trigger a full GC to keep only live objects, making the pause longer. Disk: make sure there is space for a file as large as the heap. Privacy: the dump contains everything in memory, including passwords, tokens and personal data, so store and share it carefully. Good practice: take the dump on one instance that has been removed from the load balancer; or rely on HeapDumpOnOutOfMemoryError to capture when it matters. A class histogram (GC.class_histogram) is far cheaper and often enough to confirm a leak.

How does autoboxing affect memory and speed? Give an example. Intermediate

What the interviewer is testing: performance awareness that ties directly to object layout and GC.

A primitive int is 4 bytes in a register or array. An Integer is a heap object (16 bytes plus a 4 to 8 byte reference), and values outside -128 to 127 allocate a new object on each boxing (Integer.valueOf caches only small values). So List<Integer>, Map<Long, Long> or stream().map(...) over boxed numbers create a lot of small objects and pointer-chasing, which hurts CPU caches and creates garbage. A classic bug: Long sum = 0L; for (...) sum += x; creates a new Long on every iteration. The fix is to use primitives (long sum), primitive streams (IntStream, mapToInt), primitive arrays, or primitive-specialised collections (Eclipse Collections, fastutil) when millions of elements are involved. Also beware of == on boxed values, and null unboxing causing NullPointerException. Escape analysis sometimes removes boxing in simple loops, but do not depend on it for hot paths.

Long sum = 0L;                       // boxed accumulator: one allocation per +=
for (int i = 0; i < 1_000_000; i++) sum += i;

long sum2 = 0L;                      // primitive: no allocation
for (int i = 0; i < 1_000_000; i++) sum2 += i;
What is allocation rate, and how does reducing it help GC? Senior

What the interviewer is testing: the most effective tuning of all: produce less garbage.

Allocation rate is how many MB per second your code creates. Young GCs happen each time Eden fills, so the GC frequency is roughly allocation rate divided by Eden size. A service allocating 1 GB/s with a 500 MB Eden collects twice a second. Each young GC costs time proportional to the live objects at that moment, not to the garbage, so frequent GCs mean more chances to catch objects that are mid-request (live) and promote them early, more write-barrier and card work, and more CPU. High allocation rates (several GB/s) are a typical reason for "GC uses lots of CPU". Measure it from the GC log (heap before-next minus heap after-previous, over time) or JFR allocation profiling. Reduce by: removing needless temporary objects (repeated string building, boxing, regex Pattern.compile per call, creating ObjectMapper or DateFormat per request), reuse buffers, avoid large intermediate collections (use streaming and pagination), choose primitive collections, and log lazily with parameters. Then, if needed, give the JVM a larger young generation by giving a larger heap.

What problems do very large objects and big collections cause? Intermediate

What the interviewer is testing: the typical "load the whole file or table" bug.

A big array or list needs one contiguous block. In G1 it becomes a humongous object with the issues described earlier. Growing structures copy: an ArrayList that doubles from 1 GB briefly needs 1.5 GB (old and new arrays at once) and may cause OutOfMemoryError when the live data would have fitted. Reading a 500 MB file into a String or byte[] needs the bytes plus the String copy (Java 9 and later compact strings help but you may still hold two copies), and with a JSON parse tree many times the size of the file. Loading a million rows from a database with an ORM adds entity objects, proxies and first-level cache copies. The remedies are in the design: stream (BufferedReader.lines(), JDBC fetch size, cursors, Spring Batch chunks), paginate, process in chunks, set size limits on request bodies, and pre-size collections when you know the count. A single large request can cause OutOfMemoryError for the whole service, so limit inputs at the edge.

When are classes unloaded, and why does it matter? Senior

What the interviewer is testing: link between class loaders, GC and Metaspace.

A class is unloaded only when its class loader becomes unreachable, together with all classes it defined and all their instances. Classes from the bootstrap, platform and application loaders live for the whole run, so for a plain application nothing gets unloaded. Unloading matters for dynamic systems: application servers redeploying apps, OSGi, scripting engines (Groovy, JavaScript), code generators and proxy libraries (CGLIB, ByteBuddy, Hibernate bytecode enhancement), and Lambda or reflection-heavy frameworks that spin up generated classes. Class unloading happens as part of a GC cycle (in G1 during a concurrent cycle or a Full GC; ZGC does it concurrently), and it is triggered when metaspace usage crosses the MetaspaceSize threshold. If something strongly references any one class from the loader (an object instance, a static field in a shared library, a thread), the entire loader stays, and metaspace grows until OutOfMemoryError: Metaspace. Generating a new class per request (for example compiling an expression into bytecode each time) is the classic way to blow up metaspace without any redeploy.

jcmd <pid> VM.classloader_stats
jstat -class <pid> 1000      # loaded and unloaded class counts
Which small coding habits reduce GC pressure and JVM memory cost? Intermediate

What the interviewer is testing: practical, low-risk habits from someone who has read GC logs.

First, do not optimise blindly; measure with a profiler. These habits are safe anyway. Use parameterised logging (log.debug("user {}", id)) instead of building the string yourself, since the string is built even when debug is off. Compile regex Pattern objects once as constants. Reuse thread-safe heavy objects (ObjectMapper, HttpClient, DateTimeFormatter). Pre-size collections and StringBuilder. Use try-with-resources to close things on time. Use primitives and primitive streams on hot paths. Bound every cache, queue and map, with an eviction policy. Prefer streaming over reading everything. Avoid holding references longer than needed (set big local variables out of scope by putting them in smaller methods). Avoid finalize, String.intern in unbounded cases, and exceptions for flow control in hot loops (filling a stack trace is costly). Do not call System.gc(). None of this replaces a proper heap size and collector choice, but together they often reduce GC time by half.

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview; it shows you work calmly under pressure.

The pod is OOMKilled (exit code 137) again and again, but the heap graph never reaches the limit. What is going on? Senior

What the interviewer is testing: knowing the process is bigger than the heap and how the container is killed.

Situation: Kubernetes reports OOMKilled. The application logs show no OutOfMemoryError, because the kernel killed the process with SIGKILL, not the JVM. Heap max is 1.5 GB and the limit is 2 GB.

Check first: the JVM flags in use (jcmd PID VM.command_line) and the container working set from metrics (container_memory_working_set_bytes) compared with the heap used. If the heap is, say, 1.3 GB and the working set 2 GB, then 700 MB is outside the heap. Look at what that is.

Steps:

  1. Enable -XX:NativeMemoryTracking=summary in a test or canary and run jcmd PID VM.native_memory summary: check Thread, Class, Code, GC, Internal and Other.
  2. Count threads (jcmd PID Thread.print | grep -c '^"'); 600 threads at 1 MB is 600 MB.
  3. Check direct buffers through the JMX BufferPool beans, and metaspace with jstat -gc.
  4. If NMT shows nothing large but RSS keeps growing, suspect native allocation fragmentation: try MALLOC_ARENA_MAX=2 or jemalloc.
  5. Fix the budget: lower MaxRAMPercentage to 65 to 70, cap MaxMetaspaceSize and MaxDirectMemorySize, bound thread pools, and raise the memory limit if the app truly needs more.

Prevent: load test in a container with the production limit, alert on working-set percentage not just heap, and keep a documented memory budget per service.

Likely follow-ups
  • Why no heap dump? The kernel killed the JVM instantly. You must reproduce or watch the memory before the kill.
Users report random freezes of 2 to 5 seconds in production. How do you investigate the GC? Senior

What the interviewer is testing: a methodical way from symptom to cause, including causes that are not GC itself.

Situation: latency spikes of seconds, a couple of times an hour, on a G1 service with an 8 GB heap.

Check first: do the freezes match GC log entries? Make sure GC logging is on (-Xlog:gc*); if not, enable it and wait. Search for pauses over 1 second, then read the lines around them.

Steps:

  1. If you see Pause Full (Allocation Failure) or (Metadata GC Threshold): the old gen or metaspace filled. Look at "heap after": leak or undersized heap. See the leak flow.
  2. If you see To-space exhausted or humongous allocations: add heap, reduce big allocations, or adjust region size and IHOP.
  3. If the log says a young pause took 3 s with sys time high: the machine is swapping or the container is CPU throttled; check vmstat and throttle metrics. The JVM must never be swapped.
  4. If no long GC pause at all, look for long safepoints (-Xlog:safepoint), thread stalls on a lock, a slow downstream, or a stop in a native call. A pause of "real" time in the log without GC work points to the environment.
  5. Apply one change (more heap, better pause goal, move to ZGC if the target is under 100 ms) and compare p99 latency under a load test.

Prevent: keep GC logs always on, alert on full GCs and on pause over the SLO, and set a heap dump on OOM.

After each deployment the new pods are very slow for a few minutes, then fine. Old pods are fast. What is happening and what do you do? Intermediate

What the interviewer is testing: warm-up awareness and deploy-time traffic handling.

Situation: on a rolling update the latency p99 and error rate jump for 2 to 5 minutes, then settle. CPU is high on the new pods at the start.

Check first: compare CPU and latency of new and old pods. A high CPU early that drops later with JIT compiler threads busy (top -H) is the warm-up signature. Check CPU throttling, since a tight CPU limit stretches warm-up. Check cold caches and connection pools as well.

Steps:

  1. Add a warm-up phase before the pod becomes ready: call the main endpoints with synthetic requests (including error paths), then flip readiness.
  2. Use gradual traffic ramp (slow-start in the load balancer or service mesh, or a canary release) so new pods do not take a full share at once.
  3. Give more CPU at startup (higher limit or startup boost), so the JIT can compile quickly.
  4. Speed class loading with AppCDS, trim startup work (lazy beans), and on newer JDKs consider the AOT cache from Project Leyden or CRaC.
  5. Pre-open database connections and pre-load caches in the warm-up.

Prevent: make the warm-up part of the standard service template, and test deploys under load in staging.

Heap grows slowly until the service dies after about 3 days, and the heap dump shows many instances of a request context class. How do you find the cause? Senior

What the interviewer is testing: end-to-end leak diagnosis and the ThreadLocal trap.

Situation: heap after GC rises 100 MB a day. Restart fixes it temporarily. No code change correlates.

Check first: the class histogram twice, an hour apart, to find which class grows, then a heap dump from one drained pod.

Steps:

  1. Open the dump in MAT, run Leak Suspects, and look at the dominator tree. Here, a few hundred Thread objects (the pool) retain hundreds of MB.
  2. Take "path to GC roots" for a context object: Thread → threadLocals → ThreadLocalMap → Entry → value. That is a ThreadLocal set per request and never cleared, on threads that live forever.
  3. Find the code: a filter or interceptor calls CONTEXT.set(ctx) but the cleanup is skipped when an exception is thrown.
  4. Fix: wrap in try { ... } finally { CONTEXT.remove(); }. Consider newer scoped alternatives (ScopedValue in recent Java) or passing context explicitly.
  5. Deploy and watch the "after GC" floor stay flat.
CONTEXT.set(ctx);
try {
    chain.doFilter(req, res);
} finally {
    CONTEXT.remove();     // without this, pooled threads keep the value forever
}

Prevent: code review rule for any ThreadLocal, a test that runs requests twice on one thread and asserts it is clean, and an alert on rising heap-after-GC.

An in-memory cache was added to speed up a lookup and a week later the service has OutOfMemoryError. What went wrong and how do you fix it? Intermediate

What the interviewer is testing: unbounded caches are the number one leak.

Situation: a static Map<String, Result> stores each computed result by key. Keys include user ids and search text, so the key space is huge and nothing is ever evicted.

Check first: class histogram shows HashMap$Node and Result counts rising. MAT shows the static field as the GC root path.

Steps: replace the raw map with a real cache that has a maximum size and expiry (Caffeine: maximumSize, expireAfterWrite), and optionally recordStats() to watch hit rate. Check that keys are small and well-defined with correct equals/hashCode. If entries are big, bound by weight, not by count. Do not use SoftReference as the main strategy, since its behaviour depends on the GC. For multiple instances consider an external cache (Redis) to avoid N copies, see Redis and caching.

Prevent: a rule that every cache has a size bound, a TTL and a metric.

A desktop-style or event-driven component keeps growing in memory; each new session registers a listener on a shared event bus. What do you do? Intermediate

What the interviewer is testing: the "lapsed listener" leak pattern.

Situation: a long-lived singleton EventBus holds a list of subscribers. Each user session creates an object that subscribes, but when the session ends the object is just dropped, never unsubscribed. The bus keeps a strong reference, so every ended session stays in memory with everything it references.

Check first: in the heap dump, find the subscriber class count (thousands), and the path to roots goes through the bus's list.

Steps: unsubscribe in the lifecycle end (close(), @PreDestroy, session-destroyed callback); make subscribers AutoCloseable and use try-with-resources where scope is local; or let the bus hold weak references to listeners (be careful: the listener then disappears if nothing else holds it, so the owner must keep it). Watch for lambdas and inner classes that capture this and therefore keep the whole outer object alive. Add a test that creates and destroys many sessions and asserts the subscriber count returns to zero.

Prevent: make "who removes this?" a code review question for every add or register call.

After a few hot redeploys on Tomcat, the app server throws OutOfMemoryError: Metaspace. How do you handle it? Senior

What the interviewer is testing: class loader leak diagnosis.

Situation: every redeploy leaves the previous web app's class loader in memory. After 5 or 6 redeploys metaspace is full.

Check first: jcmd PID VM.classloader_stats and jstat -class show more and more loaders and classes that never drop. Take a heap dump after two redeploys and in MAT look for several instances of the web app class loader (WebappClassLoader), which should be one.

Steps:

  1. For each old loader take "path to GC roots": the chain reveals the culprit, such as a non-daemon thread started by the app, a ThreadLocal on a container thread, a JDBC driver registered in DriverManager, a logging or JMX registration, or a static in a library placed in the shared lib folder.
  2. Fix by shutting down threads and executors in a ServletContextListener.contextDestroyed, deregistering drivers and MBeans, clearing ThreadLocals, and moving shared libraries into the webapp.
  3. Set -XX:MaxMetaspaceSize so a leak fails fast in the test environment instead of eating the host.

Prevent: in production prefer restart-based deploys (immutable container images), which sidestep the problem; Tomcat's leak prevention listener logs warnings about known patterns, read them.

CPU is at 90% on every node, and the profile shows the JVM's GC threads as the top consumers. What do you do? Senior

What the interviewer is testing: choosing between "too much garbage", "too small a heap" and "a leak".

Situation: after a feature launch, CPU doubled with no traffic increase. top -H shows "G1 Young RemSet" and GC worker threads at the top.

Check first: GC logs and jstat -gcutil PID 1000. How often do young collections happen and how big is the heap after? Is the old generation climbing? Any Full GCs?

Steps:

  1. Young GC every few hundred ms with a flat heap-after: the allocation rate is too high. Take a JFR allocation profile (or async-profiler alloc) and find the top allocating stacks; the new feature probably copies big lists or builds strings in a loop.
  2. Heap-after climbing and frequent full GCs: a leak or heap too small. Heap dump and analysis, or temporarily raise -Xmx to buy time.
  3. Old objects with many references into young cause long RemSet work: check for a big mutable old structure with frequently updated pointers.
  4. Only after the code fix consider more heap, or switching collector.

Prevent: track allocation rate and GC time as service metrics, and compare them across releases in the canary stage.

Netty-based gateway fails with "OutOfMemoryError: Direct buffer memory" while heap usage is only 30%. What is your plan? Senior

What the interviewer is testing: off-heap thinking and reference-counted buffers.

Situation: the gateway handles large payloads. Direct memory limit (default about equal to max heap) is reached, yet the heap is calm.

Check first: JMX java.nio:type=BufferPool,name=direct (count, memory used), NMT "Other" category, and Netty's own pooled allocator metrics. Enable the Netty leak detector (-Dio.netty.leakDetection.level=advanced) in a test environment.

Steps:

  1. Is it a true leak (usage rises and never falls) or a spike (many big concurrent payloads)? A flat plateau at the limit with traffic means the limit is too low; a staircase that never drops means a leak.
  2. For a leak: find unreleased ByteBufs (missing ReferenceCountUtil.release in handlers, error paths that skip release). The leak detector prints the stack where the buffer was last accessed.
  3. For a spike: bound request body size, apply back-pressure (do not read faster than you write), reduce arena sizes and cache settings of the pooled allocator.
  4. Set -XX:MaxDirectMemorySize explicitly and make sure the container limit covers it.

Prevent: load test with big payloads and slow clients; alert on the direct buffer pool size.

Production throws "unable to create native thread" under a traffic spike. Heap is fine. What do you do? Senior

What the interviewer is testing: thread explosion and the difference between heap and thread limits.

Situation: a downstream service slowed. Requests piled up, and the app created more and more threads (an unbounded cached thread pool and blocking calls) until the OS refused.

Check first: a thread dump from a surviving instance, grouped by name; the container pid limit; ulimit -u.

Steps: identify the pool with thousands of threads (all waiting on the slow call). Replace the unbounded pool with a bounded one plus a bounded queue and a rejection policy, add timeouts and circuit breakers on the downstream call so threads do not wait forever, apply back-pressure, and consider virtual threads (Java 21) if the work is mostly blocking I/O. As a stop-gap lower -Xss or raise the pid limit; do not raise heap, since that takes memory away from thread stacks.

Prevent: name pools, monitor live thread count, set timeouts on every remote call, and test with a deliberately slow dependency.

A nightly batch job fails with Java heap space after the data grew. The team wants to raise -Xmx to 32 GB. What do you say? Intermediate

What the interviewer is testing: fixing the shape of the work instead of buying memory.

Situation: the job loads all records into a list, transforms, then writes. It worked with 2 million rows and now fails with 20 million.

Check first: the heap dump from HeapDumpOnOutOfMemoryError and which collection dominates; and the shape of memory use over time. Memory that grows with input size is a design problem.

Steps: process in chunks or streams: read, transform, write a page at a time (JDBC fetch size or cursors, Spring Batch chunk-oriented steps, Files.lines); keep only aggregates in memory; avoid duplicating data (copying lists, string concatenation of big text); use compact types (primitive arrays or fastutil) when you really need big in-memory structures. Raising -Xmx is a temporary measure: it moves the cliff, makes full GCs longer, and breaks again at 40 million rows. Also check the 32 GB limit effect: above about 32 GB compressed oops are lost.

Prevent: test batch jobs with production-sized data, and make memory use independent of input size.

A production request fails with StackOverflowError only for certain customers. How do you debug it? Intermediate

What the interviewer is testing: reading a repeating stack trace to a cycle in data.

Situation: logs show a trace with thousands of lines, repeating Customer.toString, Account.toString, Customer.toString. Only customers with linked accounts fail.

Check first: the repeating section of the trace: the same 2 to 4 frames repeat. That is the cycle. Which entities or methods call each other?

Steps: find the cycle in the data model (two-way relationship parent to child and back, a JSON serializer that follows both). Break it: exclude the back reference from toString/hashCode/equals, use @JsonIgnore or @JsonManagedReference/@JsonBackReference, or map to DTOs. Add a regression test with a cyclic sample. Do not simply raise -Xss: a true cycle never ends. Make sure the log keeps the top and bottom of the trace (some frameworks truncate it at 1024 frames, see -XX:MaxJavaStackTraceDepth).

Prevent: avoid entities in log statements, use DTOs at boundaries, and use Lombok exclusions carefully.

After a traffic spike the service enters a loop of full GCs and never recovers until restarted. What happened and how do you prevent it? Senior

What the interviewer is testing: how a small shortage turns into a death spiral, and how to fail fast.

Situation: the spike raised the live set (more concurrent requests, queues filled). The old gen was nearly full, so GC runs often and frees little. Requests slow down, queues grow, more memory is held, so GC runs even more. The service is alive for health checks but useless.

Check first: GC log: full GCs back to back with the "after" number near the max. A thread dump shows request threads waiting. Queue sizes and connection counts are high.

Steps: immediate: restart or shift traffic to healthy instances. Root cause: the live set at peak does not fit. Right-size the heap using the peak live set; bound request concurrency and queue length (reject with 503 early); add load shedding and timeouts; make requests cheaper in memory. Operational safety nets: -XX:+ExitOnOutOfMemoryError so an OOME ends the process, a liveness probe that checks real work and not just that the port is open, and an alert for "GC time over 30% for 5 minutes". Do not enable -XX:-UseGCOverheadLimit to hide it.

Prevent: load test beyond expected peak, apply back-pressure, autoscale before memory saturates.

A service has fine latency on a developer machine but is poor in a 1-CPU container, and the GC log says "Using Serial". Why? Intermediate

What the interviewer is testing: JVM ergonomics in containers.

Situation: the same jar, same flags. On the laptop the log says "Using G1", in Kubernetes it says "Using Serial", and young pauses are longer.

Check first: the log line at startup (-Xlog:gc+init) and the resource limits. The JVM picks Serial when it sees fewer than 2 available processors or under about 1.8 GB of memory. A CPU limit of 1000m or a memory limit of 1 GB triggers it.

Steps: decide if Serial is actually fine (for a small heap it often is: the lowest overhead). If you need G1 for pauses, either give the pod at least 2 CPUs and 2 GB or force it with -XX:+UseG1GC; remember a CPU quota of 1 core still limits how fast G1's parallel threads can run. Also fix the dev-prod gap by testing in containers with the production limits. Check Runtime.getRuntime().availableProcessors() in the app logs on startup, and mind that the common fork-join pool and parallel streams size themselves from it.

Prevent: print effective JVM settings at startup (-XX:+PrintFlagsFinal in a debug mode or a startup log line).

After a dependency upgrade, a service throws NoClassDefFoundError and NoSuchMethodError in production, but all unit tests pass. What do you check? Intermediate

What the interviewer is testing: class path conflicts and how to find them.

Situation: the upgraded library A needs version 2 of library B, but another dependency brings version 1, and the build picked version 1 on the class path (or in the fat jar the order differs from the test class path).

Check first: the first stack trace for the first failure; if it says Could not initialize class, look further back in the logs for the original error. Then run mvn dependency:tree -Dverbose or gradle dependencyInsight --dependency B.

Steps: find the jar that actually supplies the class at runtime with -verbose:class or -Xlog:class+load (it prints the jar for each loaded class), or SomeClass.class.getProtectionDomain().getCodeSource(). Align versions with dependency management (a BOM or constraints), exclude the old transitive one, and check shaded or duplicate jars in the fat jar. Add a CI check such as the Maven enforcer dependencyConvergence rule or Gradle's strict version constraints. Make integration tests run against the packaged artifact.

Prevent: convergence rules in CI and a smoke test of the final image.

You need a heap dump from a 24 GB production heap, but taking it freezes the pod and the liveness probe kills it. What do you do? Senior

What the interviewer is testing: operational judgement about diagnostics.

Situation: the leak is suspected, and the dump takes about a minute of stop-the-world and 24 GB of disk. The liveness probe fails during the freeze.

Check first: can you get the answer cheaper? A GC.class_histogram twice already points at the growing class, and a JFR recording with OldObjectSample can show the allocation stack and the root path with 1 to 2% overhead.

Steps:

  1. Try the cheap tools first: histogram diff, JFR with jdk.OldObjectSample#cutoff=infinity for hours.
  2. If a dump is needed: remove one pod from the load balancer, disable or lengthen its liveness probe (or exec from within with the probe paused), confirm disk space (a bit above heap size) on a writable volume, then jcmd PID GC.heap_dump /dumps/h.hprof (add -all only if you want unreachable objects too).
  3. Compress and copy it out securely; it contains secrets. Analyse with MAT on a machine with a heap setting larger than the dump (MAT headless parsing for large files).
  4. Or reproduce on a smaller heap in staging with the same traffic pattern and dump there.

Prevent: rely on HeapDumpOnOutOfMemoryError with a mounted volume, and keep a runbook that says how to take a dump safely.

Latency is great for hours, but the first request after a rare event (an unusual input) is 50 times slower, then normal. Why might that happen in the JVM? Senior

What the interviewer is testing: JIT deoptimisation and lazy class loading as hidden latency sources.

Situation: a code path that ran only a few times a day is slow when first triggered.

Check first: things the JVM does lazily: class loading and initialisation (first use of an error-handling class, a locale, a charset, a regex engine, a big static initialiser), deoptimisation (the optimised hot path assumed that branch never happens; it hits the trap, drops to the interpreter, then recompiles), and cold caches in the application. Use JFR compilation and class-load events, or -Xlog:class+load and -XX:+PrintCompilation ("made not entrant") to see what happened at the time of the slow request.

Steps: include these rare paths in the warm-up (error cases, unusual inputs); preload classes at startup (Class.forName); avoid heavy static initialisers on rare paths; keep representative traffic at all times for important paths. If the slowness is a GC-related stall, the GC log will show the pause at the same timestamp.

Prevent: chaos or "rare path" tests in the pre-production warm-up.

You upgrade from Java 8 to Java 17 and see higher memory use and different GC behaviour. What do you check? Senior

What the interviewer is testing: migration awareness: defaults changed and old flags no longer apply.

Situation: same traffic, but RSS is higher, and pauses look different.

Check first: the effective flags on both (java -XX:+PrintFlagsFinal -version or jcmd VM.flags). Key differences: the default GC moved from Parallel to G1, which uses more native memory for remembered sets and background threads; the heap default in containers now follows the cgroup; PermGen flags (-XX:MaxPermSize) are ignored with a warning; CMS flags make the JVM start with warnings or fail; the GC logging flags (-XX:+PrintGCDetails) no longer exist and must be replaced by -Xlog; strong encapsulation breaks libraries that reflect into JDK internals.

Steps: remove all obsolete flags and start from a clean baseline; pick the collector deliberately (stay on Parallel if it was a batch job, or tune G1 as above); re-size the container for the new native footprint (often 10 to 20% more); update libraries to versions that support 17 (Lombok, ByteBuddy, Spring and others); then load test, comparing p99 latency, throughput and memory against the old build.

Prevent: keep the flags in version control with a comment about each, and review them at every JDK upgrade.
