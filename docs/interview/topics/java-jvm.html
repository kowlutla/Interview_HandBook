How a Java program really runs, where its memory goes, how garbage collection works, how to pick a collector, and how to debug leaks, OutOfMemoryError, slow starts and container kills. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

This page covers the runtime side of Java. For language basics see Java fundamentals, for threads and the memory model Java concurrency, and for newer language features Modern Java.

Version notes. Long-term-support (LTS) releases are 8, 11, 17, 21 and 25. The default collector is Parallel GC in Java 8 and G1 from Java 9 on (when the JVM sees at least 2 CPUs and about 1.8 GB of memory, otherwise Serial). Metaspace replaced PermGen in Java 8. CMS was removed in Java 14. ZGC became production-ready in 15, and its generational mode arrived in 21. Details of flags can change between versions, so check java -XX:+PrintFlagsFinal on your own JDK.

Mental model: the 8 ideas everything hangs on

One line: your code is compiled to portable bytecode, loaded by class loaders, run first by an interpreter and then by a JIT compiler, and every object lives on a garbage-collected heap that the JVM cleans by finding what is still reachable.
  1. Write once, run on a JVM. javac turns source into bytecode in .class files. The JVM, not the CPU, runs bytecode.
  2. Classes load lazily. A class loader finds the bytes, the JVM verifies them, and static initializers run only on first use.
  3. Memory is split by purpose. Heap (objects, shared), thread stacks (method calls, one per thread), metaspace (class metadata, native), plus code cache and direct buffers. The heap is only part of what the process uses.
  4. Garbage means unreachable. The collector asks "can I still reach it from a root?" (thread stacks, static fields), never "will the code use it?". So a forgotten reference is a leak.
  5. Most objects die young. The heap has a small young area collected often and cheaply, and a large old area collected rarely.
  6. Every collector trades three things: throughput, pause time and memory footprint. You cannot maximise all three.
  7. The JIT makes Java fast after warm-up. Hot methods become machine code using runtime knowledge. The first minutes are slower.
  8. In a container the process budget is bigger than the heap. The limit must also cover metaspace, stacks, code cache and direct memory.

1. Platform and startup

What is the difference between the JDK, the JRE and the JVM? Basic

The JVM is the engine that runs bytecode. The JRE is the JVM plus the standard class library, which is what you need to run a program. The JDK is the JRE plus developer tools like javac, jar, jcmd and jfr, which you need to build and diagnose one.

Bytecode is the portable instruction set that javac produces in .class files. The same jar runs on any OS because each OS has its own JVM that understands bytecode. Since Java 11 Oracle and OpenJDK no longer ship a separate JRE download; you either install a JDK or build a trimmed runtime with jlink. In production images I still want a JDK (or at least jcmd), because without it I cannot take a thread dump or heap dump from a running process.

Why three names exist. Java promises "write once, run anywhere". To keep that promise, the thing that actually runs your program cannot be the CPU or the OS. It has to be a middle layer that is built separately for each OS, and that layer is the JVM (Java Virtual Machine). It reads bytecode (a compact, CPU-independent instruction set) and either interprets it or compiles it to machine code on the fly. A JVM alone is not enough to run System.out.println, because that call lives in the standard library (String, collections, I/O, networking). The JVM plus that library is the JRE (Java Runtime Environment). The compiler and the tools you use while building and debugging come on top: that is the JDK (Java Development Kit).

A tiny example of the split. You write Hello.java. javac Hello.java (a JDK tool) produces Hello.class. java Hello starts a JVM which loads that class. You can look at the bytecode with javap -c Hello:

// Hello.java
public class Hello { public static void main(String[] a) { System.out.println("hi"); } }

$ javap -c Hello
  public static void main(java.lang.String[]);

    ldc           #13  // String hi
    invokevirtual #15  // PrintStream.println
    return

Those four instructions are what any JVM on Windows, Linux or macOS executes. The bytecode is the same everywhere; only the JVM differs per platform.

Where this shows up in practice. A common mistake is building a slim production image with only a JRE and then discovering, during an incident, that jcmd, jstack and jmap are not there. Another is mixing versions: code compiled with javac from Java 21 will not run on a Java 17 JVM (UnsupportedClassVersionError) unless you compile with --release 17. And because there is no separate JRE download any more, "JRE" now mostly means "a runtime image you build yourself with jlink", which can be tens of MB instead of a full JDK.

Remember: JDK = JRE + tools, JRE = JVM + libraries. JVM runs bytecode, javac makes it.

What happens when you run java Main? Walk me through it. Intermediate

The launcher starts a JVM process, which sets up the heap and other memory areas, loads core classes, then uses a class loader to find Main. The class is loaded, verified and initialized, and the JVM calls main. The method first runs in the interpreter, and the JIT compiler turns it into machine code once it proves hot.

Class loading is lazy: other classes are loaded the first time code touches them, not at startup. The garbage collector threads and JIT compiler threads start with the JVM, in the background. That is why a Java program starts slowly and then speeds up: the first calls run as slow interpreted code while the JVM profiles them. The program ends when main returns and all non-daemon threads have finished, or on System.exit.

java -cp app.jar com.acme.Main
# 1 start JVM, reserve heap  2 load Main  3 verify, init statics
# 4 run main() interpreted   5 JIT compiles hot methods

Step by step with what is actually happening.

  1. The launcher (the small native java program) parses flags, finds the JVM library and creates the JVM inside the same process. This is where -Xmx, -XX:... and the classpath are read.
  2. The JVM initialises itself. It reserves address space for the heap and metaspace, starts the GC worker threads, the JIT compiler threads and a few housekeeping threads, and loads the bootstrap classes (Object, String, Class and so on) from the runtime image.
  3. Loading Main. The application class loader searches the classpath (or module path) for com/acme/Main.class, reads the bytes and defines the class.
  4. Linking. The bytecode is verified, static fields get default values, and symbolic references are resolved lazily as they are first used.
  5. Initialization. Static initializers of Main run (and, recursively, those of anything it needs first, like its superclass).
  6. Call main(String[]) on the "main" thread. Each bytecode is first interpreted. The interpreter counts how often each method and each loop is executed.
  7. Warm-up. When a method passes a threshold (thousands of calls or loop iterations), a JIT thread compiles it to machine code in the background, and the next call uses the compiled version. Over seconds to minutes the program speeds up.
  8. Shutdown. When main returns and no non-daemon thread is left (or System.exit is called), shutdown hooks run and the JVM exits.

You can watch laziness with -verbose:class (Java 8) or -Xlog:class+load (Java 9+). A "hello world" typically loads several hundred JDK classes before your own code even runs, and a Spring Boot app loads many thousands. That is a big part of why Java startup is measured in hundreds of milliseconds to seconds, and why techniques like class data sharing (CDS), AOT caches and native image exist.

$ java -Xlog:class+load:file=load.log Main
$ head -3 load.log
[0.012s][info][class,load] java.lang.Object source: shared objects file
[0.012s][info][class,load] java.io.Serializable source: shared objects file
...
[0.095s][info][class,load] com.acme.Main source: file:/app/app.jar

"source: shared objects file" means the class came from the CDS archive, which maps pre-parsed core classes straight from disk and is why plain startup is not even slower. A frequent follow-up: "what if a non-daemon thread is still running when main ends?" The JVM keeps running until that thread finishes; that is why a forgotten thread pool stops a program from exiting.

Remember: start JVM, load classes lazily, interpret first, JIT the hot parts. The JVM exits when the last non-daemon thread ends.

Which garbage collector is the default in each Java version? Intermediate

Java 8 defaults to Parallel GC. From Java 9 onwards the default is G1, but only if the JVM sees at least 2 CPUs and about 1.8 GB of memory. On a smaller machine or container it silently falls back to Serial GC.

This matters because a tiny pod (1 CPU, 1 GB) quietly gets the single-threaded Serial collector with no warning, and teams then wonder why GC behaves differently than on their laptop. The GC log first line shows which collector is really in use: Using G1 or Using Serial. For the LTS releases: 8 (Parallel), 11 and 17 (G1, with CMS removed in 14), 21 (G1, with generational ZGC available), 25 (G1; ZGC is generational only). I always set the collector explicitly in production so it never depends on the machine size.

Why the "server-class machine" rule exists. G1 uses several parallel and concurrent threads plus extra bookkeeping memory. On a machine with fewer than 2 CPUs or under roughly 1792 MB of memory, that overhead is not worth it, so the JVM treats the machine as "not server class" and picks Serial. The same check applies to a container, using the limits the JVM sees (it is container-aware since Java 8u191 and 10). So a pod with cpu: 1 and a 1 GB limit runs Serial even on Java 21.

How to check what you really got. Do not guess, ask the JVM:

$ java -Xlog:gc -version 2>&1 | head -3
[0.004s][info][gc] Using G1

$ java -XX:+PrintFlagsFinal -version | grep -E "Use(Serial|Parallel|G1|Z|Shenandoah)GC"
     bool UseG1GC        = true   {product} {ergonomic}
     bool UseSerialGC    = false  {product} {default}

The word {ergonomic} means the JVM chose the value itself based on the machine, {default} is the built-in value, and {command line} is what you set. In an incident review this is useful: "GC pauses are different in prod than staging" is very often "staging got G1, the small prod pod got Serial".

What to say about choosing. Treat the default as a starting point, not a decision. For a service I would pin -XX:+UseG1GC (or whichever I chose) and give the pod at least 2 CPUs so GC threads have room. A related trap: setting a CPU limit lower than the CPU count can also make the JVM size GC thread pools by the limit, so GC work is squeezed and pauses stretch.

Remember: Parallel in 8, G1 from 9, but Serial on a machine under 2 CPUs or about 1.8 GB. Pin it with a flag.

2. Class loading

What is a class loader, and what are the built-in ones? Basic

A class loader finds the bytes of a class by name and turns them into a Class object in the JVM. There are three built in: the bootstrap loader for core JDK classes, the platform loader for other JDK modules, and the application loader for my classpath.

The bootstrap loader is written in native code, so String.class.getClassLoader() returns null. Before Java 9 the middle one was called the extension loader. A class's identity in the JVM is its name plus the loader that defined it. The same class file loaded by two different loaders gives two unrelated types, and casting between them fails with ClassCastException. App servers, plugin systems and frameworks use this on purpose to isolate applications.

What a class loader actually does. You write new Order(). The JVM needs the Class object for com.acme.Order. It asks the current class's loader: "give me com.acme.Order". The loader finds the bytes (from a jar, a directory, the network, even generated in memory), calls defineClass, and returns the Class. The JVM caches the result per loader, so the second request is instant.

System.out.println(Main.class.getClassLoader());            // app loader (jdk.internal...ClassLoaders$AppClassLoader)

Why identity includes the loader (a worked example). Suppose a servlet container loads com.acme.Plugin from pluginA.jar with loader L1 and again with loader L2. You now have two classes both named com.acme.Plugin. An object created from L1's class is not an instance of L2's class:

Object o = l1.loadClass("com.acme.Plugin").getDeclaredConstructor().newInstance();
Plugin p = (Plugin) o;  // ClassCastException: com.acme.Plugin cannot be cast to com.acme.Plugin

That confusing message (same name on both sides) is the classic sign of two loaders. It is also the mechanism behind isolation: two webapps in one Tomcat can use different versions of the same library without clashing, because each gets its own loader. The price is memory (every class exists once per loader) and the class loader leak problem covered below.

Custom loaders are written by extending ClassLoader and overriding findClass (not loadClass, which holds the delegation logic). Frameworks use them for plugins, hot reload, OSGi, and for generating classes at runtime (proxies, bytecode libraries).

Remember: bootstrap, platform, application, then custom. Class identity = name + loader.

Explain the parent delegation model. Why does it exist? Intermediate

Before a loader loads a class itself, it asks its parent to try first, all the way up to bootstrap. Only if every parent fails does the child load it. This guarantees that core classes like java.lang.String always come from the JDK, so nobody can slip in a fake one by putting it on the classpath.

It also avoids loading the same class twice, since a shared parent loads it once for everyone below. The cost is that a parent can never see classes only a child knows about. That is the reason for the context class loader, which libraries like JNDI or JDBC use to look down at application classes. Web containers such as Tomcat deliberately break the rule: a webapp loader looks in its own WEB-INF/lib first, so each app can ship its own library versions.

The algorithm in code form. This is essentially what ClassLoader.loadClass does:

protected Class<?> loadClass(String name, boolean resolve) {
    Class<?> c = findLoadedClass(name);        // 1. already loaded by me?
    if (c == null) {
        try {
            if (parent != null) c = parent.loadClass(name, false);  // 2. ask parent first
            else                c = findBootstrapClassOrNull(name);
        } catch (ClassNotFoundException e) { /* parent could not */ }
        if (c == null) c = findClass(name);      // 3. only now try myself
    }
    return c;
}

Walk-through with two requests. Request 1: the app code asks for java.lang.String. The app loader asks the platform loader, which asks bootstrap, which has it. Done: the JDK's String is returned. Even if a malicious jar on your classpath contains its own java/lang/String.class, it is never reached (and the JVM additionally forbids user loaders from defining java.* classes, with a SecurityException). Request 2: com.acme.Order. Bootstrap and platform say "not found", so the app loader reads it from the classpath.

Why this design. Three reasons. Security: core types cannot be replaced. Consistency: java.util.List means the same type everywhere, so a List passed between libraries is really the same class. Efficiency: shared classes load once.

The "parent cannot see child" problem and how it is solved. The JDK's JDBC DriverManager is loaded by a parent loader, but the driver you want (say a PostgreSQL jar) lives in the application loader below it. The parent cannot ask downwards. The workaround is the thread context class loader (Thread.currentThread().getContextClassLoader()): the framework sets it to the app loader, and library code in the parent uses it to look downwards. ServiceLoader works this way.

Where the rule is deliberately broken. Tomcat's webapp loader checks its own WEB-INF/classes and WEB-INF/lib first for most packages (but still delegates java.*). OSGi and the Java module system use richer graphs instead of a strict parent chain. If an interviewer asks "what goes wrong if two jars have the same class?", the answer is: the first one found on the classpath order wins, silently, which can cause NoSuchMethodError when versions differ (a classic "jar hell").

Remember: ask the parent first. It protects core classes and loads shared classes once. Web containers reverse it for webapps.

What are the phases of loading a class: loading, linking and initialization? Intermediate

Loading reads the class bytes and creates the Class object. Linking has three steps: verify the bytecode is safe, prepare static fields with default values (0, null), and resolve references. Initialization then runs static initializers and sets static fields to their real values, and it happens only on first active use.

First active use means new, calling a static method, reading a non-constant static field, or Class.forName. Using a static final compile-time constant does not trigger it, because the value is inlined at compile time. Initialization is thread-safe: the JVM holds a lock per class, so a static initializer runs exactly once. If it throws, the class is marked broken, and later uses throw NoClassDefFoundError: Could not initialize class. Two threads whose static initializers wait on each other's class can deadlock.

A small example you can run in your head. The order of output shows when initialization really happens:

class Config {
    static final int MAX = 10;                  // compile-time constant, inlined
    static final long START = System.nanoTime(); // not a constant: needs init
    static { System.out.println("Config init"); }
}
public class Main {
    public static void main(String[] args) {
        System.out.println(Config.MAX);    // prints 10, "Config init" NOT printed
        System.out.println("before");
        System.out.println(Config.START);  // now prints "Config init", then the value
    }
}
// Output:  10 / before / Config init / 123456789...

What each phase does, with the field example. Take static int count = 5;.

  • Loading: read Config.class, build the in-memory class structure in metaspace, create the java.lang.Class object on the heap.
  • Verification: check the bytecode obeys the rules (valid stack operations, no jumping into the middle of an instruction, types match). This stops a hand-crafted class file from corrupting the JVM. Classes loaded by the bootstrap loader can skip some of it, which is partly why -Xverify:none was once a startup hack (now deprecated).
  • Preparation: allocate the static storage and set count = 0. The value 5 is not there yet.
  • Resolution: turn symbolic names like "method Foo.bar" into direct references. HotSpot usually does this lazily the first time an instruction needs it.
  • Initialization: run the class initializer (<clinit>), which holds all static assignments and static blocks in source order. Now count = 5. The superclass is initialized first, interfaces only if they declare default methods.

Why lazy, thread-safe initialization is useful. The JVM guarantees that <clinit> runs once and that other threads wait until it finishes. That is exactly why the "initialization-on-demand holder" singleton is correct without any synchronized: the static nested class is only initialized on first call to getInstance().

class Singleton {
    private Singleton() {}
    private static class Holder { static final Singleton I = new Singleton(); }
    static Singleton get() { return Holder.I; }   // Holder initialized here, once, thread-safely
}

Pitfall. If a static initializer throws, the first use gets ExceptionInInitializerError (with the real cause), and every later use gets NoClassDefFoundError: Could not initialize class ... with no stack trace of the original problem. So when you see the second form, search the logs backwards for the first one. Also avoid static initializers that depend on each other's classes in a cycle across threads: two threads each holding one class's init lock and wanting the other's is a real class-init deadlock.

Remember: load, link (verify, prepare, resolve), then initialize lazily and once. A failed initializer poisons the class.

ClassNotFoundException versus NoClassDefFoundError: what is the difference and how do you debug each? Intermediate

ClassNotFoundException is a checked exception thrown when code asks for a class by name at runtime, for example Class.forName("x.Y"), and the loader cannot find it. NoClassDefFoundError is an error: the class was there when the code was compiled, but the JVM cannot find or initialize it now. The first is a "wrong name or classpath" problem. The second is usually a packaging, version or static-initializer problem.

For ClassNotFoundException I check the class name, the classpath and, for plugin or reflection code, which loader is being used. For NoClassDefFoundError I look at the message. If it says Could not initialize class X, an earlier static initializer of X failed, so I find that first exception higher in the logs. Otherwise the jar is missing at runtime, often a dependency that was provided or optional at build time, or two versions of a library on the classpath. mvn dependency:tree and -verbose:class show what really loaded.

Three concrete scenarios, one for each message.

  1. ClassNotFoundException. Class.forName("com.mysql.cj.jdbc.Driver") fails because the driver jar is not on the classpath. The class name is just a string, so the compiler could not check it. The JVM looked, found nothing, and threw a checked exception your code was forced to handle. Same family: ClassLoader.loadClass, reflection by name, Spring bean definitions by class name, ServiceLoader entries.
  2. NoClassDefFoundError, jar missing at runtime. You compiled new Helper() against helper.jar, but the deployed fat jar or container image does not contain it (for instance Maven scope provided, or an excluded transitive dependency). The first use of Helper throws NoClassDefFoundError: com/acme/Helper. Notice the slash-style name in the message: a hint that it came from the JVM linking code, not from a string you passed.
  3. NoClassDefFoundError, failed initializer. The class file is there, but its static block threw once. The message is Could not initialize class com.acme.Config. The real error is an ExceptionInInitializerError earlier in the log.

A debugging recipe I would actually use. (1) Read the full stack trace and the "Caused by" chain. (2) Run -verbose:class or -Xlog:class+load to see whether and from where the class loaded. (3) Print the classpath the process really has (jcmd PID VM.system_properties | grep class.path) because the deployed one often differs from your IDE. (4) For version clashes use mvn dependency:tree -Dverbose or gradle dependencies and look for the same artifact at two versions. A related sibling is NoSuchMethodError: the class loaded, but it is a different version than the one compiled against.

Remember: Exception = I asked by name and it is not there. Error = it was there at compile time but is missing or broken now.

What is a class loader leak, and how does it show up on redeploys? Senior

When an app is undeployed, its class loader and every class it loaded can only be freed if nothing outside still references any of them. If something does, for example a thread, a ThreadLocal or a driver registered in a parent-loader singleton, the whole old app stays in memory. After a few hot redeploys OutOfMemoryError: Metaspace appears.

A class keeps a reference to its loader, and a loader to all its classes. So one stray reference to one class pins everything. Classic culprits: a JDBC driver registered in DriverManager (a parent-loader object) and never deregistered, a non-daemon thread started by the app, a ThreadLocal value on a pooled server thread whose class came from the webapp, and a shutdown hook. The proof is in a heap dump: count instances of the loader class (WebappClassLoader) and trace the GC root path of an old one. The fix is cleanup in the context-destroyed callback, or simply restarting the server instead of hot redeploying.

The reference chain, drawn in words. After undeploy, the server drops its own pointer to WebappClassLoader and expects it to become garbage. But the loader holds all its Class objects, and each Class holds its loader, static fields and (through static fields) possibly huge data like caches. Any live object whose class came from that loader keeps the loader alive, so any single pointer from a long-lived object into the webapp pins the whole thing:

GC root: system classloader -> java.sql.DriverManager (static list of drivers)
         -> com.acme.WebappDriver instance
         -> WebappDriver.class -> WebappClassLoader
         -> every class, static cache, and Spring context of the old app

Timeline you see in production. Each hot redeploy adds one more copy of the app's classes. Metaspace after redeploy 1: 120 MB, after 2: 240 MB, after 3: 360 MB, then java.lang.OutOfMemoryError: Metaspace (or Tomcat logs "The web application [x] created a ThreadLocal with key of type [...] but failed to remove it"; Tomcat's own leak detector prints such warnings on undeploy, which is a quick first check).

Finding it. Take a heap dump after a couple of redeploys. In Eclipse MAT, run a "histogram" filtered on the class loader class and see more than one instance of the app loader. Then use "Path to GC roots, excluding weak/soft references" on an old loader. The first non-loader object in the path (a thread, a static, a driver) is the culprit.

Typical fixes.

  • Deregister JDBC drivers and shut down executor services, timers and other threads in contextDestroyed (or @PreDestroy).
  • Always call ThreadLocal.remove() in a finally in request code.
  • Put shared drivers and libraries in the server's own lib directory (parent loader) so the webapp does not register webapp classes into it.
  • In modern container-based deployment: do not hot redeploy. Replace the whole pod or process. The leak then never accumulates.

The same pattern appears outside app servers: dynamic proxies, scripting engines, and plugin frameworks that create a loader per plugin or per tenant.

Remember: one reference into the old loader keeps the whole old app alive. Restart instead of hot redeploy.

3. Memory areas, objects and allocation

What are the JVM runtime memory areas? Basic

The heap holds all objects and is shared by all threads. Each thread has its own stack with one frame per method call. Class metadata (the structure of each loaded class) lives in metaspace, which is native memory. On top of that the process uses the code cache for JIT-compiled code, and direct buffers and other native memory.

The heap is the area I tune with -Xmx, but it is only part of the process footprint. A service with -Xmx2g can easily use 3 GB in total. That gap is the root of most container kills. Each thread stack is about 1 MB by default on 64-bit Linux (-Xss), so 500 threads cost around 500 MB outside the heap.

A walk-through: what each area holds when one line runs. Imagine a thread running process():

class Service {
    static int hits = 0;                       // static field: lives with the class (metadata area / Class object)
    void process() {
        int n = 3;                             // primitive: in this method's stack frame
        Order o = new Order("A", n);           // 'o' reference: stack frame; Order object: heap
        o.items.add("pen");                    // ArrayList and its array: heap
    }
}
  • Heap: the Order, its list, the string "pen". Shared, so another thread holding a reference to the same Order sees the same data (and so synchronization matters).
  • Thread stack: one frame per active method: its local variables, its parameters and its partial results. Calling a method pushes a frame, returning pops it. Frames are not shared with other threads.
  • Metaspace: for each loaded class, its method bytecode, constant pool, field and method descriptions. Not on the Java heap. Static field storage for hits lives in the Class mirror object on the heap (since Java 7/8); metaspace holds the description.
  • Code cache: machine code the JIT produced for hot methods like process().
  • Program counter: each thread tracks which bytecode it is executing next.
  • Direct buffers and native memory: memory from ByteBuffer.allocateDirect, NIO channels, Netty pools, JNI libraries, and the JVM's own structures (GC card tables, JIT compiler working memory).

Why it is split. Different data has different lifetimes and access patterns. Stack data dies with the method call, so it needs no GC. Heap data has unpredictable lifetime, so it needs a collector. Class metadata lives as long as the loader, so it is managed separately and moved off-heap to avoid sizing it as part of the object heap.

How to see the numbers. jcmd PID VM.native_memory summary (needs -XX:NativeMemoryTracking=summary) shows Java Heap, Class, Thread, Code, GC, Internal and more. jcmd PID GC.heap_info shows the heap parts. A common sizing mistake is a 1 GB container with -Xmx1g: it will be OOM-killed by the kernel (not a Java OutOfMemoryError) the moment non-heap memory grows.

Remember: heap shared, stacks per thread, metaspace for classes. Process memory is more than heap.

What lives on the stack and what lives on the heap? Basic

Local variables and method call frames live on the thread's stack: primitives directly, and for objects only the reference. The objects themselves are on the heap. So Order o = new Order() puts the reference o on the stack and the Order object on the heap.

The stack is private to a thread, which is why locals are naturally thread-safe, and it is freed automatically when the method returns, with no GC involved. Heap objects are shared and need the garbage collector. Fields of an object, including its primitive fields, sit inside the object on the heap. One nuance: the JIT can use escape analysis to avoid allocating an object at all if it never leaves the method, so "all objects are on the heap" is the language model, not always the machine reality.

A picture of one method call. Suppose main calls total(order):

static double total(Order order) {     // frame for total(): holds 'order' (a reference), 'sum', 'i'
    double sum = 0;                     // sum: lives in the frame
    for (int i = 0; i < order.items.size(); i++)
        sum += order.items.get(i).price;
    return sum;                         // frame popped; sum copied to the caller
}
public static void main(String[] a) {
    Order order = new Order();          // main frame: 'order' = pointer 0x7a10
    System.out.println(total(order));   // heap: the Order object at 0x7a10 and its items
}
THREAD STACK (private)              HEAP (shared)
+-----------------------+
| total(): order=0x7a10 |-----+      0x7a10: [Order header | items -> 0x7b30]
|          sum=42.5 i=3 |     |      0x7b30: [ArrayList | elementData -> ...]
+-----------------------+     |
| main():  order=0x7a10 |-----+      (two frames hold the same pointer: one object)

Both frames contain the address of the same Order. Passing order to a method copies the reference (the address), not the object. This is what "Java is pass-by-value, and for objects the value is a reference" means. A method can change the object's contents through the reference, but cannot make the caller's variable point somewhere else.

Why this matters for correctness. Locals are confined to one thread, so they need no synchronization. The object on the heap can be reached from many threads, so its fields do. A lambda capturing a local copies the value, which is why captured locals must be effectively final.

Escape analysis nuance. If the JIT proves an object never leaves the method (for example a temporary Point used for arithmetic), it can scalar-replace it: keep its fields in registers and never allocate it. So in compiled code some "new" calls cost nothing and cause no GC. Do not rely on it for correctness or design; just do not fear small short-lived objects in hot code.

Common interview probe: "Where does a static variable live, and a String literal?" Static fields are stored with the class (reachable from the class's Class object, on the heap). String literals are pooled objects on the heap.

Remember: references and primitives in locals go on the stack, objects go on the heap.

How is the heap organised into generations? Explain Eden, Survivor and Old. Intermediate

The heap is split into a young generation and an old generation, because most objects die very young. New objects are allocated in Eden. A young GC copies the survivors into one of two small Survivor spaces, and objects that survive enough rounds are promoted to the old generation, which is collected rarely.

The idea is cost: a young collection only touches live objects, and most of Eden is already dead, so it is fast. Each survivor of a young GC gets its age incremented. When the age reaches a threshold (up to 15, adjusted by the JVM), or when the survivor space is too full, the object is promoted. Old-generation collections are more expensive, so I want only long-lived data to end up there. Note that G1, ZGC and Shenandoah split the heap into many regions instead of fixed contiguous areas, but they still keep the young and old idea.

A numbered walk-through with sizes. Say Eden is 80 MB, each Survivor is 10 MB, the app allocates 40 MB per second, and the tenuring threshold is 3.

  1. Eden fills in about 2 seconds. A young GC starts (stop-the-world, but short).
  2. The collector marks live objects starting from roots (stacks, statics, and old objects pointing into young, found through a card table that remembers old-to-young pointers so old does not have to be scanned). Say 6 MB are live.
  3. Those 6 MB are copied from Eden into Survivor S0 with age 1. Eden is then wiped in one step. Cost was proportional to 6 MB, not 80 MB.
  4. Next young GC: live objects from Eden (5 MB) and from S0 (4 MB still alive) are copied into S1; the S0 ones become age 2, the new ones age 1. S0 is now empty and the two survivor spaces swap roles.
  5. After surviving 3 collections (age exceeds the threshold) an object is promoted to Old. Also, if a survivor space would overflow (the "survivor overflow" case) extra objects go straight to Old.

The -Xlog:gc+age=trace table is the best way to see how much data survives per age, and whether the dynamic threshold is dropping (a threshold falling to 1 means survivor space is overloaded and objects are promoted early).

Key flags (Parallel/Serial naming; G1 sizes things itself). -Xmn or -XX:NewRatio (old:young ratio, default 2 meaning young is a third of heap), -XX:SurvivorRatio (Eden to each survivor, default 8), -XX:MaxTenuringThreshold (default 15 for Parallel, with an adaptive lower value in practice). Rule: do not hand-tune these with G1, ZGC or Shenandoah; they size and age by themselves.

Why two survivor spaces? Copying needs an empty target, so one is always the empty "to" space and the other the "from" space. This also keeps survivors compact with no fragmentation.

Remember: allocate in Eden, copy survivors, promote the old ones. Keep short-lived garbage out of Old.

What happened to PermGen, and what is Metaspace? Intermediate

PermGen was a fixed-size area inside the heap that held class metadata and was a common source of OutOfMemoryError. Java 8 removed it. Metaspace replaces it, stores the same class metadata in native memory, and grows on demand by default, up to the OS or container limit.

Because it is not capped by default, a class-loader leak or heavy runtime class generation (proxies, scripting) no longer fails fast: it quietly eats native memory until the container is killed. So I set -XX:MaxMetaspaceSize (for example 256m) to get a clear OutOfMemoryError: Metaspace instead. Interned strings and static fields moved to the normal heap already in Java 7. Metaspace is freed only when the class loader that defined the classes becomes unreachable and a GC runs.

Why PermGen was a pain. PermGen was a separate, fixed-size part of the heap (default tens of MB, set by -XX:MaxPermSize). Class metadata, interned strings (before 7) and static data competed for that small space. An app with many classes, or one that redeployed often, hit OutOfMemoryError: PermGen space. You had to guess the right size in advance.

What Metaspace changes. Metadata moved to native memory managed by the JVM in chunks. It starts small and grows as classes load. When the amount reaches a threshold (-XX:MetaspaceSize, a few tens of MB by default), the JVM triggers a GC to unload dead classes, and then raises the threshold. This is why you sometimes see a Full GC "Metadata GC Threshold" early in the life of a big app.

[2.3s][info][gc] GC(5) Pause Full (Metadata GC Threshold) 98M->41M(512M) 120ms
# Cause: metaspace crossed MetaspaceSize. Raising -XX:MetaspaceSize (say 256m) avoids these early full GCs at startup.

What can fill Metaspace. Class loader leaks (see above), huge numbers of generated classes (CGLIB, Groovy, reflection accessors, Hibernate proxies, lambdas that are regenerated), and very large applications. How to investigate: jcmd PID VM.metaspace, jcmd PID GC.class_histogram, and -Xlog:class+unload to see whether classes ever unload.

Sizing rule. Set -XX:MaxMetaspaceSize to something comfortably above the steady state (a typical Spring Boot service often sits in the 100 to 250 MB range, but measure yours) so a leak becomes a clean OOM instead of a kernel kill. Also note a separate "compressed class space" (default 1 GB reserved) that holds class pointers; it has its own OOM message "Compressed class space" in rare cases.

Remember: Metaspace = class metadata in native memory, uncapped by default. Cap it to fail fast.

How much memory does an object take, and why does it matter? Senior

Every object carries a header of about 12 bytes on a typical 64-bit JVM with compressed pointers (16 bytes without), and its total size is rounded up to a multiple of 8. So an Integer holding 4 bytes of data takes 16 bytes, and an empty Object takes 16. Many tiny objects waste far more memory than the data inside them.

A String of 10 characters is the String object plus a separate byte array, about 56 bytes in total. A HashMap<Integer,Integer> entry costs roughly 60 to 80 bytes counting the entry node and two boxed integers, for 8 bytes of real data. This is why a "small" 100 MB dataset can take 1 GB in a Java collection, and why primitive arrays or specialised collections win for big data. Newer JDKs can shrink the header to 8 bytes with compact object headers (a feature that became standard only in recent releases, so check your version). To measure real sizes I use the JOL tool or a heap dump, not guesses.

What is inside the header. The 12-byte header (with compressed class pointers) is an 8-byte mark word and a 4-byte class pointer. The mark word stores the identity hash code (once requested), GC age bits, and lock state. Arrays add a 4-byte length after the header. All object sizes round up to a multiple of 8 bytes (the alignment).

Worked examples you can reproduce with JOL (org.openjdk.jol:jol-core):

class Point { int x; int y; long id; }

A concrete cost story. A cache holding 10 million Long -> Long entries in a HashMap needs per entry: HashMap node 32 B, key 16 B, value 16 B, plus a table slot of 4 to 8 B. About 70 B each, so around 700 MB for 160 MB of actual numbers. A primitive map (for example from Eclipse Collections, fastutil) or two long[] arrays holds the same data in about 160 MB.

Compressed oops. Below a heap of roughly 32 GB, the JVM stores references in 4 bytes (shifted by 3 because of the 8-byte alignment). Crossing about 32 GB turns on 8-byte references, and all your pointer-heavy data grows by up to 20 to 30 percent; a 34 GB heap can hold less than a 31 GB one. This is a well-known reason to stay at 31 GB or below, or jump well above (48 GB and more).

What to do with it. Prefer primitives and primitive arrays for big numeric data, avoid Optional or wrapper objects inside giant collections, intern or share repeated values, and measure with a heap dump (the dominator tree shows retained sizes). Project Valhalla (value classes) aims to remove much of this tax in future Java versions.

Remember: header plus padding makes small objects expensive. Fewer objects, more primitives.

Trace the life of an object from new to being freed. Intermediate

The JVM allocates the object in Eden, from a thread-private slice so no locking is needed. If it dies before the next young GC it costs almost nothing, because the collector only copies live objects. If it survives it is copied between survivor spaces, getting older each time, and is finally promoted to old, where only a less frequent old collection frees it.

The fast allocation is a pointer bump inside a per-thread buffer (a TLAB, thread-local allocation buffer), so new is a handful of instructions. Objects larger than the TLAB are allocated more slowly, and in G1 very big ones go straight to special humongous regions. An object becomes garbage the moment no root can reach it, but memory is only reclaimed at the next collection that covers its area. The cheap path (die young) is the one to aim for: lower allocation rate and short object lifetimes mean fewer promotions.

Concrete walk-through of one request. A request creates a Request object, a List<Row> and 1000 Row objects, then returns JSON and is done 40 ms later.

  1. Allocation. Each thread owns a TLAB (a private chunk of Eden, often a few hundred KB, sized adaptively). new Row() just moves the thread's "top" pointer by the object's size and writes the header. No lock, no CAS in the common case. When the TLAB runs out, the thread gets a fresh one from Eden (this part is synchronized).
  2. Death. After the response, nothing references the 1000 rows. They are garbage but still sit in Eden, costing no CPU.
  3. Young GC. Eden fills up. The collector traces from roots. The finished request's objects are not reached, so they are simply not copied. Eden is then reset in one step. The cost of reclaiming them was zero.
  4. If the request is still running during the GC (it is a slow request), its rows are live and get copied to survivor. If it is still running at the third GC, they are promoted to Old and will linger until an old/mixed collection. This is how a slow downstream call turns normal garbage into old-generation garbage.
Allocation rate 200 MB/s, Eden 400 MB  ->  young GC every ~2 s
Request p50 = 40 ms  : almost nothing is live at GC time  -> tiny pauses
Request p99 = 8 s    : its data survives 4 GCs           -> promoted to Old

That small calculation is the reason tail latency and GC are linked: long requests keep their garbage alive across collections.

Where large objects go. In Parallel/Serial, an object larger than Eden (or than a configured threshold) goes straight to Old. In G1, objects over half a region are humongous. In both cases, large short-lived arrays (a 20 MB buffer per request) bypass the cheap path and are the classic cause of old-generation churn.

How to improve the lifecycle in code. Reduce allocation rate (reuse buffers, avoid boxing in hot loops, stream rather than load entire result sets), shorten lifetimes (release references quickly, do not store request data in long-lived structures), and avoid caches with no size bound. How to measure: -Xlog:gc* for frequency, JFR's "Allocation by Class" and "Allocation by Site" for who allocates, and jcmd PID GC.class_histogram for what is live now.

Remember: allocation is a pointer bump, dying young is free, surviving is what costs.

The heap is 2 GB but the process uses 3.5 GB. Where does the rest go? Senior

The rest is everything outside the heap: metaspace, thread stacks, the JIT code cache, direct buffers, GC bookkeeping structures and native libraries. A typical service easily adds 25 to 50 percent on top of -Xmx, and more with many threads or heavy NIO.

The way to see it is Native Memory Tracking: start with -XX:NativeMemoryTracking=summary, then run jcmd PID VM.native_memory summary. It lists each category in MB. If the numbers add up to the process size, the breakdown tells me which area to tune. If they do not, the gap is native code outside the JVM's accounting, for example a JNI library, or glibc malloc arena fragmentation. On Linux, many threads can create many malloc arenas, and setting MALLOC_ARENA_MAX=2 can reduce this.

What causes StackOverflowError and how do you fix it? Basic

Each method call pushes a frame on the thread's stack, and the stack has a fixed size (about 1 MB by default). If calls nest too deeply, usually through unbounded or accidental recursion, the stack runs out and the JVM throws StackOverflowError. The real fix is to correct the recursion, not to raise the stack size.

In a stack trace I look for a repeating pattern of the same few methods. Typical production causes: a cyclic object graph with a toString, equals or hashCode that walks both directions (parent to child to parent), a JSON serializer on a bidirectional JPA relationship, or recursion on deeply nested data (a very deep linked list or user-supplied nested JSON). Fixes: break the cycle (@JsonIgnore, exclude the back reference), convert recursion to a loop with an explicit stack or queue, or limit input depth. -Xss is a last resort, because it is multiplied by every thread. Note this is an Error, but it only kills the current thread's work, not the JVM.

A minimal reproduction and what it shows.

static int depth = 0;
static void f() { depth++; f(); }       // no base case
public static void main(String[] a) {
    try { f(); } catch (StackOverflowError e) { System.out.println("depth = " + depth); }
}
// typically prints a depth somewhere around 10,000 to 25,000 with the default 1 MB stack

Each frame takes maybe 50 to 100 bytes, so 1 MB gives a depth in the tens of thousands (the exact figure varies with JVM, JIT state and frame size, so never rely on a specific number). Frames of methods with many locals are larger, so heavier methods overflow sooner.

The most common real-world cause: a cycle in a graph.

class Order  { List<Item> items;  public String toString() { return "Order" + items; } }
class Item   { Order order;        public String toString() { return "Item" + order; } }
// order.toString() -> items.toString() -> item.toString() -> order.toString() -> ... StackOverflowError

The stack trace shows the same three or four frames repeated hundreds of times. In a log, the trace is usually truncated at 1024 frames (-XX:MaxJavaStackTraceDepth), so look at the repeating pattern near the top.

Fix decision.

  • Cyclic data: break the cycle in toString/equals/hashCode (print only the id of the parent), or use @JsonIgnore, @JsonManagedReference / @JsonBackReference, or DTOs.
  • Legitimately deep recursion (tree walk, parser): rewrite with an explicit ArrayDeque as a stack, or run it in a thread created with a bigger stack: new Thread(null, task, "deep", 64L*1024*1024).
  • Untrusted input (deeply nested JSON or regex backtracking): cap the depth, because attackers can trigger the overflow deliberately.
  • Raising -Xss: affects every thread, so 200 threads at 4 MB is 800 MB of reserved stack space. Only a last resort.

Note the difference from OutOfMemoryError: unable to create native thread: the first is one thread's stack being too deep, the second is the process being unable to get memory for a new thread's stack at all (too many threads or an OS limit).

Remember: stack overflow = runaway recursion. Find the repeating frames and break the cycle.

4. References, strings and cleanup

Explain strong, soft, weak and phantom references. When would you use each? Intermediate

A strong reference is the normal one and keeps its object alive. A soft reference is cleared only when the JVM is short on memory, so it suits caches. A weak reference is cleared at the next GC once nothing strong refers to the object, so it suits canonical maps like WeakHashMap. A phantom reference is for cleanup actions after an object is collected, and you can never get the object back from it.

All three weaker kinds can be registered with a ReferenceQueue, so I get notified when the target is cleared. In practice: I avoid SoftReference caches in servers, since their behaviour depends on GC and heap size, and use a bounded cache like Caffeine instead. Weak references are used by ThreadLocal map keys and WeakHashMap keys. Phantom references power java.lang.ref.Cleaner, the modern replacement for finalizers.

The reachability rule, spelled out. The collector decides an object's fate by the strongest reference path from a root. If any strong path exists, the object stays. If only a soft path exists, it is "softly reachable": the collector may clear it under memory pressure. If only weak paths exist, it is "weakly reachable": cleared at the next GC that notices. A phantom path means the object is already unreachable otherwise, and the reference merely lets you run cleanup after it is reclaimed.

Object o = new Object();                          // strong
WeakReference<Object> w = new WeakReference<>(o);
System.out.println(w.get() != null);             // true: o still strongly held
o = null;                                         // drop the only strong reference
System.gc();                                      // a request, but fine for a demo
System.out.println(w.get());                      // null (most likely): the object was collected

Use cases with a reason.

TypeCleared whenReal uses
StrongNever while reachableEverything normal
SoftMemory is short (before OOM), policy based on recent useMemory-sensitive caches (use with care)
WeakNext GC after losing strong refsWeakHashMap keys, canonicalizing maps, listeners that must not leak

WeakHashMap gotcha. Its keys are weak, not its values. If a value strongly references its own key, the entry never goes away. Also, using a String literal or a boxed small integer as a key defeats the purpose because those are always strongly held by the pool.

Cleaner example (a safety net for a native resource):

class NativeBuf implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final State state; private final Cleaner.Cleanable cleanable;
    static class State implements Runnable {          // must NOT reference NativeBuf
        long address;  State(long a) { address = a; }
        public void run() { free(address); }
    }
    NativeBuf() { state = new State(alloc()); cleanable = CLEANER.register(this, state); }
    public void close() { cleanable.clean(); }        // explicit, deterministic path
}

Why soft-reference caches are discouraged: when the heap fills, the collector may clear a large share of softly reachable data in a short time, and the cache can empty exactly when the system is under stress, causing a stampede to the database. A bounded cache with size and time limits (Caffeine) is predictable.

Remember: strong keeps, soft = low-memory cache, weak = next GC, phantom = cleanup hook.

What is the String pool, and what is the difference between new String("a") and "a"? Basic

The string pool is a cache of unique string values that lives in the heap. A literal like "a" is taken from the pool, so two identical literals are the same object. new String("a") always creates a new separate object on the heap, so == between it and the literal is false.

That is why strings must be compared with equals, not ==. s.intern() returns the pooled instance, adding it if missing. I do not use intern in application code: the pool is a hash table with a fixed bucket count that can become slow when it holds millions of strings, and it hides the real fix. For memory savings on many duplicate strings I would use G1's string deduplication (-XX:+UseStringDeduplication), which shares the underlying character arrays. The pool was moved from PermGen to the normal heap in Java 7, so it is garbage collected like other objects.

String a = "hi", b = "hi", c = new String("hi");
a == b            // true  (same pooled object)
a == c            // false (new object)
a.equals(c)       // true
a == c.intern()   // true

Where objects are in memory.

String a = "hi";            // literal: JVM finds or adds "hi" in the pool, a points to it
String b = "hi";            // same literal: b points to the same pooled object
String c = new String("hi");// a new String object on the heap (it shares the char data in modern JDKs)

 stack            heap

Compile-time versus run-time concatenation. A frequent trick question:

String x = "ab";
String y = "a" + "b";        // both are literals: the compiler folds it to "ab"  -> y == x is true
String p = "a";
String z = p + "b";          // computed at run time -> a new object  -> z == x is false
z.intern() == x              // true
final String q = "a";
String w = q + "b";          // q is a constant variable, so folded at compile time -> w == x is true

Why a pool at all. Strings are immutable and extremely common. Sharing identical literals saves memory and makes literal comparison cheap. It is also what makes immutability matter: if one reference could change the shared object, everyone using it would see it.

Why not intern() everything. The pool is a native hash table (default size 65536 buckets in recent JDKs, tunable by -XX:StringTableSize). Interning millions of distinct strings causes long chains and slow lookups, extra GC work to clean the table, and nothing is faster than just passing the same reference you already have. A typical legitimate use is a small, bounded set of repeated values read from external input (like country codes).

String deduplication in numbers. If a service holds 5 million strings and 60 percent have duplicate content, G1's dedup (-XX:+UseStringDeduplication) makes duplicate strings share one underlying byte array. It does not merge the String objects themselves, just the data arrays, and runs in the background on strings that survived a few collections. It cuts memory but costs some CPU, so measure with a heap dump first (a "Duplicate strings" report in tools like MAT or VisualVM) rather than turning it on blindly.

Remember: literals are pooled, new String is not. Compare with equals.

Why are finalize() and finalizers discouraged, and what replaces them? Intermediate

A finalizer runs at some unpredictable time after the object is unreachable, maybe never, on a special thread. It slows GC, can resurrect the object and hides bugs. Finalization is deprecated for removal (since Java 18). I use try-with-resources for anything that must be closed, and java.lang.ref.Cleaner as a safety net.

Objects with finalizers need extra GC passes: the first finds them unreachable and queues them, the finalizer thread runs them later, and only a following GC can free the memory. A slow or blocked finalizer then causes a pile of unreclaimed objects and eventually OutOfMemoryError. The right pattern is an AutoCloseable class used with try-with-resources, so cleanup is deterministic. If a leaked resource must still be released, register a Cleaner action that does not reference the object itself.

Why a finalizer is so costly, as a timeline.

  1. Object X has a finalize() method. When created, the JVM wraps it in a special Finalizer reference registered in a global structure (extra cost at allocation).
  2. GC cycle 1 finds X unreachable. It cannot free it yet. It moves X to a queue for the single finalizer thread, and keeps X and everything it references alive.
  3. The finalizer thread eventually calls X.finalize() (time unknown; if the thread is slow or blocked, the queue grows).
  4. GC cycle 2 or later, at the earliest, can finally free X.

So memory is held for at least one extra GC cycle, and if allocation of finalizable objects outpaces the one finalizer thread, the queue grows until OOM. A well-known real incident pattern: a library class with finalize() that closes a socket, many short-lived instances, and a heap that fills with unfinalized objects.

Other problems. A finalizer can resurrect the object by storing this somewhere. Exceptions thrown inside are silently ignored. Order between finalizers is undefined. There is no guarantee it runs at all before JVM exit. It also has security problems (a subclass can finalize a half-constructed object, a "finalizer attack").

The replacement patterns, in order of preference.

// 1. Deterministic: try-with-resources
try (InputStream in = Files.newInputStream(p)) { ... }   // close() always called, even on exception

// 2. Safety net for forgotten close(): Cleaner (see references question)
// 3. Weak/phantom references with a ReferenceQueue for custom bookkeeping

Detection: jcmd PID GC.finalizer_info shows the finalization queue length, and -Xlog:gc+ref shows reference processing time. The JDK's own FileInputStream and FileOutputStream stopped using finalizers for this reason. Since Java 18 (JEP 421) finalization is deprecated for removal, and you can run --finalization=disabled to test that your app does not depend on it.

Remember: never rely on finalize. Close explicitly with try-with-resources, Cleaner as backup.

5. Garbage collection fundamentals

How does the JVM decide something is garbage? What are GC roots? Basic

An object is garbage if it cannot be reached from any GC root by following references. Roots are things that are always alive: local variables and parameters on thread stacks, static fields, active threads, JNI references and class loaders. The collector marks everything reachable from roots and treats the rest as free space.

This is tracing, not reference counting. Java does not count references, so two objects pointing at each other with no outside reference are both garbage: cycles are no problem. The flip side is the source of Java leaks: an object that is still reachable, for example from a static map, is never collected even if the code will never use it again. "Reachable" is not the same as "needed".

Why tracing and not counting. The older idea, reference counting, keeps a counter per object and frees it at zero. It fails on cycles (A points to B, B to A, counters never reach zero) and costs an update on every pointer write. Java uses tracing: start at the roots, follow every reference, mark what you reach, and treat everything unmarked as free. The cost is proportional to the amount of live data, not to the number of dead objects.

What the roots are, concretely.

  • Local variables and parameters in every active stack frame of every thread (the collector reads these precisely using maps the JIT/interpreter provide).
  • Static fields of loaded classes (so the class and its loader must stay alive too).
  • JNI references held by native code, and objects used as locks by running threads.
  • The live Thread objects themselves, and loaded Class objects.

A tiny trace.

static List<String> cache = new ArrayList<>();     // static field = root
void handle() {
    String a = new String("x");     // reachable from the stack frame while handle() runs
    String b = new String("y");
    cache.add(b);                   // b now also reachable from the static root
}                                   // frame popped: 'a' unreachable (garbage), 'b' still live via cache

After handle() returns, a is collectable at the next GC, and b lives as long as cache holds it. If handle() is called a million times, the cache holds a million strings forever: that is the leak shape. Nothing is "lost"; it is simply still reachable.

Mark phase mechanics (tri-colour). Collectors usually describe marking as colouring: white = not yet seen, grey = seen but its references not yet followed, black = seen and fully scanned. Start with roots grey. Repeat: pick a grey object, mark its children grey, make it black. When no grey is left, all white objects are garbage. Concurrent collectors must also track references the application changes while marking runs; that is the job of write barriers (G1's snapshot-at-the-beginning) or load barriers (ZGC).

Related point: reachability is also what WeakReference and the class unloading rule use. A class can be unloaded only when its loader is unreachable.

Remember: garbage = unreachable from roots. A forgotten reference is a leak, a cycle is not.

Explain mark-sweep, mark-compact and copying collection. What are the trade-offs? Intermediate

Mark-sweep marks live objects then frees the dead ones in place, which is simple but leaves holes (fragmentation). Mark-compact marks, then slides the live objects together, which removes holes but costs time moving them. Copying collection copies live objects into an empty space and discards the old one in one go, which is fast and compact but needs spare room.

Copying is perfect for the young generation: most objects are dead, so only the few survivors are copied, and cost is proportional to live data, not to the area size. Old generations hold mostly live data, so copying everything would be wasteful, and they use mark-compact (or region-based evacuation in G1). Compaction matters because without it a big array may not fit in free memory even when total free space is large. This is the reason CMS, which only swept, eventually hit slow full GCs when fragmentation built up.

The same memory, three ways. Take a 10-slot region where A, C and F are live and the others are dead (each slot 1 MB):

Before:   [A][x][C][x][x][F][x][x][x][x]      live = A C F (3 MB), dead = 7 MB

Sweep:    [A][ ][C][ ][ ][F][ ][ ][ ][ ]      free list: 1 MB, 2 MB, 4 MB holes
          -> allocating a 5 MB array FAILS even though 7 MB is free (fragmentation)

Compact:  [A][C][F][ ][ ][ ][ ][ ][ ][ ]      one 7 MB free block, allocate by pointer bump
          (cost: move C and F, then fix every reference to them)

Copy:     from: [A][x][C][x][x][F][...]  ->  to: [A][C][F][ ][ ]...   then discard whole "from"
          (cost: only touches 3 MB of live data; needs a spare "to" space)

Why each exists. Mark-sweep touches only live objects to mark, then walks the heap to free dead ones; no moving, so it is cheap, but allocation must search free lists and fragmentation grows. Mark-compact moves survivors to one end, so allocation becomes a simple pointer bump and fragmentation is gone, at the price of an extra pass to compute new addresses and update all references (it must stop the application, or use advanced barriers). Copying is the fastest when most data is dead, because it never visits dead objects at all, but it wastes half the space it works in.

AlgorithmCost depends onFragmentationUsed for
Mark-sweepLive data + heap sizeYesOld CMS (removed), parts of concurrent phases
Mark-compactLive data + movingNoOld gen in Serial, Parallel
CopyingLive data onlyNoYoung gen everywhere; G1 and ZGC evacuate regions

The link to generations. Young is mostly garbage, so copying is nearly free there. Old is mostly live, so copying it all would be a waste of both time and space; compacting (or evacuating just the mostly-empty regions, which is G1's trick) is used instead. A follow-up an interviewer likes: "why did CMS get removed?" Because it swept without compacting, fragmentation eventually forced a single-threaded full compaction pause that was often worse than what it was meant to avoid, and G1/ZGC solved the problem better.

Remember: sweep is cheap but fragments, compact is tidy but moves, copy is fast but needs spare space. Copy for young, compact for old.

Why are generational collectors a good idea, and what are minor, major, mixed and full GC? Intermediate

Because most objects die young (the weak generational hypothesis), collecting a small young area often is cheap and reclaims most garbage, while the large old area needs collecting rarely. A minor GC collects only young. A mixed GC (G1) collects young plus some old regions. A full GC collects the whole heap and is the slow one I want to avoid.

"Major GC" is a loose term; people mean an old-generation collection. In Parallel and Serial, a full GC stops the world for the whole heap and compacts. G1 only does a full GC when it falls behind, and the full GC is then single-threaded in older JDKs, so it can last many seconds. In logs, any "Pause Full" line is a red flag. Triggers include old being full, metaspace threshold, System.gc(), or a failed promotion.

TypeCollectsPause

Mixed (G1)Young plus chosen old regionsBounded by the pause goal

Numbers that show why it works. Suppose the heap is 4 GB, the young generation is 1 GB, and the app allocates 500 MB/s. Eden fills every second or two. At each minor GC maybe 2 to 5 percent of Eden is still live. The collector copies 20 to 50 MB and frees almost 1 GB, in a few milliseconds to tens of milliseconds. A non-generational collector would have to trace the entire 4 GB (including old data that has not changed) every time. That ratio is the whole argument for generations.

The one complication: old-to-young pointers. A young GC must treat references from old objects into young as roots, otherwise it would free a young object that only an old object points to. Scanning all of old would defeat the purpose, so the JVM keeps a card table (G1: remembered sets): every write that stores a reference into an old object marks a small "card" dirty, and the young GC scans only dirty cards. That is also why code that constantly stores new young objects into long-lived old structures (a big map being refilled) makes young pauses longer.

Where the hypothesis breaks. Caches, session stores and big in-memory datasets create many medium-lived objects: not short enough to die in Eden, not permanent. They get promoted, die in old, and generate old-generation churn. Batch jobs that load a large dataset then process it are another example. That is when Parallel GC (with a large old generation) or a collector designed for this (ZGC generational has special handling) comes up. Also remember that ZGC before generational mode and Shenandoah did not use generations at all, trading simplicity for scanning the whole heap concurrently.

Remember: most objects die young, so collect young often. A full GC in the log means trouble.

What is a stop-the-world pause and what is a safepoint? Senior

A stop-the-world pause is a moment when the JVM freezes all application threads so it can do work that needs a stable heap, such as moving objects. A safepoint is the state the threads must reach first: each thread runs until it hits a safe spot, parks there, and then the JVM does its job.

Threads check for a safepoint request at safe locations such as method returns and loop back-edges. The pause is therefore time to reach the safepoint plus the work itself. One thread stuck in a long loop without such a check delays everyone (time-to-safepoint). Not only GC uses safepoints: biased-lock revocation in old JDKs, deoptimisation and some diagnostic operations do too. In a GC log, -Xlog:safepoint shows time spent reaching safepoints separately from the GC work. Concurrent collectors like ZGC and Shenandoah keep the stop-the-world parts tiny, and do most work while the app runs.

The sequence of a pause, as a timeline.

  1. The VM thread decides it needs a safepoint (for example a young GC is triggered) and sets a flag ("polling page" armed).
  2. Each Java thread, at its next safepoint poll (a cheap memory read inserted by the JIT at method returns and loop back-edges), notices the flag and parks. Threads in native code or blocked are already safe; they just must not return to Java until released.
  3. The VM thread waits until all threads have reported. This waiting is the time to safepoint (TTSP).
  4. The GC (or other VM operation) runs while everything is frozen.
  5. The flag is cleared and threads resume.
[10.001s][info][safepoint] Safepoint "G1CollectForAllocation", Time since last: 995 ms,
   Reaching safepoint: 41200 ns, Cleanup: 12000 ns, At safepoint: 8100000 ns, Total: 8153200 ns
# total 8.1 ms: almost all "At safepoint" (the GC work). If "Reaching safepoint" were 400 ms,
# one thread was stuck in a long loop without a poll: that's the TTSP problem, not the GC itself.

Why a loop without a poll hurts. A huge counted loop (an int index over billions of iterations) used to compile without safepoint polls, so one thread could run for seconds and every other thread, already stopped, waited for it. Modern JVMs added loop strip mining to bound this, but the principle remains: your app pause can be larger than the GC log pause. That is why -Xlog:safepoint and the "Application stopped" lines (-Xlog:safepoint or gc+phases in recent versions) matter when the app sees pauses the GC log does not explain.

What else uses safepoints: deoptimisation, class redefinition (agents), thread dumps (Thread.print triggers a safepoint operation), heap dumps, and some JIT code cache cleanup. A thread dump on a huge number of threads can itself cause a visible pause, so avoid taking them every second in production.

Why concurrent collectors still have pauses: they need a short moment where the heap is consistent, for example to scan thread stacks and set up marking. They make those moments independent of heap size, but not zero.

Remember: pause = time to bring all threads to a safepoint + the work done there.

What is premature promotion, and why does it hurt? Senior

Premature promotion is when short-lived objects get moved into the old generation too early, because the survivor space was too small or the young generation was too small for a burst of live data. They then die in old, where only an expensive old collection can remove them, so old fills up and full GCs start.

It looks like this in a GC log: the old generation after each young GC rises quickly and does not fall, and old collections become frequent even though the real long-lived set is small. Typical triggers are a young generation that is too small, a request burst holding many objects alive across a young GC, or big temporary buffers. Remedies: give the heap more room, stop pinning the young size too small, reduce how long request data stays alive (for example do not hold whole result sets in memory), and with G1 let it size the young generation instead of forcing -Xmn.

A concrete failure story with numbers. A service has a 4 GB heap with G1, but someone pinned -Xmn200m (young = 200 MB). It allocates 400 MB/s, so a young GC runs every 0.5 s. A request takes 2 s on average, so at any GC time about 4 requests' worth of data are live. If each request holds 30 MB, then 120 MB is live at GC time, which does not fit a survivor space of about 20 MB. The overflow is promoted straight to old. A second later those requests finish and the data is dead, but it is in old. Old fills with garbage, a concurrent cycle starts, and eventually a full GC.

The bug was not "old GC is slow", it was "young is too small for the live-at-GC volume".

# What it looks like in the log (Parallel GC style; G1 shows it in region counts)

[ 5.5s] PSYoungGen: 190M->42M(200M)  ParOldGen: 1000M->1105M(3800M)
...
[40s]   Pause Full ... ParOldGen: 3700M->1100M                          # old was mostly dead objects
# Floor of old after full GC is only 1100M: the real live set is small, the promotion was premature

How to confirm. (1) After a full GC the old generation shrinks a lot, so most of it was garbage. (2) -Xlog:gc+age=trace shows the tenuring threshold dropping to 1 and the survivor overflowing. (3) Allocation profile shows large short-lived objects.

Fix order. Remove the pinned young size so G1 can grow young. Raise total heap so there is room. Cut per-request retained data (stream, paginate, do not hold full result sets). If the pattern is "big temporary object per request", reduce its size or reuse it. Only with Parallel/Serial would you tune -XX:SurvivorRatio or MaxTenuringThreshold, and then to keep short-lived data in young one or two cycles longer. Premature promotion is one of the main reasons a slow downstream call (requests living longer) causes a GC problem at the same time.

Remember: if old grows from short-lived data, fix the young size or the object lifetime, not the old collector.

6. The collectors: Serial, Parallel, G1, ZGC

Name the HotSpot garbage collectors and what each one is for. Basic

Serial is single-threaded, for tiny heaps and single-CPU containers. Parallel uses many threads to maximise throughput, good for batch jobs that tolerate pauses. G1 is the balanced default, with pause-time goals for most services. ZGC (and Shenandoah) aim at very short pauses on large heaps. CMS was an older low-pause collector and was removed in Java 14.

All the stop-the-world collectors freeze the app while they work, but Parallel uses many threads to do it faster. G1 splits the heap into regions and collects the ones with most garbage first. ZGC does nearly all its work concurrently, so its pauses stay below about a millisecond regardless of heap size, at the cost of some CPU and memory overhead. Shenandoah is a similar low-pause collector available in OpenJDK builds from Red Hat and others, but not in every vendor build.

How each one works in a sentence, and how it pauses.

  • Serial: one thread does everything, stop-the-world. Tiny overhead, good for heaps up to a few hundred MB, single-core pods, small CLIs.
  • Parallel (throughput collector): same algorithms as Serial but uses all cores for the pause. Pauses scale with live data, so heaps of tens of GB can pause for seconds. Best total throughput. Good for batch jobs and offline processing.
  • G1: region based, mostly parallel pauses with a concurrent marking phase. Aims at a pause target (default 200 ms). The general-purpose default.
  • ZGC: concurrent, uses load barriers, pauses typically well under a millisecond (low single-digit ms at most), regardless of heap size. Supports multi-terabyte heaps. Generational since 21.
  • Shenandoah: also concurrent compaction (with Brooks pointer or load barrier depending on version), similar goal to ZGC, included in many OpenJDK builds but not Oracle JDK.
  • Epsilon: a "no-op" collector that never frees memory; used for tests and extremely short-lived jobs.

How does G1 work? Explain regions and the pause-time goal. Intermediate

G1 divides the heap into equal-sized regions (1 to 32 MB each). Any region can play the role of Eden, Survivor, Old or Humongous. It tracks how much garbage each region holds and, per collection, picks the regions that give the most space back within the pause goal (-XX:MaxGCPauseMillis, default 200 ms). That goal is a target G1 aims for, not a guarantee.

Because it works region by region, G1 can collect a chosen subset of the heap instead of everything, and it evacuates (copies) live objects out of the chosen regions into fresh ones, which compacts as a side effect. It adapts the size of the young generation to meet the pause goal. Lower the goal and young collections get smaller and more frequent, costing throughput. The name "Garbage First" means it picks the regions with the most garbage first.

A worked picture. A 4 GB heap with region size 4 MB has 1024 regions. At any time maybe 200 are Eden, 20 Survivor, 400 Old, a few Humongous, and the rest free. Roles are labels on regions, not fixed address ranges. After a collection, the evacuated Eden regions become free and Eden can be a different set of regions next time.

What a young collection does, step by step.

  1. Eden regions are full. Stop the world.
  2. Scan roots: thread stacks, statics, and the remembered sets (per-region records of which other regions point in, so G1 does not scan old to find old-to-young pointers).
  3. Copy live objects out of Eden and Survivor regions into new Survivor regions or, if old enough, Old regions (parallel, by many GC threads).
  4. Free the evacuated regions. Resume the app.
  5. Re-compute how many Eden regions fit within MaxGCPauseMillis, based on measured copy speed, and size the next young generation accordingly.

Reading a G1 log line.

[8.5s][info][gc] GC(12) Pause Young (Normal) (G1 Evacuation Pause) 1200M->310M(2048M) 14.8ms
#                       what happened                              used before->after (committed) pause

Here the 14.8 ms pause is under the 200 ms goal, so G1 may grow Eden next time to collect less often. If a pause were 300 ms, G1 would shrink Eden.

Common knobs. -XX:MaxGCPauseMillis (target), -XX:G1HeapRegionSize (1 to 32 MB, power of two; default chosen from heap size), -XX:InitiatingHeapOccupancyPercent, -XX:ParallelGCThreads and -XX:ConcGCThreads. Pitfalls. A very low goal (say 20 ms) forces tiny young generations, so collections become constant and throughput drops. A goal is a heuristic: if the live set copying cannot fit, pauses simply overrun. And G1's bookkeeping (remembered sets) costs memory, commonly 5 to 20 percent of the heap, which matters when sizing containers.

Remember: G1 = regions, collect the most garbage first, aim at the pause goal. The goal is a target, not a promise.

Describe the phases of a G1 cycle: young, concurrent marking and mixed collections. Senior

G1 does normal young collections (stop-the-world, copy live objects). When the old generation passes a threshold of the heap (the initiating occupancy, 45 percent by default and adaptive in recent versions), it runs a concurrent marking cycle beside the app to find which old regions are mostly garbage. After that it runs several mixed collections that clean young plus those old regions. If marking cannot finish before the heap fills, G1 falls back to a full GC.

The concurrent part has short stop-the-world steps at the start (piggybacked on a young GC) and at the remark. Marking uses a snapshot-at-the-beginning technique so objects changed meanwhile are handled safely. A full GC is the failure case, caused by allocation outpacing marking, by humongous allocations, or by too small a heap. Typical fixes are more headroom, a lower initiating threshold, or more concurrent threads, but first I check that the live set is not simply too large for the heap.

The phases with their log names.

  1. Young-only phase. Normal young pauses promote objects into old, so old occupancy grows.
  2. Concurrent Start. When old occupancy crosses the initiating threshold, the next young pause is a Pause Young (Concurrent Start): it also records the root set (snapshot) for marking.
  3. Concurrent Mark (app running, using ConcGCThreads): mark everything live in the snapshot; log lines Concurrent Mark Cycle.
  4. Remark (short pause, Pause Remark): finish marking, process weak references, unload classes.
  5. Cleanup (short pause, partly concurrent): count live bytes per region, free completely empty regions, and rank the remaining old regions by how much garbage they hold.
  6. Space-reclamation phase. A series of Pause Young (Mixed) collections each evacuate young plus a slice of the most-garbage old regions (limited by G1MixedGCCountTarget and the pause goal). Regions with little garbage are skipped, since they cost more to copy than they yield.
  7. When enough has been reclaimed, back to young-only.

Notice the marking cycle took 1.4 seconds during which the app allocated more. If allocation outran the free space, you would see to-space exhausted or Pause Full (G1 Compaction Pause) instead of a mixed collection.

Why concurrent mark can lose the race. The initiating threshold must be low enough that marking finishes before the heap is full. If the live set is already above the threshold permanently (a heap too small), G1 runs marking back to back and burns CPU. Recent JDKs adapt the threshold automatically (adaptive IHOP), so hand-setting it is rarely needed. Also remember the cost: concurrent threads (about a quarter of the parallel threads by default) compete with the app for CPU, which is one more reason for at least 2 to 4 cores.

Remember: young, then concurrent mark, then mixed. Full GC means marking lost the race.

What are humongous objects in G1, and why can they hurt? Senior

In G1 an object bigger than half a region is humongous. It is allocated directly into its own contiguous regions, outside the normal young path. These are expensive: they need contiguous free space, they fragment the heap, and they used to be reclaimed only after concurrent marking, so many of them cause early marking cycles and even full GCs.

With the default region size chosen from the heap, humongous starts at typically 512 KB to a few MB. Common sources are big byte arrays or buffers, large ArrayList backing arrays that grow by copy, large JSON or file contents read into a single array. How I confirm it: GC logs show "Humongous Allocation" as the cause of a GC. Fixes: allocate smaller chunks or stream the data, presize or avoid giant arrays, or increase the region size with -XX:G1HeapRegionSize (up to 32 MB) so fewer objects qualify. Newer G1 versions can reclaim humongous objects earlier, so the pain is lower in recent JDKs.

The arithmetic. A 4 GB heap usually gets 2 MB regions (G1 picks a region size so there are around 2048 regions). Humongous means 1 MB or more. A 1.2 MB byte[] needs 1 region by size, but because a humongous object must start at a region boundary and own its regions exclusively, a 2.1 MB array takes 2 regions (4 MB), wasting 1.9 MB; the wasted tail space cannot be used by anything else. So many 1.1 MB buffers waste almost half their regions.

Why they cause trouble.

  • They are allocated directly in old, bypassing the cheap young path. Short-lived humongous objects are therefore "old garbage".
  • They need contiguous free regions. A fragmented heap may have 500 MB free in scattered regions and still fail to allocate a 6 MB array, forcing a full GC.
  • In older JDKs, they were freed only after a concurrent cycle (later versions can reclaim dead humongous objects at young pauses). Allocating many of them triggers cycle starts (look for (G1 Humongous Allocation) in the log).
[30.2s][info][gc] GC(55) Pause Young (Concurrent Start) (G1 Humongous Allocation) 900M->850M(2048M) 11ms
# Every concurrent cycle is being started by a large allocation, not by normal old growth.

Typical code that does it and its fix.

// Reads a whole 50 MB response into one array: one humongous object per request
byte[] all = in.readAllBytes();

// Better: stream in 8-64 KB chunks
byte[] buf = new byte[16 * 1024];
for (int n; (n = in.read(buf)) > 0; ) out.write(buf, 0, n);

// Growing ArrayList / ByteArrayOutputStream: each doubling allocates a bigger array, copy and discard.
// Presize: new ArrayList<>(expectedSize)

How to diagnose. -Xlog:gc+humongous=debug (or gc+heap=debug) prints humongous allocation sizes; JFR's allocation events show the allocation site. If you cannot change the code, raise -XX:G1HeapRegionSize=16m so those objects are no longer over half a region. The trade-off: bigger regions mean coarser collection granularity and more waste for small heaps.

Remember: an object over half a region is humongous. Stream data instead of building giant arrays, or raise the region size.

How does ZGC achieve sub-millisecond pauses, and what does it cost? Senior

ZGC does almost all its work, including moving objects, concurrently while the application runs. The only stop-the-world steps are tiny ones that do not depend on heap size, so pauses stay around a millisecond or less even on multi-terabyte heaps. The price is some extra CPU, a bit more memory headroom, and a small cost on each object reference read.

The trick is the load barrier: a small check the JIT adds whenever the app loads an object reference. ZGC keeps metadata bits in the pointer itself (coloured pointers), so the barrier can notice that an object has moved and fix the pointer on the fly. That lets objects be relocated while threads are running. ZGC became production-ready in Java 15. Generational ZGC arrived in Java 21 (-XX:+UseZGC -XX:+ZGenerational) and from Java 23 is the default ZGC mode, with the single-generation mode removed in 24. The generational version handles high allocation rates much better because it collects young objects separately. ZGC needs spare heap, because it allocates while collecting: if allocation outruns collection, the app stalls ("allocation stall").

Intuition for load barriers. Moving an object while threads hold pointers to it is the hard part of concurrent compaction. ZGC lets threads keep their old pointers, and fixes them lazily: every time Java code loads a reference from a heap field, a tiny piece of JIT-inserted code checks the pointer's colour bits. If the colour says "this pointer is stale" (the object was relocated), the barrier looks up the new address (through a forwarding table), updates the field in place ("self-healing") and returns the right pointer. After the first touch of each field, later loads take the fast path.

The cycle, with what pauses and what does not.

  1. Pause 1 (Mark Start): flip the colour, scan thread stacks. Typically well under a millisecond.
  2. Concurrent Mark: trace the object graph with the app running.
  3. Pause 2 (Mark End): finish. Short.
  4. Concurrent: choose regions with most garbage, relocate their live objects, free regions.
  5. Pause 3 (Relocate Start): short; roots are fixed up.
  6. Concurrent Relocate and remap: finishing in the next cycle's marking.

[0.9s][info][gc,phases] Pause Mark Start 0.012 ms     # typical numbers: microseconds to a ms
[0.9s][info][gc,phases] Pause Mark End   0.021 ms
[0.9s][info][gc,phases] Pause Relocate Start 0.018 ms

What you pay. More CPU (concurrent GC threads share cores with the app), the barrier cost on reference loads (a few percent in throughput tests, workload dependent), and memory headroom: ZGC needs free space to allocate into while it collects, so you want heap larger than live set by a comfortable margin. If the app allocates faster than ZGC reclaims, threads block: Allocation Stall in the log. Fixes: bigger heap, more concurrent GC threads, lower allocation rate. Historically, non-generational ZGC also had a "multi-mapping" memory accounting quirk that confuses tools reading RSS; check numbers with NMT.

When to pick it. Heaps of tens of GB or more, p99 latency requirements in tens of milliseconds, where G1 pauses of 100-500 ms are a problem. For a 2 GB service whose G1 pauses are 20 ms, ZGC adds nothing.

Remember: ZGC moves objects while the app runs, using load barriers. Pauses are tiny, you pay CPU and headroom.

How would you choose a garbage collector for a service? Senior

I start from the goal. For a normal web or microservice, G1 (the default) is fine. For a batch or offline job where only total time matters, Parallel. For a small container with 1 CPU or a tiny heap, Serial. If I have large heaps and strict tail-latency targets and G1 still shows pauses that hurt, I try generational ZGC. Then I confirm by measuring pauses and throughput under realistic load, not by assumption.

The trade-off triangle is throughput, pause time and memory. Parallel gives the best throughput but long pauses that grow with heap size. G1 trades a little throughput for bounded pauses. ZGC gives the shortest pauses but uses more CPU and memory. Before switching collectors I check that the problem is not really my allocation rate or a leak, because no collector fixes those. And I never decide from one benchmark: I compare p99 latency, GC pause totals and CPU on a production-like load test.

A short worked comparison. Imagine the same service tested three ways on a 16 GB heap with 8 cores (numbers are illustrative of typical behaviour, not benchmark results):

ParallelHighestHundreds of msSeconds on a full GCLowest

Decision rules I would say out loud.

  1. Is it a short-lived tool or a pod with 1 CPU / under 1 GB? Serial (it is what the JVM would pick anyway).
  2. Is it batch, where only wall-clock total matters and a 2-second pause is irrelevant? Parallel.
  3. Is it a typical request/response service with latency SLOs in the hundreds of ms? G1, tuned lightly.
  4. Do you see long pauses that violate SLOs after sensible sizing, with a heap above about 8 to 16 GB, or want pauses independent of heap size? ZGC (generational on 21+).
  5. Is the p99 in the single-digit ms range for something like trading or real-time bidding? ZGC or Shenandoah, plus a profile of allocation and warm-up, because GC is only one source of pauses.

The evidence to collect before switching: GC logs with pause percentiles and total GC time share; CPU headroom (concurrent collectors use extra CPU); allocation rate; live set. Run the A/B under the same load, compare p50/p99/p999 and total CPU. A switch that moves p99.9 from 400 ms to 5 ms but doubles CPU may or may not be a win in cost terms; say that out loud.

Finally, a common mistake: switching collectors to fix a leak or a high allocation rate. That only masks the symptom until the heap is full anyway.

Remember: default G1, Parallel for batch, Serial for tiny, ZGC for strict latency. Measure, do not guess.

7. Tuning flags and reading GC logs

Which heap flags matter (-Xms, -Xmx, MaxRAMPercentage) and how do you set them? Basic

-Xmx is the maximum heap and -Xms the initial size. In production I set them equal, so the heap does not resize under load. In containers I prefer -XX:MaxRAMPercentage=70 (or about 60 to 75) over a fixed number, so the heap follows the container limit. The default is only 25 percent, which wastes memory.

Equal Xms and Xmx avoids the pause and cost of growing the heap and makes memory use predictable, at the price of committing it up front. I never set the heap equal to the container limit, since metaspace, stacks and direct buffers also need room. A rule of thumb is a heap of 60 to 75 percent of the limit, less if the service uses many threads or off-heap memory. -Xmn or NewSize pin the young size and stop G1 from tuning itself, so I avoid them with G1.

Why Xms = Xmx. If initial is smaller than max, the JVM starts small and grows the heap in steps, each growth followed by a GC and some pause. It may also shrink later and grow again. Fixing both removes that variability. The downside: the pod appears to use the whole heap immediately, which is realistic anyway for a service that will use it.

Percent flags. -XX:MaxRAMPercentage sets the max heap as a percentage of the container memory (or host RAM if no limit). -XX:InitialRAMPercentage sets the initial one; setting both to the same value mimics Xms=Xmx. -XX:MinRAMPercentage exists but only applies to small memory (below about 200 MB), which confuses people. An explicit -Xmx overrides the percentages.

# Container limit 2 GiB:
java -XX:InitialRAMPercentage=70 -XX:MaxRAMPercentage=70 -jar app.jar
#   heap = 0.7 x 2048 = about 1434 MB

java -XX:+PrintFlagsFinal -version | grep -E "MaxHeapSize|MaxRAMPercentage|InitialHeapSize"
     size_t MaxHeapSize          = 1503238144   {product} {ergonomic}   # check it matches your plan
# With no flag at all the default max heap is 25% = 512 MB, wasting 75% of the pod.

Why not a fixed -Xmx in containers? It works, but if someone changes the pod limit and forgets the flag, the heap is either too big (OOM kill) or too small. The percentage tracks the limit. Fixed values make sense on VMs with known sizes.

Related sizing flags. -Xss thread stack, -XX:MaxMetaspaceSize, -XX:MaxDirectMemorySize, -XX:ReservedCodeCacheSize. And -XX:+AlwaysPreTouch makes the JVM touch every heap page at startup, which slows start but removes page-fault latency later; useful for latency-critical services on dedicated hosts, not on a memory-overcommitted cluster.

Remember: Xms = Xmx, and in a container use MaxRAMPercentage around 70, never 100.

Which other JVM flags would you put on every production service? Intermediate

Enough to get evidence and fail clearly: heap dump on OOM, GC logging, an exit on OOM so the orchestrator restarts a broken process, and a metaspace cap. I would add native memory tracking only when investigating.

-XX:MaxRAMPercentage=70

Why exit on OOM: after an OutOfMemoryError some threads die and the service is often in a broken half-working state, and a restart is safer. The heap dump path must be on a volume that survives the restart and has enough space (a dump is about the size of the used heap). -Xlog is the unified logging flag from Java 9; Java 8 used -XX:+PrintGCDetails -Xloggc. I keep the flags in one place (a JAVA_TOOL_OPTIONS variable or the image entrypoint) so every service has them.

And JAVA_TOOL_OPTIONS is picked up by every JVM started in the environment, including tools, and prints "Picked up JAVA_TOOL_OPTIONS" on stderr: harmless but surprising.

Remember: heap dump, GC log, exit on OOM, metaspace cap. Evidence first, tuning later.

How do you tune G1 to meet a latency target? Senior

First I measure where pauses come from in the GC log, then change one thing at a time. Usually the best step is not a flag but giving G1 more heap headroom and reducing allocation. After that I adjust MaxGCPauseMillis and look at young pause times and any full GCs, and I avoid pinning the young size.

  • Pauses long because a young GC copies a lot: lower the goal a little so G1 shrinks the young generation, or cut the allocation rate and survivor volume.
  • Full GCs or "to-space exhausted": not enough free space to evacuate. More heap, lower the initiating threshold (InitiatingHeapOccupancyPercent) or fix humongous allocations.
  • Long pauses with high system time: often the OS, such as swapping or a container with a CPU limit throttling GC threads, not G1.

The trap is a tuning spree: ten flags copied from a blog make behaviour worse and unexplained. If G1 cannot meet a strict target after sensible headroom, that is the signal to try ZGC rather than to tune further.

A tuning session as a worked example. Symptom: p99 latency spikes every few minutes, GC log shows Pause Young (Mixed) of 350 ms against a 200 ms goal, and occasional to-space exhausted.

  1. Read before changing. Heap 4 GB; after-GC floor about 2.6 GB, so the live set takes 65 percent of the heap. There is little free space to evacuate into. This is the real cause: not enough headroom.
  2. First fix: more headroom. Raise heap to 8 GB (and the pod limit accordingly). Now the floor is 33 percent. Mixed pauses drop to 120 ms and the exhaustion lines disappear.
  3. Second: still some 250 ms young pauses. The log shows large "Object Copy" time. Allocation profiling finds a code path that builds 40 MB response lists. Fix the code (stream the results). Pauses fall to 60 ms.
  4. Only now touch flags, and one at a time: lower MaxGCPauseMillis to 100 and see if throughput and pause distribution both stay acceptable.

How to see which part of a pause is slow. With -Xlog:gc+phases=debug G1 prints a breakdown: Pre Evacuate Collection Set, Evacuate Collection Set (copying: look at "Object Copy", "Scan Heap Roots", "Update RS"), Post Evacuate. High "Object Copy" means too much live data to copy; high "Scan Heap Roots" or "Update RS" means big remembered sets; high Other or system time means CPU starvation, swapping, or transparent huge page stalls.

[5.2s][debug][gc,phases] GC(9)   Evacuate Collection Set: 180.4ms
[5.2s][debug][gc,phases] GC(9)     Object Copy:          168.1ms   # copying survivors dominates
[5.2s][debug][gc,phases] GC(9)     Scan Heap Roots:         6.2ms
[5.2s][info ][gc,cpu    ] GC(9) User=1.10s Sys=0.40s Real=0.19s   # Sys is high: check throttling / swap

Read User versus Real: user/real around the number of GC threads means parallelism is working; user close to real means the GC ran effectively single-threaded (likely CPU limit); high Sys hints at the OS (page faults, throttling).

Remember: read the log, add headroom, cut allocation, change one flag at a time. If G1 still cannot meet the target, try ZGC.

How do you read a GC log? What numbers do you look at first? Intermediate

I look at four things: pause durations, how often collections happen, the heap occupancy after each collection, and any Full GC or evacuation failure lines. The "heap after GC" number is the most useful: if it keeps rising over hours, there is a leak or a too-small heap.

[12.345s][info][gc] GC(41) Pause Young (Normal) (G1 Evacuation Pause) 512M->180M(1024M) 8.2ms
[98.001s][info][gc] GC(97) Pause Full (G1 Compaction Pause) 1020M->700M(1024M) 2400ms

Reading the first line: before 512 MB, after 180 MB, total heap 1024 MB, pause 8.2 ms. The second is trouble: a Full GC of 2.4 seconds that only freed 320 MB, so the live set is about 700 MB in a 1 GB heap. Plotting the after-GC occupancy over time gives a sawtooth: the floor of the teeth is the live data. A rising floor means a leak. Then I check the total GC time share, which should be a few percent. Tools such as GCeasy or GCViewer turn logs into graphs.

The four ratios worth computing. From any log excerpt:

  • Pause time: the milliseconds at the end of each pause line. Look at the max and the 99th percentile, not just the average.
  • Frequency: time difference between collections. Young GC every 100 ms means allocation rate is very high (or young is tiny).
  • GC time share: total pause time over wall time. Under 1 to 5 percent is healthy for a service; 10+ percent means the GC is working too hard.
  • Live set: heap used right after a mixed or full collection. This is the floor; trend it over hours.

Worked example. Two minutes of lines:

[60.0s] GC(10) Pause Young (Normal)  800M->120M(1024M)   9.0ms
[61.4s] GC(11) Pause Young (Normal)  830M->125M(1024M)   9.5ms
[62.9s] GC(12) Pause Young (Normal)  840M->131M(1024M)  10.1ms
...
[120.0s] GC(45) Pause Young (Normal) 900M->300M(1024M)  42ms
[121.0s] GC(46) Pause Full (G1 Compaction Pause) 1000M->640M(1024M) 1800ms

Reading it: at the start, a young GC every 1.4 s freeing 700 MB gives an allocation rate of about 500 MB/s; pauses are ~10 ms. The after-GC size rises 120, 125, 131, ..., 300 MB over the minute: the floor is climbing, which is a leak or a growing cache. At 121 s the heap cannot cope and a Full GC pauses 1.8 s and still holds 640 MB. GC time share in the first minute was about 40 x 10 ms / 60 s = under 1 percent, fine; after the full GC the app suffers.

Cause strings tell you why a GC ran: Allocation Failure (Eden or old full), G1 Evacuation Pause (normal), G1 Humongous Allocation, Metadata GC Threshold, System.gc() (someone called it; consider -XX:+DisableExplicitGC or find the caller), Ergonomics (JVM adjusting), Allocation Stall (ZGC).

Tools. Plain grep "Pause Full" first. Then upload the file to GCeasy or open it in GCViewer or JMC. Keep logs from before and after a change, so you can compare like with like. Format differs by version (Java 8 style: [GC (Allocation Failure) [PSYoungGen: 33280K->5088K(38400K)] 33280K->5096K(125952K), 0.0042 secs]): first brackets are the generation, the second pair is the whole heap.

Remember: watch pause time, frequency, and the after-GC floor. A rising floor is a leak, a Full GC is a warning.

How do you decide how big the heap should be? Senior

I measure the live set: the heap occupancy right after full or mixed collections under realistic load. Then I size the heap at about 3 to 4 times the live set, so the collector has room to work and does not run constantly. I check the result by looking at GC time share and pause times.

A small heap makes GC run often, with high CPU and more promotion. A very large heap makes each full GC (if it happens) long, wastes memory and, when above about 32 GB, loses compressed object pointers, which can make you worse off than at 31 GB. In containers the heap must also fit the memory budget with the non-heap parts. So the rule is: measure the live set, multiply, then check against the container limit, and re-measure after changes. Capacity needs change as data grows, so I watch the after-GC floor over weeks.

The method, with numbers.

  1. Run the service under realistic peak load for long enough to see several mixed or full collections (an hour or more; a day for services with daily patterns).
  2. Read heap occupancy right after the old generation has been collected (the floor): say 1.2 GB.
  3. Multiply: 3 to 4 times the live set gives 3.6 to 4.8 GB of heap. Choose 4 GB.
  4. Add the non-heap budget: about 25 to 40 percent of the heap again (metaspace, stacks, code, direct). Pod limit about 5.5 to 6 GB.
  5. Re-test: GC time share under a few percent, no full GCs, p99 pauses within the target. Adjust and repeat.

Why the multiple. A tracing collector needs free space to do its work: young generation space for allocation, space to copy survivors into, and slack so concurrent marking can finish before the heap fills. With free space equal to 3 times the live set, GCs are infrequent, so the cost per allocated byte is low. With free space tiny, collections are constant (the "GC thrash" state, where the app spends most time collecting a little each time). Some concurrent collectors like ZGC want an even larger multiple at high allocation rates.

Heap vs live setWhat you see
Under 1.5 xConstant GC, full GCs, GC overhead limit exceeded
2 xWorks, frequent collections, little burst tolerance
3 to 4 xComfortable for most services
10 xRarely collects, big pauses if a full GC happens, wasted money

The 32 GB cliff. With compressed ordinary object pointers a heap up to about 32 GB uses 4-byte references. Beyond that (the exact threshold depends on alignment and platform) references double in size, so a 33 GB heap may hold less data than 30 GB. Check with -XX:+PrintFlagsFinal | grep UseCompressedOops. Also remember latency: bigger heap means bigger worst-case full GC with Parallel, and more remembered-set memory with G1. For multi-hundred-GB heaps, move to ZGC or consider splitting into several smaller processes.

Remember: heap is about 3 to 4 times the live set. Measure it, do not guess.

8. Memory leaks and OutOfMemoryError

Java has a garbage collector. How can it still have memory leaks? Basic

A Java leak is an object that is no longer needed but is still reachable, so the GC cannot free it. Typical case: items added to a static or long-lived collection and never removed. The heap grows slowly until OutOfMemoryError, even though no memory was "lost" in the C sense.

The symptom is a rising floor in heap-after-GC and more and more frequent full GCs. The cause is nearly always a reference chain from a root, such as a static map, a cache without a limit, a listener never unregistered, a ThreadLocal on a pooled thread, or an unclosed resource. GC cannot know what the code intends. The fix is to find the chain in a heap dump and remove the reference at the right time, or to bound the structure.

The smallest leak you can write.

class SessionTracker {
    private static final Map<String, Session> ACTIVE = new HashMap<>();   // static = GC root
    static void onLogin(Session s)  { ACTIVE.put(s.id(), s); }
    // onLogout() was forgotten, or is skipped when the browser just closes
}

Every login adds a Session. Sessions that ended are never removed, so each stays reachable from the static map forever. The GC is working correctly: it only frees what is unreachable. Nothing is "lost", you are just holding on.

How it looks over time. The heap graph shows a sawtooth (allocation, then collection), but each tooth bottoms out a little higher. Plot "heap after GC" by hour: 400 MB, 520 MB, 640 MB, ... until the old generation fills, GC runs back to back, response times collapse, and finally OutOfMemoryError: Java heap space appears (or "GC overhead limit exceeded"). A leak is slow; a spike that returns to normal is not a leak.

Looks like a leak but is notHow to tell
Heap usage high, then dropsThe after-GC floor stays flat. G1 and others simply use the room they are given.
Legit growth: cache warming upGrowth stops at the cache bound
Live set bigger than heapFloor jumps with load, no slow upward drift; just needs a bigger heap

Also leak-like but off-heap: unbounded threads, direct buffers, metaspace. These do not show up in heap graphs, so always compare process memory with heap memory.

Remember: a leak in Java = still reachable but no longer needed. Find the chain from a root.

What are the most common causes of memory leaks in real Java services? Intermediate

The usual suspects are unbounded caches or static maps, listeners and callbacks registered but never removed, ThreadLocal values on pooled threads that are never cleared, unclosed resources (streams, connections, sessions), and inner classes holding a hidden reference to their outer object.

  • Static or long-lived collections: a Map used as a cache with no size limit or expiry. Use Caffeine with a maximum size and TTL.
  • Listeners and event buses: register without unregister. Object lives as long as the bus does.
  • ThreadLocal: thread pool threads live forever, so a value set per request stays unless I call remove() in a finally.
  • Bad keys: mutable keys or missing hashCode and equals make map entries pile up as duplicates.
  • Class loaders: redeploys that keep the old loader alive (see the class loader leak question).
  • Inner classes and lambdas: capture this and keep the whole outer object alive.

Short code for the top four, with the fix beside each.

// 1. Listener never removed: the bus (long-lived) holds the screen (short-lived)
bus.register(this);                       // later: bus.unregister(this) in close()/@PreDestroy

// 2. ThreadLocal on a pooled thread
private static final ThreadLocal<User> CURRENT = new ThreadLocal<>();
try { CURRENT.set(u); handle(); } finally { CURRENT.remove(); }

// 3. Mutable key: hashCode changes after insert, entry becomes unreachable by get/remove but stays in the map
Map<List<String>, V> m; key.add("x") after put(key, v)   // lost entry, never removed
// Use immutable keys (records, String, Long)

// 4. Inner class / lambda keeps the outer object
class Screen { byte[] bigImage = new byte[50_000_000];
   Runnable task() { return new Runnable() { public void run() {} }; }   // anonymous class holds Screen.this
}
// A static nested class or a lambda that does not touch 'this' avoids the hidden reference

Why a ThreadLocal leaks specifically. Each thread has a private map from ThreadLocal to value. In an app server, request threads live for the whole life of the process. If you set a value and never call remove(), that thread keeps the value until the thread dies, and a value of a class from a webapp also pins its class loader (the redeploy leak). The map's keys are weak, but the values are strong, so a stale entry's value stays until the thread calls another ThreadLocal operation that happens to clean it.

Other classic causes: a Statement or ResultSet that is not closed, an HTTP client response body not consumed, String.substring keeping a large string alive (old JDKs only), static fields in utility classes, JDBC connections not returned to the pool, Hibernate sessions that live too long (the first-level cache keeps every entity), metrics with unbounded label values (a tag per user id), and logging MDC not cleared.

A quick review habit. For every map, list, set or queue field that is static, or lives in a singleton bean, ask three questions: who adds, who removes, what is the maximum size? If any answer is "nobody" or "unbounded", that is a leak waiting for enough traffic.

Remember: unbounded cache, un-removed listener, uncleared ThreadLocal. Bound it, unregister it, remove it in finally.

How do you find a memory leak in a running production service? Senior

First confirm it is a leak: heap-after-GC keeps rising over time. Then compare two heap histograms taken some time apart to see which class count grows, take a heap dump, and open it in Eclipse MAT or VisualVM to find what holds those objects. The GC root path shows the exact reference chain to cut.

  1. Confirm: GC log or metrics show a rising floor (not just a high heap, which can be normal).
  2. Narrow down: jcmd PID GC.class_histogram twice, 10 minutes apart. The class whose count and bytes grow is the suspect.
  3. Capture: jcmd PID GC.heap_dump /dumps/h.hprof, or rely on -XX:+HeapDumpOnOutOfMemoryError. Take it off the hot path (see the heap dump scenario).
  4. Analyse: in MAT use the leak suspects report and the dominator tree, then "path to GC roots, excluding weak references" for one suspect object.
  5. Fix and verify: remove or bound the reference, deploy, and confirm the floor is flat.

What the histogram diff looks like. Two GC.class_histogram snapshots ten minutes apart (by default it forces a GC first, so you see live objects):

$ jcmd 4242 GC.class_histogram | head -6
 num     #instances         #bytes  class name
   1:       1204331      96346480  [B                         (byte arrays)
   2:       1180022      28320528  java.lang.String
   3:        640118      20483776  com.acme.RequestContext     <-- suspect

# 10 minutes later
   3:       1190440      38094080  com.acme.RequestContext     <-- grew by 550k instances

Byte arrays and strings are always near the top and often only follow the real owner, so look for an application class whose count only goes up. That is your suspect.

In MAT, concretely.

  1. Open the .hprof. Run "Leak Suspects": it reports "one instance of ConcurrentHashMap occupies 1.2 GB (62%)" with the accumulation point.
  2. Open the Dominator Tree, sorted by retained heap. The top entries are the real owners.
  3. Right-click an instance of the suspect class, "Path to GC Roots" > "exclude weak/soft references". The first entries after the root are the chain, for example Thread -> threadLocals -> ThreadLocalMap$Entry -> RequestContext or class Registry -> static listeners -> ArrayList.
  4. Look at the owner's code, decide who should have removed the entry.

Low-impact alternatives for production. Java Flight Recorder with OldObjectSample events (jcmd PID JFR.start settings=profile path-to-gc-roots=true) samples objects that survive long and can record the path to GC roots without a full dump. A dump freezes the JVM for a time proportional to heap size and needs disk space equal to the used heap (see the heap dump scenario), so try these first on big heaps.

Verify the fix. Run the same load again; the after-GC floor should be flat (not just lower). Keep the GC log or metric for a few days to prove it. A leak that took 3 days to kill the service needs a 3 day soak or an accelerated test, not a 10 minute one.

Remember: rising floor, then histogram diff, then heap dump, then GC root path. Fix and re-measure.

In a heap dump, what are shallow size, retained size, the dominator tree and the GC root path? Senior

Shallow size is the memory of the object itself. Retained size is the memory that would be freed if that object were removed, meaning the object plus everything reachable only through it. The dominator tree orders objects by retained size, so the biggest holders of memory are at the top. The GC root path shows the chain of references that keeps an object alive.

Shallow size is misleading: a HashMap object itself is small, but it may retain gigabytes through its entries. So I sort the dominator tree by retained size and look for one object that retains a surprising amount, such as a cache or a session store. Then I take one instance of the leaking type and choose "path to GC roots, exclude weak and soft references" in MAT. The first strong link out of a root, such as a static field, tells me which line of code to fix.

A small example with numbers. A Cache object has a HashMap with 1000 entries, each entry holds a 10 KB byte[]:

Cache (shallow 24 B)
  +-- HashMap (shallow 48 B)
        +-- table (shallow 4 KB)
        +-- 1000 x Node (32 B each) -> value byte[10 KB]
Shallow(Cache)  = 24 B
Retained(Cache) = 24 + 48 + 4 KB + 1000 x (32 B + 10 KB) = about 10.3 MB
# remove the single Cache object (if nothing else references the map or arrays) and 10.3 MB is freed

Retained size is the key number because it answers "what do I get back if I fix this?". It also shows why the dominator tree exists: object A dominates B if every path from a GC root to B goes through A. So everything A dominates would be freed with A. The tree sorts these, so the top row is the single object whose removal frees the most memory.

The caveat on shared objects. If two caches both reference the same 10 KB array, neither retains it alone (removing one still leaves the other path). It is attributed to their nearest common dominator, perhaps the parent. So "retained size" can under-report a leak shared across owners. In MAT, use "Merge Shortest Paths to GC Roots" or the "Group by" views to see aggregated owners.

The message after OutOfMemoryError: tells the area that ran out. Each one points to a different fix, so I read the message first.

What is the difference between a Java OutOfMemoryError and the Linux OOM killer? Senior

An OutOfMemoryError is raised inside the JVM when a JVM-managed area is full, usually the heap, and I get a stack trace and possibly a heap dump. The OOM killer (or Kubernetes OOMKilled) is the operating system killing the whole process with SIGKILL (exit code 137) when total memory use goes over the limit. The JVM gets no chance to log anything.

So a killed pod with a healthy-looking heap graph means the non-heap memory grew: threads, metaspace, direct buffers, native libraries, or the heap simply set too close to the limit. The investigation is different: use Native Memory Tracking, check kubectl describe pod for the OOMKilled reason, and compare container memory against heap. Fix by lowering the heap share, capping the off-heap areas, or raising the limit.

Why the JVM can be killed with a healthy heap. The JVM manages only the heap limit. The cgroup limit counts resident memory of the whole process: heap plus metaspace plus thread stacks plus code cache plus direct buffers plus native allocations plus page cache attributed to the container. With -Xmx at 90 percent of the limit, normal non-heap use alone crosses the line. The kernel does not ask the JVM to free anything, it just kills.

Worked numbers. Limit 2048 MB, -Xmx1800m. Non-heap in steady state is about 350 MB (metaspace 120, 80 threads 80, code 60, direct 50, GC and others 40). Total = 2150 MB, over the limit by 100 MB, so the pod dies when the heap fills past 1700 MB, long before a Java OOM. Fix: -Xmx1300m (about 63 percent), total about 1650 MB, with a 400 MB margin.

Steps when you see 137: (1) check the memory graph of the container working set, not heap; (2) compare with heap committed; (3) enable NMT and diff; (4) check for a new pattern (more threads, more traffic, bigger direct buffers, a library using native memory). Also consider that in Kubernetes the "working set" includes page cache the process touched, so heavy file I/O can inflate it. Memory limits need to account for that.

Remember: OutOfMemoryError is the JVM complaining. Exit 137 is the OS killing it, usually from non-heap growth or a heap set too big.

What causes "OutOfMemoryError: unable to create native thread"? Senior

The JVM asked the OS for a new thread and the OS said no. It is not about the heap. Typical reasons are an unbounded number of threads (a thread per request, or leaked thread pools), an OS or container limit on processes or PIDs, or not enough native memory left for another stack.

Each thread reserves its stack (about 1 MB by default) outside the heap, so thousands of threads use gigabytes. Diagnose with a thread dump: count threads and group them by name to see which pool is exploding. Then check ulimit -u and the container PID limit. Fixes: bound the pools (use a fixed or bounded executor, not newCachedThreadPool for unbounded work), fix code that creates a pool per request, reduce -Xss if safe, or on Java 21 use virtual threads for blocking I/O work, which need no OS thread each.

What the JVM does when you call new Thread().start(). It asks the OS (pthread_create) for a thread with a stack of -Xss size (virtual address space; physical pages are only touched as used). The OS may refuse because: the per-user process limit (ulimit -u) is reached, the kernel's thread limit or pid_max is reached, a container's pids cgroup limit is reached, or virtual memory or RAM for stack and bookkeeping is exhausted. The JVM then throws this error. It is a different failure from a Java heap OOM, and enlarging the heap makes it worse, because there is less room left for stacks.

Diagnosis, with commands.

# how many threads does the JVM have, and who are they?
jcmd PID Thread.print | grep '^"' | sed 's/-[0-9]*"/"/' | sort | uniq -c | sort -rn | head
   812 "http-nio-8080-exec"        <-- 812 request threads? pool max set far too high
   400 "pool-12-thread"           <-- pool-12: a new ExecutorService per call, never shut down

ulimit -u ; cat /sys/fs/cgroup/pids.max

Typical sources. (1) Executors.newCachedThreadPool() given unbounded burst work, which creates a thread per concurrent task. (2) A pool created inside a method (per request) and never shut down. (3) A blocking downstream that makes threads pile up while requests keep coming. (4) Frameworks starting a timer thread per instance. (5) Tomcat's maxThreads set to a very high value.

Fixes in order. Bound every pool (ThreadPoolExecutor with a bounded queue and a rejection policy), reuse shared pools, shut down what you create, add timeouts to downstream calls so threads are freed, and add backpressure. For blocking I/O workloads on Java 21 or newer, virtual threads (Executors.newVirtualThreadPerTaskExecutor()) are cheap (a few KB each, scheduled on a small carrier pool), so a million concurrent waits is feasible, but they do not remove the need to bound the work done, such as database connections. Lowering -Xss to 512k can help but risks StackOverflowError in deep call chains.

Remember: too many threads, not too little heap. Count and bound them.

What are direct buffers, and how can they cause an OutOfMemoryError while the heap looks fine? Senior

A direct buffer (ByteBuffer.allocateDirect) is memory outside the heap, used by NIO and Netty to avoid a copy when talking to the OS. The small Java object on the heap owns a large native block. The native block is freed only when that heap object is garbage collected, so if the heap is quiet, GC does not run, the native memory is not released, and I can hit the direct limit with a healthy heap.

The limit is -XX:MaxDirectMemorySize, which defaults to roughly the max heap size. The message is OutOfMemoryError: Direct buffer memory. Causes: buffers not released (Netty ByteBuf without release() is the classic leak), or allocating a new direct buffer per request instead of pooling. Fixes: pool and reuse buffers, release reference-counted buffers in finally, enable Netty's leak detector in test, and set the direct memory limit deliberately. Never call System.gc() to hide it.

Why direct buffers exist. When Java writes a normal byte[] to a socket, the JVM must copy it into a native buffer first because the garbage collector may move heap arrays while the OS is reading them. A direct buffer is already native memory, so the OS reads it directly: zero extra copy. Netty, Kafka clients, gRPC and NIO use them for high throughput.

The "tiny Java object, big native block" problem.

ByteBuffer b = ByteBuffer.allocateDirect(64 * 1024 * 1024);   // 64 MB native memory
// heap: DirectByteBuffer object ~ 48 bytes + a Cleaner. Native: 64 MB.
b = null;   // the 64 MB is released only when GC notices the 48-byte object is dead

If the heap has little garbage pressure (a big heap, low allocation), no GC runs for a long time, so thousands of dead direct buffers keep their native memory. The JVM tries to help: when the direct total passes the limit it calls System.gc() once and retries, which is why -XX:+DisableExplicitGC can turn a recoverable situation into an OutOfMemoryError: Direct buffer memory. Another variant is a leak, where objects are still referenced.

Netty specifics. Netty uses reference-counted pooled buffers. Every ByteBuf you receive or create must be release()d exactly once (or passed to something that does). Forgetting means the memory is never returned to the pool. Use -Dio.netty.leakDetection.level=paranoid in a test environment to get "LEAK: ByteBuf.release() was not called" messages with the allocation stack trace. Spring WebFlux and many clients hide this with their own handling, but custom handlers must follow the rules.

Sizing. Default MaxDirectMemorySize equals the max heap size (so a 4 GB heap can also use up to 4 GB direct), which doubles the worst case in a container budget. Set it explicitly, for example -XX:MaxDirectMemorySize=512m. Monitor it: the BufferPoolMXBean named "direct" (JMX) shows count and used bytes; jcmd PID VM.native_memory shows the "Other"/"Internal" growth.

Remember: direct buffers live off-heap but are freed by heap GC. Pool them, release them, and budget for them.

9. JIT, warm-up and native image

What is the JIT compiler, and why does Java need it? Basic

The JIT (just-in-time) compiler turns hot bytecode into optimised machine code while the program runs. Interpreting bytecode is slow, and compiling everything upfront would waste time on code that rarely runs. So the JVM starts by interpreting, counts how often methods and loops execute, and compiles only the hot ones.

Because it compiles at run time, it knows facts a static compiler cannot: which classes are actually loaded, which branch is taken 99.9 percent of the time, which method calls are always on the same type. It uses these to optimise aggressively, with a safety net: if an assumption later breaks, the JVM throws away the compiled code and falls back to the interpreter (deoptimisation). That is how Java can approach the speed of C++ for long-running code.

Numbers to explain the idea. Interpreting a bytecode takes roughly 10 to 50 times longer than running the same logic as optimised machine code. Compiling a method to optimised code can take a few milliseconds to hundreds of milliseconds of CPU on a background thread. So compile only what is executed often enough to pay back that cost. HotSpot counts invocations of each method and loop back-edges; when the combined counters cross a threshold (on the order of thousands of invocations for C1 and tens of thousands for C2, adjusted by tiered policy), a compile task is queued.

What "knowing the runtime" buys. A static compiler must be safe for every possible input. The JIT can speculate:

  • Monomorphic call sites. shape.area() where only Circle was ever seen: compile a type check plus a direct (inlinable) call instead of a virtual dispatch.
  • Branch profile. A branch taken 99.99 percent of the time is laid out as the straight-line path; the rare path becomes an "uncommon trap".
  • Class hierarchy analysis. If no loaded subclass overrides a method, calls to it are made direct and inlined.
  • Escape analysis, lock elision, loop unrolling, bounds-check elimination, vectorisation.

When a speculation proves wrong (a new subclass is loaded, an uncommon branch is hit), the compiled frame is converted back to interpreter state (deoptimisation) and the method recompiled with the new facts. You can see it in -XX:+PrintCompilation as "made not entrant".

$ java -XX:+PrintCompilation Main | head
   102   45       3       com.acme.Calc::add (10 bytes)        # tier 3 = C1 with full profiling
   140   58       4       com.acme.Calc::add (10 bytes)        # tier 4 = C2, fully optimised
   180   45       3       com.acme.Calc::add (10 bytes)   made not entrant   # old version retired

Practical consequence: microbenchmarks written with a naive loop and System.nanoTime measure the interpreter and half-compiled code, or get optimised away entirely (dead-code elimination). Use JMH, which warms up, forks JVMs and defeats such optimisations.

Remember: interpret first, compile the hot parts with runtime knowledge, deoptimise if a guess breaks.

Explain tiered compilation, C1 and C2, and inlining. Intermediate

HotSpot has two JIT compilers. C1 compiles quickly with light optimisation, so code gets faster soon. C2 compiles slowly with heavy optimisation for the hottest code. Tiered compilation uses both: interpreter first, then C1 (collecting profile data), then C2 for what stays hot. The most valuable optimisation C2 does is inlining.

Inlining means pasting a small called method's body into the caller. It removes call overhead, but more importantly it lets the compiler see across method boundaries, which enables other optimisations such as escape analysis (an object that never leaves the method may not be allocated on the heap at all) and dead code removal. This is why many small, simple methods and getters cost nothing in Java. Inlining is limited by method size and depth, so a giant method may not be inlined or even compiled well.

The five tiers, simply. Tier 0 is the interpreter (it also gathers profile data). Tiers 1 to 3 are C1 variants: tier 1 is simple code without profiling (for trivial methods), tier 2 is limited profiling, tier 3 is full profiling (the usual C1 stop). Tier 4 is C2. A typical hot method goes 0 to 3 to 4. If the C2 queue is long, a method may sit at tier 2 or 3, or tier 3 code is replaced by tier 2 to cut profiling overhead.

Why both compilers exist. C1 compiles in milliseconds, so the program gets faster within the first seconds, and its tier 3 code records exactly what C2 needs: branch frequencies, receiver types, loop counts. C2 spends much longer compiling but produces code that is often 2 to 3 times faster than C1's, because it uses that profile to speculate and inline deeply. Before tiered compilation (Java 7 and earlier), you had to choose a "client" (C1) or "server" (C2) mode.

Inlining, worked example.

int total(List<Item> items) {
    int sum = 0;
    for (Item it : items) sum += it.price();     // price() is a tiny getter
    return sum;
}
// after inlining price() the loop is effectively: sum += it.price_field;
// no call, no frame; the JIT can now also hoist, unroll, and vectorise the loop

Limits and flags. A method is inlined if it is small (default about 35 bytecodes, or up to about 325 if "hot"), and total inline depth and size are bounded. A 3000-bytecode method may never get inlined or even compiled (-XX:HugeMethodLimit=8000, huge methods are not compiled by default). So breaking a giant method into several moderate ones often helps performance, the opposite of the folk myth. Inspect decisions with -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining.

Code cache. Compiled code goes to the code cache (reserved size about 240 MB with tiered compilation by default, adjustable with -XX:ReservedCodeCacheSize). If it fills, the JIT stops compiling and the app slows down dramatically with a log message "CodeCache is full. Compiler has been disabled". Rare but real for very large apps.

Remember: interpreter, C1, C2. Inlining is the big win because it unlocks the other optimisations.

Why is a Java service slow right after start, and what can you do about it? Intermediate

Right after start the code runs in the interpreter and the JIT has not compiled it yet, classes are still loading, and caches are cold. It is normally slow for seconds to minutes until hot paths are compiled. To reduce it, I warm up the instance before sending real traffic, ramp traffic up gradually, and consider class data sharing or native image for startup.

Practical steps: a readiness probe that only turns ready after a warm-up phase (call the main endpoints a few thousand times with synthetic requests), slow-start or ramp-up in the load balancer so a new pod gets a trickle first, and avoiding CPU limits so tight that the JIT compiler threads starve. Application Class Data Sharing (AppCDS) speeds up class loading, and checkpoint-restore (CRaC) or GraalVM native image address startup more radically. Also remember a rolling deployment replaces fast instances with cold ones, so a latency spike after each deploy is expected without these.

A real rollout timeline. Pod starts at t=0. Readiness passes at t=20 s. The load balancer sends 1/10 of the traffic immediately (each of 10 pods is an equal share). Cold pod p99 is 1.8 s instead of 150 ms for the first 90 seconds, because the JIT still compiles, so the whole service's p99 rises on every deployment. With a rolling update over 10 pods the spike repeats ten times.

A warm-up routine in practice. Use a Spring or startup hook that runs, before marking ready, a loop that calls the in-process handlers 2000 to 10000 times with representative payloads (not just a health ping, since it must exercise the real code paths: JSON parsing, DB access, serialization). A simple form:

@EventListener(ApplicationReadyEvent.class)
void warmUp() {
    for (int i = 0; i < 5000; i++) orderService.price(sampleOrder());   // exercises the hot path
    readiness.markReady();   // only now join the load balancer
}

Better options when startup speed matters. Checkpoint/restore (CRaC or the OS-level CRIU) snapshots an already warmed JVM and restores it in tens of milliseconds, including compiled code in some implementations. Project Leyden is working on AOT caches that store loaded and linked classes (and, in newer JDKs, profile and compiled code). Native image removes the JIT entirely. Always measure: warm-up routines that touch different code than production traffic give a false sense of safety.

Remember: cold JVM = interpreter plus cold caches. Warm up before taking traffic, and ramp it slowly.

What is GraalVM native image, and what are the trade-offs? Intermediate

Native image compiles a Java application ahead of time into a standalone native executable. It starts in milliseconds and uses much less memory, which is great for serverless and short-lived or scale-to-zero services. The trade-offs are a longer, heavier build, usually lower peak throughput than a warmed-up JIT, and restrictions around reflection, dynamic proxies and dynamic class loading.

It works with a closed-world assumption: at build time it analyses what is reachable and drops the rest, so anything found only at runtime (reflection, resources, JNI) must be declared in configuration files or hints. Spring and Quarkus generate much of this for you. The GC in native image is simpler than HotSpot's, and there is no runtime profiling, so very long-running, CPU-heavy services often run faster on the normal JVM. I choose native image when startup time and memory matter more than peak speed, and stay on the JVM for steady, long-running services.

Numbers to anchor the trade-off (typical figures, vary a lot by app, so use as a rough picture only): a Spring Boot REST service on the JVM starts in 2 to 6 seconds and uses 250 to 500 MB RSS at idle; as a native image it can start in 50 to 150 ms and use 50 to 120 MB. Build time goes from seconds to a few minutes and needs several GB of RAM. Peak throughput of the native image is often lower than a warmed C2-compiled JVM, unless profile-guided optimisation (PGO) is used.

How the closed-world analysis works. The build tool starts at main, follows every call it can prove reachable (points-to analysis), and compiles only that code ahead of time. Static initialisers can run at build time and their results are baked into the image heap. The result: no class loading, no interpreter, no JIT, no profiling at run time.

Decision rule. Native image fits serverless functions, CLIs, scale-to-zero and bursty workloads, sidecars, and dense deployments where memory per instance matters. Stay on the JVM for long-running throughput-sensitive services, apps relying heavily on reflection or dynamic features, and teams that depend on mature JVM diagnostics. A third option with fewer compromises is a regular JVM with AppCDS, a tuned heap, and CRaC. Be careful with absolute claims: GraalVM and JDK versions change quickly (for example Oracle GraalVM and community editions differ in available GCs and optimisations), so verify against your version.

Remember: native image = fast start, small memory, lower peak, closed world. JVM = slow start, best peak.

10. The JVM in containers

Is the JVM aware of container limits? What does it do with them? Intermediate

Yes. Modern JVMs (8u191 and later, and 10 and later) read the container's cgroup limits for memory and CPU. The default heap is then 25 percent of the container memory, and the number of CPUs it sees (which drives GC threads, JIT threads and availableProcessors()) comes from the CPU limit, rounded up.

Two consequences matter. First, the default 25 percent is too low for most services, so set -XX:MaxRAMPercentage explicitly. Second, a CPU limit below 2 makes the JVM think it is on a tiny machine and choose Serial GC, and a limit of 1 CPU gives one GC thread and a slow JIT. Older JVMs (before 8u191) ignored cgroups and sized themselves from the host's memory, which led to instant OOM kills. Check what the JVM sees with java -XX:+PrintFlagsFinal -version | grep -E "MaxHeapSize|UseG1|ActiveProcessorCount".

What the JVM reads and decides. On Linux it looks at the cgroup files (v1 or v2) such as memory.max (memory.limit_in_bytes in v1) and cpu.max (quota and period, or cpu.cfs_quota_us / cpu.cfs_period_us in v1), plus cpu.shares in older versions. From those it sets: the "physical memory" for ergonomics, the default max heap (a quarter of it), the number of available processors (quota divided by period, rounded up), and so the GC choice (G1 versus Serial), and the default number of GC and compiler threads.

# Pod with limits: cpu 1500m, memory 2Gi
$ java -XX:+PrintFlagsFinal -XX:+UseContainerSupport -version | grep -E "MaxHeapSize|ActiveProcessorCount|UseG1GC|UseSerialGC"
   size_t MaxHeapSize = 536870912          # 25% of 2 GiB = 512 MiB
   intx   ActiveProcessorCount = 0         # 0 = autodetect; JVM sees ceil(1.5) = 2 CPUs
   bool   UseG1GC = true                   # 2 CPUs and 2 GiB just passes the server-class test

$ java -XX:+PrintContainerInfo -version     # (JDK 17+) prints what it detected from cgroups

Pitfalls to mention.

  • cpu.shares / requests: Kubernetes CPU requests become shares, not a hard cap. Newer JDKs (from about 19, with some backports) no longer use shares for sizing because they proved misleading, so a pod with request 250m and no limit sees the whole node's CPUs; thread pools are sized for 64 cores and then compete badly. Set -XX:ActiveProcessorCount or a limit in that case.
  • Old versions: before 8u191, -XX:+UseCgroupMemoryLimitForHeap was experimental; an older JVM sized heap from the node's RAM.
  • Libraries that read CPU count themselves (Runtime.availableProcessors() is container-aware, but some native libs or Netty event loop defaults and ForkJoin common pool derive from it too).
  • No memory limit set means the JVM sees the node's memory, and the heap defaults to a quarter of a 64 GB node, perhaps 16 GB.

Rule: always set both a memory limit and an explicit MaxRAMPercentage, and verify with PrintFlagsFinal inside the actual pod, not on your laptop.

Remember: the JVM reads the cgroup limit. Set MaxRAMPercentage yourself, and mind a CPU limit under 2.

How do you size container memory for a Java service? Senior

I add up everything the process uses, not just the heap: heap, metaspace, thread stacks, code cache, direct memory and some native overhead, plus a safety margin. As a starting rule the heap is 60 to 75 percent of the limit. Then I confirm by watching the real resident memory under load, and set the limit with headroom above it.

Example for a 2 GB limit: heap 1.3 GB, metaspace about 100 MB, 100 threads at 1 MB is 100 MB, code cache 50 to 100 MB, direct buffers 100 MB, plus about 100 MB for GC structures and native libraries. That is about 1.9 GB, which is too close. So either I raise the limit to 2.5 GB or lower the heap to 1.1 GB. For memory, I set the request equal to the limit, since memory is not compressible: if the pod exceeds the limit, it is killed. Heavy NIO or many threads push the non-heap share higher, so a service with Netty and 400 threads needs a lower heap percentage.

How do CPU limits in Kubernetes affect a JVM? Senior

A CPU limit is enforced by throttling: when the container uses its quota within a 100 ms period, all its threads are paused until the next period. A JVM burns CPU in bursts, from GC threads and JIT compilation, so a tight limit causes throttling that shows up as latency spikes, long GC pauses and slow warm-up, even when average CPU looks low.

Also, the JVM sizes its thread pools from the CPU count it sees, so a limit of 1 CPU means one GC thread, Serial GC, and fewer JIT threads. Common practice for latency-sensitive Java services is a CPU request that matches normal use, and either a generous limit or no CPU limit at all, while always setting a memory limit. If a limit is needed, I give at least 2 CPUs, and check container_cpu_cfs_throttled_seconds_total in metrics. -XX:ActiveProcessorCount can override what the JVM sees.

How throttling works, with numbers. A limit of 1 CPU means a quota of 100 ms of CPU time per 100 ms period, summed across all threads. A JVM with 8 busy threads (for example a parallel young GC using 4 GC threads plus 4 request threads) consumes 8 ms of CPU per millisecond of wall time. After about 12.5 ms of wall time in the period the quota is exhausted and all threads are frozen for the remaining 87.5 ms. A 10 ms GC pause becomes a ~100 ms freeze, and that freeze hits requests while the GC log may show a modest pause time (or may show it as Real time much larger than User time divided by threads).

[12.1s][info][gc,cpu] GC(40) User=0.04s Sys=0.00s Real=0.10s
# Real (100 ms) is far bigger than User/threads (40 ms / 4 threads = 10 ms): the process was throttled mid-pause.
$ cat /sys/fs/cgroup/cpu.stat
nr_periods 12000   nr_throttled 3600   throttled_usec 91000000     # 30 percent of periods throttled

In Prometheus, rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m]) gives the throttled fraction. Anything beyond a few percent for a latency-sensitive service is a smell.

Warm-up is hit particularly hard: at startup the JIT and class loading want many cores. A "startup CPU boost" (in-place resize or temporarily higher limit), or a higher limit and then reduce, helps. Also set -XX:ActiveProcessorCount deliberately if the JVM's view differs from what you want, and cap -XX:ParallelGCThreads and -XX:CICompilerCount to realistic numbers on small pods.

Remember: tight CPU limits throttle GC and JIT bursts. Prefer a generous limit and at least 2 CPUs.

How do you take and read a thread dump? What patterns do you look for? Intermediate

I take one with jcmd PID Thread.print (or kill -3 PID), and always take three, a few seconds apart, because one snapshot cannot show what is stuck versus just busy. I look at thread states: many BLOCKED threads waiting on one lock, many threads waiting on the same I/O or connection pool, or the same stack frame hot across dumps.

Each thread shows a name, state and stack. RUNNABLE threads are on CPU or doing I/O, BLOCKED means waiting to enter a synchronized block, and WAITING or TIMED_WAITING means parked or sleeping. The dump also reports a detected deadlock at the bottom, with the lock cycle. Patterns: 200 threads BLOCKED on the same monitor means lock contention, with the owner thread visible in the dump; all pool threads stuck in a socket read means a slow downstream service; threads piling up in HikariPool.getConnection means connection pool exhaustion. Naming threads and pools makes dumps readable.

The service has 100% CPU. How do you find out whether it is your code, the JIT or the GC? Senior

I find which threads burn the CPU first. Per-thread CPU from top -H -p PID gives a thread id; I convert it to hex and match it with nid in a thread dump. If those threads are named "GC Thread" or "G1 Conc", it is GC. If they are "C2 CompilerThread", it is JIT, usually just warm-up. If they are application threads, I read their stack, or sample with a profiler.

For application threads, a few thread dumps often show the same hot frame (a regex, a loop, serialization). For a precise answer I use a sampling profiler such as async-profiler or Java Flight Recorder (JFR), and read the flame graph: width is time, so the widest frame near the top is the best fix. JFR is built in, has low overhead (typically 1 to 2 percent) and is safe to run in production. A classic cause is an infinite or very long loop, a regex with catastrophic backtracking, or a hot lock spinning.

How does autoboxing affect memory and speed? Intermediate

Autoboxing wraps a primitive in an object (int to Integer). Each box is a heap object of 16 bytes for a 4-byte value, plus a reference to it, and it creates garbage. In a hot loop or a big collection like List<Integer> this multiplies memory use and allocation, and slows the code through cache misses and GC.

Long sum = 0L;                       // boxed: each += allocates a new Long
for (long i = 0; i < 1_000_000; i++) sum += i;

long sum2 = 0L;                      // primitive: no objects
for (long i = 0; i < 1_000_000; i++) sum2 += i;

Small values from -128 to 127 are cached by Integer.valueOf, which is why == on boxed numbers works for small values and fails for bigger ones: another reason to compare with equals. For large numeric data I use primitive arrays, primitive streams (IntStream), or specialised collections, and the JIT's escape analysis removes only some of the boxes, not all.

What the compiler really generates. sum += i with Long sum becomes sum = Long.valueOf(sum.longValue() + i). Each iteration allocates a new 16-byte Long (values outside the small cache -128 to 127) that the next iteration immediately abandons: 1 million iterations create about 16 MB of garbage. The escape analysis may remove some of it in simple loops, but not reliably.

Memory comparison for 1 million numbers (compressed oops, typical figures):

StructureApprox sizeNotes
int[1_000_000]4 MBcontiguous, cache friendly
List<Integer> (ArrayList)about 20 MB4 MB of references + 16 MB of Integer objects, scattered in memory
Map<Integer,Integer>about 60 to 80 MBnode 32 B + two boxed values

Speed suffers beyond memory: each element read is a pointer chase to a separate object (cache miss), which can make summing a List<Integer> several times slower than an int[].

Other traps.

Integer a = 127, b = 127;   a == b   // true  (cached)
Integer c = 128, d = 128;   c == d   // false (two objects) -> use equals
Integer x = map.get(k);     int y = x;   // NullPointerException if absent (auto-unboxing null)
list.remove(i)   // with Integer list: remove(int index) vs remove(Object): a classic surprise

Alternatives. Primitive streams (IntStream.range(...).sum()), primitive arrays, specialised collections (fastutil, Eclipse Collections, HPPC), or bit sets for flags. Valhalla (value classes) is planned to reduce the cost of wrapper-style objects in future Java releases, but today boxing is still an object. Do not rewrite everything: apply it where profiling shows allocation or cache misses in the hot path, or in structures holding millions of numbers.

Remember: a boxed value is an object. Use primitives in hot loops and big collections.

What is allocation rate, and how does reducing it help GC? Senior

Allocation rate is how many MB per second the app creates objects. Every young GC is triggered by Eden filling up, so a high rate means more frequent collections, more objects caught alive mid-flight and promoted early, and more CPU spent on GC. Cutting the rate is often a bigger win than any GC flag.

I measure it from the GC log (heap before the GC minus heap after the previous one, divided by time) or JFR's allocation profiling, which names the code that allocates the most. Typical savings: stop building throwaway strings and collections in hot paths, reuse a StringBuilder, avoid boxing, stream results instead of building a large list, cache immutable objects, and avoid logging strings built eagerly with concatenation when the level is disabled (use parameterised messages). Reduce first the biggest allocators found by profiling, not guessed ones.

How to calculate it from a GC log.

[10.0s] GC(20) Pause Young (Normal) 900M->100M(2048M)
[11.6s] GC(21) Pause Young (Normal) 920M->105M(2048M)
# between the two: heap grew from 100M (after GC 20) to 920M (before GC 21) in 1.6 s
# allocation rate = (920 - 100) MB / 1.6 s = about 510 MB/s

JFR gives it directly (jdk.ObjectAllocationSample, "Allocation Rate" in JMC), and jstat -gcutil or Micrometer's jvm.gc.memory.allocated metric trends it.

Why it hurts, step by step. Young GC frequency = Eden size / allocation rate. At 500 MB/s and a 500 MB Eden, a GC every second. Each young GC has fixed costs (stopping threads, scanning roots, card tables) plus copying what is alive. More frequent GCs mean (a) more fixed cost per second, (b) less time for requests to finish before a GC, so more of their data is alive at GC time and copied or promoted, and (c) more CPU taken from the app. Concurrent collectors need to complete a cycle before allocation consumes free memory, so a high rate directly causes allocation stalls (ZGC) or full GCs (G1).

Typical high-yield fixes, with before and after.

// 1. Logging: string built even when DEBUG is off
log.debug("user " + id + " order " + order);        // allocates a String per call
log.debug("user {} order {}", id, order);            // no allocation if disabled

// 2. Formatters and regex compiled per call
Pattern.compile(...) inside the method  ->  private static final Pattern P = Pattern.compile(...);

// 3. Boxing and streams in hot loops, intermediate collections
list.stream().map(...).collect(toList()) inside a tight loop -> a plain loop or reuse the buffer

// 4. Reading whole payloads: use streaming parsers (Jackson streaming) instead of building full trees

Measure the effect: rate before and after under the same load, plus young GC count and p99. A 30 to 50 percent cut in allocation from three or four hot spots is common and is cheaper than any tuning. A caveat: do not micro-optimise allocation in cold code; escape analysis and the TLAB make small short-lived objects cheap, so go after the top five sites in the allocation profile only.

Remember: less allocation means fewer GCs and less promotion. Profile allocations, fix the top allocators.

12. Real-life scenarios

Each scenario starts with the one-sentence diagnosis and fix you can say first. Then it follows the same shape: situation, what you check first, the fix, and how you prevent it next time.

The pod is OOMKilled (exit code 137) again and again, but the heap graph never reaches the limit. What is going on? Senior

The heap is not the only memory the process uses. Native memory (threads, metaspace, direct buffers, code cache) or a heap set too close to the container limit pushes the total over, and the kernel kills the process. I find which area grew with Native Memory Tracking, then lower the heap share or cap that area.

Situation: restarts every few hours, kubectl describe pod shows OOMKilled, no OutOfMemoryError in the logs, heap graph looks healthy.

Check first: compare container memory (RSS) against heap used. Check the flags: is -Xmx or MaxRAMPercentage close to the limit? Count threads. Restart with -XX:NativeMemoryTracking=summary and diff jcmd PID VM.native_memory summary.diff over time to see which category grows.

Fix: lower the heap to 60 to 70 percent of the limit, cap metaspace, direct memory and thread count, or raise the limit. If one native category keeps growing, that is a leak to fix (for example unreleased direct buffers or a thread-pool leak).

Prevent: a memory budget per service (heap plus non-heap), alerts on container working-set memory and not only heap, and a load test that checks RSS over hours.

Worked investigation. The pod has a 2 GiB limit and -Xmx1500m (about 73 percent). Grafana shows heap used peaking at 1.1 GB, yet the pod restarts every 6 hours.

  1. kubectl describe pod shows Last State: Terminated, Reason: OOMKilled, Exit Code: 137. Confirmed: kernel kill, not a Java OOM.
  2. The container working-set graph rises slowly from 1.7 GB to 2.0 GB over 6 hours while the heap graph is flat: something outside the heap is growing.
  3. Enable NMT on a staging pod (-XX:NativeMemoryTracking=summary), take VM.native_memory baseline after warm-up, and summary.diff 2 hours later:
Total: reserved=+310MB, committed=+280MB
-   Thread (reserved=+190MB, committed=+190MB)   <-- 190 extra threads at 1 MB each
-   Internal (committed=+60MB)
-   Class (committed=+5MB)

The thread count grew by about 190: a library creates a new scheduler thread each time a client is rebuilt on config refresh and never shuts the old one down. Fix the leak (close the old client), cap pool sizes, and lower the heap to 1.2 GB for margin. If NMT total were small but RSS large, I would suspect glibc arenas or a JNI library and try MALLOC_ARENA_MAX=2.

What the interviewer wants to hear: that you separate the two failure types (JVM OOM versus OOMKilled), you know the budget formula, and you use a measurement tool (NMT diff) rather than guessing. Mention page cache too: if the app writes large files, container working set includes cached file pages.

Remember: OOMKilled with a fine heap means non-heap growth or a heap set too big. Use NMT to see which.

Users report random freezes of 2 to 5 seconds in production. How do you investigate the GC? Senior

First prove whether the freezes are GC pauses. I turn on GC logging, line the freeze times up with "Pause" lines, and then fix the cause: a Full GC means too little headroom or a leak, long young pauses mean too much live data to copy, and pauses with high system time point to swapping or CPU throttling outside the GC.

Check first: GC log with -Xlog:gc*,safepoint. If there is no GC pause at the freeze time, look elsewhere: a safepoint delay, a thread dump showing a lock or slow downstream call, a noisy neighbour, or container CPU throttling.

  • Pause Full: the old generation is full or humongous allocations are failing. Add headroom, find leak or giant arrays.
  • Long young pause: too many survivors (large live data per request). Reduce allocation retained per request.
  • High sys time in the log (user=0.1 sys=2.5): the OS is the problem, often swap or throttled CPU.

Fix: depends on the cause above. If G1 cannot meet the target even after headroom, try generational ZGC.

Prevent: keep GC logs on always, alert on pause p99 and any Full GC.

A decision walk-through with sample evidence.

  1. Match timestamps. A user reports a freeze at 14:03:20. Search the GC log: grep "14:03:2" gc.log. Case A: a line Pause Full (G1 Compaction Pause) 3900M->3500M(4096M) 4200ms. Case B: nothing near that time. Case C: a young pause of 2 s.
  2. Case A, Full GC. The after-size of 3.5 GB in a 4 GB heap: the heap is basically full of live data. Is the floor rising over hours (leak) or just stuck high (heap too small or a spike)? Take a histogram or dump. Fix: leak repair, more heap, or reduce what is in flight.
  3. Case B, no GC. Enable -Xlog:safepoint and look for "Total" values in the seconds, or compare app-level timing against the log. Take thread dumps during a freeze (a watcher script that dumps when latency crosses a threshold). Check the node: CPU throttling stats, swap, a noisy neighbour, a disk stall if the app writes logs synchronously, or a DNS timeout.
  4. Case C, long young pause. Look at the phase breakdown (-Xlog:gc+phases=debug): high "Object Copy" means lots of survivors; high "Scan Heap Roots" implies large remembered sets; and compare User, Sys and Real in gc,cpu lines.
[14:03:20][info][gc,cpu] GC(77) User=0.10s Sys=3.80s Real=2.05s
# Sys=3.8s dominates: kernel time. Swapping or transparent huge page compaction or throttling, not the collector.

Classic Sys-time causes: the container is swapping because node memory is tight, transparent huge pages defragmentation (-XX:-UseTransparentHugePages or set THP to madvise), or the heap is partly untouched memory being faulted in (-XX:+AlwaysPreTouch fixes that at startup).

Also consider whether the cause is a pause that is not GC: a long safepoint operation (thread dump on 5000 threads, biased locking revocation in old JDKs), or a stop caused by a slow log appender writing to a full disk. Always say "I prove it from data first", and show the alert you add afterwards: p99 pause and GC share.

Remember: match freeze time to GC log lines. Full GC, long copy or OS stall each has its own fix.

After each deployment the new pods are very slow for a few minutes, then fine. What is happening and what do you do? Intermediate

The new JVMs are cold: code runs in the interpreter, classes are still loading, connection pools and caches are empty, and the JIT has not compiled the hot paths. The fix is to warm each pod up before it gets real traffic and then ramp traffic in gradually.

Check first: compare latency per pod age. Look at JIT activity (jcmd PID Compiler.queue or JFR) and CPU in the first minutes, and check whether a CPU limit is starving the compiler threads.

Fix: make the readiness probe pass only after a warm-up routine (call key endpoints with synthetic requests, open the connection pool). Use slow-start in the load balancer or service mesh. Give the pod enough CPU during startup (a startup CPU boost where supported). Consider AppCDS for faster class loading, or GraalVM native image or CRaC if startup is the main issue.

Prevent: include a warm-up phase in the standard service template, and watch p99 latency during rollouts so a bad one is stopped early.

Confirm the diagnosis with data before fixing. Chart p99 latency by pod age. If the first 3 to 5 minutes are consistently slower on every new pod and CPU is high in that window (JIT compiler threads busy), it is warm-up. Compare with jcmd PID Compiler.queue (a long queue means JIT is behind) and the number of loaded classes still rising. If instead latency stays high, it is not warm-up (maybe a DB cold cache or a leak).

The combined fix, with a Kubernetes sketch.

# 1. Do not receive traffic until warmed
readinessProbe:  { httpGet: { path: /ready, port: 8080 }, initialDelaySeconds: 10, periodSeconds: 5 }
# /ready returns 200 only after the in-process warm-up loop has finished

# 2. Give startup enough CPU (limit not tiny); no CPU limit or a generous one
resources: { requests: { cpu: "2", memory: 2Gi }, limits: { memory: 2Gi } }

# 3. Gradual ramp in the load balancer / mesh (slow-start over 60-120 s)
# 4. Rolling update with maxUnavailable 0, maxSurge 1, so old pods keep serving while new ones warm up

Warm-up content matters: replay representative requests (a sample of anonymised production traffic, or a recorded set) so that all hot code paths, not just the health endpoint, get compiled. If you cannot, ramp-up alone helps, because a pod receiving 5 percent of traffic compiles its hot paths with less user impact.

When to go further. If warm-up takes minutes and autoscaling needs fresh capacity fast, consider AppCDS (saves 20 to 40 percent of startup in many apps), CRaC checkpoint/restore, or native image, each with trade-offs (see the earlier questions). A less obvious cost: autoscalers add cold pods exactly when load is high, so cold-start latency affects the worst moments. Keep a little spare capacity or scale earlier.

Remember: cold JVM is slow. Warm it before readiness, then ramp traffic.

The heap grows slowly until the service dies after about 3 days, and the heap dump shows many instances of a request-context class. How do you find the cause? Senior

Something still holds every request context. I open the dump, pick one instance of the context class, and look at its path to the GC roots. A very common answer is a ThreadLocal on a pooled thread that is set per request and never removed, so each thread keeps its last context alive, or a static collection or listener that accumulates them.

Check first: in Eclipse MAT, run "path to GC roots, excluding weak and soft references" on one context object. If it ends at Thread.threadLocals, it is a ThreadLocal. If it ends at a static field, it is a collection. Note that one leaked context may drag along a large object graph (the request body, the session), so retained size explains why the heap grows fast.

// the fix: always clear in finally
CONTEXT.set(ctx);
try {
    chain.doFilter(req, res);
} finally {
    CONTEXT.remove();   // pooled threads live forever
}

Fix: clear in finally, or move to a request-scoped design. Prevent: wrap ThreadLocal use in one helper or filter, and add a soak test that watches the heap-after-GC floor.

The full chain in a heap dump, and why it leaks. The path to GC roots for one RequestContext looks like:

Thread "http-nio-8080-exec-5"  (a GC root: live thread)
  -> threadLocals (ThreadLocal.ThreadLocalMap)
     -> table[7] (ThreadLocalMap.Entry)
        -> value = com.acme.RequestContext        <-- retained 3.4 MB (includes the request body)

Only about 200 pooled threads exist, so a ThreadLocal alone retains at most 200 contexts (one per thread; the next request overwrites the previous). A growth to millions of instances therefore means more than one cause: for example contexts also being added to a static list for auditing, or the ThreadLocal holding a growing structure (a list the code appends to on every request and never clears), or the executor creating new threads continuously (see thread count). Always count: number of leaked instances divided by number of threads tells you which pattern it is.

Safe designs. Use a servlet filter or interceptor with try/finally for set and remove. Prefer passing context explicitly. On Java 21 or newer, ScopedValue (preview in 21) offers bounded, immutable context that cannot leak beyond its scope. For executors, wrap tasks so the context is set and cleared around each task (Spring's TaskDecorator). Also use the logging MDC carefully: MDC.clear() in finally.

An in-memory cache was added to speed up a lookup and a week later the service has OutOfMemoryError. What went wrong and how do you fix it? Intermediate

The cache has no size bound or expiry, so it grows with every new key until the heap is full. A cache without an eviction policy is a memory leak with a nice name. I replace it with a bounded cache (maximum size plus time to live), such as Caffeine, and measure the hit rate.

Check first: in a heap dump, the dominator tree shows one map retaining most of the heap. Check the key space: user ids, request ids and timestamps give nearly unbounded keys. Also check whether values hold large objects and whether keys have correct equals and hashCode (otherwise duplicates pile up).

Cache<String, Product> cache = Caffeine.newBuilder()
    .maximumSize(50_000)
    .expireAfterWrite(Duration.ofMinutes(10))
    .recordStats()
    .build();

Fix: bound by size or weight and add expiry. Prefer an external cache (Redis) when the data set is big or must be shared. Soft references are not a good bound, because they behave unpredictably. Prevent: review every static or singleton map in code review, and expose cache size and hit-rate metrics.

Why the failure shows after a week, not immediately. The key space was small in testing (a few thousand products). In production the keys include user ids, query strings or timestamps, so the number of distinct keys grows daily. A graph of cache size would climb in a straight line; the heap floor with it. The first sign is usually more frequent old collections, days before the OOM.

Sizing the bound with a number. If each entry is about 2 KB (key, value, map overhead), 50,000 entries is about 100 MB. Pick the maximum from the memory budget, not from hope: "this cache may use at most 5 percent of the heap". Use maximumWeight with a weigher when value sizes vary a lot:

Cache<String, byte[]> c = Caffeine.newBuilder()
    .maximumWeight(100L * 1024 * 1024)            // 100 MB budget
    .weigher((String k, byte[] v) -> v.length + 64)
    .expireAfterAccess(Duration.ofMinutes(30))
    .recordStats().build();
// later: c.stats().hitRate()  -> if under ~50%, the cache may cost more than it saves

Other things a good answer covers.

  • Stampede: when many threads miss the same key, use cache.get(key, loader) so only one loads it.
  • Staleness: the TTL defines how stale data can be; pick it from the business rule.
  • Multiple instances: each pod has its own copy; for shared consistent data use Redis or a distributed cache.
  • Negative caching: caching "not found" can fill the cache with junk keys from scanners; give those a short TTL.
  • GC impact: a huge on-heap cache of medium-lived entries causes old-generation churn; off-heap caches or an external store move that out of GC.

A final practical check is to export cache size, hit rate and eviction count as metrics, so that growth is visible days before it becomes an incident.

Remember: every cache needs a maximum size and a TTL, and metrics.

After a few hot redeploys on Tomcat, the app server throws OutOfMemoryError: Metaspace. How do you handle it? Senior

Each redeploy creates a new class loader, and the old one is not being freed, so old copies of all classes pile up in metaspace. That is a class loader leak: something outside the webapp still points to it. Short term I restart the server instead of hot redeploying. Long term I find the reference in a heap dump and remove it.

Check first: after a redeploy, take a heap dump and search for multiple instances of the webapp class loader (WebappClassLoaderBase). For an old one, find the path to GC roots. Usual blockers: a JDBC driver registered in DriverManager, a non-daemon thread or timer started by the app and never stopped, a ThreadLocal on a container thread, a shutdown hook or a logging framework holding an appender.

Fix: clean up in a ServletContextListener.contextDestroyed: deregister drivers, stop threads and executors, clear thread locals. Tomcat's leak prevention listener reports many of these in its logs. Setting -XX:MaxMetaspaceSize makes the failure explicit and early. Prevent: deploy by restarting or replacing containers, which is the normal practice now.

A concrete confirmation routine.

# 1. Count loaders before and after a redeploy
jcmd PID VM.classloader_stats | grep -i WebappClassLoader
   WebappClassLoader  ... classes=8200   <-- old app, should vanish after undeploy
   WebappClassLoader  ... classes=8200   <-- new app

# 2. Metaspace trend
jcmd PID VM.metaspace | head      # committed grows by ~120 MB per redeploy

# 3. Heap dump, then in MAT: histogram, filter 'WebappClassLoader', Path To GC Roots on the OLD one

A typical result: java.sql.DriverManager -> registeredDrivers -> org.postgresql.Driver -> WebappClassLoader. The driver class came from the webapp, but DriverManager belongs to the JDK, so it outlives the app. Another typical result: a java.util.Timer thread or a scheduled executor, whose thread's context class loader is the webapp loader.

Cleanup listener example.

@WebListener
public class Cleanup implements ServletContextListener {
    public void contextDestroyed(ServletContextEvent e) {
        ClassLoader cl = Thread.currentThread().getContextClassLoader();
        for (Enumeration<Driver> d = DriverManager.getDrivers(); d.hasMoreElements();) {
            Driver drv = d.nextElement();
            if (drv.getClass().getClassLoader() == cl) {
                try { DriverManager.deregisterDriver(drv); } catch (SQLException ignore) {}
            }
        }
        scheduler.shutdownNow();      // stop app-owned threads
    }
}

Alternatives that avoid the problem: put the JDBC driver jar in the server's shared lib, use the container's datasource instead of registering drivers yourself, or run each app in its own process (embedded server, containers) and redeploy by replacing the process. That last approach is the modern answer, since it also resets every other kind of leak.

Remember: one reference into the old class loader keeps the whole old app. Clean up on shutdown, or restart instead.

After a traffic spike the service enters a loop of full GCs and never recovers until restarted. What happened and how do you prevent it? Senior

The spike pushed the live data (queued requests, buffers, big result sets) close to the heap size, and each Full GC then frees almost nothing, so the next one starts at once. The JVM is thrashing: it spends nearly all its time in GC, requests time out and pile up even more, and it cannot recover. The fix is to bound the work in flight and give the heap headroom.

Check first: the GC log shows back-to-back Pause Full lines where the heap after GC stays near the maximum. The heap dump of that moment shows what is retained: usually in-flight request data, unbounded queues or caches.

Fix: bound the queues and thread pools, apply backpressure or load shedding (reject early with 429 or 503 rather than accepting everything), stream big results, and raise the heap if the legitimate live set is large. As a safety net, -XX:+ExitOnOutOfMemoryError with a restart policy is better than a zombie that never recovers. Also make the health probe fail when the process is in GC trouble, so the orchestrator replaces it.

Prevent: load test beyond the expected peak, and alert on GC time share and Full GC count.

What the death spiral looks like in a log.

[300.1s] GC(88) Pause Full (G1 Compaction Pause) 3990M->3950M(4096M) 5200ms
[305.4s] GC(89) Pause Full (G1 Compaction Pause) 3995M->3960M(4096M) 5400ms
[310.9s] GC(90) Pause Full (G1 Compaction Pause) 3996M->3965M(4096M) 5600ms
# each full GC frees only about 40 MB; the app gets 0.1 s of run time between pauses; requests time out,
# clients retry (more load), health checks may still pass because the process is "up"

Why it cannot recover. More traffic means more in-flight requests, each holding data; slow GC means slower requests; slower requests mean more of them in flight at once (Little's law: concurrency = arrival rate x latency). Memory held by in-flight work grows with latency, which grows with GC time. A positive feedback loop, with a stable bad state.

Controls that break the loop.

  1. Bound concurrency: a fixed-size thread pool, a bounded queue, and a rejection policy. A bounded queue of 100 means at most 100 queued requests' data in memory.
  2. Load shedding: return 503 or 429 quickly once the queue or active count passes a limit, rather than accepting work you cannot finish.
  3. Timeouts everywhere: client and server timeouts so abandoned requests release memory.
  4. Limit per-request memory: maximum payload sizes and page sizes.
  5. Fail fast: -XX:+ExitOnOutOfMemoryError, and optionally a health check that fails when GC time share exceeds a threshold (via a metric), so the orchestrator restarts the pod and other replicas take over.
  6. Capacity: if the legitimate live set at peak is near the heap size, raise the heap (and check non-heap budget).

A subtle point worth saying: restart is a fix for the symptom but if all replicas get the same spike, they can all spiral together (cascading failure). Shedding load at the edge and autoscaling help keep the system out of that state.

Remember: a full GC loop is thrashing near the heap limit. Bound the work, shed load, add headroom.

After a dependency upgrade, a service throws NoClassDefFoundError and NoSuchMethodError in production, but all unit tests pass. What do you check? Intermediate

This is almost always a dependency version conflict: the classpath at runtime holds a different version of a library than the one the code was compiled and tested against. I inspect the resolved dependency tree of the real artifact, find the duplicate or wrong-version jar, and pin one version.

Check first: read the exact class or method in the error. Run mvn dependency:tree -Dverbose (or gradle dependencies) and look for the library with two versions or a transitive dependency that the new version dropped. Check the packaged fat jar or WAR contents too, since the test classpath differs from the runtime one. -verbose:class or -Xlog:class+load shows which jar each class was loaded from. Also look for a shaded copy of the same library.

Fix: align versions with dependency management (BOM or constraints), exclude the stray transitive dependency, or relocate it. For NoClassDefFoundError: Could not initialize class, look higher in the logs for the first failure of the static initializer. Prevent: an integration test that runs against the packaged artifact, and a dependency convergence check in CI.

Why unit tests pass but production fails. Tests run with the Maven or Gradle test classpath, where your module's direct dependencies win. In production the artifact may be a fat jar, a WAR in an app server that provides its own copies of libraries (servlet API, logging, JSON), or a Docker image built from a different layer. "First on the classpath wins", so a different version may be picked even though the code compiled fine.

A short worked example. Library A needs guava 31 and uses ImmutableList.copyOf. Library B pulls guava 19 transitively. Maven's "nearest wins" resolves to 19, in which a method A calls does not exist. A's call fails at run time with NoSuchMethodError: com.google.common.collect.... The compile step passed because A was compiled against 31 earlier.

$ mvn dependency:tree -Dverbose -Dincludes=com.google.guava
[INFO] +- com.acme:lib-a:jar:2.0:compile
[INFO] |  \- com.google.guava:guava:jar:31.0:compile (omitted for conflict with 19.0)   <-- the culprit line
[INFO] \- com.acme:lib-b:jar:1.4:compile
[INFO]    \- com.google.guava:guava:jar:19.0:compile

$ unzip -l app.jar | grep -i guava          # which version is really packaged?
$ java -Xlog:class+load -jar app.jar | grep 'com.google.common.collect.ImmutableList'
   ... source: jar:file:/app/lib/guava-19.0.jar!/       <-- confirms the loaded jar

Fixes. Pin the version with dependencyManagement (Maven) or a constraint/BOM (Gradle), add an exclusion for the stray one, enable Maven Enforcer's dependencyConvergence rule, or use a Gradle dependency lock. Also consider the module graph, shaded jars, and for app servers, classes provided by the container (set the scope to provided only when the server really has them). Include at least one test that boots the real packaged artifact (a smoke test in CI), because that catches classpath differences.

Remember: works in tests but fails in production means a different classpath. Read the dependency tree and see which jar loaded.

You need a heap dump from a 24 GB production heap, but taking it freezes the pod and the liveness probe kills it. What do you do? Senior

A heap dump pauses the JVM while it writes about as many gigabytes as the used heap, so on a big heap it can last minutes and the probe kills the pod mid-dump. I take the dump from one instance that is pulled out of the load balancer and has its liveness check relaxed, onto a volume with enough space, or I avoid a full dump by using histograms and a smaller target.

Steps: pick one affected replica, remove it from traffic, and temporarily raise or disable the liveness probe (or use a debug sidecar). Run jcmd PID GC.heap_dump -all /dumps/h.hprof to a mounted volume (default is live objects only, which also triggers a full GC first). Compress and copy it out with kubectl cp. Open it on a machine with RAM larger than the dump, or use a tool that streams.

Cheaper options first: jcmd PID GC.class_histogram twice takes seconds and often names the leaking class. Flight Recorder's old-object sample can point to the leak path with low overhead. And -XX:+HeapDumpOnOutOfMemoryError captures the dump at the failing moment so no manual one is needed.

Prevent: have a volume and a runbook ready, and test the procedure before an incident.

Why the pod dies. Writing a dump walks the whole heap at a safepoint and streams it to disk: a 24 GB used heap may take 2 to 10 minutes depending on disk speed. The JVM does not answer the liveness probe meanwhile (the probe thread is frozen too), so after failureThreshold x periodSeconds (say 3 x 10 s) the kubelet restarts the container, and the dump is lost or truncated. The default for GC.heap_dump also runs a full GC first, adding to the pause.

A procedure that works.

  1. Choose a replica that shows the problem. Remove it from the Service (change its label so it no longer matches the selector; the pod stays alive but gets no traffic).
  2. Make sure a volume with at least the heap size of free space is mounted (an emptyDir with enough node disk, or a PVC), because the container filesystem may be small.
  3. Run the dump from inside the container: jcmd 1 GC.heap_dump /dumps/h.hprof. Because the pod no longer takes traffic and its probes cannot kill it once the label approach is used (use a probe-free debug copy or patch the probe), it completes.
  4. Compress and copy out: gzip then kubectl cp. Heap dumps contain sensitive data (passwords, personal data in memory): store and share them under the same controls as production data.
  5. Analyse on a workstation with RAM larger than the dump (MAT needs several GB over the file size; use the command-line parse mode ParseHeapDump.sh on a bigger machine and open the index).

Smaller-footprint alternatives. jcmd PID GC.class_histogram (seconds). JFR with OldObjectSample and path-to-gc-roots=true (low overhead, can name the retaining path). -XX:+HeapDumpOnOutOfMemoryError with a mounted volume so it is done once, at the moment that matters. For the future, test the procedure on staging so that on the night of an incident you only run commands, and consider a bigger terminationGracePeriodSeconds if the dump is taken on shutdown.

Remember: a heap dump freezes the JVM. Use one pulled-out replica, a big volume, and try the histogram first.

A nightly batch job fails with "Java heap space" after the data grew. The team wants to raise -Xmx to 32 GB. What do you say? Intermediate

I would not just raise the heap. I first check why memory depends on data size: most likely the job loads everything into memory before processing. A heap that grows with the data size only delays the next failure. I would change the job to stream or process in chunks so memory stays constant, and raise the heap only as a short-term bridge.

Check first: the heap dump (or histogram) at the failure shows what holds the memory: a giant List of rows, a whole file read into a string, or an ORM loading entities into one persistence context. Count how it grows with input size.

Fix: read in pages or with a cursor or stream, process and write per chunk (for example batch size 1000), clear the persistence context between chunks, and never collect the full result in a list. Where it is truly needed, use primitive arrays or compact structures. Note that going past about 32 GB loses compressed object pointers, so a 32 GB heap can hold less than a 31 GB one. And a bigger heap makes any full GC pause longer.

Prevent: test batch jobs with a data volume well above production, and monitor peak heap per run.

Show the reasoning with a calculation. The job reads 4 million rows into a List<Row>, each row 40 columns of strings. Estimate: one row about 1.5 KB in objects, so 4 million rows is about 6 GB. Last month 3 million rows needed 4.5 GB and fit in 8 GB. Doubling data (6 to 8 million) needs 12 GB or more plus overhead. Raising to 32 GB works for now, and breaks again when data doubles twice. Memory proportional to input is the real bug. Also note the cost: a 32 GB heap in a shared cluster blocks other jobs, and a full GC on it can pause for many seconds.

Rewrite as a pipeline with constant memory.

// Before: load all, then process
List<Row> all = repo.findAll();                 // whole table in memory
all.forEach(this::transform);

// After: stream with a cursor, process and write in chunks of 1000
try (Stream<Row> rows = repo.streamAll()) {       // JDBC fetchSize + forward-only cursor
    List<Out> batch = new ArrayList<>(1000);
    rows.forEach(r -> {
        batch.add(transform(r));
        if (batch.size() == 1000) { writer.writeAll(batch); batch.clear(); }
    });
    writer.writeAll(batch);
}
// With JPA: entityManager.clear() after each chunk, or use StatelessSession / JDBC directly

Memory now depends on the chunk size (about 1.5 MB per 1000 rows), not on table size, so 10x data needs the same heap. If a step truly needs everything (a global sort, a join), use an external sort or push the work into the database or a framework designed for it (Spark, SQL), or partition by key and process partitions independently.

What to say about the stopgap. "I would raise the heap to unblock tonight's run and open a ticket for the streaming rewrite," and mention heap dump verification: confirm the memory is really a loaded list and not a leak between steps. And add a data-growth test so the next doubling is caught before production.

Remember: if memory grows with the data, stream it. More heap just moves the failure date.
