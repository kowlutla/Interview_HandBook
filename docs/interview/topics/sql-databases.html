Mental model: the 8 ideas everything hangs on

One line: a relational database stores facts as rows in tables, lets you ask for them with a declarative language (you say what you want, the optimizer picks how), and protects them with transactions. Most interview answers are about three things: the shape of the data, how the engine finds it (indexes and plans), and what happens when many people change it at once (locks and isolation).
  1. Tables of rows, linked by keys. A primary key identifies a row. A foreign key says "this value must exist in that other table". Good design avoids storing the same fact twice.
  2. SQL is declarative. You describe the result. The query planner chooses indexes, join order and algorithms using statistics about the data. The same query can be fast today and slow next month because the data or the statistics changed.
  3. Logical order is not written order. A query runs as FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. This explains why you cannot use a SELECT alias in WHERE.
  4. An index is a sorted copy of some columns with pointers to the rows. It makes reads fast and writes slower. A B-tree index is the default everywhere.
  5. NULL means "unknown", not zero or empty. Comparisons with NULL give UNKNOWN, which behaves like false in WHERE. Many bugs live here.
  6. A transaction is all or nothing (atomic), keeps rules true (consistent), is not confused by others (isolated), and survives a crash (durable). The isolation level decides how much other transactions can disturb you.
  7. Readers do not block writers (MVCC). Both PostgreSQL and MySQL InnoDB keep several versions of a row. Writers still block other writers on the same row.
  8. One server is the default, scale is a ladder. Tune queries and indexes first, then add a cache, then read replicas, then partitioning, and only then sharding. Every rung adds a new kind of failure.

1. Relational design, keys and normalization

What is the relational model, and what do "table", "row", "key" and "constraint" mean? Basic

What the interviewer is testing: basic vocabulary used correctly, not a textbook recital.

A relational database stores data in tables. A table is like a spreadsheet with a fixed list of typed columns. Each row is one fact, for example one order. A primary key is the column (or columns) that identify a row uniquely and are never NULL. A foreign key is a column that holds the primary key of a row in another table, for example orders.customer_id points to customers.id. That link is how data is joined at query time instead of being copied. A constraint is a rule the database enforces for you: NOT NULL, UNIQUE, CHECK, PRIMARY KEY and FOREIGN KEY. The big idea is that the database, not the application, guarantees the data stays valid, even when five different services write to it.

Likely follow-ups
  • Why not enforce rules only in the app? Another service, a script or a bug will bypass them. Database constraints are the last line of defence and are checked under concurrency, which app code cannot do reliably.
Primary key, unique key, foreign key, candidate key, composite key: explain each. Basic

What the interviewer is testing: precise terms, and the differences in NULL handling.

A candidate key is any minimal set of columns that could identify a row. You pick one as the primary key; the others become unique keys (UNIQUE constraints). A table has one primary key but can have many unique keys. A primary key can never be NULL. A unique key may allow NULL, and PostgreSQL and MySQL both allow several NULLs in a unique column because NULL is not equal to NULL (SQL Server is the odd one that allows only one). A composite key uses more than one column, for example (order_id, line_no) for order lines. A foreign key references a primary or unique key in another table, and it stops you inserting an orphan or deleting a parent that still has children, unless you choose ON DELETE CASCADE or SET NULL.

CREATE TABLE order_line (
  order_id BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  line_no  INT    NOT NULL,
  sku      TEXT   NOT NULL,
  qty      INT    NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, line_no)
);
Likely follow-ups
  • Does a foreign key create an index? Not in PostgreSQL, you must add it on the child column. MySQL InnoDB creates one automatically if none exists.
  • Is CHECK enforced in MySQL? Since 8.0.16. Before that it was parsed and ignored.
Surrogate key or natural key as the primary key? Intermediate

What the interviewer is testing: practical judgement about keys that change.

A natural key is real data such as an email, a country code or a passport number. A surrogate key is a made-up identifier with no business meaning, like a number from a sequence or a UUID. The trouble with natural keys is that "unique and never changes" is rarely true. People change emails, companies merge, and the key is copied into every child table and every index, so a change becomes a painful cascade. Most teams use a surrogate primary key and add a UNIQUE constraint on the natural key so the business rule is still enforced. Natural keys are fine for small stable lookup tables, for example ISO country codes, and for pure join tables where the pair of foreign keys is the key.

Likely follow-ups
  • Should the surrogate key be exposed in URLs? Be careful: sequential ids leak volume and invite guessing. Use a separate public id or a random id for external use.
UUID or auto-increment bigint for primary keys? What are the trade-offs? Senior

What the interviewer is testing: do you understand how the key's shape affects index and storage behaviour.

A bigint from a sequence is 8 bytes, sorted by time, and always inserts at the right edge of the B-tree, so inserts are fast and the index stays compact. Its weaknesses: it needs one central generator (hard across shards or regions), it leaks row counts, and clients cannot make ids before saving. A random UUID (version 4) is 16 bytes, can be made anywhere without coordination, and is safe to expose. But random values land all over the index. That causes page splits, poor cache hit rates and bigger indexes. In MySQL InnoDB this is worse because the primary key is the clustered index and every secondary index stores a copy of it, so a 16 byte key makes every index fatter. The modern answer is a time-ordered UUID (UUIDv7, standardised in RFC 9562 in 2024, or ULID): the first bits are a timestamp, so inserts are mostly sequential but ids are still generated anywhere. PostgreSQL 18 added a built-in uuidv7() function; on older versions generate it in the application. Store UUIDs in the native uuid type (PostgreSQL) or BINARY(16) (MySQL), never as 36 character text.

Likely follow-ups
  • Does the leak matter? Sequential ids allow enumeration attacks if you forget authorization checks; they are not a security measure either way.
  • Why do sequences have gaps? Rolled back transactions and cached sequence blocks consume numbers. Never rely on gap-free ids.
What is normalization? Explain 1NF, 2NF and 3NF with an example. Basic

What the interviewer is testing: can you explain it with a real table, not recite definitions.

Normalization means arranging tables so each fact is stored in exactly one place. That prevents update anomalies, where you change a customer's city in one row but not in another. Take one wide table orders(order_id, customer_name, customer_city, items, product_price). 1NF: every column holds one atomic value, and there are no repeating groups. A cell like "pen, book" in items breaks it; each item becomes its own row. 2NF: the table is in 1NF and every non-key column depends on the whole key, not just part of it. If the key is (order_id, product_id), then product_price depends only on product_id, so it moves to a product table. 3NF: no non-key column depends on another non-key column. customer_city depends on customer_name, not on the order, so customers get their own table. A memory line: every non-key column depends on "the key, the whole key, and nothing but the key".

Likely follow-ups
  • What anomalies does it prevent? Update (change in many places), insert (cannot add a product without an order), delete (deleting the last order loses the product).
What is BCNF, and how is it different from 3NF? Senior

What the interviewer is testing: whether you really understand functional dependencies, not only the 3NF slogan.

A functional dependency A to B means: if two rows have the same A, they must have the same B. BCNF (Boyce-Codd normal form) says: for every dependency X to Y in the table, X must be a key (a superkey). 3NF is a bit looser: it also allows X to Y when Y is part of some candidate key. The two differ only in unusual cases with overlapping candidate keys. Example: a table (student, course, teacher) where each teacher teaches only one course, and a student has one teacher per course. Candidate keys are (student, course) and (student, teacher). The dependency teacher to course holds, but teacher alone is not a key. This is 3NF (course is part of a key) but not BCNF. The fix is to split into (teacher, course) and (student, teacher). BCNF is always achievable, but the split may lose the ability to enforce some dependency with a plain constraint. In practice, teams aim for 3NF and know BCNF as the "stricter" version. 4NF and 5NF deal with multi-valued dependencies and are rarely asked.

Likely follow-ups
  • Is every BCNF table 3NF? Yes. BCNF is strictly stronger.
When would you deliberately denormalize? What does it cost? Intermediate

What the interviewer is testing: senior judgement: normalize by default, break the rules with a reason.

Denormalization means storing a fact more than once to make reads cheaper. Typical reasons: a read-heavy page that would otherwise join six tables, a reporting table that precomputes totals, a counter such as comment_count on a post, or a snapshot of data that must not change later, such as the unit price and address on an order (this is not really duplication, it is history). The cost is that you now own the job of keeping copies in sync. You can use a trigger, application code in the same transaction, or a background job that rebuilds the numbers. Each choice can drift. My rule: normalize first, measure, add an index, and only then denormalize the one hot path, with a way to rebuild the copy from the source of truth. Materialized views are a safer form of denormalization, because the database can refresh them from the real tables.

Likely follow-ups
  • Is it OK in OLAP? Yes. Star schemas for analytics are intentionally denormalized, because the data is loaded in batches and read heavily.
Common mistakes: denormalizing "for speed" before measuring; no job to detect and repair drift.
How do you model one-to-many, many-to-many and one-to-one relationships? Basic

What the interviewer is testing: basic modelling, and the join table.

One-to-many: put a foreign key on the "many" side. One customer has many orders, so orders.customer_id references customers. Many-to-many: you cannot put a list in one column, so you add a join table (also called link or bridge table) with two foreign keys. Students and courses become enrollment(student_id, course_id) with the pair as primary key. The join table is a good place for facts about the relationship itself, such as the enrolment date or grade. One-to-one: a foreign key that is also UNIQUE (or shares the primary key), for example user_profile.user_id. It is used to split rarely read or sensitive columns off a hot table, or to model an optional extension. Self references work too: employee.manager_id points to employee.id, giving a tree.

Likely follow-ups
  • How do you store a tree or hierarchy? Parent id plus recursive CTE for most cases. Closure tables or materialized paths when you read subtrees constantly.
Why use constraints (NOT NULL, CHECK, UNIQUE, FK) instead of validating in code? What are the costs? Intermediate

What the interviewer is testing: understanding that constraints solve concurrency problems that code cannot.

Application validation says "email is not taken" by running a SELECT first. Under concurrency two requests both see "not taken" and both insert. Only a UNIQUE constraint closes that race, because the database checks it atomically. The same goes for foreign keys (a parent deleted between check and insert) and for CHECK rules such as balance >= 0. Constraints also document the data and let the optimizer make better plans in some engines. The costs: a foreign key check does an index lookup on every insert and takes a light lock on the parent row, so very high write rates and bulk loads feel it. Some large systems (for example ones that shard) drop foreign keys on purpose and rely on application checks and cleanup jobs. That is a deliberate trade-off, not a default. The right pattern is: keep constraints as the safety net and let the app validate first for friendly error messages.

Likely follow-ups
  • How do you handle the unique violation in code? Catch the specific error (PostgreSQL 23505, MySQL 1062) and turn it into a "conflict" response, or use INSERT ... ON CONFLICT.

2. Joins, grouping, subqueries and set operations

In what order does a SELECT query logically run? Why can't I use a column alias in WHERE? Basic

What the interviewer is testing: logical query order, which explains many "why is this an error" questions.

The clauses run in this logical order: FROM and JOIN (build the row set), WHERE (filter rows), GROUP BY (make groups), HAVING (filter groups), SELECT (compute columns and aliases), DISTINCT, ORDER BY, then LIMIT or OFFSET. WHERE runs before SELECT, so an alias defined in SELECT does not exist yet. That is why WHERE total > 10 fails when total is an alias. ORDER BY runs after SELECT, so it can use aliases. Window functions are computed after HAVING and before DISTINCT and ORDER BY, which is why you cannot filter on ROW_NUMBER() in WHERE and must wrap it in a subquery or CTE. The optimizer may physically run the steps in another order (pushing filters down early), but the result must look as if this order was used. MySQL and PostgreSQL allow aliases in GROUP BY and ORDER BY as an extension.

Likely follow-ups
  • Where do I filter on an aggregate? In HAVING. Filter on plain columns in WHERE, because it removes rows before grouping and is cheaper.
Explain INNER, LEFT, RIGHT and FULL OUTER join with a small example. Basic

What the interviewer is testing: the most common SQL question. Use a tiny table you can say aloud.

A join combines rows from two tables where a condition matches. Take two small tables.

emp.nameemp.dept_iddept.iddept.name
Asha1010Eng
Ben1020Sales
Chen2030HR
DevNULL

INNER JOIN keeps only matched pairs: Asha-Eng, Ben-Eng, Chen-Sales. Dev (no dept) and HR (no employee) disappear. LEFT JOIN keeps every employee, and fills dept columns with NULL when there is no match: the three above plus Dev with NULLs. RIGHT JOIN is the mirror: every department, so HR appears with NULL employee columns. FULL OUTER JOIN keeps both sides: the matched pairs, Dev with NULLs, and HR with NULLs. MySQL has no FULL OUTER JOIN; you emulate it with a LEFT JOIN UNION a RIGHT JOIN. In practice most people write LEFT joins only and swap the table order instead of using RIGHT.

SELECT e.name, d.name AS dept
FROM emp e
LEFT JOIN dept d ON d.id = e.dept_id;   -- Asha Eng, Ben Eng, Chen Sales, Dev NULL
Likely follow-ups
  • What if a department matches many employees? Rows multiply: the result has one row per matching pair, which is why joining on a non-unique key can inflate SUM.
What is the difference between a condition in ON and in WHERE for a LEFT JOIN? Intermediate

What the interviewer is testing: a classic bug that silently turns a left join into an inner join.

ON decides which rows match. WHERE filters the final result afterwards. With an inner join the two give the same answer, so people forget the difference. With a LEFT JOIN, unmatched left rows get NULLs on the right. If you then write WHERE d.name = 'Eng', the NULL rows fail the test and vanish, so Dev is gone and your LEFT JOIN behaves like an INNER JOIN. If you want "all employees, and the dept name only when it is Eng", put the condition in ON: LEFT JOIN dept d ON d.id = e.dept_id AND d.name = 'Eng'. Dev and Chen still appear, with a NULL dept. The rule: conditions about the right table that must not drop left rows go in ON; conditions that really mean "only keep these rows" go in WHERE.

-- employees with NO department row: anti-join
SELECT e.name FROM emp e
LEFT JOIN dept d ON d.id = e.dept_id
WHERE d.id IS NULL;          -- Dev
What are CROSS JOIN, self join, NATURAL JOIN, semi join and anti join? Intermediate

What the interviewer is testing: breadth, and knowing which ones to avoid.

A CROSS JOIN pairs every row of one table with every row of the other (a Cartesian product): 3 rows times 4 rows gives 12. It is useful to generate combinations, such as every product with every day, and dangerous when you forget a join condition by accident. A self join joins a table to itself under two aliases, for example employee and manager from the same employee table. NATURAL JOIN joins on all columns with the same name; it breaks silently when someone adds a column, so avoid it. A semi join asks "does a match exist?" and returns each left row at most once. You write it with WHERE EXISTS (...). An anti join asks "does no match exist?" and is written with NOT EXISTS or a LEFT JOIN with IS NULL. SQL has no keywords for the last two; the optimizer recognises the patterns.

SELECT e.name, m.name AS manager
FROM employee e LEFT JOIN employee m ON m.id = e.manager_id;
How do GROUP BY and HAVING work? Where does WHERE fit? Basic

What the interviewer is testing: grouping rules and the WHERE versus HAVING split.

GROUP BY collapses rows that share the same values in the listed columns into one row per group, and aggregate functions (COUNT, SUM, AVG, MIN, MAX) compute one value per group. Every column in SELECT must be either in GROUP BY or inside an aggregate; PostgreSQL enforces this strictly, while MySQL with ONLY_FULL_GROUP_BY (default since 5.7) also does. WHERE filters individual rows before grouping. HAVING filters groups after aggregation, so it can use aggregates. Put everything that can be a row filter in WHERE, because it shrinks the data before the expensive grouping step.

-- customers who spent more than 100 in 2025, with at least 2 orders
SELECT customer_id, COUNT(*) AS n, SUM(amount) AS total
FROM orders
WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'   -- row filter
GROUP BY customer_id
HAVING SUM(amount) > 100 AND COUNT(*) >= 2;                     -- group filter
Likely follow-ups
  • Can HAVING be used without GROUP BY? Yes, the whole table is one group.
  • GROUPING SETS, ROLLUP, CUBE? They produce subtotals and grand totals in one query. GROUP BY ROLLUP(region, city) gives per-city, per-region and overall rows.
What is the difference between COUNT(*), COUNT(column) and COUNT(DISTINCT column)? Basic

What the interviewer is testing: NULL handling in aggregates, a favourite trap.

COUNT(*) counts rows, whatever the values. COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts the different non-NULL values. All other aggregates (SUM, AVG, MIN, MAX) also ignore NULLs, and on an empty set they return NULL, except COUNT which returns 0. So AVG(score) over scores 10, 20, NULL is 15, not 10, because the NULL row is skipped; if you want NULL treated as zero use AVG(COALESCE(score, 0)). COUNT(1) and COUNT(*) are identical in speed and meaning. A common bug: COUNT(o.id) after a LEFT JOIN correctly gives 0 for customers with no orders, while COUNT(*) would give 1 because the customer row itself is counted.

How does NULL behave in comparisons, logic, sorting and aggregates? Intermediate

What the interviewer is testing: three-valued logic, the source of many production bugs.

NULL means "unknown". Any comparison with NULL, even NULL = NULL or x <> NULL, gives UNKNOWN, not true or false. WHERE keeps only rows where the condition is TRUE, so UNKNOWN rows are dropped. You must write IS NULL and IS NOT NULL. For logic, UNKNOWN AND FALSE is FALSE, UNKNOWN OR TRUE is TRUE, and NOT UNKNOWN is UNKNOWN. A CHECK constraint passes on UNKNOWN, which surprises people: CHECK (age > 0) still allows NULL. For distinctness, GROUP BY, DISTINCT and UNION treat all NULLs as one group, even though NULL does not equal NULL. For sorting, PostgreSQL puts NULLs last in ascending order (use NULLS FIRST or LAST), MySQL puts them first. Handy tools: COALESCE(a, b, 0) returns the first non-NULL, NULLIF(a, 0) returns NULL when a is 0 (useful to avoid division by zero), and IS DISTINCT FROM (PostgreSQL) or <=> (MySQL) compares with NULL as a normal value. Oracle treats an empty string as NULL, which other databases do not.

SELECT 1 WHERE NULL = NULL;        -- no row
SELECT 1 WHERE NULL IS NULL;       -- one row
SELECT 10 / NULLIF(0, 0);          -- NULL, not an error
Why can NOT IN return no rows when a NULL is in the list? Intermediate

What the interviewer is testing: the most famous NULL trap, and whether you use NOT EXISTS.

x NOT IN (1, 2, NULL) expands to x <> 1 AND x <> 2 AND x <> NULL. The last part is UNKNOWN for every x, so the whole AND can never be TRUE. The result is no rows at all, even for x = 5. This bites when the subquery column is nullable, for example WHERE id NOT IN (SELECT manager_id FROM employee), and one employee has no manager. The safe pattern is NOT EXISTS, which only tests whether a matching row exists and is not confused by NULL. A LEFT JOIN with IS NULL also works. IN has no such problem, because a single TRUE is enough. Also, NOT EXISTS usually gets a good anti-join plan, while NOT IN can be planned badly in some engines.

-- safe: employees who are not anyone's manager
SELECT e.name FROM employee e
WHERE NOT EXISTS (SELECT 1 FROM employee x WHERE x.manager_id = e.id);
UNION versus UNION ALL; what do INTERSECT and EXCEPT do? Basic

What the interviewer is testing: set operations and the cost of removing duplicates.

Set operations combine the results of two queries that have the same number of columns with compatible types. UNION returns all rows from both and removes duplicates. UNION ALL keeps every row and is faster, because deduplication needs a sort or a hash. Use UNION ALL unless you really need to remove duplicates, or you know the two sides cannot overlap. INTERSECT returns rows that appear in both. EXCEPT (called MINUS in Oracle) returns rows in the first query that are not in the second. All three treat NULLs as equal for deduplication, unlike normal comparison. The column names come from the first query. ORDER BY applies once, at the very end, to the combined result. MySQL supports INTERSECT and EXCEPT only from 8.0.31; older versions need joins or EXISTS.

SELECT email FROM newsletter
EXCEPT
SELECT email FROM unsubscribed;      -- subscribers still active
What kinds of subqueries are there? What is a correlated subquery? Intermediate

What the interviewer is testing: do you know when a subquery is a scalar value, a list, a table, or row-by-row.

A scalar subquery returns one value and can be used where a value is expected: WHERE salary > (SELECT AVG(salary) FROM emp). A list subquery returns one column and is used with IN, ANY or ALL. A derived table (subquery in FROM) returns a table you can query or join. A correlated subquery refers to a column of the outer query, so conceptually it runs once for each outer row, for example "employees who earn more than the average of their own department". Optimizers often rewrite correlated subqueries into joins, so they are not always slow, but a correlated subquery in the SELECT list over a big table without an index on the correlation column is a classic performance bug. When it is slow, rewrite it as a join to a grouped derived table, or use a window function.

SELECT e.name, e.salary
FROM emp e
WHERE e.salary > (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);
EXISTS versus IN versus JOIN: which one and why? Intermediate

What the interviewer is testing: correctness (NULLs, duplicates) before speed.

All three can answer "customers who have at least one order", but they differ in two ways. Duplicates: a JOIN returns one row per match, so a customer with 5 orders appears 5 times, and you need DISTINCT. EXISTS and IN return each customer once, because they only ask whether a match exists. NULLs: IN is fine, NOT IN is not (see the NOT IN question), and NOT EXISTS is safe. About speed: modern planners (PostgreSQL, and MySQL 8 with its semi-join optimization) turn IN and EXISTS into the same semi-join plan, so choose by readability and correctness, then check EXPLAIN. EXISTS can stop at the first match. Use a JOIN when you need columns from the other table.

SELECT c.id, c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
What is a CTE (WITH clause)? Is it faster than a subquery? Explain recursive CTEs. Intermediate

What the interviewer is testing: readability tools versus performance claims, and recursion for trees.

A common table expression is a named temporary result you define with WITH name AS (...) at the top and use like a table in the main query. Its main value is readability: you break a big query into named steps. It is not automatically faster. In PostgreSQL before version 12 a CTE was always computed once and acted as an optimization fence (the planner could not push filters into it), which sometimes hurt. From PostgreSQL 12, a CTE used once and without side effects is inlined like a subquery, and you can force either behaviour with MATERIALIZED or NOT MATERIALIZED. MySQL 8 may merge or materialize it. A recursive CTE has a starting query (the anchor) and a recursive part that joins to the CTE itself, repeating until no new rows come. It walks hierarchies such as an org chart.

WITH RECURSIVE chain AS (
  SELECT id, name, manager_id, 1 AS depth FROM employee WHERE id = 7   -- anchor
  UNION ALL
  SELECT e.id, e.name, e.manager_id, c.depth + 1
  FROM employee e JOIN chain c ON e.id = c.manager_id                   -- step up
)
SELECT * FROM chain;       -- employee 7 and all managers above them
Likely follow-ups
  • What if the data has a cycle? The recursion never ends. Add a depth limit, or track visited ids. Both databases have a recursion limit setting (MySQL cte_max_recursion_depth, default 1000).
DISTINCT versus GROUP BY: any difference? And what about conditional aggregation with CASE? Intermediate

What the interviewer is testing: basic equivalence, and the pivot trick used in reports.

For plain "give me the unique values", SELECT DISTINCT a, b and GROUP BY a, b mean the same, and planners usually produce the same plan. Use GROUP BY when you also need aggregates, and DISTINCT when you just want unique rows. A warning: a DISTINCT added only to hide duplicates caused by a bad join is a smell. Fix the join. Conditional aggregation puts a CASE inside an aggregate, so one pass over the data produces several counts, which is also how you "pivot" rows into columns. PostgreSQL has the shorter COUNT(*) FILTER (WHERE ...).

SELECT customer_id,
       COUNT(*)                                        AS orders,
       SUM(CASE WHEN status = 'PAID' THEN 1 ELSE 0 END) AS paid,
       SUM(CASE WHEN status = 'REFUNDED' THEN amount ELSE 0 END) AS refunded
FROM orders GROUP BY customer_id;

3. Window functions

What is a window function, and how is it different from GROUP BY? Intermediate

What the interviewer is testing: do you know the key idea: calculate across related rows without collapsing them.

GROUP BY squeezes many rows into one row per group, so you lose the detail. A window function computes a value across a set of related rows (the "window") but keeps every row. You write it as function() OVER (PARTITION BY ... ORDER BY ... frame). PARTITION BY splits the rows into independent groups, like GROUP BY would, but without collapsing. ORDER BY sets the order inside each partition. The optional frame says which neighbouring rows are included. This makes things easy that were painful before: rank within a group, running totals, comparing a row to the previous row, percent of group total. Window functions run after WHERE, GROUP BY and HAVING, so you cannot filter on them directly; wrap the query in a CTE or subquery. MySQL supports them from 8.0.

ROW_NUMBER, RANK, DENSE_RANK and NTILE: what is the difference and when do you pick each? Intermediate

What the interviewer is testing: tie behaviour, which decides whether "top N" is correct.

All of them number rows inside a partition by the ORDER BY. ROW_NUMBER() gives unique numbers 1, 2, 3, ... and breaks ties arbitrarily, so use it when you want exactly N rows or when you want to pick one row per group (for example the latest). RANK() gives tied rows the same number and then skips: salaries 9000, 8000, 8000, 7000 get 1, 2, 2, 4. DENSE_RANK() does not skip: 1, 2, 2, 3. It is the right choice for "the second highest salary" when ties exist, because the second distinct salary is rank 2 in dense ranking. NTILE(4) splits the partition into four roughly equal buckets (quartiles). Because ROW_NUMBER is arbitrary on ties, add a second sort column such as the id to make results repeatable.

SELECT name, dept_id, salary,
       ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC, id) AS rn,
       RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC)     AS rnk,
       DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC)     AS drnk
FROM emp;
What do LAG and LEAD do? Give a practical example. Intermediate

What the interviewer is testing: comparing a row with its neighbour without a self join.

LAG(col, n, default) returns the value of col from n rows before the current row, in the window order. LEAD looks n rows ahead. Without a partition the whole result is one sequence; with PARTITION BY it restarts for each group, so the first row of each group has no previous row and gets NULL (or your default). Before window functions you needed a self join on id = id - 1, which breaks as soon as ids have gaps. Typical uses: month-over-month change, time between two events for the same user, detecting a status change, and finding the gap between consecutive rows.

-- month over month revenue change
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS change,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS pct
FROM monthly_revenue;
How do you compute a running total and a moving average? What is a window frame? Senior

What the interviewer is testing: understanding of frames and the ROWS versus RANGE trap.

An aggregate used with OVER and an ORDER BY becomes a running aggregate: SUM(amount) OVER (ORDER BY day) adds up everything from the start to the current row. What it sums is decided by the frame. When you give ORDER BY and no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE treats rows with the same ORDER BY value as peers, so two rows on the same day both show the total including both of them. That is often a surprise. ROWS frames count physical rows instead, so ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW gives a true row-by-row running total. A 7-day moving average over daily rows is AVG(x) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW). For a total that restarts, add PARTITION BY. Also notice LAST_VALUE with the default frame returns the current row, not the last row of the partition, because the frame stops at the current row; extend the frame to UNBOUNDED FOLLOWING.

SELECT day, amount,
  SUM(amount) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running,
  AVG(amount) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS avg7
FROM daily_sales;
Likely follow-ups
  • Percent of total? amount / SUM(amount) OVER (), with an empty OVER for the whole result.
  • Cost? A window sort per distinct OVER clause, so reuse the same window spec (a named WINDOW clause) where you can.
How do you filter on the result of a window function, for example "top 3 per group"? Intermediate

What the interviewer is testing: knowing the logical order and the wrapper pattern.

Window functions are computed in the SELECT step, which is after WHERE and HAVING. So WHERE rn <= 3 in the same query is an error. You compute the number in an inner query or CTE, then filter in the outer query. Some engines (Snowflake, BigQuery, Teradata) offer QUALIFY to filter directly, but PostgreSQL and MySQL do not. The pattern is always: inner query adds ROW_NUMBER(), outer query filters.

WITH ranked AS (
  SELECT e.*, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
  FROM emp e
)
SELECT * FROM ranked WHERE rn <= 3;

4. Classic SQL puzzles with worked solutions

These are the questions that appear again and again in interviews. For each one, explain the idea first, then write the query. State how you treat ties and NULLs before the interviewer asks.

Find the second highest salary. Basic

What the interviewer is testing: ties and the "no second salary" case, more than the query itself.

Work with salaries 9000, 8000, 8000, 7000. "Second highest" almost always means the second distinct value: 8000. If you do ORDER BY salary DESC LIMIT 1 OFFSET 1 you also get 8000 here, but only by luck of data; with 9000, 9000, 8000 it returns 9000, which is wrong. Three safe solutions:

-- 1) subquery on the maximum: simplest, returns NULL if there is no second value
SELECT MAX(salary) FROM emp
WHERE salary < (SELECT MAX(salary) FROM emp);

-- 2) distinct then offset: wrap in a subquery so the result is NULL, not "no rows"
SELECT (SELECT DISTINCT salary FROM emp ORDER BY salary DESC LIMIT 1 OFFSET 1) AS second_highest;

-- 3) DENSE_RANK: the one that generalises to the Nth, and to "per department"
SELECT DISTINCT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM emp
) t WHERE r = 2;

Option 3 extends to the Nth highest by changing the number, and to each department by adding PARTITION BY dept_id. Say aloud what should happen when there is no second value: return NULL or an empty result, and pick one on purpose.

Find duplicate rows, for example duplicate emails. Basic

What the interviewer is testing: GROUP BY with HAVING, and which "duplicate" you mean.

Group by the column that should be unique, and keep groups with more than one row. Suppose users holds (1, a@x.com), (2, b@x.com), (3, a@x.com). Grouping by email gives a@x.com with count 2.

-- which values are duplicated, and how many times
SELECT email, COUNT(*) AS n
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

-- see the full duplicate rows
SELECT u.*
FROM users u
JOIN (SELECT email FROM users GROUP BY email HAVING COUNT(*) > 1) d USING (email);

Ask the interviewer whether case or spaces matter: LOWER(TRIM(email)) may be the real key. After cleaning up, add a UNIQUE constraint (or a unique index on LOWER(email)) so it cannot happen again.

Delete duplicate rows but keep one of each. Intermediate

What the interviewer is testing: a safe way to pick the survivor, and care before deleting.

Decide which row survives (usually the lowest id, or the newest). Number the rows within each duplicate group, then delete everything numbered above 1. In PostgreSQL you can delete through a CTE. MySQL does not let you delete from a table you select from in the same statement in a simple subquery, but a join delete works.

-- PostgreSQL / MySQL 8: keep the lowest id per email
DELETE FROM users WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM users
  ) t WHERE rn > 1
);

-- MySQL, self join form
DELETE u1 FROM users u1
JOIN users u2 ON u1.email = u2.email AND u1.id > u2.id;

Practical steps: first run the SELECT version and look at it, take a backup or copy the doomed rows into a side table, run in a transaction, then add the unique constraint. On a huge table delete in batches to avoid long locks and a huge transaction log.

Top N rows per group: the 2 highest paid employees in each department. Intermediate

What the interviewer is testing: window plus wrapper, and your tie decision.

Use a window function numbered per department, then keep rows with number up to N. Decide the tie rule: ROW_NUMBER gives exactly 2 rows per department, DENSE_RANK gives everyone in the top 2 salary levels (maybe more than 2 people), RANK is in between. Sample data: Eng has 9000, 8000, 8000, 7000; Ops has 6000. With ROW_NUMBER, Eng returns 9000 and one of the 8000s (arbitrary unless you add a tie-breaker) and Ops returns 6000. With DENSE_RANK, Eng returns three people.

SELECT dept_id, name, salary FROM (
  SELECT dept_id, name, salary,
         DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS r
  FROM emp
) t WHERE r <= 2;

-- PostgreSQL alternative that can use an index well for few groups: LATERAL
SELECT d.id, x.*
FROM dept d
CROSS JOIN LATERAL (
  SELECT name, salary FROM emp e WHERE e.dept_id = d.id ORDER BY salary DESC LIMIT 2
) x;

The LATERAL form runs a tiny indexed LIMIT per department, which beats sorting the whole table when you have an index on (dept_id, salary). MySQL 8.0.14 and later also support LATERAL.

Gaps and islands: find ranges of consecutive numbers (or dates) in a column. Senior

What the interviewer is testing: the "value minus row number" trick, the best-known senior SQL puzzle.

An island is a run of consecutive values, a gap is a break between runs. Take ids 1, 2, 3, 5, 6, 9. Number the rows 1, 2, 3, 4, 5, 6. Now subtract: 1-1=0, 2-2=0, 3-3=0, 5-4=1, 6-5=1, 9-6=3. Rows in the same island get the same difference, because value and row number both grow by one together. A jump in the value changes the difference. So group by that difference and take MIN and MAX.

SELECT MIN(id) AS island_start, MAX(id) AS island_end, COUNT(*) AS len
FROM (
  SELECT id, id - ROW_NUMBER() OVER (ORDER BY id) AS grp
  FROM seq
) t
GROUP BY grp
ORDER BY island_start;
-- 1..3, 5..6, 9..9

-- the gaps: first missing id after each row, using LEAD
SELECT id + 1 AS gap_start, next_id - 1 AS gap_end FROM (
  SELECT id, LEAD(id) OVER (ORDER BY id) AS next_id FROM seq
) t WHERE next_id > id + 1;      -- 4..4, 7..8

For dates, subtract the row number as days: day - ROW_NUMBER() OVER (ORDER BY day) * INTERVAL '1 day' in PostgreSQL, or DATE_SUB(day, INTERVAL rn DAY) in MySQL. If duplicates are possible, use DISTINCT first or DENSE_RANK.

Find users who logged in on 3 or more consecutive days. Senior

What the interviewer is testing: applying gaps and islands to dates, and de-duplicating first.

First reduce to one row per user per day (a user can log in many times a day). Then use the same trick: subtract the row number, in days, from the date. A run of consecutive days gives the same result. Group by user and that result and keep runs of at least 3 days.

-- PostgreSQL
WITH d AS (
  SELECT DISTINCT user_id, login_at::date AS day FROM logins
), g AS (
  SELECT user_id, day,
         day - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
  FROM d
)
SELECT user_id, MIN(day) AS from_day, MAX(day) AS to_day, COUNT(*) AS streak
FROM g GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

-- LEAD/LAG alternative for exactly "3 in a row"
SELECT DISTINCT user_id FROM (
  SELECT user_id, day,
         LEAD(day, 2) OVER (PARTITION BY user_id ORDER BY day) AS day_plus_2
  FROM d
) t WHERE day_plus_2 = day + 2;

The LEAD version checks that the date two rows ahead is exactly two days later, which means there were no gaps in between (the data is one row per day). It is short for a fixed streak length; the island version handles any length and gives the start and end dates. In MySQL, use DATE_SUB(day, INTERVAL rn DAY) for the group key and DATEDIFF(day_plus_2, day) = 2 for the LEAD version.

Find customers who have never placed an order, and customers with more than one order. Basic

What the interviewer is testing: anti-join patterns and the NOT IN trap.

For "never ordered" there are three correct forms. Use whichever you can explain; all should give the same plan on a good optimizer.

-- 1) NOT EXISTS: clearest, NULL-safe
SELECT c.id, c.name FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- 2) LEFT JOIN anti-join
SELECT c.id, c.name FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- 3) NOT IN: only if orders.customer_id can never be NULL
SELECT id, name FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);

-- more than one order
SELECT customer_id FROM orders GROUP BY customer_id HAVING COUNT(*) > 1;

Make sure there is an index on orders(customer_id); without it the anti-join scans the orders table for every customer.

Employees who earn more than their manager; and each department's highest earner. Intermediate

What the interviewer is testing: self join and "max per group" patterns.

The first is a self join: join each employee to the row of their manager and compare salaries. The second has three standard solutions: a window function, a join on grouped maxima, or a correlated subquery. The window version needs one pass and returns all ties when you use RANK or DENSE_RANK.

SELECT e.name, e.salary, m.name AS manager, m.salary AS mgr_salary
FROM employee e JOIN employee m ON m.id = e.manager_id
WHERE e.salary > m.salary;

-- highest earner per department (ties included)
SELECT name, dept_id, salary FROM (
  SELECT name, dept_id, salary, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) r FROM employee
) t WHERE r = 1;

-- PostgreSQL only: DISTINCT ON picks one row per group, fast with an index
SELECT DISTINCT ON (dept_id) dept_id, name, salary
FROM employee ORDER BY dept_id, salary DESC;

Note the inner join drops employees who have no manager (NULL manager_id), which is what you want here.

How would you compute a median, a percentile, or pivot rows into columns? Senior

What the interviewer is testing: knowing the tools, and being honest about portability.

PostgreSQL has ordered-set aggregates: PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) is the median (interpolating between the two middle values), and PERCENTILE_DISC picks an actual value. MySQL has no built-in median. The portable method uses window functions: number the rows with ROW_NUMBER and count them with COUNT(*) OVER (), then average the middle one or two rows: WHERE rn IN (FLOOR((cnt+1)/2), CEIL((cnt+1)/2)). For pivoting, standard SQL has no PIVOT keyword in PostgreSQL or MySQL; use conditional aggregation (SUM(CASE WHEN month = 'Jan' THEN amt END) AS jan) which works everywhere. The column list must be known when you write the query. If it is dynamic, build the SQL string in application code, or do the pivot in the application or reporting layer.

5. Indexes

What is an index, and how does a B-tree index make a query fast? Basic

What the interviewer is testing: the structure, and the cost in writes and space.

Without an index, finding rows with WHERE email = 'a@x.com' means reading every row (a full table scan). An index is a separate, sorted structure over one or more columns, with pointers back to the rows, like the index at the back of a book. The default type is a B-tree (really a B+tree): a shallow, wide tree of pages. The root page points to a few hundred child pages, each covering a key range, down to leaf pages that hold the sorted keys and row pointers. Leaves are linked in order. Because each page holds hundreds of keys, even a table of a hundred million rows needs only about 4 page reads to find one key, which is O(log n) with a huge base. Since the leaves are sorted, a B-tree also serves range queries (BETWEEN, >), ORDER BY without a sort, and prefix matches like LIKE 'abc%'. The price: every INSERT, UPDATE of an indexed column, and DELETE must also update the index, and indexes take disk and memory.

Likely follow-ups
  • Why B-tree and not a binary tree? Disk reads whole pages, so you want a tree that is wide and shallow, with each node a full page.
  • Does a unique constraint create an index? Yes, in both databases a UNIQUE or PRIMARY KEY is backed by a unique index.
What is a clustered index? How does InnoDB differ from PostgreSQL here? Senior

What the interviewer is testing: storage differences that change how you choose keys.

In MySQL InnoDB the table itself is stored as a B-tree ordered by the primary key. This is the clustered index: its leaf pages contain the full rows. Every secondary index stores its keys plus the primary key value, so a lookup by a secondary index finds the primary key and then does a second lookup in the clustered tree. That is why a long or random primary key (like a text or UUID v4) makes all indexes bigger and slower. In PostgreSQL the table is an unordered "heap" and every index, including the primary key, points to a row location (a tuple id). There is no automatic clustering. The CLUSTER command rewrites the table once in index order but does not keep it that way. Consequences: in InnoDB, range scans on the primary key are very fast and insert order matters; in PostgreSQL an UPDATE writes a new row version in a new place, so indexes may need new entries as well (unless it is a HOT update that stays on the same page and touches no indexed column). SQL Server also uses a clustered index, similar to InnoDB.

Likely follow-ups
  • What if an InnoDB table has no primary key? It picks the first non-null unique index, or creates a hidden 6 byte row id. Always define a primary key explicitly.
What is a composite index and the leftmost prefix rule? How do you choose column order? Intermediate

What the interviewer is testing: the most useful practical index rule.

A composite index covers several columns, such as (customer_id, status, created_at). It is sorted by the first column, then by the second inside equal first values, and so on, like a phone book sorted by last name then first name. So the index can help any query that fixes a leftmost prefix of the columns: customer_id; customer_id, status; or all three. It cannot efficiently help a query that only filters on status or created_at, because those values are scattered across the tree. A range condition stops the use of later columns for seeking: with customer_id = 5 AND status > 'A' AND created_at > ... the index seeks on the first two but must scan on the third. Column order rule of thumb: equality columns first (most selective or most commonly filtered first), then the range column, then columns used for ORDER BY. The index also serves WHERE customer_id = 5 ORDER BY status without a sort, because within one customer the rows are already sorted by status.

Likely follow-ups
  • Do I need a separate index on customer_id? No, the composite already covers it. A single-column index that is the prefix of another is redundant.
  • Can the engine skip the first column? MySQL 8.0.13 has "skip scan" and Oracle has similar, PostgreSQL 18 added a skip scan for B-trees; do not depend on it for large cardinality.
What is a covering index (index-only scan)? Intermediate

What the interviewer is testing: avoiding the second lookup into the table.

Normally an index lookup finds matching entries and then, for each one, fetches the row from the table to read other columns. That second step is random IO and often the bulk of the cost. If the index itself contains every column the query needs (in SELECT, WHERE and ORDER BY), the engine can answer from the index alone: a covering index, shown as "Index Only Scan" in PostgreSQL and "Using index" in MySQL EXPLAIN. PostgreSQL 11 added INCLUDE columns, which are stored in the leaf but not used for ordering, so you can add payload columns cheaply: CREATE INDEX ON orders (customer_id) INCLUDE (total). In MySQL you add the extra columns as normal key columns. In PostgreSQL index-only scans also depend on the visibility map, which VACUUM maintains; on a table with many recent changes the engine still visits the table to check visibility. Do not cover everything: wider indexes cost more on writes.

CREATE INDEX idx_orders_cust_cover ON orders (customer_id, created_at) INCLUDE (total);
SELECT created_at, total FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;
What are selectivity and cardinality, and why does the planner sometimes ignore my index? Intermediate

What the interviewer is testing: that an index is a cost decision, not a command.

Cardinality is the number of distinct values in a column. Selectivity is how small a share of the table a condition picks: email = '...' matches one row in a million (very selective), is_active = true matches 95% (not selective). An index lookup costs a random page read per matching row. If a condition matches a large fraction of the table (roughly more than 5 to 20%, depending on settings and table layout) reading the whole table sequentially is cheaper, so the planner chooses a sequential scan, and it is right. That is why an index on a boolean or a status with three values often goes unused. The planner decides using statistics (row counts and value histograms, refreshed by ANALYZE in PostgreSQL and ANALYZE TABLE in MySQL). A bad statistics estimate leads to a wrong plan, so when a good index is ignored, first check that statistics are fresh. Low-selectivity columns become useful as the leading column in a composite index, or in a partial index that covers only the rare value.

Name the common reasons an index is not used. Intermediate

What the interviewer is testing: this is the checklist that fixes most "slow query" tickets.

  • Function or expression on the column: WHERE DATE(created_at) = '2026-01-01' or LOWER(email) = ... cannot use a plain index on the column. Rewrite as a range (created_at >= '2026-01-01' AND created_at < '2026-01-02') or create an expression index (CREATE INDEX ON users (LOWER(email)); MySQL 8.0.13 and later supports functional indexes).
  • Type mismatch and implicit casts: comparing a varchar column to a number (WHERE phone = 12345) makes MySQL cast every row. Different collations or character sets across joined columns do the same.
  • Leading wildcard: LIKE '%abc' cannot seek a B-tree. Use a trigram index (pg_trgm) or full-text search.
  • Leftmost prefix broken: the query skips the first column of a composite index.
  • OR across different columns: may fall back to a scan. Rewrite as UNION ALL or use separate indexes that the planner can combine.
  • Low selectivity: the scan really is cheaper (see previous question).
  • Stale statistics, or a tiny table: on a small table the planner is right to scan.
  • NOT, <> and negative conditions: they match most rows, so scans win.
  • Leading arithmetic: WHERE price * 2 > 100 instead of price > 50.
EXPLAIN SELECT * FROM users WHERE LOWER(email) = 'a@x.com';   -- Seq Scan
CREATE INDEX idx_users_lower_email ON users (LOWER(email));     -- now an Index Scan
Common mistakes: forcing the index with hints before finding out why the planner avoided it; adding an index without checking the plan afterwards.
Why not index every column? What do indexes cost? Basic

What the interviewer is testing: that indexes are a trade-off.

Each index is a copy of data that must be kept in sync. An INSERT writes the row and one entry in every index. A DELETE or an UPDATE of an indexed column changes them too. So ten indexes mean roughly eleven writes per insert, more disk, more memory pressure on the buffer cache, longer backups, and more lock and WAL traffic. Extra indexes also give the planner more choices. The aim is the smallest set of indexes that serves your real queries. Look for unused indexes (PostgreSQL pg_stat_user_indexes with idx_scan = 0, MySQL sys.schema_unused_indexes) and redundant ones that are the prefix of another. A read-mostly table can afford more indexes than a write-heavy log table.

What are partial, expression and unique-partial indexes, and when are they useful? Senior

What the interviewer is testing: targeted indexing and enforcing rules with indexes.

A partial index (PostgreSQL; MySQL has no direct equivalent) covers only rows that match a condition, so it is small and cheap to maintain. If 2% of orders are "PENDING" and your worker only reads those, CREATE INDEX ON orders (created_at) WHERE status = 'PENDING' is tiny and fast, and the query must repeat the condition to use it. An expression index indexes a computed value such as LOWER(email). A unique partial index enforces a rule on a subset: "an email must be unique among rows that are not soft-deleted" is CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL. This is the standard answer to the soft-delete plus unique email problem. In MySQL you can get the same effect with a generated column that is NULL for deleted rows plus a unique index on it, because unique indexes allow multiple NULLs.

How do you make LIKE '%word%' and case-insensitive search fast? Intermediate

What the interviewer is testing: knowing B-trees cannot do infix search, and the alternatives.

A B-tree is sorted by the beginning of the string, so LIKE 'abc%' can seek, while LIKE '%abc%' has no starting point and scans the table. Options: for PostgreSQL, install the pg_trgm extension and create a GIN or GiST index on the column with gin_trgm_ops; it indexes three-letter pieces, and it also speeds up regular expressions and similarity search. For word search, use full-text search (tsvector with a GIN index in PostgreSQL, FULLTEXT index with MATCH ... AGAINST in MySQL). For case-insensitive equality, use an expression index on LOWER(col), a case-insensitive collation (MySQL's default collations are case-insensitive), or the citext type. If search is a core feature with ranking, typo tolerance and facets, move it to a search engine and treat the database as the source of truth.

6. Reading plans and tuning queries

How do you read an EXPLAIN plan? What do you look at first? Intermediate

What the interviewer is testing: a repeatable method, not memorised node names.

EXPLAIN shows the plan the optimizer chose, as a tree. Data flows from the leaves (scans) up to the root. Each node shows an estimated cost and estimated row count. EXPLAIN ANALYZE (PostgreSQL, and MySQL 8.0.18 and later) actually runs the query and adds real time and real row counts per node. Careful: it really executes, so wrap data-changing statements in a transaction and roll back. In PostgreSQL add BUFFERS to see page reads. My routine is: (1) find the node with the largest actual time; (2) compare estimated rows with actual rows: a big gap (say 100 versus 500,000) means bad statistics or a correlated filter, and that usually explains a bad plan; (3) look at scan types: a Seq Scan on a big table with a selective filter wants an index; (4) look at join types and for a nested loop with a huge outer side; (5) look for Sort nodes spilling to disk, and for "Rows Removed by Filter" being huge, which means you read much and keep little; (6) check loops, since time shown is per loop.

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, SUM(o.total) FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'PAID' GROUP BY c.name ORDER BY 2 DESC LIMIT 20;
What scan types and join algorithms does a planner choose from, and when is each right? Senior

What the interviewer is testing: inner workings that explain plan changes.

Scans. Seq Scan reads the whole table: best when you need a large share of it. Index Scan walks the index and fetches each row: best for few rows. Index Only Scan skips the table fetch when the index covers the query. Bitmap Heap Scan (PostgreSQL) collects the matching row locations from one or several indexes first, sorts them by page, and reads pages once: it sits between index scan and seq scan and can combine several indexes with AND or OR. Joins. Nested loop: for each row of the outer side, look up matches on the inner side. Excellent when the outer side is small and the inner side has an index; terrible when both are large and unindexed. Hash join: build an in-memory hash table from the smaller input, then probe it with the other. Good for large unsorted inputs and equality joins; it needs memory (work_mem) and spills to disk if it does not fit. Merge join: both inputs sorted on the join key, then walked together: good when they are already sorted by an index. MySQL used only nested loop variants before 8.0.18, which added hash join. The planner estimates all of them and picks the cheapest. When the estimate is wrong, a wrong algorithm gets picked, such as a nested loop over millions of rows.

A query was fast yesterday and slow today with no code change. What could have happened? Senior

What the interviewer is testing: systematic thinking about plan instability.

The query text is the same, so look at what the planner or the data did. (1) Plan flip: statistics were refreshed (autovacuum analyze ran) or the table grew past a threshold, and the planner switched from an index nested loop to a hash join or a sequential scan. Compare the old and new plan; in PostgreSQL auto_explain logs slow plans, and tools like pg_stat_statements show the change over time. (2) Parameter-sensitive plans: a prepared statement cached a plan for one value (a rare customer) and reuses it for another (a huge customer). PostgreSQL switches between custom and generic plans after 5 executions; it can choose a bad generic plan. (3) Data skew: a new tenant with 10 million rows. (4) Bloat or missing vacuum: a table with lots of dead rows reads slowly, and an index that is mostly empty pages. (5) Cache cold: restart or failover empties the buffer cache. (6) Locks or contention: the query is waiting, not working. Check pg_stat_activity or SHOW PROCESSLIST. (7) A blocked long transaction preventing vacuum. Fix by refreshing statistics, adding extended statistics for correlated columns, rewriting the query, or adding the missing index.

A query is slow. What is your step-by-step approach? Intermediate

What the interviewer is testing: measure first, change one thing, verify.

  1. Reproduce and measure. Get the real query with real parameters, and a timing. Is it slow always or only sometimes? Check the slow query log or pg_stat_statements to see total time (frequency times duration), not only the single slowest call.
  2. Look at the plan with EXPLAIN ANALYZE on production-sized data. A plan on a 100-row dev database tells you nothing.
  3. Fix the biggest cost. Usually: missing or unusable index, a non-sargable condition, selecting too many columns or rows, a join that multiplies rows, or an estimate error that needs fresh statistics.
  4. Reduce the work. Select only the needed columns, filter early, add LIMIT, replace OFFSET by keyset, aggregate in the database not in the app.
  5. Look beyond the query. N+1 patterns in the app, too many round trips, lock waits, an undersized connection pool, a hot row.
  6. Verify and guard. Re-run the plan and timing, test that writes did not slow down, and add a monitor.

Only after this consider caching, a materialized view, denormalization, or hardware. Stating "I would measure before touching anything" is half the answer.

What is the N+1 query problem and how do you fix it? Basic

What the interviewer is testing: the most common ORM performance bug, found in code review.

You run one query to load N parents (say 100 orders), then loop and run one more query per parent to load its children (the customer or the items): 1 + 100 queries. Each query is fast, but 101 round trips each costing a millisecond or two plus parse and lock overhead make the page slow, and it grows with the data. It usually appears with lazy loading in ORMs such as Hibernate or JPA, where touching order.getCustomer() silently fires a query. Fixes: fetch together with a JOIN (JOIN FETCH in JPQL, @EntityGraph); batch loading, where the ORM loads children for many parents in one WHERE id IN (...) query (Hibernate @BatchSize, default_batch_fetch_size); or load the children yourself with one extra IN query and group them in memory. Beware of a fetch join with a collection plus pagination: it multiplies rows and the ORM paginates in memory. Detect N+1 with query counting in tests, logging of SQL in development, and APM traces showing the same statement repeated.

-- N+1: one for the list, then one per row
SELECT * FROM orders LIMIT 100;
SELECT * FROM customers WHERE id = ?;   -- 100 times

-- fixed: 2 queries total
SELECT * FROM orders LIMIT 100;
SELECT * FROM customers WHERE id IN (?, ?, ... );
OFFSET pagination versus keyset (seek) pagination: why is OFFSET slow on deep pages? Intermediate

What the interviewer is testing: an API design question that hides a performance and correctness issue.

LIMIT 20 OFFSET 100000 makes the database produce 100,020 rows in order and throw away the first 100,000. Cost grows linearly with the page number. It is also unstable: if rows are inserted or deleted while a user pages, they see duplicates or skip rows. Keyset pagination remembers the last row seen and asks for rows after it: WHERE (created_at, id) < (:last_created, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on (created_at, id) the engine seeks straight to that spot, so page 5000 costs the same as page 1, and results are stable. The sort key must be unique, so add the id as a tie-breaker. Limits: you cannot jump to "page 37", only next and previous, and sorting by many columns is harder. For UIs that need page numbers, use OFFSET for shallow pages and cap the depth, or offer search filters. Return an opaque cursor token to clients.

CREATE INDEX idx_posts_created_id ON posts (created_at DESC, id DESC);
SELECT * FROM posts
WHERE (created_at, id) < ('2026-03-01 10:00:00', 9876)
ORDER BY created_at DESC, id DESC LIMIT 20;
Why is SELECT COUNT(*) slow on a big table, and what can you do? Intermediate

What the interviewer is testing: MVCC consequences, and practical alternatives.

Because of MVCC each transaction may see a different set of row versions, so the engine cannot keep one exact row count and just read it. It must walk a table or an index and check which rows are visible to you. PostgreSQL does this with a sequential or index-only scan; InnoDB scans the smallest secondary index. For tens of millions of rows this takes seconds. (MyISAM, the old MySQL engine, kept an exact count, which is the origin of the folklore that "COUNT(*) is instant in MySQL".) Options: do you need an exact number? An estimate from statistics (reltuples in pg_class, or EXPLAIN row estimates) is nearly free. Keep a counter table updated in the same transaction (but a single hot counter row becomes a lock bottleneck; shard it into several rows). Count with a narrow filter that an index covers. For UI "total results", show "1000+" and cap with SELECT COUNT(*) FROM (SELECT 1 FROM t WHERE ... LIMIT 1001) x. Use a materialized view or a periodic job for dashboards.

How do you insert, update or delete millions of rows efficiently and safely? Intermediate

What the interviewer is testing: batching, transaction size and lock impact.

Insert: never one statement per row with a commit each. Use multi-row INSERT ... VALUES (...), (...) in batches of 500 to 5,000, JDBC batching with rewriteBatchedStatements=true on MySQL or reWriteBatchedInserts=true on PostgreSQL, or the bulk loaders: PostgreSQL COPY, MySQL LOAD DATA INFILE. For huge initial loads, load first and create the indexes afterwards, and disable nothing that protects integrity without a plan to re-check it. Update and delete: one giant statement holds locks and fills the transaction log, replicas lag behind, and a failure rolls back everything. Work in batches by primary key range, committing each batch, with a small pause:

-- repeat until 0 rows affected
DELETE FROM events WHERE id IN (
  SELECT id FROM events WHERE created_at < now() - interval '90 days' ORDER BY id LIMIT 5000
);

On PostgreSQL deleting many rows leaves dead space that VACUUM reuses but does not return to the operating system. If you drop most of the table, copy the keepers into a new table and swap, or use partitions and drop the old partition, which is instant. Upserts: INSERT ... ON CONFLICT DO UPDATE (PostgreSQL), INSERT ... ON DUPLICATE KEY UPDATE (MySQL), and MERGE (PostgreSQL 15+).

Name quick query-writing habits that avoid performance trouble. Basic

What the interviewer is testing: daily hygiene.

  • Avoid SELECT *: it reads and ships unneeded columns, can break covering indexes, and breaks code when columns are added.
  • Filter early and keep conditions index-friendly (no function on the column).
  • Always LIMIT exploratory queries on large tables.
  • Use parameters (prepared statements), which are safe against injection and let the server reuse plans.
  • Avoid OR over different columns and DISTINCT as a patch for a bad join.
  • Use UNION ALL rather than UNION when duplicates are impossible.
  • Prefer EXISTS to COUNT(*) > 0 to test presence.
  • Keep transactions short and do not call remote services inside them.
  • Index foreign keys used in joins.
  • Fetch in batches with keyset pagination rather than loading everything into memory.

7. Transactions, isolation, MVCC and locking

Explain ACID with an example. Basic

What the interviewer is testing: each letter explained with something concrete, and what the database does to deliver it.

Use a money transfer: take 100 from account A and add 100 to B. Atomicity: both updates happen or neither; if the second fails, the first is rolled back. The database does this with a log of undo information. Consistency: the transaction moves the data from one valid state to another, so rules such as "balance is never negative" and foreign keys hold. The database enforces constraints; your own business rules are your job. Isolation: two transfers running at the same time do not corrupt each other. How strongly depends on the isolation level. Durability: once COMMIT returns, the change survives a crash or power loss. The database writes the change to a sequential log (WAL in PostgreSQL, redo log in InnoDB) and flushes it to disk before saying committed; data pages can be written later and are rebuilt from the log after a crash. Note that ACID's "C" is different from the "C" in the CAP theorem.

BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- or ROLLBACK on any error
Likely follow-ups
  • Can durability be traded away? Yes: synchronous_commit = off (PostgreSQL) or innodb_flush_log_at_trx_commit = 2 (MySQL) is faster but can lose the last moments on a crash. The data stays consistent, just slightly old.
  • Is a single statement a transaction? Yes, in autocommit mode each statement is its own transaction.
What is the write-ahead log and why does commit not write the data pages? Senior

What the interviewer is testing: the crash-safety mechanism behind durability and replication.

Changing data pages in place at random places on disk for every commit would be slow, and a crash in the middle would leave a half-written page. Instead the database first appends a small description of the change to a log, in order, and flushes it with one sequential write. That is the commit point. Dirty data pages stay in memory and are written to disk later in the background (checkpoints). After a crash, the database replays the log from the last checkpoint to rebuild any changes that had not reached the data files, and undoes the uncommitted ones. The same log also drives replication: replicas receive and replay it (PostgreSQL streaming replication ships WAL; MySQL has the binary log at the server level on top of InnoDB's redo log). It also explains why commit latency depends on log flush speed, why group commit batches many transactions into one flush, and why huge transactions create a lot of log and replica lag.

What are the four SQL isolation levels, and which anomalies does each allow? Intermediate

What the interviewer is testing: the classic table, and knowing that real databases deviate from it.

Isolation controls what a transaction sees of other transactions' work. Three classic problems: a dirty read (you read data another transaction has not committed and may roll back), a non-repeatable read (you read a row twice and a committed change from someone else makes it differ), and a phantom read (you run the same range query twice and new rows appear). Show a non-repeatable read and a phantom read as a timeline. Intermediate

What the interviewer is testing: clear explanation of anomalies without hand waving.

Two sessions, T1 and T2. A non-repeatable read: T1 reads Asha's balance (100). T2 changes it to 40 and commits. T1 reads again and sees 40. The same row has different values inside one transaction, which breaks logic like "check, then use the value". A phantom: T1 counts orders with status = 'NEW' and gets 5. T2 inserts a new NEW order and commits. T1 counts again and gets 6. A row appeared that was not in the first result. Repeatable Read prevents the first by keeping a snapshot (or read locks) for the transaction. Preventing phantoms needs range protection (gap locks in InnoDB), a snapshot (PostgreSQL), or Serializable.

How does MVCC work? How is it different in PostgreSQL and InnoDB? Senior

What the interviewer is testing: one of the best "how does it work inside" database questions.

Multi-version concurrency control keeps several versions of a row so that readers see a consistent snapshot without blocking writers, and writers do not block readers. Each version is stamped with the transaction that created it and (when removed) the one that deleted it. A reading transaction gets a snapshot of "which transactions had committed at my start" and shows only the versions visible under it. In PostgreSQL an UPDATE writes a whole new row version in the table (the heap) and marks the old one dead. Old versions stay in the table until VACUUM removes them. If vacuum cannot keep up, or a long-running transaction holds an old snapshot, dead rows pile up: "table bloat". In MySQL InnoDB an UPDATE changes the row in place and writes the old value to the undo log; readers reconstruct older versions by following undo records, and a purge thread cleans the undo log. A very long transaction makes the undo log grow and old reads slow. Either way: long transactions are bad for MVCC databases. Under MVCC, writers still block writers touching the same row, because two transactions cannot both create the next version.

Likely follow-ups
  • What is bloat and how do you spot it? Table or index size far above live data size. Cause: long transactions or heavy update traffic with autovacuum too slow. Fix: tune autovacuum, kill idle-in-transaction sessions.
  • What is transaction ID wraparound? PostgreSQL transaction ids are 32 bit and reused; vacuum must freeze old rows in time, or the server stops accepting writes to protect data. Monitor autovacuum.
What kinds of locks does a database use? Row locks, table locks, gap locks, shared and exclusive. Intermediate

What the interviewer is testing: knowing what blocks what.

A shared (S) lock lets many readers in but blocks writers. An exclusive (X) lock is taken by a writer and blocks everyone else who wants to lock the same thing. Normal plain reads under MVCC take no row locks at all. UPDATE, DELETE and SELECT ... FOR UPDATE take exclusive row locks held until the transaction ends. Table locks come from DDL such as ALTER TABLE, LOCK TABLE, and in PostgreSQL from various commands, with several modes. An ACCESS EXCLUSIVE lock in PostgreSQL blocks even plain SELECTs. InnoDB also uses gap locks (the space between index records) and next-key locks (record plus the gap before it) at Repeatable Read to prevent phantoms; they can block inserts in a range unexpectedly. Intention locks mark at table level that rows inside are locked. PostgreSQL has also advisory locks, which your application can take with its own meaning. A waiting statement queues behind the lock, and anything that arrives after it for a conflicting mode queues too: a DDL waiting for a lock blocks all later queries on that table, which is how a harmless-looking migration freezes production.

What is a deadlock, how does the database handle it, and how do you prevent it? Intermediate

What the interviewer is testing: the cause, the symptom, and practical prevention.

A deadlock is a cycle of waiting: T1 holds a lock on row A and wants row B, while T2 holds B and wants A. Neither can ever continue. The database detects the cycle (InnoDB at once; PostgreSQL after deadlock_timeout, 1 second by default), picks one transaction as the victim, rolls it back, and returns an error (MySQL error 1213, PostgreSQL SQLSTATE 40P01). The other proceeds. Your code must be ready to retry the whole transaction. To prevent them: (1) lock rows in a consistent order everywhere, for example always lower account id first; (2) keep transactions short and do slow work, such as HTTP calls, outside them; (3) update in bulk in a defined order (ORDER BY id with FOR UPDATE); (4) use the lowest suitable isolation level; (5) index the columns you filter on, since a missing index makes InnoDB lock many more rows; (6) avoid mixing foreign key checks and big updates in unpredictable order. Deadlocks are not a bug in the database; they are an expected outcome of concurrent access that you handle with retries and ordering.

Likely follow-ups
  • How do you find the cause? InnoDB: SHOW ENGINE INNODB STATUS (latest deadlock section). PostgreSQL: the server log prints both statements when log_lock_waits and deadlock logging are on.
Optimistic versus pessimistic locking: explain both and when to pick which. Intermediate

What the interviewer is testing: a core design choice for any "two users edit the same thing" problem.

Pessimistic locking assumes conflicts are likely, so it locks the row first: SELECT ... FOR UPDATE, then change it, then commit. Others wait. It is simple and safe, but it holds locks while you work and reduces throughput, and it must not span user think time (never hold a lock while a user stares at a form). Optimistic locking assumes conflicts are rare: read the row with a version number, do your work with no lock, and when saving, check that the version is unchanged: UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?. If zero rows were updated, someone else got there first, so you reload and retry or tell the user. JPA's @Version does this. Optimistic is great for web apps with low contention and long think time. Under heavy contention on a hot row it causes many retries and wasted work, and pessimistic locking (or an atomic update like SET balance = balance - 5) is better.

UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 7 AND version = 12;     -- 0 rows updated means conflict, retry
What is a lost update and how do you prevent it? Intermediate

What the interviewer is testing: a read-modify-write race, and the ladder of fixes.

Two requests both read a counter of 10. Each adds 1 in application code and writes 11. The final value is 11 instead of 12: one update was lost. This is the classic read-modify-write race and it happens at Read Committed. Fixes from simplest to heaviest: (1) atomic update in SQL: UPDATE counter SET n = n + 1 WHERE id = 1. The database applies it to the latest row, with a row lock, so nothing is lost. (2) Pessimistic lock: SELECT ... FOR UPDATE, then update. (3) Optimistic version check with retry. (4) Higher isolation: PostgreSQL Repeatable Read aborts the second writer with a serialization error that you retry; MySQL's Repeatable Read does not detect it for a plain read-then-write, so you still need a lock or an atomic statement. (5) Compare-and-set in a single statement: UPDATE ... WHERE id = 1 AND n = 10.

What is write skew? Give an example and the fixes. Senior

What the interviewer is testing: the anomaly that snapshot isolation does not stop.

Two transactions read overlapping data, make decisions from it, then write to different rows, so no row conflict is detected. Example: a hospital rule says at least one doctor must be on call. Alice and Bob are both on call. Each checks SELECT COUNT(*) FROM on_call WHERE on_call = true and sees 2, so each thinks it is safe to leave, and each sets only their own row to false. Both commit. Now nobody is on call. Neither transaction overwrote the other's row, so snapshot isolation (PostgreSQL Repeatable Read, MySQL's snapshot reads) happily allows it. Similar cases: double-booking a meeting room, claiming the same username when check-and-insert are separate, spending from two wallets with a combined limit. Fixes: (1) use Serializable isolation (PostgreSQL SSI detects the dangerous pattern and aborts one transaction; retry); (2) lock the rows you read with SELECT ... FOR UPDATE on the on_call rows, so the second transaction waits and then sees the first one's result; (3) materialize the conflict: add a row to lock (a "shift" row) or a counter; (4) add a constraint that makes the invalid state impossible, for example a unique or exclusion constraint (PostgreSQL EXCLUDE USING gist to prevent overlapping time ranges).

What does SELECT ... FOR UPDATE do? What are NOWAIT and SKIP LOCKED? Intermediate

What the interviewer is testing: explicit row locking and the job queue pattern.

SELECT ... FOR UPDATE reads rows and locks them exclusively until the transaction ends, so other writers and other FOR UPDATE readers wait. Use it for "read, decide, then write" flows where a lost update or write skew would hurt, such as taking the next seat or deducting stock. Variants: FOR SHARE (a read lock that blocks writers only), NOWAIT (fail immediately with an error instead of waiting), and SKIP LOCKED (silently skip rows another transaction has locked). SKIP LOCKED makes the database a simple work queue: many workers run the same query and each gets different rows without blocking each other. It exists in PostgreSQL 9.5+ and MySQL 8.0+. Note that the result is intentionally inconsistent (you skip some rows), so use it for queues, not for reports. Make sure the filter and the ORDER BY use an index so the lock only touches the rows you take.

BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'PENDING'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;       -- each worker gets a different 10 jobs
-- process, then:
UPDATE jobs SET status = 'DONE' WHERE id IN (...);
COMMIT;
Likely follow-ups
  • What happens if the worker crashes? The transaction rolls back and the locks are released, so the jobs become visible again. That gives at-least-once processing, so jobs must be idempotent.
How do you prevent duplicate rows under concurrency (insert if not exists)? Intermediate

What the interviewer is testing: check-then-insert races, and the right primitive.

The naive code is SELECT ... WHERE email = ?, and if nothing is found, INSERT. Two requests run the select at the same time, both find nothing, both insert. No isolation level below Serializable stops this, because there is no row to lock yet. The reliable fix is a UNIQUE constraint on the business key, then let the database arbitrate: INSERT ... ON CONFLICT (email) DO NOTHING (PostgreSQL), INSERT IGNORE or INSERT ... ON DUPLICATE KEY UPDATE (MySQL). Check the affected row count to see whether you inserted or not. For idempotent APIs, store an idempotency key with a unique constraint and return the earlier result on a repeat. Be careful with INSERT IGNORE in MySQL, which swallows other errors too (such as data truncation) as warnings. For upserts that update, ON CONFLICT DO UPDATE SET n = t.n + 1 is an atomic way to increment-or-create.

INSERT INTO page_view (page_id, day, views) VALUES (7, CURRENT_DATE, 1)
ON CONFLICT (page_id, day) DO UPDATE SET views = page_view.views + 1;
How long should a transaction be? What are the dangers of long ones, and "idle in transaction"? Senior

What the interviewer is testing: practical transaction hygiene that prevents outages.

A transaction should be as short as possible and contain only database work. A long one holds its locks (blocking others), keeps an old MVCC snapshot (so vacuum or purge cannot clean, causing bloat and growing undo), holds a connection from the pool, and increases the chance of deadlocks and conflicts. The classic outage: application code opens a transaction, calls a slow external HTTP service, and while waiting the connection sits "idle in transaction" holding locks. Under load the pool runs dry. Prevention: do remote calls before or after the transaction, not inside; set idle_in_transaction_session_timeout and statement_timeout (PostgreSQL) or innodb_lock_wait_timeout and max_execution_time (MySQL); and in Spring or JPA watch for @Transactional on methods that call other services. Use savepoints (SAVEPOINT x; ... ROLLBACK TO x) when part of a transaction can fail and be retried. In PostgreSQL an error aborts the whole transaction until you roll back, unless you use a savepoint.

How do you keep data consistent across two databases or services? What are 2PC and sagas? Senior

What the interviewer is testing: that ACID stops at one database, and the practical patterns.

A normal transaction cannot span two separate databases or a database and a message broker. Two-phase commit (2PC, XA) asks every participant to "prepare", and if all agree, tells them to commit. It gives atomicity, but it is slow, holds locks during the protocol, and blocks if the coordinator dies at the wrong moment, so it is rare in microservices. The usual answer is a saga: a series of local transactions, each with a compensating action (refund, release stock) that runs if a later step fails. You get eventual consistency, not isolation, so other users can see intermediate states. The common building block is the transactional outbox: in the same local transaction that changes your tables, insert an event row into an outbox table. A separate process reads the outbox and publishes to Kafka or a queue, retrying until it succeeds (at least once), and consumers de-duplicate. This avoids the "saved to the database but the message was lost" problem without 2PC.

8. Scaling: partitioning, sharding, replication and connection pools

Your database is getting slow as traffic grows. In what order do you scale it? Senior

What the interviewer is testing: that you reach for cheap fixes before expensive architecture.

I climb a ladder, because each step adds complexity and new failure modes. (1) Measure and fix queries: the top few queries by total time, missing indexes, N+1 patterns, and unneeded work. This alone often gives 10x. (2) Right-size the server and settings: memory for the buffer cache, connection pool size. (3) Cache hot reads in the application or in Redis, accepting some staleness. (4) Read replicas for read-heavy traffic and reports: easy to add, but you inherit replica lag. (5) Partition big tables (by time, usually) so queries and maintenance touch less data. (6) Archive or delete old data. (7) Shard (split data across servers by a key) only when one primary cannot take the write load or hold the data. Sharding breaks joins and transactions across shards, so it is the last resort. Alternatively move a workload to a better-suited store (search engine for text, time-series database for metrics). A modern managed database can scale vertically to very large machines, so many companies never need to shard.

What is table partitioning, and when does it help? Intermediate

What the interviewer is testing: partitioning is inside one database; sharding is across servers. Do you know the difference and the benefits?

Partitioning splits one logical table into smaller physical pieces on the same server, by a rule: range (one partition per month), list (per region), or hash (spread evenly). You query the parent table as usual. Benefits: partition pruning, where a query with a filter on the partition key only touches the matching partitions; cheap data removal, since dropping an old partition is instant and does not leave dead rows, unlike a huge DELETE; and faster maintenance on smaller pieces (vacuum, index rebuild). It does not make every query faster: a query that does not filter by the partition key scans all partitions, and can be slower. Rules to remember: in both PostgreSQL (declarative partitioning since version 10) and MySQL, a primary key or unique constraint must include the partition key, so global uniqueness on just id is not possible. MySQL InnoDB partitioned tables cannot have foreign keys. Create future partitions ahead of time (with a scheduled job or pg_partman), or inserts fail. Good fit: time-series, logs, events, with retention by date.

CREATE TABLE events (
  id BIGINT GENERATED ALWAYS AS IDENTITY,
  created_at TIMESTAMPTZ NOT NULL,
  payload JSONB,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);
CREATE TABLE events_2026_11 PARTITION OF events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
DROP TABLE events_2025_01;     -- retention in milliseconds
What is sharding? How do you choose a shard key, and what gets harder? Senior

What the interviewer is testing: design judgement about the costs.

Sharding (horizontal partitioning across servers) splits the data so that each server, a shard, holds a slice and handles its own reads and writes. A router (in the application, a proxy, or the database such as Vitess or Citus) sends each query to the right shard using the shard key. Strategies: hash of the key (even spread, range queries are scattered), range (easy range queries, risk of hot shards, such as all new data on the newest range), or a directory lookup table (flexible, but the lookup is a dependency). A good key has high cardinality, spreads load evenly, and is present in most queries, so each query touches one shard. For a multi-tenant SaaS, tenant_id is the natural key; for a social app, user_id. What gets harder: cross-shard joins and transactions (you need sagas or 2PC), global unique ids and constraints, aggregate queries that fan out to all shards, schema changes on many shards, and resharding when shards fill up (consistent hashing or many small virtual shards from day one make it easier). Celebrity or big-tenant "hot keys" can overload one shard. Only shard when you have proof that one primary cannot keep up.

How does database replication work, and what is the difference between synchronous and asynchronous? Intermediate

What the interviewer is testing: the model, and its consistency versus availability trade-offs.

In primary-replica (leader-follower) replication, all writes go to the primary. It records every change in a log (PostgreSQL WAL, MySQL binary log), and the replicas read that log and apply the same changes in the same order. Replicas are used to serve read traffic, run reports, and act as a hot standby for failover. Asynchronous (the default in both): the primary commits and replies without waiting for replicas. It is fast, but if the primary dies right then, the latest commits may not have reached any replica and are lost on failover, and replicas can lag. Synchronous: the primary waits until at least one replica has the log (PostgreSQL synchronous_commit with synchronous_standby_names; MySQL semi-sync or Group Replication) before confirming. No acknowledged commit is lost, but each commit pays a network round trip, and if the replica is unreachable, writes stall unless you configure fallback. Many setups use one synchronous standby and the rest asynchronous. Replication copies bad writes too: it is not a backup. Multi-primary setups need conflict resolution and are much harder.

What is replica lag, and how do you handle "I saved it but it's not there" (read-your-writes)? Senior

What the interviewer is testing: eventual consistency in a real feature.

Lag is the delay between a commit on the primary and its visibility on a replica. It is usually milliseconds, but a big transaction, a long-running query on the replica that blocks replay (PostgreSQL recovery conflicts), a slow disk, or a traffic burst can make it seconds or minutes. The user-visible bug: a user submits a form (write goes to the primary), the next page reads from a replica that has not caught up, and their change seems lost. Fixes: (1) read from the primary for a short time after that user writes (for example 5 seconds, tracked in a cookie or session); (2) route reads that need freshness (the user's own profile, the order just placed) to the primary and everything else to replicas; (3) causal tokens: return the log position (PostgreSQL LSN, MySQL GTID) at commit, and have the replica read wait until it has replayed past it, or fall back to the primary; (4) after a write, return the data from the write response instead of re-reading; (5) monitor lag (pg_stat_replication, MySQL Seconds_Behind_Source) and take lagging replicas out of rotation. Also remember monotonic reads: two reads going to two different replicas can show data going backwards in time; pinning a user to one replica fixes that.

What happens when the primary fails? What should an application developer know about failover? Senior

What the interviewer is testing: application behaviour during an infrastructure event (the operations detail is out of scope).

A monitoring tool or a managed service (RDS, Cloud SQL, Patroni, MySQL InnoDB Cluster) detects the failure, promotes a replica to primary, and moves a DNS name or virtual IP. This takes seconds to a couple of minutes. What the developer controls: connections break, so the pool must detect dead connections (validation query or keepalive) and reconnect; in-flight transactions are lost and commits whose result you never saw are in an unknown state, so retries must be idempotent (idempotency keys, unique constraints); use sensible connect and query timeouts and retry with backoff and jitter; cache DNS carefully (Java's DNS cache can pin the old address). With asynchronous replication a few acknowledged commits may be missing after promotion. Treat the database as something that goes away briefly, and test it with a failover drill. The specialist depth (quorum, fencing, split-brain protection, backup and point-in-time recovery) belongs to database operations.

Why do we use connection pooling, and how do you size a pool? Intermediate

What the interviewer is testing: that more connections does not mean more throughput.

Opening a database connection is expensive: a TCP connection, TLS, authentication, and in PostgreSQL a whole server process per connection that uses memory (several MB). A pool keeps a fixed set of open connections and lends one to each request for the duration of a transaction, then takes it back. This removes connect cost and caps the load on the database. Sizing is counter-intuitive: a database can only do real work on about as many queries at once as it has CPU cores and disks; extra concurrent queries just compete and slow everyone down. A common starting point is (CPU cores * 2) + number of disks for the whole database, which is often 10 to 30 connections, not hundreds. HikariCP, the usual Java pool, defaults to 10 and its authors recommend keeping it small. Remember that total connections = pool size times application instances, so 50 pods with a pool of 20 means 1000 connections, which can exceed the database limit (max_connections is 100 by default in PostgreSQL, 151 in MySQL). Use an external pooler such as PgBouncer (or RDS Proxy) when you have many instances. In PgBouncer's transaction mode, session state does not persist between transactions, so session-level features (SET, advisory locks, some prepared statement settings, LISTEN) can break.

Likely follow-ups
  • Requests time out waiting for a connection. Do you raise the pool size? First find who is holding connections: slow queries, transactions held open during remote calls, or a connection leak (not closing). Raising the size often makes it worse.
Explain the CAP theorem and eventual consistency in simple terms. Where do SQL and NoSQL databases sit? Senior

What the interviewer is testing: can you use CAP correctly, without the common slogans.

CAP says that when a network partition happens (servers cannot talk), a distributed system must choose: stay consistent (refuse some requests so nobody sees stale or conflicting data) or stay available (answer every request, possibly with stale data). You do not choose "two of three" freely, because partitions will happen; the real choice is C or A during a partition. A single-node database is not in this game at all. A primary with asynchronous replicas that you read from is effectively choosing availability and lets you read stale data. A system that needs a quorum, for example synchronous replication or Spanner, chooses consistency and may refuse writes when a majority is unreachable. Eventual consistency means that if writes stop, all replicas converge to the same value, but in the meantime reads may differ. Cassandra and DynamoDB let you tune this per request (read or write to one, a quorum, or all). The more useful framework than CAP is PACELC: even without a partition you trade latency for consistency. A good answer says: banks and inventory need strong consistency on writes; feeds, likes and caches can accept eventual.

9. Modelling, data types, migrations and choosing a database

SQL or NoSQL: how do you decide? Intermediate

What the interviewer is testing: trade-offs based on access patterns, not fashion.

Start from the data and the questions you will ask. A relational database is the best default: flexible ad-hoc queries and joins, strong consistency, transactions across tables, constraints, and mature tools. It fits most business systems (orders, payments, accounts, inventory) where data is related and correctness matters. Choose a NoSQL store when a specific need dominates: huge write volume or data size that one server cannot hold with simple, known access patterns (Cassandra, DynamoDB); flexible document-shaped data read as a whole (MongoDB); very fast key lookups and caching (Redis); relationships as the main question, such as "friends of friends" (graph); or search (Elasticsearch). NoSQL gives scale and flexibility by giving up something: usually joins, multi-row transactions, or ad-hoc queries, so you must design the data around your queries and may need to duplicate data. Modern PostgreSQL with JSONB covers many "schemaless" needs, and NewSQL databases (CockroachDB, Spanner, TiDB) give SQL with horizontal scale. A senior answer also admits that many systems use both (polyglot persistence): SQL as the source of truth, Redis for cache, Elasticsearch for search, fed by events.

Describe the four main NoSQL families and when you would choose each. Intermediate

What the interviewer is testing: breadth, with a concrete product and use case for each.

Key-value (Redis, DynamoDB, Memcached): you give a key, you get a value. Extremely fast and simple. Use for caches, sessions, rate limits, counters, feature flags. You cannot query by the value contents without extra structures. Document (MongoDB, Couchbase, Firestore): stores JSON-like documents with nested data, so one document holds an order and its lines. Good for content, catalogs and profiles where you read and write a whole aggregate, and where fields vary. Joins across documents are weak, and you must watch for unbounded growth of a document. Wide-column (Cassandra, HBase, Bigtable, ScyllaDB): rows are grouped by a partition key and sorted inside by a clustering key; data is written to an append-friendly structure (LSM tree), so writes are very fast and the cluster scales linearly. Use for time series, event logs, messaging history, with queries known in advance (one table per query, no joins). Graph (Neo4j, Amazon Neptune): nodes and edges are first class, and traversals such as "friends of friends within 3 hops" or fraud rings are cheap, where a relational database would need many self joins. Use when relationships are the question: recommendations, social networks, identity graphs, network topology. For most CRUD apps, none of these is needed.

B-tree storage versus LSM-tree storage: what is the trade-off? Senior

What the interviewer is testing: why different databases behave differently under write load.

A B-tree engine (PostgreSQL, InnoDB, SQL Server) updates pages in place. Reads are fast and predictable: a short walk down the tree. Writes touch random pages, and keep a write-ahead log for safety. An LSM tree (Cassandra, RocksDB, LevelDB, HBase) buffers writes in memory (a memtable), appends to a log, and periodically flushes sorted immutable files (SSTables) to disk, which are merged in the background (compaction). Writes are sequential and therefore very fast; reads may have to check several files, so Bloom filters help skip files; and compaction uses background IO and can cause latency spikes and extra disk writes (write amplification). Rule of thumb: B-trees favour read-heavy and mixed workloads with range queries and transactions; LSM trees favour write-heavy, append-mostly workloads at a large scale. You do not need to tune either as an application developer, but you should know why Cassandra does fast writes and why random UUID keys hurt an InnoDB table.

How do you change a schema on a live system without downtime? Explain expand and contract. Senior

What the interviewer is testing: safe, multi-step change thinking with old and new code running at the same time.

During a rolling deploy, old and new versions of the app run together against one database, so every schema change must work with both. The expand and contract (parallel change) pattern does it in separate deploys. Expand: add the new column, table or index in a backwards-compatible way (nullable, no breaking default). Migrate: deploy code that writes to both old and new (dual write), then backfill old rows in small batches, and verify. Switch: deploy code that reads the new column. Contract: stop writing the old one, then drop it in a later release. Example, renaming name to full_name: never run RENAME COLUMN directly, because old code breaks the moment it runs. Instead add full_name, dual write, backfill, switch reads, drop name. Keep each step small and reversible, run migrations separately from the deploy, and set a lock_timeout so a migration that cannot get its lock gives up instead of queueing behind a long query and blocking all traffic.

Which schema changes are dangerous on a big table in PostgreSQL and MySQL, and what are the safe versions? Senior

What the interviewer is testing: concrete knowledge of table rewrites and lock levels.

PostgreSQL. ADD COLUMN with a constant default is instant since version 11 (before that it rewrote the table); a volatile default (like random()) still rewrites. CREATE INDEX blocks writes, so use CREATE INDEX CONCURRENTLY, which takes longer, cannot run inside a transaction, and can leave an invalid index to drop if it fails. ALTER COLUMN TYPE usually rewrites the table. Adding NOT NULL scans the table under a strong lock; the safe path is ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT (which does not block writes), then SET NOT NULL (fast since PostgreSQL 12 because it trusts the validated check). A foreign key is added the same way: NOT VALID then VALIDATE. Always set SET lock_timeout = '3s' and retry. MySQL 8. ALGORITHM=INSTANT makes adding a column near-instant (8.0.12, and at any position from 8.0.29). Many index and column changes run INPLACE without blocking writes, but changing a column type usually copies the table. For heavy cases people use online schema change tools: gh-ost or pt-online-schema-change (copy to a shadow table, replay changes, swap). In MySQL, a waiting DDL needs a metadata lock, and one long open transaction can queue it and then block everything behind it.

SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN note text;                        -- instant, constant default
CREATE INDEX CONCURRENTLY idx_orders_cust ON orders (customer_id);
ALTER TABLE orders ADD CONSTRAINT orders_cust_fk
  FOREIGN KEY (customer_id) REFERENCES customers(id) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_cust_fk;           -- scans, but allows writes
Soft delete or hard delete? What goes wrong with soft deletes? Intermediate

What the interviewer is testing: awareness of the hidden costs of a popular pattern.

A soft delete sets a flag or a timestamp (deleted_at) instead of removing the row. It allows undo, auditing, and keeps references intact. The costs: (1) every query must remember WHERE deleted_at IS NULL; one miss leaks deleted data. ORM filters (Hibernate @Where or @SQLRestriction) and views help. (2) Unique constraints break: a user deletes an account and re-registers with the same email. Fix with a partial unique index on active rows only (PostgreSQL) or a generated column (MySQL). (3) Tables grow and indexes carry dead weight; archive or purge after a retention period. (4) Foreign keys and cascades do not apply, so children of a soft-deleted parent stay visible unless you handle them. (5) Privacy laws (GDPR "right to erasure") may require real deletion, so soft delete alone is not enough. Alternatives: move deleted rows to an archive table (a trigger or app code), use an append-only history or audit table, or rely on backups and point-in-time recovery for rare restores. I use soft delete for entities users expect to restore, hard delete with an audit log for the rest.

CREATE UNIQUE INDEX uq_users_email_active ON users (email) WHERE deleted_at IS NULL;
How should you store money? Basic

What the interviewer is testing: the floating point trap, and currency awareness.

Never use FLOAT or DOUBLE. They store binary fractions, so 0.1 + 0.2 gives 0.30000000000000004, and sums drift by cents. Use an exact type: NUMERIC(19,4) or DECIMAL(19,4) (PostgreSQL and MySQL), or store integer minor units (cents) in a BIGINT, which is fast and exact, with the currency code in a separate column (amount_minor = 1999, currency = 'USD'). Different currencies have different decimal places (JPY has 0, KWD has 3), so keep the exponent per currency. Store the currency with every amount and never add amounts of different currencies. Decide the rounding rule explicitly (banker's rounding or half-up) and where it applies, such as at line level or at invoice level, and keep the same rule everywhere. In Java use BigDecimal with a scale and a RoundingMode, never double. PostgreSQL's money type is tied to locale settings, so most teams avoid it. When you divide, such as splitting 100.00 into three parts, allocate the remainder cents explicitly.

How do you store dates and times correctly? Time zones, DATETIME versus TIMESTAMP? Intermediate

What the interviewer is testing: time zone discipline, which prevents a whole class of bugs.

The safe default: store instants (when something happened) in UTC, and convert to the user's time zone only for display. In PostgreSQL use timestamptz. Despite its name it does not store a zone: it converts the input to UTC on the way in and converts to the session time zone on the way out. Plain timestamp (without time zone) stores whatever wall-clock text you give it with no meaning, so avoid it for real events. In MySQL, TIMESTAMP is stored as UTC and converted using the session time zone, but its range ends in January 2038; DATETIME has no time zone conversion and a range up to year 9999. Many teams use DATETIME and a strict rule that the application writes UTC. For future local events, such as "the meeting is at 9:00 in Berlin", store the local time plus the zone id (Europe/Berlin), because the UTC offset can change when governments change daylight saving rules. Use date-only types for birthdays and billing dates. Set the database and application servers to UTC, and test the daylight saving changeover days. In Java prefer Instant and OffsetDateTime over the old java.util.Date.

When is it right to store JSON in a relational database? What are the pitfalls? Intermediate

What the interviewer is testing: balance: flexibility versus losing relational guarantees.

JSON columns are a good fit for data that is truly variable or only read as a whole: user preferences, third-party webhook payloads, form answers, audit snapshots, sparse attributes. They are a bad fit for data you filter, join, sort or constrain often, because you lose type checks, foreign keys, easy statistics, and simple indexes. In PostgreSQL use jsonb (binary, supports indexing, with a GIN index for containment queries such as payload @> '{"status":"paid"}'), not json (plain text that is reparsed). In MySQL use the JSON type, and index a value by creating a generated column over JSON_EXTRACT (or a functional index, 8.0.13+), and use multi-valued indexes for arrays (8.0.17+). Pitfalls: updating one key rewrites the whole value (large documents cause heavy writes; in PostgreSQL big values go to TOAST storage); no schema means old and new formats mix; and the query planner has poor statistics on JSON contents. A good compromise is to promote the fields you query (status, customer_id) to real columns and keep the long tail in JSON.

CREATE INDEX idx_events_payload ON events USING GIN (payload);
SELECT id FROM events WHERE payload @> '{"type":"refund"}';
SELECT payload->>'sku' AS sku FROM events WHERE (payload->>'qty')::int > 5;
How do you prevent SQL injection? Is an ORM enough? Basic

What the interviewer is testing: parameterised queries, and the cases where they do not apply.

SQL injection happens when user input is glued into the SQL text, so input like ' OR '1'='1 changes the meaning of the query. The fix is parameterised queries (prepared statements): the SQL text with placeholders is sent separately from the values, so the database never treats a value as code. In JDBC use PreparedStatement with ?; in JPA use named parameters, not string concatenation. An ORM protects you only when you use its parameter binding; building JPQL or native queries with string concatenation is still injectable. Things that cannot be parameters: table names, column names and ORDER BY direction. For those, check the input against an allowlist (map "price" to a known column). Also: give the application's database user the minimum rights, never admin; do not show raw database errors to users; and validate input types. Escaping by hand is fragile and not recommended.

// unsafe
stmt.executeQuery("SELECT * FROM users WHERE name = '" + name + "'");
// safe
PreparedStatement ps = con.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, name);
What are views and materialized views? When would you use each? Intermediate

What the interviewer is testing: a stored query versus stored results.

A view is a saved query with a name. It stores no data; each time you select from it the database expands it into the underlying query. Use it to hide complexity, give a stable interface when tables change, and restrict access to columns or rows. A view does not make anything faster by itself. A materialized view stores the query result physically, so reading is fast, but the data is as old as the last refresh. PostgreSQL has them built in (REFRESH MATERIALIZED VIEW; CONCURRENTLY avoids blocking readers but needs a unique index). MySQL has no native materialized views; you build a summary table and refresh it with a scheduled job or events. Use them for dashboards and expensive aggregates where staleness is acceptable. Updatable views (inserting through a view) work only for simple views and are rarely used.

Stored procedures and triggers versus logic in the application: what is your view? Senior

What the interviewer is testing: engineering judgement with reasons, not a religious answer.

Stored procedures keep the logic next to the data, save network round trips for multi-step work, and can be fast for heavy batch jobs. The downsides are real: they are harder to version, test, review and debug than application code, they tie you to one database vendor's language, they run on your most expensive and hardest-to-scale server, and the logic is split in two places. Triggers are even more hidden: they fire invisibly and can surprise people with side effects, slow bulk loads, and cascading triggers. My rule: put data integrity in the database (constraints, and sometimes a trigger for audit columns such as updated_at or a history table), and put business logic in the application, where it has tests and a deploy pipeline. Exceptions: bulk data processing close to the data, and legacy systems where it already lives. With ORMs, remember they hide SQL: use them for simple CRUD, and write explicit SQL for reports and hot paths, and always look at the SQL they generate.

How do you keep history or an audit trail of changes to rows? Intermediate

What the interviewer is testing: modelling time, a frequent real requirement.

There are four common ways. (1) Audit table filled by trigger or app code: every change inserts a row (table, row id, old and new values as JSON, user, time) into an append-only table. Simple and flexible, but triggers must be maintained. (2) History table (temporal table): keep the current row in the main table and past versions in a _history table, each with valid_from and valid_to. SQL Server and MariaDB have system-versioned tables built in; PostgreSQL and MySQL need triggers or an extension. (3) Versioned rows: never update, only insert a new version with a version number or validity range, and query "the current row". Good when history is part of the business (price lists, contracts). (4) Event sourcing: store the events as the source of truth and derive the current state. Powerful but a big architectural commitment. Also decide on retention and on privacy (personal data in history tables must also be erasable). Change data capture (Debezium reading the log) is another way to get a full change feed without triggers.

How do you design a multi-tenant database? Senior

What the interviewer is testing: isolation versus cost trade-offs, and data leakage risk.

Three models. Shared tables with a tenant_id column: cheapest and simplest to operate, scales to many small tenants, but one missed WHERE tenant_id = ? leaks data and a noisy tenant affects the others. Reduce the risk by putting tenant_id first in the indexes and primary keys, using ORM filters, and in PostgreSQL by enabling row-level security policies so the database itself enforces it. Schema per tenant: better isolation and easy per-tenant restore, but migrations run N times and thousands of schemas strain the catalog. Database per tenant: strongest isolation, simple per-tenant backup, location and compliance control, but highest cost and most operational work. Choose by tenant count, size variation and compliance. A common hybrid is shared tables for small tenants and dedicated databases for big or regulated ones. The tenant id is also a natural shard key later.

What timeouts and retry rules should an application use when talking to a database? Senior

What the interviewer is testing: resilience: bounded waiting and safe retries.

Every wait must have a limit, or one slow query can exhaust the pool and take the whole service down. Set: a connection acquisition timeout on the pool (a few seconds, fail fast), a connect timeout, a statement or query timeout (PostgreSQL statement_timeout, MySQL max_execution_time for selects), a lock wait timeout (lock_timeout; InnoDB innodb_lock_wait_timeout, default 50 seconds, which is long), and an idle in transaction timeout. Make timeouts shorter than the caller's timeout so work is not done for a request nobody waits for. Retries: retry only errors that are transient and safe: deadlock victim, serialization failure, a lost connection, a failover. Retry the whole transaction, with exponential backoff and jitter, and a small maximum. Do not retry blindly after a commit whose result is unknown unless the operation is idempotent. Never retry a validation or constraint error. Add a circuit breaker so a sick database is not hammered further.

Practical data type choices: VARCHAR versus TEXT, ENUM, booleans, and keeping tables small. Basic

What the interviewer is testing: sensible defaults, and engine-specific facts.

In PostgreSQL text and varchar(n) perform the same; the length limit only adds a check, so use text and add a CHECK if you need a limit. In MySQL, VARCHAR(n) has a row size limit (65,535 bytes per row), and sorting and temporary tables use the declared size, so choose reasonable lengths; use utf8mb4 (not the old three-byte utf8) so emoji and all characters work. For fixed sets of values, a lookup table with a foreign key is the most flexible; native ENUM types are compact, but changing the list needs a schema change (in PostgreSQL adding a value is easy, removing is not). A CHECK (status IN (...)) on a text column is a simple compromise. Use native BOOLEAN, not a char. Use the smallest suitable integer (INT goes up to about 2.1 billion; busy tables should use BIGINT from the start, because migrating an exhausted INT key later is painful). Narrow rows mean more rows per page, more cache hits, and faster scans, so keep rarely used big columns (blobs, long text) in separate tables or in object storage with only a URL in the database.

How do you combine a cache with the database, and what can go wrong? Intermediate

What the interviewer is testing: consistency issues when a second copy of the data exists.

The common pattern is cache-aside: read from the cache; on a miss read the database, then put the result in the cache with a time to live (TTL). On a write, update the database and then delete (not update) the cache key, so the next read reloads fresh data. Deleting is safer than updating, because two concurrent updates could write their results to the cache in the wrong order. Risks: a race where a reader loads the old value from the database just before a write, and then stores that old value in the cache after the writer's delete, leaving stale data until the TTL expires (so keep TTLs short enough for your tolerance, and consider versioned keys); a cache stampede when a hot key expires and thousands of requests hit the database at once (use request coalescing or a lock per key, jittered TTLs, or refresh ahead); and cache penetration from requests for keys that do not exist (cache a negative result briefly). The database stays the source of truth, and the system should still work, only slower, if the cache is empty.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview. It shows you stay calm under pressure and work from evidence.

A query that was fast for a year is now slow because the table grew. What do you do? Senior

What the interviewer is testing: a measured approach to plan changes caused by data growth.

Situation: an orders list endpoint went from 20 ms to 6 seconds. Nothing was deployed. The table grew from 2 million to 80 million rows.

Check first: get the exact slow statement from the slow query log or pg_stat_statements, then run EXPLAIN (ANALYZE, BUFFERS) on production-sized data. Look for a Seq Scan or an index scan with huge "Rows Removed by Filter", a Sort spilling to disk, and a gap between estimated and actual rows. Check the last time statistics were refreshed.

Steps:

  1. If the filter is selective and has no usable index, add one shaped for the query: equality columns first, then the range or sort column, for example (customer_id, created_at DESC). Build it with CREATE INDEX CONCURRENTLY (PostgreSQL) or online DDL (MySQL).
  2. If estimates are wrong, run ANALYZE, and consider extended statistics for correlated columns.
  3. If the query uses deep OFFSET, switch to keyset pagination.
  4. If it is an unbounded report, cut columns, add a time limit, or precompute with a materialized view or summary table.
  5. Re-run the plan and compare timings. Check that insert speed did not drop much.

Prevent: load-test with production-sized data, watch the top queries by total time, set alerts on p95 latency, partition or archive time-series tables, and review plans for any new query on a table above a few million rows.

Deadlock errors started appearing in production after a release. How do you find and fix them? Senior

What the interviewer is testing: diagnosing from logs, then fixing the ordering, plus retry as a safety net.

Situation: about 1% of checkout requests fail with "Deadlock found when trying to get lock" (MySQL 1213) or SQLSTATE 40P01 (PostgreSQL).

Check first: get the two statements involved. MySQL: SHOW ENGINE INNODB STATUS, section "LATEST DETECTED DEADLOCK". PostgreSQL: the server log prints both queries and the lock wait graph. Find which code paths run them, and what changed in the release.

Typical cause: one code path updates the order row and then the stock rows, and another updates stock rows and then the order. Or a batch loops over item ids in the order the user sent them, so two carts with items (A, B) and (B, A) lock in opposite orders.

Steps:

  1. Make every path lock in one agreed order, for example sort the item ids before updating, or run SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE first.
  2. Shorten the transaction: remove remote calls and extra reads from inside it.
  3. Check missing indexes: in InnoDB an update without a usable index locks many rows, which makes deadlocks far more likely.
  4. Add a bounded retry (two or three tries with jitter) around the whole transaction for deadlock and serialization errors.

Prevent: a code convention for lock order, a concurrency test that fires two crossed requests, and an alert on the deadlock counter.

Two admins edit the same product and one admin's change silently disappears. How do you fix it? Intermediate

What the interviewer is testing: spotting a lost update and choosing optimistic locking for human think time.

Situation: Admin A opens the product form, then Admin B opens it. B saves a new price. A saves a new description a minute later. The form posts all fields, so A's save overwrites B's price with the old value.

Check first: confirm the pattern: the update statement writes all columns from stale data. Check the audit trail or binlog to see two writes close together.

Steps: add a version column (or use updated_at). The form carries the version it loaded. The save runs UPDATE product SET ..., version = version + 1 WHERE id = ? AND version = ?. If zero rows are updated, return a conflict (HTTP 409 or an ETag mismatch with 412) and show the user the newer values. In JPA this is a @Version field and an OptimisticLockException. Do not use FOR UPDATE here, because it would hold a lock across the time the human is editing. Also change the save to update only the changed fields where it makes sense.

Prevent: use version checks by default for entities edited by people, and atomic SQL (stock = stock - 1) for counters.

Duplicate rows appear even though the code checks for existence before inserting. Why, and what is the fix? Intermediate

What the interviewer is testing: check-then-act races and constraints as the final arbiter.

Situation: users get two welcome emails and two accounts with the same email. The code does SELECT by email and inserts only if none was found.

Check first: find duplicates with GROUP BY email HAVING COUNT(*) > 1 and compare their timestamps. Rows only milliseconds apart mean a race, often from a double-click, a client retry, or two app instances.

Steps:

  1. Clean up: keep one row per key (see the delete-duplicates question), and merge or repoint child rows first.
  2. Add a UNIQUE constraint (on LOWER(email) if case is not significant).
  3. Change the code to INSERT ... ON CONFLICT DO NOTHING or catch the unique violation, and treat it as "already exists".
  4. Make the endpoint idempotent with an idempotency key, so a client retry returns the first result.

Prevent: any rule of the form "there must be only one X" belongs in a unique index. Application checks are only for friendlier messages.

After a user saves their profile, the page shows the old data for a second. What is happening? Senior

What the interviewer is testing: replica lag and read-your-writes in a real feature.

Situation: writes go to the primary and reads are load-balanced to replicas. The redirect after save reads from a replica that is a few hundred milliseconds behind.

Check first: measure lag (pg_stat_replication or Seconds_Behind_Source) and confirm that the stale read hits a replica (log which node served the query). Check whether lag spikes during batch jobs or big transactions.

Steps:

  1. Short term: after a write, route that user's reads to the primary for a few seconds (flag in session or cookie).
  2. Route known freshness-critical reads (own profile, order just placed) to the primary.
  3. Better: return the saved data in the write response so the page does not need a second read, or wait on a log position token (LSN or GTID) before reading from a replica.
  4. Fix the cause of high lag: split giant transactions, avoid heavy reports on the replica that conflict with replay, check replica hardware.

Prevent: document which reads may be stale, alert on lag, and take replicas out of rotation when lag exceeds a limit.

A migration adding a column made the whole site hang for two minutes. What happened? Senior

What the interviewer is testing: lock queues, the real mechanism behind many migration outages.

Situation: ALTER TABLE orders ... was started during business hours. Every query on orders stopped. After the migration was killed, traffic recovered.

What happened: the ALTER needed a strong lock (PostgreSQL ACCESS EXCLUSIVE, MySQL metadata lock). A long-running transaction or report was holding a lock on the table, so the ALTER waited. While it waited, every new query on the table queued behind it, even plain SELECTs. The table was effectively frozen until the old transaction finished. Another possibility is that the change needed a full table rewrite.

Steps now: find the blocker (pg_stat_activity with pg_blocking_pids(), or MySQL performance_schema.metadata_locks), end the migration or the blocking session.

Prevent:

  • Set lock_timeout (for example 3 seconds) for migrations, so they fail instead of queueing, and retry at a quiet moment.
  • Use the safe forms: CREATE INDEX CONCURRENTLY, NOT VALID constraints then VALIDATE, ALGORITHM=INSTANT or gh-ost in MySQL.
  • Kill or time-limit long transactions, and check for them before running DDL.
  • Test the migration on a production-sized copy to see whether it rewrites the table.
An endpoint that lists 50 orders takes 3 seconds and the database CPU is high. Where do you look? Intermediate

What the interviewer is testing: recognising N+1 from symptoms, not guessing.

Situation: a Spring and Hibernate service. Each query is fast, but the endpoint is slow, and the database shows thousands of identical statements per minute.

Check first: turn on SQL logging in a test run or look at an APM trace of the request. If you see one query for the list followed by 50 or 150 similar queries differing only by an id, that is N+1. Also check pg_stat_statements: a cheap statement with a huge call count.

Steps:

  1. Fetch the needed associations in the list query: JOIN FETCH or @EntityGraph for to-one relations.
  2. For collections, use batch fetching (hibernate.default_batch_fetch_size of 50 to 100) or a second query with WHERE order_id IN (...). Avoid fetch-joining a collection with pagination.
  3. For read-only lists, query a projection (DTO) with just the needed columns.
  4. Add a test that asserts the number of statements for the endpoint.

Prevent: make associations lazy by default, review SQL logs in code review, and use a query-count assertion library in tests.

The service reports "timeout waiting for connection from pool" and then everything fails. How do you diagnose it? Senior

What the interviewer is testing: finding who holds connections instead of raising the pool size.

Situation: latency climbs, then every request times out acquiring a connection, although the database CPU is low.

Check first: look at the database sessions: SELECT state, count(*) FROM pg_stat_activity GROUP BY 1. Many sessions "idle in transaction" means application code opened a transaction and is not finishing it, often waiting for a remote HTTP call or a slow downstream service. Many "active" long queries means slow SQL. Check pool metrics (active, idle, pending) and thread dumps for threads waiting inside a transaction. Also look for connection leaks: a code path that does not close the connection on error.

Steps: kill the idle-in-transaction sessions to recover; move the remote call outside the transaction; set idle_in_transaction_session_timeout, statement timeouts and a short pool acquisition timeout; enable the pool's leak detection (HikariCP leakDetectionThreshold). Do not simply raise the pool size: it moves the pressure onto the database.

Prevent: keep transactions free of network calls, alert on pool pending count and on idle-in-transaction sessions, and size pools so that instances times pool size stays below the database limit (or use PgBouncer).

A PostgreSQL table is 10 times bigger than its data and queries slow down. What is going on? Senior

What the interviewer is testing: MVCC bloat and what blocks vacuum.

Situation: a busy table with many updates. Disk usage grew, indexes are huge, and sequential scans got slower, although the row count is about the same.

Check first: compare table size to live data, look at pg_stat_user_tables (n_dead_tup, last_autovacuum). Then look for the cause: a long-running or forgotten transaction (pg_stat_activity with old xact_start), an abandoned replication slot, or a prepared transaction, all of which hold back the oldest snapshot so vacuum cannot remove dead rows.

Steps: end the old transaction, let autovacuum catch up (make it more aggressive on this table with per-table settings), and reclaim space if needed. VACUUM FULL rewrites the table but takes an exclusive lock; the pg_repack extension does it online. Rebuild bloated indexes with REINDEX CONCURRENTLY.

Prevent: idle-in-transaction timeouts, monitoring for the oldest transaction age, avoiding update patterns that rewrite whole rows constantly (consider a lower fillfactor to allow HOT updates), and removing unused replication slots.

A nightly report query makes the checkout slow on the main database. What do you change? Intermediate

What the interviewer is testing: separating workloads.

Situation: a big aggregate scan runs at 02:00, uses CPU and disk, evicts hot pages from the cache, and checkout latency rises.

Check first: confirm the correlation in time, and look at the report plan: a full scan with a large sort or hash. Check whether it holds a long transaction that delays vacuum.

Steps:

  1. Run the report on a read replica (and set the replica's query conflict settings so replay is not cancelled). Accept that data is slightly stale.
  2. Reduce the work: filter by date range with an index, aggregate incrementally into a summary table, or use a materialized view refreshed on schedule.
  3. Limit its impact: a lower-priority role with statement_timeout and limited parallelism.
  4. For heavy analytics, replicate to a warehouse (change data capture) and keep analytics off the transactional system.

Prevent: have a rule that reports never run on the primary, and watch for new reports that appear in the slow query log.

An API that lets clients page through 5 million records gets slower with every page. How do you fix it? Intermediate

What the interviewer is testing: keyset pagination as an API design decision.

Situation: clients export data by calling ?page=1, ?page=2, ... Page 20,000 takes 15 seconds, and rows sometimes repeat or are missed because data changes during the export.

Check first: the query uses LIMIT 50 OFFSET 1000000; the plan reads and throws away a million rows each call.

Steps: change the contract to cursor-based pagination. The response includes an opaque next_cursor that encodes the last (created_at, id). The next call runs WHERE (created_at, id) > (:c, :i) ORDER BY created_at, id LIMIT 50 with a matching composite index. Each page now costs the same, and results do not shift while paging. Keep the old page parameter only for small ranges, with a maximum offset, and document the change for clients (versioned endpoint, deprecation period). For full exports, offer an asynchronous export job that streams to a file.

Prevent: new list endpoints get cursor pagination and a stable unique sort key from the start.

Inserts suddenly fail with "integer out of range" or a duplicate key error on the id. What happened? Senior

What the interviewer is testing: capacity planning on key types, and an online fix.

Situation: a table with INT auto-increment ids hit 2,147,483,647 (about 2.1 billion). Writes fail. Gaps from rollbacks and failed inserts burn through numbers faster than the row count suggests.

Check first: confirm with the sequence or AUTO_INCREMENT value. Find every place that stores this id: foreign keys in other tables, caches, message schemas, API clients with 32-bit ids.

Steps: a quick stop-gap in some engines is to switch an unsigned column (MySQL INT UNSIGNED doubles the range), but the real fix is BIGINT. Altering a huge table directly rewrites it and locks it for hours. Online approach: add a new BIGINT column, backfill in batches, keep it in sync with a trigger, build the index, swap the columns in a short window, and do the same on all child tables with foreign keys, using gh-ost or pt-online-schema-change in MySQL. Meanwhile fix clients that treat ids as 32-bit. In PostgreSQL, also change the sequence type.

Prevent: use BIGINT for any table that could be large, and alert when a sequence passes 50% of its range.

Someone ran DELETE or UPDATE without a WHERE clause on production. What now? Senior

What the interviewer is testing: calm incident handling and knowing the recovery options.

Situation: a developer's console session ran UPDATE users SET status = 'INACTIVE' on all rows, and it has committed.

Check first: stop further damage: stop the person and any job that could make it worse. Find out exactly when it ran and how many rows changed. Decide whether the data can be rebuilt (is the old status derivable from other columns, an audit table, or the application events?).

Steps:

  1. If the transaction is still open, ROLLBACK immediately.
  2. If it has committed: restore the affected rows from a backup or point-in-time recovery. Do not restore over production. Restore to a separate instance at a time just before the mistake, then copy the old values back for the affected rows only, in a transaction.
  3. A delayed replica (if the team has one) or a snapshot is the quickest source.
  4. Write the post-mortem and fix the process.

Prevent: read-only database access for people by default, a change process for production data fixes, BEGIN first and check the affected row count before COMMIT, and the MySQL client option --safe-updates. Test restores regularly: a backup you have never restored is only a hope.

A "customers without orders" report suddenly returns zero rows. Nothing changed in the code. Intermediate

What the interviewer is testing: the NOT IN with NULL trap in a real report.

Situation: the query is SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM orders). It worked for months and now returns nothing, although many customers have no orders.

Check first: run the subquery alone and look for NULL values: SELECT COUNT(*) FROM orders WHERE customer_id IS NULL. A new order type (a guest checkout) probably started to insert rows with a NULL customer.

Why: id NOT IN (1, 2, NULL) is never true, because comparing with NULL is UNKNOWN, so the whole condition filters out every row.

Steps: rewrite with NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id), which is NULL-safe. Decide whether orders.customer_id should allow NULL at all; if guest orders are legitimate, keep it nullable and use the NOT EXISTS form.

Prevent: prefer NOT EXISTS as a team habit, and add a test with a NULL in the data.

Two users booked the same seat (or the last item in stock) at the same time. How do you prevent it? Senior

What the interviewer is testing: choosing between a constraint, a lock and an atomic update.

Situation: the code reads available seats, sees seat 12 is free, and inserts a booking. Two requests did this together. Stock went to minus one on a product with one unit.

Check first: identify the invariant (one booking per seat per show; stock never below zero) and where it is checked (application only).

Steps, from best to heaviest:

  1. Constraint: a unique index on (show_id, seat_id) for active bookings. The second insert fails and you show "seat taken". For time ranges (rooms), a PostgreSQL exclusion constraint prevents overlaps.
  2. Atomic update with a guard: UPDATE stock SET qty = qty - 1 WHERE sku = ? AND qty >= 1, and check that one row was updated. Add CHECK (qty >= 0) as the net.
  3. Row lock: SELECT ... FOR UPDATE on the seat or stock row before deciding.
  4. Serializable isolation with retry, when the rule spans many rows (write skew).

Prevent: state the invariant as a database rule whenever possible, and add a concurrent test that sends 50 simultaneous requests for one seat.

Several workers pick the same job from a jobs table and process it twice. How do you fix it? Intermediate

What the interviewer is testing: SKIP LOCKED, and idempotent processing.

Situation: each worker runs SELECT * FROM jobs WHERE status = 'PENDING' LIMIT 10 and then updates the rows to RUNNING. Two workers read the same rows before either updates them.

Steps:

  1. Claim jobs atomically: in one transaction, SELECT ... WHERE status = 'PENDING' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED, mark them RUNNING with a lease time (locked_until), and commit. Other workers skip locked rows and take different ones. A single statement form is UPDATE jobs SET status='RUNNING' WHERE id IN (SELECT id ... FOR UPDATE SKIP LOCKED) RETURNING *.
  2. Crash handling: a reaper query puts RUNNING jobs whose lease expired back to PENDING.
  3. Make job handlers idempotent anyway (a unique key on the result, or a check on the job state), because at-least-once delivery means a rare repeat.
  4. Index (status, id), ideally partial on PENDING, so claiming stays fast as the table grows. Delete or archive finished jobs.

Prevent: know the limits: a table-based queue is fine for thousands of jobs per second; beyond that or with fan-out, move to a real broker.

Invoices are off by a cent in the monthly totals. How do you find the cause? Intermediate

What the interviewer is testing: numeric types and rounding policy.

Situation: the sum of line items does not equal the invoice total for some customers, and the finance export differs from the app by a few cents.

Check first: look at the column types: FLOAT or DOUBLE columns, or Java double in code. Compare where rounding happens: per line, per invoice, or only for display. Look for the same value rounded in two different places (database and application) with different modes.

Steps: migrate to NUMERIC(19,4) or integer minor units with a currency column, using BigDecimal in Java. Define one rounding rule (for example half-even at line level) in one place and write it down. Allocate remainders explicitly when splitting amounts (give the extra cent to the first or the largest share). Add a reconciliation job that checks the sum of lines equals the total, and alerts on differences. Migrate old data carefully, after checking how the old floats were rounded.

Prevent: a code review rule against floating point for money, and property tests that check totals.

Daily reports show orders on the wrong day for some customers, and a scheduled job ran an hour early after a clock change. Intermediate

What the interviewer is testing: time zone discipline across database, app and users.

Situation: timestamps were stored as local server time without a zone, then the servers moved to another region, and daylight saving shifted offsets.

Check first: what type is the column (timestamp without zone, DATETIME, timestamptz)? What is the session and JVM time zone on each server? Are some rows written by services in different zones?

Steps: decide that all instants are stored in UTC (PostgreSQL timestamptz; MySQL DATETIME with a UTC-only rule, or TIMESTAMP mindful of the 2038 limit). Set database, JVM and containers to UTC. Convert old data using the zone it was written in, which means the daylight saving hour is ambiguous and needs a manual rule. For "orders per day", group by the customer's or business's zone explicitly: (created_at AT TIME ZONE 'Europe/Berlin')::date. For schedules, store the local time and zone id, and compute the next UTC instant at run time.

Prevent: a rule that the API sends ISO 8601 with offset, tests that run with a non-UTC default zone, and tests around the daylight saving dates.

A query has the right index but still does a full scan, after switching to an ORM or a new driver. Why? Senior

What the interviewer is testing: implicit type conversion killing index use.

Situation: WHERE phone = ? on a VARCHAR indexed column was fast. After a refactor, the parameter is bound as a number (or the driver sends a national character string for a non-national column), and the query takes seconds.

Check first: EXPLAIN the exact statement with the exact parameter types the app sends. In MySQL, comparing a string column to a number casts every row to a number, so the index cannot be used. A mismatch in character set or collation between joined columns has the same effect (utf8mb4 versus latin1). SQL Server with nvarchar parameters on a varchar column behaves like this too. In PostgreSQL, a cast on the column side (col::text) or on a bigint versus numeric comparison can also prevent index use.

Steps: bind the parameter with the column's type (setString not setLong), align charsets and collations, or cast the parameter side rather than the column side. Re-run EXPLAIN and check the "key" or "Index Scan" line.

Prevent: declare entity field types to match column types, and review plans for hot queries after ORM or driver upgrades.

A customer deleted their account and now cannot sign up again with the same email. Intermediate

What the interviewer is testing: the soft delete versus unique constraint conflict, and privacy.

Situation: accounts are soft-deleted with deleted_at. The unique index on email still includes deleted rows, so the sign-up insert fails.

Steps:

  1. Replace the unique index with a partial one: CREATE UNIQUE INDEX ... ON users (email) WHERE deleted_at IS NULL (PostgreSQL). In MySQL use a generated column such as active_email = IF(deleted_at IS NULL, email, NULL) with a unique index, since NULLs do not collide.
  2. Decide the business rule: should the new sign-up get a fresh account, or should it restore the old one? Either is valid, but be explicit, and consider order history and fraud flags.
  3. For privacy rules, check whether the old row must be anonymised or really deleted after a retention period, and schedule a purge.

Prevent: whenever you add soft delete, review every unique constraint, every query filter, and every foreign key relation.
