Mental model: the 8 ideas everything hangs on

One line: a relational database stores facts as rows in tables, lets you ask for them in a declarative language (you say what you want, the optimizer picks how), and protects them with transactions. Most interview answers are about three things: the shape of the data, how the engine finds it (indexes and plans), and what happens when many people change it at once (locks and isolation).
  1. Tables of rows, linked by keys. A primary key identifies a row. A foreign key says "this value must exist in that other table". Good design stores each fact once.
  2. SQL is declarative. You describe the result. The planner chooses indexes, join order and algorithms from statistics about the data. The same query can be fast today and slow next month because the data changed.
  3. Logical order is not written order. A query runs as FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. That explains why a SELECT alias does not work in WHERE.
  4. An index is a sorted copy of some columns with pointers to the rows. It makes reads fast and writes slower. B-tree is the default everywhere.
  5. NULL means "unknown", not zero or empty. A comparison with NULL gives UNKNOWN, which WHERE treats as false. Many bugs live here.
  6. A transaction is all or nothing (atomic), keeps rules true (consistent), is not confused by others (isolated) and survives a crash (durable). The isolation level decides how much others can disturb you.
  7. Readers do not block writers (MVCC). The database keeps several versions of a row. Writers still block other writers on the same row.
  8. Scale is a ladder. Fix queries and indexes first, then cache, then read replicas, then partitioning, and only then sharding. Every rung adds a new kind of failure.

1. Keys, normalization and design

Explain primary key, unique key, foreign key and composite key. Basic

A primary key uniquely identifies a row and can never be NULL; a table has exactly one. A unique key also prevents duplicates but a table can have many, and they may allow NULL. A foreign key is a column that must match a key in another table, so you cannot create an orphan row. A composite key is a key made of more than one column.

Start with the problem keys solve. A table is just a pile of rows. Without rules, nothing stops two rows describing the same customer, or an order pointing at a customer who was deleted. Keys are the rules that make a row findable and keep tables consistent with each other.

  • Primary key (PK): the one column (or column group) that identifies a row. The database enforces it as NOT NULL and unique, and builds an index on it. A table has at most one.
  • Unique key: another column (or group) that must not repeat, such as email. A table can have many. NULLs are allowed in most databases (PostgreSQL and MySQL allow several; SQL Server allows only one).
  • Foreign key (FK): a column whose value must exist as a key in another table (the parent). It is the database's guarantee of "no orphans".
  • Composite key: any of the above made of two or more columns together. The pair is unique, not each column alone.

Walk through it with data. Parent orders(id) holds 100 and 101. Child order_line uses the composite PK (order_id, line_no):

StatementResultWhy
INSERT (100, 1, 2)OKpair is new, order 100 exists
INSERT (100, 2, 1)OKorder_id repeats, but the pair is different

Choose the ON DELETE action by meaning: CASCADE for parts that cannot live without the parent (order lines), RESTRICT or NO ACTION (the default) for things you must never lose by accident (customers with orders), SET NULL for optional links.

Think of an order line: it is identified by (order_id, line_no), which is a composite primary key, and order_id is also a foreign key to orders. PostgreSQL and MySQL allow several NULLs in a unique column, because NULL is not equal to NULL. A foreign key also blocks deleting a parent that still has children, unless you choose ON DELETE CASCADE or SET NULL. PostgreSQL does not create an index on the foreign key column for you, so add one, or deletes on the parent and joins will scan the child table. MySQL InnoDB creates it automatically.

CREATE TABLE order_line (
  order_id BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  line_no  INT    NOT NULL,
  qty      INT    NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, line_no)
);

Remember: one primary key, many unique keys, foreign keys point at keys. Index your foreign keys.

Surrogate key or natural key as the primary key? Intermediate

I use a surrogate key (a generated id with no business meaning) as the primary key, and put a UNIQUE constraint on the natural key (email, country code, SKU). Natural keys look unique and stable, but in real life emails change and companies merge, and a key change would ripple through every child table.

The two kinds of key. A natural key is a value from the real world that already identifies the thing: an email, a passport number, a country code. A surrogate key is an invented value (a counter or UUID) whose only job is to be the row's identity.

Why natural keys hurt. The primary key is copied into every child table and every secondary index. Suppose users uses email as the PK, and 12 tables reference it. A user changes email from a@x.com to a@y.com. Now you must update 12 tables (or rely on ON UPDATE CASCADE, which rewrites millions of child rows and locks them), and any external system that stored the old value breaks. With a surrogate key, users(id=42) stays 42 forever and the email change is a one-row UPDATE.

The rule I follow: surrogate PK for identity, plus UNIQUE (email) for the business rule. The unique constraint still stops duplicate people; the PK just does not depend on it. The weakness of a surrogate key is that it does not prevent duplicates on its own, so forgetting the UNIQUE on the natural key is the typical mistake.

The primary key is copied into every foreign key and every secondary index, so it should be small and never change. A natural key is fine for small, stable lookup tables such as ISO country codes, and for pure join tables where the two foreign keys together are the key. Do not expose a sequential id in URLs if enumeration matters: it leaks volume and invites guessing, so use a separate public id for outside use (and still check authorization).

Remember: surrogate primary key for identity, UNIQUE on the natural key for the business rule.

UUID or auto-increment bigint for primary keys? Senior

I default to a bigint from a sequence: it is 8 bytes, always inserts at the right edge of the index, and is cheap. I pick a UUID when ids must be created outside the database, across shards, or exposed publicly, and then I prefer a time-ordered one (UUIDv7) over random UUIDv4.

Why the choice matters: how a B-tree takes inserts. An index is a sorted tree of fixed-size pages (for example 8 KB). A new key must go into the page where it sorts.

  • Sequential key (bigint from a sequence): every new id is larger than all existing ones, so it goes into the same right-most page. That page stays in memory ("hot"), fills up, then a new page is added. Writes are cheap and the index is compact (pages almost full).
  • Random key (UUIDv4): each new id sorts to a random spot. With 100 million rows the target page is almost always not in memory, so each insert may read a page from disk, and when the page is full it splits into two half-empty pages. Result: more I/O, larger index, lower cache hit rate.
  • UUIDv7: the first 48 bits are a millisecond timestamp, the rest random. New ids cluster at the right edge like a sequence, but any app server or shard can create them without asking the database.

MySQL twist. InnoDB stores the whole table inside the primary-key B-tree (the clustered index) and every secondary index entry ends with the PK value. A random 16-byte PK therefore scatters table inserts as well as making every secondary index bigger. In PostgreSQL the table (heap) is separate from the PK index, so only the index suffers.

Decision rule: single database, ids only made there: bigint. Ids made by clients, several services, offline mobile, or merged datasets: UUIDv7. Public identifiers in URLs: a separate random public id column, regardless of the PK type. Pitfall: when a bigint PK gets sharded, each shard's sequence collides, so plan ranges or a Snowflake-style generator early.

The cost of random UUIDs is the index. Random values land all over the B-tree, causing page splits, poor cache hit rates and bigger indexes. In MySQL InnoDB it is worse: the primary key is the clustered index and every secondary index stores a copy of it, so a 16-byte random key fattens all of them. UUIDv7 (RFC 9562) starts with a timestamp, so inserts are mostly sequential but ids are still generated anywhere. PostgreSQL 18 has a built-in uuidv7(); on older versions generate it in the application. Store UUIDs in the native uuid type (PostgreSQL) or BINARY(16) (MySQL), never as 36-character text. Sequences also have gaps after rollbacks, so never rely on gap-free ids.

Remember: bigint is compact and sequential. If you need UUIDs, make them time-ordered.

What is normalization? Explain 1NF, 2NF and 3NF with an example. Basic

Normalization means arranging tables so each fact is stored in exactly one place, which prevents update anomalies such as changing a customer's city in one row but not another. 1NF: every cell holds one value. 2NF: every non-key column depends on the whole key. 3NF: no non-key column depends on another non-key column. A memory line: each column depends on "the key, the whole key, and nothing but the key".

The anomaly we are curing. Suppose one wide table stores everything. Ann lives in Pune and placed 3 orders, so "Pune" is typed in three rows. Ann moves to Delhi and you update one row: now the table disagrees with itself (update anomaly). You cannot record a new product that nobody has ordered yet (insert anomaly), and deleting the only order for a product erases the product's price (delete anomaly). Normalization removes these by storing each fact once.

Start from this table (PK is (order_id, product_id)):

order_idcustomercityproduct_idproduct_namepriceqty
1AnnPuneP1Pen102
1AnnPuneP2Book501
2AnnPuneP1Pen105
  1. 1NF says every cell is a single value, with no lists such as "Pen, Book" in one cell and no repeating columns like item1, item2. The table above is already in 1NF (one row per order line).
  2. 2NF applies when the key has several columns. Every other column must depend on the whole key. Here product_name and price depend only on product_id (half the key), and customer, city only on order_id. Fix: move them out to product(product_id, name, price) and orders(order_id, customer, city). Leaving order_item(order_id, product_id, qty).
  3. 3NF: a non-key column must not depend on another non-key column. In orders, city depends on customer, not on the order. Fix: customer(customer_id, name, city) and orders(order_id, customer_id). Now Ann's city is stored once; moving house is a one-row update.

Beyond 3NF. BCNF is a slightly stricter 3NF (every determinant must be a candidate key); 3NF is what interviews and real schemas normally target. One caution: do not normalize things that are really snapshots. The price a customer paid belongs in order_item because it must not change when the product price later changes.

Cost of normalizing: more joins. That is usually fine with indexes, and the next question covers when to go the other way.

Take orders_wide(order_id, customer_name, customer_city, items, product_price). A cell like "pen, book" in items breaks 1NF, so each item becomes its own row. With key (order_id, product_id), product_price depends only on product_id, which breaks 2NF, so products get their own table. customer_city depends on the customer, not the order, which breaks 3NF, so customers get their own table. Normalization also removes insert and delete anomalies: you can add a product without an order, and deleting the last order does not erase the product.

Remember: the key, the whole key, and nothing but the key. Split until each fact lives once.

When would you deliberately denormalize? What does it cost? Intermediate

I normalize first, measure, add an index, and only then denormalize the one hot read path, for example a counter like comment_count on a post, a precomputed totals table, or a read-heavy page that would join six tables. The cost is that I now own keeping the copies in sync.

Why not always normalize? A normalized design answers "show a post with its comment count" with a join and a COUNT over comments. With 5 million comments and a feed page that shows 20 posts, that is 20 aggregations on every page view. Denormalizing means storing a redundant copy of a fact so the read becomes a single-row lookup.

Worked example: a counter column.

ALTER TABLE post ADD COLUMN comment_count INT NOT NULL DEFAULT 0;

-- on every new comment, in the SAME transaction:
BEGIN;
INSERT INTO comment(post_id, body) VALUES (7, 'nice');
UPDATE post SET comment_count = comment_count + 1 WHERE id = 7;
COMMIT;

-- the safety net: a job that recomputes and fixes drift
UPDATE post p SET comment_count = c.n
FROM (SELECT post_id, COUNT(*) n FROM comment GROUP BY post_id) c
WHERE c.post_id = p.id AND p.comment_count <> c.n;   -- PostgreSQL UPDATE ... FROM

Read cost went from an aggregation to reading one column. Write cost went up by one extra UPDATE, and now a popular post is a hot row: every comment queues on the same row lock. If that bites, keep the counter in Redis or in sharded counter rows and sum them.

Options for keeping copies in sync, from safest to riskiest:

  1. A materialized view: the database stores the query result and you refresh it (on a schedule or on demand). The source of truth is untouched.
  2. A trigger: the database updates the copy automatically, but hidden logic surprises people and slows bulk loads.
  3. Application code in the same transaction: explicit, but every code path that writes must remember to do it.
  4. Asynchronous (events or CDC feeding a read model): scales best, but the copy is briefly stale.

Say in the interview: I measure first, because a good index often makes the join fast enough. I denormalize only the proven hot path, keep the normalized tables as the truth, and write the rebuild job on day one.

The sync can be done in the same transaction by application code, by a trigger, or by a background job that rebuilds the numbers. Each can drift, so I keep a way to recompute the copy from the source of truth. Materialized views are a safer form because the database refreshes them from the real tables. A snapshot of unit price and address on an order is not really duplication: it records what was true at purchase time, which must not change later. Analytics star schemas are intentionally denormalized, since data loads in batches and is read heavily.

Remember: normalize by default. Denormalize one measured hot path, and keep a rebuild job.

Why use constraints (UNIQUE, FK, CHECK) instead of validating in code? Intermediate

Because only the database can check a rule atomically under concurrency. Code that runs a SELECT to see whether an email is free can be beaten by a second request doing the same thing at the same moment. A UNIQUE constraint closes that race. I validate in code too for friendly error messages, but constraints are the safety net.

The race, step by step. You want unique emails and write it in code: "SELECT whether the email exists; if not, INSERT". Two sign-up requests for a@x.com arrive together:

TimeRequest ARequest B
t1SELECT ... WHERE email='a@x.com' returns 0 rows
t2SELECT ... WHERE email='a@x.com' returns 0 rows
t3INSERT succeeds
t4INSERT succeeds: duplicate!

Each request did a correct check against what it could see, yet together they broke the rule. Raising the isolation level or locking helps only if used perfectly everywhere. A UNIQUE index makes the second INSERT fail at t4, because the database serialises the two writers on that index entry. Same for a foreign key: between your "does the customer exist?" check and your INSERT, another session may delete the customer.

Pattern that works:

ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email);

-- app: just try the insert and handle the failure
INSERT INTO users(email) VALUES ('a@x.com');
-- on SQLSTATE 23505 (PostgreSQL) / error 1062 (MySQL): return 409 Conflict

-- or be idempotent
INSERT INTO users(email) VALUES ('a@x.com') ON CONFLICT (email) DO NOTHING;  -- MySQL: INSERT IGNORE / ON DUPLICATE KEY

Which rules belong in the database? Anything that must always hold regardless of who writes: uniqueness, references, NOT NULL, simple CHECKs (qty > 0, status IN (...)). Rules that need other services, complex business policy or friendly messages stay in code too. Remember MySQL before 8.0.16 parsed but ignored CHECK constraints.

The same applies to foreign keys (a parent deleted between your check and your insert) and to rules like CHECK (balance >= 0). Constraints also protect against other services, scripts and bugs that write to the same tables. The costs: a foreign key check does an index lookup on each insert and takes a light lock on the parent row, so very high write rates and bulk loads feel it. Some large sharded systems drop foreign keys on purpose and use cleanup jobs; that is a deliberate trade-off, not a default. In code, catch the unique violation (PostgreSQL SQLSTATE 23505, MySQL error 1062) and return a conflict response.

Remember: check-then-insert in code is a race. A UNIQUE constraint is the only reliable guard.

2. Joins, grouping, NULL and subqueries

In what order does a SELECT run? Why can't I use a column alias in WHERE? Basic

Logically it runs FROM and JOIN, then WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY and finally LIMIT. WHERE runs before SELECT, so an alias defined in SELECT does not exist yet when WHERE is evaluated. ORDER BY runs after SELECT, so it can use aliases.

Why this matters. SQL reads like English ("SELECT this FROM that WHERE ...") but runs in a different order. Knowing the real order tells you what each clause can see.

Walk-through. Table sales(region, amount): (East, 10), (East, 20), (West, 5), (West, 7), (East, 30).

SELECT region, SUM(amount) AS total
FROM sales
WHERE amount >= 7
GROUP BY region
HAVING SUM(amount) > 20
ORDER BY total DESC
LIMIT 1;
  1. FROM: take all 5 rows.
  2. WHERE amount >= 7: drop (West, 5). Four rows remain.
  3. GROUP BY region: East = {10, 20, 30}, West = {7}.
  4. HAVING SUM > 20: East sums to 60 and stays; West sums to 7 and is dropped.
  5. SELECT: compute the output columns; total = 60 gets its name here.
  6. ORDER BY total: now the alias exists, so it works.
  7. LIMIT 1: keep the first row. Result: (East, 60).

That also answers the alias question. WHERE total > 20 fails with "column total does not exist" because step 2 happens before step 5 gives the name. Repeat the expression, or use a subquery.

Which clause sees what:

ClauseCan useCannot use
WHEREraw columnsaggregates, aliases, window results
HAVINGgroup columns, aggregatesselect aliases (in standard SQL; MySQL allows)
ORDER BYeverything, including aliases and window results-

The "as if" rule also explains why LIMIT without ORDER BY gives an arbitrary row: the database makes no promise about order unless you ask.

The optimizer may physically reorder steps (for example push filters down early), but the result must look as if this order was followed. Window functions are computed in the SELECT step, after HAVING, which is why you cannot filter on ROW_NUMBER() in WHERE and must wrap it in a subquery or CTE. Filter plain columns in WHERE (it shrinks the data before grouping) and aggregates in HAVING. MySQL and PostgreSQL allow aliases in GROUP BY as an extension.

Remember: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT. An alias exists only after SELECT.

Explain INNER, LEFT, RIGHT and FULL OUTER join with an example. Basic

A join pairs rows from two tables where a condition matches. INNER keeps only matched pairs. LEFT keeps every left row and fills the right columns with NULL when nothing matches. RIGHT is the mirror image. FULL OUTER keeps unmatched rows from both sides.

What a join is. A join builds a wider row from two tables by matching a condition, usually a foreign key to a primary key. The join type only answers one question: what do we do with rows that find no partner?

Row multiplication, the pitfall interviewers like. A join returns one output row per matching pair. If emp has 2 rows for dept 10, a department row appears twice. Suppose you SUM a department budget after joining to employees: a budget of 100 for Eng is counted twice (200). The fix is to aggregate each side separately before joining, or join to a pre-aggregated subquery.

Which to use: INNER when both sides must exist. LEFT when the left table is the thing you report on and the right is optional detail (all customers, with orders if any). FULL is rare, used for reconciliation ("what is in A but not B and vice versa"). Write LEFT and reorder tables rather than RIGHT, because queries then read in one direction.

Take employees Asha(10), Ben(10), Chen(20), Dev(NULL) and departments 10 Eng, 20 Sales, 30 HR. INNER gives three rows (Dev and HR vanish). LEFT gives those three plus Dev with a NULL department. RIGHT gives the three plus HR with a NULL employee. FULL gives all five rows. MySQL has no FULL OUTER JOIN; emulate it with a LEFT JOIN UNION a RIGHT JOIN. In practice I write LEFT joins and swap the table order instead of using RIGHT. One more point interviewers like: if one department matches many employees, rows multiply, so joining on a non-unique key can inflate a SUM.

SELECT e.name, d.name AS dept
FROM emp e
LEFT JOIN dept d ON d.id = e.dept_id;   -- Asha Eng, Ben Eng, Chen Sales, Dev NULL

Remember: INNER = matches only. LEFT = all left rows plus NULLs. FULL = both sides.

What is the difference between a condition in ON and in WHERE for a LEFT JOIN? Intermediate

ON decides which rows match. WHERE filters the final result afterwards. If I put a condition on the right table in WHERE, the NULL rows from unmatched left rows fail it and disappear, so my LEFT JOIN silently behaves like an INNER JOIN. To keep all left rows, I put that condition in ON.

Why this is subtle. In an INNER JOIN, ON and WHERE are interchangeable because both only remove rows. In an outer join they are not, because the outer join first adds NULL-padded rows for unmatched left rows, and WHERE then runs on that padded result.

Data: emp = Asha(10), Ben(10), Chen(20), Dev(NULL); dept = 10 Eng, 20 Sales.

Query A, condition in WHERE:

SELECT e.name, d.name AS dept
FROM emp e LEFT JOIN dept d ON d.id = e.dept_id
WHERE d.name = 'Eng';
-- Asha Eng
-- Ben  Eng        (2 rows: Chen and Dev are gone)

The LEFT JOIN first produced 4 rows, including (Dev, NULL). In WHERE, NULL = 'Eng' is unknown, so Dev is removed, and Chen is removed because Sales is not Eng. We wrote LEFT JOIN, but got INNER JOIN behaviour.

Query B, condition in ON:

SELECT e.name, d.name AS dept
FROM emp e LEFT JOIN dept d ON d.id = e.dept_id AND d.name = 'Eng';
-- Asha Eng
-- Ben  Eng
-- Chen NULL      (matched dept 20, but 'Sales' fails the ON, so no partner)
-- Dev  NULL

All 4 employees survive. The condition only controls which partner counts as a match.

The practical rule: ask "should failing this condition remove the left row, or only blank the right side?" Remove the row: WHERE. Only blank: ON. A typical real case: "all customers with their orders from 2025": the date filter on orders goes in ON, otherwise customers without 2025 orders vanish. The one deliberate exception is the anti-join, where WHERE right.id IS NULL is exactly what keeps only the unmatched rows.

Example: FROM emp e LEFT JOIN dept d ON d.id = e.dept_id WHERE d.name = 'Eng' drops Dev, because Dev's d.name is NULL and NULL = 'Eng' is not true. Moving it gives ... ON d.id = e.dept_id AND d.name = 'Eng': everyone stays, and only Eng members get a department name. The rule: conditions about the right table that must not drop left rows go in ON. Conditions that mean "keep only these rows" go in WHERE. For an inner join the two are equivalent, which is why people forget the difference. The anti-join (rows with no match) deliberately uses WHERE d.id IS NULL after the join.

SELECT e.name FROM emp e
LEFT JOIN dept d ON d.id = e.dept_id
WHERE d.id IS NULL;          -- employees with no department: Dev

Remember: a right-table filter in WHERE turns a LEFT JOIN into an INNER JOIN.

What are CROSS JOIN, self join, semi join and anti join? Intermediate

A CROSS JOIN pairs every row with every row (3 times 4 gives 12). A self join joins a table to itself under two aliases, such as employee and manager. A semi join returns left rows that have a match, each once, written with EXISTS. An anti join returns left rows with no match, written with NOT EXISTS or LEFT JOIN with IS NULL.

One example each, using small data. Let sizes = {S, M} and colors = {red, blue, green}.

  • CROSS JOIN (FROM sizes CROSS JOIN colors) gives 2 x 3 = 6 rows: S-red, S-blue, S-green, M-red, M-blue, M-green. Handy to build a complete grid (every product for every day) that you then LEFT JOIN facts onto, so missing combinations show as zero. The accident version is a comma join with a forgotten WHERE: two 1 million row tables give 10^12 rows.
  • Self join (employee e JOIN employee m ON m.id = e.manager_id) treats one table as two. Aliases are mandatory. Use LEFT so the top boss, whose manager_id is NULL, still appears.
  • Semi join answers "which customers have at least one order". WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id). Each customer once, even with 50 orders; no columns from orders are returned. The engine can stop at the first match per customer.
  • Anti join answers "which customers have no order": WHERE NOT EXISTS (...), or LEFT JOIN orders o ... WHERE o.id IS NULL.

How semi differs from an inner join. A customer with 3 orders produces 3 rows in an inner join but 1 row in a semi join. That is why semi joins do not need DISTINCT and do not inflate later SUMs.

Interview probe: "how would you find customers who ordered but never returned anything?" Combine them: EXISTS on orders and NOT EXISTS on returns.

CROSS JOIN is useful to generate combinations (every product with every day) and dangerous when you forget a join condition. NATURAL JOIN joins on all same-named columns and breaks silently when someone adds a column, so avoid it. SQL has no keywords for semi and anti joins; the optimizer recognises the EXISTS patterns and plans them as such.

SELECT e.name, m.name AS manager
FROM employee e LEFT JOIN employee m ON m.id = e.manager_id;

Remember: EXISTS is a semi join, NOT EXISTS is an anti join, and a forgotten ON clause makes a cross join.

How do GROUP BY and HAVING work, and where does WHERE fit? Basic

GROUP BY collapses rows with the same values in the listed columns into one row per group, and aggregates (COUNT, SUM, AVG, MIN, MAX) compute one value per group. WHERE filters rows before grouping. HAVING filters whole groups after aggregation, so it can use aggregates.

What GROUP BY really does. It sorts or hashes rows into buckets by the grouping columns, then each aggregate function reduces a bucket to one value. After grouping, a "row" means a whole bucket, so you may only select the group columns or aggregates (a bucket has many different amounts, so a bare amount is ambiguous).

Worked example. orders:

For the query on this page: WHERE removes order 5 (2024). Groups: customer 1 = {60, 70} (n=2, total=130), customer 2 = {200} (n=1), customer 3 = {30} (n=1). HAVING keeps groups with total > 100 and n >= 2: only customer 1. Result: (1, 2, 130). Customer 2 has a big total but only one order, so HAVING removes it.

Why filter in WHERE when you can. A condition on a plain column placed in HAVING gives the same answer but forces the engine to group all rows first and filter later. In WHERE it shrinks the input before grouping and can use an index. HAVING is only for conditions on aggregates.

Pitfall: selecting a column that is neither grouped nor aggregated. Old MySQL returned a random value from the bucket; with ONLY_FULL_GROUP_BY (default since 5.7) it errors. If you need the "other" columns, join back to the table or use a window function.

Every selected column must be in GROUP BY or inside an aggregate; PostgreSQL enforces this and MySQL does too with ONLY_FULL_GROUP_BY (default since 5.7). Put every row-level filter in WHERE, because it shrinks the data before the expensive grouping step. HAVING without GROUP BY treats the whole table as one group. For subtotals in one query, GROUP BY ROLLUP(region, city) adds per-region and grand-total rows.

-- customers with 2+ orders totalling over 100 in 2025
SELECT customer_id, COUNT(*) AS n, SUM(amount) AS total
FROM orders
WHERE created_at >= '2025-01-01' AND created_at < '2026-01-01'   -- row filter
GROUP BY customer_id
HAVING SUM(amount) > 100 AND COUNT(*) >= 2;                     -- group filter

Remember: WHERE filters rows, HAVING filters groups.

What is the difference between COUNT(*), COUNT(column) and COUNT(DISTINCT column)? Basic

COUNT(*) counts rows. COUNT(col) counts rows where col is not NULL. COUNT(DISTINCT col) counts the different non-NULL values. All other aggregates (SUM, AVG, MIN, MAX) also skip NULLs.

Same table, different counts. score column of 5 rows: 10, 20, 20, NULL, NULL.

The AVG row is the one that trips people: whether a missing score means "not yet known" (skip it) or "zero" (count it) is a business decision, and you must make it explicitly.

The LEFT JOIN trap. Customers: Ann (2 orders), Bob (0 orders). After customers c LEFT JOIN orders o ON ... and GROUP BY customer, Bob has one joined row with all o.* columns NULL. COUNT(*) gives Bob 1 (wrong); COUNT(o.id) gives 0 (right).

Performance note: COUNT(*) on a big InnoDB or PostgreSQL table must scan an index, because with MVCC each transaction may see a different number of rows. There is no stored row count to read, so "SELECT COUNT(*) on 500 million rows" is slow; use an approximate count from statistics or keep a counter if exactness is not needed.

So AVG(score) over 10, 20, NULL is 15, not 10, because the NULL row is ignored; use AVG(COALESCE(score, 0)) if NULL should count as zero. On an empty set SUM and AVG return NULL but COUNT returns 0. COUNT(1) and COUNT(*) are identical. A classic trap after a LEFT JOIN: COUNT(o.id) correctly gives 0 for customers with no orders, while COUNT(*) gives 1 because the customer row itself is counted.

Remember: aggregates ignore NULL, except COUNT(*). Count a right-table column after a LEFT JOIN.

How does NULL behave in comparisons, logic, sorting and aggregates? Intermediate

NULL means "unknown". Any comparison with NULL, even NULL = NULL, gives UNKNOWN, and WHERE keeps only rows where the condition is TRUE. So I must write IS NULL or IS NOT NULL. Aggregates skip NULLs, and GROUP BY, DISTINCT and UNION treat all NULLs as one group.

The core idea. SQL uses three truth values: TRUE, FALSE and UNKNOWN. NULL means "value not known", so asking whether an unknown value equals something is itself unknown. WHERE, JOIN ON and HAVING keep a row only when the condition is TRUE, so UNKNOWN is dropped just like FALSE.

A bug that really happens. Table users(id, status) has statuses 'A', 'B' and NULL. WHERE status <> 'A' returns only 'B', not the NULL row, because NULL <> 'A' is UNKNOWN. To include them: WHERE status <> 'A' OR status IS NULL, or status IS DISTINCT FROM 'A'.

Where NULLs are treated as equal anyway: GROUP BY (one NULL group), DISTINCT, UNION and set operators. A UNIQUE index in PostgreSQL and MySQL allows many NULL rows (PostgreSQL 15 added UNIQUE NULLS NOT DISTINCT to change that).

Design advice. Prefer NOT NULL columns with a real default when "absent" has a natural value (0, empty string). Keep NULL for "genuinely unknown or not applicable", and give it a documented meaning.

Three-valued logic: UNKNOWN AND FALSE is FALSE, UNKNOWN OR TRUE is TRUE, NOT UNKNOWN is UNKNOWN. A CHECK constraint passes on UNKNOWN, so CHECK (age > 0) still allows NULL. Sorting differs: PostgreSQL puts NULLs last in ascending order (use NULLS FIRST/LAST), MySQL puts them first. Handy tools: COALESCE(a, b, 0) returns the first non-NULL; NULLIF(a, 0) returns NULL when a is 0, which avoids division by zero; IS DISTINCT FROM (PostgreSQL) or <=> (MySQL) compares NULLs like normal values. Oracle treats an empty string as NULL; others do not.

SELECT 1 WHERE NULL = NULL;        -- no row
SELECT 10 / NULLIF(0, 0);          -- NULL, not an error

Remember: NULL is unknown, never equal to anything. Use IS NULL and COALESCE.

Why can NOT IN return no rows when the list contains a NULL? Intermediate

Because x NOT IN (1, 2, NULL) expands to x <> 1 AND x <> 2 AND x <> NULL. The last part is UNKNOWN for every x, so the whole AND can never be TRUE and no row passes. I use NOT EXISTS instead, which is not confused by NULL.

Step by step with data. employee: Asha (id 1, manager NULL), Ben (id 2, manager 1), Chen (id 3, manager 1). Goal: employees who manage nobody, which should be Ben and Chen.

SELECT name FROM employee
WHERE id NOT IN (SELECT manager_id FROM employee);
-- subquery returns (NULL, 1, 1)

For Ben (id 2) the engine evaluates 2 NOT IN (NULL, 1, 1) as 2 <> NULL AND 2 <> 1 AND 2 <> 1 = UNKNOWN AND TRUE AND TRUE = UNKNOWN, so Ben is not returned. Same for Chen. The query returns zero rows, and so would Asha: 1 <> NULL is UNKNOWN too.

Now the same with NOT EXISTS:

SELECT e.name FROM employee e
WHERE NOT EXISTS (SELECT 1 FROM employee x WHERE x.manager_id = e.id);
-- Ben, Chen

NOT EXISTS asks "is there any row where manager_id = this id". The NULL row never equals anything, so it simply never matches and does no harm.

Why IN is fine. x IN (1, NULL) is x = 1 OR x = NULL; if x is 1 that is TRUE OR UNKNOWN = TRUE, so a match is found. The failure is specific to negation.

Rules of thumb: use NOT EXISTS for "not in another table". If you must use NOT IN, add WHERE manager_id IS NOT NULL inside the subquery, or make sure the column is NOT NULL. This bug is dangerous because the query works for months, then one NULL arrives in production data and a report silently goes empty.

It bites when the subquery column is nullable, for example WHERE id NOT IN (SELECT manager_id FROM employee) and one employee has no manager. The report suddenly returns zero rows with no code change. IN is safe because one TRUE is enough. NOT EXISTS also tends to get a clean anti-join plan, while NOT IN can plan badly in some engines.

SELECT e.name FROM employee e
WHERE NOT EXISTS (SELECT 1 FROM employee x WHERE x.manager_id = e.id);

Remember: one NULL in a NOT IN list kills the whole result. Use NOT EXISTS.

UNION versus UNION ALL; what do INTERSECT and EXCEPT do? Basic

UNION combines two result sets and removes duplicates. UNION ALL keeps every row and is faster because it skips the sort or hash needed to deduplicate. I use UNION ALL unless I really need uniqueness. INTERSECT returns rows in both queries. EXCEPT (MINUS in Oracle) returns rows in the first but not the second.

Mental model. Set operators stack results vertically (compare joins, which add columns side by side). Both inputs must have the same number of columns with compatible types; matching is by position, not by name.

Data. a = {1, 2, 2, 3}, b = {2, 3, 4}.

PostgreSQL also has INTERSECT ALL and EXCEPT ALL which keep duplicate counts.

Why UNION ALL is the default. UNION must deduplicate the whole output, which means sorting or hashing every row. UNION ALL streams rows through. If the two inputs cannot overlap (for example data from two different months), plain UNION wastes time and, worse, could hide legitimate duplicate rows such as two identical sales.

Typical uses: combining archive and live tables (orders UNION ALL orders_archive), producing a report with a totals row, "A minus B" reconciliation (EXCEPT), and emulating FULL OUTER JOIN in MySQL. INTERSECT and EXCEPT can usually be written with EXISTS / NOT EXISTS, which many engines optimise better, and which let you return extra columns.

Both queries need the same number of columns with compatible types, and column names come from the first. ORDER BY applies once, at the end, to the combined result. These operators treat NULLs as equal when comparing rows, unlike normal comparison. MySQL supports INTERSECT and EXCEPT only from 8.0.31.

SELECT email FROM newsletter
EXCEPT
SELECT email FROM unsubscribed;      -- subscribers still active

Remember: UNION ALL by default. UNION pays for deduplication.

EXISTS versus IN versus JOIN: which one, and what is a correlated subquery? Intermediate

For "customers who have at least one order" I use EXISTS: it returns each customer once and is safe with NULLs. A JOIN returns one row per match, so a customer with 5 orders appears 5 times and needs DISTINCT. I use a JOIN when I need columns from the other table. IN and EXISTS usually get the same semi-join plan, so I choose for correctness first and check EXPLAIN.

Setup. customers = Ann(1), Bob(2), Cy(3). orders: (o1, cust 1), (o2, cust 1), (o3, cust 2).

QueryResult
SELECT c.name FROM customers c JOIN orders o ON o.customer_id = c.idAnn, Ann, Bob (3 rows; Ann twice)
... WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)Ann, Bob
... WHERE c.id IN (SELECT customer_id FROM orders)Ann, Bob

Both EXISTS and IN are "semi joins": the customer row is returned at most once. The JOIN multiplies. The practical choice:

  • Need data from the other table, or its rows multiply anyway: JOIN.
  • Only need a yes/no test: EXISTS (or IN for a plain list of values).
  • Negated test: NOT EXISTS, never NOT IN (NULL trap).

The correlated subquery, in detail. "Employees earning above their own department average." For each outer row the subquery uses that row's dept_id. With Eng average 8000 and Sales average 5000, an Eng person with 8500 and a Sales person with 4000 are compared against different numbers. Conceptually the inner query runs once per outer row; if it is unindexed and the outer table has 1 million rows, that is 1 million scans. Two cures:

-- 1) join to a grouped table: one pass to compute the averages
SELECT e.name, e.salary FROM emp e
JOIN (SELECT dept_id, AVG(salary) AS avg_sal FROM emp GROUP BY dept_id) a
  ON a.dept_id = e.dept_id
WHERE e.salary > a.avg_sal;

-- 2) a window function: one pass, no join
SELECT name, salary FROM (
  SELECT name, salary, AVG(salary) OVER (PARTITION BY dept_id) AS avg_sal FROM emp
) t WHERE salary > avg_sal;

Check EXPLAIN before rewriting: modern planners often decorrelate simple subqueries on their own.

A correlated subquery refers to a column of the outer query, so conceptually it runs once per outer row, such as "employees who earn more than the average of their own department". Optimizers often turn it into a join, but a correlated subquery in the SELECT list over a big table without an index on the correlation column is a classic performance bug. Rewrite it as a join to a grouped derived table, or use a window function. Other kinds: a scalar subquery returns one value, a list subquery feeds IN, a derived table sits in FROM.

SELECT e.name, e.salary FROM emp e
WHERE e.salary > (SELECT AVG(x.salary) FROM emp x WHERE x.dept_id = e.dept_id);

Remember: EXISTS asks "is there a match", JOIN multiplies rows. Correlated means it uses the outer row.

What is a CTE? Is it faster than a subquery? How does a recursive CTE work? Intermediate

A common table expression is a named step defined with WITH name AS (...) and used like a table in the main query. Its value is readability, not speed. A recursive CTE has an anchor query plus a recursive part that joins to the CTE itself, repeating until no new rows appear. I use it to walk hierarchies such as an org chart.

What it is. A CTE gives a name to a subquery so the main query reads top to bottom, like a temporary named variable that lives for one statement. It does not create a stored table.

WITH paid AS (
  SELECT customer_id, SUM(amount) AS total FROM orders WHERE status = 'PAID' GROUP BY customer_id
), big AS (
  SELECT customer_id FROM paid WHERE total > 1000
)
SELECT c.name FROM customers c JOIN big USING (customer_id);

Compare with three nested subqueries: the logic is identical, but each step now has a name and can be tested alone. A CTE can also be referenced twice, which avoids repeating a long subquery.

How a recursive CTE runs, with data. employee: (7, Gia, manager 4), (4, Dev, manager 2), (2, Ben, manager 1), (1, Asha, NULL). For the chain above employee 7:

  1. Anchor runs once: row (7, Gia, depth 1).
  2. Recursive step joins the previous round's rows to employee on e.id = c.manager_id: finds (4, Dev, depth 2).
  3. Again with only the new row: finds (2, Ben, depth 3).
  4. Again: (1, Asha, depth 4).
  5. Again: Asha's manager_id is NULL, so the join finds nothing. The recursion stops. Output: 4 rows.

Going down instead (everyone under Ben) is the same pattern with the join reversed: e.manager_id = c.id. Other uses: category trees, bill of materials, generating a date series (SELECT 1 UNION ALL SELECT n+1 ... WHERE n < 30).

Use UNION ALL in the recursive form (UNION also works and deduplicates, which can itself end a cycle). PostgreSQL has CYCLE / path-array tricks, and you should always keep a depth < N guard for untrusted data.

Performance: before PostgreSQL 12 a CTE was always computed once and acted as an optimization fence (filters were not pushed into it). From 12, a CTE used once without side effects is inlined like a subquery, and you can force either behaviour with MATERIALIZED or NOT MATERIALIZED. MySQL 8 may merge or materialize it. If data has a cycle, recursion never ends, so add a depth limit or track visited ids (MySQL stops at cte_max_recursion_depth, default 1000).

WITH RECURSIVE chain AS (
  SELECT id, name, manager_id, 1 AS depth FROM employee WHERE id = 7   -- anchor
  UNION ALL
  SELECT e.id, e.name, e.manager_id, c.depth + 1
  FROM employee e JOIN chain c ON e.id = c.manager_id                   -- step up
)
SELECT * FROM chain;       -- employee 7 and every manager above

Remember: CTE = readability. Recursive CTE = anchor plus step, stop on no new rows.

How do you pivot rows into columns, or count several conditions in one pass? Intermediate

I use conditional aggregation: put a CASE inside an aggregate, so one scan produces several numbers. It works in every database and is the standard way to pivot, as long as the column list is known when I write the query.

The idea. You often need several numbers about the same group: orders paid, orders refunded, money refunded. Running one query per number scans the table repeatedly. A CASE inside an aggregate lets one scan fill many columns, because each row contributes only to the columns whose condition it meets.

3. Window functions

What is a window function, and how is it different from GROUP BY? Intermediate

GROUP BY squeezes many rows into one row per group, so detail is lost. A window function calculates across a set of related rows but keeps every row. I write function() OVER (PARTITION BY ... ORDER BY ... frame). It makes ranking within a group, running totals, previous-row comparisons and percent-of-total easy.

The problem it solves. You want each employee's salary next to the average salary of their department. With GROUP BY you get one row per department and lose the employees. Before windows you had to compute the averages in a subquery and join them back. A window function does it in one step because it computes across a "window" of related rows but leaves every row in place.

Same data, two tools. emp: Asha Eng 9000, Ben Eng 8000, Eli Ops 6000.

SELECT dept, AVG(salary) FROM emp GROUP BY dept;
-- Eng 8500
-- Ops 6000            (2 rows, names gone)

SELECT name, dept, salary, AVG(salary) OVER (PARTITION BY dept) AS dept_avg FROM emp;
-- Asha Eng 9000 8500
-- Ben  Eng 8000 8500
-- Eli  Ops 6000 6000  (3 rows, nothing lost)

The three parts of OVER(...):

  • PARTITION BY divides rows into independent groups. Omit it and the whole result is one partition.
  • ORDER BY orders rows inside each partition. It is needed for ranking, LAG/LEAD, and running totals.
  • Frame (ROWS BETWEEN ...) says which rows around the current row feed an aggregate. It is covered in the running-total question.

What it can do: ranking (ROW_NUMBER, RANK), neighbours (LAG, LEAD), running or moving aggregates (SUM, AVG OVER), percent of total (amount / SUM(amount) OVER ()), first/last value per group (FIRST_VALUE), and bucketing (NTILE).

Rules to remember. Windows are evaluated after WHERE, GROUP BY and HAVING, so they see the already filtered and grouped rows. They can appear only in SELECT and ORDER BY, so to filter by a window result you wrap the query. You can mix them with GROUP BY (the window then runs over the grouped output), for example SUM(SUM(amount)) OVER (). Cost: the engine sorts by partition and order columns, so an index matching (partition_cols, order_cols) can avoid the sort.

PARTITION BY splits rows into independent groups without collapsing them. ORDER BY sets the order inside each partition. The optional frame says which neighbouring rows count. Windows run after WHERE, GROUP BY and HAVING, so you cannot filter on them directly: wrap the query in a CTE or subquery and filter outside (Snowflake and BigQuery have QUALIFY; PostgreSQL and MySQL do not). MySQL supports windows from 8.0.

Remember: GROUP BY collapses rows, a window keeps them. OVER (PARTITION BY ... ORDER BY ...).

ROW_NUMBER, RANK, DENSE_RANK and NTILE: what is the difference? Intermediate

All number rows within a partition by the ORDER BY. ROW_NUMBER gives unique 1, 2, 3, 4 and breaks ties arbitrarily. RANK gives ties the same number and then skips: 1, 2, 2, 4. DENSE_RANK gives ties the same number without skipping: 1, 2, 2, 3. NTILE(4) splits rows into four roughly equal buckets.

What do LAG and LEAD do? Give a practical example. Intermediate

LAG(col, n) returns the value from n rows before the current row in the window order, and LEAD looks n rows ahead. They compare a row with its neighbour without a self join. A typical use is month-over-month change.

The problem. "How did revenue change from last month?" needs each row to see the previous row. Without windows you self-join the table to itself with b.month = a.month - 1 (breaks for missing months and year boundaries). LAG hands you the previous row's value directly.

Worked example for the query on this page. monthly_revenue:

January has no previous row, so LAG returns NULL and so do the calculations that use it. Supply a default with the third argument: LAG(revenue, 1, 0) returns 0 instead. The second argument is the offset (LAG(x, 3) is 3 rows back). NULLIF(..., 0) guards the percentage against a division by zero.

Other patterns with the same tool:

  • Time between events: login_at - LAG(login_at) OVER (PARTITION BY user_id ORDER BY login_at) gives the gap since that user's previous login (PARTITION BY makes each user's sequence independent).
  • Detect a change: WHERE status <> LAG(status) OVER (...) inside a wrapper finds each moment a state changed.
  • Session-ising: start a new session when the gap exceeds 30 minutes: a flag column from LAG, then a running SUM of the flag.

Note that LAG looks at the previous row in the sort order, not the previous calendar month, so if March is missing the "previous" of April is February. To compare calendar periods, first generate the full month series and LEFT JOIN the data onto it.

With PARTITION BY the sequence restarts per group, so the first row of each group has no previous row and gets NULL (or your default). The old way was a self join on id = id - 1, which breaks as soon as ids have gaps. Other uses: time between two events of the same user, spotting a status change, and finding gaps between consecutive rows.

SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS change,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS pct
FROM monthly_revenue;

Remember: LAG looks back, LEAD looks ahead, and the first row gets NULL.

How do you compute a running total or moving average? What is a window frame? Senior

I use an aggregate with OVER and an ORDER BY, and I state the frame explicitly: SUM(x) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). The frame decides which neighbouring rows are included. A 7-day moving average is the same with ROWS BETWEEN 6 PRECEDING AND CURRENT ROW.

What a frame is. For each row, an aggregate window function looks at a set of rows around it: the frame. Two things define it: the unit (ROWS counts physical rows, RANGE uses values of the ORDER BY column, GROUPS counts peer groups) and the bounds (n PRECEDING, CURRENT ROW, n FOLLOWING, UNBOUNDED either side).

Worked example. daily_sales: day 1 = 10, day 2 = 20, day 3 = 30, day 4 = 40.

At the start the moving window has fewer rows than the width, so the average uses what exists. If you want NULL until the window is full, compute COUNT(*) OVER (same frame) and show NULL when it is below 7.

The default-frame trap in numbers. Suppose days 2 and 3 both have a row with the same date (two sales on the same day, 20 and 5). With only ORDER BY day, the default is RANGE, which treats same-date rows as peers, so both rows show the total including both (10+20+5 = 35 on each), and a "running" total appears to jump. With ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW you get 30 on the first and 35 on the second (the order between them is arbitrary unless you add a tie-breaker to the ORDER BY).

LAST_VALUE trap: LAST_VALUE(x) OVER (ORDER BY day) returns the current row's value, because the default frame ends at the current row. Add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING to see the true last row of the partition.

Per-group running total: add PARTITION BY account_id so the total restarts for each account, such as a bank statement's running balance. Index on (account_id, day) avoids a big sort.

The trap: when you give ORDER BY but no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE treats rows with the same ORDER BY value as peers, so two rows on the same day both show the total including both. That surprises people. ROWS counts physical rows and gives a true row-by-row total. Add PARTITION BY to restart per group. Also, LAST_VALUE with the default frame returns the current row, not the partition's last row, because the frame stops at the current row; extend it with UNBOUNDED FOLLOWING. Percent of total is amount / SUM(amount) OVER ().

SELECT day, amount,
  SUM(amount) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running,
  AVG(amount) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS avg7
FROM daily_sales;

Remember: write ROWS explicitly. The default RANGE merges rows that tie on the sort key.

How do you filter on the result of a window function, for example top 3 per group? Intermediate

I compute the number in an inner query or CTE, then filter in the outer query. WHERE rn <= 3 in the same query is an error, because window functions are computed in the SELECT step, after WHERE and HAVING.

Why the obvious attempt fails. SELECT ..., ROW_NUMBER() OVER (...) AS rn FROM emp WHERE rn <= 3 is rejected: WHERE runs before the window values exist, so rn is unknown at that point. The solution is to compute in one query level and filter in the next. A CTE is the neat way to do this.

Worked example. emp:

namedept_idsalaryrn after the inner query
Asha190001
Ben180002
Cara170003
Dan160004
Eli250001

The outer WHERE rn <= 3 then drops Dan and returns the other four rows. Numbering restarts in each partition, which is why Eli, in a different department, is 1.

Other filter-on-window problems with the same shape:

  • Latest row per user: ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC), keep rn = 1.
  • Rows above their group average: compute AVG(x) OVER (PARTITION BY g) inside, compare outside.
  • Remove duplicates: keep rn = 1 or delete rn > 1.

Some engines (Snowflake, BigQuery, Teradata) have a QUALIFY clause that filters on window results directly; PostgreSQL and MySQL do not, so the wrapper is the portable pattern. For top-N over a huge table, an index on (dept_id, salary DESC) helps the sort, and a LATERAL subquery with LIMIT (next section) can be faster still.

WITH ranked AS (
  SELECT e.*, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
  FROM emp e
)
SELECT * FROM ranked WHERE rn <= 3;

Pick the function by the tie rule you want: ROW_NUMBER gives exactly 3 rows per group, DENSE_RANK gives everyone in the top 3 salary levels. The same wrapper pattern is behind most "top N per group", "latest row per user" and "remove duplicates" puzzles.

Remember: inner query numbers the rows, outer query filters them.

4. Classic SQL puzzles with worked solutions

These come up again and again. For each one, say the idea first, then write the query. State how you treat ties and NULLs before the interviewer asks.

Find the second highest salary. Basic

I would use DENSE_RANK, because "second highest" almost always means the second distinct value, and it generalises to the Nth and to each department. A simpler version is the maximum of everything below the maximum. Both return NULL or no row when there is no second value, and I say that out loud.

Define "second highest" first. Ask: is it the second distinct value or the second row? Salaries 9000, 9000, 8000: the second distinct is 8000, but the second row is 9000. Interviews normally mean distinct, and saying so shows care.

Why each query works. Data: emp.salary = 9000, 8000, 8000, 7000.

  • MAX below MAX: the inner query returns 9000; the outer takes the largest value below it: 8000. If everyone earns the same, the WHERE leaves no rows and MAX returns NULL (no error).
  • DISTINCT + OFFSET: DISTINCT salaries sorted descending are 9000, 8000, 7000; skip one: 8000. Wrapped in a scalar subquery, "no second value" becomes NULL instead of an empty result.
  • DENSE_RANK: ranks are 9000 to 1, 8000 to 2, 8000 to 2, 7000 to 3. Filter r = 2, then DISTINCT to collapse the tied rows. Change 2 to N for the Nth, add PARTITION BY dept_id for each department.

Wrong answers to avoid:

  • ORDER BY salary DESC LIMIT 1 OFFSET 1 without DISTINCT returns 8000 here, but with 9000, 9000, 8000 returns 9000.
  • RANK instead of DENSE_RANK: ranks are 1, 2, 2, 4, so "rank 3" matches nothing; the third distinct salary would be missed.
  • Using MAX(salary) - 1 or similar arithmetic tricks.

Per department with the employee names: keep the DENSE_RANK subquery but select name, dept_id, salary instead of DISTINCT salary, and filter r = 2. On large tables an index on (dept_id, salary) helps all three.

Salaries 9000, 8000, 8000, 7000 should give 8000. ORDER BY salary DESC LIMIT 1 OFFSET 1 returns 8000 here only by luck: with 9000, 9000, 8000 it returns 9000, which is wrong, unless you add DISTINCT.

-- 1) simplest: NULL if there is no second value
SELECT MAX(salary) FROM emp
WHERE salary < (SELECT MAX(salary) FROM emp);

-- 2) DISTINCT then offset, wrapped so the result is NULL, not "no rows"
SELECT (SELECT DISTINCT salary FROM emp ORDER BY salary DESC LIMIT 1 OFFSET 1) AS second_highest;

-- 3) DENSE_RANK: change 2 to N, add PARTITION BY dept_id for per department
SELECT DISTINCT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM emp
) t WHERE r = 2;

Remember: distinct value, so DENSE_RANK = N. Decide what happens when there is no Nth.

Find duplicate rows, for example duplicate emails. Basic

Group by the column that should be unique and keep groups with more than one row: GROUP BY email HAVING COUNT(*) > 1. To see the full duplicate rows, join that result back to the table. I would also ask whether case or spaces matter, because the real key may be LOWER(TRIM(email)).

Data and result. users:

3a@x.com
4A@x.com

Mechanism. GROUP BY email makes one bucket per distinct email; COUNT(*) is the bucket size; HAVING keeps buckets of size 2 or more. The first query returns (a@x.com, 3). Note that A@x.com is not caught, because it is a different string (in a case-sensitive collation, as PostgreSQL's default is; MySQL's default collations are case-insensitive and would count it, giving 4). That is why the first clarifying question is what "same" means: use GROUP BY LOWER(TRIM(email)) if case and spaces do not matter.

Seeing the actual rows. The aggregate query shows only the value and count. The second query joins back and returns rows 1, 3 and 5 (with their ids), so you can decide which to keep. Window alternative: COUNT(*) OVER (PARTITION BY email) then filter on cnt > 1 in a wrapper.

Duplicates across several columns: list them all in GROUP BY (first_name, last_name, dob).

Preventing the problem: UNIQUE constraint on the normalized value (a unique index on LOWER(email) in PostgreSQL). Creating it fails while duplicates exist, so the clean-up (next question) comes first. NULLs: rows with NULL email form one group in GROUP BY, so filter WHERE email IS NOT NULL if NULL is legitimate.

SELECT email, COUNT(*) AS n
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

SELECT u.*
FROM users u
JOIN (SELECT email FROM users GROUP BY email HAVING COUNT(*) > 1) d USING (email);

After cleaning up, add a UNIQUE constraint (or a unique index on LOWER(email)) so it cannot happen again.

Remember: GROUP BY the key, HAVING COUNT(*) > 1, then add the constraint.

Delete duplicate rows but keep one of each. Intermediate

Decide which row survives (usually the lowest id), number the rows inside each duplicate group with ROW_NUMBER, and delete everything numbered above 1. First run it as a SELECT, take a copy of the doomed rows, and do the delete in a transaction.

Step-by-step with the data from the previous question (ids 1, 3, 5 share a@x.com).

  1. Decide the survivor rule. Here: the lowest id wins (oldest row). It could be newest, or the most complete row.
  2. Number each duplicate group. ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) gives id 1 to 1, id 3 to 2, id 5 to 3, and id 2 (unique) gets 1.
  3. Select the victims: rows with rn > 1: ids 3 and 5.
  4. Delete them. Survivors: 1 and 2.

Safe procedure on production:

BEGIN;
CREATE TABLE users_dup_backup AS
  SELECT * FROM users WHERE id IN (/* the victim select */);
DELETE FROM users WHERE id IN (/* the victim select */);
-- check: SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;  -- must be empty
COMMIT;
ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email);

What about child rows? If orders.user_id points to a deleted duplicate, the foreign key will block the delete (or cascade and lose orders). The right fix is to first re-point children at the survivor: UPDATE orders SET user_id = keep_id ... using a mapping of duplicate id to survivor id, and only then delete.

MySQL self-join form: u1.id > u2.id matches every row that has a lower-id twin, which deletes all but the lowest id. Large tables: delete in batches of a few thousand ids to keep locks short and the transaction log small. Alternative without ids (PostgreSQL): the system column ctid can identify physical rows; or rebuild the table with SELECT DISTINCT ON (email) * into a new table and swap.

-- PostgreSQL / MySQL 8: keep the lowest id per email
DELETE FROM users WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM users
  ) t WHERE rn > 1
);

-- MySQL self-join form
DELETE u1 FROM users u1
JOIN users u2 ON u1.email = u2.email AND u1.id > u2.id;

MySQL does not allow deleting from a table you select from in a plain subquery, which is why the extra wrapper (or the join form) is used. On a huge table delete in batches to avoid long locks and a giant transaction log. Finish by adding the unique constraint.

Remember: number within each group, delete rn > 1, then add a UNIQUE constraint.

I number rows per department with a window function and keep numbers up to 2, using a subquery wrapper. I choose the function by the tie rule: ROW_NUMBER gives exactly 2 rows per department, DENSE_RANK gives everyone in the top 2 salary levels, which may be more than 2 people.

The problem. "Top 2 per department" cannot be done with GROUP BY, because GROUP BY collapses rows and LIMIT applies to the whole result, not per group. You need a ranking that restarts for each department.

Worked example. emp:

The LATERAL alternative. For each department row, run a small query that fetches only its top 2 and stop. With an index on (dept_id, salary DESC) each lookup reads 2 index entries. Gaps and islands: find ranges of consecutive numbers or dates. Senior

I subtract the row number from the value. Inside a run of consecutive values both rise by one, so the difference is constant; a skipped value changes it. I group by that difference and take MIN and MAX. For ids 1, 2, 3, 5, 6, 9 this gives islands 1 to 3, 5 to 6 and 9 to 9.

The definitions. Take a sorted column of ids. An island is a maximal run of consecutive values (1, 2, 3). A gap is a stretch of missing values between islands (4). Typical uses: missing invoice numbers, uninterrupted login streaks, continuous periods a sensor was online.

Why subtracting the row number works. ROW_NUMBER increases by exactly 1 per row. Inside an island the value also increases by exactly 1 per row, so value minus row number stays constant. When a value is skipped, the value jumps by 2 or more while the row number still goes up by 1, so the difference increases and a new island begins. The constant itself is meaningless; it is just a label for the island, so you GROUP BY it.

Group by grp: grp 0 gives MIN 1, MAX 3, len 3; grp 1 gives 5, 6, len 2; grp 3 gives 9, 9, len 1.

Gaps are easier with LEAD. Next to each id put the next id; if next_id > id + 1, the missing range is id+1 to next_id - 1. Here: after 3, next is 5, so gap 4..4; after 6, next is 9, so gap 7..8. The last row has a NULL next and is skipped automatically.

Pitfalls: duplicates in the column break the arithmetic (two rows with the same value get different row numbers), so DISTINCT first. For dates, subtract the row number in days. This technique also works for "same status for consecutive rows": rank the whole sequence, rank within each status, and subtract the two row numbers to label each streak.

SELECT MIN(id) AS island_start, MAX(id) AS island_end, COUNT(*) AS len
FROM (
  SELECT id, id - ROW_NUMBER() OVER (ORDER BY id) AS grp FROM seq
) t
GROUP BY grp
ORDER BY island_start;          -- 1..3, 5..6, 9..9

-- the gaps, using LEAD
SELECT id + 1 AS gap_start, next_id - 1 AS gap_end FROM (
  SELECT id, LEAD(id) OVER (ORDER BY id) AS next_id FROM seq
) t WHERE next_id > id + 1;      -- 4..4, 7..8

For dates, subtract the row number as days (day - rn * INTERVAL '1 day' in PostgreSQL, DATE_SUB(day, INTERVAL rn DAY) in MySQL). If duplicates are possible, apply DISTINCT first or use DENSE_RANK.

Remember: value minus ROW_NUMBER is constant inside an island. Group by it.

Find users who logged in on 3 or more consecutive days. Senior

First reduce to one row per user per day, because a user can log in many times a day. Then use the same island trick: date minus row number (in days) is constant across a streak. Group by user and that value, and keep groups with at least 3 days.

Plan in three moves. (1) One row per user per day, otherwise two logins on the same day produce two row numbers and break the arithmetic. (2) Label each streak with day - row_number. (3) Group by user and label and count.

Trace for one user. Login days: 2025-03-01, 03-02, 03-03, 03-05 (extra logins on 03-02 collapsed by DISTINCT).

The first three days share the label 02-28, a group of 3, so the user qualifies, with streak 03-01 to 03-03. The 03-05 login is a separate group of 1. The label date is not a real login date; it is only an identifier for the streak.

The LEAD shortcut, and why it works. If the row two positions ahead (after dedup and sorting) is exactly day + 2, then there are exactly 3 distinct consecutive days: day, day+1, day+2. Because days are distinct and sorted, the only way the second-next day can be 2 days later is if the day between exists. This only fits a fixed length; for "N or more" change the offset to N-1, or use the grouping version.

Edge cases to mention: time zones (does a login at 23:30 UTC count for the next day locally?), login_at::date versus DATE(login_at) in MySQL, and whether the streak must end today ("current streak"), which adds a filter on the max day.

-- PostgreSQL
WITH d AS (
  SELECT DISTINCT user_id, login_at::date AS day FROM logins
), g AS (
  SELECT user_id, day,
         day - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day))::int AS grp
  FROM d
)
SELECT user_id, MIN(day) AS from_day, MAX(day) AS to_day, COUNT(*) AS streak
FROM g GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

-- shorter for exactly "3 in a row": the date two rows ahead is exactly 2 days later
SELECT DISTINCT user_id FROM (
  SELECT user_id, day,
         LEAD(day, 2) OVER (PARTITION BY user_id ORDER BY day) AS day_plus_2
  FROM d
) t WHERE day_plus_2 = day + 2;

The LEAD version is short for a fixed length; the island version handles any length and gives start and end dates. In MySQL use DATE_SUB(day, INTERVAL rn DAY) and DATEDIFF(day_plus_2, day) = 2.

Remember: distinct days first, then date minus row number, then HAVING COUNT(*) >= 3.

For "never ordered" I use NOT EXISTS, which is clear and safe with NULLs. A LEFT JOIN with WHERE o.id IS NULL is the equivalent anti-join. For "more than one order" I group orders by customer and use HAVING.

5. Indexes

What is an index, and how does a B-tree index make a query fast? Basic

An index is a separate sorted structure over one or more columns, with pointers back to the rows, like the index at the back of a book. Without it, WHERE email = ... reads every row. The default type is a B-tree: a shallow, wide tree of pages, so even a hundred million rows need only about 4 page reads to find one key.

The problem. A table of 100 million users is stored in no particular order. SELECT * FROM users WHERE email = 'a@x.com' has no choice but to read every row (a full table scan) because the email could be anywhere. That takes seconds, and every extra user makes it slower in proportion.

What an index changes. The database keeps a second structure containing only (email, pointer to row) pairs, sorted by email. Finding a name in a sorted list is a search, not a scan, like looking in the back-of-book index instead of reading the whole book.

Why a tree and not just a sorted array. A sorted array is slow to insert into (you shift everything). A B-tree keeps the keys sorted in pages (blocks of typically 8 KB or 16 KB, the unit the disk and memory cache work in) arranged in levels:

  1. The root page holds a few hundred separator keys and pointers to child pages, e.g. "keys below 30 go left, 30 to 60 go middle, above 60 go right".
  2. Internal pages repeat the idea one level down.
  3. Leaf pages hold the actual sorted keys with the row pointers, and each leaf links to the next one.

The numbers. If a page holds about 300 entries, then 2 levels reach 300 x 300 = 90,000 keys, 3 levels about 27 million, 4 levels about 8 billion. So a lookup in a 100 million row table touches roughly 4 pages, and the top 2 or 3 pages are always cached in memory. That is why an indexed lookup takes microseconds to a millisecond, versus seconds for a scan.

A lookup, step by step (find 44 in the figure): read the root (30 | 60), 44 is between 30 and 60, follow the middle pointer; read the internal page (40 | 50), 44 is between 40 and 50, follow the pointer; read the leaf (40 44 48), find 44, follow its row pointer to the table row. A range query like BETWEEN 44 AND 55 finds 44 the same way and then walks right through the linked leaves until a key exceeds 55. ORDER BY on the indexed column needs no sort for the same reason.

Writes. Inserting a key goes into its leaf. If the leaf is full it splits into two, and the parent gets a new separator; this keeps the tree balanced automatically. That bookkeeping is why each index slows INSERT and UPDATE a little.

What a B-tree cannot do: search by the end of a string (LIKE '%son'), or by a column that is not the first in a composite index. Those cases come up in the questions below.

The root page points to a few hundred child pages, each covering a key range, down to leaf pages that hold the sorted keys and row pointers. Leaves are linked in order, so range queries (BETWEEN, >), ORDER BY without a sort and prefix matches like LIKE 'abc%' are fast too. The tree is wide and shallow because disks read whole pages, so each node is a full page. The price: every INSERT, DELETE and UPDATE of an indexed column must also update the index, and indexes use disk and memory. A UNIQUE or PRIMARY KEY constraint is backed by a unique index.

Remember: B-tree = wide, shallow, sorted. Fast for equality, ranges and ORDER BY, at the cost of slower writes.

What is a clustered index? How does InnoDB differ from PostgreSQL here? Senior

In MySQL InnoDB the table itself is a B-tree ordered by the primary key, so the leaf pages contain the full rows. In PostgreSQL the table is an unordered heap and every index, including the primary key, points to a row location. So the primary key choice matters much more in InnoDB.

Two ways to store a table.

  • Heap (PostgreSQL): rows are stored in the table file in insertion order, wherever there is space. Every index, including the primary key's, is a separate structure whose entries point at the row's physical address (a block number and slot, called a ctid). The PK index has no special status.
  • Clustered (InnoDB, SQL Server): the table is a B-tree sorted by the primary key, and the leaf pages contain the full rows. There is no separate heap.

Consequences of InnoDB's design.

  • The PK is stored in every secondary index entry, so a 16-byte random PK adds 16 bytes to every entry of every index. Keep it short and sequential.
  • Inserts in PK order append at the right edge; random PKs scatter inserts and cause page splits.
  • Selecting only columns that are in a secondary index (it already includes the PK) avoids the second tree walk: this is a covering index.

Consequences of PostgreSQL's design. An UPDATE writes a whole new row version (MVCC). If the new version cannot stay on the same page, or an indexed column changed, every index needs a new entry (write amplification). A HOT update avoids it when no indexed column changes and there is room on the same page. Old versions are removed by VACUUM. CLUSTER sorts the heap once by an index but does not maintain the order afterwards.

Interview angle: "why is a UUIDv4 primary key worse in MySQL than in PostgreSQL?" Because in InnoDB it determines the physical order of the entire table and gets copied into every secondary index.

In InnoDB every secondary index stores its key plus the primary key value, so a secondary lookup finds the primary key and then does a second lookup in the clustered tree. A long or random primary key (text, UUIDv4) makes every index bigger and slower. Primary key range scans are very fast, and insert order matters. If you define no primary key, InnoDB picks the first non-null unique index or makes a hidden 6-byte id, so always define one. In PostgreSQL an UPDATE writes a new row version in a new place, so indexes may need new entries too (unless it is a HOT update that stays on the same page and touches no indexed column). The CLUSTER command rewrites the table in index order once, but does not keep it that way. SQL Server also has clustered indexes, like InnoDB.

Remember: InnoDB: rows live inside the primary key tree, so keep it short and sequential. PostgreSQL: heap plus separate indexes.

What is a composite index and the leftmost prefix rule? How do you choose column order? Intermediate

A composite index covers several columns, such as (customer_id, status, created_at). It is sorted by the first column, then by the second inside equal first values, like a phone book sorted by last name then first name. So it helps queries that fix a leftmost prefix of its columns, but not a query on status alone. For column order I put equality columns first, then the range column, then columns used for sorting.

Why order matters, with the phone-book picture. A phone book is sorted by last name, then by first name inside the same last name. You can quickly find "Smith", or "Smith, John". You cannot quickly find every "John", because Johns are scattered through the whole book. The same holds for INDEX (customer_id, status, created_at): entries are sorted by customer_id first, and only among equal customer_ids by status, and only among equal (customer_id, status) pairs by created_at.

Which queries benefit (index on (a, b, c)):

WHEREUses index how?
a = 1seek on a
a = 1 AND b = 2seek on a, b
a = 1 AND b = 2 AND c > 5seek on a, b, then a range on c
a = 1 AND c = 5seek on a only; c is checked row by row inside that a-range (it can be checked in the index, but not sought)
b = 2cannot seek (b values are scattered across every a)
a > 1 AND b = 2range on a; b is only a filter, because within a range of a the b values are not contiguous

How to choose the order, with an example. Query: WHERE customer_id = ? AND status = 'PAID' AND created_at > ? ORDER BY created_at. Equality columns first (customer_id, status), then the range/sort column (created_at). The index (customer_id, status, created_at) seeks directly to the start and reads in sorted order, with no sort step. If you swapped it to (created_at, customer_id, status), the engine would have to scan all rows after that date and filter, much worse.

Tie-breakers between equality columns: put the more selective column first only if some queries use it alone; otherwise the order among equality columns matters little, and a column used alone in other queries should lead so one index serves several queries. Remember an index (a, b) makes a separate index on (a) redundant, but not one on (b).

Cost. Wider indexes mean more writes and space; do not build one per query. Look at your top 5 to 10 queries and design a few composite indexes that serve them all.

A range condition stops later columns from being used for seeking: with customer_id = 5 AND status > 'A' AND created_at > ... the index seeks on the first two and scans on the third. The index also serves WHERE customer_id = 5 ORDER BY status without a sort, because within one customer the rows are already sorted by status. A single-column index that is a prefix of a composite one is redundant. MySQL 8.0.13 has some skip-scan ability and PostgreSQL 18 added a skip scan for B-trees, but I do not depend on it when the first column has many values.

Remember: leftmost prefix. Order columns: equality, then range, then sort.

What is a covering index (index-only scan)? Intermediate

Normally an index finds the matching entries and then fetches each row from the table to read the other columns, which is random IO and often most of the cost. A covering index contains every column the query needs, so the database answers from the index alone. EXPLAIN shows "Index Only Scan" in PostgreSQL and "Using index" in MySQL.

Two steps in a normal index lookup. (1) Search the index for matching keys. (2) For each match, follow the pointer to the table to fetch the remaining columns. Step 2 is a random page read per row, and for a query returning 5,000 rows that can be 5,000 extra page reads, which usually dominates the cost.

A covering index removes step 2 because the index already contains all columns the query touches, in SELECT, WHERE, ORDER BY and GROUP BY. The index "covers" the query.

Example. Table orders(id, customer_id, created_at, total, notes ...).

-- query
SELECT created_at, total FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;

-- index A (not covering): (customer_id, created_at)
--   finds 20 index entries in order, then 20 table fetches for total
-- index B (covering): (customer_id, created_at) INCLUDE (total)   -- PostgreSQL 11+
--   all data is in the index leaf: 0 table fetches

In the plan you want Index Only Scan (PostgreSQL) or Using index in the Extra column (MySQL). In PostgreSQL also check Heap Fetches: 0. A non-zero number means many pages are not marked all-visible, so it still visited the table (VACUUM fixes this). For InnoDB, a secondary index automatically contains the primary key, so a query selecting only id and indexed columns is covered for free.

Why not INCLUDE everything: payload columns bloat the index, slowing writes and filling the cache. And updating an included column changes the index. Use it for a hot query and measure. Large TEXT/JSON columns should never be included.

INCLUDE versus adding to the key: INCLUDE columns are not sorted or searchable, but they do not have to follow key rules, and in PostgreSQL they can be used in a unique index without becoming part of the uniqueness check, which is a useful detail.

PostgreSQL 11 added INCLUDE columns: stored in the leaf but not used for ordering, so you can add payload columns cheaply. In MySQL you add the extra columns as normal key columns. In PostgreSQL an index-only scan also depends on the visibility map that VACUUM maintains; on a table with many recent changes it still visits the table to check visibility. Do not cover everything: wider indexes cost more on every write.

CREATE INDEX idx_orders_cust_cover ON orders (customer_id, created_at) INCLUDE (total);
SELECT created_at, total FROM orders
WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;   -- no table access

Remember: all needed columns in the index means no trip to the table.

My query has an index but it is not used. What are the common reasons? Intermediate

Most often it is one of these: a function or expression on the column, a type or collation mismatch that forces a cast, a leading wildcard in LIKE, a broken leftmost prefix, or low selectivity, where reading the whole table really is cheaper. Stale statistics are the next suspect. I check the plan before touching anything.

Start with the question the planner is asking. For each candidate access path it estimates the cost. An index is chosen when it is expected to touch few pages. So there are two families of reasons: the index cannot be used for this predicate (the query is not sargable), or it can but would be more expensive (not selective, or statistics are wrong).

Why not index every column? Basic

Because every index is a copy of data that must be kept in sync. An INSERT writes the row plus one entry in every index, and a DELETE or an update of an indexed column changes them too. Ten indexes means about eleven writes per insert, plus more disk, memory pressure and replication traffic.

What happens on one INSERT into a table with a primary key and 4 secondary indexes: the row goes into the table, and an entry goes into each of 5 B-trees (each at its own sorted position, so each may touch a different page, and may split a page). Each page change is also written to the write-ahead log, and each index change is sent to replicas. So one logical write becomes about 6 physical writes.

Index every column? It also does not help: most of them would never be used, and a composite index is needed for multi-column filters anyway. A rough practical rule is that each index you add makes bulk loads noticeably slower, so for a large import, drop or defer the secondary indexes, load, then create them.

How I decide what to keep. (1) Primary and unique constraints are mandatory. (2) Foreign key columns (for joins and deletes). (3) Columns in frequent WHERE, JOIN, ORDER BY of real queries, found from the slow query log. (4) Remove indexes that are unused (check usage statistics over a full business cycle, because month-end reports count) or that are a prefix of another.

Rule of thumb: read-heavy OLTP can carry about 5 to 8 indexes per table comfortably; a write-heavy event table should have as few as one or two. Those figures are judgement, not law; measure write throughput after adding.

The aim is the smallest set of indexes that serves the real queries. I look for unused indexes (PostgreSQL pg_stat_user_indexes with idx_scan = 0, MySQL sys.schema_unused_indexes) and redundant ones that are the prefix of another. A read-mostly table can afford more indexes than a write-heavy log table.

Remember: indexes speed reads and tax writes. Keep only the ones real queries use.

Beyond B-tree: when would you use hash, GIN, GiST or BRIN indexes? Senior

B-tree for almost everything. GIN for "contains" searches on JSONB, arrays and full text. GiST for spatial data, ranges and exclusion constraints. BRIN for huge append-only tables ordered by time. Hash only for pure equality, and almost never beats a B-tree.

Why more than one type exists. A B-tree orders values on a line. That is perfect for numbers, dates, short strings. It is the wrong shape for questions like "which documents contain the word cache", "which JSON rows have tags containing x", "which shapes overlap this rectangle", or "rows in this 100 GB table from last week".

  • GIN (generalized inverted index): built like the index at the back of a book. For each element (a word, an array item, a JSON key and value) it stores the list of rows that contain it. Query WHERE tags @> ARRAY['sql'] looks up "sql" and gets its row list directly. Reads are fast; writes are slower because one row can add many entries (PostgreSQL batches these with a pending list).
  • GiST: a general balanced tree that stores bounding regions (rectangles, ranges) instead of single values. Good for "overlaps", "contains", "nearest to". It also powers exclusion constraints such as "no two bookings for the same room may overlap in time".
  • BRIN (block range index): stores only the minimum and maximum of each group of adjacent pages. A query on a time range skips whole blocks that cannot contain it. The index is tiny (kilobytes for a table of hundreds of GB), but only works if the column's values correlate with the physical order, such as an append-only log's timestamp. On shuffled data it prunes nothing.
  • Hash: equality only; no range, no sorting. A B-tree is already almost as fast for equality, so a hash index is rarely worth it.

Pick by the question, not the column type: equality or range on scalars: B-tree. "Contains" on JSONB, arrays, text search, or fuzzy LIKE (pg_trgm): GIN. Geometry, ranges and non-overlap: GiST. Giant append-only time-ordered table: BRIN, or partitioning by time.

MySQL/InnoDB comparison: B-tree, FULLTEXT (an inverted index for word search), spatial (R-tree). For JSON, index a generated column or a functional index on the path you query. In practice, search-heavy workloads may be better in a search engine (Elasticsearch); the database index is enough for moderate needs.

What are partial and expression indexes, and when are they useful? Senior

A partial index (PostgreSQL) covers only rows matching a condition, so it is small and cheap. An expression index indexes a computed value such as LOWER(email). Combined, a unique partial index enforces "email unique among rows not soft-deleted", the standard answer to the soft-delete plus unique-email problem.

Partial index: only index some rows. Take an orders table with 50 million rows where 1 percent are status = 'PENDING'. A worker repeatedly asks for the oldest pending orders. A normal index on (status, created_at) stores all 50 million entries. A partial index stores only the 500,000 pending ones:

CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status = 'PENDING';

SELECT * FROM orders WHERE status = 'PENDING' ORDER BY created_at LIMIT 100;  -- uses it
SELECT * FROM orders WHERE status = 'SHIPPED' ORDER BY created_at LIMIT 100;  -- cannot

The index is about 100 times smaller, stays in memory, and when an order stops being pending its entry is removed (so it does not grow as history accumulates). The planner uses it only when the query's WHERE clearly implies the index condition, so the query must repeat status = 'PENDING' with a constant.

Soft delete plus unique, the classic case. Users can be "deleted" by setting deleted_at, and later a new account with the same email may register. A plain UNIQUE (email) would reject it. The partial unique index (email) WHERE deleted_at IS NULL enforces uniqueness only among live rows: two deleted rows with the same email are allowed, one live row is allowed.

Expression index: index a computed value. WHERE LOWER(email) = 'a@x.com' cannot use an index on email. CREATE INDEX ON users (LOWER(email)) stores the lowercase value, so it works, but only if the query uses the exact same expression. Same for DATE(created_at) or a JSON path. MySQL 8.0.13+ offers functional indexes. MySQL has no partial indexes; use a generated column that is NULL for the rows to exclude and put a unique index on it (unique indexes allow many NULLs).

Trade-off: they are narrowly targeted, so document why they exist, or someone will drop one as "odd".

If 2 percent of orders are PENDING and a worker only reads those, CREATE INDEX ON orders (created_at) WHERE status = 'PENDING' is tiny and fast; the query must repeat the condition to use it. MySQL has no partial indexes, but you can get a similar effect with a generated column that is NULL for deleted rows plus a unique index on it, since unique indexes allow multiple NULLs.

CREATE UNIQUE INDEX uq_users_email_active ON users (email) WHERE deleted_at IS NULL;

Remember: index only the rows you query, or enforce uniqueness on a subset.

6. Query plans and tuning

A query is slow. How do you approach it? Intermediate

I measure first, I do not guess. Find the exact slow statement (slow query log or pg_stat_statements), run it with EXPLAIN (ANALYZE, BUFFERS) on realistic data, find the most expensive step, fix that one thing (an index, a rewrite, fresher statistics), and run it again to compare.

Why measure first. Slow has many causes (missing index, bad plan, locks, too many calls, network, pool starvation), and each fix is different. An index added on a guess can cost writes and fix nothing.

The routine, in order:

  1. Find the real offender. From users' complaint to a concrete statement: slow query log (MySQL long_query_time), pg_stat_statements (sort by total time, not only by average, since a 5 ms query run 10 million times costs more than a 2 s query run twice), APM traces, and the database's wait events.
  2. Reproduce it with realistic data and parameters. The same SQL can be fast on a dev table with 1,000 rows and slow on 100 million. A rare parameter value (a huge tenant) can pick a different plan.
  3. Read the plan with EXPLAIN (ANALYZE, BUFFERS). Find the node with the most time or buffers. Compare estimated and actual rows.
  4. Fix one thing at a time: index, rewrite (sargable condition, fewer columns, keyset instead of OFFSET), statistics refresh, or reduce the work (cache, pre-aggregate).
  5. Re-measure and compare before and after. Check that writes did not suffer and that other queries did not regress.

Typical findings and fixes, in a table:

If the query is quick on its own but slow in production, look for lock waits (pg_stat_activity, pg_locks, InnoDB lock waits) and a connection pool that is exhausted because other requests hold connections.

What I look for in the plan: a full scan of a big table where I expected an index, a large gap between estimated and actual rows (bad statistics), a sort or hash spilling to disk, a nested loop running millions of times, or the query fetching far more rows than it returns. Then I check the query itself: SELECT *, functions on indexed columns, OFFSET on deep pages, N+1 calls from the application. If the query is already fine, the cause may be outside it: lock waits, an exhausted connection pool, or a cold cache.

Remember: find it, EXPLAIN ANALYZE it, fix the biggest step, measure again.

How do you read an EXPLAIN plan? What do you look for? Intermediate

A plan is a tree of steps. The database runs it from the innermost, deepest steps outward, and each step shows its estimated cost and rows. Plain EXPLAIN only estimates. EXPLAIN ANALYZE really runs the query and adds actual times and row counts, so I compare estimated rows with actual rows to see where the planner guessed wrong.

What EXPLAIN is. The planner turns your SQL into an execution plan: a tree of operators, such as scan, join, sort, aggregate. EXPLAIN prints it. You read it to learn how the database will (or did) run the query, which the SQL text does not tell you.

A small PostgreSQL plan, annotated.

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20;

Limit  (cost=0.43..8.5 rows=20) (actual time=0.05..0.12 rows=20 loops=1)
  -> Index Scan Backward using idx_orders_cust_created on orders
       (cost=0.43..420.1 rows=1040) (actual time=0.05..0.11 rows=20 loops=1)
       Index Cond: (customer_id = 42)
       Buffers: shared hit=24
Planning Time: 0.2 ms   Execution Time: 0.15 ms

How to read it: the indented child runs first and feeds the parent. cost=a..b is in arbitrary planner units: a is the startup cost (before the first row), b the total. rows is the estimate; the second set of numbers is the measurement. Here the scan could have returned 1040 rows but the Limit stopped it after 20: no separate sort, because the index is already in order. Buffers: shared hit=24 means 24 pages were found in the cache; read= would be disk reads.

The checklist when reading any plan:

  1. Scan type per table and whether it is the one you expected.
  2. Estimated versus actual rows at each node. A factor of 10 or more off is the clue to bad statistics.
  3. loops: time and rows shown are per loop; multiply by loops to get the total. A node with actual time=0.1 and loops=100000 is 10 seconds.
  4. Join order and type (nested loop, hash, merge) against the data sizes.
  5. Sort or hash spilling to disk, and "Rows Removed by Filter" being far larger than the rows returned.
  6. Which node has the largest share of total time.

MySQL notes: EXPLAIN FORMAT=TREE and EXPLAIN ANALYZE (8.0.18+) give the tree with timings. In the classic table output, the key column is the index chosen, rows the estimate, type the access method, and Extra shows Using index (good), Using filesort and Using temporary (investigate).

The scan types, from cheap to expensive for selective queries: Index Only Scan (no table access), Index Scan (index then table), Bitmap Heap Scan (collect matches from one or more indexes, then read the table in page order), and Seq Scan (read everything). A Seq Scan is not automatically bad: on a small table, or when most rows match, it is the fastest. Watch the actual numbers: rows=1 loops=50000 means 50,000 repeats. Rows Removed by Filter shows work thrown away. Sort Method: external merge Disk means a sort spilled to disk. In MySQL, EXPLAIN ANALYZE exists since 8.0.18; the type column goes from const and ref (good) to ALL (full scan), and Using filesort or Using temporary are the warning signs. Warning: EXPLAIN ANALYZE executes the statement, so wrap an UPDATE or DELETE in a transaction and roll back.

Remember: compare estimated and actual rows, check scan type and loops, and remember ANALYZE really runs the query.

What join algorithms does the database use, and when does each win? Senior

Three. Nested loop: for each row of the outer side, look up matches on the inner side through an index; best when the outer side is small and the inner side is indexed. Hash join: build a hash table of the smaller input and probe it with the other; best for big, unsorted, unindexed inputs and equality joins. Merge join: walk two inputs that are already sorted in step; best when both come sorted from indexes or sorts are cheap.

Setup for a worked comparison. Join orders (outer, filtered to 20 rows) to customers (1 million rows, primary key on id) on customers.id = orders.customer_id.

  • Nested loop. Pseudocode: for each of the 20 orders: look up customers by PK. That is 20 index probes of about 4 pages each, so about 80 page reads. Very cheap. But if the outer side had 5 million rows, that is 5 million probes: ruinous. Strength: low startup cost, great with a small outer side plus an index on the inner join column, and it supports any join condition (including inequalities).
  • Hash join. Phase 1 (build): read the smaller input and put rows into an in-memory hash table keyed by the join column. Phase 2 (probe): stream the larger input and look each row up in the hash table. Each input is read once, so cost grows linearly with the data. Needs equality conditions and memory; if the hash table exceeds work_mem PostgreSQL splits both inputs into batches written to temporary files, which is much slower. Best for joining big tables with no useful index, as in reporting queries.
  • Merge join. Both inputs sorted by the join key, then two pointers move forward together, matching equal keys, like merging two sorted lists. If both sides come already sorted from indexes it is very efficient and streams with little memory; otherwise the sorts dominate. Good for big sorted inputs and for when the output also needs that order.
SituationLikely winner

Troubleshooting link to statistics. A nested loop over a million outer rows is a classic sign the planner expected a handful of rows. Fix the estimate (statistics, a better index) and the join type changes by itself. You can disable an algorithm temporarily in a session in PostgreSQL (SET enable_nestloop = off) to test a theory, never as a permanent setting.

Cost rules of thumb: nested loop is roughly outer rows times one index lookup, which is excellent for 20 rows and awful for 2 million. Hash join reads each side once but needs memory (work_mem in PostgreSQL); if it does not fit, it spills to disk in batches. Merge join handles non-equality ranges poorly but supports big sorted data. MySQL used only nested-loop variants until 8.0.18 added hash join. When a plan picks a nested loop over a huge outer side, the usual cause is an underestimated row count, so I fix the statistics first.

Remember: nested loop for small plus indexed, hash for big equality joins, merge for presorted inputs.

The planner picked a bad plan. Why does that happen and what do you do? Senior

The planner chooses by estimated cost, and the estimates come from statistics: row counts and value distributions it sampled earlier. If the statistics are stale, or the data is skewed or correlated in a way the sampling misses, the estimate is off and the plan is wrong. My first fix is to refresh statistics, not to add hints.

What the planner knows. It cannot count rows quickly, so it keeps summaries per column: the number of rows, the number of distinct values, the most common values with their frequencies, and a histogram of the rest. From these it estimates how many rows a predicate returns (its selectivity), and from that, costs.

How a bad plan arises, with a concrete case. orders.status: 99 percent are 'DONE', 0.5 percent 'PENDING'. The stats show that, so status = 'PENDING' is correctly estimated as a few thousand rows and uses an index, while status = 'DONE' gets a seq scan. Now suppose a bulk job inserts 20 million PENDING rows and statistics have not been refreshed: the planner still believes PENDING is rare, picks an index nested loop, and the query takes minutes instead of seconds. ANALYZE orders fixes it.

Why hints are last. A forced index or join order is correct only for today's data; after growth it can become the slow plan, and nobody remembers why it is there. Use hints for a short, documented emergency fix while you correct the underlying statistics or schema.

  • Skewed columns: raise the statistics target for that column, or in PostgreSQL create extended statistics for correlated columns (CREATE STATISTICS), for example city and zip code.
  • Parameter sniffing and generic plans: a prepared statement may reuse a plan built for a typical value that is terrible for a rare one. PostgreSQL switches between custom and generic plans by itself; plan_cache_mode can force one.
  • Rewrite so the estimate is easier: avoid a function on the column, split a huge OR, use a CTE or a temp table to give the planner a real row count.
  • Hints (MySQL optimizer hints, pg_hint_plan extension) are the last resort, because they hide the problem and break when data changes.

Remember: a bad plan is usually bad statistics. ANALYZE first, hints last.

Why is OFFSET pagination slow on deep pages, and what is the alternative? Intermediate

With LIMIT 20 OFFSET 100000 the database still has to produce and throw away the first 100,000 rows, so page 5,000 is much slower than page 1. The alternative is keyset (seek) pagination: remember the last row's sort key and ask for rows after it, using an index, so every page costs the same.

Why OFFSET gets slower, concretely. A database cannot jump to row 100,001 of an ordered result; rows are not numbered. For ORDER BY created_at DESC LIMIT 20 OFFSET 100000 it walks the index in order, producing 100,020 rows, discards the first 100,000, and returns 20. Page 1 reads 20 rows, page 5,000 reads 100,000, so the time grows linearly with the page number. Heavy deep-page requests (a crawler walking every page) can tie up the database.

Keyset pagination, step by step. Data sorted newest first, with (created_at, id) as the key. Page size 3:

RequestQueryRows returned (created_at, id)
page 1ORDER BY created_at DESC, id DESC LIMIT 3(10:05, 9) (10:04, 8) (10:04, 7)
page 2WHERE (created_at, id) < ('10:04', 7) ... LIMIT 3(10:03, 6) (10:02, 5) (10:02, 4)

The client sends back the last row's key. The database uses the index (created_at DESC, id DESC) to seek straight to the point after (10:04, 7) and reads 3 entries. Every page costs the same, however deep. The id tie-breaker matters: two rows at 10:04 would otherwise be skipped or repeated at a page boundary.

Another benefit: stability. With OFFSET, if a new row is inserted at the top while a user reads, every later page shifts by one and the user sees a repeated row (or misses one after a delete). Keyset anchors to a row, so it does not.

Offset also gives duplicates or missing rows when data changes between pages; keyset is stable. APIs usually expose the cursor as an opaque token. For "total pages" a count is its own slow query, so many products show only "next".

Remember: OFFSET reads and discards. Keyset seeks. Add a unique tie-breaker.

What is the N+1 query problem and how do you fix it? Basic

N+1 means one query to load a list, then one more query per row to load something related: 1 query for 100 orders plus 100 queries for their customers. Each query is fast, but the round trips add up and the database gets hammered. Fix it by loading the related data in one go with a JOIN or a batched WHERE id IN (...).

A concrete example, in numbers. A page shows 100 orders and each customer's name.

-- N+1: the app does this
SELECT * FROM orders ORDER BY created_at DESC LIMIT 100;      -- 1 query
SELECT * FROM customers WHERE id = 7;                         -- then 100 of these, one per order
SELECT * FROM customers WHERE id = 12;
...

-- Fix 1: one JOIN
SELECT o.*, c.name FROM orders o JOIN customers c ON c.id = o.customer_id
ORDER BY o.created_at DESC LIMIT 100;                         -- 1 query

-- Fix 2: batch fetch (good when joining would multiply rows)
SELECT * FROM customers WHERE id IN (7, 12, 31, ...);         -- 2 queries total

Why it hurts: each query costs a network round trip (say 1 ms) plus parsing and a connection from the pool, regardless of how small it is. 101 queries at 1 ms is 100 ms of pure latency, and under load 100 concurrent pages mean 10,000 queries per second against the database. It grows with the data (N), so it is invisible in tests with 3 rows and a disaster in production with 500.

Where it hides. ORM lazy loading in loops; GraphQL resolvers that load per field; microservice calls inside a loop (the same problem over HTTP: use a batch endpoint). The GraphQL fix is a DataLoader that collects the ids and queries once per request.

Choosing the fix (JPA example):

  • Many-to-one or one-to-one (order to customer): JOIN FETCH, or @EntityGraph.
  • One-to-many (customer to orders) with paging: first query the page of parents, then WHERE parent_id IN (...) for the children, or use batch fetching, because joining a collection multiplies parent rows and Hibernate then pages in memory.
  • Joining two collections at once creates a Cartesian product of both lists; fetch them separately.

Detect it: turn on SQL logging in a test and assert the statement count per request (the datasource-proxy or Hibernate statistics), and watch for one statement with an enormous call count in pg_stat_statements.

It usually hides inside an ORM, where touching a lazy relation (order.getCustomer()) fires a query. In JPA/Hibernate use JOIN FETCH, an entity graph, or batch fetching (@BatchSize); in Django select_related and prefetch_related. Be careful: joining a collection into a paged query multiplies rows and breaks paging, so fetch the page of parents first, then the children with IN. I find N+1 by logging the SQL count per request in tests, or seeing the same statement thousands of times in pg_stat_statements.

Remember: 1 query for the list plus N for the children. Fetch the children in one batch.

Why is SELECT * discouraged, and what is a "sargable" condition? Intermediate

SELECT * reads and ships every column, wasting IO and network, and it blocks index-only scans. It also breaks code when a column is added. A condition is sargable (search-argument-able) when the database can use an index to evaluate it, which means the bare column on one side compared to a value, with no function wrapped around the column.

Why SELECT * costs more than it looks. (1) It prevents an index-only scan, because the index would have to contain every column. (2) It reads wide columns (text, JSON, blobs) that may live in separate storage (TOAST in PostgreSQL, off-page in InnoDB) just to throw them away. (3) It sends more bytes to the application, and uses memory there. (4) It is fragile: a new column silently changes the result shape, and INSERT ... SELECT * breaks when column order differs. Name the columns. Using SELECT * for ad-hoc exploration or in EXISTS (SELECT 1 ...) contexts is harmless.

What "sargable" means. SARG stands for "search ARGument": a predicate the engine can answer by seeking in an index. The index is sorted by the raw column value. If the predicate is of the form column OP constant, the engine seeks to the constant. If you wrap the column in an expression, the sorted order of the raw column no longer helps, because the order of YEAR(created_at) values is not the order the index stores, so it has to compute the expression for every row: a full scan.

Examples with the reason:

  • WHERE YEAR(created_at) = 2026: computed per row. The rewrite is a range on the bare column, which the index can seek: first entry at 2026-01-01, read until 2027-01-01.
  • WHERE price * 1.2 > 100: move the math to the constant side. price > 83.33.
  • WHERE COALESCE(status, 'X') = 'X': rewrite as status = 'X' OR status IS NULL, or index the expression.
  • WHERE col = '5' where col is an integer is fine (the constant is converted), but the reverse, an indexed text column compared with a number, converts the column and loses the index.

If rewriting is impossible, create an expression index on exactly that expression, or a generated column with its own index.

Date range tip: use half-open ranges, >= '2026-01-01' AND < '2026-02-01'. BETWEEN '2026-01-01' AND '2026-01-31' on a timestamp misses everything after midnight of the 31st, and BETWEEN ... AND '2026-02-01' includes the first instant of the next month.

7. Transactions, isolation and locking

What does ACID mean, and how does the database actually deliver it? Basic

Atomicity: all of the transaction happens or none of it. Consistency: it moves the data from one valid state to another, with constraints enforced. Isolation: concurrent transactions do not see each other's half-finished work. Durability: once COMMIT returns, the data survives a crash. The classic example is a bank transfer: debit and credit must both happen or neither.

Why transactions exist. A business action usually needs several SQL statements. A money transfer is two updates. If the server crashes after the first, 100 has vanished from the system. A transaction groups statements into one unit that the database promises to treat as a single event.

The four properties, each with a failure it prevents:

LetterPromiseFailure without it
Atomicityall statements take effect, or nonedebit done, credit missing
Consistencyconstraints and invariants hold before and afternegative balance, orphan rows
Isolationconcurrent transactions do not see each other's partial worka report adds up numbers mid-transfer and is off by 100
Durabilityafter COMMIT returns, the change survives a crash or power losscustomer got a receipt, data gone after reboot

"Consistency" is the odd one: the database enforces the constraints you declared (NOT NULL, FK, CHECK), but it cannot know a rule you never wrote down, so it is a joint responsibility.

How a commit really works (the write-ahead log).

  1. The statement changes the page in memory (the buffer cache). That page is now "dirty" but not yet written to its place in the data file.
  2. A description of the change is appended to the log, a sequential file.
  3. On COMMIT, the log is flushed to disk (fsync). Only then does COMMIT return "success".
  4. Later, in the background, dirty data pages are written to the data files (a checkpoint).
  5. Crash recovery: on restart, replay the log for committed transactions (redo), and ignore or undo those that never committed.

Why this design: appending to one log file is a fast sequential write, while updating the true locations means many random writes. So the database makes the cheap write durable first and takes its time with the expensive ones. Atomicity on rollback comes from undo information (an undo log in InnoDB, old row versions in PostgreSQL).

The trade-off knob: the flush on each commit is the main cost of durability. Group commit batches many transactions' flush into one. Relaxing it (synchronous_commit = off in PostgreSQL, innodb_flush_log_at_trx_commit = 2 in MySQL) can lose the last fraction of a second of commits after a crash, but never corrupts data in PostgreSQL's case. Fine for metrics, wrong for payments.

Durability and atomicity come from the write-ahead log (WAL in PostgreSQL, redo log in InnoDB). Before a change reaches the data files, the log record is written and flushed to disk, and COMMIT returns only after that flush. After a crash the database replays the log to restore committed work and discards uncommitted work. Writing a log sequentially is much cheaper than updating random data pages, which is why the data files can lag behind. Isolation comes from MVCC and locks (next questions). Consistency is partly the database (constraints) and partly your code. The cost of durability is the fsync on each commit. Settings like synchronous_commit = off or innodb_flush_log_at_trx_commit = 2 trade a small window of lost commits for speed, which is fine for logs and wrong for payments.

BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- both persist, or on error ROLLBACK undoes both

Remember: log first, then data. The commit is durable once the log is flushed.

Explain the transaction isolation levels and the anomalies they prevent. Intermediate

Isolation levels say how much concurrent transactions may disturb each other. From weakest: Read Uncommitted, Read Committed, Repeatable Read, Serializable. Each level blocks more anomalies: dirty reads (seeing uncommitted data), non-repeatable reads (the same row changes between two reads), and phantoms (new rows appear in a repeated range query). Serializable behaves as if transactions ran one after another.

The problem. Many transactions run at once on the same rows. Perfect isolation (as if they ran one by one) is expensive, so databases offer levels trading safety for concurrency. The levels are defined by which of three problems they allow:

  • Dirty read: reading data another transaction has changed but not yet committed (it may roll back, and you acted on data that never existed).
  • Non-repeatable read: reading the same row twice in one transaction and getting different values because someone committed a change in between.
  • Phantom read: running the same range query twice and getting additional (or missing) rows because someone committed an insert or delete in between.

The same scenario at different levels. account A has balance 100. T1 starts and reads A. T2 updates A to 50 and commits. T1 reads A again.

What the levels still allow in real engines.

  • Read Committed allows lost updates if you read-modify-write in code, and allows write skew.
  • PostgreSQL Repeatable Read is snapshot isolation: no phantoms, but write skew is possible. If it tries to update a row that another transaction changed since its snapshot, it errors with a serialization failure and you retry.
  • MySQL Repeatable Read: plain SELECTs use the snapshot, but UPDATE and SELECT ... FOR UPDATE read the latest committed rows (a "current read"), a mix that confuses people. Gap locks block phantoms for locking reads.
  • Serializable prevents all of them but needs retries (PostgreSQL) or more locking (MySQL).

Choosing. Default level plus targeted tools covers most cases: atomic UPDATE statements, SELECT ... FOR UPDATE for read-then-write, unique constraints for "at most one". Raise to Serializable for a specific tricky transaction rather than for the whole system. Setting: BEGIN ISOLATION LEVEL REPEATABLE READ; or SET TRANSACTION ISOLATION LEVEL ....

What is MVCC and why do readers not block writers? Senior

MVCC (multi-version concurrency control) keeps several versions of a row instead of overwriting it. Each transaction reads the version that was current for its snapshot, so readers never wait for writers and writers never wait for readers. Two writers on the same row still conflict, and the second waits for the first to finish.

The old problem MVCC solves. With plain locking, a long report reading a table blocks every writer on those rows (or writers block the report). Throughput and latency suffer. MVCC says: do not overwrite, keep versions, and give every reader a consistent view as of one moment, so nobody waits.

How a snapshot decides what you see (simplified PostgreSQL). Every row version stores the id of the transaction that created it (xmin) and, if deleted or replaced, the one that removed it (xmax). When your transaction (or statement, under Read Committed) starts, it notes which transaction ids are committed. A version is visible if its creator committed before your snapshot and its remover did not (yet). So all you do is compare ids; no lock is needed.

Example timeline (row balance = 100 created by tx 10):

  1. tx 20 starts a report and takes its snapshot.
  2. tx 30 runs UPDATE ... SET balance = 50 and commits. This creates version v2 (50, created by 30) and marks v1 as removed by 30.
  3. tx 20's report reads the row: v2's creator (30) is newer than its snapshot, so v2 is invisible. It sees v1: 100. Consistent, no waiting.
  4. A new transaction 40 sees v2: 50.
  5. Once no running transaction can still need v1, VACUUM may remove it.

Where writers do still conflict. Two transactions updating the same row: the second waits for the first to commit or roll back. Then under Read Committed it re-reads the newest version and applies its update to it; under Repeatable Read it fails with a serialization error.

PostgreSQLMySQL InnoDB

Practical consequences: a long-running or idle-in-transaction session is harmful for everyone (see the long-transactions question). Also, COUNT(*) is slow because each transaction may see a different number of rows. Reading never needs locks, but a locking read (FOR UPDATE) reads the newest version and does lock.

In PostgreSQL an update writes a new row version in the same table and marks the old one dead (each version carries the transaction ids that created and deleted it). Dead versions pile up until VACUUM cleans them; neglected, the table bloats and queries slow down. A long-open transaction or idle-in-transaction session holds back cleanup, which is a classic cause of bloat. In InnoDB the row is updated in place and old versions are kept in the undo log; readers rebuild the old row by following undo records. A very long transaction makes the undo history grow and reads slower.

Remember: MVCC means many versions. Readers use old ones without locks, and long transactions block cleanup.

What is a lost update and how do you prevent it? Intermediate

A lost update happens when two transactions read the same value, both compute a new one in application code, and both write it back, so one change silently disappears. I prevent it with an atomic update in SQL, a row lock with SELECT ... FOR UPDATE, or optimistic locking with a version column. Which one depends on how conflict-prone the row is.

The mechanism in numbers. product id 7 has stock 10. Two customers each buy 1 unit at about the same time. The application does: read stock, subtract 1 in code, write the result.

StepT1T2stock in DB
1SELECT stock gives 1010
2SELECT stock gives 1010
3UPDATE stock = 9, COMMIT9
4UPDATE stock = 9, COMMIT9 (should be 8)

Both writes were valid individually; the second overwrote the first because T2 decided based on a stale read. At Read Committed nothing stops it (PostgreSQL Repeatable Read would make T2's update fail, which is a safe way to detect it).

Three cures, and how each works:

  1. Atomic update (best when possible). UPDATE product SET stock = stock - 1 WHERE id = 7 AND stock > 0. The database locks the row, evaluates stock - 1 using the current value, and releases at commit. T2 waits for T1, then computes from 9 and gets 8. The AND stock > 0 also prevents overselling: if the statement reports 0 rows updated, tell the customer it is sold out. No read in the application at all.
  2. Pessimistic lock. SELECT ... FOR UPDATE locks the row at read time, so T2's read waits until T1 commits and then sees 9. Use when the new value needs complex application logic that cannot be one SQL expression.
  3. Optimistic lock. The row has a version number. Each writer says "update where version = the one I read". T1 succeeds and bumps the version to 6; T2's WHERE version = 5 matches 0 rows, which is the signal to reload and retry (or tell the user "someone else edited this"). In JPA, put @Version on a field.

Related: the same bug exists across HTTP requests (an edit form loaded, then saved minutes later over a colleague's changes). A version or ETag in the form catches it. Interview probe: "does a transaction alone prevent this?" No; wrapping the read and write in a transaction at Read Committed still loses the update.

-- 1) atomic update: safest and simplest
UPDATE product SET stock = stock - 1 WHERE id = 7 AND stock > 0;   -- check rows affected = 1

-- 2) pessimistic: lock the row, then read-modify-write
BEGIN; SELECT stock FROM product WHERE id = 7 FOR UPDATE; ...; UPDATE ...; COMMIT;

-- 3) optimistic: a version column
UPDATE product SET stock = :new, version = version + 1 WHERE id = 7 AND version = :seen;  -- 0 rows = conflict, retry

Remember: never read-then-write blindly. Use an atomic UPDATE, a lock or a version check.

Pessimistic versus optimistic locking: when do you choose which? Intermediate

Pessimistic locking assumes conflicts are likely: lock the row first (SELECT ... FOR UPDATE) so others wait. Optimistic locking assumes they are rare: read freely, and on write check that the row has not changed (a version column), and retry if it has. I use optimistic for user edits and low-contention data, pessimistic for hot rows where retries would pile up, like a seat or a wallet balance.

Same goal, different bet. Both avoid two people overwriting each other. The difference is when you pay.

Pessimistic, in action.

BEGIN;
SELECT * FROM seat WHERE id = 12A FOR UPDATE;   -- others trying this row now WAIT
-- check seat.free, decide, write
UPDATE seat SET holder = :user WHERE id = 12A;
COMMIT;                                          -- lock released

Guarantee: no conflict can happen; the second person waits and then sees the updated seat. You pay with waiting and potential deadlocks. Variants: NOWAIT (fail at once if locked, good for "this is being edited" messages), SKIP LOCKED (queues), FOR SHARE (others may read but not change).

Optimistic, in action. Table has version INT.

SELECT id, name, version FROM customer WHERE id = 5;       -- version = 3   (no lock, time passes)
UPDATE customer SET name = :n, version = version + 1
WHERE id = 5 AND version = 3;                              -- rows affected 1: ok, 0: conflict

On 0 rows, someone else changed it in between. Reload and re-apply, or show the user a conflict message. Nothing was ever locked, so the user can take 10 minutes in an edit form safely.

Pessimistic costs: locks held across the transaction, risk of deadlocks, and waiting. It must be a short transaction, never held while waiting for the user or a remote call. Optimistic costs: nothing is held, but under heavy contention many attempts fail and retry. It also works across requests (an edit form carries the version). In JPA that is @Version. Lock options: FOR UPDATE NOWAIT fails immediately instead of waiting, and FOR SHARE blocks changes but allows other readers.

Remember: rare conflicts, use a version column. Frequent conflicts, lock the row, and keep the lock short.

What is write skew, and which isolation level stops it? Senior

Write skew is when two transactions each read the same set of rows, each decide an action is safe, and each update a different row, so a rule that spans rows breaks. The standard example: at least one doctor must stay on call; two doctors both check "two are on call", and both go off call. Snapshot isolation, including PostgreSQL's Repeatable Read, allows it. Serializable prevents it.

Why it is different from a lost update. In a lost update both transactions change the same row, so a good database can notice the clash. In write skew they change different rows, based on a shared premise they both read. Each transaction is correct on its own snapshot; the combination breaks the rule.

Worked example. Rule: at least one doctor on call. Table doctor(name, on_call): Alice true, Bob true.

StepT1 (Alice)T2 (Bob)
1SELECT COUNT(*) WHERE on_call gives 2
2SELECT COUNT(*) WHERE on_call gives 2
3count is 2, safe: UPDATE ... Alice on_call = false
4count is 2, safe: UPDATE ... Bob on_call = false
5COMMIT okCOMMIT ok (different row, no write conflict)

Final state: nobody on call. No error occurred, and under snapshot isolation no error would.

Ways to prevent it, from simplest:

  1. Make the rule a single row. Keep a roster row (or lock one parent row such as the ward) that every such transaction updates or locks with FOR UPDATE. Now they conflict on that row and serialise.
  2. Lock the rows you read: SELECT ... WHERE on_call FOR UPDATE in both transactions. The second waits, then re-evaluates (at Read Committed it sees the first's commit and counts 1).
  3. Serializable isolation. PostgreSQL's SSI sees the read-write dependency cycle and aborts one with error 40001; you retry, and the retry sees the right count.
  4. Declare it in the schema when possible: a UNIQUE or exclusion constraint for the room-booking version (EXCLUDE USING gist (room WITH =, during WITH &&)) gives a hard guarantee with no isolation tricks.

Where it shows up: double booking, "username must be unique" without a constraint, a bank account group whose sum must stay non-negative, and sprint or inventory limits across several rows.

No row is updated by both, so there is no write conflict to detect. Options: use Serializable and retry on failure (PostgreSQL's SSI tracks read-write dependencies and aborts one transaction with SQLSTATE 40001), lock the rows that were read (SELECT ... FOR UPDATE on the on-call set), or put the rule in a constraint, for example a single "lock" row everyone updates, or an exclusion constraint for overlapping bookings. The same shape appears in double-booking a room and unique-username checks without a constraint.

Remember: read the set, write another row. Fix with Serializable plus retry, or lock the rows you read.

What is a deadlock, and how do you handle and prevent it? Intermediate

A deadlock is a cycle: T1 holds a lock that T2 needs, and T2 holds a lock that T1 needs, so neither can proceed. The database detects the cycle, kills one transaction as the victim (PostgreSQL error 40P01, MySQL 1213), and the other continues. The application must catch it and retry the whole transaction. To prevent it, always lock rows in the same order and keep transactions short.

How a deadlock forms in two statements each. Table account: A = 100, B = 100. Two transfers run at the same time:

StepT1: A pays BT2: B pays A
1UPDATE A (locks row A)UPDATE B (locks row B)
2UPDATE B: wait, T2 holds BUPDATE A: wait, T1 holds A
3each waits for the other forever: deadlock

A database does not let this hang. A detector looks for cycles in the wait-for graph (PostgreSQL after deadlock_timeout, default 1 second; InnoDB immediately). It picks a victim (usually the cheapest to roll back), aborts it with an error, and the other proceeds. The victim's whole transaction is rolled back, so the application must start it again from the beginning, not retry just the failed statement.

Prevention, ranked:

  1. Consistent lock order. Always touch rows in the same order, such as ascending account id. Then T1 and T2 both lock A first; the second just waits and no cycle is possible. With the transfer example: ORDER BY id with SELECT ... FOR UPDATE on both rows first.
  2. Short transactions reduce the window in which locks are held.
  3. Index your WHERE clauses. Without an index an UPDATE can lock many more rows than it changes (InnoDB locks every row it scans), creating overlaps between unrelated statements.
  4. Lock everything you need up front (a batch of FOR UPDATE) rather than acquiring locks piecemeal.
  5. Retry with backoff as the safety net, because you cannot rule them out entirely (for example two different statements locking index entries in different orders).

Diagnosis: InnoDB: SHOW ENGINE INNODB STATUS shows "LATEST DETECTED DEADLOCK" with both statements. PostgreSQL: the server log prints the processes and queries involved (log_lock_waits helps). Frequent deadlocks usually mean a code path with inconsistent ordering, or foreign key checks and bulk updates interacting; look at the two statements named in the report.

Not to be confused with a plain lock wait, where one transaction merely waits for a slow one; that ends when the other commits, or times out (innodb_lock_wait_timeout, lock_timeout).

Typical causes: updating two accounts in opposite orders (T1 moves A to B while T2 moves B to A), or updates that lock many index entries in different orders. Fixes: lock in a consistent order (for example sort account ids), keep the transaction small, use an index so the statement locks fewer rows, and retry with a short random delay. To diagnose, read the deadlock report (SHOW ENGINE INNODB STATUS, or the PostgreSQL log).

Remember: same lock order everywhere, short transactions, and always retry on deadlock.

How would you build a job queue on a SQL table? What does SKIP LOCKED do? Senior

Each worker claims a batch of pending rows with SELECT ... FOR UPDATE SKIP LOCKED. Rows already locked by another worker are skipped instead of waited for, so workers never block each other and never take the same job. It is available in PostgreSQL 9.5+ and MySQL 8.0+.

The problem. You have a table of jobs and several workers. If each does SELECT ... WHERE status = 'PENDING' LIMIT 1 and then updates it, two workers can read the same row and run the job twice. If you add FOR UPDATE, the second worker blocks behind the first on the same row, so workers serialise on the head of the queue.

What SKIP LOCKED changes. Rows that are currently locked by someone else are silently left out of the result. Each worker therefore gets different rows. Walk through: jobs 1 to 6 pending. Worker A runs the query with LIMIT 2 and locks jobs 1, 2. Worker B runs the same query a moment later: jobs 1, 2 are locked and skipped, so it receives 3, 4. Worker C gets 5, 6. No waiting, no duplicates.

Two designs for the lifecycle:

  1. Lock for the duration of the work. Select, process, mark DONE, commit. If the worker crashes, the connection drops, the locks vanish, and the jobs become visible again automatically. Simple and safe; the cost is a transaction held open for the processing time, so only for short jobs.
  2. Claim and release. Quickly update status = 'RUNNING', locked_until = now() + interval '5 min' and commit; do the work outside any transaction; then mark DONE. A periodic job resets rows whose locked_until passed (a crashed worker). This allows long jobs, but a job can run twice if a worker is slow rather than dead, so jobs must be idempotent.
-- claim and release, one statement (PostgreSQL)
UPDATE job SET status = 'RUNNING', locked_until = now() + interval '5 minutes'
WHERE id IN (
  SELECT id FROM job WHERE status = 'PENDING' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED
) RETURNING id, payload;

Operational points: add a partial index on pending rows so polling is cheap; retry counts and a dead-letter state for poison jobs; delete or archive finished rows so the table stays small. Not a good fit when you need strict ordering across workers, replay, or very high throughput; that is what Kafka, SQS or RabbitMQ are for. The benefit of the table approach: the job and your business data change in the same transaction (the transactional outbox pattern uses this idea).

BEGIN;
SELECT id, payload FROM job
WHERE status = 'PENDING'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- process, then:
UPDATE job SET status = 'DONE' WHERE id IN (...);
COMMIT;

Without SKIP LOCKED all workers queue behind the same first row. Two design choices: keep the processing inside the transaction (a crash releases the locks and the jobs reappear, which is simple but holds a transaction open), or mark rows IN_PROGRESS with a lease timestamp and commit quickly, with a sweeper that re-queues expired leases. Jobs can then run twice, so the work should be idempotent. A partial index on status = 'PENDING' keeps polling cheap. This design is fine up to thousands of jobs per second; beyond that or for fan-out, use a real broker such as Kafka or SQS. Note that SKIP LOCKED gives an inconsistent view on purpose, so use it only for queues.

Remember: FOR UPDATE SKIP LOCKED makes a table a safe multi-worker queue. Make jobs idempotent.

Why are long transactions harmful, and what should never happen inside one? Intermediate

A transaction holds its locks until it ends, and holds back cleanup of old row versions. So a long one blocks other writers, bloats the table, grows the undo or WAL, and exhausts connections. I keep transactions short, and never call a remote service, wait for a user, or sleep inside one.

What a transaction holds while it is open.

  • Row locks on everything it has changed (and read with FOR UPDATE). Others wanting those rows wait.
  • A snapshot, so the database cannot remove old row versions the transaction might still read. Dead versions pile up (bloat in PostgreSQL, a long undo history in InnoDB).
  • A connection from the pool. 20 stuck transactions in a pool of 20 means the app is down.
  • Log space: the WAL or undo cannot be recycled past its oldest open transaction.

A real failure chain. A request starts a transaction, updates the order row, then calls the payment gateway, which hangs 30 seconds. During that time: the order row is locked, so the customer's refresh request waits; their retries each take a connection and wait too; the pool empties; health checks fail; the load balancer removes the instance; the load shifts to others which do the same. One slow dependency became an outage because it was inside a transaction.

Correct shape: do slow work outside the transaction, record the result in a short one.

// bad: transaction spans the remote call
@Transactional void pay(...) { updateOrder(); gateway.charge(); markPaid(); }
// good: three short steps, with the order status carrying the state
markPaymentPending();   // tx 1
gateway.charge();       // no tx
markPaid();             // tx 2

Things never to do inside a transaction: HTTP or message sends (if the transaction rolls back, the message is already out; use an outbox), waiting for user input, large batch processing in one commit (commit in chunks), sleeping or retrying with delays.

Safety nets: idle_in_transaction_session_timeout and statement_timeout (PostgreSQL), lock wait timeouts (lock_timeout, innodb_lock_wait_timeout), and a monitor on the longest-running transaction (pg_stat_activity.xact_start, information_schema.innodb_trx). In Spring, also check open-in-view, which can keep a connection checked out while rendering a view.

A classic incident: a method opens a transaction, calls a payment API that hangs for 30 seconds, and meanwhile holds a row lock. Other requests pile up behind it, the pool runs dry, and the whole app stalls. Fix: do the remote call outside the transaction, then open a short one to save the result. Also watch for idle in transaction sessions (PostgreSQL pg_stat_activity): a forgotten commit in a code path. Defensive settings: statement_timeout, idle_in_transaction_session_timeout (PostgreSQL), innodb_lock_wait_timeout (MySQL, default 50 seconds). With Spring's @Transactional, remember a self-call inside the same class bypasses the proxy and starts no transaction.

Remember: short transactions. No network calls or user waits inside them.

What are gap and next-key locks in MySQL InnoDB, and why do they cause surprises? Senior

In Repeatable Read InnoDB locks not only the matching index rows but also the gaps between them (a next-key lock is a row lock plus the gap before it). This stops other transactions from inserting rows into the range you scanned, which prevents phantoms. The surprise is that inserts into an unrelated-looking range get blocked, and deadlocks appear.

Why gaps need locking. At Repeatable Read, a transaction that does SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE twice should get the same rows. Locking the existing rows is not enough: another transaction could insert id 15 and the second query would find a phantom. So InnoDB also locks the empty space between index entries.

The lock types:

  • Record lock: a lock on one index entry.
  • Gap lock: a lock on the space between two index entries (no row there is locked, but inserts into the gap are blocked).
  • Next-key lock: a record lock plus the gap before it. This is InnoDB's default for range scans at Repeatable Read.

Example. A table has ids 10, 20, 30. Transaction A: SELECT * FROM t WHERE id BETWEEN 11 AND 19 FOR UPDATE. No row matches, but A locks the gap (10, 20). Transaction B: INSERT INTO t (id) VALUES (15) blocks until A commits. B inserting id 25 is fine. Two sessions can both take the same gap lock (gap locks do not conflict with each other) and then both try to insert into it, which is a classic deadlock: each insert waits for the other's gap lock.

Surprises people hit:

  • Locking reads with no usable index lock the whole scanned range, effectively the whole table.
  • DELETE FROM t WHERE created_at < ... for old rows can block inserts of new rows that sort into the locked range.
  • Unique index lookups for an existing key lock only the record, not the gap, so the behaviour depends on whether a row was found.

Mitigation: index the WHERE columns well; keep transactions short; consider Read Committed for workloads that tolerate phantoms (gap locks mostly disappear, but use row-based binlog); for queues use SKIP LOCKED or claim by primary key. To inspect, use performance_schema.data_locks (MySQL 8.0+).

Example: SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE also blocks inserting id 15 even if no row with 15 exists. A locking statement without a usable index locks far more, in the worst case every row, because InnoDB locks the index entries it scans. So the index that supports your WHERE also narrows the locks. Switching to Read Committed removes most gap locking (with row-based binary logging), at the cost of phantom reads. PostgreSQL has no gap locks; it uses snapshots and, for Serializable, predicate tracking.

Remember: InnoDB locks the scanned index range including gaps. Good indexes and Read Committed reduce it.

What are table bloat and VACUUM in PostgreSQL, and why should a developer care? Senior

Because updates and deletes leave dead row versions behind, the table grows even if the row count does not. VACUUM marks that space reusable, and autovacuum runs it automatically. A developer should care because heavy update patterns, long transactions, or disabled autovacuum cause bloat and slow queries.

Why PostgreSQL leaves garbage. Under MVCC an UPDATE does not change a row in place; it writes a new version and leaves the old one for transactions that may still need it. A DELETE only marks the row dead. These dead versions (dead tuples) occupy space until something removes them. That something is VACUUM: it scans for versions no running transaction can see any more and marks the space reusable for new rows.

A worked picture. A counter table has 1 row updated 10,000 times a minute. Without cleanup that is 10,000 new versions a minute, so a one-row table grows to hundreds of MB. With autovacuum keeping up, the same few pages are reused. If a transaction has been open for an hour, VACUUM cannot remove any version newer than that transaction's snapshot, so the table and its indexes grow fast. That is "bloat": the file contains mostly dead space, so scans read more pages, caches hold less useful data, and indexes grow too.

What a developer should do:

  • Avoid long or idle-in-transaction sessions; set idle_in_transaction_session_timeout.
  • Avoid hot-row update patterns (a single counter row updated by every request); aggregate in a cache or append rows and sum them.
  • Prefer updates that do not touch indexed columns, so they can be HOT updates (the new version stays on the same page and no index entry is needed); leave room with a lower fillfactor on hot tables.
  • Delete old data by dropping partitions rather than massive DELETEs.
  • Monitor dead tuples (pg_stat_user_tables.n_dead_tup) and autovacuum activity; tune per-table thresholds for big busy tables.

Know the limits. Plain VACUUM makes space reusable but rarely shrinks the file; VACUUM FULL rewrites it and takes an exclusive lock; pg_repack does it online. Transaction id wraparound: ids are 32-bit, so old rows must be periodically "frozen"; if autovacuum is blocked for too long PostgreSQL will eventually refuse writes to protect data, a well-known outage. Also ANALYZE (statistics) usually runs alongside autovacuum.

Common triggers: a hot table where each row is updated thousands of times (counters), a long transaction that prevents VACUUM from removing versions newer than its snapshot, and mass deletes. Mitigations: keep transactions short, avoid updating a row more often than needed (batch counter updates or keep them in a cache), lower the table's fill factor to allow in-page HOT updates, and tune autovacuum per hot table. Plain VACUUM does not shrink the file; VACUUM FULL and pg_repack rewrite it but take locks, an ops job. Transaction ID wraparound is the extreme case that autovacuum prevents by freezing old rows, which is why switching it off is dangerous.

Remember: updates leave dead versions. Keep transactions short and let autovacuum run.

When do you use Serializable, and what must the application do? Senior

I use Serializable for a small number of critical transactions whose correctness depends on reading a set and then writing based on it, such as write-skew cases, when adding explicit locks or constraints is awkward. The application must be ready to retry: the database may abort a transaction with a serialization failure (SQLSTATE 40001), and the right response is to rerun the whole transaction.

What Serializable promises. The outcome of concurrent transactions equals the outcome of running them one at a time in some order. That removes dirty, non-repeatable, phantom reads and also write skew and lost updates, without you reasoning about which anomaly applies. The price is that the database may have to abort transactions that cannot be arranged in a serial order.

How the engines do it.

  • PostgreSQL SSI: transactions run on snapshots without blocking. The database tracks "I read something that you wrote" dependencies. If it finds a dangerous cycle (the shape that causes write skew), it aborts one transaction with SQLSTATE 40001 ("could not serialize access"). Low blocking, but expect aborts, and some are false positives.
  • MySQL InnoDB: plain SELECTs become locking reads (shared locks, with next-key locks), so conflicts show up as waits and deadlocks rather than serialization errors.

Application checklist:

  1. Wrap the whole unit of work in a retry loop that catches the serialization failure (and deadlock) errors, rolls back, and reruns the entire transaction from the start, with a small randomised backoff and a maximum count (say 3 to 5 tries).
  2. Keep the transaction short and touch few rows; the odds of conflict grow with duration and footprint.
  3. Make the code re-runnable: re-read inside the transaction, no side effects until commit. Emails, HTTP calls and events belong after the final commit (or in an outbox).
  4. Use read-only transactions (SET TRANSACTION READ ONLY, or READ ONLY DEFERRABLE for big reports) so they never abort or cause aborts.

Alternatives to weigh: targeted locks (FOR UPDATE), a constraint, or a "guard" row are often simpler and predictable. Choose Serializable when the invariant is complicated and you would rather rely on the engine than on a hand-built locking scheme, and the transactions are few and short. In Spring, a retry needs to wrap the @Transactional method from outside (for example with Spring Retry), since the failed transaction is already gone.

In PostgreSQL, Serializable Snapshot Isolation (SSI) lets everyone run without blocking and only aborts when it detects a dangerous pattern of dependencies, so it needs retry logic but little blocking. It can also produce false positives, so expect some retries, and keep these transactions short. In MySQL InnoDB, Serializable turns plain SELECTs into shared-locking reads, so it blocks more and deadlocks more. Always wrap the retry in a bounded loop, and make sure side effects like emails are sent only after the final commit.

Remember: Serializable is safe but may abort. Retry the whole transaction, and keep it short.

8. Scaling and SQL versus NoSQL

The database is getting slow under load. In what order do you scale it? Intermediate

Cheapest first: fix the queries and indexes, add connection pooling, cache hot reads, scale the machine up, add read replicas, then partition big tables, and shard only as the last step. Each step adds a new kind of failure, so I move up the ladder only when measurements say the lower rung is exhausted.

Why a ladder. Each rung buys capacity at a price in complexity. If you skip to a high rung, you take on its permanent cost without needing it. Also, most "the database is slow" incidents are caused by a few bad queries, not by hardware limits.

  2. Connection pool so thousands of app threads do not each open a database connection.
  3. Cache (Redis, application cache) for hot, rarely changing reads. Cost: invalidation and stale data.
  4. Scale up (more CPU, RAM, faster disk). Simple, has a ceiling.
  5. Read replicas for read-heavy load. Cost: replication lag.
  6. Partitioning one big table inside one database.
  7. Sharding across several databases. Cost: no cross-shard joins or transactions, rebalancing pain, operational load.

Writes only scale up the ladder through partitioning and sharding; replicas help reads only. Most systems never need step 7.

Remember: indexes, pool, cache, bigger box, replicas, partition, shard. Shard last.

What is the difference between partitioning and sharding? Intermediate

Partitioning splits one large table into smaller pieces inside a single database server, and the database routes queries for you. Sharding splits data across several separate servers, and your application or a routing layer has to decide which server to ask. Partitioning helps maintenance and pruning; sharding is the one that scales writes and storage beyond one machine.

Same word "split", different layers. Partitioning is a storage feature inside one database server; the application sees one table. Sharding is an architecture; the application (or a proxy) sees many databases and must know which holds the data.

Partitioning, with an example.

CREATE TABLE event (id bigint, created_at timestamptz NOT NULL, payload jsonb)
  PARTITION BY RANGE (created_at);
CREATE TABLE event_2026_01 PARTITION OF event FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
-- query with a date filter reads only matching partitions (partition pruning)
-- retention: DROP TABLE event_2025_01;   -- instant, no giant DELETE, no bloat

Benefits: smaller indexes per partition, pruning for time-bounded queries, instant bulk delete of old data, parallel maintenance. It does not add more machines, CPUs or IO, so write scale does not change. Requirements: the partition key must be in every primary or unique key, and queries without the key scan all partitions (slower than before).

Sharding, with an example. 3 database servers. A user's data is placed by hash(user_id) mod 3. A request for user 42 goes to shard 42 mod 3 = 0. Total write and storage capacity is about three times a single server. Prices:

  • Choosing the shard key is a one-way door: wrong key means hot shards (one celebrity user or big tenant) or queries that need all shards ("scatter-gather").
  • No cross-shard transactions or joins without extra machinery (sagas, two-phase commit, application joins).
  • Global unique ids and global secondary indexes need design (for example Snowflake ids, a lookup table).
  • Rebalancing: modulo hashing moves almost all keys when adding a shard; consistent hashing or many small virtual shards (for example 1024 logical shards mapped to a few servers) lets you move whole shards later.

Read replicas and replication lag: what goes wrong and how do you handle it? Intermediate

Replicas apply the primary's changes asynchronously, so a read right after a write may hit a replica that has not caught up and return old data. The usual user-visible bug is "I saved but my change is gone". I handle it by sending a user's own recent reads to the primary, or reading from a replica only for data that tolerates staleness.

How replication works, briefly. The primary writes every change to its log (WAL, binlog). The replica streams that log and replays it. Asynchronously means the primary does not wait for the replica before confirming the commit, so commits are fast, but there is a delay between "committed on primary" and "visible on replica". Normally milliseconds, but a heavy batch job, a slow replica disk, or a long query on the replica that conflicts with replay can stretch it to seconds or minutes.

The user-visible bugs:

  1. Read-your-writes violation. User saves a profile (primary), page redirects to the profile (replica), shows the old name. They save again, confused.
  2. Time going backwards. One request hits a fresh replica, the next a lagging one, and a comment appears then disappears.
  3. Wrong decisions. A stock check on a replica says 3 left; the primary has 0. Oversell.
  4. Failover data loss. Promoting a lagging replica loses the last commits the replica never received.

Mitigations, from cheap to precise:

  • Route by criticality. Financial and inventory reads, anything followed by a write based on it: primary only. Dashboards, search pages, history: replica.
  • Sticky to primary after a write. For N seconds after a user writes (a cookie or session flag, or a time window in the session), send their reads to the primary.
  • Replica position check. Remember the write's LSN or GTID, and only read from a replica that has applied at least that position (PostgreSQL pg_last_wal_replay_lsn, MySQL WAIT_FOR_EXECUTED_GTID_SET).
  • Monitor and eject. Alert on lag and remove a replica from the load balancer over a threshold.
  • Synchronous or semi-synchronous replication for must-not-lose data: slower writes, and availability depends on the replica.

Replicas also do not scale writes: each replica replays all writes, so heavy writes make every replica busy too.

  • Read-your-writes: after a write, read from the primary for a short time (or pin the user's session to the primary), or pass the write's log position and only use a replica that reached it.
  • Critical reads (balance before a debit, inventory at checkout) always go to the primary.
  • Monitor lag and take a replica out of rotation if it is too far behind. Long queries on replicas can also delay replay.
  • Synchronous replication removes lag but adds write latency and can block writes if the replica is down.

Remember: replicas are eventually consistent. Read your own writes from the primary.

Why use a connection pool, and how big should it be? Intermediate

Opening a database connection is costly (network, authentication, a server process or thread), and a database handles only a limited number of active connections well. A pool keeps a few connections open and lends them to requests. A small pool is usually faster than a large one, because a database with 8 cores cannot run 500 queries truly at once.

What it costs to open a connection. TCP and TLS handshakes, authentication, then on the server a new process (PostgreSQL) or thread (MySQL) with its own memory, often a few MB or more. Doing that per request adds tens of milliseconds and cannot scale to thousands of requests. A pool opens N connections once and hands them out: borrow, run, return.

Why a small pool is faster, with numbers. A database with 8 cores can truly execute about 8 to 16 queries at a time. Give it 200 simultaneous active connections and the queries compete for CPU and disk, context switching, and lock contention, so each takes longer and total throughput drops. With a pool of 20, 20 queries run and the rest of the requests wait briefly in the app queue, which is cheaper because waiting in a queue is almost free and queries finish sooner. Little's law helps size it: connections needed = queries per second x average query seconds. At 500 queries per second with a 10 ms average, you need about 5 busy connections; a pool of 10 to 20 gives headroom.

Symptoms and causes:

Sizing across instances: 20 app pods x pool of 20 = 400 connections to the database; it may not handle that. Reduce the pool per pod, or use a server-side pooler (PgBouncer, ProxySQL, RDS Proxy) that multiplexes many app connections onto few database connections. In PgBouncer's transaction mode a client gets a server connection only during a transaction, so session state (SET, temporary tables, session advisory locks, and, in older versions, named prepared statements) does not persist.

A common starting point is a pool of about cores times 2 plus the number of disks, often 10 to 30 per app instance; then check that instances times pool size stays under the database's max_connections. Pool exhaustion shows up as timeouts waiting for a connection, usually caused by slow queries, long transactions, or connection leaks (not closing connections). PostgreSQL commonly sits behind PgBouncer because each connection is a process; in transaction pooling mode, session features such as session-level advisory locks and some prepared-statement usage do not work as expected. In HikariCP the key settings are maximumPoolSize, connectionTimeout and maxLifetime.

Remember: a small pool wins. When it runs dry, look for slow queries and leaks, not a bigger pool.

SQL versus NoSQL: how do you choose? Intermediate

I start with a relational database unless there is a clear reason not to: it gives transactions, constraints, joins and flexible queries, and handles most workloads, including large ones. I choose a NoSQL store when the access pattern or scale fits it: key-value for sessions and caches, document for flexible aggregates read as a whole, wide-column for huge write-heavy data with known queries, graph for relationship traversal, search engines for text.

Start from what each side is good at. A relational database models data as tables with relationships, and gives you declarative queries over any combination of columns, joins, constraints and multi-row transactions. You pay with a fixed schema and, at extreme scale, the difficulty of spreading one logical database over many machines. Most NoSQL systems start from a particular access pattern and scale target, and give up some of those general features to excel at it.

Match the data shape to the store, with examples:

  • Orders, payments, users, inventory (related entities, money, uniqueness): relational. Transactions and constraints are the point.
  • Shopping cart, session, rate-limit counter, cache (look up by one key, expire): key-value (Redis).
  • Product catalog with different attributes per category, content pages (read as one self-contained record, shape varies): document store, or PostgreSQL JSONB.
  • Sensor readings, chat messages, activity feeds (millions of writes per second, queried by key and time): wide-column such as Cassandra, or a time-series database.
  • Friends of friends, fraud rings, recommendation paths: graph database (a recursive SQL query is possible at small scale).
  • Full-text and faceted search: Elasticsearch or OpenSearch, kept as a derived copy of the source of truth.

Questions to ask instead of "which is better":

  1. What are the queries? Known and fixed (key-based), or unknown and evolving (ad-hoc)?
  2. What consistency is required? Can two users briefly see different values, or must the total always add up?
  3. What scale: rows, writes per second, data size? A single PostgreSQL server comfortably handles terabytes and thousands of writes per second; many teams adopt NoSQL long before they need it.
  4. Do we need multi-entity transactions and constraints?
  5. Can the team operate it (backups, upgrades, on-call)?

Caveats worth saying. "Schemaless" means the schema moves into application code, and every reader must cope with every old shape. Denormalized document or wide-column models make a change of access pattern expensive. And the CAP trade-off (during a partition choose consistency or availability) is a property of distributed systems, not of SQL versus NoSQL: distributed SQL databases exist too, and some NoSQL stores offer tunable consistency. The mature answer is polyglot persistence with one source of truth and derived stores kept in sync (CDC or events).

How do you change a production schema with zero downtime? Senior

I use the expand and contract pattern: make only backward-compatible changes in small steps, so old and new application versions both work at every moment. Expand (add the new column), dual-write, backfill in batches, switch reads, then contract (drop the old column) in a later release. Never rename or drop in a single deploy.

Why a single deploy is dangerous. During a rolling deploy, old and new app versions run at the same time against one schema, and a rollback must also work. If you rename a column in one step, the old version breaks the moment the migration runs. So every step has to be compatible with both the code before it and the code after it.

Worked example: rename users.fullname to users.display_name.

  1. Expand: migration adds display_name as nullable (instant, no rewrite). Old code ignores it.
  2. Dual write: deploy app version that writes both columns (and still reads fullname). A trigger can do this too.
  3. Backfill: copy old rows in batches: UPDATE users SET display_name = fullname WHERE id BETWEEN :a AND :b AND display_name IS NULL, a few thousand rows at a time, with a pause so replicas keep up and locks stay short. Verify counts.
  4. Switch reads: deploy a version that reads display_name. If something goes wrong, roll back safely because both columns are populated.
  5. Stop writing the old column, wait through a safe window (one release), then contract: drop fullname. Optionally add NOT NULL after verifying with a NOT VALID check constraint then VALIDATE.

The hidden hazard: lock queues. An ALTER TABLE needs a brief exclusive lock. If a long query is running on the table, the ALTER waits for it, and every new query on the table waits behind the ALTER. A "quick" migration can therefore freeze the table for minutes. Defence: SET lock_timeout = '2s' and retry the migration at a quiet time; run long queries off the primary.

9. Modelling and everyday practice

How do you "insert or update" safely under concurrency? Intermediate

I use the database's upsert, which does it atomically against a unique key: INSERT ... ON CONFLICT DO UPDATE in PostgreSQL and INSERT ... ON DUPLICATE KEY UPDATE in MySQL. A "SELECT, then INSERT or UPDATE" in code is a race, because two requests can both see "not found" and both insert.

The race in plain steps. "Record one page view": the naive code does SELECT for today's row; if found, UPDATE views = views + 1; if not found, INSERT with 1. Two requests arrive at midnight when no row exists yet. Both SELECTs return nothing; both run INSERT; one fails with a duplicate key error (if there is a unique constraint) or, worse, both succeed and you have two rows (if there is none).

What the upsert does. One statement: try to insert. If the unique key already exists, run the UPDATE part instead, on that existing row, atomically. The database locks the conflicting index entry, so concurrent upserts for the same key queue up and each applies its increment. Three simultaneous requests for a new key: the first inserts (views = 1), the other two see the conflict and update (2, then 3). Final value is 3, no lost count and no error.

Useful variants:

  • Insert if absent: INSERT ... ON CONFLICT (email) DO NOTHING; check the affected-row count (0 means it existed). MySQL: INSERT IGNORE, but it also hides other errors, so prefer ON DUPLICATE KEY UPDATE id = id.
  • Take the incoming value: ON CONFLICT (sku) DO UPDATE SET price = EXCLUDED.price (MySQL uses VALUES(price) or a row alias in 8.0.19+).
  • Return the row either way: add RETURNING id (PostgreSQL; with DO NOTHING it returns nothing for a conflict, so use a no-op DO UPDATE if you need the id every time).
  • Idempotent APIs: table processed_request(idempotency_key UNIQUE). In one transaction, insert the key first; if it conflicts, the request is a duplicate, so return the stored result.

Pitfalls. Without a unique index on the conflict columns there is nothing to conflict on (PostgreSQL errors out; MySQL silently inserts a duplicate). Upserts take locks, so a very hot key becomes a contention point. Each conflicting attempt consumes a sequence value in PostgreSQL and an auto-increment value in InnoDB, so ids have gaps. A standard-SQL MERGE (PostgreSQL 15+, SQL Server, Oracle) is more general but has well-known concurrency caveats, so for a simple upsert prefer the native syntax.

-- PostgreSQL
INSERT INTO page_view (page_id, day, views) VALUES (7, CURRENT_DATE, 1)
ON CONFLICT (page_id, day) DO UPDATE SET views = page_view.views + 1;

-- MySQL
INSERT INTO page_view (page_id, day, views) VALUES (7, CURRENT_DATE, 1)
ON DUPLICATE KEY UPDATE views = views + 1;

It needs a unique index to detect the conflict. For "insert if absent" use ON CONFLICT DO NOTHING and check the affected row count. The same trick makes an API idempotent: store the request's idempotency key with a unique constraint, and a retried request hits the conflict instead of doing the work twice. MERGE exists in PostgreSQL 15+ and other databases, but it is not safe against all concurrent races without care. One side effect: in MySQL InnoDB the failed insert still burns an auto-increment value, so ids have gaps.

Remember: one atomic upsert on a unique key beats check-then-write.

Soft delete versus hard delete: what are the trade-offs? Intermediate

A soft delete marks a row with deleted_at instead of removing it, so you can undo it and keep history. The price: every query must remember to filter it out, unique keys collide with deleted rows, indexes grow, and personal data stays around, which can conflict with privacy rules such as GDPR deletion requests.

What it looks like. Instead of DELETE FROM users WHERE id = 5, run UPDATE users SET deleted_at = now() WHERE id = 5. The row stays. Reading code must now add WHERE deleted_at IS NULL everywhere.

Why teams do it: an "undo" or recycle bin, an audit trail, safe handling of mistakes, and keeping foreign-key history (an old order still points to a customer who closed their account).

What goes wrong, each with an example:

  • Forgotten filter. A new report forgets the condition and counts deleted customers. Defence: a view that has the filter built in (CREATE VIEW active_users AS ...), or the ORM's global filter.
  • Unique collisions. User deletes their account, later signs up again with the same email, and UNIQUE (email) rejects it because the dead row still holds it. Fix: partial unique index on live rows only.
  • Growing tables and indexes. Deleted rows still cost space and cache. Queries need the filter as the first condition in indexes (WHERE deleted_at IS NULL partial indexes help).
  • Cascades don't happen. Child rows are not removed by the database, since the parent row still exists; your code has to cascade the flag.
  • Privacy law. "Delete my data" means actually erasing or anonymizing personal fields; setting a flag is not enough. A common design is soft delete for a grace period, then a purge job that hard-deletes or scrubs the row.
NeedBetter fit
Undo for a few dayssoft delete plus a purge job
Full history of changesaudit or history table, temporal tables, or event log
Legal erasurehard delete or anonymization
Archival of old datamove to an archive table or partition

Prefer a timestamp (deleted_at) over a boolean: it records when, and the purge job can use it. Whatever you choose, apply it consistently in one place.

Make it workable: a partial unique index WHERE deleted_at IS NULL (PostgreSQL), a view or ORM filter (Hibernate @SQLRestriction) so queries cannot forget the filter, and a scheduled purge that hard-deletes after a retention period. For audit rather than undo, an append-only history table or a log is cleaner than flags on the live table. Foreign keys still point at soft-deleted rows, so decide what children should do.

Remember: soft delete buys undo and costs filters, unique-key tricks and retention work.

How do you store money and quantities? Why not FLOAT? Basic

I store money as an exact type: DECIMAL(19,4) (or NUMERIC), or as an integer count of the smallest unit (cents), together with a currency code. FLOAT and DOUBLE store binary approximations, so 0.1 + 0.2 is not exactly 0.3 and rounding errors add up across millions of rows.

Why FLOAT is wrong, in one example. Binary floating point cannot represent most decimal fractions exactly, just as 1/3 has no finite decimal form. In double precision, 0.1 + 0.2 gives 0.30000000000000004. A single sum is off by 10^-17, harmless; but equality checks fail (total = 0.3 is false), reconciliation against a bank statement is off by cents, and errors accumulate over millions of rows. Accountants require that the books add up exactly.

The two good options:

OptionExampleNotes
DECIMAL(p, s) / NUMERICDECIMAL(19,4) stores 12345.6789exact; p is total digits, s digits after the point; easiest to read; slightly slower than integers
Integer minor units1999 for 19.99 USDexact and fast; you must convert for display; the exponent depends on the currency

Rules that keep money correct:

  • Store the currency code (ISO 4217, e.g. USD) with each amount. Never sum different currencies; convert with an explicit stored rate and keep the original amount.
  • JPY has 0 decimals, USD 2, KWD 3, so "cents" is not universal. Use the currency's minor unit, or a DECIMAL with enough scale.
  • Choose precision above display precision for prices and rates (4 decimals is typical) and round only at defined points (per invoice line or per invoice, never repeatedly). Fix the rule: HALF_UP is common in billing, HALF_EVEN (banker's rounding) avoids bias in large sums.
  • In division and percentages, do the multiplication first and round once. Allocate remainders explicitly (split 100.00 three ways: 33.33, 33.33, 33.34).
  • Application: Java BigDecimal built from a String (or from BigDecimal.valueOf), never new BigDecimal(0.1) from a double; JSON should carry amounts as strings or integers, not floats.

Quantities: counts of items are integers; weights and volumes that need fractions use DECIMAL with a declared unit. FLOAT is acceptable for measurements where approximation is inherent (sensor data, scientific values), not for anything you reconcile.

Integer minor units are fast and exact, but the number of decimals differs per currency (JPY has 0, KWD has 3), so keep the currency next to the amount and never add amounts of different currencies. Decide rounding rules in one place (for example banker's rounding or half-up) and apply them at defined points, such as per invoice line. Avoid a MySQL or PostgreSQL MONEY type, which ties you to locale and precision behaviour. The Java side should use BigDecimal with an explicit scale, never double.

Remember: money is DECIMAL or integer cents plus a currency, never FLOAT.

How should you store dates and times, especially time zones? Intermediate

I store instants (when something happened) in UTC, using timestamptz in PostgreSQL or TIMESTAMP or UTC-stored DATETIME in MySQL, and convert to the user's time zone only at the edge, when displaying. For a calendar concept like a birthday or "9:00 local time every day", store the date or local time plus the zone name (an IANA name such as Europe/Berlin), not an offset.

Two different kinds of time, which people confuse.

  • An instant: a single point on the universal timeline. "The order was placed at 2026-03-08 14:03:11 UTC." Everyone agrees on it. Store as UTC.
  • A local (wall-clock) time: "the meeting is at 9:00 in Berlin every Monday" or "the store opens at 08:00 local". It depends on the zone's rules, which can change, so you must keep the local time and the zone name.

What each database type does.

A typical bug. Server A runs in IST, server B in UTC; the app writes LocalDateTime.now() into a zone-less column. The same instant is recorded as two different values depending on the node, and reports shift by 5.5 hours. Fix: set the JVM, DB session and connection to UTC; in Java use Instant or OffsetDateTime for instants.

Daylight saving and future events. "Remind me at 09:00 Europe/Berlin on 2027-03-29": store 2027-03-29 09:00 and Europe/Berlin, because the UTC equivalent depends on rules fixed later. A stored offset like +01:00 would be wrong if a government changes the rules or if DST starts before that date. Local times that do not exist (spring forward) or occur twice (fall back) need a policy.

Dates only: a birthday or a due date is a DATE, with no time and no zone. Do not turn it into a midnight timestamp, which then shifts a day when converted. Query ranges as half-open intervals.

PostgreSQL's timestamptz does not store a zone; it converts input to UTC and renders in the session's zone. The plain timestamp type has no zone at all and is a common source of bugs. MySQL TIMESTAMP is UTC-based but stops at 2038 (as a 32-bit value), while DATETIME has no zone conversion. Offsets like +01:00 are wrong for future events because daylight saving rules change. Date range queries should use half-open intervals as shown earlier.

Remember: store UTC for instants, local time plus zone name for future local events.

When is a JSON column a good idea, and when is it a trap? Intermediate

JSON columns fit data that is flexible, sparse or read as a whole: user preferences, third-party payloads, optional attributes that differ per product type. They are a trap when you filter, join or constrain on fields inside, or when the "flexible" data is actually core and has a stable shape. Then it should be real columns.

When JSON is the right tool. Imagine a product table where laptops have ram and cpu, shirts have size and colour, and new categories arrive weekly. A column per attribute gives hundreds of mostly-NULL columns; the entity-attribute-value alternative makes queries horrible. A JSONB attrs column holds each product's own set. Also right: storing a third-party webhook payload verbatim, user-defined settings, and an event body you only ever read whole.

What you give up, compared with real columns:

Making JSON queryable. PostgreSQL: CREATE INDEX ON product USING gin (attrs) supports attrs @> '{"colour":"red"}'; for one hot field use an expression index ((attrs->>'colour')). MySQL: index a generated column, e.g. colour VARCHAR(20) GENERATED ALWAYS AS (attrs->>'$.colour').

The trap, in a sentence: a field starts as "just something we store" and ends up in WHERE, JOIN, GROUP BY and reports, and now every query digs inside JSON with no constraints and slow plans. Rule of thumb: if you filter, sort, join or constrain on it, or it exists in nearly every row, promote it to a column (a migration from JSON is easy to do with expand and contract). Use JSON for the long tail you read as a whole.

PostgreSQL JSONB can be indexed with GIN, and expression indexes make one hot field fast (CREATE INDEX ON t ((data->>'status'))). MySQL supports JSON with generated-column indexes. What you lose: type checks, foreign keys, easy constraints, statistics for the planner (so estimates are poor), and updating one field often rewrites the entire value. A reasonable hybrid is normal columns for what you query and JSONB for the long tail.

Remember: JSON for the flexible leftovers. Columns for anything you filter, join or constrain.

How do you delete or update millions of rows without hurting production? Intermediate

I do it in small batches, committing between them, instead of one huge statement. A single giant transaction holds locks for a long time, floods the log and replication, can run out of undo space, and if it fails everything rolls back. Batches of a few thousand rows with a short pause keep the system healthy and are resumable.

Why one big statement hurts, itemised. DELETE FROM event WHERE created_at < ... over 50 million rows is one transaction. It holds a lock on every deleted row until the end; writes a huge amount of log (WAL or undo and redo), which fills disks and sends a flood to replicas, making them lag by many minutes; in MVCC engines it produces 50 million dead row versions at once, which slows queries until cleaned; and if it fails at 90 percent, the rollback takes as long again.

Batching, step by step.

  1. Pick a stable ordered key (the primary key) and an indexed filter, so each batch finds its rows without scanning.
  2. Delete 1,000 to 10,000 rows, commit, then sleep a short time (tens to hundreds of milliseconds).
  3. Repeat until the statement reports 0 rows deleted.
  4. Throttle: watch replica lag, lock waits and query latency, and slow down or pause if they rise. Run during off-peak hours.
-- MySQL
DELETE FROM event WHERE created_at < NOW() - INTERVAL 90 DAY ORDER BY id LIMIT 5000;
-- repeat from a loop in app code or a scheduled job until ROW_COUNT() = 0

Batch updates use the same idea over id ranges: WHERE id BETWEEN :a AND :b, advancing the window; this does not need OFFSET and handles gaps. Make each batch idempotent (AND col IS NULL) so a restart is safe. Save progress (last id) so the job is resumable.

Better alternatives for big cases:

  • Partition by time and drop old partitions: instant, no dead rows.
  • Keep a minority: to remove 95 percent of a table, create a new table with the rows to keep, rebuild indexes, and swap names in one quick transaction.
  • TRUNCATE when the whole table goes (it is not row-by-row; takes a strong lock).

Aftercare: deleted space is reused but the file does not shrink (PostgreSQL needs VACUUM FULL or pg_repack; InnoDB needs OPTIMIZE TABLE or rebuild). Update statistics afterwards.

-- repeat until 0 rows are affected
DELETE FROM event
WHERE id IN (SELECT id FROM event WHERE created_at < now() - interval '90 days' ORDER BY id LIMIT 5000);

Make sure the filter column is indexed so each batch is cheap. In MySQL you can write DELETE ... WHERE ... LIMIT 5000 directly. Watch replica lag and slow down if it grows. For regular purging of time-based data, partition by date and DROP PARTITION, which is instant. When deleting most of a table, it is faster to copy the rows to keep into a new table and swap. Remember that deleting rows does not return disk space immediately.

Remember: small batches with commits, indexed filter, watch replica lag. Prefer dropping partitions.

Why is COUNT(*) slow on a big table, and what can you do? Intermediate

Because MVCC means the database cannot keep one cheap row count: each transaction may see a different set of rows, so it has to scan an index or the table to count what is visible to it. Fixes depend on what you need: an approximate count, a maintained counter, or a smaller filtered count with an index.

Why there is no stored row count. In an MVCC database, "how many rows are there" has no single answer: your transaction sees the rows committed before your snapshot, and another transaction running concurrently may see a different set. A global counter would have to be versioned per transaction too, and every insert and delete would then fight over that one counter. So the engine counts the rows visible to you by scanning: the smallest index or the table. A 500 million row table means reading tens of GB, even though the answer is a single number.

Remember: an exact count scans. Use estimates, counters or a "1000+" cap.

How do you store and query a hierarchy such as categories or an org chart? Senior

The simplest is an adjacency list: each row has a parent_id. Query the whole subtree with a recursive CTE. That is enough for most applications. If I need very fast subtree reads on a rarely changing tree, I switch to a materialized path or nested sets.

The data and the question. Categories: Electronics (1) contains Laptops (2) and Phones (3); Laptops contains Gaming (4). Typical queries: all descendants of Electronics, the breadcrumb (ancestors) of Gaming, and moving a subtree.

1. Adjacency list (each row stores its parent). Rows: (1, NULL), (2, 1), (3, 1), (4, 2). Subtree of 1 by recursive CTE returns 1, 2, 3, 4 with depths 0, 1, 1, 2. Ancestors of 4 use the same CTE walking upward. Moving "Laptops" under another parent is a single-row update (parent_id = ...) and the whole subtree follows. Weakness: depth costs one recursive step per level; for very deep, hot read paths it is slower than the alternatives.

2. Materialized path. Each row stores its path: 1 = /1/, 2 = /1/2/, 4 = /1/2/4/. The subtree of 2 is WHERE path LIKE '/1/2/%', a prefix match that a B-tree index serves. Ancestors are just the ids in the path. Moving a subtree means rewriting the path of every descendant. PostgreSQL's ltree type offers operators and GiST indexes for this.

3. Nested sets. Each node stores lft and rgt numbers from a depth-first walk: the subtree of a node is every row whose lft is between the node's lft and rgt, a single range query. Reads are extremely fast, but inserting or moving a node renumbers a large part of the table, so it suits trees that almost never change.

4. Closure table. A separate table stores every ancestor-descendant pair with the distance: (1,1,0), (1,2,1), (1,4,2), (2,2,0), (2,4,1) and so on. Subtree: SELECT descendant FROM closure WHERE ancestor = 1. Ancestors: the reverse. No recursion, supports foreign keys, and works with a node in several places in a DAG. Cost: more rows (up to n times depth), and maintenance on insert (copy the parent's ancestors) and moves.

Choosing: if the tree is small or queried rarely, or you are on a database with recursive CTE support, adjacency list is the best default: it is easiest to keep correct. Reach for a closure table when you need fast, frequent subtree queries with moderate changes; materialized path when you mostly need prefix and breadcrumb queries; nested sets for read-only catalogs. Cycle protection: reject a move whose new parent is inside the moved subtree.

10. Real-life scenarios

These are the incident-style questions. A good answer follows one shape: what is happening, what I check first, the fix, and how I stop it coming back.

A query that was fast for months is now slow as the table grew. What do you do? Intermediate

The plan almost certainly changed or the data outgrew an index-less access path. I get the exact query, run EXPLAIN ANALYZE, and fix what the plan shows: usually a missing or no-longer-selective index, stale statistics, or a query that fetches too much.

Situation: a dashboard query took 50 ms with 1 million rows and now takes 8 seconds with 40 million.

Check first: EXPLAIN (ANALYZE, BUFFERS). Is it a Seq Scan or a big sort? Do estimated and actual rows differ greatly? Did the table recently get a bulk load without ANALYZE? Is it a deep OFFSET page?

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE account_id = 42 AND created_at > now() - interval '7 days'
ORDER BY created_at DESC LIMIT 50;
-- Seq Scan on events ... rows removed by filter: 39,999,000
CREATE INDEX CONCURRENTLY idx_events_acct_time ON events (account_id, created_at DESC);

Fix: add the composite index (equality column first, then the sort column), run ANALYZE, select only needed columns, switch deep paging to keyset. Prevent: load-test with production-sized data, alert on slow queries from pg_stat_statements, and archive or partition old data.

Why this happens, in numbers. A query with no usable index reads the whole table. At 1 million rows that is a few thousand pages, served from cache in 50 ms. At 40 million rows it is about 40 times more pages, which no longer fit in memory, so reads go to disk: 8 seconds. Nothing in the query changed; the cost grows with the data. Even with an index, the plan can flip: when a filter used to match 1 percent and now matches 20 percent, the planner switches from an index to a scan, or an old statistics snapshot makes it choose a nested loop for a huge join.

Triage order: (1) capture the slow statement with real parameter values; (2) EXPLAIN (ANALYZE, BUFFERS) and find the node taking the time; (3) check estimated versus actual rows; (4) check what changed (data volume, a deploy, a new tenant with large data, the last ANALYZE); (5) fix; (6) re-run and compare timing. In the example plan, "Rows Removed by Filter: 39,999,000" says the engine read 40 million rows to return 50, which is exactly the signature of a missing index on the filter and sort columns. After CREATE INDEX CONCURRENTLY (so writes are not blocked) the plan becomes an index scan that reads about 50 entries in order and stops at the LIMIT, back to milliseconds regardless of table size.

Remember: same query, bigger data. Read the plan, index for the filter plus sort, refresh statistics.

The app is hanging and many sessions are waiting on locks. How do you find and fix it? Senior

Find the blocker: one session holding a lock (often a long or forgotten transaction) with a queue of waiters behind it. I identify it from the database's lock views, look at what it is doing, end it if needed, and then fix the code that held a transaction open.

Situation: latency spikes, the connection pool is exhausted, CPU on the database is low.

Check first: who blocks whom.

-- PostgreSQL
SELECT pid, pg_blocking_pids(pid) AS blocked_by, state, wait_event_type, now() - xact_start AS xact_age, left(query, 80)
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0 OR state = 'idle in transaction';
-- MySQL 8
SELECT * FROM sys.innodb_lock_waits;

Fix: if the blocker is idle in transaction, pg_terminate_backend(pid) (or KILL in MySQL) releases the queue; then find why it was left open (a remote call inside a transaction, a missing commit). A DDL waiting for a lock also blocks all later queries, so cancel that DDL first. Prevent: idle_in_transaction_session_timeout, lock_timeout on migrations, short transactions, no remote calls inside them.

Symptom pattern. Latency rises but CPU is low: threads are waiting, not working. The pool fills with sessions all waiting for the same lock.

A typical chain. Session 1 started a transaction, updated a row, and then its application hung on a remote call (idle in transaction). Sessions 2 to 200 try to update the same row and queue behind it. Then someone runs ALTER TABLE: it waits for session 1, and now even plain SELECTs queue behind the ALTER, so the whole table is frozen. Look for the root of the chain: the session that is blocking others but is not itself blocked.

Order of actions:

  1. Run the blocking query above and read the tree: who is at the head, how old is its xact_start, what was its last statement.
  2. If a waiting DDL is in the chain, cancel the DDL first (pg_cancel_backend): that releases everyone queued behind it, and lets reads through.
  3. If the head is idle in transaction or clearly stuck, terminate it (pg_terminate_backend, MySQL KILL). Its transaction rolls back, so confirm that is acceptable. Killing a session that is itself mid-rollback of a huge transaction can take a long time.
  4. Check the app recovers (pool drains), then root-cause: why was a transaction open? Add timeouts so the next one fixes itself.

Remember: find the head of the lock queue, end it, then remove the reason it was long.

Two customers bought the last item, and stock went negative. What happened and how do you fix it? Intermediate

A race: both requests read stock = 1 and both decided to sell. The fix is to make the check and the decrement one atomic statement, with a CHECK constraint as a backstop.

Situation: code does SELECT stock, checks in Java that it is above 0, then UPDATE stock = stock - 1.

Check first: is the check and write in separate statements? What is the isolation level (Read Committed does not help here)?

UPDATE product SET stock = stock - 1 WHERE id = 7 AND stock > 0;
-- affected rows = 1: sold. 0: sold out.
ALTER TABLE product ADD CONSTRAINT stock_non_negative CHECK (stock >= 0);

Fix: the conditional update above. For multi-item carts, lock rows in a fixed order with FOR UPDATE, or use optimistic versions and retry. Prevent: a concurrency test with parallel buyers, and a reconciliation job that alerts on negative stock.

Why it happened, step by step. Stock is 1. Request A: SELECT stock gives 1, Java check passes. Request B: SELECT stock gives 1, check passes. A: UPDATE stock = 0 (computed in code as 1 - 1). B: UPDATE stock = 0, or worse, with stock = stock - 1 the second one sets it to -1 because it computes from the current value without checking. Two orders were accepted for one unit. A transaction does not help at the default Read Committed level because both read before either wrote.

Why the conditional update works. UPDATE ... SET stock = stock - 1 WHERE id = 7 AND stock > 0 is a single statement. The database locks the row, so the second request waits; when the first commits, the second re-evaluates its WHERE on the new row (stock 0), matches nothing, and reports 0 rows affected, which the code treats as "sold out". The check and the change cannot be separated by another transaction. The CHECK constraint is the belt-and-braces: if some other code path forgets the condition, the database refuses the update that would make stock negative.

For carts with several items do the conditional update per product in a single transaction, ordering product ids so concurrent carts cannot deadlock; if any update affects 0 rows, roll back the whole cart. For high contention on one popular item (a flash sale), a hot row becomes the bottleneck: reserve stock in a fast store (Redis atomic decrement) and reconcile with the database afterwards.

Remember: conditional UPDATE does check and change atomically. The CHECK constraint is the safety net.

You find duplicate users with the same email in production. How do you clean up and stop it? Intermediate

Stop new duplicates first, then clean up carefully. Duplicates mean uniqueness was only checked in code, so a race (double click, retry) slipped through. The permanent fix is a unique index, which requires removing existing duplicates, and merging, not just deleting, anything that references them.

Check first: how many and which rule defines "duplicate" (case, spaces)? Which rows have child data?

SELECT LOWER(TRIM(email)) AS e, COUNT(*), array_agg(id ORDER BY id) FROM users GROUP BY 1 HAVING COUNT(*) > 1;

Fix: pick the survivor (oldest or most active), repoint foreign keys (orders, sessions) to it in a transaction, delete the others (see the delete-duplicates question), then CREATE UNIQUE INDEX CONCURRENTLY ON users (LOWER(email)). Normalise the email on write. In code catch the unique violation and return "already exists". Prevent: constraint plus idempotent registration.

Cleanup, in a safe order:

  1. Stop the bleeding. Deploy a fix that handles the race (insert and catch the unique violation) or temporarily block signups with that pattern; but the index in step 5 is the real stop.
  2. Quantify. The query above lists each duplicated email with its ids. Check how many have orders or other child rows.
  3. Choose a survivor per group by an explicit rule (oldest id, or most recent login, or the one with child data).
  4. Merge in a transaction: update each child table's foreign key from loser ids to the survivor id, merge profile fields if needed (for example keep the verified email flag), then delete the losers. Keep a backup table of the deleted rows and a mapping loser to survivor for support.
  5. Add the unique index on the normalised value, built CONCURRENTLY in PostgreSQL to avoid blocking writes. If it fails, duplicates remain: list them again. Apply the same normalisation (lower(trim())) at write time in code or with a generated column.

Be careful with sessions or tokens of the losing accounts, and any external system (billing, search index) that stores the loser id; they need the same mapping.

Remember: merge references first, then add the unique index so it cannot recur.

Your logs show deadlock errors during peak traffic. What do you do? Senior

Deadlocks are normal at low volume and a symptom of lock-order or scope problems at high volume. I read the deadlock report to see which two statements collided, make them take locks in a consistent order, shrink the transaction, and make sure the caller retries.

Check first: the report (SHOW ENGINE INNODB STATUS, or the PostgreSQL log with the two queries). Which tables and indexes, which order? Is a missing index making the statement lock many rows?

Fix:

  • Touch rows in a deterministic order (for example sort ids before a batch update, or always lock the lower account id first).
  • Keep the transaction short, and move work that does not need locks outside.
  • Add the index that makes the statement lock only the rows it needs.
  • Retry the transaction on 40P01 or 1213, with a small random backoff.

Prevent: a concurrency test with opposite-order operations, and an alert on deadlock count.

Reading a deadlock report, with an example. InnoDB prints two transactions. Transaction 1: UPDATE inventory SET qty = qty - 1 WHERE sku = 'A' holds a lock on sku A and waits for sku B. Transaction 2: UPDATE inventory SET qty = qty - 1 WHERE sku = 'B' then waits for sku A. The cause is clear: two orders contain the same two products in different order (A then B, versus B then A). The fix is in the application: sort the lines by sku before updating, so both transactions lock A first.

Another common pattern is two concurrent inserts into a table with a unique index, or gap locks in InnoDB (two sessions each take a gap lock and then both try to insert in that gap). Fixes there: a better index, reducing the transaction scope, or Read Committed if phantoms are acceptable. A third: foreign key checks locking parent rows in different orders during bulk loads; sort the batch.

Retry done right: catch the deadlock error at the transaction boundary (not inside), re-run the whole unit of work, wait a short random time (for example 20 to 100 ms, growing), and cap attempts at 3 to 5. Make sure the re-run is idempotent and sends no external side effects until it finally commits. A deadlock rate that is steady and low with retries working is acceptable; rising counts after a deploy are a bug.

Remember: consistent lock order, short transactions, retry. Do not treat a single deadlock as a bug.

Requests fail with "timeout waiting for a connection from the pool". What now? Intermediate

The pool is empty because connections are held too long or leaked, not because it is too small. I find what is holding them (slow queries, a long transaction, a leak), fix that, and only then consider changing the size.

Check first: the pool's active, idle and waiting counts. On the database, pg_stat_activity: what are the active sessions running, and are many idle in transaction? Did a deploy introduce an N+1 or a remote call inside a transaction? Is a leak detector (HikariCP leakDetectionThreshold) reporting?

Fix: cancel or optimise the slow statements, close connections in finally or try-with-resources, move remote calls out of transactions. Do not simply raise the pool size: more connections give a database with few cores more contention, and instances times pool size can exceed max_connections. Set sensible connectionTimeout so failures are fast. Prevent: dashboards for pool wait time and a statement timeout.

Why the pool empties. By Little's law, connections in use = request rate x time each holds a connection. A pool of 20 with requests holding a connection for 20 ms supports about 1,000 requests per second. If a slow query (or a remote call inside a transaction) raises the hold time to 400 ms, capacity falls to 50 per second, and the wait queue fills up even though nothing was "broken". A leak is the extreme case: a connection never returns, so the pool shrinks by one each time until it is empty.

Diagnosis questions: Is the database busy (CPU high, many active sessions with long-running queries) or quiet (sessions idle in transaction, or the app never got a connection)? Did the exhaustion start with a deploy? Does it coincide with a downstream slowdown (a dependency that is now taking 5 seconds while you hold a connection)? HikariCP exposes active, idle, pending and, with leakDetectionThreshold, logs the stack trace of the code that borrowed a connection and kept it too long.

Typical culprits and cures: (1) a missing index after data growth: fix the query; (2) a @Transactional method that calls an external API: split it; (3) code that opens a connection manually and misses a close on the exception path: use try-with-resources; (4) the web layer keeping a connection through view rendering (Spring open-in-view); (5) a thundering herd after a restart: stagger, or limit concurrency with a bulkhead. A smaller timeout and a circuit breaker make failures fast so they do not pile up.

Remember: an exhausted pool is a symptom. Look for slow queries and leaked connections.

You must add a NOT NULL column with a default to a 500 million row table without downtime. How? Senior

I avoid a table rewrite and a long exclusive lock. On modern PostgreSQL (11+) adding a column with a constant default is a metadata change and instant. Otherwise I add it as nullable, backfill in batches, add the constraint without a full-table check, and deploy the application in step with it.

Check first: engine and version, the table size, replicas, and whether the default is a constant. A volatile default (like now() or random()) still rewrites in PostgreSQL.

SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN channel text;                         -- instant, nullable
-- backfill in batches of 5000, committing, repeating until done
UPDATE orders SET channel = 'web' WHERE id BETWEEN :a AND :b AND channel IS NULL;
ALTER TABLE orders ADD CONSTRAINT channel_nn CHECK (channel IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT channel_nn;                  -- light lock, scans
ALTER TABLE orders ALTER COLUMN channel SET NOT NULL;               -- PG 12+ reuses the validated CHECK

In MySQL 8.0 use ALGORITHM=INSTANT where supported, or gh-ost or pt-online-schema-change for rebuilds. Prevent: rehearse on a production-sized copy and use a short lock timeout so a stuck DDL fails instead of blocking everyone.

Why a naive ALTER is dangerous. ALTER TABLE orders ADD COLUMN channel text NOT NULL DEFAULT 'web' on an old PostgreSQL (before 11) or on a database that rewrites the table copies all 500 million rows under an exclusive lock, which blocks every read and write for hours. Even a quick metadata ALTER needs a brief exclusive lock, and if a long transaction already uses the table, the ALTER queues and everything behind it queues too. That is why the short lock_timeout and retry matter as much as the rewrite question.

The staged plan, in words:

  1. Add the column nullable (instant). Deploy code that writes the value for new rows and tolerates NULL when reading.
  2. Backfill existing rows in id ranges of a few thousand with a short sleep, watching replica lag.
  3. Add a CHECK (col IS NOT NULL) NOT VALID: this takes only a brief lock and enforces the rule for new writes. Then VALIDATE CONSTRAINT, which scans the table but allows reads and writes during the scan.
  4. SET NOT NULL: in PostgreSQL 12+ it uses the validated CHECK to skip the scan, so it is quick. Then drop the redundant CHECK.

With PostgreSQL 11+ and a constant default, step 1 can include the DEFAULT 'web' and the existing rows read the default from metadata with no rewrite; adding NOT NULL still goes through steps 3 and 4 for safety. In MySQL 8.0, ALTER TABLE ... ADD COLUMN ..., ALGORITHM=INSTANT adds a column at the end without rebuilding; for operations that cannot be instant, gh-ost or pt-online-schema-change build a shadow copy of the table, replay ongoing changes, and swap at the end.

Remember: nullable first, batched backfill, validate the constraint later, short lock timeout.

Someone ran UPDATE or DELETE without a WHERE in production. What do you do? Senior

First stop the damage and preserve evidence: if the transaction is still open, ROLLBACK. If it is committed, I restore the affected rows from the most recent backup or a point-in-time recovery copy into a side database and merge only the affected rows back, instead of restoring the whole production database.

Check first: was it committed? Which table, how many rows, when? Is there a backup, point-in-time recovery (PostgreSQL WAL archive, MySQL binlog), or a replica with delayed replay? Stop writes to the table if needed.

Fix: restore a copy to the moment just before the mistake, export the affected rows, and update production from it, in a transaction, verifying row counts. In MySQL, tools can read the binlog to generate reverse statements. Prevent: developers do not use production accounts for ad-hoc writes; run changes inside BEGIN, check the affected row count, then COMMIT; --safe-updates in the MySQL client; reviewed scripts; and a tested restore procedure.

Decision tree.

  1. Is the transaction still open? (The person ran it in a client with auto-commit off, or a session is still connected.) Run ROLLBACK. Done, nothing lost. This is why a habit of BEGIN first matters.
  2. Committed, but the data is recent. Check whether a replica with delayed replay exists: it may still hold the old rows. Pause its replay immediately and copy the rows out. Check also for application-level soft deletes, an audit table, or Kafka topics holding the source events.
  3. Committed and no quick copy: point-in-time recovery. Restore the last full backup to a separate instance, then replay the WAL (PostgreSQL) or binlog (MySQL) up to a time just before the bad statement. Now the old values exist side by side with production.
  4. Merge back only what was lost. Export the affected rows from the restored copy into a staging table in production, compare, and update production in a transaction, restricted to the damaged rows and columns. Rows changed legitimately since the incident should not be overwritten, so match them by key and by what the bad statement changed.

Why not restore everything into production? That would erase all legitimate writes made since the backup. During the incident, consider putting the app into read-only or maintenance mode for the affected feature so more data does not diverge.

Prevention in practice: least-privilege accounts (read-only for humans by default, write access through reviewed jobs), a SQL client set to safe mode (mysql --safe-updates, which rejects UPDATE or DELETE without a key in WHERE), run every manual change as BEGIN; ...; SELECT count(*)...; COMMIT after checking the affected row count, and regularly rehearse restores.

Remember: roll back if you can. Otherwise recover the rows from a point-in-time copy and merge them back.

Users say they save a profile and then see the old data. What is going on? Intermediate

Almost certainly replication lag: the write goes to the primary and the next page load reads from a replica that has not caught up. I route reads that follow a write to the primary, and keep replicas for tolerant reads.

Check first: is read traffic routed to replicas? What is the replica lag at that moment (pg_stat_replication, Seconds_Behind_Source)? Is a cache serving the old value instead? (A stale cache gives the same symptom.)

Fix: for a short window after a write, or for the user's own profile, read from the primary. Alternatively wait until the replica reaches the write's log position, or return the saved data in the write response so the page does not re-read. Prevent: alert on replica lag, mark each repository call as primary-only or replica-ok, and test with an artificially delayed replica.

Confirming the diagnosis. Reproduce: save, then immediately check which host served the follow-up read (log the datasource, or tag queries). Compare the value on primary and replica at that moment. If both are the same but the user still sees the old value, the cause is a cache (CDN, Redis, browser). Replica lag can also be bursty: fine for hours, then seconds-long during a batch job, which is why the bug seems intermittent.

Designing the routing. Many apps annotate calls as readOnly and send all of them to replicas. That is wrong for a read that immediately follows the user's own write. Options, in order of simplicity:

  1. Return the new state from the write call (the POST response includes the saved profile), so the client does not read again.
  2. Sticky primary window: store "last write at" in the session; reads in the next few seconds go to the primary.
  3. Position-aware reads: record the primary's log position after the write; read from a replica only if it has replayed past it, otherwise use the primary.
  4. Always read your own profile from the primary while other users' pages use replicas.

Also look at lag metrics, because a lag of minutes means an unhealthy replica that should be removed from rotation, not just a routing problem.

Remember: read your own writes from the primary. Replicas are for stale-tolerant reads.

The database disk is almost full and growing. What do you check? Senior

I find what is growing before deleting anything: data, indexes, bloat, WAL or binary logs, or temp files. Then I act on that specific cause. Unthinking deletes can make it worse, and rows deleted do not return space to the OS.

Check first: the biggest tables and indexes (pg_total_relation_size, information_schema.tables), then the signs of each cause:

  • WAL or binlog piling up: a stuck replica or an unused replication slot holds WAL forever (PostgreSQL pg_replication_slots). Drop the dead slot, fix the replica, set binlog expiry.
  • Bloat: a long transaction blocking vacuum, or heavy updates. Fix the transaction, tune autovacuum, repack online later.
  • A table of old data: archive or drop partitions.
  • Runaway temp files: a bad query sorting or joining a huge set. Kill it and fix the query.

Prevent: disk and WAL alerts at 70 percent, retention policies, and partitioned time data. Immediate relief: add disk, since that is the quick safe lever.

First, the safety move. If the disk will be full in minutes, buy time before diagnosing: extend the volume (cloud disks usually allow it online), or free safe space such as old rotated logs, since a database that hits 100 percent can crash or stop accepting writes (PostgreSQL stops when WAL cannot be written).

Then find the grower, with queries.

-- PostgreSQL: largest relations, including indexes and toast
SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) FROM pg_class
WHERE relkind = 'r' ORDER BY pg_total_relation_size(oid) DESC LIMIT 10;
-- replication slots keeping WAL
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained FROM pg_replication_slots;
-- MySQL
SELECT table_name, ROUND((data_length + index_length)/1024/1024) AS mb FROM information_schema.tables ORDER BY 2 DESC LIMIT 10;

A heavy reporting query makes the main application slow. How do you separate them? Senior

Move analytics off the primary: run reports on a read replica or a separate analytics store, and protect the primary with timeouts. Reports scan huge ranges, evict useful pages from cache and compete for IO and CPU with the short transactions of the application.

Check first: find the offending query in the slow log or pg_stat_statements and its plan: does it scan the whole table? Could an index, a pre-aggregated summary table or a materialized view serve it?

Fix: in order of effort: (1) add the right index or rewrite; (2) a summary or materialized view refreshed on a schedule; (3) run it on a read replica (accepting lag; long queries on a PostgreSQL replica can conflict with replay, so set the standby delay options appropriately); (4) ship data to a warehouse or column store for real analytics. Add statement_timeout for the reporting role and a lower priority or a separate connection pool.

How a report hurts the app, concretely. A query summing a year of orders reads 30 GB. That read (1) pushes the hot pages of the online workload out of the buffer cache, so checkout queries that were memory hits now go to disk; (2) saturates disk throughput; (3) holds a snapshot open for a long time (in PostgreSQL this delays vacuum of dead rows; in InnoDB it enlarges the undo history); (4) may sort or hash large data, using memory and temp files. The application's requests are small and latency-sensitive; the report is big and throughput-oriented. They want different machines.

Separation options, cheapest first:

  1. Make the query cheaper: an index, a narrower select, or a precomputed summary table (a daily rollup updated by a job) so the report reads thousands of rows instead of millions.
  2. Materialized view refreshed nightly (PostgreSQL REFRESH MATERIALIZED VIEW CONCURRENTLY keeps it readable while refreshing).
  3. Read replica dedicated to reporting, with its own connection pool and a role with statement_timeout. Accept some lag. On a PostgreSQL hot standby, long queries can be cancelled when replay conflicts; options are max_standby_streaming_delay or hot_standby_feedback (which causes bloat on the primary), so choose knowingly.
  4. Warehouse or column store (via CDC or batch export) for heavy analytics: columnar storage and a different engine fit scans and aggregates, and the OLTP database is no longer involved.

Whatever you choose, enforce limits for the reporting role (timeouts, a cap on concurrency, off-peak scheduling) so one bad ad-hoc query cannot take down production.

Remember: keep OLTP and reporting apart: summary tables, a replica, or a warehouse.

A migration failed halfway on production. What state are you in and what do you do? Senior

It depends on whether the DDL is transactional. PostgreSQL runs most DDL inside a transaction, so a failed migration normally rolls back cleanly. MySQL commits DDL implicitly, so a half-applied migration leaves a partial change that I have to inspect and finish or reverse by hand.

Check first: the migration tool's history table (Flyway marks the failed script as failed), the actual schema state, whether the application version in production works against it, and whether data was partly backfilled.

Fix: if the schema is unchanged, fix the script and rerun. If half applied, write a small repair script that completes or reverts the missing steps, mark the migration state in the tool (flyway repair or the tool's equivalent), and rerun. Keep the application on a version compatible with both states, which is the point of expand and contract. Prevent: run migrations on a production-sized copy first, keep each migration small and idempotent (IF NOT EXISTS), use a lock timeout, and make rollback a planned step.

The two worlds, with examples.

  • PostgreSQL (transactional DDL). A migration with BEGIN; ALTER TABLE a ...; CREATE INDEX ...; ALTER TABLE b ...; COMMIT that fails at the third statement rolls back the first two as well. Schema is exactly as before. Exceptions: CREATE INDEX CONCURRENTLY cannot run inside a transaction; if it fails it leaves an invalid index that you must drop and recreate. Data backfills committed in earlier batches stay.
  • MySQL (implicit commit on DDL). Each ALTER commits immediately. If statement 3 of 5 fails, statements 1 and 2 are permanent, and re-running the script fails on statement 1 ("column already exists"). You must inspect SHOW CREATE TABLE and write a repair.

Recovery routine:

  1. Freeze further deploys. Check the tool's state (Flyway's flyway_schema_history shows the failed row; Liquibase uses its lock and changelog tables, and may need the lock released).
  2. Compare actual schema with the intended one, object by object (columns, indexes, constraints). Check for leftovers: invalid indexes, half-copied data, locks still held by the dead session.
  3. Decide forward (finish the migration with the missing steps) or backward (revert the applied ones). Prefer forward when the remaining steps are safe.
  4. Fix the history table (flyway repair), apply the fix, rerun, verify the app.

Writing migrations with IF NOT EXISTS and IF EXISTS guards, and testing them against a restored production copy including data volume and concurrent traffic, makes this situation rare and the recovery mechanical.

Remember: PostgreSQL DDL rolls back, MySQL DDL does not. Small, idempotent, backward-compatible migrations.
