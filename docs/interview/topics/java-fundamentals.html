Mental model: the 7 ideas everything hangs on

One line: in Java, variables hold either a primitive value or a reference to an object on the heap, and every call copies that value. Objects are behaviour plus state, reached through types that decide which method runs.
  1. Two kinds of values. A primitive variable holds the number itself. A reference variable holds an address of an object (or null). Almost every classic trap (==, pass-by-value, NPE) comes from mixing these up.
  2. Everything is passed by value. A method receives a copy of the primitive, or a copy of the reference. It can change the object the reference points to, but never the caller's variable.
  3. Static type decides what compiles, runtime type decides what runs. Overloads are chosen by the compiler from declared types. Overridden instance methods are chosen at run time from the real object. Fields and static methods are never overridden, only hidden.
  4. Objects are built in a fixed order. Class loading and static init once, then for each new: parent fields and constructor, then child fields and constructor.
  5. Contracts matter more than syntax. equals, hashCode and compareTo are promises that hash-based and sorted collections rely on. Break one and you get lost entries, not compile errors.
  6. Immutability is the cheapest safety. An object that never changes needs no locks, no defensive copies when shared, and is safe as a map key. Records, enums, String and List.of are built on this idea.
  7. Prefer composition and small public surface. Inheritance is the tightest coupling Java offers. Use it for true "is-a" with a stable base, otherwise combine objects, and keep fields private.

1. Primitives, wrappers and Strings

What are Java's primitive types, their sizes and default values? Basic

What the interviewer is testing: basics, plus whether you know that sizes are fixed by the language and not by the machine.

There are eight. Whole numbers: byte (8 bits), short (16), int (32), long (64), all signed. char is 16 bits and unsigned, holding a UTF-16 code unit. Decimals: float (32) and double (64), both IEEE 754 floating point. And boolean, whose size the language does not fix (the JVM usually uses a byte or int). The sizes never change between platforms, unlike C. Defaults apply only to fields and array elements: 0, 0.0, false, and '\u0000'. Local variables have no default, and the compiler refuses to compile if you read one before assigning it.

Likely follow-ups
  • Range of int? About minus 2.1 billion to plus 2.1 billion (2^31 - 1 is 2,147,483,647).
  • Is String a primitive? No. It is a class, with special language support for literals and +.
Primitive versus wrapper class: when do you use which? Basic

What the interviewer is testing: do you know the cost and the null trap of wrappers.

Each primitive has a wrapper class: Integer, Long, Double, Boolean, Character and so on. A primitive is just the value: fast, small, never null. A wrapper is a full object on the heap: it costs about 16 bytes for an Integer plus a reference, it can be null, and it can be used where objects are required, such as generics (List<Integer>), map keys, and Optional. My rule: use primitives by default for fields, locals, parameters and return values. Use a wrapper only when you need "no value" (null), or a generic type. A List<Integer> of a million numbers uses several times more memory than an int[], and unboxing a null wrapper throws NullPointerException.

Integer count = map.get("hits");   // may be null
int n = count;                       // NPE if the key was absent
Likely follow-ups
  • Why does a database column that allows NULL map to a wrapper field? Because a primitive cannot represent "unknown".
  • Why are there special streams like IntStream? To avoid boxing every element.
What are autoboxing and unboxing, and where do they bite? Basic

What the interviewer is testing: hidden costs and hidden NPEs.

Since Java 5 the compiler converts automatically between a primitive and its wrapper. Boxing turns int into Integer by calling Integer.valueOf. Unboxing calls intValue(). This is convenient, but it hides three problems. First, a null wrapper being unboxed throws NPE, often far from the cause. Second, boxing inside a loop creates lots of short-lived objects, for example a Long sum = 0L; sum += i; loop allocates a new Long on every step and can be many times slower than a long. Third, comparing wrappers with == compares references, not values, and gives surprising results (next question). In a mixed expression such as Integer plus int, Java unboxes first, so null still blows up.

Long sum = 0L;                  // bug: should be long
for (int i = 0; i < 1_000_000; i++) sum += i;   // box, add, box again
Why is Integer a = 127, b = 127; a == b true but with 128 it is false? Basic

What the interviewer is testing: the most famous Java trap. A strong answer explains the cache and says what to do instead.

Integer.valueOf(int), which boxing uses, keeps a cache of Integer objects for values from -128 to 127. Inside that range, two boxings of the same number return the same object, so == (reference comparison) is true. Outside the range, each boxing creates a new object, so two boxings of 128 are two different objects and == is false. The upper limit can be raised with -XX:AutoBoxCacheMax, but the lower limit is fixed. Byte, Short, Long and Character (0 to 127) have similar caches, and Boolean has two shared instances. Double and Float have none. The fix is simple: compare wrapper values with equals, or unbox to int first. And new Integer(5) always makes a fresh object (that constructor is deprecated since Java 9 and marked for removal since Java 16).

Likely follow-ups
  • Does a < b on Integers work by value? Yes, relational operators unbox. Only == and != compare references when both sides are wrappers.
  • What about Integer a = 128; int b = 128; a == b? True: one side is primitive, so a is unboxed.
Common mistakes: saying "it is a bug in Java". It is specified behaviour (JLS 5.1.7), and the cache exists to save memory for small numbers.
What is the difference between == and equals()? Basic

What the interviewer is testing: reference identity versus logical equality.

For primitives, == compares the values. For references, == asks "are these the exact same object in memory?". equals() asks "do these objects represent the same thing?". The default Object.equals is just this == other, so a class that does not override it has identity equality only. String, the wrappers, List, Set, Map, LocalDate and records all override it to compare content. Think of two paper copies of the same contract: == asks if it is the same sheet, equals asks if the text is the same. Always call equals on a non-null object (or use Objects.equals(a, b)) to avoid NPE, and for enums == is the right choice.

String a = new String("hi"), b = new String("hi");
a == b          // false: two objects
a.equals(b)     // true: same characters
"hi".equals(x)  // null-safe if x is null
Objects.equals(x, y)
Likely follow-ups
  • Why is == fine for enums? Each constant is a single instance, so identity and equality are the same, and == is also null-safe and type-checked at compile time.
  • Does == work on double values safely? NaN == NaN is false, and 0.0 == -0.0 is true. Use Double.compare when that matters.
Which numeric traps should every Java developer know? Intermediate

What the interviewer is testing: overflow, precision and promotion rules that cause silent wrong answers.

Integer arithmetic overflows silently and wraps around: Integer.MAX_VALUE + 1 is Integer.MIN_VALUE, and Math.abs(Integer.MIN_VALUE) is still negative. Use Math.addExact and friends to throw instead, or use long. Integer division truncates: 7 / 2 is 3, and double d = 7 / 2 is 3.0 because the division happens first. Floating point cannot represent most decimals: 0.1 + 0.2 is 0.30000000000000004, so never use double for money, and never compare doubles with ==. In an expression, byte, short and char are promoted to int, so short s = 1; s = s + 1; does not compile, while s += 1 does, because compound assignment adds a hidden cast. Casting a big long to int keeps only the low 32 bits. Casting a double to int truncates toward zero. The remainder operator % can be negative: -7 % 3 is -1, so use Math.floorMod for array indexes.

Likely follow-ups
  • How do you compute a hash bucket from a possibly negative hash? Math.floorMod(h, n), or mask with h & 0x7fffffff.
  • What does 1 / 0 do compared to 1.0 / 0? The first throws ArithmeticException, the second gives Infinity.
How should you represent money in Java? Intermediate

What the interviewer is testing: do you avoid floating point for exact values, and do you know the BigDecimal traps.

Not with double. Two good options: store the amount as a long of the smallest unit (cents, paise) together with a currency code, or use BigDecimal. With BigDecimal, create values from strings or BigDecimal.valueOf(double), never new BigDecimal(0.1), which captures the exact binary error of 0.1. Always pass a rounding mode to divide, because 1/3 has no finite decimal and throws ArithmeticException otherwise. And remember that equals on BigDecimal also compares scale, so new BigDecimal("2.0").equals(new BigDecimal("2.00")) is false. Use compareTo for numeric comparison, and stripTrailingZeros if you must hash it. In larger systems, wrap the amount and currency in an immutable Money value class (or a record) so you never add dollars to rupees by accident.

new BigDecimal("2.0").equals(new BigDecimal("2.00"))     // false
new BigDecimal("2.0").compareTo(new BigDecimal("2.00"))  // 0
a.divide(b, 2, RoundingMode.HALF_UP);
Why is String immutable, and what does that buy you? Basic

What the interviewer is testing: design reasoning, not just the fact.

Once a String is created its characters never change; methods like toUpperCase or replace return a new String. The class is final and its internal array is private and never exposed. This gives several benefits. Strings can be shared safely between threads with no locking. The String pool can reuse one object for many identical literals. The hash code can be computed once and cached, which makes Strings fast map keys. Security-sensitive values, such as a file path, a class name or a database URL, cannot be changed after they were checked. The cost is that building a string by many small appends creates many temporary objects, which is why StringBuilder exists. Since Java 9 a String stores Latin-1 text in a byte[] (one byte per char) when it can, and UTF-16 otherwise ("compact strings").

Likely follow-ups
  • Can you change a String with reflection? You could in old versions, but you should not: it breaks the pool and the cached hash, and modern Java blocks it by default with module encapsulation.
  • Why do people say use char[] for passwords? A String stays in memory until garbage collection and may be in the pool, while an array can be overwritten right after use. In practice the benefit is modest, but it is a known guideline.
What is the String pool? How do literals, new String and intern() behave? Intermediate

What the interviewer is testing: the memory model behind the == puzzle, and how many objects a line creates.

The pool (formally the string intern table) is a part of the heap, since Java 7 (before that it was in PermGen), that keeps one shared instance per distinct literal. When the class loads, every literal such as "hello" is put in the pool, and later uses of the same literal point to the same object. new String("hello") always creates a new object on the heap that is not the pooled one (the literal is in the pool too, so that line may involve two objects). s.intern() returns the pooled instance for that content, adding it if needed. Compile-time constants are also pooled: "he" + "llo" is folded by the compiler into "hello", but a + "llo" where a is a normal variable is computed at run time and gives a new object.

Likely follow-ups
  • Should I call intern() in application code? Rarely. It can save memory for huge numbers of repeated strings, but a table that is global and native can be slow. Prefer your own Map or just a smaller data model. Java 7 made the pool GC-able and larger.
  • How many objects does String s = new String("a") + "b"; create? A few: literal "a", the new String, and a result built by the concatenation (via StringBuilder or an indy call), plus the pooled literal "b". Interviewers like the thinking more than the exact number.
String, StringBuilder and StringBuffer: how do they differ and when do you use each? Basic

What the interviewer is testing: mutability and thread safety trade-offs.

String is immutable. StringBuilder is a mutable, growing buffer of characters that is not thread-safe, and it is the normal choice for building text in a loop. StringBuffer is the older version where every method is synchronized. That sounds safe, but a lock on every append is rarely what you want: you usually build a string inside one method on one thread, and when several threads do share a buffer you generally need to lock a whole sequence of operations anyway. So StringBuffer is almost never the right answer today. Both builders start with a capacity (16 by default) and grow by roughly doubling, so passing an expected size to the constructor avoids copying. For a simple one-line a + b + c you do not need a builder: the compiler already optimises it. Use String.join or StringJoiner for separators.

StringBuilder sb = new StringBuilder(64);
for (String part : parts) sb.append(part).append(',');
if (sb.length() > 0) sb.setLength(sb.length() - 1);   // drop the last comma
String csv = String.join(",", parts);                    // simpler
Likely follow-ups
  • Is s1.equals(sb) true when they have the same text? No. Different classes. Compare with s.contentEquals(sb).
Is string concatenation with + in a loop really slow? What does the compiler do? Intermediate

What the interviewer is testing: knowing the difference between a one-line concat and a concat in a loop.

A single expression such as "id=" + id + ", name=" + name is fine. Before Java 9 the compiler turned it into a StringBuilder chain. From Java 9 it uses an invokedynamic call (StringConcatFactory), which can size the result exactly and is usually faster. The problem is a loop: s += x each time creates a new String and copies all the old characters, so n appends cost O(n squared) time and produce a lot of garbage. For 100,000 appends this is the difference between milliseconds and many seconds. In a loop, create one StringBuilder outside and append inside. The JIT compiler cannot reliably rewrite that for you across iterations. Also in logging, prefer a placeholder like log.debug("user {}", id) so that the concatenation is skipped when debug is off.

Likely follow-ups
  • What does "" + null give? The text "null". Concat never throws NPE for a null operand.
How does switch work on a String, and what are the limits? Intermediate

What the interviewer is testing: knowing it is compiler magic over hashCode and equals, and the null trap.

Switch on String arrived in Java 7. The compiler turns it into two steps: a switch on s.hashCode() to jump to a candidate, then an equals check to confirm (needed because different strings can share a hash, such as "Aa" and "BB"). So it is case-sensitive and uses content equality. A null selector throws NPE, so check null first. Case labels must be compile-time constants (literals or static final constants). The old statement form falls through when you forget break. Java 14 added the arrow form and switch expressions, which do not fall through, can return a value, and force you to cover all cases for enums and sealed types. In Java 21, case null is allowed in pattern switches.

int days = switch (month) {          // Java 14+
    case "FEB" -> 28;
    case "APR", "JUN", "SEP", "NOV" -> 30;
    default -> 31;
};
What are text blocks, and what should you know about them? Basic

What the interviewer is testing: modern syntax awareness, plus the indentation rule.

A text block is a multi-line string literal that starts and ends with three double quotes. It is final in Java 15 (preview in 13 and 14). It is meant for JSON, SQL, HTML or XML, so you do not need \n and escaped quotes. The opening quotes must be followed by a line break. The compiler removes the common leading indentation (decided by the least indented line, including the closing quotes), strips trailing spaces on each line, and normalises line breaks to \n. A backslash at the end of a line joins it with the next, and \s keeps a trailing space. You can still use String.formatted(...) (Java 15) to fill in values. Be careful with SQL: build it with bind parameters, not by formatting user input into the text.

String json = """
    {
      "name": "%s",
      "active": true
    }
    """.formatted(name);
What is the difference between trim() and strip(), and which newer String methods are worth knowing? Intermediate

What the interviewer is testing: day-to-day API fluency across versions.

trim() removes characters up to code 32 (spaces and control characters) from both ends. strip() (Java 11) uses the Unicode definition of whitespace, so it also removes things like the ideographic space. Prefer strip() for new code. Other Java 11 additions: isBlank() (empty or only whitespace), lines() (a stream of lines), repeat(n). Java 12 added indent and transform. Java 15 added formatted and stripIndent. Java 16 added Stream.toList(), not on String but often used with it. Older but important: String.valueOf is null-safe where obj.toString() is not, split takes a regex (so "a.b".split(".") returns nothing, use "\\.") and drops trailing empty strings, and replace replaces text while replaceAll uses a regex.

Why are Strings such popular HashMap keys? Intermediate

What the interviewer is testing: link between immutability and hashing.

A map key must keep the same hash code for as long as it is in the map. Because a String cannot change, its hash never changes. The class also caches the hash in a field after the first call, so repeated lookups do not re-scan the text. Its equals and hashCode are correctly overridden to use content. The hash formula is s[0]*31^(n-1) + ... + s[n-1], computed with int wrap-around. Strings with the same content give the same hash even if they are different objects, so a lookup with a new String instance still finds the entry. One more property to mention: hash collisions on String keys are possible, and since Java 8 a heavily collided HashMap bucket turns into a tree, so a flood of colliding keys is only slow (O(log n)) and not catastrophic. See the collections page for the bucket details.

2. Keywords, pass-by-value and initialization

Is Java pass-by-value or pass-by-reference? Basic

What the interviewer is testing: a precise answer. Saying "objects are passed by reference" is the classic wrong answer.

Java is always pass-by-value. When you call a method, each argument is copied into the parameter. For a primitive, the number is copied. For an object, the reference (the address) is copied. So the method has its own variable that points at the same object. Through that copy it can change the object's contents, and the caller will see it. But if the method assigns a new object to its parameter, only its own copy changes, and the caller's variable still points at the old object. The proof is the swap test: you cannot write a swap(a, b) method in Java that swaps the caller's variables.

static void change(StringBuilder sb, int n, List<String> list) {
    sb.append("!");          // visible to caller: same object
    n = 99;                  // invisible: copy of a primitive
    list = new ArrayList<>(); // invisible: only the local copy was re-pointed
}
Likely follow-ups
  • So how do you return two values? Return a small record or object, since you cannot change the caller's variables.
  • Is an array passed by reference? An array is an object, so the reference is copied by value. Changing an element is visible, re-assigning the parameter is not.
Common mistakes: "primitives by value, objects by reference". Objects are never passed at all: only references are, by value.
What does static mean on a field, a method, a block and a nested class? Basic

What the interviewer is testing: class-level versus instance-level state.

static means "belongs to the class, not to an instance". A static field exists once per class (per class loader, to be exact) and is shared by all instances. A static method is called on the class, has no this, and cannot touch instance fields directly. It is not overridden, only hidden. A static initializer block static { ... } runs once when the class is initialized, for example to fill a lookup table. A static nested class does not hold a reference to an outer instance. The main danger is shared mutable static state: it is global, hidden, hard to test and not thread-safe unless you protect it. Good uses are constants, pure helper functions, factory methods and a few well-guarded caches. Keep static methods stateless.

Likely follow-ups
  • Can a static method access an instance field? Only through an object reference you give it.
  • Why is main static? So the JVM can call it without creating an object first.
What does final mean on a variable, a method, a class and a parameter? Basic

What the interviewer is testing: the difference between a final reference and an immutable object.

A final variable can be assigned only once. For a primitive that means the value is fixed. For a reference it means the variable cannot point somewhere else, but the object can still change: a final List can still have elements added. A final field must be set by the end of the constructor (or in its declaration), and that gives a thread-safety guarantee: once the constructor finishes, other threads see the correct final field values, even without synchronization (as long as this did not escape). A final method cannot be overridden. A final class cannot be extended (String, Integer). A final parameter or local variable cannot be reassigned, which helps readability and lets lambdas capture it. A local variable that is never reassigned is "effectively final" (Java 8) and can be captured by a lambda or anonymous class even without the keyword.

final List<String> names = new ArrayList<>();
names.add("ok");              // allowed
names = new ArrayList<>();    // compile error
Likely follow-ups
  • final vs finally vs finalize? A modifier, a block that always runs after try, and a deprecated method called by GC.
  • Why must lambda-captured locals be effectively final? The lambda gets a copy of the value, and allowing changes to either copy would cause confusion and thread issues.
What does transient do, and what happens to a transient field after deserialization? Intermediate

What the interviewer is testing: Java serialization behaviour.

transient tells default Java serialization to skip a field. Use it for data that should not be saved: passwords, caches, derived values, thread handles, open connections, or objects that are not Serializable. When the object is read back, the transient field is not restored from the stream. It gets the default for its type (null, 0, false), and field initializers and the constructor do not run, because deserialization does not call the constructor of a serializable class. So you must rebuild it in a readObject method or lazily. Also note that static fields are never serialized, and that transient has no effect on JSON libraries like Jackson by default (Jackson has its own @JsonIgnore, though it can be configured to respect transient).

Likely follow-ups
  • A cached total is marked transient but still non-zero after read-back? Impossible for default serialization. Check whether another library (or a custom readObject) refilled it.
What does volatile guarantee, and what does it not? Intermediate

What the interviewer is testing: visibility versus atomicity. Full coverage is on the concurrency page.

A volatile field guarantees two things. Visibility: a write by one thread is seen by later reads in other threads (no stale value held in a CPU cache or register). Ordering: a volatile write happens-before a later read of the same field, and the compiler and CPU cannot reorder normal operations across it in a way that breaks that rule. It does not make compound actions atomic. count++ on a volatile int is still three steps (read, add, write), and two threads can lose an update. Use AtomicInteger or a lock for that. Typical good uses: a stop flag (volatile boolean running), publishing an immutable object by replacing a reference, and the double-checked locking singleton.

Likely follow-ups
  • Can volatile be used on a final field? No, it is a compile error: they are opposites.
In what order does Java initialize a class and its objects when parent and child both have static blocks, instance blocks and constructors? Intermediate

What the interviewer is testing: a classic and very common output-prediction question.

First the class is initialized, once: the parent's static fields and static blocks run in source order, then the child's. This happens the first time the class is used, not when the program starts. Then for each new Child(): memory is allocated and all fields get default values (0, null). The child constructor starts, and its first step is a call to the parent constructor (explicit super(...) or implicit). The parent's instance field initializers and instance blocks run, then the parent constructor body. Back in the child: its instance field initializers and instance blocks, then the child constructor body. A second new Child() skips the static part.

Likely follow-ups
  • Where do field initializers and instance blocks go relative to the constructor? The compiler copies them to the start of each constructor, right after the super call, in source order.
When exactly is a class initialized? How does the lazy holder idiom use that? Senior

What the interviewer is testing: link between class initialization rules and thread-safe lazy singletons.

A class is loaded when it is first needed, but it is initialized (static blocks and static field initializers run) on the first of these: creating an instance with new, calling a static method, or reading or writing a static field that is not a compile-time constant. Referring to a static final int X = 5 constant does not trigger it, because the compiler inlines the value. Subclass initialization first initializes the superclass; an interface is initialized only when one of its static members is used (or, for default methods, when an implementing class is initialized). The JVM guarantees class initialization runs once and is protected by a lock, so other threads wait. That gives a thread-safe lazy singleton with no synchronized code: put the instance in a private static nested holder class, which loads only when getInstance() is first called.

public final class Config {
    private Config() {}
    private static class Holder { static final Config INSTANCE = new Config(); }
    public static Config getInstance() { return Holder.INSTANCE; }
}
Likely follow-ups
  • What if static init throws? The class gets marked failed: the first user sees ExceptionInInitializerError, and later uses see NoClassDefFoundError. In production logs, look for the first one.
Why is calling an overridable method from a constructor dangerous? Senior

What the interviewer is testing: understanding of init order and virtual dispatch together.

While the parent constructor runs, the object is already a child instance, so a call to an overridable method goes to the child's override. But the child's constructor and field initializers have not run yet. The child method therefore sees fields with default values (null, 0), or ones assigned in the declaration that has not yet executed. The result is an NPE or a wrong value that is hard to debug. The fix: do not call overridable methods in a constructor. Call private or final methods, or use a static factory plus an explicit init step, or pass what you need through the constructor parameters. Tools like IDE inspections and static analysers flag this pattern.

class Base {
    Base() { show(); }               // calls the override!
    void show() { }
}
class Child extends Base {
    private String name = "kim";
    Child() { super(); }
    @Override void show() { System.out.println(name.length()); }  // NPE: name is still null
}
What is var, and when should you avoid it? Basic

What the interviewer is testing: that you know it is still static typing, and that you use it with judgement.

var (Java 10) lets the compiler infer the type of a local variable from its initializer. It is not dynamic typing: the type is fixed at compile time. It works only for local variables with an initializer, for loop variables, and since Java 11 for lambda parameters. It does not work for fields, method parameters, return types, or var x = null. var is not a keyword but a reserved type name, so you can still have a variable called var. Use it when the type is obvious from the right side (var users = new ArrayList<User>()) or very long. Avoid it when the type matters to the reader, such as var result = service.process(), and note that var list = new ArrayList<>() infers ArrayList<Object>, and var n = 1 is an int even if you wanted a long.

3. Classes, objects and the OOP pillars

What is the difference between a class and an object, and what really happens on new? Basic

What the interviewer is testing: a clear mental model of instantiation.

A class is the blueprint: it declares fields (state) and methods (behaviour). An object is one live instance built from that blueprint, with its own copy of the instance fields. The expression new User("Asha") does these steps: the JVM makes sure the class is loaded and initialized; it allocates memory on the heap and sets every field to its default value; it runs the constructor chain (parent first); and it returns a reference to the new object. The variable on the left holds only that reference. Methods are not copied per object: all instances share one copy of the code, and the object just carries a hidden pointer to its class. Each object also has an identity (its reference), and a header with a hash code, lock information and the class pointer.

Likely follow-ups
  • How many bytes does an empty object take? Typically 16 bytes with the header on a 64-bit JVM with compressed pointers (12 bytes of header, padded to 8-byte multiples). Exact numbers depend on the JVM.
  • What is an instance versus a reference? The instance is the object on the heap, the reference is the handle you hold.
How do constructors work? What is the default constructor, and what happens when you add your own? Basic

What the interviewer is testing: the "default constructor disappears" trap and constructor chaining.

A constructor has the class name and no return type. It sets up a new object. If you write no constructor, the compiler adds a public no-argument one (with the same access as the class) that just calls super(). The moment you write any constructor, the compiler adds nothing. So a class with only User(String name) has no no-arg constructor, and a subclass that does not explicitly call super(name) fails to compile with "constructor User in class User cannot be applied". Frameworks that need a no-arg constructor (JPA, older Jackson, Java serialization of the first non-serializable parent) will fail at run time or compile time. You can have several constructors with different parameters (overloading), and they can call each other with this(...) to avoid repeating setup. Constructors are not inherited and cannot be abstract, static or final. A private constructor blocks outside instantiation: used for singletons, utility classes and static factories.

Likely follow-ups
  • Can a constructor throw an exception? Yes, checked or unchecked. If it throws, the object is never returned. Be careful about leaving half-built resources.
  • Can a constructor be synchronized? No. Use a block inside, though it is rarely needed since no other thread has the reference yet.
What are this and super used for, including this(...) and super(...)? Basic

What the interviewer is testing: constructor rules.

this is a reference to the current object. It is used to tell a field from a same-named parameter (this.name = name), to pass the current object to another method, and to return it for chaining. super.method() calls the parent's version of a method, useful when you extend behaviour instead of replacing it; super.field reads a hidden parent field. In constructors, this(args) calls another constructor of the same class, and super(args) calls a parent constructor. Either must be the first statement, and you can use only one of them in a constructor, which is why they cannot be combined. If you write neither, the compiler inserts super(). Java 22 previewed "statements before super(...)" (JEP 447), allowing validation code that does not use this before the call, and Java 25 finalized the idea as flexible constructor bodies. Neither this nor super exists in a static method.

class Account {
    private final String id; private final long cents;
    Account(String id) { this(id, 0); }              // chain to the full constructor
    Account(String id, long cents) { this.id = id; this.cents = cents; }
}
Explain the four pillars of OOP with real examples, not definitions. Basic

What the interviewer is testing: can you tie the textbook words to actual design decisions.

Encapsulation: keep state private and expose behaviour. A BankAccount has a private balance and a withdraw method that checks the limit. Nobody can set the balance to a negative number from outside, so the rule lives in one place. Abstraction: show what something does, hide how. Your code calls a PaymentGateway.charge() interface. It does not care whether Stripe or a bank is behind it. Inheritance: a class reuses and extends another. SavingsAccount extends Account gets deposit and withdraw and adds interest. It is powerful but couples the child to the parent's internals. Polymorphism: one call, different behaviour depending on the real object. for (Shape s : shapes) total += s.area(); works for circles and squares, and adding a triangle needs no change to that loop. Interviewers often add a fifth thought: prefer composition, and program to interfaces.

Likely follow-ups
  • Is a class with public fields encapsulated? No. Getter and setter pairs on every field are almost as bad: real encapsulation hides rules, not just fields.
Show encapsulation that actually protects an invariant. Intermediate

What the interviewer is testing: maturity: encapsulation protects rules, it is not "make fields private and add getters".

An invariant is something that must always be true, such as "balance is never negative" or "end date is after start date". If the fields are public, any code can break it. If the class owns the data and only allows changes through methods that check the rule, the invariant is safe and the check is in one place. Also do not leak internals: a getter that returns the internal list lets callers add to it. Return an unmodifiable view or a copy. And make the object valid from construction, so no half-built state exists.

public final class DateRange {
    private final LocalDate start, end;
    public DateRange(LocalDate start, LocalDate end) {
        if (end.isBefore(start)) throw new IllegalArgumentException("end before start");
        this.start = start; this.end = end;
    }
    public boolean contains(LocalDate d) { return !d.isBefore(start) && !d.isAfter(end); }
}

Notice there are no setters. To "change" it you create a new one. LocalDate is immutable, so nothing leaks.

What is the difference between abstraction and encapsulation? Basic

What the interviewer is testing: two ideas that people blur together.

Abstraction is about the outside view: you define a simple contract (an interface or abstract class) that says what can be done, and you hide the many ways it could be done. Encapsulation is about the inside: you bundle data with the code that works on it and hide the data so rules cannot be bypassed. A car's pedals are abstraction (you press to go, no need to know about the engine). A locked engine bay is encapsulation (you cannot reach in and change the fuel mix). In code, List is an abstraction, and the private Object[] elementData in ArrayList is encapsulation. They work together, but one is about design of contracts and the other about protecting state.

Inheritance or composition? Why do people say "favour composition over inheritance"? Senior

What the interviewer is testing: design judgement, and knowing the fragile base class problem.

Inheritance is a compile-time, whole-class relationship: the child gets everything from the parent, including parts it should not have, and it depends on how the parent works inside. If the parent changes, a child can break (the "fragile base class" problem). The famous example is HashSet extended to count added items: addAll calls add internally, so the counter goes up twice. With composition, your class has a collaborator, and exposes only the methods you choose. It is also swappable at run time (strategy), and easy to test with a fake. Use inheritance only for a real "is-a" relationship where the base class is designed for extension, documented, and stable, and where the Liskov rule holds. Otherwise wrap and delegate. Java even helps: interfaces plus default methods give shared behaviour without a shared state hierarchy.

Likely follow-ups
  • When is inheritance right? Framework extension points (abstract base classes designed for it), true type hierarchies such as exceptions, and sealed hierarchies you own.
  • What is the decorator pattern? Composition that wraps an object with the same interface to add behaviour, like BufferedReader around a Reader.
What is the Liskov Substitution Principle, with an example of breaking it? Senior

What the interviewer is testing: the rule that decides whether a subclass is legitimate.

LSP says: code written for the parent type must keep working, with the same expectations, when you pass any child. It is about behaviour, not just method signatures. The classic breakage is Square extends Rectangle. A rectangle's contract is "I can set width and height independently". A square must change both together, so code like r.setWidth(5); r.setHeight(4); assert r.area() == 20 fails for a square. Other typical violations: a child that throws UnsupportedOperationException for an inherited method (an immutable list pretending to be a mutable List), a child that strengthens preconditions (accepts less) or weakens postconditions (promises less), and a child that returns null when the parent never did. The practical test is: "would a caller need an instanceof check to be safe?". If yes, the hierarchy is wrong. Prefer a common interface, or composition.

Explain the four access levels, including the default one. Basic

What the interviewer is testing: where code can be seen from, and the subtle protected rule.

private: visible only inside the same class (and its nested classes). Package-private (no keyword): visible to any class in the same package. protected: package-private plus subclasses in other packages. public: visible everywhere (and with modules, only if the package is exported). A top-level class can only be public or package-private. The subtle point about protected: in a different package, a subclass can use the protected member only through a reference of its own type (or a subtype), not through a parent-type reference. The rule I follow: start with private, widen only when needed. Fewer public things means fewer things you must keep stable for callers.

Likely follow-ups
  • Can an overriding method reduce visibility? No. It may widen it (protected to public), but never narrow it.
  • Can you make a class private? Only a nested class can be private. A top-level class cannot.

4. Inheritance, polymorphism, abstract classes and interfaces

Abstract class versus interface: how do they differ, and how do you choose? Basic

What the interviewer is testing: a modern answer that includes default methods, not the Java 7 answer.

An abstract class is a partly built class: it can have instance fields (state), constructors, any access level, concrete and abstract methods. A class can extend only one. An interface is a contract of capabilities: no instance state (only constants), no constructors, and a class can implement many. Since Java 8 an interface can have default methods (an implementation) and static methods, and since Java 9 private methods to share code between them. So "interfaces cannot have code" is out of date. The deciding questions: do implementations share state or a template algorithm? Use an abstract class (for example a base class with fields and a process() that calls abstract steps). Is it just a capability that unrelated classes can have (Comparable, Closeable), or do you need multiple types? Use an interface. In practice: start with an interface; add an abstract skeleton class if many implementations share code (like AbstractList for List).

Likely follow-ups
  • Can an abstract class have a constructor? Yes, called by subclass constructors. It cannot be used with new directly.
  • Can an interface have fields? Only public static final constants. They are implicit, so no instance state.
  • Why no multiple inheritance of classes? Because of state and the diamond problem. Interfaces avoid state, and for default methods the rules below resolve conflicts.
What are default methods for, and how does Java resolve the diamond problem when two interfaces provide the same default? Intermediate

What the interviewer is testing: the three resolution rules.

Default methods (Java 8) let you add a method to an interface without breaking the existing implementors. That is how List.sort, Collection.stream and Map.getOrDefault were added to old interfaces. If a class inherits the same method from several places, the rules, in order, are: (1) a method from a class (or superclass) always wins over an interface default, "class wins"; (2) otherwise the more specific interface wins, i.e. a sub-interface that overrides it; (3) if still ambiguous, the compiler gives an error and you must override the method yourself, and may pick one with A.super.hello(). Default methods cannot use instance state, only call other interface methods. They also cannot override equals, hashCode or toString.

interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }
class C implements A, B {
    @Override public String hello() { return A.super.hello() + B.super.hello(); }
}
What are static and private methods in interfaces, and why were they added? Intermediate

What the interviewer is testing: Java 8 and 9 API design knowledge.

A static method in an interface (Java 8) is a utility that belongs to the contract, for example Comparator.comparing(...), List.of(...) or Map.entry(...). It used to require a separate class like Collections. It is called on the interface name, Comparator.naturalOrder(), and is not inherited by implementing classes. A private method (Java 9) lets several default or static methods share a helper without making it part of the public API. Both are about keeping related code with the interface. They do not change the rule that interfaces have no instance state. A caution: do not turn interfaces into dumping grounds of logic. Default methods should be small and derivable from the abstract ones.

What is the difference between overloading and overriding? Basic

What the interviewer is testing: compile-time versus run-time polymorphism.

Overloading: several methods in the same class (or inherited) with the same name but different parameter lists. The compiler picks one using the declared types of the arguments. The return type and exceptions alone cannot distinguish overloads. Overriding: a subclass supplies its own body for an inherited instance method with the same signature. The JVM picks the version from the actual object type when the call runs. So overloading is "static" or early binding, and overriding is "dynamic" or late binding. Always add @Override, so the compiler checks you really are overriding and that a typo like equals(Foo) does not create a silent overload.

Likely follow-ups
  • Can you overload main? Yes, but only public static void main(String[]) is the entry point.
  • Can overloads differ only by return type? No, compile error.
What are the exact rules for overriding a method? Intermediate

What the interviewer is testing: precise rules, which are all consequences of substitutability.

The overriding method must have the same name and parameter types (after generics erasure). The return type must be the same or a subtype (covariant). The access must be the same or wider. It may throw no new or broader checked exceptions: only the same, narrower, or none (unchecked ones are free). It cannot override a final, static or private method (a private one is invisible to the child, so a same-named method there is a brand new method). An instance method cannot override a static one and the other way round, that is a compile error. All of this follows one idea: wherever the parent type was accepted, the child must work with no surprises, so it can promise more but never less.

Likely follow-ups
  • Can an override add synchronized? Yes, it is not part of the signature.
  • Can an override of a method throwing IOException throw FileNotFoundException? Yes, it is narrower. Not Exception.
What is a covariant return type, and where does the JDK use it? Intermediate

What the interviewer is testing: a Java 5 feature that removes casts.

When overriding, the child method may return a more specific type than the parent. The caller who has a child reference then gets the precise type with no cast. The classic case is clone(): Object.clone() returns Object, but your class can declare public Point clone(). Builders use it too: a Shape copy() in the parent and Circle copy() in the child. Under the hood, the compiler generates a hidden "bridge method" with the old return type that calls yours, so the JVM-level signatures still match. Arrays are covariant in a different and unsafe way (Object[] a = new String[1] compiles and fails at run time with ArrayStoreException), while generic collections are invariant on purpose.

class Animal { Animal self() { return this; } }
class Dog extends Animal { @Override Dog self() { return this; } }
Dog d = new Dog().self();     // no cast needed
Explain static (compile-time) dispatch versus dynamic (run-time) dispatch with an example. Senior

What the interviewer is testing: the key to predicting overload and override output.

For a call obj.m(arg) the compiler first uses the declared type of obj and of the arguments to pick which signature will be called (overload resolution). That choice is fixed in the bytecode. Then, at run time, the JVM looks at the actual class of obj and runs that class's override of the chosen signature (a virtual call through the class's method table, called a vtable). Arguments never take part in the second step: Java has single dispatch, on the receiver only. That is why the same variable can print different things depending on whether a method is overloaded or overridden.

class Animal { void eat(Animal a) { System.out.println("animal eats animal"); } }
class Dog extends Animal {
    @Override void eat(Animal a) { System.out.println("dog eats animal"); }
    void eat(Dog d)            { System.out.println("dog eats dog"); }   // overload, not override
}
Animal a = new Dog(); Animal b = new Dog();
a.eat(b);   // "dog eats animal": signature eat(Animal) chosen at compile time, Dog's version at run time
Likely follow-ups
  • Which design pattern works around single dispatch? Visitor, which does a second virtual call to simulate double dispatch. Sealed types with pattern matching switch (Java 21) replace many visitors.
Are fields polymorphic? What is field hiding, and what about static method hiding? Intermediate

What the interviewer is testing: only instance methods are virtual.

No. Fields and static methods are resolved at compile time from the declared type of the variable. If a child declares a field with the same name as a parent's, it hides it: the object now holds two separate fields. Reading ref.name gives the parent's field if ref is declared as the parent, and the child's if declared as the child, whatever the real object is. A static method with the same signature in the child likewise hides the parent's one. Only instance methods are overridden. It is very confusing, so do not hide fields: rename, or use a method. IDEs warn about it.

class P { String name = "parent"; static String who() { return "P"; } String me() { return name; } }
class C extends P { String name = "child";  static String who() { return "C"; } }
P ref = new C();
ref.name       // "parent"  (field: declared type)
ref.who()      // "P"       (static: declared type)
ref.me()       // "parent"  (P's method sees P's field)
((C) ref).name // "child"
How does the compiler choose among overloaded methods when boxing, widening and varargs are possible? Senior

What the interviewer is testing: overload resolution phases, a source of quiz questions and real bugs.

The compiler works in three phases and stops at the first that finds a match. Phase 1: only identity and widening conversions of primitives and references, no boxing and no varargs. Phase 2: allow boxing and unboxing as well. Phase 3: allow variable-arity (varargs) methods. Inside a phase, it picks the most specific applicable method; if none is strictly more specific, it is an ambiguity error. Hence m(long) beats m(Integer) when you pass an int (widening in phase 1 before boxing in phase 2), and a plain method beats a varargs one. With null as the argument, m(Object) and m(String) pick String (more specific), but m(String) and m(Integer) give a compile error. The practical advice: do not make overloads that differ only in a way that depends on these rules. Give them different names.

static void m(long x)    { System.out.println("long"); }
static void m(Integer x) { System.out.println("Integer"); }
static void m(int... x)  { System.out.println("varargs"); }
m(5);        // long
What is upcasting and downcasting? When do you get a ClassCastException? Basic

What the interviewer is testing: the difference between compile-time and run-time checks.

Upcasting treats a child as its parent type (Animal a = new Dog()). It is always safe and needs no cast syntax, but you can then call only the parent's methods. Downcasting goes the other way (Dog d = (Dog) a). The compiler allows it when the types are related, but the JVM checks the real object at run time, and throws ClassCastException if the object is not a Dog. Guard the cast with instanceof. Needing many downcasts is a design smell: it usually means the parent type is missing a method, or you should use polymorphism or a sealed type with pattern matching. Casting between unrelated classes, such as (String) integerObj, does not compile. Casting a generic collection element, for example after a raw type, is a common source of surprise CCEs far from the cause (heap pollution).

What is pattern matching for instanceof? Intermediate

What the interviewer is testing: modern Java (final in Java 16).

Instead of checking the type and then casting on a second line, you declare a binding variable in the test: if (obj instanceof String s). If the test is true, s is already a String and is usable. Its scope is flow-based: it is in scope where the compiler can prove the match, for example in the true branch, after &&, or after an early return in the negated form if (!(o instanceof String s)) return;. It works with && but not ||. It removes boilerplate and cast mistakes, and is the base of equals implementations in modern code. Java 21 extends the idea with record patterns (o instanceof Point(int x, int y)) and pattern matching in switch. Also note that null instanceof X is always false, so no null check is needed.

@Override public boolean equals(Object o) {
    return o instanceof Money m && cents == m.cents && currency.equals(m.currency);
}
Give a real-world example of polymorphism that makes code easier to extend. Intermediate

What the interviewer is testing: can you show the open-closed benefit instead of describing it.

Take a discount calculator. The bad version has a long if / else if or switch on a customer type, and every new type means editing and retesting that method. The polymorphic version has an interface DiscountPolicy with apply(Order), and one small class per policy: NoDiscount, FestivalDiscount, LoyaltyDiscount. The checkout code calls policy.apply(order) and never changes when a new policy appears. It is also easy to test each policy alone. With Java 17 and later you can make the interface sealed when the set is closed and you want the compiler to check that every case is handled, or use an enum with constant-specific behaviour. The trade-off: polymorphism makes adding a new type easy, but adding a new operation across all types harder, the opposite of a switch.

5. Nested types, enums, records and sealed classes

What are the kinds of nested classes in Java, and when do you use each? Basic

What the interviewer is testing: the four kinds and the one that captures the outer instance.

There are four. A static nested class is declared with static inside another class. It is just a class that is namespaced there and has no link to an outer object: use it for helpers, builders (Pizza.Builder) and nodes (Map.Entry). An inner (non-static) class is an instance member, and every instance holds a hidden reference to its outer object, so it can use the outer's fields: use it for something tied to one outer instance, such as an iterator over a collection. A local class is declared inside a method and can use effectively final locals. An anonymous class has no name and is declared and created in one expression, typically to implement an interface once. If a nested class does not need the outer instance, make it static: it avoids a hidden reference and possible memory leaks.

class Outer {
    private int x = 1;
    class Inner { int twice() { return x * 2; } }        // uses Outer.this.x
    static class Nested { }
}
Outer o = new Outer();
Outer.Inner in = o.new Inner();      // needs an outer instance
Outer.Nested n = new Outer.Nested();
How can an inner or anonymous class cause a memory leak? Senior

What the interviewer is testing: hidden references and their lifetime.

A non-static inner class, or an anonymous class created in an instance method, holds a hidden reference to the enclosing object. If that inner object is stored somewhere long-lived (a static map, a cache, a listener list, a thread pool task queue, a ThreadLocal), the whole outer object stays reachable and cannot be garbage collected, with everything it references, even when you thought you had finished with it. A typical case is a big request or session object that creates an anonymous Runnable or a listener, registers it in a global event bus, and never unregisters. The fix: use a static nested class (or a lambda that does not touch this) and pass in only the few values needed, hold listeners with weak references or unregister them, and look at heap dumps for "outer" fields named this$0. Lambdas capture this only if they use an instance member, so they are less prone to this.

What is the difference between an anonymous class and a lambda? Intermediate

What the interviewer is testing: more than "lambda is shorter".

A lambda is only for a functional interface: one with a single abstract method. An anonymous class can extend a normal class, implement any interface, have several methods and its own fields. In an anonymous class, this means the anonymous object itself; in a lambda, this means the enclosing object, because a lambda does not create a new scope. An anonymous class compiles to a real class file (Outer$1.class) and is loaded as a separate class. A lambda is compiled with invokedynamic and the JVM creates its implementation at first use, which is usually lighter. An anonymous class can shadow variables of the outer scope; a lambda cannot declare a local variable with the same name as an enclosing local. See Modern Java for more on lambdas.

What is an enum in Java, and how is it different from constants in C? Basic

What the interviewer is testing: that Java enums are full classes.

An enum (Java 5) is a special class with a fixed, closed set of instances, the constants. Each constant is a single object created once when the enum class is initialized, so == is the right comparison. Enums are type-safe (you cannot pass any other int), they print their name, and they can have fields, constructors (always private), methods, and implement interfaces. They cannot extend another class, since they already extend java.lang.Enum, and cannot be extended. Useful built-ins: values(), valueOf(String) (throws IllegalArgumentException for an unknown name), name(), ordinal(), and compareTo by declaration order. They work in switch, and in EnumMap and EnumSet, which are very fast because they use arrays and bit sets.

enum Status {
    NEW("N"), PAID("P"), SHIPPED("S");
    private final String code;
    Status(String code) { this.code = code; }
    String code() { return code; }
    static Status fromCode(String c) {
        for (Status s : values()) if (s.code.equals(c)) return s;
        throw new IllegalArgumentException("unknown " + c);
    }
}
Likely follow-ups
  • Should you persist ordinal()? No. Reordering or inserting a constant silently changes the meaning of stored data. Store the name or an explicit code.
How do you give each enum constant its own behaviour, and why use EnumMap? Intermediate

What the interviewer is testing: the strategy pattern with enums, avoiding switch statements.

Declare an abstract method in the enum and give each constant a body that implements it (a constant-specific class body). The compiler forces every constant to provide it, so adding a constant without behaviour is a compile error, unlike a forgotten case in a switch. You can also pass a lambda to the constructor. An EnumMap<K, V> stores values in an array indexed by ordinal, so it is faster and smaller than a HashMap and iterates in declaration order. EnumSet is a bit mask. Use them whenever keys are enum values. And because enum constants are objects, they are thread-safe singletons and safe to share.

enum Op implements IntBinaryOperator {
    ADD("+") { public int applyAsInt(int a, int b) { return a + b; } },
    MUL("*") { public int applyAsInt(int a, int b) { return a * b; } };
    final String symbol;
    Op(String s) { symbol = s; }
}
Map<Op, Integer> counts = new EnumMap<>(Op.class);
Why is an enum the best way to write a singleton? Senior

What the interviewer is testing: knowing how singletons are attacked: serialization, reflection, class loading.

A one-element enum gives you three guarantees that you must otherwise code by hand. It is thread-safe, because the JVM initializes the class once under a lock. It is serialization-safe: Java serializes an enum by name and, on read, returns the existing constant, so deserialization cannot create a second instance (a normal singleton needs readResolve). And it is reflection-safe: Constructor.newInstance throws for enum types, so nobody can call the private constructor to build another. Joshua Bloch recommends it in Effective Java. The limits: an enum cannot extend another class, it is eagerly created when the enum class initializes (still lazy by class loading, in practice on first use), and some teams find it odd to read. If you need lazy init with an inheritance requirement, use the holder idiom. In Spring or other DI frameworks, do not hand-write singletons at all: the container does it.

public enum Registry {
    INSTANCE;
    private final Map<String, String> data = new ConcurrentHashMap<>();
    public void put(String k, String v) { data.put(k, v); }
}
Registry.INSTANCE.put("a", "b");
What is a record, and what does the compiler generate for you? Intermediate

What the interviewer is testing: modern data classes (Java 16 final; previews in 14 and 15).

A record is a compact way to declare an immutable data carrier: record Point(int x, int y) {}. The compiler generates a private final field per component, a canonical constructor, accessor methods named like the component (p.x(), not getX()), and equals, hashCode and toString based on all components. The class is implicitly final and extends java.lang.Record, so it cannot extend another class, but it can implement interfaces, have static members, extra methods and extra constructors (which must delegate to the canonical one). A compact constructor has no parameter list and is used for validation and normalisation: it runs before the fields are assigned. Records are great for DTOs, map keys, value objects and results of multiple return values. Careful: they are only shallowly immutable. A record holding a List or an array still exposes it, so copy defensively.

record Range(int lo, int hi) {
    Range {                                  // compact constructor
        if (lo > hi) throw new IllegalArgumentException(lo + " > " + hi);
    }
    int length() { return hi - lo; }
}
record Team(String name, List<String> members) {
    Team { members = List.copyOf(members); } // defensive copy
}
Likely follow-ups
  • Can a record have mutable fields or instance fields beyond components? No extra instance fields. Components only.
  • Record versus Lombok @Value? Record is a language feature with no library, but it cannot add extra fields and cannot be extended.
  • Can JPA entities be records? Not as entities (they need a no-arg constructor and mutability), but they work well as projections and DTOs.
What are sealed classes and interfaces, and why were they added? Senior

What the interviewer is testing: modern modelling of closed hierarchies (Java 17 final; previews in 15 and 16).

A sealed type restricts which classes may extend or implement it, using permits. Each permitted subclass must be declared final, sealed (continuing the restriction), or non-sealed (reopening it). If the subclasses are in the same file, permits may be omitted. The point is a closed set of cases that the compiler knows. Before, you had to choose between an open class (anyone can extend it) and an enum (a fixed set of constants only, no per-case data). Sealed types are "algebraic sum types": a Shape is either a Circle, a Rect or a Tri, each with its own fields (often records). Together with pattern matching for switch (final in Java 21) the compiler checks that your switch covers every case, with no default, so adding a new subtype breaks the build where you forgot to handle it. That replaces the visitor pattern in many cases.

sealed interface Shape permits Circle, Rect {}
record Circle(double r) implements Shape {}
record Rect(double w, double h) implements Shape {}

double area(Shape s) {
    return switch (s) {                 // Java 21, exhaustive, no default
        case Circle c -> Math.PI * c.r() * c.r();
        case Rect(double w, double h) -> w * h;
    };
}
Likely follow-ups
  • Sealed versus enum? An enum has fixed instances of one shape. Sealed has fixed types, each with different data and many instances.
  • Do sealed classes work across packages? In a named module, the subclasses must be in the same module. In the unnamed module, the same package.

6. Immutability and the Object contracts

How do you build an immutable class in Java? Intermediate

What the interviewer is testing: the full checklist, especially defensive copies of mutable parts. Many candidates stop at "make fields final".

An immutable object cannot change after construction. The recipe: (1) declare the class final (or give it only private constructors), so no subclass can add mutability; (2) make all fields private final; (3) provide no setters or any method that changes state; (4) set everything in the constructor, and validate there, so no invalid object exists; (5) if a field is a mutable type (Date, array, List), make a defensive copy when it comes in and again when you hand it out, or return an unmodifiable view; (6) do not let this escape from the constructor. A record does steps 1 to 4 for you. The reward is a class that is thread-safe without locking, safe as a hash key, safe to cache and share, and easy to reason about. The cost is a new object for each change, which the JVM handles well for small objects. Use a builder or "wither" methods (withName(...)) for classes with many fields.

public final class Booking {
    private final String id;
    private final Date start;                 // Date is mutable
    private final List<String> guests;
    public Booking(String id, Date start, List<String> guests) {
        this.id = Objects.requireNonNull(id);
        this.start = new Date(start.getTime());      // copy in
        this.guests = List.copyOf(guests);           // copy in, Java 10+
    }
    public Date getStart() { return new Date(start.getTime()); }   // copy out
    public List<String> getGuests() { return guests; }            // already immutable
}
Likely follow-ups
  • Is a class with all final fields always immutable? No, if a field is a mutable object, or the class can be subclassed, or this escapes.
  • Is String truly immutable? Yes from the outside. Its cached hash is set lazily, but that is invisible and safe.
How do Collections.unmodifiableList, List.of and List.copyOf differ? Intermediate

What the interviewer is testing: view versus copy, a very common immutability bug.

Collections.unmodifiableList(list) returns a read-only view of the same list. You cannot change it through the view, but if someone still holds the original and changes it, the "unmodifiable" list changes too. List.of(...) (Java 9) creates a truly immutable list from the given elements, and rejects null elements with NPE. List.copyOf(coll) (Java 10) makes an immutable copy (and returns the same instance if the input is already an immutable list from List.of). Stream's toList() (Java 16) returns an unmodifiable list that allows nulls. Set.of and Map.of have the same rules, and Set.of and Map.of iteration order is deliberately unspecified and can vary between runs. Mutators on all of them throw UnsupportedOperationException. Immutable collections protect the list structure only. Elements that are themselves mutable can still be changed.

What is the contract of equals? Intermediate

What the interviewer is testing: the five properties, and what breaks when one is violated.

For non-null references: reflexive (x.equals(x) is true), symmetric (x.equals(y) if and only if y.equals(x)), transitive (if x equals y and y equals z, then x equals z), consistent (repeated calls give the same answer while nothing changed), and x.equals(null) is always false. Violations cause real bugs: if symmetry fails, list.contains(a) and list.contains(b) disagree depending on who calls whom. Consistency breaks if equality depends on something volatile, such as a timestamp or a remote lookup. Transitivity is the hard one with inheritance: you cannot add a value component to a class and keep both equals and substitution correct, which is why records are final and why people prefer composition. Always override hashCode together with equals.

What is the contract between equals and hashCode, and what happens in a HashMap if you break it? Basic

What the interviewer is testing: the most asked Java contract question. Link to how HashMap finds an entry.

Rule 1: if a.equals(b) is true, then a.hashCode() == b.hashCode() must be true. Rule 2: while the object is unchanged, hashCode returns the same value each time. The reverse is not required: different objects may share a hash (a collision), it only slows things down. A HashMap or HashSet finds a key in two steps: use the hash to choose a bucket, then use equals to find the key inside that bucket. If you override equals but not hashCode, two equal objects usually land in different buckets, so set.contains(new Key(1)) returns false although an equal key is in the set, and a set accepts "duplicates". Overriding only hashCode is safe for correctness but equal objects would still not match. Default Object.hashCode is identity based (not the memory address necessarily, but unique per object in practice).

Likely follow-ups
  • Is a constant hashCode legal? Yes, but all entries collide and lookups degrade to a scan (a tree for comparable keys since Java 8).
  • How should hashCode be written? Combine the same fields used in equals, with Objects.hash(a, b) or 31 * h + field.
Write a correct equals and hashCode. Should you use getClass() or instanceof? Intermediate

What the interviewer is testing: writing it from memory, including the type check trade-off.

The steps: same reference, then null, then type check, then compare the significant fields (primitives with ==, double via Double.compare, objects with Objects.equals). On the type check: getClass() != o.getClass() is strict, so a subclass never equals its parent, which keeps symmetry and transitivity. instanceof allows subclasses to be equal, which is correct only if the class is final or the equality is defined entirely by the parent type (as in List.equals, which any list type satisfies). Under Hibernate or proxies, getClass() fails against a generated subclass, which is a reason people use instanceof there. For a final class, instanceof is simple. Today the easiest correct answer is "use a record", or let the IDE generate it.

public final class Money {
    private final long cents; private final String currency;
    // constructor omitted
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money)) return false;       // final class: instanceof is fine
        Money m = (Money) o;
        return cents == m.cents && currency.equals(m.currency);
    }
    @Override public int hashCode() { return Objects.hash(cents, currency); }
}
Likely follow-ups
  • What about float and double fields? Use Double.compare and Double.hashCode, so that NaN and -0.0 behave consistently.
  • Should a JPA entity use its database id in equals? Carefully: the id is null before saving. Prefer a business key, or a constant hashCode with an id-based equals.
What should toString() do, and what are its traps? Basic

What the interviewer is testing: practical habits for debuggability and safety.

The default is ClassName@hexHash, which is useless in logs. Override it to show the state that helps debugging, for example Order{id=7, status=PAID}. Keep it cheap and side-effect free: it is called implicitly by string concatenation, logging and debuggers. Traps: (1) infinite recursion when two objects point to each other and both print the other (a parent with children, and each child prints the parent); (2) printing secrets such as passwords, tokens and card numbers into logs; (3) triggering lazy loading in an ORM entity, causing queries or exceptions in the logger; (4) printing a huge collection; (5) treating the output as an API and parsing it later. Records and Lombok generate one, but check what it includes.

What is the contract of compareTo, and what does "consistent with equals" mean? Intermediate

What the interviewer is testing: sorted collections use compareTo, not equals.

compareTo returns negative, zero or positive for less, equal, greater. It must be antisymmetric (sgn(a.compareTo(b)) == -sgn(b.compareTo(a))), transitive, and if a.compareTo(b) == 0 then both must compare the same way against any other object. It is "consistent with equals" if compareTo == 0 exactly when equals is true. This is strongly advised but not required. When it is not consistent, sorted collections behave strangely, because TreeSet and TreeMap use compareTo only. The textbook example is BigDecimal: 2.0 and 2.00 are equal by compareTo but not by equals, so a HashSet holds both and a TreeSet holds one. Never write return a - b for ints: it overflows when the numbers are far apart. Use Integer.compare(a, b). A broken comparator can even make Collections.sort throw "Comparison method violates its general contract!".

public int compareTo(Person o) {
    int c = lastName.compareTo(o.lastName);
    return c != 0 ? c : Integer.compare(age, o.age);
}
Comparable versus Comparator: when do you use each? Basic

What the interviewer is testing: natural ordering versus external ordering.

Comparable<T> is implemented by the class itself and defines its one natural order through compareTo. String, numbers and dates are comparable. Comparator<T> is a separate object that defines any order you like, so you can sort the same list by name today and by salary tomorrow, and you can sort classes you cannot modify. Use Comparable when there is one obvious order (like dates) and Comparator for everything else. Since Java 8 comparators are built from small parts, and handle nulls too.

list.sort(Comparator.comparing(Employee::dept)
                    .thenComparing(Employee::salary, Comparator.reverseOrder())
                    .thenComparing(Employee::name, Comparator.nullsFirst(String::compareTo)));
Likely follow-ups
  • What does TreeSet do if the element is not Comparable and no Comparator was given? Throws ClassCastException on the first add.
What methods does java.lang.Object have, and which ones should you care about? Basic

What the interviewer is testing: knowledge of what every object inherits.

Eleven methods exist, listed in these groups. Identity and printing: equals, hashCode, toString, getClass (final; returns the runtime class). Copying: clone (protected, needs Cloneable). Cleanup: finalize, which is deprecated since Java 9 and deprecated for removal since Java 18 (JEP 421), because it is unpredictable, slow and a security risk. Use try-with-resources with AutoCloseable, or java.lang.ref.Cleaner as a safety net. Thread coordination: wait (three overloads), notify, notifyAll, which must be called while holding the object's monitor (inside synchronized), otherwise IllegalMonitorStateException. The first four are the ones you override all the time. See the concurrency page for wait and notify.

How does clone() work, and why is it considered broken? Senior

What the interviewer is testing: shallow versus deep copy, and awareness of better alternatives.

Object.clone() is protected and makes a field-by-field (shallow) copy. It throws CloneNotSupportedException unless the class implements the marker interface Cloneable, which itself has no methods, an odd design. For your class to be cloneable you implement Cloneable, override clone() as public, call super.clone() and cast. A shallow copy copies primitives and the references, so the clone and the original share the same inner objects (lists, arrays, other objects). If those are mutable, changing one changes the other, so you must clone them too (a deep copy). The problems: the constructor is not called (final fields cannot be re-assigned), there is a checked exception, subclasses must cooperate, and the contract is vague. Arrays have a good clone(), but it is also shallow for object arrays. Prefer a copy constructor or a static copy factory, which are explicit and type-safe, or make the class immutable so no copy is needed.

public Basket(Basket other) {              // copy constructor
    this.owner = other.owner;               // immutable String: share
    this.items = new ArrayList<>(other.items); // own list; items must be immutable too
}
Likely follow-ups
  • How do you deep-copy a complex graph? Hand-written copy methods, a serialization round trip (slow and fragile), or a mapping library. Better still, avoid sharing mutable state.
What is a marker interface? Name examples and compare with annotations. Intermediate

What the interviewer is testing: understanding of "tagging" types.

A marker interface has no methods; implementing it tags a class with a property that the runtime or a library checks with instanceof. Examples: Serializable (may be written by Java serialization), Cloneable (Object.clone is allowed), RandomAccess (get(i) is fast, so algorithms may pick an indexed loop). The advantage over an annotation: a marker is a type, so a method can demand it in its signature (void save(Serializable s)) and the compiler checks it. Annotations are more flexible: they can carry values, apply to methods and fields and parameters, and be read by tools at compile time or run time. Rule of thumb: use a marker interface when you want a type to use in parameters, otherwise use an annotation. Modern frameworks use annotations almost everywhere (@Entity, @Service).

How does Java serialization work, and why do many teams avoid it? Senior

What the interviewer is testing: know the mechanism, serialVersionUID, and the security stance.

A class that implements Serializable can be written with ObjectOutputStream: the JVM walks the object graph and writes class descriptors and non-transient, non-static field values, and reading it back rebuilds objects without calling the constructor of the serializable classes (it does call the no-arg constructor of the first non-serializable superclass). The serialVersionUID is a version stamp: if the stream's value differs from the class's, reading fails with InvalidClassException. If you do not declare it, Java computes one from the class shape, so a harmless change (new method) breaks old data. Declare it explicitly. The reasons teams avoid Java serialization: it is slow and verbose; it breaks encapsulation (private fields become a public format); it bypasses constructors and so invariants and singletons (readResolve is needed); and deserializing untrusted data is a well-known remote code execution risk (gadget chains), so never deserialize data from outside your trust boundary, and use ObjectInputFilter (Java 9) if you must. Use JSON, Protobuf or Avro with explicit schemas instead. Records are serialized by their components and always go through the canonical constructor, which is safer.

Likely follow-ups
  • Does a serializable class need serializable fields? Yes, otherwise NotSerializableException at run time, unless the field is transient.
  • What if the parent is not Serializable? Its fields are not saved, and its no-arg constructor must exist and run on read.

7. Annotations, reflection, packages, modules and varargs

What are annotations, and how do retention and target work? Intermediate

What the interviewer is testing: annotations are metadata, and nothing happens unless something reads them.

An annotation is metadata attached to code (class, method, field, parameter and more). It does not change behaviour by itself: something must read it, either the compiler or an annotation processor at build time (@Override, Lombok, MapStruct), or a framework at run time through reflection (Spring @Service, JPA @Entity, JUnit @Test). Two meta-annotations control it. @Retention: SOURCE (gone after compile), CLASS (kept in the class file but not readable at run time, the default), or RUNTIME (readable by reflection). @Target says where it may be placed (TYPE, METHOD, FIELD, PARAMETER and so on). Elements are declared like methods and may have defaults. Built-ins to know: @Override, @Deprecated(since, forRemoval), @SuppressWarnings, @FunctionalInterface, @SafeVarargs.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Timed { String name() default ""; }

for (Method m : target.getClass().getDeclaredMethods()) {
    if (m.isAnnotationPresent(Timed.class)) { /* wrap or record timing */ }
}
Likely follow-ups
  • Why does my custom annotation read as absent at run time? Default retention is CLASS, so add @Retention(RUNTIME).
  • Do annotations on an interface method get inherited by the implementation? Not for methods. Only class-level annotations marked @Inherited, and only from superclasses.
What is reflection, what is it used for, and what does it cost? Intermediate

What the interviewer is testing: how frameworks work, plus risks.

Reflection lets code inspect and use classes at run time without knowing them at compile time: get a Class object (Foo.class, obj.getClass(), Class.forName("x.Foo")), list fields, methods and annotations, create instances and call methods. It powers dependency injection, ORMs, serializers like Jackson, test frameworks and proxies. The costs: it is slower than a direct call (though the JIT and method handles reduce it, and results should be cached), it loses compile-time checking (rename a method and it fails at run time), it can break encapsulation with setAccessible(true) on private members, and it makes code harder to read and to optimise, for example for ahead-of-time compilation such as GraalVM native images, which need reflection configuration. Since Java 9 modules, and strong encapsulation of JDK internals by default from Java 16 and 17, reflecting into java.base private members fails with InaccessibleObjectException unless the module is opened with --add-opens.

Class<?> c = Class.forName("com.acme.Greeter");
Object o = c.getDeclaredConstructor().newInstance();
Method m = c.getMethod("hello", String.class);
Object result = m.invoke(o, "Asha");
Likely follow-ups
  • How does a dynamic proxy relate? java.lang.reflect.Proxy creates an object implementing interfaces at run time and routes calls to an InvocationHandler, the basis of many AOP features. Class-based proxies use CGLIB or ByteBuddy and need a non-final class.
What are packages for, and what are good practices around them? Basic

What the interviewer is testing: basic organisation and access.

A package is a namespace that groups related classes and sets the boundary of package-private access. The name is conventionally the reversed domain (com.acme.orders), and the folder structure must match. It avoids name clashes (java.util.Date and java.sql.Date). import only shortens names, it does not load anything. A static import imports static members. Practices: group by feature or domain (orders, billing), not only by layer, keep the public surface of a package small and use package-private for the rest, avoid cyclic dependencies between packages, and do not use wildcard imports so that clashes stay visible. Classes in the default (unnamed) package cannot be imported from other packages, so always declare a package in real code.

What is the Java Platform Module System (Java 9), and when do you care? Intermediate

What the interviewer is testing: a basic overview; most application developers touch it only through errors and jlink.

A module is a named group of packages with a descriptor module-info.java that says what it requires and which packages it exports. It adds a level above packages: a public class in a non-exported package is not accessible from other modules, which is "strong encapsulation". The JDK itself was split into modules (java.base, java.sql, java.xml, and so on), which allows jlink to build a small custom runtime. Other directives: opens (allow reflection at run time, needed for frameworks), requires transitive, provides ... with and uses (a service loader). Jars on the old classpath form the unnamed module, and a jar put on the module path without a descriptor is an automatic module. In practice, most business applications still run on the classpath. You meet modules when upgrading to Java 17 and a library fails with InaccessibleObjectException, and the fix is --add-opens, or a newer library version. Spring Boot fat jars normally do not use module-info.

module com.acme.orders {
    requires java.sql;
    requires transitive com.acme.core;
    exports com.acme.orders.api;
    opens com.acme.orders.model to com.fasterxml.jackson.databind;
}
How do varargs work, and what are the pitfalls? Intermediate

What the interviewer is testing: hidden array creation and overload interaction.

A parameter written String... names (Java 5) is really an array String[]. The compiler wraps the extra arguments into a new array at each call, so it allocates. It must be the last parameter, and you can have only one. Callers may pass zero arguments (an empty array, not null), several values, or an existing array. Pitfalls: (1) a call with null is ambiguous or passes a null array; (2) overload resolution tries the varargs method last (phase 3), so m(int) is preferred over m(int...); (3) passing an int[] to Object... passes it as one object, not as many (primitive arrays are not Object[]), while Arrays.asList(intArray) gives a list with one element; (4) a generic varargs T... creates a generic array and a "heap pollution" warning, silenced only when you are sure by @SafeVarargs (on static, final or private methods; Java 9 allows it on private instance methods too); (5) public APIs with varargs and frequent calls cause garbage, so provide overloads for small counts, as List.of does up to ten elements.

static int sum(int... xs) { int t = 0; for (int x : xs) t += x; return t; }
sum();            // 0, xs is an empty array
sum(1, 2, 3);     // 6
sum(new int[]{4, 5});  // 9

8. Tricky output-prediction questions

For each one, say your prediction aloud and the rule behind it, then open the answer. Interviewers care more about the rule than the output.

What does this print? String a = "hello"; String b = "hel" + "lo"; String c = "hel"; String d = c + "lo"; print(a == b, a == d, a == d.intern()); Intermediate

What the interviewer is testing: compile-time constants versus run-time concatenation.

It prints true false true. "hel" + "lo" is a constant expression, so the compiler joins it into the literal "hello", which is the pooled object, so a == b. But c is an ordinary variable, so c + "lo" is computed at run time and creates a new object that is not in the pool: a == d is false. d.intern() returns the pooled "hello", so the last comparison is true. If c were declared final String c = "hel"; it would be a constant variable, and c + "lo" would be folded too, making a == d true. The lesson: always use equals for strings.

What does this print? Integer a = 100, b = 100, c = 1000, d = 1000; print(a == b, c == d, c.equals(d)); Long l = 127L; print(l.equals(127), l.equals(127L)); Intermediate

What the interviewer is testing: the cache, plus the fact that equals is type-sensitive.

It prints true false true and then false true. Values 100 are in the cache, 1000 are not, and equals compares values. For the second line: 127 is an int, so it is boxed to Integer and Long.equals(Integer) is false, because Long.equals checks that the other object is also a Long. 127L boxes to Long, so it is true. This also explains why map.get(5) on a Map<Long, X> returns null: the key 5 is boxed as Integer, which is never equal to a Long key. It compiles because get takes Object.

What do these print? print('a' + 'b'); print("" + 'a' + 'b'); print('a' + 1); print((char)('a' + 1)); char c = 'a'; c += 1; print(c); Intermediate

What the interviewer is testing: numeric promotion of char, and string concatenation order.

Output: 195, ab, 98, b, b. Arithmetic on char promotes to int, so 'a' + 'b' is 97 + 98 = 195. Once one side of + is a String, the rest is concatenation, evaluated left to right, so "" + 'a' + 'b' is "ab", but 'a' + 'b' + "" would be "195". 'a' + 1 is the int 98. A cast brings it back to the char 'b'. The compound assignment c += 1 contains an implicit cast back to char, so it compiles and gives 'b', whereas c = c + 1 would not compile.

What do these methods return? int f() { try { return 1; } finally { return 2; } } and int g() { int x = 1; try { return x; } finally { x = 5; } } Intermediate

What the interviewer is testing: how finally interacts with return.

f() returns 2. The finally block always runs, and a return inside it replaces the earlier return (and also swallows any exception thrown in the try). That is why return in finally is considered a bug. g() returns 1. At the return x the value is copied aside, then finally runs and changes the local x to 5, but the saved value 1 is what is returned. If x were a mutable object, such as a StringBuilder, the finally block's changes to the object would be visible, since the saved thing is the reference. The only ways a finally block does not run are System.exit, a JVM crash, or an endless loop or thread kill. More on this in Exceptions and I/O.

What is the output? class P { static { print("Ps"); } { print("Pi"); } P() { print("Pc"); } } class C extends P { static { print("Cs"); } { print("Ci"); } C() { print("Cc"); } } new C(); new C(); Intermediate

What the interviewer is testing: the initialization order, applied to a concrete case.

First object: Ps Cs Pi Pc Ci Cc. Second object: Pi Pc Ci Cc. Static blocks run once, parent then child, when the class is first initialized, which is at the first new C(). For each instance, the parent's instance initializer and constructor run completely, then the child's. A variation to prepare for: if the parent constructor calls an overridden method, the child's version runs before the child's fields are set. See the init-order question above.

What prints? void m(Object o) { print("Object"); } void m(String s) { print("String"); } void m(Integer i) { print("Integer"); } then m(null), m("x"), m((Object) "x"). Senior

What the interviewer is testing: overload resolution with null and casts.

m(null) is a compile error: both String and Integer are applicable and neither is more specific than the other, so the call is ambiguous. (With only the Object and String versions, it would print String, as the most specific.) m("x") prints String. m((Object) "x") prints Object, even though the real object is a String, because overloads use the declared type at compile time. The real-life version of this bug is a logging or helper method with overloads and a caller who passes a variable typed as Object.

What is i after int i = 5; i = i++ + ++i;, and after int j = 5; j = j++;? Intermediate

What the interviewer is testing: evaluation order is defined left to right in Java (unlike C).

For the first: i++ yields 5 and sets i to 6; then ++i sets i to 7 and yields 7; the sum 5 + 7 = 12 is assigned to i, so i is 12. For the second: j++ yields the old value 5, then j becomes 6, then the assignment writes the old value 5 back, so j stays 5. Java defines the order of evaluation of operands from left to right, so the answer is the same on every JVM. In real code, never write this: one increment per statement.

What does this print? Object o = true ? 1 : 2.0; print(o); and what happens with Integer n = null; int x = flag ? n : 0;? Senior

What the interviewer is testing: the typing rules of the conditional operator.

The first prints 1.0, not 1. When both branches are numeric types, the conditional expression undergoes binary numeric promotion, so the int 1 is widened to double even though the condition chose it. The second throws NullPointerException when flag is true: the branches are Integer and int, so the expression has type int and n is unboxed, and unboxing null fails. The condition does not need to be evaluated at that branch for the type to be decided. To avoid both, keep the branches the same type, or box deliberately (flag ? n : Integer.valueOf(0)), and handle null explicitly.

What does this print? class A { String n = "A"; String get() { return n; } } class B extends A { String n = "B"; String get() { return n; } } A x = new B(); print(x.n + x.get() + ((B) x).n); Intermediate

What the interviewer is testing: fields are not virtual, methods are.

It prints ABB. x.n uses the declared type A, so it reads A's field: "A". x.get() is virtual, so B's method runs, and inside B the name n means B's own field: "B". After the cast the declared type is B, so n is "B". If B did not override get(), the call would run A's method and return A's field "A".

What is the list after this? List<Integer> list = new ArrayList<>(List.of(10, 20, 30, 1)); list.remove(1); list.remove(Integer.valueOf(1)); Intermediate

What the interviewer is testing: overload resolution phases with boxing, the cause of a real bug.

The result is [10, 30]. List has remove(int index) and remove(Object o). The call remove(1) with an int matches remove(int) in phase 1 (no boxing needed), so it removes the element at index 1, which is 20. Then remove(Integer.valueOf(1)) matches remove(Object) and removes the value 1. So the remaining list is 10 and 30. A related trap: Arrays.asList(1, 2, 3).remove(0) throws UnsupportedOperationException, because that list is fixed-size, backed by the array.

Does this throw? class T { static void hi() { print("hi"); } } T t = null; t.hi(); Intermediate

What the interviewer is testing: static calls bind to the declared type, not the object.

It prints hi and does not throw. A static method is resolved by the compile-time type of the expression, T, and the reference value is never used (the expression is evaluated, then discarded). So t.hi() is exactly T.hi(). It is legal but misleading, and IDEs warn "static member accessed via instance reference". Compare with an instance method call on a null reference, which throws NPE.

What do long a = 1 << 40;, int b = Integer.MAX_VALUE + 1; and long c = 24 * 60 * 60 * 1000 * 1000; give? Senior

What the interviewer is testing: int arithmetic is done in int even when the target is long.

The first gives 256, not about a trillion: 1 << 40 is an int shift, and for int the shift distance is taken modulo 32, so it is 1 << 8. Write 1L << 40. The second gives -2147483648, the overflow wrap. The third, microseconds per day, is the famous "Java Puzzlers" case. All operands are int, so the product overflows to 500654080 before it is widened to long. The correct form is 24L * 60 * 60 * 1000 * 1000. The rule: the target type does not influence how the right side is computed. Make one operand long first.

9. Coding-style questions

Write a thread-safe singleton. What are the options and which do you choose? Intermediate

What the interviewer is testing: several correct designs, and the broken ones.

Options: (1) eager static field private static final Foo INSTANCE = new Foo();, simple and thread-safe, but created even if never used. (2) Holder idiom, lazy and thread-safe through class initialization (shown earlier). (3) Enum singleton, which also resists serialization and reflection attacks. (4) Double-checked locking: correct only when the field is volatile; without it another thread may see a half-built object. It is more code and gives no benefit over the holder. (5) A synchronized getInstance(), correct but takes a lock on every call. In a Spring application, you write none of these: the container creates one bean per context, and that is injectable and testable. I also remind interviewers that a hand-written singleton is global state and hurts tests, so pass dependencies in instead.

public final class Cache {
    private static volatile Cache instance;
    private Cache() {}
    public static Cache get() {
        Cache c = instance;
        if (c == null) {
            synchronized (Cache.class) {
                c = instance;
                if (c == null) instance = c = new Cache();
            }
        }
        return c;
    }
}
Write a builder for a class with many optional fields. Why use one? Intermediate

What the interviewer is testing: the telescoping-constructor problem and immutable object creation.

When a class has many parameters, especially optional ones, constructors become unreadable (new Pizza(12, true, false, true, null)) and mistakes with same-typed arguments are easy. A builder gives named steps, optional values with defaults, validation in one place in build(), and the final object stays immutable. The builder is usually a static nested class with a fluent API (each setter returns this). Records with many components can use the same trick, and for two or three parameters plain constructors or a record are enough. Not every class deserves a builder. Lombok's @Builder generates this code.

public final class Pizza {
    private final int size; private final boolean cheese; private final List<String> toppings;
    private Pizza(Builder b) { size = b.size; cheese = b.cheese; toppings = List.copyOf(b.toppings); }
    public static Builder builder(int size) { return new Builder(size); }
    public static final class Builder {
        private final int size; private boolean cheese = true; private final List<String> toppings = new ArrayList<>();
        private Builder(int size) { this.size = size; }
        public Builder cheese(boolean c) { cheese = c; return this; }
        public Builder topping(String t) { toppings.add(t); return this; }
        public Pizza build() {
            if (size <= 0) throw new IllegalStateException("size");
            return new Pizza(this);
        }
    }
}
Pizza p = Pizza.builder(12).cheese(false).topping("olives").build();
Code review: what is wrong with this class? Senior

What the interviewer is testing: reading code like a reviewer: a checklist of the topics on this page.

public class Employee implements Comparable<Employee> {
    public String name;
    public List<String> skills = new ArrayList<>();
    public double salary;
    private Date joined;

    public Employee(String name, Date joined) { this.name = name; this.joined = joined; }
    public Date getJoined() { return joined; }
    public boolean equals(Employee e) { return name == e.name; }
    public int compareTo(Employee o) { return (int) (salary - o.salary); }
}

My list, from most serious: (1) equals(Employee) is an overload, not an override of equals(Object), so collections ignore it. Add @Override and the compiler would have caught it. (2) == on strings: compare with Objects.equals. (3) No hashCode, so hash collections break. (4) Public mutable fields: encapsulation is gone, and skills can be changed or replaced from anywhere. (5) Date is mutable and is stored and returned without a copy (use LocalDate, or copy). (6) compareTo casts a double difference to int, which truncates (0.5 becomes 0, treated as equal) and can overflow: use Double.compare. It is also inconsistent with equals. (7) Money as double. (8) The class is not final and has no null checks or validation. (9) No toString. A good rewrite is a record with a compact constructor for validation, or an immutable class with a builder.

Sort a list of employees by department, then by salary descending, then by name. How do you write it, and what can go wrong? Intermediate

What the interviewer is testing: fluent comparator composition, and the primitive and null traps.

Chain comparators. Use the primitive-specialised helpers to avoid boxing, reversed() only at the right place, and null-safe wrappers when a field can be null. The classic mistake is putting .reversed() at the end of a chain, which reverses the whole comparator, not just the last step.

Comparator<Employee> cmp = Comparator
    .comparing(Employee::dept)
    .thenComparing(Comparator.comparingDouble(Employee::salary).reversed())
    .thenComparing(Employee::name);
employees.sort(cmp);        // stable sort: equal items keep their order

Other things to say: List.sort and Collections.sort are stable (TimSort for objects); comparators must be consistent, or you may get "Comparison method violates its general contract"; and the lambda form (a, b) -> a.salary - b.salary is a bug for doubles and for large ints.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

Users with an id above 127 are "not found" in production, but tests pass. What is going on? Intermediate

What the interviewer is testing: the Integer cache bug in the wild.

Situation: a permission check does if (user.getId() == resource.getOwnerId()), and both fields are Integer or Long. In tests the ids are 1, 2, 3, so the cached objects make == true. In production the ids are large, each is a different object, and the check silently fails.

Check first: find where wrapper types are compared with == or !=. Reproduce with an id of 1000 in a unit test. Look at the field types: why are ids wrappers at all (probably because the DB column or JSON allows null)?

Fix: use Objects.equals(a, b), or unbox to primitives when null is impossible. If ids can never be null, change the field type to long.

if (Objects.equals(user.getId(), resource.getOwnerId())) { ... }

Prevent: a static analysis rule (Error Prone ReferenceEquality, SpotBugs RC_REF_COMPARISON, Sonar S4973), a unit test that uses ids above 127 on purpose, and a rule to prefer primitives for non-null values.

Likely follow-ups
  • Why did the same code work for a year? Because ids stayed small until a table crossed 127 rows. Bugs that depend on data size are the most dangerous.
A login check works for hard-coded test users but fails for users from the database. What do you look at? Basic

What the interviewer is testing: String identity versus equality.

Situation: code says if (role == "ADMIN"). A test passes the literal "ADMIN", which is pooled, so the same object matches. The role from the database, a JSON parser or a request is a freshly created String, so == is false.

Check first: grep for == " and != ". Print the strings with their System.identityHashCode if you need to convince someone.

Fix: "ADMIN".equals(role) (literal first, so it is null-safe). Even better, model roles as an enum, then == is correct and typos are compile errors.

Prevent: lint rules, code review, and an enum for fixed vocabularies. Do not "fix" it with intern() sprinkled around.

A HashMap entry exists (you can see it when you print the map), but get(key) returns null. Why? Senior

What the interviewer is testing: the danger of mutable keys, tied to hash bucket placement.

Situation: a Map<Account, Report> where Account.hashCode uses the mutable email and status fields. The code puts the key, then later updates account.setStatus(...). The hash changes, but the entry stays in the old bucket. A lookup now goes to the new bucket and finds nothing. Iteration still shows the entry, since it just walks all buckets. The same happens in a HashSet: contains says false and remove fails, so the entry can never be removed (a memory leak).

Check first: is the key class mutable, and does its hashCode use mutable fields? Is anyone changing the key after it was inserted? Check with a debugger: compare the key's current hash with the bucket the entry sits in.

Fix: use immutable keys (String, Long, enum, record, or an id-only wrapper). If you must mutate, remove the entry first and put it again afterwards. Do not base hashCode on fields that change.

record AccountId(long value) {}      // good key
Map<AccountId, Report> reports = new HashMap<>();

Prevent: a team rule that map keys and set elements must be immutable, and unit tests that mutate a key after insertion.

A Set<Order> contains the same order twice, although equals says they are equal. How do you debug it? Intermediate

What the interviewer is testing: systematic debugging of equals and hashCode.

Situation: deduplication with a HashSet fails. Order has an equals that compares orderId, but no hashCode. Two equal orders get identity hashes, usually land in different buckets, and the set never calls equals on them.

Check first: write a three-line test: a.equals(b), a.hashCode() == b.hashCode(), set.contains(b). If the first is true and the second false, that is it. If both are true but the set still has duplicates, check the signature: it may be equals(Order o) (an overload) rather than equals(Object), in which case the set never calls it. Also check that hashCode uses the same fields as equals, and that none of those fields are mutated.

Fix: implement both from the same business fields, with @Override, or make Order a record.

Prevent: use EqualsVerifier in tests (it checks all the contract rules), enable the compiler and linter warnings for "equals without hashCode", and use @Override everywhere.

A NullPointerException in a long chain order.getCustomer().getAddress().getCity().toUpperCase(). How do you find it and fix it properly? How is Optional misused here? Intermediate

What the interviewer is testing: practical NPE handling and Optional taste.

Situation: production log shows an NPE on that line, but which part is null? Since Java 14 (on by default from Java 15) the JVM adds helpful NPE messages, such as Cannot invoke "Address.getCity()" because the return value of "Customer.getAddress()" is null. On older versions, split the chain across lines or use a debugger.

Check first: which link is null, and is null a legal state (guest customer with no address) or a bug (missing validation upstream)? Decide that before writing any check.

Fix options: if null is a legal state, return Optional from the accessors, or handle it once at the boundary. If it is illegal, fail early with Objects.requireNonNull(x, "customer") in the constructor or at the API entrance, so the stack trace points at the real cause. A null-safe chain with Optional is fine for a local expression:

String city = Optional.ofNullable(order.getCustomer())
        .map(Customer::getAddress)
        .map(Address::getCity)
        .map(String::toUpperCase)
        .orElse("UNKNOWN");

Optional misuse to avoid: as a field or a method parameter (it is meant for return values; it is not serializable and doubles the objects); opt.get() without isPresent (just a new NPE called NoSuchElementException); if (opt.isPresent()) return opt.get(); else return x; instead of orElse; orElse(expensiveCall()), which always runs the call, where orElseGet(() -> ...) runs it only when empty; an Optional that is itself null; and wrapping collections (return an empty list instead).

Prevent: never return null for collections, annotate with @Nullable/@NonNull and use a checker, and keep the "Law of Demeter" in mind: long chains show that the caller knows too much.

Under load, reports show mixed-up data between users, and sometimes weird date errors. You find a static field. What happened? Senior

What the interviewer is testing: shared mutable static state in a multi-threaded server.

Situation: a servlet or service has private static SimpleDateFormat fmt or private static Map<String, Object> ctx or a static "current user" field. One instance serves all request threads. SimpleDateFormat keeps internal parsing state, so concurrent use gives wrong or crashing results (NumberFormatException, wrong dates). A static "current user" simply holds whoever wrote last, so one user sees another's data (a security incident).

Check first: search for non-final statics, and for static fields of mutable types (collections, formatters, Calendar, Random is fine, StringBuilder not). Reproduce with a test that runs the code from many threads.

Fix: remove the shared state: pass values through method parameters, or use per-request objects. For formatters use the immutable thread-safe DateTimeFormatter (Java 8). If you need per-thread context, use a ThreadLocal and clear it in a finally, or a framework request scope. Shared caches should be ConcurrentHashMap or a cache library.

Prevent: make statics final and immutable by rule. In multi-tenant systems, a static map keyed by anything but tenant is a red flag in review. See Java concurrency.

After a deployment, reading cached or queued objects fails with InvalidClassException. What happened and how do you prevent it? Senior

What the interviewer is testing: serialization versioning in rolling deployments.

Situation: a session store, a Redis cache, or a message queue holds Java-serialized objects. A new release adds a field or a method to the class. The class had no explicit serialVersionUID, so Java computed a new one from the class shape. New nodes cannot read old bytes (local class incompatible: stream classdesc serialVersionUID = ...), and during a rolling deploy old nodes cannot read new bytes either.

Check first: the exception text shows both ids. Check whether the class declares one, and what changed. Decide whether the data can simply be flushed (a cache) or must be kept (a queue).

Fix now: for a cache, flush it, or add a version prefix to the cache key so the new release ignores old entries. For persistent data, declare the old computed serialVersionUID explicitly (you can get it with serialver from the old jar) so compatible changes keep reading.

Prevent: always declare private static final long serialVersionUID, only make compatible changes (adding fields is compatible, removing or retyping is not), and best of all stop using Java serialization for stored or transported data. Use JSON or Protobuf with schema evolution rules, and keep a version in the key or envelope. Also never deserialize untrusted bytes.

A subclass method was meant to replace parent behaviour, but the parent's version still runs. Name the usual causes. Intermediate

What the interviewer is testing: the ways that "override" silently is not one.

Situation: you wrote the child method, it compiles, and nothing changes. Typical causes: (1) a different parameter type, so it is an overload: equals(Employee) instead of equals(Object), or compareTo(Object) versus compareTo(T); (2) a small typo in the name or in the case (tostring, hashcode); (3) the method is static or private in the parent, so it is hidden, not overridden; (4) the parent method is package-private and the child is in a different package, so the child does not see it and defines a new method; (5) a generic erasure mismatch, as List<String> versus List<Integer> parameters; (6) you overrode in a class that the framework does not use (a proxy subclass cannot override final methods, so a Spring @Transactional on a final or private method does nothing).

Check first: add @Override. If the compiler complains "method does not override", you found it. Use the IDE's gutter icons.

Prevent: a team rule that every overriding method has @Override, enforced by checkstyle or the compiler flag -Xlint plus an error-prone check.

Heap grows steadily. The heap dump shows many request objects retained through fields named this$0. What is it? Senior

What the interviewer is testing: inner classes and the hidden outer reference, found through heap analysis.

Situation: a service registers an anonymous Listener or Runnable in a long-lived structure: a static list, a scheduler, an event bus. Each anonymous instance has this$0, a hidden field pointing to the enclosing object, here a request handler holding big buffers. The listener is never removed, so every handler stays reachable.

Check first: take a heap dump (jcmd PID GC.heap_dump), open it in Eclipse MAT, find the biggest retained set, and read the "path to GC roots". A path through this$0 of an anonymous class gives the answer.

Fix: unregister listeners when done (try-with-resources or finally), make the class a static nested class or a lambda that captures only what it needs, or store weak references where that fits. Check that no ThreadLocal or static cache holds the outer object.

Prevent: the rule "inner classes are static unless they truly need the outer instance", register and unregister in pairs, and a heap-growth alert so that you see it in days, not months.

An export that builds a CSV in memory takes 40 seconds for 200,000 rows and creates huge garbage. What is the fix? Intermediate

What the interviewer is testing: spotting the quadratic string loop, then going one step further.

Situation: the code does String out = ""; for (Row r : rows) out += r.toCsv() + "\n";. Every += copies the entire string so far, so the total copying is quadratic. With 200,000 rows the result is tens of megabytes and the copying runs into terabytes of memory traffic, and the GC works hard on all those dead strings.

Check first: a profiler or a few thread dumps shows time in String.concat, StringLatin1 or array copying, and the GC log shows a high allocation rate.

Fix: use one StringBuilder (with an estimated capacity). Better still, do not build the whole file in memory: stream rows to the output (a BufferedWriter or the HTTP response) so memory stays constant. Remember to escape CSV values (commas, quotes, newlines) with a library.

try (BufferedWriter w = Files.newBufferedWriter(path)) {
    for (Row r : rows) { w.write(r.toCsv()); w.newLine(); }
}

Prevent: code review rule for string concatenation inside loops, and load tests with production-sized data.

A subclass throws NPE during construction in a field you initialised on the line above. How? Senior

What the interviewer is testing: init order and virtual calls from constructors, found in a real framework base class.

Situation: a base class constructor calls an abstract or overridable method init() (for example, to register handlers). The subclass overrides it and uses its own field private final List<String> names = new ArrayList<>();. The base constructor runs first, the override runs, and names is still null because the subclass field initializers have not run yet.

Check first: read the stack trace: the override is called from the base class constructor frame. This is visible in the first lines of the trace.

Fix: do not call overridable methods in constructors. Options: pass the data to the base constructor, make the base method final or private, move the setup to an explicit start() or @PostConstruct method that the framework calls after construction, or use a static factory method that builds then initializes.

Prevent: an IDE or static-analysis rule ("overridable method call in constructor"), and documenting that the extension hooks are called only after construction.

A "read-only" configuration object changes at run time and another module's behaviour changes with it. Find the leak. Intermediate

What the interviewer is testing: encapsulation and defensive copying in real code.

Situation: Settings has a private final List<String> allowedHosts and a getter that returns it directly. One caller does settings.getAllowedHosts().add("test.local") for a test and forgets it. The constructor also stored the list that the caller passed in, and the caller keeps changing its own list. The "final" field gave no protection, because the list object was shared both ways.

Check first: find all writers: search for the getter's usages with .add, .remove or .clear. Use a watchpoint on the list in a debugger to see who changes it.

Fix: copy in the constructor with List.copyOf, and return that immutable list (or a view) from the getter. For Date and arrays, copy in and out. Better, make the whole class a record, or use immutable types such as LocalDate. Then a change attempt throws UnsupportedOperationException at the offending line.

Prevent: a convention that all value objects are immutable, and tests that try to modify returned collections.

The invoice total is off by one cent in some orders, and reports do not reconcile. What do you do? Intermediate

What the interviewer is testing: floating point errors in money, and a safe migration plan.

Situation: prices and tax are double; 0.1 + 0.2 != 0.3, and the rounding differs depending on the order of operations, so sums of line items differ from the rounded total by a cent.

Check first: take a failing order and reproduce the exact calculation. Find every place that computes or compares amounts, and the rounding rule the business wants (per line or on the total, and which rounding mode: banking rounding HALF_EVEN or HALF_UP).

Fix: store amounts as integer minor units (cents) or as BigDecimal created from strings, with a fixed scale and explicit RoundingMode. Wrap them in an immutable Money type that has the currency and refuses to add different currencies. Compare with compareTo, not equals (scale matters). Migrate the database column to DECIMAL(19,4) or a bigint of cents, and write a one-off job to correct past data, with an audit report.

Prevent: a lint rule against double/float in the billing package and property-based tests such as "sum of parts equals total".

After adding a new enum constant in the middle, old rows in the database mean something else. What went wrong? Intermediate

What the interviewer is testing: the danger of ordinal() as a persisted value.

Situation: the JPA field uses @Enumerated(EnumType.ORDINAL) (this is the default!). The statuses were NEW(0), PAID(1), SHIPPED(2). A developer inserted PENDING after NEW. Everything after it moved up, so rows stored as 1 (paid) are now read as PENDING. No error, only wrong business data.

Check first: compare the database values with the enum order in git history. Count rows per value to see how many are affected. Stop the deployment, or roll back, if the release has just gone out.

Fix: restore the old order (add new constants at the end only) as an immediate fix; then migrate to EnumType.STRING, or to an explicit stable code with an AttributeConverter, with a data migration. Repair wrong rows from backups or audit logs.

Prevent: never persist ordinal(), a lint or review rule on EnumType.ORDINAL, and a test that reads known database values.

A sort sometimes crashes with "Comparison method violates its general contract!" in production only. Why? Senior

What the interviewer is testing: comparator contract bugs, which appear only with certain data.

Situation: the comparator is (a, b) -> a.getScore() - b.getScore() or compares doubles through an (int) cast, or handles null inconsistently. With normal data it works. With large positive and negative scores the subtraction overflows, the result has the wrong sign, and the comparison is no longer transitive. TimSort (used by List.sort and Arrays.sort for objects) can detect this in larger lists and throws IllegalArgumentException. With small inputs it quietly produces a wrongly sorted result, which is worse.

Check first: capture the data that triggered it, and test the comparator with antisymmetry and transitivity checks. Look for subtraction, casts, nulls, NaN, and comparators that use random or time-dependent values.

Fix: use Integer.compare, Double.compare or Comparator.comparingInt/Double, handle nulls with Comparator.nullsFirst, and never include mutable or changing data in the key while sorting.

Prevent: use Comparator.comparing chains, never hand-written subtraction, and run property tests with extreme values.

A cache returns a shared object. One caller edits its copy, and everyone else sees the edit. How do you fix and prevent it? Senior

What the interviewer is testing: shallow copies and shared references in caches.

Situation: an in-memory cache keeps Product objects. A pricing module gets one, applies a discount with product.setPrice(...) for one customer, and now the cached object has the discounted price for all customers. Copying with clone() or a copy constructor does not help if it only copies the references to the inner lists, because the inner List<Price> is still shared.

Check first: find who mutates objects obtained from the cache: use a test that reads, mutates, reads again. Check how the copy is made: is it shallow or deep?

Fix: best: make the cached type immutable (a record with immutable members), so sharing is safe and mutation requires withPrice(...) creating a new object. If the type has to stay mutable, return a deep copy on read, or make the cache hold DTOs and map them out. Document the rule on the cache API.

Prevent: "cache only immutable values" as a team rule, and tests that mutate a returned value and verify the cache is unchanged.

A new enum constant was added, and one feature quietly does nothing for it. How can the code be built so the compiler catches this? Senior

What the interviewer is testing: exhaustive design with enums and sealed types.

Situation: there are old-style switch statements over PaymentType with a default branch that ignores unknown values. A new type UPI is added, all the switches compile, and the one in the refund feature falls into default and silently returns without refunding.

Check first: find all switches and if chains on this enum (IDE "find usages", search for the type name), and look at their default branches.

Fix: (1) Put the behaviour inside the enum as an abstract method or a field, so a new constant cannot compile without it. (2) Use a switch expression (Java 14) over the enum without a default: the compiler then requires every constant to be covered, and a new constant is a compile error at each switch. (3) For data that differs by case, use a sealed interface with records, and a pattern-matching switch (Java 21). Where you must keep a default, make it throw IllegalStateException("unhandled " + type) instead of ignoring the value.

Prevent: a rule "no silent default on closed sets", and an integration test that loops over PaymentType.values() and runs each through each feature.
