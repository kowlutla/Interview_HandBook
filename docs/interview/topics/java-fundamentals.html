Mental model: the 7 ideas everything hangs on

One line: in Java a variable holds either a primitive value or a reference to an object on the heap, and every call copies that value. Objects are state plus behaviour, reached through types that decide which method runs.
  1. Two kinds of values. A primitive variable holds the number itself. A reference variable holds the address of an object (or null). Most classic traps (==, pass-by-value, NPE) come from mixing these up.
  2. Everything is passed by value. A method gets a copy of the primitive, or a copy of the reference. It can change the object the reference points to, never the caller's variable.
  3. Static type decides what compiles, runtime type decides what runs. Overloads are chosen by the compiler from declared types. Overridden instance methods are chosen at run time from the real object. Fields and static methods are never overridden, only hidden.
  4. Objects are built in a fixed order. Class initialization once (static parts), then for each new: parent fields and constructor, then child fields and constructor.
  5. Contracts matter more than syntax. equals, hashCode and compareTo are promises that hash-based and sorted collections rely on. Break one and you get lost entries, not compile errors.
  6. Immutability is the cheapest safety. An object that never changes needs no locks, no defensive copies when shared, and is safe as a map key. Records, enums, String and List.of are built on this idea.
  7. Prefer composition and a small public surface. Inheritance is the tightest coupling Java offers. Use it for a true "is-a" with a stable base. Otherwise combine objects, and keep fields private.

1. Primitives, wrappers and Strings

What are Java's primitive types, their sizes and default values? Basic

Java has eight primitives. Whole numbers: byte (8 bits), short (16), int (32), long (64). Decimals: float (32), double (64). Then char (16-bit unsigned UTF-16 unit) and boolean. Fields default to 0, 0.0, '\u0000' and false; object references default to null. Local variables have no default and must be assigned before use.

What a primitive is. Java has two families of types. A primitive is a raw value stored directly in the variable: the variable is the number. Everything else (String, List, your own classes) is a reference type: the variable holds an arrow to an object somewhere else. The eight primitives are the only types that are not objects, and they have no methods (5.toString() does not compile).

Why there are eight and why sizes are fixed. Different jobs need different widths: a byte for raw file data, an int for counters, a long for ids and timestamps, a double for measurements. Unlike C, where int may be 16 or 32 bits depending on the machine, Java fixes every size in the language, so the same program gives the same results on every platform. That is a big part of "write once, run anywhere".

How to pick one. In day-to-day code: int for counts and indexes, long for ids, money in minor units and epoch milliseconds, double for measurements, boolean for flags, and byte mainly for buffers. short and float are rare. Using byte or short for a single local variable saves nothing, because the JVM computes in 32-bit int anyway: byte a = 1, b = 2; byte c = a + b; does not compile, since a + b is an int.

int  i = 42;
long big = 3_000_000_000L;   // needs L: 3 billion does not fit in an int
float f = 1.5f;              // needs f: 1.5 alone is a double
char c = 'A';                // 65, a number you can print as a letter
System.out.println(c + 1);   // 66  (char arithmetic gives int)

Defaults versus locals. Fields (instance and static) get a default so an object is never half-garbage: numbers 0, boolean false, references null. Local variables get no default, because the compiler can check "definite assignment" cheaply, and it prefers a compile error over a silent 0. int x; System.out.println(x); is a compile error ("variable x might not have been initialized").

What an interviewer probes next: "what is the range of byte?" (-128 to 127), "why is char unsigned?" (it is a UTF-16 code unit, so 0 to 65535, and characters outside the basic plane need two chars), and "how big is a boolean?" (unspecified; one byte in an array is typical, and the JVM often uses a full int slot in fields).

Sizes are fixed by the language, so an int is 32 bits on every machine. The one exception is boolean, whose storage size the specification leaves to the JVM. int and double are the defaults for integer and decimal literals, so long big = 3_000_000_000L needs the L. Primitives live inside their owner: on the stack for locals, inside the object on the heap for fields. They are faster and smaller than objects and cannot be null.

Primitive versus wrapper class: when do you use which? Basic

I use primitives by default because they are faster, use less memory and cannot be null. I use a wrapper (Integer, Long, Boolean) only when I need an object: as a generic type argument like List<Integer>, or when "no value" (null) is a real state, such as an optional database column.

What a wrapper is. For every primitive there is a class that wraps it in an object: int has Integer, long has Long, boolean has Boolean, char has Character, and so on. A wrapper holds one immutable value inside a normal heap object.

Why wrappers exist. Java generics only work with reference types, so List<int> is illegal and you must write List<Integer>. Wrappers also give you somewhere to hang useful methods (Integer.parseInt, Long.compare) and a way to express "no value": an Integer can be null, an int cannot. A nullable database column or an optional JSON number maps naturally to a wrapper.

What it costs. Compare storing one million numbers:

Decision rule. Start with the primitive. Switch to the wrapper only when (1) a generic type or API demands an object, (2) null is a meaningful state, or (3) you need Optional-style "maybe absent". For numeric work on big collections, prefer int[] or IntStream; libraries such as fastutil or Eclipse Collections offer primitive-specialised lists and maps.

Pitfall to mention: a field declared Integer count; defaults to null, not 0, so count++ throws a NullPointerException on a fresh object. Declare it int unless you truly need null.

Each wrapper is an immutable object with a header, so an Integer costs about 16 bytes plus a 4 to 8 byte reference, against 4 bytes for an int. A List<Integer> of a million numbers is an array of references to a million small objects, which is slow and hard on the garbage collector. Where it matters, use int[] or primitive streams such as IntStream. Wrappers also bring traps: they can be null, and == compares references (see the next questions).

Remember: primitive for values that always exist, wrapper for generics and "maybe missing".

What are autoboxing and unboxing, and where do they bite? Basic

Autoboxing is the compiler automatically turning an int into an Integer (by calling Integer.valueOf), and unboxing is the reverse (calling intValue()). It is convenient, but it hides three costs: a NullPointerException when you unbox a null, object creation in loops, and surprising == results.

What it is. Boxing means wrapping a primitive in its wrapper object, unboxing means pulling the primitive back out. Since Java 5 the compiler does both for you ("auto"). You write Integer a = 5; and the compiler rewrites it to Integer a = Integer.valueOf(5);. You write int b = a; and it rewrites to int b = a.intValue();.

Why it exists. Before Java 5 you had to write list.add(Integer.valueOf(5)) and list.get(0).intValue() by hand. Autoboxing removed the noise so that generic collections of numbers feel natural. The price is that real work now hides behind innocent-looking syntax.

The three places it bites, step by step.

  1. Null unboxing. Integer count = map.get("x"); returns null when the key is absent. int n = count; compiles to count.intValue(), which is a method call on null, so a NullPointerException is thrown at an innocent-looking line. The same happens in if (flag) when flag is a null Boolean, and in arithmetic such as count + 1.
  2. Hidden allocation. Long total = 0L; total += i; means total = Long.valueOf(total.longValue() + i). Wrappers are immutable, so every pass of a million-iteration loop allocates a new Long object (values outside the small cache). Declaring long total removes it entirely.
  3. Overload and equality surprises. list.remove(1) removes by index, and == on two boxed numbers compares references (next question).

Quick diagnosis habit. When you see a method returning a wrapper (Integer, Boolean, Long) being assigned to a primitive or used in arithmetic, ask "can this be null?". Prefer returning primitives, or OptionalInt, or an explicit default (map.getOrDefault(key, 0)), so the null case is handled where it is created.

Integer count = map.get(key);   // null if the key is missing
int n = count;                  // NullPointerException here

Long total = 0L;
for (int i = 0; i < 1_000_000; i++) total += i;  // allocates a new Long each pass

The NPE is the most common one in real code: a method returns Integer or Boolean and the caller assigns it to a primitive. Arithmetic on a wrapper unboxes, adds, then boxes the result, so a loop accumulator declared as Long creates garbage on every iteration. Declare it long. Also, list.remove(1) on a List<Integer> removes by index, not by value, because the primitive overload wins (see the output-prediction section).

Remember: unboxing null throws NPE, and a wrapper accumulator allocates on every loop pass.

Why is Integer a = 127, b = 127; a == b true, but with 128 it is false? Basic

Because == on objects compares references, not values. Autoboxing calls Integer.valueOf, which returns a shared cached object for values from -128 to 127. So 127 gives the same object twice and == is true. 128 is outside the cache, so each boxing creates a new object and == is false. I always compare wrappers with equals.

What happens, line by line. Take Integer a = 127, b = 127;. The compiler turns each assignment into Integer.valueOf(127). Inside valueOf the JDK checks "is the number between -128 and 127?". If yes, it returns an object from a pre-built array (the Integer cache), so both a and b hold the same arrow. If no (128 or more), it calls new Integer(...), so every boxing gives a fresh object. And == on two references only asks "same arrow?".

Integer a = 127, b = 127;
System.out.println(a == b);          // true  (same cached object)
Integer c = 128, d = 128;
System.out.println(c == d);          // false (two different objects)
System.out.println(c.equals(d));     // true  (same value)
System.out.println(c == 128);        // true  (one side is primitive: c is unboxed)

The last line is worth remembering: == between a wrapper and a primitive unboxes the wrapper and compares numbers, so it is safe. The danger is only == between two wrapper objects.

Why the cache exists. Small numbers are boxed constantly (loop counters in List<Integer>, map values), so the JDK pre-allocates the 256 most common ones and shares them. That saves allocation. It is safe only because wrappers are immutable.

Why this is a production trap. Unit tests use ids 1, 2, 3, so == works. Production ids reach 5000, == silently becomes false, and a permission check or a lookup starts failing for some users only. It is a good example of a bug that passes every test. Static analysers (SpotBugs, Error Prone, Sonar) flag reference comparison on boxed types.

Rule for the interview. Say the mechanism (valueOf plus cache) and the fix (equals, or unbox to primitives), then add that the cache upper bound is configurable but you must never depend on it.

The cache is built when the Integer class loads. Its upper bound can be raised with -XX:AutoBoxCacheMax, but nobody should rely on that. Long, Short and Byte have the same -128..127 cache, Character caches 0..127, and Boolean has two shared values. new Integer(5) is deprecated for removal and always creates a new object. The danger is that code with small test data "works" and then fails in production with larger ids.

Remember: boxes in -128..127 are shared, others are not. Compare wrappers with equals, never ==.

What is the difference between == and equals()? Basic

For primitives, == compares the values. For objects, == asks "is this the very same object in memory?", while equals() asks "do these two objects mean the same thing?". The default Object.equals is just ==, so a class has to override it to get value comparison. String, the wrappers, List, BigDecimal and records already do.

Start with the picture. A reference variable is an arrow to an object. == asks "do these two arrows point at the exact same object?". equals() asks "do these two objects represent the same thing?". Two different houses can have the same floor plan: == says they are different houses, equals says they are equal designs.

Why the default is identity. Object.equals is defined as this == other, because the base class cannot know what "same content" means for your type. So a class that does not override equals behaves like identity, and two new Customer(7) objects are not equal. Classes with a natural notion of value override it: String compares characters, Integer compares the number, List compares elements in order, a record compares all components.

Customer a = new Customer(7), b = new Customer(7);
a == b          // false  (two objects)
a.equals(b)     // false unless Customer overrides equals
a == a          // true

When each is correct.

  • Primitives: only == exists (and int == long promotes to compare numbers).
  • Enums and null checks: == is right. An enum constant exists exactly once, and x == null is the only null check.
  • Everything else, especially String and boxed numbers: equals.

Null safety. a.equals(b) throws if a is null. "ADMIN".equals(role) is safe because the literal is never null, and Objects.equals(a, b) handles nulls on both sides (two nulls are equal).

Pitfall. A String "works" with == only when both sides come from literals (next questions on the pool). That accident is why the bug shows up in production but not in tests.

Two practical rules. Call equals on a known non-null value, "ADMIN".equals(role) or Objects.equals(a, b), so a null does not throw. And whenever you override equals, override hashCode too, or hash-based collections break (covered later). Enums are the one object type where == is correct, because each constant exists exactly once.

String a = new String("hi"), b = new String("hi");
a == b        // false: two objects
a.equals(b)   // true: same characters

Remember: == is identity, equals is meaning. Use equals for objects, == for primitives and enums.

Which numeric traps should every Java developer know? Intermediate

Integer overflow wraps around silently, float and double cannot represent most decimals exactly, integer division throws away the remainder, and implicit conversions can lose data. None of these throw an exception, so the program just produces a wrong number.

The common cause. Java's numeric types are fixed-width machine numbers, not mathematical numbers. Anything that does not fit, or is not exactly representable, is silently approximated instead of reported. Knowing the four failure modes lets you spot them in review.

1. Overflow (wraps around). An int is 32 bits and arithmetic is done modulo 2 to the power 32. Think of a car odometer rolling over from 999999 to 000000.

int x = Integer.MAX_VALUE;        // 2147483647
System.out.println(x + 1);        // -2147483648  (wraps, no exception)
System.out.println(Math.abs(Integer.MIN_VALUE));  // -2147483648 (no positive twin)
Math.addExact(x, 1);              // throws ArithmeticException: integer overflow

Typical real cases: summing many amounts in an int, computing a * b for file sizes, and the mid-point (lo + hi) / 2 in binary search (fix: lo + (hi - lo) / 2 or >>>).

2. Binary fractions. double stores numbers as a sum of powers of two. 0.5 and 0.25 are exact, but 0.1 is a repeating binary fraction (like 1/3 in decimal), so it is stored as the nearest representable value. That is why 0.1 + 0.2 prints 0.30000000000000004. Compare doubles with a tolerance (Math.abs(a - b) < 1e-9), and use BigDecimal for money.

3. Integer division and mixed types. If both operands are integers the result is an integer, with the fraction dropped (toward zero): 7 / 2 is 3, -7 / 2 is -3, and -7 % 2 is -1 (the remainder takes the sign of the dividend). To get 3.5 make one operand a double before dividing: 7 / 2.0 or (double) 7 / 2. The cast binds tighter than the division, so (double) (7 / 2) is already 3.0.

4. Special values and narrowing. double has NaN (never equal to anything, even itself), Infinity, and -0.0. Casting a big double or long to int clamps or wraps depending on the type: (int) 3.9e10 is Integer.MAX_VALUE, while (int) 3_000_000_000L wraps to -1294967296.

What to say: name the four, show one example of each, and give the defence: exact methods or long for counters, BigDecimal for money, explicit casts and 2.0 literals for division.

  • Overflow: Integer.MAX_VALUE + 1 is Integer.MIN_VALUE. Math.abs(Integer.MIN_VALUE) is still negative. Use Math.addExact, multiplyExact or long when overflow is possible; the exact methods throw ArithmeticException.
  • Binary fractions: 0.1 + 0.2 == 0.3 is false, since 0.1 has no exact binary form. Compare with a tolerance, or use BigDecimal.
  • Integer division: 1 / 2 is 0, and (double) (1 / 2) is still 0.0 because the cast happens after the division. Write 1 / 2.0.
  • NaN: Double.NaN != Double.NaN is true. Use Double.isNaN. Dividing a double by zero gives Infinity, but an int divided by zero throws.
  • Narrowing casts: (int) 3.9 is 3 (truncates), and (byte) 200 is -56.

Remember: overflow wraps silently, doubles are approximate, int / int truncates.

How should you represent money in Java? Intermediate

Never double. I use BigDecimal, or I store whole minor units (cents) in a long, plus a currency code. Both give exact results, and I choose the rounding rule explicitly instead of letting binary floating point choose it for me.

Why double is wrong for money. A double stores binary fractions, and amounts like 0.10 or 19.99 have no exact binary form. Each calculation adds a tiny error, and these errors accumulate and then disagree with a hand calculation or with the bank by a cent.

double total = 0;
for (int i = 0; i < 10; i++) total += 0.10;
System.out.println(total);            // 0.9999999999999999
System.out.println(total == 1.0);     // false

Two sound designs.

  • Whole minor units in a long. Store 19.99 USD as the integer 1999 cents. Integer arithmetic is exact and fast, and databases store it as BIGINT. You still need a rule for splitting (for example 100 split into 3 parts: 33, 33, 34) and for currencies with 0 or 3 decimals (JPY, KWD). Good for payment systems that mostly add and subtract.
  • BigDecimal. An arbitrary-precision decimal made of an unscaled integer and a scale ("19.99" is 1999 with scale 2). Good when you multiply by rates (tax, interest, FX), because you control the scale and rounding.

How BigDecimal behaves, with examples.

new BigDecimal(0.1)          // 0.1000000000000000055511151231257827...  (binary error captured)
new BigDecimal("0.1")        // 0.1 exactly
BigDecimal.valueOf(0.1)      // 0.1  (uses Double.toString)

BigDecimal a = new BigDecimal("2.0"), b = new BigDecimal("2.00");
a.equals(b)                  // false: scale 1 vs scale 2
a.compareTo(b) == 0          // true : numerically equal

BigDecimal.ONE.divide(new BigDecimal("3"));   // ArithmeticException: non-terminating decimal
BigDecimal.ONE.divide(new BigDecimal("3"), 4, RoundingMode.HALF_EVEN);  // 0.3333

Rounding policy. HALF_UP is what people learn at school (2.5 becomes 3). HALF_EVEN ("banker's rounding") rounds ties to the even neighbour (2.5 becomes 2, 3.5 becomes 4), which avoids a systematic upward bias over many transactions. Tax law or the business may mandate one of them, so make it an explicit decision and apply it in one place, never scattered through the code.

Other points to mention: BigDecimal is immutable (every operation returns a new object, so assign the result: total = total.add(x)), it is slower than primitives (fine for money, wrong for numeric simulations), and in JSON and databases use a decimal type, not a float. JSR 354 (javax.money) and the Joda-Money library offer ready-made Money types with the currency attached.

Rules for BigDecimal: build it from a String or BigDecimal.valueOf(double), never new BigDecimal(0.1), which captures the binary error (0.1000000000000000055...). Its equals compares scale too, so new BigDecimal("2.0").equals(new BigDecimal("2.00")) is false. Use compareTo(...) == 0 for numeric equality. divide without a scale and rounding mode throws ArithmeticException for non-terminating results like 1/3, so pass RoundingMode.HALF_EVEN (banker's rounding, standard in finance) or a MathContext. Rounding once at the end, not at every step, avoids "off by one cent" drift.

BigDecimal price = new BigDecimal("19.99");
BigDecimal total = price.multiply(BigDecimal.valueOf(3))
                        .setScale(2, RoundingMode.HALF_EVEN);

Remember: money is BigDecimal built from a String, or long cents. Compare with compareTo.

Why is String immutable, and what does that buy you? Basic

Once a String is created its characters never change; methods like toUpperCase return a new String. That makes it safe to share between threads and callers, safe as a HashMap key, safe to keep in the String pool, and safe for security-sensitive values such as file paths and class names that are validated once and then used.

What "immutable" means here. After new String("abc") exists, nothing can ever change its characters. Methods that look like edits return a different object: s.toUpperCase() does not alter s. A very common beginner bug is calling s.trim(); and ignoring the result, which does nothing.

String s = "java";
s.concat(" rocks");               // result thrown away
System.out.println(s);            // java
s = s.concat(" rocks");           // now s points to a NEW String
System.out.println(s);            // java rocks

How the language enforces it. The class is final (so no subclass can add mutable behaviour), the char/byte storage is a private final array, and no method returns that array. Reflection can still break it, but only by deliberate hacking.

Why the designers chose this, one reason at a time.

  1. Sharing is safe. The String pool can give the same object to a thousand callers, because nobody can change it under them. Without immutability the pool would be impossible.
  2. Hash keys stay valid. Strings are the most common HashMap key. If the characters could change after insertion, the hash would change and the entry would be lost (the mutable-key bug). Immutability lets String cache its hash code in a field after the first call.
  3. Thread safety for free. No locks are needed to share a String between threads.
  4. Security. Imagine openFile(path) validates the path, then another thread mutates the same char array to point at a different file before the open happens (a "time of check to time of use" attack). Immutable strings close that door. The same reasoning covers class names, URLs and database connection strings.

The trade-off and the answer to it. Building a long string by many small appends creates many short-lived objects, so use StringBuilder for that. And for secrets such as passwords, immutability is a weakness: you cannot wipe a String from memory, it lingers until garbage collection, so APIs such as KeyStore and Console.readPassword use char[], which you can overwrite with zeros after use.

It is enforced by design: String is a final class, and its internal array is private and final and never handed out. Four concrete benefits. Pooling: identical literals can share one object. Cached hash: hashCode is computed once and stored, so map lookups are cheap. Thread safety: no locks needed. Security: a checked value cannot be altered after the check. The cost is that building a string piece by piece creates many temporary objects, which is why StringBuilder exists. Since Java 9, strings made only of Latin-1 characters are stored as one byte per character ("compact strings"), halving memory for typical text.

Remember: immutable means shareable, cacheable and hash-safe. Building lots of text needs StringBuilder.

What is the String pool? How do literals, new String and intern() behave? Intermediate

The String pool is a table of unique String objects kept on the heap. A literal like "hello" is looked up there, so every "hello" in the program is the same object. new String("hello") always creates a separate object outside the pool. intern() returns the pooled copy, adding the string to the pool if needed.

The problem the pool solves. Programs contain the same text over and over ("OK", "GET", field names). Creating a fresh object for every occurrence wastes memory. Because Strings are immutable, the JVM can safely keep one shared copy and let all users point at it. That shared table is the String pool (also called the intern table).

How a literal gets there. When a class is loaded, each string literal in its constant pool is resolved lazily the first time the code runs: the JVM looks the text up in the pool, reuses the entry if it exists, or adds it. So two literals with the same text, even in different classes, are the same object.

Walking through the example.

  1. String s1 = "hello"; puts "hello" in the pool (or finds it) and s1 points to it.
  2. String s2 = "hello"; finds it, s2 points to the same object. s1 == s2 is true.
  3. String s3 = new String("hello"); forces a new object on the normal heap (the argument literal was pooled, but the new object is a separate copy). s1 == s3 is false, s1.equals(s3) is true.
  4. s3.intern() asks the pool "give me the canonical one for this text": it returns the pooled "hello" object, so s1 == s3.intern() is true.

Compile-time folding in detail.

final String a = "hel";
String b = "hel";
System.out.println(("hel" + "lo") == "hello");   // true:  constant expression
System.out.println((a + "lo") == "hello");       // true:  a is a constant variable (final + literal)
System.out.println((b + "lo") == "hello");       // false: b is not final, built at run time

Where it lives and what it costs. Since Java 7 the pool is part of the normal heap, so unused entries are collected and its size is limited only by the heap. Before that it sat in PermGen and could cause OutOfMemoryError: PermGen space if you interned too much. The table is a fixed-bucket hash table, so interning millions of distinct strings can make lookups slow; -XX:StringTableSize tunes it.

When intern() is used on purpose. Rarely: to cut memory when loading millions of repeating strings (for example a column of country codes). Even then a plain HashMap<String,String> dedup map you control, or the JVM option -XX:+UseStringDeduplication with G1, is usually a better tool.

String s1 = "hello", s2 = "hello";
String s3 = new String("hello");
s1 == s2             // true  (same pooled object)
s1 == s3             // false (s3 is a separate object)
s1 == s3.intern()    // true

The compiler also folds constant expressions: "hel" + "lo" is computed at compile time and is the pooled literal, but c + "lo" with a non-final variable c is built at run time and is not pooled. Since Java 7 the pool lives on the normal heap (before that it was in the fixed-size permanent generation), so pooled strings can be garbage collected, and its size is tunable with -XX:StringTableSize. I almost never call intern() by hand: it is slower than a map you control, and the right fix for wrong == comparisons is to use equals.

Remember: literals are pooled, new String is not. Compare Strings with equals.

String, StringBuilder and StringBuffer: how do they differ and when do you use each? Basic

String is immutable. StringBuilder is a mutable buffer for building text efficiently, and it is not thread-safe. StringBuffer is the same thing with every method synchronized, which makes it slower and is rarely needed. I use a plain String for values, and a StringBuilder when I assemble text in a loop.

The problem. Because String is immutable, each "edit" allocates a new String. If you build a result from 10,000 pieces, a naive approach creates 10,000 intermediate Strings. You need a mutable text buffer, and that is what StringBuilder and StringBuffer are.

How a builder works inside. It keeps a char/byte array bigger than the current text and a length counter. append writes into the free space and bumps the length. When the array is full, it allocates a bigger one (about double plus 2) and copies once. Because capacity grows geometrically, the average cost per append is constant, which we call amortized O(1).

For joining a collection, String.join(",", list) or Collectors.joining is clearest.

And is string concatenation with + inside a loop really slow? Intermediate

Yes. Each s += x creates a brand new String and copies all the old characters, so a loop of n appends copies about n squared characters. For 200,000 rows that is billions of copies and a lot of garbage. A single a + b + c expression is fine, but inside a loop I use one StringBuilder, or better, stream the output.

Count the copying. s += row means s = s + row. Because Strings are immutable, this allocates a new String of length len(s) + len(row) and copies both into it. Suppose each row is 10 characters. After pass 1 you copied 10 characters, after pass 2 you copied 20, after pass 3 30, and so on. For n rows the total is 10 + 20 + ... + 10n, about 5 n squared characters.

// slow

}

When plain + is fine. A single expression such as "Hello " + name + "!" (compiled into one efficient concatenation) or logging calls that run once. Do not "optimise" those into builders, it only hurts readability. Note that logging log.debug("x=" + expensive()) builds the text even when debug is off; use the parameterised form log.debug("x={}", x).

What to say in an interview: explain the quadratic copying with the 10, 20, 30 arithmetic, give the builder fix, then the streaming option for very large output, which also keeps memory flat.

The compiler turns one + expression into an efficient builder call (an invokedynamic call to StringConcatFactory since Java 9, a hidden StringBuilder before that). But that optimization is per expression: in a loop it builds a fresh builder and a fresh String every iteration, so the copying stays quadratic. For very large output, such as a CSV export, do not even build the whole text in memory: write rows straight to a Writer or OutputStream so memory stays flat.

Remember: += in a loop is quadratic. Use StringBuilder, or stream the output.

2. Keywords, pass-by-value and initialization

Is Java pass-by-value or pass-by-reference? Basic

Always pass-by-value. For a primitive the method gets a copy of the number. For an object it gets a copy of the reference, so the caller's variable and the parameter are two separate arrows pointing at the same object. The method can change the object through its arrow, but if it re-points its own arrow, the caller does not notice.

The two definitions. Pass-by-value: the method receives a copy of whatever the caller wrote as the argument. Pass-by-reference (C++ int&, C# ref): the method receives an alias for the caller's variable itself, so assigning to the parameter changes the caller's variable. Java only has the first. The confusion comes from the fact that the value being copied, for an object variable, is the reference.

Walk through it. Suppose the caller has List<String> names = new ArrayList<>();. The variable names holds an arrow (say, address 0x7A) to the list object. When you call fill(names), the parameter list is a new variable in the method's frame that gets a copy of the same arrow 0x7A. Two arrows, one list.

static void fill(List<String> list) {
    list.add("a");               // follows the arrow: caller's list now has "a"
    list = new ArrayList<>();    // changes only the local arrow
    list.add("b");               // goes into the NEW list, which nobody else sees
}
List<String> names = new ArrayList<>();
fill(names);
System.out.println(names);       // [a]

The swap test (the proof). If Java were pass-by-reference, swap(x, y) could exchange the caller's two variables. In Java it cannot, whatever the types, because swap only exchanges its own copies:

static void swap(String a, String b) { String t = a; a = b; b = t; }
String x = "1", y = "2";
swap(x, y);
System.out.println(x + y);       // 12  (unchanged)

Primitives and Strings. A primitive is copied by value, so void inc(int n) { n++; } never affects the caller. A String parameter is a copy of the arrow to an immutable object, so the method cannot change the text, only re-point its own arrow.

Design consequences. (1) A method that mutates a collection or object you passed has a visible side effect: document it, or work on a copy (new ArrayList<>(input)). (2) To return several results, return a small record or object; do not hope to "assign out" through parameters. (3) final on a parameter only stops re-pointing the local arrow, it does not make the object immutable.

The one-liner for interviews: "Java passes everything by value; for objects that value is the reference, so you can mutate the shared object but never re-point the caller's variable."

void change(StringBuilder sb, String s) {
    sb.append(" world");      // changes the shared object: caller sees it
    sb = new StringBuilder(); // re-points the local copy only: caller unaffected
    s = s + "!";              // String is immutable: new object, caller unaffected
}

The classic proof is the swap method: swap(a, b) cannot swap the caller's variables in Java, because it only swaps its own copies. In a real-code review this matters in two ways: a method that mutates a passed-in list or object has a side effect the caller can see, so document it or copy first; and a method cannot "return two values" by assigning to its parameters.

Remember: Java copies the arrow, not the object. Mutation is visible to the caller, re-assignment is not.

What does static mean on a field, a method, a block and a nested class? Basic

static means "belongs to the class, not to any one object". A static field has one copy shared by all instances. A static method is called on the class and has no this. A static block runs once when the class is initialized. A static nested class has no hidden link to an outer instance.

The idea. Normally every object has its own copy of the fields, and methods run on an object (this). static says "this member belongs to the class itself, not to any instance". It exists once per class (per class loader), you reach it through the class name, and it is there before any object is created.

The four places it appears.

  • Static field: one shared variable, such as a counter or a constant. static final constants (Math.PI) are the safe and common use.
  • Static method: no this, so it cannot read instance fields. Good for pure helpers (Math.max, Collections.sort) and factories (List.of).
  • Static block: code that runs once when the class is initialized, used to set up a static field that needs several statements (building a lookup map).
  • Static nested class: a class declared inside another that does not need an outer instance.
class Counter {
    static int created = 0;           // one for the whole class
    final int id;                     // one per object
    Counter() { id = ++created; }
}
new Counter(); new Counter();
System.out.println(Counter.created);  // 2
// static int helper() { return id; } // compile error: no instance here

Static methods are not overridden. The call target is fixed by the compiler from the declared type, so there is no polymorphism. A subclass defining the same static method hides the parent's. That also makes static methods hard to mock in tests, a practical reason to keep business logic in injectable instances.

Why mutable statics are dangerous. The field is one object shared by every thread, every request and every test in the JVM. Two parallel requests writing a static currentUser will see each other's value, and tests leak state into each other. A static collection that only ever gets added to is a memory leak, because static fields are GC roots for as long as the class stays loaded (often for the life of the application).

Rule of thumb. Static is fine for constants, pure functions and factories. For anything stateful, use an instance and pass or inject it.

Consequences worth stating. A static method cannot touch instance fields directly, and it is not polymorphic: it is chosen by the declared type, so a subclass method with the same signature hides it rather than overriding it. Static fields are global state: they are shared by every thread and every request, so a mutable static is a thread-safety and test-isolation problem (see the scenario on shared static state). Static fields live as long as their class is loaded, so a static collection that only grows is a classic memory leak. Prefer static final constants and stateless utility methods.

Remember: static = one per class. Mutable static = shared global state, so be careful.

What does final mean on a variable, a method, a class and a parameter? Basic

On a variable, final means it can be assigned only once. On a method, it cannot be overridden. On a class, it cannot be extended. On a parameter, the method cannot re-assign it. A final reference still lets you change the object it points to: final stops re-pointing, not mutation.

One keyword, four meanings. The common thread: "this cannot change later".

On aEffectWhy you use it
local variable or parameterassigned oncereadability, and needed (or effectively needed) for lambdas
fieldassigned once, in the declaration or every constructorimmutable objects, thread-safe publication
methodcannot be overriddenprotect a step of an algorithm; the JIT can inline it
classcannot be extendedString, wrappers, records: designed not to be subclassed

Final is about the variable, not the object. A final reference variable can never point elsewhere, but the object it points to can still change if its class is mutable. That is the most common misconception.

final int[] a = {1, 2};
a[0] = 99;                 // fine: array elements are not final
// a = new int[3];         // compile error

final StringBuilder sb = new StringBuilder("x");
sb.append("y");            // fine

Blank finals. A final field may be left unassigned at declaration if every constructor assigns it exactly once. The compiler checks this ("definite assignment"), so you can never forget it: leaving it unset is a compile error. That is how immutable classes get their per-instance values.

Effectively final and lambdas. A lambda or inner class copies the value of a captured local at creation time. Because the copy and the original could drift apart if the local changed later, Java requires the local to be final or effectively final (never reassigned after the first assignment). That is why int count = 0; list.forEach(x -> count++); does not compile; use an AtomicInteger or a stream reduction instead.

Memory-model guarantee. Once a constructor finishes, every thread is guaranteed to see the final fields with their assigned values, even if the object was published through a data race, as long as this did not escape during construction. That is the technical reason immutable classes can be shared without locks.

Constants. static final primitives and Strings initialised with a constant expression are inlined by the compiler into the classes that use them. If you change such a constant in a library and recompile only the library, old callers still hold the old value until they are recompiled, a classic binary-compatibility surprise.

final List<String> names = new ArrayList<>();
names.add("Asha");        // fine: the list is mutable
names = new ArrayList<>(); // compile error: re-assignment

Final instance fields have an extra guarantee from the Java memory model: once the constructor finishes, other threads see the correct values of final fields without extra synchronization (provided this did not escape during construction). This is why immutable classes use final fields. Lambdas and inner classes may capture only final or effectively final locals (assigned once, even without the keyword). Make a class final when it is not designed for extension (String is final); that is a safer default than leaving subclassing open by accident.

Remember: final = no re-assignment, no override, no subclass. It does not make the object immutable.

In what order does Java initialize a class and its objects when parent and child both have static blocks, instance blocks and constructors? Intermediate

Static parts first, once per class, parent before child. Then for each new Child(): the parent's instance initializers and field initializers (in text order), then the parent constructor, then the child's instance initializers, then the child constructor. The parent always finishes completely before the child starts.

Why there is an order at all. An object of a subclass contains a parent part and a child part. The child part may depend on the parent part being ready, so Java builds the parent first. And a class's static setup must happen before any object of it can exist. The rules below are the same every time, so you can predict output by pure reading.

Two phases.

  1. Class initialization (once per class, the first time it is actively used). Parent class first, then child. Static field initializers and static blocks run top to bottom in source order.
  2. Object creation (every new). (a) Memory is allocated and every field holds its default (0, false, null). (b) The constructor starts and immediately calls the parent constructor (super(...)). (c) Before the parent constructor body runs, the parent's instance field initializers and instance blocks run, in source order. (d) The parent constructor body runs. (e) Then the child's instance initializers and instance blocks. (f) Then the child constructor body.

Trace one example fully.

class P {
    static { System.out.println("P static"); }
    int a = init("P field");
    { System.out.println("P block"); }
    P() { System.out.println("P ctor"); }
    static int init(String s) { System.out.println(s); return 1; }
}
class C extends P {
    static { System.out.println("C static"); }
    int b = init("C field");
    C() { System.out.println("C ctor"); }
}
new C();
// P static, C static, P field, P block, P ctor, C field, C ctor

The second new C() prints only P field, P block, P ctor, C field, C ctor, because the static part ran already.

Common follow-ups. (1) "What if the child constructor calls this(...)?" Instance initializers run once, in the constructor that actually calls super. (2) "Where do static fields get their default before the block runs?" At class preparation, before any initializer, so a static block can see a later-declared static field as 0 or null. (3) "What is printed if a parent constructor calls an overridden method?" See the constructor-overridable question: the child's field is still at its default.

Tip. In an output-prediction question, write the six steps on paper and tick them off. Do not guess.

class P { static { print("Ps"); } { print("Pi"); } P() { print("Pc"); } }
class C extends P { static { print("Cs"); } { print("Ci"); } C() { print("Cc"); } }
new C();   // Ps Cs Pi Pc Ci Cc
new C();   // Pi Pc Ci Cc   (static blocks do not run again)

Before any of this, the memory for the object is allocated and all fields hold default values (0, false, null). That is why code that runs early can see a field as null even though it has an initializer. The first line of every constructor is an implicit or explicit call to super(...), which is how the parent part gets built first. Static fields and static blocks are executed in the order they appear in the source.

Remember: static (parent, child) once, then parent instance init and constructor, then child instance init and constructor.

When exactly is a class initialized? How does the lazy holder idiom use that? Senior

A class is initialized lazily, the first time it is actively used: creating an instance, calling a static method, or reading or writing a non-constant static field. Initializing a subclass first initializes its parent. The JVM guarantees this runs once and is thread-safe, which is exactly what the lazy holder singleton relies on.

Loading versus initialization. These are different. Loading reads the .class bytes and creates the class object. Initialization runs the static initializers. The JVM may load a class early, but the language (JLS 12.4.1) says initialization happens only on the first active use, which is what makes static setup lazy.

The list of triggers.

  • Creating an instance with new.
  • Calling a static method.
  • Reading or writing a static field that is not a compile-time constant.
  • Initializing a subclass (the superclass is initialized first). Note: this does not initialize the interfaces it implements, unless they declare default methods.
  • Running a class as the program's main class, or Class.forName("X").

Non-triggers. Foo.class, declaring Foo[] arr, and reading static final int MAX = 10 (the compiler copies the number into the caller, so Foo is never touched).

class Lazy {
    static { System.out.println("Lazy init"); }
    static final int K = 5;          // compile-time constant
    static int n = 7;
}
int a = Lazy.K;                      // prints nothing
Class<?> c = Lazy.class;             // prints nothing
int b = Lazy.n;                      // prints "Lazy init"

Why initialization is thread-safe. The JVM holds an initialization lock per class. If two threads touch the class at once, one runs the static code and the other waits until it finishes; afterwards the result is visible to everyone (a happens-before edge). So a static final field set in a static initializer is safely published without synchronized. The lazy holder idiom exploits exactly this: the inner Holder class is only initialized when get() first touches Holder.INSTANCE.

Failure mode. If a static initializer throws, the first user sees ExceptionInInitializerError (the real cause is inside). The class is then marked erroneous, and every later use throws NoClassDefFoundError: Could not initialize class X with no stack of the original problem. In logs, always search upward for the first error. Also beware of cyclic static initialisation between two classes, where one sees the other's static fields still at default values.

What does not trigger initialization: reading a compile-time constant (static final int X = 5, which is inlined by the compiler), declaring a variable or an array of the type, or referring to a class literal Foo.class. A static block that throws turns into ExceptionInInitializerError, and later uses of that class fail with NoClassDefFoundError, which confuses people in production.

class Config {
    private Config() {}
    private static class Holder { static final Config INSTANCE = new Config(); }
    static Config get() { return Holder.INSTANCE; }  // Holder loads on first call
}

Nothing is created until get() is called, no synchronized or volatile is needed, and the class-initialization lock does the safe publication.

Remember: classes initialize on first real use, once, under a JVM lock. That makes the holder idiom free and thread-safe.

Why is calling an overridable method from a constructor dangerous? Senior

Because the parent constructor runs before the child's fields are initialized. If the parent constructor calls a method the child overrides, the child's version runs on a half-built object and sees default values: null, 0 or false, even when the field has an initializer. The result is a confusing NullPointerException or wrong state.

Replay it as a timeline. Create new Child() with the example from the answer:

  1. The JVM allocates the object. All fields hold defaults: name is null.
  2. Child() starts and its first action is the implicit super(), so Base() runs.
  3. Base() calls init(). Dynamic dispatch picks Child.init(), because the real object is a Child.
  4. Child.init() reads name. The initializer = "child" has not run yet, because child field initializers run only after super() returns. So name is null and name.length() throws.
  5. (Never reached) the field initializer would have run, then the rest of the child constructor.

Why this is surprising. Normally dynamic dispatch is a feature: the right override runs. In a constructor it runs on an object whose subclass part is not built yet, so the override sees a half-initialised object and may violate its own invariants. Even a final field can be observed with its default value in this window, which is the one way to see a final field change.

Safe alternatives.

  • Call only private, static or final methods from constructors (they cannot be overridden). Documenting an overridable method as "called by the constructor" is the other option, as AbstractList style classes do carefully.
  • Use the template-method pattern with an explicit init() invoked by whoever creates the object, or a static factory that constructs, then initialises.
  • Prefer composition and constructor parameters, so the parent receives what it needs instead of asking the child for it.

Static analysers flag this ("overridable method call in constructor", Sonar S1699). It is also a favourite whiteboard puzzle.

class Base {
    Base() { init(); }                 // runs the child's override
    void init() {}
}
class Child extends Base {
    private String name = "child";     // assigned AFTER Base() returns
    @Override void init() { System.out.println(name.length()); } // NPE
}
new Child();

The order is: allocate (name = null), run Base() which calls Child.init() (name is still null), and only then the field initializer sets "child". The fix: in constructors call only private, static or final methods, or make the class final. If a class needs a setup hook, use a separate init() step called by the creator, or a factory method.

Remember: in a constructor, never call a method a subclass can override.

What is var, and when should you avoid it? Basic

var (Java 10) lets the compiler infer the type of a local variable from its initializer. It is not dynamic typing: the variable has a fixed, compile-time type, you just do not write it. I use it when the type is obvious from the right-hand side, such as var users = new ArrayList<User>(), and avoid it when the type becomes unclear.

What it does. var asks the compiler to work out the declared type from the right-hand side. After var names = new ArrayList<String>();, names has the compile-time type ArrayList<String>, exactly as if you had written it. The bytecode is identical. It is not a dynamic type like JavaScript's var, and var is not a keyword but a "reserved type name", so you can still name a variable var.

Why it was added. To cut repetition where the type is obvious and long: Map<String, List<Order>> byCustomer = new HashMap<String, List<Order>>(); says the type twice. It also helps with types you cannot or do not want to write (anonymous classes, intersection types).

var count = 10;               // int
var price = 9.99;             // double
var text = "hi";              // String
var users = new ArrayList<User>();   // ArrayList<User>
for (var u : users) { ... }   // User
// var x;                      // error: no initializer
// var y = null;               // error: null has no type
// var f = () -> 1;            // error: lambda needs a target type
// var arr = {1, 2};           // error: array initializer needs a type

The traps. (1) var list = new ArrayList<>(); infers ArrayList<Object>, because the diamond has nothing to infer from. (2) var id = 5; is an int; if later code needs long, the intent was lost. (3) Declaring with var hides a change of return type: var r = repo.find(); silently changes when find() returns something else. (4) Programming to interfaces: var list = new ArrayList<String>() has the concrete type ArrayList, not List, so List<String> list = new ArrayList<>() is better when you want to restrict yourself to the interface.

Where it is allowed. Local variables with an initializer, for and enhanced-for variables, try-with-resources, and (Java 11) lambda parameters, which allows annotations: (@NonNull var x, var y) -> .... It is not allowed for fields, method parameters or return types.

Style rule. Use var when the right side makes the type obvious (new, a clearly typed factory, a literal). Spell the type out when the name and expression do not reveal it. Choose good variable names, because with var the name carries more of the meaning.

It works only for local variables, loop variables and try-with-resources, not for fields, parameters or return types, and the variable must be initialized (var x; and var x = null; do not compile). Two gotchas: var list = new ArrayList<>() infers ArrayList<Object>, and var n = 1 is an int even if you meant long. Avoid var x = service.process() where the reader cannot tell the type. A good test: would a reviewer know the type without hovering in the IDE?

Remember: var = inferred, still static. Use when the type is obvious, skip when it hides intent.

3. Classes, objects and the OOP pillars

What is the difference between a class and an object, and what really happens on new? Basic

A class is the blueprint: it defines fields and methods. An object is one instance built from it, living on the heap with its own copy of the instance fields. On new Foo() the JVM loads and initializes the class if needed, allocates heap memory with every field set to its default, runs the constructor chain, and returns a reference to the new object.

Class versus object, with a plain analogy. A class is an architect's blueprint for a house type. An object is one actual house built from it. All houses share the same design, but each has its own address, own paint colour and own occupants. In code, the class defines the fields (what each instance stores) and methods (what it can do); each object stores its own field values.

What new Foo() really does, in the JVM's words.

  1. If class Foo is not yet loaded, the class loader finds Foo.class, verifies it and links it. Then the static initializers run (once).
  2. The JVM allocates a block on the heap large enough for the object header plus all instance fields (including inherited ones). The allocation is usually a fast pointer bump inside a thread-local allocation buffer (TLAB).
  3. The block is zeroed, so every field has its default value.
  4. The constructor chain runs: parent first, then child, with field initializers as described in the initialization-order question.
  5. The expression new Foo() evaluates to a reference, which you usually store in a variable.
class Point { int x, y; Point(int x, int y) { this.x = x; this.y = y; } }
Point p = new Point(1, 2);
Point q = p;               // q is another arrow to the SAME object
q.x = 99;
System.out.println(p.x);   // 99
Point r = new Point(1, 2); // a different object
System.out.println(p == r);// false

Lifetime. The object lives as long as something can reach it through a chain of references starting from a "GC root" (a local variable on a running thread's stack, a static field, and so on). When nothing can reach it, the garbage collector may reclaim it. You never free objects yourself, and a null assignment is rarely necessary except for long-lived fields.

What is shared and what is per object. Instance fields: one copy per object. Static fields: one copy per class. Methods: code is stored once per class, and each call passes this to say which object to work on. Extra detail for seniors: the object header holds a pointer to the class metadata and the lock/hash state, which is why even an empty object takes about 16 bytes.

The variable you hold is only that reference (the arrow), not the object. Several variables can point at one object, and an object nobody points at becomes garbage and is reclaimed by the garbage collector. The object itself contains a header (a pointer to its class plus bookkeeping, roughly 12 to 16 bytes) and then its fields. Methods are not copied per object: all instances share the class's code.

Remember: class = blueprint, object = heap instance, variable = reference to it.

How do constructors work? What is the default constructor, and how do this(...) and super(...) fit in? Basic

A constructor initializes a new object: same name as the class, no return type, not inherited. If I write no constructor, the compiler adds a public no-argument default one; the moment I write any constructor, the default disappears. The first statement of every constructor is either this(...) (call another constructor of the same class) or super(...) (call the parent's), and if I write neither, the compiler inserts super().

The role of a constructor. After the JVM allocates an object with all fields zeroed, a constructor is the code that puts it into a valid starting state: it assigns fields, validates arguments and acquires what the object needs. Its job is to make sure no one ever holds a half-built, invalid object. It looks like a method with the class's name and no return type, but it is not a method: it is not inherited and is only run through new (or this(...) / super(...)).

The rules, in the order you meet them.

  1. No constructor written, compiler adds one. A public (or same access as the class) no-argument constructor that calls super(). Frameworks such as JPA and some serializers need this no-arg constructor.
  2. Any constructor written, no default is added. If you add Account(String id), then new Account() stops compiling unless you also write the no-arg one.
  3. The first statement is a constructor call. Either this(...) to delegate to a sibling or super(...) to delegate to the parent. If you write neither, the compiler inserts super(). Therefore a child class compile-fails if the parent has no no-arg constructor and the child does not call a parent constructor explicitly.
  4. Fields assigned in the constructor. A final field must be assigned exactly once in every path.
class Animal {
    final String name;
    Animal(String name) { this.name = name; }          // only constructor
}
class Dog extends Animal {
    Dog() { super("dog"); }                            // must pass a name
    // Dog() { }  // would not compile: Animal() does not exist
}

Constructor patterns. Chaining with this(...) keeps validation in one place (the "telescoping" constructors problem appears when there are many optional parameters, which a builder or static factory solves). A private constructor with a static getInstance gives a singleton; a private constructor on a class of only static methods prevents instantiation; protected constructors suit abstract classes. Prefer a static factory (Money.of("EUR", 5)) when the name adds meaning, when you want to return cached instances or subtypes, or when failure should be explicit.

Pitfalls. Do not call overridable methods in a constructor, do not let this escape (registering as a listener, starting a thread) before the constructor finishes, and keep heavy I/O out of constructors. Constructors cannot be abstract, static or final.

That is why a subclass fails to compile when the parent has only constructors with arguments: the implicit super() finds nothing to call, so I must write super(args) myself. Use this(...) to chain overloaded constructors and keep validation in one place. You can use only one of this(...) and super(...), and it must come first (newer JDKs relax this: flexible constructor bodies, allowing some statements before super(...), were previewed for several releases and I believe finalized in Java 25, but "first statement" is still the standard answer). this alone is the current object, used to tell a field from a parameter of the same name; super.method() calls the parent's version of an overridden method. A private constructor blocks outside creation, which is how singletons, utility classes and factories work. When there are many optional parameters, prefer a static factory or a builder.

class Account {
    private final String id; private final long balance;
    Account(String id) { this(id, 0); }              // chain
    Account(String id, long balance) {               // single place to validate
        if (balance < 0) throw new IllegalArgumentException("balance");
        this.id = id; this.balance = balance;
    }
}

Remember: every constructor starts with this(...) or super(...), implicit super() by default. Write any constructor and the default is gone.

Explain the four pillars of OOP with real examples, not definitions. Basic

Encapsulation: keep state private and expose behaviour, so a BankAccount allows withdraw(amount) but never lets outside code set the balance directly. Abstraction: callers depend on a simple contract, like PaymentGateway.charge(), not on how it talks to a bank. Inheritance: a class reuses and specializes a parent, like SavingsAccount extends Account. Polymorphism: the same call behaves differently by actual type, so payment.pay() runs the card, wallet or UPI version.

Start from the problem OOP solves. Large programs fail when everything can touch everything. The four pillars are four tools for keeping code changeable. Present each with a tiny real example and its benefit.

1. Encapsulation: protect the state. Keep fields private and give outsiders only operations that keep the object valid. Benefit: you can change the internal representation (store cents in a long instead of a double) without breaking any caller, and an invalid state (negative balance) is impossible to create.

2. Abstraction: expose what, hide how. Callers see a small contract. List.add works the same whether the list is an array or a linked list. Benefit: you can replace the implementation, and a reader needs to understand less.

3. Inheritance: reuse and specialise. A SavingsAccount is an Account with interest rules added. Benefit: shared code lives in one place. Cost: tight coupling, so use it only for true "is-a" relationships and prefer composition otherwise.

4. Polymorphism: one call, many behaviours. The caller writes against the parent type, and the object's actual class decides what runs.

interface PaymentMethod { void pay(long cents); }
class Card implements PaymentMethod { public void pay(long c) { /* call card gateway */ } }
class Upi  implements PaymentMethod { public void pay(long c) { /* call UPI */ } }

void checkout(PaymentMethod m, long total) { m.pay(total); }   // no if/else on type
checkout(new Upi(), 500);

Adding Wallet means adding a class, not editing checkout. This is the "open for extension, closed for modification" principle in action. There are three kinds of polymorphism worth naming: subtype (the example), parametric (generics) and ad-hoc (overloading).

How they connect. Encapsulation protects each object, abstraction defines the contract between objects, polymorphism makes the contract pluggable, and inheritance is one (the heaviest) way to share code behind it. Interviewers like a candidate who adds the caveat "I use interfaces and composition far more than class inheritance".

Common trap question. "Is Java 100 percent object-oriented?" No: it has primitives, static members and (since 8) functional style. It is a mostly object-oriented language.

The one that matters most in design is polymorphism, because it removes if/else chains on type. Instead of if (type == CARD) ... else if (type == UPI) ..., I define a PaymentMethod interface with several implementations, and adding a new method means adding a class, not editing a long conditional. Be ready to say the honest caveat: inheritance is the pillar to use least, because it couples a child tightly to its parent (see composition).

Remember: hide state (encapsulation), expose a contract (abstraction), reuse sparingly (inheritance), let the object decide (polymorphism).

What is the difference between abstraction and encapsulation? Basic

Abstraction is about what the caller needs to know: I show a simple contract and hide the complexity behind it, so a List user does not care whether it is an array or a linked list. Encapsulation is about protecting the data: I make fields private and control every change through methods, so the object can never be put into an invalid state. One hides complexity, the other guards state.

Two ideas that are easy to mix up. Both are about "hiding", but they hide different things for different reasons.

Example with both. Think of a car. The pedal and steering wheel are an abstraction: you say "go faster" without knowing about fuel injection. The sealed engine bay and locked fuel cap are encapsulation: you cannot reach in and change the injection timing in a way that wrecks the engine.

interface Cache { Optional<String> get(String key); void put(String k, String v); }  // abstraction

    private final Map<String, String> map;     // encapsulated: private
    private final int max;                      // invariants kept inside
    LruCache(int max) { this.max = max; this.map = new LinkedHashMap<>(16, 0.75f, true); }
    public Optional<String> get(String k) { return Optional.ofNullable(map.get(k)); }

    private void evictOldest() { /* ... */ }
}

Callers depend on Cache (abstraction) and can be given a Redis-backed implementation tomorrow. LruCache keeps its map private so nobody can add entries beyond the limit (encapsulation).

You can have one without the other. A class with public fields but implementing an interface has abstraction without encapsulation. A well-guarded concrete class with no interface has encapsulation without abstraction. Good design usually has both.

They work together. An interface or abstract class is the tool for abstraction (design level). Private fields, validation in constructors and setters, and not returning internal mutable collections are the tools for encapsulation (implementation level). A good one-line contrast: abstraction decides what to expose, encapsulation enforces how it may be changed.

Remember: abstraction hides complexity, encapsulation protects state.

Show encapsulation that actually protects an invariant. Intermediate

Getters and setters on every field are not encapsulation, they just move the field access. Real encapsulation means the class itself enforces its rule, here "the balance never goes negative", and offers operations instead of raw setters. Internal mutable parts, like a list of transactions, are never handed out directly.

The goal: an invariant. An invariant is a rule that must always be true for an object, like "balance is never negative" or "end date is after start date". Encapsulation is the discipline of making it impossible for any code outside the class to break the invariant. If the rule can be broken from elsewhere, you must re-check it in every caller, and sooner or later somebody forgets.

Anti-pattern: the anemic bean.

class Account { private long balance; public long getBalance(){...} public void setBalance(long b){...} }
// caller code scattered everywhere:
if (acc.getBalance() >= amt) acc.setBalance(acc.getBalance() - amt);   // check-then-act, not atomic

Problems: the rule is in the caller, so each caller must copy it; the read-modify-write is not atomic, so two threads can both pass the check and overdraw; and nothing stops setBalance(-5).

Better design, in steps.

  1. Make the state private and, where possible, final.
  2. Offer intention-revealing operations (withdraw, deposit) instead of setters.
  3. Check the invariant inside those operations and throw on violation. Because the check and the change are in one method, you can make that method synchronized or use a lock or atomic once, rather than in every caller.
  4. Never expose internals: return copies or unmodifiable views, never the live collection.
  5. Validate in the constructor so an invalid object can never exist.
Account acc = new Account(100);
acc.withdraw(150);        // throws IllegalArgumentException, balance stays 100
List<Txn> h = acc.history();
h.clear();                // UnsupportedOperationException: copy is read-only

Leaking an internal is the subtle case. A getter returning List<Txn> that is the live field gives the caller a remote control over your state. Return List.copyOf (a snapshot), Collections.unmodifiableList (a live read-only view), or a stream. Likewise a constructor that stores the caller's list must copy it, or the caller can still change it later.

What to say: "Setters are not encapsulation; behaviour with guarded state is." Then mention "tell, don't ask" and the atomicity benefit.

public final class Account {
    private long balance;                               // cents
    private final List<Txn> history = new ArrayList<>();

    public void withdraw(long amount) {
        if (amount <= 0 || amount > balance) throw new IllegalArgumentException();
        balance -= amount;
        history.add(new Txn(-amount));
    }
    public List<Txn> history() { return List.copyOf(history); }  // safe copy
}

There is no setBalance: the only way to change the balance is through methods that check the rule. Returning history directly would let a caller call clear() on it and break the account from outside. The same idea is called "tell, don't ask": call account.withdraw() rather than reading the balance, deciding, and writing it back, which also removes a race condition between the read and the write.

Remember: operations over setters, and never leak a mutable internal.

Inheritance or composition? Why do people say "favour composition over inheritance"? Senior

I use inheritance only for a true "is-a" relationship with a base class designed for it. Otherwise I use composition: hold the other object in a field and delegate to it. Inheritance ties the child to the parent's implementation, so a change in the parent can silently break the child (the fragile base class problem), and the child inherits methods it should not have.

Definitions. Inheritance (class B extends A) makes B a kind of A: B automatically gets all of A's non-private members and can be used wherever an A is expected. Composition means B has an A as a private field and calls its methods when needed ("has-a"). Both reuse code, but they couple differently.

Why inheritance is risky. A subclass is bound to its parent's implementation, not only its public contract. If the parent changes how its methods call each other, the child can silently break. This is the fragile base class problem. The child also inherits every public method, even ones that make no sense for it, and it cannot choose a different parent later.

Worked example (Effective Java). We want a set that counts how many elements were ever added.

class CountingSet<E> extends HashSet<E> {
    int added = 0;
    @Override public boolean add(E e) { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { added += c.size(); return super.addAll(c); }
}
var s = new CountingSet<String>();
s.addAll(List.of("a", "b", "c"));
System.out.println(s.added);   // 6, not 3!

Reason: HashSet.addAll (via AbstractCollection) calls add for each element, which is already counted. The author of CountingSet could not know this implementation detail; a future JDK could even change it and silently change the answer. With composition we forward only what we need:

class CountingSet<E> {
    private final Set<E> inner = new HashSet<>();
    private int added;
    boolean add(E e) { added++; return inner.add(e); }
    boolean addAll(Collection<? extends E> c) { boolean ch = false; for (E e : c) ch |= add(e); return ch; }
}

Now the behaviour depends only on our code, and inner could be a TreeSet tomorrow. To keep the type usable as a Set, implement the Set interface and forward (the "forwarding class" or decorator pattern).

When inheritance is the right call. (1) A real is-a with the Liskov property (see next question). (2) The parent was designed and documented for extension (abstract skeletons like AbstractList, framework base classes that say "extend me"). (3) You control both sides, ideally in the same package or module. Everything else: composition plus an interface. Make classes final unless you designed them for extension.

Testing and flexibility. Composition lets you inject a fake collaborator in a unit test and swap strategies at run time (change the delegate), neither of which class inheritance allows. That is why frameworks lean on dependency injection.

The famous example: a CountingSet extends HashSet overrides add and addAll to count additions. But HashSet.addAll internally calls add for each element, so each element is counted twice. The child depended on a parent internal detail that is not documented. The JDK's own Stack extends Vector is another regret: a stack lets you insert in the middle. With composition, the class holds a Set and forwards only the methods it wants, and can swap the implementation later. Composition also works with interfaces and testing (inject a fake). Rules: inherit only when the parent is meant to be extended (documented or abstract), the relationship is a real is-a, and you control both; otherwise mark classes final.

Remember: inheritance = "is-a" and tight coupling, composition = "has-a" and flexibility. Default to composition.

What is the Liskov Substitution Principle, with an example of breaking it? Senior

LSP says that wherever the code uses a parent type, I must be able to use any subtype without breaking correctness. A subclass must keep the parent's promises: accept at least the same inputs, give at least the same guarantees, and not throw surprises. The classic break is Square extends Rectangle.

What it says, in plain words. Barbara Liskov's principle: if S is a subtype of T, then a program that works with T must still work when you give it an S. "Is-a" in code is not about real-world taxonomy (a square is a rectangle in geometry), it is about whether the subclass honours the parent's behavioural contract.

The rectangle and square example, concretely.

class Rectangle { protected int w, h;
    void setWidth(int w)  { this.w = w; }
    void setHeight(int h) { this.h = h; }
    int area() { return w * h; } }
class Square extends Rectangle {
    @Override void setWidth(int w)  { this.w = w; this.h = w; }
    @Override void setHeight(int h) { this.w = h; this.h = h; } }

static void resize(Rectangle r) { r.setWidth(5); r.setHeight(4); assert r.area() == 20; }
resize(new Rectangle());  // ok, area 20
resize(new Square());     // area 16: the caller's expectation is broken

The caller of Rectangle relied on an unwritten promise: width and height change independently. Square broke it.

The formal rules (design by contract).

  • Preconditions cannot be strengthened: a subclass method may not demand more than the parent (rejecting inputs the parent accepted).
  • Postconditions cannot be weakened: it must deliver at least what the parent promised.
  • Invariants must be kept and the subclass must not throw new kinds of exceptions the parent never threw.

Real JDK-style violations. A read-only collection that extends a mutable interface and throws UnsupportedOperationException on add (the JDK itself has List.of, a documented compromise). An override that does nothing, or a subclass of Bird called Penguin whose fly() throws. Client code full of instanceof checks is a symptom: callers had to learn which subtypes to distrust.

How to fix. Re-model so the base type only promises what every subtype can honour. Split interfaces (Bird and FlyingBird), make the shapes immutable (a Square record with side is perfectly fine), or use composition. LSP is the "L" in SOLID and is the reason "is-a" must mean "behaves-as-a".

A rectangle lets you set width and height independently. A square must keep them equal, so its setWidth also changes height. Code written for rectangles, r.setWidth(5); r.setHeight(4); assert r.area() == 20, now fails for a square, although the types are "compatible". Rule of thumb: a subtype may not strengthen preconditions (demand more from callers), may not weaken postconditions (promise less), and must not throw new unexpected exceptions. Warning signs are overrides that throw UnsupportedOperationException, empty overrides, and instanceof checks in client code. The fix is usually a different model: separate Shape implementations, or immutable shapes.

Remember: a subtype must be usable anywhere its parent is, without surprises. "Is-a" in code means "behaves-as-a".

Explain the four access levels, including the default one. Basic

From narrowest to widest: private (this class only), package-private (no keyword: same package), protected (same package, plus subclasses anywhere), and public (everywhere). The default with no keyword is package-private, not public. A top-level class can only be public or package-private.

Why access control exists. Everything a class makes visible becomes a promise to its users: you can no longer rename or remove it without breaking someone. Access modifiers let you decide how big that promise is, which is the mechanical side of encapsulation.

Plain-language meaning of each level.

  • private: only code inside the same top-level class (including its nested classes) can see it. Use for fields and helper methods.
  • package-private (write nothing): classes in the same package. Good for helper classes and for members tests in the same package can reach.
  • protected: the package, plus subclasses in other packages. It is for members designed to be used or overridden by subclasses.
  • public: everyone. This is your API.

The subtle protected rule, with an example. Code in a subclass in another package can access a protected member only on its own type (this, or another instance of the subclass), not on an arbitrary parent-typed reference.

package a;  public class Base { protected void ping() {} }
package b;  public class Sub extends Base {
    void test(Base other, Sub mine) {
        this.ping();     // ok
        mine.ping();     // ok
        // other.ping(); // compile error: other is a Base, not necessarily a Sub
    }
}

Other rules interviewers ask.

  • A top-level class is only public or package-private. Nested classes may use all four. A public class must live in a file with the same name.
  • Overriding may not reduce visibility (see override rules). Interface members are implicitly public, so implementing a method in a class needs the keyword public: writing it without is a compile error.
  • private is per class, not per object: one instance can read another instance's private field of the same class (this.x == other.x in equals).
  • Java 9 modules add exports: a public class in a non-exported package is invisible to other modules. Reflection on private members is blocked for JDK internals unless --add-opens is given.

Guideline. Start as closed as possible. Widening later is non-breaking, narrowing is breaking. Prefer package-private over protected unless subclassing is intended, and keep all instance fields private.

Practical guidance: start with private and widen only when needed. Fields should almost always be private. protected is part of the public contract for subclasses, so use it sparingly; and a subclass in another package may use a protected member only through its own type, not through a parent reference. An override may widen access (protected to public) but never narrow it. Interface methods are implicitly public. Since Java 9, modules add another layer: a public class in a package that its module does not export is not accessible to other modules.

Remember: private, package (default), protected, public. Default is package-private.

4. Inheritance, polymorphism, abstract classes and interfaces

Abstract class versus interface: how do they differ, and how do you choose? Basic

An interface describes a capability that any class can promise, and a class can implement many. An abstract class is a partly finished class with state and constructors that subclasses complete, and a class can extend only one. I choose an interface for the contract and an abstract class when subclasses really share fields or a template of steps.

Two different jobs. An interface says "any object that can do these things". It is a role or capability: Comparable, Runnable, PaymentMethod. Unrelated classes can play it. An abstract class says "this is the common starting point for a family of related classes, and it is not finished". It can hold fields, constructors, and a mix of concrete and abstract methods.

Why a class can implement many interfaces but extend only one class. Java avoids multiple inheritance of state, which causes the diamond problem (two parents with the same field, which one wins?). Interfaces carry no instance state, so combining several is safe. Java 8 default methods allow behaviour in interfaces, and the conflict rules handle same-named defaults.

A concrete case: the template method.

abstract class Report {                        // shared state + algorithm skeleton
    protected final String title;
    Report(String title) { this.title = title; }
    public final String render() {             // fixed order of steps
        return header() + body() + footer();
    }
    protected String header() { return "== " + title + " ==\n"; }
    protected abstract String body();          // subclasses fill this in
    protected String footer() { return "\n-- end --"; }
}
class SalesReport extends Report {
    SalesReport() { super("Sales"); }
    protected String body() { return "total: 42"; }
}

Here an interface would not work as well, because the skeleton uses a shared field (title) and a constructor. In contrast, interface Notifier { void send(String msg); } with EmailNotifier, SmsNotifier and a test double is a pure capability and belongs in an interface.

Decision rule.

  1. Default to an interface for what callers depend on (parameter and field types, public APIs).
  2. Add an abstract class only when implementers genuinely share state or a template, and offer it as an optional skeleton (AbstractMap implements the Map contract so you do not rewrite all of it).
  3. If you must evolve a published interface without breaking implementers, add a default method.

Frequently asked extras. Interface fields are public static final constants. An abstract class can have a constructor, but you cannot call new on it directly (only through a subclass). A functional interface (exactly one abstract method) can be the target of a lambda, an abstract class cannot. A sealed interface restricts who may implement it.

Default methods blurred the line, but they cannot hold state, so the real dividing line is state and the single-inheritance limit. A common good design is both: an interface for the contract (List) plus an abstract skeleton class (AbstractList) that does most of the work. Interface fields are implicitly public static final. Prefer the interface as the type in method signatures and fields, which keeps callers decoupled from the implementation.

What are default methods for, and what happens when two interfaces provide the same default method? Intermediate

Default methods (Java 8) let an interface add a method with a body, so existing implementations do not break. That is how List.sort and Collection.stream were added without touching every class. If two interfaces give the same default, the class does not compile until it overrides the method itself, and it can pick one with A.super.hello().

The problem defaults solve. Before Java 8, adding a method to an interface broke every class that implemented it, since they all lacked the new method. That made it nearly impossible to evolve the Collections API. A default method gives the new method a body that all existing implementers inherit automatically. Java 8 used this to add Iterable.forEach, Collection.stream, List.sort and Map.getOrDefault without touching any implementation.

The diamond problem. If a class implements two interfaces with a default method of the same signature, the compiler cannot guess which one you want. The rules to resolve a call, in priority order:

  1. Class wins: a concrete method declared in the class or inherited from a superclass beats any interface default ("class always wins").
  2. Most specific interface wins: if one interface extends the other and re-declares the default, the sub-interface's version is used.
  3. Otherwise, compile error: you must override the method in the class, and may delegate with InterfaceName.super.method().
interface Walker { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }
class Duck implements Walker, Swimmer {
    public String move() { return Walker.super.move() + "+" + Swimmer.super.move(); }
}
System.out.println(new Duck().move());   // walk+swim

class Base { public String move() { return "base"; } }
class Fish extends Base implements Swimmer { }
System.out.println(new Fish().move());   // base  (class wins)

Related features. static interface methods are called as Interface.method() and are not inherited. private interface methods (Java 9) let several defaults share code. Defaults cannot override equals, hashCode or toString, because these always come from Object (class wins).

Design caution. Defaults are for evolving APIs and optional behaviour with a sensible implementation in terms of the abstract methods (Comparator.reversed()). They are not a replacement for abstract classes: they cannot see state. And a library adding a default method can still clash with your own class, so evolve public interfaces deliberately.

The conflict rules, in order: (1) a method from the class or a superclass always wins over any interface default, (2) otherwise the most specific interface wins (a sub-interface beats its parent), (3) otherwise it is ambiguous and a compile error. Interfaces can also have static methods (utility methods tied to the interface, not inherited by implementers) and, since Java 9, private methods to share code between defaults.

interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }
class C implements A, B {
    public String hello() { return A.super.hello() + B.super.hello(); }  // must decide
}

Remember: class beats interface, specific beats general, otherwise you must override.

What is the difference between overloading and overriding? Basic

Overloading is several methods with the same name but different parameter lists in one class; the compiler picks one from the declared argument types. Overriding is a subclass replacing an inherited instance method with the same signature; the JVM picks it at run time from the object's real class. Overloading is compile-time, overriding is run-time.

Same word root, different mechanism. To overload is to put several methods with one name side by side, each with a different parameter list, so a caller's argument types select one. To override is to replace a parent's method in a subclass with the same signature so that, through a parent-typed variable, the child's version runs.

A mixed example that interviewers love.

class Animal { String speak(Animal a) { return "animal-animal"; } }
class Dog extends Animal {
    @Override String speak(Animal a) { return "dog-animal"; }   // override
    String speak(Dog d)              { return "dog-dog"; }      // overload (new method)
}
Animal x = new Dog();  Dog y = new Dog();
x.speak(y);   // dog-animal : compiler picks speak(Animal) from x's declared type; run time uses Dog's override
y.speak(y);   // dog-dog    : declared types are Dog, Dog; the overload speak(Dog) is the best match
y.speak(x);   // dog-animal

The first call surprises people: the argument y is a Dog, but because the receiver is declared as Animal, which has only speak(Animal), that is the signature the compiler chooses. The JVM then runs Dog's override of exactly that signature.

Constructors and varargs. Constructors can be overloaded but never overridden. Overload resolution (next questions) prefers exact match, then widening, then boxing, then varargs, so print(int...) loses to print(int). Avoid overloads with the same number of parameters of related types, they confuse readers: sort(List) versus sort(Collection). Use different names when behaviour differs.

class Printer {
    void print(Object o) { ... }     // overloads
    void print(String s) { ... }
}
class Animal { String sound() { return "..."; } }
class Dog extends Animal { @Override String sound() { return "Woof"; } }  // override

Changing only the return type is not overloading, and it does not compile. Always write @Override: if you mistype the name or the parameter type, it becomes a compile error instead of a silently new method, which is the cause of a classic bug (see the accidental-override scenario). Only instance methods are overridden: static methods are hidden, private methods are not visible, and fields are never overridden.

Remember: overload = same name, different parameters, compile time. Override = same signature, run time.

What are the exact rules for overriding a method, and what is a covariant return type? Intermediate

An override must have the same name and parameter types, a return type that is the same or a subtype (covariant), access that is the same or wider, and may throw no new or broader checked exceptions. It cannot override a final, static or private method. The rules exist so that code written against the parent still works for every child.

Why the rules look the way they do. They all follow from one principle: code written against the parent type must keep working with any child. Each rule closes a hole.

Examples of legal and illegal overrides.

class Parent {
    protected Number value() throws IOException { return 1; }
}
class Child extends Parent {
    @Override public Integer value() { return 2; }     // ok: wider access, covariant, fewer exceptions
    // @Override Number value() throws Exception {...} // error: broader checked exception
    // @Override private Number value() {...}          // error: weaker access
}

Covariant returns in practice. Object.clone() returns Object, so a class that wants cloneable callers to avoid a cast declares @Override public Point clone(). Builder hierarchies use it too: a subclass overrides build() to return the more specific type.

Generics and bridge methods. If class Box implements Comparable<Box> declares compareTo(Box), the compiler also generates a hidden bridge method compareTo(Object) that casts and calls the real one, because after type erasure the interface method takes Object. That is how an override with a narrower parameter type, which looks like an overload in source, still satisfies the interface at run time.

Other details. The overriding method may add synchronized or final, drop abstract, and may drop the throws clause. A static method with the same signature as a parent's instance method (or vice versa) is a compile error. Always write @Override: it makes the compiler check every rule above and catches typos.

  • Access can widen, never narrow: a parent protected may become public, not private, otherwise code using the parent type would suddenly lose access.
  • Checked exceptions: the override may throw fewer or narrower ones, or none. Unchecked exceptions are unrestricted.
  • Covariant return: the override may return a more specific type, so no cast is needed at the call site. Object.clone() returns Object, but a class can declare public Point clone().

Under the hood the compiler adds a synthetic bridge method with the parent's signature that calls the real one, which is how the JVM keeps both views consistent. A frequent confusion is that @Override checks these rules for you at compile time, which is the reason to always use it.

Remember: same signature, return same or narrower, access same or wider, exceptions same or narrower.

Explain static (compile-time) dispatch versus dynamic (run-time) dispatch with an example. Senior

The compiler first chooses which method signature to call, using the declared types of the arguments. At run time the JVM then chooses which implementation of that signature to run, using the real class of the receiver object. So overloads follow the declared type, and overrides follow the actual object.

Split the call into two decisions. Every method call obj.m(arg) is decided in two stages, by two different actors using different information.

  1. Compile time (javac): which signature? Look at the declared (static) type of obj to find the class to search, and the declared types of the arguments to pick the best overload. Result: a fixed method signature written into the bytecode, say Vet.treat(Animal).
  2. Run time (JVM): which implementation? The invokevirtual instruction looks at the actual class of the receiver object, finds the most specific implementation of that exact signature (via the class's virtual method table), and runs it.

So overloads are decided in step 1 (static dispatch), overrides in step 2 (dynamic dispatch). Only the receiver takes part in step 2. The arguments are never re-examined at run time. This is called single dispatch.

class Animal { String sound() { return "..."; } }
class Dog extends Animal { String sound() { return "Woof"; } }
class Vet {
    String treat(Animal a) { return "generic " + a.sound(); }
    String treat(Dog d)    { return "dog " + d.sound(); }
}
Animal a = new Dog();
Vet vet = new Vet();
vet.treat(a);              // "generic Woof"
//   step 1: declared arg type is Animal  -> treat(Animal)
//   step 2: inside, a.sound() is virtual -> Dog.sound() = "Woof"
vet.treat((Dog) a);        // "dog Woof"

What this implies for design. If you want behaviour to depend on the runtime type of an argument too (double dispatch), Java gives no direct support. The classic answer is the visitor pattern: the element calls visitor.visit(this), and inside the element class this has the precise type. In modern Java, a sealed interface plus a pattern switch does the same job more simply.

Performance note for seniors. Virtual calls are cheap thanks to the JIT: if class hierarchy analysis shows one loaded implementation, or profiling shows a call site always sees one class (monomorphic), the call is inlined with a guard. Calls seeing two classes are bimorphic and still fast; many classes (megamorphic) fall back to a table lookup. private, static and final methods and constructors use non-virtual instructions.

class Animal { }  class Dog extends Animal { }
class Vet {
    void treat(Animal a) { print("animal"); }
    void treat(Dog d)    { print("dog"); }
}
Animal a = new Dog();
new Vet().treat(a);   // "animal": overload chosen from the declared type Animal

If Dog overrides Animal.sound(), then a.sound() runs Dog's version, because the receiver is really a Dog. Inside the JVM, a virtual call (invokevirtual) looks up the method in the receiver's method table. The JIT compiler often inlines it when only one implementation is loaded. Only the receiver is dispatched dynamically; the arguments are not (Java has no multiple dispatch), which is why the visitor pattern exists.

Remember: overloads: decided by javac from declared types. Overrides: decided by the JVM from the real object.

Are fields polymorphic? What is field hiding, and what about static method hiding? Intermediate

No. Only instance methods are polymorphic. A field or a static method is resolved from the declared type of the variable, not the object's real class. If a child declares a field with the same name as the parent's, it hides it: the object holds both, and which one you see depends on the variable's type.

Why fields are different. Polymorphism is implemented for method calls only: the JVM's virtual dispatch looks up methods in the receiver's class. A field access is resolved statically, at compile time, from the declared type of the expression. And an object of a subclass that declares a field with the same name physically contains two fields: the parent's and the child's.

class A { String name = "A"; String name() { return name; } }
class B extends A { String name = "B"; }          // hides A.name (does not replace it)
B b = new B();
A a = b;
System.out.println(b.name);        // B   (declared type B)
System.out.println(a.name);        // A   (declared type A, same object!)
System.out.println(((A) b).name);  // A
System.out.println(a.name());      // A   (A.name() reads A's field; B did not override it)

Walk through: all four lines use the same object, only the static type of the expression changes, and that alone selects the field. The last line shows the trap: a method defined in A refers to A's field, even for a B object.

Static method hiding follows the same rule.

class P { static String who() { return "P"; } }
class Q extends P { static String who() { return "Q"; } }
P p = new Q();
p.who();   // "P": chosen from the declared type (and the compiler warns: use P.who())
Q.who();   // "Q"

Why hiding is bad. The code reads as if the child replaced the field, but the parent's methods keep using the parent's copy, which leads to bugs where half of the code sees one value and half sees the other. There is no use case that is not better served by a different name, a constructor parameter, or an overridable getter.

How to do it properly. Keep fields private (which also avoids hiding collisions, since private fields are not visible to children), and expose behaviour through methods, which are polymorphic. Call statics on the class name. Linters and IDEs warn about hidden fields (HiddenField, Sonar S2387).

class A { String n = "A"; String get() { return n; } static String who() { return "A"; } }
class B extends A { String n = "B"; String get() { return n; } static String who() { return "B"; } }
A x = new B();
x.n        // "A"  field: declared type
x.get()    // "B"  method: real type
x.who()    // "A"  static: declared type (do not call statics on instances)

Hiding is almost always a mistake: it makes code read differently from how it runs. Avoid reusing a parent's field name, and call static methods on the class name, not on an instance. Access fields through methods and the polymorphism works as expected.

Remember: methods follow the object, fields and statics follow the variable's type.

What are upcasting and downcasting, and when do you get a ClassCastException? Basic

Upcasting treats a subclass object as its parent type; it is always safe and automatic, Animal a = new Dog(). Downcasting goes back to the subtype, (Dog) a, needs an explicit cast, and is checked at run time: if the object is not really a Dog, you get a ClassCastException. I guard it with instanceof.

Two directions. Think of an inheritance tree. Moving up to a more general type (Dog to Animal) never loses anything that the variable is promising, so it is always legal and needs no syntax. Moving down to a more specific type (Animal to Dog) claims "trust me, it really is a Dog", which the compiler cannot verify, so you must write the cast and the JVM checks it when it runs.

Animal a = new Dog();       // upcast: implicit, always safe
Dog d = (Dog) a;            // downcast: the object really is a Dog: ok
Animal c = new Cat();
Dog bad = (Dog) c;          // compiles, throws ClassCastException at run time
if (c instanceof Dog dog) { dog.bark(); }   // check + cast + variable in one (Java 16)

What the compiler checks. It rejects a cast between classes that cannot possibly be related ((String) someInteger is a compile error). Between related types it allows the cast and defers to the run-time check. With an interface, almost any cast compiles, since a subclass might implement it.

Why you might need casts, and why you should need them rarely. Casting appears when a collection holds a general type, in equals (after the type check) and when integrating legacy APIs. Generics removed most of the casts that old code needed ((String) list.get(0)). A long if (x instanceof A) ... else if (x instanceof B) ladder is a smell: either the behaviour belongs in a method on the type (polymorphism), or the set of subtypes is closed and should be a sealed hierarchy with a pattern switch, which the compiler checks for completeness.

Behaviour with generics. A cast to List<String> is "unchecked": due to type erasure the JVM cannot verify the element type, so a ClassCastException may appear later, far from the cast (heap pollution). Avoid unchecked casts, and if unavoidable, isolate them with @SuppressWarnings("unchecked") and a comment.

Numeric casts are a different operation. (int) 3.9 converts the value (3), and (byte) 300 keeps the low 8 bits (44). These never throw, they just lose information.

Since Java 16, instanceof can bind a variable in one step, which removes the repeated cast:

if (shape instanceof Circle c && c.radius() > 10) {   // c is only in scope where it is a Circle
    ...
}
String d = switch (shape) {                              // Java 21: pattern switch
    case Circle c -> "circle " + c.radius();
    case Rect r   -> "rect " + r.w();
    default       -> "other";
};

instanceof is false for null, so it also guards against null. A downcast is a design smell when it appears in long instanceof chains: that usually means the behaviour should be a polymorphic method on the type, or the hierarchy should be sealed and handled with a pattern switch. Casting a primitive is a different thing (a numeric conversion that may lose data).

Remember: upcast is free and safe, downcast is checked at run time. Check with instanceof.

5. Nested types, enums, records and sealed classes

What are the kinds of nested classes in Java, and when do you use each? Basic

There are four. A static nested class is a normal class placed inside another for organization, with no link to an outer instance. An inner (non-static) class is tied to an outer instance and can use its fields. A local class is declared inside a method. An anonymous class is a one-off class defined and instantiated in a single expression. My default is a static nested class, and I choose an inner class only when it truly needs the outer object.

Why nest a class at all. When a class is only meaningful inside another (a Node of a linked list, a Builder for a class, an Entry of a map), declaring it inside the outer class keeps the namespace clean, signals the relationship and lets it use the outer class's private members.

The costs of inner classes. Each inner instance stores an extra pointer to the outer object (a few bytes, but also a lifetime link: the outer object cannot be collected while the inner is reachable). Serialising an inner class drags the outer class in as well. Static nested classes have neither cost, so they are the default; IDEs and Sonar even suggest making an inner class static when it does not use the outer instance.

Capturing locals. Local and anonymous classes (and lambdas) may use local variables of the enclosing method only if they are final or effectively final, because the class gets its own copy of the value.

Visibility. The outer class can reach the nested class's private members and vice versa (the compiler arranges this, using nestmates since Java 11 rather than synthetic accessor methods).

The important detail is that an inner class carries a hidden reference to its outer object (a synthetic field often seen as this$0), and you create it with an outer instance: outer.new Inner(). That hidden link is convenient, but it keeps the outer object alive for as long as the inner one lives, which is a source of memory leaks. A static nested class has no such link, so the Builder in a builder pattern or Map.Entry are static nested. Local and anonymous classes can read local variables of the enclosing method only if they are final or effectively final.

Remember: default to static nested. Inner and anonymous classes hold the outer object alive.

How can an inner or anonymous class cause a memory leak? Senior

An inner or anonymous class holds a hidden reference to its outer instance. If the inner object is stored somewhere long-lived, such as a static field, a registered listener, a cache or a running thread, then the whole outer object, and everything it references, cannot be garbage collected, even if you think you are only keeping the small inner object.

The chain that causes the leak. Three facts combine. (1) A non-static inner class or an anonymous class created in an instance method holds a hidden strong reference to the enclosing object (this$0). (2) Anything reachable from a GC root is never collected. (3) Long-lived holders (a static list, a singleton's listener list, a scheduled executor, a cache, a running thread) are GC roots or reachable from them. So registering a tiny inner object in a long-lived holder pins the entire outer object, including all its large fields.

chain:  static EVENTS  ->  anonymous Listener  ->  this$0  ->  Screen  ->  byte[50 MB]

A typical story. A web or GUI screen registers a listener in start() and never calls unregister in close(). Each time the user opens a screen, 50 MB stays alive. The heap grows over hours until a full GC cannot reclaim anything and OutOfMemoryError follows. The same pattern appears with Thread subclasses, TimerTasks, callbacks given to a long-lived framework, and Handler/Runnable objects on Android.

Diagnosis recipe.

  1. Take a heap dump (jcmd PID GC.heap_dump file.hprof) or use a profiler after repeating the action several times.
  2. Find the class whose instance count keeps growing (histogram).
  3. Choose an instance and run "path to GC roots, excluding weak references". The path will list the static or thread root, then the inner class, then a this$0 edge.

Cures.

  • Declare the callback as a static nested class, or a top-level class, and pass only the small pieces of data it needs.
  • A lambda that does not mention this or an instance member captures nothing and holds no outer reference (a lambda that does use an instance member does capture this).
  • Always pair register with unregister (try/finally or a close() method), and shut down executors.
  • If the registry should not keep things alive, store WeakReferences or use a WeakHashMap or a Guava/Caffeine cache with weak keys.

Double-brace initialisation (new HashMap<>() {{ put("a", 1); }}) creates an anonymous subclass each time and, in instance code, captures the outer instance: return it from a method and you may leak the outer object. Use Map.of instead.

class Screen {
    private final byte[] bigData = new byte[50_000_000];
    void start() {
        EVENTS.register(new Listener() {          // anonymous class captures Screen.this
            public void onEvent(Event e) { ... }
        });
    }
}   // EVENTS (static) keeps every Screen and its 50 MB alive

Fixes: make the listener a static nested class (or a lambda that does not use this), hold a WeakReference to the outer if needed, and always unregister listeners and shut down executors when the owner goes away. Another trap is the "double-brace initialization" new ArrayList<>() {{ add(1); }}, which creates an anonymous subclass that captures the outer instance. Note that newer compilers (around JDK 18) can drop the hidden outer field when an inner class never uses it, so do not rely on the exact field being present or absent. A heap dump showing this$0 chains is the usual evidence.

Remember: a long-lived inner object keeps its whole outer object alive. Use static nested classes and unregister.

What is the difference between an anonymous class and a lambda? Intermediate

A lambda is a short way to write an implementation of a functional interface (one abstract method). An anonymous class can implement any interface or extend any class and can have its own fields and several methods. The key difference is this: inside an anonymous class this is the anonymous object itself, inside a lambda this is the enclosing object.

What each one is. An anonymous class is a full class without a name, defined and instantiated in one expression: new Comparator<String>() { public int compare(String a, String b) {...} }. A lambda is a compact notation for an instance of a functional interface, an interface with exactly one abstract method: (a, b) -> a.length() - b.length(). The compiler uses the target type to know which interface and method is meant.

Which to pick. Use a lambda (or better, a method reference such as String::length) for a single short behaviour. Both can leak. An anonymous class created in an instance method always captures the outer instance; a lambda captures it only if it uses this or an instance member. A lambda cannot shadow local variables, and both can capture only final or effectively final locals. Use a lambda for small behaviour passed to forEach, Comparator or Runnable; use an anonymous class (or a named class) when you need state, multiple methods, or a non-functional interface.

What is an enum in Java, and how is it different from constants in C? Basic

A Java enum is a real class with a fixed set of instances, one per constant. Each constant is a singleton object that can have fields, a constructor and methods, and enums are type safe: a method taking Status cannot be passed 7 or a random String. Compare with ==, they work in switch, and each has name(), ordinal() and values().

The problem enums solve. Before enums, a fixed set of choices was written as integer or String constants: static final int PAID = 1;. Nothing stops you passing 7, or the "wrong" group of constants, and printing gives a bare number. A Java enum declares a closed set of named values as a real type, so the compiler rejects anything else.

What an enum really is. enum Status { ACTIVE, CLOSED } compiles to a final class that extends java.lang.Enum<Status>, with one public static final instance per constant, created once when the class initializes. The constructor is private, so no one can create more. That is why == is correct for enums, and why an enum is the simplest safe singleton.

enum Planet {
    MERCURY(3.303e+23, 2.4397e6), EARTH(5.976e+24, 6.37814e6);
    private final double mass, radius;                 // each constant has its own state
    Planet(double mass, double radius) { this.mass = mass; this.radius = radius; }
    double surfaceGravity() { return 6.67300E-11 * mass / (radius * radius); }
}
Planet p = Planet.valueOf("EARTH");       // by name (IllegalArgumentException if unknown)
p.name();                                 // "EARTH"
p.ordinal();                              // 1: position in the declaration
for (Planet x : Planet.values()) { ... }  // all constants, in order
switch (p) { case EARTH -> ...; case MERCURY -> ...; }

Useful guarantees. Enums are serializable by name (no duplicate instances after deserialization), they implement Comparable (declaration order) and have a good hashCode, toString() returns the name unless overridden, and values() returns a fresh array copy each call, so cache it in a static field if you call it in a hot path.

Why ordinal() is dangerous. It is the position, so inserting or reordering constants changes it. If you store it in a database or a file, old data silently changes meaning (see the scenario on enum ordinals). Store name() or an explicit code field instead. Renaming a constant also changes name(), so for an external contract a dedicated code is the most stable.

Compared with C. A C enum is just an integer in disguise. A Java enum is an object: it can have fields, methods, implement interfaces, carry per-constant behaviour, and it cannot be created from an arbitrary number. It cannot extend another class, and nobody can extend it.

enum Status {
    ACTIVE("A"), SUSPENDED("S"), CLOSED("C");
    private final String code;
    Status(String code) { this.code = code; }     // constructor is implicitly private
    String code() { return code; }
    static Status fromCode(String c) { for (Status s : values()) if (s.code.equals(c)) return s; throw new IllegalArgumentException(c); }
}

Enums extend java.lang.Enum, so they cannot extend another class, but they can implement interfaces. valueOf("ACTIVE") parses a name and throws IllegalArgumentException for an unknown one. Serialization and reflection cannot create extra instances, and Enum.compareTo orders by declaration. Never persist ordinal(); persist a stable name or code (see the enum-ordinal scenario).

Remember: an enum is a class with a closed set of singletons. Compare with ==, store the name or code, not the ordinal.

How do you give each enum constant its own behaviour, and why use EnumMap? Intermediate

Declare an abstract method in the enum and let each constant implement it with its own body (constant-specific class body), or have the enum implement an interface. That replaces switch statements scattered across the code: adding a constant forces you to define its behaviour. EnumMap and EnumSet are fast, compact collections specialized for enum keys.

Per-constant behaviour (the strategy pattern built into the language). A scattered switch on an enum is easy to forget to update when a new constant is added. Instead put the behaviour in the enum and let each constant supply it, so the compiler forces you to provide it.

enum Shipping {
    STANDARD { long cost(long w) { return 5 + w; } },
    EXPRESS  { long cost(long w) { return 20 + 3 * w; } };
    abstract long cost(long weightKg);            // each constant must implement
}
long c = Shipping.EXPRESS.cost(4);                // 32

Each constant with a body is an anonymous subclass of the enum. Where all constants share one formula and differ only by data, plain constructor fields (EXPRESS(20, 3)) are simpler. An enum can implement an interface (enum Op implements IntBinaryOperator), which is how you let enums plug into code written against the interface.

EnumMap and EnumSet. Because an enum has a small known number of values, specialised collections exist.

Adding a default turns that check off, so avoid it unless you truly want a catch-all (and then throw for unknown rather than silently continuing).

    MUL { int apply(int a, int b) { return a * b; } };
    abstract int apply(int a, int b);
}
Map<Status, Integer> counts = new EnumMap<>(Status.class);

An EnumMap is backed by a plain array indexed by ordinal, and an EnumSet by a bit mask, so both are faster and use less memory than HashMap and HashSet, and they iterate in declaration order. In a switch expression over an enum without a default, the compiler checks that every constant is handled, so adding a new constant gives a compile error where you forgot it. A default branch hides that safety net.

Remember: behaviour in the constant beats switch statements. Use EnumMap and EnumSet for enum keys.

What is a record, and what does the compiler generate for you? Intermediate

A record (final in Java 16) is a compact way to declare an immutable data carrier. record Point(int x, int y) {} gives me private final fields, a canonical constructor, accessors x() and y(), and equals, hashCode and toString based on all components. It replaces boilerplate-heavy value classes and DTOs.

The problem. A plain data holder (a coordinate, a DTO, a map key) needs fields, a constructor, getters, equals, hashCode and toString. That is thirty lines of boilerplate that must be kept in sync and are easy to get wrong (a forgotten field in equals). A record states only the components and the compiler writes the rest.

record Point(int x, int y) { }

Point p = new Point(1, 2);
p.x();                         // 1  (accessor, not getX)
p.equals(new Point(1, 2));     // true: compares every component
p                              // prints: Point[x=1, y=2]
p.hashCode() == new Point(1, 2).hashCode();  // true

What you get exactly. A private final field per component; a canonical constructor with all components; accessors named after the components; and value-based equals, hashCode and toString. The class is implicitly final, extends java.lang.Record, and cannot declare other instance fields.

Customising it.

  • Compact constructor (no parameter list): runs before the fields are assigned. Validate or normalise the parameters here, and the compiler then assigns them.
  • Extra constructors must delegate to the canonical one: Point() { this(0, 0); }.
  • Methods and static members are allowed (double dist() { ... }, static Point origin()). You may override an accessor or toString.
  • Interfaces can be implemented, which pairs well with sealed interfaces.
record Range(int lo, int hi) {
    Range {                                  // compact constructor
        if (lo > hi) throw new IllegalArgumentException(lo + " > " + hi);
    }
}

Shallow immutability: the key caveat. The fields are final but a component that is a mutable object is still mutable. record Order(List<String> items) lets the caller keep the original list and change it later, which changes the record's equals and hashCode. Copy in the compact constructor (items = List.copyOf(items);) and return only immutable types.

Where records fit. DTOs, API responses, value objects, composite map keys (record Key(String tenant, long id)), multiple return values, and stream pipelines. Not for JPA entities (they need a no-arg constructor, mutability and proxies), or for classes with behaviour tied to hidden state. Jackson and most libraries support records in recent versions (check the version you use). Records also deconstruct in patterns: if (o instanceof Point(int x, int y)) (Java 21).

record Order(String id, List<String> items) {
    Order {                                   // compact constructor: validate and copy
        if (id == null || id.isBlank()) throw new IllegalArgumentException("id");
        items = List.copyOf(items);           // defensive copy, immutable
    }
    boolean isEmpty() { return items.isEmpty(); }
}

Limits: a record is implicitly final, cannot extend a class (it can implement interfaces), cannot declare extra instance fields, and its accessors are named x() not getX(), which some older frameworks must be told about. It is shallowly immutable: a record holding a mutable List or Date is only as immutable as that component, hence the defensive copy. Records are a good fit for value objects, map keys, API responses and stream results, and not for entities that change, nor for classes needing a framework-required no-argument constructor.

Remember: record = immutable data class with equals, hashCode and toString free. Copy mutable components.

What are sealed classes and interfaces, and why were they added? Senior

A sealed type (final in Java 17) lists exactly which classes may extend or implement it, using permits. Normally a public interface is open to anyone, so the compiler can never know all the cases. Sealing closes the hierarchy, so the compiler can check a switch over it for completeness, and I get something close to a safe sum type.

The problem. Interfaces and abstract classes are open: anyone, in any package or library, can add another implementation. That is great for extension but bad when you model a fixed set of possibilities, such as the result of a payment (success, declined, error) or the node types in an expression tree. The compiler cannot know it has seen all cases, so a switch over them needs a defensive default and you find new cases only when something breaks at run time.

What sealed does. sealed ... permits A, B, C tells the compiler "exactly these types, and no others, extend me". Every permitted subtype must declare how it continues: final (no further subclasses), sealed (with its own permits), or non-sealed (opens the hierarchy again). Records and enums are implicitly final so they fit naturally. If the permitted classes are in the same file, permits may be omitted and is inferred.

sealed interface Result permits Ok, Err {}
record Ok(String data) implements Result {}
record Err(int code, String msg) implements Result {}

static String show(Result r) {
    return switch (r) {                        // no default: compiler verifies Ok and Err are covered
        case Ok ok   -> "data " + ok.data();
        case Err err -> "error " + err.code();
    };
}
// Later: add `record Timeout() implements Result {}` and update permits:
// every switch above now fails to compile until Timeout is handled.

What you gain. (1) Exhaustive pattern matching checked by the compiler: new cases cannot be forgotten. (2) A modelling tool for "one of these shapes" (algebraic data types, sum types), together with records for the "product" part. (3) A cleaner alternative to the visitor pattern for closed hierarchies. (4) Library authors can expose a type that users can consume but not extend, without making everything final.

When not to use it. If third parties are supposed to add implementations (a plugin interface), keep it open. Sealed hierarchies are best when you own all the cases and the cases change together with their consumers. A new case is a breaking change for any code with an exhaustive switch, which is intentional but must be planned in a published API.

Rules to know. Permitted subclasses must be in the same module (or the same package in the unnamed module) and must directly extend the sealed type. Sealed is checked by the compiler and also by the JVM, and reflection can list the cases (Class.getPermittedSubclasses()). It was previewed in Java 15 and 16 and final in Java 17; pattern switch that makes it shine is final in Java 21.

sealed interface Shape permits Circle, Rect {}
record Circle(double r) implements Shape {}
record Rect(double w, double h) implements Shape {}

double area(Shape s) {
    return switch (s) {                          // Java 21, no default needed
        case Circle c -> Math.PI * c.r() * c.r();
        case Rect r   -> r.w() * r.h();
    };
}

Each permitted subclass must say how it continues: final (end), sealed (restrict further) or non-sealed (reopen). Permitted subclasses must live in the same module (or same package if unnamed module). If I add a new Triangle to the permits list, every pattern switch without a default fails to compile until I handle it, which is the whole point. It is the modern alternative to the visitor pattern for closed domains such as events, commands and results.

Remember: sealed = closed hierarchy, so the compiler checks switches are exhaustive.

6. Immutability and the Object contracts

How do you build an immutable class in Java? Intermediate

Make the class final, make every field private final, provide no setters, and copy any mutable object on the way in (constructor) and on the way out (getter). Methods that "change" the object return a new one. Immutable objects are thread-safe without locks, safe as map keys, and easy to reason about.

Why bother. An object that never changes after construction cannot be corrupted by another piece of code, needs no locking when shared between threads, can be used as a hash key, can be freely cached or reused, and has exactly one state to think about. Most bugs in "mysterious change" categories disappear. The standard recipe has five steps and the usual failures are all in step 4.

  1. Make the class final (or give it only private constructors and static factories), so a subclass cannot add mutable state or override accessors.
  2. Make all fields private final.
  3. No setters and no methods that modify state. "Changing" operations return a new instance (like String.replace, or LocalDate.plusDays).
  4. Copy mutable inputs in, copy mutable outputs out. If the constructor stores the caller's List or Date and the caller keeps its reference, the caller can still change your "immutable" object. Likewise a getter must not return the internal mutable object.
  5. Do not let this escape in the constructor (starting a thread or registering a listener with this), so no one sees a partly built object.

Seeing the failure.

final class Bad { private final List<String> tags; Bad(List<String> t) { tags = t; } List<String> tags() { return tags; } }
List<String> src = new ArrayList<>(List.of("a"));
Bad b = new Bad(src);
src.add("hacked");               // b.tags() now contains "hacked"
b.tags().clear();                // and any caller can empty it

Fix: tags = List.copyOf(t); in the constructor, and return tags directly (it is immutable). Note the cost is one copy at construction, which is cheap compared with defensive copies on every read.

Modern shortcuts. A record gives steps 1 to 3 automatically, and you add the copying in a compact constructor. Use java.time types instead of Date, List.copyOf or Map.copyOf instead of copying by hand, and BigDecimal or String for values. Libraries such as Immutables or Lombok's @Value generate the boilerplate.

Trade-off. Large immutable objects that change often (a big map updated in a loop) create garbage on each change: use a mutable builder to assemble, then freeze. For true persistent updates on big structures look at persistent collections libraries. Mention also that immutability does not mean "deeply immutable": the guarantee is only as strong as the weakest component.

public final class Booking {
    private final String id;
    private final Date start;                    // Date is mutable: copy it
    private final List<String> guests;

    public Booking(String id, Date start, List<String> guests) {
        this.id = id;
        this.start = new Date(start.getTime());  // defensive copy in
        this.guests = List.copyOf(guests);
    }
    public Date start() { return new Date(start.getTime()); }   // copy out
    public List<String> guests() { return guests; }             // already immutable
}

The step people forget is the defensive copy: a final field holding a mutable object still lets the caller change that object through their own reference. Better still, use immutable types inside (java.time.LocalDate, List.copyOf, records). Do not let this escape from the constructor (for example by registering it as a listener), and make the class final or its constructor private so a subclass cannot add mutability. The cost is one new object per change, which the JVM handles well, and builders or "with" methods keep it ergonomic. String, the wrappers, BigDecimal and java.time types are immutable in the JDK.

Remember: final class, private final fields, no setters, copy mutable parts in and out.

How do Collections.unmodifiableList, List.of and List.copyOf differ? Intermediate

Collections.unmodifiableList(list) is a read-only view of the same list: if someone changes the original, the "unmodifiable" view changes too. List.of(...) (Java 9) builds a truly immutable list. List.copyOf(c) (Java 10) makes an immutable snapshot copy, and reuses the object if it is already an immutable list. For safe publishing I use List.copyOf.

  • Any modification attempt on the immutable ones throws UnsupportedOperationException.

  • Stream.toList() (Java 16) returns an unmodifiable list that allows nulls; Collectors.toList() gives a mutable ArrayList but that is not guaranteed.

The immutable collections are shallow: the list cannot change, but the elements can if they are mutable objects.

What is the contract of equals, and how do people break it? Intermediate

equals must be an equivalence relation: reflexive (x.equals(x)), symmetric (x.equals(y) exactly when y.equals(x)), transitive (if x equals y and y equals z, x equals z), consistent (same answer if nothing changed), and x.equals(null) is false. The usual breakages are symmetry and transitivity, caused by inheritance.

Five rules, in plain language. The contract of Object.equals says it is an equivalence relation on non-null objects:

  • Reflexive: x.equals(x) is true.
  • Symmetric: x.equals(y) is true exactly when y.equals(x) is.
  • Transitive: if x equals y and y equals z, then x equals z.
  • Consistent: repeated calls give the same result as long as the compared data is unchanged.
  • Non-null: x.equals(null) is false (and must not throw).

Why it matters. HashMap, HashSet, List.contains, indexOf, remove and many frameworks silently assume these properties. If they do not hold, collections behave unpredictably: list.contains(a) can be true while the same check the other way round is false.

How inheritance breaks symmetry, step by step.

class Point { final int x, y;
    public boolean equals(Object o) { return o instanceof Point p && p.x == x && p.y == y; } }
class ColorPoint extends Point { final String color;
    public boolean equals(Object o) {
        return o instanceof ColorPoint c && super.equals(o) && c.color.equals(color); } }

Point p = new Point(1, 2);
ColorPoint cp = new ColorPoint(1, 2, "red");
p.equals(cp);    // true  (a ColorPoint is a Point with the same x and y)
cp.equals(p);    // false (p is not a ColorPoint)

Fixing it by letting ColorPoint.equals ignore color when comparing to a plain Point restores symmetry but breaks transitivity: red equals plain, plain equals blue, yet red does not equal blue. In general, you cannot add a value-affecting field in a subclass and keep equals correct.

The ways out. (1) Use getClass() == o.getClass() in the parent: strict, symmetric, but it violates Liskov (a subclass instance is never equal to a parent instance, which surprises frameworks that create proxies, like Hibernate). (2) Prefer composition: ColorPoint has a Point field and a asPoint() view, not inheritance. (3) Make the classes final or use records.

Other classic violations. Comparing double with == (NaN is not equal to itself), using fields that change (breaks consistency), and equals based on resources outside the object, like a URL's DNS lookup (java.net.URL.equals does network lookups, which is why people use URI). Declaring equals(Point p) overloads rather than overrides, so a List<Point> never uses it: always write @Override.

Example: Point(x, y) and ColorPoint extends Point with a color. If Point.equals uses instanceof, then a plain point equals a color point (same x, y), but ColorPoint.equals also compares color, so the reverse is false. Symmetry is broken. If you make ColorPoint ignore color when compared to a Point, you lose transitivity (red point equals plain point equals blue point, but red does not equal blue). There is no way to extend an instantiable class and add a value component while keeping equals correct. The practical answers are: use getClass() comparison (strict) or prefer composition (the ColorPoint has a Point). Another common bug is declaring equals(Foo other), which overloads instead of overriding, and a missing @Override hides it.

Remember: reflexive, symmetric, transitive, consistent, false for null. Inheritance plus new fields breaks it.

What is the contract between equals and hashCode, and what happens in a HashMap if you break it? Basic

If two objects are equal by equals, they must return the same hashCode. The reverse is not required: different objects may share a hash (a collision). If I override equals but not hashCode, equal objects land in different buckets, so a HashMap or HashSet cannot find them: get returns null and a set holds "duplicates".

How a HashMap finds a key, step by step. This is the whole reason the contract exists.

  1. Compute h = key.hashCode(), spread its bits a little, and take h mod tableSize to choose a bucket (an array slot).
  2. Look only inside that bucket. For each entry whose stored hash matches, call key.equals(entryKey).
  3. First match wins. If none, the key is absent.

So hash is a fast filter that narrows millions of entries to a handful, and equals is the final judge. For this to work, two keys that equals considers the same must land in the same bucket, which means they must have the same hash code. Hence the contract:

  • Equal objects must have equal hash codes. (One-way rule.)
  • Unequal objects may share a hash (a collision); fewer collisions means faster maps.
  • The hash must stay the same during one run as long as the fields used by equals do not change.

What a violation looks like.

class Key { final int id; Key(int id) { this.id = id; }
    @Override public boolean equals(Object o) { return o instanceof Key k && k.id == id; } }  // no hashCode!
Map<Key, String> m = new HashMap<>();
m.put(new Key(1), "one");
System.out.println(m.get(new Key(1)));   // null (usually): default hashCode differs per object, so the bucket differs
Set<Key> s = new HashSet<>(List.of(new Key(1), new Key(1)));  // size 2 despite equals

Notice the failure is probabilistic: two different objects can land in the same bucket by luck, so tests may pass on a small map and fail in production. The default Object.hashCode is derived from object identity.

Writing a good hash. Combine the same fields used in equals, using Objects.hash(a, b, c) (convenient) or 31 * h + field (no array allocation). A constant such as return 42; is legal and correct, but every key then collides, and the map degrades to a list scan (Java 8 turns a long chain into a balanced tree, which helps only if keys are Comparable). Collisions are also a denial-of-service vector: an attacker who can choose keys (HTTP parameters) can force worst-case behaviour, which is why String.hashCode's predictability matters and tree bins were added.

Related rules. Never use mutable fields in the hash of an object that is stored in a hash collection (the entry is stranded, see the scenario). hashCode is not a unique id and the exact values are not stable between JVM versions, so never persist or send them.

A HashMap lookup is two steps: hashCode picks the bucket, then equals picks the entry inside the bucket. Break the first step and the second never gets a chance. hashCode must also stay the same while the object sits in a collection, so do not compute it from mutable fields of a key (see the mutable-key scenario). A good hash spreads values evenly: a constant return 1; is legal but turns the map into a list of collisions (a tree in Java 8+ buckets for comparable keys, still slow).

@Override public int hashCode() { return Objects.hash(id, email); }  // same fields as equals

Remember: equal objects must have equal hashes. Override both together, from the same immutable fields.

Write a correct equals and hashCode. Should you use getClass() or instanceof? Intermediate

I use the same fields in both, compare with Objects.equals for reference fields, and handle identity and null first. For the type check: getClass() is strict and keeps the contract safe in open class hierarchies. instanceof is right when the class is final, or when equality is defined by an interface for all implementers (as List does). With a final class, instanceof is simplest.

Build it in a fixed order, so you do not forget a case.

  1. if (this == o) return true; a cheap shortcut that also satisfies reflexivity.
  2. if (o == null) return false; and the type check.
  3. Cast to the type, then compare each significant field: primitives with ==, floating point with Double.compare / Float.compare, references with Objects.equals (null safe), arrays with Arrays.equals.
  4. Write hashCode using the very same fields, nothing more.

Tooling. Let the IDE, a record, Lombok (@EqualsAndHashCode, check callSuper for hierarchies) or Immutables generate them, then test with EqualsVerifier, which probes the contract (symmetry, subclasses, null fields, mutability). Performance note: Objects.hash boxes primitives and allocates a varargs array, which matters only in very hot code.

    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Customer c = (Customer) o;
    return id == c.id && Objects.equals(email, c.email);

For JPA entities, equality by database id is delicate because the id is null before saving and proxies are subclasses, so teams often use a business key or a constant hash with an id-based equals. Records and Lombok's @EqualsAndHashCode generate all this for you, but check which fields they include.

What should toString() do, and what are its traps? Basic

toString should return a short, readable description for logs and debugging, such as Order{id=42, status=PAID}. The default prints the class name and hash (Order@1b6d3586), which is useless. Traps: leaking secrets, expensive or recursive calls, and triggering database loads.

What it is for. toString() is how an object introduces itself whenever it is converted to text: string concatenation, String.valueOf, println, log placeholders (log.info("order {}", order)), debugger views and assertion failure messages. Without an override you get com.acme.Order@1b6d3586 (class name and identity hash), which tells you nothing.

@Override public String toString() {
    return "Order{id=" + id + ", status=" + status + ", items=" + items.size() + "}";
}
// Order{id=42, status=PAID, items=3}

Design guidelines.

  • Be useful and concise. Include the identifying fields and key state, not the whole object graph. A log line with 5,000 items is useless and slow.
  • Never include secrets or personal data (passwords, tokens, card numbers, health data). Logs are copied to many systems and kept for years. Mask or omit, and override toString on credential classes to return something like ****.
  • Avoid cycles. Order.toString prints customer, whose toString prints orders, which print the customer again: a StackOverflowError. Print ids of related objects.
  • Avoid side effects and I/O. With JPA, touching a lazy collection inside toString triggers a database query, or a LazyInitializationException after the session closed. Debuggers and loggers call toString at surprising moments.
  • Do not use it as a data format. Code that parses toString() breaks when someone adds a field. Provide an explicit method (toJson, format) for machine use.

Related facts. Arrays do not override it ([I@6d06d69c), use Arrays.toString or Arrays.deepToString. Records print Point[x=1, y=2]. Concatenating a null reference prints "null", it does not throw, but calling obj.toString() on null does. toString must not return null.

Never include passwords, tokens or personal data, because logs outlive code. Do not include a field that points back to the parent (a bidirectional Order to Customer to Order relation gives infinite recursion and a StackOverflowError). With ORM entities, printing a lazy collection can trigger a query or a LazyInitializationException, so print ids only. Do not depend on its exact format for logic: parsing it breaks when someone adds a field. Records, IDE generators and Lombok produce it for you.

Remember: toString is for humans and logs: short, safe, no secrets, no cycles.

Comparable versus Comparator: when do you use each, and what does "consistent with equals" mean? Basic

Comparable is the class's own natural order, written once inside the class with compareTo, for example LocalDate. Comparator is an external order passed in when sorting, so I can have many orders for one class, like sort employees by salary or by name. I implement Comparable for one obvious default order and use Comparators for everything else.

The problem. Sorting and ordered collections need a rule to answer "which comes first?". That rule can be built into the class or supplied from outside.

record Emp(String name, String dept, int salary) {}

The rules for a correct compareTo or compare. Antisymmetric (sgn(a.compareTo(b)) == -sgn(b.compareTo(a))), transitive, and consistent. The strong recommendation: also consistent with equals (compareTo == 0 iff equals). When they disagree, TreeSet and TreeMap use the comparison, not equals, to decide "same element". With BigDecimal, "1.0" and "1.00" are not equal but compare 0, so a TreeSet silently drops one while a HashSet keeps both.

Why subtraction is a bug. return a.age - b.age; overflows when the numbers are far apart (for example Integer.MAX_VALUE - (-1) becomes negative), and the result can contradict itself so sorting misbehaves. Use Integer.compare(a.age, b.age), or better Comparator.comparingInt. For nullable keys: Comparator.nullsFirst(Comparator.naturalOrder()).

Decision rule. If one order is obvious and permanent (dates, ids, version numbers) implement Comparable. For business-specific, multiple or third-party orders use Comparators, and keep reusable ones as named constants.

list.sort(Comparator.comparing(Employee::dept)
                    .thenComparing(Employee::salary, Comparator.reverseOrder())
                    .thenComparing(Employee::name));

compareTo must be antisymmetric, transitive and consistent. "Consistent with equals" means compareTo == 0 exactly when equals is true. When it is not, sorted collections behave surprisingly, because TreeSet and TreeMap use compare, not equals, to decide "same". The standard example is BigDecimal: 2.0 and 2.00 are not equal, but compare as 0, so a TreeSet keeps only one of them while a HashSet keeps both. Never write return a.x - b.x, which overflows for large values; use Integer.compare. For null fields use Comparator.nullsFirst.

Remember: Comparable = one natural order, Comparator = any order from outside. Use Integer.compare, never subtraction.

What methods does java.lang.Object have, and which ones should you care about? Basic

Every class inherits equals, hashCode, toString, getClass, clone, finalize, and wait, notify, notifyAll. In daily work I override the first three together, use getClass in equals, and the wait and notify trio only for low-level thread coordination.

Why Object matters. Every class, directly or indirectly, extends java.lang.Object, so these methods are available on every object, and a handful are meant to be overridden. Interviews ask this to see whether you know which methods have contracts and which are legacy.

  • equals, hashCode, toString: override as a set (see the contract questions).
  • getClass(): the runtime class; it is final.
  • clone(): protected and shallow; mostly avoided (next question).
  • finalize(): deprecated for removal since Java 18. It runs at an unpredictable time, or never, and slows the garbage collector. Use try-with-resources, or Cleaner as a safety net.
  • wait/notify/notifyAll: must hold the object's monitor (inside synchronized); mostly replaced by java.util.concurrent.

Remember: equals, hashCode and toString together. Avoid clone and finalize.

How does clone() work, and why is it considered broken? Senior

Object.clone() makes a shallow field-by-field copy without calling a constructor, and only works if the class implements the empty marker interface Cloneable. Shallow means inner objects are shared between original and copy, so changing a list in one changes the other. Because of that and its awkward design, I prefer a copy constructor or a static factory.

What a copy means. An object may hold primitives and references to other objects. A shallow copy makes a new outer object whose fields have the same values, so reference fields point to the same inner objects. A deep copy also duplicates the inner objects (as deep as needed).

class Team implements Cloneable {
    String name; List<String> members = new ArrayList<>();
    @Override public Team clone() {
        try { return (Team) super.clone(); }      // shallow: members list is shared
        catch (CloneNotSupportedException e) { throw new AssertionError(e); }
    }
}
Team a = new Team(); a.members.add("Asha");
Team b = a.clone();
b.members.add("Ben");
System.out.println(a.members);   // [Asha, Ben]  : both teams see the change

Why the design is considered broken (Effective Java Item 13).

  • Cloneable is an empty marker interface and does not declare clone(). The real method is on Object, protected. The flag changes the behaviour of Object.clone in a way no other interface does: without it, it throws CloneNotSupportedException (a checked exception you must catch).
  • It creates the object without calling any constructor, so invariants established by constructors are bypassed.
  • It cannot copy final fields that need a new object.
  • Subclasses must cooperate: every class in the chain must call super.clone() and not new, otherwise the copy has the wrong class.
  • Making a deep copy requires clone-ing every mutable field by hand, and getting it wrong is a silent shared-state bug.

Alternatives.

Team(Team other) {                        // copy constructor
    this.name = other.name;
    this.members = new ArrayList<>(other.members);
}
static Team copyOf(Team t) { ... }        // or a static copy factory
int[] c = arr.clone();                    // arrays are fine: shallow copy, no cast needed
List<String> l2 = List.copyOf(l);         // collections have their own copy constructors/factories

For truly deep graphs, a copy constructor per class, a serialization round-trip with a safe format (JSON mapping), or a library copier. Records and immutable types avoid the question altogether: nothing needs copying if nothing can change.

The design problems: Cloneable has no clone method (the interface does not declare it), Object.clone is protected and throws a checked exception, it bypasses constructors (so invariants may not run), and it clashes with final fields (it cannot re-assign them) and with subclasses (each class in the chain must cooperate). A deep copy means cloning each mutable field by hand. A copy constructor is plain Java, type safe and can deep-copy exactly what is needed. One exception: array.clone() is fine and idiomatic for a shallow array copy.

Team(Team other) {                              // copy constructor
    this.name = other.name;
    this.members = new ArrayList<>(other.members);  // own list, shared (immutable) elements
}

Remember: clone is shallow and awkward. Use a copy constructor and copy mutable fields yourself.

How does Java serialization work, and why do many teams avoid it? Senior

A class that implements Serializable can be turned into a byte stream with ObjectOutputStream and rebuilt with ObjectInputStream. The stream carries the class name, a serialVersionUID, and all non-transient, non-static fields. I avoid it for anything new: it is fragile across versions, slow, and deserializing untrusted bytes is a well-known remote code execution risk.

What it is. Serialization converts an object graph into a byte sequence, deserialization rebuilds it. In Java, built-in serialization works for classes that implement the marker interface Serializable and is used with ObjectOutputStream.writeObject(obj) and ObjectInputStream.readObject(). Older frameworks (RMI, HTTP session replication, some caches and queues) used it by default.

class User implements Serializable {
    private static final long serialVersionUID = 1L;
    String name;
    transient String password;           // not written
}
try (var out = new ObjectOutputStream(new FileOutputStream("u.bin"))) { out.writeObject(user); }
try (var in = new ObjectInputStream(new FileInputStream("u.bin"))) { User u = (User) in.readObject(); }
// u.password is null after reading

What gets written. The class descriptor (name, serialVersionUID, field list), then every non-static, non-transient field, recursively for all referenced objects (shared references are preserved: the same object referenced twice is written once). Every object in the graph must itself be serializable, or NotSerializableException follows.

Compatibility and versioning. On read, the stored UID is compared with the class's UID. If you did not declare one, it is derived from the class's structure, so adding a method or field changes it and old data cannot be read (InvalidClassException). With an explicit constant you may make compatible changes: adding fields (they read as default), but removing or changing a field type is not safe. Customisation hooks: writeObject/readObject private methods, readResolve (to preserve singletons and enums), writeReplace and Externalizable.

Why teams avoid it.

  1. Security. Reading a stream constructs objects and runs code during deserialization. An attacker who controls bytes can chain classes already on your classpath (a "gadget chain") to execute commands. This has caused many real CVEs. If you must deserialize, use an ObjectInputFilter allow-list (Java 9+, process-wide filter via -Djdk.serialFilter or jdk.serialFilter property).
  2. Fragility. Class shape is part of the data format, so refactoring becomes risky.
  3. Bypasses constructors and invariants, and exposes private fields in the stream.
  4. Size and speed, and it is Java only.

Better choices. JSON (Jackson), Protobuf, Avro or Thrift with an explicit schema give cross-language, versionable, safer formats. If a class must stay Serializable (legacy session or cache), declare the UID, keep a serialization proxy for important invariants, and test old-to-new reads. Records can be serialized, with deserialization going through the canonical constructor (so validation runs), which is safer than classes.

  • serialVersionUID: a version number. If the stored value and the current class differ, reading fails with InvalidClassException. If you do not declare it, Java computes one from the class shape, so even a harmless added method can change it. Declare it explicitly and change it only on purpose.
  • transient: a field marked transient is skipped and comes back as 0, false or null after reading. Use it for caches, threads and secrets. Static fields are never saved.
  • Constructor: the constructor of the Serializable class is not run on read, but the no-argument constructor of the first non-serializable parent is, which can surprise you.
  • Security: attackers craft streams that trigger "gadget chains" in classes on your classpath. If you must read serialized data, restrict it with an ObjectInputFilter (Java 9+).

Prefer JSON, Protobuf or Avro with an explicit schema for storage and messages. For in-memory caches that survive deployments, a changed class shape is the classic production failure (see the InvalidClassException scenario).

Remember: declare serialVersionUID, mark secrets transient, never deserialize untrusted data, prefer JSON or Protobuf.

7. Annotations and reflection

What are annotations, and how do retention and target work? Intermediate

An annotation is metadata attached to code, like @Override, @Deprecated or @Transactional. It does nothing by itself: something else reads it. @Retention says how long it survives (source, class file, or runtime), and @Target says where it may be placed (class, method, field, parameter). Frameworks such as Spring and JUnit read runtime annotations through reflection.

What an annotation is. It is a typed label that you attach to a declaration (class, method, field, parameter, package, even a type use). It carries no behaviour. A tool must read it and act. @Override is read by the compiler (an error if nothing is overridden). @Test is read by JUnit through reflection. @Getter is read by Lombok during compilation to generate code. @Transactional is read by Spring at start-up to wrap beans in a proxy.

Defining one.

@Retention(RetentionPolicy.RUNTIME)           // visible at run time
@Target({ElementType.METHOD, ElementType.TYPE})  // where it may be used
public @interface Audited {
    String action();                           // element without default: required
    int level() default 1;                     // optional element
}

@Audited(action = "transfer", level = 2)
void transfer(...) {}

// Reading it with reflection
Method m = Svc.class.getDeclaredMethod("transfer", ...);
Audited a = m.getAnnotation(Audited.class);    // null if retention is not RUNTIME
String action = a.action();

Meta-annotations (annotations about annotations).

Meta-annotationControls
@RetentionSOURCE (compiler only), CLASS (kept in the .class file but not loaded: default), RUNTIME (readable by reflection)
@Targetwhich declarations are allowed
@Inheriteda class annotation is also seen on subclasses (not on interfaces or methods)
@Repeatablethe same annotation may appear several times
@Documentedincluded in generated Javadoc

The three ways annotations are consumed. (1) The compiler itself (@Override, @FunctionalInterface, @SuppressWarnings). (2) Annotation processors run during compilation and generate code or checks (Lombok, MapStruct, Dagger). (3) Runtime reflection by frameworks (Spring, JPA, Jackson, JUnit), where the cost is paid at start-up or per call.

Pitfalls. Forgetting RUNTIME retention is the most common "my annotation is ignored" bug. Spring annotations on a method only work through the proxy, so a self-call (this.save()) from within the same class skips @Transactional. Element values must be compile-time constants. Heavy use of annotations moves logic out of sight: keep the processing code documented and tested.

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Audited { String action(); }

If you forget RUNTIME, the default retention is CLASS and reflection will never see your annotation, a common "why is my annotation ignored?" bug. Annotation elements are limited to constants, strings, enums, classes, other annotations and arrays of these. @Inherited lets a subclass see an annotation on its parent class (classes only), and @Repeatable allows the same annotation twice.

Remember: annotations are inert metadata. Use RUNTIME retention if reflection must see them.

What is reflection, what is it used for, and what does it cost? Intermediate

Reflection lets a program inspect and use classes at run time without knowing them at compile time: list a class's fields and methods, read annotations, create objects and call methods by name. Frameworks depend on it: Spring injects beans, Jackson fills fields, Hibernate maps entities, JUnit finds @Test methods. The costs are speed, safety and encapsulation.

What it lets you do. Normally the compiler needs to know types in advance. Reflection (java.lang.reflect) lets a program discover and use types at run time, by name: find a class, list its constructors, fields, methods and annotations, create instances, read and write fields, invoke methods. It is the basis of everything "magic" in Java frameworks.

How a framework uses it, in miniature. Suppose a JSON library gets {"name":"Asha"} and a target class User:

Class<User> cls = User.class;                          // or Class.forName("com.acme.User")
User u = cls.getDeclaredConstructor().newInstance();   // call the no-arg constructor
Field f = cls.getDeclaredField("name");
f.setAccessible(true);                                 // bypass private (subject to module rules)
f.set(u, "Asha");                                      // write the field
for (Method m : cls.getDeclaredMethods())
    if (m.isAnnotationPresent(PostConstruct.class)) m.invoke(u);

Spring does the same to find @Component classes, call constructors with the right dependencies, and inject @Autowired fields. Hibernate reads @Entity and @Column to map objects to tables. JUnit finds methods with @Test. Dynamic proxies (java.lang.reflect.Proxy) create implementations of interfaces at run time, which is how Spring AOP and Feign clients work.

Costs and risks.

  • Performance. A reflective call goes through access checks and argument boxing, so it was historically several times slower than a direct call. Modern JVMs optimise a lot (and reflection since JDK 18 is built on method handles), so the cost is acceptable for start-up wiring but not for tight loops. Cache Method and Field objects; use MethodHandle or generated code in hot paths.
  • Safety. Mistakes surface as run-time exceptions (NoSuchMethodException, IllegalAccessException, InvocationTargetException that wraps the real error: unwrap with getCause()). Renaming a method in the IDE does not update a string name.
  • Encapsulation. setAccessible(true) can read private data. With the module system (Java 9+, enforced by default for JDK internals since Java 16 and without the opt-out flag in 17), reflective access to java.* internals fails with InaccessibleObjectException unless the module is opened (--add-opens), and your own modules must opens packages to frameworks.
  • Native images and shrinkers. GraalVM native-image and ProGuard analyse code statically, so reflective targets must be declared in configuration or hints (Spring AOT generates them).

Guideline. Use reflection in infrastructure, libraries and tests. In business code prefer interfaces, generics and plain method calls, which the compiler can check.

Class<?> c = Class.forName("com.acme.Report");
Object r = c.getDeclaredConstructor().newInstance();
Method m = c.getMethod("run", String.class);
m.invoke(r, "daily");
  • Slower: lookups and checks cost more than a direct call. Cache the Method or Field objects, and for hot paths prefer MethodHandle or generated code.
  • No compile-time safety: a renamed method fails at run time with NoSuchMethodException, not at build time.
  • Breaks encapsulation: setAccessible(true) reads private fields. Since Java 16/17, the module system strongly encapsulates JDK internals, so such access to java.* internals fails unless explicitly opened with --add-opens.
  • Tooling: native-image compilers (GraalVM) and code shrinkers need configuration for reflective access.

Remember: reflection powers frameworks. Use it in infrastructure code, not in business logic.

8. Tricky output-prediction questions

Interviewers use these to see whether you know the rules, not whether you can guess. For each one, say the rule out loud before the answer.

What does this print? String a = "hello"; String b = "hel" + "lo"; String c = "hel"; String d = c + "lo"; print(a == b, a == d, a == d.intern()); Intermediate

It prints true false true. "hel" + "lo" is a constant expression, so the compiler joins it into the literal "hello", which is the pooled object, so a == b. c + "lo" uses a variable, so it is built at run time as a new object, so a == d is false. d.intern() returns the pooled "hello", so the last one is true.

Trace each line like the compiler does.

  1. String a = "hello"; the literal goes into the pool, a points to the pooled object (call it P).
  2. String b = "hel" + "lo"; both operands are literals, so this is a constant expression (JLS 15.29). javac evaluates it during compilation and stores the single literal "hello". b also points to P. So a == b is true.
  3. String c = "hel"; String d = c + "lo"; c is an ordinary variable. javac cannot assume it will not change, so the join happens at run time and creates a new String object D on the heap. a == d is false.
  4. d.intern() looks up "hello" in the pool, finds P and returns it. a == d.intern() is true.

Variations that are asked next.

final String c2 = "hel";            // constant variable: final, initialised with a constant expression
String e = c2 + "lo";
a == e;                              // true : e is folded at compile time too

final String c3 = getPrefix();      // final but not a constant expression
(c3 + "lo") == a;                    // false

a == new String("hello");            // false
a.equals(new String("hello"));       // true

Take-away. The behaviour depends on whether the compiler can prove the value is constant, which is far too subtle to rely on. In real code, compare strings with equals. In an interview, say the rule ("constant expressions are folded and pooled, anything computed at run time is a new object") and then say you would never depend on it.

A twist interviewers add: if c were declared final String c = "hel";, then c + "lo" is also a compile-time constant and a == d becomes true. Either way, the real answer in code is to compare with equals.

Remember: constants are joined at compile time and pooled, run-time concatenation makes a new String.

What does this print? Integer a = 100, b = 100, c = 1000, d = 1000; print(a == b, c == d, c.equals(d)); Long l = 127L; print(l.equals(127), l.equals(127L)); Intermediate

First line: true false true (100 is cached, 1000 is not, equals compares values). Second line: false true. l.equals(127) boxes 127 as an Integer, and Long.equals returns false for any argument that is not a Long, even with the same numeric value.

Line 1, in three comparisons. Integer a = 100, b = 100; both come from Integer.valueOf(100), inside the -128..127 cache, so they are one shared object and a == b is true. Integer c = 1000, d = 1000; is outside the cache, so valueOf creates two objects and c == d is false (the reference comparison). c.equals(d) compares the numeric value and is true.

Line 2, why l.equals(127) is false.

  1. Long l = 127L; is a Long object.
  2. The argument 127 is an int literal. equals takes Object, so it is boxed to Integer.valueOf(127). No widening to long happens, because boxing of the primitive int gives an Integer.
  3. Long.equals(Object o) is implemented as o instanceof Long && value == ((Long) o).longValue(). An Integer is not a Long, so the result is false, even though the numbers match.
  4. l.equals(127L) boxes to a Long, same type and value, so it is true.

The production version of this bug.

Map<Long, String> users = new HashMap<>();
users.put(5L, "Asha");
int id = 5;
users.get(id);          // null! the key is boxed as Integer, which is never equal to Long 5
users.get((long) id);   // "Asha"
Set<Long> ids = new HashSet<>(List.of(1L));
ids.contains(1);        // false
ids.remove(1);          // false, removes nothing

Collections' get, contains and remove accept Object, so the compiler does not warn. The fixes are the L suffix, an explicit cast, or declaring the variable as long so it is boxed to Long. Related: new Long(1).equals(1), Short versus Integer, and Double versus Float all behave the same way.

That second point is a real bug source: longValue.equals(intValue) is always false, and map.get(intKey) on a Map<Long, ...> never finds anything. Write 127L, or convert explicitly.

Remember: wrapper equals checks the type too. Integer(5) is not equal to Long(5).

What do these print? print('a' + 'b'); print("" + 'a' + 'b'); print('a' + 1); print((char)('a' + 1)); char c = 'a'; c += 1; print(c); Intermediate

They print 195, ab, 98, b, b. A char is a number, so adding two chars or a char and an int gives an int (97 + 98 = 195). Once a String is on the left, + is concatenation. To get a char back you cast. c += 1 works without a cast because compound assignment includes an implicit cast.

Rules to apply one at a time.

  1. 'a' + 'b': both operands are char. Arithmetic promotes them to int (97 and 98), the sum is the int 195, and println(int) prints 195.
  2. "" + 'a' + 'b': evaluated left to right. "" + 'a' is a String concatenation giving "a", then "a" + 'b' gives "ab". Once a String is on the left, + always concatenates.
  3. 'a' + 1: char plus int promotes to int: 98.
  4. (char) ('a' + 1): the cast turns 98 back into the character with code 98, which is 'b'. println(char) prints b.
  5. char c = 'a'; c += 1;: compound assignment E1 op= E2 means E1 = (T) (E1 op E2), with an implicit cast to the type T of E1. So c becomes 'b' with no cast written.
char c = 'a';
// c = c + 1;       // compile error: possible lossy conversion from int to char
c += 1;              // ok: implicit cast
c++;                 // ok, now 'c'
final char k = 'a';
char d = k + 1;      // ok! k + 1 is a constant expression whose value fits in char

System.out.println((char) 65);        // A
System.out.println('a' < 'b');         // true (compares numbers)
for (char x = 'a'; x <= 'e'; x++) System.out.print(x);   // abcde
System.out.println("" + 'a' + 1);     // a1

Why it matters. Building a string like 'a' + 'b' + "c" prints "195c" (the first two are added as numbers). Interviewers use this to check that you know promotion rules: byte, short and char operands become int before any arithmetic, and the implicit cast in compound assignment is the one exception that lets you shrink without writing a cast.

Which means c = c + 1 does not compile (int to char needs a cast), but c += 1 and c++ do. The same implicit narrowing applies to byte b = 10; b += 5;.

Remember: char arithmetic gives int. Compound assignment casts back silently.

What do these return? int f() { try { return 1; } finally { return 2; } } and int g() { int x = 1; try { return x; } finally { x = 2; } } Intermediate

f() returns 2 and g() returns 1. finally always runs before the method really returns. A return inside finally replaces the earlier return (and even swallows an exception). In g, the return value 1 is saved before finally runs, so changing the variable x afterwards does not change what is returned.

How a return really works. When a method hits return expr, it first evaluates expr and stores the value in a temporary slot. If the return is inside a try with a finally, the JVM then runs the finally block, and afterwards completes the return with the saved value, unless the finally block itself completes abruptly (with its own return, throw, break or continue), which replaces everything.

Trace both methods.

int f() { try { return 1; } finally { return 2; } }
// 1. evaluate 1, save it
// 2. run finally: return 2 -> this overrides the saved value
// result: 2

int g() { int x = 1; try { return x; } finally { x = 2; } }
// 1. evaluate x, which is 1, save the VALUE 1 (primitive copy)
// 2. run finally: x = 2 changes the local only
// 3. return the saved 1
// result: 1

If g returned a mutable object (a StringBuilder) and finally appended to it, the caller would see the append, since the saved value is the reference and the object is the same. That is the difference between changing a variable and changing an object.

The swallowed exception trap.

int h() {
    try { throw new IllegalStateException("real problem"); }
    finally { return 0; }       // exception disappears, method returns 0
}

Compilers and linters warn (-Xlint:finally, Sonar S1143). Similarly, an exception thrown from finally replaces the one from the try, losing the root cause; try-with-resources solves this by attaching the cleanup exception as suppressed (getSuppressed()).

When finally does not run. System.exit(), Runtime.halt(), the JVM crashing, the thread being killed at the OS level, or an infinite loop or deadlock inside the try. Daemon threads in progress at JVM exit also do not finish their finally blocks.

Rules to state: finally runs after a return, a break or an exception; it does not run if the JVM exits (System.exit), the thread is killed, or the try never ends. Never return, break or throw from finally, since it hides the original exception. For cleanup, prefer try-with-resources.

Remember: the return value is captured first, finally runs next, and a return in finally wins.

What prints for m(null) when you have m(Object) and m(String)? And if you also add m(Integer)? Senior

With m(Object) and m(String), it prints "String": null fits both, and the compiler picks the most specific parameter type. After adding m(Integer), the call no longer compiles: String and Integer are unrelated, neither is more specific, so the call is ambiguous.

How the compiler picks an overload. It works in three phases and stops at the first phase that finds at least one applicable method:

  1. Strict: identity and widening primitive or reference conversions only (no boxing, no varargs).
  2. Loose: boxing and unboxing allowed.
  3. Variable arity: varargs methods.

Within the phase, if several methods apply, it chooses the most specific: method A is more specific than B if A's parameter types can all be passed to B. String is more specific than Object, since every String is an Object.

static void m(Object o)  { System.out.println("Object"); }
static void m(String s)  { System.out.println("String"); }
m(null);           // String: both apply, String is more specific
m("x");            // String
m((Object) "x");   // Object: declared type decides, not the runtime type
// adding: static void m(Integer i) { ... }
// m(null);        // error: reference to m is ambiguous (String and Integer are unrelated)

Other classics with the same rules.

static void p(long x)    { System.out.println("long"); }
static void p(Integer x) { System.out.println("Integer"); }
static void p(int... x)  { System.out.println("varargs"); }
p(5);              // long: phase 1 (widening int to long) beats boxing in phase 2
p(Integer.valueOf(5));  // Integer: exact in phase 1

Also print(char[]) versus print(Object) with print(null) picks char[]. And sb.append(null) on a StringBuilder is ambiguous (String, StringBuffer, char[], CharSequence overloads), which is why you cast it.

Design rule. API designers should avoid overloads that become ambiguous for null or differ only in related reference types. Prefer distinct names (removeAt, removeValue) or Optional where it helps.

Overload resolution happens in phases: first exact matches and widening only; then boxing and unboxing; then varargs. The first phase that finds any candidate wins, and within it the most specific method is chosen. That is why m(long) beats m(Integer) for the argument 5 (widening beats boxing), and m(int...) comes last. To resolve the ambiguity, cast the argument: m((String) null).

Remember: most specific type wins, widening before boxing before varargs, unrelated types make it ambiguous.

What is i after int i = 5; i = i++ + ++i;, and after int j = 5; j = j++;? Intermediate

i is 12 and j is 5. Java evaluates operands left to right. i++ gives the old value 5 and sets i to 6. Then ++i makes i 7 and gives 7. The sum 5 + 7 = 12 is then assigned to i, overwriting everything. For j = j++, j++ returns 5 and increments j to 6, but then the assignment writes the old 5 back.

Rules. Java evaluates operands strictly left to right. i++ (post-increment) yields the old value and then increments the variable. ++i (pre-increment) increments first and yields the new value. The assignment i = expr happens last and overwrites whatever the variable currently holds.

Second case, j = j++. The right side yields 5 and sets j to 6, then the assignment stores 5 into j. The increment is lost, so j is 5. It is a no-op in effect.

int k = 5;
int a = k++;      // a = 5, k = 6

Why interviewers ask. In C and C++ similar expressions are undefined, so the answer depends on the compiler. In Java the order is precisely defined, which a good candidate knows. Also mention that i++ on a field, from several threads, is a read-modify-write and is not atomic (use AtomicInteger.incrementAndGet() or a lock). And never write such expressions in real code: one modification per statement.

Unlike C, Java defines this order, so the answer is the same on every JVM. In real code, never use an incremented variable twice in one expression.

Remember: post-increment returns the old value, pre-increment the new one, and the final assignment overwrites.

What does this print? Object o = true ? 1 : 2.0; print(o); And what happens with Integer n = null; int x = flag ? n : 0;? Senior

The first prints 1.0, not 1. If the two branches of a ternary are numeric, Java applies numeric promotion to a common type, here double, even though the value is assigned to an Object. The second throws a NullPointerException when flag is true: with an Integer and an int branch, the result type is int, so n is unboxed, and unboxing null fails.

The typing rules of cond ? a : b. The type of the whole conditional expression is decided at compile time from the types of a and b, not from where the result is stored.

  • If both are the same type, that type is the result.
  • If one is a primitive (or a wrapper convertible to numeric) and the other numeric, binary numeric promotion applies: int and double give double.
  • If one is int and the other a boxed Integer, the result is int (the Integer is unboxed).
  • If both are references (or one is null), the result is a reference type with no unboxing.

First case. true ? 1 : 2.0 has int and double operands, so the type is double. The value 1 is promoted to 1.0 before it is boxed into a Double that is stored in o. Printing shows 1.0. Compare true ? Integer.valueOf(1) : "x", whose result is Object and prints 1.

Second case, the NPE.

Integer n = null;
int x = flag ? n : 0;          // operands: Integer and int -> type int
//   flag true: n is unboxed via n.intValue() -> NullPointerException
Integer y = flag ? n : Integer.valueOf(0);   // both Integer: no unboxing, y = null
Integer z = flag ? n : null;                 // fine, z = null
Integer w = (n != null) ? n : 0;             // safe

It also bites in the common pattern Integer v = map.containsKey(k) ? map.get(k) : 0;: if the map holds a null value for the key, the result type is int, so the null is unboxed and throws.

How to avoid. Keep both branches the same type, use Optional or getOrDefault, and be wary of ternaries with mixed boxed and primitive operands. Compilers do not warn by default, but SpotBugs does (NP_NULL_ON_SOME_PATH).

Both are hidden-conversion bugs. The fix for the second is to avoid mixing: Integer x = flag ? n : Integer.valueOf(0); or int x = (n != null) ? n : 0;. When two branches are both reference types (or one is null), no unboxing happens.

Remember: a ternary with mixed numeric types promotes and unboxes. Unboxing null throws.

What is the list after this? List<Integer> list = new ArrayList<>(List.of(10, 20, 30, 1)); list.remove(1); list.remove(Integer.valueOf(1)); Intermediate

The result is [10, 30]. list.remove(1) picks the overload remove(int index) (an exact primitive match), so it removes the element at index 1, which is 20. remove(Integer.valueOf(1)) picks remove(Object), so it removes the value 1.

Why there are two removes. List has remove(int index) and, inherited from Collection, remove(Object o). For a List<Integer> both look like remove(1). Overload resolution runs the strict phase first (no boxing): the argument 1 is an int and remove(int) matches exactly. The remove(Object) overload would need boxing, which belongs to the second phase, so it is never considered.

List<Integer> l = new ArrayList<>(List.of(5, 6, 7));
l.remove(Integer.valueOf(6));   // by value  -> [5, 7]
l.remove((Integer) 5);          // by value  -> [7]
l.remove((int) 0);              // by index  -> []

Habit. When a collection's element type is Integer and you call remove, say out loud "index or value?" and write the box explicitly for the value case. Also remember that removing while iterating with a for-each loop throws ConcurrentModificationException; use removeIf or an Iterator.

The same trap exists on Set: set.remove(1) on a Set<Long> removes nothing, because 1 is an Integer, not a Long. Method resolution picks the overload before any boxing is considered.

Remember: remove(int) is by index, remove(Object) is by value. Box explicitly when you mean value.

What do long a = 1 << 40;, int b = Integer.MAX_VALUE + 1; and long c = 24 * 60 * 60 * 1000 * 1000; give? Senior

They give 256, -2147483648 and 500654080, all wrong for the intent. In each case the arithmetic is done in int first and only then widened to long, so the overflow has already happened. The shift distance for an int is taken modulo 32, so 1 << 40 is 1 << 8.

The rule. The type of an arithmetic expression is decided by its operands only. If both operands are int, the arithmetic is done in 32 bits, and the result, already overflowed, is widened to long afterwards if assigned to a long. The target type on the left of = never changes how the right side is calculated.

Case 1: long a = 1 << 40; For an int left operand, the shift distance is masked to the low 5 bits (distance mod 32): 40 & 31 = 8. So the expression is 1 << 8 = 256. With 1L << 40 a long shift uses mod 64 and gives 1,099,511,627,776.

Case 2: int b = Integer.MAX_VALUE + 1; 2,147,483,647 + 1 wraps around to -2,147,483,648 in two's complement. No error, no warning.

Case 3: 24 * 60 * 60 * 1000 * 1000 The true value is 86,400,000,000. Evaluated left to right in int: 24*60 = 1440, *60 = 86,400, *1000 = 86,400,000 (fits), *1000 = 86,400,000,000, which does not fit in 32 bits. The int result is 86,400,000,000 mod 2 to the power 32, shown as a signed number: 500,654,080. Then it is widened to long. With 24L * 60 * 60 * 1000 * 1000, the first multiplication is already long, and the rest follow.

long micros = 24L * 60 * 60 * 1000 * 1000;   // 86400000000
long bits   = 1L << 40;
long sum    = Integer.MAX_VALUE + 1L;         // 2147483648
long safe   = Math.multiplyExact(100_000, 100_000);  // int overload: throws ArithmeticException
long safe2  = Math.multiplyExact(100_000L, 100_000);  // long overload: 10_000_000_000

Where this appears in real code. Timeouts and sizes in constants (int ONE_DAY_MS = 24*60*60*1000 is fine, 25 days is not: 25*24*60*60*1000 overflows), computing file sizes (blocks * blockSize), time arithmetic with Date, and bit flags (1 << 31 is negative; use 1L or BitSet for more than 31 flags). The compiler does not warn about constant overflow, so rely on *Exact methods, long literals and tests with big values.

The fix is to make one operand long before the operation: 1L << 40, Integer.MAX_VALUE + 1L, and 24L * 60 * 60 * 1000 * 1000 (that is 86,400,000,000 microseconds per day). The assignment target type does not influence how the right-hand side is calculated. Constants that would overflow in an int are still allowed by the compiler: it does not warn.

Remember: widening happens after the arithmetic. Put the L on the operand, not on the variable.

9. Coding-style questions

Write a thread-safe singleton. What are the options and which do you choose? Intermediate

My first choice is a single-constant enum: it is thread-safe, serialization-safe and reflection-safe in three lines. If I need a normal class, I use the lazy holder idiom. I avoid the hand-written double-checked locking unless needed. In a Spring application I simply let the container manage a singleton bean.

What a singleton is and why people regret it. A singleton class allows exactly one instance in the JVM and gives global access to it. It is useful for things that truly exist once (a registry, a configuration object). The cost is hidden global state: it is hard to test (cannot swap it for a fake), couples classes to a concrete type and, if mutable, needs thread-safety. In frameworks the container's singleton scope gives the "one instance" without the downsides, so hand-written singletons are mostly for libraries and small utilities.

Three ways, and what each guards against.

Why double-checked locking needs volatile. inst = new Cache() is three steps: allocate memory, run the constructor, store the reference into inst. Without volatile the JIT or CPU may reorder steps 2 and 3, so another thread might see a non-null inst whose constructor has not finished and use a half-built object. The first check outside the lock is for speed (no lock once initialised) and the second inside the lock prevents two threads creating two instances. Volatile forbids that reordering (and since Java 5 the memory model makes it correct).

Ways a normal singleton is broken. Reflection (setAccessible(true) on the private constructor, so throw if an instance exists), serialization (a read creates a new object, fix with readResolve() { return INSTANCE; }), cloning (do not implement Cloneable), and multiple class loaders (each loader has its own "singleton", relevant in app servers and OSGi).

Say in an interview. "Enum if I can, holder idiom if I need a class, DCL only with volatile. In Spring I let the container manage the singleton scope and inject it, which keeps it testable."

// 1. Enum: the simplest and safest
enum Registry { INSTANCE; public void register(String s) { ... } }

// 2. Holder: lazy, thread-safe, no locks (class init is guarded by the JVM)
final class Config {
    private Config() {}
    private static class Holder { static final Config I = new Config(); }
    static Config get() { return Holder.I; }
}

// 3. Double-checked locking: must use volatile
final class Cache {
    private static volatile Cache inst;
    static Cache get() {
        if (inst == null) { synchronized (Cache.class) { if (inst == null) inst = new Cache(); } }
        return inst;
    }
}

Why volatile in option 3: without it another thread can see the reference before the object is fully built (reordering). A plain eager static final instance is also fine when creation is cheap. Ways to break a normal singleton: reflection calling the private constructor, deserialization creating a copy (fix with readResolve), and multiple class loaders. An enum is immune to the first two. Mention the trade-off too: singletons are global state and make testing harder, so prefer dependency injection.

Remember: enum first, holder second, double-checked locking only with volatile.

Write a builder for a class with many optional fields. Why use one? Intermediate

A builder fixes two problems: constructors with many parameters are unreadable (new User("a", null, 0, true, null)), and setters leave an object half-built and mutable. The builder collects values by name, validates once in build(), and produces an immutable object.

Which problems it fixes. Compare three ways of making a User with name, email, age, phone, active flag:

  • Telescoping constructors: new User("a", null, 0, null, true). You must remember positions, and many overloads are needed.
  • JavaBean setters: u.setName(..); u.setAge(..);. The object is half-built between calls, cannot be immutable and is awkward across threads.
  • Builder: named, optional steps, validation in one place, then an immutable object.

How the code works. The builder is a separate (static nested) class with the same fields. Each setter-like method stores the value and returns this so calls can be chained (a fluent interface). build() performs the cross-field validation and calls the private constructor of the real class, which copies the values into its final fields. Because the target class has only a private constructor taking a builder, the only way to create it is through the builder, so an invalid or half-built User cannot exist.

User u = User.builder("Asha")        // required: in the builder's factory
             .email("a@x.com")
             .age(30)
             .build();               // validate, then freeze

// invalid usage is rejected at build time:
User.builder("Ben").age(-1).build();   // IllegalArgumentException("age")

Design details.

  • Required parameters belong in the builder's constructor or factory, so you cannot forget them; optional ones are setters with defaults.
  • Copy mutable inputs (a List) in build() so the builder can be reused without affecting built objects.
  • Offer toBuilder() to produce a modified copy of an immutable object (a "with" pattern).
  • For inheritance, use a generic self-typed builder (Builder<T extends Builder<T>>), but that is complex, which is one more reason to avoid deep hierarchies.

When not to use it. With two or three parameters, a constructor or a record is clearer. With records, a compact constructor validates, and a static factory can give names to common variants. For test data, a builder with sensible defaults is very valuable (the "test data builder" pattern). Lombok's @Builder and the Immutables library remove the boilerplate; the builder is also what Spring, Jackson (@JsonPOJOBuilder) and many SDKs expose (HttpRequest.newBuilder()).

public final class User {
    private final String name; private final String email; private final int age;
    private User(Builder b) { name = b.name; email = b.email; age = b.age; }

    public static Builder builder(String name) { return new Builder(name); }   // required field up front

    public static final class Builder {
        private final String name; private String email; private int age;
        private Builder(String name) { this.name = name; }
        public Builder email(String e) { this.email = e; return this; }
        public Builder age(int a) { this.age = a; return this; }
        public User build() {
            if (age < 0) throw new IllegalArgumentException("age");   // validate here
            return new User(this);
        }
    }
}
User u = User.builder("Asha").email("a@x.com").age(30).build();

Required fields go in the builder's constructor so they cannot be forgotten. Alternatives: records with a compact constructor when there are few fields, static factory methods for named variants, and Lombok's @Builder to avoid writing it by hand. Copy mutable collections inside build().

Remember: a builder gives readable calls, validation in one place and an immutable result.

Sort a list of employees by department, then by salary descending, then by name. How do you write it, and what can go wrong? Intermediate

I chain comparators: comparing for the first key, then thenComparing for each tiebreaker. Salary descending is Comparator.reverseOrder() applied to that one key, not to the whole chain. The sort is stable, so equal elements keep their original order.

Building blocks of the Comparator API.

  • Comparator.comparing(keyExtractor) sorts by a key using that key's natural order. comparingInt/Long/Double avoid boxing for primitive keys.
  • .thenComparing(...) is the tie-breaker, used only when all earlier comparators say "equal".
  • comparing(key, keyComparator) and thenComparing(key, keyComparator) let you choose the order of that key only, e.g. Comparator.reverseOrder().
  • .reversed() reverses the whole comparator built so far.
  • nullsFirst(c) and nullsLast(c) wrap a comparator so null keys do not throw.

Worked example with data.

record Employee(String name, String dept, int salary) {}
List<Employee> list = new ArrayList<>(List.of(
    new Employee("Zed",  "IT", 90), new Employee("Amy", "HR", 70),
    new Employee("Bob",  "IT", 90), new Employee("Cat", "IT", 120)));

list.sort(Comparator.comparing(Employee::dept)
        .thenComparing(Employee::salary, Comparator.reverseOrder())
        .thenComparing(Employee::name));
// HR Amy 70 | IT Cat 120 | IT Bob 90 | IT Zed 90
//  dept asc    salary desc (120 before 90)    name asc breaks the 90-90 tie (Bob before Zed)

If you wrote .thenComparing(Employee::salary).reversed().thenComparing(Employee::name) the reversal would also flip the department order, producing a different, wrong result: reversed applies to everything to its left.

Stability. List.sort and Collections.sort use a stable merge-based algorithm (TimSort) for objects, meaning elements that compare equal keep their previous relative order. This lets you sort in several passes (sort by name, then stable-sort by department) and is why a sort by one key does not scramble earlier ordering. Arrays.sort on primitive arrays uses dual-pivot quicksort (stability is irrelevant for primitives).

Performance and correctness notes. Comparator.comparing(Employee::dept) calls the key extractor on every comparison, O(n log n) times; for expensive keys, precompute (a decorate-sort-undecorate pattern). Keep comparators consistent and never use subtraction. For a query-like ordering in a large data set, sort in the database (ORDER BY with an index) instead of loading everything into memory.

employees.sort(
    Comparator.comparing(Employee::dept)
              .thenComparing(Employee::salary, Comparator.reverseOrder())
              .thenComparing(Employee::name));

What can go wrong: a null dept or name throws NPE, so wrap that key with Comparator.nullsFirst(...) or nullsLast. Putting .reversed() at the end of the chain flips every key, not just the last, which is a common mistake. Subtraction comparators (a.salary - b.salary) can overflow. The comparator must be consistent (transitive); otherwise TimSort can throw "Comparison method violates its general contract". For primitives, use comparingInt and comparingDouble to avoid boxing.

Remember: comparing(...).thenComparing(...), reverse per key, handle nulls, never subtract.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

Users with an id above 127 are "not found" in production, but tests pass. What is going on? Intermediate

Someone compared two Integer or Long ids with ==. Small test ids hit the box cache (-128..127) and are the same object, large production ids are not. I replace it with Objects.equals or unbox to primitives, and add a test with an id of 1000.

Why it happens, in one trace. Test data: user.getId() is 5 and resource.getOwnerId() is 5. Both are Long objects produced by Long.valueOf(5), which returns the cached instance, so == compares the same arrow and is true. Production data: id 4,201, each boxing makes a new object, so == compares two different arrows and is false. The check "is this user the owner?" returns false only for users with ids above 127, which is why it looks random.

How to prove it quickly. In a jshell or unit test: Long a = 4201L, b = 4201L; System.out.println(a == b); prints false while a.equals(b) prints true. If the fields come from JSON or a database mapper, they may be wrappers because the column is nullable, which is exactly the reason the code uses a wrapper type in the first place.

A safer pattern. If the ids can never be null, change the field and getter to long. Then == is a numeric comparison and the bug cannot exist. If null is possible, use Objects.equals(a, b) (treats two nulls as equal, which may or may not be what you want; for permission checks you usually want null to deny).

Situation: a permission check does if (user.getId() == resource.getOwnerId()) and both are wrapper types. In tests the ids are 1, 2, 3, so == is true. In production the ids are large, each is a different object, and the check silently fails. It worked for a year until a table passed 127 rows.

Check first: grep for == and != on wrapper-typed fields. Reproduce with an id of 1000. Ask why the id is a wrapper at all (a nullable column or JSON field, probably).

Fix: Objects.equals(a, b), or use long where null is impossible.

Prevent: static analysis (Error Prone ReferenceEquality, SpotBugs RC_REF_COMPARISON, Sonar), tests with large ids on purpose, a rule to prefer primitives for non-null values.

Remember: tests with small numbers hide wrapper == bugs. Test with 1000.

A login check works for hard-coded test users but fails for users from the database. What do you look at? Basic

Almost certainly role == "ADMIN". A hard-coded literal is the pooled object, so == matches; a String read from a database or JSON is a fresh object, so it does not. Use "ADMIN".equals(role), or better, model roles as an enum.

Why it happens. A String literal in the source is interned in the pool when the class is loaded, so the test "ADMIN" and the "ADMIN" in the code are the same object and == is true. A role read from a database column, a JSON body or a request header is built by the library at run time into a new String, so it is a different object with the same characters, and == is false. The code was correct only by coincidence of the test setup.

Quick check. Print role.equals("ADMIN") and role == "ADMIN" side by side with a value read from the database. You will see true and false.

Why not intern? Calling intern() on every incoming value makes == work but costs a pool lookup per call and keeps the habit of using an unsafe operator. Putting the literal first, "ADMIN".equals(role), is also null-safe. Better, convert once at the boundary: Role r = Role.valueOf(text), after which the code compares enum constants with == correctly, and an unknown value fails fast at the edge instead of denying silently.

Situation: the test passes the literal "ADMIN", the same pooled instance as the one in the code. The real value arrives as a new String from the driver or parser, so identity comparison is false even though the characters match.

Check first: grep for == " and != ".

Fix: "ADMIN".equals(role) (literal first is also null-safe). For fixed vocabularies, an enum makes == correct and typos compile errors. Do not "fix" it by sprinkling intern().

Prevent: lint rules, review, and enums for fixed sets of values.

Remember: == on Strings works only by accident. Use equals or an enum.

A HashMap entry exists (you can see it when you print the map), but get(key) returns null. Why? Senior

The key was mutated after it was inserted, and its hashCode depends on the changed field. The entry still sits in the bucket for the old hash, but get now looks in the bucket for the new hash and finds nothing. Iteration still shows it, which is why it looks like a ghost. I use immutable keys.

Replay the sequence with numbers. Say Account.hashCode() returns Objects.hash(id, status).

  1. map.put(acc, report) with status OPEN: hash is 3, the entry goes into bucket 3 and the entry stores that hash value.
  2. acc.setStatus(CLOSED): the object's hash would now be 7. Nothing in the map is updated, because the map does not know the key changed.
  3. map.get(acc): the map computes the hash again, gets 7, looks in bucket 7, finds nothing, returns null. Even if it did reach the right bucket, the stored hash (3) would not match.
  4. System.out.println(map) and iteration walk all buckets, so they still show the entry. It is stranded, not deleted.

Consequences. containsKey is false, put of the same key adds a second entry (a duplicate), remove fails to remove, and the stranded entry can only be reached by iterating. It also leaks memory. The same applies to elements of a HashSet and to keys of HashMap-backed structures such as ConcurrentHashMap. For TreeMap, mutating the field that drives compareTo breaks the tree ordering in the same way.

How to detect in review. Search for map keys and set element types that are entities or classes with setters, and check whether hashCode or compareTo reads mutable fields. The simplest cure is to key by an immutable id (Map<Long, Account> or a record key).

Situation: a Map<Account, Report> where Account.hashCode uses the mutable status. The code puts the key, then calls account.setStatus(CLOSED).

Check first: is the key class mutable, does hashCode use mutable fields, and does anyone change the key after insertion?

Fix: use immutable keys (String, Long, enum, a record, or an id-only wrapper). If you must mutate, remove the entry first and put it again afterwards.

record AccountId(long value) {}      // good key
Map<AccountId, Report> reports = new HashMap<>();

Prevent: a team rule that map keys and set elements are immutable, and a unit test that mutates a key after insertion.

Remember: mutate a key and the entry is lost. Keys must be immutable.

A Set<Order> contains the same order twice, although equals says they are equal. How do you debug it? Intermediate

The usual cause is that hashCode is missing or does not use the same fields as equals, so the two equal orders hash into different buckets and never get compared. Another is that equals was written as an overload equals(Order o) instead of an override of equals(Object).

Why a Set can hold "equal" objects. HashSet.add(x) computes x.hashCode(), goes to that bucket, and only compares with equals against elements in the same bucket. If two equal orders have different hash codes (the default identity-based hash, or fields that differ from those used in equals), they sit in different buckets and equals is never called between them. The set sees two distinct elements.

A five-minute debugging routine.

  1. Pick the two "duplicates" a and b and print a.equals(b), a.hashCode(), b.hashCode().
  2. If equals is true and the hashes differ, hashCode is missing or uses different fields.
  3. If equals is false, check the signature: public boolean equals(Order o) is an overload, and Set calls equals(Object), which is still the identity version. A missing @Override is the tell.
  4. If both look right, check for fields that differ in the objects, such as a timestamp included in equals, or subclasses where getClass() differs (proxies).
class Order {
    long id;
    public boolean equals(Order o) { return o != null && id == o.id; }    // overload!
}
new Order(1).equals((Object) new Order(1));   // false: Object.equals (identity) runs
new Order(1).equals(new Order(1));            // true: overload chosen statically

This shows why the bug is confusing: direct calls work, collections do not. Correct with @Override equals(Object) and a matching hashCode.

Check first: print a.equals(b) and a.hashCode() == b.hashCode(). If equals is true and the hashes differ, the contract is broken. Then check the signature of equals and whether @Override is present (it would have caught the overload).

Fix: override both from the same immutable fields, using Objects.equals and Objects.hash, or make Order a record.

Prevent: @Override everywhere, a test with EqualsVerifier, and records for value objects.

Remember: equal but duplicated in a Set means hashCode or equals is wrong. Always write @Override.

A NullPointerException in a long chain order.getCustomer().getAddress().getCity().toUpperCase(). How do you find it and fix it properly? Intermediate

On Java 14 and later (helpful messages are on by default from Java 15) the NPE message names exactly which call returned null. The real fix is not to scatter null checks but to decide which values may legitimately be absent, and make that explicit in the model.

Reading the exception message. Since Java 14 (default on in 15), the message tells which part was null: Cannot invoke "Address.getCity()" because the return value of "Customer.getAddress()" is null. On older JVMs the stack trace points to a line number only, so split the chain across lines or use a debugger to find the null.

Why a chain of getters is risky. Each .getX() assumes the previous result is non-null (the "train wreck"). Adding a null check at every step produces a pyramid of if statements, and checking everywhere also hides the real question: which of these may legitimately be missing? Model absence deliberately.

// 1. Optional pipeline: each step is skipped when a value is missing
String city = Optional.ofNullable(order)
        .map(Order::getCustomer)
        .map(Customer::getAddress)
        .map(Address::getCity)
        .map(String::toUpperCase)
        .orElse("UNKNOWN");

// 2. Enforce "never null" where it is created
this.customer = Objects.requireNonNull(customer, "customer");

// 3. Collections: return empty, not null
List<Item> items() { return items == null ? List.of() : items; }

Rules of thumb for Optional. Use it as a return type to say "might be absent". Do not use it for fields, method parameters or collections (an empty collection already means "none"), and never call get() without checking, prefer orElse, orElseGet, orElseThrow, ifPresent. orElse(expensive()) evaluates its argument even when the value is present; use orElseGet for costly defaults.

Long-term prevention. Nullability annotations (@Nullable, @NonNull) checked by a tool such as NullAway or the IDE, validation at API boundaries, and the Law of Demeter ("tell, don't ask": give Order a method shippingCity() so callers do not navigate the graph).

Situation: the stack trace points to one line with four calls, and older JVMs do not say which one was null.

Check first: read the NPE message ("because the return value of Customer.getAddress() is null"). Check the data: is a missing address valid?

Fix: if the value may be absent, return Optional from getters used for lookup, or chain safely: Optional.ofNullable(order).map(Order::getCustomer).map(Customer::getAddress).map(Address::getCity).map(String::toUpperCase).orElse("UNKNOWN"). If it must never be null, enforce it at construction with Objects.requireNonNull. Return empty collections, never null.

Prevent: nullability annotations, Optional as a return type only (not for fields or parameters), and validation at the boundaries.

Remember: decide who may be null, then model it: Optional for "maybe", requireNonNull for "never".

Under load, reports show mixed-up data between users, and sometimes weird date errors. You find a static field. What happened? Senior

A mutable static field is shared by every request thread. Two requests write and read it at the same time, so they see each other's data. A static SimpleDateFormat is the classic case: it is not thread-safe and keeps internal state while parsing, which produces wrong dates or strange exceptions only under concurrency.

Why the symptoms look strange. A static field exists once per JVM. A web server runs many request threads in the same JVM, so all requests share it. Code like static User current; ... current = loadUser(req); ... render(current); works with one user and fails with two: request B overwrites current between request A's assignment and use, so A renders B's data.

The SimpleDateFormat case. SimpleDateFormat keeps a working Calendar inside it that parse and format mutate. Two threads using one instance interleave their steps and get wrong dates, or exceptions like NumberFormatException: multiple points. It works in single-thread tests, so the bug appears only under load and is hard to reproduce.

// broken
private static final SimpleDateFormat FMT = new SimpleDateFormat("yyyy-MM-dd");

// fixed: immutable, thread-safe
private static final DateTimeFormatter FMT = DateTimeFormatter.ISO_LOCAL_DATE;
LocalDate d = LocalDate.parse(text, FMT);

Reproducing. Run the suspect method from a thread pool of 50 threads, a million iterations, and compare results with a single-thread run. Tools: jcstress, a stress test, or ThreadSanitizer-like detection in code review (SpotBugs STCAL_STATIC_SIMPLE_DATE_FORMAT_INSTANCE).

Options for shared mutable state. Make it a local or a parameter; make it immutable; use a thread-safe class (ConcurrentHashMap, AtomicLong, LongAdder); guard with a lock; or use ThreadLocal (always remove() it at the end of the request, since pooled threads live on and leak or mix data). In Spring, prefer beans that are stateless, and request-scoped objects for per-request data.

Situation: private static final SimpleDateFormat FMT = ... or a static currentUser variable. It works in single-user tests and fails under load.

Check first: grep for non-final statics, and static mutable objects (SimpleDateFormat, HashMap, ArrayList). Reproduce with a parallel test.

Fix: use immutable thread-safe types: java.time.DateTimeFormatter. Make request data local variables or method parameters. For shared mutable data, use a concurrent collection or proper locking, or a ThreadLocal (and clear it) as a last resort.

Prevent: static analysis rules, "no mutable static state" in the code guidelines, and concurrency tests.

Remember: static mutable state is shared by all threads. Prefer locals and immutable shared objects.

After a deployment, reading cached or queued objects fails with InvalidClassException. What happened and how do you prevent it? Senior

The classes were changed between writing and reading, and the stored serialVersionUID no longer matches the new class. Without an explicit UID, Java computes it from the class shape, so even adding a method changes it. I declare the UID explicitly and keep changes backward compatible, or I move to a schema-based format.

Why a deploy triggers it. Version 1 wrote objects into Redis, a session store or a queue. Version 2 of the class is deployed (field added, method added). On read, the JVM compares the UID in the stream with the new class's UID. If the class did not declare serialVersionUID, Java computes one by hashing the class name, interfaces, fields and non-private methods, so almost any change gives a different number and the read fails with InvalidClassException: local class incompatible. In a rolling deploy it is worse: both versions run at once and each may fail to read the other's data.

Compatible and incompatible changes (with a fixed UID).

ChangeSafe to read old data?
Add a fieldyes (old data gives the default value)
Add or remove methodsyes
Remove a fieldyes, the value is ignored
Change a field's type (int to long)no
Move the class or change its superclass hierarchyno
Rename a fieldno (it reads as a new field)

Quick mitigation during an incident. Clear the affected cache keys, or restore the old UID value. You can read the old UID from the exception text, or compute it with the serialver tool on the old class file, and then declare it in the new class: private static final long serialVersionUID = <old value>L;.

Lasting fix. Avoid Java serialization for anything that outlives one process. Store JSON or Protobuf with a schema, put a version in the cache key (user:v2:42) so a new release starts with fresh keys, and set TTLs on cached data so stale shapes age out.

Situation: objects serialized into a Redis or session cache, a file or a queue by version 1 are read by version 2.

Check first: the exception text shows both UIDs ("local class serialVersionUID = ... stream classdesc serialVersionUID = ..."). Diff the class between the two builds.

Fix now: flush the old cache, or restore the old UID value so compatible changes (adding a field) can be read. Added fields come back as defaults.

Prevent: an explicit serialVersionUID and a rule about which changes are compatible. For caches and messages, use JSON, Protobuf or Avro with a schema, and include a version in the cache key so a deploy starts with a clean key space.

Remember: declare the UID or lose old data on every change. Better, do not use Java serialization for storage.

A subclass method was meant to replace parent behaviour, but the parent's version still runs. Name the usual causes. Intermediate

The method does not actually override. The usual causes: a different parameter type (so it is an overload, not an override), a typo in the name, the method is static or private (hidden, not overridden), or the parent method is final. Writing @Override turns every one of these into a compile error.

The most common cause, seen concretely.

class Parent { void handle(Object o) { System.out.println("parent"); } }
class Child extends Parent {
    void handle(String s) { System.out.println("child"); }   // overload, not override
}
Parent p = new Child();
p.handle("x");              // prints "parent": the compiler chose handle(Object) from Parent's view
new Child().handle("x");    // prints "child": here the overload is a better match
// with @Override on Child.handle(String) the compiler says: method does not override or implement a method from a supertype

Checklist of why an "override" does not take effect.

  • Different parameter types (including a different generic argument, boxing, or int versus long).
  • Typo or different capitalisation in the name (tostring(), hashcode()).
  • The parent method is private (child's method is unrelated), static (hidden) or final (compile error).
  • Different package and the parent method is package-private: it is not visible, so the child's method does not override it.
  • The object was created from the parent class, or the call goes through a different path (for example a Spring proxy calling an unadvised self-invocation).

Habit that prevents it. Always annotate with @Override, including interface implementations. Turn on the checkstyle MissingOverride rule or the compiler lint option so a missing annotation is flagged in the build.

Situation: a child defines equals(Order o) or process(Integer x) where the parent has process(int x). Calls through the parent type still reach the parent's method.

Check first: compare signatures exactly. Add @Override and see whether the compiler complains. Check for static and private modifiers, and for generics (an override with a different type argument is not an override).

Fix: match the signature and add @Override.

Prevent: require @Override in the code style (the compiler can warn with -Xlint:all, IDEs and checkstyle can enforce it).

Remember: if it was meant to override, say so with @Override and let the compiler check.

Heap grows steadily. The heap dump shows many request objects retained through fields named this$0. What is it? Senior

An inner or anonymous class holds a hidden reference to its outer object, and that is the field this$0. Something long-lived (a static list, a cache, a scheduled task, a registered listener) keeps the small inner objects, and through this$0 each one keeps a whole request object alive, so memory never shrinks.

How to follow the evidence. A typical retained chain in the heap dump or in Eclipse MAT's "path to GC roots" looks like this:

java.util.concurrent.ScheduledThreadPoolExecutor  (GC root: thread / static)
  -> ScheduledFutureTask -> RequestHandler$1 (anonymous Runnable)
     -> this$0 -> RequestHandler
        -> request, response, 4 MB payload

Each request creates a RequestHandler that schedules an anonymous Runnable (for a timeout or retry). The scheduler queue is long-lived and holds the runnable, and via this$0 the whole handler with its payload. If tasks are cancelled but not removed from the queue (the default for ScheduledThreadPoolExecutor unless setRemoveOnCancelPolicy(true)), they remain until their delay passes.

Fix steps.

  1. Replace the anonymous class by a static nested class or a lambda that only captures the small values it needs (an id, a callback), not this.
  2. Cancel futures and unregister listeners when the request ends, and consider setRemoveOnCancelPolicy(true).
  3. Bound any cache or queue (size and time limits).
  4. Verify with a soak test: repeat the operation 100,000 times and watch the old generation after full GC with a flat line expected. Use jcmd GC.class_histogram before and after.

Note that modern javac (around JDK 18 and later) omits the this$0 field when an inner class never uses it, so in new builds the leak path can look different, but lambdas or methods that use the outer instance still hold it.

Check first: in the heap dump (Eclipse MAT, VisualVM), pick a retained request object and follow "path to GC roots". It ends in a static collection or a thread, passing through a this$0 field.

Fix: make the inner class a static nested class, or a lambda that does not use this, and pass only the data it needs. Remove the entry from the long-lived collection when done, unregister listeners, or hold only a WeakReference.

Prevent: a code-review rule against anonymous classes registered into long-lived objects, bounded caches, and leak tests that check memory after many requests.

Remember: this$0 in a GC-root path means an inner class is keeping its outer object alive.

The invoice total is off by one cent in some orders, and reports do not reconcile. What do you do? Intermediate

It is almost certainly double arithmetic or rounding at the wrong place. I move money to BigDecimal (from Strings) or whole cents in a long, choose one explicit rounding mode, and round at defined points, such as once per invoice line.

Reproduce a typical drift. A 10 percent discount on three items of 0.10 each:

double total = 0.10 + 0.10 + 0.10;            // 0.30000000000000004
double rounded = Math.round(total * 100) / 100.0;   // fine here, but not always
// sum of per-line rounded values vs rounded sum:
// lines 1.005, 1.005 -> each rounds to 1.01 (2.02) vs sum 2.01 rounded -> 2.01 : one cent off

Two separate problems often coexist: (1) binary representation error from double, and (2) a policy inconsistency: rounding each line and summing gives a different total from summing and rounding once. The second is not fixed by BigDecimal alone, you must decide the rule with the business and implement it everywhere (invoice, report, ledger, tax).

Reconciliation approach.

  1. Pick a failing invoice and recompute with exact decimals by hand or in a spreadsheet set to the same rounding rule.
  2. Grep for double, float, Math.round, new BigDecimal(double) and integer divisions like percent / 100.
  3. Introduce a Money value class (BigDecimal amount, Currency currency) with the scale and rounding mode fixed inside. All arithmetic goes through it, so no caller can round differently.
  4. Store as DECIMAL(19,4) (or integer minor units) in the database, never FLOAT.
  5. Backfill: decide how to correct historic invoices, and add a nightly reconciliation job that compares the line sum with the stored total.

Test with awkward values: 0.1, 0.07, 1.005, three-way splits of 1.00 (0.33 + 0.33 + 0.34, assign the remainder cent to one line), and large totals.

Situation: 0.1 + 0.2 is not exactly 0.3 in binary. Summing many doubles and rounding at the end, or rounding each line differently from the total, produces cent differences that vary by order.

Check first: find an order that is off and recompute by hand. Look for double and float in prices, new BigDecimal(double) and implicit int division.

Fix: use BigDecimal built from String or valueOf, setScale(2, RoundingMode.HALF_EVEN), compare with compareTo. Decide whether to round each line then sum, or sum then round, document it, and apply it everywhere (including the reports).

Prevent: a Money value class, tests with tricky amounts (0.1, 0.07, 1/3 splits), and a rule against double for currency.

Remember: money is never double. One rounding rule, applied at one place.

After adding a new enum constant in the middle, old rows in the database mean something else. What went wrong? Intermediate

The column stores ordinal(), the position of the constant. Inserting a new constant shifts every later position, so old numbers now point at different constants. I persist a stable name or an explicit code, and never the ordinal.

The timeline of the incident.

  1. Version 1: enum Status { NEW, PAID, SHIPPED }. JPA stores the ordinal: 0, 1, 2. A paid order is saved as 1.
  2. Version 2 inserts PENDING after NEW: NEW, PENDING, PAID, SHIPPED. Ordinals are now 0, 1, 2, 3.
  3. The old row with value 1 is read as PENDING. A paid order is now "pending", and shipped orders (old 2) read as PAID. No exception, because every number is still a valid ordinal. Numbers beyond the old range (3) would even fail with ArrayIndexOutOfBounds in some mappers.

Repair. Write a migration that maps old numbers to the intended names for rows created before the change (using the release time or a version marker), switch the mapping to @Enumerated(EnumType.STRING) (the column becomes a VARCHAR holding "PAID") or to an AttributeConverter that maps an explicit stable code, and ship the code change together with the data migration.

enum Status {
    NEW("N"), PENDING("P"), PAID("D"), SHIPPED("S");
    final String code;
    Status(String code) { this.code = code; }
    static Status fromCode(String c) { for (Status s : values()) if (s.code.equals(c)) return s; throw new IllegalArgumentException(c); }
}
// JPA: @Convert(converter = StatusConverter.class) maps Status <-> code

Trade-off. EnumType.STRING is readable and safe against reordering, but renaming a constant breaks stored rows and uses more space than a number. An explicit code survives both reordering and renaming. The same rule applies to enums sent in JSON or stored in files and to EnumMap persisted indirectly.

Situation: JPA @Enumerated without a value defaults to EnumType.ORDINAL. Before: NEW=0, PAID=1, SHIPPED=2. After inserting PENDING at position 1, old "1" rows now read as PENDING instead of PAID.

Check first: what do the stored values look like (numbers)? Compare against git history of the enum.

Fix: migrate the data to the intended meaning, and switch the mapping to @Enumerated(EnumType.STRING) or an explicit code with an attribute converter.

Prevent: a rule never to store ordinal(), explicit codes for stable external contracts, and append-only enum changes where the order matters. Remember that renaming a constant also breaks stored names, so a code field is the most stable choice.

Remember: store the name or code, never the ordinal.

A sort sometimes crashes with "Comparison method violates its general contract!" in production only. Why? Senior

The comparator is inconsistent, so it breaks the rules of ordering (antisymmetric and transitive), and TimSort notices while merging. The usual causes are subtraction that overflows (return a.x - b.x), comparing doubles with NaN, mixing criteria that are not transitive, or data that changes during the sort. It shows up only in production because the check needs enough elements and the right data.

Why subtraction fails, with numbers. compare(a, b) { return a.x - b.x; } with a.x = Integer.MAX_VALUE and b.x = -10 computes 2,147,483,647 - (-10), which overflows to a negative number. The comparator then says a is smaller than b, which contradicts the real order. Because the comparator now disagrees with itself across different pairs (not transitive), TimSort's merge phase can detect an impossible state and throw IllegalArgumentException: Comparison method violates its general contract!.

Why only in production. TimSort uses plain binary insertion sort for small runs (fewer than 32 elements here) and does not look for contract violations, so unit tests with a handful of values pass. Large arrays with real data and extreme values go through the merge logic, which checks consistency. The behaviour also depends on the data order, so it can look intermittent.

Other causes of an inconsistent comparator.

  • Comparing double with a hand-written a > b ? 1 : -1 (never returns 0, and NaN breaks every comparison). Use Double.compare.
  • Returning (int) (a.time - b.time) for longs (the cast wraps).
  • Random or time-dependent comparators, or elements modified by another thread during the sort.
  • Combining criteria in a way that is not a total order (for example "A before B if they differ by more than 1").
// wrong
list.sort((a, b) -> a.score - b.score);
// right
list.sort(Comparator.comparingInt(Item::score));
// right, explicit
list.sort((a, b) -> Integer.compare(a.score, b.score));

Detect early. A property test that generates random lists, including Integer.MIN_VALUE, MAX_VALUE, 0 and duplicates, and checks that sgn(compare(a,b)) == -sgn(compare(b,a)) and transitivity. Sonar and Error Prone flag subtraction comparators.

Situation: small test lists use a simple insertion sort path (arrays under 32 elements) and never detect the problem. Production lists are bigger, and contain values like Integer.MIN_VALUE or very large numbers.

Check first: read the comparator: subtraction, (int) casts of long differences, null handling, a mix of fields. Reproduce with a big random list including extreme values.

Fix: use Integer.compare, Long.compare, Double.compare or Comparator.comparing. Do not mutate elements while sorting.

Prevent: never hand-write subtraction comparators, and test comparators with random data (property tests checking sign symmetry and transitivity).

Remember: never compare with subtraction. Use Integer.compare or Comparator.comparing.
