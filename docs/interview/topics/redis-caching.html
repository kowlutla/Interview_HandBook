Mental model: the 8 ideas everything hangs on

One line: a cache trades freshness and simplicity for speed. Redis is an in-memory data structure server, mostly single-threaded, so each command is fast and atomic. Every caching bug is some way the cache and the source of truth disagree, or a way many requests hit the database at once.
  1. Cache is a copy, the database is the truth. You must always be able to rebuild a cache entry. If you cannot, it is not a cache, it is a database, and needs durability.
  2. Hit rate is the whole game. Average latency is roughly hit_rate times cache time plus miss_rate times database time. A drop from 99% to 90% means ten times more database load.
  3. Every entry needs a way to die. TTL, eviction, or explicit invalidation. Without one, memory fills and data goes stale.
  4. Invalidation is the hard part. Updating the database and the cache are two separate writes. Any order can fail halfway.
  5. Failures come in crowds. Many callers miss the same key together (stampede), many keys expire together (avalanche), or one key gets all the traffic (hot key).
  6. Redis runs commands one at a time. That makes single commands and Lua scripts atomic, and makes one slow command stall everyone.
  7. Choose the right data structure. Sorted set for leaderboards, hash for objects, stream for logs, string with INCR for counters. The command is the unit of atomicity.
  8. Redis availability is asynchronous. Replication, persistence and failover all trade a little data for speed. Know the loss window.

1. Caching fundamentals and patterns

Why do we cache, and what makes data a good candidate? Basic

What the interviewer is testing: can you justify a cache with numbers and not just add it by habit.

We cache to make reads faster and to protect the database. A Redis read takes well under a millisecond on a good network, while a database query with joins can take tens of milliseconds. A cache also lets one database serve many more users, because most reads never reach it. Good candidates are data that is read much more often than it changes, expensive to compute, and fine to be a little stale: product catalogs, user profiles, configuration, rendered pages, permission lookups. Bad candidates are data that changes on every request, data that must be perfectly fresh such as an account balance during a transfer, and data that is read once and never again, because the miss cost is paid and nothing is saved. A cache also adds new problems: staleness, a new component that can fail, and extra code. So I ask first: what is the read to write ratio, how stale can this be, and what is the hit rate I expect?

Likely follow-ups
  • How do you measure whether a cache helps? Hit rate, p99 latency with and without it, and database load before and after.
  • What is a good hit rate? Depends, but for read-heavy data 90 to 99 percent is common. Below about 80 percent, ask whether it is worth it.
Explain the cache-aside pattern. Why is it the most common one? Basic

What the interviewer is testing: the default pattern, and that you know who owns the logic.

In cache-aside (also called lazy loading) the application talks to both the cache and the database. On a read it first asks the cache. On a hit it returns the value. On a miss it reads the database, writes the result into the cache with a TTL, and returns it. On a write it updates the database and then deletes (or updates) the cache entry. It is popular because the cache only holds data that was really requested, the cache can die and the system still works (just slower), and it works with any cache and any database. The weak spots are: the first request for each key is always slow, entries can go stale between a database change and the cache update, and every service must implement the same logic correctly.

String get(String id) {
    String v = redis.get("user:" + id);
    if (v != null) return v;               // hit
    v = db.loadUser(id);                   // miss: go to the source
    if (v != null) redis.setex("user:" + id, 300, v);
    return v;
}
void update(User u) {
    db.save(u);
    redis.del("user:" + u.id);             // invalidate, next read refills
}
Likely follow-ups
  • Why delete on write and not update the cache? Deleting is simpler and safer: you cannot write a wrong value, and the next read rebuilds it from the truth.
Common mistakes: forgetting a TTL, so a missed invalidation lives forever; caching null results without a short TTL (see cache penetration).
Compare read-through, write-through and write-behind (write-back). Intermediate

What the interviewer is testing: whether you can place each pattern on the consistency versus speed line.

In read-through the cache itself loads from the database on a miss. The application only talks to the cache, and a loader plugged into the cache does the database read. Cache-aside is the same idea with the logic in your code. In write-through every write goes to the cache, and the cache writes to the database synchronously before returning. The cache is always current, reads are fast, but writes are slower because they pay for both. In write-behind (write-back) the write goes to the cache and returns at once; the cache saves to the database later, in batches. Writes are very fast and the database load is smoothed, but if the cache node dies before flushing, those writes are lost, and the database is briefly behind. Redis itself does not do read-through or write-through. You build them in your code, or use a library, or a data grid that supports them.

Likely follow-ups
  • When would you use write-behind? Counters, view counts, analytics: high write rate, and losing a few seconds is acceptable.
How do you choose a TTL? Basic

What the interviewer is testing: practical judgement, and awareness that TTL is the safety net.

The TTL is how long you accept stale data, so it is a business decision, not a technical one. Ask: if this value changes in the database and the cache does not know, how long can users see the old value? For a product description, five minutes may be fine. For a feature flag, maybe 30 seconds. For a bank balance, probably do not cache at all. TTL is also a safety net: even if your invalidation code has a bug, the wrong value dies after the TTL. Longer TTL gives a higher hit rate and less database load, shorter gives fresher data. Two practical rules: add random jitter so many keys do not expire in the same second, and keep the TTL shorter for entries that are expensive to be wrong about. Short TTL on negative results (not found) is also wise.

SET product:42 "{...}" EX 300         # 5 minutes
TTL product:42                        # seconds left, -1 no expiry, -2 no key
Common mistakes: no TTL at all; the same TTL for millions of keys loaded together (avalanche); resetting the TTL by accident, since a plain SET without EX removes the old TTL.
"There are only two hard things: cache invalidation and naming things." What are the main invalidation strategies? Intermediate

What the interviewer is testing: a layered answer that mixes TTL with explicit invalidation.

There are four common ways. First, time based: just use a TTL and accept staleness for that period. Second, explicit delete on write: when the code changes the data, it deletes the cache key. Third, event driven: the database or service publishes a change event (for example through change data capture or a message queue) and a consumer deletes or updates the cache. This is useful when many services write the same table. Fourth, versioned keys: include a version in the key, like product:42:v17, or a namespace version number, so a change simply makes new keys and old ones age out by TTL. In real systems I combine them: explicit delete or events for freshness, TTL as a safety net. Invalidating collections (for example a list page that contains a changed product) is the hardest part, because you must know which cached lists include that item; a short TTL or a version number on the list is usually easier than tracking dependencies.

Likely follow-ups
  • Why delete rather than update the cache? Races: two concurrent updates can write the cache in the wrong order. A delete is idempotent.
  • What if the delete fails? Retry through a queue, and rely on the TTL as the last defence.
Can cache-aside serve stale data forever even with correct code? Show me the race. Senior

What the interviewer is testing: concurrency thinking about two systems with no shared transaction.

Yes, there is a classic race. Thread A reads key K, misses, and reads the database: value v1. Before A writes the cache, thread B updates the database to v2 and deletes the cache key (nothing there yet, so nothing happens). Then A, slow, writes v1 into the cache. Now the cache holds v1, the database holds v2, and the entry stays wrong until the TTL ends. This is rare because the window between A's read and A's write is short, but at high volume it happens. Defences: a TTL, which bounds the damage; a delayed double delete, where the writer deletes the key again after a short delay, say 500 ms to 1 second, to remove a late stale write; or storing a version or timestamp with the value and writing only if it is newer (a small Lua script does the compare and write atomically). For truly strict needs, read from the database, or use a change-data-capture stream as the only invalidator, since it carries the order of changes.

What consistency can you promise with a cache in front of a database? Senior

What the interviewer is testing: honest trade-off language, not "it is always consistent".

Two separate stores cannot be updated atomically without a distributed transaction, which you do not want on a hot path. So the honest promise is eventual consistency with a bound: after a write, the cache may serve the old value until the delete reaches it or the TTL ends. You can make the window small with delete-on-write, and make it safe with TTLs. Some reads need stronger guarantees: for "read your own writes" (a user edits a profile and must see it at once), after a write I can bypass the cache for that user for a few seconds, or write the new value straight into the cache, or route the read to the database. For money movement, locks, and inventory decrement, the database (or Redis used as a primary with atomic commands) is the authority, not a stale copy. I tell the team clearly which data may be stale and for how long, and write that down per cache.

Likely follow-ups
  • What about multiple replicas of the cache? Each can lag; clients reading from Redis replicas may also see older data than the primary.
What is a multi-level cache, and what are the risks of a local in-process cache? Intermediate

What the interviewer is testing: layered design and the problems of per-instance copies.

A multi-level cache has several layers: L1 is inside the application process (Caffeine, Guava), L2 is a shared cache (Redis), and the database is behind them. L1 is the fastest, with no network hop, a few hundred nanoseconds. L2 is shared, so all instances see the same data, and it protects the database when an instance restarts and its L1 is empty. The risk of L1 is that every instance has its own copy. When data changes, the other instances still hold the old value, so L1 TTLs must be short (seconds), or you broadcast invalidations (for example over Redis pub/sub, or Redis client-side caching with tracking, available since Redis 6). L1 also uses heap memory, so it needs a size limit. I use L1 only for small, hot, rarely changing data, such as config or reference lists, and keep it short lived.

How does HTTP and CDN caching fit with an application cache? Intermediate

What the interviewer is testing: that caching is not only Redis, and that you know the headers.

The cheapest request is the one that never reaches your servers. HTTP caching uses response headers. Cache-Control: max-age=3600 lets browsers and CDNs reuse the response for an hour without asking. s-maxage sets a different time for shared caches like a CDN. no-store forbids storing sensitive data, private means only the user's browser may cache it, and public allows shared caches. For revalidation, the server sends an ETag (a fingerprint) or Last-Modified; the client later sends If-None-Match, and the server replies 304 Not Modified with no body if nothing changed. stale-while-revalidate lets a cache serve the old copy while it fetches a fresh one in the background. For static files, name them with a content hash (app.3f9a1c.js) and cache them for a year: a change means a new URL, so no invalidation is needed. The Vary header tells caches which request headers change the response, for example Accept-Encoding. A CDN purge API handles the rest. Redis then sits behind this, for data that is dynamic or personalised.

Likely follow-ups
  • Danger of caching authenticated responses at a CDN? You can serve one user's data to another. Use private or no-store, and be careful with Vary.
How do you design cache keys and values? Intermediate

What the interviewer is testing: practical hygiene that prevents bugs and memory waste.

A key should be readable, unique and predictable: service:entity:id:variant, for example catalog:product:42:en. Include everything that changes the value: tenant id, language, API version, and user role if the result depends on it. Missing a tenant id in the key is a classic data leak bug in multi-tenant systems. Keep keys short because they use memory, but not cryptic. Put a version in the key (v2) so a deploy that changes the value format does not read old-shape data. For values, store only what you need, not whole object graphs. JSON is easy to debug; binary formats such as Protobuf or MessagePack are smaller and faster. Compress large values if they are bigger than a few KB. Avoid very large values (over a megabyte), since they block the single thread while being copied and add network time. Avoid storing complex lists of ids unbounded, they become big keys.

Common mistakes: a key that omits the tenant; changing the serialization format without changing the key, so old entries cannot be read after deploy; using KEYS * to find keys (use SCAN).

2. Cache failure modes: stampede, penetration, avalanche, hot keys

What is a cache stampede (thundering herd) and how do you prevent it? Intermediate

What the interviewer is testing: a famous failure mode, and several practical defences.

A stampede happens when a popular key expires, and many requests miss at the same moment. All of them run the same expensive query against the database. The database slows down, so each rebuild takes longer, so more requests pile up, and it can collapse. Defences, from simple to strong: (1) single flight / per-key lock: the first request that misses takes a short lock (SET lock:key token NX PX 5000) and rebuilds; others wait briefly and re-read, or get the old value. (2) Serve stale while revalidating: store a soft expiry inside the value; when it passes, one caller refreshes in the background while everyone else still gets the old value. (3) Probabilistic early refresh: each reader has a small chance of refreshing before the real expiry, higher as the expiry gets closer, so refresh happens before the herd arrives. (4) Jittered TTLs so keys do not expire together. (5) Pre-warm hot keys with a scheduled job, and never let them expire. In Spring, @Cacheable(sync = true) gives per-JVM single flight, but not across instances.

Likely follow-ups
  • What if the lock holder crashes? The lock has a TTL, so others can proceed after it expires.
What is cache penetration, and how do you stop it? Intermediate

What the interviewer is testing: awareness of requests that can never be cached by normal logic.

Penetration means requests for keys that do not exist in the database either, so the cache never holds an answer and every request goes through to the database. It can be a bug, or an attack: someone sends thousands of random ids. The defences: (1) cache the negative result, store a marker like NULL with a short TTL (30 to 60 seconds), so repeats are served from the cache. (2) Validate input early: reject ids with the wrong format or range, before any lookup. (3) A Bloom filter in front: a small, fast structure that can say "definitely not present" or "maybe present". Load it with all valid ids; if it says "not present", return not found without touching cache or database. A Bloom filter can have false positives (it says maybe, but it is not there) and never false negatives, so no real item is rejected. It needs updating when new items are created. (4) Rate limit abusive clients.

Likely follow-ups
  • Danger of negative caching? A record created right after the miss will look missing until the short TTL ends; so keep it short, or delete the marker on create.
  • Is there a Bloom filter in Redis? Yes, the RedisBloom module (included in Redis Stack, and built into Redis 8). Or implement with a bitmap.
What is a cache avalanche, and how is it different from a stampede? Intermediate

What the interviewer is testing: can you separate "one hot key" from "many keys at once or the whole cache gone".

A stampede is about one hot key expiring with many readers. An avalanche is about many keys failing together, so the database sees a huge wave of misses for many different queries. Two causes: a lot of keys were loaded at the same time with the same TTL (for example a nightly warm-up with a one hour TTL), so they all expire together; or the cache itself went down or was flushed, so everything misses. Fixes: add random jitter to TTLs (for example base 600 s plus a random 0 to 120 s), stagger warm-ups, run Redis with replicas and automatic failover so the whole cache is not lost, add a local L1 cache, protect the database with a circuit breaker, a rate limiter or request queue so it degrades instead of collapsing, and have a plan to serve a reduced response (stale data, default values) when the database is overloaded.

int ttl = 600 + ThreadLocalRandom.current().nextInt(120);   // jitter
redis.setex(key, ttl, value);
What is a hot key, and what do you do about it? Senior

What the interviewer is testing: understanding that Redis scaling is per key, not just per cluster.

A hot key is one key that gets a very large share of traffic, for example the product page of a flash sale or a global config key. In a Redis Cluster, a key lives on exactly one master, so adding nodes does not help: that one node saturates its CPU or network while others sit idle. Options: (1) add a local L1 cache in each app instance with a short TTL (even 1 to 5 seconds), which removes most traffic. (2) Replicate the key under several names, such as hot:cfg:0 to hot:cfg:7, and have each reader pick one at random; the copies land on different slots and nodes. (3) Read from replicas if slight staleness is acceptable. (4) Shrink the value, since a large value on a hot key also saturates the network. (5) For counters, shard the counter into N sub-keys and sum on read. To find hot keys: redis-cli --hotkeys (needs an LFU eviction policy), MONITOR in a test only (it is heavy), or client side metrics.

Likely follow-ups
  • Why not just add more shards? Hashing sends the same key to the same shard every time.
What is a big key and why is it dangerous? Intermediate

What the interviewer is testing: the link between one-thread execution and large values.

A big key is a key whose value is very large: a string of several MB, or a hash, list, set or sorted set with millions of elements. Because Redis runs commands one at a time on one thread, any command that touches the whole big key (DEL, HGETALL, SMEMBERS, LRANGE 0 -1) blocks every other client until it finishes, which can be hundreds of milliseconds. Big keys also cause network spikes, uneven memory in a cluster, slow replication, and slow expiry. Fixes: use UNLINK instead of DEL (frees memory in a background thread, Redis 4.0), read in pieces with HSCAN, SSCAN, ZSCAN or ranges, split one large key into buckets (user:123:orders:0, :1), set TTLs, and find them with redis-cli --bigkeys or MEMORY USAGE key.

redis-cli --bigkeys                # sample the biggest key of each type
MEMORY USAGE session:big           # bytes for one key
UNLINK session:big                 # non-blocking delete
Why is KEYS * dangerous in production, and what do you use instead? Basic

What the interviewer is testing: a classic production mistake.

KEYS pattern walks the entire key space in one command. It is O(N) in the number of keys. With ten million keys it can block the server for seconds, and since Redis handles commands one at a time, every other request waits, so the app times out. Use SCAN instead. It walks the key space in small steps using a cursor: you call it with cursor 0, get a batch plus a new cursor, and repeat until the cursor returns 0. Each call is quick, so other clients keep being served. The trade-offs: SCAN may return a key more than once, and keys added or removed during the walk may or may not appear, so your code must be idempotent. COUNT is only a hint for the batch size. There are matching commands for collections: HSCAN, SSCAN, ZSCAN.

SCAN 0 MATCH session:* COUNT 500
# returns: 1) next cursor  2) batch of keys. Stop when cursor is 0

3. Redis internals and the single-threaded model

What is Redis, and what makes it different from a plain key-value cache? Basic

What the interviewer is testing: that you see Redis as a data structure server and not only a string cache.

Redis (Remote Dictionary Server) is an in-memory data store. The data lives in RAM, so reads and writes take microseconds. Unlike a simple cache that stores opaque blobs, Redis understands data types: strings, lists, hashes, sets, sorted sets, streams, bitmaps, HyperLogLog and geospatial indexes, and it offers atomic commands on each of them, such as incrementing a counter, adding to a sorted set, or popping from a list. It can persist data to disk (RDB snapshots and the AOF log), replicate to other nodes, fail over automatically (Sentinel), and shard data (Cluster). It supports pub/sub, streams, Lua scripting and transactions. People use it as a cache, a session store, a rate limiter, a leaderboard, a queue, a lock service, and sometimes as a primary database for small, fast data. The caveat is memory: the whole data set must fit in RAM, which makes it costly for large data.

Likely follow-ups
  • Is Redis a database or a cache? Both, depending on persistence and how you use it. With persistence and replication it can be a primary store for the right data.
Redis is single-threaded. Why is it still so fast? Intermediate

What the interviewer is testing: a very common question; the answer should be nuanced, not "Redis has no threads".

The command execution runs on one main thread. That is fast for four reasons. First, all data is in memory, so there is no disk wait. Second, there are no locks and no context switching between threads for data access, which removes a lot of overhead and makes every command atomic. Third, Redis uses an event loop with I/O multiplexing (epoll on Linux), so one thread can watch thousands of sockets and handle whichever is ready. Fourth, the data structures are carefully designed and most commands are O(1) or O(log N). The thread usually is not the bottleneck; the network is. Not everything is single threaded: background threads close files, flush the AOF and free memory lazily (UNLINK), and since Redis 6.0 you can turn on I/O threads to read and write sockets in parallel, though commands still execute on the main thread. Persistence forks a child process. To use many CPU cores, you run several Redis processes, usually as a Cluster.

Likely follow-ups
  • What is the downside? CPU-heavy or O(N) commands block everyone; one process uses one core for commands.
What does "Redis commands are atomic" really mean, and what does it not cover? Intermediate

What the interviewer is testing: the difference between one atomic command and a multi-step read-modify-write.

Because one thread executes commands one by one, a single command runs to completion with nobody seeing a half-done state. INCR, SETNX, LPUSH and ZADD are all atomic. Two clients calling INCR counter at the same time always give +2. But a sequence of commands is not atomic. If your code does GET balance, adds 10 in Java, then SET balance, another client can sneak in between, and one update is lost. Fixes: use a single atomic command (INCRBY, HINCRBY), use WATCH with MULTI/EXEC for optimistic locking, or put the whole sequence in a Lua script, which runs as one unit. Also note: atomic does not mean durable. A command can succeed in memory and still be lost if the server crashes before persistence.

# wrong: read-modify-write across the network
v = GET stock:42;  SET stock:42 (v-1)
# right: one atomic command
DECR stock:42
What is pipelining, and how is it different from a transaction? Intermediate

What the interviewer is testing: that you understand round-trip cost and do not confuse batching with atomicity.

Normally a client sends one command, waits for the reply, then sends the next. Each wait is a network round trip, often 0.2 to 1 ms inside a data center, much longer than the time Redis needs to run the command. Pipelining means sending many commands without waiting for each reply, then reading all the replies together. It can raise throughput by ten times or more for bulk work, such as loading 10,000 keys. Redis queues the replies in memory, so batch in chunks of a few hundred to a few thousand, not millions. Pipelining is only about network efficiency: the commands are not atomic, other clients' commands can run between them, and one failing command does not stop the rest. A transaction (MULTI to EXEC) gives the guarantee that the queued commands run together with no other client in between. They combine well: clients commonly send a transaction inside a pipeline. In a Cluster, a pipeline must be split by node, since keys are on different servers.

// Jedis style
Pipeline p = jedis.pipelined();
for (String k : keys) p.get(k);
List<Object> replies = p.syncAndReturnAll();
Likely follow-ups
  • Alternative for many keys of one type? MGET/MSET is one command; in Cluster, all keys must be in the same slot.
How does Redis expire keys internally? Senior

What the interviewer is testing: why memory can stay high after TTLs pass, and why reads still never return expired data.

Redis combines two methods. Lazy expiry: when a client reads a key, Redis checks its expiry time. If it is past, the key is deleted and treated as missing. So you never get an expired value. Active expiry: a background job in the main thread, several times per second (10 by default), samples a number of keys that have a TTL (about 20 per round), deletes the expired ones, and if more than about 25 percent were expired it repeats right away, with a time limit so it does not stall requests. This means an expired key that nobody reads can stay in memory for a while, until the sampler finds it. If you create many keys with identical TTLs, a mass expiry happens at once; Redis can spend a lot of time deleting, causing a latency spike. That is another reason for TTL jitter. On replicas, keys are not expired by themselves; the primary sends explicit DEL commands, so replicas stay consistent (a replica hides logically expired keys from reads in recent versions).

Likely follow-ups
  • Does EXPIRE survive a restart? The expiry time is stored as an absolute time in RDB and AOF, so yes; time passing while the server was down counts.
Is Redis only in memory? How does it save data, and how does memory relate to the data size? Basic

What the interviewer is testing: basic understanding of the memory cost model.

The working data set lives in RAM; disk is only used for persistence (snapshots and the append-only file) and to restart. Reading never touches the disk. Memory used is bigger than the raw data: every key carries overhead for pointers, the key string, and expiry data; small objects can use several times more memory than their payload. Typical sizing: a key plus a small string value is on the order of 50 to 100 bytes of overhead. The setting maxmemory caps the memory; when it is reached, the eviction policy decides what happens. Persistence needs extra memory headroom: a fork-based snapshot uses copy-on-write, so under heavy writes the process can use up to double. A developer should be able to estimate memory by multiplying (key count) by (average entry size plus overhead), and to use INFO memory and MEMORY USAGE to check.

4. Data structures and their use cases

Name the main Redis data types and when you would use each. Basic

What the interviewer is testing: breadth, and matching the structure to the problem.

String: the basic type (up to 512 MB): cached JSON, counters with INCR, flags, locks. Hash: a map of fields to values, good for an object such as a user, where you can read or update one field without loading the rest. List: a linked-list style sequence, push and pop at both ends in O(1); used for simple queues, recent activity feeds, and capped logs. Set: unique unordered members; tags, unique visitors, and set math (SINTER for common friends). Sorted set (ZSET): unique members each with a numeric score, kept in order; leaderboards, priority queues, time-based windows, rate limiting. Stream: an append-only log with consumer groups; event processing. Bitmap and HyperLogLog: compact flags per user id, and approximate unique counts with 12 KB per counter and about 0.8 percent error. Geo: store coordinates and query by radius. Newer: JSON and search modules (Redis Stack, and built in Redis 8).

Store a user object: JSON string or hash? Intermediate

What the interviewer is testing: trade-offs and not defaulting to one answer.

A JSON string is simplest: one GET returns the whole object, you deserialize it, done. It is great when you always read and write the whole thing, and when the object has nesting. The downside is that updating one field means reading, changing and writing the whole value, which is not atomic, and the size cost grows with the object. A hash stores fields separately: HSET user:7 name Asha plan pro. You can read one field with HGET, increment a field atomically with HINCRBY, and update a single field without touching others. It cannot hold nested objects directly, and before Redis 7.4 you could not expire individual fields, only the whole key. Small hashes are stored in a compact encoding (listpack), using less memory than many separate string keys. My rule: whole-object cache means a string, partial updates and counters per object means a hash.

HSET user:7 name "Asha" plan "pro" logins 0
HINCRBY user:7 logins 1
HGET user:7 plan
How does a sorted set work, and what are its complexities? Intermediate

What the interviewer is testing: know the structure behind the commonly used leaderboard type.

A sorted set holds unique members, each with a floating-point score, always ordered by score (ties broken alphabetically by member). Internally, large sorted sets use a skip list plus a hash table. The skip list is layered linked lists that allow search, insert and delete in O(log N), and range reads in O(log N + M), where M is the number of items returned. The hash table gives O(1) lookup of a member's score. Small sorted sets use a compact listpack instead. Key commands: ZADD (add or update score), ZINCRBY, ZRANGE (with REV, BYSCORE, BYLEX in Redis 6.2 and later), ZRANK/ZREVRANK (position), ZRANGEBYSCORE, ZREM, ZREMRANGEBYSCORE, ZCARD. Because rank queries are O(log N), you can find any player's rank among millions without scanning.

Can you use a Redis list as a queue? What are the limits? Intermediate

What the interviewer is testing: reliability awareness, and when to move to streams or a real broker.

Yes, for simple cases. Producers do LPUSH queue job, consumers do BRPOP queue 5, a blocking pop that waits up to 5 seconds, so they do not busy-poll. The limits are about reliability. Once a consumer pops a job, Redis forgets it. If the consumer crashes before finishing, the job is lost. A safer variant is LMOVE (or the older RPOPLPUSH) that atomically moves the job to a "processing" list, then removes it after success; a reaper re-queues jobs stuck too long. Still, you build acknowledgements, retries, dead-letter handling and delays yourself. For anything important, use Streams with consumer groups, which give acknowledgements and pending lists, or a real message broker (Kafka, RabbitMQ, SQS). Libraries such as Sidekiq-style tools or Redisson build more structure on top.

What are bitmaps and HyperLogLog, and when are they worth it? Intermediate

What the interviewer is testing: approximate and compact data structures for analytics.

A bitmap is a string treated as an array of bits. SETBIT active:2026-11-17 1234567 1 marks user id 1234567 as active that day. One bit per user means 10 million users fit in about 1.2 MB. BITCOUNT gives the number of active users, and BITOP AND across days gives users active on all of them. It works best when ids are dense integers. HyperLogLog counts distinct items approximately. PFADD visitors:2026-11-17 user42, then PFCOUNT. Each HLL uses at most about 12 KB no matter how many items, with a standard error of about 0.81 percent. You cannot list the members or remove them, only count and merge (PFMERGE). Use HLL for "unique visitors" at big scale, and a set only when you need exact answers or the members themselves.

What are Redis internal encodings, and why should a developer care? Senior

What the interviewer is testing: memory awareness and why many small keys can be wasteful.

Redis picks a compact or a general representation per key, based on size. Small hashes, lists, sets and sorted sets use listpack (a flat, packed array; it replaced ziplist in Redis 7.0), which is very memory efficient but O(N) to search, fine for a few hundred elements. When the element count or the value size passes configured limits (for example hash-max-listpack-entries 128 and hash-max-listpack-value 64 bytes), Redis converts to the general form: hash table, skip list, or quicklist (a linked list of listpacks) for lists. Integers in a set can use a compact intset. Strings use SDS (simple dynamic strings), with the int, embstr and raw encodings. You can check with OBJECT ENCODING key. The practical lesson: storing a million small objects as hashes with a few fields is much cheaper than a million separate string keys, and bucketing small items into hashes saves memory.

OBJECT ENCODING user:7        # listpack or hashtable
MEMORY USAGE user:7

5. Persistence and replication

Explain RDB and AOF persistence and compare them. Intermediate

What the interviewer is testing: durability trade-offs, a staple of Redis interviews.

RDB takes a point-in-time snapshot of the whole data set into one compact file (dump.rdb), on a schedule such as "after 3600 s if at least 1 key changed" or by BGSAVE. Redis forks a child process, and the child writes the file while the parent keeps serving. Restart is fast and the file is small, good for backups, but you lose everything since the last snapshot, possibly minutes. AOF (append-only file) logs every write command. On restart Redis replays the log. The appendfsync setting decides when data is forced to disk: always (every write, safest, slow), everysec (the default; lose at most about one second), or no (the OS decides). The AOF grows, so Redis periodically rewrites it into the shortest list of commands that rebuilds the data (since Redis 7.0 this uses a base file plus incremental files, called multi-part AOF). AOF is more durable but larger and slower to load. Many setups enable both; if both are on, Redis loads the AOF at restart since it is more complete. Pure cache use can run with no persistence at all.

Likely follow-ups
  • Which one for a pure cache? Neither, or RDB only so a restart is not cold. For primary data, AOF with everysec, plus replicas.
What happens when Redis forks for BGSAVE or AOF rewrite, and why can it cause latency or memory spikes? Senior

What the interviewer is testing: an understanding of a real operational side effect developers hit.

Redis calls fork() to make a child process. The child sees a frozen copy of memory through copy-on-write: parent and child share the same memory pages until one of them changes a page, at which point the OS copies that page. So right after the fork, extra memory is small. But while the child writes the snapshot (seconds to minutes), the parent keeps taking writes, and each touched page is copied. Under a heavy write load, memory use can approach double. Also the fork itself must copy the page tables of the process, which for a very large instance (tens of GB) can pause the main thread for tens or hundreds of milliseconds, visible as a latency spike. Mitigations: keep headroom (do not run at 80 percent of the host's RAM), keep instances moderate in size, take snapshots on a replica instead of the primary, avoid very frequent saves, and watch latest_fork_usec in INFO. Linux transparent huge pages make this worse, so ops teams turn them off.

How does Redis replication work? Intermediate

What the interviewer is testing: async replication and its consequences.

A replica connects to the primary with REPLICAOF host port. On the first connection it does a full sync: the primary forks and creates an RDB snapshot, sends it, and meanwhile buffers new writes, then sends the buffered writes. After that, the primary streams every write command to each replica continuously. If a replica disconnects for a short while, it reconnects and asks for just the missed part with partial resync (PSYNC), which works if the missing data still sits in the primary's replication backlog, a circular buffer (1 MB by default, can be set larger). If the gap is too big, a full sync happens again, which is costly. Replication is asynchronous by default: the primary answers the client first, then sends to replicas. So a replica can be slightly behind, and writes acknowledged to the client can be lost if the primary dies before they replicate. Replicas are read-only by default, used for read scaling, backups and failover. WAIT numreplicas timeout can block until some replicas have acknowledged, which reduces but does not eliminate the loss window.

Can you read from replicas for scaling? What are the catches? Intermediate

What the interviewer is testing: knowing that replica reads are stale reads.

Yes, replicas can serve reads and so multiply read capacity, and they take load off the primary. The catches: replication is asynchronous, so a replica may return a value older than one you just wrote. For a cache that is usually fine, since it is already allowed to be stale. For "write then read the same key" you may see old data, so read from the primary for that path. Another catch: if a replica is far behind or was just reconnected, its data may be quite old, so check lag if you care. Clients support it differently: Lettuce has ReadFrom settings (for example REPLICA_PREFERRED), Redisson and Jedis have their own options. In Cluster, a client must send READONLY on the replica connection to allow reads. Also remember that replica reads do not help a hot key problem fully, nor write throughput.

Your service stores sessions in Redis. What persistence and availability setup do you choose? Senior

What the interviewer is testing: deciding from the cost of losing the data, not from habit.

Ask first: what happens if all sessions vanish? If users just log in again, that is annoying but tolerable, and I do not need strong durability. Then I would use a primary with one or two replicas and automatic failover (Sentinel, or a managed service with multi-AZ), with RDB snapshots or AOF everysec so a restart is not totally empty. If losing sessions is costly (for example a long checkout), I would still accept that async replication can lose the last second of writes, and I would keep critical state in the database anyway, keeping only a session id and a small amount of data in Redis. I would avoid appendfsync always because it destroys throughput. If the product needs zero loss, Redis with async replication is the wrong primary store, and the database should be the source of truth with Redis as a cache of it.

6. High availability: Sentinel and Cluster

What does Redis Sentinel do, and how does failover work? Intermediate

What the interviewer is testing: high availability for a single-shard setup and the idea of quorum.

Sentinel is a set of separate processes (run at least three) that watch a primary and its replicas. They do four jobs: monitoring, notification, automatic failover, and telling clients where the current primary is. Each Sentinel pings the nodes. If one cannot reach the primary for down-after-milliseconds, it marks it as subjectively down. When a quorum (for example 2 of 3) agree, it becomes objectively down. The Sentinels then elect a leader among themselves, which picks the best replica (by priority, replication offset, and run id), promotes it with REPLICAOF NO ONE, and points the other replicas to it. Clients ask Sentinel for the current primary address (SENTINEL get-master-addr-by-name), so a Sentinel-aware client reconnects to the new primary. Sentinel gives high availability but not sharding: all data still fits on one primary. And because replication is async, a failover can lose the latest writes.

Likely follow-ups
  • Why three Sentinels and not two? A majority is needed; with two, losing one leaves no majority.
  • What is split brain? An old primary cut off by the network still accepts writes while a new one is promoted; those writes are lost when it rejoins as a replica. min-replicas-to-write limits it.
How does Redis Cluster shard data? Explain hash slots. Intermediate

What the interviewer is testing: sharding model, and the constraints it puts on application code.

Redis Cluster splits the key space into 16384 hash slots. For each key, the slot is CRC16(key) mod 16384. Each master node owns a range of slots, for example three masters own 0-5460, 5461-10922 and 10923-16383. Each master usually has one or more replicas for failover. Adding a node means moving some slots (and their keys) to it, with no rehashing of everything. A smart client downloads the slot map and sends each command straight to the right node. If its map is old, the node replies MOVED slot host:port (permanent move, update the map) or ASK (a temporary redirect during a slot migration). The big rule for developers: commands that touch several keys (MGET, transactions, Lua scripts, SUNION) work only if all keys are in the same slot. You force this with hash tags: only the text inside {} is hashed, so {user:7}:profile and {user:7}:cart land together. Cluster supports only database 0.

Likely follow-ups
  • Why 16384 slots? A compact node-gossip message size and enough granularity for up to about 1000 nodes.
  • Specialist boundary: planning shard counts, resharding operations and cluster tuning is an operator topic.
How does a Cluster handle node failure, and can it lose writes? Senior

What the interviewer is testing: failure behaviour and consistency limits of Cluster.

Nodes gossip with each other over a cluster bus. If a master does not respond for cluster-node-timeout, other nodes mark it as possibly failed, and when a majority of masters agree, it is failed. One of its replicas then asks the masters to vote, and the winner becomes the new master of those slots. The cluster stays available as long as every slot has a reachable owner and a majority of masters is up. Otherwise (with default settings) the cluster stops accepting commands for the affected slots, because it prefers consistency over availability for those. Writes can still be lost: replication between a master and its replica is async, so a write that was acknowledged and not yet copied vanishes when the replica is promoted. The same happens in a network partition: a master isolated with a minority of the cluster keeps accepting writes for a time until it notices; those writes are discarded later. For developers, this means the client must handle MOVED, ASK, CLUSTERDOWN and timeouts with retries.

Sentinel or Cluster: how do you choose? Intermediate

What the interviewer is testing: sizing judgement and awareness of the cost of sharding.

The question is whether the data and traffic fit on one node. If the data fits in memory on one machine and one node can handle the throughput (often 100k+ simple ops per second), use a primary with replicas and failover (Sentinel, or a managed service that does it for you). It is simpler: all commands, transactions, scripts and multiple databases work. If you need more memory than one machine, or more write throughput than one core can do, use Cluster to shard. The price: multi-key operations are limited to a slot, you design keys with hash tags, clients must be cluster-aware, and operations are harder. Another path is client-side sharding or a proxy such as Twemproxy or Envoy, which are less common now. Managed offerings (ElastiCache, Azure Cache, Memorystore) hide much of this. I start simple and move to Cluster only when measurements say so.

7. Eviction, memory and slow commands

What happens when Redis reaches maxmemory? Explain the eviction policies. Intermediate

What the interviewer is testing: the knobs that decide whether Redis drops data or rejects writes.

maxmemory sets the memory limit. When it is reached, maxmemory-policy decides what to do. The default is noeviction: reads still work but writes that need memory fail with an error (OOM). That is right for a primary data store, wrong for a cache. For caches you choose an eviction policy. allkeys-lru evicts the least recently used key from all keys, a sound default for general caches. allkeys-lfu evicts the least frequently used (Redis 4.0 and later), better when a few keys are consistently popular and scans should not push them out. volatile-lru, volatile-lfu and volatile-ttl only consider keys that have a TTL; volatile-ttl removes the ones expiring soonest. allkeys-random and volatile-random pick randomly. The volatile policies fall back to an error if no key has a TTL, which surprises people. Rule: cache-only instance, use allkeys-lru or allkeys-lfu; mixed instance with must-keep data, use a volatile policy and give only cache keys a TTL (or better, use separate instances).

CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lfu
INFO stats      # evicted_keys, expired_keys, keyspace_hits, keyspace_misses
Is Redis LRU exact? How does it work, and what is LFU? Senior

What the interviewer is testing: knowing the real implementation, a classic follow-up to "implement an LRU cache".

No, it is approximate. A real LRU needs a linked list updated on every access, which costs memory and time. Instead, each key stores a small 24-bit field with a coarse last-access time. When eviction is needed, Redis samples a few random keys (maxmemory-samples, default 5), and evicts the oldest among them. Raising it to 10 gets close to true LRU at some CPU cost. Newer versions also keep a pool of good candidates across rounds. LFU (Redis 4.0) reuses the same 24 bits: 16 bits for a last-decrement time and 8 bits for a logarithmic access counter. The counter grows probabilistically (more accesses are needed to move up as it gets higher, controlled by lfu-log-factor) and decays over time (lfu-decay-time), so old popularity fades. LFU protects frequently used keys from a one-time scan that would flush an LRU cache. In an interview, you may be asked to code an LRU cache: a hash map plus a doubly linked list gives O(1) get and put (Java: LinkedHashMap with access order).

Memory keeps growing even though you set TTLs. What do you check? Intermediate

What the interviewer is testing: a systematic approach to memory problems.

First look at INFO memory and INFO keyspace. The keyspace line shows how many keys have a TTL: keys=5000000,expires=1200000 means most keys never expire. Likely causes: some code path writes keys without TTL (a plain SET after SETEX removes the TTL; INCR on a new key creates it without a TTL); a key pattern with unbounded cardinality, such as one key per request id or per user per minute; collections that only grow (a list, set or stream with no trimming); big keys; lots of expired keys still not deleted because the sampler is behind; and fragmentation (mem_fragmentation_ratio well above 1.5), where allocated memory is much more than used. Then sample with --bigkeys and SCAN with TTL to find key prefixes without expiry. Fixes: add TTLs, cap collections (LTRIM, XTRIM MAXLEN), change the key design, set maxmemory with an eviction policy so growth cannot take the host down.

Redis latency suddenly spikes. How do you find the cause? Senior

What the interviewer is testing: a methodical diagnosis path, using Redis's own tools.

Because commands run one at a time, a spike usually means something took a long time on the main thread, or the machine or network was busy. I check, in order: (1) the slow log (SLOWLOG GET 20), which lists commands that exceeded a threshold (default 10 ms, execution time only, not network or queue time); typical culprits are KEYS, HGETALL on big hashes, SMEMBERS, large DEL, SORT, ZUNIONSTORE and long Lua scripts. (2) INFO commandstats to see which commands burn time. (3) Persistence: fork time (latest_fork_usec), AOF fsync stalls with appendfsync always or a slow disk. (4) Mass expiry: a flood of keys expiring in the same second. (5) Swapping: if the OS swaps Redis memory to disk, latency explodes; check memory limits. (6) Network: connection count, big replies saturating bandwidth. (7) Client side: a connection pool that is too small, or a slow client reading big replies. redis-cli --latency and LATENCY DOCTOR help. The fix follows the cause: replace O(N) commands with SCAN-based ones, split big keys, add jitter, add memory headroom.

Which Redis commands are dangerous on big collections, and what are the safe alternatives? Intermediate

What the interviewer is testing: knowing command complexity, since the thread is shared.

Any command that is O(N) in the size of a collection is risky when N is large: KEYS, HGETALL, HKEYS, SMEMBERS, LRANGE 0 -1, ZRANGE 0 -1, SUNION and SINTER of large sets, SORT, FLUSHALL, and DEL of a huge key. Safer ways: SCAN, HSCAN, SSCAN, ZSCAN for walking; ranges with limits (ZRANGE key 0 99) for paging; UNLINK for deleting; FLUSHALL ASYNC for flushing; and splitting big collections. The documentation page of every command lists its time complexity, a habit worth building. Also be careful with Lua scripts that loop over big sets, since the script blocks everyone while it runs. Use rename-command or ACLs to disable KEYS, FLUSHALL and CONFIG for application users.

8. Transactions, Lua scripts, pub/sub and streams

How do Redis transactions work, and how are they different from SQL transactions? Intermediate

What the interviewer is testing: knowing Redis transactions have isolation but no rollback.

MULTI starts a transaction, then commands are queued (the server answers QUEUED), and EXEC runs them all in sequence with no other client's command in between. So you get isolation and atomic execution order. But there is no rollback. If one command fails at run time (for example INCR on a non-number), the other commands still run. If a command has a syntax error when queued, the whole transaction is discarded at EXEC. DISCARD cancels a queued transaction. For optimistic locking there is WATCH key: if a watched key is changed by another client before EXEC, the EXEC returns nil and nothing runs; your code retries. A SQL transaction gives you rollback, isolation levels and durability tied to commit; Redis gives you a simple batch. Also, you cannot read a value inside the transaction and use it in a later command of the same transaction, since the commands are only queued, not executed until EXEC. For that logic you use Lua.

WATCH balance:7
v = GET balance:7           # app reads
MULTI
SET balance:7 (v - 50)
EXEC                        # nil if someone else changed balance:7
When and why would you use a Lua script in Redis? Intermediate

What the interviewer is testing: how to make a multi-step read-modify-write atomic.

A Lua script runs inside Redis as one unit. Because the server is single threaded, nothing else runs while it executes, so your whole read-decide-write logic is atomic, and costs one round trip instead of several. It is the usual answer to "check a value, then change it" problems: safe lock release (delete the key only if it holds my token), a token bucket rate limiter, conditional updates with version checks, or "decrement stock only if above zero". Rules: pass every key the script touches in the KEYS array (needed for Cluster routing) and other values in ARGV; keep it short, since a slow script blocks all clients (there is a busy-script limit of 5 seconds by default, after which other clients get an error); make it deterministic. Use EVALSHA with the script hash to avoid resending the script text. Redis 7.0 added Functions, scripts stored on the server and loaded as a library, replacing the need to load scripts from every client.

-- release lock only if I still own it
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
How does Redis pub/sub work, and what are its limits? Intermediate

What the interviewer is testing: knowing it is fire and forget, with no storage.

Subscribers run SUBSCRIBE channel (or PSUBSCRIBE news.* for patterns). A publisher runs PUBLISH channel message, and Redis pushes the message to every client subscribed at that moment, and returns the number of receivers. Messages are not stored. If a subscriber is disconnected, slow or not yet subscribed, it never sees the message, and there is no acknowledgement or replay. A slow subscriber's output buffer can grow, and Redis disconnects it if it passes client-output-buffer-limit pubsub. Good uses: ephemeral notifications, cache invalidation broadcasts to local caches, chat presence, live updates where missing one is fine. Not good for: jobs that must be processed, order events, anything needing delivery guarantees. In Cluster, a published message is broadcast to all nodes, which costs bandwidth; Redis 7.0 added sharded pub/sub (SPUBLISH, SSUBSCRIBE) to confine it to a shard. For guaranteed delivery, use Streams or Kafka.

What are Redis Streams and consumer groups? How are they different from pub/sub? Senior

What the interviewer is testing: durable messaging with acknowledgements, and when to use it over a broker.

A stream (Redis 5.0) is an append-only log stored in a key. XADD adds an entry with an auto-generated id (millisecond time plus sequence) and some fields. Entries stay until you trim them (XTRIM or MAXLEN on XADD), so late readers can replay history with XRANGE or XREAD. Consumer groups let several workers share a stream: XGROUP CREATE, then each worker calls XREADGROUP, and Redis delivers each entry to just one consumer in the group. The entry goes into the group's pending entries list until the consumer calls XACK. If a worker dies, the entry stays pending; another worker can claim it with XAUTOCLAIM (Redis 6.2) after an idle time and retry. So you get at-least-once delivery and work sharing. Compared to pub/sub: streams persist, are replayable and acknowledged. Compared to Kafka: simpler to run and good for modest volume, but limited by memory of one shard, no built-in partitioning of one stream across nodes, and a weaker ecosystem for big data pipelines.

XADD orders * orderId 991 amount 40
XGROUP CREATE orders billing $ MKSTREAM
XREADGROUP GROUP billing w1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders billing 1731800000000-0

  • How do you avoid duplicates? Make handlers idempotent, since a claim after a crash can redeliver.

9. Distributed locks

How do you implement a distributed lock with a single Redis? Intermediate

What the interviewer is testing: the safe pattern and why each piece exists.

Acquire with one atomic command: SET lock:order:42 <random-token> NX PX 30000. NX means set only if the key does not exist, so only one client wins. PX 30000 gives a 30 second lease, so if the holder crashes the lock disappears by itself. The value is a unique random token for this client. To release, you must delete the key only if it still holds your token, and the compare and delete must be atomic, so use a Lua script. Without the token check, this can happen: your work takes longer than the lease, the lock expires, another client acquires it, and then you finish and delete their lock. Older code used SETNX then EXPIRE as two commands, which is unsafe: a crash between them leaves a lock that never expires. If the lock is not acquired, retry with a short sleep and jitter, up to a time limit.

SET lock:order:42 7f3a9c NX PX 30000
-- release (Lua): only if token matches
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1]) else return 0 end
What is Redlock, and what is the Kleppmann versus Antirez debate? Senior

What the interviewer is testing: can you discuss correctness of distributed locks and not just recite a recipe.

A single Redis lock fails if that Redis dies and the replica that takes over did not get the lock key yet (async replication), so two clients can hold the lock. Redlock, proposed by Redis's author (Salvatore Sanfilippo, "antirez"), uses N independent Redis masters, usually five. The client takes the current time, tries to acquire the lock on all of them with the same key, token and short timeouts, and counts the lock as held if it got a majority (3 of 5) and the elapsed time is less than the lease. If it fails, it releases all. In 2016 Martin Kleppmann wrote a critique. His points: Redlock assumes bounded network delay, process pauses and clock drift, which real systems do not guarantee. A client can pause (GC, page fault) after getting the lock, the lease expires, another client takes it, and the first client resumes believing it still holds the lock. Time jumps on a Redis node can also expire locks early. His advice: if the lock is for efficiency (avoid duplicate work), a single Redis lock is fine; if it is for correctness, you need a fencing token (a number that increases with each lock grant, checked by the resource) and a system that gives that, such as ZooKeeper or etcd, or better, the database's own constraints. Antirez replied that the timing assumptions are acceptable in practice and that fencing is possible, but Redlock's random token does not give a monotonic one. My answer in an interview: use Redis locks for efficiency, and for anything where a double run causes damage use database transactions, unique constraints, or optimistic version checks, as the final guard.

Likely follow-ups
  • What is a lock watchdog? Libraries such as Redisson renew the lease periodically while the holder is alive, which avoids picking a fixed time, but does not remove the pause problem.
  • Is the Redisson lock Redlock? Redisson has a RedLock class, but its plain RLock uses a single node with a Lua script and a watchdog (default lease 30 s).
What are the practical pitfalls of Redis locks in application code? Senior

What the interviewer is testing: experience with real lock bugs.

Main pitfalls: (1) Lease shorter than the work. Pick the lease from the p99 duration with margin, or use a renewing watchdog, and have the work check it is still within the lease. (2) Releasing someone else's lock, solved by the token check. (3) No reentrancy. The same thread asking twice deadlocks itself unless the library supports reentrant locks. (4) Locks that never expire. Always set a TTL. (5) Failover loses the lock with async replication, so assume rare double holders and make the protected action idempotent. (6) Lock contention: a single global lock becomes a bottleneck; use fine grained keys (per order, not per system). (7) Busy waiting. Retry with backoff and jitter, and a maximum wait. (8) Cluster: the lock key lives on one node; fine, but remember that node's failover. A design that does not need a lock is better: use a database unique key, a compare-and-set update (UPDATE ... WHERE version = ?), or a queue with one consumer per key.

10. Patterns: rate limiter, leaderboard, session store

Design a rate limiter with Redis. Compare the algorithms. Senior

What the interviewer is testing: a favourite design question; the algorithm choice and atomicity.

The simplest is a fixed window counter: key rate:user7:2026-11-17T10:15 (the current minute), INCR it, set the expiry on first use, reject if above the limit. It is cheap but allows a burst of double the limit across a window boundary (100 at 10:15:59 and 100 at 10:16:00). A sliding window log keeps each request time in a sorted set: remove entries older than the window (ZREMRANGEBYSCORE), count with ZCARD, add the new one. It is exact but uses memory per request. A sliding window counter mixes the current and previous window counts with a weight, a good compromise with two small counters. A token bucket stores the token count and last refill time; each request refills by elapsed time and takes one token; it allows bursts up to the bucket size with a steady average rate, and is the common choice for APIs. Whichever you pick, the read-check-write steps must be atomic, so do them in a Lua script, or at least use INCR and set the expiry only when the count is 1 (or use SET NX EX first). Key by user, API key or IP, return 429 with Retry-After, and decide whether to fail open or closed if Redis is down; most APIs fail open.

local c = redis.call("INCR", KEYS[1])

Design a real-time leaderboard with Redis. Intermediate

What the interviewer is testing: use of the sorted set and awareness of its limits.

Use one sorted set per board, for example lb:global, with the player id as the member and the score as the score. ZADD lb:global 1500 player:7 sets a score; ZINCRBY lb:global 20 player:7 adds points atomically. Top 10: ZRANGE lb:global 0 9 REV WITHSCORES (or ZREVRANGE in older versions). A player's rank: ZREVRANK lb:global player:7, zero-based, in O(log N). The neighbours of a player: get the rank, then a range around it. Time-bound boards (daily, weekly) use a key per period, lb:2026-11-17, with a TTL, and sums are done with ZUNIONSTORE. Ties: scores are doubles; to break ties by earliest achieved, encode the time into the fractional part of the score. The database still holds the truth, and the sorted set can be rebuilt from it. Limits: one sorted set lives on one node; for hundreds of millions of members, shard by player range or region and merge top lists, and the memory use is notable (about 50 to 100 bytes per member).

How would you use Redis as a session store, and what should you watch for? Intermediate

What the interviewer is testing: the stateless-service pattern and its availability implications.

Web servers behind a load balancer should be stateless, so any instance can serve any request. The session data therefore lives in a shared store such as Redis. The browser holds only a session id in a cookie (random, long, HttpOnly, Secure). Redis holds session:<id> as a hash or string, with a TTL equal to the idle timeout, refreshed on each request (a sliding expiry) with EXPIRE. In Spring, Spring Session with Redis does this with an annotation and configuration. Things to watch: Redis availability becomes login availability, so use replication and failover; decide what happens on loss (users log in again); keep sessions small, avoid putting big objects in them; set an absolute maximum lifetime in addition to the idle one; secure the Redis network and use TLS and auth; and be careful about serialization, since changing a session class between deploys can make old sessions unreadable. Alternatives are signed stateless tokens (JWT), which avoid the lookup but make early revocation harder.

How do you implement idempotency or de-duplication of requests with Redis? Intermediate

What the interviewer is testing: use of SET NX as a cheap atomic claim.

Each request carries an idempotency key (for example a client-generated id). On arrival the service runs SET idem:<key> "processing" NX EX 86400. If it returns OK, this is the first time, so process the request and then store the final result under the same key. If it returns nil, the request was seen before: if the stored state is the result, return it; if it is still "processing", return a conflict or ask the caller to retry shortly. The TTL limits memory. This protects against retries from clients and message redelivery. The caveat is durability: if Redis loses the key (failover, eviction), a duplicate may pass, so for money or inventory, back it with a unique constraint in the database too. Redis gives the fast path, the database gives the guarantee.

11. Spring Cache, clients and practical usage

How does Spring's cache abstraction work with Redis? Intermediate

What the interviewer is testing: daily Spring knowledge, and the proxy pitfalls.

You enable it with @EnableCaching and add annotations on methods. @Cacheable("users") runs the method on a miss and stores the result; on a hit the method is skipped. @CachePut always runs the method and updates the cache. @CacheEvict removes an entry (or all, with allEntries = true). The cache key defaults to the method arguments; set it with SpEL, key = "#id". You can skip caching with condition or unless (for example unless = "#result == null"). Under the hood Spring wraps the bean in a proxy, an AOP interceptor, which consults a CacheManager. With Redis, you use RedisCacheManager (from spring-boot-starter-data-redis plus spring.cache.type=redis). Defaults to know: entries have no TTL unless you set one in RedisCacheConfiguration.entryTtl, and the default value serializer is JDK serialization, which is bulky and fragile; configure JSON for readability. Keys are prefixed with the cache name, like users::42.

@Cacheable(cacheNames = "users", key = "#id", unless = "#result == null")
public User find(long id) { return repo.findById(id).orElse(null); }

@CacheEvict(cacheNames = "users", key = "#u.id")
public void update(User u) { repo.save(u); }

@Bean RedisCacheManager cacheManager(RedisConnectionFactory f) {
  var cfg = RedisCacheConfiguration.defaultCacheConfig()
      .entryTtl(Duration.ofMinutes(10))
      .serializeValuesWith(SerializationPair.fromSerializer(
          new GenericJackson2JsonRedisSerializer()));
  return RedisCacheManager.builder(f).cacheDefaults(cfg).build();
}
What are the common pitfalls with @Cacheable? Senior

What the interviewer is testing: real experience with Spring's proxy model and cache semantics.

(1) Self-invocation: calling a @Cacheable method from another method of the same class bypasses the proxy, so no caching happens. Move it to another bean. (2) The annotated method must be public, and the class must be proxyable. (3) No TTL by default, so stale data lives forever. (4) Stampede: concurrent misses all run the method; sync = true makes one thread per key per JVM load it, but not across instances, and it is not supported together with some options. (5) Null caching: by default Redis cache can store nulls (unless disabled), so a miss for a missing id can be cached; set unless or disableCachingNullValues() on purpose. (6) Serialization: a class change between deployments makes JDK-serialized entries unreadable, giving errors after a deploy; version the cache name or use a tolerant JSON format. (7) Key collisions: two methods with the same cache name and arguments share entries; use explicit keys. (8) Transactions: a cache eviction can run before the database transaction commits, so a concurrent reader refills the old value; use TransactionAwareCacheManagerProxy or evict after commit. (9) Cache errors failing the request: configure a CacheErrorHandler so a Redis outage degrades into a miss rather than a 500.

Lettuce versus Jedis versus Redisson: how do they differ? Intermediate

What the interviewer is testing: client library knowledge, connection handling and thread safety.

Jedis is the simple, older client. A Jedis connection is not thread safe, so you take one from a pool (JedisPool), use it, and return it; blocking, one connection per concurrent call. Lettuce is built on Netty and non-blocking. One connection can be shared by many threads safely, since commands are multiplexed over it; it supports async and reactive APIs, Sentinel, Cluster, and automatic pipelining. It is the default in Spring Boot since version 2. Pooling is needed only for blocking commands or transactions. Redisson is a higher-level client that offers Java-style distributed objects: locks (with a watchdog), semaphores, maps, queues, rate limiters, and a local cache. It is convenient but adds a layer and its own conventions. In all cases, set timeouts (connect and command), size the pool, enable cluster topology refresh, and have retry rules with backoff; a missing timeout is how one slow Redis hangs all application threads.

What should your service do when Redis is down or slow? Senior

What the interviewer is testing: resilience thinking: cache failure must not become an outage.

First decide what Redis is for. If it is a cache, the service should keep working, slower, by falling back to the database, but protected: a Redis outage means a 100 percent miss rate, which can crush the database (an avalanche). So I use short client timeouts (tens to a few hundred milliseconds), a circuit breaker that stops calling Redis for some seconds after repeated failures, a bulkhead or rate limit on the fallback database path, and possibly a small local cache for the hottest data. Handle exceptions around cache calls so they never break the request. Return degraded responses when needed. If Redis holds sessions, plan the behaviour: log users out, or fall back to a read-only mode. If Redis is used for locks or rate limiting, choose fail open or fail closed deliberately: a rate limiter usually fails open, a payment lock usually fails closed. Test this with a chaos drill: stop Redis in staging and watch the database.

How do you secure Redis from an application point of view? Intermediate

What the interviewer is testing: basic hygiene; open Redis servers are a well-known source of breaches.

By default Redis has no password and trusts the network, so it must never be exposed to the internet. Steps: bind to private interfaces and use network rules (security groups); enable authentication with ACL users (Redis 6.0), giving the application a user limited to the commands and key patterns it needs, and disabling dangerous commands like FLUSHALL, CONFIG, KEYS, DEBUG; use TLS for traffic between app and Redis, especially across hosts; keep secrets out of code (secret manager); do not store sensitive data in clear if it is not needed; and keep the version patched. Cached data is still real data: a cache of personal data falls under the same privacy rules and should have a TTL and a delete path (for example for a deletion request).

12. Redis versus other options

Redis or Memcached: how do you choose? Basic

What the interviewer is testing: informed comparison, not a fan opinion.

Both are in-memory key-value stores used for caching. Memcached is simple: only string (blob) values, multi-threaded so it uses many CPU cores on one machine, a slab allocator, LRU eviction, no persistence, no replication in the core (clients shard across nodes by consistent hashing). It is a great plain cache at very high throughput with simple memory behaviour. Redis offers rich data types, persistence, replication, automatic failover, Cluster, Lua, pub/sub, streams, atomic operations on structures, and per-key TTLs with several eviction policies. Command execution is mostly single-threaded. Choose Memcached when you only need a simple, big, multi-core blob cache and want the simplest operations. Choose Redis when you need data structures (counters, sets, sorted sets), atomic operations, high availability, persistence, or features like locks, queues and rate limiting. In practice Redis is the default choice because one tool covers many needs; but a pure cache of large objects on a big multi-core machine is a place where Memcached still shines.

Can Redis replace your database? When is it a primary store? Senior

What the interviewer is testing: knowing the limits of memory-first storage and async durability.

Sometimes, for the right data. Good primary-store cases: ephemeral or rebuildable state such as sessions, rate limit counters, leaderboards, real-time presence, feature flags, and queues of short-lived jobs. Why not for everything: (1) data must fit in RAM, which is costly at large sizes; (2) durability is weaker, since AOF everysec and async replication can lose the last second of writes; (3) there is no rich query language or joins, and secondary indexes need modules (Redis Search) or manual maintenance; (4) transactions are limited, with no rollback; (5) Cluster restricts multi-key operations. For money, orders, user accounts and anything needing audit and strong consistency, use a relational or other proper database, and use Redis in front of it. The practical line: if you can rebuild it, Redis may be the primary; if losing a second of it costs money, it should not be.

When is a local in-process cache (Caffeine) better than Redis? Intermediate

What the interviewer is testing: not reaching for Redis when a simpler cache fits.

A local cache avoids the network, so reads cost nanoseconds to microseconds and cannot fail due to a network. It is ideal for small, hot, read-mostly data that tolerates short staleness: reference data, configuration, feature flags, parsed templates, public keys, results of pure computations. Caffeine gives size-based eviction (Window TinyLFU, which has a better hit rate than plain LRU), time-based expiry, and refresh-after-write. Its weaknesses: each instance has its own copy (more total memory, and copies can differ), a restart starts cold, memory is part of the JVM heap and adds to GC load, and invalidation across instances needs a broadcast. Redis is better when data is large, must be shared and consistent between instances, must survive an app restart, or needs shared counters and locks. Many systems use both: Caffeine for L1 with a few seconds of TTL, Redis for L2.

What happened with the Redis license, and what is Valkey? Intermediate

What the interviewer is testing: awareness of the ecosystem, since it affects what a team runs.

Until Redis 7.2, Redis was under the permissive BSD license. In March 2024, Redis Ltd moved newer versions (7.4 onward) to a dual source-available license (RSALv2 or SSPLv1), which restricted cloud providers from offering it as a managed service without a deal. In response the Linux Foundation, with AWS, Google, Oracle and others, created Valkey, a BSD-licensed fork of Redis 7.2.4, which keeps the same protocol and commands, so existing clients work. In 2025, Redis 8 added the AGPLv3 license as an option, making it open source again by the OSI definition. For an application developer: the client code and commands are the same; what changes is which engine your company or cloud provider runs (for example AWS ElastiCache and Memorystore offer Valkey), plus newer features that may differ between the two. I would say this with the caution that license details are best checked at the source.

13. Real-life scenarios

Scenario: after a release, the cache hit rate falls from 95% to 60% and database CPU climbs. What do you do? Senior

What the interviewer is testing: structured diagnosis from the symptom to the key-level cause.

Situation: the release is the obvious suspect, since the load did not change. First checks: compare keyspace_hits and keyspace_misses over time in INFO stats and see when the fall began. Check evicted_keys (memory pressure) and expired_keys (TTL change). Diff the release for anything touching cache keys: a changed key format or version prefix, a new variable (such as user id or timestamp) in the key that made every key unique, a shorter TTL, a changed serializer, or a new code path that bypasses the cache. Steps: sample live keys with SCAN and look at their shape; if keys now include a request-specific part, the cache is full of one-use entries. Check whether deploy caused a cold cache (new key prefix means all misses at first, which is expected and should recover). If it is a bug, hotfix the key, or roll back. If memory is full and evicting, the new entries pushed useful ones out; look at big values or a new key family. Prevent: a hit-rate dashboard and alert per cache name, cache key unit tests, a canary release that watches hit rate, and a rule that key format changes are rolled out with a warm-up.

Scenario: Redis hits maxmemory and the app starts throwing OOM errors on writes. Senior

What the interviewer is testing: knowing the eviction policy, and short-term versus long-term fixes.

Situation: errors like OOM command not allowed when used memory > 'maxmemory'. That message means the policy is noeviction (the default) or a volatile policy with no keys that have a TTL. First checks: INFO memory (used_memory versus maxmemory), INFO keyspace (keys versus keys with expires), CONFIG GET maxmemory-policy, and --bigkeys. Immediate relief: if this is a cache, set maxmemory-policy allkeys-lru (or LFU) so it evicts and keeps working; otherwise raise maxmemory if the host has room, or delete a known junk prefix using SCAN and UNLINK (never KEYS). Find the cause: a key family with no TTL, a growing list or stream, or unbounded key cardinality. Prevent: TTL on every cache key (a code review rule), cap collections, alert at 80 percent memory, separate must-keep data from cache data into different instances, and test with production-like volumes.

Scenario: p99 latency of every service using Redis jumps to 800 ms every few minutes. Senior

What the interviewer is testing: linking periodic spikes to something that blocks the one thread.

Situation: a regular pattern points to a scheduled thing: a background job, snapshot or mass expiry. First checks: SLOWLOG GET for long commands in the same minutes. Look at who runs at that time: a cron job doing KEYS, SMEMBERS on a big set, or a big DEL. Check latest_fork_usec and RDB save times (rdb_last_bgsave_time_sec), since a snapshot on a big instance can pause the server during the fork. Check expiry waves: many keys loaded with the same TTL expiring together. Check AOF with always or a slow disk. Check that the host is not swapping. Steps: correlate with INFO commandstats, LATENCY HISTORY, and the app's own metrics. Fix by cause: replace the heavy command with SCAN or chunks, use UNLINK, add TTL jitter, move snapshots to a replica, add headroom. Prevent: a slow-log alert, code review of Redis commands for complexity, and a rule that batch jobs use SCAN.

Scenario: Redis failed over to a replica and users lost their last few seconds of data. Is that a bug? Senior

What the interviewer is testing: knowing this is expected from async replication, and the options to reduce it.

Situation: not a bug in Redis; it is the design. The primary acknowledged writes, then died before sending them to the replica, so the promoted replica never had them. Checks: compare replication offsets from before the failure (INFO replication, master_repl_offset vs replica offset), see the lag metrics, and check whether a network partition caused an old primary to accept writes that were thrown away. Options: (1) accept it, if the data is a cache or a session. (2) Reduce the window: min-replicas-to-write 1 with min-replicas-max-lag 10 makes a primary refuse writes when it has no connected replica with small lag, which limits the data a split-brain primary can accept. (3) WAIT 1 100 after critical writes, so the client waits until one replica has the write; it narrows the gap but is not a guarantee, since failover may still choose another node. (4) Keep the truth in a durable database and use Redis as a derived copy. (5) For queues, use the database or Kafka. Prevent: write down the recovery point you accept for each Redis use, and test failover in staging.

Scenario: during a flash sale one Redis Cluster node is at 100% CPU while the other nodes are idle. Senior

What the interviewer is testing: hot key recognition in a sharded system.

Situation: the signature of a hot key: one slot, one node. First checks: per-node metrics (ops per second, network out), then find the key: redis-cli --hotkeys on that node (requires an LFU policy), a short MONITOR sample on a replica or in a low-risk window (it is heavy), or client-side counters. Check the value size too: a big value on a hot key saturates the network. Immediate fix: add a local L1 cache of 1 to 5 seconds in the app for that key, which usually removes 90 percent or more of the traffic; serve reads from replicas; or copy the key into N variants (sale:42:0 to sale:42:7) and read a random one, writing all on change. For a hot counter such as stock or likes, split it into sub-counters. Prevent: load test the flash sale path, pre-warm and replicate known hot keys, put a CDN or page cache in front of read-only pages, and add hot-key detection to monitoring.

Scenario: right after a deploy that restarted all pods and flushed a local cache, the database was overwhelmed. Senior

What the interviewer is testing: cold-start behaviour, a stampede on many keys at once.

Situation: every instance started with an empty L1, and perhaps the release also changed the cache key version, so Redis had nothing either. All traffic missed at once. Immediate: shed load: lower traffic with a rate limit or a feature switch, scale out the database read replicas if possible, and let the cache warm; do not restart again, which resets the warm-up. Root causes to check: a simultaneous rolling restart, a key-version bump without warm-up, no single-flight, and all TTLs equal. Fixes: use a rolling deploy with a small batch size and readiness checks so only a few instances are cold at a time; add per-key single-flight locking; pre-warm the hottest keys before routing traffic (a startup task or a warm-up endpoint); keep Redis (L2) warm by not bumping key versions casually, or by dual-reading old and new key versions for a while; use TTL jitter; add a circuit breaker and request coalescing on the database path. Prevent: include cold-start in load tests, and make the deploy checklist say "does this change cache keys?".

Scenario: a user updates their profile but keeps seeing the old data for several minutes. Senior

What the interviewer is testing: tracing an invalidation gap through all the cache layers.

Situation: the data is in the database but a cache still serves the old copy. Checks, layer by layer: browser or CDN (response headers: Cache-Control, Age); L1 local cache per instance (refreshing the page shows old and new data alternately, depending on the instance hit, which is a strong hint); Redis (GET the key and compare, TTL); and the read replica of the database if replication lags. Look at the write path: does it delete the right key? A key built differently on write and read (a tenant or language missing) is a very common bug. Does the delete happen before the transaction commits, so a concurrent read refilled the old data? Did the delete fail silently (exception swallowed)? Was it the race of the slow reader? Fix: correct the key, evict after commit, add retry for failed invalidations, bypass the cache for the user's own reads after a write for a short period. Prevent: an integration test that updates and reads through the real cache, TTL as safety net, and a single helper that builds keys for both read and write.

Scenario: database load spikes, but the cache hit rate looks normal, and the logs show requests for ids that do not exist. Senior

What the interviewer is testing: recognising cache penetration and responding in layers.

Situation: clients ask for random or non-existent ids (a scanner, a bug or an attack). Each one misses, queries the database, finds nothing, caches nothing, and repeats. Hit rate may look fine because normal traffic dominates, while the database still burns. Checks: top requested ids that return 404, source IPs, and database queries returning zero rows. Steps: (1) immediately rate limit or block the offending source at the gateway or WAF. (2) Validate ids early (format, range). (3) Cache negative results with a short TTL (30 to 60 seconds). (4) If the key space of valid ids is bounded and known, put a Bloom filter in front. (5) Return 404 quickly, with minimal work. Prevent: monitor the ratio of not-found results, apply per-client rate limits, and consider the negative TTL against "created just after" cases by deleting the null marker on create.

Scenario: a scheduled job guarded by a Redis lock ran twice at the same time and charged some customers twice. Senior

What the interviewer is testing: the limits of leases, and defence in depth.

Situation: two instances both believed they held the lock. Possible causes: the lease expired while the first run was still going (a long GC pause, a slow downstream call); the release was done without a token check and deleted another run's lock; Redis failed over and the new primary lacked the lock key; a clock or timeout setting made the lease shorter than expected. Checks: job logs with lock acquire and release times, lease length against actual duration, Redis failover events at that time, and the code that releases the lock. Fix: a token plus Lua release; a lease longer than the worst-case run with a renewal watchdog; but most importantly make the charge idempotent: use an idempotency key per customer per billing period and a unique constraint in the database, so a second run is harmless. This is the Kleppmann argument: a lock gives efficiency, only the resource itself can give correctness. Prevent: a fencing token or version check on the charge, an alert on overlapping runs, and a test that forces a pause.

Scenario: every night at 02:00 the database is hit by a wave of queries and the API slows down. Senior

What the interviewer is testing: spotting an avalanche from the periodic pattern.

Situation: the exact time suggests a batch of keys that were all written with the same TTL at the same time, for example a warm-up job at 01:00 with a one-hour TTL, or a daily key such as report:2026-11-17 that expires at midnight UTC. Checks: graph expired_keys per second in Redis, which will show a spike at 02:00; look at the TTL distribution of the key family through a sample (SCAN plus TTL); check the job schedule. Fix: add random jitter to the TTL, spread the warm-up over time or in batches, refresh keys before expiry (a refresh-ahead job), and for must-have hot keys avoid expiry entirely and update by a job. Add the protections for the wave itself: single-flight, a circuit breaker and a rate limiter for the database. Prevent: a TTL policy in code review ("TTL always has jitter") and a dashboard of expiry spikes.

Scenario: Redis becomes unreachable for ten minutes and the whole site goes down, even though Redis is "just a cache". Senior

What the interviewer is testing: resilience, timeouts and graceful degradation.

Situation: the site depended on Redis more than intended. What usually happened: the client had no or a long timeout, so threads were stuck waiting for Redis, the thread pool filled, and every request, even those not needing Redis, queued. Or the exceptions were not caught, so each cache call failed the request. Or the fallback to the database overloaded it. Immediate: restore Redis (failover, restart), and meanwhile reduce load. Real fix: short connect and command timeouts (for example 50 to 200 ms), a circuit breaker so threads stop waiting, a CacheErrorHandler that treats errors as misses, a bulkhead so cache calls use a limited pool, a protected fallback to the database with a limit, and a degraded mode (serve stale from L1, hide non-essential features). Prevent: a game day where Redis is blocked in staging, and a clear map of which features are fail-open and which are fail-closed.

Scenario: after moving from a single Redis to a Cluster, the app throws CROSSSLOT errors. Senior

What the interviewer is testing: the main code impact of sharding.

Situation: code that worked on one node does multi-key operations, like MGET a b c, a transaction over several keys, a Lua script touching keys passed incorrectly, or SUNION. In Cluster all keys of one command must hash to the same slot, otherwise the node returns CROSSSLOT Keys in request don't hash to the same slot. Steps: list the offending commands from the error logs. For keys that belong together (one user's data), add a hash tag so they share a slot: {user:7}:profile, {user:7}:cart. For bulk reads of unrelated keys, send individual commands in a pipeline (the cluster-aware client splits them per node), or group keys by slot in your code. For Lua, pass every touched key in KEYS. Be careful with hash tags: too coarse a tag (for example one tag for the whole tenant) creates a hot slot or a big shard. Prevent: test against a Cluster in CI (a small local Cluster in containers), and design key names with the slot in mind from the start.

Scenario: someone ran DEL on a key with five million members and every service timed out for two seconds. Senior

What the interviewer is testing: single-thread blocking and the non-blocking alternatives.

Situation: DEL on a large set, hash or sorted set is O(N) and frees memory on the main thread, so all clients wait. Confirm: SLOWLOG shows the DEL, and the latency spike matches the time. Fix going forward: use UNLINK, which removes the key from the key space at once and frees memory in a background thread. To trim a big collection gradually, use scan commands and delete in chunks (SSCAN plus SREM, ZREMRANGEBYRANK in slices). Enable lazy freeing: lazyfree-lazy-user-del yes makes DEL act like UNLINK, and lazyfree-lazy-expire yes does the same for expiries (Redis 6.0 added the user-del setting). Also stop the key from becoming huge: cap or split it. Prevent: a code review rule that big collections are deleted with UNLINK, with a memory and size alert on keys.

Scenario: a rate limiter built on INCR sometimes leaves counters that never expire, and users stay blocked forever. Senior

What the interviewer is testing: non-atomic multi-step logic and its crash window.

Situation: the code does INCR key, then in a second call EXPIRE key 60 if the result was 1. If the process crashes, or the second call fails or times out, between the two calls, the counter exists without a TTL. It grows to the limit and never resets. Checks: TTL key returns -1 for the blocked users, and SCAN with a TTL check finds more. Immediate: delete or set a TTL on the stuck keys. Fix: make it atomic with a Lua script that does INCR and EXPIRE together, or a MULTI/EXEC block, or use SET key 0 EX 60 NX first (creates it with a TTL if absent) and then INCR (INCR keeps the TTL). A second safeguard: if the TTL is -1 after the increment, set it. Prevent: a general rule that anything with "check then act" in Redis goes into a script, and a periodic audit that counts keys with no TTL in rate-limit prefixes.
