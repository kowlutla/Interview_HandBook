Mental model: the 7 ideas everything hangs on

One line: a cache trades freshness and simplicity for speed. Redis is an in-memory data structure server that runs commands one at a time, so each command is fast and atomic. Every caching bug is either the cache and the database disagreeing, or many requests hitting the database at once.
  1. The cache is a copy, the database is the truth. You must always be able to rebuild a cache entry. If you cannot, it is a database and needs durability.
  2. Hit rate is the whole game. Going from a 99% to a 90% hit rate means ten times more database load.
  3. Every entry needs a way to die. A TTL, eviction, or explicit invalidation. Otherwise memory fills and data goes stale.
  4. Invalidation is the hard part. Updating the database and the cache are two separate writes, and any order can fail halfway.
  5. Failures come in crowds. Many callers miss one key (stampede), many keys expire together (avalanche), or one key takes all the traffic (hot key).
  6. Redis runs one command at a time. That makes single commands and Lua scripts atomic, and makes one slow command stall everyone.
  7. Replication and persistence are asynchronous. Both trade a little data for speed. Know the loss window.

1. Caching patterns, TTL and invalidation

Why do we cache, and what makes data a good candidate? Basic

We cache to make reads faster and to protect the database. A Redis read takes well under a millisecond, while a query with joins can take tens of milliseconds, and most reads never reach the database at all. Good candidates are read-heavy, expensive to compute, and fine to be slightly stale: product catalogs, profiles, config, permission lookups.

Bad candidates are data that changes on every request, data that must be perfectly fresh (a balance during a transfer), and data read once and never again. A cache also costs you something: staleness, one more component that can fail, and extra code. So before adding one I ask three things: what is the read-to-write ratio, how stale can this be, and what hit rate do I expect? For read-heavy data 90 to 99 percent is common. Below about 80 percent I would question the cache. I measure it with the hit rate (keyspace_hits versus keyspace_misses in INFO stats), p99 latency and database load before and after.

The idea from scratch. A cache is a small, fast copy of data that is slow to get from its original place. The database holds the truth on disk and is shared by everyone, so it is the scarce resource. Every read we answer from memory is a read the database never sees. That is why caching often helps scalability more than raw speed: one database can serve far more users if 95 of every 100 reads stop at the cache.

A worked example. Say a product page needs a 20 ms query and the site gets 2,000 page views per second. Without a cache that is 2,000 queries per second, which is 40 seconds of database work every second, so you would need many connections and replicas. With a 95 percent hit rate only 100 queries per second reach the database, and the other 1,900 reads cost about 0.3 ms each. Notice how sensitive this is: at a 90 percent hit rate the database gets 200 queries per second, twice as much. A few points of hit rate can double the load behind it.

What an interviewer probes next. They ask what you lose by adding a cache: you now have two copies of the data that can disagree, a new component that can fail, and a cold-start problem (an empty cache after restart sends all traffic to the database). Always say that you would measure the hit rate first rather than add a cache by habit.

Remember: cache what is read often, costly to build and allowed to be a bit old. Then measure the hit rate.

Explain the cache-aside pattern. Why is it the most common one? Basic

In cache-aside (lazy loading) the application owns the logic. On a read it asks the cache first. On a miss it reads the database, puts the result in the cache with a TTL, and returns it. On a write it updates the database and then deletes the cache entry, so the next read refills it.

It is popular because the cache only holds data that was really requested, the system keeps working if the cache dies (just slower), and it works with any cache and database. The weak spots: the first read of each key is slow, entries can be stale between a database change and the invalidation, and every service must implement the same logic correctly.

String get(String id) {
    String v = redis.get("user:" + id);
    if (v != null) return v;               // hit
    v = db.loadUser(id);                   // miss: go to the source
    if (v != null) redis.setex("user:" + id, 300, v);
    return v;
}
void update(User u) {
    db.save(u);                            // 1. database first
    redis.del("user:" + u.id);             // 2. then invalidate
}
Watch out: forgetting the TTL, so one missed invalidation lives forever. Also caching "not found" results without a short TTL (see penetration).

Why the application owns the logic. In cache-aside the cache is a dumb store. It never talks to the database; only your code moves data between the two. That is why it is called "aside": the cache sits beside the data path instead of in front of it. It is the default choice because it needs nothing special from the cache or the database.

Walk through one key, user:7.

  1. Request 1 does GET user:7 and gets nil (a miss). It reads the row from the database (say 15 ms), stores it with SETEX user:7 300 ... and returns.
  2. Requests 2 to N in the next five minutes get a hit in under a millisecond. The database sees none of them.
  3. A profile update writes the database, then deletes user:7. The next read is a miss and loads the new row.
  4. If nobody updates it, the TTL expires after 300 seconds and the next read refreshes it anyway.

Why "write the database first, then delete". If you delete the cache first, a reader can slip in between the delete and the database write, miss, read the old row and put it back, and then the stale value sits there until the TTL. Deleting after the commit shrinks that window a lot (it does not remove it; see the race question below). Also note that the delete should happen only after the database transaction has committed, otherwise a reader can refill the cache with the pre-commit value.

When to choose something else. If many services would each have to re-implement this code, or you want the loading logic in one place, use a read-through setup (a cache layer or library that loads for you). If you cannot tolerate even a short stale window, cache-aside alone is not enough and you need the safeguards covered in the next few questions.

Remember: read: cache, then database, then fill. Write: database first, then delete the key.

On a write, why delete the cache key instead of updating it? Intermediate

Because a delete cannot leave a wrong value behind, but an update can. If two writers update the database and the cache in different orders, the cache can end up holding the older value while the database has the newer one. A delete is safe to repeat and the next read rebuilds the entry from the truth.

Example: writer 1 sets the database to A, writer 2 sets it to B, but writer 2 writes the cache first and writer 1 second. The cache now says A, the database says B, until the TTL ends. With delete, the worst case is one extra miss. The price of delete is a cache miss right after every write, so for data written very often, deleting wastes the cache; there, a short TTL or a version check on update is better. If the delete itself fails, retry it through a queue and rely on the TTL as the last defence.

Why this is a real design question. After you change the database, the cache copy is wrong and you have two choices: overwrite it with the new value (update) or throw it away (delete). Update looks smarter because it saves the next reader a miss, but it needs the correct final value computed in the right order, and that is hard when two writers run at the same time.

Timeline of the failure with update. Writer 1 and writer 2 are two different requests changing the same product price.

  1. Writer 1 writes the database: price = 10.
  2. Writer 2 writes the database: price = 12 (now the newest).
  3. Writer 2 updates the cache: 12.
  4. Writer 1, delayed by a GC pause, updates the cache: 10.

The database says 12, the cache says 10, and the cache will keep saying 10 until the TTL. With delete, step 3 and step 4 both just remove the key, and the next reader loads 12 from the database. The final state is the same no matter how the two deletes are ordered, which is what "idempotent" buys you.

When update is still the right call. If the value is expensive to rebuild and read immediately after the write (for example a computed score shown right after the user submits), delete causes a visible slow read for the first reader. Then you can write the new value in, but guard it: use a version number or timestamp in the value and only write if yours is newer (an atomic compare in a Lua script), or serialize writers per key.

What if the delete itself fails? The database is already updated, so the cache is stale until the TTL. Retry the delete (a small retry loop, or publish an invalidation event that a consumer retries), and keep the TTL as the last line of defence. This is why every cached key should have a TTL.

Remember: deleting is idempotent and cannot write a wrong value. Updating can.

Compare read-through, write-through and write-behind (write-back). Intermediate

Read-through means the cache itself loads from the database on a miss, so the app only talks to the cache. Write-through means every write goes to the cache and the cache writes to the database synchronously: always consistent, but writes are slower. Write-behind means the cache acknowledges at once and flushes to the database later in batches: very fast writes, but data can be lost if the cache dies before flushing.

Redis does none of these by itself. You build them in your code, with a library, or with a data grid. Cache-aside is basically read-through with the logic in your service. I use write-behind only for data where losing a few seconds is acceptable and the write rate is high: view counts, analytics counters, "last seen" times.

The core question is who does the work and when. There are two jobs: loading data into the cache on reads, and getting writes to the database. The three patterns answer them differently.

Write-behind in more detail. The app increments a view counter 5,000 times per second. Writing each one to the database would melt it. With write-behind the cache absorbs the increments (INCR views:42) and a worker flushes the totals to the database every few seconds, one write per key instead of thousands. The price: if Redis dies (or its AOF window is lost) the unflushed increments vanish, and while the data sits in the cache the database is behind, so any report reading the database is slightly wrong. Combining this with a Redis Stream or list as a durable buffer narrows the loss.

Write-through in more detail. It keeps the cache warm for data just written, so the next read is a hit. But you pay the latency of both stores on every write, and you also cache items that may never be read again. If the cache write succeeds and the database write fails you must roll one back, which is the same dual-write problem as everywhere else in distributed systems.

Say this in an interview. "Redis itself does none of these; they are patterns in the app or a library. I default to cache-aside, use write-behind only for counters where a few seconds of loss is fine, and avoid write-through unless the extra write latency is acceptable."

Remember: write-through = consistent but slower. Write-behind = fast but can lose data. Cache-aside = you decide.

How do you choose a TTL? Basic

The TTL is how long I accept stale data, so I pick it from the business, not from technology. I ask: if this value changes in the database and the cache does not know, how long can users see the old one? A product description may be fine for 5 minutes, a feature flag for 30 seconds, an account balance should not be cached at all.

The TTL is also my safety net: even if the invalidation code has a bug, the wrong value dies when the TTL ends. Longer TTL gives a better hit rate, shorter gives fresher data. Two rules I always follow. Add random jitter so many keys do not expire in the same second. Use a short TTL (30 to 60 seconds) for "not found" results.

SET product:42 "{...}" EX 300      # 5 minutes
TTL product:42                      # seconds left; -1 = no expiry, -2 = no key
Watch out: a plain SET without EX removes the old TTL (unless you use KEEPTTL). Many "keys that never expire" bugs come from this.

Think of TTL as a promise to the user, not a tuning knob. A TTL of 5 minutes means "you might see data that is up to 5 minutes old". So the product owner, not the cache, decides the number. Ask: what is the damage if this is stale? A wrong stock count at checkout is costly; a wrong follower count is not.

Rules of thumb with examples.

  • Reference data that almost never changes (country list): hours or a day, plus explicit delete on change.
  • Product description or profile: 1 to 10 minutes, with a delete on update.
  • Feature flags and permission checks: 30 to 60 seconds, so changes (and revocations) take effect quickly.
  • Negative results ("id not found"): 30 to 60 seconds, so a newly created record shows up fast.
  • Authoritative values like balances: do not cache, or cache for a very short time only for display.

Jitter, explained. If a batch job fills 100,000 keys at 09:00 with a TTL of exactly 600 seconds, they all expire at 09:10:00 and 100,000 requests miss together (an avalanche). Adding a random 0 to 20 percent to each TTL spreads the expiries over two minutes.

int ttl = 600 + ThreadLocalRandom.current().nextInt(120);
redis.setex(key, ttl, value);

Sliding versus absolute TTL. Resetting the TTL on every read (a sliding TTL, as sessions do) keeps hot keys alive but means a key that is read constantly can never be refreshed from the source. For cache data I use an absolute TTL. For sessions I use sliding idle timeout plus an absolute maximum.

Follow-up to expect. "What if the TTL is too short?" The hit rate falls and the database works harder. "Too long?" Users see stale data after a missed invalidation. You tune it from the hit rate and the staleness complaints you actually get.

Remember: TTL = acceptable staleness, plus a safety net. Always add jitter.

How does Redis actually expire keys? Senior

Two ways together. Lazy expiry: when a key is read, Redis checks its expiry time and deletes it if it is past, so you never get an expired value. Active expiry: a background job on the main thread samples keys that have a TTL, several times a second, and deletes the expired ones.

So an expired key that nobody reads can stay in memory for a while until the sampler finds it. The sampler takes about 20 keys per round and repeats immediately if more than about 25 percent were expired, with a time cap so it does not stall requests. The effect: if millions of keys share the same expiry second, Redis spends time deleting them and latency spikes. That is one more reason for TTL jitter. On replicas, keys are not expired independently; the primary sends explicit DEL commands, so replicas stay in step. The expiry is stored as an absolute time, so it survives a restart (time spent down counts).

Why two mechanisms. Imagine Redis had to delete each key exactly at its expiry time. It would need a timer per key, or a sorted structure it scans constantly, which costs CPU and memory for millions of keys. Redis picks a cheaper, approximate design: check on access (so correctness is exact), and clean up in the background (so memory is eventually reclaimed).

How the active cycle behaves. Several times per second (the hz setting, default 10) Redis runs a short cycle on the main thread:

  1. Pick a random sample of about 20 keys from the set of keys that have a TTL.
  2. Delete the ones that have expired.
  3. If more than about a quarter of the sample was expired, assume many more are waiting and repeat, up to a time budget.

So a key that expired but is never read may use memory for a while. That explains the common question "I set TTLs but memory did not drop": the keys are logically gone (a read returns nil) yet physically still there until sampled. It also explains why INFO keyspace may show keys counted that are already expired.

The mass-expiry problem. Suppose five million keys all expire in the same second. The repeat-while-more-than-25-percent loop keeps running and deleting, eating main-thread time, and commands queue behind it. You see a latency spike with no slow command in the slow log, because the work is internal housekeeping. The fixes are TTL jitter and, on big deletes, lazy freeing (lazyfree-lazy-expire yes so the memory is released by a background thread).

Replication and persistence details. Replicas do not decide expiry themselves (otherwise clocks would diverge); the primary sends a DEL (or UNLINK) when a key expires, so replicas match. A replica may still return a logically expired key in a narrow window before the DEL arrives, though newer versions hide it on reads. RDB and AOF store the absolute expiry timestamp, so if Redis is down past the expiry, the key is gone on load.

Remember: lazy on read plus sampling in the background. Same-second expiry means a spike, so use jitter.

What are the main cache invalidation strategies? Intermediate

Four: time-based (just a TTL), explicit delete on write, event-driven (a change event triggers the delete), and versioned keys. In real systems I combine them: explicit delete or events for freshness, and a TTL as the safety net for when those fail.

  • Delete on write: the code that changes data also deletes the key. Simple, but every writer must remember.
  • Event-driven: the database or service publishes a change (change data capture or a message queue) and a consumer deletes the key. Best when many services write the same table.
  • Versioned keys: put a version in the key (product:42:v17) so a change creates new keys and old ones age out by TTL. Good for lists and pages.

The hardest case is collections: a changed product sits inside many cached list pages, and tracking which ones is painful. A short TTL or a version number on the list is usually easier than tracking dependencies. For "read your own writes" (a user edits a profile and must see it now), I bypass the cache for that user for a few seconds, or write the new value straight in. Honest promise to the business: eventual consistency with a bound, never "always fresh".

The hardest problem in caching, restated simply. The cache holds a copy. When the original changes, the copy must change or disappear. Every strategy answers "who notices the change, and how do they tell the cache?"

Versioned keys, with an example. To cache the product list for a category, keep a small counter ver:cat:5. The list key is list:cat:5:v17. Any product change in the category does INCR ver:cat:5, so readers look up v18, miss, and rebuild, while v17 simply expires. You never have to find and delete all the list pages that contained the changed product.

Why events beat in-code deletes for shared tables. If three services and a nightly job all modify the orders table, asking each one to remember cache deletes will fail eventually. Change data capture (reading the database log, for example with Debezium) turns each committed row change into an event, and one consumer deletes the keys. It also keeps changes in commit order, which helps with the race described below.

Say the honest summary. "The cache is eventually consistent. I pick a delete or event for freshness and a TTL for safety, and I tell the business the maximum staleness (for example 60 seconds)."

Remember: delete or event for freshness, TTL as the net. Promise "eventually consistent within N seconds".

Can cache-aside serve stale data forever even with correct code? Show me the race. Senior

Yes, there is a classic race. A reader misses and reads value v1 from the database. Before it writes the cache, a writer updates the database to v2 and deletes the key (nothing to delete yet). Then the slow reader writes v1 into the cache. The cache now holds v1, the database holds v2, until the TTL ends.

It is rare because the window between the reader's read and write is short, but at high volume it happens. Defences: the TTL bounds the damage; a delayed double delete (the writer deletes again after about a second) removes a late stale write; or store a version with the value and write only if it is newer, using a small Lua script so the compare and write are atomic. For strict needs, read from the database, or let a change-data-capture stream be the only invalidator, since it keeps the order of changes.

Why this matters. Many people believe "write DB, then delete cache" is perfectly safe. It is safe in the common case but has one interleaving that is not, and a senior candidate should be able to draw it. The key insight: a reader's miss path is "read database, then write cache" and these two steps are not atomic, so a writer can run entirely between them.

Why it is rare. It needs the reader's database read to start before the write commit, and its cache write to land after the writer's delete. The reader's two steps usually take a millisecond or two, while a database commit often takes longer than a reader's cache write, so the order usually works out. Under heavy load, with a slow replica read or a GC pause in the reader, it does happen, and the result lasts until the TTL, which can be minutes.

Defences compared.

  • TTL: caps the damage. Always on.
  • Delayed double delete: after the write, delete, wait about as long as one slow read (say 500 ms to 1 s), delete again, usually through a queue or scheduler. It catches the late stale write. It is a heuristic, not a proof.
  • Version check: store {version, data}. A refill only writes if its version is newer than the stored one, using a Lua script so compare and write are atomic. This is the correct fix, but needs a version column in the database.
  • Short lease on the refill: the writer sets a tombstone with a short TTL; readers do not refill while a tombstone exists.
  • CDC as the only invalidator: events come in commit order, so deletes always follow the commit.

The interview point. The honest answer is "cache-aside is not strictly consistent; here is the exact race and here is how I bound it", rather than claiming it is perfect.

Remember: a slow reader can refill an old value after the delete. TTL, delayed double delete or version check.

What is a multi-level cache, and when is a local in-process cache (Caffeine) better than Redis? Intermediate

A multi-level cache stacks layers: L1 inside the application process (Caffeine), L2 shared in Redis, then the database. L1 has no network hop, so reads take nanoseconds and cannot fail from the network. L2 is shared by all instances and survives an app restart. I use L1 only for small, hot, rarely changing data with a short TTL, and Redis for everything shared or large.

The risk of L1 is that every instance has its own copy. After a change the other instances still serve the old value, so L1 TTLs must be seconds, or you broadcast invalidations (Redis pub/sub, or Redis client-side caching with tracking, since Redis 6). L1 also lives on the JVM heap, so it needs a size limit and adds GC load, and a restart starts it cold. Caffeine uses Window TinyLFU, which gets a better hit rate than plain LRU. Typical L1 data: reference lists, config, feature flags, public keys.

What each layer buys you. Each layer is closer to the user, faster, and smaller. The browser and CDN can answer without reaching your servers at all (controlled with Cache-Control and ETag). L1 in the JVM answers in nanoseconds with no network. Redis answers in a fraction of a millisecond and is shared. The database is the truth.

AspectL1 (Caffeine)L2 (Redis)
LatencyNanoseconds to microsecondsAbout 0.2 to 1 ms (network hop)

The consistency problem, with numbers. You run 20 instances, each with an L1 TTL of 60 seconds. A product is updated and Redis is invalidated immediately, but each instance still holds its own L1 copy for up to 60 more seconds, so users may see old data depending on which instance serves them (that is the "refresh shows old and new alternately" symptom). Two fixes: keep L1 TTL tiny (1 to 5 seconds), or broadcast invalidations so every instance drops its copy (Redis pub/sub, or Redis client-side caching, where the server tells clients which keys changed).

Why L1 shines for hot keys. A single hot key in Redis lives on one node. A 2-second L1 in each of 50 instances turns thousands of reads per second into at most 25 per second for that key, with a bounded staleness of 2 seconds.

Sizing and eviction. L1 must have a maximum size (entries or weight) or it causes GC pressure and memory errors. Caffeine uses a Window TinyLFU policy: it admits a new entry only if it looks more valuable than the one it would evict, which resists one-time scans that would flush a plain LRU.

Remember: L1 = fastest but per-instance and stale-prone. L2 Redis = shared. Keep L1 small and short-lived.

2. Failure modes: stampede, penetration, avalanche, hot and big keys

What is a cache stampede (thundering herd) and how do you prevent it? Intermediate

A stampede is when a popular key expires and many requests miss at the same moment, so they all run the same expensive query against the database. I prevent it by letting only one request rebuild the value: a short per-key lock, or serving the old value while one caller refreshes it in the background.

Why it hurts: the database slows down, so each rebuild takes longer, so more requests pile up, and it can collapse. Defences, simple to strong:

  • Per-key lock (single flight): the first miss takes SET lock:key token NX PX 5000 and rebuilds. Others wait briefly and re-read the cache. The lock TTL frees it if the holder crashes.
  • Serve stale while revalidating: store a soft expiry inside the value. After it passes, one caller refreshes while everyone else still gets the old value.
  • Probabilistic early refresh: each reader has a small chance to refresh before the real expiry, rising as expiry nears.
  • Jitter and pre-warming: spread TTLs and refresh known hot keys on a schedule.

In Spring, @Cacheable(sync = true) gives single flight inside one JVM only, not across instances.

The mechanism, with numbers. A hot key is read 2,000 times per second and rebuilding it takes 300 ms. When it expires, in those 300 ms about 600 requests arrive, all see a miss, and all run the same expensive query. The database, now slower under 600 parallel copies, takes 600 ms to answer, which lets 1,200 more requests miss. This feedback loop is why a stampede can take down a database that is perfectly fine at normal load.

Single flight with a lock, step by step.

  1. Reader misses and tries SET lock:product:42 token NX PX 5000.
  2. The winner loads from the database, writes the cache, and releases the lock (compare-token Lua).
  3. The losers sleep a short random time (for example 50 ms), then re-read the cache. After a couple of tries they either get the fresh value or, if the wait is too long, fall back to a stale copy or compute it themselves.

The lock TTL must be longer than the rebuild time but short enough that a crashed winner does not block everyone for long.

Stale-while-revalidate, the smoother option. Store the value with a logical expiry inside it, like {data, softExpiry}, and give the Redis key a much longer physical TTL. When a reader sees the soft expiry has passed, it takes the lock, refreshes in the background, and everybody (including itself) keeps returning the old value meanwhile. Users never wait, and the database sees one query. The price: data can be a little older than the soft expiry.

Probabilistic early refresh (XFetch). Each read decides randomly whether to refresh early, with higher probability as the expiry nears and as the rebuild cost grows. No locks are needed because refreshes are spread out in time.

Which one. Few hot keys with costly rebuilds: stale-while-revalidate or lock. Many keys with moderate cost: jitter plus probabilistic refresh. Always fine to pre-warm a known hot list on a schedule.

Remember: one hot key, many rebuilders. Let one rebuild (lock or stale-while-revalidate), the rest wait or read stale.

What is cache penetration, and how do you stop it? Intermediate

Penetration is requests for keys that do not exist in the database either, so the cache never holds an answer and every request goes through to the database. It can be a bug or an attack with random ids. I stop it with input validation, caching the "not found" result for a short time, and a Bloom filter for large id spaces.

  • Negative caching: store a marker like NULL with a 30 to 60 second TTL. If a record is created right after, delete the marker on create.
  • Validate early: reject ids with the wrong format or range before any lookup.
  • Bloom filter: a small structure that says "definitely not present" or "maybe present". Load it with all valid ids and answer "not found" without touching cache or database. It has false positives but never false negatives, so no real item is rejected. It must be updated when items are created. Redis offers one through the RedisBloom module (built into Redis 8).
  • Rate limit abusive clients.

Why normal caching cannot help here. Cache-aside caches what it finds. If the database has no row for id=999999999, there is nothing to cache, so each request misses and hits the database. One client sending random ids at 5,000 requests per second can make the database do 5,000 pointless lookups per second, while your cache hit rate looks fine for real traffic.

Defence layers, cheapest first.

  1. Validate input at the edge: ids must match a format and range (a positive number below your max id). This removes junk for free.
  2. Negative caching: on a database miss, store a sentinel like __NULL__ for 30 to 60 seconds. Repeated requests for the same missing id are now served from Redis. Problem: attackers use different random ids each time, so this alone does not stop an attack. Also delete the sentinel when the record is created.
  3. Bloom filter: a bit array plus several hash functions. Add all valid ids at load time. Asking "is id X present?" gives "definitely no" or "probably yes". A "definitely no" is answered immediately, with no cache or database call, so random ids never reach the database. With about 10 bits per element you get roughly a 1 percent false-positive rate; a false positive just means one wasted lookup. Standard Bloom filters cannot delete items, so rebuild periodically if ids are removed (or use a cuckoo filter).
  4. Rate limit per IP or key, and alert on a high miss ratio per client.

Penetration versus the neighbours. Penetration is requests for data that does not exist. Stampede is many requests for data that exists but just expired. Avalanche is many keys expiring or the cache dying. They have different fixes, and interviewers like to see you separate them.

Remember: missing keys are never cached by normal logic. Validate, cache the null briefly, Bloom filter, rate limit.

What is a cache avalanche, and how is it different from a stampede? Intermediate

A stampede is one hot key with many readers. An avalanche is many different keys failing together, so the database sees a wave of many different queries. It happens when lots of keys were loaded with the same TTL and expire together, or when the whole cache goes down or is flushed. The fix is TTL jitter, spreading warm-ups, a highly available Redis, and protection on the database side.

Concretely: add random jitter (base 600 s plus a random 0 to 120 s), stagger warm-up jobs, run Redis with replicas and automatic failover, keep a small local L1 cache, and protect the database with a circuit breaker, a rate limiter or a queue so it degrades instead of collapsing. Have a reduced response ready (stale data or defaults) for when the database is overloaded.

int ttl = 600 + ThreadLocalRandom.current().nextInt(120);   // jitter
redis.setex(key, ttl, value);

Two ways an avalanche starts. First, expiry alignment: a deploy, a warm-up job or a cache flush loads a large number of keys with the same TTL, and later they all expire together. Second, cache loss: Redis restarts without persistence, a failover loses the data, or someone runs FLUSHALL, and the hit rate falls from 95 percent to 0 instantly. In both cases the database suddenly gets a large share of the full read traffic, which it was never sized for.

How it differs from a stampede, side by side.

StampedeAvalanche

Layers of defence.

  • Prevent alignment: jitter every TTL; load in batches with pauses; never give a whole data set one fixed expiry.
  • Prevent cache loss: replicas with automatic failover; for caches that are expensive to warm, enable RDB so a restart is not fully cold.
  • Warm before switching traffic: after a planned flush or a new cluster, pre-load the hottest keys before sending users.
  • Protect the database: concurrency limit or queue in front of it, circuit breaker, request coalescing, and a degraded response (serve stale or defaults) when it is overloaded.

The principle: assume the cache will sometimes be empty and design the system so an empty cache means slow, not down.

Remember: stampede = one key, many callers. Avalanche = many keys at once. Jitter the TTLs.

What is a hot key, and what do you do about it? Senior

A hot key is one key that gets a huge share of traffic, such as a flash-sale product or a global config. In a Redis Cluster a key lives on exactly one node, so adding nodes does not help: that node saturates while others sit idle. The usual fix is a short-lived local cache in each app instance, plus copies of the key under several names.

  • Local L1 cache with a 1 to 5 second TTL removes most of the traffic.
  • Key copies: store hot:cfg:0 to hot:cfg:7 and read one at random. They hash to different slots and nodes. Writers update all copies.
  • Replica reads if slight staleness is fine.
  • Shrink the value, since a large value also saturates the network.
  • Counters: split into N sub-counters and sum on read.

To find hot keys: redis-cli --hotkeys (needs an LFU eviction policy), a brief MONITOR in a quiet window (it is heavy), or client-side metrics. More shards do not help because hashing sends the same key to the same shard every time.

Why scaling out does not fix it. In Cluster each key maps to exactly one slot and so to one master. If one key receives 200,000 reads per second and one node can handle about 100,000 operations per second of that kind, that node saturates while the others are idle. Adding shards moves other keys around but never splits this one.

How key copies work, with a snippet. Instead of one key cfg:home, store eight copies cfg:home:0 to cfg:home:7. Their different names hash to different slots, so (with luck) different nodes. Readers pick a random suffix. Writers update or delete all eight.

int n = ThreadLocalRandom.current().nextInt(8);
String v = redis.get("cfg:home:" + n);   // reads spread over up to 8 nodes

For writes: update all copies, accept that for a few milliseconds they differ. For a hot counter use the same idea in reverse: INCR likes:42:{0..7} at random and sum the eight on read (or sum periodically).

The local cache option is usually the best first step. It costs no extra Redis memory and removes the load at the source. A 1 to 5 second TTL in each app instance means Redis sees at most one read per instance per few seconds for that key. The cost is bounded staleness.

Replica reads spread load over a primary and its replicas for that shard, which gives maybe two to three times capacity, not more, and reads may lag.

Detection matters. Hot keys show up as one node with high CPU or network out while the others are quiet. redis-cli --hotkeys works only when an LFU policy is set because it reads the access-frequency counter. In production prefer application-side metrics (count by key prefix) over MONITOR, which can itself slow Redis down.

Remember: one key = one node. Spread the reads with L1, key copies or replicas.

What is a big key, and why are KEYS * and big deletes dangerous? Intermediate

A big key holds a huge value, like a multi-MB string or a collection with millions of members. Redis runs one command at a time, so any command that touches the whole thing (DEL, HGETALL, SMEMBERS, KEYS *) blocks every other client until it finishes. I use UNLINK for deletes and the SCAN family for walking, and I split big keys into buckets.

KEYS pattern is O(N) over all keys; with ten million keys it can freeze the server for seconds. SCAN walks in small steps with a cursor: call it with 0, get a batch plus a new cursor, repeat until the cursor is 0. Each call is quick so others are served. Catch: SCAN may return a key twice, and keys added during the walk may be missed, so the code must be idempotent. HSCAN, SSCAN and ZSCAN do the same inside collections. UNLINK removes the key at once and frees memory in a background thread. Find big keys with redis-cli --bigkeys or MEMORY USAGE key. Also use FLUSHALL ASYNC rather than plain FLUSHALL.

SCAN 0 MATCH session:* COUNT 500   # returns next cursor + batch; stop at cursor 0
UNLINK session:big                 # non-blocking delete

The core idea: one thread, so size matters. Redis executes commands one at a time. A command that takes 2 ms is invisible. A command that takes 2 seconds means every other client waits 2 seconds. Cost depends on how much data the command touches, so a huge key turns an ordinary command into a stall.

How SCAN works, in plain words. You call SCAN 0. Redis looks at a small slice of the key table and returns a cursor (say 4096) plus a handful of keys. You call SCAN 4096 and continue until the cursor returns 0. Between calls other clients run, so nothing blocks. The guarantee is that keys present for the whole scan are returned at least once. Keys can repeat, and keys added or removed during the scan may or may not appear. COUNT is only a hint for how much work per call.

Preventing big keys. Cap collection size by design: bucket a huge hash into 1,000 smaller hashes using id mod 1000; trim lists and streams; put a rolling window on sorted sets. A rule of thumb many teams use is to keep values under about 10 KB and collections under about 10,000 elements, although the right limit depends on your latency target.

Cluster angle. A big key also makes slot distribution uneven, since the whole key sits on one node, and resharding must move it as a single unit.

Remember: O(N) command on a big key stalls everyone. SCAN, not KEYS. UNLINK, not DEL.

3. Redis internals

What is Redis, and how is it different from a plain key-value cache? Basic

Redis is an in-memory data structure server. The data lives in RAM, so operations take microseconds, and unlike a plain cache of opaque blobs it understands types (strings, hashes, lists, sets, sorted sets, streams) with atomic commands on each. It can also persist to disk, replicate, fail over, and shard.

So it is used as a cache, session store, rate limiter, leaderboard, lock service, simple queue, and sometimes as a primary store for small fast data. Disk is only for persistence and restart; reads never touch it. The caveat is memory: everything must fit in RAM, which is costly at large sizes, and a key has overhead beyond its payload (tens of bytes), so many tiny keys use much more than the raw data. maxmemory caps usage and the eviction policy decides what happens when it is reached.

Think of it as a server for data structures. A plain cache like a hash map in your program stores key to blob and gives you back the blob. Redis is a separate server process, reached over the network, that stores key to typed value. Because it understands the type, it can do work on the server: add to a counter, push to a list, add a member to a sorted set and report its rank. Each of those is one atomic command, so many clients can share the structure safely without locking in the app.

Why memory, and what that implies. RAM access takes about 100 nanoseconds, a network hop inside a data center about a few hundred microseconds, and an SSD read roughly a hundred microseconds or more. Keeping data in RAM means the network, not storage, becomes the main cost, which is why a Redis command typically completes in well under a millisecond. The matching limits: capacity equals RAM (a 64 GB box holds roughly 64 GB minus overhead), cost per GB is higher than disk, and a restart empties memory unless persistence is configured.

What you get on top of the data structures.

  • Expiry and eviction: per-key TTL and memory-limit policies, which is what makes it a cache.
  • Persistence: RDB snapshots and the AOF log.
  • Replication, Sentinel and Cluster: copies for reads and failover, and sharding for scale.
  • Extras: pub/sub, streams, Lua scripting, geo, bitmaps, and modules (search, JSON, Bloom filters; several are bundled in Redis 8).

Common roles with a one-line reason each. Cache (fast, TTL), session store (shared state across stateless servers), rate limiter (atomic counters), leaderboard (sorted set), distributed lock (SET NX PX), lightweight queue (list or stream).

What interviewers want to hear. That you know it is not a database replacement by default: memory bound, async replication, weak durability by default settings. Redis licensing changed in 2024 (a source-available license, then an OSS option added again with Redis 8), and forks like Valkey exist, but the commands and client libraries you use are largely the same.

Remember: in-memory, rich types, atomic commands. Not just a cache, but bounded by RAM.

Redis is single-threaded. Why is it still so fast? Intermediate

Command execution runs on one thread, and that is fast for four reasons. Data is in memory, so there is no disk wait. There are no locks or thread context switches on data. An event loop (epoll) lets one thread serve thousands of sockets. And the data structures are efficient, with most commands O(1) or O(log N). The bottleneck is usually the network, not the CPU.

It is not strictly single-threaded: background threads free memory lazily (UNLINK), close files and flush the AOF, and since Redis 6.0 optional I/O threads read and write sockets in parallel, while commands still execute on the main thread. Persistence uses a forked child process. The downside: one slow command (KEYS, a big DEL, a long Lua script) delays everyone, and one process uses one core for commands. To use more cores you run several instances, usually as a Cluster.

The trade Redis made. Multi-threaded servers must protect shared data with locks. Locks cost CPU (waiting, cache-line bouncing, context switches) and bring bugs like deadlocks. Redis avoids all of that by having exactly one thread touch the data. Every command is naturally atomic and ordered, and the code stays simple.

Is one core enough? A single core running simple in-memory operations can execute on the order of a hundred thousand commands per second (more with pipelining), and the practical limit is usually the network card or the client round trips, not the CPU. Per command the CPU work is tiny: parse, look up in a hash table, do an O(1) or O(log N) operation, write the reply.

How one thread serves thousands of clients. It uses an event loop on top of epoll (or kqueue). The OS tells it which sockets have data, it reads each request, runs it, queues the reply, and moves on. It never blocks waiting for one slow client, because sockets are non-blocking.

Where multiple threads and processes do exist.

  • I/O threads (Redis 6.0 and later, off by default): read and parse requests and write replies in parallel; command execution is still single-threaded. Helps when network I/O is the bottleneck.
  • Background threads: lazy freeing (UNLINK), closing files, AOF fsync.
  • Forked child processes: RDB snapshots and AOF rewrites, so the main thread keeps serving.

The consequences to remember. A slow command blocks everyone, so avoid O(N) commands on big data and long Lua scripts. To use many cores, run many Redis processes (a Cluster, or several instances per host, one per core). Some alternatives (such as Dragonfly or KeyDB) are multi-threaded designs, and Memcached is multi-threaded, but they pay in complexity.

Remember: in memory, no locks, event loop, efficient structures. One slow command blocks all.

What does "Redis commands are atomic" really mean, and what does it not cover? Intermediate

One command runs to completion with nobody seeing a half-done state, so two clients doing INCR counter always give +2. But a sequence of commands is not atomic: if I GET, change the value in Java, then SET, another client can slip in between and one update is lost. For sequences I use a single command like INCRBY, a Lua script, or WATCH with MULTI/EXEC.

Also, atomic does not mean durable: a command can succeed in memory and still be lost if the server crashes before persistence or replication. And in a Cluster, atomicity across several keys only works if they live in the same slot.

# wrong: read-modify-write across the network
v = GET stock:42;  SET stock:42 (v-1)
# right: one atomic command
DECR stock:42
Watch out: "Redis is atomic so my code is safe" is the classic wrong claim. Only single commands and scripts are atomic.

What "atomic" means precisely. A command either has not started or has fully finished from every other client's point of view. Nobody can see a counter half incremented or a list half pushed. Redis gets this for free from the single command-execution thread.

The lost-update bug, step by step. Two servers sell the last tickets. Stock is 10.

  1. Server A: GET stock returns 10.
  2. Server B: GET stock returns 10.
  3. A computes 9 and runs SET stock 9.
  4. B computes 9 and runs SET stock 9.

Two tickets sold, stock dropped by one. Each command was atomic, but the sequence was not. With DECR stock the read, change and write happen in one command, so the result is 8.

Which tool for which case.

Simple increment, append, pushThe built-in command (INCRBY, HINCRBY, LPUSH)

Read, decide, then write several keysLua script (or a Function in Redis 7)

What atomic does not give you. It does not give durability (a crash can lose an acknowledged write), it does not give rollback, and across a Cluster it works only inside one slot, so multi-key commands need hash tags. It also does not make your Java code thread-safe; it only protects what happens inside Redis. Mention that a retry after a timeout can run an increment twice, so counters that must be exact need an idempotency key.

Remember: one command is atomic, a GET-then-SET is not. Use INCR, Lua or WATCH.

What is pipelining, and how is it different from a transaction? Intermediate

Pipelining sends many commands without waiting for each reply, then reads all replies together. It saves network round trips, which usually cost far more than running the command. A transaction (MULTI/EXEC) is about isolation: queued commands run together with nobody in between. Pipelining is not atomic.

A round trip is often 0.2 to 1 ms inside a data center, while Redis runs a simple command in microseconds, so loading 10,000 keys one by one is mostly waiting. A pipeline can give ten times more throughput. Redis buffers the replies in memory, so send chunks of a few hundred to a few thousand commands. In a pipeline, other clients' commands can run between yours, and one failing command does not stop the rest. They combine: a transaction can be sent inside a pipeline. In a Cluster, a pipeline must be split per node. For many keys, MGET and MSET are single commands, but in a Cluster the keys must share a slot.

Pipeline p = jedis.pipelined();
for (String k : keys) p.get(k);
List<Object> replies = p.syncAndReturnAll();

The problem pipelining solves. Each normal command is a round trip: send, wait, receive. If the round trip is 0.5 ms and Redis needs 5 microseconds to run the command, 99 percent of the time is spent waiting on the network. Sending 10,000 commands one by one then takes 5 seconds, almost all of it idle.

How it works. The client writes many commands to the socket back to back without reading. Redis processes them in order and queues replies; the client then reads all replies. The same 10,000 commands may take well under 100 ms. It is the single cheapest throughput win for bulk loads, cache warming and batch reads.

Practical advice.

  • Batch in chunks (for example 500 to 5,000 commands). An unbounded pipeline makes Redis buffer huge replies in memory and can hit the client output buffer limit.
  • In Cluster, group commands by node (clients such as Lettuce do this for you, but cross-slot batching is not transparent in every client).
  • Lettuce pipelines automatically across threads on a shared connection, while Jedis needs an explicit pipeline object. Spring's executePipelined wraps it.
  • Use MGET and MSET when you only need multiple gets or sets of strings, since they are simpler than a pipeline.

An interviewer may ask "does pipelining make the commands atomic?" The answer is no; it only reduces latency. If you need isolation, wrap them in MULTI/EXEC or a script.

Remember: pipeline = fewer round trips, not atomic. MULTI/EXEC = isolated, no rollback.

4. Data structures and their use cases

Name the main Redis data types and when you would use each. Basic

String for cached values, counters and locks. Hash for objects with fields. List for simple queues and recent-N feeds. Set for unique members and set math. Sorted set for leaderboards and time windows. Stream for a durable event log. Bitmap and HyperLogLog for compact flags and approximate unique counts. The rule: pick the type whose commands already do what you need atomically.

  • String (up to 512 MB): SET/GET, INCR, SET NX for locks.
  • Hash: read or update one field without loading the rest (HGET, HINCRBY).
  • List: push and pop at both ends in O(1); capped logs and simple queues.
  • Set: uniqueness, tags, "common friends" with SINTER.
  • Sorted set: members with a score, kept in order; ranks, top-N, sliding-window rate limits.
  • Bitmap: one bit per user id, so 10 million users take about 1.2 MB (daily active flags). HyperLogLog: approximate distinct count in at most about 12 KB with about 0.81 percent error; you can count and merge but not list members.
  • Geo: store coordinates, query by radius.

How to choose, as a short decision list.

  • Need one opaque value, a counter, or a lock? String.
  • Need a small record whose fields you read or change separately? Hash.
  • Need order of insertion and cheap push and pop at the ends? List.
  • Need uniqueness and set operations (union, intersection)? Set.
  • Need ordering by a number and rank queries? Sorted set.
  • Need a durable log that several workers can share? Stream.
  • Need yes/no flags per id in huge numbers? Bitmap. Need an approximate unique count? HyperLogLog.

Examples with real commands.

SET page:home:hits 0 ; INCR page:home:hits           # counter
SADD tags:post:9 redis cache ; SINTER tags:post:9 tags:post:12   # shared tags
SETBIT active:2026-11-17 1234567 1 ; BITCOUNT active:2026-11-17   # daily active users
PFADD uniq:2026-11-17 user7 user9 ; PFCOUNT uniq:2026-11-17        # approx unique visitors
GEOADD shops 77.59 12.97 shopA ; GEOSEARCH shops FROMLONLAT 77.6 12.9 BYRADIUS 5 km

Memory intuition. Redis stores small hashes, sets, lists and sorted sets in a compact encoding (listpack, intset) and switches to a hash table or skip list when they grow past configured limits. So many small collections are very memory efficient, while large ones cost much more per element. OBJECT ENCODING key shows which one is in use.

Common mistakes. Using a list as a set (O(N) membership checks), storing a huge JSON in a string and rewriting it per field change, using a sorted set when plain insertion order would do, and using Pub/Sub where durability is needed. Also, HyperLogLog counts distinct items but cannot list or remove them, and bitmaps need dense numeric ids to be efficient (sparse ids waste memory).

Remember: string cache/counter, hash object, list queue, set unique, zset ranking, stream log, HLL approximate count.

Store a user object: JSON string or hash? Intermediate

If I always read and write the whole object, I use a JSON string: one GET, one deserialize, and nesting is fine. If I need to read or update single fields, or keep a counter per object, I use a hash.

With a string, changing one field means read, change, write the whole value, which is not atomic. A hash keeps fields separate: HSET user:7 name Asha plan pro, then HGET for one field, or HINCRBY user:7 logins 1 atomically. A hash cannot hold nested objects directly, and fields cannot have their own expiry in older versions (per-field expiry arrived in Redis 7.4). Small hashes use a compact encoding (listpack), so many small hashes cost less memory than many separate string keys.

How does a sorted set work, and what are its complexities? Intermediate

A sorted set holds unique members, each with a numeric score, always ordered by score. Internally it is a skip list plus a hash table, so add, remove and rank lookups are O(log N), reading a range is O(log N + M) for M results, and getting one member's score is O(1). That is why it fits leaderboards with millions of players.

A skip list is layered linked lists: upper layers skip ahead, so search is logarithmic without the rebalancing of a tree. Small sorted sets use a compact listpack instead. Key commands: ZADD (add or update), ZINCRBY, ZRANGE (with REV, BYSCORE in 6.2 and later), ZREVRANK, ZREM, ZREMRANGEBYSCORE, ZCARD. Ties on score are ordered alphabetically by member.

What it is, from scratch. A normal set holds unique members with no order. A sorted set (zset) gives each member a floating-point score and keeps the members ordered by it. Adding an existing member just updates its score. You can ask for "the top 10", "the rank of this member", or "everyone with a score between 100 and 200" and get the answer without sorting anything yourself.

Why two structures inside. The skip list keeps members in score order and supports fast range and rank queries. The hash table maps member to score for O(1) lookups. Using both gives O(1) ZSCORE and O(log N) ordered operations. Memory cost is higher than a plain set, so Redis uses a compact listpack for small zsets (default up to 128 elements) and converts when they grow.

A skip list in one picture. Level 0 is a sorted linked list of all nodes. Level 1 links about every second node, level 2 about every fourth, and so on, chosen randomly when a node is inserted. To find a score you start at the top level, move right while the next node is smaller, and drop down a level when you would overshoot. This halves the search space each level, giving O(log N) without the rebalancing logic of a tree.

Uses beyond leaderboards. Sliding-window rate limiting (score = timestamp), delayed job queues (score = run-at time; workers take the lowest score that is due), time-ordered feeds, and priority queues. Caveat: scores are doubles, so integers above 2^53 lose precision; and one huge zset lives on one node.

Remember: skip list plus hash: O(log N) for add, remove and rank. Great for top-N.

5. Persistence, replication and Cluster

Explain RDB and AOF persistence and compare them. Intermediate

RDB is a point-in-time snapshot of the whole data set in one compact file. It restarts fast but you lose everything since the last snapshot. AOF logs every write command and replays it on restart; with the default everysec fsync you lose at most about one second. For a pure cache I may use neither, or RDB only so a restart is not cold. For data I care about I use AOF with everysec plus replicas.

RDB: triggered by rules like "after 3600 s if 1 key changed" or BGSAVE. Redis forks a child that writes the file while the parent keeps serving. AOF: appendfsync always is safest but slow, everysec is the default, no leaves it to the OS. The log grows, so Redis rewrites it into the shortest set of commands that rebuilds the data (Redis 7 uses a base file plus incremental files). If both are on, Redis loads the AOF at restart because it is more complete.

The fork has a cost: the child shares memory with the parent by copy-on-write, so under heavy writes memory can approach double during a save, and forking a very large instance can pause the main thread briefly. Keep memory headroom and take snapshots on a replica if you can.

The question persistence answers. Redis keeps data in RAM. If the process or machine dies, RAM is gone. Persistence writes enough to disk to rebuild memory on restart. The two options trade restart speed, file size and how much recent data you can lose.

How a snapshot is made, step by step. The parent calls fork(). The child gets a frozen view of memory (the OS shares pages and copies a page only when the parent modifies it, called copy-on-write) and writes it to a temp file, then renames it over the old file. If the instance is 20 GB and the write rate is high, many pages get copied, so memory use can grow noticeably (in the worst case close to double) and the fork call itself can pause the main thread for tens or hundreds of milliseconds on big heaps. That is the "latency spike every few minutes" cause in the scenarios later.

The three fsync settings. always: fsync after every write, slow, safest. everysec: fsync once per second in a background thread, the usual choice. no: leave flushing to the OS, fastest, loses up to about 30 seconds in the worst case on Linux. The AOF is rewritten in the background when it grows past a size threshold, compressing history into the minimum commands.

How to choose.

  • Pure cache that can be rebuilt: no persistence, or RDB only so a restart is warm.
  • Session or derived data that you would rather not lose: AOF everysec, possibly with RDB too, plus replicas.
  • Remember that persistence is not backup: copy RDB files off the host regularly, and test a restore.

Remember: RDB = fast restart, lose minutes. AOF everysec = lose about a second. Cache-only: maybe neither.

How does Redis replication work, and what are its limits? Intermediate

A replica connects to the primary, receives a full snapshot once, and then gets a continuous stream of every write command. It is asynchronous: the primary answers the client first and replicates after. So a replica can lag, and a write the client saw acknowledged can be lost if the primary dies before it reaches a replica. Replicas give read scaling and failover, not extra durability.

First connection: full sync (the primary forks, sends an RDB file, and buffers writes made meanwhile). After a short disconnect: partial resync (PSYNC) from the replication backlog, a circular buffer (1 MB by default); if the gap is bigger, a costly full sync happens again. Reading from replicas multiplies read capacity but returns possibly stale data, so use the primary for "write then read the same key". WAIT numreplicas timeout blocks until replicas acknowledge, which narrows the loss window but is not a guarantee. Replicas are read-only by default.

What replication is for. Three things: a hot standby for failover, extra read capacity, and a source for taking snapshots without loading the primary. It is not a way to make writes safer, because the acknowledgement does not wait for replicas.

The life of a replica, step by step.

  1. The replica sends PSYNC to the primary with its replication id and offset.
  2. First time (or too far behind): the primary starts a background save, sends the RDB file, and meanwhile buffers new writes. The replica loads the file, then applies the buffered writes. This is a full resync, which is expensive for large data sets (fork, disk or network, memory).
  3. Afterwards the primary streams every write command to the replica. The replica tracks an offset.
  4. If the link drops briefly, the replica reconnects and asks to continue from its offset. If that offset is still in the primary's backlog buffer, only the missing part is sent (partial resync); otherwise another full resync happens.

Sizing the backlog. The default backlog is small (1 MB). If the primary does 5 MB of writes per second and the link drops for 10 seconds, the backlog overflows and a full resync follows, possibly repeating if the primary is under pressure. Increase repl-backlog-size for busy primaries.

Read from replicas, with care. Replication lag is normally milliseconds but can grow to seconds under load or during a big resync. If a user writes and immediately reads from a replica, they may not see their own write. Route read-your-own-writes to the primary. Also note that replicas can serve reads of keys that have logically expired in a narrow window, and that heavy slow commands on a replica do not affect the primary but can delay replication apply.

Durability angle. Replicas improve availability, not durability: because the ack does not wait, WAIT or min-replicas-to-write are the only ways to shrink the loss window. If the primary restarts empty without persistence and its replicas reconnect, they will copy the empty data set and also lose everything; so a primary with persistence off should not auto-restart in a way that triggers this.

Remember: async replication: fast, but a failover can lose the last writes. Replica reads can be stale.

What does Sentinel do, and when would you use it instead of Cluster? Intermediate

Sentinel is a set of separate processes (at least three) that watch a primary and its replicas, detect failure by majority vote, promote a replica, and tell clients the new primary address. It gives high availability but no sharding. I use it when all data fits on one machine; I move to Cluster only when one node cannot hold the memory or handle the write rate.

Failover flow: a Sentinel that cannot reach the primary marks it "subjectively down"; when a quorum agrees it is "objectively down"; the Sentinels elect a leader, which picks the best replica (priority, then replication offset) and promotes it. Three Sentinels because a majority is needed: with two, losing one leaves no majority. Because replication is async, a failover can lose the latest writes. A network partition can also leave an old primary accepting writes that are discarded later (split brain); min-replicas-to-write limits this.

The problem it solves. With only replication, when the primary dies someone (or something) must notice, choose a replica, promote it, point the other replicas at it, and tell every client. Doing that by hand takes minutes of downtime. Sentinel automates all of it and also serves as the source of "who is the current primary" for clients.

Why three or more Sentinels, and what quorum means. A single Sentinel could be the one that lost its network and wrongly declare the primary dead. Requiring several to agree avoids false failovers. The quorum setting (for example 2 of 3) is how many must agree the primary is down; but to actually run the failover, one Sentinel must be elected leader by a majority of all Sentinels. So with two Sentinels, if one is down no majority exists and no failover can happen. Place the Sentinels on different hosts or zones.

Client side. A Sentinel-aware client (Lettuce, Jedis with Sentinel pool, Spring RedisSentinelConfiguration) is given the Sentinel addresses and a master name. It asks "who is the master of mymaster?" and reconnects when told the answer changed. A plain client configured with a fixed IP will keep talking to the dead primary.

Failure behaviours worth mentioning. The failover takes seconds (detection time down-after-milliseconds, election, promotion), during which writes fail. Acknowledged writes not yet replicated are lost. A partitioned old primary may keep accepting writes for a while; after it rejoins it becomes a replica and discards them. Setting min-replicas-to-write makes an isolated primary stop accepting writes, which limits that loss.

How does Redis Cluster shard data? Explain hash slots. Intermediate

The key space is split into 16384 hash slots. The slot of a key is CRC16(key) mod 16384, and each master node owns a range of slots. A cluster-aware client keeps the slot map and sends each command straight to the right node. Adding a node means moving some slots, not rehashing everything. The big rule for developers is that a multi-key command only works if all its keys are in the same slot.

If the client's map is old, the node replies MOVED slot host:port (update the map) or ASK (temporary, during migration). You force related keys into one slot with hash tags: only the text inside {} is hashed, so {user:7}:profile and {user:7}:cart land together. Otherwise MGET, transactions and Lua scripts on several keys fail with CROSSSLOT. Each master normally has a replica; if a master fails, its replica is promoted after a majority of masters agree. Replication is still async, so Cluster can lose acknowledged writes too. Cluster supports only database 0. Choosing shard counts and resharding are operator topics.

The problem and the idea. One node cannot hold more memory than its host has and handles only one core's worth of commands. To scale, split the keys over several masters. A naive hash(key) mod N breaks when N changes (almost every key moves). Redis Cluster instead uses a fixed number of buckets, 16384 hash slots, and assigns slots to nodes. Adding a node means handing over some slots (and the keys in them) rather than rehashing everything.

A request, step by step.

  1. The client computes CRC16("user:42") mod 16384, say 9842.
  2. Its cached slot map says slot 9842 belongs to Master B, so it sends the command there.
  3. If the slot moved, B replies MOVED 9842 hostC:6379. The client updates its map and retries on C. During a migration a node may answer ASK for keys already moved.

Hash tags in practice. Hashing only the part inside braces lets related keys share a slot.

MGET {order:77}:header {order:77}:items     # same slot, works
MGET order:77:header order:78:header         # may fail with CROSSSLOT
EVAL "..." 2 {u:7}:cart {u:7}:stock ...      # script keys must share a slot

Tag with care: putting all of a tenant's keys on one tag makes that tenant one big hot node and prevents spreading.

Failure handling. Nodes gossip over a second port (the cluster bus). If a majority of masters decide a master is unreachable, one of its replicas is promoted. If a slot range has no master and cluster-require-full-coverage is yes (default), the whole cluster stops accepting writes; many teams set it to no for caches. Minimum recommended is three masters, each with at least one replica.

What changes for the developer. Only database 0; multi-key operations, transactions and scripts need same-slot keys; use a cluster-aware client (Lettuce or Jedis cluster mode) with topology refresh enabled; pub/sub messages are broadcast across nodes (shard channels exist in 7); and the memory of one node limits any single key.

Remember: 16384 slots, CRC16 mod 16384, one master per slot. Multi-key commands need the same slot: use {hash tags}.

6. Eviction and memory

What happens when Redis reaches maxmemory? Explain the eviction policies. Intermediate

It depends on maxmemory-policy. The default noeviction makes writes fail with an OOM error while reads still work, which is right for a primary store and wrong for a cache. For a cache I set allkeys-lru, or allkeys-lfu when a few keys are consistently popular. If the instance mixes must-keep data and cache data, I use a volatile policy and give only cache keys a TTL, or better, use separate instances.

  • allkeys-lru / allkeys-lfu: evict the least recently, or least frequently, used key from all keys.
  • volatile-lru / volatile-lfu / volatile-ttl: consider only keys that have a TTL (volatile-ttl removes those expiring soonest). If no key has a TTL, writes fail like noeviction, which surprises people.
  • random variants pick at random.

Redis LRU is approximate: it samples a few random keys (maxmemory-samples, default 5) and evicts the oldest of them, which avoids the memory and time cost of a full linked list. LFU keeps a small logarithmic counter that decays over time, so a one-time scan cannot flush hot keys. If an interviewer asks you to code an LRU cache: a hash map plus a doubly linked list gives O(1) get and put (in Java, LinkedHashMap with access order).

CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lfu
INFO stats      # evicted_keys, expired_keys, keyspace_hits, keyspace_misses

Expiry versus eviction, a distinction worth stating. Expiry removes keys whose TTL has passed, regardless of memory. Eviction removes keys that are still valid because memory is full. A cache needs both: TTL for freshness, eviction so a full cache keeps working instead of rejecting writes.

What happens at the limit, in order.

  1. A write command arrives and used memory is above maxmemory.
  2. Redis applies the policy: it evicts some keys until enough memory is freed.
  3. If the policy is noeviction, or no eligible keys exist (for example a volatile policy with no TTL keys), the command fails with an OOM error. Reads keep working.
PolicyCandidatesChoose when
noevictionNoneRedis is a primary store; failing is better than losing data

allkeys-lfuAll keys, least frequently usedA stable popular set; scans must not flush it

LRU versus LFU, with an example. A nightly report job reads 5 million keys once. Under LRU those keys are all "recently used" and push out your really popular keys. LFU counts access frequency (with decay, so it also forgets old fame), so keys read once stay low and are evicted first. Choose LFU when you have a clear hot set plus occasional scans.

Practical points. Memory used for replication and client output buffers counts toward the limit but is not evicted, so leave headroom (set maxmemory to maybe 70 to 80 percent of the host RAM, less if you snapshot with fork). Watch evicted_keys: a steady non-zero rate means the working set does not fit and the hit rate is suffering, so add memory or shrink values. Redis eviction is approximate (sampling), and a larger maxmemory-samples (10) improves accuracy at a small CPU cost.

Remember: default noeviction = writes fail. Cache: allkeys-lru or allkeys-lfu. Redis LRU samples, it is not exact.

Memory keeps growing even though you set TTLs. What do you check? Intermediate

First INFO keyspace: the line keys=5000000,expires=1200000 shows how many keys have no TTL. Most often some code path writes keys without a TTL, or the key space has unbounded cardinality, or a collection only grows. Then I find the offending prefix with SCAN and TTL, and fix the code, not just the symptom.

Typical causes: a plain SET after SETEX removes the TTL; INCR on a new key creates it without a TTL; one key per request id or per user per minute; a list, set or stream with no trimming (LTRIM, XTRIM); big keys (--bigkeys); and fragmentation (mem_fragmentation_ratio well above 1.5). Expired keys nobody reads can also linger until the sampler finds them. As a guard, set maxmemory with an eviction policy so growth cannot take the host down.

A systematic way to debug, in order.

  1. Is it really keys? Compare used_memory with used_memory_rss in INFO memory. If RSS is much higher (mem_fragmentation_ratio above about 1.5), the allocator holds freed memory; consider active defragmentation or a restart during a quiet period. If used memory itself grows, continue.
  2. Key count and TTL coverage: INFO keyspace shows keys=N,expires=M. A big gap means many keys never expire.
  3. Which prefix? Sample with SCAN and check TTL and MEMORY USAGE per key, or run redis-cli --memkeys and --bigkeys. Group the results by prefix.
  4. Match the prefix to the code that writes it.

The usual culprits, each with the cause.

  • No TTL set: SET key v (clears an earlier TTL), or INCR/HSET creating a new key, since only SET ... EX, EXPIRE and SETEX add a TTL.
  • Unbounded cardinality: a key per request id, per session without cleanup, or per user per second.
  • Unbounded collections: a list or stream that is only appended to. Trim with LTRIM, XADD ... MAXLEN ~ 100000 or XTRIM.
  • Fat values: verbose JSON, no compression, or large serialized Java objects.
  • Replication and client buffers: a slow replica or pub/sub subscriber can make the output buffer grow (INFO clients, client-output-buffer-limit).

Fixing it for good: add a code review rule "every cache write has a TTL", wrap Redis writes in one helper that enforces it, set maxmemory plus a sensible policy, and alert on used_memory and on the ratio of keys without TTL.

Remember: compare keys with expires, find the prefix with no TTL, cap collections, set maxmemory.

7. Atomicity, Lua scripts and messaging

How do Redis transactions work, and how are they different from SQL transactions? Intermediate

After MULTI the commands are queued, and EXEC runs them in order with no other client's command in between. So you get isolation, but no rollback: if one command fails at run time, the others still run. For optimistic locking you add WATCH key: if another client changes a watched key before EXEC, EXEC returns nil, nothing runs, and your code retries.

A syntax error found while queuing discards the whole transaction at EXEC, but a runtime error (INCR on a non-number) does not undo the rest. Because commands are only queued, you cannot read a value inside the transaction and use it in a later command of the same transaction. For that logic you need WATCH in the app, or better, a Lua script.

WATCH balance:7
v = GET balance:7           # app reads
MULTI
SET balance:7 (v - 50)
EXEC                        # nil if someone else changed balance:7

What you actually get. Redis transactions provide two guarantees: the queued commands run one after another without interruption (isolation), and either all are queued and run or, if a queuing error occurs, none run. They do not provide rollback of runtime errors, so the "A" in ACID is not there in the SQL sense.

Compare with SQL.

PropertySQL databaseRedis MULTI/EXEC
Rollback on failureYesNo: other commands still execute
Read a value mid-transaction and branchYesNo: commands are only queued
IsolationConfigurable levelsFull: nothing runs in between
DurabilityCommit is durableDepends on AOF and replication settings

Why no rollback? The Redis authors argued that runtime command errors in a transaction are programming errors (wrong type), found in development, and that skipping rollback keeps Redis simple and fast.

How WATCH gives optimistic locking, walked through. You want to subtract 50 from a balance only if it is at least 50.

  1. WATCH balance:7 then GET balance:7 returns 120.
  2. Your code decides it is allowed and starts MULTI, queues DECRBY balance:7 50.
  3. EXEC: if no one modified balance:7 since the WATCH, it runs. If someone did, EXEC returns nil (aborted) and you retry from step 1.

Under heavy contention the retries pile up, so for hot keys a Lua script is simpler and faster, since it does the check and write server-side in one step. In Cluster all keys in a transaction must be in one slot. Spring's SessionCallback is the way to run MULTI/EXEC correctly on one connection, because plain template calls may use different pooled connections.

Remember: MULTI/EXEC = isolated batch, no rollback. WATCH adds optimistic locking.

When and why would you use a Lua script in Redis? Intermediate

When I need a check-then-act sequence to be atomic, such as "release the lock only if I own it", "decrement stock only if above zero" or a token-bucket rate limiter. A Lua script runs inside Redis as one unit, so nothing else runs meanwhile, and it costs one round trip instead of several.

Rules: pass every key the script touches in KEYS (needed for Cluster routing) and other values in ARGV. Keep it short, since a slow script blocks all clients (after the busy-script limit, about 5 seconds, others get an error). Use EVALSHA with the script hash to avoid resending the text. Redis 7 added Functions, scripts stored on the server as a library.

-- release lock only if I still own it
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end

Why scripts exist. Redis commands are atomic one by one, but real logic is often "look at the value, decide, then change several keys". With separate commands another client can change the data between your read and your write. A Lua script is sent to Redis and executed on the main thread as a single indivisible step, so the whole read-decide-write sequence happens with nobody in between. It also replaces many round trips with one.

A second example: safe stock decrement.

-- KEYS[1] = stock key, ARGV[1] = quantity wanted
local s = tonumber(redis.call("GET", KEYS[1]) or "0")
if s >= tonumber(ARGV[1]) then
  redis.call("DECRBY", KEYS[1], ARGV[1])
  return 1       -- reserved
end
return 0         -- not enough stock

Called from Java as one execute(script, keys, args). Two buyers can never both take the last unit, which a GET-then-DECR sequence cannot guarantee.

Rules that keep it safe.

  • Declare keys in KEYS: required so Cluster can route to the right node, and the keys must be in the same slot.
  • Keep it short and deterministic: no loops over huge data; the script blocks the server. Past busy-reply-threshold (formerly lua-time-limit, default 5 s) Redis starts to reply BUSY to others, and you can only SCRIPT KILL a script that has not written yet.
  • Cache by hash: SCRIPT LOAD returns a SHA1, then call EVALSHA. Clients handle the NOSCRIPT fallback; Spring's DefaultRedisScript does this.
  • Redis 7 Functions: named libraries loaded into the server and persisted, easier to manage than loose scripts.

Scripts also make good rate limiters, lock releases, and compare-and-set updates (the version check from the stale-cache race). Mention that scripts are not rolled back on error either.

Remember: Lua = atomic read-decide-write in one round trip. Keep it short and pass keys in KEYS.

How does Redis pub/sub work, and what are its limits? Intermediate

Subscribers run SUBSCRIBE channel, a publisher runs PUBLISH channel message, and Redis pushes the message to whoever is subscribed at that moment. Nothing is stored: a subscriber that is offline, slow or not yet subscribed never sees it, and there is no acknowledgement or replay. So it suits ephemeral notifications and cache-invalidation broadcasts, not jobs that must be processed.

A slow subscriber's output buffer grows, and Redis disconnects it when it passes client-output-buffer-limit pubsub. In a Cluster, a published message is broadcast to every node; Redis 7 added sharded pub/sub (SPUBLISH) to confine it to a shard.

How it works, in a picture of time. Imagine a radio station. Anyone tuned in at the moment of the broadcast hears it; nobody can listen to it later. PUBLISH news "hello" returns how many subscribers received it right now. If the count is 0 the message is simply gone, and Redis does not store it anywhere.

Good uses. Telling all app instances to drop a local cache entry (cache invalidation broadcast), live notifications where a missed one is harmless (typing indicators, presence), chat-style fan-out to connected websocket servers. The subscriber being connected is the whole delivery guarantee, so reconnect logic must also resync state (for example reload from a source of truth after a reconnect).

Limits and pitfalls.

  • A subscriber connection is dedicated: once subscribed it cannot run normal commands, so libraries use a separate connection.
  • Slow subscribers: messages queue in the server's output buffer; past the limit Redis closes the connection (and the messages are lost).
  • Pattern subscriptions (PSUBSCRIBE) cost CPU for every publish since each pattern is checked.
  • In Cluster, classic publishes are propagated to all nodes, which is heavy with many channels; use sharded pub/sub (7.0+) where possible.
  • Keyspace notifications (events for expired keys) also use pub/sub and are lossy; do not use them for must-not-miss logic such as "process when this key expires".

Remember: pub/sub = fire and forget. Miss it and it is gone.

What are Redis Streams, and when would you use them instead of pub/sub or a list queue? Senior

A stream is an append-only log stored in a key. Consumer groups let several workers share it: each entry goes to one worker and stays pending until that worker acknowledges it, so I get at-least-once delivery, replay, and recovery from crashed workers. A plain list queue forgets a job once popped, and pub/sub forgets everything, so for anything important I use a stream, or a real broker like Kafka or SQS.

XADD appends with an auto id (millisecond time plus sequence). Workers call XREADGROUP; the entry sits in the group's pending list until XACK. If a worker dies, another claims the entry with XAUTOCLAIM (6.2) after an idle time. Entries stay until trimmed (XTRIM), so late readers can replay. Since a claim can redeliver, handlers must be idempotent. Versus Kafka: simpler to run and fine for modest volume, but one stream lives on one shard and is bounded by memory. A list can work for simple jobs: LPUSH plus blocking BRPOP, or LMOVE to a processing list for safety, but you build acks and retries yourself.

XADD orders * orderId 991 amount 40
XGROUP CREATE orders billing $ MKSTREAM
XREADGROUP GROUP billing w1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders billing 1731800000000-0

The mental model. A stream is a log: entries are appended with increasing ids and are not removed when read. Each reader keeps its own position. This is the idea behind Kafka, in a smaller form inside Redis.

Consumer groups, step by step. Suppose an orders stream, and three billing workers in group billing.

  1. A producer calls XADD orders * orderId 991, which appends an entry with id like 1731800000000-0.
  2. Worker 1 calls XREADGROUP GROUP billing w1 ... STREAMS orders >. The > means "entries never delivered to this group". Redis gives the entry to w1 only and records it in the group's pending entries list (PEL) with the delivery time.
  3. w1 processes it and calls XACK. The entry leaves the PEL.
  4. If w1 crashes, the entry stays pending. Another worker runs XAUTOCLAIM (or XPENDING then XCLAIM) for entries idle longer than, say, 60 seconds, and takes it over.

This gives at-least-once delivery: after a crash the same entry may be processed twice, so the handler must be idempotent (for example, a unique order id in the database). For poison messages, track the delivery count in XPENDING and move entries over some count to a dead-letter stream.

Operational caveats. Streams live in memory, so cap them with MAXLEN or MINID trimming (the ~ form is cheaper). A stream is one key, so one shard in Cluster. And persistence and failover caveats of Redis apply: an acknowledged XADD can be lost on failover. That is the reason for choosing a durable broker when messages are business-critical.

8. Distributed locks

How do you implement a distributed lock with a single Redis? Intermediate

Acquire with one atomic command: SET lock:order:42 <random-token> NX PX 30000. NX means only one client can create it, and PX gives a 30 second lease so the lock vanishes if the holder crashes. To release, delete the key only if it still holds my token, using a Lua script so the compare and delete are atomic.

The token matters. Without it: my work outlives the lease, the lock expires, another client takes it, and then I finish and delete their lock. The old pattern of SETNX then EXPIRE is unsafe: a crash between the two leaves a lock that never expires. If I fail to acquire, I retry with a short sleep, jitter and a maximum wait. Practical pitfalls: the lease must exceed the p99 work time (or a library watchdog, like Redisson's, renews it); plain locks are not reentrant; use fine-grained keys (per order, not global); and assume that a failover or a long pause can still produce two holders, so make the protected action idempotent.

SET lock:order:42 7f3a9c NX PX 30000
-- release (Lua): only if token matches
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1]) else return 0 end

What a lock is for. You want only one worker at a time to do a task, for example one instance running a nightly job, or one request processing order 42. A lock key in Redis is a shared "token on the table" that any instance can try to take.

Why each part of the command matters.

  • NX: set only if the key does not exist. Two clients racing get one success; Redis serializes them.
  • PX 30000: a lease. If the holder crashes the lock vanishes after 30 s instead of staying forever.
  • Random token as value: identifies the owner so only the owner can release.
  • One command: acquiring and setting the expiry in two steps (SETNX then EXPIRE) can leave a lock with no expiry if the client dies in between.

What goes wrong without the token, as a timeline.

  1. A takes the lock (30 s), starts a task that unexpectedly takes 40 s.
  2. At 30 s the lock expires; B takes it.
  3. At 40 s A finishes and runs DEL lock, deleting B's lock. Now C can also enter while B is still working.

With the token, A's delete finds a different value and does nothing.

Lease length and renewal. Pick a lease longer than the worst realistic run, or have a watchdog extend it while the work is alive (Redisson does this by default: 30 s lease renewed every 10 s while the client is alive). A watchdog protects against slow work but not against a frozen process, because a frozen process cannot renew, though it also cannot know it lost the lock when it wakes up.

Spring option. Spring Integration's RedisLockRegistry or Redisson's RLock save you from writing this. For one-job-at-a-time scheduling, ShedLock is a library built for exactly that, usually on top of a database or Redis.

The honest limit. A single-Redis lock is best-effort. A failover can lose the lock key; a long pause can outlive the lease. Use it for efficiency, and protect correctness with idempotency or a database constraint, as discussed next.

Remember: SET NX PX with a random token, release with a Lua compare-and-delete. A lease can expire, so make the work idempotent.

What is Redlock, and what is the Kleppmann versus Antirez debate? Senior

A single Redis lock can be lost on failover, because the replica may not yet have the lock key. Redlock takes the lock on five independent Redis masters and counts it as held if a majority (3 of 5) grants it within the lease time. Kleppmann argued it is still unsafe for correctness, because it relies on timing assumptions (no long pauses, no clock jumps) and gives no fencing token. My answer: Redis locks are fine for efficiency (avoiding duplicate work); for correctness add a fencing token or a database constraint.

Kleppmann's scenario: a client gets the lock, pauses (GC, page fault), the lease expires, another client takes the lock, and the first resumes believing it still holds it. Clock jumps on a node can also expire locks early. He advised: if the lock is for efficiency, a single Redis lock is enough; if it is for correctness, you need a fencing token (an ever-increasing number checked by the resource itself), from a system such as ZooKeeper or etcd, or simply use the database's own guard: unique constraints, UPDATE ... WHERE version = ?, or transactions. Antirez replied that the timing assumptions are acceptable in practice; but Redlock's random token is not monotonic, so it cannot serve as a fencing token. Redisson's plain RLock is a single-node lock with a watchdog (default lease 30 s), not Redlock.

The problem Redlock tries to fix. With one Redis, if the primary dies right after granting a lock and before the replica copies it, the replica becomes primary without the lock key and a second client acquires the same lock. Two holders exist. Redlock tries to survive that by using several independent masters.

The algorithm in steps.

  1. Record the start time. Try to acquire the same lock (same random token, short per-node timeout) on each of 5 independent masters, one after another.
  2. The lock counts as acquired if a majority (3 or more) said yes and the elapsed time is less than the lease validity (lease minus elapsed minus a clock drift allowance).
  3. If not acquired, release on all nodes and retry after a random delay.

Kleppmann's critique, in plain terms. The safety depends on time. If a client pauses (garbage collection, a stalled VM, slow disk) for longer than the lease, it will resume and write while someone else legitimately holds the lock. No checking of the clock on the client can fix this, because the pause may happen right after the check. A correct lock needs a fencing token: each acquisition returns a number that always increases, and the protected resource (database or storage) rejects writes with a number lower than one it has already seen. Redlock hands out random values, not increasing numbers, so it cannot be used for fencing. He also noted that nodes' clocks can jump, which can shorten leases.

Antirez's reply. Real systems already rely on bounded clock drift and process pauses are rare and can be detected by comparing times after acquisition; so for many uses Redlock is good enough.

How to answer the interview question. Classify the lock. If it only prevents duplicate work (efficiency, for example refreshing a cache), a single Redis lock is fine. If correctness depends on mutual exclusion (money, inventory), use something with fencing (ZooKeeper, etcd, or a database row lock or optimistic version), or design the operation to be idempotent so a double run is harmless. Redisson also offers a RedLock implementation, but many practitioners avoid it for the reasons above.

Remember: lock for efficiency: Redis is fine. Lock for correctness: fencing token or a database constraint.

9. Patterns: rate limiter, leaderboard, session store

Design a rate limiter with Redis. Compare the algorithms. Senior

I would use a token bucket for an API: it allows short bursts and keeps a steady average rate. The simplest option is a fixed-window counter (INCR a per-minute key, expire it, reject above the limit), but it allows double the limit across a window boundary. Whatever the algorithm, the check-and-update must be atomic, so I run it in a Lua script.

  • Fixed window: key rate:user7:10:15, INCR, set expiry on the first hit. Cheap, but 100 requests at 10:15:59 plus 100 at 10:16:00 pass a limit of 100 per minute.
  • Sliding window log: a sorted set of request times; remove old entries (ZREMRANGEBYSCORE), count with ZCARD, add the new one. Exact, but memory per request.
  • Sliding window counter: blend the current and previous window counts with a weight. Two small counters, a good compromise.
  • Token bucket: store token count and last refill time; each request refills by elapsed time and takes one token.

Key by user, API key or IP; return 429 with Retry-After; decide whether to fail open or closed if Redis is down (most APIs fail open). Do INCR and EXPIRE together: if the app crashes between two separate calls, the counter never expires and the user stays blocked forever.

-- fixed window, atomic via Lua: KEYS[1]=counter  ARGV[1]=limit ARGV[2]=window seconds
local c = redis.call("INCR", KEYS[1])
if c == 1 then redis.call("EXPIRE", KEYS[1], ARGV[2]) end
if c > tonumber(ARGV[1]) then return 0 end
return 1

Start from the requirement. "Allow at most N requests per user per window." The design questions are: how exact must the limit be, may short bursts be allowed, how much memory per user, and what happens if Redis fails. A limiter shared across many API servers needs a central counter, which is why Redis is a natural fit.

Token bucket as Lua, in words. Keep a hash with tokens and ts. On each request: compute elapsed time since ts, add elapsed * rate tokens up to the capacity, set ts to now, and if tokens are at least 1 subtract one and allow; else deny and return how long until the next token. Use the Redis server time (TIME inside the script) so that app server clock skew does not matter. All of this inside one script means no race between instances.

Sliding window log, example. A zset per user, score = timestamp in ms. For each request: remove entries older than now minus 60,000, count the rest, and if the count is below 100, add this request and allow. The cost is one zset entry per request, so it suits low limits (100 per minute) but not millions per second.

Production details.

  • Put the limiter in a gateway or filter so every route is covered; return 429 with Retry-After and rate-limit headers.
  • Choose the key: user id for logged-in users, API key, otherwise IP (careful with shared NAT addresses).
  • Set a TTL on every limiter key so idle users cost nothing.
  • Decide fail-open (allow if Redis is down, usual for public APIs) versus fail-closed (login or payment endpoints), and add a small local fallback limiter.
  • In Cluster, the keys used in one script must share a slot; one user key per call is fine.

Remember: fixed window is simple but leaks at the edge. Token bucket allows bursts. Make it atomic with Lua.

Design a real-time leaderboard with Redis. Intermediate

One sorted set per board: the player id is the member and the score is the score. ZINCRBY adds points atomically, ZRANGE ... REV WITHSCORES gives the top N, and ZREVRANK gives any player's rank in O(log N), even among millions. The database remains the source of truth and the set can be rebuilt from it.

Daily or weekly boards use one key per period (lb:2026-11-17) with a TTL, and ZUNIONSTORE combines them. To break ties by who reached the score first, encode time into the fractional part of the score. Neighbours of a player: get the rank, then read a range around it. Limits: one sorted set lives on one node; for hundreds of millions of members, shard by region or score range and merge the top lists. Memory is roughly 50 to 100 bytes per member.

ZINCRBY lb:global 20 player:7
ZRANGE lb:global 0 9 REV WITHSCORES      # top 10 (6.2+; older: ZREVRANGE)
ZREVRANK lb:global player:7              # my rank, 0 is first

Why a sorted set fits so well. A leaderboard needs three operations to be fast at any scale: change a player's score, list the top N, and find a player's rank. A relational table needs an index and an ORDER BY ... LIMIT or a COUNT(*) of players with higher scores, which gets slow with millions of rows and constant updates. A sorted set does each of these in O(log N) in memory.

The three core operations, with values.

ZINCRBY lb:global 50 player:7        # player 7 earned 50 points; returns new score
ZRANGE lb:global 0 9 REV WITHSCORES   # top 10 with scores
ZREVRANK lb:global player:7           # 0-based rank from the top (add 1 for display)
ZRANGE lb:global (rank-2) (rank+2)    # players around me (compute indexes in app)

Time-bound boards. For a weekly board use a key per period (lb:2026-W47), update both global and weekly sets, and give the weekly set a TTL of a few weeks. To combine days into a week use ZUNIONSTORE lb:week 7 lb:d1 ... lb:d7 (with WEIGHTS if some days count more).

Ties. Equal scores are ordered by member name, which is rarely what you want. A common trick is to pack a time part into the fractional digits of the score (for example points plus a small number that is larger for earlier achievers), keeping the total within the 53-bit precision of a double, so the earlier achiever ranks higher.

Scaling and safety.

  • Keep the database as the system of record (or an events log); if Redis loses data, rebuild the set from it.
  • For huge boards (hundreds of millions), shard by something sensible (country, game) and merge top N, because a single sorted set is one key on one node.
  • Do not call ZRANGE 0 -1 on a big board; always page.
  • Show "approximate rank" for far-down players if exact rank is not needed, and use a cache for the top-10 page that is read by everybody.

Remember: sorted set: ZINCRBY to score, ZRANGE REV for top N, ZREVRANK for my rank.

How would you use Redis as a session store, and what should you watch for? Intermediate

Web servers should be stateless so any instance can serve any request, so the session data lives in Redis and the browser holds only a random session id in a cookie (HttpOnly, Secure). Redis stores session:<id> with a TTL equal to the idle timeout, refreshed on each request. In Spring, Spring Session with Redis does this with configuration.

Watch for: Redis availability becomes login availability, so use replication with failover and decide what happens on loss (users log in again). Keep sessions small. Add an absolute maximum lifetime besides the idle one. Use TLS and auth. Be careful with serialization: changing a session class between deploys can make old sessions unreadable. Alternative: signed stateless tokens (JWT) avoid the lookup but make early revocation harder.

The problem. If sessions live in a web server's memory, the user must always return to the same server (sticky sessions), a restart logs people out, and scaling out is awkward. Moving the session data to a shared store makes the web tier stateless: any instance can serve any request.

Request flow, step by step.

  1. User logs in. The server creates a random, unguessable session id (at least 128 bits from a secure random source) and stores session:<id> in Redis (a hash with user id, roles, a few attributes) with a TTL of, say, 30 minutes.
  2. The response sets a cookie containing only that id: HttpOnly (JavaScript cannot read it), Secure (HTTPS only), SameSite (CSRF protection).
  3. Each later request carries the cookie; the server reads Redis, and refreshes the TTL (EXPIRE), giving a sliding idle timeout.
  4. Logout deletes the key, so the session is invalid immediately.

Design decisions to mention.

  • Idle and absolute timeouts: store the creation time and force re-login after, say, 8 hours even if active.
  • Revocation: deleting the key kills a session at once, which is the main advantage over JWTs that stay valid until they expire (unless you keep a deny list, which is a state store again). Also allows "log out everywhere" by keeping a set of session ids per user.
  • Persistence and HA: if Redis loses data, users must log in again. For most sites that is acceptable; if not, use AOF and replicas. Decide the failure mode up front.
  • Size and serialization: keep sessions small (ids and flags, not whole objects); use JSON or a stable format, since a changed Java class can make old sessions unreadable after a deploy.
  • Security: TLS to Redis, authentication and ACLs, rotate the session id on login (prevents fixation).

Spring. Adding spring-session-data-redis and @EnableRedisHttpSession (or the equivalent property) replaces the servlet container's session with the Redis-backed one; the application code that uses HttpSession does not change.

Remember: cookie holds only the id; Redis holds the data with a sliding TTL. Plan for Redis loss.

10. Spring Cache and resilience

How does Spring's cache abstraction work with Redis? Intermediate

I enable it with @EnableCaching and annotate methods. @Cacheable runs the method only on a miss and stores the result, @CachePut always runs and updates the cache, and @CacheEvict removes an entry. Spring wraps the bean in a proxy that consults a CacheManager; with Redis that is RedisCacheManager. Two defaults I always change: entries have no TTL, and values use JDK serialization.

The key defaults to the method arguments; set it with SpEL, key = "#id". Use unless = "#result == null" or condition to skip caching. Redis keys are prefixed with the cache name, like users::42. Set entryTtl and a JSON serializer in RedisCacheConfiguration, since JDK serialization is bulky and breaks when a class changes.

@Cacheable(cacheNames = "users", key = "#id", unless = "#result == null")
public User find(long id) { return repo.findById(id).orElse(null); }

@CacheEvict(cacheNames = "users", key = "#u.id")
public void update(User u) { repo.save(u); }

@Bean RedisCacheManager cacheManager(RedisConnectionFactory f) {
  var cfg = RedisCacheConfiguration.defaultCacheConfig()
      .entryTtl(Duration.ofMinutes(10))
      .serializeValuesWith(SerializationPair.fromSerializer(
          new GenericJackson2JsonRedisSerializer()));
  return RedisCacheManager.builder(f).cacheDefaults(cfg).build();
}

What the abstraction is. Spring's cache support is a thin layer: you put annotations on methods, and Spring generates a proxy around the bean. When someone calls the method, the proxy builds a key, asks a CacheManager for the named cache, and either returns the cached value or calls the real method and stores its result. Redis is only one possible backing store (Caffeine, Ehcache and others use the same annotations), so swapping the store does not change business code.

Flow of one @Cacheable call.

  1. Caller invokes userService.find(42) (a call through the Spring proxy).
  2. Proxy computes key users::42 and does GET in Redis.
  3. Hit: deserialize and return; the method body never runs.
  4. Miss: run the method (database query), serialize the result, SET users::42 ... EX ttl, return it.
AnnotationRuns the method?Cache effectTypical use

@CacheEvictAlwaysRemoves entry (or all with allEntries = true)Delete and update methods

Configuration choices that matter.

  • Per-cache TTL: pass a map of RedisCacheConfiguration by cache name, so users lives 10 minutes and flags 30 seconds.
  • Serializer: JSON (Jackson) rather than JDK. Mind default typing, because the JSON must carry or know the class to deserialize back; and avoid classes without default constructors.
  • Key prefix: set a prefix per app or version (computePrefixWith) so deployments with incompatible classes do not read each other's entries.
  • Null handling: by default nulls are cached; disableCachingNullValues() changes this.

When the annotations are not enough. They give simple cache-aside only. For stampede control beyond sync = true, multi-level caching, or Redis-specific features (hashes, TTL jitter), use RedisTemplate directly or a library such as Redisson or a Caffeine plus Redis composite.

What are the common pitfalls with @Cacheable? Senior

The biggest one is self-invocation: calling a @Cacheable method from another method of the same class bypasses the proxy, so nothing is cached. Others: no TTL by default, stampede on concurrent misses, cached nulls, serialization breaking after a deploy, key collisions, and eviction before the transaction commits.

  • Self-invocation / private methods: the proxy is skipped. Move the method to another bean; it must be public.
  • No TTL: stale data lives forever. Configure entryTtl.
  • Stampede: concurrent misses all run the method. sync = true helps per JVM only.
  • Null caching: nulls can be cached, so a missing id stays missing. Decide on purpose with unless or disableCachingNullValues().
  • Serialization: changing a class between deploys can make old entries unreadable; use tolerant JSON or version the cache name.
  • Key collisions: same cache name and arguments in two methods share entries; use explicit keys.
  • Transactions: an eviction can run before the database commit, so a concurrent reader refills the old value; evict after commit (TransactionAwareCacheManagerProxy).
  • Redis errors failing requests: add a CacheErrorHandler so an outage becomes a miss, not a 500.

The proxy explained, because it causes the top pitfall. Spring caching works by wrapping your bean in a generated subclass or JDK proxy. Calls coming from other beans go through the proxy and see the caching logic. A call from inside the same object, this.find(id), goes straight to the real method and skips the proxy, so no caching, no eviction, no transaction either. The same applies to private or final methods, and to methods on objects you created with new rather than getting from Spring.

@Service class UserService {
  public User profile(long id) { return find(id); }   // self-call: NOT cached
  @Cacheable("users") public User find(long id) { ... }
}
// fix: move find() to another bean (UserRepositoryCache), or inject self, or use AspectJ mode

The transaction ordering pitfall, explained. Suppose @Transactional @CacheEvict on update. The eviction happens when the method returns, but the database commit may happen a moment later, when the transaction proxy completes. In that gap a concurrent reader misses, reads the old committed row, and caches it. After the commit the cache holds stale data until the TTL. The fix: evict after commit (wrap the cache manager with TransactionAwareCacheManagerProxy, or use @TransactionalEventListener(AFTER_COMMIT) to evict).

Other pitfalls, quickly.

  • Key defaults: with several arguments the key is a combination; with none it is a constant; two different methods with the same cache name and arguments can collide. Use explicit keys such as "'user:' + #id".
  • Caching mutable or lazy objects: caching a JPA entity with lazy collections fails on deserialization or serves a detached object; cache DTOs.
  • Large collections: a cached list is replaced as a whole; one change evicts the whole list.
  • Errors: by default a Redis exception propagates and fails the call. Implement CacheErrorHandler to log and treat the error as a miss.
  • Testing: unit tests that call the class directly or use a mock cache miss all of this; add an integration test through the real proxy (embedded or Testcontainers Redis).

Remember: proxy means no self-calls. No TTL by default. Treat cache errors as misses.

What should your service do when Redis is down or slow? Senior

If Redis is a cache, the service must keep working, slower, but protected. I use short client timeouts (tens to a few hundred milliseconds), a circuit breaker that stops calling Redis for a few seconds after repeated failures, and a limit on the fallback path to the database, because a Redis outage means a 100 percent miss rate that can crush the database.

Catch cache exceptions so they never fail the request, and return degraded responses if needed (stale data from a local L1, hide non-essential features). For other uses choose fail-open or fail-closed on purpose: a rate limiter usually fails open, a payment lock usually fails closed. Sessions: decide between logging users out and a read-only mode. Also set client pool size and timeouts: a missing timeout is how one slow Redis hangs every application thread. Test it: block Redis in staging and watch the database.

Think in terms of dependencies and failure modes. If Redis is only a cache, then "Redis is slow" or "Redis is down" must degrade to "pages load slower", never to "site is down". The danger is not the missing cache itself, but how your app reacts: threads waiting, retries piling up, and a database suddenly receiving all reads.

What happens without protection, as a chain.

  1. Redis stops answering. The client has a 2 s (or infinite) timeout.
  2. Each request thread blocks 2 s waiting for the cache, so the thread pool fills up (200 threads at 100 requests per second are exhausted in 2 s).
  3. Requests queue, latency goes to timeouts, health checks fail, instances restart, and the site is effectively down even though only the cache failed.

The layered defence.

  • Short timeouts: connect and command timeouts of about 50 to 200 ms, so a slow Redis costs a bounded delay.
  • Circuit breaker (Resilience4j): after, say, 50 percent failures, open for 10 seconds and skip Redis entirely (go straight to the fallback), then probe again (half-open).
  • Bulkhead: a separate small thread pool or semaphore for cache calls so they cannot take every thread.
  • Protect the database: a concurrency limit, rate limit, or request coalescing on the fallback path, because every read is now a miss.
  • Degrade gracefully: serve stale data from a local L1, hide non-critical features (recommendations), return cached HTTP responses from a CDN.

Finally, rehearse it: block the Redis port in staging, watch thread pool usage and database load, and fix what breaks before production does it for you.

Remember: short timeout, circuit breaker, protected fallback, deliberate fail-open or fail-closed.

Redis or Memcached: how do you choose? Basic

I choose Redis by default, because one tool gives me data structures, atomic operations, TTLs with eviction policies, persistence, replication and failover. I would pick Memcached only for a very simple, large, multi-core blob cache where I want the simplest possible operations.

Memcached stores only string blobs, is multi-threaded (uses many cores on one machine), has no persistence or built-in replication, and shards on the client side by consistent hashing. Redis commands run on one thread, but you can run several instances or a Cluster. If you need counters, sets, sorted sets, locks, queues or rate limiting, Redis is the answer.

Where Memcached is genuinely good. It is very simple: a distributed hash table for byte blobs with LRU eviction. It is multi-threaded, so a single large machine can serve high throughput across many cores, its memory management (slab allocator) is predictable, and there is little to configure or get wrong. For a plain "cache of rendered pages or query results", it works well and many large sites ran on it for years.

Where Redis wins, with concrete examples.

  • Atomic operations on structures: counters (INCR), leaderboards, sets, without reading and writing blobs. Memcached has increments but no structures.
  • Partial updates: change one hash field instead of rewriting a big blob.
  • Availability: replication plus automatic failover (Sentinel or Cluster). With Memcached, a lost node means a cold slice of the cache (and clients rehash).
  • Persistence and warm restarts (optional RDB or AOF).
  • More roles: locks, queues and streams, pub/sub, sessions, rate limiting. One system to operate instead of two.
  • Eviction choices: LRU and LFU, volatile or all keys; plus per-key TTL.

When Memcached still makes sense. A very large, read-mostly, blob-only cache where the throughput of a single multi-core node matters and you do not want to run more processes; or a team that already operates it well. With modern Redis (I/O threads, Cluster), the performance gap is small for most workloads, so the decision is usually about features and operations.

Can Redis replace your database? When is it a primary store? Senior

For rebuildable or short-lived data, yes: sessions, rate-limit counters, leaderboards, presence, feature flags. For money, orders and accounts, no: I keep a real database as the truth and Redis in front of it. The line: if I can rebuild it, Redis may be the primary; if losing a second of it costs money, it should not be.

Why not for everything: the data set must fit in RAM, which is costly; durability is weaker (AOF everysec plus async replication can lose the last second of writes); there are no joins or rich queries, and secondary indexes need modules or manual upkeep; transactions have no rollback; and Cluster restricts multi-key operations.

Two questions decide it. Can I lose this data, and can I query it the way I need? If losing a few seconds of writes is acceptable (or the data can be rebuilt from elsewhere) and access is by key or simple structure, Redis may be the primary. If I need durable commits, relational queries, constraints or an audit trail, a database is.

Primary in Redis: user sessions, rate limiter counters, leaderboards that can be rebuilt, feature flags, presence, job state with a short life, and an inventory "hold" with a few minutes of life. The middle path. Use Redis in front of the database (cache), or as a derived copy that a pipeline keeps in sync (a leaderboard recomputed from game events). Closing line for the interview: "Redis is the fastest tier of my architecture, not the one I trust for the final record."

Remember: Redis as primary only for data you can rebuild or can afford to lose a little of.

12. Real-life scenarios

Scenario: after a release, the cache hit rate falls from 95% to 60% and database CPU climbs. What do you do? Senior

The load did not change, so the release changed the cache keys or TTLs. I compare hits and misses over time, diff the release for anything touching keys, then sample live keys to see their shape. Then I fix or roll back the key change.

Situation: the release is the suspect. Check first: keyspace_hits and keyspace_misses in INFO stats to see when the fall began; evicted_keys (memory pressure) and expired_keys (TTL change). Look for: a changed key format or version prefix (a new prefix is all-miss at first, then recovers), a request-specific part like a timestamp or request id in the key (every key unique, cache full of one-use entries), a shorter TTL, a changed serializer, or a code path that bypasses the cache. Use SCAN to look at real keys. Fix: correct the key, or roll back; if memory is full and evicting, find the new big key family. Prevent: a hit-rate alert per cache name, key unit tests, a canary that watches hit rate, and a warm-up when the key format must change.

Why "same traffic, lower hit rate" points at keys. The hit rate is hits divided by lookups. If lookups are the same and hits fell, then lookups are asking for keys that are not there, or the keys that are there were removed too early. Three possibilities: the keys changed (so old entries are useless), entries are expiring or being evicted faster, or the cache was emptied.

A decision table to work from.

Resolve and prevent. Fix and redeploy, or roll back. A unit test that asserts the exact key string for each cached method catches this class of bug. Alert on hit rate per cache name (not just overall), because a drop in one small cache is invisible in the total.

Remember: a hit-rate drop right after a deploy usually means the key changed. Look at live keys.

Scenario: Redis hits maxmemory and the app starts throwing OOM errors on writes. Senior

The policy is noeviction (the default), or a volatile policy with no keys that have a TTL. For a cache I switch to allkeys-lru or allkeys-lfu right away, then find which key family grew and fix the root cause.

Situation: OOM command not allowed when used memory > 'maxmemory'. Check first: INFO memory, INFO keyspace (keys versus keys with expires), CONFIG GET maxmemory-policy, --bigkeys. Relief: change the policy if it is a cache; raise maxmemory if the host has room; or delete a known junk prefix with SCAN and UNLINK (never KEYS). Cause: keys without a TTL, a growing list or stream, or unbounded key cardinality. Prevent: a TTL on every cache key (review rule), cap collections, alert at 80 percent memory, and keep must-keep data in a separate instance from cache data.

Reading the error. The message OOM command not allowed when used memory > 'maxmemory' means Redis is refusing writes by design. It is the effect of noeviction, or of a volatile policy with no evictable keys. Reads still succeed, so the symptom is "reads fine, writes fail", which can look like a partial outage.

Triage in three steps.

  1. Stop the bleeding. If it is a cache, CONFIG SET maxmemory-policy allkeys-lru takes effect immediately and memory starts being reclaimed. If the host has spare RAM, raise maxmemory briefly (leave room for replication buffers and fork copy-on-write). Do not run KEYS or FLUSHALL on a production instance without thinking, because they either block or destroy data.
  2. Find the growth. Compare INFO keyspace now with a dashboard from last week. Check the key families with --bigkeys, --memkeys and SCAN sampling. Typically one prefix is responsible.
  3. Fix the cause. A missing TTL, an uncapped list or stream, or a new feature caching large payloads.

A trap to mention. Changing the policy to an eviction policy on an instance that also stores "must keep" data (locks, sessions, queues) can silently delete that data. If the instance is mixed, either split it into separate instances or use volatile-lru and make sure only disposable keys have TTLs.

Prevent. Alerts at 70 and 85 percent of maxmemory, an alert on a rising evicted_keys, a review checklist that every new key family states its TTL and expected cardinality, and capacity planning that leaves 20 to 30 percent headroom for the fork and replication buffers.

Remember: OOM on write = noeviction. Cache: allkeys-lru. Then hunt the key family with no TTL.

Scenario: p99 latency of every service using Redis jumps to 800 ms every few minutes. Senior

A regular pattern means something scheduled is blocking the single Redis thread: a cron job running an O(N) command, a big delete, a snapshot fork, or a mass expiry. I start with the slow log and line it up with the spike times.

Check first: SLOWLOG GET 20 (default threshold 10 ms, execution time only), then INFO commandstats. Who runs at that time? A job doing KEYS, SMEMBERS or HGETALL on a big key, or a big DEL. Then persistence: latest_fork_usec and save times, AOF with always or a slow disk. Then expiry waves (many keys with the same TTL), swapping, and a too-small client pool. Fix by cause: replace the heavy command with SCAN or chunks, use UNLINK, add TTL jitter, snapshot on a replica, keep memory headroom. Prevent: a slow-log alert and a review rule that batch jobs use SCAN.

The key reasoning. Redis serves everything on one thread, so latency for all clients rises together when that thread is busy or blocked. A spike repeating every few minutes tells you something periodic is occupying it: a scheduled job, a persistence event or a mass expiry. The slow log records commands slower than a threshold, but not time spent forking or in the expiry loop, so you check several sources.

Scenario: Redis failed over to a replica and users lost their last few seconds of data. Is that a bug? Senior

No, it is the design. Replication is asynchronous: the primary acknowledged the writes and died before sending them to the replica, so the promoted replica never had them. I either accept it for cache and session data, or shrink the window, or keep the truth in a durable database.

Check: replication offsets before the failure (INFO replication) and lag metrics; whether a partition let an old primary accept writes that were later discarded. Options: (1) accept it for a cache or session. (2) min-replicas-to-write 1 with min-replicas-max-lag 10 makes a primary refuse writes when it has no healthy replica, which limits what a cut-off primary can accept. (3) WAIT 1 100 after critical writes narrows the gap, but is not a guarantee. (4) Use Redis as a derived copy of a durable database. (5) For queues that must not lose jobs, use Kafka or the database. Prevent: write down the data loss you accept per use case, and test failover in staging.

Explain the timeline to the stakeholder.

  1. 10:00:00.000 The client writes order:5 = paid; the primary applies it and replies OK.
  2. 10:00:00.002 The primary is about to send it to the replicas, but the host dies.
  3. 10:00:03 Sentinel or Cluster promotes a replica that does not have that write.
  4. The client was told "OK", yet the new primary has never heard of it.

That window is the replication lag (usually milliseconds), plus anything in the replication backlog that had not been sent. If the old primary was cut off by a network partition and kept accepting writes for some seconds before being demoted, the loss can be larger, since all those writes are discarded when it rejoins as a replica.

What to say about the design. "Asynchronous replication optimizes latency over durability, so I decide per use case how much loss is tolerable, document it, and put anything above that threshold in a durable store." Also mention Redis Cluster has the same property, and AOF everysec adds a second loss window only on a full crash, not on a replica promotion.

Remember: async replication can lose the last writes by design. Decide the acceptable loss per use case.

Scenario: during a flash sale one Redis Cluster node is at 100% CPU while the other nodes are idle. Senior

That is a hot key: one key, one slot, one node. I find the key, then take the traffic off it with a short local cache in the app, key copies or replica reads. More shards will not help.

Check first: per-node ops per second and network out, then find the key with redis-cli --hotkeys (needs an LFU policy), a short MONITOR sample in a low-risk window (heavy), or client counters. Check value size too: a big value on a hot key saturates the network. Fix: a 1 to 5 second local cache for that key removes most traffic; or copy it into N variants (sale:42:0 to sale:42:7), read a random one and write all on change; or read from replicas. For a hot counter such as stock or likes, split it into sub-counters. Prevent: load-test the sale path, pre-warm and replicate known hot keys, put a CDN or page cache in front of read-only pages, and alert on hot keys.

Recognise the signature. One node pinned at 100 percent CPU (or network) while others idle, with total traffic well within the cluster's capacity, is the textbook hot key or hot slot. During a flash sale, one product, its stock counter, or a promotion config receives most of the traffic. Adding nodes cannot help, because a single key can never be split by the cluster.

Immediate mitigation (minutes).

  • Put a 1 to 2 second in-process cache in front of the hot read key (a config or product page). Even at 50,000 reads per second across 100 instances, Redis then sees about 50 to 100 reads per second for it.
  • Serve the page itself from a CDN or response cache if it is the same for everyone.
  • Shed load that is not essential for a while.

The stock counter is special. A counter that every purchase decrements cannot be cached locally. Options: split the stock into N sub-counters (stock:42:0 to stock:42:7) with a share of the units each, and decrement a random one, retrying another if it is empty; or reserve batches per instance (each app instance takes 50 units from the central counter and sells from its local batch); or put the purchase requests in a queue and serialize decrements. The trade is more complexity and possible small imbalance between shards, but the load spreads.

Confirming it is not something else. Check that it is not a big value (network), a Lua script that is slow, or a slot imbalance due to a hash tag that put too many keys together (CLUSTER COUNTKEYSINSLOT). Use per-node INFO commandstats and client-side metrics by key prefix.

Prevention. Load test with realistic skew (Zipf-like) not uniform keys, pre-split known hot keys before an event, use a CDN for public pages, and have a runbook with the toggles ready.

Remember: one node pinned = hot key. Add L1 cache or key copies, not shards.

Scenario: a user updates their profile but keeps seeing the old data for several minutes. Senior

The database has the new data, so some cache layer still serves the old copy. I check the layers one by one: browser or CDN, per-instance local cache, Redis, and the database read replica. The most common root cause is a write path that deletes a different key than the read path uses.

Check: response headers (Cache-Control, Age); if refreshing shows old and new data alternately, it is a per-instance L1 cache; GET and TTL the Redis key; replica lag. Then the write path: is the key built differently on write and read (tenant or language missing)? Does the delete run before the transaction commits, so a concurrent read refilled the old value? Did the delete fail and the exception get swallowed? Or the slow-reader race? Fix: correct the key, evict after commit, retry failed invalidations, bypass the cache for that user for a few seconds after a write. Prevent: one helper that builds keys for both read and write, an integration test through the real cache, and the TTL as safety net.

Why this is hard to see. Several layers can hold a copy, so "the data is wrong" does not tell you which layer is wrong. A disciplined approach is to ask the same question at each layer, from the database outward, until you find the first layer that disagrees with the one before it.

The most frequent root causes, with examples.

  • Key mismatch: the read key is profile:{tenant}:{id}:{lang} but the eviction only knows profile:{id}, so it deletes nothing.
  • Order of operations: delete before commit, so a concurrent read refilled the old value.
  • Swallowed failure: the delete threw a timeout, the code logged it and moved on, and the entry stays until the TTL (several minutes).
  • Race: the slow reader refilled the old value after the invalidation.

For the user's immediate need, after a write you can set a short "recently written" flag so reads for that user bypass the cache for N seconds. Prevent with a single key-builder shared by readers and writers, retries for failed invalidations, and an agreed staleness bound documented per cache.

Remember: walk the layers one by one. Check that read and write build the same key.

Scenario: a scheduled job guarded by a Redis lock ran twice at the same time and charged some customers twice. Senior

Two instances both believed they held the lock: the lease expired during a long run, or the release deleted someone else's lock, or a failover lost the lock key. The real fix is to make the charge idempotent with a unique constraint, because a Redis lock only gives efficiency, not correctness.

Check: job logs with lock acquire and release times against the lease length, Redis failover events at that time, and the release code (token check?). Fix: token plus Lua release; a lease longer than the worst-case run, with a renewal watchdog; and above all an idempotency key per customer per billing period with a unique constraint in the database, so a second run does nothing. Prevent: a fencing token or version check at the resource, an alert on overlapping runs, and a test that forces a pause (the Kleppmann argument).

Be careful about the story you tell. "Redis lock failed" is too vague. List the ways two instances can both hold a lock, and check logs for each.

CauseEvidence in logs or metrics
Work longer than the leaseRun time greater than lease; second instance acquired during the first run
Process pause (GC, VM freeze)Gap in the first instance's logs; GC logs show a long pause

Why the real fix is not "a better lock". Any lock based on leases has a window where two holders can exist, because the holder cannot know instantly that its lease ended. So make the protected operation safe to run twice. For billing: a table charge(customer_id, period, ...) with a unique key on (customer_id, period), and the job inserts first; the second run fails the insert and skips. Or pass an idempotency key to the payment provider so a repeat request returns the original result instead of charging again.

Layered remediation.

  1. Today: identify the affected customers and refund; the idempotency key work is the permanent fix.
  2. Lock hygiene: random token, Lua compare-and-delete, a lease longer than p99 (or a watchdog), and log acquire and release with durations.
  3. If the job truly needs exclusive access, use a fencing token or a database row lock (SELECT ... FOR UPDATE SKIP LOCKED) as the guard, rather than Redis.
  4. Monitor: alert when two runs overlap, and record job run ids.

Remember: the lock is for efficiency. Make the action idempotent, with a database constraint as the final guard.

Scenario: Redis becomes unreachable for ten minutes and the whole site goes down, even though Redis is "just a cache". Senior

The site depended on Redis more than intended: no or long timeouts filled the thread pool, or cache exceptions failed the requests, or the fallback overloaded the database. I restore Redis, then add short timeouts, a circuit breaker, error handling that treats failures as misses, and a protected fallback.

What usually happened: threads stuck waiting for Redis until the pool was full, so even requests that did not need Redis queued. Fix: connect and command timeouts of 50 to 200 ms, a circuit breaker, a CacheErrorHandler (cache errors become misses), a bulkhead so cache calls use a limited pool, a rate-limited fallback to the database, and a degraded mode (serve stale from L1, hide non-essential features). Prevent: a game day where Redis is blocked in staging, and a clear list of which features fail open and which fail closed.

The usual root causes, in the order they appear in post-mortems.

  1. No or long timeouts: the default of some clients is infinite or several seconds. Every request waits, threads run out, health checks fail.
  2. Exceptions bubbling up: a cache call that throws turns a harmless miss into a 500.
  3. Retry storms: retries multiply load and delay recovery when Redis returns (everyone reconnects and reloads at the same moment).
  4. Fallback overload: all reads go to the database at the same time and it collapses, making the outage worse and longer.
  5. Hidden hard dependencies: sessions, rate limiting or locks quietly required Redis for every request.

What the corrected design does during the same outage. Commands time out in 100 ms, the circuit breaker opens after a few failures and subsequent calls skip Redis instantly, the cache error handler turns failures into misses, a limiter allows only a safe number of concurrent database fallbacks, and non-critical features switch off. Users see slower pages for some requests and a few missing widgets, not errors.

Recovery behaviour matters as well. When Redis returns empty (cold), the hit rate starts at zero. Use a half-open breaker that ramps up, jittered TTLs, and pre-warming of the hottest keys so the database is not hit with the full load again.

Architecture and process. Run Redis with replicas and automatic failover; keep a small local L1 for the most important reads; classify every Redis use as fail-open or fail-closed in the design doc; and hold a game day: blackhole Redis in staging (drop its port with a firewall rule or proxy), watch which dashboards turn red, and fix them. Add alerting on cache error rate, not only on Redis host metrics.

Remember: a cache outage must become slower, not down. Timeout, breaker, protected fallback.

Scenario: a rate limiter built on INCR sometimes leaves counters that never expire, and users stay blocked forever. Senior

The code does INCR and then a separate EXPIRE. If the process crashes or the second call fails in between, the counter has no TTL, grows to the limit and never resets. I fix it by making the two steps atomic with a Lua script, and clean up the stuck keys.

Check: TTL key returns -1 for blocked users; SCAN with a TTL check finds the rest. Immediate: delete or set a TTL on those keys. Fix: a Lua script doing INCR plus EXPIRE together, or SET key 0 EX 60 NX first and then INCR (which keeps the TTL). A second guard: if TTL is -1 after the increment, set it. Prevent: a rule that any check-then-act logic in Redis goes into a script, and an audit that counts keys with no TTL in rate-limit prefixes.

Replay the failure, step by step.

  1. First request of the window: INCR rl:user7 returns 1 (the key is created without a TTL).
  2. The app is about to call EXPIRE rl:user7 60 but the pod is killed, the connection drops, or the call times out.
  3. The key now lives forever. Each later request increments it; once it passes the limit, every request is rejected and nothing ever resets it.

The bug is classic "two non-atomic calls that must be a unit". It is rare on any one request, so it only shows up at scale or during deployments (pods being restarted), which is why it looks mysterious.

Three ways to fix it.

-- 1) Lua: atomic (also fixes the case where the key lost its TTL)
local c = redis.call("INCR", KEYS[1])
if c == 1 or redis.call("TTL", KEYS[1]) == -1 then
  redis.call("EXPIRE", KEYS[1], ARGV[1])
end
return c

-- 2) Create with the TTL first, then INCR (INCR keeps the existing TTL)
SET rl:user7 0 EX 60 NX
INCR rl:user7

Option 3 is a pipeline or MULTI/EXEC with INCR and EXPIRE together, which sends both commands as a unit (the server either gets both or none arrives if the connection breaks mid-transaction), but the script is more robust because it can also repair a key whose TTL is missing.

Cleaning up. Find affected keys: SCAN MATCH rl:* then TTL equal to -1, and set a TTL or delete them (batch with a pipeline, never KEYS). Then add a monitor that counts keys with no TTL for the rate-limit prefix, so a recurrence is noticed immediately. Also review other places where code does read-then-write or two dependent commands (locks with SETNX then EXPIRE, counters with unique-set-plus-increment), since the same bug pattern likely exists there.

Remember: two calls are not atomic. INCR plus EXPIRE belong in one Lua script.
