Mental model: the 7 ideas everything hangs on

One line: a cache trades freshness and simplicity for speed. Redis is an in-memory data structure server that runs commands one at a time, so each command is fast and atomic. Every caching bug is either the cache and the database disagreeing, or many requests hitting the database at once.
  1. The cache is a copy, the database is the truth. You must always be able to rebuild a cache entry. If you cannot, it is a database and needs durability.
  2. Hit rate is the whole game. Going from a 99% to a 90% hit rate means ten times more database load.
  3. Every entry needs a way to die. A TTL, eviction, or explicit invalidation. Otherwise memory fills and data goes stale.
  4. Invalidation is the hard part. Updating the database and the cache are two separate writes, and any order can fail halfway.
  5. Failures come in crowds. Many callers miss one key (stampede), many keys expire together (avalanche), or one key takes all the traffic (hot key).
  6. Redis runs one command at a time. That makes single commands and Lua scripts atomic, and makes one slow command stall everyone.
  7. Replication and persistence are asynchronous. Both trade a little data for speed. Know the loss window.

1. Caching patterns, TTL and invalidation

Why do we cache, and what makes data a good candidate? Basic

We cache to make reads faster and to protect the database. A Redis read takes well under a millisecond, while a query with joins can take tens of milliseconds, and most reads never reach the database at all. Good candidates are read-heavy, expensive to compute, and fine to be slightly stale: product catalogs, profiles, config, permission lookups.

Bad candidates are data that changes on every request, data that must be perfectly fresh (a balance during a transfer), and data read once and never again. A cache also costs you something: staleness, one more component that can fail, and extra code. So before adding one I ask three things: what is the read-to-write ratio, how stale can this be, and what hit rate do I expect? For read-heavy data 90 to 99 percent is common. Below about 80 percent I would question the cache. I measure it with the hit rate (keyspace_hits versus keyspace_misses in INFO stats), p99 latency and database load before and after.

Remember: cache what is read often, costly to build and allowed to be a bit old. Then measure the hit rate.

Explain the cache-aside pattern. Why is it the most common one? Basic

In cache-aside (lazy loading) the application owns the logic. On a read it asks the cache first. On a miss it reads the database, puts the result in the cache with a TTL, and returns it. On a write it updates the database and then deletes the cache entry, so the next read refills it.

It is popular because the cache only holds data that was really requested, the system keeps working if the cache dies (just slower), and it works with any cache and database. The weak spots: the first read of each key is slow, entries can be stale between a database change and the invalidation, and every service must implement the same logic correctly.

String get(String id) {
    String v = redis.get("user:" + id);
    if (v != null) return v;               // hit
    v = db.loadUser(id);                   // miss: go to the source
    if (v != null) redis.setex("user:" + id, 300, v);
    return v;
}
void update(User u) {
    db.save(u);                            // 1. database first
    redis.del("user:" + u.id);             // 2. then invalidate
}
Watch out: forgetting the TTL, so one missed invalidation lives forever. Also caching "not found" results without a short TTL (see penetration).

Remember: read: cache, then database, then fill. Write: database first, then delete the key.

On a write, why delete the cache key instead of updating it? Intermediate

Because a delete cannot leave a wrong value behind, but an update can. If two writers update the database and the cache in different orders, the cache can end up holding the older value while the database has the newer one. A delete is safe to repeat and the next read rebuilds the entry from the truth.

Example: writer 1 sets the database to A, writer 2 sets it to B, but writer 2 writes the cache first and writer 1 second. The cache now says A, the database says B, until the TTL ends. With delete, the worst case is one extra miss. The price of delete is a cache miss right after every write, so for data written very often, deleting wastes the cache; there, a short TTL or a version check on update is better. If the delete itself fails, retry it through a queue and rely on the TTL as the last defence.

Remember: deleting is idempotent and cannot write a wrong value. Updating can.

Compare read-through, write-through and write-behind (write-back). Intermediate

Read-through means the cache itself loads from the database on a miss, so the app only talks to the cache. Write-through means every write goes to the cache and the cache writes to the database synchronously: always consistent, but writes are slower. Write-behind means the cache acknowledges at once and flushes to the database later in batches: very fast writes, but data can be lost if the cache dies before flushing.

Redis does none of these by itself. You build them in your code, with a library, or with a data grid. Cache-aside is basically read-through with the logic in your service. I use write-behind only for data where losing a few seconds is acceptable and the write rate is high: view counts, analytics counters, "last seen" times.

Remember: write-through = consistent but slower. Write-behind = fast but can lose data. Cache-aside = you decide.

How do you choose a TTL? Basic

The TTL is how long I accept stale data, so I pick it from the business, not from technology. I ask: if this value changes in the database and the cache does not know, how long can users see the old one? A product description may be fine for 5 minutes, a feature flag for 30 seconds, an account balance should not be cached at all.

The TTL is also my safety net: even if the invalidation code has a bug, the wrong value dies when the TTL ends. Longer TTL gives a better hit rate, shorter gives fresher data. Two rules I always follow. Add random jitter so many keys do not expire in the same second. Use a short TTL (30 to 60 seconds) for "not found" results.

SET product:42 "{...}" EX 300      # 5 minutes
TTL product:42                      # seconds left; -1 = no expiry, -2 = no key
Watch out: a plain SET without EX removes the old TTL (unless you use KEEPTTL). Many "keys that never expire" bugs come from this.

Remember: TTL = acceptable staleness, plus a safety net. Always add jitter.

How does Redis actually expire keys? Senior

Two ways together. Lazy expiry: when a key is read, Redis checks its expiry time and deletes it if it is past, so you never get an expired value. Active expiry: a background job on the main thread samples keys that have a TTL, several times a second, and deletes the expired ones.

So an expired key that nobody reads can stay in memory for a while until the sampler finds it. The sampler takes about 20 keys per round and repeats immediately if more than about 25 percent were expired, with a time cap so it does not stall requests. The effect: if millions of keys share the same expiry second, Redis spends time deleting them and latency spikes. That is one more reason for TTL jitter. On replicas, keys are not expired independently; the primary sends explicit DEL commands, so replicas stay in step. The expiry is stored as an absolute time, so it survives a restart (time spent down counts).

Remember: lazy on read plus sampling in the background. Same-second expiry means a spike, so use jitter.

What are the main cache invalidation strategies? Intermediate

Four: time-based (just a TTL), explicit delete on write, event-driven (a change event triggers the delete), and versioned keys. In real systems I combine them: explicit delete or events for freshness, and a TTL as the safety net for when those fail.

  • Delete on write: the code that changes data also deletes the key. Simple, but every writer must remember.
  • Event-driven: the database or service publishes a change (change data capture or a message queue) and a consumer deletes the key. Best when many services write the same table.
  • Versioned keys: put a version in the key (product:42:v17) so a change creates new keys and old ones age out by TTL. Good for lists and pages.

The hardest case is collections: a changed product sits inside many cached list pages, and tracking which ones is painful. A short TTL or a version number on the list is usually easier than tracking dependencies. For "read your own writes" (a user edits a profile and must see it now), I bypass the cache for that user for a few seconds, or write the new value straight in. Honest promise to the business: eventual consistency with a bound, never "always fresh".

Remember: delete or event for freshness, TTL as the net. Promise "eventually consistent within N seconds".

Can cache-aside serve stale data forever even with correct code? Show me the race. Senior

Yes, there is a classic race. A reader misses and reads value v1 from the database. Before it writes the cache, a writer updates the database to v2 and deletes the key (nothing to delete yet). Then the slow reader writes v1 into the cache. The cache now holds v1, the database holds v2, until the TTL ends.

It is rare because the window between the reader's read and write is short, but at high volume it happens. Defences: the TTL bounds the damage; a delayed double delete (the writer deletes again after about a second) removes a late stale write; or store a version with the value and write only if it is newer, using a small Lua script so the compare and write are atomic. For strict needs, read from the database, or let a change-data-capture stream be the only invalidator, since it keeps the order of changes.

Remember: a slow reader can refill an old value after the delete. TTL, delayed double delete or version check.

What is a multi-level cache, and when is a local in-process cache (Caffeine) better than Redis? Intermediate

A multi-level cache stacks layers: L1 inside the application process (Caffeine), L2 shared in Redis, then the database. L1 has no network hop, so reads take nanoseconds and cannot fail from the network. L2 is shared by all instances and survives an app restart. I use L1 only for small, hot, rarely changing data with a short TTL, and Redis for everything shared or large.

The risk of L1 is that every instance has its own copy. After a change the other instances still serve the old value, so L1 TTLs must be seconds, or you broadcast invalidations (Redis pub/sub, or Redis client-side caching with tracking, since Redis 6). L1 also lives on the JVM heap, so it needs a size limit and adds GC load, and a restart starts it cold. Caffeine uses Window TinyLFU, which gets a better hit rate than plain LRU. Typical L1 data: reference lists, config, feature flags, public keys.

Remember: L1 = fastest but per-instance and stale-prone. L2 Redis = shared. Keep L1 small and short-lived.

2. Failure modes: stampede, penetration, avalanche, hot and big keys

What is a cache stampede (thundering herd) and how do you prevent it? Intermediate

A stampede is when a popular key expires and many requests miss at the same moment, so they all run the same expensive query against the database. I prevent it by letting only one request rebuild the value: a short per-key lock, or serving the old value while one caller refreshes it in the background.

Why it hurts: the database slows down, so each rebuild takes longer, so more requests pile up, and it can collapse. Defences, simple to strong:

  • Per-key lock (single flight): the first miss takes SET lock:key token NX PX 5000 and rebuilds. Others wait briefly and re-read the cache. The lock TTL frees it if the holder crashes.
  • Serve stale while revalidating: store a soft expiry inside the value. After it passes, one caller refreshes while everyone else still gets the old value.
  • Probabilistic early refresh: each reader has a small chance to refresh before the real expiry, rising as expiry nears.
  • Jitter and pre-warming: spread TTLs and refresh known hot keys on a schedule.

In Spring, @Cacheable(sync = true) gives single flight inside one JVM only, not across instances.

Remember: one hot key, many rebuilders. Let one rebuild (lock or stale-while-revalidate), the rest wait or read stale.

What is cache penetration, and how do you stop it? Intermediate

Penetration is requests for keys that do not exist in the database either, so the cache never holds an answer and every request goes through to the database. It can be a bug or an attack with random ids. I stop it with input validation, caching the "not found" result for a short time, and a Bloom filter for large id spaces.

  • Negative caching: store a marker like NULL with a 30 to 60 second TTL. If a record is created right after, delete the marker on create.
  • Validate early: reject ids with the wrong format or range before any lookup.
  • Bloom filter: a small structure that says "definitely not present" or "maybe present". Load it with all valid ids and answer "not found" without touching cache or database. It has false positives but never false negatives, so no real item is rejected. It must be updated when items are created. Redis offers one through the RedisBloom module (built into Redis 8).
  • Rate limit abusive clients.

Remember: missing keys are never cached by normal logic. Validate, cache the null briefly, Bloom filter, rate limit.

What is a cache avalanche, and how is it different from a stampede? Intermediate

A stampede is one hot key with many readers. An avalanche is many different keys failing together, so the database sees a wave of many different queries. It happens when lots of keys were loaded with the same TTL and expire together, or when the whole cache goes down or is flushed. The fix is TTL jitter, spreading warm-ups, a highly available Redis, and protection on the database side.

Concretely: add random jitter (base 600 s plus a random 0 to 120 s), stagger warm-up jobs, run Redis with replicas and automatic failover, keep a small local L1 cache, and protect the database with a circuit breaker, a rate limiter or a queue so it degrades instead of collapsing. Have a reduced response ready (stale data or defaults) for when the database is overloaded.

int ttl = 600 + ThreadLocalRandom.current().nextInt(120);   // jitter
redis.setex(key, ttl, value);

Remember: stampede = one key, many callers. Avalanche = many keys at once. Jitter the TTLs.

What is a hot key, and what do you do about it? Senior

A hot key is one key that gets a huge share of traffic, such as a flash-sale product or a global config. In a Redis Cluster a key lives on exactly one node, so adding nodes does not help: that node saturates while others sit idle. The usual fix is a short-lived local cache in each app instance, plus copies of the key under several names.

  • Local L1 cache with a 1 to 5 second TTL removes most of the traffic.
  • Key copies: store hot:cfg:0 to hot:cfg:7 and read one at random. They hash to different slots and nodes. Writers update all copies.
  • Replica reads if slight staleness is fine.
  • Shrink the value, since a large value also saturates the network.
  • Counters: split into N sub-counters and sum on read.

To find hot keys: redis-cli --hotkeys (needs an LFU eviction policy), a brief MONITOR in a quiet window (it is heavy), or client-side metrics. More shards do not help because hashing sends the same key to the same shard every time.

Remember: one key = one node. Spread the reads with L1, key copies or replicas.

What is a big key, and why are KEYS * and big deletes dangerous? Intermediate

A big key holds a huge value, like a multi-MB string or a collection with millions of members. Redis runs one command at a time, so any command that touches the whole thing (DEL, HGETALL, SMEMBERS, KEYS *) blocks every other client until it finishes. I use UNLINK for deletes and the SCAN family for walking, and I split big keys into buckets.

KEYS pattern is O(N) over all keys; with ten million keys it can freeze the server for seconds. SCAN walks in small steps with a cursor: call it with 0, get a batch plus a new cursor, repeat until the cursor is 0. Each call is quick so others are served. Catch: SCAN may return a key twice, and keys added during the walk may be missed, so the code must be idempotent. HSCAN, SSCAN and ZSCAN do the same inside collections. UNLINK removes the key at once and frees memory in a background thread. Find big keys with redis-cli --bigkeys or MEMORY USAGE key. Also use FLUSHALL ASYNC rather than plain FLUSHALL.

SCAN 0 MATCH session:* COUNT 500   # returns next cursor + batch; stop at cursor 0
UNLINK session:big                 # non-blocking delete

Remember: O(N) command on a big key stalls everyone. SCAN, not KEYS. UNLINK, not DEL.

3. Redis internals

What is Redis, and how is it different from a plain key-value cache? Basic

Redis is an in-memory data structure server. The data lives in RAM, so operations take microseconds, and unlike a plain cache of opaque blobs it understands types (strings, hashes, lists, sets, sorted sets, streams) with atomic commands on each. It can also persist to disk, replicate, fail over, and shard.

So it is used as a cache, session store, rate limiter, leaderboard, lock service, simple queue, and sometimes as a primary store for small fast data. Disk is only for persistence and restart; reads never touch it. The caveat is memory: everything must fit in RAM, which is costly at large sizes, and a key has overhead beyond its payload (tens of bytes), so many tiny keys use much more than the raw data. maxmemory caps usage and the eviction policy decides what happens when it is reached.

Remember: in-memory, rich types, atomic commands. Not just a cache, but bounded by RAM.

Redis is single-threaded. Why is it still so fast? Intermediate

Command execution runs on one thread, and that is fast for four reasons. Data is in memory, so there is no disk wait. There are no locks or thread context switches on data. An event loop (epoll) lets one thread serve thousands of sockets. And the data structures are efficient, with most commands O(1) or O(log N). The bottleneck is usually the network, not the CPU.

It is not strictly single-threaded: background threads free memory lazily (UNLINK), close files and flush the AOF, and since Redis 6.0 optional I/O threads read and write sockets in parallel, while commands still execute on the main thread. Persistence uses a forked child process. The downside: one slow command (KEYS, a big DEL, a long Lua script) delays everyone, and one process uses one core for commands. To use more cores you run several instances, usually as a Cluster.

Remember: in memory, no locks, event loop, efficient structures. One slow command blocks all.

What does "Redis commands are atomic" really mean, and what does it not cover? Intermediate

One command runs to completion with nobody seeing a half-done state, so two clients doing INCR counter always give +2. But a sequence of commands is not atomic: if I GET, change the value in Java, then SET, another client can slip in between and one update is lost. For sequences I use a single command like INCRBY, a Lua script, or WATCH with MULTI/EXEC.

Also, atomic does not mean durable: a command can succeed in memory and still be lost if the server crashes before persistence or replication. And in a Cluster, atomicity across several keys only works if they live in the same slot.

# wrong: read-modify-write across the network
v = GET stock:42;  SET stock:42 (v-1)
# right: one atomic command
DECR stock:42
Watch out: "Redis is atomic so my code is safe" is the classic wrong claim. Only single commands and scripts are atomic.

Remember: one command is atomic, a GET-then-SET is not. Use INCR, Lua or WATCH.

What is pipelining, and how is it different from a transaction? Intermediate

Pipelining sends many commands without waiting for each reply, then reads all replies together. It saves network round trips, which usually cost far more than running the command. A transaction (MULTI/EXEC) is about isolation: queued commands run together with nobody in between. Pipelining is not atomic.

A round trip is often 0.2 to 1 ms inside a data center, while Redis runs a simple command in microseconds, so loading 10,000 keys one by one is mostly waiting. A pipeline can give ten times more throughput. Redis buffers the replies in memory, so send chunks of a few hundred to a few thousand commands. In a pipeline, other clients' commands can run between yours, and one failing command does not stop the rest. They combine: a transaction can be sent inside a pipeline. In a Cluster, a pipeline must be split per node. For many keys, MGET and MSET are single commands, but in a Cluster the keys must share a slot.

Pipeline p = jedis.pipelined();
for (String k : keys) p.get(k);
List<Object> replies = p.syncAndReturnAll();

Remember: pipeline = fewer round trips, not atomic. MULTI/EXEC = isolated, no rollback.

4. Data structures and their use cases

Name the main Redis data types and when you would use each. Basic

String for cached values, counters and locks. Hash for objects with fields. List for simple queues and recent-N feeds. Set for unique members and set math. Sorted set for leaderboards and time windows. Stream for a durable event log. Bitmap and HyperLogLog for compact flags and approximate unique counts. The rule: pick the type whose commands already do what you need atomically.

  • String (up to 512 MB): SET/GET, INCR, SET NX for locks.
  • Hash: read or update one field without loading the rest (HGET, HINCRBY).
  • List: push and pop at both ends in O(1); capped logs and simple queues.
  • Set: uniqueness, tags, "common friends" with SINTER.
  • Sorted set: members with a score, kept in order; ranks, top-N, sliding-window rate limits.
  • Bitmap: one bit per user id, so 10 million users take about 1.2 MB (daily active flags). HyperLogLog: approximate distinct count in at most about 12 KB with about 0.81 percent error; you can count and merge but not list members.
  • Geo: store coordinates, query by radius.

Remember: string cache/counter, hash object, list queue, set unique, zset ranking, stream log, HLL approximate count.

Store a user object: JSON string or hash? Intermediate

If I always read and write the whole object, I use a JSON string: one GET, one deserialize, and nesting is fine. If I need to read or update single fields, or keep a counter per object, I use a hash.

With a string, changing one field means read, change, write the whole value, which is not atomic. A hash keeps fields separate: HSET user:7 name Asha plan pro, then HGET for one field, or HINCRBY user:7 logins 1 atomically. A hash cannot hold nested objects directly, and fields cannot have their own expiry in older versions (per-field expiry arrived in Redis 7.4). Small hashes use a compact encoding (listpack), so many small hashes cost less memory than many separate string keys.

HSET user:7 name "Asha" plan "pro" logins 0
HINCRBY user:7 logins 1
HGET user:7 plan

Remember: whole object, one blob: string. Partial updates or counters: hash.

How does a sorted set work, and what are its complexities? Intermediate

A sorted set holds unique members, each with a numeric score, always ordered by score. Internally it is a skip list plus a hash table, so add, remove and rank lookups are O(log N), reading a range is O(log N + M) for M results, and getting one member's score is O(1). That is why it fits leaderboards with millions of players.

A skip list is layered linked lists: upper layers skip ahead, so search is logarithmic without the rebalancing of a tree. Small sorted sets use a compact listpack instead. Key commands: ZADD (add or update), ZINCRBY, ZRANGE (with REV, BYSCORE in 6.2 and later), ZREVRANK, ZREM, ZREMRANGEBYSCORE, ZCARD. Ties on score are ordered alphabetically by member.

Remember: skip list plus hash: O(log N) for add, remove and rank. Great for top-N.

5. Persistence, replication and Cluster

Explain RDB and AOF persistence and compare them. Intermediate

RDB is a point-in-time snapshot of the whole data set in one compact file. It restarts fast but you lose everything since the last snapshot. AOF logs every write command and replays it on restart; with the default everysec fsync you lose at most about one second. For a pure cache I may use neither, or RDB only so a restart is not cold. For data I care about I use AOF with everysec plus replicas.

RDB: triggered by rules like "after 3600 s if 1 key changed" or BGSAVE. Redis forks a child that writes the file while the parent keeps serving. AOF: appendfsync always is safest but slow, everysec is the default, no leaves it to the OS. The log grows, so Redis rewrites it into the shortest set of commands that rebuilds the data (Redis 7 uses a base file plus incremental files). If both are on, Redis loads the AOF at restart because it is more complete.

The fork has a cost: the child shares memory with the parent by copy-on-write, so under heavy writes memory can approach double during a save, and forking a very large instance can pause the main thread briefly. Keep memory headroom and take snapshots on a replica if you can.

Remember: RDB = fast restart, lose minutes. AOF everysec = lose about a second. Cache-only: maybe neither.

How does Redis replication work, and what are its limits? Intermediate

A replica connects to the primary, receives a full snapshot once, and then gets a continuous stream of every write command. It is asynchronous: the primary answers the client first and replicates after. So a replica can lag, and a write the client saw acknowledged can be lost if the primary dies before it reaches a replica. Replicas give read scaling and failover, not extra durability.

First connection: full sync (the primary forks, sends an RDB file, and buffers writes made meanwhile). After a short disconnect: partial resync (PSYNC) from the replication backlog, a circular buffer (1 MB by default); if the gap is bigger, a costly full sync happens again. Reading from replicas multiplies read capacity but returns possibly stale data, so use the primary for "write then read the same key". WAIT numreplicas timeout blocks until replicas acknowledge, which narrows the loss window but is not a guarantee. Replicas are read-only by default.

Remember: async replication: fast, but a failover can lose the last writes. Replica reads can be stale.

What does Sentinel do, and when would you use it instead of Cluster? Intermediate

Sentinel is a set of separate processes (at least three) that watch a primary and its replicas, detect failure by majority vote, promote a replica, and tell clients the new primary address. It gives high availability but no sharding. I use it when all data fits on one machine; I move to Cluster only when one node cannot hold the memory or handle the write rate.

Failover flow: a Sentinel that cannot reach the primary marks it "subjectively down"; when a quorum agrees it is "objectively down"; the Sentinels elect a leader, which picks the best replica (priority, then replication offset) and promotes it. Three Sentinels because a majority is needed: with two, losing one leaves no majority. Because replication is async, a failover can lose the latest writes. A network partition can also leave an old primary accepting writes that are discarded later (split brain); min-replicas-to-write limits this.

Remember: Sentinel = failover without sharding (3 or more, majority). Cluster = sharding when one node is not enough.

How does Redis Cluster shard data? Explain hash slots. Intermediate

The key space is split into 16384 hash slots. The slot of a key is CRC16(key) mod 16384, and each master node owns a range of slots. A cluster-aware client keeps the slot map and sends each command straight to the right node. Adding a node means moving some slots, not rehashing everything. The big rule for developers is that a multi-key command only works if all its keys are in the same slot.

If the client's map is old, the node replies MOVED slot host:port (update the map) or ASK (temporary, during migration). You force related keys into one slot with hash tags: only the text inside {} is hashed, so {user:7}:profile and {user:7}:cart land together. Otherwise MGET, transactions and Lua scripts on several keys fail with CROSSSLOT. Each master normally has a replica; if a master fails, its replica is promoted after a majority of masters agree. Replication is still async, so Cluster can lose acknowledged writes too. Cluster supports only database 0. Choosing shard counts and resharding are operator topics.

Remember: 16384 slots, CRC16 mod 16384, one master per slot. Multi-key commands need the same slot: use {hash tags}.

6. Eviction and memory

What happens when Redis reaches maxmemory? Explain the eviction policies. Intermediate

It depends on maxmemory-policy. The default noeviction makes writes fail with an OOM error while reads still work, which is right for a primary store and wrong for a cache. For a cache I set allkeys-lru, or allkeys-lfu when a few keys are consistently popular. If the instance mixes must-keep data and cache data, I use a volatile policy and give only cache keys a TTL, or better, use separate instances.

  • allkeys-lru / allkeys-lfu: evict the least recently, or least frequently, used key from all keys.
  • volatile-lru / volatile-lfu / volatile-ttl: consider only keys that have a TTL (volatile-ttl removes those expiring soonest). If no key has a TTL, writes fail like noeviction, which surprises people.
  • random variants pick at random.

Redis LRU is approximate: it samples a few random keys (maxmemory-samples, default 5) and evicts the oldest of them, which avoids the memory and time cost of a full linked list. LFU keeps a small logarithmic counter that decays over time, so a one-time scan cannot flush hot keys. If an interviewer asks you to code an LRU cache: a hash map plus a doubly linked list gives O(1) get and put (in Java, LinkedHashMap with access order).

CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lfu
INFO stats      # evicted_keys, expired_keys, keyspace_hits, keyspace_misses

Remember: default noeviction = writes fail. Cache: allkeys-lru or allkeys-lfu. Redis LRU samples, it is not exact.

Memory keeps growing even though you set TTLs. What do you check? Intermediate

First INFO keyspace: the line keys=5000000,expires=1200000 shows how many keys have no TTL. Most often some code path writes keys without a TTL, or the key space has unbounded cardinality, or a collection only grows. Then I find the offending prefix with SCAN and TTL, and fix the code, not just the symptom.

Typical causes: a plain SET after SETEX removes the TTL; INCR on a new key creates it without a TTL; one key per request id or per user per minute; a list, set or stream with no trimming (LTRIM, XTRIM); big keys (--bigkeys); and fragmentation (mem_fragmentation_ratio well above 1.5). Expired keys nobody reads can also linger until the sampler finds them. As a guard, set maxmemory with an eviction policy so growth cannot take the host down.

Remember: compare keys with expires, find the prefix with no TTL, cap collections, set maxmemory.

7. Atomicity, Lua scripts and messaging

How do Redis transactions work, and how are they different from SQL transactions? Intermediate

After MULTI the commands are queued, and EXEC runs them in order with no other client's command in between. So you get isolation, but no rollback: if one command fails at run time, the others still run. For optimistic locking you add WATCH key: if another client changes a watched key before EXEC, EXEC returns nil, nothing runs, and your code retries.

A syntax error found while queuing discards the whole transaction at EXEC, but a runtime error (INCR on a non-number) does not undo the rest. Because commands are only queued, you cannot read a value inside the transaction and use it in a later command of the same transaction. For that logic you need WATCH in the app, or better, a Lua script.

WATCH balance:7
v = GET balance:7           # app reads
MULTI
SET balance:7 (v - 50)
EXEC                        # nil if someone else changed balance:7

Remember: MULTI/EXEC = isolated batch, no rollback. WATCH adds optimistic locking.

When and why would you use a Lua script in Redis? Intermediate

When I need a check-then-act sequence to be atomic, such as "release the lock only if I own it", "decrement stock only if above zero" or a token-bucket rate limiter. A Lua script runs inside Redis as one unit, so nothing else runs meanwhile, and it costs one round trip instead of several.

Rules: pass every key the script touches in KEYS (needed for Cluster routing) and other values in ARGV. Keep it short, since a slow script blocks all clients (after the busy-script limit, about 5 seconds, others get an error). Use EVALSHA with the script hash to avoid resending the text. Redis 7 added Functions, scripts stored on the server as a library.

-- release lock only if I still own it
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end

Remember: Lua = atomic read-decide-write in one round trip. Keep it short and pass keys in KEYS.

How does Redis pub/sub work, and what are its limits? Intermediate

Subscribers run SUBSCRIBE channel, a publisher runs PUBLISH channel message, and Redis pushes the message to whoever is subscribed at that moment. Nothing is stored: a subscriber that is offline, slow or not yet subscribed never sees it, and there is no acknowledgement or replay. So it suits ephemeral notifications and cache-invalidation broadcasts, not jobs that must be processed.

A slow subscriber's output buffer grows, and Redis disconnects it when it passes client-output-buffer-limit pubsub. In a Cluster, a published message is broadcast to every node; Redis 7 added sharded pub/sub (SPUBLISH) to confine it to a shard.

Remember: pub/sub = fire and forget. Miss it and it is gone.

What are Redis Streams, and when would you use them instead of pub/sub or a list queue? Senior

A stream is an append-only log stored in a key. Consumer groups let several workers share it: each entry goes to one worker and stays pending until that worker acknowledges it, so I get at-least-once delivery, replay, and recovery from crashed workers. A plain list queue forgets a job once popped, and pub/sub forgets everything, so for anything important I use a stream, or a real broker like Kafka or SQS.

XADD appends with an auto id (millisecond time plus sequence). Workers call XREADGROUP; the entry sits in the group's pending list until XACK. If a worker dies, another claims the entry with XAUTOCLAIM (6.2) after an idle time. Entries stay until trimmed (XTRIM), so late readers can replay. Since a claim can redeliver, handlers must be idempotent. Versus Kafka: simpler to run and fine for modest volume, but one stream lives on one shard and is bounded by memory. A list can work for simple jobs: LPUSH plus blocking BRPOP, or LMOVE to a processing list for safety, but you build acks and retries yourself.

XADD orders * orderId 991 amount 40
XGROUP CREATE orders billing $ MKSTREAM
XREADGROUP GROUP billing w1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders billing 1731800000000-0

Remember: pub/sub forgets, list loses jobs on crash, stream keeps and acknowledges. Make handlers idempotent.

8. Distributed locks

How do you implement a distributed lock with a single Redis? Intermediate

Acquire with one atomic command: SET lock:order:42 <random-token> NX PX 30000. NX means only one client can create it, and PX gives a 30 second lease so the lock vanishes if the holder crashes. To release, delete the key only if it still holds my token, using a Lua script so the compare and delete are atomic.

The token matters. Without it: my work outlives the lease, the lock expires, another client takes it, and then I finish and delete their lock. The old pattern of SETNX then EXPIRE is unsafe: a crash between the two leaves a lock that never expires. If I fail to acquire, I retry with a short sleep, jitter and a maximum wait. Practical pitfalls: the lease must exceed the p99 work time (or a library watchdog, like Redisson's, renews it); plain locks are not reentrant; use fine-grained keys (per order, not global); and assume that a failover or a long pause can still produce two holders, so make the protected action idempotent.

SET lock:order:42 7f3a9c NX PX 30000
-- release (Lua): only if token matches
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1]) else return 0 end

Remember: SET NX PX with a random token, release with a Lua compare-and-delete. A lease can expire, so make the work idempotent.

What is Redlock, and what is the Kleppmann versus Antirez debate? Senior

A single Redis lock can be lost on failover, because the replica may not yet have the lock key. Redlock takes the lock on five independent Redis masters and counts it as held if a majority (3 of 5) grants it within the lease time. Kleppmann argued it is still unsafe for correctness, because it relies on timing assumptions (no long pauses, no clock jumps) and gives no fencing token. My answer: Redis locks are fine for efficiency (avoiding duplicate work); for correctness add a fencing token or a database constraint.

Kleppmann's scenario: a client gets the lock, pauses (GC, page fault), the lease expires, another client takes the lock, and the first resumes believing it still holds it. Clock jumps on a node can also expire locks early. He advised: if the lock is for efficiency, a single Redis lock is enough; if it is for correctness, you need a fencing token (an ever-increasing number checked by the resource itself), from a system such as ZooKeeper or etcd, or simply use the database's own guard: unique constraints, UPDATE ... WHERE version = ?, or transactions. Antirez replied that the timing assumptions are acceptable in practice; but Redlock's random token is not monotonic, so it cannot serve as a fencing token. Redisson's plain RLock is a single-node lock with a watchdog (default lease 30 s), not Redlock.

Remember: lock for efficiency: Redis is fine. Lock for correctness: fencing token or a database constraint.

9. Patterns: rate limiter, leaderboard, session store

Design a rate limiter with Redis. Compare the algorithms. Senior

I would use a token bucket for an API: it allows short bursts and keeps a steady average rate. The simplest option is a fixed-window counter (INCR a per-minute key, expire it, reject above the limit), but it allows double the limit across a window boundary. Whatever the algorithm, the check-and-update must be atomic, so I run it in a Lua script.

  • Fixed window: key rate:user7:10:15, INCR, set expiry on the first hit. Cheap, but 100 requests at 10:15:59 plus 100 at 10:16:00 pass a limit of 100 per minute.
  • Sliding window log: a sorted set of request times; remove old entries (ZREMRANGEBYSCORE), count with ZCARD, add the new one. Exact, but memory per request.
  • Sliding window counter: blend the current and previous window counts with a weight. Two small counters, a good compromise.
  • Token bucket: store token count and last refill time; each request refills by elapsed time and takes one token.

Key by user, API key or IP; return 429 with Retry-After; decide whether to fail open or closed if Redis is down (most APIs fail open). Do INCR and EXPIRE together: if the app crashes between two separate calls, the counter never expires and the user stays blocked forever.

-- fixed window, atomic via Lua: KEYS[1]=counter  ARGV[1]=limit ARGV[2]=window seconds
local c = redis.call("INCR", KEYS[1])
if c == 1 then redis.call("EXPIRE", KEYS[1], ARGV[2]) end
if c > tonumber(ARGV[1]) then return 0 end
return 1

Remember: fixed window is simple but leaks at the edge. Token bucket allows bursts. Make it atomic with Lua.

Design a real-time leaderboard with Redis. Intermediate

One sorted set per board: the player id is the member and the score is the score. ZINCRBY adds points atomically, ZRANGE ... REV WITHSCORES gives the top N, and ZREVRANK gives any player's rank in O(log N), even among millions. The database remains the source of truth and the set can be rebuilt from it.

Daily or weekly boards use one key per period (lb:2026-11-17) with a TTL, and ZUNIONSTORE combines them. To break ties by who reached the score first, encode time into the fractional part of the score. Neighbours of a player: get the rank, then read a range around it. Limits: one sorted set lives on one node; for hundreds of millions of members, shard by region or score range and merge the top lists. Memory is roughly 50 to 100 bytes per member.

ZINCRBY lb:global 20 player:7
ZRANGE lb:global 0 9 REV WITHSCORES      # top 10 (6.2+; older: ZREVRANGE)
ZREVRANK lb:global player:7              # my rank, 0 is first

Remember: sorted set: ZINCRBY to score, ZRANGE REV for top N, ZREVRANK for my rank.

How would you use Redis as a session store, and what should you watch for? Intermediate

Web servers should be stateless so any instance can serve any request, so the session data lives in Redis and the browser holds only a random session id in a cookie (HttpOnly, Secure). Redis stores session:<id> with a TTL equal to the idle timeout, refreshed on each request. In Spring, Spring Session with Redis does this with configuration.

Watch for: Redis availability becomes login availability, so use replication with failover and decide what happens on loss (users log in again). Keep sessions small. Add an absolute maximum lifetime besides the idle one. Use TLS and auth. Be careful with serialization: changing a session class between deploys can make old sessions unreadable. Alternative: signed stateless tokens (JWT) avoid the lookup but make early revocation harder.

Remember: cookie holds only the id; Redis holds the data with a sliding TTL. Plan for Redis loss.

10. Spring Cache and resilience

How does Spring's cache abstraction work with Redis? Intermediate

I enable it with @EnableCaching and annotate methods. @Cacheable runs the method only on a miss and stores the result, @CachePut always runs and updates the cache, and @CacheEvict removes an entry. Spring wraps the bean in a proxy that consults a CacheManager; with Redis that is RedisCacheManager. Two defaults I always change: entries have no TTL, and values use JDK serialization.

The key defaults to the method arguments; set it with SpEL, key = "#id". Use unless = "#result == null" or condition to skip caching. Redis keys are prefixed with the cache name, like users::42. Set entryTtl and a JSON serializer in RedisCacheConfiguration, since JDK serialization is bulky and breaks when a class changes.

@Cacheable(cacheNames = "users", key = "#id", unless = "#result == null")
public User find(long id) { return repo.findById(id).orElse(null); }

@CacheEvict(cacheNames = "users", key = "#u.id")
public void update(User u) { repo.save(u); }

@Bean RedisCacheManager cacheManager(RedisConnectionFactory f) {
  var cfg = RedisCacheConfiguration.defaultCacheConfig()
      .entryTtl(Duration.ofMinutes(10))
      .serializeValuesWith(SerializationPair.fromSerializer(
          new GenericJackson2JsonRedisSerializer()));
  return RedisCacheManager.builder(f).cacheDefaults(cfg).build();
}

Remember: Cacheable / CachePut / CacheEvict through a proxy. Set a TTL and a JSON serializer yourself.

What are the common pitfalls with @Cacheable? Senior

The biggest one is self-invocation: calling a @Cacheable method from another method of the same class bypasses the proxy, so nothing is cached. Others: no TTL by default, stampede on concurrent misses, cached nulls, serialization breaking after a deploy, key collisions, and eviction before the transaction commits.

  • Self-invocation / private methods: the proxy is skipped. Move the method to another bean; it must be public.
  • No TTL: stale data lives forever. Configure entryTtl.
  • Stampede: concurrent misses all run the method. sync = true helps per JVM only.
  • Null caching: nulls can be cached, so a missing id stays missing. Decide on purpose with unless or disableCachingNullValues().
  • Serialization: changing a class between deploys can make old entries unreadable; use tolerant JSON or version the cache name.
  • Key collisions: same cache name and arguments in two methods share entries; use explicit keys.
  • Transactions: an eviction can run before the database commit, so a concurrent reader refills the old value; evict after commit (TransactionAwareCacheManagerProxy).
  • Redis errors failing requests: add a CacheErrorHandler so an outage becomes a miss, not a 500.

Remember: proxy means no self-calls. No TTL by default. Treat cache errors as misses.

What should your service do when Redis is down or slow? Senior

If Redis is a cache, the service must keep working, slower, but protected. I use short client timeouts (tens to a few hundred milliseconds), a circuit breaker that stops calling Redis for a few seconds after repeated failures, and a limit on the fallback path to the database, because a Redis outage means a 100 percent miss rate that can crush the database.

Catch cache exceptions so they never fail the request, and return degraded responses if needed (stale data from a local L1, hide non-essential features). For other uses choose fail-open or fail-closed on purpose: a rate limiter usually fails open, a payment lock usually fails closed. Sessions: decide between logging users out and a read-only mode. Also set client pool size and timeouts: a missing timeout is how one slow Redis hangs every application thread. Test it: block Redis in staging and watch the database.

Remember: short timeout, circuit breaker, protected fallback, deliberate fail-open or fail-closed.

11. Redis versus other options

Redis or Memcached: how do you choose? Basic

I choose Redis by default, because one tool gives me data structures, atomic operations, TTLs with eviction policies, persistence, replication and failover. I would pick Memcached only for a very simple, large, multi-core blob cache where I want the simplest possible operations.

Memcached stores only string blobs, is multi-threaded (uses many cores on one machine), has no persistence or built-in replication, and shards on the client side by consistent hashing. Redis commands run on one thread, but you can run several instances or a Cluster. If you need counters, sets, sorted sets, locks, queues or rate limiting, Redis is the answer.

AspectRedisMemcached
Data typesStrings, hashes, lists, sets, sorted sets, streamsStrings only
ThreadingOne thread for commands (I/O threads since 6.0)Multi-threaded
PersistenceRDB and AOFNone
Replication and failoverBuilt inNot in core
ShardingCluster (hash slots)Client-side hashing

Remember: Memcached = simple multi-threaded blob cache. Redis = data structures plus HA plus persistence.

Can Redis replace your database? When is it a primary store? Senior

For rebuildable or short-lived data, yes: sessions, rate-limit counters, leaderboards, presence, feature flags. For money, orders and accounts, no: I keep a real database as the truth and Redis in front of it. The line: if I can rebuild it, Redis may be the primary; if losing a second of it costs money, it should not be.

Why not for everything: the data set must fit in RAM, which is costly; durability is weaker (AOF everysec plus async replication can lose the last second of writes); there are no joins or rich queries, and secondary indexes need modules or manual upkeep; transactions have no rollback; and Cluster restricts multi-key operations.

Remember: Redis as primary only for data you can rebuild or can afford to lose a little of.

12. Real-life scenarios

Scenario: after a release, the cache hit rate falls from 95% to 60% and database CPU climbs. What do you do? Senior

The load did not change, so the release changed the cache keys or TTLs. I compare hits and misses over time, diff the release for anything touching keys, then sample live keys to see their shape. Then I fix or roll back the key change.

Situation: the release is the suspect. Check first: keyspace_hits and keyspace_misses in INFO stats to see when the fall began; evicted_keys (memory pressure) and expired_keys (TTL change). Look for: a changed key format or version prefix (a new prefix is all-miss at first, then recovers), a request-specific part like a timestamp or request id in the key (every key unique, cache full of one-use entries), a shorter TTL, a changed serializer, or a code path that bypasses the cache. Use SCAN to look at real keys. Fix: correct the key, or roll back; if memory is full and evicting, find the new big key family. Prevent: a hit-rate alert per cache name, key unit tests, a canary that watches hit rate, and a warm-up when the key format must change.

Remember: a hit-rate drop right after a deploy usually means the key changed. Look at live keys.

Scenario: Redis hits maxmemory and the app starts throwing OOM errors on writes. Senior

The policy is noeviction (the default), or a volatile policy with no keys that have a TTL. For a cache I switch to allkeys-lru or allkeys-lfu right away, then find which key family grew and fix the root cause.

Situation: OOM command not allowed when used memory > 'maxmemory'. Check first: INFO memory, INFO keyspace (keys versus keys with expires), CONFIG GET maxmemory-policy, --bigkeys. Relief: change the policy if it is a cache; raise maxmemory if the host has room; or delete a known junk prefix with SCAN and UNLINK (never KEYS). Cause: keys without a TTL, a growing list or stream, or unbounded key cardinality. Prevent: a TTL on every cache key (review rule), cap collections, alert at 80 percent memory, and keep must-keep data in a separate instance from cache data.

Remember: OOM on write = noeviction. Cache: allkeys-lru. Then hunt the key family with no TTL.

Scenario: p99 latency of every service using Redis jumps to 800 ms every few minutes. Senior

A regular pattern means something scheduled is blocking the single Redis thread: a cron job running an O(N) command, a big delete, a snapshot fork, or a mass expiry. I start with the slow log and line it up with the spike times.

Check first: SLOWLOG GET 20 (default threshold 10 ms, execution time only), then INFO commandstats. Who runs at that time? A job doing KEYS, SMEMBERS or HGETALL on a big key, or a big DEL. Then persistence: latest_fork_usec and save times, AOF with always or a slow disk. Then expiry waves (many keys with the same TTL), swapping, and a too-small client pool. Fix by cause: replace the heavy command with SCAN or chunks, use UNLINK, add TTL jitter, snapshot on a replica, keep memory headroom. Prevent: a slow-log alert and a review rule that batch jobs use SCAN.

Remember: periodic spike = something scheduled blocks the one thread. Slow log first.

Scenario: Redis failed over to a replica and users lost their last few seconds of data. Is that a bug? Senior

No, it is the design. Replication is asynchronous: the primary acknowledged the writes and died before sending them to the replica, so the promoted replica never had them. I either accept it for cache and session data, or shrink the window, or keep the truth in a durable database.

Check: replication offsets before the failure (INFO replication) and lag metrics; whether a partition let an old primary accept writes that were later discarded. Options: (1) accept it for a cache or session. (2) min-replicas-to-write 1 with min-replicas-max-lag 10 makes a primary refuse writes when it has no healthy replica, which limits what a cut-off primary can accept. (3) WAIT 1 100 after critical writes narrows the gap, but is not a guarantee. (4) Use Redis as a derived copy of a durable database. (5) For queues that must not lose jobs, use Kafka or the database. Prevent: write down the data loss you accept per use case, and test failover in staging.

Remember: async replication can lose the last writes by design. Decide the acceptable loss per use case.

Scenario: during a flash sale one Redis Cluster node is at 100% CPU while the other nodes are idle. Senior

That is a hot key: one key, one slot, one node. I find the key, then take the traffic off it with a short local cache in the app, key copies or replica reads. More shards will not help.

Check first: per-node ops per second and network out, then find the key with redis-cli --hotkeys (needs an LFU policy), a short MONITOR sample in a low-risk window (heavy), or client counters. Check value size too: a big value on a hot key saturates the network. Fix: a 1 to 5 second local cache for that key removes most traffic; or copy it into N variants (sale:42:0 to sale:42:7), read a random one and write all on change; or read from replicas. For a hot counter such as stock or likes, split it into sub-counters. Prevent: load-test the sale path, pre-warm and replicate known hot keys, put a CDN or page cache in front of read-only pages, and alert on hot keys.

Remember: one node pinned = hot key. Add L1 cache or key copies, not shards.

Scenario: a user updates their profile but keeps seeing the old data for several minutes. Senior

The database has the new data, so some cache layer still serves the old copy. I check the layers one by one: browser or CDN, per-instance local cache, Redis, and the database read replica. The most common root cause is a write path that deletes a different key than the read path uses.

Check: response headers (Cache-Control, Age); if refreshing shows old and new data alternately, it is a per-instance L1 cache; GET and TTL the Redis key; replica lag. Then the write path: is the key built differently on write and read (tenant or language missing)? Does the delete run before the transaction commits, so a concurrent read refilled the old value? Did the delete fail and the exception get swallowed? Or the slow-reader race? Fix: correct the key, evict after commit, retry failed invalidations, bypass the cache for that user for a few seconds after a write. Prevent: one helper that builds keys for both read and write, an integration test through the real cache, and the TTL as safety net.

Remember: walk the layers one by one. Check that read and write build the same key.

Scenario: a scheduled job guarded by a Redis lock ran twice at the same time and charged some customers twice. Senior

Two instances both believed they held the lock: the lease expired during a long run, or the release deleted someone else's lock, or a failover lost the lock key. The real fix is to make the charge idempotent with a unique constraint, because a Redis lock only gives efficiency, not correctness.

Check: job logs with lock acquire and release times against the lease length, Redis failover events at that time, and the release code (token check?). Fix: token plus Lua release; a lease longer than the worst-case run, with a renewal watchdog; and above all an idempotency key per customer per billing period with a unique constraint in the database, so a second run does nothing. Prevent: a fencing token or version check at the resource, an alert on overlapping runs, and a test that forces a pause (the Kleppmann argument).

Remember: the lock is for efficiency. Make the action idempotent, with a database constraint as the final guard.

Scenario: Redis becomes unreachable for ten minutes and the whole site goes down, even though Redis is "just a cache". Senior

The site depended on Redis more than intended: no or long timeouts filled the thread pool, or cache exceptions failed the requests, or the fallback overloaded the database. I restore Redis, then add short timeouts, a circuit breaker, error handling that treats failures as misses, and a protected fallback.

What usually happened: threads stuck waiting for Redis until the pool was full, so even requests that did not need Redis queued. Fix: connect and command timeouts of 50 to 200 ms, a circuit breaker, a CacheErrorHandler (cache errors become misses), a bulkhead so cache calls use a limited pool, a rate-limited fallback to the database, and a degraded mode (serve stale from L1, hide non-essential features). Prevent: a game day where Redis is blocked in staging, and a clear list of which features fail open and which fail closed.

Remember: a cache outage must become slower, not down. Timeout, breaker, protected fallback.

Scenario: a rate limiter built on INCR sometimes leaves counters that never expire, and users stay blocked forever. Senior

The code does INCR and then a separate EXPIRE. If the process crashes or the second call fails in between, the counter has no TTL, grows to the limit and never resets. I fix it by making the two steps atomic with a Lua script, and clean up the stuck keys.

Check: TTL key returns -1 for blocked users; SCAN with a TTL check finds the rest. Immediate: delete or set a TTL on those keys. Fix: a Lua script doing INCR plus EXPIRE together, or SET key 0 EX 60 NX first and then INCR (which keeps the TTL). A second guard: if TTL is -1 after the increment, set it. Prevent: a rule that any check-then-act logic in Redis goes into a script, and an audit that counts keys with no TTL in rate-limit prefixes.

Remember: two calls are not atomic. INCR plus EXPIRE belong in one Lua script.
