Mental model: the 8 ideas everything hangs on

One line: microservices trade the simplicity of one process for independent deployment and scaling. You pay with the network: every call can be slow, fail, or arrive twice, and every piece of data has exactly one owner.
  1. Boundaries come from the business, not from technology. A service should own one business capability (a bounded context). If two services must always change and deploy together, the boundary is wrong.
  2. The network is not a function call. Calls can be slow, lost, duplicated or answered after you gave up. Design every call with a timeout, a retry policy and a plan for failure.
  3. Each service owns its data. Nobody reads another service's tables. You ask through an API or an event. That is what keeps services independent.
  4. No distributed ACID, so think in sagas. A business operation across services becomes a series of local transactions plus compensating actions. Data is eventually consistent.
  5. At-least-once is the real world. Messages and retries produce duplicates, so consumers and write APIs must be idempotent.
  6. Failure must be contained. Timeouts, circuit breakers, bulkheads and load shedding stop one slow service from taking down the whole system.
  7. You cannot debug what you cannot see. Correlation ids, structured logs, metrics and distributed traces are not optional extras.
  8. Contracts are promises. Once a client depends on your API, you may only add, never remove or change meaning. Evolve in small, backward compatible steps.

1. Monolith, service boundaries and domain design

What is the difference between a monolith and microservices, and what does each cost? Basic

What the interviewer is testing: whether you see microservices as a trade-off and not as a goal.

A monolith is one deployable unit. All the code runs in one process and usually shares one database. Calls between modules are plain function calls, so they are fast and can share one transaction. Microservices split the system into many small, separately deployed services, each owning one business capability and its own data. They talk over the network.

The monolith is simpler to build, test, debug and deploy. The cost is that everything is deployed together, one bad module can crash everything, and a big team steps on each other. Microservices give independent deployment, independent scaling, technology freedom and clearer team ownership. The cost is large: network failures, eventual consistency, many pipelines, harder debugging and a need for strong tooling. The honest summary is that microservices solve an organisation and scaling problem, and they create a distributed systems problem.

Likely follow-ups
  • What is the main benefit in one sentence? Teams can ship and scale their part without waiting for others.
  • What is the main cost? Everything that used to be a method call is now a network call that can fail.
When should you NOT use microservices? Senior

What the interviewer is testing: maturity. Weak candidates say microservices are always better.

I would not start with microservices when the team is small (say under 10 to 15 engineers), when the product is new and the domain is still changing, or when the organisation has no automated deployment, monitoring and on-call practice. In a young product we do not yet know where the real boundaries are. If we draw them wrong, every change crosses several services and we get all the cost with none of the benefit.

It is also a bad idea when the real problem is slow code or a slow database, because splitting does not fix that. A simple rule I use: start with a well-structured modular monolith, measure, and extract a service only when there is a clear reason such as a different scaling profile, a separate team that needs its own release cycle, or a strict isolation need (security, compliance). Many well-known companies went back from too many services to fewer, larger ones for this reason.

Likely follow-ups
  • What signals say it is time to split? Teams blocked by shared deploys, one module needing very different scaling, long build and test times, or a part with different security needs.
Common mistakes: starting with 30 services for a team of 5; splitting by technical layer (UI service, DB service) instead of by business capability.
What is a modular monolith and why is it often the best starting point? Intermediate

What the interviewer is testing: do you know the middle path and how to prepare for later extraction.

A modular monolith is one deployable application whose code is divided into strict modules. Each module has a public interface and hides its internals, including its own tables. Other modules may only call that interface, never reach into its database tables. It is enforced by package visibility, build rules or architecture tests.

The benefit is that you get clear business boundaries and simple operations at the same time. A call is still a method call, a transaction can still span modules while the product is young, and refactoring boundaries is cheap. If a module later needs to become a service, you already have a clean interface and separate data, so extraction is mostly moving code behind a network call. It is the best way to learn where the true boundaries are before paying the microservice tax.

Likely follow-ups
  • How do you stop modules from leaking into each other? Architecture tests (for example ArchUnit in Java), separate schemas per module, and code review rules.
How big should a microservice be? Intermediate

What the interviewer is testing: whether you size by purpose and ownership, not by lines of code.

There is no correct line count. A good service is sized by a business capability and by team ownership. A common guide is that one small team (a "two pizza" team) can own it fully, understand it in their heads, rewrite it in a few weeks if needed, and deploy it alone. Signs that a service is too big: many unrelated reasons to change, several teams editing it, long builds. Signs that it is too small (a "nano service"): a single change needs edits in three services, services always deploy together, or a service only wraps one table with CRUD.

A useful test is cohesion and coupling. Things that change together should live together. Things that change for different reasons should be apart. If two services must be released in a fixed order, merge them or fix the boundary.

Likely follow-ups
  • Is one service per table a good idea? Usually no. It copies the database design and makes every use case chatty.
What is a bounded context, and how does it help find service boundaries? Intermediate

What the interviewer is testing: Domain-Driven Design basics applied to splitting a system.

In Domain-Driven Design (DDD), a bounded context is a part of the business where every word has one clear meaning and one model. The word "Customer" means different things in different places. In Sales it is a lead with a contact person. In Billing it is a legal entity with a tax id and a payment method. In Shipping it is just a delivery address. Trying to build one big Customer class for everyone creates a tangled model that everybody fears to touch.

So you let each context have its own model and its own data, and you translate at the edges. A bounded context is the best first guess for a service boundary, because it already has its own language, its own rules and usually its own team. To find contexts, I talk to domain experts, run an event storming workshop (put business events on a wall and group them), and watch where the same word changes meaning.

Likely follow-ups
  • Is one context always one service? Not always. A context may contain several services, but a service should not span two contexts.
  • What is a context map? A picture of how contexts relate, such as upstream/downstream, shared kernel, or anti-corruption layer.
What is an aggregate in DDD and why does it matter for microservices? Senior

What the interviewer is testing: can you connect DDD to transaction boundaries and data consistency.

An aggregate is a cluster of objects that must be consistent together, with one root entity that is the only way in. For example an Order (root) with its order lines. Rules like "total equals the sum of lines" are checked inside one transaction on that aggregate. Other aggregates are referenced only by id, never by direct object link.

This matters because an aggregate is the natural unit of a transaction and of ownership. A single aggregate always lives inside one service and one database transaction. Anything that spans aggregates, and certainly anything that spans services, is eventually consistent and handled with events or sagas. Designing small aggregates keeps transactions short and lowers lock contention. If you find you need a transaction over two services, it is a hint that the boundary or the aggregate is drawn badly.

Likely follow-ups
  • How do aggregates talk to each other? By id and by domain events.
How do you migrate a monolith to microservices safely? Senior

What the interviewer is testing: incremental migration, not a big-bang rewrite.

I use the strangler fig pattern. I put a routing layer (a gateway or proxy) in front of the monolith. Then I pick one capability at a time, build it as a new service, and move traffic for it from the monolith to the service. The monolith slowly shrinks until it can be retired. Each step is small and reversible, because the router can send traffic back.

The hard part is data. First I make the module boundary clean inside the monolith. Then I give the new service its own database, copy the data across (with dual writes or change data capture while both run), and switch the source of truth. I start with something loosely coupled and low risk, not the core of the system. I also invest early in the platform: CI/CD, logging, tracing and monitoring, otherwise the first services will hurt. A big-bang rewrite almost always runs late and loses features.

Likely follow-ups
  • What do you extract first? A loosely coupled, low risk capability with clear data, such as notifications or a catalog read model.
  • How do you keep data in sync during migration? Change data capture or dual writes with reconciliation, then switch the owner.
What is a distributed monolith and how do you recognise one? Senior

What the interviewer is testing: the most common failure of microservice projects.

A distributed monolith has many services, but they are so tightly coupled that they behave like one application that is harder to run. You get the cost of the network with none of the freedom. Typical symptoms: you must deploy several services together in a fixed order; one change touches many repositories; services share a database or share a big common library with business objects; a long chain of synchronous calls means one failure breaks everything; a staging environment is needed to test anything because services cannot be tested alone.

The fixes are about the boundaries and the data. Redraw the boundaries around business capabilities. Give each service its own data. Replace chatty sync calls with events or with a data copy the service needs. Make API changes backward compatible so deploys are independent, and test with consumer-driven contracts. Sometimes the right fix is to merge services back together.

Likely follow-ups
  • One quick test? Can you deploy any one service to production on its own, on a Tuesday afternoon, without telling anyone? If not, they are coupled.
What is Conway's law and how does it affect microservices? Intermediate

What the interviewer is testing: link between team structure and architecture.

Conway's law says a system's design will copy the communication structure of the organisation that builds it. If you have a frontend team, a backend team and a database team, you will get a three-layer system, and every feature needs all three teams. For microservices this means the team layout and the service layout should match: a small cross-functional team owns a service (or a few related services) from code to production.

The "inverse Conway manoeuvre" is to shape the teams first, so that the architecture you want appears naturally. If two services are owned by one team, they tend to merge. If one service is owned by four teams, it becomes slow and political. When I review a design I always ask "who owns this and who gets paged for it?".

Is it fine to share code between services through a common library? Intermediate

What the interviewer is testing: knowing where code sharing creates hidden coupling.

It depends on what is shared. Sharing technical, stable, non-business code is fine: logging setup, a tracing helper, an HTTP client with retry and timeout defaults, security filters. Sharing business models is dangerous. If an Order class lives in a shared jar, then changing it forces every service to upgrade and redeploy, and you have rebuilt a monolith with extra steps.

For the contract between services, I prefer to generate client code from the API definition (OpenAPI or protobuf) instead of sharing a hand-written model. Each service then owns its own internal model. If you do use a shared library, version it with semantic versioning, keep it small, and never make the services depend on getting the latest version at the same time. A little duplication between services is usually cheaper than coupling.

Likely follow-ups
  • What about a sidecar or mesh instead of libraries? That moves cross-cutting code (mTLS, retries) out of the app, so it is language independent, at the cost of another moving part.

2. Communication, gateway, discovery and configuration

Synchronous versus asynchronous communication between services: how do you choose? Intermediate

What the interviewer is testing: coupling, availability and latency trade-offs.

Synchronous means the caller sends a request (REST or gRPC) and waits for the answer. It is simple to understand and gives an immediate result, which is right when the user needs the answer now, like "get the price of this product". The cost is temporal coupling: the callee must be up at that moment. If a request passes through four services in a chain, the availability is multiplied: four services at 99.9 percent give about 99.6 percent, and the latencies add up.

Asynchronous means the sender puts a message or event on a broker (Kafka, RabbitMQ, SQS) and goes on. The receiver processes it when it can. This decouples in time, absorbs spikes, and lets you add new consumers without changing the sender. The cost: the result is not immediate, the flow is harder to follow, and you must handle duplicates, ordering and eventual consistency. My rule: use sync for queries and for steps where the user must wait for the answer; use async for commands and facts that other services react to, and for anything that can be done a bit later.

Likely follow-ups
  • Can you make a sync API from async? Yes, request and reply with a correlation id, or return 202 Accepted and let the client poll or get a callback.
What is the difference between a command, an event and a query? Intermediate

What the interviewer is testing: messaging vocabulary and how it shapes coupling.

A command is a request to do something, such as "ChargeCard". It is addressed to one receiver, it can be rejected, and the sender cares about the outcome. An event is a fact that already happened, such as "OrderPlaced". It is published to anyone who is interested, and the publisher does not know or care who listens. A query asks for data and changes nothing.

The difference matters for coupling. With commands the sender knows the receiver, so it is more coupled. With events the publisher is unaware of consumers, so you can add a new consumer (analytics, notifications) without touching the publisher. Name events in the past tense, and put enough data in the event so consumers do not have to call back immediately (event-carried state transfer), while not leaking internal details.

Likely follow-ups
  • Thin event or fat event? A thin event only has the id and forces a call back. A fat event carries the data and avoids chatty calls but can get stale and is harder to change.
At-most-once, at-least-once and exactly-once: what do they mean and what do you really get? Senior

What the interviewer is testing: honest understanding of delivery guarantees and idempotent consumers.

At-most-once means a message is sent once and may be lost, never duplicated. At-least-once means it is retried until acknowledged, so it is never lost but may be delivered several times. Exactly-once means one effect per message. Over a network, true exactly-once delivery is not possible, because if an acknowledgement is lost the sender cannot know whether the receiver processed the message.

What we really build is at-least-once delivery plus an idempotent consumer, which gives "effectively once" processing. The consumer stores the id of each processed message (an inbox table, or a unique key) and ignores a message it has seen, or the operation is naturally idempotent (set status to PAID). Some platforms advertise exactly-once, for example Kafka transactions, but that holds inside Kafka (read, process, write back to Kafka). The moment you touch an external database or call an HTTP API, you still need idempotency.

Likely follow-ups
  • When is at-most-once fine? Metrics, logs and other data where losing one sample does not matter.
Common mistakes: saying "we use Kafka so we have exactly-once" without an idempotent write to the database.
What is a dead letter queue and how do you handle poison messages? Intermediate

What the interviewer is testing: practical message-consumer reliability.

A poison message is one the consumer can never process, for example malformed JSON or a bug on one data shape. If you keep retrying it, it blocks the queue (especially in an ordered partition) or burns CPU forever. The standard answer is: retry a limited number of times with backoff, then move the message to a dead letter queue (DLQ), a separate queue for failed messages, and carry on with the next one. The DLQ message keeps the original payload, the error and the retry count.

A DLQ is not a trash can. You need an alert on its size, a way to inspect messages, and a way to replay them after the bug is fixed. Also separate transient errors (database timeout, retry later) from permanent errors (invalid data, send to DLQ at once). Be careful that replay is safe, which again needs idempotent consumers.

What does an API gateway do, and what should it NOT do? Basic

What the interviewer is testing: the single entry point idea and the risk of a fat gateway.

An API gateway is the single front door for clients. It receives all external requests and routes them to the right service. It also handles cross-cutting work in one place: authentication and token validation, TLS termination, rate limiting, request logging and tracing headers, response caching, request size limits, and sometimes protocol translation (HTTP to gRPC). Clients only know one address and do not need to know how many services exist behind it.

What it should not do is business logic. If the gateway starts to contain rules, data joins and orchestration of ten services, it becomes a bottleneck and a shared monolith that every team must edit. Keep it thin and mostly configuration. Also remember it is a single point of failure and a hot path, so run it redundantly and watch its latency. Examples are Kong, NGINX, AWS API Gateway, Spring Cloud Gateway and Envoy-based gateways.

Likely follow-ups
  • Gateway versus load balancer? A load balancer spreads traffic over copies of one service. A gateway routes by path and applies API policies across many services.
  • Gateway versus service mesh? The gateway handles north-south traffic (outside to inside). A mesh handles east-west traffic (service to service).
What is the Backend for Frontend (BFF) pattern and when do you use it? Intermediate

What the interviewer is testing: aggregation for different clients without a god gateway.

A BFF is a small backend made for one kind of client, for example one for the mobile app, one for the web app, and one for partners. Different clients need different data shapes. A mobile screen wants one compact response to save battery and round trips, while the web page wants more fields. If everyone calls the generic services directly, the client makes many calls and does a lot of mapping. If you put all variations in one shared gateway, it becomes a mess of if-statements.

The BFF calls the downstream services, combines and trims the data, and returns exactly what its client needs. It is owned by the same team as the client, so they can change it without negotiating. It should hold only presentation-level aggregation, not business rules. The cost is some duplicated code across BFFs and more things to deploy.

Likely follow-ups
  • BFF versus GraphQL? GraphQL lets one flexible endpoint serve many client shapes. A BFF gives you simple, specific REST endpoints per client. They can be combined.
How does service discovery work, and what are client-side and server-side discovery? Intermediate

What the interviewer is testing: how services find each other when instances come and go.

In the cloud, service instances start, stop and move all the time, so their IP addresses change. We cannot hard-code them. Instead, each instance registers itself (or the platform registers it) in a service registry, with health checks to remove dead ones. A caller asks for the name, for example "payment", and gets the current healthy addresses.

In client-side discovery the caller asks the registry (Eureka, Consul) and picks an instance itself with a load-balancing rule. It gives smart client choices but puts logic in every client and language. In server-side discovery the caller calls a stable address, like a load balancer or a Kubernetes Service, and that component finds a healthy instance. This is simpler for clients. In Kubernetes, the Service name resolves through cluster DNS (for example payment.shop.svc) to a virtual IP that spreads traffic over ready pods, so most teams get discovery for free.

Likely follow-ups
  • What if the registry is down? Clients cache the last known list and keep working with it.
How do you manage configuration and secrets across many services and environments? Intermediate

What the interviewer is testing: twelve-factor config, safe secrets, and avoiding rebuilds per environment.

The rule from the twelve-factor approach is: build one artifact (one container image) and give it different configuration per environment from the outside. Never bake environment values into the image. Config comes from environment variables, mounted files (Kubernetes ConfigMaps) or a central config service (Spring Cloud Config, Consul, AWS AppConfig). Central config is versioned in Git so you can see who changed what and roll back.

Secrets (passwords, keys, tokens) are different. They must not live in Git or in images. Use a secret manager (Vault, AWS Secrets Manager, Kubernetes Secrets with encryption at rest), give each service only the secrets it needs, rotate them, and prefer short-lived credentials. For feature behaviour use feature flags instead of config redeploys. Also validate config at startup and fail fast with a clear message.

Likely follow-ups
  • Can config change without a restart? Yes with a refresh mechanism or by watching a config store, but changes must be safe and observable, so many teams prefer rolling restarts for simplicity.
What is a service mesh and do you need one? Senior

What the interviewer is testing: can you name the benefit and the cost without overselling.

A service mesh (Istio, Linkerd) puts a small proxy, called a sidecar, next to every service instance. All traffic between services goes through these proxies, and a control plane configures them. This moves cross-cutting network features out of application code: mutual TLS between services, retries and timeouts, circuit breaking, traffic splitting for canaries, and uniform metrics and traces.

The benefit is consistency in any language and central policy. The cost is complexity: extra containers per pod, added latency, more resources, a new thing to debug and upgrade, and a learning curve. I would add a mesh when there are many services in several languages and strict security needs such as mutual TLS everywhere. For ten services in one language, a good client library plus an ingress is usually enough. This is where platform-team depth begins, so as an application developer I only need to know what it gives me and how it changes my retries (do not retry in both the app and the mesh, or you multiply them).

Why do many companies use REST outside and gRPC or messaging inside? Intermediate

What the interviewer is testing: matching protocol to audience.

Outside, you talk to browsers, mobile apps and partners you do not control. REST over HTTP and JSON works everywhere, is easy to read and debug with a browser or curl, and is easy to cache. Inside, you control both sides, and performance and strict contracts matter more. gRPC uses HTTP/2 and Protocol Buffers, a compact binary format with a schema. It is smaller and faster to parse, supports streaming in both directions, and generates typed client and server code in many languages from one .proto file. Messaging and events are used for flows that should not be tied to one request.

The cost of gRPC is that it is harder to call by hand, browsers need a gateway (gRPC-Web), and load balancing HTTP/2 needs care because one long connection can pin all traffic to one instance. So the common split is a public REST (or GraphQL) edge, and gRPC and events behind it. It is not a rule, many fine systems use REST only.

3. Resilience: timeouts, retries, breakers and friends

Why must every remote call have a timeout, and how do you pick the value? Basic

What the interviewer is testing: the number one cause of cascading failures.

Without a timeout, a call to a slow or hung service waits forever. Each waiting call holds a thread, a connection and memory. When many requests pile up, the caller runs out of threads and stops answering, and then its callers do the same. One slow dependency becomes a full outage. A timeout turns "slow" into a fast, clear failure that you can handle.

To choose a value, look at the real latency of the callee, for example its p99 (99 percent of calls are faster than this), and set the timeout a bit above that, not at ten times it. Set separate timeouts for connect (short, say 1 second) and for read. Also respect the overall budget: if the user request has 2 seconds in total, a chain of three calls cannot each take 2 seconds. Pass a deadline down the chain (gRPC does this natively) so deeper services stop work that nobody is waiting for any more. Many libraries default to no timeout or very long ones, so set them explicitly.

// Java 11+ HttpClient
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(1)).build();
HttpRequest req = HttpRequest.newBuilder(URI.create(url))
    .timeout(Duration.ofSeconds(2)).build();
Likely follow-ups
  • What happens to the work on the server when the client times out? Often it continues. So write operations must be idempotent, because the client may retry something that already succeeded.
Common mistakes: using the library default; one big timeout for everything; client timeout longer than the caller's own timeout.
How should retries work? Explain exponential backoff and jitter. Intermediate

What the interviewer is testing: retries help for transient errors and hurt when done badly.

A retry helps when the failure is short-lived: a dropped connection, a 503 during a deploy, a timeout from a brief spike. It does not help when the request itself is wrong (400) or the server is truly overloaded. Retry only on errors that are likely transient, and only for operations that are safe to repeat, meaning idempotent ones.

Waiting between tries is key. Exponential backoff doubles the wait each time (100 ms, 200 ms, 400 ms and so on, with a cap), which gives the server room to recover. Jitter adds randomness to each wait. Without it, a thousand clients that failed together all retry at the same moment again and again, creating waves that keep the server down. Full jitter means waiting a random time between zero and the backoff value. Also cap the number of attempts (3 is common), respect a Retry-After header, and keep a total time budget.

// full jitter, in pseudo-code
sleep = random(0, min(cap, base * 2^attempt))
Likely follow-ups
  • Which status codes would you retry? 502, 503, 504, 429 (honour Retry-After), connection errors and timeouts. Not 400, 401, 403, 404, 422.
What is a retry storm and how do you prevent it? Senior

What the interviewer is testing: multiplication of retries across layers.

A retry storm happens when retries make a small problem into a big one. Say service A calls B, B calls C, and each layer retries three times. One user request can turn into 3 x 3 x 3 = 27 calls hitting C, just when C is struggling. The extra load keeps C down, even after the original cause is gone.

Protections: retry at one layer only, usually closest to the failure or at the edge, not at every hop. Use a retry budget: allow retries only as a small fraction of normal traffic (for example 10 percent), so when most calls fail the retries are cut off. Add exponential backoff with jitter. Combine retries with a circuit breaker, so once the callee is clearly unhealthy you stop calling it for a while. And make servers able to shed load with a fast 503 or 429 so clients back off. Also check that the mesh and the application are not both retrying.

Likely follow-ups
  • Should a client retry a 429? Yes, but only after the time in Retry-After, and with the budget in mind.
Explain the circuit breaker pattern and its states. Intermediate

What the interviewer is testing: fail fast to protect both sides.

A circuit breaker wraps calls to a dependency and watches the results. In the closed state calls go through normally while it counts failures. When the failure rate in a recent window goes over a threshold (say 50 percent of the last 20 calls, or slow calls above a limit), it opens. In the open state calls fail immediately without touching the dependency, so you do not waste threads on a service that is down, and you give it room to recover. After a wait time, the breaker goes half-open: it lets a few trial calls through. If they succeed, it closes again. If they fail, it opens again.

When open, you return a fallback or an error that the caller can handle. Tune it per dependency, count slow calls as failures too, and expose the state as a metric and an alert. Libraries: Resilience4j in Java (Hystrix is retired), Polly in .NET, or the mesh.

Likely follow-ups
  • Where should the breaker live? Around each remote dependency, per instance of the caller. Do not share one breaker for different dependencies.
  • What do you return when open? A cached value, a default, a degraded result, or a clear error.
What is the bulkhead pattern? Intermediate

What the interviewer is testing: isolation of resources so one failure does not drain everything.

The name comes from ship bulkheads: walls that stop water in one compartment from sinking the whole ship. In software, you give each dependency or each kind of work its own limited pool of resources, such as a separate thread pool, connection pool or concurrency limit. If the Recommendation service becomes slow and uses up its 10 threads, the 40 threads used for Payments are still free, so checkout keeps working.

Without bulkheads, all outgoing calls share one pool. A single slow dependency takes all the threads, and the whole service goes down even though most of its dependencies are healthy. You can apply the idea at several levels: thread pools or semaphores inside a service, separate connection pools, separate instances for critical traffic, and even separate clusters for different tenants. The cost is that some capacity sits idle, and you must size the pools sensibly.

What is rate limiting and which algorithms are common? Intermediate

What the interviewer is testing: protecting a service and being fair to clients, with algorithm trade-offs.

Rate limiting caps how many requests a client may make in a time window. It protects the service from overload, from abuse, and from one noisy tenant starving others. When the limit is hit you return 429 Too Many Requests with a Retry-After header. The key can be an API key, a user, a tenant or an IP address.

Main algorithms: Fixed window counts per minute, simple but allows a double burst around the window edge. Sliding window smooths that by looking at the last N seconds. Token bucket adds tokens at a steady rate into a bucket with a maximum size, and each request takes one token, which allows short bursts while keeping the average rate. Leaky bucket processes at a constant rate and queues or drops the rest. Token bucket is the most common. In a cluster the counters must be shared, typically in Redis with atomic operations, or you accept a rough local limit per instance. Do it at the gateway for coarse limits, and in services for per-tenant fairness.

Likely follow-ups
  • Rate limiting versus load shedding? Rate limiting is per client policy. Load shedding drops work when the whole service is overloaded, whoever sends it.
  • More depth: rate limiting chapter.
What is idempotency and why is it essential in microservices? Intermediate

What the interviewer is testing: whether you design for retries and duplicates.

An operation is idempotent if doing it once or many times gives the same final result. "Set the order status to PAID" is idempotent. "Add 100 to the balance" is not. In a distributed system we cannot avoid duplicates: a client times out and retries although the first call succeeded, a broker redelivers a message, a user double-clicks the pay button. So any operation that can be repeated must be safe to repeat.

How to get there: prefer naturally idempotent operations (PUT, set state). For operations that are not, use an idempotency key: the client sends a unique id with the request, and the server stores the key with the result. On a repeat with the same key it returns the stored result and does not run the operation again. For message consumers, record processed message ids in an inbox table inside the same transaction as the business change. The key check and the business write must be atomic, or two parallel duplicates can both pass the check; a unique constraint on the key solves that.

Likely follow-ups
  • How long do you keep keys? Long enough to cover the longest realistic retry window, such as 24 hours or a few days.
  • More depth: idempotency chapter.
What is graceful degradation and what are good fallbacks? Intermediate

What the interviewer is testing: product thinking about failure, not just technical patterns.

Graceful degradation means that when a non-critical part fails, the system still gives a reduced but useful result, instead of an error page. For a shop page, if the recommendation service is down, show the product without recommendations, or show a cached or generic "popular items" list. If the review service is slow, show the page and load reviews later. If the pricing service is down, a stale cached price might be acceptable for browsing but not for checkout.

The key step is classifying each dependency as critical or optional, together with the product owner. Fallback options: cached data, a default value, a simpler algorithm, a queue for later processing, or a clear message. Be careful with fallbacks that hide problems or that are never tested, so you should test them often, for example with chaos or fault injection. Also be careful with fallbacks for money or security decisions: failing closed is usually better than guessing.

What is the difference between liveness, readiness and startup health checks? Intermediate

What the interviewer is testing: correct use of health endpoints in Kubernetes-style platforms.

A liveness check answers "is this process stuck so badly that it needs a restart?". If it fails, the platform kills and restarts the instance. A readiness check answers "can this instance take traffic right now?". If it fails, the instance is removed from the load balancer but not killed. It is used during startup, while warming a cache, or while a dependency is unavailable. A startup check gives a slow-starting application time before liveness begins.

A common mistake is to put dependency checks in the liveness probe. If the database is down and liveness fails, the platform restarts every instance at once and makes things worse. Liveness should be cheap and only check the process itself. Readiness may check things the instance needs to work, but even there, think twice: if every instance reports not ready because a shared dependency is down, you get a total outage instead of degraded service.

GET /actuator/health/liveness    # process ok?
GET /actuator/health/readiness   # ready for traffic?
What is load shedding and how is it different from backpressure? Senior

What the interviewer is testing: staying alive under overload.

When a service gets more work than it can handle, queues grow, latency climbs, and soon every request is too slow to be useful: throughput collapses. Load shedding means the service deliberately rejects some requests early, with a fast 503 or 429, so that the rest are served within good time. It is better to serve 80 percent well than 100 percent badly. You can shed by priority (keep checkout, drop recommendations), by age (drop requests the client already gave up on), or by simple concurrency limits.

Backpressure is the signal that flows back to the producer to slow down: a bounded queue that blocks or rejects when full, a reactive stream demand, a consumer lag that makes producers pause, or HTTP 429. Shedding is what the overloaded server does; backpressure is how the sender learns to slow down. Use bounded queues everywhere. An unbounded queue just hides overload until the memory runs out.

4. Data ownership, transactions and consistency

Why should each microservice own its database? Basic

What the interviewer is testing: the foundation of loose coupling.

If two services read and write the same tables, the table structure becomes a hidden API. Any schema change needs both teams to agree and deploy together, and one service can break the other by a slow query or a lock. You have a distributed monolith. When each service owns its data and exposes it only through its API or events, it can change its schema, even its database type, without telling anyone. It can also scale and fail on its own.

"Own" does not always mean a separate database server. It can be a separate schema or a separate set of tables with strict access rules, as long as no other service touches it. Separate servers give stronger isolation but cost more to run. The price of this rule is that you lose cross-service joins and cross-service transactions, which is what the next questions are about.

Likely follow-ups
  • Different database types per service? Yes, polyglot persistence: relational for orders, document store for catalog, search engine for search. Only if it brings a real benefit, since each type costs operations effort.
A team wants to share one database between services "just for now". What do you say? Intermediate

What the interviewer is testing: pragmatism plus knowing the risks.

I explain the risks first: hidden coupling through the schema, joint deployments, one team's heavy query slowing another, and no clear owner of the data rules. These problems only grow with time, and "for now" tends to become forever. Then I look for the real need behind the request. Often they just need data from another service. Options: call that service's API, subscribe to its events and keep a local copy of the fields needed, or use a read-only reporting replica for analytics.

If there is a temporary migration, for example while splitting a monolith, a shared database can be acceptable as a short, tracked step, with a rule that only one service writes to each table and a date to remove it. A shared database for reporting through a separate read replica or a data warehouse fed by events is a normal pattern, because it is not on the transaction path.

How do you query data that lives in several services (the "join" problem)? Intermediate

What the interviewer is testing: options when joins are no longer possible.

There are three main options. API composition: one service (or the gateway or a BFF) calls the owners and joins the results in memory. It is simple and fine for small result sets, but it is slow for big lists, has the availability of all calls combined, and cannot sort or filter across services efficiently. Data replication: a service keeps its own copy of the fields it needs from another service, updated through events. Reads are fast and local, but the copy can be slightly stale and you must handle updates. CQRS read model: build a dedicated read database (maybe Elasticsearch) fed by events from several services, designed for exactly the queries you need.

My rule: for a couple of items on a detail page, use composition. For lists with filters and sorting across services, build a read model. Store only what you need, and accept that the data is eventually consistent.

Likely follow-ups
  • What about GraphQL federation? It composes several services behind one schema, but under the hood it is still API composition with the same limits.
What is eventual consistency and how do you live with it as a developer? Intermediate

What the interviewer is testing: practical handling of stale reads in UX and logic.

Eventual consistency means that after a write, other copies of the data are not updated at the same instant, but if no new writes happen they all converge to the same value after some short time. In microservices it is normal, because services update each other through events. For example after an order is placed, the inventory and the order history may be updated a few hundred milliseconds apart.

Ways to live with it: design the UI so it does not assume instant truth (show "processing" status, update when the event arrives); return the new state from the write itself so the user sees their own change (read-your-writes); make operations idempotent and order-tolerant (use version numbers and ignore older updates); keep strong consistency inside one aggregate and one service, where it is cheap, and use eventual consistency only across services; and add reconciliation jobs to detect and repair drift. Also be clear with the business which parts need strong consistency, such as money movement, and design those carefully.

Why is two-phase commit (2PC) usually avoided in microservices? Senior

What the interviewer is testing: knowing what 2PC is and the real reasons it fails at scale.

In 2PC a coordinator asks all participants to prepare (do the work and promise they can commit, holding locks). If all say yes, it tells them to commit. If any says no, everyone rolls back. It gives atomic all-or-nothing across databases.

The problems: it is blocking. Participants hold locks from prepare until the coordinator decides. If the coordinator crashes between the phases, participants are stuck "in doubt" and the locks stay, so throughput drops and deadlocks appear. It needs every participant to support the protocol (XA), which most message brokers, REST APIs and NoSQL stores do not. Latency adds up from several round trips, and availability is the product of all participants being up. So it does not fit independent, heterogeneous, separately deployed services. We use sagas instead: a series of local transactions with compensations, trading atomicity and isolation for availability and autonomy. 2PC is still used inside one organisation's database cluster or with a few XA resources, where the cost is acceptable.

Likely follow-ups
  • What is 3PC? An attempt to reduce blocking with another phase, but it still fails under network partitions, so it is rarely used.
  • More depth: distributed transactions chapter.
What is the saga pattern? Walk through an example. Intermediate

What the interviewer is testing: the main alternative to distributed transactions.

A saga is a business transaction made of several local transactions, one per service. Each step commits on its own. If a later step fails, the saga runs compensating transactions for the steps already done, to undo their effect in a business sense. Example, placing an order: (1) Order service creates the order as PENDING. (2) Payment service charges the card. (3) Inventory service reserves the stock. (4) Order is marked CONFIRMED. If inventory fails in step 3, we run compensations: refund the payment, and cancel the order.

Important points: a compensation is a new business action, not a database rollback. A refund is not the same as the charge never happening, since the customer may see both. Compensations must be idempotent and must be able to succeed even if retried, because they cannot be allowed to fail. Sagas have no isolation: other requests can see the in-between state (a PENDING order). You handle that with semantic locks (status fields), commutative updates, or re-reading values. Order steps so that the ones most likely to fail, or hard to undo, come first.

Likely follow-ups
  • What if a step cannot be compensated, such as an email already sent? Put it last, after the point of no return (a "pivot step").
  • More depth: sagas chapter.
Saga choreography versus orchestration: how do you choose? Senior

What the interviewer is testing: trade-off between decentralised events and a central coordinator.

In choreography, there is no central controller. Each service listens to events and reacts: Order publishes OrderPlaced, Payment hears it, charges, and publishes PaymentCompleted, Inventory hears that, and so on. It is loosely coupled and simple for two or three steps, with no single point of failure. But the flow is hidden across many services, hard to see, hard to change, and can create cyclic dependencies. Debugging "where is my order stuck?" is painful.

In orchestration, a central orchestrator (an Order Saga service or a workflow engine such as Temporal, Camunda or AWS Step Functions) tells each service what to do and tracks the state. The flow is explicit in one place, easy to follow, test and monitor, and compensation logic is centralised. The cost: one more component to build and run, and the risk of putting too much business logic in it. My choice: choreography for short, simple flows with few participants; orchestration for longer flows with branching, timeouts and compensations, which is most real business processes.

Likely follow-ups
  • Where does orchestrator state live? In its own database, so it can resume after a crash. That state is the saga log.
What is the dual-write problem? Senior

What the interviewer is testing: recognising the most common data-consistency bug in event-driven code.

Dual write means one piece of code writes to two systems that cannot share a transaction, for example saves an order to the database and then publishes an event to Kafka. There is no atomicity between them. If the database commit succeeds and the process crashes before publishing, the event is lost, and other services never learn about the order. If you publish first and the database commit then fails, you published an event for something that never happened. Wrapping both in a try block does not help, because a crash can happen anywhere between the two steps.

The fix is to write only to one place atomically. The standard solution is the transactional outbox: write the event into an outbox table in the same local database transaction as the business change, and let a separate process publish it. Another way is event sourcing, where the event is the data. Distributed transactions (2PC) are the heavy alternative.

Explain the transactional outbox pattern. Senior

What the interviewer is testing: a concrete, widely used reliability pattern, and its caveats.

In one local transaction the service writes its business data (the order row) and also inserts a row in an outbox table that holds the event to send. Since both are in the same database transaction, either both exist or neither does. A separate relay then reads new outbox rows and publishes them to the broker, marking them as sent after the broker confirms. There are two ways to relay. A polling publisher queries the table on a timer, which is simple. Change data capture (CDC) with a tool such as Debezium reads the database transaction log and streams outbox rows, with low delay and no polling load.

Delivery is at-least-once: if the relay publishes and crashes before marking the row, it sends again. So consumers must be idempotent, and every event needs a unique id. Ordering per aggregate is kept by using the aggregate id as the partition key. The outbox also needs cleaning, so delete or archive old rows. Its twin on the receiving side is the inbox table, which stores processed message ids to deduplicate.

Likely follow-ups
  • Outbox versus listen-to-yourself? Some teams publish first and let the service consume its own event to update its DB, but you then lose read-your-writes, so outbox is more common.
What makes a good compensating action, and what if the compensation fails? Senior

What the interviewer is testing: depth on failure of the failure path.

A compensation must be idempotent, because it can be retried, and it must be retryable until success, because the system cannot leave a saga half-undone. Design each step so the undo is always possible: reserve stock (can be released) before charging, and charge (can be refunded) before sending a shipment (cannot be unsent). Keep the transaction ids so the undo refers to exactly the thing it reverses.

If a compensation fails, retry with backoff. If it keeps failing, put the saga in a "needs attention" state, raise an alert, and send it to a human with all context. Do not silently drop it. Orchestrators and workflow engines give you durable retries and visibility for this. Also record the saga state at every step, so after a crash it continues where it was. Finally, accept that some actions are only semantically undone: a refund shows on the customer's statement, and an email cannot be recalled. Tell the user honestly with a follow-up message.

What is CQRS, and when is it worth using? Intermediate

What the interviewer is testing: separation of read and write models, and honest costs.

CQRS stands for Command Query Responsibility Segregation. It means using different models for changing data (commands) and for reading data (queries). The write side is shaped around business rules and consistency. The read side is shaped around screens and queries: denormalised, pre-joined, often in a different store such as Elasticsearch or a key-value cache. The write side publishes events when it changes, and a projection updates the read side, so the read model is eventually consistent.

It is worth it when reads and writes have very different load or shape (many more reads, complex search screens), or when you need to combine data from several services into one fast view. It is not worth it for plain CRUD. The costs: two models to maintain, eventual consistency between them, more moving parts and the need to rebuild projections. A light version is just a separate read replica or a few database views with no event bus, which already gives some benefit with little cost.

Likely follow-ups
  • Does CQRS require event sourcing? No. They fit together but are independent.
  • How do you hide the lag in the UI? Return the new state from the write, or show a pending marker until the read model catches up.
What is event sourcing, and what are its benefits and risks? Senior

What the interviewer is testing: understanding of a powerful but demanding pattern.

In normal systems you store the current state and overwrite it on each change. In event sourcing you store every change as an immutable event in an append-only log (AccountOpened, MoneyDeposited, MoneyWithdrawn). The current state is computed by replaying the events for that entity. For speed you take periodic snapshots and replay only the events after the latest one.

Benefits: a perfect audit trail, ability to rebuild state at any past time, to create new read models by replaying history, and natural events to publish with no dual-write problem. Risks and costs: a different way of thinking, hard querying (you need projections, so it is usually combined with CQRS), event schema evolution forever (old events must still be readable, so use versioned events and upcasters), handling of personal data deletion (immutable log versus the right to erasure, often solved by encrypting per-user data and discarding the key), and replay time. I would use it in domains where history is the product, such as ledgers, trading or audit-heavy workflows, and not for ordinary CRUD.

Likely follow-ups
  • How do you handle concurrent writes to one entity? Optimistic concurrency: append with the expected version, fail if someone else appended first.
How do you prevent lost updates and double processing across services without distributed locks? Senior

What the interviewer is testing: alternatives to heavy locking.

Distributed locks are fragile: a holder can pause (long garbage collection) while its lock expires, then wake up and write anyway. So I avoid them for correctness and use data-level checks. Optimistic concurrency: each row has a version number, and the update says "set the new value where id = X and version = 5". If someone else changed it, zero rows update and you retry or report a conflict. HTTP exposes this with ETag and If-Match. Unique constraints turn duplicates into errors (one payment per idempotency key). Conditional writes and compare-and-set exist in most stores. Single-writer by partition: route all work for one entity to the same consumer, for example using the entity id as the Kafka key, so no two workers handle it at the same time.

Use a lock only for efficiency (avoid duplicate work), where a rare double run is harmless. If you need a lock for correctness, use a fencing token, a number that grows with each lock grant and that the resource checks, so a stale holder is rejected.

5. Evolution, testing, observability, security and deployment

How do you change an API or event schema without breaking consumers? Senior

What the interviewer is testing: backward compatibility discipline, the key to independent deployment.

The goal is to deploy a producer and its consumers in any order. So changes must be backward compatible: old clients keep working with the new server. Safe changes: add a new optional field, add a new endpoint, add a new optional parameter, add a new enum value only if clients are told to ignore unknown ones. Unsafe: remove or rename a field, change a type, make an optional field required, change the meaning of a value, change the error format.

Rules that help: clients should follow the tolerant reader rule (ignore unknown fields, do not fail on new enum values), and servers should follow the robustness idea of being strict in what they send. For a real breaking change use the expand and contract (parallel change) steps: add the new way next to the old one, move all consumers over and verify with metrics, and only then remove the old way. When that is not possible, publish a new version (v2) and run both for a deprecation period. For events and protobuf, use a schema registry with compatibility checks in CI so a breaking schema cannot be published.

Likely follow-ups
  • How do you know nobody uses the old field? Log or count its usage, and check consumer-driven contract tests.
What is contract testing and why use it instead of end-to-end tests? Intermediate

What the interviewer is testing: a testing strategy that keeps services independent.

A contract test checks that a provider and its consumers agree on the API without running everything together. In consumer-driven contracts (Pact, Spring Cloud Contract), each consumer writes down what it needs from the provider: "when I send GET /orders/42 I expect 200 and these fields". That contract is published. The provider's pipeline runs those contracts against its real code, and if a change would break a consumer, the provider's build fails before release. The consumer's tests run against a stub generated from the same contract, so they are fast and do not need the real service.

Compared with big end-to-end tests across many services, contract tests are fast, stable, run in each service's own pipeline, and point to exactly which consumer and field broke. End-to-end tests are slow, flaky, need a shared environment, and give vague failures. I keep a very small number of end-to-end tests for the most critical journeys, and rely on contract tests plus good unit and integration tests for the rest.

How do you test a microservice? Describe the layers. Intermediate

What the interviewer is testing: a realistic test pyramid for services.

Base: many fast unit tests for business logic, with no network. Next: integration tests for the service with its real database and broker (Testcontainers starts a real Postgres or Kafka in Docker), which catch mapping, SQL and serialisation problems that mocks hide. Then component tests that start the whole service and fake its neighbours with stubs or WireMock, to test the API as a black box. Then contract tests for each integration with other services. At the top, a few end-to-end tests for critical journeys in a shared environment, and smoke tests after each deployment.

Also test failure behaviour: timeouts, errors from dependencies, duplicate messages, out-of-order events. And test in production safely with canary releases, feature flags and good monitoring, since some problems only appear under real traffic. A common trap is to mock everything and then be surprised in production.

What are logs, metrics and traces, and why do microservices need all three? Basic

What the interviewer is testing: the three pillars of observability and what each is good for.

Metrics are numbers over time: request rate, error rate, latency percentiles, CPU, queue depth. They are cheap and good for dashboards and alerts, and tell you that something is wrong. Logs are detailed event records with context. They tell you what happened in one place, and are best structured (JSON) so they can be searched. Traces follow one request through many services as a tree of timed spans. They tell you where the time went and which service failed.

In a monolith you can read one log file. With 30 services one user action touches many of them, so you need to connect the records. The usual flow: an alert fires on a metric (error rate up), you open a trace to find the slow or failing service, then you read that service's logs for the same trace id. Standard tools: OpenTelemetry for instrumentation, Prometheus and Grafana for metrics, an ELK stack or similar for logs, Jaeger or Tempo for traces.

Likely follow-ups
  • Which metrics matter most? The golden signals: latency, traffic, errors, saturation. For a request-driven service also use RED (rate, errors, duration).
What is a correlation id, and how does distributed tracing propagate context? Intermediate

What the interviewer is testing: practical tracing: where ids come from and how they travel.

A correlation id (or trace id) is a unique id created at the entry point of a request, by the gateway or the first service. Every service passes it on to every call it makes (HTTP header, gRPC metadata, message header) and writes it into every log line. Then you can search one id and see the whole story across services. Distributed tracing formalises this. A trace is the whole request and has a trace id. Each unit of work is a span with its own span id and a parent span id, with start time and duration. The standard header is W3C traceparent, for example 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 (version, trace id, parent span id, flags).

The classic failure is that the id is dropped at a boundary: an async thread pool, a message queue, a scheduled job, or a library that does not copy headers. Then the trace breaks in two. Use the framework instrumentation (OpenTelemetry agents) and copy the context into message headers and into thread-local storage for async work. Put the trace id in the error response too, so a user can report it.

Likely follow-ups
  • What is sampling? Keeping only a share of traces (say 1 percent plus all errors and slow ones) to control cost.
What are good logging practices in microservices? Intermediate

What the interviewer is testing: logs that are useful at three in the morning.

Write structured logs, usually JSON, with fixed fields: timestamp, level, service name, version, trace id, user or tenant id where allowed, and message. Log to standard output and let the platform collect them, not to local files. Use levels honestly: ERROR means a person might need to act, WARN is unusual but handled, INFO is key business events, DEBUG is off in production by default. Do not log secrets, tokens, card numbers or personal data, and mask what you must keep.

Avoid logging the same error at every layer as the exception bubbles up: log once where it is handled, with context. Avoid log spam in hot loops, because it costs money and hides real signals. Add the key business ids (order id) so you can find the story. Set sampling or rate limits for noisy logs. Logs are a debugging tool, but alert from metrics, not from log search, since metrics are cheaper and more reliable.

What are SLI, SLO and SLA, and how do they guide alerting? Intermediate

What the interviewer is testing: user-focused reliability thinking.

An SLI (service level indicator) is a measurement of user experience, such as "percentage of requests that succeed in under 300 ms". An SLO (objective) is the target for it, such as 99.9 percent over 30 days. An SLA (agreement) is a contract with a customer that often has money penalties if missed, and is looser than the internal SLO. The gap between the SLO and 100 percent is the error budget: at 99.9 percent you may fail 0.1 percent of requests, about 43 minutes per month. While the budget is healthy the team ships features. When it is used up, the team slows down and works on reliability.

For alerting, page a person only when the user is being hurt now or the error budget is burning fast, not for every CPU spike. Alert on symptoms (error rate, latency) rather than causes. Many noisy alerts train people to ignore them.

How do you secure service-to-service calls? Senior

What the interviewer is testing: zero-trust thinking inside the network.

The old idea "inside the network is trusted" is dangerous: one compromised service then reaches everything. So each call should prove who is calling and be encrypted. Two common building blocks work together. Mutual TLS (mTLS): both sides present certificates, so the server knows exactly which service is calling and the traffic is encrypted. Certificates are short-lived and rotated automatically, usually by a mesh or a platform such as SPIFFE. Tokens: a signed token (JWT) carries the identity and permissions. For machine-to-machine calls, a service gets its own token using the OAuth2 client credentials flow.

On top of authentication you need authorisation: service A may call only the endpoints it needs, using network policies, mesh policies or scopes in the token. Also apply least privilege to secrets and database accounts. For user context, pass the end user's identity along (see the token propagation question) so downstream services can check that the user, and not just the calling service, is allowed.

Likely follow-ups
  • Should every service validate the token, or only the gateway? Both. The gateway is a convenience and a first filter, but services must not trust the network. More depth: security chapter.
Explain OAuth2 and JWT in the context of APIs. Which flows do you use? Intermediate

What the interviewer is testing: correct use of authorization versus authentication, and token handling.

OAuth2 is a framework for delegated authorisation: a user lets an application act on their behalf without sharing the password. The authorisation server issues an access token that the client sends in Authorization: Bearer .... OpenID Connect (OIDC) adds an ID token for authentication, meaning who the user is. A JWT (JSON Web Token) is a common token format: three Base64 parts (header, payload with claims like sub, exp, aud, scope, and a signature). The resource server verifies the signature using the issuer's public key (JWKS), and checks expiry, issuer and audience, so no call to the auth server is needed for each request.

Flows: for users in browsers and mobile apps use the Authorization Code flow with PKCE (a one-time secret that protects the code from interception). For service-to-service use Client Credentials. The old implicit and password flows are discouraged. Keep access tokens short-lived (minutes) and use refresh tokens to get new ones. A JWT is signed, not encrypted, so never put secrets in it. A weakness of self-contained tokens is that they cannot be revoked easily before expiry, so use short lifetimes, or opaque tokens with introspection when instant revocation is needed.

Likely follow-ups
  • What must you validate in a JWT? Signature and algorithm (reject "none"), expiry, issuer, audience, and required scope.
  • Where do you store tokens in a browser? Preferably in memory or in an HttpOnly, Secure, SameSite cookie, and not in local storage where scripts can read it.
Common mistakes: using OAuth2 as "login" without OIDC; long-lived JWTs with no revocation plan; trusting the token payload without verifying the signature.
Should a service pass the user's token to the next service, or use its own identity? Senior

What the interviewer is testing: the confused deputy risk and downstream authorisation.

There are two models. Token forwarding: service A passes the user's token to B, so B can check what that user is allowed to do. It keeps user context and is simple, but B must trust tokens meant for A (audience problem) and a stolen token works everywhere. Better is token exchange (OAuth2 token exchange, RFC 8693): A swaps the user's token for a new one with the right audience for B and reduced scope. The other model is service identity only: A calls B with its own service credentials (mTLS or client credentials), and B trusts A to have checked the user. It is simple for background jobs, but B loses the user context and A becomes a "confused deputy" that could be tricked into using its wide power for a user who should not have it.

My approach: authorise the user at the edge and again in the service that owns the data, pass user identity as a signed claim or exchanged token, and also authenticate the service itself with mTLS. For asynchronous events, include the user or tenant id in the message, and remember the original token may have expired by the time it is processed.

What deployment practices do microservices need? Intermediate

What the interviewer is testing: application-developer level knowledge of shipping many services safely.

Each service has its own pipeline: build, unit and contract tests, scan, build a container image, deploy to a test environment, then to production. The artifact is immutable: the same image goes through every environment, only config differs. Production rollouts are gradual. Rolling update replaces instances in small batches with health checks. Blue-green runs a full new copy and switches traffic at once, with an instant switch back. Canary sends a few percent of traffic to the new version, watches error rate and latency, and then increases. Feature flags separate deploying code from turning on the feature, so you can release dark and roll back by switching a flag.

Also needed: health checks and graceful shutdown (finish in-flight requests, stop taking new ones), resource limits, autoscaling on a meaningful metric, and a rollback path. Schema changes must be compatible with both old and new code, because during a rollout both run together. Cluster operations and autoscaler tuning are platform-team depth, not expected here.

Likely follow-ups
  • How do you do a database change with no downtime? Expand and contract again: add the new column, deploy code that writes both, backfill, switch reads, and drop the old column in a later release.
What does graceful shutdown mean, and why do deployments drop requests without it? Intermediate

What the interviewer is testing: a real production detail behind "random 502s during deploy".

When the platform stops an instance, it sends a termination signal (SIGTERM) and, after a grace period, kills it. A graceful application reacts to SIGTERM by first reporting "not ready" so the load balancer stops sending new requests, then finishes the requests already in progress, closes connections and consumers cleanly, and exits. Without that, in-flight requests are cut off and clients see errors on every deploy.

A subtle problem is timing: the load balancer or service registry needs a few seconds to learn the instance is gone, so new requests may still arrive after SIGTERM. A short delay before stopping the listener, plus a grace period longer than the longest request, fixes it. Message consumers must stop polling, finish the current message and commit offsets before exit. Frameworks such as Spring Boot (server.shutdown=graceful) support this, but you need to turn it on and match the platform's grace period.

6. REST design basics

What is REST, and what makes an API RESTful? Basic

What the interviewer is testing: that you know REST is a set of constraints, not just "JSON over HTTP".

REST (Representational State Transfer) is an architecture style from Roy Fielding's thesis. You model things as resources (an order, a customer), each with a URL. You work with them through a small, uniform set of operations, the HTTP methods. Clients get and send representations of the resource, usually JSON. The main constraints are: client and server are separate; the server is stateless (each request carries everything needed, no session memory on the server); responses say whether they are cacheable; the interface is uniform; the system is layered (proxies, gateways can sit in between); and, in the strict form, hypermedia drives the flow (HATEOAS).

In daily work, "RESTful" usually means: nouns in URLs, correct HTTP methods and status codes, stateless calls and JSON. Strictly, most public "REST" APIs stop at level 2 of the Richardson maturity model (resources and verbs) and skip hypermedia. It is fine to say so in an interview and to explain why.

Likely follow-ups
  • What does stateless buy you? Any instance can serve any request, so scaling out and failover are easy.
How do you design resource URLs? Give examples of good and bad ones. Basic

What the interviewer is testing: consistent, predictable naming.

Use nouns, not verbs, because the HTTP method is already the verb. Use plural collection names and ids for items. Express ownership with nesting, but keep it shallow (about two levels). Use lowercase and hyphens, and keep the structure stable. Query parameters are for filtering, sorting and paging, not for identifying the resource.

Some actions do not fit CRUD, for example "cancel an order" or "reset a password". Options: model it as a sub-resource or state change (POST /orders/42/cancellation, or PATCH status), or use a clear action endpoint (POST /orders/42:cancel as in some Google APIs). Pick one style and apply it everywhere.

Likely follow-ups
  • Should ids be sequential numbers? Prefer opaque ids (UUID or similar). Sequential ids leak business volume and allow guessing, which is a risk if authorisation checks are weak.
Which HTTP methods are safe and which are idempotent? Why does it matter? Basic

What the interviewer is testing: core HTTP semantics, used for retries, caching and design.

A method is safe if it does not change server state (read-only): GET, HEAD, OPTIONS. A method is idempotent if calling it once or many times has the same effect on the server: GET, HEAD, OPTIONS, PUT, DELETE (and TRACE). POST and PATCH are not idempotent by definition, although you can make a particular POST idempotent with an idempotency key. All safe methods are idempotent, but not the other way round (DELETE and PUT change state).

It matters because clients, proxies and libraries use it. A client or gateway may automatically retry an idempotent request after a timeout, but not a POST, since it could create two orders. Caches may store GET responses. Crawlers and prefetchers may call GET freely, so a GET that deletes data is a serious bug. Note that idempotent talks about the server state, not the response: the first DELETE returns 204 and the second may return 404, and it is still idempotent.

  • Is DELETE idempotent if the second call returns 404? Yes, the server state after one or many calls is the same.
What is the difference between PUT and PATCH? Basic

What the interviewer is testing: full replace versus partial update, and the effect on clients.

PUT replaces the whole resource with the body you send. If you leave out a field, it is cleared or reset to default. It is idempotent: sending the same PUT twice gives the same result. It is also good for "create or replace at a known URL". PATCH sends only the changes. It is cheaper for big resources, and it is safer when several clients edit different fields, because a client does not overwrite fields it never read.

PATCH has two common formats. JSON Merge Patch (RFC 7396) sends a partial JSON object: fields present are set, fields set to null are removed. It is simple, but you cannot set a field to null on purpose or change one array element. JSON Patch (RFC 6902) sends a list of operations (add, replace, remove, test) with paths, which is precise but more complex. PATCH is not guaranteed to be idempotent: an operation like "add 1 to the counter" is not. In practice use PATCH for updates in most APIs, and combine it with ETag and If-Match to avoid lost updates.

PATCH /customers/7
Content-Type: application/merge-patch+json
{ "phone": "+91-99999-00000", "nickname": null }
Likely follow-ups
  • If a client sends PUT with a field it does not know about, what happens? It may wipe it. That is why PATCH is friendlier when the API grows.
When do you use POST and when PUT to create a resource? Basic

What the interviewer is testing: who chooses the identifier, and idempotency.

Use POST to a collection (POST /orders) when the server decides the id. Each call creates a new resource, so it is not idempotent. The reply should be 201 Created with a Location header pointing to the new resource and usually the resource in the body. Use PUT to a specific URL (PUT /users/ana@example.com/avatar) when the client knows the id, as in "store this at this address". PUT is idempotent, so retries are safe: the second call replaces the same thing with the same content. PUT may return 201 if it created the resource and 200 or 204 if it replaced it.

POST is also the general-purpose method for actions that do not fit other verbs, such as triggering a job or a search with a huge body. When the creating call must be safe to retry, use POST with an idempotency key.

Which HTTP status codes do you use and when? Basic

What the interviewer is testing: precise use of codes, which clients rely on for decisions like retries.

The first digit gives the class: 2xx success, 3xx redirect or not modified, 4xx the client made a mistake, 5xx the server failed. The most used: 200 OK for a successful read or update with a body. 201 Created for a create, with Location. 202 Accepted when work is queued and not done yet. 204 No Content for success with no body (delete, or update). 304 Not Modified for a conditional GET where the client's cache is still valid. 400 Bad Request for malformed input. 401 Unauthorized for missing or invalid credentials. 403 Forbidden for valid identity without permission. 404 Not Found. 405 Method Not Allowed. 409 Conflict for a state conflict such as a duplicate or version clash. 412 Precondition Failed when If-Match does not match. 415 Unsupported Media Type. 422 Unprocessable Content for well-formed but semantically invalid input. 429 Too Many Requests. 500 Internal Server Error for an unexpected bug. 502 Bad Gateway, 503 Service Unavailable (try later) and 504 Gateway Timeout for upstream problems.

Likely follow-ups
  • Should errors always return 200 with an error body? No. It breaks monitoring, caches, retries and generic clients.
Common mistakes: returning 200 for errors; using 500 for validation errors; 404 for an empty list (use 200 with an empty array).
What is the difference between 401 and 403, and when do you return 404 instead? Basic

What the interviewer is testing: authentication versus authorisation, and information leakage.

401 Unauthorized really means "unauthenticated": the request has no credentials or invalid or expired ones. The response should include a WWW-Authenticate header, and the client can fix it by logging in or refreshing its token. 403 Forbidden means the server knows who you are, but you are not allowed to do this. Logging in again will not help.

A security detail: for a resource the caller is not allowed to see, returning 403 reveals that it exists. If existence is itself sensitive (for example another tenant's order id), return 404 Not Found so you do not leak information. The same thinking applies to login errors: do not say "user does not exist" versus "wrong password".

400, 422 or 409: how do you choose for validation and conflict errors? Intermediate

What the interviewer is testing: fine distinction and consistency.

400 is for requests the server cannot understand at all: broken JSON, wrong types, a missing required parameter. 422 Unprocessable Content is for requests that are well-formed but fail business or semantic validation: the end date is before the start date, or the email format is invalid. Many teams simply use 400 for both, which is acceptable if it is consistent and the body explains the problems. 409 Conflict means the request is fine, but conflicts with the current state of the resource: creating a user with an email that already exists, or updating with an old version.

What matters more than the exact code is the body: return a machine-readable list of what is wrong, per field, so a client can show it. Also document your choice and keep it the same in all services.

How should an API return errors? What is problem+json? Intermediate

What the interviewer is testing: a consistent, machine-readable error contract.

Every error should have the right HTTP status and a body with the same shape across all endpoints and services. The standard is Problem Details for HTTP APIs (RFC 9457, which replaced RFC 7807) with media type application/problem+json. Standard fields: type (a URI that identifies the kind of problem, stable and documented), title (short human summary), status, detail (explanation for this occurrence) and instance (the URI of this occurrence). You may add your own fields, such as a list of field errors, an error code and the trace id.

  "type": "https://api.example.com/problems/invalid-order",
  "title": "Order is not valid",

  "detail": "Quantity must be at least 1.",
  "instance": "/orders/draft/91",

Never leak stack traces, SQL or internal hostnames in the body. Log them on the server and give the client the trace id. Clients should branch on type or a stable error code, not on the message text, which may be translated or reworded.

How do you paginate a large collection? Compare offset and cursor pagination. Intermediate

What the interviewer is testing: performance and correctness under changing data.

Offset pagination (?offset=100&limit=20 or ?page=6&size=20) is simple, allows jumping to any page, and shows total pages. But on a big table, the database has to scan and skip all the earlier rows, so deep pages get slow. Worse, when rows are inserted or deleted while the user pages, items are skipped or shown twice.

Cursor (keyset) pagination returns an opaque next cursor that encodes the last item seen, such as its sort key and id. The query becomes "where (created_at, id) is less than the cursor, order by created_at desc, id desc, limit 20", which uses an index and stays fast at any depth, and is stable when data changes. You can only go forward and back, not jump to page 50, and the sort must be deterministic, so always add a unique tiebreaker like the id. I use cursors for feeds, large and fast-changing lists, and offset for small, admin-style lists. Always cap the maximum page size, and return links or a cursor in the response.

GET /orders?limit=20&cursor=eyJ0IjoiMjAyNi0xMS0xNyIsImlkIjo5MX0
{ "items": [ ... ], "next": "eyJ0IjoiMjAyNi0xMS0xNiIsImlkIjo3MX0" }
Likely follow-ups
  • How to give a total count cheaply? Often you do not: show "more" instead. An exact count on a big table is expensive; use an estimate or a cached count if the UI really needs it.
How do you design filtering, sorting and field selection? Intermediate

What the interviewer is testing: practical API ergonomics and protection of the database.

Keep it in query parameters on the collection. Filtering by equality is simple: ?status=SHIPPED&customerId=7. For ranges use a clear convention, such as ?createdFrom=2026-01-01&createdTo=2026-01-31, or operators like ?price[gte]=10. Sorting: ?sort=-createdAt,name (minus for descending). Field selection or sparse fieldsets: ?fields=id,status,total, which saves bandwidth for big resources. Full-text search: ?q=laptop, usually backed by a search engine.

Guard the system. Allow only a whitelist of filter and sort fields, and make sure each one has an index. Otherwise a client can sort by an unindexed column on a 100-million-row table and bring the database down. Limit page size, validate values, and never build SQL from raw parameters (SQL injection). For very complex queries, consider a dedicated search endpoint with a POST body, or GraphQL.

What does "stateless" mean for a REST service, and where does the state go? Basic

What the interviewer is testing: the property that lets a service scale horizontally.

Stateless means the server keeps no client conversation state between requests. Each request has everything needed to process it: credentials (a token), the resource id and the parameters. Any instance can handle any request, so a load balancer can send requests anywhere, instances can be added or killed freely, and failover is simple. It does not mean the system has no state. State still exists, but it lives in the right places: the database for business data, a shared cache such as Redis for sessions if you must have them, and the client for its own UI state.

Signed tokens like JWT help here because the user's identity travels with each request, with no server-side session lookup. Sticky sessions (routing a user to the same instance) are a workaround that hurts scaling and failover, so avoid them in new designs.

7. REST in depth: versioning, caching, concurrency and security

What are the ways to version a REST API, and which do you prefer? Intermediate

What the interviewer is testing: trade-offs, and that versioning is the last resort.

Options: URI path (/v1/orders) is the most common. It is obvious, easy to route, cache and test in a browser, but the URL of a resource changes between versions. Header versioning (Api-Version: 2) or media type versioning (Accept: application/vnd.shop.v2+json) keeps URLs stable and is purer, but is harder to test, to cache (needs Vary) and to explain. Query parameter (?version=2) is easy but easily ignored by caches and is not liked much.

I prefer path versioning with major versions only, for its simplicity, and I try hard not to need it. Most changes should be additive and backward compatible, so the same version keeps working. Create v2 only for a real breaking change, run both versions for an announced deprecation period (use Deprecation and Sunset headers and tell consumers), watch usage of v1, and then retire it. Do not create a new version for every release, since each version is something you must maintain, test and secure.

Likely follow-ups
  • Is adding a field a breaking change? Not if clients ignore unknown fields, which is why the contract must say so.
What is HATEOAS, and do you actually use it? Intermediate

What the interviewer is testing: theory versus pragmatic judgement.

HATEOAS (Hypermedia As The Engine Of Application State) means the server's responses include links that tell the client what it can do next, so the client follows links instead of building URLs from documentation. For example, an order response has a cancel link only when the order can still be cancelled. The client just checks whether the link is present. That moves business rules (when can I cancel?) to the server and lets the server change URLs without breaking clients.

{ "id": 42, "status": "PENDING", "total": 99.5,
  "_links": {
    "self":   { "href": "/orders/42" },
    "cancel": { "href": "/orders/42/cancellation", "method": "POST" },
    "pay":    { "href": "/orders/42/payment", "method": "POST" } } }

In practice it is the least used REST constraint. Few client developers follow links dynamically. They read the documentation and hard-code paths. Links add size and effort, and there is no single standard (HAL, JSON:API, Siren). I use it where it clearly helps: pagination links (next, prev), links to related resources, and "allowed actions" for workflow-heavy resources. I would not insist on full HATEOAS for an internal API.

How does HTTP caching work? Explain Cache-Control, ETag and conditional requests. Intermediate

What the interviewer is testing: using HTTP's built-in caching to cut load and latency.

Two ideas: freshness and validation. With Cache-Control: max-age=60, the client or a shared cache (CDN, proxy) may reuse the response for 60 seconds without asking the server. public allows shared caches, private only the user's own browser (for personal data), no-store forbids storing at all (for sensitive data), no-cache means "store it but check with the server before every reuse". After the response becomes stale, validation avoids sending the body again. The server gives an ETag (a fingerprint of the content, or a version). The client sends it back with If-None-Match. If nothing changed, the server replies 304 Not Modified with no body. Last-Modified and If-Modified-Since do the same with timestamps, but are less precise.

Likely follow-ups
  • What does Vary do? It says which request headers change the response (such as Accept-Language or Authorization), so caches keep separate copies.
  • Can you cache authenticated responses? Only with private, never public, unless the cache key includes the user.
How do you stop two clients from overwriting each other's updates in a REST API? Senior

What the interviewer is testing: optimistic concurrency with HTTP preconditions.

The problem is the lost update: client A and B both read order 42, both change it, and the second PUT silently overwrites the first. Fix it with optimistic concurrency using ETags. On GET the server returns an ETag (a version or hash). When the client updates, it sends If-Match: "v7". The server compares it with the current version. If equal, it applies the change and returns a new ETag. If different, someone else changed the resource, so it returns 412 Precondition Failed, and the client must re-read, merge and retry. If a client sends no If-Match on an API that requires it, return 428 Precondition Required.

On the database side this maps to a version column and an update such as where id = ? and version = ?, checking that one row was updated. It does not lock anything, so it scales well and fits the web, where a client can disappear. Use pessimistic locks only for short, high-contention sections.

How do you make a POST safe to retry? Explain idempotency keys, with the duplicate payment case. Senior

What the interviewer is testing: a complete and correct design of idempotent POST, including concurrency and storage.

The client generates a unique key (a UUID) for each logical operation and sends it in a header, such as Idempotency-Key: 7c9e.... It reuses the same key when it retries. The server, before doing the work, looks up the key. If not found, it records the key as "in progress", does the work, saves the response (status and body) with the key, and returns it. If found and complete, it returns the saved response without redoing the work. If found and in progress (a parallel duplicate), it returns 409 Conflict or waits briefly. If the same key comes with a different request body, it is a client bug and the server returns 422.

Details that matter: the check-and-insert must be atomic, with a unique constraint on the key, otherwise two parallel retries both pass. Store the key together with the business change in one database transaction where possible. Scope keys per client or account. Keep them for about 24 hours or longer. Payment providers like Stripe use exactly this design. Note that this protects against retries of the same intent, not against a user deliberately making two payments.

Likely follow-ups
  • Does the server need a key if the operation is a PUT? No, PUT is naturally idempotent.
How do you communicate rate limits to API clients? Intermediate

What the interviewer is testing: client-friendly limits.

When a client exceeds the limit, return 429 Too Many Requests with a Retry-After header (seconds to wait or a date) and a problem+json body. It is also kind to tell clients their quota before they hit it, using headers such as RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset (an IETF draft, with many APIs still using X-RateLimit-* names). Document limits per plan and per endpoint, and apply stricter limits to expensive endpoints (search, export) and to sensitive ones (login, password reset).

Good clients read these headers, slow down, and use backoff with jitter. For different customers use different tiers, and keep a separate burst allowance. Also consider limiting by cost and not only by count: a request that triggers a heavy query counts for more. A 503 is for the server being overloaded in general, while 429 is for one client being over its quota.

What are the main security risks for a REST API and how do you defend against them? Senior

What the interviewer is testing: practical API security, following the OWASP API Security Top 10.

The biggest risk is broken object-level authorisation: a user changes the id in /orders/42 to /orders/43 and sees someone else's data. Defence: check on every request that this user may access this object, in the service that owns the data, not only at the gateway. Next is broken authentication: weak tokens, no expiry, tokens in URLs. Use standard flows, short-lived tokens and TLS everywhere. Excessive data exposure and mass assignment: returning whole entities or binding request JSON straight to a model lets a client read or set fields like isAdmin. Use explicit request and response DTOs with only allowed fields.

Also: lack of rate limiting (abuse, brute force, scraping); injection (always use parameterised queries, validate input type, size and range); security misconfiguration (verbose errors, open CORS, default credentials); improper inventory (old versions and forgotten endpoints still running, so keep an API catalogue); and unsafe consumption of other APIs (validate what third parties send). Add audit logging, secrets management, dependency scanning and least privilege for service accounts.

Likely follow-ups
  • Is hiding ids with UUIDs a defence? Only slightly. It is obscurity, so authorisation checks are still required.
What is CORS and why does it cause errors in browser calls? Intermediate

What the interviewer is testing: the browser security model, which every API developer meets.

Browsers apply the same-origin policy: a script from https://app.example.com may not read responses from a different origin (different scheme, host or port), such as https://api.example.com. CORS (Cross-Origin Resource Sharing) is the way the API server opts in to allow it. The server sends headers such as Access-Control-Allow-Origin: https://app.example.com. For requests that could change things, such as PUT, DELETE, or custom headers like Authorization, the browser first sends a preflight request, an OPTIONS call asking "is this allowed?". The server answers with allowed methods, headers and a max-age for caching that answer.

Key points: CORS is enforced by the browser only. curl and servers ignore it. It protects users, not the API, so it is not a replacement for authentication. Do not use * with credentials, and do not blindly echo any origin back. Use an explicit allow-list. A typical error "blocked by CORS policy" means the server did not return the right headers, often because the preflight failed or was blocked by the gateway or auth filter before reaching CORS handling.

What is content negotiation, and how do Accept and Content-Type work? Basic

What the interviewer is testing: basic HTTP header literacy.

Content-Type describes the format of the body being sent, in a request or response, such as application/json. Accept is sent by the client and lists the formats it can handle and prefers (Accept: application/json, application/xml;q=0.5). The server picks one and sets Content-Type in the response. If it cannot produce any of them, it returns 406 Not Acceptable. If the client sends a body in a format the server cannot read, the server returns 415 Unsupported Media Type. Similar headers exist for language (Accept-Language) and compression (Accept-Encoding: gzip).

When the response depends on a request header, the server adds Vary so caches store separate versions. Always send an explicit charset-aware type and avoid guessing the type from the file name.

What is the Richardson maturity model? Intermediate

What the interviewer is testing: vocabulary to describe how RESTful an API is.

It rates web APIs in four levels. Level 0: one endpoint and one method (usually POST) carrying commands, like old SOAP or RPC over HTTP. Level 1: separate resources with their own URLs, but still often one verb. Level 2: proper use of HTTP methods and status codes on those resources (GET to read, POST to create, DELETE to delete, 404 for missing). Level 3: hypermedia controls, the responses include links to next actions (HATEOAS).

Most good real-world APIs sit at level 2, and that is a reasonable target. Level 3 is the full REST definition by Fielding. The model is a way to talk about design, not a quality score.

How do you deprecate and retire an API endpoint or version responsibly? Intermediate

What the interviewer is testing: managing consumers you do not control.

First, measure who uses the old endpoint: log client id and version per request. Then announce: documentation, email to registered owners, and a date. Add machine-readable signals to responses: the Deprecation header (when it was deprecated), the Sunset header (RFC 8594, the date it will stop working) and a Link header pointing to the migration guide. Offer a replacement and a clear migration path, and keep both working for a defined period, long enough for external clients (months, not days).

As the date approaches, contact the remaining heavy users directly. Before switching off, you can run "brownouts": short planned outages that make forgotten clients visible. After the date, return 410 Gone with a pointer to the new API, and later remove the code. Never retire without checking real traffic first.

8. REST, gRPC, GraphQL, OpenAPI and special cases

Compare REST, gRPC and GraphQL. When do you pick each? Intermediate

What the interviewer is testing: judgement on API style, not fashion.

REST: resource oriented, JSON over HTTP, human-readable, cacheable by HTTP, works with any client, huge tooling. Weak spots: over-fetching (too many fields), under-fetching (several calls for one screen), and no strict contract unless you add OpenAPI. Best for public and partner APIs and simple CRUD. gRPC: RPC with a strict .proto schema, binary Protocol Buffers over HTTP/2, small and fast, streaming in both directions, deadlines, generated clients. Weak spots: not readable by hand, limited browser support, harder caching. Best for internal service-to-service calls with low latency and strong contracts. GraphQL: one endpoint and a typed schema, the client asks exactly the fields it needs, even across related objects, in one request. Weak spots: caching is harder (usually POST), the N+1 query problem on the server, query cost control (clients can send expensive queries), and more complexity. Best when many different clients need flexible views over a rich graph of data, such as mobile and web apps.

What is the N+1 problem in GraphQL, and how do you solve it? Senior

What the interviewer is testing: the main server-side performance trap of GraphQL.

GraphQL resolves each field with its own function. Suppose a query asks for 50 posts and the author of each post. The first resolver loads 50 posts with one query. Then the author resolver runs once per post, so 50 more queries, hence 1+N. With nested levels it gets much worse. The fix is batching with a DataLoader: the author resolver does not query at once. It asks the loader for author id 7. The loader collects all ids requested in the same tick, then runs one query (where id in (...)) and also caches results within the request. So 50 queries become 1 or 2.

Also protect the server: set limits on query depth and complexity, use persisted queries (only pre-approved queries run), add timeouts, and apply authorisation in resolvers per field. Without these, a client can send a deeply nested query that costs a lot.

What is OpenAPI and how do you use it in practice? Intermediate

What the interviewer is testing: contract-first thinking and tooling.

OpenAPI (formerly Swagger) is a standard, language-neutral way to describe a REST API in YAML or JSON: paths, methods, parameters, request and response schemas, status codes, security schemes and examples. It is the contract between provider and consumers. The current version is 3.1, which aligns schemas with JSON Schema. From one document you can generate interactive documentation (Swagger UI, Redoc), client SDKs, server stubs, mock servers, request validators and contract tests.

There are two ways to work. Design-first: write and review the OpenAPI file first, agree with consumers, then implement. It gives a stable contract and lets frontend and backend work in parallel. Code-first: annotate code and generate the spec (springdoc in Spring, for example). It is quicker, but the spec may drift or reflect accidental details. Either way, keep the spec in version control, lint it (Spectral), and in CI check that changes are backward compatible with a diff tool, so a breaking change is caught in the pull request.

paths:
  /orders/{id}:
    get:
      summary: Get one order
      parameters:
        - { name: id, in: path, required: true, schema: { type: string } }
      responses:
        "200": { description: OK }
        "404": { description: Not found }
How do you design an API for a long-running operation, such as generating a report? Senior

What the interviewer is testing: asynchronous request-reply over HTTP.

Do not hold the HTTP connection open for minutes. The connection or a proxy will time out, and the client cannot tell what happened. Instead, accept the work and give the client a way to follow it. The client sends POST /reports. The server validates, queues the job, and replies at once with 202 Accepted and a Location header for a status resource, like /reports/jobs/123. The client polls GET /reports/jobs/123, which returns the state (QUEUED, RUNNING, SUCCEEDED, FAILED), progress, and, when done, a link to the result (/reports/456). A common detail: while running return 200 with the status and maybe a Retry-After hint, and when finished return 303 See Other to the result or include its URL.

Other ways to tell the client: a webhook callback URL given in the request, or a push channel (SSE or WebSocket), so the client does not poll. Make the POST idempotent with a key so a retry does not start the job twice. Support cancellation (DELETE on the job), keep results for a limited time, and make jobs survive restarts by storing state in a database or a queue.

How do you handle file upload and download in an API, including large files? Intermediate

What the interviewer is testing: not pushing big binaries through your application servers.

For small files, a multipart/form-data POST works: the file and its metadata in one request. Set a maximum size, check the content type by inspecting the bytes (not just the file name), scan for malware, and store a generated name, never the user's raw file name (path traversal). For large files, avoid streaming everything through your service. A better design is the pre-signed URL pattern: the client asks the API for an upload URL, the API checks permissions and returns a short-lived signed URL for object storage (S3 or similar), and the client uploads directly to storage. Then the client (or a storage event) tells the API that the upload is done, and the API records the metadata. This saves your servers' bandwidth and memory.

For very big files add chunked or resumable upload (multipart upload in S3, or the tus protocol) so a network break only repeats one part, and verify integrity with a checksum. For download, use streaming and Range requests (206 Partial Content) so clients can resume, set Content-Disposition, and use signed, expiring URLs or a CDN for protected files.

How do you design bulk operations (create or update many items in one call)? Intermediate

What the interviewer is testing: partial failure handling, which is the hard part.

Sending 1,000 separate requests is slow and chatty, so a bulk endpoint helps, such as POST /orders/bulk or a batch resource with an array. The key design question is what happens when some items fail. Two options: all or nothing (one transaction, any error fails the whole batch, simple but harsh) or partial success, where each item is processed on its own and the response reports per-item results. For partial success the usual reply is 207 Multi-Status or a plain 200 with a result array listing id or index, status and error for each item, so the client can retry only the failed ones.

Also: limit the batch size (say 100 to 1000), make it idempotent (a key for the whole batch and per-item keys), keep the order of results the same as the input, and for very large batches switch to the asynchronous pattern (202 and a job) or a file import. Be careful with timeouts and database locks from huge transactions.

How do webhooks work, and how do you make them reliable and secure? Intermediate

What the interviewer is testing: event delivery to external systems over HTTP.

A webhook is a callback: instead of the client polling for changes, you register a URL, and when something happens the provider sends an HTTP POST with the event to that URL. It is simple and near real-time. Since the receiver may be down, the sender must treat it as at-least-once delivery: retry with exponential backoff for some hours or days, then mark the endpoint as failing and tell the owner. Because retries cause duplicates, each event carries a unique id so the receiver can deduplicate, and events may arrive out of order, so include a timestamp or sequence and let the receiver fetch the latest state if needed.

Security: the receiver must verify that the call is really from the provider, using a shared secret to compute an HMAC signature of the body (sent in a header, with a timestamp to stop replay), and use HTTPS. The sender must protect itself against SSRF (a customer registering an internal address as a URL) by blocking private IP ranges. The receiver should answer 2xx fast and process the event asynchronously, otherwise the sender's timeout triggers more retries.

Your mobile app makes eight REST calls to render one screen and is slow. What are your options? Intermediate

What the interviewer is testing: fixing under-fetching without breaking the resource model.

First measure which calls are necessary and which can be parallel. Options, from least to most work: run independent calls in parallel and cache what is stable; use HTTP caching and compression; add field selection or expansion (?expand=items,customer) so one call returns related data; create a BFF endpoint tailored to that screen that calls the services in the data centre (fast network) and returns one compact response; or adopt GraphQL where the client states what it needs. On slow mobile networks the number of round trips matters more than payload size, and HTTP/2 or HTTP/3 helps by multiplexing.

Avoid the temptation to turn every REST resource into a custom "screen" endpoint in the core services. Keep the domain APIs clean and put the screen-specific aggregation in the BFF layer.

How do you push updates to clients: polling, long polling, SSE or WebSocket? Intermediate

What the interviewer is testing: choosing the simplest option that works.

Polling: the client asks every few seconds. It is simple and works everywhere, but wastes requests and has delay. Long polling: the server holds the request open until there is news or a timeout, then the client asks again. It is more timely, but ties up connections. Server-Sent Events (SSE): one long-lived HTTP response where the server streams events one way to the browser, with automatic reconnect. It is simple, works over normal HTTP and is great for notifications and live dashboards. WebSocket: a full two-way connection after an HTTP upgrade. It is best for chat, games and collaborative editing, but needs more care for scaling (many open connections, sticky routing, a pub-sub layer between instances), authentication on connect and heartbeat handling.

My default: polling for slow-changing data, SSE for one-way server push, and WebSocket only when you really need two-way low latency messages.

9. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

One service becomes slow and within minutes the whole platform is down (cascading failure). What do you do? Senior

What the interviewer is testing: incident handling and knowing the resilience patterns by cause.

Situation: the Recommendation service answers in 20 seconds instead of 100 ms. Callers have no timeout, so their threads wait. Thread pools fill up, the callers stop answering their own callers, and the slowdown spreads up to the gateway.

Check first: open the dashboards for error rate and latency per service, and a trace of a slow request, to find the first service that went bad (the root, not the loudest victim). Check recent deployments and config changes, and look at thread pool and connection pool saturation in the victims.

Steps: stop the bleeding first. Roll back the recent change if there is one. Turn off the non-critical dependency with a feature flag, or open a circuit breaker manually, so callers use a fallback. Shed load at the gateway (return 503 for low-priority routes). Scale the sick service only if the cause is load and not a bug, because scaling a service with a slow database makes the database worse. Then fix the cause.

Prevention: timeouts on every call (shorter than the caller's own), circuit breakers with fallbacks, bulkheads so each dependency has its own pool, limits on queues, load shedding, and a clear list of critical versus optional dependencies. Run game days or fault injection tests, and write the incident review without blame.

A customer was charged twice for one order. How did it happen and how do you fix and prevent it? Senior

What the interviewer is testing: idempotency and the at-least-once reality.

Situation: support reports two identical charges a few seconds apart for order 8841.

Check first: find both charge records and compare timestamps, request ids and trace ids. Typical causes: the client timed out and retried the POST; a gateway or mesh retried automatically a non-idempotent call; the user double-clicked; or a message queue redelivered a "charge" command after the consumer crashed before acknowledging. The trace shows which one it was.

Steps now: refund the duplicate (a compensating action, itself idempotent), apologise, and list other affected orders by querying for duplicates (same order id and amount within a short window). Fix: require an idempotency key on the charge endpoint, with a unique constraint, so a retry returns the first result. For queue consumers, store processed message ids in the same transaction as the charge. Pass the idempotency key on to the payment provider (most support it). Disable the double click in the UI as a courtesy, not as the real protection. Check that gateway retries are only for idempotent methods.

Prevention: a reconciliation job that compares your records to the provider's daily and alerts on duplicates, and a test that sends the same request twice in parallel.

One downstream service is slow but not down, and it drags your service with it. What do you do? Senior

What the interviewer is testing: the "slow is worse than down" insight.

Situation: the Tax service now takes 8 seconds per call. It is not failing, so health checks pass and nothing looks broken, but your checkout latency and thread usage climb.

Check first: latency percentiles (p95, p99) per dependency, in-flight request counts, and thread and connection pool usage. A slow service holds resources longer, so by Little's law the number of busy threads grows, even with unchanged traffic.

Steps: lower the timeout for that call to something reasonable (a bit above its normal p99) so you fail fast. Treat slow calls as failures in the circuit breaker (a slow-call-rate threshold), so it opens. Use a bulkhead to cap how many threads Tax can take. Provide a fallback: a cached or estimated tax, flagged for later correction, if the business allows it. If the call is optional, skip it or do it asynchronously. Talk to the owning team and give them the trace.

Prevention: alerts on dependency latency and not only errors, per-dependency pools, tested fallbacks, and agreed latency SLOs between teams.

You deployed an API change and another team's service starts failing in production. What now, and how do you stop it happening again? Senior

What the interviewer is testing: quick rollback and contract discipline.

Situation: you renamed customerName to fullName in the Order API response. The Billing service reads customerName and now crashes on null values.

Check first: confirm the link: errors in Billing started at your deploy time, and the failing field matches your change. Steps: roll back your deployment at once, because that restores service and buys time. Do not try to hot-fix forward under pressure unless rollback is impossible. Tell the affected team and the incident channel. Then redo the change the compatible way: expand and contract. Return both customerName and fullName, ask consumers to migrate, check usage of the old field, and remove it later (or version the API).

Prevention: consumer-driven contract tests (Pact) in your pipeline that would have failed the build. An OpenAPI diff check for breaking changes. Tolerant readers in consumers (do not fail on missing optional fields). A canary release so only a small share of traffic sees a bad change first, and a registry of API consumers so you know whom to tell.

Order says PAID but the Inventory service never reserved stock. How did the data get inconsistent and how do you repair it? Senior

What the interviewer is testing: eventual consistency failures and repair strategy.

Situation: some orders are PAID, but no stock reservation exists, so the warehouse cannot ship.

Check first: follow the event path for one order: was the PaymentCompleted event written (outbox table), published (broker), and consumed (consumer logs, offsets, DLQ)? Common causes: a dual write where the service saved to the database and crashed before publishing; a consumer that threw an error and the message went to a DLQ nobody watched; a deploy that changed the event schema so the consumer could not parse it; or a consumer that treated a duplicate check wrongly and skipped real work.

Steps: find all affected orders with a query that compares the two services. Repair them by replaying the events (from the outbox, the topic, or the DLQ) into the consumer, which must be idempotent so replays are safe. If events are gone, run a one-time reconciliation script that calls the owning service API and creates the missing reservations. Tell the business which orders were delayed.

Prevention: transactional outbox, idempotent consumers, alerts on DLQ size and consumer lag, schema compatibility checks, and a scheduled reconciliation job that continuously compares the two sides and fixes or flags drift. Treat "saga stuck for more than N minutes" as an alert.

Your team says "we have 25 microservices but every release needs five teams on a call". What is wrong and what do you do? Senior

What the interviewer is testing: diagnosing a distributed monolith and fixing it step by step.

Situation: releases are coordinated, a staging environment with everything is needed to test, and an outage in one service takes others down.

Check first: draw the dependency graph from traces or gateway logs and look at three things: which services always change together in Git history, which share a database or a shared model library, and which sit in long synchronous chains. Those show the wrong boundaries.

Steps: pick the worst cluster, for example three services that always change together. Merge them into one service, because that is often the cheapest fix. For shared databases, move to one owner per table and give others an API or events. Replace long sync chains with events or local data copies. Add backward compatible API rules and contract tests so services can deploy in any order. Remove the shared business library, and generate clients from the API definition instead. Track the metric "percentage of releases that needed another team" and bring it to zero.

Prevention: boundaries from business capabilities and team ownership, a rule that every service must deploy alone, and architecture reviews before new services appear.

After a short database outage, the service stays down for 30 minutes even though the database is back. Why? Senior

What the interviewer is testing: metastable failures and retry amplification.

Situation: the database was down for two minutes. It is healthy again, but the API still returns errors and the database CPU is at 100 percent.

Check first: request rate to the service and the database compared to normal. If it is three to ten times normal, retries are the cause: clients and layers retried failed calls without backoff, and a queue of work built up. The system is stuck in a self-sustaining overload, not a real fault.

Steps: reduce load so the system can drain. Shed traffic at the gateway or return 503 with Retry-After, pause background jobs and consumers, and bring traffic back gradually (ramp up). Cold caches and empty connection pools after a restart add to the load, so warm them or limit concurrency. Once the queue is empty, recovery is quick.

Prevention: exponential backoff with jitter, a retry budget, retries at one layer only, circuit breakers, bounded queues, request deadlines so the server drops work that nobody waits for any more, and connection pool limits sized to the database. Test recovery after an outage, and not only the outage.

Customers complain that orders stay in PENDING forever. How do you find and fix stuck sagas? Senior

What the interviewer is testing: operating a workflow, with visibility and recovery.

Situation: 2 percent of orders never move from PENDING to CONFIRMED or CANCELLED.

Check first: query the saga state store (or order table) for orders in PENDING older than a threshold, and group them by the last completed step. This shows where it sticks: always after payment, for example. Look at that step's consumer logs, the DLQ, consumer lag, and timeouts. Typical causes are a lost message, a consumer error on a rare data shape, a reply that arrived but was not matched to the saga (wrong correlation id), or a missing timeout.

Steps: for current orders, retry the step (idempotent) or run the compensation to cancel and refund, depending on the business rule. Fix the root bug. Then add what was missing: a saga timeout per step, so that no saga can wait forever. After a timeout it retries a few times, then compensates or moves to a "needs attention" state with an alert.

Prevention: durable saga state, metrics for count and age of in-flight sagas, a dashboard for the stuck ones, and an orchestrator or workflow engine with built-in timers and retries. Test the unhappy paths: step failure, duplicate replies, late replies.

Events arrive out of order: a "ProfileUpdated" overwrote a newer value with an older one. What do you do? Senior

What the interviewer is testing: ordering guarantees and version-aware consumers.

Situation: a customer changed their address twice. The read model ended up with the first address.

Check first: how are events partitioned? Ordering is only guaranteed within one partition (in Kafka) for one key. If the producer did not use the customer id as the key, the two events went to different partitions and were consumed in either order. Also check for parallel consumer threads and for retries that re-deliver an old event after a newer one was processed.

Steps: short term, repair the affected rows from the source of truth. Fix the design: key events by aggregate id, process one partition sequentially per key, and make the consumer version-aware. Each event carries a version number or timestamp from the aggregate, and the consumer applies it only if it is newer than what it has stored (update ... where id = ? and version < ?), and ignores older ones. This also makes duplicates harmless.

Prevention: events with an aggregate id and a sequence number, tests that deliver events shuffled and duplicated, and a periodic reconciliation with the source.

A cache entry expires and suddenly the downstream database is overwhelmed. What happened and how do you fix it? Senior

What the interviewer is testing: cache stampede in a service context.

Situation: the product catalog service caches a popular item for 60 seconds. At the expiry, 2,000 requests miss at the same time and all query the database.

Check first: the database query rate at the same moment as cache misses on one key, which shows the stampede (also called thundering herd or dog-pile). Fixes: use request coalescing (single flight): only one request loads the value and others wait for it. Add random jitter to expiry times so many keys do not expire together. Refresh early, in the background, before expiry (refresh-ahead), or serve slightly stale data while one request refreshes (stale-while-revalidate). For very hot keys use a lock or a longer TTL. Protect the database with a limit on concurrent queries and a circuit breaker.

Prevention: load test the cold-cache case, and pre-warm caches after deploys. More depth: caching failures chapter.

Users get random 401 errors, but only on some requests between services. How do you debug it? Senior

What the interviewer is testing: debugging auth across hops.

Situation: the web app works, but about 1 in 20 checkouts fails with 401 from the Payment service.

Check first: use the trace id to find which hop returned the 401, and read that service's log for the reason (expired, bad signature, wrong audience, unknown key id). Typical causes: a token that expired during a long chain or a queue delay (a background job holds the user's token for hours); clock skew between servers, so a token looks "not yet valid" or expired (allow a small leeway, about 30 to 60 seconds, and use NTP); a signing key rotation where one service still has the old public key cache (kid not found, so refresh the JWKS on unknown kid); or one instance with an old config that points to the wrong issuer or audience.

Steps: fix the cause found. For async work, do not carry the user's short-lived token. Use a service identity plus the user id as data, or exchange tokens at processing time.

Prevention: metrics on auth failures by reason, a JWKS cache with refresh on unknown key, health of time sync, and an integration test of key rotation.

You must rename a database column used by a service running with ten instances and zero downtime. How? Senior

What the interviewer is testing: safe schema evolution during rolling deployments.

Situation: rename phone to mobile_number. During a rolling deploy old and new code run together, so a plain rename would break the old instances at once.

Steps (expand and contract): (1) Add the new column mobile_number as nullable, a compatible change. (2) Deploy code that writes to both columns and reads the old one. (3) Backfill old rows in small batches, to avoid long locks. (4) Deploy code that reads the new column, still writing both. (5) After checking that nothing reads the old column, deploy code that writes only the new one. (6) Drop the old column in a later release. Each step is deployable and can be rolled back.

Watch for: large backfills, locks (add columns without defaults that rewrite the table on older database versions), and other consumers such as reporting jobs that read the column. Prevention: a migration tool (Flyway or Liquibase) in the pipeline, a rule that migrations must be backward compatible with the previous app version, and a review checklist for schema changes.

One customer's batch job floods your API and other customers see timeouts. What do you do? Senior

What the interviewer is testing: fairness, rate limiting and isolation in a multi-tenant API.

Situation: tenant T-77 started an import calling your API at 2,000 requests per second. Everyone else slows down.

Check first: request counts by tenant or API key at the gateway, and which endpoints are hit. Confirm the traffic is legitimate and not an attack.

Steps now: apply a per-tenant rate limit or lower their quota at the gateway, returning 429 with Retry-After, and contact the customer. Move heavy endpoints for that tenant to a separate queue or pool if needed. Fix: per-tenant quotas by plan with burst allowance, concurrency limits per tenant (so slow queries cannot take all threads), a bulk or async import API so customers do not hammer single-item endpoints, and weighted fair queueing for background work. For critical large customers consider dedicated capacity (a cell or separate deployment).

Prevention: dashboards by tenant, alerts on unusual share of traffic, and clear documentation of limits and best practice for batch use.

Two support agents edit the same customer record and one agent's changes silently disappear. How do you fix it in the API? Intermediate

What the interviewer is testing: lost update and optimistic locking.

Situation: agent A and agent B load customer 7 at the same time. A saves a new phone number. B, whose screen still shows the old data, saves a new address with a PUT of the whole record. The phone number goes back to the old value.

Check first: confirm the API uses PUT with full replacement and has no version check. Steps: add a version to the record and return it as an ETag. Require If-Match on updates. When B saves with the old ETag, the server returns 412 Precondition Failed, and the UI tells B that the record changed, reloads it, and lets B reapply the edit. Also move to PATCH so clients send only the fields they changed, which reduces conflicts. In the database, use update ... where id = ? and version = ?.

Prevention: make optimistic concurrency a default in the API guidelines, and write a test with two concurrent updates.

The API gateway has become the bottleneck and every team is blocked on changes to it. What do you do? Senior

What the interviewer is testing: keeping a shared component thin and team-owned.

Situation: the gateway contains routing for 40 services, custom transformation scripts, and some business rules. A change needs the platform team, and one bad deploy affects all traffic.

Check first: what logic lives in the gateway? Sort it into cross-cutting (auth, rate limits, TLS, routing) and business logic. Check the latency it adds and its CPU use.

Steps: move business logic and data aggregation out into services or BFFs owned by product teams. Keep the gateway for cross-cutting policy and configuration. Make routing configuration declarative and in Git, with each team owning its own routes through self-service pull requests and automated validation, so the platform team is not a gate. Split into several gateways if needed (one per domain or per client type), and run enough replicas with canary deploys for gateway config changes. Add per-route metrics.

Prevention: a rule that the gateway has no business logic, review of every new plugin, and load tests for the gateway itself.

A user asks to delete their data, but their data is in 12 services and in an event log. What is your approach? Senior

What the interviewer is testing: data ownership applied to privacy requirements.

Situation: under privacy law (such as GDPR) a user requests erasure. Their personal data was copied into read models, caches, search indexes, backups and event streams.

Check first: use a data inventory: which service is the owner of personal data, and which services hold copies. Without the inventory you cannot promise deletion.

Steps: the owning service starts the process and publishes a UserErasureRequested event. Each service that holds a copy deletes or anonymises it, and reports the result. Track completion in a workflow with retries and an audit record. For immutable event logs, avoid storing personal data directly in events: store a reference id, or encrypt personal fields with a per-user key (crypto-shredding) and delete the key. Handle backups by expiry policy, documented. Respect legal retention rules, for example invoices that must be kept.

Prevention: design with privacy in mind: minimise copies, keep personal data in few services, tag fields in schemas as personal, and test the deletion flow regularly.

A list endpoint was fast in testing but times out in production with a big customer. How do you investigate and fix it? Intermediate

What the interviewer is testing: practical API performance work on pagination and queries.

Situation: GET /orders?customerId=... returns all orders and takes 40 seconds for a customer with 2 million orders.

Check first: the slow query log and the query plan for the underlying SQL, the response size, and whether the endpoint is paginated at all. Typical causes: no limit, a missing index on the filter and sort columns, an offset on a deep page, or an N+1 pattern where the code loads related items in a loop.

Steps: add mandatory pagination with a maximum page size, switch to cursor pagination for deep lists, add a composite index matching the filter and sort order (for example (customer_id, created_at desc, id desc)), replace the N+1 with a join or a batched query, return only needed fields, and compress responses. For exports, offer an asynchronous export job instead of a giant response.

Prevention: performance tests with production-like data volumes, and API guidelines that make pagination and bounded queries the default for every collection.

A database password was committed to the Git repository of a service. What do you do? Intermediate

What the interviewer is testing: security incident reflexes.

Situation: a developer pushed application.yml with a production database password. The repository is accessible to many people and possibly mirrored.

Steps: assume the secret is compromised, since removing it from Git does not remove it from history, forks or clones. Rotate the password immediately: create a new credential, deploy it through the secret manager, and disable the old one. Check the database and access logs for use of the leaked credential in the exposure window. Tell the security team, as per the incident process. Then clean the repository history if policy requires it (it does not replace the rotation).

Prevention: keep secrets in a secret manager and inject them at runtime, add secret scanning in pre-commit hooks and in CI, use short-lived credentials, separate credentials per service and environment with least privilege, and keep config files in the repository free of real values.
