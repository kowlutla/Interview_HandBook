Distributed Systems interview questions

The questions senior developers really get asked: CAP and consistency, replication, sharding, consensus, distributed transactions, idempotency, retries, rate limiting, caching and production incidents. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

Mental model: the 8 ideas everything hangs on

One line: a distributed system is many computers that fail separately, talking over a network that can lose, delay, duplicate and reorder messages, with no shared clock. Every hard question is about what you do when you cannot tell "slow" from "dead".
  1. Partial failure. One machine either works or crashes. In a distributed system part of it can be broken while the rest runs, and you often cannot tell which part.
  2. Unreliable network. A message can be lost, delayed, delivered twice or arrive out of order. If you got no reply, you do not know whether the request ran.
  3. No shared clock. Each machine has its own clock and they drift. Timestamps from two machines cannot reliably order events.
  4. Timeouts are guesses. A timeout cannot prove a node is dead. It only says "I stopped waiting".
  5. Replicate for availability, partition for scale. Copies survive failures but must be kept in step. Splitting data gives size and throughput but makes cross-node work hard.
  6. Agreement needs a majority. To decide one thing safely (leader, commit, lock owner) nodes use a quorum. Two majorities always overlap, so two conflicting decisions cannot both win.
  7. At-least-once plus idempotency beats "exactly once". Retry until you hear back and make repeats harmless.
  8. Everything is a trade-off. Consistency, availability, latency, cost. A strong answer names what you give up.

1. Failures and the basics

What is a distributed system, and why is it harder than a single-machine program? Basic

It is several computers cooperating over a network so they look like one system. It is harder because of partial failure: some nodes or links can break while the rest keep running, messages can be lost, delayed or duplicated, and there is no shared clock. So a "no reply" never tells me whether the work happened.

On one machine a call either returns or the process dies, and everything shares one memory and one clock. Across machines I get three extra problems: unreliable networks, independent failures and clock drift. Everything else on this page (retries, idempotency, quorums, fencing) exists to cope with these three. I accept the cost only for a reason: capacity beyond one machine, availability when a machine dies, or low latency near users.

Remember: partial failure plus unreliable network plus no shared clock. Do not distribute unless you must.

What are the eight fallacies of distributed computing? Which ones have hurt you most? Basic

They are false assumptions people make: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology does not change, there is one administrator, transport cost is zero, and the network is homogeneous. The three that bite most in real code are "the network is reliable", "latency is zero" and "topology does not change".

Concrete examples. Reliable network: a call without a timeout hangs a thread forever, and a retry without idempotency double-charges. Zero latency: a loop making one remote call per item turns a 1 ms local loop into 1000 ms or worse (the N+1 problem across services). Static topology: hard-coded IPs break when pods are rescheduled, and a DNS answer cached for hours points at a dead node. My habit is to give every remote call a timeout, a bounded retry policy, and a plan for "what if this is slow or gone".

Remember: every remote call can be slow, fail, or run twice. Code it that way.

How can you tell whether a remote node is dead or just slow? Intermediate

You cannot, not for certain. The usual tool is a heartbeat plus a timeout: if I hear nothing for longer than the timeout, I treat the node as failed. That is a guess, so the design must stay safe even when the guess is wrong.

A short timeout finds real crashes quickly but raises false alarms during GC pauses, network blips or load spikes. A false alarm is costly: a healthy leader gets replaced, work is duplicated, and the extra load can cause more false alarms. A long timeout is stable but slow to react. Production systems pick a middle value, and some (Cassandra, Akka) use an adaptive detector that scores suspicion based on past heartbeat gaps instead of a fixed number. The safety rule: never let a wrong "dead" verdict corrupt data. That is what fencing tokens and majority quorums are for (see the split-brain questions).

Remember: a timeout is a suspicion, not a fact. Make wrong suspicions harmless.

Each of three services has 99.9% availability and a request needs all three. What is the overall availability, and how do you improve it? Intermediate

Availabilities multiply for a chain: 0.999 x 0.999 x 0.999 is about 99.7%, which is roughly 26 hours of downtime a year instead of 8.8. Dependencies in series always make you less available than your weakest part. To improve it I remove hard dependencies, add redundancy where the dependency is parallel, or degrade gracefully.

Redundancy works the other way: two independent replicas each at 99.9% give 1 - (0.001 x 0.001) = 99.9999% if either one can serve. But the replicas must fail independently (different zones, not the same rack or the same bad deploy). Practical levers: make the call optional with a fallback (show the page without recommendations), cache the data locally, make the call asynchronous so it is off the critical path, and cut fan-out. Five 99.9% hard dependencies already give about 99.5%.

Remember: in series multiply (worse), in parallel redundancy helps (better). Fewer hard dependencies is the cheapest fix.

2. CAP, PACELC and consistency models

Explain the CAP theorem. Why is "pick two of three" misleading? Basic

CAP says that when a network partition happens (nodes cannot talk to each other), a replicated system must choose: stay consistent (linearizable) by refusing some requests, or stay available by answering with possibly stale data. "Pick two" is misleading because partitions are not optional on a real network, so the real choice is C or A, and only during a partition.

The terms are strict. Consistency here means linearizability: every read sees the latest completed write, as if there were one copy. Availability means every non-failing node answers every request. Without a partition you can have both. A CP system (etcd, ZooKeeper, HBase) refuses or errors on the minority side. An AP system (Cassandra, DynamoDB in eventual mode, DNS) answers on both sides and reconciles later, so some writes may conflict. CAP says nothing about latency or about normal operation, which is why PACELC exists. Also, the choice is per operation in many systems, not for the whole product.

Remember: partitions are a fact, so CAP is "C or A during a partition". There is no "CA" for a distributed system.

What does PACELC add to CAP, and where do common databases fall? Intermediate

PACELC says: if there is a Partition choose Availability or Consistency, Else (normal operation) choose Latency or Consistency. It adds the trade-off that matters every day: even with no partition, keeping replicas strongly consistent costs latency because writes must wait for other nodes.

Typical placements (these are defaults and can be tuned): DynamoDB and Cassandra are PA/EL (available in a partition, low latency otherwise, weaker consistency). Spanner, CockroachDB, etcd and ZooKeeper lean PC/EC (consistent always, pay latency, especially across regions). MongoDB defaults to PC/EC for primary reads, but reading from secondaries moves it towards latency. A single-region primary with an async replica is "EL" for replica reads. In an interview, naming one example per quadrant and explaining the knob (quorum size, read concern, sync vs async replication) beats reciting the acronym.

Remember: CAP is about the failure case, PACELC adds the everyday case: strong consistency costs latency even when nothing is broken.

Walk me through the consistency models from strongest to weakest. Intermediate

From strongest: linearizable (behaves like one copy, reads see the latest write), sequential (everyone sees the same order, not necessarily real-time), causal (causes are seen before effects), then session guarantees such as read-your-writes and monotonic reads, and finally eventual (replicas converge if writes stop). Stronger is easier to reason about but costs latency and availability.

A simple way to remember it is by the bug each level prevents. Linearizable: no stale reads, ever. Causal: a reply is never seen before the question it answers. Read-your-writes: I see my own update. Monotonic reads: I never see data go back in time between two reads. Eventual: only "they will agree sometime". Most systems let you pick per operation: strong for the money balance, eventual for the like counter. Remember that serializable (transactions behave as if run one by one) is a different axis: it is about multi-object transactions, not recency.

Remember: linearizable, causal, read-your-writes, eventual. Each level is named after the bug it stops.

What exactly is linearizability, and how is it different from serializability? Senior

Linearizability is a recency guarantee on a single object: once a write completes, every later read, from anywhere, sees it, as if there was one copy. Serializability is an isolation guarantee for multi-object transactions: the result equals some one-at-a-time order, but that order need not match real time. A system with both is called strict serializable (Spanner, for example).

Example: I update my profile and the call returns. A linearizable store means a friend reading afterwards cannot see the old name. A serializable-but-not-linearizable database could legally serve that friend a slightly older snapshot, as long as the transactions still look like they ran in some sequence. Linearizability is what you need for locks, leader election and unique-username checks, because they depend on "latest value" being really latest. It costs a coordination round trip (consensus or a leader read), so it is the thing you spend on small, critical data only.

Remember: linearizable = recency on one object. Serializable = isolation across many objects. Different axes.

What does "eventually consistent" really promise, and what does it not? Basic

It promises one thing: if writes stop, all replicas will converge to the same value. It does not say how long that takes, and it does not promise anything about reads in between, so I may read old data, or see updates out of order.

In practice "eventually" is usually milliseconds to a few seconds, and it gets longer under load or failure. The application must tolerate stale reads and concurrent writes: pick a conflict rule (last write wins, merge, or let the user decide), and add session guarantees where users would notice, such as read-your-writes. Good fits: counters, feeds, product catalogue, caches, DNS. Bad fits: account balances, inventory that must not go negative, anything uniqueness-related.

Remember: eventual = "they agree once things calm down". Nothing about the meantime.

A user updates their profile, refreshes, and sees the old data. How do you give read-your-writes consistency? Intermediate

The write went to the leader but the read hit a replica that had not caught up. To fix it I make sure a user reads their own recent writes from a place that has them: the leader, or a replica known to be caught up past their write.

Practical options. (1) For a short window after a write (say 10 to 30 seconds), route that user's reads to the leader. (2) Return a position token (log offset or timestamp) with the write, send it back on reads, and let a replica serve only if it has applied up to that position, otherwise wait or go to the leader. (3) Sticky routing of a user to one replica, which also gives monotonic reads (time never goes backwards) but not read-your-writes after a failover. (4) Update the client's local state right after a successful write. Watch for multi-device users: a token in one browser does not help the phone.

Remember: after a write, read from the leader or from a replica that has caught up to my write position.

If I read and write at a quorum (W + R > N), do I get linearizability? Senior

Not guaranteed. W + R > N makes the read set overlap the write set, so a read will see at least one copy of the latest completed write. But with concurrent writes, sloppy quorums, clock-based conflict resolution or partially failed writes, you can still read stale or flip-flopping values.

Example with N = 3, W = 2, R = 2. A write succeeds on node A, is still in flight to B, and the writer sees a timeout. One reader asks A and B and gets the new value; a later reader asks B and C and gets the old one, because the write is only half done. The new value appeared and then vanished, which violates linearizability. Real linearizable reads need either a read repair before returning (some stores do this per request) or consensus (Raft or Paxos based stores). Also, with a sloppy quorum (writes accepted by any reachable nodes) the overlap guarantee disappears.

Remember: quorum overlap gives "probably fresh", not "linearizable". For strict guarantees use consensus.

3. Time, ordering and IDs

Why can't you trust wall-clock time in a distributed system? Basic

Because every machine has its own clock, and they drift apart and get corrected in jumps. So "timestamp A is before timestamp B" across two machines proves nothing. I never use wall-clock timestamps from different machines to order events or decide who wins, and I use a monotonic clock to measure durations.

Quartz clocks drift by milliseconds per day. NTP (the protocol that corrects them) typically keeps machines within a few milliseconds on a good LAN and tens of milliseconds over the internet, and it can step a clock backwards or forwards. VM pauses, leap seconds and sleeping laptops add more jumps. In Java use System.nanoTime() (monotonic, only for elapsed time) for timeouts and currentTimeMillis() only for display. For ordering, use a logical clock, a version number, a database sequence, or a consensus log, not "latest timestamp".

Remember: wall clock for humans, monotonic clock for durations, logical clocks or versions for ordering.

What is the happens-before relation, and how do Lamport clocks use it? What can they not tell you? Intermediate

Event A happens-before B if they are on the same node with A first, or A is a message send and B its receive, or through a chain of those. A Lamport clock is a counter that respects this: if A happens-before B, then timestamp(A) is less than timestamp(B). The reverse is not true, so a Lamport clock cannot tell me whether two events were concurrent.

The rule is tiny. Each node keeps a counter. Increment it on every local event. Put it on every outgoing message. On receive set counter = max(own, received) + 1. Break ties by node id to get a total order. That gives a consistent ordering (used for example in simple distributed mutual exclusion and total-order broadcast), but if I see timestamps 5 and 7, I cannot tell whether event 5 caused event 7 or they were unrelated. For that you need vector clocks.

Remember: Lamport: causal implies smaller number, but smaller number does not imply causal. Counter = max + 1 on receive.

How do vector clocks work, and how do they detect conflicts? Senior

A vector clock keeps one counter per node. A version A is older than B if every counter in A is less than or equal to the matching counter in B. If neither is older, the two versions are concurrent, which means a real conflict that the system or application must resolve.

Example with nodes X and Y. Value v1 has [X:1, Y:0]. Client 1 updates via X to get [X:2, Y:0]. Client 2, who only saw v1, updates via Y to get [X:1, Y:1]. Neither dominates the other, so they are siblings. Dynamo-style stores (Riak, the original Dynamo) keep both and let the application merge, for example by taking the union of two shopping carts. The cost is metadata that grows with the number of writers, so real systems prune it or use dotted version vectors. Many modern stores skip this and use last-write-wins, accepting that a concurrent update can be lost.

Remember: vector clock = a counter per node. If neither version dominates, they are concurrent: merge them.

Why is last-write-wins dangerous, and what do you use instead? Intermediate

Last-write-wins (LWW) keeps the write with the highest timestamp and silently throws away the others. Since clocks on different machines disagree, a write that really happened later can lose, and truly concurrent writes lose data with no error. I use it only when losing an update is acceptable, such as a cache entry or an idempotent overwrite.

Example: a user edits their profile on two devices. Device B's clock is 200 ms behind, so its newer edit gets an older timestamp and the stale edit "wins". Safer options: a version number with compare-and-set (reject the write if the version has changed), vector clocks with an explicit merge, field-level merging, a CRDT, or routing all writes for a key through one leader so the order is decided in one place.

Remember: LWW = "silently lose one of two writes, and clock skew picks the loser". Prefer versions or merges.

How do you generate unique, roughly time-ordered IDs across many machines? Intermediate

I use a Snowflake-style 64-bit ID: a timestamp, a machine id, and a per-millisecond sequence number packed into one number. Each machine generates IDs locally with no coordination, they are unique, and they sort roughly by time. If I do not need sorting, a random UUID is simpler.

Typical Snowflake layout: 41 bits of milliseconds since a custom epoch (about 69 years), 10 bits of machine id, 12 bits of sequence (4096 IDs per millisecond per machine). Problems to mention: if a clock moves backwards the generator must wait or refuse, machine ids must be assigned uniquely (via config or a coordination service), and the order is only "roughly" time order across machines. UUIDv4 is random, so it is poor for B-tree index locality (inserts scatter); UUIDv7 and ULID put a timestamp first and fix that. A database auto-increment or sequence is fine for one database but becomes a bottleneck and a single point of failure when shared.

Remember: time bits + machine bits + sequence bits = unique without coordination. Guard against clocks going backwards.

4. Replication

Why replicate data, and what are the three replication architectures? Basic

I replicate for availability (survive a node loss), for read scalability (spread reads over copies) and for lower latency (copies near users). The three architectures are single-leader (one node takes writes, followers copy), multi-leader (several nodes take writes) and leaderless (any node takes writes, quorums decide).

Single-leader (PostgreSQL, MySQL, MongoDB, Kafka partitions) is the simplest: one place decides the write order, so there are no write conflicts. Its limits are write throughput on one node and a failover step when the leader dies. Multi-leader suits multiple regions or offline-capable clients, but concurrent writes can conflict and need a resolution rule. Leaderless (Cassandra, DynamoDB-style) has no failover at all and tolerates slow nodes, but conflict handling and stale reads become your problem. Replication keeps copies of the same data; it does not help data that is too big for one node, which is partitioning.

Remember: single-leader is the default. Go multi-leader or leaderless only for multi-region writes or extreme availability, and then plan for conflicts.

Synchronous versus asynchronous replication: what are the trade-offs? Basic

Synchronous replication makes the leader wait for follower acknowledgement before confirming a write, so no confirmed write is lost if the leader dies, but writes are slower and a dead follower can block them. Asynchronous confirms immediately and copies later, so it is fast and tolerant of slow followers, but a leader crash can lose recent writes.

Fully synchronous to every follower is rarely used: one slow node stalls everything. The common compromise is semi-synchronous: wait for one follower (or a quorum) and the rest are async, so there is always at least one up-to-date copy. Async also creates replication lag, where followers serve old data. The right choice depends on what a lost write costs: for payments use sync or quorum (PostgreSQL synchronous commit, MySQL semi-sync, Kafka acks=all with min.insync.replicas); for analytics replicas async is fine.

Remember: sync = durable but slower and fragile. Async = fast but can lose the latest writes. Semi-sync is the usual middle.

What problems does replication lag cause, and how do you handle them? Intermediate

Lag means a follower is behind the leader, so reads from it can be stale. The visible problems are: users not seeing their own writes, time appearing to go backwards between two reads, and answers that arrive before the questions they answer. I handle them with leader reads for critical paths, session guarantees and monitoring the lag.

Fixes by symptom. Not seeing my own write: read-your-writes (see that question). Time going backwards (page refresh hits a different, older replica): monotonic reads, by pinning a user to one replica. Out-of-order conversation (a reply shown before the question because they live on different shards): consistent-prefix reads or causal consistency. Also alert on lag in seconds and take a replica out of rotation when it passes a limit. A long query or big batch on a follower can itself cause lag, so watch for that.

Remember: three lag symptoms, three fixes: own writes (read-your-writes), time travel (monotonic reads), wrong order (causal or prefix).

What happens during a leader failover, and what can go wrong? Intermediate

Followers notice the leader is silent, pick the most up-to-date follower as the new leader, and redirect clients to it. The risks are losing writes the old leader had not replicated (async), two nodes believing they are leader (split brain), and flapping when the timeout is too aggressive.

Steps: detect the failure by timeout, elect a new leader (by consensus or by an operator or tool), reconfigure clients and followers, and make sure the old leader steps down if it comes back. Pitfalls. Lost writes: the new leader never saw the last few commits, and when the old leader rejoins its extra writes are discarded, which may even clash with ids already handed out. Split brain: protect with term numbers and fencing. False failover: a long GC pause triggers an election and extra load makes it worse. Many teams use automatic failover with a conservative timeout and a majority-based coordinator (Raft in Patroni via etcd, MongoDB replica set elections, Kubernetes operators).

Remember: failover = detect, elect, redirect, fence the old leader. Async replication means you can lose the last writes.

When would you use multi-leader replication, and how are write conflicts resolved? Senior

I use it when I need local writes in several regions, or when clients must write offline and sync later. The price is write conflicts: two leaders can accept different updates to the same record at the same time. I avoid conflicts by design where I can, and otherwise resolve them with a clear rule.

Avoidance first: route each record to one home region so only one leader writes it. If conflicts are possible, the options are last-write-wins (simple, loses data), merge by field or by data type (CRDTs, set union), keep both versions and ask the application or user (like a Git merge conflict), or custom logic. Conflicts are detected asynchronously, after both writes were already acknowledged, so the application cannot tell the user at write time. Other gotchas: auto-increment keys collide, and constraints (uniqueness, foreign keys) cannot be enforced across leaders. For most teams a single leader with read replicas in other regions is simpler and good enough.

Remember: multi-leader buys local writes and costs conflict handling. Avoid conflicts by routing; otherwise merge.

How does leaderless replication (Dynamo style) work? Explain quorums with N, W and R. Intermediate

The client (or a coordinator node) sends each write to N replicas and waits for W acknowledgements, and sends each read to N replicas and waits for R answers. If W + R > N, the nodes I read from must include at least one that saw the latest write, so the read can return the newest version. A typical setting is N = 3, W = 2, R = 2.

Tuning: W = N, R = 1 gives fast reads and slow writes that fail if any node is down. W = 1, R = N is the reverse. W = R = 2 of 3 tolerates one slow or dead node on both paths. Stale replicas are healed by three mechanisms: read repair (a read that sees an old copy writes the newest back), hinted handoff (a stand-in node keeps writes for a down replica and delivers them when it returns, used with sloppy quorums for higher availability but weaker guarantees), and anti-entropy (a background comparison, often with Merkle trees, to find and fix differences). Which version is newest is decided by timestamps or vector clocks, so conflicts follow the same rules as before.

Remember: W + R > N means overlap. Read repair, hinted handoff and anti-entropy keep replicas converging.

What is a CRDT, and when would you use one? Senior

A CRDT (conflict-free replicated data type) is a data structure designed so replicas can be updated independently and any merge order gives the same result. I use one when I want multi-region or offline writes without a coordinator and without losing updates, for example counters, sets and collaborative text.

Merge has to be commutative, associative and idempotent. A grow-only counter keeps one number per replica; merge takes the maximum per replica and the value is the sum. A PN-counter uses two of them for increments and decrements. A set that only grows merges by union; an OR-set tracks add tags so removes work. Where it fits: like counts, presence, shopping carts (Redis Enterprise active-active, Riak, Automerge). Where it does not: anything with a global invariant such as "balance never below zero" or "only one winner", because replicas cannot know about each other's pending changes. Cost: metadata and tombstones that grow.

Remember: CRDTs merge without coordination, but they cannot enforce a global limit.

5. Partitioning (sharding)

What is partitioning (sharding), how is it different from replication, and how do you choose the key? Basic

Partitioning splits the data so each node holds only a slice, which scales storage and write throughput. Replication keeps copies of the same data for availability. Real systems do both: split into partitions, then replicate each one. The shard key decides everything, so I pick one with high cardinality, even spread and the access pattern I query by.

Two main methods. Range partitioning (key ranges, like HBase or Spanner): range scans are cheap, but sequential keys such as timestamps pile all writes on the latest range (a hot spot). Hash partitioning (hash of the key, like Cassandra or DynamoDB): load spreads evenly, but range queries must hit every partition. A good key example: user_id for user data. A bad one: country (few values, skewed) or created_at (hot latest range). Queries that do not include the shard key become scatter-gather across all partitions, slow and costly, and joins across shards are very hard.

Remember: replication = copies, partitioning = slices. Range keeps order, hash spreads load. The key choice is the design.

Explain consistent hashing. Why is it better than hash(key) mod N, and how does rebalancing work? Intermediate

With hash(key) mod N, changing N changes the answer for almost every key, so adding one node reshuffles nearly all data. Consistent hashing puts both nodes and keys on a ring. A key belongs to the first node clockwise from it, so adding or removing a node only moves the keys next to it, about 1/N of the total.

Plain consistent hashing gives uneven slices, so each physical node is placed on the ring many times as virtual nodes (for example 100 to 256). That evens out load and lets a new node take a little from many neighbours. A bigger machine can take more virtual nodes. Replicas are typically the next R distinct nodes clockwise. The alternative is a fixed number of slots assigned to nodes: Redis Cluster has 16384 hash slots, and moving a slot moves its keys; Kafka and many databases use a fixed partition count that you move between brokers. Rebalancing then copies the moved ranges in the background and flips ownership at the end, ideally throttled so it does not hurt live traffic.

Remember: ring + clockwise owner + virtual nodes. Add or remove a node and only about 1/N of the keys move.

One partition gets far more traffic than the others (hot key or hot shard). What do you do? Intermediate

First find out whether it is one hot key (a celebrity user, a viral item) or a bad key design that sends a whole range to one shard. For a hot key I cache it in front, replicate it for reads, or split the key into several sub-keys. For a bad design I change the shard key.

Tools by cause. Hot reads on one key: in-process or Redis cache, read replicas, request coalescing. Hot writes on one key (a counter, a trending item): split into key#0 .. key#9 by adding a random suffix, write to a random one, and sum on read. Sequential keys (timestamps, auto-increment) on a range-partitioned store: hash-prefix the key or bucket it, for example by hash(user) % 16 plus time. A hot tenant: give that tenant its own shard. Hashing alone does not fix a single hot key, since the key still maps to one place. Autoscaling the whole cluster is the expensive last resort, because only one shard is hot.

Remember: diagnose the hot key vs the bad key design. Cache and replicate hot reads, split hot writes with a suffix.

How do you handle a query or transaction that spans partitions? Senior

First I try to avoid it by choosing the shard key so related data lives together, such as all of one customer's rows on one shard. If I cannot, a read becomes scatter-gather over all shards, and a write needs a distributed transaction (two-phase commit) or a saga with compensations.

Design moves: keep an aggregate in one partition (orders with their items), denormalise or duplicate data to avoid cross-shard joins, maintain a separate global secondary index or search index for lookups by another field (accepting that it is updated asynchronously), and prefer eventual consistency with sagas to 2PC for business flows. Databases that offer cross-shard transactions (Spanner, CockroachDB, Vitess with care, MongoDB multi-document) pay with extra round trips and lock holding. Latency of scatter-gather is set by the slowest shard, so it gets worse as shard count grows.

Remember: best cross-shard transaction is the one you design away with the right key. Otherwise saga over 2PC.

6. Consensus, leaders and locks

What is consensus, and where does it show up in systems you use? Basic

Consensus is getting several nodes to agree on one value, even when some nodes crash and messages are delayed. It is the building block for leader election, a replicated log, distributed locks and configuration. I rarely implement it. I use systems built on it: etcd, ZooKeeper, Consul, Kafka's KRaft controllers, and databases like Spanner or CockroachDB.

The algorithms (Paxos, Raft, ZAB) all follow the same rule: a decision needs a majority of nodes, and any two majorities overlap, so two different decisions can never both succeed. That gives safety (never two different answers) even under partitions, and progress only while a majority can talk. The price is latency (a network round trip to a majority per decision) and unavailability on the minority side. So I keep consensus for small, critical metadata (who is leader, config, locks), not for bulk data.

Remember: consensus = majority agreement on one value. Use it for small critical data, through etcd or ZooKeeper.

Why do consensus clusters use odd sizes and a majority? Basic

A majority of N nodes is floor(N/2) + 1. Any two majorities share at least one node, which prevents two conflicting decisions. Odd sizes are used because an even size adds cost without adding fault tolerance: 3 and 4 nodes both survive only one failure, and 5 and 6 both survive two.

A cluster of 2f + 1 nodes tolerates f failures. A 3-node cluster needs 2 up, a 5-node cluster needs 3 up. Even more important is what happens in a partition: with 4 nodes split 2 and 2, neither side has a majority, so the cluster stops. With 5 nodes split 3 and 2, the side with 3 carries on. More nodes also make every write slower (more acks and more messages), so 3 or 5 is the norm, 7 is rare. For multi-zone safety, spread nodes over 3 zones, so losing one zone still leaves a majority.

Remember: majority = N/2 + 1. 3 nodes tolerate 1 failure, 5 tolerate 2. Even sizes add no safety.

How does Raft work? Explain leader election and log replication. Intermediate

Raft keeps one leader at a time. Clients send writes to the leader, which appends them to its log and copies them to followers. An entry is committed when a majority has stored it, and only then applied. If followers stop hearing from the leader, one becomes a candidate and wins a new term by getting votes from a majority.

Election: each follower has a randomised election timeout (the paper suggests 150 to 300 ms). When it expires, the node increments its term (a logical epoch number), votes for itself and asks others for votes. A node gives one vote per term, and only to a candidate whose log is at least as up to date as its own. This rule means a new leader always has every committed entry. Randomised timeouts make split votes rare. Replication: the leader sends AppendEntries with the new entries (also used as heartbeat). Once a majority has the entry, the leader marks it committed and tells followers. A stale leader from an old term is rejected because its term number is lower.

Remember: terms + randomised timeouts + majority commit. The vote rule ("log at least as up to date") keeps committed entries safe.

How would you implement leader election for an application service? Intermediate

I would not write my own. I use a lock with a lease in etcd, ZooKeeper or Consul (or a framework on top, like Curator or Kubernetes leader election): each instance tries to create the same key with a time-to-live, the winner is leader and keeps renewing it, and if it dies the key expires and another instance takes over.

ZooKeeper: instances create ephemeral sequential nodes under a path, and the lowest sequence number is leader; each other watches only the one just before it, to avoid a herd of notifications. etcd: a key attached to a lease, created only if absent (compare-and-set transaction). Two safety points. The old leader may not know it lost leadership (GC pause, network issue), so any write it makes must be protected by a fencing token (the revision or term number) checked by the resource. And the leader must stop work when it cannot renew, before its lease ends. A simpler option for many apps is a database row lock or a Kubernetes Lease object.

Remember: lease on a consensus store, renew to stay leader, fencing token to be safe.

What is split brain, and how do you prevent it? Intermediate

Split brain is when two nodes both believe they are the leader and both accept writes, usually after a network partition or a long pause. It corrupts data because the two histories diverge. I prevent it with majority quorums (only the side with a majority may elect a leader), term or epoch numbers, and fencing tokens so a stale leader's writes are rejected.

A majority quorum makes two leaders in the same term impossible: the minority side cannot get enough votes. But an old leader on the minority side does not instantly learn it was replaced. It will keep trying to write until it notices. That is the gap that fencing closes: every leadership grant carries a number that only grows, and the storage layer refuses any request with an older number. Two-node setups are a trap: with no tie-breaker they cannot tell a dead peer from a partition, so add a third node or a witness. Older HA clusters use STONITH ("shoot the other node in the head"): physically power off the suspect node before taking over.

Remember: majority for deciding, fencing token for enforcing. Never run a two-node cluster without a tiebreaker.

What is a fencing token, and why is a lock or lease without one unsafe? Senior

A fencing token is a number that increases every time the lock is granted. The client sends it with every write, and the storage rejects any write with a lower token than one it has already seen. Without it, a client whose lease expired during a pause can wake up, still believe it holds the lock, and overwrite newer data.

The classic failure: client 1 gets the lock with token 33, then freezes for 40 seconds in a GC pause. The lease expires, client 2 gets token 34 and writes. Client 1 wakes up, has no way to know, and writes with token 33. The storage has already seen 34, so it rejects 33. The key point is that the check happens at the resource, not at the lock service: no timing assumption on the client can be trusted. ZooKeeper's zxid or a node's version, etcd's revision, or a database row's version column work as tokens. The resource must support the check, which is why locks over arbitrary external APIs are best-effort only.

Remember: a lock tells me who should write, a fencing token lets the resource refuse who should not.

When do you need a distributed lock, and what are the options? Intermediate

I need one only when several processes must not touch the same resource at once and a database constraint or atomic update cannot do the job. I first try to avoid the lock: a unique constraint, a conditional update or a single consumer per key is simpler and safer. If a lock is truly needed I use a lease on etcd or ZooKeeper, or Redis for efficiency-only cases.

Two different purposes. Efficiency locks avoid duplicate work (two workers both rebuilding a report): an occasional double run is fine, so Redis SET key value NX PX 30000 is enough, and release only if the value is still mine. Correctness locks protect data (one writer at a time): need a consensus store plus fencing tokens, because leases can expire during pauses. Often the lock can be replaced: UPDATE ... WHERE version = ?, a unique index (INSERT fails for the second caller), SELECT ... FOR UPDATE in a single database, or partitioning work so each key has one owner. Always set a TTL so a crashed holder does not block everyone.

Remember: prefer a constraint or conditional update to a lock. Redis lock for efficiency, consensus store plus fencing for correctness.

What is Redlock, and why is it controversial? Senior

Redlock is a Redis-based algorithm that takes the same lock on several independent Redis nodes (usually 5) and treats it as acquired if a majority granted it within a short time. It is controversial because its safety relies on bounded clock drift and bounded pauses, and it has no fencing token, so a paused client can still act after its lock expired.

The critique (Martin Kleppmann's well-known article) is that a lock for correctness needs a monotonically increasing token that the resource checks, and Redlock does not give one. Redis's author argued that it is fine for most real uses, which are efficiency locks. My position: for efficiency (avoid duplicate work) a single Redis lock or Redlock is acceptable; for correctness use ZooKeeper, etcd or a database, with fencing. Also note that a single Redis with async replication can lose a lock on failover, which is another reason not to trust it for safety.

Remember: Redlock is fine to save work, not to protect data: no fencing token, timing assumptions.

When would you use ZooKeeper, etcd or Consul, and what should you not put in them? Intermediate

I use them for small, critical coordination data: leader election, locks and leases, service discovery, and shared configuration, where I need linearizable reads and writes and change notifications. I do not use them as a general database or for high-volume data, because every write goes through consensus.

They keep a small replicated state (megabytes, not gigabytes) in memory with a consensus log, and offer watches (get told when a key changes) and ephemeral keys or leases (the key disappears when the owner dies). Limits: write throughput of a few thousand per second, latency tied to a majority round trip, and a minority side that cannot serve. Kubernetes uses etcd for all cluster state; Kafka historically used ZooKeeper and now uses its own Raft (KRaft) controllers. Keep payloads small, avoid chatty clients, and never put business data or large blobs in there.

Remember: small, critical, coordination data only. Not a database.

7. Distributed transactions, idempotency and messaging

How does two-phase commit (2PC) work, and what is its main weakness? Intermediate

A coordinator asks every participant to prepare (promise it can commit and hold its locks). If all say yes, the coordinator logs the decision and tells everyone to commit; if any says no, everyone aborts. The main weakness is blocking: if the coordinator dies after participants voted yes, they must wait, holding locks, until it returns.

After a yes vote a participant has given up the right to decide alone, so it cannot safely commit or abort by itself. That "in doubt" state can freeze rows for a long time and block other transactions. 2PC also adds latency (two round trips plus forced log writes) and couples the availability of every participant. It is fine inside one database engine or with XA across a few trusted resources; it is a poor fit across independent microservices, which is why sagas are common there. Three-phase commit reduces blocking on paper but assumes bounded delays, so it is rarely used.

Remember: prepare, then commit. Blocks if the coordinator fails after "yes". Avoid across microservices.

What is a saga, and how do orchestration and choreography differ? Intermediate

A saga splits a business transaction into a sequence of local transactions, one per service, and undoes completed steps with compensating actions if a later step fails. It gives eventual consistency without distributed locks. Orchestration has a central coordinator that tells each service what to do next; choreography has services react to each other's events with no central brain.

Example: place order, reserve stock, charge payment, ship. If payment fails, the saga runs "release stock" and "cancel order". Orchestration is easier to follow, monitor and change, but adds a central component. Choreography is loosely coupled and good for 2 to 3 steps, but the flow becomes hard to see as it grows. Rules for steps: every step and every compensation must be idempotent and retryable, since messages repeat. Compensation is a business-level undo (refund, not "delete payment"), and some actions cannot be undone (email sent, parcel shipped), so put those last or add a pending state. Saga steps are visible while in progress (stock reserved but not yet paid), so design the UI and states for that: there is no isolation.

Remember: local transactions plus compensations. Idempotent steps, no isolation, orchestrate when it gets complex.

What is the transactional outbox pattern, and what problem does it solve? Intermediate

It solves the dual-write problem: updating my database and publishing a message are two systems, so one can succeed while the other fails. With an outbox I write the business change and the event row in the same local database transaction, and a separate relay publishes the outbox rows to the broker afterwards, at least once.

The bug it fixes: save(order); publish(OrderPlaced). If the process crashes between them, the order exists but no event is ever sent. Reverse the order and you can publish an event for an order that was rolled back. With the outbox both rows commit or neither does. The relay is either a poller (select unsent rows, publish, mark as sent) or change data capture on the outbox table (Debezium reading the database log). Since the relay can publish twice after a crash, consumers must be idempotent, and the event id is the dedupe key. Cleanup of old rows is needed. Ordering per aggregate is kept by publishing in outbox order with the aggregate id as the partition key.

Remember: never write DB and broker separately. Outbox row in the same transaction, relay publishes, consumers are idempotent.

What is idempotency, and how do you make a payment API idempotent? Intermediate

An operation is idempotent if doing it twice has the same effect as doing it once. For a payment API I require a client-generated idempotency key on each request. The server stores the key with the result in a table with a unique constraint, and if the same key comes again it returns the stored response instead of charging again.

Why it matters: after a timeout the client cannot tell if the charge happened, so it must be allowed to retry safely. Flow: insert the key (unique) in the same transaction as the charge; on a duplicate key, return the saved result. Handle three cases: first call (do the work), repeat after completion (return saved response), repeat while the first is still running (return 409 or wait). Also compare the request body hash with the saved one and reject a reused key with different content. Keep keys for a time window (Stripe documents 24 hours). HTTP: GET, PUT and DELETE are meant to be idempotent, POST and PATCH are not by default. Natural idempotency is best: "set status to PAID" repeats safely, "add 10 to balance" does not.

BEGIN;
INSERT INTO idempotency(key, request_hash, status) VALUES (:k, :h, 'IN_PROGRESS');  -- unique(key)
-- on duplicate key: SELECT the stored response and return it
charge(...);
UPDATE idempotency SET status='DONE', response=:resp WHERE key=:k;
COMMIT;

Remember: unique key plus stored response. The client may retry, the server never repeats the effect.

Explain at-most-once, at-least-once and exactly-once delivery. Basic

At-most-once sends and never retries, so messages can be lost but never repeat. At-least-once retries until acknowledged, so nothing is lost but duplicates happen. Exactly-once means each message has its effect once. It cannot be guaranteed by the network alone, so in practice I build it as at-least-once delivery plus idempotent processing.

With a message consumer the ordering of "process" and "commit offset" decides the semantic. Commit first, then process: a crash loses the message (at-most-once). Process first, then commit: a crash means it is processed again (at-least-once). Choose at-least-once and handle duplicates, for example with a processed-message-id table or natural idempotent updates. At-most-once only fits data you can lose, like metrics samples.

Remember: commit before work = may lose. Commit after work = may repeat. Exactly-once = repeat plus idempotent.

Is exactly-once delivery possible? Kafka says it supports "exactly-once". What does that cover? Senior

Exactly-once delivery over an unreliable network is impossible (the Two Generals problem: the sender can never be sure the last message arrived). What is possible is exactly-once effect inside a controlled boundary. Kafka's exactly-once covers read-process-write between Kafka topics, not side effects outside Kafka like an email or a call to another API.

Kafka gives two pieces: the idempotent producer (producer id and sequence numbers let the broker drop duplicate sends caused by retries) and transactions (a consumer's output records and its offset commit are written atomically; consumers use isolation.level=read_committed to skip aborted data). Together a Kafka Streams style job gets exactly-once processing. The moment my consumer writes to a database or calls an HTTP API, the guarantee is gone, and I need an idempotent write (upsert by event id) or to store the offset together with the result in the same database transaction.

Remember: exactly-once is a boundary, not a magic property. Outside the boundary use idempotency.

How do you keep message ordering in a distributed system? Intermediate

Global ordering is expensive and rarely needed. I keep order per key: send all messages for one entity (an order, a user) to the same partition with that entity id as the key, and have one consumer thread handle a partition. Order across different keys is not guaranteed and I design so it does not matter.

Breakers of order: multiple producers without a key, a retry that lands after a later message (Kafka needs the idempotent producer, which keeps order with several in-flight requests), consumers that process one partition's messages in parallel threads, and a rebalance mid-processing. If events can still arrive out of order (different topics, retries), put a version or sequence number in each event and let the consumer ignore older ones, or buffer and reorder, or use state checks ("cancel before create": park it until the create arrives or reject safely).

Remember: order per key through the partition key. Add a version in the event for the leftover cases.

How do you prevent lost updates in read-modify-write sequences across requests or services? Intermediate

A lost update happens when two callers read the same value, both change it, and the second write overwrites the first. I prevent it by making the change atomic in the database, or by optimistic locking: add a version column and write only if the version is still what I read.

Options, simplest first. (1) Atomic statement: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0; check the row count. (2) Optimistic locking: UPDATE ... SET qty = ?, version = version + 1 WHERE id = ? AND version = ?; zero rows updated means someone else got there first, so re-read and retry (JPA @Version does this). (3) Pessimistic lock: SELECT ... FOR UPDATE, simple but holds locks and does not span services. (4) For HTTP APIs use ETag with If-Match so a stale client gets 412. (5) Across services, route all changes for the entity through one owner or one queue partition. Do not rely on an application-level "check then write" with no atomicity, nor on a distributed lock if a conditional write can do it.

Remember: atomic update or version check. Never read, compute and blindly write.

8. Resilience, retries and rate limiting

How do you choose timeouts, and what is a deadline? Intermediate

Every remote call gets a timeout, because without one a slow dependency holds my threads forever. I set it from measured latency, for example a bit above the p99 of that call, and keep the timeouts shorter as I go down the call chain. A deadline is the absolute time by which the whole request must finish, passed along so each hop knows how much time is left.

Two kinds: connect timeout (short, like 1 second) and read or request timeout. A per-hop timeout alone is not enough: if the gateway gives up after 5 seconds but the service keeps working for 10, I waste capacity on answers no one will read, and the client's retry doubles the load. With a deadline (gRPC propagates it automatically; with HTTP pass a header or remaining budget), the downstream call can fail fast or skip work when the budget is gone. The rule: the caller's timeout must be longer than the sum of what it waits for, including retries, and the outermost one is the smallest budget you give the user.

Remember: always set a timeout; callee's budget must fit inside the caller's. Pass a deadline down.

How should retries be done? What are exponential backoff with jitter and a retry storm? Intermediate

I retry only idempotent operations and only for transient errors (timeouts, 503, connection reset), with a limited number of attempts, exponential backoff (wait 100 ms, 200, 400...) and random jitter so clients do not all retry at the same moment. A retry storm is when many clients retry at once against a struggling service and keep it down.

Jitter matters: without it, a thousand clients that failed together retry together, in synchronised waves. A common formula is "full jitter": sleep = random(0, min(cap, base * 2^attempt)). Do not retry 4xx client errors. Retry at one layer only: if three layers each make up to 4 attempts (the first try plus 3 retries), one user call can become 4 x 4 x 4 = 64 calls to the bottom service. Add a retry budget (for example retries at most 10 percent of traffic), respect Retry-After, and combine with a circuit breaker.

for (int attempt = 0; attempt < MAX; attempt++) {
    try { return call(); }
    catch (TransientException e) {
        long cap = Math.min(MAX_WAIT_MS, BASE_MS << attempt);
        Thread.sleep(ThreadLocalRandom.current().nextLong(cap + 1)); // full jitter
    }
}
throw new GaveUpException();

Remember: idempotent only, bounded, exponential backoff plus jitter, retry at one layer.

What is a circuit breaker, and how do you configure it? Intermediate

A circuit breaker stops calling a dependency that is failing, so my threads are not tied up and the dependency can recover. It has three states: closed (normal), open (calls fail immediately), and half-open (a few trial calls to see if it recovered). It opens when the failure rate or slow-call rate over a window passes a threshold.

Typical settings (Resilience4j names): sliding window of 20 to 100 calls, failure rate threshold 50 percent, slow call threshold, wait duration in open state (10 to 60 s), a few permitted calls in half-open, and a minimum number of calls before judging. When open I return a fallback: cached data, a default, or a clear error. Count timeouts and 5xx, not business errors like 404. Watch out: a breaker per dependency (or per host) is better than one global one, and breaker state per instance means each instance learns separately.

Remember: closed, open, half-open. Fail fast with a fallback, probe before closing.

What are bulkheads, and how do they limit the blast radius of a slow dependency? Intermediate

A bulkhead gives each dependency its own limited pool of resources (threads, connections, semaphore permits), like watertight compartments in a ship. If one dependency becomes slow, it can only exhaust its own pool, and calls to the others still work.

Without bulkheads, one shared thread pool or connection pool is a shared fate. A slow recommendations service holds all 200 request threads, and then even login and checkout cannot get a thread: a local slowdown becomes a site-wide outage. With separate pools (say 20 threads for recommendations, 50 for payments) the slow one fills its 20 and further calls are rejected quickly while the rest of the site runs. Implementations: separate thread pools or semaphores (Resilience4j Bulkhead), separate HTTP client connection pools, separate queues per tenant or priority, even separate deployments for critical and non-critical traffic. Use together with timeouts and circuit breakers.

Remember: separate pools per dependency, so one slow neighbour cannot eat all my threads.

What is backpressure, and how is it different from load shedding? Intermediate

Backpressure is the slow consumer telling the producer to slow down, so work does not pile up without limit. Load shedding is the overloaded service deliberately rejecting some work (for example with 503 or 429) so the rest finishes on time. Backpressure pushes the problem upstream; shedding protects the service when upstream cannot or will not slow down.

Backpressure examples: a bounded queue that blocks or rejects the producer when full, reactive streams request(n), TCP windows, Kafka consumers that simply fall behind (the lag is the buffer). Unbounded queues are a trap: they hide overload until memory runs out, and by then the latency for everything is huge. Shedding rules: reject early and cheaply, drop low-priority or non-critical work first, prefer failing new requests over timing out old ones already in progress, and tell clients to back off (429 or 503 with Retry-After). Adaptive concurrency limits (limit in-flight requests based on measured latency) are an advanced version.

Remember: bounded queues everywhere. Slow the sender if you can, drop the lowest-value work if you cannot.

Compare token bucket, leaky bucket, fixed window and sliding window rate limiting. Intermediate

Token bucket refills tokens at a steady rate up to a capacity and each request takes one, so it allows short bursts but limits the average. Leaky bucket drains requests at a constant rate, smoothing bursts. Fixed window counts per time slot and is simple but allows double the limit at a boundary. Sliding window counts over the last N seconds and removes that boundary problem. I usually pick token bucket.

The fixed window flaw: with a limit of 100 per minute, a client sends 100 at 12:00:59 and 100 at 12:01:01, so 200 within two seconds. Sliding window log (store each timestamp) is exact but uses memory; sliding window counter (weighted sum of current and previous window) is a cheap approximation. Token bucket needs two numbers per client (tokens, last refill time), allows bursts up to capacity and is the common choice for APIs (used by Stripe, AWS API Gateway). Leaky bucket suits shaping traffic to a downstream system that needs a smooth rate. Reply with 429 Too Many Requests and a Retry-After header.

Remember: token bucket = average rate plus burst. Fixed window double-spends at the edge.

How do you enforce a rate limit across many servers? Senior

The usual answer is a shared counter in Redis, updated atomically with a Lua script (or INCR plus EXPIRE for fixed windows), keyed by user or API key. For very high traffic I let each node keep a local budget and sync periodically, accepting a small error. I place the limiter at the gateway so rejected requests are cheap.

Trade-offs. A central Redis check adds a network hop per request and Redis becomes a dependency: if it is down, decide to fail open (allow, risky) or fail closed (reject, safe but harmful). The read-then-write race is the classic bug: two nodes both read 99 and both allow, so the check and decrement must be one atomic operation (Lua script, or INCR then compare). Local approach: split the global limit into per-node shares, or sync counts every few hundred milliseconds, which is cheaper but allows overshoot. Other design points: limit key (user, IP, tenant, endpoint), different tiers per plan, returning remaining quota in headers (X-RateLimit-Remaining), and a separate stricter limit for expensive endpoints.

-- Redis Lua, fixed-window sketch
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return c   -- caller compares with the limit

Remember: atomic shared counter in Redis, or local budgets with periodic sync. Decide fail-open or fail-closed in advance.

9. Caching strategies and consistency

What are the common caching strategies: cache-aside, read-through, write-through and write-behind? Basic

Cache-aside: the application checks the cache, on a miss reads the database and fills the cache. It is the default and I use it most. Read-through is the same but the cache library loads the data. Write-through writes to cache and database together, so the cache is always fresh but writes are slower. Write-behind writes to the cache and saves to the database later, which is fast but can lose data.

Cache-aside is simple and resilient (the cache can be empty or down and the app still works), but the first read after a miss is slow and the cache can go stale. Write-through keeps reads fast and consistent, costing write latency and caching data that may never be read. Write-behind batches writes for speed, and risks loss if the cache node dies before flushing, so it fits counters and non-critical data. Always set a TTL (time to live) as a safety net, and decide what to cache: read-heavy, rarely changing, expensive to compute.

Remember: cache-aside by default, always with a TTL. Write-through for freshness, write-behind for speed at a loss risk.

How do you keep a cache consistent with the database? What races exist in cache-aside? Intermediate

On a write I update the database first and then delete the cache key (not update it), plus a TTL as a safety net. Deleting is safer than updating because two concurrent writers can set the cache in the wrong order. Even so a small stale window remains, so I accept eventual consistency or use versioned values.

The classic race: a reader misses, reads the old value from the database, and is slow. Meanwhile a writer updates the database and deletes the key. Then the slow reader puts the old value into the cache, and it stays stale until the TTL expires. It is rare but real. Mitigations: short TTL, delete again after a short delay (delayed double delete), store a version number in the value and refuse to overwrite with an older one, or invalidate from the database change log (CDC) so deletes follow the real commit order. Never "update the DB then update the cache" from two writers, and never delete the cache before the database update (a reader will refill the old value). If the cache delete fails, retry it or rely on TTL.

Remember: database first, then delete the key, always with a TTL. Perfect consistency needs versions or CDC.

What is a cache stampede (thundering herd), and how do you prevent it? Intermediate

A stampede happens when a hot key expires and hundreds of requests all miss at the same moment and hit the database together, which can take it down. I prevent it by letting only one request rebuild the value (single-flight or a lock), adding random jitter to TTLs, and serving slightly stale data while one refresh runs.

Three techniques. Single flight: the first request takes a short lock (in-process or SET NX in Redis) and recomputes; the others wait briefly or get the old value. TTL jitter: expire at TTL plus a random few percent, so many keys do not expire together after a deploy or a cache warm-up. Stale-while-revalidate: keep a soft TTL (when to refresh) and a hard TTL (when to drop); after the soft TTL one background refresh happens while everybody still gets the old value. For very hot keys, refresh proactively before expiry. A related issue is cache penetration (many requests for keys that do not exist): cache the "not found" result briefly or use a Bloom filter. And after a cold start, warm the cache or ramp traffic up slowly.

Remember: one rebuilder, jittered expiry, serve stale during refresh.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview. It shows you stay calm and look for causes, not only symptoms.

After a network blip, two database nodes both think they are primary and both accepted writes. What do you do? Senior

This is split brain. I stop writes to one side immediately (fence the old primary), pick the side with the more complete history as truth, then reconcile the writes the other side accepted. Long term I fix the failover design with a majority quorum and fencing, so it cannot happen again.

Situation: two primaries accepted writes for some minutes, so the data has diverged.

Check first: which node does the quorum or orchestrator consider primary, how many writes each side took, and which clients wrote to which side.

  1. Stop the bleeding: make the losing side read-only or shut it down (fence it at the network, storage or load balancer level).
  2. Keep both data sets. Compare them, then replay or merge the writes from the losing side. Conflicts such as the same order on both sides need a business decision (or a manual review for money).
  3. Rebuild the losing node as a follower from the winner.

Prevent: automatic failover only with a majority-based coordinator (a third voter or witness, not a two-node pair), term numbers, a fencing step before promotion, and clients that always find the primary through the coordinator, not a fixed address.

Remember: fence first, reconcile second, and fix failover so a majority must agree.

A customer was charged twice for one order. Where do you look, and how do you fix it for good? Senior

Almost always a retry or a redelivery without idempotency: the first call succeeded but the response was lost, and something retried. I refund the customer, find which layer retried, and add an idempotency key with a unique constraint so a repeat returns the earlier result.

Situation: two successful payment captures with the same order id, a few seconds apart.

Check first: the trace of both attempts. Same request retried by the client, gateway or service after a timeout? A double click? A message consumed twice after a consumer timeout? Did the payment provider get one idempotency key or two?

  1. Refund the duplicate and record the cause.
  2. Find the retry layer. Typical: gateway timeout is 5 s, the payment call takes 6 s, the gateway retried while the first call was still running.
  3. Generate one idempotency key per order attempt, store it with a unique constraint, and pass it to the provider (the usual Idempotency-Key header). A retry then gets the earlier result.
  4. Make the consumer idempotent too: unique constraint on (order_id, payment_type).
  5. Line up the timeouts so the inner call finishes before the outer retry starts, and a retry reuses the same key.

Prevent: a daily reconciliation of provider settlements against the ledger, an alert on two captures for one order, and a test that injects a lost response.

Watch out: removing retries (then payments get lost), or a "check if already paid" read before the write, which races.

Remember: timeout plus retry equals duplicate, unless the operation is idempotent.

Stock goes negative: two requests each read the quantity, subtract, and write back. How do you fix it? Intermediate

This is a lost update caused by read-modify-write without atomicity. I make the decrement one conditional statement in the database, UPDATE ... SET qty = qty - 1 WHERE qty > 0, and check the updated row count.

Situation: qty is 1, two buyers read 1, both write 0 and both succeed, or both subtract and the count goes below zero.

Check first: where the read and the write happen, whether they share a transaction, and the isolation level (at read committed this is possible).

  1. Replace the read then write by an atomic conditional update and treat zero rows updated as "sold out".
  2. If logic needs the value first, use a version column (optimistic lock) and retry on conflict, or SELECT ... FOR UPDATE inside one transaction.
  3. Add a CHECK (qty >= 0) constraint as a last guard.
  4. If stock is in a cache or another service, make the database the single owner of the number.

Prevent: a concurrency test with parallel buyers on the last unit.

Remember: push the check into the write itself. The database decides, not the application.

A job leader paused for 40 seconds (long GC), a new leader took over, and then the old one woke up and wrote bad data. How do you stop this class of bug? Senior

The old leader did not know its lease had expired. I fix it with fencing tokens: each leadership grant gets an increasing number, and the database or storage rejects any write carrying an older number. Shorter pauses help, but only fencing makes it safe.

Situation: leader A held a lease, froze, lease expired, B became leader and wrote, then A resumed and overwrote B's work.

Check first: GC logs and lease timestamps to confirm the pause. Check how long the lease is versus the worst pause.

  1. Use a monotonic token (etcd revision, ZooKeeper zxid, or a counter bumped on each election) and send it with every write.
  2. Make the resource reject lower tokens, for example UPDATE ... WHERE fence_token <= :mine with an update of the stored token.
  3. Have the leader check "do I still hold the lease?" right before the critical write, and stop work when a renewal fails. This narrows the window but does not close it.
  4. Tune GC and heap, and keep lease time well above normal pauses.

Prevent: a failure test that freezes the leader process (SIGSTOP) and checks that stale writes are refused.

Remember: time-based leases are not enough. The resource must enforce the token.

Checkout calls payment, then inventory, then shipping. Shipping times out after payment succeeded. What is the correct behaviour? Senior

A timeout does not mean shipping failed, so I do not blindly refund. I retry shipping idempotently or look up its state. If it truly fails, I run compensations (release stock, refund) as a saga, and the order sits in a clear pending status until it resolves.

Situation: money taken, shipping state unknown.

Check first: ask shipping for the status by the order's idempotency key. Did it create the shipment?

  1. Treat the order as PENDING_SHIPPING, not failed.
  2. Retry the shipping call with the same key and backoff. Because it is idempotent, a repeat is safe.
  3. If it fails for good (rejected, or retries exhausted), start compensation: cancel inventory reservation, refund payment, mark the order cancelled, tell the customer.
  4. Drive this with an orchestrated saga or outbox events so the process survives a crash mid-way.

Prevent: idempotent steps and compensations, a reconciliation job for orders stuck in pending, and alerts on age of pending orders.

Remember: unknown is not failed. Query or retry with the same key, compensate only on a confirmed failure.

Users say "I saved my settings, but the page shows the old values". Only some users, only sometimes. What is it? Intermediate

Most likely replication lag: the save went to the primary and the next page load read from a read replica that had not caught up. The fix is read-your-writes: read from the primary (or a caught-up replica) for a short time after a write.

Situation: intermittent stale reads right after a write, affecting a subset of users.

Check first: replica lag metrics at the incident time, whether reads use a replica pool, and whether a cache entry survived the write (the same symptom).

  1. Reproduce: write, then read in a loop, and see which backend answers.
  2. Route the writer's reads to the primary for a short window, or pass a log position and wait for a replica to reach it.
  3. If a cache is involved, delete the key after the database write.
  4. If the lag is large, find the cause: a long-running query or a big batch on the replica, or too few resources.

Prevent: alert on replica lag, expose "lag" in dashboards, and design read paths with the lag in mind.

Remember: after a write, read from the place that has it. Lag is the first suspect for "sometimes stale".

The database says an order exists, but no "OrderPlaced" event was ever published, so downstream never shipped it. Why, and how do you fix it? Senior

Classic dual write: the service saved the order and then published the event as two separate steps, and the process crashed or the broker was down in between. I fix it with a transactional outbox so the event is saved atomically with the order, and I repair the missing events from the database.

Situation: some orders in the database have no matching event on the broker.

Check first: the code path (save, then publish?), error logs around the missing orders, broker outages at that time.

  1. Repair now: find orders without a published event (by comparing database to downstream) and republish them. Consumers must be idempotent for this to be safe.
  2. Fix the design: write an outbox row in the same transaction as the order, and let a relay or CDC (Debezium) publish it with retries.
  3. Keep the event id stable so duplicates can be dropped downstream.

Prevent: a reconciliation job and an alert on the unpublished outbox row age or count.

Remember: never write the database and the broker separately. Outbox plus idempotent consumers.

A non-critical recommendations service got slow, and then the whole website went down. Explain and fix. Senior

This is a cascading failure. Callers waited on the slow service with no tight timeout, so their threads filled up, then every other endpoint on the same pool starved. I fix it with a short timeout, a circuit breaker with a fallback, and a separate bulkhead pool, so the optional feature fails alone.

Situation: latency in one dependency spread into a full outage.

Check first: thread pool and connection pool saturation on the web tier, timeout settings, retry settings (retries make it worse), and whether the page needs the data to render.

  1. Right now: turn the feature off with a flag, or have the breaker open.
  2. Set a short timeout (for example 200 to 300 ms) and a fallback (empty list or cached recommendations).
  3. Put the call in its own bulkhead (separate pool) so it cannot take all threads.
  4. Remove retry multiplication and add a retry budget.
  5. Load shed instead of queueing: reject quickly when the pool is full.

Prevent: classify dependencies as critical or optional, test with latency injection, and alert on pool saturation.

Remember: a slow dependency is worse than a dead one. Timeout, breaker, bulkhead, fallback.

A downstream service had a 30-second slowdown, but the outage lasted 40 minutes, long after it recovered. Why? Senior

A retry storm. During the slowdown clients timed out and retried, queues filled with requests nobody was waiting for, and the retry load kept the service overloaded even after the original cause was gone. The fix is backoff with jitter, retry budgets, load shedding and short queues.

Situation: the trigger was brief, but the system stayed in a bad state (a metastable failure).

Check first: request rate against the service during and after the incident (was it much above normal?), the number of retries per layer, and queue lengths.

  1. Recover: shed load (reject or drop part of the traffic), drain or purge stale queues, scale up, or temporarily disable retries to break the loop.
  2. Retry at one layer only, with exponential backoff and full jitter plus a cap on attempts and a retry budget.
  3. Use bounded queues and drop requests whose deadline already passed, since the user has gone.
  4. Add a circuit breaker so callers stop hitting a struggling service.

Prevent: load tests that include a short slowdown and recovery, and watch for retry rate in the dashboards.

Remember: retries turn a blip into an outage. Backoff, jitter, budgets, shed load.

An "OrderCancelled" event arrives at a service before the "OrderCreated" event for the same order. What happens, and how do you design for it? Senior

If the consumer assumes order, the cancel finds no order and is dropped, then the create arrives and the order is wrongly active. I prevent it by keeping order per key (same partition key), putting a version in each event, and making handlers tolerate arrival in any order.

Situation: events for one entity were reordered, for example by different topics, retries or parallel consumers.

Check first: do both events share a partition key and a topic, are retries or parallel threads in play, and does the event carry a sequence or version?

  1. Same topic, key = order id, one consumer thread per partition (idempotent producer to keep order on retries).
  2. Carry a version or sequence number. The consumer applies an event only if it is newer than the stored version and ignores older ones.
  3. For a cancel with no order yet: record a tombstone or "cancelled" marker, so the later create is applied as cancelled; or park the event and retry after a short delay.
  4. Make state transitions explicit (a small state machine) so an illegal transition is detected and handled.

Prevent: property tests that shuffle events, and a dead-letter queue for events that never resolve.

Remember: do not trust arrival order. Key by entity, carry a version, and make handlers order tolerant.
