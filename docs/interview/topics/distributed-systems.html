Mental model: the 8 ideas everything hangs on

One line: a distributed system is many computers that fail separately, talking over a network that can lose, delay, duplicate and reorder messages, with no shared clock. Every hard question is about what you do when you cannot tell "slow" from "dead".
  1. Partial failure. One machine either works or crashes. In a distributed system part of it can be broken while the rest runs, and you often cannot tell which part.
  2. Unreliable network. A message can be lost, delayed, delivered twice or arrive out of order. If you got no reply, you do not know whether the request ran.
  3. No shared clock. Each machine has its own clock and they drift. Timestamps from two machines cannot reliably order events.
  4. Timeouts are guesses. A timeout cannot prove a node is dead. It only says "I stopped waiting".
  5. Replicate for availability, partition for scale. Copies survive failures but must be kept in step. Splitting data gives size and throughput but makes cross-node work hard.
  6. Agreement needs a majority. To decide one thing safely (leader, commit, lock owner) nodes use a quorum. Two majorities always overlap, so two conflicting decisions cannot both win.
  7. At-least-once plus idempotency beats "exactly once". Retry until you hear back and make repeats harmless.
  8. Everything is a trade-off. Consistency, availability, latency, cost. A strong answer names what you give up.

1. Failures and the basics

What is a distributed system, and why is it harder than a single-machine program? Basic

It is several computers cooperating over a network so they look like one system. It is harder because of partial failure: some nodes or links can break while the rest keep running, messages can be lost, delayed or duplicated, and there is no shared clock. So a "no reply" never tells me whether the work happened.

Start with the single-machine picture. In one program, a function call either returns a result or the whole process dies. All threads share one memory and one clock, so "did it happen?" always has a clear answer. Now put the caller and the callee on two machines. The call becomes a message over a network, and the network is a third thing that can fail on its own.

Why we do it anyway. There are only three good reasons: the data or traffic does not fit on one machine (scale), one machine dying must not take the service down (availability), or users are far away and you want a copy close to them (latency). If none of these applies, a single well-sized database and a few app servers is the better design.

What gets harder, with an example. Suppose a checkout service calls a payment service and gets no answer for 2 seconds. On one machine this cannot happen. Here at least four things could be true: the request never arrived, the payment service is slow and will finish later, it finished and crashed before replying, or the reply was lost. The checkout service sees the same silence in all four cases. Whatever it does next (retry, give up, ask again later) must be correct in every case. That one problem is behind most of this page.

  • Partial failure: a part can be broken while the rest works, and you often cannot see which.
  • Unreliable network: messages get lost, delayed, duplicated or reordered.
  • No shared clock: each machine has its own time, so "which came first" is not obvious.

An interviewer usually follows up with "so what do you do about it?". The short answer is: timeouts on every call, retries made safe by idempotency, replication with quorums for state, and consensus only for the few things that need one agreed answer.

On one machine a call either returns or the process dies, and everything shares one memory and one clock. Across machines I get three extra problems: unreliable networks, independent failures and clock drift. Everything else on this page (retries, idempotency, quorums, fencing) exists to cope with these three. I accept the cost only for a reason: capacity beyond one machine, availability when a machine dies, or low latency near users.

Remember: partial failure plus unreliable network plus no shared clock. Do not distribute unless you must.

What are the eight fallacies of distributed computing? Which ones have hurt you most? Basic

They are false assumptions people make: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology does not change, there is one administrator, transport cost is zero, and the network is homogeneous. The three that bite most in real code are "the network is reliable", "latency is zero" and "topology does not change".

What the list is. In the 1990s engineers at Sun wrote down the assumptions that developers new to networking kept making. Each is false, and each one produces a bug that only appears in production. Learn them as a checklist you run over any design.

FallacyWhat actually happensWhat I do about it

Latency is zeroA same-zone call costs about 0.5 to 2 ms, a cross-region call 50 to 150 msBatch calls, avoid N+1 across services, cache
Bandwidth is infiniteLarge payloads and chatty protocols saturate linksPagination, compression, send ids not blobs
The network is secureTraffic can be sniffed or spoofed inside the data centre tooTLS and mutual auth between services
Topology does not changePods move, IPs change, DNS answers go staleService discovery, short DNS TTLs, retry on reconnect

Transport cost is zeroSerialisation costs CPU, and cross-zone traffic costs moneyEfficient formats, keep chatty traffic in one zone
The network is homogeneousMixed hardware, OS and protocol versionsBackward-compatible formats, tolerant readers

A worked N+1 example. A page shows 200 orders, and for each order the code calls the customer service to get a name. Locally that loop is microseconds. With 2 ms per call it becomes 400 ms, and under load some calls take 50 ms, so p99 explodes. The fix is one batched call (getCustomers(ids)) or keeping the name in the order row.

When asked "which hurt you most", pick one and tell a short story: what broke, how you noticed (usually a latency graph or a thread-pool exhaustion), and what you changed.

Concrete examples. Reliable network: a call without a timeout hangs a thread forever, and a retry without idempotency double-charges. Zero latency: a loop making one remote call per item turns a 1 ms local loop into 1000 ms or worse (the N+1 problem across services). Static topology: hard-coded IPs break when pods are rescheduled, and a DNS answer cached for hours points at a dead node. My habit is to give every remote call a timeout, a bounded retry policy, and a plan for "what if this is slow or gone".

Remember: every remote call can be slow, fail, or run twice. Code it that way.

How can you tell whether a remote node is dead or just slow? Intermediate

You cannot, not for certain. The usual tool is a heartbeat plus a timeout: if I hear nothing for longer than the timeout, I treat the node as failed. That is a guess, so the design must stay safe even when the guess is wrong.

Why it is impossible to be sure. The only evidence you ever get about a remote node is messages arriving from it. If messages stop, every explanation looks identical: the node crashed, the network between you dropped packets, or the node is alive but paused (a long garbage-collection pause, a swapped-out process, an overloaded CPU). Silence has no cause printed on it.

How failure detection works.

  1. Each node sends a small heartbeat every interval (say every 1 second).
  2. The watcher keeps the time of the last heartbeat.
  3. If no heartbeat arrives for the timeout (say 5 seconds), the watcher declares the node suspected or failed and starts reacting (election, removing it from a load balancer, reassigning its work).

The trade-off in numbers. With a 1 s timeout a real crash is noticed in about 1 s, but a 2 s GC pause now causes a false failover. With a 30 s timeout the false alarms disappear but every real crash means 30 s of downtime. There is no setting that is right for both, so you choose by what each mistake costs.

Adaptive detectors. Instead of "gap above 5 s", the phi accrual detector keeps a history of heartbeat gaps and outputs a suspicion level that rises smoothly the longer the silence is, relative to that node's normal rhythm. A node on a flaky link therefore gets more tolerance than one on a steady link.

The deeper point. Since a verdict can be wrong, correctness must never rely on it. The old leader that was wrongly declared dead may still be running and writing. That is why the next questions on leases and fencing tokens exist: they make a wrong verdict harmless instead of trying to make it never wrong.

A short timeout finds real crashes quickly but raises false alarms during GC pauses, network blips or load spikes. A false alarm is costly: a healthy leader gets replaced, work is duplicated, and the extra load can cause more false alarms. A long timeout is stable but slow to react. Production systems pick a middle value, and some (Cassandra, Akka) use an adaptive detector that scores suspicion based on past heartbeat gaps instead of a fixed number. The safety rule: never let a wrong "dead" verdict corrupt data. That is what fencing tokens and majority quorums are for (see the split-brain questions).

Remember: a timeout is a suspicion, not a fact. Make wrong suspicions harmless.

Each of three services has 99.9% availability and a request needs all three. What is the overall availability, and how do you improve it? Intermediate

Availabilities multiply for a chain: 0.999 x 0.999 x 0.999 is about 99.7%, which is roughly 26 hours of downtime a year instead of 8.8. Dependencies in series always make you less available than your weakest part. To improve it I remove hard dependencies, add redundancy where the dependency is parallel, or degrade gracefully.

Where the numbers come from. Availability is the fraction of time a component works. 99.9% ("three nines") means it is down 0.1% of the time, which is about 8.76 hours per year or about 43 minutes per month. If a request needs service A and B and C all working, it succeeds only when all three are up at the same moment. If their failures are independent, the probabilities multiply.

SetupCalculationResultDowntime per year
One service at 99.9%0.99999.9%about 8.8 hours
3 in series0.999 x 0.999 x 0.999about 99.7%about 26 hours
5 in series0.999 to the power 5about 99.5%about 44 hours
2 replicas in parallel1 - (0.001 x 0.001)99.9999%about 30 seconds

Reading the table. Every hard dependency you add in the request path lowers your ceiling. A service built from ten 99.9% parts cannot honestly promise 99.9%. The parallel row shows why redundancy is so powerful, but only if the two copies truly fail independently. Two replicas on the same host, or both running the same buggy release, fail together and the real number is much closer to a single copy.

How I raise availability, in order of cost.

  1. Remove the dependency from the critical path. Make the call asynchronous, or read from a local cache.
  2. Make it optional. If recommendations are down, render the page without them (graceful degradation, default value, stale data).
  3. Add redundancy across zones and load balance, so one copy dying does not matter.
  4. Add timeouts, circuit breakers and bulkheads so a slow dependency does not eat your threads and turn "slow" into "down".

Pitfall: availability numbers hide partial failure. A service that responds but with errors on 5% of requests is "up" to a ping check. Define availability by successful requests (an SLI) rather than by process liveness.

Redundancy works the other way: two independent replicas each at 99.9% give 1 - (0.001 x 0.001) = 99.9999% if either one can serve. But the replicas must fail independently (different zones, not the same rack or the same bad deploy). Practical levers: make the call optional with a fallback (show the page without recommendations), cache the data locally, make the call asynchronous so it is off the critical path, and cut fan-out. Five 99.9% hard dependencies already give about 99.5%.

Remember: in series multiply (worse), in parallel redundancy helps (better). Fewer hard dependencies is the cheapest fix.

2. CAP, PACELC and consistency models

Explain the CAP theorem. Why is "pick two of three" misleading? Basic

CAP says that when a network partition happens (nodes cannot talk to each other), a replicated system must choose: stay consistent (linearizable) by refusing some requests, or stay available by answering with possibly stale data. "Pick two" is misleading because partitions are not optional on a real network, so the real choice is C or A, and only during a partition.

Define the three letters precisely, because interviewers test this.

  • Consistency (C): linearizability. Every read returns the value of the most recent completed write, as if there were one copy of the data.
  • Availability (A): every request to a node that is working gets a non-error answer (it does not have to be the latest data).
  • Partition tolerance (P): the system keeps working even when the network splits nodes into groups that cannot talk to each other.

Why it is a theorem and not an opinion. Imagine two replicas, one in each data centre, and the link between them is cut. A client writes x = 2 to replica A. A second client then reads x from replica B. B has two choices and only two. It can answer with its old value x = 1, which is available but not consistent. Or it can refuse (or wait forever), which is consistent but not available. It cannot know about x = 2 because the link is down, so no third option exists. That is the whole proof, in one picture.

Why "pick two" misleads. You do not get to pick "CA". A single machine is CA only because it is not distributed. Once data lives on several machines, partitions will occur (cables, switches, misconfigured firewalls, long pauses that look like partitions), so P is forced. The real decision is what to give up during the partition, and it applies only while the partition lasts. When the network is healthy, a good system gives both C and A.

How I use it in an answer. I do not label a whole database "CP" or "AP". I ask per operation: "if this write cannot reach a majority, is it worse to reject it or to accept it and risk a conflict?" For a bank transfer: reject. For adding an item to a shopping cart: accept and merge later. Amazon's Dynamo paper chose exactly that for carts.

During a partitionExamples (default behaviour)
CPMinority side refuses reads or writes; no stale dataetcd, ZooKeeper, HBase, Spanner
APBoth sides keep answering; replicas diverge and are merged laterCassandra, DynamoDB eventual reads, DNS

Pitfall: CAP says nothing about latency, durability or what happens with no partition, and "available" in CAP is stricter than "mostly up" in marketing. Do not use CAP to justify slow reads; that is PACELC's job.

The terms are strict. Consistency here means linearizability: every read sees the latest completed write, as if there were one copy. Availability means every non-failing node answers every request. Without a partition you can have both. A CP system (etcd, ZooKeeper, HBase) refuses or errors on the minority side. An AP system (Cassandra, DynamoDB in eventual mode, DNS) answers on both sides and reconciles later, so some writes may conflict. CAP says nothing about latency or about normal operation, which is why PACELC exists. Also, the choice is per operation in many systems, not for the whole product.

Remember: partitions are a fact, so CAP is "C or A during a partition". There is no "CA" for a distributed system.

What does PACELC add to CAP, and where do common databases fall? Intermediate

PACELC says: if there is a Partition choose Availability or Consistency, Else (normal operation) choose Latency or Consistency. It adds the trade-off that matters every day: even with no partition, keeping replicas strongly consistent costs latency because writes must wait for other nodes.

The gap in CAP. CAP only describes the rare moment of a partition. But most of the time the network works, and you still face a design choice every single request: if data is copied to several nodes, do you wait for those copies before answering (consistent, slower) or answer straight away from one node (fast, maybe stale)? Daniel Abadi named this PACELC to capture both situations in one sentence.

How to read the acronym. "If Partition: Availability or Consistency; Else: Latency or Consistency." So every system gets a pair such as PA/EL or PC/EC.

A concrete latency example. A write is made in Frankfurt with a replica in Virginia, about 90 ms away round trip. If the leader waits for Virginia to acknowledge, every write costs at least 90 ms but nothing is lost and replicas agree (EC). If it acknowledges immediately and sends the copy in the background, writes cost under 5 ms but Virginia may be a few hundred ms behind, and a failover can lose the last writes (EL).

PairMeaningTypical systems
PA/ELAvailable in a partition, fast otherwiseCassandra, DynamoDB (default), Riak
PC/ECConsistent always, pays latency alwaysSpanner, CockroachDB, etcd, ZooKeeper, VoltDB
PA/ECAvailable in a partition, consistent otherwiseMongoDB is often placed here in the papers, depending on settings

Treat the table as defaults. Almost every one of these products lets you move along the scale with a setting: Cassandra consistency level, DynamoDB strongly consistent reads, MongoDB read and write concerns. The sentence an interviewer wants is "this is a knob, here is the knob, here is its price".

Typical placements (these are defaults and can be tuned): DynamoDB and Cassandra are PA/EL (available in a partition, low latency otherwise, weaker consistency). Spanner, CockroachDB, etcd and ZooKeeper lean PC/EC (consistent always, pay latency, especially across regions). MongoDB defaults to PC/EC for primary reads, but reading from secondaries moves it towards latency. A single-region primary with an async replica is "EL" for replica reads. In an interview, naming one example per quadrant and explaining the knob (quorum size, read concern, sync vs async replication) beats reciting the acronym.

Remember: CAP is about the failure case, PACELC adds the everyday case: strong consistency costs latency even when nothing is broken.

Walk me through the consistency models from strongest to weakest. Intermediate

From strongest: linearizable (behaves like one copy, reads see the latest write), sequential (everyone sees the same order, not necessarily real-time), causal (causes are seen before effects), then session guarantees such as read-your-writes and monotonic reads, and finally eventual (replicas converge if writes stop). Stronger is easier to reason about but costs latency and availability.

Why there is a spectrum at all. Strong consistency needs coordination between replicas on every operation, and coordination costs latency and availability. Weaker models let replicas answer on their own. Each model is a promise about what a reader can observe; the weaker the promise, the more your application code must cope.

Each level, with a tiny example. Say Alice posts "I'm engaged!" then comments "Congrats!" appears from Bob.

  • Linearizable: after the post returns, nobody anywhere sees the old state. Reads and writes behave as one copy in real time.
  • Sequential: all clients see the same single order of operations, but it may lag behind real time. Two users may disagree with the wall clock but never with each other.
  • Causal: if one operation could have influenced another (Bob read the post, then commented), everyone sees the post before the comment. Unrelated operations can appear in different orders on different replicas.
  • Session guarantees: weaker, per client. Read-your-writes: I see my own writes. Monotonic reads: I never see older data after seeing newer. Monotonic writes: my writes apply in the order I made them.
  • Eventual: replicas converge if updates stop; nothing is promised in the meantime.

How to choose. Use the weakest model whose anomalies your users cannot notice or that you can repair. Inventory counts, balances, unique names and locks need linearizable or serializable behaviour. Social feeds, view counters and recommendations are fine with eventual plus read-your-writes. Causal consistency is a sweet spot because it can be provided without blocking during a partition.

Pitfall: words are used loosely. "Strong consistency" in a vendor page might mean linearizable, or only "read from the primary". Ask what exactly is guaranteed and under which settings.

A simple way to remember it is by the bug each level prevents. Linearizable: no stale reads, ever. Causal: a reply is never seen before the question it answers. Read-your-writes: I see my own update. Monotonic reads: I never see data go back in time between two reads. Eventual: only "they will agree sometime". Most systems let you pick per operation: strong for the money balance, eventual for the like counter. Remember that serializable (transactions behave as if run one by one) is a different axis: it is about multi-object transactions, not recency.

Remember: linearizable, causal, read-your-writes, eventual. Each level is named after the bug it stops.

What exactly is linearizability, and how is it different from serializability? Senior

Linearizability is a recency guarantee on a single object: once a write completes, every later read, from anywhere, sees it, as if there was one copy. Serializability is an isolation guarantee for multi-object transactions: the result equals some one-at-a-time order, but that order need not match real time. A system with both is called strict serializable (Spanner, for example).

Two ideas that sound alike. They come from different fields. Linearizability comes from distributed systems and is about one object and time. Serializability comes from databases and is about groups of operations (transactions) and isolation.

Linearizability, step by step. Each operation takes some time, from the moment the client sends it to the moment it gets a reply. A system is linearizable if every operation appears to take effect at one instant somewhere between those two moments, and all clients agree on those instants. A practical test: once any client has seen the new value, no client may see the old value again, and a read that starts after a write has finished must see that write.

A small timeline. x starts at 1.

t=0   Client A: write x = 2 starts
t=3   Client A: write x = 2 returns OK
t=4   Client B: read x starts -> must return 2 (the write finished before the read began)
t=1   Client C: read x starts, returns during the write -> may return 1 or 2, but if it returns 2,
      then any read starting after it must also return 2

Serializability. Transactions T1 (transfer money) and T2 (report total) run concurrently. The result must equal running T1 then T2, or T2 then T1, for example to avoid a report that sees half a transfer. Nothing says that order matches the clock. A database may serialise T2 "before" T1 even though T2 started later, so a reader could see slightly old data.

LinearizabilitySerializability
ScopeSingle object, single operationMulti-object transactions
GuaranteeRecency, real-time orderEquivalent to some serial order

Strict serializability gives both and is what Spanner provides, using TrueTime to bound clock uncertainty. Linearizable reads in Raft stores require the leader to confirm it is still leader (a heartbeat round or a lease) before answering.

Example: I update my profile and the call returns. A linearizable store means a friend reading afterwards cannot see the old name. A serializable-but-not-linearizable database could legally serve that friend a slightly older snapshot, as long as the transactions still look like they ran in some sequence. Linearizability is what you need for locks, leader election and unique-username checks, because they depend on "latest value" being really latest. It costs a coordination round trip (consensus or a leader read), so it is the thing you spend on small, critical data only.

Remember: linearizable = recency on one object. Serializable = isolation across many objects. Different axes.

What does "eventually consistent" really promise, and what does it not? Basic

It promises one thing: if writes stop, all replicas will converge to the same value. It does not say how long that takes, and it does not promise anything about reads in between, so I may read old data, or see updates out of order.

What actually happens. A write is accepted by one replica (or a few) and copied to the others in the background. For a short time different replicas hold different values. If nobody writes again, a background process (replication, read repair, anti-entropy) makes them equal. That final agreement is all the model promises.

Anomalies you must expect, with an example.

  • Stale read: you set your display name, reload, and the replica still serves the old one.
  • Time travel: one read hits a fresh replica, the next hits a stale one, and the value goes backwards.
  • Lost or conflicting update: two people edit the same record on different replicas. The system must have a rule (last write wins, merge, keep both) or one edit silently disappears.
  • Order anomalies: a reply appears before the question.

How applications live with it. Pick a conflict rule explicitly instead of accepting the default. Use idempotent, commutative operations where you can (add to a set, increment a counter with a CRDT). Add session guarantees for the user-visible cases. Show optimistic UI. For the few things that cannot tolerate staleness, read from the leader or use a quorum or strongly consistent read for just that path.

When it is the right choice. When availability and latency matter more than seeing the very latest value, and the data is naturally mergeable: DNS, shopping carts, likes, activity feeds, caches. Never for uniqueness checks or money without extra protection.

In practice "eventually" is usually milliseconds to a few seconds, and it gets longer under load or failure. The application must tolerate stale reads and concurrent writes: pick a conflict rule (last write wins, merge, or let the user decide), and add session guarantees where users would notice, such as read-your-writes. Good fits: counters, feeds, product catalogue, caches, DNS. Bad fits: account balances, inventory that must not go negative, anything uniqueness-related.

Remember: eventual = "they agree once things calm down". Nothing about the meantime.

A user updates their profile, refreshes, and sees the old data. How do you give read-your-writes consistency? Intermediate

The write went to the leader but the read hit a replica that had not caught up. To fix it I make sure a user reads their own recent writes from a place that has them: the leader, or a replica known to be caught up past their write.

Why it happens. With single-leader replication and asynchronous followers, a write goes to the leader and returns OK. The follower may apply it only 50 to 500 ms later (or seconds under load). If the very next page load is served by that follower, the user sees their old profile and thinks the save failed. Nothing is broken; the system promised only eventual consistency. Read-your-writes (also called read-after-write) adds a small promise: I will always see my own writes, though other people may still see old data briefly.

Four ways to provide it, from simple to precise.

  1. Read from the leader for things the user may have just edited (their own profile), and from followers for everything else.
  2. Time window: for N seconds after a user writes, send all of that user's reads to the leader. Choose N bigger than normal lag. Simple, but wasteful and fragile if lag grows.
  3. Position token: the write response carries the log position (or hybrid timestamp). The client sends it with the next read, and the follower answers only if it has applied at least that position, else it waits briefly or redirects. This is exact and cheap, and it is how several databases and cloud services expose it (for example MySQL GTID waits or Cosmos DB session tokens).
  4. Client-side update: after a successful save, the browser updates its own display from the response and does not need to re-read.

Edge cases that interviewers like. Multiple devices: the laptop wrote, the phone reads; the token or time window must be stored server-side per user rather than in one browser. Cross-region: if the user's reads move to another region after a write, the token must be honoured there too. And after a leader failover, a follower that was behind may become leader and lose the write you were promised, so read-your-writes also depends on durable replication.

Practical options. (1) For a short window after a write (say 10 to 30 seconds), route that user's reads to the leader. (2) Return a position token (log offset or timestamp) with the write, send it back on reads, and let a replica serve only if it has applied up to that position, otherwise wait or go to the leader. (3) Sticky routing of a user to one replica, which also gives monotonic reads (time never goes backwards) but not read-your-writes after a failover. (4) Update the client's local state right after a successful write. Watch for multi-device users: a token in one browser does not help the phone.

Remember: after a write, read from the leader or from a replica that has caught up to my write position.

If I read and write at a quorum (W + R > N), do I get linearizability? Senior

Not guaranteed. W + R > N makes the read set overlap the write set, so a read will see at least one copy of the latest completed write. But with concurrent writes, sloppy quorums, clock-based conflict resolution or partially failed writes, you can still read stale or flip-flopping values.

The claim being tested. Quorum math says that if you write to W of N replicas and read from R of N with W + R > N, the read set and write set share at least one replica. People then conclude "the read always sees the latest write, so it is linearizable". The first half is true; the conclusion needs more.

Why the overlap is not enough. The overlap only guarantees that some replica you read from has the new value. It does not guarantee that the new value is the one chosen if you also read an old one. That needs a rule such as "highest version wins", and that rule depends on timestamps or version vectors, which can be wrong. The failure cases:

  • Write that did not complete. The write reached 1 of 3 replicas before the client timed out. It was never acknowledged as successful, yet readers whose R set includes that replica will see it, then a later reader may not. The value appears and disappears.
  • Concurrent writes. Two writes race; replicas receive them in different orders; with last-write-wins and skewed clocks the "winner" can be the older write.
  • Sloppy quorum and hinted handoff. To stay available, a write may be accepted by nodes that are not in the key's normal replica set. Then the W nodes and the R nodes may not overlap at all until handoff finishes.
  • Failed repair and replica changes while membership is changing.

What gives real linearizability. A single leader or a consensus protocol (Raft, Paxos) that orders writes and makes reads go through the leader (or run a read-index check). Some leaderless systems offer lightweight transactions or compare-and-set, built on Paxos, for exactly the keys that need it (for example Cassandra's lightweight transactions).

Good interview line: "quorums make staleness unlikely and bounded by repair, but only consensus makes it impossible".

Example with N = 3, W = 2, R = 2. A write succeeds on node A, is still in flight to B, and the writer sees a timeout. One reader asks A and B and gets the new value; a later reader asks B and C and gets the old one, because the write is only half done. The new value appeared and then vanished, which violates linearizability. Real linearizable reads need either a read repair before returning (some stores do this per request) or consensus (Raft or Paxos based stores). Also, with a sloppy quorum (writes accepted by any reachable nodes) the overlap guarantee disappears.

Remember: quorum overlap gives "probably fresh", not "linearizable". For strict guarantees use consensus.

3. Time, ordering and IDs

Why can't you trust wall-clock time in a distributed system? Basic

Because every machine has its own clock, and they drift apart and get corrected in jumps. So "timestamp A is before timestamp B" across two machines proves nothing. I never use wall-clock timestamps from different machines to order events or decide who wins, and I use a monotonic clock to measure durations.

Two kinds of clock on every machine. The time-of-day clock returns the calendar time and is synchronised with other machines by NTP; it can jump forwards or backwards when corrected. The monotonic clock only moves forward and measures elapsed time on that machine; its absolute value is meaningless and cannot be compared across machines.

What goes wrong with time-of-day clocks, with a scenario. Server A has a clock 3 ms ahead of server B. Two users update the same row: A writes at real time 100.000 and stamps 100.003; B writes 1 ms later at real time 100.001 and stamps 100.001 (its clock is accurate). A "latest timestamp wins" rule keeps A's write, which was actually earlier. B's update is lost silently. Real skew can be hundreds of milliseconds after a bad NTP sync, and a VM that was paused or migrated can wake up seconds behind.

  • Drift: cheap quartz clocks drift by about tens of parts per million, which is a few seconds per day if never corrected.
  • Steps: NTP corrects by slewing (speeding up or slowing down) if the error is small, but may step the clock for big errors.
  • Leap seconds repeat or skip a second; some systems smear them over hours.
  • Pauses: a process can be frozen (GC, VM migration) between checking the time and acting on it.

What I use instead.

  1. Durations and timeouts: monotonic clock (System.nanoTime() in Java, time.monotonic() in Python).
  2. Ordering events: a counter assigned by one authority (database sequence, Kafka partition offset, Raft log index), or logical clocks (Lamport, vector).
  3. When physical time is unavoidable: bound the uncertainty. Google Spanner's TrueTime returns an interval [earliest, latest] using GPS and atomic clocks, and a commit waits out the uncertainty window (a few ms). Hybrid logical clocks (used by CockroachDB) combine physical time with a counter.

Pitfall: lease and lock expiry that relies on clocks agreeing is a classic source of split-brain bugs.

Quartz clocks drift by milliseconds per day. NTP (the protocol that corrects them) typically keeps machines within a few milliseconds on a good LAN and tens of milliseconds over the internet, and it can step a clock backwards or forwards. VM pauses, leap seconds and sleeping laptops add more jumps. In Java use System.nanoTime() (monotonic, only for elapsed time) for timeouts and currentTimeMillis() only for display. For ordering, use a logical clock, a version number, a database sequence, or a consensus log, not "latest timestamp".

Remember: wall clock for humans, monotonic clock for durations, logical clocks or versions for ordering.

What is the happens-before relation, and how do Lamport clocks use it? What can they not tell you? Intermediate

Event A happens-before B if they are on the same node with A first, or A is a message send and B its receive, or through a chain of those. A Lamport clock is a counter that respects this: if A happens-before B, then timestamp(A) is less than timestamp(B). The reverse is not true, so a Lamport clock cannot tell me whether two events were concurrent.

First, what "happens-before" means. Without a global clock you cannot say event A was at 10:00:01 and B at 10:00:02. What you can say is whether A could have influenced B. Leslie Lamport defined: A happens-before B (written A -> B) if (1) both are on the same process and A came first, or (2) A is the sending of a message and B is its receipt, or (3) there is a chain through other events (transitive). If neither A -> B nor B -> A, the events are concurrent: no information could have flowed between them.

The Lamport clock algorithm. Every process keeps an integer counter, starting at 0.

  1. Before each local event, counter = counter + 1.
  2. When sending a message, add 1 and attach the counter value.
  3. When receiving a message with value m, set counter = max(counter, m) + 1.

Worked example. P1 and P2 both start at 0. P1 does a local event (1), then sends a message to P2 with 2. P2 meanwhile did two local events (counter 2). On receive P2 sets max(2, 2) + 1 = 3. The receive (3) is larger than the send (2), as required. If P2 had been at 10, the receive would be 11, and P2's clock jumps forward to stay consistent with causality.

What it guarantees and what it does not. If A -> B then L(A) < L(B). The converse fails: L(A) < L(B) does not mean A caused B, they may be unrelated and just have gotten different counts. So Lamport timestamps give a consistent total order (break ties by process id) that respects causality, but they cannot detect concurrency.

Where it is used. Total-order broadcast, distributed mutual exclusion (Lamport's own algorithm), ordering log entries, and as the basis for hybrid logical clocks. When you need to detect conflicts instead of just ordering, move to vector clocks.

The rule is tiny. Each node keeps a counter. Increment it on every local event. Put it on every outgoing message. On receive set counter = max(own, received) + 1. Break ties by node id to get a total order. That gives a consistent ordering (used for example in simple distributed mutual exclusion and total-order broadcast), but if I see timestamps 5 and 7, I cannot tell whether event 5 caused event 7 or they were unrelated. For that you need vector clocks.

Remember: Lamport: causal implies smaller number, but smaller number does not imply causal. Counter = max + 1 on receive.

How do vector clocks work, and how do they detect conflicts? Senior

A vector clock keeps one counter per node. A version A is older than B if every counter in A is less than or equal to the matching counter in B. If neither is older, the two versions are concurrent, which means a real conflict that the system or application must resolve.

The problem a Lamport clock cannot solve. Two replicas each receive a different update to the same key at about the same time. A Lamport clock gives them numbers like 5 and 7 and a system would silently pick 7. But the writers did not know about each other, so neither is "newer"; they conflict. We need a clock that can say "these are concurrent".

How a vector clock works. Each version carries a map from node to counter, for example {X:2, Y:0}.

  1. When node N updates a value, it takes the clock of the version it started from and increments its own entry.
  2. To compare two clocks V and W: V is before W if every entry of V is less than or equal to the matching entry in W (missing entries count as 0) and at least one is strictly less. Then W supersedes V, and V can be discarded.
  3. If neither is before the other, they are concurrent, so both are kept as siblings.
  4. A client that reads siblings merges them in application logic and writes back with a clock that is the entry-wise maximum, plus its increment, so the merged version dominates both.

Walking the example. Cart v1 = [milk], clock {X:1}. Client 1 adds eggs via X: {X:2} = [milk, eggs]. Client 2 saw only v1 and adds bread via Y: {X:1, Y:1} = [milk, bread]. Compare: X:2 > X:1 but Y:0 < Y:1, so neither dominates, so concurrent. On the next read the application unions them into [milk, eggs, bread] with clock {X:2, Y:1}. Nothing was lost. (Removing an item is trickier: a plain union can bring a deleted item back, which is why OR-sets exist.)

Trade-offs. Metadata grows with the number of nodes that ever wrote (client-side ids make it worse), so real systems truncate or use dotted version vectors. The benefit is no lost writes; the cost is that the application must handle siblings. Many databases chose simpler last-write-wins for that reason.

Example with nodes X and Y. Value v1 has [X:1, Y:0]. Client 1 updates via X to get [X:2, Y:0]. Client 2, who only saw v1, updates via Y to get [X:1, Y:1]. Neither dominates the other, so they are siblings. Dynamo-style stores (Riak, the original Dynamo) keep both and let the application merge, for example by taking the union of two shopping carts. The cost is metadata that grows with the number of writers, so real systems prune it or use dotted version vectors. Many modern stores skip this and use last-write-wins, accepting that a concurrent update can be lost.

Remember: vector clock = a counter per node. If neither version dominates, they are concurrent: merge them.

Why is last-write-wins dangerous, and what do you use instead? Intermediate

Last-write-wins (LWW) keeps the write with the highest timestamp and silently throws away the others. Since clocks on different machines disagree, a write that really happened later can lose, and truly concurrent writes lose data with no error. I use it only when losing an update is acceptable, such as a cache entry or an idempotent overwrite.

What LWW does. Each write carries a timestamp. When replicas hold different values for a key, the one with the larger timestamp is kept and the others are dropped. It is the default conflict rule in Cassandra, and many caches and replication tools work this way. It is attractive because it is simple, needs no coordination and always converges.

The two ways it loses data, with an example.

  1. Clock skew. Alice's laptop (clock 2 s fast) saves a note at real time 10:00:00 and stamps 10:00:02. Bob's phone (accurate) saves a different edit at 10:00:01 real time and stamps 10:00:01. Bob edited later, but Alice's older edit wins. Bob's change vanishes with no error.
  2. Concurrent writes. Two edits to different fields of the same row, made at nearly the same time, are treated as competing whole-row versions. One whole row wins, and the other person's field change is lost even though there was no real conflict.

Alternatives, by situation.

NeedUse
Detect that someone else changed it firstVersion column and compare-and-set (optimistic locking): UPDATE ... WHERE id=? AND version=?; on 0 rows updated, tell the user to retry

Counters, sets, collaborative textCRDTs

When LWW is fine: overwriting a cached value, "last seen" timestamps, sensor readings where a newer reading really replaces the old, and idempotent writes of the same value. If you must use it, use a reliable timestamp source and make sure the timestamp is assigned by the server, not by clients.

Example: a user edits their profile on two devices. Device B's clock is 200 ms behind, so its newer edit gets an older timestamp and the stale edit "wins". Safer options: a version number with compare-and-set (reject the write if the version has changed), vector clocks with an explicit merge, field-level merging, a CRDT, or routing all writes for a key through one leader so the order is decided in one place.

Remember: LWW = "silently lose one of two writes, and clock skew picks the loser". Prefer versions or merges.

How do you generate unique, roughly time-ordered IDs across many machines? Intermediate

I use a Snowflake-style 64-bit ID: a timestamp, a machine id, and a per-millisecond sequence number packed into one number. Each machine generates IDs locally with no coordination, they are unique, and they sort roughly by time. If I do not need sorting, a random UUID is simpler.

Requirements that drive the design. Many machines must create IDs at the same time without asking a central server each time (that would be a bottleneck and a single point of failure). IDs must never repeat. It is a big bonus if they sort by creation time, because database indexes then append at the end instead of scattering inserts, and "latest N" queries are cheap.

The options.

ApproachProsCons
DB auto-incrementSmall, ordered, simpleOne writer; hard to scale across shards; leaks volume; hard in multi-leader
UUIDv4 (random 128-bit)No coordination; collisions practically impossibleNot sortable; random inserts fragment B-tree indexes; 16 bytes

Snowflake bit layout walk-through. 1 unused sign bit, then 41 bits of millisecond timestamp since a chosen epoch (2^41 ms is about 69 years), 10 bits of worker id (1024 workers), and 12 bits of sequence (4096 ids per millisecond per worker, so about 4 million per second per worker). To make an ID: take the current ms; if it is the same ms as the last ID, increment the sequence, and if the sequence overflows wait for the next ms; otherwise reset the sequence to 0. Shift and OR the three fields together.

The main failure mode. If the system clock steps backwards (an NTP correction), the generator could repeat a timestamp and sequence and produce a duplicate. Good generators remember the last timestamp used and refuse or wait until time catches up. The other pitfall is two workers getting the same worker id after a bad deployment, which breaks uniqueness; assign ids via a coordination service or from the pod ordinal.

State the trade-off in the answer: "sortable and compact, but it depends on clocks and on unique worker ids".

Typical Snowflake layout: 41 bits of milliseconds since a custom epoch (about 69 years), 10 bits of machine id, 12 bits of sequence (4096 IDs per millisecond per machine). Problems to mention: if a clock moves backwards the generator must wait or refuse, machine ids must be assigned uniquely (via config or a coordination service), and the order is only "roughly" time order across machines. UUIDv4 is random, so it is poor for B-tree index locality (inserts scatter); UUIDv7 and ULID put a timestamp first and fix that. A database auto-increment or sequence is fine for one database but becomes a bottleneck and a single point of failure when shared.

Remember: time bits + machine bits + sequence bits = unique without coordination. Guard against clocks going backwards.

4. Replication

Why replicate data, and what are the three replication architectures? Basic

I replicate for availability (survive a node loss), for read scalability (spread reads over copies) and for lower latency (copies near users). The three architectures are single-leader (one node takes writes, followers copy), multi-leader (several nodes take writes) and leaderless (any node takes writes, quorums decide).

Why copies at all. A single copy of data dies with its machine. Keeping the same data on several machines gives three separate benefits, and it helps to say which one you are after because each pushes the design differently.

  • Availability and durability: if one node or even one zone is lost, another copy keeps serving and no data is lost.
  • Read scalability: reads can be spread over N copies, which is useful when reads vastly outnumber writes (often 10 to 1 or more).
  • Latency: put a copy near users in each region.

The one hard problem: keeping copies in step when the data changes. Static data is trivial to replicate. The three architectures are three answers to "who is allowed to accept a write?".

Single-leaderMulti-leaderLeaderless
Who takes writesOne nodeOne per region or siteAny replica, via quorum

FailoverNeeded (promote a follower)Another leader already existsNone; quorum tolerates failures

ExamplesPostgreSQL, MySQL, MongoDB, KafkaMulti-region MySQL, CouchDB, calendar appsCassandra, Riak, DynamoDB (as designed in the paper)

Decision rule. Start single-leader: it is the easiest to reason about, and with read replicas it covers most needs. Choose multi-leader only when you really need writes accepted in several regions or offline. Choose leaderless when you need very high write availability and can accept eventual consistency and conflict handling.

Remember that replication does not increase write capacity (every copy must apply every write) and it does not solve data bigger than one machine. For that, partition first, then replicate each partition.

Single-leader (PostgreSQL, MySQL, MongoDB, Kafka partitions) is the simplest: one place decides the write order, so there are no write conflicts. Its limits are write throughput on one node and a failover step when the leader dies. Multi-leader suits multiple regions or offline-capable clients, but concurrent writes can conflict and need a resolution rule. Leaderless (Cassandra, DynamoDB-style) has no failover at all and tolerates slow nodes, but conflict handling and stale reads become your problem. Replication keeps copies of the same data; it does not help data that is too big for one node, which is partitioning.

Remember: single-leader is the default. Go multi-leader or leaderless only for multi-region writes or extreme availability, and then plan for conflicts.

Synchronous versus asynchronous replication: what are the trade-offs? Basic

Synchronous replication makes the leader wait for follower acknowledgement before confirming a write, so no confirmed write is lost if the leader dies, but writes are slower and a dead follower can block them. Asynchronous confirms immediately and copies later, so it is fast and tolerant of slow followers, but a leader crash can lose recent writes.

The choice, as a timeline. A client writes to the leader. The leader writes its own log, then sends the change to followers.

Synchronous:   client -> leader -> follower(s) -> ack back -> leader acks client      (waits for followers)
Asynchronous:  client -> leader -> leader acks client   ... later: leader -> followers  (does not wait)

What you get and lose. With sync, when the client hears "OK" the data is on at least two machines, so losing the leader right now loses nothing. The cost is latency (the slowest awaited follower sets the pace, perhaps 1 to 2 ms in the same zone, 80 ms or more across regions) and availability (if the awaited follower is down, writes stall). With async, writes are as fast as the leader alone, and a slow or dead follower does not matter, but if the leader dies, anything not yet copied (from a few milliseconds to seconds of writes) is gone, even though the client was told OK.

Why not "sync to everyone". With 5 followers all required, five machines must be healthy for any write to succeed, which is worse availability than one machine. So real setups use semi-synchronous: require acknowledgement from one follower (PostgreSQL synchronous_commit with one sync standby, MySQL semi-sync) or from a quorum (Raft: majority; Kafka: acks=all and min.insync.replicas=2 of 3). The system tolerates losing any one machine without losing data, and without waiting for the slowest one.

How to decide. Ask what one lost write costs. Orders and payments: at least one sync or quorum copy, ideally in another zone. Analytics copy, reporting replica, cache fill: async. Cross-region replicas: usually async because of latency, with a stated recovery point (RPO) that accepts the loss of a few seconds.

Pitfall: async replicas make failover lossy, and a "synchronous" setup that silently falls back to async when the standby is down gives a false sense of safety. Know what your configuration does in that case.

Fully synchronous to every follower is rarely used: one slow node stalls everything. The common compromise is semi-synchronous: wait for one follower (or a quorum) and the rest are async, so there is always at least one up-to-date copy. Async also creates replication lag, where followers serve old data. The right choice depends on what a lost write costs: for payments use sync or quorum (PostgreSQL synchronous commit, MySQL semi-sync, Kafka acks=all with min.insync.replicas); for analytics replicas async is fine.

Remember: sync = durable but slower and fragile. Async = fast but can lose the latest writes. Semi-sync is the usual middle.

What problems does replication lag cause, and how do you handle them? Intermediate

Lag means a follower is behind the leader, so reads from it can be stale. The visible problems are: users not seeing their own writes, time appearing to go backwards between two reads, and answers that arrive before the questions they answer. I handle them with leader reads for critical paths, session guarantees and monitoring the lag.

What lag is. The follower applies the leader's log some time after the leader did. Normally this is milliseconds, but it grows with heavy write bursts, a slow disk or network, a long-running query holding back apply, or a follower that was restarted and is catching up. During that time a read from the follower is a read of the past.

Three anomalies, with examples.

  1. Read-your-writes violated. You post a comment and reload; the replica has not got it yet, so it looks lost.
  2. Monotonic reads violated. Reload 1 hits replica A (up to date) and shows 10 comments; reload 2 hits replica B (lagging) and shows 8. The user sees time run backwards.
  3. Consistent-prefix violated. With sharded data, "Mr. A: How far can you see?" and "Mrs. B: About 10 miles" live on different shards. An observer reading a lagging shard may see the answer without the question.

Fixes.

AnomalyFix
Own writes missingRead from leader (or caught-up replica) after writes; position tokens
Time goes backwardsPin each user or session to one replica (hash of user id)
Out-of-order cause and effectWrite related data to the same partition, or use causal consistency
Lag too largeAlert on lag in seconds, remove the replica from rotation, find the blocking query or slow disk

Operational view. Track lag (for example Seconds_Behind_Master in MySQL, pg_stat_replication in PostgreSQL), and have the router skip any replica above a threshold. Pinning a user to one replica breaks when that replica fails, so be ready to fall back. The deeper design question is whether the product can be built to tolerate stale reads at all, since fixing it later is much harder.

Fixes by symptom. Not seeing my own write: read-your-writes (see that question). Time going backwards (page refresh hits a different, older replica): monotonic reads, by pinning a user to one replica. Out-of-order conversation (a reply shown before the question because they live on different shards): consistent-prefix reads or causal consistency. Also alert on lag in seconds and take a replica out of rotation when it passes a limit. A long query or big batch on a follower can itself cause lag, so watch for that.

Remember: three lag symptoms, three fixes: own writes (read-your-writes), time travel (monotonic reads), wrong order (causal or prefix).

What happens during a leader failover, and what can go wrong? Intermediate

Followers notice the leader is silent, pick the most up-to-date follower as the new leader, and redirect clients to it. The risks are losing writes the old leader had not replicated (async), two nodes believing they are leader (split brain), and flapping when the timeout is too aggressive.

The goal. If the single leader dies, writes stop until someone else takes over. Failover is the process of promoting a follower so the service resumes with minimal data loss and, above all, with exactly one leader.

The steps, in order.

  1. Detect. Followers or a monitor notice missing heartbeats for longer than the timeout (commonly some seconds to 30 seconds).
  2. Choose the new leader. Prefer the follower with the most up-to-date log, by log position. In Raft this is built into the voting rule; in a classic MySQL or PostgreSQL setup a tool such as Patroni or Orchestrator picks it.
  3. Promote and reconfigure. The chosen node starts accepting writes, other followers re-point to it, and clients or the proxy are told the new address (DNS, virtual IP, service discovery).
  4. Fence the old leader. If it comes back it must become a follower (and discard writes that were never replicated), not keep serving as leader.

What goes wrong, with examples.

  • Lost writes. With async replication, the old leader acknowledged commit 1050 but the best follower only has 1048. After promotion 1049 and 1050 are gone. Worse, if a database used auto-increment ids and some had already been given to other systems (a cache, a Redis, another service), the new leader will reuse them, causing a real incident (a GitHub outage in 2012 is the well-known example of this pattern).
  • Split brain. The old leader was only slow, not dead, and both accept writes.
  • Failover storms. The timeout is too short, load causes a pause, a failover happens, the new leader is cold and slow, which triggers another failover.
  • Clients keep talking to the old address because of cached DNS or connection pools.

Mitigations: conservative timeouts, a majority-based coordinator (etcd with Patroni, Raft inside the database), semi-synchronous replication to avoid loss, fencing of the old node, and regular failover drills so you know it works before you need it.

Steps: detect the failure by timeout, elect a new leader (by consensus or by an operator or tool), reconfigure clients and followers, and make sure the old leader steps down if it comes back. Pitfalls. Lost writes: the new leader never saw the last few commits, and when the old leader rejoins its extra writes are discarded, which may even clash with ids already handed out. Split brain: protect with term numbers and fencing. False failover: a long GC pause triggers an election and extra load makes it worse. Many teams use automatic failover with a conservative timeout and a majority-based coordinator (Raft in Patroni via etcd, MongoDB replica set elections, Kubernetes operators).

Remember: failover = detect, elect, redirect, fence the old leader. Async replication means you can lose the last writes.

When would you use multi-leader replication, and how are write conflicts resolved? Senior

I use it when I need local writes in several regions, or when clients must write offline and sync later. The price is write conflicts: two leaders can accept different updates to the same record at the same time. I avoid conflicts by design where I can, and otherwise resolve them with a clear rule.

When it makes sense.

  • Multi-region writes. With a single leader in Virginia, a user in Singapore pays about 200 ms for every write. With a leader in each region, writes are local and replicate between regions in the background. Each region also keeps working if the inter-region link fails.
  • Offline clients. A phone calendar is effectively a leader of its own copy and syncs when online.
  • Collaborative editing. Every participant's device accepts edits at once.

The problem that appears. Two leaders each accept a write to the same record before hearing about the other. When they exchange changes, there are two competing versions. Because replication is asynchronous, both clients were already told "saved", so you cannot just return an error.

Example. Title of a wiki page is "Draft". In Europe a user changes it to "Plan A", while in the US another changes it to "Plan B", within the same second. After sync each side sees the other's change. The system must now decide the final title.

Other traps. Auto-increment primary keys collide between leaders (use UUIDs or ranges), uniqueness and foreign-key constraints cannot be checked globally, and replication topologies (circular, star, all-to-all) can deliver changes out of causal order. Many "multi-leader" problems are solved more simply with a single leader plus follower reads, so ask whether you truly need local writes before taking on this complexity.

Avoidance first: route each record to one home region so only one leader writes it. If conflicts are possible, the options are last-write-wins (simple, loses data), merge by field or by data type (CRDTs, set union), keep both versions and ask the application or user (like a Git merge conflict), or custom logic. Conflicts are detected asynchronously, after both writes were already acknowledged, so the application cannot tell the user at write time. Other gotchas: auto-increment keys collide, and constraints (uniqueness, foreign keys) cannot be enforced across leaders. For most teams a single leader with read replicas in other regions is simpler and good enough.

Remember: multi-leader buys local writes and costs conflict handling. Avoid conflicts by routing; otherwise merge.

How does leaderless replication (Dynamo style) work? Explain quorums with N, W and R. Intermediate

The client (or a coordinator node) sends each write to N replicas and waits for W acknowledgements, and sends each read to N replicas and waits for R answers. If W + R > N, the nodes I read from must include at least one that saw the latest write, so the read can return the newest version. A typical setting is N = 3, W = 2, R = 2.

The idea. There is no special node. A client (or any node acting as coordinator) sends a write to all N replicas of the key and counts acknowledgements; when W have answered it reports success. A read goes to all N replicas and returns when R have answered, taking the newest version among those answers. If the read and write sets must overlap (W + R > N), at least one answer will have the latest completed write.

Why this tolerates failures. With N = 3, W = 2, R = 2, one node can be down or slow and every operation still succeeds, with no failover step, no election and no promotion. That is the central attraction of this design (Amazon's Dynamo, Cassandra, Riak).

Tuning cheat sheet (N = 3).

WREffect
31Fast reads; writes fail if any node is down
22Balanced; survives one node down; overlap guaranteed
13Fast writes; slow reads; reads fail if a node is down
11Fastest, no overlap, stale reads likely (eventual)

How a replica that missed a write catches up (three mechanisms; the diagram below shows the first):

  • Read repair: when a read sees that one replica returned an older version, the coordinator writes the newer one back to it.
  • Hinted handoff: if a target node is down, another node holds the write as a "hint" and forwards it when the node returns. With a sloppy quorum the hint holder counts toward W, which improves availability but breaks the overlap guarantee until the hint is delivered.
  • Anti-entropy: a background process compares replicas (using Merkle trees to find the differing key ranges cheaply) and copies missing data. It also repairs data that is rarely read.

Limits to mention: concurrent writes need version or timestamp rules, a write that fails below W may still be partially applied, and strict linearizability is not provided (see the quorum question).

Tuning: W = N, R = 1 gives fast reads and slow writes that fail if any node is down. W = 1, R = N is the reverse. W = R = 2 of 3 tolerates one slow or dead node on both paths. Stale replicas are healed by three mechanisms: read repair (a read that sees an old copy writes the newest back), hinted handoff (a stand-in node keeps writes for a down replica and delivers them when it returns, used with sloppy quorums for higher availability but weaker guarantees), and anti-entropy (a background comparison, often with Merkle trees, to find and fix differences). Which version is newest is decided by timestamps or vector clocks, so conflicts follow the same rules as before.

Remember: W + R > N means overlap. Read repair, hinted handoff and anti-entropy keep replicas converging.

What is a CRDT, and when would you use one? Senior

A CRDT (conflict-free replicated data type) is a data structure designed so replicas can be updated independently and any merge order gives the same result. I use one when I want multi-region or offline writes without a coordinator and without losing updates, for example counters, sets and collaborative text.

The problem. In multi-leader or leaderless systems and offline apps, replicas change independently and must merge later. Last-write-wins loses data, and hand-written merge code is error-prone. A CRDT (Conflict-free Replicated Data Type) is a data structure whose design guarantees that merging any set of replica states in any order, with duplicates, gives the same result everywhere. So replicas can converge without a coordinator or locks.

The three math properties of merge: commutative (A merge B = B merge A), associative (grouping does not matter) and idempotent (merging the same thing twice is harmless). These make network reordering and duplicate delivery irrelevant.

Examples built up from simple.

  1. G-Counter (grow-only counter). Each replica keeps its own slot in a vector, for example {A:3, B:5}. A replica only increments its own slot. Merge takes the per-slot maximum. The total is the sum of the slots (8). Replica C seeing {A:3, B:4} and later {A:3, B:5} just takes the maxima.
  2. PN-Counter. Two G-counters, one for increments, one for decrements. Value = P minus N.
  3. G-Set. Elements can only be added. Merge is union.
  4. OR-Set (observed-remove set). Each add gets a unique tag. A remove deletes only the tags it has observed. A concurrent add of the same element has a new tag so it survives ("add wins"), which fixes the "deleted item reappears" or "add lost" problem of naive sets.
  5. Sequence CRDTs for text editing (used by collaborative editors, with libraries such as Automerge or Yjs).

Where they are used. Redis Enterprise active-active, Riak data types, Azure Cosmos DB and Akka distributed data, collaborative documents, presence and "likes".

Limits. They cannot enforce invariants that need global knowledge: "stock never below 0" or "only one person gets the last ticket", because two replicas can each approve a purchase of the last item. Those still need coordination (reservations, a leader, escrow). Metadata also grows (tombstones, tags) and needs periodic garbage collection. Operation-based variants need reliable causal delivery; state-based ones send whole states, so delta variants are used.

Merge has to be commutative, associative and idempotent. A grow-only counter keeps one number per replica; merge takes the maximum per replica and the value is the sum. A PN-counter uses two of them for increments and decrements. A set that only grows merges by union; an OR-set tracks add tags so removes work. Where it fits: like counts, presence, shopping carts (Redis Enterprise active-active, Riak, Automerge). Where it does not: anything with a global invariant such as "balance never below zero" or "only one winner", because replicas cannot know about each other's pending changes. Cost: metadata and tombstones that grow.

Remember: CRDTs merge without coordination, but they cannot enforce a global limit.

5. Partitioning (sharding)

What is partitioning (sharding), how is it different from replication, and how do you choose the key? Basic

Partitioning splits the data so each node holds only a slice, which scales storage and write throughput. Replication keeps copies of the same data for availability. Real systems do both: split into partitions, then replicate each one. The shard key decides everything, so I pick one with high cardinality, even spread and the access pattern I query by.

Why partition. A single machine has a ceiling on disk, memory and write throughput. When the data (say 20 TB) or the write rate (say 200k writes per second) is beyond that, you split it into partitions (also called shards), each on its own node, and route each request to the right one. Each node now handles about 1/N of the data and traffic.

Choosing the key, by walking through a case. An orders table. Option 1, partition by created_at range: all today's writes hit the latest partition (a hot spot) while old partitions idle. Option 2, by country: a handful of values, and "US" is huge, so very uneven. Option 3, hash of customer_id: even spread, and "all orders for customer X" is one partition. If you also need "orders by status across all customers", that becomes scatter-gather or needs a secondary index.

A good key checklist.

  • High cardinality (many distinct values) so data can spread.
  • Evenly accessed, no single value hit much harder than others.
  • Matches the most common query so one request touches one partition.
  • Stable: if the key changes, the row has to move.

Secondary indexes are the other cost. A local index (each partition indexes its own rows) makes writes cheap but queries on that field scatter to all partitions. A global index (partitioned by the indexed value) makes reads cheap but writes touch two partitions and are usually asynchronous. Finally, plan for resharding: fixed partition counts well above node count (for example 1024 partitions on 10 nodes) make it easier to add nodes.

Two main methods. Range partitioning (key ranges, like HBase or Spanner): range scans are cheap, but sequential keys such as timestamps pile all writes on the latest range (a hot spot). Hash partitioning (hash of the key, like Cassandra or DynamoDB): load spreads evenly, but range queries must hit every partition. A good key example: user_id for user data. A bad one: country (few values, skewed) or created_at (hot latest range). Queries that do not include the shard key become scatter-gather across all partitions, slow and costly, and joins across shards are very hard.

Remember: replication = copies, partitioning = slices. Range keeps order, hash spreads load. The key choice is the design.

Explain consistent hashing. Why is it better than hash(key) mod N, and how does rebalancing work? Intermediate

With hash(key) mod N, changing N changes the answer for almost every key, so adding one node reshuffles nearly all data. Consistent hashing puts both nodes and keys on a ring. A key belongs to the first node clockwise from it, so adding or removing a node only moves the keys next to it, about 1/N of the total.

The problem with modulo. A simple router uses node = hash(key) mod N. With 4 nodes, key hash 10 goes to node 2. Add a fifth node and 10 mod 5 is node 0. Most keys change node (only about 1 in N stay put), so adding capacity triggers a huge data move, and in a cache it means nearly every entry misses at once, dumping load on the database.

Consistent hashing, step by step.

  1. Imagine the hash output range (0 to 2^32 - 1) bent into a circle.
  2. Hash each node's name onto the circle: A at 100, B at 400, C at 800.
  3. To place a key, hash it and walk clockwise to the first node. Key at 450 goes to C, key at 900 wraps around to A, key at 50 goes to A.
  4. Add node D at 600. Only keys between 400 and 600 (previously C's) now belong to D. All other keys are untouched. Remove a node and only its keys go to its clockwise neighbour.

Why virtual nodes. With only a few points on the ring, slices have random sizes, so one node may own 40% of the keys. And when a node dies, its whole load falls on a single neighbour. Giving every physical node, say, 128 positions on the ring evens out sizes by the law of large numbers, spreads a failed node's load over many neighbours, and lets you give a larger machine more positions.

Where it appears. Dynamo and Cassandra (token ring), memcached client libraries, CDNs and load balancers using ring-hash for stickiness, and a variant in many sharded stores. Redis Cluster uses a related idea: 16384 fixed hash slots, each mapped to a node, and resharding moves slots.

Rebalancing mechanics. New node joins, takes ownership of its ranges, streams the data for those ranges from the previous owners (throttled), and only then starts serving them; the old owner deletes afterwards. During the move, reads may need to check both. Pitfalls: consistent hashing balances keys, not load, so a hot key stays hot (see the hot partition question), and a plain ring has no notion of racks or zones unless you add placement rules for replicas.

Plain consistent hashing gives uneven slices, so each physical node is placed on the ring many times as virtual nodes (for example 100 to 256). That evens out load and lets a new node take a little from many neighbours. A bigger machine can take more virtual nodes. Replicas are typically the next R distinct nodes clockwise. The alternative is a fixed number of slots assigned to nodes: Redis Cluster has 16384 hash slots, and moving a slot moves its keys; Kafka and many databases use a fixed partition count that you move between brokers. Rebalancing then copies the moved ranges in the background and flips ownership at the end, ideally throttled so it does not hurt live traffic.

Remember: ring + clockwise owner + virtual nodes. Add or remove a node and only about 1/N of the keys move.

One partition gets far more traffic than the others (hot key or hot shard). What do you do? Intermediate

First find out whether it is one hot key (a celebrity user, a viral item) or a bad key design that sends a whole range to one shard. For a hot key I cache it in front, replicate it for reads, or split the key into several sub-keys. For a bad design I change the shard key.

What it looks like. One node shows 95% CPU and throttling errors while the rest of the cluster is at 10%. Adding more nodes does not help, because the extra nodes do not receive the hot traffic. The first step is therefore diagnosis, not scaling.

Diagnose which of three situations you are in.

  1. One hot key. A celebrity's profile or a viral product. Check per-key request metrics or a top-keys report.
  2. Hot range from a bad key. Time-based or auto-increment keys on a range-partitioned store send all new writes to the last partition.
  3. Hot tenant or skewed data. One customer is 100 times bigger than the others.

Fixes for each.

  • Hot read key: cache it (in-process plus Redis), add read replicas, request coalescing so concurrent misses make one backend call, and even a CDN for public data.
  • Hot write key (counter, like count): write sharding. Instead of one row likes:post42, keep likes:post42:0 to likes:post42:9. Each write picks a random suffix; a read sums the ten. Or buffer increments in memory and flush in batches.
  • Sequential keys: prefix with a hash or bucket, e.g. (user_id % 16, timestamp), or use hash partitioning. Cost: range scans by time now need 16 queries merged.
  • Hot tenant: isolate it on a dedicated shard, or sub-shard by a second column.

Mention the managed-database angle. Services like DynamoDB split partitions automatically and adaptive capacity helps, but a single hot item is still bound by per-partition limits, so the design fixes above still apply. Also set up alerts on partition-level metrics, because cluster-average metrics hide the problem.

Tools by cause. Hot reads on one key: in-process or Redis cache, read replicas, request coalescing. Hot writes on one key (a counter, a trending item): split into key#0 .. key#9 by adding a random suffix, write to a random one, and sum on read. Sequential keys (timestamps, auto-increment) on a range-partitioned store: hash-prefix the key or bucket it, for example by hash(user) % 16 plus time. A hot tenant: give that tenant its own shard. Hashing alone does not fix a single hot key, since the key still maps to one place. Autoscaling the whole cluster is the expensive last resort, because only one shard is hot.

Remember: diagnose the hot key vs the bad key design. Cache and replicate hot reads, split hot writes with a suffix.

How do you handle a query or transaction that spans partitions? Senior

First I try to avoid it by choosing the shard key so related data lives together, such as all of one customer's rows on one shard. If I cannot, a read becomes scatter-gather over all shards, and a write needs a distributed transaction (two-phase commit) or a saga with compensations.

Why it is hard. Inside one partition a database can use local locks and one log to make a transaction atomic. Across partitions, each has its own log and its own failures. To make "debit account A on shard 1 and credit account B on shard 2" all-or-nothing, you need a protocol that all participants follow even if some crash halfway.

Strategy 1: avoid it by design. Choose the partition key so that things that change together live together. Orders and their line items share the customer or order id key. A transfer between two accounts is the classic case that cannot always be co-located, so decide whether it must be atomic.

Strategy 2: two-phase commit. A coordinator prepares all shards then commits (see the 2PC question). Works, but holds locks across round trips and blocks if the coordinator fails. Distributed SQL databases (Spanner, CockroachDB) do this under the hood but make it reliable by running each shard as a Raft group, so no single machine failure blocks the commit. You still pay extra latency, especially across regions.

Strategy 3: saga. Do local steps one by one with compensations. Eventual consistency, no cross-shard locks, but intermediate states are visible and you must write the compensation logic.

Reads across shards. A query without the shard key is sent to every shard and the results merged (scatter-gather). The response time is that of the slowest shard, so a 99th percentile of 50 ms per shard turns into a much worse tail with 100 shards (probability that at least one is slow rises quickly). Mitigations: a secondary or search index, a pre-aggregated or denormalised read model (CQRS), restricting the fan-out with a filter on the shard key, and timeouts with partial results.

Decision: first try co-location, then the saga for business flows that tolerate eventual consistency, and use distributed transactions only for the few operations that truly need atomicity.

Design moves: keep an aggregate in one partition (orders with their items), denormalise or duplicate data to avoid cross-shard joins, maintain a separate global secondary index or search index for lookups by another field (accepting that it is updated asynchronously), and prefer eventual consistency with sagas to 2PC for business flows. Databases that offer cross-shard transactions (Spanner, CockroachDB, Vitess with care, MongoDB multi-document) pay with extra round trips and lock holding. Latency of scatter-gather is set by the slowest shard, so it gets worse as shard count grows.

Remember: best cross-shard transaction is the one you design away with the right key. Otherwise saga over 2PC.

How do you add shards or rebalance a live sharded database without downtime? Senior

I never move data in place. I copy the affected key ranges to the new shard in the background while the old shard keeps serving, catch up on changes made during the copy, then switch routing for those ranges in one small step and delete the old copy later. The routing table and the cutover must be atomic and reversible.

Why it is risky. Data is moving while users read and write it. If a write lands on the old shard after the copy finished, it is silently lost on the new shard. If two shards both think they own a range, writes diverge. The whole procedure is about never having a moment where ownership is ambiguous.

Step by step (the usual online resharding recipe).

  1. Plan with many small logical partitions. Hash keys into, say, 1024 fixed slots and map slots to nodes. Rebalancing then means moving whole slots, never rehashing keys. (Redis Cluster, Kafka partitions and many sharded stores work like this.)
  2. Snapshot copy. Stream the slot's data from the source shard to the new shard, throttled so live traffic is not hurt.
  3. Catch up. Apply all changes made since the snapshot, using the source's change log (CDC), until the new shard is a few milliseconds behind.
  4. Cutover. Briefly block or queue writes for that slot (milliseconds), apply the last changes, then update the routing metadata (stored in a consensus store or a config service) so the slot points to the new shard. Clients with an old routing cache get a "moved" redirect (Redis uses MOVED) and refresh.
  5. Verify and clean up. Compare counts or checksums, watch error rates, keep the old data for a while in case of rollback, then delete it.

Pitfalls: secondary indexes and cross-shard references that must move together, hot slots (moving one slot may not fix a hot key), the extra load during the copy on the source, and routers caching stale maps. Always rehearse on a copy of production data, and make the move resumable so a crash in the middle does not start over.

Remember: fixed slots, copy, catch up with the change log, atomic routing switch, delete last.

6. Consensus, leaders and locks

What is consensus, and where does it show up in systems you use? Basic

Consensus is getting several nodes to agree on one value, even when some nodes crash and messages are delayed. It is the building block for leader election, a replicated log, distributed locks and configuration. I rarely implement it. I use systems built on it: etcd, ZooKeeper, Consul, Kafka's KRaft controllers, and databases like Spanner or CockroachDB.

The problem. Several nodes must agree on one thing, such as "who is the leader right now?", "was this transaction committed?", or "what is the next entry in the log?". It sounds easy, but with crashes and delayed messages it is tricky. If two nodes each decide differently (two leaders), data gets corrupted. Consensus is a protocol that guarantees agreement (no two nodes decide differently), validity (the decided value was proposed by someone) and termination (eventually everyone decides, as long as enough nodes work).

The FLP result, in one line. In a fully asynchronous network where even one node may crash, no algorithm can guarantee both safety and termination. Real protocols (Paxos, Raft) keep safety always, and give up guaranteed termination: they make progress only when the network behaves well enough for long enough, usually using timeouts and randomisation.

How a majority makes it work. A decision is final once a majority accepted it. Since any two majorities share a member, a later proposal that also needs a majority will meet at least one node that remembers the earlier decision, and so can be forced to repeat it. That overlap is the core trick of every consensus algorithm.

What it gives you in practice.

  • Replicated state machine: every node applies the same log in the same order, so all copies behave as one reliable service (etcd, Consul, CockroachDB ranges, Kafka KRaft).
  • Leader election and leases.
  • Atomic configuration and membership changes.
  • Linearizable reads and writes for the small data it stores.

Costs. At least one round trip to a majority per decision (a few milliseconds in a zone, tens to hundreds across regions), throughput limited by the leader, and no progress without a majority. So use it for control-plane data and use cheaper replication for bulk data. Mention that consensus tolerates crash failures; if nodes can be malicious (Byzantine), you need other protocols (PBFT, blockchain consensus) which cost far more.

The algorithms (Paxos, Raft, ZAB) all follow the same rule: a decision needs a majority of nodes, and any two majorities overlap, so two different decisions can never both succeed. That gives safety (never two different answers) even under partitions, and progress only while a majority can talk. The price is latency (a network round trip to a majority per decision) and unavailability on the minority side. So I keep consensus for small, critical metadata (who is leader, config, locks), not for bulk data.

Remember: consensus = majority agreement on one value. Use it for small critical data, through etcd or ZooKeeper.

Why do consensus clusters use odd sizes and a majority? Basic

A majority of N nodes is floor(N/2) + 1. Any two majorities share at least one node, which prevents two conflicting decisions. Odd sizes are used because an even size adds cost without adding fault tolerance: 3 and 4 nodes both survive only one failure, and 5 and 6 both survive two.

The rule. A majority (quorum) of N voters is any group bigger than half: floor(N/2) + 1. For N = 3 that is 2; for 5 it is 3; for 4 it is 3; for 6 it is 4.

Why a majority is the right size. Take any two groups that each hold more than half of the nodes. Together they would need more than N nodes if disjoint, which is impossible, so they must share at least one node. That shared node is the safety net: if group 1 elected leader X in term 5, then group 2 trying to elect leader Y in the same term needs votes from a node that already voted for X in that term, so it cannot happen. In log replication, a new leader's voters overlap with the set that stored every committed entry, so the committed entry cannot be lost.

Placement. A 3-node cluster in 3 availability zones survives a zone loss; three nodes in one zone do not. Two zones plus tie-breaker (a small witness node in a third site) is a common compromise. Larger clusters are rarely better: 5 is plenty for most control planes, as more nodes mean more replication traffic and slower commits.

A cluster of 2f + 1 nodes tolerates f failures. A 3-node cluster needs 2 up, a 5-node cluster needs 3 up. Even more important is what happens in a partition: with 4 nodes split 2 and 2, neither side has a majority, so the cluster stops. With 5 nodes split 3 and 2, the side with 3 carries on. More nodes also make every write slower (more acks and more messages), so 3 or 5 is the norm, 7 is rare. For multi-zone safety, spread nodes over 3 zones, so losing one zone still leaves a majority.

How does Raft work? Explain leader election and log replication. Intermediate

Raft keeps one leader at a time. Clients send writes to the leader, which appends them to its log and copies them to followers. An entry is committed when a majority has stored it, and only then applied. If followers stop hearing from the leader, one becomes a candidate and wins a new term by getting votes from a majority.

Why Raft exists. Paxos is correct but famously hard to understand and to build a full system from. Raft (2014) splits consensus into three independent parts that can be taught and implemented separately: leader election, log replication and safety rules. The goal is the same: a cluster that behaves like one reliable state machine.

Node roles. Each node is a follower (passive), a candidate (asking for votes) or the leader (handles all client writes). Time is divided into terms, numbered 1, 2, 3, ...; each term has at most one leader. Every message carries the sender's term, and a node that sees a higher term immediately steps down to follower, which is how stale leaders are neutralised.

Election, as a timeline.

  1. Followers expect a heartbeat from the leader. Each has a random election timeout (about 150 to 300 ms in the paper's examples).
  2. The first to time out becomes a candidate, increments its term (say 7), votes for itself and sends RequestVote to the others.
  3. A node votes for a candidate if it has not voted in this term yet and the candidate's log is at least as up to date as its own (higher last term, or equal last term and longer log).
  4. With votes from a majority, the candidate becomes leader and starts sending heartbeats. If votes split, everyone times out again at different random times and retries.

Log replication. The leader appends the client command to its log, sends AppendEntries to followers (also acts as heartbeat), and when a majority has stored the entry, marks it committed, applies it to its state machine and replies to the client. Followers learn the commit index in later messages and apply too. If a follower's log differs, the leader walks back to the last matching index and overwrites the follower's conflicting suffix, so logs converge on the leader's.

Safety in one sentence. Because a candidate needs a majority and may only win with a log at least as up to date as that majority's, any elected leader already contains every committed entry. A leader also only commits entries from its own term directly (older ones are committed along with them), which avoids a subtle overwrite scenario.

Extras: membership changes via joint consensus or single-server changes, log compaction by snapshots, and linearizable reads through the leader (read index or lease). Pitfalls: a lagging disk (fsync) on the leader stretches everything, and a node isolated from the network that keeps timing out can inflate its term and disrupt a healthy cluster, which is why implementations add a pre-vote phase.

Election: each follower has a randomised election timeout (the paper suggests 150 to 300 ms). When it expires, the node increments its term (a logical epoch number), votes for itself and asks others for votes. A node gives one vote per term, and only to a candidate whose log is at least as up to date as its own. This rule means a new leader always has every committed entry. Randomised timeouts make split votes rare. Replication: the leader sends AppendEntries with the new entries (also used as heartbeat). Once a majority has the entry, the leader marks it committed and tells followers. A stale leader from an old term is rejected because its term number is lower.

Remember: terms + randomised timeouts + majority commit. The vote rule ("log at least as up to date") keeps committed entries safe.

How would you implement leader election for an application service? Intermediate

I would not write my own. I use a lock with a lease in etcd, ZooKeeper or Consul (or a framework on top, like Curator or Kubernetes leader election): each instance tries to create the same key with a time-to-live, the winner is leader and keeps renewing it, and if it dies the key expires and another instance takes over.

What the application needs. Say you run 3 instances of a scheduler service, but exactly one should send the nightly emails. You need the instances to agree on "who is the leader", to notice when that instance dies, and to pick a new one, all without ever having two active at once for long.

Use an existing coordination service. Basic recipe with leases:

  1. Every instance tries to create the key /service/leader with its own id and a TTL of, say, 15 seconds, only if the key does not exist (atomic create or compare-and-set).
  2. Exactly one succeeds and is the leader. The others set a watch on the key.
  3. The leader renews (heartbeats) the lease every 5 seconds. If it crashes or is cut off, renewals stop and the key expires after 15 s.
  4. The watchers see the key vanish, race to create it again, and one wins.

ZooKeeper variant. Each candidate creates an ephemeral sequential node under /election, getting names like n_0001, n_0002. The lowest is leader. Each other candidate watches only its immediate predecessor, so when the leader dies just one node wakes up instead of all (this avoids the herd effect). Ephemeral nodes disappear when the client session ends.

Ready-made options. Kubernetes Lease objects (client-go leader election), Curator's LeaderLatch (ZooKeeper), Consul sessions and locks, etcd's election package, Spring Integration lock registries, or a row in your database with a heartbeat column if you already have one.

The safety gap you must mention. Leader election tells you who should be leader, but the old leader may not yet know it lost the lease (a GC pause or partition). If it then writes to a shared resource, there can be two writers. Two defences: the leader should treat itself as dead a little before its lease ends (stop work when it cannot renew), and shared resources should reject writes with a stale fencing token (next two questions).

ZooKeeper: instances create ephemeral sequential nodes under a path, and the lowest sequence number is leader; each other watches only the one just before it, to avoid a herd of notifications. etcd: a key attached to a lease, created only if absent (compare-and-set transaction). Two safety points. The old leader may not know it lost leadership (GC pause, network issue), so any write it makes must be protected by a fencing token (the revision or term number) checked by the resource. And the leader must stop work when it cannot renew, before its lease ends. A simpler option for many apps is a database row lock or a Kubernetes Lease object.

Remember: lease on a consensus store, renew to stay leader, fencing token to be safe.

What is split brain, and how do you prevent it? Intermediate

Split brain is when two nodes both believe they are the leader and both accept writes, usually after a network partition or a long pause. It corrupts data because the two histories diverge. I prevent it with majority quorums (only the side with a majority may elect a leader), term or epoch numbers, and fencing tokens so a stale leader's writes are rejected.

What it looks like in an incident. A network link between two data centres flaps. The standby thinks the primary is dead and promotes itself. But the primary is alive and still accepts writes from clients that can reach it. Now two nodes both say "I am the leader" and both accept writes. For minutes, orders are written to two separate databases with colliding ids. When the link heals, the two histories cannot be simply merged, and someone must throw one away (losing real customer data).

Prevention layers, from weakest to strongest.

  1. Quorum voting. Only a group with a strict majority may elect a leader or accept writes. A minority partition goes read-only or stops. For this to work you need an odd count (or a tie-breaker witness) and nodes spread over at least 3 failure domains.
  2. Epochs (terms). Every leader has an increasing number. Followers reject messages from lower epochs, so a stale leader's replication attempts fail and it discovers the new term and steps down.
  3. Fencing tokens. The storage or downstream service checks the token on every write, rejecting any older than what it has seen. This protects even when the stale leader does not know it is stale.
  4. STONITH / resource fencing. In older two-node clusters, the survivor kills the other (power switch, cloud API) or revokes its access to shared storage (SCSI reservation) before taking over. Brutal but effective.
  5. Leader-side self-check. A leader that cannot reach a majority within a lease period stops serving writes.

Common causes beyond partitions: a long GC or VM pause, a misconfigured health check, a standby promoted by a human while the old primary is still up, and clock jumps affecting lease expiry. In the interview, show you can name the cause, the detection (conflicting leaders in metrics, diverging log positions) and the repair process, which may require manual reconciliation.

A majority quorum makes two leaders in the same term impossible: the minority side cannot get enough votes. But an old leader on the minority side does not instantly learn it was replaced. It will keep trying to write until it notices. That is the gap that fencing closes: every leadership grant carries a number that only grows, and the storage layer refuses any request with an older number. Two-node setups are a trap: with no tie-breaker they cannot tell a dead peer from a partition, so add a third node or a witness. Older HA clusters use STONITH ("shoot the other node in the head"): physically power off the suspect node before taking over.

Remember: majority for deciding, fencing token for enforcing. Never run a two-node cluster without a tiebreaker.

What is a fencing token, and why is a lock or lease without one unsafe? Senior

A fencing token is a number that increases every time the lock is granted. The client sends it with every write, and the storage rejects any write with a lower token than one it has already seen. Without it, a client whose lease expired during a pause can wake up, still believe it holds the lock, and overwrite newer data.

The problem in plain terms. A lock with a time limit (a lease) is meant to give one process exclusive access. But a process cannot reliably know whether its lease is still valid at the moment it acts. Between checking "I hold the lock" and performing the write, it can be paused for any length of time (GC, CPU starvation, VM migration, a slow network packet sitting in a queue). When it resumes, the lock has been given to someone else, yet it proceeds, and two writers overlap. No client-side check can close this gap, because the pause can happen right after the check.

The fix: let the resource reject stale holders. The lock service hands out a number that increases with every grant (33, 34, 35, ...). The client attaches its number to every request to the resource. The resource remembers the highest number it has accepted and rejects any request with a lower one. So the sleeper's late write with 33 is refused after 34 has been seen. The check is done by the party that holds the data, so it does not rely on anyone's timing.

Where the token comes from. ZooKeeper's zxid or the node's version, etcd's modification revision, a Raft term plus index, a database sequence incremented in the same transaction that grants the lock, Kafka's producer epoch (this is exactly how Kafka fences zombie producers) and its consumer group generation id.

Using it in a database. Store last_token alongside the row and write with UPDATE doc SET body=?, last_token=? WHERE id=? AND last_token <= ?. If zero rows change, the writer is stale.

Limits. The resource must be able to compare tokens. Calling a third-party API that does not support tokens cannot be fenced, so locks there are only best-effort. And fencing does not stop a stale holder from doing harmless reads or from reading stale data; it protects writes. That is why a distributed lock "for correctness" without fencing is considered unsafe.

The classic failure: client 1 gets the lock with token 33, then freezes for 40 seconds in a GC pause. The lease expires, client 2 gets token 34 and writes. Client 1 wakes up, has no way to know, and writes with token 33. The storage has already seen 34, so it rejects 33. The key point is that the check happens at the resource, not at the lock service: no timing assumption on the client can be trusted. ZooKeeper's zxid or a node's version, etcd's revision, or a database row's version column work as tokens. The resource must support the check, which is why locks over arbitrary external APIs are best-effort only.

Remember: a lock tells me who should write, a fencing token lets the resource refuse who should not.

When do you need a distributed lock, and what are the options? Intermediate

I need one only when several processes must not touch the same resource at once and a database constraint or atomic update cannot do the job. I first try to avoid the lock: a unique constraint, a conditional update or a single consumer per key is simpler and safer. If a lock is truly needed I use a lease on etcd or ZooKeeper, or Redis for efficiency-only cases.

Start by asking whether you need a lock. A distributed lock is slow, complex and has subtle failure modes, so alternatives come first. Common replacements:

GoalLock-free solution
Only one row per keyUnique index; the second insert fails
Update only if unchangedOptimistic locking: UPDATE ... WHERE id=? AND version=?
Decrement stock safelyUPDATE stock SET qty=qty-1 WHERE id=? AND qty>0
One consumer per entityPartition by key so each key has one owner thread or instance
Same job not run twiceIdempotent job plus a "claimed by" row with a unique key

When a lock really is needed: coordinating work on something that is not a single database row, such as a leader doing cluster-wide maintenance, a shared file or external resource, or a long multi-step operation.

Two quality levels.

  • Efficiency lock (avoid wasted work). If it fails and two workers run, you only waste time. A Redis lock is good enough: 
    SET lock:report-42 <random-id> NX PX 30000     # acquire, auto-expires in 30 s
-- release only if I still own it (Lua script, atomic):
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) end
    The random id stops me from deleting a lock someone else acquired after mine expired.
  • Correctness lock (data must not be corrupted). Use a consensus-based service (ZooKeeper, etcd, Consul) or the database, and always combine with fencing tokens at the resource.

Operational rules. Always use a TTL (a crashed holder must not block forever). Choose the TTL longer than the operation, or renew it with a watchdog thread. Keep the critical section short. Decide what happens when the lock service is unreachable (fail closed for correctness, fail open for efficiency). Log lock acquisition and release with the owner id to debug stuck locks.

Two different purposes. Efficiency locks avoid duplicate work (two workers both rebuilding a report): an occasional double run is fine, so Redis SET key value NX PX 30000 is enough, and release only if the value is still mine. Correctness locks protect data (one writer at a time): need a consensus store plus fencing tokens, because leases can expire during pauses. Often the lock can be replaced: UPDATE ... WHERE version = ?, a unique index (INSERT fails for the second caller), SELECT ... FOR UPDATE in a single database, or partitioning work so each key has one owner. Always set a TTL so a crashed holder does not block everyone.

Remember: prefer a constraint or conditional update to a lock. Redis lock for efficiency, consensus store plus fencing for correctness.

What is Redlock, and why is it controversial? Senior

Redlock is a Redis-based algorithm that takes the same lock on several independent Redis nodes (usually 5) and treats it as acquired if a majority granted it within a short time. It is controversial because its safety relies on bounded clock drift and bounded pauses, and it has no fencing token, so a paused client can still act after its lock expired.

What the algorithm does. The client takes the current time, tries to set the same lock key (with random value and TTL) on 5 independent Redis servers one by one, with small timeouts. If it got the lock on at least 3 (a majority) and the elapsed time is less than the lock TTL, it considers the lock acquired with the remaining time as its validity. Otherwise it releases on all. The idea is to survive the failure of single Redis nodes, improving on a lock in one Redis that might lose it on failover (because Redis replication is asynchronous, the lock key may not have reached the replica that gets promoted).

The critique (Martin Kleppmann, 2016).

  1. Timing assumptions. Safety depends on bounded network delay, bounded process pauses and bounded clock drift. Real systems violate these (a GC pause after acquiring the lock, a clock jump on a Redis node making a key expire early).
  2. No fencing token. Redlock gives each holder a random value, not a monotonically increasing number, so the storage cannot reject a stale holder.
  3. Therefore it is "neither fish nor fowl": too heavy for a simple efficiency lock (5 servers) and not safe enough for a correctness lock.

The defence (Salvatore Sanfilippo, Redis's author). Most practical uses are efficiency locks where rare violations are tolerable, and he argued that the clock assumptions are reasonable in practice. The debate is a good thing to cite to show you know both sides.

My recommended position. Efficiency: one Redis instance with SET NX PX (or Redisson-style helpers) is usually enough; accept the small risk. Correctness: use a linearizable store (ZooKeeper, etcd, or a database row) and a fencing token validated by the resource. If a Redis-based lock must protect important data, treat it as a hint and still protect writes with a version check in the database.

The critique (Martin Kleppmann's well-known article) is that a lock for correctness needs a monotonically increasing token that the resource checks, and Redlock does not give one. Redis's author argued that it is fine for most real uses, which are efficiency locks. My position: for efficiency (avoid duplicate work) a single Redis lock or Redlock is acceptable; for correctness use ZooKeeper, etcd or a database, with fencing. Also note that a single Redis with async replication can lose a lock on failover, which is another reason not to trust it for safety.

Remember: Redlock is fine to save work, not to protect data: no fencing token, timing assumptions.

When would you use ZooKeeper, etcd or Consul, and what should you not put in them? Intermediate

I use them for small, critical coordination data: leader election, locks and leases, service discovery, and shared configuration, where I need linearizable reads and writes and change notifications. I do not use them as a general database or for high-volume data, because every write goes through consensus.

What they are. A small, replicated, strongly consistent key-value store whose entire job is to be the one reliable source of truth for coordination. Internally they run a consensus protocol (ZooKeeper: ZAB, etcd and Consul: Raft), so reads and writes are linearizable, and the data survives the loss of a minority of nodes.

Features that make them useful beyond a plain key-value store.

  • Watches: a client asks to be notified when a key or directory changes, so no polling is needed.
  • Ephemeral keys or leases: a key tied to a client session or TTL that is deleted automatically when the client dies. That is the building block for liveness, locks and election.
  • Compare-and-set and transactions on keys, and a monotonically increasing version or revision (useful as a fencing token).
  • Hierarchical keys (ZooKeeper znodes, etcd prefix ranges).

What they are used for.

UseExample
Leader election and locksKubernetes controllers, Patroni for PostgreSQL
Service discovery and healthConsul registrations with health checks
Dynamic config and feature flagsWatch a key, reload on change
Cluster membership and metadataKubernetes stores all object state in etcd; Kafka (older) and HBase used ZooKeeper

What not to put there, and why. Every write is replicated to a majority and fsynced, so throughput is modest (thousands of writes per second) and the data set is kept small (etcd defaults to a space quota of a couple of GB, and is recommended to stay in the single-digit GB). Do not store user data, big values, high-churn counters, or use it as a queue. Avoid thousands of clients each holding many watches, or heartbeating too often, as that can overload it.

Operational notes. Run 3 or 5 nodes across zones; keep it on fast disks (fsync latency matters most); back up regularly; and remember that if you lose the majority, everything that depends on it (leader election, config reads) stalls, so design clients to survive its brief unavailability.

They keep a small replicated state (megabytes, not gigabytes) in memory with a consensus log, and offer watches (get told when a key changes) and ephemeral keys or leases (the key disappears when the owner dies). Limits: write throughput of a few thousand per second, latency tied to a majority round trip, and a minority side that cannot serve. Kubernetes uses etcd for all cluster state; Kafka historically used ZooKeeper and now uses its own Raft (KRaft) controllers. Keep payloads small, avoid chatty clients, and never put business data or large blobs in there.

Remember: small, critical, coordination data only. Not a database.

What is a gossip protocol, and what is it used for? Intermediate

In gossip, every node periodically picks a few random peers and exchanges what it knows. Information spreads through the cluster like a rumour, reaching all N nodes in about log N rounds without any central coordinator. It is used for membership, failure detection and spreading small bits of state in large clusters, for example in Cassandra, Consul (Serf) and Redis Cluster.

Why not just broadcast. If one node told all N nodes about every change, it would be a bottleneck and a single point of failure, and the traffic would grow with N squared when everyone does it. Gossip keeps each node's load constant: every second, talk to maybe 3 random peers.

How it works, with numbers. Node A learns that node X is down. In round 1 it tells 3 peers; in round 2 each of those tells 3 more (about 9 new nodes know), then about 27, and so on. The number of informed nodes roughly multiplies each round, so a 1000-node cluster is informed in around 7 to 10 rounds, a few seconds with a 1 s interval. Even if some messages are lost or nodes are down, the many random paths make the spread reliable.

What it carries. A membership list with a heartbeat counter per node. Each node increments its own counter and gossips the table; if a node's counter has not increased for a while in anyone's view, it is suspected, and after a longer time declared dead. Good implementations (SWIM, used by Consul and memberlist) add indirect probes: before declaring X dead, ask other nodes to ping X, which avoids false alarms from a single bad link.

Trade-offs. Gossip is scalable, decentralised and robust, but it is eventually consistent: for a few seconds different nodes have different views, and it gives no ordering or agreement guarantees. So it is good for membership and monitoring data, and wrong for things that need one agreed answer, such as who is the leader or whether a lock is held; use consensus for those.

Remember: random peers, exchange state, log N rounds. Great for membership and failure detection, not for agreement.

What is the difference between crash faults and Byzantine faults, and which does your system need to handle? Senior

A crash fault means a node stops or goes silent but never lies. A Byzantine fault means a node can behave arbitrarily: send wrong data, contradict itself, or act maliciously. Almost all systems inside one organisation (etcd, ZooKeeper, Kafka, databases) assume crash faults only, because it is much cheaper. Byzantine tolerance is for settings where participants do not trust each other, such as public blockchains.

The cost difference, in numbers. Crash-fault consensus (Raft, Paxos) needs 2f + 1 nodes to tolerate f failures: 3 nodes for 1 failure. Byzantine fault tolerance (PBFT and relatives) needs 3f + 1 nodes: 4 nodes for 1 failure, with more message rounds (every node talks to every other) and cryptographic signatures. It is slower and harder to scale, so it is only used where it is needed.

A concrete example. If one Raft follower returns a corrupted log entry because of a bug, Raft is not designed for it and may misbehave. A Byzantine protocol would outvote the bad node, since other nodes would see that its answer disagrees with the honest majority.

What I do in practice inside a company. Treat nodes as crash-only, but defend against the non-malicious "almost Byzantine" cases that really occur: checksums on data at rest and on the wire (disk and memory corruption exist), authenticated and authorised service calls so a compromised service cannot impersonate another, schema validation of messages, and quorum reads or scrubbing in storage systems (HDFS and S3 verify checksums). If an interviewer asks about blockchains or multi-party systems with untrusted members, then say BFT protocols (PBFT, Tendermint) are the answer, with the 3f + 1 cost.

Remember: crash faults need 2f + 1 nodes, Byzantine faults need 3f + 1. Internal systems assume crash-only and add checksums and authentication.

7. Distributed transactions, idempotency and messaging

How does two-phase commit (2PC) work, and what is its main weakness? Intermediate

A coordinator asks every participant to prepare (promise it can commit and hold its locks). If all say yes, the coordinator logs the decision and tells everyone to commit; if any says no, everyone aborts. The main weakness is blocking: if the coordinator dies after participants voted yes, they must wait, holding locks, until it returns.

The problem it solves. A transaction touches data in several databases (or services): move 100 from account A (database 1) to account B (database 2). Either both changes happen or neither. If database 1 commits and database 2 fails, money disappears. A single database solves this with its own log, but across two independent systems you need a protocol that makes them agree on the outcome.

The two phases.

  1. Phase 1, prepare (voting). The coordinator sends PREPARE to every participant. Each does all the work except the final commit: it checks constraints, takes locks, and writes the changes durably to its log so it can commit even after a crash. Then it replies YES (and promises to commit if told) or NO.
  2. Phase 2, commit or abort. If everyone said YES, the coordinator writes COMMIT to its own durable log (this is the real decision point) and sends COMMIT to all. If any said NO or timed out, it sends ABORT. Participants finish and release locks, then acknowledge.

Why it blocks. After saying YES, a participant cannot decide on its own, because the coordinator might have decided either way. If the coordinator crashes after collecting votes and before telling everyone, participants are stuck in the in-doubt state. They must keep holding the row locks, which block other transactions, until the coordinator recovers and reads its log. In practice, stuck in-doubt transactions are a real operational pain (for example in XA setups), often requiring manual resolution.

Other costs. Extra round trips, forced disk writes at several points, all participants must be up for commit, and reduced throughput because locks are held across network waits. The failure of the coordinator is a single point of failure unless the coordinator itself is replicated by consensus (as Spanner and CockroachDB do for each transaction record).

When to use it: inside one database cluster (it is how distributed SQL databases commit across shards), or XA across a couple of trusted, fast resources (a database plus a JMS broker). When not to: across independent microservices owned by different teams, over slow links, or for long-running business processes. Use sagas instead. Three-phase commit adds a pre-commit phase to reduce blocking but only works with bounded delays, so it is rarely used.

After a yes vote a participant has given up the right to decide alone, so it cannot safely commit or abort by itself. That "in doubt" state can freeze rows for a long time and block other transactions. 2PC also adds latency (two round trips plus forced log writes) and couples the availability of every participant. It is fine inside one database engine or with XA across a few trusted resources; it is a poor fit across independent microservices, which is why sagas are common there. Three-phase commit reduces blocking on paper but assumes bounded delays, so it is rarely used.

Remember: prepare, then commit. Blocks if the coordinator fails after "yes". Avoid across microservices.

What is a saga, and how do orchestration and choreography differ? Intermediate

A saga splits a business transaction into a sequence of local transactions, one per service, and undoes completed steps with compensating actions if a later step fails. It gives eventual consistency without distributed locks. Orchestration has a central coordinator that tells each service what to do next; choreography has services react to each other's events with no central brain.

Why not just a transaction. In a microservice system, order, inventory and payment each own their own database. You cannot hold a database transaction over all three (2PC is too tight a coupling and blocks). A saga replaces one big atomic transaction with a chain of small local ones. Each local transaction commits immediately and publishes an event or response. If a step fails, the saga runs compensating transactions to semantically undo the earlier steps, in reverse order.

Walkthrough: place an order.

  1. Order service: create order in PENDING state (local commit).
  2. Inventory service: reserve 2 units (local commit).
  3. Payment service: charge 50 (fails: card declined).
  4. Compensation: Inventory releases the 2 units; Order marks the order CANCELLED.

On success the last step marks the order CONFIRMED.

Two coordination styles.

OrchestrationChoreography
ControlA saga orchestrator sends commands and tracks stateServices publish events; others react
VisibilityThe flow is written in one place; easy to monitor and debugThe flow is implicit across services; hard to see
CouplingServices depend on the orchestrator's commandsLoose, but risk of cyclic dependencies

Rules that make sagas work. Each step and each compensation must be idempotent and retryable, because messages repeat. State lives in the saga (an order status field or the orchestrator's persisted state) so recovery after a crash can continue or compensate. Some actions cannot be undone (an email, a shipment), so place them last or make them "pending" until the saga completes (the pivot step idea). Because sagas lack isolation, other transactions can see intermediate states, so use countermeasures such as "semantic locks" (a PENDING flag), commutative updates, or re-reading values before acting.

Example: place order, reserve stock, charge payment, ship. If payment fails, the saga runs "release stock" and "cancel order". Orchestration is easier to follow, monitor and change, but adds a central component. Choreography is loosely coupled and good for 2 to 3 steps, but the flow becomes hard to see as it grows. Rules for steps: every step and every compensation must be idempotent and retryable, since messages repeat. Compensation is a business-level undo (refund, not "delete payment"), and some actions cannot be undone (email sent, parcel shipped), so put those last or add a pending state. Saga steps are visible while in progress (stock reserved but not yet paid), so design the UI and states for that: there is no isolation.

Remember: local transactions plus compensations. Idempotent steps, no isolation, orchestrate when it gets complex.

What is the transactional outbox pattern, and what problem does it solve? Intermediate

It solves the dual-write problem: updating my database and publishing a message are two systems, so one can succeed while the other fails. With an outbox I write the business change and the event row in the same local database transaction, and a separate relay publishes the outbox rows to the broker afterwards, at least once.

The dual-write problem, in detail. A service must (1) update its database and (2) tell other services via a message broker. These are two different systems with no shared transaction. In code:

orderRepo.save(order);           // step 1: DB commit
broker.publish(orderPlacedEvent); // step 2: network call

If the process crashes or the broker is down between the lines, the order exists but nobody hears about it, and downstream stock is never reserved. Swapping the lines is no better: an event goes out for an order that later rolls back. Retrying the publish in code does not help if the process itself dies.

The outbox solution. Add an outbox table in the same database. In one local transaction, insert the order and an outbox row (event id, aggregate id, type, payload, created time):

BEGIN;
INSERT INTO orders(...) VALUES (...);
INSERT INTO outbox(id, aggregate_id, type, payload) VALUES (:eid, :oid, 'OrderPlaced', :json);
COMMIT;

The database guarantees both or neither. Then a separate process, the relay, takes unsent outbox rows and publishes them, marking them sent only after the broker confirms. If the relay crashes after publishing but before marking, it publishes again after restart. So delivery is at-least-once and consumers must deduplicate by the event id.

Two relay implementations.

  • Polling publisher: a scheduled job runs SELECT ... WHERE sent = false ORDER BY id LIMIT 100, publishes, then updates. Simple; adds some latency and DB load; use FOR UPDATE SKIP LOCKED with several relays.
  • Change data capture (CDC): a tool such as Debezium tails the database transaction log and streams outbox inserts to Kafka. Lower latency, no polling load, and ordering follows the log.

Operational notes: delete or archive old outbox rows; keep payloads small; use the aggregate id as the partition key to preserve per-entity ordering; monitor the lag between the outbox insert and publication. The consumer-side mirror is the inbox pattern (store processed event ids) for idempotent handling.

The bug it fixes: save(order); publish(OrderPlaced). If the process crashes between them, the order exists but no event is ever sent. Reverse the order and you can publish an event for an order that was rolled back. With the outbox both rows commit or neither does. The relay is either a poller (select unsent rows, publish, mark as sent) or change data capture on the outbox table (Debezium reading the database log). Since the relay can publish twice after a crash, consumers must be idempotent, and the event id is the dedupe key. Cleanup of old rows is needed. Ordering per aggregate is kept by publishing in outbox order with the aggregate id as the partition key.

Remember: never write DB and broker separately. Outbox row in the same transaction, relay publishes, consumers are idempotent.

What is idempotency, and how do you make a payment API idempotent? Intermediate

An operation is idempotent if doing it twice has the same effect as doing it once. For a payment API I require a client-generated idempotency key on each request. The server stores the key with the result in a table with a unique constraint, and if the same key comes again it returns the stored response instead of charging again.

The definition with examples. An operation is idempotent when running it once or ten times leaves the system in the same final state. SET balance = 100 is idempotent; ADD 100 to balance is not. Deleting a file by name is idempotent. Creating an order from a POST is not unless you make it so.

Why we need it. Because of the timeout problem, the only safe way for a client to recover from "I do not know if it worked" is to try again. Retries only work if repeating cannot cause a second effect. Without it, a mobile user on a bad network taps Pay twice and is charged twice. Message brokers also deliver at least once, so consumers face duplicates too.

The idempotency-key pattern, step by step.

  1. The client generates a unique key (a UUID) for the logical operation, sends it in a header (Idempotency-Key), and reuses the same key on every retry of that operation.
  2. The server looks up the key. Not found: record it as IN_PROGRESS, do the work, store the response, mark DONE, all in one transaction with the business change if possible.
  3. Found and DONE: return the stored response without doing the work again.
  4. Found and IN_PROGRESS: another attempt is still running, so return 409 Conflict (or wait). A unique constraint on the key makes this race-safe.
  5. Found with a different request body hash: reject (the client reused a key wrongly).

Which layer should do it. If the payment goes to a downstream processor, pass the key down too (Stripe, Adyen and others accept one), so a retry between your service and theirs is also safe. For a consumer of events, the equivalent is a processed_events(event_id) table or a natural upsert.

Natural idempotency is best. Prefer "set" over "add", use client-supplied resource ids with PUT (PUT /orders/{uuid}), and use conditional updates. Retention: keep keys long enough to cover client retries (hours to days), and clean up afterwards. Pitfall: storing the key in a different system or transaction from the effect reopens the gap you were trying to close.

Why it matters: after a timeout the client cannot tell if the charge happened, so it must be allowed to retry safely. Flow: insert the key (unique) in the same transaction as the charge; on a duplicate key, return the saved result. Handle three cases: first call (do the work), repeat after completion (return saved response), repeat while the first is still running (return 409 or wait). Also compare the request body hash with the saved one and reject a reused key with different content. Keep keys for a time window (Stripe documents 24 hours). HTTP: GET, PUT and DELETE are meant to be idempotent, POST and PATCH are not by default. Natural idempotency is best: "set status to PAID" repeats safely, "add 10 to balance" does not.

BEGIN;
INSERT INTO idempotency(key, request_hash, status) VALUES (:k, :h, 'IN_PROGRESS');  -- unique(key)
-- on duplicate key: SELECT the stored response and return it
charge(...);
UPDATE idempotency SET status='DONE', response=:resp WHERE key=:k;
COMMIT;

Remember: unique key plus stored response. The client may retry, the server never repeats the effect.

Explain at-most-once, at-least-once and exactly-once delivery. Basic

At-most-once sends and never retries, so messages can be lost but never repeat. At-least-once retries until acknowledged, so nothing is lost but duplicates happen. Exactly-once means each message has its effect once. It cannot be guaranteed by the network alone, so in practice I build it as at-least-once delivery plus idempotent processing.

The three guarantees, by who is responsible for what.

SemanticSender behaviourFailure outcomeTypical use
At-most-onceSend once, no retryMessage can be lost, never duplicatedMetrics, logs where loss is fine
At-least-onceRetry until acknowledgedNever lost, may be duplicatedMost business events
Exactly-once (effect)At-least-once plus dedupe or transactionsEach message takes effect oncePayments, inventory

Why the sender cannot do better. After sending, the sender waits for an acknowledgement. If none arrives, it cannot distinguish "message lost" from "ack lost". It must either resend (risking a duplicate) or not (risking loss). That is the fundamental choice, and why "exactly once delivery" is not possible as a pure network property.

A consumer example with a queue or Kafka.

At-most-once:   commit offset -> process message     (crash in between: message skipped, lost)
At-least-once:  process message -> commit offset     (crash in between: reprocessed, duplicate)

To get an effect of exactly once on top of at-least-once, make the processing idempotent. Options: a unique business key (insert with ON CONFLICT DO NOTHING), an upsert, a table of processed event ids checked in the same transaction as the business write, or storing the consumer offset in the same database transaction as the results.

The question to ask in a design: "what happens if this message is processed twice?" If the answer is "something bad", add idempotency. If you cannot tolerate loss, never choose at-most-once.

With a message consumer the ordering of "process" and "commit offset" decides the semantic. Commit first, then process: a crash loses the message (at-most-once). Process first, then commit: a crash means it is processed again (at-least-once). Choose at-least-once and handle duplicates, for example with a processed-message-id table or natural idempotent updates. At-most-once only fits data you can lose, like metrics samples.

Remember: commit before work = may lose. Commit after work = may repeat. Exactly-once = repeat plus idempotent.

Is exactly-once delivery possible? Kafka says it supports "exactly-once". What does that cover? Senior

Exactly-once delivery over an unreliable network is impossible (the Two Generals problem: the sender can never be sure the last message arrived). What is possible is exactly-once effect inside a controlled boundary. Kafka's exactly-once covers read-process-write between Kafka topics, not side effects outside Kafka like an email or a call to another API.

Why true exactly-once delivery is impossible. This is the Two Generals problem. Two parties can only communicate over an unreliable channel, and want to be sure the other received a message. A acknowledges B's message, but A cannot know whether its acknowledgement arrived, so it needs an acknowledgement of that, and so on forever. Any finite protocol leaves a last message whose loss cannot be detected. So "delivered exactly once" can never be guaranteed purely by the network.

What vendors really mean. They guarantee that the effects inside their own system happen once. Kafka's feature has three parts:

  1. Idempotent producer (enable.idempotence=true, default in recent clients): each producer has an id and each partition a sequence number. A retry of the same batch is recognised by the broker and dropped, so retries cannot create duplicates or reorder.
  2. Transactions: a producer can write to several partitions and commit offsets atomically (sendOffsetsToTransaction), so "consume, transform, produce" is all or nothing.
  3. Consumer isolation: with isolation.level=read_committed downstream consumers only see committed transactional records.

Where the guarantee ends. The moment your processing writes to a database, sends an email, charges a card or calls an HTTP API, that action is outside Kafka's transaction. If the consumer crashes after the side effect but before the commit, the message is reprocessed and the effect repeats. You need the same tools as before: idempotent writes keyed by event id, or an outbox/inbox pattern, or storing the offset in the same database transaction as the result and seeking to it on startup.

How to phrase it in an interview. "Exactly-once processing is an end-to-end property built from at-least-once delivery and idempotent or transactional effects. Kafka gives it inside Kafka; for anything outside, I add idempotency myself."

Kafka gives two pieces: the idempotent producer (producer id and sequence numbers let the broker drop duplicate sends caused by retries) and transactions (a consumer's output records and its offset commit are written atomically; consumers use isolation.level=read_committed to skip aborted data). Together a Kafka Streams style job gets exactly-once processing. The moment my consumer writes to a database or calls an HTTP API, the guarantee is gone, and I need an idempotent write (upsert by event id) or to store the offset together with the result in the same database transaction.

Remember: exactly-once is a boundary, not a magic property. Outside the boundary use idempotency.

How do you keep message ordering in a distributed system? Intermediate

Global ordering is expensive and rarely needed. I keep order per key: send all messages for one entity (an order, a user) to the same partition with that entity id as the key, and have one consumer thread handle a partition. Order across different keys is not guaranteed and I design so it does not matter.

Why total order is a bad goal. A single global order means one sequencer (one partition, one leader) through which everything passes. That caps throughput at one machine and creates a single bottleneck. Most business rules only need order among events of the same entity: the events of order 17 must be processed as created, paid, shipped, but order 17 and order 18 can interleave freely.

The standard technique: key-based partitioning. A broker like Kafka keeps strict order inside one partition only. If the producer uses the entity id as the message key, all events for that entity hash to the same partition, so they are stored and read in order. Within a consumer group each partition goes to exactly one consumer at a time, so one thread sees that entity's events sequentially. Scale by adding partitions (different entities spread out).

Ways ordering gets broken.

  • No key or different keys for related events (the "paid" event keyed by payment id rather than order id lands on another partition).
  • Producer retries with several in-flight requests: batch 1 fails and is retried after batch 2 succeeded. Fix: idempotent producer, or max.in.flight.requests.per.connection of 5 or less with idempotence (which preserves order).
  • Parallel processing of one partition's messages by a thread pool in the consumer.
  • Changing partition count, which changes the key-to-partition mapping for new messages.
  • Events from different sources (an API call and a Kafka event) racing.
  • Retry topics: a failed message sent to a retry queue is processed after later ones.

Defence in depth. Put a version or sequence number in each event. The consumer applies an event only if its version is exactly last-applied plus one; if it is older it ignores it (already applied), and if it is newer it parks or fetches the missing data. This also makes processing idempotent. Where order truly must be global (rare), use a single partition or a consensus-ordered log and accept the throughput limit.

Breakers of order: multiple producers without a key, a retry that lands after a later message (Kafka needs the idempotent producer, which keeps order with several in-flight requests), consumers that process one partition's messages in parallel threads, and a rebalance mid-processing. If events can still arrive out of order (different topics, retries), put a version or sequence number in each event and let the consumer ignore older ones, or buffer and reorder, or use state checks ("cancel before create": park it until the create arrives or reject safely).

Remember: order per key through the partition key. Add a version in the event for the leftover cases.

How do you prevent lost updates in read-modify-write sequences across requests or services? Intermediate

A lost update happens when two callers read the same value, both change it, and the second write overwrites the first. I prevent it by making the change atomic in the database, or by optimistic locking: add a version column and write only if the version is still what I read.

What the bug looks like. Two requests both read qty = 5. Each computes 5 - 1 = 4 and writes 4. Two items were sold but the stock dropped by one. The second write replaced the first without knowing about it, which is why it is called a lost update. It happens whenever the application does read, compute, write as separate steps, even inside two separate transactions at the default isolation level (read committed in most databases). Snapshot isolation does not always prevent it either, although some databases (PostgreSQL at repeatable read) will abort the second one.

The ladder of fixes, preferring the simplest.

  1. Make the change a single atomic statement. The database does the read and write under its own row lock: 
    UPDATE stock SET qty = qty - 1 WHERE id = 7 AND qty > 0;   -- rows affected = 0 means sold out
  2. Optimistic locking when the computation needs application code. Read the row with its version, and write only if the version is unchanged: 
    SELECT qty, version FROM stock WHERE id = 7;            -- qty=5, version=12
UPDATE stock SET qty = 4, version = 13 WHERE id = 7 AND version = 12;
-- 0 rows updated: someone else won; re-read and retry
    JPA's @Version does exactly this and throws OptimisticLockException.
  3. Pessimistic locking: SELECT ... FOR UPDATE inside a transaction blocks others on that row until commit. Good when conflicts are frequent and retries would be wasteful; it holds locks, so keep transactions short.
  4. HTTP level: return an ETag on GET, require If-Match on PUT, and answer 412 Precondition Failed when it no longer matches. This extends optimistic locking to API clients (including a user who left a form open for an hour).
  5. Single writer: route all updates for an entity to one owner, such as a Kafka partition keyed by the entity id.

Choosing. Low contention and a computation in code: optimistic. High contention on a hot row (flash sale): atomic statement or pessimistic, and think about sharding the counter. Across microservices there is no shared database transaction, so make one service the owner of the number and let others ask it.

Options, simplest first. (1) Atomic statement: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0; check the row count. (2) Optimistic locking: UPDATE ... SET qty = ?, version = version + 1 WHERE id = ? AND version = ?; zero rows updated means someone else got there first, so re-read and retry (JPA @Version does this). (3) Pessimistic lock: SELECT ... FOR UPDATE, simple but holds locks and does not span services. (4) For HTTP APIs use ETag with If-Match so a stale client gets 412. (5) Across services, route all changes for the entity through one owner or one queue partition. Do not rely on an application-level "check then write" with no atomicity, nor on a distributed lock if a conditional write can do it.

Remember: atomic update or version check. Never read, compute and blindly write.

8. Resilience, retries and rate limiting

How do you choose timeouts, and what is a deadline? Intermediate

Every remote call gets a timeout, because without one a slow dependency holds my threads forever. I set it from measured latency, for example a bit above the p99 of that call, and keep the timeouts shorter as I go down the call chain. A deadline is the absolute time by which the whole request must finish, passed along so each hop knows how much time is left.

Why a missing timeout is a bug. Many client libraries default to infinite or very long waits (some HTTP clients and JDBC drivers). If the server hangs, each request thread parks forever. With a pool of 200 threads and 200 stuck requests, the service stops answering everything, including endpoints that never touch the slow dependency. A timeout converts an unbounded wait into a bounded, handled error.

Which timeouts exist. Connect timeout (how long to establish a TCP and TLS connection, keep it short, around 1 s), read or socket timeout (silence on an open connection), and a total request timeout (overall cap including everything). Also a timeout for acquiring a connection from the pool, which people forget.

Picking a number. Measure the dependency's latency distribution. A common start is slightly above the p99 or p99.9 under normal load, so that only genuinely abnormal calls time out. Too low and you create errors and retries from normal variance; too high and you do not protect the thread pool. Then check it fits the whole chain.

Budget example. User waits at most 3 s. Gateway to Service A has 3 s. A calls B and C in sequence; if B has a 2 s timeout, C has only 1 s left, not another 2 s. Passing a deadline solves this: the request carries "must finish by 12:00:03.000", each hop computes the remaining time, sets its own timeout from it, and skips work if there is no time left. gRPC deadlines are propagated automatically; with HTTP, send a header such as X-Request-Deadline or the remaining milliseconds.

Also stop work after a timeout (cancel the downstream call, check cancellation in long loops), otherwise the timeout hides rather than removes the load.

Two kinds: connect timeout (short, like 1 second) and read or request timeout. A per-hop timeout alone is not enough: if the gateway gives up after 5 seconds but the service keeps working for 10, I waste capacity on answers no one will read, and the client's retry doubles the load. With a deadline (gRPC propagates it automatically; with HTTP pass a header or remaining budget), the downstream call can fail fast or skip work when the budget is gone. The rule: the caller's timeout must be longer than the sum of what it waits for, including retries, and the outermost one is the smallest budget you give the user.

Remember: always set a timeout; callee's budget must fit inside the caller's. Pass a deadline down.

How should retries be done? What are exponential backoff with jitter and a retry storm? Intermediate

I retry only idempotent operations and only for transient errors (timeouts, 503, connection reset), with a limited number of attempts, exponential backoff (wait 100 ms, 200, 400...) and random jitter so clients do not all retry at the same moment. A retry storm is when many clients retry at once against a struggling service and keep it down.

Why retry at all. Many failures are brief: a pod restarting, a dropped connection, a brief leader election, a throttle. A retry after a short wait often succeeds and hides the problem from users. But a careless retry can double charges and can turn a small problem into an outage, so the rules matter.

The rules.

  1. Only retry safe operations. Reads, idempotent writes, or writes with an idempotency key. Retrying a non-idempotent POST can duplicate the effect.
  2. Only retry transient errors: timeouts, connection resets, 503, 429 (after waiting as told). Never retry 400, 401, 403, 404, 422; they will fail the same way.
  3. Bound the attempts (3 is common) and the total time (respect the deadline).
  4. Back off exponentially: wait 100 ms, 200 ms, 400 ms, 800 ms so the dependency gets room to recover.
  5. Add jitter (randomness) so clients spread out.
  6. Retry at one layer and have the others fail fast.

Why jitter matters, with numbers. A service blips for one second and 1000 clients fail together. With pure exponential backoff all 1000 retry at exactly 100 ms, again together at 300 ms, and so on, each wave a spike. With full jitter each picks a random time in the window, so the 1000 arrivals spread over the interval and the load is smooth.

Retry amplification. If the browser retries 3 times, the gateway 3 times, the service 3 times, one click can produce 27 calls to the database layer exactly when it is least able to cope. This is the heart of the retry storm: a slowdown increases traffic by a large factor, which deepens the slowdown. Defences are retry budgets (retries limited to about 10 percent of normal traffic, as in Envoy and gRPC retry throttling), a circuit breaker, and honouring Retry-After.

Prefer hedging (sending a second request after the p95 time) only for idempotent reads and with care, since it also adds load.

Jitter matters: without it, a thousand clients that failed together retry together, in synchronised waves. A common formula is "full jitter": sleep = random(0, min(cap, base * 2^attempt)). Do not retry 4xx client errors. Retry at one layer only: if three layers each make up to 4 attempts (the first try plus 3 retries), one user call can become 4 x 4 x 4 = 64 calls to the bottom service. Add a retry budget (for example retries at most 10 percent of traffic), respect Retry-After, and combine with a circuit breaker.

for (int attempt = 0; attempt < MAX; attempt++) {
    try { return call(); }
    catch (TransientException e) {
        long cap = Math.min(MAX_WAIT_MS, BASE_MS << attempt);
        Thread.sleep(ThreadLocalRandom.current().nextLong(cap + 1)); // full jitter
    }
}
throw new GaveUpException();

Remember: idempotent only, bounded, exponential backoff plus jitter, retry at one layer.

What is a circuit breaker, and how do you configure it? Intermediate

A circuit breaker stops calling a dependency that is failing, so my threads are not tied up and the dependency can recover. It has three states: closed (normal), open (calls fail immediately), and half-open (a few trial calls to see if it recovered). It opens when the failure rate or slow-call rate over a window passes a threshold.

The analogy and the problem. An electrical breaker trips when a circuit draws too much, to stop a fire. A software breaker trips when a dependency is clearly failing, to stop wasting resources and to give the dependency room to recover. Without one, every call to a dead service waits for its full timeout (say 2 s), holds a thread for that time, and the caller degrades even though the outcome is certain.

The states in plain words.

  • Closed: normal. Calls pass through. The breaker records successes and failures in a sliding window (last 50 calls, or last 30 seconds).
  • Open: the failure or slow-call rate crossed the threshold (e.g. at least 50 percent of the last 50 calls). For the wait period (say 30 s), every call fails instantly with a "circuit open" error, without touching the network. The caller returns a fallback.
  • Half-open: after the wait, allow a small number of probe calls (say 5). If they succeed the breaker closes; if they fail it re-opens for another wait. This prevents a recovering service from being hit by the full load immediately.

Worked example. Recommendations API starts timing out. Of the last 50 calls, 30 fail (60 percent), so the breaker opens. For 30 s the product page shows "popular items" from a cache instead, in microseconds. At 30 s five probes go through: 4 succeed, so it closes and normal traffic resumes.

Configuration advice. Set a minimum number of calls before the failure rate is meaningful (otherwise 1 failure out of 2 trips it). Include slow calls as failures, since slowness is what exhausts threads. Count only server-side or network failures, not 404s or validation errors. Use one breaker per dependency (and per endpoint class if their health differs). Expose breaker state as a metric and alert on open.

Limits. A breaker without a sensible fallback only converts slow errors into fast errors, which is still better, but not enough for critical flows. State is per instance, so each learns separately (usually acceptable). It complements timeouts, retries and bulkheads; it does not replace them.

Typical settings (Resilience4j names): sliding window of 20 to 100 calls, failure rate threshold 50 percent, slow call threshold, wait duration in open state (10 to 60 s), a few permitted calls in half-open, and a minimum number of calls before judging. When open I return a fallback: cached data, a default, or a clear error. Count timeouts and 5xx, not business errors like 404. Watch out: a breaker per dependency (or per host) is better than one global one, and breaker state per instance means each instance learns separately.

Remember: closed, open, half-open. Fail fast with a fallback, probe before closing.

What are bulkheads, and how do they limit the blast radius of a slow dependency? Intermediate

A bulkhead gives each dependency its own limited pool of resources (threads, connections, semaphore permits), like watertight compartments in a ship. If one dependency becomes slow, it can only exhaust its own pool, and calls to the others still work.

The ship analogy, and the real failure. A ship is divided into watertight compartments, so a hole floods one compartment and not the whole hull. In software, the "water" is the slowness of a dependency, and the "hull" is your shared thread pool or connection pool.

Failure without bulkheads, by numbers. A web service has one pool of 200 threads. Normally a call to Recommendations takes 20 ms, so it uses about 1 thread at a time at 50 requests per second. Recommendations degrades and each call now takes 10 s. At the same 50 requests per second, 500 threads would be needed, so all 200 are soon stuck waiting. Login and checkout, which share the pool, now cannot get threads and time out. A non-critical dependency has taken everything down.

With bulkheads. Give Recommendations its own pool of 20 slots. When all 20 are busy, further recommendation calls are rejected immediately (or served from a fallback), and the other 180 threads continue serving login and checkout normally. The damage is limited to the compartment.

Ways to implement it.

Sizing: pool size is roughly requests per second times average latency (Little's law), plus headroom. Pitfall: too many tiny pools waste capacity, so isolate by criticality and failure behaviour rather than creating one for every call. Combine with timeouts and a circuit breaker so slots free up quickly.

Without bulkheads, one shared thread pool or connection pool is a shared fate. A slow recommendations service holds all 200 request threads, and then even login and checkout cannot get a thread: a local slowdown becomes a site-wide outage. With separate pools (say 20 threads for recommendations, 50 for payments) the slow one fills its 20 and further calls are rejected quickly while the rest of the site runs. Implementations: separate thread pools or semaphores (Resilience4j Bulkhead), separate HTTP client connection pools, separate queues per tenant or priority, even separate deployments for critical and non-critical traffic. Use together with timeouts and circuit breakers.

Remember: separate pools per dependency, so one slow neighbour cannot eat all my threads.

What is backpressure, and how is it different from load shedding? Intermediate

Backpressure is the slow consumer telling the producer to slow down, so work does not pile up without limit. Load shedding is the overloaded service deliberately rejecting some work (for example with 503 or 429) so the rest finishes on time. Backpressure pushes the problem upstream; shedding protects the service when upstream cannot or will not slow down.

The root problem. If producers can send faster than consumers can process, something has to give. With an unbounded queue, nothing visibly gives at first: the queue grows, latency of every item grows (an item waits behind everything ahead of it), and finally memory runs out or items become so old that the work is useless. The aim of both techniques is to keep queues short and decisions explicit.

Backpressure: slow the source. The consumer signals "I am full" and the producer waits, buffers or sends less. Examples you can name:

  • A bounded blocking queue: put() blocks when full, so the producing thread slows down.
  • Reactive Streams (Project Reactor, RxJava, Akka Streams): the subscriber calls request(n) and the publisher sends no more than n.
  • TCP flow control: the receiver advertises a window; the sender stops when it is zero.
  • Kafka: consumers pull at their own pace, so the broker retains the backlog as lag; producers are throttled by quotas and buffer limits.
  • HTTP/2 and gRPC flow control windows.

It works when the producer can actually slow down (a batch job, an internal pipeline). It does nothing when the producers are independent external users who will not wait.

Load shedding: drop work on purpose. When overloaded the service rejects part of the incoming load so that the accepted part is served fast. Rejecting 20 percent of requests with a fast 503 is better than serving 100 percent at 30 s latency, when nobody is waiting any more.

  • Reject early, before doing expensive work, ideally at the edge.
  • Choose what to drop: low-priority endpoints, free tier users, background work first.
  • Prefer newest-first or "drop requests already past their deadline" so you do not work on abandoned requests.
  • Signal the client: 429 or 503 with Retry-After, and make clients back off.

Relationship. Backpressure moves the queue upstream where it can be managed; shedding discards at the point of overload. Real systems use both, plus capacity limits per client and autoscaling (which is too slow for sudden spikes).

Backpressure examples: a bounded queue that blocks or rejects the producer when full, reactive streams request(n), TCP windows, Kafka consumers that simply fall behind (the lag is the buffer). Unbounded queues are a trap: they hide overload until memory runs out, and by then the latency for everything is huge. Shedding rules: reject early and cheaply, drop low-priority or non-critical work first, prefer failing new requests over timing out old ones already in progress, and tell clients to back off (429 or 503 with Retry-After). Adaptive concurrency limits (limit in-flight requests based on measured latency) are an advanced version.

Remember: bounded queues everywhere. Slow the sender if you can, drop the lowest-value work if you cannot.

Compare token bucket, leaky bucket, fixed window and sliding window rate limiting. Intermediate

Token bucket refills tokens at a steady rate up to a capacity and each request takes one, so it allows short bursts but limits the average. Leaky bucket drains requests at a constant rate, smoothing bursts. Fixed window counts per time slot and is simple but allows double the limit at a boundary. Sliding window counts over the last N seconds and removes that boundary problem. I usually pick token bucket.

What rate limiting is for. Protect a service from one client using too much (accident or abuse), keep things fair between tenants, control cost, and slow brute-force attacks. The algorithm decides how a limit like "100 requests per minute" is measured. Each has a different feel when a client sends a burst.

Token bucket worked example. r = 5 tokens per second, b = 10. A client idle for a while has a full bucket (10). It sends 10 requests at once: all allowed, bucket 0. The 11th is rejected. After 1 s there are 5 tokens, so 5 more are allowed. Over a long period the average is 5 per second, but short bursts of 10 are fine. Token vs leaky. Token bucket is "meter" style (the request goes through immediately if there are tokens). Leaky bucket is "shaper" style (requests wait in a queue and leave at a steady rate), useful to protect a downstream that needs a flat load. Choose token bucket for APIs, leaky when smoothness matters, sliding window counter when you want simple, accurate per-window limits.

The fixed window flaw: with a limit of 100 per minute, a client sends 100 at 12:00:59 and 100 at 12:01:01, so 200 within two seconds. Sliding window log (store each timestamp) is exact but uses memory; sliding window counter (weighted sum of current and previous window) is a cheap approximation. Token bucket needs two numbers per client (tokens, last refill time), allows bursts up to capacity and is the common choice for APIs (used by Stripe, AWS API Gateway). Leaky bucket suits shaping traffic to a downstream system that needs a smooth rate. Reply with 429 Too Many Requests and a Retry-After header.

Remember: token bucket = average rate plus burst. Fixed window double-spends at the edge.

How do you enforce a rate limit across many servers? Senior

The usual answer is a shared counter in Redis, updated atomically with a Lua script (or INCR plus EXPIRE for fixed windows), keyed by user or API key. For very high traffic I let each node keep a local budget and sync periodically, accepting a small error. I place the limiter at the gateway so rejected requests are cheap.

The difficulty. With 10 API servers behind a load balancer, a per-server counter allows up to 10 times the intended limit because each server only sees a tenth of the traffic. The counter must be shared, or the servers must coordinate in some way, and doing this should not become the bottleneck.

Approach 1: central store (most common). Keep the counter in Redis, keyed by client and window, e.g. rl:{apiKey}:{minute}. The check must be atomic, or two servers will both read 99 and both allow the 100th and 101st. Use INCR (atomic) and set an expiry on first increment, or a Lua script that runs as one step. A token bucket in Lua reads tokens and timestamp, refills, decrements, and writes back in one script call. Cost: one network round trip per request (about 0.5 ms in the same zone), and Redis capacity; shard keys across Redis nodes for scale.

Approach 2: local counters with periodic sync. Each server allows a share of the limit locally (global 1000/s over 10 servers is 100/s each, or a dynamic share based on observed traffic) and exchanges usage every few hundred ms. No per-request network call, but the limit can be exceeded by the sync interval's worth of traffic, and uneven load wastes some quota. Used when limits are generous and approximate is fine.

Approach 3: at the edge. Enforce in the API gateway, CDN or service mesh (Envoy global rate-limit service, Kong, cloud WAF). Rejecting there keeps bad traffic away from your app, and many gateways ship a Redis-backed implementation.

Decisions to state in an interview.

  • Fail-open or fail-closed if Redis is down. Fail-open protects availability but exposes you; fail-closed protects the backend but may cause an outage. Often: fail-open for general APIs with a local fallback limit, fail-closed for login or sensitive endpoints.
  • The limit key: API key, user, IP (beware NATed clients), tenant, endpoint. Cost-weighted limits for expensive calls.
  • Response: 429 with Retry-After and headers like X-RateLimit-Remaining.
  • Clock: use the Redis server time rather than app server clocks for window boundaries.

Trade-offs. A central Redis check adds a network hop per request and Redis becomes a dependency: if it is down, decide to fail open (allow, risky) or fail closed (reject, safe but harmful). The read-then-write race is the classic bug: two nodes both read 99 and both allow, so the check and decrement must be one atomic operation (Lua script, or INCR then compare). Local approach: split the global limit into per-node shares, or sync counts every few hundred milliseconds, which is cheaper but allows overshoot. Other design points: limit key (user, IP, tenant, endpoint), different tiers per plan, returning remaining quota in headers (X-RateLimit-Remaining), and a separate stricter limit for expensive endpoints.

9. Caching strategies and consistency

What are the common caching strategies: cache-aside, read-through, write-through and write-behind? Basic

Cache-aside: the application checks the cache, on a miss reads the database and fills the cache. It is the default and I use it most. Read-through is the same but the cache library loads the data. Write-through writes to cache and database together, so the cache is always fresh but writes are slower. Write-behind writes to the cache and saves to the database later, which is fast but can lose data.

Why cache. A database read might take 5 to 50 ms and the database can only serve so many queries per second. A memory cache like Redis answers in about 0.5 ms and can serve tens of thousands to hundreds of thousands of reads per second. If 90 percent of reads hit the cache, the database sees only 10 percent of the traffic. The price is that there are now two copies of the data, and they can disagree.

The four patterns, as flows.

  1. Cache-aside (lazy loading). Read: check the cache; on a miss, read the database, put the result in the cache with a TTL, return it. Write: update the database, then delete (invalidate) the cache key. The application owns all the logic.
  2. Read-through. The application only talks to the cache layer, and the cache itself loads from the database on a miss. Same effect as cache-aside, but the loading code lives in the cache provider.
  3. Write-through. A write goes to the cache, which synchronously writes the database before returning. The cache is always fresh, reads are fast, and the cost is slower writes and caching data that may never be read.
  4. Write-behind (write-back). A write goes to the cache and returns at once; the cache flushes to the database later in batches. Very fast and good at absorbing write bursts, but data not yet flushed is lost if the cache node fails, and ordering and failure handling get complex.

Which to choose. Default to cache-aside: simple, resilient when the cache is cold or down. Use write-through when readers must see fresh data and write volume is modest. Use write-behind for high-volume, loss-tolerant data such as counters or view counts. Always set a TTL so mistakes heal. Cache-aside is simple and resilient (the cache can be empty or down and the app still works), but the first read after a miss is slow and the cache can go stale. Write-through keeps reads fast and consistent, costing write latency and caching data that may never be read. Write-behind batches writes for speed, and risks loss if the cache node dies before flushing, so it fits counters and non-critical data. Always set a TTL (time to live) as a safety net, and decide what to cache: read-heavy, rarely changing, expensive to compute.

Remember: cache-aside by default, always with a TTL. Write-through for freshness, write-behind for speed at a loss risk.

How do you keep a cache consistent with the database? What races exist in cache-aside? Intermediate

On a write I update the database first and then delete the cache key (not update it), plus a TTL as a safety net. Deleting is safer than updating because two concurrent writers can set the cache in the wrong order. Even so a small stale window remains, so I accept eventual consistency or use versioned values.

Why it is hard. The cache and the database are two separate stores with no shared transaction. Any sequence of "write one, then the other" can be interleaved with another request's sequence, and with network failures between the steps. Perfect consistency is not available cheaply, so the goal is to make the stale window small and self-healing.

The recommended write path. Update the database, then delete the cache key. The next read misses and reloads fresh data. Why delete instead of update the cache? If two writers update concurrently, W1 may write the database first but W2 may write the cache last, leaving the cache holding W1's older value while the database holds W2's. A delete does not carry a stale value, so it avoids this class of race.

The remaining race, as a timeline.

t1  Reader R: cache miss on key K, reads DB -> old value v1
t2  Writer W: updates DB to v2
t3  Writer W: deletes K from cache
t4  Reader R: (slow) puts v1 into cache   <- stale, and stays until TTL

This needs R to be slower than the whole write, so it is rare, but under load it happens. Options to shrink it:

  • TTL as the safety net, shorter for important data.
  • Delayed double delete: delete again about a second after the write, to catch a late refill. Pragmatic, not perfect.
  • Versioned values: store the row version in the cache entry, and only set when the version is greater than the cached one (a conditional set).
  • Leases (as in Facebook's memcache): a miss gets a lease token; an invalidation voids outstanding tokens, so the late stale set is rejected.
  • CDC-driven invalidation: a process reads the database change log and deletes or updates cache keys in commit order, which also covers writes from other services and failed deletes.

Other pitfalls. Wrong order (delete cache, then update DB) lets a reader refill the old value in between. A failed cache delete after a committed database write leaves stale data, so retry it or push it through a queue. Multi-level caches (local plus Redis) need invalidation broadcast. If the business cannot tolerate staleness for a value, do not cache it, or read it from the database for that path.

The classic race: a reader misses, reads the old value from the database, and is slow. Meanwhile a writer updates the database and deletes the key. Then the slow reader puts the old value into the cache, and it stays stale until the TTL expires. It is rare but real. Mitigations: short TTL, delete again after a short delay (delayed double delete), store a version number in the value and refuse to overwrite with an older one, or invalidate from the database change log (CDC) so deletes follow the real commit order. Never "update the DB then update the cache" from two writers, and never delete the cache before the database update (a reader will refill the old value). If the cache delete fails, retry it or rely on TTL.

Remember: database first, then delete the key, always with a TTL. Perfect consistency needs versions or CDC.

What is a cache stampede (thundering herd), and how do you prevent it? Intermediate

A stampede happens when a hot key expires and hundreds of requests all miss at the same moment and hit the database together, which can take it down. I prevent it by letting only one request rebuild the value (single-flight or a lock), adding random jitter to TTLs, and serving slightly stale data while one refresh runs.

What happens, with numbers. A homepage query takes 800 ms to compute and is cached for 60 s. It is requested 2000 times per second. At the moment of expiry, every request in the next 800 ms misses, so about 1600 identical expensive queries start together on the database. It slows down, the rebuild takes longer, more requests pile up, and the database can fail. A hot key with a short TTL, or many keys loaded at the same time with the same TTL, makes this a scheduled outage.

Defences.

  1. Single flight (request coalescing). Only one caller rebuilds; others wait for its result. In one process use a per-key lock or a future map (Caffeine's LoadingCache does this). Across servers use a short Redis lock (SET lock:key id NX PX 5000); callers that fail to get it sleep briefly and re-check the cache, or serve stale data.
  2. TTL jitter. Add a random amount, e.g. TTL = 60 s plus or minus 10 percent, so keys loaded together expire at different times.
  3. Stale-while-revalidate. Store a soft expiry inside the value. After the soft expiry, the first request triggers an async refresh while all requests keep getting the stale value until the new one lands. Users never wait.
  4. Proactive refresh. A background job refreshes the hottest keys before they expire. Probabilistic early expiration (each request has a small chance to refresh as expiry nears) does this without coordination.
  5. Never expire, update on change for a few critical keys, with a periodic safety refresh.

Related problems to mention. Penetration: requests for keys that do not exist (random ids from an attacker or a bug) always miss and hit the database. Cache a short-lived "not found" value, validate ids first, or put a Bloom filter in front. Avalanche: many keys expiring together, or the whole cache restarting (cold cache). Use jitter, warm the cache before taking traffic, rate-limit the database path, and make the cache highly available (replication).

Three techniques. Single flight: the first request takes a short lock (in-process or SET NX in Redis) and recomputes; the others wait briefly or get the old value. TTL jitter: expire at TTL plus a random few percent, so many keys do not expire together after a deploy or a cache warm-up. Stale-while-revalidate: keep a soft TTL (when to refresh) and a hard TTL (when to drop); after the soft TTL one background refresh happens while everybody still gets the old value. For very hot keys, refresh proactively before expiry. A related issue is cache penetration (many requests for keys that do not exist): cache the "not found" result briefly or use a Bloom filter. And after a cold start, warm the cache or ramp traffic up slowly.

Remember: one rebuilder, jittered expiry, serve stale during refresh.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview. It shows you stay calm and look for causes, not only symptoms.

After a network blip, two database nodes both think they are primary and both accepted writes. What do you do? Senior

This is split brain. I stop writes to one side immediately (fence the old primary), pick the side with the more complete history as truth, then reconcile the writes the other side accepted. Long term I fix the failover design with a majority quorum and fencing, so it cannot happen again.

Why this happens (so you can explain the root cause). The failover tool saw heartbeats stop and promoted the standby. But the old primary was only unreachable from the standby, not dead, and some application servers could still reach it. A two-node pair has no way to decide who is right. The damage is that both sides assigned ids and accepted business transactions independently.

Reconciliation, in more detail. Choose the primary with the most complete and recent history as the base, usually the promoted one if the clients moved to it. Export the other side's writes made after the split point (use the log position where they diverged). For each, decide: no conflict (new rows with different ids) are replayed on the winner; conflicts (same order or account changed on both sides) need a rule such as latest business timestamp, or a manual review by the owning team. For money, reconcile against the payment provider's records, which are the neutral truth. Communicate to customers whose actions were lost or duplicated.

Say this at the end. The real fix is architectural: a quorum so the minority cannot promote, and fencing so a stale primary cannot write. Add a game-day test that partitions the primary and checks that exactly one side accepts writes.

Situation: two primaries accepted writes for some minutes, so the data has diverged.

Check first: which node does the quorum or orchestrator consider primary, how many writes each side took, and which clients wrote to which side.

  1. Stop the bleeding: make the losing side read-only or shut it down (fence it at the network, storage or load balancer level).
  2. Keep both data sets. Compare them, then replay or merge the writes from the losing side. Conflicts such as the same order on both sides need a business decision (or a manual review for money).
  3. Rebuild the losing node as a follower from the winner.

Prevent: automatic failover only with a majority-based coordinator (a third voter or witness, not a two-node pair), term numbers, a fencing step before promotion, and clients that always find the primary through the coordinator, not a fixed address.

Remember: fence first, reconcile second, and fix failover so a majority must agree.

A customer was charged twice for one order. Where do you look, and how do you fix it for good? Senior

Almost always a retry or a redelivery without idempotency: the first call succeeded but the response was lost, and something retried. I refund the customer, find which layer retried, and add an idempotency key with a unique constraint so a repeat returns the earlier result.

Why a double charge is the classic distributed bug. It comes straight from the timeout ambiguity: the first attempt succeeded, its response was lost or too slow, and a client, gateway or queue retried. Retrying is correct behaviour; the missing piece is idempotency in the payment path.

How the idempotency key stops it. The order service creates an attempt id once (for example pay-{orderId}-{attempt}) and uses that same value on every retry. The payment service has a table with a unique index on the key. Attempt 1 inserts the key and charges. Attempt 2 collides with the unique index, loads the stored result and returns it, with no second charge. If attempt 2 arrives while attempt 1 is still running, it gets "in progress" and waits or fails with 409. Pass the same key to the external provider too, so a retry between your service and the provider is also safe.

Common root causes to list. Double submit in the UI (disable the button and use a client-generated key), gateway retry on timeout combined with a slow provider, consumer redelivery after a rebalance or ack timeout, and a manual retry from a support tool. A good postmortem names which one happened and shows the fix at that layer plus the general guard in the payment service.

Situation: two successful payment captures with the same order id, a few seconds apart.

Check first: the trace of both attempts. Same request retried by the client, gateway or service after a timeout? A double click? A message consumed twice after a consumer timeout? Did the payment provider get one idempotency key or two?

  1. Refund the duplicate and record the cause.
  2. Find the retry layer. Typical: gateway timeout is 5 s, the payment call takes 6 s, the gateway retried while the first call was still running.
  3. Generate one idempotency key per order attempt, store it with a unique constraint, and pass it to the provider (the usual Idempotency-Key header). A retry then gets the earlier result.
  4. Make the consumer idempotent too: unique constraint on (order_id, payment_type).
  5. Line up the timeouts so the inner call finishes before the outer retry starts, and a retry reuses the same key.

Prevent: a daily reconciliation of provider settlements against the ledger, an alert on two captures for one order, and a test that injects a lost response.

Watch out: removing retries (then payments get lost), or a "check if already paid" read before the write, which races.

Remember: timeout plus retry equals duplicate, unless the operation is idempotent.

Stock goes negative: two requests each read the quantity, subtract, and write back. How do you fix it? Intermediate

This is a lost update caused by read-modify-write without atomicity. I make the decrement one conditional statement in the database, UPDATE ... SET qty = qty - 1 WHERE qty > 0, and check the updated row count.

Why it is not just "a rare race". Under normal load the two reads and writes rarely overlap. In a flash sale, hundreds of requests hit the same row within a few milliseconds, and the window between read and write (an application round trip, maybe 5 ms) is wide enough to overlap constantly. So the bug is invisible in test and loud in production.

The fixed code.

int updated = jdbc.update("UPDATE stock SET qty = qty - ? WHERE sku = ? AND qty >= ?", n, sku, n);
if (updated == 0) throw new OutOfStockException(sku);

The database takes a row lock for the duration of the single statement, evaluates qty >= ? against the current value and applies the change, so two buyers are processed one after the other. Only one gets the last unit. If the product is extremely hot, one row becomes a bottleneck (every update waits on the same lock); then shard the counter into several rows, or reserve stock in batches per server and reconcile.

Situation: qty is 1, two buyers read 1, both write 0 and both succeed, or both subtract and the count goes below zero.

Check first: where the read and the write happen, whether they share a transaction, and the isolation level (at read committed this is possible).

  1. Replace the read then write by an atomic conditional update and treat zero rows updated as "sold out".
  2. If logic needs the value first, use a version column (optimistic lock) and retry on conflict, or SELECT ... FOR UPDATE inside one transaction.
  3. Add a CHECK (qty >= 0) constraint as a last guard.
  4. If stock is in a cache or another service, make the database the single owner of the number.

Prevent: a concurrency test with parallel buyers on the last unit.

Remember: push the check into the write itself. The database decides, not the application.

A job leader paused for 40 seconds (long GC), a new leader took over, and then the old one woke up and wrote bad data. How do you stop this class of bug? Senior

The old leader did not know its lease had expired. I fix it with fencing tokens: each leadership grant gets an increasing number, and the database or storage rejects any write carrying an older number. Shorter pauses help, but only fencing makes it safe.

Why more careful code cannot fix this. Even if the old leader checks "do I still hold the lease?" immediately before writing, a pause can occur between that check and the write itself (the JVM can stop at any safepoint, the OS can deschedule the thread, a network packet can sit in a buffer). Time-based reasoning on the client is always racy.

How the fix works end to end. The election service gives leader A token 41. B later gets token 42. B writes with 42 and the database stores max_token = 42. When A wakes and writes with 41, the statement UPDATE ... WHERE max_token <= 41 matches nothing, and the write is rejected with a clear error. A then sees it was fenced, stops, and re-enters the election as a follower.

Where the token lives. For a database table, a column on the guarded row or a small leader_epoch table checked in the same transaction. For object storage or a queue, put the token in the object name or check it in the service in front. Kafka does this for you with producer epochs. If the target cannot check tokens (a third-party API), narrow the exposure by making operations idempotent and by having the leader stop quickly when renewal fails.

Situation: leader A held a lease, froze, lease expired, B became leader and wrote, then A resumed and overwrote B's work.

Check first: GC logs and lease timestamps to confirm the pause. Check how long the lease is versus the worst pause.

  1. Use a monotonic token (etcd revision, ZooKeeper zxid, or a counter bumped on each election) and send it with every write.
  2. Make the resource reject lower tokens, for example UPDATE ... WHERE fence_token <= :mine with an update of the stored token.
  3. Have the leader check "do I still hold the lease?" right before the critical write, and stop work when a renewal fails. This narrows the window but does not close it.
  4. Tune GC and heap, and keep lease time well above normal pauses.

Prevent: a failure test that freezes the leader process (SIGSTOP) and checks that stale writes are refused.

Remember: time-based leases are not enough. The resource must enforce the token.

Checkout calls payment, then inventory, then shipping. Shipping times out after payment succeeded. What is the correct behaviour? Senior

A timeout does not mean shipping failed, so I do not blindly refund. I retry shipping idempotently or look up its state. If it truly fails, I run compensations (release stock, refund) as a saga, and the order sits in a clear pending status until it resolves.

Core idea: timeout means unknown. After the shipping call times out, there are three possibilities: the shipment was created, it was not, or it is still being created. Refunding right away risks shipping an item that was refunded. Ignoring it risks charging a customer for nothing. The only correct move is to resolve the unknown.

Resolving it. Shipping exposes an idempotent create keyed by order id. Repeating the call either creates the shipment (first time) or returns the existing one. Alternatively query by the key first. Retry with exponential backoff for a bounded time. If shipping returns a definite rejection (address invalid, item unavailable), run compensation: release stock, refund payment, mark the order cancelled, and notify the customer. If it stays unknown beyond a limit, flag the order for manual review rather than guessing.

Design points to say aloud. The order has an explicit state machine (CREATED, PAID, SHIPPING_PENDING, SHIPPED, CANCELLED) persisted with each step, and the orchestrator reads that state after a crash. Compensations are themselves idempotent, since they may run twice. A scheduled reconciliation scans for orders stuck in a pending state for longer than the allowed time. This is the saga pattern in action.

Situation: money taken, shipping state unknown.

Check first: ask shipping for the status by the order's idempotency key. Did it create the shipment?

  1. Treat the order as PENDING_SHIPPING, not failed.
  2. Retry the shipping call with the same key and backoff. Because it is idempotent, a repeat is safe.
  3. If it fails for good (rejected, or retries exhausted), start compensation: cancel inventory reservation, refund payment, mark the order cancelled, tell the customer.
  4. Drive this with an orchestrated saga or outbox events so the process survives a crash mid-way.

Prevent: idempotent steps and compensations, a reconciliation job for orders stuck in pending, and alerts on age of pending orders.

Remember: unknown is not failed. Query or retry with the same key, compensate only on a confirmed failure.

Users say "I saved my settings, but the page shows the old values". Only some users, only sometimes. What is it? Intermediate

Most likely replication lag: the save went to the primary and the next page load read from a read replica that had not caught up. The fix is read-your-writes: read from the primary (or a caught-up replica) for a short time after a write.

Why "only some users, only sometimes" points to lag. A read pool of replicas answers each request from a different replica, and lag varies from replica to replica and moment to moment. A user who saves and reloads quickly gets stale data only if the reload lands on a lagging replica, which explains the randomness. If everyone were affected all the time, I would suspect a bug or a cache instead.

Proving it. Add a response header that reports which node served the read and its applied log position, or log them. Check lag graphs for the incident window. Save, then reload 100 times in a script and count stale answers. Rule out the other common cause, a stale cache entry that was not invalidated: bypass the cache and see if the symptom vanishes.

Fix options in order of effort. Quick: after a write, set a short-lived cookie or session flag and send that user's reads to the primary for about 10 to 30 seconds. Better: carry the write's log position (GTID in MySQL, LSN in PostgreSQL) and have the router choose a replica that has reached it. For specific read-after-write pages (settings), always read from the primary. Finally address the lag itself: look for long transactions on replicas that block apply, undersized replica hardware, or bursts of bulk writes, and alert when lag exceeds a limit.

Situation: intermittent stale reads right after a write, affecting a subset of users.

Check first: replica lag metrics at the incident time, whether reads use a replica pool, and whether a cache entry survived the write (the same symptom).

  1. Reproduce: write, then read in a loop, and see which backend answers.
  2. Route the writer's reads to the primary for a short window, or pass a log position and wait for a replica to reach it.
  3. If a cache is involved, delete the key after the database write.
  4. If the lag is large, find the cause: a long-running query or a big batch on the replica, or too few resources.

Prevent: alert on replica lag, expose "lag" in dashboards, and design read paths with the lag in mind.

Remember: after a write, read from the place that has it. Lag is the first suspect for "sometimes stale".

The database says an order exists, but no "OrderPlaced" event was ever published, so downstream never shipped it. Why, and how do you fix it? Senior

Classic dual write: the service saved the order and then published the event as two separate steps, and the process crashed or the broker was down in between. I fix it with a transactional outbox so the event is saved atomically with the order, and I repair the missing events from the database.

Why it hides. Most of the time both steps succeed, so tests and happy-path production look fine. The gap shows up only on crashes, deploys that kill the process between the two statements, or broker blips, so the symptom is a handful of orders without events, discovered by a customer complaint.

Repair first. Query the orders table for rows older than a few minutes with no corresponding downstream state. Republish events for those orders using their stable ids. Because consumers deduplicate on event id, republishing orders that did get processed is harmless. Do this under supervision and in batches.

Permanent fix: outbox. Insert the event into an outbox table in the same transaction as the order. A relay (poller or Debezium CDC) publishes it and retries until the broker acknowledges. If the relay crashes mid-way, it republishes and consumers drop the duplicate. Add a metric for the oldest unpublished outbox row, and alert if it exceeds a minute, so a stuck relay is noticed quickly. Mention the alternative of "listen to yourself" (publish first, consume your own event to write the DB), which has its own trade-offs and is less common.

Situation: some orders in the database have no matching event on the broker.

Check first: the code path (save, then publish?), error logs around the missing orders, broker outages at that time.

  1. Repair now: find orders without a published event (by comparing database to downstream) and republish them. Consumers must be idempotent for this to be safe.
  2. Fix the design: write an outbox row in the same transaction as the order, and let a relay or CDC (Debezium) publish it with retries.
  3. Keep the event id stable so duplicates can be dropped downstream.

Prevent: a reconciliation job and an alert on the unpublished outbox row age or count.

Remember: never write the database and the broker separately. Outbox plus idempotent consumers.

A non-critical recommendations service got slow, and then the whole website went down. Explain and fix. Senior

This is a cascading failure. Callers waited on the slow service with no tight timeout, so their threads filled up, then every other endpoint on the same pool starved. I fix it with a short timeout, a circuit breaker with a fallback, and a separate bulkhead pool, so the optional feature fails alone.

The mechanism, step by step. (1) Recommendations slows from 20 ms to 10 s. (2) Each homepage request calls it synchronously and now holds a thread for 10 s. (3) At 100 requests per second, 1000 threads would be needed; the pool of 200 fills in 2 seconds. (4) New requests queue, including those for unrelated pages, and then time out. (5) Health checks fail, the load balancer removes instances, and the remaining ones get even more load: the cascade. (6) Clients retry, multiplying load.

The fix, layer by layer.

  • Timeout 200 to 300 ms on the call, so a thread is held for at most that time.
  • Fallback: an empty carousel, or yesterday's cached recommendations. The page loads without that block.
  • Circuit breaker: after enough failures, stop calling it for 30 s, so no thread is held at all.
  • Bulkhead: a pool of 10 to 20 for this dependency.
  • Async or lazy loading: render the page first and fetch recommendations from the browser or in the background.
  • Health checks: make liveness independent of optional dependencies, so a degraded optional feature does not remove healthy instances.

The lesson interviewers want: every dependency should be classified critical or optional, and optional ones must fail independently.

Situation: latency in one dependency spread into a full outage.

Check first: thread pool and connection pool saturation on the web tier, timeout settings, retry settings (retries make it worse), and whether the page needs the data to render.

  1. Right now: turn the feature off with a flag, or have the breaker open.
  2. Set a short timeout (for example 200 to 300 ms) and a fallback (empty list or cached recommendations).
  3. Put the call in its own bulkhead (separate pool) so it cannot take all threads.
  4. Remove retry multiplication and add a retry budget.
  5. Load shed instead of queueing: reject quickly when the pool is full.

Prevent: classify dependencies as critical or optional, test with latency injection, and alert on pool saturation.

Remember: a slow dependency is worse than a dead one. Timeout, breaker, bulkhead, fallback.

A downstream service had a 30-second slowdown, but the outage lasted 40 minutes, long after it recovered. Why? Senior

A retry storm. During the slowdown clients timed out and retried, queues filled with requests nobody was waiting for, and the retry load kept the service overloaded even after the original cause was gone. The fix is backoff with jitter, retry budgets, load shedding and short queues.

The metastable failure idea. Some systems have two stable states: healthy, and overloaded. A short trigger can push them into the overloaded state, and a feedback loop (here, retries and growing queues) keeps them there even after the trigger is gone. The recovery does not happen by itself.

Timeline with numbers. Normal load 1000 requests per second (rps), capacity 1500 rps. For 30 s the service slows down, requests time out at 2 s, and clients retry 3 times. Offered load becomes up to 4000 rps. Queues fill with requests whose clients already gave up, but the server still burns CPU on them. Even after the slowdown ends, offered load is above capacity, queue wait stays above the client timeout, so almost every response arrives too late to be used (goodput near zero) and clients keep retrying. The system is stuck until load drops below capacity for long enough to drain.

Getting out. Reduce offered load below capacity: shed traffic at the edge (return 503 to a fraction), pause retrying clients, restart or scale to clear queues, and make the server drop requests whose deadline has already passed. Staying out: retry budget and a single retry layer, jittered backoff, short bounded queues with newest-first or deadline-aware dropping, and adaptive concurrency limits. In the post-incident write-up, explain why the system had a metastable state, not only what triggered it.

Situation: the trigger was brief, but the system stayed in a bad state (a metastable failure).

Check first: request rate against the service during and after the incident (was it much above normal?), the number of retries per layer, and queue lengths.

  1. Recover: shed load (reject or drop part of the traffic), drain or purge stale queues, scale up, or temporarily disable retries to break the loop.
  2. Retry at one layer only, with exponential backoff and full jitter plus a cap on attempts and a retry budget.
  3. Use bounded queues and drop requests whose deadline already passed, since the user has gone.
  4. Add a circuit breaker so callers stop hitting a struggling service.

Prevent: load tests that include a short slowdown and recovery, and watch for retry rate in the dashboards.

Remember: retries turn a blip into an outage. Backoff, jitter, budgets, shed load.

An "OrderCancelled" event arrives at a service before the "OrderCreated" event for the same order. What happens, and how do you design for it? Senior

If the consumer assumes order, the cancel finds no order and is dropped, then the create arrives and the order is wrongly active. I prevent it by keeping order per key (same partition key), putting a version in each event, and making handlers tolerate arrival in any order.

Why reordering happens even with a broker. Order is guaranteed only within one partition, from one producer path. Events can diverge when they go to different topics or partitions (the created event keyed by order id, the cancelled event keyed by customer id), when a failed message goes to a retry topic and is replayed later, when a consumer processes a partition with a thread pool, or when two services publish events for the same entity.

Design for tolerance, with a concrete handler.

onEvent(e):
  row = load(e.orderId)
  if row == null:
      if e.type == CANCELLED: save(orderId, status=CANCELLED, version=e.version)   // remember it
      elif e.type == CREATED: save(orderId, status=ACTIVE, version=e.version)
      return
  if e.version <= row.version: return          // old or duplicate, ignore
  apply(e); row.version = e.version; save(row)

With a stored cancelled marker, a later CREATED with a lower version is ignored, so the order stays cancelled. The version is assigned by the order service when it creates the event (the aggregate's sequence number), not by wall-clock time.

Also say: for events that make no sense yet and that cannot be recorded, park them in a delayed retry or dead-letter queue with an alert, so they are not silently dropped. And test by shuffling and duplicating events in a property test.

Situation: events for one entity were reordered, for example by different topics, retries or parallel consumers.

Check first: do both events share a partition key and a topic, are retries or parallel threads in play, and does the event carry a sequence or version?

  1. Same topic, key = order id, one consumer thread per partition (idempotent producer to keep order on retries).
  2. Carry a version or sequence number. The consumer applies an event only if it is newer than the stored version and ignores older ones.
  3. For a cancel with no order yet: record a tombstone or "cancelled" marker, so the later create is applied as cancelled; or park the event and retry after a short delay.
  4. Make state transitions explicit (a small state machine) so an illegal transition is detected and handled.

Prevent: property tests that shuffle events, and a dead-letter queue for events that never resolve.

Remember: do not trust arrival order. Key by entity, carry a version, and make handlers order tolerant.

Offset commit before work gives?At-most-once. After work: at-least-once.
Retry best practice?Idempotent calls only, backoff plus jitter, capped attempts, one layer.
Circuit breaker states?Closed, open, half-open.
Bulkhead?Separate resource pools so one slow dependency cannot drain everything.
Backpressure vs load shedding?Ask the producer to slow down versus reject excess work.
Token bucket property?Allows bursts up to bucket size, and a steady average rate.
Distributed rate limit race?Read-then-write on a shared counter. Use an atomic Lua script or INCR.
Cache-aside write path?Update the database, then delete the cache key.
Stampede fixes?Single flight, jittered TTL, stale-while-revalidate.
Availability of three 99.9% services in series?About 99.7% (roughly 26 hours down a year).

Closing line for an interview: "In a distributed system a timeout never tells me whether the work happened, so I design for it: retries with backoff and jitter, idempotent operations, fencing for anything with a leader or a lock, and a clear choice of consistency per operation.
