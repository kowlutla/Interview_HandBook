Mental model: the 8 ideas everything hangs on

One line: a collection is an object that holds references to other objects. Each one makes a trade-off between lookup speed, insertion speed, ordering, memory and thread safety. Interviews are about knowing which trade-off each class made, and why.
  1. Two families. Collection (List, Set, Queue) holds single elements. Map holds key to value pairs and is a separate hierarchy.
  2. Interface versus implementation. Declare List<String>, create ArrayList. The choice of class is a performance and behaviour decision, the interface is the contract.
  3. Arrays or links or hashes or trees. Almost every class is built on one of four structures: a resizable array (ArrayList, ArrayDeque, PriorityQueue), a linked list (LinkedList), a hash table (HashMap, HashSet), or a balanced tree (TreeMap, TreeSet). Big-O follows from the structure.
  4. Hash tables need a good equals and hashCode. Break the contract and elements vanish or duplicate. Mutate a key after inserting it and the entry is lost.
  5. Order is a feature you choose. HashMap has no useful order. LinkedHashMap keeps insertion (or access) order. TreeMap keeps sorted order.
  6. Most classes are not thread safe. Sharing an ArrayList or HashMap between threads without a lock gives lost updates, or worse. Use the concurrent classes, not the old synchronized ones.
  7. Iterators are fail-fast. Change a collection while you loop over it, and you usually get ConcurrentModificationException. Remove through the iterator, or with removeIf.
  8. Boxing costs memory. A collection of Integer is a collection of objects, not numbers. That is often the real performance problem.

1. Framework basics

Describe the Java Collections Framework hierarchy. Basic

What the interviewer is testing: that you have a clean map in your head, not a list of random class names.

At the top is Iterable, which only promises that you can loop over the thing with a for-each loop. Collection extends it and adds the basic group operations: add, remove, contains, size, stream. Three main sub-interfaces follow. List is ordered, indexed, and allows duplicates. Set allows no duplicates, and its sub-interfaces SortedSet and NavigableSet add sorted order. Queue is for holding elements before processing, and Deque is a queue you can use at both ends. Map is a separate tree: key to value pairs, with SortedMap, NavigableMap and ConcurrentMap below it. Then there are implementations: ArrayList, HashSet, HashMap and so on. Two helper classes, Collections and Arrays, hold static utilities.

Likely follow-ups
  • Why is Map not a Collection? Because a Map is a set of pairs, and methods like add(E) do not make sense for it. It gives you three Collection views instead: keySet, values, entrySet.
  • Which interface do you declare variables as? The interface (List, Map), so you can swap the implementation later.
What is the difference between Collection and Collections? And Arrays versus ArrayList? Basic

What the interviewer is testing: a warm-up. Wrong answers are a bad sign.

Collection (singular) is an interface, the parent of List, Set and Queue. Collections (plural) is a final utility class with only static methods: sort, reverse, shuffle, unmodifiableList, synchronizedList, emptyList, max, frequency and so on. Arrays is the same idea for plain arrays: sort, fill, copyOf, asList, toString, equals. An array has a fixed size, can hold primitives, and is built into the language. An ArrayList is a class that wraps an array, resizes itself, and holds objects only.

What is the difference between Iterable and Iterator? Basic

What the interviewer is testing: how the for-each loop really works.

Iterable<T> is something you can loop over: it has one method, iterator(), which returns a fresh Iterator. The Iterator<T> is the cursor: hasNext(), next(), and an optional remove(). The enhanced for loop for (String s : list) is just sugar. The compiler turns it into Iterator it = list.iterator(); while (it.hasNext()) { String s = it.next(); ... }. That is why you can use for-each on your own class if it implements Iterable. For arrays the compiler uses a plain index loop instead. Each call to iterator() gives an independent cursor, so two loops over the same list do not disturb each other.

class Range implements Iterable<Integer> {
    private final int from, to;
    Range(int from, int to) { this.from = from; this.to = to; }
    public Iterator<Integer> iterator() {
        return new Iterator<>() {
            int cur = from;
            public boolean hasNext() { return cur < to; }
            public Integer next() { return cur++; }
        };
    }
}
for (int i : new Range(0, 3)) System.out.println(i);   // 0 1 2
Likely follow-ups
  • What does ListIterator add? Moving backwards, add, set and index access, lists only.
  • What is Spliterator? The iterator used by streams, able to split work for parallel processing.
List, Set, Map, Queue: when do you pick each? Basic

What the interviewer is testing: basic design instinct.

Use a List when position matters or duplicates are fine: a list of orders in the sequence they arrived, rows of a result. Use a Set when uniqueness is the point: the set of distinct user ids seen today. Use a Map when you need to find a value quickly by a key: user id to user, word to count. Use a Queue or Deque when elements wait to be handled in some order: first in first out for tasks, last in first out for a stack, or by priority. A quick test: if you write a loop to search a list for an element, you probably wanted a Set or a Map. If you keep removing from the front of a list, you wanted a Queue.

Likely follow-ups
  • Does a Set keep order? Only LinkedHashSet (insertion) and TreeSet (sorted). HashSet does not promise any order.
Why can't you put an int in a List? What happens when you do list.add(5)? Basic

What the interviewer is testing: generics, autoboxing and their cost.

Generics work with reference types only, because of type erasure: at runtime a List<Integer> is just a List holding Object references. Primitive int is not an object. When you write list.add(5) the compiler inserts Integer.valueOf(5) (autoboxing), and when you read int x = list.get(0) it inserts intValue() (unboxing). Integer.valueOf reuses cached objects for -128 to 127 and allocates a new object otherwise. So a list of a million ints is a million objects of about 16 bytes each, plus the references to them. This is also why comparing boxed values with == is a bug: it compares references, and works only for the cached small values. Use equals. Java's Project Valhalla is working on value types to fix the cost, but as of Java 21 it has not shipped.

Integer a = 127, b = 127;   // a == b  is true  (cached)
Integer c = 128, d = 128;   // c == d  is false (two objects)
c.equals(d);                // true
Likely follow-ups
  • What if the value is null and you unbox it? NullPointerException. A classic bug with map.get(k) assigned to an int.
  • How do you avoid boxing? Use arrays, or primitive collection libraries such as fastutil, Eclipse Collections or Trove.
Which useful default methods did Java 8 add to the collection interfaces? Intermediate

What the interviewer is testing: whether you write modern Java or Java 6 style.

On Collection: removeIf(predicate), stream(), parallelStream(), and forEach from Iterable. On List: replaceAll(operator) and sort(comparator). On Map: getOrDefault, putIfAbsent, computeIfAbsent, computeIfPresent, compute, merge, replaceAll, forEach, and remove(key, value). They replace long if/else blocks and, in concurrent maps, they are atomic. A very common one is counting: map.merge(word, 1, Integer::sum), and grouping: map.computeIfAbsent(key, k -> new ArrayList<>()).add(value).

Map<String, List<String>> byDept = new HashMap<>();
byDept.computeIfAbsent("eng", k -> new ArrayList<>()).add("Asha");
Map<String, Integer> counts = new HashMap<>();
for (String w : words) counts.merge(w, 1, Integer::sum);
list.removeIf(s -> s.isEmpty());
Likely follow-ups
  • Difference between computeIfAbsent and putIfAbsent? computeIfAbsent builds the value lazily only when needed, and returns the value. putIfAbsent needs the value built up front and returns the old one.
What is the RandomAccess marker interface for? Intermediate

What the interviewer is testing: depth on List implementations and how library code adapts to them.

RandomAccess has no methods. A list class implements it to say "calling get(i) is fast, constant time". ArrayList and Vector do, LinkedList does not. Generic algorithms check it with instanceof and pick a strategy. For example Collections.binarySearch uses index based search on a RandomAccess list and an iterator based search on a LinkedList, and Collections.shuffle, reverse and fill also switch on it. When you write your own algorithm on a List parameter, remember that for (int i...) list.get(i) on a LinkedList is O(n squared) overall, and prefer the for-each loop which works well with any list.

What are the keySet, values and entrySet views of a Map, and what happens if you change them? Intermediate

What the interviewer is testing: the "view" concept, which appears again in subList and unmodifiable wrappers.

These three methods do not copy anything. They return live views backed by the map. If you remove an entry through map.keySet().remove(k) or through an iterator over entrySet(), the entry disappears from the map. If you change the map, the view shows the change. You cannot add through keySet or values, it throws UnsupportedOperationException. The best way to loop over everything is entrySet(), because it gives you the key and the value together, with no second lookup. Looping over keySet() and calling get(key) inside does an extra hash lookup (or tree search) for every element. Entry.setValue writes through to the map, too.

for (Map.Entry<String, Integer> e : map.entrySet()) {
    if (e.getValue() == 0) e.setValue(-1);        // writes to the map
}
map.values().removeIf(v -> v < 0);               // removes entries from the map
map.keySet().removeAll(staleKeys);

2. Lists

How does ArrayList work inside, and how does it grow? Basic

What the interviewer is testing: the most asked collection question. Answer with numbers.

An ArrayList holds an Object[] elementData and an int size. The array length is the capacity, the number of slots. size is how many are in use. With new ArrayList<>() no array is allocated at first (it shares an empty array). The first add allocates 10 slots. When the array is full, the next add creates a new array of about 1.5 times the size (oldCapacity + (oldCapacity >> 1)), copies all elements with Arrays.copyOf (a fast native copy), and drops the old array. So capacity goes 10, 15, 22, 33, 49 and so on. A single add is O(1) normally, and O(n) on the add that triggers growth. Spread over many adds, the average is O(1), which is called amortized constant time. Reading by index is O(1). Insert or remove in the middle shifts the tail with System.arraycopy, so that is O(n). If you know the size in advance, pass it to the constructor, or call ensureCapacity, to skip all the copies.

Likely follow-ups
  • Why 1.5 and not 2? Less wasted memory after growth, and the freed older blocks can be reused by later allocations.
  • Maximum size? About Integer.MAX_VALUE - 8; beyond that you get OutOfMemoryError.
  • What does trimToSize do? Shrinks the array to size, to save memory on a list that will not grow again.
ArrayList versus LinkedList: which is faster, and when would you really use LinkedList? Basic

What the interviewer is testing: whether you repeat the textbook table or know what happens on real hardware.

The textbook says: ArrayList has O(1) get and O(n) insert in the middle, LinkedList has O(n) get and O(1) insert in the middle. That is true on paper but misleading. To insert in the middle of a LinkedList you first have to walk to that position, which is O(n) anyway. The walk chases pointers across the heap, and each node is a separate object, so the CPU cache misses all the time. An ArrayList copies a block of contiguous memory, which is extremely fast even for 100,000 elements. In practice ArrayList wins at almost everything, including adding at the end, iteration and memory (a LinkedList node costs about 24 bytes extra per element: a header, an item reference, and two links). LinkedList wins only in rare cases: when you already hold a ListIterator positioned in the list and insert or remove many times during one pass, or when you need a queue and nothing better is at hand (but ArrayDeque is better even there). My default is ArrayList, and I would need a measured reason to choose otherwise.

Likely follow-ups
  • What does LinkedList implement that ArrayList does not? Deque, so it also works as a queue and a stack.
  • Is LinkedList get(i) always from the head? No, it starts from the nearer end, head or tail, so the worst case is n/2 steps.
Common mistakes: saying "LinkedList is faster for insert and delete" without mentioning the cost of finding the position.
How is LinkedList built, and which operations are cheap? Intermediate

What the interviewer is testing: structure knowledge, and that you know it is also a Deque.

LinkedList is a doubly linked list. It keeps references first and last and a size. Every element lives in a private Node object with three fields: item, next and prev. That is about 24 bytes per node on a compressed-pointer JVM, on top of the element itself. Cheap operations (O(1)): addFirst, addLast, removeFirst, removeLast, getFirst, getLast, and remove through an iterator that already points at the node. Expensive ones (O(n)): get(i), set(i), add(i, x), contains, indexOf. It allows null elements. It is not thread safe. Because it implements Deque it can be used as a stack or queue, but ArrayDeque does that job with less memory and better cache behaviour.

What is wrong with Vector and Stack? Why are they called legacy? Basic

What the interviewer is testing: history, and the right modern replacement.

Vector is from Java 1.0, before the collections framework. It is an array list where every method is synchronized. That sounds safe, but it is a poor kind of safe. Each call takes a lock even when only one thread is used, which costs time. And single calls being synchronized does not make a sequence of calls safe: if (!v.contains(x)) v.add(x) is still a race between two threads. Its growth is to double the capacity, so it wastes more memory than ArrayList. Stack extends Vector, which is a design mistake: a Stack lets you call get(i) and add(i, x) and so breaks the idea of a stack. Modern replacements: ArrayList for single-threaded use; CopyOnWriteArrayList or a lock when threads share it; ArrayDeque for stack and queue. The Javadoc itself recommends Deque over Stack.

Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); stack.push(2);
stack.pop();    // 2   last in, first out
Likely follow-ups
  • Is Collections.synchronizedList better? It is the same idea (one lock on every call) with the same compound-action problem, but it can wrap any list.
How does CopyOnWriteArrayList work, and when is it a good choice? Intermediate

What the interviewer is testing: a classic trade-off: read speed versus write cost.

CopyOnWriteArrayList keeps its data in a volatile array that is never modified in place. Every write (add, set, remove) takes a lock, makes a full copy of the array with the change applied, and then swaps the reference to the new array. Readers do no locking: they read the current array reference and use it. An iterator keeps the array that existed when it was created, a snapshot, so it never throws ConcurrentModificationException, and it never sees later changes. It does not support remove through the iterator. Reads are very fast and contention free, writes cost O(n) and create garbage. So it fits "read very often, change very rarely" data: a list of event listeners, a list of subscribers, configuration. It is a bad choice for a list that is written often or is large, because each add copies everything.

Likely follow-ups
  • What is the set version? CopyOnWriteArraySet, built on top of it. Its contains is O(n).
  • Is it consistent? Each read sees a complete old or new version, never half of a change.
What are the gotchas of Arrays.asList? Intermediate

What the interviewer is testing: a favourite trap question that shows real experience.

Arrays.asList(a, b, c) returns a list that is a thin wrapper over the array. It is fixed-size: set works, but add and remove throw UnsupportedOperationException. It is write-through: if you change the list, the original array changes, and the other way round. And it has a nasty surprise with primitive arrays: Arrays.asList(new int[]{1,2,3}) gives a List<int[]> with one element, because int[] is a single object and not an Object[]. Use Integer[], or IntStream.of(arr).boxed().toList(). The class is a private nested Arrays.ArrayList, not java.util.ArrayList. When you want a normal mutable list, copy it: new ArrayList<>(Arrays.asList(...)). From Java 9, if you want an immutable list, use List.of(...).

String[] arr = {"a", "b"};
List<String> view = Arrays.asList(arr);
view.set(0, "z");     // arr[0] is now "z"
view.add("c");        // UnsupportedOperationException

List<int[]> oops = Arrays.asList(new int[]{1, 2, 3});
oops.size();          // 1, not 3
Likely follow-ups
  • Does it allow null elements? Yes. List.of does not.
What is special about List.of, Set.of and Map.of (Java 9)? How is it different from Collections.unmodifiableList? Intermediate

What the interviewer is testing: modern API knowledge and immutability details.

The factory methods List.of, Set.of, Map.of and Map.ofEntries return truly immutable collections: any add, remove or set throws UnsupportedOperationException. They reject nulls: a null element or key throws NullPointerException at creation, and even list.contains(null) throws. Set.of and Map.of reject duplicate elements or keys with IllegalArgumentException. The iteration order of Set.of and Map.of is deliberately unspecified and changes from one JVM run to the next (a per-run random salt), so tests that depend on it will flake. They are compact, small objects optimized for few elements. List.copyOf, Set.copyOf and Map.copyOf make an immutable copy, and return the same instance if the input is already such a collection. Collections.unmodifiableList is different: it is a read-only view over a list that someone else can still change.

Likely follow-ups
  • Are the elements immutable too? No. The collection structure is, the objects inside are whatever they are (shallow immutability).
What does subList return, and what traps does it hide? Intermediate

What the interviewer is testing: views and structural modification.

list.subList(from, to) returns a view of that range, not a copy. Changes to the sublist write through to the original, and the other way round. A very handy trick is list.subList(0, 3).clear(), which removes a range from the parent in one go. The traps are two. First, if you change the parent list structurally (add or remove) and then touch the sublist, you get ConcurrentModificationException. Second, the view holds a reference to the whole parent, so keeping a tiny sublist of a huge list in a long-lived field keeps the whole big list from being garbage collected. When you want an independent copy, write new ArrayList<>(list.subList(a, b)).

What is the problem with list.remove(1) on a List<Integer>? Basic

What the interviewer is testing: overload resolution and boxing.

List has two methods: remove(int index) and remove(Object o). When you call list.remove(1) with an int literal, Java picks the exact match without boxing, so it removes the element at index 1, not the value 1. To remove the value, write list.remove(Integer.valueOf(1)) or list.remove((Integer) 1). The first form returns the removed element, the second returns a boolean. This bug is common in code that handles ids or numbers. Also keep in mind that removal in an ArrayList shifts the tail, so removing many elements one by one in a loop is O(n squared); use removeIf, which compacts once in O(n).

List<Integer> l = new ArrayList<>(List.of(10, 20, 1));
l.remove(1);                    // removes index 1 (20)  -> [10, 1]
l.remove(Integer.valueOf(1));   // removes the value 1   -> [10]
Why is list.contains slow and what do you do about it? Basic

What the interviewer is testing: a common performance bug found in code reviews.

List.contains and indexOf scan the elements one by one calling equals, so they are O(n). Doing this inside a loop over another list makes the whole thing O(n times m). With 50,000 elements on each side that is 2.5 billion comparisons, many seconds. The fix is to put the lookup side in a HashSet (or a HashMap when you need the value), which gives expected O(1) per lookup, and the whole job becomes O(n + m). The same is true for list.remove(Object) and removeAll(otherList): removeAll calls other.contains for each element, so if other is a List the cost is quadratic. Convert it to a Set first.

Set<Long> blocked = new HashSet<>(blockedIds);          // O(m)
List<Order> ok = orders.stream()
    .filter(o -> !blocked.contains(o.customerId()))     // O(1) each
    .toList();
How do you sort a list, and is the sort stable? Basic

What the interviewer is testing: modern sorting syntax and what "stable" means.

Use list.sort(comparator) (Java 8) or Collections.sort(list) for natural order. For objects, Java uses TimSort, a hybrid of merge sort and insertion sort that is stable and runs in O(n log n), and O(n) on already sorted or nearly sorted data. Stable means that elements that compare equal keep their original relative order. That matters when you sort by several keys in turn: sort by name, then stable-sort by department, and people in one department stay ordered by name. For primitive arrays, Arrays.sort(int[]) uses dual-pivot quicksort, which is not stable, but stability makes no sense for primitives because equal ints are indistinguishable. list.sort copies the list into an array, sorts it, and writes it back, so it also works for LinkedList.

people.sort(Comparator.comparing(Person::dept)
                      .thenComparing(Person::name));
people.sort(Comparator.comparingInt(Person::age).reversed());

3. Sets

How does HashSet work inside? How does it keep elements unique? Basic

What the interviewer is testing: HashSet is HashMap in disguise, and uniqueness rests on equals and hashCode.

A HashSet owns a HashMap. Each element you add becomes a key in that map, and the value is one shared dummy object called PRESENT. add(e) is just map.put(e, PRESENT) == null. So add returns true if the key was new, and false if an equal key was already there. "Equal" means the same hashCode first, then equals returns true. That is why a class used in a HashSet must have consistent equals and hashCode. All operations are expected O(1). There is no useful iteration order, and it can change after a resize. HashSet allows one null. The default initial capacity is 16 with load factor 0.75, same as HashMap.

Likely follow-ups
  • What happens when I add an object that overrides equals but not hashCode? Two equal objects usually land in different buckets, so the set holds both, which breaks uniqueness.
  • HashSet(Collection c) capacity? About max(c.size()/0.75 + 1, 16), so it does not resize while copying.
HashSet, LinkedHashSet, TreeSet: how do they differ? Basic

What the interviewer is testing: ordering and cost trade-offs.

HashSet: hash table, expected O(1) for add, remove, contains, no order, allows one null. LinkedHashSet: a HashSet that also keeps a doubly linked list through its entries, so iteration follows insertion order. Same O(1) cost, a little more memory, and iteration is faster than HashSet when the table is sparse, since it walks the list instead of empty buckets. Re-adding an existing element does not change its position. TreeSet: a red-black tree (it wraps a TreeMap), O(log n) for the operations, elements kept sorted, either by natural order (Comparable) or a Comparator you pass in. It gives range methods such as first, last, floor, ceiling, headSet, tailSet, subSet. TreeSet does not allow null with natural ordering, because compareTo on null throws. Pick HashSet by default, LinkedHashSet when order matters (for example to remove duplicates and keep the first-seen order), TreeSet when you need sorted data or nearest-value queries.

A TreeSet drops elements that I think are different. Why? Senior

What the interviewer is testing: that TreeSet and TreeMap use the comparator, not equals, to decide equality.

A tree-based set decides "same element" by compare(a, b) == 0 (or compareTo), and never calls equals. If your comparator looks at only one field, two objects that differ in other fields but tie on that field are treated as duplicates, and the second add silently returns false. Example: a TreeSet<Employee> sorted by salary will keep only one employee for each salary. The fix is to add a tie-breaker, for instance comparing(Employee::salary).thenComparing(Employee::id). The general rule is that compareTo should be consistent with equals: a.compareTo(b) == 0 exactly when a.equals(b). The well known example of a class that breaks the rule is BigDecimal: new BigDecimal("2.0") and new BigDecimal("2.00") are not equal, but compare as 0. A HashSet keeps both, a TreeSet keeps one.

Set<Employee> byPay = new TreeSet<>(Comparator.comparingInt(Employee::salary));
byPay.add(new Employee(1, "Asha", 100));
byPay.add(new Employee(2, "Ravi", 100));   // returns false: ties count as duplicates
byPay.size();                              // 1
How do you do union, intersection and difference on sets? And remove duplicates from a list while keeping order? Basic

What the interviewer is testing: bulk operations and a very common small coding task.

The bulk methods on Collection give you set algebra. Union: a.addAll(b). Intersection: a.retainAll(b). Difference: a.removeAll(b). Subset test: a.containsAll(b). They change a in place, so copy first if you need the original: new HashSet<>(a). To remove duplicates from a list and keep the first-seen order, pass it through a LinkedHashSet. If sorted order is fine, a TreeSet works too. Remember that these bulk operations call contains on the argument, so if the argument is a List they cost O(n times m); make the argument a Set.

List<String> unique = new ArrayList<>(new LinkedHashSet<>(names));  // keeps first-seen order
Set<Integer> common = new HashSet<>(a);
common.retainAll(b);                                              // intersection
What are EnumSet and Set.of, and why use EnumSet over HashSet for enums? Intermediate

What the interviewer is testing: knowing the specialised, faster structures.

EnumSet is a set specialised for one enum type. Inside, it is a bit vector: one bit per enum constant, stored in a single long when the enum has 64 constants or fewer (the class is RegularEnumSet) and in a long[] for larger enums. So add, contains and remove are a single bit operation, bulk operations like union are one bitwise OR, memory is a few bytes, and iteration is in declaration order of the enum. You make one with factory methods: EnumSet.of(MON, TUE), allOf, noneOf, range, complementOf. It does not allow null. It is the standard way to model flags and permissions, instead of an int bitmask. EnumMap is its map counterpart, covered in the Maps section.

4. HashMap in depth

These answers describe Java 8 and later unless a question says Java 7. The Java 8 rewrite of HashMap (JDK 8, 2014) is the version asked in almost every interview.

How does HashMap work internally? Basic

What the interviewer is testing: the number one Java interview question. Give the whole story: array, hash, bucket, equals, chain, resize, tree.

A HashMap is an array of buckets (Node[] table). Each bucket holds the start of a small linked list of entries, and each entry stores the hash, the key, the value and a next pointer. To put(key, value), it calls key.hashCode(), mixes the bits a little, and turns that into an array index with (table.length - 1) & hash. If the bucket is empty, it stores a new entry there. If not, it walks the chain and compares each entry: first the stored hash, then == or equals on the key. If a match is found, it replaces the value. If not, it appends a new entry at the end of the chain. get follows the same path: same hash, same bucket, then compare keys. When the number of entries goes above capacity times loadFactor (16 times 0.75 = 12 at the start), the table doubles and entries are spread over the new buckets. Since Java 8, a chain that gets too long (8 or more nodes in a table of at least 64 slots) turns into a red-black tree, which protects against bad hash codes. Average cost of put and get is O(1); the worst case is O(log n) in Java 8 (it was O(n) in Java 7).

Likely follow-ups
  • What is a collision? Two different keys that map to the same bucket. It is normal, and it is why equals is always checked.
  • Is get really O(1)? Expected O(1) with a good hash; O(log n) worst case in Java 8 when a bucket is a tree.
  • What is stored in the entry? hash, key, value, next. The stored hash avoids calling equals on most non-matching entries.
What is the "hash spreading" step (h ^ (h >>> 16)) and why does it exist? Senior

What the interviewer is testing: a detail only people who have read the source know.

The bucket index is hash & (n - 1). With a table of 16 slots, that uses only the lowest 4 bits of the hash. All the higher bits are ignored. Many real hash codes differ only in their high bits (for example floats, or ids that are multiples of a big power of two), so they would all collide in the same few buckets. Java 8 therefore XORs the upper 16 bits of the hash code into the lower 16 bits first: hash = h ^ (h >>> 16). Now the high bits also influence the low bits that the mask keeps. It is a cheap step (one shift and one XOR) that gives a decent spread without the heavy multi-shift function used in Java 7. Here is the worked example for a table of 16 slots.

Likely follow-ups
  • What was it in Java 7? A longer function with several shifts and XORs (h ^= (h >>> 20) ^ (h >>> 12); h ^ (h >>> 7) ^ (h >>> 4)), and an optional random seed for Strings. Java 8 simplified it because trees now handle the worst case.
Why is the HashMap capacity always a power of two? Intermediate

What the interviewer is testing: the reasoning, not the fact.

There are two reasons. First, speed of the index calculation. With a power of two length n, hash & (n - 1) gives the same result as a modulo (hash % n) for non-negative numbers, but an AND is much cheaper than a division, and it also works for negative hash codes without a sign fix. For n = 16, n - 1 is binary 1111, so the mask keeps the lowest four bits. If n were 10, n - 1 is 1001, and the mask would ignore some bits for ever and put nothing in several buckets. Second, resizing becomes simple. When the table doubles from n to 2n, the new index of an entry is either the old index, or the old index plus n. Which one depends on a single bit of the hash (the bit at the value n), so each bucket can be split into two in one pass, with no rehash. If you pass a capacity that is not a power of two to the constructor, the map rounds it up (new HashMap<>(100) allocates 128 slots, using tableSizeFor).

Likely follow-ups
  • What is the maximum capacity? 2^30 (1,073,741,824). After that the map stops resizing and chains just grow.
  • Is the table allocated in the constructor? No, lazily on the first put, in Java 7u40 and later and in Java 8.
Walk me through exactly what happens in map.put(k, v). Intermediate

What the interviewer is testing: can you narrate the algorithm step by step, in order.

Step one, compute the spread hash from k.hashCode(). Step two, if the table is still null or empty, allocate it (16 slots by default). Step three, compute the index (n - 1) & hash. Step four, if that bucket is empty, put a new node there. Otherwise step five: check the first node, and if its hash is equal and its key is the same reference or equals, remember it as the existing node. Step six: if the bucket is a tree, insert into the tree; otherwise walk the chain, comparing as you go, and if you reach the end, append a new node at the tail. If that makes the chain long (it already held 8 nodes, so the new one is the 9th), call treeifyBin. If an existing node was found, overwrite its value and return the old value (the entry order does not change). Step seven: if this was a new entry, increase modCount and size, and if size is now above the threshold, resize.

Likely follow-ups
  • What does put return? The previous value for that key, or null if there was none (or if null was stored).
  • Does replacing a value count as a structural modification? No, modCount is not changed, so it is safe during iteration.
How does get(key) find a value, and why must you override both equals and hashCode? Basic

What the interviewer is testing: the connection between lookup and the equals/hashCode contract.

get does the same thing as put up to the lookup: it spreads the hash, finds the bucket, and checks the first node. Then it follows the chain (or the tree) comparing hash == hash && (k == key || key.equals(k)). The hash is the fast filter that finds the right bucket; equals is the final check that picks the right entry in the bucket. So the two methods work as a pair. If you override equals but not hashCode, two objects that are equal get the default identity hash codes, which are different. They fall into different buckets, and get(new Key(1)) does not find the entry stored with new Key(1). If you override hashCode but not equals, they reach the same bucket but equals still compares references, so the lookup fails again. The contract: equal objects must have equal hash codes; unequal objects may share a hash code, but fewer shared codes means faster maps.

class Key {                                   // BROKEN: only equals
    final int id; Key(int id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof Key k && k.id == id;
    }
}
Map<Key, String> m = new HashMap<>();
m.put(new Key(1), "one");
m.get(new Key(1));        // null (usually): different hash codes

// fix: add  @Override public int hashCode() { return Integer.hashCode(id); }
// or use a record: record Key(int id) {}  - equals and hashCode are generated
What is the load factor and why is the default 0.75? Intermediate

What the interviewer is testing: the time versus space trade-off.

The load factor says how full the table is allowed to get before it grows. The resize threshold is capacity times loadFactor. With 16 slots and 0.75, the table resizes when the 13th entry is added (size becomes 13, which is above 12). A low load factor, say 0.5, means more empty buckets and fewer collisions: faster lookups, more memory, and resizes happen sooner. A high one, say 1.0 or more, saves memory but makes chains longer and slows lookups. The JDK authors chose 0.75 as a good middle ground: with a good hash function, the number of entries per bucket is roughly Poisson distributed, and at 0.75 most buckets hold zero, one or two entries, and the chance of a chain of 8 is about 6 in 100 million (the number is written in the source comments). You can set it through the constructor, new HashMap<>(capacity, 0.5f), but I would change it only after measuring.

Likely follow-ups
  • What is the threshold for the default map? Initial capacity 16, threshold 12; then 32 and 24; then 64 and 48, doubling each time.
What happens during a HashMap resize, and why is it expensive? Senior

What the interviewer is testing: internals and cost awareness.

When the size passes the threshold, resize() allocates a new array of twice the length and moves every entry. The cost is O(n), plus allocation of a large array, and garbage from the old one. Because capacity is a power of two, an entry in old bucket j goes to either j or j + oldCapacity in the new table. Java 8 checks one bit: (hash & oldCap) == 0 means the entry stays at j, otherwise it moves to j + oldCap. It splits each chain into a "low" list and a "high" list in one walk, keeping the relative order of the entries, and drops each list into its slot. No hash is recomputed (the hash is stored in the node), and tree buckets split the same way (and turn back into plain chains if they are 6 nodes or less). In a large map one resize can pause the calling thread for noticeable time, so if you know you will store a million entries, size the map up front and avoid about 20 resizes.

Likely follow-ups
  • Why is order preserved in Java 8 but reversed in Java 7? Java 7 inserted each moved entry at the head of its new bucket, flipping the chain order. That flip is what enabled the infinite loop race (see the Java 7 question).
  • Is resizing incremental? Not in HashMap, it is all at once. ConcurrentHashMap shares the work between threads.
When and why does a HashMap bucket turn into a tree? What are 8, 6 and 64? Senior

What the interviewer is testing: the Java 8 improvement and the three constants.

Long chains are slow: lookups in one bucket are O(chain length). They happen with poor hash codes, or deliberately: an attacker can send many keys with the same hash and make a web server crawl (a hash flooding denial of service attack). Java 8 therefore switches a long bucket to a red-black tree, making lookups in that bucket O(log n). The rules: TREEIFY_THRESHOLD = 8: when a bucket already holds 8 nodes and a new one is added, treeifyBin is called. MIN_TREEIFY_CAPACITY = 64: but if the table has fewer than 64 slots, the map resizes instead, because a short table is the likelier cause of crowded buckets. UNTREEIFY_THRESHOLD = 6: when a resize splits a tree bucket into pieces of 6 nodes or less, they convert back to plain lists. The gap between 8 and 6 stops a bucket from flipping back and forth. Inside the tree, nodes are ordered by hash first, then by compareTo if the keys are the same class and Comparable, and as a last resort by a tie-break on System.identityHashCode. So keys that implement Comparable get full benefit; keys that do not may need a search of both subtrees. Tree nodes also keep the next pointers, so iteration still works like a list. Tree nodes are about twice as large as plain nodes, which is the reason trees are used only when needed.

Likely follow-ups
  • Why 8? Under good hashing a chain of 8 is about one in 10 million, so treeification is rare and means "something is wrong with the hash".
  • Does treeification change the worst case? Yes: O(n) in Java 7, O(log n) in Java 8, if the keys are comparable.
What are the main differences between HashMap in Java 7 and Java 8? Senior

What the interviewer is testing: up-to-date knowledge and the reasons behind the changes.

First, trees. Java 7 used only linked lists, so a bad or malicious set of hash codes gave O(n) lookups. Java 8 treeifies long buckets (O(log n)). Second, insertion point. Java 7 inserted a new entry at the head of the chain; Java 8 appends at the tail. Third, resize. Java 7 re-computed the index for every entry and put each moved entry at the head of its new chain, which reversed the chain order and made concurrent resizing able to build a cycle (see the infinite loop question). Java 8 splits each chain into a low and high part and keeps the order. Fourth, hash function: complex in Java 7 (with an optional randomised hash seed for String keys), the simple h ^ (h >>> 16) in Java 8. Fifth, the node class changed from Entry to Node (plus TreeNode), and the lazy table allocation arrived with Java 7u40 and Java 8. Sixth, the new default methods: getOrDefault, computeIfAbsent, merge and so on. One thing did not change: HashMap is still not thread safe, and misuse can still lose data in Java 8, only without the endless loop.

Why could HashMap loop forever in Java 7 when used by several threads? Senior

What the interviewer is testing: concurrency failure modes and a famous production bug.

In Java 7, when a table resizes, the transfer method walks each old chain and moves each entry to the new table by inserting it at the head of its new chain. That reverses the order of entries that stay together. Now imagine two threads both trigger a resize at the same time, on a bucket with A pointing to B. Thread 1 reads A and remembers next = B, then the scheduler pauses it. Thread 2 finishes its whole resize, and in the (shared) entries the chain is now B pointing to A. When thread 1 resumes, it still thinks "A, then B". It puts A at the head of its new bucket, then moves to B, whose next is already A. Following the links, B points to A and A points to B: a circular list. Any later get that lands in that bucket loops for ever and burns 100 percent of a CPU core. This was a well known production problem (threads stuck in HashMap.get in thread dumps). Java 8 changed the transfer to keep order, so this exact loop no longer happens, but HashMap in Java 8 can still lose entries, give stale reads and corrupt its size, so the real fix is always to use ConcurrentHashMap.

Likely follow-ups
  • Can Java 8 HashMap lose data under concurrency? Yes. Two threads can both write into the same empty bucket and one write is lost, and size can drift.
Does HashMap allow null keys and values? How about the other maps? Basic

What the interviewer is testing: a quick comparison across map classes.

HashMap allows one null key and any number of null values. The null key always has hash 0 (the code says key == null ? 0 : spread(key)), so it lives in bucket 0. LinkedHashMap follows HashMap. TreeMap with natural ordering throws NullPointerException for a null key, because it calls compareTo on the key; null values are allowed. Hashtable and ConcurrentHashMap allow neither null keys nor null values. EnumMap rejects null keys, allows null values. Map.of and List.of reject all nulls. With HashMap there is one ambiguity worth knowing: get(k) returning null can mean "no such key" or "key mapped to null". Use containsKey to tell them apart, which is the same reason ConcurrentHashMap banned nulls (it cannot check containsKey and get atomically).

How do you size a HashMap when you know how many entries it will hold? Intermediate

What the interviewer is testing: practical tuning, and a classic off-by-load-factor mistake.

A resize costs O(n) and creates garbage, so for a big map it is worth avoiding. The trap is that new HashMap<>(1000) does not mean "room for 1000 entries". It means 1000 slots, rounded up to 1024, and the threshold is 0.75 times that, so 768. Storing 1000 entries would still resize once. The right capacity is expected / 0.75 + 1, so for 1000 entries use about 1334, which rounds up to 2048 slots. Since Java 19 there is a factory that does this for you: HashMap.newHashMap(1000), with HashSet.newHashSet and LinkedHashMap.newLinkedHashMap alongside. Guava has Maps.newHashMapWithExpectedSize. Do not over do it: an oversized table wastes memory and makes iteration slower, since iteration visits every slot.

int expected = 1_000;
Map<String, Order> m1 = new HashMap<>((int) (expected / 0.75f) + 1);  // any Java
Map<String, Order> m2 = HashMap.newHashMap(expected);                    // Java 19+
What goes wrong if a HashMap key is mutated after insertion? Intermediate

What the interviewer is testing: why map keys should be immutable.

The map filed the entry in a bucket chosen by the key's hash code at the time of insertion, and it also stored that hash in the node. If you change a field that takes part in hashCode and equals, the key now hashes to a different bucket. A lookup with the changed key looks in the new bucket and finds nothing. A lookup with the old value of the key goes to the right bucket but equals now fails against the changed key. The entry is still in the map: it counts in size(), it shows up in iteration, but you can no longer get or remove it. That is a memory leak plus lost data. It is the same for a HashSet and for a TreeMap (where the tree order breaks). The rules: use immutable keys (String, Integer, UUID, records, enums), or never mutate fields used in equals and hashCode while the object is in a hash collection. This is also why List as a key is risky: a list's hash depends on its elements.

Set<List<Integer>> set = new HashSet<>();
List<Integer> k = new ArrayList<>(List.of(1, 2));
set.add(k);
k.add(3);                  // hash code changes
set.contains(k);           // false, though the same object is inside
set.size();                // 1
How do you write a good hashCode, and what happens with a bad one? Intermediate

What the interviewer is testing: practical equals/hashCode craft.

A good hashCode uses the same fields as equals (no more), and spreads different objects over many values. The standard recipe is to combine the fields with a multiplier, as String does with 31: result = 31 * result + field.hashCode(). In practice use Objects.hash(a, b, c) or let your IDE or a record generate it. Objects.hash allocates a varargs array and boxes primitives, so in a very hot path write the arithmetic by hand. A bad hashCode (a constant, or only the first letter of a name) does not break correctness, but all entries land in few buckets. In Java 7 that meant O(n) lookups. In Java 8 the bucket becomes a tree, so it is O(log n) if keys are Comparable, still much slower than O(1). Never include a field that changes, never use System.currentTimeMillis() or random values, and compute the hash from the same data that equals compares.

@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Account a)) return false;
    return id == a.id && Objects.equals(region, a.region);
}
@Override public int hashCode() { return Objects.hash(id, region); }
Likely follow-ups
  • Can two unequal objects have the same hash code? Yes, collisions are allowed.
  • What is "Aa".hashCode() versus "BB"? Both are 2112, a classic collision, handy for testing.
What is a hash flooding attack, and how does Java protect against it? Senior

What the interviewer is testing: security-aware thinking for services that take external input.

If an attacker knows how keys are hashed, they can send many different keys (such as request parameter names or JSON fields) that all share the same hash code. In a plain chained hash map, they land in one bucket, each insertion costs O(n), and a few megabytes of input can take minutes of CPU. That was a famous attack on web frameworks in 2011. Java defends in layers. Since Java 8, a crowded bucket becomes a red-black tree, so the damage is reduced to O(log n) per operation when the keys are Comparable (strings are). Java 7u6 had an optional alternative hashing for strings that was removed again in Java 8 in favour of trees. Application frameworks also cap the number of parameters and JSON fields accepted. If you write a service that builds a map from untrusted keys, limit input sizes, and prefer keys with a good hash such as String or UUID.

What order does HashMap iterate in, and can I rely on it? Basic

What the interviewer is testing: not building logic on unspecified behaviour.

The iteration order is bucket by bucket from index 0 up, and inside a bucket along the chain. That depends on the hash codes, the capacity, and the insertion history, so it looks random, and it can change when the map resizes, or between JDK versions. The documentation says "no guarantee about order", so tests that compare a printed map to a fixed string, or APIs that return a HashMap and expect stable JSON field order, are bugs waiting to happen. For small Integer keys it often looks sorted (because the hash of an Integer is its value), which tricks people into relying on it. If you need insertion order use LinkedHashMap, if you need sorted order use TreeMap. Iteration cost is proportional to the capacity plus the size, so a huge, mostly empty table is slow to loop over.

HashMap vs Hashtable vs Collections.synchronizedMap vs ConcurrentHashMap. Intermediate

What the interviewer is testing: choosing a map for a threaded program.

HashMap: no locks, fastest, not thread safe, allows null. Hashtable (Java 1.0): every method synchronized on the whole table, so threads queue up even for reads; no nulls; legacy, avoid in new code. Its iterator is fail-fast, and it also exposes an old Enumeration. Collections.synchronizedMap(map): a wrapper that puts one mutex around every call, same contention as Hashtable, but works for any Map (including TreeMap). To iterate over it you must hold the lock yourself: synchronized (m) { for (...) }. ConcurrentHashMap: built for concurrent use: reads are lock-free, writes lock only one bucket (or use a CAS), no nulls, atomic compute, merge and putIfAbsent, and iterators that never throw ConcurrentModificationException. For shared maps in new code, use ConcurrentHashMap.

Likely follow-ups
  • Why is Hashtable's lowercase "t" in the name? It predates the Java naming convention. A fun but real trivia point.
  • Is Properties a map? Yes, it extends Hashtable, which is one reason people still meet it.
How much memory does a HashMap use per entry? Senior

What the interviewer is testing: memory awareness for large in-memory maps.

On a 64-bit HotSpot JVM with compressed pointers, one HashMap.Node is about 32 bytes: a 12-byte object header, the cached hash (4), and three 4-byte references key, value, next, rounded up to 32. The table adds about 4 bytes per slot, and with a load factor of 0.75 there are roughly 1.3 to 2.7 slots per entry, so a few more bytes. So the map itself costs around 40 bytes per entry before counting the key and the value objects. For Map<Integer, Integer> add two Integer objects of 16 bytes each, about 72 bytes per entry in total, to store 8 bytes of real data. A million such entries is roughly 70 MB. LinkedHashMap adds two more references per entry (about 40 bytes per node), TreeMap entries are about 40 bytes (key, value, left, right, parent, colour flag). Where this matters, use primitive-specialised maps (fastutil, Eclipse Collections), arrays indexed by id, or a database.

What do merge, compute, computeIfAbsent and getOrDefault do, and what are their traps? Intermediate

What the interviewer is testing: fluent, safe use of the Java 8 map API.

getOrDefault(k, d) returns the value, or d if the key is absent (it does not store anything). putIfAbsent(k, v) stores only when the key is absent (or mapped to null) and returns the old value. computeIfAbsent(k, f) calls f(k) when the key is absent, stores the result and returns it, the best tool for a map of lists. computeIfPresent(k, f) recomputes only if the key exists. compute(k, f) always calls f(k, oldOrNull); returning null removes the entry. merge(k, v, f) stores v if the key is absent, otherwise stores f(old, v), and removes the entry if f returns null: perfect for counters. The traps: in a plain HashMap, changing the same map from inside the mapping function throws ConcurrentModificationException in Java 9 and later (so recursive memoisation such as a Fibonacci cache with computeIfAbsent fails). In a ConcurrentHashMap the same recursion can deadlock or throw IllegalStateException: Recursive update. Keep the function short and free of side effects.

Map<Character, Integer> freq = new TreeMap<>();
for (char c : s.toCharArray()) freq.merge(c, 1, Integer::sum);

Map<Long, Long> memo = new HashMap<>();
long fib(long n) {          // BROKEN on Java 9+: modifies memo inside computeIfAbsent
    if (n < 2) return n;
    return memo.computeIfAbsent(n, k -> fib(k - 1) + fib(k - 2));
}

5. LinkedHashMap, TreeMap and the special maps

How does LinkedHashMap keep order, and what is access order? Intermediate

What the interviewer is testing: structure, and the hook that makes LRU caches easy.

LinkedHashMap extends HashMap. Its entries are the HashMap nodes with two extra pointers, before and after, forming a doubly linked list through all the entries, plus head and tail references. The hash table still gives O(1) lookup; the list gives the iteration order. By default the order is insertion order (re-putting an existing key does not move it). With the constructor new LinkedHashMap<>(16, 0.75f, true) the order is access order: every get, put or compute on a key moves its entry to the tail, so the head is the least recently used entry. Iteration is faster than HashMap when the table is large and sparse, because it follows the list. The extra cost is two references per entry (about 8 bytes). In Java 21 it also implements SequencedMap, adding firstEntry, lastEntry, putFirst, putLast, pollFirstEntry and reversed().

Likely follow-ups
  • Is LinkedHashMap thread safe? No. And in access-order mode even get changes it, so concurrent reads are also unsafe.
Implement an LRU cache using LinkedHashMap. Intermediate

What the interviewer is testing: the shortest correct solution, and knowing the hook method.

Create a subclass of LinkedHashMap with access order turned on, and override removeEldestEntry. The map calls this hook after every put; if it returns true, the eldest (least recently used) entry is removed. That is the whole cache. Reads are O(1), writes are O(1), and the size stays bounded. For thread safety, wrap it with Collections.synchronizedMap, since even get modifies the order, so a read lock is not enough. For heavy concurrent use do not hand-roll it; use Caffeine, which gives size limits, expiry, statistics, and much better concurrency.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxEntries;
    LruCache(int maxEntries) {
        super(16, 0.75f, true);            // true = access order
        this.maxEntries = maxEntries;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxEntries;
    }
}
Map<String, String> cache = Collections.synchronizedMap(new LruCache<>(100));
Likely follow-ups
  • How would you do it without LinkedHashMap? A HashMap from key to a node, and your own doubly linked list: move a node to the front on access, evict the tail. See the coding section.
How does TreeMap work, and what can it do that HashMap cannot? Intermediate

What the interviewer is testing: sorted maps and navigation methods.

TreeMap stores its entries in a red-black tree, a self-balancing binary search tree. After every insert or delete it recolours and rotates nodes to keep the height at most about 2 log2(n). So put, get, remove, containsKey are all O(log n), slower than HashMap's O(1), but the keys are always in sorted order, by natural order or by the Comparator given to the constructor. That sorted order gives the NavigableMap methods: firstKey, lastKey, floorKey(k) (greatest key at or below k), ceilingKey(k) (smallest key at or above k), lowerKey, higherKey, headMap, tailMap, subMap (live range views) and descendingMap. Uses: time series lookup ("the price in force at time t" is floorEntry(t)), leaderboards, interval problems, ranges. It treats two keys as the same when compareTo returns 0, not when equals is true. It is not thread safe; ConcurrentSkipListMap is the concurrent sorted map.

Likely follow-ups
  • Why red-black and not a plain BST? A BST fed sorted data turns into a linked list with O(n) lookups. Balancing prevents that.
  • Does headMap copy? No, it is a view over the same tree.
HashMap, LinkedHashMap or TreeMap: how do you choose? Basic

What the interviewer is testing: the standard decision, justified.

Start with HashMap: expected O(1), the least memory of the three, and good for most lookups where order does not matter. Take LinkedHashMap when you need a predictable iteration order (the order in which things were added, for example for stable output or for ordered JSON), or an LRU cache. It costs a little more memory. Take TreeMap when you need the keys sorted, or questions like "which key is closest to this one", or "all keys between a and b". It costs O(log n) per operation, and keys must be mutually comparable. The rule: do not pay for order you do not use. A common mistake is using TreeMap "to make output look nice" in a hot path, and paying log n on every call for it.

What is IdentityHashMap, and when would you use it? Senior

What the interviewer is testing: knowledge of rarely used but legitimate classes.

IdentityHashMap compares keys with == (reference equality) and hashes them with System.identityHashCode, ignoring the equals and hashCode you wrote. Two different String objects with the same text are two different keys. Internally it does not use bucket chains: it is a single flat array with keys and values stored next to each other and linear probing (if a slot is taken, try the next one), which is compact and fast. It deliberately breaks the general Map contract, so the Javadoc warns about it. It fits cases where object identity is the real meaning: tracking which objects were already visited in a graph walk (serialisation, deep copy, cycle detection, object graph size estimators), per-instance metadata, and proxy or framework internals. For a set of identities, use Collections.newSetFromMap(new IdentityHashMap<>()).

What is WeakHashMap, and why is it a poor cache? Senior

What the interviewer is testing: reference types meeting collections, and a classic memory-leak trap.

In a WeakHashMap each key is held through a WeakReference. When no other strong reference to the key object exists, the garbage collector may clear it, and the map then removes the entry (lazily, on the next map operation, using a ReferenceQueue). So entries disappear without anyone calling remove. It fits "extra data attached to an object for as long as that object lives", for example metadata about class loaders or listeners. As a cache it is poor for three reasons. First, the entry lives while the key is strongly reachable, not while it is useful, so it is often kept too long or dropped at random moments. Second, keys such as interned strings, string literals, and small cached Integer values are never collected. Third, the values are held strongly: if a value refers back to its own key, the key never becomes weakly reachable and the entry never goes away. That is the most common leak with this class. For real caches use Caffeine or Guava with size and time limits. Details of reference strengths are in Java: JVM.

What is EnumMap and why is it better than HashMap for enum keys? Intermediate

What the interviewer is testing: knowing the optimised special case.

EnumMap stores its values in a plain array indexed by the ordinal() of the enum key (the position of the constant in the declaration). A lookup is one array access, with no hashing, no buckets, no resize, no collision. Memory is one slot per enum constant, no entry objects. Iteration order is the declaration order of the enum, which is deterministic. Null keys are not allowed, null values are. The constructor needs the enum class: new EnumMap<>(Day.class). Use it whenever the keys are all from one enum, for example counts per status, handlers per command type, a table per day of the week. EnumSet is the set version, backed by a bit vector. Neither is thread safe.

Map<Status, Integer> perStatus = new EnumMap<>(Status.class);
for (Order o : orders) perStatus.merge(o.status(), 1, Integer::sum);
What is ConcurrentSkipListMap, and when do you use it instead of TreeMap? Senior

What the interviewer is testing: a sorted map that works under concurrency, and why not a tree.

A skip list is a linked list with extra "express lanes": a bottom level holds all entries in sorted order, and higher levels hold random subsets, so a search starts at the top and drops down, giving expected O(log n). Balanced trees such as red-black trees need rotations that touch many nodes, which is hard to do without locks. Skip list inserts only change a few local pointers, so they can be done with compare-and-swap (CAS) operations, and the structure is lock-free. ConcurrentSkipListMap (and ConcurrentSkipListSet) implement NavigableMap, so you get floorKey, ceilingKey, subMap in a thread-safe way. Iterators are weakly consistent and never throw ConcurrentModificationException. size() is O(n), because there is no stored counter. Use it when you need sorted order with concurrent readers and writers (a shared order book, a time-ordered event index); use ConcurrentHashMap when order is not needed, since it is faster.

6. ConcurrentHashMap

How does ConcurrentHashMap work in Java 8 and later? Senior

What the interviewer is testing: the most asked concurrent collection question. Know CAS, bin-level locks, and lock-free reads.

In Java 8 the design was rewritten. There is one big table, Node<K,V>[], like HashMap. The fields val and next in a node are volatile, and array slots are read with volatile semantics. Reads (get) take no lock at all: they compute the bucket and walk the chain, and the volatile reads guarantee they see a published node. Writes lock only one bucket. For put: if the bucket is empty, the new node is installed with a CAS (compare-and-swap: "set this slot to my node only if it is still null", an atomic CPU instruction), with no lock and a retry if another thread won. If the bucket is not empty, the thread does synchronized (firstNodeOfBucket), walks the chain, and updates or appends. So two threads block each other only when they write to the same bucket. Long buckets become trees (TreeBin) at the same 8 and 64 thresholds as HashMap. The size is tracked with a striped counter (see the size question). When the table must grow, threads that arrive help to move buckets (cooperative resize).

Likely follow-ups
  • What does the concurrencyLevel constructor argument do now? It is only a sizing hint; the segments are gone.
  • Is it fully lock-free? No: reads are lock-free and empty-bin inserts use CAS, but a collision in a non-empty bin takes a synchronized lock on that bin.
How was ConcurrentHashMap built in Java 7 (segments), and what was its weakness? Senior

What the interviewer is testing: history, and why the design changed.

In Java 7 (and 6), a ConcurrentHashMap was an array of Segment objects, 16 by default (set by concurrencyLevel, rounded up to a power of two). Each Segment extended ReentrantLock and held its own small hash table. A write picked the segment from the high bits of the hash, locked only that segment, and updated its table. So up to 16 threads (the segment count) could write at the same time, if they hit different segments. Reads did not lock: entry values were volatile. Weaknesses: the number of segments was fixed when the map was created, so you could not get more write concurrency later; each segment is a separate table with its own resize, and that wasted memory (a map with 16 segments allocates 16 sub-tables even if it holds three entries); and size() was awkward: it summed the counts of all segments without locks, compared modification counts, retried up to twice, and then locked every segment to get a stable total. Java 8 replaced this with the per-bin design, which has finer locking, less memory, and faster size counting.

Why is ConcurrentHashMap.size() only an estimate, and what is mappingCount? Senior

What the interviewer is testing: understanding that a single exact shared counter is a bottleneck.

A single shared size field would be a hot spot: every put and remove from every thread must update it, and the CAS retries or the lock would slow all writers. So Java 8 uses the same idea as LongAdder. There is a baseCount field, and under contention threads switch to an array of CounterCell objects, each thread adding to a cell chosen by a thread-specific hash. size() adds baseCount and all cells together. While other threads keep updating, the sum can be slightly stale or off, because the cells are read at slightly different moments, so the result is a snapshot-ish estimate, not a number that was true at one instant. That is fine for monitoring, but you should not use it for decisions such as "if size() < max then put", because the check and the put are not atomic anyway. mappingCount() is the same value as a long, recommended since a map may hold more than Integer.MAX_VALUE entries. isEmpty() has the same caveat.

Likely follow-ups
  • How do you enforce a hard limit on a concurrent map? Use a separate atomic counter or a Semaphore, or use a cache library (Caffeine) that handles bounded size.
Why does ConcurrentHashMap not allow null keys or values? Intermediate

What the interviewer is testing: reasoning about concurrency semantics, not memorising a rule.

The reason is ambiguity. With a normal map, if get(k) returns null you can call containsKey(k) to find out if the key is absent or mapped to null. In a concurrent map, another thread can add or remove the key between your two calls, so the second call gives you a wrong explanation. Banning null values makes null mean one thing only: "no mapping". That makes methods like putIfAbsent, computeIfAbsent and remove(key, value) well-defined, as null can be the internal signal for "absent". Doug Lea, the author, has also explained that allowing nulls would hide bugs in concurrent code. Null keys are banned because the hash and equality code does not handle them. If you need to represent "empty" values, use Optional, a sentinel object, or a special enum constant.

Is if (!map.containsKey(k)) map.put(k, v) safe on a ConcurrentHashMap? Intermediate

What the interviewer is testing: the difference between thread-safe methods and thread-safe sequences of methods.

No. Each call is atomic on its own, but the pair is not. Two threads can both see that the key is absent, and both put, so the second silently overwrites the first, and if the value is an expensive object you created it twice. The same applies to "get, modify, put": two threads read 5, both write 6, one increment is lost. The fix is to use the single atomic methods: putIfAbsent, computeIfAbsent, compute, merge, replace(k, old, new). For counting use map.merge(key, 1L, Long::sum), or a LongAdder as the value for very high contention: map.computeIfAbsent(k, x -> new LongAdder()).increment(). The mapping function inside compute methods runs while the bin is locked, so keep it quick, do no I/O, and do not touch the same map from inside it.

ConcurrentMap<String, LongAdder> hits = new ConcurrentHashMap<>();
hits.computeIfAbsent(url, k -> new LongAdder()).increment();   // atomic and cheap

// WRONG: lost update
Integer old = map.get(k);  map.put(k, old == null ? 1 : old + 1);
// RIGHT
map.merge(k, 1, Integer::sum);
Do ConcurrentHashMap iterators throw ConcurrentModificationException? What do they guarantee? Intermediate

What the interviewer is testing: the correct word "weakly consistent", rather than the muddy "fail-safe".

No, they never throw it. The iterators of ConcurrentHashMap are weakly consistent. They walk the table as it is while you iterate. They reflect the state of the map at some point at or after the creation of the iterator, may or may not show changes made after that, never show the same key twice, and never fail because of concurrent updates. So you can remove entries in a loop without an error. The price is that you get no exact snapshot: if another thread adds a key during your loop, you may or may not see it. That is fine for cleaning up stale entries, or for monitoring. If you need a true snapshot, copy first (new HashMap<>(map) is itself weakly consistent, so lock around it when exactness matters) or use CopyOnWriteArrayList-style snapshot structures.

How does ConcurrentHashMap resize without stopping everybody? Senior

What the interviewer is testing: depth on the Java 8 design.

When the count passes the threshold, a thread allocates the next table (double size), and begins to transfer bins from the old table to the new one, starting from the high end. Each thread claims a chunk of bins (a "stride", at least 16 bins) using a CAS on a shared index. For every bin it has moved, it puts a special ForwardingNode in the old table, which points to the new table. Other threads that run into a ForwardingNode during put do not wait: they help with the transfer for a while, then retry. Threads that run get and meet a ForwardingNode just follow it to the new table and read there. Each bin is split into low and high lists like in HashMap, under that bin's lock. So the resize work is shared by the threads that need the map, reads continue, and there is no single stop-the-world copy. The total work is the same O(n), but spread out.

ConcurrentHashMap versus Collections.synchronizedMap: when would you still pick the synchronized wrapper? Senior

What the interviewer is testing: trade-offs, not "always use CHM".

ConcurrentHashMap is the right default for shared maps: more parallelism, atomic compound methods, safe iteration. But it is not always the better fit. The synchronized wrapper gives you one lock for the whole map, so you can make a multi-step operation atomic by holding that lock yourself: "check the size, then put, then update a second structure". CHM cannot do that across several keys, since it only guarantees atomicity per key. The wrapper also accepts nulls, keeps the ordering of the wrapped map (a LinkedHashMap for LRU, a TreeMap for sorting), and can be simpler when contention is low. The costs: all threads, including readers, serialise on that lock, and iteration needs manual locking. For sorted concurrent access use ConcurrentSkipListMap. For a concurrent LRU cache use a library, not either.

How do you make a concurrent Set, and what are the other concurrent collections? Intermediate

What the interviewer is testing: breadth of the java.util.concurrent toolbox.

There is no ConcurrentHashSet class. Use ConcurrentHashMap.newKeySet() (Java 8), which returns a Set backed by a CHM, or Collections.newSetFromMap(new ConcurrentHashMap<>()). The toolbox: ConcurrentHashMap (hash map), ConcurrentSkipListMap and ConcurrentSkipListSet (sorted), CopyOnWriteArrayList and CopyOnWriteArraySet (read-mostly), ConcurrentLinkedQueue and ConcurrentLinkedDeque (lock-free, unbounded), and the BlockingQueue family for producer-consumer hand-off. Do not build your own from a HashSet plus synchronized unless you also need multi-step atomicity.

How does ArrayDeque work, and why is it preferred over Stack and LinkedList? Intermediate

What the interviewer is testing: circular buffers, and modern stack and queue practice.

ArrayDeque is a resizable circular array: an Object[] with a head index and a tail index that wrap around the end of the array. Adding at the front moves head back by one (wrapping to the end if needed), adding at the back moves tail forward. Both ends are O(1), with no shifting of elements and no node objects. When full, it allocates a larger array and copies the elements into the front of it (older JDKs kept the length a power of two and used a bit mask for wrapping; newer ones grow by about double while small, then by half). It does not allow null elements, because null marks an empty slot and poll returns null for "empty". It is faster than LinkedList as a queue, with less memory, since there is no per-element node and the array is cache friendly, and it is faster than Stack because it has no synchronisation. Use push/pop/peek for a stack, offer/poll for a queue. It is not thread safe.

  • Does it implement List? No, so no get(i).
How do you implement a stack and a queue in Java today? Basic

What the interviewer is testing: a practical coding habit.

Use ArrayDeque for both, declared as the interface Deque (or Queue). As a stack (last in, first out), use push, pop and peek, which work on the front of the deque. As a queue (first in, first out), use offer to add at the tail and poll to remove from the head. Avoid java.util.Stack (legacy, synchronised, inherits Vector methods) and avoid LinkedList unless you need nulls. If many threads share it, use ConcurrentLinkedDeque or a BlockingQueue. Typical uses: a stack for DFS, undo, bracket matching, and a queue for BFS and level-order traversal.

Deque<Character> st = new ArrayDeque<>();
for (char c : s.toCharArray()) {                 // balanced brackets
    if ("({[".indexOf(c) >= 0) st.push(c);
    else {
        if (st.isEmpty()) return false;
        char o = st.pop();
        if ("({[".indexOf(o) != ")}]".indexOf(c)) return false;
    }
}
return st.isEmpty();
How does PriorityQueue work, and what are its complexities? Intermediate

What the interviewer is testing: the binary heap in an array, and how siftUp and siftDown work.

PriorityQueue is a binary min-heap stored in a plain array. A heap is a complete binary tree where each parent is less than or equal to its children, so the smallest element is always at the root (index 0). Because the tree is complete, it fits in an array without pointers: for the node at index i, the parent is (i - 1) / 2, and the children are 2i + 1 and 2i + 2. peek reads index 0: O(1). offer adds the element at the end and sifts up: while it is smaller than its parent, swap with the parent: O(log n). poll takes the root, moves the last element to the root and sifts down: swap with the smaller child until the order holds: O(log n). remove(Object) and contains are O(n), as they search the array. Building from an existing collection with the constructor new PriorityQueue<>(collection) uses heapify in O(n), which is cheaper than n inserts. Order comes from Comparable or a Comparator. It is not thread safe (PriorityBlockingQueue is), allows no nulls, and is not stable for equal priorities.

Likely follow-ups
  • Why is iterating or printing a PriorityQueue not sorted? Only the parent-child order is guaranteed. Use repeated poll to get sorted order.
  • Max-heap? new PriorityQueue<>(Comparator.reverseOrder()).
Why does a heap suit "top K" problems? What is the complexity? Intermediate

What the interviewer is testing: choosing a heap of size K, and the "min-heap for the largest" twist.

To find the K largest of n items, keep a min-heap of size K. For each item: add it, and if the heap now has more than K elements, remove the smallest (the root). At the end, the heap holds the K largest items, and the root is the K-th largest. Each step costs O(log K), so the total is O(n log K), and memory is O(K). That beats sorting everything (O(n log n)) when K is much smaller than n, and it works on a stream: you do not need all data in memory at once. The twist that candidates miss: use a min-heap to track the largest, since the root is the weakest of the current top K and the first to be thrown out. For the K smallest use a max-heap. If the data fits in memory and K is large, sorting or quickselect (average O(n)) is also fine.

int[] topK(int[] nums, int k) {
    PriorityQueue<Integer> heap = new PriorityQueue<>();   // min-heap
    for (int x : nums) {
        heap.offer(x);
        if (heap.size() > k) heap.poll();                    // drop the smallest
    }
    return heap.stream().mapToInt(Integer::intValue).toArray();
}
What is a BlockingQueue and which implementations exist? Intermediate

What the interviewer is testing: producer-consumer building blocks, and choosing between them.

A BlockingQueue is a thread-safe queue where put waits if the queue is full and take waits if it is empty, so threads coordinate without hand-written wait and notify. The family: ArrayBlockingQueue: bounded, a fixed array, one lock, optional fairness. LinkedBlockingQueue: linked nodes, optionally bounded (default is Integer.MAX_VALUE, so effectively unbounded), two locks (one for put, one for take) so producers and consumers do not block each other. PriorityBlockingQueue: unbounded, ordered by priority, put never blocks. DelayQueue: elements become available only after their delay expires, used for scheduling and expiry. SynchronousQueue: no capacity at all, each put waits for a matching take, a direct hand-off. LinkedTransferQueue: unbounded, adds transfer that waits until a consumer receives the element. LinkedBlockingDeque: a blocking double-ended queue. Choosing the bound and the full-queue policy is a core design decision: details of thread pools using them are in Java: Concurrency.

Likely follow-ups
  • Which queue does Executors.newFixedThreadPool use? An unbounded LinkedBlockingQueue, so a slow consumer means the queue grows until memory runs out.
  • And newCachedThreadPool? A SynchronousQueue, so it creates a new thread when none is free.
ArrayBlockingQueue versus LinkedBlockingQueue: which one and why? Senior

What the interviewer is testing: locks and memory trade-offs, and the bounded rule.

ArrayBlockingQueue has a fixed capacity chosen up front, one ReentrantLock shared by producers and consumers (with two conditions, notEmpty and notFull), and one pre-allocated array: no garbage per element, predictable memory, but a single lock for everything. LinkedBlockingQueue uses two locks, putLock and takeLock, and an atomic counter, so a producer and a consumer can work at the same time, which often gives better throughput with several threads. It allocates a node per element (more garbage and memory). The big trap is its default capacity: with no argument, it is unbounded. If producers are faster than consumers, it grows until you get an OutOfMemoryError. My rule: always give the queue a bound, so that a slow consumer pushes back on producers (backpressure) instead of eating memory. With a bounded queue, decide what happens when it is full: block, drop, or reject with an error.

Write a producer-consumer with a BlockingQueue. Intermediate

What the interviewer is testing: a standard coding task, with correct shutdown.

The queue does the waiting and the locking for you. The producer calls put, the consumer calls take. The one tricky part is stopping the consumer. A common solution is a poison pill: a special marker object the producer puts last, and the consumer exits when it takes it. With several consumers, put one pill per consumer. Also handle InterruptedException properly: restore the interrupt flag, or exit.

BlockingQueue<String> q = new ArrayBlockingQueue<>(100);   // bounded: backpressure
final String POISON = new String("STOP");                    // unique object, compared with ==

Thread producer = new Thread(() -> {
    try {
        for (String line : lines) q.put(line);               // blocks when full
        q.put(POISON);
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
Thread consumer = new Thread(() -> {
    try {
        while (true) {
            String s = q.take();                             // blocks when empty
            if (s == POISON) break;
            handle(s);
        }
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
What is ConcurrentLinkedQueue, and when do you prefer it to a BlockingQueue? Senior

What the interviewer is testing: blocking versus non-blocking designs.

ConcurrentLinkedQueue is an unbounded, lock-free FIFO queue. It is a linked list in which head and tail are updated with CAS, using the Michael and Scott algorithm. Producers and consumers never block each other, and a slow thread cannot stall others. Its poll returns null when empty (it never waits). size() is O(n), since it counts nodes by walking, and can be wrong under concurrent changes, so do not call it on a hot path, and use isEmpty() instead. Iterators are weakly consistent. Choose it when threads should never block and you poll in a loop, or in an event loop that does other work in between, and the volume is naturally limited. Choose a BlockingQueue when the consumer should sleep until work arrives, or when you need a bound for backpressure. ConcurrentLinkedDeque is the double-ended version.

8. Ordering, utilities and the equals/hashCode contract

Comparable versus Comparator: what is the difference and when do you use each? Basic

What the interviewer is testing: basic design, and fluent Java 8 comparator code.

Comparable<T> is implemented by the class itself, with one method compareTo(T other). It defines the natural order, the one obvious order for the type (numbers by value, strings alphabetically, dates by time). There can be only one. Comparator<T> is a separate object with compare(a, b). It defines any other order, so you can have many: by name, by age, reversed. It also lets you sort classes you cannot edit. Both return a negative number if the first is smaller, zero if equal, positive if larger. In Java 8 you build comparators from method references: Comparator.comparing(Person::name).thenComparing(Person::age), .reversed(), Comparator.nullsFirst(...), comparingInt (avoids boxing). Sorted collections (TreeMap, TreeSet, PriorityQueue) and Collections.sort use the natural order unless you supply a comparator.

record Person(String name, int age) {}
List<Person> ps = ...;
ps.sort(Comparator.comparing(Person::name, String.CASE_INSENSITIVE_ORDER)
                  .thenComparingInt(Person::age).reversed());

What is the compare contract, and what are the classic bugs in a comparator? Senior

What the interviewer is testing: catching the bugs that show up as rare production exceptions.

A valid comparator must be: antisymmetric (compare(a,b) and compare(b,a) have opposite signs), transitive (a before b and b before c means a before c), and consistent (the same answer every time, and ties behave the same). The classic bugs: (1) Subtraction: return a.age - b.age; overflows for large values (for example Integer.MIN_VALUE and 1), giving the wrong sign. Use Integer.compare(a, b). (2) Inconsistent tie-breaking or float chaos, such as comparing doubles with NaN, or comparing by a random number or a mutable field. (3) Forgetting a case, such as returning -1 when a is less and 1 otherwise, never 0. These can make TimSort throw IllegalArgumentException: Comparison method violates its general contract!, but only for larger inputs (about 32 elements and up), so it often escapes tests. (4) Null handling: use nullsFirst or nullsLast. (5) Consistency with equals for sorted sets and maps.

// BAD: overflow
Comparator<Item> bad = (a, b) -> a.price - b.price;
// GOOD
Comparator<Item> good = Comparator.comparingInt(Item::price);
Which sorting algorithms do Collections.sort and Arrays.sort use? Senior

What the interviewer is testing: knowing the stability and performance guarantees.

For objects (Collections.sort, List.sort, Arrays.sort(T[])) Java uses TimSort since Java 7: a merge sort that finds natural runs (already sorted stretches), extends short runs with insertion sort, and merges them. It is stable, O(n log n) worst case, and O(n) on data that is already sorted or reverse sorted, which is very common in real data. It needs up to n/2 extra memory. For primitives (Arrays.sort(int[])) Java uses dual-pivot quicksort, average O(n log n), not stable (irrelevant for primitives), no extra memory for most inputs. Arrays.parallelSort splits the array, sorts pieces with the fork/join pool and merges, which pays off for big arrays (thousands of elements and up) on multi-core machines. Before Java 7 objects used a plain merge sort, and an ordering bug in a comparator would not show up the way it does with TimSort.

State the equals and hashCode contract and show how breaking it affects collections. Intermediate

What the interviewer is testing: the contract and its concrete, observable consequences.

The equals contract: reflexive (x.equals(x)), symmetric (x.equals(y) iff y.equals(x)), transitive, consistent (same answer if nothing changed), and x.equals(null) is false. The hashCode contract: the same object returns the same hash while its equals-relevant fields are unchanged; if two objects are equal, they must return the same hash code; unequal objects may share a hash code. Effects: if equals is overridden without hashCode, HashSet stores "duplicates", HashMap.get misses stored entries, and contains says false. If equals is not symmetric (the usual way: comparing with a subclass or with a String), list.contains(a) and list.contains(b) can give different answers for the same pair. If hashCode uses a mutable field, entries get lost after a change. ArrayList.contains, indexOf and remove(Object) only use equals (and call it on the argument, o.equals(elem)), while hash collections use both. Records and Lombok-style generators give correct pairs automatically. The language-level details are in Java: Fundamentals.

Should I keep data in a TreeSet or sort a list when needed? Intermediate

What the interviewer is testing: deciding on access patterns rather than on habit.

Think about how the data is used. If you load data once, then read it in order many times, build an ArrayList and sort it once: O(n log n) total, then fast, cache-friendly iteration and binary search. If you insert and remove continually and need the sorted view or nearest-key queries at any time, a TreeSet or TreeMap costs O(log n) per change and gives the order for free, while keeping a list sorted would cost O(n) per insert. If you only need the smallest or largest item repeatedly, a PriorityQueue is cheaper than both. If you need only "top K", use a heap of size K. And if you need sorted order exactly once, at the end, collect into any structure and sort once. Do not use a TreeMap just to get ordered output of a few thousand entries produced once.

9. Iterators, removal and immutability

What is a fail-fast iterator and how does ConcurrentModificationException happen? Basic

What the interviewer is testing: the modCount mechanism, and that a single thread can trigger it.

Most collections (ArrayList, HashMap, HashSet, LinkedList, TreeMap) keep a counter called modCount that goes up each time the structure changes (add, remove, clear, resize; not a plain set of an element). When you ask for an iterator, it copies the current value into expectedModCount. On every next() (and remove()) it checks that the two are equal. If the collection was changed by anything other than this iterator, the numbers differ and it throws ConcurrentModificationException at once. That is "fail-fast": it stops early instead of returning wrong data. It is a best-effort check, a bug detector, not a thread safety tool, and it can happen in a single thread. The classic way is to remove from a list inside a for-each loop.

List<String> names = new ArrayList<>(List.of("a", "b", "c", "d"));
for (String n : names) {
    if (n.equals("b")) names.remove(n);     // ConcurrentModificationException
}

  • Does set(i, x) change modCount? No, only structural changes do.

Why does removing the second-to-last element in a for-each loop not throw, but removing others does? Senior

What the interviewer is testing: real understanding of how the check works, not just the slogan.

Look at ArrayList.Itr. hasNext() is just cursor != size. It does not check modCount. Only next() checks. Suppose the list is [a, b, c, d], and while you are looking at c (so the cursor is 3) you remove c. The size becomes 3, so cursor (3) != size (3) is false, hasNext() returns false, the loop ends and next() is never called, so no exception, and d was never visited. The loop silently skipped an element. Removing any other element makes hasNext() true and the next call to next() throws. This is a real quirk and a good reason not to rely on the exception: the safe way is to never modify during iteration, except through the iterator or removeIf. ArrayList.forEach and removeIf check modCount at the end of the loop, so they throw even in this case.

What are the safe ways to remove elements while iterating? Basic

What the interviewer is testing: a practical, correct toolbox.

Option one: removeIf(predicate) (Java 8), the simplest. For an ArrayList it works in one pass and compacts the array once, so it is O(n), and it is also the fastest way. Option two: use an Iterator and call it.remove(), which removes the last element returned by next() and keeps the iterator valid. Option three: loop with an index backwards on a list, so removals do not shift the elements you have not yet seen. Option four: build a new collection with the elements you want to keep (streams: filter then toList). Option five: for maps, map.entrySet().removeIf(...), map.values().removeIf(...) or map.keySet().removeAll(...). Option six: use a concurrent collection (ConcurrentHashMap, CopyOnWriteArrayList) if other threads also change it. Avoid calling list.remove(i) repeatedly inside a loop, it is O(n squared).

What does "fail-safe" mean for iterators? Is the term accurate? Intermediate

What the interviewer is testing: precise vocabulary, and the two designs behind the loose word.

"Fail-safe" is the common interview word for iterators that do not throw ConcurrentModificationException. The Javadoc does not use it, and it is misleading: nothing is "safe" in a magical way, you just get different guarantees. There are two designs. Snapshot iterators (CopyOnWriteArrayList, CopyOnWriteArraySet) iterate over a frozen copy of the array taken when the iterator was made. They never see later changes, and never fail. The cost is the copying on every write. Weakly consistent iterators (ConcurrentHashMap, ConcurrentLinkedQueue, ConcurrentSkipListMap) walk the live structure. They may or may not show changes made after they were created, never throw, and never return an element twice. The comparison to remember: fail-fast detects and throws (so the bug is visible), snapshot is consistent but stale, weakly consistent is live but not exact. Copying a collection with a normal iterator, such as new ArrayList<>(hashMap.keySet()), is not "fail-safe": the copy itself can fail if other threads change the source.

What can a ListIterator do that an Iterator cannot? Intermediate

What the interviewer is testing: small API depth that helps in list editing.

ListIterator works only on lists, and it moves in both directions: hasPrevious(), previous(), and it knows its position with nextIndex() and previousIndex(). It can also change the list while iterating, safely: set(e) replaces the last element returned, add(e) inserts at the current position, and remove() deletes the last one returned. You get one by calling list.listIterator() or listIterator(startIndex). A good use is editing a LinkedList in a single pass, where each add or remove through the iterator is O(1) because the iterator already holds the node. List.replaceAll(op) covers the "set each element" case for ArrayLists.

    String s = it.next();
    if (s.isEmpty()) it.remove();

    else if (s.equals("x")) it.add("x2");     // inserted after x

What is the difference between an unmodifiable and an immutable collection? Intermediate

What the interviewer is testing: a subtle, practical distinction behind many API-design bugs.

An unmodifiable collection is one that you cannot change through this reference. Collections.unmodifiableList(list) returns a read-only view of list: calls to add or remove on the view throw UnsupportedOperationException, but if the code that owns the original list changes it, the view changes as well. An immutable collection is one that nobody can change: List.of, Set.of, Map.of, List.copyOf, Stream.toList() (Java 16; though it allows nulls), Guava's ImmutableList. They are separate data, not backed by anything else. Both are shallow: the elements inside can still be mutable objects, so a "read-only" list of Date or of your own mutable beans can still be changed by editing the elements. For a safe API, copy at the boundary: store List.copyOf(input) in the constructor (defensive copy in) and return an unmodifiable view or the immutable list (defensive copy out), and make the elements immutable as well, for example with records.

List<String> src = new ArrayList<>(List.of("a"));
List<String> view = Collections.unmodifiableList(src);
List<String> frozen = List.copyOf(src);
src.add("b");
view.size();     // 2  (a live view!)
frozen.size();   // 1  (a real snapshot)

  • Does final List<String> x make the list immutable? No, final only stops reassignment of the variable.
A class returns its internal list from a getter. What can go wrong and how do you fix it? Intermediate

What the interviewer is testing: encapsulation of mutable state, a common review comment.

If the getter returns the field itself, the caller can add, remove or clear the list and so break the invariants of your object, without your class knowing (for example an Order whose total is cached while the caller adds items). Worse, in threaded code, the caller can iterate while your class modifies the same list. There are three fixes, from cheap to strong. Return an unmodifiable view: Collections.unmodifiableList(items), cheap, no copying, callers still see later changes. Return a copy: List.copyOf(items) or new ArrayList<>(items), O(n) per call, gives a snapshot. Or do not expose the list at all: offer methods such as addItem, forEachItem, itemCount, stream(). Also copy in the constructor and setter, otherwise the caller who passed the list in still holds a handle to your internals.

public final class Order {
    private final List<Item> items;
    public Order(List<Item> items) { this.items = List.copyOf(items); }   // copy in
    public List<Item> items()       { return items; }                      // immutable already
}

10. Sequenced collections (Java 21)

What are sequenced collections in Java 21 and what problem do they solve? Intermediate

What the interviewer is testing: that you follow the platform; JEP 431 is the biggest collections change since Java 9.

Before Java 21, getting "the first" or "the last" element, or iterating in reverse, was different for every collection. For a List it was get(0) and get(size() - 1). For a Deque it was getFirst(), getLast(). For a LinkedHashSet there was no direct way to get the last element at all (you had to iterate everything). For a SortedSet it was first() and last(). Java 21 adds three interfaces that unify this: SequencedCollection, SequencedSet and SequencedMap, for collections that have a defined encounter order. They add getFirst(), getLast(), addFirst(e), addLast(e), removeFirst(), removeLast(), and reversed(), which returns a live reverse-order view, not a copy. For SequencedMap the methods are firstEntry, lastEntry, pollFirstEntry, pollLastEntry, putFirst, putLast, reversed, and the views sequencedKeySet, sequencedValues, sequencedEntrySet. List, Deque, LinkedHashSet, SortedSet (so TreeSet), LinkedHashMap and SortedMap (so TreeMap) are retrofitted. HashSet and HashMap are not sequenced, since they have no defined order.

l.getLast();                // "c"
for (String s : l.reversed()) { }      // c b a, no copy
LinkedHashMap<String,Integer> m = new LinkedHashMap<>();
m.putFirst("x", 1);         // move or insert at the front

  • Which exception for an empty list? getFirst() and getLast() throw NoSuchElementException.

Are there compatibility gotchas with sequenced collections? Senior

What the interviewer is testing: awareness of what a platform upgrade can break.

A few. The new reversed() method on List may clash with a reversed() or getFirst() method that your own class, or a library such as Guava or Eclipse Collections, already defines on a custom list type: after upgrading to 21, a class can fail to compile or change its return type, so libraries ship fixes. Collections.reverse(list) (reverses in place) is not the same as list.reversed() (a view). List.of(...).addFirst(x) throws UnsupportedOperationException since the list is immutable, and so does addFirst on Arrays.asList. TreeSet.addFirst also throws, since a sorted set decides placement on its own. The default getFirst on a List is implemented through get(0), so on a custom list make sure it behaves. Check which Java version your service really runs: this API is not available on Java 17.

What are the differences between collect(Collectors.toList()), Stream.toList() and toUnmodifiableList()? Intermediate

What the interviewer is testing: small API differences that matter when code later modifies the list.

collect(Collectors.toList()) (Java 8) returns, in practice, an ArrayList that you can change, though the specification promises nothing. Stream.toList() (Java 16) returns an unmodifiable list (it throws UnsupportedOperationException on add), and, unlike List.of, it allows null elements. When should you not use a stream on a collection? Intermediate

What the interviewer is testing: judgement, not fashion.

Streams are great for filter, map and group pipelines, and they read well. A plain loop is better in several cases. In very hot paths with small collections, stream setup costs allocation and indirection. When the body needs to change local state, throw checked exceptions, or exit early in complicated ways. When you need to modify the collection you iterate: a stream must not modify its source (it can throw ConcurrentModificationException or give undefined results). When debugging: a long chain is harder to step through. And parallelStream() is a trap for small data or for I/O work: it uses the shared common fork-join pool, and one slow or blocking task can stall other parts of the application. A good rule is that parallel streams pay off for CPU-heavy work on large, easily splittable data (arrays, ArrayList), measured with a benchmark, not guessed.

How much memory does a List<Integer> use compared with an int[]? Why does it matter? Senior

What the interviewer is testing: object overhead awareness, which explains many "why is my heap so big" incidents.

An int[1_000_000] is one object: 4 bytes per element, about 4 MB, contiguous in memory. An ArrayList<Integer> with a million elements has an Object[] with 4 bytes per reference (with compressed pointers), plus a separate Integer object of 16 bytes per value (12 bytes object header plus 4 bytes of data), unless the value is in the cache of -128 to 127. That is about 20 MB for the same numbers, five times as much, and the Integer objects can be scattered across the heap, so iteration causes cache misses and the garbage collector must scan and track a million objects. A HashMap<Integer,Integer> costs about 70 bytes per entry, as computed earlier. The same story applies to Long, Double and Boolean. It matters in big in-memory indexes, analytics, and any hot path in which millions of boxed values are created and thrown away. Options: plain arrays, BitSet for sets of small ints, primitive collections (fastutil Int2IntOpenHashMap, Eclipse Collections IntIntHashMap), and primitive streams (IntStream). Always profile before choosing, since for a thousand elements this is irrelevant.

Find the duplicate elements in a list or array. Basic

What the interviewer is testing: reaching for a hash set instead of a nested loop, and noticing that Set.add returns a boolean.

The brute force compares every pair, O(n squared). Better: walk once with a HashSet called seen. seen.add(x) returns false if the element was already there, so that element is a duplicate. Collect those into a second set (so each duplicate is reported once). Time O(n), extra space O(n). Alternative with streams: count with groupingBy and keep those with count above 1. If the values are in a small range 0 to n-1, you can mark visited positions in the array itself to use O(1) extra space, but say that you are modifying the input.

static Set<Integer> duplicates(int[] a) {
    Set<Integer> seen = new HashSet<>();
    Set<Integer> dups = new LinkedHashSet<>();
    for (int x : a) {
        if (!seen.add(x)) dups.add(x);       // add returns false: already present
    }
    return dups;
}

Count the frequency of words, and find the first non-repeating character. Basic

What the interviewer is testing: merge for counting and LinkedHashMap for keeping order.

For frequencies, use a map from item to count, updated with merge(item, 1, Integer::sum). That is O(n). For the first non-repeating character, you need two ideas together: counts, and the order of first appearance. A LinkedHashMap keeps insertion order, so after counting every character, scan the map in order and return the first with count 1. Alternative with two passes over the string and a plain HashMap: count first, then walk the string again and return the first character whose count is 1. For a fixed alphabet such as lowercase letters, an int[26] is faster and needs no boxing.

static Map<String, Integer> wordFreq(String text) {
    Map<String, Integer> freq = new HashMap<>();
    for (String w : text.toLowerCase().split("\\W+")) {
        if (!w.isEmpty()) freq.merge(w, 1, Integer::sum);
    }
    return freq;
}

static char firstUnique(String s) {
    Map<Character, Integer> c = new LinkedHashMap<>();
    for (char ch : s.toCharArray()) c.merge(ch, 1, Integer::sum);
    for (Map.Entry<Character, Integer> e : c.entrySet())
        if (e.getValue() == 1) return e.getKey();

Group words that are anagrams, and group employees by department. Intermediate

static Collection<List<String>> groupAnagrams(String[] words) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String w : words) {
        char[] c = w.toCharArray();
        Arrays.sort(c);
        groups.computeIfAbsent(new String(c), k -> new ArrayList<>()).add(w);
    }
    return groups.values();
}

Find the top K most frequent elements. Intermediate

What the interviewer is testing: combining a frequency map with a size-K min-heap, and stating the complexity.

Step one: count with a HashMap, O(n). Step two: keep a min-heap of size K ordered by count. Offer each entry; if the heap grows beyond K, poll the smallest. When done, the heap has the K most frequent. Time O(n + m log K), where m is the number of distinct elements; space O(m). Sorting all entries would be O(m log m), worse when K is small. A bucket sort alternative is O(n): make a list for each possible count (up to n), put each element in the bucket of its count, then read buckets from the highest count downwards. That is a good thing to mention for a senior role.

static List<Integer> topKFrequent(int[] nums, int k) {
    Map<Integer, Integer> freq = new HashMap<>();
    for (int n : nums) freq.merge(n, 1, Integer::sum);

    PriorityQueue<Map.Entry<Integer, Integer>> heap =
        new PriorityQueue<>(Map.Entry.comparingByValue());      // min-heap by count
    for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
        heap.offer(e);
        if (heap.size() > k) heap.poll();
    }
    List<Integer> result = new ArrayList<>();
    while (!heap.isEmpty()) result.add(heap.poll().getKey());
    Collections.reverse(result);                                 // most frequent first
    return result;
}
Merge overlapping intervals. Intermediate

What the interviewer is testing: sort first, then one pass; a classic of sorting plus lists.

Sort the intervals by start. Then walk through them keeping a result list. For each interval: if the result is empty or the last result interval ends before this one starts, there is no overlap, so append it. Otherwise they overlap (or touch), so extend the last result interval to the larger of the two ends. Time O(n log n) for the sort, then O(n); space O(n) for the output. Ask whether touching intervals like [1,3] and [3,5] should merge; the code below treats them as overlapping. Use Integer.compare or comparingInt, not subtraction.

static int[][] merge(int[][] intervals) {
    int[][] sorted = intervals.clone();
    Arrays.sort(sorted, Comparator.comparingInt(a -> a[0]));
    List<int[]> out = new ArrayList<>();
    for (int[] cur : sorted) {
        if (out.isEmpty() || out.get(out.size() - 1)[1] < cur[0]) {
            out.add(cur.clone());                                // no overlap
        } else {
            int[] last = out.get(out.size() - 1);
            last[1] = Math.max(last[1], cur[1]);                 // extend
        }
    }
    return out.toArray(new int[0][]);
}
// [[1,3],[2,6],[8,10],[9,12]]  ->  [[1,6],[8,12]]
Implement an LRU cache from scratch with O(1) get and put. Senior

What the interviewer is testing: combining two structures: a hash map for lookup and a doubly linked list for order.

A map alone cannot tell which entry is oldest; a list alone cannot find an entry fast. Together they can. The HashMap maps a key to its list node. The doubly linked list keeps nodes from most recently used (near the head) to least recently used (near the tail). On get: look up the node, move it to the front, return the value. On put: if the key exists, update the value and move the node to the front; otherwise create a node, add it at the front, and if the size is above capacity, remove the node before the tail and its map entry. Dummy head and tail nodes remove all the null checks. Every step is O(1). It is not thread safe; for threads, lock the methods, since even a get changes the list.

class LRUCache<K, V> {
    private static class Node<K, V> { K key; V val; Node<K, V> prev, next; }
    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<>();
    private final Node<K, V> head = new Node<>(), tail = new Node<>();   // dummies

    LRUCache(int capacity) { this.capacity = capacity; head.next = tail; tail.prev = head; }

    synchronized V get(K key) {
        Node<K, V> n = map.get(key);
        if (n == null) return null;
        unlink(n); addFirst(n);
        return n.val;
    }
    synchronized void put(K key, V val) {
        Node<K, V> n = map.get(key);
        if (n != null) { n.val = val; unlink(n); addFirst(n); return; }
        n = new Node<>(); n.key = key; n.val = val;
        map.put(key, n); addFirst(n);
        if (map.size() > capacity) {
            Node<K, V> lru = tail.prev;
            unlink(lru); map.remove(lru.key);
        }
    }
    private void unlink(Node<K, V> n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFirst(Node<K, V> n) {
        n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n;
    }
}
Two-sum: find two numbers that add to a target. And intersect two arrays. Basic

What the interviewer is testing: the "remember what I have seen" map idea.

For two-sum, walk the array once and keep a map from value to index. For each x, the number you need is target - x. If it is already in the map, you have the pair; otherwise store x and carry on. Time O(n), space O(n), versus O(n squared) for two loops. Look-up before insert handles the case where both numbers are equal. For the intersection of two arrays, put one array in a HashSet, then walk the other and collect those present, using a second set so each value shows once. Or use retainAll on a copy of the set. If the arrays are already sorted, two pointers need no extra memory.

static int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> idx = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = idx.get(target - nums[i]);
        if (j != null) return new int[] { j, i };
        idx.put(nums[i], i);
    }
    return new int[0];
}

static Set<Integer> intersect(int[] a, int[] b) {
    Set<Integer> in = new HashSet<>();
    for (int x : a) in.add(x);
    Set<Integer> out = new LinkedHashSet<>();
    for (int x : b) if (in.contains(x)) out.add(x);
    return out;
}

How would you implement your own simple HashMap? Senior

What the interviewer is testing: whether you understand the structure well enough to build it: array, hash to index, chaining, resize.

Keep it short and say what you leave out. An array of nodes, each node with key, value and next. The index is (h ^ (h >>> 16)) & (table.length - 1) with a power-of-two length. put walks the chain, replaces if the key matches (Objects.equals), otherwise adds at the head or tail. After inserting, if size is above 0.75 times the length, double the table and re-insert all nodes. get walks the chain. I would mention what I skipped: treeification, null-key special case, iteration with fail-fast checks, shrinking, and thread safety.

class MyMap<K, V> {
    private static class Node<K, V> { final K k; V v; Node<K, V> next;
        Node(K k, V v, Node<K, V> n) { this.k = k; this.v = v; this.next = n; } }
    private Node<K, V>[] table = newTable(16);
    private int size;

    @SuppressWarnings("unchecked")
    private static <K, V> Node<K, V>[] newTable(int n) { return (Node<K, V>[]) new Node[n]; }
    private int idx(Object k, int len) { int h = Objects.hashCode(k); return (h ^ (h >>> 16)) & (len - 1); }

    V get(K k) {
        for (Node<K, V> n = table[idx(k, table.length)]; n != null; n = n.next)
            if (Objects.equals(n.k, k)) return n.v;
        return null;
    }
    void put(K k, V v) {
        int i = idx(k, table.length);
        for (Node<K, V> n = table[i]; n != null; n = n.next)
            if (Objects.equals(n.k, k)) { n.v = v; return; }
        table[i] = new Node<>(k, v, table[i]);
        if (++size > table.length * 3 / 4) resize();
    }
    private void resize() {
        Node<K, V>[] old = table, nt = newTable(old.length * 2);
        for (Node<K, V> head : old)
            for (Node<K, V> n = head; n != null; ) {
                Node<K, V> next = n.next;
                int j = idx(n.k, nt.length);
                n.next = nt[j]; nt[j] = n; n = next;
            }
        table = nt;
    }
}

14. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

A service on Java 7 hits 100 percent CPU on one core, and thread dumps show threads stuck in HashMap.get. What happened? Senior

What the interviewer is testing: recognising the famous HashMap resize race, and the real fix.

Situation: after a traffic spike, requests hang and one or more CPU cores sit at 100 percent. The service has a static HashMap used as a shared cache, with no synchronisation.

Check first: take three thread dumps a few seconds apart (jstack or jcmd Thread.print). If the same threads sit in HashMap.get, HashMap.put or HashMap.transfer with an identical stack every time, the loop is endless. In Java 7, two threads resizing at once can leave two entries pointing at each other (see the Java 7 loop diagram), so a lookup in that bucket never ends. Confirm that the map is shared and written by several threads.

Fix: restart to recover (the cycle is permanent in memory). Replace the map with ConcurrentHashMap. Also upgrade: Java 7 is long out of support, and Java 8 does not create this exact cycle, though it can still lose entries.

// before: shared mutable HashMap
private static final Map<String, Config> CACHE = new HashMap<>();
// after
private static final Map<String, Config> CACHE = new ConcurrentHashMap<>();
Config c = CACHE.computeIfAbsent(key, this::load);

Prevent: a review rule that any static or singleton-held collection must be a concurrent one or be guarded by a lock; static analysis (SpotBugs, Error Prone) flags many of these; load tests with several threads.

A multithreaded job fills a HashMap, and the final size is lower than the number of inserts, with no errors. Why? Intermediate

What the interviewer is testing: silent data corruption from unsafe sharing.

Situation: 8 threads each put 100,000 distinct keys into one HashMap. The final size() is 783,512 instead of 800,000, and sometimes a value is missing, with no exception.

Check first: is the map shared without a lock? Is the count off by a different amount on every run? That points to a data race. Two threads that write the same empty bucket at the same time both see "empty", and the second write overwrites the first node. The size field is incremented with a plain ++, which is not atomic, so increments are lost too. Resizes during concurrent puts can drop entries as well.

Fix: use ConcurrentHashMap. If each thread builds its own part, give every thread its own plain HashMap, then merge the results at the end on one thread (no sharing, no locks, usually the fastest). For counting, use merge or LongAdder. Do not "fix" it with Hashtable unless the performance is acceptable.

Prevent: a stress test with many threads, run in CI, that checks the counts; thread-confinement by design.

The heap grows slowly until the service runs out of memory after a few days, and the heap dump shows a huge static map. What do you do? Senior

What the interviewer is testing: the classic collections memory leak, and a structured heap-dump investigation.

Situation: old generation usage rises after every full GC, ending in OutOfMemoryError: Java heap space. The service has been up for days.

Check first: take a heap dump (jcmd PID GC.heap_dump, or -XX:+HeapDumpOnOutOfMemoryError) and open it in Eclipse MAT or VisualVM. Look at the "dominator tree" and the "leak suspects" report: one ConcurrentHashMap or ArrayList held by a static field, with millions of entries. The "path to GC roots" shows the static field that keeps everything alive. Check the code that fills it: a per-request or per-user cache, a registry of listeners that are added but never removed, a ThreadLocal, or an "audit" list.

Fix: decide what the map is for. If it is a cache, replace it with a bounded cache with eviction (Caffeine: maximumSize, expireAfterWrite) or a LinkedHashMap with removeEldestEntry. If it is a registry, add the matching remove in a finally or lifecycle method. If entries should vanish with their key objects, WeakHashMap can work (beware values that refer to the key).

Prevent: every long-lived collection must have a stated bound or an owner who removes entries; monitor old-gen after GC and alert on a slope; add a cache metric for size.

An entry exists in a HashMap (you can see it when you print the map), yet get returns null. What is going on? Intermediate

What the interviewer is testing: the mutable-key trap in a concrete form.

Situation: a Map<Customer, Order>. Later in the request a setter changes customer.setEmail(...). After that, map.get(customer) returns null, map.containsKey is false, but map.size() is unchanged, and iterating the map still shows the entry.

Check first: look at the key class. Does its hashCode use mutable fields (here the email)? The entry was stored in the bucket for the old hash. After the change, the lookup hashes to a different bucket, finds nothing, and the entry can never be found or removed through normal calls: a leak and a logic bug.

Fix: make the key immutable, or key on a stable identifier: Map<Long, Order> keyed by customer.getId(). If you must change a key, remove the entry first, change the object, then put it again. To recover now, rebuild the map: new HashMap<>(oldMap) re-hashes everything with the current hash codes.

Prevent: use records or immutable value types as keys; never base hashCode on fields that change; add a unit test that stores then looks up a key after normal use.

A nightly job that matches 100,000 records against a blocklist takes hours. You find a loop with list.contains. What do you do? Intermediate

What the interviewer is testing: spotting hidden quadratic behaviour and fixing it with the right structure.

Situation: the job reads 100,000 customers and a blocklist of 50,000 ids, and does blocked.contains(customer.id()) for each. The blocklist is an ArrayList. That is up to 5 billion equals calls.

Check first: profile or take a few thread dumps, and see the time inside ArrayList.indexOf. Confirm with a small experiment: double the input and see if the run time quadruples.

Fix: load the blocklist into a HashSet once (O(m)), and use contains on the set (O(1) expected). The job becomes O(n + m), seconds instead of hours. If the data is already sorted, a binarySearch or two pointers also works. Also check removeAll, retainAll and containsAll with a List argument: they hide the same quadratic cost.

Set<String> blocked = new HashSet<>(blockedList);
List<Customer> ok = customers.stream()
    .filter(c -> !blocked.contains(c.id()))
    .toList();

Prevent: in review, ask "what is the size of this list and how often do we search it?"; add a performance test with realistic volumes.

Production logs show ConcurrentModificationException from a method that "only loops over a list". How do you find and fix it? Intermediate

What the interviewer is testing: distinguishing the single-thread cause from the multi-thread cause.

Situation: a stack trace ends in ArrayList$Itr.checkForComodification, in a for-each loop. It happens sometimes only.

Check first: read the loop body. Is there any call, direct or indirect, that adds to or removes from the same list (an event handler, a callback, a remove in an if)? That is a bug in one thread, and it is deterministic. If the body does not touch the list, but the exception is rare, another thread is changing the list: a classic race on a shared field, for example a listeners list that is iterated while another thread registers a listener.

Fix (same thread): use removeIf or Iterator.remove, or collect the changes and apply them after the loop, or loop over a copy: for (X x : new ArrayList<>(list)). Fix (threads): use CopyOnWriteArrayList for read-mostly lists like listeners, a concurrent collection for others, or lock around both the loop and the change. Catching and ignoring the exception is not a fix.

Prevent: avoid sharing mutable lists; expose copies or unmodifiable views; test callbacks that re-enter.

A fixed thread pool feeding from a queue runs out of memory when a downstream service slows down. Why, and what is the fix? Senior

What the interviewer is testing: unbounded queues and backpressure.

Situation: an ExecutorService from Executors.newFixedThreadPool(8) receives a task per message. When the database slows down, memory climbs, latency rises, and finally OutOfMemoryError.

Check first: the heap dump shows millions of Runnable objects inside a LinkedBlockingQueue. The factory method creates a queue with capacity Integer.MAX_VALUE: producers never block, so a slow consumer means a queue that grows without limit.

Fix: create a ThreadPoolExecutor by hand with a bounded queue, such as new ArrayBlockingQueue<>(1000), and a rejection policy that fits: CallerRunsPolicy slows the producer down (natural backpressure), AbortPolicy fails fast, a custom handler can drop or spill to disk. Add metrics for queue size and rejections. The same logic applies to every in-memory buffer between a fast producer and a slow consumer. See Java: Concurrency for executors in detail.

Prevent: a team rule that all queues and caches have a bound; load test with a slow downstream.

Someone added a HashMap cache to speed up a lookup and a week later the service is slower and uses far more memory. What now? Intermediate

What the interviewer is testing: that a cache needs a policy, not just a map.

Situation: a "memoisation" map keyed by user input, such as a search string or a request id, only ever grows. Hit rate is low, since most keys are unique.

Check first: cache size over time, hit ratio, and the number of distinct keys. If the key space is unbounded (free text, timestamps, ids that never repeat), the cache is mostly a leak. Also check if values are big objects, and if the key includes volatile data.

Fix: use a real cache library with a maximum size and a time limit (Caffeine.newBuilder().maximumSize(10_000).expireAfterWrite(10, MINUTES)), and record stats. If you cannot add a library, use a LinkedHashMap LRU with removeEldestEntry behind a lock. Choose keys with high reuse. Only cache if the computation is expensive and repeated.

Prevent: treat a cache as a feature with size, expiry, and metrics, and review the hit rate after a week in production.

After a refactor, rows with the same score appear in a different order in a report, and sometimes a sort throws "Comparison method violates its general contract". What is wrong? Senior

What the interviewer is testing: stability, tie-breaking and the comparator contract in practice.

Situation: two symptoms. First: ties in the report come out in a different order than before. Second: a IllegalArgumentException: Comparison method violates its general contract! from TimSort, only with large inputs.

Check first: for the ordering: which sort is used? List.sort and Collections.sort are stable, so ties keep the input order, and the input order may have changed (for example the source is now a HashSet or a parallel stream, whose order is arbitrary). Arrays.sort on primitives is not stable. For the exception: read the comparator. Look for a - b subtraction (overflow), a comparator that returns 1 but never 0 for equal items, Double compared with NaN, or one that depends on a field that is mutated during the sort.

Fix: add an explicit total order with a final tie-breaker, such as the id: comparing(Row::score).reversed().thenComparing(Row::id). Use Integer.compare, Double.compare and comparingInt. Never "fix" the exception with the system property that switches the old merge sort on, since that hides the bug. Sort a copy of immutable snapshots.

Prevent: property-based tests for comparators (reflexive, antisymmetric, transitive), and always declare the tie-breaker when the output is shown to users.

A latency-sensitive service shows frequent young GCs and a profile full of Integer.valueOf and HashMap nodes. What is your plan? Senior

What the interviewer is testing: allocation profiling and pragmatic de-boxing.

Situation: p99 latency spikes line up with young GC pauses; the allocation rate is 2 GB per second; the hot path counts events per id in a Map<Long, Integer> and sums into a Long.

Check first: capture an allocation profile (Java Flight Recorder or async-profiler in alloc mode). It shows Long.valueOf, Integer.valueOf, HashMap$Node and iterator objects as the top allocators. Check the GC log for young collection frequency.

Fix: in order of effort: use primitive locals and accumulators instead of Long and Integer; replace Stream<Integer> with IntStream; use comparingInt; where ids are dense, use an int[] or long[] indexed by id; where they are sparse, use a primitive map (fastutil Long2IntOpenHashMap) which holds keys and values in flat arrays; presize collections to avoid resize garbage; reuse objects where safe. Re-measure each change: the JIT may already remove some boxing.

Prevent: allocation budget checks in performance tests; code review attention on collections of boxed numbers in hot loops.

A method that returns Arrays.asList(...) works in tests, but a caller crashes with UnsupportedOperationException. Another caller gets a list of size 1. Explain both. Basic

What the interviewer is testing: concrete knowledge of the fixed-size list.

Situation: List<String> roles = Arrays.asList("a", "b"), and later roles.add("c") throws UnsupportedOperationException. In another place Arrays.asList(intArray) gives a list with one element.

Check first: the stack trace points to AbstractList.add. Arrays.asList returns a fixed-size list wrapping the array: you can set, but not add or remove. For the second case: a primitive int[] is a single object, so the generic varargs treats it as one element, giving List<int[]>.

Fix: if the caller needs to edit the list, return new ArrayList<>(Arrays.asList(...)). If nobody should edit it, return List.of(...) (Java 9) and say so in the Javadoc. For ints: Arrays.stream(arr).boxed().collect(Collectors.toList()) or use Integer[]. Also remember it is write-through to the array.

Prevent: decide mutability in the method contract; test with a caller that modifies the result.

A TreeSet of employees seems to "lose" people: the set has 40 entries but the database has 100. Why? Intermediate

What the interviewer is testing: comparator ties are treated as duplicates in sorted collections.

Situation: new TreeSet<>(Comparator.comparing(Employee::department)) is used to "keep employees sorted by department". After adding 100 employees only one per department remains.

Check first: a TreeSet uses compare to decide equality: two employees in the same department compare as 0, so the second add is rejected without any warning (it returns false). The set has as many entries as there are distinct departments.

Fix: add a tie-breaker so the comparator is consistent with equals: comparing(Employee::department).thenComparing(Employee::id). If you only wanted to group, a TreeMap<String, List<Employee>> is the right structure. If you need a sorted view for display, sort a List.

Prevent: a rule of thumb for sorted collections: comparators must end with a unique key; test with duplicate sort keys.

Two requests created the same expensive object even though the code checks a ConcurrentHashMap first. How do you fix it? Senior

What the interviewer is testing: atomic compound operations, and the limits of computeIfAbsent.

Situation: code does if (!map.containsKey(k)) map.put(k, createConnectionPool(k));. The log shows two pools created for the same tenant, one leaked.

Check first: there is a check-then-act gap between containsKey and put, and two threads passed the check at the same time. The map is thread safe, the sequence is not.

Fix: use map.computeIfAbsent(k, this::createPool): it runs the function at most once per key, atomically, and other threads that ask for the same key wait for the result. Two cautions: the function runs while the bin is locked, so it must be fast and must not modify the same map (in Java 8 this can hang, and later versions throw IllegalStateException: Recursive update), and other keys that share the bin are blocked meanwhile. If creation is slow or can block, store a Future or CompletableFuture (or Lazy holder) in the map using computeIfAbsent and complete it outside the lock. Also decide what happens on failure: do not cache a failed attempt forever.

Prevent: a code-review checklist: no containsKey then put on concurrent maps; use the atomic methods.

A unit test that compares the printed form of a Set.of or HashSet fails randomly on the CI server. Why? Basic

What the interviewer is testing: not relying on unspecified iteration order.

Situation: assertEquals("[b, a, c]", set.toString()) passes on a laptop and fails on CI, or passes on the first run and fails on the next.

Check first: which collection? Set.of and Map.of use a per-JVM-run random salt, so their order changes on every run by design (Java 9 and later). A HashSet or HashMap order depends on hash codes and capacity, and objects without a hashCode override use identity hashes, which change per run. Different JDK versions also order differently.

Fix: compare as sets (assertEquals(Set.of("a","b","c"), actual)), since Set.equals ignores order; or sort before comparing; or, when order is part of the contract, use LinkedHashSet or TreeSet in the production code and test the order. For JSON output, ordered maps make output deterministic.

Prevent: never assert on the iteration order of an unordered collection.

A stream with Collectors.toMap works in testing but crashes in production with "Duplicate key". What do you do? Intermediate

What the interviewer is testing: data assumptions in the stream API.

Situation: users.stream().collect(toMap(User::email, u -> u)) throws IllegalStateException: Duplicate key a@x.com (attempted merging values ...) for one production tenant. A different dataset throws NullPointerException.

Check first: the message names the key and both values. Check the data: are emails really unique (case differences? whitespace? soft-deleted rows)? The NullPointerException comes from a null value, which toMap does not accept (it uses HashMap.merge).

Fix: decide the business rule and say it in code with a merge function: keep the newest ((a, b) -> a.updated().isAfter(b.updated()) ? a : b), keep the first, or group into lists with groupingBy if duplicates are valid. Normalise the key (toLowerCase(Locale.ROOT), trim). Filter out nulls before collecting. Log and count duplicates, because they signal a data-quality problem.

Prevent: always pass a merge function unless uniqueness is enforced by a constraint; test with duplicate input.

A listener list was changed to CopyOnWriteArrayList to fix a ConcurrentModificationException, and now the CPU and GC are high. What happened? Senior

What the interviewer is testing: understanding that copy-on-write trades writes for reads.

Situation: after the change, the exception is gone. A week later the service burns CPU in Arrays.copyOf, and the GC logs show a high allocation rate. The list is also used as a work buffer with thousands of adds per second.

Check first: how often is the list written, and how big is it? Each add or remove copies the whole array, O(n), and creates garbage; with 50,000 elements and 1,000 writes per second, that is 50 million element copies per second plus 200 KB of new arrays each time.

Fix: use copy-on-write only for "read often, write rarely" data (listeners, routing tables). For a frequently written list, use a ConcurrentLinkedQueue or a BlockingQueue if it is a buffer, a ConcurrentHashMap.newKeySet() if it is a registry, or a normal list with a lock (or ReentrantReadWriteLock). If writes come in bursts, batch them and swap one new immutable list in (an AtomicReference to an immutable list).

Prevent: know the access pattern before you choose, and measure the write rate.

A small list of "recent ids" holds a few elements, but a heap dump shows it keeps a 2-million-element list alive. Why? Senior

What the interviewer is testing: views that retain their backing structure.

Situation: this.recent = allIds.subList(0, 10); is stored in a long-lived field. The code later drops its own reference to the big allIds, and expects it to be collected. Memory stays high.

Check first: in the heap dump, the SubList object references its parent list, which holds the 2 million elements. A subList is a view, not a copy, so it keeps the whole parent reachable. Another variant of the same issue: String.substring in Java 6, and a large keySet view stored in a field.

Fix: copy what you keep: this.recent = new ArrayList<>(allIds.subList(0, 10)) or List.copyOf(...). Also note that a structural change to the parent invalidates the sublist with a ConcurrentModificationException.

Prevent: never store a view (subList, keySet, values, headMap, unmodifiableList) in a long-lived field unless you want that coupling.

On startup, loading 10 million entries into a HashMap takes much longer than expected and causes GC pauses. How do you speed it up? Intermediate

What the interviewer is testing: resize cost and presizing, with numbers.

Situation: a cache warm-up loop builds new HashMap<>() and puts 10 million entries. It is slow and the log shows several long GC pauses.

Check first: a map that starts with 16 slots must resize about 20 times to reach 16 million slots (2^24), copying all entries each time, and every resize creates a large temporary array. The old arrays become garbage, and the huge arrays can go straight to the old generation (humongous allocation with G1).

Fix: size the map up front: new HashMap<>((int) (10_000_000 / 0.75f) + 1) or HashMap.newHashMap(10_000_000) in Java 19. That allocates the 16 million slot table once. Also review memory: 10 million boxed entries at about 70 bytes each is 700 MB; consider primitive maps or a different store. If the load can be parallel, build in segments or use ConcurrentHashMap with a good initial size.

Prevent: whenever the size is known or easily estimated, pass it to the constructor; load-test startup.

An API endpoint that parses a JSON body into a Map suddenly uses 100 percent CPU for one request, and thread dumps show HashMap.putVal. What do you suspect? Senior

What the interviewer is testing: security thinking about collections used on untrusted input.

Situation: a single, large request makes one thread spin in HashMap.putVal or tree code for seconds or minutes. Other requests are also slow because of CPU pressure.

Check first: look at the body: thousands of keys that are different strings with the same hash code (strings like "Aa" and "BB" collide, and their combinations multiply). A hash-flooding input puts everything in one bucket. In Java 7 each put was O(n); in Java 8 the bucket is a tree and cost is O(log n) per put, so it is much milder, but still heavy with millions of keys.

Fix: limit input: maximum body size, maximum number of fields, maximum depth, maximum key length, enforced by the web framework or JSON parser settings; reject early. Keep the JDK up to date. Do not use TreeMap just for this, but note that it is immune because it does not use hashes. Add a request timeout and rate limiting.

Prevent: treat every collection that is built from external input as an attack surface: bound the number of elements.

A developer prints a PriorityQueue to check the sorting and sees an unsorted list. Is it broken? Basic

What the interviewer is testing: what the heap guarantees, and what it does not.

Situation: pq.addAll(List.of(5, 1, 4, 2, 3)); System.out.println(pq); prints [1, 2, 4, 5, 3]. The developer reports a bug. Another one loops with a for-each and gets the same unsorted order.

Check first: the output is a valid min-heap: every parent is smaller than its children (1 at the root, 2 and 4 below, then 5 and 3). A heap guarantees only that the root is the smallest, not a full order. toString, the iterator, stream() and toArray all follow the internal array order.

Fix: to get sorted output, remove with poll() in a loop (this empties the queue), or copy to a list and sort it, or use a TreeSet (without duplicates), or TreeMap with counts. If the code must also support changing priorities, remember that a changed element does not move automatically: remove and re-add it.

Prevent: document that the queue is for "next smallest", and never rely on iteration order.

A WeakHashMap used as a cache never shrinks, even after GC. What do you check? Senior

What the interviewer is testing: reference reachability reasoning.

Situation: WeakHashMap<Session, SessionInfo> was introduced so entries go away when a session ends, but heap use keeps growing and size() stays high after forced GCs.

Check first: three usual causes. One: the value (SessionInfo) holds a strong reference to its key (the Session), so the key stays strongly reachable through the map's own value, and never becomes weakly reachable. Two: the key is also referenced elsewhere (a list of active sessions, a thread local, a listener), so it is not garbage. Three: the keys are interned strings, literals or cached boxed numbers, which are never collected. A heap dump plus "path to GC roots, excluding weak references" in MAT shows who holds the key.

Fix: remove the back-reference (store only the data you need, or make the value hold the key weakly), or drop WeakHashMap and use an explicit lifecycle (remove when the session ends) or a bounded cache with expiry.

Prevent: avoid WeakHashMap for caches; use it for metadata attached to objects whose lifecycle you do not control, and check that values never refer to the keys.
