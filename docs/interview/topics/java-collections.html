Mental model: the 8 ideas everything hangs on

One line: a collection holds references to objects, and every class is a trade-off between lookup speed, insert speed, ordering, memory and thread safety. Interviews test whether you know which trade-off each class made, and why.
  1. Two families. Collection (List, Set, Queue) holds single elements. Map holds key to value pairs and is a separate hierarchy.
  2. Interface versus implementation. Declare List<String>, create ArrayList. The interface is the contract; the class is a performance decision.
  3. Four structures. Almost every class is a resizable array (ArrayList, ArrayDeque, PriorityQueue), a linked list (LinkedList), a hash table (HashMap, HashSet) or a balanced tree (TreeMap, TreeSet). Big-O follows from the structure.
  4. Hash tables need a good equals and hashCode. Break the contract and entries vanish or duplicate. Mutate a key after inserting it and the entry is lost.
  5. Order is a feature you pick. HashMap has no useful order, LinkedHashMap keeps insertion (or access) order, TreeMap keeps sorted order.
  6. Most classes are not thread safe. Sharing an ArrayList or HashMap between threads without protection loses updates or worse. Use the concurrent classes, not the old synchronized ones.
  7. Iterators are fail-fast. Change a collection while looping and you usually get ConcurrentModificationException. Remove through the iterator or with removeIf.
  8. Boxing costs memory. A List<Integer> is a list of objects, not numbers. That is often the real performance problem.

1. Framework basics

Explain the collections hierarchy. Is Map a Collection? Basic

Under Iterable sits Collection, with three children I use daily: List (ordered, duplicates allowed), Set (no duplicates) and Queue/Deque (processing order). Map is not a Collection. It is a separate hierarchy because it stores key to value pairs, not single elements.

What it is, from scratch. The Java Collections Framework is a set of interfaces (the contracts) and classes (the ready-made implementations) for holding groups of objects. You code against the interface, for example List, and pick an implementation, for example ArrayList, only when you create the object.

Why the split into two trees. A Collection holds single elements, so its core method is add(e). A Map holds pairs, so its core method is put(key, value). Those two shapes cannot share one interface without awkward methods, so the designers kept them apart. Everything under Collection can be looped with for-each because Collection extends Iterable. A Map cannot be looped directly: you loop one of its views.

InterfacePromiseTypical class
Listpositions, duplicates allowedArrayList
Setno duplicatesHashSet, TreeSet
Queue / Dequeelements leave in processing order (FIFO, LIFO, by priority)ArrayDeque, PriorityQueue
Mapkey to value, unique keysHashMap, TreeMap

Small example. Map<String,Integer> stock = new HashMap<>(); stock.put("pen", 5); then for (String k : stock.keySet()) works because keySet() is a Set, which is a Collection. stock.values() is a plain Collection (values can repeat, so it cannot be a Set). entrySet() gives Map.Entry objects, one per pair.

What an interviewer probes next: "why declare the interface type?" Because the choice of class is a performance decision you may want to change later (swap ArrayList for LinkedList, or HashMap for ConcurrentHashMap) without touching any caller.

A map still gives you collection views: keySet(), values() and entrySet(). These are live views, so removing from the view removes from the map. Collections (with an s) is only a utility class with static helpers such as sort and unmodifiableList. Collection is the interface. Mixing those two up is a classic slip.

Remember: List, Set and Queue are Collections. Map is its own tree. Collections is just helpers.

What is the difference between Iterable and Iterator? Basic

Iterable is something that can give me an iterator, and it is what the for-each loop needs. Iterator is the cursor itself, with hasNext(), next() and an optional remove(). Each call to iterator() returns a fresh cursor, so several loops can run over one collection at once.

The problem they solve. Different collections store data in very different ways (an array, linked nodes, a hash table, a tree). Code that wants to visit every element should not care which. The Iterator is the common way to say "give me the next element" regardless of the storage.

How the pieces fit.

  1. Iterable<T> has one method: Iterator<T> iterator(). A class that implements it can be the target of for-each.
  2. Iterator<T> is the cursor: hasNext() asks "is there another one?", next() returns it and moves forward, remove() deletes the element last returned.
  3. The compiler turns for (String s : list) { ... } into roughly for (Iterator<String> it = list.iterator(); it.hasNext(); ) { String s = it.next(); ... }.

Because each call to iterator() builds a new cursor with its own position, two nested loops over the same list (for example comparing every pair) do not disturb each other. Once an iterator is exhausted it cannot be rewound, you create another.

Example of your own Iterable.

class Range implements Iterable<Integer> {
    final int lo, hi;
    Range(int lo, int hi) { this.lo = lo; this.hi = hi; }
    public Iterator<Integer> iterator() {
        return new Iterator<>() {
            int next = lo;
            public boolean hasNext() { return next < hi; }
            public Integer next() { return next++; }
        };
    }
}
for (int i : new Range(0, 3)) System.out.println(i);   // 0 1 2

Pitfall. remove() is optional, so an iterator over an immutable collection throws UnsupportedOperationException. Calling remove() twice without a next() between them throws IllegalStateException. There is also ListIterator for lists, which can go backwards and can also add and set.

For-each over a collection is just sugar for an iterator loop, which is why changing the collection inside the loop trips the fail-fast check. Implementing Iterable<T> on my own class lets callers write for (T t : mine). An iterator is single use: when it is exhausted I ask for a new one.

Remember: Iterable produces, Iterator is the cursor. For-each is an Iterator in disguise.

Why can't I put an int in a List, and what does that cost? Basic

Generics only work with reference types, so List<int> is illegal and Java boxes each int into an Integer object. That is automatic, but every element is a separate heap object, so you pay in memory, cache misses and garbage collection.

Why generics exclude primitives. Generics in Java are implemented by type erasure: at run time a List<String> is just a List holding Object references, and the compiler inserts casts. A primitive such as int is not an object and has no reference, so it cannot be stored where an Object is expected. The language therefore wraps it in a box class (Integer, Long, Double, and so on). Converting in is boxing, converting out is unboxing, and the compiler does both silently (autoboxing).

What the cost looks like. An int[] of 1,000 numbers is one block of about 4 KB. A List<Integer> of 1,000 numbers is an array of 1,000 references plus up to 1,000 separate Integer objects of about 16 bytes each, so around 20 KB, spread across the heap. Visiting them means following a pointer per element, which defeats the CPU cache, and creating them loads the garbage collector. A loop such as for (int i...) list.add(i) allocates a new object for each value above 127.

The three traps, with examples.

Integer a = 127, b = 127;   a == b   // true, both come from the cache
Integer c = 1000, d = 1000; c == d   // false, two different objects
c.equals(d)                          // true, always compare with equals

Map<String,Integer> m = new HashMap<>();
int n = m.get("missing");            // NullPointerException: unboxing null

Long total = 0L;
for (int i = 0; i < 1_000_000; i++) total += i;   // boxes a new Long each pass: slow

The last one is a silent performance bug: a boxed accumulator creates a million temporary objects. Use a primitive long.

What to do. For small or ordinary lists, boxing does not matter, keep the readable code. For large numeric data in a hot path, use int[], or the primitive streams (IntStream), or a primitive-specialised collection library (fastutil, Eclipse Collections). Project Valhalla may change this in future JDKs, but today you cannot rely on it.

Two traps come with it. == on two Integer objects compares references, and it only seems to work for values from -128 to 127 because the JDK caches those. Always use equals. Also, unboxing a null from a map throws NullPointerException: int n = map.get("missing"); fails. For large numeric data use int[] or a primitive-specialised library, not List<Integer>.

Remember: a collection holds objects. Integer compare with equals, and watch unboxing of null.

2. Lists

How does ArrayList work internally and how does it grow? Basic

ArrayList wraps a plain Object[] plus a size counter. When the array is full, it allocates a bigger one, about 1.5 times the old length, and copies everything over. So get(i) is O(1), appending is amortised O(1), and inserting or removing in the middle is O(n) because elements shift.

What it is, from scratch. A Java array has a fixed length chosen at creation. You cannot add a sixth element to an array of five. ArrayList hides that limit: it owns an array, remembers how many slots are actually used (size), and when the array runs out of room it quietly creates a bigger one.

Why growth is multiplicative. If it grew by one slot each time, adding n items would copy 1 + 2 + ... + n elements, which is O(n squared). Growing by half (a geometric factor) means the total copying over n adds is about 3n, so each add is O(1) on average. This is called amortised O(1): most adds cost one write, an occasional add costs a big copy, and the average stays small.

Walk through an example. You add 11 elements to a new ArrayList.

  1. First add: the shared empty array is replaced by an array of 10 slots. Elements 1 to 10 are plain writes into slots 0 to 9, size goes 1 to 10.
  2. 11th add: the array is full, so a new array of length 10 + 5 = 15 is allocated and the 10 elements are copied (Arrays.copyOf). The old array becomes garbage. The element lands in slot 10, size = 11.
  3. The next growth happens when you add the 16th element, to capacity 22.

Middle operations. add(2, x) shifts every element from index 2 to the right by one (System.arraycopy), then writes. remove(2) shifts them left. That is O(n) but a fast native block copy, which is why ArrayList is competitive even for middle edits on moderate sizes.

Pitfalls.

  • Capacity versus size: new ArrayList<>(100) has capacity 100 but size() 0, so get(0) still throws IndexOutOfBoundsException.
  • Memory is not returned when you remove items. A list that once held 5 million elements keeps the 5-million-slot array until trimToSize() or until it is replaced. Removed slots are set to null so the objects themselves can be collected.
  • The 1.5 factor and the 10 default are implementation details of OpenJDK. Say "about 1.5 times" in an interview, and mention that the numbers are what HotSpot does today.

The no-arg constructor starts with an empty shared array and allocates capacity 10 on the first add. The growth formula is newCapacity = old + (old >> 1), so 10, 15, 22, 33 and so on. Each grow is one O(n) copy, but they get rarer, which is why the average append stays cheap. If I know the size, new ArrayList<>(n) or ensureCapacity(n) avoids repeated copying. Shrinking never happens automatically: call trimToSize() if memory matters. It is not thread safe.

Remember: array + size, grows by 1.5x, O(1) get, O(n) middle insert. Pre-size when you know N.

ArrayList versus LinkedList: which one and why? Basic

I almost always pick ArrayList. Textbooks say LinkedList wins at insert and delete, but it must first walk to the position (O(n)), and each node is a separate object with two extra pointers. In practice ArrayList wins on speed and memory, even for many middle inserts, because arrays are contiguous and CPU-cache friendly.

The textbook claim, and why it misleads. A linked list inserts and deletes in O(1) because it only rewires pointers, while an array must shift elements. That is true only once you are standing at the right node. To insert at index 500, LinkedList first has to walk 500 nodes, which is O(n) pointer chasing, with each node somewhere different in memory. ArrayList shifts the same elements but in one contiguous block copy that the CPU does at memory speed. So for an insert at a random index, ArrayList normally wins, even though both are "O(n)".

What a node costs. Each LinkedList element lives in a Node object with three references (item, prev, next) plus an object header: about 24 bytes before you count the element itself. An ArrayList slot is one 4-byte reference (with compressed pointers). More objects also means more garbage collection work and worse cache behaviour, because the nodes are scattered.

Worked comparison. Take a list of 100,000 integers and remove every other element using indexes. LinkedList.get(i) in a loop is O(n) each, giving O(n squared) in total. On ArrayList you would use removeIf, a single O(n) pass. The "linked list is good at removal" idea only holds when you already hold an iterator at the position and remove during one traversal.

When LinkedList is actually reasonable.

  • You need a List and a Deque in one object and the sizes are small, and you do many removals through an iterator while traversing. Even then ArrayDeque is usually better for pure queue or stack use.
  • You must avoid the occasional large array copy (a hard latency ceiling), and you have measured it.

Decision rule. Start with ArrayList. If it is a queue or stack, use ArrayDeque. Switch to LinkedList only with a benchmark that shows it winning. Interviewers like candidates who say "constant factors and cache locality matter as much as the Big-O".

LinkedList's real O(1) cases are only at the two ends, or through an iterator already at the position. For queue and stack work at the ends, ArrayDeque is faster and lighter than LinkedList too. A node costs about 24 bytes plus the element, against 4 bytes per slot in an array. Let me be fair: LinkedList does allow null, implements both List and Deque, and never does a big array copy, so it has no resize pause. But I would need a measured reason to choose it.

Remember: default to ArrayList, use ArrayDeque for queues and stacks, and LinkedList rarely.

Why shouldn't I use Vector, Stack or Hashtable? Basic

They are legacy classes from Java 1.0 where every method is synchronized. That costs locking on every call even when only one thread is used, and it still does not make compound actions safe, such as check-then-add. Modern code uses ArrayList, ArrayDeque and ConcurrentHashMap instead.

What these classes are. Vector (a growable array), Stack (a LIFO built on Vector) and Hashtable (a hash map) come from Java 1.0, before the Collections Framework existed. To make them usable from several threads, every public method was marked synchronized, so only one thread at a time can run any method on the same object.

Why that is the wrong kind of safety.

  1. It costs something every time. Even if only one thread ever touches the list, each call acquires and releases a lock. Modern JVMs reduce the cost, but it is not free and it blocks real concurrent readers.
  2. It does not make sequences safe. Thread safety of single calls does not protect two calls in a row. Consider: if (!vec.contains(x)) vec.add(x);. Two threads can both see "not contained" and both add. You still need your own lock around the pair.
  3. Iteration is still unsafe. Looping over a Vector while another thread adds to it throws ConcurrentModificationException, because the iterator is not covered by the per-method lock.

Stack's extra design flaw. Stack inherits from Vector, so a "stack" object also lets you call get(2), add(0, x) or remove(1), which violate stack discipline. That is inheritance used where composition was needed. Also its push/pop work at the end of the array, which is fine, but the class is still synchronised for no benefit.

Modern replacements.

OldUse insteadWhy
VectorArrayList (or CopyOnWriteArrayList if shared and read-heavy)no per-call lock
StackArrayDeque with push/pop/peekproper stack API, faster
HashtableHashMap (or ConcurrentHashMap if shared)finer locking, atomic methods

You will still meet these in old code and in interview trivia ("is Vector thread safe?" yes per call, but not for compound actions). The one-sentence answer: method-level synchronisation protects the data structure's internal state, not your logic.

Stack is also badly designed: it extends Vector, so it exposes get(i) and insertElementAt, which break the idea of a stack. Use Deque<Integer> stack = new ArrayDeque<>() with push and pop. For a thread-safe list I would use CopyOnWriteArrayList or guard a normal list myself. Collections.synchronizedList is better than Vector but still needs manual locking around iteration.

Remember: method-level synchronized does not give safe compound operations. Skip the legacy trio.

What is CopyOnWriteArrayList and when is it a good choice? Intermediate

It is a thread-safe list where every write (add, set, remove) copies the whole underlying array and then swaps in the new one. Readers never lock and never fail, because they see a stable snapshot. It is a good fit for read-heavy, write-rare data such as listener lists or small config lists, and a bad fit for anything written often.

The idea. Normally a thread-safe list needs locks so readers do not see half-finished changes. CopyOnWriteArrayList takes the opposite approach: the internal array is never modified after it is published. A write makes a brand-new array containing the change and then swaps the single reference (a volatile field) to it. A reader that grabbed the old reference keeps reading the old, consistent array.

Walk through an example. The list holds [A, B]. A reader starts an iterator, which captures the current array v1. A writer calls add(C):

  1. The writer takes the list's lock (writers are serialised among themselves).
  2. It makes a copy of v1 with one extra slot, writes C, producing v2 = [A, B, C].
  3. It publishes v2 as the current array and unlocks.

The reader still loops over v1 = [A, B] and never sees C or any error. A new iterator created afterwards sees [A, B, C].

Why this suits listener lists. A typical use is "the list of event listeners": it is read on every event (thousands of times a second) but changed only when a component registers or unregisters (a few times a minute). Readers pay nothing, and you can safely call a listener that itself unregisters, because that only changes the copy.

When it is wrong.

  • Frequent writes: each add costs O(n) time and O(n) garbage. 10,000 adds to a growing list copy about 50 million references in total.
  • Large lists: even rare writes copy a big array.
  • You need to see the latest data inside a loop. A snapshot may be stale by the time you act on it.

Siblings and pitfalls. CopyOnWriteArraySet is built on it (so its contains is O(n), not O(1)). Iterators do not support remove(). For "add if not already there" use addIfAbsent so the check and the add are one atomic step. If the interviewer asks for an alternative for write-heavy shared lists: a plain list guarded by a lock, a ConcurrentLinkedQueue, or a BlockingQueue, depending on the access pattern.

A write is O(n) in time and creates a full new array, so thousands of writes on a big list cause heavy garbage and lock contention among writers. An iterator walks the snapshot taken when it was created, so it never throws ConcurrentModificationException but also does not see later changes, and its remove() is unsupported. Single writes are atomic, but a check-then-add still needs addIfAbsent or a lock.

Remember: snapshot reads, copying writes. Great for many readers and rare writers, terrible otherwise.

What is surprising about Arrays.asList? Intermediate

It returns a fixed-size list that is a view over the original array, not an ArrayList. I can set elements, and that writes through to the array, but add and remove throw UnsupportedOperationException. If I need a normal modifiable list, I wrap it: new ArrayList<>(Arrays.asList(a)).

Why this method exists. Java has no list literal before Java 9. Arrays.asList(a, b, c) was the quick way to get a List from a few values, and also a way to use List methods (contains, sort, indexOf) on an existing object array without copying it. To make it cheap it does not copy: it returns a small adapter class (a private class named ArrayList inside Arrays, different from java.util.ArrayList) that reads and writes the original array directly.

What that implies, step by step.

  1. Size is fixed because the array's length is fixed. add and remove are not implemented and throw UnsupportedOperationException.
  2. set and sort work, and write straight into the array. Change the array and the list shows it, and the other way around.
  3. It is a view of an array that exists elsewhere, so there is no independent copy.

The primitive-array trap in detail. The signature is asList(T... a). With Integer[] the compiler treats it as the varargs array, so you get a list of three integers. With int[], T cannot be int, so the whole int[] is passed as a single element and you get a List<int[]> of size 1. list.contains(2) then silently returns false.

int[] p = {1, 2, 3};
Arrays.asList(p).size();              // 1  (a list containing the array)
Integer[] q = {1, 2, 3};
Arrays.asList(q).size();              // 3
List<Integer> ok = Arrays.stream(p).boxed().toList();   // 3, immutable (Java 16+)

Choosing the right factory.

NeedUse
Read-only fixed valuesList.of(...) (Java 9+), truly immutable, no nulls
Modifiable list from valuesnew ArrayList<>(List.of(...))
Write-through view of an arrayArrays.asList(array), on purpose

A related pitfall in production: a method returns Arrays.asList(...), tests pass a modifiable list, and the code fails later when a caller calls add.

A second trap is primitives. Arrays.asList(new int[]{1,2,3}) gives a List<int[]> with one element, because int[] is an object, not an array of Integer. Use Integer[], List.of(1,2,3) or IntStream.boxed(). Changing the array afterwards also changes the list, which can surprise people.

String[] a = {"x", "y"};
List<String> v = Arrays.asList(a);
v.set(0, "z");        // a[0] is now "z"
v.add("w");           // UnsupportedOperationException

Remember: asList is a fixed-size window on the array. Copy it into an ArrayList to modify.

What does List.of give me, and how does it differ from Collections.unmodifiableList? Intermediate

List.of (Java 9) builds a truly immutable list: nothing can change it, it rejects null elements, and nobody holds another reference that can change it. Collections.unmodifiableList(x) is only a read-only view over x, so if someone changes x, the view changes too.

Three different things people call "read-only".

Who can change itNullsCost
new ArrayList<>()anyone with the referenceallowednormal
Collections.unmodifiableList(x)nobody through this reference, but the owner of x still canas in xtiny wrapper, no copy
List.of(...), List.copyOf(x)nobody at allrejectedcompact array, copy for copyOf

Why the distinction matters. Imagine class Order keeps a List<Item> items and its getter returns Collections.unmodifiableList(items). The caller cannot call add on the result, so the class looks protected. But Order itself continues to items.add(...), and a caller who stored the earlier view now sees the list change under its feet, possibly in the middle of its own loop. With List.copyOf(items) the caller holds a snapshot that nobody changes, which is safe to cache or hand to another thread.

Design reasons for the stricter rules of List.of. The null ban lets the implementation use null internally and makes Optional-style reasoning simpler. The unspecified iteration order of Set.of and Map.of (it is randomised per JVM run via a salt) stops code from depending on an order that was never promised. Duplicate elements in Set.of and duplicate keys in Map.of throw IllegalArgumentException, because a literal with a duplicate is almost certainly a typo.

Caveats. They are shallowly immutable: List.of(new StringBuilder("a")) still lets you append to that builder. For more than 10 pairs, Map.of has no overload, use Map.ofEntries. List.copyOf(x) returns x itself if it is already an immutable list, so it is cheap to call defensively. Stream.toList() (Java 16) returns an unmodifiable list too, but one that allows nulls.

Use List.copyOf(x) (Java 10) when I want an immutable snapshot of an existing list. Set.of and Map.of work the same way, throw on duplicate elements or keys, and their iteration order is unspecified and can differ between runs, so never depend on it. Even contains(null) on List.of throws NPE. Immutable collections are also the safest thing to share between threads. Note that they are shallowly immutable: the elements themselves can still be mutable.

List<String> src = new ArrayList<>(List.of("a"));
List<String> view = Collections.unmodifiableList(src);
List<String> copy = List.copyOf(src);
src.add("b");     // view now has [a, b]; copy still has [a]

Remember: unmodifiable is a read-only window, immutable is a fixed copy. Returning internal lists? Use List.copyOf.

What happens with list.remove(1) on a List<Integer>? Intermediate

remove(1) calls remove(int index) and deletes the element at position 1, not the value 1. To remove the value I write list.remove(Integer.valueOf(1)). Java picks the exact primitive overload first, and boxing only happens if no exact match exists.

Why there are two methods named remove. List declares remove(int index) because lists have positions, and it inherits remove(Object o) from Collection, which removes the first element equal to o. Both exist legitimately. The trouble starts with List<Integer>, where an element and an index are both "an integer".

How the compiler chooses. Overload resolution happens in phases. First it looks for a method that applies without any boxing or unboxing. Given an int argument, remove(int) matches exactly in phase one, so it is chosen and remove(Object) is never considered. Only if there were no exact match would it box the int and try remove(Object). To force the object version you must pass an Integer, via Integer.valueOf(1) or a cast (Integer) 1.

List<Integer> l = new ArrayList<>(List.of(5, 1, 7, 1));
l.remove(1);                    // index 1 removed  -> [5, 7, 1]
l.remove(Integer.valueOf(1));   // first value 1    -> [5, 7]
l.remove(10);                   // IndexOutOfBoundsException: index 10, size 2

The last line shows the usual symptom of the mix-up: not wrong data but an unexpected IndexOutOfBoundsException when the "value" you meant is larger than the list.

Same trap in Sets and in loops. Set has only remove(Object), so there is no ambiguity, but boxing can still hurt: in Set<Short> s, s.remove(i - 1) computes an int, boxes it to Integer, and an Integer is never equal to a Short, so nothing is removed and no error is raised. Also removing inside a counting loop by index shifts the elements left, so the loop skips the next one, unless you step back (i--) or iterate backwards.

Rule of thumb. For lists of numbers, name your intent: use removeIf(x -> x == 1) for "by value" and remove(idx) only with a variable that is clearly an index.

Both overloads exist on List, which is the root of the confusion. The same overload trap shows up in Set, where remove takes an object, so a Set<Short> with remove(i - 1) silently removes nothing because the argument becomes an Integer. Either way, remove-by-value is O(n) in an ArrayList, plus the shift.

List<Integer> l = new ArrayList<>(List.of(10, 1, 5));
l.remove(1);                    // removes index 1 (the value 1): [10, 5]
l.remove(Integer.valueOf(10));  // removes value 10: [5]

Remember: an int argument means index, an Integer object means value.

3. Sets

How does HashSet work, and how does it decide something is a duplicate? Basic

A HashSet is a HashMap in disguise: each element is stored as a key, and every value is the same dummy object. add(e) is really map.put(e, PRESENT), and it returns false if the key was already there. Duplicates are decided by hashCode first, then equals.

What it is, from scratch. A Set is a collection that refuses duplicates. The cheapest way to test "have I seen this?" quickly is a hash table, so HashSet reuses HashMap rather than inventing a new structure. Internally there is one field, private transient HashMap<E,Object> map, and one shared dummy value PRESENT. Your elements are the keys. That is the entire trick, and it means everything you learn about HashMap (buckets, load factor, resize, treeify) applies to HashSet unchanged.

Step by step for set.add("pen").

  1. Call "pen".hashCode(), spread the bits, take the bucket index.
  2. Look in that bucket. If a node has the same hash and equals says true, the element is already present: map.put returns the old dummy value (non-null), so add returns false and nothing changes.
  3. Otherwise a new node is added and put returns null, so add returns true.

That boolean is useful: if (!seen.add(x)) is the standard one-line duplicate check.

The two-step test, and why both parts exist. hashCode narrows the search to one bucket (fast, but different objects can share a hash). equals then confirms identity of value. If a class overrides equals but forgets hashCode, two equal objects hash to different buckets, so the set never compares them and holds both. If a class overrides neither, equality is by reference, so two new Point(1,2) are distinct.

Set<String> s = new HashSet<>();
s.add("a");    // true
s.add("a");    // false, duplicate
s.add(null);   // true: one null is allowed

Costs and variants. add, contains, remove are O(1) on average. Iteration is O(capacity + size), so a big set that has shrunk is slow to iterate. Iteration order is arbitrary and may change after resize. LinkedHashSet remembers insertion order, TreeSet sorted order. Never mutate an element's hash-relevant fields while it sits in the set, or contains will not find it.

So add, contains and remove are O(1) on average, with no order guaranteed. The elements' equals and hashCode must be consistent, otherwise two "equal" objects land in different buckets and both stay. LinkedHashSet adds a linked list through the entries so iteration follows insertion order, at a small memory cost. TreeSet is the sorted variant, covered next.

Remember: HashSet = HashMap keys only. Duplicate means same hash, then equals true.

How does TreeSet decide duplicates, and what goes wrong with a bad comparator? Intermediate

TreeSet (like TreeMap) never calls equals. Two elements are "the same" when the comparator or compareTo returns 0. So if my comparator only compares one field, other elements with that same field value are silently dropped.

Why a tree set does not use equals. A TreeSet is a sorted structure: to find where an element belongs it asks "is the new one smaller, larger or the same as this node?" using compare(a, b) (or a.compareTo(b)). A result of 0 is the only signal of "same". It never calls equals or hashCode. Therefore the comparator is the definition of duplicates.

Worked example of the data loss. Three employees: Asha 50000, Bela 50000, Chen 60000. A set sorted only by salary:

  1. Add Asha: tree is [Asha].
  2. Add Bela: compare(Bela, Asha) = 0, so the set treats Bela as already present and silently ignores it. add returns false.
  3. Add Chen: different salary, added.

Result: 2 elements, and Bela is gone with no exception. Adding .thenComparing(Emp::id) makes ties impossible, so all three stay, in salary order and then id order.

The contract to keep. A comparator is "consistent with equals" when compare(a,b)==0 exactly when a.equals(b). If it is not, a TreeSet and a HashSet holding the same objects disagree about size and membership. The JDK documents that the behaviour of such a set is well defined but violates the general Set contract, and some classes do it on purpose: BigDecimal("1.0") and BigDecimal("1.00") are not equals but compare as 0, so they collapse in a TreeSet and stay separate in a HashSet.

Useful features once you have it right.

  • first(), last(), pollFirst().
  • floor(x) (greatest element at most x), ceiling(x) (smallest at least x), lower, higher.
  • headSet, tailSet, subSet: live range views.
  • descendingSet() for reverse order.

Pitfalls. A comparator that throws or is inconsistent over time corrupts the tree. Comparing floating-point fields with subtraction or == is fragile, use Double.compare. If you only want "sorted output with duplicates allowed", use a list and sort instead.

Example: a set of employees sorted by salary will keep only one employee per salary. The fix is a tie-breaker: compare salary, then id. The comparator should be consistent with equals, otherwise the set breaks the general Set contract and behaves differently from a HashSet holding the same data. TreeSet is a red-black tree: O(log n) operations, sorted iteration, and range queries like first, floor, ceiling, headSet and subSet. It does not allow null with natural ordering.

Set<Emp> s = new TreeSet<>(Comparator.comparingInt(Emp::salary)
                                  .thenComparing(Emp::id));

Remember: sorted sets use compare()==0 as "same". Always add a tie-breaker.

HashSet, LinkedHashSet or TreeSet: which do I pick? Basic

HashSet by default, because it is the fastest (O(1) average). I use LinkedHashSet when I need to iterate in insertion order, for example to remove duplicates while keeping order. I use TreeSet only when I need sorted iteration or range queries, accepting O(log n).

Why there are three. They all enforce uniqueness, but they store data differently, so each wins on a different axis:

  • HashSet is a hash table. Fastest, but it forgets order.
  • LinkedHashSet is a hash table plus a linked list through the entries. Same speed class, plus a predictable iteration order (the order you inserted).
  • TreeSet is a red-black tree. Slower (O(log n)) but always sorted, and it answers "what is next above 40?" questions.

Examples of choosing.

  1. Remove duplicates from a list but keep the first-seen order. new ArrayList<>(new LinkedHashSet<>(list)). A plain HashSet would scramble the order, a TreeSet would sort it.
  2. Check whether a user id is in a blocklist of a million ids. HashSet. Order is irrelevant, and O(1) lookup is the point.
  3. Keep the set of active ports and find the next free port above 8080. TreeSet with ceiling(8080) style queries (or higher).
  4. A set of enum constants such as permissions. EnumSet, which stores a bit per constant in a long, so contains is a bit test and union is one OR.

Set operations in code. Remember they change the receiver, so copy first when you need the original.

Set<Integer> a = new HashSet<>(List.of(1, 2, 3));
Set<Integer> b = Set.of(2, 3, 4);
Set<Integer> both = new HashSet<>(a); both.retainAll(b);   // intersection: [2, 3]
Set<Integer> all  = new HashSet<>(a); all.addAll(b);      // union: [1, 2, 3, 4]
Set<Integer> only = new HashSet<>(a); only.removeAll(b);   // difference: [1]

What to watch. HashSet and LinkedHashSet depend on a correct hashCode/equals. TreeSet depends on a comparator with a tie-breaker, and rejects null with natural ordering. For thread safety, wrap with Collections.synchronizedSet, or use ConcurrentHashMap.newKeySet() (a concurrent hash set) or ConcurrentSkipListSet (a concurrent sorted set).

For set maths use bulk operations on a copy: retainAll is intersection, addAll union, removeAll difference. They mutate the receiver, so copy first. Sets of enum values are best as EnumSet, a bit-vector that is very fast and compact.

Remember: hash for speed, linked for insertion order, tree for sorted and ranges.

4. HashMap in depth

How does HashMap work internally? Basic

HashMap is an array of buckets. For a key I compute hashCode(), spread its bits, and take hash & (length - 1) to pick a bucket. Entries in the same bucket form a linked list, and since Java 8 a long list turns into a balanced tree. get finds the bucket, then uses equals to find the exact key. Average cost is O(1).

The problem a hash table solves. To find a key in a list you compare against elements one by one: O(n). If instead you could compute, from the key alone, the exact slot where it must live, you would jump straight there: O(1). A hash table does exactly that. The function that turns a key into a number is hashCode(), and the slot is that number reduced to the array size.

Following one key through, with numbers. Suppose the table has 16 buckets and you call put("Asha", 1).

  1. "Asha".hashCode() gives a 32-bit int, say 2,000,000,000 (the real value does not matter).
  2. HashMap spreads it (h ^ (h >>> 16)) so high bits also influence the low ones.
  3. Index = spread & 15, which keeps only the low 4 bits, so a number from 0 to 15. Say 1.
  4. Bucket 1 is empty, so a node (hash, key "Asha", value 1, next = null) is stored there.

Later put("Kiran", 9) may also land in bucket 1. That is a collision: two different keys, same bucket. It is normal and expected, since there are far more possible keys than buckets. The new node is chained after the first one. get("Kiran") goes to bucket 1, finds the "Asha" node, sees that the key is different (hash or equals fails), moves to the next node and finds "Kiran". So equals is what finally identifies the key. The hash only chooses where to look.

Why resizing is part of the design. If the table stayed at 16 buckets while you stored 10,000 entries, each chain would hold about 600 nodes and lookups would be slow. So when the count exceeds capacity * 0.75 the table doubles (16 to 32 to 64, and so on) and chains shorten again. This keeps the average chain under about one node.

What this tells you to do in practice.

  • Give your key class a good hashCode and a matching equals. A bad hash gives long chains.
  • Make keys immutable. A key whose hash changes is lost in the wrong bucket.
  • Do not depend on iteration order: it is bucket order, which changes after a resize.
  • Pre-size when you know the count, to avoid repeated O(n) resizes.

The deeper questions (hash spreading, power of two, put and get flow, treeify) are the next few entries. They all hang off this one picture: array of buckets, chain or tree inside each bucket, equals to confirm.

Each entry holds the hash, key, value and a next pointer. Two different keys can share a bucket (a collision), which is why equals is needed after the hash matches. The table starts at 16 buckets, and when the entry count passes 75 percent of the capacity (the load factor) it doubles and entries are redistributed. The array is created lazily on the first put. HashMap is not thread safe.

Remember: index = hash and (n-1), chain or tree in the bucket, equals picks the key, doubles at 75 percent full.

Why does HashMap mix the hash bits before using them? Senior

Because the bucket index only uses the low bits of the hash (the mask n - 1). Many real hash codes differ only in their high bits, so they would all collide in a small table. HashMap fixes that with h ^ (h >>> 16), which folds the high 16 bits into the low 16 bits.

Setting the scene. The table index is hash & (n - 1). For n = 16 that is hash & 0b1111: only the lowest 4 bits of the 32-bit hash are used. The upper 28 bits are thrown away. That is fine only if the lowest bits already vary a lot between keys. Many hash functions do not guarantee that.

A concrete bad case. Suppose your keys are Float values like 1.0, 2.0, 3.0, 4.0. A float's hash is its raw bits, and for these round numbers the low 20 or so bits are all zero, and only the high bits differ. Mask to 4 bits and every key gets index 0. All entries collide in one bucket, and a hash table degrades to a list. The same happens for hash codes that are multiples of 1024, for many Long ids that step by powers of two, and for memory-address-like hashes.

The fix, in one line. hash = h ^ (h >>> 16). Shift the top 16 bits down to the bottom 16 and XOR them with the original. After this, each of the low 16 bits is a mix of two original bits (one low, one high). Now the keys above differ in their low bits too, and spread across buckets. It only handles the top half, and tables rarely exceed 65,536 buckets, so 16 bits of mixing is enough for typical sizes.

Why not a stronger mixer. Java 7 used several shifts and XORs. Java 8 cut it down to one because (a) the cost is paid on every get and put, so it should be near zero, and (b) if a bucket still gets crowded, Java 8's treeified buckets limit the damage to O(log n).

What this means for you. You do not call this yourself. But it explains why a poor hashCode still hurts (spreading cannot invent variation that is not there), and why String and Integer keys behave well. An interviewer may ask "why >>> and not >>": >>> is the unsigned shift, filling with zeros, so negative hashes do not smear the sign bit across the result.

It is one XOR and one shift, so it is almost free, and it makes the low bits depend on all the bits. With a table of 16 buckets only 4 bits of the hash choose the bucket. Without spreading, keys like Float values or large multiples of 1024 could land in the same few buckets. Java 7 used a heavier multi-step scramble, Java 8 simplified it because treeified buckets already limit the damage from bad distribution.

Remember: small tables only see the low bits, so Java 8 XORs the high half into the low half.

Why is the HashMap capacity always a power of two? Senior

Two reasons. First, the bucket index becomes a cheap bit mask, hash & (n - 1), instead of a slow modulo, and the mask uses every low bit evenly. Second, when the table doubles, each entry either stays at its index or moves exactly oldCapacity slots forward, decided by one bit, so a resize needs no re-hash.

Reason 1: the mask trick, shown in binary. Choosing a bucket means turning any int into a number from 0 to n-1. The usual way is hash % n, a division, which is slow and can give negative results for negative hashes. If n is a power of two, there is an equivalent that is a single AND instruction.

n = 16    n - 1 = 15 = 0000 1111
hash = 0b...1011 0110 (any int)
hash & 15 = 0000 0110 = 6          (same as hash mod 16, never negative)

With n = 16 the mask 1111 passes the four low bits and every value 0 to 15 is reachable. With a non-power-of-two such as n = 10, n-1 = 9 = 1001. The AND can only produce bit patterns made from those two bits (0, 1, 8, 9), so buckets 2 to 7 are never used and the table wastes most of its space and crowds the rest.

Reason 2: cheap resizing, shown with an example. Grow from 16 to 32. The index uses 4 bits before and 5 bits after. The extra bit is bit 4 (value 16). A node at old index 6 goes to new index 6 if bit 4 of its hash is 0, or to 6 + 16 = 22 if that bit is 1. So the whole move is: test one bit of the stored hash, no recomputation, no division. If the size were not a power of two there would be no such neat rule and every entry would need a full re-index.

How the constructor enforces it. You can pass any number to new HashMap<>(100). The internal method tableSizeFor rounds it up to the next power of two (128). So the real capacity is never what you asked for, which is why the sizing formula in the sizing question uses N / 0.75 and relies on this rounding.

Trade-off to mention. Doubling means the table can be up to twice as big as needed, and memory is wasted on empty buckets. That is accepted in exchange for speed. Also note this is a HashMap-specific design: some other hash tables (for example open-addressing ones) use prime sizes instead.

If n is a power of two, n - 1 is all ones in binary (15 is 1111), so the AND keeps the low bits intact. With a non-power-of-two such as 10, n - 1 is 1001 and some buckets could never be hit. If I pass a capacity like 100 to the constructor, HashMap rounds it up to 128 (tableSizeFor). That rounding is why sizing a map with "number of entries" is slightly wrong, covered in the sizing question.

Remember: power of two gives a fast mask and a one-bit split on resize.

Walk me through what happens on map.put(key, value). Intermediate

I compute and spread the hash, create the table if it is the first put, and find the bucket. If it is empty I drop a new node in. If not, I walk the chain or tree: if a node has the same hash and an equals key I replace its value, otherwise I append a new node. After inserting, I check whether the size passed the threshold and resize if so.

Same flow, with a numeric trace. Take an empty HashMap (no table yet) and run three puts.

  1. put("Asha", 1): table is null, so resize() allocates 16 buckets and sets threshold to 12. Say the index is 1. Bucket empty, so store the node. size = 1. Returns null (no previous value).
  2. put("Kiran", 9), same index 1: the first node has a different key. The next pointer is null, so the new node is appended after it. Chain length is 2. size = 2.
  3. put("Asha", 5): the first node in bucket 1 has the same hash and equals true. HashMap replaces the value, size stays 2, and put returns 1, the old value.

The decisions inside, in order. (a) Is the table allocated? (b) Is the target bucket empty? (c) Does the first node match? (d) If the bucket is a tree, insert into the tree. (e) Otherwise walk the chain: match, or append at the tail, counting the length. (f) If the chain length reached the treeify limit, call treeifyBin. (g) After a new node, increment size and compare with the threshold.

What treeifyBin does. It does not blindly build a tree. If the table has fewer than 64 buckets it calls resize() instead, on the reasoning that a small table with a long chain is better fixed by spreading entries out than by building a tree. Only when the table is at least 64 does it convert the chain to red-black tree nodes.

Why hash is compared before equals. equals can be expensive (a long string, a composite key). Comparing the cached int hash first rejects almost every non-matching node cheaply. Only when the hashes are equal does it call equals. This is also why, if two keys are equal but have different hash codes, they never meet.

Pitfalls. A put that replaces an existing key does not touch modCount in a structural way (no resize, no size change). put is not atomic across threads, which is where lost updates come from. Using putIfAbsent or computeIfAbsent avoids double lookups when you only want to insert once.

Details a senior should add: the old value is returned from put (or null). In a chain, the new node goes to the tail in Java 8 (head in Java 7). When the chain reaches 8 nodes and the table has at least 64 buckets, it is converted to a red-black tree. Replacing the value of an existing key does not change the size, so it never triggers a resize. The hash comparison runs before equals, so equals is only called on likely matches.

Remember: hash, bucket, same key then replace, else append, then maybe treeify, then maybe resize.

And map.get(key)? Why is it O(1) and when is it not? Intermediate

I compute the hash, go to the bucket, and compare the first node by hash and equals. If it is not a match, I walk the chain, or search the tree if the bucket is treeified. With a decent hash function, buckets hold one or two nodes, so it is O(1) on average.

The steps, with an example. Map holds "Asha"=1 and "Kiran"=9 chained in bucket 1. get("Kiran"):

  1. Compute hash("Kiran") and the index, 1.
  2. Read table[1], the "Asha" node. Compare its stored hash with the key's hash. If hashes differ, skip it without calling equals. Here it is not our key, so move to next.
  3. Next node is "Kiran": hash equal and equals true, return its value 9.
  4. If the chain ends (next is null) without a match, return null.

Why O(1) on average is honest. With the load factor held at 0.75, the average chain length is below one node. Most gets inspect one or two nodes. The key assumption is that hashCode spreads keys well. The JDK source describes chain lengths as roughly Poisson distributed with mean about 0.5, so long chains are rare.

When it is not O(1).

  • Bad hashCode (constant, or only a few distinct values): everything lands in a few buckets. Java 7 then costs O(n). Java 8 builds trees and costs O(log n), but only if the keys are Comparable and the table has at least 64 buckets. Otherwise the tree has to search more widely.
  • Expensive hashCode or equals: a key class with a slow hash makes every operation slow, even with short chains. Strings cache their hash, so repeat lookups of the same string object are cheap. A List key recomputes its hash each time, O(length).
  • Hash-flooding attacks: an attacker sends many keys that share a hash (older JDK web servers were vulnerable through request parameter maps). Trees make the effect much smaller in Java 8 and later.

A separate cost: iteration. get is O(1), but looping the map visits all buckets, so it costs O(capacity + size). A map that once held a million entries and has since been cleared down to ten still has a huge table. If iteration is the main use, consider LinkedHashMap, whose iteration is O(size).

The worst case is every key in one bucket. That is O(n) in Java 7 and O(log n) in Java 8 because the bucket becomes a tree (when keys are Comparable; otherwise the tree is slower to search). A bad hashCode, such as returning a constant, destroys the O(1). Iterating a HashMap costs O(capacity + size), so a huge, mostly empty table is slow to iterate.

Remember: O(1) needs a well-spread hashCode. Worst case is O(log n) in Java 8, O(n) in Java 7.

What is the load factor, and why 0.75? Intermediate

The load factor is how full the table may get before it doubles. At the default 0.75 and capacity 16, the threshold is 12, so the 13th entry triggers the resize. 0.75 is a compromise: higher saves memory but increases collisions, lower means fewer collisions but a bigger, emptier table.

What it controls. The load factor is the ratio of entries to buckets at which HashMap decides the table is too crowded. The map stores a threshold = capacity x load factor. The default table of 16 with 0.75 has threshold 12. The put that makes the size 13 triggers a resize to 32 buckets, with new threshold 24, and so on.

The trade-off, in numbers. Think of throwing n balls into m bins at random.

Load factorAverage entries per bucketEffect
0.5up to 0.5very few collisions, but the table is at least twice the entry count (more memory, more resizes)
0.75up to 0.75the JDK's chosen balance: about 1 in 3 buckets empty, chains stay short
1.0 or more1 or morecompact, but collisions rise sharply, so get and put slow down

The JDK source notes that with 0.75 the expected chain length follows a Poisson distribution with mean around 0.5, so long chains are very rare. 0.75 is "a good tradeoff between time and space" in their words, not a magic mathematical constant.

Both constructor parameters. new HashMap<>(initialCapacity, loadFactor). A lower initial capacity does not cap the map: it simply grows. The initial capacity only decides how soon the first resizes happen.

When would you change it?

  • Lookup-heavy, memory is plentiful: a lower factor, for example 0.5, to keep chains short. Rare in practice.
  • Huge map, memory-tight, mostly sequential access: a higher factor, for example 1.0, accepting more collisions. Also rare.
  • Most common real change: not the factor at all, but the initial capacity, when you know the entry count in advance (see the sizing question).

Pitfall. People quote "resize when 75 percent full" and forget it is strictly greater than: with threshold 12, the 12th entry fits, the 13th triggers the resize. Also HashSet shares the same load factor because it is a HashMap inside.

The cost of a resize is O(n), so I want few of them. A lower factor such as 0.5 speeds up lookups at the price of more memory. A higher one like 1.0 packs tightly and slows lookups. In practice I almost never change 0.75. What I do change is the initial capacity when I know the entry count, to avoid repeated resizes.

Remember: threshold = capacity x 0.75. Resize when size goes above it, 12 for the default 16.

How does a HashMap resize, and why is it expensive? Senior

It allocates a table twice as large and moves every entry across, so it is O(n) and can cause a latency spike on the put that triggers it. In Java 8 the move is cheap per entry: each node either stays at index j or goes to j + oldCapacity, chosen by one bit of its hash, and the relative order inside a chain is preserved.

Why a resize is needed at all. The bucket index depends on the table length (hash & (n-1)). When you make the table larger, the index of most entries changes, so they cannot stay where they are. HashMap allocates a new array of double size and moves every node. Chains also get shorter, which is the whole purpose.

The one-bit rule, with a worked example. Old capacity 16 (mask 01111), new capacity 32 (mask 11111). Take three nodes that all sit in bucket 5 of the old table, with these spread hashes (low 5 bits shown):

Hash low 5 bitshash & 16New index
0010105 (stays, the "low" list)
101011621 = 5 + 16 (moves, the "high" list)
00101 (another key)05

The code builds two lists per old bucket while walking it once, keeping the original order within each list, and then stores them in slots j and j + oldCap. No hash is recomputed (the hash is stored in the node), and no node is allocated again: the existing nodes are relinked.

Why it hurts.

  • O(n) work happens inside one put, so p99 latency of that single call spikes. For a map with tens of millions of entries this can be hundreds of milliseconds.
  • The new table must be allocated while the old one still exists: a brief 1.5x memory peak. A very large array may land in a big region of the heap.
  • If another thread is reading or writing, an unsynchronised HashMap can lose entries or return wrong answers during the move.

What to do about it. Pre-size to the known entry count. For a cache that should never be resized in the hot path, create it with a generous capacity at start-up. For maps shared by threads use ConcurrentHashMap, which also resizes incrementally with the help of the threads that touch it.

Tree buckets on resize. When a treeified bucket is split into low and high halves, each half that ends up with 6 or fewer nodes is converted back to a plain list (untreeify). A half bigger than 6 stays (or becomes) a tree.

The bit test is (hash & oldCap) == 0: zero means the node stays in the "low" bucket, non-zero goes to the "high" bucket. No hash is recomputed. Because the old bucket is split into two, treeified buckets can shrink back to a list (untreeify at 6 or fewer nodes). Resizing is also why a map should be pre-sized in a hot path, and why one big map in a latency-sensitive service can cause a brief pause. In a multi-threaded misuse, concurrent resizes cause lost entries (and in Java 7, the infinite loop).

Remember: doubling splits each bucket in two by one hash bit. O(n) total, so pre-size.

When does a bucket become a tree? What are 8, 6 and 64? Senior

Since Java 8, when a single bucket's chain grows to 8 nodes and another is added, and the table has at least 64 buckets, HashMap converts that chain into a red-black tree. This turns the worst-case lookup from O(n) into O(log n). If the table is smaller than 64, it resizes instead. When a tree shrinks to 6 nodes or fewer, it goes back to a list.

Why trees were added. Before Java 8 a bucket was always a linked list, so a bad or malicious hash (many keys with the same hash code) turned lookups into O(n) scans. An attacker could send a few thousand colliding keys to a web service and burn the CPU. A balanced tree bounds the worst case to O(log n). But a tree node is about twice as big as a list node, and trees are only worth it when chains are really long, so the JDK chose conservative thresholds.

The rule, stated precisely. Treeifying needs BOTH conditions:

  1. a single bucket's chain has reached 8 nodes and a 9th node is being added (TREEIFY_THRESHOLD = 8), and
  2. the table has at least 64 buckets (MIN_TREEIFY_CAPACITY = 64).

If the chain is long but the table is smaller than 64 (for example 16 or 32), HashMap does not build a tree. It resizes the table instead. Reasoning: with so few buckets a long chain probably means the table is just too small, and doubling it will spread the nodes out more cheaply than a tree would.

The way back. When a tree bucket is split during a resize and one half has 6 or fewer nodes, it becomes a plain list again (UNTREEIFY_THRESHOLD = 6). Removals can also shrink a tree enough for it to be converted back. The gap between 8 and 6 stops a bucket from flipping between list and tree if its size hovers around one number.

How a tree bucket is searched. Nodes are ordered by hash value first. For equal hashes the code compares keys with compareTo if the key class implements Comparable of its own type. If keys are not comparable, it falls back to an internal tie-break based on class name and identity hash for inserting, and a lookup may have to search both subtrees. So treeification fully pays off only with Comparable keys. Note that TreeNode also keeps the next pointers, so the bucket can still be iterated like a list.

Why 8. The JDK comment gives a Poisson estimate: with a good hash and the default load factor, the chance of a bucket reaching 8 entries is about 0.00000006 (roughly six in a hundred million). So in normal use trees almost never appear. When they do, something is wrong with the hash function or the data. If you see many TreeNode objects in a heap dump, suspect a poor hashCode.

Why the gap between 8 and 6: so that a bucket does not flip back and forth between list and tree on repeated add and remove. Why 8: with a good hash, chains this long are astronomically rare (Poisson distribution, about 6 in a hundred million for a bucket at load factor 0.75), so trees mostly appear only under bad hashes or attacks. Tree nodes use about twice the memory of list nodes. Search inside a tree compares by hash first, then by compareTo if keys are Comparable, otherwise it may need to scan, so Comparable keys give the real benefit.

Remember: 8 to treeify (table at least 64), 6 to untreeify, so worst case is O(log n).

How is HashMap in Java 8 different from Java 7? Senior

Three changes. Java 8 inserts at the tail of a chain (Java 7 inserted at the head), it turns long chains into red-black trees (Java 7 never did, so worst case was O(n)), and it resizes without reversing chain order. The head insertion plus reversing resize was what allowed the infamous infinite loop under concurrent use.

Why the redesign. Java 7's HashMap had three weak spots: worst-case O(n) lookups when many keys collide (attackable), a resize that reversed chains (which enabled the infinite-loop bug), and a heavier hash-mixing function. Java 8 addressed each.

Change by change, with the reason.

  1. Tail insertion instead of head insertion. A new node is appended to the end of its chain. In Java 7 it was placed at the front, because that is O(1) without walking the chain. Appending requires walking the chain anyway (to check for an existing key), so the cost is the same, and the order of nodes becomes stable.
  2. Order-preserving resize. Instead of re-inserting each node at the head of its new chain (which reverses the chain), Java 8 splits a chain into a low list and a high list and keeps their relative order. With order preserved, two threads resizing at once can no longer create a circular link by reversing in opposite directions.
  3. Red-black tree bins. Chains of 8 or more (in a table of at least 64) become trees, so worst-case lookup is O(log n) instead of O(n). It is a defence against both bad hash functions and deliberate hash flooding.
  4. Simpler hash spreading. One XOR and shift instead of a multi-step mix.

Same in both versions. Default capacity 16, load factor 0.75, power-of-two table, not thread safe, one null key allowed, fail-fast iterators. Java 8 also added the functional methods (computeIfAbsent, merge, forEach), and later releases added newHashMap (19).

The most common wrong answer. "Java 8 HashMap is thread safe now." It is not. Two threads can still overwrite each other's put in the same bucket, a resize can drop nodes, and a reader can see a half-built table. What Java 8 removed is the endless loop, not the data races.

How to answer in an interview. Give the table above, then say: "The visible effect is that worst-case get is O(log n) and the resize loop bug is gone, but sharing a HashMap across threads is still a bug, use ConcurrentHashMap."

Java 8 also spreads the hash more cheaply (one XOR and shift), and added lambdas-friendly methods such as computeIfAbsent, merge, getOrDefault. Be careful: Java 8 HashMap is still not thread safe. It can lose updates or throw odd errors, only the endless loop is gone. Java 7 also had a hash seed option to resist hash flooding, which trees replaced as the main defence.

How did HashMap cause an infinite loop in Java 7? Senior

If two threads resized the same HashMap at once, the Java 7 transfer code, which inserts at the head and so reverses each chain, could make two nodes point to each other. A later get on that bucket loops forever, burning 100 percent of a CPU core. The root cause is sharing an unsynchronised HashMap between threads.

Background you need. In Java 7, resizing walked each old chain and inserted every node at the head of its new chain. Walking A then B and head-inserting each produces B then A in the new bucket: the chain order flips. The code of the loop is, in outline: read next = e.next, set e.next = newTable[i], set newTable[i] = e, then continue with e = next. Single-threaded this is correct. The danger appears when two threads run it on the same chain.

Timeline of the failure, step by step. The chain in bucket 1 is A -> B (A.next = B, B.next = null). Both buckets of the new table happen to map A and B to the same new bucket.

  1. Thread 1 starts its transfer: it has e = A and next = B, then the scheduler pauses it.
  2. Thread 2 runs the whole resize. It head-inserts A (new chain: A) then B (new chain: B -> A). Now B.next = A and A.next = null in the shared nodes.
  3. Thread 1 resumes with its stale local variables e = A, next = B, into its own empty new table. It places A (A.next = null), then moves on to B. But B.next now points to A, because Thread 2 left it that way. So Thread 1 places B in front of A (B.next = A), then follows B.next back to A and processes A a second time, putting it in front of B, which sets A.next = B.
  4. Now A.next = B and B.next = A, a cycle.

Any later get or put that reaches this bucket and does not find its key follows next forever. The thread spins at 100 percent of one core, which is the classic symptom in the logs and thread dumps. Several such threads can saturate all cores.

Why Java 8 is not affected in the same way. It splits the chain preserving order, with no reversal, so there is no way for two threads to produce opposing pointers. It can still lose data and show inconsistent contents.

How to recognise it in production. CPU pinned on one or more cores, requests hang, and repeated thread dumps show the same threads with HashMap.get or HashMap.put or HashMap.transfer at the top of the stack. What to do: restart (the cycle is permanent), then replace the shared HashMap with ConcurrentHashMap, or guard it with a lock.

Say bucket 1 has A then B. Thread 1 reads A and its next pointer (B), then gets paused. Thread 2 completes a resize and, because transfer reverses order, the new chain is B then A (B.next = A). Thread 1 resumes with its stale view, puts A at the head of a new bucket and sets A.next = B, so now A.next = B and B.next = A: a cycle. The fix is never sharing HashMap across threads. Use ConcurrentHashMap. Java 8 removed this particular bug, but data can still be lost.

Remember: head insert plus concurrent resize made a cycle. The cure is ConcurrentHashMap, not a newer JDK.

Does HashMap allow null keys and values? What about the other maps? Basic

HashMap allows one null key (stored in bucket 0, because its hash is defined as 0) and any number of null values. Hashtable and ConcurrentHashMap allow neither. TreeMap rejects a null key when using natural ordering, though null values are fine.

How the null key is handled. The hash function is (key == null) ? 0 : spread(key.hashCode()), so a null key hashes to 0 and lives in bucket 0. A HashMap can therefore hold exactly one null key (a second put(null, ...) replaces the value). Null values need no special handling, they are just a stored reference.

The ambiguity problem with null values. In a map that allows null values, get(k) returning null has two meanings: the key is absent, or it is present with value null. How should I size a HashMap if I know I will store N entries? Intermediate

Pass an initial capacity of about N / 0.75 + 1, so the map never resizes while I fill it. Passing N itself is a common mistake: the threshold would be 0.75 N, so the map still resizes. Since Java 19 there is HashMap.newHashMap(N), which does the arithmetic for me.

The mistake, with numbers. You are about to insert 1,000 entries. new HashMap<>(1000) looks right, but the constructor rounds 1000 up to 1024 buckets, and the threshold is 1024 x 0.75 = 768. When entry number 769 arrives the map doubles to 2048 and moves everything. So passing N does not prevent a resize. You needed the threshold to be at least N.

The right calculation. Need threshold >= N, i.e. capacity >= N / 0.75.

For small maps in cold code I do not bother. Guava's Maps.newHashMapWithExpectedSize does the same on older Java.

Remember: capacity = N / 0.75 + 1, or HashMap.newHashMap(N) on Java 19+.

What happens if I mutate an object after using it as a HashMap key? Intermediate

The entry is effectively lost. The map filed it in the bucket for the old hash code. After the mutation, hashCode() gives a different value, so get looks in a different bucket and finds nothing. The entry still exists and still uses memory, but I cannot reach it by key. Same problem for a HashSet.

Why it happens, step by step. A hash-based collection stores each entry in the bucket chosen by the hash at the time of insertion, and keeps that hash inside the node. Lookups recompute the hash of the key you pass in and go to that bucket.

  1. m.put(k, "v") where k = [1] has hash 32. The entry goes into bucket (32-based index), say 0.
  2. Code later calls k.add(2). The list is now [1, 2] with hash 994.
  3. m.get(k) computes 994, looks in bucket 2 (say), finds nothing. Returns null.
  4. Even if it reached the right bucket, the stored hash (32) no longer matches, and HashMap compares stored hashes first.

The entry is still physically in the map. size() counts it, iteration over entrySet() shows it, but get, containsKey and remove(k) cannot find it. It is a memory leak that you cannot clean up by key. The only ways out are iterating and removing with an iterator, or rebuilding the map.

The same trap shows up in sets. Put a mutable object in a HashSet, change a field used by hashCode, and contains says false. You can then add the "same" object a second time and the set holds it twice. In a TreeMap or TreeSet the equivalent is changing a field the comparator uses: the tree's ordering breaks and lookups follow the wrong branches.

Where it bites in real code. JPA entities as keys (with a database id assigned on save, so the hash changes after persist), mutable DTOs as cache keys, and lists or arrays as keys. A collection key is only as stable as its contents.

Rules for safe keys.

  • Prefer immutable key types: String, boxed numbers, enums, java.time types, records of immutable fields.
  • If the key must be a custom class, make it final with final fields, and derive hashCode and equals only from those fields.
  • Never base hashCode on a field that changes (for JPA entities, use a business key or a constant hash, not a generated id).
  • If you must change a key, remove the entry first, change it, then insert again.

The cure is to use immutable keys: String, Integer, enums, records, or classes with final fields. If a key must be mutable, never change the fields that take part in equals and hashCode while it is in the map. Removing and re-adding around the change is the only safe route.

List<Integer> k = new ArrayList<>(List.of(1));
Map<List<Integer>, String> m = new HashMap<>();
m.put(k, "v");
k.add(2);
m.get(k);          // null: the hash changed, wrong bucket
m.containsKey(k);  // false, yet m.size() is still 1

Remember: keys must be immutable in everything that feeds hashCode.

HashMap versus Hashtable versus synchronizedMap versus ConcurrentHashMap? Intermediate

HashMap is fastest but not thread safe. Hashtable and Collections.synchronizedMap make every method take one big lock, so they are safe but do not scale and still break compound actions and iteration. ConcurrentHashMap is the right choice for shared maps: lock-free reads, fine-grained locks for writes, and atomic methods like merge.

One axis at a time. The four options differ in what they protect and how coarse the protection is.

  • HashMap: no protection, no cost. Right when one thread owns the map (local variable, per-request object, or built once then only read).
  • Hashtable: every method is synchronized on the table object. One thread at a time, including readers. Legacy.
  • Collections.synchronizedMap(new HashMap<>()): the same single-lock idea as a wrapper. The map's own methods are individually safe, but to iterate you must manually lock the wrapper object, otherwise you can still get a ConcurrentModificationException.
  • ConcurrentHashMap: readers do not lock, writers lock only the bucket they touch (or CAS on an empty one). Offers atomic compound methods (putIfAbsent, compute, merge).

Why "synchronised" does not mean "safe for my logic". Take a request counter: Integer c = map.get(k); map.put(k, c == null ? 1 : c + 1);. On Hashtable or a synchronised map, both calls are individually safe, but two threads can both read 5 and both write 6, so one increment is lost. The lock was released between the two calls. The fix needs a single atomic operation (merge on a ConcurrentHashMap), or your own synchronized block around the whole read-modify-write.

Throughput difference. With one global lock, eight threads doing gets effectively run one at a time. With ConcurrentHashMap, gets run fully in parallel and puts to different buckets run in parallel. On a many-core machine with a read-heavy workload, the gap is often an order of magnitude, though you should measure your own case.

Decision rule. Single thread: HashMap. Shared and mutated: ConcurrentHashMap. Shared, written once at start-up and then read only: a HashMap safely published (final field, or wrapped with Map.copyOf or Collections.unmodifiableMap of a map nobody else changes). Need to do a multi-key atomic update: an explicit lock, whatever the map class.

Which Map methods from Java 8 should I know (getOrDefault, computeIfAbsent, merge)? Intermediate

The three I use daily: getOrDefault(k, d) for a safe read, computeIfAbsent(k, f) to create a value lazily (the multimap and cache pattern) and merge(k, v, f) to combine values (the counting pattern). They replace the clumsy get, null-check, put sequence, and on ConcurrentHashMap they are atomic.

The problem they solve. Before Java 8, common patterns took several lines and two lookups, and in concurrent code they were racy:

// old: counting words

What is the best way to loop over a Map, and what do keySet, values and entrySet really return? Basic

Loop over entrySet() when you need both key and value, keySet() when you need only keys and values() when you need only values. Looping over keySet() and calling get for each key does an extra lookup per entry. All three are live views of the map, not copies.

A view is an object that reads from, and writes through to, the map itself. keySet() costs nothing to create. If you call map.keySet().remove(k) the entry disappears from the map, and if the map changes later the view shows it. Views support removal (remove, removeIf, retainAll, clear) but not add, because there is no value to attach.

for (Map.Entry<String,Integer> e : map.entrySet()) {       // best: one pass
    System.out.println(e.getKey() + " = " + e.getValue());
}
map.forEach((k, v) -> System.out.println(k + " = " + v));    // Java 8, same thing
map.values().removeIf(v -> v == 0);                          // delete by value
map.keySet().removeAll(blockedKeys);                         // delete many keys

Why entrySet beats keySet plus get. For a HashMap each get(k) repeats hashing and bucket lookup. For a TreeMap it repeats an O(log n) search. The entry iteration walks the nodes you already have in hand.

Rules and traps.

  • Changing the map (put of a new key, remove) while looping it directly throws ConcurrentModificationException in the usual maps. Removing through the iterator or removeIf is allowed. Changing a value with entry.setValue(x) is also allowed and writes through.
  • Entries of a HashMap are the real nodes. Do not keep an entry reference after the map changes in a way that removes or restructures it.
  • Iteration order: HashMap arbitrary, LinkedHashMap insertion or access, TreeMap sorted, ConcurrentHashMap unspecified but weakly consistent.
  • Map.entry(k, v) (Java 9) and new AbstractMap.SimpleEntry<>(k, v) create standalone entries not tied to any map.

Remember: entrySet for both key and value, all three are live views, and remove through the view or the iterator.

5. LinkedHashMap, TreeMap and the special maps

What is LinkedHashMap and how does it keep order? Intermediate

LinkedHashMap is a HashMap whose entries are also threaded on a doubly linked list. The hash table gives O(1) lookup, and the list gives a predictable iteration order: insertion order by default, or access order if I pass accessOrder = true. It costs two extra pointers per entry.

The gap it fills. HashMap is fast but iterates in an order you cannot predict. TreeMap iterates in a predictable sorted order but costs O(log n) and needs comparable keys. Often you only want "the order I put things in", for example to print config entries in file order, or to return JSON fields in a stable order. LinkedHashMap gives that at HashMap speed.

How it is built. It extends HashMap, so all the bucket logic is inherited. Each entry (a subclass of the HashMap node) has two extra fields, before and after, which link all entries in one doubly linked list, and the map holds head and tail pointers. The hash table answers "where is key K?" and the list answers "what comes next?". Iteration walks the list, so it costs O(size) rather than O(capacity).

Two ordering modes, with a trace. Insert A, B, C, then call get(A), then insert D.

ModeOrder after the stepsWhat moves entries
insertion order (default)A, B, C, Dnothing: only first-time inserts append; a put on an existing key does not move it
access order (accessOrder = true)B, C, A, Dget, put of an existing key, getOrDefault, merge etc. move the entry to the tail

In access order the head is therefore always the least recently used entry. That is what makes it an LRU cache.

Costs and caveats.

  • About 16 more bytes per entry (two pointers) than HashMap on a compressed-pointer JVM, and slightly slower writes because the list must be maintained.
  • In access-order mode a read changes the structure, so two threads reading at once corrupt it, and reading while iterating can throw ConcurrentModificationException. Even "read-only" use needs locking.
  • Java 21 adds sequenced-map methods: firstEntry(), lastEntry(), pollFirstEntry(), putFirst, reversed().
  • LinkedHashSet is the set version and behaves the same way (insertion order only).

When to choose which. Need only lookup: HashMap. Need stable, predictable iteration or LRU eviction: LinkedHashMap. Need sorted by key or range queries: TreeMap.

Re-inserting an existing key does not change its position in insertion-order mode. In access-order mode, every get or put moves the entry to the tail, so the head is always the least recently used. That is the basis of an LRU cache. A subtle consequence: in access-order mode even get counts as a structural change, so reading while iterating can throw ConcurrentModificationException. Iteration is also faster than HashMap because it walks the list, not the whole table.

Remember: HashMap plus a linked list. Insertion order by default, access order for LRU.

How do I build a simple LRU cache in Java? Intermediate

Extend LinkedHashMap with access order on, and override removeEldestEntry to return true once the size passes my limit. The map then evicts the least recently used entry automatically after each put. It is about five lines, and O(1) for get and put.

What an LRU cache is. A cache has limited space. When it is full and a new item arrives, something must go. Least Recently Used says: evict the entry that has not been touched for the longest time, on the theory that recent use predicts future use. It needs two things quickly: find an entry by key, and know which entry is the oldest by last use. A hash table gives the first, a recency-ordered list gives the second. LinkedHashMap in access-order mode is exactly those two combined.

How the code works.

  1. super(16, 0.75f, true): the third argument turns on access order, so every get and put moves the entry to the tail (most recent end).
  2. After every put of a new key, HashMap's code calls removeEldestEntry(eldest), passing the head of the list. If it returns true the map removes that entry.
  3. Our override returns size() > max, so as soon as we exceed the limit the oldest entry goes.

Trace with max = 3.

put(a) put(b) put(c)    order (old to new): a b c
get(a)                  order: b c a        // a was just used
put(d)                  inserts d -> size 4 > 3 -> evict head b
                        order: c a d

Making it thread safe. Collections.synchronizedMap(new LruCache<>(100)) locks every call, which works, but under heavy load that one lock is a bottleneck. For production use Caffeine, which uses an admission policy and concurrent buffers, supports time-based expiry, loading functions and statistics. Guava's cache is the older option.

What an interviewer may add. "Why does a read need a write lock?" because reordering is a write. "What about LFU?" Least frequently used needs counts per entry (a map of counts to lists, or a heap), which LinkedHashMap does not provide. "Can you build it without LinkedHashMap?" Yes: the HashMap plus doubly linked list version in the coding section.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int max;
    LruCache(int max) { super(16, 0.75f, true); this.max = max; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) {
        return size() > max;
    }
}

It is not thread safe. Wrap it with Collections.synchronizedMap for light use, but even get mutates it, so reads need the lock too. For a real service I would use Caffeine, which gives size and time based eviction, concurrency and statistics. In an interview, the follow-up is to build it by hand with a HashMap and a doubly linked list, which is in the coding section.

Remember: LinkedHashMap(accessOrder=true) + removeEldestEntry. Caffeine in production.

How does TreeMap work, and when would I choose it over HashMap? Intermediate

TreeMap is a red-black tree, a self-balancing binary search tree, so keys stay sorted and get, put and remove are O(log n). I choose it when I need sorted iteration or "nearest key" queries; otherwise HashMap is faster at O(1).

What it is, from scratch. A binary search tree keeps keys so that everything in the left subtree is smaller and everything in the right is larger. To find a key, start at the root and go left or right at each node. In a balanced tree the height is about log2(n): a million keys need about 20 comparisons. A plain tree can degrade into a long chain when keys are inserted in sorted order, so TreeMap uses a red-black tree, which recolours and rotates nodes on insert and delete so that the longest path is never more than about twice the shortest. That guarantees O(log n).

The ordering rule. Order comes from the key's compareTo (natural order) or a Comparator given to the constructor. As with TreeSet, two keys that compare as 0 are the same key, even if equals says no.

What you get that HashMap cannot give.

  • Sorted iteration of keys, values and entries.
  • firstKey(), lastKey(), pollFirstEntry().
  • Neighbour queries: floorKey(k) is the greatest key at most k, ceilingKey(k) the smallest at least k, lowerKey and higherKey are the strict versions.
  • Range views: headMap(to), tailMap(from), subMap(from, to), descendingMap(). They are views, so changes write through to the original.

Worked example: price tiers. Orders over 0 pay 5 percent, over 100 pay 8, over 500 pay 10. Store {0: 5, 100: 8, 500: 10} in a TreeMap and look up an order of 250 with floorEntry(250): the greatest key at most 250 is 100, so 8 percent. Without a tree you would write an if-else chain or scan a list.

TreeMap<Integer,Integer> tier = new TreeMap<>(Map.of(0, 5, 100, 8, 500, 10));
int pct = tier.floorEntry(250).getValue();   // 8

Costs. get, put, remove, floor, ceiling are all O(log n). Iterating all entries is O(n). Each entry stores key, value, left, right, parent and a colour flag, about 40 bytes, more than a HashMap node. No null keys with natural ordering. Not thread safe: ConcurrentSkipListMap is the concurrent sorted map.

Decision. Use HashMap unless you need ordering or nearest-key queries. If you only need the smallest or largest repeatedly, a PriorityQueue is lighter. If you need sorted output once, sort a list.

Its extra power is navigation: firstKey, lastKey, floorKey(k) (greatest key at most k), ceilingKey(k) (smallest key at least k), headMap, tailMap and subMap, which are live range views. Typical uses: time-bucketed data, price tiers, finding the interval containing a value. Keys need natural ordering or a Comparator, and null keys are not allowed with natural ordering. As with TreeSet, key equality is decided by compare returning 0, not equals. It is not thread safe; ConcurrentSkipListMap is the concurrent sorted alternative.

Remember: sorted keys, O(log n), and floor/ceiling/range queries. Equality means compare()==0.

What are EnumMap, WeakHashMap and IdentityHashMap, and when would I use them? Intermediate

EnumMap is a map whose keys are constants of one enum, stored in a plain array indexed by ordinal, so it is the fastest and smallest map for that case. WeakHashMap holds its keys weakly, so an entry disappears once nothing else references the key. IdentityHashMap compares keys with == instead of equals. Each solves a narrow problem that a normal HashMap handles badly.

EnumMap. An enum has a fixed, known set of constants, each with an ordinal number 0, 1, 2 and so on. EnumMap allocates an array with one slot per constant and stores the value for constant c at vals[c.ordinal()]. There is no hashing, no collisions, no resize, and the iteration order is the enum's declaration order. get and put are O(1) with tiny constants. Use it whenever the key is an enum, for example EnumMap<DayOfWeek, List<Shift>>. The matching set class is EnumSet, a bit vector. Null keys are not allowed.

WeakHashMap. A normal map keeps its keys alive: as long as the entry is there, the garbage collector cannot free the key. WeakHashMap wraps each key in a WeakReference. When no strong reference to the key exists anywhere else, the GC may collect it, and the map then drops the entry the next time it is accessed. A typical use is metadata attached to objects whose lifetime you do not control (a per-object cache), where you do not want the map itself to cause a leak. Cautions: keys must be objects with identity semantics, because an interned String literal or a cached Integer may never be collected, entries vanish at unpredictable times, and values must not strongly reference their own key, or the entry is never freed. For serious caching, Caffeine with weak keys or soft values is usually a better tool.

IdentityHashMap. It uses System.identityHashCode and ==. Two equal but distinct objects are different keys. Typical uses are in frameworks that must track object graphs: serialisation libraries that remember which object was already written (to handle cycles), deep-copy utilities and topological algorithms over objects. It also ignores a broken equals or hashCode. It deliberately violates the general Map contract, so do not hand one to code that expects normal map semantics.

6. ConcurrentHashMap

How does ConcurrentHashMap work in Java 8, and how did Java 7 differ? Senior

In Java 8 it is one big table of bins. Reads take no lock at all. To write into an empty bin it uses a CAS (compare-and-swap, an atomic hardware instruction). For a non-empty bin it takes a synchronized lock on just that bin's first node. So two threads only block each other if they hit the same bin. Java 7 instead split the map into 16 segments, each with its own lock.

The goal. A map shared by many threads must not corrupt itself, but a single lock around the whole map makes threads queue even when they touch different keys. ConcurrentHashMap's job is to let as many threads as possible work at once while staying correct.

Java 7: segments. The map was an array of 16 (by default) segments, each a small hash table with its own ReentrantLock. A write locked only its segment, so up to 16 writers could run together. Limits: the number 16 was fixed at construction, so more cores could not help, each segment had its own overhead, and size() had to lock or retry across segments.

Java 8: lock per bin. The segments were removed. There is one array of bins, as in HashMap, and each operation works on just the bin it needs:

  1. get: compute the hash, read the bin head, walk the chain. No lock. Safety comes from volatile reads of the table slot, the node val and next fields, which guarantee the reader sees fully constructed nodes.
  2. put into an empty bin: a CAS (compare-and-set) tries to install the new node in the slot only if it is still null. If another thread won, retry. No lock held.
  3. put into a non-empty bin: synchronized (firstNodeOfBin), then walk the chain, update or append. Only threads working on the same bin wait.
  4. Long bins: the same treeify rule as HashMap (8 nodes and table of at least 64), stored as a TreeBin that has its own read-write protection.
  5. Resize: a thread that notices a resize in progress helps by moving a range of bins, so the work is shared. Moved bins are marked with a forwarding node so readers can find their data in the new table.

Counting. A single shared counter would be a hot spot. The size is a base count plus an array of counter cells, with threads picking a cell by a probe, the same idea as LongAdder. That is why size() sums values that may be moving.

What it means for you. Reads scale perfectly, writes to different bins run in parallel, and individual operations are atomic. It does not make your multi-step logic atomic, which is the next question but one. Iterators never throw ConcurrentModificationException. Null keys and values are forbidden.

Common trap. Because reads are lock-free, a reader can see an update from another thread, but the combination "get then put" is never atomic. Use compute, merge or putIfAbsent.

The Java 8 design scales with the table size rather than a fixed 16 segments, uses less memory, and treeifies long bins like HashMap. Value and next fields are volatile, which is how readers see fresh data without locking. Resizing is cooperative: other threads that touch the map during a resize help move bins. The size is kept in striped counters (as in LongAdder) instead of a single hot variable.

Remember: Java 8: lock-free reads, CAS for empty bins, lock the first node otherwise. Java 7: 16 segment locks.

Why is ConcurrentHashMap.size() only an estimate? Senior

Because there is no single counter to read. Updates add to a base count plus several striped cells to avoid contention, and size() sums them while other threads may still be updating. The answer is correct for some moment, but may be stale by the time I use it. Don't make decisions that need an exact size.

Why a single number is hard. Imagine counting people entering a stadium through 50 gates. You can have one clerk with a clicker at a central desk, but every person has to wait to report in: a bottleneck. Or each gate keeps its own clicker and you add them up when asked. That is fast for entering, but the total is only right if nobody enters while you add. ConcurrentHashMap takes the second approach, because a single shared counter updated by every put and remove from every thread would be the contention point that the lock-free design avoids.

The mechanics. There is a baseCount field updated with CAS. If the CAS fails due to contention, the thread falls back to a striped array of CounterCell objects and increments a cell chosen by the thread's hash. size() returns baseCount plus the sum of the cells. While summing, other threads can still change cells, so the answer is a value that was approximately right at some moment during the call.

What this implies in code.

// WRONG: not a real limit under concurrency
if (map.size() < MAX) map.put(k, v);    // many threads can pass the check together

// Better: enforce the limit with a different mechanism,
// e.g. a Semaphore, an AtomicInteger permit, or a cache library with max size.

Both the check and the put can interleave with other threads. Also isEmpty() is only a hint, and a loop "while (!map.isEmpty()) ..." can end while others are still adding.

Other details. size() returns an int, capped at Integer.MAX_VALUE. mappingCount() returns a long and is recommended in new code. When no other thread is updating (for example after all writers finished), the value is exact. Operations like forEach, keySet().size() and values().size() inherit the same semantics. If an exact bounded size is a requirement, you need external coordination or a structure designed for it (a bounded cache such as Caffeine, which enforces its maximum approximately and asynchronously, by the way).

For a concurrent map this is by design: an exact size would need stopping all writers. mappingCount() returns a long and is preferred for very large maps (size is an int). The same logic is why isEmpty() then put is not an atomic pair, and why "if size is below max, add" does not enforce a limit under concurrency.

Remember: size is a snapshot sum of counters. Never build logic on exact size under concurrency.

Why doesn't ConcurrentHashMap allow null keys or values? Senior

Because null would make get ambiguous in a concurrent setting. If get(k) returns null, I cannot tell "absent" from "present with null value", and I cannot safely call containsKey afterwards because another thread may have changed the map between my two calls. Banning nulls removes the ambiguity.

The scenario that breaks. Suppose a map allowed null values, and two threads run these at about the same time.

// Thread 1                          // Thread 2
v = map.get("k");     // null        map.put("k", "x");
if (v == null) {
   boolean has = map.containsKey("k");   // now true!
   ...
}

Thread 1 saw null, then asked "is the key there?" and got a different answer than the first call implied. Is the value null because the key is absent, or because null was stored? With concurrent modification there is no way to answer correctly in two calls. In a plain HashMap used by one thread, get then containsKey is always consistent. That is why HashMap can allow nulls and ConcurrentHashMap cannot afford to.

The design result. In ConcurrentHashMap, get returning null always means "no mapping". The same convention shapes the compound methods: putIfAbsent returns null when the insert happened; computeIfAbsent leaves the key absent if the function returns null; compute and merge remove the entry if the function returns null. Doug Lea, who wrote the class, has explained that null is meant to be a signal, not data.

Keys. A null key is banned for a different reason: the code calls key.hashCode() without a special case, and avoiding the special case keeps the fast path short.

What to do when you need "empty".

  • Store Optional.empty() or a dedicated NONE sentinel object. Check for it explicitly.
  • Or store a wrapper record with a boolean flag.
  • Or just do not store the key, and treat "absent" as empty.

Pitfall. Migrating from HashMap to ConcurrentHashMap can introduce a NullPointerException at runtime in code that stored nulls, so check call sites. Hashtable, Map.of and ConcurrentSkipListMap also reject nulls.

In a plain HashMap this is not a problem because I control the only thread. So in ConcurrentHashMap, null means "no mapping", always. This is also why putIfAbsent and compute have clean semantics, and why a function returning null from compute means "remove the key". If I need to store "no value", I use Optional or a sentinel object.

Remember: in a concurrent map, null can only mean absent. So it is banned as key and value.

Is a check-then-put on a ConcurrentHashMap thread safe? Senior

No. Each individual method is atomic, but two calls in a row are not. if (!map.containsKey(k)) map.put(k, v) has a gap where another thread can insert in between, and the two threads overwrite each other. I use the atomic single-call versions: putIfAbsent, computeIfAbsent, compute and merge.

The distinction. Thread safe means each individual method call behaves as if it happened in one indivisible step. A sequence of two calls is not indivisible. Between them any other thread may run. This is the single most common concurrency mistake with concurrent collections.

Lost-update trace. Counter at "k" is 5. Two threads execute the racy version:

  1. T1: c = map.get(k) returns 5.
  2. T2: c = map.get(k) returns 5.
  3. T1: map.put(k, 6).
  4. T2: map.put(k, 6). Final value 6, but two increments happened, so it should be 7.

Every call was atomic and there was still a bug. With merge(k, 1, Integer::sum) the map performs read, add and write under its own bin lock, so the final value is 7.

Check-then-act with a loader. if (!map.containsKey(k)) map.put(k, load(k)); can run load twice for one key and create two different objects, with the later one overwriting the first, while the first thread continues to use its orphan copy. map.computeIfAbsent(k, this::load) runs the function while holding the bin lock, so exactly one thread computes it and the others wait for and receive the same result.

Which atomic method for which job.

IntentMethod

Limits. The map can make one key's operation atomic. It cannot make "move 10 from account A to account B" atomic, because that touches two keys. That requires one lock around both, a single-writer design, or a transaction. And a slow function inside computeIfAbsent blocks other writers to the same bin, so for long loads store a CompletableFuture or use a loading cache.

// racy: lost updates
Integer c = map.get(k); map.put(k, c == null ? 1 : c + 1);

// atomic
map.merge(k, 1, Integer::sum);
// per-key lazy init, loader runs at most once
map.computeIfAbsent(k, key -> load(key));

Keep the lambda short and never update the same map inside it, because it runs while a bin is locked, and a recursive update can deadlock or throw. For counters under heavy contention, a LongAdder as the value scales better than merge with Integer. Watch for compound logic across several keys: the map cannot make that atomic, a lock is needed.

Remember: thread-safe methods, not thread-safe sequences. Use merge, compute and putIfAbsent.

What does "weakly consistent iterator" mean in ConcurrentHashMap? Senior

The iterator never throws ConcurrentModificationException and never returns an element twice. It reflects the map at some point at or after its creation, and it may or may not show entries added or removed while I iterate. So it is safe to loop and modify at once, but it is not a snapshot.

Three iterator behaviours, side by side.

KindIf the collection changes during iterationUsed by
Fail-fastthrows ConcurrentModificationException (best effort)ArrayList, HashMap, HashSet
Snapshotsees only the data as of iterator creation, never changesCopyOnWriteArrayList

How it works in ConcurrentHashMap. The iterator walks the table array bin by bin, traversing each bin's current nodes. It does not lock. If another thread adds an entry to a bin the iterator has not reached yet, it will probably see it. If the entry goes into a bin it already passed, it will not. If a resize happens, the iterator follows forwarding nodes and still visits each entry once. So the result is some mix of the old and new state.

Example. Thread A loops over the map while thread B removes key "x" and adds key "y". A might see x (if it passed that bin before removal), might see y, might see both or neither. What it will never see is an exception, a duplicate, or a corrupted node.

Why this is useful. It lets you do housekeeping in one loop without stopping other threads: for (var e : map.entrySet()) if (expired(e.getValue())) map.remove(e.getKey()); is legal and safe. The same code on a HashMap would throw. (You can also call map.values().removeIf(...), or map.entrySet().removeIf(...), which is neater.)

What it does not give you. A point-in-time view. If you need a consistent report ("total of all values right now"), the sum may include some updates and miss others. Options: accept approximate figures, take the copy new HashMap<>(map) (also not atomic, the copy itself iterates weakly), or pause writers with your own lock. The bulk methods forEach, reduce, search take a parallelism threshold and are weakly consistent in the same way, and their functions should not depend on order or on seeing every update.

This is different from fail-fast (throws on change) and from a copy-on-write snapshot (never sees changes). It means I can remove entries inside a for-each loop over a ConcurrentHashMap, which would throw on a HashMap. Bulk operations such as forEach, reduce and search with a parallelism threshold are also weakly consistent. If I need an exact point-in-time view, I must copy the map under my own coordination.

Remember: weakly consistent = no exception, no duplicates, maybe stale. Not a snapshot.

Why prefer ConcurrentHashMap over Collections.synchronizedMap? Intermediate

A synchronized map uses one lock for everything, so all threads queue, even readers. ConcurrentHashMap lets readers run freely and lets writers to different bins proceed in parallel. It also gives atomic compound methods and iterators that don't throw. Under real concurrency it can be many times faster.

Picture the difference. Collections.synchronizedMap(map) puts a single door in front of the whole map: every get, put, size and iteration step goes through synchronized (mutex). With ten threads, nine wait outside at any moment, even when they want completely different keys. ConcurrentHashMap has many doors, one per bin, and no door at all for readers.

If I need to lock the whole map for a multi-key update, a synchronized map or an explicit lock is the right tool.

Remember: one global lock versus per-bin locks and lock-free reads.

Which thread-safe collections does the JDK offer, and when do I use each? Intermediate

For maps, ConcurrentHashMap (or ConcurrentSkipListMap when I need sorted order). For lists, CopyOnWriteArrayList when reads dominate. For queues, ConcurrentLinkedQueue (unbounded, lock-free) or a BlockingQueue when threads must wait. The old synchronized wrappers are the fallback, not the first choice.

Why several classes and not one. There is no structure that is best for every access pattern under concurrency. Each class makes a different bet about who reads, who writes and who waits.

Reading the table in the question as a decision.

  • ConcurrentHashMap: default for a shared lookup structure. Unordered.
  • ConcurrentSkipListMap / Set: a skip list (layers of linked lists that let you jump ahead), giving sorted order with O(log n) and lock-free operations. Choose it when you need a TreeMap shared across threads, since TreeMap has no concurrent version.
  • CopyOnWriteArrayList / Set: many readers, almost no writers. Writers copy the whole array.
  • ConcurrentLinkedQueue / Deque: unbounded, lock-free (CAS based) FIFO. Never blocks, so a consumer must poll or use another signalling.
  • BlockingQueue family: threads wait. ArrayBlockingQueue (bounded, array), LinkedBlockingQueue (optionally bounded, two locks), PriorityBlockingQueue (unbounded heap), DelayQueue (elements available after a delay), SynchronousQueue (direct hand-off), LinkedTransferQueue.

Choosing for a typical need. A shared in-memory cache keyed by id: ConcurrentHashMap (or Caffeine for eviction). A leaderboard that must stay sorted and be updated by many threads: ConcurrentSkipListMap. A list of subscribers: CopyOnWriteArrayList. A work queue between a producer and consumer pool: bounded BlockingQueue. A lock-free queue where you do not mind spinning: ConcurrentLinkedQueue.

Common mistakes.

  • Using ConcurrentHashMap and then doing check-then-act with separate calls.
  • Putting a mutable object inside a concurrent collection and mutating it without protection: the collection protects only its own links, not the contents.
  • Choosing ConcurrentLinkedQueue where you need back-pressure: it is unbounded and can grow without limit.
  • Expecting size() to be cheap or exact: for ConcurrentLinkedQueue it is O(n) and approximate.

Fall-back. Collections.synchronizedXxx wrappers are fine for low contention or when you need a lock that spans several operations. Everything above can be replaced by an explicit lock around an ordinary collection when your access pattern is complicated.

7. Queues, Deques and heaps

What should I use for a stack or a queue in Java? Basic

Use ArrayDeque for both. As a queue: offer at the tail, poll from the head. As a stack: push and pop at the head. It is a growable circular array, so every end operation is O(1) amortised, and it is faster and lighter than LinkedList and the legacy Stack.

Terms first. A queue is first-in, first-out (FIFO): like a line at a counter, you join at the back and leave from the front. A stack is last-in, first-out (LIFO): like a pile of plates, you put on top and take from the top. A deque ("deck", double-ended queue) allows adding and removing at both ends, so it can act as either. ArrayDeque implements Deque.

Why not LinkedList or Stack. LinkedList allocates a node object per element (extra memory and garbage). Stack is a synchronised Vector with a leaky API. ArrayDeque keeps elements in one array, which is cache friendly and allocation free in steady state.

How the circular array works. The array has a head index (where the first element is) and a tail index (the next free slot). Adding at the tail writes at tail and moves it forward; removing from the head reads head and moves it forward. When an index would pass the end of the array it wraps to 0 (it uses a bit mask because the length is a power of two). When the array is full it doubles and the elements are copied in order. Nothing is ever shifted, so both ends are O(1).

Method names, grouped by intent.

RoleInsertRemoveLook
Queue (FIFO)offer(x) / addLastpoll() / removeFirstpeek()
Stack (LIFO)push(x) = addFirstpop() = removeFirstpeek()

Each pair has a throwing form (add, remove, element) and a safe form (offer, poll, peek) that returns null or false when it cannot act. The null is exactly why ArrayDeque forbids storing null elements.

Everyday uses. Depth-first search with an explicit stack, breadth-first search with a queue, undo history, parsing balanced brackets, and sliding-window maximum (store indexes in a deque). A subtle point: push inserts at the front, so iterating a stack prints the most recent element first, the reverse of what Stack does.

Deque<Character> st = new ArrayDeque<>();
for (char c : "([])".toCharArray()) {
    if (c == '(' || c == '[') st.push(c);
    else if (st.isEmpty() || !match(st.pop(), c)) return false;
}
return st.isEmpty();

Not suitable for: concurrent use (use ConcurrentLinkedDeque or a BlockingDeque), priority order (use PriorityQueue), and when you need to remove from the middle by value cheaply (O(n)).

A circular array keeps a head and tail index that wrap around, so there is no shifting. It does not allow null (null is how poll says "empty"), and it is not thread safe. Prefer offer/poll/peek, which return a special value on failure, over add/remove/element, which throw. For thread hand-off use a BlockingQueue instead.

Remember: ArrayDeque for stack and queue. No nulls, not thread safe.

How does PriorityQueue work, and what are its gotchas? Intermediate

PriorityQueue is a binary min-heap stored in an array: the smallest element (by natural order or my comparator) is always at the head. peek is O(1), offer and poll are O(log n). I use it to repeatedly get the next smallest or most urgent item, as in scheduling, Dijkstra, or merging sorted lists.

What a heap is. A binary min-heap is a binary tree with one rule: every parent is less than or equal to both its children. So the smallest element is always at the root. It does not keep everything sorted, only the parent-child rule. That weaker promise is what makes it cheap to maintain. The tree is "complete" (filled level by level, left to right), so it can be stored in an ordinary array with no pointers: the root at index 0, children of index i at 2i+1 and 2i+2, parent at (i-1)/2.

Insert, with a trace. Heap array [1, 3, 2, 7, 4, 5, 9], and we offer 0.

  1. Place 0 at the next free index 7 (the end of the array).
  2. Its parent index is (7-1)/2 = 3, holding 7. 0 < 7, swap. Now 0 is at index 3.
  3. Parent of 3 is 1, holding 3. 0 < 3, swap. 0 at index 1.
  4. Parent of 1 is 0, holding 1. 0 < 1, swap. 0 is the root. Stop.

This "sift up" takes at most the tree height, log2 n steps.

Poll (remove the smallest). Take the root as the result, move the last array element into the root, then "sift down": repeatedly swap it with the smaller child until it is not larger than either. Also O(log n). Reading the root with peek is O(1).

What you must not assume. The array is not sorted. After the insert above the array is [0, 1, 2, 3, 4, 5, 9, 7] (try it), and a for-each or toString prints exactly that. To get sorted output you must poll repeatedly. contains and remove(Object) are O(n) (a linear search, then a sift). For equal priorities the order is not specified, not FIFO. If you need a stable tie-break, add a sequence number to the comparator.

Min or max. Default is a min-heap. For max-heap use new PriorityQueue<>(Comparator.reverseOrder()). Do not write the comparator as a subtraction (overflow).

Mutating priorities. If you change the field that decides the ordering of an element already in the queue, the heap is not re-arranged and results are wrong. Remove and re-add it. Typical uses: Dijkstra's shortest path, task schedulers, merging k sorted lists, top-k queries, event simulation. Thread-safe version: PriorityBlockingQueue.

For a node at index i, its children are at 2i+1 and 2i+2, and its parent at (i-1)/2. Insert adds at the end and sifts up, poll moves the last element to the root and sifts down. Gotchas: iteration and toString are not sorted, only the head is guaranteed. remove(Object) and contains are O(n). For a max-heap pass Comparator.reverseOrder(). Ties come out in no promised order. It is not thread safe (use PriorityBlockingQueue) and has no nulls. Building from a collection is O(n) via heapify.

Remember: min-heap in an array. peek O(1), offer/poll O(log n), iteration not sorted.

How do I find the K largest elements with a PriorityQueue? Intermediate

I keep a min-heap of size K. For each element I add it, and if the heap grows past K I remove the smallest. At the end the heap holds the K largest. It is O(n log K) time and O(K) memory, better than sorting everything (O(n log n)) and it works on a stream.

The goal and the naive way. From n numbers, find the K largest. Sorting everything costs O(n log n) and needs all data in memory. But you only want K numbers, so most of the sorting effort is wasted. Better: keep a small "leaderboard" of the best K seen so far.

Why a min-heap for the largest. The leaderboard needs to answer, quickly, "who is the weakest member right now?", because that is the one a newcomer must beat and the one to evict. The weakest of the K largest is the smallest of them, and a min-heap gives its smallest at the root in O(1). A max-heap would give the strongest, which is the wrong end.

Trace. data = [5, 1, 9, 3, 7, 8], K = 3.

ReadHeap contents after stepAction
5{5}add
1{1, 5}add
9{1, 5, 9}add, size = K
3{3, 5, 9}add then poll 1 (smallest)
7{5, 7, 9}add then poll 3
8{7, 8, 9}add then poll 5

Final heap {7, 8, 9}, and peek() = 7 is the 3rd largest. Each element costs one offer and at most one poll, each O(log K), so the total is O(n log K) with only K items in memory. When n is a billion log lines and K is 10, this is a huge win, and it works on a stream you can read only once.

Optimisation. Skip the offer if the heap is full and the new value is not greater than peek(): if (heap.size() < k) heap.offer(x); else if (x > heap.peek()) { heap.poll(); heap.offer(x); }. Most elements are rejected after one comparison.

Alternatives. Quickselect (partition like quicksort) finds the K-th element in O(n) average on in-memory arrays, but modifies the array and has bad worst cases. Sorting is fine for small inputs and when you need the whole order. For K smallest use a max-heap of size K. For objects, give the heap a comparator on the field that matters, and for "K most frequent" count first (see the coding question).

PriorityQueue<Integer> heap = new PriorityQueue<>();   // min-heap
for (int x : data) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();   // drop the smallest
}
// heap now holds the k largest; heap.peek() is the kth largest

The min-heap feels backwards at first: the root is the smallest of the kept K, i.e. the entry bar to beat. For the K smallest use a max-heap. If K is close to n, just sort. If the data fits in memory and K is tiny, a quickselect gives O(n) average but needs the whole array.

Remember: K largest uses a min-heap of size K. Evict the smallest each time.

What is a BlockingQueue and how is it used for producer-consumer? Intermediate

A BlockingQueue is a thread-safe queue where put waits when the queue is full and take waits when it is empty. That gives producer-consumer coordination for free: producers and consumers share the queue, and no manual wait/notify is needed. A bounded queue also gives back-pressure, since fast producers are slowed down.

The problem. A producer thread creates work (requests, messages) and a consumer thread processes it. They run at different speeds. Without coordination you need to answer: what does the consumer do when there is nothing? what does the producer do when the buffer is full? Hand-written wait() and notify() code for this is notoriously easy to get wrong (missed signals, spurious wakeups, lost interrupts). A BlockingQueue packages the answer.

Four styles for each case, so you pick how much waiting is acceptable. Blocking threads sleep without using CPU, and are woken when the condition changes.

Why bounded matters: back-pressure. Suppose the producer makes 1,000 items per second and the consumer handles 500. With an unbounded queue the backlog grows by 500 every second until memory runs out. With a bounded queue of 1,000, the producer's put blocks once the queue is full, which slows the producer to the consumer's pace. The system stays stable. This is called back-pressure, and it is the main reason to prefer bounded queues.

Shutdown patterns. (1) Poison pill: a special item meaning "stop". (2) Interrupt the consumer thread and handle InterruptedException. (3) Use an ExecutorService and call shutdown. Whatever you do, never swallow the interrupt silently.

Where it is used without you noticing. Every ThreadPoolExecutor has a BlockingQueue for pending tasks, so the choice of queue (bounded or not, direct hand-off or buffer) decides the pool's behaviour under load.

Pitfalls. Null elements are not allowed. size() is only a snapshot. A consumer blocked in take() forever on a queue nobody will fill again leaks a thread: pair with timeouts or shutdown signals.

BlockingQueue<Job> q = new ArrayBlockingQueue<>(1000);
// producer:  q.put(job);          // blocks if full
// consumer:  Job j = q.take();    // blocks if empty
// timed:     q.offer(job, 1, TimeUnit.SECONDS);

Shutdown needs care: a common trick is a "poison pill" element that tells the consumer to stop. Use the timed offer and poll if a thread must not wait forever. Thread pools (ThreadPoolExecutor) use a BlockingQueue internally for their task queue.

Remember: put blocks when full, take blocks when empty. Bound the queue.

ArrayBlockingQueue is a fixed-size array with one lock. SynchronousQueue has no capacity: each put waits for a matching take.

For hand-off between exactly-matched producers and consumers, SynchronousQueue. Other members you may be asked about: PriorityBlockingQueue (unbounded heap), DelayQueue (items available only after their delay), LinkedTransferQueue.

The unbounded default is a classic production bug: if consumers are slower than producers, the queue grows until the heap is gone. Always pass a capacity. SynchronousQueue is a direct hand-off, used by Executors.newCachedThreadPool, which therefore creates a new thread when none is idle. Executors.newFixedThreadPool uses an unbounded LinkedBlockingQueue, which is why people in production prefer to build a ThreadPoolExecutor with a bounded queue and an explicit rejection policy.

Remember: Linked defaults to unbounded, so always set a bound. Synchronous is zero-capacity hand-off.

Write a simple producer-consumer with a BlockingQueue. Intermediate

One shared bounded queue, a producer thread that calls put, a consumer thread that calls take in a loop, and a poison pill to stop it. The queue handles all blocking and thread safety.

The design in plain words. Three pieces: a shared bounded queue (the buffer and the synchronisation), a producer that puts items, and a consumer that takes them. Because put blocks when the buffer is full and take blocks when it is empty, neither thread needs a lock, a flag, or a sleep loop.

Why a poison pill. The consumer is stuck in take() in an endless loop, so it needs a way to learn "no more work is coming". A special sentinel item placed in the queue after the last real item does it: it is delivered in order, so everything before it is processed first. It must be compared by identity or equality with something that cannot be a real job (a dedicated object, not a common string).

Multiple consumers. One pill is consumed by one consumer only. With 4 consumers the producer must put 4 pills, or each consumer must re-insert the pill it received before exiting. The same applies with multiple producers: the pills must be sent only after all producers finish (use a CountDownLatch or a join).

The interrupt rule. put and take throw InterruptedException if the thread is interrupted while waiting. Catching it and doing nothing hides a shutdown request. Either let it propagate or call Thread.currentThread().interrupt() to restore the flag, as the snippet does.

The same thing with an executor (what you would write in a real project).

ExecutorService workers = Executors.newFixedThreadPool(4);
BlockingQueue<Job> q = new ArrayBlockingQueue<>(100);
for (int i = 0; i < 4; i++) workers.submit(() -> {
    try { while (true) process(q.take()); }
    catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
// producer thread: q.put(job) ...
workers.shutdownNow();   // interrupts the blocked takes

Here shutdown works by interrupt instead of a pill. Choose the pill when you want the consumers to finish all queued work first, and interrupt when you want to stop promptly. Also mention testing: a bounded queue with a slow consumer is the quickest way to see that back-pressure works.

static final String STOP = "STOP";
BlockingQueue<String> q = new ArrayBlockingQueue<>(100);

Thread producer = new Thread(() -> {
    try {
        for (int i = 0; i < 1000; i++) q.put("job-" + i);
        q.put(STOP);                       // tell the consumer to end
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});

Thread consumer = new Thread(() -> {
    try {
        for (String s; !(s = q.take()).equals(STOP); ) process(s);
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});
producer.start(); consumer.start();

With several consumers, the producer must send one pill per consumer. In real code I would use an ExecutorService and restore the interrupt flag on InterruptedException, as shown.

Remember: bounded queue, put and take, poison pill per consumer, restore the interrupt flag.

8. Ordering, utilities and the equals/hashCode contract

What is the equals and hashCode contract, and what breaks if I violate it? Intermediate

If two objects are equal by equals, they must return the same hashCode. The reverse is not required: equal hash codes with different objects is just a collision. Break the rule, for example by overriding equals but not hashCode, and HashMap and HashSet silently misbehave: get misses entries, and duplicates get through.

The two methods, in plain terms. equals answers "are these two objects the same value?". hashCode gives a quick number used as a first filter by hash-based collections. By default (Object) both are about identity: equal only to itself. When you want value equality, as for a Point(1,2), you override both.

The contract.

  1. If a.equals(b) then a.hashCode() == b.hashCode(). (Equal objects must have equal hashes.)
  2. The reverse is not required: different objects may share a hash (collision).
  3. The hash must stay the same while the object is unchanged, within one run.
  4. equals must be reflexive (a.equals(a)), symmetric (a.equals(b) iff b.equals(a)), transitive, consistent, and a.equals(null) is false.

A concrete failure.

class P {
    final String n;
    P(String n) { this.n = n; }
    @Override public boolean equals(Object o) { return o instanceof P p && n.equals(p.n); }
    // hashCode not overridden: uses identity hash
}
Set<P> s = new HashSet<>();
s.add(new P("ann"));
s.contains(new P("ann"));   // usually false: different identity hashes, different buckets
s.add(new P("ann"));        // true: the set now holds two "equal" objects

The two "ann" objects get different identity hashes, so they usually land in different buckets and equals is never called. It is intermittent: they may happen to land in the same bucket, which makes the bug worse to debug.

Common ways the symmetry rule breaks. A subclass adds a field and overrides equals: point.equals(coloredPoint) is true but coloredPoint.equals(point) is false. Using getClass() instead of instanceof keeps symmetry but breaks substitution. The robust options: make the class final, use composition, or use a record (which generates correct equals, hashCode, toString for its components).

Practical checklist. Override both together. Use the same fields in both. Use Objects.equals for nullable fields. Compare floating-point fields with Double.compare. Do not include mutable fields if the object is used as a key. Let the IDE, a record or Lombok generate them. For JPA entities, think carefully: a generated id is null before persist, so a hash based on it changes.

Why: HashMap uses the hash to choose the bucket and only then calls equals. Two equal objects with different hashes go to different buckets and never meet. The full equals contract is reflexive, symmetric, transitive, consistent, and false for null. Use the same fields in both methods, and only immutable fields. Records, Lombok @EqualsAndHashCode or Objects.equals/Objects.hash remove the boilerplate. Inheritance makes symmetry hard (subclass adds a field), which is one reason to prefer composition or final classes.

class P { String n; P(String n) { this.n = n; }
  public boolean equals(Object o) { return o instanceof P p && n.equals(p.n); }
  // hashCode forgotten
}
Set<P> s = new HashSet<>(); s.add(p1); s.contains(new P("same name")); // usually false

Remember: equal objects must have equal hash codes. Override both together, from immutable fields.

What makes a good hashCode? Intermediate

It must be consistent with equals, cheap, and spread values evenly so that different objects usually land in different buckets. The standard recipe combines the same fields equals uses with a multiplier, which is exactly what Objects.hash(a, b, c) does.

Goal. A hash function should map distinct objects to well-spread ints, quickly, and the same way for equal objects. "Spread" matters because the table index uses only a few bits of the hash, so collisions mean longer chains.

The standard recipe, with a worked example. Start with a non-zero seed (17 in older advice), and for each field that takes part in equals do result = 31 * result + hash(field). For a class with id = 7 and name = "ab":

int r = 1;
r = 31 * r + Long.hashCode(7);       // 31 * 1 + 7 = 38
r = 31 * r + "ab".hashCode();        // 31 * 38 + 3105 = 4283
// "ab".hashCode() itself is 'a'*31 + 'b' = 97*31 + 98 = 3105

This is what Objects.hash(id, name) and Arrays.hashCode do. Multiplying by an odd number keeps information from being shifted out, and combining each field after multiplying makes order matter, so (1, 2) and (2, 1) hash differently. 31 is popular because it is odd, prime, and 31 * x = (x << 5) - x, cheap on old hardware. The JVM still handles it well today.

Rules of thumb.

  • Fields: exactly the ones used by equals (or a subset of them, never a field that equals ignores).
  • Use Double.hashCode, Long.hashCode for primitives, Objects.hashCode for nullable object fields (null becomes 0).
  • Do not use fields that change while the object is in a hash collection.
  • Do not use the identity hash of other objects, or random numbers.
  • A cache for the result is fine for immutable objects with expensive hashing (String does it).

Bad examples. return 1; is legal and correct, but every key collides, so HashMap behaves like a list (or a tree, in Java 8). return id % 10 gives only ten distinct values, so chains of length n/10. Summing field hashes loses order information: (a, b) and (b, a) collide.

Performance note. Objects.hash(...) allocates an array (varargs) and boxes primitives. In a hot path, write it by hand. Strings and records are already optimised. If an interviewer asks how many bits matter: HashMap folds the high 16 bits into the low ones, so what you need is variation in any bits.

The classic formula is 31 * result + field.hashCode(). 31 is an odd prime, and the multiply compiles to a shift and subtract. A constant hash is legal but turns the map into a list (a tree in Java 8). A common bug is hashing a mutable field. Objects.hash boxes primitives and allocates an array, so in a very hot path I write the arithmetic by hand. Strings cache their hash, which is a big reason they make great keys.

@Override public int hashCode() { return Objects.hash(id, name); }

Remember: same fields as equals, spread bits evenly, never a mutable field.

Comparable versus Comparator: which and when? Basic

Comparable is the natural order built into the class itself (compareTo), so there is just one. Comparator is a separate object that defines an ordering from outside, so I can have many: by name, by date, descending. I implement Comparable once for the obvious order and pass Comparators for everything else.

The problem. Sorting and sorted collections need a way to ask "which comes first?". Java has two answers, depending on where that rule lives.

Comparable: the rule is inside the class. The class implements Comparable<T> with compareTo(T other), returning a negative number, zero or a positive number. That makes it the type's natural order, such as String alphabetical or Integer numeric. There can be only one, because a class has one compareTo. Collections.sort(list), TreeSet and TreeMap use it when you give no comparator.

Comparator: the rule is outside. A separate object with compare(a, b). You can have as many as you want and you can write one for a class you cannot change (like String or a library type).

Building comparators. Java 8 made them composable:

Rules for a correct comparator.

  • Antisymmetric: if compare(a,b) > 0 then compare(b,a) < 0.
  • Transitive: a before b and b before c implies a before c.
  • Consistent with equals, if the result is used in a TreeSet or TreeMap (otherwise elements disappear as duplicates).
  • Never subtract to compare (overflow), and never return only 0 or 1 for "not equal" (this breaks symmetry and can make TimSort throw "Comparison method violates its general contract").

Choosing. If a type has a single obvious ordering and you own it (a Money or Version type), implement Comparable. For everything else, pass a Comparator, so the sort rule is visible at the call site.

people.sort(Comparator.comparing(Person::lastName)
                      .thenComparing(Person::age, Comparator.reverseOrder()));
list.sort(Comparator.nullsLast(Comparator.naturalOrder()));

Comparators compose with comparing, thenComparing, reversed and the null-handling helpers. TreeMap, TreeSet, PriorityQueue and sort methods accept either. The sort contract needs the comparator to be consistent: if a is before b and b before c, then a is before c, otherwise TimSort may throw IllegalArgumentException: Comparison method violates its general contract.

Remember: Comparable = the class's one natural order. Comparator = any order from outside.

Why is comparing with a - b a bug? Intermediate

Because the subtraction can overflow. With a = Integer.MAX_VALUE and b = -1, a - b wraps to a negative number, so the comparator says a is smaller, which is wrong. This produces a broken sort or a "violates its general contract" exception that appears only on certain data.

The overflow, with real numbers. An int holds values from -2,147,483,648 to 2,147,483,647. Subtracting two ints can leave that range, and Java silently wraps around (two's complement).

int a = 2_000_000_000, b = -2_000_000_000;
a - b                    // 4,000,000,000 does not fit: wraps to -294,967,296 (negative!)
(a - b) < 0              // true  -> the comparator says a < b, which is false

A comparator (x, y) -> x - y is therefore right for small numbers (all your unit tests, with values like 3 and 7), and wrong for large or mixed-sign values in production. Sorting a list with it gives a wrong order, and in the worst case breaks the transitivity that TimSort checks, producing IllegalArgumentException: Comparison method violates its general contract! at random, depending on the data. Bugs that appear only with particular data are the most expensive kind.

The correct forms.

Integer.compare(a, b)                           // returns -1, 0, 1 with no overflow
Comparator.comparingInt(Person::age)            // primitive-specialised, no boxing
Comparator.comparing(Person::name)              // for Comparable keys
Double.compare(x, y)                            // handles NaN and -0.0 consistently

Why not x < y ? -1 : 1. It never returns 0 for equal values, so compare(a, a) is 1. That violates the contract (equal items must give 0), which can make sorts or TreeSets behave oddly. Use Integer.compare. Floating point with == or subtraction also fails on NaN and on tiny differences cast to int: (int)(x - y) turns 0.4 into 0, "equal".

Same idea elsewhere. The midpoint (lo + hi) / 2 in a binary search overflows for large indexes, so people write lo + (hi - lo) / 2. Counting or hashing with int arithmetic has the same silent wrap. Interviewers like this question because it checks whether you know ints wrap rather than throw.

Use Integer.compare(a, b), Long.compare, Double.compare, or Comparator.comparingInt(...). These also handle Double NaN and negative zero consistently, unlike a manual <. The comparator must also be antisymmetric, transitive and consistent over time (not depend on mutable or random state).

Remember: never subtract to compare. Use Integer.compare or Comparator.comparingInt.

Which sorting algorithms does Java use, and does it matter? Intermediate

For objects (Collections.sort, List.sort, Arrays.sort(Object[])) Java uses TimSort: a stable merge-sort hybrid that is O(n log n) worst case and close to O(n) on data that is already mostly sorted. For primitive arrays like int[] it uses dual-pivot quicksort, which is faster but not stable (stability does not matter for primitives).

What "stable" means, with an example. Take records already ordered by name: (Asha, Pune), (Bela, Delhi), (Chen, Pune). Now sort by city only. A stable sort keeps equal elements in their previous relative order: Delhi first, then Pune with Asha before Chen. An unstable sort may output Chen before Asha. Stability makes multi-key sorting easy (sort by the minor key first, then by the major key) and keeps results reproducible.

TimSort for objects. It looks for existing sorted runs in the data (ascending, or strictly descending which it reverses), extends short runs to a minimum length using binary insertion sort, and then merges runs with rules that keep the merge tree balanced. Result: O(n log n) worst case, O(n) when the data is already sorted or nearly so (real-world data often is), stable, and about n/2 extra elements of temporary space. It was created by Tim Peters for Python and has been the default for object sorting in Java since Java 7.

Dual-pivot quicksort for primitives. Arrays.sort(int[]) picks two pivot values and splits the array into three parts. It is O(n log n) on average, faster than classic quicksort in practice, in-place, and not stable, which is irrelevant for primitives because equal ints are indistinguishable. Details have changed across JDK versions, so say "typically".

Related facts.

  • List.sort(cmp) and Collections.sort copy the list into an array, sort it, and write it back, so a LinkedList is sorted efficiently too.
  • Arrays.parallelSort splits the work across cores, useful for large arrays.
  • stream.sorted() is stable for ordered streams.
  • Sorting cost is O(n log n) comparisons, so an expensive comparator (parsing a string each time) dominates. Precompute a key if needed (Comparator.comparing(keyExtractor) still calls the extractor on every comparison).

When not to sort. If you need data to stay sorted as you insert, use a TreeSet/TreeMap or a heap. If you only need the top K, use a heap, O(n log K). If you need the smallest element once, a linear scan is enough.

Stable means equal elements keep their original relative order, which matters when sorting by one field after another, such as sorting by city after sorting by name. TimSort needs temporary space up to n/2 elements. List.sort copies the list to an array, sorts, and writes back. The sort on a plain list cannot beat O(n log n), so for "keep it sorted as I insert" a TreeSet or heap is better than repeated sorts.

Remember: objects: TimSort, stable. Primitives: dual-pivot quicksort, not stable.

9. Iterators, removal and immutability

What is a fail-fast iterator, and how does it work? Intermediate

Collections like ArrayList and HashMap keep a counter called modCount that increases on every structural change (add, remove, clear). An iterator remembers the value when it was created, and on each next() it compares. If they differ, it throws ConcurrentModificationException immediately. It fails fast to expose bugs early, instead of returning garbage later.

The problem it guards against. An iterator keeps a position inside the collection's internal structure (an array index, a bucket and node). If the collection is restructured behind its back, for example elements shift left after a removal or the hash table is rebuilt in a resize, the iterator's position no longer means what it did. It could skip elements, return one twice, or read freed slots. Rather than return silently wrong data, collections detect the change and stop.

How it works. Every structural modification (adding, removing, clearing, resizing) increments an int field called modCount in the collection. When you call iterator(), the iterator copies it into expectedModCount. The first thing next() does is if (modCount != expectedModCount) throw new ConcurrentModificationException(). The iterator's own remove() changes the collection and then sets expectedModCount = modCount, which is why that route is legal.

A single-thread example that surprises beginners.

List<String> names = new ArrayList<>(List.of("a", "b", "c"));
for (String s : names) {
    if (s.equals("a")) names.remove(s);   // modCount 1 -> 2, iterator expects 1
}                                         // next iteration: next() throws CME

No second thread is involved, so the name "Concurrent" modification is misleading: it means "modified while an iteration is in progress".

What counts as structural. Adding or removing elements, and resizing. Replacing an element (list.set) or a map's value for an existing key is not structural, so it does not trigger it.

Limits of the guarantee. The check is not synchronised, so with real threads the iterator might not see the new modCount and not throw, while still reading inconsistent data. The Javadoc says plainly that fail-fast behaviour cannot be guaranteed and should be used only to detect bugs, never to implement program logic. So you must not write code that catches ConcurrentModificationException as a control mechanism.

The three ways out. Use Iterator.remove() or removeIf for same-thread removal; use concurrent collections (weakly consistent iterators) for multi-thread access; or iterate over a copy (new ArrayList<>(list)) when you must modify the original in the loop, accepting the copy cost.

It is best effort, not a guarantee, and it is also not about threads only: the classic trigger is modifying the list inside a for-each loop in a single thread. set(i, x) on an ArrayList is not a structural change, so it does not trip it. Calling the iterator's own remove() is safe because it updates the expected count. Concurrent collections use weakly consistent iterators instead.

Remember: modCount versus expectedModCount, checked in next(). Remove only via the iterator.

Why does removing the second-to-last element in a for-each loop not throw? Senior

Because the exception is thrown in next(), not in hasNext(). After removing the second-to-last element, the size shrinks by one, so the cursor equals the size, hasNext() returns false, and the loop ends before next() ever checks modCount. Any other position throws on the next iteration.

Where the check lives. In ArrayList, hasNext() is simply cursor != size. It does not look at modCount. Only next() calls checkForComodification(). A for-each loop alternates hasNext() then next(), so the question is whether the loop gets to call next() again after the removal.

Trace with a list of 4: [a, b, c, d]. Remove "c" (the second to last) while at "c".

  1. Iteration visits a, b, c. After returning "c" the iterator's cursor is 3.
  2. The loop body removes "c": the list becomes [a, b, d], size = 3, modCount increased.
  3. Loop calls hasNext(): cursor (3) != size (3) is false. The loop ends. "d" was never visited, and no exception was thrown.

Now remove "a" instead (at the first element): cursor is 1, size becomes 3, hasNext() is true, next() sees the modCount mismatch and throws. Remove the last element "d": cursor is 4, size becomes 3, 4 != 3 is true, so hasNext() says yes, next() throws. Only the second-to-last position hides the problem.

The lesson, and a related silent bug. The code was wrong in all cases, since "d" was skipped; in one case Java just failed to tell you. The check is a convenience for catching bugs. The related silent bug: an index loop for (int i = 0; i < list.size(); i++) if (bad(list.get(i))) list.remove(i); throws nothing, but after each removal the next element moves into index i and is skipped, so two bad elements in a row leave one behind. Fix by iterating backwards, decrementing i after a removal, or using removeIf.

Why an interviewer asks this. It tests whether you know the mechanism (check in next(), based on modCount) rather than the slogan "it always throws". The right closing sentence: "never rely on the exception, remove through the iterator or removeIf".

This shows the fail-fast check is a best-effort bug detector, not a safety guarantee, so I must never rely on it, or on its absence, for correctness. Just as bad, removing by index inside a plain index loop never throws but skips the element after each removal, because elements shift left. The correct tools are Iterator.remove() or removeIf.

Remember: the check lives in next(). Quirks like this are why fail-fast is only a hint.

What is the right way to remove elements while looping? Basic

Use removeIf if the rule is a simple condition, or an explicit Iterator and call it.remove(). Never call list.remove inside a for-each. For a map, use map.entrySet().removeIf(...) or map.keySet().removeIf.

Three safe patterns, and when to use each.

SituationUse
Remove everything matching a conditionremoveIf(predicate)
Need to inspect and decide in a loop, or do other work as wellexplicit Iterator with it.remove()
Keep a subset in a new collection, leave the originalstream().filter(...).toList() or collect

Why it.remove() works but list.remove() does not. The iterator knows its own position. When it removes the element it just returned, it adjusts its cursor and refreshes its expected modification count, so it stays consistent with the list. Removing through the list changes the list without telling the iterator, and the next next() detects the mismatch.

The performance difference. Removing one element from an ArrayList shifts all later elements left: O(n). Removing k elements one at a time, with remove(i) or it.remove() on an ArrayList, can therefore be O(n * k), up to O(n squared). ArrayList.removeIf is smarter: it first marks the matching elements, then compacts the array in one pass, so it is O(n) total. For 100,000 elements with 50,000 removals the difference is minutes versus milliseconds. On a LinkedList it.remove() is O(1) per removal, but the node overhead usually outweighs it.

Maps and sets. map.entrySet().removeIf(e -> e.getValue() == null), map.keySet().removeIf(...), map.values().removeIf(...). All are views, so removal writes through to the map.

Other cases.

  • Removing while iterating over a CopyOnWriteArrayList or ConcurrentHashMap does not throw, since their iterators are snapshot or weakly consistent. The CopyOnWrite iterator does not support its own remove(), but you can call list.remove on the list.
  • Removing by position from the end is cheap: list.subList(from, size).clear() removes a tail range at once.
  • If the elements must be removed from an immutable list, create a new list: immutable lists throw UnsupportedOperationException.
list.removeIf(x -> x.isExpired());
map.entrySet().removeIf(e -> e.getValue() < 0);

for (Iterator<Item> it = list.iterator(); it.hasNext(); ) {
    if (it.next().bad()) it.remove();
}

ArrayList.removeIf is also faster: one pass, O(n), whereas calling remove(i) repeatedly shifts the array each time, giving O(n squared). Another option is to collect the survivors into a new list with a stream filter. A for-each over a concurrent collection is safe, as those iterators are weakly consistent.

Remember: removeIf or Iterator.remove(). Never remove inside for-each.

What is the difference between unmodifiable and immutable collections, and how do I return a collection from a class safely? Intermediate

Unmodifiable means "I cannot change it through this reference", but it is a view, so whoever owns the underlying list can still change what I see. Immutable means nobody can change it. When a class returns its internal list, I return List.copyOf(items) (a snapshot), or an unmodifiable view if I want callers to see later changes, and I copy on the way in too.

Why the question matters: encapsulation. A class that stores a list and returns it from a getter has given the caller a remote control for its internal state. Any code that calls order.getItems().clear() bypasses every rule the class enforces (a total, a limit, a status check).

Three levels of protection, from weakest to strongest.

  1. Return the list itself. Caller can mutate it. Bad.
  2. Return Collections.unmodifiableList(items). The caller cannot change it through this reference. But it is a live view, so it also reflects the owner's later changes (maybe even mid-loop), and any other holder of the underlying list can still change it. Cheap: no copying.
  3. Return List.copyOf(items). A frozen snapshot, safe to keep, cache or share with other threads. Costs a copy of the references, O(n), but if the source is already an immutable List.of list, no copy is made.

The input side, with a bug example. A constructor takes a list and stores the reference.

List<Item> mine = new ArrayList<>(List.of(a, b));
Order o = new Order(mine);      // Order stores 'mine' directly
mine.add(freeGift);             // the caller changes the order's contents later

Copying on the way in (this.items = List.copyOf(in)) closes this hole. This pairing, copy in and copy out, is called defensive copying. Note that List.copyOf throws on null elements, so validate first or choose new ArrayList<>(in) if nulls are legal.

Deep versus shallow. All of the above freeze the list structure, not the objects inside. If Item has a setter, the caller can still do order.items().get(0).setPrice(0). For a truly immutable aggregate the elements must be immutable too (records with final fields, immutable value classes, or copies of the elements).

Which to pick. Immutable copy for safety and thread sharing. Unmodifiable view when the collection is large and you deliberately want callers to see updates, and you accept the aliasing. Also useful: Collections.emptyList() and List.of() return shared instances, so the empty case allocates nothing.

This is defensive copying. Without it a caller can mutate my internal state, or a constructor argument that I stored can be changed behind my back, breaking my class invariants. Both unmodifiable views and immutable collections are only shallow: if the elements are mutable, they can still change, so the elements also need to be immutable for true safety. Collections.emptyList() and List.of() avoid allocating for the empty case.

public List<Item> items() { return List.copyOf(items); }   // snapshot
public Order(List<Item> in) { this.items = List.copyOf(in); }  // copy on the way in

Remember: view versus copy. Copy in, copy out, and keep elements immutable too.

What are sequenced collections in Java 21? Intermediate

Java 21 added the interfaces SequencedCollection, SequencedSet and SequencedMap for collections with a defined encounter order. They give uniform getFirst(), getLast(), addFirst, addLast, removeFirst, removeLast and reversed() on List, Deque, LinkedHashSet, LinkedHashMap, TreeSet and TreeMap. Before, getting the last element of different collections needed different code.

The gap it fills. Before Java 21, getting the first or last element of an ordered collection was inconsistent. A List: list.get(list.size() - 1) (and get(0) on an empty list gives an IndexOutOfBoundsException). A Deque: getLast(). A LinkedHashSet: no direct method, you had to iterate or stream the whole set. A SortedSet: last(). A LinkedHashMap: nothing at all for the last entry. Reversing iteration needed Collections.reverse on a copy, or a descending iterator on a Deque only. Java 21 (JEP 431) added three interfaces that put one vocabulary on every collection that has a defined encounter order.

The interfaces.

  • SequencedCollection: getFirst(), getLast(), addFirst(e), addLast(e), removeFirst(), removeLast(), reversed(). Parent of List and Deque.
  • SequencedSet: the same for sets with an order (LinkedHashSet, SortedSet and TreeSet).
  • SequencedMap: firstEntry(), lastEntry(), pollFirstEntry(), putFirst, putLast, reversed(), and sequenced views of keys, values and entries.

Examples.

List<String> l = new ArrayList<>(List.of("a", "b", "c"));
l.getLast();            // "c"   (instead of l.get(l.size() - 1))
l.reversed();           // view: c, b, a  (no copy); changes write through
LinkedHashSet<String> s = new LinkedHashSet<>(l);
s.getFirst();           // "a"
LinkedHashMap<String,Integer> m = new LinkedHashMap<>();
m.putFirst("z", 0);     // puts at the front (new in 21)

Behaviour details. getFirst() and getLast() on an empty collection throw NoSuchElementException. Methods that cannot be honoured throw UnsupportedOperationException: addFirst on a sorted set (the position is dictated by the comparator), any modification of an immutable list. reversed() is a view, so changes to the original show in it. HashSet and HashMap are not sequenced, since their order is arbitrary.

Compatibility warning. Adding methods to interfaces can clash with your own subclass or utilities that already define getFirst or reversed with a different return type. Check when you upgrade. You need Java 21 or later, so on Java 17 you still write the old idioms.

reversed() returns a live view, not a copy. getFirst() on an empty list throws NoSuchElementException. HashSet and HashMap are not sequenced since they have no order, and List.of style immutable collections throw on addFirst. I would mention this as a convenience that removes the old list.get(list.size() - 1) idiom, and that it needs Java 21 or later.

Remember: Java 21: getFirst, getLast and reversed() across ordered collections. reversed() is a view.

10. Streams over collections (short)

How do I turn a list into a Map or group it with streams, and what goes wrong? Intermediate

Use Collectors.toMap(keyFn, valueFn) for one value per key and Collectors.groupingBy(fn) for a list per key. The big trap is that toMap throws IllegalStateException: Duplicate key when two elements produce the same key, so I pass a merge function as the third argument if duplicates are possible.

What a collector does. A stream produces elements one by one. A Collector describes how to gather them into a result: a list, a set, a map, a count, a string. stream.collect(collector) does the gathering. The two you use most for maps are toMap and groupingBy.

toMap: one value per key. You give a function for the key and one for the value. If two elements yield the same key, toMap cannot know which value wins, so by default it throws IllegalStateException: Duplicate key X (attempted merging values A and B). The third argument is a merge function that decides. It is the single most common stream bug in production data jobs, since the test data usually has unique keys.

// users: (1,"Asha"), (2,"Bela"), (1,"Asha-new")
users.stream().collect(Collectors.toMap(User::id, User::name));                  // throws
users.stream().collect(Collectors.toMap(User::id, User::name, (a, b) -> b));     // keep last
users.stream().collect(Collectors.toMap(User::id, User::name, (a, b) -> a + "," + b)); // join

groupingBy: a list (or other result) per key. The key function classifies each element, and a downstream collector says what to do with each group. The default downstream is toList().

Map<String, Long> perCity = users.stream()
    .collect(Collectors.groupingBy(User::city, Collectors.counting()));
Map<String, Set<String>> namesByCity = users.stream()
    .collect(Collectors.groupingBy(User::city, TreeMap::new,
             Collectors.mapping(User::name, Collectors.toSet())));
Map<Boolean, List<User>> adults = users.stream()
    .collect(Collectors.partitioningBy(u -> u.age() >= 18));

The second one shows the 3-argument form with a map factory (TreeMap::new for sorted keys) and mapping to transform values before collecting. partitioningBy is a special grouping into exactly two groups, true and false, both always present.

More points to know. toMap throws NullPointerException if a value is null (it uses merge internally), while groupingBy rejects a null key ("element cannot be mapped to a null key"). The resulting map type is unspecified: you get a HashMap in practice, so ask for LinkedHashMap::new if you need order. For a concurrent or parallel stream, toConcurrentMap and groupingByConcurrent exist. Stream.toList() (16) is shorter and unmodifiable.

Map<Long, User> byId = users.stream()
    .collect(Collectors.toMap(User::id, u -> u, (a, b) -> a)); // keep first

Map<String, List<User>> byCity = users.stream()
    .collect(Collectors.groupingBy(User::city));

Map<String, Long> count = users.stream()
    .collect(Collectors.groupingBy(User::city, Collectors.counting()));

Other points: toMap also throws NullPointerException on a null value. The result is a plain HashMap unless I pass a map supplier (for example TreeMap::new or LinkedHashMap::new). Stream.toList() (Java 16) returns an unmodifiable list and allows nulls, while Collectors.toList() gives a modifiable list in practice, but its type is not guaranteed.

Remember: toMap needs a merge function for duplicates. groupingBy makes lists, counting makes totals.

11. Choosing, complexity and memory

Give me the time complexity of the common collections. Basic

Array-backed lists are fast at index access and appending. Hash-based sets and maps give O(1) average lookup. Tree-based ones give O(log n) but keep order. Heaps give O(1) peek and O(log n) insert and remove. Linked lists are slow at everything except the ends.

What the notation is telling you. Big-O describes how the cost grows as n grows, ignoring constants. O(1): the cost does not depend on n (one array index). O(log n): each step halves the problem (tree descent, binary search), so a million items need about 20 steps. O(n): looks at every element once. O(n log n): sorting. It says nothing about how fast one operation is at one particular size.

Where each number comes from.

  • ArrayList.get(i) is O(1): a slot index calculation. contains is O(n): it compares with each element until it finds one.
  • ArrayList add at the end is amortised O(1): occasional O(n) copy on growth, spread across many adds. Middle insert: shift the tail, O(n).
  • LinkedList get(i) is O(n): walk from the nearer end. Insert at an end is O(1): rewire pointers.
  • HashMap or HashSet: O(1) expected if the hash spreads well. Worst case O(log n) with trees in Java 8+.
  • TreeMap or TreeSet: O(log n) for everything, because of tree height.
  • PriorityQueue: peek O(1); offer and poll O(log n) (sift up or down the height); remove(Object) and contains O(n).
  • ArrayDeque: O(1) at both ends.

Amortised, expected, worst: three different promises. Amortised O(1) (ArrayList add) means the average over a long sequence of operations, even though a single operation may be slow. Expected O(1) (HashMap) means on average over the randomness of the hash, with a worst case possible. Worst-case O(log n) (TreeMap) holds for every single operation.

Examples where the table misleads.

  • For 10 elements, ArrayList.contains (a short linear scan over contiguous memory) can beat HashSet.contains (hash computation, pointer chasing).
  • A HashMap<Integer,Integer> and an int[] are both "O(1)" lookups, but the array is ten times faster and a fifth of the memory.
  • A LinkedList insert in the middle is "O(1) after reaching the spot", but reaching the spot is O(n) and cache-hostile, so ArrayList often wins.

How to answer. Give the table, then add "and for small n or hot paths I would measure, because constants, boxing and cache behaviour decide". Interviewers hear that as experience.

How do I choose the right collection for a problem? Intermediate

I ask four questions in order: do I look things up by key or just iterate, do I need uniqueness, do I need an order (insertion, sorted, priority), and do several threads touch it. The answers point to one class almost every time.

The thinking process, as a short script. You are given a requirement. Ask in this order:

  1. Is it key to value? Yes: a Map. No: a Collection.
  2. Are duplicates allowed, and do I need positions? Positions or duplicates: List. Uniqueness: Set.
  3. Which order do I need? None: hash-based (fastest). Insertion or access order: Linked variant. Sorted or range queries: Tree variant. Processing order (FIFO, LIFO, priority): Queue, Deque or PriorityQueue.
  4. Is it shared across threads, and how? Many readers, few writers: copy-on-write or an immutable snapshot. Many writers: ConcurrentHashMap or a concurrent queue. Handing work between threads: a bounded BlockingQueue.
  5. How big, and what are the elements? Millions of numbers: primitive arrays. Enum keys: EnumMap or EnumSet. Known size: pre-size.

Fixed read-only data: List.of. Then I check the key quality (immutable, good hashCode) and the expected size, so I can pre-size.

Remember: key? unique? ordered? shared? Those four questions pick the class.

How much memory does a List<Integer> or a HashMap really use? Senior

A lot more than the raw data. An int[] uses 4 bytes per number. An ArrayList<Integer> uses 4 bytes per reference plus a separate 16-byte Integer object, so about 5 times more, and the objects are scattered on the heap, hurting CPU cache speed and adding GC work. A HashMap entry costs about 32 bytes for the node, plus 4 or so for the table slot, on top of the key and value objects.

Counting bytes, from scratch. On a 64-bit HotSpot JVM with compressed ordinary object pointers (the default for heaps below about 32 GB), a reference is 4 bytes, and every object has a header of about 12 bytes, with sizes rounded up to a multiple of 8. Therefore:

  • Integer: header 12 + value 4 = 16 bytes. Long: 12 + 8 = 20, rounded up to 24 bytes.
  • int[1000]: 16-byte array header + 4,000 = about 4 KB.
  • ArrayList<Integer> of 1,000: its array of 4-byte references (about 4 KB) plus 1,000 Integer objects at 16 bytes (16 KB) = about 20 KB, five times the primitive array. Values from -128 to 127 are shared cache objects, so only larger values cost the extra.

HashMap entry cost. Each entry is a HashMap.Node object: header 12, hash 4, key 4, value 4, next 4 = 28, rounded to 32 bytes. Add 4 bytes of table slot per entry at 0.5 to 0.75 load (so about 6 to 8 bytes after load factor), and the key and value objects themselves. For a HashMap<Integer,Integer> with values beyond the cache: 32 + 16 + 16 + roughly 8 = about 70 to 75 bytes per entry. A million entries is therefore roughly 70 to 80 MB, versus about 8 MB for two parallel int[] arrays. A TreeMap node is larger still (about 40 bytes) and LinkedHashMap adds 8 more bytes of pointers.

Other hidden costs.

  • Empty collections still cost: an ArrayList object plus its array, a HashMap object (about 48 bytes) plus a 16-slot table once used. A million small maps are a large heap.
  • Over-allocated capacity: an ArrayList can have up to 50 percent unused slots. A hash table at load 0.75 right after a resize is about 38 percent full.
  • GC: millions of small objects mean more marking work, longer pauses and worse cache locality, since objects are scattered.

Ways to reduce it. Primitive arrays or specialised collections (fastutil's Int2IntOpenHashMap, Eclipse Collections, Trove-style maps), an EnumMap for enum keys, BitSet for sets of small ints, a single sorted array with binary search for read-only maps, storing records in arrays of structures only when needed, and sharing immutable instances. To check rather than guess, measure with a heap histogram (jmap -histo), Java Object Layout (JOL), or a profiler. These figures vary with JVM flags and version, so quote them as approximate.

That means a HashMap<Integer, Integer> with a million entries can take roughly 70 to 80 MB, mostly overhead. All numbers are approximate for a 64-bit JVM with compressed pointers. Ways to cut it: use primitive arrays or a primitive-specialised library (fastutil, Eclipse Collections) for large numeric data, use an EnumMap for enum keys, avoid keeping many tiny collections, and pre-size to avoid slack. Small Integer values from -128 to 127 are cached, which hides the cost in toy tests.

Remember: boxed collections cost around 5x the raw data, plus GC and cache misses.

12. Common coding questions with solutions

Count word frequency and find duplicates in a list. Basic

I walk the list once and count in a HashMap using merge. That is O(n) time and O(unique) space. Duplicates are the entries with a count above one. For "does it contain a duplicate" I can instead stop at the first failed Set.add.

The idea. Counting how often each distinct item appears is the "histogram" problem, and a hash map is the natural tool: the key is the item, the value is its count so far. For each item you look it up (O(1)), add one, and store it back. One pass over n items is O(n) time. Space is the number of distinct items.

Trace. words = [to, be, or, not, to, be]. Start with an empty map.

Duplicates are the entries with count above 1: to and be.

Why merge. freq.merge(w, 1, Integer::sum) means "if absent store 1, otherwise store old + 1". One lookup, no null check, and no boxing mistakes with get returning null. The older way, freq.put(w, freq.getOrDefault(w, 0) + 1), also works but does two lookups.

Variants an interviewer might ask for.

  • "Is there any duplicate?" Stop early with if (!seen.add(x)) return true;. Space is O(n) in the worst case.
  • "Find the first non-repeating character." Count with a LinkedHashMap (or an int[26] for lowercase letters), then scan in the original order for count 1.
  • "No extra memory?" Sort and compare neighbours, O(n log n) time and O(1) extra space. Or, if values are in 1..n, mark visited indexes in the array itself.
  • "Stream version": words.stream().collect(Collectors.groupingBy(Function.identity(), Collectors.counting())).

Say aloud: case sensitivity, punctuation and normalisation (toLowerCase) are decisions to confirm with the interviewer.

List<String> dups = freq.entrySet().stream()
    .filter(e -> e.getValue() > 1).map(Map.Entry::getKey).toList();

// quick check: add() returns false if already present

Set<String> seen = new HashSet<>();

The stream form is groupingBy(w -> w, counting()). If I must keep first-seen order, use a LinkedHashMap. If the input is huge and has few distinct values, memory is the number of distinct values, not n.

Remember: frequency is a HashMap with merge. Duplicate check is a HashSet add that returns false.

Group a list of objects by a field without streams. Basic

A Map from the field to a list, filled with computeIfAbsent. It creates the list the first time a key appears and then I add to it. One pass, O(n).

The idea. Grouping means building a map from a category to the list of things in that category. With an Employee list and the department as the category you get {HR=[e1, e4], IT=[e2, e3, e5]}. Do it in one pass: for each item, find its group, creating the group the first time you meet that key.

What computeIfAbsent is doing. It is a "get or create" operation. byDept.computeIfAbsent("IT", d -> new ArrayList<>()) returns the existing list for IT if present, or runs the function, stores the new empty list and returns it. Either way you receive the list and call .add(e) on it. Without it you would write four lines: get, check null, create, put, then add.

// the old way
List<Employee> g = byDept.get(e.dept());
if (g == null) { g = new ArrayList<>(); byDept.put(e.dept(), g); }
g.add(e);

Trace. Staff: (Asha, IT), (Bela, HR), (Chen, IT). First item: no key IT, creates [], adds Asha, giving {IT=[Asha]}. Second creates HR. Third finds IT and appends, giving {IT=[Asha, Chen], HR=[Bela]}.

Which map to use. HashMap for no order, LinkedHashMap if groups should appear in first-seen order, TreeMap for sorted keys. The group container can be a Set (HashSet::new) to also remove duplicates.

Classic follow-up: group anagrams. Two words are anagrams if their sorted letters are equal. Use the sorted letters as the key: String key = new String(sortedChars), then computeIfAbsent(key, k -> new ArrayList<>()).add(word). "eat", "tea", "ate" all map to "aet". Time O(n * L log L) for n words of length L. A faster key for lowercase words is a 26-count signature.

Pitfall. The key class needs correct equals/hashCode, and the key must not be mutated later.

Map<String, List<Employee>> byDept = new HashMap<>();
for (Employee e : staff) {
    byDept.computeIfAbsent(e.dept(), d -> new ArrayList<>()).add(e);
}

Use TreeMap if the groups must come out sorted by key, LinkedHashMap for first-seen order. The stream version is Collectors.groupingBy(Employee::dept). A classic variant is grouping anagrams: the key is the sorted characters of each word.

Remember: computeIfAbsent(key, k -> new ArrayList<>()).add(x) is the grouping idiom.

Two sum: find two numbers that add up to a target. Basic

One pass with a HashMap from value to index. For each number I check whether target - n was already seen. If yes, I have the pair, otherwise I store this number. That is O(n) time and O(n) space, compared with O(n squared) for two nested loops.

The brute force and why we improve on it. Check every pair: two nested loops, O(n squared). For 100,000 numbers that is five billion checks. The question to ask is: for the current number x, what do I need? Exactly target - x. If I could look up "have I already seen the value target - x?" in O(1), one pass suffices. A hash map answers that.

Find the K most frequent elements. Intermediate

Count with a HashMap, then keep a min-heap of size K ordered by count. Each element costs O(log K), so total time is O(n log K) and space O(n). It beats sorting all distinct values (O(d log d)) when K is small.

Two stages. First count (a HashMap, O(n)). Then choose the K entries with the largest counts. The second stage is the "top K" problem from the PriorityQueue question, applied to the map entries, with the count as the priority.

Trace. words = [a, b, a, c, b, a, d], K = 2. Counts: a=3, b=2, c=1, d=1. Heap keyed by count (smallest count at the root), size capped at 2:

  1. offer a(3): heap [a3].
  2. offer b(2): heap [b2, a3].
  3. offer c(1): size 3 > 2, so poll the smallest, c1. Heap [b2, a3].
  4. offer d(1): poll d1. Final heap holds b2 and a3.

Each of d distinct words costs O(log K), so O(n + d log K), usually written O(n log K). The heap never holds more than K entries.

Getting a nice ordered answer. Polling the min-heap yields the K items from least to most frequent, so fill a list from the back, or reverse it at the end.

The O(n) bucket-sort version. A count can be at most n, so make an array of lists bucket[0..n] where bucket[c] holds the words with count c. Fill it in one pass over the map, then scan from the highest index down collecting words until you have K. Time O(n), space O(n). Mention it when the interviewer says "can you do better than n log K?".

Edge cases to say aloud. Ties at the K-th place (include all or an arbitrary one, or break by alphabet: add thenComparing on the word). K larger than the number of distinct items. An empty input. A stream that does not fit in memory: use an approximate method (Count-Min Sketch plus a heap), a point that shows seniority.

Map<String, Integer> freq = new HashMap<>();
for (String w : words) freq.merge(w, 1, Integer::sum);

PriorityQueue<Map.Entry<String, Integer>> heap =
    new PriorityQueue<>(Map.Entry.comparingByValue());      // min-heap by count
for (Map.Entry<String, Integer> e : freq.entrySet()) {
    heap.offer(e);
    if (heap.size() > k) heap.poll();
}
// heap holds the k most frequent (in no particular order)

If counts are bounded by n, a bucket sort (index = count) gives O(n). The interviewer often asks for this follow-up. State ties explicitly: add a secondary key (such as alphabetical) if output must be deterministic.

Remember: count with a map, then a size-K min-heap. Bucket sort if you need O(n).

Implement an LRU cache by hand (get and put in O(1)). Senior

I combine a HashMap for O(1) lookup with a doubly linked list that keeps usage order. The map points from key to list node. On every get or put, I move the node to the front (most recent). When the capacity is exceeded, I remove the node at the tail (least recent) and delete its key from the map. Both structures are needed: the map alone has no order, the list alone has no fast lookup.

What you are building. A cache with a fixed capacity where get and put are both O(1) and, when full, the least recently used entry is dropped. The difficulty is doing two things in constant time: find an entry by key, and find / move the entry that is oldest by use.

Why exactly these two structures.

  • A HashMap gives O(1) lookup from key to node, but has no notion of recency.
  • A doubly linked list keeps entries in recency order: most recent at the head, oldest at the tail. Because it is doubly linked, and we hold the node reference from the map, we can unlink any node in O(1) without searching.
  • A singly linked list or an array would need O(n) to unlink or shift.

Details that get tested.

  • Sentinel nodes (dummy head and tail) mean unlink and insert never have to special-case an empty or one-element list.
  • The node must store its key, because when you evict the tail node you need its key to delete the map entry.
  • put on an existing key updates the value and moves it to the front, with no eviction and no size change.
  • Capacity 0 or negative should be rejected, and null values should be defined (is "absent" null?).

Threading and variants. Both get and put modify the list, so a single lock (or synchronized methods) is the simple answer. For scale, use Caffeine, or a sharded set of LRUs. LFU needs frequency counts: a map from key to node plus a map from frequency to a list. In Java, the shortcut is LinkedHashMap(accessOrder = true) with removeEldestEntry, but be ready to build it manually when asked.

class LRU<K, V> {
    class Node { K k; V v; Node prev, next; }
    private final int cap;
    private final Map<K, Node> map = new HashMap<>();
    private final Node head = new Node(), tail = new Node();   // sentinels
    LRU(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }

    V get(K k) {
        Node n = map.get(k);
        if (n == null) return null;
        unlink(n); addFirst(n); return n.v;
    }
    void put(K k, V v) {
        Node n = map.get(k);
        if (n != null) { n.v = v; unlink(n); addFirst(n); return; }
        if (map.size() == cap) { Node last = tail.prev; unlink(last); map.remove(last.k); }
        n = new Node(); n.k = k; n.v = v; map.put(k, n); addFirst(n);
    }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFirst(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}

Sentinel head and tail nodes remove all null checks. The node must store its key so the map entry can be deleted on eviction. For multiple threads, I would lock the whole structure (reads mutate it) or use Caffeine.

Remember: HashMap for lookup plus doubly linked list for recency. Node stores its key.

Sort a map by value, or get the entry with the highest value. Intermediate

A map cannot be sorted in place, so I sort its entries and collect into a LinkedHashMap that remembers the order. For just the maximum, I do not sort at all: a single pass with Collections.max on the entries is O(n).

Why maps are not "sorted" in place. A HashMap has no order to change. TreeMap has an order, but it is always by key, and cannot be sorted by value, because looking up by key requires the key order. So "sort a map by value" really means "produce an ordered sequence of the entries by value", and to keep that order in a map-like container you need LinkedHashMap, which iterates in insertion order.

Steps.

  1. Take the entries: map.entrySet().stream().
  2. Sort with a comparator on the value, such as Map.Entry.comparingByValue() (ascending) or with Comparator.reverseOrder() as an argument (descending).
  3. Collect into a LinkedHashMap. The 4-argument toMap needs a merge function (never used here since keys are unique) and the map supplier LinkedHashMap::new.
Map<String,Integer> sorted = map.entrySet().stream()
    .sorted(Map.Entry.comparingByValue(Comparator.reverseOrder()))
    .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue,
                              (a, b) -> a, LinkedHashMap::new));
// {pear=9, kiwi=4, fig=4, apple=1}   ties: input order (the sort is stable)

Using comparingByValue(Comparator.reverseOrder()) avoids the generic type-witness noise of comparingByValue().reversed().

Ties and secondary order. To sort by value then by key, use .thenComparing(Map.Entry.comparingByKey()), with the type witness needed in some forms.

If you only want one or few results. The maximum: Collections.max(map.entrySet(), Map.Entry.comparingByValue()).getKey(), O(n). The top 3: a min-heap of size 3, O(n log 3). Sorting everything is O(n log n) and wasteful for that.

Mistakes. Collecting into a normal HashMap (order lost). Sorting by getValue with a subtraction comparator (overflow). Mutating the map while its entries are being streamed. Expecting the sorted LinkedHashMap to stay sorted after later put calls: it keeps insertion order, not value order.

Map<String, Integer> sorted = map.entrySet().stream()
    .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
    .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue,
             (a, b) -> a, LinkedHashMap::new));

Map.Entry<String, Integer> top =
    Collections.max(map.entrySet(), Map.Entry.comparingByValue());

Collecting into a plain HashMap would throw away the order, which is a common mistake. A TreeMap sorts by key only, never by value. Sorting is O(n log n). For the top few, use the heap approach.

Remember: sort the entries, collect into a LinkedHashMap. For the max, just scan.

Implement a simple HashMap with chaining. Senior

An array of buckets, each a linked list of key-value nodes. put hashes the key to an index, walks the chain to update an existing key or adds a new node, and get walks the chain with equals. When the size passes load factor times capacity, I double the array and re-insert every node.

What the interviewer wants to see. That you understand the three essential mechanisms: turning a hash into a bucket index, resolving collisions with a chain compared using equals, and growing the table when it gets full. Everything else is optional polish.

Step by step through the code.

  1. idx(key, n): take hashCode (0 for null), fold the high bits in, and AND with n-1. This requires n to be a power of two, which is why the table starts at 16 and only doubles.
  2. get: jump to table[idx] and walk the linked chain until a node whose key equals the argument. If the chain ends, return null.
  3. put: walk the same chain. If a key matches, overwrite its value and return (size unchanged). Otherwise create a node and link it at the head (simplest, O(1)) and increase size.
  4. Resize: after an insertion, if size > 0.75 * capacity, allocate an array of double length and re-insert every existing node. Because the index depends on the table length, you must recompute it (or use the one-bit trick that the real HashMap uses).

Trace. Capacity 4 (to keep the example small), keys with indexes: "a"->1, "e"->1, "b"->2. put a: bucket 1 = [a]. put e: bucket 1 = [e, a] (head insert, collision). put b: bucket 2 = [b], size 3 which is not above 3 (0.75 x 4), so no resize. put c: size 4 > 3, resize to 8; every node is re-inserted using hash & 7.

Honest list of what is missing, which you should say. remove (walk the chain with a previous pointer), iteration and size() accessor, null-safe value handling, thread safety, tree buckets for long chains, a custom load factor and initial capacity, and fail-fast iterators. A generic array creation produces an unchecked warning, which is why @SuppressWarnings appears.

Likely follow-ups. "What if all keys collide?" O(n) per operation unless buckets become trees. "Why power-of-two sizes?" the mask trick. "Why store the hash in the node?" avoid recomputation on resize and speed up comparisons (the real HashMap does that, this simplified version does not). "How would you add remove?" keep a pointer to the previous node while walking the chain, then relink.

class MyMap<K, V> {
    static class Node<K, V> { final K k; V v; Node<K, V> next;
        Node(K k, V v, Node<K, V> n) { this.k = k; this.v = v; this.next = n; } }
    private Node<K, V>[] table = new Node[16];
    private int size;

    private int idx(Object k, int n) {
        int h = k == null ? 0 : k.hashCode();
        return (h ^ (h >>> 16)) & (n - 1);
    }
    V get(Object k) {
        for (Node<K, V> n = table[idx(k, table.length)]; n != null; n = n.next)
            if (Objects.equals(n.k, k)) return n.v;
        return null;
    }
    void put(K k, V v) {
        int i = idx(k, table.length);
        for (Node<K, V> n = table[i]; n != null; n = n.next)
            if (Objects.equals(n.k, k)) { n.v = v; return; }
        table[i] = new Node<>(k, v, table[i]);          // insert at head
        if (++size > table.length * 0.75) resize();
    }
    @SuppressWarnings("unchecked")
    private void resize() {
        Node<K, V>[] old = table;
        table = new Node[old.length * 2];
        for (Node<K, V> head : old)
            for (Node<K, V> n = head; n != null; n = n.next) {
                int i = idx(n.k, table.length);
                table[i] = new Node<>(n.k, n.v, table[i]);
            }
    }
}

Say what is missing: remove, thread safety, tree buckets, and iteration. The point of the exercise is the index mask, the equals check inside the chain, and the resize.

Remember: hash, mask, walk the chain with equals, double at 75 percent and re-insert.

A service on Java 7 sits at 100 percent CPU on one core, and thread dumps show threads stuck in HashMap.get. What happened? Senior

Most likely a shared, unsynchronised HashMap was resized by two threads at once, which in Java 7 can form a cycle in a bucket chain, so a later get loops forever. I confirm with thread dumps, restart to recover, and replace the map with ConcurrentHashMap.

Why this is a distinctive symptom. Most concurrency bugs give wrong answers or exceptions. A HashMap cycle gives neither: threads simply never come back. That is why CPU stays high and nothing is logged. The giveaway in the thread dumps is a thread in state RUNNABLE inside HashMap.get, HashMap.put or HashMap.transfer, with the same line number in every dump taken seconds apart. A healthy get finishes in microseconds, so seeing it in three consecutive dumps cannot be a coincidence.

The mechanism is explained in the Java 7 infinite loop question: a resize that reverses a chain can, when run by two threads simultaneously, leave two nodes pointing at each other, and any lookup that walks that bucket and does not find its key circles forever. The more threads reach that bucket, the more cores get stuck, so a single bad resize can take the whole service down gradually.

Additional steps to mention. Take the dumps with jstack -l pid or jcmd pid Thread.print, also capture a heap dump if allowed, find the owner of the map (a static field, a singleton cache), and check the Java version in the process arguments. Rolling restart to restore service is the immediate action since the cycle survives in memory. After the fix, prove it: write a stress test with many threads doing puts and gets on a cold map.

Situation: after a traffic spike, requests hang and a core is pinned. A static HashMap is used as a shared cache with no locking.

Check first: take three thread dumps a few seconds apart (jstack or jcmd Thread.print). The same threads in HashMap.get or HashMap.transfer with an identical stack each time means an endless loop.

Fix: the cycle is permanent in memory, so restart. Then use ConcurrentHashMap (with computeIfAbsent for loading). Moving to Java 8 removes this exact cycle, but the map can still lose entries.

Prevent: a review rule that any static or singleton-held collection is concurrent or guarded, plus static analysis and multi-threaded load tests.

Remember: same stack in HashMap in several dumps means a cycle. Shared maps must be concurrent.

Under load, a shared HashMap counter ends up with fewer entries or lower counts than expected, with no exception. Why? Intermediate

Concurrent unsynchronised writes to a HashMap race with each other: two threads overwrite the same bucket slot or both do read-modify-write on a count, so updates are lost silently. The fix is ConcurrentHashMap with an atomic merge.

Why silent loss happens. A HashMap put is several steps: find the bucket, read its head, create a node, write it into the slot. Suppose two threads put different keys that fall in the same empty bucket. Both read the bucket as empty, both create a node and write it: the second write overwrites the first, so the first key vanishes. No exception, no log. A counter that does put(k, get(k) + 1) has the read-modify-write race described earlier: two threads read 41, both write 42. A resize running at the same time can also drop whole chains, because one thread's nodes are moved into a table that another thread then replaces.

Why it appears only under load. With a single thread, or with low traffic, the interleaving is rare. Under load the probability of two threads overlapping on a bucket or a key is high, and the loss rate grows with concurrency. That is why unit tests pass and production shows 9,870 out of 10,000.

How to prove it. Write a test with, say, 32 threads each calling merge 100,000 times on a few keys, and compare the total against 3,200,000. The unsynchronised map gives fewer, and the concurrent map gives exactly the expected number. The test becomes the regression guard.

Choosing the fix. ConcurrentHashMap.merge for a per-key counter. LongAdder values when a few keys are extremely hot (it stripes the count across cells). AtomicLong if there are very few fixed keys. A synchronized block if the update touches several keys together.

Situation: a metrics map shows 9,870 hits where 10,000 requests were made. Some runs also show missing keys.

Check first: is the map shared across threads? Is the update map.put(k, map.get(k) + 1)? That is a read-modify-write that two threads can interleave, and the resize can also drop nodes.

Fix: ConcurrentHashMap plus map.merge(k, 1, Integer::sum). For very hot counters, use ConcurrentHashMap<K, LongAdder> and computeIfAbsent(k, x -> new LongAdder()).increment(). A synchronized block works but serialises everything.

Prevent: a concurrent test that hammers the map from many threads and checks the total.

Remember: silent loss, no exception, is the signature of unsynchronised writes. Use atomic merge.

A service slowly runs out of memory, and a heap dump shows a huge static HashMap or List. How do you handle it? Intermediate

A static collection that only ever grows is a memory leak, because the garbage collector cannot free anything it still references. I find it in the heap dump, then bound it with an eviction policy or remove entries when they are done.

What "leak" means in Java. The garbage collector frees objects that cannot be reached from a GC root (static fields, thread stacks, and so on). A static map is a root. Everything the map references, directly or through its values, stays alive for the life of the class. If the code only adds and never removes, the retained size only grows. It is not "lost memory" in the C sense, it is memory you still hold by accident.

How the pattern looks in practice. A "temporary" cache keyed by request id, session id or user id that is filled on every request and cleaned up only on a happy path. Listener lists never unregistered. Thread-local maps holding per-request data in pooled threads. Per-tenant maps that never forget a tenant. The sawtooth in the GC log is the clue: each full GC reclaims less, the post-GC floor of old generation keeps rising.

Reading the heap dump. In Eclipse MAT open the "Dominator tree" or "Leak suspects" report. Look for one object (say a ConcurrentHashMap) with a retained size of gigabytes, then expand it to see typical keys and values and follow "path to GC roots" to find the static field. That tells you which class owns it and the code that fills it.

Choosing the right fix.

If the data is...Use

Add a gauge for the collection's size so you notice growth before the OutOfMemoryError.

Situation: old-generation usage climbs after every full GC until an OutOfMemoryError. It restarts and repeats.

Check first: open a heap dump (Eclipse MAT or VisualVM) and look at the dominator tree. A single map holding most of the retained size, with keys such as session ids or request ids, is the leak. Check who adds and who removes.

Fix: use a bounded cache (Caffeine with a maximum size and expiry, or a LinkedHashMap LRU), make sure every put has a matching remove, and use weak references only when I truly want GC-driven eviction. Also check for entries whose key was mutated, which can never be removed.

Prevent: never use a plain static map as a cache. Add size metrics and an alert on it.

Remember: a collection that only grows is a leak. Every cache needs a size or time bound.

map.get(key) returns null for a key you are sure you inserted, and map.size() still counts it. What is wrong? Intermediate

The key object was changed after insertion, so its hashCode changed and the map now looks in the wrong bucket. The entry is stranded. The fix is immutable keys.

Why this one is confusing. Three facts seem contradictory: the entry is counted by size(), it appears when you iterate, and yet get and containsKey fail. The resolution: iteration walks the buckets and returns whatever nodes exist, without hashing. Lookup hashes the key you pass, and goes to the bucket for the new hash. The node sits in the bucket of the old hash. The map never rehashes existing nodes when a key changes, because it has no way of knowing.

Diagnosing quickly. A test: loop over entrySet(), and for each key call map.containsKey(key). Any entry where the loop shows it but the check says false is a stranded entry. Also compare key.hashCode() now with the hash stored in the node (visible in a debugger).

Why entities are the usual culprit. In JPA code, an entity often has a generated id (null until saved) or lazily loaded fields, and a Lombok @Data or @EqualsAndHashCode on it includes mutable fields. Put the entity in a HashSet, change a field, and the set is corrupted. Safer choices: key by the primary key value, or define equality on an immutable business key.

Fixing existing damage. You cannot remove a stranded entry by key. Rebuild: new HashMap<>(oldMap) iterates the old map's nodes and re-inserts each entry with its current hash, which repairs it (if keys are now consistent). Alternatively remove through an iterator and re-add.

Same class of bug. A TreeMap whose comparator uses a field you later change, a HashSet<List<X>> whose lists are modified after insertion, and arrays used as keys (identity hash, no value equality).

Situation: a HashMap<Customer, Order> where Customer has a mutable email field used in hashCode. After an email update, lookups fail but the size is unchanged, and iterating the map still shows the entry.

Check first: does the key class have setters on fields used by equals/hashCode? Does iterating the entries show the key while containsKey says false? That is the signature.

Fix: key by an immutable id (a long or a record) rather than the entity. If the key must change, remove the entry first, change the key, then put it again. To recover a corrupted map, build a fresh one from its entries.

Prevent: make key classes immutable, and avoid entities as keys.

Remember: it is in the map but unreachable. Mutating a key is the cause. Use immutable ids.

A job that checks "is this id already processed?" against a List of 500,000 ids gets slower and slower. What do you do? Basic

List contains scans the whole list, O(n), so the loop is O(n squared). Switch the lookup structure to a HashSet, which is O(1) on average, and the time drops from minutes to milliseconds.

The arithmetic that makes it slow. ArrayList.contains(x) compares x with elements from the start until one matches, so on average it scans half the list when the item is present and the whole list when it is absent. With 500,000 ids already stored, each new check can cost up to 500,000 comparisons. Processing 500,000 records is then about 500,000 x 250,000 = 125 billion comparisons, which explains minutes or hours instead of seconds. And it gets slower as the list grows, which matches "slower and slower".

Why a HashSet fixes it. HashSet.contains hashes the id, goes to one bucket, compares one or two nodes. Cost does not grow with n. Half a million checks take a few tens of milliseconds. The price is memory: a HashSet of 500,000 Long values uses roughly 40 to 50 MB (node, boxed Long, table slot), more than a list.

Set<Long> processed = new HashSet<>(1_000_000);
for (Record r : records) {
    if (!processed.add(r.id())) continue;   // false means already seen
    handle(r);
}

Note that add doubles as the check, so there is one hash lookup per record.

Alternatives when memory or scale matters. A long-specialised set (fastutil LongOpenHashSet) uses a fraction of the memory. A BitSet if ids are dense small integers. A Bloom filter for a "probably seen" test with a tiny footprint and no false negatives. A database unique constraint or a key-value store if the state must survive restarts or be shared between instances.

General lesson. Any time you write list.contains or list.indexOf inside a loop, you have O(n squared). Replace the list with a set or a map keyed by the thing you look up.

Situation: 500,000 records, each checked with processed.contains(id) on an ArrayList. CPU is busy in indexOf.

Check first: a profiler or thread dump showing ArrayList.indexOf on top. Confirm the elements have a proper equals and hashCode.

Fix: Set<Long> processed = new HashSet<>(1_000_000) and use add's return value: if (!processed.add(id)) continue;. Keep a List only when order matters, or use LinkedHashSet for both. For billions of ids, a Bloom filter or a database check is a better fit.

Prevent: think about the access pattern when choosing a collection. Membership tests mean Set or Map.

Remember: contains on a List is O(n). Membership questions belong in a Set.

Production logs show ConcurrentModificationException from a method that "only loops over a list". How do you find and fix it? Intermediate

Either code inside the loop changes the same list (single thread, deterministic), or another thread changes it (intermittent). I read the loop body first, then check whether the list is shared. The fix is removeIf or Iterator.remove in the first case, and a concurrent collection or a copy in the second.

Two different root causes, two different fingerprints.

  • Deterministic, same thread. The exception happens every time that code path runs, often with small data. Something inside the loop body modifies the list being iterated. It is frequently indirect: the body calls a method that fires an event, and a listener (or a callback, a service call, a setter that triggers a refresh) adds to or removes from the same list.
  • Intermittent, multi-thread. It appears only under load, cannot be reproduced locally, and the stack trace may show different callers. Another thread changes the collection while this one iterates. Note that fail-fast detection is best-effort, so with threads you may also see no exception but wrong data.

How to find the writer. In the same-thread case, read the stack trace: the line in your loop is the next() that failed, and the earlier iteration did the modification, so search the loop body and everything it calls for add, remove, clear on that list. A temporary debugging trick is to wrap the list in a class that logs a stack trace on modification. In the multi-thread case, find all references to the list (is it a static, a singleton field, a value returned from a getter?) and check who writes.

Fix options, in order of preference.

  1. Stop sharing: make each thread work on its own list, or pass immutable snapshots.
  2. Same-thread removal: removeIf; additions during traversal: collect them in a second list and addAll after the loop.
  3. Iterate over a copy when the loop's callbacks may change the original: for (T t : new ArrayList<>(list)). Cheap and often the pragmatic fix for listener lists.
  4. Concurrent collections (CopyOnWriteArrayList if reads dominate) or a lock around both the writes and the iteration.

Copying under no lock does not fix a real race, since the copy itself iterates the list. Do the copy inside a lock, or use a CopyOnWrite list.

Situation: the stack trace ends in ArrayList$Itr.checkForComodification, in a for-each.

Check first: does anything in the body, directly or through a callback or event handler, add to or remove from this list? If yes, it fails every time that path runs. If not and it fails randomly, the list is shared between threads.

Fix: same thread: removeIf, Iterator.remove, collect changes and apply after the loop, or loop over a copy. Threads: CopyOnWriteArrayList for read-mostly data, or take a copy under a lock, or use a concurrent collection.

Prevent: do not share mutable lists, return copies or unmodifiable views, and test callbacks that re-enter.

Remember: deterministic means same-thread modification. Intermittent means a shared list.

A worker service goes out of memory while its executor "queue" keeps growing. What is the cause? Senior

The queue is unbounded: producers are faster than consumers and the backlog keeps growing in memory. LinkedBlockingQueue defaults to Integer.MAX_VALUE capacity, and so does Executors.newFixedThreadPool. I bound the queue and decide what to do when it is full.

The underlying maths. If tasks arrive at 2,000 per second and workers finish 1,500 per second, the backlog grows by 500 per second, or 1.8 million per hour. Each queued task holds its payload objects, so memory climbs steadily until the JVM throws OutOfMemoryError, or spends all its time in garbage collection. A queue converts a rate mismatch into a memory problem unless it has a limit.

Where the hidden unbounded queues are.

  • Executors.newFixedThreadPool(n) and newSingleThreadExecutor(): a LinkedBlockingQueue with capacity Integer.MAX_VALUE.
  • new LinkedBlockingQueue<>() or ConcurrentLinkedQueue used as a buffer.
  • Framework internals: unbounded in-memory event buses, async logging queues, scheduled executors, Kafka consumers that poll faster than they process, @Async with default executors (check your Spring configuration).

What to decide when the queue is full. That is the design question behind the rejection policy.

Situation: heap climbs during a traffic burst, and a dump shows millions of pending tasks in a LinkedBlockingQueue.

Check first: queue size metric against throughput, how many consumers, whether a downstream call is slow. Slow consumers plus an unbounded queue is the classic combination.

Code that works in a unit test throws UnsupportedOperationException in production when it calls list.add. Why? Basic

The list is a fixed-size or immutable one, such as Arrays.asList, List.of, Collections.unmodifiableList, Stream.toList() or Collections.emptyList(), and it was passed to code that tries to modify it. I find where the list came from and copy it into a new ArrayList before changing it.

You put 1,000 employees in a TreeSet sorted by salary and only 300 come out. Where did the rest go? Intermediate

TreeSet treats elements as duplicates when the comparator returns 0. Employees with equal salary compare equal, so only the first of each salary was kept. I add a tie-breaker such as the id to the comparator.

Why this is a trap even for experienced developers. The comparator comparingInt(Emp::salary) looks like "sort by salary", which is what we want from an ordering. But in a TreeSet the comparator has a second job: it defines identity. Every add descends the tree comparing the new element with existing ones. If any comparison returns 0, the add stops and returns false, discarding the new element. 1,000 employees with only 300 distinct salaries leaves exactly 300.

Confirming the diagnosis in two lines. emps.stream().map(Emp::salary).distinct().count() equals the set size. Also check the return value of add: false for the dropped ones.

Comparator<Emp> bySalaryThenId = Comparator.comparingInt(Emp::salary)
                                           .thenComparing(Emp::id);
Set<Emp> set = new TreeSet<>(bySalaryThenId);   // now all 1,000 stay

Is a TreeSet the right tool at all? If the goal is a sorted view for display, a list sorted once (list.sort(comparator)) is simpler and keeps duplicates. A TreeSet earns its place when you need to keep inserting and querying ranges, or the next higher or lower element. Also consider TreeMap<Integer, List<Emp>> (salary to the employees with that salary) if grouping by salary is the real requirement.

Same trap elsewhere. TreeMap keys, PriorityQueue (which, unlike TreeSet, keeps equal elements, so a PriorityQueue with this comparator would retain all 1,000), ConcurrentSkipListSet, and Stream.distinct uses equals and is not affected. A good habit is that a comparator for a sorted set ends with a field that is unique.

Situation: the set size is far below the input size, with no errors. The comparator is comparingInt(Emp::salary).

Check first: count distinct salaries. If it equals the set size, the comparator is the culprit.

Fix: comparingInt(Emp::salary).thenComparing(Emp::id). If I only need sorting and not uniqueness, collect into a list and sort it instead.

Prevent: make every sorted-collection comparator consistent with equals, ending in a unique field.

Remember: in a sorted set, compare()==0 means duplicate. End comparators with a unique key.

You switched to ConcurrentHashMap but a "check then insert" still creates duplicates or runs the loader twice. Why? Senior

Each ConcurrentHashMap call is atomic, but if (!containsKey) put is two calls with a gap between them. I replace it with computeIfAbsent or putIfAbsent, which do the check and the insert as one atomic step.

Replaying the failure. Two threads need a value for key K that takes 2 seconds to load.

  1. T1: containsKey(K) is false. T2: containsKey(K) is false (T1 has not yet put).
  2. Both call load(K). The load runs twice, doubling the database or network work, and possibly creating two different instances (two connections, two parsers).
  3. T1 puts its instance, T2 puts its own, overwriting. T1 keeps using an instance that is no longer in the map, so later updates to the shared one are not seen by T1.

Every call was thread safe. The bug is in the gap between check and put.

What computeIfAbsent changes. The map holds a lock on the bin while the function runs, so a second thread asking for the same key waits and then receives the first thread's value. The loader runs once per key. Calls for other keys that fall in other bins continue in parallel.

Its trade-off: the function runs under a bin lock. A slow loader (2 seconds) blocks every other operation on the same bin, including unrelated keys that share it. It must not call back into the same map, which may deadlock or throw an IllegalStateException: Recursive update. A common pattern for slow loads is to store a future:

Map<String, CompletableFuture<Data>> cache = new ConcurrentHashMap<>();
CompletableFuture<Data> f = cache.computeIfAbsent(key,
        k -> CompletableFuture.supplyAsync(() -> load(k)));   // returns immediately
Data d = f.join();   // callers wait here, outside the bin lock

Think about failures too: remove a failed future from the map (cache.remove(key, f)), or every later caller gets the same failure. A loading cache library such as Caffeine handles this, plus expiry and size bounds.

Situation: a cache loads an expensive object twice for the same key under load, or two threads each create a different instance.

Check first: look for containsKey followed by put, or get followed by put.

Fix: cache.computeIfAbsent(key, this::load) runs the loader at most once per key. Keep the loader fast and never touch the same map inside it. For slow loaders, store a CompletableFuture as the value so waiting does not hold a bin lock, or use Caffeine's loading cache. Multi-key invariants need an explicit lock.

Prevent: treat "thread-safe collection" as thread-safe operations only, and review compound actions.

Remember: thread-safe methods are not thread-safe sequences. Use the single-call atomic ones.

A nightly job fails with "IllegalStateException: Duplicate key" from Collectors.toMap. How do you fix it? Intermediate

Two input elements produced the same key and toMap has no rule for which value to keep. I decide the business rule and pass it as a merge function, or use groupingBy if I want all of them.

Why it fails at night and not in tests. The job passes while the input has unique ids. A nightly feed eventually contains a repeated id: a retried record, a correction row, two sources merged. toMap throws IllegalStateException: Duplicate key 42 (attempted merging values X and Y), which shows the key and both values, a useful start for diagnosis.

The decision is a business rule, not a coding trick. The merge function (a, b) -> ... receives the existing and the new value:

RuleMerge function
keep the first(a, b) -> a
keep the last (feed order matters)(a, b) -> b
keep the newest by timestamp(a, b) -> a.ts().isAfter(b.ts()) ? a : b
sum amountsmake the value a number, Integer::sum
keep alluse groupingBy instead, producing lists
reject loudlykeep the default exception, but wrap with a clear message

Silent merges can hide data problems. If duplicates should not exist, "keep first" turns a data-quality issue into wrong output without anyone noticing. Count and log the duplicates, or send them to a quarantine file. For critical flows, fail the job with a clear message and let the owners fix the source.

Other toMap failures to know. A null value throws NullPointerException. The map is a HashMap unless you pass a supplier, so a stable output order needs LinkedHashMap::new. Parallel streams with plain toMap are correct but may merge in a different order, so a "keep first" rule is not reliable there; use toConcurrentMap or sequential processing when order is part of the rule.

Situation: the job turns a list of records into a map by id, and new data contains a repeated id.

Check first: the exception message names the key. Look at the data: is the duplicate a data-quality bug, or legitimately several rows?

Fix: toMap(Rec::id, r -> r, (a, b) -> a.updated().isAfter(b.updated()) ? a : b) to keep the newest, or groupingBy(Rec::id) for lists. Silent "keep first" can hide bad data, so log duplicates when it matters.

Prevent: always provide a merge function when keys are not guaranteed unique.

Remember: toMap without a merge function crashes on duplicates. Decide the rule.

You used CopyOnWriteArrayList to fix a ConcurrentModificationException and now CPU and GC are high. Why? Senior

The list is written to often, and every write copies the entire array. With thousands of elements and frequent adds, that means constant O(n) copying and a flood of garbage. CopyOnWriteArrayList is for read-mostly data. I switch to a structure that fits the write pattern.

Why swapping the class "fixed" the exception. CopyOnWriteArrayList iterators work on a snapshot and never throw ConcurrentModificationException. So the symptom vanished. But the real cause, concurrent reads and writes on a list, was handled by brute force: every write allocates a new array.

The cost, in numbers. A list of 50,000 elements and 200 adds per second: each add copies 50,000 references (about 200 KB), so 40 MB per second of garbage and 10 million reference copies per second, plus a lock that serialises writers. The young generation fills quickly and GC runs often, and CPU is spent copying. As the list grows, each add gets slower: the cost is proportional to the size, not constant.

How to confirm it. A profiler or a JFR allocation recording shows Arrays.copyOf called from CopyOnWriteArrayList.add as the biggest allocator. GC logs show a high allocation rate with short, frequent young collections. Check the read to write ratio: copy-on-write pays off only when reads outnumber writes by orders of magnitude (for example 10,000 to 1).

Better matches by workload.

WorkloadBetter structure
producers append, consumers removeBlockingQueue or ConcurrentLinkedQueue
lookups by key, updates oftenConcurrentHashMap
periodic bulk refresh, many readersbuild a new immutable list, then assign it to a volatile field (one copy per refresh, not per element)
frequent writes and in-order iteration with mutationArrayList guarded by a ReentrantReadWriteLock

The principle: pick the collection by access pattern; do not pick it to make an exception disappear.

Situation: the CME went away, but allocation rate and GC pauses spiked and throughput fell.

Check first: the read to write ratio, the list size, and an allocation profile showing Arrays.copyOf from CopyOnWriteArrayList.add.

Fix: for a queue-like workload use ConcurrentLinkedQueue or a BlockingQueue. For a shared map use ConcurrentHashMap. For a list written in batches, build a new list off to the side and swap one reference (a volatile field holding an immutable list). Or lock a normal ArrayList.

Prevent: choose by access pattern, not to silence an exception.

Remember: copy-on-write is for many reads, rare writes. Do not use it to hide a CME.

A latency-sensitive service holds millions of Long and Integer values in maps and lists and suffers long GC pauses. What would you change? Senior

Boxed numbers in collections create millions of small objects, which inflates the heap and the GC work. I cut the number of objects by switching to primitive arrays or a primitive-specialised collection library for the hot data, and I measure before and after.

Why millions of boxed values hurt the GC. Garbage collectors work by visiting live objects. A Map<Long,Long> with 20 million entries holds about 60 million heap objects: a node, a key and a value per entry. Marking has to follow all of them, so a full or concurrent mark takes longer, remembered sets and card tables grow, and memory is fragmented into small pieces. Young collections that have to copy survivors take longer too, and promoting many small objects to the old generation increases old-generation pressure. Pause times rise with the number of live objects, not just with bytes.

Sizing the problem. Roughly 70 to 80 bytes per entry, so 20 million entries is 1.4 to 1.6 GB, while the real data (two longs) is 320 MB. The remaining 1.1 GB is overhead.

Options, from least to most effort.

  1. Right-size and pre-size the collections, remove unneeded ones, avoid copying them.
  2. Switch hot code from Stream<Long> to LongStream, and avoid boxing in loops (long accumulators, mapToLong).
  3. Use a primitive-keyed map such as fastutil's Long2LongOpenHashMap (open addressing in two arrays: about 16 bytes per entry plus load slack, with no per-entry objects).
  4. If the keys are known and static, a sorted long[] plus a parallel long[] and binary search (O(log n), minimal memory, zero GC work).
  5. Move the data off the heap: memory-mapped files, an embedded store (Chronicle Map, RocksDB), or a cache service, at the price of serialisation and API complexity.

Do not forget to measure. Take a heap histogram before and after, compare GC logs (pause time, allocation rate), and test with realistic data volumes. Tuning the collector (G1 region size, ZGC) helps the pauses, but reducing the object count attacks the cause.

Situation: a Map<Long, Long> with 20 million entries uses several GB, with frequent young and old collections.

Check first: a heap histogram (jmap -histo or a profiler) showing java.lang.Long, HashMap$Node and Object[] at the top. GC logs for pause times.

Fix: use long[] with a sorted binary search or an open-addressing primitive map (fastutil, Eclipse Collections, or similar). Pre-size collections, and avoid temporary boxing in hot loops (IntStream instead of Stream<Integer>). If the data is large and static, a memory-mapped file or an off-heap store is the next step.

Prevent: capacity test with realistic data volumes, and track allocation rates.

Remember: boxed collections cost roughly 5x the memory. Use primitives for big numeric data.
