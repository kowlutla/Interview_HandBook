How to use this page

Every question is a collapsible. Try to answer out loud first, then open it. In a design interview the storage choice is rarely judged on the product name. It is judged on whether you start from the access pattern (what is read and written, how often, how big, how consistent) and then pick the store that makes those operations cheap. Practice phrasing: "The workload is X, so the dominant operation is Y, which suggests Z, and the cost I accept is W."

Choosing a database

How do you choose a database for a new system? Basic

Start from the workload, not the brand. Ask these in order:

  1. Data shape and relationships: rows with joins, nested documents, a graph, a time series, blobs?
  2. Access patterns: lookup by key, range scans, ad hoc queries, full-text, aggregations over billions of rows?
  3. Read/write ratio and volume: 100 writes/s or 500,000? Data size today and in 3 years?
  4. Consistency needs: can two users briefly see different values, or is this money?
  5. Latency and availability targets: single-digit milliseconds? Must survive a region loss?
  6. Operational reality: what does the team already run well? A boring database you know beats an exotic one.
Say: "Default to a relational database unless a requirement forces otherwise: scale beyond one primary, a very simple access pattern at huge volume, or a data shape that fits badly into tables."
SQL versus NoSQL: how do you decide? Basic
Relational (SQL)NoSQL (broad family)
ModelTables, foreign keys, joinsKey-value, document, wide-column, graph
SchemaEnforced up frontOften flexible, enforced by the app
QueriesAd hoc, any column, joinsDesigned around known access patterns
TransactionsMulti-row ACID is the defaultOften single-key or single-partition only (varies by product)
ScalingVertical plus read replicas; sharding is workHorizontal partitioning is built in

Pick SQL when data is relational, queries are varied, and integrity matters (orders, payments, inventory). Pick NoSQL when the access pattern is narrow and known, volume or write rate exceeds what one primary handles, or the shape is naturally a document, graph, or time series. "NoSQL scales, SQL does not" is a myth: a well-tuned Postgres or MySQL handles tens of thousands of transactions per second on one node, and many companies run sharded MySQL at huge scale.

Trap: choosing NoSQL "for scale" with 50 GB of data and then needing joins and transactions. Choose by need, not by fashion.
When is a key-value store the right choice, and what are its limits? Basic

A key-value store maps a key to an opaque value and supports get, put, delete in about one network hop. Good fits: sessions, shopping carts, feature flags, user profiles by id, idempotency keys, caches. Examples: DynamoDB, Redis, Riak, etcd (for small config data).

Limits: you can only query by key (or key prefix or range in some products). No "find all users in city X" without building your own secondary index. Large values hurt. Cross-key transactions are limited or missing. If the product needs more than a few access paths, you will end up reimplementing a database badly on top.

What is a document database and when would you use it over relational? Basic

A document database (MongoDB, Couchbase, Firestore, DocumentDB) stores self-contained JSON-like documents, each looked up by id, with indexes on fields inside the document. It shines when an entity is read and written as one unit and its shape varies: product catalog entries with different attributes per category, CMS content, user profiles with optional parts.

The key idea is that you embed data that is always read together (an order with its line items) so one read returns everything, instead of joining three tables. The cost: duplicated data is harder to keep consistent, many-to-many relationships are awkward, and a document that grows without bound (a comment array with millions of entries) becomes a problem. Modern relational databases also have JSON columns (Postgres jsonb), so "flexible schema" alone is no longer a strong reason to leave SQL.

What is a wide-column store (Cassandra, Bigtable, HBase) and what is it good at? Intermediate

Data is addressed by a partition key (which node owns it) and a clustering key (sort order inside the partition). Within a partition, rows are stored sorted, so range reads such as "last 100 events for device 42" are one sequential read. Most are built on an LSM tree, so writes are very fast and the system scales to many nodes with no single primary (Cassandra) or with a master per tablet range (Bigtable, HBase).

  • Good at: massive write throughput, time-ordered data per entity, messaging inboxes, event logs, IoT, always-on multi-datacenter replication.
  • Bad at: ad hoc queries, joins, strong multi-row transactions, and anything where you did not design the table for the query. The rule is "one table per query".
  • Danger: hot partitions (one partition key taking all traffic) and unbounded partitions (a key that grows forever). Fix by bucketing the key, for example (device_id, day).
When do you need a graph database? Intermediate

When the questions are about relationships and paths: friends of friends, "who is connected to this fraudulent account within 3 hops", recommendation by shared neighbours, dependency or permission graphs. A graph database (Neo4j, Neptune, JanusGraph) stores edges as direct pointers, so a traversal costs time proportional to the part of the graph visited, not to table size. In SQL the same query is a chain of self-joins whose cost grows quickly with depth.

Use it when depth is variable or greater than about 2 or 3 and traversal is the main query. For a simple "list my friends" lookup, a join table is fine. Graph stores are harder to shard because edges cross partitions, which is why very large social graphs are usually custom-built on top of sharded key-value or MySQL storage.

What makes a time-series database different, and when do you use one? Intermediate

Time-series data is append-mostly, timestamped, queried by time range and often aggregated (average CPU per minute over the last day). Specialised stores (InfluxDB, TimescaleDB, Prometheus, VictoriaMetrics, ClickHouse used this way) give you:

  • Time-partitioned storage, so old chunks can be dropped or moved cheaply.
  • Strong compression (delta and delta-of-delta encoding of timestamps, XOR of floats), often 10x or more.
  • Built-in downsampling and retention policies, and time-bucket functions.
  • Fast ingestion of many small writes.

Watch out for high cardinality: if a label such as user id has millions of values, the number of distinct series explodes and indexes and memory blow up. Use a time-series store for metrics, IoT, and monitoring. Do not use it for transactional data.

Why is a search engine like Elasticsearch not your primary database? Intermediate

Search engines (Elasticsearch, OpenSearch, Solr) build an inverted index (term to list of documents) and give relevance-ranked text search, filters, facets and aggregations. They are near real-time: a document becomes searchable after a refresh, about a second by default. They do not give multi-document transactions, and their durability and consistency story is weaker than a primary database (replicas can diverge, and a bad mapping change needs a full reindex).

The standard pattern: the primary database is the source of truth; a pipeline (change data capture or an outbox plus a queue) feeds the search index, which is a derived, rebuildable view. If the index is lost, rebuild it from the source.

Where do in-memory stores fit, and what do you risk by using one as a database? Basic

In-memory stores (Redis, Memcached, Hazelcast, Aerospike partly on flash) serve reads in well under a millisecond. Use them for caches, rate-limit counters, leaderboards (sorted sets), session data, distributed locks, and short-lived state.

Risks as a primary store: memory is expensive (RAM per GB costs many times disk), a restart can lose data unless persistence is configured (Redis RDB snapshots and AOF log trade durability against speed), and replication is usually asynchronous, so a failover can lose the last few writes. Use it as primary only when losing recent writes is acceptable or when the data can be rebuilt.

OLTP versus OLAP: what is the difference and why separate them? Basic
OLTPOLAP
PurposeRun the business: place order, update profileAnalyse the business: revenue by region by month
Query shapeMany small reads/writes touching a few rowsFew huge scans aggregating millions or billions of rows
Storage layoutRow-orientedColumn-oriented
Latency goalMillisecondsSeconds to minutes
ExamplesPostgres, MySQL, DynamoDBSnowflake, BigQuery, Redshift, ClickHouse

Separate them because a 10-minute analytic scan on the production database eats I/O and CPU and slows customer requests, and because the optimal physical layout differs. Data flows OLTP to OLAP through ETL/ELT or change data capture.

Why are column stores faster for analytics? Intermediate

A row store keeps all columns of a row together; a column store keeps each column together. A query like SELECT SUM(amount) FROM sales WHERE year = 2025 needs two columns out of, say, 50. The row store reads all 50 columns of every row from disk; the column store reads only 2 columns.

Extra wins: same-type values stored together compress very well (run-length, dictionary encoding), and the CPU can process them in vectorised batches. The cost: single-row inserts and point lookups by row are slow, because one row is spread over many column files. That is why column stores take bulk loads and OLTP stays on row stores.

What is NewSQL and when would you consider it? Senior

NewSQL systems (Google Spanner, CockroachDB, YugabyteDB, TiDB) offer a SQL interface and ACID transactions, but are horizontally scalable and replicate with consensus (Paxos or Raft), so they survive node and often region loss without losing committed data. Spanner adds TrueTime (GPS and atomic clocks) to give externally consistent transactions across the globe.

Consider them when you need relational semantics and a write load or data size beyond one primary, or multi-region active-active with strong consistency. Costs: higher write latency (a commit needs a quorum, and across regions that means tens to hundreds of milliseconds), more operational complexity, and cross-shard transactions that are slower than single-node ones. If one big Postgres with replicas meets the need, it is simpler.

What is polyglot persistence and what does it cost? Intermediate

Using different stores for different jobs in one system, each matching its workload: Postgres for orders, Redis for sessions and cache, Elasticsearch for search, S3 for images, ClickHouse for analytics, Kafka as the event log.

Benefit: each part is cheap and fast for its task. Cost: more systems to run, monitor, back up and secure; data must be copied between stores, so you need a clear source of truth per entity and a propagation mechanism (CDC, outbox) with eventual consistency; and there are no transactions across stores. Add a store only when a real requirement justifies the operational price.

Walk me through picking storage for: a product catalog, a shopping cart, an audit log, and user-uploaded photos. Intermediate

An interviewer asks "why not just use Postgres for everything?" How do you respond? Senior

It is a legitimate position for most early-stage systems. Postgres gives transactions, joins, jsonb, full-text search, geospatial, and extensions for time-series. One database means one backup story, one set of skills, and consistent transactions.

Then name the limits that make you add something: a write rate or data size beyond one primary (move to sharding or a distributed store); analytics that hurt OLTP (add a warehouse or replica); relevance-ranked search at scale (add a search engine); sub-millisecond reads for hot keys (add a cache); blobs (object store, because large files bloat the database and its backups). Show that you scale the architecture when evidence demands it, not before.

ACID, BASE, transactions and isolation

What does ACID mean, with an example for each letter? Basic

Take a bank transfer of 100 from account A to B.

  • Atomicity: both the debit and the credit happen, or neither. A crash in the middle rolls back the debit.
  • Consistency: the transaction moves the database from one valid state to another, respecting constraints (balance not negative, foreign keys hold). Note this is mostly the application and constraints doing their part; it is a different "consistency" from the one in CAP.
  • Isolation: concurrent transfers do not see each other's half-done work. How strictly depends on the isolation level.
  • Durability: once commit returns, the data survives a crash. Implemented by writing to a write-ahead log and flushing it to disk (fsync) before acknowledging.
What is BASE and how does it contrast with ACID? Basic

BASE = Basically Available, Soft state, Eventually consistent. The system keeps answering even during failures, state may change over time as replicas converge, and given no new writes all replicas end up equal. It is a design stance for large distributed stores that prefer availability and low latency over immediate agreement.

It is not "no guarantees". You still design for it: use idempotent writes, version numbers or vector clocks, conflict resolution (last-write-wins, CRDTs, app-level merge), and read-your-writes tricks where users would notice. Choose ACID for money, inventory, and uniqueness; choose BASE for feeds, counters, carts, and view counts where a stale read for a second is harmless.

List the common concurrency anomalies. Intermediate
  • Dirty read: you read data another transaction has not committed (and may roll back).
  • Non-repeatable read: you read a row twice in one transaction and get different values because someone committed in between.
  • Phantom read: you run the same range query twice and new rows appear (or vanish) because someone inserted or deleted matching rows.
  • Lost update: two transactions read the same value, both compute a new one, and the second write overwrites the first. Classic: two clients doing read balance, add 10, write.
  • Write skew: two transactions read an overlapping set, each makes a decision that is valid alone, and write different rows, together breaking an invariant. Example: two doctors both on call both check "at least 2 on call" and both go off call, leaving none.
Explain the SQL isolation levels and which anomalies each prevents. Intermediate

Defaults differ: Postgres and Oracle default to read committed; MySQL InnoDB defaults to repeatable read. Behaviour at "repeatable read" varies between engines (Postgres uses snapshot isolation there, which still allows write skew; InnoDB uses next-key locks to block many phantoms). Hedge this in an interview and say "check the engine".

Say: "Higher isolation costs throughput and causes aborts or lock waits, so I use the lowest level that protects my invariant, and I use explicit locking or constraints for the specific hot spots."
What is MVCC and why do databases use it? Intermediate

Multi-version concurrency control keeps several versions of a row. A reader sees a consistent snapshot as of its start (or statement start), while writers create new versions. Result: readers do not block writers and writers do not block readers. Postgres stores old versions in the table and cleans them with vacuum; InnoDB keeps them in undo logs.

Cost: old versions pile up if a long-running transaction holds a snapshot open, bloating storage and slowing queries. A forgotten open transaction is a well-known production problem.

How do you prevent lost updates? Intermediate
  1. Atomic update in the database: UPDATE acct SET bal = bal - 100 WHERE id = 1 AND bal >= 100. No read-modify-write in the app. Best option when possible.
  2. Pessimistic lock: SELECT ... FOR UPDATE locks the row until commit. Simple, but holds locks and can deadlock.
  3. Optimistic concurrency: keep a version column; UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?. If zero rows change, someone else won; retry. Good when conflicts are rare.
  4. Higher isolation: serializable (or Postgres repeatable read, which aborts the loser).
  5. In key-value stores: compare-and-set or conditional writes (DynamoDB condition expressions).
How would you handle write skew, such as "at least one doctor on call"? Senior

Snapshot isolation does not catch it because the two transactions write different rows. Options: run at true serializable (Postgres SSI detects the dangerous pattern and aborts one); lock the rows you read (SELECT ... FOR UPDATE on all on-call rows); materialise the conflict by locking a single summary row (for example a "shift" row) that both must update; or enforce the rule with a constraint or unique index where expressible. The same pattern appears in double-booking a meeting room: a unique constraint on (room, time_slot) is the cleanest guard.

What is a deadlock in a database and how do you reduce it? Intermediate

Transaction 1 locks row A and waits for B; transaction 2 locks B and waits for A. The database detects the cycle and kills one as the victim (the app sees an error and must retry).

Reduce by: acquiring locks in a consistent order (always lower account id first), keeping transactions short, avoiding user think-time inside a transaction, indexing so updates lock only the needed rows (a missing index can cause range or table locks), and retrying deadlock errors with backoff.

How do you do a transaction across several databases or services? Senior
  • Two-phase commit (2PC): a coordinator asks all participants to prepare, then to commit. Gives atomicity but blocks if the coordinator dies after prepare, adds latency, and many modern stores do not support it. Used inside some distributed databases and in XA setups.
  • Saga: a sequence of local transactions, each with a compensating action (refund, release stock) if a later step fails. Eventually consistent; intermediate states are visible, so design for them.
  • Outbox pattern: write the business row and an event row in one local transaction; a relay publishes the event to the broker. Solves "update the database and send the message" atomically without 2PC.
  • Avoid it: keep data that must change together in one database or partition by choosing partition keys carefully.
What is a write-ahead log and why does it give durability? Intermediate

Before changing data pages, the database appends a description of the change to a sequential log and flushes it to disk. A sequential append is fast, whereas updating scattered data pages is slow random I/O. On commit, only the log must be durable. After a crash, the database replays the log to redo committed work and undo uncommitted work. The same log is shipped to replicas (physical replication) and to CDC tools. Tuning knob: how often to fsync; flushing less often is faster but can lose the last moments of commits on a crash (for example Postgres synchronous_commit off).

Why do storage designs need idempotent writes? Intermediate

Networks time out and clients retry; a retry of a non-idempotent write (charge card, insert order) duplicates it. Give each logical request a unique idempotency key and store it with a unique constraint, so the second attempt either returns the original result or fails harmlessly. Example: INSERT INTO payments (idem_key, ...) ... ON CONFLICT DO NOTHING. Natural idempotent operations such as "set status = shipped" are safe to repeat; "increment by 1" is not.

Indexing

What is a database index and why does it speed up queries? Basic

An index is a separate sorted (or hashed) structure that maps column values to row locations, like a book index. Without it, finding WHERE email = 'a@b.com' means scanning every row (O(n)). With a B-tree index it is O(log n): for a billion rows that is roughly 3 or 4 page reads since each node holds hundreds of keys. Indexes also make ORDER BY and range queries cheap because keys are stored sorted.

How does a B-tree index work and why is it used so widely? Intermediate

A B-tree (in practice a B+ tree) is a balanced, wide tree of fixed-size pages (often 4 to 16 KB). Internal pages hold keys and child pointers; leaf pages hold keys and row pointers (or the rows themselves) and are linked to each other for range scans. Because each page holds hundreds of keys, the tree is only 3 to 4 levels deep even for billions of rows. Inserts find the leaf, and a full page splits in two.

Strengths: fast point lookups and range scans, predictable read latency, mature. Weakness: updates are in place, which means random writes and page splits, so write throughput is lower than LSM, and random inserts such as UUID v4 keys fragment pages (time-ordered keys like UUID v7 or ULID are friendlier).

Say: "B-tree for read-heavy and mixed OLTP with range queries; LSM when ingestion rate is the bottleneck and I can accept compaction cost and slightly slower reads."
Walk through an LSM write and read. Senior
  1. Write: append to the WAL (for crash safety), insert into the sorted in-memory memtable, acknowledge.
  2. When the memtable is full, flush it as an immutable sorted file (SSTable).
  3. Read: check memtable, then SSTables newest to oldest; a Bloom filter per file says "definitely not here" to skip most files.
  4. Compaction merges files, drops overwritten values, and writes tombstones for deletes (removed later, which is why a delete-heavy workload can slow reads).
How do composite indexes work and why does column order matter? Intermediate

A composite index on (country, city, created_at) is sorted by country, then city within country, then created_at. It can be used for queries that filter on a leftmost prefix: country; country and city; country, city and created_at. It cannot efficiently serve a query on only city (the sort order of city is only meaningful within one country).

Ordering rule of thumb: equality columns first, then the range or sort column last. For WHERE user_id = ? AND created_at > ? ORDER BY created_at, index (user_id, created_at) gives both the filter and the sort with no extra sort step. Putting the range column first would stop the later columns from narrowing the scan.

What is a covering index? Intermediate

An index that contains every column a query needs, so the database answers from the index alone and never touches the table (an "index-only scan"). Example: for SELECT status FROM orders WHERE user_id = ?, an index on (user_id, status) (or (user_id) INCLUDE (status) in Postgres or SQL Server) is covering. It saves a random table lookup per row. The price is a bigger index and more write cost, so cover only your hottest queries.

If indexes make reads fast, why not index every column? Basic
  • Every insert, update (of an indexed column) and delete must also update every index: write amplification. A table with 8 indexes does about 9 writes per insert.
  • Indexes use disk and RAM; if hot indexes no longer fit in memory, everything slows.
  • The optimizer has more plans to consider and may pick poorly.
  • Low-selectivity columns (a boolean, a status with 3 values) give little benefit alone because the index still matches a large share of rows.

Index for real query patterns, verify with EXPLAIN, and drop unused ones (databases expose usage stats).

A query has an index on the column, yet the database does a full scan. Why? Intermediate
  • A function or cast on the column: WHERE LOWER(email) = ... or WHERE DATE(created_at) = .... Use a functional index or rewrite as a range.
  • Leading wildcard: LIKE '%abc' cannot use a B-tree.
  • Type mismatch (string compared to integer), forcing an implicit cast.
  • Leftmost-prefix violation on a composite index.
  • Low selectivity: the planner estimates most rows match, and a sequential scan is cheaper than many random lookups.
  • Stale statistics, so the planner estimates wrongly (run ANALYZE).
  • OR across different columns, or NOT IN patterns.
When would you use a hash index, a bitmap index, or a partial index? Senior
  • Hash index: equality lookups only, O(1), no range or ordering. Rarely worth it over a B-tree.
  • Bitmap index: one bitmap per distinct value; good for low-cardinality columns in read-mostly analytic tables (Oracle, some warehouses). Bad under heavy concurrent writes.
  • Partial (filtered) index: indexes only rows matching a condition, for example WHERE status = 'PENDING'. If 1 percent of orders are pending and you poll for them, this index is tiny and fast.
  • Unique index: enforces a constraint as well as accelerating lookups.
How do secondary indexes work in NoSQL stores, and what are the trade-offs? Senior

In a partitioned store, data is placed by the primary key. A secondary index lets you query by another attribute, and there are two designs:

Local (document-partitioned)Global (term-partitioned)
Where the index livesEach partition indexes only its own rowsOne index partitioned by the indexed value, across the cluster
Write costCheap, one partitionA write touches the data partition and one or more index partitions; often updated asynchronously
Read costScatter-gather: query every partition, tail latency grows with cluster sizeOne partition read, but may be slightly stale
ExamplesCassandra local indexes, MongoDB, Elasticsearch shardsDynamoDB global secondary indexes (eventually consistent), Cassandra materialised views (with caveats)

Practical guidance: prefer designing the table to answer the query (one table per access pattern, duplicating data), and use a secondary index only for low-volume or less critical lookups.

How does primary key choice (auto-increment, UUID, snowflake id) affect storage? Senior
  • Auto-increment: sequential, compact, B-tree friendly (appends to the right edge). Downsides: a single-writer bottleneck when sharded, guessable ids, and a hot right-most page under extreme insert rates.
  • Random UUID v4: unique without coordination, but random inserts scatter across the B-tree, causing page splits, poor cache locality and 16-byte keys copied into every secondary index.
  • Time-ordered ids (UUID v7, ULID, snowflake): unique without central coordination yet roughly sorted by time, so insert locality is good. In range-sharded stores, however, they create a hot last shard; hash the key or prefix with a bucket when write rate is huge.

Storage engines and amplification

What are write, read and space amplification? Senior
  • Write amplification: bytes physically written to disk per byte the application wrote. A B-tree writes the WAL record plus a whole page (say 8 KB) to change a 100-byte row. An LSM rewrites data repeatedly as compaction pushes it down levels; leveled compaction can reach 10x to 30x or more (workload-dependent), which also wears out SSDs.
  • Read amplification: disk reads per logical read. LSM may check several files; B-tree reads a page for one row.
  • Space amplification: disk used divided by logical data size, caused by old versions, fragmentation, and not-yet-compacted duplicates.

You cannot minimise all three. Leveled compaction lowers read and space amplification but raises write amplification; size-tiered compaction does the opposite. Choosing an engine means choosing which one hurts least for your workload.

Row-oriented versus column-oriented storage: when each? Intermediate

Row storage keeps a record contiguous: ideal when you fetch or update whole rows by key (OLTP). Column storage keeps each column contiguous: ideal when you aggregate a few columns over many rows (OLAP). Hybrid designs exist (Postgres columnar extensions, SingleStore, wide-column stores group columns into families). Rule: if queries say "get order 123", use rows; if they say "sum revenue by month", use columns.

Why does RAM size matter so much for a database? Intermediate

Databases keep hot pages and index pages in a buffer pool or the OS page cache. A read from RAM costs about 100 ns; from SSD about 100 microseconds; from a spinning disk several milliseconds. If the working set (the data and indexes touched regularly) fits in memory, nearly all reads are memory hits. When it stops fitting, hit ratio falls and latency jumps sharply. Sizing rule: keep all hot indexes in memory, and watch the cache hit ratio and disk I/O as the data grows.

What can go wrong with LSM compaction in production? Senior
  • Compaction falls behind the write rate: SSTable count grows, reads slow (more files to check), and eventually the engine throttles or stalls writes.
  • I/O contention: compaction competes with foreground reads, producing p99 latency spikes.
  • Tombstone buildup: heavy deletes (or TTL expiry, or queue-like usage) leave many tombstones that every read must skip; Cassandra famously warns about "queue as a table" anti-pattern.
  • Space spikes: size-tiered compaction can temporarily need up to double the disk.

Mitigations: rate-limit compaction, choose strategy to fit the workload (time-window compaction for TTL time-series), keep disks at less than about 50 to 70 percent full, and avoid delete-heavy modelling.

What is a Bloom filter and where do storage systems use it? Intermediate

A compact bit array plus several hash functions that answers "is key X in this set?" with either "definitely not" or "probably yes". It has false positives but no false negatives. LSM engines keep one per SSTable, so a lookup for a missing key skips almost all files without any disk read. Used also in HBase, Bigtable, and to avoid caching one-hit-wonders. With about 10 bits per key the false-positive rate is around 1 percent.

Normalization, data modelling and schema evolution

What is normalization and what problem does it solve? Basic

Organising tables so each fact is stored once. Third normal form in plain words: every non-key column depends on the key, the whole key, and nothing but the key. If an order table repeats customer name and address on each row, changing an address means updating many rows, and missing one creates inconsistency (update anomaly). Normalising splits customers into their own table referenced by id.

Benefits: no duplication, easy consistent updates, smaller rows. Cost: reads need joins.

When do you denormalize, and what do you pay? Intermediate

Denormalize when reads vastly outnumber writes and joins are the bottleneck, or when the store has no joins (most NoSQL). Examples: store author_name inside each post so rendering a feed needs no join; keep an order_total column instead of summing line items each time; maintain a like_count counter.

You pay with write complexity and possible inconsistency: every copy must be updated when the source changes, via the same transaction, a trigger, or an async pipeline. Decide per field whether staleness matters. Author display name being stale for a few seconds is fine; a stale price at checkout is not. Start normalised, denormalize measured hot paths.

What does "model data for access patterns" mean in NoSQL? Intermediate

In relational design you model the entities first and write queries later. In a store like DynamoDB or Cassandra you list the queries first, then design keys so each query is a single-partition read. Example for an e-commerce app on DynamoDB:

  • Q1: get customer profile: key PK=CUST#42, SK=PROFILE.
  • Q2: list a customer's orders newest first: PK=CUST#42, SK=ORDER#2026-11-17#9001, one query returns profile and orders together (single-table design).
  • Q3: find an order by id: a global secondary index on order id.

Pitfalls: a new query that no key supports means a table scan or a migration, so confirm access patterns before committing, and watch for hot partition keys.

Embed or reference in a document model? Intermediate

Hybrid is common: embed a snapshot (product name and price at order time, which should be frozen anyway) and also store the product id as a reference.

How do you model many-to-many relationships (for example users and groups) across SQL and NoSQL? Intermediate

SQL: a join table membership(user_id, group_id) with indexes in both directions. NoSQL: store the relationship twice, one item per direction, keyed so each direction is a single-partition query (PK=USER#1, SK=GROUP#7 and PK=GROUP#7, SK=USER#1), and update both together (transactional write if the store offers it, else an idempotent pair of writes). Very large groups need paging and bucketing to avoid a giant partition.

How do you change a schema with no downtime? Senior

Use the expand and contract (parallel change) pattern, so that old and new application versions work with the database at every step. To rename column name to full_name:

  1. Expand: add the nullable column full_name (no table rewrite in most engines when it has no default or a cheap default).
  2. Deploy code that writes to both columns and reads from the old one.
  3. Backfill old rows in small batches (throttled, with pauses) so it does not saturate the primary or replication.
  4. Deploy code that reads from the new column (verify equality first, perhaps in shadow mode).
  5. Stop writing the old column, then later contract: drop it in a separate release.
Trap: a single migration that renames the column while old servers still run causes errors during the rolling deploy. Also never mix a risky schema change and a code change in the same release; each step must be independently reversible.
Which schema changes are dangerous on a big table, and how do you do them safely? Senior
  • Adding an index: may lock writes. Use online variants (Postgres CREATE INDEX CONCURRENTLY, MySQL online DDL) and watch the I/O.
  • Adding a column with a default or changing a type: older engines rewrite the whole table under a lock. Newer ones (Postgres 11 and later for constant defaults) avoid this; check your version.
  • Adding NOT NULL or a foreign key: validates all rows under lock. Add as NOT VALID or as a check, backfill, then validate separately.
  • Large backfills: single huge UPDATE bloats the log, lags replicas and holds locks; batch by primary key range.
  • Tools: gh-ost, pt-online-schema-change (MySQL) build a shadow table, copy rows, tail the change stream, then swap names.
  • Always set a lock timeout so a blocked DDL fails instead of queueing behind a long query and stalling every other query behind it.
How do you evolve schemas in schemaless stores and in event or file formats? Senior

"Schemaless" really means schema-on-read: the code must handle every shape ever written. Include a schemaVersion field, make new fields optional with defaults, and either migrate lazily on read (upgrade and write back) or with a background job. For serialized data (Avro, Protobuf, Parquet) use a schema registry and follow compatibility rules: adding optional fields is backward and forward compatible; renaming or changing a type is not. Never reuse a field number or name for a different meaning.

What is soft delete, and what are its pitfalls? Intermediate

Instead of removing a row, set deleted_at (or is_deleted). Benefits: undo, audit trail, safe references from other tables, easier sync (clients learn of deletes). Pitfalls:

  • Every query must filter deleted_at IS NULL; one forgotten filter leaks deleted data. Use views, ORM defaults, or row-level policies.
  • Unique constraints break: a deleted user's email blocks re-registration. Use a partial unique index WHERE deleted_at IS NULL.
  • Tables and indexes grow forever; need a purge or archive job.
  • Compliance: laws such as GDPR require real erasure on request, so soft delete alone is not enough; add a hard-delete or anonymisation path with a defined delay.
  • Foreign key and cascade semantics become manual.
How do you store a counter, such as likes or view counts, at scale? Senior
  • Low rate: UPDATE ... SET n = n + 1 (atomic) is fine.
  • A hot row (a viral post) serialises on one row lock. Fix: shard the counter into N sub-counters and sum them on read; or buffer increments in Redis and flush totals periodically; or stream events to Kafka and aggregate.
  • Exact uniqueness (unique viewers) needs a set or an approximate structure such as HyperLogLog (about 12 KB per counter, about 1 percent error in Redis).
  • Accept eventual consistency in the displayed count if the business allows; keep the authoritative record (the like rows) separately.
When is a JSON column in a relational table a good idea? Intermediate

Good for sparse, rarely queried, user-defined attributes or for storing a raw payload alongside parsed columns. Postgres jsonb supports indexing (GIN) and operators. Bad when you filter, join, or enforce constraints on those fields constantly, since you lose type checks, foreign keys and efficient statistics. Rule: columns for what you query and constrain, JSON for the long tail.

Databases need block storage for random in-place I/O. User content and backups go in object storage.

Why not store images in the database? Basic

Large blobs bloat tables and backups, evict useful pages from the buffer cache, make replication slow, and use expensive database storage and I/O for data that needs no queries. Object storage is much cheaper per GB, scales without sharding effort, serves directly to browsers (and through a CDN), and is replicated for durability. Store the object key and metadata (owner, size, content type, checksum) in the database. Small blobs (a few KB, such as avatars thumbnails) in the database are sometimes acceptable for simplicity.

How does an object store such as S3 achieve its durability and scale? Senior

At concept level: objects are split and stored redundantly across many disks and several availability zones, either by full replication (3 copies) or erasure coding (split into k data and m parity fragments, any k of k+m rebuild the object, about 1.4x to 1.5x storage instead of 3x). Metadata (key to location) lives in a separate, partitioned index service; listing and lookups go through the key prefix, so very hot prefixes may need spreading. Background scrubbing verifies checksums and repairs bad fragments. AWS advertises 11 nines of durability for S3, which means very low data-loss probability, not that availability is 100 percent. S3 has offered strong read-after-write consistency since December 2020.

How do you design uploads of large files (for example 5 GB videos)? Senior
  1. Do not route bytes through your app servers. The client asks your API for an upload, authorises it, and gets a pre-signed URL (time-limited, scoped to one key) to upload directly to object storage.
  2. Multipart / chunked upload: split into parts (for example 8 to 100 MB). Upload parts in parallel, retry only failed parts, and finish with a "complete" call that assembles them. S3 multipart allows up to 10,000 parts per object.
  3. Resumability: the client asks which parts are already stored and continues (S3 multipart ListParts, or the tus protocol).
  4. Integrity: per-part checksum (MD5, CRC32C or SHA-256) verified by the store; whole-file checksum recorded.
  5. Completion event: the store emits an event (notification to a queue) that triggers post-processing: virus scan, transcoding, thumbnail, metadata row update. Mark the item "processing" until done.
  6. Cleanup: a lifecycle rule aborts incomplete multipart uploads after N days, otherwise orphan parts silently cost money.
  7. Security: validate content type and size limits at presign time and after upload, scan before serving, serve user content from a separate domain.
How do you serve large or popular files efficiently? Intermediate

Put a CDN in front of object storage so popular content is served from edge caches near users; set cache headers and use versioned or content-hashed file names so you can cache for a long time and "invalidate" by changing the name. Support HTTP range requests so players can seek and downloads can resume. For private content use signed URLs or signed cookies with expiry. For video, use adaptive bitrate streaming (HLS or DASH): pre-transcode into several resolutions chopped in a few-second segments.

How would you avoid storing duplicate files? Intermediate

Content-addressable storage: compute a hash (SHA-256) of the file and use it as the object key. If the key already exists, skip the upload and just add a reference row (user to hash). Needs reference counting, or a garbage-collection sweep, before deleting a blob. For large files, hash per chunk (4 MB chunks as in Dropbox-like sync) to dedupe partial similarity and upload only changed chunks. Privacy note: letting a client learn "this hash already exists" can leak that someone else has the file, so some systems still require a proof of possession.

How do you structure file metadata versus file data? Intermediate

Keep a metadata table (id, owner, name, size, content type, checksum, storage key, status, created_at) in a database where you can query and enforce permissions, and keep bytes in object storage under a key derived from an id (not from the user-provided name, which can collide or be malicious). Make the two consistent with an order of operations: create metadata as PENDING, upload, then flip to READY on the completion event; a sweeper removes stale pending rows and orphaned objects.

Retention, tiering, time-series, analytics and search

How do you design data retention and archival? Intermediate

Start from requirements: how long must the data be kept (legal, audit, business), how long must it be fast, and when must it be deleted (privacy). Then define tiers:

TierAgeStorageAccess
Hot0 to 30 daysPrimary database or SSD-backed storeMilliseconds
Warm1 to 12 monthsCheaper store, compressed, fewer replicasSeconds
Cold1 to 7 yearsObject storage in columnar files (Parquet), infrequent-access classMinutes, via query engine
ArchiveCompliance onlyGlacier-type classHours to restore

Automate moves with lifecycle policies (object storage) or scheduled jobs (copy, verify, then delete from hot). Make retention a per-data-class setting, keep an index so archived records can be found, and test restores, since an archive that cannot be read back is not an archive.

Why partition big tables by time, and how does it help retention? Intermediate

With range partitions per day or month, queries with a time filter touch only relevant partitions (partition pruning), indexes per partition stay small, and old data leaves by dropping or detaching a partition, an instant metadata operation. Compare with DELETE FROM t WHERE ts < ... on 2 billion rows: hours of work, huge log volume, replica lag, table bloat and vacuum pressure. Same idea in Cassandra (TTL plus time-window compaction), Elasticsearch (index per day, then delete old indices) and time-series databases (chunks).

What is downsampling and why do metric systems use it? Intermediate

Keep raw data at full resolution for a short window (say 15 days at 10-second points) and keep rolled-up aggregates (min, max, average, count per 5 minutes, then per hour) for longer. Trend charts for the last year do not need 10-second points, and storage drops by orders of magnitude (360 raw points per hour become 1 rollup). Store both sum and count, not just average, so you can combine rollups correctly. Trade-off: you cannot recover spikes inside the rolled-up interval, so keep max and percentile sketches when they matter.

How does data get from the operational database into analytics storage? Intermediate
  • Batch ETL or ELT: nightly or hourly extract, load into a warehouse, then transform with SQL. Simple, but data is hours old and extracts load the source.
  • Change data capture (CDC): read the database's log (Debezium and similar) and stream row changes to Kafka then into the warehouse or lake; low latency and minimal source load, and preserves deletes.
  • Dual write from the app: avoid; the two writes can diverge.

Land raw data in object storage as Parquet partitioned by date (a data lake), then query with Spark, Trino, Athena or a warehouse. Never run heavy analytics on the primary; at most a dedicated replica.

Data lake versus data warehouse? Intermediate

A warehouse stores curated, structured data with a schema, optimised for SQL analytics and BI (Snowflake, BigQuery, Redshift). A lake stores raw data of any form in cheap object storage (schema on read) for data science, machine learning and reprocessing. Modern "lakehouse" table formats (Iceberg, Delta, Hudi) add transactions and schema evolution to files in object storage, blurring the line. The lake is usually the cheap source of truth for raw history; the warehouse serves fast, governed queries.

How does full-text search work at a conceptual level? Intermediate
  1. Analysis: text is split into tokens, lowercased, stripped of stop words, and stemmed ("running" to "run"), so queries match word variants.
  2. Inverted index: map each term to a posting list of documents (and positions) containing it. Query "red shoes" fetches two lists and intersects or unions them.
  3. Ranking: score by relevance, classically TF-IDF or BM25 (term frequency in the document, rarity across the corpus, field length), plus boosts.
  4. Scale: the index is split into shards across nodes; a query fans out to all shards and merges the top results.

A SQL LIKE '%shoe%' cannot use a B-tree and scans every row; that is why a real search index is needed once data and query variety grow. Postgres full-text search is enough for modest needs; use a dedicated engine for faceting, fuzzy matching, typo tolerance and large corpora.

How do you keep a search index in sync with the primary database? Senior
  • Outbox or CDC: changes in the primary produce events consumed by an indexer. Reliable and ordered per key.
  • Use versions: index with an external version (updated_at or sequence) so late or duplicate events cannot overwrite newer state.
  • Handle deletes explicitly (tombstone events).
  • Reindex plan: mapping changes need a new index; build it in parallel from the source, then switch an alias atomically.
  • Expect lag (seconds). Where users must see their own write (their new post), read that item from the primary, or show it optimistically.
How would you store and query location data ("restaurants within 2 km")? Senior

Plain latitude and longitude columns with range filters scan too much. Options: a geospatial index (PostGIS GiST, MongoDB 2dsphere, Redis GEO) using R-trees; or map points into a geohash or a hierarchical cell id (S2, H3), so nearby points share a prefix or cell. Query the target cell plus its neighbours, then filter by exact distance. Geohash cells have edge effects (two close points can have different prefixes), so always check neighbour cells. Choose cell size by typical radius; very dense areas may need adaptive subdivision (quadtree).

Connection pooling, N+1 and slow queries

What is connection pooling and why is it needed? Basic

Opening a database connection costs a TCP handshake, TLS, authentication, and (in Postgres) a whole server process, and the database can only hold so many (often hundreds). A pool keeps a fixed set of open connections that application threads borrow and return, saving setup time and capping load on the database.

Key settings: maximum pool size, minimum idle, connection timeout (how long a caller waits for a free connection), idle timeout, max lifetime (shorter than any firewall or database idle cut-off), and validation. Examples: HikariCP in Java, PgBouncer in front of Postgres.

How do you size a connection pool? Senior

Bigger is not better. The database does real work only on about as many connections as it has CPU cores and disk parallelism; extra ones just queue inside it and add context switching. A common starting formula is about (2 x cores) + effective spindles for the database total, then tested under load. The important arithmetic: per-instance pool size x number of instances must stay below the database's max connections. With 50 pods and a pool of 20 you ask for 1,000 connections. Autoscaling the app tier can therefore take down the database. Use a pooler (PgBouncer in transaction mode) or a smaller pool, and use Little's law: connections needed is about queries per second x average query time in seconds (200 qps x 0.02 s = 4 busy connections).

Requests suddenly hang with "timeout waiting for connection from pool". What happened? Senior

The pool is exhausted: all connections are checked out. Typical causes:

  • Connection leak: code borrows and never returns (missing close, exception path). Pool active count rises and never falls. Use leak detection.
  • Slow queries or a lock hold connections longer, so throughput of the pool drops; a long transaction blocking others piles up requests.
  • Holding a connection while doing slow non-database work (calling an external HTTP API inside a transaction).
  • Traffic spike or retry storm.
  • A database failover leaving dead connections in the pool.

Fix by finding the root cause in pool metrics (active, idle, pending) and slow-query logs, keep transactions short, set statement and connection timeouts, and not simply raising the pool size, which pushes the overload onto the database.

What is the N+1 query problem and how do you fix it? Basic

Loading a list with one query, then issuing one more query per item for related data. Fetching 100 orders and then each order's customer produces 1 + 100 = 101 queries; each is fast, but the round trips add up (100 x 2 ms = 200 ms) and load the database. Common with ORMs due to lazy loading.

Fixes: a join (or fetch join), a batched WHERE id IN (...) second query (2 queries total), the ORM's eager or batch-fetch option, or a data-loader that batches within a request (GraphQL). Detect with query counts per request in tests and logs. Fixing N+1 by joining may cause huge row multiplication when joining several collections; then use separate batched queries.

A query became slow in production. How do you investigate? Senior
  1. Confirm and scope: which query, since when, how often, how slow (p50 vs p99). Use the slow query log or pg_stat_statements. What changed: deploy, data growth, new traffic, schema change?
  2. Look at the plan: EXPLAIN (ANALYZE). Look for sequential scans on big tables, estimated versus actual row counts far apart (stale statistics), sorts spilling to disk, nested loops over large sets, and many rows fetched then discarded.
  3. Check the environment: lock waits, long-running transactions, cache hit ratio, replication lag, I/O saturation, connection count.
  4. Fix by cheapest effective action: add or reshape an index, rewrite the query (select needed columns, avoid functions on indexed columns), update statistics, paginate with keyset instead of offset, cache results, precompute.
  5. Prevent: alert on query latency, load-test with production-sized data, review plans in code review.
Why does LIMIT 20 OFFSET 1000000 get slower, and what is the alternative? Intermediate

The database must produce and discard the first million rows before returning 20, so cost grows with the offset. Pages also drift when rows are inserted during browsing. Use keyset (seek) pagination: remember the last row's sort key and ask for the next page with WHERE (created_at, id) < (:last_ts, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20, backed by an index on (created_at, id). Cost stays constant per page. The trade-off is that you cannot jump to "page 500" directly; most feeds do not need that.

Name common query-level mistakes that hurt performance. Intermediate
  • SELECT * when you need 3 columns (more I/O, defeats covering indexes).
  • Queries in a loop instead of one set-based query; row-by-row inserts instead of batches (batching 1,000 inserts per statement or using bulk load can be 10x to 100x faster).
  • Functions on indexed columns; implicit type casts.
  • Unbounded queries with no LIMIT.
  • Large IN lists or counting a whole table (COUNT(*) on a billion rows) on the hot path; keep a maintained counter or use an estimate.
  • Long transactions and holding locks while calling other services.
  • Sorting large result sets without an index.

Read-heavy versus write-heavy design

What are the main levers for a read-heavy workload? Intermediate
  1. Indexes and good queries first; cheapest and most effective.
  2. Caching: application cache (Redis), HTTP and CDN cache for public content. Highest leverage because most reads never reach the database.
  3. Read replicas: scale reads horizontally; accept replication lag (read-your-writes needs care, such as reading from the primary for a short time after a write).
  4. Denormalize or precompute: materialised views, summary tables, precomputed feeds.
  5. Search engine or column store for complex read patterns.
  6. Sharding when even this is not enough.

Storage of choice: B-tree based relational store with replicas plus cache.

What are the main levers for a write-heavy workload? Intermediate
  1. Choose a write-optimised engine: LSM-based store (Cassandra, ScyllaDB, DynamoDB, RocksDB-based) for sustained ingestion.
  2. Shard (partition) writes by a key with good distribution so no hot partition forms; replicas do not help writes since every replica applies every write.
  3. Batch and buffer: put a queue or log (Kafka) in front, and write in batches, which smooths spikes and lets storage work at its own pace. Group commits.
  4. Reduce write cost: fewer indexes, narrower rows, append-only models instead of update in place, async index building.
  5. Aggregate before storing (counters, rollups) when raw events are not needed individually.
  6. Mind durability settings: relaxing fsync or replication acknowledgement buys speed at the cost of possible loss; only where acceptable.
How do you quickly estimate whether one database node can handle the load? Intermediate

Rough rules (hedge them, since hardware varies): a well-tuned relational node on SSD handles on the order of 1,000 to 10,000 simple writes per second and maybe 10,000 to 50,000 indexed reads per second; a LSM store node often ingests tens of thousands of writes per second per node. Convert business numbers: 100 million daily active users each making 10 requests = 1 billion requests per day, about 11,600 per second on average, with peaks 2x to 5x. Then ask the read/write split, payload size, and total data per year (rows x row size x retention) to compare with node disk and RAM. If you exceed a single node on any axis (writes, storage, working set in RAM), plan sharding or a distributed store.

What is a materialized view and when do you use one? Intermediate

A query result stored physically as a table and refreshed on a schedule or incrementally. Use it when an expensive aggregation is read often and slight staleness is fine, such as a daily sales summary dashboard. It trades storage and refresh work for read speed. The caveat is staleness and the refresh cost; databases differ on whether refresh is incremental or a full recompute and whether it blocks reads.

What is the idea of separating the write model from the read model (CQRS) in storage terms? Senior

Writes go to a store shaped for correctness and transactions (normalised relational or an event log); a pipeline projects those changes into one or more read stores shaped for each query (denormalised documents, search index, cache, column store). Each side scales and is tuned independently. The price is eventual consistency between them, extra moving parts, and the need to rebuild a projection from the log when a read model changes. Use it when read and write shapes or loads differ greatly, not as default.

Scenarios and real-life problems

Your primary database CPU is at 95 percent every afternoon and latency is climbing. What do you do? Senior
  1. Triage now: find the top queries by total time (not only slowest); look for a new deploy, a runaway job, or a missing index. Kill or throttle offending jobs; shed non-essential load.
  2. Short-term fixes: add the missing index (online), move reports to a replica, add caching for the hottest read, lower pool sizes if connections are thrashing.
  3. Medium term: read replicas, query rewrites, denormalise hot paths, partition large tables.
  4. Long term: vertical scale if cheap, then sharding or move workloads to better-fit stores.

Say that you would measure before changing anything and change one thing at a time.

A DynamoDB or Cassandra table throttles even though total capacity looks fine. What is wrong? Senior

A hot partition: one partition key receives a disproportionate share of traffic (a celebrity user, a "today's date" key, a tenant id with one giant tenant), and per-partition throughput limits apply regardless of the table total. Fixes: pick a higher-cardinality key; add a random or calculated suffix (write sharding, key#0..9) and read all suffixes; cache hot reads; for time-based keys combine with another dimension; split big tenants. Check the key distribution before launch, using expected traffic, not just row counts.

A migration that added an index locked the orders table for 20 minutes during peak. How do you prevent a repeat? Senior
  • Use online index creation (concurrent build) and a lock timeout, so the statement gives up instead of blocking.
  • Rehearse on a production-sized copy to learn duration and I/O effect.
  • Run in off-peak windows with a kill switch; watch replication lag during the build.
  • Review DDL like code, with a checklist (locks taken, table rewrite, backfill batching).
  • For big changes, use online schema-change tools (gh-ost, pt-osc) or expand and contract.
A write-heavy database disk hit 100 percent and the database stopped accepting writes. How could this happen and what do you do? Senior

Common causes: logs or WAL growing because a replica or CDC consumer stopped consuming (the replication slot retains log files, a known Postgres hazard); a long transaction preventing cleanup of old versions; compaction needing temporary space; unbounded table growth with no retention; runaway temp files from a bad query.

Response: free space safely (remove the stuck replication slot or fix the consumer, drop old partitions, expand the volume online), confirm no corruption, then add the missing guardrails: disk-usage alerts at 70 and 85 percent, max slot or retention limits, retention jobs and capacity forecasting.

Users update their profile and, on refresh, see the old value. The system uses read replicas. Why, and how do you fix it? Intermediate

Asynchronous replication lag: the write went to the primary and the read hit a replica that has not applied it yet. Fixes: read-your-writes routing (after a write, send that user's reads to the primary for a few seconds, or until the replica's log position passes the write's position); sticky routing for a session; write the new value into the client or cache immediately; or synchronous replication for critical paths at a latency cost. Monitor lag and fall back to the primary when lag exceeds a threshold.

You need to pick storage for a messaging inbox with 1 billion messages per day and a "load latest 50 messages of a conversation" query. What do you reason? Senior

Dominant operations: very high append rate, read the newest N of one conversation, rarely update, retention for a long time. That points to an LSM wide-column or key-value store partitioned by conversation id, clustered by time descending, so the latest 50 are one sequential read of one partition. 1 billion per day is about 11,600 writes per second on average, easily spread across nodes. Watch partition size for very long conversations (bucket by time, for example per month), keep message ids time-ordered, keep older data in cheaper tiers, and keep search over history as a separate derived index. A relational store would work at smaller scale; the argument for the wide-column store is write volume and horizontal scaling. (This is reasoning about a storage choice, not a full design.)

Insert latency on a table keeps degrading as it grows past memory, though the query load is unchanged. What is likely and what do you do? Senior

The primary key is probably a random UUID. Random inserts touch random leaf pages of the B-tree; once the index no longer fits in RAM, almost every insert causes a disk read plus page splits. Remedies: time-ordered keys (UUID v7, ULID, bigint sequence) so inserts hit the hot right-edge pages; remove unneeded indexes; partition by time so the active partition's indexes fit in memory; more RAM. Changing a primary key on a large live table needs an expand and contract migration.

Can you describe an industry incident where database operations or backups failed badly, and the lessons? Senior

GitLab, January 2017: an engineer trying to fix replication lag on the production Postgres ran a delete of a data directory on the wrong server, removing a large amount of production data. Recovery was hard because several backup mechanisms turned out not to be working as expected, and they restored from a staging snapshot taken some hours earlier, losing several hours of data (the company published a detailed public post-mortem and live-streamed the recovery). Details such as exact figures are best checked against their post-mortem.

Lessons: backups are only real if restores are tested regularly; make destructive commands hard to run on production (distinct prompts, access separation); monitor backup jobs and alert on failure; keep replication and backup tooling simple and documented.

What are lessons from large-scale database outages caused by cascading load or failover? Senior

A well-known pattern: GitHub, October 2018 had a brief loss of network connectivity between data centers, which triggered an automated MySQL primary failover to the other site; the two sides had accepted different writes, and it took a long time (more than a day, as I recall) to reconcile and restore, with degraded service. Takeaways (hedged, see the company post-mortem): automated failover across high-latency links can produce split-brain style divergence; cross-region replication must be designed for partitions; and recovery from divergent data is slow and manual, so rehearse it.

More generally: failover storms (every client reconnecting at once) and connection pools overwhelming a freshly promoted primary are common second-order failures. Use jittered backoff and connection limits.
