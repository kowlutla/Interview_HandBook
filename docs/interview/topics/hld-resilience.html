HLD: Resilience and High Availability interview questions

Availability math and nines, redundancy and failover, timeouts, retries, circuit breakers, bulkheads, load shedding, backpressure, graceful degradation, multi-AZ and multi-region, disaster recovery, chaos engineering, safe deployments, cells and blast radius, and SLOs with error budgets, as interviewers ask them.

How to use this page

Each question is a collapsible. Try to answer aloud first, then open it. Resilience questions are rarely about a single technique. Interviewers want to hear that you know what fails, how failure spreads, and which small mechanism stops it from spreading. A good habit: for any design, say "what happens when this dependency is slow, not just down?" Slow is worse than down, because slow ties up threads and connections.

Availability math, SPOFs and redundancy

What is availability, and how is it measured? Basic

Availability is the fraction of time (or of requests) in which a system does its job correctly. Time-based: uptime / (uptime + downtime). Request-based (more common at large companies): successful requests / valid requests. Request-based is better because a partial outage that fails 30 percent of calls for an hour is not "up" and not "down" in a time-based view.

Two things people forget: define what "successful" means (a 200 that takes 40 seconds is a failure for the user), and decide who measures it (from inside the service, or from a probe or the client side). Client-side measurement catches network and DNS problems the server never sees.

How much downtime does each "nine" allow? Basic
AvailabilityDowntime per yearPer 30-day month
99% (two nines)about 3.65 daysabout 7.2 hours
99.9%about 8.8 hoursabout 43 minutes
99.95%about 4.4 hoursabout 22 minutes
99.99%about 52 minutesabout 4.3 minutes
99.999%about 5.3 minutesabout 26 seconds

Memory trick: 99.9 percent is about 43 minutes a month. Each extra nine divides by ten. At four nines you have 4 minutes a month, which is less than a human can even page, log in and diagnose. So four nines and above must be reached through automation (automatic failover, automatic rollback), not through on-call heroics.

How do you compute the availability of a system built from several components? Intermediate

In series (every component must work): multiply. A request that goes through a load balancer (99.99%), an app (99.95%) and a database (99.95%) gives 0.9999 x 0.9995 x 0.9995 = about 99.89%. Series chains are always worse than their weakest link, and every extra hard dependency costs you.

In parallel (redundant, any one is enough): multiply the failure probabilities. Two independent replicas each at 99% give 1 - (0.01 x 0.01) = 99.99%. Three give 99.9999%.

Trap: the parallel formula assumes failures are independent. Two replicas in the same rack, same AZ, same deployment pipeline or sharing one config push fail together. Real availability of "redundant" systems is capped by the shared parts: the deploy tool, the DNS, the config store, the human operator.
Say: "If my service has five hard dependencies each at 99.9 percent, I cannot promise better than about 99.5 percent unless I make some of them soft dependencies with fallbacks."
What is a single point of failure, and how do you find them in a design? Basic

A single point of failure (SPOF) is any component whose failure takes down the whole system because there is no alternative. Walk the request path and ask "if this box vanished now, what happens?" for each item:

  • Obvious: one database primary, one load balancer, one app server.
  • Less obvious: one DNS provider, one certificate that expires, one config or feature-flag service, one auth service, one message broker, one AZ, one cloud region, one engineer who knows the runbook, one CI/CD pipeline you need to push a fix.
  • Logical SPOFs: a bad config pushed to all nodes at once, a shared library bug, a poison message that crashes every consumer.

Remove a SPOF by redundancy (N+1 or more) plus automatic failover, or by making the dependency optional. Redundancy that you never test is a SPOF you believe is gone.

What types of redundancy exist (N+1, N+2, 2N, active-active)? Intermediate
  • N+1: N units carry the load, one spare. Cheap, survives a single failure. During a failure you run at full utilization of what is left.
  • N+2: survives one failure while another unit is in maintenance or deploying. Common for stateless tiers.
  • 2N: a full duplicate of everything. Expensive, used for critical facilities or regions.
  • Active-active: all copies serve traffic. Spare capacity is spread out, not idle.
  • Active-passive: a standby sits idle until needed.

Key sizing point: if you have 3 AZs and want to survive one AZ loss, each AZ must be able to take 50 percent more load, so you run at most about 66 percent utilization overall. With 2 AZs it is 50 percent. This is why "N+1 across AZs" costs more headroom than it sounds.

Why is making a stateless tier highly available easy but a stateful tier hard? Intermediate

Stateless servers are interchangeable. Put N behind a load balancer, drop the dead ones, add more. Nothing is lost when one dies.

Stateful systems (databases, queues, caches with data) must keep copies consistent. Failover then forces choices: lose the last few writes (asynchronous replication, nonzero RPO), or pay write latency and availability (synchronous or quorum replication). Also split brain: two nodes both believing they are primary. Hence the standard advice: push state to a small number of well-understood replicated stores, and keep everything else stateless.

Failover, standby modes and health checks

Compare active-active and active-passive. When do you pick which? Intermediate
Active-passiveActive-active
TrafficPrimary serves, standby waitsAll nodes serve
Capacity useStandby idle (waste)Good use of hardware
FailoverNeeds detection and promotion, so a gap of seconds to minutesNear instant, remaining nodes absorb the load
Hidden riskStandby is untested and may not work when neededRemaining nodes may be overloaded after a loss; data conflicts if stateful
DataSingle writer, simple consistencyMultiple writers need conflict resolution or partitioned ownership

Pick active-active for stateless services and for data that can be partitioned or tolerates conflicts (last-write-wins, CRDTs). Pick active-passive for strongly consistent single-writer data (a relational primary) where conflict handling is too costly. Note that "active-active" databases often really mean each partition has one owner, with different owners in different regions.

What are hot, warm and cold standby? Basic
  • Hot: standby is running, data replicated continuously, can take traffic in seconds. Highest cost, lowest recovery time.
  • Warm: standby exists but scaled down (for example a small replica, or servers running at minimum size). Needs scale-up before full load. Minutes.
  • Cold: only backups and infrastructure code exist. You build the environment and restore data when disaster strikes. Cheapest, hours or more.

The choice is a cost versus recovery time trade, driven by the business RTO and RPO (see the DR section).

Walk through what actually happens during an automatic database failover. What can go wrong? Senior
  1. Monitor detects the primary is unhealthy (missed heartbeats for N seconds).
  2. Quorum or a consensus service confirms the primary is really gone, to avoid split brain.
  3. The old primary is fenced (cut off from storage, network, or killed) so it cannot accept writes if it wakes up.
  4. The most up-to-date replica is promoted.
  5. Clients are redirected (DNS update, virtual IP, proxy, or client library discovery).
  6. Remaining replicas repoint to the new primary. The old primary rejoins as a replica after catching up or rewinding.

Things that go wrong: false positive from a network blip causing needless failover (flapping); lost writes with asynchronous replication; split brain when fencing fails; stale DNS caches and connection pools still pointing at the old primary; replica promoted is far behind; the new primary cannot handle the load because caches are cold; failover triggers during an overload and the retry storm kills the new primary too. Tune detection time: too short means flapping, too long means longer outage.

What is split brain and how do you prevent it? Intermediate

Split brain is two nodes (or two partitions) each believing they are the leader and both accepting writes, so data diverges. It happens when failure detection mistakes a network partition for a node death.

Prevention: majority quorum (a leader needs votes from more than half of the nodes, so only one side of a partition can have it), fencing tokens (a monotonically increasing number so storage rejects writes from an old leader), STONITH (shoot the other node in the head, power-fence it), and leases with clock-bounded expiry. Use an odd number of voters, typically 3 or 5.

What is a health check? How do liveness, readiness and deep checks differ? Basic

A health check is an endpoint or probe that tells the load balancer or orchestrator whether an instance should receive traffic or be restarted.

  • Liveness: is the process alive and not stuck? Failure means restart it. Keep it trivial (no dependency calls).
  • Readiness: can it serve traffic right now (warmed up, config loaded, connected)? Failure means remove from the load balancer but do not restart.
  • Startup: gives slow-booting apps time before liveness begins.
  • Shallow vs deep: shallow checks only the process; deep checks dependencies such as the DB.
Trap: a deep health check that calls the database. When the database slows down, every instance fails its check, the load balancer removes all of them, and a partial dependency problem becomes a total outage. Also the restart loop (liveness fails because a dependency is down) makes things worse. Prefer shallow liveness, readiness that checks only local state, and handle dependency failure inside the request path with breakers and fallbacks. Many load balancers also have a "panic mode" or fail-open: if all targets look unhealthy, send traffic to all anyway.
How do you tune health check interval, threshold and timeout? Intermediate

Time to detect failure is about interval x unhealthy-threshold. Example: check every 5 s, 3 failures required, so about 15 s to eject. Faster detection means more false positives from a single dropped probe or GC pause. Use a threshold of 2 to 3 to filter noise, a lower threshold for healthy (to rejoin) or a higher one to avoid flapping, and a probe timeout shorter than the interval. Passive health checking (watch real traffic errors, outlier detection) catches failures faster than active probes and costs nothing extra; combine both.

What is a gray failure and why is it hard? Senior

A gray failure is a component that is neither fully up nor fully down: it passes health checks but is slow, drops some requests, or has one bad disk or NIC. Binary detection misses it, and the node keeps receiving its full share of traffic.

Defences: outlier detection on real traffic (eject hosts whose error rate or latency is far above the fleet), client-side observation and not only server self-reporting, comparing a node with its peers, and load balancing algorithms that favour fast nodes (least outstanding requests, power of two choices). Hedged requests also mask it for the caller.

Can you use DNS for failover? What are the limits? Intermediate

Yes: health-checked DNS records (for example weighted or failover routing) steer clients to a healthy endpoint. Limits: the TTL and, more importantly, clients, resolvers and JVMs that cache beyond the TTL; connection pools holding long-lived connections to the old IP; slow propagation means a failover of minutes, not seconds. Use short TTLs (30 to 60 s) for failover records, and for faster switches use anycast or a global load balancer, or a virtual IP inside a site.

Timeouts and retries

Why must every remote call have a timeout? Basic

Without a timeout, a call to a hung dependency blocks a thread (or connection, or socket) forever. Use Little's law: concurrent requests in flight = arrival rate x latency. At 500 requests per second and a normal 20 ms latency you need about 10 busy threads. If the dependency hangs and latency goes to infinity, in-flight work grows until your pool of, say, 200 threads is exhausted in under half a second, and your service is now down too, even though only a dependency failed. That is how one slow service becomes a cascading outage.

Many default client timeouts are infinite or very long (some HTTP clients, JDBC without socket timeouts). Always set connect timeout, read (response) timeout and an overall deadline explicitly.

How do you choose a timeout value? Intermediate
  • Start from the measured latency distribution of the dependency, not a guess. A common starting point is slightly above p99 or p99.9 of healthy latency (for example p99 is 80 ms, so timeout 200 to 300 ms).
  • Too short: healthy-but-slow calls get cut, and combined with retries you generate extra load.
  • Too long: threads pile up during failures, and the user has long gone anyway.
  • It must fit the caller budget: if your API promises 1 s total, and calls three dependencies in sequence, each timeout must be well below 1 s, and the retry must also fit.
  • Separate connect timeout (short, tens to hundreds of ms inside a data center) from read timeout.
  • Revisit with real data; alert when calls approach the timeout.
What is deadline propagation and why use it instead of per-hop timeouts? Senior

Instead of every hop having its own fixed timeout, the entry point sets a deadline (an absolute time or remaining budget) and passes it down in headers or context (gRPC does this natively with deadlines). Each downstream service uses only the remaining time and gives up when the deadline passes, and can refuse to start work that cannot finish.

Without it, a user who has already given up at 2 s still has three layers of services working until their individual 5 s timeouts, wasting capacity during exactly the moments when capacity is scarce. Also nested timeouts must decrease down the chain: if A waits 1 s for B but B waits 2 s for C, A times out and retries while B and C are still working on the abandoned request, which is amplification.

When should you retry a failed request, and when should you not? Basic

Retry when the failure is probably transient: connection reset, timeout, 503, 429 with a Retry-After, a throttled call. Do not retry when it will not help: 400 and other client errors, 401/403, validation failure, 404, or a deterministic bug. Do not retry non-idempotent operations unless they carry an idempotency key. And do not retry if the system is overloaded and you are not sure your retries are bounded, because retries add load to a system already failing.

What is exponential backoff with jitter, and why do you need the jitter? Intermediate

Backoff: wait longer between each retry, typically doubling: 100 ms, 200 ms, 400 ms, 800 ms, up to a cap (say 20 s) and a max attempt count. This gives the dependency time to recover.

Jitter: randomize the wait. Without it, 10,000 clients that failed at the same instant all retry at exactly 100 ms, then 200 ms, in synchronized waves, which keeps hitting the server in spikes (a thundering herd). Randomness spreads the retries over time.

full jitter:         sleep = random(0, min(cap, base * 2^attempt))
equal jitter:        t = min(cap, base * 2^attempt); sleep = t/2 + random(0, t/2)
decorrelated jitter: sleep = min(cap, random(base, prev_sleep * 3))

AWS's well-known analysis found full jitter to complete the total work in the least time under contention. State the rule: backoff controls how long, jitter controls when, and a cap plus attempt limit controls how much.

What is retry amplification? Give a numeric example. Senior

If each layer in a call chain retries independently, the number of requests multiplies. With a chain A calls B calls C calls D, and each layer makes up to 3 attempts, then when D is failing, D sees up to 3 x 3 x 3 = 27 attempts for every user request. A dependency that is merely struggling at 100 percent load suddenly gets 3x or more, and cannot recover.

Fixes: retry at one layer only (usually the one closest to the user or the one with the best knowledge), use retry budgets, make lower layers fail fast and not retry, propagate "do not retry" hints or a retry-attempt header so servers can shed retried traffic first, and always use deadlines so abandoned requests get dropped.

What is a retry storm and how does it keep an outage going after the root cause is fixed? Senior

A retry storm is a feedback loop: a brief slowdown causes timeouts, clients retry, the retries raise load, which causes more timeouts and more retries. The system reaches a metastable state where the extra retry load alone is enough to keep it overloaded, even after the original trigger (a deploy, a blip, a failover) has gone. Recovery then needs active action: shed load, turn retries off, restart in a throttled way, or temporarily reduce incoming traffic.

Prevent with backoff and jitter, retry budgets, circuit breakers, load shedding at the server, and capacity headroom. Google's SRE writing and AWS's builders library both describe this pattern, and several large outages have had a retry or reconnect storm as the amplifier.

What is a retry budget? How is it different from a fixed retry count? Senior

A fixed count says "up to 3 retries per request", which under a full outage triples traffic. A retry budget caps retries as a fraction of overall traffic: for example "retries may be at most 10 percent of the requests sent in the last minute" (or a token bucket that is topped up by successes and drained by retries). Under normal conditions a few failures get retried; during an outage the budget empties quickly and the client just fails fast, so total load rises by at most about 10 percent instead of 200 percent. Envoy, gRPC and Finagle all have forms of this.

What is idempotency and why is it required for safe retries? Basic

An operation is idempotent if doing it several times has the same effect as doing it once. Setting a value, PUT, DELETE are naturally idempotent. "Add 100 dollars to the balance" or "create an order" are not.

It matters because on a timeout the client cannot know whether the server did the work. If it retries a non-idempotent call, the customer may be charged twice. So either the operation is naturally idempotent or you give it an idempotency key.

How do you implement idempotency keys on the server? Intermediate
  1. Client generates a unique key (a UUID) per logical operation and sends it on the first try and every retry (header such as Idempotency-Key).
  2. Server does an atomic insert of the key into a store with a unique constraint, in the same transaction as the business write where possible.
  3. If the key is new: process and save the response with the key.
  4. If the key exists and is complete: return the saved response without redoing the work.
  5. If the key exists and is still in progress: return a conflict or make the caller wait.
  6. Expire keys after a window (for example 24 hours).
Trap: checking "have I seen this key?" and then doing the work as two separate steps is a race. The check and the claim must be atomic. Also validate that a reused key carries the same request body, otherwise return an error. For consumers of at-least-once queues, the same idea appears as a dedupe table keyed by message id.
What are hedged requests and when do they help? Senior

A hedged request sends the same read to a second replica if the first has not answered within a short delay (usually about the p95 latency), and uses whichever returns first, cancelling the other. It cuts tail latency. In Google's "The Tail at Scale" description, hedging after the 95th percentile adds only about 5 percent extra load but can slash the 99.9th percentile sharply.

Use only for idempotent, side-effect-free operations (reads), with cancellation, and keep hedges within a retry budget. Do not hedge when the system is already overloaded: it then amplifies load. It also helps with gray failures (one slow node) since the second copy goes to a different node.

Circuit breakers and bulkheads

What is a circuit breaker and what problem does it solve? Basic

A circuit breaker wraps calls to a dependency and watches their failures. When failures pass a threshold, it "opens" and immediately rejects further calls (fail fast) for a period, instead of letting each caller wait for a timeout. This protects the caller (no tied-up threads), and gives the sick dependency breathing room with no incoming load, so it can recover.

Like an electrical breaker, it trips to prevent damage, then is tested and reset.

Explain the three states of a circuit breaker. Intermediate
  • Closed: normal. Count failures or slow calls in a sliding window.
  • Open: after the failure rate crosses the threshold, reject immediately for a cool-down period (for example 30 s).
  • Half-open: after the cool-down allow a small number of trial requests. If they succeed, close; if any fails, reopen (often with a longer wait).
How do you tune a circuit breaker? What mistakes are common? Senior
  • Failure measure: use failure rate over a sliding window (for example 50 percent of the last 20 calls or last 10 s), with a minimum request volume (for example at least 20 calls) so two failures out of three at 3 AM do not trip it. Count timeouts and slow calls (slow-call-rate threshold), not just exceptions.
  • Which errors count: 5xx, timeouts, connection errors. Not 4xx caused by a bad request, or a business "not found".
  • Open duration: long enough for recovery (seconds to a minute), possibly growing with each failed probe.
  • Half-open probes: few, so you do not slam a recovering service.
  • Granularity: one breaker per dependency (or per endpoint or per host), not one global one. A breaker per instance isolates one bad host; per service reacts to whole-service failure.
  • What happens when open: have a defined fallback (cached value, default, queue for later, clear error), not just an exception.
Trap: breakers that are in each client process do not share state, so a fleet of 1,000 clients each need to see failures before tripping, and they all probe at slightly different times. Also, a too-sensitive breaker flaps and itself causes an outage; a breaker on a dependency with low traffic never gets enough samples.
How do circuit breakers, timeouts and retries fit together? Intermediate

Order of wrapping, outermost first, is typically: bulkhead, circuit breaker, retry (with backoff, budget), timeout around each attempt. Timeouts bound each call. Retries cover transient errors. The breaker notices persistent errors and stops retries and calls entirely. When the breaker is open, retries should not run (rejecting immediately is the point). Add a fallback outside everything. Each of them alone is not enough: retries without breaker amplify load, a breaker without timeouts never sees the slow failures.

What is the bulkhead pattern? Give an example. Intermediate

Named after ship compartments: isolate resources so a failure in one part cannot sink everything. Give each dependency (or each customer, or each request class) its own thread pool, connection pool, semaphore or queue with a hard cap.

Example: a service calls Payments and Recommendations with one shared pool of 200 threads. Recommendations becomes slow, all 200 threads end up stuck waiting on it, and checkout (Payments) cannot get a thread, so the whole service is down because of a nonessential feature. With separate pools (say 150 for payments, 30 for recommendations, 20 reserve) the recommendations pool is exhausted and fails fast while checkout keeps working.

Other bulkheads: separate clusters for internal versus public traffic, per-tenant quotas so one noisy tenant cannot starve others, separate processes, separate AZs or cells, and separate queues for priority classes.

Thread-pool bulkhead versus semaphore bulkhead? Senior

Thread-pool isolation runs the call on a dedicated pool: calls can be abandoned on timeout without blocking the caller thread, and the pool size is the cap. Costs: thread handoff, context switch, loss of thread-local context. Semaphore isolation just counts concurrent calls in the caller thread and rejects above N: very cheap, but a hung call still holds the caller thread (so you also need real timeouts). Use semaphores for fast, nonblocking or async clients, and pools for blocking calls to risky dependencies. With async or reactive stacks, limit in-flight requests with a concurrency limiter instead.

Overload, load shedding, rate limiting and backpressure

What happens to a server as load goes past its capacity, and what should it do? Intermediate

Without protection, throughput does not just plateau, it often collapses (goodput falls): queues grow, latency rises, requests time out on the client side but the server still processes them (wasted work), memory pressure and GC rise, and retries add load. The server spends its time on requests whose callers have given up.

A well-behaved server instead holds throughput at its maximum and rejects the excess quickly and cheaply: bounded queues, concurrency limits, load shedding with fast 503/429 and a Retry-After, dropping requests whose deadline has already passed, and prioritising important traffic. "Fail fast on the excess to keep serving the rest" is the principle.

What is load shedding? How is it different from rate limiting? Intermediate
Rate limitingLoad shedding
TriggerA per-client or per-key policy (quota)Actual server health (CPU, queue length, latency)
PurposeFairness, abuse prevention, costSurvive overload
Who is rejectedThe client exceeding its shareLowest-priority or newest requests, regardless of client
Static or dynamicMostly configured limitsDynamic, reacts to current state

You need both. Rate limits may all be respected and still overload you, for example when many clients are within quota after a failover shifted traffic. Shedding choices: drop by priority (health checks and checkout above analytics), drop requests already past deadline, drop the newest or oldest depending on policy (LIFO under overload can serve fresher requests that still have a live caller), and return a clear cheap error.

How do you decide when to start shedding? Senior
  • Concurrency limit: cap in-flight requests at a number derived from load tests. Adaptive limiters (like TCP congestion control, AIMD or gradient-based approaches in Netflix's concurrency-limits library) learn the limit from latency.
  • Queue delay: if a request has waited longer than X ms in the queue, drop it (CoDel style). Queue length alone is a poor signal, queue wait time is better.
  • CPU or memory thresholds, with a small hysteresis to avoid oscillation.
  • Per priority thresholds: shed lowest priority first at 70 percent, next at 85 percent, and so on, so critical traffic is last to go.

Make shedding cheap: reject before parsing the body or doing auth, as early as possible (at the edge or load balancer if you can).

How do rate limits and quotas protect a system from overload, and where should they be applied? Intermediate

They bound the maximum load any one caller can create, so one buggy client or abusive tenant cannot starve everyone (noisy neighbour). Apply at several layers: the edge or API gateway (per API key, per IP), per service (per upstream caller), and per expensive operation (exports, search). Return 429 with a Retry-After. Sum of per-client quotas should be sane relative to total capacity (otherwise quotas give no real protection), and quotas should be lower than the capacity you can actually deliver with one AZ lost.

Common algorithms: token bucket (allows bursts, steady refill rate), leaky bucket (smooths output), fixed window (simple, but allows a 2x burst at the window boundary), sliding window log or counter (accurate). Token bucket is the usual default. In a distributed setup, counters are kept in something like Redis, or each node enforces its share locally for lower latency and slight inaccuracy.

How does a token bucket work? Basic

A bucket holds up to B tokens and is refilled at R tokens per second. Each request removes one token; if the bucket is empty the request is rejected or delayed. So you allow a sustained rate of R and a burst up to B. Example: R = 10 per second and B = 50: a client idle for 5 seconds can send 50 requests at once, then 10 per second. Implementation needs only two numbers per key (tokens, last refill time), computed lazily at request time.

What is backpressure and how do you implement it? Intermediate

Backpressure is a signal from a slow consumer to a fast producer to slow down, instead of letting data pile up without bound. Without it, an unbounded queue just converts overload into memory exhaustion and huge latency.

  • Bounded queues: when full, block the producer, or reject.
  • Pull-based consumption: the consumer asks for work when ready (Kafka consumers poll, Reactive Streams request(n)).
  • Credits or windows: TCP flow control and HTTP/2 flow control windows.
  • Explicit signals: 429 or 503 plus Retry-After, gRPC resource-exhausted status.
  • Drop policies: drop oldest, drop newest, sample, or coalesce when data is lossy (metrics, telemetry).
Trap: an unbounded in-memory queue between threads is the classic hidden backpressure bug: everything looks fine until memory blows up. Always bound queues, and decide the full-queue policy deliberately.
What is queue-based load leveling and when do you use it? Intermediate

Put a durable queue between a bursty producer and a consumer that works at a steady rate. The queue absorbs spikes; consumers process at their sustainable pace, so the backend is sized for average load and not for peak. Example: a flash sale sends 20,000 orders per second for a minute, while the fulfilment system can do 2,000 per second. Orders are accepted into the queue and drained over ten minutes.

Conditions: the work can be asynchronous (user does not need an immediate result, so you return 202 Accepted and a status link), you monitor queue age and depth with an alert on "oldest message age", and you have a dead-letter queue for poison messages and a cap on how stale a message may become. Note the trade: latency rises during bursts, and you now have a second system to operate. If the queue grows without bound then consumers are simply under capacity; leveling handles bursts, not sustained overload.

What is a poison message and how do you stop it from taking a consumer fleet down? Intermediate

A message that always fails processing (bad format, triggers a bug). Under at-least-once delivery it is redelivered forever, blocking a partition or burning capacity, and sometimes crashing each consumer in turn. Use a max-retry count with backoff, then move the message to a dead-letter queue (DLQ) with its error context, alert on DLQ depth, and give operators a way to inspect and replay after the fix. Process the message inside a try-catch boundary so one bad record does not kill the process.

Graceful degradation, fallbacks and cascading failures

What is graceful degradation? Give examples. Basic

When a part fails or load is too high, the system keeps delivering its core function with reduced features, instead of failing completely. Examples:

  • Product page loads without recommendations, reviews or live stock count if those services are down.
  • Search falls back from personalised ranking to a simple popular-items list.
  • Video player lowers resolution and not stop playing.
  • Write path accepts orders and queues the confirmation email for later.
  • A site goes read-only during a database failover.

To make this possible, classify each dependency as hard (cannot function without it) or soft (nice to have) at design time, and make as many soft as you can.

Fail open or closedAllow the request if the authorisation or fraud check is down, or denyOpen risks security or fraud; closed risks availability
Trap: a fallback that is never exercised usually does not work when needed, and a fallback path that is heavier than the main path (for example falling back to a full database query when the cache dies) can itself cause the cascade. Test fallbacks regularly, and make sure they are cheaper than the primary.
When should a protective component fail open and when fail closed? Senior

Decide by the cost of a wrong decision versus the cost of unavailability. Fail closed (deny) for security-critical decisions: authorisation, payment fraud blocking on high amounts, encryption key service. Fail open (allow) where the protective check is a safeguard rather than the function: a rate limiter whose Redis is down (allow traffic, since blocking all users is worse than briefly missing limits), a feature flag service (use last known flags or defaults), a recommendation filter. Document the choice per component and alert whenever a component is running in fail-open mode.

What is a cascading failure and what are the common ways it starts? Senior

A failure in one component raises load or latency elsewhere, which then fails and pushes the problem further, like dominoes. Common triggers and amplifiers:

  • Server overload: one node dies, its traffic moves to the rest, they overload and die too. Each further death makes it worse.
  • Resource exhaustion: threads, connections, file descriptors, memory used up while waiting on a slow dependency.
  • Retry storms and amplification.
  • Cold caches or restarts: after a restart, the empty cache sends all reads to the database.
  • Health-check or autoscaler reactions that remove capacity during load.
  • Shared dependency: everyone calls the same auth service, DNS or config store.
  • Leader or coordinator failure that triggers expensive rebalancing in every node.

Defences: load shedding, timeouts and deadlines, circuit breakers, bulkheads, retry budgets, capacity headroom (N+2), cache warmup and request coalescing, and slow, staged rollouts of changes. Get a cascade under control by cutting load first (shed, block retries, scale up, turn off nonessential features) before trying to fix the root cause.

What is the thundering herd problem and how do you mitigate it? Intermediate

Many clients or processes act at the same moment against one resource. Typical cases: a hot cache key expires and thousands of requests all rebuild it from the database; all clients reconnect right after a server restarts; cron jobs all start at minute 0; a lock is released and every waiter wakes up; a mass retry after an outage.

Mitigations:

  • Jitter on TTLs, cron schedules, retry timers and reconnects.
  • Request coalescing (single-flight): only one request rebuilds the key while the others wait for its result.
  • Serve stale while revalidating, or refresh a cache entry before it expires in the background.
  • Cache locks or probabilistic early refresh.
  • Staged ramp-up of traffic after recovery, connection rate limits, and exponential backoff on reconnect.
  • Pre-warming caches before shifting traffic.
A cache fronts a database. The cache cluster dies and restarts empty. What happens and how do you protect the database? Senior

All reads miss and hit the database. If the cache was absorbing 95 percent of reads, the database suddenly sees 20x its normal read load and falls over, then the cache cannot be refilled because the database is down: a cold-start cascade.

Protection: the database must be protected independently of the cache with a concurrency limit and load shedding; single-flight coalescing per key; warm the cache gradually (ramp traffic by percentage, or preload hot keys); keep a replicated or sharded cache so one node loss only loses a fraction; use a small in-process local cache as a second layer; stale-while-error; and consider designing so that the system survives with the cache hit rate near zero for key paths, or sheds the rest. State the lesson: a cache that is required for survival is not a cache, it is a hard dependency, so treat it as one.

Multi-AZ, multi-region, disaster recovery

What is the difference between an availability zone and a region, and why design for AZ failure first? Basic

A region is a geographic area. An availability zone (AZ) is one or more physically separate data centers in a region, with independent power, cooling and networking, connected to the others by low-latency links (typically a few ms or less). Spreading across AZs protects against a data-center failure at modest cost and small latency, so it is the baseline: deploy every tier across at least 2, preferably 3 AZs, with enough spare capacity to lose one. Multi-region protects against a whole region failing (rarer, but it does happen, often from a software or control-plane problem) and also gives users lower latency, but it costs much more in complexity and money.

How do you design a typical web service to survive loss of an AZ? Intermediate
  • Load balancer spans 3 AZs; instances in an autoscaling group across 3 AZs.
  • Capacity: each AZ sized so the remaining two can carry the full load (about 50 percent per AZ headroom with three AZs, so about 66 percent total utilisation max).
  • Database: synchronous standby in another AZ (managed services do this), automatic failover; read replicas across AZs.
  • Caches and queues clustered across AZs with replicas in different AZs.
  • Avoid cross-AZ chatter where possible (latency and data transfer cost), but keep zonal affinity soft: if the local AZ's backend is dead, route elsewhere.
  • No AZ-specific singletons (one NAT gateway, one NFS server, one self-hosted tool).
  • Test by actually draining an AZ.
What are the main multi-region architectures and their trade-offs? Senior

Cross-region latency is tens to hundreds of ms (for example about 70 ms between US coasts, more across oceans), so synchronous replication across regions is usually too slow for latency-sensitive writes. That means asynchronous replication, so RPO greater than zero unless you accept slower writes (Spanner-style or quorum across regions).

What commonly breaks multi-region designs in practice? Senior
  • Hidden dependency on one region: a global service homed in one region (IAM, config, DNS control plane, a shared database, a third-party SaaS).
  • Failover requires control-plane operations (create instances, change DNS, assume roles) in the very region that is failing. Prefer data-plane-only failover that needs no new resources to be created.
  • The standby has never taken real traffic: capacity quotas, certificates, secrets, feature flags, IAM roles or data not replicated.
  • Capacity: when one region fails the other must absorb 100 percent. Quotas and scale-up speed matter; others in the same cloud region may be doing failover at the same moment.
  • Replication lag leads to data loss or stale reads after failover; no plan for reconciling writes that were in flight.
  • Failback (returning) is harder than failover and is often not designed.
  • Cost and operational burden: two of everything, and twice the deploys.
How is traffic steered between regions? Intermediate

Options: geo or latency-based DNS with health checks; anycast IPs with a global load balancer or CDN edge, which fail over in seconds without waiting on DNS caches; client-side logic (the SDK tries the next region). Ensure health checks represent real user success (synthetic transactions), and add a manual override ("drain region X") which is used far more often than automatic failover, especially for planned maintenance and deploys.

Define RTO and RPO. How do they drive the design? Basic
  • RTO (Recovery Time Objective): the maximum acceptable time from the disaster to service restored. "We must be back in 15 minutes."
  • RPO (Recovery Point Objective): the maximum acceptable amount of data loss, measured in time. "We can lose at most 5 minutes of writes."

RPO drives data strategy: RPO of 24 h is satisfied by nightly backups; minutes needs asynchronous replication or continuous log shipping; zero needs synchronous replication across failure domains. RTO drives compute strategy: hours is fine with rebuild from code; minutes needs a running standby. Both are business decisions with a cost, so ask the business or product owner "what does one hour of downtime or one minute of lost orders cost?" Do not set them at zero by default. Also note RTO and RPO are objectives; what you demonstrate in an actual drill is the actual recovery time, and they often differ.

Compare the four disaster recovery strategies: backup and restore, pilot light, warm standby, multi-site active-active. Intermediate

Why does "we have backups" not equal "we can recover"? Intermediate

A backup is only proven by a successful restore. Backups fail silently: wrong paths, corrupted files, expired credentials, partial snapshots, missing encryption keys (backup is encrypted with a key that lived in the lost system), restore time far longer than expected (restoring 20 TB over a network takes hours), or schema and tooling versions that no longer match. Also backups replicated by the same pipeline as production can copy corruption or a malicious or accidental delete (replication is not backup: a dropped table replicates in seconds).

Good practice: automated periodic restore tests with integrity checks, backups in a separate account or region with separate credentials and immutability (object lock or write-once) against ransomware and operator error, point-in-time recovery for databases, a documented and timed restore runbook, and monitoring on backup age.

Well-known example: in 2017 GitLab accidentally deleted a production database directory while handling a replication problem and found several of its backup methods had not been working; it recovered from a snapshot taken some hours earlier, losing several hours of data. (Details hedged: the lesson is that untested backups failed.)

How do you keep a DR plan real over time? Intermediate
  • Run scheduled DR exercises, ideally by really failing over production (or a prod-like environment) and measuring actual RTO and RPO.
  • Keep infrastructure as code so the DR site cannot drift from production; deploy to both sites through the same pipeline.
  • Run some real production traffic through the DR site continuously (even 1 to 5 percent) so you know it works.
  • Keep runbooks short and executable, rehearsed by people who are not the author, with a clear decision owner on "declare disaster".
  • Do not have the runbook, credentials or chat tool living only inside the infrastructure that failed.
  • Practise failback too.
What is static stability? Senior

A statically stable system keeps working during a failure of a dependency without having to take any new action (no control-plane calls, no scaling up, no failover decision). AWS uses this term in its builders' library. Example: instead of relying on autoscaling to replace a lost AZ's capacity during the incident (which needs APIs that may be impaired), pre-provision enough capacity in the remaining AZs ahead of time, so on AZ loss the load balancer just stops sending to the dead AZ and nothing else must happen. Another example: data-plane components cache the last known configuration and keep serving if the control plane is down; a service continues to use cached DNS or credentials until they truly expire.

The rule: separate the control plane (creates and changes things, complex, less available) from the data plane (does the work, simple, highly available), and make recovery depend only on the data plane.

Deployment safety

Why are deployments one of the top causes of outages, and what is the general defence? Intermediate

Most incidents in mature systems trace to a change: a code release, a config push, a schema migration, a certificate or dependency upgrade. Defence: make changes small, gradual, observable and reversible. Roll out to a small share first, watch automatic health signals, expand in stages, and be able to roll back in minutes. Avoid changes that hit every region and AZ at once, and treat config and feature-flag pushes as deployments with the same safeguards (several well-known large outages were a global config change with no staged rollout).

How does blue-green deployment work and what are its limits? Basic

Two identical environments. Blue runs the current version and takes traffic. You deploy the new version to Green, test it with smoke tests (and maybe shadow traffic), then switch the router or load balancer from Blue to Green. If something is wrong you switch back right away. Blue stays up for a while as an instant rollback.

Pros: near zero downtime, fast and simple rollback. Limits: needs double capacity during the switch; the switch is all-or-nothing for users (a bug reaches everyone at once unless you shift gradually); database changes must work with both versions since Blue and Green share one database; in-flight sessions and long-running jobs need draining.

What is a canary release? How is it different from blue-green and from a rolling update? Intermediate

A canary sends a small share of real traffic (1 percent, then 5, 25, 50, 100) to the new version while most users stay on the old one, comparing key metrics (error rate, latency, business metrics like checkout success) of canary against baseline. If metrics degrade, automatically roll back. The name is from canaries in coal mines.

  • Rolling update: replaces instances in batches until all run the new version. Gradual, but there is no isolated comparison group and rollback means rolling again.
  • Blue-green: whole-environment switch; a copy of the full fleet.
  • Canary: controlled exposure with automated judgement. Best blast-radius control.

Good canary practice: compare against a baseline on the same traffic mix (not against historic data), wait long enough to see slow failures (memory leaks, cache expiry), pick canary users randomly or by internal users first, roll out region by region and AZ by AZ ("one-box, then one AZ, then one region, then the world"), and automate rollback.

What makes a rollback safe, and when is rolling forward better? Senior

Rollback is safe when the previous version can still read everything the new version wrote. That requires backward-compatible data formats, schemas, messages and APIs for at least one release. If the new version has already migrated data irreversibly or written new message formats the old version cannot parse, rollback breaks things worse. Rules: keep the previous artifact deployable, keep rollbacks rehearsed and fast (minutes), never mix an irreversible migration with a code release, and decouple deploy from release with feature flags so the first remedy is "turn it off" and not "redeploy". Roll forward (hotfix) when rollback is impossible due to irreversible data changes, or when the fix is tiny and well understood and the rollback would itself be riskier.

How do feature flags help resilience, and what risks do they add? Intermediate

Flags separate deploying code from enabling behaviour. Benefits: ship code dark, enable for internal users then 1 percent then everyone, instant off-switch without a deploy ("kill switch"), degrade features under load by turning off expensive ones, A/B testing.

Risks: flag combinations multiply test states; stale flags become dead code and hidden behaviour (remove them after rollout); the flag service becomes a dependency (use local cache and safe defaults, so if it is down the system keeps the last known values); flag changes are production changes needing audit, review and staged rollout. A famous example is Knight Capital in 2012, where a reused old flag on one server with old code that was not updated led to an incorrect automated trading and a huge loss within about 45 minutes (widely reported at roughly 440 million dollars). It is usually quoted as a lesson on incomplete deployment, dead code and no kill switch.

What is the expand and contract (parallel change) pattern for database migrations? Senior

Change a schema across several releases so that old and new code both work at every step, with no downtime and a possible rollback each time. Example: rename column name to full_name.

  1. Expand: add full_name (nullable). Deploy nothing else yet.
  2. Deploy code that writes to both columns and reads the old one (or reads new with fallback to old).
  3. Backfill existing rows in small batches (throttled, to not overload the database).
  4. Switch reads to the new column. Verify.
  5. Stop writing the old column.
  6. Contract: drop the old column in a later release, once nothing uses it and rollback to the old version is no longer needed.

Why: during a rolling deploy old and new code run at the same time, and a rollback means old code runs on the new schema. A single step "rename and deploy" breaks one of them. Also avoid long table locks (use online schema change tools), add indexes concurrently, and never combine a destructive change with a feature release.

What automated safeguards should a deployment pipeline have? Intermediate
  • Automated tests and a staging environment with realistic data shape.
  • Progressive delivery with bake time between stages and automatic rollback on alarms.
  • Health and business metric gates (error rate, p99 latency, orders per minute).
  • Deployment windows and freezes at peak business times; no deploys of risky changes on Friday evening or during peak (a social guardrail, but also a staffing one).
  • One change at a time per service so cause is clear; version and change annotations on dashboards.
  • Config validation and linting before push, and config rollout in stages like code.
  • Ability to halt the pipeline globally.

Blast radius, cells, chaos engineering, SLOs

What is blast radius, and how do you limit it? Intermediate

Blast radius is how much of the system or how many users are affected when something fails or a bad change goes out. Limit it by splitting along fault boundaries: AZs, regions, cells, shards, tenants; by staged rollouts so a bad release hits 1 percent before 100; by per-tenant quotas; by separating control and data planes; and by not sharing databases, caches or queues between unrelated features. Ask for every component: "if this breaks, what percent of customers see it?" and aim to reduce that number by design.

What is cell-based architecture? How does it differ from simply having more replicas? Senior

A cell is a complete, self-contained instance of the service (compute, storage, queues) serving a fixed subset of users or tenants. A thin, simple router maps a customer to a cell. Cells share nothing at runtime. Compared with one big fleet of replicas where a poison request, bad data or a noisy tenant can take down everyone, a cell failure hits only about 1/N of customers.

Benefits: bounded blast radius, safer deploys (deploy cell by cell, starting with a small cell), cells have a fixed tested maximum size so scaling is by adding cells (no surprise limits), easier to reason about and test. Costs: routing layer and cell mapping to run, uneven utilisation, cross-cell operations (reporting, moving a tenant between cells) are harder, and more infrastructure to manage. The router must be extremely simple and highly available since it is the shared part. Shuffle sharding (give each customer a random subset of workers) is a related technique which makes it unlikely two customers share the same full set, so one poison customer does not take out another's capacity.

What is shuffle sharding with a quick numeric intuition? Senior

Instead of every customer using all 8 workers (one bad customer kills all) or customers pinned to fixed groups, each customer is assigned a random subset of, say, 2 of 8 workers. There are 28 distinct pairs. If a customer's requests crash the 2 workers it uses, only customers whose subset is exactly that same pair (about 1 in 28, or with clients retrying across their workers, only those with full overlap) are fully affected; everyone else still has at least one healthy worker. With larger pools (for example 100 workers, subset of 5) the number of combinations is about 75 million, so full overlap is very unlikely. Route 53 uses this idea per AWS's description.

What is chaos engineering and how do you start doing it safely? Intermediate

Chaos engineering is the practice of deliberately injecting failures to test that the system handles them, and to find weaknesses before real incidents do. It is science and not random destruction: define steady state (for example orders per minute and error rate), hypothesise it will hold under failure, inject the failure, observe, and fix what breaks. Netflix popularised it with Chaos Monkey (randomly terminate instances), later a family such as Chaos Kong (simulate losing a region).

Safe start:

  1. Begin in staging with a known small experiment (kill one instance, add 200 ms latency to one dependency, block one dependency).
  2. Have monitoring, a clear abort button, and a limited blast radius (small percent of traffic, off-peak).
  3. Run with the team present, as a game day.
  4. Move to production gradually when staging is boring.
  5. Turn findings into fixes, and automate the experiment as a regression test.

What is a game day, and what makes one useful? Basic

A game day is a scheduled exercise where the team simulates a failure (real or tabletop) and practises detection, diagnosis and recovery. It tests people, runbooks, dashboards, paging and communication as well as software. Useful ones have: a written scenario and hypothesis, defined roles (incident commander, communications, scribe), real alerts that must be noticed, a blameless review afterward with tracked action items, and rotating participants so that new on-call engineers have done it before. A common finding: the runbook is out of date, or the dashboard needed does not exist, or nobody has permission to do the fix.

How much capacity headroom should you keep, and why? Intermediate

Enough to survive the worst failure you have promised to survive, plus growth and traffic spikes while scaling reacts. Rule: if you must survive loss of one of 3 AZs, run below about 66 percent of total capacity at peak; with 2 AZs below 50 percent. Add margin for deploys (rolling updates take instances out), autoscaling lag (minutes to launch and warm instances), and bursts. Queueing theory also gives a reason: latency rises sharply as utilisation approaches 100 percent (in a simple M/M/1 model, wait grows like 1/(1 - utilisation)), so a system at 90 percent utilisation has far worse tail latency than at 60. Cost objections are answered by comparing the cost of idle capacity with the cost of an outage, and by using reserved or spot capacity wisely, but do not rely on spot for the part that must survive a failure.

Why is autoscaling not a substitute for overload protection? Intermediate

Autoscaling reacts in minutes (metric delay, launch time, warm-up, cache fill), but overload kills in seconds. It also depends on the control plane being available, can be capped by quotas or by a dependency (scaling the app tier just pushes more load onto the same database), and can hurt: new instances start cold and may be given full traffic immediately. Use autoscaling for gradual load change and keep load shedding, concurrency limits and headroom for sudden spikes. Scale on a leading indicator (queue depth, concurrency, request rate) rather than CPU alone.

What is the difference between an SLI, SLO and SLA? Basic
  • SLI (indicator): a measured number, such as the fraction of requests that succeed in under 300 ms.
  • SLO (objective): the internal target for it, such as 99.9 percent over 30 days.
  • SLA (agreement): the contract with customers, with consequences (credits, penalties) if broken. It is set looser than the SLO so you have a margin.

Choose SLIs the user would feel: availability (good requests / valid requests), latency percentiles, freshness, correctness, durability. Prefer percentiles to averages because averages hide tails.

What is an error budget and how does it change team behaviour? Intermediate

Error budget = 100 percent minus the SLO. A 99.9 percent monthly SLO allows 0.1 percent bad requests, or about 43 minutes of full outage per 30 days. It turns reliability into a shared, measurable resource: while budget remains, the team can ship features and take risks; when it is spent, the team slows feature releases and puts effort into reliability work until it recovers. This resolves the argument between "ship faster" and "be safer" with data, and shows when a 100 percent target is wrong (it is nearly infinitely expensive and leaves no room for change). It also helps to stop over-investing in reliability once the SLO is comfortably met.

How do you alert on SLOs without drowning in noise? Senior

Alert on burn rate: how fast the error budget is being consumed compared with the rate that would exactly use it up by the end of the window. Burn rate 1 means on track to spend it all; 14.4 means a 30-day budget would be gone in about 2 days. The approach in Google's SRE workbook: use multi-window, multi-burn-rate alerts, for example page when burn rate is above about 14 over both 1 hour and 5 minutes (fast burn, severe), and open a ticket when it is about 1 to 6 over longer windows such as 6 hours to 3 days (slow burn). The short window makes the alert reset quickly after recovery; the long window prevents paging on blips. This pages only for things that matter to users, instead of on every CPU spike.

Your service has a 99.99 percent SLO but depends on a third-party API with a 99.9 percent SLA. What do you do? Senior

You cannot exceed your hard dependencies' availability, so convert the hard dependency into a soft one or reduce reliance:

  • Cache results, serve stale on error.
  • Make the call asynchronous with a queue and retry later (accept the order, charge when the provider is back).
  • Use a second provider with failover.
  • Circuit breaker plus fallback response.
  • Exclude the dependency's failures from your SLI only if the contract and users agree they are out of scope (usually not accepted by users); otherwise be honest and set the SLO to what is achievable.
What is your general checklist for handling any dependency failure? Intermediate
  1. Classify: hard or soft dependency.
  2. Set connect and read timeouts, and propagate the deadline.
  3. Retry only idempotent calls with backoff, jitter and a budget, at one layer.
  4. Wrap in a circuit breaker and bulkhead.
  5. Define the fallback (stale, default, queue, fail open or closed) and test it.
  6. Add metrics: latency histograms, error rates per dependency, breaker state, pool saturation.
  7. Load test and chaos test the dependency being slow and being down.
  8. Know what happens at startup if the dependency is down (do not crash-loop; start in degraded mode).
What is a metastable failure? Senior

A state where the system stays broken even after the original trigger is gone, because a sustaining feedback loop (typically retries, cache misses with expensive recomputation, or queue backlogs) keeps load above capacity. Research by Bronson, Huang and colleagues described these. Example: a brief database slowdown causes cache entries not to refill; the high miss rate keeps the database slow. Recovery means breaking the loop: shed load, disable retries, pre-warm, shrink the request rate and ramp back gradually. Prevention: do not rely on caches to survive; make retry loops bounded; keep headroom; and use admission control.

Why is a long queue in front of a service a hidden danger? Intermediate

By Little's law, queue wait = queue length / throughput. A queue of 10,000 on a service doing 1,000 per second means 10 seconds of delay for the last request, which is probably past the caller's timeout, so the server does work no one is waiting for. Use short bounded queues, drop items older than their deadline, and prefer rejecting fast (so the client can try elsewhere) to making users wait. In bursty-but-batch work (background jobs) long queues are acceptable because there is no waiting caller.

Situational and real-life scenarios

Your checkout service suddenly has p99 latency of 30 s and thread pools full. The only change is that the recommendation service got slow. What do you do, and what should have prevented it? Senior

Right now: stop the bleeding. Turn off the recommendation call with a feature flag or kill switch, or open the breaker manually; restart or scale only if needed; confirm checkout latency recovers.

Why it happened: a soft dependency was treated like a hard one. It had no timeout (or a long one), shared a thread pool with checkout, and had no fallback.

Fixes: a 100 to 200 ms timeout, a separate bulkhead for it, a circuit breaker with an empty-list fallback, and a chaos test "recommendations return in 10 s". Add alerts on pool saturation.

A database failover took 40 seconds. After it completed, the new primary stayed overloaded for 30 minutes. Why, and what do you do next time? Senior

Probable causes: during the 40 s, clients timed out and retried; connection pools reconnected all at once; app-level queues filled; caches may have been cold. When the primary came back it received the backlog plus fresh traffic plus retries, a metastable state.

Handle it live: shed load at the edge (lower rate limits, reject non-critical traffic), disable or cap retries, restart app tier in waves so connections come back gradually, then ramp traffic up in steps.

Prevent: retry budgets with jitter, connection pool limits and slow reconnect, server-side concurrency limit, a failover game day that measures what happens afterward, and a runbook step "ramp traffic gradually after failover".

One of three AZs loses power during peak. Your service is at 80 percent utilisation. What happens? Senior

Two AZs now have to carry 100 percent of the load, which is 80 / (2/3) = 120 percent of their capacity. Latency climbs, queues grow, timeouts start, retries pile on, and the remaining AZs fail too: a cascade. Even if autoscaling kicks in, launching capacity takes minutes (and launches in the surviving AZs from everyone else's failover competes for capacity).

Immediate: shed low-priority traffic and degrade features to get below 100 percent; scale out manually and fast. Design fix: keep peak utilisation below about 66 percent for a 3-AZ design, pre-provision (static stability) and test by draining an AZ in a game day.

Every day at exactly 09:00 your database CPU spikes to 100 percent for a minute. Why might that be, and how do you fix it? Intermediate

A synchronised event: many cache keys with the same TTL set at 08:00, a cron job started by many nodes at once, a batch of clients reconnecting or a scheduled campaign hitting a hot key. It is a thundering herd.

Fix: add jitter to TTLs and schedules, single-flight on cache rebuilds, refresh ahead of expiry, stagger cron jobs, and rate limit the batch. Find it first by looking at the key or query pattern at that time in logs and metrics.

A config change pushed to all servers at once makes every instance crash on startup. How could you have avoided it, and how do you recover? Senior

Avoid: treat config as code (review, schema validation, tests); roll out in stages (canary, one AZ, one region); keep the last known good config and automatically revert if the new one fails to load or health checks fail; make parsers tolerant (ignore unknown fields, do not crash on a bad optional value).

Recover: roll back the config in the central store; instances that are crash-looping may need an out-of-band path to fetch it (hence the config distribution must not depend on the failing system). Out-of-band access to fix things is itself a resilience requirement: several well-known large outages (for example Facebook's October 2021 outage, reported as triggered by a configuration change to backbone routers that also disrupted tools engineers needed to fix it) were prolonged because the recovery tools depended on the broken system.

A major cloud provider has a regional service outage. Your app is multi-AZ but single-region. What can you do during the event, and what do you do afterwards? Senior

During: you cannot add capacity in the failing region, so focus on communication (status page), shedding load, degrading features (read-only mode, serve from cache), and if a warm standby or restore path exists in another region and the outage is expected to be long, decide on failover using the RTO against the expected duration. Check which of your own dependencies (CI/CD, monitoring, status page, login) are hosted in the same failing region and so unavailable.

Afterwards: decide with the business whether the risk justifies multi-region (cost versus outage cost), at least implement cross-region backups, pilot light for the critical path, and remove control-plane dependency in recovery. Notable examples: the 2017 AWS S3 outage in us-east-1 (widely reported as caused by an operator command that removed more servers than intended) hit many sites whose own status pages or tools depended on S3; the lesson is hidden dependencies and the need for tested recovery of foundational services.

Your circuit breaker opens and closes every few seconds ("flapping") and users see intermittent errors. What do you check? Senior
  • Minimum request volume too low, so a few failures trip it. Raise the minimum calls in the window.
  • Open duration too short, so half-open probes keep hitting a still-sick dependency. Lengthen it or back off exponentially.
  • Counting errors that are not dependency health (4xx, business exceptions).
  • Breaker is shared across too many hosts or endpoints: one bad endpoint opens it for all. Split per endpoint or per host.
  • Failure threshold too sensitive for normal error rate; set it from data.
  • Half-open allows too many trial calls.
Customers report being charged twice. Payments timed out and the client retried. How do you fix it properly? Intermediate

The retried POST was not idempotent. Add an idempotency key generated by the client per payment attempt, store it atomically with the result (unique constraint), return the stored result for repeats, and pass the key to the downstream payment provider if it supports it. Add reconciliation (a nightly job comparing our ledger with the provider) for the cases that slip through, and refund the duplicates. For safety also make the UI disable the button after a click, but never rely on that.

One tenant's batch job runs a heavy query pattern and slows every other tenant. What do you do short and long term? Intermediate

Short term: throttle or temporarily block that tenant's traffic (rate limit, quota) and kill the offending queries.

Long term: per-tenant rate limits and concurrency caps (bulkhead), separate pools or queues for batch versus interactive traffic, priority-based scheduling, query cost limits and timeouts, optionally move large tenants to their own cell or shard, and add per-tenant metrics so you see it quickly.

An interviewer asks: "Your design depends on an auth service in the request path. What if it is down?" How do you answer? Senior

Good answer outline:

  1. Reduce calls: use signed tokens (JWT or similar) that services verify locally with cached public keys, so the auth service is needed only at login and token refresh.
  2. Cache authorisation decisions for short periods.
  3. Deploy the auth service itself multi-AZ and multi-region, with its own bulkheads and capacity headroom, because everything depends on it (it is the most critical service, so treat it with the highest SLO).
  4. If the auth service is unreachable: existing valid tokens keep working until expiry (static stability), new logins show a clear error, and risky actions fail closed while low-risk reads can continue.
  5. Rate limit and cache negative results to protect it from retry storms after recovery.
You are on call and a dashboard shows error rates climbing across the fleet. What are the first steps? Intermediate
  1. Assess user impact and declare an incident; assign an incident commander and a communicator.
  2. Ask "what changed?" (deploys, config, flags, traffic, dependencies) and check the change log first; if a recent change correlates, roll it back or turn off the flag. Mitigate before diagnosing.
  3. If it is load: shed or throttle, scale, disable expensive features, block retries.
  4. Isolate: is it one AZ, one region, one dependency, one tenant? Drain the bad part.
  5. Communicate status regularly.
  6. After recovery, run a blameless postmortem with timeline, root causes, contributing factors, and action items with owners.

More conceptual questions

What does "fail fast" mean, and is it always right? Basic

Detect a problem as early as possible and report it immediately instead of continuing in a bad state or waiting a long time. Examples: validate input at the edge, refuse to start if required config is missing, reject requests when overloaded, open a breaker. It saves resources and makes problems visible. It is not right when a short wait or retry would likely succeed (transient blips) or when failing a whole startup for a nonessential dependency makes things worse; there prefer degraded mode.

What are MTBF and MTTR, and why do many teams focus on MTTR? Intermediate

MTBF is mean time between failures; MTTR is mean time to recover. Availability is roughly MTBF / (MTBF + MTTR). To go from 99.9 to 99.99 you can make failures ten times rarer (very hard, and bugs and human errors never go to zero) or recover ten times faster (often more achievable by automation, fast rollback, redundancy and good detection). In complex systems failures are inevitable, so shrinking detection and recovery time, and the share of users affected, usually gives the best return.

With at-least-once delivery and retries, how do you get effectively-once results? Intermediate

True exactly-once delivery over an unreliable network is not possible in general; what you build is at-least-once delivery plus an idempotent consumer. The consumer records processed message ids (or uses natural idempotency such as "set status to shipped") in the same transaction as its side effect, so a redelivery is detected and ignored. Outbox pattern on the producer side ensures that the database change and the message publish do not diverge.

Which signals tell you a service is becoming unhealthy before users complain? Intermediate

The four golden signals from Google SRE: latency (split successful and failed), traffic, errors, saturation. Specifically for resilience: p99 latency per dependency, in-flight requests and queue depth or age, thread or connection pool saturation, retry rate and retries as a share of traffic, circuit breaker state changes, shed or rejected request counts, replication lag, error budget burn rate, and cache hit rate. Saturation is the leading indicator; errors are lagging.

How do you shut down or deploy instances without dropping requests? Intermediate
  1. Instance receives a termination signal (SIGTERM).
  2. It marks itself not ready, so the load balancer stops sending new requests (deregistration delay).
  3. It finishes in-flight requests, up to a grace period.
  4. It closes connections, flushes buffers, and releases leases or locks.
  5. It exits, and is killed forcefully only if the grace time runs out.

Pitfalls: the load balancer keeps routing for a few seconds after deregistration (so wait a bit before shutdown), long-lived connections (websockets, streaming) need a reconnect-with-jitter plan, and consumers must hand back unacknowledged messages. On startup do the reverse: warm up before reporting ready, and avoid receiving full traffic cold (slow start).

How does moving from synchronous calls to asynchronous messaging improve resilience, and what does it cost? Intermediate

With synchronous calls, availability multiplies down the chain and latency adds up. With a durable queue or event log in between, the producer succeeds as soon as the message is stored, and the consumer can be down, slow or deploying with no user impact; the backlog is processed later (temporal decoupling). Costs: eventual consistency, no immediate result, extra component to run and monitor, need for idempotent consumers and ordering decisions, and the need to bound backlog age. Use sync where the user needs the answer now (checking a balance), async where it can be deferred (emails, analytics, fulfilment).
