How to use this page

Each question is a collapsible. Try to answer out loud first, then open it. Kafka internals (log segments, ISR, rebalancing protocol) live on a separate page; here the focus is design level: what to choose, why, and what breaks. When I say "broker" I mean the server that stores and routes messages (Kafka, RabbitMQ, SQS, Pub/Sub and so on). Names of vendors are examples of a style, not the only choice.

Why async, and the messaging models

Why would you make part of a system asynchronous? Basic
Say this: "Async means the caller hands off a message and moves on instead of waiting. I use it to keep the user path fast, to absorb bursts, and to stop a slow or failing dependency from taking down the main flow. The price is eventual consistency, duplicates and harder debugging."

What it is. In a synchronous call the caller waits for the answer before doing anything else. In an asynchronous design the caller writes a message (a small record describing work or a fact) to a broker (the server that stores and routes messages) and returns. Some other process picks the message up later and does the work.

Why it exists. Picture checkout. If the request handler saves the order, charges the card, sends the email, updates analytics, notifies the warehouse and refreshes the search index, the customer waits for the sum of all six, and if the email provider is down the whole checkout fails. Most of those steps are not needed to answer "was my order accepted?".

What you get:

  • Short user path: checkout saves the order and returns in about 200 ms. The email, analytics and warehouse steps run afterwards.
  • Decoupling in time: the consumer can be down or slow for a while and the producer still works, because the broker holds the work.
  • Load leveling: a burst of 50,000 requests per second is absorbed by the queue and drained at the 5,000 per second the workers can do. Users see some delay instead of errors.
  • Failure isolation: a slow email provider affects only the email worker.
  • Independent scaling: add workers for the slow step without touching the producer.
  • Fan-out: one event can feed many consumers, and the producer does not need to know them.

What you pay. Results are eventually consistent (the email may arrive seconds after the order page), messages can be delivered twice, ordering needs thought, and debugging means following a request across services and a broker. You also operate one more piece of infrastructure.

Decision rule. Anything the user must see before they can continue stays synchronous. Anything that merely has to happen eventually, and can be retried, goes async.

Remember: async trades immediacy and simplicity for resilience and throughput. Always name the costs.

Compare a message queue, pub/sub, and event streaming. Intermediate
Say: "Queue when the message is a task to do once; pub/sub when it is a fact many parties care about; a log when I need replay, ordering per key, and many independent readers."

The three differ in one core question: what happens to a message after someone reads it, and who gets to read it.

Message queue (SQS, RabbitMQ classic queue)Pub/sub (SNS, Google Pub/Sub topic with subscriptions, RabbitMQ fanout exchange)Event streaming (Kafka, Kinesis, Pulsar)
ModelEach message goes to one consumer among many (work distribution)Each message is copied to every subscriberAppend-only log; each consumer group reads at its own offset
After consumeMessage is acked then deletedDeleted per subscription after ackStays until retention expires (days or forever); reading does not remove it
ReplayNo (once deleted, gone)Usually no (some offer seek or snapshot)Yes, rewind the offset
OrderingBest effort, FIFO variants exist with limitsMostly noneStrict inside a partition
Best forTask jobs: resize image, send emailNotify many services of somethingEvent backbone, analytics, CDC, replay, high throughput

Queue, in words. Think of a ticket counter with one line and several clerks. Each ticket is handled by exactly one clerk, then thrown away. Good for jobs: "resize this image". Add more workers and the line drains faster.

Pub/sub, in words. Think of a newsletter. Publishing once sends a copy to every subscriber. The publisher does not know who they are. Each subscriber's copy is independent, so one subscriber being slow does not affect others (if each has its own durable queue).

Log, in words. Think of a ledger book that is only appended to. Readers keep their own bookmark (the offset). Reading does not erase anything, so a new reader can start from page one, and an old reader can rewind to reprocess after fixing a bug. The log is split into partitions for parallelism, and order is guaranteed only within a partition.

Blurred lines. SNS fanning into one SQS queue per consumer gives pub/sub with durable per-consumer queues. Kafka consumer groups give queue behaviour inside a group (members share partitions) and pub/sub behaviour across groups (each group sees everything).

Pitfall. Choosing a queue and later needing replay or a second independent reader means a migration. Ask early: "will anyone ever need to re-read history, or will a second team want the same data?" If yes, use a log.

Remember: queue = one reader per message, deleted; pub/sub = copy per subscriber; log = retained, offset-based, replayable.

When would you pick RabbitMQ or SQS over Kafka, and the reverse? Intermediate
Say: "A traditional queue for per-message task handling with simple operations; a log when I need throughput, per-key ordering, several independent readers or replay."

The deciding factor is the unit of work. A queue treats each message as an independent task: acknowledge it, retry it, delay it, route it, give it priority, individually. A log treats messages as a sequence that consumers walk through, tracking only a position (offset).

Pick a traditional queue when:

  • Tasks have very different durations (a 50 ms job and a 5 minute job). Any free worker takes the next message, so a slow one does not hold up the others.
  • You want per-message retry with delay, priorities, or routing rules (RabbitMQ exchanges and bindings).
  • Throughput is moderate and you do not need replay.
  • You want little operations work (SQS is fully managed: no partitions, no brokers to size).
  • You want worker count to be unrelated to any partition count.

Pick a log when:

  • Throughput is very high (hundreds of thousands of messages per second is routine for a tuned cluster).
  • You need ordering per key (all events for one order, one after another).
  • Several teams read the same data independently, each at its own pace.
  • You need replay: rebuild an index, fix a consumer bug, backfill a new service.
  • You do stream processing, CDC or event sourcing.

The head-of-line problem. In a log, a consumer processes a partition in order, so a message that keeps failing blocks everything behind it unless you move it to a retry topic (which then affects ordering). A queue has no ordering to protect, so a failing message simply becomes visible again later while others flow past it.

Parallelism cap. A log's parallelism is limited by partition count: 12 partitions means at most 12 active consumers in a group. A queue lets you run 200 workers.

Example. Sending order confirmation emails: SQS with a DLQ is plenty. Feeding every order change to search, billing, fraud and the warehouse, with the ability to rebuild search from scratch: Kafka.

Remember: task semantics and simplicity lead to a queue; sequence semantics, scale, fan-in of many readers and replay lead to a log.

Push vs pull delivery: which is better for consumers? Intermediate
Say: "Pull lets the consumer control its own rate, so backpressure is natural; push has the lowest latency but needs a bounded in-flight window so a slow consumer is not flooded."

The two models. In push, the broker sends each message to the consumer as soon as it arrives (RabbitMQ consumers, SNS calling an HTTP endpoint, webhooks). In pull, the consumer asks the broker for the next batch when it is ready (Kafka, SQS).

Push problem. The broker has to guess how fast the consumer can go. If it guesses wrong, a slow consumer is buried: memory fills, timeouts fire, messages are redelivered, and things get worse. The fix is a limit on unacknowledged messages. RabbitMQ calls this prefetch: "send me at most 20 messages that I have not acked yet". With that window, push behaves a lot like pull.

Pull strengths. The consumer fetches only when it has capacity, so overload shows up as rising lag in the broker (a visible, safe place) instead of crashes in the consumer. Batching is easy: fetch 500 messages, process, commit once. The cost is polling overhead when the queue is empty. Long polling removes most of it: the request waits on the broker side (SQS up to 20 seconds) and returns as soon as a message exists, or empty after the wait.

Webhooks are push over HTTP with every push downside: the receiver may be down or slow, so the sender must retry, sign requests and handle duplicates.

Decision rule. Default to pull for internal worker pools. Use push for low-latency delivery to clients or when consumers cannot poll, and always bound what is in flight.

Remember: the question is who controls the rate. Pull gives it to the consumer; push needs a prefetch limit to approximate that.

When is async the wrong choice? Senior
Say: "Async is wrong when the user needs the result to continue, when I need strong consistency across steps, or when the scale is too small to justify a broker. And I watch for the distributed monolith, where messages hide a synchronous dependency."

A senior answer shows you know async is a tool with costs, not a default.

  • The user needs the answer to proceed. Payment authorization result, login, "is this username taken?". You can fake sync with polling, but you add job ids, status endpoints and timeouts for nothing.
  • You need strong consistency. A transfer between two accounts in one database should be one ACID transaction, not two events with a window where money has left one account and not arrived in the other.
  • Low volume, simple system. A broker must be deployed, secured, monitored and paid for. For 20 requests a minute, a direct call or a database-backed job table is simpler.
  • The caller must react to failure immediately. If the right response to a rejected request is to show the user an error now (409 conflict, 422 invalid), sending it to a queue delays the very feedback needed.
  • Debuggability matters. A synchronous call chain has one trace and one stack. A web of events has no obvious owner of the flow, and "why did order 42 not ship?" means searching several topics.
  • The distributed monolith. Service A publishes a request event, then waits (blocks, polls) for service B's reply event. You now have all the coupling of a sync call plus extra latency, duplicates and a broker. That is worse than a plain HTTP call.

Example. Reserve-stock inside checkout: the customer must know now whether the item is available. Make it a sync call with a timeout and a clear failure path; make "send confirmation email" async.

Trap: saying "async scales better" with no cost. Name the costs: eventual consistency, duplicates, ordering, observability, and the extra system to run.

Remember: go async for work that can wait and be retried; keep sync what the user or a transaction depends on.

How do you design an async API: 202 Accepted, polling, webhooks? Intermediate
Say: "Return 202 with a job id immediately, process on a queue, and let the client poll a status endpoint or receive a webhook. The submit is made idempotent with an idempotency key."

Why. Some work takes longer than an HTTP request should stay open: a video transcode, a report export, a bulk import. Holding the connection for minutes hits proxy timeouts (often 30 to 60 seconds) and ties up server threads. So the API accepts the request, promises to do it, and reports the result later.

Flow:

  1. Client sends POST /exports with the parameters and an Idempotency-Key header.
  2. Server validates input (reject bad requests now, synchronously), inserts a job row with status QUEUED, publishes a message, and returns 202 Accepted with {"jobId":"123"} and Location: /exports/123.
  3. A worker consumes the message and updates the row: RUNNING, then SUCCEEDED (with the result location) or FAILED (with a reason).
  4. The client learns the outcome:
    • Polling: GET /exports/123 every few seconds. Simplest, works through any firewall. The server sends Retry-After and clients back off so polling does not become load. For finished jobs return 200 with the result or a redirect to it.
    • Webhook: the server calls a client URL on completion. Needs signed payloads, retries and an idempotent receiver.
    • Push channel (WebSocket or server-sent events) for browser UIs.

Idempotency. If the client times out and resends the POST, the key lets the server return the same job instead of creating a second export. Store key to job id with a unique constraint.

Also define: job expiry (delete results after N days), a cancel endpoint, progress percent for long jobs, and what a failed job returns (error code, whether retrying makes sense).

Pitfall. Returning 202 and losing the job: write the job row and the queue message atomically (outbox), or the client polls a job that never runs.

Remember: 202 + job id + Location header + status endpoint (or webhook) + idempotency key.

What goes wrong with webhooks and how do you make them reliable? Intermediate
Say: "A webhook is push over HTTP to a server I do not control, so I assume it is down, slow, duplicated, out of order and spoofed, and I design for all five."

A webhook is a callback: when something happens, your system sends an HTTP POST to a URL the customer registered. It is cheap for the sender but puts reliability work on both sides.

  • Receiver down or slow. The sender retries with exponential backoff for hours or days (many providers go for a day or more), then marks the endpoint failing, notifies the owner and eventually disables it. The sender uses a short request timeout (a few seconds) so slow receivers do not pile up open connections.
  • Duplicates. Retries mean at-least-once. Every event carries a unique id; the receiver stores processed ids and skips repeats.
  • Out of order. Event "updated" can arrive before "created". The receiver should either compare version numbers or treat the payload as a hint and fetch current state from the sender's API.
  • Spoofing and replay. Anyone can POST to a public URL. The sender signs the body (HMAC with a shared secret) and includes a timestamp in the signed data; the receiver verifies the signature in constant time and rejects old timestamps.
  • Slow receiver processing. The receiver should verify, save the raw event, return 2xx quickly, and process from its own queue. Doing 20 seconds of work inside the HTTP handler causes the sender to time out and retry.
  • One bad subscriber hurting others. Deliver per subscriber from separate queues, so one failing endpoint cannot hold up delivery to the rest (isolation again).
  • SSRF. If users supply the URL, the sender could be tricked into calling internal addresses (cloud metadata, private network). Resolve and block private ranges, restrict ports and do not follow redirects blindly.

Good extras: a delivery log and a "replay this event" button in the sender's dashboard, and a way to list missed events through an API so receivers can catch up after downtime.

Remember: sign, retry with backoff, dedupe by event id, ack fast and process async, isolate subscribers.

Delivery guarantees, ordering, and consumers

Explain at-most-once, at-least-once and exactly-once delivery. Basic
Say: "At-most-once may lose messages, at-least-once may duplicate them, and exactly-once is really at-least-once plus idempotency. My default is at-least-once with idempotent consumers."

Where the guarantee comes from. It depends on when the consumer acknowledges (acks) a message relative to doing the work. The broker only deletes (or advances past) a message once it gets the ack.

GuaranteeHowRiskUse for
At-most-onceAck before processing (or fire and forget)Message lost if consumer crashes mid-workMetrics, telemetry where loss is fine
At-least-onceAck after processing; redeliver if no ackDuplicatesThe default for almost everything
Exactly-onceAt-least-once plus dedup or transactionsCost and scope limitsMoney, inventory (effect, not delivery)

Timeline for the same crash. A worker receives message M ("charge order 42"):

  1. Ack first, then work: receive M, ack, crash before charging. The broker thinks M is done. The charge never happens (lost: at-most-once).
  2. Work first, then ack: receive M, charge the card, crash before ack. The broker never got the ack, so it redelivers M. Another worker charges again (duplicate: at-least-once).

There is no ordering of "work" and "ack" that avoids both problems, because they are two separate systems. So you pick the failure that is cheaper to handle. Duplicates can be neutralised by making the work idempotent (safe to repeat); losses cannot be recovered. That is why at-least-once is the default.

Effectively once. At-least-once delivery plus an idempotent consumer gives outcomes as if each message was processed once, even though it may have been delivered twice.

When at-most-once is fine: a CPU metric sampled every 10 seconds. Losing one sample is harmless and the cheaper path is simpler and faster.

Remember: ack after work = at-least-once; ack before work = at-most-once; "exactly-once" = idempotency or atomic commit on top.

Is exactly-once delivery real? How do you treat vendor claims? Senior
Say: "Exactly-once delivery between independent systems is impossible; what exists is an exactly-once effect inside one system boundary, via atomic commit of output and input position, or idempotent writes."

Why delivery cannot be exactly-once. This is the Two Generals problem. A sender transmits a message and waits for an ack. If no ack arrives, either the message was lost or the ack was lost, and the sender cannot tell which. It has two choices: resend (the receiver may get two copies) or give up (the receiver may get none). Over an unreliable network there is no third option.

What vendors actually deliver. A bounded scope where both the input position and the output can be committed together:

  • Kafka's idempotent producer gives each producer an id and sequence numbers per partition, so the broker discards a retried duplicate (within one producer session).
  • Kafka transactions let a consumer-process-produce job write its output messages and its input offsets in one atomic commit. Consumers set to read only committed data never see aborted output. This is exactly-once for read-process-write inside Kafka (topic A to topic B).
  • Stream engines (Flink, Kafka Streams) combine checkpoints with transactional or idempotent sinks for the same effect.

Where the guarantee ends. The moment your handler writes to an external database, calls an HTTP API, or sends an email, Kafka's transaction cannot cover it. You are back to at-least-once and need idempotency in that external step.

Example of the gap. Handler reads message, calls the email provider, then commits the offset. Crash between the send and the commit: the message is redelivered and the customer gets two emails. You can shrink the window (record a send id in a database first, pass the provider an idempotency key if it supports one), but you cannot remove it.

How to talk about vendor claims. Ask: what is the boundary of the guarantee, what does it cost (latency, throughput), and what happens at the edges (sinks and sources outside the system)? A good answer: "Exactly-once is atomic commit of the output and the input position, or idempotent writes. It holds within a system boundary only."

Trap: promising exactly-once for a side effect like sending an email or calling a third party. Say instead "effectively once, with dedup on a business key".

Remember: network makes delivery at-least-once; exactly-once is an effect you build with idempotency or transactions within a scope.

What is an idempotent consumer and how do you build one? Intermediate
Say: "An operation is idempotent if doing it twice has the same effect as once. Because at-least-once delivers duplicates, the consumer either uses naturally idempotent writes or records processed message ids in the same transaction as the effect."

Why. With at-least-once, "debit 50 from account A" may arrive twice. Without protection the account loses 100. Idempotency makes the second delivery harmless.

Techniques, from best to worst:

  • Naturally idempotent operations. "Set status to SHIPPED", "upsert row by key", "put this object at this path", "set balance snapshot to X". Repeating them changes nothing. Prefer these over "add 1" or "append", which are not idempotent.
  • Dedup table. Each message has a unique id assigned by the producer. In one database transaction: insert the id into processed_messages (primary key) and apply the business change. If the insert fails because of a duplicate key, skip the work. The atomicity is the whole point: "check if seen, then do it" as two steps has a race (two copies processed at the same time both pass the check).
  • Conditional writes with versions. UPDATE ... WHERE version = :expected. Repeats and out-of-order messages are rejected.
  • Idempotency keys on external calls. Pass a key to the payment provider so a retry returns the first result instead of charging again.
BEGIN;
INSERT INTO processed(msg_id) VALUES (:id);   -- fails if seen
UPDATE account SET balance = balance - :amt WHERE id = :acc;
COMMIT;

Walk through. Message m-77 arrives, insert succeeds, balance drops by 50, commit. The ack is lost, m-77 is redelivered, the insert hits the primary key, the transaction aborts, nothing changes, and the consumer acks. The balance dropped once.

Housekeeping. The dedup table grows. Delete rows older than a TTL that is longer than the broker's maximum redelivery or retention window; after that no duplicate can show up.

Pitfall. Dedup in a cache or separate store that is not in the same transaction as the effect. A crash between "mark seen" and "apply" loses the message; between "apply" and "mark seen" allows a duplicate.

Remember: prefer naturally idempotent writes; otherwise store the message id atomically with the effect.

Where can deduplication happen and what are the limits? Intermediate
Say: "Broker-side dedup is limited in time and scope, consumer-side dedup in the same transaction as the effect is authoritative, and a unique business constraint is the strongest because it survives producer resends with new ids."

There are three layers. Each catches a different kind of duplicate.

  • Broker side. SQS FIFO drops messages with the same deduplication id sent within a 5 minute window. Kafka's idempotent producer discards a retry of the same batch, but only within one producer session and per partition. Useful against producer retries, but time-limited and unable to catch a duplicate sent an hour later, or after a producer restart.
  • Consumer side. A dedup store keyed by message id: a database table, or Redis with a TTL. With a database table updated in the same transaction as the business effect, it is airtight. With Redis it is a separate system, so the crash windows from the previous answer return.
  • Business key. A rule in the data model: a unique constraint such as UNIQUE(order_id, step) on the payments table. Even if the producer crashes and resends the same business action with a brand new message id, the database refuses the second row.

Choosing the key. A message id is generated by the messaging layer or producer and can change if the producer retries and builds a new message. A business id (order id plus step name) identifies the intent and stays the same. Dedup on the business id when you can.

Example. Producer crashes after sending "charge order 42" and restarts. It resends with a fresh message id m-99. Broker dedup cannot see a duplicate (different id), consumer message-id dedup cannot either, but UNIQUE(order_id) on the charges table stops the second charge.

Remember: layer the defences, and trust the one closest to the data.

How do you preserve ordering in a distributed queue? Intermediate
Say: "Global order does not scale, so I preserve order per entity: route messages by a key (order id) so all events for that entity land on one partition read by one consumer at a time."

Why not global order. To totally order all messages, a single process must see them one after another, which means one consumer and no horizontal scale. What the business usually needs is weaker: events for the same entity (order 42 created, paid, shipped) must be seen in that order. Events for different orders can interleave freely.

Mechanism. The producer attaches a key. The broker maps key to partition (for example hash(key) mod partitions). Each partition is read by exactly one consumer in a group at a time, in order. So every event for key K goes to the same partition, then to one consumer, in the order it was written.

  • Kafka: message key hashed to a partition.
  • SQS FIFO: message group id; ordering holds inside a group, and different groups proceed in parallel.
  • RabbitMQ: consistent-hash exchange or sharded queues, one consumer per queue.

What silently breaks it:

  • Retries that reorder. A failed message goes to a retry topic and its successor is applied first.
  • Producer-side reordering. Several in-flight requests on one connection where an earlier one fails and is retried after a later one succeeded (Kafka's idempotent producer prevents this).
  • Changing the partition count. The key-to-partition mapping changes, so new events for a key go to a different partition than its old ones and can overtake them.
  • Parallelism inside a consumer. A consumer that hands messages from one partition to a thread pool loses order.

Remember: order per key via partition key or group id; never promise global order; protect it from retries and repartitioning.

A partitioning key is skewed (one customer sends 40 percent of traffic). What do you do? Senior
Say: "Confirm it is a hot key from per-partition metrics, then decide whether I really need per-customer ordering. If not, use a finer key; if yes, make that partition's consumer faster or isolate the big tenant."

Why it happens. A partition is processed by one consumer at a time. If key = customerId and one customer produces 40 percent of traffic, one partition gets 40 percent of the work while other consumers idle. Adding consumers does not help because the extra ones have no partition to read.

Confirm first. Per-partition throughput and lag: one partition far behind, others near zero. Then find the key: sample keys on that partition.

Options, in order:

  1. Finer key. If order is only needed per order, key by orderId (or customerId plus orderId). The big customer's traffic then spreads across all partitions.
  2. Make the hot partition's consumer faster. Batch writes to the database, use async I/O, remove per-message round trips, cache lookups. If the work inside a key can be parallelised without breaking correctness (independent sub-entities), fan out inside the consumer carefully.
  3. Dedicated topic and consumers for the large tenant, so it cannot slow smaller ones (the noisy-neighbour fix). Route by tenant tier at the producer.
  4. Salting. Key plus a random suffix 0..N spreads the load but destroys per-key order. Acceptable only for commutative operations (counters, sums) that are aggregated later.

Example. Click events keyed by advertiser: one advertiser has 40 percent. Counts are commutative, so salt the key into 8 sub-keys, partially aggregate per sub-key, then merge. If instead you need each advertiser's events in order, you keep the key and speed up the consumer.

Remember: order requirements decide what you can do; if order is not needed per big key, spread it.

How do you choose partition count? Intermediate
Say: "Partitions cap consumer parallelism, so I size from target throughput over per-consumer throughput with 2 to 3 times headroom, balanced against the broker overhead of too many partitions."

What a partition is for. A partition is one ordered slice of a topic. It is the unit of parallelism: within a consumer group each partition is read by at most one member. So 6 partitions means at most 6 consumers do useful work; a seventh sits idle.

Sizing method.

  1. Estimate peak throughput, for example 60 MB/s or 30,000 messages/s.
  2. Measure what one consumer can handle, for example 3,000 messages/s.
  3. Partitions needed is about 30,000 / 3,000 = 10. Add headroom for growth and bursts, so 24 to 30. Also check the broker side: throughput per partition on the producer and storage side.

Why not just pick 1,000. Each partition costs broker memory and file handles, lengthens leader election and recovery after a broker failure, increases end-to-end latency in some configurations, and makes consumer group rebalances slower and heavier.

Why not start tiny. Increasing the count later is possible in Kafka, but it changes the key-to-partition mapping: old and new events for one key can then sit on different partitions and lose order. Decreasing is not supported without recreating the topic. So pick with growth in mind, and use a number with many divisors (12, 24, 48) so consumers divide evenly.

Queues differ. SQS standard queues and RabbitMQ work queues have no partition cap on workers. This is one reason they suit tasks with fluctuating worker counts.

Remember: partitions = max parallelism; size for peak plus growth; changing later remaps keys.

What is a consumer group and how does it differ from competing consumers? Intermediate
Say: "Competing consumers is the pattern, several workers sharing one queue. A consumer group is Kafka's implementation: members split the partitions, and each separate group gets its own full copy of the stream."

Competing consumers. Several identical workers read from one queue. Each message is handled by exactly one of them. This gives horizontal scale and automatic load balancing: a fast worker simply takes more messages.

Consumer group. Applying the same idea to a log. The group has a name; the broker assigns each partition to one member of the group. The group keeps one committed offset per partition. A second group with a different name has its own offsets and receives every message again, regardless of what the first group does.

So you get two levels:

  • Across groups: pub/sub. Billing and analytics each use their own group; both get every order event, and each can lag or replay independently.
  • Inside a group: queue semantics. The billing service runs 6 instances; they share the topic's 12 partitions, 2 each.

Scaling and rebalance. Add instances up to the partition count. When a member joins, leaves or crashes, the group rebalances: partitions are reassigned. During a classic rebalance consumption pauses briefly, and uncommitted work may be redone by the new owner (so handlers must be idempotent). Newer cooperative protocols move only the partitions that need to move, reducing the pause. Frequent rebalances (a consumer exceeding its poll timeout, or autoscaling flapping) look like lag with no work done.

Remember: members of a group share the work; different groups each get everything.

How do acks, visibility timeout and redelivery work in a queue? Intermediate
Say: "A received message is not deleted, only hidden. If the worker acks in time it is deleted; if the worker crashes or is slow, the message reappears and another worker takes it. So set the timeout above the p99 processing time."

The mechanism. A queue cannot delete a message the moment it hands it out, because the worker might die before finishing. So it hands out a lease:

  1. Worker calls receive. The broker returns the message and makes it invisible to others for a period (SQS visibility timeout, default 30 seconds). RabbitMQ marks it unacked and holds it against that connection.
  2. Worker processes, then acks (SQS: delete the message; RabbitMQ: basic ack). The broker removes it permanently.
  3. If no ack arrives before the timeout (SQS), or the connection drops (RabbitMQ), the message becomes visible or is requeued, and the next worker gets it. The receive count goes up.

Tuning the timeout.

  • Too short. The job takes 45 seconds, the timeout is 30. The message reappears while the first worker is still running, and a second worker starts the same job: concurrent duplicate processing. Set the timeout above p99 processing time, or have the worker extend it (heartbeat) while it works.
  • Too long. After a crash the message stays hidden for a long time, delaying recovery.

Rules. Ack only after the work and its side effects are durable. Track the receive count; after N attempts, move the message to a DLQ, so a poison message does not cycle forever. Handlers must be idempotent because redelivery is normal, not exceptional.

Remember: receive = lease, ack = delete, timeout = lease length; redelivery means duplicates are possible.

When should a log consumer commit its offset: before or after processing? Intermediate
Say: "After. Committing before gives at-most-once and loses messages on a crash; committing after gives at-least-once, replaying a little, which idempotent handlers absorb."

What an offset commit is. In a log, the consumer's position is a number per partition (the next message to read). Committing stores that number in the broker (or elsewhere) so that after a restart or rebalance the consumer resumes from it. It is the log equivalent of an ack.

Timeline. The consumer fetches offsets 100 to 199.

  • Commit 200 first, then process: crash at offset 150. After restart it resumes at 200. Messages 150 to 199 were never processed: lost.
  • Process, then commit 200: crash at offset 150. After restart it resumes from the last commit, 100, and reprocesses 100 to 149 (already done): duplicates, none lost.

How often. Committing after every message is slow (a round trip each). Commit per batch (or auto-commit on an interval, but be careful that auto-commit can commit before processing has finished). A crash replays at most one batch, which idempotency covers.

Stronger options.

  • Kafka to Kafka: commit offsets in the same transaction as the output writes (exactly-once inside Kafka).
  • Output to a database: store the offset in the same database transaction as the result, and on startup seek to the stored offset instead of the broker's. Then the position and the effect are atomic.

Pitfall. Committing offsets for messages still being processed by async threads. Only commit what has fully completed, in order.

Remember: process then commit; batch the commits; make handlers idempotent.

Why can a retry topic break ordering, and what are the options? Senior
Say: "A retry topic lets later messages for the same key overtake a failed one. I either block and retry in place with a bound, park the key, or make the handlers version-aware so stale or late messages are harmless."

The problem. Normal flow keeps order within a partition. To avoid blocking on a failing message, many designs move it to a retry topic and carry on. Example for key K (an account):

  1. Message 1: "set limit 500". Fails (database lock timeout). Moved to the retry topic with a 1 minute delay.
  2. Message 2: "set limit 900". Processed immediately on the main topic. Limit is 900.
  3. A minute later message 1 is retried and succeeds. The limit is now 500, which is wrong: the older value overwrote the newer one.

Options:

  • Block the partition and retry in place. Preserves order, but one bad message stalls everything behind it, including other keys on that partition. Use a bounded number of attempts with short backoff, then dead-letter. Fine when failures are rare and brief.
  • Park the key. When message 1 for K goes to retry, record K as "in retry" in a store; later messages for K are diverted to the retry flow too, to be replayed after. Order is kept without blocking other keys, but it needs state and care.
  • Make processing order-tolerant. Each event carries a per-entity version or sequence number. The handler applies an event only if it is newer than what is stored and ignores stale ones. Message 1 (version 7) arriving after message 2 (version 8) is dropped. This is usually the most robust option.

Choose. If events are snapshots or "set" operations, use versioning. If events are deltas that must be applied in sequence (ledger entries), block or park.

Remember: any path that reinserts a message later can reorder; protect with versions, parking or in-place retry.

Failures, retries, backpressure

How should retries work for a failing consumer? Basic
Say: "Classify the error, retry only transient ones with capped exponential backoff and jitter, bound the attempts, then dead-letter. Handlers must be idempotent."

Why not just retry immediately forever. If the cause is a database outage, instant retries hammer a system that is trying to recover, and if the cause is a bad payload, no retry will ever succeed and the message blocks or burns capacity.

The recipe:

  • Classify errors. Transient (timeout, 503, deadlock, connection reset) might work next time: retry. Permanent (validation failure, malformed JSON, unknown type, most 4xx) never will: send straight to a DLQ.
  • Exponential backoff. Wait 1 s, 2 s, 4 s, 8 s, ... doubling, with a cap such as 5 minutes. Gives the dependency growing room to recover.
  • Jitter. Add randomness (for example wait a random time between 0 and the backoff). Without it, 10,000 messages that failed together all retry together, in synchronised waves. Jitter spreads them out.
  • Bounded attempts. After say 5 tries, dead-letter. Keep an attempt counter in a header.
  • Non-blocking delay. Sleeping inside the consumer stalls its partition. Instead use retry tiers (topics or queues like retry-1m, retry-10m, retry-1h) or broker delay features, where the consumer republishes with an incremented attempt header, then moves on.
  • Circuit breaker. If the downstream is clearly down (many consecutive failures), stop consuming for a while rather than spending every message's retry budget. Messages wait safely in the broker.

Example. Payment gateway returns 503 for 90 seconds. Messages retry at about 1 s, 2 s, 4 s, 8 s, 16 s plus random jitter; most succeed on the third or fourth try once the gateway recovers. A message with an invalid currency code goes to the DLQ on the first failure.

Pitfall. Retries at several layers multiply (see retry storm), and retries without idempotency cause duplicates.

Remember: classify, back off with jitter, bound, dead-letter, stay idempotent.

What is a retry storm and how do you prevent it? Senior
Say: "A retry storm is when retries add load to an already struggling dependency and push it further down. I retry at one layer with backoff and jitter, cap retries with a budget, use circuit breakers, and let the queue buffer instead."

How it builds up. A database becomes slow. Calls start timing out. Each timeout triggers a retry, which adds load, which makes the database slower, which causes more timeouts. The system is now being kept down by its own retries.

Amplification across layers. If the browser retries 3 times, the API service retries each call 3 times, and the worker retries each call 3 times, one user action becomes 3 x 3 x 3 = 27 calls against the dependency during exactly the time it can least afford them.

Prevention:

  • Retry at one layer (usually the one closest to the failing call, or the outermost one that owns the user request) and nowhere else.
  • Backoff with jitter so retries are spread out and not synchronised.
  • Retry budget: allow retries only up to a fraction (for example about 10 percent) of normal request volume. When the budget is gone, fail fast.
  • Circuit breaker: after enough failures, stop calling for a cooling-off period, then probe with a few requests.
  • Load shedding at the dependency: reject excess requests quickly (503 with Retry-After) instead of queueing them until they all time out.
  • Timeouts shorter than the caller's own timeout, so work abandoned by the caller is not still running.

Messaging angle. A queue is a natural shock absorber. When a downstream is unhealthy, pausing the consumers (and letting the backlog sit) is better than retrying hard. Resume slowly when it recovers.

Remember: one retry layer, jittered backoff, budget, breaker, shed load.

What is a dead letter queue and how do you operate one? Basic
Say: "A DLQ is a side queue where messages go after exhausting their retries. It keeps bad messages from blocking the main flow while preserving them for diagnosis and redrive. Alert on it, because a DLQ nobody reads is just slow data loss."

What it is. Normally a message that fails is retried. If it keeps failing, you need somewhere to put it. Throwing it away loses data; leaving it blocks the line. A dead letter queue (DLQ) is that parking place. SQS has a redrive policy with maxReceiveCount (after N receives without a delete, move it); RabbitMQ has a dead-letter exchange; in Kafka you publish to a separate topic such as orders.dlq, usually from your own consumer code.

What to store. The original payload unchanged, plus metadata: failure reason, exception and stack trace, attempt count, source topic, partition and offset, timestamp, and the consumer version. These make debugging and replay possible.

Operating it:

  • Alert on depth above zero (or growth rate). It is a symptom of a bug, a bad deploy or a producer breaking its contract.
  • Inspect tooling: a way to browse messages and see the failure reason.
  • Redrive: after the bug is fixed, move messages back to the main queue (SQS offers a redrive feature; otherwise a small script). Handlers must be idempotent since some may partly have run.
  • Retention: keep it longer than your response time. SQS retention maxes at 14 days; a failure on Friday must not expire before Monday. For compliance, copy to durable storage.
  • Security: payloads in a DLQ may contain personal data. Give it the same access controls and retention rules as the main queue.

Pitfall. One DLQ for everything with mixed reasons becomes unmanageable; use one per source queue and tag reasons. Also, redriving a poison message without fixing the cause just fills the DLQ again.

Remember: quarantine, alert, inspect, fix, redrive.

What is a poison message and how do you handle it? Intermediate
Say: "A poison message fails every time it is processed. I cap attempts, dead-letter it, separate deserialization errors from business errors, and treat a burst of identical failures as a contract or deploy problem."

What it is. A message the consumer can never process successfully: corrupt bytes, a field type the code does not expect, a value that triggers a bug (division by zero on one record), or a reference to something that no longer exists.

Damage by broker type:

  • Log with in-order processing: the consumer fails on offset 500, retries forever, and offset 501 onward are never reached. The partition is stuck and lag grows.
  • Queue: the message keeps reappearing after each visibility timeout, wasting capacity, and if it crashes the worker each time you get a crash loop that also disrupts healthy messages.

Handling:

  • Cap the attempts (via a counter header or the broker's receive count) and divert to the DLQ, then continue.
  • Separate error types. Wrap deserialization in its own try block. A payload that cannot even be parsed is certainly permanent: dead-letter it at once without retries. A framework feature (Spring's error-handling deserializer, for example) does this.
  • Catch crashes. If a message kills the process (out of memory), the receive count must still increase so it reaches the DLQ.
  • Look for patterns. One poison message is data. A hundred with the same error after a deploy means a producer broke the schema or a consumer release is wrong. Roll back or fix, then redrive.
  • Alert on DLQ arrivals and on repeated failures for a single offset.

Remember: never let one bad message block the rest; bound, quarantine, investigate.

What is backpressure and how do you apply it in a messaging system? Intermediate
Say: "Backpressure is a slow consumer signalling upstream to slow down so queues and memory do not grow without bound. A queue only delays the problem; I bound in-flight work, shed or reject at the edge, autoscale within what the sink can take, and protect the database."

Why it exists. A queue absorbs bursts, but if producers are faster than consumers for long enough, the queue grows until storage runs out or messages are so old they are useless (a 2 hour old "your driver is arriving" notification). Something must push back.

Levers:

  • Pull and bounded in-flight work. Pull consumers fetch only when ready. Bound concurrency per consumer: prefetch count, max.poll.records, a semaphore or a bounded thread pool with a bounded queue.
  • Bounded queues. When full, either block the producer (slows it), reject (HTTP 429 or 503 with Retry-After so clients back off), or drop the lowest-priority items.
  • Load shedding. Under overload, drop or sample non-critical work first (analytics events, debug telemetry) to keep critical flows alive.
  • Autoscale consumers on lag or message age, with a ceiling.
  • Rate limit producers per tenant so one cannot starve others.
  • Protect the sink. If 10 workers use 10 database connections, scaling to 100 workers may just move the overload to the database. Cap concurrency to what the downstream accepts, and make the cap the limiting factor, not the worker count.

Example. Image resize workers take 200 ms per image; the upload API publishes 3,000 per second at a peak while workers do 2,000 per second. Queue grows by 1,000 per second. Options: autoscale workers to 2x (if CPU allows), shed thumbnails for non-premium users, or return 429 on bulk uploads. Decide in advance which.

Pitfall. Unbounded in-memory queues inside a consumer: it silently accumulates until it runs out of memory, hiding the backlog from the broker's lag metrics.

Remember: bound everything, push back at the edge, shed the unimportant, protect the sink.

Why is queue depth (or consumer lag) a good signal, and what are its limits? Intermediate
Say: "Depth or lag shows whether consumers keep up and is the best autoscaling input, but age of the oldest message, per partition, is the better alert. Depth alone hides stuck consumers and broken producers."

What it measures. Depth is the number of messages waiting in a queue. Lag in a log is the latest offset minus the consumer's committed offset. A rising number means arrivals exceed processing. Falling means catching up.

Limits and improvements:

  • Count is not urgency. 10,000 messages that drain in 2 seconds are fine; 100 messages stuck for an hour are a failure. Age of the oldest message (or lag expressed in time) matches what users feel and what SLOs state. SQS exposes ApproximateAgeOfOldestMessage.
  • Averages hide stuck partitions. A dead consumer on one partition shows lag on just that partition. Alert per partition (or on max lag), not on the topic total.
  • Zero can be bad. If a producer is broken, depth stays at zero. Alert on "no messages for X minutes" where steady traffic is expected.
  • Rate matters. Depth growing at 1,000 per second is more urgent than a flat large number.

Sizing with Little's law. Concurrent workers needed = arrival rate x average processing time. At 2,000 messages per second with 50 ms per message: 2,000 x 0.05 = 100 workers busy on average. Add headroom (30 to 50 percent) for bursts, or you run at 100 percent utilisation where queues grow without limit.

Remember: alert on age and per-partition lag; autoscale on lag rate; keep a no-traffic alarm.

Scenario: consumer lag keeps growing at 2 AM. What do you check, in what order? Senior
Say: "First narrow it: one partition or all. Then rate in versus rate out, then per-message time and its dependencies, then rebalance churn and retries. Mitigate by scaling if the sink has room, otherwise shed or defer."

Work from cheap, high-information checks to expensive ones.

  1. One partition or all? One partition points to a hot key or a poison message stuck on that offset. All partitions point to capacity or a shared dependency.
  2. Did the input rate rise? A nightly batch job, an upstream retry loop, or a new feature publishing more. Compare produce rate with the last week at the same hour.
  3. Did per-message time rise? Check handler latency and downstream dependencies: database slow (a 2 AM backup or maintenance job), a third-party API throttling you, long GC pauses, a recent deploy that added a slow call.
  4. Rebalance loop? Consumers joining and leaving (processing exceeds the poll timeout, pods being killed for memory, autoscaler flapping). The group spends its time rebalancing and does little work, which looks like lag with idle CPU.
  5. Failures and retries? Error rate up means retries multiply load, and the DLQ may be filling. Look at the top exception.

Mitigation. If the sink (database, API) has spare capacity, scale consumers up to the partition count. If the sink is the bottleneck, scaling makes it worse: instead pause non-critical producers, shed or defer low priority work, and let the backlog drain once the dependency recovers. Communicate the expected delay.

Afterwards. Add the alert on message age that should have fired before anyone was paged for symptoms, and add a runbook for it.

Remember: narrow scope, compare in/out rates, check dependencies, rebalance, retries; do not scale blindly into a saturated sink.

How do you give some messages priority? Intermediate
Say: "Separate queues per priority with dedicated or weighted workers, plus a guaranteed minimum share for bulk work so it does not starve."

Why a single mixed queue fails. If a tenant imports 2 million rows into the same queue as interactive requests ("send my password reset"), the reset email waits behind the whole import. This is the noisy-neighbour problem.

Options:

  • Separate queues per priority (high, normal, bulk), each with its own workers. High never waits behind bulk. Simple and predictable; cost is idle capacity if one lane is empty (mitigate with shared workers that prefer the high lane).
  • Weighted consumption. One worker pool polls lanes in proportion, e.g. 70 percent of capacity to high, 20 percent normal, 10 percent bulk, and takes from lower lanes when higher ones are empty.
  • Priority field in one queue (RabbitMQ supports it). Convenient but costs throughput, works poorly with large backlogs and can starve low priorities.

Rules:

  • Guarantee a minimum share for bulk, or old low-priority messages may wait forever (starvation). Sometimes raise a message's priority as it ages.
  • Lane by tenant or source too: put a big single-tenant import in its own lane or rate limit it.
  • Keep the priority set small (2 to 4). Ten levels no one can reason about.

Log note. In Kafka there is no per-message priority within a partition; use separate topics per priority, and consumers that read the high-priority topic first.

Remember: lanes, weights, a floor for bulk, and isolate big tenants.

How does a broker avoid losing messages? Intermediate
Say: "Loss can happen producer to broker, inside the broker, and broker to consumer. I close each gap: durable acks and retries at the producer, replication before ack in the broker, and ack-after-work at the consumer."

Follow one message through its three hops.

  1. Producer to broker. Fire-and-forget loses messages if the network drops or the broker is down. Instead wait for the broker's acknowledgement that the message is stored, and retry on timeout. Retries create duplicates, so enable the idempotent producer (Kafka) or dedup ids (SQS FIFO). In an application, pair the DB write with an outbox so a crash before publishing does not lose the event.
  2. Inside the broker. One server holding the only copy loses data if it dies. Replicate: for example Kafka with replication factor 3, acks=all (leader waits for all in-sync replicas) and min.insync.replicas=2, so a write is acknowledged only when at least two copies exist. Disable unclean leader election, which would promote an out-of-date replica and silently lose acked messages. Disk flush settings matter less when replication is in place; SQS and other managed services replicate across availability zones for you.
  3. Broker to consumer. Commit the offset or ack only after the work is done, as covered earlier. Retention must exceed the longest time a consumer might be down.

Trade-off. More replicas acking means higher write latency and lower availability under failures (if too few in-sync replicas exist, writes are rejected) in exchange for safety. For telemetry choose speed (acks=1 or even 0); for payments choose durability.

Remember: ack durable on write, replicate before ack, ack after work on read.

Event-driven architecture

What is event-driven architecture and what do you gain and lose? Basic
Say: "Services communicate by publishing events, facts that already happened, and others react. I gain loose coupling and easy extension; I lose visibility of the flow and take on eventual consistency and schema discipline."

What it is. In a request-driven design, the Order service calls Payment, then Inventory, then Email, one by one: it must know them all. In an event-driven design, Order just publishes OrderPlaced (a fact, past tense) and stops. Payment, Inventory and Email each subscribe and react on their own. The publisher does not know who listens.

Why it helps. Add a loyalty-points service next quarter: it subscribes to OrderPlaced. Order's code and deployment do not change. Each consumer scales and fails independently, and the event stream doubles as an audit trail.

What you lose:

  • Implicit flow. "What happens when an order is placed?" has no single place to read the answer. You have to find all subscribers.
  • Eventual consistency. After OrderPlaced, the stock count updates a moment later. The UI and business rules must tolerate the gap.
  • Harder debugging. A request spreads across services and time.
  • Contract risk. The event schema is a public API with unknown consumers; careless changes break them (see schema evolution).
  • Cycles. A reacts to B's event, B reacts to A's, and they ping-pong forever.

Mitigations: propagate a correlation id in every event header and use distributed tracing; keep an event catalog documenting each event and its consumers; use consumer-driven contract tests; add loop guards (do not emit an event as a reaction to an event you caused without a clear terminating rule).

Remember: events decouple producers from consumers, at the price of an implicit flow that you must make observable.

What is event sourcing and what are its tradeoffs? Intermediate
Say: "Event sourcing stores the sequence of events as the source of truth and derives current state by replaying them. It gives audit and rebuildability at the cost of snapshots, schema evolution pain, separate read models and a learning curve."

What it is. A normal database stores the current state: balance = 70. Event sourcing stores what happened: AccountOpened, MoneyDeposited 100, MoneyWithdrawn 30. The balance is computed by replaying the events: 100 - 30 = 70. A bank ledger is the classic analogy: the balance is a sum over entries, and entries are never erased.

Mechanics.

  1. A command arrives ("withdraw 30"). Load the account's events, rebuild state, check rules (enough money?).
  2. If valid, append a new event MoneyWithdrawn 30 (append-only, usually with an expected version to detect concurrent writers).
  3. Publish the event so read models and other services update.

Benefits: full audit history; rebuild any state or new read model by replay; time travel ("what was the balance last Tuesday?"); natural fit with event-driven systems; debugging by replaying a sequence.

Costs:

  • Replay cost. A long-lived entity with 100,000 events is slow to load; use snapshots (store state every N events and replay only the tail).
  • Schema evolution. Events are forever. Old versions must stay readable; you write upcasters that convert old shapes to the new one on read.
  • Queries. You cannot easily ask "all accounts with balance over 1,000" from an event log, so you build read models (typically CQRS).
  • Mistakes. You cannot edit history; a wrong event is fixed by a compensating event.
  • Privacy. Deleting a person's data conflicts with immutability. A common answer is crypto-shredding: encrypt personal fields with a per-user key and delete the key.
  • Learning curve and tooling.

When. Where history is the domain: ledgers, trading, audit-heavy workflows, collaborative editing. Avoid it for plain CRUD.

Trap: confusing event sourcing with publishing events. A service can be event-driven (publishes events) while keeping a normal state table as its source of truth. Event sourcing is specifically that the events are the source of truth.

Remember: state = fold(events); snapshots for speed; read models for queries; compensate instead of edit.

What is CQRS and when is it worth it? Intermediate
Say: "CQRS uses one model for writes and a separate, denormalised model for reads, updated through events. It is worth it when read and write needs differ sharply; for plain CRUD it just adds lag and moving parts."

What it is. Command Query Responsibility Segregation. Commands change state and are validated against a normalised, consistent write model. Queries read from a separate model shaped for screens (denormalised, perhaps in a search index or cache). Events from the write side update the read side, so the read side is eventually consistent.

Example. An e-commerce write model is normalised: orders, order_lines, products. The "my orders" screen needs one row per order with product names, totals and status. A read model stores exactly that document per order, built by a projector listening to order events. The screen does one lookup instead of five joins.

Worth it when:

  • Reads and writes have very different load or shape (heavy search and dashboards, simple writes), so you want to scale and store them differently.
  • You need many different views of the same data.
  • You use event sourcing (CQRS is almost required to query it).

Not worth it when: basic CRUD with one view. You pay in lag, duplicated data and extra operations.

Read-your-writes. After a user saves, the read model may not have caught up, so they see old data. Fixes: return the new state or version in the command response and render it, route the user's next read to the write side briefly, or have the UI wait for the read model to reach that version.

Note. CQRS does not require separate databases or event sourcing; the lightest form is just separate code paths for commands and queries.

Remember: split read and write models only when their needs diverge, and plan for projection lag.

Choreography vs orchestration for event-driven workflows? Intermediate
Say: "Choreography means each service reacts to events with no central brain; orchestration means a coordinator drives the steps. Choreography for simple fan-out reactions, orchestration for long multi-step processes with failure handling."

Choreography. Each service listens and emits its own events: Order emits OrderPlaced; Payment reacts and emits PaymentCaptured; Inventory reacts to that and emits StockReserved; Shipping reacts. Nobody has the whole picture.

  • Pros: loose coupling, no single point of failure or bottleneck, easy to add a step.
  • Cons: the overall flow is invisible (you must read every service to know it), cyclic dependencies sneak in, and timeouts, compensation and "where is order 42 stuck?" are hard.

Orchestration. A coordinator (a workflow engine such as Temporal, AWS Step Functions or Camunda, or your own state machine) sends commands to participants, waits for replies, tracks state, handles timeouts and runs compensation.

  • Pros: the flow is explicit and readable in one place, status is easy to query, retries, timeouts and compensations are centralised.
  • Cons: the orchestrator must itself be highly available and durable, and it can grow into a "god service" holding business logic that belongs in the participants. Participants are coupled to its commands.

Outbox, CDC, sagas, schemas, replay

What is the dual-write problem? Intermediate
Say: "A service must update its database and publish an event, but those are two systems with no shared transaction, so a crash between them leaves them inconsistent. Retrying does not close the window; the outbox pattern does."

The two orders, both broken.

  1. DB first, then publish. Save order 42, crash before publishing. The order exists but OrderPlaced was never sent: payment, search and email never learn of it. Silent loss.
  2. Publish first, then DB. Publish OrderPlaced, then the database write fails (constraint, outage). Others act on an order that does not exist (phantom event).

Even a careful try/catch cannot fix it. If the process is killed (deploy, out of memory, power loss) between the two steps, no code runs to compensate. And two-phase commit across a database and a broker is mostly unsupported or too costly.

The deeper point. Any time one logical action updates two independent stores, "both or neither" is not available for free. The same issue appears with database plus cache, or database plus search index.

The fix. Write only to one store atomically (the database, including an outbox row describing the event), and let a separate process deliver the event reliably afterwards. That is the outbox pattern in the next question.

Remember: two systems, no atomicity; make one the source of truth and derive the other.

How does the transactional outbox pattern work? Intermediate
Say: "Write the business change and an outbox row in the same local DB transaction. A separate relay, by polling or CDC, publishes outbox rows to the broker and marks them sent. Delivery is at-least-once, so consumers are idempotent."

Steps:

  1. In the same local DB transaction that changes the business tables, insert a row into an outbox table: id, aggregate id, event type, payload, created_at, sent flag. Either both rows commit or neither does.
  2. A separate relay reads unpublished outbox rows in insertion order, publishes them to the broker, then marks them sent (or deletes them). It runs by polling (a query every few hundred ms; simple but adds latency and load) or by tailing the database log with CDC (low latency, no polling; the next answer).

Failure walk-through. The service commits order 42 plus an outbox row, then crashes. Nothing has been published yet, but the row is durable. On restart, the relay finds the row and publishes it. Events cannot be lost, only delayed.

At-least-once. The relay may publish, then crash before marking the row sent. After restart it publishes again, so a consumer can see a duplicate. Use the outbox row id as the event id so consumers can dedup.

Ordering. Process rows in insertion order (id or sequence) and publish with the aggregate id as the key, so events for one entity stay in order. With several relay instances, partition by aggregate id or use FOR UPDATE SKIP LOCKED carefully, otherwise order can break.

Housekeeping. Delete or archive sent rows, or the table grows forever.

Trade-off. Needs one table and one relay per service, adds slight latency, and the event is eventually published (not instantly). It is worth it because the alternative is silent inconsistency.

Remember: atomic write of data plus event row; relay publishes at-least-once; dedupe by event id.

What is change data capture (CDC) and how does it relate to the outbox? Intermediate
Say: "CDC reads the database's transaction log and turns each committed row change into an event, with no polling and no app changes. I use it to implement the outbox relay and to feed search, caches and warehouses."

What it is. Every database already writes all committed changes to a log for its own recovery and replication (MySQL binlog, Postgres write-ahead log). A CDC tool (Debezium is the best-known open-source one, often running on Kafka Connect) reads that log and emits an event per inserted, updated or deleted row, including before and after values.

Uses:

  • Keep a search index or cache in sync with the source table.
  • Replicate into a data warehouse or lake.
  • Build read models.
  • Outbox relay: tail only the outbox table. The application writes the outbox row in its transaction, CDC publishes it. No polling query is needed.

Advantages over polling the tables: low latency (milliseconds to seconds), no extra query load, captures every change in commit order, does not miss rows updated twice between polls, and captures deletes.

Disadvantages:

  • Schema leakage. If you capture business tables directly, events mirror internal table layouts. A column rename in the database becomes a breaking event change for every consumer. Fix by capturing a dedicated outbox table whose payload is a deliberately designed event.
  • Operations. Needs database configuration (log level, replication slot), log retention long enough that the connector can catch up after downtime (an abandoned Postgres replication slot can fill the disk), and an initial snapshot of existing rows.
  • Events are at-least-once; consumers dedupe.

Remember: CDC is the transport that reads the DB log; outbox is the pattern that makes the event intentional.

How does a saga work with events, and what about failures? Senior
Say: "A saga replaces a distributed transaction with a chain of local transactions, each followed by an event. If a step fails, earlier steps are undone with compensating actions, not rollbacks."

Why. In microservices each service owns its database, and a transaction across several is not available (2PC is rarely practical). Placing an order touches Order, Payment and Inventory. A saga makes this work with eventual consistency.

Happy path and failure path:

Order: OrderCreated (status PENDING)
 Payment: reserves money     -> PaymentCaptured
 Inventory: reserves stock   -> StockReserved  (or StockFailed)
 On StockFailed: Payment refunds (compensation) -> PaymentRefunded
                 Order marks CANCELLED

Key ideas:

  • Compensation is a new business action, not a database rollback. A refund is a new transaction. A sent email cannot be unsent, so order the steps so the hard-to-undo ones come last, and write the compensation ("sorry, order cancelled") as another message.
  • Idempotent and retryable. Every step and every compensation must tolerate duplicates, and a compensation must eventually succeed (retry until done, or alert a human).
  • No isolation. Other readers can see intermediate states (money captured, stock not yet reserved). Use semantic locks (a PENDING status that blocks conflicting operations) or reservations, and show customers "processing".
  • Persist saga state and timeouts. If a reply event is lost, a timer must notice and trigger compensation, or the saga hangs forever.
  • Style: choreography (services react to each other's events) for 2 or 3 steps; orchestration (a coordinator holding the state machine) beyond that.

Pitfall. Forgetting the failure of the compensation itself, and failing to handle events that arrive after the saga was cancelled (a late PaymentCaptured after cancel needs an automatic refund).

Remember: local transactions + events + compensations + persisted state with timeouts.

How do you evolve event schemas without breaking consumers? Senior
Say: "An event is a public contract and old events may live for years. I make only compatible changes, enforce them with a schema registry, and for a real breaking change publish a new version alongside the old and migrate consumers."

Why it is hard. Producers and consumers deploy at different times, and a log may hold years of old events. So at any moment old readers meet new data and new readers meet old data.

Compatibility terms:

  • Backward compatible: new code can read old data. (Consumers upgraded first can still read old events.)
  • Forward compatible: old code can read new data. (Producers upgraded first do not break old consumers.)
  • Full: both. Aim for this so deploy order does not matter.

Safe vs unsafe changes:

SafeUnsafe
Add an optional field with a defaultRemove or rename a field
Consumers ignore unknown fieldsChange a field's type
Add a new enum value if consumers handle unknownsChange the meaning of an existing field

Practices:

  • Use a schema format with compatibility rules (Avro, Protobuf, JSON Schema) and a schema registry that rejects an incompatible schema when the producer registers it, and in CI before deploy.
  • For a real breaking change: publish OrderPlaced v2 on a new topic (or alongside), dual-publish while consumers migrate, then retire v1. Carry a version or type in the envelope.
  • Consumer-driven contract tests show producers which fields each consumer really uses.
  • With event sourcing, upcasters convert old stored events to the latest shape when read.
Trap: reusing a field with a new meaning (for example amount switching from dollars to cents). Old data and old consumers silently misread it. Add a new field and deprecate the old one.

Remember: add-only, default values, registry checks, version for breaking changes.

What should every event carry (the envelope)? Intermediate
Say: "A consistent envelope: event id, type and schema version, event time, source and entity id, a per-entity sequence, correlation and causation ids, tenant, and then the payload."

The envelope is the metadata wrapped around the business payload so every consumer can handle events uniformly. Each field exists for a reason:

  • Event id (unique). Lets consumers dedup duplicates.
  • Event type and schema version. Tells consumers how to parse and whether they understand it.
  • Event time (when it happened) distinct from publish time (when it was sent). Needed for windowing and for handling late data.
  • Source service and entity id. Which system and which entity. The entity id is also the natural partition key so per-entity order holds.
  • Per-entity sequence or version number. Detects gaps (missed event) and stale events (older than what you have), enabling safe out-of-order handling.
  • Correlation id (shared by everything in one business flow, e.g. the original request) and causation id (the id of the event or command that caused this one). Together they let tracing rebuild the chain across services.
  • Tenant id for multi-tenant systems, for isolation and routing.
  • Payload. Keep personal data minimal: an event is copied to many consumers and may live for years.

How do replay and reprocessing work, and what must you watch out for? Senior
Say: "In a log I reset a consumer group's offset to reprocess history, to fix a bug, build a new read model or backfill a service. Handlers must be idempotent, external side effects must be suppressed, and the replay must not overload live traffic."

Mechanism. A log keeps messages until retention expires, and the consumer's position is just a number. Resetting it (to the beginning, to a timestamp) makes the consumer read old messages again. Typical reasons:

  • A consumer bug corrupted its output; fix the code, rewind, reprocess.
  • Build a new read model, index or service from history.
  • Recover a lost datastore.
  • Backfill a new consumer with the data from before it existed.

What to watch:

  • Idempotency. Otherwise the output is applied twice (counts doubled).
  • Side effects. A replay must not resend 3 million emails or re-charge cards. Split handlers: ones that update state (safe to replay) and ones that act on the outside world (guarded by a record of what was already done, or switched off in replay mode).
  • Load. Replaying at full speed alongside live traffic can overload downstream databases. Throttle, or run the replay in a separate consumer group writing to a new output (new table or index), then switch over at the end (blue-green for data).
  • Retention. The log must still hold the history you need. Compacted topics keep only the latest value per key, which suffices to rebuild state but not the full history.
  • Old schemas. Old events use old formats; the consumer must still parse them (another reason for schema compatibility).
  • Ordering with live data. Plan how replayed old events interact with newer state (version checks).
  • No retention, no replay. Queues like SQS delete consumed messages. There the source of truth must be the database or an archive: copy the stream to object storage for long-term replay.

Remember: replay is powerful only if handlers are idempotent, side effects are guarded, and you replay into a fresh output.

Batch, stream, and time

Batch vs stream processing: how do you choose? Basic
Say: "Choose by how fresh the business needs the answer. Batch processes a bounded dataset on a schedule and is simple and cheap; stream processes events continuously for second-level results but is harder to run."
BatchStream
InputBounded dataset (yesterday's files)Unbounded, continuous events
LatencyMinutes to hoursMilliseconds to seconds
StrengthSimple, cheap, easy to rerun, high throughput, complex joinsFresh results, reacting in time (fraud, alerts)
Hard partsStaleness, big spikes at schedule timeState, time, late data, always-on operations

Batch, in words. A job starts at 02:00, reads all of yesterday's orders, computes revenue per region, writes a report, and stops. If something is wrong, fix the code and rerun on the same input. Resource use is bursty: a big cluster for an hour, then nothing.

Stream, in words. A long-running job reads each order event as it arrives and updates running totals. Results are always current, but the job never stops: you must monitor it, upgrade it without losing state, and handle events that arrive late or out of order.

Examples. Daily revenue report: batch. Blocking a fraudulent card within a second: stream. A dashboard refreshed every 5 minutes: micro-batch (small batches every few seconds, as Spark Structured Streaming does by default) is a fair middle path.

Decision rule. Ask "what is the business cost of an answer being N hours old?". If low, use batch. Modern engines also treat batch as a special case of stream over a bounded input, so one codebase can serve both.

Remember: freshness requirement drives it; batch is simpler, stream is fresher.

Lambda vs kappa architecture at the concept level? Intermediate
Say: "Lambda runs a batch path and a speed path and merges them; kappa uses only a replayable stream path. Kappa avoids two codebases but needs a log with long retention and a capable stream engine."

Lambda. The same data goes down two paths:

  • Batch layer: recomputes accurate results over all history, slowly (hours).
  • Speed layer: a stream job gives fast but possibly approximate results for recent data.
  • Serving layer: merges both at query time (batch result for old data plus speed result for the last few hours).

The origin was that early stream engines were not trustworthy, so batch was the "truth". The cost: two codebases computing the same logic, which drift apart, and a merge to maintain.

Kappa. Only a stream path. The log (for example Kafka with long retention) is the source of truth. To fix a bug or change logic, deploy the new job version, replay the log from the start into a new output table, and when it has caught up, switch readers to it and drop the old. One codebase.

NeedsBoth toolchainsLong retention (or tiered storage) and a stream engine with solid state and exactly-once-effect

Today. Teams lean kappa-like where they can (and lakehouse tables that support both batch and streaming reads blur the line), and keep batch for heavy historical analytics or where team skill and tooling favour it.

Remember: lambda = two paths merged; kappa = one replayable stream.

What is windowing in stream processing? Intermediate
Say: "A stream never ends, so aggregates need a bounded slice: a window. Tumbling windows are fixed and disjoint, sliding windows overlap, and session windows follow bursts of activity separated by idle gaps."

Why. "Count orders" over an infinite stream has no final answer. "Count orders in each minute" does. A window defines which events belong together for an aggregate.

  • Tumbling: fixed size, no overlap, each event in exactly one window: 12:00 to 12:01, 12:01 to 12:02, and so on.
  • Sliding (hopping): fixed length that advances by a smaller step: "last 5 minutes, updated every minute". An event lands in several windows (here 5). Good for smoothed rates and moving averages.
  • Session: windows defined by activity per key. A window stays open while events keep arriving and closes after a gap of inactivity (user session ends after 30 minutes idle). Lengths vary per user.

Example. "Orders per minute per city" is a tumbling window keyed by city. Events: (Pune, 12:00:10), (Pune, 12:00:50), (Pune, 12:01:05). Window 12:00 to 12:01 for Pune has count 2; the next window has count 1.

Related. Which time the window uses (event time vs processing time) and when a window is closed (watermarks) are covered in the next question. Also note that state for open windows must be stored and checkpointed.

Remember: tumbling = disjoint, sliding = overlapping, session = gap-based.

What is event time vs processing time, and how do you handle late data? Senior
Say: "Window on event time, the moment it happened, not processing time. A watermark estimates how complete the data is; late events are dropped, accepted within allowed lateness, or sent to a side output for correction."

The two clocks. Event time is when the thing happened (a phone tapped "buy" at 12:00:05). Processing time is when your system saw it (maybe 12:03 because the phone was in a tunnel). If you window by processing time, a delayed event is counted in the wrong minute, and results change depending on network luck and backlog. Event time gives repeatable, correct results, but means you must decide how long to wait for stragglers.

Watermark. The engine's running estimate: "I do not expect any more events with time before T". When the watermark passes the end of a window (12:01), that window is complete and emitted. A simple watermark is "highest event time seen minus 2 minutes".

Late events (event time behind the watermark) can be:

  • Dropped. Simple; accept slightly wrong counts.
  • Accepted within allowed lateness. Keep the window state for an extra period (say 10 minutes); a late event updates and re-emits the result.
  • Sent to a side output for a separate correction path, for example a nightly batch that recomputes exact numbers.

The trade-off. A longer wait gives more complete results but delays them. A shorter wait is fast but loses stragglers. Choose with the business: a fraud alert wants speed and can accept approximate; billing wants completeness and can wait or correct later.

Downstream. If a window result can be re-emitted with an update, the sink must handle it: write with upserts keyed by (window, key) so the newer value replaces the older.

Remember: event time + watermark + lateness policy; latency vs completeness.

How does a stream processor keep state and survive a crash? Intermediate
Say: "State lives in a local store, and the engine periodically checkpoints it together with the input offsets to durable storage. After a crash it restores the last checkpoint and replays from that offset, giving effectively exactly-once with idempotent or transactional sinks."

Why state. Counts, windows and joins need memory of earlier events: "how many orders so far in this window?". Keeping it only in process memory loses it on a crash, and fetching it from a remote database per event is too slow.

Mechanism.

  1. State is kept locally next to the computation, often in an embedded store like RocksDB, partitioned by key (each worker holds the state for its keys).
  2. Periodically (every few seconds to minutes) the engine takes a consistent checkpoint: a snapshot of all operator state plus the current input offsets, written to durable storage (object storage, HDFS). Flink does this with barriers flowing through the stream; Kafka Streams instead writes state changes to a changelog topic.
  3. On a crash, restart workers, restore state from the last checkpoint, and rewind input to the offsets stored in it. Events processed after the checkpoint are reprocessed.
  4. Because state and offsets are restored together, internal results are exactly-once. For output to external systems, use transactional sinks (two-phase commit) or idempotent writes (upserts), otherwise reprocessed events produce duplicate output.

Concerns: state size (a large join or a long window can reach hundreds of GB; restore takes time), checkpoint overhead, and choosing a key that spreads state evenly. Use state TTL to expire old entries and standby replicas to cut recovery time.

Remember: local state + checkpoint (state and offsets together) + replay from checkpoint.

Scheduling, fan-out, notifications

How do you implement scheduled and delayed jobs at scale? Intermediate
Say: "For a few jobs, broker delay features; for scale, a durable jobs table with an indexed run_at claimed using SKIP LOCKED, or time buckets feeding a queue. For recurring cron, one leader or lock, plus idempotent jobs."

Problem. "Send this reminder in 3 days", "retry in 10 minutes", "expire this order at 15:30" for millions of items. A plain queue delivers immediately, so you need a way to hold work until its time.

Options:

  • Broker delay features. SQS per-message delay up to 15 minutes; RabbitMQ delayed-message plugin or the TTL plus dead-letter trick. Limited range and precision; poor for days-long delays.
  • Jobs table. Columns: id, payload, run_at (indexed), status. A poller selects due rows and claims them: SELECT ... WHERE run_at <= now() AND status='PENDING' ORDER BY run_at LIMIT 100 FOR UPDATE SKIP LOCKED. SKIP LOCKED makes several pollers share the table without picking the same row. Durable, queryable, cancellable, fine into the millions of jobs.
  • Redis sorted set with score = run time. Pollers fetch members with score up to now and claim them atomically (Lua script). Fast, but think about persistence and failover.
  • Time buckets (timer wheel). Store jobs grouped by minute. A ticker loads the next minute's bucket into a work queue. Scales to very large counts because only near-term jobs are in the hot path.
  • Workflow engines (Temporal and similar) offer durable timers as a built-in.

Recurring (cron) jobs. If 10 instances each run the cron, the job runs 10 times. Use leader election, a distributed lock or lease, or a dedicated scheduler service that enqueues the run. Even then, a double run is possible (a lease expires while the job still runs), so make jobs idempotent. Record each run so missed runs after downtime can be detected and caught up.

Pitfalls. Thundering herd at round times (everything scheduled at 00:00): add random jitter. Clock skew between machines: use database time. Jobs that outlive the claim: use a lease timeout and heartbeat.

Remember: durable store with indexed run time and safe claim; one scheduler; idempotent jobs.

Fan-out on write vs fan-out on read? Intermediate
Say: "Fan-out on write precomputes each recipient's inbox so reads are cheap but writes multiply; fan-out on read stores once and merges at read time. For skewed audiences I use a hybrid."

The classic case is a social feed: when Alice posts, her followers must see it in their feed.

  • Fan-out on write (push). On post, copy the post id into the feed list of every follower. Reading a feed is one fast lookup of a precomputed list. But one post by an account with 10 million followers means 10 million writes, causing spikes and delays, and much of that work is wasted on inactive users.
  • Fan-out on read (pull). Store the post once. When Bob opens his feed, fetch recent posts from each of the 300 accounts he follows and merge. Writes are cheap; reads are expensive and slower, especially for users with many follows.
  • Hybrid. Push for ordinary authors (few followers). For very large accounts ("celebrities"), do not push; at read time, merge the pushed feed with recent posts pulled from the celebrities the user follows. Also skip pushing to users who have been inactive for weeks.

Decision rule. Compare the read to write ratio and the shape of the follower distribution. The same reasoning applies to notifications and to pub/sub topic design.

Remember: pay at write or pay at read; hybrid when a few producers are huge.

How do you fan out one event to many independent consumers safely? Intermediate
Say: "Give each consumer its own durable queue or consumer group fed from the topic, so each has its own retries, DLQ, pace and lag, and a slow consumer cannot affect the others."

Patterns:

  • SNS to SQS: publish to one SNS topic; each consumer service has its own SQS queue subscribed to it. Each queue buffers, retries and dead-letters independently.
  • Kafka: one consumer group per consuming team on the same topic; each keeps its own offsets.

Why isolation. Suppose email, analytics and search all consume OrderPlaced. If analytics is slow, only analytics' queue grows. If search starts failing, only search's DLQ fills. The others are not delayed, and each can be scaled, paused or replayed independently.

The bug to avoid. Pointing all consumers at one shared queue. Then they compete: each message goes to only one of them, so email might get an order and search never sees it. Fan-out needs a copy per consumer.

Extras: subscription filters (consumers receive only event types they want), and a schema contract so a change does not break all consumers at once.

Remember: one queue or group per consumer; shared queue means competing, not fan-out.

What are the building blocks of a notification pipeline? Intermediate
Say: "Intake onto a queue, a notification service that applies preferences, templates and dedup, per-channel queues and workers, provider adapters with retry and fallback, and delivery tracking, all with idempotency keys."

Walk the pipeline from trigger to phone:

  1. Trigger intake. An API or event from other services ("order shipped"). Accept fast, put it on a queue, return.
  2. Notification service. Resolves the recipient, checks preferences and consent (opt-outs, quiet hours, per-channel settings, legal requirements), picks the channel(s), and renders a template with localisation (language, time zone).
  3. Dedup and rate limiting. Do not send the same alert twice; cap per-user frequency; collapse a burst into a digest ("5 new comments").
  4. Per-channel queues and workers for push, email and SMS, isolated so a slow SMS vendor does not delay push. Use priority lanes: one-time passwords before marketing.
  5. Provider adapters to APNs, FCM, email and SMS gateways. Each has retry with backoff, a circuit breaker, rate limits and, ideally, a fallback to a second provider.
  6. Delivery tracking. Store status (sent, delivered, opened, failed) from provider callbacks; handle bounces and invalid device tokens by removing them so you stop sending to them.
  7. Scheduling for delayed or time-zone-aware sends.

Reliability. Treat providers as unreliable and delivery as at-least-once. An idempotency key per notification (user, event, channel) checked before sending is what prevents a double SMS when a worker retries.

Remember: queue everything, respect preferences, isolate channels, retry per provider, track delivery.

How do you send a notification to 50 million users without overloading anything? Senior
Say: "Shard the audience into many jobs, process them in parallel under throttles matched to provider and backend limits, use priority lanes so the broadcast does not starve transactional messages, and make each shard resumable and idempotent."

Why a loop fails. One process looping over 50 million users is slow (at 1,000 per second it takes about 14 hours), cannot resume cleanly after a crash, and when it sends it hammers the user database and the push provider at the same time.

Design:

  1. Shard. Split the audience by user id range into, say, 5,000 shards of 10,000 users. Publish one job per shard.
  2. Parallel workers. Many workers each take a shard, page through its users, look up preferences, and enqueue per-channel sends.
  3. Throttle to the provider's rate limits and to what the preference store and user database accept. Spread the send over minutes, or tens of minutes, if the product allows, instead of seconds.
  4. Priority lanes. Broadcast traffic goes in a low-priority lane, so OTP and transactional alerts still go out immediately.
  5. Resumable and idempotent. Record progress per shard (last user id processed) and use an idempotency key (campaign id plus user id), so a crashed worker resumes without sending twice.
  6. Segment smartly. Respect opt-outs and quiet hours, and skip invalid tokens; time-zone-aware sending staggers the load naturally.

The spike after. If the notification is good, millions open the app within minutes. Prepare the backend (capacity, caches warmed, feature flag to degrade) or deliberately stagger the send in waves so the surge is manageable.

Remember: shard, throttle, prioritise, resume safely, and plan for the response spike.

Real-life scenarios

Customers were charged twice after a broker hiccup. How did it happen and how do you fix it? Senior
Say: "Almost certainly at-least-once redelivery: the worker charged the card but the ack never reached the broker. Fix with an idempotency key to the provider, a unique constraint per order, and a dedup record in the same transaction as the ledger entry."

How it happened.

  1. Worker receives "charge order 42" and calls the payment provider. The card is charged.
  2. Before the ack, something goes wrong: the worker crashes, a network blip loses the ack, a rebalance revokes the partition, or the visibility timeout (say 30 s) expires because the provider call took 40 s.
  3. The broker redelivers the message. A second worker (or the same one) charges again.

Immediate response: find duplicates (group charges by order id), refund the extra, tell customers.

Fix, in layers:

  • Idempotency key on the provider call (order id plus purpose). The provider returns the original result for a repeated key instead of charging again.
  • Unique constraint on payments (one per order) so the database refuses a second row.
  • Dedup record in the same transaction as the ledger entry.
  • Timeouts: set the visibility timeout above p99 call time, or heartbeat to extend it; set a provider call timeout below it.

Prevent recurrence. A reconciliation job comparing orders with provider charges daily, alerting on mismatches, plus a test that kills the worker between charge and ack.

Remember: assume redelivery; make the money-moving step idempotent end to end.

One partition's lag grows while others are fine. Diagnose. Senior
Say: "One lagging partition means something specific to that partition: a poison message, a hot key, a bad consumer instance, or an unusually slow data shape."

All the partitions use the same code and the same downstream, so the difference lies in the data on that partition or the instance reading it.

  1. Poison message. The consumer retries one offset forever. Signs: committed offset not moving, the same offset in logs and exceptions. Fix: bounded retries then DLQ.
  2. Hot key. One key sends most of the traffic to that partition. Signs: that partition's incoming rate is much higher than others. Fix: re-key, isolate the key on a dedicated topic, or speed up the handler.
  3. Bad instance. The consumer owning that partition is on an unhealthy host, stuck in long GC pauses, or blocked on a hung connection. Signs: that instance's CPU, memory, GC or thread dumps look unlike its peers. Fix: restart or replace; add timeouts to external calls so one hang cannot freeze a thread.
  4. Slow data shape. A huge payload or an expensive record type lands there. Signs: handler duration histogram for that partition. Fix: size limits, offload large payloads to object storage.

Order of checks. Look at the consumer logs for a repeating offset first (cheapest), then per-partition produce rate, then instance health.

Remember: single-partition lag is a data or instance problem, not a capacity problem.

Search results are missing items that exist in the database. How could events have been lost? Senior
Say: "The classic cause is a dual write: the service saved to the DB then published, and a crash or broker error between the two lost the event. Other candidates are early acks, unwatched DLQs, expired retention and schema breaks."

The search index is a derived copy of the database, kept in sync by events. Each way an event can vanish is a place to check:

  • Dual write. DB commit succeeded, publish failed or never ran. No trace exists in the broker.
  • Ack before indexing. Consumer acked, then crashed before writing to the index.
  • DLQ ignored. Failed events sit in a dead letter queue nobody monitors.
  • Retention expired. A lagging or paused consumer fell behind the retention window; the broker deleted unread messages.
  • Schema change. A new field or format made the consumer drop or skip events (silently on deserialization errors).
  • Ordering race. A delete event processed before the create, leaving a stale or missing document.

Fixes. Outbox plus CDC for publishing; ack after the index write succeeds; alert on DLQ depth and lag well before retention; fail loudly on deserialization errors.

Healing drift. Because losses will still happen eventually, add a periodic reconciliation (compare ids or checksums between DB and index) and a way to rebuild the index by replay or a full reindex from the source of truth.

Remember: derived stores drift; prevent loss, detect it, and be able to rebuild.

Real-world: what did a retry or queue related outage teach engineers? Senior
Say: "Public post-mortems repeatedly show retry amplification: clients' retries and timeouts add load to a struggling system and slow recovery. The lessons are capped backoff with jitter, retries at one layer, and load shedding."

Example. AWS's public summary of its December 2021 us-east-1 event describes an automated scaling activity that led to a surge of connection activity overwhelming networking devices between its internal network and the main network. The resulting latency and errors, together with clients' retry and timeout behaviour, made recovery harder. I am recalling this from memory, so treat details as approximate and read the AWS summary for specifics.

The general lesson, also in AWS's Builders' Library article on timeouts, retries and backoff with jitter:

  • Retries multiply load exactly when capacity is lowest.
  • Use capped exponential backoff with jitter, retry at a single layer, cap total retries (budget), and have servers shed excess load quickly rather than queueing it.
  • Design recovery so clients do not all return at once: gradually re-admit traffic.
  • Keep the monitoring and control plane independent of the thing that is failing, so operators can see and act.

How to use it in an interview. Tie it to a design choice: "Because of this I would put retry logic in one place, add jitter, and make the queue the buffer, pausing consumers when downstream is unhealthy."

Remember: failures are made worse by well-meaning clients; design the client side of recovery.

You inherit a checkout that calls six services synchronously and times out at peak. What do you move to async? Senior
Say: "Keep sync only what the customer must see before confirmation: validate cart, authorize payment, reserve stock. Move everything else to async through the outbox, add idempotency to the sync calls, and measure."

Why it times out. Latency adds up (six calls, each with its own p99), and availability multiplies: if each service is 99.9 percent available, six in series give about 99.4 percent. At peak, one slow service backs up threads and the whole checkout stalls.

Split the calls:

Stay sync (customer needs it now)Move async (can happen after)
Validate cart and pricesConfirmation email
Authorize paymentLoyalty points
Reserve stockAnalytics, recommendations
Search index and warehouse notification

Steps:

  1. Write the order and an outbox row in one transaction; publish OrderPlaced via the relay. Each async consumer has its own queue and DLQ.
  2. Add a status to the order (PENDING, CONFIRMED) so the UI can show "processing" for anything that can still fail later, and a compensation path (cancel and refund) if a later step fails.
  3. Give the remaining sync calls timeouts, circuit breakers and idempotency keys so client retries are safe.
  4. Roll out gradually (one consumer at a time, behind a flag), comparing results.
  5. Measure checkout p99 before and after, and monitor message age and DLQ for the async parts.

Remember: sync for what the user must see, async via outbox for the rest, with statuses and idempotency.
