How to use this page

Each question is a collapsible. Try to answer out loud first, then open it. Kafka internals (log segments, ISR, rebalancing protocol) live on a separate page; here the focus is design level: what to choose, why, and what breaks. When I say "broker" I mean the server that stores and routes messages (Kafka, RabbitMQ, SQS, Pub/Sub and so on). Names of vendors are examples of a style, not the only choice.

Why async, and the messaging models

Why would you make part of a system asynchronous? Basic

Synchronous means the caller waits for the result. Asynchronous means the caller hands off work (a message) and moves on; the work finishes later. Reasons to go async:

  • Latency of the user path: checkout returns in 200 ms after saving the order; sending the email, updating analytics and notifying the warehouse happen afterwards.
  • Decoupling in time: the consumer can be down or slow and the producer still works; the broker holds the work.
  • Load leveling: a burst of 50,000 requests per second is absorbed by the queue and drained at the 5,000 per second the workers can handle.
  • Failure isolation: a slow email provider does not take down checkout.
  • Independent scaling: add workers without touching the producer.
  • Fan-out: one event, many interested consumers, without the producer knowing them.

The price: eventual consistency, harder debugging, duplicates, ordering questions and more moving parts.

In practice the lines blur: SNS fanning into several SQS queues gives pub/sub plus durable per-consumer queues; Kafka consumer groups give queue semantics inside a group and pub/sub across groups.

Say: "Queue when the message is a task to do once; pub/sub when it is a fact many parties care about; a log when I need replay, ordering per key, and many independent readers."
When would you pick RabbitMQ or SQS over Kafka, and the reverse? Intermediate
  • Pick a traditional queue when: per-message handling (individual ack, per-message retry and delay, priorities, routing rules), moderate throughput, no need for replay, and you want a simple operational story (SQS is fully managed). Slow tasks of varying duration work well because any free worker takes the next message.
  • Pick a log/stream when: very high throughput, per-key ordering, several independent consumers of the same data, replay and reprocessing, event sourcing or CDC pipelines, stream processing.
  • A log has a head-of-line issue: within a partition one stuck message blocks later ones for that consumer, unless you move failures to a retry topic. A queue has no ordering but handles stuck messages by visibility timeout.
  • Parallelism in a log is capped by partition count; in a queue you can add as many workers as you like.
Push vs pull delivery: which is better for consumers? Intermediate
  • Push (broker sends to consumer; RabbitMQ consumers, SNS to HTTP): lowest latency, but the broker must guess consumer speed. Without a limit (RabbitMQ "prefetch") a slow consumer is flooded.
  • Pull (consumer asks; Kafka, SQS): the consumer controls its own rate, so backpressure is natural, and batching is easy (fetch 500 at once). Cost: polling overhead, solved by long polling (the request waits up to about 20 s for data).

Rule of thumb: pull gives the consumer control and is safer at scale; push is fine with a bounded in-flight window. Webhooks are push with all the downsides (receiver may be down, you must retry).

When is async the wrong choice? Senior
  • The user needs the answer now to proceed: payment authorization result, login, "is this username taken?". Faking it with polling adds complexity for nothing.
  • You need strong consistency across steps (a bank transfer inside one database should be one transaction, not events).
  • Low volume, simple system: a queue adds a broker to operate, monitor and secure for work that a direct call handles.
  • The caller must know about failure immediately to act on it (return 409 to the user).
  • Debuggability matters more than decoupling: a call chain with a trace is easier than a web of events with no clear owner.
  • Risk of "distributed monolith by events": services still need each other's replies, so you have sync coupling hidden behind messages, with extra latency.
Trap: saying "async scales better" with no cost. Name the costs: eventual consistency, duplicates, ordering, observability.
How do you design an async API: 202 Accepted, polling, webhooks? Intermediate

When the work takes longer than a request should (video transcode, report export, bulk import):

  1. Client calls POST /exports. Server validates, stores a job row (status QUEUED), puts a message on a queue, and returns 202 Accepted with a job id and a Location: /exports/123 header.
  2. Worker processes, updating status (RUNNING, SUCCEEDED, FAILED) and storing the result location.
  3. Client learns the outcome by one of:
    • Polling: GET /exports/123 every few seconds; simple, works through any firewall; use Retry-After and backoff so polling does not become load.
    • Webhook: server calls the client URL when done. Needs signature verification, retries with backoff, and idempotent receivers.
    • Push channel (WebSocket, SSE) for browsers.
  4. Make the submit idempotent with a client-supplied Idempotency-Key, so a retried POST does not create two jobs.

Also define: job expiry, cancel, and what a result of a failed job looks like.

What goes wrong with webhooks and how do you make them reliable? Intermediate
  • Receiver is down or slow: sender retries with exponential backoff for hours or days, then marks the endpoint failing and alerts the owner.
  • Duplicates and out-of-order delivery: receiver dedups on event id, and treats the payload as a hint then fetches current state if order matters.
  • Spoofing: sign the body (HMAC with shared secret, include a timestamp to stop replay) and receivers verify before processing.
  • Slow receiver: receiver should ack with 2xx fast and process on its own queue. Sender uses a short timeout.
  • One bad subscriber hurting others: deliver per subscriber from separate queues so one failing endpoint does not block the rest.
  • SSRF: if users supply URLs, block internal addresses.

Delivery guarantees, ordering, and consumers

Explain at-most-once, at-least-once and exactly-once delivery. Basic
GuaranteeHowRiskUse for
At-most-onceAck before processing (or fire and forget)Message lost if consumer crashes mid-workMetrics, telemetry where loss is fine
At-least-onceAck after processing; redeliver if no ackDuplicatesThe default for almost everything
Exactly-onceAt-least-once plus dedup or transactionsCost and scope limitsMoney, inventory (effect, not delivery)

The practical design: at-least-once delivery plus idempotent consumers gives "effectively once" outcomes.

Is exactly-once delivery real? How do you treat vendor claims? Senior

Over an unreliable network, a sender that gets no ack cannot tell whether the message arrived (the Two Generals problem), so it must resend or risk loss. True exactly-once delivery between two independent systems is impossible; what exists is exactly-once processing effect inside a bounded scope.

  • Kafka's idempotent producer plus transactions give exactly-once for read-process-write inside Kafka (consume from topic A, write to topic B and commit offsets atomically). Once you write to an external database or call an HTTP API, you are back to at-least-once and need idempotency.
  • The honest answer: "Exactly-once is atomic commit of the output and the input position, or idempotent writes. It holds within a system boundary only."
Trap: promising exactly-once for a side effect like sending an email. A crash between send and ack means a duplicate email; you can only reduce, not remove, the window (record a send id first, use provider idempotency keys).
What is an idempotent consumer and how do you build one? Intermediate

An operation is idempotent if doing it twice has the same effect as once. Since at-least-once will deliver duplicates, consumers must tolerate them.

  • Naturally idempotent: "set status to SHIPPED", upsert by key, "put object at path". Prefer these over "add 1" or "append".
  • Dedup table: each message has a unique id (producer-assigned). In one DB transaction: insert id into processed_messages (primary key) and apply the business change. If insert fails with duplicate key, skip. The atomicity matters; check-then-act in two steps has a race.
  • Conditional writes with versions: apply only if version = expected; also protects against out-of-order messages.
  • External calls: pass an idempotency key to the payment provider so a retry returns the earlier result.
BEGIN;
INSERT INTO processed(msg_id) VALUES (:id);   -- fails if seen
UPDATE account SET balance = balance - :amt WHERE id = :acc;
COMMIT;

Clean the dedup table by TTL longer than the broker's max redelivery or retention window.

Where can deduplication happen and what are the limits? Intermediate
  • Broker side: SQS FIFO dedups by message deduplication id within a 5 minute window; Kafka idempotent producer dedups retries within a producer session per partition. Limited in time and scope.
  • Consumer side: dedup store keyed by message id (database, or Redis with TTL). Authoritative because it is in the same transaction as the effect when using a database.
  • Business key dedup: "one payment per order id" enforced by a unique constraint. Strongest, because it survives even a producer that resends with a new message id.

Choose the key carefully: a message id changes if the producer retries and generates a new one; a business id (order id plus step) does not.

How do you preserve ordering in a distributed queue? Intermediate

Global ordering across a scaled queue is not realistic; it forces one consumer. What you usually need is ordering per entity (all events for order 42 in order). Do this by routing on a key:

  • Kafka: producer key hashed to a partition; one partition is read by one consumer in a group, so per-key order holds.
  • SQS FIFO: message group id; ordering inside a group.
  • RabbitMQ: consistent-hash exchange or sharded queues, one consumer per queue.

Things that break it: retries that reinsert later messages first (a failed message retried via another topic arrives after its successor), multiple producer threads without ordering, increasing partition count (changes the key-to-partition mapping), and parallel processing inside one consumer.

A partitioning key is skewed (one customer sends 40 percent of traffic). What do you do? Senior
  • Confirm via per-partition lag and throughput metrics: one partition far behind.
  • If strict order per customer is not needed, key by a finer key (customer plus order id).
  • If order is needed per customer, you cannot spread it; make that partition's consumer faster (batching, async I/O, cheaper processing), or give the big tenant a dedicated topic and consumers.
  • Salting (key plus random suffix 0..N) spreads load but breaks per-key order; fine for commutative operations like counters, aggregated later.
How do you choose partition count? Intermediate

Partitions cap consumer parallelism in a group (more consumers than partitions sit idle). Estimate: target throughput divided by per-consumer throughput, then add headroom (often 2x to 3x). Too many partitions cost broker memory, file handles, longer recovery and rebalances. Because changing the count remaps keys, choose with future growth in mind. Queues like SQS standard have no such cap.

What is a consumer group and how does it differ from competing consumers? Intermediate

Competing consumers is the pattern: several identical workers read one queue and each message is handled by exactly one of them, giving horizontal scale. A consumer group (Kafka term) is the implementation for logs: group members share partitions, each partition goes to one member. A different group has its own offsets and sees every message, so groups give pub/sub semantics across teams while members give queue semantics inside a team.

  • Billing and analytics each use their own group: both get every order event.
  • Scaling out: add members up to the partition count. When members join or leave, partitions are reassigned (rebalance), which briefly pauses consumption.
How do acks, visibility timeout and redelivery work in a queue? Intermediate

When a worker receives a message it is not deleted; it becomes invisible (SQS visibility timeout, default 30 s) or unacked (RabbitMQ). If the worker acks in time, the broker deletes it. If the worker crashes or is too slow, the message reappears and another worker takes it. Consequences:

  • Set the timeout above the p99 processing time, or extend it with a heartbeat. Too short gives duplicate concurrent processing; too long delays recovery after a crash.
  • Always ack after the work and its side effects are durable.
  • Track a receive count; after N, send to a DLQ.
When should a log consumer commit its offset: before or after processing? Intermediate

After. Commit before gives at-most-once (crash loses messages); commit after gives at-least-once (crash reprocesses a few). Committing every message is slow, so commit per batch and accept that a crash replays up to one batch, which idempotency covers. For exactly-once inside Kafka, commit offsets in the same transaction as the output writes. If the output is a database, store the offset in the same database transaction as the result and seek to it on start.

Why can a retry topic break ordering, and what are the options? Senior

If message 1 for key K fails and is moved to a retry topic while message 2 for K continues on the main topic, message 2 gets applied before 1. Options:

  • Block the partition and retry in place (preserves order, but one bad message stalls everything behind it; use a bounded retry count).
  • When a key has a message in retry, park all later messages for that key too (needs state).
  • Make processing tolerant: version numbers on state, apply only newer versions, ignore stale ones. This is usually the most robust.

Failures, retries, backpressure

How should retries work for a failing consumer? Basic
  • Classify errors: transient (timeout, 503, deadlock) are retried; permanent (validation failure, malformed payload, 4xx) are not, go straight to a DLQ.
  • Exponential backoff (1 s, 2 s, 4 s, 8 s...) with a cap, plus jitter (random spread) so thousands of failed messages do not retry in lockstep and hammer a recovering dependency.
  • Bounded attempts (say 5), then dead letter.
  • Delayed retry without blocking: retry tiers (topics or queues retry-1m, retry-10m, retry-1h) or delay queues; the consumer republishes with an attempt counter header.
  • Use a circuit breaker so when the dependency is down you stop consuming instead of burning every message's retry budget.
  • Retries need idempotent handlers.
What is a retry storm and how do you prevent it? Senior

A dependency slows down, timeouts trigger retries, retries add load, the dependency falls over harder. With layered retries (client retries 3x, service retries 3x, worker retries 3x) one failure becomes 27 calls. Prevent with: retries at one layer only, backoff with jitter, retry budgets (retries limited to about 10 percent of traffic), circuit breakers, and load shedding at the dependency. A queue is a natural buffer: pausing consumers is a better response than retrying hard.

What is a dead letter queue and how do you operate one? Basic

A DLQ is a side queue for messages that could not be processed after the allowed attempts (SQS redrive policy with maxReceiveCount, RabbitMQ dead-letter exchange, or a "-dlq" topic in Kafka). It keeps bad messages from blocking the main flow and from being lost.

  • Store the original payload plus failure reason, stack trace, attempt count, source topic and offset as headers.
  • Alert on DLQ depth above zero; a DLQ nobody looks at is just a slow way to lose data.
  • Provide tooling to inspect, fix, and redrive (replay) messages back to the main queue once the bug is fixed.
  • Set retention longer than your response time (SQS max 14 days; do not let evidence expire over a weekend).
  • Watch for PII sitting in a DLQ with weaker access controls.
What is a poison message and how do you handle it? Intermediate

A message that fails every time it is processed (corrupt payload, unexpected schema, a bug triggered by one value). In a log with in-order processing it blocks the partition forever; in a queue it cycles endlessly and wastes capacity, and may crash the worker each time (a "crash loop").

  • Cap attempts; on exceeding, divert to the DLQ and continue.
  • Catch deserialization errors separately from business errors so a bad payload is dead-lettered at once rather than retried.
  • Alert, and look for a pattern: one poison message is data, a hundred with the same error is a bad deploy or a producer breaking the contract.
What is backpressure and how do you apply it in a messaging system? Intermediate

Backpressure is the mechanism by which a slow consumer signals upstream to slow down, so queues and memory do not grow without bound. A queue alone only moves the problem: if producers are faster than consumers forever, the queue grows until storage is gone or latency is useless.

  • Pull consumers naturally limit themselves (fetch only when ready); bound in-flight work per consumer (prefetch, max.poll.records, a semaphore).
  • Bounded queues: when full, block the producer, or reject (HTTP 429 / 503 with Retry-After), or drop the lowest priority.
  • Load shedding: drop or sample non-critical work (analytics events) first.
  • Autoscale consumers on lag or depth, up to a cap set by the downstream database.
  • Rate limit producers per tenant so one cannot starve others.
  • Protect the sink: scaling workers 10x may just move the overload to the database. Cap concurrency to what the downstream accepts.
Why is queue depth (or consumer lag) a good signal, and what are its limits? Intermediate

Depth (messages waiting) or lag (log: latest offset minus committed offset) shows whether consumers keep up. Rising depth means arrival rate exceeds processing rate. It is the best input for autoscaling workers and for alerts.

  • Better than raw depth: age of the oldest message (or lag in time). 10,000 messages that drain in 2 seconds are fine; 100 messages stuck for an hour are not.
  • Depth by itself hides stuck consumers: a dead consumer in a partitioned log shows lag on one partition only; watch per-partition.
  • Zero depth can also mean the producer is broken. Alert on "no messages for X minutes" where traffic is expected.
  • Use Little's law for sizing: workers needed = arrival rate x average processing time. 2,000 msg/s at 50 ms each needs 100 concurrent workers, plus headroom.
Scenario: consumer lag keeps growing at 2 AM. What do you check, in what order? Senior
  1. Is it all partitions or one? One suggests a hot key or a poison message stuck; all suggests a capacity or dependency problem.
  2. Did producer rate rise (batch job, retry loop upstream, a new feature)?
  3. Did per-message time rise? Check the downstream (DB slow, third-party API throttling), GC pauses, a recent deploy.
  4. Are consumers in a rebalance loop (frequent joins or leaves, processing exceeding the poll timeout)? That looks like lag with no work done.
  5. Are messages failing and retrying? Retry traffic can multiply load.

Mitigation: scale consumers if the sink has room; otherwise shed or defer low priority work, pause non-critical producers, and drain after the dependency recovers. Afterwards add the alert on message age that should have fired first.

How do you give some messages priority? Intermediate

Prefer separate queues per priority (high, normal, bulk) with dedicated workers, or a weighted ratio such as 70 percent of capacity to high, with bulk getting what is left. Single-queue priority fields exist (RabbitMQ) but cost throughput and can starve low priority. Always prevent starvation of bulk work with a minimum share, and keep bulk imports from a single tenant in their own lane so they cannot delay interactive traffic (the noisy neighbour problem).

How does a broker avoid losing messages? Intermediate

Loss can occur at three places: producer to broker, inside the broker, broker to consumer.

  • Producer: wait for the broker's durable ack (not fire and forget), retry on timeout (with idempotent producer to avoid duplicates).
  • Broker: replicate to several nodes before acking (for example, replication factor 3 and acks from all in-sync replicas), flush or replicate policy, and avoid electing out-of-date leaders.
  • Consumer: ack after processing, as discussed.

The tradeoff is latency versus durability: more replicas acking means slower but safer writes.

Event-driven architecture

What is event-driven architecture and what do you gain and lose? Basic

Services communicate by publishing events (facts that happened, in past tense: OrderPlaced) rather than calling each other with commands (ReserveStock). Publishers do not know who listens. New consumers can be added with no change to the producer.

  • Gain: loose coupling, easy extension, natural audit trail, independent scaling and failure.
  • Lose: the flow is implicit (who reacts to OrderPlaced? hard to see), eventual consistency, harder end-to-end debugging, schema contracts become critical, and cycles (A reacts to B reacts to A) can appear.
  • Mitigate with distributed tracing (propagate a correlation id in headers), an event catalog, and consumer-driven contract tests.
What is the difference between an event and a command? Basic

A command is a request to do something, addressed to one handler, which may reject it ("CapturePayment"). An event is a record that something already happened, broadcast to anyone, and cannot be rejected ("PaymentCaptured"). Naming matters: the producer owns events about its own domain. Using events as disguised commands ("SendEmailEvent") brings back coupling because the producer expects a specific reaction.

Event notification vs event-carried state transfer: when do you use each? Intermediate

PayloadThin: id and type, e.g. {orderId: 42, type: OrderShipped}Fat: the full data needed, e.g. the whole order with address and items

A middle path is a medium event with the fields most consumers need plus an id for the rest. Use ECST when consumers need a local read model and independence; use notification when data is large, sensitive, or must be current.

What is event sourcing and what are its tradeoffs? Intermediate

Instead of storing the current state of an entity, store the full sequence of events that changed it (AccountOpened, MoneyDeposited 100, MoneyWithdrawn 30). Current state is derived by replaying events. A bank ledger is the classic analogy: the balance is a sum over entries.

  • Benefits: full audit history, ability to rebuild state or new read models by replay, "what was the state last Tuesday?" queries, natural fit with event-driven systems.
  • Costs: replay is slow for long histories so you need snapshots (store state every N events); events are forever, so schema evolution is hard (upcasting old versions); queries need separate read models (usually CQRS); fixing a bad event means writing a compensating event, not editing history; GDPR deletion conflicts with immutability (crypto-shredding: encrypt per user and drop the key); the team learning curve is real.
  • Use it where history is the domain (finance, ledgers, audit-heavy workflows). Avoid it for plain CRUD.
Trap: confusing event sourcing with merely publishing events. A service can be event-driven without storing events as its source of truth.
What is CQRS and when is it worth it? Intermediate

Command Query Responsibility Segregation: use separate models for writes (commands, validated, normalized, consistent) and reads (queries, denormalized, shaped for screens). The read side is updated from the write side by events, so it is eventually consistent.

  • Worth it: very different read and write loads or shapes (heavy search and dashboards, simple writes), many different views of the same data, event sourcing.
  • Not worth it: basic CRUD. It adds lag, duplication and operations.
  • Handle read-your-writes: after a command, return the new state or version, or have the UI wait or poll until the read model catches up.
Choreography vs orchestration for event-driven workflows? Intermediate
  • Choreography: each service reacts to events and emits its own; no central brain. Loosely coupled and simple for 2 or 3 steps, but the overall flow is invisible and cyclic dependencies sneak in.
  • Orchestration: a coordinator (workflow engine such as Temporal, Step Functions, Camunda, or your own state machine) sends commands to participants and tracks state. The flow is explicit, timeouts and compensation are in one place; the orchestrator must be made highly available and may become a god service.

Rule: choreography for simple fan-out reactions; orchestration for long, multi-step business processes with failure handling.

Outbox, CDC, sagas, schemas, replay

What is the dual-write problem? Intermediate

A service must update its database and publish an event. These are two systems with no shared transaction. If you write the DB then publish and crash between, the event is lost (other services never learn of the order). If you publish first then the DB write fails, you announced something that did not happen. Retrying does not fix it; the failure window always exists.

How does the transactional outbox pattern work? Intermediate
  1. In the same local DB transaction that changes the business tables, insert a row into an outbox table (id, aggregate id, type, payload, created_at).
  2. A separate relay reads unpublished outbox rows and publishes them to the broker, then marks them sent (or deletes them). Either by polling (simple, adds some latency and DB load) or by tailing the DB log with CDC.

The relay gives at-least-once (it may publish then crash before marking sent), so consumers must be idempotent. Use the outbox row id as the event id for dedup. To keep per-entity order, publish with the aggregate id as key and process outbox rows in insertion order.

What is change data capture (CDC) and how does it relate to the outbox? Intermediate

CDC reads the database's transaction log (MySQL binlog, Postgres WAL) and turns every committed row change into an event, without polling the tables or changing application code (Debezium is the well known open source tool). Uses: feed search indexes and caches, replicate to a warehouse, build read models, and implement the outbox relay (tail only the outbox table).

  • Pros over polling: low latency, no query load, captures commit order, nothing missed.
  • Cons: events mirror the table schema, so internal schema changes leak to consumers; fix by CDC on a dedicated outbox table with a purpose-built payload. Also needs log retention and DB config, and initial snapshots for existing data.
How does a saga work with events, and what about failures? Senior

A saga replaces a distributed transaction with a sequence of local transactions, each followed by an event; if a step fails, earlier steps are undone with compensating actions.

Order: OrderCreated
 Payment: reserves money     -> PaymentCaptured
 Inventory: reserves stock   -> StockReserved  (or StockFailed)
 On StockFailed: Payment refunds (compensation) -> PaymentRefunded
                 Order marks CANCELLED
  • Compensation is a new business action, not a rollback: a sent email cannot be unsent, so order steps so the hard-to-undo ones come last (and use "pending" states to expose in-between status).
  • Steps and compensations must be idempotent and retryable; a compensation must succeed eventually.
  • No isolation: other readers see intermediate states. Use semantic locks (status PENDING) or reservations.
  • Save saga state and timeouts, so a lost reply does not leave it stuck forever.
  • Choose choreography for 2 or 3 steps, orchestration beyond.
How do you evolve event schemas without breaking consumers? Senior

An event is a public contract and old events may live for years in the log. Rules:

  • Backward compatible: new readers can read old data. Forward compatible: old readers can read new data. Aim for both ("full") so producers and consumers can deploy in any order.
  • Safe changes: add optional fields with defaults; ignore unknown fields. Unsafe: remove or rename a field, change a type, change meaning.
  • Use a schema format with rules (Avro, Protobuf, JSON Schema) and a schema registry that rejects incompatible changes at publish time (and in CI).
  • For a real breaking change: publish a new version (OrderPlaced v2) on a new topic or alongside, dual-publish during migration, then retire v1 after consumers move. Include a version or type in the envelope.
  • Consumer-driven contract tests tell producers who depends on which field.
  • With event sourcing, "upcasters" convert old stored events to the latest shape on read.
Trap: reusing a field with a new meaning. Add a new field instead.
What should every event carry (the envelope)? Intermediate
  • Unique event id (dedup), event type and schema version.
  • Timestamp of occurrence (event time) distinct from publish time.
  • Source service and entity id (also used as the partition key), and a sequence or version number per entity (detect gaps and stale events).
  • Correlation id and causation id (tracing a business flow across services), tenant id.
  • Payload; keep personal data minimal.
How do replay and reprocessing work, and what must you watch out for? Senior

With a log, resetting a consumer group's offset (to a time or the beginning) reprocesses history. Reasons: fix a consumer bug, build a new read model or index, recover a lost datastore, backfill a new service.

  • Handlers must be idempotent, or output is applied twice.
  • Side effects must be suppressed or deduped: a replay must not resend 3 million emails or re-charge cards. Separate "update state" handlers (safe to replay) from "do external action" handlers (guard by record of already-done).
  • Replay at the same time as live traffic can overload downstream; throttle, or build the new view in a separate consumer group and switch over at the end.
  • Retention must cover the history you need; compacted topics keep the last value per key, good for state rebuild.
  • Old events use old schemas, so the consumer must still parse them.
  • Queues without retention cannot replay; the source of truth must be the database or an archive (copy the stream to object storage).

Batch, stream, and time

Batch vs stream processing: how do you choose? Basic
BatchStream
InputBounded dataset (yesterday's files)Unbounded, continuous events
LatencyMinutes to hoursMilliseconds to seconds
StrengthSimple, cheap, easy to rerun, high throughput, complex joinsFresh results, reacting in time (fraud, alerts)
Hard partsStaleness, big spikes at schedule timeState, time, late data, always-on operations

Choose by the freshness the business really needs. A daily revenue report is batch. Blocking a fraudulent card is stream. Micro-batch (Spark Structured Streaming style, a batch every few seconds) sits in between. Batch is a special case of stream over a bounded input in modern engines.

Lambda vs kappa architecture at the concept level? Intermediate
  • Lambda: two paths over the same data: a batch layer (accurate, recomputed over all history) and a speed layer (stream, fast approximate), merged at query time. Problem: two codebases that must compute the same thing, and a merge to maintain.
  • Kappa: only a stream path. The log is the source of truth; to fix a bug or change logic, replay the log through new code into a new output and swap. One codebase. Needs a log with long retention and a stream engine capable of large replays and correct state.

Modern teams lean kappa-like where possible, and keep batch for heavy historical analytics or when stream tooling is not mature enough in the team.

What is windowing in stream processing? Intermediate

Because the stream never ends, aggregates (count, sum) need a bounded slice: a window.

  • Tumbling: fixed, non-overlapping (each minute: 12:00 to 12:01, 12:01 to 12:02).
  • Sliding (hopping): fixed length that moves by a smaller step (last 5 minutes, updated every minute); an event lands in several windows.
  • Session: grouped by activity, closed after a gap of inactivity (user session ends after 30 minutes idle).

Example: "orders per minute per city" is a tumbling window keyed by city.

What is event time vs processing time, and how do you handle late data? Senior

Event time is when the thing happened (phone tapped at 12:00:05). Processing time is when the system saw it (maybe 12:03 after the phone came out of a tunnel). Windowing on processing time is easy but wrong when delays vary; use event time.

  • A watermark is the engine's estimate "no events older than T are still expected". When the watermark passes the end of a window, the window is emitted.
  • Late events (after the watermark) can be: dropped, accepted within an allowed lateness period (and the result is updated), or sent to a side output for correction by a batch job.
  • The tradeoff is latency versus completeness: a long wait gives more accurate results but delays them.
  • Updated results must be handled downstream: use upserts keyed by window.
How does a stream processor keep state and survive a crash? Intermediate

Operators like counts and joins hold state (often in a local embedded store such as RocksDB). To survive failure, the engine takes periodic checkpoints of state together with the input offsets, to durable storage; on a crash it restores the last checkpoint and replays from that offset. With idempotent or transactional sinks this gives effectively exactly-once results. Changelog topics (Kafka Streams) serve the same role. Key concern: state size and restore time, so partition by key to spread it.

Scheduling, fan-out, notifications

How do you implement scheduled and delayed jobs at scale? Intermediate
  • Broker delay features: SQS delay up to 15 minutes; RabbitMQ delayed-message plugin or TTL plus dead-letter trick; limited range and precision.
  • Database table of jobs with run_at indexed; a poller selects due rows with SELECT ... FOR UPDATE SKIP LOCKED, so several pollers can share the table without double pick. Simple, durable, queryable, cancelable. Fine to millions of jobs.
  • Redis sorted set scored by run time: poll for items with score less than now; fast, but ensure durability and atomic claim (Lua).
  • Timer wheel or hierarchical buckets: bucket by minute in the store, a ticker loads the next minute's bucket into a queue; scales to huge counts.
  • Workflow engines (Temporal) give durable timers.
  • Recurring jobs (cron): avoid every node running the same cron. Use leader election or a distributed lock/lease, or a scheduler service, and make jobs idempotent since a double run is possible. Add a run record so missed runs after downtime can be detected.

Beware thundering herd at round times (everybody schedules at 00:00); add random jitter.

Fan-out on write vs fan-out on read? Intermediate
  • Fan-out on write (push): when an item is created, copy or enqueue it to every recipient's inbox immediately. Reads are cheap and fast (read one precomputed list). Writes are expensive: one post by an account with 10 million followers means 10 million inbox writes, creating spikes and delay.
  • Fan-out on read (pull): store the item once; when a recipient reads, gather from sources and merge. Writes are cheap; reads are expensive and slower, especially for users with many sources.
  • Hybrid: push for ordinary producers, pull for very large producers ("celebrities") and merge at read time. Also skip inactive users when pushing.

Choose by read to write ratio and the shape of the fan-out distribution. The same logic applies to notifications and to pub/sub topic design.

How do you fan out one event to many independent consumers safely? Intermediate

Give each consumer its own durable queue or consumer group fed from the topic (SNS to one SQS queue per consumer; Kafka one group per team). Then each has its own retries, DLQ, speed and lag, and one slow consumer does not delay or block the others. A single shared queue for different consumers is a bug: they would compete for messages instead of each getting a copy.

What are the building blocks of a notification pipeline? Intermediate
  1. Trigger intake: API or events from services ("order shipped"), accepted fast and put on a queue.
  2. Notification service: resolves recipients, looks up preferences and consent (opt-outs, quiet hours, per-channel settings), picks the channel, renders a template with localization.
  3. Dedup and rate limiting: do not send the same alert twice; cap per-user frequency; collapse bursts into a digest.
  4. Per-channel queues and workers (push, email, SMS), isolated so a slow SMS vendor does not delay push. Priority lanes: OTP codes before marketing.
  5. Provider adapters (APNs, FCM, email, SMS gateways) with retry, backoff, circuit breaker and fallback to a second provider.
  6. Delivery tracking: store status (sent, delivered, opened, failed) from provider callbacks; handle bounces and invalid device tokens by removing them.
  7. Scheduling for delayed sends, and idempotency key per notification to survive retries.

Treat the provider as unreliable and assume at-least-once; the idempotency key is what prevents double SMS.

How do you send a notification to 50 million users without overloading anything? Senior

Do not loop in one process. Split the audience into shards (by user id range), publish one job per shard, and let many workers process them in parallel. Throttle to the provider's limits and to what the backends (preference store, user DB) accept; spread over minutes rather than seconds if the product allows. Use priority lanes so a broadcast does not starve transactional messages. Track progress per shard and make shards resumable and idempotent, so a worker crash resends nothing twice. Expect the traffic spike after the push (users open the app at once) and prepare the backend, or stagger the send.

Real-life scenarios

Customers were charged twice after a broker hiccup. How did it happen and how do you fix it? Senior

Likely cause: at-least-once delivery. The payment worker charged the card, then the ack was lost (worker crash, visibility timeout shorter than the call time, or a rebalance), so the message was redelivered and charged again.

  • Immediate: find duplicates by order id, refund.
  • Fix: pass an idempotency key (order id plus attempt scope) to the payment provider; add a unique constraint on payment per order; store a dedup record in the same transaction as the ledger entry; set the visibility timeout above p99 call time.
  • Prevent recurrence: a reconciliation job comparing orders with provider charges.
One partition's lag grows while others are fine. Diagnose. Senior

Candidates: (1) a poison message the consumer retries forever in place; (2) a hot key sending most traffic to that partition; (3) the consumer instance for that partition is on a bad host or stuck in GC or a long call; (4) a slow handler for one specific data shape (a huge payload). Look at the consumer logs for the repeated offset, at per-key traffic distribution, and at the instance health. Fix by dead-lettering the poison message with a bounded retry, rekeying or isolating the hot key, or replacing the instance.

Search results are missing items that exist in the database. How could events have been lost? Senior

A classic dual write: the service saved to the DB and then published to the broker, and a crash or broker error between the two lost the event. Others: consumer acked before indexing and crashed, a DLQ nobody reviewed, retention expired before a lagging consumer caught up, schema change made the consumer drop events. Fix with the outbox plus CDC, ack after the write, a DLQ alert, and lag alerts well before retention. Add a periodic reconciliation or rebuild by replay from the source of truth to heal drift.

Real-world: what did a retry or queue related outage teach engineers? Senior

Public post-mortems repeatedly show retry amplification. For example, the December 2021 AWS us-east-1 event, as AWS described it, involved a surge of connection activity from an automated scaling activity that overwhelmed networking devices, and the resulting retries and timeouts from clients made recovery harder (details hedged; read the AWS summary for specifics). The general lesson, also stated in AWS's builders library, is to use capped exponential backoff with jitter, retry at one layer, and design systems to shed load so recovery is not blocked by their own clients.

You inherit a checkout that calls six services synchronously and times out at peak. What do you move to async? Senior

Keep on the sync path only what the customer must see before the confirmation: validate cart, authorize payment, reserve stock. Move to async via the outbox: confirmation email, loyalty points, analytics, search index update, warehouse notification, recommendation updates. Add a status field so the UI can show "processing" for anything that can still fail; add idempotency keys to the remaining sync calls so client retries are safe; add timeouts and circuit breakers to the sync ones. Measure p99 before and after, and monitor queue age for the async pieces.
