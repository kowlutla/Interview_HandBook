Mental model: the 8 ideas everything hangs on

One line: an exception is an object that travels up the call stack until someone handles it; generics are a compile-time check that is erased before runtime; I/O is bytes plus (sometimes) a charset plus a resource that must be closed.
  1. An exception is a normal object with a captured stack. Creating it walks the stack and records it, which is the expensive part. Throwing it unwinds frames until a matching catch is found.
  2. Checked vs unchecked is a compiler rule, not a runtime difference. Only the compiler forces you to handle checked ones. At runtime they behave the same.
  3. Never lose the cause. Wrap with the original as the cause, log once at the boundary, and never swallow silently.
  4. Handle exceptions at the layer that can do something about them. Lower layers translate technical errors to meaningful ones; the top layer turns them into a response.
  5. Generics exist only at compile time. The compiler checks types, inserts casts, then erases the type arguments. At runtime a List<String> is just a List.
  6. Bytes are not text. Text needs a charset to turn bytes into characters. Always say the charset out loud in code.
  7. Every opened resource needs a guaranteed close. In modern Java that means try-with-resources. A forgotten close is a production leak, not a style problem.
  8. Reflection and proxies are how frameworks work. Annotations are only data; some code (Spring, Jackson, Hibernate) reads them at runtime using reflection, and pays a cost for it.

1. Exception basics

Draw the exception hierarchy. What are Throwable, Error, Exception and RuntimeException? Basic

What the interviewer is testing: the basic map, and whether you know which branch the compiler checks.

Throwable is the root. Only a Throwable can be thrown or caught. It has two children. Error means a serious problem in the JVM or environment, such as OutOfMemoryError, StackOverflowError or NoClassDefFoundError. You normally do not catch these, because the program usually cannot repair them. Exception means a problem your code might reasonably handle. Under Exception, RuntimeException and its children (NullPointerException, IllegalArgumentException, IllegalStateException, IndexOutOfBoundsException) are unchecked. Everything else under Exception (IOException, SQLException, InterruptedException) is checked. Errors and RuntimeExceptions are unchecked; the compiler does not force you to declare or catch them.

Likely follow-ups
  • Can you throw a Throwable directly? Yes, but nobody should; use a specific type.
  • Is InterruptedException checked? Yes, and it needs special handling (see the interrupt question).
What is the difference between checked and unchecked exceptions? Basic

What the interviewer is testing: the rule, and the intent behind it.

A checked exception must be either caught or declared with throws in the method signature. The compiler enforces this. An unchecked exception needs neither. The original idea was: use checked for failures the caller can reasonably recover from and that are outside the program's control, like a missing file or a network drop. Use unchecked for programming mistakes, like a null argument or an index out of range, where the right fix is to change the code, not to catch. At runtime there is no difference between them. It is purely a compile-time contract on method signatures.

void read() throws IOException { ... }   // caller must handle
void check(int n) { if (n < 0) throw new IllegalArgumentException("n < 0"); }  // no declaration needed
Likely follow-ups
  • Is a custom exception checked by default? It is checked if it extends Exception, unchecked if it extends RuntimeException.
Checked exceptions: good idea or a mistake? What do you do in your own code? Senior

What the interviewer is testing: whether you have an opinion backed by real trade-offs, not a slogan.

The case for checked: the signature tells you honestly what can fail, and the compiler stops you ignoring it. The case against, which most of the industry now accepts: they leak implementation details up the layers (a SQLException in a service interface), they force empty or wrapping catch blocks, and they do not work with lambdas because standard functional interfaces like Function declare no checked exceptions. Adding a new checked exception to an interface breaks every caller and implementation. Spring, Hibernate and most modern libraries chose unchecked. My practice: use unchecked exceptions by default with clear, domain-named types; keep checked ones for the few places where the caller truly has a different recovery path, such as a business "insufficient funds" outcome in a small API, and even then consider returning a result object instead. At boundaries with legacy APIs I translate checked to unchecked and keep the cause.

Likely follow-ups
  • Which languages dropped checked exceptions? C#, Kotlin, Scala, and others never had them.
  • What is "sneaky throw"? A trick that throws a checked exception without declaring it, using generics erasure. It works but hides contracts. Avoid it.
Common mistakes: saying "checked is always bad". Say it depends on whether the caller can recover and whether the exception crosses an abstraction boundary.
Should you ever catch an Error such as OutOfMemoryError or StackOverflowError? Intermediate

What the interviewer is testing: judgement about what is recoverable.

Normally no. After an OutOfMemoryError the JVM may be in a bad state: other threads can also fail anywhere, even inside your own error handler, and data structures may be half updated. The sensible reaction is to log if possible and let the process die, so the orchestrator restarts it (run with -XX:+ExitOnOutOfMemoryError or -XX:+HeapDumpOnOutOfMemoryError to get a dump). A StackOverflowError is more recoverable, because the stack unwinds when you catch it; some parsers catch it to reject deeply nested input, but fixing the recursion is better. There are legitimate catches at a top-level boundary: a worker thread's loop catches Throwable so one bad task does not kill the thread, logs it, and carries on. catch (Exception e) does not catch Errors, so a catch-all for Errors needs Throwable and a good reason. Never catch ThreadDeath or LinkageError and carry on as if nothing happened.

Likely follow-ups
  • Difference between NoClassDefFoundError and ClassNotFoundException? The first is an Error: the class was there at compile time and is missing or failed to initialize at runtime. The second is a checked exception from Class.forName when the class is not found by name.
How does catch ordering work, and what does the compiler complain about? Basic

What the interviewer is testing: the first-match rule.

The JVM checks catch blocks from top to bottom and runs the first one whose type matches (the thrown object is an instance of the catch type). So you must put the more specific subclass first. If you put catch (Exception e) before catch (IOException e), the second can never run, and the compiler gives an error "exception has already been caught". Also, catching a checked exception that the try block can never throw is a compile error (except for Exception and Throwable themselves).

try { read(); }
catch (FileNotFoundException e) { /* specific first */ }
catch (IOException e)           { /* then the parent */ }

2. try, catch, finally and resources

Explain the exact execution order of try, catch and finally. Basic

What the interviewer is testing: basic control flow, including what happens to a return value.

The try block runs. If it finishes normally, control goes to finally, then continues after the statement. If it throws, the first matching catch runs, then finally. If no catch matches, finally still runs and then the exception continues upward. If the try or catch does a return, the return value is calculated and saved first, then finally runs, then the method really returns the saved value. That is why changing a primitive in finally does not change what was returned, but changing a mutable object that was returned does show.

Likely follow-ups
  • Can there be try with finally and no catch? Yes.
  • Can the catch itself throw? Yes, and finally still runs before that new exception moves on.
What does this print, and why is return inside finally dangerous? Intermediate

What the interviewer is testing: the classic trap, and the habit of avoiding it.

static int f() {
    int x = 1;
    try { return x; }          // value 1 is saved
    finally { x = 2; }         // does not change the saved value
}                              // returns 1

static int g() {
    try { throw new RuntimeException("boom"); }
    finally { return 42; }     // exception is discarded, returns 42
}

In f the return value was already copied, so the answer is 1. In g a return (or break or continue) inside finally overrides whatever was happening, including a thrown exception. The exception vanishes with no trace. That is why it is bad practice, and many compilers and linters warn about it. The same thing happens if the finally block itself throws: the new exception replaces the original, and the original cause is lost. Keep finally blocks tiny and non-throwing, or use try-with-resources which handles this properly.

Common mistakes: thinking the saved value changes if you modify the variable. It does not for primitives and references (the reference is saved), but the object it points to can change.
When does a finally block not run? Intermediate

What the interviewer is testing: that "always runs" has exceptions.

Finally does not run if the JVM stops before reaching it: System.exit() inside try (or catch), a crash such as a fatal native error, the process being killed with kill -9, or power loss. It also does not complete if the thread loops forever or blocks forever in the try block. In a daemon thread, when the last non-daemon thread ends the JVM exits and the daemon thread is stopped mid-way, so its finally may never run. Finally also cannot protect you against the machine disappearing, so it is not a place for critical durability: use transactions and idempotent recovery for that.

Likely follow-ups
  • Do shutdown hooks run after System.exit? Yes, hooks registered with Runtime.addShutdownHook run, but finally blocks of other threads do not.
What is try-with-resources and why is it better than try/finally? Basic

What the interviewer is testing: modern resource handling since Java 7.

A resource is anything that implements AutoCloseable (or Closeable): files, streams, sockets, JDBC connections. You declare it in the parentheses after try, and Java calls close() for you at the end, whether the block finishes normally or throws. If you declare several, they are closed in reverse order of creation, like unstacking plates. The old way needed a finally block with null checks and a nested try/catch for close(), which was verbose and, crucially, a failing close() would replace the real exception. Try-with-resources fixes that with suppressed exceptions. Since Java 9 you can use an existing effectively-final variable: try (res).

try (var in  = Files.newBufferedReader(src);
     var out = Files.newBufferedWriter(dst)) {
    in.transferTo(out);
}   // out closed first, then in
Likely follow-ups
  • What if a resource expression is null? Nothing is closed for it; no NPE.
  • If the constructor of B throws, is A closed? Yes. Resources already created are closed.
What are suppressed exceptions? When would you see one? Intermediate

What the interviewer is testing: can you read a real stack trace from a try-with-resources failure.

Imagine the body of a try-with-resources throws exception E, and then close() also throws exception C. Only one exception can propagate, and the primary one (E) is the useful one, because it is the real cause. Java attaches C to E using E.addSuppressed(C). You can read them with e.getSuppressed(), and the stack trace prints them under "Suppressed:". If the body succeeded but close throws, then C simply propagates as the main exception. You can call addSuppressed yourself in hand-written cleanup code when you want to keep two failures, for example while closing several resources in a loop and remembering all errors.

Exception in thread "main" java.io.IOException: write failed
    at App.run(App.java:12)
    Suppressed: java.io.IOException: close failed
        at MyRes.close(MyRes.java:8)
        at App.run(App.java:10)
Likely follow-ups
  • Why is it called suppressed? Because it was suppressed from propagating, and parked on the main exception.
What is multi-catch, and what are its restrictions? How does precise rethrow work? Intermediate

What the interviewer is testing: Java 7 features and their small rules.

Multi-catch lets one block handle several unrelated exception types: catch (IOException | SQLException e). The alternatives must not be related by inheritance (you cannot write IOException | Exception), because the broader type would make the narrower one pointless. The variable e is implicitly final, so you cannot reassign it. Its static type is the closest common supertype of the alternatives. Precise rethrow is a related Java 7 improvement: if you catch Exception e and rethrow it, and e is effectively final, the compiler knows that only the exceptions the try block can actually throw come out, so your method can declare just those checked exceptions instead of throws Exception.

try { work(); }
catch (IOException | SQLException e) {
    log.error("failed", e);
    throw e;               // precise rethrow: compiler knows the real types
}
What is exception chaining, and how do you preserve the cause? Basic

What the interviewer is testing: the habit that makes production bugs debuggable.

When you catch a low-level exception and throw a different one, pass the original as the cause. Then the final stack trace shows "Caused by:" lines all the way down to the root. Use the constructor new MyException("message", cause), or initCause for old exception classes that have no cause constructor. Without the cause you only see where you rethrew, and the real failure (a timeout, a constraint violation) is lost. Write a message that adds context the low level did not know, such as the order id, and not just the same words again. Use getCause() in a loop to find the root cause, or ExceptionUtils.getRootCause from commons-lang.

try { repo.save(order); }
catch (SQLException e) {
    throw new OrderStoreException("cannot save order " + order.id(), e);   // cause kept
}
Common mistakes: throw new RuntimeException(e.getMessage()) (loses the stack and type) and e.printStackTrace() followed by a new exception (prints to stderr, outside your logging system).
What does "swallowing an exception" mean and why is it so harmful? Basic

What the interviewer is testing: your instincts on error handling quality.

Swallowing means catching an exception and doing nothing: an empty catch block, or only a comment, or logging only e.getMessage() and continuing. The code goes on with wrong or missing data, and the failure shows up much later, far from the real cause, with no trace to follow. It is one of the most expensive habits in production support. Each catch should do one of three things: recover for real (a documented fallback), translate and rethrow with the cause, or log with the full stack and an explicit decision to continue. If you really want to ignore, such as when closing a resource quietly after a failure, say so in a named helper (closeQuietly) and still log at debug level.

catch (IOException e) { }                              // bad: silent
catch (IOException e) { log.warn(e.getMessage()); }    // bad: no stack, no cause
catch (IOException e) { log.warn("cache write failed, continuing without cache", e); }  // ok if intended
Are exceptions slow? What is the real cost, and when does it matter? Intermediate

What the interviewer is testing: understanding where the cost is, instead of repeating "exceptions are slow".

The expensive part is creating the exception, not throwing it. The Throwable constructor calls fillInStackTrace(), which walks the whole call stack and records every frame. With a deep stack (Spring, servlets, frameworks routinely give 100 or more frames) this takes microseconds to tens of microseconds and allocates memory. Unwinding through a few frames is cheap in the JIT-compiled case. So using exceptions for normal control flow, for example one per failed lookup in a hot loop, can hurt, and a flood of exceptions in a hot path shows up in profilers. Fixes: do not use exceptions for expected outcomes (return Optional or a result), reuse a pre-built exception for a truly hot control-flow path, or override fillInStackTrace (or use the protected constructor with writableStackTrace=false) for lightweight exceptions. One more detail: for certain built-in exceptions (NullPointerException, ArrayIndexOutOfBoundsException) the JIT may start throwing a pre-allocated instance with no stack trace after many throws, which confuses people reading logs. Flag -XX:-OmitStackTraceInFastThrow turns that off.

class LightException extends RuntimeException {
    LightException(String m) { super(m, null, false, false); } // no suppression, no stack trace
}
Likely follow-ups
  • Is try/catch itself costly when nothing is thrown? No. The exception table is data, with no cost on the normal path.
  • Why do I see an NPE with an empty stack trace in logs? The fast-throw optimization above. Look at earlier occurrences of the same error.
What are the rules for exceptions when overriding a method? Intermediate

What the interviewer is testing: a rule people often half-remember.

An overriding method may declare fewer checked exceptions, the same ones, or narrower subclasses of them. It may not add a new checked exception or a broader one, because a caller using the parent type would not know to handle it. It may freely throw any unchecked exception. A constructor of a subclass must declare any checked exceptions the super constructor declares (or broader). For interface implementations the same applies: the interface method sets the maximum. This is another reason checked exceptions cause design friction: a new implementation that talks to a database cannot throw SQLException through an interface that did not allow it.

class Base { void run() throws IOException { } }
class Ok1 extends Base { void run() throws FileNotFoundException { } }  // narrower: ok
class Ok2 extends Base { void run() { } }                                // fewer: ok
class Bad extends Base { void run() throws Exception { } }               // broader: compile error
How should you handle InterruptedException? Senior

What the interviewer is testing: an exception that is really a cancellation signal; mishandling it causes hangs on shutdown.

An InterruptedException means another thread asked this thread to stop what it is doing. When it is thrown, Java clears the thread's interrupt flag. If you simply swallow it, you erase the cancellation request and the thread keeps running, so the executor never shuts down. The rules: if you can, let it propagate by declaring throws InterruptedException. If you cannot (for example inside a Runnable), restore the flag with Thread.currentThread().interrupt() and then exit your loop or return quickly. Do not log and continue as if nothing happened. Blocking calls like sleep, wait, join, BlockingQueue.take and Future.get all throw it. More on threads in Java concurrency.

try { queue.put(item); }
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restore the signal
    return;                               // stop cleanly
}

3. Exception design and error handling strategy

How do you design a good custom exception? Intermediate

What the interviewer is testing: API design sense, not just extends RuntimeException.

Name it after what went wrong in the domain, not after the technology: PaymentDeclinedException, not MyException. Pick checked or unchecked deliberately (usually unchecked). Provide at least a message constructor and a message-plus-cause constructor, so the cause can always be preserved. Add useful fields, like an error code, the id of the entity, or whether a retry is sensible, instead of making callers parse the message. Keep a small hierarchy: one base for your module (OrderException) with a few meaningful children, so callers can catch broadly or narrowly. Make the message safe: no passwords, tokens or full personal data. Add serialVersionUID because Throwable is Serializable (the compiler lint warns). Do not create one class per error message; an enum error code inside one exception class is often enough.

public class PaymentDeclinedException extends RuntimeException {
    private static final long serialVersionUID = 1L;
    private final String paymentId;
    private final boolean retryable;
    public PaymentDeclinedException(String paymentId, boolean retryable, String msg, Throwable cause) {
        super(msg, cause);
        this.paymentId = paymentId; this.retryable = retryable;
    }
    public String paymentId() { return paymentId; }
    public boolean retryable() { return retryable; }
}
Likely follow-ups
  • Should exception fields be mutable? No; make them final. Exceptions travel across threads.
  • Should the exception build the message with expensive data? Avoid it; the message is built even when nobody reads it.
What is exception translation, and where should it happen in a layered application? Senior

What the interviewer is testing: whether you understand error handling as part of architecture.

Translation means catching a low-level exception at a layer boundary and throwing one that makes sense for the layer above, with the original attached as the cause. A repository catches SQLException and throws OrderStoreException; the service turns that into a domain outcome such as OrderNotFoundException or TemporarilyUnavailableException; the web layer maps domain exceptions to HTTP status codes and a stable error body. This stops upper layers depending on JDBC or an HTTP client, keeps messages meaningful, and lets you swap implementations. The cost is a little more code and care that each translation keeps the cause. Frameworks do this for you: Spring translates JDBC and JPA errors into its DataAccessException hierarchy, and @ControllerAdvice with @ExceptionHandler maps exceptions to responses in one place.

Likely follow-ups
  • Where do you convert exceptions to HTTP status codes? In one central handler, not scattered in controllers.
Design an error handling strategy for a layered REST service. Senior

What the interviewer is testing: a coherent policy, not isolated tips.

I would set a few rules for the whole team. First, separate three kinds of failure: client mistakes (bad input, not found, conflict: map to 4xx, do not alert), expected business outcomes (insufficient funds), and system failures (database down, timeout: map to 5xx, alert). Second, use a small set of unchecked domain exceptions carrying an error code and a safe message. Third, validate at the edge (Bean Validation) and fail fast with IllegalArgumentException or a validation error, so deep layers can trust their inputs. Fourth, one global handler turns exceptions into a consistent JSON error body (Spring 6 supports RFC 9457 ProblemDetail) that includes a correlation id, never a stack trace. Fifth, log each failure once, at the layer that finally handles it, with the stack and the correlation id. Sixth, for calls to other services, apply timeouts, bounded retries for transient errors only, and a circuit breaker. Seventh, make writes idempotent so a retry is safe. Finally, test the failure paths, not just the happy ones.

Likely follow-ups
  • What do you return to the client for a 500? A generic message and the correlation id. Details stay in the logs.
  • Where does transaction rollback fit? See the Spring rollback question below.
Why is "log and throw" an anti-pattern? What should you do instead? Intermediate

What the interviewer is testing: experience with real logs.

If every layer logs the exception and rethrows it, one failure produces three or five log entries with the same stack. That doubles the noise, makes error counts wrong (one failure looks like five), and confuses whoever reads the log at 3 a.m. The rule is: either handle the exception (and log it there) or let it propagate (and add context in a wrapper). Not both. Log at the boundary where the exception stops travelling: the controller advice, the message consumer loop, the scheduler wrapper. If a lower layer has useful context the upper layer lacks, put it into the exception message rather than into a separate log line. The one exception to the rule: log at a boundary that hides the failure from the caller, for example when you swallow an optional operation and continue.

// bad
catch (SQLException e) { log.error("db failed", e); throw new StoreException("db failed", e); }
// good
catch (SQLException e) { throw new StoreException("cannot load order " + id, e); }  // logged once at the top
What are the alternatives to exceptions for error handling? When would you use a Result type? Senior

What the interviewer is testing: awareness of modern styles and their limits in Java.

Exceptions suit unexpected, exceptional failures that most callers cannot handle locally. For expected outcomes, a normal return value is clearer and cheaper: Optional for "may be absent", a boolean or enum for a simple status, or a result type (Result<T, E>, also called Either) that carries success or failure and forces the caller to look at both. In Java 17 and later, a sealed interface with record cases plus pattern-matching switch (final in Java 21) gives a compiler-checked result type with no library. Libraries like Vavr offer Try and Either. Use results for validation and business rules where failure is common and local, and exceptions for unexpected faults that should unwind. The trap is mixing styles: a method that returns a Result and also throws forces callers to handle both.

sealed interface Result<T> permits Ok, Err {}
record Ok<T>(T value) implements Result<T> {}
record Err<T>(String code) implements Result<T> {}

String msg = switch (parse(input)) {
    case Ok<Integer> ok -> "value " + ok.value();
    case Err<Integer> err -> "error " + err.code();
};
Likely follow-ups
  • Why not Optional for errors? It says "nothing" but not why.
When is it safe to retry after an exception? How do idempotency and retries connect? Senior

What the interviewer is testing: that error handling does not stop at the catch block.

Retry only transient failures: timeouts, connection resets, HTTP 503 or 429. Never retry validation errors, authentication failures or other deterministic errors, since the answer will not change. The danger is a timeout where you do not know whether the first attempt succeeded: retrying a "create payment" call could charge twice. That is why you make operations idempotent: the client sends an idempotency key (a unique id for the logical operation), and the server stores it with the result, so a second request with the same key returns the first result instead of repeating the work. Reads and PUT-style "set to this value" updates are naturally idempotent. A good retry policy has a small max attempt count, exponential backoff with random jitter (so many clients do not retry in lockstep), an overall deadline, and a circuit breaker when the dependency is clearly down. Libraries: Resilience4j, Spring Retry. See Microservices and REST and Distributed systems for the system-level view.

Likely follow-ups
  • What is a retry storm? Many layers each retry three times, so one failure becomes 27 calls. Retry at one layer only.
In Spring, which exceptions roll back a transaction? Intermediate

What the interviewer is testing: how exception types affect real behavior.

By default @Transactional rolls back on unchecked exceptions (RuntimeException and Error) and commits on checked exceptions. That surprises people: a method that throws a checked IOException after writing to the database will still commit. To change it use @Transactional(rollbackFor = Exception.class). A second trap is catching the exception inside the transactional method and swallowing it: the proxy sees a normal return and commits, even though part of the work failed. A third is calling a transactional method from the same class (self-invocation), which bypasses the proxy so no transaction logic runs at all. See Hibernate and JPA for more.

How do you deal with NullPointerException in a principled way? Basic

What the interviewer is testing: practical null discipline, not just "check for null".

A NullPointerException means you used a reference that points to nothing. Since Java 14 (default on from 15), the message tells exactly which variable or call was null, such as Cannot invoke "String.length()" because "name" is null, which saves a lot of debugging time. To prevent them: validate arguments early with Objects.requireNonNull(x, "x") so failure happens at the entry, not three calls later; return empty collections instead of null; use Optional for return values that may be absent (not for fields or parameters); and use annotations such as @Nullable with a checker. Do not catch NPE to hide bugs. Return an unmodifiable empty list, or an Optional, and make the contract clear in Javadoc.

4. Exceptions in lambdas, threads, constructors and static initializers

How do you deal with checked exceptions inside lambdas and streams? Intermediate

What the interviewer is testing: a daily annoyance, and whether your fix is sensible.

Standard functional interfaces such as Function, Consumer and Supplier do not declare checked exceptions, so a lambda that calls a method throwing IOException does not compile. Options: catch inside the lambda and wrap in an unchecked exception (simple, local); write a small helper that converts a throwing function into a normal one; define your own functional interface that declares throws Exception and wrap it once; or avoid streams for that step and use a plain loop, which is often the clearest. Remember also that an exception thrown in the middle of a stream pipeline stops the whole pipeline, and with a parallel stream it may be thrown from a worker thread. If you want "skip bad items", catch inside the lambda and return an empty Optional or a Result, then filter.

@FunctionalInterface interface ThrowingFn<T,R> { R apply(T t) throws Exception; }
static <T,R> Function<T,R> unchecked(ThrowingFn<T,R> f) {
    return t -> { try { return f.apply(t); }
                  catch (Exception e) { throw new RuntimeException(e); } };
}
paths.stream().map(unchecked(Files::readString)).toList();   // toList: Java 16
Common mistakes: wrapping with new RuntimeException(e.getMessage()) and losing the cause, or swallowing the error inside forEach so the pipeline "succeeds" with missing data.
An exception is thrown inside a task submitted to an ExecutorService. Where does it go? Senior

What the interviewer is testing: a classic silent failure in concurrent code.

It depends on how you submitted. With submit(), the task is wrapped in a FutureTask, which catches any Throwable and stores it inside the Future. Nothing is logged and nothing is thrown until someone calls future.get(), which throws an ExecutionException whose cause is your exception. If you never call get(), the failure is silently lost. With execute(), the exception escapes the Runnable, kills that worker thread, and goes to the thread's UncaughtExceptionHandler, which by default prints the stack to stderr; the pool then creates a replacement worker. In a ScheduledExecutorService, a periodic task that throws is cancelled and never runs again, with no message. Fixes: wrap the task body in try/catch that logs, set a handler through a custom ThreadFactory, always handle the Future result, and for scheduled jobs always catch Throwable inside the task.

executor.submit(() -> {
    try { doWork(); }
    catch (Throwable t) { log.error("job failed", t); }   // never let it vanish
});
Likely follow-ups
  • How about CompletableFuture? Exceptions are stored in the future and wrapped in CompletionException; use exceptionally or handle, and always end a chain with one.
  • Parallel streams? The first exception is rethrown to the caller; others may be lost.
What is an UncaughtExceptionHandler and how do you set one? Intermediate

What the interviewer is testing: a global safety net for threads.

When a thread ends because of an exception that nobody caught, the JVM calls that thread's UncaughtExceptionHandler. If none is set, the thread group prints the stack trace to System.err, which many production setups never collect. You can set one per thread with thread.setUncaughtExceptionHandler, for all new threads with Thread.setDefaultUncaughtExceptionHandler, or inside a custom ThreadFactory for a pool. In the handler, log with your logger, add the thread name, and maybe raise a metric. It only fires for threads that die from the exception: it will not fire for exceptions stored in a Future. The main thread behaves the same: the default handler prints and the JVM exits when no other non-daemon threads remain.

ThreadFactory tf = r -> {
    Thread t = new Thread(r, "worker");
    t.setUncaughtExceptionHandler((th, ex) -> log.error("thread {} died", th.getName(), ex));
    return t;
};
What happens if a constructor throws an exception? Any danger? Intermediate

What the interviewer is testing: object lifecycle and resource safety.

If a constructor throws, the new expression never produces a reference. The caller gets the exception and no object, and the half-built object becomes garbage. This is the right way to reject invalid arguments: a constructor should leave you with a valid object or nothing. The dangers are about what already happened: if the constructor opened a file or started a thread before failing, nothing will call close() on it, so the resource leaks. Do the validation first, acquire resources last, and close what you opened in a catch block before rethrowing. Another danger is leaking this (registering the object in a listener list or starting a thread from the constructor) before it is fully built. In old Java, a finalizer on a half-built object could "resurrect" it, a known attack on security-sensitive classes, which is another reason to avoid finalizers.

What happens when a static initializer throws? What is ExceptionInInitializerError? Senior

What the interviewer is testing: a confusing production failure with two different error names.

When a class is first used, the JVM runs its static initializers once. If one throws an unchecked exception, the JVM wraps it in ExceptionInInitializerError (an Error) for the first caller, with the real exception as the cause. The class is then marked as failed. Every later attempt to use that class in the same classloader throws NoClassDefFoundError with the message "Could not initialize class X", and that second error does not show the original cause. In the logs you often see the second error thousands of times, and the first, informative error is long gone. So when you see "Could not initialize class", search the logs back for the first ExceptionInInitializerError. Prevention: keep static initialization simple and safe, do not read config or connect to remote systems there, and use lazy holders or explicit init methods that can be retried.

Likely follow-ups
  • Can the class be recovered? Not in the same classloader; you need a restart or a new loader.
How do you read a long stack trace with several "Caused by" sections? Basic

What the interviewer is testing: daily debugging skill.

The first line is the outermost exception: the last one thrown, usually from the top layer. The lines under it are the call stack from the throwing point down to the thread start, with the most recent call first. Then each "Caused by:" line starts the previous exception's cause, and the last "Caused by:" is the root cause, which is almost always where you should look first. The line "... 23 more" means those frames are the same as the enclosing trace and were omitted to save space. Find the first frame in your own package inside the root cause section; that is where your code touched the failing call. Also look for "Suppressed:" entries. When the bottom cause is a generic message, check the surrounding log lines with the same correlation id.

5. Generics

Why were generics added, and what do they give you? Basic

What the interviewer is testing: the motivation, as a base for later questions.

Before Java 5 a List held Object, so you had to cast on every read, and a wrong type was found only at runtime as a ClassCastException. Generics let you say List<String>. The compiler then checks every add and get, so type errors become compile errors, and the casts are inserted for you. They also let you write one algorithm (a method, a class) that works for many types without losing type information, which is why the collections, Optional, Stream and CompletableFuture are generic. The price is erasure: generics were added in a backward-compatible way, so the type information exists only at compile time.

List raw = new ArrayList();      raw.add(1);  String s = (String) raw.get(0); // fails at runtime
List<String> typed = new ArrayList<>(); typed.add(1);                         // fails at compile time
What is type erasure and what exactly does the compiler do? Intermediate

What the interviewer is testing: the central fact about Java generics.

After checking types, the compiler removes (erases) the type arguments from the bytecode. A type parameter T with no bound becomes Object; T extends Number becomes Number. Where code reads a value as String, the compiler inserts a cast. If needed it also generates bridge methods so overriding still works. The class file keeps some generic information as metadata (signatures), which reflection and tools can read, but the runtime objects carry no type arguments. So an ArrayList<String> and an ArrayList<Integer> are the same class at runtime. This was a deliberate choice for migration compatibility, so old non-generic code and new generic code could work together.

Likely follow-ups
  • Why not reified generics like C#? Compatibility with millions of existing classes. Project Valhalla works on specialized generics for primitives in the future.
What can you NOT do with generics because of erasure? Intermediate

What the interviewer is testing: concrete consequences, the favorite follow-up.

You cannot create an instance of T (new T()), because the runtime does not know it. You cannot use instanceof List<String> (only instanceof List<?>) or cast to a parameterized type without an unchecked warning. You cannot create arrays of a generic type: new T[10] and new List<String>[10] are errors. You cannot use primitives as type arguments (List<int>), so you pay for boxing. You cannot declare a static field of type T, because statics belong to the class, not an instance. A generic class cannot extend Throwable, and you cannot catch T. You cannot overload two methods that differ only in type arguments, because they erase to the same signature. The common workaround for needing the type is to pass a Class<T> token, or a factory Supplier<T>.

class Box<T> {
    private final Class<T> type;
    Box(Class<T> type) { this.type = type; }
    T make() throws Exception { return type.getDeclaredConstructor().newInstance(); }
}
void m(List<String> a) {}
void m(List<Integer> a) {}   // compile error: same erasure
What are bounded type parameters? Explain <T extends Comparable<T>>. Intermediate

What the interviewer is testing: how to give a type parameter capabilities.

A bound limits what types are allowed and lets you call methods of the bound. In <T extends Number> you can call doubleValue() on a T. In <T extends Comparable<T>>, T must be comparable with itself, so you can call a.compareTo(b). This pattern (a type referring to itself) is called a recursive bound. In real code the more flexible form is <T extends Comparable<? super T>>, because a class like java.sql.Timestamp extends Date and compares as a Date, not as itself. Multiple bounds use &: <T extends Number & Comparable<T>>, with at most one class and it must come first. The erasure of such a type is its first bound.

static <T extends Comparable<? super T>> T max(Collection<? extends T> c) {
    Iterator<? extends T> it = c.iterator();
    T best = it.next();
    while (it.hasNext()) { T x = it.next(); if (x.compareTo(best) > 0) best = x; }
    return best;
}
Explain wildcards and the PECS rule: Producer Extends, Consumer Super. Senior

What the interviewer is testing: the hardest everyday generics topic. A clear answer here signals real depth.

? extends T means "some unknown subtype of T". You can safely read items out as T (the list produces T), but you cannot add anything except null, because the real list might be a List<Integer> while you hold it as List<? extends Number>. ? super T means "some unknown supertype of T". You can safely write a T in (the list consumes T), but anything you read out is only an Object. ? alone means unknown type: read as Object, write nothing. So: if a parameter produces values for you, use extends; if it consumes values from you, use super; if both, use no wildcard. The classic example is Collections.copy(List<? super T> dest, List<? extends T> src).

double sum(List<? extends Number> xs) { double s = 0; for (Number n : xs) s += n.doubleValue(); return s; }
void fill(List<? super Integer> out) { out.add(1); out.add(2); }   // can take List<Number> or List<Object>
sum(List.of(1, 2.5));     // ok
fill(new ArrayList<Number>());  // ok
Likely follow-ups
  • Why is List<Integer> not a List<Number>? Because you could then add a Double through the Number view and break the Integer list. See invariance below.
  • What is wildcard capture? The compiler gives the unknown type a temporary name so a helper method <T> void swapHelper(List<T> l) can work on a List<?>.
Arrays are covariant but generics are invariant. What does that mean and why does it matter? Senior

What the interviewer is testing: the reason behind generic design.

Covariant means "if Integer is a Number, then Integer[] is a Number[]". For arrays, that is true in Java. That sounds handy, but it is unsafe: you can assign an Integer[] to a Number[] variable and then store a Double. The compiler allows it, and the runtime throws ArrayStoreException, because arrays remember their real element type. Generics chose the safer path: they are invariant, so List<Integer> is not a List<Number> and the unsafe store is rejected at compile time. Since generics are erased, they could not do the runtime check that arrays do, so they needed the stricter compile-time rule. Wildcards (? extends) give back flexible read-only views safely. This also explains why you cannot make a generic array: arrays check their element type at runtime, and that type is erased.

Number[] a = new Integer[1];
a[0] = 1.5;                          // compiles; ArrayStoreException at runtime
List<Number> l = new ArrayList<Integer>();   // compile error: invariant
How do generic methods work, and how does type inference help? Intermediate

What the interviewer is testing: the syntax and the compiler's reasoning.

A generic method declares its own type parameter before the return type: static <T> List<T> listOf(T a, T b). It can be used inside a non-generic class, and it works independent of any class parameter. At the call site you rarely write the type, because the compiler infers it from the arguments and from the target type (what you assign the result to). The diamond new ArrayList<>() (Java 7, and with anonymous classes from Java 9), lambdas (Java 8) and var (Java 10) all lean on inference. When inference fails, you can give an explicit type witness: Collections.<String>emptyList(). Inference can pick a surprising type, such as Object or an intersection type, when the arguments are of mixed types, which sometimes shows up as a confusing compile error message.

static <T> T firstOr(List<T> xs, T fallback) { return xs.isEmpty() ? fallback : xs.get(0); }
String s = firstOr(names, "none");         // T inferred as String
var m = new HashMap<String, List<Integer>>();   // var + diamond (Java 10+)
What is a raw type, and why should you avoid it? Basic

What the interviewer is testing: legacy awareness and type-safety discipline.

A raw type is a generic class used without type arguments: List instead of List<String>. It exists only so pre-Java-5 code still compiles. When you use a raw type, the compiler switches off generic checks for that expression and gives only an "unchecked" warning, so you can add an Integer into what other code believes is a list of strings. The mistake blows up later, somewhere else, as a ClassCastException. Raw types also make all members of that type erased, which affects even unrelated generic methods called on them. If you truly do not care about the element type, write List<?>, which is safe: you can read Objects and cannot add. Do not suppress unchecked warnings widely; suppress on the smallest scope with a comment explaining why it is safe.

What is heap pollution, and how can it cause a ClassCastException that looks impossible? Senior

What the interviewer is testing: deep understanding of what erasure allows.

Heap pollution means a variable of a parameterized type refers to an object that is not of that type. It happens when unchecked warnings are ignored: through raw types, unchecked casts, or generic varargs. The JVM cannot detect it at the point of the mistake, because type arguments are erased. The failure comes later, at the compiler-inserted cast on the read, in a line that looks perfectly safe. The stack trace points at innocent code, and the real culprit was an earlier unchecked add. Example below: the list is given a Integer through a raw alias, then String s = strings.get(0) fails.

List<String> strings = new ArrayList<>();
List raw = strings;                 // unchecked warning
raw.add(42);                        // pollution: no error here
String s = strings.get(0);          // ClassCastException: Integer cannot be cast to String

Generic varargs are another source: static <T> void f(T... xs) creates a T[] that is really an Object[], so the method can store wrong things in it. If your method only reads the array and does not leak it, mark it @SafeVarargs (allowed on static, final and, since Java 9, private methods). Defensive practice: treat every unchecked warning as a bug until proven safe; use Collections.checkedList in suspicious boundaries, which checks type at insertion time.

What is a reifiable type? Senior

What the interviewer is testing: the vocabulary behind instanceof, arrays and varargs rules.

A reifiable type is one whose full type information is available at runtime. These are: primitives, non-generic classes and interfaces, raw types, parameterized types where all arguments are unbounded wildcards (List<?>), and arrays of reifiable types. List<String> and T are not reifiable, because erasure removed their arguments. The rules built on this idea: instanceof and casts to a non-reifiable type are unchecked or illegal; you can only create arrays of reifiable types (new List<?>[3] works, new List<String>[3] does not); and a varargs parameter of a non-reifiable type gives the "possible heap pollution" warning. When you need a non-reifiable type at runtime anyway, use a type token such as Jackson's TypeReference or Guava's TypeToken: they capture the type through an anonymous subclass, because the generic superclass signature TypeReference<List<String>> is kept in the class metadata.

Why can't you create a generic array, and how do collections like ArrayList get around it? Senior

What the interviewer is testing: connecting arrays, erasure and unchecked casts.

new T[n] is illegal because arrays need their real element type at runtime to do store checks, and T is erased. If it were allowed you could build a List<String>[], put in a List<Integer> through an Object[] alias, and the array check could not detect it. Library code gets around it by creating an Object[] and casting: (T[]) new Object[n]. This is an unchecked cast, safe only if the array never escapes to code that expects a real T[] (for example a String[]), otherwise a ClassCastException follows. ArrayList stores Object[] internally and casts on each read. If you must return a real T[], pass a Class<T> and use Array.newInstance(type, n), or accept an IntFunction<T[]>, as stream.toArray(String[]::new) does.

@SuppressWarnings("unchecked")
T[] make(int n) { return (T[]) new Object[n]; }      // ok inside, bad if returned as String[]
String[] arr = list.stream().toArray(String[]::new); // the clean way
What is a bridge method? Senior

What the interviewer is testing: knowing that the compiler quietly generates code to keep polymorphism working with erasure.

Take Comparable<T>: after erasure its method is compareTo(Object). Your class Money implements Comparable<Money> writes compareTo(Money). These are different signatures, so on the JVM level you have not overridden anything. The compiler solves it by generating a hidden bridge method compareTo(Object) that casts its argument to Money and calls your method. You can see it with javap -p and by the ACC_BRIDGE flag in reflection (Method.isBridge()). Bridge methods also appear for covariant return types. They are the reason reflection-based frameworks sometimes find two methods with the same name, and why annotations on the real method may need to be looked up on the non-bridge one. A stack trace may show an extra frame for the bridge too.

class Money implements Comparable<Money> {
    public int compareTo(Money o) { ... }         // what you wrote
    // public int compareTo(Object o) { return compareTo((Money) o); }  // generated bridge
}
How can you get the generic type at runtime anyway (for example in Jackson)? Senior

What the interviewer is testing: practical workaround knowledge.

Erasure removes type arguments from objects, but the class file still stores generic signatures of declarations: fields, method parameters and return types, and the generic superclass. Reflection exposes these through getGenericSuperclass(), Field.getGenericType() and ParameterizedType. The super type token trick uses this: you create an anonymous subclass new TypeReference<List<User>>() {}. Its generic superclass records List<User> permanently, and the library reads it. That is why Jackson needs mapper.readValue(json, new TypeReference<List<User>>() {}): with List.class it would produce a list of maps, not Users. The simpler tool is a Class<T> token for non-generic cases.

Give guidance on designing a generic API: what mistakes do you see? Senior

What the interviewer is testing: taste, which senior engineers need.

Prefer generic methods and wildcard parameters to accept the widest input: take Collection<? extends T>, not List<T>, when you only read. Return concrete, precise types, not wildcards: a return type List<? extends Foo> forces callers to deal with wildcards. Do not over-generify: a type parameter used once (appearing in only one place) is often better as a wildcard. Avoid raw types and unchecked casts. Keep bounds simple, and do not build types like Map<String, List<Map<Integer, Set<X>>>> in public APIs; give them a name by creating a small class or record. Prefer composition with a lambda (Function<T,R>) to deep generic class hierarchies. And document the rule for nulls and mutability. Fewer type parameters make an API easier to read and to evolve.

6. Java I/O: streams, readers, buffering, charsets

What is the difference between byte streams and character streams (readers/writers)? Basic

What the interviewer is testing: the most basic I/O split, and whether you know where charsets come in.

InputStream and OutputStream move raw bytes: images, zip files, network packets. Reader and Writer move characters (text). A reader sits on top of a stream and uses a charset to decode bytes to characters, and a writer encodes characters back to bytes. The bridge classes are InputStreamReader and OutputStreamWriter. Use streams for binary data and readers for text, and always give the charset explicitly: new InputStreamReader(in, StandardCharsets.UTF_8). Using a reader on binary data corrupts it, and using a stream on text forces you to decode by hand.

Why does buffering matter, and when do you need to flush? Intermediate

What the interviewer is testing: performance and data-loss awareness.

Each call to FileInputStream.read() can become a system call into the operating system, which is slow compared to memory. A buffered wrapper (BufferedInputStream, BufferedReader, default 8 KB) reads a big block once and hands out small pieces from memory. Reading a file one byte at a time without a buffer can be orders of magnitude slower. For writes it is the same: a BufferedWriter collects data and writes in chunks. The catch: data sitting in the buffer is not yet written. flush() pushes it down to the underlying stream; close() flushes and then closes. If you forget to close a buffered writer, the tail of your file can be silently missing. Note also that flush only passes data to the OS; to force it to disk you need FileChannel.force(true) or FileDescriptor.sync(). Also remember that GZIPOutputStream must be closed (or finish()ed) to write its trailer, or the file is corrupt.

try (var w = new BufferedWriter(new FileWriter("out.txt", StandardCharsets.UTF_8))) {  // Java 11+ ctor
    w.write("hello"); w.newLine();
}   // close() flushes
Explain charsets and encodings. What is the default charset, and why is it a trap? Intermediate

What the interviewer is testing: a classic source of garbled-text production bugs.

A charset is a rule that maps characters to bytes. ASCII uses 1 byte per character and only covers English. ISO-8859-1 uses 1 byte and covers Western European letters. UTF-8 uses 1 to 4 bytes per character and covers all of Unicode, with ASCII as a subset; it is the sensible default for almost everything. UTF-16 uses 2 or 4 bytes. If you write with one charset and read with another, you get garbage such as "Ã©" instead of "é" (called mojibake), or replacement characters. In Java, new String(bytes), getBytes(), FileReader and InputStreamReader(in) without a charset use the platform default. Before Java 18 that depended on the OS (often Cp1252 on Windows and UTF-8 on Linux), so code worked on a laptop and broke on the server. From Java 18 (JEP 400) the default is UTF-8 everywhere, but older runtimes still exist, so pass the charset explicitly. The NIO helpers Files.readString, Files.newBufferedReader and Files.lines always default to UTF-8.

byte[] b = "café".getBytes(StandardCharsets.UTF_8);          // 5 bytes
String wrong = new String(b, StandardCharsets.ISO_8859_1);   // "cafÃ©"  (mojibake)
String ok = new String(b, StandardCharsets.UTF_8);           // "café"
Likely follow-ups
  • What does a decoder do with invalid bytes? InputStreamReader silently replaces them with U+FFFD; Files.readAllLines throws MalformedInputException; a CharsetDecoder can be set to REPORT, REPLACE or IGNORE.
  • What is a BOM? A byte-order mark at the file start (EF BB BF for UTF-8). Java's UTF-8 reader does not strip it, so the first field of a CSV may contain an invisible character.
  • Is String.length() the number of characters? It counts UTF-16 code units; emoji take two. Use codePointCount for real characters.
How do you read a very large file efficiently without running out of memory? Intermediate

What the interviewer is testing: streaming mindset and API knowledge.

Do not read the whole file into memory. Files.readAllBytes, Files.readString and Files.readAllLines load everything (and are limited to about 2 GB because arrays are indexed by int), so they are fine for small config files only. For big files, process line by line with BufferedReader.readLine() or Files.lines(path), which returns a lazy Stream<String> that must be closed. For binary data, read in chunks into a fixed byte array (8 KB to 1 MB) or use a FileChannel with a direct buffer. For random access to a huge file, use a memory-mapped file. Keep your per-record state small, write results out as you go, and avoid accumulating everything in a list. If the work is CPU-heavy, split the file by byte ranges and process ranges in parallel, remembering that lines span ranges. For tabular data at scale, a framework such as Spark is more suitable than hand-written code.

try (Stream<String> lines = Files.lines(path)) {       // lazy, close it
    long errors = lines.filter(l -> l.contains("ERROR")).count();
}

try (InputStream in = Files.newInputStream(path)) {
    byte[] buf = new byte[1 << 16]; int n;
    while ((n = in.read(buf)) != -1) { process(buf, n); }
}
Common mistakes: using readAllLines on a 5 GB log; forgetting to close the stream from Files.lines (it holds a file handle); building one giant String with +=.
What is the best way to copy a stream or a file in modern Java? Basic

What the interviewer is testing: knowing the standard helpers instead of hand-written loops.

For files, Files.copy(source, target, REPLACE_EXISTING) does it, often using native OS copy support. For streams, in.transferTo(out) (Java 9) copies in an internal buffer. in.readAllBytes() (Java 9) is fine for small content. Files.copy(InputStream, Path) writes a stream to a file. Note that Files.copy does not copy a directory's contents, only creates the empty directory; to copy a tree you walk it with Files.walkFileTree. If you copy to a final name while someone reads it, they may see a half file; write to a temporary file in the same directory and then Files.move(tmp, target, ATOMIC_MOVE).

Files.copy(src, dst, StandardCopyOption.REPLACE_EXISTING);
try (var in = socket.getInputStream(); var out = Files.newOutputStream(dst)) { in.transferTo(out); }
Is a Java 8 Stream the same as an InputStream? Basic

What the interviewer is testing: the naming confusion, a frequent warm-up.

No. They are unrelated. java.io.InputStream is a source of bytes that you read and close. java.util.stream.Stream is a pipeline of operations (filter, map, collect) over a sequence of objects, evaluated lazily and usable once. They meet in practice only when a stream wraps a resource: Files.lines, Files.walk and Files.list return a Stream that holds an open file or directory and so must be closed, ideally with try-with-resources. More on streams in Modern Java.

7. NIO, files and paths

What is the difference between java.io.File and java.nio.file.Path/Files? Why prefer NIO.2? Basic

What the interviewer is testing: modern file API knowledge since Java 7.

File is the old API. Its methods often return false on failure instead of telling you why (delete(), mkdir()), it has poor support for symbolic links and file attributes, and it has no good way to walk a tree. Path (an immutable path value) and the Files utility class (Java 7, NIO.2) throw descriptive exceptions such as NoSuchFileException and AccessDeniedException, support copy and move options, atomic moves, attributes, links, directory streams and tree walking, and work with other file systems such as zip files. Convert between them with file.toPath() and path.toFile(). Create paths with Path.of("a", "b") (Java 11) or Paths.get. Useful methods: resolve (join), relativize, normalize (remove ..), toAbsolutePath.

Path p = Path.of("data", "in.csv");
if (Files.notExists(p)) Files.createDirectories(p.getParent());
Files.writeString(p, "a,b\n", StandardCharsets.UTF_8);
try (Stream<Path> s = Files.walk(Path.of("data"))) { s.filter(Files::isRegularFile).forEach(System.out::println); }
Likely follow-ups
  • Difference between Files.list and Files.walk? List is one directory level; walk is recursive. Both need closing.
  • How do you prevent path traversal (../../etc/passwd or zip-slip)? Resolve against the base, normalize, then check startsWith(base) before use.
Explain NIO channels and buffers. How is a ByteBuffer different from a byte array? Senior

What the interviewer is testing: whether you understand the NIO model and the position/limit mechanics.

A channel (FileChannel, SocketChannel) is a connection to something that can do I/O, and it reads and writes through buffers, not streams. A ByteBuffer is a block of memory with three numbers: capacity (its size), position (next index to read or write) and limit (first index you must not touch). To write into it, you call channel.read(buf); to then read what was written, you call flip(), which sets limit to the old position and position to 0. After consuming, clear() (reset all) or compact() (keep unread bytes) prepares for the next write. A buffer can be on the heap (allocate) or direct (allocateDirect, outside the Java heap, which avoids one copy during I/O but is costly to allocate and not freed promptly). Channels can also do transferTo, which lets the OS move data between files or to a socket without going through user space (zero-copy). Buffers are not thread-safe.

try (FileChannel ch = FileChannel.open(path, StandardOpenOption.READ)) {
    ByteBuffer buf = ByteBuffer.allocate(8192);
    while (ch.read(buf) != -1) {
        buf.flip();
        while (buf.hasRemaining()) consume(buf.get());
        buf.clear();
    }
}
Likely follow-ups
  • When is NIO better than classic I/O? For many connections with few threads (selectors), for zero-copy, and for memory mapping. For simple file reads, the plain Files helpers are just as good.
What are selectors and non-blocking I/O, and how do they relate to Netty or Tomcat? Senior

What the interviewer is testing: the model behind scalable servers, at developer level.

In classic blocking I/O, one thread waits on each socket, so 10,000 connections mean 10,000 threads and a lot of memory and switching. With NIO, a channel is set non-blocking and registered with a Selector. One thread asks the selector "which of my channels are ready to read, write or accept?", and handles only those. That is an event loop; the operating system provides the readiness notification (epoll on Linux). Netty and the non-blocking parts of Tomcat, Vert.x and Spring WebFlux are built on this. The trade-off is a more complex programming model (callbacks, never block the event loop), and that CPU-heavy or blocking work must be moved to another thread pool. Since Java 21, virtual threads let you write simple blocking-style code and still handle huge numbers of connections, which reduces the need for hand-written non-blocking code. Details are on the concurrency page.

What is a memory-mapped file, and when would you use one? Senior

What the interviewer is testing: a powerful tool and its sharp edges.

FileChannel.map(mode, position, size) returns a MappedByteBuffer, which asks the OS to map the file into the process address space. You then read and write the file as if it were memory. The OS loads pages on demand and writes dirty pages back, so there is no copy between kernel and Java buffers, and several processes can share the same mapping. It is great for large read-heavy files with random access (indexes, databases, log segments, like Kafka and Lucene do). Limits and costs: one mapping is limited to 2 GB (Integer.MAX_VALUE bytes) because buffers are int-indexed, so large files need several mappings; the mapping is not released when you close the channel, only when the buffer is garbage collected (there is no public unmap before the newer Foreign Function and Memory API, final in Java 22, which has deterministic closing); page faults can cause unpredictable latency; and errors such as a file truncated by another process may cause a JVM-level InternalError instead of a clean exception. For plain sequential reads, a buffered stream is simpler and just as fast.

try (FileChannel ch = FileChannel.open(path, StandardOpenOption.READ)) {
    MappedByteBuffer m = ch.map(FileChannel.MapMode.READ_ONLY, 0, ch.size());  // < 2 GB
    byte first = m.get(0);
}
How does WatchService work and what are its limits? Intermediate

What the interviewer is testing: practical knowledge for hot-reload features.

WatchService (Java 7) tells you when files in a directory are created, modified or deleted. You register a directory with dir.register(watcher, ENTRY_CREATE, ENTRY_MODIFY, ENTRY_DELETE), then loop on watcher.take() (blocks until events arrive), read the events, and call key.reset() to continue receiving. On Linux it uses inotify, so it is efficient. On macOS the JDK implementation has historically used polling with a delay of several seconds. Limits: it watches a single directory, not subfolders, so you register each one yourself; events can be duplicated or come in bursts (editors write several times), so debounce; an OVERFLOW event means you lost some, so rescan the directory; and a file that is still being written may be seen as created before it is complete, so wait until it is stable or have writers move a finished file into place. Network file systems may not give events at all.

try (WatchService ws = FileSystems.getDefault().newWatchService()) {
    dir.register(ws, StandardWatchEventKinds.ENTRY_CREATE);
    for (;;) {
        WatchKey key = ws.take();
        for (WatchEvent<?> ev : key.pollEvents()) handle(dir.resolve((Path) ev.context()));
        if (!key.reset()) break;
    }
}
How do you write a file so readers never see a half-written file? Senior

What the interviewer is testing: durability and consistency thinking.

Write the full content to a temporary file in the same directory (same file system), flush and, if durability matters, force it to disk, and then rename it over the final name with Files.move(tmp, target, ATOMIC_MOVE, REPLACE_EXISTING). A rename within one file system is atomic on common systems, so a reader sees either the old complete file or the new complete file, never a mix. A crash during the write leaves only a stray temp file. Use Files.createTempFile(dir, "x", ".tmp") for the temp name. If you also care about surviving power loss, fsync the temp file before the rename, and on some systems fsync the directory afterward. Not all file systems and options support atomic move across devices; in that case AtomicMoveNotSupportedException is thrown.

What are common file API surprises on Windows versus Linux? Intermediate

What the interviewer is testing: real-world experience with cross-platform code.

On Windows you usually cannot delete or rename a file while some process (including your own JVM, through an unclosed stream) has it open, and you get AccessDeniedException or FileSystemException. On Linux you can delete an open file: the name disappears, and the data lives until the last handle closes (which also means disk space is not freed while a leaked handle exists). Path separators differ, case sensitivity differs, and long paths have limits on older Windows. Use Path instead of string concatenation, never hard code / or \, and use Files.delete (throws) rather than File.delete (returns false). File locks from FileChannel.lock() are advisory on many systems and are per JVM, not per thread.

8. Serialization

How does Java serialization work? What do Serializable, transient and serialVersionUID do? Basic

What the interviewer is testing: the basics, and whether you know the version-compatibility rule.

Java serialization turns an object graph into a byte stream (ObjectOutputStream.writeObject) and rebuilds it later (ObjectInputStream.readObject). A class opts in by implementing the marker interface Serializable, which has no methods. All non-static, non-transient fields are written, and every object they reference must also be serializable, or you get NotSerializableException. A transient field is skipped and comes back as null, 0 or false; static fields are not part of the object, so they are skipped too. serialVersionUID is a version number for the class. When reading, Java compares the number in the stream with the one in the loaded class and throws InvalidClassException if they differ. If you do not declare it, Java computes one from the class structure (fields, methods, modifiers), so even a harmless change like adding a method changes it. Declare it explicitly: private static final long serialVersionUID = 1L;. Change it only when you make an incompatible change on purpose.

Likely follow-ups
  • What if the parent class is not Serializable? Its fields are not saved; on reading, the parent's no-arg constructor runs to initialize them, and it must be accessible, or deserialization fails.
  • Are constructors of a serializable class called on read? No, the constructor of the class itself is skipped; that is one reason it is risky for invariants.
Which class changes are compatible with existing serialized data? Senior

What the interviewer is testing: evolution of persisted data, a real source of outages.

With a fixed serialVersionUID, these are generally compatible: adding a field (old data gives it the default value), removing a field (the data is ignored), adding or removing methods, adding a class to the hierarchy in some cases, and making a field non-transient to transient with care. Incompatible: changing a field's type, moving a class to another package or renaming it (the class name is in the stream), changing the class from Serializable to non-serializable, switching between class and enum, and changing the class hierarchy in certain ways. If you did not fix the id and the compiler-computed one changes, even compatible changes break reading. For long-lived data, plan versioning yourself, or use a format designed for evolution, as the alternatives question below explains.

How do you customize serialization: writeObject, readObject, readResolve, writeReplace? Senior

What the interviewer is testing: knowing the hooks, and why invariants matter.

You can add private methods writeObject(ObjectOutputStream) and readObject(ObjectInputStream). Call defaultWriteObject() or defaultReadObject() first to handle normal fields, then write or read extra data, for example to encode a transient field in a safe form. In readObject you must treat the stream like untrusted input: re-validate invariants and make defensive copies of mutable fields, because deserialization creates an object without running your constructor. readResolve() lets you replace the freshly built object with another, which is how a singleton or an enum-like class stays unique after deserialization. writeReplace() lets you serialize a different object instead. The safest design is the serialization proxy pattern: writeReplace returns a small private nested class holding the logical state, and its readResolve rebuilds the real object through the normal constructor, so all validation runs.

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    if (amount < 0) throw new InvalidObjectException("amount must be >= 0");   // re-validate
    items = List.copyOf(items);                                                  // defensive copy
}
private Object readResolve() { return INSTANCE; }   // singleton stays single
Why is deserializing untrusted data dangerous? How do you protect against it? Senior

What the interviewer is testing: one of the best-known Java vulnerability classes.

readObject will instantiate whatever classes the stream names, and run their readObject methods, before your code gets the chance to check the type. An attacker builds a stream using "gadget" classes already present on the classpath (famous cases used Apache Commons Collections or Spring classes). Chained together, their normal methods run commands or open connections as a side effect of deserializing. The result can be remote code execution, so OWASP lists unsafe deserialization as a top risk. Protection, in order of strength: do not deserialize untrusted bytes at all; use a data-only format (JSON, Protobuf) with a fixed schema; if you must use Java serialization, set an allow-list serialization filter (ObjectInputFilter, Java 9, backported to 8u121; a JVM-wide filter by -Djdk.serialFilter=com.myco.*;!*; context-specific filters in Java 17), limit depth, array size and stream bytes, keep libraries patched, and run with least privilege. Never use enableDefaultTyping style features in JSON mappers on untrusted input, since they bring the same class of problem to Jackson.

What are the alternatives to Java serialization, and when would you choose each? Intermediate

What the interviewer is testing: practical format choice.

Java's built-in format is Java-only, fragile across versions, slow and large compared with others, and a security risk, so Effective Java advises avoiding it. For APIs and config use JSON (Jackson, Gson): human readable, universal, but text-heavy and weakly typed. For service-to-service messages and storage with a schema, use Protocol Buffers, Avro or Thrift: compact binary, explicit schemas, defined rules for adding fields, code generation, and wide language support. Avro is common with Kafka and data pipelines. For in-memory caches that need fast Java object encoding, libraries like Kryo exist, but keep their security and compatibility limits in mind. For Java-to-Java persistence of simple data, a record written as JSON is usually the least trouble. The deciding questions: who reads it (humans or machines), how long must old data stay readable, how big and how fast must it be, and is the source trusted.

How do records and enums behave with Java serialization? Senior

What the interviewer is testing: modern-Java awareness (records are Java 16).

A record can implement Serializable. It is serialized from its components only, and the serialization hooks writeObject, readObject, readObjectNoData and Externalizable are ignored for records. On reading, the stream's component values are passed to the canonical constructor, so your validation in the compact constructor runs, which closes the "object built without invariants" hole that ordinary classes have. The serialVersionUID of a record is 0 unless you declare one, and the check on matching ids is waived by default for records, though declaring it is still good practice. Enums are serialized by name only, and are always deserialized to the same constant, so they are safe singletons; you cannot customize their serialization, and renaming a constant breaks old data. Jackson and other JSON libraries support records natively in recent versions (Jackson 2.12 and later).

What is Externalizable, and how is it different from Serializable? Intermediate

What the interviewer is testing: knowing the rarely-used full-control option and its costs.

Externalizable extends Serializable but gives you complete control: you implement writeExternal(ObjectOutput) and readExternal(ObjectInput) and write exactly the bytes you want, so nothing is saved automatically, not even superclass fields. On reading, Java first calls the class's public no-argument constructor and then readExternal. It can give smaller and faster output than default serialization, and you decide the format, which allows a hand-managed version number. The costs are more code to maintain, the risk of forgetting a field, and the mandatory public constructor. The security issues are the same, since it is still Java object deserialization. Today most teams pick a schema-based format instead.

What happens to static, transient and final fields in serialization, and what about a field that references a non-serializable object? Basic

What the interviewer is testing: quick, exact rules.

Static fields belong to the class and are not written. Transient fields are skipped on purpose and get the default value on reading (so a transient final field cannot be re-set after deserialization without tricks). Use transient for things that should not travel: caches, open resources, threads, and secrets like passwords. A non-transient field whose object is not serializable (a Thread, a Connection, a logger instance) throws NotSerializableException at write time. Fix it by making the field transient and rebuilding it in readObject or lazily, or by redesigning so the object does not hold such a reference. Also remember that serialization writes an object graph: one reference can drag in a huge structure, including an entire Spring context if you are careless.

9. JSON and Jackson essentials

How should you use and configure ObjectMapper? Intermediate

What the interviewer is testing: real project usage, including a common performance mistake.

ObjectMapper is thread-safe once configured, and it is expensive to create because it builds caches of serializers and deserializers. So create one, configure it at start-up, and reuse it (in Spring, inject the one Spring Boot gives you). Do not create a new mapper per request, and do not change its configuration after it is in use. Typical settings: register JavaTimeModule (the jsr310 module) for java.time types; disable WRITE_DATES_AS_TIMESTAMPS so dates are ISO-8601 strings; decide on FAIL_ON_UNKNOWN_PROPERTIES; set setSerializationInclusion(NON_NULL) if you want to omit nulls; and consider ParameterNamesModule for constructor binding. Use ObjectReader/ObjectWriter for per-call variations. This page describes the Jackson 2.x line (com.fasterxml.jackson); Jackson 3 moves to new package names, so check the version in your project.

ObjectMapper mapper = JsonMapper.builder()
    .addModule(new JavaTimeModule())
    .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
    .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
    .build();
List<User> users = mapper.readValue(json, new TypeReference<List<User>>() {});
What happens with unknown JSON properties, and what is your policy? Intermediate

What the interviewer is testing: API compatibility thinking.

By default plain Jackson fails with UnrecognizedPropertyException when the JSON has a field your class does not know (FAIL_ON_UNKNOWN_PROPERTIES is true). Spring Boot's auto-configured mapper turns it off, so the same code behaves differently in a Boot app and in a unit test with a plain mapper, which surprises people. For reading data from other systems, tolerate unknown fields (@JsonIgnoreProperties(ignoreUnknown = true) or the global switch), because a producer adding a field should not break all consumers. This is the "tolerant reader" idea. For input you want strict validation on, such as a public API payload where typos must be caught, keep it on. Also decide how to handle unknown enum values (READ_UNKNOWN_ENUM_VALUES_AS_NULL or a default via @JsonEnumDefaultValue), missing fields (they become null or default), and nulls versus absent fields.

How do you handle polymorphic JSON (an interface or base class with several subtypes)? Senior

What the interviewer is testing: a standard hard case, and its security side.

JSON has no type information, so you add a discriminator field. With @JsonTypeInfo(use = NAME, property = "type") and @JsonSubTypes on the base type, Jackson writes "type":"card" and reads it back to the right subclass. Use logical names, listed explicitly, as in the example. Do not use use = CLASS or global default typing with untrusted input: they let the sender pick any class name to instantiate, which has produced many remote-code-execution CVEs in the same family as Java deserialization. Java 17 sealed interfaces fit nicely, because the permitted subtypes are the exact list you would put in @JsonSubTypes.

@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
    @JsonSubTypes.Type(value = CardPayment.class, name = "card"),
    @JsonSubTypes.Type(value = UpiPayment.class,  name = "upi")})
public sealed interface Payment permits CardPayment, UpiPayment {}
How do you handle dates and times in JSON? Intermediate

What the interviewer is testing: a field where bugs are common.

Without the jsr310 module, Jackson 2 refuses or mishandles java.time types (LocalDate, Instant). With JavaTimeModule registered, dates are written as numbers by default; disable WRITE_DATES_AS_TIMESTAMPS to get ISO-8601 text such as 2026-11-17T10:15:30Z. Use Instant or OffsetDateTime (a point in time with UTC offset) for events and API timestamps, and LocalDate only for calendar dates without time zone, like a birthday. Avoid the legacy Date and SimpleDateFormat (not thread-safe). Always make the time zone explicit; sending a local time without zone is the root of many bugs. Use @JsonFormat on one field when a specific pattern is required by a contract.

Does Jackson work with records and immutable classes? What about generics? Intermediate

What the interviewer is testing: modern data classes and known pitfalls.

Records are supported from Jackson 2.12, using the canonical constructor, so no annotations are needed in the simple case. For ordinary immutable classes you need to tell Jackson how to construct them: annotate a constructor with @JsonCreator and parameters with @JsonProperty, or compile with -parameters and register ParameterNamesModule. Lombok @Value and builders need @Jacksonized or similar. For generic types, pass a TypeReference (see the type token question), because of erasure; otherwise the elements come back as LinkedHashMap, and a ClassCastException follows later when your code treats them as your type. Also remember that numbers into Object fields become Integer, Long or Double by size, and money should use BigDecimal (consider USE_BIG_DECIMAL_FOR_FLOATS).

10. Networking basics

How do Socket and ServerSocket work, and what timeouts must you set? Intermediate

What the interviewer is testing: low-level networking and the "no default timeout" trap.

A ServerSocket listens on a port; accept() blocks until a client connects and returns a Socket for that connection. A client creates new Socket(host, port). Both ends read and write bytes using getInputStream() and getOutputStream(); TCP is a byte stream with no message boundaries, so you must frame messages yourself (length prefix or delimiter), and one write may arrive as several reads. By default the connect and read operations can block forever. Always set a connect timeout (socket.connect(addr, ms)) and a read timeout (setSoTimeout(ms)), which makes a stalled read throw SocketTimeoutException. Thread-per-connection is simple but does not scale to very many connections; pool the threads, or use NIO or virtual threads (Java 21). Always close sockets in try-with-resources.

try (Socket s = new Socket()) {
    s.connect(new InetSocketAddress(host, 8080), 2_000);   // connect timeout
    s.setSoTimeout(5_000);                                  // read timeout
    s.getOutputStream().write(request);
}
HttpURLConnection versus java.net.http.HttpClient: which do you use and why? Intermediate

What the interviewer is testing: modern JDK knowledge (Java 11).

HttpURLConnection is the old API from the 1990s: mutable, awkward, no HTTP/2, no asynchronous mode, and unclear behaviour around errors and streams (you must read the error stream yourself on a 4xx). HttpClient (standard in Java 11) has a builder, immutable clients and requests, HTTP/2 with fallback to HTTP/1.1, WebSocket support, proxy and redirect settings, and both send (blocking) and sendAsync (returns a CompletableFuture). Create one client and reuse it, because it holds a connection pool and thread resources. Set the connectTimeout on the client and a timeout on each request. Remember it does not throw on 404 or 500: you check response.statusCode() yourself. In real apps people usually use higher-level clients (Spring RestClient/WebClient, OkHttp, Feign) on top, which add serialization, retries and metrics.

HttpClient client = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com/users/1"))
    .timeout(Duration.ofSeconds(5)).header("Accept", "application/json").GET().build();
HttpResponse<String> res = client.send(req, HttpResponse.BodyHandlers.ofString());
if (res.statusCode() != 200) throw new IllegalStateException("HTTP " + res.statusCode());
What network failures should a Java client expect, and how do the exceptions differ? Senior

What the interviewer is testing: diagnosing production network problems.

UnknownHostException means DNS failed. ConnectException: Connection refused means the host answered but nothing listens on that port. SocketTimeoutException: connect timed out means no answer in time (firewall drop, host down); Read timed out means the connection was made but the server was too slow to reply. SocketException: Connection reset means the peer closed abruptly, often an idle connection killed by a load balancer or a server restart, and a pooled connection may have gone stale. SSLHandshakeException points to certificate or protocol problems, such as a missing CA in the truststore (PKIX path building failed). Timeouts and resets are usually transient and can be retried only if the operation is idempotent. Another common issue: the JVM caches DNS results for a while (networkaddress.cache.ttl), which matters when addresses change behind a name.

11. Reflection, annotations and dynamic proxies

What is reflection, what is it used for, and what does it cost? Intermediate

What the interviewer is testing: how frameworks work, and trade-off awareness.

Reflection lets code inspect and use classes at runtime without knowing them at compile time: list fields and methods (getDeclaredMethods), read annotations, create objects (getDeclaredConstructor().newInstance()), call methods (Method.invoke) and read or write fields, even private ones after setAccessible(true). Frameworks live on it: Spring injects dependencies and creates beans, Jackson maps JSON to fields, Hibernate maps entities, JUnit finds @Test methods. Costs: slower than a direct call (lookups, boxing of arguments, access checks, hard for the JIT to inline), though modern JVMs reduced the gap (since JDK 18 method invocation uses method handles internally); no compile-time safety, so typos in a method name fail at runtime; harder refactoring and tooling; and weaker security and encapsulation. Since Java 9 the module system, and strongly from Java 16 and 17, blocks deep reflection into JDK internals unless you pass --add-opens. GraalVM native images need reflection use declared in advance. Practical rule: cache the Method or Field objects, do lookups once at start-up, and prefer plain code or MethodHandle when speed matters.

Class<?> c = Class.forName("com.acme.Handler");
Object h = c.getDeclaredConstructor().newInstance();
Method m = c.getMethod("handle", String.class);
Object result = m.invoke(h, "hello");     // InvocationTargetException wraps what the method throws
Likely follow-ups
  • What does InvocationTargetException mean? The invoked method itself threw; the real exception is getCause(). Unwrap it.
  • Does reflection break singletons? It can call a private constructor; an enum singleton is protected from this.
How do annotations work? What are retention policies, and who reads them? Intermediate

What the interviewer is testing: the key idea that an annotation does nothing by itself.

An annotation is metadata attached to code. It has no behavior. Something else must read it. @Retention says how long it survives: SOURCE (compiler only, like @Override), CLASS (kept in the class file but not loaded at runtime, the default), or RUNTIME (readable by reflection, which is what Spring's @Service or JUnit's @Test need). @Target says where it can be used. There are two ways it gets processed. At compile time, annotation processors (Lombok, MapStruct, Dagger, Immutables) read source annotations and generate code, so there is no runtime cost and the tooling sees the result. At runtime, a framework scans classes, reads annotations with reflection, and acts: builds beans, wraps methods in proxies, binds JSON. Runtime scanning has a startup cost, which is one reason frameworks add ahead-of-time processing (Spring AOT, Quarkus, Micronaut) for fast startup and native images.

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD)
public @interface Timed { String value() default ""; }

for (Method m : bean.getClass().getDeclaredMethods())
    if (m.isAnnotationPresent(Timed.class)) register(bean, m);
What is a dynamic proxy and how do Spring AOP and @Transactional use it? Senior

What the interviewer is testing: the mechanism behind many "magic" annotations, and its limits.

A JDK dynamic proxy (java.lang.reflect.Proxy.newProxyInstance) builds, at runtime, a class that implements the interfaces you give it. Every method call on it is routed to one InvocationHandler.invoke(proxy, method, args). In the handler you can run code before and after, then call the real object with method.invoke(target, args). That is how transactions, security checks, caching and metrics are added without touching business code. JDK proxies need an interface. For classes without one, Spring uses a subclass generated by CGLIB or ByteBuddy (the class cannot be final, and its methods cannot be final or private). Consequences you must know: a call from one method to another on this (self-invocation) does not pass through the proxy, so @Transactional or @Cacheable on the inner method is ignored; only public methods called from outside are advised; and checked exceptions not declared by the interface get wrapped in UndeclaredThrowableException.

Why do you sometimes see InvocationTargetException or UndeclaredThrowableException in a trace? Senior

What the interviewer is testing: unwrapping exceptions correctly in framework-style code.

When you call Method.invoke and the target method throws, reflection wraps the exception in InvocationTargetException and you must call getCause() to get the real one; catching only the wrapper and logging getMessage() gives you a useless null. A dynamic proxy's handler can throw only unchecked exceptions or the checked ones the interface method declares. If it throws some other checked exception, the proxy wraps it in UndeclaredThrowableException. A typical handler therefore catches InvocationTargetException, rethrows e.getCause(), so callers see the original type. The same wrapping idea applies to ExecutionException from futures and CompletionException from CompletableFuture: unwrap before deciding what to do.

try { return method.invoke(target, args); }
catch (InvocationTargetException e) { throw e.getCause(); }   // keep the original type
MethodHandle versus reflection: when do you choose which? Senior

What the interviewer is testing: awareness of faster alternatives.

A MethodHandle (Java 7) is a typed, directly executable reference to a method, field or constructor. Access is checked when you look it up, not on each call, and if the handle is held in a static final field the JIT can inline the call almost like a direct call. A Method from reflection always does access checks and boxing of arguments, so it is slower in tight loops. The price is a harder API (MethodHandles.lookup().findVirtual(...), and signature-polymorphic invokeExact). Frameworks use handles or generated bytecode in hot paths. For most application code the difference does not matter: reflection called a few thousand times at start-up is fine, and the rule is to avoid it in per-request inner loops, and to cache lookups.

12. Java logging

What are SLF4J, Logback and Log4j2, and how do they relate? Basic

What the interviewer is testing: facade versus implementation.

SLF4J is a facade: an API (Logger, LoggerFactory) that your code compiles against. It does no logging itself. At runtime a binding routes the calls to a real implementation: Logback (the default in Spring Boot, the native SLF4J implementation), Log4j2, or the JDK's java.util.logging. This lets libraries log through SLF4J without forcing a choice on the application. Rules of thumb: have exactly one implementation on the classpath (two bindings give a warning and an arbitrary choice), bridge other APIs (jul-to-slf4j, log4j-over-slf4j) so everything ends in one place, and create the logger as private static final Logger log = LoggerFactory.getLogger(MyClass.class). The implementation is configured by logback.xml or log4j2.xml: appenders (console, file, JSON), layouts and per-package levels.

What do the log levels mean, and what should go at each level? Basic

What the interviewer is testing: judgement, which protects on-call engineers from noise.

ERROR: an operation failed and someone may need to act, a real bug or a lost request. WARN: something unexpected happened, but the system handled it, such as a retry that succeeded or a deprecated call. INFO: important business or lifecycle events at low volume, such as service started, job finished with a count. DEBUG: details for developers, off in production by default. TRACE: very fine detail. Do not log a user mistake (bad input) as ERROR, or alerts become noise; and do not log a real failure as INFO, or you will not find it. Production is typically INFO for your code and WARN for noisy libraries, and levels can be changed at runtime to debug one package without a restart.

Why use parameterized logging instead of string concatenation? How do you log an exception properly? Basic

What the interviewer is testing: a basic performance and correctness habit.

With log.debug("user " + id + " loaded " + user), the string is built every time, even if DEBUG is off, and user.toString() is called for nothing. With log.debug("user {} loaded {}", id, user) SLF4J only formats the message if the level is enabled, so a disabled debug call costs almost nothing. If building an argument is itself costly, guard it with if (log.isDebugEnabled()) or use the SLF4J 2 fluent API with a lambda: log.atDebug().addArgument(() -> expensive()).log("x {}"). For exceptions, pass the exception as the last argument with no placeholder: log.error("cannot save order {}", id, e) prints the message and the full stack with causes. Writing log.error(e.getMessage()) or "..." + e drops the stack trace.

log.info("order {} created for customer {}", orderId, customerId);
log.error("payment failed for order {}", orderId, ex);     // ex last: full stack trace
What is MDC and how do you use it for tracing a request? What breaks it? Intermediate

What the interviewer is testing: practical observability.

MDC (Mapped Diagnostic Context) is a per-thread map of key and value pairs that the logging layout adds to every log line, using a pattern such as %X{traceId}. A servlet filter or interceptor puts traceId, userId or tenantId at the start of a request and removes them in a finally block at the end. Then every line from that request, in any class, carries the id, so you can search one request across a log of thousands. The weak point: MDC is stored in a ThreadLocal, so when work moves to another thread (an executor, CompletableFuture.supplyAsync, reactive pipelines) the values are not there. Fix by copying the map into the task when you submit it and setting it again inside, or by using a wrapping executor or the tracing library's context propagation. And always clear MDC in a finally block: pool threads are reused, and a stale value would label the next request with the wrong id, which is both confusing and a data-leak risk.

MDC.put("traceId", traceId);
try { chain.doFilter(req, res); }
finally { MDC.clear(); }

Map<String,String> ctx = MDC.getCopyOfContextMap();
executor.submit(() -> { MDC.setContextMap(ctx); try { work(); } finally { MDC.clear(); } });
What should you never log, and how do you keep logs safe and useful? Intermediate

What the interviewer is testing: security and privacy awareness.

Never log passwords, API keys, tokens, session ids, full card numbers, or personal data that rules like GDPR protect, such as full email, phone or national id. Be careful with toString() of request or entity objects and with logging whole HTTP headers (the Authorization header) or whole request bodies. Mask or hash sensitive fields, and exclude them from toString. Also beware of log injection: user input containing newlines can forge fake log lines, so sanitize or use a structured JSON layout that escapes it. Keep logs useful: one event per line, include ids (order id, trace id) instead of dumping objects, write structured JSON in production so a log platform can query fields, and never log inside tight loops or per-record at INFO. Logs are also stored for long periods and read by many people, so treat them as data you must protect.

How does logging affect performance, and what do async appenders do? Senior

What the interviewer is testing: knowing logging is I/O on your request path.

Each enabled log call formats a message, takes a lock or queue, and writes to a file or console, which is I/O. Under heavy load, synchronous logging on the request thread can add latency, and a slow disk or a blocked stdout pipe (a full container log buffer) can stall the whole app. An async appender puts events on a queue and a background thread writes them, so request threads pay only for the enqueue. Trade-offs: if the queue is full you must choose between blocking and dropping (Logback's AsyncAppender can discard lower-level events when the queue is above a threshold), and after a crash the last events in memory can be lost. Log4j2's async loggers use a lock-free ring buffer and are faster. Keep the volume under control: avoid DEBUG in production by default, avoid per-item INFO logs, and avoid expensive argument computing. Include %caller-style location info only when needed, because it needs a stack walk.

How do you log exceptions in a way that makes incidents quick to debug? Intermediate

What the interviewer is testing: operational empathy for the person reading your logs.

Log it once, at the place that handles it, with the whole exception object so you get the stack and causes. Include the identifying context in the message: tenant, order id, operation name, and the correlation id (MDC adds it). Say what you were trying to do ("cannot send invoice for order 17"), not only what broke. Choose the level by impact: user errors at WARN or INFO (or not at all), system failures at ERROR. Avoid multi-line free-text messages; keep each event parseable. For very frequent repeated errors, limit the rate (log the first, then a count per minute), since a retry loop can write millions of identical stacks and fill the disk, which turns one failure into an outage. Also expose metrics (error counters) so alerts do not depend on grepping logs.

13. Resources and cleanup

AutoCloseable versus Closeable, and how do you write a good close()? Intermediate

What the interviewer is testing: API contract details.

AutoCloseable (Java 7) is the interface that try-with-resources needs: one method close() throws Exception. Closeable (older, in java.io) extends it, narrows the exception to IOException, and promises that calling close() twice is harmless. A good close(): make it idempotent (safe to call twice), release resources in reverse order of acquisition, do not hide failures but do not let one failed release stop the others from being released, and avoid throwing from it when you can. Do not declare throws Exception in your own implementation if you throw nothing, so callers are not forced to catch it. Document whether close also closes the objects it wraps. For InterruptedException, the docs of AutoCloseable advise that a close which may throw it should be designed with care, since it can be suppressed.

public final class Conn implements AutoCloseable {
    private boolean closed;
    @Override public void close() {          // no checked exception, idempotent
        if (closed) return;
        closed = true;
        release();
    }
}
Why is finalize() discouraged, and what are Cleaner and PhantomReference? Senior

What the interviewer is testing: why you should not rely on the garbage collector to close things.

finalize() runs at an unpredictable time, maybe never, on a special finalizer thread. It slows garbage collection, keeps objects alive longer, can resurrect the object, hides exceptions, and has been a security risk. It is deprecated since Java 9 and deprecated for removal since Java 18 (JEP 421). The replacement for a safety net is java.lang.ref.Cleaner (Java 9): you register an object along with a cleanup action, and when the object becomes unreachable, the action runs on a cleaner thread. The action must not capture the object itself (or it never becomes unreachable). Internally it uses PhantomReferences, which are enqueued after the object is collected and do not give access to it. Even so, a Cleaner is only a backstop for leaks, not a plan: it gives no timing guarantees. The real design is an AutoCloseable used in try-with-resources, with the Cleaner as a last-resort safety net for native memory or handles. Do not rely on a GC to release scarce things like file descriptors, since a large heap may go a long time without a collection while handles run out.

How do you find and prevent file handle or connection leaks? Senior

What the interviewer is testing: debugging a very common production failure ("Too many open files").

Symptoms: java.io.IOException: Too many open files, pool exhaustion messages ("Timeout waiting for connection from pool"), and slowly growing latency. To find it: on Linux count handles with ls /proc/<pid>/fd | wc -l or lsof -p, and see which targets repeat (the same file or remote host); take a thread dump to see threads waiting on the pool; and enable your pool's leak detection (HikariCP leakDetectionThreshold logs a stack of the code that borrowed the connection and did not return it). Typical causes: a missing close on an early-return or exception path, a Files.lines or Files.list stream not closed, an HTTP response body not consumed, or a stream stored in a field. Prevention: try-with-resources everywhere, wrap resources in small methods that own the whole lifecycle, static analysis (SpotBugs, Sonar rules for resource leaks), a sensible ulimit, and monitoring of open descriptors.

How do you shut down an application cleanly so resources are released? Intermediate

What the interviewer is testing: lifecycle thinking beyond a single try block.

On SIGTERM the JVM starts shutdown and runs all registered shutdown hooks (Runtime.getRuntime().addShutdownHook) in parallel, then exits. A kill -9 gives no chance. Frameworks wire it for you: Spring closes the context in order (@PreDestroy, DisposableBean, close() on beans), and Spring Boot offers graceful shutdown to finish in-flight requests. For your own executors, call shutdown(), wait with awaitTermination(timeout), and if tasks do not finish call shutdownNow(), which interrupts them, so tasks must handle interruption properly. In hooks do fast, idempotent work with a time limit, because hooks run while the app is half stopped and objects they need may already be closed. Do not call System.exit from a hook (it deadlocks). Tie this to your platform's grace period, such as Kubernetes terminationGracePeriodSeconds.

14. Real-life scenarios

Each scenario is answered the same way: the situation, what you check first, the fix, and how you prevent it next time.

Orders silently stop being saved. The logs show nothing wrong. A teammate finds an empty catch block. What do you do? Intermediate

What the interviewer is testing: a calm approach to a swallowed exception.

Situation: a save method catches Exception, does nothing, and returns. The caller thinks the order was saved. Support tickets arrive days later. First check: reproduce with a failing input and temporarily log at the catch; look at the data (missing rows) and the time the first one went missing, and compare with the deploy that introduced the catch (version control blame). Fix: remove the empty catch. Catch only the exceptions you can handle; for the rest, translate and rethrow with the cause, or let them travel up to the global handler that logs once and returns a 5xx. Reprocess the missed orders from the source data. Prevent: code review rule against empty catch, static analysis (SpotBugs, Sonar "empty catch"), a metric on save failures with an alert, and a test that proves a failing repository results in a failure response.

// before
try { repo.save(order); } catch (Exception e) { }
// after
try { repo.save(order); }
catch (DataAccessException e) { throw new OrderStoreException("cannot save order " + order.id(), e); }
After a few hours the service fails with "Too many open files" and "Timeout waiting for connection from pool". How do you investigate? Senior

What the interviewer is testing: a structured leak hunt.

Situation: the error appears only under load or after hours, and a restart "fixes" it for a while, which suggests a leak. First check: count open descriptors for the process (ls /proc/PID/fd | wc -l) over time and see whether they grow; group by target with lsof -p PID to see if they are files, sockets to one host, or database connections. Take a thread dump to see threads blocked waiting for the pool. Turn on pool leak detection (HikariCP leakDetectionThreshold), which prints the stack of the code that borrowed a connection and never returned it. Fix: usually a path that does not close: an early return or an exception before close(), a Files.lines stream, or an HTTP body that was not consumed. Convert to try-with-resources. Prevent: try-with-resources by rule, lint rules for resource leaks, a dashboard for open file descriptors and pool usage, and a load test that runs long enough to show slow leaks.

An error in processing never shows up, and the method returns a normal-looking result. The code has return in a finally block. What happened? Intermediate

What the interviewer is testing: the finally-overrides-exception trap in a real context.

Situation: the method wrote to a file in try, and in finally it did return status (or threw from close() in a hand-written finally). Exceptions from try were discarded. First check: read the method for any return, break or throw inside finally, and run a test that makes the try block throw. Fix: remove the return from finally; put the return after the try statement; move cleanup into try-with-resources so that close errors become suppressed exceptions on the primary one. If you must handle two failures in manual cleanup, catch the second one and add it with addSuppressed. Prevent: enable compiler lint -Xlint:finally (it warns when finally cannot complete normally), static analysis, and a unit test where the body throws.

Customer names with accents show as "Ã©" after a release to Linux, though they looked fine on laptops. Why, and how do you fix it? Intermediate

What the interviewer is testing: charset awareness in a real defect.

Situation: a CSV written on a Windows laptop (default Cp1252) is read on a Linux server whose default is UTF-8, or the other way. The bytes are right; the decoding is wrong. First check: look at the raw bytes with a hex tool (xxd): "é" as C3 A9 means UTF-8; E9 means ISO-8859-1 or Cp1252. Check the code for new String(bytes), getBytes(), FileReader and InputStreamReader without a charset, and the JVM property file.encoding. Also check the database connection charset and HTTP header Content-Type: charset. Fix: pass StandardCharsets.UTF_8 everywhere; agree the encoding as part of the file or API contract; repair already-corrupted data by re-decoding (new String(s.getBytes(ISO_8859_1), UTF_8)) if it was misdecoded exactly once. Prevent: a lint or Sonar rule banning charset-less overloads, run tests with a non-UTF-8 default (-Dfile.encoding=Cp1252 on older JDKs), and use Java 18 or newer where UTF-8 is the default.

A nightly import job fails with OutOfMemoryError on a 4 GB file, although it worked on small test files. What is wrong? Intermediate

What the interviewer is testing: streaming versus loading.

Situation: the code does Files.readAllLines or reads the file into one String, then parses into a list of objects. A 4 GB file needs far more than 4 GB of heap, because Java strings and objects have overhead (a Latin text string may take 1 to 2 times its size, objects add headers and pointers). First check: the heap dump or GC log (-XX:+HeapDumpOnOutOfMemoryError) shows one huge array or list as the largest object. Fix: stream: BufferedReader.readLine() in a loop (or Files.lines in try-with-resources), process each record, and write results in batches (for databases, JDBC batches of 500 to 5000 rows, committing per batch). Keep memory use constant regardless of file size. If you need sorting or grouping, use external sort or load in a database. Prevent: a test with a generated large file, a memory limit in CI for the job, and a code rule that bulk reads are only for known-small files.

A ClassCastException is thrown on a line that does String s = list.get(0), where list is a List<String>. How is that possible? Senior

What the interviewer is testing: heap pollution in practice.

Situation: the trace says "Integer cannot be cast to String" at a line that looks type-safe. The compiler inserted the cast at that read; the wrong object was put in earlier through an unchecked path. First check: find who creates or fills the list: search for raw types, unchecked casts, (List) something, reflection, legacy code, a JSON mapper that was given List.class and returned maps, or a generic varargs method. Compile with -Xlint:unchecked and read the warnings in those files. Fix: correct the producer: pass a TypeReference to Jackson, remove raw types, validate elements at the boundary (Collections.checkedList to catch the bad insert at its source, in tests). Prevent: treat unchecked warnings as errors in new code (-Werror with lint), keep @SuppressWarnings("unchecked") on the smallest scope with a comment, and avoid raw types at API boundaries.

A security scan flags an endpoint that reads a Java-serialized object from a cookie. How serious is it and what do you do? Senior

What the interviewer is testing: a clear risk assessment and remediation plan.

Situation: the server calls ObjectInputStream.readObject() on bytes the client controls. This is critical: with a gadget class on the classpath, an attacker can run commands on the server. First check: confirm the data path (is it authenticated, signed, or encrypted with a key the client does not know?), list the libraries on the classpath that are known to have gadget chains, and check the logs for odd class names in exceptions such as InvalidClassException, which can hint at probing. Immediate step: put a strict ObjectInputFilter allow-list in front (or block the endpoint) and patch vulnerable libraries. Real fix: stop using Java serialization for client-supplied data: keep session state on the server, or send JSON with an explicit schema, signed with an HMAC (verify the signature before parsing). Prevent: a dependency scan, a ban on readObject for external input in code review, and a security test for it. Rotate any secrets the host held if exploitation is possible.

After a deploy, reading cached or persisted objects fails with InvalidClassException "local class incompatible". What happened? Intermediate

What the interviewer is testing: serialVersionUID in a real outage.

Situation: Redis or session store holds objects written by the old version; the new version has a different class structure. No explicit serialVersionUID existed, so the computed one changed when someone added a field or method. The message shows "stream classdesc serialVersionUID = X, local class serialVersionUID = Y". First check: confirm the diff of that class between versions, and whether old and new nodes run together during a rolling deploy (so they read each other's data). Quick fix: if the change was compatible, set the explicit serialVersionUID equal to the old value (from the error message) so that old data reads again; otherwise flush the cache or sessions, accepting a one-time miss. Prevent: declare serialVersionUID on every serializable class (compiler lint -Xlint:serial), keep serialization-sensitive classes stable, version cache keys by app version, and prefer a schema-based or JSON format for data that outlives a deploy.

The disk fills up at 3 a.m. because a log file grew by tens of gigabytes in an hour. What do you do? Senior

What the interviewer is testing: handling a log flood, and the root causes behind it.

Situation: the same error repeats thousands of times per second, each with a long stack trace, usually inside a retry loop or a message consumer that fails and immediately re-reads the same message. First check: find the top repeated message (sort | uniq -c | sort -rn | head over a sample), see the first occurrence time and the deploy or dependency outage that started it. Immediate steps: stop the bleeding: free disk (truncate or compress the rotated files, do not delete a file the app holds open, truncate it instead), raise the log level of the noisy logger at runtime, or stop the loop (pause the consumer). Root fix: add backoff to the retry, move poison messages to a dead-letter queue, log once per interval with a count, and do not log full stacks for known expected failures. Prevent: log rotation with size and total caps (Logback SizeAndTimeBasedRollingPolicy with totalSizeCap), shipping logs off-box, alerts on log volume and disk, and async appenders with bounded queues.

A background job "ran fine" in the pool but half the records were never processed, and nothing is in the logs. Why? Senior

What the interviewer is testing: the lost-exception behavior of executors.

Situation: tasks were submitted with executor.submit(...) and the returned Future was ignored, so exceptions were stored and never read. First check: search the code for submit( calls whose result is dropped; reproduce with a task that throws and confirm that no log appears; check whether the pool silently replaced dead workers (with execute, the default handler writes only to stderr, which your log collector may not capture). Fix: catch Throwable inside the task and log with the record id, or collect the Futures and call get() (or use invokeAll or CompletableFuture with handle), and count failures; make the job report "processed X, failed Y" and fail loudly if Y is above zero. Prevent: a wrapper executor that logs every failure, an uncaught exception handler set in the ThreadFactory, and reconciliation checks (input count equals output count).

Logs show thousands of "NoClassDefFoundError: Could not initialize class X" after a deploy. Where is the real error? Senior

What the interviewer is testing: the two-stage static init failure.

Situation: the class has a static initializer or a static field that threw during the first use, giving one ExceptionInInitializerError. Every later use only says "Could not initialize class". First check: search the logs from the deploy start for ExceptionInInitializerError (it appears once, may be on a different thread, and may have been rotated). Its "Caused by" is the real problem, often a missing config value, a failed connection or parse of a resource file, or a wrong environment variable. If the first error is lost, restart with the same config and watch start-up. Fix: fix the cause, then restart, because that class cannot be reinitialized in the same classloader. Prevent: do not put risky work in static initializers; load config in an explicit start-up phase that fails fast with a clear message; add a smoke test that touches the key classes at start-up; keep early log lines available on rollouts.

A partner added one new field to their JSON and your service started returning 500 for all their requests. What happened and how do you fix it? Intermediate

What the interviewer is testing: tolerant reader and API evolution.

Situation: the logs show UnrecognizedPropertyException: Unrecognized field "x". A plain ObjectMapper (default fail-on-unknown true) is in use, for instance one created by hand in a client class instead of the Spring-managed one. First check: find where that mapper is built; compare with the Boot-configured mapper that disables the check. Fix: make the consumer tolerant: @JsonIgnoreProperties(ignoreUnknown = true) on the DTOs or disable FAIL_ON_UNKNOWN_PROPERTIES on that mapper; deploy; ask the partner to publish a change policy (adding optional fields is allowed). Prevent: one shared mapper bean configured centrally, contract tests that include an extra unknown field, and a rule: be strict on what you send, tolerant on what you receive. Return a 400, not a 500, when payloads really are invalid.

A method failed halfway, but part of the data was committed anyway even though it has @Transactional. Why? Senior

What the interviewer is testing: how exception handling interacts with proxies and transactions.

Situation: three common causes. One: the method threw a checked exception, and by default Spring commits for checked exceptions. Two: the method caught the exception inside itself, so the proxy saw a normal return. Three: the transactional method was called from another method in the same class, so the proxy was bypassed and there was no transaction at all. A fourth: a private or final method, or the call came from a non-Spring-managed object. First check: turn on logging.level.org.springframework.transaction=DEBUG to see whether a transaction began and whether it rolled back; read the code for the three patterns. Fix: use rollbackFor for checked exceptions, rethrow after logging, and move the inner method to another bean (or inject the proxy). Prevent: tests that assert nothing is persisted after a forced failure (an integration test with a real database).

Logs for one request show another user's trace id. How can that happen, and why is it a security problem? Senior

What the interviewer is testing: ThreadLocal reuse and context leakage.

Situation: the filter puts traceId in the MDC on request start but does not clear it on every exit path. Pool threads are reused, so the next request on that thread carries the old values until it overwrites them, and some paths (an async task, an early return) never do. Also, work passed to another pool without copying MDC shows no id or a stale one. Beyond confusion, tenant or user ids in logs under the wrong request can mislead an investigation or leak data between tenants. First check: look at the filter or interceptor: is MDC.clear() in a finally block? Find executors used in the request path. Fix: clear in finally; wrap executors to copy and then restore context; for reactive code use the library's context propagation. Prevent: shared wrappers for executors, a test that runs two requests on one thread and checks the second sees only its own values.

The whole service hangs at peak: all request threads are stuck in a call to a partner API. What is the likely cause and fix? Senior

What the interviewer is testing: timeouts as a design requirement.

Situation: the partner became slow, not down. The HTTP client had no read timeout (sockets and HttpURLConnection default to waiting forever), so each request thread blocked, the server pool filled, and every endpoint, even those not using the partner, stopped responding. First check: a thread dump shows many threads in SocketInputStream.read or sun.nio.ch read methods in your client code; check client settings for connect and read timeouts. Fix: set a connect timeout (1 to 3 seconds) and a request timeout based on the partner's real latency; limit concurrent calls with a bulkhead (a separate small pool or semaphore); add a circuit breaker and a fallback; retry only idempotent calls with backoff. Prevent: a code rule that every outbound call has explicit timeouts, dashboards for outbound latency per dependency, and a fault-injection test with a slow stub.

A scheduled cleanup job ran for weeks and then simply stopped running, with no error in the logs. What happened? Senior

What the interviewer is testing: the documented behavior of periodic tasks.

Situation: the job uses ScheduledExecutorService.scheduleAtFixedRate (or scheduleWithFixedDelay). If one run throws an exception that escapes the task, all further executions are suppressed, and the exception is stored in the returned ScheduledFuture, which nobody reads. First check: confirm that the task has no try/catch around the body, and look for the first failure time (a database blip, a null pointer) around when the job stopped. A thread dump will show no scheduler activity for that job. Fix: wrap the whole body in try { ... } catch (Throwable t) { log.error(...) }, so one bad run does not cancel the schedule; then restart the job. If you use Spring @Scheduled, the framework logs and continues, but check your error handler anyway. Prevent: a heartbeat metric (last successful run time) with an alert if it is older than two intervals.

A downstream system sometimes picks up half-written files from your export folder. How do you stop that? Intermediate

What the interviewer is testing: atomic publish and file-watch pitfalls.

Situation: your job writes straight into the watched directory under the final name, and the consumer (a WatchService or a poller) sees the create event and starts reading before the write finishes. First check: compare the timestamps of the failing reads with the writer's duration; confirm both use the same directory. Fix: write to a temporary name or a different directory on the same file system (.tmp suffix, or a staging folder), flush and close, then Files.move(tmp, finalName, ATOMIC_MOVE), so the file appears whole in one step. The consumer ignores .tmp files. Alternatively write a small marker file after the data file, or give the producer and consumer a manifest. Prevent: make this a shared utility for all exports, document the contract (naming and completion rule), and test with a deliberately slow writer.

After a network timeout, your client retried "create payment" and the customer was charged twice. How do you prevent it? Senior

What the interviewer is testing: link between exception handling, retries and idempotency.

Situation: the first request reached the server and succeeded, but the response was lost, so the client saw a timeout (an exception that says "unknown outcome", not "failed"). Its retry created a second payment. First check: compare the two requests in server logs: same payload, different request ids, a few seconds apart. Fix: add an idempotency key: the client generates a unique key per logical operation and sends it on every retry; the server stores the key with the result in the same transaction as the payment (unique constraint) and returns the stored result for a repeat. Also make the client treat timeouts as "unknown" and query the status before retrying when possible. Refund the duplicates. Prevent: a rule that every non-idempotent POST in the platform accepts an idempotency key, retries use backoff with jitter and a max attempt count, and tests that replay the same request twice.
