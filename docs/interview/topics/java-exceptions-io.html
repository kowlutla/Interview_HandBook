How exceptions really behave and how to design error handling, what generics are (and are not) at runtime, files and NIO, charsets, and serialization. Each answer starts with a short spoken reply, then goes deeper, then ends with one line to remember.

Mental model: the ideas everything hangs on

One line: an exception is an object that travels up the call stack until someone handles it; generics are a compile-time check that is erased before runtime; I/O is bytes plus (sometimes) a charset plus a resource that must be closed.
  1. An exception is a normal object with a captured stack. Creating it walks the stack and records it, which is the expensive part. Throwing it unwinds frames until a matching catch is found.
  2. Checked vs unchecked is a compiler rule only. At runtime they behave the same.
  3. Never lose the cause. Wrap with the original as the cause, log once where it is finally handled, never swallow silently.
  4. Handle an exception at the layer that can do something about it. Lower layers translate technical errors; the top layer turns them into a response.
  5. Generics exist only at compile time. The compiler checks types, inserts casts, then erases the type arguments.
  6. Bytes are not text. Text needs a charset. Always name it in code.
  7. Every opened resource needs a guaranteed close. In modern Java that means try-with-resources.
  8. Java serialization rebuilds objects without calling your constructor. That is the root of both its bugs and its security problems.

1. Exception basics

Draw the exception hierarchy. What are Throwable, Error, Exception and RuntimeException? Basic

Throwable is the root, and only a Throwable can be thrown or caught. It has two children. Error is for serious JVM problems such as OutOfMemoryError that the program normally cannot fix. Exception is for problems the code might handle, and under it RuntimeException and its children are unchecked, while everything else (IOException, SQLException) is checked.

So "unchecked" means Error plus RuntimeException and their children: the compiler does not force you to catch or declare them. Typical runtime exceptions are NullPointerException, IllegalArgumentException, IllegalStateException and IndexOutOfBoundsException. All of them are programming mistakes. A custom exception is checked if it extends Exception and unchecked if it extends RuntimeException.

Remember: Throwable splits into Error (do not catch) and Exception; RuntimeException is the unchecked part of Exception.

What is the difference between checked and unchecked exceptions? Basic

A checked exception must be either caught or declared with throws, and the compiler enforces that. An unchecked exception needs neither. The intent was: checked for failures the caller can reasonably recover from and that are outside the program's control (a missing file, a dropped network), unchecked for programming mistakes like a null argument, where the fix is to change the code.

At runtime there is no difference at all. The rule is purely a compile-time contract on method signatures. That is why a method can throw an unchecked exception from deep inside without any signature change, while adding a new checked exception forces changes in every caller.

void read() throws IOException { ... }   // caller must handle or declare
void check(int n) {
    if (n < 0) throw new IllegalArgumentException("n < 0");   // no declaration needed
}

Remember: checked = the compiler makes you deal with it; unchecked = your bug or an Error. Same behaviour at runtime.

Are checked exceptions a good idea or a mistake? What do you use in your own code? Senior

Good idea in theory, awkward in practice, so I default to unchecked exceptions with clear domain names. I keep a checked one only where the caller really has a different recovery path. At the boundary with legacy APIs I translate checked to unchecked and keep the cause.

The case for checked: the signature honestly lists what can fail and the compiler stops you ignoring it. The case against, which most of the industry accepted (Spring and Hibernate are unchecked): they leak implementation details up the layers (a SQLException in a service interface), they push people into empty or wrapping catch blocks, and they do not work with lambdas, because Function and friends declare no checked exceptions. Adding a checked exception to an interface also breaks every implementation and caller.

Watch out: do not say "checked is always bad". Say it depends on whether the caller can recover and whether the exception crosses an abstraction boundary.

Remember: checked leaks details and breaks lambdas, so unchecked by default, checked only for real recoverable cases.

Should you ever catch an Error such as OutOfMemoryError or StackOverflowError? Intermediate

Normally no. After an OutOfMemoryError the JVM may be in a bad state, so the sensible reaction is to log if possible and let the process die so the orchestrator restarts it. The legitimate catch is at the top of a worker loop, where I catch Throwable so one bad task does not silently kill the thread, and I log it.

Other threads can also fail anywhere after an OOM, even inside your own handler, and data structures may be half updated. Useful flags are -XX:+HeapDumpOnOutOfMemoryError and -XX:+ExitOnOutOfMemoryError. A StackOverflowError is more recoverable, since the stack unwinds when you catch it, but fixing the runaway recursion is the real answer. Note that catch (Exception e) does not catch Errors.

A classic follow-up: ClassNotFoundException is a checked exception from Class.forName when a class cannot be found by name, while NoClassDefFoundError is an Error meaning the class existed at compile time but is missing or failed to initialize at runtime.

Remember: do not try to recover from an Error; catch Throwable only at a boundary to log, then fail or restart.

2. try, catch, finally and resources

Explain the execution order of try, catch and finally. When does finally not run? Basic

The try block runs. If it throws, the first matching catch runs. Then finally runs in every case, whether the try finished, threw, or returned. After that the method continues, returns, or rethrows. Finally does not run only if the JVM stops first: System.exit(), a crash, kill -9, or power loss.

If try or catch does a return, the return value is computed and saved first, then finally runs, then the method returns the saved value. So changing a local primitive in finally does not change what is returned, but changing a mutable object that was returned does show. A finally also will not complete if the thread loops or blocks forever, and a daemon thread can be stopped mid-way when the JVM exits. So finally is not a place for critical durability: use transactions and idempotent recovery.

Remember: finally runs on every path unless the JVM dies first. The return value is saved before finally runs.

What does this print, and why is return inside finally dangerous? Intermediate

The first method returns 1, because the return value was already saved before finally changed the variable. The second returns 42 and the exception disappears, because a return (or break or continue) inside finally overrides everything, including a thrown exception, with no trace.

static int f() {
    int x = 1;
    try { return x; }          // value 1 is saved
    finally { x = 2; }         // does not change the saved value
}                              // returns 1

static int g() {
    try { throw new RuntimeException("boom"); }
    finally { return 42; }     // exception is discarded, returns 42
}

The same thing happens if finally itself throws: the new exception replaces the original, and the original cause is lost. Keep finally blocks tiny and non-throwing, or use try-with-resources, which handles this properly. The compiler flag -Xlint:finally warns when a finally cannot complete normally.

Remember: never return or throw from finally; it silently replaces the real outcome.

What is try-with-resources and why is it better than try/finally? Basic

Any object that implements AutoCloseable (files, streams, sockets, JDBC connections) can be declared in the parentheses after try, and Java calls close() automatically at the end, even if the block throws. Several resources are closed in reverse order. It is better than try/finally because it is shorter, it cannot forget to close, and a failing close() no longer hides the real exception.

The old pattern needed a finally with null checks and a nested try/catch for close, and if close threw, it replaced the real error. Try-with-resources keeps the body's exception as the main one and attaches the close failure to it as a suppressed exception. If a resource expression is null, nothing is closed for it and there is no NPE. If opening resource B fails, resource A (already open) is still closed. Since Java 9 you can write try (res) for an existing effectively final variable.

try (var in  = Files.newBufferedReader(src);
     var out = Files.newBufferedWriter(dst)) {
    in.transferTo(out);
}   // out closed first, then in

Remember: open in order, close in reverse, body exception wins, close failures become suppressed.

What are suppressed exceptions? When would you see one? Intermediate

When the body of a try-with-resources throws exception E and then close() also throws C, only one can propagate. Java keeps E, the real cause, and attaches C to it with E.addSuppressed(C). You read them with getSuppressed(), and the stack trace prints them under "Suppressed:".

If the body succeeded but close throws, then C simply propagates as the main exception. You can call addSuppressed yourself in hand-written cleanup, for example when closing several resources in a loop and wanting to keep every failure.

java.io.IOException: write failed
    at App.run(App.java:12)
    Suppressed: java.io.IOException: close failed
        at MyRes.close(MyRes.java:8)

Remember: primary exception = body failure; suppressed = failures during close that would otherwise hide it.

AutoCloseable versus Closeable, and how do you write a good close()? Intermediate

AutoCloseable (Java 7) is what try-with-resources needs: one method, close() throws Exception. Closeable (in java.io) extends it, narrows the exception to IOException and requires that closing twice is harmless. A good close() is idempotent, releases in reverse order of acquisition and does not let one failed release stop the others.

Do not declare throws Exception in your own implementation if you throw nothing, otherwise every caller must catch it. Document whether close also closes anything it wraps. And never rely on the garbage collector to release scarce things such as file handles: finalize() is deprecated for removal since Java 18 because it runs at an unpredictable time, maybe never. Cleaner (Java 9) is only a last-resort safety net, not a plan.

public final class Conn implements AutoCloseable {
    private boolean closed;
    @Override public void close() {   // no checked exception, idempotent
        if (closed) return;
        closed = true;
        release();
    }
}

Remember: make close idempotent and non-throwing if you can; the GC is not a close mechanism.

What is exception chaining, and how do you preserve the cause? Basic

When I catch a low-level exception and throw a different one, I pass the original as the cause: new OrderStoreException("cannot save order 17", e). Then the stack trace shows "Caused by:" lines down to the root. Without the cause, only the place where I rethrew is visible and the real failure is lost.

For old exception classes with no cause constructor use initCause. Write a message that adds context the low level did not know, such as the order id, instead of repeating the same words. To find the root, walk getCause() in a loop. When reading a trace, the last "Caused by" is the root cause and usually the first place to look.

try { repo.save(order); }
catch (SQLException e) {
    throw new OrderStoreException("cannot save order " + order.id(), e);   // cause kept
}
Watch out: throw new RuntimeException(e.getMessage()) loses the type and stack. e.printStackTrace() writes to stderr, outside your logging.

Remember: always pass the cause as the second constructor argument.

How do you read a long stack trace with several "Caused by" sections? Basic

The first line is the outermost exception, the last one thrown. Below it are the calls, most recent first. Each "Caused by:" starts the cause of the previous one, and the last "Caused by:" is the root cause, which is where I start. Inside that section I look for the first frame in my own package.

A line like "... 23 more" means those frames are identical to the enclosing trace and were left out to save space. Also look for "Suppressed:" entries from try-with-resources. If the root cause message is generic, search the surrounding log lines with the same correlation id.

Remember: read from the bottom "Caused by", then find the first frame in your own code.

What does "swallowing an exception" mean and why is it so harmful? Basic

Swallowing means catching an exception and doing nothing: an empty catch block, or logging only e.getMessage() and carrying on. The code continues with wrong or missing data, and the failure shows up much later with no trace to follow. Each catch should do one of three things: recover for real, translate and rethrow with the cause, or log with the full stack and an explicit decision to continue.

If you truly want to ignore something, for example closing quietly after a failure, say so in a named helper and still log at debug level.

catch (IOException e) { }                            // bad: silent
catch (IOException e) { log.warn(e.getMessage()); }  // bad: no stack, no cause
catch (IOException e) {
    log.warn("cache write failed, continuing without cache", e);  // ok if intended
}

Remember: a catch block must recover, rethrow with the cause, or log the full stack on purpose. Never nothing.

Are exceptions slow? Where does the cost come from? Intermediate

The expensive part is creating the exception, not throwing it. The Throwable constructor calls fillInStackTrace(), which walks the whole call stack and records every frame. With the deep stacks typical in Spring or servlet code that is microseconds and some memory per exception. A try block that never throws costs nothing, because the handler table is just data.

So using exceptions for normal control flow, for instance one per failed lookup in a hot loop, can hurt. Fix it by returning Optional or a result for expected outcomes. For a truly hot path you can use the protected constructor with writableStackTrace=false to skip the stack.

class LightException extends RuntimeException {
    LightException(String m) { super(m, null, false, false); }  // no suppression, no stack trace
}

One log-reading trap: after many throws, the JIT may throw a pre-allocated NullPointerException or similar with an empty stack trace. If you see that, look for earlier occurrences of the same error, or run with -XX:-OmitStackTraceInFastThrow.

Remember: the cost is the stack capture at creation; do not use exceptions for expected outcomes.

What are the rules for exceptions when overriding a method? Intermediate

An overriding method can throw the same checked exceptions, narrower ones, or none. It cannot add a new or broader checked exception, because a caller using the parent type would not know to handle it. It may freely throw any unchecked exception.

class Base { void run() throws IOException { } }
class Ok1 extends Base { void run() throws FileNotFoundException { } }  // narrower: ok
class Ok2 extends Base { void run() { } }                                // fewer: ok
class Bad extends Base { void run() throws Exception { } }               // broader: compile error

The same rule applies to interface implementations: the interface method sets the maximum. This is one more source of friction with checked exceptions: an implementation that talks to a database cannot throw SQLException through an interface that did not allow it.

Remember: an override may narrow or drop checked exceptions, never widen them.

How should you handle InterruptedException? Senior

It means another thread asked this one to stop. I either let it propagate by declaring throws InterruptedException, or, if I cannot, I restore the flag with Thread.currentThread().interrupt() and then return or exit the loop. I never swallow it, because that erases the cancellation request and the thread keeps running.

When the exception is thrown, Java clears the interrupt flag, so catching it and carrying on loses the signal and the executor never shuts down cleanly. Blocking calls such as sleep, wait, join, BlockingQueue.take and Future.get all throw it. More on threads in Java concurrency.

try { queue.put(item); }
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restore the signal
    return;                               // stop cleanly
}

Remember: propagate it, or re-set the interrupt flag and stop. Never swallow it.

3. Exception design and error handling strategy

How do you design a good custom exception? Intermediate

I name it after what went wrong in the domain (PaymentDeclinedException, not MyException), usually make it unchecked, and always provide a constructor that takes a message and a cause. I add useful final fields such as an error code or entity id, so callers do not have to parse the message.

Keep a small hierarchy: one base per module (OrderException) with a few meaningful children, so callers can catch broadly or narrowly. Keep messages safe: no passwords, tokens or personal data. Add serialVersionUID, because Throwable is Serializable. Do not create one class per error message; an enum error code inside one class is often enough.

public class PaymentDeclinedException extends RuntimeException {
    private static final long serialVersionUID = 1L;
    private final String paymentId;
    private final boolean retryable;
    public PaymentDeclinedException(String paymentId, boolean retryable, String msg, Throwable cause) {
        super(msg, cause);
        this.paymentId = paymentId; this.retryable = retryable;
    }
    public String paymentId() { return paymentId; }
    public boolean retryable() { return retryable; }
}

Remember: domain name, message plus cause constructor, final fields with data, small hierarchy.

What is exception translation, and where should it happen in a layered application? Senior

Translation means catching a low-level exception at a layer boundary and throwing one that makes sense to the layer above, with the original as the cause. The repository turns SQLException into a store error, the service turns that into a domain outcome, and the web layer maps domain exceptions to HTTP status codes in one central place. That way upper layers never depend on JDBC or an HTTP client.

The cost is a little extra code and the discipline to keep the cause every time. Frameworks help: Spring translates JDBC and JPA errors into its DataAccessException hierarchy, and @ControllerAdvice with @ExceptionHandler maps exceptions to responses in one place.

Remember: translate at each layer boundary, keep the cause, map to HTTP in one handler.

Design an error handling strategy for a layered REST service. Senior

I separate three kinds of failure: client mistakes (bad input, not found, conflict: 4xx, no alert), expected business outcomes (insufficient funds), and system failures (database down, timeout: 5xx, alert). I use a small set of unchecked domain exceptions, one global handler that returns a consistent error body with a correlation id and never a stack trace, and I log each failure once where it is finally handled.

  • Validate at the edge (Bean Validation) and fail fast, so deep layers can trust their inputs.
  • One error format: Spring 6 supports RFC 9457 ProblemDetail. For a 500 return a generic message plus the correlation id; details stay in the logs.
  • Calls to other services: timeouts, bounded retries for transient errors only, a circuit breaker.
  • Make writes idempotent so a retry is safe (see the duplicate-payment scenario).
  • Test the failure paths, not just the happy ones.

Remember: classify failures (client, business, system), one global handler, log once, safe retries.

Why is "log and throw" an anti-pattern? How should you log an exception? Intermediate

If every layer logs the exception and rethrows it, one failure produces five log entries with the same stack. That doubles the noise, makes error counts wrong and confuses whoever reads the log at 3 a.m. The rule is: either handle it (and log it there) or let it propagate (adding context in a wrapper). Not both.

Log at the boundary where the exception stops travelling: the controller advice, the message consumer loop, the scheduler wrapper. Pass the exception object as the last argument so the logger prints the stack and all causes, and put identifying context in the message (order id, operation), plus the correlation id from MDC. Choose the level by impact: user errors at WARN or INFO, system failures at ERROR. For a repeating error in a retry loop, rate-limit the log, because millions of identical stacks can fill the disk.

// bad: logged here and again at the top
catch (SQLException e) { log.error("db failed", e); throw new StoreException("db failed", e); }
// good: add context, log once at the top
catch (SQLException e) { throw new StoreException("cannot load order " + id, e); }

log.error("cannot send invoice for order {}", orderId, ex);   // exception last, no placeholder for it

Remember: handle or propagate, never both. Log once, with the exception object, at the end of the road.

What are the alternatives to exceptions? When would you use a Result type? Senior

Exceptions suit unexpected failures that most callers cannot handle locally. For expected outcomes, a normal return value is clearer and cheaper: Optional for "may be absent", or a result type that carries success or failure and forces the caller to look at both. I use results for validation and business rules where failure is common and local, and exceptions for real faults.

In Java 21 a sealed interface with record cases plus a pattern-matching switch gives a compiler-checked result type with no library (libraries like Vavr offer Try and Either). Optional is poor for errors because it says "nothing" but not why. The trap is mixing styles: a method that returns a Result and also throws makes callers handle both.

sealed interface Result<T> permits Ok, Err {}
record Ok<T>(T value) implements Result<T> {}
record Err<T>(String code) implements Result<T> {}

String msg = switch (parse(input)) {
    case Ok<Integer> ok -> "value " + ok.value();
    case Err<Integer> err -> "error " + err.code();
};

Remember: expected failure = return value; unexpected failure = exception. Pick one style per method.

In Spring, which exceptions roll back a transaction? Intermediate

By default @Transactional rolls back on unchecked exceptions (RuntimeException and Error) and commits on checked ones. So a method that writes to the database and then throws IOException still commits. To change that use @Transactional(rollbackFor = Exception.class).

Two more traps give the same "it committed anyway" symptom. If you catch the exception inside the transactional method and swallow it, the proxy sees a normal return and commits. And if you call a transactional method from another method in the same class (self-invocation), the call bypasses the proxy, so no transaction logic runs at all. Private or final methods are also not intercepted by proxies. See Hibernate and JPA.

Remember: rollback on RuntimeException and Error only; swallowed exceptions and self-invocation also defeat it.

How do you deal with NullPointerException in a principled way? Basic

I stop nulls at the entry and avoid returning them. I validate arguments early with Objects.requireNonNull(x, "x"), return empty collections instead of null, and use Optional for return values that may be absent (not for fields or parameters). I never catch an NPE to hide a bug.

Since Java 14 (on by default from 15) the NPE message says exactly what was null, for example Cannot invoke "String.length()" because "name" is null, which saves a lot of debugging time. Annotations like @Nullable with a checker make the contract visible.

Remember: fail fast with requireNonNull, return empty not null, Optional only for return values.

4. Exceptions in lambdas, threads and static initializers

How do you deal with checked exceptions inside lambdas and streams? Intermediate

The standard functional interfaces (Function, Consumer, Supplier) declare no checked exceptions, so a lambda calling something that throws IOException does not compile. The simplest fix is to catch inside the lambda and rethrow as an unchecked exception with the cause. For repeated use, write a small helper, or just use a plain loop, which is often clearest.

An exception in the middle of a stream pipeline stops the whole pipeline. If you want to skip bad items, catch inside the lambda and return an empty Optional or a result, then filter.

@FunctionalInterface interface ThrowingFn<T,R> { R apply(T t) throws Exception; }
static <T,R> Function<T,R> unchecked(ThrowingFn<T,R> f) {
    return t -> { try { return f.apply(t); }
                  catch (Exception e) { throw new RuntimeException(e); } };  // cause kept
}
paths.stream().map(unchecked(Files::readString)).toList();   // toList: Java 16

Remember: wrap in an unchecked exception with the cause, or use a loop. Never drop the cause.

An exception is thrown inside a task submitted to an ExecutorService. Where does it go? Senior

It depends on how I submitted it. With submit() the exception is stored inside the Future and nothing is logged unless someone calls get(), which throws ExecutionException. With execute() it kills the worker thread and goes to the thread's uncaught exception handler, which by default only prints to stderr. A periodic task in a ScheduledExecutorService that throws is silently cancelled and never runs again.

The fix is to wrap the task body in a try/catch that logs, and always handle the Future result. For pools, set a handler through a custom ThreadFactory with setUncaughtExceptionHandler. The handler only fires for threads that die from the exception, never for ones stored in a Future. For CompletableFuture, exceptions are wrapped in CompletionException, so end every chain with exceptionally or handle.

executor.submit(() -> {
    try { doWork(); }
    catch (Throwable t) { log.error("job failed", t); }   // never let it vanish
});

Remember: submit hides it in the Future, execute prints to stderr, scheduled tasks stop. Catch and log inside the task.

What happens when a static initializer throws? What is ExceptionInInitializerError? Senior

The first caller gets ExceptionInInitializerError with the real exception as its cause. The class is then marked as failed, and every later use in that classloader throws NoClassDefFoundError: Could not initialize class X, which does not show the original cause. So in the logs you see the useless second error thousands of times, and the informative first one is long gone.

When you see "Could not initialize class", search the logs backwards for the first ExceptionInInitializerError, whose "Caused by" is the real problem (often a missing config value or a failed resource load). You cannot recover in the same classloader; you need to fix the cause and restart. Prevention: keep static initialization simple, never connect to remote systems there, and load config in an explicit start-up phase that fails fast with a clear message.

Remember: first failure = ExceptionInInitializerError (real cause); every later one = NoClassDefFoundError (no cause).

5. Generics

What are generics for, and what is type erasure? Intermediate

Generics let the compiler check types, so List<String> rejects an Integer at compile time and you do not cast on every read. Type erasure means that after checking, the compiler removes the type arguments: at runtime a List<String> is just a List, and new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass().

Before Java 5 a List held Object, so you cast on every read and a wrong type failed at runtime with ClassCastException. Erasure was a deliberate choice so old non-generic code and new generic code could work together. The compiler replaces an unbounded T with Object (or with its bound, for T extends Number), inserts casts where values are read, and generates hidden bridge methods where needed so overriding still works. The class file keeps generic signatures of declarations as metadata, which reflection can read, but objects carry no type arguments.

Remember: generics are checked at compile time, erased at runtime, and the compiler adds the casts.

What can you NOT do with generics because of erasure? Intermediate

Anything that needs the type argument at runtime. You cannot write new T(), new T[10] or new List<String>[10], and you cannot use instanceof List<String> (only List<?>). You also cannot use primitives as type arguments, so List<int> is illegal and you pay for boxing.

Other consequences: no static field of type T (statics belong to the class, not an instance), a generic class cannot extend Throwable, and two methods that differ only in type arguments clash because they erase to the same signature. The usual workaround for needing the type is to pass a Class<T> token or a Supplier<T>.

class Box<T> {
    private final Class<T> type;
    Box(Class<T> type) { this.type = type; }
    T make() throws Exception { return type.getDeclaredConstructor().newInstance(); }
}
void m(List<String> a) {}
void m(List<Integer> a) {}   // compile error: same erasure

Remember: no new T, no generic arrays, no instanceof with type arguments, no primitives. Pass a Class token instead.

What are bounded type parameters and generic methods? Explain <T extends Comparable<T>>. Intermediate

A bound limits which types are allowed and lets me call the bound's methods. In <T extends Comparable<T>>, T must be comparable with itself, so I can call a.compareTo(b). A generic method declares its own type parameter before the return type, as in static <T> T firstOr(List<T> xs, T fallback), and the compiler usually infers T from the arguments.

The more flexible real-world form is <T extends Comparable<? super T>>, because a subclass such as java.sql.Timestamp compares as its parent Date, not as itself. Multiple bounds use & (T extends Number & Comparable<T>), with the class first. After erasure, T becomes its first bound. When inference fails you can give an explicit witness: Collections.<String>emptyList().

static <T extends Comparable<? super T>> T max(Collection<? extends T> c) {
    Iterator<? extends T> it = c.iterator();
    T best = it.next();
    while (it.hasNext()) { T x = it.next(); if (x.compareTo(best) > 0) best = x; }
    return best;
}
String s = firstOr(names, "none");   // T inferred as String

Remember: a bound gives T abilities; use Comparable<? super T> for the flexible form.

Explain wildcards and the PECS rule: Producer Extends, Consumer Super. Senior

? extends T means "some unknown subtype of T": I can safely read items out as T, but I cannot add anything (except null). ? super T means "some unknown supertype of T": I can safely write a T in, but reads only give me Object. So if a parameter produces values for me I use extends, if it consumes values from me I use super, and if both I use the exact type.

Why can't I add to a List<? extends Number>? The real list might be a List<Integer>, and adding a Double would corrupt it. The classic example is Collections.copy(List<? super T> dest, List<? extends T> src). A bare ? means unknown: read as Object, write nothing.

double sum(List<? extends Number> xs) { double s = 0; for (Number n : xs) s += n.doubleValue(); return s; }
void fill(List<? super Integer> out) { out.add(1); out.add(2); }
sum(List.of(1, 2.5));               // ok
fill(new ArrayList<Number>());     // ok

Remember: PECS: producer extends (read), consumer super (write), both means no wildcard.

What is the difference between List<?>, List<Object> and a raw List? Intermediate

List<Object> is a list that holds anything, and I can add any object to it, but it only accepts exactly that type: a List<String> cannot be passed to it. List<?> accepts a list of any element type, but I can only read items as Object and cannot add (except null). A raw List turns the generic checks off completely and should be avoided.

So when a method only needs to look at the list without caring about element type (for example print it or get its size), List<?> is the right choice. List<Object> is rarely what you want, because of invariance: List<String> is not a List<Object>.

void printAll(List<?> xs)        { for (Object o : xs) System.out.println(o); }  // takes any list
void addAny(List<Object> xs)     { xs.add("x"); xs.add(1); }                      // only List<Object>
printAll(List.of("a"));   // ok
addAny(new ArrayList<String>());   // compile error

Remember: List<?> = any list, read-only in practice. List<Object> = exactly that type. Raw = no safety.

Arrays are covariant but generics are invariant. What does that mean and why does it matter? Senior

Covariant means that because Integer is a Number, Integer[] is also a Number[]. That is true for arrays, and it is unsafe: I can store a Double through a Number[] alias and get an ArrayStoreException at runtime. Generics are invariant: List<Integer> is not a List<Number>, so the same mistake is rejected at compile time.

Arrays remember their real element type and check every store at runtime. Generics are erased, so they cannot do that runtime check and needed the stricter compile-time rule. Wildcards (? extends) give back flexibility safely, as read-only views. This is also why you cannot create a generic array: arrays check element types at runtime, and that type is erased.

Number[] a = new Integer[1];
a[0] = 1.5;                                  // compiles; ArrayStoreException at runtime
List<Number> l = new ArrayList<Integer>();   // compile error: invariant

Remember: arrays are covariant and checked at runtime; generics are invariant and checked at compile time.

What is a raw type, and why should you avoid it? Basic

A raw type is a generic class used without type arguments, like List instead of List<String>. It exists only so pre-Java-5 code still compiles. With a raw type the compiler switches off the generic checks and gives only an "unchecked" warning, so a wrong value goes in silently and blows up later, somewhere else, as a ClassCastException.

If you do not care about the element type, write List<?>, which is safe. Do not suppress unchecked warnings widely: suppress on the smallest scope, with a comment saying why it is safe.

Remember: never use raw types; use List<?> if the element type does not matter.

What is heap pollution, and how can it cause a ClassCastException that looks impossible? Senior

Heap pollution means a variable of a parameterized type refers to an object that is not of that type. It happens through raw types, unchecked casts or generic varargs. The JVM cannot see it at the point of the mistake because the type arguments are erased, so the failure appears later, at the compiler-inserted cast on a line that looks perfectly safe.

List<String> strings = new ArrayList<>();
List raw = strings;                 // unchecked warning
raw.add(42);                        // pollution: no error here
String s = strings.get(0);          // ClassCastException: Integer cannot be cast to String

Generic varargs are another source: static <T> void f(T... xs) creates an array that is really an Object[], so the method could store wrong things in it. If your method only reads the array and does not leak it, mark it @SafeVarargs. Another common real-world case: a JSON mapper given List.class returns a list of maps, and the cast fails when you read an element as your class (use a TypeReference). To find the culprit, compile with -Xlint:unchecked and in tests wrap suspicious lists with Collections.checkedList, which checks at insertion.

Remember: treat every unchecked warning as a bug until proven safe; the exception shows up far from the cause.

Why can't you create a generic array, and how does ArrayList get around it? Senior

new T[n] is illegal because arrays need their real element type at runtime to check stores, and T is erased. Library code gets around it by creating an Object[] and casting: (T[]) new Object[n]. That unchecked cast is safe only if the array never escapes to code expecting a real T[].

If it were allowed, you could build a List<String>[], put a List<Integer> in through an Object[] alias, and the array's runtime check could not catch it. ArrayList keeps an Object[] internally and casts on each read. When you must return a real typed array, pass a Class<T> and use Array.newInstance, or accept an IntFunction<T[]>, which is what stream.toArray(String[]::new) does.

@SuppressWarnings("unchecked")
T[] make(int n) { return (T[]) new Object[n]; }       // fine inside, ClassCastException if returned as String[]
String[] arr = list.stream().toArray(String[]::new);  // the clean way

Remember: store an Object[] and cast on read; to return a real typed array, take a Class or an array constructor.

If generics are erased, how does Jackson still know the type when I pass a TypeReference? Senior

Erasure removes type arguments from objects, but the class file still stores the generic signature of declarations: fields, method parameters and the generic superclass. new TypeReference<List<User>>() {} creates an anonymous subclass whose generic superclass records List<User> permanently, and the library reads it with reflection.

That is why mapper.readValue(json, new TypeReference<List<User>>() {}) works, while passing List.class would give a list of maps, not Users. Guava's TypeToken and Spring's ParameterizedTypeReference use the same "super type token" trick. For non-generic cases a plain Class<T> token is enough.

Remember: an anonymous subclass keeps its generic superclass in the class file; frameworks read it back.

6. Java I/O: streams, readers, buffering, charsets

What is the difference between byte streams and character streams (readers and writers)? Basic

InputStream and OutputStream move raw bytes: images, zip files, network packets. Reader and Writer move characters. A reader sits on top of a stream and uses a charset to decode bytes into characters, and a writer encodes characters back. I use streams for binary data, readers for text, and I always name the charset.

The bridge classes are InputStreamReader and OutputStreamWriter: new InputStreamReader(in, StandardCharsets.UTF_8). A reader on binary data corrupts it, and a stream on text forces you to decode by hand. Each wrapper adds one job (the decorator pattern), and closing the outermost one closes the rest.

Remember: streams = bytes, readers = characters via a charset. Say the charset out loud.

Why does buffering matter, and when do you need to flush? Intermediate

Each unbuffered read() or write() can become a system call into the OS, which is slow compared to memory. A buffered wrapper (BufferedReader, BufferedOutputStream, default 8 KB) moves data in big blocks and hands out small pieces from memory, which can be orders of magnitude faster. The catch is that data sitting in the buffer is not written yet, so I must flush() or, better, close(), which flushes first.

If you forget to close a buffered writer, the tail of the file can be silently missing. flush() only hands data to the OS; to force it to disk you need FileChannel.force(true). A GZIPOutputStream must be closed (or finish()ed) to write its trailer, or the file is corrupt.

try (var w = Files.newBufferedWriter(Path.of("out.txt"))) {   // UTF-8 by default
    w.write("hello"); w.newLine();
}   // close() flushes

Remember: buffer for speed, close (which flushes) so the last bytes are not lost.

Explain charsets. What is the default charset, and why is it a trap? Intermediate

A charset is the rule that maps characters to bytes. UTF-8 (1 to 4 bytes per character, ASCII as a subset) is the sensible choice for almost everything. If you write with one charset and read with another you get garbage like "Ã©" instead of "é". The trap: new String(bytes), getBytes(), FileReader and new InputStreamReader(in) use the platform default, which before Java 18 depended on the OS, so code worked on a laptop and broke on the server.

From Java 18 (JEP 400) the default is UTF-8 everywhere, but older runtimes still exist, so I always pass the charset. The NIO helpers Files.readString, Files.newBufferedReader and Files.lines default to UTF-8 regardless of version.

byte[] b = "café".getBytes(StandardCharsets.UTF_8);          // 5 bytes
String wrong = new String(b, StandardCharsets.ISO_8859_1);   // "cafÃ©"  (mojibake)
String ok = new String(b, StandardCharsets.UTF_8);           // "café"

Smaller traps: invalid bytes are silently replaced by InputStreamReader but throw MalformedInputException in Files.readAllLines. A UTF-8 byte-order mark (EF BB BF) is not stripped, so the first CSV field may contain an invisible character. And String.length() counts UTF-16 units, so an emoji counts as 2.

Remember: always pass StandardCharsets.UTF_8; never trust the platform default.

How do you read a very large file efficiently without running out of memory? Intermediate

I stream it instead of loading it. For text I use BufferedReader.readLine() or Files.lines(path) in try-with-resources, and for binary data I read in fixed chunks (8 KB to 1 MB). I process each record, write results out as I go and keep per-record state small, so memory use stays constant however large the file is.

Files.readAllBytes, readString and readAllLines load everything (and are limited to about 2 GB because arrays are int-indexed), so they are for small config files only. Files.lines returns a lazy stream that holds an open file, so it must be closed. Java strings and objects also have overhead, so a 4 GB file can need far more than 4 GB of heap once parsed into objects. For database loads use JDBC batches (hundreds to a few thousand rows) and commit per batch.

try (Stream<String> lines = Files.lines(path)) {       // lazy, close it
    long errors = lines.filter(l -> l.contains("ERROR")).count();
}
try (InputStream in = Files.newInputStream(path)) {
    byte[] buf = new byte[1 << 16]; int n;
    while ((n = in.read(buf)) != -1) { process(buf, n); }
}

Remember: stream and process as you go; read-all methods are only for small files.

7. NIO, files and paths

What is the difference between java.io.File and java.nio.file.Path and Files? Why prefer NIO.2? Basic

File is the old API: methods like delete() and mkdir() just return false on failure without saying why, and it handles links and attributes poorly. Path and the Files helper class (NIO.2, Java 7) throw descriptive exceptions such as NoSuchFileException and AccessDeniedException, and support copy and move options, atomic moves, attributes, symbolic links, directory walking and even zip file systems. I use Path/Files in all new code.

Convert with file.toPath() and path.toFile(). Create paths with Path.of("a", "b") (Java 11). Useful methods: resolve (join), relativize, normalize (remove ..). Files.list is one level and Files.walk is recursive; both return streams that must be closed. To prevent path traversal (../../etc/passwd, zip-slip), resolve against the base, normalize, then check startsWith(base).

Path p = Path.of("data", "in.csv");
Files.createDirectories(p.getParent());
Files.writeString(p, "a,b\n", StandardCharsets.UTF_8);
try (Stream<Path> s = Files.walk(Path.of("data"))) { s.filter(Files::isRegularFile).forEach(System.out::println); }

Remember: Path and Files give real exceptions and more features; File only returns booleans.

What is the difference between classic I/O and NIO? When do selectors matter? Intermediate

Classic I/O is stream based and blocking: a thread calls read() and waits until data arrives, so one busy connection needs one thread. NIO is buffer and channel based and can be non-blocking: many channels are registered with one Selector, and a single thread asks "which channels are ready?" and handles only those. Classic I/O is simple and fine for files and modest concurrency; NIO selectors matter when you hold thousands of mostly idle connections.

With 10,000 blocking connections you need about 10,000 threads, which costs memory and context switching. With a selector, one event-loop thread (backed by epoll on Linux) serves them all. Netty, Vert.x and Spring WebFlux are built on this. The trade-off is a harder programming model: you must never block the event loop, and heavy or blocking work must move to another pool. Tomcat uses NIO to hold connections cheaply but still gives each active request its own thread. Since Java 21, virtual threads let you write simple blocking-style code and still scale to many connections, which reduces the need for hand-written non-blocking code (see concurrency).

Remember: blocking = a thread per connection; NIO selector = one thread for many ready channels.

Explain NIO channels and buffers. How is a ByteBuffer different from a byte array? Senior

A channel (FileChannel, SocketChannel) is a connection that reads and writes through buffers rather than streams. A ByteBuffer is a block of memory with three numbers: capacity (its size), position (next index to read or write) and limit (first index you must not touch). After filling it from a channel I call flip() to switch to reading, then clear() or compact() to prepare for the next fill.

A plain byte array has no notion of "how much is valid", while a buffer tracks it. flip() sets limit to the old position and position to 0. A buffer can be on the heap (allocate) or direct (allocateDirect, outside the Java heap), which avoids one copy during I/O but is costlier to allocate and not freed promptly. FileChannel.transferTo lets the OS move data to a socket without passing through user space (zero-copy, typically via sendfile). Buffers are not thread-safe.

try (FileChannel ch = FileChannel.open(path, StandardOpenOption.READ)) {
    ByteBuffer buf = ByteBuffer.allocate(8192);
    while (ch.read(buf) != -1) {
        buf.flip();
        while (buf.hasRemaining()) consume(buf.get());
        buf.clear();
    }
}

Remember: fill, flip, drain, clear. A buffer tracks position and limit; an array does not.

How do you write a file so readers never see a half-written file? Senior

I write the full content to a temporary file in the same directory, close it, and then rename it over the final name with Files.move(tmp, target, ATOMIC_MOVE). A rename within one file system is atomic on common systems, so a reader sees either the old complete file or the new complete file, never a mix. A crash during the write leaves only a stray temp file.

The temp file must be on the same file system, otherwise atomic move fails with AtomicMoveNotSupportedException. Use Files.createTempFile(dir, "x", ".tmp") for the name, and tell consumers to ignore .tmp files. If you also need to survive power loss, force the temp file to disk before the rename. This matters when another process watches the folder (a file-watch event can fire before the write finishes).

Path tmp = Files.createTempFile(dir, "export", ".tmp");
Files.writeString(tmp, content, StandardCharsets.UTF_8);
Files.move(tmp, dir.resolve("export.csv"), StandardCopyOption.ATOMIC_MOVE);

Remember: write to a temp file in the same folder, then atomic rename.

8. Serialization

How does Java serialization work? What do Serializable and transient do? Basic

Serialization turns an object graph into a byte stream (ObjectOutputStream.writeObject) and rebuilds it later (ObjectInputStream.readObject). A class opts in by implementing the marker interface Serializable, which has no methods. All non-static, non-transient fields are written, and every object they reference must also be serializable, or I get NotSerializableException.

A transient field is skipped and comes back as null, 0 or false; use it for caches, threads, connections and secrets. static fields belong to the class and are not written. Two details interviewers like: on reading, the constructor of the class itself is not called (that is why invariants can break), and if the parent class is not Serializable, its public or protected no-arg constructor runs to initialize the parent's fields. Serialization writes the whole graph, so one careless reference can drag in a huge structure.

Remember: Serializable opts in; transient and static are skipped; the constructor is not run on read.

What is serialVersionUID? What happens if you do not declare it? Intermediate

It is a version number for the class. When reading, Java compares the number in the stream with the one in the loaded class and throws InvalidClassException if they differ. If I do not declare it, Java computes one from the class structure, so even a harmless change like adding a method changes it and old data becomes unreadable. So I declare it explicitly: private static final long serialVersionUID = 1L;.

With a fixed id, adding a field is compatible (old data gives it the default value) and removing a field is compatible (the data is ignored). Changing a field's type, renaming or moving the class (the class name is in the stream), or changing between class and enum is incompatible. This causes real outages when old and new nodes share a cache or session store during a rolling deploy. For data that outlives a deploy, prefer a schema-based or JSON format.

Remember: declare it yourself; a computed one changes on almost any edit.

How do you customize serialization: writeObject, readObject, readResolve, the serialization proxy? Senior

I add private writeObject and readObject methods, call defaultWriteObject() or defaultReadObject() first, then handle extra data. In readObject I treat the stream as untrusted input: re-validate invariants and make defensive copies, because deserialization builds the object without running my constructor. readResolve() swaps in another object, which keeps a singleton single.

The safest design is the serialization proxy pattern: writeReplace returns a small private nested class holding the logical state, and its readResolve rebuilds the real object through the normal constructor, so all validation runs. Records work like this by design: they are rebuilt through the canonical constructor (their custom hooks are ignored). Enums are serialized by name only and always come back as the same constant.

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    if (amount < 0) throw new InvalidObjectException("amount must be >= 0");   // re-validate
    items = List.copyOf(items);                                                  // defensive copy
}
private Object readResolve() { return INSTANCE; }   // singleton stays single

Remember: deserialization skips the constructor, so re-validate in readObject or use a serialization proxy.

Why is deserializing untrusted data dangerous? How do you protect against it? Senior

readObject instantiates whatever classes the stream names and runs their readObject methods before my code can check the type. An attacker builds a stream from "gadget" classes already on the classpath whose normal methods chain together into running a command, so the result can be remote code execution. The best protection is to never deserialize untrusted Java objects: use a data-only format such as JSON or Protobuf with a fixed schema.

If I must use Java serialization, I set an allow-list ObjectInputFilter (Java 9, backported to 8u121; JVM-wide with -Djdk.serialFilter=com.myco.*;!*, per-stream filters, and context-specific filters since Java 17), limit depth, array size and stream bytes, keep libraries patched, and run with least privilege. The same class of problem appears in JSON mappers with default typing enabled on untrusted input.

Remember: the object is built before you can check it. Never deserialize untrusted bytes; otherwise allow-list with ObjectInputFilter.

What are the alternatives to Java serialization, and when would you choose each? Intermediate

Java's built-in format is Java-only, fragile across versions, slow, large and a security risk, so I avoid it for anything new. For APIs and config I use JSON (Jackson). For service-to-service messages and storage I use a schema-based binary format such as Protobuf or Avro, which are compact and have clear rules for adding fields. The deciding questions are: who reads it, how long must old data stay readable, how big and fast must it be, and is the source trusted.

FormatReadableSize/speedSchema evolutionTypical use
Java serializationNoLarge, slowFragileLegacy only
JSONYesLarger, fineFlexible, looseREST APIs, config
ProtobufNoSmall, fastStrong rulesgRPC, internal messages
AvroNoSmall, fastSchema registryKafka, data pipelines

Remember: JSON for humans and APIs, Protobuf or Avro for compact evolving messages, Java serialization for nothing new.

What is Externalizable, and how is it different from Serializable? Intermediate

Externalizable extends Serializable but gives me full control: I implement writeExternal and readExternal and write exactly the bytes I want, and nothing is saved automatically, not even superclass fields. On reading, Java first calls the class's public no-argument constructor and then readExternal.

It can give smaller and faster output and lets me manage versions by hand. The costs are more code, the risk of forgetting a field, and the mandatory public constructor. The security issues are the same as for Serializable. Today most teams pick a schema-based format instead.

Remember: Externalizable = you write every byte, and the class needs a public no-arg constructor.

9. Real-life scenarios

Each scenario is answered the same way: a one-line diagnosis, then situation, what you check first, the fix, and how you prevent it next time.

Orders silently stop being saved. The logs show nothing wrong. A teammate finds an empty catch block. What do you do? Intermediate

An empty catch swallowed the failure, so callers think the save worked. I remove it, let the exception travel (translated, with the cause) to the global handler that logs once and returns a 5xx, and reprocess the missed orders from the source data.

Situation: a save method catches Exception, does nothing and returns; support tickets arrive days later. Check first: reproduce with a failing input, find when the first order went missing and compare with the deploy that added the catch (version control blame). Fix: catch only what you can handle; translate and rethrow the rest. Prevent: a review rule and static analysis against empty catch blocks, a metric and alert on save failures, and a test that proves a failing repository gives a failure response.

// before
try { repo.save(order); } catch (Exception e) { }
// after
try { repo.save(order); }
catch (DataAccessException e) { throw new OrderStoreException("cannot save order " + order.id(), e); }

Remember: a swallowed exception turns a loud failure into silent data loss.

After a few hours the service fails with "Too many open files" and "Timeout waiting for connection from pool". How do you investigate? Senior

That is a resource leak: something opens files, sockets or connections and does not close them on every path. I confirm the descriptor count grows, find what is leaking, and fix it with try-with-resources.

Check first: count open descriptors over time (ls /proc/PID/fd | wc -l on Linux) and group with lsof -p PID to see whether they are files, sockets to one host, or database connections. Take a thread dump to see threads waiting for the pool. Turn on pool leak detection (HikariCP leakDetectionThreshold), which prints the stack of the code that borrowed a connection and never returned it. Fix: usual culprits are an early return or exception before close(), an unclosed Files.lines or Files.list stream, or an HTTP response body not consumed. Prevent: try-with-resources by rule, static analysis for resource leaks, dashboards for open descriptors and pool usage, and a long-running load test that exposes slow leaks.

Remember: a problem that grows with time and a restart that "fixes" it means a leak. Count descriptors, then try-with-resources.

Customer names with accents show as "Ã©" after a release to Linux, though they looked fine on laptops. Why, and how do you fix it? Intermediate

The bytes are right but they are being decoded with the wrong charset, because some code uses the platform default, which differs between a Windows laptop and a Linux server. I pass StandardCharsets.UTF_8 everywhere and agree the encoding as part of the file or API contract.

Check first: look at the raw bytes with xxd: "é" as C3 A9 is UTF-8, E9 is ISO-8859-1 or Cp1252. Search the code for new String(bytes), getBytes(), FileReader and InputStreamReader without a charset, and check the database connection charset and the HTTP Content-Type charset. Fix: explicit charsets; repair already-corrupted data by re-decoding (new String(s.getBytes(ISO_8859_1), UTF_8)) if it was misdecoded exactly once. Prevent: a lint rule against charset-less overloads, tests run with a non-UTF-8 default on older JDKs, and Java 18 or newer where UTF-8 is the default.

Remember: garbled text means a charset mismatch. Look at the bytes, then name the charset in code.

A nightly import job fails with OutOfMemoryError on a 4 GB file, although it worked on small test files. What is wrong? Intermediate

The job loads the whole file (Files.readAllLines or one big String) and builds a big list of objects, so memory grows with file size. I switch to streaming: read line by line, process each record, and write results in batches.

Check first: a heap dump (-XX:+HeapDumpOnOutOfMemoryError) shows one huge array or list as the largest object. Remember that Java strings and objects carry overhead, so a 4 GB file needs well over 4 GB of heap once parsed. Fix: BufferedReader.readLine() in a loop or Files.lines inside try-with-resources, JDBC batches of a few hundred to a few thousand rows with a commit per batch, so memory stays constant. For sorting or grouping, use external sort or let the database do it. Prevent: a test with a generated large file, a heap limit in CI, and a rule that bulk-read methods are for known-small files only.

Remember: memory should not grow with input size. Stream and batch.

A security scan flags an endpoint that reads a Java-serialized object from a cookie. How serious is it and what do you do? Senior

It is critical: the server calls readObject() on bytes the client controls, so a gadget class on the classpath can give an attacker code execution. I block or filter the endpoint at once, then replace the design so no client-supplied Java objects are deserialized.

Check first: is the data signed or encrypted with a key the client does not know? Which libraries on the classpath have known gadget chains? Do logs show odd class names in InvalidClassException (probing)? Immediate step: a strict allow-list ObjectInputFilter or disable the endpoint, and patch vulnerable libraries. Real fix: keep session state on the server, or send JSON with an explicit schema and an HMAC checked before parsing. Prevent: dependency scanning, a code-review ban on readObject for external input, and rotating any secrets the host held if exploitation is possible.

Remember: client-controlled Java deserialization equals remote code execution. Replace it, do not just patch it.

A scheduled cleanup job ran for weeks and then simply stopped, with no error in the logs. What happened? Senior

One run threw an exception that escaped the task, and ScheduledExecutorService.scheduleAtFixedRate (and scheduleWithFixedDelay) suppresses all later runs when that happens. The exception sits in the returned ScheduledFuture, which nobody reads. I wrap the whole body in try/catch (Throwable), log it, and restart the job.

Check first: confirm there is no try/catch around the task body and look for a failure (a database blip, a null pointer) around the time it stopped; a thread dump will show no activity for that job. Fix: catch Throwable inside the task so one bad run does not cancel the schedule. Spring @Scheduled logs the error and keeps going, but check your error handler anyway. Prevent: a heartbeat metric (last successful run time) with an alert if it is older than two intervals.

Remember: an uncaught exception cancels a periodic task silently. Catch inside, and alert on a missing heartbeat.

After a network timeout, your client retried "create payment" and the customer was charged twice. How do you prevent it? Senior

A timeout means "unknown outcome", not "failed": the first request probably succeeded and only the response was lost. I make the operation idempotent with an idempotency key, so the retry returns the stored result instead of creating a second payment.

Check first: compare the two requests in the server logs: same payload, different request ids, seconds apart. Fix: the client generates one unique key per logical operation and sends it on every retry. The server stores the key with the result in the same transaction as the payment, under a unique constraint, and returns the stored result for a repeat. Refund the duplicates. Retry only transient errors (timeouts, 503, 429), with a small attempt limit, exponential backoff with random jitter, and retries at one layer only (otherwise three layers of retries turn one failure into 27 calls). Prevent: every non-idempotent POST accepts an idempotency key, and tests replay the same request twice. See Distributed systems.

Remember: never retry a non-idempotent call without an idempotency key.

A @Transactional method failed halfway, but part of the data was committed anyway. Why? Senior

Almost always one of three causes: the method threw a checked exception (Spring commits for those by default), it caught the exception itself so the proxy saw a normal return, or it was called from another method in the same class, which bypasses the proxy so there is no transaction at all.

Check first: set logging.level.org.springframework.transaction=DEBUG to see whether a transaction started and whether it rolled back, then read the code for the three patterns (also private or final methods, and objects not managed by Spring). Fix: rollbackFor = Exception.class for checked exceptions, rethrow after logging, and move the inner method into another bean. Prevent: an integration test against a real database that forces a failure and asserts nothing was persisted. Details in the Spring rollback question above.

Remember: checked exception, swallowed exception, or self-invocation: those are the three reasons a rollback does not happen.

Files.lines must be...?Closed (try-with-resources); it holds a file handle.
ByteBuffer flip?Switch from writing to reading: limit=position, position=0.
Atomic file publish?Write temp file, then Files.move with ATOMIC_MOVE.
serialVersionUID?Class version id; if absent it is computed and changes easily.
Safest serialization approach?Do not deserialize untrusted Java objects; use JSON or Protobuf.
Externalizable needs?Public no-arg constructor, plus readExternal and writeExternal.
