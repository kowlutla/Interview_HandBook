Mental model: the 7 ideas everything hangs on

One line: threads share one heap, so every shared mutable variable needs a rule that makes writes atomic (all or nothing), visible (other threads see them) and ordered (not reordered unexpectedly). Locks, volatile, atomics and immutability are the four ways to give that rule.
  1. Shared heap, private stacks. Each thread has its own stack (local variables are safe). Objects on the heap can be reached by many threads. Trouble only starts with shared and mutable state.
  2. Three separate problems. Atomicity (an operation cannot be seen half done), visibility (a write by one thread is seen by another) and ordering (the order you wrote is the order others see). Different tools fix different ones.
  3. CPUs and the JIT reorder and cache. Without a rule, a thread may keep a value in a register or cache and never see another thread's update.
  4. Happens-before is the rule. The Java Memory Model says: if action A happens-before B, then B sees everything A did. Locks, volatile, thread start/join and executors create these edges.
  5. Prefer not sharing. Immutable objects, thread confinement (ThreadLocal, one owner) and message passing (queues) avoid locks entirely.
  6. Threads are a limited, costly resource. A platform thread is an OS thread with about 1 MB stack. Pools bound them. Virtual threads (Java 21) make blocking cheap.
  7. Concurrency bugs hide. They appear under load, on other hardware, once a week. So you design for correctness, test with stress, and know how to read a thread dump.

1. Threads: the basics

What is the difference between a process and a thread? Basic

What the interviewer is testing: the basic model, and why threads are both cheap and dangerous.

A process is a running program with its own private memory space. A thread is a path of execution inside a process. All threads in one process share the same heap and open files, but each has its own stack and program counter. Because they share memory, threads talk to each other easily and are cheaper to create and switch than processes. The price is that they can corrupt each other's data, so you need synchronization. Processes are isolated: one crash does not kill the others, and they talk through pipes, sockets or files. A Java application is one process (one JVM), and inside it you have many threads, for example your main thread, GC threads, JIT compiler threads and your request threads.

Likely follow-ups
  • What does a context switch cost? The OS saves registers and swaps stacks, and caches go cold. It costs microseconds, so thousands of busy threads waste CPU.
  • How much memory does a thread take? A platform thread reserves about 1 MB of stack by default on 64-bit Linux (-Xss), though it is committed lazily.
Describe the thread lifecycle and the states in Thread.State. Basic

What the interviewer is testing: can you read a thread dump. The states are exactly what jstack prints.

There are six states. NEW: the object exists but start() has not been called. RUNNABLE: running, or ready to run and waiting for a CPU. Java does not separate "running" from "ready". A thread blocked in native socket IO also shows RUNNABLE, which surprises people. BLOCKED: waiting to enter a synchronized block because another thread holds the monitor. WAITING: waiting with no timeout for another thread's action, after Object.wait(), Thread.join() or LockSupport.park(). TIMED_WAITING: the same but with a timeout, like sleep(ms), wait(ms), join(ms). TERMINATED: the run() method finished or threw. A terminated thread cannot be restarted; calling start() again throws IllegalThreadStateException.

Likely follow-ups
  • Why is a thread waiting on a ReentrantLock shown as WAITING and not BLOCKED? Because it parks through LockSupport, not through the monitor.
  • Can a thread go from WAITING to BLOCKED? Yes: after notify, the waiter must reacquire the monitor, and if someone holds it, it is BLOCKED.
What are the ways to create and run a thread in Java? Basic

What the interviewer is testing: basics, and whether you know raw threads are rarely the right answer.

The classic ways: extend Thread and override run(); pass a Runnable to a Thread constructor (preferred, since it separates the task from the thread and does not use up your single inheritance); or implement Callable when you need a result. In real code you almost never call new Thread. You submit tasks to an ExecutorService or use CompletableFuture, so a pool controls how many threads exist. Since Java 21 you can also start virtual threads with Thread.ofVirtual().start(r) or Thread.startVirtualThread(r).

Thread t = new Thread(() -> System.out.println("hi"), "worker-1");
t.start();

ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> 21 * 2);

Thread v = Thread.ofVirtual().name("v1").start(() -> work());   // Java 21
Likely follow-ups
  • Why prefer Runnable to extending Thread? Composition over inheritance, and the same task can run on any executor.
What happens if you call run() instead of start()? Basic

What the interviewer is testing: a classic that checks you know what start does.

start() asks the JVM to create a new OS-level thread (for a platform thread), and that new thread then calls run(). If you call run() yourself, it is a normal method call on the current thread. Nothing runs in parallel, and you will see the caller's thread name in a stack trace. Also, start() may be called only once per Thread object, while run() can be called many times. This is a favourite source of "my async code is not async" bugs.

What is the difference between Runnable and Callable, and what is a Future? Basic

What the interviewer is testing: task abstractions and result handling.

Runnable.run() returns nothing and cannot throw checked exceptions. Callable<V>.call() returns a value and may throw any exception. When you submit either to an executor you get a Future, which is a handle to a result that is not ready yet. get() blocks until the task finishes and returns the value, or throws ExecutionException wrapping what the task threw. get(timeout, unit) adds a timeout. cancel(true) tries to cancel and interrupts the running thread. isDone() and isCancelled() poll the state. The weakness of plain Future is that you cannot chain actions or react without blocking; that is why CompletableFuture exists.

Future<String> f = pool.submit(() -> fetch(url));
try {
    String body = f.get(2, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    f.cancel(true);              // interrupt the worker
} catch (ExecutionException e) {
    throw e.getCause() == null ? e : new RuntimeException(e.getCause());
}
Likely follow-ups
  • What does submit(Runnable) return from get()? null.
  • What is FutureTask? A class that is both Runnable and Future; executors wrap your task in one.
What is a daemon thread? Basic

What the interviewer is testing: JVM shutdown rules, and a common cause of "my app will not exit".

The JVM exits when all non-daemon (user) threads have finished. Daemon threads are background helpers, like the garbage collector, and they do not keep the JVM alive. When the last user thread ends, daemon threads are simply stopped in the middle, with no finally blocks guaranteed to run. So never do work that must complete (writing a file, committing) in a daemon thread. You must call setDaemon(true) before start(), otherwise it throws IllegalThreadStateException. A new thread inherits the daemon flag from its parent. Executor threads from Executors.newFixedThreadPool are non-daemon, so forgetting shutdown() can keep the JVM running. All virtual threads are always daemon.

Likely follow-ups
  • How do I make a pool use daemon threads? Pass a custom ThreadFactory that sets the flag.
What is the difference between sleep() and wait()? Basic

What the interviewer is testing: monitor semantics. This is among the most asked Java concurrency questions.

Thread.sleep(ms) is a static method on Thread. It pauses the current thread for a time and keeps any locks it holds. It wakes when the time is over or when interrupted. Object.wait() is an instance method of Object. The thread must already hold that object's monitor (be inside synchronized(obj)), otherwise you get IllegalMonitorStateException. wait() releases the monitor and parks the thread in the object's wait set until another thread calls notify or notifyAll on the same object, or a timeout or interrupt happens. When it wakes it must reacquire the monitor before continuing. So sleep is "pause for time", wait is "pause until a condition might be true". Because of that, wait is always used with a condition in a loop.

  • Why is wait defined on Object, not Thread? Because the monitor belongs to the object; every object can be a condition-queue.
What does join() do, and how does it relate to happens-before? Basic

What the interviewer is testing: coordination, plus the hidden memory-visibility guarantee.

t.join() makes the calling thread wait until thread t has terminated. join(ms) waits at most that long. Internally it waits on the Thread object itself, which is why you should never use a Thread object as your own lock. Join also gives a memory guarantee: everything the finished thread wrote happens-before the return from join, so the caller sees all those writes without extra synchronization. The same is true of start(): what you wrote before t.start() is visible to t. In modern code, join is mostly replaced by Future.get(), CountDownLatch or CompletableFuture.allOf.

Thread a = new Thread(() -> result = compute());
a.start();
a.join();                // after this line, 'result' is safely visible
System.out.println(result);
How does thread interruption work, and how should you handle InterruptedException? Intermediate

What the interviewer is testing: cooperative cancellation. Wrong handling is one of the most common bugs in code review.

Java has no safe way to force-stop a thread. Interruption is a polite request. t.interrupt() sets the thread's interrupt flag. If the thread is in a blocking call such as sleep, wait, join or a BlockingQueue.take(), that call throws InterruptedException and clears the flag. If it is running normal code, nothing happens until the code checks Thread.currentThread().isInterrupted(). Thread.interrupted() is a static check that also clears the flag. Good handling is either to let the exception propagate (declare throws), or, if you cannot, to restore the flag with Thread.currentThread().interrupt() so callers up the stack can see it. Never swallow it with an empty catch: it hides a shutdown request, and the pool can then never stop.

while (!Thread.currentThread().isInterrupted()) {
    try {
        Job j = queue.take();            // blocks, throws on interrupt
        process(j);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // restore the flag
        break;                                 // and stop
    }
}
Likely follow-ups
  • Is blocking on synchronized interruptible? No. Use lock.lockInterruptibly() when you need that.
  • Does blocking socket IO react to interrupt? Classic InputStream reads do not; close the socket instead. NIO channels and virtual threads do react.
Common mistakes: catch (InterruptedException e) {}, or logging and carrying on in a loop that will then spin forever.
Why are Thread.stop(), suspend() and resume() deprecated, and how do you stop a thread properly? Intermediate

What the interviewer is testing: safe termination design.

stop() throws ThreadDeath inside the target thread at any point, which releases all its monitors immediately, even when it was halfway through updating a data structure. Other threads then see broken, half-updated objects. suspend() freezes a thread while it still holds locks, which easily deadlocks. They have been deprecated since Java 1.2, and Thread.stop() throws UnsupportedOperationException from Java 20. The right way is cooperative: use the interrupt flag, or a volatile boolean running flag that the loop checks, and let the thread clean up and exit by itself. For pools, use shutdown() then awaitTermination(), and shutdownNow() as the last resort, which interrupts workers.

What happens when a thread throws an uncaught exception? Intermediate

What the interviewer is testing: error handling across threads, a frequent production blind spot.

The exception cannot cross threads, so it does not reach the thread that started it. For a plain Thread, the JVM calls its UncaughtExceptionHandler; by default that prints the stack trace to stderr and the thread dies. Other threads continue. In an executor it depends on how you submit. execute(Runnable) lets the exception reach the worker's handler, the worker thread dies and the pool creates a replacement. submit(...) catches the exception and stores it in the returned Future, so if you never call get(), the failure is silently lost. In CompletableFuture, an exception completes the future exceptionally and also disappears if nobody handles it. Defensive habits: set a default handler with Thread.setDefaultUncaughtExceptionHandler, wrap task bodies in try/catch that logs, and always consume futures.

Do thread priorities and Thread.yield() help? Intermediate

What the interviewer is testing: whether you know scheduling is up to the OS and cannot be relied on for correctness.

Priorities (1 to 10) are only hints. Linux often ignores them for normal threads, so you cannot use them to enforce order or to avoid starvation. Thread.yield() is also a hint that the current thread is willing to give up the CPU; the scheduler may ignore it. Neither guarantees anything, so correct programs must work under any scheduling order. Use proper synchronization (locks, latches, queues) for ordering. The rare legit use of yield or Thread.onSpinWait() (Java 9) is in busy-wait loops inside low-level lock-free code.

2. Monitors, volatile and the Java Memory Model

What does synchronized do? What is a monitor or intrinsic lock? Basic

What the interviewer is testing: the foundation: mutual exclusion plus visibility.

Every Java object has a hidden lock called its monitor or intrinsic lock. synchronized makes a thread acquire that lock before running the block and release it on exit, even if an exception is thrown. Only one thread can hold a given monitor at a time, others wait and show as BLOCKED. That gives you mutual exclusion (only one thread in the critical section). It also gives visibility: when a thread releases the monitor, all its writes are flushed, and the next thread that acquires the same monitor sees them. The word "same" matters: two threads locking different objects do not protect each other. Synchronized does not give fairness, a timeout, or interruptibility; for those you need ReentrantLock.

class Counter {
    private int n;
    public synchronized void inc() { n++; }      // locks 'this'
    public synchronized int get() { return n; }  // reads must lock too!
}
Likely follow-ups
  • Do reads need synchronized too? Yes, if writes use it; otherwise the reader may see a stale value.
  • What does the bytecode use? monitorenter and monitorexit for blocks; a flag ACC_SYNCHRONIZED for methods.
What is the difference between a synchronized instance method, a static synchronized method and a synchronized block? Basic

What the interviewer is testing: which lock object is used. Mixing them up gives silent races.

A synchronized instance method locks this, so two different objects of the same class do not block each other. A static synchronized method locks the Class object (Foo.class), one lock for the whole class. An instance method and a static method therefore use different locks and can run at the same time. A synchronized block lets you pick the lock explicitly and protect only the small part that needs it. Best practice is a private final lock object, so outside code cannot lock it by accident and cause deadlocks or contention.

private final Object lock = new Object();
void update() {
    prepare();                       // no lock held here
    synchronized (lock) { shared++; }
}
static synchronized void a() { }     // lock: Foo.class
synchronized void b() { }            // lock: this  (a and b can overlap)
Common mistakes: locking on a string literal, a boxed Integer or an object that is reassigned. Strings are interned and shared across libraries; boxed values may be cached; a reassigned field means threads lock different objects.
What does "reentrant" mean for a lock? Basic

What the interviewer is testing: why a synchronized method can call another synchronized method of the same object without deadlock.

A reentrant lock lets the thread that already owns it acquire it again. The lock keeps an owner and a hold count. Each acquire adds one, each release subtracts one, and the lock is really free only when the count returns to zero. Without this, a synchronized method that calls another synchronized method on the same object would block on itself forever. Both synchronized and ReentrantLock are reentrant. The practical risk with ReentrantLock is forgetting that you locked twice and unlocking only once; getHoldCount() helps debugging.

synchronized void outer() { inner(); }   // fine: same thread, same monitor
synchronized void inner() { }
What does volatile guarantee, and what does it not? Basic

What the interviewer is testing: the most misunderstood keyword in Java.

A write to a volatile variable is immediately visible to any thread that later reads it, and the JVM may not reorder ordinary reads and writes across it in a harmful way. More exactly, the volatile write happens-before every later read of that variable, and everything the writer did before the write is visible to the reader after the read. So it is perfect for a status flag (volatile boolean running) or for safely publishing an object reference. What it does not give is atomicity of compound actions. count++ on a volatile int is still read, add, write: two threads can both read 5 and both write 6, losing an update. For that, use AtomicInteger, LongAdder or a lock. A volatile also makes 64-bit long and double reads and writes atomic.

volatile boolean running = true;
void worker() { while (running) { doWork(); } }   // sees the change
void stop()   { running = false; }               // visible to worker

volatile int hits;
void bad() { hits++; }                           // NOT atomic: lost updates
Likely follow-ups
  • Without volatile, can the loop above run forever? Yes. The JIT may hoist the read of running out of the loop, so the thread never re-reads it.
  • Does volatile on an array reference make the elements volatile? No, only the reference.
Volatile versus synchronized: when is each enough? Intermediate

What the interviewer is testing: choosing the lightest correct tool.

Use volatile when one thread writes a single variable and others only read it, or when every write is an independent value that does not depend on the old value, like a flag, a config reference swapped as a whole, or a "ready" marker. Use synchronized (or a lock) when several variables must change together as one unit (an invariant like low <= high), or when the new value depends on the old one (counters, check-then-act). Volatile never blocks, so it is cheaper, but it cannot make two actions one atomic step. Synchronized gives both atomicity and visibility but can block and contend.

Explain atomicity, visibility and ordering with a small example each. Intermediate

What the interviewer is testing: a clean mental model. Strong candidates separate these three.

Atomicity: an operation happens as one indivisible step. i++ is three steps (read, add, write), so two threads can interleave and lose an increment. Visibility: a write by thread A becomes seen by thread B. If A sets done = true in a plain field, B may loop forever because it kept an old copy in a register or cache. Ordering: the program order you wrote may not be the order other threads observe. The compiler and CPU may reorder independent statements. If thread A does data = 42; ready = true; thread B might see ready == true but data == 0. Synchronized fixes all three. Volatile fixes visibility and ordering but not atomicity of compound actions. Atomics fix atomicity and visibility for a single variable.

int data; boolean ready;               // plain fields: broken
// A: data = 42; ready = true;
// B: if (ready) print(data);          // may print 0 !
// fix: make 'ready' volatile. The write to data happens-before the volatile
//      write, so B sees 42 after it reads ready == true.
What is the Java Memory Model? Senior

What the interviewer is testing: can you reason about correctness without knowing the hardware.

The JMM (JSR-133, Java 5) is the part of the language spec that defines which values a read of a shared variable is allowed to see. It exists because real machines have store buffers, caches and out-of-order execution, and compilers reorder code. Rather than describe hardware, the JMM defines a partial order called happens-before. If write W happens-before read R, then R must see W or a later write. If there is no happens-before between a write and a read of the same variable, that is a data race, and the read may see any older or newer value, including stale ones. The JMM guarantees that a program with no data races behaves as if threads ran in some interleaving in program order (sequential consistency for data-race-free programs). So the working rule is: protect every shared variable with locks or volatile, then you can forget about reordering.

Likely follow-ups
  • What is "out-of-thin-air" value? A read returning a value no thread ever wrote; the JMM forbids it for normal fields.
  • What did Java 5 change? Before, volatile did not prevent reordering with normal accesses and double-checked locking was broken.
List the happens-before rules you rely on. Senior

What the interviewer is testing: concrete knowledge of what creates visibility.

Each rule says "A happens-before B", so B sees A's effects:

  • Program order: within one thread, each action happens-before the next one in code order.
  • Monitor lock: unlock of a monitor happens-before every later lock of the same monitor.
  • Volatile: a write to a volatile variable happens-before every later read of it.
  • Thread start: t.start() happens-before any action in t.
  • Thread end: every action in t happens-before another thread returns from t.join() or sees t.isAlive() == false.
  • Interrupt: calling interrupt() happens-before the interrupted thread detects it.
  • Final fields: the end of a constructor happens-before the first read of the object's final fields (if this does not escape).
  • Transitivity: if A before B and B before C, then A before C.
  • Library rules: submitting a task to an executor happens-before the task runs; a task's result happens-before Future.get() returns; putting into a concurrent collection or queue happens-before the matching get or take; countDown() happens-before the matching await() returns.
Can the compiler or CPU reorder my code? Give an example where it hurts. Senior

What the interviewer is testing: understanding why unsynchronized code is wrong even if "it works on my machine".

Yes. The compiler, the JIT and the CPU may reorder or cache operations as long as the result is the same for a single thread (the "as-if-serial" rule). Other threads can notice the difference. Example: with x = 1; y = 2; a second thread might see y == 2 while x == 0. Another: a loop while (!done) { } can be rewritten as if (!done) while (true) { }, because the JIT sees nothing in the loop that changes done. Also, partially constructed objects: obj = new Foo() is allocate, run constructor, assign reference, and the last two may swap, so another thread can see a non-null reference to an unfinished object. That last one is exactly what breaks unsafe double-checked locking. Memory barriers inserted for volatile, synchronized and atomics are what stop these.

What is safe publication, and how do final fields help? Senior

What the interviewer is testing: why immutable objects are special, and how object sharing goes wrong.

Publishing means making an object reachable by other threads. It is safe when the publishing action creates a happens-before edge to the readers. Safe ways: assign it to a volatile field or an AtomicReference; assign it inside a synchronized block (readers also lock); store it in a concurrent collection or hand it over through a BlockingQueue; or initialize it in a static initializer (class loading is thread-safe). If you just assign to a plain field, another thread can see the reference but stale or default values in the object's fields. Final fields have a special guarantee: once a constructor finishes, any thread that sees the reference also sees the final fields' correct values and everything reachable through them, even without synchronization. So an immutable object (all final fields, no leaked this) is safe to publish by plain assignment. Never let this escape from a constructor, for example by registering a listener or starting a thread there.

Explain double-checked locking. Why is volatile needed? Senior

What the interviewer is testing: a classic that combines lazy initialization with the memory model.

The goal is lazy creation of a singleton while avoiding a lock on every call. First check without lock: if the instance is not null, return it. Only if null, enter a synchronized block and check again (the second check, because another thread may have created it while we waited), then create it. Without volatile, instance = new Foo() can be reordered so the reference becomes visible before the constructor finished. A second thread passes the first check, sees a non-null but half-built object and uses it. Since Java 5, declaring the field volatile forbids that reordering and fixes the pattern. In practice, simpler alternatives are better: the holder-class idiom or an enum.

class Config {
    private static volatile Config instance;      // volatile is essential
    static Config get() {
        Config c = instance;                       // one volatile read
        if (c == null) {
            synchronized (Config.class) {
                c = instance;
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }
}
Are reads and writes of long and double atomic? Senior

What the interviewer is testing: a detail from the language spec that shows depth.

The spec says reads and writes of a plain (non-volatile) long or double are allowed to be done as two separate 32-bit operations. So a reader could see the high half of one write and the low half of another, a "torn" value. In practice, 64-bit JVMs on modern hardware do this atomically, but the spec only guarantees it when the variable is volatile. References and 32-bit primitives are always read and written atomically (only the single read or write, not x++). To be correct and portable, mark shared longs and doubles volatile or use AtomicLong.

How do wait(), notify() and notifyAll() work? Why must wait be in a loop? Intermediate

What the interviewer is testing: the classic condition-wait pattern and its pitfalls.

Every object has a monitor with an entry queue (threads wanting the lock) and a wait set (threads that called wait()). Inside synchronized, a thread whose condition is not true calls wait(): it releases the monitor and joins the wait set. Another thread changes the state and calls notify() (wakes one waiter) or notifyAll() (wakes all). Woken threads must still reacquire the monitor, so they run one after the other. You must always check the condition in a while loop, never an if, for three reasons: spurious wakeups (the JVM may wake a waiter for no reason), another thread may have already consumed the state before you got the lock, and with notifyAll several waiters wake but only one condition is satisfied. Also, always change the state before notifying, and do both under the same lock.

synchronized (lock) {
    while (queue.isEmpty()) {        // while, never if
        lock.wait();
    }
    item = queue.poll();
}
// producer
synchronized (lock) {
    queue.add(x);
    lock.notifyAll();
}
Likely follow-ups
  • notify or notifyAll? Prefer notifyAll unless all waiters are identical and one wake-up is enough. A lone notify can wake the wrong thread and cause a lost signal.
  • What is a lost wake-up? Notify happened before the waiter started waiting. The loop with a condition check prevents it.
How is synchronized implemented, and is it slow? Senior

What the interviewer is testing: whether you still believe the old "synchronized is slow" myth.

Each object has a header word that holds lock state. When a lock is uncontended, HotSpot uses a cheap lightweight lock: one compare-and-swap that stores a pointer in the header. When contention appears, the lock is inflated to a full monitor object that uses OS support to park and wake threads. Parking is the expensive part (microseconds), so the real cost of synchronized is contention, not the keyword itself. The JIT also helps: it removes locks on objects that never escape a thread (lock elision via escape analysis) and merges neighbouring locks (lock coarsening). Biased locking, which made single-thread access nearly free, was disabled by default in JDK 15 and removed later. Since Java 6, synchronized and ReentrantLock perform about the same in most workloads; pick on features, not speed.

3. Race conditions, deadlock, livelock, starvation

What is a race condition, and how is it different from a data race? Intermediate

What the interviewer is testing: precise vocabulary and the two main patterns.

A race condition is a logic bug: the result depends on the timing of threads. The two usual patterns are check-then-act (if (!map.containsKey(k)) map.put(k, v): another thread can insert between the check and the put) and read-modify-write (count++). A data race is a memory-model term: two threads access the same variable, at least one writes, and there is no happens-before between them. You can have a race condition without a data race (every single access is synchronized, but the sequence of two calls is not atomic), and a data race that happens to be harmless. The fix for a race condition is to make the whole compound action atomic: one lock around both steps, an atomic method such as putIfAbsent or merge, or a CAS loop.

// race condition even with a thread-safe map:
if (!map.containsKey(k)) { map.put(k, expensive()); }

// fixed, atomic:
map.computeIfAbsent(k, key -> expensive());
Show me exactly how count++ loses an update, and give three fixes. Basic

What the interviewer is testing: the standard demo of atomicity.

count++ compiles to three steps: load the field, add one, store it. If thread A loads 5, then thread B loads 5, both add one and both store 6. Two increments produced one. Fixes: (1) make the method synchronized (or use a lock); simple and correct, some contention. (2) Use AtomicInteger.incrementAndGet(), which uses a hardware compare-and-swap, no lock. (3) For very high contention counters that are read rarely, use LongAdder, which spreads updates over several cells. Volatile alone is not a fix.

AtomicInteger count = new AtomicInteger();
count.incrementAndGet();

LongAdder hits = new LongAdder();
hits.increment();            // many threads
long total = hits.sum();     // approximate while updating
What is a deadlock? What conditions are needed, and how do you prevent it? Intermediate

What the interviewer is testing: theory plus practical prevention.

A deadlock is when two or more threads each hold a resource and wait for one held by another, so nobody ever proceeds. It needs four conditions together: mutual exclusion (the resource is exclusive), hold and wait (hold one, ask for another), no preemption (you cannot take a lock by force) and circular wait (a cycle of waiting). Break any one and deadlock is impossible. The most practical fix is to break circular wait with a global lock order: always take locks in the same order, for example by account id. Others: use tryLock(timeout) and back off (breaks hold and wait), take only one lock at a time, hold locks for short times and never call unknown code (callbacks, overridable methods) while holding a lock, or use higher-level structures such as concurrent collections.

Likely follow-ups
  • Can a single thread deadlock? Not with reentrant locks. It can with a non-reentrant lock, or by waiting on a task queued behind itself in a single-thread pool.
  • Does a database deadlock look the same? Same idea; the DB detects it and kills one transaction. A JVM does not detect it automatically.
How do you detect a deadlock in a running JVM? Intermediate

What the interviewer is testing: practical diagnosis skill.

Take a thread dump with jstack <pid> or jcmd <pid> Thread.print (or kill -3 <pid> on Linux, which prints to stdout). For locks from synchronized and java.util.concurrent ownable locks the dump ends with a section "Found one Java-level deadlock", listing each thread, the lock it waits for and who owns it. In code, ThreadMXBean.findDeadlockedThreads() returns the ids of deadlocked threads (it covers both monitors and ownable synchronizers), so a health-check thread can log or alert. VisualVM and JConsole have a "Detect Deadlock" button. Deadlocks on plain wait/notify missing signals are not "found" by this check; you recognise them as threads WAITING forever with nobody to notify them.

ThreadMXBean mx = ManagementFactory.getThreadMXBean();
long[] ids = mx.findDeadlockedThreads();
if (ids != null) {
    for (ThreadInfo ti : mx.getThreadInfo(ids, true, true)) log.error("{}", ti);
}
What are livelock and starvation? Intermediate

What the interviewer is testing: the other liveness failures, not only deadlock.

In a livelock threads are not blocked; they keep running and reacting to each other, but make no progress. The picture is two people in a corridor who both step aside the same way, again and again. In code, two threads each use tryLock, fail, release and retry at the same moment forever. It shows as high CPU with no progress. Fix with random back-off or a fixed order. Starvation is when a thread is ready but never gets the resource, for example low-priority threads when greedy ones keep taking the lock, or a reader-preferring read-write lock where writers wait forever, or an unfair lock under constant load. Fixes: fair locks (new ReentrantLock(true)), bounded work per thread, separate pools so slow tasks cannot starve fast ones, and not holding locks for long.

Write code that transfers money between two accounts without deadlock. Senior

What the interviewer is testing: lock ordering, tie-breaking and thinking about edge cases (same account).

The naive version locks from then to. If thread 1 transfers A to B while thread 2 transfers B to A, they deadlock. The fix is to lock in a fixed global order, here by a unique id. If ids can tie (or you have no ids), use System.identityHashCode and a separate "tie-breaker" lock for the rare collision. Also handle from == to, which would otherwise lock the same lock twice (fine for reentrant locks, but check anyway).

void transfer(Account from, Account to, long amt) {
    Account first  = from.id < to.id ? from : to;
    Account second = first == from ? to : from;
    synchronized (first) {
        synchronized (second) {
            if (from.balance < amt) throw new IllegalStateException("funds");
            from.balance -= amt;
            to.balance   += amt;
        }
    }
}
Likely follow-ups
  • What if the lock order is hidden across two services? Then use timeouts with tryLock and retry, or redesign so one owner serializes the operations (a queue).

4. Locks, atomics and ThreadLocal

What does ReentrantLock give you that synchronized does not? Intermediate

What the interviewer is testing: whether you pick the right tool and use it safely.

ReentrantLock is an explicit lock with extra abilities: tryLock() and tryLock(time, unit) to avoid waiting forever, lockInterruptibly() so a waiting thread can be cancelled, an optional fair mode that serves threads in arrival order, multiple Condition objects per lock, and diagnostics such as isLocked(), getQueueLength(). The price is that you must unlock yourself, and always in a finally, otherwise an exception leaves the lock held forever. Synchronized releases automatically, is simpler and cannot be forgotten. Default to synchronized for simple cases; move to ReentrantLock when you need timeouts, interruption, fairness or several conditions.

private final ReentrantLock lock = new ReentrantLock();
void update() {
    lock.lock();
    try {
        // critical section
    } finally {
        lock.unlock();         // always in finally
    }
}
boolean tryIt() throws InterruptedException {
    if (!lock.tryLock(200, TimeUnit.MILLISECONDS)) return false;
    try { return work(); } finally { lock.unlock(); }
}
Common mistakes: putting lock() inside the try block (if lock fails, finally unlocks a lock you do not hold); unlocking from a different thread.
What is a fair lock and why is it not the default? Intermediate

What the interviewer is testing: throughput versus fairness trade-off.

A fair lock gives the lock to the longest-waiting thread. A non-fair lock lets a newly arriving thread "barge in" and grab the lock if it happens to be free at that moment. Barging is faster, because the waiting thread must be woken up (slow) while the arriving thread is already running on a CPU. With a fair lock there is more parking and unparking, so throughput is often several times lower. Fairness prevents starvation, but it only guarantees order of lock acquisition, not that the scheduler runs threads fairly. synchronized is not fair. The default non-fair lock is right unless you have measured starvation.

What is a Condition, and why use it over wait/notify? Intermediate

What the interviewer is testing: modern wait-notify and bounded buffer design.

A Condition is created from a lock (lock.newCondition()) and gives await(), signal() and signalAll(), which play the roles of wait, notify and notifyAll. The big advantage is that one lock can have several independent wait queues. In a bounded buffer you keep notFull and notEmpty, so producers wake only consumers and the other way, instead of waking everybody with notifyAll. It also offers awaitNanos, awaitUninterruptibly, and timeouts. The same rules as before apply: hold the lock when calling await/signal, and wait in a while loop because of spurious wakeups.

lock.lock();
try {
    while (count == items.length) notFull.await();
    items[put] = x; put = (put + 1) % items.length; count++;
    notEmpty.signal();
} finally { lock.unlock(); }
How does ReentrantReadWriteLock work, and when does it hurt? Intermediate

What the interviewer is testing: when more locks are not better.

It holds a pair: a read lock shared by many readers, and a write lock exclusive. While readers hold it, other readers can enter, but a writer must wait. While a writer holds it, everyone waits. It pays off when reads are much more frequent than writes and each read takes real time (reading a large in-memory table). When the critical section is tiny, a plain lock is often faster, because the read lock itself does an atomic update of a shared counter and cache line, so many readers still contend. Rules: a thread holding the write lock can take the read lock (downgrade is allowed), but a thread holding the read lock cannot upgrade to write; trying that deadlocks. A steady stream of readers can starve a writer in non-fair mode.

rw.readLock().lock();
try { return map.get(k); } finally { rw.readLock().unlock(); }
// write
rw.writeLock().lock();
try { map.put(k, v); } finally { rw.writeLock().unlock(); }
What is StampedLock and its optimistic read? Senior

What the interviewer is testing: Java 8 lock with a different style and sharp edges.

StampedLock (Java 8) returns a long "stamp" with each lock call. Its special feature is the optimistic read: tryOptimisticRead() returns a stamp without locking anything. You read the fields into locals, then call validate(stamp). If no writer got in meanwhile, the data you read is consistent and you paid almost nothing. If validation fails, you fall back to a real read lock and read again. This beats a read-write lock when reads dominate and are short. Limits: it is not reentrant, it has no Condition, you must pass the stamp back to unlock, and optimistic reads can see inconsistent values until validated, so you must copy to locals and never act on them before validate.

long s = sl.tryOptimisticRead();
double x = this.x, y = this.y;          // copy to locals
if (!sl.validate(s)) {
    s = sl.readLock();
    try { x = this.x; y = this.y; } finally { sl.unlockRead(s); }
}
return Math.hypot(x, y);
What is CAS (compare-and-swap), and how do atomic classes use it? Intermediate

What the interviewer is testing: lock-free basics.

CAS is a single CPU instruction: "if the memory holds expected value E, set it to N, and tell me whether it worked". It is atomic in hardware. AtomicInteger and friends build on it with a retry loop: read the current value, compute the new one, try compareAndSet(old, new); if another thread changed it in between, the CAS fails and you loop again with fresh data. No thread ever blocks or holds a lock, so a slow thread cannot stop others (this is called lock-free). Under high contention many CAS attempts fail and waste CPU, which is why LongAdder exists. Modern JDKs implement incrementAndGet as a single hardware fetch-and-add on x86, not a loop. Since Java 9 VarHandle exposes CAS, with finer memory-ordering modes, on any field.

AtomicInteger max = new AtomicInteger();
void update(int v) {
    int cur;
    do { cur = max.get(); if (v <= cur) return; }
    while (!max.compareAndSet(cur, v));       // retry if someone raced us
}
// Java 8+: max.accumulateAndGet(v, Math::max);
What is the ABA problem, and how do you solve it? Senior

What the interviewer is testing: the weak spot of CAS.

CAS only checks "is the value still equal to what I read?". If it changed from A to B and back to A, CAS succeeds although things happened in between. For a counter that does not matter. For pointer-based structures it can be a real bug: in a lock-free stack, thread 1 reads top = A and next = B, gets paused. Thread 2 pops A, pops B, pushes A back (with a different next). Thread 1 resumes, CAS sees top still A and succeeds, setting top to the stale B, which is no longer in the stack. Fix by adding a version: AtomicStampedReference pairs the reference with an int stamp that you increment on each change, so CAS compares both. AtomicMarkableReference uses a boolean mark. In garbage-collected Java ABA is much rarer than in C, because a node cannot be freed and re-used while someone still references it, but it is still possible when you recycle objects or use values like integers.

AtomicStampedReference<Node> top = new AtomicStampedReference<>(null, 0);
int[] h = new int[1];
Node cur = top.get(h);
top.compareAndSet(cur, newNode, h[0], h[0] + 1);
Which atomic classes exist and when would you use each? Intermediate

What the interviewer is testing: breadth of java.util.concurrent.atomic.

AtomicInteger, AtomicLong and AtomicBoolean for single counters and flags. AtomicReference<V> for swapping an immutable object as a whole, such as a config snapshot. AtomicIntegerArray and friends for arrays of atomic cells. AtomicIntegerFieldUpdater to update a volatile field of existing objects without an extra wrapper object per instance (saves memory in big collections). AtomicStampedReference and AtomicMarkableReference against ABA. LongAdder, LongAccumulator, DoubleAdder for heavily contended statistics. A good pattern is an AtomicReference to an immutable object: build the new object, then updateAndGet(old -> old.with(...)). The function must be side-effect free because it can run more than once.

Why is LongAdder faster than AtomicLong under contention? Senior

What the interviewer is testing: contention and cache-line thinking.

With AtomicLong, all threads CAS the same memory location. Each success invalidates that cache line on other cores and most CASes fail and retry, so throughput stops scaling. LongAdder keeps a base value and, once it detects contention, an array of cells. Each thread hashes to its own cell and increments it with its own CAS, so threads rarely collide. The cells are padded (using @Contended) so each lives on a separate cache line. sum() adds base plus all cells. The trade-off: sum() is not an atomic snapshot (concurrent updates may be missed), it uses more memory, and you cannot do compare-and-set on it. So use it for metrics, hit counters and statistics, and use AtomicLong when you need exact values with conditional updates, like sequence generators or limits.

Likely follow-ups
  • Is ConcurrentHashMap.size() related? Yes, it uses the same striped-counter idea internally.
What is ThreadLocal, and when is it useful? Intermediate

What the interviewer is testing: thread confinement and the correct use of per-thread state.

A ThreadLocal<T> gives each thread its own independent copy of a variable. Each Thread object holds a small map from ThreadLocal to value, so get() reads the map of the current thread, with no locking. Good uses: per-thread non-thread-safe helpers such as a SimpleDateFormat (although DateTimeFormatter is thread-safe and better), per-request context in a servlet thread (user id, trace id, security context, MDC for logging), and per-thread random or buffer objects. Initialize with ThreadLocal.withInitial(() -> new Foo()). Its weaknesses: values are hidden global state that is hard to follow, they do not automatically move to other threads (async tasks lose them), and in thread pools they leak.

private static final ThreadLocal<Context> CTX = new ThreadLocal<>();
void handle(Request r) {
    CTX.set(new Context(r.user()));
    try { service.run(); }
    finally { CTX.remove(); }       // essential in pools
}
How can ThreadLocal cause a memory leak? Senior

What the interviewer is testing: a well-known production leak, and the internals behind it.

Inside each thread, the ThreadLocalMap holds entries whose key is a weak reference to the ThreadLocal object but whose value is a strong reference. If the ThreadLocal object becomes unreachable (for example when a web app is redeployed), the key is cleared but the value stays strongly reachable from the thread. In a pool the worker threads live as long as the server, so those values live forever, and so does the class loader that loaded their classes: a class-loader leak that fills up metaspace on every redeploy. Even without redeploys, you leak between requests: a pooled thread keeps the previous request's data (a security hole if user context is not cleared) and large buffers stay allocated per thread. Java does sweep stale entries during later set/get calls, but only some of the time, which is not a guarantee. The fix is discipline: always call remove() in a finally, wrap task execution in a decorator that clears it, avoid storing big objects, and prefer passing explicit parameters or, in Java 21+, ScopedValue (preview in 21, final in 25).

Does a ThreadLocal value reach child threads or async tasks? Senior

What the interviewer is testing: context propagation, a very common bug with MDC, security context and tenant ids.

No. A plain ThreadLocal is private to the thread. InheritableThreadLocal copies the parent's value to a child thread at the moment of creation, but pools create threads once and reuse them, so later tasks see stale or missing values. For executors you must propagate context yourself: capture the value in the submitting thread, set it inside the task and clear it after (a wrapping Runnable). Spring offers TaskDecorator and Micrometer's context-propagation library does this generically for MDC and security. In Java 21+ with structured concurrency and ScopedValue, bindings are inherited by child tasks automatically within a scope. With virtual threads, ThreadLocal still works, but remember there may be millions of threads, so per-thread caches become expensive.

5. Thread safety design

What does "thread-safe" mean, and what strategies make code thread-safe? Intermediate

What the interviewer is testing: design thinking, in order of preference.

A class is thread-safe if it behaves correctly when used by many threads, with no extra synchronization by the callers. Strategies, from best to worst: (1) Do not share: keep state in local variables, so each thread has its own. (2) Immutability: objects that never change can be shared freely. (3) Thread confinement: only one thread ever touches the object (ThreadLocal, an actor or single-thread executor). (4) Use safe building blocks: concurrent collections, atomics, queues. (5) Guard shared mutable state with locks, and document which lock guards which field (@GuardedBy). Keep the critical sections small and never call foreign code while holding a lock. Also remember that thread-safe parts do not make a thread-safe whole: two atomic calls in a row are not atomic together.

Likely follow-ups
  • Is a stateless Spring singleton bean thread-safe? Yes, as long as it has no mutable fields. Adding a mutable field to a singleton is a common bug.
How do you make a class immutable, and why does it help concurrency? Intermediate

What the interviewer is testing: the recipe and the subtle traps.

An immutable object cannot change after construction, so threads can share it with no locks and no visibility problems (final fields are also safely published). The recipe: make the class final (or all constructors private) so no subclass can add mutable state; make all fields private final; provide no setters; do not let this escape in the constructor; and make defensive copies of mutable inputs (a Date, a List) in the constructor and of mutable outputs in the getters, or hold unmodifiable types such as List.copyOf. Since Java 16 a record gives you final fields and accessors with one line, but its components are only shallowly immutable: a record holding an ArrayList is not safe. To "change" an immutable object you create a new one, which pairs well with AtomicReference. String, boxed numbers, LocalDate and BigDecimal are immutable.

public record Range(int lo, int hi, List<String> tags) {
    public Range {
        if (lo > hi) throw new IllegalArgumentException();
        tags = List.copyOf(tags);         // defensive, immutable copy
    }
}
Common mistakes: final List field and thinking the list is immutable (only the reference is final); exposing the internal array from a getter.
What are the thread-safe ways to write a singleton? Intermediate

What the interviewer is testing: several valid answers and their trade-offs.

Option 1: eager static field. private static final Foo INSTANCE = new Foo(); Class loading is thread-safe, so it is simple, but created even if never used. Option 2: initialization-on-demand holder. A private static nested class holds the instance, and is only loaded (and so created) on the first call of getInstance(). It is lazy, lock-free and correct, and is my default choice. Option 3: enum singleton, which also survives serialization and reflection attacks. Option 4: double-checked locking with a volatile field. Works but is the most code. Option 5: synchronized getInstance(): correct and simple but locks on every call. In a Spring or CDI app, you usually let the container manage singletons and do not write any of this.

public final class Registry {
    private Registry() {}
    private static class Holder { static final Registry I = new Registry(); }
    public static Registry get() { return Holder.I; }   // lazy, thread-safe
}
enum Cache { INSTANCE; /* fields, methods */ }
What is false sharing? Senior

What the interviewer is testing: hardware awareness for high-performance code.

CPUs move memory in cache lines, usually 64 bytes. If two threads write to two different variables that sit on the same cache line, each write invalidates the other core's copy of the whole line, so the line bounces between cores although the threads never touch the same variable. Performance can drop several times. Example: an array of long counters, one per thread; neighbours share a line. Fixes: pad the data so hot fields are on separate lines (manually with unused long fields, or the JDK internal @Contended annotation, which for user code needs -XX:-RestrictContended), or give each thread its own object, or use LongAdder which already pads its cells. You only worry about this after profiling shows contention on hot counters, queues' head and tail indexes, or ring buffers (LMAX Disruptor pads for this reason).

How do you reduce lock contention? Senior

What the interviewer is testing: performance reasoning beyond "add synchronized".

First measure: a thread dump or profiler shows where threads wait. Then, in rough order of payoff: hold locks for less time (move IO, logging, and computation outside the critical section); lock splitting (separate locks for independent state, instead of one big lock); lock striping (an array of locks chosen by hash, like the old ConcurrentHashMap segments); replace locks with atomics or concurrent collections; use read-write locks or StampedLock for read-heavy data; use copy-on-write for rarely changing data; and use thread confinement or per-thread aggregation merged at the end (the LongAdder idea). Sometimes the best fix is architectural: partition the data so each worker owns a shard and no locking is needed.

6. Executors and thread pools

Why use a thread pool instead of creating threads? Basic

What the interviewer is testing: the reasons behind the Executor framework.

Creating a platform thread is expensive: the OS allocates a stack (about 1 MB reserved) and kernel structures, which takes tens to hundreds of microseconds. Unlimited threads also exhaust memory and make the scheduler thrash. A pool reuses a fixed set of workers, so you pay the creation cost once and you put an upper limit on concurrency. It also separates what to run (a task) from how to run it (the policy: how many threads, which queue, what to do when full), and gives you lifecycle control (shutdown), results via Future, and a place to add monitoring and naming. Since Java 21 virtual threads change the picture for blocking IO, but pools remain right for CPU-bound work and for limiting access to a resource.

Explain how ThreadPoolExecutor works: core size, max size, queue. In which order are they used? Intermediate

What the interviewer is testing: the single most common pool question. Most people get the order wrong.

The constructor takes corePoolSize, maximumPoolSize, keepAliveTime, a BlockingQueue, a ThreadFactory and a RejectedExecutionHandler. When a task arrives: (1) if fewer than core threads are running, start a new thread, even if others are idle. (2) Otherwise try to put the task in the queue. (3) Only if the queue is full, start extra threads up to the maximum. (4) If you are at max and the queue is full, the rejection policy runs. So threads beyond core are created only when the queue is full, not when it is non-empty. With an unbounded queue, the queue never fills, so the pool never grows beyond core and max is meaningless. Threads above core that stay idle longer than keepAliveTime are removed. allowCoreThreadTimeOut(true) lets core threads time out too.

Likely follow-ups
  • How does a worker get tasks? Each worker loops on queue.take() (or poll(keepAlive) for extra threads) and runs them.
  • What does prestartAllCoreThreads() do? Starts all core workers up front.
Which queue would you choose for a pool, and what are the effects? Intermediate

What the interviewer is testing: the queue decides the pool's behaviour under load.

Unbounded LinkedBlockingQueue (used by fixed pools): never rejects, so under overload the queue and memory grow until OutOfMemoryError, and latency climbs without limit; max threads is ignored. ArrayBlockingQueue or bounded LinkedBlockingQueue: gives back-pressure; when full, extra threads (up to max) start and then the rejection policy fires. Usually the best production choice. SynchronousQueue (used by cached pools): no storage; every task needs a free thread right away or a new thread is created, so it grows up to max (unbounded for cached). PriorityBlockingQueue: run important tasks first, but it is unbounded and starvation of low priority is possible. DelayQueue underlies scheduled executors. A bounded queue plus CallerRunsPolicy is a simple way to slow producers down.

What are the rejection policies, and which would you use? Intermediate

What the interviewer is testing: overload handling, a sign of production experience.

A task is rejected when the pool is shut down, or when both the queue and the max threads are full. Four built-in handlers: AbortPolicy (default) throws RejectedExecutionException, so the caller knows. CallerRunsPolicy runs the task in the submitting thread, which slows the producer down naturally (back-pressure), but blocks the caller, which may be a request or event-loop thread. DiscardPolicy silently drops the new task. DiscardOldestPolicy drops the oldest queued task and retries the new one. Silent discard is dangerous unless the task is truly optional (metrics, caches warmup). For important work, abort and return "server busy" (HTTP 503 or 429), or use caller-runs for internal pipelines. You can also write your own handler that logs, counts, and blocks briefly by putting into the queue with a timeout.

new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),
    new NamedThreadFactory("orders"),
    new ThreadPoolExecutor.CallerRunsPolicy());
What is wrong with the Executors factory methods? Intermediate

What the interviewer is testing: why many style guides (and the Alibaba and Sonar rules) ban them.

newFixedThreadPool(n) and newSingleThreadExecutor() use an unbounded LinkedBlockingQueue: a slow downstream makes the queue grow until OutOfMemoryError, with no back-pressure. newCachedThreadPool() uses a SynchronousQueue and max threads of Integer.MAX_VALUE: a burst or a slow call makes it create thousands of threads and exhaust memory or hit the OS thread limit. newScheduledThreadPool also has an unbounded queue and effectively fixed core. All use default thread names (pool-3-thread-1), which makes thread dumps hard to read, and default AbortPolicy. Better: construct ThreadPoolExecutor directly with a bounded queue, a named ThreadFactory, a deliberate rejection policy, and metrics. Spring's ThreadPoolTaskExecutor does this with properties. For simple, short-lived tools they are fine.

How do you size a thread pool for CPU-bound versus IO-bound work? Senior

What the interviewer is testing: a reasoned estimate, then measurement.

For CPU-bound tasks (computation, no waiting), more threads than cores only add context switches, so use about cores or cores + 1. For IO-bound tasks (database, HTTP calls), threads spend most time waiting, so you can run more. The classic formula is threads = cores * (1 + wait / compute). If a task waits 90 ms and computes 10 ms, then wait/compute = 9, and with 8 cores you get about 80 threads. Treat it as a starting point and then load-test. Also respect downstream limits: a pool of 80 against a database connection pool of 20 only builds a queue at the connection pool. Another way is Little's law: concurrency = throughput * latency. For 500 requests per second at 200 ms latency you need about 100 requests in flight. Use separate pools for CPU and IO work, and for slow and fast dependencies (the bulkhead pattern), so one slow service cannot eat every thread. Read cores with Runtime.availableProcessors(), which is container-aware in modern JDKs (since 10).

What is the difference between execute() and submit(), and between shutdown() and shutdownNow()? Basic

What the interviewer is testing: exception behaviour and clean shutdown.

execute(Runnable) is from Executor, returns nothing and lets an exception reach the thread's uncaught handler. submit accepts Runnable or Callable, returns a Future, and captures any exception inside that future. shutdown() is graceful: the pool accepts no new tasks but finishes the running and queued ones. shutdownNow() stops accepting, tries to interrupt running tasks, and returns the list of tasks that never started. Neither blocks, so call awaitTermination(timeout) after. The standard pattern is shutdown, wait, then shutdownNow if the wait timed out. From Java 19 ExecutorService is AutoCloseable, and close() does exactly that, so try-with-resources works.

pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();
    pool.awaitTermination(5, TimeUnit.SECONDS);
}
// Java 19+: try (var ex = Executors.newFixedThreadPool(4)) { ... }
What do invokeAll, invokeAny and ExecutorCompletionService do? Intermediate

What the interviewer is testing: handling many tasks without writing manual loops.

invokeAll(tasks) runs a collection of Callables and blocks until all complete, returning a list of Futures in the same order. invokeAny(tasks) returns the result of the first task that completes successfully and cancels the rest, useful for querying redundant replicas. A plain loop over future.get() in submission order waits for slow early tasks even if later ones finished. ExecutorCompletionService wraps an executor and puts finished futures on a queue, so take() returns them in completion order. That is the right tool when you want to process results as soon as each arrives. Both have timeout variants.

Can a thread pool deadlock itself? Senior

What the interviewer is testing: "thread starvation deadlock", a subtle real-world failure.

Yes. If a task running in a pool submits another task to the same pool and waits for its result, and all threads are occupied by such waiting parent tasks, the child tasks sit in the queue and nothing can run them. With a single-thread executor this happens with one nested call. With a pool of 10 it happens when 10 parents run together. A thread dump shows every worker WAITING in Future.get and the queue full. Fixes: use separate pools for parent and child tasks, make the first stage asynchronous with CompletableFuture composition instead of blocking in get, use a bounded wait with a timeout, or use ForkJoinPool, which can run child tasks on the waiting thread (helping).

Why give pool threads names, and how do you do it? Intermediate

What the interviewer is testing: operational awareness.

When you read a thread dump, pool-7-thread-3 tells you nothing, while order-service-io-3 tells you which component is stuck. Names also appear in logs and profilers. You supply a ThreadFactory that sets the name, the daemon flag and an uncaught exception handler. Guava has ThreadFactoryBuilder and Spring has CustomizableThreadFactory, or you write six lines yourself. You should also expose pool metrics (active threads, queue size, completed tasks, rejections) to your monitoring, because queue growth is the earliest warning of overload.

AtomicInteger n = new AtomicInteger();
ThreadFactory tf = r -> {
    Thread t = new Thread(r, "orders-io-" + n.incrementAndGet());
    t.setDaemon(false);
    t.setUncaughtExceptionHandler((th, ex) -> log.error("died {}", th.getName(), ex));
    return t;
};
How does ScheduledExecutorService work, and what is the difference between fixed rate and fixed delay? Intermediate

What the interviewer is testing: the replacement for Timer, and its gotchas.

A scheduled pool keeps tasks in a DelayedWorkQueue ordered by next run time, and workers sleep until the head task is due. schedule(task, delay) runs once. scheduleAtFixedRate(task, initial, period) starts runs at fixed times: 0, P, 2P, and so on. If a run takes longer than the period, the next one starts as soon as it finishes (runs never overlap, but they bunch up to catch up). scheduleWithFixedDelay(task, initial, delay) waits a fixed delay after the previous run ends, so the gap is always at least the delay; better for polling and cleanup. The big gotcha: if a periodic task throws an exception, all future runs are silently cancelled. Always wrap the body in try/catch. The old java.util.Timer has one thread and dies completely on an uncaught exception, so avoid it.

ScheduledExecutorService s = Executors.newScheduledThreadPool(2);
s.scheduleWithFixedDelay(() -> {
    try { cleanup(); }
    catch (Exception e) { log.error("cleanup failed", e); }   // keep it alive
}, 0, 30, TimeUnit.SECONDS);
How does ForkJoinPool work, and what is work stealing? Senior

What the interviewer is testing: divide-and-conquer pools and why they are different from a normal pool.

ForkJoinPool (Java 7) is built for tasks that split into smaller subtasks (RecursiveTask returns a value, RecursiveAction does not). A task calls fork() to schedule a subtask and join() to get its result. Each worker thread has its own double-ended queue (deque). It pushes and pops its own tasks at one end (cheap, no contention). An idle worker steals from the other end of a busy worker's deque, which balances the load without a central queue. When a task calls join(), the worker does not sit idle: it runs other tasks meanwhile. The recipe is: if the problem is small, solve directly (a threshold); otherwise split in two, fork one half, compute the other directly, then join. It suits CPU-bound, non-blocking work. Blocking inside tasks starves the pool unless you use ForkJoinPool.managedBlock.

Likely follow-ups
  • What is the common pool? ForkJoinPool.commonPool(), a shared JVM-wide pool with parallelism cores minus one, used by parallel streams and by default by CompletableFuture.
What are the pitfalls of parallel streams? Senior

What the interviewer is testing: judgement. Parallel is not automatically faster, and shared pools are dangerous.

list.parallelStream() splits the source and runs on the common ForkJoinPool, shared by the whole JVM, with parallelism of about cores minus one (the calling thread helps too). Pitfalls: (1) Blocking IO inside the pipeline (HTTP, DB calls) holds common-pool threads. Other parallel streams and default CompletableFutures in the same JVM then slow down or stall. (2) Small data or cheap operations are slower, because splitting and merging cost more than the work. Rule of thumb: needs many thousands of elements or heavy per-element work. (3) Poor sources split badly: LinkedList, Stream.iterate, and ordered operations like limit or findFirst are expensive in parallel. ArrayList, arrays and ranges split well. (4) Shared mutable state in lambdas (adding to an ArrayList, incrementing a counter) is a race; use collect or reduce. (5) Operations must be stateless, associative and non-interfering. (6) Thread-local or transactional context does not propagate to common-pool threads. If you really need isolation, run the stream inside your own ForkJoinPool (pool.submit(() -> stream.parallel()...).get()), which works in practice though it is an implementation detail rather than a documented guarantee. For IO, prefer an explicit executor or virtual threads.

// BAD: race on a non-thread-safe list
List<Integer> out = new ArrayList<>();
ids.parallelStream().forEach(i -> out.add(i * 2));

// GOOD
List<Integer> out2 = ids.parallelStream().map(i -> i * 2).collect(Collectors.toList());
How does Spring @Async choose its executor, and what can go wrong? Senior

What the interviewer is testing: framework-level concurrency in daily work.

With @EnableAsync, a call to an @Async method returns at once and the body runs on a TaskExecutor. Without configuration, plain Spring Framework falls back to SimpleAsyncTaskExecutor, which creates a new thread per call with no limit. Spring Boot auto-configures a ThreadPoolTaskExecutor (since Boot 2.1) with core 8 and an unbounded queue, so max is never used and a slow backend means the queue grows until memory runs out. Define your own bean with bounded queueCapacity, a rejection policy and a thread name prefix, and name it in @Async("ioExecutor"). Other traps: @Async works through a proxy, so calling the method from the same class (self-invocation) runs it synchronously; the method must be public; exceptions in a void method need an AsyncUncaughtExceptionHandler; the transaction, security context and MDC do not move to the new thread. Spring Boot 3.2 with Java 21 can switch to virtual threads with spring.threads.virtual.enabled=true.

7. CompletableFuture

What is CompletableFuture, and what does it add over Future? Intermediate

What the interviewer is testing: async composition basics (Java 8).

Future only lets you wait. CompletableFuture (Java 8) is a Future and a CompletionStage: you attach callbacks that run when the result arrives, build pipelines, combine several futures, handle errors, and complete it manually with complete(v) or completeExceptionally(e). This lets you write non-blocking code like "fetch the user, then fetch their orders, then render", without a thread sitting in get(). Starting points are supplyAsync(supplier), runAsync(runnable) and completedFuture(value). Java 9 added orTimeout, completeOnTimeout and delayedExecutor.

CompletableFuture<String> cf = CompletableFuture
    .supplyAsync(() -> userClient.get(id), ioPool)
    .thenApply(User::name)
    .orTimeout(2, TimeUnit.SECONDS)
    .exceptionally(ex -> "unknown");
What is the difference between thenApply, thenCompose and thenCombine? Intermediate

What the interviewer is testing: the map versus flatMap distinction, asked in almost every CompletableFuture interview.

thenApply(fn) is like map: fn takes the result and returns a plain value; you get CompletableFuture<U>. If fn itself returns a CompletableFuture, you would get a nested CompletableFuture<CompletableFuture<U>>. thenCompose(fn) is like flatMap: fn takes the result and returns another CompletableFuture, and the result is flattened. Use it for dependent async steps, where the second call needs the first call's result. thenCombine(other, fn) runs two independent futures in parallel and merges both results. thenAccept consumes the result and returns Void; thenRun ignores the result.

CompletableFuture<Order> o = getUser(id).thenCompose(u -> getLastOrder(u));  // dependent
CompletableFuture<Page>  p = userF.thenCombine(adsF, Page::new);              // independent
Which thread runs my CompletableFuture stage? What do the Async variants mean? Senior

What the interviewer is testing: the hidden threading rules, the source of many production stalls.

supplyAsync(s) without an executor runs on ForkJoinPool.commonPool() (or, if the machine has fewer than 2 cores, a new thread per task). The same pool is used by parallel streams, so blocking calls there are harmful. Always pass your own executor for IO. For the follow-up stages: thenApply(fn) runs on whichever thread completes the previous stage, or, if it was already complete when you attach it, on the calling thread. That can be surprising: a heavy thenApply may run on your Netty or Tomcat thread. thenApplyAsync(fn) always submits fn to the common pool, and thenApplyAsync(fn, executor) to your executor. So use the Async version with an explicit executor when the step is slow or when you must leave a latency-sensitive thread. Cheap, non-blocking transformations are fine with the non-async variants.

Likely follow-ups
  • Does cancelling a CompletableFuture stop the running code? No. cancel only completes the future exceptionally; the running task is not interrupted.
How do you handle exceptions in a CompletableFuture chain? Intermediate

What the interviewer is testing: exception wrapping and recovery methods.

An exception in a stage completes that stage exceptionally, and every dependent stage is skipped and completes exceptionally too, until a handler turns it into a normal value. The exception is usually wrapped in a CompletionException (in the dependent stages), and get() wraps it in ExecutionException while join() throws CompletionException (unchecked). Handlers: exceptionally(ex -> fallback) recovers only on failure. handle((value, ex) -> ...) sees both outcomes and returns a new value. whenComplete((v, ex) -> ...) observes both but does not change the result (good for logging; the exception still flows on). exceptionallyCompose (Java 12) recovers with another async call. Unwrap with ex.getCause() when you check the type. If nobody attaches a handler or calls get/join, the failure is silent.

cf.thenApply(this::parse)
  .handle((v, ex) -> {
      if (ex != null) {
          Throwable root = ex instanceof CompletionException ? ex.getCause() : ex;
          log.warn("failed", root);
          return Defaults.EMPTY;
      }
      return v;
  });
How do you run many calls in parallel and wait for all of them? Intermediate

What the interviewer is testing: fan-out/fan-in, a normal service requirement.

CompletableFuture.allOf(f1, f2, ...) returns a CompletableFuture<Void> that completes when all inputs complete (or fails if any failed, after all have finished). It does not give the values, so you then call join() on each original future, which is now instant. anyOf(...) completes with the first result. Always add a timeout (orTimeout) and decide per call whether a failure should fail everything or be replaced by a default. Do not start the futures inside a sequential stream that joins each one, because that serializes them.

List<CompletableFuture<Price>> fs = shops.stream()
    .map(s -> CompletableFuture.supplyAsync(() -> s.price(item), ioPool)
                 .completeOnTimeout(Price.NONE, 1, TimeUnit.SECONDS))
    .toList();                                          // all started now
CompletableFuture.allOf(fs.toArray(new CompletableFuture[0])).join();
List<Price> prices = fs.stream().map(CompletableFuture::join).toList();
What are common CompletableFuture mistakes in production code? Senior

What the interviewer is testing: hard-won experience.

(1) Blocking calls on the default common pool; one slow HTTP client freezes unrelated work. (2) Calling join() or get() inside another stage, which blocks a pool thread and can cause starvation deadlock. (3) No timeout: a hung dependency leaves futures pending forever and pins resources. (4) Swallowed exceptions: futures never read and no handler. (5) Assuming context follows: MDC, security and transaction do not follow into async stages. (6) Using thenApply for an async step and ending with nested futures. (7) Assuming cancel(true) interrupts the work. (8) Unbounded fan-out: starting 10,000 futures at once on an unbounded executor, which overloads the downstream. Limit with a bounded pool or a Semaphore. (9) Heavy work inside thenApply on a latency-critical thread. Keep each stage small, name your executors and add metrics.

8. Synchronizers and concurrent collections

What is a CountDownLatch, and how does it differ from CyclicBarrier? Intermediate

What the interviewer is testing: two similar classes with different purposes.

CountDownLatch(n) starts with a count. Threads call countDown() to decrease it; threads that called await() are blocked until the count reaches zero, then released. It is one-shot: it cannot be reset. The usual uses are "main waits for N workers to finish" and a "start gate" (count 1) that releases all workers at once. In the first case the counting threads and waiting threads are different groups. CyclicBarrier(parties) is the opposite: all parties threads call await() and block until the last arrives; then all continue together, and the barrier resets automatically for the next round. It can run an optional barrier action once per round. It fits phased parallel algorithms ("everyone finish step 1, then start step 2"). If one waiting thread is interrupted or times out, the barrier is "broken" and the others get BrokenBarrierException.

What is a Semaphore, and where would you use it? Intermediate

What the interviewer is testing: limiting concurrent access, a common design need.

A Semaphore holds a number of permits. acquire() takes a permit and blocks if none is left. release() returns one. It limits how many threads use a resource at the same time, for example a pool of 10 database connections, at most 5 concurrent calls to a fragile partner API, or a cap on in-flight tasks to protect memory. With one permit it acts like a lock, but unlike a lock any thread may release, not just the owner, and it is not reentrant. tryAcquire(timeout) lets you fail fast, which is how you do a simple bulkhead. Always release in a finally. Fair mode is optional. With virtual threads, a Semaphore is the standard way to cap concurrency, because you no longer limit it with pool size.

Semaphore gate = new Semaphore(5);
void call() throws InterruptedException {
    if (!gate.tryAcquire(100, TimeUnit.MILLISECONDS)) throw new BusyException();
    try { partner.invoke(); } finally { gate.release(); }
}
What are Phaser and Exchanger? Senior

What the interviewer is testing: breadth beyond the two famous synchronizers.

Phaser (Java 7) is a reusable barrier with a dynamic number of parties and numbered phases. Threads can register() and arriveAndDeregister() while it runs, arriveAndAwaitAdvance() waits for the others, and you can override onAdvance to run code per phase or to terminate. It also supports tiering for huge groups. Use it when the number of participants changes, which a CyclicBarrier cannot handle. Exchanger<V> is a meeting point for exactly two threads: each calls exchange(myObject), blocks until the other arrives, and they swap objects. A classic use is double buffering: a filler thread and a drainer thread swap a full buffer for an empty one. Both are rarely needed in application code, so a short, correct description is enough in an interview.

How does ConcurrentHashMap achieve thread safety, and how is it different from Hashtable and synchronizedMap? Senior

What the interviewer is testing: one of the top three Java concurrency questions.

Hashtable and Collections.synchronizedMap use one lock for every operation, so all threads queue up, and iterating still needs manual locking. ConcurrentHashMap (CHM) in Java 7 used 16 lock segments. Since Java 8 there are no segments: the table is an array of bins, an empty bin is filled with a CAS, and when the bin already has nodes, the thread takes a synchronized lock on the first node of that bin only. So writers to different bins never block each other, and reads are lock-free (nodes use volatile fields). Long collision chains (8 or more) turn into red-black trees, as in HashMap. The size is kept in striped counters, so size() is an estimate under concurrent change. Iterators are weakly consistent: they never throw ConcurrentModificationException and may or may not show updates made after they were created. CHM forbids null keys and values, because get returning null would be ambiguous between "absent" and "mapped to null" in a concurrent setting. Atomic methods: putIfAbsent, computeIfAbsent, compute, merge, replace. Keep compute functions short and never update the same map inside them.

Likely follow-ups
  • Is if (!map.containsKey(k)) map.put(k, v) safe on CHM? No: two calls are not atomic. Use putIfAbsent or computeIfAbsent.
  • Why did concurrent resize break old HashMap? In Java 7 two threads resizing could create a cyclic chain and make get loop forever; do not use HashMap across threads. See Java: Collections for the map internals.
When use Collections.synchronizedList, CopyOnWriteArrayList, or something else? Intermediate

What the interviewer is testing: choosing a thread-safe collection by access pattern.

Collections.synchronizedList wraps every method in one lock. Individual calls are safe, but iterating, or check-then-act sequences, still need you to lock the list yourself, otherwise ConcurrentModificationException or lost updates happen. CopyOnWriteArrayList copies the whole array on every write, and iterators work on an immutable snapshot, so reads and iteration need no lock and never fail. It is ideal for read-mostly, small lists, like a listener list. It is terrible for frequent writes, because each add is O(n) and creates garbage. For queues use ConcurrentLinkedQueue (lock-free, unbounded) or a BlockingQueue. For sorted maps use ConcurrentSkipListMap. For maps use ConcurrentHashMap. For a set, ConcurrentHashMap.newKeySet() or CopyOnWriteArraySet. For simply passing work between threads, a queue is better than any shared list.

What is a BlockingQueue, and which implementations exist? Intermediate

What the interviewer is testing: the standard hand-off structure between threads.

A BlockingQueue is a thread-safe queue whose put() blocks when it is full and take() blocks when it is empty; there are also offer/poll with timeouts, and non-blocking variants that return false or null. This gives you producer-consumer with no wait/notify code, and a bounded queue gives back-pressure, since fast producers are slowed down. Types: ArrayBlockingQueue (bounded, one lock, optional fairness); LinkedBlockingQueue (optionally bounded, two locks so put and take run in parallel); PriorityBlockingQueue (unbounded, ordered); DelayQueue (items become available after a delay); SynchronousQueue (zero capacity, a direct hand-off); LinkedTransferQueue (transfer() waits until a consumer takes the item); LinkedBlockingDeque. A hand-off between threads also creates happens-before: what the producer did before put is visible after the consumer's take.

How do you stop consumers of a blocking queue cleanly? Intermediate

What the interviewer is testing: shutdown design for pipelines.

A consumer blocked in take() will wait forever if no more items arrive. Two standard ways. The poison pill: the producer puts a special sentinel object at the end (one per consumer). When a consumer takes it, it stops (and for several consumers, each one must get its own pill, or the consumer re-puts it). The second way is interruption: call shutdownNow() on the executor, so take() throws InterruptedException, and the consumer exits. Pills drain the queue first, so no work is lost. Interrupt is faster but abandons whatever is still queued. Use poll(timeout) in the consumer loop if you also want a periodic check on a stop flag.

What is the difference between ConcurrentLinkedQueue and LinkedBlockingQueue? Intermediate

What the interviewer is testing: non-blocking versus blocking queues.

ConcurrentLinkedQueue is unbounded and lock-free (CAS-based, the Michael-Scott algorithm). poll() returns null at once when empty and there is no blocking take. It scales well when many threads contend, and is good when consumers have other work to do and just check. Its size() is O(n). LinkedBlockingQueue uses locks, can be bounded, and offers blocking put/take. It is the natural choice for worker pools and producer-consumer where consumers should sleep when idle and producers need back-pressure. If you need blocking with low latency across many cores, LinkedTransferQueue is a mix.

9. Virtual threads and modern concurrency

What are virtual threads (Java 21), and why were they added? Intermediate

What the interviewer is testing: the biggest concurrency change in Java in years (JEP 444, final in Java 21 LTS).

A virtual thread is a java.lang.Thread that is managed by the JVM, not by the OS. It is very cheap: it starts with a small stack that lives on the heap and grows as needed, so you can have millions. The JVM runs virtual threads on a small pool of normal threads called carrier threads (a ForkJoinPool with parallelism equal to the CPU count by default). When code in a virtual thread does a blocking call (socket read, sleep, BlockingQueue.take, a lock from java.util.concurrent), the JVM unmounts it: its stack is saved on the heap and the carrier is free to run another virtual thread. When the call can continue, the thread is mounted again, maybe on another carrier. The reason: the old "one thread per request" style is simple to write and debug but limited to a few thousand threads, while async or reactive code scales but is hard to write and read. Virtual threads give the simple blocking style with the scale of async. Your code stays the same: you only change how threads are created.

try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        ex.submit(() -> { Thread.sleep(Duration.ofSeconds(1)); return fetch(); });
    }
}   // close() waits for all tasks

Thread t = Thread.ofVirtual().name("v-", 0).start(() -> handle(req));
Likely follow-ups
  • Are virtual threads faster? Not for one request; they raise throughput when work is mostly waiting. For CPU-bound work they give nothing.
  • Are they daemon threads? Always, and they have a fixed priority.
When should you use virtual threads, and when not? Senior

What the interviewer is testing: judgement, not enthusiasm.

Use them for server code that handles many concurrent tasks that mostly wait on IO: REST services calling databases and other services, fan-out calls, crawlers, message handlers. One thread per task, plain blocking code. In Spring Boot 3.2+ you enable it with spring.threads.virtual.enabled=true. Do not use them for CPU-bound work (a fixed-size pool of about core-count threads is right); for code that needs thread-bound pooling of expensive objects; or when a library pins carriers (see the next question). Rules of thumb: never pool virtual threads, create one per task, since they are cheap like objects. Limit concurrency with a Semaphore, not pool size, because the pool no longer protects your database or the partner API from 10,000 simultaneous calls; your connection pool is still limited. Avoid heavy ThreadLocal use (millions of copies), and remember code that assumed "pool of 20 threads means 20 concurrent calls" may suddenly overload something.

What is pinning of virtual threads, and how do you find and avoid it? Senior

What the interviewer is testing: a real limitation that shows up in production, and version awareness.

A virtual thread is pinned when it cannot unmount while blocking, so it holds its carrier thread hostage. In Java 21 to 23 this happens when it blocks inside a synchronized block or method (the monitor is tied to the carrier's stack), or while a native method or foreign call is on its stack. Pinning is not a bug but it kills scalability: a handful of pinned threads that block on slow IO can take all carriers, and the app freezes even though CPU is idle. Java 24 (JEP 491) removed most monitor pinning, so synchronized no longer pins in the typical case; native frames still pin. Detection: run with -Djdk.tracePinnedThreads=full (Java 21) or record the JFR event jdk.VirtualThreadPinned. Mitigation on 21: replace long-blocking synchronized sections with ReentrantLock, which unmounts properly, and upgrade old JDBC drivers and libraries that use synchronized around IO. Short synchronized sections that do not block are harmless.

How do thread dumps and monitoring change with virtual threads? Senior

What the interviewer is testing: operational readiness.

A classic jstack dump lists only platform threads, so you will not see your million virtual threads, and that is intentional. To get them, use jcmd <pid> Thread.dump_to_file -format=json file.json, which includes virtual threads, grouped by their container. Thread names are empty by default, so give them names. Stack traces of virtual threads are normal, and exceptions look the same. Tools such as profilers and JFR support them (JFR has events for start, end and pinning). Metrics that counted pool threads no longer reflect load; track in-flight requests, semaphore permits in use and downstream latencies instead.

What is structured concurrency, and what is its status? Senior

What the interviewer is testing: awareness of where the language is going, and honesty about preview features.

Structured concurrency treats a group of related subtasks as one unit of work with a clear scope, like a block of code: subtasks started in a scope must finish before the scope exits. This fixes problems with free-running futures: thread leaks (a failed sibling leaves others running), forgotten cancellation, and unclear ownership. With StructuredTaskScope you fork subtasks (each on a virtual thread), then join, and the scope policies decide what happens: ShutdownOnFailure cancels the siblings as soon as one fails, ShutdownOnSuccess returns the first success and cancels the rest. It was a preview API in Java 21 (JEP 453), run with --enable-preview, and it was still in preview in later releases (the API was reshaped around a Joiner in Java 25), so confirm the current status before using it in production code. ScopedValue (immutable per-scope data inherited by child tasks) is its companion and became final in Java 25. I would say it as: "a good model to learn and use in new, preview-tolerant code, but not yet something I rely on in a long-lived API."

// Java 21 preview (API shape differs in later versions)
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user  = scope.fork(() -> findUser(id));
    var order = scope.fork(() -> findOrder(id));
    scope.join().throwIfFailed();          // wait; propagate the first failure
    return new View(user.get(), order.get());
}
Reactive programming versus thread-per-request: how do you choose? Senior

What the interviewer is testing: architectural trade-off without dogma.

Thread-per-request is simple: code reads top to bottom, stack traces are meaningful, debugging and ThreadLocal context work. Its limit was the number of OS threads, a few thousand. Reactive (Reactor, RxJava, WebFlux) uses a few event-loop threads and never blocks: you describe a pipeline of operators, and the framework schedules callbacks. It scales to very many connections and gives back-pressure built in, and it suits streaming. The costs are a steep learning curve, hard-to-read stack traces, "one blocking call freezes the event loop", and every library in the chain must be non-blocking. With virtual threads (Java 21) most of the scalability argument for reactive in ordinary request/response services is gone, since you get thousands of cheap threads with plain code. Reactive still wins for real streaming, complex event composition, back-pressure across stages, and where a team already has a mature reactive stack. For a new CRUD-style service on Java 21 I would start with virtual threads.

10. Thread dumps and diagnosing problems

How do you take and read a thread dump? Intermediate

What the interviewer is testing: the number one skill for diagnosing hangs and spikes.

Take it with jstack <pid> or jcmd <pid> Thread.print, or send kill -3 <pid> (output goes to the process's stdout); on Windows use jcmd or Ctrl+Break. Take three dumps, five to ten seconds apart, because one dump is a single moment and you need to see what stays the same. Each thread has a name, state and stack. Read by state: RUNNABLE threads are the CPU users (check whether they are really computing or sitting in socket read). BLOCKED with "waiting to lock <0x...>" shows monitor contention, and the dump names the owner ("locked <0x...>"). WAITING / TIMED_WAITING on parking to wait for are usually idle pool workers, or threads waiting on a lock, a future or a queue. Group the threads by identical stack top: 200 threads in the same method means that is the bottleneck. Look at the end for "Found one Java-level deadlock".

"http-nio-8080-exec-17" #58 prio=5 tid=0x... nid=0x2f1a waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
	at com.shop.PriceCache.get(PriceCache.java:42)
	- waiting to lock <0x00000007a1b2c3d0> (a com.shop.PriceCache)
"http-nio-8080-exec-3" #44 ... RUNNABLE
	at com.shop.PriceCache.reload(PriceCache.java:77)
	- locked <0x00000007a1b2c3d0> (a com.shop.PriceCache)
The JVM is at 100% CPU. How do you find the exact thread and line responsible? Intermediate

What the interviewer is testing: a standard on-call procedure.

(1) Find the process: top, note the pid. (2) Show threads of that process: top -H -p PID and note the thread ids (decimal) with the highest CPU. (3) Convert the id to hex: printf '%x\n' 12345. (4) Take a thread dump with jstack PID and search for nid=0x followed by that hex; that thread's stack shows where it spends time. (5) Repeat a few times to confirm it is not a one-off. Typical causes: an infinite or very long loop, a livelock or spin on a CAS, a regex with catastrophic backtracking, a hot lock spin, or an unbounded recursion. If the hot threads are named like GC Thread or G1 Concurrent, the real problem is memory pressure: check GC logs and heap use (see Java: JVM). For a better view use a sampling profiler, JFR or async-profiler, which show a flame graph over time instead of one moment.

Most request threads are BLOCKED or WAITING and latency is high. What do you check? Senior

What the interviewer is testing: diagnosing contention versus exhaustion.

Group the dump by the top frames. Case 1: many threads BLOCKED on the same monitor and one thread RUNNABLE holding it: a lock held during slow work (IO inside synchronized, a cache reload, big logging). Fix: shrink the critical section or use a concurrent structure. Case 2: all worker threads WAITING or in socket read inside the same client call: a downstream is slow or down, and your pool is exhausted waiting for it. Fix: timeouts everywhere, circuit breaker, bulkhead, a separate pool. Case 3: threads WAITING on a connection pool (HikariPool.getConnection): the DB pool is exhausted, often by a leak or by transactions that call remote services while holding a connection. Case 4: threads waiting on Future.get in the same pool: starvation deadlock. Then correlate with metrics: active threads, queue sizes, DB pool usage and downstream latency percentiles.

Which tools do you use to investigate concurrency problems? Intermediate

What the interviewer is testing: practical toolbox knowledge.

jstack and jcmd Thread.print for dumps. jcmd Thread.dump_to_file for virtual threads (Java 21). JConsole and VisualVM to browse threads, see states and detect deadlocks live. Java Flight Recorder (jcmd PID JFR.start, free in OpenJDK 11+) records lock contention, thread parking, pinning and GC with low overhead; open the file in JDK Mission Control. async-profiler for CPU and lock flame graphs. ThreadMXBean for in-process checks (deadlocks, per-thread CPU time). For correctness bugs: stress tests, jcstress (OpenJDK's concurrency stress harness), repeated runs, and thread-safety annotations with static analysis such as SpotBugs or Error Prone's @GuardedBy checks. Logs with thread names help to follow a request.

How do you test concurrent code? Senior

What the interviewer is testing: realism about how hard this is.

You cannot prove thread safety by testing, but you can find many bugs. Run the code with many threads started together using a CountDownLatch start gate, repeat thousands of times, and check an invariant at the end (for example the sum is exact). Use a small number of iterations of different thread counts, and run on a machine with several cores, because a single core hides races. Use jcstress for memory-model questions. Avoid Thread.sleep in tests to "wait for" async work: use latches, Awaitility, or make the executor injectable and run tasks synchronously in unit tests. Prefer designs that are testable: pure functions, immutable data, small critical sections with explicit locks. Finally, review: most concurrency bugs are found by reading the code and asking "which lock protects this field?"

11. Coding questions

Implement producer-consumer with a BlockingQueue. Basic

What the interviewer is testing: the standard hand-off, shutdown and interrupt handling.

Use a bounded ArrayBlockingQueue so a fast producer cannot fill memory. The producer calls put; the consumer calls take. To stop, the producer sends a poison pill. I keep the interrupt rule: restore the flag and exit.

public class Pipeline {
    private static final String POISON = "__END__";
    public static void main(String[] a) throws Exception {
        BlockingQueue<String> q = new ArrayBlockingQueue<>(10);
        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= 20; i++) q.put("job-" + i);   // blocks if full
                q.put(POISON);
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "producer");
        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    String j = q.take();                          // blocks if empty
                    if (j.equals(POISON)) break;
                    System.out.println("done " + j);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "consumer");
        producer.start(); consumer.start();
        producer.join();  consumer.join();
    }
}
Likely follow-ups
  • Now do it with wait/notify. Write a bounded buffer with synchronized, a while loop on "full" or "empty", and notifyAll after each change, as in the wait/notify question above.
  • Many consumers? Put one pill per consumer.
Print numbers 1 to N alternately from two threads (odd and even). Intermediate

What the interviewer is testing: wait/notify mastery: a shared turn, a loop on the condition, and correct termination.

The two threads share a counter. Each thread waits until it is its turn (the parity of the counter matches), prints, increments, and wakes the other. Key points: the condition in a while loop; notifyAll; and when the counter passes N, the thread that notices must wake the other so it can also exit, or it will wait forever.

class OddEven {
    private int n = 1;
    private final int max;
    OddEven(int max) { this.max = max; }

    void run(boolean odd) throws InterruptedException {
        synchronized (this) {
            while (true) {
                while (n <= max && (n % 2 == 1) != odd) wait();   // not my turn
                if (n > max) { notifyAll(); return; }              // finished: free the other
                System.out.println(Thread.currentThread().getName() + " " + n++);
                notifyAll();
            }
        }
    }
    public static void main(String[] args) {
        OddEven o = new OddEven(10);
        new Thread(() -> { try { o.run(true);  } catch (InterruptedException e) {} }, "odd").start();
        new Thread(() -> { try { o.run(false); } catch (InterruptedException e) {} }, "even").start();
    }
}

A Semaphore version is shorter: two semaphores, one with 1 permit for odd and one with 0 for even; each thread acquires its own, prints, and releases the other's.

Likely follow-ups
  • Extend to three threads printing in rotation? Use the same idea with n % 3, or a chain of three semaphores.
Write a program that deadlocks, then fix it. Intermediate

What the interviewer is testing: that you understand lock order, and can show it.

Two threads take two locks in opposite order. A short sleep between the first and the second lock makes the deadlock appear every time.

Object a = new Object(), b = new Object();
Thread t1 = new Thread(() -> {
    synchronized (a) { sleep(100);
        synchronized (b) { System.out.println("t1 got both"); } }
}, "t1");
Thread t2 = new Thread(() -> {
    synchronized (b) { sleep(100);
        synchronized (a) { System.out.println("t2 got both"); } }   // opposite order
}, "t2");
t1.start(); t2.start();
// jstack shows: "Found one Java-level deadlock"

// FIX 1: both threads lock a first, then b (global order).
// FIX 2: use ReentrantLock.tryLock(timeout) on both and back off if the second fails.

I would add that real deadlocks are rarely this obvious: the two lock acquisitions hide behind method calls and callbacks, which is why a documented lock order and short critical sections matter.

Make three threads run in order: first, second, third. Intermediate

What the interviewer is testing: basic synchronizer use instead of sleep or join hacks.

Use two CountDownLatches (or semaphores). Thread two waits for latch one, thread three waits for latch two. Each thread counts down its latch after finishing. This also gives happens-before between the steps.

CountDownLatch l1 = new CountDownLatch(1), l2 = new CountDownLatch(1);
Runnable first  = () -> { System.out.println("first");  l1.countDown(); };
Runnable second = () -> { await(l1); System.out.println("second"); l2.countDown(); };
Runnable third  = () -> { await(l2); System.out.println("third"); };
// start in any order: output is always first, second, third
Implement a thread-safe rate limiter (token bucket). Senior

What the interviewer is testing: an algorithm plus correct concurrency and time handling.

A token bucket holds up to capacity tokens and refills at a steady rate. A request takes one token; with none it is rejected (or waits). Instead of a refill thread, compute the refill lazily on each call from the time elapsed. Use System.nanoTime() (monotonic, not affected by clock changes). The check, refill and decrement must be one atomic step, so a lock is fine for a single-node limiter. For very high rates, you could keep the state in an AtomicReference of an immutable (tokens, timestamp) pair and CAS it.

public final class TokenBucket {
    private final long capacity;
    private final double refillPerNano;
    private double tokens;
    private long last = System.nanoTime();

    public TokenBucket(long capacity, double ratePerSecond) {
        this.capacity = capacity;
        this.refillPerNano = ratePerSecond / 1_000_000_000.0;
        this.tokens = capacity;
    }
    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) * refillPerNano);
        last = now;
        if (tokens >= 1.0) { tokens -= 1.0; return true; }
        return false;
    }
}
Likely follow-ups
  • Token bucket versus leaky bucket versus sliding window? Token bucket allows bursts up to capacity; leaky bucket smooths output to a constant rate; sliding window is more exact per interval but stores more state.
  • Across many servers? You need shared state, for example Redis with a Lua script, or an API gateway limiter. A JVM-local limiter only limits one instance. Guava's RateLimiter is a ready local option.
Implement a thread-safe bounded (LRU) cache. Senior

What the interviewer is testing: combining a data structure with correct locking, and knowing when to use a library.

LinkedHashMap in access-order mode (third constructor argument true) with an overridden removeEldestEntry is a ready LRU. It is not thread-safe, and note that even get() modifies it (it moves the entry to the end), so a read-write lock does not help: every method must take the same exclusive lock. A simple synchronized wrapper is correct and often fast enough. For heavy concurrent use, do not hand-roll; use Caffeine, which has a high-performance concurrent design with size or time-based eviction and a good admission policy.

public class LruCache<K, V> {
    private final Map<K, V> map;
    public LruCache(final int capacity) {
        this.map = new LinkedHashMap<>(16, 0.75f, true) {          // access order
            @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) {
                return size() > capacity;
            }
        };
    }
    public synchronized V get(K k)            { return map.get(k); }
    public synchronized void put(K k, V v)    { map.put(k, v); }
    public synchronized V computeIfAbsent(K k, Function<K, V> f) {
        return map.computeIfAbsent(k, f);   // atomic with respect to this lock
    }
}
Likely follow-ups
  • How would you avoid one lock? Stripe the cache into several segments by key hash, each with its own lock and LRU.
Write a bounded buffer with ReentrantLock and two Conditions. Senior

What the interviewer is testing: the textbook example of Condition use.

Two conditions give two separate wait queues, so a producer's signal wakes only a consumer, and the reverse. Both waits are in while loops.

class BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    BoundedBuffer(int n) { items = new Object[n]; }

    void put(T x) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();
            items[tail] = x; tail = (tail + 1) % items.length; count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }
    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[head]; items[head] = null;
            head = (head + 1) % items.length; count--;
            notFull.signal();
            return x;
        } finally { lock.unlock(); }
    }
}

12. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview; it shows you work calmly under pressure.

The application stops responding. CPU is near zero, requests time out. What do you do? Senior

What the interviewer is testing: a clear first-response routine for a hang.

Situation: health checks fail, but the process is alive and not using CPU. That points to threads waiting, not computing: a deadlock, an exhausted pool, or everyone waiting for a dead dependency.

Check first: do not restart yet, because a restart destroys the evidence. Take three thread dumps ten seconds apart (jcmd PID Thread.print), plus a quick look at connection pool and GC logs.

Steps:

  1. Search the dump for "Found one Java-level deadlock". If present, you have the two threads, the locks and the code lines.
  2. If not, group by stack top. All HTTP workers in one socket read means a slow or dead dependency. All in getConnection means the DB pool is exhausted. All in a monitor means contention on one lock.
  3. Restore service: restart or fail over after saving the dumps, scale out only if the cause is capacity.
  4. Fix the cause: lock order, timeouts, pool sizes.

Prevent: timeouts on every remote call, circuit breakers, a periodic ThreadMXBean.findDeadlockedThreads check with an alert, named threads, and metrics for pool usage and queue length.

CPU is at 100% on one production instance after a release. How do you find the cause? Senior

What the interviewer is testing: thread-to-line tracing and sensible rollback.

Situation: a recent change correlates with the spike, only some instances are affected, or all.

Check first: is it user code or GC? top -H -p PID shows the hot thread ids. If they are named GC Thread, it is memory pressure, so look at heap and GC logs. If they are application threads, continue.

Steps:

top -H -p 4321                 # hot thread id e.g. 4388
printf '%x\n' 4388             # 1124
jcmd 4321 Thread.print | grep -A 20 'nid=0x1124'

Repeat three times. A stack that always sits in the same loop, a regex Pattern.matches, a HashMap.get spin (a data race on a plain HashMap in older Java) or a CAS retry loop tells you the cause. Consider rollback first if the release is clearly the trigger, then analyse with JFR or async-profiler on a canary.

Prevent: load tests in the pipeline, canary releases, alerts on CPU per instance, and code review for loops with no exit and for shared plain collections.

Every request thread is busy and the service returns 503, but the database looks fine. What happened? Senior

What the interviewer is testing: thread pool exhaustion and cascading failure.

Situation: Tomcat's worker pool (default 200 threads) is full, new requests queue in the accept queue and time out. CPU is low.

Check first: thread dump. In this scenario most worker threads sit in SocketInputStream.read or HttpClient calls to one downstream service, which has become slow (for example 30 s instead of 200 ms). By Little's law, 200 threads at 30 s each handle only about 7 requests per second, so the pool fills quickly.

Steps: confirm with downstream latency metrics. Apply a short timeout and a circuit breaker so that threads are released quickly and fail fast. Give that dependency its own bounded pool or semaphore (bulkhead), so its slowness cannot take all request threads. Return a fallback or cached response.

Prevent: connect and read timeouts on every client (never infinite, which is the default in many clients), a bulkhead per dependency, alerts on the active thread count and downstream p99. With virtual threads, the thread limit moves away, so the semaphore bulkhead becomes essential.

Inventory or counters are slightly wrong under load: updates are lost. Find and fix it. Intermediate

What the interviewer is testing: read-modify-write races at code and database level.

Situation: stock goes below zero, or a counter shows 9,870 after 10,000 increments. It never reproduces on a developer laptop.

Check first: look for a shared field updated by ++, +=, or a pattern "read from map, compute, put back". Check whether the state lives in one JVM (then a lock or atomic fixes it) or in a database or several instances (then the JVM lock is useless).

Steps: in-process: AtomicInteger, LongAdder for stats, map.merge(k, 1, Integer::sum) or a lock around the whole sequence. In the database: do it in one statement (UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0 and check the updated row count), or use optimistic locking with a version column and retry, or pessimistic SELECT ... FOR UPDATE. Across instances, a JVM synchronized does not help at all.

Prevent: write a concurrency test that hammers the operation from many threads and checks the final total; avoid read-then-write in application code when the store can do it atomically.

Memory grows after every redeploy, and users sometimes see another user's data. Suspect ThreadLocal. Senior

What the interviewer is testing: the ThreadLocal in a pool failure, covering both leak and data-bleed.

Situation: two symptoms. (a) Metaspace or heap grows on each hot redeploy of a war on a shared Tomcat until OutOfMemoryError. (b) A request occasionally shows the previous request's tenant or user.

Check first: heap dump (jcmd PID GC.heap_dump), then in a tool such as Eclipse MAT look at what holds the old class loader: the path often goes thread, ThreadLocalMap, entry value. Search the code for ThreadLocal.set with no remove, and for filters or interceptors that set context at the start of a request.

Steps: put set and remove in the same try/finally (a servlet filter or a task decorator), so the thread is clean when it returns to the pool. For user context, treat any leftover value as a security bug. Tomcat itself logs "created a ThreadLocal ... but failed to remove it" on stop, which is a hint. For async tasks propagate context explicitly.

Prevent: a code rule that ThreadLocals are always cleared in finally, a test that runs two requests on one thread, and in Java 21+ consider ScopedValue where available.

Two services update the same two records in opposite order and requests hang or fail with lock timeouts. Senior

What the interviewer is testing: deadlock beyond JVM locks: database rows and distributed locks.

Situation: service A locks account 1 then account 2, service B locks account 2 then account 1, using DB row locks (SELECT FOR UPDATE) or a distributed lock such as Redis. At peak, each holds one and waits for the other. The database kills one with a deadlock error, or a distributed lock without a timeout hangs for ever.

Check first: the database deadlock log (for example MySQL SHOW ENGINE INNODB STATUS or PostgreSQL logs) shows the two statements. For distributed locks, look at lock TTLs and who holds them. A JVM thread dump shows threads WAITING in the JDBC driver or the Redis client, with no Java-level deadlock reported, which is a clue that the cycle is outside the JVM.

Steps: impose a global order of acquisition across both services (lock the lower id first), shorten transactions, add lock timeouts or TTLs, and make the retry logic idempotent with back-off and jitter so two retries do not collide again. Consider one owner per entity (partition the work by account id on a queue) so that no cross-service locking is needed.

Prevent: document the lock order as part of the API contract, avoid calling other services while holding a lock, and alert on deadlock counts.

A slow report endpoint using parallelStream() makes unrelated endpoints slow. Why? Senior

What the interviewer is testing: the shared common pool.

Situation: after a new report feature shipped, other parts of the app that use parallel streams or default CompletableFuture.supplyAsync become slow whenever someone runs the report.

Check first: dump threads named ForkJoinPool.commonPool-worker-N. If they are all inside the report's lambda, doing HTTP or JDBC calls, the cause is confirmed. The pool has only cores minus one threads (7 on an 8-core machine), and blocking calls hold them.

Steps: take blocking work out of the parallel stream. Use a dedicated bounded executor for the IO and CompletableFuture.supplyAsync(task, ioPool), or virtual threads. Use parallel streams only for CPU-bound, side-effect-free, large-data work. If you must keep a parallel stream, run it inside your own ForkJoinPool so it cannot starve the common one.

Prevent: code review rule "no blocking calls in parallel streams or default async stages"; a Sonar or ArchUnit rule against parallelStream/supplyAsync without an executor.

Memory climbs and emails are sent hours late. The app uses @Async for sending. What is wrong? Senior

What the interviewer is testing: unbounded queue behaviour in Spring's async executor.

Situation: the mail server became slow. The @Async executor (Boot default: core 8, unbounded queue) accepts every call, so the queue holds hundreds of thousands of tasks with their captured objects. Latency grows without bound, heap grows, and eventually OutOfMemoryError kills the app and loses all queued emails.

Check first: the executor's queue size metric (executor.queued in Micrometer for Boot), heap histogram (jcmd PID GC.class_histogram) showing many of the task classes, and the thread dump showing 8 threads stuck in the mail client.

Steps: define an explicit ThreadPoolTaskExecutor with a bounded queueCapacity, a sensible max size, a rejection policy (CallerRunsPolicy to slow producers, or abort and handle the TaskRejectedException), and a thread name prefix. Add timeouts to the mail client. For work that must not be lost (emails), do not rely on an in-memory queue at all: write it to a database outbox or a message broker and process from there with retries.

Prevent: alerts on queue depth and age of the oldest task; load test the failure of a dependency.

A config reload sometimes leaves some threads using old or half-initialised settings. How do you fix it? Senior

What the interviewer is testing: safe publication and immutable snapshots.

Situation: a reload thread updates fields of a shared Settings object one by one (url, then timeout, then retries). Request threads read these fields without any synchronization. Readers may see a mix of old and new values (a torn state) or never see the update (stale reads) because there is no happens-before.

Check first: find the object, mark which fields are written outside the constructor and who reads them. No volatile, no lock: confirmed.

Steps: make Settings immutable (final fields or a record). On reload, build a complete new instance and publish it with a single write to a volatile Settings current or AtomicReference<Settings>. Readers copy the reference once to a local variable at the start of a request and use that snapshot consistently.

private volatile Settings current = Settings.load();
void reload()  { current = Settings.load(); }          // one atomic publish
void handle()  { Settings s = current; use(s.url(), s.timeout()); }

Prevent: prefer immutable shared objects; flag mutable shared fields in review.

A plain HashMap used as a shared cache sometimes loses entries or a thread spins at 100% CPU. Intermediate

What the interviewer is testing: why HashMap is not safe and what to use.

Situation: a cache is a static HashMap that many request threads read and write. Symptoms: missing entries, size() wrong, rare ConcurrentModificationException, and in old Java 7 code, a thread stuck forever in HashMap.get because two concurrent resizes created a cycle in a bucket chain. Java 8 removed that specific loop but the data is still corrupted.

Steps: replace it with ConcurrentHashMap and use computeIfAbsent for the load-on-miss step. Keep the compute function short and do not touch the same map inside it (a recursive computeIfAbsent can livelock or throw in modern Java). If the loader is slow, store a CompletableFuture or a lazy holder as the value so that one thread loads and others wait on it, which also prevents a cache stampede (many threads loading the same key).

Prevent: a team rule that shared collections are concurrent types; use Caffeine for caches with expiry and size limits.

A nightly cleanup scheduled with scheduleAtFixedRate simply stopped running after one failure. Why, and how do you stop it happening? Intermediate

What the interviewer is testing: the silent cancellation behaviour of periodic tasks.

Situation: the job ran fine for weeks. One night a database timeout threw an exception. After that nothing ran, and nothing was logged, because the exception is stored in the ScheduledFuture that nobody reads.

Why: the contract says that if any execution throws, subsequent executions are suppressed.

Steps: wrap the body in a try/catch for Throwable (or Exception) that logs and keeps going. Keep the ScheduledFuture and check it in a health check. In Spring, @Scheduled already catches and logs exceptions and continues, but with one scheduler thread by default long tasks delay all others: set spring.task.scheduling.pool.size higher. If the job runs on several instances, add a distributed lock (ShedLock) to avoid double runs.

Prevent: a heartbeat metric "last successful run", with an alert if it is older than the period.

A command-line job finishes its work but the JVM never exits. Intermediate

What the interviewer is testing: non-daemon threads and pool shutdown.

Situation: main() returned, all the work is done, but the process stays alive and CI times out.

Check first: a thread dump of the idle process. It lists non-daemon threads like pool-1-thread-1 WAITING on a queue take. That means an ExecutorService was never shut down: the JVM stays alive as long as any non-daemon thread exists.

Steps: call shutdown() in a finally (or use try-with-resources on Java 19+), then awaitTermination. For helper pools that should never keep the app alive, use a ThreadFactory that makes daemon threads. A Timer and scheduled executors have the same issue. As a last resort System.exit, but it skips normal cleanup and hides the leak.

Prevent: own each pool's lifecycle in one place (a Spring bean with destroy method, or try-with-resources), and avoid creating pools inside methods that are called repeatedly, which leaks threads (next scenario).

The service dies with OutOfMemoryError: unable to create native thread. What do you check? Senior

What the interviewer is testing: thread leaks and OS limits, which differ from heap errors.

Situation: the heap is fine, but after some hours thread creation fails. This error means the OS refused a new thread: a per-user process limit (ulimit -u), container pids limit, or native memory for stacks is gone (each thread reserves about 1 MB of address space).

Check first: the thread count over time (JMX ThreadCount, or ls /proc/PID/task | wc -l) and a thread dump grouped by thread name. Thousands of threads named pool-NNN-thread-1 mean someone creates a new executor per request or per call and never shuts it down; thousands of identical stacks in one call means a cached pool exploding because every task blocks on a slow service.

Steps: make the executor a shared singleton, bound the pool (not newCachedThreadPool), shut down executors you create, and fix the slow dependency with timeouts. A short-term relief is raising limits, but that only delays the crash.

Prevent: alert on thread count, ban Executors.newCachedThreadPool() in service code, and prefer a virtual thread executor for IO-heavy fan-out on Java 21.

Throughput stops scaling when you add cores: 4 cores to 16 cores gives almost no gain. Senior

What the interviewer is testing: Amdahl's law in practice and lock contention analysis.

Situation: CPU usage stays low or odd, and the dump shows many threads BLOCKED on one monitor, or profiles show time in Unsafe.park and CAS retries.

Check first: a lock profile (JFR "Java Monitor Blocked" events, or async-profiler -e lock) tells which lock is hot and how long threads wait. Also look at a global counter (AtomicLong being hammered), a shared SimpleDateFormat in a synchronized wrapper, a synchronized logger appender, or a single-connection resource.

Steps: shrink the critical section; use striping or sharding; replace a hot AtomicLong with LongAdder; use a concurrent map instead of a synchronized one; use read-write lock or copy-on-write for read-mostly data; check false sharing on per-thread counters in adjacent array slots. Measure again after each change, since the next bottleneck may be elsewhere (memory bandwidth, the database).

Prevent: include a scalability test on a multi-core box before launch.

When a popular cache entry expires, hundreds of requests all hit the database at once. How do you fix it in code? Senior

What the interviewer is testing: single-flight loading, the concurrency side of caching.

Situation: the check-then-load pattern if (cache.get(k) == null) { v = db.load(k); cache.put(k, v); } lets every thread that sees a miss load the same value. The database gets hundreds of identical queries and slows down, which makes the requests slower, which causes more waiting threads: a feedback loop.

Steps: make the load happen once per key: ConcurrentHashMap.computeIfAbsent (the other threads for this key block until it finishes, and the compute must be quick and not touch the map), or store a CompletableFuture<V> in the map with putIfAbsent so waiters share one in-flight load without blocking a bin. Caffeine's LoadingCache does this correctly, and supports refreshAfterWrite to reload in the background so readers never see an expired entry. Add jitter to expiry times so many keys do not expire together.

Prevent: use a library cache, not a hand-written one; add a timeout to the loader.

You switched a service to virtual threads on Java 21 and under load it freezes or the database falls over. Senior

What the interviewer is testing: practical limits of virtual threads: pinning and missing back-pressure.

Situation: two different failure shapes. (a) The service freezes while CPU is idle. (b) The database or a partner API is overwhelmed by thousands of concurrent calls.

Check first: for (a), run with -Djdk.tracePinnedThreads=full or record the jdk.VirtualThreadPinned JFR event. On Java 21 to 23 a virtual thread blocking inside synchronized (often in an old JDBC driver or a library) pins its carrier; with all carriers pinned, nothing runs. For (b), count concurrent calls: there is no longer a pool of 200 threads acting as a throttle.

Steps: (a) replace blocking synchronized sections in your code with ReentrantLock, update drivers, or move to Java 24 where monitor pinning is largely removed. (b) add explicit limits: a Semaphore in front of the database or API, and keep the connection pool sized to what the database can take; callers now wait on the pool or semaphore instead of on a thread. Also remove heavy ThreadLocal caching.

Prevent: load test with virtual threads before switching in production, watch pinned events and the in-flight request metric.

Requests sometimes hang for minutes in a service that fans out with CompletableFuture. Senior

What the interviewer is testing: missing timeouts and blocking-in-pipeline issues.

Situation: a controller starts three async calls, then allOf(...).join(). When one dependency stalls, the request thread waits as long as that call does, which may be forever, and request threads pile up.

Check first: dump: request threads WAITING in CompletableFuture.join or get, and the async threads in socket reads. Check HTTP client settings: many clients have no default read timeout.

Steps: set client connect and read timeouts, then add a future-level timeout: orTimeout(1, SECONDS) or completeOnTimeout(default, 1, SECONDS) for each branch, and decide which branches may degrade. Use your own bounded executor and remember that the timeout only completes the future, it does not stop the underlying call (the client timeout does). Limit overall fan-out with a semaphore.

Prevent: a rule that every remote call and every join has a timeout, and a latency budget per request.

Closing line for an interview: "I first try not to share mutable state at all: immutable objects, confinement and queues. When I must share, I name the exact lock or atomic that guards each field, keep critical sections short, and put timeouts on every wait. I use bounded pools with named threads, and on Java 21 I use virtual threads for blocking IO with a semaphore as the limiter. When things go wrong, I take thread dumps before I restart."
Trap to avoid: saying "volatile makes it thread-safe" or "ConcurrentHashMap makes my code thread-safe". Volatile gives visibility only, and thread-safe parts do not make a thread-safe sequence: a check-then-act across two calls is still a race.
