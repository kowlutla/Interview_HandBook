Mental model: the 7 ideas everything hangs on

One line: threads share one heap, so every shared mutable variable needs a rule that makes writes atomic (all or nothing), visible (other threads see them) and ordered (not reordered unexpectedly). Locks, volatile, atomics and immutability are the four ways to give that rule.
  1. Shared heap, private stacks. Local variables live on a thread's own stack and are safe. Objects on the heap can be reached by many threads. Trouble starts only with state that is both shared and mutable.
  2. Three separate problems. Atomicity (nobody sees a half-done operation), visibility (a write by one thread is seen by another) and ordering (others see steps in the order you wrote them). Different tools fix different ones.
  3. CPUs and the JIT reorder and cache. Without a rule, a thread may keep a value in a register or core cache and never see another thread's update.
  4. Happens-before is the rule. The Java Memory Model says: if action A happens-before B, then B sees everything A did. Locks, volatile, thread start and join, and executors create these edges.
  5. Prefer not sharing. Immutable objects, thread confinement (one owner) and message passing (queues) avoid locks entirely.
  6. Threads are a limited, costly resource. A platform thread is an OS thread with about 1 MB of stack reserved. Pools bound them. Virtual threads (Java 21) make blocking cheap.
  7. Concurrency bugs hide. They show up under load, on other hardware, once a week. So you design for correctness, test with stress, and know how to read a thread dump.

1. Threads: the basics

What is the difference between a process and a thread? Basic

A process is a running program with its own private memory. A thread is a path of execution inside a process. All threads of one process share the heap, but each has its own stack and program counter. That makes threads cheap to create and good at sharing data, and also dangerous, because they can corrupt each other's data.

Start from what each one owns. When you launch a program, the operating system creates a process: it gets its own private slice of memory (its address space), its own open files and its own identity. Nothing outside can read that memory by accident. A thread is one independent line of execution running inside a process. It owns only a tiny bit of private state, namely a call stack (local variables and the chain of method calls) and a program counter (which instruction is next). Everything else, the heap, static fields and open files, is shared with the other threads of that process.

ProcessThread
MemoryPrivate address spaceShares heap and statics, private stack
Creation costHeavy (new address space)Lighter, but still an OS object (about 1 MB of reserved stack by default)
Talking to each otherSockets, pipes, files, shared memory (explicit)Just read and write the same objects (implicit, and dangerous)
If one crashesThe others surviveAn uncaught fatal error such as OutOfMemoryError can take the whole JVM down

Why this matters for Java. One running Java application is one process, the JVM, which already contains many threads before your code does anything: the main thread, garbage collector threads, JIT compiler threads, and later your request-handling threads. The shared heap is why threads are convenient (pass an object by reference, no copying) and also why concurrency bugs exist at all. If two processes want to share a counter they must agree on a protocol. If two threads want to share a counter, they simply touch the same field, and nothing stops them from doing it badly.

Cost angle. Switching the CPU from one thread to another (a context switch) costs microseconds and also throws away warm CPU caches. A machine with 8 cores running 5,000 busy threads spends a real fraction of its time just switching. That is the reason we pool threads (section 6) and the reason virtual threads (section 9) were invented.

A follow-up an interviewer likes: "Why not use processes for everything, since they are safer?" Answer: they are, and that is a valid design (browser tabs, some Python servers). But sharing large in-memory data between processes is slow or awkward, and thousands of processes are far heavier than thousands of threads.

Remember: process = private memory, thread = shared heap plus own stack. Sharing is the benefit and the bug source.

Describe the thread lifecycle and the states in Thread.State. Basic

There are six states: NEW (created, not started), RUNNABLE (running or ready for a CPU), BLOCKED (waiting to enter a synchronized block), WAITING (waiting with no timeout, for example wait(), join(), park()), TIMED_WAITING (the same with a timeout, like sleep(ms)) and TERMINATED (run() finished or threw).

The six states, in plain words. Thread.State is an enum with exactly six values:

  • NEW: the Thread object exists but start() has not been called.
  • RUNNABLE: the thread is either executing on a CPU or is ready and waiting for the OS scheduler to give it one. Java does not distinguish the two.
  • BLOCKED: the thread wants to enter a synchronized block or method but another thread owns that monitor. It does nothing until the monitor is free.
  • WAITING: the thread waits with no time limit for another thread to do something: Object.wait(), Thread.join(), LockSupport.park() (which every ReentrantLock, queue and latch uses internally).
  • TIMED_WAITING: the same, but with a deadline: sleep(ms), wait(ms), join(ms), parkNanos.
  • TERMINATED: run() returned or threw. A thread object can never be started again.

A short timeline. Here is one thread's life in a typical request worker:

t0  new Thread(task)            -> NEW
t1  thread.start()              -> RUNNABLE   (running or ready)
t2  enters synchronized(x), x is held by someone else
                                -> BLOCKED    (until the owner leaves)
t3  gets x, calls x.wait()      -> WAITING    (releases x; sits in the wait set)
t4  another thread: x.notify()  -> BLOCKED    (must re-acquire x first)
t5  re-acquires x               -> RUNNABLE
t6  calls Thread.sleep(500)     -> TIMED_WAITING
t7  run() returns               -> TERMINATED

Notice t4: after a notify the waiting thread does not go straight to running. It first goes back to BLOCKED because it must win the monitor again.

Why you must know this. These are the exact words jstack and jcmd Thread.print print, so reading a thread dump is reading this enum. A dump with 190 threads BLOCKED on the same <0x...> address tells you about lock contention. 190 threads WAITING in LinkedBlockingQueue.take are just idle workers (normal). 190 threads RUNNABLE in socketRead0 are waiting on the network even though Java reports RUNNABLE, because native IO shows up as RUNNABLE.

Common traps. (1) A thread waiting for a ReentrantLock shows WAITING, not BLOCKED, because that lock parks instead of using a monitor. Only synchronized produces BLOCKED. (2) Calling start() twice throws IllegalThreadStateException. (3) RUNNABLE does not mean it is using CPU right now.

Remember: BLOCKED means "waiting for a monitor". Everything else that waits is WAITING or TIMED_WAITING.

What is the difference between start() and run()? Basic

start() asks the JVM to create a new OS thread, which then calls run(). Calling run() directly is just an ordinary method call on the current thread, so nothing runs in parallel. start() can be called only once per thread object.

What actually happens. A Thread object is just a Java object holding a Runnable. start() is the method that asks the JVM to ask the OS for a brand-new thread of execution. That new thread then calls your run() method. Calling run() yourself skips all of that: it is an ordinary method call that executes in whatever thread you are already in.

Thread t = new Thread(() -> System.out.println("in " + Thread.currentThread().getName()));

t.run();     // prints "in main"      - same thread, caller waits for it to finish
t.start();   // prints "in Thread-0"  - new thread, caller continues immediately

Timeline of the difference (the task takes 5 s):

run():    main: [ ...call run()...5 s of work... ] then main continues      total 5 s, sequential
start():  main: [start] continue at once ...
          T-0:          [ ...5 s of work... ]                                parallel with main

Why it exists this way. Creating a thread is a heavy, OS-level action, so the API separates "describe the work" (run) from "launch it on a new thread" (start). The Runnable is only a description and can be reused by an executor, a test, or a plain call.

Pitfalls. The classic bug is new Thread(task).run(). It compiles, works, and silently makes the code sequential, so a "parallel" feature is not parallel and a slow task blocks the caller (often a web request thread). The second rule: start() may be called only once. And start() gives a happens-before edge: everything the starting thread did before start() is visible inside the new thread.

In real projects I rarely call new Thread at all. I hand a task to an ExecutorService, which creates, names, reuses and limits the threads for me.

Remember: start = new thread, run = plain call.

What is the difference between Runnable, Callable and Future? Basic

Runnable.run() returns nothing and cannot throw checked exceptions. Callable.call() returns a value and may throw. A Future is the handle I get back when I submit a task: it lets me wait for the result with get(), ask if it is done, or cancel it.

Three roles. Think of ordering food. A Runnable or Callable is the order (the work to do). The executor is the kitchen. The Future is the receipt you get back so you can check later.

RunnableCallable<V>
Methodvoid run()V call() throws Exception
Returns a resultNoYes

Usable with new Thread(...)YesNo, only via executors / FutureTask

A lambda with a return value is treated as a Callable by submit; a lambda with no value is a Runnable. That is why the compiler can pick correctly.

ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> computePrice());   // Callable, runs on a pool thread
// ... do other useful work here, in parallel ...
try {
    int price = f.get(2, TimeUnit.SECONDS);                // wait at most 2 s
} catch (TimeoutException e)   { f.cancel(true); }         // give up
  catch (ExecutionException e) { log.error("task failed", e.getCause()); }  // task threw
  catch (InterruptedException e) { Thread.currentThread().interrupt(); }

What Future offers: get() (block until done, return the value), get(timeout), isDone(), isCancelled(), cancel(mayInterrupt). If the task threw, get() rethrows it wrapped in an ExecutionException, so the real error is in getCause().

Limits that matter. A plain Future can only be asked or waited on. You cannot say "when it finishes, do X", you cannot combine two futures without blocking, and get() without a timeout can hang forever if the task never finishes. That gap is exactly why CompletableFuture (section 7) exists. Also, cancel(true) only sends an interrupt to the worker thread. If the task never checks for interruption, it keeps running.

Remember: Runnable = no result, Callable = result and exceptions, Future = the receipt.

What is the difference between sleep() and wait()? Basic

sleep pauses the current thread for a time and keeps every lock it holds. wait must be called inside a synchronized block on that object, releases that object's monitor, and sleeps until another thread calls notify or notifyAll (or a timeout or interrupt happens).

Two different jobs. sleep means "do nothing for a while". wait means "I cannot continue until some condition becomes true, so let someone else work on it and wake me when they have changed it". The key technical difference is what happens to locks.

Why wait must release the lock. Imagine a consumer waiting for an item in a shared list. The item can only be added by a producer that needs the same lock. If the consumer kept the lock while waiting, the producer could never get in and both would be stuck forever. So wait atomically releases the monitor and sleeps; when notified, the thread must re-acquire the monitor before it continues.

// Consumer                              // Producer
synchronized (list) {                      synchronized (list) {
    while (list.isEmpty())                     list.add(item);
        list.wait();   // lock released       list.notifyAll();   // wakes consumer
    use(list.remove(0));                   }   // consumer can only continue after
}                                              // the producer leaves this block

The danger of sleep inside a lock. synchronized (x) { Thread.sleep(1000); } holds x for a whole second, and every other thread that needs x is BLOCKED for that second. The same applies to any slow call (IO, remote call) under a lock. Both methods throw InterruptedException, which you must not swallow (next question).

Remember: sleep keeps the lock, wait gives it up.

How do you stop a running thread? What does interrupt() do? Intermediate

I never kill a thread. I ask it to stop with interrupt() and the task checks the flag and exits cleanly. interrupt() sets the thread's interrupted flag, and if the thread is in sleep, wait, join or a blocking queue call, that call throws InterruptedException right away.

Why we cannot just kill a thread. Java once had Thread.stop(). It killed the thread immediately by throwing an error at an arbitrary point, which released every lock it held in the middle of an update and left shared objects half-written. It is deprecated for removal and, in recent JDKs, no longer works. So Java uses cooperative cancellation: you ask the thread to stop, and the thread's own code decides where it is safe to stop.

How interrupt() works. Every thread has a boolean interrupted flag. t.interrupt() does two things:

  1. sets the flag on t;
  2. if t is currently blocked in sleep, wait, join, a BlockingQueue.take/put, lockInterruptibly or similar, that call wakes up and throws InterruptedException, and clears the flag.

Plain CPU code (a loop doing arithmetic) is not interrupted by anything. It must look at the flag itself with Thread.currentThread().isInterrupted(). And blocking socket reads of the old java.io API ignore interrupts (close the socket instead).

The rule everyone gets wrong. Because the exception clears the flag, if you catch InterruptedException and do nothing, the stop request is lost and the thread carries on, so it seems "unkillable". Either let the exception propagate (declare throws), or restore the flag so callers further up still see it:

// worker loop that stops cleanly
while (!Thread.currentThread().isInterrupted()) {
    try {
        process(queue.take());               // blocks; interrupt wakes it
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();  // restore the flag
        break;                               // and leave the loop
    }
}
// cleanup (close files, release resources) runs here

Timeline of a shutdown: main calls worker.interrupt() at t=0 while the worker is blocked in take(). At once take() throws, the catch restores the flag, the loop exits, cleanup runs, the thread ends. Total shutdown time is the time of the current task, not forever.

In practice: with executors, shutdownNow() and future.cancel(true) just call interrupt(), so the same rule applies to every task you write. Long loops should check the flag every so often, and any library method documented as "interruptible" should be allowed to propagate its exception.

Remember: stopping is cooperative. Never swallow InterruptedException: rethrow it or restore the flag.

What is a daemon thread, and why does it matter for JVM shutdown? Basic

A daemon thread is a background helper thread that does not keep the JVM alive. The JVM exits when the last non-daemon (user) thread finishes, and at that moment it kills all daemon threads on the spot, without running their finally blocks. Threads you create are non-daemon by default, so a forgotten pool thread can stop a program from ever exiting.

How it works. A thread inherits the daemon flag from the thread that creates it, and you can change it with setDaemon(true) only before start(). The JVM's own helpers (garbage collector, JIT compiler threads) are daemons. The main thread and threads you create normally are not.

Thread t = new Thread(() -> { while (true) { heartbeat(); sleepQuietly(1000); } });
t.setDaemon(true);   // must be before start()
t.start();
// when main ends and no non-daemon threads remain, the JVM exits and t is just dropped

When to use it. Only for work that is safe to abandon at any instruction: a metrics reporter, a cache cleaner, a heartbeat. Never for work that must finish, like writing a file or committing a transaction, because the JVM may cut it off in the middle with no cleanup. For work that must finish, use non-daemon threads and shut them down properly with shutdown() and awaitTermination.

The production symptom. "My app printed 'done' but the process will not exit." Almost always an executor that was never shut down: its worker threads are non-daemon and keep the JVM alive. Fix by shutting the executor down (or by using a ThreadFactory that makes daemon threads as a last resort). Virtual threads are always daemon threads, so they never keep the JVM alive.

Remember: the JVM waits for non-daemon threads and abruptly drops daemon ones. Daemon only for abandonable work.

2. Monitors, volatile and the Java Memory Model

What does synchronized do? Basic

It gives mutual exclusion and visibility. Only one thread at a time can hold a given object's monitor (its built-in lock), so only one can be inside any block guarded by that same object. When a thread leaves the block, its writes are flushed, and the next thread that enters sees them.

What problem it solves. Suppose two threads run balance += x on the same account. That one line is really read, add, write, and two threads can interleave inside it and lose an update. We need a way to say "only one thread may be inside this code at a time". That is mutual exclusion, and synchronized is Java's built-in way to get it.

How it works. Every Java object has a hidden monitor (an intrinsic lock). synchronized (obj) { ... } means: acquire obj's monitor, run the block, release the monitor, even if an exception is thrown. If another thread holds the monitor, you wait (state BLOCKED) until it is released.

private int balance;
public synchronized void deposit(int x) { balance += x; }     // locks this
public synchronized int  balance()      { return balance; }   // reads need it too

Timeline with two threads, balance = 100:

T1: lock(this) ok        read 100  add 50  write 150   unlock
T2:    wants lock -> BLOCKED ............................ lock ok  read 150  add 20  write 170  unlock
final balance = 170   (without the lock it could be 120 or 150)

The half people forget: visibility. The CPU may keep balance in a per-core cache. Releasing a monitor forces the thread's writes out, and acquiring a monitor makes it see the latest writes of whoever released it last (a happens-before edge, next questions). That is why the reader method also needs synchronized: a plain read can return a stale value forever, even though writes are protected.

Limits that explain why ReentrantLock exists. You cannot try the lock with a timeout, you cannot interrupt a thread that is waiting for it, you cannot choose fairness, there is one wait set per monitor, and the lock must be released in the same block that acquired it (no hand-over across methods). In exchange you get automatic release and very good JVM optimization.

Pitfalls: locking too much (including IO) makes everything serial; locking different objects in different places gives no protection at all (next question).

Remember: synchronized = exclusion + visibility, and both sides (read and write) must use the same lock.

What object does synchronized lock on for instance methods, static methods and blocks? Basic

An instance method locks this. A static method locks the Class object. A synchronized (x) block locks whatever object x is. Two threads block each other only if they use the same lock object.

The rule. A lock only excludes threads that use the same object as the lock. So the real question is "which object?":

CodeLock object
synchronized void m() (instance method)this
static synchronized void m()Foo.class (the Class object)
synchronized (x) { ... }whatever object x refers to

Consequences, with an example.

class Counter {
    private int a, b;
    synchronized void incA() { a++; }       // locks this
    synchronized void incB() { b++; }       // locks this -> blocks incA (same lock!)
    static synchronized void reset() { }    // locks Counter.class -> does NOT block incA
}
Counter c1 = new Counter(), c2 = new Counter();
// c1.incA() and c2.incA() run in parallel: different 'this' objects, different locks

Three effects follow. First, two synchronized methods of one object block each other even if they touch unrelated fields (coarse). Second, a static and an instance synchronized method do not exclude each other, so static state guarded by an instance lock is unprotected. Third, two instances never block each other, so a static counter must be guarded by a static lock.

Bad lock objects.

  • A non-final field: if the field is reassigned, threads lock different objects at different times.
  • A boxed Integer or a String literal: these may be cached or interned and shared with unrelated code in the JVM, causing surprising contention or deadlock.
  • this when it is exposed: any outside code can write synchronized (yourObject) and interfere.

The safe pattern is a private final lock object, which outside code cannot touch and which can guard a specific group of fields. Document it: // guarded by lock.

private final Object lock = new Object();
void update() { synchronized (lock) { /* guarded state */ } }

Remember: instance method = this, static method = the Class, block = what you name. Same lock or no protection.

What does "reentrant" mean for a lock? Basic

A thread that already holds a lock can acquire it again without blocking itself. The lock counts how many times the owner took it and frees it only when the owner has released it the same number of times. Both synchronized and ReentrantLock work this way.

The problem it solves. Suppose a synchronized method calls another synchronized method on the same object:

class Account {
    synchronized void transfer(Account to, int amt) { withdraw(amt); to.deposit(amt); }
    synchronized void withdraw(int amt) { ... }   // needs the same lock transfer() already holds
}

If locks were not reentrant, transfer would hold the lock and then wait for the same lock inside withdraw: a thread deadlocked with itself. Subclasses make this very common: an overriding synchronized method that calls super.method() also needs the lock a second time.

How reentrancy works. The lock remembers two things: which thread owns it and a hold count. When a thread asks for a lock it already owns, the count simply goes up (1, 2, 3...) and the thread continues. Each exit or unlock() decrements it. Only when the count reaches 0 does the lock become free for others.

lock.lock();        // count 1
  lock.lock();      // same thread: count 2, no blocking
  lock.unlock();    // count 1, still held
lock.unlock();      // count 0, released

Important detail with ReentrantLock: you must call unlock() as many times as you called lock(), otherwise the lock stays held forever (getHoldCount() helps debug this). With synchronized the JVM balances it for you.

What it does not mean. Reentrant protects a single thread from itself. It does nothing to prevent two different threads from deadlocking each other. Also the old Semaphore and StampedLock are not reentrant, so calling them recursively from the same thread can block you.

Remember: reentrant = the owner can re-enter, a hold count tracks it.

What does volatile guarantee? Basic

Two things: visibility and ordering. A write to a volatile variable is seen immediately by any thread that reads it afterwards, and everything the writer did before that write is also visible to the reader. It does not make compound operations like count++ atomic and it does not give mutual exclusion.

The problem. Each CPU core has its own caches, and the JIT compiler is allowed to keep a variable in a register. So a thread can write done = true and another thread, looping on while (!done), may never see it: the compiler may even turn the loop into while (true), because within that one thread the value never changes. Marking the field volatile tells the JVM "this variable is shared, never cache it privately, and do not reorder around it".

private volatile boolean running = true;
void stop() { running = false; }              // thread 1
void loop() { while (running) { work(); } }   // thread 2 sees the change soon

The two guarantees.

  1. Visibility: a read of a volatile variable always sees the latest write by any thread.
  2. Ordering (happens-before): everything the writer did before the volatile write is visible to a reader that sees that write. Think of it as a one-way gate: earlier writes cannot be moved after it, later reads cannot be moved before it.
// writer thread                     // reader thread
config = new Config(...);            if (ready) {            // volatile read
ready  = true;   // volatile write       use(config);       // guaranteed to see the new Config
                                     }

What it does not give. No atomicity for compound actions: count++ on a volatile int is still read, add, write, so two threads can lose an update. No mutual exclusion: two threads can both be past the check. Reads and writes of one volatile variable are atomic (including long and double, which are not guaranteed atomic when plain on some 32-bit JVMs).

Good uses: a stop flag, a "ready" flag as above, and a reference to an immutable object that is replaced as a whole (a config snapshot). Bad uses: counters, "check then act", or several fields that must change together. Volatile is also cheap, but not free: it blocks some optimizations.

Remember: volatile = latest value for everyone, not atomic read-modify-write.

When would you use volatile, and when synchronized or an atomic class? Intermediate

Volatile when one thread writes a standalone value and others only read it. An atomic class (AtomicInteger and friends) when I need an atomic update of a single variable, like a counter. synchronized or a lock when several variables must change together or a check-then-act sequence must not be interleaved.

A decision, not a definition. Ask three questions about the shared state:

  1. Is the new value independent of the old value, with one writer or last-write-wins? (a flag, a swapped config) Then volatile is enough.
  2. Is it one variable, but the new value depends on the old one? (count++, "max so far", "set if still X") Then an atomic class: AtomicInteger, AtomicLong, AtomicReference, or LongAdder for heavy statistics.
  3. Do several variables have to stay consistent with each other, or must a check and the following action not be interleaved? Then synchronized or a Lock, around the whole sequence.
NeedToolWhy

Counter, id generator, one-variable updateAtomicInteger, AtomicLong, LongAdderAtomic read-modify-write without a lock

Why atomics per field are not enough: an example. A transfer between two accounts: a.addAndGet(-50); b.addAndGet(+50); Each line is atomic, yet another thread reading in between sees 50 missing from the total. The rule "total stays constant" is an invariant over two variables, so one lock must cover both updates (and the read of both).

// wrong: two atomics, torn view in between
a.addAndGet(-50);        // another thread may sum a + b right here
b.addAndGet(+50);
// right: one lock guards the invariant, readers use the same lock
synchronized (lock) { a -= 50; b += 50; }

Rule of thumb for answers: volatile is the lightest and the easiest to misuse. If you are unsure, use a lock first and optimize only after you measure contention.

Remember: one value, one writer: volatile. One variable, many writers: atomic. Several values: lock.

What are atomicity, visibility and ordering, and which tool fixes which? Intermediate

Atomicity means an operation cannot be seen half done. Visibility means a write by one thread becomes visible to others. Ordering means other threads see steps in the order the program wrote them. Locks fix all three, volatile fixes visibility and ordering, atomics fix atomicity (and visibility) for one variable.

Why three words. A "thread-safety bug" is vague. Naming which of these three properties is broken tells you which tool to reach for.

  • Atomicity: an operation made of several steps is seen by others as one indivisible step. Broken example: count++ (read, add, write) loses an update when two threads interleave.
  • Visibility: when thread A writes a value, thread B eventually (and at the right moment) sees it. Broken example: while (!done) never ends because B reads a stale cached copy.
  • Ordering: other threads see operations in the order the program describes. Broken example: thread A does data = 42; ready = true; but the compiler or CPU reorders it, so B sees ready == true and still reads data == 0.

Debugging recipe. Match the symptom to the missing property:

Note that locks fix all three only if both the writer and the reader use the same lock. A writer inside synchronized and a reader outside it gets no guarantee.

Remember: atomic (not half done), visible (seen by others), ordered (in program order). Name the missing one.

What is the Java Memory Model and why does it exist? Senior

The Java Memory Model (JMM) is the specification of when one thread is guaranteed to see another thread's writes. It exists because CPUs have per-core caches and store buffers, and the compiler and JIT reorder instructions for speed. Without a contract, code would behave differently on every machine. The JMM defines that contract through happens-before.

Why a memory model is needed. Modern hardware and compilers are allowed, and encouraged, to be clever: CPUs have per-core caches and store buffers (a write may sit there for a while before others can see it), CPUs execute instructions out of order, and the JIT compiler reorders, merges or deletes memory accesses when nobody looks. All of this is invisible in single-threaded code, because the result is the same ("as-if-serial"). With several threads it is not: one thread can observe another's writes late, out of order, or not at all. If Java promised nothing, the same program would behave differently on x86, ARM, and different JIT versions.

What the JMM is. It is the part of the Java language spec (rewritten in Java 5 as JSR-133) that defines exactly when a read in one thread is guaranteed to see a write from another. It is the contract between you and the JVM: the JVM must keep the guarantees, and in return may optimize everything else.

The core tool: happens-before. If action A happens-before action B, then B is guaranteed to see all effects of A, and A appears ordered before B. Where there is no happens-before edge between a write and a read, the read may return the old value, the new value, or (for several variables) a confusing mix.

Thread A:  data = 42;  ready = true;      // plain fields
Thread B:  if (ready) print(data);        // may print 0, or never see ready = true
// no happens-before edge between the two threads -> no promise at all
// make 'ready' volatile -> edge exists -> B prints 42

Data race, defined. Two threads access the same variable, at least one access is a write, and no happens-before ordering exists between them. The JMM then gives only weak guarantees, so such code is simply buggy, even if it passes tests today.

Why this is a feature. Because the JMM promises order only across synchronization points, everything between them can be reordered and cached freely. That is why uncontended Java code is fast on all CPUs. The price is on you: share data only through edges (locks, volatile, atomics, queues, thread start/join), and you can reason about it as if it ran in order (this property is called "sequential consistency for data-race-free programs").

Remember: no happens-before edge means no guarantee. The JMM is the contract that lets the compiler stay fast and your code stay correct.

Explain happens-before and the main rules that create it. Senior

Happens-before is a guarantee: if action A happens-before action B, then everything A did is visible to B and A is ordered before B. The edges I rely on are: program order within one thread, unlock then lock of the same monitor, volatile write then volatile read of the same variable, Thread.start() then everything in that thread, thread end then join(), and submitting a task to an executor then the task running. It is also transitive.

What it is, simply. "A happens-before B" is not about wall-clock time. It means "B is guaranteed to see everything A did, and A is ordered before B as far as B can tell". Without such an edge, a thread may see old data. The JMM lists the ways to create edges; learn these:

Transitivity is the magic. In the diagram below, data = 42 is a plain write, yet it becomes visible: it is before the volatile write in program order, the volatile write happens-before the volatile read, and the volatile read is before the read of data in program order. Chain: A to B to C to D.

ready = true;       // volatile       print(data);     // must print 42
                                  }

Worked failure. If ready were a plain field, no edge links the two threads, so the consumer may see ready == true and still read data == 0, or never see ready change. If the consumer reads data before reading the volatile (wrong order), the edge does not help, because program order in the consumer thread no longer chains through.

How to use this in an interview: when asked "is this code thread-safe?", look for a chain of edges from every write to every read of each shared variable. A single missing link is a data race.

Remember: edges come from lock/unlock, volatile, start/join, executors and concurrent collections. Chain them or you have a race.

What is safe publication and why can another thread see a half-built object? Senior

Publishing means making an object reachable by another thread. It is safe only if the hand-off creates a happens-before edge. If I just assign the object to a plain shared field, the reader may see the reference before the constructor's writes, because the compiler or CPU can reorder them, and so it can see default values like null or 0 in the fields.

Two ideas first. To publish an object means to make it reachable by another thread (store it in a shared field, put it in a collection, pass it to a thread). A thread seeing the reference is not the same as seeing the object's contents correctly.

How a half-built object appears. holder = new Holder() is several steps: allocate memory, run the constructor (set fields), store the reference into holder. Without an ordering rule, the compiler or CPU may make the reference store visible before the field writes. Another thread then reads holder != null and uses an object whose fields still hold defaults (0, null, false).

class Holder { int a = 1; final int b; Holder() { b = 2; } }

static Holder h;                       // plain: UNSAFE publication
// thread 1:  h = new Holder();
// thread 2:  if (h != null) use(h.a);  // may see h.a == 0 !

static volatile Holder hv;             // SAFE: volatile write gives happens-before

Safe ways to publish (each one creates a happens-before edge):

  • write the reference to a volatile field or an AtomicReference;
  • write it while holding a lock, and read it while holding the same lock;
  • put it into a concurrent collection or hand it over a BlockingQueue;
  • initialize it in a static initializer (class loading is thread-safe);
  • make the fields final.

Final fields get a special rule. After a constructor ends normally, any thread that sees the object reference is guaranteed to see the correct values of its final fields (and what they point to, as of the end of construction), with no synchronization. That is why immutable classes are safe to share. The guarantee breaks if this escapes during construction, for example by registering a listener or starting a thread inside the constructor: the other thread can see a half-initialized object.

Practical rule: prefer immutable objects, and when you must hand over a mutable one, hand it over through a queue or a volatile/atomic reference, not a plain field.

Remember: an unsafe publication can show a non-null object with empty fields. Publish via volatile, lock, concurrent collection, or final fields.

Why does double-checked locking need volatile? Senior

Because creating an object is several steps, and without volatile they can be reordered: allocate memory, publish the reference, then run the constructor. Another thread doing the unsynchronized first check can then see a non-null reference to a half-built object. Volatile forbids that reordering.

What DCL is for. A lazy singleton wants to create its object once, on first use, without paying for a lock on every later call. Double-checked locking tries: check without a lock; if null, take the lock and check again; create it.

class Config {
    private static volatile Config instance;       // volatile is essential
    static Config get() {
        Config c = instance;                       // 1st check, no lock (fast path)
        if (c == null) {
            synchronized (Config.class) {
                c = instance;                      // 2nd check, now exclusive
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }
}

Why volatile. instance = new Config() is three steps: (1) allocate memory, (2) run the constructor, (3) store the reference. The compiler or CPU may do 3 before 2. A second thread doing the unlocked first check can then see instance != null, skip the lock, and use an object whose constructor has not finished: wrong values in its fields. Volatile forbids that reordering and gives the happens-before edge between the writer's constructor and the reader.

T1: allocate -> store ref ------------------------> run constructor (later!)
T2:                     reads instance != null -> uses half-built object  (BUG without volatile)

Why two checks. The first avoids locking on the hot path. The second is needed because two threads may both pass the first check and queue for the lock; the later one must not create a second instance.

The local variable c is a small optimization: it reads the volatile field once on the fast path instead of twice.

Better alternatives (what I would actually write).

  • Holder-class idiom: private static class H { static final Config I = new Config(); }. The JVM initializes H lazily on first access and does so under an internal lock, so it is lazy, thread-safe, and has no volatile read in the fast path.
  • Enum singleton: also safe against reflection and serialization tricks.
  • Spring bean: let the container create the singleton and inject it.

DCL was truly broken before Java 5 (the old memory model); since Java 5 it is correct with volatile.

Remember: DCL without volatile is broken. Prefer the holder-class idiom or an enum.

How do wait(), notify() and notifyAll() work? Why is wait always in a loop? Intermediate

A thread holding a monitor calls wait() when a condition is not true yet. That releases the monitor and parks the thread in the monitor's wait set. Another thread changes the state and calls notify or notifyAll. The woken thread must re-acquire the monitor and then re-check the condition, which is why the call sits in a while loop, never an if.

What problem it solves. Thread-to-thread coordination: "I (a consumer) cannot go on until the list is non-empty; someone else will make that true." Spinning on the condition wastes CPU. wait/notify lets the thread sleep and be woken exactly when something changes.

The mechanism. Every object's monitor has an entry set (threads wanting the lock) and a wait set (threads that called wait). Step by step:

  1. Thread C enters synchronized (q), sees the queue empty, calls q.wait().
  2. wait() atomically releases the monitor and puts C in the wait set (state WAITING).
  3. Thread P enters synchronized (q), adds an item, calls q.notifyAll(), and leaves the block.
  4. C is moved out of the wait set. It has to re-acquire the monitor (BLOCKED while P still holds it), and only then returns from wait().
  5. C re-checks its condition and continues.
synchronized (queue) {
    while (queue.isEmpty())       // WHILE, not if
        queue.wait();             // releases the lock while waiting
    item = queue.remove();        // condition is true here, lock is held
}
// producer side
synchronized (queue) { queue.add(x); queue.notifyAll(); }

Why a while loop, never if. (1) Spurious wakeups: the spec allows a thread to wake with no notify at all. (2) Stolen condition: between the notify and C re-acquiring the lock, another consumer may have grabbed the item. (3) notifyAll wakes everybody, and only one can use the item. In each case, the condition must be tested again after waking.

notify or notifyAll? notify wakes one arbitrary waiter. If the waiting threads wait for different conditions (producers waiting for "not full" and consumers waiting for "not empty" on the same monitor), notify may wake the wrong kind, which then goes back to sleep, and the wakeup is lost: the system hangs. So default to notifyAll and let each thread re-check. Use Condition objects (separate wait sets) or a BlockingQueue to avoid this wake-everyone cost.

Other rules: call them only while holding that object's monitor (else IllegalMonitorStateException); change the shared state before calling notify, inside the same synchronized block; a notify with no waiter is simply lost (so the state must be stored in a variable, never in the notify itself).

Remember: wait in a while loop, notifyAll by default, always inside synchronized on the same object.

3. Race conditions, deadlock, livelock, starvation

What is a race condition? How is it different from a data race? Basic

A race condition is a bug where the result depends on how threads happen to interleave. A data race is the narrower, technical case: two threads access the same variable at the same time, at least one writes, and nothing orders them. You can have a race condition without a data race (two properly locked calls in the wrong order) and a data race without visible harm.

Race condition, in one picture. The program is correct if threads happen to run one way and wrong if they run another way, and you do not control which one happens. "Race" means the threads race, and the winner changes the result.

Two classic patterns.

  • Check-then-act: you check a condition, then act on it, but the condition may change between the two.
  • Read-modify-write: you read a value, compute a new one, write it back, and someone else changed it in between.
// check-then-act: both threads see "absent" and both create -> two objects, one overwritten
if (!map.containsKey(k)) map.put(k, new Session());

// read-modify-write: both read 5, both write 6 -> one increment lost
count = count + 1;

Timeline of the first one (a thread-safe map, still wrong):

T1: containsKey("u1") -> false
T2: containsKey("u1") -> false
T1: put("u1", sessionA)
T2: put("u1", sessionB)     // overwrites A; whoever holds A now has an orphan

Each call on the map is safe alone; the sequence is not. That is the main lesson: thread-safe components do not compose into a thread-safe sequence.

Race condition versus data race. A data race is a precise memory-model term: two threads access the same variable, at least one writes, with no happens-before ordering. A race condition is the broader logical bug "outcome depends on timing". They overlap but differ:

  • Data race but harmless: two threads set the same boolean flag to true without sync (still a spec violation).
  • Race condition without a data race: every access is properly locked, but two separate locked calls are made in a wrong order or split a logical operation (if (map.contains) map.put on a synchronized map).

Fixes: make the whole sequence atomic (one lock around it, or one atomic method like putIfAbsent, merge, compareAndSet), or remove the sharing (immutability, confinement, queues). Why they survive testing: the bad interleaving can need a window of nanoseconds, so it appears under production load, on more cores, or once a week.

Remember: thread-safe parts do not make a thread-safe sequence. Guard the whole check-then-act.

Why is count++ not thread-safe, even if count is volatile? Basic

Because count++ is three steps: read, add one, write. Two threads can both read 5, both compute 6 and both write 6, so one increment is lost. Volatile only makes each single read and write visible. It does not stop two threads from interleaving between the steps.

What count++ really is. It looks like one operation, but the JVM executes three: load the field into a register, add 1, store the register back. Two threads can interleave between those steps.

count = 5
T1: read 5
T2: read 5
T1: add 1 -> 6, write 6
T2: add 1 -> 6, write 6      // overwrites with 6, not 7
count = 6                     // expected 7: one increment lost

Why volatile does not help. volatile guarantees that each single read sees the latest write and each write is visible. In the timeline above that was already true: T2 read the real latest value (5) at that moment. The problem is the gap between read and write, and volatile does nothing about gaps. It gives visibility, not atomicity of a multi-step operation.

Three fixes, from lightest to heaviest.

AtomicInteger count = new AtomicInteger();
count.incrementAndGet();                         // CAS loop: read, add, compareAndSet, retry

LongAdder hits = new LongAdder();                // many writers, stats only
hits.increment();

synchronized (lock) { count++; }                 // or a lock when several fields change together

map.merge(key, 1, Integer::sum);                 // ConcurrentHashMap: atomic per-key counter
// NOT: map.put(key, map.get(key) + 1)           // same lost-update bug

Beyond the JVM. A Java lock protects only one process. If the counter is a database row or the app runs on several instances, two instances can still both read 10 and write 9. Make the database do the atomic step: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0 (check the updated row count), or use optimistic locking with a version column.

Pattern to remember: any x = f(x) on shared state, any ++, +=, "get then put", is a lost-update suspect.

Remember: ++ is read, add, write. Volatile does not glue those three together.

What is a deadlock? What are the conditions and how do you prevent it? Intermediate

A deadlock is when two or more threads each hold a lock the other needs, so all wait forever. It needs four conditions together: mutual exclusion, hold and wait, no preemption, and circular wait. I prevent it by breaking one, and the cheapest is circular wait: always acquire locks in the same global order.

What it is. Two or more threads each hold a lock and each waits for a lock held by another in the cycle. No one can proceed and nobody gives up, so they wait forever. The program is alive but frozen.

// Thread 1                               // Thread 2
synchronized (A) {                         synchronized (B) {
    // ... small delay ...                     // ... small delay ...
    synchronized (B) { ... }                   synchronized (A) { ... }
}                                          }
// T1 holds A, wants B.  T2 holds B, wants A.  Stuck.

The four necessary conditions (Coffman). A deadlock needs all four; break any one and it cannot happen:

  1. Mutual exclusion: the resource can be used by only one thread at a time (locks).
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: a lock cannot be taken away; only its owner releases it.
  4. Circular wait: there is a cycle of threads each waiting for the next one's lock.

Prevention techniques, mapped to the conditions.

  • Lock ordering (breaks circular wait): every code path acquires locks in the same global order, for example by account id. The cheapest and most reliable.
  • Timeouts with tryLock (breaks hold-and-wait/no-preemption): if you cannot get the second lock in time, release the first, back off for a random delay, and retry. Random delay avoids a livelock (next question but one).
  • One coarse lock, or no nested locks: fewer locks, fewer cycles.
  • No alien calls under a lock: do not call listeners, callbacks or overridable methods while holding a lock, since you do not know what locks they take.
  • Avoid locks: queues, immutable data, a single owner thread per resource.
void transfer(Account a, Account b, long amt) {
    Account first  = a.id < b.id ? a : b;      // always lock the lower id first
    Account second = first == a ? b : a;
    synchronized (first) {
        synchronized (second) { a.debit(amt); b.credit(amt); }
    }
}
// transfer(x, y) and transfer(y, x) now lock in the same order: no cycle possible

Gotcha: if two accounts can have equal ids (or you use hashCode which can collide), add a tie-breaker lock. Database row locks and distributed locks deadlock the same way, and the same rules apply.

Remember: same lock order everywhere, tryLock with timeout as a safety net, and no foreign calls under a lock.

How do you detect a deadlock in a running application? Intermediate

I take a thread dump with jcmd PID Thread.print (or jstack PID). The JVM detects lock cycles itself and prints "Found one Java-level deadlock" at the end, listing each thread, the lock it holds, the lock it waits for and the code line. Inside the app, ThreadMXBean.findDeadlockedThreads() does the same check and can drive an alert.

Step by step.

  1. Get a thread dump while the app is stuck: jcmd <pid> Thread.print (or jstack <pid>, or kill -3 <pid> which prints to the process's stdout).
  2. Look at the bottom of the dump. If the JVM found a lock cycle among threads, it prints a section like this:
Found one Java-level deadlock:
=============================
"worker-1":
  waiting to lock monitor 0x00007f...  (object 0x000000076ab1, a Account),
  which is held by "worker-2"
"worker-2":
  waiting to lock monitor 0x00007f...  (object 0x000000076ab2, a Account),
  which is held by "worker-1"
Java stack information for the threads listed above:
  "worker-1": at Bank.transfer(Bank.java:42) ...

It names each thread, the lock it waits for, the lock it holds and the exact source line, which usually makes the fix obvious (lock order).

Detecting it from inside the application. ManagementFactory.getThreadMXBean().findDeadlockedThreads() returns the ids of threads in a cycle on either synchronized monitors or java.util.concurrent locks (findMonitorDeadlockedThreads covers only monitors). Run it on a scheduler every 30 seconds and log or alert when it returns non-null. Do not use it to "recover": threads cannot be freed, only reported.

What the detector does not find. A hang without a lock cycle: all workers waiting on a future that needs the same pool (starvation deadlock), a thread waiting for a notify that already happened, a missing countDown(), or everyone waiting on a database. For those, take three dumps 5 to 10 seconds apart and compare: threads stuck on the same line each time are the suspects, and the "waiting on" and "locked" addresses show who waits for whom. Always save the dumps before restarting, because a restart destroys the evidence.

Remember: dump first. "Found one Java-level deadlock" names the threads and lines. No such text does not mean no hang.

What are livelock and starvation? Intermediate

In a livelock the threads are not blocked; they keep reacting to each other and doing work, but make no progress, like two people in a corridor who both keep stepping aside. In starvation a thread is ready but never gets the resource because others always win. A deadlock burns no CPU; a livelock usually does.

Three different ways to make no progress.

Threads stateCPUCause
DeadlockAll blocked on each otherIdleCycle of lock waits
LivelockRunning, reacting to each otherBusyEveryone keeps backing off or retrying in sync
StarvationOne thread is ready but never scheduled or servedOthers work fineUnfair locks, priorities, pool hogged by long tasks

Livelock example. The usual "fix" for deadlock is tryLock and back off. If both threads do exactly that at the same time, they livelock:

T1: lock(A) ok -> tryLock(B) fails -> unlock(A) -> retry immediately
T2: lock(B) ok -> tryLock(A) fails -> unlock(B) -> retry immediately
// repeat forever, both very busy, nobody finishes
// fix: sleep a RANDOM time before retrying, or use a fixed lock order

It is the corridor picture: two people step to the same side, then both step to the other side, over and over. Their actions are in lockstep. Randomness breaks the symmetry.

Starvation causes and cures.

  • Unfair lock: the default ReentrantLock and synchronized let a running thread "barge in" ahead of waiters, so an unlucky waiter can wait very long. new ReentrantLock(true) grants the longest waiter first, at a throughput cost.
  • Writers starved by readers with a read-write lock under constant read traffic.
  • Pool starvation: a few long tasks occupy all threads of a small pool and short tasks wait. Use separate pools for different workload classes.
  • Thread priorities are only hints; rely on design, not priorities.

How to spot them: deadlock = threads BLOCKED and CPU flat, the dump says so. Livelock = high CPU, threads RUNNABLE in a retry loop, no deadlock report. Starvation = one task or thread class has huge latency while the system looks healthy overall.

Remember: deadlock = stuck and quiet, livelock = busy and stuck, starvation = never gets a turn.

4. Locks, atomics and ThreadLocal

What does ReentrantLock give you that synchronized does not? Intermediate

Control. ReentrantLock can try without blocking (tryLock), wait with a timeout, wait in a way that responds to interrupts (lockInterruptibly), be created fair, and offer several Condition queues. synchronized is simpler and cannot be forgotten open, so I use it by default and switch to the lock only for one of those features.

Same core job, more control. Both give mutual exclusion and visibility (unlock happens-before the next lock) and both are reentrant. The difference is the extra options ReentrantLock exposes and the extra care it needs.

Which to choose. Default to synchronized: shorter, impossible to forget to release, and the JVM optimizes it well (biased locking, once a trick, was disabled by default in Java 15 and removed in later releases). Switch to ReentrantLock only for a concrete need: timeout, try-lock, interruptible lock, fairness, multiple conditions, or on Java 21 to avoid pinning around blocking code.

Fairness trade-off. A fair lock serves waiters in arrival order and prevents starvation, but because every release must hand the lock to a sleeping thread instead of letting a running one grab it, throughput can fall by a large factor. Use it only when starvation is an observed problem.

Remember: synchronized for simplicity, ReentrantLock for tryLock, timeout, interruptibility, fairness and several conditions. Unlock in finally.

How does ReentrantLock work inside? What is AbstractQueuedSynchronizer? Senior

Most locks and synchronizers in java.util.concurrent (ReentrantLock, Semaphore, CountDownLatch, read-write lock) are built on AQS. It holds one volatile int state and a FIFO queue of waiting threads. To acquire, a thread tries to change state with CAS. If that fails, it joins the queue and parks (sleeps with no CPU). On release, the successor at the head of the queue is unparked and tries again.

The big idea. Writing a correct lock is hard: you must store the state, let threads take it atomically, put losers to sleep without wasting CPU, and wake them in the right order. AQS (AbstractQueuedSynchronizer) is a framework that does all of that once. A concrete lock or synchronizer only decides what the state number means, and AQS provides blocking, queueing, timeouts and interruption.

Two parts.

  1. A single volatile int state changed with CAS (compare-and-swap).
  2. A FIFO queue of waiting threads (a variant of the CLH queue), each node holding a thread and its status.

Acquire, step by step (an exclusive lock):

  1. Thread tries CAS state 0 to 1. If it succeeds it owns the lock and records itself as owner. Done, no queue, no OS call (the uncontended fast path).
  2. If CAS fails, the thread creates a queue node, appends itself at the tail, and tries once more.
  3. If it is not at the front or still cannot get it, it parks (LockSupport.park): the OS stops scheduling it, so it uses no CPU.
  4. When the owner calls release, state goes back to 0 and AQS unparks the first waiter, which retries the CAS.

What "state" means in each class:

ClassMeaning of stateMode
ReentrantLockHold count (0 free); owner thread is stored separatelyExclusive
SemaphoreNumber of available permitsShared
CountDownLatchRemaining count; at 0 everyone is releasedShared
ReentrantReadWriteLockRead count in the high bits, write hold count in the low bitsBoth

Why it is good to know. It explains why these classes share features (timed tryAcquire, lockInterruptibly, fair or non-fair mode, getQueueLength()) and why they cost almost nothing when uncontended but involve OS park/unpark when contended. Fairness is just "a newcomer checks the queue first" versus "a newcomer may barge in with CAS".

Remember: AQS = a volatile state, CAS to take it, a FIFO queue of parked threads. Each class just decides what state means.

What is a Condition, and why is it better than wait/notify? Intermediate

A Condition is the wait/notify of a ReentrantLock, but one lock can have several of them. A bounded buffer can have "not full" and "not empty" separately, so a producer wakes only consumers and a consumer wakes only producers. With plain wait/notify there is one wait set, so I must use notifyAll and wake everybody.

The problem with plain wait/notify. One monitor has exactly one wait set. In a bounded buffer, producers wait for "not full" and consumers wait for "not empty", but both groups sit in the same wait set. When a consumer removes an item and wants to wake a producer, it cannot target producers: notify may wake another consumer (which just goes back to sleep and the signal is lost), so you are forced to use notifyAll and wake everybody, producers and consumers, just to let one thread proceed.

What Condition gives. It is a separate wait queue attached to a Lock, created with lock.newCondition(). You can create as many as you like for one lock, one per logical reason to wait.

private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();   // producers wait here
private final Condition notEmpty = lock.newCondition();   // consumers wait here

void put(T x) throws InterruptedException {
    lock.lock();
    try {
        while (count == capacity) notFull.await();   // releases lock while waiting
        add(x);
        notEmpty.signal();                           // wake ONE consumer only
    } finally { lock.unlock(); }
}

Same rules as wait: you must hold the lock when calling await or signal (else IllegalMonitorStateException); await atomically releases the lock while sleeping and re-acquires it before returning; always test the condition in a while loop (spurious wakeups, stolen conditions).

When to use it. When you implement your own blocking structure with more than one reason to wait. In most application code, a BlockingQueue (itself built on conditions, for example ArrayBlockingQueue) is the better choice, so you do not write this by hand.

Remember: Condition = several wait queues per lock, so you wake only the right group.

What is a ReadWriteLock? When does it help and what are its traps? Intermediate

It lets many threads read at the same time, but a writer gets exclusive access. It pays off when reads clearly dominate and reading takes real time. For short reads, a plain lock or a concurrent map is often just as fast, because the read lock itself has overhead.

The idea. Reading does not change data, so many readers could safely run together. Only a writer needs to be alone. A ReadWriteLock has two locks: a read lock that many threads may hold at once, and a write lock that is exclusive (no readers, no other writer). ReentrantReadWriteLock is the standard implementation.

private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
private Map<String,String> data = new HashMap<>();

String get(String k) {
    rw.readLock().lock();
    try { return data.get(k); } finally { rw.readLock().unlock(); }
}
void put(String k, String v) {
    rw.writeLock().lock();
    try { data.put(k, v); } finally { rw.writeLock().unlock(); }
}

When it pays off. Reads vastly outnumber writes and each read takes real time (so that parallel readers actually save time). For tiny reads, taking the read lock costs about as much as the work itself, so a plain lock or a ConcurrentHashMap is as fast and simpler.

Traps.

  • No upgrade (read to write): if a thread holding the read lock asks for the write lock, it waits for all readers to leave, including itself: it deadlocks on itself. Release the read lock first, take the write lock, then re-check the condition because things may have changed.
  • Downgrade is allowed: take the write lock, take the read lock, then release the write lock. You keep seeing a consistent state and let other readers in.
  • Writer starvation: a steady stream of readers can delay writers. The default mode is non-fair with some heuristics; fair mode helps but is slower.
  • No Condition on the read lock.

Often-better alternative. For read-mostly data such as configuration or a routing table, keep an immutable snapshot in a volatile field or AtomicReference. Readers just read the reference (no lock, no cost). A writer builds a whole new object and swaps the reference.

Remember: readers share, writers exclude. No read-to-write upgrade. For read-mostly data, swap an immutable snapshot instead.

What is StampedLock and its optimistic read? Senior

It is a faster read-write lock (Java 8) with a third mode: optimistic read. A reader takes a stamp without locking, reads the fields, then asks validate(stamp) whether a writer came in meanwhile. If yes, it retries or falls back to a real read lock. For read-heavy code with short reads this is the fastest option in the JDK.

The idea. Even a read lock has a cost: it writes to shared memory to count readers, and under many readers that counter becomes a bottleneck. StampedLock (Java 8) adds an optimistic read: read the data without taking any lock, then check afterwards whether a writer got in. If no writer did, the read was valid and you paid almost nothing. If one did, you fall back to a real read lock and read again.

Every lock method returns a stamp (a long) that you pass back to unlock or validate:

private final StampedLock lock = new StampedLock();
private double x, y;

double distance() {
    long s = lock.tryOptimisticRead();        // no blocking, just a version stamp
    double cx = x, cy = y;                    // copy to LOCAL variables
    if (!lock.validate(s)) {                  // did a writer run in between?
        s = lock.readLock();                  // yes: take a real read lock
        try { cx = x; cy = y; } finally { lock.unlockRead(s); }
    }
    return Math.sqrt(cx * cx + cy * cy);      // compute only after the data is validated
}
void move(double dx, double dy) {
    long s = lock.writeLock();
    try { x += dx; y += dy; } finally { lock.unlockWrite(s); }
}

Why copy to locals first. Until validate says yes, the values may be inconsistent (x from before a write, y from after). You must not act on them, throw on them or loop on them before validating.

Costs and rules.

  • Not reentrant: locking twice from the same thread can deadlock itself.
  • No Condition support, and the stamp must be passed to the right unlock call.
  • It can convert modes (tryConvertToWriteLock), which is more flexible than the read-write lock, but easy to misuse.
  • It is not interruptible in the default calls (use the ...Interruptibly variants).

When I would use it: a proven hot read path on small data (a coordinates object, a counter pair) where measurements show the read lock is the bottleneck. Otherwise a simpler design wins (immutable snapshot, ConcurrentHashMap).

Remember: StampedLock = read without lock, then validate. Not reentrant, no conditions.

What is CAS, and how do the atomic classes use it? Intermediate

Compare-and-swap is a CPU instruction that says: "set this variable to the new value only if it still holds the expected value, and tell me whether it worked". Atomic classes use it in a loop: read the current value, compute the new one, try to CAS, and retry if another thread got there first. There is no lock and no thread is ever put to sleep.

The problem CAS solves. A lock makes a thread wait if someone else holds it, and waiting threads must be parked and woken by the OS. For tiny operations like incrementing a counter that is wasteful. CPUs provide a single indivisible instruction, compare-and-swap, that does the check and the update in one atomic step.

What CAS means. CAS(address, expected, new): "if the variable at address still equals expected, set it to new and report success; otherwise change nothing and report failure." In Java it is compareAndSet.

The retry loop that atomic classes use (this is the actual idea behind incrementAndGet):

int old, next;
do {
    old  = value;          // 1. read
    next = old + 1;        // 2. compute
} while (!cas(old, next)); // 3. try; if another thread changed value, repeat

Two threads, counter = 5:

T1: read 5, compute 6
T2: read 5, compute 6
T1: CAS(5 -> 6) succeeds, value = 6
T2: CAS(5 -> 6) FAILS (value is 6 now) -> loop: read 6, compute 7, CAS(6 -> 7) succeeds
value = 7   // no lost update, and nobody blocked or slept
AtomicInteger n = new AtomicInteger();
n.incrementAndGet();                         // CAS loop inside
n.updateAndGet(v -> Math.min(v + 1, 100));   // your function may run several times: keep it pure
n.compareAndSet(5, 6);                       // true only if it was 5

Properties. Lock-free (a stuck thread cannot block the others), no context switch, great at low or medium contention. Under heavy contention many threads fail and retry, burning CPU, which is why LongAdder exists. A CAS works on one variable. For two related fields, put them in one immutable object and CAS the reference with AtomicReference. Beware the ABA problem (next question). Where used: Atomic*, ConcurrentHashMap, ConcurrentLinkedQueue, AQS locks, VarHandle (Java 9).

Remember: CAS = read, compute, "set if still unchanged", retry. Lock-free, one variable, pure update function.

What is the ABA problem? Senior

CAS only checks that the value is the same as before, not that nothing happened in between. If a value goes A to B and back to A, my CAS succeeds although the world changed. It matters mostly in lock-free structures built on node pointers.

What CAS cannot see. CAS asks "is the value still A?" It cannot ask "has it stayed A the whole time?" If it went A, then B, then back to A, the CAS succeeds, although the state of the world changed in between. That is the ABA problem.

When it is harmless. For a plain counter: if the value returns to 5, 5 is 5. Nothing else depends on the history. So ABA matters for structures where the value is a pointer and something else depends on what the pointer leads to.

Classic example: lock-free stack. Stack top is A, A.next is B.

T1: reads top = A, next = B, then gets paused before its CAS
T2: pops A, pops B, pushes A back          // top is A again, but A.next is now null/C
T1: resumes: CAS(top, A -> B) succeeds   // top still looks like A!
// stack now points at B, which was already removed: corrupted structure
// the correct stack would be: A.next (the new one)

T1's CAS succeeded because the top reference matched, but the assumption "A.next is B" was stale.

Fixes.

  • Version stamp: AtomicStampedReference compares the reference and an int stamp that you increment on every change. A to B to A has stamps 1, 2, 3, so a CAS expecting (A, stamp 1) fails.
  • AtomicMarkableReference: reference plus a boolean mark (used for "logically deleted" in lock-free lists).
  • Never reuse nodes: in Java the garbage collector will not recycle a node while a thread still references it, so many classic pointer-reuse ABAs cannot happen unless you pool or recycle objects yourself.

Interview line: "ABA means CAS sees equal value, not equal history; I add a version counter or avoid recycling objects."

Remember: CAS sees "same value", not "same history". Add a version stamp if history matters.

When do you use LongAdder instead of AtomicLong? Intermediate

LongAdder for a counter that is updated by many threads and read rarely, like metrics, request counts and hit counts. AtomicLong when I need the exact current value in logic, like an id generator or "decrement if above zero".

The problem. AtomicLong.incrementAndGet() uses a CAS loop on one memory location. With 32 threads all incrementing, they keep hitting the same cache line and failing each other's CAS; most of the time is spent retrying, and that cache line bounces between cores.

The idea behind LongAdder. Do not make everyone fight over one variable. Keep a small array of cells (the "striping" or "sharding" idea). Each thread tends to update its own cell, so there is little or no contention. When you ask for the total, add up all cells.

LongAdder hits = new LongAdder();
hits.increment();            // very cheap even with many threads
hits.add(5);
long total = hits.sum();     // adds base + all cells; NOT an atomic snapshot
hits.reset();                // or sumThenReset()

AtomicLong when the value drives logic: id generation, "decrement if above zero", sequence numbers. Related: LongAccumulator (min, max, or any associative function), DoubleAdder. Under low contention, LongAdder behaves like AtomicLong, so it is a safe default for counters.

What is false sharing, and how can it slow down concurrent code? Senior

False sharing is a performance problem: two threads write to two different variables that happen to sit on the same CPU cache line (usually 64 bytes). The hardware moves whole cache lines between cores, so each write invalidates the other core's copy and the line bounces back and forth, even though the threads share no data logically. The code is correct but much slower than expected.

How it happens. A CPU does not cache single variables; it caches 64-byte lines. If thread 1 updates counterA and thread 2 updates counterB, and both fields are neighbours in memory (for example two long fields of one object, or adjacent array elements), they live on one line.

class Counters { volatile long a; volatile long b; }   // a and b are probably on one cache line

core 1 writes a -> core 2's copy of the line is invalidated
core 2 writes b -> core 1's copy is invalidated (must reload the line)
...repeat millions of times: each write becomes a cache miss

Fixes.

  • Padding: put unused fields between hot variables so each lands on its own line. This is what LongAdder's cells do internally (with the JDK-internal @Contended annotation).
  • Use LongAdder or per-thread state that is merged later, instead of hand-padding.
  • Re-layout data so that things written by different threads are not adjacent (separate arrays, or chunks that are larger than a line).

How to recognize it. Throughput does not scale as you add threads even though there is no lock contention, and a profiler shows many cache misses on small fields. It is a micro-level concern: I would mention it as the reason for striping in LongAdder and for padding in high-performance queues (for example the Disruptor), not something to fix without measurements.

Remember: unrelated variables on one 64-byte cache line make cores fight. Pad them apart or stripe the state.

What is ThreadLocal and when do you use it? Intermediate

ThreadLocal gives each thread its own private copy of a variable, so no locking is needed. Typical uses are per-request context (user id, trace id, tenant) in a web server, and per-thread non-thread-safe helper objects like the old SimpleDateFormat.

The idea. Instead of sharing one variable among threads and protecting it, give every thread its own copy. No sharing means no locking. A ThreadLocal<T> is a handle: when you call get() or set(), it reads or writes the value belonging to the calling thread.

How it works inside. Each Thread object has a private map (ThreadLocalMap) from ThreadLocal objects to values. tl.get() means "look up tl in my thread's map".

static final ThreadLocal<String> TRACE_ID = new ThreadLocal<>();

// in a servlet filter
TRACE_ID.set(newId());
try {
    chain.doFilter(req, res);        // any code in this thread can call TRACE_ID.get()
} finally {
    TRACE_ID.remove();               // ALWAYS clean up (pooled threads are reused)
}

Typical uses.

  • Per-request context that would otherwise need to be passed through every method: trace id, user, tenant, locale, security context, logging MDC. Frameworks (Spring Security, Logback MDC) use it heavily.
  • Non-thread-safe helpers that are costly to create: the old SimpleDateFormat, a MessageDigest, a buffer. (Better today: use immutable DateTimeFormatter.)

Cautions.

  • Pools reuse threads: a value set by request 1 is still there for request 2 unless removed.
  • Not inherited by new threads or async tasks: a task submitted to an executor runs on another thread and sees an empty ThreadLocal. InheritableThreadLocal copies only when a thread is created, which does not help with pools. Frameworks use task decorators to copy context explicitly.
  • Hidden state: hard to test and hard to follow.
  • Virtual threads: they support thread locals, but with millions of virtual threads each holding a big value, memory adds up. ScopedValue (final in Java 25) is the intended immutable, bounded-lifetime alternative.

Remember: ThreadLocal = one copy per thread. Set and remove in the same try/finally.

How can ThreadLocal cause a memory leak or data leak? Senior

Pooled threads never die, so their ThreadLocalMap lives as long as the pool. The map holds the key (the ThreadLocal) weakly, but the value strongly. If I never call remove(), the value stays reachable from the thread forever. That is a memory leak. It can also be a data leak: the next request on that thread reads the previous user's value.

Where the data lives. The value is not stored in the ThreadLocal object; it is stored in the thread's own map. So the value is reachable for as long as the thread is alive. In a thread pool (Tomcat's 200 workers, an executor), threads live for the whole life of the application. A value you set and never removed stays reachable until that thread overwrites it, which may be never.

The weak-key detail, and why it does not save you. The map entry holds the ThreadLocal (key) through a weak reference but the value strongly. When your code drops the ThreadLocal, the key can be collected, leaving an entry (null key, big value). The JDK cleans such stale entries only lazily, when the map happens to be touched, so you cannot rely on it. And while a ThreadLocal is still referenced (a static field, the normal case), nothing is collected at all.

Two different bugs with the same cause:

  1. Memory leak. A big object (a cache, a buffer, a byte[] per request) stays reachable on each pooled thread. Worse on an application server with redeploys: if the value's class (or the ThreadLocal's class) comes from the web application's class loader, the pooled thread keeps that whole class loader and every class in it alive. Each redeploy adds another copy: OutOfMemoryError: Metaspace. Tomcat even logs "created a ThreadLocal with key ... but failed to remove it".
  2. Data leak (a security bug). Request 1 of user Alice sets CURRENT_USER = alice on worker 17 and forgets to remove it. If request 2 on worker 17 does not set it (a path that skips the filter, or an error before the set), it reads Alice's identity. Wrong data shown to the wrong tenant.

The fix is a pattern, not a tool.

CTX.set(value);
try { handle(); }
finally { CTX.remove(); }     // in the same method, in a filter/interceptor/task wrapper

Put it in one place (a servlet filter or HandlerInterceptor for requests; a decorated executor for tasks) so no code path can forget. Diagnose with a heap dump: in a tool such as Eclipse MAT, follow the path from the leaked object to GC roots: thread, ThreadLocalMap, Entry, value.

Remember: in a pool, a ThreadLocal without remove() leaks memory and leaks the last user's data.

5. Thread safety design

How do you make a class thread-safe? What are the strategies? Intermediate

In order of preference: do not share (keep state local to a method, or confined to one thread), share but do not mutate (immutable objects), or share and mutate with a clear rule: one lock that guards each piece of state, an atomic variable, or a concurrent collection. I pick the rule that removes the most risk first.

Start from the cause. Bugs need state that is both shared and mutable. Remove either word and the problem disappears. So the strategies are ordered by how much of the problem they delete:

  1. Do not share (confinement). Keep data local to one method (locals live on the thread's stack), or owned by exactly one thread. A single "owner" thread that receives commands through a queue is the actor-style pattern: only it touches the state. ThreadLocal is another form.
  2. Share but do not mutate (immutability). Final fields, no setters, copy on change. No writes means no races, and no locks needed.
  3. Share and mutate, with a written rule. Pick one mechanism per piece of state and apply it everywhere: one lock guarding all accesses (reads included), an atomic variable, or a concurrent collection.
// 3. one lock guards BOTH fields; the invariant is: low <= high
class Range {
    private int low, high;                // guarded by this
    synchronized void setLow(int v)  { if (v > high) throw new IllegalArgumentException(); low = v; }
    synchronized void setHigh(int v) { if (v < low)  throw new IllegalArgumentException(); high = v; }
    synchronized boolean contains(int v) { return low <= v && v <= high; }
}

Design rules that go with them.

  • Name the guard. Next to each shared field write which lock protects it (// guarded by lock). If you cannot say it, nobody can review it.
  • Invariants over several fields need one lock covering all of them (the example above).
  • Composing thread-safe parts does not give a thread-safe whole. Two ConcurrentHashMaps updated in sequence can still be seen half-updated.
  • Do not leak: do not let this escape in a constructor, do not return internal mutable collections, and do not call unknown code (listeners, overridable methods) while holding a lock.
  • Keep critical sections small and never do IO inside them.

In a Spring application the practical version is: singleton beans must be stateless or hold only immutable or thread-safe state; per-request data lives in method parameters, not in bean fields.

Remember: don't share, don't mutate, or guard with one clear rule. Prefer them in that order.

How do you create an immutable class, and why is it automatically thread-safe? Intermediate

Make the class final, all fields private final, no setters, and defensively copy any mutable object that goes in or comes out. Since nothing can change after construction, there is nothing to race on, and final-field semantics guarantee other threads see the fully built object. Immutable objects need no locks at all.

Why immutable means thread-safe. All the hazards of concurrency come from writes that others can see in an inconsistent state. If an object never changes after construction, there is no inconsistent state to see. Add the Java Memory Model's final-field guarantee: after the constructor finishes, every thread that gets a reference is guaranteed to see the final fields set correctly, even if the reference was published through a data race. So immutable objects can be shared freely with no lock, no volatile and no copies.

Recipe.

  1. Declare the class final (so nobody subclasses it and adds mutable state), or make the constructor private with factories.
  2. Make every field private final.
  3. No setters or any method that changes state.
  4. Do not let this escape from the constructor.
  5. Defensive copies of mutable inputs (on the way in) and outputs (on the way out).
public final class Order {
    private final String id;
    private final List<Item> items;                     // List is mutable, so protect it
    public Order(String id, List<Item> items) {
        this.id = id;
        this.items = List.copyOf(items);                // copy IN; result is unmodifiable
    }
    public List<Item> items() { return items; }         // already unmodifiable: safe to return
    public Order withItem(Item i) {                     // "change" = build a new object
        var n = new ArrayList<>(items); n.add(i);
        return new Order(id, n);
    }
}

The "shallow" trap. final List<Item> items only freezes the reference, not the list's contents. Without List.copyOf, the caller who passed the list could still modify it later, and the "immutable" object changes. The elements themselves must be immutable too (or copied). Java records are the same: components are final, but a List component is still mutable unless you copy it in the compact constructor.

Costs. Each "change" allocates a new object; usually cheap, and the JVM is good at short-lived garbage. Large collections need persistent or copy-on-write structures. The JDK models are immutable on purpose: String, Integer, java.time.*, List.of.

Remember: final class, final fields, copy mutable parts in and out. Immutable means no locks.

How do you write a thread-safe singleton? Intermediate

The simplest correct choices are an enum singleton or the holder-class idiom. Both are lazy and thread-safe because the JVM initializes a class exactly once under its own lock. In a Spring app I just declare a bean, which is a singleton by default.

Two separate questions. (1) Is the creation of the single instance thread-safe? (2) Is the instance's state thread-safe? Interviews ask about the first; real bugs come from the second.

Safe creation options.

// 1. Eager: created when the class loads. Simple, thread-safe, not lazy.
class A { static final A INSTANCE = new A(); private A() {} }

// 2. Holder class idiom: lazy AND thread-safe, no locks, no volatile.
class Registry {
    private Registry() {}
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    static Registry get() { return Holder.INSTANCE; }   // Holder loads on the first call
}

// 3. Enum: lazy, thread-safe, safe against reflection and serialization copies.
enum Cache { INSTANCE; public Object get(String k) { return null; } }

Why 2 and 3 are safe. The JVM guarantees that a class is initialized exactly once, under an internal lock, and that the result is visible to all threads (class initialization has happens-before semantics). So you borrow the JVM's own once-only machinery instead of writing your own locks.

Other options. Double-checked locking works only with a volatile field (see the DCL question). A plain synchronized static get() is correct but locks on every call. In a Spring or CDI application, do not write singletons at all: declare a bean, since the default scope is singleton, and inject it. That also makes tests easy (inject a fake).

The state trap. A singleton is shared by every thread by definition. If it holds a mutable field such as a HashMap cache, a SimpleDateFormat, or "current user", it needs its own protection (ConcurrentHashMap, immutable fields, or no per-request state). Thread-safe construction does nothing for that.

Remember: enum or holder class. Thread-safe creation does not make the object's state thread-safe.

How do you reduce lock contention? Senior

Hold locks for less time and lock less data per lock. Do slow work (IO, remote calls, heavy computing) outside the critical section, split one big lock into several independent ones, use striping or concurrent structures, and replace locks with immutable snapshots, atomics or LongAdder where possible.

What contention is. A lock is contended when threads regularly arrive while another holds it. They go BLOCKED or parked, CPU sits idle, latency rises, and throughput stops growing as you add threads. The cure is to reduce either how long the lock is held, or how often different threads need the same lock.

1. Hold it for less time. The biggest win is usually moving slow work outside the lock.

// bad: remote call while holding the lock; everyone queues behind a 200 ms call
synchronized (cache) {
    if (!cache.containsKey(id)) cache.put(id, remote.load(id));
}
// better: do the slow part outside, then update quickly
Value v = cache.get(id);
if (v == null) { v = remote.load(id); cache.putIfAbsent(id, v); }   // ConcurrentHashMap

Other ways: copy the data under the lock and process the copy outside; precompute before locking; never do IO, logging of big objects or callbacks inside a lock.

2. Lock less data per lock (split the lock).

  • Lock splitting: separate unrelated fields under separate locks (users and orders each have their own).
  • Lock striping: an array of locks chosen by key hash, so different keys rarely collide. ConcurrentHashMap (per-bin locking) and LongAdder (per-thread cells) are built on this idea.

3. Do not lock at all where you can avoid it.

  • Atomic classes or LongAdder for counters.
  • Immutable snapshot swapped by an AtomicReference or volatile for read-mostly data; CopyOnWriteArrayList for tiny read-mostly lists.
  • Read/write locks or StampedLock when reads dominate and are not tiny.

4. Measure first. A thread dump showing many threads BLOCKED on one monitor address, or JFR (jdk.JavaMonitorEnter) / async-profiler lock mode, tells you which lock is hot. Splitting a lock that is not hot only adds deadlock risk. If you split, keep a global lock order. Also remember Amdahl's law: if 20% of the work is serialized behind a lock, the best speed-up is 5x no matter how many cores you have.

Remember: shorter sections, smaller scope, no IO under a lock. Measure before splitting.

6. Executors and thread pools

Why use a thread pool instead of creating a thread per task? Basic

Because threads are expensive and unlimited threads kill the server. A pool reuses a fixed set of threads, so there is no creation cost per task, and its size is a hard cap on concurrency. When load rises beyond the cap, work waits in a queue instead of exhausting memory and CPU.

What a thread costs. A platform thread is an OS thread. Creating one takes tens to hundreds of microseconds, reserves about 1 MB of stack address space (-Xss, committed lazily), and registers with the scheduler. Each running thread also adds context-switch overhead and thrashes CPU caches. For a task that runs 2 ms, spending 0.1 ms to create a thread for it is a 5% tax, and the real danger is the lack of any limit.

// thread-per-task: no limit, no reuse
for (Request r : requests) new Thread(() -> handle(r)).start();
// 20,000 requests at once -> 20,000 threads -> 20 GB of stack reserved,
// heavy context switching, then: OutOfMemoryError: unable to create native thread

What a pool gives you.

  1. Reuse: worker threads are created once and loop taking tasks from a queue. No per-task creation cost.
  2. A cap: the maximum pool size is a hard limit on concurrency, so the machine, the database and downstream services are protected.
  3. Queueing: bursts above the limit wait in a queue (ideally a bounded one) instead of overloading the system.
  4. One place for management: thread names, uncaught exception handling, metrics (active threads, queue length), shutdown.
20 requests arrive, pool of 4 workers, tasks take 100 ms each:
workers: 4 busy at once, 16 wait in the queue
total time about 5 x 100 ms = 500 ms, memory stays flat, no thread explosion

Analogy: a fixed number of cashiers with a single line, instead of hiring a new cashier for every customer who walks in.

Exception to the rule. Virtual threads (Java 21) are so cheap, a few hundred bytes to kilobytes of heap each, that you create one per task and do not pool them. You still need a limit somewhere (a semaphore or a connection pool), because the cap that the pool used to provide is gone.

Remember: a pool = reuse + a cap + a queue + one place to manage threads.

How does ThreadPoolExecutor handle a new task? Explain core size, queue and max size. Intermediate

In this order: if fewer than corePoolSize threads are running, start a new thread for the task. Otherwise put the task in the queue. Only if the queue is full, start extra threads up to maximumPoolSize. If the queue is full and the pool is at max, the rejection policy runs.

The four settings. corePoolSize (threads kept even when idle), workQueue (where tasks wait), maximumPoolSize (hard cap on threads), and the RejectedExecutionHandler (what happens when no more room). The order of use is the part people get wrong.

Rule for each new task:

  1. Fewer than core threads running: start a new thread, even if other threads are idle.
  2. Otherwise try to put the task in the queue.
  3. If the queue is full and fewer than max threads: start an extra thread.
  4. Queue full and at max: reject.

Worked example. core = 2, max = 4, queue = ArrayBlockingQueue(2). Tasks arrive faster than they finish:

task1 -> new thread T1 (core)          threads: 2   queue: []
task2 -> new thread T2 (core)          threads: 2   queue: []
task3 -> queue                         threads: 2   queue: [3]
task4 -> queue                         threads: 2   queue: [3,4]   (full)
task5 -> queue full, below max: T3     threads: 3   queue: [3,4]
task6 -> new thread T4                 threads: 4   queue: [3,4]
task7 -> at max, queue full -> REJECTED (AbortPolicy throws RejectedExecutionException)

The surprise: max is reached last. Extra threads appear only when the queue is full. With an unbounded queue (new LinkedBlockingQueue<>()), it never fills, so the pool never grows beyond core and maximumPoolSize is silently ignored. With a SynchronousQueue (capacity 0, direct hand-off), the queue is "always full", so the pool grows straight to max: that is the cached pool.

Shrinking. Threads above core that are idle longer than keepAliveTime exit. With allowCoreThreadTimeOut(true) core threads may too.

new ThreadPoolExecutor(
    8, 16,                                   // core, max
    60, TimeUnit.SECONDS,                    // keepAlive for threads above core
    new ArrayBlockingQueue<>(200),           // BOUNDED queue
    namedThreadFactory("orders"),            // readable thread names in dumps
    new ThreadPoolExecutor.CallerRunsPolicy());   // back-pressure when full

Inside: each worker is a thread running a loop: take a task from the queue (or run its first task), run it, repeat. A task that throws does not kill the pool; the worker is replaced.

Remember: core first, then queue, then up to max, then reject. Max grows only when the queue is full.

Which queue and which rejection policy do you pick? Intermediate

A bounded queue, sized to the burst I am willing to absorb, and a rejection policy that tells callers to slow down: CallerRunsPolicy for internal back-pressure, or AbortPolicy (the default) when I can return "busy" to the client. I avoid unbounded queues and silent discards.

Two decisions, one purpose. The queue decides how much burst you absorb. The rejection policy decides what the caller experiences when you cannot absorb any more. Together they decide whether an overload becomes slow-but-fine, a clean error, or an outage.

Queue choices.

  • ArrayBlockingQueue or a bounded LinkedBlockingQueue: the normal choice. Caps memory and gives back-pressure.
  • Unbounded LinkedBlockingQueue: avoid. The pool never grows past core, the queue grows without limit, latency grows with it, and eventually OutOfMemoryError.
  • SynchronousQueue: no buffer; each task must be handed to a free thread directly, else a new thread (up to max) or rejection. Used by the cached pool.
  • PriorityBlockingQueue: run urgent tasks first; unbounded, so combine it with another limit.

How big? Size the queue by latency, not by feel. If a task takes 5 ms and 8 workers drain the queue, a queue of 10,000 means the last request waits about 10,000 x 5 ms / 8 = 6 seconds, probably after the client gave up. A small queue plus fast rejection is often better than a long one.

Rejection policies (used when queue is full and threads are at max, or after shutdown):

PolicyBehaviorUse when
AbortPolicy (default)Throws RejectedExecutionExceptionYou can return "busy" (HTTP 503/429) and must handle the exception
CallerRunsPolicyThe submitting thread runs the task itselfNatural back-pressure: producer slows down. Avoid if the caller must stay responsive (event loop)
DiscardPolicySilently drops the new taskTruly optional work (metrics sample)
DiscardOldestPolicyDrops the oldest queued task, retries the new oneOnly the freshest data matters

You can also write your own handler: log, increment a "rejected" metric, and return an error. Alert on the rejected count; a silently discarding pool hides data loss.

Remember: bounded queue plus a rejection policy that pushes back. An unbounded queue is a hidden memory leak.

Why do many teams ban the Executors.newFixedThreadPool and newCachedThreadPool factory methods? Intermediate

Because both hide an unbounded resource. newFixedThreadPool uses an unbounded queue, so a slow consumer lets tasks pile up until the heap runs out. newCachedThreadPool allows an unlimited number of threads, so a burst can create thousands and fail with "unable to create native thread". I build a ThreadPoolExecutor myself with bounded settings.

The factories are convenient, but each one hides an unbounded resource. Look at what they build:

What I do instead. Build a ThreadPoolExecutor explicitly with a bounded queue, a rejection policy, a sensible max, and a named ThreadFactory. The explicit constructor makes the limits visible in code review, which is the real reason many style guides (for example the Alibaba Java guideline) forbid the factory methods.

Further good habits. Name threads ("orders-pool-3") so dumps are readable. Set an uncaught exception handler. Use a separate pool per kind of work, so slow IO tasks cannot starve quick CPU tasks (bulkhead). Export queue size, active count and rejected count as metrics. With virtual threads on Java 21, newVirtualThreadPerTaskExecutor() removes the thread limit, so then add a semaphore to cap concurrency.

Remember: Executors factories hide unbounded queues or unbounded threads. Build a ThreadPoolExecutor with limits.

How do you decide the size of a thread pool? Intermediate

It depends on what the tasks do. For CPU-bound work, about the number of cores (or cores + 1). For IO-bound work, more: roughly cores x (1 + wait time / compute time). Then I load test and adjust, because the formula is only a start.

Why the right size matters. Too few threads: CPUs sit idle while tasks wait. Too many: context switching, memory use, and overload of downstream systems. The answer depends on what a task spends its time doing.

CPU-bound tasks (compute, parsing, compression): a thread is always using a core. More threads than cores only adds switching. Use about N_cpu or N_cpu + 1.

IO-bound tasks (database, HTTP, disk): a thread spends most of its time waiting, so the core is free for other threads. You can run more threads than cores. A rule of thumb (from Brian Goetz, "Java Concurrency in Practice"):

threads = cores x target_utilization x (1 + wait_time / compute_time)

Example. 8 cores, task = 10 ms of compute + 90 ms waiting on a database. Ratio is 9.

threads = 8 x 1.0 x (1 + 90/10) = 80
throughput at 80 threads  = 80 / 0.1 s = 800 tasks per second
throughput at 8 threads   =  8 / 0.1 s =  80 tasks per second (cores idle 90% of the time)

But the chain has a smallest link. If the database connection pool allows only 20 connections, 80 threads just wait for connections, adding memory and latency for nothing. Size by the tightest limit among: threads, DB connections, remote rate limits, memory per task. A related check is Little's law: concurrency = arrival rate x latency. To handle 500 requests/s at 200 ms each, you need about 100 requests in flight, so about 100 threads (or virtual threads).

Practical advice.

  • Use separate pools for CPU work and for blocking IO. Do not mix.
  • Treat the formula as a start, then load test and watch queue length, active threads and p99 latency.
  • Containers: availableProcessors() follows the CPU limit of the container, so check what your JVM actually sees.
  • On Java 21, blocking IO tasks do not need a sized pool: use virtual threads and a semaphore to cap what the downstream can take.

Remember: CPU-bound = cores, IO-bound = cores x (1 + wait/compute), capped by the slowest dependency.

What is the difference between execute() and submit()? What happens to exceptions? Intermediate

execute(Runnable) returns nothing; an exception escapes to the thread's uncaught exception handler, and that worker thread dies and is replaced. submit() returns a Future and captures any exception inside it, so nothing is printed and the error appears only when someone calls get().

Same job, different failure behavior. Both hand a task to the pool. The difference is what happens to the result and to exceptions.

execute(Runnable)submit(Runnable/Callable)
Returnsnothinga Future
Task throwsGoes to the thread's uncaught exception handler (stack trace on stderr by default); the worker thread dies and the pool replaces itThe exception is stored inside the Future; nothing is printed; the worker survives
You see the errorIn logs, immediatelyOnly when someone calls future.get()

The production trap. With submit and a "fire and forget" style, a failing task disappears without a trace:

pool.submit(() -> { throw new IllegalStateException("boom"); });   // no log, no error, nothing
// if nobody calls get(), the failure is never noticed: jobs "silently do nothing"

pool.submit(() -> {
    try { work(); }
    catch (Throwable t) { log.error("task failed", t); }           // log INSIDE the task
});

Fixes. Either catch and log inside every task (wrap tasks in a helper), or keep the future and handle it later (get(), or CompletableFuture.whenComplete). For execute, set a thread factory with an UncaughtExceptionHandler so even escaping exceptions get logged and metered. afterExecute in a ThreadPoolExecutor subclass can also inspect throwables, and for submit you must unwrap the Future there.

What the exception looks like at get(): wrapped in ExecutionException; the real error is e.getCause(). A task that throws never harms the pool, only itself. The same "exception hides in the future" rule applies to CompletableFuture and to scheduled tasks.

Remember: submit swallows exceptions into the Future. Always log inside the task or call get().

How do you shut down an executor properly? Intermediate

Call shutdown() to stop accepting new tasks while finishing queued ones, wait with awaitTermination(timeout), and if it times out call shutdownNow(), which interrupts running tasks and returns the tasks that never started. One owner is responsible for this, usually at application stop.

Why it matters. A pool's worker threads are usually non-daemon, so an executor that is never shut down keeps the JVM alive after main ends, and on application stop its threads may be killed in the middle of a task. A graceful shutdown lets in-flight work finish and stops new work coming in.

Three methods:

  • shutdown(): no new tasks accepted (they get rejected); already submitted tasks, queued ones included, still run. Returns immediately.
  • awaitTermination(timeout): blocks until all tasks have finished or the time is up. Returns true if finished.
  • shutdownNow(): attempts to stop now: clears the queue (returns those never-started tasks as a list) and interrupts running workers. It only sends interrupts; a task that ignores interruption keeps running.
pool.shutdown();                                         // 1. stop intake
try {
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {  // 2. wait politely
        List<Runnable> dropped = pool.shutdownNow();     // 3. then interrupt
        if (!pool.awaitTermination(10, TimeUnit.SECONDS))
            log.warn("pool did not terminate; {} tasks never started", dropped.size());
    }
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}

Timeline: t=0 shutdown(): 40 tasks queued, 8 running. t=0 to 12 s: tasks drain. t=12 s: terminated, awaitTermination returns true. If tasks were still running at 30 s, shutdownNow() interrupts them, and their code must respond to interruption (see the interrupt question) or the pool never ends.

Modern shortcuts. Since Java 19, ExecutorService is AutoCloseable: try (var exec = Executors.newFixedThreadPool(4)) { ... } calls shutdown and waits for termination on exit. Spring's ThreadPoolTaskExecutor has setWaitForTasksToCompleteOnShutdown(true) and setAwaitTerminationSeconds. Give each executor one owner that is responsible for closing it.

Remember: shutdown, awaitTermination, then shutdownNow. Forgetting it keeps the JVM alive.

Can a thread pool deadlock itself? Senior

Yes: thread-starvation deadlock. If a task running in a pool submits a subtask to the same pool and blocks waiting for it, then when all threads are busy waiting for subtasks that sit in the queue, nobody is left to run them, and everything hangs. There is no lock cycle, so the deadlock detector says nothing.

The pattern. A pool deadlocks itself when tasks running in it wait for other tasks that are queued in the same pool. There is no lock cycle; the cycle is between "threads" and "queue slots".

ExecutorService pool = Executors.newFixedThreadPool(2);

Future<String> parent = pool.submit(() -> {
    Future<String> child = pool.submit(() -> "data");   // goes to the queue
    return child.get();                                  // parent holds a thread and waits
});

Timeline with a pool of 2 threads and two parents submitted at once:

Thread-1: runs parentA -> submits childA -> childA waits in the queue -> parentA blocks in get()
Thread-2: runs parentB -> submits childB -> childB waits in the queue -> parentB blocks in get()
Queue: [childA, childB]   Free threads: 0
childA needs a thread; both threads are waiting for children. Nothing can ever run. Hang forever.

It also happens with a single-thread executor (one task waiting on another submitted to itself), and with a larger pool under heavy load: it is intermittent, which makes it nasty. All threads fill up with parents only when enough arrive at once.

How to recognize it. The deadlock detector says nothing (no locks involved). A thread dump shows every worker in Future.get, CompletableFuture.join or CountDownLatch.await, while the queue is non-empty and CPU is idle. Application hangs under load but works in light tests.

Fixes.

  • Separate pools: parent tasks in one pool, child tasks in another, so children can always run.
  • Do not block in pool threads: chain with thenCompose/thenCombine instead of calling get() in the middle.
  • Use ForkJoinPool for recursive subtask work: a worker waiting in join() runs other queued subtasks meanwhile, so it cannot starve.
  • Bound the fan-out so parents cannot occupy every thread, and use timeouts on get so a stall at least becomes an error.

Remember: never block a pool thread on work that needs the same pool. Separate pools or async chaining.

How do scheduleAtFixedRate and scheduleWithFixedDelay differ? What if the task throws? Intermediate

Fixed rate starts runs at fixed intervals (0, 10 s, 20 s ...) measured from the start. Fixed delay waits the given time after the previous run ends. And if a periodic task throws an exception, all further runs are silently cancelled, so I always wrap the body in try/catch.

The difference in one timeline (period/delay 10 s, each run takes 3 s):

scheduleAtFixedRate(task, 0, 10, SECONDS):       starts at 0, 10, 20, 30 ...  (start-to-start = 10 s)
  run:  [0-3]       [10-13]      [20-23]
scheduleWithFixedDelay(task, 0, 10, SECONDS):    waits 10 s AFTER each run ends
  run:  [0-3] ...wait 10... [13-16] ...wait 10... [26-29]    (end-to-start = 10 s)
  • Fixed rate targets a steady schedule on the clock (a heartbeat every 10 s). If a run takes longer than the period, the next one starts as soon as the previous finishes (late, and executions of the same task never overlap). After a long pause it may fire several times in a quick catch-up.
  • Fixed delay guarantees a rest period between runs. Prefer it for polling or cleanup where overlap or bunching would hurt.

The big trap. If one execution throws (even a RuntimeException), all later executions are suppressed and the exception is stored in the returned ScheduledFuture. Nothing is logged unless you call get(). So the job runs fine for weeks and then stops forever after one bad day. Always wrap the body:

ScheduledFuture<?> f = scheduler.scheduleWithFixedDelay(() -> {
    try { poll(); }
    catch (Throwable t) { log.error("poll failed, will retry next cycle", t); }
}, 0, 10, TimeUnit.SECONDS);

Other things to know. A pool of 1 thread runs jobs one after another, so one slow job delays all others; size it for the number of long jobs. newScheduledThreadPool uses an unbounded delay queue. Spring's @Scheduled logs the error and continues, but by default uses a single scheduler thread (configure spring.task.scheduling.pool.size). Add a "last successful run" metric and an alert, so silence becomes a visible failure.

Remember: rate = fixed start times, delay = gap after end. Catch everything inside a periodic task.

What is the Fork/Join framework and work stealing? Intermediate

Fork/Join is a pool for divide-and-conquer work: a task splits itself into smaller subtasks (fork), waits for them (join) and combines results. Each worker has its own deque (double-ended queue) of tasks, and an idle worker steals tasks from the far end of a busy worker's deque, so all cores stay busy without a single shared queue.

What it is for. Divide-and-conquer on CPU-bound data: split a big job into halves until the pieces are small, compute them in parallel, then combine. Example: sum an array of 100 million numbers by splitting it recursively.

class SumTask extends RecursiveTask<Long> {
    final long[] a; final int lo, hi;
    SumTask(long[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }
    protected Long compute() {
        if (hi - lo <= 10_000) {                       // small enough: do it directly
            long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s;
        }
        int mid = (lo + hi) / 2;
        SumTask left = new SumTask(a, lo, mid), right = new SumTask(a, mid, hi);
        left.fork();                                   // run left asynchronously
        return right.compute() + left.join();          // run right here, then wait for left
    }
}
long total = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));

Work stealing: how it keeps cores busy. Each worker has its own double-ended queue (deque). A worker pushes and pops its own tasks at one end (newest first, which is cache-friendly). When a worker runs out of tasks, it steals from the opposite (oldest) end of another worker's deque. The oldest tasks are usually the biggest chunks, so one steal gives lots of work, and the two ends rarely collide.

Why no starvation deadlock. A normal pool thread that waits for a subtask just sleeps. A Fork/Join worker that calls join() keeps running other tasks (its own or stolen) until the subtask is done, so waiting is productive.

Where you meet it without writing it. The common pool (ForkJoinPool.commonPool(), about cores - 1 threads by default) runs parallel streams and default CompletableFuture async stages. Virtual threads are scheduled on a ForkJoinPool too.

Rules. CPU-bound, non-blocking tasks only; blocking IO inside ties up a scarce worker. Choose a sensible threshold for splitting: too small and the overhead of task objects beats the computation. For blocking work, use ForkJoinPool.managedBlock or a separate pool.

Remember: split, fork, join, and idle workers steal. CPU-bound work only, never blocking IO.

Should you use parallel streams? What are the risks? Intermediate

Only for CPU-heavy work on large data, with no side effects, and after measuring. They split the data across the shared common ForkJoinPool. For small collections, IO work, or code that calls blocking services, they are slower or harmful.

What it does. list.parallelStream() (or .parallel()) splits the source into chunks and processes them on the shared common ForkJoinPool plus the calling thread, then merges results. It is a one-word way to use all cores, which is why it is tempting and why it is misused.

When it can help. All of: (a) the work per element is CPU-heavy (roughly more than microseconds per item), (b) the data is big (thousands of elements or more), (c) the source splits cheaply (ArrayList, arrays, ranges; poor with LinkedList, Stream.iterate, or sources reading IO), (d) the operations are stateless and independent, (e) you measured and it is faster.

What goes wrong.

  • Shared common pool. Everything in the JVM that uses it (other parallel streams, default CompletableFuture async stages) competes for about cores - 1 threads. One parallel stream that blocks on HTTP or a database call can slow unrelated endpoints (see the scenario).
  • Shared mutable state. A lambda that adds to a shared ArrayList is a data race. Use collect, toList() or reduce, which are designed for parallel execution.
  • Order and reduction rules. reduce needs an associative function with a proper identity. forEach has no order; forEachOrdered keeps order but removes most parallelism. findFirst and limit on ordered streams can be costly.
  • Overhead beats gain. For 100 small items, splitting and merging costs more than the work; the parallel version is slower.
// wrong: race, may lose elements or throw
List<String> out = new ArrayList<>();
ids.parallelStream().forEach(id -> out.add(load(id)));

// right: let the stream collect safely (and not for IO-bound load() anyway)
List<String> out2 = ids.parallelStream().map(this::cpuHeavy).toList();

Rule I follow: default to a plain sequential stream; use a parallel one only for large, CPU-only, side-effect-free work after a benchmark, and for IO fan-out use a dedicated executor or virtual threads. Running inside your own ForkJoinPool.submit(...) is a known trick to avoid the common pool, but it is an implementation detail rather than a guaranteed contract.

Remember: parallel streams share one common pool. CPU-only, big data, no side effects, measured.

How does Spring's @Async run tasks, and what do people get wrong? Intermediate

With @EnableAsync, Spring wraps the bean in a proxy, and a call to an @Async method is handed to a TaskExecutor instead of running on the caller's thread. The caller gets a return of void, a Future or a CompletableFuture right away. The common mistakes are the default executor, self-invocation and lost context.

How it works. With @EnableAsync, Spring creates a proxy around beans that have @Async methods. When another bean calls such a method, the call goes through the proxy, which wraps the invocation in a task and submits it to a TaskExecutor. The caller returns immediately; the real method runs later on an executor thread.

@Service
class Mailer {
    @Async("mailPool")                          // name of YOUR executor bean
    public CompletableFuture<Void> send(Mail m) { smtp.send(m); return CompletableFuture.completedFuture(null); }
}
@Configuration @EnableAsync
class AsyncConfig {
    @Bean("mailPool") ThreadPoolTaskExecutor mailPool() {
        var e = new ThreadPoolTaskExecutor();
        e.setCorePoolSize(4); e.setMaxPoolSize(8); e.setQueueCapacity(100);   // bounded
        e.setThreadNamePrefix("mail-"); e.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        return e;
    }
}

What people get wrong.

  • Default executor. With no executor configured, plain Spring falls back to SimpleAsyncTaskExecutor, which starts a new thread for every call with no pooling or limit. Spring Boot auto-configures a ThreadPoolTaskExecutor (core size 8; the default queue capacity is unbounded, so check your version's settings), which is also not what you want under heavy load. Define your own bounded pool and name it.
  • Self-invocation. this.send(m) from another method of the same class skips the proxy, so it runs synchronously on the caller thread with no error. Move the method to another bean, or inject the bean into itself.
  • Return types. Only void, Future or CompletableFuture are meaningful. For void, an exception goes to AsyncUncaughtExceptionHandler; otherwise it is in the returned future.
  • Lost context. SecurityContext, request-scoped beans and logging MDC live in thread-locals and do not follow the task to another thread. Use a TaskDecorator that copies them (and clears them after).
  • Transactions. The async method runs in a different thread, so it does not participate in the caller's transaction: if the caller rolls back, the async work may already have happened. Run it after commit (for example with @TransactionalEventListener).
  • Fire and forget failures are invisible unless you log or handle them.

With Spring Boot 3.2+ on Java 21, spring.threads.virtual.enabled=true makes the default executors use virtual threads, which changes the sizing concerns (use a semaphore to cap concurrency).

Remember: @Async = proxy + executor. Configure a bounded pool, avoid self-calls, and propagate context.

7. CompletableFuture

What is CompletableFuture and why is it better than Future? Intermediate

CompletableFuture (Java 8) is a future you can chain. Instead of blocking on get(), I describe what happens next: thenApply to transform the result, thenCompose to start a dependent async call, thenCombine to merge two independent results, and exceptionally or handle for errors. Plain Future can only block and wait.

The problem with Future. A plain Future gives only get(). To use the result of call 1 in call 2 you must block a thread on get(), then start call 2. With three dependent calls, threads sit idle waiting, and you cannot say "when this finishes, do that". A CompletableFuture (Java 8) is a future that you can chain, combine and complete yourself: you describe what should happen when the result arrives, and the pipeline runs without anyone blocking.

CompletableFuture<OrderSummary> f =
    CompletableFuture.supplyAsync(() -> userClient.get(id), ioPool)   // stage 1, on ioPool
        .thenCompose(u -> CompletableFuture.supplyAsync(() -> ordersClient.forUser(u.id()), ioPool)) // stage 2 needs stage 1
        .thenApply(OrderSummary::from)                              // plain transform
        .exceptionally(e -> OrderSummary.empty());                  // fallback on any failure above
// nothing blocks here; call f.join() or thenAccept(...) at the edge of the system

Building blocks:

  • Start: supplyAsync(supplier, executor), runAsync, completedFuture(v), or new CompletableFuture<>() completed later by complete(v) / completeExceptionally(e). That last form is how you wrap a callback-based API.
  • Transform: thenApply (map), thenCompose (flatMap), thenAccept (consume), thenRun.
  • Combine: thenCombine (two futures), allOf, anyOf.
  • Errors: exceptionally, handle, whenComplete. Time: orTimeout, completeOnTimeout (Java 9).

Why it is better in practice. No thread waits for stage 1 while stage 2 is pending: each stage runs when its input is ready. Independent calls run in parallel and the total time is the slowest one, not the sum.

Costs. Stack traces are harder to read, errors are easy to lose, and it is tempting to call join() in the middle and block anyway. On Java 21, simple blocking code on virtual threads often replaces such chains with plain sequential code that scales just as well; CompletableFuture remains useful for explicit fan-out, combining results and APIs that already return it.

Remember: a Future you can chain, combine and recover from, without blocking.

What is the difference between thenApply, thenCompose and thenCombine? Intermediate

thenApply is map: transform the result with a plain function. thenCompose is flatMap: my function itself returns a CompletableFuture (a dependent async call), and it gets flattened. thenCombine merges two independent futures that run in parallel.

Same idea as Stream.map and flatMap. The difference is what your function returns.

MethodYour functionThinkResult
thenApply(fn)returns a plain value RmapCompletableFuture<R>
thenCompose(fn)returns a CompletableFuture<R> (another async call)flatMapCompletableFuture<R> (flattened)
thenCombine(other, fn)takes both results, returns a valuezip two independent futuresCompletableFuture<R>
CompletableFuture<User> user = getUserAsync(id);

// thenApply: the next step is plain, instant code
CompletableFuture<String> name = user.thenApply(User::name);

// thenCompose: the next step is ITSELF async (returns a future)
CompletableFuture<List<Order>> orders = user.thenCompose(u -> getOrdersAsync(u.id()));

// WRONG choice: thenApply here gives CompletableFuture<CompletableFuture<List<Order>>>
var nested = user.thenApply(u -> getOrdersAsync(u.id()));

// thenCombine: two independent calls started together, merged at the end
CompletableFuture<Page> page = getUserAsync(id).thenCombine(getAdsAsync(id), Page::new);

If you see a future inside a future in your types, you wanted thenCompose.

Latency effect. Suppose user lookup takes 100 ms, orders 200 ms, ads 150 ms. Sequential user then orders (compose) takes about 300 ms because the second needs the first. User and ads (combine) take about 150 ms, the slower of the two, not 250 ms, because both start immediately. Choose compose for dependency, combine for independence.

Related variants: thenAccept (consume the result, returns Void), thenRun (ignore the result), and the ...Async versions (run the step on an executor, covered next).

Remember: apply = map, compose = flatMap (dependent call), combine = two in parallel.

On which thread do CompletableFuture stages run? What does the Async suffix change? Senior

If I do not pass an executor, supplyAsync and the ...Async methods run on the shared ForkJoin common pool. The non-async methods like thenApply run on whichever thread completes the previous stage, or on the caller's thread if it is already complete. For blocking IO I always pass my own executor.

Where a stage runs depends on the method you chose.

CallThread that runs it
supplyAsync(fn) / runAsync(fn) (no executor)Shared ForkJoinPool.commonPool()
supplyAsync(fn, myExecutor)Your executor
thenApply(fn) (no Async)The thread that completes the previous stage; or, if the previous stage is already done when you attach, the thread that calls thenApply
thenApplyAsync(fn)Common pool (a new task is submitted)
thenApplyAsync(fn, myExecutor)Your executor

So the Async suffix means "do not run my callback inline on whoever finishes the previous step; schedule it as a new task".

Why this matters, three real problems.

  1. Blocking on the common pool. The common pool has about cores - 1 threads, and the whole JVM shares it (parallel streams too). A few blocking HTTP calls inside supplyAsync without an executor can freeze unrelated work. If the pool would have fewer than 2 threads (a 1-CPU container), CompletableFuture falls back to starting a new thread per task, which is also not what you want.
  2. A callback running on a sensitive thread. A non-async thenApply attached to a future completed by a Netty event loop or an HTTP client IO thread runs on that thread. A slow callback there stalls all IO handled by it.
  3. A heavy callback running on a thread you did not expect, such as the thread that happened to call complete().
private final Executor io = new ThreadPoolExecutor(20, 20, 0, SECONDS, new ArrayBlockingQueue<>(500), named("io"));

CompletableFuture.supplyAsync(() -> client.fetch(id), io)         // blocking call on MY pool
    .thenApply(this::parse)                                       // cheap, fine inline
    .thenApplyAsync(this::heavyTransform, cpuPool);               // heavy: explicit pool

Rules I follow: always pass an executor for IO; one bounded pool per kind of dependency (bulkhead); keep inline callbacks tiny; use ...Async(fn, executor) for anything heavy.

Remember: default is the shared common pool. Give blocking IO your own executor.

How do you handle errors in a CompletableFuture chain? Intermediate

An exception in any stage skips the following stages and ends in the final future. I recover with exceptionally (give a fallback value), handle (get both result and exception, return a new value), or observe it with whenComplete (it does not change the outcome). If nobody handles it, it stays hidden until someone calls get or join.

How failure flows. If a stage throws, its future completes exceptionally. Every dependent stage (thenApply, thenCompose ...) is skipped and its future also completes exceptionally with the same error. The error travels to the end of the chain, where someone must handle it.

MethodCalled whenWhat it does
exceptionally(fn)only on failureTurn the error into a fallback value
handle((v, ex) -> ...)alwaysSee result or error, return a new value: success or recovery in one place
whenComplete((v, ex) -> ...)alwaysSide effect only (log, metrics); result or error passes through unchanged
CompletableFuture.supplyAsync(() -> { throw new IllegalStateException("db down"); }, io)
    .thenApply(x -> x + "!")                      // skipped
    .orTimeout(2, TimeUnit.SECONDS)               // Java 9: fail with TimeoutException if too slow
    .handle((v, ex) -> ex == null ? v : fallback(ex))   // recover here
    .whenComplete((v, ex) -> { if (ex != null) log.error("pipeline failed", ex); });

Wrapping rules. The original exception may arrive wrapped: in later stages and in handle it is often a CompletionException with your exception as getCause() (a stage that fails directly may show the raw exception). future.get() throws a checked ExecutionException; join() throws an unchecked CompletionException. So unwrap before testing the type:

Throwable root = ex instanceof CompletionException ? ex.getCause() : ex;

Silent failure. A future that nobody reads never reports its exception. For fire-and-forget pipelines always end with whenComplete (or exceptionally) that logs. Timeouts: orTimeout fails the future; completeOnTimeout(default, t, unit) supplies a default. Note that these do not stop the underlying work; they only complete the future. And cancel(true) on a CompletableFuture does not interrupt the running task; it just completes the future with CancellationException.

Remember: exceptionally = fallback, handle = both, whenComplete = peek. Unhandled errors vanish silently.

How do you run several calls in parallel and wait for all of them? Intermediate

Start every call first as its own CompletableFuture on a proper executor, then combine with allOf(...), which completes when all are done. Then read each result with join(), which does not block any more because they are finished. anyOf completes when the first one does.

Goal. Call three services in parallel and merge: total latency should be the slowest call (say 300 ms), not the sum (700 ms).

The pattern. (1) Start all calls without waiting, each on a proper IO executor. (2) Combine them with allOf. (3) After it completes, read each result with join(); since the futures are done, join() does not block.

var a = CompletableFuture.supplyAsync(() -> svcA.call(), io);
var b = CompletableFuture.supplyAsync(() -> svcB.call(), io);
var c = CompletableFuture.supplyAsync(() -> svcC.call(), io);

CompletableFuture.allOf(a, b, c)
    .orTimeout(3, TimeUnit.SECONDS)        // bound the whole fan-out
    .join();                               // wait for all (throws if any failed or timed out)
Result r = merge(a.join(), b.join(), c.join());

Common mistakes.

  • Accidentally sequential: supplyAsync(A).join() before starting B makes B wait for A. Start all first.
  • allOf returns CompletableFuture<Void>, so results come from the original futures (a.join()).
  • One failure: if any future fails, allOf still waits for all of them, then completes exceptionally. Handle each branch (exceptionally to a default) if partial results are acceptable.
  • anyOf completes with the first to finish (result type is Object); useful for "fastest replica wins". It does not cancel the losers.
  • Unbounded fan-out: for a list of 100,000 items, starting a future per item floods the pool. Batch them or limit with a Semaphore.
// for a list: start all first (collect to list), THEN join in a second pass
List<CompletableFuture<Item>> fs = ids.stream().map(id -> CompletableFuture.supplyAsync(() -> load(id), io)).toList();
List<Item> items = fs.stream().map(CompletableFuture::join).toList();

On Java 21 an alternative is structured concurrency or simply one virtual thread per call; the idea of "start everything, then wait, with a timeout" stays the same.

Remember: start all, then allOf, then join. Add a timeout.

What are the common CompletableFuture mistakes in production code? Senior

Five: running blocking IO on the common pool, calling join() or get() inside another async stage (blocking a pool thread, which can starve the pool), no timeout, swallowed exceptions, and losing thread context (MDC, security, transaction) between stages.

Five mistakes I look for in code review, with why each hurts.

  1. Blocking IO on the common pool (no executor given). The shared pool is tiny and starves other work. Fix: pass a dedicated, bounded executor.
  2. Blocking inside a stage. Calling join() or get() inside a callback holds a pool thread idle. If the awaited future needs the same pool, you get the starvation deadlock from the executor section. Fix: chain with thenCompose and thenCombine instead of waiting.
  3. No timeout. A hung dependency means a future that never completes, a request that never returns and, under load, an exhausted pool. Fix: orTimeout on every external call, plus client timeouts.
  4. Lost or swallowed errors. A future nobody joins swallows its exception; exceptionally(e -> null) hides real failures behind a null that blows up later. Fix: log in whenComplete; return explicit fallbacks.
  5. Lost context. MDC logging fields, the Spring security context, tenant id and transaction are thread-bound and do not move to the pool thread. Fix: wrap the executor (for example Spring's TaskDecorator) to copy the context in and clear it afterwards.
// bad: blocks a pool thread inside a stage and has no timeout
cf1.thenApplyAsync(x -> cf2.join(), io);

// better: compose, with a timeout
cf1.thenCompose(x -> cf2).orTimeout(2, TimeUnit.SECONDS);

Plus two more. Unbounded fan-out (a future per item for a huge list) and assuming cancel interrupts the task (it does not). Cheap rule: every async stage that does IO names its executor, every external call has a timeout, and every chain ends in a handler.

Remember: own executor, timeout, handle errors, never block inside a stage, carry the context.

8. Synchronizers and concurrent collections

What is the difference between CountDownLatch and CyclicBarrier? Intermediate

CountDownLatch is a one-time gate: some threads call countDown(), other threads wait in await() until the count reaches zero, and then it stays open forever. CyclicBarrier makes N threads wait for each other at a meeting point, then all go together, and it resets for the next round.

The two questions they answer. CountDownLatch: "wait until N things have happened". CyclicBarrier: "wait until all N of us have arrived, then everyone goes together, and again next round".

CountDownLatchCyclicBarrier
Who waitsWaiters call await(); others call countDown() (different roles)All N parties call await() (same role)
ReusableNo, one-shot; the count never goes back upYes, resets automatically each round
When it opensCount hits 0N-th thread arrives (optionally runs a barrier action first)
FailureIf a worker forgets countDown, waiters hang (use a timeout)If one party is interrupted or times out, the barrier breaks: all waiters get BrokenBarrierException

Latch example 1: wait for workers.

CountDownLatch done = new CountDownLatch(3);
for (int i = 0; i < 3; i++)
    pool.execute(() -> { try { work(); } finally { done.countDown(); } });  // finally: never forget
done.await(10, TimeUnit.SECONDS);     // main continues once all 3 are finished

Latch example 2: start gate for a test. A latch of count 1 holds back all threads so they start at the same moment, and a second latch tells the test when all are done. That gives a sharp race to expose bugs.

Barrier example: phased work. Three threads each compute part of a simulation step; nobody may begin step 2 before all three finished step 1:

CyclicBarrier barrier = new CyclicBarrier(3, () -> mergeStep());   // action runs once per round
// in each of the 3 threads:
for (int step = 0; step < 100; step++) { computePart(step); barrier.await(); }

Memory effect: countDown() happens-before the return of await(), so waiters see the workers' writes. Related: Phaser is a flexible barrier where parties can register and deregister dynamically; Exchanger swaps data between two threads. In everyday code, CompletableFuture.allOf or ExecutorService.invokeAll often replace a latch.

Remember: latch = "wait for events", one use. Barrier = "wait for each other", reusable.

What is a Semaphore and when do you use it? Intermediate

A semaphore holds a number of permits. acquire() takes one and blocks if none are left, release() gives one back. I use it to limit how many threads use a resource at once: at most 10 concurrent calls to a partner API, 20 database-heavy tasks, or a bounded fan-out.

What it is. A counter of permits. acquire() takes a permit, and if none are left, waits. release() returns a permit and wakes a waiter. It limits how many threads can be in a section at the same time, whereas a lock allows exactly one.

private final Semaphore limit = new Semaphore(10);       // at most 10 concurrent calls

String call() throws InterruptedException {
    limit.acquire();                                      // 11th caller waits here
    try { return partnerApi.fetch(); }
    finally { limit.release(); }                          // ALWAYS release in finally
}

Timeline (3 permits, 5 threads):

t0: T1, T2, T3 acquire -> permits 0.   T4, T5 call acquire() -> WAITING
t1: T2 finishes, release() -> permits 1 -> T4 wakes and acquires -> permits 0
t2: T1 releases -> T5 acquires ... so never more than 3 inside at once

Typical uses.

  • Cap concurrent calls to a fragile or rate-limited downstream (bulkhead).
  • Cap concurrent heavy tasks (image resizing, report generation) to protect memory.
  • Replace the pool-size limit when you move to virtual threads: one virtual thread per task, a semaphore for the limit.
  • Simple resource pool (a fixed number of connection-like objects).

Options and details. tryAcquire() and tryAcquire(timeout) fail fast instead of waiting (good for load shedding: return HTTP 429 when busy). new Semaphore(n, true) is fair (FIFO). acquire(k) takes several permits at once.

Pitfalls. A semaphore has no owner: any thread can release, even one that never acquired, which silently raises the permit count above what you intended; and a missing release (forgot finally) leaks permits until everything stops. A semaphore with one permit looks like a lock but is not reentrant and not owner-checked.

Remember: semaphore = N permits to cap concurrency. Release in finally.

How does ConcurrentHashMap work, and how is it different from Hashtable and synchronizedMap? Intermediate

Hashtable and Collections.synchronizedMap lock the whole map on every call, so all threads queue up. ConcurrentHashMap (Java 8+) locks only one bucket at a time: it uses CAS to insert into an empty bucket and synchronized on the first node of a non-empty bucket, and reads take no lock at all. So many threads work in parallel.

The problem with the old designs. Hashtable and Collections.synchronizedMap(map) make every method synchronized on one lock, so only one thread at a time can use the map, even for reads of different keys. On 32 cores, 31 wait. And iterating a synchronized map still requires holding the lock manually.

How ConcurrentHashMap (Java 8+) does it. The table is an array of bins. For an operation on a key:

  • get: no lock at all. Table slots and node values are read with volatile semantics, so a reader sees a consistent, recent node.
  • put into an empty bin: a lock-free CAS installs the new node.
  • put into a non-empty bin: synchronized on the first node of that bin only, so writers to other bins proceed in parallel.
  • Long chains (at least 8 nodes, with a large enough table) are converted to red-black trees, as in HashMap, so a hash-collision attack does not turn operations into O(n).
  • Resizing is cooperative: threads that hit a resizing table help move bins.

(Java 7 used a fixed array of 16 "segments", each a lock; Java 8 replaced that with per-bin locking, which is finer and uses less memory.)

Hashtable / synchronizedMapConcurrentHashMap
LockingOne lock for the whole mapCAS and per-bin locks; lock-free reads
Null keys/valuesHashtable: no. synchronizedMap(HashMap): yesNo nulls at all
IteratorFail-fast (ConcurrentModificationException)Weakly consistent: never throws CME; may or may not show concurrent updates
Compound opsManual lockingAtomic putIfAbsent, compute*, merge

Why no nulls. In a concurrent map, get(k) == null would not tell you whether the key is absent or mapped to null, and you cannot check with containsKey because the map can change in between.

Cautions. size() and isEmpty() are only estimates under concurrent updates. Bulk operations (forEach, reduce, search with a parallelism threshold) exist. Using CHM does not make your multi-step logic atomic (next question).

Remember: CHM = CAS for empty bins, lock one bin otherwise, lock-free reads, no nulls. Not one global lock.

Is if (!map.containsKey(k)) map.put(k, v) safe on a ConcurrentHashMap? Intermediate

No. Each call is thread-safe, but two calls together are not: two threads can both see "absent" and both put. I use the atomic methods built for this: putIfAbsent, computeIfAbsent, compute, merge and replace.

Short answer: no. containsKey is atomic, put is atomic, but the pair is not. Another thread can slip in between your check and your act.

T1: containsKey("a") -> false
T2: containsKey("a") -> false
T1: put("a", v1)
T2: put("a", v2)           // overwrites v1; T1 keeps using an object nobody else knows

Use the single-call atomic methods. CHM runs each of them as one atomic step per key:

MethodUse
putIfAbsent(k, v)Insert only if no mapping; returns the existing value or null. (v is created even if not used)
computeIfAbsent(k, fn)Create the value lazily, only if absent; the creation runs once per key
compute(k, fn), computeIfPresentAtomic read-modify-write of one key
merge(k, v, fn)Insert v, or combine old and new: counters, sums
replace(k, old, new), remove(k, v)Conditional update / delete (CAS-like)
map.merge(word, 1, Integer::sum);                              // atomic counter per key
List<String> l = map.computeIfAbsent(key, k -> new ArrayList<>());   // atomic create
l.add(x);   // BUG: l is a plain ArrayList shared by all threads using this key!
// fix: map.compute(key, (k, cur) -> { var n = cur == null ? new ArrayList<String>() : new ArrayList<>(cur); n.add(x); return n; });
// or use a concurrent value type: ConcurrentHashMap<K, Queue<V>> / CopyOnWriteArrayList

Rules for the lambdas. They run while the bin is locked, so keep them short and fast: no blocking IO, no slow computation, and never touch the same map inside (it can deadlock or throw "Recursive update"; newer JDKs detect some cases). A slow computeIfAbsent blocks other threads with keys in the same bin.

The deeper lesson: a thread-safe container protects its own internal structure, not your logic. If the invariant spans the map plus something else (a counter next to the map, two maps), you need your own lock around the whole step.

Remember: the map is thread-safe, your check-then-act is not. Use putIfAbsent, computeIfAbsent, merge.

What is CopyOnWriteArrayList, and when do you use it instead of a synchronized list? Intermediate

CopyOnWriteArrayList copies the whole backing array on every write, and readers use the old array without any lock. It is ideal for small lists that are read very often and changed rarely, like listener lists or configuration. For frequent writes it is very slow, because each add copies the array.

How copy-on-write works. CopyOnWriteArrayList keeps its elements in an array that is never modified in place. A write (add, set, remove) takes a lock, copies the whole array, changes the copy, and swaps the reference. A read just reads the current array reference: no lock, no waiting, no ConcurrentModificationException.

array = [A, B, C]                       reader R1 starts iterating over this array
writer: copy -> [A, B, C, D]            then swaps the reference to the new array
R1 keeps iterating [A, B, C]            sees a consistent snapshot, not D
R2 starting now iterates [A, B, C, D]

Costs and benefits:

  • Reads and iteration: very fast and never blocked. Iterators are snapshots; iterator remove() and set() throw UnsupportedOperationException.
  • Writes: O(n) each (copy the whole array), plus garbage. Fine for 10 writes a day on 20 elements; terrible for 1000 writes a second on 100,000 elements.

Ideal use: listener or observer lists, small configuration lists, routing tables: read all the time, changed rarely. (CopyOnWriteArraySet is the set version.)

Versus Collections.synchronizedList. That wrapper puts a lock on every call, so readers block each other, and iteration is still unsafe unless you lock the list yourself for the whole loop:

List<String> list = Collections.synchronizedList(new ArrayList<>());
synchronized (list) { for (String s : list) use(s); }   // required, else ConcurrentModificationException

Choosing a concurrent collection:

What is a BlockingQueue and how does it help producer-consumer designs? Intermediate

A BlockingQueue is a thread-safe queue where put() blocks when it is full and take() blocks when it is empty. That one structure replaces hand-written wait/notify code for producers and consumers, and a bounded one gives back-pressure for free: fast producers are slowed down instead of filling memory.

The problem it removes. A producer-consumer design needs: a shared buffer, mutual exclusion on it, "wait if empty" for consumers and "wait if full" for producers. Writing that with wait/notify is the classic source of lost wakeups and deadlocks. A BlockingQueue does all of it inside one tested class.

The four method families (for the same operation, they differ in what they do when the queue cannot satisfy you):

ThrowsReturns special valueBlocksTimes out
Insertaddoffer (false if full)putoffer(e, t, unit)
Removeremovepoll (null if empty)takepoll(t, unit)

Back-pressure. With a bounded queue (capacity 100), if producers are faster than consumers the queue fills up and put() blocks the producers: the system slows its inputs instead of running out of memory. That is the main reason to choose a bounded queue. With offer, a full queue lets you shed load deliberately (reject the request).

Implementations:

  • ArrayBlockingQueue: fixed capacity, one lock, optional fairness.
  • LinkedBlockingQueue: linked nodes, separate locks for put and take (more throughput); unbounded unless you pass a capacity, so always pass one.
  • SynchronousQueue: capacity 0; each put waits for a take. Direct hand-off.
  • PriorityBlockingQueue: unbounded, ordered by priority.
  • DelayQueue: an element can be taken only after its delay has expired (schedulers, retry queues).
  • LinkedTransferQueue: hand-off plus buffering.

Stopping consumers. A consumer blocked in take() never ends by itself. Either interrupt it, or send a poison pill: a special element that tells the consumer to exit (one per consumer). The memory-visibility bonus: everything a producer did before put is visible to the consumer after the matching take.

Remember: bounded blocking queue = hand-off plus back-pressure. Prefer it over wait/notify.

9. Virtual threads and modern concurrency

What are virtual threads (Java 21) and how do they work? Intermediate

Virtual threads are lightweight threads managed by the JVM instead of the OS. I write normal blocking code, but when a virtual thread blocks (on a socket, a sleep, a queue), the JVM unmounts it from its carrier thread (a real OS thread) and the carrier runs another virtual thread. So a few carriers can serve hundreds of thousands of waiting tasks.

The problem they solve. A server that does one blocking call per request (database, HTTP) wastes OS threads: each of the 200 platform threads in a pool sits idle most of the time waiting, and you cannot just create 50,000 of them (1 MB stack each, scheduling cost). The workaround was asynchronous or reactive code: efficient, but harder to write, debug and read. Virtual threads (Java 21, JEP 444) keep the simple "one thread per request, blocking code" style and make it cheap.

How they work.

  • A virtual thread is a normal Thread object, scheduled by the JVM rather than the OS. Its stack is stored in the heap and grows as needed (hundreds of bytes to some KB), so you can have millions.
  • A small number of real OS threads, carrier threads (a ForkJoinPool, by default about one per CPU core), actually run them.
  • When a virtual thread hits a blocking operation (socket read, sleep, BlockingQueue.take, a ReentrantLock), the JVM unmounts it: it copies its stack to the heap, and the carrier immediately runs another virtual thread. When the IO is ready, the thread is mounted again, on any free carrier.
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var req : requests) exec.submit(() -> handle(req));   // one virtual thread per task
}                                                              // close() waits for all tasks
Thread.ofVirtual().name("worker-1").start(() -> handle(r));

Timeline. 10,000 virtual threads each doing "call a service for 200 ms" on 8 carriers: all 10,000 start, each parks (unmounts) at the call, the 8 carriers are free for other work, and about 200 ms later they all resume. Total: about 200 ms and a few MB, instead of 10,000 OS threads.

What they are and are not.

  • Good for IO-bound work, many concurrent waits. Throughput rises, one request's latency does not fall.
  • No gain for CPU-bound work; cores are the limit. And scheduling is cooperative (no time slicing), so a long CPU loop can monopolize a carrier.
  • Never pool them. They are cheap per task, so create one each; pooling defeats the purpose. Limit concurrency with a Semaphore if needed.
  • They are always daemon threads, and they work with existing code (Thread API, ThreadLocal, java.util.concurrent).

Spring Boot 3.2+ can use them with spring.threads.virtual.enabled=true.

Remember: a cheap thread per task, blocking becomes free for IO. Never pool them. No gain for CPU-bound work.

When should you use virtual threads, and what do you watch out for when moving to them? Senior

Use them when the work is mostly waiting (HTTP calls, database, messaging) and you want simple blocking code with high concurrency. Do not use them for CPU-bound tasks. When migrating, watch four things: pinning, resource limits that the pool used to enforce, ThreadLocal use, and heavy synchronized blocks around IO.

Decision rule. Use virtual threads when the application spends most of its time waiting (HTTP clients, JDBC, messaging, files) and handles many concurrent requests: the typical microservice. Do not use them as a speed-up for CPU-heavy computation, and do not expect a single request to get faster.

Migration checklist, with the reason for each item.

  1. Replace the pool's implicit limit. A fixed pool of 50 used to cap calls to the database or a partner API at 50. With a virtual thread per task, nothing caps it, and you can overload the downstream or run out of DB connections. Add a Semaphore (bulkhead) per dependency; the connection pool already caps DB use but now many threads wait for it.
  2. Check pinning. A virtual thread that blocks inside synchronized (Java 21 to 23) or a native call stays stuck on its carrier. Prefer ReentrantLock around blocking code, update old drivers, check with JFR (next question).
  3. Review ThreadLocal. It works, but one million virtual threads with a large thread-local value mean one million copies. Cache objects (formatters, buffers) in a thread-local only if cheap; consider passing context explicitly or ScopedValue (final in Java 25).
  4. Remove thread pools for IO tasks and stop sizing them by the "cores times factor" formula. Keep a bounded platform pool for CPU-bound work.
  5. Do not pool virtual threads and avoid long CPU loops on them.
  6. Observability. Regular thread dumps (jstack) do not list virtual threads; use jcmd <pid> Thread.dump_to_file -format=json file. Monitoring that counts threads needs adjusting, because there can be a million.
// the semaphore bulkhead replaces "pool size = 20"
static final Semaphore DB_LIMIT = new Semaphore(20);
Object query() throws InterruptedException {
    DB_LIMIT.acquire();
    try { return db.query(); } finally { DB_LIMIT.release(); }
}

What I would say in an interview: "Virtual threads for IO-bound services after load testing for pinning and with explicit limits. Platform threads for CPU-bound work."

Remember: IO-bound yes, CPU-bound no. Replace the pool's cap with a semaphore.

What is virtual thread pinning? Senior

A virtual thread is pinned when it cannot be unmounted from its carrier while blocked, so it holds the OS thread hostage. In Java 21 this happens when it blocks inside a synchronized block or in a native call. If many virtual threads are pinned at once, the few carriers are all stuck and the application stalls.

What pinning is. The power of a virtual thread is that when it blocks, it can unmount from its carrier so the carrier runs something else. A virtual thread is pinned when it blocks but cannot unmount, so it keeps the carrier occupied while doing nothing. A few pinned threads are harmless; if all carriers (about one per core) are pinned at once, no virtual thread can run: the application freezes under load.

When it happens (Java 21):

  • Blocking inside a synchronized block or method: the JVM cannot move the monitor ownership off the carrier.
  • Blocking inside a native method or foreign call (JNI).
// Java 21: this pins the carrier for the whole blocking call
synchronized (lock) { return httpClient.send(request); }   // blocks while holding the monitor

// friendlier on Java 21: ReentrantLock lets the virtual thread unmount while it waits
lock.lock();
try { return httpClient.send(request); } finally { lock.unlock(); }

How it was improved. Java 24 (JEP 491) reworked monitors so that a virtual thread blocked in synchronized normally no longer pins its carrier. Native frames and some class-initialization cases can still pin. So the advice depends on your JDK: on 21 to 23, avoid blocking IO under synchronized (switch to ReentrantLock, upgrade libraries such as old JDBC drivers); on 24+, it matters much less.

How to find it. JFR event jdk.VirtualThreadPinned reports each pinned blocking call with a stack trace (it fires when a pinned thread blocks longer than a threshold). On Java 21, -Djdk.tracePinnedThreads=full prints a stack whenever a thread blocks while pinned (the flag was removed in later releases). Symptoms in production: throughput collapses under load, with threads waiting but carriers busy, while a lighter test works fine.

Good practice regardless of version: keep synchronized blocks short and never do IO inside them.

Remember: blocking inside synchronized or native pins the carrier (mostly fixed in Java 24). Use ReentrantLock on 21.

What is structured concurrency, and what is it for? Senior

It treats a group of related subtasks as one unit with a clear lifetime: the code that starts subtasks must also wait for them, in the same scope. If one subtask fails, the others are cancelled, and nothing is left running after the scope ends. It fixes the usual problems of ad-hoc futures: leaked tasks and forgotten error handling.

The problem with unstructured concurrency. With plain executors and futures, a task you start can outlive the method that started it. If one subtask fails, siblings keep running and waste resources; if the method returns early, nobody waits for them; thread dumps do not show who owns whom. This is like a program with goto instead of blocks: start and end are unconnected.

The idea. Treat a group of related subtasks like a block of code: subtasks are started inside a scope, the scope does not end until they are all finished (or cancelled), and failures are handled at the scope boundary. The parent-child relationship is explicit, so cancellation and error propagation follow it.

// Java 21 preview API (names have changed in later previews)
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<User>  user  = scope.fork(() -> findUser(id));      // each runs in its own virtual thread
    Subtask<Order> order = scope.fork(() -> findOrder(id));
    scope.join().throwIfFailed();                              // wait; if one failed, the other is cancelled
    return new Page(user.get(), order.get());
}   // leaving the block guarantees no subtask is still running

Timeline: both subtasks start together. If findUser fails after 20 ms, the scope cancels findOrder (interrupts it), join returns, throwIfFailed throws. A sibling task cannot leak. With ShutdownOnSuccess, the first success wins and the rest are cancelled (fastest replica).

Benefits: no leaked threads, automatic cancellation, clear error propagation, and readable thread dumps with the parent-child relationship.

Status warning. StructuredTaskScope was a preview API in Java 21 and has stayed in preview, with API changes between releases (newer previews replace the new ...ShutdownOnFailure() constructors with factory methods and policies). Preview features need --enable-preview and may change, so check your JDK before using it in production, and treat the code above as a sketch of the idea. ScopedValue (a companion API: immutable context shared with child tasks) became final in Java 25. Before then, the same pattern can be done manually with invokeAll/CompletableFuture plus careful cancellation.

Remember: subtasks live and die inside one scope: wait for all, cancel on failure. Preview API, so check your JDK.

Reactive (WebFlux) or virtual threads: how do you choose? Senior

For new IO-heavy services on Java 21+, I start with virtual threads and plain blocking code, because they give most of the scalability with far simpler code, stack traces and debugging. I choose reactive when I need real streaming with back-pressure, event-driven pipelines, or I am already inside a reactive stack.

What problem both solve. Handling many concurrent requests that mostly wait on IO, without one expensive OS thread per waiting request.

Reactive (Spring WebFlux, Reactor, RxJava). A few event-loop threads never block. Code is written as a pipeline of operators (map, flatMap) that describe what to do when data arrives; the framework calls your code when IO completes. It scales very well, with built-in back-pressure (a slow consumer tells the producer to slow down) and good support for streams. The cost is a different programming model: nothing happens until something subscribes, stack traces are hard to follow, debugging and testing are harder, context (security, MDC, transactions) travels through the pipeline instead of thread-locals, and one blocking call on an event-loop thread stalls many requests.

Virtual threads. Keep ordinary blocking code, one thread per request. When code blocks, the JVM parks the virtual thread cheaply. You get most of the scalability of reactive IO with normal control flow, debuggers, stack traces, thread-locals and try/catch.

// reactive style
Mono<Page> page = userClient.get(id).flatMap(u -> ordersClient.forUser(u.id()).map(o -> new Page(u, o)));

// virtual-thread style (blocking, but cheap)
User u = userClient.get(id);
List<Order> o = ordersClient.forUser(u.id());
return new Page(u, o);
Choose virtual threads whenChoose reactive when
New or existing blocking (MVC, JDBC) service on Java 21+You need streaming with back-pressure between stages
Team values simple, debuggable codeThe stack is already reactive end to end (R2DBC, reactive clients)
Typical request/response with several IO callsVery high fan-out of events: SSE, WebSocket, gateways

Reasonable stance: default to virtual threads for request/response services; use reactive where the data flow is naturally a stream. Both can coexist, but never call blocking code from a reactive event-loop thread (offload it to a scheduler) and do not wrap reactive code in blocking calls everywhere.

Remember: virtual threads for simple scalable blocking code, reactive when you need streaming and back-pressure.

10. Thread dumps and diagnosing problems

How do you take and read a thread dump to find a hang? Senior

I take three dumps a few seconds apart with jcmd PID Thread.print (or jstack PID, or kill -3), then compare. Threads that sit at the same stack line in all three are the stuck ones. First I look for "Found one Java-level deadlock". If none, I group threads by what they wait on.

What a thread dump is. A snapshot of every thread: name, state, the stack of method calls, and which locks it holds or waits for. One dump is a photo; to see "stuck" you need several photos.

How to take them.

jcmd 4321 Thread.print                 # preferred; also: jstack 4321 ; kill -3 4321 (to stdout)
# for virtual threads too:
jcmd 4321 Thread.dump_to_file -format=json /tmp/dump1.json
# take three, 5-10 seconds apart; save them BEFORE restarting anything

How to read it, in order.

  1. Search for "Found one Java-level deadlock". If present, it names the threads, the locks and the lines. Done.
  2. Compare the three dumps. Threads on the same line each time are stuck; threads whose stacks change are working.
  3. Group threads by their top frames. The biggest group tells the story.
"http-nio-8080-exec-17" #53 prio=5 tid=0x... nid=0x1a2b waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
	at com.acme.Cache.get(Cache.java:41)
	- waiting to lock <0x000000076ab1> (a com.acme.Cache)     <- who owns 0x...ab1 ?
"http-nio-8080-exec-3" ...
	at java.net.SocketInputStream.socketRead0(Native Method)  <- owner is itself waiting on IO
	- locked <0x000000076ab1> (a com.acme.Cache)

What common patterns mean:

  • Many BLOCKED on the same address: lock contention. Find the thread with locked <0x...> for that address and see what it is doing; if it does IO inside the lock, that is the culprit.
  • Many threads in HikariPool.getConnection or ArrayBlockingQueue.take on a pool: the database connection pool is exhausted.
  • All request threads in socketRead0: a slow or dead downstream with no timeout.
  • All pool workers in Future.get / join with a non-empty queue: pool starvation deadlock.
  • Idle workers WAITING on a queue's take: normal; ignore.
  • RUNNABLE in a native read is waiting for IO, not computing.

Cross-check with CPU: low CPU plus many waiting threads is a blocking problem; high CPU needs the hot-thread method (next question). Name your threads (orders-pool-3), or the dump is unreadable.

Remember: three dumps, deadlock section first, then group by what threads wait on. Never restart before saving them.

The trick. The OS knows CPU use per OS thread, and a Java thread dump prints each thread's OS id in hex (nid=0x...). So: find the busiest OS thread, convert its id to hex, find it in the dump.

printf '%x\n' 4388                    # prints 1124  (decimal to hex)

How do you test concurrent code? Senior

I cannot prove the absence of races by testing, so I combine: design that avoids shared state, stress tests that hammer the code from many threads and check an invariant, and tools that find races for me. A passing test only means it did not fail this time.

The hard truth. A passing concurrency test only proves "it did not fail this time". A race might need a one-in-a-million interleaving. So you combine good design with tests that make failure likely and tools that look for problems systematically.

1. Design first. The best test strategy is having little shared mutable state: immutable objects, confinement, queues. Then there is less to test.

2. Stress test with an invariant. Hammer the code from many threads, then check a property that must always hold (total count, no lost items, no duplicates):

@Test void counterIsExact() throws Exception {
    int threads = 32, perThread = 100_000;
    var counter = new MyCounter();
    var start = new CountDownLatch(1);                 // start gate: everyone begins together
    var done  = new CountDownLatch(threads);
    for (int i = 0; i < threads; i++) new Thread(() -> {
        try { start.await(); for (int j = 0; j < perThread; j++) counter.increment(); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        finally { done.countDown(); }
    }).start();
    start.countDown();
    assertTrue(done.await(30, TimeUnit.SECONDS));      // a timeout turns a hang into a failure
    assertEquals(threads * perThread, counter.get());  // invariant: no lost updates
}

3. Make failure likely. More threads than cores, many repetitions (@RepeatedTest), different machines and CI, a stress run overnight. Adding artificial yields or small delays in test builds can widen race windows.

4. Never wait with Thread.sleep. It is both slow and flaky. Use latches, futures, join with a timeout, or Awaitility (await().atMost(...).until(...)).

5. Use tools. jcstress (OpenJDK) tests low-level memory-model behavior with all interleavings sampled; static analysis and annotations (for example checks for "guarded by"); thread sanitizers in some ecosystems; a thread dump or JFR when a test hangs.

6. Always put a timeout on every wait in a test, so a deadlock fails the test rather than hanging the CI build. Also test shutdown: no leaked non-daemon threads after the test ends.

Remember: latch-started stress test plus an invariant check, with timeouts everywhere. No sleeps.

11. Coding questions

Write a producer-consumer with a BlockingQueue. Intermediate

I create one bounded ArrayBlockingQueue, producers call put(), consumers call take(), and the queue does all the waiting. To stop, the producer puts a poison pill (a special end marker) once per consumer.

The problem. Some threads produce work (read files, receive requests) and others consume it (parse, store). They run at different speeds, so you need a buffer between them, plus rules for "buffer empty" and "buffer full". A BlockingQueue gives you all of that in one class.

BlockingQueue<String> q = new ArrayBlockingQueue<>(100);
static final String STOP = "__STOP__";
static final int CONSUMERS = 3;

Runnable producer = () -> {
    try {
        for (String s : source) q.put(s);                      // blocks when full
        for (int i = 0; i < CONSUMERS; i++) q.put(STOP);       // one pill per consumer
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};
Runnable consumer = () -> {
    try {
        for (String s; !(s = q.take()).equals(STOP); ) handle(s);   // blocks when empty
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

ExecutorService pool = Executors.newFixedThreadPool(1 + CONSUMERS);
pool.submit(producer);
for (int i = 0; i < CONSUMERS; i++) pool.submit(consumer);
pool.shutdown();

Timeline.

producer fast, queue fills to 100 -> put() blocks -> producer sleeps (back-pressure)
consumer takes one item         -> a slot frees  -> producer wakes, puts one more
source ends: producer puts STOP x3 -> each consumer takes exactly one STOP and exits
queue empty and consumers faster  -> take() blocks; consumers sleep until data arrives

Why each choice.

  • Bounded queue: an unbounded one lets a fast producer fill the heap. The bound is the back-pressure.
  • No locks, no wait/notify: the queue is already thread-safe and handles waiting. Fewer places for bugs.
  • Poison pill, one per consumer: a consumer blocked in take() never ends on its own. Each pill is consumed by exactly one consumer. With a single pill, only one of three consumers stops and the program hangs.
  • Visibility: what the producer wrote to an item before put is visible to the consumer after take.

Variations to mention. Multiple producers: the last one to finish (count with an AtomicInteger or CountDownLatch) sends the pills. An alternative stop signal is interrupting the consumers, but then items still in the queue may be lost. For ordering by priority use PriorityBlockingQueue. Pitfall: do not let handle() throw out of the loop, or that consumer dies silently; catch and log inside.

Remember: bounded queue, put/take, one poison pill per consumer.

Write a bounded buffer yourself with ReentrantLock and Condition. Senior

One lock, two conditions: "notFull" for producers and "notEmpty" for consumers. Each operation takes the lock, waits in a while loop until its condition holds, does the change, and signals the other side.

What you are building. A fixed-size queue where put waits when full and take waits when empty, using only a lock and conditions. It is the textbook version of what ArrayBlockingQueue does, and it tests whether you understand await/signal.

class BoundedBuffer<T> {
    private final Object[] items; private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();
    BoundedBuffer(int n) { items = new Object[n]; }

    void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();   // loop, not if
            items[tail] = x; tail = (tail + 1) % items.length; count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }
    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[head]; items[head] = null;
            head = (head + 1) % items.length; count--;
            notFull.signal();
            return x;
        } finally { lock.unlock(); }
    }
}

Timeline (capacity 1).

C: take()  -> lock, count == 0 -> notEmpty.await()   [releases the lock, sleeps]
P: put(A)  -> lock, store A, count=1, notEmpty.signal(), unlock
C: wakes   -> must re-acquire lock first, re-checks "count == 0": false -> takes A, signals notFull

Points to say out loud.

  • await() releases the lock while sleeping and re-acquires it before returning. Without that, nobody could ever put.
  • The while loop handles spurious wakeups and the case that another consumer took the item between the signal and your wakeup.
  • Two conditions on one lock: producers wait on notFull, consumers on notEmpty. With synchronized you have one wait set, so you must notifyAll, waking everyone including the wrong kind. Separate conditions let signal() wake exactly the right side.
  • unlock() in finally, and signal while holding the lock.
  • The lock gives memory visibility for count, head, tail, so none needs to be volatile.

Common mistakes: if instead of while; calling await/signal without holding the lock (IllegalMonitorStateException); one shared condition with signal (can wake a producer when a producer must not run, causing a stuck system). Improvement: awaitNanos for timeouts, and a separate put and take lock for more throughput (as LinkedBlockingQueue does).

Remember: lock, while-loop await, change, signal the other side, unlock in finally.

Print odd and even numbers alternately from two threads. Intermediate

Two threads share one counter and one lock. Each waits (in a loop) until it is its turn, prints, increments and notifies. Using synchronized with wait/notifyAll is the expected answer.

The task. Two threads print 1 to 10 in order: one prints odd numbers, the other even numbers, taking turns. It looks silly but tests wait/notify, the while-loop rule and termination handling.

class OddEven {
    private int n = 1; private final int max = 10;
    synchronized void print(boolean odd) throws InterruptedException {
        while (n <= max) {
            while (n <= max && (n % 2 == 1) != odd) wait();   // not my turn
            if (n <= max) { System.out.println(Thread.currentThread().getName() + " " + n++); }
            notifyAll();
        }
    }
}
// OddEven o = new OddEven();
// new Thread(() -> { try { o.print(true);  } catch (InterruptedException e) {} }, "odd").start();
// new Thread(() -> { try { o.print(false); } catch (InterruptedException e) {} }, "even").start();

Timeline.

n=1: even runs first -> n%2==1 but it wants even -> wait() (releases the monitor)
     odd runs -> prints 1, n=2, notifyAll
     odd loops -> n=2 is not odd -> wait()
     even wakes -> prints 2, n=3, notifyAll ... and so on until n = 11
n=11: the thread that waits sees n > max, leaves the inner loop, outer loop ends, thread exits

Why it is written like this.

  • Shared state (n) is protected by the same monitor used for wait/notifyAll.
  • wait() inside a while that checks "is it my turn": it handles spurious wakeups.
  • The exit case matters: after the last number, the other thread is waiting for a turn that will never come. The check n <= max in the wait loop, plus the final notifyAll, lets it escape. Forgetting this is the most common bug: the program prints 1 to 10 and then hangs.
  • notifyAll (not notify) is safer, though with only two threads notify would also work.

Alternative with two semaphores (cleaner, hands a baton back and forth):

Semaphore oddTurn = new Semaphore(1), evenTurn = new Semaphore(0);
// odd thread:  for (int i = 1; i <= 9; i += 2) { oddTurn.acquire();  print(i); evenTurn.release(); }
// even thread: for (int i = 2; i <= 10; i += 2) { evenTurn.acquire(); print(i); oddTurn.release(); }

The semaphore version is easy to extend to three threads in rotation (A, B, C). Note the point of the exercise is the hand-off logic; in real code you would not alternate threads like this.

Remember: shared counter, wait until it is my turn, print, notifyAll. Don't forget the exit condition.

Make three threads run in a fixed order: T1, then T2, then T3. Intermediate

The simplest way is join(): T2 starts only after T1 has finished, and so on. If the threads must run side by side but their critical steps happen in order, I use a CountDownLatch per hand-off, or CompletableFuture.thenRun.

Key insight. The order in which you call start() says nothing about the order in which threads run. The scheduler decides. If you need an order, you must create it with synchronization: a hand-off that makes a later step wait for an earlier one.

Option 1: join() (simplest, when each thread can run to completion before the next starts):

Thread t1 = new Thread(() -> step("T1"));
Thread t2 = new Thread(() -> step("T2"));
Thread t3 = new Thread(() -> step("T3"));
t1.start(); t1.join();     // main waits until T1 ends
t2.start(); t2.join();
t3.start(); t3.join();

This works but is sequential: no real concurrency.

Option 2: latches (threads exist side by side, but each waits for the previous one's signal):

CountDownLatch l1 = new CountDownLatch(1), l2 = new CountDownLatch(1);
Thread t1 = new Thread(() -> { step("T1"); l1.countDown(); });
Thread t2 = new Thread(() -> { await(l1); step("T2"); l2.countDown(); });
Thread t3 = new Thread(() -> { await(l2); step("T3"); });
t3.start(); t2.start(); t1.start();      // deliberately reversed start order
t3 starts -> waits on l2.  t2 starts -> waits on l1.  t1 starts -> prints T1, countDown(l1)
t2 wakes -> prints T2, countDown(l2).  t3 wakes -> prints T3.     Output: T1 T2 T3

Option 3: a chained future (each stage runs after the previous one):

CompletableFuture.runAsync(() -> step("T1"))
    .thenRun(() -> step("T2")).thenRun(() -> step("T3")).join();

Option 4: Semaphores or a single-thread executor (Executors.newSingleThreadExecutor() runs submitted tasks in submission order).

Implement a simple thread-safe rate limiter. Senior

I would write a token bucket: it holds up to N tokens, refills at a fixed rate, and each request takes one token or is refused. It handles bursts up to N and a steady average rate, and the state update is a small critical section.

Two different limits, do not mix them up. A concurrency limit says "at most 10 at the same time" (a Semaphore). A rate limit says "at most 100 per second" (a token bucket, leaky bucket or fixed or sliding window). The question asks for the second.

Token bucket. Picture a bucket that holds up to capacity tokens. Tokens drip in at a steady rate. Each request removes one token; if the bucket is empty, the request is refused. A full bucket allows a burst of capacity requests, then the average settles to the refill rate.

class TokenBucket {
    private final long capacity; private final double refillPerNano;
    private double tokens; private long last = System.nanoTime();
    TokenBucket(long capacity, double perSecond) {
        this.capacity = capacity; this.tokens = capacity; this.refillPerNano = perSecond / 1e9;
    }
    synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) * refillPerNano);   // lazy refill
        last = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;                      // caller can reject (HTTP 429) or retry later
    }
}

Example. capacity 5, 1 token per second: five requests at t=0 all pass (tokens 5 to 0); a sixth at t=0.2 s fails (0.2 tokens); a request at t=1.0 s passes.

Design points.

  • Lazy refill: no background thread; tokens are computed from the elapsed time at each call.
  • One lock: the read-compute-write of tokens and last must be atomic. The critical section is a few arithmetic operations, so contention is low. A lock-free version would keep state in an AtomicReference to an immutable (tokens, time) pair and CAS it; not worth it unless proven necessary.
  • System.nanoTime() is monotonic; wall-clock time can jump (NTP) and break the math.
  • Blocking variant: instead of returning false, compute the wait time and sleep (what Guava's RateLimiter.acquire() does).

Limits of this design. It limits one JVM. With ten instances and a 100 per second limit you would allow up to 1000. For a global limit use a shared store (Redis script) or an API gateway; for production use libraries (Guava RateLimiter, Resilience4j, Bucket4j). A fixed-window counter is simpler but allows a double burst at a window boundary.

Remember: token bucket = refill by elapsed time, take one token, else reject. A JVM limiter covers only one instance.

12. Real-life scenarios

Every answer follows the same shape: the diagnosis in one sentence, then the situation, what to check first, the fix, and how to prevent it. Say this shape aloud in the interview; it shows you work calmly under pressure.

The application stops responding. CPU is near zero, requests time out. What do you do? Senior

Near-zero CPU means threads are waiting, not computing: a deadlock, an exhausted pool, or everyone waiting on a dead dependency. I do not restart first. I take three thread dumps, find what the threads wait on, restore service, then fix the root cause.

Situation: health checks fail and requests time out, but the process is alive, memory is normal and CPU is near zero. The system is not busy; it is waiting. Three usual suspects: a Java-level deadlock, an exhausted pool (threads or DB connections), or all threads waiting on a dead dependency.

Check first (in this order):

jcmd 4321 Thread.print > dump1.txt      # then again after 10 s, and 10 s later
jcmd 4321 GC.heap_info                  # is it a GC freeze? (long pauses also look like a hang)
# plus: connection-pool metrics, downstream health, recent deploy/config change

Three dumps matter because one photo cannot show "stuck": threads on the same line in all three are stuck. Save the dumps before restarting; a restart destroys the evidence.

Read the dump:

  1. Search "Found one Java-level deadlock". If present you have threads, locks and line numbers. Done.
  2. Otherwise group threads by top frame:
    • HTTP workers in socketRead0: a slow or dead dependency with no timeout.
    • Workers in HikariPool.getConnection: DB pool exhausted (a leaked connection, or a slow query holding them).
    • Many BLOCKED on one monitor address: contention; find the owner and what it is doing (often IO inside synchronized).
    • Pool workers in Future.get with a full queue: pool-starvation deadlock.
  3. Restore service (restart, or fail over to a healthy instance), then fix the cause: lock order, timeouts, pool sizing.

Prevent: timeouts on every remote call, circuit breakers, an alert that calls ThreadMXBean.findDeadlockedThreads(), named threads, metrics for pool usage, queue length and connection wait time. Mention in an interview that you restore service quickly but only after capturing evidence, and that you separate "restore" from "root cause".

Remember: idle CPU plus hang = take dumps first, then read what threads wait on.

CPU is at 100% on one production instance after a release. How do you find the cause? Senior

I check whether the busy threads are GC or application threads with top -H, map the hottest thread id to a thread dump line, and roll back if the release is clearly the trigger. Analysis then continues on a canary or in staging.

Situation: one instance (or all of them) runs at 100% CPU after a release; latency rises, maybe health checks time out. Busy CPU means some thread is actively computing, or the JVM is thrashing in garbage collection.

Check first: GC or application code? The top threads tell you:

top -H -p 4321                 # shows per-thread CPU; note the hottest thread id, e.g. 4388
printf '%x\n' 4388             # 1124   (decimal to hex)
jcmd 4321 Thread.print | grep -A 20 'nid=0x1124'
  • If the hot threads are "GC Thread" or similar, the problem is memory (leak, heap too small, huge allocation rate): read GC logs and take a heap dump; stack traces will not help.
  • If it is an application thread, read its stack. Repeat 3 times; a stack that always shows the same few methods is the hot spot.

Typical causes seen in the stack: a loop with a missing exit or runaway retry; a regex with catastrophic backtracking (Pattern$Loop.match); a busy-wait or a CAS retry spin; a plain HashMap corrupted by concurrent writes and spinning in get (older JDKs); heavy JSON or XML parsing in a loop; debug logging on a hot path; a cache stampede recomputing the same value on all threads.

Fix: if the release is the obvious trigger, roll back first: restoring users matters more than understanding. Then reproduce on a canary or staging, and use a sampling profiler (JFR: jcmd PID JFR.start duration=60s filename=/tmp/x.jfr, or async-profiler) to get a flame graph, which is more reliable than a few dumps. Fix the code and add a regression test.

Prevent: load tests in the pipeline, canary releases with automatic CPU/latency rollback, per-instance CPU alerts, code review for loops without exit conditions and for plain collections shared between threads.

Remember: hot thread id to hex to dump line. Roll back first when the release is the clear cause.

Every request thread is busy and the service returns 503, but the database looks fine. What happened? Senior

A downstream call became slow with no short timeout, so every worker thread sits waiting on it and the pool is exhausted. I confirm with a thread dump, add timeouts and a circuit breaker, and isolate that dependency with its own bounded pool (a bulkhead).

Situation: Tomcat's worker pool (default 200 threads in a standard Spring Boot setup) is full. New requests queue in the accept queue and then time out as 503 or gateway errors. CPU is low and the database looks healthy, so it is tempting to blame the network; the real cause is usually one slow dependency.

Timeline of how it happens:

t0  partner API normally answers in 200 ms; 200 threads handle ~1000 requests/s
t1  partner API slows to 30 s; no read timeout is set
t2  each request thread now waits 30 s inside the HTTP client call
t3  all 200 threads are stuck; capacity = 200 / 30 s = ~7 requests/s (Little's law: concurrency = rate x latency)
t4  everything else on the service (even endpoints that do not call the partner) is starved
    -> queue grows -> clients time out and retry -> load increases

Check first: a thread dump. Most workers are in a socket read or HTTP client call to one host. Also check the downstream's latency metrics and the service's active-thread gauge.

Fix:

  • Set connect and read timeouts short (a few seconds at most, based on the downstream's real latency).
  • Add a circuit breaker so a failing dependency is skipped immediately (threads released at once) and probed occasionally.
  • Add a bulkhead: a separate bounded pool or a Semaphore for that dependency, so its slowness consumes only its own share of threads.
  • Return a fallback or cached response, or a quick 503 with Retry-After.
  • Do not just raise the thread count; that moves the limit and increases memory and downstream load.

Prevent: a rule that no client has an infinite timeout, a bulkhead per dependency, alerts on active threads and downstream p99. With virtual threads there is no thread limit, so the semaphore bulkhead becomes more important, not less.

Remember: slow dependency plus no timeout equals exhausted pool. Timeout, breaker, bulkhead.

Situation: stock goes below zero, or a counter shows 9,870 after 10,000 increments, or a balance is slightly off. It never reproduces on a laptop with one request at a time and appears under load. This is the signature of a read-modify-write race.

A database or shared by several instancesA JVM lock protects only one instance; you need the database to make it atomic

Search for ++, +=, "get, compute, put" on shared fields and maps, and for if (!map.containsKey) put.

Fix (one JVM): AtomicInteger/AtomicLong, LongAdder for hot statistics, map.merge(k, 1, Integer::sum) or compute on a ConcurrentHashMap, or one lock around the whole read-compute-write sequence (not just the write).

Fix (database):

UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0     -- atomic; check updated row count == 1
-- or optimistic locking: UPDATE ... SET qty=?, version=version+1 WHERE id=? AND version=?   (retry if 0 rows)
-- or SELECT ... FOR UPDATE inside a transaction (pessimistic)

Prevent: a concurrency test that hammers the operation from many threads with a latch start and asserts the final total; avoid doing read-then-write in application code when the store can do it atomically; add a database CHECK (qty >= 0) constraint as a last line of defense.

Remember: JVM lock for one process, database atomicity for many instances.

Memory grows after every redeploy, and users sometimes see another user's data. Suspect ThreadLocal. Senior

A ThreadLocal is set on pooled threads and never removed. The pooled thread keeps the value (and its class loader) alive, and the next request on that thread reads the previous user's value. The fix is set and remove in the same try/finally, usually in a filter.

Situation: two symptoms with one cause. (a) After each hot redeploy on a shared Tomcat, Metaspace or heap grows until OutOfMemoryError. (b) A request occasionally sees the previous request's user, tenant or locale: a security bug, since data from one user leaks to another.

Why it happens. A ThreadLocal value lives in the thread's own ThreadLocalMap. Servlet containers and executors reuse threads, so the thread (and everything in its map) lives far longer than a request:

request 1 on thread http-7: threadLocal.set(userA)   // never removed
request 2 on thread http-7: reads threadLocal.get()   // sees userA unless it sets again -> data bleed
redeploy: the old webapp's class is referenced by the value in http-7's map
          -> the old ClassLoader and all its classes cannot be collected -> leak

Check first:

  • Heap dump (jcmd PID GC.heap_dump file.hprof), open in Eclipse MAT: "path to GC roots" of the old class loader shows thread, ThreadLocalMap, entry.
  • Search the code for ThreadLocal.set( with no matching remove(). Tomcat also logs "created a ThreadLocal with key of type ... but failed to remove it" on stop.

Fix: always set and remove in one try/finally, centrally (servlet filter, interceptor, task decorator):

try { CONTEXT.set(ctx); chain.doFilter(req, res); }
finally { CONTEXT.remove(); }

For async work, pass context explicitly or with a task decorator that sets and clears it on the worker thread; do not assume it follows the request.

Prevent: a code rule that thread-locals are cleared in finally, a test that runs two requests on the same single thread and checks isolation, and a hot-redeploy check in staging. On newer JDKs consider ScopedValue (final in Java 25) for per-request context.

Remember: pooled thread plus ThreadLocal without remove = leak and data bleed.

Two services update the same two database rows in opposite order and requests hang or fail with lock timeouts. Senior

It is a deadlock in the database, the same lock-ordering problem as in Java. The fix is to always touch rows in one consistent order (for example by primary key) and keep transactions short.

Situation: service A transfers money by updating account 1, then account 2. Service B does the reverse, updating 2 then 1. Each runs in its own transaction.

A: UPDATE account 1   (holds row lock 1)        B: UPDATE account 2   (holds row lock 2)
A: UPDATE account 2   -> waits for B             B: UPDATE account 1   -> waits for A
=> circular wait. The database detects it and kills one transaction (deadlock error),
   or, if it cannot see it, waits until a lock timeout expires.

It is the same deadlock as two Java locks taken in opposite order, with row locks instead of monitors, and no thread dump will show it because the waiting happens inside the database.

Check first: the database's deadlock report (for example the latest-deadlock section in MySQL/InnoDB status, or the Postgres server log) which shows both statements and the rows involved. Then find all code paths that lock more than one row, and compare their order.

Fix:

  • One consistent order: always lock in ascending primary-key order, whatever the business direction of the transfer.
  • Or lock all rows in one statement: SELECT ... WHERE id IN (1, 2) ORDER BY id FOR UPDATE.
  • Retry on deadlock (bounded, with jitter). A database deadlock error is an expected, designed-for failure that is safe to retry if the transaction is idempotent.
  • Keep transactions short, and never call remote services or wait for user input inside one: this shrinks the window for conflicts.

Prevent: a team rule for lock order, optimistic locking (version column) where conflicts are rare, and load tests that run opposing flows at the same time. Monitor deadlock counts as a metric.

Remember: same order everywhere, short transactions, retry on deadlock.

An unrelated endpoint became slow after another team added a parallelStream() with an HTTP call inside. Senior

Parallel streams and default CompletableFuture stages share one common ForkJoinPool with only about cores minus 1 threads. Blocking calls inside it starve everything else that uses the pool. I move the blocking work to a dedicated executor.

Situation: an endpoint that nobody touched slowed down right after another team deployed a feature that uses list.parallelStream().map(this::callRemote). The unrelated endpoint also uses the default pool (for example a CompletableFuture.supplyAsync without an executor).

Why. Parallel streams and default async CompletableFuture stages both run on the common ForkJoinPool: one pool per JVM, sized about cores minus 1 (so only 3 threads on a 4-core container). It is designed for short CPU-bound tasks. A blocking HTTP call holds a worker for its whole duration:

commonPool has 3 workers.  parallelStream with 100 items, each call takes 2 s.
all 3 workers sit in socketRead0; the other 97 items queue; any other code using the common pool waits behind them

Check first: a thread dump shows every ForkJoinPool.commonPool-worker-N in a socket read, plus other callers waiting. Also check the container's CPU limit, which sets the pool size.

Fix:

ExecutorService io = new ThreadPoolExecutor(20, 20, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(200),
        new ThreadPoolExecutor.CallerRunsPolicy());
List<CompletableFuture<R>> fs = items.stream()
    .map(i -> CompletableFuture.supplyAsync(() -> callRemote(i), io)
                               .orTimeout(3, TimeUnit.SECONDS)).toList();
// or on Java 21: one virtual thread per call, with a Semaphore to cap concurrency

Keep parallel streams for CPU-only work on large data, never for IO.

Prevent: a code-review rule: no blocking IO in parallel streams or in async stages on the default pool; always pass an explicit executor to *Async methods; export common-pool metrics (queued task count, active threads).

Remember: the common pool is shared by the whole JVM. Never block it.

The service runs out of memory, and the heap dump is full of queued tasks from an executor. What is the cause? Senior

An unbounded executor queue (typically newFixedThreadPool) with producers faster than consumers: tasks pile up on the heap. I bound the queue, choose a rejection policy that pushes back, and fix the slow consumer.

Situation: heap grows steadily, the old generation is constantly collected, finally OutOfMemoryError: Java heap space. The heap dump shows millions of FutureTask or Runnable objects inside a LinkedBlockingQueue that belongs to a ThreadPoolExecutor.

Why. Executors.newFixedThreadPool(n) uses an unbounded queue. The pool never rejects, so if tasks arrive faster than the n workers finish them, the queue grows without limit; each queued task holds its data (request payload, objects), so memory runs out. Often the trigger is a slow downstream that made each task slower, so the queue fills.

arrival: 500 tasks/s   service rate: 8 workers x 40/s = 320/s
queue grows 180 tasks per second -> 650,000 per hour, each holding a payload -> OOM

Check first: executor metrics (queue size, active count, completed count) and downstream latency; in the heap dump, which task type dominates and what they reference. A related failure is newCachedThreadPool, which has no thread limit and ends with "unable to create native thread".

Fix:

new ThreadPoolExecutor(8, 8, 0L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),                    // bounded queue
    new ThreadPoolExecutor.CallerRunsPolicy());          // slows the submitter instead of dropping

Choose the rejection policy deliberately: CallerRunsPolicy pushes back on the producer, AbortPolicy returns a quick "busy" error (map it to HTTP 429/503), a custom handler can drop or spill to disk. Add timeouts to the slow call; fix the real bottleneck rather than only bounding it.

Prevent: forbid the Executors factory methods for production pools in code review, export queue-size and rejected-count metrics and alert on them, load-test overload behavior.

Remember: an unbounded queue is a hidden memory leak. Bound it and decide what happens when it is full.

A cache built on a plain HashMap sometimes loses entries, throws odd exceptions or spins at 100% CPU. Intermediate

A HashMap is not thread-safe. Concurrent put calls can lose entries or corrupt its structure, and during a resize an old Java 7 map could even form a cycle and make get loop forever. I replace it with ConcurrentHashMap and use atomic methods such as computeIfAbsent.

Situation: a hand-made cache is a static HashMap or a singleton-bean field, used by many request threads. Symptoms: entries disappear, size() looks wrong, odd exceptions (ConcurrentModificationException, NullPointerException or ClassCastException inside HashMap), or a thread spinning at 100% CPU in HashMap.get.

Why it breaks. HashMap has no synchronization or visibility guarantees. Two concurrent put calls into the same bucket can overwrite each other (lost entry). A concurrent resize can leave the structure inconsistent; in Java 7 and earlier, a resize race could create a cycle in a bucket's linked list so get looped forever. Java 8 changed the resize code and is less prone to the infinite loop, but the map is still unsafe: lost updates and corrupted state remain possible.

T1: put(k1) -> bucket 5 empty, plans to store new node
T2: put(k2) -> bucket 5 empty, plans to store new node
both write bucket 5: one entry is silently lost

Check first: is the map shared (static field, singleton, cached in a bean)? A dump of a spinning thread in HashMap.get/put confirms it. Also look for the check-then-put pattern.

Fix:

private final ConcurrentHashMap<String, Config> cache = new ConcurrentHashMap<>();
Config get(String key) { return cache.computeIfAbsent(key, this::load); }   // one load per key

Keep the loader fast (it runs under the bin lock) or load outside and use putIfAbsent. For a real cache with size limit, expiry and refresh, use Caffeine, not a hand-made map.

Prevent: make shared collections concurrent by type, never keep per-request data in singleton fields, run a stress test, and consider static analysis for shared mutable fields.

Remember: shared plus mutable plus HashMap = bug. Use ConcurrentHashMap or Caffeine.

A scheduled job ran fine for weeks, then silently stopped. No error in the logs. Intermediate

With ScheduledExecutorService, an exception thrown by a periodic task cancels all further runs, and the exception is kept in the returned future, so nothing is logged. I wrap the task body in try/catch and log.

Situation: a periodic job (cache refresh, report, cleanup) ran for weeks, then the effects just stopped. Logs contain no error. The process is healthy otherwise.

Why. With ScheduledExecutorService.scheduleAtFixedRate or scheduleWithFixedDelay, if one run throws an exception, all later runs are cancelled. The exception is not printed; it is stored in the returned ScheduledFuture, which nobody reads.

scheduler.scheduleAtFixedRate(() -> refresh(), 0, 1, TimeUnit.MINUTES);
// run #5: refresh() throws NullPointerException
// -> the task is silently cancelled; runs #6, #7 ... never happen; no log line

Other causes to rule out: a long-running job blocking a single scheduler thread, so other jobs are delayed or never run (default Spring scheduler has one thread); a deadlocked job holding that thread; the executor was shut down; a job that now takes longer than its period (fixedRate then runs back-to-back to catch up).

Check first: how is it scheduled, and is the returned future ignored? Calling get() on it would show the stored exception. A thread dump will show whether the scheduler thread is stuck in one job.

Fix:

scheduler.scheduleWithFixedDelay(() -> {
    try { refresh(); }
    catch (Throwable t) { log.error("refresh failed", t); }   // never let it escape
}, 0, 1, TimeUnit.MINUTES);

Use a pool of more than one thread if jobs can overlap in time or run long, and add timeouts to what they call. In Spring, @Scheduled logs the exception and keeps the schedule, but the single default thread still applies.

Prevent: a "last successful run" timestamp metric with an alert, so silence becomes visible; a heartbeat log line.

Remember: an uncaught exception ends a periodic task. Catch inside, and alert on missing runs.

The process does not exit after main finishes, or does not stop on shutdown. Why? Intermediate

The JVM exits only when all non-daemon threads have ended. A thread pool that was never shut down, a consumer blocked in take(), or a timer thread keeps it alive. I find the live non-daemon threads in a dump and shut down their owners.

Situation: main returns, or you send a stop signal, but the process stays alive (or a CI test run never finishes).

Rule. The JVM exits when the last non-daemon thread ends (or on System.exit). main finishing does not stop the JVM if other non-daemon threads are alive. Threads created with new Thread and threads in executors are non-daemon by default.

Usual culprits:

  • An ExecutorService never shut down: even idle core threads keep the JVM alive.
  • A consumer blocked in BlockingQueue.take() waiting for items that will never come.
  • A Timer, a scheduler, a Kafka or HTTP client thread, a non-daemon background thread from a library.
  • A shutdown hook that waits on something that is blocked (the JVM then hangs during shutdown).

Check first: take a thread dump of the stuck process. Threads whose header lacks the word daemon (for example "pool-1-thread-1") are what keeps it alive; their stacks show what they wait for, and the creator is usually visible from the thread name or stack.

Fix:

pool.shutdown();                                         // stop accepting, let queued tasks finish
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) pool.shutdownNow();   // interrupt stragglers
// consumers: send a poison pill or interrupt them
Runtime.getRuntime().addShutdownHook(new Thread(this::stop));            // orderly cleanup on SIGTERM
// Java 19+: try (var exec = Executors.newFixedThreadPool(4)) { ... }   // close() shuts down and waits

Marking pool threads as daemon is a last resort, because daemon threads are killed abruptly in the middle of work.

Prevent: give every executor one owner with a clear stop method, test the shutdown path, and make blocking consumers interruptible.

Remember: JVM waits for non-daemon threads. Find them in a dump and shut down their owner.

After switching a service to virtual threads, it works in tests but freezes under load. What do you check? Senior

I check for pinned virtual threads and for missing limits. On Java 21 a virtual thread that blocks inside synchronized pins its carrier; with many such threads all carriers stall. Also the old pool size no longer limits calls to the database or a partner API.

Situation: a service was switched to virtual threads (for example spring.threads.virtual.enabled=true or newVirtualThreadPerTaskExecutor). Tests and light load are fine. Under production load it freezes, or timeouts and errors explode.

Two usual causes.

  1. Pinning. A virtual thread normally unmounts from its carrier while it waits. On Java 21 to 23, a virtual thread that blocks inside a synchronized block (or native call) stays pinned to its carrier. There are only about as many carriers as CPU cores, so a handful of pinned threads can occupy all of them and nothing else runs. Java 24 largely removes the synchronized case.
  2. Lost implicit limits. The old pool of 50 threads also limited concurrent calls to the database or a partner API. Now there may be 5,000 concurrent calls: the downstream is overloaded, the connection pool times out, errors cascade.
carriers = 8.  8 virtual threads each block on IO inside synchronized -> all 8 carriers pinned
the other 9,992 virtual threads are runnable but have no carrier -> service looks frozen, CPU low

Check first:

  • JFR event jdk.VirtualThreadPinned, or on Java 21 -Djdk.tracePinnedThreads=full (prints a stack when a thread blocks while pinned).
  • A virtual-thread-aware dump: jcmd PID Thread.dump_to_file -format=json file.json (plain jstack does not list virtual threads).
  • Connection pool wait times and downstream error rates. Many virtual threads waiting for a few connections is expected; a timeout storm is not.

Fix:

// replace blocking-under-synchronized with a ReentrantLock (lets the virtual thread unmount)
lock.lock(); try { return client.call(); } finally { lock.unlock(); }
// restore the limit explicitly
static final Semaphore PARTNER = new Semaphore(50);

Upgrade drivers and libraries that use synchronized around IO, consider Java 24+ if you can, and do not pool virtual threads.

Prevent: load test before the switch, alert on pinned events and connection wait time, set explicit per-dependency limits.

Remember: pinned carriers and missing limits. Lock instead of synchronized on 21, semaphore for caps.
