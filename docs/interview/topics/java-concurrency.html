Mental model: the 7 ideas everything hangs on

One line: threads share one heap, so every shared mutable variable needs a rule that makes writes atomic (all or nothing), visible (other threads see them) and ordered (not reordered unexpectedly). Locks, volatile, atomics and immutability are the four ways to give that rule.
  1. Shared heap, private stacks. Local variables live on a thread's own stack and are safe. Objects on the heap can be reached by many threads. Trouble starts only with state that is both shared and mutable.
  2. Three separate problems. Atomicity (nobody sees a half-done operation), visibility (a write by one thread is seen by another) and ordering (others see steps in the order you wrote them). Different tools fix different ones.
  3. CPUs and the JIT reorder and cache. Without a rule, a thread may keep a value in a register or core cache and never see another thread's update.
  4. Happens-before is the rule. The Java Memory Model says: if action A happens-before B, then B sees everything A did. Locks, volatile, thread start and join, and executors create these edges.
  5. Prefer not sharing. Immutable objects, thread confinement (one owner) and message passing (queues) avoid locks entirely.
  6. Threads are a limited, costly resource. A platform thread is an OS thread with about 1 MB of stack reserved. Pools bound them. Virtual threads (Java 21) make blocking cheap.
  7. Concurrency bugs hide. They show up under load, on other hardware, once a week. So you design for correctness, test with stress, and know how to read a thread dump.

1. Threads: the basics

What is the difference between a process and a thread? Basic

A process is a running program with its own private memory. A thread is a path of execution inside a process. All threads of one process share the heap, but each has its own stack and program counter. That makes threads cheap to create and good at sharing data, and also dangerous, because they can corrupt each other's data.

Processes are isolated: one crash does not kill the others, and they talk through sockets, pipes or files. A Java application is one process (one JVM) with many threads: main, GC threads, JIT compiler threads and your request threads. A platform thread reserves about 1 MB of stack (-Xss, usually committed lazily) and a context switch costs microseconds, so thousands of busy threads waste CPU.

Remember: process = private memory, thread = shared heap plus own stack. Sharing is the benefit and the bug source.

Describe the thread lifecycle and the states in Thread.State. Basic

There are six states: NEW (created, not started), RUNNABLE (running or ready for a CPU), BLOCKED (waiting to enter a synchronized block), WAITING (waiting with no timeout, for example wait(), join(), park()), TIMED_WAITING (the same with a timeout, like sleep(ms)) and TERMINATED (run() finished or threw).

These are exactly the words jstack prints, so knowing them lets me read a thread dump. Two surprises: Java does not separate "running" from "ready", and a thread blocked in native socket IO still shows RUNNABLE. Waiting for a ReentrantLock shows WAITING (it parks), not BLOCKED. Only synchronized gives BLOCKED. A terminated thread cannot be restarted: a second start() throws IllegalThreadStateException.

Remember: BLOCKED means "waiting for a monitor". Everything else that waits is WAITING or TIMED_WAITING.

What is the difference between start() and run()? Basic

start() asks the JVM to create a new OS thread, which then calls run(). Calling run() directly is just an ordinary method call on the current thread, so nothing runs in parallel. start() can be called only once per thread object.

A classic bug is new Thread(task).run(): the code works but blocks the caller. Today I rarely create threads by hand. I submit a Runnable or Callable to an executor, so thread creation, naming and limits live in one place.

Remember: start = new thread, run = plain call.

What is the difference between Runnable, Callable and Future? Basic

Runnable.run() returns nothing and cannot throw checked exceptions. Callable.call() returns a value and may throw. A Future is the handle I get back when I submit a task: it lets me wait for the result with get(), ask if it is done, or cancel it.

ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> computePrice());   // Callable
int price = f.get(2, TimeUnit.SECONDS);                    // blocks, with timeout

get() blocks, and if the task threw, it rethrows wrapped in ExecutionException. Plain Future cannot chain steps or combine results, which is why CompletableFuture exists. cancel(true) only interrupts the worker, so the task must cooperate.

Remember: Runnable = no result, Callable = result and exceptions, Future = the receipt.

What is the difference between sleep() and wait()? Basic

sleep pauses the current thread for a time and keeps every lock it holds. wait must be called inside a synchronized block on that object, releases that object's monitor, and sleeps until another thread calls notify or notifyAll (or a timeout or interrupt happens).

sleep is a Thread static method used for delays. wait is an Object method used for coordination: "wait until my condition is true". Calling wait without owning the monitor throws IllegalMonitorStateException. Both throw InterruptedException if interrupted.

Remember: sleep keeps the lock, wait gives it up.

How do you stop a running thread? What does interrupt() do? Intermediate

I never kill a thread. I ask it to stop with interrupt() and the task checks the flag and exits cleanly. interrupt() sets the thread's interrupted flag, and if the thread is in sleep, wait, join or a blocking queue call, that call throws InterruptedException right away.

Two rules decide whether it works. First, when InterruptedException is thrown the flag is cleared, so the catch block should either rethrow or call Thread.currentThread().interrupt() to restore it. Swallowing it silently is the common bug that makes a thread unkillable. Second, a CPU loop must check isInterrupted() itself. Thread.stop() is deprecated for removal because it releases locks mid-update and leaves objects half-written.

while (!Thread.currentThread().isInterrupted()) {
    try { process(queue.take()); }
    catch (InterruptedException e) { Thread.currentThread().interrupt(); break; }
}

Remember: stopping is cooperative. Never swallow InterruptedException: rethrow it or restore the flag.

2. Monitors, volatile and the Java Memory Model

What does synchronized do? Basic

It gives mutual exclusion and visibility. Only one thread at a time can hold a given object's monitor (its built-in lock), so only one can be inside any block guarded by that same object. When a thread leaves the block, its writes are flushed, and the next thread that enters sees them.

The second half is the one people forget: synchronized is not only a lock, it is also a happens-before edge (unlock then lock on the same monitor). So reads must use the same lock too, otherwise they may see stale data. The lock is released automatically on exit, even through an exception. Its limits: no timeout, no way to interrupt a waiting thread, no fairness choice, and one condition queue per monitor. Those are the reasons ReentrantLock exists.

private int balance;
public synchronized void deposit(int x) { balance += x; }
public synchronized int  balance()      { return balance; }  // reads need the lock too

Remember: synchronized = exclusion + visibility, and both sides (read and write) must use the same lock.

What object does synchronized lock on for instance methods, static methods and blocks? Basic

An instance method locks this. A static method locks the Class object. A synchronized (x) block locks whatever object x is. Two threads block each other only if they use the same lock object.

So a synchronized instance method and a synchronized static method do not exclude each other, and two instances of the same class do not exclude each other either. A common bug is locking on something that changes or is shared by accident: a non-final field, a boxed Integer, or an interned String literal that unrelated code also locks on. I prefer a private final lock object, because outside code cannot grab it.

private final Object lock = new Object();
void update() { synchronized (lock) { /* guarded state */ } }

Remember: instance method = this, static method = the Class, block = what you name. Same lock or no protection.

What does "reentrant" mean for a lock? Basic

A thread that already holds a lock can acquire it again without blocking itself. The lock counts how many times the owner took it and frees it only when the owner has released it the same number of times. Both synchronized and ReentrantLock work this way.

Without it, a synchronized method calling another synchronized method on the same object, or a subclass calling super.method(), would deadlock on itself. With ReentrantLock each lock() needs its own unlock(), which is why getHoldCount() exists for debugging.

Remember: reentrant = the owner can re-enter, a hold count tracks it.

What does volatile guarantee? Basic

Two things: visibility and ordering. A write to a volatile variable is seen immediately by any thread that reads it afterwards, and everything the writer did before that write is also visible to the reader. It does not make compound operations like count++ atomic and it does not give mutual exclusion.

Without volatile, a thread may cache a value in a register and loop forever on a flag that another thread already changed. The JIT may even hoist the read out of the loop. Volatile is the right tool for one independent flag or a reference that is safely published: volatile boolean running, or a volatile reference to an immutable config object that is swapped as a whole. It is the wrong tool when the new value depends on the old one (count++) or when several fields must change together.

private volatile boolean running = true;
void stop() { running = false; }          // thread 1
void loop() { while (running) { work(); } } // thread 2 now sees it

Remember: volatile = latest value for everyone, not atomic read-modify-write.

When would you use volatile, and when synchronized or an atomic class? Intermediate

Volatile when one thread writes a standalone value and others only read it. An atomic class (AtomicInteger and friends) when I need an atomic update of a single variable, like a counter. synchronized or a lock when several variables must change together or a check-then-act sequence must not be interleaved.

Example of the third case: moving money between two balances. Each field could be atomic and the transfer would still be wrong, because another thread can see the money gone from one account and not yet in the other. The invariant (total is constant) needs one lock around both updates.

Remember: one value, one writer: volatile. One variable, many writers: atomic. Several values: lock.

What are atomicity, visibility and ordering, and which tool fixes which? Intermediate

Atomicity means an operation cannot be seen half done. Visibility means a write by one thread becomes visible to others. Ordering means other threads see steps in the order the program wrote them. Locks fix all three, volatile fixes visibility and ordering, atomics fix atomicity (and visibility) for one variable.

A good way to debug: when a bug appears, ask "which of the three is missing?" A lost counter update is atomicity. A loop that never ends is visibility. A reader seeing a half-built object is ordering (safe publication).

Remember: atomic (not half done), visible (seen by others), ordered (in program order). Name the missing one.

What is the Java Memory Model and why does it exist? Senior

The Java Memory Model (JMM) is the specification of when one thread is guaranteed to see another thread's writes. It exists because CPUs have per-core caches and store buffers, and the compiler and JIT reorder instructions for speed. Without a contract, code would behave differently on every machine. The JMM defines that contract through happens-before.

The idea is simple: if write A happens-before read B, B must see A. If there is no happens-before edge between them, B may see the old value, the new value, or (for reordered writes) a surprising mix. Within one thread, the program appears to run in order (as-if-serial), but other threads may see reordered effects. A data race (two threads touch one variable, one writes, no happens-before) is exactly the situation where the JMM promises nothing useful. The JMM is also what lets the JIT and CPU stay fast: it only constrains what is synchronized.

Remember: no happens-before edge means no guarantee. The JMM is the contract that lets the compiler stay fast and your code stay correct.

Explain happens-before and the main rules that create it. Senior

Happens-before is a guarantee: if action A happens-before action B, then everything A did is visible to B and A is ordered before B. The edges I rely on are: program order within one thread, unlock then lock of the same monitor, volatile write then volatile read of the same variable, Thread.start() then everything in that thread, thread end then join(), and submitting a task to an executor then the task running. It is also transitive.

Transitivity is what makes volatile useful: writes made before the volatile write become visible after the matching volatile read, even plain fields. That is the "publish with a flag" pattern shown below. If one link is missing, the last read can be stale.

  • Other edges: a Future's completion happens-before get() returns; actions before putting into a concurrent collection happen-before actions after taking from it; CountDownLatch.countDown() happens-before the matching await() returns.
  • Plain unsynchronized fields have no edges at all.

Remember: edges come from lock/unlock, volatile, start/join, executors and concurrent collections. Chain them or you have a race.

What is safe publication and why can another thread see a half-built object? Senior

Publishing means making an object reachable by another thread. It is safe only if the hand-off creates a happens-before edge. If I just assign the object to a plain shared field, the reader may see the reference before the constructor's writes, because the compiler or CPU can reorder them, and so it can see default values like null or 0 in the fields.

Safe ways to publish: store it in a volatile field, store it under a lock, put it in a concurrent collection or hand it over a BlockingQueue, create it in a static initializer, or make its fields final. Final fields get a special guarantee: once the constructor finishes normally, every thread sees their correct values without any further sync, provided this did not escape during construction. That is one reason immutable objects are easy to share. Leaking this from a constructor (registering a listener, starting a thread) breaks this guarantee.

class Holder { int a = 1; }
static Holder h;             // plain field: unsafe to publish through
static volatile Holder hv;   // safe

Remember: an unsafe publication can show a non-null object with empty fields. Publish via volatile, lock, concurrent collection, or final fields.

Why does double-checked locking need volatile? Senior

Because creating an object is several steps, and without volatile they can be reordered: allocate memory, publish the reference, then run the constructor. Another thread doing the unsynchronized first check can then see a non-null reference to a half-built object. Volatile forbids that reordering.

class Config {
    private static volatile Config instance;
    static Config get() {
        Config c = instance;                 // first check, no lock
        if (c == null) {
            synchronized (Config.class) {
                c = instance;                // second check, under lock
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }
}

The first check avoids locking on the hot path, the second prevents two threads both creating one. Simpler alternatives are better in practice: an enum singleton or the holder-class idiom (private static class H { static final Config I = new Config(); }), which are lazy and thread-safe thanks to class initialization rules, with no volatile and no lock. In Spring I would just let the container make a singleton bean.

Remember: DCL without volatile is broken. Prefer the holder-class idiom or an enum.

How do wait(), notify() and notifyAll() work? Why is wait always in a loop? Intermediate

A thread holding a monitor calls wait() when a condition is not true yet. That releases the monitor and parks the thread in the monitor's wait set. Another thread changes the state and calls notify or notifyAll. The woken thread must re-acquire the monitor and then re-check the condition, which is why the call sits in a while loop, never an if.

Three reasons for the loop: spurious wakeups are allowed by the spec, another thread may have taken the item between the notify and my re-acquiring the lock, and with notifyAll several waiters wake for one event. I use notifyAll by default: notify wakes only one arbitrary waiter, which is wrong if waiters are waiting for different conditions, and can leave the system stuck. In new code I would rather use a BlockingQueue or Condition.

synchronized (queue) {
    while (queue.isEmpty()) queue.wait();     // condition re-checked after every wakeup
    item = queue.remove();
}

Remember: wait in a while loop, notifyAll by default, always inside synchronized on the same object.

3. Race conditions, deadlock, livelock, starvation

What is a race condition? How is it different from a data race? Basic

A race condition is a bug where the result depends on how threads happen to interleave. A data race is the narrower, technical case: two threads access the same variable at the same time, at least one writes, and nothing orders them. You can have a race condition without a data race (two properly locked calls in the wrong order) and a data race without visible harm.

The two usual patterns are check-then-act (if (!map.containsKey(k)) map.put(k, v)) and read-modify-write (count++). Each call may be thread-safe on its own, but the sequence is not. The fix is to make the whole sequence one atomic unit: hold one lock around it, use an atomic operation like putIfAbsent or merge, or avoid shared state. Races are hard because they pass tests on a laptop and fail under production load.

Remember: thread-safe parts do not make a thread-safe sequence. Guard the whole check-then-act.

Why is count++ not thread-safe, even if count is volatile? Basic

Because count++ is three steps: read, add one, write. Two threads can both read 5, both compute 6 and both write 6, so one increment is lost. Volatile only makes each single read and write visible. It does not stop two threads from interleaving between the steps.

Fixes: AtomicInteger.incrementAndGet() (a CAS loop), synchronized around the update, or LongAdder for a statistics counter with heavy contention. The same thing happens with map.put(k, map.get(k) + 1); use map.merge(k, 1, Integer::sum) on a ConcurrentHashMap. And note a JVM lock does nothing if the real state is a database row shared by several instances. There you use an atomic UPDATE ... SET qty = qty - 1 or optimistic locking.

Remember: ++ is read, add, write. Volatile does not glue those three together.

What is a deadlock? What are the conditions and how do you prevent it? Intermediate

A deadlock is when two or more threads each hold a lock the other needs, so all wait forever. It needs four conditions together: mutual exclusion, hold and wait, no preemption, and circular wait. I prevent it by breaking one, and the cheapest is circular wait: always acquire locks in the same global order.

  • Lock ordering: sort by a stable key, for example account id, and always lock the smaller first.
  • Timeouts: tryLock(timeout); on failure release what you hold, back off and retry (this breaks "hold and wait", but watch for livelock; add random delay).
  • Fewer locks: one coarse lock, or avoid nested locking; do not call unknown code (callbacks, listeners) while holding a lock.
  • Lock-free design: queues, immutable data, one owner thread per resource.
void transfer(Account a, Account b, long amt) {
    Account first = a.id < b.id ? a : b, second = first == a ? b : a;
    synchronized (first) { synchronized (second) { a.debit(amt); b.credit(amt); } }
}

Remember: same lock order everywhere, tryLock with timeout as a safety net, and no foreign calls under a lock.

How do you detect a deadlock in a running application? Intermediate

I take a thread dump with jcmd PID Thread.print (or jstack PID). The JVM detects lock cycles itself and prints "Found one Java-level deadlock" at the end, listing each thread, the lock it holds, the lock it waits for and the code line. Inside the app, ThreadMXBean.findDeadlockedThreads() does the same check and can drive an alert.

It covers both synchronized monitors and java.util.concurrent locks (findMonitorDeadlockedThreads is the older, monitor-only variant). The detector finds only lock cycles. A hang caused by a lost notify, an exhausted pool or a missing countDown has no cycle, so I must read the dump myself: take three dumps a few seconds apart and see which threads never move. Details are in the diagnosing section.

Remember: dump first. "Found one Java-level deadlock" names the threads and lines. No such text does not mean no hang.

What are livelock and starvation? Intermediate

In a livelock the threads are not blocked; they keep reacting to each other and doing work, but make no progress, like two people in a corridor who both keep stepping aside. In starvation a thread is ready but never gets the resource because others always win. A deadlock burns no CPU; a livelock usually does.

Livelock typically comes from naive deadlock avoidance: both threads tryLock, fail, release and retry at the same moment, forever. The cure is randomized backoff or an ordering rule. Starvation comes from unfair locks, thread priorities, or one long-running task occupying a small pool. Cures: a fair lock (new ReentrantLock(true), which costs throughput), separate pools for different work classes, and short critical sections.

Remember: deadlock = stuck and quiet, livelock = busy and stuck, starvation = never gets a turn.

4. Locks, atomics and ThreadLocal

What does ReentrantLock give you that synchronized does not? Intermediate

Control. ReentrantLock can try without blocking (tryLock), wait with a timeout, wait in a way that responds to interrupts (lockInterruptibly), be created fair, and offer several Condition queues. synchronized is simpler and cannot be forgotten open, so I use it by default and switch to the lock only for one of those features.

private final ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(500, TimeUnit.MILLISECONDS)) {
    try { update(); }
    finally { lock.unlock(); }      // always in finally
} else { /* back off, report busy */ }
  • Memory semantics are the same: unlock happens-before the next lock.
  • The price is discipline: forget unlock() in finally and the lock is held forever.
  • Fair mode (new ReentrantLock(true)) serves the longest waiter first and avoids starvation, but is much slower than the default, because the default lets a running thread "barge in" and grab the lock.
  • Both are reentrant. Since Java 6, synchronized is well optimized (biased locking was removed in Java 21), so do not choose the lock for speed.

Remember: synchronized for simplicity, ReentrantLock for tryLock, timeout, interruptibility, fairness and several conditions. Unlock in finally.

How does ReentrantLock work inside? What is AbstractQueuedSynchronizer? Senior

Most locks and synchronizers in java.util.concurrent (ReentrantLock, Semaphore, CountDownLatch, read-write lock) are built on AQS. It holds one volatile int state and a FIFO queue of waiting threads. To acquire, a thread tries to change state with CAS. If that fails, it joins the queue and parks (sleeps with no CPU). On release, the successor at the head of the queue is unparked and tries again.

Each synchronizer only defines what state means. For ReentrantLock it is the hold count (0 means free, plus an owner thread field for reentrancy). For Semaphore it is the number of free permits. For CountDownLatch it is the remaining count. This is why they all share the same fairness, interruptible and timed waiting behavior. The fast path (uncontended lock) is one CAS and no OS involvement, which is why these locks are cheap when there is no contention.

Remember: AQS = a volatile state, CAS to take it, a FIFO queue of parked threads. Each class just decides what state means.

What is a Condition, and why is it better than wait/notify? Intermediate

A Condition is the wait/notify of a ReentrantLock, but one lock can have several of them. A bounded buffer can have "not full" and "not empty" separately, so a producer wakes only consumers and a consumer wakes only producers. With plain wait/notify there is one wait set, so I must use notifyAll and wake everybody.

The rules are the same as wait: call await() while holding the lock (it releases the lock while waiting), and always inside a while loop that re-checks the condition. Use signal() to wake one and signalAll() to wake all. await(timeout) and awaitNanos give timed waits. For ready-made use, ArrayBlockingQueue is built exactly this way.

Remember: Condition = several wait queues per lock, so you wake only the right group.

What is a ReadWriteLock? When does it help and what are its traps? Intermediate

It lets many threads read at the same time, but a writer gets exclusive access. It pays off when reads clearly dominate and reading takes real time. For short reads, a plain lock or a concurrent map is often just as fast, because the read lock itself has overhead.

  • No upgrade: a thread holding the read lock that tries to take the write lock deadlocks (it waits for itself to release). Release the read lock first, then take the write lock and re-check.
  • Downgrade is allowed: take the write lock, take the read lock, then release the write lock.
  • Writer starvation: with a steady stream of readers, writers can wait a long time (the lock is non-fair by default, with some heuristics).

For read-mostly data, I often skip the lock: keep an immutable snapshot in an AtomicReference (or volatile) and replace it whole on update. Readers take no lock at all.

Remember: readers share, writers exclude. No read-to-write upgrade. For read-mostly data, swap an immutable snapshot instead.

What is StampedLock and its optimistic read? Senior

It is a faster read-write lock (Java 8) with a third mode: optimistic read. A reader takes a stamp without locking, reads the fields, then asks validate(stamp) whether a writer came in meanwhile. If yes, it retries or falls back to a real read lock. For read-heavy code with short reads this is the fastest option in the JDK.

long s = lock.tryOptimisticRead();
double x = this.x, y = this.y;          // copy to locals
if (!lock.validate(s)) {                // a writer interfered
    s = lock.readLock();
    try { x = this.x; y = this.y; } finally { lock.unlockRead(s); }
}

The costs: it is not reentrant, it has no Condition, and mistakes are easy (using the fields before validating, losing the stamp). The optimistic read may see inconsistent values until validated, so only copy to locals and compute after validation. I would use it only for a proven hot spot.

Remember: StampedLock = read without lock, then validate. Not reentrant, no conditions.

What is CAS, and how do the atomic classes use it? Intermediate

Compare-and-swap is a CPU instruction that says: "set this variable to the new value only if it still holds the expected value, and tell me whether it worked". Atomic classes use it in a loop: read the current value, compute the new one, try to CAS, and retry if another thread got there first. There is no lock and no thread is ever put to sleep.

AtomicInteger n = new AtomicInteger();
n.incrementAndGet();                         // CAS loop inside
n.updateAndGet(v -> Math.min(v + 1, 100));   // function must be side-effect free
n.compareAndSet(5, 6);                       // true only if it was 5

CAS is great at low and medium contention. Under heavy contention many threads retry, wasting CPU. The update function in updateAndGet may run several times, so keep it pure. A CAS handles a single variable only. For two fields, put them into one immutable object and CAS the reference (AtomicReference). On the JDK side: AtomicInteger/Long/Boolean/Reference, the field updaters and VarHandle (Java 9) all use this.

Remember: CAS = read, compute, "set if still unchanged", retry. Lock-free, one variable, pure update function.

What is the ABA problem? Senior

CAS only checks that the value is the same as before, not that nothing happened in between. If a value goes A to B and back to A, my CAS succeeds although the world changed. It matters mostly in lock-free structures built on node pointers.

Classic example: a lock-free stack. Thread 1 reads top = A, with A.next = B, and is paused. Meanwhile thread 2 pops A, pops B and pushes A back. Now top is A again, but A.next is something else. Thread 1 resumes, CAS (A to B) succeeds, and it sets the top to the already-removed B. The fix is to add a version: AtomicStampedReference compares the reference and an int stamp, and AtomicMarkableReference uses a boolean mark. For counters it does not matter: counter values going back to the same number is harmless. In Java, garbage collection removes a part of the problem, because a node cannot be reused while someone still holds a reference to it.

Remember: CAS sees "same value", not "same history". Add a version stamp if history matters.

When do you use LongAdder instead of AtomicLong? Intermediate

LongAdder for a counter that is updated by many threads and read rarely, like metrics, request counts and hit counts. AtomicLong when I need the exact current value in logic, like an id generator or "decrement if above zero".

Under heavy contention every thread on an AtomicLong fights over one memory cell, and failed CASes waste CPU. LongAdder keeps several cells (striping): each thread usually updates a different cell, and sum() adds them up when asked. That gives much higher write throughput. The trade-off is that sum() is not an atomic snapshot (updates happening during the sum may or may not be counted), and it uses more memory. You also cannot do compare-and-set on it. Related: LongAccumulator for min, max or other combiners.

Remember: LongAdder for stats with many writers, AtomicLong when you need exact, conditional updates.

What is ThreadLocal and when do you use it? Intermediate

ThreadLocal gives each thread its own private copy of a variable, so no locking is needed. Typical uses are per-request context (user id, trace id, tenant) in a web server, and per-thread non-thread-safe helper objects like the old SimpleDateFormat.

Inside, each Thread has its own map from ThreadLocal to value, so reading it is a lookup in the current thread's map. Cautions: in thread pools, threads live a long time and are reused, so the value must be removed after use (next question). A child thread or an async task does not see the parent's value automatically (InheritableThreadLocal copies only at thread creation, which does not work with pools). It is also hidden state that makes code harder to test. With virtual threads, millions of per-thread copies get expensive, and Java 25's ScopedValue is the intended replacement for many uses.

static final ThreadLocal<String> TRACE = new ThreadLocal<>();
TRACE.set(id);
try { handle(); } finally { TRACE.remove(); }

Remember: ThreadLocal = one copy per thread. Set and remove in the same try/finally.

How can ThreadLocal cause a memory leak or data leak? Senior

Pooled threads never die, so their ThreadLocalMap lives as long as the pool. The map holds the key (the ThreadLocal) weakly, but the value strongly. If I never call remove(), the value stays reachable from the thread forever. That is a memory leak. It can also be a data leak: the next request on that thread reads the previous user's value.

On an app server with redeploys it is worse: a value whose class came from the web app's class loader keeps that whole class loader alive (a Metaspace leak). The key is weak, so a stale entry is cleaned only lazily when the map happens to be touched. The only reliable fix is set and remove in the same try/finally, usually in a servlet filter, interceptor or task wrapper.

Remember: in a pool, a ThreadLocal without remove() leaks memory and leaks the last user's data.

5. Thread safety design

How do you make a class thread-safe? What are the strategies? Intermediate

In order of preference: do not share (keep state local to a method, or confined to one thread), share but do not mutate (immutable objects), or share and mutate with a clear rule: one lock that guards each piece of state, an atomic variable, or a concurrent collection. I pick the rule that removes the most risk first.

  • Confinement: local variables, ThreadLocal, or a single owner thread that receives work through a queue.
  • Immutability: final fields, no setters, defensive copies. Safe by construction.
  • Guarding: every access to the state, reads and writes, under the same lock. I document "guarded by X" next to the field.
  • Compose from thread-safe parts, with care: a thread-safe map plus a thread-safe list do not make a thread-safe pair of operations.

Also keep critical sections short, never call foreign code (callbacks, listeners) while holding a lock, and do not let this escape from a constructor. Most Spring singleton beans are fine if they hold no mutable per-request state.

Remember: don't share, don't mutate, or guard with one clear rule. Prefer them in that order.

How do you create an immutable class, and why is it automatically thread-safe? Intermediate

Make the class final, all fields private final, no setters, and defensively copy any mutable object that goes in or comes out. Since nothing can change after construction, there is nothing to race on, and final-field semantics guarantee other threads see the fully built object. Immutable objects need no locks at all.

public final class Order {
    private final String id;
    private final List<Item> items;
    public Order(String id, List<Item> items) {
        this.id = id;
        this.items = List.copyOf(items);     // defensive copy, unmodifiable
    }
    public List<Item> items() { return items; }
}

The catch is "shallow": final List alone still allows adding to the list. Java records are shallowly immutable the same way, so use List.copyOf in the constructor. For updates you create a new object (withStatus(...)). String and the java.time classes are immutable for exactly this reason. Creating objects costs a little, but cheaply and safely avoids a whole class of bugs.

Remember: final class, final fields, copy mutable parts in and out. Immutable means no locks.

How do you write a thread-safe singleton? Intermediate

The simplest correct choices are an enum singleton or the holder-class idiom. Both are lazy and thread-safe because the JVM initializes a class exactly once under its own lock. In a Spring app I just declare a bean, which is a singleton by default.

class Registry {
    private Registry() {}
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    static Registry get() { return Holder.INSTANCE; }   // created on first call
}
enum Cache { INSTANCE; /* fields and methods */ }

Eager static final X = new X() is also thread-safe, just not lazy. Double-checked locking works only with volatile (see the DCL question). The enum also resists reflection and serialization attacks that can create a second instance of a normal singleton class. A singleton that holds mutable state is still a shared mutable object, so it needs its own protection. Singletons also make tests harder, so prefer injection.

Remember: enum or holder class. Thread-safe creation does not make the object's state thread-safe.

How do you reduce lock contention? Senior

Hold locks for less time and lock less data per lock. Do slow work (IO, remote calls, heavy computing) outside the critical section, split one big lock into several independent ones, use striping or concurrent structures, and replace locks with immutable snapshots, atomics or LongAdder where possible.

  • Shrink the section: copy the data under the lock, then process the copy outside. Never do IO while holding a lock.
  • Split locks (striping): lock per user or per bucket instead of one global lock. ConcurrentHashMap is this idea built in.
  • Read-mostly data: an immutable snapshot swapped through AtomicReference, or CopyOnWriteArrayList.
  • Measure first: thread dumps show many threads BLOCKED on one monitor; a profiler (JFR lock events, async-profiler) shows the hot lock. Splitting locks increases deadlock risk, so keep a clear lock order.

Remember: shorter sections, smaller scope, no IO under a lock. Measure before splitting.

6. Executors and thread pools

Why use a thread pool instead of creating a thread per task? Basic

Because threads are expensive and unlimited threads kill the server. A pool reuses a fixed set of threads, so there is no creation cost per task, and its size is a hard cap on concurrency. When load rises beyond the cap, work waits in a queue instead of exhausting memory and CPU.

Creating an OS thread costs time (tens to hundreds of microseconds) and reserves about 1 MB of stack. Ten thousand threads means 10 GB of address space reserved, heavy context switching, and eventually OutOfMemoryError: unable to create native thread. A pool also gives one place to set names, handle exceptions, monitor queue length and shut down cleanly. The one exception is virtual threads (Java 21), which are so cheap that you create one per task and do not pool them.

Remember: a pool = reuse + a cap + a queue + one place to manage threads.

How does ThreadPoolExecutor handle a new task? Explain core size, queue and max size. Intermediate

In this order: if fewer than corePoolSize threads are running, start a new thread for the task. Otherwise put the task in the queue. Only if the queue is full, start extra threads up to maximumPoolSize. If the queue is full and the pool is at max, the rejection policy runs.

The surprising part: extra threads appear only when the queue is full. With an unbounded queue (LinkedBlockingQueue with no capacity), the queue never fills, so the pool never grows past core and maximumPoolSize is ignored. Threads above core die after keepAliveTime of idleness. Each worker is a thread looping on queue.take() and running tasks. A SynchronousQueue (no storage) makes the pool grow straight to max, which is what the cached pool does.

new ThreadPoolExecutor(
    8, 16,                                   // core, max
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),           // bounded queue
    namedThreadFactory("orders"),
    new ThreadPoolExecutor.CallerRunsPolicy());

Remember: core first, then queue, then up to max, then reject. Max grows only when the queue is full.

Which queue and which rejection policy do you pick? Intermediate

A bounded queue, sized to the burst I am willing to absorb, and a rejection policy that tells callers to slow down: CallerRunsPolicy for internal back-pressure, or AbortPolicy (the default) when I can return "busy" to the client. I avoid unbounded queues and silent discards.

  • ArrayBlockingQueue / bounded LinkedBlockingQueue: the normal choice. Gives back-pressure and caps memory.
  • SynchronousQueue: direct hand-off, no buffering. Used with a large max (cached pool).
  • PriorityBlockingQueue: unbounded priority ordering; use with care.
  • AbortPolicy: throws RejectedExecutionException. Handle it.
  • CallerRunsPolicy: the submitting thread runs the task itself, which naturally slows the producer. Not good if the caller is a latency-critical thread (event loop).
  • DiscardPolicy / DiscardOldest: silently drop work. Only for tasks that really are optional (metrics, hints).

Queue size is a latency decision: a queue of 10,000 with 5 ms tasks means a request can wait 10 seconds, which is usually worse than being rejected quickly.

Remember: bounded queue plus a rejection policy that pushes back. An unbounded queue is a hidden memory leak.

Why do many teams ban the Executors.newFixedThreadPool and newCachedThreadPool factory methods? Intermediate

Because both hide an unbounded resource. newFixedThreadPool uses an unbounded queue, so a slow consumer lets tasks pile up until the heap runs out. newCachedThreadPool allows an unlimited number of threads, so a burst can create thousands and fail with "unable to create native thread". I build a ThreadPoolExecutor myself with bounded settings.

How do you decide the size of a thread pool? Intermediate

It depends on what the tasks do. For CPU-bound work, about the number of cores (or cores + 1). For IO-bound work, more: roughly cores x (1 + wait time / compute time). Then I load test and adjust, because the formula is only a start.

Example: 8 cores, each task computes 10 ms and waits 90 ms for a database. Ratio is 9, so about 8 x 10 = 80 threads. But do not size the pool beyond what the downstream can take: if the database connection pool has 20 connections, 80 threads just queue for connections. So the real limit is the smallest resource in the chain (threads, connections, remote rate limits). Prefer separate pools for CPU work and for blocking IO, and watch queue length and active thread count as metrics. On Java 21, blocking IO work is better done on virtual threads with a semaphore for the limit.

Remember: CPU-bound = cores, IO-bound = cores x (1 + wait/compute), capped by the slowest dependency.

What is the difference between execute() and submit()? What happens to exceptions? Intermediate

execute(Runnable) returns nothing; an exception escapes to the thread's uncaught exception handler, and that worker thread dies and is replaced. submit() returns a Future and captures any exception inside it, so nothing is printed and the error appears only when someone calls get().

That second point is a classic production trap: with submit and no get(), a failing task fails completely silently. Either read the future, or catch and log inside the task. Same rule for CompletableFuture: an exception sits in the future until someone handles it. Also, a task that throws kills only itself; the pool stays healthy.

pool.submit(() -> { throw new IllegalStateException("boom"); });  // silent!
pool.submit(() -> { try { work(); } catch (Exception e) { log.error("task failed", e); } });

Remember: submit swallows exceptions into the Future. Always log inside the task or call get().

How do you shut down an executor properly? Intermediate

Call shutdown() to stop accepting new tasks while finishing queued ones, wait with awaitTermination(timeout), and if it times out call shutdownNow(), which interrupts running tasks and returns the tasks that never started. One owner is responsible for this, usually at application stop.

pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();
    pool.awaitTermination(10, TimeUnit.SECONDS);
}

If I forget, non-daemon pool threads keep the JVM from exiting: the process "won't stop". shutdownNow() only sends interrupts, so tasks that ignore interruption keep running. In Java 19+ ExecutorService is AutoCloseable, and close() does this shutdown-and-wait sequence for you (try-with-resources). In Spring, ThreadPoolTaskExecutor has a waitForTasksToCompleteOnShutdown setting.

Remember: shutdown, awaitTermination, then shutdownNow. Forgetting it keeps the JVM alive.

Can a thread pool deadlock itself? Senior

Yes: thread-starvation deadlock. If a task running in a pool submits a subtask to the same pool and blocks waiting for it, then when all threads are busy waiting for subtasks that sit in the queue, nobody is left to run them, and everything hangs. There is no lock cycle, so the deadlock detector says nothing.

It is easy to trigger with a single-thread executor, or with a small fixed pool under load: parent tasks occupy all the threads, children wait in the queue. In a thread dump you see all workers in Future.get() or CompletableFuture.join(), and the queue is not empty. Fixes: use a separate pool for the child tasks, do not block inside pool tasks (use thenCompose chaining), or use ForkJoinPool, which is designed for tasks that wait for subtasks because a waiting worker runs other tasks meanwhile.

Remember: never block a pool thread on work that needs the same pool. Separate pools or async chaining.

How do scheduleAtFixedRate and scheduleWithFixedDelay differ? What if the task throws? Intermediate

Fixed rate starts runs at fixed intervals (0, 10 s, 20 s ...) measured from the start. Fixed delay waits the given time after the previous run ends. And if a periodic task throws an exception, all further runs are silently cancelled, so I always wrap the body in try/catch.

With fixed rate, if one run takes longer than the period, the next run starts late, right after the previous one finishes (runs of the same task never overlap). Fixed delay is safer when the gap matters, such as polling. The silent stop is a very common production bug: a single unexpected exception once and the scheduled job never runs again, with nothing in the logs, because the exception lives in the returned ScheduledFuture. The default ScheduledThreadPoolExecutor in newScheduledThreadPool also has an unbounded queue. In Spring, @Scheduled behaves differently: it logs the error and keeps going, but by default it uses a single thread, so one slow job delays the rest.

scheduler.scheduleWithFixedDelay(() -> {
    try { poll(); } catch (Throwable t) { log.error("poll failed", t); }
}, 0, 10, TimeUnit.SECONDS);

Remember: rate = fixed start times, delay = gap after end. Catch everything inside a periodic task.

What is the Fork/Join framework and work stealing? Intermediate

Fork/Join is a pool for divide-and-conquer work: a task splits itself into smaller subtasks (fork), waits for them (join) and combines results. Each worker has its own deque (double-ended queue) of tasks, and an idle worker steals tasks from the far end of a busy worker's deque, so all cores stay busy without a single shared queue.

The owner takes from the newest end (cache-friendly, big tasks left for thieves), while thieves take from the oldest end. A worker that waits on a join does not just sleep: it runs other tasks meanwhile, which is why Fork/Join does not suffer the starvation deadlock of normal pools. Use it for CPU-bound recursive work (RecursiveTask), not for blocking calls. A shared common pool (ForkJoinPool.commonPool(), by default cores minus 1 threads) also runs parallel streams and default CompletableFuture async stages.

Remember: split, fork, join, and idle workers steal. CPU-bound work only, never blocking IO.

Should you use parallel streams? What are the risks? Intermediate

Only for CPU-heavy work on large data, with no side effects, and after measuring. They split the data across the shared common ForkJoinPool. For small collections, IO work, or code that calls blocking services, they are slower or harmful.

  • Shared pool: every parallel stream and default CompletableFuture in the JVM shares one pool. One slow, blocking stream starves all others, which is a real production incident (see scenarios).
  • Overhead: splitting and merging cost more than the work for small or cheap tasks. Sources like LinkedList or Stream.iterate split badly.
  • Correctness: lambdas must be stateless and non-interfering. Writing to a shared ArrayList from forEach is a data race; use collect. reduce needs an associative function.
  • Order: forEach is unordered; forEachOrdered keeps order but loses parallelism.

Remember: parallel streams share one common pool. CPU-only, big data, no side effects, measured.

How does Spring's @Async run tasks, and what do people get wrong? Intermediate

With @EnableAsync, Spring wraps the bean in a proxy, and a call to an @Async method is handed to a TaskExecutor instead of running on the caller's thread. The caller gets a return of void, a Future or a CompletableFuture right away. The common mistakes are the default executor, self-invocation and lost context.

  • Executor: without configuration, plain Spring uses SimpleAsyncTaskExecutor, which creates a new thread for each call (no limit). Spring Boot auto-configures a ThreadPoolTaskExecutor (core 8, unbounded queue by default in recent versions, so check yours). I define my own bounded executor and name it in @Async("ioPool").
  • Self-invocation: calling an @Async method from another method of the same class bypasses the proxy, so it runs synchronously.
  • Exceptions: in a void method they go to an AsyncUncaughtExceptionHandler; otherwise they are in the returned future.
  • Context: the security context, request scope and MDC logging fields do not follow the task automatically; use a TaskDecorator to copy them.
  • Transactions: the async method runs in its own thread, so it is not part of the caller's transaction.

Remember: @Async = proxy + executor. Configure a bounded pool, avoid self-calls, and propagate context.

7. CompletableFuture

What is CompletableFuture and why is it better than Future? Intermediate

CompletableFuture (Java 8) is a future you can chain. Instead of blocking on get(), I describe what happens next: thenApply to transform the result, thenCompose to start a dependent async call, thenCombine to merge two independent results, and exceptionally or handle for errors. Plain Future can only block and wait.

CompletableFuture.supplyAsync(() -> userClient.get(id), ioPool)
    .thenCompose(u -> ordersClient.forUser(u.id()))     // next async call
    .thenApply(OrderSummary::from)                      // plain transform
    .exceptionally(e -> OrderSummary.empty());

It can also be completed manually (complete(value)), which makes it a bridge to callback-based APIs. The main benefit is that no thread sits idle waiting for the first step while the second is pending: stages run when their input is ready. The costs are harder stack traces and the temptation to block anyway with join(). On Java 21 with virtual threads, plain blocking code is often simpler and just as scalable.

Remember: a Future you can chain, combine and recover from, without blocking.

What is the difference between thenApply, thenCompose and thenCombine? Intermediate

thenApply is map: transform the result with a plain function. thenCompose is flatMap: my function itself returns a CompletableFuture (a dependent async call), and it gets flattened. thenCombine merges two independent futures that run in parallel.

If I used thenApply with a function that returns a future, I would get a CompletableFuture<CompletableFuture<X>>, which is the sign I wanted thenCompose. Use thenCompose when step 2 needs step 1's result (user then orders). Use thenCombine when the two do not depend on each other (price and stock), because both start immediately and total time is the slower one, not the sum. Variants: thenAccept (consume, returns void), thenRun (ignore result).

Remember: apply = map, compose = flatMap (dependent call), combine = two in parallel.

On which thread do CompletableFuture stages run? What does the Async suffix change? Senior

If I do not pass an executor, supplyAsync and the ...Async methods run on the shared ForkJoin common pool. The non-async methods like thenApply run on whichever thread completes the previous stage, or on the caller's thread if it is already complete. For blocking IO I always pass my own executor.

The common pool has only about cores minus 1 threads and is shared with parallel streams, so blocking calls in it starve everything else. And if it has fewer than two threads (a single-CPU container), CompletableFuture falls back to starting a new thread per task. The other trap is that a non-async callback may run inside a thread that must not be blocked (an IO event loop thread), so a slow callback there is a hidden stall. Rules I follow: pass an executor for every async stage that does IO, give each dependency its own bounded pool, and use thenApplyAsync(fn, executor) when the callback itself is heavy.

Remember: default is the shared common pool. Give blocking IO your own executor.

How do you handle errors in a CompletableFuture chain? Intermediate

An exception in any stage skips the following stages and ends in the final future. I recover with exceptionally (give a fallback value), handle (get both result and exception, return a new value), or observe it with whenComplete (it does not change the outcome). If nobody handles it, it stays hidden until someone calls get or join.

  • Wrapping: in later stages the exception arrives wrapped in CompletionException; in get() it is wrapped in ExecutionException. Use e.getCause() to see the real one.
  • get() vs join(): get throws checked exceptions; join throws unchecked CompletionException.
  • Fire and forget: a future nobody reads fails silently, so end the chain with whenComplete to log.
  • Timeouts (Java 9): orTimeout(2, SECONDS) fails with TimeoutException; completeOnTimeout(default, 2, SECONDS) supplies a default.
cf.orTimeout(2, TimeUnit.SECONDS)
  .handle((v, ex) -> ex == null ? v : fallback());

Remember: exceptionally = fallback, handle = both, whenComplete = peek. Unhandled errors vanish silently.

How do you run several calls in parallel and wait for all of them? Intermediate

Start every call first as its own CompletableFuture on a proper executor, then combine with allOf(...), which completes when all are done. Then read each result with join(), which does not block any more because they are finished. anyOf completes when the first one does.

var a = CompletableFuture.supplyAsync(() -> svcA.call(), io);
var b = CompletableFuture.supplyAsync(() -> svcB.call(), io);
var c = CompletableFuture.supplyAsync(() -> svcC.call(), io);
CompletableFuture.allOf(a, b, c).orTimeout(3, TimeUnit.SECONDS).join();
Result r = merge(a.join(), b.join(), c.join());

Notes: allOf returns CompletableFuture<Void>, so results are read from the originals. If one fails, allOf still waits for the rest and then completes exceptionally. Do not write the calls in a way that starts the second only after joining the first (that makes them sequential). For a list, use a stream to start them all first and a second stream to join. Do not cancel with cancel(true) expecting an interrupt: for CompletableFuture it does not interrupt the running task.

Remember: start all, then allOf, then join. Add a timeout.

What are the common CompletableFuture mistakes in production code? Senior

Five: running blocking IO on the common pool, calling join() or get() inside another async stage (blocking a pool thread, which can starve the pool), no timeout, swallowed exceptions, and losing thread context (MDC, security, transaction) between stages.

  • No timeout: a hung downstream makes the future never complete and holds the request. Use orTimeout.
  • Blocking inside stages: a stage that blocks on another future in the same pool is the pool-deadlock pattern.
  • Context loss: thread-locals (logging MDC, Spring security) are not copied to the pool thread. Wrap executors to copy them.
  • Hidden failure: a future that nobody reads fails silently.
  • Unbounded fan-out: creating one future per item for 100,000 items floods the pool. Bound it with a semaphore or batches.

Remember: own executor, timeout, handle errors, never block inside a stage, carry the context.

8. Synchronizers and concurrent collections

What is the difference between CountDownLatch and CyclicBarrier? Intermediate

CountDownLatch is a one-time gate: some threads call countDown(), other threads wait in await() until the count reaches zero, and then it stays open forever. CyclicBarrier makes N threads wait for each other at a meeting point, then all go together, and it resets for the next round.

Latch use: the main thread waits until N workers finish startup, or a test starts all threads at the same moment (a start gate with count 1). Barrier use: phased parallel algorithms where every thread must finish round 1 before round 2 starts; it can run a barrier action once per round. If one thread of a barrier times out or is interrupted, the barrier breaks and every waiting thread gets BrokenBarrierException. A latch cannot be reset; create a new one. Phaser is the flexible variant when the number of parties changes. In day-to-day code, most people use CompletableFuture.allOf or invokeAll instead.

Remember: latch = "wait for events", one use. Barrier = "wait for each other", reusable.

What is a Semaphore and when do you use it? Intermediate

A semaphore holds a number of permits. acquire() takes one and blocks if none are left, release() gives one back. I use it to limit how many threads use a resource at once: at most 10 concurrent calls to a partner API, 20 database-heavy tasks, or a bounded fan-out.

private final Semaphore limit = new Semaphore(10);
String call() throws InterruptedException {
    limit.acquire();
    try { return client.fetch(); }
    finally { limit.release(); }                 // release in finally
}

It is not owner-based: any thread can release, and a release without an acquire raises the permit count above what you started with, which is a bug source. tryAcquire(timeout) allows failing fast. A semaphore with 1 permit is like a lock, but not reentrant and not tied to an owner. With virtual threads it becomes the standard way to limit concurrency, because you stop limiting with pool size.

Remember: semaphore = N permits to cap concurrency. Release in finally.

How does ConcurrentHashMap work, and how is it different from Hashtable and synchronizedMap? Intermediate

Hashtable and Collections.synchronizedMap lock the whole map on every call, so all threads queue up. ConcurrentHashMap (Java 8+) locks only one bucket at a time: it uses CAS to insert into an empty bucket and synchronized on the first node of a non-empty bucket, and reads take no lock at all. So many threads work in parallel.

  • Neither keys nor values may be null, because get() returning null would be ambiguous in a concurrent map.
  • Long collision chains turn into trees (red-black), as in HashMap.
  • Iterators are weakly consistent: they never throw ConcurrentModificationException, and may or may not show updates made during iteration.
  • size() is an estimate under concurrent updates; do not use it for decisions.
  • Java 7 used segments (a fixed number of locks). Java 8 replaced this with per-bucket locking.

Remember: CHM = CAS for empty bins, lock one bin otherwise, lock-free reads, no nulls. Not one global lock.

Is if (!map.containsKey(k)) map.put(k, v) safe on a ConcurrentHashMap? Intermediate

No. Each call is thread-safe, but two calls together are not: two threads can both see "absent" and both put. I use the atomic methods built for this: putIfAbsent, computeIfAbsent, compute, merge and replace.

map.merge(word, 1, Integer::sum);                         // atomic counter per key
List<String> l = map.computeIfAbsent(key, k -> new ArrayList<>()); // atomic create
// l itself is a plain ArrayList: adding to it still needs its own protection

The function you pass runs while the bucket is locked, so keep it short, do not block, and never modify the same map inside it (it can deadlock or throw IllegalStateException: Recursive update). This also explains the common double-bug: a ConcurrentHashMap<K, ArrayList> is safe for the map operations but not for the lists inside it. Use a concurrent value type or merge/compute so the update runs under the bucket lock.

Remember: the map is thread-safe, your check-then-act is not. Use putIfAbsent, computeIfAbsent, merge.

What is CopyOnWriteArrayList, and when do you use it instead of a synchronized list? Intermediate

CopyOnWriteArrayList copies the whole backing array on every write, and readers use the old array without any lock. It is ideal for small lists that are read very often and changed rarely, like listener lists or configuration. For frequent writes it is very slow, because each add copies the array.

Iteration works on a snapshot taken at the start, so it never throws ConcurrentModificationException, but it will not show later changes, and iterator remove() is not supported. A Collections.synchronizedList locks every call, and iterating it still needs a manual synchronized (list) around the whole loop, or you get ConcurrentModificationException. Quick guide: read-mostly small list means copy-on-write, a queue means BlockingQueue or ConcurrentLinkedQueue, a map means ConcurrentHashMap, a sorted map means ConcurrentSkipListMap.

Remember: copy-on-write = lock-free snapshot reads, expensive writes. For rarely changed small lists only.

What is a BlockingQueue and how does it help producer-consumer designs? Intermediate

A BlockingQueue is a thread-safe queue where put() blocks when it is full and take() blocks when it is empty. That one structure replaces hand-written wait/notify code for producers and consumers, and a bounded one gives back-pressure for free: fast producers are slowed down instead of filling memory.

  • ArrayBlockingQueue: bounded, one lock.
  • LinkedBlockingQueue: optionally bounded (unbounded by default, so set a capacity), separate put and take locks, better throughput.
  • SynchronousQueue: no storage, a direct hand-off between a producer and a consumer.
  • PriorityBlockingQueue: unbounded, ordered by priority. DelayQueue: elements become available after a delay.
  • Non-blocking forms: offer (returns false if full) and poll (null if empty), plus timeouts.
  • To stop consumers, send a "poison pill" (a special end marker) or interrupt them.

Remember: bounded blocking queue = hand-off plus back-pressure. Prefer it over wait/notify.

9. Virtual threads and modern concurrency

What are virtual threads (Java 21) and how do they work? Intermediate

Virtual threads are lightweight threads managed by the JVM instead of the OS. I write normal blocking code, but when a virtual thread blocks (on a socket, a sleep, a queue), the JVM unmounts it from its carrier thread (a real OS thread) and the carrier runs another virtual thread. So a few carriers can serve hundreds of thousands of waiting tasks.

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var req : requests) exec.submit(() -> handle(req));   // one virtual thread per task
}
Thread.ofVirtual().name("worker-1").start(() -> handle(r));

A virtual thread costs about a few hundred bytes to kilobytes of heap, not 1 MB of OS stack, so you create one per task and never pool them. They are final in Java 21 (JEP 444). The carriers are a ForkJoinPool sized to the number of cores. They help IO-bound servers (the "thread per request" style scales again without reactive code). They give nothing for CPU-bound work, which is limited by cores. Spring Boot 3.2+ can use them with spring.threads.virtual.enabled=true.

Remember: a cheap thread per task, blocking becomes free for IO. Never pool them. No gain for CPU-bound work.

When should you use virtual threads, and what do you watch out for when moving to them? Senior

Use them when the work is mostly waiting (HTTP calls, database, messaging) and you want simple blocking code with high concurrency. Do not use them for CPU-bound tasks. When migrating, watch four things: pinning, resource limits that the pool used to enforce, ThreadLocal use, and heavy synchronized blocks around IO.

  • Limits move: the pool size used to cap concurrency to your database or a partner API. With one virtual thread per task nothing caps it, so add a Semaphore or a connection pool limit.
  • ThreadLocal: works, but a million virtual threads each with a large thread-local means a million copies. Prefer passing context or ScopedValue (final in Java 25).
  • Pinning: see the next question.
  • Do not pool them and do not use them for long CPU loops: virtual threads are scheduled cooperatively, with no time slicing, so a CPU hog can hold a carrier.
  • Throughput rises only when waiting dominates. A single request is not faster.

Remember: IO-bound yes, CPU-bound no. Replace the pool's cap with a semaphore.

What is virtual thread pinning? Senior

A virtual thread is pinned when it cannot be unmounted from its carrier while blocked, so it holds the OS thread hostage. In Java 21 this happens when it blocks inside a synchronized block or in a native call. If many virtual threads are pinned at once, the few carriers are all stuck and the application stalls.

In Java 21 to 23, the fix was to replace synchronized with ReentrantLock around blocking IO, especially in libraries such as older JDBC drivers. Java 24 (JEP 491) removed the synchronized pinning in most cases; native frames and some class-initialization cases can still pin. To find it, use JFR (the jdk.VirtualThreadPinned event) or the flag -Djdk.tracePinnedThreads on Java 21. If you are stuck on 21, keep critical sections short and do not do IO inside synchronized, which was good advice anyway.

Remember: blocking inside synchronized or native pins the carrier (mostly fixed in Java 24). Use ReentrantLock on 21.

What is structured concurrency, and what is it for? Senior

It treats a group of related subtasks as one unit with a clear lifetime: the code that starts subtasks must also wait for them, in the same scope. If one subtask fails, the others are cancelled, and nothing is left running after the scope ends. It fixes the usual problems of ad-hoc futures: leaked tasks and forgotten error handling.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user  = scope.fork(() -> findUser(id));
    var order = scope.fork(() -> findOrder(id));
    scope.join().throwIfFailed();            // wait, cancel the rest if one fails
    return new Page(user.get(), order.get());
}

Each subtask runs in its own virtual thread. It was a preview API in Java 21, and its API has changed between preview releases and may still be in preview in your JDK, so check before relying on it and do not teach one release's method names as final. The idea is stable and worth knowing: "fan-out and fan-in with cancellation, scoped to a block". Related: ScopedValue is the immutable, inheritable alternative to ThreadLocal (final in Java 25).

Remember: subtasks live and die inside one scope: wait for all, cancel on failure. Preview API, so check your JDK.

Reactive (WebFlux) or virtual threads: how do you choose? Senior

For new IO-heavy services on Java 21+, I start with virtual threads and plain blocking code, because they give most of the scalability with far simpler code, stack traces and debugging. I choose reactive when I need real streaming with back-pressure, event-driven pipelines, or I am already inside a reactive stack.

Reactive code uses few threads and never blocks them, but the programming model is harder: callbacks or operator chains, lost stack traces, context passing through the pipeline, and the risk that one blocking call on an event-loop thread stalls everything. Virtual threads keep the thread-per-request model and let blocking be cheap. Where reactive still wins: streaming data with back-pressure between stages, WebSocket/SSE fan-out, and libraries that are reactive end to end. A mixed system is fine, but never call blocking code from a reactive event-loop thread.

Remember: virtual threads for simple scalable blocking code, reactive when you need streaming and back-pressure.

10. Thread dumps and diagnosing problems

How do you take and read a thread dump to find a hang? Senior

I take three dumps a few seconds apart with jcmd PID Thread.print (or jstack PID, or kill -3), then compare. Threads that sit at the same stack line in all three are the stuck ones. First I look for "Found one Java-level deadlock". If none, I group threads by what they wait on.

  • BLOCKED, "waiting to lock <0x...>": find the thread that has "locked <0x...>" with the same address. If that owner is itself waiting on IO, that is the culprit.
  • WAITING on a pool's queue or a condition: usually idle workers, which is normal. Many threads in getConnection mean the connection pool is exhausted.
  • All request threads in socketRead0: a slow or dead downstream with no timeout.
  • All pool threads in Future.get with a full queue: pool starvation deadlock.
  • RUNNABLE in native read: not necessarily busy; it is waiting on IO.

Name your threads, because "pool-3-thread-7" tells nothing. Save the dumps before any restart.

Remember: three dumps, deadlock section first, then group by what threads wait on. Never restart before saving them.

CPU is at 100%. How do you find the thread and the code responsible? Senior

I find the hot thread with top -H -p PID (per-thread view), convert its thread id to hex, and look for nid=0x... with that value in a thread dump. That shows exactly which code the thread is running. I repeat three times, because one sample can mislead.

top -H -p 4321                      # hot thread id, e.g. 4388
printf '%x\n' 4388                  # 1124
jcmd 4321 Thread.print | grep -A 20 'nid=0x1124'

If the hot threads are named like "GC Thread", the problem is memory pressure, so look at GC logs and the heap instead. If they are application threads, the stack tells the story: a tight loop, a regular expression with catastrophic backtracking, a CAS retry spin, or in old code a HashMap corrupted by concurrent writes. For a more reliable view over time, use a sampling profiler (JFR or async-profiler), as one snapshot can lie.

Remember: top -H, thread id to hex, match nid in the dump, repeat. GC thread means look at memory.

How do you test concurrent code? Senior

I cannot prove the absence of races by testing, so I combine: design that avoids shared state, stress tests that hammer the code from many threads and check an invariant, and tools that find races for me. A passing test only means it did not fail this time.

  • Stress test: start N threads together with a CountDownLatch start gate, run the operation thousands of times, then assert the final state (total count, no lost items).
  • Make it likely to fail: more threads than cores, repeat the test many times, run on a different machine and in CI.
  • Never use Thread.sleep to "wait for the other thread": use latches, futures or Awaitility with a timeout.
  • Tools: jcstress (JMM-level tests by the OpenJDK team), thread-safety annotations and static analysis, and a thread dump or JFR when a test hangs.

Always give every wait in a test a timeout, so a deadlock fails the test instead of hanging the build.

Remember: latch-started stress test plus an invariant check, with timeouts everywhere. No sleeps.

11. Coding questions

Write a producer-consumer with a BlockingQueue. Intermediate

I create one bounded ArrayBlockingQueue, producers call put(), consumers call take(), and the queue does all the waiting. To stop, the producer puts a poison pill (a special end marker) once per consumer.

BlockingQueue<String> q = new ArrayBlockingQueue<>(100);
static final String STOP = "__STOP__";

Runnable producer = () -> {
    try {
        for (String s : source) q.put(s);          // blocks when full
        for (int i = 0; i < CONSUMERS; i++) q.put(STOP);
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};
Runnable consumer = () -> {
    try {
        for (String s; !(s = q.take()).equals(STOP); ) handle(s);   // blocks when empty
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

Why this is right: bounded capacity gives back-pressure, there is no explicit lock or wait/notify, and the pills guarantee every consumer ends exactly once. Without pills, consumers would block on take() forever (a classic "program does not exit" bug).

Remember: bounded queue, put/take, one poison pill per consumer.

Write a bounded buffer yourself with ReentrantLock and Condition. Senior

One lock, two conditions: "notFull" for producers and "notEmpty" for consumers. Each operation takes the lock, waits in a while loop until its condition holds, does the change, and signals the other side.

class BoundedBuffer<T> {
    private final Object[] items; private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();
    BoundedBuffer(int n) { items = new Object[n]; }

    void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();   // loop, not if
            items[tail] = x; tail = (tail + 1) % items.length; count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }
    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[head]; items[head] = null;
            head = (head + 1) % items.length; count--;
            notFull.signal();
            return x;
        } finally { lock.unlock(); }
    }
}

Points to say: await() releases the lock while waiting, the while loop handles spurious wakeups, and separate conditions mean signal() wakes the right kind of thread, so no notifyAll thundering herd. This is nearly what ArrayBlockingQueue does.

Remember: lock, while-loop await, change, signal the other side, unlock in finally.

Print odd and even numbers alternately from two threads. Intermediate

Two threads share one counter and one lock. Each waits (in a loop) until it is its turn, prints, increments and notifies. Using synchronized with wait/notifyAll is the expected answer.

class OddEven {
    private int n = 1; private final int max = 10;
    synchronized void print(boolean odd) throws InterruptedException {
        while (n <= max) {
            while (n <= max && (n % 2 == 1) != odd) wait();   // not my turn
            if (n <= max) { System.out.println(Thread.currentThread().getName() + " " + n++); }
            notifyAll();
        }
    }
}
// new Thread(() -> o.print(true)).start();  new Thread(() -> o.print(false)).start();

Key points: the condition is checked in a while, the exit case (n > max) is handled so the second thread is not left waiting, and it works for any number of threads if you generalize the turn test. A clean alternative is two Semaphores passing a baton: odd releases even, even releases odd.

Remember: shared counter, wait until it is my turn, print, notifyAll. Don't forget the exit condition.

Make three threads run in a fixed order: T1, then T2, then T3. Intermediate

The simplest way is join(): T2 starts only after T1 has finished, and so on. If the threads must run side by side but their critical steps happen in order, I use a CountDownLatch per hand-off, or CompletableFuture.thenRun.

CountDownLatch l1 = new CountDownLatch(1), l2 = new CountDownLatch(1);
Thread t1 = new Thread(() -> { step("T1"); l1.countDown(); });
Thread t2 = new Thread(() -> { await(l1); step("T2"); l2.countDown(); });
Thread t3 = new Thread(() -> { await(l2); step("T3"); });
t3.start(); t2.start(); t1.start();      // start order does not matter

// or with futures
CompletableFuture.runAsync(() -> step("T1"))
    .thenRun(() -> step("T2")).thenRun(() -> step("T3"));

The latch also gives a happens-before edge, so T2 sees T1's writes. Note that start() order never decides execution order; only synchronization does.

Remember: start order means nothing. Order comes from join, latches or chained futures.

Implement a simple thread-safe rate limiter. Senior

I would write a token bucket: it holds up to N tokens, refills at a fixed rate, and each request takes one token or is refused. It handles bursts up to N and a steady average rate, and the state update is a small critical section.

class TokenBucket {
    private final long capacity; private final double refillPerNano;
    private double tokens; private long last = System.nanoTime();
    TokenBucket(long capacity, double perSecond) {
        this.capacity = capacity; this.tokens = capacity; this.refillPerNano = perSecond / 1e9;
    }
    synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - last) * refillPerNano);
        last = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;                      // caller can reject (HTTP 429) or retry later
    }
}

It uses the monotonic System.nanoTime(), not wall-clock time, which can jump. The lock is held for a few arithmetic operations, so contention is low. For a high-volume path, I would use an existing library (Guava RateLimiter, Resilience4j) or do the check at an API gateway or in Redis when the limit must hold across many instances, since a JVM-local limiter only limits one instance. A semaphore limits concurrency (how many at once), a token bucket limits rate (how many per second).

Remember: token bucket = refill by elapsed time, take one token, else reject. A JVM limiter covers only one instance.

12. Real-life scenarios

Every answer follows the same shape: the diagnosis in one sentence, then the situation, what to check first, the fix, and how to prevent it. Say this shape aloud in the interview; it shows you work calmly under pressure.

The application stops responding. CPU is near zero, requests time out. What do you do? Senior

Near-zero CPU means threads are waiting, not computing: a deadlock, an exhausted pool, or everyone waiting on a dead dependency. I do not restart first. I take three thread dumps, find what the threads wait on, restore service, then fix the root cause.

Situation: health checks fail, but the process is alive and idle.

Check first: three dumps ten seconds apart (jcmd PID Thread.print), plus connection-pool and GC logs. A restart destroys the evidence.

Fix:

  1. Search the dump for "Found one Java-level deadlock": it gives threads, locks and lines.
  2. Otherwise group by top frame. All HTTP workers in a socket read: a slow dependency. All in getConnection: the DB pool is exhausted. All BLOCKED on one monitor: contention, often IO inside synchronized.
  3. Restore service (restart or fail over after saving the dumps), then fix: lock order, timeouts, pool sizes.

Prevent: timeouts on every remote call, circuit breakers, an alert on findDeadlockedThreads, named threads, metrics for pool usage and queue length.

Remember: idle CPU plus hang = take dumps first, then read what threads wait on.

CPU is at 100% on one production instance after a release. How do you find the cause? Senior

I check whether the busy threads are GC or application threads with top -H, map the hottest thread id to a thread dump line, and roll back if the release is clearly the trigger. Analysis then continues on a canary or in staging.

Situation: the spike started with a release, maybe on all instances.

Check first: GC or user code? Hot threads named "GC Thread" mean memory pressure (look at heap and GC logs).

top -H -p 4321                 # hot thread id, e.g. 4388
printf '%x\n' 4388             # 1124
jcmd 4321 Thread.print | grep -A 20 'nid=0x1124'

Fix: repeat three times. A stack stuck in the same loop, a regex, an unsynchronized HashMap spin or a CAS retry loop identifies the cause. If the release is the obvious trigger, roll back first, then profile with JFR or async-profiler.

Prevent: load tests in the pipeline, canary releases, per-instance CPU alerts, review of loops without an exit and of plain collections shared between threads.

Remember: hot thread id to hex to dump line. Roll back first when the release is the clear cause.

Every request thread is busy and the service returns 503, but the database looks fine. What happened? Senior

A downstream call became slow with no short timeout, so every worker thread sits waiting on it and the pool is exhausted. I confirm with a thread dump, add timeouts and a circuit breaker, and isolate that dependency with its own bounded pool (a bulkhead).

Situation: Tomcat's worker pool (200 threads by default) is full, new requests wait in the accept queue and time out. CPU is low.

Check first: thread dump. Most workers are in a socket read or HTTP client call to one service that now takes 30 s instead of 200 ms. By Little's law (concurrency = rate x latency), 200 threads at 30 s each serve only about 7 requests per second.

Fix: short connect and read timeouts, a circuit breaker so threads are released at once, and a separate bounded pool or semaphore for that dependency so it cannot take all request threads. Return a fallback or cached answer.

Prevent: timeouts on every client (never infinite), a bulkhead per dependency, alerts on active threads and downstream p99. With virtual threads, the thread limit disappears, so a semaphore bulkhead becomes essential.

Remember: slow dependency plus no timeout equals exhausted pool. Timeout, breaker, bulkhead.

Inventory or counters are slightly wrong under load: updates are lost. Find and fix it. Intermediate

This is a read-modify-write race: two requests read the same old value and both write back. I find the ++, += or "read, compute, put" sequence and make it atomic: an atomic class or lock in one JVM, a single SQL statement or a version column across instances.

Situation: stock goes below zero, or a counter shows 9,870 after 10,000 increments. It never reproduces on a laptop.

Check first: is the state in one JVM (a lock or atomic fixes it) or in a database or several instances (a JVM lock is useless)?

Fix: in process: AtomicInteger, LongAdder for stats, map.merge(k, 1, Integer::sum), or one lock around the whole sequence. In the database: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0 and check the updated row count, or optimistic locking with a version column and retry, or SELECT ... FOR UPDATE.

Prevent: a test that hammers the operation from many threads and checks the final total; avoid read-then-write in application code when the store can do it atomically.

Remember: JVM lock for one process, database atomicity for many instances.

Memory grows after every redeploy, and users sometimes see another user's data. Suspect ThreadLocal. Senior

A ThreadLocal is set on pooled threads and never removed. The pooled thread keeps the value (and its class loader) alive, and the next request on that thread reads the previous user's value. The fix is set and remove in the same try/finally, usually in a filter.

Situation: (a) Metaspace or heap grows on each hot redeploy on a shared Tomcat until OutOfMemoryError. (b) A request occasionally shows the previous request's user or tenant, which is a security bug.

Check first: heap dump (jcmd PID GC.heap_dump), then in Eclipse MAT look at the path to the old class loader: thread, ThreadLocalMap, entry value. Search for ThreadLocal.set with no remove.

Fix: wrap the request (servlet filter, interceptor or task decorator) in try/finally with remove(). For async tasks, pass context explicitly. Tomcat logs "created a ThreadLocal ... but failed to remove it" on stop, which is a hint.

Prevent: a code rule that thread-locals are always cleared in finally, and a test that runs two requests on the same thread.

Remember: pooled thread plus ThreadLocal without remove = leak and data bleed.

Two services update the same two database rows in opposite order and requests hang or fail with lock timeouts. Senior

It is a deadlock in the database, the same lock-ordering problem as in Java. The fix is to always touch rows in one consistent order (for example by primary key) and keep transactions short.

Situation: service A updates account 1 then 2, service B updates 2 then 1, each inside a transaction. Each holds one row lock and waits for the other. The database picks a victim (deadlock error) or the waits hit a lock timeout.

Check first: the database's deadlock log shows the two statements and rows. Check which code paths take multiple row locks.

Fix: sort the ids and lock in ascending order, or lock both rows in one statement (SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE). Retry the transaction on a deadlock error, which is the expected, designed-for failure. Shrink transactions and never call remote services inside one.

Prevent: a team rule for lock order, optimistic locking where conflicts are rare, and retry logic with a limit and jitter.

Remember: same order everywhere, short transactions, retry on deadlock.

An unrelated endpoint became slow after another team added a parallelStream() with an HTTP call inside. Senior

Parallel streams and default CompletableFuture stages share one common ForkJoinPool with only about cores minus 1 threads. Blocking calls inside it starve everything else that uses the pool. I move the blocking work to a dedicated executor.

Situation: latency rises in code that does not even call the new feature.

Check first: a thread dump shows all ForkJoinPool.commonPool-worker-N threads in a socket read, and other tasks waiting.

Fix: replace parallelStream() with a CompletableFuture per item on a bounded IO executor (or virtual threads on Java 21), with timeouts. Keep parallel streams for CPU-only work.

Prevent: a code-review rule: no blocking IO in parallel streams or in async stages on the default pool. Metrics for the common pool's queue.

Remember: the common pool is shared by the whole JVM. Never block it.

The service runs out of memory, and the heap dump is full of queued tasks from an executor. What is the cause? Senior

An unbounded executor queue (typically newFixedThreadPool) with producers faster than consumers: tasks pile up on the heap. I bound the queue, choose a rejection policy that pushes back, and fix the slow consumer.

Situation: heap grows steadily, old GC runs constantly, finally OutOfMemoryError. The dump shows millions of Runnable or FutureTask objects inside a LinkedBlockingQueue.

Check first: the pool's queue size and active count metrics, and downstream latency (a slow consumer is often the real trigger).

Fix: build the ThreadPoolExecutor with an ArrayBlockingQueue and CallerRunsPolicy or an abort that returns "busy". Add a timeout to the slow call. A related variant: newCachedThreadPool instead creates thousands of threads and fails with "unable to create native thread".

Prevent: ban the Executors factories in code review, export queue size and rejected-count metrics, and alert on them.

Remember: an unbounded queue is a hidden memory leak. Bound it and decide what happens when it is full.

A cache built on a plain HashMap sometimes loses entries, throws odd exceptions or spins at 100% CPU. Intermediate

A HashMap is not thread-safe. Concurrent put calls can lose entries or corrupt its structure, and during a resize an old Java 7 map could even form a cycle and make get loop forever. I replace it with ConcurrentHashMap and use atomic methods such as computeIfAbsent.

Check first: is that map shared between threads (a static field, a singleton bean)? A thread dump of a spinning thread inside HashMap.get or put confirms it.

Fix: ConcurrentHashMap and computeIfAbsent(key, loader) so that one thread loads each missing value. For a real cache with size limits and expiry use Caffeine, not a hand-made map.

Prevent: make shared collections obviously concurrent by type, and never keep per-request data in singleton fields.

Remember: shared plus mutable plus HashMap = bug. Use ConcurrentHashMap or Caffeine.

A scheduled job ran fine for weeks, then silently stopped. No error in the logs. Intermediate

With ScheduledExecutorService, an exception thrown by a periodic task cancels all further runs, and the exception is kept in the returned future, so nothing is logged. I wrap the task body in try/catch and log.

Check first: is the job registered with scheduleAtFixedRate or scheduleWithFixedDelay, and is the returned ScheduledFuture ignored? Calling get() on it would show the stored exception. Also check whether another long job blocks the single scheduler thread.

Fix: catch Throwable inside the task, log it, and let the next run proceed. Use more than one scheduler thread if jobs can run long. In Spring @Scheduled an exception is logged and the schedule continues, but the default is a single scheduler thread.

Prevent: a "last successful run" metric with an alert, so silence becomes visible.

Remember: an uncaught exception ends a periodic task. Catch inside, and alert on missing runs.

The process does not exit after main finishes, or does not stop on shutdown. Why? Intermediate

The JVM exits only when all non-daemon threads have ended. A thread pool that was never shut down, a consumer blocked in take(), or a timer thread keeps it alive. I find the live non-daemon threads in a dump and shut down their owners.

Check first: a thread dump lists threads; the ones without "daemon" in their header (for example "pool-1-thread-1") are the cause.

Fix: call shutdown() then awaitTermination() on executors, send poison pills or interrupt consumers, and register a shutdown hook for orderly cleanup. Marking pool threads as daemon is a last resort, because daemons can be killed in the middle of work.

Prevent: give every executor one owner with a close or stop method, and use try-with-resources on ExecutorService (Java 19+).

Remember: JVM waits for non-daemon threads. Find them in a dump and shut down their owner.

After switching a service to virtual threads, it works in tests but freezes under load. What do you check? Senior

I check for pinned virtual threads and for missing limits. On Java 21 a virtual thread that blocks inside synchronized pins its carrier; with many such threads all carriers stall. Also the old pool size no longer limits calls to the database or a partner API.

Check first: JFR event jdk.VirtualThreadPinned (or -Djdk.tracePinnedThreads=full on Java 21), and a thread dump with jcmd PID Thread.dump_to_file -format=json file, which includes virtual threads. Look at the database connection pool: thousands of virtual threads waiting for a few connections is expected, but a timeout storm is not.

Fix: replace synchronized around blocking IO with ReentrantLock (or upgrade to Java 24+ where this pinning is mostly gone), upgrade old drivers, and add a Semaphore bulkhead per downstream. Do not pool virtual threads.

Prevent: load test before the switch, and alert on pinned events and connection wait time.

Remember: pinned carriers and missing limits. Lock instead of synchronized on 21, semaphore for caps.

Closing line for an interview: "I first try not to share mutable state at all: immutable objects, confinement and queues. When I must share, I name the exact lock or atomic that guards each field, keep critical sections short, and put timeouts on every wait. I use bounded pools with named threads, and on Java 21 I use virtual threads for blocking IO with a semaphore as the limiter. When things go wrong, I take thread dumps before I restart."
Trap to avoid: saying "volatile makes it thread-safe" or "ConcurrentHashMap makes my code thread-safe". Volatile gives visibility only, and thread-safe parts do not make a thread-safe sequence: a check-then-act across two calls is still a race.
