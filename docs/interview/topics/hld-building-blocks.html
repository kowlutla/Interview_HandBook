HLD: Algorithms and Building Blocks interview questions

The data structures and algorithms that system design answers rest on: consistent and rendezvous hashing, Bloom filters, HyperLogLog, Count-Min Sketch, LSM trees and B-trees, tries and inverted indexes, geo indexes, Merkle trees and gossip, rate limiting algorithms, ID generation, load balancing, cache eviction, encodings, consensus-adjacent mechanics (leader election, failure detectors, WAL, 2PC, vector clocks, CRDTs), scheduling and ranking basics.

How to use this page

Each question is a collapsible. Try to answer aloud first, then open it. This page has no full system designs. It covers the algorithms underneath them. For each building block, be ready to say four things: what it is, why you would use it (with a concrete number or example), how it works in a few sentences, and what it costs. Interviewers at senior level care most about the trade-offs and the failure modes, so read the "Trap" boxes.

Hashing and partitioning

Why does hash(key) % N break when you add or remove a server? Basic

With modulo placement, a key lives on server hash(key) mod N. When N changes from 4 to 5, almost every key maps to a different server. Only about 1 in 5 keys keep their old home. For a cache that means roughly 80 percent of keys miss at once, and the misses stampede the database. For a sharded store it means moving most of the data.

Consistent hashing (next question) fixes this: adding a node moves only about 1/N of the keys.

What is consistent hashing and how does it work? Basic

Hash both keys and servers onto the same circular space (for example 0 to 2^32 - 1). A key is stored on the first server found moving clockwise from the key's position. When a server is added, it takes over only the keys between itself and its predecessor on the ring. When it is removed, only its keys move to its successor. On average only K/N keys move (K keys, N servers).

Implementation: keep a sorted array or tree of node positions, binary search for the key hash (O(log N)). Used by Dynamo, Cassandra, memcached client libraries (ketama), and CDN request routing.

What are virtual nodes and why are they needed? Intermediate

With one point per server, ring arcs are uneven. With 3 servers, one may own 50 percent of the keys and another 15 percent. Also, when a server dies, all its load falls on one neighbour, which may then fail too (a cascade).

Virtual nodes give each physical server many positions on the ring (often 100 to 256, Cassandra historically defaulted to 256 and later lowered it). Benefits:

  • Load evens out statistically (variance falls roughly with the square root of the number of vnodes).
  • A dead server's load spreads over many survivors.
  • Heterogeneous hardware: give a bigger machine more vnodes.
  • A new node streams small pieces from many peers in parallel.

Costs: bigger routing metadata, and more ranges to repair or stream (with many vnodes, repair and replica-set coverage get more complex).

How does consistent hashing handle replication and hot keys? Intermediate

For replication factor 3, store the key on the first node clockwise plus the next two distinct physical nodes (skip vnodes of the same machine, ideally also skip the same rack or zone). That list is the "preference list" in Dynamo.

Consistent hashing does not fix hot keys. One celebrity key still lands on one node set. Mitigations: key splitting (append a random suffix 0..9 and read all 10), a local in-process cache in front, or replicating the hot key to more nodes.

What is rendezvous (highest random weight) hashing and when is it better than a ring? Intermediate

For each key, compute score(key, node) = hash(key, node) for every node and pick the node with the highest score. If you need R replicas, take the top R. Removing a node only reassigns keys that had it as the winner, so movement is minimal, same as the ring.

Ring + vnodesRendezvous
Lookup costO(log N) binary searchO(N) hashes per key
StateSorted ring of vnodesJust the node list
BalanceNeeds many vnodesNaturally uniform
Weighted nodesMore vnodesWeighted score formula

Pick rendezvous for small to medium node sets (tens to a few hundred) where simplicity and uniformity matter, such as picking a cache or an upstream per request. Pick a ring when N is large and lookups are hot. Jump consistent hash (Google) is another option: O(log N) time, no memory, but nodes must be numbered 0..N-1 and you can only add or remove at the end.

Trap: Sharding by timestamp or by an auto-increment id with range sharding sends all writes to the last shard.

Probabilistic data structures

What is a Bloom filter and why use one? Give an example. Basic

A Bloom filter is a bit array of m bits plus k hash functions. To add an item, set the k bits its hashes point to. To query, check those k bits: if any is 0, the item is definitely not in the set. If all are 1, it is probably in the set. No false negatives, some false positives, and you cannot delete or list items.

Example: an LSM database (Cassandra, HBase, RocksDB) keeps a Bloom filter per SSTable. A read for a missing key would otherwise touch several files on disk. The filter lets it skip nearly all of them in memory. Another: Chrome-style "is this URL possibly malicious" prechecks, or a crawler checking "have I seen this URL" without storing all URLs.

How do you size a Bloom filter? What is the false-positive rate? Intermediate

For n items, m bits and k hashes, the false-positive rate is about (1 - e^(-kn/m))^k. The best k is (m/n) * ln 2. Rules of thumb:

Target FP rateBits per itemHash functions
1%about 9.6about 7
0.1%about 14.4about 10

Example: 100 million URLs at 1 percent needs about 960 million bits, around 120 MB. Storing the URLs themselves would take many GB. If you add more than n items the FP rate climbs fast, so size for peak or use a scalable Bloom filter (a chain of filters).

Trap: Saying "Bloom filters have false negatives when full". They do not. A full filter just says "probably yes" to everything.
What is a counting Bloom filter and what are the alternatives for deletion? Intermediate

Replace each bit with a small counter (usually 4 bits). Add increments the k counters, delete decrements them, query checks all are non-zero. It supports deletes at about 4 times the memory. Counter overflow is a risk (saturate and never decrement a saturated counter).

Alternatives: a Cuckoo filter (stores short fingerprints, supports delete, often better space at low FP rates), or periodically rebuilding a plain filter from the source of truth, which is what most LSM stores effectively do since SSTables are immutable.

What is HyperLogLog and what problem does it solve? Intermediate

It estimates the number of distinct elements (cardinality) in a stream using a tiny, fixed amount of memory. Idea: hash each item to a uniform bit string. The longer the run of leading zeros seen, the rarer the event, so the more distinct items you probably saw (seeing a hash with 20 leading zeros suggests about 2^20 items). To cut variance, split items into m buckets by the first bits, keep the max leading-zero count per bucket, and combine with a harmonic mean.

  • Redis PFADD / PFCOUNT uses about 12 KB per key and gives about 0.81 percent standard error, for sets of billions.
  • Sketches are mergeable (take the per-bucket max), so you can count unique visitors per hour and union hours or shards into a day with no double counting.
  • Limits: it only counts, it cannot tell you whether an item is present, and it cannot delete. The result is approximate.

Example: unique daily viewers per video for 100 million videos. Exact sets are impossible; 12 KB sketches fit.

What is a Count-Min Sketch? What are its error properties? Intermediate

A 2D array of counters, d rows by w columns, with one hash function per row. Update: for each row, increment counter[row][hash_row(item)]. Estimate: take the minimum across the d rows. Collisions can only inflate counters, so the estimate never under-counts, it may over-count. With width w = e/epsilon and depth d = ln(1/delta), the overcount is at most epsilon times the total stream size with probability 1 - delta.

Use it for frequency estimates over huge key spaces where a hash map will not fit, such as per-IP request counts, or as the admission filter in TinyLFU. It is weak for low-frequency items (error is relative to the total), good for heavy ones.

How do you find the top K most frequent items in a stream (heavy hitters)? Intermediate
  1. Exact, small key space: hash map of counts plus a min-heap of size K. O(n log K).
  2. Big key space, one machine: Count-Min Sketch for counts plus a size-K min-heap of candidates. On each item, update the sketch, read the estimate, and push into the heap if it beats the smallest.
  3. Space-Saving / Misra-Gries: keep only m counters. When a new item arrives and no slot is free, evict the item with the lowest count and give the newcomer count+1. Guarantees any item with frequency above n/m is retained.
  4. Distributed: each shard keeps local top-K (or a sketch), a merger combines. Caveat: global top-K can include an item that is not top-K on any single shard, so take local top-K' with K' larger than K, or merge sketches (they are additive) and then rank.
  5. Time windows: one sketch per minute bucket and sum the last N, or use decaying counts.

Example: trending hashtags in the last hour.

What sampling techniques come up in system design, and when are they used? Intermediate
  • Reservoir sampling: pick k items uniformly from a stream of unknown length in one pass. Keep the first k; for item number i (i greater than k), pick random j in 1..i and if j is at most k replace slot j. Used for uniform samples of logs or events.
  • Head-based trace sampling: decide at the start of a request (say 1 percent) and propagate the decision. Cheap, but you may miss rare errors.
  • Tail-based sampling: buffer whole traces and keep slow or failed ones. Better signal, higher cost.
  • Deterministic hash sampling: keep an item if hash(id) mod 100 < 5. All services agree on the same 5 percent without coordination, so joins across datasets still work.
  • Stratified sampling: sample per segment so small segments are not lost.
Trap: Sampling rates must be recorded, or counts computed from samples cannot be scaled back up.

Storage engine structures

What is an LSM tree? Explain memtable, WAL, SSTable and compaction. Intermediate

A Log-Structured Merge tree turns random writes into sequential ones.

  1. Write: append to the write-ahead log (WAL) on disk for durability, then insert into an in-memory sorted structure, the memtable (often a skip list).
  2. Flush: when the memtable is full (say 64 MB), write it out as an immutable, sorted file, an SSTable (Sorted String Table), with an index and usually a Bloom filter. Then the WAL segment can be dropped.
  3. Read: check memtable, then SSTables from newest to oldest. Bloom filters and block indexes skip most files.
  4. Compaction: background merge of SSTables to drop overwritten values and tombstones (delete markers) and to bound the number of files to check.

Used by Cassandra, HBase, RocksDB, LevelDB, ScyllaDB, and as the engine under many systems (CockroachDB uses Pebble, a RocksDB-like engine).

Compare size-tiered and leveled compaction. What is write amplification? Senior

Write amplification = bytes physically written to disk divided by bytes the app wrote. Leveled compaction can reach 10 to 30x. This matters for SSD wear and for throughput. Also mention time-window compaction for TTL or time-series data: whole old files are dropped without merging.

Trap: Compaction is background IO. If the app writes faster than compaction can keep up, files pile up, reads slow and the engine eventually stalls writes (RocksDB write stalls). Watch pending-compaction metrics.

Say: For a write-heavy ingest path such as metrics, events or messaging with mostly key lookups, I pick an LSM engine. For OLTP with many range scans, secondary indexes and strict latency, a B-tree engine is the safer default.
What is a skip list and why do systems like Redis and LevelDB use it? Intermediate

A skip list is a sorted linked list with extra "express lane" levels. Each node is promoted to the next level with probability 1/2 (or 1/4), so level 1 has about half the nodes, level 2 a quarter, and so on. Search starts at the top level, moves right while the next key is smaller, then drops down. Expected O(log n) for search, insert and delete, with no rebalancing.

Why use it instead of a balanced tree: much simpler code, and it is friendlier to concurrency, because an insert only changes a few local pointers (lock-free variants exist, such as Java's ConcurrentSkipListMap). Redis sorted sets (ZSET) combine a skip list with a hash table: the skip list gives rank and range queries (ZRANGEBYSCORE, ZRANK), and the hash gives O(1) score lookup. Memtables in LevelDB, RocksDB and HBase use skip lists. Cost: more pointers per node, poorer cache locality than arrays.

What is a write-ahead log and what guarantees does it give? Basic

Rule: record the intended change in an append-only log and make it durable (fsync) before applying it to the main data structure. After a crash, replay the log to redo committed changes (and undo incomplete ones in ACID databases). It converts random writes into one sequential append, which is fast, and gives atomicity and durability.

  • Used by Postgres (WAL), MySQL InnoDB (redo log), LSM stores (commit log), Kafka (the log is the data), Raft (replicated log), etcd.
  • The same log can feed replication (streaming replicas, CDC).
  • Cost and knob: fsync per commit is slow (about 1 ms on SSD, more on disk), so systems group-commit (batch many commits into one fsync) or let you relax durability (innodb_flush_log_at_trx_commit, synchronous_commit).
Trap: A write acknowledged after the OS page cache but before fsync can be lost on power failure. Say which one you mean.
What is checkpointing and why is it needed alongside a log? Intermediate

A log grows forever and replaying it from the beginning takes too long. A checkpoint is a snapshot of state at a known log position (an LSN or offset). Recovery loads the latest checkpoint and replays only the log after it; older log segments can be deleted.

  • Databases: flush dirty pages and record the checkpoint LSN. Postgres checkpoints bound recovery time.
  • Raft: snapshot the state machine and truncate the log up to the snapshot index.
  • Stream processors (Flink): periodic distributed snapshots plus source offsets, so restart gives exactly-once state.
  • Kafka consumers: committed offsets are a form of checkpoint.

Trade-off: frequent checkpoints shorten recovery but cost IO; infrequent ones make recovery slow.

What is a consistent snapshot and how is one taken in a distributed system? Senior

A consistent snapshot is a global state that could have actually existed: if the snapshot includes the receipt of a message it must also include its send. Taking naive per-node copies at slightly different times breaks this (money counted twice or lost).

  • Chandy-Lamport: an initiator records its state and sends a marker on every outgoing channel. A node that receives its first marker records its state, marks that channel empty and sends markers on its outgoing channels; it then records messages that arrive on other channels until each also delivers a marker. Flink's checkpoint barriers are this idea.
  • MVCC / timestamps: read as of a timestamp T; every node returns the versions valid at T. Spanner uses TrueTime to pick globally ordered T.
  • Copy-on-write storage snapshots (LVM, EBS, ZFS) for a single volume: instant, but crash-consistent only unless the app quiesces.

Indexes and search structures

What is a trie and where is it used in system design? Basic

A trie (prefix tree) stores strings character by character; each node is a prefix and each path from the root spells a key. Lookup of a string of length L costs O(L) regardless of how many strings are stored. All strings with a prefix sit in one subtree.

Use: autocomplete / typeahead (walk to the prefix node, then return the best completions), spell correction, IP routing tables (longest prefix match with a binary trie), dictionary lookup.

Typeahead trick: store at each node the top-N completions by score precomputed, so a query is O(L) with no subtree walk. Memory is the cost; compress with a radix tree (merge single-child chains) or use a DAWG/FST (Lucene uses FSTs for its term dictionary). For huge scale, shard by first 1 to 2 characters or by hash of prefix, and rebuild offline from query logs periodically.

What is an inverted index and how does a search query use it? Basic

A forward index maps document to its words. An inverted index maps each term to a sorted postings list of document ids (optionally with term frequency and positions).

doc1: "red fast car"      red  -> [1, 3]
doc2: "blue car"          fast -> [1]
doc3: "red bike"          car  -> [1, 2]
                          blue -> [2]

Query "red car": look up both lists and intersect: [1,3] AND [1,2] gives [1]. Sorted lists are intersected by merging in linear time, with skip pointers for speed. OR is a union; phrase queries use positions.

Pipeline: tokenise, lowercase, remove stop words, stem, then index. Real engines (Lucene, so Elasticsearch and Solr) write immutable segments that are merged in the background, much like an LSM tree, so new documents are searchable after a refresh interval (about 1 second in Elasticsearch) rather than instantly. Sharding: a document is stored in one shard (doc-partitioned), so a query fans out to all shards and merges the top results.

How does search ranking work at a conceptual level (TF-IDF, BM25, signals)? Intermediate
  • TF-IDF: a term counts more if it appears often in the doc (term frequency) and is rare across the corpus (inverse document frequency). "the" scores near zero; "kubernetes" scores high.
  • BM25 (default in Lucene and Elasticsearch): TF-IDF with saturation (the 10th occurrence adds less than the 2nd) and document length normalisation (a short doc that matches beats a long one).
  • Link and quality signals: PageRank-style authority, freshness, click-through rate, personalisation, location.
  • Learning to rank: a model re-scores the top few hundred candidates using many features.

Typical architecture is two stages: cheap retrieval (inverted index, or vector nearest-neighbour search for semantic matches) to get hundreds or thousands of candidates, then an expensive ranker on those only. Evaluate with precision/recall, NDCG, and online A/B tests.

Local versus global secondary indexes in a sharded store: what is the trade-off? Senior
  • Local (document-partitioned): each shard indexes only its own rows. Writes are cheap and atomic with the row. A query on the indexed field must scatter to all shards and gather (tail latency grows with shard count). Used by Cassandra secondary indexes, Elasticsearch, MongoDB.
  • Global (term-partitioned): the index itself is sharded by the indexed value. A query hits one index shard. But a write now touches the data shard and one or more index shards, so you need a distributed transaction or accept eventual consistency (DynamoDB global secondary indexes are asynchronously updated).

Geospatial indexes

How does geohash work and what are its weaknesses? Intermediate

Geohash repeatedly halves the longitude and latitude ranges, interleaving the resulting bits, then encodes them in base32. The result is a short string naming a rectangular cell. Longer string means smaller cell (5 characters is about 5 km by 5 km, 6 is about 1.2 km by 0.6 km, 7 about 150 m).

  • Strength: a shared prefix means nearby, so a normal B-tree or string index on the hash supports "find places in this cell" as a prefix query. Simple to build in any database or Redis (GEOADD uses a geohash-derived score in a sorted set).
  • Weakness 1: two points close together can sit across a cell boundary with totally different prefixes. So nearby search queries the cell plus its 8 neighbours, then filters by real distance.
  • Weakness 2: fixed-size cells: dense cities have huge cells' worth of points while the ocean is empty; cells are distorted near the poles.
How does a quadtree work and when do you prefer it over geohash? Intermediate

A quadtree recursively splits a square region into four quadrants. A leaf holds at most a threshold number of points (say 100). When a leaf overflows, it splits into four children. Dense areas become deep; empty ones stay as one big node. Nearby search: descend to the leaf for the point, then check neighbouring leaves within the radius.

GeohashQuadtree
StructureFixed grid, stored as strings in any indexAdaptive tree, usually in memory
Dense areasCells overloadedSplits automatically
UpdatesTrivial (change a key)Move between leaves, rebalance
DistributionEasy to shard by prefixHarder; each server holds a tree built from a region

Use geohash for a simple, database-friendly, frequently updated moving objects; quadtree when density varies hugely and the data is mostly static (points of interest).

What are S2 / H3 cells and what is an R-tree? Senior

S2 (Google): projects the sphere onto the six faces of a cube and orders cells along a Hilbert curve, giving a 64-bit cell id per level (levels 0 to 30). Hilbert ordering keeps nearby cells close in id space better than geohash's Z-order, and the sphere handling avoids polar distortion. A region is covered by a small set of cell id ranges. Used in Google Maps, MongoDB 2dsphere indexes, Foursquare. H3 (Uber) uses hexagons, which have equal distance to all neighbours, which makes "ring around a cell" queries and surge-pricing smoothing cleaner.

R-tree: a balanced tree where each node stores the minimum bounding rectangle (MBR) of its children. Leaves hold object rectangles. A query descends only into children whose MBR overlaps the query box. Good for rectangles, polygons and ranges (PostGIS GiST indexes, SQLite R*Tree). MBRs of siblings can overlap, so a query may follow several branches.

Replication and convergence building blocks

What is a Merkle tree and how is it used for anti-entropy? Intermediate

A Merkle tree is a hash tree: leaves are hashes of data blocks (or key ranges), and each parent is the hash of its children. The root hash summarises everything. If two replicas have the same root hash, their data is identical.

Anti-entropy is the background process that repairs replica drift. Two replicas exchange root hashes; if they differ, they compare children, descend only into mismatching subtrees, and finally transfer just the differing key ranges. Cost is proportional to the number of differences, not the data size. Dynamo and Cassandra (nodetool repair) do this per key range. Also used in Git, Bitcoin, and certificate transparency logs (for inclusion proofs of O(log n) size).

Trap: Building the tree means reading all data in the range (an IO heavy scan), so repair is scheduled and throttled. And it detects only differences, it does not decide which version wins; use timestamps or vector clocks for that.
What is gossip (epidemic) protocol and why use it? Intermediate

Every T seconds (say 1), each node picks a few random peers and exchanges what it knows (membership, heartbeat counters, schema versions). Information spreads like an epidemic: the number of informed nodes roughly doubles per round, so a cluster of N nodes converges in about O(log N) rounds. A 1000-node cluster needs on the order of 10 to 15 rounds.

  • Pros: no central coordinator, bounded per-node load, tolerant of node failures and message loss, scales to thousands of nodes.
  • Cons: eventual, not instant; duplicate messages; convergence time is probabilistic; hard to reason about exact ordering.
  • Used by: Cassandra and Dynamo membership and failure info, Consul and Serf (SWIM), Redis Cluster bus, aggregating metrics.
What is a vector clock and how does it detect conflicts? Senior

Wall clocks cannot order events across machines reliably. A vector clock is a map {nodeId: counter} attached to each version. A node increments its own counter on each write, and on receiving a message takes the element-wise max of its clock and the incoming one.

Compare clocks A and B: if every counter in A is less than or equal to B (and one is smaller), A happened-before B and B can overwrite A. If neither dominates, the writes are concurrent: a real conflict.

Start:        X = {A:1}
Client 1 via node A: write -> {A:2}
Client 2 via node B (from {A:1}): write -> {A:1, B:1}
Compare {A:2} and {A:1,B:1}: neither dominates -> conflict, keep both siblings

Resolution is up to the app (merge, e.g. union shopping carts, as in the Dynamo paper) or the system (last-write-wins, which silently drops data). Cost: clock size grows with the number of writers; systems prune old entries (Dynamo) or use dotted version vectors (Riak). Lamport clocks are simpler (one counter) but give only a total order consistent with causality, they cannot detect concurrency.

What goes wrong with last-write-wins? Intermediate

LWW picks the version with the highest timestamp. Problems: clock skew between nodes means the "later" write may actually be older, so a newer update is silently lost; two concurrent updates to different fields of one record overwrite each other wholesale; and no error is ever surfaced. Cassandra uses LWW per column, which narrows the damage but does not remove skew issues. Mitigations: NTP discipline, hybrid logical clocks, conditional writes (compare-and-set / lightweight transactions), vector clocks, or CRDTs.

What is a CRDT and what are the common building blocks? Senior

A Conflict-free Replicated Data Type is a data structure whose merge operation is commutative, associative and idempotent, so replicas that have received the same updates (in any order, with duplicates) converge to the same state without coordination. Two styles: state-based (ship state, merge with a join) and operation-based (ship ops, need reliable causal delivery).

Used by Riak data types, Redis Enterprise active-active, collaborative editors, offline-first apps. Trade-offs: metadata growth (tombstones, per-node slots), and not every invariant can be expressed (for example "balance never below zero" needs coordination).

Rate limiting algorithms

Explain the token bucket algorithm. Basic

A bucket holds up to B tokens and refills at R tokens per second. Each request removes a token; if the bucket is empty the request is rejected (or delayed). So the long-term rate is R, and bursts up to B are allowed.

Lazy implementation needs only two numbers per key, tokens and lastRefill:

now = clock()
tokens = min(B, tokens + (now - lastRefill) * R)
lastRefill = now
if tokens >= 1: tokens -= 1; allow
else: reject

Pros: memory-cheap, allows bursts, easy to explain (used by AWS API Gateway, Stripe, many gateways). Cons: the burst can overload a fragile backend; two parameters to tune.

What is the leaky bucket and how does it differ from the token bucket? Basic

Requests enter a fixed-size queue and are drained at a constant rate. If the queue is full, new requests are dropped. The output is smooth, so it shapes traffic for backends that need steady load (and is the idea behind network traffic shaping).

What is the fixed window counter and what is its flaw? Basic

Count requests per key in each fixed time slot, for example INCR user:42:2026-11-17T10:05 with a 60-second TTL; reject above the limit (say 100 per minute). Extremely cheap: one counter per key per window.

Flaw: boundary bursts. A client sends 100 requests at 10:05:59 and 100 more at 10:06:00. Both windows are within the limit, yet 200 requests arrived in about 2 seconds, twice the intended rate.

Compare sliding window log and sliding window counter. Intermediate
  • Sliding window log: store a timestamp per request (Redis sorted set). On each request remove entries older than the window, count the rest, add the new one if under the limit. Exact, but memory is O(limit) per key and each op is O(log n). Use for low limits where exactness matters (for example 5 login attempts per 15 minutes).
  • Sliding window counter: keep counts for the current and previous fixed windows and weight the previous one by how much of it still overlaps:
estimate = current + previous * (1 - elapsedFractionOfCurrentWindow)
e.g. previous=84, current=36, 25% into the window -> 36 + 84*0.75 = 99

Two counters per key, close to accurate (it assumes requests in the previous window were evenly spread; Cloudflare reported very small error in its traffic). Good default for high-volume APIs.

How do you implement rate limiting across many gateway nodes? Senior
  1. Central store (Redis): every node calls Redis. The read-modify-write must be atomic, so use a Lua script (token bucket refill and take in one step) or INCR with EXPIRE. Adds one network hop (about 0.5 to 1 ms) and Redis becomes a dependency.
  2. Sticky routing: hash the client key to one limiter node, so counters are local. Fails over poorly and unbalances hot clients.
  3. Local limits plus periodic sync: each node gets a share (limit/N) or syncs counts every few hundred ms. Fast and survives store outages, but the global limit can overshoot a little.
  4. Sharded Redis by key to scale.

Decide fail-open vs fail-closed when the limiter store is down. Most public APIs fail open (availability over strict limits), but security limits such as login attempts may fail closed. Return 429 Too Many Requests with Retry-After, and clients should use exponential backoff with jitter. Race conditions: without atomic ops, two nodes both read "99" and both allow request 100.

How does a Snowflake ID work and what are the clock problems? Senior

Twitter's layout: 1 unused bit, 41 bits of milliseconds since a custom epoch (about 69 years), 10 bits of machine id (1024 workers), 12 bits of per-millisecond sequence (4096 ids per ms per worker, about 4 million per second per worker). Ids are k-sortable by time without coordination.

Clock issues and handling:

  • Clock moves backwards (NTP step, leap second, VM pause): could mint duplicates. Remember the last timestamp; if now is lower, wait until it catches up, or refuse and alert if the gap is large.
  • Sequence exhausted in one ms: spin until the next millisecond.
  • Worker id assignment: must be unique; lease it from ZooKeeper, etcd or a DB, never reuse a live id after a restart without a safe gap.
  • Ordering is only approximate across workers (skew of a few ms), so do not treat Snowflake order as strict causal order.
Why can random UUIDs hurt database performance? Intermediate

A primary key index in a B-tree prefers inserts at the right edge (monotonic ids). Random UUID v4 keys land on random pages, causing page splits, poor cache hit ratio (the whole index becomes the working set) and write amplification. In MySQL InnoDB the clustered index makes it worse, and every secondary index also carries the 16-byte primary key. Fixes: UUID v7 / ULID (time prefix), storing as 16-byte binary not a 36-char string, or a separate surrogate bigint key.

How do you produce short IDs: base62, hashing, counters? Intermediate
  • Base62 of a counter: take a unique integer and write it in digits 0-9, a-z, A-Z. 62^7 is about 3.5 trillion, so 7 characters cover a very large space. Unique by construction, no collisions, but sequential ids are guessable and need a distributed counter (ranges handed out to servers in blocks, such as 1M per server, to avoid a hot counter).
  • Hash and truncate: hash (MD5, SHA-256, or faster Murmur) the long value and take the first 7 characters. Stateless and deterministic, but truncation collides (birthday problem: with 62^7 space, collisions start showing at about a couple of million items). Must check the DB and retry with a salt on collision.
  • Random: random 7 characters plus a uniqueness check or unique constraint with retry.

To stop enumeration, permute or encrypt the counter before encoding (for example a Feistel cipher), or add random bits.

What is URL-safe encoding and how do base64, base62 and base32 differ? Basic

URLs reserve characters such as / ? # & = + %. Standard base64 uses + and / and pads with =, which are unsafe in URLs. Base64url swaps them for - and _ and usually drops padding (used in JWTs). Percent-encoding (%20) escapes arbitrary characters in a URL.

  • Base64: 6 bits per char, 33 percent size overhead.
  • Base62: only letters and digits, no special characters at all; slightly longer; not a bit-aligned encoding (works on integers, not byte streams).
  • Base32: 5 bits per char, case-insensitive, avoids ambiguous letters in Crockford form (ULID). Good for codes humans type.
  • Base58 removes 0, O, I, l (Bitcoin addresses).
Trap: Base64 and encoding are not encryption. An encoded token is readable by anyone.
Which hash function would you use for which job? Intermediate
  • Non-cryptographic (MurmurHash3, xxHash, CityHash, FNV): fast and well distributed. Use for sharding, hash tables, Bloom filters, consistent hashing. Not safe against adversarial inputs (hash-flooding), so keyed variants such as SipHash are used in hash maps exposed to attackers.
  • Cryptographic (SHA-256, SHA-3, BLAKE3): collision and preimage resistant. Use for integrity, content-addressed storage, Merkle trees, signatures, dedup by content.
  • Password hashing (bcrypt, scrypt, Argon2): intentionally slow and salted; never use plain SHA for passwords.
  • MD5 and SHA-1 are broken for security but still seen as quick checksums.

What is columnar storage and why is it fast for analytics? Intermediate

A row store keeps all columns of one row together (good for fetching or updating one record, OLTP). A column store keeps each column together (Parquet, ORC, ClickHouse, Redshift, BigQuery). A query like SELECT avg(price) FROM sales WHERE year=2026 reads only the two columns it needs, not 50.

  • Compression: a column has one type and repeated values, so dictionary encoding, run-length encoding, delta encoding and bit-packing give 5 to 10x compression.
  • Vectorised execution: process batches of values with SIMD.
  • Skipping: row groups store min/max statistics, so whole chunks are skipped (predicate pushdown).
  • Cost: writing or updating one row touches many column files, so these systems batch loads and are poor for point updates.
How do you choose a compression algorithm for storage and network? Intermediate
  • LZ4 / Snappy: very fast (hundreds of MB/s per core), modest ratio (about 2x). Default for hot paths, Kafka, RocksDB upper levels.
  • Zstd: strong ratio at tunable speed; good general default (levels trade CPU for size). Supports trained dictionaries for small messages.
  • Gzip/deflate: ubiquitous in HTTP; slower than Zstd for similar ratio.
  • Brotli: best for static web assets, slow to compress.

Rule: compress when CPU is cheaper than bytes (cross-region links, cold storage); skip for already-compressed data (JPEG, video). Compress before encrypting, never after (ciphertext does not compress), and be aware of attacks that exploit compression with secrets (CRIME/BREACH).

L4 versus L7 load balancing, and what is health checking? Intermediate

L4 balances TCP/UDP connections using IP and port: fast, protocol-agnostic, cannot see URLs or headers. L7 understands HTTP: routes by path, host or header, terminates TLS, retries, and balances per request (important for HTTP/2 and gRPC where one long connection carries many requests, so an L4 balancer would pin all traffic to one backend).

Health checks: active (probe /health every few seconds, remove after N failures, re-add after M successes) and passive (outlier detection: eject a backend after consecutive 5xx). Separate "liveness" from "readiness" so a slow-starting or overloaded instance is not killed but is taken out of rotation.

How do you build an LRU cache with O(1) operations? Basic

Combine a hash map (key to node) with a doubly linked list ordered by recency. Get: look up node, move it to the head, return value. Put: if the key exists update and move to head; otherwise insert at head, and if over capacity remove the tail node and its map entry. All O(1). In Java LinkedHashMap with access order and removeEldestEntry does this.

Weakness: a one-time scan over a large dataset flushes the entire hot set (scan pollution). In production, concurrency also matters: one global lock on the list is a bottleneck, so Redis approximates LRU by sampling a few keys and evicting the oldest of the sample, and Caffeine buffers access events and applies them asynchronously.

Compare LRU, LFU, ARC and TinyLFU. Senior
  • LRU: evicts the least recently used. Simple, adapts quickly to shifting working sets, vulnerable to scans.
  • LFU: evicts the least frequently used. Keeps long-term popular items; but old items with a high historical count never leave (needs ageing or decay), and new items start with count 1 and get evicted at once. Redis offers an approximate LFU with a probabilistic counter and decay.
  • ARC (Adaptive Replacement Cache): keeps two lists, recent-once and seen-twice-or-more, plus ghost lists of recently evicted keys. Hits in ghost lists tell it to grow one side or the other, so it self-tunes between recency and frequency and resists scans. Patent history limited its use (ZFS uses it).
  • TinyLFU / W-TinyLFU (Caffeine): a compact frequency sketch (Count-Min, with periodic halving to age counts) acts as an admission gate: a new item only replaces the victim if its estimated frequency is higher. A small window LRU lets bursts of new items in. High hit ratios with little memory.

Also: FIFO, CLOCK (cheap LRU approximation with a reference bit), random, TTL-based, and size-aware policies for variable object sizes (GDSF).

Say: I start with LRU, and move to W-TinyLFU or an LFU variant if traces show scans or a stable hot set. I check the actual hit ratio on production traces before choosing.
Scenario: a popular cache key expires and the database melts. What is happening and how do you stop it? Senior

This is a cache stampede (thundering herd, or dog-piling). Thousands of requests miss at once and all recompute the same expensive value. Fixes, by algorithm:

  • Request coalescing / single flight: only one caller rebuilds; others wait for the result (a per-key lock or in-flight future map).
  • Jittered TTLs: add a random few percent so many keys do not expire together.
  • Stale-while-revalidate: serve the expired value while one background refresh runs.
  • Probabilistic early refresh: as expiry nears, each request refreshes with a growing probability (XFetch).
  • Warm the cache before cutover, and for a cold restart or a node added to a ring, throttle the miss traffic.

Coordination mechanics

What algorithms are used for leader election? Senior
  • Bully algorithm: the node with the highest id wins. A node that notices the leader is gone sends election messages to higher ids; if none answer, it declares itself leader. Simple, many messages, and the highest-id node flapping causes churn.
  • Ring algorithm: circulate an election token around a logical ring, collecting ids; the highest becomes leader.
  • Raft: time is split into terms. A follower whose randomised election timeout (for example 150 to 300 ms) expires without a heartbeat becomes candidate, increments the term and requests votes. A node grants one vote per term and only to a candidate whose log is at least as up to date. A majority wins. Randomised timeouts avoid split votes. The leader sends heartbeats and log entries. Paxos and Zab (ZooKeeper) are comparable.
  • External lease or lock: use ZooKeeper (ephemeral sequential nodes; lowest sequence is leader and others watch their predecessor), etcd or Consul leases, or a DB row with a TTL.
Trap (split brain): an old leader that is paused (long GC, network partition) may still think it is leader. Use fencing tokens: every leadership grant carries an increasing number, and storage rejects writes with a lower number. A time-based lease alone is not safe because clocks pause and drift.
How do heartbeats and failure detectors work, and why is failure detection hard? Senior

In an asynchronous network you cannot tell "dead" from "slow" or "partitioned". A failure detector therefore only suspects.

  • Fixed-timeout heartbeat: peer sends a heartbeat every second; suspect after 3 missed. Simple, but a fixed threshold is either slow to detect or too jumpy under load.
  • Phi accrual detector (Cassandra, Akka): learns the distribution of heartbeat arrival times and outputs a suspicion level phi; the application picks a threshold (for example 8). It adapts to network jitter.
  • SWIM (Consul/Serf, memberlist): each node periodically pings a random peer; on no reply, asks k other nodes to ping it indirectly (to rule out a bad link between just the two), and only then marks it suspect, then dead after a timeout. Detection load stays constant per node and gossip spreads the verdict.

Trade-off: short timeouts give fast failover but false positives (needless leader elections, rebalancing storms when a GC pause looks like death). Long timeouts give slow recovery. Typical choices are a few seconds.

How does two-phase commit work, and what are its failure modes? Senior
  1. Prepare (vote): the coordinator asks every participant "can you commit?" Each participant durably logs its vote (it must be able to commit later), locks the resources and replies yes or no.
  2. Commit/abort: if all say yes, the coordinator logs the decision, then tells everyone to commit; any no or timeout means abort. Participants acknowledge.
  • Blocking: if the coordinator crashes after participants voted yes, they cannot decide alone and hold locks until it recovers. This is the main weakness.
  • Latency: two round trips plus fsyncs, and locks held throughout, so throughput suffers and contention grows.
  • Participant down: coordinator aborts after a timeout.
  • 3PC adds a pre-commit phase to reduce blocking but assumes bounded delays and is rarely used.
  • Alternatives: consensus-replicated coordinators (Spanner runs 2PC across Paxos groups so the coordinator state itself is highly available), sagas with compensating actions, or the transactional outbox for DB-plus-message-queue atomicity.
Say: 2PC gives atomicity but sacrifices availability and latency, so across service boundaries I prefer sagas, and I keep 2PC inside one database or one consensus-backed system.
What is a quorum and how do R, W and N relate? Intermediate

With N replicas, writes wait for W acks and reads query R replicas. If R + W > N, every read set overlaps every write set, so a read sees at least one replica with the latest write. N=3, W=2, R=2 is common. W=N, R=1 favours reads; W=1, R=N favours writes. Smaller R and W means lower latency but weaker consistency.

Caveat: overlap alone does not give linearizability (sloppy quorums, hinted handoff, concurrent writes, and clock-based conflict resolution can still show stale or lost data). Consensus protocols use majority quorums for the same overlap reason.

Data processing building blocks

Explain the MapReduce idea and when it still matters. Intermediate

A programming model for processing huge datasets in parallel on commodity machines. The user writes two functions: map (record to key-value pairs) and reduce (key plus all its values to a result). The framework handles splitting input, scheduling near the data, the shuffle (partition the map output by key and sort/group it), retrying failed tasks and stragglers.

Word count
map("the cat the") -> (the,1) (cat,1) (the,1)
shuffle: the -> [1,1,...], cat -> [1]
reduce(the, [1,1,...]) -> (the, total)

Optimisations: a combiner pre-aggregates on the map side to shrink the shuffle; skewed keys (one hot key) create a straggler reducer, fixed by key salting. Classic MapReduce writes to disk between stages and is slow for iterative work; Spark keeps data in memory and uses DAGs, while the same map/shuffle/reduce idea underlies SQL group-by and joins in these engines. Use it for batch ETL, index building, log aggregation, and large joins where the data does not fit on one machine.

How are large distributed joins executed, and what is data skew? Senior
  • Broadcast (map-side) join: if one table is small (fits in memory, say under 100 MB), send it to every node and join locally. No shuffle.
  • Shuffle hash / sort-merge join: repartition both tables by the join key so matching keys meet on one node, then join. Expensive network shuffle.
  • Skew: a hot key (a null id, a celebrity user) overloads one reducer. Fix with salting (split the hot key into key#0..key#9 and replicate the other side 10 times), handling hot keys separately with a broadcast, or adaptive query execution.
What other compact structures show up (bitmaps, roaring bitmaps, HyperLogLog sets, rolling hash)? Intermediate
  • Bitmap: one bit per id. "Which of 100 million users logged in on day D" is 12.5 MB; AND/OR across days answers retention. Redis SETBIT/BITCOUNT/BITOP. Sparse sets waste space, so Roaring bitmaps compress by chunk (used in Lucene, Druid, Pinot).
  • Rolling hash (Rabin-Karp, content-defined chunking): splits files at content-determined boundaries so a small insertion does not change all later chunks. Used by rsync and dedup backup and storage (Dropbox-like sync).
  • MinHash / SimHash: estimate similarity between documents, for near-duplicate detection.

Scheduling, deduplication and idempotency

Where are priority queues used in system design, and how are they implemented? Basic

A binary heap gives O(log n) insert and extract-min and O(1) peek. Uses: scheduling jobs by priority or deadline, merging k sorted streams (k-way merge in compaction and external sort, with a heap of size k), top-K tracking (min-heap of size K), Dijkstra for routing, timers (next due time).

In distributed systems a single in-memory heap is not enough. Options: multiple queues per priority class with weighted draining (for example 8:3:1) so low priority does not starve; a sorted set in Redis with the score as priority or due time; and ageing (raise the priority of waiting items) to prevent starvation.

How do you implement a delay queue or scheduled jobs (run this at time T)? Intermediate
  • DB polling: table with run_at and status; workers query WHERE run_at <= now AND status='pending' ... FOR UPDATE SKIP LOCKED with an index on run_at. Simple and durable; polling latency and load grow with scale.
  • Redis sorted set: score = due epoch ms; a worker takes members with score at most now using ZRANGEBYSCORE and removes them atomically (Lua or ZPOPMIN).
  • Broker features: SQS delay up to 15 minutes, RabbitMQ delayed-message plugin or TTL plus dead-letter exchange; Kafka has no native delay, so use tiered delay topics or a scheduler service.
  • Hierarchical timing wheel (next question) for millions of in-memory timers.
  • Sharded scheduler: partition jobs by hash and give each shard a lease owner, with leader election per shard, so one job does not fire twice.

Always make the job handler idempotent: at-least-once firing is the realistic guarantee.

What is a timing wheel and why is it better than a heap for many timers? Senior

A circular array of buckets, each representing one tick (for example 1 ms or 1 s). A timer expiring in d ticks is added to bucket (current + d) mod size; each tick, the pointer advances and fires everything in the next bucket. Insert and cancel are O(1), versus O(log n) for a heap, which matters with millions of timers (connection timeouts, request timeouts).

Timers farther than one revolution use a hierarchical wheel, like a clock: seconds wheel, minutes wheel, hours wheel. When the coarse wheel's bucket comes due, its timers cascade down into the finer wheel. Kafka uses hierarchical timing wheels for delayed operations (produce and fetch purgatory), and Linux kernel timers and Netty's HashedWheelTimer use the same idea. Trade-off: precision is limited to the tick size.

How does an idempotency key table work, and what are its pitfalls? Senior

Goal: if a client retries (timeout, network error), the side effect happens only once. The client sends a unique Idempotency-Key (a UUID) with each logical operation, and the server keeps a table:

idempotency(key PK, request_hash, status, response_body, created_at)
1. INSERT key with status=IN_PROGRESS   (unique constraint makes this atomic)
2. if insert fails: key already seen
     - COMPLETED -> return stored response
     - IN_PROGRESS -> return 409 or wait
     - request_hash differs -> 422 (same key, different payload: client bug)
3. do the work, then UPDATE status=COMPLETED + response
  • Do the business write and the key update in one transaction, or a crash in between creates a duplicate or a stuck key.
  • Expire keys after a window (Stripe keeps them about 24 hours).
  • Natural alternative: a unique business constraint (order id plus payment attempt) or conditional writes.
  • Pitfall: a key stuck IN_PROGRESS after a crash needs a timeout and recovery rule.
How do you deduplicate events in a stream using a time window? Senior

Brokers such as Kafka, SQS and Pub/Sub deliver at least once, so consumers see duplicates. Approach: every event carries a unique id; the consumer checks a set of recently seen ids and drops repeats. You cannot remember ids forever, so keep a dedup window (for example 24 hours, longer than the maximum retry or replay delay): Redis SET id NX EX 86400, a table with a TTL, or a per-partition state store in the stream processor. SQS FIFO has a 5-minute dedup window by default.

  • Memory: 100M ids per day at 16 bytes is about 1.6 GB raw; a Bloom filter shrinks it but its false positives would wrongly drop real events, so only use it as a fast pre-filter followed by an exact check, or when occasional loss is acceptable.
  • Duplicates arriving after the window slip through, so the downstream write should also be idempotent (upsert by key).
  • Kafka's idempotent producer dedups retries per partition using producer id and sequence numbers; end-to-end exactly-once still needs transactional or idempotent sinks.
Scenario: customers report being charged twice after a gateway timeout. Which building blocks fix it? Senior
  1. Cause: the client timed out, retried, and the first request had actually succeeded.
  2. Add an idempotency key per payment attempt, generated by the client and stored with a unique constraint server-side (see the table above).
  3. Make the downstream call to the payment processor carry the same key.
  4. Reconcile: a periodic job compares our records with the processor's and refunds duplicates.
  5. Retry policy: exponential backoff with jitter, a retry budget, and only retry idempotent operations.

Real-life scenarios and incidents

Scenario: one shard of your hash-partitioned store is at 95 percent CPU while the others idle. What do you check and do? Senior
  1. Identify the cause: a hot key (one celebrity or tenant), a skewed shard key (most rows share a value, or a null default), or an uneven ring (too few vnodes).
  2. Hot key: add a local cache or replicate reads; split the key with a suffix; use Count-Min Sketch or sampled access logs to find the top keys.
  3. Skewed key: choose a better shard key or compound key; add salt.
  4. Uneven partitions: more vnodes or smaller fixed partitions, then move a few partitions to the idle nodes.
  5. Do not just add nodes before knowing the cause: a single hot key stays on one node however large the cluster.
Scenario: after a long GC pause, two nodes both believed they were the leader and corrupted data. How do you prevent a repeat? Senior

This pattern is described in discussions of distributed lock safety (for example Martin Kleppmann's critique of Redis-based Redlock locks). The paused node resumed, did not realise its lease had expired, and wrote anyway. Fix: fencing tokens. The lock service returns a monotonically increasing number with each grant; the storage layer remembers the highest token seen and rejects writes with a smaller one. Also: keep leases short relative to expected pauses, check lease validity right before side effects, tune GC, and prefer consensus-backed locks (etcd, ZooKeeper) over best-effort ones for correctness-critical work.

Which well-known outages illustrate these building blocks going wrong? Senior
  • Cloudflare, July 2019: a regular expression with catastrophic backtracking in a WAF rule drove CPUs to 100 percent globally for about 30 minutes. Lesson: algorithmic worst cases matter; prefer linear-time regex engines and stage rollouts.
  • Facebook, 2010 (and similar cache incidents elsewhere): an invalid cached configuration value made clients all query the database to repair it, overwhelming it. Lesson: cache stampede and feedback loops, throttle repair traffic.
  • AWS DynamoDB, 2015: a metadata-service slowdown after a new feature increased membership load caused storage nodes to time out and retry, amplifying load (details per AWS's post-event summary; recall specifics loosely). Lesson: retries without backoff and budgets amplify failures.
  • Leap second bugs (2012, 2015, 2017): clock steps caused hangs and spikes in Linux and some Java systems. Lesson: do not assume monotonic wall clocks; use monotonic clocks for durations, and smear leap seconds.

In an interview, only cite details you are sure of and frame the lesson, not the trivia.
