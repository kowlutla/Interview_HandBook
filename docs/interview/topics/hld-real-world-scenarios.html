HLD: Real-World Scenarios and Incidents interview questions

Situational "what would you do" questions about running production systems (latency spikes, bad deploys, hot keys, retry storms, split brain, bad migrations, leaked credentials and more), plus the well-known industry outages (S3 2017, GitHub 2018, Cloudflare 2019, Facebook 2021, Knight Capital, GitLab, CrowdStrike and others) and the design lessons each one teaches.

How to use this page

Senior interviews often drop the whiteboard and ask "it is 2 a.m., X is happening, what do you do?". The interviewer wants to see a calm, ordered method: stop the bleeding first, find the cause second, fix it properly third, and make sure it cannot happen again fourth. Each scenario below is answered that way. The second half covers real outages that interviewers like to reference. Incident details are described at headline level and hedged where public write-ups differ; do not quote numbers from memory in an interview, quote the lesson.

The general method

Production is on fire. What is your general order of operations? Senior
  1. Confirm and scope: is it real (monitoring can be wrong), who is affected (all users, one region, one tenant, one endpoint), and since when?
  2. Ask "what changed?": deploys, config pushes, feature flags, traffic shape, cron jobs, certificate or quota expiry, upstream vendor changes. Most incidents correlate with a change.
  3. Mitigate before you understand: roll back, flip the flag off, shed load, fail over, scale out. Restoring service beats finding the root cause.
  4. Communicate: one incident commander, a status channel, regular updates, a customer-facing status page.
  5. Find root cause once stable, using the signals you preserved (logs, metrics, heap dumps, thread dumps).
  6. Fix and prevent: blameless postmortem, action items with owners, tests or guardrails so the same class of failure is caught earlier.
Say: "Mitigate first, diagnose second. I use the four golden signals (latency, traffic, errors, saturation) to find which tier is unhappy, then ask what changed."
What are the golden signals and the USE and RED methods, and how do they help in an incident? Basic
  • Four golden signals (Google SRE book): latency, traffic, errors, saturation.
  • RED (for services): Rate, Errors, Duration.
  • USE (for resources such as CPU, disk, pool): Utilization, Saturation, Errors.
Use RED on every service to find which hop is slow or failing, then USE on that service's resources (CPU, memory, threads, connection pool, disk, network) to find what is saturated. Look at percentiles (p95, p99), not averages, because averages hide tail latency.
What makes a good blameless postmortem, and why does the "blameless" part matter? Intermediate
A good postmortem has: a timeline (detection, escalation, mitigation, resolution), impact (users, duration, money), root cause and contributing factors (usually several), what went well, what went badly, and action items with owners and dates. Blameless means you ask "how did the system allow a human to make this mistake?" instead of "who did it?". If people fear punishment they hide information, and you lose the true cause. Many famous incidents below (S3 typo, GitLab deletion) were turned into guardrail changes, not firings.
How do you make sure you hear about an incident before customers do? Intermediate
Alert on symptoms users feel (error rate, latency SLO burn rate, failed synthetic checks that run a real login or checkout), not only on causes (CPU). Use multi-window burn-rate alerts on an SLO so a fast burn pages immediately and a slow burn opens a ticket. Add black-box probes from outside your network, since a dashboard that lives in the same failed region or behind the same failed DNS will go dark with it (a lesson from the Facebook 2021 outage below).

Scenarios: latency, load and capacity

Latency suddenly spikes on a service. How do you investigate? Senior

First checks

  • Is it all requests or only the tail (p99)? All endpoints or one? One region, host or tenant?
  • What changed in the last hour: deploy, config, flag, traffic mix, dependency version?
  • Trace a slow request (distributed tracing): which span grew? Own code, a database call, a downstream service, a queue wait?
  • Saturation: CPU, GC pauses, thread pool queue depth, connection pool wait, disk IO, network retransmits.

Common culprits: a slow dependency, a missing index after data growth, GC pressure, lock contention, a noisy neighbour, cold caches after restart, DNS or TLS handshakes on every call (no connection reuse), a retry storm adding load.

Mitigate: roll back the change, shed or rate-limit low-priority traffic, scale out if CPU-bound, enable a cache or serve stale, set tighter timeouts so slow calls do not hold threads.

Prevent: latency SLOs with alerts, per-dependency timeouts and circuit breakers, load tests on realistic data volumes, canary deploys with automatic latency comparison.

The error rate climbs right after a deploy. What do you do? Senior
  1. Roll back or halt the rollout now if the timing matches. Do not debug live in front of users.
  2. Compare the canary or new version's error rate against the old version (same time window). Look at the error type: 5xx from your code, 4xx from a changed contract, timeouts to a dependency.
  3. Check what else shipped: config, flags, a schema migration, a dependency upgrade, an API change from another team.
  4. Reproduce in staging with the failing request from the logs.

Trap: the rollback may not be safe if the deploy included a data or schema change (see the rollback question below). Also remember a deploy can expose a latent problem such as cold caches or a new traffic pattern, not only a code bug.

Prevent: progressive delivery (1 percent, 10 percent, 50 percent) with automated analysis that halts on error-rate regression, feature flags to decouple deploy from release, backward-compatible changes (expand then contract).

Database CPU is at 100 percent. What do you check and do? Senior

Find who is using the CPU

  • Top queries by total time (pg_stat_statements in PostgreSQL, performance_schema or slow query log in MySQL, Query Store or DMVs in SQL Server). One query running a million times is as bad as one huge query.
  • Did a query plan change (stale statistics, a plan flip to a full scan)? Was an index dropped or never created for new data volumes?
  • Did traffic change? New feature, bot traffic, a cache that stopped working and sent reads to the database?
  • Is it a lock or connection pile-up, with many sessions spinning on the same row?

Mitigate now: kill the runaway queries, add the missing index (online or concurrently), turn off the offending feature, shift reads to replicas, throttle the caller, scale the instance up as a stopgap.

Fix properly: rewrite the query, add indexes or covering indexes, fix N+1 patterns, add a cache with correct invalidation, pagination by key instead of large OFFSET, move analytics to a replica or warehouse.

Prevent: slow-query dashboards, query review for new code, load tests with production-sized data, statement timeouts.

A query that was fast for a year suddenly becomes slow at scale. Why, and what do you do? Intermediate
Typical reasons: the table crossed a size where the optimizer picks a different plan; an index no longer fits in memory so it hits disk; statistics are stale; the query was O(n) (sequential scan, large OFFSET, unindexed LIKE) and n finally hurts; data skew (one tenant has most rows); lock contention rising with concurrency.

Steps: run EXPLAIN (ANALYZE) on the real query with real parameters, compare against the old plan, refresh statistics, add or fix the index, use keyset pagination, partition or archive old data. Prevention: test with data volumes 10x today's and track query latency per query fingerprint over time.

Traffic doubles in a week (a launch or viral event). How do you prepare? Senior
  1. Measure the current headroom: peak utilization per tier, and which resource saturates first (usually the database or a connection limit, not stateless web servers).
  2. Load test at 2x and 3x with production-like data and traffic mix; find the first bottleneck, fix it, repeat.
  3. Scale the easy parts: stateless tiers behind autoscaling, pre-warmed (do not rely on reactive scaling for a sudden spike), CDN and caches for read-heavy content.
  4. Protect the hard parts: read replicas, connection pooling or a proxy, queue-based write smoothing, rate limits and load shedding priorities (checkout over browse).
  5. Check third-party limits (payment, email, maps API quotas) and cloud account quotas (instances, IPs, IOPS).
  6. Prepare a runbook: kill switches for expensive features, degraded modes, on-call rota, a war room on launch day.
Say: "Doubling is rarely about web servers. I look for the first non-horizontally-scalable thing: the primary database, a lock, a quota, a single queue partition."
Your autoscaler is flapping (scale up, scale down, repeat). Why, and how do you fix it? Intermediate
Causes: the scale-out and scale-in thresholds are too close together; the metric reacts to the scaling itself (adding instances drops average CPU, which triggers scale-in, which raises CPU again); slow startup so the metric is high while new capacity is still warming; a noisy metric with a short window.

Fixes: add hysteresis (scale out at 70 percent, in at 40 percent), longer cooldown or stabilization windows (Kubernetes HPA has a scale-down stabilization window), scale on a better signal such as queue depth or requests per instance, use warm pools or pre-provisioned capacity, scale in slowly and out quickly, and set sensible minimums. Also check readiness probes: instances that are not ready should not count as capacity or as healthy metrics.

You suspect a memory leak in production. What do you do? Senior

Symptoms: memory climbs steadily and never returns to baseline after GC, GC time rises, then OOM kills or restarts, often with a sawtooth pattern across restarts.

Mitigate: restart on a schedule or on a memory threshold, add instances behind a rolling restart so the fleet does not die together, roll back if it started with a deploy.

Investigate: take a heap dump (or a native memory profile) from a leaking instance and compare two dumps over time; look at the dominator tree for the objects that keep growing. Typical causes: unbounded caches or maps, listeners never deregistered, per-request objects stored in static or thread-local state, unclosed streams or connections, unbounded queues, large per-tenant data held forever. Also rule out "not a leak": container limit set below the JVM heap plus native overhead, or off-heap/direct buffers.

Prevent: bounded caches (size and TTL), bounded queues, memory alerts on the trend (not just a threshold), soak tests, a canary that runs for hours before wide rollout.

A disk is filling up on a production host. How do you handle it? Intermediate
  1. Find what is growing: du by directory, and check for deleted-but-still-open files (lsof shows them; space is not freed until the process closes them).
  2. Usual suspects: logs without rotation or at DEBUG level, core or heap dumps, database WAL or binlog not being archived or purged (a stuck replica or replication slot can pin WAL), temp files, a runaway message log.
  3. Mitigate: rotate or truncate logs, move or delete old files, expand the volume, remove the stuck replication slot after confirming it is safe.
  4. Prevent: alert at 70 and 85 percent and on predicted time-to-full, log rotation and retention, ship logs off-host, quotas, and monitor inodes too (a disk can be "full" with free bytes but no inodes).
Trap: a database that runs out of disk often stops accepting writes or crashes; a full disk is a hard failure, so alert on the trend, not at 99 percent.
One tenant is hurting everyone else in a multi-tenant system (noisy neighbour). What do you do? Senior

Detect: per-tenant metrics (requests, CPU time, DB time, bytes) so you can see the top consumers. Without tenant-level dimensions you cannot even prove it.

Mitigate now: throttle that tenant with a per-tenant rate limit or concurrency cap, move them to a lower-priority queue, or temporarily isolate them to dedicated capacity.

Design fixes

  • Per-tenant quotas and fair queuing (weighted fair share) so one tenant cannot consume the whole worker pool.
  • Bulkheads: separate thread pools, connection pools or queues per tenant tier.
  • Cell-based or shuffle-sharded architecture so a bad tenant only impacts a small slice.
  • Sharding by tenant with the ability to move big tenants to their own shard.
  • Cost-based limits (query complexity), not just request counts.
A third-party API you depend on (payments, email, maps) goes down. What happens and what should you have designed? Senior
Without protection, calls hang until timeouts, threads pile up, and your own service goes down with theirs. Design for it:
  • Short timeouts, a circuit breaker that opens after repeated failures, and a clear fallback.
  • Decouple through a queue where the business allows it (send the email later; accept the order and charge asynchronously).
  • Idempotency keys so retries after recovery do not double-charge.
  • For critical paths, a secondary provider (payment routing across two PSPs) and graceful degradation (hide the maps widget, not the whole page).
  • Status-page monitoring and your own synthetic checks of the vendor; contract SLAs; a runbook saying who flips the failover.
During the outage: communicate, queue what you can, and reconcile when the vendor returns (compare your records with theirs).

Scenarios: databases, caches and queues

Replica lag keeps growing. How do you investigate and what do you do? Senior

Why lag happens: the replica applies changes slower than the primary produces them. Common causes: a heavy write burst or a huge batch or bulk update; a single-threaded apply on the replica (classic MySQL replication) falling behind a multi-threaded primary; long-running queries on the replica blocking replay (PostgreSQL recovery conflicts); an underpowered replica (disk IO, smaller instance); network limits between regions; a large transaction that must be applied as one unit.

Check: lag trend and when it began; primary write rate; replica CPU, IO, and apply thread state; long queries on the replica; whether one big transaction is in flight.

Mitigate: stop or throttle the bulk job, kill long replica queries, route lag-sensitive reads (read-your-writes) to the primary, remove the lagging replica from the read pool until caught up, enable parallel apply, upgrade the replica.

Product-level safety: after a write, read from the primary or pin the session to it for a few seconds; send a version or LSN token with the user session and only read from a replica that has reached it. Break big batch jobs into small chunks with sleeps. Alert on lag in seconds, and have the app stop using replicas past a threshold.

The cache hit ratio suddenly collapses. What do you do? Senior

First protect the database, because the misses fall through to it.

  • Causes: a cache node died or restarted (cold cache); a flush or key-prefix/version change in a deploy; a key format change (new code builds different keys); eviction because memory is full or a big new key set; TTLs set identically so everything expired together; a bot or crawler scanning cold keys; cache penetration (requests for non-existent keys).
  • Mitigate: shed load or rate limit, enable request coalescing so one miss fills the cache while others wait, serve stale data while refreshing in the background, warm the cache for hot keys, scale the cache or fix the memory limit, roll back the key change.
  • Prevent: add jitter to TTLs, use consistent hashing so a node loss only moves a slice, cache negative results (short TTL) or a Bloom filter for non-existent keys, never change key format without dual-read, and size the database to survive a cold cache or have load shedding in front of it.
Everything stampedes the database after a restart or cache flush (thundering herd). What is happening and how do you stop it? Senior
When a hot key expires (or the whole cache is cold), many concurrent requests all miss and all hit the database to recompute the same value. The database slows, so recomputation takes longer, more requests pile up, and it can fall over. A restart makes it worse: every client reconnects at once, every cache is empty, and connection pools open together.

You find a hot partition or hot key. How do you handle it? Senior

Symptom: one shard, Kafka partition or DynamoDB partition is saturated while others idle; throttling or high latency for a subset of requests. Cause: skewed keys (a celebrity user, a viral product, one big tenant), or a monotonic key (timestamps, sequential ids) sending all new writes to one range.

Fixes by type

  • Hot read key: local in-process caching, replicate the hot key across several cache nodes (key suffix 0..N and pick randomly), CDN.
  • Hot write key (counters, likes): split into sub-counters (shard the counter and sum on read), or buffer and batch updates.
  • Skewed partition key: salt the key (user_id plus a small random or hash suffix) at the cost of scatter-gather on read, or choose a higher-cardinality key; for big tenants give them dedicated partitions.
  • Monotonic keys: hash the key prefix or use a different ordering so writes spread.
  • Adaptive capacity or auto-splitting where the datastore supports it, but do not rely on it for a single-key hotspot, since one key cannot be split.
Say: "The first step is to prove it is skew with per-partition metrics, then choose between spreading the key (salting) and absorbing the load (caching, batching)."
A queue backlog keeps growing. What do you do? Senior

Backlog grows when arrival rate is above processing rate, so find which changed.

  1. Consumers: are they alive, crash-looping, or stuck? Did processing time per message rise (slow dependency, a poison message being retried forever, a bigger payload)? Lag per partition: if one partition is huge, it is a hot key or a stuck consumer.
  2. Producers: did the rate spike (a batch job, a retry loop, an upstream bug producing duplicates)?
  3. Mitigate: scale consumers (limited by partition count in Kafka-like systems, so increase partitions or split the topic), move poison messages to a dead-letter queue, pause low-priority producers, drop or sample non-critical messages, add a priority lane.
  4. Fix: batch processing, remove the slow synchronous call, make consumers idempotent so retries are cheap.
  5. Prevent: alert on lag growth and message age (not only depth), a dead-letter queue with limited retries, backpressure to producers, capacity tests.
Trap: adding consumers does not help if the bottleneck is the database they write to, or if ordering requires one consumer per key.
One bad message blocks the whole queue or partition. What is the pattern to handle it? Intermediate
This is a poison message: the consumer fails, does not commit, and re-reads the same message forever (head-of-line blocking in an ordered partition). Handle it with bounded retries (with backoff), then route the message to a dead-letter queue with the error and metadata, commit past it, and alert. Separate transient failures (retry with delay, possibly through a retry topic) from permanent ones (parse error, schema mismatch: go to the DLQ immediately). Keep a tool to inspect and replay DLQ messages after a fix. Validate and version message schemas at the producer to reduce poison messages in the first place.
Connection pool exhaustion: requests hang and the logs say "timeout waiting for connection". What now? Senior

Why: all connections are checked out and not returned. Either demand rose, or each request holds a connection longer (slow queries, a lock wait, a slow downstream call made while holding a transaction), or connections leak (not closed on an error path).

Check: pool active versus max metrics; thread dump to see what threads holding connections are doing; the database's view of sessions (idle in transaction, long running, waiting on locks); a recent change that added a remote call inside a transaction.

Mitigate: kill stuck sessions, restart leaking instances, shed load. Increasing the pool size is a risky fix: the database has a limit (total connections across all app instances) and more concurrent queries usually makes it slower. Keep pools small and put a proxy or pooler (PgBouncer, RDS Proxy) in front when many instances connect.

Fix and prevent: use try-with-resources, set a leak-detection threshold and max lifetime, never do remote calls inside a transaction, set statement and lock timeouts, size the pool from Little's law (concurrency = rate times time held), and alert on pool wait time.

Scenarios: cascading failure and retry storms

A retry storm is taking down a dependency. What is happening and how do you stop it? Senior

A dependency slows or fails briefly. Every client retries (often at several layers: SDK, service, gateway), multiplying load maybe 3x to 10x just when the dependency is weakest. It cannot recover because the retry traffic keeps it saturated. Even after the original trigger is gone, the system stays down (a metastable failure).

Stop it now: shed load at the dependency or in front of it, disable retries by config or flag, open circuit breakers manually, reduce traffic (rate limit clients), restart in stages, and only then let traffic back gradually.

Design to avoid it

  • Exponential backoff with jitter, and a cap on attempts.
  • A retry budget (retries allowed to be at most about 10 percent of requests) instead of per-request counts.
  • Retry at one layer only, not at every layer of the call chain.
  • Circuit breakers and server-side load shedding that returns a fast error (503 plus Retry-After).
  • Deadlines propagated through the call chain so work for a caller who has already given up is dropped.
  • Idempotent operations so retries are safe.
One slow dependency causes a cascading failure across the platform. How does it happen and how do you contain it? Senior
D slows (not dead, just slow, which is worse than failing fast). C's threads wait on D until its pool is full, C then slows, and the problem climbs the call chain until the front door is unresponsive. Healthy features that never call D die too, because they share thread pools.

Containment: timeouts shorter than the caller's timeout; circuit breakers; bulkheads (separate pools per dependency so D can only exhaust its own); load shedding; fallbacks and cached data; async decoupling with queues; avoid deep synchronous call chains; health checks that do not mark everything unhealthy at once (otherwise the load balancer removes all instances and makes it worse).

A shared dependency fails, health checks fail everywhere, and the load balancer removes every instance. What went wrong? Intermediate
The health check tested a deep dependency (database) so a database blip made all instances look dead, the load balancer sent traffic nowhere, and the whole service went down even though the processes were fine. Use separate liveness (process is alive; restart if not), readiness (can serve now; stop sending traffic if not) and keep deep dependency checks out of liveness. Configure the load balancer with "fail open" or a minimum healthy threshold so that if all backends look bad it still routes to them. Degrade gracefully (serve cached or partial responses) instead of failing health.

Scenarios: consistency, messaging and time

After a network partition you discover two nodes both think they are the primary (split brain). What do you do? Senior

Immediate: stop writes to one side (fence it: revoke its access, power it off, block it at the network or storage layer), choose the side that has the most complete data, and freeze automated failover so it does not flap.

Then: find the writes that landed on the losing side during the overlap, decide how to merge or replay them (conflicting rows need business rules or manual review), and reconcile downstream systems that consumed events from the wrong primary.

Design to avoid it

  • Quorum-based leader election (Raft, Paxos, ZooKeeper, etcd): a leader needs a majority, so only one side of a partition can have one.
  • Fencing tokens: every lease or leadership term has an increasing number, and storage rejects writes with an older token.
  • STONITH (shoot the other node in the head) in clustered setups.
  • An odd number of voters across failure domains; a witness node.
  • Do not let a failover tool promote on a short blip; require confirmation from several observers.
See the GitHub 2018 incident below for a real example.
Data is inconsistent between two services (the order says paid, the payment service says no). How do you handle it? Senior

Why it happens: a dual write (update database, then publish an event, and one half fails), a lost or duplicated message, out-of-order events, a partial failure of a saga, or two services owning the same fact.

Short term: run a reconciliation job comparing the two sources of truth, repair based on a declared authority (the payment provider is the truth for payments), and write an audit record.

Long term

  • One owner per fact; others hold read-only copies updated from events.
  • Transactional outbox: write the data and the event in the same local transaction; a relay publishes events (at least once).
  • Idempotent consumers and versioned or timestamped events so duplicates and reorders are harmless.
  • Sagas with compensating actions and timeouts for multi-service workflows.
  • Periodic reconciliation as a standard safety net, with alerts on mismatch counts.
Customers were charged twice. How could it happen and how do you prevent it? Senior

Causes: the client timed out and retried; a user double-clicked; a queue redelivered after a consumer crashed before acknowledging (at-least-once delivery); a failover replayed a request; a job ran twice (two schedulers).

Immediate: identify affected charges by finding duplicate (customer, amount, time window, reference) tuples, refund, and notify.

Prevention

  • Idempotency key generated by the client per logical operation and stored with a unique constraint along with the result; a repeat returns the saved result instead of re-executing. Payment providers expose this as an idempotency-key header.
  • Make the state change and the dedup record atomic (the same transaction), not two separate steps.
  • Consumers dedupe by message id; use conditional updates (compare-and-set on a version or state machine: only move from PENDING to PAID once).
  • Distributed locks or leader election for scheduled jobs, plus a dedup guard in the job itself, because locks can expire.
Trap: "exactly-once delivery" is not available over an unreliable network. You get at-least-once delivery plus idempotent processing, which together act like exactly-once effects.
Messages are being lost: producers say sent, consumers never saw them. Where do you look? Senior
Walk the pipeline hop by hop and ask who acknowledged what.
  1. Producer: fire-and-forget without waiting for acks; the process exited before flushing its buffer; no retry on failure; the DB commit succeeded but the publish failed (dual write; fix with an outbox).
  2. Broker: acknowledgement level too weak (for Kafka, acks=1 with leader failure before replication; replication factor 1; unclean leader election; retention shorter than consumer lag so messages expired before being read).
  3. Consumer: auto-commit offsets before processing finished (crash means the message is skipped); an exception swallowed and acked; a filter bug dropping messages; messages sent to a DLQ nobody watches.
  4. Network and routing: wrong topic or routing key, TTL expiry on the queue.
Debug using end-to-end counters (sent, broker received, consumed) and a unique id per message that you can trace. Fix: strong acks (acks=all with min in-sync replicas of 2 and replication factor 3), commit offsets after processing, outbox pattern, DLQ alerts, and a reconciliation count between producer and consumer.
What kinds of bugs does clock skew cause, and how do you design around it? Senior
Clocks on different machines drift (milliseconds up to seconds, or much worse if NTP breaks), and they can jump backward when synced. Real bugs:
  • Last-write-wins using timestamps silently discards the newer write when the writer's clock is behind.
  • Lease or lock expiry decided with local clocks: a paused process (GC) still believes it holds the lock.
  • Certificate or token validation fails (not yet valid, or expired) on a host with a wrong clock.
  • Event ordering and TTL calculations are wrong; negative durations; duplicate or missing scheduled runs; metrics with weird timestamps.
  • Leap seconds causing hangs or spikes (a known source of past incidents in some systems).

Design around it: use monotonic clocks for measuring durations; use logical clocks (Lamport, vector clocks) or database-generated sequence numbers for ordering; use fencing tokens instead of trusting lease timing; monitor NTP offset and alert; leave margins on token expiry; use a time source with bounded uncertainty where it matters (Google Spanner's TrueTime is the famous example, with commit wait).

Someone accidentally deleted production data. How do you restore, and how do you prevent it? Senior

Immediate: stop further damage (disable the job, revoke the access), preserve evidence, and if there are replicas stop replication immediately if it has not yet applied the delete (a delayed replica is built for this). Decide the target: the whole database to a point in time, or just the affected rows.

Restore: point-in-time recovery from a base backup plus WAL or binlog to just before the mistake, into a separate instance; extract the lost rows and merge them back into production (so you do not lose valid writes made after the delete). Soft-deleted data can be undeleted from the app layer. Object stores with versioning let you restore previous versions.

Prevent

  • Backups that are tested by restoring regularly; an untested backup is a hope, not a backup (the GitLab 2017 lesson).
  • Point-in-time recovery enabled; delayed replica; backups stored in a different account or region with deletion protection.
  • Least privilege: engineers do not use production admin credentials by default; require break-glass, peer review for destructive commands, and prompts that make the target environment obvious.
  • Soft deletes and retention windows; deletion protection flags on databases and buckets.
  • Know your RPO (how much data you may lose) and RTO (how long recovery may take).

Scenarios: change, deploy and configuration

A schema migration goes wrong in production. How do you do migrations safely? Senior

How migrations hurt: ALTER TABLE takes a lock that blocks reads and writes on a large table; adding a column with a default rewrites the table in some engines or versions; adding an index non-concurrently blocks writes; a backfill saturates IO and replication; renaming or dropping a column breaks old application versions still running during the rollout.

Safe pattern: expand, migrate, contract

  1. Expand: add the new nullable column or table (cheap, backward compatible); create indexes online or concurrently.
  2. Deploy code that writes both old and new (dual write) and reads the old one.
  3. Backfill in small batches with throttling, watching replica lag.
  4. Switch reads to the new one; verify with comparisons or shadow reads.
  5. Contract: stop writing the old one, then drop it in a later release once rollback is no longer needed.
Also: test the migration on a production-sized copy, set a lock timeout so the migration fails fast instead of queuing everything behind it, use online schema-change tools (gh-ost, pt-online-schema-change, or the engine's online DDL), and keep each step independently reversible.
You need to roll back a release but cannot because data has already changed. What do you do? Senior
This happens when the new version wrote data in a new format, applied a destructive migration, or sent messages the old code cannot read. Options: roll forward with a hotfix; keep the new schema but redeploy the old code if it tolerates the data (it often fails); write a fixer script to convert data back; or disable the new feature with a flag while the data stays.

Prevention is the real answer: make every release backward compatible with the previous one (old code must run on the new schema, new code on the old), separate schema changes from the code releases that need them, ship risky features behind flags, use the expand-contract pattern, version message and API formats, and never drop or rewrite data in the same release that depends on it. Practice rollback as part of the release process. The Knight Capital case below is partly about this.

A configuration change broke everything at once. Why is this so common and how do you protect against it? Senior
Config is often pushed globally and instantly, unlike code which goes through canaries; config changes bypass tests; and a bad value (empty list, wrong regex, a lowered limit, an expired certificate reference) is read by every instance at the same moment. Several famous outages (Facebook 2021 network command, Cloudflare 2019 rule, CrowdStrike 2024 content update) were this kind of global push.
  • Treat config as code: version control, review, validation, and schema checks before applying.
  • Roll out progressively (one cell or region, then widen) with automatic rollback on health regressions.
  • Keep the last known good config and fall back to it if the new one fails to parse or fails health checks.
  • Have an emergency kill switch, and make sure it does not depend on the thing that is broken.
  • Separate the rollout of risky config from the rollout of code, and record every change so "what changed?" is quick to answer.
How do feature flags help during incidents, and what are their risks? Intermediate
Flags separate deploy from release, so you can turn off a bad feature in seconds without a rollback, release to 1 percent of users first, and have a kill switch for expensive features under load. Risks: stale flags pile up as dead code and unlinked combinations; a flag service outage (cache the last known values locally and default to a safe value); untested flag combinations; flag changes also need audit and review because they are production changes. Remove flags once a rollout is complete. Knight Capital (below) is the cautionary tale of reusing an old flag.

Scenarios: infrastructure, regions and security

An outage is caused by an expired certificate or a DNS problem. How do you respond and prevent it? Intermediate

Expired certificate: clients fail TLS handshakes, often for one internal service-to-service link, which then looks like random failures. Mitigate by issuing and deploying a new certificate (and reloading the process if it caches the old one), then find every place the old one is used (load balancers, mTLS between services, client trust stores, pinned certificates). Prevent with automated issuance and renewal (ACME, a cert manager), short-lived certs, an inventory, and alerts at 30, 14 and 7 days before expiry, plus synthetic checks that read the served certificate's expiry.

DNS: symptoms are intermittent "cannot resolve" errors, or traffic going to the wrong place after a change. Remember caching: a record's TTL means a change or a rollback takes that long to propagate, and some resolvers ignore TTLs. Lower the TTL before a planned change, keep the change reviewed and staged, avoid a single DNS provider for critical zones (the Dyn 2016 lesson), and make sure your tooling and monitoring do not depend on the same DNS you are repairing (Facebook 2021).

A whole cloud region goes down. What happens, and what should the design have been? Senior

The honest answer depends on the architecture you chose before the incident. Options, in rising cost:

StrategyRTO / RPONotes
Backup and restore in another regionHours / minutes to hoursCheapest; slow; must be rehearsed
Pilot light (data replicated, compute off)Tens of minutesNeeds infrastructure as code to scale up quickly
Warm standbyMinutesScaled-down copy always running
Active-active multi-regionNear zeroHardest: conflict handling, data residency, cost

During the event: decide to fail over (a human decision with clear criteria is often better than an automatic one that can itself cause damage), shift DNS or global traffic management, promote replicas and accept the RPO, and watch for the capacity crunch as everyone else fails over too (the standby region may lack capacity, so reserve it). Hidden dependencies are the usual surprise: a global control plane, a single-region auth service, DNS, or a deployment tool living in the failed region. After recovery, plan the fail-back as carefully as the failover. Run game days so the first failover is not in production anger.

A credential (API key or database password) was leaked, for example committed to a public repository. What do you do? Senior
  1. Revoke or rotate immediately; do not first spend time deciding if it was abused. Removing it from the repo or git history does not help because it is already copied, so assume it is compromised.
  2. Scope the blast radius: what could this credential access? Check audit logs (cloud trail, database logs, API usage) for use from unknown IPs or at odd times.
  3. Contain: revoke sessions or tokens issued with it, check for persistence (new users, keys, access rules, scheduled jobs, new instances), and rotate anything it could read (secrets in the same vault).
  4. Notify: security team, and legal or customers if data was accessed (there are regulatory deadlines in many regions).
  5. Prevent: secret scanning in pre-commit and CI, a secret manager with short-lived dynamic credentials (so a leak expires by itself), least privilege and scoped keys, IP or network restrictions, and a rehearsed rotation procedure (a credential you cannot rotate quickly is a risk).
You are under a DDoS attack or a sudden abusive traffic spike. What do you do? Intermediate
Distinguish an attack from a legitimate surge (a marketing campaign) by looking at the traffic shape: sources, user agents, paths, and the presence of valid sessions. Then layer defences: CDN or DDoS-protection service to absorb volumetric floods at the edge; WAF and rate limits per IP, token, and path; bot challenges; caching of expensive public pages; autoscaling with a spend cap; blocking by ASN or country if clearly attributable; and protecting the origin by allowing only the CDN's addresses. Design pre-incident: keep origin IPs hidden, make expensive endpoints authenticated or cheap to reject, and have an escalation contact at the CDN or provider. Watch for application-layer attacks (a few requests that are costly, such as search or login) which volumetric protection does not stop.

Well-known industry incidents

Each entry says what happened, the root cause, and the design lesson. These are summarized from the public post-mortems as best remembered; exact durations and numbers are intentionally left out or hedged.

AWS S3 us-east-1 outage (2017): what happened and what does it teach? Senior

What happened: In February 2017, Amazon S3 in the US-EAST-1 region had a multi-hour outage. Because many websites, tools and even other AWS services depended on S3 in that region, a large part of the internet had problems. There was even an amusing side effect: the AWS status dashboard itself depended on S3.

Root cause (per AWS's post-event summary): an engineer was debugging a billing-system slowness and ran a command intended to remove a small number of servers from a subsystem, but one input was entered incorrectly and a much larger set of servers was removed. This took out capacity for core S3 subsystems (index and placement). Those subsystems had not been fully restarted for years, and restarting them took much longer than expected because the service had grown so much.

Lessons

  • Guard operational tooling: limit how much can be removed at once, enforce a minimum capacity, and require confirmation for large blast radius.
  • Rehearse cold restarts of core components; recovery time grows with scale if untested.
  • Partition into cells so one subsystem failure has a smaller blast radius.
  • Hidden dependencies on a single region: a multi-region design and a status page that does not depend on the thing being reported on.
Say: "A typo is not a root cause; the root cause is a tool that allowed a typo to remove too much capacity too fast."
GitHub 2018 outage: database failover and split brain. What happened? Senior

What happened: In October 2018 GitHub had a degraded service for roughly a day (about 24 hours, per the post-mortem as I recall). Data in their MySQL clusters was inconsistent for a time, so they chose to prioritize data integrity over availability and restored while some features stayed degraded.

Root cause: during routine maintenance on networking equipment, connectivity between their US East Coast network hub and the primary data center was lost for a very short period (tens of seconds). Their orchestration tooling promoted a primary in the other data center. When connectivity returned, each side had accepted writes the other did not have, so writes existed in two places. The cross-coast latency then also meant the application, which expected the primary to be local, performed poorly.

Lessons

  • Automatic failover on a brief network blip is dangerous; consider the cost of an unnecessary failover versus waiting.
  • Failing over across a high-latency link changes application behaviour; test cross-site operation.
  • Quorum and fencing are needed to prevent two primaries accepting writes; cross-site replication has to be designed for the case where both sides diverge.
  • Choose consistency over availability when data correctness is at stake, and be transparent with users.
  • Have tools to reconcile divergent writes. Restoring from backup took long, so restore time should be measured and practised.
Cloudflare 2019 outage: regular expression CPU exhaustion. What happened? Senior

What happened: In July 2019 Cloudflare's network returned 502 errors for roughly half an hour (per their report, as I remember). Traffic dropped sharply worldwide.

Root cause: a new rule deployed to the Web Application Firewall (WAF) contained a regular expression that exhibited catastrophic backtracking, using huge CPU on the machines that evaluated it. Because WAF rules were deployed globally and immediately (in a "simulate" mode, but the regex still ran), CPU on edge servers was exhausted everywhere at once. Recovery came from using a global kill switch to disable the WAF managed rules, then fixing the rule and the regex engine choice.

Lessons

  • Roll out even "safe" rule or config pushes progressively with canaries, not globally at once.
  • Use regex engines with linear-time guarantees (such as RE2-style) for untrusted or fast-changing patterns, or enforce CPU limits and timeouts per rule.
  • Have a fast global kill switch that works even when the platform is overloaded.
  • Test rules against production-like traffic and include performance tests in the change pipeline.
Facebook (Meta) October 2021 outage: BGP and DNS. What happened? Senior

What happened: In October 2021 Facebook, Instagram and WhatsApp were unreachable for around six hours. Engineers also had trouble reaching internal tools and even physical access was reportedly slowed, which prolonged recovery.

Root cause (per Facebook's engineering write-up): a command issued during routine maintenance of their backbone network unintentionally disconnected their data centers from each other. An audit tool that should have blocked the command had a bug. Their DNS servers, designed to withdraw their BGP route advertisements when they cannot reach the data centers (a health check), then did so. With the BGP routes withdrawn, the rest of the internet could no longer find Facebook's DNS servers, so the names stopped resolving.

Lessons

  • Out-of-band access: the tools and communications used for recovery must not depend on the systems being recovered (the internal tooling relied on the same network and DNS).
  • Safeguards that "fail safe" locally can be globally catastrophic: a health check that withdraws routes can make a partial fault total.
  • Guard rails and audit tools for dangerous network commands need to be tested too.
  • Independent monitoring and communication channels, and a rehearsed recovery for a total loss of the backbone.
Knight Capital (2012): what happened? Senior

What happened: In August 2012 the trading firm Knight Capital lost roughly 440 million dollars in under an hour (about 45 minutes) due to a faulty software deployment, which nearly ended the company.

Root cause (from the SEC findings and widely reported analyses): new code was deployed to eight servers for a new trading program, but the deployment reached only seven; one server kept old code. The new release reused a flag that, on the old code, activated a long-dead test routine (often described as "Power Peg"). On the one stale server that routine started sending a flood of unintended orders to the market. There was no kill switch ready and the team lacked a clear process to stop it; attempts to fix it by rolling back code on the other servers made things worse.

Lessons

  • Automate deployments and verify that every host has the same version.
  • Remove dead code; never repurpose an old flag for a new meaning.
  • Pre-trade risk limits and circuit breakers (a kill switch and exposure caps) independent from the strategy code.
  • Alerts and clear runbooks: errors and anomalous order flow appeared earlier but were not acted on.
  • Rolling back partial deploys can compound damage; know the right action beforehand.
GitLab (2017) database deletion and backup failures: what happened? Senior

What happened: In January 2017 GitLab.com lost about six hours of database data (issues, merge requests and so on, but not git repositories) and was down for many hours. GitLab publicly shared a candid post-mortem, and even live-streamed the recovery.

Root cause: while fighting a spam-driven load spike and replication lag, an engineer, tired and late at night, tried to resynchronize the secondary database, and ran a delete of the data directory on the primary instead of the secondary. Most of the data was removed before it was stopped. Then it turned out that none of the backup mechanisms was working as expected: regular backups had been failing silently (a version mismatch of the dump tool, with failure emails going unseen), disk snapshots were not enabled for that host, and the replication was the very thing that had broken. An engineer had luckily taken a manual snapshot about six hours earlier, which was used for recovery. (Details such as the exact number of backup methods are as I remember them.)

Lessons

  • A backup that has never been restored is not a backup; test restores and monitor backup jobs actively (a failed backup must page).
  • Destructive commands on production need guard rails: clear prompts showing the host name, separate credentials, and a second pair of eyes.
  • Do not do risky maintenance while exhausted; incident hygiene and on-call handover matter.
  • Replication is not backup (it also replicates deletions).
  • Radical transparency builds customer trust.
Google authentication outage (December 2020): what happened? Senior

What happened: In December 2020 many Google services (Gmail, YouTube, Drive and others) were unavailable for around 45 minutes because authentication failed.

Root cause (from Google's incident report, as I remember): an automated quota-management system, during a migration of the identity service's user-ID service to a new quota system, had a stale reported usage value of zero for that service. As a result the system reduced the service's allotted quota to near zero, so the authentication backend rejected requests, and everything that needed authentication failed. Safeguards that should have caught the mismatch did not apply because of the circumstances of the migration. The fix was to restore the quota.

Lessons

  • Automation that can shrink a critical resource needs sanity bounds (never reduce below a floor; reject a sudden drop to zero).
  • Shared identity or quota services are single points of failure for everything; give them special protection and independence.
  • Staged rollout and detection of mismatches between a system's real usage and its recorded usage.
  • Graceful degradation: authenticated sessions that can continue for a while without calling the authentication backend.
Roblox outage (October 2021): what happened? Senior

What happened: In late October 2021 Roblox was down for about 73 hours (I recall that number from their post-mortem; treat it as approximate).

Root cause (per Roblox's post-mortem, as I recall): their service discovery and configuration system, HashiCorp Consul, degraded. Two contributing factors were named: a recently enabled streaming feature in Consul that led to heavy contention on a single channel under high load, and performance problems in the BoltDB storage layer that Consul used for its write-ahead log (pathological behaviour with a large freelist after heavy write churn). Because nearly all of their services depended on Consul, the entire platform suffered, and the recovery was hard since the system needed Consul to bring itself back up.

Lessons

  • Core infrastructure (service discovery, config, secrets) is a dependency of everything; treat it as tier zero with its own capacity planning, isolation and rollback.
  • Avoid circular dependencies in the recovery path (the tools to fix it need the thing that is broken).
  • Roll out new features in the most critical component gradually; load test at your real scale.
  • Telemetry systems should not depend on the failing system; a hard-to-diagnose failure can last a long time without good observability.
Dyn DNS DDoS (October 2016): what happened? Intermediate

What happened: In October 2016 the DNS provider Dyn was hit by large DDoS attacks in several waves, and many major sites (Twitter, Netflix, Reddit, GitHub and others) were unreachable for many users, particularly in North America and parts of Europe.

Root cause: a volumetric attack, widely attributed to the Mirai botnet made up of compromised internet-of-things devices such as cameras and routers with default passwords, against Dyn's DNS infrastructure. Customers who used only Dyn as their DNS provider could not be resolved.

Lessons

  • Do not rely on one DNS provider: use multiple authoritative DNS providers for critical domains.
  • DNS TTL and resolver caching (longer TTLs helped some customers survive).
  • Third-party dependencies (even ones you do not see in the architecture diagram) are part of your availability.
  • Security of the wider ecosystem (weak IoT defaults) is a systemic risk.
Heartbleed (2014): what happened and what does it teach as a systemic lesson? Intermediate

What happened: In April 2014 a serious bug was disclosed in OpenSSL's implementation of the TLS heartbeat extension. A client could ask the server to echo back a payload and lie about its length; the server did not check, so it returned up to about 64 KB of adjacent memory, which could include private keys, session tokens and passwords. A large share of HTTPS servers was affected.

Root cause: a missing bounds check (a classic buffer over-read) in C code.

Lessons

  • Open-source critical infrastructure was underfunded and under-reviewed; this led to initiatives to fund it.
  • Memory-unsafe languages make this class of bug easy; consider memory-safe languages and fuzzing for security-critical parsers.
  • Incident response had to be broad: patch, then revoke and reissue certificates, rotate keys and invalidate sessions, since leaks cannot be detected.
  • Know your software bill of materials, to answer "where do we use this library?" quickly (the same question came again with Log4Shell in 2021).
  • Forward secrecy limits how much past traffic can be decrypted after a key leaks.
CrowdStrike (July 2024): what happened? Senior

What happened: On 19 July 2024 a faulty content update to CrowdStrike's Falcon endpoint security sensor caused a large number of Windows machines to crash with a blue screen and boot-loop. Airlines, hospitals, banks and media were disrupted worldwide, and recovery often required manual, hands-on fixes per machine (booting into safe mode and deleting a file).

Root cause (from CrowdStrike's published analysis, as I remember it): a rapid-response content configuration update contained data that the sensor's content interpreter handled incorrectly, causing an out-of-bounds memory read in kernel-level code (a mismatch in the number of input fields between the definition and the content, which validation did not catch). The update was released to all customers at once.

Lessons

  • Staged (canary) rollouts for every change, including data or content updates, with the ability to halt; CrowdStrike afterwards committed to staged deployment and customer control over update timing.
  • Code that runs in the kernel and loads on boot must be extremely defensive: a crash there means an unbootable machine, so failing safe (skip bad content) matters.
  • Validate content with the same rigour as code, including fuzzing and testing across real configurations.
  • Recovery needs to be possible at scale without manual hands-on work, such as remote recovery paths.
  • Concentration risk: a single vendor's agent on most of your fleet is a single point of failure.
Are there other incidents worth citing, and what is the general pattern? Intermediate
Others that are commonly cited (only headline level here, check details before quoting): the AWS Kinesis us-east-1 outage in November 2020, where a capacity addition pushed servers past an operating system thread limit and affected dependent services such as CloudWatch and Cognito (as I recall); Slack's outage on the first working day of January 2021, with load and network scaling issues around the AWS Transit Gateway during the return-to-work surge (headline only; I am less sure of the specifics); the Amazon Prime Day 2018 early issues with load and capacity; and the Cloudflare outage of November 2023 after a power-related event at a data center. Do not quote specifics you cannot verify. In an interview, name one or two you know well and focus on the pattern instead.

How do chaos engineering and game days reduce the chance of these incidents? Intermediate
Chaos engineering injects controlled failure (kill instances, add latency, drop a dependency, cut a zone) in a monitored way to verify the system degrades as designed. Game days rehearse humans and runbooks: failover a region, restore from backup, rotate a leaked key, run an incident with a time limit. They find hidden dependencies, untested restores and unclear ownership before a real incident does. Start in staging with a small blast radius, define a steady-state metric and an abort condition, then move to production gradually.
Which design principles would you list as defences against whole-platform outages? Senior
  • Limit blast radius: cells, shards, regions, per-tenant isolation, shuffle sharding.
  • Progressive delivery for code, config and data; automated health-gated rollout and rollback.
  • Fail fast and degrade gracefully: timeouts, circuit breakers, bulkheads, load shedding, fallbacks.
  • Static stability: the data plane keeps working when the control plane is down (keep serving with the last known config).
  • Independent recovery path: out-of-band access, tested backups, rehearsed rollback.
  • Observability: SLO alerting, traces, per-tenant metrics, synthetic probes from outside.
  • Human factors: blameless culture, guard rails on dangerous commands, clear on-call ownership and runbooks.
