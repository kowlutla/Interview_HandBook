Mental model: the 7 ideas everything hangs on

One line: Git is a content-addressed database of snapshots. A commit is a snapshot plus a parent link. A branch is just a movable label on a commit. Almost every command either adds objects or moves a label.
  1. Snapshots, not diffs. Each commit stores the full tree of files at that moment (shared with older commits when unchanged). Diffs are computed on demand.
  2. Content addressing. Every object is named by the hash of its content. Same content gives the same name. Change anything and the name changes.
  3. Commits form a graph (a DAG). Each commit points to its parent(s). History is that graph. It never has cycles.
  4. Refs are cheap labels. Branches, tags and remote-tracking branches are small files holding a commit hash. HEAD says which one you are on.
  5. Three local areas. Working tree (files you edit), index (the next commit you are building), repository (committed history). Plus a remote copy.
  6. Objects are immutable. "Rewriting history" means building new commits and moving a label. The old ones stay until garbage collection, which is why recovery usually works.
  7. Fetch is safe, push is the dangerous one. Fetch only adds to your local copy. Push changes a shared label. Most disasters are a push of the wrong thing.

1. Fundamentals and the object model

What is Git, and how is it different from SVN or Perforce? Basic

Git is a distributed version control system: every clone has the full history, so commit, log, diff and branch all work offline and fast. SVN and Perforce keep history on one central server and need it for most operations. Git also stores snapshots of the whole project, so a branch is only a pointer and costs almost nothing.

The problem version control solves. Several people change the same set of files over months. You need to know who changed what and why, be able to go back to any earlier state, and let people work in parallel without overwriting each other. A version control system (VCS) records that history. The old generation (CVS, SVN, Perforce) keeps the history on one central server, and a developer's laptop holds only the files of one version plus a few bookkeeping bits.

What "distributed" changes in practice. When you run git clone you get the whole database: every commit, every branch, every file version. That has concrete consequences:

  • Speed and offline work. git log, git diff, git blame and git commit read local files only, so they take milliseconds and work on a plane. In SVN each of those is a network round trip.
  • Cheap branching. A Git branch is a small pointer, so you create one for every task and delete it afterwards. Branching in old tools was heavy, so people avoided it and merges became painful.
  • Resilience. Every clone is a full backup. If the server dies, any clone can restore it.
  • Review before sharing. You commit locally, tidy the commits, and only then push. In SVN every commit is immediately public.

When Git is not the best fit. Very large binary assets (game art, video) with exclusive locks, or a single repo with millions of files and a need for per-directory permissions. Perforce still wins there. Git's answers are LFS, partial clone and sparse checkout, but they are add-ons.

What an interviewer probes next. "Is Git really not diff based?" At the logical level it stores snapshots. Inside packfiles (the compressed storage format) it uses delta compression between similar objects to save space, but that is a storage trick, not the data model.

Older tools mostly store "what changed per file per revision". Git stores the full tree at each commit and shares unchanged files between commits. In SVN a branch is a directory copy, in Perforce it is a server-side integration. The price of the Git model is that huge binary files and per-file locking are weak spots, which is why Git LFS and partial clone exist. "No central server" is true technically, but teams still agree that one remote (origin) is the source of truth.

Remember: Git = distributed + snapshots + cheap branches. Central tools = one server + file deltas.

Explain the working tree, the index (staging area) and the repository. Why is there a staging area? Basic

The working tree is the files I edit. The index (staging area) is the exact list of file versions that will go into my next commit. The repository is the saved history in .git. I use the index to build clean, focused commits out of a messy working tree.

Why three places and not two. Most tools have "my files" and "the saved history". Git adds a middle layer so that what you commit is a deliberate choice rather than "whatever is on disk right now". Imagine you fixed a bug and also started a half-finished refactor in the same file. With a staging area you commit the bug fix alone and keep working on the refactor.

A small walk-through. Suppose app.py is committed and clean.

  1. You edit it (add a line A). git status says "modified, not staged". git diff shows A, git diff --staged shows nothing.
  2. git add app.py. The file is now in the index. git diff shows nothing and git diff --staged shows A.
  3. You edit it again (add line B). Now the file is in both states: --staged shows A, plain git diff shows B.
  4. git commit records A only. B is still an unstaged change.

That "staged and modified at the same time" state surprises people, and interviewers like to ask about it. The fix is to remember that the index holds a copy of the file taken at add time.

Handy commands. git add -p lets you accept or reject each hunk. git restore --staged f removes a file from the next commit without touching your edits. git status -sb shows two letters per file (left = index vs HEAD, right = working tree vs index), for example MM means staged and modified again.

git add copies the current file contents into the index (file .git/index). git commit turns the index into a tree, wraps it in a commit, and moves the current branch. The index also stores file timestamps and sizes, so git status can skip files that did not change. Because three copies can differ, there are three different diffs:

git diff            # working tree vs index   (unstaged)
git diff --staged   # index vs last commit    (what will be committed)
git diff HEAD       # working tree vs last commit (both together)

A file can be both staged and modified: stage it, edit it again, and the commit gets the staged version only. git add -p stages only some hunks of a file.

Remember: edit, then add, then commit. A commit contains what is in the index, not what is on disk.

What are the four kinds of Git objects? Basic

Blob, tree, commit and annotated tag. A blob holds the bytes of one file. A tree is a directory listing that points to blobs and other trees. A commit points to one top-level tree plus its parent commits and the message. An annotated tag is a named pointer to another object, with its own message.

Why content addressing. Git is at heart a key-value store: the key is the SHA-1 (or SHA-256 in new repos) hash of the content, and the value is the content. Same bytes give the same key, so Git stores them once and can detect any corruption. Everything else in Git is built from just four kinds of values.

Walking through a tiny repo. Take a project with README and src/main.c:

  • The two files become two blobs. A blob has no name, no permissions, only the bytes.
  • The folder src becomes a tree with one line: 100644 blob 3a1f... main.c. The root folder is another tree with lines for README (a blob) and src (a tree).
  • The commit says: "my root tree is 9f1c..., my parent is 4be7..., author Asha, message ...".
  • An annotated tag says: "I name object 7c1a..., tagged by Asha on this date, message 'Release 1.0', optional signature".

Because the name is in the tree, renaming a file creates a new tree but reuses the same blob. Git does not record renames at all; tools like git log --follow and git blame -M detect them afterwards by comparing content.

Storage detail. New objects start as "loose" files under .git/objects/ab/cdef.... Later git gc packs many objects into one packfile and stores similar objects as deltas of each other, which is how a repo with large history stays small.

Try it. echo hello | git hash-object --stdin prints the blob id without storing anything. Run it on any machine and you get the same id, which is the whole point.

Pitfall. A tag object and a commit are different things. A lightweight tag is only a ref pointing to a commit and has no tag object. Only annotated tags are the fourth object type.

All four live in .git/objects, compressed, and are named by the hash of their content. File names are stored in the tree, not in the blob, so two files with the same content share one blob. An unchanged file is the same blob in every commit, which is why snapshots are cheap.

git cat-file -p HEAD         # tree, parent, author, message
git ls-tree -r HEAD          # every file with mode and blob hash

Git cannot store an empty directory (no blob to hold), so people add a .gitkeep file.

Remember: blob = file bytes, tree = folder, commit = snapshot + parents, tag = named pointer.

What exactly is inside a commit? Does it store a diff? Basic

No diff. A commit stores the hash of one root tree, the hashes of its parents, author and committer (name, email, time) and the message. It does not store the branch name either. The commit hash is computed from all of that text.

Why this matters. People say "a commit is a diff" because the UI shows a diff. That mental model breaks as soon as you do something advanced. If a commit were a diff, cherry-picking or rebasing would be trivial; in reality Git has to compute the diff between a commit and its parent, then apply it elsewhere. Seeing a commit as "a complete snapshot plus a pointer to its parent" explains why checkout is instant, why history is a graph, and why rebase creates new commits.

The fields, one by one.

  • tree: the id of the root directory snapshot. This one id pins the exact content of every file.
  • parent lines: zero for the first commit, one for a normal commit, two or more for a merge. These links form the history graph.
  • author: who wrote the change and when. committer: who created this commit object and when. They differ after rebase, cherry-pick, commit --amend by another person, or when a maintainer applies a patch from email.
  • message: free text. Gerrit adds a Change-Id footer, and platforms use Co-authored-by: lines.

The hash is computed from these exact lines. The commit id is the SHA of the text above, so changing even the commit message by one character changes the id. That is why --amend produces a different commit.

How a diff is shown. git show HEAD compares the commit's tree with its first parent's tree and prints the difference. For a merge it shows a "combined diff" by default. Because snapshots are compared, Git can also detect renames and moved lines even though it never stored them.

What the branch name has to do with it. Nothing. The commit does not know which branches contain it. That is why you can delete a branch and the commit survives, and why git branch --contains SHA has to search for you.

A root commit has no parent, a normal commit has one, a merge commit has two or more. Author and committer can differ: when someone rebases or cherry-picks your commit, you stay the author and they become the committer. A repo can have several root commits, for example after merging unrelated histories.

$ git cat-file -p HEAD

Remember: commit = tree + parents + author + committer + message. Diffs and branch names are not stored.

Why does rewriting one old commit change every commit after it? Intermediate

Because a commit's hash includes its parent's hash. If I change commit B, it gets a new hash. Commit C recorded the old B as its parent, so C must be rebuilt to point to the new B, and that gives C a new hash too. This continues up to the branch tip.

The idea in one sentence. Every commit id is the hash of its content, and its content includes the parent id, so ids chain together like blocks in a ledger. Change an early block and every later block's id changes.

A concrete example. History is A, B, C, D (D is the tip, main points to D). You want to fix a typo in the message of B with git rebase -i and reword.

  1. Git builds B' : same tree as B, same parent A, new message. New hash, because the message changed.
  2. C originally said "parent: B". Now C must say "parent: B'". Its text changed, so it gets a new hash C', although its files are identical.
  3. Same for D to D'.
  4. The label main moves from D to D'. A is untouched because nothing before B changed.

The old B, C and D still sit in the object store, now unreachable except through the reflog. You did not edit anything. You built a parallel history and moved a label.

Consequences you must be able to name.

  • Integrity: a tag or a commit id certifies the entire history below it. Signing one commit signs everything before it indirectly.
  • Rewriting costs more the further back you go. Rewording the commit at the tip changes one hash. Editing a commit 200 commits back rewrites 200.
  • Why force-push is a team problem. Your teammate has old C. The server now has C'. Same changes, different ids, so Git cannot tell they are "the same work" and treats them as divergent histories. A git pull then merges both and produces duplicates.
  • Why filtering a secret out of history is a big operation. Every commit after the secret gets a new id, so every clone, open PR and tag must be redone.

Probe: "Is Git a blockchain?" It shares the hash-chain idea, but it has no consensus, no mining and anyone with write access can move a label.

The file contents (blobs and trees) are reused. Only the commit objects are new. This hash chain makes history tamper-evident: nobody can quietly edit the past. It is also why force-pushing a rewritten branch hurts teammates: their old commits and your new ones no longer share hashes, so Git sees two different histories.

Remember: parent hash is part of the child's hash, so one change ripples to the tip.

What is a branch, really? Why is creating one so cheap? Basic

A branch is just a tiny file holding one commit hash. Creating a branch writes that small file and copies nothing. "Being on a branch" means that when I commit, Git makes the new commit and moves that file to it.

Why it is cheap. In older tools, creating a branch meant copying a directory, so people avoided it. In Git the history already is a graph of immutable commits, so a branch needs only one fact: "which commit is my tip?". That fact is a single hash stored in a 41-byte file.

What happens when you commit.

  1. .git/HEAD contains ref: refs/heads/main, so Git knows you are "on main".
  2. git commit creates commit E whose parent is the commit currently stored in refs/heads/main (say D).
  3. Git overwrites that file with the hash of E. Nothing else changes.

So "a branch grows" simply means "its label moves forward when you commit while on it". Other branches do not move.

Commands that show it.

cat .git/refs/heads/main      # prints one 40 character hash
git branch feature            # writes .git/refs/heads/feature with the same hash
git branch -d feature         # deletes only the label (refuses if unmerged)
git branch -D feature         # force delete, commits become unreachable
git branch -vv                # tip commit and upstream per branch

Common confusion. People think a branch "contains" commits like a folder. It does not. A commit is on a branch only in the sense that you can reach it by following parent links from the label. That is why two branches can share all older commits without any copying.

Local versus remote. main is yours and moves when you commit. origin/main is a read-only copy of the server's label that moves only on fetch, pull or push.

Pitfall. git branch -D on a branch with unpushed work orphans those commits. The reflog still holds them for weeks, but you should know the hash or find it with git reflog.

The file is .git/refs/heads/<name>, about 41 bytes (or a line in packed-refs). Deleting a branch deletes only the label. Commits no longer reachable from any label stay on disk until garbage collection, which by default waits weeks, so a deleted branch is usually recoverable.

Remember: a branch is a 41-byte label on a commit. Moving it is cheap, deleting it deletes no commits.

What is HEAD? What do HEAD~1, HEAD^, HEAD^2 and HEAD@{1} mean? Basic

HEAD is "where I am now": normally a pointer to the current branch, which points to a commit. HEAD~1 and HEAD^ both mean the first parent. HEAD^2 means the second parent of a merge commit, the branch that was merged in. HEAD@{1} is different: it means where HEAD was one move ago, taken from the reflog.

HEAD as "you are here". HEAD is Git's cursor. Normally it holds the name of a branch (a symbolic reference), and that branch holds a commit. So "HEAD" means "the tip of the branch I am on". When it holds a bare hash instead, that is the detached state. Many commands default to HEAD: git diff compares to HEAD, git commit uses it as the parent, git reset moves what it points to.

Two different navigation systems. Interviewers test whether you can keep these apart.

They can be combined: HEAD~2^2 is "go back two first-parents, then take the second parent of that commit".

Worked example. You are on main at merge commit M. M merged feature into main. Then HEAD^1 is the last commit of main before the merge, and HEAD^2 is the last commit of feature. To see what the merge brought in: git log HEAD^1..HEAD^2 or git diff HEAD^1 HEAD. git revert -m 1 M says "keep parent 1 as the mainline".

Why @{} is a separate thing. After git checkout feature, HEAD@{1} is the commit you were on before, even though it is not an ancestor of feature. That is the key to git reset --hard HEAD@{1} as an undo button. The reflog is per clone, so a teammate's HEAD@{1} is different.

Shell gotchas. On Windows cmd the caret must be doubled (HEAD^^), and in PowerShell you quote "HEAD@{1}". ~ avoids the problem.

.git/HEAD usually contains ref: refs/heads/main. ~N walks N steps back along first parents. ^N chooses which parent of one commit. They are the same for ordinary commits and differ only on merges. @{n} and main@{yesterday} use your local reflog, not ancestry.

Watch out: HEAD@{1} is "previous position of HEAD" (could be on another branch), not "the parent".

Remember: ~ goes back along first parents, ^ picks a parent, @{} reads the reflog.

What happens inside Git when you run git add and git commit? Intermediate

git add writes the file content as a blob object and records its hash in the index. git commit builds tree objects from the index, creates a commit pointing to that tree and to the current commit as parent, then moves the current branch to the new commit.

Why look inside. This is the question that proves you know that Git is a content store with pointers on top. Walk through it as a story and it sticks.

Step 1: git add a.txt.

  1. Git reads the file and computes its hash, using a header like "blob 3" plus the bytes.
  2. It compresses the content and writes it to .git/objects/xx/yyyy... as a blob. If that blob already exists (the same content was seen before), nothing new is written.
  3. It updates .git/index with a line: file name, mode, blob hash, size and timestamp.

Step 2: git commit -m "add a".

  1. Pre-commit and commit-msg hooks run. If a hook fails, nothing is written.
  2. Git converts the index into tree objects, one per directory, writing the deepest folders first, then the root tree. Unchanged folders reuse the existing tree id.
  3. It writes the commit object: root tree id, parent = what HEAD resolves to, author, committer, message.
  4. It moves the branch that HEAD points to (refs/heads/main) to the new commit and appends a line to the reflog.

You can watch this: git cat-file -p HEAD shows the commit, git cat-file -p HEAD^{tree} shows the root tree, and git ls-files --stage prints the index.

Consequences.

  • A commit is fast because it writes only the changed blobs and the trees on the path to them.
  • A secret that was added but never committed already sits in the object store as a blob. Unstaging it does not remove it until gc prunes it.
  • A file edited after add is committed in its added state. That is the reason for the "staged and modified" status.
  • git commit -a only auto-stages files already tracked. A brand-new file needs an explicit git add.

Detail: trees are written bottom up, one per directory. A line is appended to the reflog. Hooks such as pre-commit and commit-msg run before the commit object is made. If I add a file and edit it again before committing, the commit holds the version from the time of add. commit -a stages changes to already-tracked files first; new files are not included.

echo hi > a.txt
git add a.txt            # blob created, index updated
git commit -m "add a"    # tree + commit created, main moves

Remember: add = blob + index entry. Commit = tree + commit + branch moves.

git checkout does too many things. What replaced it? Basic

Since Git 2.23, git switch changes branches and git restore restores files. The old checkout did both and also detached HEAD, which confused people. It still works.

Why the split happened. git checkout grew two unrelated jobs under one name. git checkout feature moves HEAD to another branch (safe, refuses if it would lose changes). git checkout -- file overwrites a file from the index (destructive, no warning). Beginners typed one when they meant the other, and a typo like git checkout main file silently replaced files. Git 2.23 introduced two commands with clearer names. It also marked them experimental at first, so their exact behaviour could still change in rare cases.

What happens when you switch with uncommitted changes. If the files you changed are identical in both branches, they come along. If the target branch has a different version of a file you modified, Git refuses with "Your local changes would be overwritten". Then you commit, stash, or use git switch --merge to try to carry them over (it can produce conflicts).

Which of these are dangerous? Only the ones that touch the working tree and overwrite files: git restore file and git checkout -- file. They throw away changes that exist nowhere else. git restore --staged is safe, because your edits remain in the working tree and only the staging is undone.

Tip. git restore -p asks hunk by hunk, a good way to discard only part of your edits. Interviewers also ask what git checkout still does that these do not: it still works on old Git versions and in older scripts, so you will see it in docs and CI files.

git switch -c fix/login          # create and switch
git switch -                     # back to previous branch
git switch --detach v1.4.0       # look at a tag, no branch
git restore --staged app.py      # unstage
git restore app.py               # discard edits (cannot be undone)
git restore --source=HEAD~2 app.py   # file from an older commit

Key safety fact: restoring the working tree overwrites uncommitted work, and that data was never in a commit, so there is no way back.

Remember: switch = branches, restore = files. Discarding uncommitted edits is permanent.

2. Branches and merging

What is a fast-forward merge, and when does Git create a merge commit instead? Basic

If the branch I merge into has not moved since the other branch split off, Git just slides my branch label forward. That is a fast-forward: no new commit and the history stays a straight line. If both branches have new commits, Git does a three-way merge and records a merge commit with two parents.

Start from the situation. You branched feature off main at commit B. While you worked, did anybody add commits to main? That one question decides everything.

  • No. main is still at B, which is an ancestor of feature. Merging means "move the main label forward to the feature tip". Git does not need to combine anything, so no new commit is made. This is a fast-forward.
  • Yes. Both lines have commits the other lacks (they have diverged). Git must combine the two sets of changes, and records the result as a merge commit with two parents. If the changes touch different places, it succeeds on its own, otherwise you resolve conflicts.

Why choose --no-ff even when a fast-forward is possible. A fast-forward erases the fact that a group of commits was developed together. With --no-ff you get a merge commit M whose second parent is the feature tip, so "everything this feature did" is visible as one unit, and you can undo it with git revert -m 1 M. The cost is a busier graph.

Why choose --ff-only. It gives you a safety net: either history stays linear or the command fails and you decide what to do (usually rebase first). It is also the safest way to update a branch that should only mirror another, like your fork's main from upstream/main.

Quick test to tell what will happen. git merge-base main feature prints the common ancestor. If it equals main's tip, a fast-forward is possible.

Pitfall. git pull does a merge underneath, so a plain pull on a diverged branch silently creates a merge commit "Merge branch 'main' of origin". That is why teams set pull.ff only or pull.rebase true.

I can force a merge commit with --no-ff, which leaves a visible "this feature landed together" point that is easy to revert as one unit. I can refuse anything but a fast-forward with --ff-only, and make that the default with git config merge.ff only.

git merge feature            # ff if possible, else merge commit
git merge --no-ff feature    # always a merge commit
git merge --ff-only feature  # fail instead of creating a merge commit

Remember: fast-forward = move a label. Diverged branches = merge commit with two parents.

How does a three-way merge decide what to keep? What is the merge base? Intermediate

Git finds the merge base, the best common ancestor of the two tips. For each file it compares base to ours and base to theirs. If only one side changed a region, Git takes that change. If both changed the same region differently, that is a conflict and a human decides.

Why two versions are not enough. Imagine timeout is 30 in my file and 10 in yours. Who is right? With only two files, Git cannot know. If it knows the original was 10, it can see I changed it to 30 while you did nothing, so 30 wins. The original is the merge base, the most recent commit that both branches have in their history.

The algorithm, per region of each file.

baseourstheirsresult
xxxx (nobody changed it)

Git also works on whole files: if one side deleted a file and the other edited it, that is a conflict too, as is a file renamed on one side and edited on the other. Rename detection is by content similarity, so the edit usually follows the rename correctly.

Which base? Git computes it as the best common ancestor. After a criss-cross (two branches merged into each other) there can be two or more equally good ancestors. The ort strategy (default since Git 2.34, replacing recursive) merges those ancestors into a temporary virtual base first, which gives fewer false conflicts. You can inspect candidates with git merge-base --all A B.

What a clean merge does not promise. Git works on lines. If I rename a method in one file and you add a new call to the old name in another, there is no textual overlap, Git merges cleanly and the build breaks. So the merged result must always be compiled and tested, and that is the reason CI runs on the merge result of a PR.

Handy. git diff main...feature (three dots) shows what feature changed since the merge base, exactly the diff a PR displays.

The base is what lets Git tell "I changed this" from "they changed this". A plain two-way compare cannot do that. If the same change was made on both sides, it is taken once. Git merges text lines, not meaning, so a merge can be clean and still break the build. That is why CI should run on the merged result. With several possible bases (criss-cross merges) the default ort strategy first merges the bases into a virtual one.

git merge-base main feature     # show the base commit

Remember: one side changed, take it. Both changed the same spot differently, conflict.

You get a merge conflict. What exactly do you do? Basic

I run git status to see the "both modified" files, open each one, and decide the final content between the conflict markers. Often it is a mix of both sides. Then I remove the markers, build and test, git add the files, and finish with git commit (or git rebase --continue in a rebase). If it goes badly, git merge --abort takes me back to before the merge.

What a conflict is. It is not an error. Git is saying "both sides changed this exact spot differently and I will not guess". It stops the merge half way, leaves the clean parts staged, and marks the conflicted parts in the file.

Reading the markers. Between <<<<<<< and ======= is the version from the branch you are on (HEAD, "ours"). Between ======= and >>>>>>> is the version from the branch being merged ("theirs"). With diff3 or zdiff3 style a third block shows the original, which often makes the right answer obvious: if the base is X, ours is Y and theirs is X-with-a-tweak, you probably want Y plus the tweak.

The process, step by step.

  1. git status lists "Unmerged paths" with "both modified" for each file.
  2. Open a file and find every marker block. Decide the final text. This can be ours, theirs, or a hand-merged blend. Delete the three marker lines.
  3. Rebuild and run the tests. A conflict means two people touched related logic, so the combined code can be wrong even if it compiles.
  4. git add file tells Git "this file is resolved". git status should show no unmerged paths.
  5. Finish with git commit (the merge message is prefilled), or git rebase --continue / git cherry-pick --continue if the conflict came from those commands.

Tools that help. git mergetool opens a three-pane editor. IDEs have the same. git checkout --conflict=diff3 file restores the markers if you resolved wrongly and want to start over for that file. git diff during a conflict shows a combined diff of only the disputed regions. Turn on rerere (reuse recorded resolution) if you rebase often: Git remembers how you resolved a conflict and replays it.

Good etiquette. If you do not understand the other side's change, ask its author. Choosing wrongly can quietly delete a teammate's fix. Never resolve with "accept all mine" to make red go away.

I set merge.conflictStyle zdiff3 (Git 2.35+, diff3 on older) so the markers also show the base text, which makes the decision much easier. If I do not understand the other change, I ask its author.

In a conflict, which side is "ours" and which is "theirs"? Why is it swapped during rebase? Intermediate

In a merge, "ours" is the branch I am on and "theirs" is the branch I merge in. In a rebase it looks swapped: "ours" is the branch I am rebasing onto, and "theirs" is my own commit being replayed. The rule is the same in both: "ours" is whatever HEAD currently is.

The definition that never changes. "Ours" is the version in the commit that HEAD currently is. "Theirs" is the version from the commit being brought in. The naming works naturally for a merge, because you stand on your branch (HEAD) and pull another one in.

Why a rebase flips it. A rebase does not edit your commits in place. It does this:

  1. Moves HEAD to the new base (for git rebase main, the tip of main).
  2. Takes your first commit and re-applies its change on top (a cherry-pick). If it conflicts, HEAD is main plus the commits already replayed, so "ours" = the upstream side, and "theirs" = the commit being replayed, which is your original work.
  3. Repeats for each of your commits.

The mental translation: during a rebase, ours = the branch I am rebasing onto, theirs = my own work. In a merge it is the opposite way round.

Operation"ours""theirs"
git merge feature (on main)mainfeature
git rebase main (on feature)main (the new base)my feature commit being replayed
git cherry-pick Xmy current branchcommit X

Safer habits. Read the marker labels (the part after <<<<<<< and >>>>>>> shows branch or commit names), or avoid the keyword entirely and open the file in a three-way tool. Also separate two things: git checkout --ours file takes a whole file from one side, while the merge options -X ours and -X theirs only decide conflicting hunks and still merge the rest. Both can silently drop a colleague's work, so use them knowingly. (Do not confuse -X ours with the -s ours strategy, which ignores the other side completely.)

During a rebase Git first moves HEAD to the new base (say updated main), then replays my commits one at a time on top of it. So HEAD is main's version and the incoming change is mine. To avoid mistakes I read the marker labels and avoid --ours and --theirs during a rebase unless I am sure.

# during rebase onto main, keep MY version of the file:
git checkout --theirs path/file
# during a merge of feature into main, keep the main version:
git checkout --ours path/file

Remember: ours = HEAD. In a rebase, HEAD is the base, so my own commits are "theirs".

Merge commit, squash merge, rebase merge: what is the difference, and which would you pick? Intermediate

A merge commit keeps every branch commit and adds one joining commit. A squash merge turns the whole branch into one new commit on main. A rebase merge replays each commit onto main with new hashes. I pick squash for teams with messy work-in-progress commits, merge commits for long-lived or release branches, and rebase merge only when each commit is clean and builds.

How to decide.

  • Each commit is a careful, buildable step (kernel style, or a refactor sequence you want to preserve)? Use rebase merge.
  • Long-lived branches, release branches, or merging main into a release branch? Use a real merge commit. Squashing those would break the ancestry link that later merges depend on.

The trap with squash. Because the feature branch's commits are not ancestors of main, Git does not know the branch is merged. Trade-offs. Merge commit: full fidelity but noisy graph. Squash: clean, one commit per PR and easy revert, but individual commits are lost. Rebase merge: linear with all commits, but every hash changes, and a non-green middle commit breaks bisect.

What is a detached HEAD, and how do you not lose work in it? Basic

Detached HEAD means HEAD points straight at a commit instead of at a branch. It happens when I check out a tag or a hash, and during rebase or bisect. Commits I make there have no branch, so after I switch away they look lost. To keep them I create a branch right there: git switch -c rescue.

What it means. Normally HEAD says "I am on branch main", and a new commit moves main. In detached state HEAD holds a raw commit id. A new commit still gets created, with the current commit as parent, and HEAD moves to it, but no branch label moves with it. The new commits are therefore reachable only through HEAD.

When it happens, on purpose or not.

  • git switch --detach v1.4.0 or git checkout <hash> to look at or build an old version.
  • During a rebase (HEAD detaches while commits are replayed), a bisect, or a cherry-pick sequence.
  • Checking out origin/main directly instead of creating a local tracking branch.
  • Submodules, which are checked out at a pinned commit by default.

The danger. As soon as you switch to another branch, nothing points to your detached commits. They are "unreachable". Git prints a warning ("you are leaving 2 commits behind") with the hash of the last one. If you scroll past it, you must find the hash later through the reflog. After about 30 days the garbage collector may delete them for good.

Three ways to keep the work.

  1. Before leaving: git switch -c rescue. This puts a label on the current commit.
  2. After leaving: copy the hash from the warning or git reflog, then git branch rescue HASH.
  3. Bring it into another branch: git switch main then git cherry-pick HASH or git merge HASH.

When to use detached HEAD happily. Experiments you intend to throw away: check out the old tag, try a patch, run the build, then switch back. Nothing is lost because you never intended to keep it.

If I already left, the commits are still in the reflog for weeks: git reflog to find the hash, then git branch rescue HASH. Detached HEAD is useful for inspecting an old release or running a build of a tag.

Remember: commits with no label get lost. Name them with a branch before you leave.

3. Rebase and history

What is the difference between merge and rebase? Basic

Merge joins two branches with a merge commit and keeps history exactly as it happened. Rebase re-applies my commits on top of the new base, so history becomes a straight line, but those commits get new hashes. I rebase my own private branches and merge shared ones.

Same goal, different history. You are on feature, and main has moved on. You want your branch to include the new main commits. There are two ways:

  • Merge: git merge main creates one new commit with two parents. All existing commits keep their hashes. The graph shows that you worked in parallel.
  • Rebase: git rebase main finds your commits (those not on main), sets them aside, moves your branch to the tip of main, and replays them one by one on top. The new commits C', D' have the same changes and messages, but new parents and so new hashes. The graph looks as if you started work today.

How I choose. Before I open a PR, my own branch is private, so I rebase it on main (clean, no noise merges). Once teammates have the branch, I merge. For integrating a finished feature into main, the team policy decides (merge, squash or rebase merge).

Pitfalls. Rebasing a branch that others have pulled; rebasing across a big merge commit (the merge is dropped and flattened unless you use --rebase-merges); and forgetting to force-push after rebasing a branch that is already on the server. Use --force-with-lease for that push.

A common sentence: "Rebase changes where my work starts; merge records that two lines joined." Both give the same final files.

The content is the same either way. Rebase gives cleaner history, and merge is safer because it never rewrites anything. The old commits stay in the object store and reflog until garbage collection.

Remember: merge keeps history, rebase rewrites it. Never rebase what others already have.

What is the "golden rule of rebase", and what actually goes wrong if you break it? Intermediate

Never rebase commits that other people already have. Rebase makes copies with new hashes, and I then have to force-push to replace the originals. A teammate who pulled the old commits now has history that has diverged from mine.

Why the rule exists. A rebase does not move commits, it creates new ones with different ids (because the parent changed, see the hash chain). Once other people have the old ids, any rewrite creates two versions of the same work in the world, and Git has no way to know they are the same.

A timeline of the damage.

  1. Asha and Ravi both pull branch feature, at commits A-B-C.
  2. Asha rebases feature onto a newer main and force-pushes. The server now has A'-B'-C'.
  3. Ravi, who still has A-B-C and adds D, runs git pull. Git sees his history and the server's history diverge right after main. It merges them.
  4. Ravi's branch now contains A, B, C, A', B', C' and D. Changes appear twice, conflicts reappear, and a file Asha deliberately removed in B' may come back from B.

Fixing it needs Ravi to rebase his D onto the new history with git rebase --onto origin/feature OLD_C D. Teams lose hours here.

The rule in practice.

  • Safe: your private branch, or a PR branch only you push to. Reviewers who just read it are not affected, although inline review comments may become outdated.
  • Agree first: a shared feature branch. Tell the team, ask everyone to push their work, rewrite once, then each person does git fetch and git reset --hard origin/feature (after saving anything unpushed).
  • Never: main, release branches, tags that were published.

The safety net. Branch protection that blocks force pushes on shared branches turns the golden rule into something the server enforces, which is how mature teams run it. --force-with-lease also stops you from overwriting a teammate's new push.

If they then pull with merge, both the old and the new versions of the same changes get merged: duplicate commits, repeated conflicts, and sometimes already-removed work coming back. I only rewrite branches that I own. For a shared feature branch I agree it with the team first, and always push with --force-with-lease. My own open PR branch is normally fine to rebase.

Remember: rewrite only what is yours. Force pushes belong to your own branches.

I finished a rebase and it is wrong. How do I undo it? Intermediate

If nothing else has happened since, git reset --hard ORIG_HEAD puts the branch back to where it was before the rebase. Otherwise I look in git reflog, find the entry just before "rebase (start)" and reset to that hash.

Why undoing a rebase is almost always possible. A rebase builds copies of your commits and finally moves the branch label to the last copy. The original commits are still in the object database, just no longer pointed at by the branch. You only need the id of the old tip.

Three ways to find that id.

  1. ORIG_HEAD. Commands that move HEAD dramatically (rebase, merge, reset) save the old position there. Right after the rebase, git reset --hard ORIG_HEAD restores it. The next such command overwrites ORIG_HEAD, so do it quickly.
  2. The reflog. git reflog lists entries. Find rebase (start): checkout main and take the entry just below it, which is the branch state before the rebase. Reset to that entry.
  3. The branch reflog. git reflog show feature is shorter, because it only lists the movement of that branch. feature@{1} is "feature one move ago".
$ git reflog
a1b2c3d HEAD@{0}: rebase (finish): returning to refs/heads/feature
9f8e7d6 HEAD@{1}: rebase (pick): Add validation
...
4be7d2a HEAD@{6}: rebase (start): checkout main
c0ffee1 HEAD@{7}: commit: Add validation     <- my state before the rebase
$ git reset --hard HEAD@{7}

If the rebased branch was pushed. Remote still has the new commits. After the local reset you need git push --force-with-lease to put the old ones back, and that is a rewrite, so tell anyone who may have fetched in the meantime.

Check before resetting. Compare with git diff HEAD@{7} HEAD or git range-diff to see what the rebase actually changed. Sometimes the rebase was right and only one conflict resolution was wrong, and then a small fix commit beats a full undo.

Pitfall. reset --hard also throws away uncommitted edits. Commit or stash first.

This works because rebase only copies commits and moves a label. The originals still exist until garbage collection. If I already force-pushed, I reset locally and force-push again with --force-with-lease, after telling anyone who pulled in between.

git reflog                       # find "rebase (start)" and the line above it
git reset --hard HEAD@{5}        # or the hash you found

Remember: rebase never destroys the old commits quickly. ORIG_HEAD or reflog finds them.

What can you do with git rebase -i? Intermediate

git rebase -i main opens a list of my commits, oldest first, and I change the verb on each line. I use it to squash small commits, reword messages, reorder, drop a commit, or stop to split one. I do this before opening a PR so reviewers see a clean story.

What it does. git rebase -i main takes every commit in main..HEAD, writes one line each (oldest at the top) in your editor, and then replays them according to the commands you edit. It is the tool to turn a messy working history into a series that a reviewer can read.

A typical clean-up, step by step. The branch has five commits: "Add parser", "wip", "fix typo in parser", "Add validation", "remove debug print". You open git rebase -i main and change the list to:

pick   a1b2c3 Add parser
fixup  b2c3d4 wip
fixup  c3d4e5 fix typo in parser
pick   d4e5f6 Add validation
fixup  e5f6a7 remove debug print   # folds into the commit above it

After saving, Git replays and the result is two commits (note: fixup melds into the nearest pick above it, so reorder lines if a fixup belongs to an earlier commit; use drop to delete a commit entirely). Each line is applied in order; if a step conflicts the rebase stops, you fix it and run git rebase --continue.

The shortcut: fixup commits. When review feedback concerns an older commit, run git commit --fixup=a1b2c3. This creates a commit named "fixup! Add parser". Later git rebase -i --autosquash main moves it right after its target and marks it fixup automatically. Set rebase.autoSquash true and you never reorder by hand.

The verbs, in one line each. pick keep; reword keep, new message; edit stop here so you can change the content or split it; squash merge into the commit above and edit the combined message; fixup same but discard this message; drop delete; exec run a shell command (put tests after each commit to prove every commit builds); break pause. Reordering lines reorders commits.

Cautions. It rewrites history, so it is for unshared commits (or branches you own). Reordering commits that touch the same lines causes conflicts. If you panic: git rebase --abort. After a bad one: ORIG_HEAD or reflog.

  • pick keep it, reword change the message, edit stop to amend or split.
  • squash meld into the previous commit and combine messages, fixup same but drop its message.
  • drop remove it. exec cmd runs a command after a step, for example the tests.
pick   a1b2c3 Add parser
fixup  d4e5f6 typo

drop   0f1e2d debug logging
exec   mvn -q test

To split a commit: mark it edit, run git reset HEAD^, stage and commit in pieces, then git rebase --continue. An empty todo list aborts the rebase.

Remember: pick, reword, edit, squash, fixup, drop. Only on commits not yet shared.

Explain git rebase --onto with a real example. Senior

git rebase --onto NEWBASE OLDBASE BRANCH replays the commits in OLDBASE..BRANCH on top of NEWBASE. It lets me move a slice of history. Typical case: topic-b was built on topic-a, topic-a got squash-merged to main, so I run git rebase --onto main topic-a topic-b to move only topic-b's own commits.

The plain form first. git rebase main means "take the commits that are on my branch but not on main and replay them on main". Git decides "which commits are mine" by itself, using main as the cut point. The three-argument form lets you specify that cut point.

Syntax in words. git rebase --onto NEWBASE UPSTREAM BRANCH = "take the commits that are reachable from BRANCH but not from UPSTREAM, and replay them on NEWBASE". Read it as: "move these commits (after UPSTREAM, up to BRANCH) onto NEWBASE". If you leave BRANCH out, it is the current branch.

Why you need it, using the page's example. topic-b was created from topic-a (commits A1, A2, then B1, B2). Then topic-a was squash-merged into main as a single new commit N. History on main does not contain A1 and A2, only N, which has the same content under another id. If you run git rebase main on topic-b, Git thinks A1, A2, B1, B2 are all yours, replays all four, and A1/A2 conflict with N (which already has their changes). With --onto you say "my commits start after A2":

git rebase --onto main topic-a topic-b
# replays topic-a..topic-b = B1, B2 onto main

Other uses.

  • Remove a range from the middle: branch has commits 1-2-3-4-5 and you want to drop 3-4. git rebase --onto 2 4 branch (commits after 4, replayed on 2).
  • Move a branch to start from a different base, for example from develop to release/1.4 when the work should have been based on the release: git rebase --onto release/1.4 develop feature.
  • Recover from the golden-rule situation where a teammate's base was rewritten (see the golden rule answer).

Check first. git log --oneline UPSTREAM..BRANCH lists exactly the commits that will move. If that list is wrong, the rebase will be wrong.

A plain git rebase main here would also replay topic-a's old commits and conflict with their squashed copy. The same tool can cut a range out of the middle of a branch.

Remember: --onto NEW OLD BRANCH = move the commits between OLD and BRANCH to NEW.

You are mid-rebase, with conflicts. What commands do you have, and what if you get lost? Intermediate

Fix the files, git add them, then git rebase --continue. --skip drops the current commit, for when upstream already has the same change. --abort returns everything to how it was before the rebase and is always safe. If I am lost, I abort and try a simpler route.

What state you are in. Git is replaying your commits one at a time. It stopped on commit number N because applying it on the new base conflicts. Git remembers the todo list in .git/rebase-merge/. Your branch is temporarily detached at the half-replayed result.

The loop.

  1. git status shows "interactive rebase in progress; onto abc123; Last command done (3 of 7)" and the conflicted files.
  2. Resolve each file (remember the ours/theirs swap), then git add it.
  3. git rebase --continue. Git creates the commit and moves to the next, which may conflict again.
  4. At the end the branch label moves to the last new commit.

What does git pull do, and should you use pull --rebase? Intermediate

git pull is git fetch plus a merge. If I have local commits and the remote also moved, that creates a noisy "Merge branch main of origin" commit. I prefer git pull --rebase, or pull --ff-only, so I choose what happens and history stays linear.

What pull really is. git pull = git fetch followed by an integration step into the current branch. The integration is a merge by default. Whether this is good depends on what happened locally.

  • I have no new local commits: the merge is a fast-forward, my branch just moves up. Fine.
  • I have local commits and the remote also moved: the branches have diverged. A merge produces "Merge branch 'main' of origin/main" commit that carries no meaning. A project with many developers fills up with these.

git pull --ff-only          # fail instead of creating a hidden merge

Remember: pull = fetch + merge. Prefer rebase or ff-only to avoid noise merges.

4. Remotes and workflows

What is a remote, and what is a remote-tracking branch like origin/main? Basic

A remote is a named URL in my config, and origin is just the default name from git clone. A remote-tracking branch like origin/main is a read-only local label that records where main was on the server the last time I talked to it. Only fetch, pull and push move it, so it can be stale.

Three things with similar names. Beginners mix them up, so separate them clearly.

Why remote-tracking branches exist. They let Git compare "what I have" and "what the server had" without a network call. git status says "Your branch is ahead of 'origin/main' by 2 commits" by comparing two local labels. That is also why the message can be out of date: nobody told Git about new server commits until you run git fetch.

Upstream (tracking) relation. Each local branch can name one remote-tracking branch as its upstream (branch.main.remote and branch.main.merge in config). It is used as the default for git pull, git push (depending on push.default), git status and the shortcut @{u}. git push -u origin feature sets it the first time. git branch -vv prints it with ahead/behind counts.

Examples. git log origin/main..main lists commits I have not pushed. git log main..origin/main lists commits that I have not merged. git remote show origin queries the server and reports branches that are stale.

Housekeeping. When someone deletes a branch on the server, your origin/feature stays until you run git fetch --prune. Set fetch.prune true so this happens automatically. A repo can have several remotes (origin, upstream, a colleague's fork), each with its own set of tracking branches.

A local branch can have an upstream, which links it to a remote-tracking branch. That link is what makes plain git pull, git push and the "ahead 2, behind 1" line in git status work.

git remote -v
git branch -vv                       # upstream and ahead/behind per branch
git push -u origin feature           # push and set upstream
git config --global push.autoSetupRemote true   # Git 2.37+

Remember: origin/main is my last known copy of the server, not the server itself.

What is the difference between fetch, pull and clone? Basic

clone copies the whole repository and sets up origin. fetch downloads new commits and updates my origin/* labels, but never touches my branches or files, so it is always safe. pull is fetch plus a merge or rebase into my current branch, so it can change my files and cause conflicts.

Why the distinction matters. Fetch is a read of the remote. It cannot hurt your work. Pull also modifies your current branch and the files in your working tree, so it can fail with conflicts or, worse, silently merge something unexpected. A careful person fetches, looks, then integrates.

What each command does, step by step.

  1. git clone URL: creates a directory, runs git init, registers origin, downloads all objects and all branches as origin/*, creates one local branch (the remote's default branch) set to track its remote branch, and checks it out.
  2. git fetch: asks the server which labels have moved, downloads the missing objects, updates origin/*. Your local branches and files do not change. It also fetches tags that point into the downloaded history.
  3. git pull: runs fetch and then merge origin/main into the current branch (or rebase, depending on configuration).

The safe routine.

git fetch
git log --oneline HEAD..origin/main     # what is new on the server?
git diff HEAD...origin/main --stat      # what files changed?
git merge --ff-only origin/main         # or: git rebase origin/main

Related ideas. git fetch origin main:main updates the local main directly if it is a fast-forward, without switching to it. git fetch --all contacts every remote. git push is the reverse direction and the only one that changes the server.

Pitfall. People think git pull "gets the latest" with no risk. If you have local commits and uncommitted changes, it can stop half-way. Use --autostash or commit first.

A careful habit: fetch first, look at what came in with git log HEAD..origin/main, then decide to merge, rebase or wait.

Remember: fetch looks, pull changes my branch. Fetch first when in doubt.

Your push is rejected with "non-fast-forward" or "fetch first". What does it mean and what do you do? Basic

It means the remote branch has commits I do not have, so moving it to my commit would throw those away. Git only allows a push that fast-forwards. I run git fetch, then git rebase origin/feature (or merge), test, and push again. I do not reach for --force, because that would delete my colleague's commits from the server.

Why the server says no. A push means "make remote branch X point to my commit". The server accepts this only if my commit already includes the commit X currently points to, so that the move is a fast-forward and no existing commit becomes unreachable. If someone else pushed in the meantime, my commit is missing their commit, so accepting would erase it. Git prints ! [rejected] main -> main (fetch first) (the remote has commits you lack) or (non-fast-forward) (your local branch diverged from its remote counterpart).

The fix, step by step.

  1. git fetch to download their commits.
  2. Look: git log --oneline HEAD..origin/feature, so you know what you are about to combine with.
  3. Integrate: git rebase origin/feature (linear) or git merge origin/feature. Resolve conflicts if any.
  4. Run the tests, because their change and yours now live together.
  5. git push. It is a fast-forward now, so it is accepted. (If main is busy, another push can sneak in before you; repeat.)

When a force push is legitimate. If you rewrote the history on purpose (rebased your private branch or amended a commit), the server will also reject the push, because your new commits no longer include the old tip. Then the correct answer is git push --force-with-lease, not a plain --force. The lease makes sure you are not overwriting something you have not seen.

Where this commonly bites. Two people on one feature branch, and a shared main on a busy repo where you want to push straight away. For the second case the team should use PRs and a merge queue instead of racing each other.

What not to do. Do not --force "to make the error go away". Do not git pull blindly and push a merge if the project's convention is a linear history. Do not delete and re-clone, which loses your unpushed work.

Force is only correct when I rewrote my own history on purpose, such as an amend or rebase of my own branch, and then I use --force-with-lease.

Remember: rejected = I am behind. Fetch and integrate, do not force.

What is --force-with-lease and why is it better than --force? Intermediate

--force overwrites the remote branch no matter what is there. --force-with-lease overwrites it only if the remote is still where I last saw it, so if a teammate pushed meanwhile, my push fails and their work survives. It is a compare-and-swap, and it should be the only force I ever use.

The problem with plain force. git push --force says "set the remote branch to my commit, whatever it was". Suppose at 10:00 you fetch feature (tip X). At 10:05 Ravi pushes commit Y on top of X. At 10:10 you rebase and push --force. The server's feature now points to your commit, and Y is gone from the branch. You never saw Y, so you did not mean to remove it.

What the lease does. --force-with-lease says: "set the remote branch to my commit only if it still points to what my origin/feature remote-tracking branch says (X)". The server compares. It sees Y, not X, and refuses. You fetch, look at Y, and decide. This is a compare-and-swap, the same idea as optimistic locking in a database.

FlagOverwrites ifRisk

--force-with-lease --force-if-includesas above AND my local branch contains that remote tipsmallest of the three
--force-with-lease=feature:SHAremote equals the SHA I givesafe, because I choose the expectation explicitly

The loophole explained. Editors and tools often run git fetch in the background. That updates origin/feature to include Y, so the lease check sees "remote = my last known copy" and passes, even though you never integrated Y into your branch. --force-if-includes adds a check on your local reflog that your branch really includes the remote tip you are about to overwrite. Pinning the SHA by hand also closes the gap.

Policy. Alias git pushf to the safe form, so nobody types bare --force. On the server, forbid force pushes on main, release branches and tags. On personal PR branches, allow them.

One caveat: if an IDE or a background job fetched in between, my tracking ref is already updated and the lease passes even though I never looked at the new commits. --force-if-includes (Git 2.30+) adds a check that my local history actually contains the remote tip. I can also pin the expected value: --force-with-lease=feature:SHA.

git config --global alias.pushf "push --force-with-lease --force-if-includes"

Nobody should force-push to main at all: protect it on the server.

Remember: lease = "only if nobody else pushed since I looked".

Explain the fork-and-pull-request workflow, and how you keep a fork in sync. Intermediate

I fork the repo (my own server copy), clone my fork, and add the original as a second remote called upstream. I work on a topic branch, push it to my fork (origin), and open a PR to upstream. To stay in sync I fetch upstream and fast-forward my fork's main to it.

Why forks exist. In open source (and in companies with strict access control) most contributors cannot push to the main repository. A fork is a server-side copy of the repo under your account, where you can push freely. You then ask the maintainers to pull your changes with a pull request (PR). The maintainers keep control over what lands, you get a personal sandbox.

The full cycle.

  1. Click Fork on the host. You now own you/repo.
  2. git clone you/repo. Here origin = your fork.
  3. git remote add upstream org/repo. Here upstream = the original repo (read-only for you).
  4. git switch -c fix/typo upstream/main: start the topic branch from the latest upstream main, not from your fork's old main.
  5. Commit, git push -u origin fix/typo, and open a PR from you:fix/typo to org:main.
  6. Reviewers ask for changes. You push more commits (or amend or rebase and force-push with lease) to the same branch, and the PR updates by itself.
  7. After merge, delete the branch and update main from upstream.

Keeping the fork in sync. git fetch upstream then git switch main, git merge --ff-only upstream/main, git push origin main. Never commit directly to your fork's main: if you do, it diverges from upstream and syncing requires a reset. Hosts also offer a "Sync fork" button that does the same.

Same idea without forks. Many companies let everyone push topic branches into one shared repo and open PRs from them. Forks are mainly about permissions, not about Git itself.

Pitfalls. A PR branch based on an old main grows conflicts. A PR from your fork's main (instead of a topic branch) locks you out of starting a second PR. Secrets or large files pushed to a fork are visible to everyone if the fork is public.

git remote add upstream https://example.com/org/repo.git
git fetch upstream
git switch main && git merge --ff-only upstream/main
git push origin main

Remember: origin = my fork, upstream = the real repo. Keep my main as a clean mirror.

I choose by how the product is released. For web services deployed continuously I use trunk-based development or GitHub Flow: short branches, PRs, and deploy from main. For versioned products that ship on a schedule and support old versions, I use main plus release branches, and Git Flow only if the team already works that way.

5. Commits, pull requests and safeguards

What makes a good commit and a good commit message? Basic

A good commit is atomic: one logical change that builds and passes tests on its own, so it is easy to review, revert and cherry-pick. The message has a short imperative subject of about 50 characters, a blank line, and a body that explains why, since the diff already shows what.

Why it matters. Commits are read much more often than they are written: in code review, in git blame and git log years later, in git bisect, during a revert at 2 a.m. A good commit makes each of these tasks easier.

Properties of a good commit.

  • Atomic. One logical change. Test: can you describe it in one sentence without "and"? If you must say "and", it is probably two commits.
  • Self-contained. The code builds and tests pass at this commit. Then bisect works and a cherry-pick or revert of it makes sense by itself.
  • Reviewable. A mechanical change (rename, reformat) is separate from a behaviour change. A reviewer can skim the first and read the second carefully.
  • Free of noise. No debug prints, no commented-out code, no unrelated files, no secrets, no generated output.

The message shape.

I do not mix a refactor, a format sweep and a bug fix in one commit. What safeguards would you put on the main branch? Intermediate

Branch protection on the server: no direct pushes, no force pushes, no deletion. Changes only through a pull request with at least one approval, code-owner review for sensitive paths, and required status checks (build, tests, lint, security scan) passing. I apply the rules to admins as well, so "one emergency push" never becomes normal.

Principle. Anything that must be true for every change must be enforced by the server, because it is the only place every contributor has to pass through. Branch protection (GitHub) and protected branches (GitLab) are rules on a branch name.

The core rules and what each prevents.

Merge queue explained. Two PRs can each pass CI against the old main but break each other when merged. "Require branches to be up to date" forces each PR to rebase and rerun CI before merging, which is safe but serial and slow. A merge queue tests each PR on top of the PRs ahead of it, then merges in order, so you get safety and throughput.

Other layers. Secret scanning with push protection, tag protection (so release tags cannot be moved), restricted who can create release branches, and audit log alerts on any settings change.

Trade-offs. Too many required reviewers slows delivery and leads to rubber-stamping. The rule of thumb is: strict on main and release branches, light on personal branches. Extras: dismiss stale approvals when new commits arrive, require resolved conversations, optionally require signed commits or linear history, and turn on secret scanning with push protection. "Require branch to be up to date" is safe but costly, since every merge makes others rebase and re-run CI. A merge queue fixes that.

Remember: PR + review + green checks + no force push. Enforce on the server, for admins too.

What are Git hooks? Why can they not be your only safeguard? Intermediate

Hooks are scripts Git runs at certain events, kept in .git/hooks. Client side: pre-commit (lint, secret scan), commit-msg (message format), pre-push (tests). Server side: pre-receive and update reject bad pushes. They cannot be the only safeguard because client hooks are not copied by clone and anyone can skip them with --no-verify.

What they are. A hook is an executable file in .git/hooks/ (or the folder named by core.hooksPath) whose name matches an event. Git runs it at that moment, and a non-zero exit code usually aborts the operation. Sample files ending in .sample are inactive until renamed.

HookRunsTypical use

post-receive (server)after a push is acceptedtrigger CI or notify chat (usually done by the platform now)

Why client hooks are weak. .git is not part of the repository content, so a hook is not cloned. Each developer must install it. Anybody can bypass it with --no-verify, delete it, or use a GUI that skips it. They are excellent for fast feedback (catch a lint error in 2 seconds rather than after a 10-minute CI run) but not for guarantees.

How teams share them.

  • Commit the scripts in the repo (for example .githooks/) and run git config core.hooksPath .githooks in an onboarding script.
  • Use a hook manager (pre-commit framework, Husky for Node, Lefthook) with a config file that is tracked.

The right layering. Same check at three levels: pre-commit hook (fast, helpful), CI job (mandatory, same command), server rule (the platform refuses to merge unless CI is green). On hosted platforms you often cannot install server hooks, so required status checks play that role. Keep hooks fast (a few seconds), or people will bypass them.

I share client hooks with core.hooksPath pointing to a tracked folder, or with tools like pre-commit, Husky or Lefthook. Real enforcement lives on the server: branch protection, required CI checks and server hooks, because the client is not trusted.

git config core.hooksPath .githooks
git commit --no-verify     # skips pre-commit and commit-msg

Remember: hooks help the developer, server rules protect the repo.

How do you stop secrets from being committed in the first place? Intermediate

I use several layers. Locally a pre-commit scanner (gitleaks, detect-secrets, trufflehog). On the server the platform's push protection rejects known token patterns. In CI a scan job on every PR. And by design: secrets live in a vault or the platform's secret store and reach the app through environment variables, and the repo holds only templates like .env.example.

Why the first line of defence is prevention. Once a secret reaches a remote it must be treated as public. Bots scan public GitHub in minutes, and private repos are cloned to many laptops and CI caches. Rotation is mandatory afterwards, which is slow and disruptive. So block leaks early and cheaply.

Layers, from developer to platform.

  1. Do not have secrets in the working tree. Local config reads environment variables or a secret manager (Vault, AWS Secrets Manager, Kubernetes secrets). .env is in .gitignore, with a committed .env.example listing names only.
  2. Pre-commit scanner (gitleaks, detect-secrets, trufflehog) catches patterns and high-entropy strings in staged changes before a commit exists.
  3. Server push protection. GitHub secret scanning with push protection rejects pushes containing known token formats (AWS keys, GitHub tokens, and so on). GitLab has similar features.
  4. CI scan on every PR and a periodic scan of full history, to catch old leaks and things the earlier layers missed.
  5. Less valuable secrets. Short-lived credentials (OIDC from CI to cloud, IAM roles), least privilege, and per-environment keys, so a leak has a small blast radius.

If one leaks anyway. Order matters: revoke or rotate, then check logs for abuse, then remove from code, and only then consider rewriting history (see the leaked-key scenario). Removing the file in a later commit does not remove it from earlier commits, forks, PR refs or other clones.

Pitfalls. False positives make people disable scanners, so tune with allowlists and baselines. Test fixtures with fake keys need a documented exception. Scanners miss custom secrets, so also review config files by eye.

Deleting a secret in a later commit does not remove it from history. The real answer to a leak is to rotate the credential first, then clean history if needed.

Remember: prevent in layers, but once leaked, rotate.

6. Undoing things and selective apply

Explain git reset --soft, --mixed and --hard. Basic

git reset COMMIT always moves the current branch to COMMIT. The mode decides what else changes. --soft moves only the branch, so the undone changes stay staged. --mixed (the default) also resets the index, so the changes stay in my files but unstaged. --hard resets branch, index and files, so uncommitted work is gone for good.

First understand what reset does to your three areas. Recall the three places: the commit that the current branch points to (HEAD), the index, and the working tree. git reset <commit> does up to three steps, and the flag says how far it goes:

  1. Move the branch (and HEAD with it) to the target commit. Always happens in all three modes.
  2. Reset the index to match that commit. Happens in --mixed and --hard.
  3. Reset the working tree to match. Happens only in --hard.

Example. You have commits A-B-C (HEAD at C). You changed x.py in C and you want to undo C.

CommandBranch now atChanges of C areUse it for
reset --soft BBstaged (ready to commit again)redo the commit, or squash the last N commits into one
reset --mixed B (default)Bin the files, unstagedsplit C into smaller commits with add -p
reset --hard BBgone from the files tooabandon C and any other uncommitted edits

Why --hard is the dangerous one. The first two never delete content. They only move labels or unstage. Hard also overwrites your files. Uncommitted edits were never stored as objects, so no reflog entry exists for them. Committed work is recoverable: git reflog shows where the branch was before, and git reset --hard HEAD@{1} brings it back.

Squashing with soft. git reset --soft HEAD~3 && git commit -m "one message" merges the last three commits into one, with no editor list. It is the quick alternative to rebase -i.

Do not confuse with these. git reset file (with a path) never moves the branch, it only unstages that file. git restore and git checkout -- file change the working tree from the index or a commit. git reset --hard origin/main is the standard way to make your local branch exactly equal to the server's (it discards your local commits, so check git log origin/main..HEAD first).

Pitfall. Resetting a branch that others share, then pushing: that is a rewrite of shared history. Use revert there.

Use soft for "redo this commit", mixed for "uncommit and stage differently", hard for "throw it all away". Committed work lost by a hard reset can be recovered through the reflog, but uncommitted changes cannot. --keep is a safer hard that refuses if it would overwrite local changes. With a path, git reset file just unstages that file and moves no branch.

git reset --soft HEAD~1        # undo commit, keep changes staged
git reset HEAD~1               # undo commit, keep changes unstaged
git reset --hard origin/main   # make local branch identical to remote

Remember: soft moves 1 area, mixed 2, hard 3. Hard is the only one that loses uncommitted work.

When do you use revert and when reset? Basic

If the commit is already pushed and others may have it, I use git revert: it adds a new commit that undoes the old one, so history only grows. If the commit exists only on my machine, I use git reset or amend, because rewriting private history hurts nobody.

The question to ask first: has anyone else got this commit?

  • No (only on my machine). Rewriting is free. reset or amend make the commit vanish from the branch, leaving a clean history.
  • Yes (pushed to a shared branch). Others have built on it or at least fetched it. If you remove it from the server by force, their copies still contain it and the next pull brings it back, or breaks. So you add a new commit that cancels the old one, and everybody simply pulls it.

How revert works. git revert X computes the inverse of X's diff (X compared with its parent, reversed) and applies it on the current branch as a new commit "Revert 'message'" that references X. It uses a three-way merge, so if later commits touched the same lines, you may get conflicts to resolve.

How do you revert a merge commit, and what is the trap when you merge the branch again? Senior

A merge commit has two parents, so I must tell Git which one is the mainline: git revert -m 1 MERGE_SHA keeps parent 1 and undoes what came from the other side. The trap is that Git still remembers the merge. If I fix the feature and merge again, only the new commits come in, and the original changes stay missing. First I revert the revert, then merge the fixes.

Why a merge needs -m. A normal commit has one parent, so the "change it made" is unambiguous: commit minus parent. A merge commit M has two parents (P1 = mainline, P2 = feature tip). "The change M made" could mean "relative to P1" (the feature's contents arriving) or "relative to P2". Git will not guess: git revert M fails with "is a merge but no -m option was given". -m 1 means "treat parent 1 as the mainline", so the revert removes everything that came in from parent 2.

What the revert does and does not do. The revert commit R changes the files back to how they were before the feature. But the graph still says "the feature's commits are merged into main". Git decides what a future merge brings in by ancestry, not by content.

The trap, step by step.

  1. Feature has commits F1, F2. They are merged by M, then reverted by R. Main has no feature code.
  2. Developers fix the feature by adding F3 on the same branch and merge again.
  3. Git computes the merge base: the feature tip's history includes F1 and F2, and those are already ancestors of main, so only F3 is "new". Main receives F3 only, which usually does not compile or work, because F1 and F2 content is missing. Often no conflict appears either, so it looks fine.

The two ways out.

  • Revert the revert (git revert R) to bring back F1+F2 content, then merge the branch with F3. Conflicts are limited to genuinely changed lines.
  • Re-create the branch: git rebase or cherry-pick F1..F3 onto a new branch, giving new ids which are not ancestors of main, and merge that.

A well-known write-up of this is Linus Torvalds' "revert a faulty merge" how-to in the Git docs. Take away: before reverting a big merge, decide how you will land the fixed version. Feature flags often make the whole situation unnecessary.

The alternative is to rebuild the feature as fresh commits (cherry-pick or rebase onto a new branch) and merge that branch.

Remember: revert -m 1 for the merge. To re-merge later, revert the revert first.

How do you fix the last commit (message or content)? What changes in history? Basic

git commit --amend replaces the last commit with a new one. For just the message, git commit --amend -m "better message". To add a forgotten file, stage it and run git commit --amend --no-edit. Fine if unpushed. If it was pushed, I need a force-push, which affects anyone who pulled it.

What amend really does. git commit --amend takes the current index (plus the staged changes you added since) and the old message, and creates a new commit with the same parent as the old one. Then it moves the branch to the new commit. The old commit becomes unreachable (still in reflog). So amending is a tiny rebase of one commit.

Common recipes.

git commit --amend                    # edit message in editor, and include staged changes
git commit --amend -m "New message"   # message only
git add forgotten.txt
git commit --amend --no-edit          # add a file, keep the message
git commit --amend --reset-author     # fix author after a wrong git config
git commit --amend --date=now         # refresh the date

Is it safe? It depends on whether the commit was shared.

  • Not pushed: completely safe, no one can tell.
  • Pushed to my own PR branch: fine if I know nobody else uses it. I need git push --force-with-lease. Reviewers lose the exact diff between revisions in some UIs, so for big reviews add new commits and squash at merge.
  • Pushed to a shared branch: do not, add a new commit instead.

Older commits. Amend works only on HEAD. For an older commit: git commit --fixup=SHA then git rebase -i --autosquash, or rebase -i with reword (message) or edit (content).

Pitfalls. Amending after a hook auto-formatted files can mix concerns, and an amend while a rebase is in progress changes the commit that is being replayed (that is what the edit command is for). If you amend and realise the old version was better, git reset --hard HEAD@{1} restores it.

The old commit is not edited. A new commit with a new hash takes its place, and the old one stays in the reflog. For an older commit I use interactive rebase with reword or edit, or a fixup commit plus autosquash. --reset-author fixes the author of the last commit.

Remember: amend = replace the last commit. Safe only before push.

How does git stash work, and what are its limits? Basic

git stash saves my uncommitted changes and resets the working tree to HEAD, so I can switch tasks. git stash pop re-applies the latest stash and removes it, apply re-applies and keeps it. By default untracked files are not stashed; -u adds them and -a adds ignored files too.

Why stash exists. You are halfway through a change, and an urgent task needs a clean working tree on another branch. You do not want to commit half-baked code. Stash saves your dirty state (changes to tracked files, plus staged changes) somewhere safe and resets the tree to HEAD. Later you restore it.

The everyday flow.

  1. git stash push -u -m "wip: parser": saves tracked changes and untracked files and cleans the tree.
  2. git switch hotfix, fix, commit, push, switch back.
  3. git stash list shows stash@{0}: On feature: wip: parser.
  4. git stash pop re-applies the newest stash and drops it. If it conflicts, the stash is kept, so you do not lose it; resolve the conflict and drop it yourself.

Limits and traps. Stashes are local: they are not pushed and not in a fresh clone. They have no branch context, so after weeks "stash@{4}" means nothing; name them with -m or prefer a short-lived WIP commit on a branch. Applying onto a different base may conflict. Binary files and renames can behave oddly. git stash without -u leaves new files behind, which surprises people when the tree is "clean" but a file is still there.

Alternative. git worktree add lets you work on another branch with no stash at all. A dropped stash can be found with git fsck --unreachable, as long as gc has not run.

Internally a stash is a commit with two or three parents (HEAD, the index state, and optionally untracked files), stored under refs/stash. Limits: it is local and private, it can conflict on pop, and a dropped stash is recoverable only until garbage collection, via git fsck --unreachable | grep commit. Name stashes with -m so I can find them later.

git stash push -u -m "wip: parser"
git stash list
git stash pop            # or: git stash apply stash@{1}
git stash branch fix-x   # make a branch from a stash

Remember: stash = temporary commits on the side. Add -u for new files, name your stashes.

What does cherry-pick do, and what are its risks? Intermediate

git cherry-pick SHA takes the change introduced by one commit and applies it on my current branch as a new commit with a new hash, keeping the author. I use it to backport a fix to a release branch. The risks: the same change now exists twice under different hashes, and the commit may depend on earlier commits I did not pick.

What it does. Take the changes that commit X introduced (X compared to its parent) and apply them to the branch you are on, creating a new commit with the same author and message but a new committer, parent and hash. Technically it is a three-way merge where the base is X's parent, "ours" is your HEAD and "theirs" is X.

Good uses.

  • Backport a fix from main to a release branch (the most common use).
  • Rescue one commit that you made on the wrong branch.
  • Pull a commit out of a branch that is not ready to merge as a whole.

Why it is risky.

  • Hidden dependencies. The commit may rely on a function added by an earlier commit that you did not pick. The pick applies cleanly but the code does not compile, or worse, compiles and behaves differently. Always build and test after picking.
  • Duplicates. The same change now exists twice with different ids. When the two branches are later merged, Git usually realises the content is equal and is quiet, but if either side changed the area again you get confusing conflicts. git cherry -v main release/1.4 compares by patch content and marks which commits are already applied (-) or not (+).
  • Lost traceability. Use -x so the message gets "(cherry picked from commit abc...)".

Useful flags. -n apply without committing (combine several picks). -m 1 for a merge commit. X..Y picks a range (excludes X). --continue, --skip, --abort as in rebase. Empty picks (change already present) stop with a message, and --skip or --allow-empty decides.

Rule of thumb. One or two targeted picks is normal. If you keep picking whole feature branches around, switch to merge or to a branch strategy where fixes flow from older to newer branches.

I pass -x to record "(cherry picked from commit ...)" in the message, which helps traceability on backports. A merge commit needs -m 1. A later merge of the original branch often copes with the duplicate but can conflict. Heavy cherry-picking is a sign the branching model needs work.

git switch release/1.4
git cherry-pick -x 4be7d2a
git cherry-pick --continue    # or --abort

Remember: cherry-pick copies a change, not history. Use -x on backports.

You pushed a bad commit to a shared branch. What do you do? Intermediate

First stop the damage: tell the team, and if it is deployed, roll the deployment back, which is faster than a code fix. Then git revert BAD_SHA and push the revert as a normal commit, through the usual PR if the branch is protected. This keeps everyone's history valid.

Think in two time scales. Production and history have different urgency. Users are hurting now, and history can be cleaned in an hour.

  1. Stop the damage (minutes). If the bad commit is deployed, roll back to the last good release with your deploy tool (previous container image, feature flag off). This is usually faster and less risky than a code change. Tell the team in the incident channel and ask them to pause merging to the branch.
  2. Fix the branch (minutes to an hour). Run git revert BAD_SHA (or -m 1 for a merge) on a short branch, open a PR, get a fast review and green CI, and merge. History shows a bad commit, its revert, and everything stays consistent for all clones.
  3. Fix forward, if quicker. If the bug is a one-line mistake, a normal fix commit can be better than a revert. Choose by risk, not pride.
  4. Learn (next day). Add the missing test or alert, and write what happened. If it was reverted, the re-land PR should link the original and the revert, and explain what is different now.

Why not reset and force-push. Everyone who pulled the bad commit has it locally and may have committed on top. Your force push creates divergent histories and they must repair it, during an incident, when attention is short. It also deletes the evidence. Branch protection should make it impossible anyway.

The exception. Secrets and legally sensitive or huge files. There, history must be rewritten, so announce it, schedule it, and have everyone re-clone. Rotate the secret before the rewrite (see the scenario).

Check before you revert. Is anything built on top that depends on the bad commit? Did a migration or data change go out with it, so that the revert needs a data fix as well? A revert of code does not undo a database migration.

I rewrite shared history only if the commit contains a secret or a huge file, and then with team coordination (and I rotate the secret anyway). Afterwards I add the missing test or check, and note in the PR why it was reverted so a re-land is done carefully.

Remember: roll back the deploy first, revert in Git second, never rewrite shared history.

A file is in .gitignore but Git still tracks it. Why, and how do you fix it? Basic

Ignore rules apply only to files Git is not yet tracking. If the file was committed earlier, it stays tracked. I run git rm --cached path (with -r for folders) and commit, which stops tracking but keeps the file on disk.

How Git decides what to track. Git tracks a file once it has been added to the index. .gitignore only affects files Git does not already know: it hides them from git status and makes git add . skip them. A file already in the index and in commits keeps being tracked, and edits to it are still shown. This is the reason "I added it to .gitignore but it still shows up".

The fix, step by step.

  1. Add the pattern to .gitignore, for example config/local.yml or build/.
  2. git rm --cached config/local.yml (or git rm -r --cached build/). --cached removes it from the index only, so the file stays on your disk.
  3. Commit both changes together. After the commit, teammates who pull will see the file deleted in their working tree, so warn them to back up their local copies (a plain pull deletes the real file for them).

Debugging an ignore rule. git check-ignore -v path prints which file and line caused the ignore (or nothing, if the path is not ignored). Common gotchas: a pattern with a leading slash is anchored at that folder; !pattern can re-include a file but not inside an ignored parent directory; a trailing slash matches directories only.

Where to put rules.

A config file that everyone edits. Commit config.example.yml and ignore the real one. Avoid git update-index --assume-unchanged and --skip-worktree for this, because they are local hacks that break during merges and are easy to forget.

If it contained a secret. Untracking does not erase history. Rotate the secret.

That does not remove it from history, so a leaked secret still needs rotating. git check-ignore -v path shows which rule matches. Place rules by scope: project-wide in .gitignore, personal editor files in a global file (core.excludesFile), local-only in .git/info/exclude. 7. History, debugging and recovery

What is the reflog and how does it save you after a bad reset or rebase? Intermediate

The reflog is a local journal of where HEAD and each branch pointed over time. After a bad reset --hard or rebase, the commits are not gone, the branch label just moved away. I run git reflog, find the line from before the mistake, and restore with git reset --hard HEAD@{4} or make a branch at that hash.

What it is. Every time HEAD or a branch label moves (commit, checkout, merge, rebase, reset, pull), Git appends a line to a local log: old hash, new hash, who, when and why. This log is the reflog. It records the movements of labels, which is exactly what you need when a command moved a label somewhere you did not want. It is separate from git log, which shows ancestry.

$ git reflog
3f2a1b0 HEAD@{0}: reset: moving to HEAD~3
9d8c7b6 HEAD@{1}: commit: Add retry logic
a4b5c6d HEAD@{2}: commit: Add timeout config
...
$ git reset --hard HEAD@{1}      # back to before the reset

Recovery recipe.

  1. Stay calm and do not run git gc or git clean.
  2. git reflog (or git reflog show branchname). Read the "why" column to find the last entry that looks right. Time-based forms also work: main@{2.hours.ago}.
  3. Inspect it: git show HASH, git log --oneline HASH.
  4. Restore: git branch rescue HASH (safest, nothing moves) or git reset --hard HASH.

What it covers. A dropped branch (find its last tip), a bad reset --hard (committed work), a botched rebase, an amend you regret, a merge you want to undo. It also covers files that were committed once and then lost.

What it does not cover.

  • Uncommitted changes. Never stored as objects, so a reset --hard or checkout -- file destroys them. (Anything you had git added is a blob and may be found with git fsck --lost-found.)
  • Other people's clones. The reflog is per repository on your machine. A bare server repository usually keeps none, which is why recovery after a server force push needs a developer's clone.
  • Old entries. They expire (gc.reflogExpire 90 days, gc.reflogExpireUnreachable 30 days by default), after which gc can delete the commits.

Interview probe. "How is the reflog different from git log?" Log walks parent links from a commit. Reflog walks time for a ref. A commit can be in the reflog and not in any log if it is unreachable.

Limits: it is local only (a fresh clone has none), and entries expire: 90 days for reachable ones and 30 days for unreachable ones by default. Uncommitted changes never enter the reflog. For one branch, use git reflog show feature.

Remember: committed work is almost never lost. Reflog first, panic never.

What does "reachable" mean, and when does Git actually delete things? Senior

An object is reachable if I can get to it from a ref (branch, tag, HEAD, stash, remote-tracking branch, reflog entry) by following parent and tree pointers. Everything else is unreachable. Git never deletes at once: git gc prunes unreachable loose objects only after they are older than 2 weeks, and reflog entries protect commits for 30 to 90 days.

The idea. Git's object database only ever grows during normal work. To decide what is garbage, it uses a graph definition: start from every root (branches, tags, HEAD, remote-tracking branches, the stash, and reflog entries) and follow every pointer (commit to parents, commit to tree, tree to blobs and subtrees, tag to target). Everything you can touch is reachable. The rest is unreachable and may be removed.

When things disappear, as a timeline.

  1. You run git reset --hard or delete a branch. Commits become unreachable from branches, but the reflog entries still count as roots (while the entries live), so nothing is garbage yet.
  2. Reflog entries expire: 30 days if the commit is unreachable from the branch's current tip, 90 days otherwise (defaults).
  3. The commit is now unreachable from any root. git gc runs automatically now and then (when there are many loose objects or packs), but it only prunes unreachable loose objects older than gc.pruneExpire (2 weeks by default). This protects objects being created by a concurrent command.
  4. Pruned. The object is gone from this clone.

Why it matters in practice.

  • Recovery: you usually have weeks to get lost commits back.
  • Secrets: removing a leaked file from history does not erase it everywhere. Old objects remain in your clone, in other developers' clones, in the server's packfiles and PR refs (refs/pull/*), and in forks, until each is pruned. To clean your own clone: expire the reflog and gc with --prune=now. A hosting provider usually must run its own garbage collection or purge cached views.
  • Size: a repo stays large after you delete a big file in a later commit, because older commits still reference it. Only a history rewrite plus gc shrinks it.

Useful commands. git fsck --lost-found lists dangling commits and blobs. git count-objects -vH shows loose size and packs. git gc --aggressive repacks harder and is rarely needed. git prune is the low-level pruning step, and a plain git gc already runs it.

The flip side matters for secrets: after rewriting history to remove a leaked file, old objects remain in my clone, in forks and in the host's caches until pruned.

git reflog expire --expire=now --all
git gc --prune=now      # destructive; only when you are sure

Remember: unreachable does not mean deleted. Weeks of grace, which is both rescue and leak.

How does git bisect work, and how do you automate it? Intermediate

Bisect finds the commit that introduced a bug by binary search. I mark the current commit bad and an old one good, Git checks out the middle, I test and say good or bad, and the range halves each time. 1,000 commits need about 10 steps. I automate it with git bisect run ./script.sh.

Why binary search. Suppose a test passes in v2.3 and fails today, and there are 1,000 commits between. Testing each would take 1,000 builds. Because the answer is monotonic (good, good, ..., first bad, bad, bad), you can test the middle: if it is good, the culprit is in the later half, otherwise the earlier half. After about log2(1000) = 10 tests you have it.

Manual flow.

  1. git bisect start, git bisect bad (HEAD is broken), git bisect good v2.3.0.
  2. Git checks out the commit in the middle (detached HEAD) and prints how many steps remain.
  3. You build and test, then type git bisect good or git bisect bad. (Use git bisect skip if this commit cannot be tested.)
  4. Repeat. Finally Git prints "abc123 is the first bad commit" with its message.
  5. git bisect reset returns you to where you started. git bisect log saves the trail, which you can replay.

Automated flow. Write a script that exits with the right code, then git bisect run ./check.sh does everything without you. Exit 0 means good, 1 to 127 except 125 means bad, 125 means "cannot test, skip", and 128 or more aborts the bisect. Example script content: build the project, run one failing test, return its status. A build failure should exit 125, not 1, otherwise the broken-build commits are classed as the bug.

Requirements and pitfalls.

  • A deterministic test. A flaky test points bisect at a random commit. Re-run uncertain checks several times in the script.
  • A real "good" starting point. If you guess wrong, the result is nonsense. Check it out and test it first.
  • History with many merges or long-broken stretches: try git bisect start --first-parent to walk only the mainline, then bisect inside the faulty merge.
  • Commits that mix several changes (WIP style) make the answer less useful. Atomic, buildable commits make bisect precise. That is a major reason to keep them.
  • You can bisect for any property, not only bugs: "when did this get slow", "when did this file change behaviour" (rename the terms with --term-old and --term-new).

The script exits 0 for good, 1 to 127 (except 125) for bad, and 125 to skip a commit that cannot be tested (for example it does not build). git bisect reset returns me to my branch. Pitfalls: flaky tests give wrong answers, so the check must be deterministic. On merge-heavy mainlines use --first-parent.

git bisect start
git bisect bad                 # current commit is broken
git bisect good v2.3.0
git bisect run ./test_repro.sh # exit 0 good, 1 bad, 125 skip
git bisect reset

Remember: bisect = binary search over commits. 1,000 commits is about 10 tests.

How do you find who changed a line and why, and how do you skip formatting commits in blame? Intermediate

git blame file shows, for each line, the last commit that changed it. I read that commit with git show SHA to learn the reason and follow the ticket id. For mass-reformat commits that hide the real author, I list their hashes in .git-blame-ignore-revs and use git blame --ignore-revs-file.

What blame answers. For each line of a file it shows the last commit that changed the line, with author and date. It tells you which commit to read. The reasoning is in that commit's message, its PR and ticket. So the habit is a two-step: blame, then git show (or open the PR).

$ git blame -L 40,44 src/Pay.java
4be7d2a1 (Asha 2025-03-02 40) int retries = 3;
9f3c11e0 (Ravi 2025-11-10 41) if (code == 502) retry();

The "last touched" problem. Formatting, renames and mass edits make every line show the person who ran the formatter. There are three tools:

  • -w ignores whitespace-only changes.
  • -M detects lines moved within the file, -C detects lines copied from other files (use -C -C -C for stronger searches). This finds the original author after a refactor split a file.
  • --ignore-rev SHA or an ignore-revs file skips named commits as if they never happened. Commit the list as .git-blame-ignore-revs, one hash per line (comments with #), run git config blame.ignoreRevsFile .git-blame-ignore-revs. GitHub's blame view honours that file name automatically.

Going further back. In the blame result, the line may be from a commit that only changed it slightly. Use git blame SHA^ -- file to blame the previous version of the file, repeating until the origin appears. IDEs show this as "annotate" and have "previous revision" buttons. git log -L 40,44:file shows the full history of that line range, which often beats repeated blame.

Combine with search. If the line was deleted, blame cannot show it. Use git log -S"text" to find when it was removed.

Attitude. The name is a pointer to context, not a person to blame. In a post-mortem, the useful question is "what in our process allowed this change", not who typed it.

Useful flags: -L 40,60 for a range, -w to ignore whitespace, -M and -C to follow lines moved or copied between places and files. Set blame.ignoreRevsFile once, and note that GitHub reads that file name by itself. Blame is for understanding, not for blaming people.

git blame -L 40,60 -w src/Pay.java
git config blame.ignoreRevsFile .git-blame-ignore-revs

Remember: blame, then show the commit, and ignore the reformat commits.

How do you search history for when a line, a function or a string was added or removed? Intermediate

I use the pickaxe: git log -S"retryCount" lists commits where the number of occurrences of that string changed, so it finds where it was added or removed. -G"regex" matches diff lines by regex. git log -L :funcName:file shows the history of one function with its diffs.

The problem. Plain git log filters by message, author or path. But often you remember only the code: "there used to be a retryCount here, who removed it and why?". Git can search the content of changes.

ToolFinds commits whereExample

Difference between -S and -G. If a commit moves a line (removes in one place, adds in another), the count of the string stays the same, so -S skips it and -G shows it, because a matching line was added or deleted. -S is better for "when was this introduced or removed".

Worked example. A config key cache.ttl vanished. Run git log -S"cache.ttl" --oneline -- config/. The list shows the commit that added it and the commit that removed it. Then git show REMOVING_SHA shows the diff and message. If the whole file was deleted, use git log --diff-filter=D -- config/app.yml.

Tips. Add -p to see the diff, --all to search all branches, --follow for a single file across renames, --since="2 weeks ago" to limit work. Searches walk every commit and can be slow on huge repos, so narrow by path.

Other filters: --author, --since, --grep (commit message), -- path, --diff-filter=D for deleted files, --no-merges. git log --graph --oneline --decorate --all draws history. To search file contents at a given commit use git grep pattern REV.

git log -S"timeout" --oneline -- src/
git log --diff-filter=D --name-only -- "*Config.java"   # who deleted it
git log -L :parseHeader:src/Parser.java

Remember: -S = string count changed, -G = regex in diff, -L = function history.

8. Tags, releases and backports

Lightweight tag versus annotated tag: what is the difference and which for releases? Basic

A lightweight tag is just a name pointing at a commit, like a branch that never moves. An annotated tag is a real object with a tagger, date and message, and it can be signed. I use annotated tags for releases, because they record who tagged it and why, work with git describe, and many tools only treat annotated tags as releases.

What a tag is for. A branch label moves; a tag is a name that is meant to stay on one commit forever, such as v1.4.0. Tags mark releases, so you can later say "build exactly what shipped".

Why annotated for releases. It records who released and when, carries release notes in the message, can be cryptographically verified (git tag -v), and the host's "Releases" page and git describe work from it. git describe prints names like v1.4.0-12-g4be7d2a, meaning "12 commits after v1.4.0, at commit 4be7d2a", which is handy as a build version.

Sharing tags. git push does not send tags. Use git push origin v1.4.0, git push --follow-tags (only annotated tags reachable from the pushed commits) or git push --tags (all, including stray local ones; avoid). Also git fetch --tags to receive them.

Immutability. If you move a tag after publishing, anyone who already fetched keeps the old one (Git does not update existing tags on fetch unless forced), so two people see different "v1.4.0". Package registries and build caches may have used the old commit. If you tagged the wrong commit, publish v1.4.1 and mark v1.4.0 as bad. Protect tags on the server.

Semver reminder. MAJOR.MINOR.PATCH: breaking change, new feature, fix. Prefix v is a convention.

Tags are not pushed by default: git push origin v1.4.0, or git push --follow-tags for annotated tags on pushed commits. A published tag should never move, because caches and consumers rely on it. If I tagged the wrong commit, I release a new version instead.

git tag -a v1.4.0 -m "Release 1.4.0"
git tag -s v1.4.0 -m "Release 1.4.0"     # signed
git push origin v1.4.0
git tag -d v1.4.0 && git push origin :refs/tags/v1.4.0   # delete (avoid for released tags)

Remember: releases get annotated tags. Push them explicitly. Never move a published tag.

How would you manage release branches and versions for a product that supports several versions at once? Senior

I develop on main and cut release/1.4 when a version is feature-complete. Only bug fixes go on a release branch. I tag each release from it (v1.4.0, then v1.4.1) using semantic versioning. The rule for fixes is: fix on main first, then cherry-pick to each supported release branch with -x, so no fix is ever lost in a future version.

The problem. A product (an SDK, a database, an on-prem server) has customers on 1.4, 1.5 and 2.0 at the same time. A security fix must reach each line without dragging in unfinished features from main.

The structure.

  • main: next version, where all development lands.
  • release/1.4, release/1.5: created from main (or from a tag) when that version is feature-frozen. Only bug fixes, security fixes and version bumps go in.
  • Tags v1.4.0, v1.4.1 on the release branch. Binaries are always built from a tag by CI, never from a laptop.

How a fix flows.

  1. Reproduce, fix and test on main. Merge through a PR.
  2. For each supported release line that has the bug, cherry-pick with -x onto a branch from release/x.y, run that line's tests, PR into the release branch.
  3. Tag the patch release and publish release notes (which PRs, which CVEs).

Why main first: if you fix only the release branch, the next minor release (cut from main) regresses the bug. The rule "no fix on a release branch unless it is already on main (or explicitly not applicable)" prevents that. Many projects enforce it with a PR template question and a label like backport-1.4 which a bot uses to open the cherry-pick PR.

The alternative: merge up. Fix on the oldest affected branch, then merge release/1.4 into release/1.5 into main. Ancestry then proves the fix is everywhere (git branch --contains), and there are no duplicate commits. The cost: the oldest branch must be cleanly mergeable forward, and unrelated release-only commits (version bumps) cause conflicts. Both work; the team should pick one and write it down.

Other duties. A published support policy (for example the last two minors get fixes), automated end-of-life for branches, signed tags and artifacts, a changelog generated from PR titles or Conventional Commits, and verifying with git tag --contains FIX_SHA which releases include the fix.

Some teams do the opposite: fix on the oldest affected branch and merge forward. That keeps ancestry clean but needs a clear merge path. I automate release builds from the tag, generate notes from merged PRs, sign artifacts, and retire branches on a published support schedule. Semantic versioning: major for breaking changes, minor for features, patch for fixes.

Remember: fix main first, then backport. Tag every release from its branch.

Walk through backporting a fix from main to an older release branch. Intermediate

Fix and merge on main first, with a test. Then I branch from the release branch (not main), run git cherry-pick -x SHA, resolve conflicts, run the release branch's full tests, and open a PR into release/1.4 that links the original PR. After merging I tag the patch release, for example v1.4.1.

Why the order matters. You always fix main first, so that the next release is never worse than the old one. The backport is a mechanical copy of that already-reviewed fix.

Step by step.

  1. Find the fix commit(s) on main. With squash merges this is one SHA. With merge-commit PRs, list the commits of the PR (git log MERGE^1..MERGE^2).
  2. Branch from the release branch, not from main: git switch -c backport/1.4-npe-fix origin/release/1.4. Branching from main would drag unreleased work into the release.
  3. Cherry-pick with trace: git cherry-pick -x SHA (for several commits, oldest first). The message gets "(cherry picked from commit SHA)".
  4. Resolve conflicts with the release code in mind. Code often differs (refactored names, missing helper). Sometimes the fix needs a small rewrite. Test that the original bug is gone on this branch: add or port the regression test.
  5. Run the release branch's full CI, not only the new test. Open the PR into release/1.4, linking the original PR and ticket.
  6. After merge: bump version (1.4.1), tag, build from the tag, publish notes.
  7. Verify: git tag --contains NEW_SHA and, for every other supported line, check the fix reached it.

When the backport is not a clean pick. If the fix depends on earlier refactors, either backport those too (more risk) or write a separate minimal fix for the old code, mention it in the PR and have the original author review it. Security fixes may need embargoed branches and coordinated disclosure.

Pitfalls. Forgetting a supported line, picking in the wrong order, shipping an untested backport, and not leaving the link to the original commit, which makes audits painful.

If the fix was squash-merged on main there is one commit to pick; if it was several commits, pick them in order. I check that the fix does not depend on other changes missing from the old branch. Many platforms offer a backport bot or label that does these steps.

git switch -c backport/1.4-fix release/1.4
git cherry-pick -x 4be7d2a

Remember: main first, branch from the release, cherry-pick -x, test, PR, tag.

9. Configuration, hygiene and performance

What is Git LFS and what are its trade-offs? Intermediate

Git LFS (Large File Storage) stores big files outside the repo on an LFS server and keeps only a small text pointer in Git. Clones stay small and fast, and I download only the versions I check out. The cost is extra setup: server support, quotas, and an LFS install on every machine and CI runner.

The problem. Git stores every version of every file forever, and every clone downloads all of them. For text that is fine because deltas compress well. For a 200 MB design file edited 30 times, compression helps little, so the repo grows by gigabytes and clones become slow. Hosts also set per-file and per-repo size limits.

How LFS solves it.

  1. You declare patterns: git lfs track "*.psd". This writes a line in .gitattributes (which you commit).
  2. When you git add a matching file, a clean filter replaces the content with a tiny pointer file (version, oid sha256:..., size) and uploads the real bytes to the LFS server (often the same host, different storage).
  3. Git commits only the pointer. History therefore stays small.
  4. On checkout a smudge filter reads the pointer and downloads the real file for that revision, so you only fetch the versions you actually use.

Trade-offs.

BenefitCost
Small repo and fast cloneseverybody and every CI runner needs git-lfs installed (a missing install leaves pointer files in the tree)

Alternatives. Store build outputs and big assets in an artifact repository (Artifactory, Nexus, S3) and put only a version and checksum in Git. For datasets, tools like DVC do something similar. For plain generated files, do not commit them at all.

Pitfall. Adding the track rule after the file is already committed does nothing for the old commits. Also check that the mirror, backup and fork tooling you use supports LFS objects.

I enable it with git lfs track "*.psd", which writes rules to .gitattributes. Files already in history stay there unless I rewrite history with git lfs migrate import. Alternative: keep binaries in an artifact store (Nexus, Artifactory, S3) and reference them by version.

Remember: LFS = pointers in Git, bytes on a server. Migrating old history needs a rewrite.

A teammate force-pushed over main and the last 15 commits disappeared. What do you do? Senior

The 15 commits still exist as objects. Only the main label moved. I freeze pushes, find the old tip from any recent clone, CI run or the host's push log, put a branch on it, and move main back with a lease-protected push.

Why this is recoverable, in plain words. A force push does not delete commits on the server. It changes where the label main points. The 15 "lost" commits are still stored as objects, they just have no label. The server garbage-collects such objects only after a grace period, so the clock is ticking but not fast. Your job is to find the old tip id, put a label on it, and put main back.

The sequence, with who does what.

  1. Freeze (first 5 minutes). Announce "do not push, pull or reset main". Ask the host admin to block pushes to main. Nobody should run git gc, or git push --force to "fix" it, because an uninformed second force push can make the old tip harder to find.
  2. Find the old tip. Sources, from easiest: (a) any teammate's clone that fetched recently: git reflog show origin/main prints the previous values, so the id before the bad push is there; (b) the last green CI run or deploy record, which lists the commit id; (c) the host's audit or events log, or the PR page of the last merged PR; (d) the hosting provider's support, which can restore from a server-side log.
  3. Make it safe. From a clone that has the commit, create a branch (git branch rescue-main OLD_SHA) and push it under a new name. Now the commits have a label on the server and cannot be garbage collected.
  4. Restore main. Compare first: git log --oneline OLD_SHA..origin/main shows commits that were pushed after the bad force. If someone legitimately pushed on top of the bad state, decide whether to cherry-pick or merge them back. Then push main to OLD_SHA with a lease pinned to the bad value, as in the snippet.
  5. Re-sync everyone. Teammates run git fetch and git switch main && git reset --hard origin/main (after saving local commits to a branch). Open PRs that were based on the bad state may need a rebase.
  6. Re-enable protection and find the cause. Why was a force push allowed? Often a wrong flag (git push -f) or an alias, a rule that exempts admins, or a CI token with too much power.

In the follow-up, mention a blameless post-mortem, an alert on forced ref updates, and server-side rules. That shows you treat it as a process failure and not as one person's failure.

Situation: remote main points to an older or different commit. Nothing is deleted yet.

Check first: tell the team not to pull or reset, and not to run git gc. Find OLD_SHA from a teammate's git reflog show origin/main, the last green CI build, PR merge records, or the host's audit log. The host support can also restore from a server-side reflog.

git fetch origin
git reflog show origin/main            # on a machine that still has the old tip
git branch rescue-main OLD_SHA
git push origin rescue-main            # safe copy first
git push --force-with-lease=main:BAD_SHA origin OLD_SHA:main

Fix: lift branch protection briefly if it blocks the push, restore main, then re-apply any valid new commits on top by cherry-pick or merge. Everyone then fetches and resets their local main.

Prevent: branch protection that blocks force pushes and deletions on main for everyone including admins, and an alert on forced updates of protected refs.

Remember: find the old SHA, label it, move main back. Never run gc.

Someone committed and pushed a cloud access key. What are the steps, in order? Senior

Rotate the key first, clean history later. I assume it is already stolen, because scanners find leaks in minutes. Then I remove it from code, check the provider logs for misuse, and only then decide whether a history rewrite is worth it.

Why the order is "rotate first". The moment a key is pushed, assume somebody or some bot has copied it. Rewriting history cannot take it back from copies. Only invalidating the key works. If you spend an hour on filter-repo first, the key stays usable for that hour. So the sequence is: make the key worthless, find out whether it was used, remove it from code, and only then decide how much to clean.

Detailed steps.

  1. Contain (minutes). Disable or rotate the credential (for cloud keys: deactivate, create a new one, update the secret store and redeploy consumers). Check what permissions it had: that defines the blast radius.
  2. Investigate (hours). Review the provider's audit logs (for example CloudTrail) from the first push time to now for calls from unknown IPs, new resources (crypto mining instances are typical), data reads. Open a security incident and involve the security team.
  3. Fix the code. Replace the key with a lookup from the secret manager or environment, in a normal PR.
  4. Decide about history. Questions: Is the repo public or widely forked? Is the secret more than a credential (customer data, signing key)? Does compliance require it? If the key is rotated and the repo is private, many teams stop. If you do rewrite: work on a fresh mirror clone, run git filter-repo --replace-text expressions.txt (or remove the file path), force-push all branches and tags, ask everyone to re-clone (not pull), ask the host to delete cached views, PR refs and run garbage collection. Old forks and local clones still keep it, so rotation was the real fix.
  5. Close out. Post-mortem: how did it get through, and which layer failed (local scan, push protection, review)?

What the interviewer wants to hear. That you do not trust "delete and commit", that you know history rewrites are disruptive and incomplete, and that you prefer prevention (short-lived credentials, push protection) so that a leak has a small cost.

Check first: who owns the key, what it can access, and since when it was exposed.

  1. Revoke or rotate the key and issue a new one through the secret manager. Check access logs for use, and open a security incident if misused.
  2. Remove it from code in a normal commit (load from a secret store or environment).
  3. History cleaning: for a private repo with a rotated key many teams stop here. For public repos, compliance or high-value secrets, run git filter-repo --replace-text on a mirror, force-push, ask everyone to re-clone, and ask the host to purge cached views and PR refs.
  4. Write a short post-mortem.

Prevent: pre-commit scanner, push protection, CI scanning, short-lived credentials (OIDC roles instead of static keys) and least-privilege keys.

Watch out: cleaning history before rotating, or believing a follow-up "remove key" commit solves it.

Remember: revoke, then fix code, then maybe rewrite. Leaked means rotated.

A big feature branch was merged to main and broke production. How do you back it out cleanly, and ship the fix later? Senior

Roll back the deployment first for speed, then git revert -m 1 MERGE_SHA through a normal PR. When the feature is fixed, revert the revert before merging again, otherwise Git thinks the old commits are already merged.

The two separate problems. (1) Production is broken now. (2) The code on main must be restored and the feature must come back later. Treat them separately and in that order.

1. Stop the bleeding. If your pipeline can redeploy the previous release, do it. It takes minutes and does not depend on Git at all. If the merge included a database migration or data change, check whether rollback is safe, because a code rollback does not undo a schema change. Feature flags would have turned the feature off without any deploy.

2. Clean revert. M has two parents. git show --no-patch --format=%P M prints them: first is the main before the merge, second is the feature tip. git revert -m 1 M creates R, which undoes everything the feature brought in, while keeping everything else that was committed on main afterwards (other people's work). Run CI on the revert PR, merge, redeploy.

3. Shipping the fix later. The feature branch's old commits are still considered "already merged". If you merge the fixed branch directly, you only get the new commits. Two correct ways:

  • git revert R (revert the revert) first, so the old feature code returns, then merge the fixes. Conflicts, if any, are about real changes.
  • Or create a new branch that re-applies the old and new commits (git rebase/cherry-pick onto current main). New ids mean Git sees them as new work.

Check before declaring victory. git diff PRE_MERGE_SHA main --stat should show only the changes that others made after the merge. If the revert touched unrelated files, you resolved a conflict wrongly.

Prevention matters in the answer: smaller PRs, a merge queue and canary deploys catch "green PR, red production", and long-lived branches should merge main in regularly.

Situation: merge commit M is on main and deployed, others have committed on top.

Check first: can I redeploy the previous tag? Confirm M is a merge: git show --no-patch --format=%P M shows two parents.

git switch -c revert-feature main
git revert -m 1 M          # undo the feature side, keep main side
# test, PR, merge, deploy
# later, when the feature is fixed:
git revert REVERT_SHA      # revert the revert: old changes are back
git merge feature-fixed    # only the new fixes need merging

Alternative: rebuild the old and new commits on a fresh branch by rebase or cherry-pick so the merge is not blocked by the earlier merge record.

Prevent: feature flags (switch off without a revert), smaller PRs, canary deploys and a merge queue.

Remember: revert -m 1, and later revert the revert before re-merging.

You rebase a 30-commit branch and hit the same conflict again and again. What now? Intermediate

Abort with git rebase --abort and pick an easier route: merge main into the branch (conflicts solved once), or squash my commits into a few first, or turn on rerere so repeated resolutions replay automatically.

Why it repeats. A rebase replays commits one at a time. Suppose commit 1 changed Config.java line 40, and commit 2 changed it again, and main also changed line 40. You resolve a conflict at commit 1, then commit 2 modifies the same line and conflicts again, and so on for each of the 30 commits. A performance regression appeared sometime in the last 400 commits. How do you find the cause? Intermediate

I use git bisect run with a script that builds and runs the benchmark and exits 1 when it is too slow. 400 commits need only about 9 steps and it runs unattended.

Why bisect fits. You have a known good point (last month's tag) and a known bad point (today). Between them 400 commits, one of which caused the slowdown. Perf regressions are monotonic enough (fast, fast, ..., slow, slow), which is the condition for binary search. The command tests about 9 commits instead of 400.

Making the check automatic. The script is the important part. It must (1) build, (2) run a benchmark, (3) compare to a threshold, and (4) exit with the right code.

#!/bin/sh
./gradlew -q assemble || exit 125          # cannot build: skip this commit
t=$(./run_bench.sh)                        # prints milliseconds
[ "$t" -lt 250 ]                           # exit 0 (good) if fast enough, 1 (bad) if not

Performance numbers are noisy. Use a threshold with margin (for example the good median is 200 ms and the bad median is 400 ms, set the limit at 300 ms), run the benchmark a few times per commit and use the median, and pin the machine (no other jobs).

Then choose: revert the commit, or fix forward by optimising. If it is a big merge commit, rerun inside it with --first-parent first, so you find the faulty merge, then bisect its commits.

Prevent. A performance gate in CI on key benchmarks, tracked over time, so the regression is caught on the PR instead of 400 commits later.

Check first: a repeatable pass/fail test, and a known good tag from last month.

Remember: label first, then move main back.

Push fails because a 300 MB file is in your commit. You deleted it in a later commit and it still fails. Intermediate

Deleting the file in a new commit does not help, because the push still carries the earlier commit that added it. I have to remove it from that commit: amend, interactive rebase, or git filter-repo, and if the file really belongs in the repo I put it under Git LFS.

Why deleting it later does not help. A push sends all commits that the server does not have yet. Your branch is commits C1 (adds the 300 MB file) and C2 (deletes it). The server receives C1 as well, so the file is part of the pushed data and gets rejected (or, where allowed, stored forever and bloating every clone). The deletion in C2 only affects the latest snapshot, not history.

So you must change the commit that added it. Since nothing is pushed yet (the push failed), rewriting local history is safe. Pick the least heavy tool:

  1. Just the last commit: git rm --cached big.bin, add the path to .gitignore, git commit --amend.
  2. A few commits ago: git rebase -i origin/main, mark the commit with edit, remove the file, amend, git rebase --continue. If a later commit touches the file, expect a conflict to resolve.
  3. Several commits or unsure which: git filter-repo --path big.bin --invert-paths (or git rebase over the range). Run it on a fresh clone because it rewrites all history.
  4. The file really belongs in the repo: git lfs track "*.bin" then git lfs migrate import --include="*.bin" --include-ref=refs/heads/feature to convert history into pointers.

Check it worked. git rev-list --objects --all | git cat-file --batch-check='%(objectsize) %(rest)' | sort -n | tail lists the biggest objects. The file should not appear for the commits you will push. Even after a rewrite, the old blob lives in your clone until the reflog expires and gc runs, but it will not be pushed since no pushed commit references it.

If it had been pushed to a remote that accepted it, removing it needs a coordinated history rewrite and repo cleanup on the host, so catching it before the push is much cheaper. A size check in a pre-commit or pre-receive hook is the prevention.

Situation: hosts reject single files above a limit (GitHub blocks files over 100 MB, though limits depend on the host).

  • In the last commit: git rm --cached big.bin then git commit --amend.
  • A few commits back: git rebase -i origin/main, mark that commit edit, remove the file, amend, continue.
  • Many commits: git filter-repo --path big.bin --invert-paths.
  • Needed in the repo: git lfs migrate import --include="*.bin".

Prevent: ignore or LFS rules for that type, a pre-commit size check and a server-side limit.

Remember: history keeps data. Remove it from the commit that added it.

After a teammate's commit, every file in the repo shows as modified. What happened? Intermediate

Usually line endings (CRLF versus LF), or file mode changes. I look at git diff --stat and the raw diff to tell which, then fix it for everyone with a .gitattributes file.

Why a whole repo shows as modified. Git compares bytes. If a file's lines end with CRLF (Windows) in one checkout and LF (Linux, macOS) in another, every line differs. Likewise a changed executable bit shows as a mode change for the file. Neither is a real code change, but Git reports them.

How the mess starts. core.autocrlf is a per-user setting. One developer has true (convert to CRLF on checkout, LF on commit), another has false or input. An editor saves CRLF into a file that is LF in the repo, a script is edited on Windows, or a tool rewrites all files. Then the commit contains whole-file diffs, or later checkouts show everything modified.

Diagnose in 30 seconds.

  • git diff --stat: huge counts with equal lines added and removed suggest line endings.
  • git diff --ignore-space-at-eol --stat or git diff -w --stat: if the diff disappears, it was whitespace or line endings.
  • git diff showing old mode 100644 / new mode 100755 means file modes. git config core.fileMode false hides it locally (typical on Windows or mounted drives).
  • git ls-files --eol shows each file's index and working tree line endings.

The proper fix is in the repository, not in each person's config. Commit a .gitattributes:

* text=auto
*.sh text eol=lf
*.bat text eol=crlf
*.png binary

Then git add --renormalize . and commit it as its own commit, add that commit id to .git-blame-ignore-revs. Teammates should commit or stash first, then refresh (git rm --cached -r . then git reset --hard is the classic way, only after saving work). An .editorconfig and a CI check stop it coming back.

Check first: ^M or lines that look identical means line endings. "old mode 100644 new mode 100755" means file mode (common on Windows or mounted drives): git config core.fileMode false locally. Only whitespace changes point to an auto-formatter.

Fix: add .gitattributes with * text=auto (and explicit rules for scripts), run git add --renormalize ., commit that alone, and add its hash to .git-blame-ignore-revs. Teammates commit or stash their work before refreshing their files. Prevent: the attributes file, .editorconfig and a CI format check.

Remember: everything changed means line endings or modes. Fix it in .gitattributes.
