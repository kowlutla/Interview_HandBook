Version notes used on this page: git switch and git restore arrived in Git 2.23 (2019). The default merge strategy is ort since 2.34 (it replaced recursive). git init still creates master unless you set init.defaultBranch. GitHub and GitLab create main for new repositories, and the Git project has announced that Git 3.0 will make main the default.

Mental model: the 7 ideas everything hangs on

One line: Git is a content-addressed database of snapshots. A commit is a snapshot plus a parent link. A branch is just a movable label on a commit. Almost every command either adds objects or moves a label.
  1. Snapshots, not diffs. Each commit stores the full tree of files at that moment (shared with older commits when unchanged). Diffs are computed on demand.
  2. Content addressing. Every object is named by the hash of its content. Same content gives the same name. Change anything and the name changes.
  3. Commits form a graph (a DAG). Each commit points to its parent(s). History is that graph. It never has cycles.
  4. Refs are cheap labels. Branches, tags and remote-tracking branches are small files holding a commit hash. HEAD says which one you are on.
  5. Three local areas. Working tree (files you edit), index (the next commit you are building), repository (committed history). Plus a remote copy.
  6. Objects are immutable. "Rewriting history" means building new commits and moving a label. The old ones stay until garbage collection, which is why recovery usually works.
  7. Fetch is safe, push is the dangerous one. Fetch only adds to your local copy. Push changes a shared label. Most disasters are a push of the wrong thing.

1. Fundamentals and the object model

What is Git, and how is it different from SVN or Perforce? Basic

Git is a distributed version control system: every clone has the full history, so commit, log, diff and branch all work offline and fast. SVN and Perforce keep history on one central server and need it for most operations. Git also stores snapshots of the whole project, so a branch is only a pointer and costs almost nothing.

Older tools mostly store "what changed per file per revision". Git stores the full tree at each commit and shares unchanged files between commits. In SVN a branch is a directory copy, in Perforce it is a server-side integration. The price of the Git model is that huge binary files and per-file locking are weak spots, which is why Git LFS and partial clone exist. "No central server" is true technically, but teams still agree that one remote (origin) is the source of truth.

Remember: Git = distributed + snapshots + cheap branches. Central tools = one server + file deltas.

Explain the working tree, the index (staging area) and the repository. Why is there a staging area? Basic

The working tree is the files I edit. The index (staging area) is the exact list of file versions that will go into my next commit. The repository is the saved history in .git. I use the index to build clean, focused commits out of a messy working tree.

git add copies the current file contents into the index (file .git/index). git commit turns the index into a tree, wraps it in a commit, and moves the current branch. The index also stores file timestamps and sizes, so git status can skip files that did not change. Because three copies can differ, there are three different diffs:

git diff            # working tree vs index   (unstaged)
git diff --staged   # index vs last commit    (what will be committed)
git diff HEAD       # working tree vs last commit (both together)

A file can be both staged and modified: stage it, edit it again, and the commit gets the staged version only. git add -p stages only some hunks of a file.

Remember: edit, then add, then commit. A commit contains what is in the index, not what is on disk.

What are the four kinds of Git objects? Basic

Blob, tree, commit and annotated tag. A blob holds the bytes of one file. A tree is a directory listing that points to blobs and other trees. A commit points to one top-level tree plus its parent commits and the message. An annotated tag is a named pointer to another object, with its own message.

All four live in .git/objects, compressed, and are named by the hash of their content. File names are stored in the tree, not in the blob, so two files with the same content share one blob. An unchanged file is the same blob in every commit, which is why snapshots are cheap.

git cat-file -p HEAD         # tree, parent, author, message
git ls-tree -r HEAD          # every file with mode and blob hash

Git cannot store an empty directory (no blob to hold), so people add a .gitkeep file.

Remember: blob = file bytes, tree = folder, commit = snapshot + parents, tag = named pointer.

What exactly is inside a commit? Does it store a diff? Basic

No diff. A commit stores the hash of one root tree, the hashes of its parents, author and committer (name, email, time) and the message. It does not store the branch name either. The commit hash is computed from all of that text.

A root commit has no parent, a normal commit has one, a merge commit has two or more. Author and committer can differ: when someone rebases or cherry-picks your commit, you stay the author and they become the committer. A repo can have several root commits, for example after merging unrelated histories.

$ git cat-file -p HEAD
tree 9f1c...
parent 4be7...
author Asha <asha@example.com> 1731800000 +0530
committer Asha <asha@example.com> 1731800000 +0530

Fix null check in payment retry

Remember: commit = tree + parents + author + committer + message. Diffs and branch names are not stored.

Why does rewriting one old commit change every commit after it? Intermediate

Because a commit's hash includes its parent's hash. If I change commit B, it gets a new hash. Commit C recorded the old B as its parent, so C must be rebuilt to point to the new B, and that gives C a new hash too. This continues up to the branch tip.

The file contents (blobs and trees) are reused. Only the commit objects are new. This hash chain makes history tamper-evident: nobody can quietly edit the past. It is also why force-pushing a rewritten branch hurts teammates: their old commits and your new ones no longer share hashes, so Git sees two different histories.

Remember: parent hash is part of the child's hash, so one change ripples to the tip.

What is a branch, really? Why is creating one so cheap? Basic

A branch is just a tiny file holding one commit hash. Creating a branch writes that small file and copies nothing. "Being on a branch" means that when I commit, Git makes the new commit and moves that file to it.

The file is .git/refs/heads/<name>, about 41 bytes (or a line in packed-refs). Deleting a branch deletes only the label. Commits no longer reachable from any label stay on disk until garbage collection, which by default waits weeks, so a deleted branch is usually recoverable.

Remember: a branch is a 41-byte label on a commit. Moving it is cheap, deleting it deletes no commits.

What is HEAD? What do HEAD~1, HEAD^, HEAD^2 and HEAD@{1} mean? Basic

HEAD is "where I am now": normally a pointer to the current branch, which points to a commit. HEAD~1 and HEAD^ both mean the first parent. HEAD^2 means the second parent of a merge commit, the branch that was merged in. HEAD@{1} is different: it means where HEAD was one move ago, taken from the reflog.

.git/HEAD usually contains ref: refs/heads/main. ~N walks N steps back along first parents. ^N chooses which parent of one commit. They are the same for ordinary commits and differ only on merges. @{n} and main@{yesterday} use your local reflog, not ancestry.

Watch out: HEAD@{1} is "previous position of HEAD" (could be on another branch), not "the parent".

Remember: ~ goes back along first parents, ^ picks a parent, @{} reads the reflog.

What happens inside Git when you run git add and git commit? Intermediate

git add writes the file content as a blob object and records its hash in the index. git commit builds tree objects from the index, creates a commit pointing to that tree and to the current commit as parent, then moves the current branch to the new commit.

Detail: trees are written bottom up, one per directory. A line is appended to the reflog. Hooks such as pre-commit and commit-msg run before the commit object is made. If I add a file and edit it again before committing, the commit holds the version from the time of add. commit -a stages changes to already-tracked files first; new files are not included.

echo hi > a.txt
git add a.txt            # blob created, index updated
git commit -m "add a"    # tree + commit created, main moves

Remember: add = blob + index entry. Commit = tree + commit + branch moves.

git checkout does too many things. What replaced it? Basic

Since Git 2.23, git switch changes branches and git restore restores files. The old checkout did both and also detached HEAD, which confused people. It still works.

git switch -c fix/login          # create and switch
git switch -                     # back to previous branch
git switch --detach v1.4.0       # look at a tag, no branch
git restore --staged app.py      # unstage
git restore app.py               # discard edits (cannot be undone)
git restore --source=HEAD~2 app.py   # file from an older commit

Key safety fact: restoring the working tree overwrites uncommitted work, and that data was never in a commit, so there is no way back.

Remember: switch = branches, restore = files. Discarding uncommitted edits is permanent.

2. Branches and merging

What is a fast-forward merge, and when does Git create a merge commit instead? Basic

If the branch I merge into has not moved since the other branch split off, Git just slides my branch label forward. That is a fast-forward: no new commit and the history stays a straight line. If both branches have new commits, Git does a three-way merge and records a merge commit with two parents.

I can force a merge commit with --no-ff, which leaves a visible "this feature landed together" point that is easy to revert as one unit. I can refuse anything but a fast-forward with --ff-only, and make that the default with git config merge.ff only.

git merge feature            # ff if possible, else merge commit
git merge --no-ff feature    # always a merge commit
git merge --ff-only feature  # fail instead of creating a merge commit

Remember: fast-forward = move a label. Diverged branches = merge commit with two parents.

How does a three-way merge decide what to keep? What is the merge base? Intermediate

Git finds the merge base, the best common ancestor of the two tips. For each file it compares base to ours and base to theirs. If only one side changed a region, Git takes that change. If both changed the same region differently, that is a conflict and a human decides.

The base is what lets Git tell "I changed this" from "they changed this". A plain two-way compare cannot do that. If the same change was made on both sides, it is taken once. Git merges text lines, not meaning, so a merge can be clean and still break the build. That is why CI should run on the merged result. With several possible bases (criss-cross merges) the default ort strategy first merges the bases into a virtual one.

git merge-base main feature     # show the base commit

Remember: one side changed, take it. Both changed the same spot differently, conflict.

You get a merge conflict. What exactly do you do? Basic

I run git status to see the "both modified" files, open each one, and decide the final content between the conflict markers. Often it is a mix of both sides. Then I remove the markers, build and test, git add the files, and finish with git commit (or git rebase --continue in a rebase). If it goes badly, git merge --abort takes me back to before the merge.

I set merge.conflictStyle zdiff3 (Git 2.35+, diff3 on older) so the markers also show the base text, which makes the decision much easier. If I do not understand the other change, I ask its author.

<<<<<<< HEAD
timeout = 30
||||||| base
timeout = 10
=======
timeout = 20
>>>>>>> feature

git diff --name-only --diff-filter=U   # list conflicted files
git checkout --ours file               # take a whole file from one side
Watch out: committing with markers left in, taking one side blindly, and skipping tests after the resolution.

Remember: edit, remove markers, test, add, continue. Abort is always available.

In a conflict, which side is "ours" and which is "theirs"? Why is it swapped during rebase? Intermediate

In a merge, "ours" is the branch I am on and "theirs" is the branch I merge in. In a rebase it looks swapped: "ours" is the branch I am rebasing onto, and "theirs" is my own commit being replayed. The rule is the same in both: "ours" is whatever HEAD currently is.

During a rebase Git first moves HEAD to the new base (say updated main), then replays my commits one at a time on top of it. So HEAD is main's version and the incoming change is mine. To avoid mistakes I read the marker labels and avoid --ours and --theirs during a rebase unless I am sure.

# during rebase onto main, keep MY version of the file:
git checkout --theirs path/file
# during a merge of feature into main, keep the main version:
git checkout --ours path/file

Remember: ours = HEAD. In a rebase, HEAD is the base, so my own commits are "theirs".

Merge commit, squash merge, rebase merge: what is the difference, and which would you pick? Intermediate

A merge commit keeps every branch commit and adds one joining commit. A squash merge turns the whole branch into one new commit on main. A rebase merge replays each commit onto main with new hashes. I pick squash for teams with messy work-in-progress commits, merge commits for long-lived or release branches, and rebase merge only when each commit is clean and builds.

Trade-offs. Merge commit: full fidelity but noisy graph. Squash: clean, one commit per PR and easy revert, but individual commits are lost. Rebase merge: linear with all commits, but every hash changes, and a non-green middle commit breaks bisect.

Remember: merge = keep shape, squash = one commit per PR, rebase = linear copy.

What is a detached HEAD, and how do you not lose work in it? Basic

Detached HEAD means HEAD points straight at a commit instead of at a branch. It happens when I check out a tag or a hash, and during rebase or bisect. Commits I make there have no branch, so after I switch away they look lost. To keep them I create a branch right there: git switch -c rescue.

If I already left, the commits are still in the reflog for weeks: git reflog to find the hash, then git branch rescue HASH. Detached HEAD is useful for inspecting an old release or running a build of a tag.

Remember: commits with no label get lost. Name them with a branch before you leave.

3. Rebase and history

What is the difference between merge and rebase? Basic

Merge joins two branches with a merge commit and keeps history exactly as it happened. Rebase re-applies my commits on top of the new base, so history becomes a straight line, but those commits get new hashes. I rebase my own private branches and merge shared ones.

The content is the same either way. Rebase gives cleaner history, and merge is safer because it never rewrites anything. The old commits stay in the object store and reflog until garbage collection.

Remember: merge keeps history, rebase rewrites it. Never rebase what others already have.

What is the "golden rule of rebase", and what actually goes wrong if you break it? Intermediate

Never rebase commits that other people already have. Rebase makes copies with new hashes, and I then have to force-push to replace the originals. A teammate who pulled the old commits now has history that has diverged from mine.

If they then pull with merge, both the old and the new versions of the same changes get merged: duplicate commits, repeated conflicts, and sometimes already-removed work coming back. I only rewrite branches that I own. For a shared feature branch I agree it with the team first, and always push with --force-with-lease. My own open PR branch is normally fine to rebase.

Remember: rewrite only what is yours. Force pushes belong to your own branches.

I finished a rebase and it is wrong. How do I undo it? Intermediate

If nothing else has happened since, git reset --hard ORIG_HEAD puts the branch back to where it was before the rebase. Otherwise I look in git reflog, find the entry just before "rebase (start)" and reset to that hash.

This works because rebase only copies commits and moves a label. The originals still exist until garbage collection. If I already force-pushed, I reset locally and force-push again with --force-with-lease, after telling anyone who pulled in between.

git reflog                       # find "rebase (start)" and the line above it
git reset --hard HEAD@{5}        # or the hash you found

Remember: rebase never destroys the old commits quickly. ORIG_HEAD or reflog finds them.

What can you do with git rebase -i? Intermediate

git rebase -i main opens a list of my commits, oldest first, and I change the verb on each line. I use it to squash small commits, reword messages, reorder, drop a commit, or stop to split one. I do this before opening a PR so reviewers see a clean story.

  • pick keep it, reword change the message, edit stop to amend or split.
  • squash meld into the previous commit and combine messages, fixup same but drop its message.
  • drop remove it. exec cmd runs a command after a step, for example the tests.
pick   a1b2c3 Add parser
fixup  d4e5f6 typo
reword 7a8b9c Add validation
drop   0f1e2d debug logging
exec   mvn -q test

To split a commit: mark it edit, run git reset HEAD^, stage and commit in pieces, then git rebase --continue. An empty todo list aborts the rebase.

Remember: pick, reword, edit, squash, fixup, drop. Only on commits not yet shared.

Explain git rebase --onto with a real example. Senior

git rebase --onto NEWBASE OLDBASE BRANCH replays the commits in OLDBASE..BRANCH on top of NEWBASE. It lets me move a slice of history. Typical case: topic-b was built on topic-a, topic-a got squash-merged to main, so I run git rebase --onto main topic-a topic-b to move only topic-b's own commits.

A plain git rebase main here would also replay topic-a's old commits and conflict with their squashed copy. The same tool can cut a range out of the middle of a branch.

Remember: --onto NEW OLD BRANCH = move the commits between OLD and BRANCH to NEW.

You are mid-rebase, with conflicts. What commands do you have, and what if you get lost? Intermediate

Fix the files, git add them, then git rebase --continue. --skip drops the current commit, for when upstream already has the same change. --abort returns everything to how it was before the rebase and is always safe. If I am lost, I abort and try a simpler route.

Simpler routes: squash my commits first so there is only one set of conflicts, merge main into the branch instead, or turn on rerere. git status shows which step I am on ("2 of 7"). Remember that "ours" and "theirs" are swapped here. After finishing I run tests and use git range-diff to compare the old and new series.

git range-diff main ORIG_HEAD HEAD

Remember: continue, skip, abort. Abort is the free escape hatch.

What does git pull do, and should you use pull --rebase? Intermediate

git pull is git fetch plus a merge. If I have local commits and the remote also moved, that creates a noisy "Merge branch main of origin" commit. I prefer git pull --rebase, or pull --ff-only, so I choose what happens and history stays linear.

Rebasing is safe here because my local commits are not shared yet. I set it once with git config --global pull.rebase true. Recent Git versions warn until you choose a pull strategy. --autostash stashes my dirty files around the pull.

git config --global pull.rebase true
git config --global rebase.autoStash true
git pull --ff-only          # fail instead of creating a hidden merge

Remember: pull = fetch + merge. Prefer rebase or ff-only to avoid noise merges.

4. Remotes and workflows

What is a remote, and what is a remote-tracking branch like origin/main? Basic

A remote is a named URL in my config, and origin is just the default name from git clone. A remote-tracking branch like origin/main is a read-only local label that records where main was on the server the last time I talked to it. Only fetch, pull and push move it, so it can be stale.

A local branch can have an upstream, which links it to a remote-tracking branch. That link is what makes plain git pull, git push and the "ahead 2, behind 1" line in git status work.

git remote -v
git branch -vv                       # upstream and ahead/behind per branch
git push -u origin feature           # push and set upstream
git config --global push.autoSetupRemote true   # Git 2.37+

Remember: origin/main is my last known copy of the server, not the server itself.

What is the difference between fetch, pull and clone? Basic

clone copies the whole repository and sets up origin. fetch downloads new commits and updates my origin/* labels, but never touches my branches or files, so it is always safe. pull is fetch plus a merge or rebase into my current branch, so it can change my files and cause conflicts.

A careful habit: fetch first, look at what came in with git log HEAD..origin/main, then decide to merge, rebase or wait.

Remember: fetch looks, pull changes my branch. Fetch first when in doubt.

Your push is rejected with "non-fast-forward" or "fetch first". What does it mean and what do you do? Basic

It means the remote branch has commits I do not have, so moving it to my commit would throw those away. Git only allows a push that fast-forwards. I run git fetch, then git rebase origin/feature (or merge), test, and push again. I do not reach for --force, because that would delete my colleague's commits from the server.

Force is only correct when I rewrote my own history on purpose, such as an amend or rebase of my own branch, and then I use --force-with-lease.

Remember: rejected = I am behind. Fetch and integrate, do not force.

What is --force-with-lease and why is it better than --force? Intermediate

--force overwrites the remote branch no matter what is there. --force-with-lease overwrites it only if the remote is still where I last saw it, so if a teammate pushed meanwhile, my push fails and their work survives. It is a compare-and-swap, and it should be the only force I ever use.

One caveat: if an IDE or a background job fetched in between, my tracking ref is already updated and the lease passes even though I never looked at the new commits. --force-if-includes (Git 2.30+) adds a check that my local history actually contains the remote tip. I can also pin the expected value: --force-with-lease=feature:SHA.

git push --force-with-lease --force-if-includes origin feature
git config --global alias.pushf "push --force-with-lease --force-if-includes"

Nobody should force-push to main at all: protect it on the server.

Remember: lease = "only if nobody else pushed since I looked".

Explain the fork-and-pull-request workflow, and how you keep a fork in sync. Intermediate

I fork the repo (my own server copy), clone my fork, and add the original as a second remote called upstream. I work on a topic branch, push it to my fork (origin), and open a PR to upstream. To stay in sync I fetch upstream and fast-forward my fork's main to it.

git remote add upstream https://example.com/org/repo.git
git fetch upstream
git switch main && git merge --ff-only upstream/main
git push origin main

Remember: origin = my fork, upstream = the real repo. Keep my main as a clean mirror.

Compare Git Flow, GitHub Flow and trunk-based development. Which would you choose? Senior

I choose by how the product is released. For web services deployed continuously I use trunk-based development or GitHub Flow: short branches, PRs, and deploy from main. For versioned products that ship on a schedule and support old versions, I use main plus release branches, and Git Flow only if the team already works that way.

Git Flow has long-lived develop and main, plus feature, release and hotfix branches. It adds merge overhead and delays integration. GitHub Flow has one long-lived branch and short feature branches. Trunk-based goes further: everyone integrates into main at least daily, branches live hours, and unfinished work hides behind feature flags. DORA research links trunk-based practice with higher delivery performance.

Remember: continuous deploy = trunk or GitHub Flow. Shipped versions with long support = release branches.

5. Commits, pull requests and safeguards

What makes a good commit and a good commit message? Basic

A good commit is atomic: one logical change that builds and passes tests on its own, so it is easy to review, revert and cherry-pick. The message has a short imperative subject of about 50 characters, a blank line, and a body that explains why, since the diff already shows what.

I do not mix a refactor, a format sweep and a bug fix in one commit. In the body I mention side effects, trade-offs and the ticket id, so that someone running git blame in two years understands the reason. I never commit secrets, generated files or large binaries. Some teams use Conventional Commits (feat(api): add paging), which tools turn into changelogs and version bumps.

Retry payment capture on 502 from gateway

The gateway returns 502 during its nightly failover (about 30 s).
Retry up to 3 times with backoff, only for idempotent captures.
Refs PAY-1234

Remember: one change per commit. Subject says what, body says why.

What safeguards would you put on the main branch? Intermediate

Branch protection on the server: no direct pushes, no force pushes, no deletion. Changes only through a pull request with at least one approval, code-owner review for sensitive paths, and required status checks (build, tests, lint, security scan) passing. I apply the rules to admins as well, so "one emergency push" never becomes normal.

Extras: dismiss stale approvals when new commits arrive, require resolved conversations, optionally require signed commits or linear history, and turn on secret scanning with push protection. "Require branch to be up to date" is safe but costly, since every merge makes others rebase and re-run CI. A merge queue fixes that.

Remember: PR + review + green checks + no force push. Enforce on the server, for admins too.

What are Git hooks? Why can they not be your only safeguard? Intermediate

Hooks are scripts Git runs at certain events, kept in .git/hooks. Client side: pre-commit (lint, secret scan), commit-msg (message format), pre-push (tests). Server side: pre-receive and update reject bad pushes. They cannot be the only safeguard because client hooks are not copied by clone and anyone can skip them with --no-verify.

I share client hooks with core.hooksPath pointing to a tracked folder, or with tools like pre-commit, Husky or Lefthook. Real enforcement lives on the server: branch protection, required CI checks and server hooks, because the client is not trusted.

git config core.hooksPath .githooks
git commit --no-verify     # skips pre-commit and commit-msg

Remember: hooks help the developer, server rules protect the repo.

How do you stop secrets from being committed in the first place? Intermediate

I use several layers. Locally a pre-commit scanner (gitleaks, detect-secrets, trufflehog). On the server the platform's push protection rejects known token patterns. In CI a scan job on every PR. And by design: secrets live in a vault or the platform's secret store and reach the app through environment variables, and the repo holds only templates like .env.example.

Deleting a secret in a later commit does not remove it from history. The real answer to a leak is to rotate the credential first, then clean history if needed.

Remember: prevent in layers, but once leaked, rotate.

6. Undoing things and selective apply

Explain git reset --soft, --mixed and --hard. Basic

git reset COMMIT always moves the current branch to COMMIT. The mode decides what else changes. --soft moves only the branch, so the undone changes stay staged. --mixed (the default) also resets the index, so the changes stay in my files but unstaged. --hard resets branch, index and files, so uncommitted work is gone for good.

Use soft for "redo this commit", mixed for "uncommit and stage differently", hard for "throw it all away". Committed work lost by a hard reset can be recovered through the reflog, but uncommitted changes cannot. --keep is a safer hard that refuses if it would overwrite local changes. With a path, git reset file just unstages that file and moves no branch.

git reset --soft HEAD~1        # undo commit, keep changes staged
git reset HEAD~1               # undo commit, keep changes unstaged
git reset --hard origin/main   # make local branch identical to remote

Remember: soft moves 1 area, mixed 2, hard 3. Hard is the only one that loses uncommitted work.

When do you use revert and when reset? Basic

If the commit is already pushed and others may have it, I use git revert: it adds a new commit that undoes the old one, so history only grows. If the commit exists only on my machine, I use git reset or amend, because rewriting private history hurts nobody.

Revert also leaves an audit trail ("Revert X because it broke checkout"). I can revert several commits with git revert OLD..NEW, or add -n to stage the inverse without committing, to combine several reverts in one commit.

git revert 4be7d2a
git revert -n HEAD~3..HEAD     # inverse of the last 3, uncommitted

Remember: shared = revert. Private = reset.

How do you revert a merge commit, and what is the trap when you merge the branch again? Senior

A merge commit has two parents, so I must tell Git which one is the mainline: git revert -m 1 MERGE_SHA keeps parent 1 and undoes what came from the other side. The trap is that Git still remembers the merge. If I fix the feature and merge again, only the new commits come in, and the original changes stay missing. First I revert the revert, then merge the fixes.

The alternative is to rebuild the feature as fresh commits (cherry-pick or rebase onto a new branch) and merge that branch.

Remember: revert -m 1 for the merge. To re-merge later, revert the revert first.

How do you fix the last commit (message or content)? What changes in history? Basic

git commit --amend replaces the last commit with a new one. For just the message, git commit --amend -m "better message". To add a forgotten file, stage it and run git commit --amend --no-edit. Fine if unpushed. If it was pushed, I need a force-push, which affects anyone who pulled it.

The old commit is not edited. A new commit with a new hash takes its place, and the old one stays in the reflog. For an older commit I use interactive rebase with reword or edit, or a fixup commit plus autosquash. --reset-author fixes the author of the last commit.

Remember: amend = replace the last commit. Safe only before push.

How does git stash work, and what are its limits? Basic

git stash saves my uncommitted changes and resets the working tree to HEAD, so I can switch tasks. git stash pop re-applies the latest stash and removes it, apply re-applies and keeps it. By default untracked files are not stashed; -u adds them and -a adds ignored files too.

Internally a stash is a commit with two or three parents (HEAD, the index state, and optionally untracked files), stored under refs/stash. Limits: it is local and private, it can conflict on pop, and a dropped stash is recoverable only until garbage collection, via git fsck --unreachable | grep commit. Name stashes with -m so I can find them later.

git stash push -u -m "wip: parser"
git stash list
git stash pop            # or: git stash apply stash@{1}
git stash branch fix-x   # make a branch from a stash

Remember: stash = temporary commits on the side. Add -u for new files, name your stashes.

What does cherry-pick do, and what are its risks? Intermediate

git cherry-pick SHA takes the change introduced by one commit and applies it on my current branch as a new commit with a new hash, keeping the author. I use it to backport a fix to a release branch. The risks: the same change now exists twice under different hashes, and the commit may depend on earlier commits I did not pick.

I pass -x to record "(cherry picked from commit ...)" in the message, which helps traceability on backports. A merge commit needs -m 1. A later merge of the original branch often copes with the duplicate but can conflict. Heavy cherry-picking is a sign the branching model needs work.

git switch release/1.4
git cherry-pick -x 4be7d2a
git cherry-pick --continue    # or --abort

Remember: cherry-pick copies a change, not history. Use -x on backports.

You pushed a bad commit to a shared branch. What do you do? Intermediate

First stop the damage: tell the team, and if it is deployed, roll the deployment back, which is faster than a code fix. Then git revert BAD_SHA and push the revert as a normal commit, through the usual PR if the branch is protected. This keeps everyone's history valid.

I rewrite shared history only if the commit contains a secret or a huge file, and then with team coordination (and I rotate the secret anyway). Afterwards I add the missing test or check, and note in the PR why it was reverted so a re-land is done carefully.

Remember: roll back the deploy first, revert in Git second, never rewrite shared history.

A file is in .gitignore but Git still tracks it. Why, and how do you fix it? Basic

Ignore rules apply only to files Git is not yet tracking. If the file was committed earlier, it stays tracked. I run git rm --cached path (with -r for folders) and commit, which stops tracking but keeps the file on disk.

That does not remove it from history, so a leaked secret still needs rotating. git check-ignore -v path shows which rule matches. Place rules by scope: project-wide in .gitignore, personal editor files in a global file (core.excludesFile), local-only in .git/info/exclude. For a tracked config file that each dev edits, keep a template file and a local untracked copy; update-index --skip-worktree is fragile.

Remember: .gitignore only affects untracked files. Use rm --cached to untrack.

7. History, debugging and recovery

What is the reflog and how does it save you after a bad reset or rebase? Intermediate

The reflog is a local journal of where HEAD and each branch pointed over time. After a bad reset --hard or rebase, the commits are not gone, the branch label just moved away. I run git reflog, find the line from before the mistake, and restore with git reset --hard HEAD@{4} or make a branch at that hash.

Limits: it is local only (a fresh clone has none), and entries expire: 90 days for reachable ones and 30 days for unreachable ones by default. Uncommitted changes never enter the reflog. For one branch, use git reflog show feature.

Remember: committed work is almost never lost. Reflog first, panic never.

What does "reachable" mean, and when does Git actually delete things? Senior

An object is reachable if I can get to it from a ref (branch, tag, HEAD, stash, remote-tracking branch, reflog entry) by following parent and tree pointers. Everything else is unreachable. Git never deletes at once: git gc prunes unreachable loose objects only after they are older than 2 weeks, and reflog entries protect commits for 30 to 90 days.

The flip side matters for secrets: after rewriting history to remove a leaked file, old objects remain in my clone, in forks and in the host's caches until pruned.

git reflog expire --expire=now --all
git gc --prune=now      # destructive; only when you are sure

Remember: unreachable does not mean deleted. Weeks of grace, which is both rescue and leak.

How does git bisect work, and how do you automate it? Intermediate

Bisect finds the commit that introduced a bug by binary search. I mark the current commit bad and an old one good, Git checks out the middle, I test and say good or bad, and the range halves each time. 1,000 commits need about 10 steps. I automate it with git bisect run ./script.sh.

The script exits 0 for good, 1 to 127 (except 125) for bad, and 125 to skip a commit that cannot be tested (for example it does not build). git bisect reset returns me to my branch. Pitfalls: flaky tests give wrong answers, so the check must be deterministic. On merge-heavy mainlines use --first-parent.

git bisect start
git bisect bad                 # current commit is broken
git bisect good v2.3.0
git bisect run ./test_repro.sh # exit 0 good, 1 bad, 125 skip
git bisect reset

Remember: bisect = binary search over commits. 1,000 commits is about 10 tests.

How do you find who changed a line and why, and how do you skip formatting commits in blame? Intermediate

git blame file shows, for each line, the last commit that changed it. I read that commit with git show SHA to learn the reason and follow the ticket id. For mass-reformat commits that hide the real author, I list their hashes in .git-blame-ignore-revs and use git blame --ignore-revs-file.

Useful flags: -L 40,60 for a range, -w to ignore whitespace, -M and -C to follow lines moved or copied between places and files. Set blame.ignoreRevsFile once, and note that GitHub reads that file name by itself. Blame is for understanding, not for blaming people.

git blame -L 40,60 -w src/Pay.java
git config blame.ignoreRevsFile .git-blame-ignore-revs

Remember: blame, then show the commit, and ignore the reformat commits.

How do you search history for when a line, a function or a string was added or removed? Intermediate

I use the pickaxe: git log -S"retryCount" lists commits where the number of occurrences of that string changed, so it finds where it was added or removed. -G"regex" matches diff lines by regex. git log -L :funcName:file shows the history of one function with its diffs.

Other filters: --author, --since, --grep (commit message), -- path, --diff-filter=D for deleted files, --no-merges. git log --graph --oneline --decorate --all draws history. To search file contents at a given commit use git grep pattern REV.

git log -S"timeout" --oneline -- src/
git log --diff-filter=D --name-only -- "*Config.java"   # who deleted it
git log -L :parseHeader:src/Parser.java

Remember: -S = string count changed, -G = regex in diff, -L = function history.

8. Tags, releases and backports

Lightweight tag versus annotated tag: what is the difference and which for releases? Basic

A lightweight tag is just a name pointing at a commit, like a branch that never moves. An annotated tag is a real object with a tagger, date and message, and it can be signed. I use annotated tags for releases, because they record who tagged it and why, work with git describe, and many tools only treat annotated tags as releases.

Tags are not pushed by default: git push origin v1.4.0, or git push --follow-tags for annotated tags on pushed commits. A published tag should never move, because caches and consumers rely on it. If I tagged the wrong commit, I release a new version instead.

git tag -a v1.4.0 -m "Release 1.4.0"
git tag -s v1.4.0 -m "Release 1.4.0"     # signed
git push origin v1.4.0
git tag -d v1.4.0 && git push origin :refs/tags/v1.4.0   # delete (avoid for released tags)

Remember: releases get annotated tags. Push them explicitly. Never move a published tag.

How would you manage release branches and versions for a product that supports several versions at once? Senior

I develop on main and cut release/1.4 when a version is feature-complete. Only bug fixes go on a release branch. I tag each release from it (v1.4.0, then v1.4.1) using semantic versioning. The rule for fixes is: fix on main first, then cherry-pick to each supported release branch with -x, so no fix is ever lost in a future version.

Some teams do the opposite: fix on the oldest affected branch and merge forward. That keeps ancestry clean but needs a clear merge path. I automate release builds from the tag, generate notes from merged PRs, sign artifacts, and retire branches on a published support schedule. Semantic versioning: major for breaking changes, minor for features, patch for fixes.

Remember: fix main first, then backport. Tag every release from its branch.

Walk through backporting a fix from main to an older release branch. Intermediate

Fix and merge on main first, with a test. Then I branch from the release branch (not main), run git cherry-pick -x SHA, resolve conflicts, run the release branch's full tests, and open a PR into release/1.4 that links the original PR. After merging I tag the patch release, for example v1.4.1.

If the fix was squash-merged on main there is one commit to pick; if it was several commits, pick them in order. I check that the fix does not depend on other changes missing from the old branch. Many platforms offer a backport bot or label that does these steps.

git switch -c backport/1.4-fix release/1.4
git cherry-pick -x 4be7d2a

Remember: main first, branch from the release, cherry-pick -x, test, PR, tag.

9. Configuration, hygiene and performance

What is Git LFS and what are its trade-offs? Intermediate

Git LFS (Large File Storage) stores big files outside the repo on an LFS server and keeps only a small text pointer in Git. Clones stay small and fast, and I download only the versions I check out. The cost is extra setup: server support, quotas, and an LFS install on every machine and CI runner.

I enable it with git lfs track "*.psd", which writes rules to .gitattributes. Files already in history stay there unless I rewrite history with git lfs migrate import. Alternative: keep binaries in an artifact store (Nexus, Artifactory, S3) and reference them by version.

Remember: LFS = pointers in Git, bytes on a server. Migrating old history needs a rewrite.

Submodules, subtree or a monorepo: how do you share code between repositories? Senior

My first choice for shared code is a versioned package from a registry. Where the source must be pinned and built together, a submodule embeds another repo at an exact commit. Subtree copies the other project's files into a folder. A monorepo puts everything in one repo and needs tooling to stay fast.

  • Submodule: the parent stores only a pointer to a commit. Exact and clean, but clones need --recurse-submodules, updates are two steps, and people forget to push the submodule first, leaving the parent pointing to a commit nobody can fetch.
  • Subtree: no extra clone steps, but history is mixed and syncing is manual.
  • Monorepo: atomic cross-project changes and one version of dependencies, but needs partial clone, sparse checkout, a build graph and code owners.
git clone --recurse-submodules URL
git submodule update --init --recursive
git config submodule.recurse true

Remember: package first, submodule to pin source, monorepo for atomic change.

What is git worktree and when is it better than stash or a second clone? Intermediate

git worktree add ../hotfix release/1.4 creates a second working folder for the same repo, on another branch, sharing one object database. I use it to fix a release branch or review a PR while my feature work sits untouched, with no stash, no dirty tree and no second full clone.

Rule: a branch can be checked out in only one worktree at a time. Clean up with git worktree remove and git worktree prune.

git worktree add ../app-hotfix -b hotfix/x release/1.4
git worktree list
git worktree remove ../app-hotfix

Remember: worktree = another folder, same repo, different branch, no stash.

10. Real-life scenarios

Each scenario starts with the one-sentence diagnosis and fix you can say first. Then it follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Saying this shape aloud shows you work calmly under pressure.

A teammate force-pushed over main and the last 15 commits disappeared. What do you do? Senior

The 15 commits still exist as objects. Only the main label moved. I freeze pushes, find the old tip from any recent clone, CI run or the host's push log, put a branch on it, and move main back with a lease-protected push.

Situation: remote main points to an older or different commit. Nothing is deleted yet.

Check first: tell the team not to pull or reset, and not to run git gc. Find OLD_SHA from a teammate's git reflog show origin/main, the last green CI build, PR merge records, or the host's audit log. The host support can also restore from a server-side reflog.

git fetch origin
git reflog show origin/main            # on a machine that still has the old tip
git branch rescue-main OLD_SHA
git push origin rescue-main            # safe copy first
git push --force-with-lease=main:BAD_SHA origin OLD_SHA:main

Fix: lift branch protection briefly if it blocks the push, restore main, then re-apply any valid new commits on top by cherry-pick or merge. Everyone then fetches and resets their local main.

Prevent: branch protection that blocks force pushes and deletions on main for everyone including admins, and an alert on forced updates of protected refs.

Remember: find the old SHA, label it, move main back. Never run gc.

Someone committed and pushed a cloud access key. What are the steps, in order? Senior

Rotate the key first, clean history later. I assume it is already stolen, because scanners find leaks in minutes. Then I remove it from code, check the provider logs for misuse, and only then decide whether a history rewrite is worth it.

Check first: who owns the key, what it can access, and since when it was exposed.

  1. Revoke or rotate the key and issue a new one through the secret manager. Check access logs for use, and open a security incident if misused.
  2. Remove it from code in a normal commit (load from a secret store or environment).
  3. History cleaning: for a private repo with a rotated key many teams stop here. For public repos, compliance or high-value secrets, run git filter-repo --replace-text on a mirror, force-push, ask everyone to re-clone, and ask the host to purge cached views and PR refs.
  4. Write a short post-mortem.

Prevent: pre-commit scanner, push protection, CI scanning, short-lived credentials (OIDC roles instead of static keys) and least-privilege keys.

Watch out: cleaning history before rotating, or believing a follow-up "remove key" commit solves it.

Remember: revoke, then fix code, then maybe rewrite. Leaked means rotated.

A big feature branch was merged to main and broke production. How do you back it out cleanly, and ship the fix later? Senior

Roll back the deployment first for speed, then git revert -m 1 MERGE_SHA through a normal PR. When the feature is fixed, revert the revert before merging again, otherwise Git thinks the old commits are already merged.

Situation: merge commit M is on main and deployed, others have committed on top.

Check first: can I redeploy the previous tag? Confirm M is a merge: git show --no-patch --format=%P M shows two parents.

git switch -c revert-feature main
git revert -m 1 M          # undo the feature side, keep main side
# test, PR, merge, deploy
# later, when the feature is fixed:
git revert REVERT_SHA      # revert the revert: old changes are back
git merge feature-fixed    # only the new fixes need merging

Alternative: rebuild the old and new commits on a fresh branch by rebase or cherry-pick so the merge is not blocked by the earlier merge record.

Prevent: feature flags (switch off without a revert), smaller PRs, canary deploys and a merge queue.

Remember: revert -m 1, and later revert the revert before re-merging.

The repository is 12 GB, a fresh clone takes 40 minutes, and CI is slow. What is your plan? Senior

First find out why it is big: many files, long history, or large blobs. Then use the right tool: shallow or blobless clones in CI, partial clone plus sparse-checkout for developers, and move big binaries out of history. Do not just buy a faster machine.

Check first: git count-objects -vH, then list the biggest blobs:

git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n -r | head
  • CI: --depth 1 or --filter=blob:none, a cached mirror, and sparse checkout for needed paths.
  • Developers: git clone --filter=blob:none --sparse, git maintenance start, core.fsmonitor.
  • Root cause: remove big binaries from history with git filter-repo or git lfs migrate (coordinated rewrite, everyone re-clones), and add a server-side size limit.
  • For a true monorepo add build caching and ownership, not just Git tuning.

Prevent: size limits on push, LFS or an artifact store for binaries, no generated files in Git.

Remember: measure the blobs, then shallow for CI, partial + sparse for devs, clean history once.

You made commits in detached HEAD, switched back to main, and now they seem gone. Basic

They are not gone. They just have no branch. I run git reflog, find the hash of my last commit, and run git branch rescue HASH.

Check first: do not run gc. The reflog shows the commit entry just before the "checkout: moving from HASH to main" line.

git reflog
# 7c1a9e2 HEAD@{1}: commit: fix retry logic     (your work)
git branch rescue 7c1a9e2
git switch rescue

Prevent: read the "you are leaving N commits behind" warning, and run git switch -c name as soon as I decide to keep work from a detached state.

Remember: unlabeled commits live in the reflog. Label them quickly.

You rebase a 30-commit branch and hit the same conflict again and again. What now? Intermediate

Abort with git rebase --abort and pick an easier route: merge main into the branch (conflicts solved once), or squash my commits into a few first, or turn on rerere so repeated resolutions replay automatically.

Situation: the branch lived for weeks and main changed the same files, so each of my commits conflicts when replayed.

Check first: git status shows the step ("4 of 30"). If I am lost, abort. It is always safe.

  1. Merge instead: git merge main resolves everything once. Fine if the PR will be squash-merged.
  2. Squash first: git rebase -i $(git merge-base main HEAD), squash to a few commits, then rebase onto main.
  3. Rerere: git config rerere.enabled true, abort, run again.
  4. Smaller steps: rebase onto earlier points of main (main~50, then closer).

After finishing I run tests and git range-diff against the old branch. Prevent: integrate with main daily, keep branches short, no mass reformatting in feature branches.

Remember: many conflicts in a rebase mean one big merge or a squash is cheaper.

Customers on v2.3 and v3.0 both hit a security bug. You must patch both lines. How do you do it with Git? Intermediate

Fix it once on main with a regression test, then cherry-pick it with -x onto the release/2.3 branch, test there, and tag a patch release on each line.

git switch -c fix/cve-2026-1234 main
# commit, PR, merge, tag v3.0.5
git switch -c backport/2.3-cve release/2.3
git cherry-pick -x MAIN_FIX_SHA
# conflict? adapt to the 2.3 code, rerun the 2.3 tests
# PR into release/2.3, tag v2.3.9, publish advisory

The fix must exist in main and every supported branch, and each patch release is built from a tag. I verify with git branch -r --contains FIX_SHA or git cherry -v. Prevent: a written support policy, a backport label or bot, and tests on every release line.

Remember: fix main, cherry-pick -x to each supported line, tag each.

A performance regression appeared sometime in the last 400 commits. How do you find the cause? Intermediate

I use git bisect run with a script that builds and runs the benchmark and exits 1 when it is too slow. 400 commits need only about 9 steps and it runs unattended.

Check first: a repeatable pass/fail test, and a known good tag from last month.

git bisect start
git bisect bad HEAD
git bisect good v3.1.0
git bisect run ./bench_check.sh     # about 9 steps
git bisect log > bisect.txt
git bisect reset

Commits that do not build exit 125 (skip). With many merges use --first-parent first, then bisect inside the faulty merge. Once found I read the commit with git show, confirm by reverting locally, then fix forward or revert. Prevent: a benchmark gate in CI.

Remember: automate bisect with a script. Exit 125 skips.

You committed three commits directly on main instead of a feature branch, and have not pushed yet. Basic

I put a new branch on the current tip, then move main back to the remote state: git branch feature/x, git reset --hard origin/main, git switch feature/x. The commits stay safe because the new label points at them before main moves.

Check first: git log --oneline origin/main..main confirms exactly which commits are mine and that nothing is pushed. If I have uncommitted changes, I stash first.

git branch feature/payment-retry
git reset --hard origin/main
git switch feature/payment-retry

If I already pushed to main, the fix differs: revert the commits through a PR (a protected main should have blocked the push). Prevent: protect main and show the branch name in my shell prompt.

Remember: label first, then move main back.

Push fails because a 300 MB file is in your commit. You deleted it in a later commit and it still fails. Intermediate

Deleting the file in a new commit does not help, because the push still carries the earlier commit that added it. I have to remove it from that commit: amend, interactive rebase, or git filter-repo, and if the file really belongs in the repo I put it under Git LFS.

Situation: hosts reject single files above a limit (GitHub blocks files over 100 MB, though limits depend on the host).

  • In the last commit: git rm --cached big.bin then git commit --amend.
  • A few commits back: git rebase -i origin/main, mark that commit edit, remove the file, amend, continue.
  • Many commits: git filter-repo --path big.bin --invert-paths.
  • Needed in the repo: git lfs migrate import --include="*.bin".

Prevent: ignore or LFS rules for that type, a pre-commit size check and a server-side limit.

Remember: history keeps data. Remove it from the commit that added it.

After a teammate's commit, every file in the repo shows as modified. What happened? Intermediate

Usually line endings (CRLF versus LF), or file mode changes. I look at git diff --stat and the raw diff to tell which, then fix it for everyone with a .gitattributes file.

Check first: ^M or lines that look identical means line endings. "old mode 100644 new mode 100755" means file mode (common on Windows or mounted drives): git config core.fileMode false locally. Only whitespace changes point to an auto-formatter.

Fix: add .gitattributes with * text=auto (and explicit rules for scripts), run git add --renormalize ., commit that alone, and add its hash to .git-blame-ignore-revs. Teammates commit or stash their work before refreshing their files. Prevent: the attributes file, .editorconfig and a CI format check.

Remember: everything changed means line endings or modes. Fix it in .gitattributes.

git config --global commit.gpgsign true       # with gpg.format ssh for SSH signing
Closing line for an interview: "Git is a graph of immutable snapshots and a few movable labels. Rewriting history only moves labels and builds new commits, so almost anything committed can be recovered through the reflog. I rewrite only what is mine and unshared, I use revert for shared history, and I protect main on the server."
Trap to avoid: saying "git reset deletes commits" or "revert rewrites history". Reset moves a label and can orphan commits; revert adds a new commit and never rewrites.
