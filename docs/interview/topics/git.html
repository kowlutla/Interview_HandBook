Mental model: the 7 ideas everything hangs on

One line: Git is a content-addressed database of snapshots. A commit is a snapshot plus a parent link. A branch is just a movable label on a commit. Almost every command either adds objects, or moves a label.
  1. Snapshots, not diffs. Each commit stores the full tree of files at that moment (shared with older commits when unchanged). Diffs are computed on demand.
  2. Content addressing. Every object is named by the hash of its content. Same content gives the same name. Change anything and the name changes.
  3. Commits form a graph (a DAG). Each commit points to its parent(s). History is that graph. It never has cycles.
  4. Refs are cheap labels. Branches, tags and remote-tracking branches are small files holding a commit hash. HEAD says which one you are on.
  5. Three local areas. Working tree (files you edit), index (the next commit you are building), repository (committed history). Plus a remote copy.
  6. Objects are immutable. "Rewriting history" means building new commits and moving a label. The old ones stay until garbage collection, which is why recovery usually works.
  7. Fetch is safe, push is the dangerous one. Fetch only adds to your local copy. Push changes a shared label. Most disasters are a push of the wrong thing.

1. Fundamentals and the object model

BasicWhat is Git, and how is it different from SVN or Perforce?

What the interviewer is testing: do you know that Git is distributed and snapshot based, not just "a tool with commands".

Git is a distributed version control system. Every clone holds the full history, so almost every command (log, diff, commit, branch) works offline and is fast. In SVN or Perforce there is one central server that holds history, and you need it for most operations. Git stores snapshots of the whole tree and links them by parent pointers, while older tools mostly store a list of file changes per revision. Branching in Git is almost free because a branch is only a pointer; in SVN a branch is a directory copy, and in Perforce it is a server-side integration. The cost of the Git model is that it is weaker at huge binary files and at fine-grained per-file locking, which is why LFS and partial clone exist.

Likely follow-ups
  • Is Git really "no central server"? Technically yes, but teams treat one remote (origin) as the agreed source of truth.
  • Why is Git fast? Local data, compressed objects, and the hash-addressed layout means most operations only read small files.
BasicExplain the working tree, the index (staging area) and the repository.

What the interviewer is testing: the core model behind add, commit, reset, restore and diff.

The working tree is the actual files on disk that you edit. The index, also called the staging area or cache, is a binary file at .git/index that lists exactly which file versions will go into the next commit. The repository is the object database in .git/objects plus the refs (branches, tags). git add copies the current file contents into the index. git commit turns the index into a tree object, wraps it in a commit, and moves the current branch to it. This is why you can stage only part of a change (git add -p) and why git diff (working tree vs index) and git diff --staged (index vs last commit) show different things.

git status                 # summary of both comparisons
git diff                   # working tree vs index (unstaged)
git diff --staged          # index vs HEAD (what will be committed)
git diff HEAD              # working tree vs HEAD (both together)
Likely follow-ups
  • Why have a staging area at all? It lets you craft clean, focused commits from a messy working tree.
  • Is the index just a list of names? It stores path, mode, blob hash, and file stat data used to detect changes quickly.
BasicWhat are the four kinds of Git objects?

What the interviewer is testing: internal knowledge. This question separates users from people who understand Git.

A blob holds the bytes of one file, with no name. A tree is a directory: a list of entries, each with a mode, a name, and the hash of a blob or a sub-tree. A commit points to one top-level tree, to zero or more parent commits, and holds author, committer, timestamps and the message. An annotated tag is a named, optionally signed pointer to another object, with its own message. All four are stored in .git/objects, zlib-compressed, named by the hash of their content. File names live in trees, not in blobs, so two files with identical content share one blob.

git cat-file -t HEAD         # commit
git cat-file -p HEAD         # tree, parent, author, message
git cat-file -p HEAD^{tree}  # entries of the root tree
git ls-tree -r HEAD          # every file with mode and blob hash
Likely follow-ups
  • Where is the file name stored? In the tree, not the blob.
  • What does an empty directory look like? Git cannot store it, since there is no blob; people add a .gitkeep file.
BasicWhat exactly is inside a commit?

What the interviewer is testing: can you read raw commit data and explain what is and is not stored.

A commit stores: the hash of one root tree, the hashes of its parents (none for the first commit, one normally, two or more for a merge), author name, email and time, committer name, email and time, and the message. It does not store a diff and it does not store the branch name. Author and committer can differ: when you rebase or cherry-pick someone's commit, the author stays and the committer becomes you. The commit hash is the SHA of all that text, so changing even the message, or the parent, gives a new hash.

$ git cat-file -p HEAD
tree 9f1c...
parent 4be7...
author Asha <asha@example.com> 1731800000 +0530
committer Asha <asha@example.com> 1731800000 +0530

Fix null check in payment retry
Likely follow-ups
  • Which commit has no parent? The root commit. A repo can have several roots (after merging unrelated histories).
  • Does Git know which branch a commit was made on? No. Branches are labels that move.
IntermediateWhy does rewriting one old commit change every commit after it?

What the interviewer is testing: hash chaining, and why history rewrite affects other people.

A commit's hash is computed over its content, and that content includes the parent's hash. If you change commit B (message, content, anything), B gets a new hash. Commit C stored B's old hash as its parent, so C must be rewritten to point to the new B, which gives C a new hash, and so on to the tip. The tree contents may be identical, but the commits are different objects. This is a Merkle-chain: it makes history tamper-evident, and it is also why force-pushing a rewritten branch breaks everyone who had the old commits: their history and yours no longer share those hashes.

Likely follow-ups
  • So can a signed commit be silently edited? No; any change changes the hash, and the signature covers that content.
  • What is not changed by a rewrite? The blobs and trees, they are reused.
IntermediateHow is a blob hash computed, and is SHA-1 still safe?

What the interviewer is testing: whether you know the object format and the SHA-1 story.

Git hashes a header plus the content: the text blob, a space, the byte length, a zero byte, then the file bytes. So git hash-object of a file is not the same as sha1sum of the file. Git has used SHA-1 since the start. In 2017 a practical SHA-1 collision was shown. Git answered by adding collision detection (the sha1dc library) which rejects the known attack patterns, and by building SHA-256 support (git init --object-format=sha256). SHA-256 repositories exist but are still not widely supported by hosting services, so most real repositories stay on SHA-1. Git's hash is for identity and integrity, not for security: security comes from signed commits and tags, and access control.

echo 'hello' | git hash-object --stdin
git init --object-format=sha256 demo   # experimental interop
Likely follow-ups
  • Why do short hashes work? Git only needs a unique prefix; 7 to 12 characters is common.
BasicWhat is a branch, really? Why is creating one so cheap?

What the interviewer is testing: the pointer model, which makes merge and rebase easy to explain.

A branch is a text file in .git/refs/heads/ (or a line in packed-refs) that contains one commit hash, 41 bytes. Creating a branch writes that file; nothing is copied. When you commit on a branch, Git creates the new commit with the current tip as parent, then updates the file to the new hash. That is all "being on a branch" means. Deleting a branch deletes only the label; commits that are no longer reachable from any label become garbage after some weeks, but are not removed at once.

Likely follow-ups
  • Where is the branch list kept? .git/refs/heads/ and .git/packed-refs.
BasicWhat is HEAD? What do HEAD~1, HEAD^ and HEAD@{1} mean?

What the interviewer is testing: revision syntax, which you need for reset, rebase and recovery.

HEAD is a file (.git/HEAD) that normally holds a symbolic reference such as ref: refs/heads/main. It means "the commit I am on, through this branch". HEAD~1 (or HEAD~) is the first parent of HEAD, HEAD~3 goes three first-parent steps back. HEAD^ also means first parent, but HEAD^2 means the second parent of a merge commit, which is the branch that was merged in. HEAD@{1} is different: it comes from the reflog and means "where HEAD was one move ago", regardless of ancestry. main@{yesterday} works the same way for a branch on your own machine.

git show HEAD~2        # grandparent along first parents
git show HEAD^2        # the merged-in side of a merge commit
git show HEAD@{3}      # where HEAD was 3 moves ago (reflog)
git log main@{2.days.ago}
Common mistakes: mixing up ~ and ^. They are the same for ordinary commits and differ only on merge commits.
IntermediateWhat happens inside Git when you run git add and git commit?

What the interviewer is testing: can you connect user commands to objects and refs.

git add file compresses the file, writes a blob object into .git/objects (if that content is new), and updates the index entry for that path to the blob's hash. git commit then does four things: writes tree objects from the index (one per directory, bottom up), creates a commit object pointing at the root tree and at the current HEAD commit as parent, writes it with your message and identity, and finally moves the current branch file to the new commit hash. It also appends a line to the reflog. Hooks (pre-commit, commit-msg) run before the commit object is made.

Likely follow-ups
  • If I add a file and then edit it again before commit, what is committed? The version at the time of add, not the newer edits.
  • What does commit -a do? Stages all changes to tracked files first. New files are not included.
IntermediateWalk me through the .git directory.

What the interviewer is testing: comfort with Git as files, which helps in recovery and debugging.

HEAD is the current branch pointer. config holds repo-level settings and remotes. index is the staging area. objects/ holds loose objects (two-hex-digit folders) and objects/pack/ holds packfiles. refs/heads, refs/tags, refs/remotes hold branch, tag and remote-tracking labels, and packed-refs holds many of them in one file. logs/ is the reflog. hooks/ holds sample scripts, which are not shared by clone. info/exclude is a private ignore file. Special files appear during operations: MERGE_HEAD, ORIG_HEAD, REBASE_HEAD, and the rebase-merge/ directory while a rebase is running. In a worktree or submodule, .git is a file that points to the real directory.

Likely follow-ups
  • What is ORIG_HEAD? The previous tip saved before risky moves like reset, merge and rebase. git reset --hard ORIG_HEAD undoes a merge you just did.
SeniorWhat are packfiles, and how does Git keep repositories small?

What the interviewer is testing: storage internals and why gc matters.

New objects start as "loose": one zlib-compressed file each. That is simple, but slow and wasteful with thousands of objects. git gc (or git repack) combines objects into a packfile, with an index file for lookup. Inside a pack Git uses delta compression: it stores one version of an object in full and others as small deltas against it. It picks delta bases by similarity (name, size), not only by history order, so two versions of a file far apart can still delta well. The same pack format is used on the wire: a fetch or push builds a pack of exactly the missing objects, which is why transfers are small. Extra helpers on big repos are the multi-pack-index, reachability bitmaps for fast clone, and the commit-graph file for fast history walks.

git count-objects -vH      # loose vs packed sizes
git verify-pack -v .git/objects/pack/pack-*.idx | head
git gc --aggressive        # rarely worth it; use maintenance instead
Likely follow-ups
  • Why is a big binary that changes often a problem? Binary deltas are poor, and every version stays in history forever, so clones grow.
IntermediateGit does not store renames. How does it show them, and how do I follow a file's history across a rename?

What the interviewer is testing: understanding that rename tracking is computed, not recorded.

A commit only stores trees, so a rename is just "one path disappeared and another appeared with the same or very similar content". When you run git diff, log or merge, Git guesses renames by comparing blobs. An exact hash match is a certain rename; otherwise it uses a similarity score (default 50%). Because it is a guess, large edits plus a rename in one commit may show as delete and add. Best practice: rename in its own commit, with no content changes. For history, git log --follow file works for a single file. Merges also use rename detection, so a rename on one branch and an edit on the other usually merges cleanly.

git log --follow -p -- src/Util.java
git diff -M50% main feature          # tune similarity
git log -M -C --stat                 # also detect copies
Basicgit checkout does too many things. What replaced it?

What the interviewer is testing: modern Git habits.

git checkout used to mean three things: switch branches, restore files, and detach HEAD. Since Git 2.23, two clearer commands exist. git switch changes branches (git switch -c new creates and switches, git switch - goes back). git restore restores file contents: git restore file throws away working-tree changes, git restore --staged file unstages, and git restore --source=HEAD~2 file brings a file from another commit. The old checkout still works and you will see it in older docs. A key safety fact: restore on the working tree overwrites uncommitted work with no way back, because that data was never in a commit.

git switch -c fix/login          # new branch
git switch --detach v1.4.0       # look at a tag without a branch
git restore --staged app.py      # unstage
git restore app.py               # discard edits (cannot undo)
BasicWhat are the states a file can be in, and what does git status tell me?

What the interviewer is testing: basic daily fluency.

A file is untracked (Git has never been told about it), tracked and unmodified, modified (changed in the working tree, not staged), or staged (changes in the index). A file can be both: staged with one version and modified again after. git status shows three groups: changes to be committed (index vs HEAD), changes not staged (working tree vs index), and untracked files. It also tells you the branch, whether it is ahead or behind its upstream, and what to do during a merge or rebase. git status -sb is the short form with branch info.

Likely follow-ups
  • Why does an ignored file still show if tracked? Ignore rules only affect untracked files. Use git rm --cached to stop tracking.

2. Branches and merging

BasicWhat is a fast-forward merge, and when does Git create a merge commit instead?

What the interviewer is testing: the two kinds of merge, and what a merge commit is.

If the branch you are merging into has not moved since the other branch split off, then the other branch already contains all of your history. Git just moves your branch label forward to that tip. This is a fast-forward: no new commit, history stays a straight line. If both branches have new commits, Git cannot just move a label. It finds the common ancestor, combines both sets of changes (a three-way merge) and records a new merge commit with two parents. You can force a merge commit with --no-ff, or refuse anything but a fast-forward with --ff-only.

git switch main
git merge feature            # ff if possible, else merge commit
git merge --no-ff feature    # always a merge commit
git merge --ff-only feature  # fail instead of creating a merge commit
Likely follow-ups
  • Why use --no-ff? It keeps a visible "this feature landed together" point, easy to revert as one unit.
  • Can I make --ff-only the default? Yes, git config merge.ff only, or pull.ff only for pulls.
IntermediateHow does a three-way merge decide what to keep? What is the merge base?

What the interviewer is testing: why Git can auto-merge, and where conflicts come from.

Git finds the merge base: the best common ancestor of the two tips (git merge-base A B). Then for each file it compares base to ours and base to theirs. If only one side changed a region, take that change. If both made the identical change, take it once. If both changed the same region differently, that is a conflict and Git leaves markers for a human. Using the base is what lets Git tell "I changed this" from "they changed this"; a plain two-way compare could not. Merges work on lines, not meaning, so a merge can be clean textually and still break the build, which is why CI on the merged result matters.

Likely follow-ups
  • What if there are several possible bases (criss-cross merges)? The ort strategy merges the bases into a virtual base first.
  • Which strategy is the default? ort since Git 2.34. It is faster than recursive and handles renames better.
BasicYou get a merge conflict. What exactly do you do?

What the interviewer is testing: a calm, correct routine, not panic.

First, git status lists "both modified" files. Open each, find the markers <<<<<<<, =======, >>>>>>>, and decide the final content, which is often a mix of both sides, not just one. Remove all markers. Build and run tests. Then git add each file to mark it resolved, and git commit (or git rebase --continue if rebasing). If it goes badly, git merge --abort returns to the state before the merge. Turn on merge.conflictStyle zdiff3 (Git 2.35 or newer; diff3 before) so you also see the base text in the markers; it makes decisions much easier. Talk to the author of the other change if you are not sure what they meant.

<<<<<<< HEAD
timeout = 30
||||||| base
timeout = 10
=======
timeout = 20
>>>>>>> feature
Likely follow-ups
  • How do I see only conflicted files? git diff --name-only --diff-filter=U.
  • Take one whole file from a side? git checkout --ours file or --theirs file, then add.
Common mistakes: committing with markers left in; resolving by taking one side blindly; not running tests after the resolution.
IntermediateIn a conflict, which side is "ours" and which is "theirs"? Why is it swapped during rebase?

What the interviewer is testing: a classic trap that causes people to discard the wrong code.

In a merge, "ours" is the branch you are on (HEAD) and "theirs" is the branch you are merging in. In a rebase, Git replays your commits one by one on top of the new base. At that moment HEAD is the branch you are rebasing onto (for example the updated main), and the commit being applied is yours. So "ours" is the upstream, and "theirs" is your own commit being replayed. It is confusing but consistent: ours is always "the thing HEAD currently is". A good habit is to avoid --ours/--theirs in a rebase unless you are sure, and read the marker labels instead.

# during rebase onto main, keep MY version of the file:
git checkout --theirs path/file
# during a merge of feature into main, keep MY (main) version:
git checkout --ours path/file
Likely follow-ups
  • Difference between the merge option -X ours and strategy -s ours? -X ours only prefers our side where there is a conflict, and still merges the rest. -s ours takes only our tree and ignores their changes completely while recording a merge.
IntermediateMerge commit, squash merge, rebase merge: what is the difference, and which would you pick?

What the interviewer is testing: team policy trade-offs, not a single "right" answer.

A merge commit keeps every branch commit and adds one commit that joins them: full fidelity, noisy graph, easy to revert as one unit with -m 1. A squash merge collapses the whole branch into one new commit on main: clean, linear history, one commit per PR, easy revert, but you lose the individual commits, and the original branch is not an ancestor, so reusing that branch afterwards causes false conflicts. A rebase merge replays each commit onto main with new hashes: linear, keeps individual commits, but every hash changes and commits can break bisect if they were not individually green. I usually choose squash for teams that write messy WIP commits, merge commits for long-lived or release branches where history matters, and rebase merge only when commits are curated and each one builds.

git merge --squash feature   # stages the combined change
git commit                   # you write one message
Likely follow-ups
  • After a squash merge, why do I get conflicts if I continue on the old branch? Git does not know the squash commit contains your commits, so it replays them again. Start a new branch from main.
SeniorWhat merge strategies and options exist, and when would you use them?

What the interviewer is testing: depth beyond the default merge.

Strategies (-s): ort is the default for two heads. recursive is the older one. octopus merges more than two branches and refuses if there is a conflict. ours keeps our tree entirely and records the other branch as merged: useful to declare "this old branch is dead, mark it merged". subtree handles merging a project that lives in a sub-directory. Options (-X) tune the default: -X ours or -X theirs resolve conflicts on one side, -X ignore-space-change or ignore-all-space help after a re-format, -X find-renames=70 tunes rename detection, -X patience or histogram change the diff algorithm to produce better alignment. Use -X theirs sparingly: it silently takes one side on conflicting hunks and can hide real problems.

Likely follow-ups
  • When is octopus used in practice? Rare: combining many topic branches into an integration branch.
BasicHow do I back out of a merge that has gone wrong, or one I already finished?

What the interviewer is testing: knowing the safe exits, and the difference before and after the commit.

While the merge is in progress (conflicts, not yet committed): git merge --abort restores the state from before. If you committed the merge locally but have not pushed: git reset --hard ORIG_HEAD, or git reset --hard HEAD~1 (first parent), since the merge moved the branch and nothing else depends on it yet. If you already pushed and others may have pulled it: do not rewrite; use git revert -m 1 MERGE_SHA to add a new commit that undoes the merge. Always check git status and git log --graph --oneline before choosing.

Likely follow-ups
  • What does -m 1 mean? Choose parent number 1 (the mainline) as the side to keep.
IntermediateWhat is the difference between A..B and A...B in log and diff?

What the interviewer is testing: range syntax, often used in PR review and release notes.

For git log: main..feature means commits reachable from feature but not from main, i.e. what the PR adds. main...feature (three dots) means commits in either branch but not both: the symmetric difference, the work unique to each side. For git diff the meaning changes: git diff main..feature compares the two tips directly; git diff main...feature compares feature to the merge base, which is "what feature changed" and is what pull request pages show. If main moved on, the two-dot diff will include main's own new changes in reverse, which confuses reviewers.

git log --oneline main..feature       # what the PR adds
git log --left-right main...feature   # who has what
git diff main...feature               # PR-style diff
BasicWhat is a detached HEAD, and how do you not lose work in it?

What the interviewer is testing: a very common beginner trap with a simple fix.

Normally HEAD points to a branch, and the branch points to a commit. In detached state HEAD points straight to a commit. You get there with git switch --detach, by checking out a tag or a commit hash, or in the middle of a rebase or bisect. Commits you make there have no branch, so when you switch away nothing refers to them and they look lost. They are still in the reflog for weeks. To keep them, create a branch while you are there: git switch -c rescue. If you already left, find the hash with git reflog and run git branch rescue HASH.

Likely follow-ups
  • Is detached HEAD ever useful? Yes: inspect an old release, run a build of a tag, or try an experiment.
SeniorWhat is git rerere and when is it worth turning on?

What the interviewer is testing: practical tools for repeated conflicts.

The name means "reuse recorded resolution". When enabled (git config rerere.enabled true), Git remembers the exact conflict text and how you resolved it, storing it in .git/rr-cache. The next time the same conflict appears, it applies your earlier resolution automatically (you still need to add and continue). It shines when you repeatedly rebase a long branch onto a moving main, when you re-do a merge after aborting, when you maintain a long-lived integration branch, or when you test-merge branches to see conflicts. It does not decide anything new; it only replays your own earlier decisions. Review the result, since a recorded resolution can be wrong for a slightly different context.

Likely follow-ups
  • Does rerere share across machines? No, it is local to the repo, unless you share the cache by hand.
BasicHow do you delete a branch locally and on the remote, and what is the difference between -d and -D?

What the interviewer is testing: cleanup commands and the safety check.

git branch -d name deletes only if the branch is fully merged into its upstream or HEAD, otherwise it refuses. -D forces deletion even if commits would become unreachable, so use it only when you are sure (and remember the reflog can bring it back for a while). To delete on the remote: git push origin --delete name, or the older git push origin :name. Other people's local copies of remote-tracking branches stay until they run git fetch --prune. You cannot delete the branch you are on.

git branch -d feature/login
git push origin --delete feature/login
git fetch --prune                    # clean stale origin/* names
git branch --merged main             # candidates to delete

3. Rebase and history

BasicWhat is the difference between merge and rebase?

What the interviewer is testing: the most asked Git question. A clear picture and a rule for when to use each.

Both bring the changes of one branch into another. Merge keeps history as it happened and adds a merge commit that joins the two lines. Rebase takes your commits, lifts them off, and re-applies them one by one on top of the new base. The result looks like you started your work today from the latest main. The content is the same, but rebase makes new commits with new hashes (C' and D'), and gives a straight line. Rebase gives cleaner history; merge is safer because it never rewrites anything. The rule: rebase your own local or private branch before sharing; do not rebase commits other people already have.

Likely follow-ups
  • What happens to the old C and D? They are still in the object store and reflog until garbage collection.
  • Which gives better git bisect? A linear history of green commits.
IntermediateWhat is the "golden rule of rebase", and what actually goes wrong if you break it?

What the interviewer is testing: can you explain the failure, not just repeat the slogan.

The rule: never rebase commits that exist outside your own repository, meaning commits others may have based work on. Rebasing creates copies with new hashes and then you must force-push to replace the old ones. A teammate who already pulled the old commits has them in their history. When they fetch, Git sees your branch and theirs as diverged. If they pull with merge, the old and new versions of the same changes are both merged: duplicate commits, duplicate conflicts, and sometimes reverted work coming back. The fix is communication: only rewrite branches that you own, agree on it for shared feature branches, and use --force-with-lease. Your own open PR branch is normally fine to rebase and force-push.

Likely follow-ups
  • A teammate rebased a branch I use. How do I recover? git rebase --onto new-base old-base my-branch, using the old tip as the "upstream" so only my commits move.
SeniorHow does git rebase work internally?

What the interviewer is testing: deep understanding that explains conflict behaviour and recovery.

Rebase first computes the list of commits to replay: those reachable from the branch but not from the upstream (upstream..branch). It saves the original tip in ORIG_HEAD. Then it detaches HEAD at the new base (the upstream, or the --onto target). For each commit on the list, in order, it does a cherry-pick: a three-way merge using the commit's parent as the base, then creates a new commit with the same author and message but new committer, parent and hash. Commits whose changes already exist upstream (same patch ID) are skipped. At the end it moves the branch label to the last new commit and re-attaches HEAD. If a conflict happens, it stops with the state in .git/rebase-merge. Because each commit is replayed separately, the same conflict can appear repeatedly, which is why squashing first, or rerere, helps.

Likely follow-ups
  • How do I undo a rebase that finished? git reset --hard ORIG_HEAD if nothing else happened, or pick the pre-rebase entry in the reflog.
  • What is the patch ID? A hash of the diff ignoring line numbers and whitespace, used to detect "this change is already there".
IntermediateWhat can you do with git rebase -i? Clean up a messy branch before a PR.

What the interviewer is testing: hands-on history editing.

git rebase -i main (or HEAD~5) opens a todo list, oldest commit first. You change the verb on each line. pick keeps it. reword changes the message. edit stops so you can amend or split the commit. squash melds it into the previous commit and combines messages; fixup does the same but drops its message. drop removes the commit. You can also reorder lines, or add exec make test lines to run tests after a commit, which finds a commit that breaks the build. Save and Git replays. If the editor result is empty, the rebase aborts.

pick   a1b2c3 Add parser
fixup  d4e5f6 typo
reword 7a8b9c Add validation
drop   0f1e2d debug logging
exec   mvn -q test

  • How do I split a commit? Mark it edit, then git reset HEAD^, stage in parts, commit several times, git rebase --continue.
IntermediateWhat are fixup commits and --autosquash? How do you apply review feedback cleanly?

What the interviewer is testing: a workflow trick that keeps reviews easy and history clean.

During review you want small follow-up commits so the reviewer sees what changed. Create them with git commit --fixup=TARGET_SHA. This writes a commit titled fixup! original title. When the PR is approved, run git rebase -i --autosquash main: Git moves each fixup right after its target and sets it to fixup automatically, so you just save. Set rebase.autoSquash true to make this the default. Then git push --force-with-lease. The reviewer got incremental diffs, and the final history has clean commits.

git commit --fixup=a1b2c3
git rebase -i --autosquash main
git push --force-with-lease
SeniorExplain git rebase --onto with a real example.

What the interviewer is testing: whether you can move a slice of history, a skill that saves people in stacked-branch work.

Plain git rebase main means "take my commits since I forked from main, and put them on main's tip". --onto separates three things: new base, old base (where to cut), and the branch. git rebase --onto NEWBASE OLDBASE BRANCH replays the commits in OLDBASE..BRANCH on NEWBASE. Example: you built topic-b on top of topic-a, then topic-a was squash-merged to main. If you now rebase topic-b onto main normally, Git would also replay topic-a's old commits and conflict. Instead: git rebase --onto main topic-a topic-b moves only the commits that are on topic-b but not on topic-a. Same tool removes a range from the middle of a branch.

IntermediateYou are mid-rebase, with conflicts. What commands do you have, and what if you get lost?

What the interviewer is testing: staying calm inside an operation with state.

When it stops, fix the conflict, git add the files, then git rebase --continue. git rebase --skip drops the current commit (use when upstream already has the same change). git rebase --abort puts everything back as before you started: always safe. git status tells you which step you are on ("2 of 7"). If you are lost, abort and try a different approach: merge main into your branch instead, squash your commits first so there is only one set of conflicts, or enable rerere. Remember that "ours" and "theirs" are swapped here. After finishing, run tests and compare with git range-diff to check that the rebased commits still equal the old ones.

git range-diff main ORIG_HEAD HEAD   # compare old vs new series
SeniorPlain rebase drops merge commits. How do you keep a branch structure while rebasing?

What the interviewer is testing: knowing flags that exist for non-trivial history.

By default git rebase flattens: merge commits in the range are dropped and their side branches are linearised. If your branch contains merges that are meaningful (for example an integrated sub-feature) use git rebase --rebase-merges (Git 2.18+, it replaced the old --preserve-merges, which was removed). It recreates the merge structure on top of the new base, and the todo list shows label, reset and merge commands. Conflicts in re-created merges can be harder to follow. If the merges are only "I merged main into my branch to stay current", flattening is exactly what you want, since after rebase the merges are no longer needed.

Likely follow-ups
  • Alternative to rebasing a branch with merges? Just merge into it, or squash the whole branch.
SeniorHow do you rebase stacked branches (a chain of PRs) without doing it by hand for each one?

What the interviewer is testing: modern workflow tools for stacked PRs.

A stack is branch A, then B on A, then C on B. When A changes, B and C must be rebased. Since Git 2.38, git rebase --update-refs rebases the tip (C) and also moves the intermediate branch labels (A, B) that point to commits in the range, so the whole stack follows. Set rebase.updateRefs true to make it default. Before that you rebased each branch in order with --onto. After squash-merging A to main, use --onto main A B. Push all branches with --force-with-lease. Review tools and helpers (gh stack-like tools, Graphite, git-branchless, Sapling) exist, but plain Git can do it.

IntermediateWhat does git pull do, and should you use pull --rebase?

What the interviewer is testing: the hidden merge in pull, and noisy "Merge branch main of origin" commits.

git pull is git fetch followed by an integrate step: merge by default. If you have local commits and the remote also moved, that creates a merge commit with a dull message, repeated again and again by developers: history noise. git pull --rebase replays your local commits on top of the fetched ones instead, so history stays linear. Safe because those local commits are not shared yet. Set it once: git config --global pull.rebase true. Since Git 2.33 pull warns until you choose; pull.ff only is another safe choice: fail if a plain fast-forward is not possible and let me decide. Also --autostash stashes dirty files around the pull.

git config --global pull.rebase true
git config --global rebase.autoStash true
git pull --ff-only          # refuse to create hidden merges
SeniorLinear history or merge commits: how do you argue each side?

What the interviewer is testing: engineering judgement about trade-offs.

For linear history (squash or rebase merges): easier to read with git log, easier bisect, easy revert of a single commit, simple release notes. The cost: the original commits and branch shape are lost with squash, and rebase makes the author rewrite commits, which has a risk. For merge commits: exact record of what happened, no history rewrite, conflict resolution is recorded once in the merge, and a whole feature can be reverted with one revert -m 1. The cost: a noisy graph and harder bisect (use --first-parent to see only mainline). My default for product teams: squash merge via PR with a good title, protected main, and merge commits only for release-branch back-merges. The best answer says: pick one, document it, and enforce it with branch rules.

git log --first-parent --oneline main     # mainline view of a merge-heavy history
git bisect start --first-parent            # bisect on mainline only (Git 2.29+)

4. Remotes and workflows

BasicWhat is a remote, and what is a remote-tracking branch like origin/main?

What the interviewer is testing: the difference between the server's branch and your local view of it.

A remote is a named URL stored in your config; origin is just the default name given by git clone. A remote-tracking branch such as origin/main is a read-only local label that records where main was on the remote the last time you talked to it. You cannot commit on it. Only fetch, pull and push move it. So origin/main can be stale; it says nothing about the server right now. A local branch can have an upstream setting that links it to a remote-tracking branch, and that link is what makes plain git pull, git push and "ahead 2, behind 1" in git status work.

git remote -v
git branch -vv                       # local branches with upstream and ahead/behind
git branch --set-upstream-to=origin/main main
git push -u origin feature           # push and set upstream
git config --global push.autoSetupRemote true   # Git 2.37+
BasicWhat is the difference between fetch, pull and clone?

What the interviewer is testing: safe versus changing commands.

git clone copies the whole repository, sets up origin, and checks out the default branch. git fetch downloads new objects and updates your remote-tracking branches such as origin/main, but never touches your local branches or working files, so it is always safe. git pull is fetch plus integrating into the current branch (merge, or rebase with --rebase), so it can change your files and cause conflicts. A careful habit is: fetch first, look at what came in (git log HEAD..origin/main), then decide to merge, rebase, or wait.

BasicYour push is rejected with "non-fast-forward" or "fetch first". What does it mean and what do you do?

What the interviewer is testing: the safety rule of push and a non-destructive fix.

The remote branch has commits that you do not have, so moving it to your commit would throw those away. Git refuses unless the new tip contains the old tip (a fast-forward). The fix is to bring the remote work into yours: git fetch, then git rebase origin/feature (or merge), run tests, and push again. Do not reach for --force; that would delete your colleague's commits from the remote. If you rewrote your own history on purpose (after an amend or rebase of your own branch), then it is correct to overwrite, and you use --force-with-lease.

Likely follow-ups
  • Message "Updates were rejected because the tip of your current branch is behind". Same thing: you are behind, pull first.
IntermediateWhat is --force-with-lease and why is it better than --force?

What the interviewer is testing: safe force-push habits, a typical production-risk question.

--force says "set the remote branch to my commit, whatever is there". --force-with-lease says "set it, but only if the remote branch is still where I last saw it", meaning it equals my remote-tracking ref. If someone pushed a new commit in the meantime, the push fails, and you did not destroy their work. It is a compare-and-swap. Two caveats: if a background process fetches for you (an IDE auto-fetch), your tracking ref is already updated, and the lease passes even though you never looked at the new commits; --force-if-includes (Git 2.30) adds a check that your local history actually contains the remote tip. You can also pin the expected value: --force-with-lease=feature:SHA. Make it your only force option, ideally an alias.

git push --force-with-lease --force-if-includes origin feature
git config --global alias.pushf "push --force-with-lease --force-if-includes"
Likely follow-ups
  • Should anyone ever force push to main? No. Protect main on the server so it is impossible.
IntermediateWhat does git push do when you just type it? What is push.default?

What the interviewer is testing: knowing config that decides what gets pushed.

The result depends on push.default. The default since Git 2.0 is simple: push the current branch to its upstream, and only if the names match (and it errors if no upstream is set). The old default matching pushed every branch that had the same name on both sides, which surprised people. Other values: current pushes the current branch to a branch with the same name, creating it; upstream pushes to the configured upstream even if the name differs; nothing forces you to name the target. push.autoSetupRemote true (Git 2.37) creates the upstream automatically on first push, so you do not need -u.

IntermediateExplain the fork-and-pull-request workflow, and how you keep a fork in sync.

What the interviewer is testing: open-source and cross-team contribution flow.

You do not have write access to the main repository, so you fork it (your own server-side copy), clone your fork, and add the original as a second remote named upstream. You work on a topic branch, push to your fork (origin), and open a pull request from your fork's branch to the upstream repo. To stay in sync: git fetch upstream, then rebase or merge upstream/main into your branch and update your fork's main. Never work directly on your fork's main; keep it as a clean mirror of upstream so you can always branch from it.

git remote add upstream https://example.com/org/repo.git
git fetch upstream
git switch main && git merge --ff-only upstream/main
git push origin main
SeniorCompare Git Flow, GitHub Flow and trunk-based development. Which would you choose?

What the interviewer is testing: process judgement tied to release style.

Git Flow uses long-lived develop and main, plus feature, release and hotfix branches. It suits versioned products that ship on a schedule and support old versions, but it adds merge overhead and delays integration. GitHub Flow has one long-lived branch (main), short feature branches, PRs, and deploy from main: simple, good for web services deployed continuously. Trunk-based development pushes the idea further: everyone integrates into main at least daily, branches live hours, unfinished work is hidden behind feature flags, and release branches are cut only when needed. Research on delivery performance (DORA) links trunk-based practice to higher deploy frequency. Choose by how you release: continuous deployment means trunk or GitHub Flow; shipped installers with long support means release branches (trunk plus release branches).

BasicWhy do deleted remote branches still show up locally, and how do you clean up?

What the interviewer is testing: remote-tracking branches are local copies.

When a branch is deleted on the server (often when a PR is merged), your origin/feature label stays, because fetch normally only adds. Run git fetch --prune (or set fetch.prune true) to delete tracking labels whose remote branch is gone. Your own local branch of the same name is not touched; delete it with git branch -d. A quick cleanup of merged locals: git branch --merged main | grep -v main reviewed and piped to git branch -d. For squash-merged branches --merged does not detect them, because their commits are not in main; check git branch -vv for gone.

IntermediateCan a repo have several remotes? How do you push to two places, or move a repo to a new host?

What the interviewer is testing: remote handling and migrations.

Yes. A remote is just a name plus URL, and you can have any number (origin, upstream, a backup, a CI mirror). To push to two hosts, either push to each remote name, or add a second push URL to one remote with git remote set-url --add --push origin URL2. To migrate a repo with full history use a mirror: git clone --mirror OLD, then git push --mirror NEW; this copies all branches and tags. Check the pull request refs and hosting-specific data (issues, PRs, CI settings), which are not in Git and need the platform's importer. Remember to update CI and branch protection on the new host.

git clone --mirror https://old.example.com/team/app.git
cd app.git
git push --mirror https://new.example.com/team/app.git
IntermediateWhat is a shallow clone, and what breaks with it?

What the interviewer is testing: CI performance and its side effects.

git clone --depth 1 downloads only the latest commit (and its tree), with no history. It is much faster and smaller, and is the default in many CI systems. Things that break or surprise: git log and blame stop at the shallow boundary, git describe cannot find tags, merge-base against main may fail so diff against the target branch is wrong, version tools that count commits misbehave, and pushing from a shallow clone is more limited. Fix with git fetch --unshallow or --deepen N, or set the CI to fetch full depth (or fetch-depth: 0 in GitHub Actions) for jobs that need history, such as release versioning and changed-files detection.

5. Commits, pull requests and safeguards

BasicWhat makes a good commit and a good commit message?

What the interviewer is testing: engineering discipline that makes history useful later.

A good commit is atomic: one logical change, builds and passes tests by itself, easy to revert or cherry-pick. Do not mix a refactor, a formatting sweep and a bug fix. The message has a short subject (about 50 characters, imperative: "Fix null check in retry"), a blank line, then a body that explains why, not what, since the diff already shows what. Mention side effects, trade-offs, and the ticket id. Someone running git blame two years later should understand the reason. Never commit secrets, generated files or large binaries.

Retry payment capture on 502 from gateway

The gateway returns 502 during its nightly failover (about 30 s).
Retry up to 3 times with backoff, only for idempotent captures.
Refs PAY-1234
Likely follow-ups
  • Conventional Commits? A format like feat(api): add paging that tools use to generate changelogs and version bumps.
BasicHow do you commit only part of the changes in a file?

What the interviewer is testing: use of the index for clean commits.

Use git add -p (patch mode). Git shows each changed hunk and asks: y stage, n skip, s split the hunk into smaller ones, e edit the hunk by hand. Only the staged hunks go into the next commit; the rest remain as working-tree changes. Verify with git diff --staged. The same idea exists for restore and stash (git restore -p, git stash -p) and for amending. This is how you turn one afternoon of mixed work into three clean commits.

IntermediateHow do you keep pull requests reviewable?

What the interviewer is testing: collaboration maturity.

Keep each PR small and about one thing, ideally a few hundred changed lines at most. Separate mechanical changes (renames, formatting) from logic into their own PRs or commits, since reviewers cannot see logic hidden in a big move. Write a description: why, what, how tested, risks, rollout. Run lint and tests before asking for review. Open early as a draft for direction. For large features, ship in slices behind a feature flag or use stacked PRs. Respond to review with fixup commits so the reviewer sees what changed, then squash. Use CODEOWNERS to request the right reviewers automatically.

IntermediateWhat safeguards would you put on the main branch?

What the interviewer is testing: preventing incidents with server rules.

Use branch protection (GitHub rulesets, GitLab protected branches): no direct pushes, no force pushes, no deletion. Require a pull request with at least one approval (two for sensitive areas), dismiss stale approvals when new commits arrive, require code-owner review through a CODEOWNERS file, and require status checks (build, unit tests, lint, security scans) to pass on an up-to-date branch. Optionally require signed commits, linear history, and resolved conversations. Apply the rules to admins too, or the "one emergency push" becomes the norm. Add secret scanning with push protection, and a merge queue for busy repos.

Likely follow-ups
  • Why is "require branch to be up to date" costly? Every merge forces others to rebase and re-run CI: that is the problem a merge queue solves.
SeniorWhat is a merge queue and what problem does it solve?

What the interviewer is testing: semantic conflicts and CI throughput on busy repos.

Two PRs can each pass CI against main and still break main when both merge, because neither tested the combination (a semantic conflict, often with no textual conflict). Forcing "update branch and re-run CI" before every merge fixes correctness but serialises everyone. A merge queue (GitHub merge queue, GitLab merge trains, Bors-style tools) automates it: approved PRs enter a queue; the system builds a temporary branch of main plus the queued PRs in order, runs CI on that exact result, and only then fast-forwards main. If a PR fails, it is removed and the ones behind it are re-tested without it. Main always stays green, with parallel testing. Requirement: CI must run on the queue's temporary branch events (for GitHub, the merge_group trigger).

IntermediateWhat are Git hooks? Which ones matter, and why can they not be your only safeguard?

What the interviewer is testing: automation limits.

Hooks are scripts that Git runs at events, found in .git/hooks. Client side: pre-commit (lint, secret scan, format; fast), commit-msg (check message format), pre-push (run tests), pre-rebase. Server side: pre-receive and update (reject pushes, enforce rules, scan secrets), post-receive (trigger CI, notify). The weakness is that client hooks are not cloned with the repo, and anyone can skip them with --no-verify. Share them using core.hooksPath pointing to a tracked folder, or tools like pre-commit, Husky or Lefthook. But the real enforcement must be on the server (branch protection, CI checks, server hooks), since the client is not trusted.

git config core.hooksPath .githooks
git commit --no-verify     # skips pre-commit and commit-msg
SeniorHow do signed commits work, and what do they actually prove?

What the interviewer is testing: supply-chain security thinking.

Author name and email in a commit are just text; anyone can write user.email as someone else. A signature binds the commit content to a private key. Git supports GPG (OpenPGP), S/MIME, and since Git 2.34 SSH keys (gpg.format ssh), which is much easier to manage. Sign with git commit -S or set commit.gpgsign true. Hosts show "Verified" when the signature matches a key registered to the account; GitHub also has vigilant mode that flags unsigned commits. What it proves: this key holder created or approved the commit, and the content has not changed since. It does not prove the code is good, nor that the key was not stolen. For releases, sign tags too (git tag -s). A pull request squash merged in the web UI is signed by the platform, not the author.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git log --show-signature -1
IntermediateHow do you stop secrets from being committed in the first place?

What the interviewer is testing: prevention layers.

Layer it. Local: a pre-commit scanner (gitleaks, detect-secrets, trufflehog) and an ignore file for env and key files. Server: the hosting platform's push protection (GitHub secret scanning push protection, GitLab secret detection) rejects a push that contains a known token pattern. CI: a scan job on every PR and a scheduled scan of full history. Design: keep secrets in a vault or the platform's secret store, load them through environment variables at runtime, commit only templates like .env.example, and use short-lived credentials where possible. Deleting a secret in a later commit does not remove it; it stays in history, so the only real answer to a leak is to rotate it.

IntermediateWhat does CODEOWNERS do, and how does it combine with branch protection?

What the interviewer is testing: ownership at scale.

A CODEOWNERS file (in the repo root, .github/, or docs/) maps path patterns to people or teams. When a PR touches matching files the platform requests those owners as reviewers automatically. If branch protection says "require review from code owners", the PR cannot merge without an approval from an owner of every touched area. The last matching pattern wins. It lets a security team own /auth/ and a platform team own /deploy/ without needing to read every PR. Keep owners as teams rather than people, so absence does not block merges, and keep the file itself owned by a small trusted group.

6. Undoing things and selective apply

BasicExplain git reset --soft, --mixed and --hard.

What the interviewer is testing: one of the top three Git questions; it tests the three-areas model.

git reset COMMIT always moves the current branch to COMMIT. The mode decides what else changes. --soft: only the branch moves; the index and working tree stay, so the undone commits' changes appear as staged. Good for "redo this commit". --mixed (the default): the branch moves and the index is reset to match; your files stay, so changes appear unstaged. Good for "uncommit and re-stage differently". --hard: branch, index and working tree all match COMMIT; every uncommitted change is gone and cannot be recovered (committed work can, through the reflog). --keep is a safer hard that refuses if it would overwrite local changes.

git reset --soft HEAD~1    # undo commit, keep changes staged
git reset HEAD~1           # undo commit, keep changes unstaged
git reset --hard origin/main   # make local branch identical to remote (destructive)
Likely follow-ups
  • What does git reset file do? Unstage that file (same as restore --staged); no branch move when a path is given.
BasicWhen do you use revert and when reset?

What the interviewer is testing: shared versus private history.

git reset moves a branch backwards and so rewrites history; use it on commits that only exist on your machine. git revert SHA adds a new commit that applies the inverse of the old one; history only grows, so it is safe on shared branches such as main, and it leaves an audit trail ("Revert X because it broke checkout"). The rule: if it has been pushed and others may have it, revert. If it is only local, reset or amend. You can revert several commits (git revert OLD..NEW) or stage without committing (-n) to combine reverts into one commit.

git revert 4be7d2a
git revert -n HEAD~3..HEAD     # inverse of the last 3, uncommitted
SeniorHow do you revert a merge commit, and what is the trap when you try to merge the branch again?

What the interviewer is testing: a genuine gotcha with merge history; strong candidates know it.

A merge commit has two parents, so Git does not know which side to undo. You must say which parent is the mainline: git revert -m 1 MERGE_SHA keeps parent 1 (the branch you merged into) and undoes what came from the other side. The trap: after that, Git considers the feature branch's commits as already merged, because they are ancestors of main. If you fix the feature and merge it again, Git brings in only the new commits and the original changes stay missing. Two fixes: first revert the revert (git revert REVERT_SHA) to bring the old changes back, then merge the new fixes; or rebuild the feature as new commits (rebase or cherry-pick them onto a fresh branch) and merge that.

BasicHow do you fix the last commit (message or content)? What changes in history?

What the interviewer is testing: everyday repair and awareness of rewriting.

git commit --amend replaces the last commit with a new one. For the message only: git commit --amend -m "better message". To add a forgotten file: stage it and run git commit --amend --no-edit. The old commit is not edited; a new one with a new hash replaces it on your branch. That is fine for unpushed commits. If you already pushed, amending needs a force-push, which affects anyone who pulled it. For an older commit use an interactive rebase with reword or edit, or a fixup commit plus autosquash. To change author on the last commit: git commit --amend --reset-author.

BasicHow do you discard local changes in one file, or all of them? What cannot be undone?

What the interviewer is testing: knowing which operations are destructive.

For one file: git restore file (old style git checkout -- file). To discard everything tracked: git restore . or git reset --hard. To delete untracked files: git clean -fd (add -x to include ignored files). Both are permanent for work that was never staged or committed, because Git has no copy. Always preview: git clean -nd lists what would go. One partial safety net: if you ever staged the file (git add), its blob exists in the object store and can be found with git fsck --lost-found, but it is awkward. Stash first if you are unsure: git stash -u keeps a copy.

BasicHow does git stash work, and what are its limits?

What the interviewer is testing: daily workflow and understanding that stash is made of commits.

git stash saves your uncommitted changes (tracked files, staged and unstaged) as special commits and resets the working tree to HEAD, so you can switch tasks. git stash pop re-applies the latest and drops it; apply re-applies and keeps it. By default untracked files are not stashed: add -u, and -a for ignored files too. Name stashes (git stash push -m "wip parser"), list them with git stash list, and stash specific paths with git stash push -- path. Internally a stash is a commit with two or three parents (HEAD, the index, and untracked files), saved under refs/stash. Limits: it is local and shared with no one, it can conflict on pop, and a dropped stash is only recoverable until garbage collection: find it with git fsck --unreachable | grep commit.

git stash push -u -m "wip: parser"
git stash list
git stash pop            # or: git stash apply stash@{1}
git stash branch fix-x   # make a branch from a stash
IntermediateWhat does cherry-pick do, and what are its risks?

What the interviewer is testing: selective apply and its downsides, especially for backports.

git cherry-pick SHA takes the change introduced by one commit (its diff against its parent) and applies it on your current branch as a new commit with a new hash; the author is kept. You can pick a range (A..B) or several commits, and use -x to add a line "(cherry picked from commit ...)" to the message, which is good for traceability on backports. For a merge commit you must pass -m 1. Risks: the same change exists twice with different hashes, so a later merge of the original branch can conflict or reapply (Git often copes through patch matching, but not always); the commit may depend on earlier commits that you did not pick; and over-use is a sign that branches are not planned well.

git switch release/1.4
git cherry-pick -x 4be7d2a
git cherry-pick --continue / --abort
IntermediateYou pushed a bad commit to a shared branch. What do you do?

What the interviewer is testing: choosing the non-destructive option under pressure.

First stop the bleeding: tell the team in chat, and if it is deployed, roll the deployment back (a deploy rollback is faster than a code fix). In Git, use git revert BAD_SHA and push the revert as a normal commit, through the normal PR path if the branch is protected. This keeps everyone's history valid. Only if the commit contains a secret or huge file is it worth rewriting history, and then with coordination. After the incident, add the missing test or check, and write a note in the PR about why it was reverted so that a re-land is done carefully.

BasicA file is in .gitignore but Git still tracks it. Why, and how do you fix it?

What the interviewer is testing: ignore rules apply only to untracked files.

Ignore patterns are consulted only for files Git is not yet tracking. If the file was committed earlier, it stays tracked and changes still show. Remove it from the index but keep it on disk: git rm --cached path (use -r for directories), commit, and the ignore rule now takes effect. This does not delete it from history, so secrets still need rotation. Check which rule matches with git check-ignore -v path. Where to put rules: project-wide in .gitignore, personal editor junk in a global file (core.excludesFile), and local-only in .git/info/exclude. For a tracked file that devs edit locally, git update-index --skip-worktree exists but is fragile; prefer a template file plus a local copy.

7. History, debugging and recovery

IntermediateWhat is the reflog and how does it save you after a bad reset or rebase?

What the interviewer is testing: the key recovery tool. Knowing it shows you are not afraid of Git.

The reflog is a local journal of where HEAD and each branch pointed over time. Every commit, checkout, reset, rebase, merge and pull appends a line. So after git reset --hard or a bad rebase, the "lost" commits are not gone; the branch label just moved away from them. Run git reflog, find the line before the mistake (for example HEAD@{4}: commit: add parser), and restore with git reset --hard HEAD@{4} or make a new branch at it. Limits: it is local only (a fresh clone has none), and entries expire: 90 days for reachable ones, 30 days for unreachable ones by default (gc.reflogExpire, gc.reflogExpireUnreachable). Uncommitted changes never enter the reflog.

Likely follow-ups
  • Reflog for one branch? git reflog show feature.
  • When is data truly gone? After the reflog entry expires and gc prunes it (unreachable loose objects older than 2 weeks by default), or when it was never committed.
SeniorThe reflog does not have it. How can a commit or file still be recovered?

What the interviewer is testing: deeper recovery tools and honest limits.

Several places may still have the object. (1) git fsck --lost-found (or --unreachable --no-reflogs) lists dangling commits and blobs, objects with nothing pointing to them but not yet pruned. Inspect them with git show HASH. (2) The remote and other clones: a teammate who pulled before the bad push has the commits, and the server's own reflog or the hosting platform's events and PR refs (refs/pull/N/head) often keep them. (3) For deleted stashes, dangling commits whose message starts with "WIP on". (4) For a file that was staged but never committed, a dangling blob. Garbage collection removes unreachable loose objects only after gc.pruneExpire (2 weeks), so act fast and do not run git gc --prune=now. Uncommitted, unstaged work is not recoverable by Git; use editor local history or backups.

git fsck --lost-found
git show 9a7c1ef
git branch recovered 9a7c1ef
IntermediateHow does git bisect work, and how do you automate it?

What the interviewer is testing: systematic debugging of a regression with logarithmic search.

Bisect finds the commit that introduced a bug by binary search over history. You mark one commit as bad (current) and one as good (an old release). Git checks out the middle commit; you test and say good or bad; Git halves the range again. For 1,000 commits you need about 10 steps. It works best with a linear, buildable history. Automate with git bisect run SCRIPT, where the script exits 0 for good, 1 to 127 (except 125) for bad, and 125 to skip an untestable commit (does not build). When done, git bisect reset returns you to your branch. Pitfalls: flaky tests give wrong answers, so make the check deterministic or repeat it; a broken-build commit in the middle needs skip; use --first-parent on merge-heavy mainlines.

git bisect start
git bisect bad                 # current commit is broken
git bisect good v2.3.0
git bisect run ./test_repro.sh # exit 0 good, 1 bad, 125 skip
git bisect reset
IntermediateHow do you find who changed a line and why, and how do you skip formatting commits in blame?

What the interviewer is testing: using history as documentation.

git blame file shows, per line, the last commit that changed it. Add -L 40,60 for a range, -w to ignore whitespace, and -M or -C to follow lines moved or copied between places and files. A line's last change is often a mass reformat. Put the hash of that commit in a file (for example .git-blame-ignore-revs) and use git blame --ignore-revs-file .git-blame-ignore-revs, or set blame.ignoreRevsFile; GitHub reads that file name automatically. Then from the commit shown, run git show SHA to read the reason, and follow the ticket id. Blame is for understanding, not blaming people.

IntermediateHow do you search history for when a line, a function or a string was added or removed?

What the interviewer is testing: a toolbox beyond git log.

The pickaxe: git log -S"retryCount" finds commits where the number of occurrences of that string changed, so it finds the commit that added or removed it. -G"regex" matches commits whose diff lines match a regex. git log -L :funcName:file shows the history of one function (or -L 10,30:file for lines) with diffs. Useful filters: --author, --since, --grep (message search), --all, -- path, --diff-filter=D for deleted files, --merges or --no-merges. git log --graph --oneline --decorate --all draws the shape of history. To search content at a given commit use git grep pattern REV.

git log -S"timeout" --oneline -- src/
git log --diff-filter=D --name-only -- "*Config.java"   # who deleted it
git log -L :parseHeader:src/Parser.java
git log --first-parent --since="2 weeks ago" --oneline main
BasicHow do you get back a file that was deleted several commits ago?

What the interviewer is testing: restore from history.

Find the commit that deleted it: git log --diff-filter=D --oneline -- path/file. The file still exists in that commit's parent. Restore it from there: git restore --source=SHA^ -- path/file (older form git checkout SHA^ -- path/file), which puts it in the working tree and the index; then commit. If you want the whole older version of the file in a new path, git show SHA^:path/file > copy.txt. The same pattern restores any earlier version of a file without changing the rest of the tree.

SeniorWhat does "reachable" mean, and when does Git actually delete things?

What the interviewer is testing: understanding of garbage collection, which explains both recovery windows and leaked-data risk.

An object is reachable if you can get to it by starting from a ref (branches, tags, HEAD, stash, remote-tracking refs, and reflog entries) and following parent and tree pointers. Everything else is unreachable. Git never deletes on the spot. git gc, which runs automatically after enough loose objects pile up and via git maintenance, repacks reachable objects and removes unreachable loose ones older than gc.pruneExpire (2 weeks default). Reflog entries keep their commits alive until they expire (90 days, or 30 for unreachable ones). So a deleted branch is recoverable for weeks. The opposite side matters for secrets: after you remove a leaked file by rewriting history, old objects remain in your clone, in forks, in the host's caches and pull-request refs, until pruned.

git reflog expire --expire=now --all
git gc --prune=now      # destructive; only after you are sure
BasicWhich diff and show commands do you use daily to inspect changes?

What the interviewer is testing: practical fluency.

git diff for unstaged, git diff --staged for staged, git diff main...HEAD for what my branch changes compared to the point it forked. --stat gives a file summary, --name-only just names, -w ignores whitespace, --word-diff highlights words, and --color-moved shows moved blocks as moves rather than delete and add. git show SHA shows one commit with its diff, git show SHA:path shows a file as of that commit. git log -p shows the patches, git shortlog -sn counts commits per author, and git range-diff compares two versions of a patch series, handy after a rebase.

8. Tags, releases and backports

BasicLightweight tag versus annotated tag: what is the difference and which for releases?

What the interviewer is testing: object model plus release discipline.

A lightweight tag is just a ref (a name pointing at a commit), like a branch that never moves. An annotated tag is a real object with its own tagger, date and message, and can be signed (-s). Use annotated tags for releases: they carry who and when and why, show up in git describe, and many tools treat only annotated ones as releases. Tags are not pushed by default: git push origin v1.4.0, or git push --follow-tags which pushes annotated tags reachable from pushed commits. Tags should be immutable: moving a published tag confuses caches and consumers. If you tagged the wrong commit, make a new version rather than rewriting the tag.

git tag -a v1.4.0 -m "Release 1.4.0"
git tag -s v1.4.0 -m "Release 1.4.0"     # signed
git push origin v1.4.0
git tag -d v1.4.0 && git push origin :refs/tags/v1.4.0   # delete (avoid for released tags)
IntermediateWhat does git describe give you and how is it used in builds?

What the interviewer is testing: traceable build versions.

git describe finds the nearest annotated tag reachable from the commit and prints it with the number of commits since, and the short hash: for example v1.4.0-12-g4be7d2a, meaning 12 commits after v1.4.0, at commit 4be7d2a (the g stands for git). Build scripts stamp this string into the binary or the image tag, so any running artifact can be mapped back to the exact source. Add --dirty to mark builds from a modified tree, and --tags to include lightweight tags. In CI it needs history and tags to be fetched; a shallow clone gives an error or just a hash.

SeniorHow would you manage release branches and versions for a product that supports several versions at once?

What the interviewer is testing: release engineering design.

Develop on main (trunk). When a version is feature-complete, cut release/1.4 from main; only bug fixes go there, with stricter review. Tag each release from the release branch (v1.4.0, then v1.4.1 for patches) using semantic versioning (major for breaking, minor for features, patch for fixes). The rule for fixes: fix on main first, then cherry-pick to the supported release branches (with -x), so no fix is ever lost in a future version. Some teams do the opposite (fix on the oldest affected branch and merge forward); that guarantees history ancestry but needs a clean merge path. Automate with release tooling that builds from the tag, generates notes from merged PRs, and signs artifacts. Retire release branches on a published support schedule.

IntermediateWalk through backporting a fix from main to an older release branch.

What the interviewer is testing: concrete cherry-pick workflow with the risks.

Fix and merge on main first, with a test. Then branch from the release branch, not main: git switch -c backport/1.4-fix release/1.4. Run git cherry-pick -x SHA. If the fix was squash-merged on main, there is exactly one commit to pick; if it was several commits, pick the range in order. Resolve conflicts, since the older code may differ, then run the release branch test suite, not only the new test. Open a PR into release/1.4 that links the original PR. After merging, tag the patch release (v1.4.1). Check that dependent changes are not required. Many platforms offer a "backport" bot or label that does these steps.

IntermediateProduction is broken and the fix must ship now, but main has unreleased work. What is your Git flow?

What the interviewer is testing: separating a safe hotfix from unfinished work.

Branch from the exact commit or tag that is running in production (git switch -c hotfix/payment-npe v2.8.3), not from main. Make the smallest possible fix with a test, get a fast review, and run the pipeline. Tag the result (v2.8.4) and deploy from the tag. Then bring the fix back: merge the hotfix into main (or cherry-pick it), so the next release has it, and into any other supported release branch. If rollback is quicker than a fix, roll back the deployment first and fix calmly. Afterwards review why the bug escaped, and add tests.

IntermediateHow do you produce release notes or find what is in release B but not in release A?

What the interviewer is testing: range queries as release tools.

git log v1.3.0..v1.4.0 --oneline --no-merges lists the commits reachable from v1.4.0 but not from v1.3.0. With squash merges each line equals one PR; add --first-parent to list only mainline commits when merges are used. git shortlog v1.3.0..v1.4.0 groups by author. To check whether a specific fix is in a release: git tag --contains SHA or git branch -r --contains SHA. To see what was backported but is missing in another branch, git cherry -v release/1.4 main compares by patch ID (a plus sign means not applied). Conventional Commit messages and a tool can turn this into a formatted changelog.

9. Configuration, hygiene and performance

BasicWhat are the config levels in Git, and which settings should every developer set?

What the interviewer is testing: setup knowledge and awareness of precedence.

Three main levels, later ones override earlier ones: --system (whole machine), --global (your user: ~/.gitconfig), and --local (this repo: .git/config). There is also --worktree, and includeIf sections let you switch identity by folder (work versus personal). Must-have settings: user.name and user.email, init.defaultBranch main, pull.rebase true (or pull.ff only), fetch.prune true, push.autoSetupRemote true, rerere.enabled true, merge.conflictStyle zdiff3, rebase.autoSquash true, core.autocrlf or better a .gitattributes file, and a signing setup.

git config --list --show-origin
git config --global includeIf."gitdir:~/work/".path ~/.gitconfig-work
IntermediateTeammates on Windows and Linux produce whole-file diffs. How do you fix line endings properly?

What the interviewer is testing: .gitattributes versus per-user config.

Windows uses CRLF, Unix uses LF. If each person's core.autocrlf differs, files flip back and forth. The robust fix is to commit a .gitattributes file so the rule lives in the repo and applies to everyone: * text=auto lets Git normalise text files to LF in the repository, and you can force *.sh text eol=lf (scripts must keep LF) and *.bat text eol=crlf. Mark binaries as binary. Then renormalise once: git add --renormalize ., commit this alone, and add its hash to the blame-ignore file. Also keep core.autocrlf as input on Linux/Mac and true on Windows if you have no attributes file.

IntermediateWhat is Git LFS and what are its trade-offs?

What the interviewer is testing: handling large binaries.

Git LFS (Large File Storage) replaces large files in the repository with small text pointers (a version, an object id and a size), and stores the real bytes on a separate LFS server. Clone and checkout download only the versions you need. You configure it with git lfs track "*.psd", which writes rules to .gitattributes. Benefits: the repo stays small and fast, binary history does not bloat clones. Costs: it needs server support and bandwidth quotas, a second download step, an LFS install on every machine and CI runner, and pointers make offline use harder. Already committed big files stay in history unless you migrate them with git lfs migrate import (a history rewrite). Alternatives: keep binaries in an artifact repository (Nexus, Artifactory, S3) and refer to them by version.

SeniorSubmodules, subtree or a monorepo: how do you share code between repositories?

What the interviewer is testing: architectural trade-offs, plus the sharp edges of submodules.

A submodule embeds another repo at a fixed commit: the parent stores only the pointer (a "gitlink"). It gives exact reproducibility and clean separation. The pain: a clone needs --recurse-submodules (or git submodule update --init), people forget to push the submodule before the parent (the parent then points to a commit nobody can fetch), updates are two-step, and detached HEADs surprise people. Subtree copies the other project's files into a folder of your repo and can split them back out: no extra clone steps, but history is mixed and syncing is manual. A monorepo puts everything in one repo: atomic cross-project changes and one version of dependencies, but needs tooling (partial clone, sparse checkout, build graph, code owners). My first choice for shared libraries is a versioned package from a registry, and submodules only for source that must be pinned and built together.

git clone --recurse-submodules URL
git submodule update --init --recursive
git config submodule.recurse true
SeniorWhat are partial clone, sparse-checkout and shallow clone, and how do they differ?

What the interviewer is testing: modern big-repo tooling and the difference between what you download and what you check out.

Three separate knobs. Shallow (--depth N) limits how much history is downloaded. Partial clone (--filter=blob:none, or --filter=tree:0) keeps the full commit history but leaves out file contents, fetched lazily from the server the first time you need them (a "blobless" clone, the usual choice for developers; "treeless" is lighter still but slower for some history commands). Sparse-checkout limits which paths appear in your working tree; with cone mode you list directories and Git shows only those. Combine partial clone plus sparse-checkout for a large monorepo: you download history and only the files for your folders. Shallow is best for CI builds that do not need history; blobless suits developers because history commands still work.

git clone --filter=blob:none --sparse URL big
cd big
git sparse-checkout set services/billing libs/common
IntermediateWhat is git worktree and when is it better than stash or a second clone?

What the interviewer is testing: productivity techniques.

git worktree add ../hotfix release/1.4 creates a second working directory for the same repository, checked out on another branch, sharing one object database. You can review a PR, run a long build, or fix a release branch in one folder while your feature work sits untouched in the other: no stash, no dirty tree, no second full clone and no duplicate objects. Rules: a branch can be checked out in only one worktree at a time. Clean up with git worktree remove and git worktree prune. It is also handy to compare behaviour of two branches side by side, and for agents or tools that need an isolated checkout.

git worktree add ../app-hotfix -b hotfix/x release/1.4
git worktree list
git worktree remove ../app-hotfix
SeniorWhy does Git get slow on a huge repo, and what do you do about it?

What the interviewer is testing: performance diagnosis with concrete tools.

Causes: git status must check every tracked file (cost grows with file count), clone and fetch move large packs, and history walks (log, blame, reachability) read many commits. Fixes in order: (1) Run git maintenance start (scheduled gc, prefetch, commit-graph, incremental repack). (2) Enable the commit-graph (fetch.writeCommitGraph), which speeds up history queries. (3) Use core.fsmonitor true and core.untrackedCache true so status asks the OS what changed (built-in file system monitor on Windows and macOS). (4) Use partial clone plus sparse-checkout so you do not hold everything. (5) Keep blobs out of history: LFS or artifact stores. (6) Microsoft's scalar command (part of Git) configures many of these for you. (7) Split the repo only if the above is not enough. Measure first with GIT_TRACE=1 or GIT_TRACE_PERFORMANCE=1, and git count-objects -vH.

SeniorHow do you permanently remove a file or secret from the entire history?

What the interviewer is testing: the correct modern tool and understanding of the aftermath.

Use git filter-repo (a separate Python tool, recommended by the Git project) rather than the slow and error-prone git filter-branch; BFG Repo-Cleaner is another fast option. Work on a fresh mirror clone: git filter-repo --invert-paths --path secrets.env (or --replace-text to scrub strings). It rewrites every commit, so every hash after the first affected one changes. Then force-push all branches and tags, ask every developer to re-clone (an old clone can push the bad history back), and ask the host to clear cached views and PR refs. Forks, caches and clones may still hold the data, so this is damage limiting. The real fix for a secret is to rotate it, and to do that first.

git clone --mirror URL repo.git && cd repo.git
git filter-repo --invert-paths --path config/prod.env
git push --force --mirror
IntermediateWhich settings and aliases make Git safer and faster for a team?

What the interviewer is testing: practical hygiene.

Safety: push.default simple, a force alias that always uses --force-with-lease, pull.ff only or pull.rebase true, rebase.autoStash, merge.conflictStyle zdiff3, rerere.enabled, fetch.prune. Speed: core.fsmonitor, core.untrackedCache, feature.manyFiles true for large trees, and git maintenance start. Team: commit .gitattributes, a .gitignore, .git-blame-ignore-revs, CODEOWNERS and a shared hooks directory. Useful aliases: a pretty graph log, last for log -1 --stat, undo for reset --soft HEAD~1, pushf for the lease force. Do not hide dangerous commands behind short aliases without the safety flags.

git config --global alias.lg "log --graph --oneline --decorate --all"
git config --global alias.undo "reset --soft HEAD~1"
git config --global alias.pushf "push --force-with-lease --force-if-includes"
SeniorWhat are Git attributes and filters used for (diff drivers, merge drivers, clean and smudge)?

What the interviewer is testing: extensibility knowledge that seniors reach for in awkward repos.

.gitattributes assigns behaviour per path pattern. text, eol and binary control line endings and diffing. diff=NAME picks a custom diff driver (for example show a spreadsheet or a minified file as text). merge=union merges by keeping both sides' lines, useful for append-only lists such as a changelog; merge=ours with a custom driver can keep the local copy of generated files; -diff hides noisy generated files. filter=NAME runs a clean script when files are staged and a smudge script on checkout: LFS uses exactly this. linguist-generated collapses a file in GitHub review. Lockfiles are best handled by "take either side, then regenerate".

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

SeniorA teammate force-pushed over main and the last 15 commits disappeared. What do you do?

What the interviewer is testing: incident calm, knowing that commits survive in many places, and prevention.

Situation: the remote main label now points to an older or different commit. The 15 commits still exist as objects; only the label moved.

Check first: freeze pushes and tell the team not to pull or reset, and not to run git gc. Find the old tip. The best sources: any clone that fetched recently (git reflog show origin/main on a teammate's machine, or git log origin/main before they fetch again), the CI system's last successful build (it shows the commit SHA), the PR merge records, the hosting platform's audit log or push events, and the platform's API for push events. The host support can also restore from server-side reflog.

Steps:

# on a machine that still has the old tip
git fetch origin
git reflog show origin/main        # find OLD_SHA, the tip before the force push
git branch rescue-main OLD_SHA
git push origin rescue-main        # keep a safe copy first
# restore main. If the rewritten commits are wanted too, merge or cherry-pick them
git push --force-with-lease=main:BAD_SHA origin OLD_SHA:main

If the force-push also contained valid new commits, do not blindly overwrite again: reset main to OLD_SHA, then cherry-pick or merge the new valid work on top. Tell everyone to git fetch and reset local main to origin.

Prevent: branch protection with "block force pushes" and "restrict deletions" on main for everyone including admins, use --force-with-lease only on feature branches, push protection rules, and an audit alert for forced updates to protected refs.

Likely follow-ups
  • What if nobody has the old SHA? Ask the host (server-side reflog or backup), check CI logs and release tags, search PR pages for the "merged commit" ids.
SeniorSomeone committed and pushed a cloud access key. What are the steps, in order?

What the interviewer is testing: correct priority: revoke first, clean later.

Situation: an AWS key (or a token, or a password) is in a commit on a remote, maybe public, maybe in forks and CI logs.

Check first: assume it is already compromised: scanners find leaks in minutes. Who owns the key, what can it access, and since when was it exposed? Check access logs of the provider for use.

Steps:

  1. Rotate or revoke the key immediately and issue a new one through the secret manager. Check the provider logs for unauthorised use and open a security incident if so.
  2. Remove it from the code (load from the secret store or environment) in a normal commit, so the build is clean.
  3. Then decide on history cleaning: for a private repo with a rotated key, many teams stop here. For public repos, compliance, or high-value secrets, rewrite history with git filter-repo --replace-text on a mirror, force-push, ask everyone to re-clone, and ask the host to purge cached views and PR refs and contact support about forks.
  4. Write a short post-mortem.

Prevent: pre-commit scanner, platform push protection, secret scanning on CI, short-lived credentials (OIDC roles instead of static keys), and least-privilege keys.

Common mistakes: cleaning history first and rotating later; thinking a follow-up "remove key" commit solves it.
SeniorA big feature branch was merged to main and broke production. How do you back it out cleanly, and ship the fix later?

What the interviewer is testing: revert of a merge and the re-merge trap.

Situation: merge commit M is on main, deployed, and users are failing. Others have committed on top of M.

Check first: can you roll back the deployment to the previous tag? Do that first for speed. Confirm M is a merge: git show --no-patch --format=%P M lists two parents.

Steps:

git switch -c revert-feature main
git revert -m 1 M          # keep parent 1 (main side), undo the feature side
# run tests, open PR, merge, deploy
# later, when the feature is fixed:
git revert REVERT_SHA      # "revert the revert" brings the old changes back
git merge feature-fixed    # now only the new fixes need merging

Alternative for the second round: create a new branch with the old and new commits rebased or cherry-picked, so the merge is not blocked by the earlier merge record.

Prevent: feature flags so risky code can be switched off without a revert, smaller PRs, canary deploys, and merge queue so main is always tested as it will land.

SeniorThe repository is 12 GB, a fresh clone takes 40 minutes, and CI is slow. What is your plan?

What the interviewer is testing: measure, find the cause, fix with the right tool.

Situation: clone and fetch are slow, git status lags, CI spends most time on checkout.

Check first: why is it big: many files, long history, or large blobs? git count-objects -vH for size; list biggest blobs: git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n -r | head. Look for binaries, build outputs, data dumps, vendored dependencies.

Steps:

  • CI: shallow clone (--depth 1) or a blobless partial clone, plus a cache of the repo or a persistent mirror; fetch only needed paths with sparse checkout.
  • Developers: git clone --filter=blob:none --sparse and git sparse-checkout set on needed folders; run git maintenance start; enable core.fsmonitor and commit-graph.
  • Root cause: move big binaries out of history with git filter-repo or git lfs migrate (coordinated rewrite, everyone re-clones), and add pre-receive rules that reject files above a size limit.
  • If it is a true monorepo, add build caching and ownership, not just Git tuning.

Prevent: size limits on the server, LFS or artifact store for binaries, no generated files in Git, and periodic repo health checks.

BasicYou made commits in detached HEAD, switched back to main, and now they seem gone.

What the interviewer is testing: reflog use under a very common mistake.

Situation: git warned "you are leaving 2 commits behind", you ignored it, and your work has no branch.

Check first: do not panic and do not run gc. git reflog lists where HEAD went; look for the entry with your commit message just before the "checkout: moving from HASH to main" line.

git reflog
# 7c1a9e2 HEAD@{1}: commit: fix retry logic     (your work)
git branch rescue 7c1a9e2
git switch rescue

Now the commits have a name. Merge or cherry-pick them wherever you wanted. Prevent: read the warning git prints when leaving detached HEAD, and run git switch -c name as soon as you decide to keep work from a detached state.

IntermediateYou rebase a 30-commit branch and hit the same conflict again and again. What now?

What the interviewer is testing: a pragmatic way out and awareness of rerere and squash.

Situation: the branch lived for weeks and main changed a lot in the same files. Each of your commits touches the conflicting lines, so each replay conflicts.

Check first: git status shows the step ("4 of 30"). If you are far into it and confused, run git rebase --abort: it is always safe.

Options, best first:

  1. Merge instead: git merge main on your branch resolves all conflicts once, in one commit. If the PR will be squash-merged, the intermediate history does not matter.
  2. Squash first, then rebase: git rebase -i $(git merge-base main HEAD), squash to a few commits, then rebase onto main: conflict resolved once per commit.
  3. Enable rerere (git config rerere.enabled true), abort, and run again: your first resolutions are replayed automatically afterwards.
  4. Reduce the delta: rebase in steps onto intermediate points of main (git rebase main~50, then closer).

After finishing, run tests and git range-diff against the old branch. Prevent: integrate with main daily, keep branches short, use feature flags, and avoid mass reformatting in feature branches.

IntermediateCustomers on v2.3 and v3.0 both hit a security bug. You must patch both lines. How do you do it with Git?

What the interviewer is testing: multi-version release handling.

Situation: main is v3.x, release/2.3 is supported, and the fix must ship in both without losing it in the future.

Steps:

# 1. fix on main (or on the oldest affected branch) with a regression test
git switch -c fix/cve-2026-1234 main
# ... commit, PR, merge, tag v3.0.5
# 2. port to the older line
git switch -c backport/2.3-cve release/2.3
git cherry-pick -x MAIN_FIX_SHA
# conflict? adapt code to the 2.3 structure, rerun the 2.3 test suite
# PR into release/2.3, tag v2.3.9, publish advisory

Rule: the fix must exist in every supported branch and in main, and the patch release is built from a tag. Check with git branch -r --contains FIX_SHA or git cherry -v. Prevent: a documented support policy, a backport label or bot, and tests that exist on each release line.

IntermediateA performance regression appeared sometime in the last 400 commits. How do you find the cause?

What the interviewer is testing: systematic search and automation.

Situation: the nightly benchmark went from 200 ms to 900 ms. Nobody knows which change did it.

Check first: get a repeatable test with a clear pass or fail, e.g. a script that builds and runs the benchmark and exits 1 if above 400 ms. Find a known good commit or tag from last month.

git bisect start
git bisect bad HEAD
git bisect good v3.1.0
git bisect run ./bench_check.sh     # about 9 steps for 400 commits
git bisect log > bisect.txt
git bisect reset

Handle commits that do not build with exit code 125 (skip). If history has many merges, use --first-parent first, then bisect inside the faulty merge. Once found, read the commit with git show, confirm by reverting it locally, then fix forward or revert. Prevent: benchmark gates in CI so the regression is blocked on the PR.

BasicYou committed three commits directly on main instead of a feature branch, and have not pushed yet.

What the interviewer is testing: the "move commits" idiom with branch and reset.

Check first: git status and git log --oneline origin/main..main to confirm exactly which commits are yours and that nothing is pushed.

git branch feature/payment-retry     # label the commits you made, at current tip
git reset --hard origin/main         # move main back to the remote state
git switch feature/payment-retry     # continue here

This is safe because the commits are kept by the new branch label before main moves. If you had also uncommitted changes, stash first. If you already pushed to main, the fix is different: revert the commits through a PR (protected main should have blocked the push anyway). Prevent: protect main so a local commit cannot be pushed, and a pre-commit or prompt that shows the branch name.

BasicYou deleted a branch with -D and then realised it had unmerged work. How do you get it back?

What the interviewer is testing: branches are labels; commits live on.

When you delete a branch Git prints the hash it pointed to: Deleted branch feature (was 9a7c1ef). If you can see it, run git branch feature 9a7c1ef and you are done. If not, git reflog shows the last commit made on that branch (the line "commit: ..."), then git branch feature HASH. If it had been pushed, git fetch still has origin/feature, or you can restore it from the web page of the closed PR (GitHub has a "restore branch" button). This works until garbage collection prunes the commits, which takes weeks. Prevent: use -d, which refuses unmerged branches, and avoid -D unless you checked.

IntermediatePush fails because a 300 MB file is in your commit. You deleted it in a later commit and it still fails.

What the interviewer is testing: history keeps data; removal needs a rewrite.

Situation: hosts reject single files over about 100 MB (the exact limit depends on the host). Deleting the file in a new commit does not help because the push still carries the earlier commit that added it.

Steps (unpushed local commits): remove it from the commit that added it. If it was in the last commit, git rm --cached big.bin, then git commit --amend. If it was a few commits back, run git rebase -i origin/main, mark that commit edit, remove the file, amend, continue. If many commits are involved, use git filter-repo --path big.bin --invert-paths. If the file really belongs in the repo, track it with Git LFS before committing (git lfs migrate import --include="*.bin" can convert it now). Add the file type to .gitignore or LFS rules and a server-side size limit. Prevent: pre-commit size check.

Basicgit status says "Your branch and origin/main have diverged, 2 and 3 different commits each". What does it mean and what do you do?

What the interviewer is testing: reading status and choosing integrate over overwrite.

It means you have 2 local commits the remote does not have, and the remote has 3 commits you do not have. Neither side contains the other. Look first: git fetch, then git log --oneline --left-right main...origin/main. Then integrate. For a personal branch: git rebase origin/main (replays your 2 on top of their 3) and push. For a shared branch where others rely on your commits: git merge origin/main. Do not use reset --hard origin/main unless you want to throw away your 2 commits, and do not force-push, which would delete their 3. If the divergence happened because you amended or rebased a commit that was already pushed, rebase with --onto, or accept that the remote needs --force-with-lease.

IntermediateYou ran git stash drop (or clear) by mistake and need the changes back.

What the interviewer is testing: stash is made of commits that remain until gc.

When you drop a stash, Git prints its hash: Dropped refs/stash@{0} (b1e9c0f...). Apply it with git stash apply b1e9c0f or git branch recovered b1e9c0f. If the message is gone, find dangling commits: git fsck --no-reflogs --unreachable | grep commit, then check each with git show HASH (stash commits are titled "WIP on branch: ..." or "On branch: your message"). Do it soon, before gc prunes them, and never run git gc --prune=now while looking. Prevent: use stash apply first, and drop only after the change is committed. For anything that matters, commit to a temporary branch instead of stashing.

IntermediateAfter a teammate's commit, every file in the repo shows as modified. What happened?

What the interviewer is testing: line endings, file modes and formatting diagnostics.

Check first: git diff --stat and git diff | head. If you see ^M or lines identical to the eye, it is line endings (CRLF versus LF). If the diff says "old mode 100644 new mode 100755", it is file mode (common on Windows or a mounted drive): git config core.fileMode false locally. If it is only whitespace, check an auto-formatter.

Fix for line endings: add a .gitattributes with * text=auto (and explicit rules for scripts), run git add --renormalize ., commit that alone with a clear message, and add its hash to .git-blame-ignore-revs. Ask teammates to run git rm --cached -r . && git reset --hard only after they have committed or stashed their own work. Prevent: attributes file in the repo, .editorconfig, and a CI check on formatting.

BasicYou ran git reset --hard and lost a day of work. Is it recoverable?

What the interviewer is testing: the line between committed and uncommitted data.

Split by what kind of work it was. Committed work is recoverable: git reflog, find the tip before the reset, and git reset --hard HEAD@{1} or make a branch there. Staged but never committed work: the file contents were written as blobs when you ran add, so git fsck --lost-found can list dangling blobs, but you get content without file names; it is tedious but possible. Never staged or committed changes are gone from Git's view. Try the editor's local history (JetBrains Local History, VS Code Timeline), file-system snapshots, backups. Prevent: commit often (even WIP commits you later squash), use git stash -u before risky operations, and prefer reset --keep or switch, which refuse to overwrite local changes.

SeniorA three-month feature branch must merge, and main has changed in hundreds of files. How do you land it without a disaster?

What the interviewer is testing: risk reduction rather than heroic merging.

Situation: a big-bang merge will conflict heavily and cannot be reviewed.

Approach:

  1. Stop the drift: merge main into the branch weekly from now (rerere on), so each merge is small.
  2. Do the big merge in a dedicated integration branch, not on main. Resolve once, get CI green, and let two people review the conflict resolutions (git diff main...integration and git show --remerge-diff MERGE_SHA on Git 2.36 or newer shows exactly what the human changed in the merge).
  3. Prefer slicing: merge preparatory refactors first as small PRs, put new behaviour behind a feature flag, and land the rest in pieces to main.
  4. Run the full test suite and a staged rollout (canary). Keep the merge as a merge commit, so you can revert it with -m 1 if it fails.

Prevent: trunk-based practice, flags, and a team rule that branches older than a week are reviewed in stand-up.

IntermediateMain is red because of a merged PR and ten other people are blocked. What do you do in the first 15 minutes?

What the interviewer is testing: restore service first, diagnose second.

Check first: find the first failing commit in CI history and the PR that introduced it (git log --first-parent on main, or the CI timeline). Is it a real bug, a flaky test, or an infrastructure failure?

Steps: announce in the team channel that you are handling it. If it is a real regression, revert the PR right away (git revert -m 1 MERGE or revert the squash commit), merge the revert quickly with the minimum required approval, and let the author re-land a fixed version with a test. Do not try a clever forward fix while main is red. If it is a flaky test, quarantine it with a ticket. If the cause is the combination of two PRs, that is the case a merge queue prevents. Prevent: merge queue or required up-to-date checks, a team rule "red main is priority zero", and flaky test tracking.

IntermediateYour last five commits used the wrong author email (a personal one). How do you correct them?

What the interviewer is testing: rewriting small local history and the push consequence.

If unpushed: git rebase -r HEAD~5 --exec "git commit --amend --no-edit --reset-author" after fixing user.email with git config user.email work@company.com. That resets author to the current config for each of the five. Verify with git log --format='%h %an %ae' -5. If pushed to your own PR branch, push again with --force-with-lease. If it is on shared main history, do not rewrite; instead add a .mailmap entry, which makes tools such as log and shortlog display the canonical identity. Fix the root cause with the right includeIf identity per folder, and enable a server rule that checks the author domain.

SeniorA colleague's build fails with "fatal: remote error: upload-pack: not our ref" on a submodule. What happened?

What the interviewer is testing: submodule model: the parent stores only a commit pointer.

Situation: the parent repo records submodule commit S. S was created locally in the submodule and never pushed, or the submodule branch was force-pushed or rebased, so the server no longer has S.

Check first: git submodule status and git ls-tree HEAD path/to/sub to see the recorded SHA, then ask the author, or look in the submodule's remote for it.

Fix: the author enters the submodule and pushes the missing commit (git push inside it), or creates a branch pointing to it so it is not pruned. If it is lost, update the pointer to a commit that exists (cd sub; git switch main; git pull; cd ..; git add sub; git commit). Prevent: git push --recurse-submodules=check (or on-demand) refuses to push the parent unless the submodule commits are pushed, push.recurseSubmodules in config, and a CI step that runs git submodule update --init --recursive on every PR.

IntermediateYou amended and force-pushed your PR branch, and the reviewer says their comments and history are confusing. What should you have done?

What the interviewer is testing: review etiquette around rewriting.

Force-pushing your own PR branch is allowed, but it breaks the reviewer's view of "what changed since I last looked", and on some platforms it hides earlier comments as outdated. A better habit: while the PR is under review, add small fixup! commits (or normal commits) so the reviewer sees incremental diffs; push normally. When the PR is approved, squash with rebase -i --autosquash, or let the platform squash on merge, which needs no force-push. If you must rebase for conflicts, say so in the PR and use git range-diff output as a comment, so the reviewer can see the change in a series. Always use --force-with-lease.
