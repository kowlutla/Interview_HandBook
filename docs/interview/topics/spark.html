Mental model: the 8 ideas everything hangs on

One line: Spark splits your data into partitions, runs the same code on each partition in parallel (tasks), and only moves data between machines (a shuffle) when an operation needs rows with the same key together. Transformations only build a plan. An action runs it.
  1. Driver and executors. The driver is one process that holds your program, builds the plan and schedules work. Executors are worker processes that hold data in memory and run tasks.
  2. Partitions are the unit of parallelism. One partition is processed by one task at a time. More partitions means more parallel tasks, up to the number of cores you have.
  3. Lazy evaluation. filter, select, join do nothing yet. They add to a plan. Only an action (count, write, collect) starts a job.
  4. Narrow versus wide. A narrow step (map, filter) works on each partition alone. A wide step (groupBy, join, repartition) needs data from many partitions, so it causes a shuffle.
  5. Shuffle is the cost center. It writes to disk, moves data over the network and reads it back. Most Spark tuning is "avoid, shrink or balance the shuffle".
  6. Job, stage, task. An action makes a job. A job is cut into stages at every shuffle. A stage is a set of identical tasks, one per partition.
  7. The optimizer is on your side. DataFrame and SQL code goes through Catalyst (plan rewrites) and Tungsten (fast code and memory layout). Opaque code (Python lambdas, UDFs, RDD functions) blocks it.
  8. Lineage gives fault tolerance. Spark remembers how each partition was computed, so a lost partition is recomputed instead of restored from a replica.

1. Why Spark, and the architecture

What is Apache Spark and why did it replace MapReduce for most workloads? Basic

What the interviewer is testing: do you understand the real design difference, not just "Spark is faster".

Spark is a distributed engine for processing large data sets in parallel across a cluster. You write transformations on a distributed collection, and Spark splits the work into tasks and runs them on many machines. MapReduce forces every job into a fixed map then reduce shape and writes the result of every stage to disk (HDFS). A chain of ten steps becomes ten jobs, each reading and writing disk. Spark describes the whole chain as one plan (a DAG), keeps intermediate data in memory where it can, and only touches disk at shuffles. It also offers one engine for batch, SQL, streaming, machine learning and graphs, instead of separate tools. The claim of "up to 100 times faster" is for in-memory iterative jobs; for a single big scan-and-aggregate the gain is usually a few times, and Spark still spills to disk when data does not fit.

Likely follow-ups
  • Is MapReduce dead? Mostly for new work. The idea (map, shuffle, reduce) is still inside Spark.
  • When is Spark a bad choice? Tiny data (a single machine is faster), low-latency single-row lookups, and heavy per-record transactional work.
Explain the driver, the executors and the cluster manager. Basic

What the interviewer is testing: the basic runtime picture you need to reason about any failure.

The driver is the process that runs your main method. It creates the SparkSession, turns your code into a plan, cuts the plan into stages and tasks, and hands tasks to executors. It also tracks task status and collects small results. The executors are JVM processes on worker machines. Each has some cores (task slots) and some memory. They run tasks, keep cached data and write shuffle files. The cluster manager only hands out resources: it starts the executor processes when the driver asks. It does not understand your job. Because the driver is a single process, it is a single point of failure: if the driver dies, the application dies. Executors, on the other hand, can be lost and replaced while the job continues.

Likely follow-ups
  • Who decides how many tasks run? The driver, from the number of partitions. How many run at once depends on total executor cores.
  • Does data flow through the driver? Not normally. Executors read the files directly. Data only reaches the driver with collect, toPandas and similar.
YARN, Kubernetes, standalone: how do they differ, and what are client and cluster deploy modes? Intermediate

What the interviewer is testing: can you deploy and debug a job on the platform your company uses.

Standalone is Spark's own simple manager (a master and workers). It is easy to start and fine for small dedicated clusters. YARN is the Hadoop resource manager: Spark asks for containers, and the job shares the cluster with other Hadoop workloads through queues. Kubernetes (supported since 2.3, generally available in 3.1) runs the driver and each executor as pods, so you package Spark in a container image and the cluster handles scheduling and isolation. Mesos support was removed in 3.2 and later. The deploy mode says where the driver runs. In client mode the driver runs on the machine that submitted the job, which is good for notebooks and the interactive shell, but the job dies if that machine or its network dies. In cluster mode the driver runs inside the cluster, which is the normal choice for production and scheduled jobs, and logs are read from the cluster. The right sizing and queue settings of the cluster itself are an ops topic.

spark-submit --master yarn --deploy-mode cluster \
  --num-executors 10 --executor-cores 4 --executor-memory 8g \
  --class com.acme.Etl app.jar 2026-11-17

spark-submit --master k8s://https://api-server:443 --deploy-mode cluster \
  --conf spark.kubernetes.container.image=acme/spark:3.5 \
  --conf spark.executor.instances=10 local:///opt/app/app.jar
Likely follow-ups
  • Why does a driver in client mode on a laptop often fail? The executors must connect back to it, and firewalls or slow links break that.
  • What does --master local[4] do? Runs everything in one JVM with four threads. It is the mode used for unit tests.
What are SparkContext and SparkSession? Basic

What the interviewer is testing: API history and entry points.

SparkContext is the original entry point (Spark 1.x). It connects to the cluster and creates RDDs. Spark 2.0 added SparkSession as one single entry point that wraps the context, the SQL context and the Hive context. You use it to read data (spark.read), run SQL (spark.sql), and set configs (spark.conf). Normally one active session per application is enough. You can get the underlying context with spark.sparkContext when you need RDDs, broadcast variables or accumulators. In a managed platform such as a notebook, the spark variable is already created for you.

val spark = SparkSession.builder()
  .appName("daily-etl")
  .config("spark.sql.shuffle.partitions", "400")
  .getOrCreate()
Likely follow-ups
  • What is Spark Connect (3.4+)? A thin client protocol: your code talks to a remote Spark server over gRPC, so the client process does not hold the driver.
What happens, step by step, when you submit a Spark application? Intermediate

What the interviewer is testing: end to end understanding of the runtime.

First spark-submit asks the cluster manager to start the driver (in cluster mode) or starts it locally. The driver registers with the cluster manager and requests executors. The manager launches them and they register back with the driver. Your code then runs on the driver. Transformations just build a logical plan. When an action is called, the driver optimises the plan, turns it into a physical plan, and the DAG scheduler cuts it into stages at shuffle boundaries. For each stage the task scheduler creates one task per partition, prefers executors that already hold the data (data locality), and sends the tasks. Executors run them, write shuffle output or return results, and report back. When the last stage is done the action returns. If a task fails it is retried (default 4 attempts). When the program ends, the driver tells the manager to release the executors.

Likely follow-ups
  • What is data locality? Running a task on the node that already has its input block, to avoid moving data. Levels: process local, node local, rack local, any.

2. RDD, DataFrame, Dataset and lazy evaluation

RDD vs DataFrame vs Dataset: what is the difference and which do you use? Basic

What the interviewer is testing: the most common Spark question. They want trade-offs, not definitions.

An RDD (Resilient Distributed Dataset) is a distributed collection of plain objects with functions you write. Spark knows nothing about what is inside, so it cannot optimise and it must serialise whole Java objects. A DataFrame is a distributed table: rows with named, typed columns. Spark knows the schema, so Catalyst can optimise the plan and Tungsten can store data in a compact binary format. A Dataset is a DataFrame with compile-time types: Dataset[Person] in Scala or Java. In fact, in Scala DataFrame is simply Dataset[Row]. In Python and R only DataFrames exist, since there are no compile-time types. For almost all work I use DataFrames or Spark SQL, because they are fastest. I use a typed Dataset when I want compile-time safety and my logic is complex in Scala or Java. I drop to RDDs only for unstructured data, custom partitioning, or low-level control.

Likely follow-ups
  • Why can a typed lambda like ds.filter(p => p.age > 18) be slower than df.filter("age > 18")? The lambda is a black box: Catalyst cannot push it down to Parquet, and each row must be turned into an object first.
  • Is the RDD API deprecated? No, but it is rarely the right tool; the DataFrame API is the main one.
Common mistakes: saying "Datasets are always better because they are typed". Typed lambdas give up optimisation.
What is lazy evaluation and why does Spark use it? Basic

What the interviewer is testing: whether you can predict when code actually runs.

Lazy means that transformations such as filter, select, join and withColumn do not process any data. They only record what to do, building a plan. Work starts when you call an action such as count, show, collect or write. The benefit is that Spark sees the whole plan before running. It can drop unused columns, push filters down to the file scan, merge steps into one pass, and pick join strategies. For example, if you read a 1 TB table, filter on one day and then take 10 rows, Spark can read only the needed files. The surprise for beginners is that a bug in a transformation (for example a bad column name) may only show when an action runs, and that the same plan re-runs from scratch for every action unless you cache it.

val df = spark.read.parquet("/data/events")   // nothing read yet (only schema)
val x  = df.filter($"day" === "2026-11-16")   // still nothing
x.count()                                      // job 1 runs now
x.write.parquet("/out/x")                      // job 2: recomputes from scratch
Likely follow-ups
  • Does spark.read do any work? It may run a small job to list files and read the schema (and infer schema from CSV or JSON, which scans data).
  • Is an invalid column name caught early? DataFrame analysis checks names when you build the step, but data-dependent errors only appear at run time.
Transformations vs actions: give examples and say which triggers a job. Basic

What the interviewer is testing: basic fluency.

A transformation returns a new DataFrame or RDD and is lazy. Examples: select, filter, withColumn, groupBy().agg(), join, union, distinct, repartition, orderBy. An action returns a value to the driver or writes output, and starts a job. Examples: count, collect, take, first, show, reduce, foreach and write (save, saveAsTable). A few calls blur the line: sort and orderBy are transformations but need a quick sampling job to find range boundaries; cache is lazy; checkpoint is eager by default. The number of jobs in the UI equals the number of actions (plus these small helper jobs).

Likely follow-ups
  • Is groupBy alone an action? No. It returns grouped data; the aggregation (agg, count) is still a transformation on DataFrames.
What does "Resilient Distributed Dataset" really mean? What are the five properties of an RDD? Intermediate

What the interviewer is testing: foundations behind lineage and scheduling.

Distributed: the data is split into partitions on different machines. Resilient: a lost partition can be rebuilt from its lineage. Dataset: a collection you can operate on. Internally an RDD is described by five things: a list of partitions; a function to compute each partition; a list of dependencies on parent RDDs; optionally a partitioner (for key-value RDDs, how keys map to partitions); and optionally preferred locations for each partition (for data locality). The scheduler uses dependencies to find stage boundaries, and the compute function and partitions to create tasks. RDDs are immutable: every transformation makes a new one.

Likely follow-ups
  • Why immutable? It makes lineage and recomputation safe, and removes the need for locking.
How do you define a schema when reading data, and why not just use inferSchema? Intermediate

What the interviewer is testing: production habits for CSV and JSON.

For CSV and JSON, inferSchema reads the data (CSV fully by default, JSON with a scan) to guess types. That costs an extra pass over the input, and the guess can change from day to day: a column that was always integer might suddenly contain a word, or the first file may have only nulls. This breaks downstream jobs silently. In production I give an explicit schema, either a StructType or a DDL string. Parquet and ORC carry their schema in the file, so no inference is needed, but different files in one folder can disagree, and then you may need mergeSchema or a table format that manages schema evolution. A set read mode helps with bad rows: PERMISSIVE (default, bad fields become null), DROPMALFORMED, or FAILFAST.

val schema = "id BIGINT, name STRING, amount DECIMAL(12,2), ts TIMESTAMP"
val df = spark.read.schema(schema)
  .option("header", "true").option("mode", "FAILFAST")
  .csv("s3://bucket/raw/orders/")
Likely follow-ups
  • How do you capture bad records? Option columnNameOfCorruptRecord in permissive mode, or badRecordsPath on some platforms.
Why is collect() dangerous, and what do you use instead? Basic

What the interviewer is testing: awareness that the driver is a small, single machine.

collect() pulls every row of the result from all executors into the driver's memory as one local array. If the data is large, the driver runs out of memory (OutOfMemoryError) or hits spark.driver.maxResultSize (default 1 GB) and the whole job dies, even if the cluster has hundreds of gigabytes free. Use instead: show(n) or take(n) or limit(n) to look at a sample; write to save results to storage; agg to reduce first and then collect the small answer; and foreachPartition or a write to send data to an external system from the executors. toPandas() has the same problem, so apply it only to small aggregated results (and enable Arrow to make it faster).

Likely follow-ups
  • Is limit(10) followed by collect safe? Yes, for the row count. But wide rows or large strings can still be big.
  • Alternative to iterate on the driver without all data at once? toLocalIterator() pulls one partition at a time.
What are broadcast variables and accumulators? Intermediate

What the interviewer is testing: shared variables and their limits.

Normally, a variable captured in a closure is copied into every task. If it is big (say a 200 MB lookup map), it is sent again for every task. A broadcast variable sends a read-only value to each executor once, and tasks on that executor share it. Use it for lookup tables and models. An accumulator is a variable that tasks can only add to, and the driver can read. It is used for counters, such as the number of bad rows. The catch: Spark guarantees an accumulator updated inside an action is counted once per task, but inside a transformation it may be counted more than once, because tasks can be retried or a stage recomputed. So treat transformation accumulators as approximate metrics, never as business logic.

val lookup = spark.sparkContext.broadcast(countryMap)   // Map[String,String]
val bad = spark.sparkContext.longAccumulator("badRows")
df.foreach { r => if (r.isNullAt(0)) bad.add(1) }       // action: counted once
println(bad.value)
Likely follow-ups
  • How is a broadcast join related? The small table is broadcast the same way, so no shuffle is needed.

3. DAG, stages, shuffle and partitioning

What are narrow and wide dependencies? Basic

What the interviewer is testing: the concept that decides stage boundaries and cost.

A narrow dependency means each output partition depends on only one (or a few fixed) input partitions. map, filter, select, union and coalesce are narrow. Spark can run a chain of them in one pass inside one task, with no data movement. A wide dependency (shuffle dependency) means an output partition needs data from many input partitions. groupByKey, reduceByKey, join (unless broadcast or both sides co-partitioned), distinct, repartition and orderBy are wide. The rows must be redistributed so rows with the same key land together. Wide dependencies create stage boundaries, and failure recovery is also more expensive for them, because a lost output partition needs data from many parents.

Likely follow-ups
  • Is coalesce narrow? Yes, it merges neighbouring partitions without a shuffle (unless you ask for shuffle).
  • Is join always wide? No. A broadcast join, or a join of two inputs already partitioned the same way, has narrow dependencies.
Explain job, stage and task, and how Spark decides the number of each. Basic

What the interviewer is testing: reading the Spark UI with understanding.

Each action creates one job. Spark walks back through the plan and cuts it into stages at every wide dependency (shuffle). Inside a stage all steps are narrow, so they are pipelined: a record flows through read, filter and map without being stored between steps. A stage runs as a set of tasks, one per partition, and all tasks in a stage run the same code on different data. A stage can only start when its parent stages have finished writing shuffle files. So number of stages is about the number of shuffles plus one; number of tasks in a stage is the number of partitions of its input (for the first stage, how many input splits; for later stages, spark.sql.shuffle.partitions unless AQE merged them). The task is the smallest unit that gets retried.

Likely follow-ups
  • Why does my job have a "skipped stage" in the UI? Its shuffle output already exists from an earlier job, so Spark reused it.
  • How many tasks run at once? Total executor cores divided by spark.task.cpus (default 1).
What is a shuffle and why is it the expensive part of Spark? Intermediate

What the interviewer is testing: the single most important performance concept.

A shuffle redistributes data across partitions so rows with the same key end up together. It works in two sides. In the map side, each task of the earlier stage decides, for every row, which output partition it belongs to (by hashing the key), and writes its rows into a shuffle file on local disk, sorted or grouped by target partition. In the reduce side, each task of the next stage fetches its slice from every map task's file over the network and merges them. It is expensive for four reasons: disk write, network transfer, serialisation and deserialisation of every row, and a barrier (the next stage waits for all map tasks). It also creates M times R small fetches (M map tasks, R reduce tasks), and it is where data skew, spills and out-of-memory errors show up. The best tuning is to avoid it (broadcast joins, filter early), shrink it (select only needed columns, partial aggregation) and balance it.

Likely follow-ups
  • What shuffle manager is used? The sort-based shuffle (the only one since 2.0). Each map task writes one data file plus an index file.
  • What is the external shuffle service? A process per node that serves shuffle files, so executors can be removed (dynamic allocation) without losing shuffle data.
Which operations cause a shuffle, and how can you avoid or reduce them? Intermediate

What the interviewer is testing: practical performance habits.

Shuffle causes: groupBy/groupByKey/reduceByKey, join and cogroup (except broadcast), distinct, repartition, orderBy/sort, window functions with partitionBy, and intersect/except. Ways to cut the cost: filter and select columns before the shuffle so fewer bytes move; use a broadcast join when one side is small; use aggregations that combine on the map side first (reduceByKey, or DataFrame agg, which do partial aggregation) instead of groupByKey which ships every value; reuse an already partitioned table (bucketed tables avoid the shuffle of a join); do one shuffle instead of several by chaining operations on the same key; and avoid distinct plus groupBy on the same key back to back. For stability, set a sensible partition count so each reduce task handles about 100 to 200 MB.

Likely follow-ups
  • How do I see shuffles in the plan? df.explain() shows Exchange nodes. Each is a shuffle (or a broadcast).
Why is reduceByKey preferred over groupByKey in the RDD API? Intermediate

What the interviewer is testing: map-side combine, a classic question.

groupByKey sends every single (key, value) pair across the network and builds, per key, a full collection of values in memory. If one key has millions of values, that single collection can run a task out of memory. reduceByKey takes a combine function and first applies it inside each map partition, so each map task sends at most one record per key. The reduce side then combines those partial results. This is the same idea as a Hadoop combiner. A word count over a billion words ships one count per word per partition instead of a billion pairs. The same effect exists in DataFrames: groupBy().agg(sum(...)) does partial aggregation automatically, so with DataFrames the question rarely arises. Use groupByKey only when you truly need all values together (and they fit in memory), and consider aggregateByKey or combineByKey when the result type differs from the value type.

Likely follow-ups
  • Does the combine function need special properties? It must be associative and commutative, because partial results are combined in any order.
What are partitions, and how many should you have? Intermediate

What the interviewer is testing: can you size parallelism sensibly.

A partition is a chunk of the data that one task processes. For file input, Spark creates partitions of about spark.sql.files.maxPartitionBytes (128 MB by default), so a 10 GB Parquet folder gives roughly 80 input partitions. After a shuffle, the count is spark.sql.shuffle.partitions (default 200), unless AQE coalesces them. Too few partitions: not enough parallelism, idle cores, and very big tasks that spill or run out of memory. Too many: tiny tasks where scheduling overhead dominates, many small output files, and a heavy driver. A common rule of thumb is two to four partitions per core in the cluster, with each partition around 100 to 200 MB after the shuffle. The 200 default is wrong for both small jobs (200 tiny tasks) and large ones (a 1 TB shuffle with 200 partitions gives 5 GB per task and spills). With AQE (Spark 3.x), set the number high and let it coalesce small ones.

df.rdd.getNumPartitions
spark.conf.set("spark.sql.shuffle.partitions", "800")
spark.conf.set("spark.sql.adaptive.enabled", "true")          // default true since 3.2
Likely follow-ups
  • How do I find partition sizes? The stage page in the Spark UI shows task input/shuffle read size and its min, median and max.
repartition vs coalesce: what is the difference and when do you use each? Basic

What the interviewer is testing: shuffle awareness in a very common call.

repartition(n) does a full shuffle and produces n evenly sized partitions (round-robin, or hash if you give columns). You can increase or decrease the count, and it fixes skew in the layout. coalesce(n) only decreases the count by merging neighbouring partitions inside the same executor, without a shuffle. It is cheap, but the result can be uneven, because it just glues partitions together. Use coalesce before writing to reduce the number of output files, when the data is already reasonably balanced. Use repartition when you need more partitions, even sizes, or to partition by a column (for example repartition($"customer_id") before a join or write). A subtle trap: coalesce(1) on a big dataset pulls the whole upstream computation into a single task, which makes the earlier steps run with one core. Use repartition(1) there so only the final step is single.

Likely follow-ups
  • Does AQE change this? It can coalesce shuffle partitions automatically, but not your explicit repartition(n) output count on the final write unless you use REBALANCE hints.
  • What is repartitionByRange? Partitions by sampled value ranges, so output is sorted across partitions. Useful for range queries.
How are rows assigned to partitions, and what is a partitioner? Intermediate

What the interviewer is testing: knowing why same keys meet, and how to exploit it.

For a key-value shuffle, the default HashPartitioner computes hash(key) mod numPartitions. So all rows with the same key go to the same partition, which is what makes joins and aggregations correct. RangePartitioner samples the data to pick ranges and is used by sortBy/orderBy, so partition 0 holds the smallest keys and so on. If an RDD already has a known partitioner and a later operation uses the same one, Spark can skip the shuffle: for example, two RDDs partitioned by the same hash into the same count can be joined with narrow dependencies. Operations such as map drop the partitioner (Spark cannot know you kept the key) while mapValues and filter keep it. In DataFrames the equivalent is reading bucketed tables, or using repartition($"key") on both sides before a join, though AQE and the optimizer already handle most cases.

Likely follow-ups
  • What is a custom partitioner for? Fixing skew with a known hot key, or placing related data together for a downstream step.
What is data skew and how do you detect and fix it? Senior

What the interviewer is testing: the most common real production slowness. They want a method, not one trick.

Skew means the data is unevenly spread over partitions after a shuffle: a few keys (a null, a default value like "unknown", one huge customer) have far more rows than others. The task that gets that key holds most of the data. All other tasks finish in seconds, and one runs for an hour, and may spill or run out of memory. Detect: in the Spark UI stage page, compare the max task duration and shuffle-read size against the median. A big gap is skew. Also run groupBy(key).count().orderBy(desc) to see hot keys. Fix, in order of effort: (1) turn on AQE skew join handling (Spark 3.x), which splits oversized partitions automatically for sort-merge joins; (2) filter or handle nulls and default keys separately, as they are often junk; (3) broadcast the small side so no shuffle is needed; (4) salting: add a random suffix to the hot key on the big side and replicate the other side across all suffixes; (5) pre-aggregate before the join to shrink the hot key; (6) isolate the hot keys: process them with a broadcast join and the rest normally, then union.

Likely follow-ups
  • Why does a null key cause skew? Nulls hash to one partition, and in an inner join they would not match anyway, so filter them first.
  • Does salting work for aggregations? Yes: aggregate by (key, salt) first, then aggregate by key again (two-phase aggregation).
Show how salting a skewed join works. Senior

What the interviewer is testing: can you actually write the fix.

The big table has a hot key, say customer 42 with 100 million rows. In the big table, add a random number from 0 to N-1 to each row (the salt) and join on (key, salt). In the small table, copy each row N times, once for each salt value. Now customer 42's rows are spread over N different join keys, so they go to N different partitions, and every one still finds its matching rows in the other side. The cost is that the other side grows N times for the replicated rows, so only replicate the hot keys if you can, and pick N by how large the hot key is (often 10 to 50). In Spark 3.x with AQE the skew-join feature does a similar thing automatically for sort-merge joins, so use salting when AQE cannot (for example for aggregations, or joins types that AQE does not split, such as the preserved side of an outer join).

val N = 16
val bigS   = big.withColumn("salt", (rand() * N).cast("int"))
val smallS = small.withColumn("salt", explode(array((0 until N).map(lit): _*)))
val joined = bigS.join(smallS, Seq("customer_id", "salt")).drop("salt")
Likely follow-ups
  • Is it safe if the job is retried? rand() is seeded per partition, so results are deterministic for the same partitioning, but to be safe derive salt from another column (like hash(order_id) % N).
Common mistakes: salting both sides randomly (rows no longer match); forgetting to drop the salt column; replicating the whole small table for every key, not only for hot keys.
What happens if a task, an executor or a whole stage fails? Intermediate

What the interviewer is testing: failure model and retry settings.

If one task fails (an exception, a lost connection), the scheduler retries it, up to spark.task.maxFailures times (default 4; 1 in local mode). If it fails that many times, the stage and the job fail. If an executor dies (for example killed by YARN for using too much memory), its running tasks are re-run elsewhere, and any shuffle files stored there are lost. Reducers that need them get a FetchFailed error, and Spark re-runs the earlier map stage for the missing partitions, and then the reduce stage. A stage can be retried a few times (spark.stage.maxConsecutiveAttempts, default 4). If the driver dies, the application is lost, unless the cluster manager restarts it, and for streaming it resumes from a checkpoint. A straggler (a slow task) can be duplicated using speculative execution (spark.speculation), where the first copy to finish wins.

Likely follow-ups
  • Why can retries cause duplicates in the output? A task may write part of its output, fail, and write again. The commit protocol handles files, but external side effects (an API call, a database insert) are not rolled back.
What is Adaptive Query Execution (AQE) and what three things does it do? Intermediate

What the interviewer is testing: modern Spark 3 knowledge.

Normally the plan is fixed before the job runs, using estimates that are often wrong. AQE (Spark 3.0, on by default from 3.2) re-plans while running, after each shuffle stage finishes, using the real sizes of the shuffle output. It does three main things. (1) Coalesces shuffle partitions: if many partitions after a shuffle are tiny, it merges them into fewer, aiming at spark.sql.adaptive.advisoryPartitionSizeInBytes (64 MB). So you can set a high partition count and not worry. (2) Switches join strategy: if one side turns out smaller than the broadcast threshold after filters, it changes a sort-merge join into a broadcast join. (3) Handles skew joins: it splits a partition that is much bigger than the median (skewedPartitionFactor 5 times the median and above skewedPartitionThresholdInBytes 256 MB) into sub-partitions and duplicates the other side's matching partition. In Spark 3.2 and later it can also optimise skewed shuffles and use local shuffle reads. It works only for queries with a shuffle or subquery, and it does not help RDD code.

Likely follow-ups
  • How do I see it? The SQL tab shows AdaptiveSparkPlan with "isFinalPlan=true" after the run.
  • Does AQE remove the need for tuning? It reduces it, but it cannot fix a huge skew on an aggregation or a bad data layout.

4. Joins

What join strategies does Spark have, and how does it choose? Intermediate

What the interviewer is testing: the key performance topic for SQL and ETL work.

Spark has five physical join strategies. Broadcast hash join: copy the small table to every executor, build a hash map, and stream the big table through it. No shuffle of the big table, so it is the fastest. It is chosen automatically if one side is under spark.sql.autoBroadcastJoinThreshold (10 MB default). Shuffle hash join: shuffle both sides by the join key, then build a hash table of the smaller side in each partition. Used when one side is much smaller but too big to broadcast, and it needs memory for the hash table. Sort-merge join: shuffle both sides by key, sort each partition, and merge. It is the default for two large tables because it can spill to disk and scales well. Broadcast nested loop join and cartesian product join are the slow fallbacks for non-equality conditions (like a.x < b.y) and for cross joins. You can force a choice with hints: broadcast(df), or SQL /*+ BROADCAST(t) */, SHUFFLE_HASH, MERGE.

Likely follow-ups
  • Which tables can be broadcast in an outer join? Only the non-preserved side: the right side of a left outer join, for example.
  • Why is the 10 MB default so small? The broadcast goes through the driver and is copied to every executor, so big ones risk memory trouble.
How does a broadcast join work, and what can go wrong with it? Intermediate

What the interviewer is testing: understanding of where memory goes.

Spark collects the small table to the driver, builds it into a compact hash relation, and broadcasts it to every executor over a torrent-like protocol. Each executor then joins its partitions of the big table locally. Nothing from the big table moves. What can go wrong: the table is bigger than you thought (the on-disk size of compressed Parquet can be 5 to 10 times smaller than in memory), so the driver or the executors run out of memory; the broadcast takes longer than spark.sql.broadcastTimeout (300 s) because the small side is itself a slow subquery; or the statistics are wrong, so Spark does not broadcast when it could. Fixes: use the broadcast() hint only when you know the size, filter and project the small table first, and check the plan with explain for BroadcastExchange and BroadcastHashJoin. AQE can also convert to broadcast at run time using real sizes.

import org.apache.spark.sql.functions.broadcast
val out = orders.join(broadcast(countries), Seq("country_code"), "left")
out.explain()   // look for BroadcastHashJoin
Likely follow-ups
  • What is the hard limit? A broadcast relation cannot exceed about 8 GB, and 2 GB in older versions; practically keep it far below that.
How does a sort-merge join work, and why is it the default for big tables? Intermediate

What the interviewer is testing: deeper join knowledge.

Both inputs are shuffled so that rows with equal join keys land in the same partition number. Then each partition on each side is sorted by the key. A task walks through both sorted streams together, like merging two sorted lists, and emits matching rows. It only needs to hold a few rows in memory at a time, and the sort can spill to disk, so it never fails on memory the way a hash join can. That is why it is the default for two large tables. The costs are two shuffles (one per side) and two sorts. If both tables are already bucketed and sorted by the join key with the same number of buckets, Spark can skip the shuffle and sort entirely, which is the main reason to bucket frequently joined tables. The join is also sensitive to skew: all rows of one key must meet in one task.

Likely follow-ups
  • When is shuffle hash join better? When one side is a lot smaller than the other, since it avoids sorting the large side. It must fit in memory per partition.
How do you join a huge table with a small one efficiently? Basic

What the interviewer is testing: the standard answer is broadcast, but the reasoning matters.

Use a broadcast join. The small table is sent to every executor, and each task joins its slice of the big table locally, so the big table is never shuffled. First reduce the small table as much as possible: select only the columns you need and filter rows. Check that Spark chose it (explain shows BroadcastHashJoin). If the table is a bit over the 10 MB threshold, raise spark.sql.autoBroadcastJoinThreshold (for example to 100 MB) or use the broadcast() hint. If it is too large to broadcast safely, the next option is a shuffle hash join with a hint, and for two big tables a sort-merge join. Also remember that broadcast does not work when the small side is the preserved side of an outer join.

What are common join mistakes that give wrong results or blow up the data? Intermediate

What the interviewer is testing: correctness, not only speed.

First, duplicate keys: if the key is not unique in both tables, rows multiply (many-to-many). A join that should return one million rows can return one billion. Always check key uniqueness with a count. Second, null keys: in SQL, null never equals null, so rows with null keys are dropped in an inner join; use the null-safe operator <=> (eqNullSafe) when you want them to match. Third, ambiguous columns: joining on a condition expression leaves two columns with the same name; join on Seq("id") to get one. Fourth, filtering after an outer join in the WHERE clause turns it into an inner join; put the right-side filters in the ON condition. Fifth, accidental cartesian product when the condition is missing or always true; Since Spark 3.0 implicit cartesian products are allowed by default (spark.sql.crossJoin.enabled is true), so Spark will not stop you; check the plan for CartesianProduct. Use left_semi and left_anti joins for "exists" and "not exists" checks, since they do not multiply rows.

Likely follow-ups
  • Difference between left semi and inner join? A semi join returns only left columns and each left row at most once.
What is bucketing, and how is it different from partitioning? Senior

What the interviewer is testing: physical data layout trade-offs.

Partitioning (partitionBy("date")) splits a table into folders by column value. It helps queries that filter on that column skip whole folders (partition pruning). It works for columns with a low number of distinct values. Bucketing (bucketBy(64, "user_id")) hashes a column into a fixed number of files. It helps with joins and aggregations on that column: if two tables are bucketed on the join key with the same bucket count, Spark can join them without any shuffle. You can combine them. Downsides of bucketing: it needs a table in the metastore (saveAsTable), every writer must respect the bucket spec, it can create many small files (buckets times write tasks), and the file layout is Hive-hash compatible only in some paths. Modern table formats such as Iceberg and Delta offer other layout features (hidden partitioning, Z-ordering, clustering) which many teams now use instead.

df.write.bucketBy(64, "user_id").sortBy("user_id").saveAsTable("events_b")

5. Catalyst, Tungsten, serialization, UDFs, windows and SQL

What is the Catalyst optimizer? Walk me through the phases. Intermediate

What the interviewer is testing: knowing why DataFrame code is fast, and how to read explain.

Catalyst is the rule-based query optimiser inside Spark SQL. Your DataFrame code or SQL goes through four steps. (1) Parse to an unresolved logical plan: names are only text. (2) Analysis: look up tables, columns and types in the catalog, giving a resolved logical plan (this is where "column not found" errors come from). (3) Logical optimisation: rules rewrite the plan to something equivalent but cheaper, such as predicate pushdown (filter earlier, into the file scan), column pruning (read only needed columns), constant folding, combining filters and projections, and join reordering. (4) Physical planning: generate candidate physical plans (for example, which join strategy), choose one using a cost model, then generate Java code for it (whole-stage code generation, from Tungsten). In Spark 3, AQE adds a fifth, run-time re-optimisation. Use df.explain("formatted") or explain(true) to see all the plans.

Likely follow-ups
  • What is predicate pushdown? Passing the filter to the data source (for example Parquet row-group statistics) so unneeded data is never read.
  • Does the order of my filter and join matter? Usually not for DataFrames, because Catalyst reorders. It does matter around opaque UDFs.
How do you read an explain plan to find a performance problem? Senior

What the interviewer is testing: practical debugging with the plan.

Read it from the bottom up: the bottom is the scan, the top is the final result. I look for four things. (1) The scan node: does it show PushedFilters, PartitionFilters and only the columns I need (ReadSchema)? If a partition filter is missing, I am reading the whole table, often because I wrapped the partition column in a function. (2) Exchange nodes: each is a shuffle or broadcast. Count them and ask whether each is necessary. (3) The join type: SortMergeJoin where I expected a broadcast means size statistics are missing or too large. (4) Opaque nodes such as BatchEvalPython or ArrowEvalPython (Python UDF) or a MapElements (typed lambda), which break whole-stage code generation (nodes marked with a star * are generated; no star means interpreted). The SQL tab of the UI shows the same plan with real row counts and times per node, which is the best way to see where time goes.

df.explain("formatted")     // Spark 3.0 and later: readable, numbered nodes
spark.sql("EXPLAIN COST SELECT ...")   // adds statistics
What is Tungsten, and what is whole-stage code generation? Senior

What the interviewer is testing: engine internals that explain DataFrame speed.

Tungsten (Spark 1.5 to 2.0) is a set of low-level engine improvements. First, off-heap or compact binary row storage: rows are kept as raw bytes in a format called UnsafeRow, instead of Java objects. This avoids object headers and pointer chasing and cuts garbage collection a lot. Second, cache-friendly algorithms for sorting and hashing that work on the binary data. Third, whole-stage code generation: instead of each operator calling the next one for every row (virtual function calls, "Volcano" model), Spark generates one Java method for a whole chain of operators (scan, filter, project, aggregate) that works like a hand-written tight loop, keeping values in CPU registers. This can give several times speedup on CPU-bound parts. It is why the plan marks fused operators with a star. It also explains why Python UDFs and typed lambdas are slow: they break the generated code and force conversion to objects. Newer vectorised readers (Parquet, ORC) and columnar execution continue the same line of work.

Likely follow-ups
  • Does Tungsten use off-heap memory? Optionally (spark.memory.offHeap.enabled), but the binary format also works on-heap.
Java serialization vs Kryo: what do you use and why does it matter? Intermediate

What the interviewer is testing: shuffle and cache cost awareness for RDD code.

Serialization turns objects into bytes to send them over the network (shuffle, broadcast, task closures) or to store them serialised in cache. Spark's default for RDD data is Java serialization, which is flexible but slow and produces large output. Kryo is a faster and more compact library (often 2 to 10 times smaller) and is recommended for RDD jobs: set spark.serializer=org.apache.spark.serializer.KryoSerializer and register your classes (spark.kryo.registrationRequired=true to catch missing ones). For DataFrames and Datasets, row data uses Tungsten's own binary encoders, so Kryo matters little for the data itself, but it still helps for closures and shuffle of custom objects. A related, common error is Task not serializable: the function you pass to a transformation references something that cannot be serialised (a database connection, a logger, or the enclosing class). Fix it by creating such objects inside mapPartitions (once per partition), or by making them transient lazy, or by moving the code to a standalone object.

rdd.mapPartitions { it =>
  val conn = Db.connect()          // created on the executor, per partition
  try it.map(r => lookup(conn, r)).toList.iterator finally conn.close()
}
Likely follow-ups
  • Why does the whole enclosing class get serialised? In Scala and Java a lambda that uses a field of the class captures this. Copy the field into a local variable first.
Why are UDFs slow, and what do you do instead? Intermediate

What the interviewer is testing: preferring built-ins and knowing the cost of leaving the optimizer.

A user-defined function is a black box to Catalyst. It cannot push filters through it, reorder it, or generate code for it. Also, each row must be converted from Spark's binary format into JVM objects (and back). A plain Python UDF is worse: rows are serialised, sent to a separate Python worker process, computed one row at a time, and sent back. That can be 10 to 100 times slower than the equivalent built-in. So the order of preference is: (1) a built-in function from org.apache.spark.sql.functions or SQL (there are hundreds, including when, regexp_extract, transform, aggregate for arrays); (2) a Spark SQL expression composed of built-ins; (3) a pandas UDF (vectorised, uses Arrow); (4) a Scala/Java UDF (stays in the JVM, but still opaque); (5) a plain Python UDF as the last choice. Null handling is another trap: your UDF must handle nulls itself.

// slow: opaque to Catalyst
val up = udf((s: String) => if (s == null) null else s.trim.toUpperCase)
df.withColumn("n", up($"name"))
// better: built-ins, optimisable
df.withColumn("n", upper(trim($"name")))
Likely follow-ups
  • Can I make a UDF non-deterministic? By default it is assumed deterministic and may run more than once or be reordered. Mark with asNondeterministic() if it is not.
What is a pandas UDF and why is it faster than a normal Python UDF? Intermediate

What the interviewer is testing: PySpark performance knowledge.

A pandas UDF (also called a vectorised UDF, Spark 2.3+) receives a whole batch of values as a pandas.Series (or DataFrame), not one row at a time. Data is moved between the JVM and the Python worker using Apache Arrow, a columnar in-memory format, so there is no per-row pickling. Python then uses vectorised pandas or NumPy operations on the batch. It is typically several times to tens of times faster than a row UDF. Variants: scalar (Series to Series), grouped map via groupBy().applyInPandas() (a whole group becomes a pandas DataFrame), mapInPandas and mapInArrow (iterator over batches) and grouped aggregate. Limits: still a black box to Catalyst, still a separate process, and a group handed to applyInPandas must fit in worker memory, so skewed groups can crash. Batch size is controlled by spark.sql.execution.arrow.maxRecordsPerBatch (default 10000).

import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf("double")
def to_celsius(f: pd.Series) -> pd.Series:
    return (f - 32) * 5.0 / 9.0

df.withColumn("c", to_celsius("temp_f"))
Likely follow-ups
  • Other uses of Arrow? spark.sql.execution.arrow.pyspark.enabled speeds toPandas() and createDataFrame(pandas_df).
How do window functions work in Spark, and what do they cost? Intermediate

What the interviewer is testing: a very common coding question, plus its performance side.

A window function computes a value for each row using a set of related rows, without collapsing them like groupBy. You define a window with partitionBy (which rows are related), orderBy (their order) and optionally a frame such as rowsBetween or rangeBetween. Then apply a ranking function (row_number, rank, dense_rank), an analytic one (lag, lead, first), or an aggregate (sum, avg) over it. Cost: Spark must shuffle so each partition-key group is in one task, then sort inside each group. A window with no partitionBy sends all data to one task, with a warning in the log. A very large group (skew) is processed by a single task. Typical use: "latest record per key" or "top N per group".

val w = Window.partitionBy("customer_id").orderBy($"updated_at".desc)
val latest = df.withColumn("rn", row_number().over(w)).filter($"rn" === 1).drop("rn")
val running = df.withColumn("total", sum("amount").over(
  Window.partitionBy("customer_id").orderBy("ts").rowsBetween(Window.unboundedPreceding, Window.currentRow)))
Likely follow-ups
  • rank vs dense_rank vs row_number? row_number is always unique; rank leaves gaps after ties; dense_rank has no gaps.
  • Cheaper way to get "latest per key"? groupBy(key).agg(max(struct(ts, cols...))) avoids a sort.
How do SQL and the DataFrame API relate, and what are temp views and the catalog? Basic

What the interviewer is testing: that SQL and DataFrame code are the same engine.

SQL and DataFrame code compile to the same logical plan and use the same optimiser, so there is no speed difference. Pick whichever is clearer: SQL for big queries and analysts, the DataFrame API for programmatic building and unit testing. To mix them, register a DataFrame as a temporary view with createOrReplaceTempView("t"), which lives only within the session, and query it with spark.sql. A global temp view is shared across sessions of the same application. The catalog holds the table metadata: with Hive support it is the Hive metastore, so tables persist and are shared. Tables can be managed (Spark owns the data; dropping the table deletes files) or external (you give a location; dropping removes only metadata). Table formats like Delta and Iceberg add their own catalogs and ACID behaviour.

df.createOrReplaceTempView("orders")
spark.sql("SELECT country, SUM(amount) FROM orders GROUP BY country").show()
Likely follow-ups
  • What does ANSI mode change (default on in Spark 4)? Invalid casts and arithmetic overflow raise errors instead of returning null or wrapping, which catches bad data earlier.
What are the common surprises with nulls, casts and dates in Spark SQL? Intermediate

What the interviewer is testing: data correctness habits.

Null compared with anything is null (not true), so WHERE x != 5 silently drops rows where x is null. Use IS NULL, coalesce or the null-safe equality. A failed cast in Spark 3.x without ANSI mode returns null, not an error, so a bad number string becomes null and your totals quietly shrink. In Spark 4 (ANSI default) the same cast fails the query, and try_cast gives the old lenient behaviour. Integer overflow also wraps around silently in non-ANSI mode. Timestamps have a session time zone (spark.sql.session.timeZone): a TIMESTAMP is an instant, displayed in that zone, so the same data shows different clock times on different clusters unless you set it. Parsing a date with the wrong pattern returns null, and Spark 3 changed the date pattern parser (Java DateTimeFormatter) which broke some older patterns. Always set the zone and test boundary rows.

6. Reading and writing data

Why is Parquet the usual choice, and how does Spark benefit from it? Basic

What the interviewer is testing: file format fundamentals.

Parquet is a columnar format: values of one column are stored together, not row by row. For analytics, queries usually touch a few columns out of many, so Spark reads only those (column pruning) and skips the rest. Same-type values together compress very well (dictionary and run-length encoding, plus Snappy or Zstd). Each file is split into row groups, and each row group stores min and max statistics per column, so Spark can skip whole groups that cannot match a filter (predicate pushdown). The schema is stored in the file, so no inference is needed. Compare: CSV and JSON are text, row-based, with no schema or types, so they are big and slow; Avro is row-based and good for streaming and record-level writes; ORC is columnar like Parquet and common in Hive shops. Parquet is weak for frequent small updates, since files are immutable; that is the job of Delta, Iceberg or Hudi on top.

Likely follow-ups
  • Why does filtering on a high-cardinality column often not skip anything? Min and max cover wide ranges unless the data is sorted by that column.
How does partitionBy work when writing, and what are the pitfalls? Intermediate

What the interviewer is testing: layout decisions and the small-files problem.

df.write.partitionBy("date", "country") creates folders like date=2026-11-16/country=IN/part-0001.parquet. A later query that filters on date and country reads only matching folders (partition pruning). The pitfalls: (1) too many distinct values (for example partitioning by user id) gives millions of tiny folders and files, which slows listing and reading. Choose a column with low cardinality that queries filter on, usually a date. (2) Each write task writes a file for every partition value it holds, so 200 tasks times 365 dates can give 73,000 files. Fix by repartitioning by the same columns before the write so each partition value comes from few tasks. (3) Overwrite behaviour: by default, mode("overwrite") with partitionBy deletes the whole table path. Set spark.sql.sources.partitionOverwriteMode=dynamic to replace only the partitions present in the new data. (4) The partition column is stored in the folder name, not in the files.

spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")
df.repartition($"date")                 // one task per date, fewer files
  .write.mode("overwrite").partitionBy("date").parquet("s3://b/events/")
Likely follow-ups
  • Why can a filter like WHERE to_date(ts) = ... skip pruning? The filter is not on the partition column itself, so Spark cannot map it to folders. Filter on date directly.
What is the small files problem, and how do you prevent and fix it? Intermediate

What the interviewer is testing: a classic production problem with clear fixes.

Thousands of tiny files (a few KB to a few MB) hurt in many ways. Listing them is slow (especially on S3), each file becomes a read task with fixed overhead, the HDFS NameNode keeps metadata for each, and Parquet metadata and compression work worse on small files. They come from: too many shuffle partitions at write time, partitionBy with many values, frequent streaming micro-batches writing a file each time, and incremental appends. Prevent by controlling the number of output files: coalesce(n) or repartition(n) before write, repartition by the partition column, maxRecordsPerFile, and AQE (which coalesces shuffle output). For SQL, the hint /*+ REBALANCE */ (Spark 3.2+) balances output sizes. Fix existing data by a compaction job: read the folder and rewrite it into files of about 128 to 512 MB. Table formats provide this natively (Delta OPTIMIZE, Iceberg rewrite_data_files). For reading, Spark can pack small files into one task, controlled by spark.sql.files.maxPartitionBytes and openCostInBytes.

What are the save modes, and is a Spark write atomic? Intermediate

What the interviewer is testing: safe output handling and rerun behaviour.

The modes are append (add files), overwrite (replace the path or the matching partitions), ignore (do nothing if data exists) and errorifexists (the default, fail). Plain file writes are not truly atomic. Each task writes to a temporary location, and on job commit the files are moved to the final path by the output committer. On HDFS this rename is quick and mostly safe. On S3 a rename is a copy, slow and not atomic, so use a cloud-optimised committer (the S3A "magic" or "directory" committers, or a table format) otherwise a failure can leave partial output. Readers who list the folder during the commit can see half the data. For real atomic updates and safe reruns, write to a table format (Delta, Iceberg, Hudi) that commits through a transaction log, or write to a new versioned folder and switch a pointer when done.

Likely follow-ups
  • What are the _SUCCESS marker and _temporary folder? The marker is written after a good commit, and downstream jobs can wait for it. Leftover _temporary shows a failed job.

How do you read from or write to a relational database with Spark efficiently? Intermediate

What the interviewer is testing: know the default single-connection trap.

By default a JDBC read uses one connection and one partition, so one task reads the whole table, however large the cluster is. To parallelise, give partitionColumn, lowerBound, upperBound and numPartitions: Spark issues that many queries, each with a range predicate on a numeric, date or timestamp column. Choose an indexed, evenly distributed column, and keep numPartitions small enough (for example 8 to 32) not to overload the database. Use fetchsize for reads and batchsize for writes. You can also push a subquery as the table to let the database filter and aggregate. For writes, repartition to control the number of concurrent connections, use append, and remember that a retried task can insert twice, so make the target idempotent (an upsert or a unique key), or write to a staging table and merge.

spark.read.format("jdbc").option("url", url).option("dbtable", "orders")
  .option("partitionColumn", "id").option("lowerBound", 1).option("upperBound", 50000000)
  .option("numPartitions", 16).option("fetchsize", 10000).load()

7. Caching, memory model and tuning

When should you cache or persist a DataFrame, and what are the storage levels? Intermediate

What the interviewer is testing: knowing that cache is not free and not always useful.

Because of lazy evaluation, every action recomputes a DataFrame from its source. If you reuse an expensive result several times (for example in an iterative algorithm, or when it feeds two outputs), cache() keeps it after the first computation so later actions read from memory. Do not cache something used once, something cheap to recompute, or something so large it just evicts other data. Caching is lazy: nothing is stored until an action runs. cache() on a DataFrame uses MEMORY_AND_DISK; on an RDD it is MEMORY_ONLY. With persist(level) you choose: MEMORY_ONLY (partitions that do not fit are recomputed), MEMORY_AND_DISK (the rest spills to disk), _SER variants (serialised, smaller but costs CPU), DISK_ONLY, and _2 variants (replicated on two nodes). Always unpersist() when done. Cached data is not a fault-tolerance mechanism: if an executor is lost, its blocks are recomputed from lineage.

val enriched = raw.join(dim, "id").filter($"valid")
enriched.persist(StorageLevel.MEMORY_AND_DISK)
enriched.count()                       // materialises the cache
enriched.write.parquet("/out/a")       // reads from cache
enriched.unpersist()
Likely follow-ups
  • Difference between cache and checkpoint? Cache keeps lineage and may be recomputed; checkpoint writes to reliable storage and cuts the lineage.
Explain Spark's memory model: execution, storage, user and reserved memory. Senior

What the interviewer is testing: can you reason about executor memory errors.

Each executor JVM heap (spark.executor.memory) is divided like this. About 300 MB is reserved. Of the rest, spark.memory.fraction (0.6 by default) is the unified memory region, shared by two uses: execution memory (buffers for shuffles, joins, sorts and aggregations) and storage memory (cached data and broadcast variables). The remaining 40% is user memory for your own objects, UDF data and internal metadata. Since Spark 1.6 the boundary between execution and storage is soft. Within the unified pool, spark.memory.storageFraction (0.5) is a protected part for storage. Execution can borrow free storage space and can even evict cached blocks down to that protected amount, while storage cannot evict execution data. On top of the heap there is memory overhead (spark.executor.memoryOverhead, default the larger of 384 MB and 10% of the heap; larger by default for PySpark and Kubernetes): off-heap memory used by the JVM, native libraries, network buffers and the Python worker processes. The cluster manager container size is heap plus overhead. If the total exceeds it, YARN or Kubernetes kills the container, which shows as "container killed by YARN for exceeding memory limits".

Likely follow-ups
  • Is the 0.6 fraction a hard split? No. It is the size of the shared pool; execution and storage trade space inside it.
  • How many tasks share the memory? Each running task gets between 1/(2N) and 1/N of the execution pool, where N is the number of active tasks in the executor, so more cores per executor means less memory per task.
What is a spill, and when is it a problem? Intermediate

What the interviewer is testing: reading task metrics.

When a task needs more execution memory than it can get (for a sort, aggregation or hash table), Spark writes part of its in-memory data to local disk, and reads it back later to merge. This is a spill. It keeps the job alive instead of failing, but it is much slower, because of extra disk writes, serialisation and merge passes. The Spark UI stage page shows "Spill (Memory)" and "Spill (Disk)" per task. A little spill is normal; large spill means tasks are too big for their memory. Causes: too few shuffle partitions (each task gets a huge partition), skew (one key), too many cores per executor (less memory per task), or wide rows. Fixes: increase partitions (so each task is smaller), fix skew, give executors more memory or fewer cores, select fewer columns, and use AQE with an advisory partition size. Note the spill is on local disk, so full local disks can also fail a job.

Likely follow-ups
  • Spill (Memory) is much larger than Spill (Disk). Why? Memory size is the deserialised in-memory size; disk is serialised and compressed.
An executor fails with OutOfMemoryError or "container killed by YARN". How do you tell the cause and fix it? Senior

What the interviewer is testing: structured diagnosis rather than "raise memory".

Two very different failures look similar. Java heap OOM (java.lang.OutOfMemoryError: Java heap space or GC overhead limit exceeded): the JVM heap was full. Common causes: a huge or skewed partition, groupByKey building giant collections, a large broadcast, a large cached dataset, or too many cores sharing the heap. Container killed (YARN: "Container killed by YARN for exceeding memory limits... consider boosting spark.executor.memoryOverhead"; Kubernetes: pod status OOMKilled, exit code 137): the process used more total memory than the container, even though the heap was fine. Common causes: PySpark workers and pandas UDFs, native libraries, many threads and network buffers, off-heap use. Fixes: for heap errors, add partitions (smaller tasks), fix skew, reduce cores per executor, avoid groupByKey, raise executor.memory. For container kills, raise spark.executor.memoryOverhead (or spark.executor.pyspark.memory for Python). Before changing numbers, check the UI: which stage, which task, was it skewed, how big was the shuffle read.

Likely follow-ups
  • Why does adding executor memory sometimes not help? If one key holds more data than any single task can handle, the data size per task, not the total memory, is the problem.
Common mistakes: raising heap memory when the real error is overhead; or the opposite, which only makes the container larger and the next kill later.
When does the driver run out of memory, and how do you avoid it? Intermediate

What the interviewer is testing: the driver is a bottleneck people forget.

The driver holds the plan, the metadata of all tasks, and any data you bring back. It fails with OOM mostly for these reasons: collect(), toPandas() or a big take of large results; broadcasting a large table (it is first collected on the driver); too many partitions (hundreds of thousands of tasks means large scheduler state and many status updates); listing a table with millions of files or partitions, since file metadata is loaded on the driver; very long lineage or plans built in a loop (for example hundreds of withColumn or union calls, which makes the plan huge and the analysis slow); and a large number of accumulators or listener events. Fixes: write results instead of collecting, limit and aggregate first, raise spark.driver.memory, lower partition counts, compact small files, use a table format with a manifest instead of listing, and checkpoint or restructure loops that grow the plan. Use select with a list of columns instead of a loop of withColumn calls.

How do you decide the number of executors, cores and memory per executor? Senior

What the interviewer is testing: practical tuning reasoning. Heavy cluster capacity planning belongs to platform teams; a developer needs the rules of thumb.

Start from the node size. A common sweet spot is 4 to 5 cores per executor: more than about 5 cores per executor can hurt because many tasks fight for I/O throughput on the same HDFS or S3 client and share one heap (more GC, less memory per task); one core per executor wastes memory on duplicated overhead and does not share broadcasts. Leave one core and some memory per node for the operating system and daemons. Then divide the node memory by the number of executors on it and subtract about 10% for overhead. For example, a node with 16 cores and 64 GB gives three executors of 5 cores, about 19 GB total each, so roughly 17 GB heap plus 2 GB overhead. The total cores times 2 to 4 should about match the number of partitions you aim to process. Then adjust from evidence: spill and GC time in the UI say more memory per task; idle cores in a long stage say more partitions or fewer cores per executor. Memory per task is roughly the executor memory times 0.6 divided by cores.

Likely follow-ups
  • What about very fat executors (a 64-core, 400 GB JVM)? Garbage collection pauses get long, so most teams stay at moderate sizes.
What is dynamic allocation and when is it risky? Intermediate

What the interviewer is testing: resource use and shuffle file lifetime.

With spark.dynamicAllocation.enabled=true, Spark adds executors when tasks are pending for a while and removes executors that stay idle (default 60 seconds). Settings: minExecutors, maxExecutors, initialExecutors, and executorIdleTimeout. It is good for shared clusters and jobs with uneven stages, because you pay for resources only while using them. The catch is that an executor stores shuffle files for later stages, and removing it would lose them. So you need either the external shuffle service (on YARN) or, since Spark 3.0, spark.dynamicAllocation.shuffleTracking.enabled (works on Kubernetes without a service), where Spark keeps executors that still hold needed shuffle data. Other risks: executors holding cached data are not removed by default (cachedExecutorIdleTimeout is infinite), ramp-up delay hurts short stages, and a streaming job usually needs a fixed size or the dedicated streaming version of scaling. Set a sane maxExecutors, or one job can take the whole cluster.

A Spark job is slow. In what order do you investigate? Senior

What the interviewer is testing: method. This is a favourite open question.

I start with the Spark UI, not with config changes. First, which stage takes most of the time (Jobs and Stages tabs). Then, inside that stage, look at the task metric summary: is the max much bigger than the median (skew)? Is there spill, a lot of GC time, or a huge shuffle read? Is the stage waiting on few tasks while cores sit idle (too few partitions)? Next the SQL tab: the plan with row counts shows whether a filter was pushed down, which join strategy was used, and where a big Exchange sits. Then act on the cause. Skew: AQE, salting, isolate hot keys. Big shuffle: broadcast, filter and select earlier, bucket. Spill or OOM: more partitions, more memory per task. Slow read: fewer small files, partition pruning, Parquet. Slow Python: replace UDFs. After that, check scheduling: executors idle between stages (dynamic allocation delay), or a slow external system (JDBC, API). Only then tune sizes. I change one thing at a time and compare with the same data.

How do you spot and reduce garbage collection problems in Spark? Senior

What the interviewer is testing: JVM awareness for developers.

The Spark UI executors tab and the stage task table show "GC Time". If GC time is more than about 10% of task time, memory is under pressure. Causes: many small Java objects (RDD of case classes, Java collections in UDFs), large cached objects held on heap in deserialised form, and very big executors. Remedies in order: use DataFrames, since Tungsten stores rows in binary form and creates far fewer objects; cache serialised (MEMORY_ONLY_SER or the default for DataFrames) or use Kryo; reduce the data per task with more partitions; reduce cores per executor; and remove needless caching. Switching the collector (G1GC is the usual choice on Java 11 and 17) and tuning its regions helps for large heaps, but it is a last step, not a first. In Spark 4 the default JDK is 17 or 21.

What is speculative execution, and when would you avoid it? Intermediate

What the interviewer is testing: straggler handling and its side effects.

A straggler is a task that runs much slower than its peers, often due to a bad node, a noisy disk or a slow network. With spark.speculation=true, Spark checks periodically and, if a task runs longer than a multiple of the median (speculation.multiplier, default 1.5) once a quantile of tasks (0.75) has finished, it starts a second copy on another executor. Whichever finishes first wins and the other is killed. It helps with hardware problems. It does not help with skew, because the copy gets the same large partition and is equally slow. Avoid it when tasks have side effects that are not idempotent (writing to a database, calling an API), because two copies run the same code. For file output Spark's commit protocol makes sure that only one copy's files are committed, but for custom sinks it is your job. It also wastes resources if the real cause is data size.

8. Structured Streaming

What is Structured Streaming, and how does it relate to batch DataFrames? Basic

What the interviewer is testing: the core model of treating a stream as an unbounded table.

Structured Streaming (Spark 2.0 and later, stable from 2.2) lets you write a streaming job with the same DataFrame or SQL code as a batch job. Spark treats the stream as a table that keeps growing: new data arrives as new rows appended to an "input table". Your query describes how to compute a result table from it, and Spark runs it incrementally on each new chunk of data, updating the result. The engine takes care of progress tracking, retries and state. The default execution is micro-batch: every trigger, Spark takes the new data since the last batch, runs a normal batch job on it, and writes the output. This gives latencies of roughly 100 ms to a few seconds, and exactly-once guarantees. There is also a continuous processing mode with about 1 ms latency (experimental, at-least-once, limited operations), which few teams use. The older DStream API (Spark Streaming) is legacy and should not be used for new work.

Likely follow-ups
  • What are output modes? append (only new final rows), update (changed rows), complete (whole result table, only for small aggregates).
  • What triggers exist? Default: next batch as soon as the last ends. processingTime("1 minute"), availableNow (process all available data then stop, Spark 3.3+, replaces the deprecated once).
What is a checkpoint in Structured Streaming and what happens if you lose or change it? Intermediate

What the interviewer is testing: restart and upgrade correctness.

The checkpoint location is a folder on reliable storage (HDFS, S3) that you must give for any production query (option("checkpointLocation", path)). It stores: the offsets log (which input range each batch covers), the commit log (which batches finished), the query's state store files (for aggregations, joins, deduplication), and metadata. On restart, Spark reads it, finds the last committed batch, and continues from the next range, so no data is lost or processed twice (given a replayable source and an idempotent sink). If you delete it, the query starts over from the source's starting offsets (latest by default for Kafka, so you may skip data, or earliest, so you may reprocess everything) and state is lost. If you change the query, some changes are compatible (adding a filter, changing a sink in some cases), others are not: changing the grouping keys or the state schema, or the number of shuffle partitions of a stateful query, breaks recovery, and you need a new checkpoint location and a plan for backfill. One checkpoint folder per query, never shared.

Likely follow-ups
  • Why can't I change spark.sql.shuffle.partitions for a running stateful stream? State is stored per partition, and the count is fixed in the checkpoint.
What are event time, processing time and a watermark? Intermediate

What the interviewer is testing: the hardest streaming concept: late data and state cleanup.

Event time is when the event actually happened, written in the data (for example a click timestamp). Processing time is when Spark sees it. They differ because of network delay, mobile devices that go offline and similar. For a window aggregation ("clicks per 5 minutes"), you want event time. The problem is that data can arrive late, so Spark must keep each window's state open in case more events come, and without a limit that state grows forever. A watermark sets that limit: withWatermark("event_time", "10 minutes") means "I accept events up to 10 minutes older than the newest event time seen so far". Spark computes the watermark as the maximum event time seen minus the delay. A window that ends before the watermark is considered final: its result is emitted (in append mode) and its state is dropped. Events that arrive later than the watermark may be ignored. So the watermark is a trade-off between completeness (a longer delay) and memory and latency (a shorter delay).

Likely follow-ups
  • Does the watermark drop the whole window at once? Windows ending at or before the watermark are finalised; late rows that belong to them are dropped, with no error shown.
  • With several input streams? Spark uses the minimum of their watermarks by default (spark.sql.streaming.multipleWatermarkPolicy).
What is state in streaming, where does it live, and how do you keep it from growing without bound? Senior

What the interviewer is testing: a top production issue for streaming jobs.

Some operations must remember data between batches: aggregations (running counts), dropDuplicates (seen keys), stream-stream joins (rows waiting for a match), and custom logic with mapGroupsWithState or flatMapGroupsWithState. This state is stored per shuffle partition in a state store. The default store keeps it in executor JVM memory, backed up to the checkpoint each batch. Big state means GC pauses and out-of-memory. From Spark 3.2 you can use the RocksDB state store (spark.sql.streaming.stateStore.providerClass), which keeps state on local disk and off-heap, and scales to far larger state. To bound state: always use a watermark on windowed aggregations and stream-stream joins (with a time range condition in the join) so old keys expire; for deduplication include the event time column and watermark so old ids are dropped (or use dropDuplicatesWithinWatermark in 3.5+); set a timeout in arbitrary stateful operators; and avoid grouping by a column with unbounded cardinality (like a random id) without expiry. Spark 4.0 adds transformWithState with TTL and better state APIs. Monitor "numRowsTotal" in state operators from query.lastProgress.

Likely follow-ups
  • Which operations are stateless? select, filter, map, and joins of a stream with a static table.
How does Spark read from Kafka, and how are offsets handled? Intermediate

What the interviewer is testing: the most common streaming integration.

The Kafka source is a built-in format (format("kafka"), with the spark-sql-kafka package). Each Kafka partition becomes a Spark input partition, so the maximum read parallelism equals the number of topic partitions (use minPartitions to split further). Each record arrives with columns key and value as binary, plus topic, partition, offset, timestamp; you cast and parse the value (for example with from_json or Avro). Importantly, Spark does not use Kafka consumer-group offset commits for its progress. It tracks offsets itself in the checkpoint, which is what lets it give exactly-once processing on restart. This also means that lag shown by Kafka tools for a consumer group is not meaningful; use the query progress metrics instead. Control the rate with maxOffsetsPerTrigger, and choose startingOffsets (earliest or latest; only used on the first start without a checkpoint). If Kafka has already deleted data the query needs (retention passed), you get an error unless failOnDataLoss=false, which silently skips it.

val raw = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "k1:9092")
  .option("subscribe", "orders")
  .option("startingOffsets", "latest")
  .option("maxOffsetsPerTrigger", 200000)
  .load()
val parsed = raw.select(from_json($"value".cast("string"), schema).as("o")).select("o.*")
Likely follow-ups
  • How to write back to Kafka? format("kafka") sink needs a value column; it is at-least-once, so downstream consumers should be idempotent.
Does Structured Streaming give exactly-once? What does it need from the source and the sink? Senior

What the interviewer is testing: a precise answer about end-to-end guarantees.

Spark's guarantee is exactly-once for the results of the query, under conditions. It needs three things. (1) A replayable source: it can re-read the same offsets after a failure (Kafka, files; not a plain socket). (2) Offset tracking and a deterministic plan: Spark writes the planned offsets to the checkpoint before running a batch, so a retried batch covers exactly the same input. (3) An idempotent or transactional sink: if a batch was partly written before a crash and then re-run, writing it again must not create duplicates. File sinks (Parquet, etc.) track committed batches in a metadata log, so they are exactly-once. Delta or Iceberg tables commit transactionally. Kafka sink is only at-least-once. For databases, use foreachBatch and make the write idempotent, using the batchId or an upsert with a primary key. So "exactly-once" in practice means "at-least-once delivery plus idempotent writes". Side effects such as calling an API are not covered.

df.writeStream.foreachBatch { (batch: DataFrame, batchId: Long) =>
  batch.write.format("delta").mode("append")
    .option("txnAppId", "orders-job").option("txnVersion", batchId)   // idempotent write
    .save("/tables/orders")
}.option("checkpointLocation", "/chk/orders").start()
Likely follow-ups
  • Can foreachBatch run twice for the same batch id? Yes, after a failure it re-runs the batch, so the code inside must be idempotent.
What kinds of joins does streaming support, and what are their limits? Senior

What the interviewer is testing: depth on stateful operations.

Stream to static joins (a stream enriched with a dimension table) are stateless and simple: inner and left outer where the stream is on the left. The static side is re-read per batch (so keep it small or cache it with care, since changes are only seen if it is re-read). Stream to stream joins buffer rows from both sides as state until a match can arrive. Without bounds, state grows forever, so you should put watermarks on both inputs and a time-range condition in the join (for example b.ts BETWEEN a.ts AND a.ts + INTERVAL 1 HOUR). Inner joins work with or without watermarks (but state grows without them). Outer joins (left, right, full) need the watermark and time constraint, because Spark can only emit the "no match" row after it knows no match can still arrive; this makes outer results delayed. Arbitrary joins that cannot be made incremental (some full outer cases, joining after an aggregation in append mode) are not allowed.

Compare the streaming sinks and when you would use foreachBatch. Intermediate

What the interviewer is testing: choosing the output path correctly.

Built-in sinks: file (Parquet, JSON, CSV; append only, exactly-once), Kafka (at-least-once), console and memory (for debugging only), and foreach / foreachBatch (your code). foreachBatch gives you each micro-batch as a normal DataFrame plus the batch id. That lets you do things streaming sinks do not support: write to several targets, run a MERGE (upsert) into a table, use a JDBC or other batch-only connector, and run extra batch logic. Its guarantee is at-least-once, so use the batch id for idempotency. Cache the batch if you write it twice, and unpersist it at the end. The foreach sink works per row with open, process and close methods, which is rarely a good idea for throughput.

df.writeStream.foreachBatch { (b: DataFrame, id: Long) =>
  b.persist(); b.write.mode("append").parquet("/lake/raw"); upsertToDb(b, id); b.unpersist()
}.start()
When would you choose Structured Streaming with micro-batches, a continuous engine like Flink, or just a scheduled batch job? Senior

What the interviewer is testing: judgement, not tool loyalty.

If the freshness needed is hours or a day, a scheduled batch job is simplest and cheapest, and with Trigger.AvailableNow you can even run the same streaming code as an incremental batch every N minutes, which keeps checkpoints and exactly-once handling while releasing the cluster between runs. Structured Streaming micro-batch fits latencies from a few seconds to minutes, especially when you already use Spark, need the same code for batch and stream, and want strong integration with the lake (Delta, Iceberg). A record-at-a-time engine like Flink fits sub-second latency, complex event-time handling with fine control, and very large keyed state with low-latency access. Spark's continuous mode exists but is limited. I would weigh team skills and operations cost as much as raw latency, because most "real-time" requirements turn out to be fine with 30 seconds to a few minutes.

How do you monitor a streaming query and tell when it is falling behind? Intermediate

What the interviewer is testing: operating streaming jobs.

Use query.lastProgress or a StreamingQueryListener, and the Streaming tab of the UI. Key numbers: inputRowsPerSecond (arrival rate) against processedRowsPerSecond (how fast you process). If arrival is higher than processing, you are falling behind. batchDuration compared with the trigger interval: if batches take longer than the trigger, they queue up. durationMs breaks time into planning, reading, writing and committing. stateOperators shows state row counts and memory, so you can see growth. For Kafka, the progress shows per-partition start, end and latest offsets, so you can compute lag (latest minus end). Send these to your metrics system and alert on lag trend, batch duration, state size and failures. Common fixes for lag: more partitions or cores, maxOffsetsPerTrigger to protect against huge catch-up batches, fixing a slow sink, reducing state, and avoiding tiny batches.

9. Fault tolerance, languages, testing and the ecosystem

What is lineage, and how does Spark use it for fault tolerance? Intermediate

What the interviewer is testing: the Spark answer to "what if a node dies".

Lineage is the recorded graph of transformations that produced a dataset from its source. Spark does not replicate computed data like HDFS does. If a partition is lost (an executor died), the scheduler looks at the lineage, finds the parent partitions, and recomputes only that lost partition by re-running the steps. For narrow dependencies this touches one parent partition, so it is cheap. For wide dependencies it may need many parents, unless their shuffle files still exist. It works because transformations are deterministic and the input is re-readable. Weak points: a very long lineage (iterative loops with hundreds of steps) makes recomputation expensive and can overflow the driver with a deep plan, and non-deterministic steps (random numbers without a seed, reading a changing source) can give different data on recompute. The fix for a long lineage is a checkpoint.

What is the difference between checkpoint() and cache(), and when do you checkpoint in batch jobs? Intermediate

What the interviewer is testing: lineage truncation.

cache() keeps data in executor memory or local disk but still remembers the lineage; if the cache is lost, it recomputes from the source. checkpoint() saves the data to reliable storage (set spark.sparkContext.setCheckpointDir to HDFS or S3) and cuts the lineage: the new dataset starts from the saved files. Use it when the plan has grown huge, for example after dozens of iterations in a graph or machine learning loop, or after many chained unions; a very long plan slows the analysis on the driver and increases recomputation cost. On DataFrames, checkpoint() is eager by default (it runs a job at once); localCheckpoint() stores on executors' local disk and is faster but not safe if an executor dies. A cheaper, widely used alternative is to write the intermediate result to a Parquet table and read it back, which also helps debugging. Do not confuse it with the streaming checkpoint, which is a different mechanism.

PySpark vs Scala vs Java for Spark: how do they differ in performance and in practice? Intermediate

What the interviewer is testing: informed language choice.

For DataFrame and SQL code the language barely matters for speed. Python only builds the plan; the JVM executes it with Catalyst and Tungsten. The slowdown appears when Python code runs on the executors: plain Python UDFs, RDD lambdas, and toPandas. Then every row crosses from the JVM to a Python worker process and back. In PySpark the driver talks to the JVM through Py4J, and each executor starts Python worker processes next to its JVM (so PySpark needs more memory overhead). Scala is the native language: typed Datasets, full access to internals and new APIs first, no serialisation boundary for UDFs, and easy custom data sources or Catalyst extensions. Java is fully supported, but its Dataset API is more verbose (encoders, lambdas with explicit types); it fits teams that are already on Java. Python wins on data-science ecosystem, ease, and hiring. A sensible rule: use PySpark with built-ins and pandas UDFs for most pipelines, and Scala or Java for performance-critical custom logic and shared libraries.

Likely follow-ups
  • How do you ship Python dependencies? --py-files, a conda or venv archive (--archives), or a container image.
What should a Java developer know when using Spark's Java API? Intermediate

What the interviewer is testing: practical points for a Java shop, which is common.

Use Dataset<Row> for DataFrames, and use functions from org.apache.spark.sql.functions.* (static imports) for expressions. For typed Datasets you need an Encoder: Encoders.bean(Person.class) works for Java beans with a no-argument constructor and getters and setters; Encoders.STRING() for primitives. Lambdas passed to map or filter need a cast to MapFunction<T,U> to resolve overloads between the Java and Scala versions. Everything captured by a lambda must be serialisable, so avoid capturing the enclosing class (use a static method or a small static nested class). Scala-specific types (Seq, Option) appear in some APIs, and conversion helpers are needed. Build with Maven or Gradle and mark Spark as provided scope so the cluster's jars are used; build a shaded (fat) jar for your own dependencies and watch for version clashes (Guava, Jackson, Netty). Spark 4 requires Java 17 or later.

Dataset<Person> ds = df.as(Encoders.bean(Person.class));
Dataset<String> names = ds.map((MapFunction<Person, String>) Person::getName, Encoders.STRING());
How do you unit test and integration test Spark code? Intermediate

What the interviewer is testing: engineering quality for data pipelines.

Structure the code so the transformations are plain functions: DataFrame => DataFrame, with the reading and writing at the edges. Then tests build tiny input DataFrames in memory, call the function, and compare to an expected DataFrame. Use a local session shared by the whole test suite (master("local[2]"), small spark.sql.shuffle.partitions like 2, UI disabled) because creating a session for each test is slow. In Scala, the libraries spark-testing-base, scalatest with a shared session trait, or Spark's own test helpers work. In Python, use pytest with a session-scoped fixture; chispa or pyspark.testing.assertDataFrameEqual (3.5+) compares DataFrames. Compare in a way that ignores row order unless order matters. Cover edge cases: nulls, empty input, duplicates, skewed keys, time zones. For integration tests, run a small sample against a real table format and storage (a container or local files), and for streaming use MemoryStream as the source and the memory sink to test batch by batch, with Trigger.AvailableNow or processAllAvailable(). Add data quality checks in the pipeline (row counts, null rates, uniqueness) as run-time tests.

def test_dedupe(spark):
    src = spark.createDataFrame([(1, "a"), (1, "a"), (2, "b")], "id INT, v STRING")
    out = dedupe(src)
    assertDataFrameEqual(out, spark.createDataFrame([(1, "a"), (2, "b")], "id INT, v STRING"))
What do you look at in the Spark UI? Intermediate

What the interviewer is testing: hands-on experience.

Jobs tab: the timeline of jobs and executor events. Stages: per stage the task counts, duration, a metrics summary (min, 25th, median, 75th, max) of task time, input and shuffle sizes, spill and GC time. A big gap between median and max says skew. Storage: cached datasets, their size in memory and on disk, and the fraction cached. Environment: the effective configs, which is where to check if your setting was really applied. Executors: per executor memory use, task time, GC time, shuffle read and write, failed tasks, and which executors were lost. SQL / DataFrame: the plan graph with row counts and time per node, and the final AQE plan. Structured Streaming: input rate, process rate, batch duration. For finished applications, use the Spark History Server, which needs spark.eventLog.enabled and a log directory.

Why do teams use Delta, Iceberg or Hudi on top of Parquet with Spark? Senior

What the interviewer is testing: modern lakehouse awareness, and the limits of plain files.

Plain Parquet folders have no transactions: a failed job can leave half the files, readers can see partial writes, two writers can conflict, and you cannot update or delete a row without rewriting files by hand. Table formats add a metadata layer (a transaction log or manifest files) over Parquet. That gives ACID commits (a write becomes visible all at once), row-level MERGE, UPDATE and DELETE, schema evolution, time travel (query an older version), faster planning with file statistics instead of directory listing, and compaction tools. They also make streaming sinks and idempotent reruns much easier. Delta Lake started at Databricks; Iceberg came from Netflix and is widely adopted with many engines; Hudi came from Uber and is strong at record-level upserts and incremental pulls. The cost is another dependency, table maintenance (compaction, snapshot expiry, vacuum), and format-specific behaviour. For a developer, the answer to "how do I safely rerun a job and not get duplicates" is very often "write with MERGE or overwrite into a table format".

How do you design a Spark batch job to be safely rerunnable? Senior

What the interviewer is testing: pipeline design maturity.

The aim is that running the job twice for the same input gives the same output, with no duplicates and no gaps. Rules I follow: parameterise by a business date or batch id, not by "now"; read a clearly defined input slice; make the output deterministic (avoid unseeded rand, current_timestamp in keys, or unordered first); write with overwrite of the exact partition (partitionOverwriteMode=dynamic) or a table-format MERGE on a business key, rather than blind append; write to a staging location and then swap or commit; and record the run in a control table so you can detect double runs. Keep external side effects out of tasks, or make them idempotent with a key. Deduplicate on a natural key with a window and row_number when the source can deliver repeats. Finally, test the rerun path explicitly: run twice and compare counts and checksums.

For an interview, the three to remember are: Spark 2 brought the unified DataFrame and Dataset API and Tungsten; Spark 3 brought AQE and the Kubernetes and Python improvements; Spark 4 brought ANSI-by-default and removed old Java and Scala support. If you cannot remember an exact minor version, say "around 3.2".

Spark vs Hive, Presto/Trino, Flink and dbt: where does Spark fit? Senior

What the interviewer is testing: breadth and positioning.

Spark is a general engine for large-scale ETL, heavy transformations, machine learning and streaming, with code in several languages. Hive (on Tez or MapReduce) is the older SQL-on-Hadoop layer; its metastore is still the common catalog that Spark uses. Presto and Trino are interactive SQL query engines: they stream data between stages in memory without fault tolerance for long queries (by default), which makes them fast for ad hoc queries but weaker for hours-long ETL; Spark survives failures by recomputing. Flink is a record-at-a-time streaming engine with lower latency and finer state control. dbt is a SQL transformation framework that runs inside a warehouse or on Spark, not an engine itself. A typical modern platform: Spark for ingestion and heavy transforms, a table format on object storage, and Trino or a warehouse for interactive queries.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, steps, and how you prevent it next time. Say this shape aloud in the interview, it shows you work calmly under pressure.

A nightly job that usually takes 20 minutes now takes 3 hours, and one task in the join stage runs forever. What do you do? Senior

What the interviewer is testing: skew diagnosis with a method.

Situation: 199 of 200 tasks finish in seconds and one task keeps running, reading gigabytes. That is the shape of skew, and it often starts when a new upstream feed brings a flood of one key (a null, "unknown", or one big customer).

Check first: the stage page: compare the median and max of task duration and shuffle read size. Then find the hot key with a quick count.

df.groupBy("customer_id").count().orderBy($"count".desc).show(10)
df.filter($"customer_id".isNull).count()

Steps: if the hot key is null or a placeholder, filter it out before the join (it never matches in an inner join). Make sure AQE is on (spark.sql.adaptive.enabled and skewJoin.enabled), which splits big partitions of a sort-merge join. If the other side is small enough, broadcast it. Otherwise salt the hot keys (replicate the small side by N and add a random salt to the big side), or process hot keys separately with a broadcast join and union the result with the normal join.

Prevent: a data quality check on key distribution (top-key share), alerts when the max/median task time ratio is high, and a rule that nulls and defaults are cleaned in the ingest layer.

Likely follow-ups
  • What if AQE is on and still slow? The skew rules need the partition to be above 256 MB and 5 times the median, and they do not split the preserved side of some outer joins; fall back to salting.
Executors keep dying with OutOfMemoryError during a groupBy on a big table. How do you fix it? Senior

What the interviewer is testing: diagnosis instead of "add more memory".

Situation: tasks fail with java.lang.OutOfMemoryError: Java heap space or GC overhead limit exceeded, retried four times, and the stage fails.

Check first: the error text (heap versus "container killed"), which stage, and whether the failing tasks are the large ones (skew) or all of them (partitions too big). Check the shuffle read size per task and the number of shuffle partitions. Check whether the code uses groupByKey, collect_list or collect_set on a big group, which builds one giant collection in memory.

Steps: (1) raise the shuffle partitions so each task is around 100 to 200 MB, or let AQE size them; (2) replace groupByKey or collect_list with a real aggregation that combines on the map side; (3) fix skew if one key is huge; (4) reduce cores per executor so each task has more memory; (5) only then raise spark.executor.memory. If the message is "killed by YARN for exceeding memory limits", raise spark.executor.memoryOverhead instead.

Prevent: keep an eye on spill and GC time in the UI for every new job, and load-test with a day of peak data.

A job writes 200,000 tiny Parquet files every day and downstream queries are slow. Fix it. Intermediate

What the interviewer is testing: write-side control and compaction.

Situation: the output folder has many files of a few KB. Listing takes minutes, readers create too many tasks, and the metastore is slow.

Check first: how many write tasks there are (shuffle partitions or input partitions), how many distinct partitionBy values each task holds, and whether a streaming job appends tiny batches.

Steps: repartition by the same columns you use in partitionBy before writing, so each partition value is produced by few tasks. Set the partition count from the data size (about 128 to 512 MB per file), use maxRecordsPerFile as a safety net, and use the REBALANCE hint or AQE. For past data, run a compaction job: read each day folder and rewrite it with coalesce or repartition. If you use Delta or Iceberg, schedule OPTIMIZE or rewrite_data_files.

df.repartition($"date")
  .write.option("maxRecordsPerFile", 5000000)
  .partitionBy("date").mode("overwrite").parquet(out)

Prevent: a check on file count and average file size at the end of the job; for streaming sinks, a longer trigger interval and a compaction job.

The Spark UI shows tens of gigabytes of shuffle spill and the stage is very slow. What do you change? Senior

What the interviewer is testing: link between partition size, memory and spill.

Situation: "Spill (Memory)" and "Spill (Disk)" columns are large, tasks have long durations, and local disks are busy.

Check first: shuffle read per task. If it is, for example, 3 GB per task with 200 partitions, each task cannot hold its data in its share of execution memory. Check cores per executor and the memory per task.

Steps: increase spark.sql.shuffle.partitions (or lower the AQE advisory size) so tasks are about 100 to 200 MB. If one task is much bigger, it is skew and needs the skew fixes. Select only the needed columns before the shuffle so rows are narrower. Give each task more memory: fewer cores per executor, or more executor memory. Consider the sort-merge join over shuffle hash if hash tables are the issue. After each change compare the spill and the total time.

Prevent: set partition counts relative to data volume, not a fixed 200, and let AQE coalesce.

The driver crashes with an OutOfMemoryError right after a "collect" in a report job. Explain and fix. Basic

What the interviewer is testing: the driver as a bottleneck.

Situation: a job that worked on test data fails in production after printing "collecting results", with a driver OOM or the error "total size of serialized results is bigger than spark.driver.maxResultSize".

Check first: the code for collect(), toPandas(), large take or a big broadcast, and the size of the dataset at that point.

Steps: do the aggregation on the cluster and only bring back the small result. If the goal is to save data, write it with df.write instead of collecting it. If you really need the rows locally, use limit or toLocalIterator(). Do not just raise spark.driver.memory and maxResultSize: it only moves the limit, and one machine will never scale as the data grows. For Pandas conversion, enable Arrow and convert only aggregated data.

Prevent: code review rule: no collect on data that can grow; test with realistic volumes.

A Kafka to Spark streaming job falls further behind every hour. What do you check? Senior

What the interviewer is testing: streaming troubleshooting.

Situation: the Kafka lag grows, batch durations are longer than the trigger interval, and the input rate is above the processed rate.

Check first: lastProgress: where does the batch time go (query planning, reading, state, writing, commit)? Is the slow part one stage, and is it skew again? How many Kafka partitions are there (the read parallelism limit) and how many cores? Did the input rate increase, or did batch time increase for the same input (state or sink getting slower)?

Steps: if reading is the limit, add partitions to the topic and cores to the job. If a sink is slow (a database), batch writes, increase its parallelism, or move to a faster sink. If state grows, add or shorten the watermark, or switch to RocksDB. Use maxOffsetsPerTrigger so a catch-up does not make one gigantic batch that fails. Fix shuffle partitions (the default 200 is often too many for small batches and costs overhead). If data is skewed by key, apply the skew fixes inside the batch.

Prevent: alert on lag trend and on batch duration over trigger interval, keep headroom (processing at 50 to 60% of capacity), and test replays of a busy day.

A streaming aggregation works for a week and then runs out of memory. State keeps growing. Why, and what is the fix? Senior

What the interviewer is testing: watermark and state lifecycle.

Situation: executors fail with OOM or GC time rises steadily; stateOperators.numRowsTotal in the progress only goes up.

Check first: is there a watermark on the event-time column, and is the aggregation grouped by a time window? A grouping by a column with unbounded values (session id, request id) and no watermark never expires keys. Was the watermark defined on a column that is later changed or recomputed (the watermark must be defined on the same column used in the window, before the aggregation)?

Steps: add withWatermark("event_time", "15 minutes") and group by window(event_time, ...), so old windows are closed and dropped. For deduplication, include the event time and use a watermark (or dropDuplicatesWithinWatermark). Switch to the RocksDB state store for large state. Check that a stalled input (an idle partition with no data) is not holding the watermark back, since the watermark is based on the maximum event time seen. Because the state schema is stored in the checkpoint, changing it needs a new checkpoint and a backfill.

Prevent: a dashboard of state rows and state memory per query, and a rule that every stateful query declares how its state expires.

You must join a 2 TB fact table with a 300 MB dimension table, and the job shuffles the 2 TB. How do you make it faster? Intermediate

What the interviewer is testing: knowing when and how to broadcast.

Situation: the plan shows SortMergeJoin with two Exchanges, and the 2 TB side is shuffled and sorted. The dimension is 300 MB on disk.

Check first: the real in-memory size of the small side after filtering and selecting needed columns (Parquet compresses, memory can be several times larger), and the executor memory. The default threshold is 10 MB, so Spark did not choose broadcast.

Steps: project and filter the dimension to what is needed, then use broadcast(dim) or raise autoBroadcastJoinThreshold. 300 MB is usually fine when executors have a few GB, but check the driver memory since the table passes through it. Confirm BroadcastHashJoin in the plan. If it is too large to broadcast, use a shuffle hash join hint or bucket both tables on the key. With AQE on, Spark may switch to broadcast by itself if the filtered size is under the threshold.

Prevent: table statistics (ANALYZE TABLE ... COMPUTE STATISTICS) so the optimizer knows sizes.

After a task failure and retry, the output table has duplicate rows. How can that happen, and how do you stop it? Senior

What the interviewer is testing: idempotency and commit protocols.

Situation: counts are higher than the source after a run with failures, speculation or a restart.

Check first: what kind of sink: plain files, a JDBC database, Kafka, an API? File writes through Spark's commit protocol are safe against task retries: a failed task's files are discarded, and only a successful attempt is committed. Duplicates usually come from other places: a JDBC or API write inside tasks (a retried task inserts again), speculative tasks running side effects twice, rerunning the whole job with append for the same date, a streaming restart without idempotent writes in foreachBatch, or a source with duplicates (Kafka at-least-once producers).

Steps: make writes idempotent: overwrite exact partitions, or MERGE on a business key into a table format, or use a primary key with upsert in the database. In foreachBatch, use the batch id. Disable speculation for non-idempotent sinks. Deduplicate on a key (window with row_number, or dropDuplicates). Check the S3 committer setup, since the old rename-based committers can leave partial or duplicate output on failure.

Prevent: the rerun test (run the job twice and compare), a unique-key check at the end of the pipeline.

A PySpark job takes 4 hours because of one Python UDF. How do you speed it up? Intermediate

What the interviewer is testing: knowing the cost ladder.

Situation: the plan has BatchEvalPython, and the CPU of the Python workers is the bottleneck.

Check first: what the UDF does. Most cleanups (string trimming, regex, date parsing, conditionals, array operations) have built-in equivalents.

Steps: (1) rewrite it with built-in functions (regexp_extract, when, transform, expr) so Catalyst can optimise it; (2) if logic needs Python libraries, convert it to a pandas UDF (Arrow batches, vectorised); (3) for per-partition setup such as loading a model, use mapInPandas so the model loads once per task; (4) as last option, write a Scala or Java UDF and ship the jar. Also push filters before the UDF so it sees fewer rows, and check that spark.sql.execution.arrow.pyspark.enabled is on. Measure again on a sample.

Prevent: a code review rule to prefer built-ins and a small library of tested helper expressions.

A query that filters on one date still reads the whole table. Why, and what do you change? Intermediate

What the interviewer is testing: partition pruning and pushdown.

Situation: the table is partitioned by event_date but the scan reads all folders; the UI shows terabytes of input.

Check first: explain("formatted") on the scan: is PartitionFilters empty? Common causes: the filter wraps the partition column in a function (date_format(event_date, ...) or cast) or compares it with a different type; the filter is on a column derived from the partition column, such as a timestamp event_ts; the filter value comes from a subquery or a join (it needs dynamic partition pruning, Spark 3+, which works only in some join shapes); or the table is a set of files read with spark.read.parquet(path) where the folder names are not key=value.

Steps: filter directly on the partition column with a literal of the same type, add the partition filter beside the timestamp filter, or read the specific path. Select only needed columns, and check PushedFilters for Parquet predicate pushdown. For a join-driven filter, check that dynamic partition pruning is enabled and the plan shows dynamicpruningexpression.

Prevent: document the partition column and its type, and review plans for new queries on large tables.

The final write to S3 takes longer than the whole computation, and sometimes leaves partial output. What is going on? Senior

What the interviewer is testing: object-store commit behaviour.

Situation: all tasks finish quickly, then the job sits in "commit" for a long time, and after a failure the folder has some files but no _SUCCESS.

Check first: which output committer is in use. The classic file committers write to a temporary directory and then rename files into place. On S3, a rename is a copy plus delete and is not atomic, so job commit is slow, and a failure in the middle leaves a mix. Version 2 of the file committer algorithm also makes files visible before the job ends.

Steps: use a committer made for object stores: the S3A "magic" or "directory" staging committers (with the Spark cloud committer bindings), or a table format such as Delta or Iceberg, which commits by writing a small log or metadata file. Reduce the number of output files so there is less to commit. Make downstream readers wait for the _SUCCESS file or use the table snapshot. Rerun with overwrite of the exact partition so a repeat is safe.

Prevent: a standard platform write helper that configures the committer and file sizes for everyone.

After adding cache() everywhere to speed things up, the job got slower and executors run out of memory. Why? Intermediate

What the interviewer is testing: cache is a trade-off, not a free speedup.

Situation: many DataFrames are cached and never unpersisted. GC time is high and the Storage tab shows datasets only partly cached.

Check first: the Storage tab (fraction cached, size on disk and in memory), and whether each cached DataFrame is used more than once.

Steps: remove caches on data used once or cheap to recompute. Keep a cache only for expensive results reused by several actions. Choose MEMORY_AND_DISK (or serialised) for big datasets. Cached blocks take space from the unified pool, so execution memory shrinks and shuffles spill more. Call unpersist() when finished. Project columns and filter rows before caching so there is less to hold. Cache is also not the same as materialisation: it happens at the first action; if that is a cheap take(1), only one partition is cached. Use count() to fill it fully.

Prevent: a rule to justify each cache with a measurement.

A join that should return about 10 million rows returns 4 billion and fills the disk. What happened? Intermediate

What the interviewer is testing: join correctness and data quality.

Situation: the output is far larger than either input, shuffle write is huge, and executors fail on disk space.

Check first: key uniqueness on each side: groupBy(key).count().filter(count > 1). If both sides have duplicates for a key, the join creates a many-to-many product, so a key present 1,000 times on each side gives 1,000,000 output rows. Also check for default or null-like key values ("", "N/A", 0) that many rows share, and for a missing or wrong join condition that became a cartesian product (look for CartesianProduct or BroadcastNestedLoopJoin in the plan).

Steps: deduplicate or aggregate the side that should be unique, using a window with row_number to keep the latest row. Filter junk keys. Add the missing join condition columns (for example the date or tenant id). If a many-to-many join is truly intended, pre-aggregate before it. Add an assertion in the pipeline that a dimension key is unique and that the output row count does not exceed the left side for a left join.

Prevent: uniqueness checks at the ingest of dimension tables and a post-join count guard.

You have 400 cores, but a stage runs only 20 tasks and the cluster is idle. How do you improve it? Intermediate

What the interviewer is testing: parallelism tuning.

Situation: the stage page shows 20 tasks, each long and each reading a lot, and most executors do nothing.

Check first: where the 20 comes from. Reading a few large non-splittable files (for example 20 gzip CSV files) gives exactly one task per file. A previous coalesce(20) or repartition(20) is still active. A low spark.sql.shuffle.partitions was set globally. A JDBC read without partition options gives one task.

Steps: if files are not splittable, repartition right after the read to spread the work for later steps (the read itself stays at 20 tasks), and in the long term convert to Parquet or split files. Remove the early coalesce, or move it to just before the write. Raise shuffle partitions to a multiple of your cores (2 to 4 times), or leave it to AQE with a high initial value. For JDBC, set partition column and bounds. Check that the executors you asked for were actually granted (Executors tab), especially with dynamic allocation.

Prevent: a quick check of task counts in the first run of any new job.

A daily job suddenly fails or returns nulls because the upstream team changed a column type. How do you handle schema changes safely? Intermediate

What the interviewer is testing: schema management in real pipelines.

Situation: yesterday the column amount was an integer, today some files have it as a string with decimals. With inference or non-ANSI casting, the job runs and quietly produces nulls, or it fails with a Parquet "cannot convert" error.

Check first: the schemas of old and new files (printSchema, or read a few files one by one), and how the job reads: inferred, merged, or explicit schema. Check null counts of key columns against yesterday.

Steps: read with an explicit schema and a strict mode (FAILFAST, or capture bad rows in a quarantine location) so errors are loud. Use try_cast semantics where you really want leniency, and count the rows that failed to convert. For Parquet with mixed schemas, either read the old and new data separately and cast to a common type, or use mergeSchema if the types are compatible. Table formats (Delta, Iceberg) manage evolution by explicit changes and reject incompatible writes. Agree with the upstream team on a data contract and notification of changes.

Prevent: contract tests, and data quality checks of null rate and value ranges after every load.

Your job spends 15 minutes at the start doing nothing visible on executors, with the driver at 100% CPU. What is happening? Senior

What the interviewer is testing: driver-side bottlenecks that people overlook.

Situation: the Spark UI shows no running jobs for a long time, or a stage starts only after many minutes. Executors are idle.

Check first: a thread dump of the driver, or the driver log. The usual suspects are: file listing of a table with hundreds of thousands of partitions and files (it lists directories and reads footers on the driver), plan analysis of a very big plan built in a loop (hundreds of withColumn, union or self-joins make a plan that takes minutes to analyse and optimise), schema inference over many files, and a huge number of tasks to serialise.

Steps: for listing, use partition pruning, table formats or a metastore with partition statistics, compact the small files, and set the parallelism of file listing (spark.sql.sources.parallelPartitionDiscovery.threshold). For deep plans, replace loops of withColumn with one select, break the lineage with a checkpoint or a write and read back, and avoid repeated unions of many DataFrames (union all at once). Give the driver more cores and memory if needed. Provide a schema to skip inference.

Prevent: keep the number of files and partitions of a table under control and watch for time to first task as a metric.
