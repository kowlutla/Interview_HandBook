Mental model: the 8 ideas everything hangs on

One line: Spark splits your data into partitions, runs the same code on each partition in parallel (tasks), and only moves data between machines (a shuffle) when an operation needs rows with the same key together. Transformations only build a plan. An action runs it.
  1. Driver and executors. The driver is one process that holds your program, builds the plan and schedules work. Executors are worker processes that hold data in memory and run tasks.
  2. Partitions are the unit of parallelism. One partition is processed by one task at a time. More partitions means more parallel tasks, up to the number of cores.
  3. Lazy evaluation. filter, select, join do nothing yet. They add to a plan. Only an action (count, write, collect) starts a job.
  4. Narrow versus wide. A narrow step (map, filter) works on each partition alone. A wide step (groupBy, join, repartition) needs data from many partitions, so it causes a shuffle.
  5. Shuffle is the cost center. It writes to disk, moves data over the network and reads it back. Most tuning is "avoid, shrink or balance the shuffle".
  6. Job, stage, task. An action makes a job. A job is cut into stages at every shuffle. A stage is a set of identical tasks, one per partition.
  7. The optimizer is on your side. DataFrame and SQL code goes through Catalyst (plan rewrites) and Tungsten (fast code and memory layout). Opaque code (UDFs, lambdas) blocks it.
  8. Lineage gives fault tolerance. Spark remembers how each partition was computed, so a lost partition is recomputed instead of restored from a replica.

1. Why Spark, and the architecture

What is Apache Spark, and why did it replace MapReduce for most workloads? Basic

Spark is a distributed engine that runs your transformations on many machines in parallel. MapReduce writes the result of every step to disk and forces a fixed map-then-reduce shape. Spark describes the whole chain as one plan, pipelines steps in memory, and touches disk only at shuffles. It also gives one engine for batch, SQL, streaming and machine learning.

A ten-step MapReduce pipeline is ten jobs, each reading and writing HDFS. In Spark the same pipeline is one job where consecutive narrow steps run in a single pass over each partition. The "100 times faster" claim holds for iterative in-memory work. For one big scan-and-aggregate, expect a few times faster, and Spark still spills to disk when data does not fit. Spark is a poor fit for tiny data (one machine is faster) and for low-latency single-row lookups.

The problem it solves. Data too big for one machine has to be split across many, and a real job is rarely one step: you read, clean, join, aggregate, then maybe repeat the aggregate with different inputs. In MapReduce every step is its own job, and between jobs the result is written to HDFS (three replicas, disk and network) and read back. Machine learning loops or multi-stage ETL pay that toll again and again.

What Spark does differently.

  1. You describe the whole pipeline first. Spark sees all the steps before running any of them.
  2. Consecutive steps that do not need data from other machines (filter, map, select) are fused and run in one pass over each chunk of data, so intermediate results are never stored.
  3. Data goes to disk only when it must move between machines (a shuffle), when a cache spills, or at the final write.
  4. One engine and one API serve SQL, DataFrames, streaming and ML, so you do not stitch together separate systems.

Tiny example. "Read logs, keep errors, count per service, join with the owner table, write." In MapReduce that is several jobs with HDFS writes between them. In Spark it is one job with two stages: stage 1 reads, filters and partially counts; one shuffle; stage 2 finishes the count, joins and writes.

When Spark is the wrong tool. Small data (a laptop and pandas or a database is faster, because Spark has startup and scheduling overhead), low-latency lookups of single rows (use a database or key-value store), and sub-millisecond event processing (micro-batch Spark is not built for that). Be fair to MapReduce in an interview: its disk-based design is still robust for huge, simple, one-pass jobs. Spark's win is a richer programming model plus removing the disk tax between steps.

Remember: MapReduce = disk after every step. Spark = one plan, memory between steps, disk only at shuffles.

Explain the driver, the executors and the cluster manager. What are client and cluster deploy modes? Basic

The driver is the process running my main method. It builds the plan, cuts it into stages and tasks, and schedules them. Executors are JVMs on worker machines that run the tasks, cache data and write shuffle files. The cluster manager (YARN, Kubernetes, standalone) only hands out machines and starts executors. It does not understand my job.

The driver is a single point of failure: if it dies, the application dies. Executors can be lost and replaced while the job continues. Data does not flow through the driver. Executors read files directly, and data only reaches the driver through collect or toPandas.

Deploy mode says where the driver runs. In client mode it runs on the machine that submitted the job: good for notebooks and the shell, but the job dies if that machine or its network dies. In cluster mode it runs inside the cluster, which is the normal choice for scheduled production jobs. Local mode (--master local[4]) runs everything in one JVM and is what unit tests use. Sizing the cluster itself is an ops topic.

spark-submit --master yarn --deploy-mode cluster \
  --num-executors 10 --executor-cores 4 --executor-memory 8g \
  --class com.acme.Etl app.jar 2026-11-17

Picture it as a manager and workers. The driver is the project manager holding the plan. Executors are the workers, each with a few hands (cores) and a desk (memory). The cluster manager is the facilities office: it gives you rooms and workers when you ask, then steps out of the way. It does not know what your job does.

What happens at startup.

  1. spark-submit starts the driver (location depends on deploy mode).
  2. The driver registers with the cluster manager and asks for N executors of a given size.
  3. The cluster manager launches executor JVMs on worker nodes.
  4. Executors connect back to the driver directly. From now on tasks go driver to executor and results flow back, with no manager in between.

Why client versus cluster matters. In client mode the driver is a process on your edge node or laptop. It streams logs to your terminal, which is convenient, but the executors talk to it constantly, so a slow or flaky network between you and the cluster slows the job, and if you close the laptop the job dies. In cluster mode the cluster starts the driver inside itself (on YARN, in the ApplicationMaster container; on Kubernetes, in a driver pod). The submit command can return, and the driver sits close to the executors. That is why schedulers such as Airflow use cluster mode.

Client modeCluster mode
Driver runs onThe submitting machineA node inside the cluster

Pitfalls. Driver memory and executor memory are set separately (--driver-memory). A job that calls collect or broadcasts a big table needs a larger driver. Executors that die are replaced (dynamic allocation can also add or remove them), but a dead driver cannot be replaced, so streaming jobs run in cluster mode with a supervisor that restarts the application and recovers from the checkpoint.

Remember: driver plans and schedules, executors compute, cluster manager only lends machines.

What happens, step by step, between calling an action and getting the result? Intermediate

The driver takes the logical plan I built, optimizes it, turns it into a physical plan, and the DAG scheduler cuts it into stages at every shuffle. For each stage the task scheduler creates one task per partition and sends the tasks to executors. Executors run them, write shuffle output or return results, and the next stage starts when the previous one finishes.

The scheduler prefers to put a task on a node that already holds its input block (data locality) to avoid moving data. A failed task is retried, 4 attempts by default. When the last stage completes, the action returns. If I never call an action, none of this happens, which is why a bug in a transformation can surface only at the action.

Walk-through with an example. Take orders.filter(amount > 100).groupBy("country").count().write.parquet(out).

  1. Action. write is the action. Until now only a plan (a tree of operators) existed.
  2. Optimize. Catalyst resolves column names, pushes the amount > 100 filter into the Parquet scan, prunes columns to just amount and country, and picks a physical plan: scan, partial hash aggregate, Exchange (shuffle by country), final hash aggregate, write.
  3. Cut into stages. The DAG scheduler cuts at the Exchange: stage 0 is scan + partial aggregate, stage 1 is final aggregate + write.
  4. Create tasks. If the input has 80 file splits, stage 0 has 80 tasks. Stage 1 has one task per shuffle partition (200 by default, fewer if AQE coalesces).
  5. Schedule. The task scheduler hands tasks to free cores, preferring executors that already hold the data block (locality: process-local, node-local, rack-local, then any). If no local slot frees up in about 3 seconds (spark.locality.wait), it settles for a farther one.
  6. Run and shuffle. Stage 0 tasks write shuffle files to local disk and report their location to the driver. When all 80 are done, stage 1 tasks fetch their slices.
  7. Finish. Stage 1 tasks write the output files and a commit step makes them visible. The driver marks the job done and the action returns.

Failures on the way. A failed task is simply rerun, up to 4 times. If a shuffle file is lost (the executor holding it died), the scheduler reruns the needed tasks of the previous stage. If one task is very slow, speculation (off by default) can launch a duplicate. The Spark UI shows exactly this structure under Jobs, Stages and SQL, which is the first place to look when something is slow.

Remember: action, then plan, then stages at shuffles, then one task per partition.

2. RDD, DataFrame, Dataset and lazy evaluation

RDD vs DataFrame vs Dataset: what is the difference, and which do you use? Basic

An RDD is a distributed collection of plain objects with functions I write, so Spark knows nothing about what is inside. A DataFrame is a distributed table with named, typed columns, so Spark can optimize the plan and store data compactly. A Dataset is a DataFrame with compile-time types (Scala and Java only). I use DataFrames or SQL for almost everything, and drop to RDDs only for unstructured data or custom low-level control.

Because a DataFrame has a schema, Catalyst can push filters into the file scan and prune columns, and Tungsten keeps rows in a compact binary format. An RDD gets none of that and must serialize whole Java objects. In Scala, DataFrame is just Dataset[Row]. Python has only DataFrames.

RDDDataFrameDataset
Schema known to SparkNoYesYes
Catalyst and TungstenNoYesYes (lambdas are opaque)
Compile-time type safetyYesNoYes
LanguagesAllAllScala, Java
Watch out: "Datasets are always better because they are typed" is wrong. A typed lambda like ds.filter(p => p.age > 18) is a black box: Catalyst cannot push it down to Parquet and each row becomes an object first. df.filter("age > 18") can be pushed down.

Why the distinction exists. The RDD was Spark's first API (2010s): a distributed list of objects plus functions you wrote. It is flexible, but Spark cannot see inside your lambda, so it cannot rearrange or skip any work. DataFrames came later with a schema, so Spark knows "this column is an int, that one is a string" and can plan around that.

What the schema buys you, concretely. Take df.select("name").filter("age > 18") over Parquet.

  • Column pruning: only the name and age columns are read from disk.
  • Predicate pushdown: the age filter is checked against Parquet row-group statistics, so whole chunks are skipped.
  • Compact storage: Tungsten stores rows as bytes. An RDD of Java objects holds each row as many small objects with headers and pointers, which costs several times more memory and more garbage collection.

With an RDD of Person objects and rdd.filter(_.age > 18).map(_.name), Spark reads every full row, builds every object, and calls your code. Same answer, much more work.

Where Dataset fits. A Dataset[Person] gives compile-time types: a typo like p.agee fails to compile, while df("agee") fails at run time. The price is that lambdas are opaque and each row must be decoded to an object. A common compromise is to use DataFrame operations for the heavy lifting and convert to a typed Dataset only at the edges.

When I still use an RDD. Truly unstructured data parsed by custom code, fine control over partitioning (partitionBy with a custom partitioner), or legacy code. Even then I try to get to a DataFrame as soon as the data has a shape.

Remember: RDD = objects, DataFrame = table Spark understands, Dataset = DataFrame plus types. Prefer the one the optimizer can see into.

What is lazy evaluation, and what is the difference between transformations and actions? Basic

Transformations such as select, filter, join and groupBy only record what to do. They build a plan and process no data. An action such as count, show, collect or write starts a job. The benefit is that Spark sees the whole plan first, so it can prune columns, push filters into the scan and pick join strategies.

Example: read a 1 TB table, filter one day, take 10 rows. Spark reads only the files for that day. The surprises are that errors in a transformation can appear only when an action runs, and that every action re-runs the plan from the source unless I cache the result. Small exceptions: orderBy is a transformation but triggers a quick sampling job, and cache is lazy while checkpoint is eager.

val x = spark.read.parquet("/data/events")     // plan only
         .filter($"day" === "2026-11-16")       // still nothing
x.count()                                       // job 1 runs now
x.write.parquet("/out/x")                       // job 2: recomputes from scratch

Why it is designed this way. If Spark ran each step the moment you wrote it, it would materialise a full intermediate result after every call (a 1 TB filter output, then a 1 TB select output). By waiting, it can look at the entire chain and execute it as one optimized plan. Think of writing a shopping list versus walking to the shop once per item.

Classification.

Transformations (lazy, return a new DataFrame)Actions (run a job)
select, filter, withColumn, join, groupBy().agg(), union, distinct, repartitioncount, show, collect, take, first, foreach, write, toPandas

What it means in practice.

  • Each action is a separate job that starts from the source. In the snippet above, count() reads and filters the files; write then reads and filters them again. Two actions, double the work. Fix: cache() the result, or restructure so one action does everything.
  • Errors appear late. A wrong column name is caught at analysis time (when you build the DataFrame), but a bad cast or a division by zero in the data appears only when the action runs, possibly deep inside a task on an executor.
  • Debugging. To see what a DataFrame holds, you must run an action: df.show(5), and df.explain() shows the plan without running it.
  • Timing code is misleading. Wrapping a transformation in a timer measures nothing. Time the action.

Not everything is lazy: read with schema inference scans files immediately, spark.sql("create table ...") and similar commands run eagerly, and orderBy/sort runs a small sampling job at plan time to choose range boundaries.

Remember: transformations build the plan, actions run it, and each action recomputes unless cached.

Why is collect() dangerous, and what do you use instead? Basic

collect() pulls every row from all executors into the driver's memory as one local array. With big data the driver runs out of memory or hits spark.driver.maxResultSize (1 GB by default) and the whole job dies, even though the cluster has plenty free. I use show(n), take(n) or limit(n) to look at samples, write to save results, and aggregate first so only a small answer comes back.

toPandas() has the same problem, so apply it only to small aggregated results (and enable Arrow to speed it up). To walk through a large result on the driver without holding it all, toLocalIterator() pulls one partition at a time. Raising driver memory only moves the limit: one machine never scales with the data. Other causes of driver OOM are broadcasting a large table (it passes through the driver), hundreds of thousands of tasks, and a huge plan built in a loop.

Why it fails, step by step. Suppose 200 executors hold 50 GB of results in total. collect() makes every task send its rows to the driver, which deserializes them into one in-memory array. The driver has maybe 4 to 8 GB of heap, so it either exceeds spark.driver.maxResultSize (job aborted with a clear message) or throws OutOfMemoryError (driver dies, application dies). It is a single machine being asked to hold what a cluster held.

What to do for each real need.

I want to...Use
Look at some rowsdf.show(20), df.limit(100).collect()

The rule behind it. The cluster scales with data, the driver does not. If your code does a loop on the driver over a collected result, it is almost always better written as a distributed operation (join, groupBy, window, mapPartitions). A common interview probe: "driver OOM but executors are fine, what do you look at?" Answer: collect/toPandas, a large broadcast, too many tasks (each task result is tracked on the driver), or a very large logical plan built in a loop.

Remember: the driver is one small machine. Reduce on the cluster, write on the cluster, bring back only small results.

What are broadcast variables and accumulators? Intermediate

A broadcast variable sends a read-only value to each executor once, and all tasks on that executor share it. I use it for lookup maps and models. An accumulator is a counter that tasks can only add to and the driver reads, for example the number of bad rows. Accumulator updates are only reliable inside actions. Inside transformations they can be counted twice.

Without broadcast, a variable captured in a closure is copied into every task, so a 200 MB map is sent thousands of times. A broadcast join uses the same mechanism for the small table. Accumulators in transformations over-count because tasks can be retried and stages recomputed, so treat them as approximate metrics, never as business logic.

val lookup = spark.sparkContext.broadcast(countryMap)
val bad = spark.sparkContext.longAccumulator("badRows")
df.foreach { r => if (r.isNullAt(0)) bad.add(1) }   // action: counted once
println(bad.value)

Broadcast variables, in detail. When a function you pass to map uses a local variable, Spark copies it into the serialized task, so every task carries its own copy. With 5,000 tasks and a 200 MB lookup map that is a terabyte of traffic. sc.broadcast(value) sends it once per executor (using a torrent-like transfer between executors, so the driver is not the only sender), stores it in executor memory, and tasks read lookup.value. It is read-only, so there are no consistency problems. Call lookup.destroy() or unpersist() when finished to free memory. In DataFrame code you rarely write this by hand: the broadcast() join hint does it for a table.

Accumulators, in detail. Tasks run in different JVMs, so a plain var count incremented in a lambda changes only a local copy and the driver sees 0. An accumulator is a special variable whose "add" is sent back to the driver and merged. The driver can read .value, tasks cannot.

Why the guarantee is weak. Spark guarantees each task's update is applied exactly once only for updates inside actions (such as foreach). In a transformation (such as map), if the task is retried, if a speculative copy runs, or if the stage is recomputed because the data was not cached, the add happens again. So a "bad rows" counter may show 1,050 for 1,000 bad rows. Fine for monitoring, wrong for logic like "stop if more than 1% bad".

Rule of thumb. Broadcast for read-only data you would otherwise ship repeatedly. For counting inside the pipeline with reliable results, compute it with DataFrame aggregation (count(when(cond, 1))) instead of an accumulator.

Remember: broadcast = ship big read-only data once per executor. Accumulator = write-only counter, trustworthy only in actions.

3. DAG, stages, shuffle and partitioning

What are narrow and wide dependencies (transformations)? Basic

In a narrow transformation each output partition depends on one input partition, so no data moves. map, filter, select and union are narrow. In a wide transformation an output partition needs data from many input partitions, so rows must be redistributed across the network. groupBy, join, distinct, repartition and orderBy are wide. Wide ones cause a shuffle and a new stage.

A chain of narrow steps runs in one pass inside one task. Wide steps are also costlier to recover: a lost output partition needs data from many parents. Two exceptions worth knowing: coalesce is narrow (it merges neighbouring partitions), and a join is not always wide: a broadcast join, or a join of two inputs already partitioned the same way, has narrow dependencies.

The one question to ask. "To compute output partition k, how many input partitions do I need?" If the answer is one (or a fixed small set that lives together), it is narrow. If the answer is "a piece of every input partition", it is wide.

Why it matters.

  • Speed: narrow steps run inside one task on one machine with no network. A chain such as filter, then map, then select becomes one loop over each partition.
  • Stages: every wide dependency forces Spark to wait until all parent tasks finish and the shuffle files exist, so it starts a new stage there.
  • Recovery: if a partition is lost, a narrow child needs one parent partition recomputed; a wide child may need all of them.

Worked example. df.filter(...).select(...).groupBy("k").sum("v").filter("sum(v) > 10"). The first filter and select are narrow. groupBy is wide: the rows for key "A" are spread over all input partitions and must be brought together. The final filter is narrow again. So the job has two stages with one shuffle between.

A subtle point. Wide transformations do a partial aggregation on the map side before the shuffle (so the shuffle carries per-key sums, not raw rows). This is why groupBy().sum() is much cheaper than it looks. Also, union is narrow (it just concatenates partition lists), and coalesce is narrow.

Remember: narrow = stays inside a partition. Wide = rows cross the network = shuffle = stage boundary.

Explain job, stage and task, and how Spark decides how many of each. Basic

Each action creates one job. Spark cuts the job into stages at every shuffle. A stage is a set of tasks, one per partition, all running the same code on different data. So stages are roughly the number of shuffles plus one, and tasks in a stage equal the number of partitions it processes.

Inside a stage all steps are narrow, so a record flows through read, filter and map without being stored between steps (pipelining). A stage starts only after its parent stages have written their shuffle files. Task count for the first stage is the number of input splits (about 128 MB each for files). For later stages it is spark.sql.shuffle.partitions (200 by default) unless AQE merges them. How many tasks run at once is total executor cores. The task is the smallest unit that gets retried. A "skipped stage" in the UI means its shuffle output from an earlier job was reused.

A numbers example. You read 10 GB of Parquet (about 80 splits of 128 MB), filter, group by country, and write. Result:

  • 1 action (write) = 1 job.
  • 1 shuffle (the groupBy) = 2 stages.
  • Stage 0 = 80 tasks (one per input split). Stage 1 = up to 200 tasks (one per shuffle partition), or fewer if AQE merges small ones.
  • With 40 cores in the cluster, stage 0 runs in two waves of 40 tasks (80 / 40), and each task is retried independently if it fails.

Why this model matters for debugging. The Spark UI is organised exactly this way. A slow job becomes "which stage is slow?", then "which tasks in that stage?". If task durations are even, the stage is simply big (add parallelism or reduce work). If one task is far longer than the rest, it is skew. If there are fewer tasks than cores, parallelism is too low.

Common confusions.

  • Several actions mean several jobs, and each re-runs the plan unless data is cached. Skipped stages in the UI show shuffle output being reused from an earlier job.
  • Stages are cut by shuffles, not by the number of transformations. Ten narrow steps are still one stage.
  • Independent stages (for example the two inputs of a join) can run at the same time. A stage that depends on another waits.
  • A task is a unit of failure and retry. A stage failing means a task failed four times, or a shuffle fetch failed repeatedly.

Remember: action = job, shuffle = stage boundary, partition = task.

What is a shuffle, and why is it the expensive part of Spark? Intermediate

A shuffle redistributes data across partitions so rows with the same key end up together, which joins and aggregations need. Each map task writes its rows to local disk grouped by target partition, then each reduce task fetches its slice from every map task over the network. It is expensive because of disk writes, network transfer, serialization of every row, and a barrier: the next stage waits for all map tasks.

The target partition is hash(key) mod numPartitions. With M map tasks and R reduce tasks there are up to M times R small fetches. Shuffle is also where skew, spills and out-of-memory errors show up. The best tuning is to avoid it (broadcast joins, filter early), shrink it (select only needed columns, aggregate before the shuffle) and balance it (sensible partition count, skew handling). In the plan, every Exchange node is a shuffle or a broadcast.

Why a shuffle exists at all. Some operations need all rows of a key in one place. To sum sales per country, every "IN" row, wherever it is stored, must meet at one task. Data is spread by how it was stored, not by key, so rows must be moved. That movement is the shuffle.

The mechanism, with a tiny example. 3 map tasks, 2 reduce partitions, key = country, partition = hash(country) mod 2.

  1. Map task 1 holds rows (IN, 5), (US, 3), (IN, 2). It first combines locally: IN 7, US 3.
  2. It sorts its output by target partition and writes one data file plus one index file. Say IN goes to partition 0 and US to partition 1.
  3. When all map tasks are done, reduce task 0 asks every map output for its slice of partition 0 and fetches them (local ones from disk, remote over the network, handled by the external or built-in shuffle service).
  4. Reduce task 0 merges what it received: IN 7 + IN 4 + ... and produces the final totals.

Where the cost comes from.

CostWhy
SerializationEvery row is turned into bytes and back
DiskMap output is always written to local disk first, so it survives and can be fetched
NetworkUp to M x R fetches; mostly small reads, which hurt on slow disks
BarrierNo reduce task starts until every map task finishes, so the slowest map task sets the pace
MemoryReduce side sorts or aggregates in memory and spills if it does not fit

What an interviewer probes next. "How do you tell a shuffle is the problem?" Stage page: large Shuffle Write and Shuffle Read, spill, fetch-wait time. "How do you cut it?" Less data (filter and select first), map-side combine, broadcast joins, fewer wide operations chained, bucketing. "What if a shuffle file is lost?" The map stage is rerun for that part, which is why executor loss late in a job hurts (and why an external shuffle service or dynamic allocation with shuffle tracking matters).

Remember: shuffle = disk + network + serialization + a wait. Fewer, smaller, balanced shuffles.

Which operations cause a shuffle, and how do you avoid or reduce them? Intermediate

Shuffles come from groupBy, join (except broadcast), distinct, repartition, orderBy, window functions with partitionBy, and intersect or except. I reduce them by filtering and selecting columns before the shuffle, broadcasting the small side of a join, aggregating on the map side, and using bucketed tables for joins I do often.

Prefer aggregations that combine partially before shuffling (DataFrame agg, RDD reduceByKey) over ones that ship every value (groupByKey). Chain operations on the same key so Spark shuffles once, not three times. Do not stack distinct and groupBy on the same key. Check the result with df.explain() and count the Exchange nodes.

Go through them by reason. Operations that need rows with the same key together: groupBy, join, distinct (it is a group by all columns), window with partitionBy, intersect, except. Operations that reorder globally: orderBy. Operations whose job is to move data: repartition. A plain select, filter, withColumn, union never shuffle.

Reduction tactics with examples.

  1. Filter and select first. Fewer rows and narrower rows mean smaller shuffle files. Catalyst often does this for you, but not across UDFs or when you write the filter after a join of two derived tables.
  2. Broadcast the small side of a join: zero shuffle for the big table.
  3. Aggregate before joining. If you join 1 billion events to a table and then sum per user, aggregate events per user first (maybe 10 million rows), then join.
  4. Reuse one partitioning. If you do groupBy("user") and then a join on "user", Spark can often reuse the first partitioning and skip the second shuffle when the plan allows it. Chaining operations on the same key helps.
  5. Bucket both tables on the join key (details in the bucketing question) for joins you run daily.
  6. Avoid unnecessary repartition, distinct, orderBy: a global sort just to write sorted output is an expensive shuffle.

How to prove it. Run df.explain() before and after. Each Exchange hashpartitioning(...) or Exchange rangepartitioning(...) is a shuffle. BroadcastExchange is a broadcast, not a shuffle of the big side. In the SQL tab of the UI the "data size total" on each Exchange node shows how many bytes moved.

Remember: filter early, select few columns, broadcast small tables, combine before you shuffle.

Why is reduceByKey preferred over groupByKey? Intermediate

reduceByKey applies the combine function inside each map partition first, so each map task sends at most one record per key across the network. groupByKey sends every single (key, value) pair and builds the full list of values for each key in memory, which is slow and can run a task out of memory on a hot key.

It is the same idea as a Hadoop combiner. A word count over a billion words ships one count per word per partition instead of a billion pairs. The combine function must be associative and commutative, because partial results merge in any order. DataFrame groupBy().agg(sum(...)) already does partial aggregation, so the problem mostly exists in the RDD API. Use aggregateByKey when the result type differs from the value type, and groupByKey only when you truly need all values together.

Tiny example. Word count over 3 partitions. Partition 1 holds [a, a, a, b], partition 2 holds [a, b, b], partition 3 holds [a, a].

  • groupByKey: sends all 9 pairs across the network. The reducer for "a" receives six 1s from three machines, builds the list [1,1,1,1,1,1] in memory, then sums it.
  • reduceByKey(_ + _): each partition first merges its own pairs: (a,3),(b,1) | (a,1),(b,2) | (a,2). Only 5 pairs travel. The reducer adds 3 + 1 + 2.

Now scale to a billion words with 20,000 distinct words and 1,000 partitions: groupByKey ships a billion records, while reduceByKey ships at most 20,000 x 1,000 = 20 million.

Why memory also matters. groupByKey builds the entire value list per key on one task. If a key has a hundred million values, that task runs out of memory, which is a classic cause of "executor OOM on a hot key". reduceByKey keeps only a running accumulator per key.

Which function to pick.

NeedUse
Sum, max, min, count, where the result type equals the value typereduceByKey

Truly need every value (rare)groupByKey, carefully
You are using DataFramesgroupBy().agg(...); the optimizer already does the partial aggregation

Edge case. Not every aggregate can combine partially. collect_list, percentile_approx (uses sketches, so it can), and exact median cannot be merged trivially; for those, expect more data in the shuffle and more memory per key.

Remember: combine on the map side first. reduceByKey ships summaries, groupByKey ships everything.

What are partitions, and how many should you have? Intermediate

A partition is a chunk of data processed by one task. My target is two to four partitions per CPU core in the cluster, each around 100 to 200 MB after a shuffle. Too few means idle cores and big tasks that spill or run out of memory. Too many means tiny tasks where scheduling overhead dominates and lots of small output files.

For file input, Spark makes partitions of about spark.sql.files.maxPartitionBytes (128 MB), so 10 GB of Parquet gives roughly 80 partitions. After a shuffle the count is spark.sql.shuffle.partitions (default 200). That default is wrong at both ends: 200 tiny tasks for a small job, and 5 GB per task for a 1 TB shuffle. With AQE on, set the number high and let it coalesce small partitions. Check actual sizes in the stage page of the UI (min, median, max of shuffle read).

df.rdd.getNumPartitions
spark.conf.set("spark.sql.shuffle.partitions", "800")

Where partitions come from. Reading files: Spark packs file bytes into splits of up to maxPartitionBytes (128 MB); several small files can share one partition. After a shuffle: spark.sql.shuffle.partitions. After repartition(n) or coalesce(n): n. From a JDBC read without options: 1. From Kafka: one per topic partition.

Why 100 to 200 MB. Think of each task as needing working memory about the size of its partition (often 2 to 3 times more once rows are decoded and sorted). With 4 GB of execution memory shared by 4 running tasks, each has about 1 GB, so partitions of 100 to 200 MB fit comfortably. Much bigger and tasks spill to disk or fail. Much smaller (say 1 MB) and the scheduler spends more time launching tasks than the tasks spend working (each task costs on the order of tens of milliseconds of overhead).

Worked example. A 1 TB shuffle on a cluster with 400 cores.

  • Default 200 partitions: 5 GB per task. Tasks spill heavily or crash, and only 200 of 400 cores are used.
  • Set to 8,000: about 128 MB per task, 20 waves of 400 tasks. Healthy.
  • Set to 80,000: about 12 MB per task, big scheduling and shuffle-fetch overhead (80,000 x 80,000 fetch pairs).

Both ends of the failure. Too few: idle cores, spills, OOM and long single tasks. Too many: scheduler overhead, many tiny output files, and many small shuffle fetches. With AQE (on by default from 3.2) I set the initial count generously (or via spark.sql.adaptive.coalescePartitions.initialPartitionNum) and AQE merges small neighbours to the advisory size, so the setting becomes "high enough", not "exactly right".

Remember: aim for 100 to 200 MB per partition and a few partitions per core. 200 is a default, not an answer.

repartition vs coalesce: what is the difference, and when do you use each? Basic

repartition(n) does a full shuffle and gives n evenly sized partitions. It can increase or decrease the count and can partition by a column. coalesce(n) only decreases the count by merging neighbouring partitions without a shuffle, so it is cheap but can leave uneven sizes. I use coalesce to reduce output files when data is already balanced, and repartition when I need more partitions, even sizes, or to partition by a key.

A classic trap: coalesce(1) on a big job pulls the whole upstream computation into one task, so everything before it runs on one core. repartition(1) keeps the earlier steps parallel and only the last step is single. Related: repartitionByRange splits by sampled value ranges, which gives sorted-across-partitions output.

Why two calls? Reducing partitions is a common need (fewer output files) and it is often possible without moving data, so Spark offers a cheap method for that case. Doing a full shuffle for every change would be wasteful.

How each works. coalesce(2) on 4 partitions simply assigns P1+P2 to one task and P3+P4 to another. There is no hash, no network, but the new partitions are as uneven as the old ones (if P1 was 10x bigger, the merged partition stays big). repartition(2) hashes (or round-robins) every row to one of 2 new partitions through a shuffle, so sizes come out even, at the cost of moving all the data.

The classic trap, explained. Because coalesce has no shuffle boundary, Spark pipelines everything above it into the same tasks. So df.heavyJoin().coalesce(1).write... runs the whole heavy computation in one task, on one core. repartition(1) adds a stage boundary: the heavy work stays parallel, then one task writes. If you need a single output file, that is usually the right trade.

Other uses. repartition(col) before partitionBy(col) on write avoids a tiny file from every task for every value (see the small files question). repartitionByRange(n, col) gives sorted ranges, useful before writing sorted data. In SQL, the REBALANCE hint lets AQE size the partitions for you.

Remember: coalesce glues (no shuffle, only fewer). repartition rebuilds (shuffle, any number, even).

What is data skew, and how do you detect and fix it? Senior

Skew means a few keys (a null, "unknown", one huge customer) have far more rows than the rest, so one task gets most of the data and runs for an hour while the others finish in seconds. I detect it in the Spark UI by comparing the max task time and shuffle read against the median. I fix it with AQE skew-join handling, by filtering junk keys, by broadcasting, or by salting.

Fixes in order of effort: (1) turn on AQE skew join (Spark 3.x), which splits oversized partitions of a sort-merge join automatically. (2) Filter or separately handle nulls and default values, which are often junk and never match in an inner join. (3) Broadcast the small side so there is no shuffle. (4) Salt the hot key (next question). (5) Pre-aggregate before the join. (6) Process hot keys with a broadcast join and the rest normally, then union. To find the hot key: groupBy(key).count().orderBy(desc).

Why skew hurts so much. A stage finishes when its slowest task does. If 199 tasks take 10 seconds and one takes 45 minutes, the job takes 45 minutes and 199 cores sit idle. Adding machines changes nothing. Skew also causes the worst memory failures, since that one task may hold more data than fits.

How it arises. Hash partitioning sends all rows with the same key to the same task. If one key (null, "unknown", a default id, a very large customer or a bot user) holds 30% of the rows, that task gets 30% of the data. It is not a bug in Spark; it is how key grouping works.

Detecting it.

  1. Spark UI stage page: the summary table shows min, 25th, median, 75th and max of task duration and shuffle read. Max far above the median means skew.
  2. Find the culprit key: df.groupBy("key").count().orderBy(desc("count")).show(10).
  3. Check for nulls first; they are the most common hot key.

Fixes, with the reasoning.

FixWhen it fits

Isolate hot keysA few known keys: broadcast-join those, normal join the rest, union
SaltingAQE cannot help (aggregations, outer joins on the skewed side)

Pitfalls. Speculative execution does not help, since the copy gets the same big partition. Raising executor memory only delays the crash. Skewed aggregations (not joins) are not fixed by AQE's skew-join feature, so you salt them in two steps: aggregate by (key, salt), then by key.

Remember: a stage lasts as long as its slowest task. Skew is about the longest bar, not the average.

How does salting a skewed join work? Senior

I add a random number from 0 to N-1 (the salt) to each row of the big table, copy each row of the small table N times, once per salt value, and join on the key plus the salt. The hot key's rows now spread over N different partitions, and each still finds its match. The cost is that the small side grows N times, so I replicate only the hot keys if I can.

Pick N from the size of the hot key, often 10 to 50. AQE does something similar automatically for sort-merge joins, so I use salting when AQE cannot help, for example for skewed aggregations (aggregate by key plus salt first, then by key again) or full outer joins.

val N = 16
val bigS   = big.withColumn("salt", (rand() * N).cast("int"))
val smallS = small.withColumn("salt", explode(array((0 until N).map(lit): _*)))
val joined = bigS.join(smallS, Seq("customer_id", "salt")).drop("salt")
Watch out: salting both sides randomly (rows no longer match), forgetting to drop the salt, and replicating the whole small table when only a few keys are hot.

The idea in plain words. The problem is that one key means one task. Salting makes the key less unique on purpose: rows for the hot key "ACME" become "ACME#0", "ACME#1", ... "ACME#15", which hash to 16 different tasks. To keep the join correct, the other side must also have all 16 variants so every salted row still finds its match.

Worked example. big has 100 million rows, 40 million of them for customer "ACME". small has one row per customer. With N = 16:

  1. Each big row gets a random salt 0..15. ACME's 40 million rows spread to about 2.5 million per salt value.
  2. Each small row is exploded into 16 copies, one per salt. ACME's single row becomes 16 rows.
  3. Join on (customer_id, salt). Each ACME salt group is a separate partition holding 2.5 million big rows and 1 small row.
  4. Drop the salt column from the result.

The big table's total work is unchanged; it is just spread. The small table grows 16 times (cheap if it is small, expensive if it is not).

Salting an aggregation. Aggregations are easier because nothing needs replicating: first groupBy(key, salt).sum(v), then groupBy(key).sum(sum_v). The first step spreads the hot key; the second combines 16 partial sums per key, which is tiny. This works for sum, count, min, max. Averages need sum and count carried separately.

Salting only the hot keys. To avoid growing the whole small table, use salt N only for keys known to be hot and salt 0 (a single copy) for all others, via when(col in hotKeys, rand*N).otherwise(0) on the big side and an exploded set only for hot keys on the small side. More code, much less data.

Choosing N. Aim for hot-key rows divided by N to be near a normal partition size. Too small leaves skew, too big wastes replication and shuffle. Check with the UI after the change; the longest task should now be close to the median.

Remember: spread the hot key on the big side, replicate the other side across all salts.

What is Adaptive Query Execution (AQE) and what does it do? Intermediate

AQE re-plans the query while it runs, using the real sizes of the shuffle output instead of estimates made before the job started. It does three main things: it coalesces many small shuffle partitions into fewer, switches a sort-merge join to a broadcast join when one side turns out small, and splits skewed partitions in a join. It arrived in Spark 3.0 and is on by default from 3.2.

After each shuffle stage finishes, Spark has exact statistics, so it can re-optimize the rest of the plan. Coalescing aims at spark.sql.adaptive.advisoryPartitionSizeInBytes (64 MB by default), so I can set a high shuffle partition count and not worry. Skew handling splits a partition that is above 5 times the median and above 256 MB (skewedPartitionFactor and skewedPartitionThresholdInBytes). It helps SQL and DataFrame queries with a shuffle, not RDD code, and it does not fix skewed aggregations. In the UI the SQL tab shows AdaptiveSparkPlan.

The problem AQE solves. Before a query runs, Spark must guess sizes from table statistics, and the guess is often wrong: after a filter and a join, "this side is about 5 GB" might really be 8 MB, or one partition might hold a hot key. The static plan, including 200 shuffle partitions, is fixed up front. AQE waits: shuffle stages are materialised, their real sizes are known, and the plan for the remaining stages is rebuilt.

The three features, each with an example.

  1. Coalescing shuffle partitions. You set 2,000 shuffle partitions to be safe, but a stage outputs only 3 GB. Instead of 2,000 tiny tasks, AQE merges neighbouring partitions up to the 64 MB advisory size, giving about 50 tasks.
  2. Join strategy switch. The plan said sort-merge join because the estimate for the right side was 2 GB. After the filter below it actually produced 6 MB. AQE converts the join to a broadcast hash join at run time. The big side's shuffle may already have been written by then, but the sort and the network fetch of the big side are saved (it is read locally), and the rest of the plan benefits from the cheaper join.
  3. Skew join. After the shuffle, a partition of 5 GB against a median of 80 MB is split into smaller pieces, each joined with a copy of the matching other-side partition, so many tasks share the hot key.

Key settings. spark.sql.adaptive.enabled, coalescePartitions.enabled, skewJoin.enabled, advisoryPartitionSizeInBytes, and autoBroadcastJoinThreshold (AQE applies it to the real sizes it measured).

Limits to mention. It only reacts at shuffle boundaries, so a query with no shuffle gets nothing. Skew handling applies to joins, not aggregations. In practice streaming micro-batches typically do not get AQE. Plans in explain look like AdaptiveSparkPlan isFinalPlan=false before the run, and the final plan is visible in the UI SQL tab after.

Remember: AQE = re-plan after each shuffle with real sizes: coalesce, switch to broadcast, split skew.

4. Joins

What join strategies does Spark have, and how does it choose one? Intermediate

For equality joins Spark picks a broadcast hash join if one side is under the threshold (10 MB by default), which avoids shuffling the big side. Otherwise it uses a sort-merge join, which shuffles and sorts both sides and scales to any size. A shuffle hash join sits in between: shuffle both sides, then hash the smaller one in each partition. For non-equality conditions it falls back to a slow nested loop or cartesian join.

Broadcast is the fastest, but the small side must fit in memory on the driver and every executor. Shuffle hash join is used when one side is much smaller but too big to broadcast; it needs memory for the hash table, so Spark prefers sort-merge by default (spark.sql.join.preferSortMergeJoin is true). I can force a choice with hints: broadcast(df) or SQL /*+ BROADCAST(t) */, SHUFFLE_HASH, MERGE. I confirm the choice with explain.

Understand each strategy as a trade.

StrategyHow it worksNeedsCost
Broadcast hash joinCopy the small table to every executor, build a hash map, stream the big table past itSmall side fits in memory everywhereNo shuffle of the big side; fastest
Sort-merge joinShuffle both sides by key, sort each partition, merge the two sorted streamsEquality condition, sortable keysTwo shuffles and two sorts; robust, can spill
Shuffle hash joinShuffle both sides, build a hash map of the smaller side in each partitionSmaller side's partition fits in memoryTwo shuffles, no sort

The selection logic in order. Spark first looks for a hint on either side (broadcast, merge, shuffle_hash, shuffle_replicate_nl). With no hint, if the condition is an equality and one side is estimated under autoBroadcastJoinThreshold, it broadcasts. Otherwise for equality it uses sort-merge (shuffle hash only if you set preferSortMergeJoin=false, or AQE judges a side small enough per partition). Non-equality conditions need a nested loop and Spark broadcasts one side if it can.

Which side may be broadcast. For an inner join either side. For a left outer join only the right side can be broadcast, because the left side's unmatched rows must be preserved by whichever task owns them. Right outer: only the left side. Full outer: neither (in common versions).

Practical advice. Look at explain and trust it over memory of the rules. If a join you expect to broadcast does not, check that statistics exist (table stats, or the source is a file with known size) and that the estimate is under the threshold. Raise the threshold carefully (100 to 500 MB is common on large executors) and watch driver memory. Use a hint for derived tables whose size Spark cannot estimate well.

Remember: small side, broadcast. Two big sides, sort-merge. Non-equality, slow nested loop.

How do you join a huge table with a small one, and what can go wrong with a broadcast join? Intermediate

I use a broadcast join. Spark collects the small table to the driver, sends it to every executor, and each task joins its slice of the big table locally, so the big table is never shuffled. First I shrink the small table: select only needed columns and filter rows. Then I check explain shows BroadcastHashJoin, and use the broadcast() hint if Spark did not choose it.

What can go wrong: the table is bigger in memory than on disk (compressed Parquet can expand several times), so the driver or executors run out of memory. The build takes longer than spark.sql.broadcastTimeout (300 s) because the small side is itself a slow query. Or statistics are missing so Spark does not broadcast when it could (run ANALYZE TABLE ... COMPUTE STATISTICS). In an outer join only the non-preserved side can be broadcast, for example the right side of a left outer join. If the table is too big, fall back to a shuffle hash hint or bucketing.

import org.apache.spark.sql.functions.broadcast
val out = orders.join(broadcast(countries), Seq("country_code"), "left")
out.explain()   // look for BroadcastHashJoin

Walk through a broadcast join. Big table: 2 billion orders. Small table: 50,000 countries.

  1. Spark runs the small side's plan and collects the result to the driver.
  2. The driver turns it into a hash map in memory and broadcasts it to every executor (executors share it among their tasks).
  3. Each task on the big side reads its partition of orders and looks up each row in the local hash map. No row of the big table leaves its machine.
  4. Output rows are produced in place, so the big side needs no shuffle and no sort.

Failure modes explained.

  • Driver or executor OOM: a 100 MB Parquet file can expand to 1 GB as decoded rows plus a hash table, and the driver holds it too while collecting. Symptoms: OutOfMemoryError on the driver during the broadcast, or on executors.
  • Timeout: the default spark.sql.broadcastTimeout is 300 seconds. If the small side comes from a slow subquery or a busy database, the build can time out. Cache or materialise it first.
  • Table too big for the threshold: if you force a broadcast of a table that is really 5 GB, it will either fail or cause heavy network traffic since 5 GB goes to each executor.
  • Missing statistics: Spark cannot know a table's size without stats (or a known file size), so it falls back to sort-merge. Fix with ANALYZE TABLE t COMPUTE STATISTICS or add the hint.
  • Wrong side for outer joins: broadcasting the preserved side is not supported, so the hint is ignored and Spark picks another strategy.

Making the small side smaller. select only the join key and needed columns, filter rows out, and deduplicate. A two-column lookup table is far smaller than the 40-column dimension.

If it is too big to broadcast but still much smaller than the other side: try the shuffle-hash hint (avoids sorting the big side), bucket both tables, or filter the big side first (semi-join with the keys of the small side).

Remember: broadcast removes the big-side shuffle. Shrink first, and watch driver and executor memory.

How does a sort-merge join work, and why is it the default for big tables? Intermediate

Both inputs are shuffled so equal keys land in the same partition, then each partition is sorted by the key. A task walks through the two sorted streams together, like merging two sorted lists, and emits the matches. It needs only a few rows in memory at a time and the sort can spill to disk, so it does not fail on memory the way a hash join can. That is why it is the default for two large tables.

The costs are two shuffles and two sorts. If both tables are bucketed and sorted by the join key with the same bucket count, Spark skips the shuffle and sort entirely. The join is sensitive to skew, because all rows of one key must meet in one task. Shuffle hash join beats it when one side is much smaller, since it avoids sorting the large side, but that hash table must fit in memory per partition.

Why sorting makes joining cheap in memory. If both inputs are sorted by key, you only need to look at the current row on each side, like merging two sorted decks of cards. You never have to hold a whole side in a hash table.

Steps, with a mini example. Orders has key values [1,1,2,5] in a partition, customers has [1,2,3,5] in the same partition.

  1. Shuffle: both sides are hash-partitioned by the join key into the same number of partitions, so a given key exists in one partition for each table.
  2. Sort: within each partition, each side is sorted by key (external sort that can spill to disk).
  3. Merge: two pointers move forward. Key 1 on both: output the 2 order rows times 1 customer row. Then 2 matches. 3 exists only on the right, so an inner join skips it. 5 matches. Pointers never go back, except to replay a group of equal keys.

Why it is robust. Memory use is bounded by the largest group of equal keys, not by table size, and sorting spills. This is why Spark prefers it over hash joins: hash joins can fail with out-of-memory when a partition's hash table is too big.

Costs and when to avoid. Two full shuffles and two sorts are slow for big data. It suffers from skew because one key's rows must meet in one task. Avoid by broadcasting a small side, or by bucketing both tables by the key with the same bucket count (and sorting them): then Spark sees matching distribution and ordering, and the plan has no Exchange or Sort. In explain look for SortMergeJoin with Sort and Exchange children.

Remember: shuffle, sort, merge. Slow but safe for any size, and bucketing can remove the first two steps.

What common join mistakes give wrong results or blow up the data? Intermediate

The big ones are duplicate keys, null keys, filtering after an outer join, and a missing join condition. Duplicate keys on both sides multiply rows (many-to-many), so a join that should give a million rows can give a billion. Null never equals null in SQL, so null keys are dropped in an inner join. A WHERE filter on the right side after a left join silently turns it into an inner join. A missing condition gives a cartesian product.

My habits: check key uniqueness with groupBy(key).count() before joining. Use the null-safe operator <=> (eqNullSafe) if nulls should match. Put right-side filters of an outer join in the ON condition, not in WHERE. Join on Seq("id") to avoid two columns with the same name. Since Spark 3.0 implicit cartesian products are allowed by default, so Spark will not stop me, and I look for CartesianProduct in the plan. For "exists" and "not exists" checks I use left_semi and left_anti joins, which return only left columns and never multiply rows.

The mistakes, each with a concrete case.

  1. Duplicate keys multiply rows. If an order id appears twice in payments (a retry), joining orders to payments gives two rows per order and the revenue sum doubles. Cause: the key was assumed unique but is not.
  2. Null keys never match. null = null is unknown, not true, so rows with a null key disappear in an inner join and get no match in a left join. If nulls should match, use a.k <=> b.k (null-safe equality) in SQL or eqNullSafe in the API.
  3. Filter after outer join. orders LEFT JOIN returns r ON ... WHERE r.status = 'ok' drops every order with no return, since the unmatched side is null and the filter rejects null. It behaves like an inner join. To keep the left rows, move the condition into the ON clause.
  4. Missing condition gives a cartesian product. 1 million rows by 1 million rows is 10^12 combinations. Check the plan for CartesianProduct or BroadcastNestedLoopJoin.
  5. Ambiguous columns. After a.join(b, a("id") === b("id")) there are two id columns, and selecting id fails or picks wrongly. Join on Seq("id") to get one.
  6. Join type choice. "Rows in A that have a match in B" is left_semi (no duplication even if B has many matches). "Rows in A with no match in B" is left_anti. Both return only A's columns and are cheaper than join-then-filter or NOT IN (which has dangerous null behaviour: if the subquery returns any null, NOT IN returns nothing).

Defensive habits. Check count(*) versus count(distinct key) on the side that should be unique, and compare row counts before and after a left join: for a left join with a unique right side, the counts must match.

Remember: before a join ask "is the key unique, and what about nulls?". Use semi and anti joins for exists checks.

What is bucketing, and how is it different from partitioning? Senior

Partitioning (partitionBy("date")) splits a table into folders by column value, so queries that filter on that column skip whole folders. Bucketing (bucketBy(64, "user_id")) hashes a column into a fixed number of files, so two tables bucketed the same way on the join key can be joined with no shuffle. Partition for filters on low-cardinality columns, bucket for repeated joins and aggregations on a high-cardinality key.

The catches with bucketing: it needs a metastore table (saveAsTable), every writer must respect the same bucket spec and count, and it can create many small files (buckets times write tasks). Many teams now rely on table formats (Iceberg, Delta) with their own layout features such as hidden partitioning and clustering instead.

df.write.bucketBy(64, "user_id").sortBy("user_id").saveAsTable("events_b")

Start from the problem. A sort-merge join shuffles both tables every time it runs. If you join events to users on user_id daily, that is the same shuffle, repeated, forever. Bucketing pays that shuffle once, at write time.

How it works. bucketBy(64, "user_id") assigns each row to bucket hash(user_id) mod 64 and writes each task's rows into per-bucket files (optionally sorted within the file with sortBy). The bucket spec is stored in the metastore. When Spark joins two tables bucketed the same way (same column and the same bucket count; newer versions can optionally coalesce counts that are multiples of each other), it knows bucket k of one table matches bucket k of the other, so it joins them pairwise with no Exchange, and if they are also sorted, no Sort either. It also helps groupBy(user_id), distinct and window functions on that column.

partitionBybucketBy

They combine: partitionBy("date").bucketBy(64, "user_id") gives date pruning plus bucket joins within each date.

Costs. Writing is slower (a shuffle and sort at write time). Every writer must use the same bucket count and hash or the benefit silently disappears. Choosing the count is awkward: too few gives big buckets, too many creates many small files (files = write tasks x buckets, unless you repartition by the bucket column first). Reading is only faster when the join key matches the bucket column. Because of these frictions, many teams use broadcast joins and AQE and reserve bucketing for a few big, stable, repeatedly joined tables.

Remember: partitioning prunes folders for filters. Bucketing pre-shuffles files for joins.

5. Optimizer, serialization, UDFs and windows

What is the Catalyst optimizer? Walk me through the phases. Intermediate

Catalyst is Spark SQL's rule-based query optimizer. My SQL or DataFrame code is parsed into a logical plan, analyzed (table and column names resolved against the catalog), optimized by rewrite rules, and then turned into a physical plan with a chosen join strategy, and finally into generated Java code. Because it sees the whole plan, it can push filters down and read fewer columns.

The key rewrites are predicate pushdown (filter at the file scan, using Parquet statistics), column pruning (read only needed columns), constant folding, combining filters and projections, and join reordering. "Column not found" errors come from the analysis phase. In Spark 3, AQE adds a run-time re-optimization step. The filter and join order I write usually does not matter for DataFrames, because Catalyst reorders, except around opaque UDFs. See the plans with df.explain("formatted").

Why an optimizer at all. You write what you want ("revenue per country for last week"), not how. Many different execution plans give the same answer, and some are 100 times cheaper. Catalyst searches for a cheaper equivalent plan using rewrite rules, the way a database optimizer does.

The phases with an example. Query: SELECT country, sum(amount) FROM orders JOIN users USING(user_id) WHERE day = '2026-11-16' GROUP BY country.

  1. Parse: text becomes an unresolved tree. Names such as orders and amount are just strings.
  2. Analysis: looks names up in the catalog, attaches types, resolves amount to orders.amount. Typos fail here ("cannot resolve column").
  3. Logical optimization: rules rewrite the tree. The day filter is pushed below the join, straight to the scan of orders. Unused columns are dropped (column pruning). Constants are folded (1 + 2 becomes 3). Adjacent filters or projections are merged.
  4. Physical planning: turns logical operators into concrete ones and chooses strategies: broadcast hash join versus sort-merge, hash aggregate versus sort aggregate. A cost model uses table statistics when available.
  5. Code generation: chains of operators in one stage are compiled into a single Java function (Tungsten, see below).

What it cannot see through. A UDF, a typed lambda or mapPartitions is a black box: Catalyst cannot push filters across it, drop columns it uses, or reorder around it. That is why built-in functions are preferred.

Statistics matter. Join choices and reordering use table and column statistics (ANALYZE TABLE ... COMPUTE STATISTICS FOR COLUMNS) when cost-based optimization is enabled. Without them, Spark estimates from file sizes. AQE then corrects the estimates at run time.

To see all stages: df.explain(true) prints parsed, analyzed, optimized logical and physical plans.

Remember: parse, analyze, optimize (pushdown, pruning), plan physically, generate code.

How do you read an explain plan to find a performance problem? Senior

I read it from the bottom up: the bottom is the scan, the top is the result. I check four things: the scan for pushed filters and only the columns I need, the Exchange nodes (each is a shuffle or broadcast), the join type, and any opaque nodes such as Python UDFs. Then I confirm with real row counts and times in the SQL tab of the UI.

  • Scan: PartitionFilters, PushedFilters and ReadSchema should show my filters and columns. A missing partition filter means a full scan, often because I wrapped the partition column in a function.
  • Exchange: count them and ask if each is needed.
  • Join: SortMergeJoin where I expected a broadcast means missing statistics or a big small-side.
  • Opaque nodes: BatchEvalPython (Python UDF) or a typed lambda breaks whole-stage code generation. Fused operators are marked with a star *.
df.explain("formatted")                  // Spark 3.0+: readable, numbered nodes
spark.sql("EXPLAIN COST SELECT ...")      // adds statistics

How to read one. A physical plan is a tree printed with the final operator on top and the scans at the bottom. Data flows upward, so read from the bottom. Short sample:

== Physical Plan ==
*(2) HashAggregate(keys=[country], functions=[sum(amount)])
+- Exchange hashpartitioning(country, 200)
   +- *(1) HashAggregate(keys=[country], functions=[partial_sum(amount)])
      +- *(1) Project [country, amount]
         +- *(1) Filter (day = 2026-11-16)
            +- FileScan parquet [country,amount,day]
                 PartitionFilters: [day = 2026-11-16], PushedFilters: [], ReadSchema: struct<country,amount>

Reading it bottom up: scan reads only 3 columns and, thanks to PartitionFilters, only that day's folder. A partial aggregate runs in stage 1, then one Exchange (the single shuffle) by country, then the final aggregate in stage 2. The *(1) and *(2) are whole-stage codegen groups, which map to stages.

Red flags and what they mean.

  • Empty PartitionFilters on a partitioned table: full scan (function around the partition column, or wrong column).
  • Empty PushedFilters: the filter could not go to the file reader, e.g. it uses a UDF, a cast, or a complex expression.
  • ReadSchema with many columns: something upstream selects everything, or a UDF takes the whole row.
  • SortMergeJoin where one side is tiny: missing statistics or a broadcast hint needed.
  • Many Exchange nodes: redundant shuffles, such as distinct after groupBy on the same key.
  • BatchEvalPython / ArrowEvalPython: Python UDF stage; code generation is broken at this point.
  • CartesianProduct / BroadcastNestedLoopJoin: missing equality condition.

Plan versus reality. The plan shows intent. The SQL tab of the UI adds actual row counts and sizes per node, which tells you where a join exploded or a filter did not filter. With AQE the final plan only exists after the run.

Remember: scan filters, Exchange count, join type, opaque nodes. Bottom up.

What is Tungsten, and what is whole-stage code generation? Senior

Tungsten is the engine-level speed work behind DataFrames. It stores rows as compact binary bytes instead of Java objects, which cuts memory and garbage collection, and it uses whole-stage code generation: Spark generates one tight Java loop for a chain of operators (scan, filter, project, aggregate) instead of calling one operator after another per row. That gives several times speedup on CPU-bound work.

The older "Volcano" style makes a virtual function call per operator per row. The generated code keeps values in CPU registers and avoids that. It also explains why Python UDFs and typed lambdas are slow: they break the generated code and force each row to be converted to an object. Off-heap memory is optional (spark.memory.offHeap.enabled), the binary format works on-heap too.

Two problems it fixes. (1) Java objects are bloated. A row of three fields as Java objects can cost over 100 bytes with headers, pointers and boxing; as packed bytes it needs maybe 30. More objects also means more garbage collection. (2) The classic row-at-a-time "Volcano" model chains operators with virtual calls: each row asks the filter for the next row, which asks the scan, and so on. Per-row call overhead dominates when the real work is a comparison.

What Tungsten does.

  • Binary row format (UnsafeRow): fields are laid out in a byte array with a null bitmap. It can be compared and hashed directly, with no deserialization, and can live on-heap or off-heap.
  • Cache-friendly algorithms: hash maps and sorts that work on the binary data and pack keys and pointers together so the CPU cache is used well.
  • Whole-stage code generation: Spark writes one Java method for a whole stage of narrow operators, compiles it at run time (with Janino), and runs a tight loop like a hand-written one.

Mini picture. For scan, filter age > 18, project name, the generated code is essentially while (scan.hasNext()) { row = scan.next(); if (row.age > 18) output(row.name); }. No intermediate objects, no per-operator calls.

How you see and break it. In explain, operators prefixed by *(n) are in a code-generated stage. A Python UDF, an RDD conversion or a typed lambda breaks the chain, because the data has to be turned into objects. Very wide plans (hundreds of columns or deeply nested expressions) can exceed the JVM method size limit, and Spark then falls back to the slower interpreted path for that stage. A vectorised Parquet reader and columnar caches are related ideas for scanning many values per call.

Remember: Tungsten = binary rows + one generated loop per stage. Opaque code breaks the loop.

What does "Task not serializable" mean, and what is Kryo for? Intermediate

Spark must serialize the function I pass to a transformation and send it to executors. "Task not serializable" means that function captured something that cannot be serialized: a database connection, a logger, or the enclosing class through this. I fix it by creating such objects inside mapPartitions (once per partition on the executor), by copying the needed field into a local variable, or by using a standalone object. Kryo is a faster, more compact serializer for RDD data and shuffles.

Serialization matters for shuffles, broadcasts, closures and cached serialized data. Java serialization is the default for RDDs: flexible but slow and bulky. Kryo (spark.serializer=org.apache.spark.serializer.KryoSerializer) is typically much faster and smaller, and I register my classes. DataFrames and Datasets use Tungsten's own binary encoders for row data, so Kryo matters less there. A lambda that uses a class field captures the whole class, which is the usual cause of the error.

rdd.mapPartitions { it =>
  val conn = Db.connect()           // created on the executor, once per partition
  try it.map(r => lookup(conn, r)).toList.iterator finally conn.close()
}

Why serialization appears everywhere. Spark runs your code on other machines, so anything that crosses a machine boundary is turned into bytes: (a) the function you pass to map and everything it references (the closure), (b) shuffled records, (c) broadcast values, (d) cached data in serialized form, (e) results returned to the driver.

What "Task not serializable" really says. Spark tried to serialize your closure and found an object inside it that is not java.io.Serializable. Typical culprits:

  • A JDBC connection, HTTP client, or logger captured from the driver. These hold sockets and cannot be copied to another machine anyway.
  • A method call or field access inside a class: rdd.map(x => x * factor) where factor is a field captures this, the whole outer object, including its non-serializable members.

Fixes, in order of preference.

  1. Copy needed fields to local values first: val f = this.factor; rdd.map(_ * f).
  2. Create resources on the executor: open the connection inside mapPartitions or foreachPartition, once per partition, and close it there (the example in the answer). Never one connection per row, and never one captured from the driver.
  3. Make the class Serializable only if it is cheap and safe to copy.
  4. Use a Scala object (a static, created per JVM) for helpers.

Java versus Kryo. Java serialization writes class descriptions and is slow and large. Kryo uses compact class ids and is typically several times faster and smaller. Set spark.serializer to Kryo and register your classes with spark.kryo.classesToRegister; spark.kryo.registrationRequired=true catches unregistered classes. Shuffles of simple types already use Kryo internally. DataFrames avoid the issue for data because rows use Tungsten's binary format; but a UDF closure is still serialized with Java serialization.

Remember: closures travel to executors. Create connections there, never capture them. Kryo for RDD speed.

Why are UDFs slow, and what do you use instead? Intermediate

A UDF is a black box to Catalyst: it cannot push filters through it, reorder it or generate code for it, and every row must be converted from Spark's binary format to objects and back. A plain Python UDF is worse: rows travel to a separate Python process one at a time. So I prefer, in order: built-in functions, a pandas UDF (vectorized with Arrow), a Scala or Java UDF, and a plain Python UDF last.

Built-ins cover most needs (when, regexp_extract, transform, aggregate for arrays) and stay fully optimizable. A pandas UDF receives a whole batch as a pandas.Series using Arrow, so there is no per-row pickling. It is often many times faster than a row UDF. Variants: groupBy().applyInPandas() and mapInPandas (a good place to load a model once per task). A group handed to applyInPandas must fit in worker memory. Your UDF also has to handle nulls itself.

// slow: opaque to Catalyst
val up = udf((s: String) => if (s == null) null else s.trim.toUpperCase)
// better: built-ins, fully optimizable
df.withColumn("n", upper(trim($"name")))

What the cost really is. In a built-in expression, the engine works on packed binary rows inside generated code. A Scala UDF forces Spark to convert each row's fields into JVM objects, call your function, and convert the result back; also, the optimizer can no longer push filters or prune columns through it, and it cannot tell whether the function is deterministic or null-safe. A Python UDF adds a second process: rows are serialized, sent over a socket to a Python worker, processed one by one, and sent back. That serialization usually costs far more than the function itself.

Pandas UDF (vectorized). Spark converts batches of rows to Apache Arrow (a columnar in-memory format shared by the JVM and Python), hands your function a pandas.Series for each batch, and takes a Series back. Transfer is columnar and bulk, and your function can use vectorised pandas or NumPy. It typically gives a large speedup over row-at-a-time Python UDFs, though still slower than a built-in.

Example of replacing a UDF.

# slow: Python UDF
@udf("string")
def tier(a): return "high" if a > 1000 else "low"
df.withColumn("t", tier("amount"))

# fast and optimizable: built-in
from pyspark.sql import functions as F
df.withColumn("t", F.when(F.col("amount") > 1000, "high").otherwise("low"))

When a UDF is the right call. Logic that truly cannot be written with built-ins (a proprietary parser, an ML model, a library call). Then: pandas UDF if in Python; Scala or Java UDF for JVM libraries; load heavy resources once per task (mapInPandas, an iterator-style pandas UDF, or a lazily initialised static) rather than per row.

Other traps. Mark deterministic functions deterministic (default) so the optimizer can reuse them; handle nulls explicitly; do not do network calls row by row inside a UDF without batching and timeouts.

Remember: built-in beats pandas UDF beats Scala UDF beats Python UDF.

How do window functions work in Spark, and what do they cost? Intermediate

A window function computes a value per row using related rows without collapsing them like groupBy does. I define the window with partitionBy (which rows are related), orderBy and optionally a frame, then apply a ranking function (row_number, rank), an analytic one (lag, lead) or an aggregate. Cost: a shuffle so each group sits in one task, plus a sort inside each group.

A window without partitionBy sends all data to one task, and Spark warns about it. A very big group (skew) also lands in one task. row_number is always unique, rank leaves gaps after ties, dense_rank does not. The typical use is "latest record per key" or "top N per group".

val w = Window.partitionBy("customer_id").orderBy($"updated_at".desc)
val latest = df.withColumn("rn", row_number().over(w)).filter($"rn" === 1).drop("rn")

What problem windows solve. groupBy collapses rows: ten orders per customer become one row. Often you need to keep every row but add something that depends on its neighbours: the previous order's amount, the running total, the rank within the customer, the latest row. Window functions give each row a view over a "window" of related rows.

The three parts. partitionBy chooses which rows belong together (per customer). orderBy orders them inside the group. The optional frame (rowsBetween or rangeBetween) limits which neighbours count; with an orderBy the default frame is "from the start of the partition to the current row", which gives running totals.

Example data. Orders of customer C1: day 1 amount 10, day 2 amount 30, day 3 amount 20.

dayamountrow_number by daylag(amount)running sum

Cost and mechanism. To compute this, Spark shuffles by the partition key so each customer is in one task, sorts each group by the order key, then streams through computing values. So a window needs one shuffle plus a sort, and one group must fit in one task. Pitfalls: no partitionBy moves everything to one partition (one core); a huge or hot group causes skew and memory trouble; several windows with different partition keys cause several shuffles, while windows with the same partition and order spec share one.

Choosing the function. Latest record per key: row_number ordered by timestamp descending, keep 1 (add a tie-breaker column so the result is deterministic). Top N per group: row_number or dense_rank and filter <= N. Ties: rank gives 1,1,3; dense_rank gives 1,1,2; row_number gives 1,2,3 (arbitrary among ties). When only the max is needed, a groupBy with max_by or a struct trick (max(struct(ts, value))) avoids sorting everything.

Remember: window = shuffle by partition key + sort inside. Always give it a partitionBy.

6. Reading and writing data

Why is Parquet the usual choice, and how do you choose between file formats? Basic

Parquet is columnar: values of one column are stored together. Analytics queries touch a few columns of many, so Spark reads only those (column pruning). Same-type values compress well, and each row group stores min and max statistics, so Spark can skip groups that cannot match a filter (predicate pushdown). The schema is inside the file, so no inference is needed.

FormatLayoutGood forWeak at
ParquetColumnarAnalytics, Spark defaultRow-level updates
ORCColumnarHive-centred stacksLess support outside Hive
AvroRowKafka messages, write-heavy, schema evolutionColumn scans
JSON, CSVText, rowLanding raw data, exchangeSize, speed, no real types

The usual pattern: land raw data as it arrives, then convert to Parquet, often inside a table format (Delta, Iceberg) that adds updates. Gzip-compressed CSV or JSON is not splittable, so one file becomes one task. For CSV and JSON give an explicit schema instead of inferSchema: inference costs an extra pass and the guessed types can change day to day.

Row versus column storage, with an example. A table of 100 million rows with 50 columns. A query needs the sum of amount where country = 'IN'. A row format (CSV, Avro, JSON) stores each row's 50 values together, so you must read every byte. Parquet stores all amount values in a block, all country values in another, so you read 2 of the 50 columns (about 4% of the bytes).

Inside a Parquet file. The file is split into row groups (commonly 128 MB or so). Each row group has one column chunk per column, divided into pages. Each column chunk records min, max and null counts. Pages are encoded (dictionary, run-length, delta) and then compressed (Snappy is the common default in Spark, zstd or gzip compress harder). The footer holds the schema and all the statistics.

What you gain.

  • Column pruning: read only needed columns.
  • Predicate pushdown: a row group whose amount max is below your filter is skipped without reading its data.
  • Compression: same-typed, similar values compress 3 to 10 times better than text. A country column with 200 distinct values becomes tiny dictionary ids.
  • Splittable: row groups give parallelism even when a compression codec is used inside.

When another format is better. Avro for messages and write-heavy row-at-a-time pipelines, schema evolution with a registry (Kafka). JSON or CSV only for raw landing or human exchange. ORC is equivalent to Parquet in idea and common in Hive shops. Parquet by itself cannot update rows in place; use Delta or Iceberg for that.

Practical advice. Sort or cluster data by commonly filtered columns when writing, so min/max statistics are tight and pushdown skips more. Avoid very many tiny files and extremely wide nested schemas. Beware schema merge: mergeSchema across thousands of files costs a lot, and a column that changed type between files can produce read errors.

Remember: columnar + compressed + statistics = Parquet. Give text formats an explicit schema.

How does partitionBy work when writing, and what are the pitfalls? Intermediate

df.write.partitionBy("date", "country") creates folders like date=2026-11-16/country=IN/, and later queries that filter on those columns read only matching folders. The pitfalls are too many distinct values (millions of tiny folders), every write task producing a file for each value it holds, and overwrite mode deleting the whole table by default.

Pick a low-cardinality column that queries filter on, usually a date. If 200 tasks each hold 365 dates, you get up to 73,000 files; repartition($"date") before the write fixes that. By default mode("overwrite") replaces the whole path, so set spark.sql.sources.partitionOverwriteMode=dynamic to replace only the partitions present in the new data. A filter like WHERE to_date(ts) = ... cannot prune, because it is not on the partition column itself.

spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")
df.repartition($"date")
  .write.mode("overwrite").partitionBy("date").parquet("s3://b/events/")

What is on disk. partitionBy("date") writes /events/date=2026-11-16/part-0001.parquet. The value lives in the folder name, not in the file. When you later run WHERE date = '2026-11-16', Spark lists and reads only that folder (partition pruning), turning a scan of years into one day.

The file-count pitfall, worked out. You have 200 write tasks and 365 dates in the data. Each task holds rows from many dates, and each task writes one file per date it holds. Worst case: 200 x 365 = 73,000 files of a few KB. Fix: repartition($"date") first, which shuffles so all rows of one date sit in one task, giving about one file per date (or repartition(n, $"date") for more files per date; add a salt column if one date is huge).

Overwrite behaviour. The default partitionOverwriteMode is static: mode("overwrite") deletes everything under the path, then writes. Reprocessing one day would delete all other days. With dynamic, only the partitions present in the new DataFrame are replaced, which is what a daily backfill wants. With table formats, replaceWhere or MERGE give safer control.

Choosing the column. Good: date (query filters on it, bounded cardinality). Bad: user_id (millions of folders, listing becomes the bottleneck), or any column nobody filters on (only costs files). Rule of thumb: each partition folder should hold at least hundreds of MB to a few GB. Several levels (date, country) multiply the folder count.

Query side. Pruning needs a filter on the raw partition column. Wrapping it in a function (to_date(date_str)) can defeat pruning. The partition column's values come from folder names, so types are inferred (a "007" may become the int 7); declare the schema if that matters.

Remember: partition by a low-cardinality filter column, repartition by it first, and use dynamic overwrite.

What is the small files problem, and how do you prevent and fix it? Intermediate

Thousands of tiny files make listing slow (especially on S3), create one read task per file with fixed overhead, and compress poorly. They come from too many write tasks, partitionBy with many values, and streaming jobs that write a file per micro-batch. I prevent them by controlling the output partition count before the write, and I fix existing ones with a compaction job that rewrites them into files of about 128 MB to 1 GB.

Prevention: coalesce(n) or repartition(n) before the write, repartition by the partition column, maxRecordsPerFile as a safety net, the REBALANCE hint in SQL (3.2+), and AQE. For existing data, read the folder and rewrite it, or use table-format maintenance (Delta OPTIMIZE, Iceberg rewrite_data_files). On the read side Spark can pack small files into one task (maxPartitionBytes, openCostInBytes).

Why small files hurt, in concrete terms.

  • Listing: on S3 or HDFS, listing 200,000 files is slow, and the driver does it before planning (a long "nothing running" gap at job start).
  • Tasks: each file costs open/close latency, footer reads and a share of task scheduling. Reading 10,000 files of 2 MB takes far longer than 20 files of 1 GB, though the bytes are the same.
  • Compression and statistics: tiny Parquet files have poor compression and weak row-group statistics.
  • Metadata: HDFS NameNode memory, metastore partition entries and table-format manifests all grow with file count.

Where they come from. (1) Writing with many tasks and few rows each. (2) partitionBy where every task holds every value. (3) Streaming appends: a micro-batch every 10 seconds with 200 shuffle partitions makes up to 200 files per batch. (4) Late data trickling into old partitions.

Prevent at write time. Control the number of tasks writing: coalesce(n) if data is balanced, repartition(n) or repartition(col) otherwise. Decide n as data size divided by target file size (say 256 MB). maxRecordsPerFile caps file size from above only. AQE's coalescing reduces shuffle partitions automatically before the write. For streaming, use a longer trigger, fewer shuffle partitions, or write to a table format with auto-compaction.

Repair after the fact. Compaction: read a partition, repartition to the right file count, write to a new location, then swap (never overwrite the same path you are reading in a single plan without staging). With Delta use OPTIMIZE; Iceberg has rewrite_data_files. Schedule it per partition after it stops receiving data.

Trade-off. Files that are too big (many GB) limit parallelism and make updates costly. Between 128 MB and 1 GB is typical, adjusted to your read patterns.

Remember: fix the writer's partition count first, compact for streaming appends. Aim for 128 MB to 1 GB files.

7. Caching, memory model and tuning

When should you cache or persist a DataFrame, and what is the difference from checkpoint? Intermediate

I cache when an expensive result is reused by several actions, for example an iterative algorithm or one result feeding two outputs. Without it every action recomputes from the source. I do not cache data used once, cheap to recompute, or too large, because it evicts other data. Cache is lazy: nothing is stored until the first action runs, and I call unpersist() when done.

cache() on a DataFrame uses MEMORY_AND_DISK, on an RDD MEMORY_ONLY. With persist(level) I can pick memory only (missing partitions are recomputed), memory and disk, serialized variants (smaller, more CPU), or _2 replicas. Cached blocks use the same unified memory pool as shuffles, so over-caching makes shuffles spill. Cache is not fault tolerance: a lost block is recomputed from lineage. Checkpoint, by contrast, writes to reliable storage and cuts the lineage.

enriched.persist(StorageLevel.MEMORY_AND_DISK)
enriched.count()                  // fills the cache (a full pass)
enriched.write.parquet("/out/a")  // reads from cache
enriched.unpersist()

What caching really does. Every action rebuilds a DataFrame from the source. If the pipeline contains an expensive join and you use the result twice, the join runs twice. cache() marks the plan so that, the first time its partitions are computed, they are kept on the executors. Later actions read the stored blocks instead of recomputing.

Good and bad candidates.

Cache itDo not cache it
A result used by 2 or more actions or branchesData used once
Iterative algorithms (ML loops, graph passes)Data that is cheap to recompute (a simple filtered read)
A small-to-medium result of an expensive join or aggregationData far larger than executor memory (spills or evicts, may be slower than recompute)
Interactive exploration of one datasetRaw input just before a single write

Storage levels. MEMORY_ONLY: deserialized objects, fastest, but a partition that does not fit is not stored and is recomputed. MEMORY_AND_DISK: overflow goes to disk. _SER variants: stored as bytes, smaller, more CPU. DISK_ONLY, and _2 for two replicas. For DataFrames, the cache is stored in a columnar compressed form, so it is usually smaller than the object form.

Checkpoint versus cache. Cache is a performance hint kept on executors; if an executor is lost, those blocks are recomputed from lineage, and lineage is kept. checkpoint() writes the data to reliable storage (HDFS or S3) and truncates lineage, giving fault tolerance and a short plan for long iterative jobs. It costs a full write. localCheckpoint() truncates lineage but stores on executors only (faster, not fault tolerant).

Pitfalls. Forgetting unpersist (memory leaks across a long job). Caching a DataFrame then changing a source file underneath: you get stale data. The first action pays the full cost, so one-off use is a net loss. Check the Storage tab of the UI: fraction cached and sizes. If "fraction cached" is below 100% with MEMORY_ONLY, you are recomputing partially.

Remember: cache only what is expensive and reused. It is lazy, it takes execution memory, and it is not a backup.

Explain Spark's executor memory model: execution, storage, user and overhead. Senior

The executor heap (spark.executor.memory) has about 300 MB reserved. Of the rest, 60% is the unified region shared by execution memory (shuffles, joins, sorts) and storage memory (cache, broadcast). The other 40% is user memory for my own objects. Outside the heap there is overhead memory (max of 384 MB and 10% of the heap) for JVM native use, network buffers and Python workers. The container size is heap plus overhead.

The boundary between execution and storage is soft. Half of the unified region (spark.memory.storageFraction, 0.5) is protected for storage. Execution can borrow free storage space and can evict cached blocks down to that protected amount, but storage cannot evict running execution data. Each running task gets roughly between 1/(2N) and 1/N of the execution pool, where N is the active tasks, so more cores per executor means less memory per task.

Why this matters. Almost every executor failure and spill is a memory-budget question, and the answer depends on which region ran out. Knowing the layout tells you which knob to turn.

Walk the numbers. Executor heap 10 GB (spark.executor.memory=10g).

  1. Reserved: about 300 MB, untouchable.
  2. Usable: 10 GB minus 0.3 GB = about 9.7 GB.
  3. Unified region: 60% of usable, about 5.8 GB, shared by execution and storage.
  4. Storage protected share: 50% of the unified region, about 2.9 GB, which execution cannot evict.
  5. User memory: the other 40%, about 3.9 GB, for your own data structures, UDF objects and Spark's metadata.
  6. Overhead (outside the heap): max(384 MB, 10% of 10 GB) = 1 GB. The container request is about 11 GB.

Execution versus storage. Execution memory is used while a task runs: shuffle buffers, hash tables for joins and aggregations, sort buffers. It is freed at task end. Storage memory holds cached blocks and broadcast values. If execution needs more, it takes unused storage space, and can evict cached blocks above the protected share. If storage needs room, it can use free execution space but cannot kick out execution that is in use. So heavy caching can squeeze shuffles into spilling, and a huge shuffle can evict your cache.

Per-task share. If the executor has 4 running tasks, each can get between 1/8 and 1/4 of the execution pool. That is why fewer cores per executor means more memory per task, which is a quick fix for spills.

An executor fails with OutOfMemoryError or "container killed". How do you tell the cause and fix it? Senior

How do you decide cores and memory per executor? Senior

My starting rule is about 4 to 5 cores per executor, then divide the node memory among its executors, leaving some for the operating system and roughly 10% for overhead. Then I adjust from evidence in the UI: spill and GC time say more memory per task, idle cores say more partitions or fewer cores per executor. Capacity planning of the whole cluster belongs to the platform team.

Why 4 to 5: a single-core executor wastes memory on duplicated overhead and cannot share broadcasts. Very many cores per executor share one heap (more garbage collection, less memory per task) and compete for I/O throughput. This is a rule of thumb, not a law. Example: a 16-core, 64 GB node can hold three executors of 5 cores, each about 19 GB in total, so roughly 17 GB heap plus 2 GB overhead. Memory per task is about executor memory times 0.6 divided by cores.

Why not one core per executor, or one executor per node?

  • Tiny executors (1 core): every executor has its own JVM overhead and its own copy of broadcast data, there is little room for memory sharing between tasks, and you get many connections to the driver and shuffle service.
  • Giant executors (30+ cores, 200 GB): many tasks contend for one heap, so garbage collection pauses grow (large heaps scan slowly), HDFS client throughput per executor tops out (commonly cited around 5 concurrent streams), and a single lost executor loses a lot of work and cached data.
  • Middle (4 to 5 cores, 8 to 32 GB): a balance between those.

Worked sizing. Node: 16 cores, 64 GB, running YARN. Reserve 1 core and 1 GB for the OS and node daemons: 15 cores and about 63 GB usable. With 5 cores per executor you get 3 executors per node. Memory per executor is about 63/3 = 21 GB total, which includes the overhead (10% means heap about 19 GB, overhead about 2 GB); you might round down to be safe: --executor-cores 5 --executor-memory 18g with overhead 2 GB. Each running task then gets roughly (18 GB x 0.6 x 0.95) / 5, about 2 GB of execution memory share, if all 5 slots are busy.

8. Structured Streaming

What is Structured Streaming, and how does it relate to batch DataFrames? Basic

Structured Streaming lets me write a streaming job with the same DataFrame or SQL code as a batch job. Spark treats the stream as a table that keeps growing and runs my query incrementally on each new chunk of data. By default it is micro-batch: every trigger it takes the new data since the last batch, runs a normal batch job on it, and writes the output. Latency is typically from about 100 ms to a few seconds, with exactly-once results.

The engine handles progress tracking, retries and state. Before each batch it writes the planned input offsets to a checkpoint, so after a crash it can replay exactly the same range. There is an experimental continuous mode for roughly 1 ms latency, with at-least-once and limited operations, which few teams use. The older DStream API (Spark Streaming) is legacy.

The core idea. Imagine the input stream as a table where new rows are appended forever. You write an ordinary query over that table (select, groupBy, joins). Spark's job is to keep the result table correct as rows arrive, without recomputing everything each time.

What happens each micro-batch, with an example. Query: count orders per country from a Kafka topic, trigger every 10 seconds.

  1. Spark asks Kafka for the latest offsets and decides batch 17 covers offsets 5000 to 5400 per partition.
  2. It writes that planned range to the checkpoint's offsets log, before processing.
  3. It runs the query over only those 400 new rows per partition, as a normal batch job (stages, shuffle, tasks). The running counts per country come from the state store and are updated with the new rows.
  4. It writes results to the sink, then records "batch 17 committed" in the commit log.
  5. Repeat. If the app crashes between steps 2 and 4, on restart Spark sees batch 17 planned but not committed and re-runs the same range, so the sink must tolerate a repeat of that batch (idempotent or transactional).

Why this design. Reusing the batch engine gives Catalyst, Tungsten and the same APIs for free, and micro-batches make exactly-once reasoning simple, since each batch is a deterministic function of a recorded offset range. The price is latency of at least about a few hundred milliseconds from batch overhead.

Related ideas. The older DStream API operated on RDDs without schema or event-time support and is legacy. Continuous processing (experimental) trades guarantees for about 1 ms latency. For true event-at-a-time low latency or complex event time, Flink is often compared; for hour-level freshness a scheduled availableNow job is enough. Batch and streaming code share logic, but streaming has restrictions: no arbitrary sort on an unbounded stream (outside complete-mode aggregates), limited distinct, and actions like count() or show() need writeStream instead.

Remember: a stream is an unbounded table, processed as a series of small batch jobs with checkpointed offsets.

What are output modes and triggers? Intermediate

The output mode says what is written each batch: append writes only new final rows, update writes rows that changed, and complete rewrites the whole result table (only sensible for small aggregates). The trigger says when a batch runs: by default as soon as the last one finishes, or fixed with processingTime("1 minute"), or availableNow, which processes everything available and then stops.

Not every combination is allowed. An aggregation with a watermark in append mode emits a window only after the watermark passes it. availableNow (Spark 3.3+, replaces the deprecated once) is handy: I run the same streaming code as an incremental batch on a schedule, which keeps checkpoints and exactly-once handling while releasing the cluster between runs. For hours-level freshness a scheduled availableNow job is simpler and cheaper than a permanent stream.

df.writeStream.outputMode("append")
  .trigger(Trigger.AvailableNow())
  .option("checkpointLocation", "/chk/orders")
  .format("parquet").start("/lake/orders")

Output modes, with the same example. Query: orders per country, new orders arrive.

Triggers.

  • Default: start the next batch immediately when the previous finishes. Lowest latency, but under light traffic it creates many tiny batches and tiny files.
  • processingTime("1 minute"): a batch at most every interval; a good way to trade latency for bigger batches and fewer files.
  • availableNow: process everything that arrived since the last run, in one or more batches (respecting rate limits), then stop. Great for scheduled incremental ingestion, and it respects maxOffsetsPerTrigger, unlike the deprecated once, which forced one giant batch.
  • Continuous: experimental low latency, rarely used.

Decision rule. Need seconds-level freshness: processing-time trigger on a long-running cluster. Freshness of an hour or more, or cost matters: availableNow on a schedule. Either way keep the same checkpoint folder, so each run picks up where the last stopped.

Remember: mode = what rows to write, trigger = when to run. AvailableNow = streaming code as incremental batch.

What is a checkpoint in Structured Streaming, and what happens if you lose or change it? Intermediate

The checkpoint is a folder on reliable storage that records which input offsets each batch covered, which batches committed, and the state store files. On restart Spark reads it and continues from the next range, so no data is lost or processed twice (given a replayable source and an idempotent sink). If I delete it, the query starts over from the source's starting offsets and the state is gone. One checkpoint folder per query, never shared.

After deletion, a Kafka source starts from startingOffsets (latest by default, so I may skip data, or earliest, so I may reprocess everything). When I change the query, some changes are compatible (adding a filter), but changing grouping keys, the state schema, or the number of shuffle partitions of a stateful query breaks recovery. State is stored per partition and that count is fixed in the checkpoint. Then I need a new checkpoint and a backfill plan.

What is inside the folder.

  • offsets/: for each batch id, the input range planned (written before the batch runs).
  • commits/: batch ids that finished successfully.
  • state/: snapshots and delta files of the state store, per operator and per partition.
  • metadata: the query id.

Recovery logic. On start, Spark compares the last offsets entry with the last commit. If they match, it plans the next batch. If offsets is ahead of commits by one, the last batch was interrupted, so it re-runs exactly that range, and reloads state to the last committed version. This is the basis of the exactly-once story.

What happens in common situations.

EventResult
Normal restart, same codeContinues from the next offset, state restored

Change aggregation keys, add a new stateful operator, change number of shuffle partitions in a stateful query, change the sink typeFails to restart, or silently wrong; need a new checkpoint

Operational advice. Put the checkpoint on reliable storage (HDFS, S3, ADLS), never on local disk. Keep it with the output so backups and migrations stay consistent. When a stateful change is unavoidable, start a new checkpoint at a known offset and backfill the gap with a batch job, checking for overlaps and duplicates. Old files are cleaned automatically (minBatchesToRetain), but the folder grows with state size.

Remember: the checkpoint is the query's memory. Lose it and you lose position and state. Stateful changes need a new one.

What are event time, processing time and a watermark? Intermediate

Event time is when the event happened, written in the data. Processing time is when Spark sees it. They differ because of network delays and offline devices. For "clicks per 5 minutes" I use event time. A watermark such as withWatermark("event_time", "10 minutes") tells Spark how late data may be, so it knows when a window is final, can emit it, and can delete its state.

Without a watermark Spark must keep every window open forever in case late events arrive, and state grows without limit. Spark computes the watermark as the maximum event time seen so far minus the delay. Windows that end before the watermark are closed. Events that arrive behind it for closed windows are dropped, silently. It is a trade-off: a longer delay is more complete, a shorter one saves memory and gives lower latency. With several input streams Spark uses the minimum watermark by default.

Why two clocks. A phone records a click at 12:03 while offline and uploads it at 12:30. Processing time says 12:30; event time says 12:03. Business questions ("clicks per 5-minute window") want event time, but then late data is possible, which processing time never has.

The dilemma a watermark resolves. When can the 12:00-12:05 window be called done? Never, strictly, because an event could still show up. But waiting forever means keeping state forever. The watermark is a promise: "I assume no data older than max-event-time minus delay will arrive." That lets Spark finalise windows and free their state.

Worked timeline (delay 10 minutes, windows 5 minutes).

  1. Events arrive up to 12:22. Watermark = 12:22 - 10 = 12:12.
  2. Windows ending at or before 12:12 (12:00-12:05, 12:05-12:10) are final. In append mode they are emitted now; their state is deleted.
  3. Window 12:10-12:15 is still open (ends after the watermark). An event stamped 12:11 arriving now is still counted.
  4. An event stamped 12:07 arrives. Its window is closed, so it is dropped silently. (Dropping is by window state; non-aggregating queries are not affected.)

Rules to remember. The watermark only moves forward, and is computed from the data seen, so an idle stream does not advance it (a quiet topic can hold windows open). It is evaluated at the start of the next batch, so output is delayed by about a batch. With multiple input streams the global watermark is by default the minimum of the inputs' watermarks (configurable, spark.sql.streaming.multipleWatermarkPolicy), so one slow stream holds everything back.

Choosing the delay. Measure lateness from your data (the 99th or 99.9th percentile of arrival time minus event time). A larger delay raises completeness, memory and latency; a smaller one does the opposite. Late rows are lost, so compare against a batch recount, or route late rows to a side output if completeness matters.

Remember: watermark = max event time minus allowed delay. Behind it, windows close and late rows are dropped.

What is state in streaming, and how do you keep it from growing without bound? Senior

State is data Spark must remember between batches: running aggregations, the keys seen by dropDuplicates, rows waiting for a match in a stream-stream join, and custom state in flatMapGroupsWithState. It lives in a state store per shuffle partition, backed up to the checkpoint. To bound it I always use a watermark, so old windows and keys expire, and I avoid grouping by an unbounded key (a random request id) without expiry.

The default state store keeps state in executor heap, so big state means garbage collection pauses and out-of-memory errors. From Spark 3.2 the RocksDB state store keeps state on local disk and off-heap, which scales to far larger state. For deduplication, include the event time column plus a watermark (or dropDuplicatesWithinWatermark in 3.5+). Stream-stream joins need a watermark on both sides and a time-range condition. I watch numRowsTotal of the state operators in query.lastProgress: if it only goes up, state is not expiring. Stateless operations (select, filter, stream-to-static joins) hold no state.

What counts as state. Anything Spark must remember across batches because a later batch needs it: partial aggregates (running sum per key), seen keys for deduplication, one side of a stream-stream join waiting for a match, and your custom state in flatMapGroupsWithState. Stateless queries (select, filter, map) need none.

How it is stored and protected. State is partitioned like the shuffle (one store per partition per operator), held in executor memory (default provider) or in RocksDB (3.2+), and each batch writes a delta file to the checkpoint; periodic snapshots allow fast recovery.

Why unbounded state kills jobs. Take groupBy(userId).count() with 50 million distinct users. Without a watermark or timeout, every user ever seen stays in state. Heap use rises, GC gets longer, batch time grows, eventually executors die and the restart is slow because loading state takes ages. The symptom is a job that is fine for weeks and then degrades.

Bounding techniques.

Monitoring. In lastProgress.stateOperators watch numRowsTotal, memoryUsedBytes and for RocksDB the store metrics. Use RocksDB for large state, and size shuffle partitions up front: the partition count of stateful operators cannot change without a new checkpoint.

Remember: every stateful query must say how its state expires: watermark or timeout. RocksDB for big state.

How does Spark read from Kafka, and how are offsets handled? Intermediate

The built-in Kafka source maps each Kafka partition to a Spark input partition, so read parallelism is capped by the topic's partition count. Records arrive with key and value as binary plus topic, partition, offset and timestamp, and I cast and parse the value. Importantly, Spark does not commit offsets to Kafka consumer groups. It tracks offsets itself in the checkpoint, which is what enables exactly-once processing on restart.

So Kafka's consumer-group lag tools are not meaningful for a Spark query. Use the query progress metrics. maxOffsetsPerTrigger limits batch size, protecting against a huge catch-up batch. startingOffsets only applies on the first start without a checkpoint. If Kafka has already deleted data the query needs, it errors unless failOnDataLoss=false, which silently skips the gap.

val raw = spark.readStream.format("kafka")
  .option("kafka.bootstrap.servers", "k1:9092")
  .option("subscribe", "orders")
  .option("maxOffsetsPerTrigger", 200000)
  .load()
val parsed = raw.select(from_json($"value".cast("string"), schema).as("o")).select("o.*")

How a batch reads Kafka. The driver asks Kafka for the latest offsets per partition, computes the range since the last batch for each, and creates one Spark task per Kafka partition (or splits, if minPartitions is set). Each task reads its offset range using a Kafka consumer cached on the executor.

The columns you get. key and value (binary), topic, partition, offset, timestamp, timestampType. You cast value to a string and parse (JSON with from_json, Avro with a schema or a registry integration).

Offsets, the key difference from a normal consumer. A plain Kafka consumer commits offsets to the broker's consumer group. Spark does not: it records offsets in its own checkpoint, and sets its own group ids internally. Consequences:

  • Consumer-lag dashboards based on committed group offsets do not show Spark's progress. Monitor with lastProgress (endOffset versus latestOffset) or by computing lag from the metrics.
  • Restarting with a new checkpoint ignores where the old query stopped; use startingOffsets (a JSON of exact offsets works) for deliberate positioning.
  • Changing the topic's partition count mid-flight is supported for new partitions (picked up), but plan it.

Rates and safety options. maxOffsetsPerTrigger bounds batch size, so a restart after downtime does not make a 100x batch that runs out of memory. failOnDataLoss (default true) fails the query if offsets it needs were deleted by retention or a topic was recreated. Turn it off only if skipping is acceptable. kafka.* options pass through to the client (security settings such as SASL or SSL).

Parallelism cap. 12 partitions mean at most 12 read tasks, even with 100 cores. Fix by repartitioning after the read for downstream work, or increasing topic partitions (a Kafka design decision), or minPartitions to split ranges.

Remember: offsets live in the Spark checkpoint, not in Kafka. Parallelism is capped by topic partitions.

Does Structured Streaming give exactly-once? What does it need from the source and the sink? Senior

It gives exactly-once for the results of the query, under three conditions: a replayable source (Kafka, files, not a plain socket), offsets written to the checkpoint before a batch runs so a retried batch covers the same input, and an idempotent or transactional sink. In practice "exactly-once" means at-least-once delivery plus idempotent writes.

File sinks track committed batches in a metadata log, so they are exactly-once. Delta and Iceberg commit transactionally. The Kafka sink is only at-least-once. For databases I use foreachBatch, which hands me each micro-batch as a normal DataFrame plus a batch id, and make the write idempotent with the batch id or an upsert on a primary key. After a failure foreachBatch can run twice for the same batch id. Side effects such as calling an API are not covered by any guarantee. Cache the batch if I write it twice, and unpersist it at the end.

df.writeStream.foreachBatch { (batch: DataFrame, batchId: Long) =>
  upsertToTable(batch, batchId)      // MERGE on a key, safe to run twice
}.option("checkpointLocation", "/chk/orders").start()

Break the claim into two halves. Delivery of input is "at-least-once" (after a crash a batch may be re-read). The effect on the output is "exactly-once" only if re-running a batch does not change the result. Structured Streaming provides the machinery for that; the sink must cooperate.

The three ingredients.

  1. Replayable source. Kafka, files and Kinesis can re-deliver the same offsets or file list. A raw socket cannot.
  2. Deterministic, recorded batch boundaries. The offsets are written to the checkpoint before processing, so a retry of batch N reads exactly the same records. (If the transformation itself is non-deterministic, e.g. calls rand() or an external lookup that changes, the retry can produce different output.)
  3. Idempotent or transactional sink. Writing batch N twice must equal writing it once.

Sink by sink.

SinkGuaranteeWhy
File sinks (Parquet etc.)Exactly-onceA metadata log lists committed files per batch; readers using that log ignore leftover files from failed attempts
Delta, IcebergExactly-onceAtomic commits; batch id recorded to skip duplicates (e.g. Delta txnAppId and version options)

A failure walkthrough. Batch 17 writes 400 rows to Postgres, then the app crashes before the commit log entry. On restart Spark runs batch 17 again with the same 400 rows. With INSERT you now have 800 rows. With INSERT ... ON CONFLICT (order_id) DO UPDATE, you still have 400. Alternatively, store batchId in a progress table in the same transaction, and skip a batch that is already recorded.

Things no guarantee covers. Emails, API calls and any side effect inside transformations; end-to-end exactly-once across systems also needs the downstream consumer to read committed data only.

Remember: replayable source + checkpointed offsets + idempotent sink = effectively exactly-once.

9. Fault tolerance and practice

What is lineage, and how does Spark use it for fault tolerance? Intermediate

Lineage is the recorded graph of transformations that produced a dataset from its source. Spark does not replicate computed data. If a partition is lost because an executor died, the scheduler walks the lineage, finds the parent partitions, and recomputes only that partition. It works because transformations are deterministic and the input can be re-read.

For narrow dependencies a lost partition needs one parent partition, so it is cheap. For wide dependencies it may need many, unless the shuffle files still exist. Weak points: a very long lineage (iterative loops with hundreds of steps) makes recomputation costly and the plan huge, and non-deterministic steps (unseeded random numbers, a changing source) can give different data on recompute. For a long lineage I use checkpoint(), which writes to reliable storage and cuts the lineage (or write to Parquet and read it back). Failed tasks are retried up to 4 times (spark.task.maxFailures); a lost shuffle file triggers a re-run of the map stage; a dead driver ends the application.

Why not replicate like HDFS? Intermediate data is huge and mostly short-lived. Storing three copies of every intermediate result would multiply memory and I/O. Because Spark's transformations are deterministic functions of their inputs, it keeps a small description instead: "partition 3 of this dataset = filter(map(partition 3 of the file))".

Recovery walkthrough. A job has stages A (read, map) then B (aggregate). An executor dies when stage B is half done.

  1. The driver notices heartbeats stopped, marks the executor lost, and reschedules its running tasks elsewhere.
  2. If those tasks need shuffle output that lived on the dead executor's disk, the fetch fails. The scheduler marks that map output lost and re-runs only the map tasks that produced it (stage A, specific partitions).
  3. When the map outputs exist again, the reduce tasks run and the job finishes. Other completed work stays valid.

Narrow versus wide recomputation. Rebuilding a narrow partition replays one chain on one parent partition. Rebuilding a wide partition needs slices from many parents, so a failure late in a long job with a lost shuffle can mean rerunning large chunks of earlier stages. The external shuffle service (or shuffle tracking on Kubernetes) keeps shuffle files alive when an executor exits, which avoids this in many cases.

When lineage becomes a liability. Iterative jobs (loops of 100 iterations that keep adding transformations) create very long lineage: planning slows, memory on the driver grows, a stack overflow can happen when serializing the plan, and a failure replays everything. Use checkpoint() every N iterations; it saves data reliably and starts a new short lineage. Also, a non-deterministic source (a changing table, rand() without seed, a file overwritten mid-job) can make the recomputed partition differ from the first run, silently corrupting results. Prefer snapshots or table-format time travel as input.

What lineage does not protect. The driver (a driver crash ends the app; streaming recovers using the checkpoint on restart) and external side effects.

Remember: Spark stores the recipe, not copies. A lost piece is cooked again from its parents.

PySpark vs Scala vs Java for Spark: how do they differ in performance? Intermediate

For DataFrame and SQL code the language barely matters, because Python only builds the plan and the JVM executes it with Catalyst and Tungsten. The slowdown appears when Python code runs on the executors: plain Python UDFs, RDD lambdas and toPandas. Then every row crosses from the JVM to a Python worker process and back. So I use PySpark with built-ins and pandas UDFs for most pipelines, and Scala or Java for performance-critical custom logic and shared libraries.

Executors start Python worker processes next to the JVM, so PySpark needs more memory overhead. Scala is the native language: typed Datasets, new APIs first, no serialization boundary for UDFs. Java is fully supported but its Dataset API is more verbose (encoders, explicit lambda types). For Java builds, mark Spark as provided scope so the cluster's jars are used, and watch for dependency clashes (Guava, Jackson).

Where the Python code actually runs. In PySpark, your df.filter(...).groupBy(...) calls go through a bridge (Py4J) to the JVM driver, which holds the real plan. The executors run JVM code. Nothing about the language slows down the data plane, so a pure DataFrame job in Python and Scala produce the same plan and run at essentially the same speed.

When Python enters the data path. Whenever a function must run per row or per batch inside Python: a plain UDF, an RDD map with a lambda, mapInPandas, applyInPandas. Spark then starts Python worker processes on each executor and moves data between JVM and Python. Costs: serialization of every value, process memory outside the JVM heap (so more memoryOverhead), no whole-stage codegen across that step.

Other factors in the choice. Team skills and the ML ecosystem (pandas, scikit-learn, notebooks) favour Python. Typed Datasets, access to internal APIs, custom data sources and connectors, and shared libraries favour Scala or Java. New features sometimes appear in Scala first. Debugging errors in PySpark shows long Java stack traces plus Python ones. Packaging differs (wheels, conda environments, zip files versus fat jars).

Interview-safe answer. "Same engine; write DataFrame code, avoid Python UDFs, and the language is not the bottleneck. I use Scala or Java where I need typed APIs, custom connectors or maximum control."

Remember: same engine either way. Slowness is Python code on executors, not the language of the driver.

Why do teams use Delta, Iceberg or Hudi on top of Parquet? Senior

Plain Parquet folders have no transactions. A failed job leaves half the files, readers see partial writes, and updating or deleting a row means rewriting files by hand. Table formats add a metadata layer (a transaction log or manifests) that gives atomic commits, row-level MERGE, UPDATE and DELETE, schema evolution, time travel, and faster planning through file statistics instead of directory listing.

They also make streaming sinks and idempotent reruns much easier. Delta came from Databricks, Iceberg from Netflix (many engines support it), Hudi from Uber (strong at upserts and incremental pulls). The cost is another dependency and table maintenance: compaction, snapshot expiry and vacuum. For a developer, the answer to "how do I safely rerun a job without duplicates" is often "write with MERGE or overwrite into a table format".

What goes wrong with plain Parquet folders.

  • No atomic writes: a job that fails halfway leaves some files. Readers may see partial data, and a rerun appends duplicates.
  • No row-level change: to delete one user's rows (GDPR) you rewrite entire files and folders by hand.
  • Concurrent writers collide: two jobs overwriting a partition race.
  • Slow planning: listing millions of files on object storage is slow.
  • Schema evolution is manual and risky across files.

The fix: a metadata layer. The table is still Parquet data files, plus a log. Delta keeps an ordered transaction log (JSON actions plus checkpoints) of "add file X, remove file Y". Iceberg keeps snapshots that point to manifest lists and manifests listing data files with statistics. Hudi keeps a timeline plus indexes. A reader reads the log to learn the exact file list for a version, so it sees a consistent snapshot. A writer adds new files and then commits by atomically adding a log entry (with optimistic concurrency checks), so a failed job commits nothing.

What you get.

CapabilityExample use
ACID commits, isolationReaders never see half-written output
MERGE / UPDATE / DELETEUpsert CDC changes by key; delete a user
Time travelQuery yesterday's version, roll back a bad write
Schema evolutionAdd or rename columns safely
File-level statistics and pruningSkip files without listing directories
Streaming source and sinkExactly-once streaming writes, incremental reads

Costs and choice. Row-level updates are implemented as copy-on-write (rewrite files; fast reads) or merge-on-read (write delete or delta files, merge when reading; fast writes). You must run maintenance: compaction, expiring old snapshots, removing orphan files (VACUUM in Delta). Pick by ecosystem: Delta if Databricks-centred, Iceberg for multi-engine (Spark, Trino, Flink, Snowflake), Hudi for heavy upsert and incremental pull workloads. Check the sibling Data Engineering page for deeper Iceberg coverage.

Remember: table format = Parquet files + transaction log. Atomic writes, upserts, time travel.

How do you design a Spark batch job so it can be safely rerun? Senior

Running the job twice for the same input must give the same output with no duplicates and no gaps. So I parameterize by a business date or batch id (not "now"), read a clearly defined input slice, make the output deterministic, and write with an overwrite of the exact partition or a MERGE on a business key rather than a blind append.

Concretely: avoid unseeded rand, current_timestamp in keys and unordered first. Use partitionOverwriteMode=dynamic or a table-format MERGE. Write to a staging location, then commit or swap. Keep external side effects out of tasks, or make them idempotent with a key. Deduplicate the input on a natural key with row_number when the source can deliver repeats. Record each run in a control table to detect double runs. Then test the rerun path: run twice and compare counts and checksums.

Why this is a design question. Failures and reruns are normal: a node dies, someone reruns a day for a bug fix, the scheduler retries. A job that is not safe to repeat turns every retry into a data-quality incident.

The checklist, each with the reason.

  1. Take the logical time as a parameter (--date 2026-11-16), not current_date(). A rerun the next day would otherwise read different data.
  2. Read an immutable, well-defined input slice. Reading "everything in the folder" while another process writes to it makes reruns differ. Prefer partitioned landing data or a table snapshot / time-travel version.
  3. Deterministic transformation. Avoid unseeded rand(), uuid() as keys, current_timestamp() in business keys, first()/collect_list over unordered data, and window functions with ties and no tie-breaker. Derive surrogate keys by hashing business columns.
  4. Write so repeat = replace. Overwrite exactly the partition for that date (dynamic partition overwrite) or MERGE on the business key. Never blind append for reprocessable data.
  5. Atomic publish. Write to a staging path or temp table, validate, then swap or commit (table format commit, or rename of a partition). A half-written output must not be visible.
  6. Dedupe the input. Upstream retries create duplicates; keep one row per natural key with row_number over (key order by ingestion time desc).
  7. Contain side effects. API calls, emails and database inserts inside tasks can run twice (retries, speculation). Use idempotency keys or move them out of the Spark job.
  8. Record runs (control table: run id, date, row counts, status) and skip or flag duplicates.

Example write.

spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")
daily.write.mode("overwrite").partitionBy("date").parquet(out)   // rerun for one date replaces only that date

Prove it. In tests, run the job twice on the same input and assert identical row counts, key uniqueness and a checksum; also run a day, then a backfill of that day, and compare.

Remember: same input slice, deterministic transform, overwrite or merge. Test it by running twice.

What is speculative execution, and what do task and stage retries mean for your code? Senior

Speculation launches a duplicate copy of a task that is running much slower than its peers, and takes whichever copy finishes first. It helps with a sick node but not with skew. Separately, failed tasks are retried (4 attempts by default) and lost shuffle data triggers stage reruns, so any task can run more than once. My code must tolerate that: no non-idempotent side effects inside tasks.

Why it exists. A stage waits for its slowest task. Sometimes a task is slow not because of its data but because its machine is slow (a failing disk, a noisy neighbour, a stuck network). Spark can detect this: with spark.speculation=true, once a quantile of tasks (default 75%) in a stage has finished, tasks running longer than a multiple (default 1.5) of the median are candidates. Spark starts a second copy on another executor. The first copy to finish wins and the other is killed.

When it helps and when it hurts.

SituationEffect of speculation
One bad node slows some tasksHelps a lot
Data skew (one huge partition)No help: the copy gets the same huge partition and also runs long; it wastes cores
Tasks write to an external system (database, API)Dangerous: both copies may perform the side effect
Output to files through the commit protocolSafe: only the winning attempt's files are committed
Cluster already tight on resourcesAdds load; can slow others

Retry levels. Task failure (exception, executor lost): rerun up to spark.task.maxFailures times (4). Fetch failure (a shuffle file is gone): the map stage tasks that produced it are re-run, and the reduce stage is retried (stage attempts are limited, a few by default). Executor loss: tasks reschedule elsewhere, and the cluster manager launches a replacement. Driver loss: the application ends (a supervisor must restart it).

What this means for your code. A task function can execute twice for the same partition, even for a successful job. So: make external writes idempotent, treat accumulators in transformations as approximate, avoid reading mutable external state in tasks, and be careful with non-determinism (a retried task with rand() may produce different rows; a shuffle with random keys can then lose or duplicate rows in rare retry cases, so seed or sort first).

Remember: speculation fixes slow machines, not slow data. Any task can run twice, so make side effects idempotent.

How do you read a large database table into Spark in parallel, and what can go wrong? Intermediate

A plain JDBC read uses one connection and one task, so it is slow and leaves the cluster idle. I give Spark a numeric (or date) partition column with lower and upper bounds and a partition count, and Spark issues that many range queries in parallel. I choose an indexed, evenly spread column and keep the count within what the database can serve.

How it works. With partitionColumn=id, lowerBound=1, upperBound=10000000, numPartitions=10, Spark makes 10 queries: WHERE id < 1000001 OR id IS NULL, WHERE id >= 1000001 AND id < 2000001, ... up to WHERE id >= 9000001. The bounds only decide the strides; rows outside the bounds still land in the first or last partition, so they are not lost, but they can make those partitions huge.

val df = spark.read.format("jdbc")
  .option("url", jdbcUrl).option("dbtable", "orders")
  .option("partitionColumn", "id").option("lowerBound", 1)
  .option("upperBound", 10000000).option("numPartitions", 10)
  .option("fetchsize", 10000).load()

Pitfalls.

  • Skewed column: if ids are clustered, some partitions get most rows. Use a more even column, a hash expression, or a custom list of predicates (spark.read.jdbc(url, table, predicates, props)).
  • Too many connections: 200 partitions means 200 concurrent queries on a production database. Cap numPartitions and run against a replica.
  • Unindexed column: every range query scans the table.
  • Small fetch size: some drivers default to a small fetch size, causing many round trips; set fetchsize.
  • Pushdown: filters and column selection are pushed to the database for simple expressions; a subquery in dbtable or query can pre-filter on the database side.
  • Consistency: parallel range queries run at different moments, so a changing table can give an inconsistent snapshot; snapshot or use a replica for exact results.

For repeated large extracts, prefer change data capture into Kafka or a table format over repeated full JDBC pulls.

Remember: JDBC read = 1 task unless you set partitionColumn, bounds and numPartitions. Parallel for Spark, load for the database.

10. Real-life scenarios

Every answer follows the same shape: situation, what you check first, the fix, and how you prevent it next time. Say that shape aloud in the interview. It shows you work calmly under pressure.

A nightly job that usually takes 20 minutes now takes 3 hours, and one task in the join stage runs forever. What do you do? Senior

That is data skew: one hot key (often a null, a placeholder or one huge customer) sends most rows to one task. I confirm it in the stage page, find the hot key, then filter it if it is junk, let AQE split it, broadcast the small side, or salt the key.

Situation: 199 of 200 tasks finish in seconds, one keeps running and reads gigabytes. It often starts when a new upstream feed floods one key.

Check first: compare median and max task duration and shuffle read in the stage page. Find the hot key:

df.groupBy("customer_id").count().orderBy($"count".desc).show(10)
df.filter($"customer_id".isNull).count()

Fix: filter null or placeholder keys before the join (they never match in an inner join). Make sure AQE and skewJoin.enabled are on. Broadcast the other side if it is small. Otherwise salt the hot keys, or join hot keys separately with a broadcast join and union the result. AQE skew handling needs the partition to be above 5 times the median and 256 MB, so salting is the fallback.

Prevent: a data-quality check on the top-key share, an alert on max-to-median task time, and cleaning nulls and defaults at ingest.

The thought process an interviewer wants to hear. "One task is slow, the rest are done" is the signature of skew, not of a cluster-wide problem. So I do not touch memory or executor counts first. I confirm with numbers, find the key, and pick the cheapest fix for that key.

Worked numbers. Stage page: median task 6 s, max task 2 hours, max shuffle read 38 GB versus median 0.3 GB. The top-key query shows customer_id = NULL has 40% of the rows (a new upstream bug started sending nulls). Because an inner join never matches nulls, filtering them out before the join is correct and instantly removes the skew; the stage drops back to minutes. If the key is real (one large legitimate customer), then try AQE skew handling (check it is enabled, and that the partition is above the 5x median and 256 MB thresholds), then broadcast if the other side is small, then salting for the hot key only.

Why the job got slower "suddenly". Data volume or key distribution changed, not the code. That is why I add an alert on max-to-median task time or a daily top-key share check, so the next regression is a ticket instead of a 3 AM page.

Side note on a trap. Increasing spark.sql.shuffle.partitions does not fix this: all rows of the hot key still hash to a single partition.

Remember: one task runs forever means skew. Find the hot key, then filter, AQE, broadcast or salt.

Executors keep dying with OutOfMemoryError during a groupBy on a big table. How do you fix it? Senior

Tasks are holding more data than their memory share, from too few partitions, skew, or a groupByKey or collect_list building giant collections. I make tasks smaller and aggregate on the map side first, and raise memory only at the end.

Situation: tasks fail with Java heap space or GC overhead limit exceeded, are retried four times, and the stage fails.

Check first: the exact error (heap versus "container killed"), which stage, and whether only the big tasks fail (skew) or all of them (partitions too big). Check shuffle read per task and the partition count, and grep the code for groupByKey and collect_list.

Fix: (1) raise shuffle partitions so tasks are about 100 to 200 MB, or let AQE size them. (2) Replace groupByKey or collect_list with a real aggregation. (3) Fix skew. (4) Fewer cores per executor so each task has more memory. (5) Only then raise spark.executor.memory. If the message is "killed by YARN for exceeding memory limits", raise spark.executor.memoryOverhead instead.

Prevent: watch spill and GC time for every new job, and test with a peak-day volume.

Reasoning. A heap OOM during a groupBy means a task's share of memory was too small for the data it received. Possible reasons: partitions too big (few partitions for the volume), skew (one key's rows too many), or the aggregation itself builds large objects (collect_list, groupByKey), or too many cores share one heap.

Example. A 2 TB table is grouped with the default 200 partitions: 10 GB per task, with 4 tasks sharing an 8 GB executor heap. Each task has about 1 GB of execution memory. Even with spilling, hash aggregation of 10 GB cannot fit and the task dies. Setting 10,000 partitions (about 200 MB each) and using 3 cores per executor lets each task work in a few hundred MB and the job passes. No memory increase needed.

Sequence I follow. Read the error text and class (heap versus container killed). Check which tasks fail (all or the big ones). Fix partitions or skew. Replace collection aggregates. Reduce cores per executor. Add memory last. If the cause is "container killed", change overhead instead, which is outside the heap. After the fix, check spill and GC in the stage page to confirm that the margin is healthy, not just barely passing.

Remember: smaller tasks first, more memory last. Read the error to pick heap or overhead.

A job writes 200,000 tiny Parquet files every day and downstream queries are slow. Fix it. Intermediate

Too many write tasks each hold a bit of every partition value, so each writes a tiny file. I repartition by the partition column before writing, size the output at 128 MB to 512 MB per file, and compact the existing data.

Situation: listing takes minutes, readers create too many tasks, and the metastore is slow.

Check first: the number of write tasks, how many distinct partitionBy values each holds, and whether a streaming job appends tiny batches.

Fix: repartition($"date") before the write, maxRecordsPerFile as a safety net, and the REBALANCE hint or AQE. For old data run a compaction job (read each day, rewrite with coalesce or repartition) or use Delta OPTIMIZE or Iceberg rewrite_data_files.

df.repartition($"date")
  .write.option("maxRecordsPerFile", 5000000)
  .partitionBy("date").mode("overwrite").parquet(out)

Prevent: a check on file count and average file size at the end of the job. For streaming, a longer trigger interval plus scheduled compaction.

Why 200,000 files from one job. Say the job runs 2,000 write tasks and each holds rows of about 100 dates (data arrives mixed). Each task writes up to 100 files. That is 200,000 small files per run. It is the product of tasks and distinct partition values.

Fix with numbers. If the day's data is 60 GB and you want about 256 MB files, you need about 240 files per run. With partitionBy("date") and 30 dates: repartition(30 * 8, $"date") hashes each date to a few tasks (8 files per date), giving 240 files. If one date is much bigger than the others, add a salt column so the large date spreads across more tasks (hash on date and salt).

Cleaning the backlog. Compact old partitions in a separate job that reads one date at a time, repartitions to the right count, and writes to a temp location, then swaps (or run OPTIMIZE / rewrite_data_files in a table format). Do it off-peak, because compaction itself reads all those small files, and throttle it to avoid hammering object storage.

Verify. After the change: file count and average file size per partition (SQL on the table's files or a storage listing), plus the query's task count and listing time. Keep this check as part of the pipeline.

Remember: files per partition value = write tasks holding it. Repartition by the partition column.

The Spark UI shows tens of gigabytes of shuffle spill and the stage is very slow. What do you change? Senior

Spill means tasks are too big for their share of execution memory, so Spark writes to disk and merges back. I increase the shuffle partitions so tasks are about 100 to 200 MB, fix any skew, and give each task more memory.

Situation: the "Spill (Memory)" and "Spill (Disk)" columns are large and local disks are busy.

Check first: shuffle read per task. If it is 3 GB per task with 200 partitions, no task can hold its data. Check cores per executor and memory per task. One much bigger task points to skew.

Fix: raise spark.sql.shuffle.partitions or lower the AQE advisory size. Select only the needed columns before the shuffle so rows are narrower. Use fewer cores per executor or more executor memory. Compare spill and total time after each change.

Prevent: set partitions relative to data volume, not a fixed 200, and let AQE coalesce.

What spill means. Aggregations and sorts keep data in memory buffers. When the buffer exceeds the task's memory share, Spark sorts and writes the data to local disk as a chunk and starts again, then merges all chunks at the end. It works, but the cost is disk I/O plus extra serialization, often making a stage several times slower. "Spill (Memory)" is the size of the data in memory format, "Spill (Disk)" is the on-disk (compressed) size.

Example. Shuffle read is 3 GB per task (200 partitions of 600 GB). A task has about 1 GB of execution memory. It spills about 2 GB, perhaps several times. Moving to 3,000 partitions gives 200 MB per task, which fits, and spill drops to zero. Stage time falls from 40 to 8 minutes.

Order of fixes. (1) More, smaller partitions (or lower the AQE advisory size). (2) Check skew, because a single huge task will spill however many partitions you set. (3) Select only the needed columns and drop wide unused columns before the shuffle. (4) Fewer cores per executor so each task gets more memory. (5) More executor memory or a higher memory.fraction only as a last step. (6) Faster local disks (SSD) soften the cost if spill is unavoidable.

Not every spill is a problem. A small spill on a stage that is not the bottleneck can be ignored. Judge by time and by comparing runs.

Remember: spill = task bigger than its memory. Smaller tasks beat bigger heaps.

A Kafka to Spark streaming job falls further behind every hour. What do you check? Senior

Input is arriving faster than the job processes it. I read lastProgress to see where batch time goes, then fix the bottleneck: read parallelism, a slow sink, growing state, or skew.

Situation: Kafka lag grows, batch duration exceeds the trigger interval, and inputRowsPerSecond is above processedRowsPerSecond.

Check first: the breakdown in durationMs (read, state, write, commit). Is one stage slow, and is it skew? How many Kafka partitions and cores do I have? Did input grow, or did batch time grow for the same input (slow sink, growing state)?

Fix: if reading is the limit, add topic partitions and cores. If the sink is slow (a database), batch the writes or use a faster sink. If state grows, add or shorten the watermark, or switch to RocksDB. Use maxOffsetsPerTrigger so a catch-up does not create one gigantic batch. Lower the shuffle partitions for small batches (200 is often too many).

Prevent: alert on lag trend and batch duration over trigger interval, keep headroom (run at 50 to 60% capacity), and replay a busy day in testing.

Principle. The system is stable only if the processing rate is at least the input rate. Lag growth means the batch time exceeds the arrival interval, so each batch is bigger than the last (a feedback loop), and it needs to be broken at the slowest phase.

Read the progress report. In query.lastProgress: inputRowsPerSecond versus processedRowsPerSecond (the second must be higher), batchId spacing, and the durationMs map: addBatch (the actual work), getBatch, queryPlanning, walCommit, commitOffsets. Large addBatch means processing or sink is slow. Large walCommit means the checkpoint storage (for example S3) is slow.

After a task failure and retry, the output table has duplicate rows. How can that happen, and how do you stop it? Senior

File writes through Spark's commit protocol are safe against task retries, so duplicates come from side effects that are not idempotent: JDBC or API writes inside tasks, speculative tasks, a rerun with append, or a streaming restart. I make writes idempotent with an overwrite of the exact partition or a MERGE on a key.

Situation: counts are higher than the source after a run with failures, speculation or a restart.

Check first: the sink type. A retried task that inserts into a database inserts again. A speculative copy runs the side effect twice. Rerunning the whole job with append for the same date doubles it. A foreachBatch without the batch id repeats a batch after restart. The source itself (Kafka at-least-once producers) may deliver repeats.

Fix: overwrite exact partitions, or MERGE on a business key into a table format, or upsert on a primary key in the database. In foreachBatch use the batch id. Turn off speculation for non-idempotent sinks. Deduplicate on a key (row_number window or dropDuplicates). On S3, make sure a proper committer or table format is used.

Prevent: the rerun test (run twice, compare) and a unique-key check at the end of the pipeline.

Which writes are safe on their own. Spark's file output committer writes task output to temporary locations and promotes only the committed attempt, so a failed, retried or speculative task does not duplicate files. (On object stores, use a committer designed for it, or a table format, since plain rename-based commit is not atomic there.) So when duplicates show up, look beyond plain file writes.

Sources of duplicates, with an example each.

  • Task inserts into a database: foreachPartition sends INSERTs. The task fails after 800 of 1,000 rows and retries, and now 800 rows exist twice. Fix with an upsert on a key or write in one transaction per task attempt.
  • Speculation: two copies of a task both call an API. Disable speculation for that job or make the call idempotent.
  • Job rerun with append: the nightly job is rerun after a partial failure and appends the same day again. Fix with overwrite of that date or MERGE.
  • Streaming restart: foreachBatch re-runs the last batch. Use the batch id or a MERGE.
  • Upstream duplicates: the source is at-least-once, so the same event arrives twice. Deduplicate on an event id.

Backstop. Even with all of the above, add a final uniqueness assertion on the business key (count versus count distinct) and fail the run before publishing if it is violated. Catching duplicates early is cheaper than correcting downstream reports.

Remember: retries are normal. Make every write idempotent: overwrite the partition or merge on a key.

A query that filters on one date still reads the whole table. Why, and what do you change? Intermediate

Partition pruning is not kicking in because the filter is not directly on the partition column with a matching type, for example it wraps the column in a function or filters on a derived timestamp. I filter on the partition column itself with a literal of the same type.

Situation: the table is partitioned by event_date, but the scan reads all folders and the UI shows terabytes of input.

Check first: explain("formatted") on the scan. Is PartitionFilters empty? Common causes: date_format(event_date, ...) or a cast around the column, a filter only on event_ts (a different column), a value that comes from a subquery or join (needs dynamic partition pruning, Spark 3+, which works only for some join shapes), or folder names that are not key=value.

Fix: filter directly on event_date = '2026-11-16', add the partition filter beside the timestamp filter, or read the specific path. Select only needed columns and check PushedFilters for Parquet pushdown.

Prevent: document the partition column and its type, and review plans of new queries on large tables.

Why pruning is picky. Spark prunes partitions by evaluating the filter against partition column values (known from folder names) at planning time. It can do this only when the predicate is a simple comparison on the partition column itself with a constant. When the column is wrapped in a function or cast, Spark would have to evaluate the function for each folder name, and in many cases it does not.

Examples.

PredicatePrunes?
event_date = '2026-11-16'Yes

Related causes. Type mismatch (comparing a string partition to an int); a view that hides the partition column behind an expression; reading the table by path with the base path option mixed up so the partition column is not recognised; table statistics or metastore partition listing slow on very many partitions.

Remember: prune on the raw partition column. Wrap it in a function and Spark reads everything.

A join that should return about 10 million rows returns 4 billion and fills the disk. What happened? Intermediate

The join keys are not unique on both sides, so rows multiply: a key present 1,000 times on each side gives 1,000,000 output rows. I deduplicate or aggregate the side that should be unique, filter junk keys, and add any missing join condition.

Situation: output is far larger than either input, shuffle write is huge, and executors fail on disk space.

Check first: key uniqueness on each side with groupBy(key).count().filter(count > 1). Look for default values ("", "N/A", 0) that many rows share, and for a missing condition that became a cartesian product (CartesianProduct or BroadcastNestedLoopJoin in the plan).

Fix: keep the latest row per key with row_number. Filter junk keys. Add the missing condition columns (a date or tenant id). If many-to-many is intended, pre-aggregate before it. Add pipeline assertions: dimension key is unique, and a left join does not return more rows than the left side.

Prevent: uniqueness checks at dimension ingest and a post-join count guard.

Arithmetic of an explosion. A join returns, per key, left_count x right_count rows. If order 42 appears 3 times in orders (reprocessed feeds) and 5 times in shipments, you get 15 rows for it. At scale, one default key such as "unknown" held by 200,000 rows on each side makes 40 billion rows alone. So a few keys dominate the output.

Diagnosis flow.

  1. Compare row counts: inputs versus output. Anything above the expected is multiplication.
  2. For each side compute count(*) against count(distinct key); find keys with count above 1: groupBy(key).count().filter("count > 1").
  3. Sort the duplicates by count to find the junk keys (empty strings, 0, "N/A", -1).
  4. Check the plan for a missing condition (CartesianProduct, BroadcastNestedLoopJoin). A forgotten date or tenant column in a multi-column key is a frequent reason.

Fixes. Deduplicate the side that is supposed to be unique, choosing a rule (latest by timestamp via row_number). Remove placeholder keys before joining. Join on the complete key. If many-to-many is genuinely needed, aggregate one side to the grain you need before joining, so you multiply less. As protection, assert after the join that the row count did not increase for a left join with a unique right side, and fail the job if it does, instead of filling the disk.

Remember: output far bigger than inputs means duplicate keys. Check uniqueness before every join.

You have 400 cores, but a stage runs only 20 tasks and the cluster is idle. How do you improve it? Intermediate

The stage has too few partitions, so most cores have nothing to do. I find where the 20 comes from (a few big non-splittable files, an early coalesce, a low shuffle partition setting, or an unpartitioned JDBC read) and spread the work with a repartition.

Situation: the stage page shows 20 long tasks and most executors sit idle.

Check first: the source of 20. Twenty gzip CSV files give exactly one task per file because gzip is not splittable. An earlier coalesce(20) or repartition(20) may still be in the plan. spark.sql.shuffle.partitions may be set low. A JDBC read without partition options gives one task. Also check the Executors tab that I actually got the executors I asked for.

Fix: for non-splittable files, repartition right after the read so later steps are parallel (the read itself stays at 20 tasks), and convert to Parquet long term. Remove the early coalesce or move it just before the write. Raise shuffle partitions to 2 to 4 times the cores, or leave it to AQE with a high start. For JDBC, set partitionColumn, lowerBound, upperBound and numPartitions (an indexed, evenly spread column, and a number the database can handle).

Prevent: look at task counts on the first run of any new job.

Principle. Spark can run at most as many tasks at the same moment as there are partitions in the stage. 20 partitions can use at most 20 cores, however many exist. So find out why the partition count is 20.

Investigate in this order.

  1. Which stage? If it is the first (read) stage, the input is the cause. If it is a later one, the shuffle partition setting or an earlier repartition is.
  2. Input is 20 big non-splittable files (gzip CSV or JSON, some binary formats): one task per file, no way to split. Check file names and compression. Remedy: after the read, repartition(2000) to parallelise everything downstream, and in the longer term write splittable formats (Parquet, or bzip2/LZO with an index) from the source.
  3. A hard-coded coalesce(20) or repartition(20) left in the code from an earlier time. Removing it or moving it to the end (just before the write) restores parallelism.
  4. Low spark.sql.shuffle.partitions set in the job or cluster defaults, with AQE merging more aggressively than needed (check the advisory partition size and min partition settings).
  5. JDBC without partition options (one task) or a source with one partition (small Kafka topic).

Verify resources too. In the Executors tab check that you actually received the executors you requested (dynamic allocation and quota may have given fewer), and that tasks are not waiting on scheduling or locality delay.

Target. Two to four tasks per core, each with about 100 to 200 MB, as in the partitions question.

Remember: parallelism = partitions. Few tasks and idle cores means find who capped the partition count.
