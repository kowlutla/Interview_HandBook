Case study 17 · Worked solutions

Design a Message Queue

We design a Kafka-class distributed log from an empty whiteboard: how a broker stores messages on disk, how partitions and replicas give throughput and durability, how consumers share work and remember where they are, and what happens when machines die. The target is one million messages per second, and we build up to it step by step instead of reciting a product manual.

The conceptual background (queue versus log versus publish/subscribe, what a partition and an offset are) is taught in Chapter 34, and patterns built on top of queues (fan-out, retries, dead letters) are in Chapter 35. Here we do the opposite job: assume the interviewer says "do not use Kafka, build one", and derive every mechanism from a requirement and a number.

How to approach this problem (read this first)

What the interviewer is really testing. Nobody expects you to recite a product manual. The interviewer wants to see three things. First, can you explain why a log on disk is fast (sequential writes, page cache, batching) instead of just saying "Kafka is fast". Second, can you keep acknowledged data safe when machines die, which means replication, the in-sync set, and who is allowed to become leader. Third, can you explain how many consumers share work and remember their place, and what "exactly once" honestly means. Everything else is detail around those three hard parts.

The thinking order, step by step

  1. Clarify the shape of the service. Ask whether this is a shared platform, how many consumers read the same message, and whether replay is needed. Say: "Before I design anything, I want to know if several teams read the same stream and if they need to re-read old data." This comes first because replay and fan-out decide whether messages are deleted when read or kept as a log.
  2. Fix the guarantees. Ask about ordering, durability and delivery. Say: "I will assume order per key, no loss of acknowledged messages after one machine dies, and at-least-once delivery." These three words drive almost every later choice, so pin them down before any numbers.
  3. Estimate throughput first, then storage. Multiply messages per second by size to get bytes per second, then multiply by the replication factor and retention. Say: "One million messages a second at 1 KB is about 1 GB a second, so I am sizing for sequential disk, not random writes." Bytes per second comes first because it tells you whether disk, network or memory is the bottleneck.
  4. Draft the producer and consumer calls. Sketch Produce with acks, and Fetch with an offset. Say: "Producers send batches to the leader of a partition, and consumers pull from an offset." The offset is the idea that holds the whole API together.
  5. Start with one box, one log file. Say: "The simplest design is one server with an append-only file." Then list what breaks: one disk limits throughput, one machine loses data, and consumers need to share work. Each failure names the next feature.
  6. Evolve to partitions plus replicas. Say: "I split the topic into partitions for throughput, and give each partition a leader and two followers in different zones for durability." Draw the cluster, then the produce sequence with acks.
  7. Dive into replication and the in-sync set. This is the first place the interviewer will push. Explain the high watermark, why election is only from in-sync replicas, and what unclean election costs.
  8. Dive into consumers. Groups, offsets, commit order, rebalancing, then the idempotent producer and transactions. Say: "Commit after processing gives at-least-once, so handlers must be idempotent."
  9. Close with failures, scaling and cost. Walk each failure (follower, leader, zone, consumer), then quotas, tiered storage and what changes at ten times the load.

The decision points

  • Log or per-message queue? Ask: do many groups need the same data, and is replay needed? Yes to both here, so a retained log (section 10 compares the two).
  • Push or pull? Ask: who controls the speed? Pull lets slow consumers fall behind safely and makes batching natural, so pull.
  • Majority quorum or in-sync set for replication? Ask: what does each extra copy cost? At about 0.9 PB raw, copies are the main cost, so the in-sync set with f+1 copies wins (section 7).
  • Commit before or after processing? Ask: is losing a message worse than seeing it twice? For business events, duplicates are easier to handle than loss, so commit after.
  • Consistency or availability when replicas are lost? Ask: is a stalled partition worse than a lost message? For orders, wait (clean election). For clicks, promote (unclean).
Interview tip Build the design by breaking the one-box version out loud. "One log file breaks in three ways, so I add partitions, then replicas, then consumer groups" shows the interviewer that each component exists for a reason, which is worth more than naming every feature.

Common mistakes on this problem

  • Saying "disk is slow" and building an in-memory queue. Fix: explain that sequential disk plus page cache is fast, and show the arithmetic.
  • Promising global ordering. Fix: promise order per partition only, and route by key.
  • Claiming exactly-once with no caveat. Fix: say at-least-once plus idempotent processing, and name where the boundary is.
  • Forgetting what happens to the old leader. Fix: mention epochs and truncation of the uncommitted tail.
  • Picking partition count at random. Fix: derive it from throughput per partition and the number of consumers you want.
  • Ignoring the cost of rebalances. Fix: mention cooperative rebalancing and static membership.

1. Problem statement and clarifying questions

The prompt: "Design a distributed message queue that lets producers publish messages and consumers read them, at very high throughput, without losing acknowledged messages." 2. Requirements and scope

2.1 Functional

  • Create topics (named streams), each split into a configurable number of partitions.
  • Producers append messages (key, value, headers, timestamp) to a topic; the system chooses the partition by key hash or round robin.
  • Consumers read messages in order from a partition starting at any offset; consumers cooperate in consumer groups so each partition is read by exactly one member of a group at a time.
  • Consumers commit progress (offsets) so a restart resumes where it stopped.
  • Configurable retention (time or size) and log compaction.
  • Opt-in idempotent producer and atomic multi-partition transactions.

2.2 Non-functional

  • Throughput: 1M msg/s peak (1 GB/s) with horizontal scale-out.
  • Durability: no loss of acknowledged messages under a single broker failure.
  • Availability: a partition stays writable through one broker failure after a short failover (seconds).
  • Latency: milliseconds when batching is tuned for it; throughput is the primary goal.
  • Scalability: add brokers and partitions without downtime.

2.3 Out of scope

Per-message priorities, delayed or scheduled delivery, arbitrary message filtering on the broker, a SQL query layer, cross-region active/active replication, and a stream-processing engine. We touch some of these in the evolution section, but they would distract from the core: a fast, durable, replicated log.

3. Estimation with real arithmetic

Estimation drives the design here more than in most problems, because the numbers decide whether a spinning disk, an SSD, or memory is the right primary store.

3.1 Throughput

  • Peak ingress: 1,000,000 msg/s × 1 KB = 1,000 MB/s = about 1 GB/s. Average: 500,000 × 1 KB = 500 MB/s.
  • Replication factor 3: the leader receives each byte once, then two followers fetch it. Cluster-internal replication traffic at peak is 2 × 1 GB/s = 2 GB/s, and total bytes written to disks across the cluster is 3 × 1 GB/s = 3 GB/s.
  • Three consumer groups each read the whole stream: egress 3 × 1 GB/s = 3 GB/s at peak. Mostly served from the page cache (section 5.2).
  • Total network at peak across the cluster: 1 (in) + 2 (replication) + 3 (out) = 6 GB/s, roughly 48 Gbit/s.

3.2 Storage

  • Per day at average rate: 500 MB/s × 86,400 s = 43.2 TB/day (one copy).
  • 7-day retention: 43.2 × 7 = 302 TB; with RF 3 = about 907 TB, say 0.9 PB raw.
  • With 70 percent target disk utilization we provision 0.9 / 0.7 = 1.3 PB.

3.3 Broker count

  • Disk write per broker: we want each broker to stay near 100 to 150 MB/s of combined leader and follower writes so that reads and compaction have headroom. 3 GB/s ÷ 150 MB/s = 20 brokers by write bandwidth.
  • Storage: 1.3 PB ÷ 30 brokers = about 43 TB per broker (for example 12 × 4 TB drives in a JBOD layout). Storage prefers more brokers than bandwidth does, so we choose 30 brokers, leaving per-broker peak write at 3 GB/s ÷ 30 = 100 MB/s.
  • Network per broker: 6 GB/s ÷ 30 = 200 MB/s, comfortably inside a 10 Gbit/s NIC (1.25 GB/s), which also leaves room for rebuilds after a failure.

3.4 Partitions

  • A single partition is written by one leader thread and read sequentially. A prudent target is about 10 MB/s produce per partition. 1 GB/s ÷ 10 MB/s = 100 partitions minimum for the hottest topic.
  • Consumers are the other bound: if one consumer thread can process 5 MB/s of business logic, a group needs 1,000 MB/s ÷ 5 = 200 consumers, hence at least 200 partitions. We provision 600 partitions for the big topic (3x headroom, divisible by many group sizes).
  • Across the platform, 3,000 partitions with RF 3 gives 9,000 replicas, which is 300 per broker. That is well inside the comfortable range (each replica is a few open files and a memory-mapped index).

3.5 Segment and index sizing

  • Segment size 1 GB. A sparse index entry every 4 KB of log, each 8 bytes (4 byte relative offset, 4 byte file position): 1 GB ÷ 4 KB = 262,144 entries × 8 B = 2 MB per segment index. A broker with 43 TB holds about 43,000 segments, so all indexes total roughly 86 GB, memory-mapped lazily, and only the hot ones are resident.

3.6 Memory and page cache

  • Each broker: 64 GB RAM, 6 GB JVM heap (or equivalent), roughly 55 GB left to the operating system page cache.
  • Ingress per broker averages 500 MB/s ÷ 30 = about 17 MB/s of leader writes (plus follower writes, about 50 MB/s total). 55 GB of cache therefore holds around 55,000 MB ÷ 50 MB/s = 1,100 s, about 18 minutes of recent data. Consumers that keep up read the tail straight from memory and never touch the disks.
Key idea The numbers show that 1 GB/s is easy only because every access is sequential and batched. 1M individual random writes per second would need an enormous SSD fleet. 1 GB/s of sequential appends is a couple of dozen cheap machines.

4. API design

4.1 Producer API

Produce(topic, [records], acks = 0 | 1 | all, producerId, epoch, baseSequence, txnId?)
  record = { key: bytes, value: bytes, headers: map, timestamp: int64 }
  response per partition = { partition, baseOffset, errorCode, logAppendTime }

Records are sent in batches per partition. The batch is also the unit that is compressed, checksummed, replicated and written to disk. producerId, epoch and baseSequence support idempotence (section 8).

4.2 Consumer API

Fetch(topic, partition, fetchOffset, maxBytes, maxWaitMs, minBytes)
  response = { highWatermark, records[], lastStableOffset }
JoinGroup(groupId, memberId, subscriptions)   -> assignment
Heartbeat(groupId, memberId, generation)
CommitOffset(groupId, topic, partition, offset, generation)

minBytes and maxWaitMs give long polling: the broker parks the fetch until enough data exists or a timeout passes, so idle consumers do not spin. Consumers pull; the broker never pushes. Pull lets a slow consumer fall behind safely (the data is still on disk), makes batching natural, and moves flow control to the reader.

4.3 Admin and metadata API

CreateTopic(name, partitions, replicationFactor, configs)
Metadata(topics) -> { brokers[], per partition: leader, leaderEpoch, replicas[], isr[] }

Clients ask any broker for metadata, cache it, and send each produce or fetch directly to the leader of the target partition. There is no central router in the data path.

5. Data model and storage choice

5.1 Why an append-only log

The central decision is the on-disk structure. A message queue does three things to data: append to the end, read a contiguous range starting somewhere, and delete from the front. A B-tree (see Chapter 19) is built for random updates in place and pays write amplification we never need. An LSM tree sorts by key, which also is not needed because order here is arrival order. A plain append-only file is both the simplest and the fastest structure: writes are sequential, reads are sequential, and deletion is dropping whole files. The idea is the same write-ahead log that databases use for durability, promoted to be the primary storage.

5.2 Segments, index and page cache

Each partition is a directory of segment files. A segment is a pair (or trio) of files named by the offset of its first message: 00000000000012345678.log holds records, .index maps offsets to file positions, and .timeindex maps timestamps to offsets. Only the newest segment is written (the active segment); when it reaches 1 GB (or a time limit) the broker rolls a new one. Old segments are immutable, which makes caching, deletion, copying to cold storage and compaction all simple.

Walkthrough. The top row is one partition as a folder of files. The two blue-green boxes are closed segments, the amber box is the active segment that takes all new writes, and the arrow on the right is the next write. The bottom row traces a read of offset 2,000,500. 1. The broker picks the segment whose file name is the largest first-offset not above the target, here 2000000. 2. It binary searches that segment's sparse index (blue box) and lands on the floor entry, relative offset 452 at file position 61,440. 3. It seeks to that position in the log file (amber box) and scans forward over batch headers to offset 500. 4. The bytes come from the page cache (purple box) if they are recent, and go to the socket by zero copy. It is drawn this way to show that a lookup never reads much: a few kilobytes at most, instead of walking the whole log or keeping a full index. On a whiteboard, draw the three segments first, then the index with one highlighted row. If you remove the index, every fetch must scan a segment from its start. If you remove segments, deletion means rewriting one giant file.

Why a sparse index. Indexing every message would cost 8 bytes per 1 KB message, an index 0.8 percent of the data, and would force random index writes. A sparse index of one entry per 4 KB shrinks it 4x again and is written only as the log grows. A lookup does a binary search for the greatest indexed offset less than or equal to the target, then scans forward at most a few kilobytes. That scan is cheap because one batch header gives its length, so the broker can skip whole batches without decoding records.

Why disks are fine. Sequential disk throughput on commodity drives is hundreds of MB/s, and on SSDs several GB/s, while random access can be 100 to 1,000 times slower. Our access pattern never seeks except at consumer start. The broker also does not keep its own cache: it writes through the operating system, which keeps recently written pages in the page cache. The broker does not call fsync for every write; durability comes from replication to other machines (section 6.3), and the OS flushes dirty pages in the background. Skipping a private cache avoids duplicating data in memory (once in a heap cache, once in the page cache), avoids garbage collection pauses on a huge heap, and means a broker restart keeps its warm cache.

Zero copy. A naive send of a file over a socket copies data four times: disk to kernel buffer, kernel to user buffer, user to socket buffer, socket to NIC. Because the log format on disk equals the wire format, the broker can use the sendfile system call, which moves pages from the page cache straight to the network card with no user-space copy. Consumers reading the tail therefore cost the broker almost no CPU, which is why three consumer groups per topic are affordable. (Caveat: with TLS enabled the data must be encrypted in user space, so zero copy is lost and CPU becomes the limit; we return to this in cost.)

6. A first simple design, then the scaled architecture

6.1 One box

Start with a single server and a single log file: producers append, consumers read from an offset, a background job deletes old segments. This already supports replay, many independent readers (each tracks its own offset), and trivially high throughput. It fails in three ways, and each failure drives one major part of the design:

  1. One writer, one disk limits throughput. Fix: split the topic into partitions, spread over many brokers.
  2. The machine dies and the data is gone or unavailable. Fix: replicate every partition to other brokers with one elected leader.
  3. Several consumer processes want to share the work without reading the same message twice. Fix: consumer groups assign each partition to one member and store committed offsets.

6.2 Scaled architecture

Key properties of this layout: (1) the load is balanced because leaders, and therefore client traffic, are spread evenly over brokers; (2) the replica set of a partition spans three availability zones so a zone loss costs at most one replica; (3) clients bypass the controller entirely, so the controller is not a throughput bottleneck.

6.3 Produce flow with acks

Walkthrough. Read this as a sequence diagram: time runs downward, each vertical line is one machine, and solid arrows are requests the producer or leader sends while dashed arrows are the followers' long-poll fetches. The green arrows carry data back. 1. The producer sends one compressed batch to the leader. 2. The leader assigns offsets 500 to 599 and appends to the active segment in the page cache. 3. Both followers already have fetches waiting, so the new data completes them. 4. The leader returns the batch to each. 5. Each follower appends it. 6. Each follower's next fetch asks for offset 600, which doubles as the acknowledgement that it stored everything below. 7. The leader sees every in-sync replica at 600 and moves the high watermark. 8. Only now does it answer the producer. The design reuses the fetch path for replication, so there is no separate replication protocol. On a whiteboard, mark step 7 clearly, since that is the commit point. If you answer the producer at step 2 you get acks=1 and a loss window.
  1. The producer sends a compressed batch to the partition leader (found from cached metadata).
  2. The leader checks authorization, quotas and the idempotence sequence, assigns consecutive offsets, and appends to the active segment (this lands in the page cache).
  3. Followers have fetch requests parked at the leader; the new data completes them.
  4. Each follower appends the bytes to its own log.
  5. The follower's next fetch carries the new offset, telling the leader it is caught up.
  6. When all members of the in-sync replica set (ISR) have the batch, the leader advances the high watermark and only data below the high watermark is visible to consumers.
  7. With acks=all the leader now responds to the producer.

6.4 Producer-side batching and acks

Per-message requests would waste the network and disk: a 1 KB message wrapped in a request header spends a round trip for 1 KB of payload. Producers therefore accumulate records per partition in memory and send when a batch reaches batch.size (say 64 KB) or has waited linger.ms (say 5 ms), whichever comes first. At 1,000 msg/s on one partition that is a batch of 5 records every 5 ms; at 100,000 msg/s per producer the batches fill by size and linger never triggers. Batching gives order-of-magnitude throughput gains for a few milliseconds of latency, and it lets compression work (a compressor needs many similar records to find redundancy). The producer keeps several requests in flight per broker (default 5) to hide round-trip latency.

acksProducer is told success whenLoss windowTypical use
0Bytes are handed to the network, no replyAny broker or network failure loses data silentlyMetrics, best-effort telemetry
1Leader appended (not yet replicated)Leader dies before followers fetch: acknowledged data lostLogs where rare loss is fine, lowest latency
allEvery in-sync replica has the batch AND ISR size is at least min.insync.replicasNone while at least one ISR member survivesBusiness events, default for important topics

With RF 3 and min.insync.replicas=2, acks=all tolerates one broker failure without losing data and without losing write availability. If two replicas are down, the ISR falls to 1, below the minimum, and the leader rejects writes (a deliberate choice of consistency over availability for that partition; see Chapter 24 for the general leader-follower tradeoffs and quorum reasoning).

Messages are partitioned by hash(key) mod numPartitions, so all events for one key (say one order id) go to one partition and keep their relative order. Without a key, producers use a sticky strategy: fill one batch for one partition, then move to another, which produces full batches instead of many tiny ones.

7. Deep dive 1: replication, ISR and leader election

7.1 Why ISR instead of a pure majority quorum

A Raft-style group (Chapter 29) commits an entry when a majority has it, so with 3 replicas the commit needs 2, and the slowest replica never delays a write. Kafka-style replication instead tracks a dynamic in-sync replica set: the replicas that are caught up with the leader (within replica.lag.time.max.ms, typically 30 s, of having fetched up to the log end). A write is committed when all ISR members have it. The two schemes compare as follows.

PropertyMajority quorum (Raft style)ISR (wait for all in-sync)
Replicas needed to survive f failures with no committed-data loss2f + 1 (3 replicas tolerate 1)f + 1 (2 replicas tolerate 1; 3 tolerate 2 if min ISR is 1)
Write latencyMedian of replicas (a slow minority is ignored)Slowest ISR member, but a slow one is evicted from the ISR after the lag timeout
Storage cost for given fault toleranceHigherLower; matters at petabytes
ElectionVoting among replicas, handled by the algorithmAny ISR member is safe; chosen by controller, so a separate consensus (metadata quorum) is needed
Failure modeUnavailable if majority lostUnavailable if ISR below min, or if all ISR members lost

Choice: ISR, because at 0.9 PB raw the replica count is the cost driver, and because tolerating f failures with f + 1 copies is cheaper than 2f + 1. The price is that we need an external strongly consistent coordinator for leadership, which we already have for metadata (section 7.3). The data path stays cheap; the consensus runs only on rare metadata changes.

7.2 High watermark, log end offset and truncation

Walkthrough. Each horizontal bar is one replica's log, drawn longer when it holds more offsets. Amber is the leader, green is a follower, and the red bar is a log holding data nobody else has. The top block is the healthy state: B1 and B2 hold offsets up to 599, B3 lags at 549. The label LEO means log end offset, the next offset a replica would write. The high watermark is the offset below which data is committed and visible to consumers. The lower block follows a crash. 1. B1 dies after taking offsets 600 to 650 that only it holds. 2. The controller elects B2, an in-sync replica, and bumps the epoch to 5. 3. B1 comes back with a longer log, drawn in red. 4. It asks the new leader where epoch 4 ended. 5. It truncates 600 to 650, then fetches from B2 as a follower. This picture shows why election is limited to in-sync replicas and why consumers read only below the high watermark. On a whiteboard, draw the red tail and cross it out. Remove epochs and the old leader could keep a divergent tail.

Leader epoch is a number that increments on each leadership change and is stamped on batches. When a restarted replica rejoins, it asks the new leader "where did epoch N end?" and truncates to that offset. Without epochs, replicas that merely compared high watermarks could diverge silently after a rapid double failover, a historical source of data loss bugs.

7.3 Controller election and metadata

Leader election for a partition must be decided by one authority, otherwise two brokers could both think they lead (split brain; see Chapter 29). We run a small controller quorum (3 or 5 nodes) using Raft to maintain a replicated metadata log: topic definitions, partition replica assignments, current leader and ISR for each partition, broker registrations. One quorum member is the active controller. Brokers register and send heartbeats to the controller (every few seconds, session timeout about 10 s). When a broker's session expires:

  1. The controller marks the broker fenced and finds every partition it led.
  2. For each, it picks the first live replica in the assignment that is in the ISR, bumps the leader epoch, records the change in the metadata log (committed by the Raft majority) and publishes it to brokers.
  3. Brokers update their roles; clients receive a NotLeaderForPartition error on their next request, refresh metadata and retry the new leader.

Thousands of leaders can be moved in seconds because the decision is one metadata record per partition and followers already hold the data. If the active controller itself dies, the quorum elects a new one in a second or two, and the new controller already has the full metadata log in memory (this is the reason metadata lives in a Raft log rather than being re-read from an external store).

7.4 ISR shrink and unclean election

If a follower falls behind by more than the lag timeout (slow disk, GC, network trouble), the leader removes it from the ISR and reports the new ISR to the controller. Writes continue with a smaller ISR, which is the availability benefit, but the durability margin is smaller. If the ISR shrinks to just the leader and that leader dies, no in-sync replica exists. There is a choice, and it is a classic consistency versus availability decision:

PolicyBehaviourCostUse when
Clean only (unclean.leader.election=false)Partition stays offline until an ISR member returnsUnavailable (maybe for minutes or until the machine is repaired)Orders, payments, anything where loss is worse than delay
Unclean allowedAn out-of-sync replica becomes leader immediatelySilently loses the messages it lacked; consumer offsets may point beyond the new log endMetrics, click streams where being up beats completeness

Our default: clean only, min.insync.replicas=2, RF 3, acks=all for tier-1 topics. Combined, the system never acknowledges data that exists on fewer than 2 machines, and never promotes a replica that missed acknowledged data.

8. Deep dive 2: consumer groups, offsets and delivery semantics

8.1 Consumer groups and rebalancing

A consumer group is a set of consumer processes that share a group.id. The group's contract: each partition of the subscribed topics is assigned to exactly one member at a time, so members process disjoint subsets in parallel and per-partition order is kept. Parallelism is capped by partition count (600 partitions, at most 600 useful consumers). A second group with a different id receives its own full copy, which is how publish/subscribe fan-out works over a log.

Membership is managed by a group coordinator, which is simply the broker that leads the __consumer_offsets partition that the group id hashes to. That makes coordinators scale out with no new component and gives them automatic failover.

Rebalances are the main operational pain of group consumption. In the eager protocol every member revokes all partitions, so a deploy that restarts 200 consumers one by one triggers 200 full pauses. Mitigations: cooperative rebalancing (only the moved partitions stop), static membership (a consumer with a fixed instance id that restarts within the session timeout keeps its partitions without any rebalance), and a sticky assignor that minimizes movement. Heartbeats run on a background thread; if the processing loop exceeds max.poll.interval the member is considered dead, so slow handlers need smaller batches or an async hand-off.

8.2 Offsets and commit strategies

The consumer's position is a single integer per partition, the offset of the next message to read. To survive restart, it commits that integer to the coordinator, which writes (group, topic, partition) -> offset into the compacted __consumer_offsets topic. When a partition is assigned, the consumer starts at the committed offset (or at earliest or latest if none exists, by configuration). Where the commit happens relative to processing determines the delivery guarantee.

StrategySequenceIf crash between stepsResult
Commit before processingcommit, processOffset says done but work not doneAt-most-once: message lost
Commit after processingprocess, commitWork done but offset not stored; reprocessed after restartAt-least-once: duplicates (default recommendation)
Atomic process + commitboth in one transaction (same DB, or Kafka transaction)Neither happened, or both didExactly-once effect

A batch commit every N messages or every second (async) is typical for throughput; the cost is that after a crash up to a batch worth of messages replay, so handlers must be idempotent (for patterns see Chapter 35).

8.3 Idempotent producer

The produce path has its own duplicate source: a producer sends a batch, the leader appends it, the ack is lost, and the producer retries, creating a second copy. The idempotent producer fixes this without the broker storing every message id. Each producer gets a producerId from the broker (and an epoch). It numbers batches per partition with a monotonically increasing sequence number. The leader remembers, per (producerId, partition), the last few sequence numbers and offsets it accepted (the last 5 batches match the 5 in-flight limit). A retried batch with an already-seen sequence is acknowledged with the original offset and not appended; a sequence gap triggers an error, which also means that with retries, ordering in one partition is preserved. The state is rebuilt after failover from the producer-id snapshots and the log itself, because the leader's followers see the same producer fields in each batch.

Scope is limited: it dedups within one producer session and one partition. A restarted producer gets a new id unless it uses a stable transactional.id.

8.4 Transactions and exactly-once processing

The common stream-processing loop is consume, transform, produce to another topic, commit the input offsets. For exactly-once, the output records and the input offset commit must be atomic. The transaction protocol:

Walkthrough. Four vertical lines are the producer, the transaction coordinator, the output partitions and the offsets topic. Time runs down. Black arrows are the producer's requests, green arrows are the coordinator's follow-up writes. 1. The producer registers with its stable transactional id, which bumps its epoch and fences any older instance. 2. It tells the coordinator which partitions it will write, and that is logged. 3. It writes records to the output partitions, where they exist on disk but stay hidden from read_committed readers. 4. It adds the input offsets to the same transaction. 5. It asks to commit. 6. The coordinator writes PREPARE_COMMIT to its log: this is the decision point, and after it the outcome cannot be undone. 7. The coordinator writes commit markers into every touched partition and the offsets topic. 8. It writes COMPLETE and readers can now see the records. The producer is answered after step 6. It is drawn this way to show that one logged decision makes many writes atomic. Remove step 6 and a crash could leave some partitions committed and others not.

Records of an uncommitted transaction are physically in the partition logs (so they do not need a separate buffer), but consumers set to read_committed never see them: the broker serves only up to the last stable offset (the first offset of the earliest still-open transaction) and filters aborted records using an aborted-transactions index. A stable transactional.id plus an epoch fences zombie producers: when a replacement starts, the old instance's writes are rejected. Cost: one extra commit-marker round per transaction, so transactions are batched (commit every 100 ms rather than per message), and a long-open transaction delays visibility of everything after it in that partition.

Watch out "Exactly-once" holds only inside the system boundary: records in topics and offsets. An external side effect (an email, an HTTP call, a write to a non-transactional database) can still repeat; for those, make the handler idempotent with a dedup key or an outbox, as in Chapter 35.

9. Deep dive 3: retention, compaction and ordering

9.1 Retention

Retention deletes whole closed segments, never individual messages. A background task checks each partition and removes segments whose newest record is older than retention.ms (7 days) or while the partition exceeds retention.bytes. Deleting a file is a constant-time metadata operation, so it costs far less than an update-in-place store. One caveat: because a segment is deleted only when its newest record expires, and the active segment is never deleted, a quiet partition can keep much older data than 7 days; time-based segment rolling (for example roll at least every 24 hours) bounds that.

9.2 Compaction

Some topics hold state, not events: "the current profile of user 42", "current price of item 9", the consumer offsets topic itself. For these we want to keep at least the latest value for every key instead of a time window. Log compaction does this. A cleaner thread scans a partition's closed segments and builds an in-memory map of key to the latest offset (about 24 bytes per key with a hash of the key, so 1 GB of cleaner memory covers around 40 million keys). It then rewrites the segments, copying only records that are the newest for their key, into new segments, and swaps them in. Offsets of surviving records do not change; compaction just leaves gaps. A delete is a record with a null value (a tombstone), which is kept for delete.retention.ms so that slow consumers see the delete, then removed.

OptionKeepsCleanup costReplay semanticUse for
Time/size deleteEverything for the windowNear zero (drop files)Full history for the windowEvent streams, logs, clicks
CompactionLatest value per key, unbounded timeRead and rewrite IO, cleaner CPU, memory mapRebuilds current state; history is lostChangelogs, config, offsets, caches
Both (compact,delete)Latest per key, but only inside a time windowBoth costsBounded stateSession-like state with expiry

Compaction is the same garbage-collection idea as an LSM tree's compaction (Chapter 19), applied to a log: duplicates of a key are the stale versions. The cleaner only compacts closed segments and throttles IO so it does not hurt producers, and the "dirty ratio" (fraction of the log not yet compacted) triggers it.

9.3 Ordering

  • Within a partition, order equals append order, and consumers see exactly that order. No ordering is promised across partitions.
  • Order for a key is therefore achieved by routing all messages for the key to one partition. This couples correctness to the partition count: if you increase partitions from 600 to 900, hash(key) mod N changes and a key's later events move to a different partition, breaking per-key order across the change. Practice: over-provision partitions up front, or accept a one-time drain-and-switch when resizing keyed topics.
  • Producer retries can reorder batches if multiple requests are in flight and an earlier one fails. Idempotence (with at most 5 in-flight) keeps order because the broker rejects out-of-sequence batches and the client resends in sequence.
  • Consumer side: process each partition on a single thread, or dispatch to workers keyed by message key, otherwise parallel handlers reorder results.
  • A hot key (one customer producing 30 percent of traffic) pins load to one partition. Mitigation: salt the key into sub-keys when per-key strict order is not needed, or give the hot tenant a dedicated topic.

10. Contrast: log (Kafka-style) versus per-message-ack queue (SQS-style)

There is no offset, order is only best-effort in standard queues, and acknowledgement is per message.

11. Scaling, hot spots, backpressure and multi-tenancy

11.1 Scaling out

  • Add brokers: new brokers start empty. A reassignment moves chosen partition replicas to them by having them join as additional followers, catch up by fetching, enter the ISR, and then the old replica is removed. Throttle replication (for example 50 MB/s per broker) so rebalancing traffic does not starve normal traffic. Moving 43 TB at 50 MB/s takes 43,000,000 MB / 50 = 860,000 s, about 10 days, which is why a cluster rebalancer moves a fraction at a time and why tiered storage (section 12) makes elasticity much faster: only the local hot part, a few hours of data, must move.
  • Add partitions: raises parallelism but changes key-to-partition mapping (section 9.3).
  • Rack-aware placement: replicas of a partition go to different availability zones.
  • Leader balancing: a periodic "preferred leader" election returns leadership to the first replica in the assignment so no broker accumulates too much leader traffic after failures.

11.2 Hot spots

A broker is hot when its leader partitions receive more bytes than average. Causes: a hot key, an unevenly sized topic, or too many leaders after failover. Remedies: move the hottest partition to a lighter broker, split the key space, size partitions by bytes not by count, and monitor per-broker bytes in/out and request-handler idle percentage.

11.3 Backpressure

Overload must degrade gracefully. We apply backpressure at several layers:

  1. Producer client buffer: buffer.memory (say 64 MB) bounds queued batches; when full, send() blocks for max.block.ms and then fails, pushing the pressure into the application.
  2. Broker request queues: a bounded queue between network threads and IO threads; if full, network threads stop reading sockets, so TCP windows close and the clients slow.
  3. Quotas: the broker computes a throttle time and delays the response (and mutes the channel) for clients exceeding their byte rate; well-behaved clients just see longer latency.
  4. Pull consumers: a consumer that cannot keep up simply reads more slowly; lag grows but nothing breaks, because disk absorbs the backlog. Backlog is bounded by retention: lag beyond 7 days means data loss for that group, which is the alert threshold to watch.

11.4 Multi-tenancy and quotas

With hundreds of teams on one cluster, one noisy tenant must not harm others. Controls:

12. Tiered storage

At 0.9 PB raw on local disks, 7 days of retention is costly and makes broker replacement slow. But most reads touch only the last minutes (page cache) and the long tail is for occasional replay. Tiered storage keeps a short local tier (for example 6 hours) on broker disks and offloads closed segments to an object store (S3-like), keeping the 7 days or even months there.

Walkthrough. Arithmetic: the hot tier holds 6 hours: 500 MB/s × 21,600 s = 10.8 TB per copy, 32 TB with RF 3, about 1 TB per broker instead of 30 TB. The object store keeps one durable copy of 302 TB (the store replicates internally). That cuts expensive broker SSD capacity by roughly 28x and makes adding or replacing a broker a matter of copying about 1 TB, in under an hour at 400 MB/s, instead of days. Design details: upload only closed segments below the high watermark; keep the index and leader-epoch checkpoint with each segment so a new leader can serve it; retention deletes remote segments by metadata; and a metadata record per segment is tracked in an internal topic. Tradeoffs: the first byte of a cold read is slower (tens of milliseconds), object store request fees apply, and compacted topics are harder to tier.

13.1 Consistency and idempotency decisions in one place

  • Committed means present on all ISR members (at least 2 by min ISR). Consumers read only committed data.
  • Leadership is changed only by the Raft-backed controller and is fenced by an epoch, so there is at most one effective leader per partition per epoch.
  • Retry safety through producer idempotence; effectively-once across topics through transactions; everything outside needs idempotent consumers.
  • Durability does not depend on fsync per write; it depends on independent failure of replicas in different zones. If a whole region loses power simultaneously, un-flushed page cache on all three replicas can be lost. That is a conscious tradeoff; set a periodic flush or choose cross-region mirroring when the risk matters.

13.2 Multi-region note

A stretch cluster across regions pays inter-region latency on every acks=all write and is fragile to partitions. The usual design is one cluster per region with asynchronous mirroring (a consumer-producer pipeline that copies topics and translates offsets). Failover is then eventually consistent, with a recovery point equal to mirror lag, similar to async replication tradeoffs in Chapter 24. We leave it out of scope but mention it, which is exactly the right depth in an interview.

14. Security, monitoring, SLOs and cost

14.1 Security and abuse

  • TLS between clients and brokers and between brokers; SASL or mutual TLS for identity; ACLs per principal on topics, groups and transactional ids.
  • Quotas (section 11.4) double as abuse control. A maximum message size (1 MB) protects memory.
  • Encryption at rest through disk or volume encryption; client-side payload encryption for sensitive fields since the broker stores bytes opaquely.
  • TLS defeats zero copy, so size CPU for it or terminate TLS in hardware offload, otherwise plan for roughly 2x broker CPU on the consumer path.

14.3 Cost

The cost is dominated by disks and cross-zone network. With 30 brokers and 6 GB/s of internal traffic, cross-zone bytes (leader to followers in other zones, 2 GB/s at peak) are billed in most clouds, so cost-aware designs let consumers fetch from the nearest replica (follower fetching) rather than always the leader, saving about two thirds of consumer cross-zone traffic. Compression multiplies capacity by 2x to 5x. Tiered storage removes most SSD cost. Right-size retention per topic: a default of 7 days across 3,000 partitions, when most consumers are real-time, wastes petabytes.

15. Evolution, phasing and alternatives not chosen

15.1 What to build first

  1. Phase 1: a single-node broker with append-only segments, sparse index, producer batching, pull-based fetch and committed offsets stored in a topic. Validates the storage format and 1 GB/s on one big machine.
  2. Phase 2: partitions across brokers, metadata service, leader/follower replication with ISR, acks and min ISR, controller failover.
  3. Phase 3: consumer groups with coordinator and rebalancing, retention, compaction.
  4. Phase 4: idempotent producer, transactions, quotas and security.
  5. Phase 5: tiered storage, follower fetching, cross-region mirroring, self-service tooling.

15.2 At 10x scale (10M msg/s, 10 GB/s)

  • Brokers: about 300 by the same arithmetic, which stresses the controller (roughly 30,000 partitions to 100,000 replicas). The Raft-based metadata log handles this, but we would split into multiple clusters per business domain (cell architecture) to limit blast radius and rebalancing times.
  • Tiered storage becomes mandatory, since 9 PB raw is not affordable on local SSD.
  • Broker count per cluster is capped by partition-replica count per broker and controller memory; a "federated cluster" layer or a routing proxy gives clients one logical namespace.
  • Zero-copy tail reads give way to CPU limits once TLS is everywhere, so we scale CPU and use kernel TLS offload.

16. Interview Q&A

Why is Kafka-style storage fast on spinning or cheap disks when "disk is slow"?

The slowness of disks is the slowness of seeks, not of streaming. Because we only append to the end of a file and read forward from an offset, the drives do large sequential transfers at hundreds of MB/s. On top of that the operating system page cache holds the recently written tail, so tail readers never touch the disk, and producer batching plus compression turn many small messages into big writes. Finally the log format equals the wire format, so sendfile moves bytes from cache to NIC without copying them through the application. Our 1 GB/s needs about 30 machines mostly for capacity, not because any single piece is slow.

A producer gets a timeout on an acks=all send. Was the message written? What do you do?

You do not know: the leader may have appended and replicated the batch and the response was lost, or the request never arrived. The right behaviour is to retry, and to make the retry safe with the idempotent producer, which attaches a producer id and sequence number so the leader recognizes a duplicate batch and returns the original offset instead of appending again. Without idempotence a retry creates duplicates, so the consumer would need its own dedup key. Retries should use bounded exponential backoff with jitter and an overall delivery timeout so a long outage fails loudly instead of queuing forever.

What exactly guarantees that an acknowledged message is not lost when the leader dies?

Three rules together. First, with acks=all the leader acknowledges only after every in-sync replica has the batch, and the ISR must contain at least min.insync.replicas (2) members, so the data exists on at least two machines in different zones. Second, a new leader is elected only from the ISR, so it has all committed data. Third, the old leader's extra uncommitted tail is truncated on return using leader epochs. If you violate any rule (acks=1, unclean election, min ISR 1) you reopen a loss window, which is exactly the set of knobs we expose per topic.

How do you choose the number of partitions, and what goes wrong if you pick badly?

Take the larger of two numbers: target throughput divided by per-partition throughput (1 GB/s over 10 MB/s is 100), and the maximum consumer parallelism you will ever want (200 consumers at 5 MB/s each is 200), then add headroom, so 600 for our big topic. Too few partitions caps throughput and consumer scale; too many increases open files, memory for indexes, replication fetch overhead, failover time (each partition needs a leader election), and end-to-end latency since each partition batches separately. For keyed topics the count is also hard to change later, because hash mod N reshuffles keys, so you over-provision at the start.

Explain a consumer rebalance and how you would reduce its impact.

When a member joins, leaves, or stops heartbeating, the group coordinator bumps the generation and the members run JoinGroup and SyncGroup to receive a new partition assignment. With the eager protocol every member stops consuming while this happens, which on a large group can mean tens of seconds of zero throughput, and repeated rolling deploys cause repeated stalls. I would use cooperative rebalancing so only moved partitions pause, static membership with an instance id so a quick restart keeps its partitions, a sticky assignor, and a session timeout longer than typical restarts. I would also keep the poll loop short so slow processing is not mistaken for a dead consumer.

How would you provide exactly-once delivery?

I would not claim it end to end. Inside the log system you combine an idempotent producer (no duplicates from retries), transactions (output records and consumer offsets commit atomically, with transactional.id fencing to kill zombie instances), and read_committed consumers that skip aborted data. That gives exactly-once for consume-transform-produce between topics. For an external effect such as a database row or an email, the sink must either take part in the same transaction (store the offset in the same database transaction as the result) or be idempotent with a deduplication key. So the honest answer is at-least-once delivery plus idempotent processing, which produces an exactly-once effect.

When would you pick compaction rather than time-based retention?

Pick compaction when the topic represents the latest state per key and new consumers need to rebuild that state, like user profiles, configuration, or the consumer offsets topic itself; time-based retention would delete a key that simply has not changed in 7 days, which is wrong. Pick time retention for events, where each record is a fact at a moment and the window of replay is what matters. Compaction costs read and rewrite IO and memory for the key map, and it gives up history of intermediate values, and deletes need tombstones kept long enough for slow consumers to observe them.

Why use a log instead of SQS-style queue for this? When is the opposite right?

The log keeps one integer of state per group and partition rather than per message state, which is why it reaches millions of messages per second, supports replay by resetting an offset, and lets many groups read independently at no extra write cost. The price is head-of-line blocking per partition, parallelism capped by partitions, and no native delays or per-message retry. A per-message queue with a visibility timeout is the right choice for a task pool: independent jobs of uneven duration, elastic worker counts, retry counts and dead-lettering per message, and no need for order or replay. Many real platforms run both, with the log as the system of record for events.

A partition is offline and the business wants it back now. What are the options and risks?

First check if an ISR member is merely slow or restarting; waiting for it is the safe path and preserves all committed data. If the ISR replicas are truly gone, one can enable unclean leader election for that topic and promote an out-of-sync replica. That restores availability immediately but permanently loses the messages the replica did not have, possibly leaves consumers with committed offsets beyond the new end of log (they reset to earliest or latest), and can reorder history seen by downstream systems. This is a business decision per topic: for payments I would wait, for clickstream I would promote. After the incident I would review why the ISR shrank to one, for example min ISR 2 not being enforced.

How does the system stay balanced and avoid a noisy neighbor?

Balance comes from spreading partition leaders evenly across brokers, using rack-aware replica placement, periodically re-electing preferred leaders, and moving hot partitions with throttled reassignments. Isolation uses per-client quotas on produce and fetch bytes and on request-handler time, enforced by delaying responses rather than rejecting, plus caps on partitions and connections per tenant and ACL-scoped topic prefixes. For tenants whose peaks are huge or whose data is critical, a dedicated cluster is cleaner than tuning quotas. Monitoring per-tenant bytes and throttle time shows who is pushing the limits before others notice.

How does tiered storage change failure recovery and consumer behaviour?

With only about 6 hours of data local, a replacement broker has to copy around 1 TB rather than 30 TB, so recovery and expansion drop from days to under an hour, and the window in which the ISR is reduced is much shorter. Consumers that read recent data see no change; consumers replaying older data are served from the object store with higher first-byte latency but without evicting the hot data from the page cache, since remote reads bypass it. The risks are additional dependencies (the object store must be available for old reads), per-request costs, and complexity for compacted topics, which are often kept local.

18. Recap

  • The core is an append-only, segmented log per partition with a sparse index; sequential IO, the OS page cache, batching, compression and zero copy turn 1 GB/s into about 30 modest brokers.
  • Estimation: 1M msg/s × 1 KB = 1 GB/s; RF 3 gives 3 GB/s of disk writes, about 0.9 PB raw for 7 days; 600 partitions for the large topic.
  • Durability comes from leader plus ISR replication across zones: acks=all, min ISR 2, election only from the ISR, epoch-based truncation, and a Raft-backed controller to avoid split brain.
  • Consumers pull, keep one offset per partition per group, and share work via coordinator-managed groups; commit after processing gives at-least-once, idempotent producers and transactions give effectively-once inside the system.
  • Retention deletes whole segments; compaction keeps the latest value per key; ordering holds per partition only, so key routing and partition count must be planned.
  • Operations: backpressure through bounded buffers and throttling, tenant quotas, tiered storage for cheap elasticity, and alerts on under-replicated partitions and consumer lag.
  • Versus a per-message queue with visibility timeouts: the log trades flexible per-message handling for throughput, replay and cheap fan-out.
