Design a URL Shortener

A URL shortener turns a long web address into a short one and sends anyone who opens the short one to the long one. It looks trivial, which is exactly why interviewers like it: the interesting work is in generating unique short codes at scale, choosing the right redirect status code, serving a read-heavy hot path from cache, counting clicks without slowing redirects down, and surviving abuse. This page walks through a complete interview solution, with numbers.

1. Problem statement and clarifying questions

The prompt is usually one sentence: "Design a service like bit.ly or TinyURL." A strong candidate spends the first few minutes turning that sentence into a precise problem, following the approach in Chapter 1. The service has two core actions. A user submits a long URL such as https://example.com/products/2024/summer-sale?utm_source=mail&utm_campaign=jul and receives a short URL such as https://sho.rt/aZ3k9Qb. Later, anyone who requests the short URL is redirected to the original.

Here are the questions worth asking, and the answers this solution assumes.

2. Requirements and scope

2.1 Functional requirements

  • Create: given a long URL (and optionally a custom alias, an expiry time, and an owner), return a short URL.
  • Redirect: given a short code, respond with a redirect to the long URL, as fast as possible.
  • Custom alias: a registered user can request a specific code if it is free and passes validation.
  • Expiry and deletion: links can expire at a chosen time or be deleted by the owner; afterwards they return 404 or 410.
  • Analytics: owners can see total clicks and breakdowns by time, country, referrer, and device.
  • Abuse handling: block known malicious destinations, rate limit creation, and allow takedown.

2.2 Non-functional requirements

  • Latency: redirect p99 below 50 ms inside the data center; the user should not feel an extra hop.
  • Availability: the redirect path is the product. Aim for 99.99%, which allows about 52 minutes of downtime a year. See Chapter 41.
  • Durability: once a short link is issued, it must never be lost or reassigned to a different destination. A lost mapping breaks every page that embedded the link.
  • Scalability: handle 10x growth by adding machines, not by redesign.
  • Uniqueness: no two long URLs may ever receive the same code at the same time.
  • Eventual consistency for analytics: counts may lag by a minute or so.

2.3 Out of scope

We will not design the web front end, user accounts and billing, a link-in-bio product, A/B destination testing, QR code generation, or an enterprise custom-domain onboarding flow (beyond a brief mention). We also will not build a full anti-phishing classifier; we will integrate with one.

3. Estimation

Estimation, covered in Chapter 2, tells us which parts of the design are hard. We use round numbers and show the arithmetic.

3.1 Traffic

  • New links: 100 million per month. A month has about 2.6 million seconds (30 days x 86,400). So average writes = 100,000,000 / 2,600,000 ≈ 40 per second. With a peak factor of 5 (campaigns, bursts), peak writes ≈ 200 per second.
  • Redirects: read to write 100:1, so 10 billion redirects per month. Average = 10,000,000,000 / 2,600,000 ≈ 3,850 per second, call it 4,000. Peak with factor 5 ≈ 20,000 per second. Viral links make it spikier, which is why the cache and CDN matter.

Even 20,000 requests per second is modest for a single well-tuned cache cluster. The hard part is not raw throughput. It is keeping the hot path tiny and correct, and keeping tail latency low when one link suddenly takes 50,000 requests per second by itself.

3.2 Storage

  • Links over 5 years: 100 million x 12 x 5 = 6 billion rows.
  • Row size: code (7 bytes), long URL (average about 200 bytes, capped at 2,048), owner id (8), created and expiry timestamps (16), flags and metadata (about 50). Round to 500 bytes including index overhead.
  • Total: 6,000,000,000 x 500 bytes = 3 x 10^12 bytes = 3 TB for the mapping table. Per year, about 600 GB. This fits comfortably on a modest sharded cluster, and it would even fit on one large machine, but we want the throughput, replication, and operational headroom of sharding.

3.3 Code length

Base62 uses the characters a-z, A-Z, 0-9, so 62 symbols. With length 6 there are 62^6 ≈ 56.8 billion codes. With length 7 there are 62^7 ≈ 3.52 trillion. We need 6 billion codes in five years, so six characters would technically suffice (a fill ratio of about 10%), but random generation at 10% fill suffers noticeable collision retries, and counters give us no benefit from the extra headroom. Seven characters gives fill of 0.17%, room for custom aliases to share the space without trouble, and 10x growth without lengthening anything. We choose 7 characters.

3.4 Bandwidth

A redirect response is just a status line and headers, about 500 bytes. Peak 20,000 per second x 500 bytes = 10 MB/s = 80 Mbit/s outbound. Inbound requests are about 300 bytes. This is trivial network load.

3.5 Cache memory

Link popularity follows a heavy-tailed distribution: a small share of links gets most clicks. Suppose 20% of links account for 80% of the traffic. A daily working set of, say, 100 million distinct codes at about 200 bytes per cache entry (code, long URL, expiry, flags, Redis overhead) is 100,000,000 x 200 = 20 GB. That fits in the memory of a small Redis cluster (three shards of 16 GB with replicas), as discussed in Chapter 15. A hit ratio above 95% is realistic; with it, only 5% of 20,000 peak, about 1,000 reads per second, reach the database.

3.6 Click events

Every redirect emits one event of about 200 bytes (timestamp, code, country, user agent hash, referrer). At 4,000 events per second average: 800 KB/s ≈ 70 GB per day raw, about 25 TB per year uncompressed. Compressed columnar storage cuts this by 5 to 10x. Raw events are kept for 30 to 90 days; hourly and daily aggregates are kept long term and are tiny.

5.2 Why this storage

The mapping is a pure key-value lookup: given a code, return a row. There are no joins, no range scans on the hot path, and no multi-row transactions. That shape fits a distributed key-value or wide-column store such as DynamoDB or Cassandra (Chapter 20), and it also fits a sharded relational database such as MySQL or PostgreSQL (Chapter 18).

OptionStrengthsWeaknesses
Sharded MySQL/PostgresFamiliar; a unique primary key gives free collision detection; easy "my links" queries; strong consistency on the primary.You operate sharding yourself (Chapter 25); resharding is work.

Choice. A horizontally sharded key-value store with a conditional "insert if absent" write for the links table, a Redis cache in front of it, and a separate column-oriented analytics store (ClickHouse, Druid, or a lake with Parquet files) for click events. The reasons: the mapping is accessed only by key, uniqueness must be enforced atomically per key, and the scale of 3 TB with 20,000 reads per second is easy for such a store. Analytics has a completely different access pattern (scan and aggregate millions of rows), so mixing it into the OLTP store would hurt both. The same service can be built on sharded SQL with equal correctness; the rest of the design does not depend on this choice.

6. A first, simple design

Start with the simplest thing that works, then find where it breaks. One application server and one database:

Where this breaks as traffic grows:

  1. Every redirect hits the database. At 20,000 peak reads per second one database starts to struggle, and latency is dominated by disk or network. Cache fixes it.
  2. Code generation. A single auto-increment column is a single point of failure and a bottleneck once there are many writers or shards.
  3. Single point of failure. One app server and one database mean any failure is an outage.
  4. Analytics cannot be an UPDATE links SET clicks = clicks + 1 on the hot row. A viral link would serialize thousands of writers on one row.

7. The scaled architecture

The reasoning behind the split is that the read path and the write path have wildly different load (100:1) and different failure tolerance. The redirect service has no dependency on the ID allocator, the safety checker, or the analytics store being healthy. If Kafka is down, redirects still work; if the allocator is down, existing links still resolve. Splitting them lets us scale and deploy each separately (see Chapter 9 for balancing, and Chapter 40 for isolating dependencies).

7.1 Request flow: create a short link

  1. The create service authenticates the caller and rate limits it (Chapter 16).
  2. It validates the URL: well-formed, scheme http or https, length at most 2,048, not pointing at the shortener itself (to avoid redirect loops).
  3. It asks the safety checker whether the host is on a blocklist or flagged (section 12).
  4. If a custom alias was given, it skips the allocator and uses the alias as the code. Otherwise it takes the next ID from its local range and encodes it in base62.
  5. It performs a conditional insert, "insert if the code does not exist". If this fails (alias taken, or a hash collision), the API returns 409 for aliases or retries with a new code.
  6. It returns 201 with the short URL. It may prime the cache with the new entry so the first click is a hit.

7.2 Request flow: follow a short link

Detailed behavior of the redirect service:

  1. Parse the code from the path. Reject anything not matching [A-Za-z0-9_-]{1,16} immediately without touching any store, which protects the database from garbage traffic.
  2. Look in a tiny in-process cache first (a few thousand of the very hottest codes, for a few seconds). This absorbs a viral link before it even reaches Redis.
  3. Look in Redis. A hit returns the long URL, status flags and expiry.
  4. On a miss, read the link store. If the row exists and is active and unexpired, write it to Redis with a TTL. If it does not exist, write a short-lived negative cache entry (a "not found" marker for 30 to 60 seconds) so that scanners guessing random codes do not hammer the database; see Chapter 14.
  5. Check expiry and status: expired or deleted gives 410; disabled for abuse gives a warning page or 451/404.
  6. Publish the click event (best effort, with a local buffer), then return the redirect.

8. Deep dive 1: generating unique short codes

This is the part interviewers push on hardest. The requirement: produce codes that are short, unique across all machines and regions, cheap to generate, and (preferably) not trivially guessable. There are four standard approaches. All of them eventually produce a number or a hash and then encode it as a base62 string, so we start with the encoding.

8.1 Base62 encoding

Base62 is the same idea as writing a number in another base. Decimal uses 10 digits; base62 uses 62 symbols: 0-9 (values 0 to 9), a-z (10 to 35), A-Z (36 to 61). To encode a number, repeatedly divide by 62 and collect the remainders, then reverse them. Example: the number 125 is 2 x 62 + 1, so its digits are 2 and 1, written "21". The number 1,000,000,000 in base62 is "15ftgG" (6 characters). Any number below 62^7 ≈ 3.52 trillion fits in 7 characters, and we left-pad with the zero symbol to get fixed width if we want.

Why base62 and not base64? Base64 adds + and /, which are awkward in URLs (they need escaping). The URL-safe variant uses - and _ instead, which is acceptable but looks odd and is easier to break when someone copies a link in a document that wraps at hyphens. Base62 is plain letters and digits. Some systems also drop look-alike characters (0, O, 1, l, I) giving base58, which helps if codes are read aloud or typed from print, at the cost of slightly longer codes (58^7 ≈ 2.2 trillion, still plenty).

8.2 Option A: counter with ranges (our choice)

Keep a global counter. Each new link takes the next number, and the code is its base62 encoding. The danger is the counter itself: a single incrementing row is a serialization point and a single point of failure. The fix is range allocation (also called a ticket server with batching).

How it works step by step. The allocator stores one number, next_free. When a create server starts or runs out, it asks for a block: the allocator atomically reads next_free, adds 1,000, stores it, and returns the old value as the start of the block. The allocator needs durability and atomicity, so it lives in a small replicated store with consensus (etcd, ZooKeeper, or a SQL row with a transaction; see Chapter 29 and Chapter 30). The server then increments a local counter and encodes each number. Because blocks never overlap, uniqueness is guaranteed with no collision checks at all.

What happens on failure. If a server crashes with 600 unused numbers in its block, those numbers are simply lost. That is fine: 1,000 per crash out of 3.5 trillion is nothing, and gaps in a code space are invisible. If the allocator is briefly unavailable, servers keep serving from their current block (1,000 numbers at 200/s total fleet peak, so about 25 to 50 seconds per server of headroom even at peak; make the block 10,000 to ride out longer outages). If the allocator loses its state, a rollback of next_free would reissue numbers, so it must be replicated and the block size is added to the persisted value before the block is handed out.

The guessability problem. Sequential numbers give sequential codes: aZ3k9Qb is followed by aZ3k9Qc. Anyone can enumerate all links, which leaks private URLs and lets competitors estimate your volume. Two fixes. First, apply a reversible permutation to the number before encoding: for example multiply by a large constant coprime to 62^7 modulo 62^7, or run a small Feistel cipher keyed with a secret over the 42-bit space. Because the mapping is a bijection, uniqueness is preserved and the output looks random. Second, accept guessability and treat codes as unlisted-but-not-secret, and give private links a longer random token. We choose the permutation: it keeps collision-free uniqueness and removes enumeration.

8.3 Option B: hash the long URL and handle collisions

Compute a hash (MD5 or SHA-256) of the long URL, take the first 42 bits (the information in 7 base62 characters is 7 x log2(62) ≈ 41.7 bits), and encode it. Identical URLs give identical codes, which provides deduplication for free. But hashes collide: by the birthday bound, with n codes in a space of N, the collision probability reaches about 50% when n ≈ 1.2 x sqrt(N). With N = 3.5 x 10^12, sqrt(N) ≈ 1.9 million, so we expect collisions after only a couple of million links, long before our 6 billion. So every insert needs collision handling: on conflict, check whether the stored row has the same long URL (then it is a duplicate, reuse the code) or a different one (a true collision). For a true collision, append a salt or counter to the input and re-hash, then retry. At 6 billion rows in a 3.5 trillion space, the probability that any single new insert collides is about 6e9 / 3.5e12 ≈ 0.17%, so retries are rare but must be correct. The cost is a conditional write per attempt and a design that still must be careful with races between two creators inserting the same code simultaneously (the conditional insert handles it).

8.4 Option C: random codes

Draw 42 random bits from a cryptographic generator, encode, and insert with "if not exists". It is simple, unguessable, and needs no coordination. The collision chance per insert equals the fill ratio (0.17% at 6 billion links), and rises as the space fills, so you must retry on conflict. It is a fine choice for smaller services, and it is what many custom-alias and private-link flows use.

8.5 Option D: Snowflake-style 64-bit IDs

A Snowflake ID packs a timestamp (41 bits of milliseconds), a machine id (10 bits), and a per-millisecond sequence (12 bits) into 64 bits. Each machine generates IDs independently with no coordination beyond a unique machine id; see Chapter 32 for how that works and the clock-skew risks. The catch for a URL shortener is size: 64 bits in base62 needs 11 characters (62^10 is about 8.4 x 10^17, which is less than 2^64 ≈ 1.8 x 10^19, so 11 characters). A code of 11 characters is not very "short". You can shrink it by using fewer timestamp bits or a custom epoch, but then you are building a different scheme.

Decision: counter ranges with a keyed permutation. Uniqueness is structural, so the create path is one conditional write that can never legitimately fail on a generated code (the condition is a safety net, not the mechanism), and tail latency stays low. Hashing is kept as a secondary index only if the product wants "same URL, same user, same code" deduplication (section 9.4).

8.7 Custom aliases and the shared namespace

Custom aliases such as summer live in the same keyspace as generated codes, so a user could choose aZ3k9Qb and later collide with a generated code. Three rules prevent trouble. First, custom aliases must not look like generated codes: require length different from 7 or require at least one character outside the generated alphabet, such as a hyphen (my-sale). We pick: generated codes are exactly 7 base62 characters; aliases are 3 to 30 characters from [a-z0-9-] and must not be exactly 7 characters of pure base62. Second, reserve words (api, admin, login, static, and offensive terms) are rejected. Third, the insert is conditional, so two users racing for the same alias get exactly one winner and one 409 Conflict. Aliases are case-insensitive for the alias namespace (store lowercase) to avoid look-alike impersonation.

9. Deep dive 2: 301 versus 302, caching and analytics

9.1 What the two codes mean

Both 301 and 302 tell the browser "the resource is at the URL in the Location header". The difference is permanence. 301 Moved Permanently says the move is permanent, so browsers and intermediaries may cache it, often indefinitely, and search engines transfer ranking to the target. 302 Found (a temporary redirect) says do not remember this; ask again next time. There are also 307 and 308 (the same as 302 and 301 but forbidding a method change from POST to GET); for simple GET redirects 301 and 302 behave the same in practice.

9.2 Trade-offs

Concern301302
Server loadLower: repeat visitors by the same browser skip us.Higher: every click arrives.

Decision. Default to 302 with Cache-Control: private, max-age=0 (or a very short value) because analytics, expiry, and takedown are core requirements. Offer 301 as an opt-in for owners who explicitly accept the loss of analytics and revocability. This is a classic requirements-driven choice: if the product were a pure permanent-vanity-URL service with no analytics, 301 would be right and would cut traffic dramatically. When 301 is used, set a finite max-age (for example one day) instead of leaving the default heuristics, so mistakes can eventually heal.

9.3 Caching the hot read path, layer by layer

Redirects are the textbook cache-aside workload (Chapter 13): the data is small, read many times, written once, and the key is exact. We stack three layers.

  1. In-process cache (per redirect instance). An LRU of about 10,000 entries with a 5 to 30 second TTL. It absorbs a link going viral: if one code receives 50,000 requests per second across 20 instances, each instance sees 2,500 per second, and the local cache turns it into one Redis read per TTL per instance. It also protects against a "hot key" melting a single Redis shard.
  2. Redis cluster. Cache-aside with key l:{code} and value of the long URL plus flags and expiry. TTL 24 hours with random jitter of plus or minus 10%, so many entries created together do not expire together. Eviction policy allkeys-lru. Sizing is the 20 GB computed in section 3.5.
  3. CDN or edge (optional). For 301 links and 302 links marked "cacheable for 60 seconds", the edge can answer without reaching the origin, and an edge worker can even compute the redirect itself. This makes global redirect latency tens of milliseconds, at the price of slightly stale revocation. See Chapter 12. Analytics must then be collected from edge logs rather than origin events.

Failure patterns to defend against, from Chapter 14:

  • Cache stampede. A hot entry expires and 5,000 concurrent requests all miss together. Mitigation: request coalescing (only one in-flight database read per code per instance, others wait for it), jittered TTLs, and refresh-ahead for the very hottest keys.
  • Cache penetration. Scanners request random nonexistent codes, each a guaranteed miss. Mitigation: the strict pattern check, negative caching for 30 to 60 seconds, and optionally a Bloom filter of all existing codes in front of the database (Chapter 57) so "definitely does not exist" is answered from memory.
  • Staleness after change. On delete, disable, or edit, the create/admin service updates the database first, then deletes the Redis key and publishes an invalidation message to the instances' local caches. Worst case, a missed message is bounded by the local TTL (30 seconds), which fits the "one minute stale is acceptable" requirement. For abuse takedowns, a separate small "denylist" is checked on every redirect and pushed to instances immediately.
  • Cache outage. If Redis dies, the database would receive 100% of reads. The store is sized for the 5% miss rate, not 100%. Mitigation: local caches still absorb much of the load, connection limits and load shedding protect the database, and Redis is deployed with replicas and automatic failover.

9.4 Deduplication (same URL, same code?)

Should two requests for the same long URL return the same code? Per-user dedupe is a nice feature (clicking "shorten" twice does not create two links), but sharing a code between different users breaks per-user analytics and ownership, and a user deleting it would break the other's link. So we dedupe only within one owner and only when asked, by keeping a secondary index on (owner_id, url_hash). Anonymous creation always makes a new code. The index is a small table separate from the hot mapping table, so it adds no cost to redirects.

9.5 Expiry

Expiry has two parts: enforcement and cleanup. Enforcement is done at read time: the redirect service compares expires_at with the current time, and the Redis TTL is set to the lesser of 24 hours and the time remaining, so a cached entry can never outlive the link. Cleanup is lazy plus a sweeper: a background job scans for rows expired more than 30 days ago and moves them to cold storage or deletes them. Codes of deleted links are not reused for a long grace period (and with a 3.5 trillion space we never need to reuse them), because recycling a code would make an old printed link silently open someone else's page, which is both a security and a trust failure.

10. Deep dive 3: click analytics without slowing redirects

The naive approach, incrementing a counter in the link row on every click, creates a write on the read path (100 times more writes than the whole creation workload) and a hot row for viral links. The right approach is to treat a click as an event and move aggregation off the hot path, which is the stream-processing pattern from Chapter 37 and the log architecture from Chapter 34.

10.1 The event

Each event carries a unique event id (a random 128-bit value, used for deduplication), the code, a timestamp, a hashed IP address (never store raw IPs longer than needed; see Chapter 56), the country resolved at the edge or by a GeoIP lookup, the user agent, and the referrer host. Bots are filtered later by user-agent rules and by suspicious patterns such as many hits from one IP within seconds.

10.2 Delivery guarantees and counting

Kafka delivers at least once, and the producer may retry, so duplicates occur. The stream job drops events whose id it has already seen in a time window (a state store or a Bloom filter with periodic rotation), producing effectively once counting. For a click counter exact precision is not critical: if the redirect service cannot reach Kafka, it buffers a bounded number of events in memory and on local disk and drops beyond that, preferring a few lost clicks over a failed redirect. Users should be told counts are approximate and eventually consistent, typically within a minute or two.

10.3 Hot keys and partitioning

If the Kafka key is the code, one viral link puts all its events in one partition, which becomes a hot partition. Mitigations: key by code + random bucket (0 to 7) so one link spreads over 8 partitions, and sum the buckets downstream; or let the stream job pre-aggregate in the redirect service itself (each instance counts clicks per code in memory and flushes a delta every second). Local pre-aggregation reduces 20,000 events per second to perhaps 1,000 deltas per second and is the cheapest fix, at the cost of losing per-event detail unless we also log raw events. A common compromise: send raw events to the log (for flexible analysis) and also maintain real-time approximate counters in Redis with INCR for the "total clicks" number shown immediately in the UI.

10.4 Options compared

We choose the Kafka pipeline plus Redis totals. Batch processing of raw files (a nightly job) is the safety net that corrects the streaming numbers and powers re-computation if a bug is found; this is the lambda-style pairing discussed in Chapter 37.

11. Scaling, sharding and hot spots

11.1 Stateless tiers

The redirect and create services hold no durable state, so scaling them is a matter of adding instances behind the load balancer and letting an autoscaler react to CPU and request rate (Chapter 43). 20,000 requests per second at about 2,000 per instance gives 10 instances, plus a margin for failures and deploys: 20 to 30.

11.2 Sharding the link store

3 TB with 20,000 reads per second can technically live on a large replicated database, but we shard for operational reasons: faster backups, smaller failure domains, and room for 10x. The partitioning rules from Chapter 25 apply.

Shard by the code. The redirect lookup is always by code, so a single-shard read serves every redirect, with no scatter-gather. Hash partitioning of the code gives even data and load; range partitioning would funnel new sequential codes to one shard, which is why the permutation in section 8.2 helps even here. Use many more logical slots than machines (4,096 slots over 16 nodes), so moving a slot is a copy of a small piece; this is the virtual-node idea from consistent hashing (Chapter 57).

The "my links" query asks for all links by owner, which crosses shards because owners' links are scattered by code. Keep a separate index table partitioned by owner_id containing (owner_id, created_at, code), updated on create (asynchronously through a queue, or in the same write as a transaction-less dual write with a repair job). Reads of the dashboard tolerate a second of lag.

Each shard has one leader and two followers (Chapter 24). Redirect misses can read from followers, since a row never changes after creation except status; the rare delete reads the leader for correctness when it matters (the abuse path).

11.3 Hot spots

A viral link is a hot key rather than a hot shard problem: one code gets, say, 100,000 reads per second. The in-process cache plus Redis replicas for hot keys plus the CDN make it harmless. Writes are never hot, since every link is written once. Creation bursts, such as a marketing system creating a million links in a minute, are handled by the rate limiter (per-owner quotas, token bucket) and by the fact that allocation is local.

11.4 Rate limits

Creation is limited per API key and per IP (for example 100 per hour anonymous, 10,000 per day free tier). Redirects have a generous per-IP limit that mostly exists to protect against floods, enforced at the edge or gateway (Chapter 11). Algorithm details live in Chapter 16.

12. Multi-region

Users are global, and a redirect crossing an ocean adds 150 ms. Since reads dominate and a link never changes after creation, the data is ideal to replicate everywhere (Chapter 26).

Generated codes are conflict-free by construction. Give each region its own pool of blocks (for example, the allocator assigns ranges from distinct segments of the number space, or the region index is part of the number before the permutation). Two regions cannot produce the same number, so asynchronous replication cannot create conflicts for generated codes.

Custom aliases are the hard case. Two users in different regions might claim summer in the same second. Asynchronous replication would accept both locally and discover the conflict later. Options: route all alias claims to one owner region chosen by hashing the alias (the creator pays a cross-region round trip, which is acceptable for a rare action), or use a globally consistent store such as Spanner or a quorum-based database for aliases only. Consistency choices follow Chapter 28: for the alias namespace we choose consistency over latency; for redirects we choose availability and speed.

Read-after-create. A user creates a link in the US and a friend clicks it in Europe within 200 ms, before replication arrives. The friend's region gets a local miss. To avoid a false 404, the redirect service on a miss in the local replica asks the code's home region (the prefix identifies it) before giving up, and caches the result. This costs one cross-region call, only for fresh links. Alternatively, return the short URL only after replication to at least one other region (slower creation, stronger guarantee).

Region failure. If a region is lost, traffic shifts through DNS or anycast to another region, which already has every replicated row up to the replication lag. The few links created in the last seconds in the failed region might be missing until it recovers; for a service that treats the link as durable, wait for a second replica acknowledgment on creation (synchronous cross-region copy) at the cost of 50 to 150 ms added to creation latency. Since creation is not the latency-critical path, many designs choose that. Disaster recovery targets are discussed in Chapter 41.

13.1 Consistency decisions

  • The link row is write-once for the destination. A code maps to one long URL for life; edits (if a product allows them) create a new version and invalidate caches. This immutability is what makes aggressive caching and multi-region replication safe.
  • Uniqueness is enforced by a single atomic conditional insert at the owning shard, not by a read-then-write. A read-check-then-insert has a race: two creators both see "free" and both insert.
  • Status (active, disabled, deleted) is the only mutable field. Reads tolerate bounded staleness, 30 to 60 seconds, except for the abuse denylist, which is pushed.
  • Idempotent creation: the client's Idempotency-Key maps to the resulting code in a small table with a 24 hour TTL, so a retry after a timeout returns the same code instead of a second one. A subtle point is that the key and the link must be written atomically (the same shard), or the key table must be written first with a pending state; see Chapter 32.

14. Security, abuse, monitoring and cost

14.1 Abuse and malware

Shorteners hide the destination, which makes them favorites for phishing and malware distribution. A responsible design assumes abuse from day one.

  • At creation: check the destination host and full URL against threat-intelligence lists (Google Safe Browsing style services, internal blocklists), reject URLs pointing at private IP ranges, localhost, or the shortener's own domain (to prevent loops and SSRF-style probing from any later preview feature), require CAPTCHA or an account after a threshold, and rate limit per account and per IP.
  • After creation: a re-scan job checks destinations periodically, because a benign page can be swapped for a malicious one later. On a hit the link status becomes disabled and a denylist update is pushed to all instances, so the redirect shows an interstitial warning page or a 451/404 within seconds.
  • Interstitial and preview: for new or low-reputation links, show a "you are about to visit..." page, which also defeats some phishing. A + suffix (sho.rt/aZ3k9Qb+) can show the destination without following it.
  • Open redirect and header injection: validate the URL and encode it properly when placing it in the Location header, rejecting control characters and newlines to prevent response splitting. Only allow http and https schemes; never javascript: or data:.
  • Enumeration and privacy: permuted codes plus 404 rate limiting prevent harvesting; for sensitive links offer longer, random codes (12 characters) and optional password protection.
  • Abuse takedown tooling: admins can disable by code, by domain (all links to evil.example), or by owner, with audit logs. General guidance is in Chapter 55.

14.3 Cost

Compute is small: about 30 redirect instances and 6 create instances. The link store at 3 TB with 3 replicas is about 9 TB of SSD. Redis at 20 GB with replicas is a few hundred dollars a month. The dominant cost in practice is analytics: 70 GB per day raw events, mostly storage and the stream cluster. Control it by sampling or aggregating early, keeping raw data for 30 to 90 days in compressed Parquet, and keeping only aggregates beyond that. A CDN reduces origin compute but adds per-request fees; at a few thousand requests per second the origin is usually cheaper than the CDN for 302s, so use the CDN selectively.

15. Evolution and phasing

15.1 What to build first

  1. Phase 1 (week 1): one region, a SQL primary with replica, a single create/redirect service, random 7-character codes with a conditional insert, 302 redirects, Redis cache-aside. This handles hundreds of redirects per second and is correct.
  2. Phase 2: separate the create and redirect services, introduce the counter-range allocator with the permutation, add the Kafka click pipeline and a stats API, add blocklist checks and rate limits.
  3. Phase 3: shard the store, add the in-process cache and Bloom filter, add the CDN path for opt-in 301 links.
  4. Phase 4: multi-region replication, custom-domain support, abuse scanning loops, full SLO dashboards.

15.2 At 10x scale

At 1 billion new links a month and 200,000 peak redirects per second: the cache grows to about 200 GB across more Redis shards, the link store to 30 TB across 64 or more nodes (the slot mapping makes this a rebalance rather than a redesign), 7 characters still suffice for five years (60 billion links in a 3.5 trillion space, 1.7% fill), and Kafka goes from tens to hundreds of partitions. The hot-key defenses and local pre-aggregation become mandatory rather than nice to have. Edge compute (running the redirect in a CDN worker with a replicated key-value store) becomes attractive to cut global latency further.

15.3 Alternatives not chosen

  • Pure hashing of the long URL gives free dedupe but needs collision logic and weakens per-owner analytics.
  • Auto-increment from one database is simplest but a single point of failure, and sequential codes are enumerable.
  • A fully serverless design (edge function plus managed key-value store) minimizes operations; it is a good answer for a small team but gives less control over caching layers and analytics.
  • Bigger alphabet (Unicode) would shorten codes but breaks copy-paste and typing; not worth it.

16. Interview Q&A

Why not use an auto-increment column and encode it? What goes wrong at scale?

A single auto-increment works until you have multiple writers or shards: it becomes a single point of failure and a serialization bottleneck, and it exposes sequential codes that anyone can enumerate. The fix is to keep the counter idea but lease ranges of numbers to each create server, so the central allocator is touched once per thousand links, and to apply a keyed bijective permutation before base62 encoding so codes look random. Uniqueness stays guaranteed by construction because ranges never overlap.

How many characters do you need, and how did you decide?

We expect 6 billion links in five years. Base62 with 6 characters gives about 56.8 billion codes, with 7 gives about 3.52 trillion. Six would fit but would be 10% full, causing noticeable collision retries for random schemes and leaving little room for growth or custom aliases. Seven characters keeps the fill under 0.2% and survives a 10x growth, at the cost of just one extra character in the URL.

What happens when two users submit the same long URL at the same time?

By default each request gets its own code, because per-link ownership and analytics matter, so there is no conflict at all. If the product offers per-owner dedupe, we look up (owner_id, url_hash) and return the existing code, and we guard the race between two concurrent first-time requests with a unique constraint on that pair, so one insert wins and the other re-reads and returns the winner's code. Different owners never share a code.

Why 302 instead of 301? When would you use 301?

A 301 can be cached permanently by browsers and intermediaries, so repeat clicks never reach us. That removes analytics for those clicks and prevents us from expiring, editing, or disabling a link for browsers that have already cached it. Because analytics, expiry and abuse takedown are requirements, 302 is the default. For a permanent vanity link with no analytics need, 301 reduces load and passes search ranking to the destination, so we allow it as an explicit opt-in with a finite max-age.

A single link goes viral with 100,000 requests per second. What breaks and how do you protect it?

The risk is one hot key: all those requests hit the same Redis shard and, on expiry, a stampede hits the database. We defend in layers. Each redirect instance has a small in-process cache with a short TTL, which turns the load into a handful of Redis reads. Redis keys have jittered TTLs and request coalescing so only one fetch per instance refills an expired entry. For known hot links we can replicate the key across several cache nodes, and a CDN can serve opted-in links entirely at the edge.

How do you count clicks without slowing down redirects or losing accuracy?

The redirect only appends an event to Kafka, asynchronously, and returns immediately. A stream job deduplicates events by event id, enriches them with country and device, and writes windowed aggregates to an OLAP store, while raw events go to object storage so a nightly batch can recompute and correct the numbers. If Kafka is unreachable, the service buffers a bounded number of events and then drops them, because losing some clicks is better than failing redirects. The dashboard shows eventually consistent counts, usually within a minute or two.

How do you handle custom aliases that might collide with generated codes or each other?

We separate the namespaces by format: generated codes are exactly seven base62 characters, while aliases are 3 to 30 characters from lowercase letters, digits and hyphens and may not be exactly seven pure-base62 characters. Reserved words are rejected. The insert is a conditional write, so when two people race for the same alias exactly one succeeds and the other gets 409 Conflict. In multi-region, alias claims are routed to a single owning region or a strongly consistent store, because asynchronous replication could otherwise accept both.

How do you shard the link store, and what about the "list my links" query?

We partition by a hash of the code into 4,096 logical slots mapped to physical nodes, because redirects look up by code and that gives single-shard reads and even distribution. Slots move between nodes when we add capacity, without rehashing everything. Listing links by owner would require scattering across all shards, so we maintain a second table partitioned by owner id holding the owner's codes, updated asynchronously on creation, with a repair job to fix any missed updates.

How do you stop the service being used for phishing and malware?

At creation we check the destination against threat-intelligence and blocklists, reject private addresses and loops, and rate limit by account and IP, with CAPTCHAs for anonymous users. After creation we rescan destinations periodically since a page can turn malicious later, and a disable action pushes to a denylist that every redirect instance checks, so takedown takes seconds. Using 302 rather than 301 matters here, since browsers do not cache the redirect and the block takes effect on the next click. We also offer a preview page for low-reputation links.

What does the system do if a region goes down, and how do you avoid false 404s for new links?

Traffic is steered to another region by DNS or anycast, and that region already holds every link replicated up to the replication lag, so redirects continue. A link created moments before the failure may not have replicated; to bound this we can require a second-region acknowledgment before returning success on creation, trading some creation latency. For links that are created in one region and clicked in another before replication arrives, a local miss falls back once to the code's home region, which is identifiable from the code, and the result is cached.

Hash the URL versus a counter: how would you defend each choice?

Hashing gives deduplication and needs no coordinator, but it has probabilistic collisions that appear after only millions of links (birthday bound) and needs retry logic and conditional writes on every insert. A counter with leased ranges makes uniqueness structural, needs one tiny coordinator touched rarely, and produces compact codes, but needs a permutation to stop enumeration and a secondary index if you want dedupe. I choose the counter because collisions are the kind of rare bug that is expensive to debug, and uniqueness by construction removes the whole class.

17. Recap

  • Scale: 100 million links a month is only 40 creations per second, but 100:1 reads give 4,000 redirects per second on average and 20,000 at peak; 6 billion rows is about 3 TB; the cache working set is about 20 GB.
  • Codes: 7 base62 characters (3.5 trillion codes), produced from leased counter ranges and a keyed permutation. Uniqueness is guaranteed by construction, and a conditional insert is the safety net. Hashing and random codes need collision handling; Snowflake IDs give 11-character codes.
  • Redirects: 302 by default so every click is counted and links can be revoked; 301 is opt-in for permanent links without analytics.
  • Hot path: in-process cache, then Redis cache-aside with jittered TTLs, request coalescing, negative caching and a Bloom filter; the link row is immutable so caching and replication are safe.
  • Analytics: events to Kafka asynchronously, stream aggregation, raw files for recomputation, and eventually consistent counts.
  • Data: sharded key-value store partitioned by a hash of the code with many logical slots; a separate owner index for "my links".
  • Multi-region: replicate everywhere, per-region ID ranges avoid conflicts, aliases need a single owner, fresh-link misses fall back to the home region.
  • Abuse: scan at creation and afterwards, rate limit, denylist pushed instantly, preview pages.
