Case study 9 · Worked solutions

Design Dropbox / Google Drive

A file sync service keeps a folder identical on a laptop, a phone and the cloud, even when devices go offline, edit the same file, or upload a 50 GB video over a flaky hotel network. This worked solution designs it for 500 million users: how files are cut into chunks, stored once, uploaded in parallel, tracked by a sharded metadata service, and propagated to other devices through a change journal, with conflict handling that never loses data.

How to approach this problem (read this first)

The prompt says "design Dropbox", and the danger is to start drawing boxes for upload and download. Three things are really being tested. First, can you move very few bytes: a one-byte edit to a big file must not re-upload the file, which leads to chunking, hashing and dedup. Second, can you keep a small, strongly consistent metadata store and use it to tell many devices what changed, without polling, which leads to namespaces, a change journal and cursors. Third, can you handle two devices editing the same file offline without ever losing data. Everything else (sharing, versions, security) hangs off those three ideas.

The thinking order, step by step

  1. Pin the scope. Ask how many users and devices, the largest file, whether the file tree must be strongly consistent, and whether real-time co-editing is in scope. You say: "Is this a synced folder with sharing and version history, and is Google-Docs style co-editing out of scope?" Why now: co-editing is a different system, so this answer decides the conflict policy before you touch the design.
  2. Estimate storage first, then metadata QPS. Compute 500 M users times 2 GB for about 1 EB logical, then dedup to about 670 PB. Then compute commits per second (2,300 average, 7,000 peak) and metadata operations (175,000 per second at peak). You say: "Bytes are huge but simple, metadata is small but hot and must be correct, so I will split the two." Why now: that split is the whole architecture, and the numbers prove it.
  3. Draft the API in two halves. Write the block calls (check, put, get by hash) and the metadata commit call with a parent revision. You say: "Bytes go straight to the block API, and a tiny commit call makes a new version visible." Why now: the commit is the one atomic step, so naming it early gives you the consistency story.
  4. Name the entity that drives the model. Say that a namespace (a file tree root, private or shared) is the key for files, versions and the journal. You say: "I key everything by namespace id so a commit is one transaction on one shard." Why now: sharing and sharding both depend on this choice, so make it before drawing storage.
  5. Show the naive design and its failures. Draw one server with local disk and whole-file upload, then list: full re-upload, no resume, lost disk, polling, no dedup. You say: "Each of these problems becomes one component in the real design." Why now: it gives you a visible path to evolve, and the interviewer sees you reason from failure.
  6. Deep dive chunking and upload order. Explain content-defined chunks, the check-then-put-then-commit sequence, and why bytes come before metadata. You say: "A version only becomes visible after every chunk is durable, so nobody sees a file with missing pieces." Why now: this is the part the interviewer is most likely to probe.
  7. Deep dive propagation to other devices. Describe the gap-free journal, a cursor per device, and a long-poll that only says which namespace changed. You say: "The notification is a hint, the journal is the truth, so a lost hint only delays sync." Why now: now that bytes are safe, show how the rest of the world learns about them.
  8. Handle conflicts and failures. Use parent revision to detect a stale commit, keep both files as a conflicted copy, and walk through client crash, GC and failover. You say: "I never use timestamps to pick a winner, because clocks lie and that destroys data." Why now: failures last because they only make sense once the happy path is clear.
  9. Close with scale and evolution. Name hot spots (huge shared namespace, many tiny files), then what you build first. You say: "MVP is fixed chunks and one SQL cluster, and the schema already shards by namespace." Why now: it shows judgment about phasing, not just a final picture.

The decision points

  • Fixed or content-defined chunks. Ask yourself: do edits shift bytes? Documents and source files get inserts in the middle, so content-defined chunking limits a change to one or two chunks. Fixed chunks are fine for VM images and databases that edit in place.
  • SQL or key-value for metadata. Ask yourself: do I need a multi-row atomic commit? A commit checks the revision, inserts a version, moves a pointer and appends to the journal together, so sharded SQL by namespace fits better than a plain key-value store.
  • Polling or push for sync. Ask yourself: how many devices are idle most of the time? With 100 million devices, polling is millions of useless requests per second, so use long-poll hints plus cursors.
  • Last write wins or keep both. Ask yourself: is losing data ever acceptable? Durability is the top requirement, so reject stale commits and keep a conflicted copy.
  • Shard by user, file or namespace. Ask yourself: what must be on one shard for a transaction? A folder and its journal, which is the namespace. User sharding breaks shared folders, file sharding scatters a folder.

Common mistakes on this problem

  • Proxying all file bytes through the metadata servers. Fix: send bytes to a block tier or pre-signed object-store URLs and keep metadata calls tiny.
  • Using whole-file hashes only. Fix: hash chunks, so a small edit uploads one chunk and identical content dedups.
  • Resolving conflicts with timestamps. Fix: use a parent revision check and keep a conflicted copy.
  • Polling the whole tree. Fix: use a journal with a cursor per device and a long-poll hint.
  • Forgetting that dedup leaks information. Fix: ask for proof of possession and authorize every block read through a file that references it.
  • Deleting a chunk the moment its count hits zero. Fix: queue it for garbage collection after a grace period and confirm with a mark phase.

1. Problem statement and clarifying questions

The prompt is "Design Dropbox." The first job in an interview (see Chapter 1) is to turn that sentence into a scoped problem. The product is a synced folder: the user installs a client, drops files into a folder, and the same files appear on every other device they own, and on the web. Users can also share files and folders with other people, view older versions, and restore deleted files.

Questions to ask, and the answers we will assume for the rest of the page:

QuestionAssumed answer
How many users?500 million registered, 100 million daily active (DAU).
How much data per user?Heavily skewed. Average about 2 GB stored across all users (most accounts are small or dormant); a few power users hold terabytes.
File sizes?Mostly small (documents, photos, source code), but the service must accept files up to 50 GB. Average file about 10 MB.
How many devices per user?About 3 (laptop, phone, web). Sync must work across all of them.
What consistency do users expect?The metadata (what files exist, in which version) must be strongly consistent per account. Propagation to other devices may take seconds.
How fast should a change appear on another device?Small files: p95 under 5 seconds when the other device is online. Large files: limited by bandwidth.
Do we need real-time co-editing of documents?No. That is a separate system (collaborative editor, see also Chapter 16 for protecting such APIs). Here two edits to one file produce a conflict, not a merge.
Durability?Extremely high. Losing a user's file is the worst possible failure. Target eleven nines of durability for stored data.
Offline use?Yes. Clients edit offline and sync on reconnect.
Encryption, compliance?Encryption in transit and at rest is required; end-to-end encryption is out of scope for the base design (discussed in the security section).

2. Requirements

2.1 Functional

  • Upload, download, rename, move and delete files and folders from any device.
  • Automatic sync: a change on one device appears on the user's other devices.
  • Resume interrupted uploads and downloads; upload very large files reliably.
  • Share a file or folder with other users with view or edit permission; shared folders appear in the recipient's tree.
  • Version history (for example 30 days or 100 versions) and restore.
  • Offline edits that reconcile on reconnect, with conflicts preserved rather than overwritten.

2.2 Non-functional

  • Durability over everything: never lose acknowledged data.
  • Efficiency: do not re-upload bytes the server already has (dedup) or bytes that did not change (delta sync). Bandwidth and storage are the dominant costs.
  • Consistency of the file tree: a client must never see a file that points to chunks that do not exist, and two clients must converge on the same tree.
  • Availability: reads and syncs keep working during a single data center failure.
  • Scalability: hundreds of billions of files, exabytes of data, millions of sync connections.

2.3 Out of scope

Real-time collaborative editing, full-text search of file contents, photo/video transcoding (a streaming concern, see Chapter 10), billing, and end-to-end (zero-knowledge) encryption. We mention hooks for them in the evolution section.

3. Estimation

Estimation technique is covered in Chapter 2. Here are the numbers that drive design decisions, with the arithmetic shown.

3.1 Storage

  • Logical data: 500 M users × 2 GB = 1,000 PB = 1 EB of user-visible data.
  • Dedup (identical chunks across users and versions stored once) typically saves a large fraction; assume a ratio of 1.5. Unique data: 1 EB / 1.5 = about 670 PB.
  • Erasure coding in the block store (Chapter 21), for example 10 data + 4 parity shards, costs 1.4x: 670 PB × 1.4 = about 940 PB raw. Versions add more (we keep changed chunks only, so assume +30%), leading to roughly 1.2 EB raw. This is the budget line that dominates cost.
  • Files: 500 M × 200 files = 100 billion files. At average 10 MB this matches the 1 EB figure (100 B × 10 MB = 1 EB).
  • Chunks: with 4 MB chunks, large files split into many chunks and small files into one, so assume an average of 3 MB per chunk: 670 PB / 3 MB = about 220 billion unique chunks. A chunk index entry is about 50 bytes (hash, location, refcount): 220 B × 50 B = 11 TB. That fits comfortably in a sharded key-value store, but not in one machine's memory.
  • Metadata: a file-version row is about 300 bytes plus a chunk list. 100 B files × about 3 retained versions × 300 B = about 90 TB, plus chunk lists (a pointer per chunk, about 40 bytes). Call it 150 TB of sharded relational metadata. Small compared with the blocks (about 0.015% of the volume), but it is the hot, latency-critical part.

3.2 Traffic

  • File changes (new files plus edits): 100 M DAU × 2 per day = 200 M per day. Average = 200 M / 86,400 = about 2,300 commits per second; peak (3x, morning in each time zone) about 7,000 per second.
  • Uploaded bytes before optimization: 200 M × 10 MB = 2 PB per day. Delta sync and dedup remove about half: 1 PB per day over the wire = 1 PB / 86,400 s = 11.6 GB/s = about 93 Gbit/s average, about 280 Gbit/s at peak.
  • Chunk writes: 1 PB / 3 MB = 330 M per day = about 3,900 per second average, about 12,000 at peak.
  • Downloads: each change is pulled by about 2 other devices, so egress is about 2 PB per day = 185 Gbit/s average, about 550 Gbit/s at peak. Read:write byte ratio about 2:1; but read:write on metadata is much higher (see below).
  • Metadata operations (list folder, get cursor, stat, commit): 100 M DAU × 50 per day = 5 B per day = about 58,000 per second average, about 175,000 per second at peak. This is a classic read-heavy relational workload (read:write about 10:1).

3.3 Connections and notifications

If 50 M users are online at peak with 2 devices each, that is 100 M long-lived notification connections. At about 50,000 connections per server (memory per idle connection is a few KB) we need about 2,000 notification servers. The notification payload is tiny (a few bytes saying "namespace X changed"), so this tier is bound by connection count, not bandwidth. See Chapter 6.

Key takeaway The block store is huge in bytes but simple (immutable blobs). The metadata store is small in bytes but has the hard correctness and QPS requirements. The design splits the two on purpose and spends most of its cleverness on moving as few bytes as possible.

4. API design

The client talks to two kinds of endpoints: metadata endpoints (small JSON, strongly consistent) and block endpoints (large bytes, directly to storage). Separating them lets the bytes flow past the metadata servers entirely. API style is discussed in Chapter 5.

POST /v1/blocks/check          { hashes: [h1, h2, ...] }
  -> { missing: [h2, ...] }                 // which chunks the server does not have yet

PUT  /v1/blocks/{hash}                       // body = chunk bytes (up to ~4 MB)
  -> 200 (idempotent: same hash, same bytes)

POST /v1/files/commit
  { namespace_id, path, parent_rev, size, mtime,
    chunks: [{hash, size}, ...], client_id, idempotency_key }
  -> { rev, cursor }  |  409 { conflict_with_rev }

POST /v1/files/upload_session/start    -> { session_id }   // large files
PUT  /v1/files/upload_session/{id}?offset=N                // append part, resumable
POST /v1/files/upload_session/{id}/finish  { commit: {...} }

GET  /v1/files/list_folder     { namespace_id, path, cursor? }
  -> { entries: [...], cursor, has_more }
GET  /v1/files/list_changes    { namespace_id, cursor, longpoll_timeout? }
  -> { changes: [{op, path, rev, chunks...}], cursor, has_more }
GET  /v1/notify/subscribe      { cursors: {ns1: c1, ns2: c2} }   // long-poll
  -> { changed: [ns1] }

POST /v1/shares                { namespace_id|path, grantee, role }
GET  /v1/files/versions        { path }          POST /v1/files/restore { path, rev }
GET  /v1/blocks/{hash}                           // download a chunk (pre-signed or via CDN)

Three details matter. First, chunks are addressed by their hash, not by a server-assigned id, so uploading the same chunk twice is naturally idempotent (Chapter 32). Second, commit carries parent_rev: the revision the client's edit was based on. That is how the server detects conflicts (section 9). Third, every change feed is cursor-based: the client stores an opaque cursor and asks "what changed since this cursor", never "give me everything".

5. Data model and storage choice

Three kinds of data with very different needs, so three stores:

DataShape and sizeStore and reason
Chunk bytesImmutable blobs, 4 MB, about 1 EBObject storage with erasure coding (Chapter 21). Cheap per GB, eleven-nines durability, no random updates needed because chunks are never modified.
Chunk index (hash to location, refcount)220 B small records, about 11 TB, point lookups at 10k+ per secondSharded key-value store keyed by hash (Chapter 20). Hash keys spread evenly, so there are no hot shards.
File tree, versions, sharing, journalRelational, about 150 TB, 175k QPS peakSharded SQL (MySQL or Postgres) because we need transactions across several rows (a commit, a move) with strong consistency, plus secondary indexes. Sharded by namespace_id (Chapter 25).

5.1 The key concept: namespaces

A namespace is a file tree root: every user has a private root namespace, and every shared folder is its own namespace that is mounted into the tree of each member. All metadata is keyed by namespace_id. This single decision is what makes sharing and sharding work together: a shared folder is one unit with its own journal and its own permissions, no matter how many people mount it, and a transaction never needs to span two shards for ordinary edits.

namespace(ns_id, owner, kind[root|shared], created)
mount(user_id, ns_id, mount_path, role)          -- who sees which namespace, and where
file(ns_id, file_id, parent_id, name, is_dir,
     latest_rev, deleted, UNIQUE(ns_id, parent_id, name))
file_version(ns_id, file_id, rev, size, mtime, chunk_list[], client_id, created)
journal(ns_id, seq BIGINT, file_id, op, rev, ts)    -- append-only change log
block_index(hash, size, store_loc, refcount)        -- separate key-value store

The journal is the heart of sync. Every successful commit, move or delete appends one row with the next sequence number in that namespace (1, 2, 3...). A cursor is just "namespace N, sequence S". Because sequence numbers are allocated inside the same transaction as the change, the journal is gap-free and ordered.

File identity uses a stable file_id, not the path, so a rename is a one-row update of parent_id/name and does not touch chunks. Moving a folder with a million files is also one row: children point to the folder's id, not to a path string.

7. Deep dive 1: chunking, hashing and dedup

7.1 Why chunk at all

Treating a file as one blob has three costs. A 1-byte edit to a 2 GB file re-uploads 2 GB. A connection drop at 99% restarts from zero. And two users uploading the same 2 GB installer store it twice. Splitting each file into chunks, naming each chunk by its content hash (SHA-256), solves all three: unchanged chunks are skipped, finished chunks survive a disconnect, and identical chunks collapse to one stored copy. A file is then just an ordered chunk list, which is what the metadata service stores. Content hashing and probabilistic structures are in Chapter 57, and the Merkle-tree idea (hash of hashes) in Chapter 33.

7.2 Fixed-size versus content-defined chunking

Fixed-size chunking cuts every 4 MB at byte offsets 0, 4 MB, 8 MB, and so on. It is trivial and fast. Its weakness is the boundary shift problem: insert one byte near the start of a file and every later byte moves by one position, so every later chunk has different content and a different hash. A small edit looks like a total rewrite.

Content-defined chunking (CDC) chooses cut points from the data itself. A rolling hash (Rabin fingerprint or a faster variant such as Gear/FastCDC) slides over a small window of bytes, and a boundary is declared wherever the hash satisfies a condition, for example its low 22 bits are zero, which happens on average once per 4 MB. Minimum and maximum sizes (say 1 MB and 16 MB) prevent pathological tiny or huge chunks. Because boundaries depend on local content, an insert only disturbs the chunk it lands in; the boundaries after it re-synchronize and all later chunks keep their old hashes.

Choice: content-defined chunking with a 4 MB average (1 MB minimum, 16 MB maximum) for files over a size threshold, and a single chunk for files under 4 MB (no need to chunk a 30 KB document). The client does the chunking, which keeps hashing CPU off our servers and means unchanged bytes never even cross the network.

7.3 Chunk size tradeoff

Smaller chunks give finer delta sync and better dedup, but they multiply metadata. At 64 KB average, the 670 PB of unique data would have 10 trillion chunks, and the index would be 500 TB, while each request moves little data so per-request overhead dominates. At 64 MB, the metadata is tiny but a one-byte edit uploads 64 MB. About 4 MB balances the two; mobile clients on poor links may use smaller chunks to make resume cheaper.

7.4 Dedup

Dedup works because the chunk hash is the chunk's identity. The upload protocol first sends the list of hashes to /blocks/check; the server answers with the subset it lacks, and the client uploads only those. This even lets a client "upload" a file instantly if all chunks already exist, because the same file was uploaded by someone else (the famous instant-upload effect).

Watch out: cross-user dedup leaks information If the server says "I already have this chunk", an attacker who knows a file's hash can learn that someone stored it (the confirmation-of-file attack), and could even claim ownership of a chunk without having the bytes. Defenses: require the client to prove it has the bytes (the server challenges with a random offset range to hash with a nonce), scope dedup per account or per team for sensitive tiers, and never reveal "exists" to an unauthorized caller unless proof is supplied. Many real services accept cross-user dedup with proof-of-possession; strict zero-knowledge designs give it up.

Each stored chunk has a reference count: the number of file versions that include it. Deleting a version decrements counts. A chunk with zero references is not deleted immediately but queued for garbage collection after a grace period (say 7 days), because a concurrent upload may be about to reference it. A mark-and-sweep scan, done offline, repairs any refcount drift. Getting this wrong deletes live data, so GC is slow and cautious by design.

8. Deep dive 2: resumable, parallel upload and the sync protocol

8.1 The upload flow

The ordering of steps is what guarantees consistency: bytes first, then metadata. A file version becomes visible only when its commit succeeds, and the commit succeeds only if every chunk it names is already durably stored. So no client can ever see a file whose chunks are missing.

Walkthrough. Each vertical line is a lifeline for one actor: client, block service, object store and metadata service. Read the numbered messages top to bottom. 1. The client chunks and hashes locally. 2. It sends the list of hashes to the block service. 3. The service replies with only the missing ones. 4. The client puts those chunks, several in parallel. 5 and 6. The block service writes to the object store and gets a durable acknowledgement. 7. Chunk acks return to the client. 8. Only now does the client send the commit with the chunk list, parent revision and idempotency key. 9. The metadata service checks that every chunk exists and the parent revision matches, then does one transaction: insert the version, bump the revision, append a journal row. 10. The client receives the new revision and cursor. 11. A notification is published. The design avoids the alternative of committing first, which could show a file with missing chunks. Point at the gap between steps 7 and 8: a crash there leaves only orphan chunks.

8.2 Parallel and resumable

Chunks are independent, so the client uploads 4 to 8 in parallel over several connections, saturating the link far better than one TCP stream (a single stream's throughput is bounded by window size and round-trip time; see Chapter 3). Each chunk is a separate small request, so a dropped connection costs at most one chunk. After reconnecting, the client simply repeats check: the server reports what it still lacks, and the upload continues. No server-side session state is required for normal files, because the hash makes everything idempotent.

For very large files (tens of GB), the client keeps an upload session on the server recording the committed chunk offsets so a resumed client can ask "where was I", and so a half-finished 50 GB upload survives a laptop reboot. This is the same pattern as object-store multipart upload (Chapter 21): parts are uploaded independently, then finalized by a single commit. Hashing a 50 GB file takes minutes of CPU, so the client hashes and uploads as a pipeline instead of hashing the whole file first.

Bytes need not pass through our app servers. The block service can return a short-lived pre-signed URL per chunk so the client writes straight to the object store, or terminate the request at an edge proxy close to the user to cut round-trip time. Downloads go through a CDN where files are shared widely (Chapter 12), though most private file data has low reuse and is served directly.

8.3 Delta sync

Chunk-level dedup already is a coarse delta: only changed chunks move. A finer delta applies when a large file is edited in place (a 2 GB database dump with 30 KB changed). Within a 4 MB changed chunk, the client can use an rsync-style rolling checksum against the server's old version of that chunk to send just the changed byte ranges (a binary diff), and the server reconstructs the new chunk. This costs server CPU and requires the old chunk, so it is applied only to large chunks of files that change often, as an optimization on top of CDC. Compression (for compressible types) is applied before encryption and upload.

8.4 The sync protocol: journal, cursors and notifications

The other half is telling the other devices. The wrong design is polling "list everything" (millions of devices times a full tree scan). The right design is a change journal with cursors:

  1. Every namespace has an append-only journal with a monotonically increasing sequence number, written in the same transaction as the metadata change.
  2. A device remembers a cursor per namespace: the last sequence it has applied.
  3. When a device comes online or is told something changed, it calls list_changes(ns, cursor) and gets all journal entries after that sequence, in order, plus a new cursor. It applies them, downloads the missing chunks, and saves the cursor.
  4. To avoid polling, the device holds a long-poll request open to the notification service: "tell me if any of these (ns, cursor) pairs is stale". The server holds the request up to about 60 seconds and replies the moment a commit happens. The reply says only which namespace changed, not the details; the device then calls list_changes. (WebSocket or server-sent events work equally well; long-poll is simplest to run through corporate proxies. See Chapter 6.)
Walkthrough. Four lifelines: device A, the metadata shard, the notify service and device B. Step 0 is the quiet state: B already has a long-poll open with cursor 41. 1. A commits and the shard assigns journal sequence 42 inside the same transaction. 2. The shard publishes a small message saying the namespace changed. 3. The shard acknowledges A, so A never waits for B. 4. The notify service answers B's open request with only the namespace name. 5. B calls list_changes with its old cursor 41. 6. The shard returns the entries after 41 and a new cursor 42. 7. B downloads missing chunks and applies the change. 8. B opens a new long-poll with cursor 42. The key design choice is that the notification carries no data, so losing it only delays sync because the cursor still finds the change. On the whiteboard, draw the dashed long-poll lines in a different style. Without the journal, a lost message means a lost update.

This design has useful properties. The journal is the single source of truth, so notifications can be best-effort. A device offline for a month sends its old cursor and catches up with one call (or, if the journal was compacted past that cursor, gets a "reset" response and does a full tree listing, then a new cursor). Delivery is at-least-once and applying a journal entry is idempotent (apply rev 7 of file X), which is the usual recipe from Chapter 32. Clients also reconcile locally: a scan compares the local filesystem's files with the client's database (path, size, mtime, chunk hashes) and detects changes the filesystem watcher missed.

The notification tier is stateless apart from the connection map. A pub-sub layer (Redis pub/sub or a Kafka topic, Chapter 34) lets any metadata server publish "ns 8123 changed", and the notification servers holding a subscription for that namespace wake their waiting connections. Namespaces with many members (a shared folder of 10,000 employees) fan out to many connections, so large fan-out goes through batching and jittered re-fetch to avoid a thundering herd of list_changes calls.

9. Deep dive 3: the metadata service, the file tree and conflicts

9.1 Sharded SQL and the commit transaction

Metadata uses relational shards because commits need a multi-row transaction: check that parent_rev equals the file's latest revision, insert the new version, update latest_rev, allocate the next journal sequence, and insert the journal row. All rows have the same ns_id, so all of this happens inside one shard in one local ACID transaction, with no distributed transaction (Chapter 31 explains what that avoids).

Draw the two levels of mapping on the whiteboard. If you remove the shard map and hash directly to clusters, every rebalance would rehash and move data.

Sharding by ns_id (not by user and not by file) is the central trade. Pros: a namespace's tree, versions and journal are co-located, so listing a folder, committing and reading changes are single-shard operations. Cons: one enormous namespace (a company's shared drive with 100 million files) becomes a hot shard that cannot be split by hash. Mitigations: give very large namespaces their own dedicated shard, tune per-namespace rate limits, and split such a namespace internally by top-level folder only as a last resort (and accept that cross-subtree moves then become cross-shard operations). Details on shard keys and rebalancing are in Chapter 25.

Our scale: 150 TB of metadata over 256 physical clusters, each holding about 600 GB, is comfortable, and 175,000 peak QPS is about 700 per cluster, which is easy. Each cluster has one primary and two replicas (Chapter 24). Reads that need the latest state (the commit check, list_changes right after a notification) go to the primary; pure browsing can read replicas, accepting a tiny staleness, and uses read-your-writes by pinning a session to the primary for a short time after its own write (Chapter 28).

Cross-namespace operations are the awkward case. Moving a file from a private folder into a shared folder crosses two namespaces, possibly on two shards. Handle it as a copy-then-delete saga (Chapter 48): commit the new file in the destination (chunks are shared by hash, so no bytes are copied), then tombstone the source. The brief window where both exist is acceptable and the retry is idempotent.

9.2 Conflict detection

Two devices may edit the same file without seeing each other's change: laptop and phone both offline, or two collaborators on a shared folder. The server must not silently let one overwrite the other. The mechanism is optimistic concurrency with a base revision: each commit declares parent_rev, the revision it was based on. The server accepts the commit only if parent_rev equals the current latest_rev of that file. Otherwise some other commit landed first, and the second writer has a conflict.

Why not use timestamps ("last write wins")? Device clocks disagree by seconds to minutes, and some are simply wrong (Chapter 27). LWW would pick a winner by a meaningless clock and destroy the loser's work. Revisions are ordered by the server, per file, inside the transaction, which is a total order we can trust. For whole-tree causality across devices, version vectors are overkill because the server is a single serialization point for each namespace; that central authority is why this is simpler than a peer-to-peer sync tool (Chapter 28 discusses when you do need vectors).

9.3 Conflict resolution: keep both

A file sync service cannot understand an arbitrary binary file well enough to merge it. The safe policy is: the first commit wins the name, the second becomes a conflicted copy. The server rejects the stale commit with 409. The client then downloads the winning version, and uploads its own as a new file named for example Report (Kiran's conflicted copy 2026-11-17).docx, at the same location. Nothing is lost, and the human merges. For text and some structured formats, an application-level three-way merge using the common ancestor parent_rev could be attempted, but it is an optional enhancement because wrong merges are worse than visible conflicts.

Walkthrough. Read the top row as the server's history of report.docx: revision 5, then revision 6 written by device A. 1. Both devices start from revision 5. 2. The reason for the design is that the server, not a clock, orders revisions, and that a sync service cannot merge arbitrary binary files. Other tree conflicts need rules too. Edit versus delete: if A deletes a file while B edits it, B's edit wins (resurrect the file with B's content) because data preserved beats data destroyed. Rename versus edit never conflicts because identity is the file_id. Two files created with the same name: the unique constraint on (ns_id, parent_id, name) rejects the second, which then gets a conflicted-copy name. Move a folder into its own descendant (A moves X into Y while B moves Y into X) would create a cycle: the commit transaction checks ancestry and rejects the second move.

10. Sharing, permissions and versioning

Sharing maps onto namespaces. Sharing a folder converts that folder into its own namespace (if it is not already), then adds mount rows giving each member a path and role (viewer, editor, owner). Because the journal and commits belong to the namespace, collaborators sync the shared folder exactly as they sync their own files; nothing special exists on the sync path other than a permission check at the metadata service on every call. Permissions for nested sub-folders inherit from the namespace; an exception (a restricted sub-folder) is created by splitting it into its own namespace again. This avoids per-file ACL lookups on the hot path. The ACL service caches (Chapter 13) role lookups keyed by (user, ns), invalidated on membership changes, and revocation takes effect within seconds because notification connections are also closed for removed members.

Link sharing (anyone with the link) uses an unguessable random token (at least 128 bits) that maps to (ns, file, role, expiry, optional password). Links are served via the web/CDN path and are rate-limited and revocable.

Versioning falls out of the model. Each commit creates a new file_version row with its own chunk list; old versions remain until retention expires. Because versions share unchanged chunks by hash, keeping 100 versions of a 1 GB file that changes by 1% per edit costs about 2x, not 100x. Restore is just a new commit whose chunk list copies an old version's list (no bytes move). Deleting a file sets a tombstone and keeps its versions for the retention window (say 30 days free, 180 days paid) before their chunk references are released. Retention enforcement is a background job that decrements refcounts and feeds the chunk garbage collector.

11. Offline clients and the many-small-files problem

The client is half the system. It keeps a local database (SQLite) mapping each path to the last synced revision, size, mtime and chunk hashes, and a pending-operations queue. A filesystem watcher (inotify, FSEvents, ReadDirectoryChangesW) produces events; because event delivery can drop under load, periodic full scans verify. Offline edits queue locally. On reconnect, the client first pulls remote changes (list_changes), then pushes local changes with their base revisions, so conflicts are detected exactly as in section 9 and resolved without losing anything. Moves detected as "delete plus create of the same content" are turned into a rename by matching hashes, avoiding a re-upload.

Mobile uses selective sync and on-demand "smart" files: the tree is listed, but bytes are fetched only on open, and clients hold a bounded cache. Mobile also needs battery-aware behavior: no persistent long-poll connection; use the platform push service (APNs, FCM) to wake the app, which then calls list_changes. See Chapter 56.

12. Scaling, caching and cost

  • Block tier: stateless, scale by adding nodes. 12,000 chunk writes per second at peak, 4 MB each, is about 48 GB/s; with 25 Gbit/s (about 3 GB/s) of usable NIC per node, we need about 16 nodes just for ingress, so provision about 50 for redundancy and headroom, and more for downloads. Place block services next to the object store region to keep bytes off the long haul.
  • Chunk index: a hash-keyed KV store (consistent hashing, Chapter 25). A Bloom filter in front of each node answers "definitely not stored" cheaply, so the common "new chunk" case avoids a disk lookup (Chapter 57).
  • Metadata cache: folder listings and ACLs cached in Redis (Chapter 15) keyed by (ns, folder, journal seq); the sequence in the key makes invalidation implicit, since any change bumps the sequence. A cache stampede on a popular shared folder is avoided with request coalescing (Chapter 14).
  • Tiering: chunks untouched for 90 days move to cheaper cold storage classes (Chapter 21). At 670 PB unique, if 70% is cold and the cold tier costs about a third as much, the saving is large. The catch is retrieval latency, which a "restoring from archive" state in the client hides.
  • Cost drivers: storage (about 1.2 EB raw) dominates; egress is second. Dedup (1.5x) and delta sync directly cut both. Erasure coding (1.4x) versus 3x replication saves about 1.6 bytes of storage per user byte, which at this scale is hundreds of petabytes.

Worked bandwidth check: 93 Gbit/s average ingress at 1 PB per day. A single large region would need about 300 Gbit/s peak ingress, so spread across at least three regions with clients routed to the nearest by DNS or anycast (Chapter 4).

The consistency summary: strong within a namespace for metadata (single primary per shard, serialized commits, journal in the same transaction); immutable and content-addressed for bytes, so there are no consistency problems on blocks; eventual for propagation to other devices, with a convergence bound of seconds. The commit is the linearization point. This matches the "choose per feature" advice of Chapter 28: during a partition between regions we prefer consistency for writes to a namespace (route to its home region) and accept that remote readers see slightly old data.

14. Security, abuse and monitoring

  • Encryption: TLS in transit; at rest each chunk is encrypted with a per-chunk or per-namespace data key, and data keys are wrapped by a master key held in a KMS (Chapter 55). Convergent encryption (key derived from content) preserves dedup but reveals whether a file is a known one; per-user keys give up cross-user dedup. This is a deliberate product decision. True end-to-end encryption means the server cannot chunk, dedup or preview, so it is out of scope.
  • Authorization: every block fetch checks that the caller can read a file that references that chunk (pre-signed URLs are scoped to a chunk and expire in minutes); knowing a hash must not be enough to download it.
  • Abuse: per-account quotas on storage and on request rate; malware scanning and known-bad-content hash matching run asynchronously after upload (the async workers), with sharing blocked for flagged files; link sharing is rate-limited to resist scraping and used as a bandwidth-abuse vector (Chapter 16).
  • Monitoring and SLOs: commit success rate 99.99%; p95 commit latency under 300 ms; p95 end-to-end propagation (commit to notification delivered) under 2 s for online devices; chunk durability checks (scrub error rate); GC backlog and refcount mismatch counters; notification connection counts; queue depth of the async workers. Alert on the sync-lag SLI, the time between a commit and the last online member of the namespace applying it, which is what users actually feel (Chapter 54).

15. Evolution, phasing and alternatives not chosen

15.1 What to build first

  1. MVP: single region; fixed 4 MB chunks with hashing and dedup per user; object store for blocks; one SQL cluster with namespace-based schema and a journal; long-poll notifications; conflicted-copy resolution. This already supports resumable upload and efficient sync, and the namespace schema means it is shardable later without a rewrite.
  2. Scale-out: shard the metadata by namespace, add the chunk-index KV, CDC chunking in the client, batch commits, notification fan-out tier.
  3. Maturity: sharing and link sharing, versioning and retention, cold tiering, cross-user dedup with proof of possession, multi-region, delta sync for large files, pack files for small objects.

15.2 At 10x scale (5 billion users, 10 EB)

Metadata becomes about 1.5 PB; a two-level shard map (namespace to logical shard to cluster) already handles that, with more clusters. The chunk index grows to about 110 TB, still fine. Storage cost is the issue, so invest in better compression, cold tiers, and own hardware (the largest providers eventually build their own storage fleets to escape cloud object-store pricing). Notification fan-out hits 1 billion connections, which pushes toward cell-based architecture where each cell serves a subset of users end to end (Chapter 42) and toward hierarchical pub-sub.

15.3 Alternatives not chosen

  • One big key-value store for metadata: scales easily, but loses multi-row transactions for commit and rename, and makes the tree-integrity rules (unique names, cycle checks) hard. Systems that do this (a NewSQL database or a KV store with a transaction layer) are valid, but sharded SQL is simpler to reason about for this shape of data.
  • Whole-file storage with no chunking: far simpler, fine for a small internal tool; fails on large files, resume and dedup.
  • Peer-to-peer LAN sync (devices on one office network exchange chunks directly): a real optimization of production services; it saves egress but adds a security and discovery surface. A good future item.
  • CRDT-based merge for documents: the right answer for collaborative documents, but a different product (see the collaborative editor case study).
  • Polling instead of notifications: trivial, but 100 M devices polling every 30 seconds is 3.3 M requests per second of pure waste. Long-poll plus cursors cuts that to near zero when nothing changes.

16. Interview Q&A

Why chunk files instead of storing them whole, and how big should the chunks be?

Chunking gives you four things at once: you upload only changed pieces, an interrupted upload resumes from the last finished chunk, identical content across files and users is stored once through hash addressing, and large files can be transferred in parallel. Size is a tradeoff between metadata overhead and delta granularity. Very small chunks (64 KB) create trillions of index entries and request overhead; very large chunks (64 MB) make a tiny edit re-upload a lot. Around 4 MB average works well, with content-defined boundaries and 1 MB to 16 MB bounds. I would also not chunk files smaller than one chunk.

A user inserts a paragraph at the top of a large document. How much is re-uploaded?

With fixed-size chunks, every byte after the insertion shifts, so every chunk's hash changes and the whole file would be re-uploaded. With content-defined chunking, boundaries are set by a rolling hash over the local bytes, so only the chunk containing the insertion changes and the later boundaries re-synchronize to the same places. The client hashes its new chunks, asks the server which hashes are missing, and uploads only that one chunk plus the new commit with an updated chunk list. For a very large chunk you could also send a binary delta against the old chunk.

How do two devices stay in sync without polling the whole tree?

Each namespace has an ordered change journal, with a sequence number assigned inside the same transaction as the change. Each device stores a cursor, which is the last sequence it applied, and calls list_changes with that cursor to get only newer entries. To learn promptly that something changed, the device holds a long-poll or WebSocket to a notification service that is told by the metadata service on each commit. The notification only says which namespace changed, so losing it is harmless: the device will see the change on its next poll or reconnect. Cursors also let a device that was offline for weeks catch up with one call.

How do you detect and handle a conflict?

Every commit carries the revision the edit was based on, parent_rev. The metadata service, inside the commit transaction, compares it to the file's current latest revision. If they differ, another device committed first, so we reject with a conflict instead of overwriting. The client then keeps the winning version in place and uploads its own as a conflicted copy with a descriptive name, so no data is lost and the user merges. I avoid last-write-wins timestamps because device clocks are unreliable and would silently destroy edits. For edit versus delete I resurrect the edited file, since preserving data is safer.

Why shard metadata by namespace rather than by user or file id?

A commit must atomically check the base revision, insert the version, update the latest pointer and append to the journal, and a rename must update tree rows consistently. Putting everything for one namespace on one shard keeps these in a local ACID transaction, without distributed commit. Sharding by file id would scatter a folder across shards and make listing and moves multi-shard. Sharding by user breaks shared folders, which belong to several users. The namespace is the natural unit for sync, sharing and permissions. The cost is that a giant namespace can be a hot shard, which I handle with dedicated shards and per-namespace limits.

How does dedup work, and what are the security risks?

The chunk's SHA-256 hash is its key. The client sends hashes, the server replies which it lacks, and only those are uploaded, so identical content from any user is stored once with a reference count. The risk is that revealing a chunk exists leaks that someone stored that content, and a client who only knows the hash could claim the data. Mitigate with proof of possession (the server asks for a hash of a random byte range mixed with a nonce), scope dedup to a user or team for sensitive tiers, and authorize every block read through the files that reference it. Garbage collection of zero-reference chunks waits for a grace period to avoid racing with new uploads.

How do you make a 50 GB upload reliable?

Split it into chunks of several MB and upload many in parallel, each with its own retry. Because chunks are addressed by hash, a retry is idempotent, and after any disconnect the client asks the server what is missing and continues. An upload session on the server records progress so a restart of the client can resume. The client pipelines hashing and uploading rather than hashing the whole file first. Only after all chunks are durable does the client send a single commit with the chunk list, so a half-uploaded file is never visible. This mirrors multipart upload in object stores.

What if the notification service goes down entirely?

Sync becomes slower but not incorrect. The journal and cursors are the source of truth, and clients fall back to polling list_changes at a modest interval (with jitter to avoid a storm), so devices still converge, only in tens of seconds instead of a couple. The notification servers hold only soft state (the connection map), so they can be restarted or replaced at will, and clients reconnect with backoff. We alert on the sync-lag SLI. That is a strong reason to keep notifications as hints and never put data in them.

How would you support sharing a folder with 10,000 people?

The folder is its own namespace with one journal, so edits create one journal row regardless of members, and metadata cost does not multiply by member count. The notification fan-out does: one commit must wake up to 10,000 devices, then each calls list_changes. I batch and coalesce notifications, add random jitter before the follow-up fetch, and serve the journal read from a cache keyed by the sequence number so 10,000 identical requests are cheap. Chunk downloads of a popular file go through a CDN. The namespace gets its own dedicated shard and rate limits, because it is the likeliest hot spot.

How do you delete data safely, and implement versioning cheaply?

Each version is a chunk list, and chunks are shared by hash, so keeping many versions costs only the changed chunks. Deleting a file adds a tombstone and keeps its versions for the retention period. When a version expires, a background job decrements reference counts of its chunks. A chunk reaching zero is queued for garbage collection after a grace period, then confirmed by a mark phase that no version references it, and only then deleted from the object store. Slow and double-checked deletion is intentional: the cost of a leaked chunk is a few MB, but the cost of deleting a live chunk is a customer's lost file.

How would you handle end-to-end encryption if the product required it?

The client would encrypt chunks with keys the server never sees, so the server cannot chunk, hash for dedup, scan for malware, or generate previews. Chunking and hashing would move entirely to the client, and dedup would be limited to a single user's data (or use convergent encryption, accepting its leak that a known file is detectable). Sharing requires exchanging keys between users, typically by wrapping each namespace key with each member's public key, with rekeying on membership removal. Search, thumbnails, and server-side conflict merge are lost. It is a real product tradeoff, which is why I treat it as a separate tier rather than the default.

17. Recap

  • Split the problem: immutable chunk bytes go to an erasure-coded object store; small, strongly consistent metadata goes to namespace-sharded SQL. Bytes flow around the metadata servers.
  • Estimation drives choices: about 1 EB logical, 670 PB unique, 100 B files, 2,300 commits per second (7,000 peak), about 93 Gbit/s average ingress, 175,000 metadata QPS peak, 100 M notification connections.
  • Content-defined chunking (about 4 MB) with hashing gives delta sync, dedup and resumable parallel upload; protect dedup with proof of possession and reference-counted, delayed garbage collection.
  • Upload order is bytes first, commit last, so a file version never refers to missing chunks. Commits are idempotent and use a base revision for optimistic concurrency.
  • Sync uses a per-namespace gap-free journal, per-device cursors, and long-poll notifications that are only hints; clients converge even if notifications are lost.
  • Conflicts are detected by base revision and resolved by keeping both (conflicted copies); never trust timestamps.
  • Sharing is namespaces plus mounts; versions are chunk lists; most hot spots (large files, many small files, huge shared folders) have specific mitigations: parallel sessions, batching, pack files, dedicated shards.
