Case study 13 · Worked solutions

Design Uber / Nearby Search

A ride-hailing service must keep a live map of a million moving cars, find the best few of them around any rider in milliseconds, hand a trip to exactly one driver, and keep every phone in sync. This worked solution builds that system step by step, and then shows how the same ideas simplify into a Yelp-style search for places that do not move.

1. Problem statement and clarifying questions

The prompt is short: "Design a ride-hailing service like Uber." In an interview the first job is to turn that sentence into a problem that fits in 45 minutes. The interesting core is geospatial: drivers move constantly, riders ask "who is near me", and the system must pair them. Everything else (payments, driver onboarding, ratings, maps rendering) is real but secondary. Following the framework in Chapter 1, I would ask the questions below and state the answers I will assume, so the interviewer can correct me early.

2. Requirements and scope

2.1 Functional requirements

  • Drivers go online or offline and stream their location.
  • A rider sees nearby available drivers on a map and an estimated pickup time and price.
  • A rider requests a trip with a pickup and destination; the system selects a driver, offers the trip, handles decline or timeout, and reassigns.
  • Both parties see each other's live location and trip status until the trip ends.
  • The trip moves through a defined set of states, and each change is durable and visible to both apps.
  • Location history is stored for support, fraud checks, analytics, and model training.

2.2 Non-functional requirements

  • Low latency on the nearby query (p99 under 100 ms inside the service) and on dispatch.
  • High write throughput for locations: hundreds of thousands per second, mostly overwriting the previous value for the same driver.
  • Correct assignment: a driver is never assigned twice, a rider never gets two cars for one request, even under retries and crashes.
  • Availability over perfect freshness for the location index: losing a few seconds of positions is acceptable, losing the ability to dispatch is not. Trip state, in contrast, must be durable and strongly consistent per trip (Chapter 28).
  • Regional isolation: a failure in one city's infrastructure must not stop other cities.

2.3 Out of scope

Payments and receipts, driver background checks, map tile rendering, turn-by-turn navigation, pooled rides, driver incentives, chat between rider and driver, and fraud models. I will name where they would plug in but not design them.

3. Estimation

The method comes from Chapter 2: pick round numbers, show arithmetic, and use the results to decide the architecture.

3.1 Trips and dispatch

  • 20 million trips per day is 20,000,000 / 86,400, about 230 trips per second on average. Demand is peaky (evening rush, Friday night), so assume a peak of 3 times, about 700 trip requests per second worldwide.
  • Each request may produce several offers (some drivers decline): assume 3 offers on average, so about 2,100 offers per second at peak. This is small. Dispatch is not a scale problem; correctness is.

3.2 Driver location updates

  • Peak online drivers: 1,000,000. Each sends a fix every 4 seconds, so 1,000,000 / 4 = 250,000 updates per second at peak.
  • Average over the day: assume 600,000 drivers online on average, so 150,000 updates per second.
  • Message size: driver id (8 bytes), latitude and longitude (8 bytes), heading, speed, accuracy, timestamp, status: about 40 bytes of useful data, roughly 100 bytes with framing. At peak that is 250,000 x 100 bytes = 25 MB/s inbound (about 200 Mbit/s), spread over the world. This is modest for the network but very large for any system that writes every update to a disk-based relational table.

3.3 Nearby queries

  • Opening the app shows cars around the rider. Assume 5 million app opens per day in busy windows, plus riders who keep the map open and refresh every 5 seconds. Say 200,000 riders have the map open at peak, refreshing every 5 s: 40,000 queries per second at peak. In practice we push the map via the realtime channel rather than poll, but we budget for 40,000 reads per second.
  • Read to write ratio on the location index: 40,000 queries against 250,000 writes, so this store is write-heavy, unusual for a "search" system.

3.4 Memory for the live index

  • One live record per driver: id, lat, lon, heading, speed, status, cell, timestamp, current trip id: about 100 bytes, rounded to 200 bytes with hash-table overhead. 1,000,000 x 200 bytes = 200 MB. Even at 10 million drivers it is 2 GB.
  • Conclusion: the entire live driver set fits in the memory of one machine. We shard for write throughput (250,000 writes per second is too many for one Redis instance, which does roughly 100,000 simple operations per second per core) and for regional isolation, not for capacity.

3.5 Location history

  • Points per day on average: 150,000 per second x 86,400 = about 13 billion points per day.
  • At 40 bytes per point: 13 x 10^9 x 40 = about 520 GB per day raw, or about 190 TB per year. Columnar compression on sorted, delta-encoded data typically gives 4 to 8 times, so around 30 to 50 TB per year compressed. This goes to a stream plus object storage, never to the serving index.
  • Many products downsample (keep one point per 10 seconds after a week, or only trip-time points), cutting this further.

3.6 Realtime connections

  • 1,000,000 online drivers hold a persistent connection each, plus riders in active trips and with the map open: say 500,000 more. 1.5 million concurrent connections. At roughly 100,000 per gateway machine that is 15 machines per peak, in practice 40 to 60 for headroom and regional spread.
Key idea The numbers tell the story. Driver positions are a small, hot, overwrite-heavy dataset (200 MB) with a high write rate (250,000 per second), so it lives in memory and is sharded for throughput. Trips are rare (700 per second) and need strong correctness, so they live in a durable database. History is huge and cold, so it flows through a stream into cheap storage. Three data shapes, three stores.

4. API design

Two kinds of interfaces exist: ordinary request/response HTTPS for actions (request a ride, get an estimate), and a persistent bidirectional connection for streams (driver locations up, offers and positions down). See Chapter 5 for API principles and Chapter 6 for the realtime options.

4.1 Request/response (HTTPS, JSON or protobuf)

GET  /v1/nearby-drivers?lat=37.77&lon=-122.41&radius_m=2000&type=economy
     -> { drivers: [ { id_masked, lat, lon, heading } ... up to 20 ], eta_min: 3 }

POST /v1/fare-estimates        { pickup, dropoff, type }
     -> { fare_low, fare_high, surge: 1.4, quote_id, expires_at }

POST /v1/trips                 { quote_id, pickup, dropoff, type }
     Header: Idempotency-Key: 7f3c...        (same key = same trip, never a second one)
     -> 202 { trip_id, state: "REQUESTED" }

POST /v1/trips/{id}/cancel     { reason }
GET  /v1/trips/{id}            -> full trip document (for reconnect and recovery)

POST /v1/drivers/me/status     { online: true, vehicle_type }
POST /v1/offers/{offer_id}/accept   |   /decline

The Idempotency-Key matters: mobile networks drop responses, and an impatient user taps twice. Without a key the retry would create a second trip; with it, the server returns the first trip. Mechanics are in Chapter 32. The ride request returns 202 Accepted immediately, because matching takes unknown time; progress arrives on the realtime channel.

4.2 Realtime messages (WebSocket)

driver -> server   { t: "loc", lat, lon, hdg, spd, acc, ts, seq }        every ~4 s
server -> driver   { t: "offer", offer_id, trip_id, pickup, eta_s, fare, expires_in_s: 15 }
driver -> server   { t: "accept", offer_id }
server -> rider    { t: "trip", trip_id, state, driver: { name, car, plate }, version }
server -> rider    { t: "pos", trip_id, lat, lon, hdg, eta_s }              every ~2-4 s while en route

Every trip message carries a version number that increases with each state change, so a phone that sees version 7 after version 8 (because of reordering) can ignore the older one. The location message carries a client sequence number seq for the same reason: the server must not let a late packet overwrite a newer position.

5. Data model and storage choices

Three data shapes need three storage designs.

5.1 Live driver index (in memory)

This is the "where is everyone right now" store. Redis (Chapter 15) is a natural fit: single-digit-microsecond operations on in-memory structures, TTLs, and sorted sets. Layout:

drv:{driver_id}   HASH   lat, lon, hdg, spd, ts, status, cell, trip_id      TTL 15 s
cell:{cell_id}    ZSET   member = driver_id, score = last update timestamp

On each update we write the driver hash (and refresh its TTL), and if the driver crossed into a new cell, remove the id from the old cell's set and add it to the new one. Redis also offers built-in geospatial commands (GEOADD, GEOSEARCH) which store members in one sorted set scored by a 52-bit geohash. They are convenient, but a single key cannot expire individual members and one huge key lives on one shard, so the per-cell layout is better at this scale. The reasoning is in section 8.

5.2 Trips and driver assignment state (durable)

Trips are few, long-lived, and must be correct, so they live in a replicated database. A relational store partitioned by trip id, or a strongly consistent NoSQL such as one with conditional writes (Chapter 20), both work; I would pick sharded relational because trip, offer and driver-assignment updates benefit from transactions (Chapter 18).

trips(trip_id PK, rider_id, driver_id NULL, state, version, pickup, dropoff,
      quote_id, fare, region, created_at, updated_at)
offers(offer_id PK, trip_id, driver_id, state[PENDING|ACCEPTED|DECLINED|EXPIRED],
       expires_at)
driver_assignment(driver_id PK, trip_id NULL, status[AVAILABLE|OFFERED|BUSY], version)

The driver_assignment table is the single source of truth for "is this driver free". It is deliberately a tiny, separate row per driver so that a conditional update on it is the arbiter of the one-driver-one-trip rule (section 11).

5.3 Location history (stream then columnar storage)

Every update is also published to a log (Chapter 34), partitioned by driver id so each driver's points stay ordered. Consumers write batches to object storage in a columnar format (Chapter 21, Chapter 37), partitioned by day and region, and a time-series or analytics store serves "show the route of trip X". Trip routes are also stored compactly with the trip itself (a polyline) for receipts and disputes.

6. Geospatial indexing: the core idea

A database index on (lat, lon) cannot answer "points within 2 km" well. A normal B-tree sorts by one key; sorting by latitude finds a horizontal band around the world, and sorting by longitude finds a vertical band, and the intersection is not contiguous in either order. We need a way to map two dimensions to one while keeping nearby points mostly nearby in the one-dimensional order, or to partition space into buckets and look up buckets. Chapter 58 covers the techniques in depth; here is the working recap and the choice.

6.1 The candidates

  • Geohash. Interleave the bits of longitude and latitude and write the result in base 32. Each extra character divides the cell by 32 (a 5-bit refinement alternating between lon and lat). A 6-character geohash covers roughly 1.2 km by 0.6 km, and a 7-character one roughly 150 m by 150 m. Points sharing a prefix share a cell, so a prefix lookup finds a cell. The catch: two points very close across a cell boundary can have completely different prefixes (the antimeridian and the equator-like seams are the worst), so you must always query the cell and its 8 neighbours. Cells are rectangles whose real-world shape changes with latitude.
  • Quadtree. Recursively split a square into four children whenever a node holds more than K points. Dense downtown regions become deep trees with tiny leaves; deserts remain a single big leaf. This adapts to density, which is attractive, but it is a pointer-heavy tree that changes as points move; every update may delete from one leaf and insert into another, possibly triggering splits and merges. Good for static or slowly changing data; awkward for 250,000 moves per second.
  • S2 (Google). Project the sphere onto the six faces of a cube and order cells along a Hilbert space-filling curve. A cell has a 64-bit id, and the hierarchy is 30 levels deep. A region (circle or polygon) is converted into a small covering of cell ids at mixed levels. Hilbert order preserves locality better than the Z-order used by geohash, and cell shapes are nearly uniform across the globe.
  • H3 (Uber). Hexagonal cells in a hierarchy of 16 resolutions. Hexagons have a useful property: every neighbour is the same distance from the centre (six equidistant neighbours, no corner neighbours), which makes "ring" queries and smooth density maps (surge) cleaner. Resolution 8 hexagons are about 0.7 km2, resolution 9 about 0.1 km2. Cells at a level are not perfect parents of the next level (hexagons cannot tile exactly), a minor quirk.

Decision Use a fixed-resolution hierarchical cell id as the index key (H3 or S2; geohash would also work). The cell id is a cheap pure function of latitude and longitude, so a location update does not touch any tree, and a query is "compute neighbours, read buckets". Pick a level of about 1 km cells for dispatch lookups and a coarser parent (about 10 to 20 km) as the sharding unit. I would mention geohash first because every interviewer knows it, and say I would use H3 in production because its uniform neighbours make surge and ring expansion clean. Quadtrees are the right answer for the static POI variant in section 16.
Watch out Do not search "the cell containing the rider" only. A rider on the edge of a cell would miss a driver 20 metres away across the boundary. Always include neighbours, and always finish with an exact distance (haversine) filter, because the neighbour ring covers more area than the circle.

7. A first simple design

Start simple, as Chapter 1 advises. One application server and one database: drivers POST their location every 4 seconds, the server runs UPDATE drivers SET lat=?, lon=?, cell=?, ts=? WHERE id=?, and a nearby query is SELECT ... WHERE cell IN (9 ids) AND status='AVAILABLE' with an index on cell. A rider requests a trip, the server picks the nearest driver, and polls tell each phone what changed.

This works for a demo. It breaks in four predictable ways, and naming them motivates every later component:

  1. Write load. 250,000 updates per second against an indexed table is far beyond one database, and each one rewrites an index entry. The data is disposable the moment the next fix arrives, so paying for durability is wasteful. This pushes the live index into memory.
  2. Polling. Phones polling for state waste battery, add seconds of delay, and multiply request count. This pushes us to persistent connections.
  3. Double assignment. Two requests selecting the same nearest driver at the same moment would both succeed. This forces an atomic claim step.
  4. One box, one city. A single machine is a single point of failure and has one geographic location; cross-ocean latency is unacceptable for a city on another continent.

8. Scaled high-level architecture

8.1 Components and their jobs

  • Realtime gateway terminates WebSocket connections (Chapter 6), authenticates them, and forwards messages inward. It keeps a map from user id to connection. It is stateless apart from that map, which is rebuilt as clients reconnect.
  • Location service validates updates, writes the live index, and publishes to the log.
  • Live driver index is the sharded in-memory store of section 5.1.
  • Dispatch service performs the nearby search, ranking, offers, timeouts and reassignment.
  • Trip service owns the trip state machine and the assignment table, and is the only writer of those.
  • ETA/routing service answers "how long from A to B by road now".
  • Surge job is a stream-processing job that computes demand and supply per cell.
  • Event log and history store carry location history and trip events to analytics.

8.2 Location ingest in detail

Walkthrough, in order:

  1. The driver app sends a fix over the already-open WebSocket. It batches nothing; every 4 seconds is fine. If the driver is stationary the app can slow to every 10 to 15 seconds to save battery and load. If the driver is on a trip it can speed up to every 2 seconds for a smooth rider map.
  2. The gateway adds the authenticated driver id (never trust an id inside the payload) and forwards it to the location service, choosing an instance by hashing the driver id so one driver's updates stay ordered.
  3. The location service computes the cell id from lat/lon. It runs a short Lua script or pipeline on the shard for that cell: compare seq to the stored one (drop if older), write the hash, refresh the 15-second TTL, and if the cell changed, move the id between cell sets. A driver who stops sending (phone dies, tunnel) vanishes from the index automatically after the TTL, with no cleanup job.
  4. The service publishes the same fix to the event log asynchronously. If the log is slow, the service buffers a small amount and then drops; history is allowed to have gaps, the live index is not blocked.

8.3 Why a cell set per key and not one geospatial key

Redis's GEOSEARCH works on one sorted set: simple, but a city-sized set is one key on one shard, so the largest city sets the limit of a single core, and members cannot expire individually (stale drivers would linger until removed explicitly). Per-cell keys fix both: keys spread across the cluster, expiry is handled by the timestamp score (ZREMRANGEBYSCORE on read or a periodic sweep) plus the TTL on the driver hash, and each query reads a small set. The cost is that we implement neighbour lookup ourselves, which the cell library gives us.

9. The nearby query and ranking

There are two consumers of the same index: the map (show cars around me, approximate, cacheable) and dispatch (choose the best driver for a real request, precise). Both do the following:

  1. Compute the home cell and its ring-1 neighbours (7 hexagons or 9 squares).
  2. Issue the reads in parallel to the shards holding those cells (usually one or two shards, see section 15) and read the drivers' compact records.
  3. Filter out stale records (older than about 10 seconds), drivers whose status is not AVAILABLE, and drivers who do not match the vehicle type.
  4. Filter by exact distance to a maximum radius, and if fewer than a target (say 10) remain, expand to ring 2 and repeat. Each ring multiplies the cells read, so cap expansion (two or three rings).
  5. Rank the candidates.

9.1 Ranking: straight-line distance is not enough

A driver 300 metres away across a river or on the other side of a divided highway may be 12 minutes away by road, while one 900 metres away on the same street is 2 minutes away. So ranking uses ETA to pickup, not distance. Calling a routing engine for all 40 candidates is wasteful, so use a two-stage approach: pre-rank by straight-line distance (cheap), take the top 8 to 10, then ask the ETA service for the road time of just those, in one batch call. The ETA service (a road graph with precomputed shortcuts, often contraction hierarchies, plus live traffic speeds per road segment) answers each in about a millisecond or less; a batch of 10 stays in single-digit milliseconds. Additional ranking terms often include driver heading (a car already driving toward the rider is better), acceptance history, and fairness (do not always burn the same driver's idle time).

9.2 ETA and price shown on the map

The ETA shown on the nearby screen is the best driver's ETA in that cell, and does not need to be fresh per rider. Results for a rider tapping around the same block can be cached for a few seconds, keyed by cell (Chapter 13). A cached "5 cars, 3 min" is acceptable; dispatch for a real request never uses cached results.

10. Dispatch: offers, timeouts and reassignment

When the rider requests a trip, the trip service creates the trip in state REQUESTED and hands it to dispatch. Dispatch has to turn a ranked list into exactly one accepted driver. There are three common strategies:

StrategyHowProsCons
Sequential offersOffer to the best driver; wait up to about 15 s; on decline or timeout offer to the next.Simple, one driver at a time, no wasted offers, easy to reason about.Slow when drivers decline; each decline costs seconds.
Broadcast to N, first accept winsOffer to the top 3 to 5 at once; the first to accept gets it.Faster pickup.Drivers see offers that vanish; needs a strict atomic claim; drivers get annoyed.
Batched global matchingEvery 2 seconds, solve an assignment problem over all open requests and available drivers in a region to minimise total wait.Better overall efficiency in busy areas; avoids greedy mistakes (nearest driver stolen from another rider who had no other).More complex; adds up to the batch interval of latency.

I would start with sequential offers (first version) and describe batched matching as the evolution at scale. Greedy "nearest driver per request" can be globally worse: if two riders request at the same time and one driver is nearest to both, giving that driver to rider A may leave rider B with a 15-minute wait, while giving B the same driver and A another 3-minute driver would have been better overall.

10.1 Details that interviewers probe

  • Offer timeout. Typically 10 to 20 seconds. The timer lives in the dispatch worker but must survive its crash, so the offer row stores expires_at and a scheduler (Chapter 38) or delayed queue wakes a handler at that time; the handler checks "is this offer still PENDING?" and expires it. A late accept after expiry must be rejected by the same check.
  • Hold during an offer. While A is considering an offer, no other trip should offer A. Setting A's assignment status to OFFERED (with the offer id and expiry) does that; the nearby query already filters on AVAILABLE. If A declines or times out, a conditional update flips A back to AVAILABLE only if it still holds this offer.
  • Reassignment. Beyond decline and timeout there is a driver cancelling after accepting, or a driver app going silent while en route. The trip returns to MATCHING, the previous driver is excluded for this trip, and dispatch runs again with a fresh search and a priority boost for the rider (they already waited).
  • Giving up. After a bounded total time (for example 2 minutes) or number of offers (say 8) the trip becomes NO_DRIVERS and the rider is told, possibly with a suggestion to try later or a higher price.
  • Many requests, few drivers. Process requests in arrival order per region; sequential dispatch with a per-region queue prevents two workers racing for the same pool, although correctness never depends on that (section 11).

11. Deep dive: one driver, one trip

This is the part of the design where correctness matters most and a loose approach causes real harm: two riders are told the same car is coming. The location index is eventually consistent and cannot be the arbiter, because it can show a driver as available for a few seconds after they accepted another trip. So the index is a hint; a separate strongly consistent record is the authority.

Decision: use option A as the source of truth, with option B as an optional fast pre-check to avoid pointless database work. The conditional write is a compare-and-set on a row: of two concurrent claims for the same driver, the database serialises them and exactly one sees the row in the expected state. Add a version or fencing-style check so that a stale worker (one that was paused for 30 seconds, woke up, and still believes it holds the offer) cannot overwrite a newer state: its update names an expected version or offer id that no longer matches, and affects zero rows.

Key idea Do the assignment as a state transition on a durable row, not as a lock. A lock says "I may act"; a conditional write says "the world is still as I thought, and now it is changed". The second remains correct when processes pause, crash, retry, or run twice.

11.2 The two-sided claim

The accept touches two entities: the trip (REQUESTED to ACCEPTED) and the driver (OFFERED to BUSY). If they live in different shards this is a distributed transaction (Chapter 31). The cleanest fix is to avoid one: store the assignment on the driver shard first (the claim is the commit point), then update the trip by id asynchronously with retries, and let a reconciliation process repair mismatches. Equivalent view as a saga (Chapter 48): step 1 claim the driver, step 2 attach the driver to the trip, compensation if step 2 fails (release the driver). Another approach is to colocate: shard both trips and assignments by region so a trip and its drivers live in the same database shard, and use one local transaction. Because a trip is local to a city, regional colocation is natural and I would pick it.

11.3 Idempotency and retries

Every state-changing call carries a key (trip_id + offer_id + action), so a retried accept returns the previous result rather than failing or re-applying. A driver app that loses its connection right after tapping accept reconnects and fetches the trip, learning the true state. The rider side uses the idempotency key from the request so a double tap yields one trip.

12. The trip state machine

The state machine is where rules live. It defines the legal transitions (for example COMPLETED is terminal; ACCEPTED may return to MATCHING but IN_PROGRESS may not), who may trigger each (driver app, rider app, system timer, support), and which side effects fire on entry: a push notification, an event on the log, a charge on completion, a surge counter on request. Putting this in one service with conditional writes means two components can never push the trip into contradictory states, and the version number lets clients ignore stale messages. Transitions publish an event to the log using the outbox pattern (write the event in the same transaction as the state change, a separate relay publishes it), so downstream payment and analytics never miss or invent a transition (Chapter 36).

13. Surge pricing and demand signals

Surge pricing nudges supply and demand toward balance in an area: when requests outnumber available drivers, the multiplier rises, which reduces marginal demand and attracts drivers. The system part is a streaming aggregation (Chapter 37):

  1. Events: trip requests (with pickup cell) and driver availability counts come from the log.
  2. A windowed job counts, per cell at about H3 resolution 8 (roughly 0.7 km2), the requests in the last 1 to 5 minutes and the number of available drivers now. Neighbouring cells are smoothed together, so prices do not jump from 1.0 to 2.5 across a street.
  3. The multiplier is a function of the demand-to-supply ratio, clamped (say 1.0 to 5.0), rate-limited so it changes gradually, and recomputed every 30 to 60 seconds.
  4. The result is written into an in-memory map (cell to multiplier) replicated to the API servers.
  5. When the rider gets a fare estimate, the server reads the multiplier for the pickup cell and returns a quote_id that locks the price for a short time. The trip stores the quote, so a surge change mid-request does not change what the rider agreed to.

Surge is a good example of derived data: it can be a little stale, computed per cell independently, and recomputed if lost. It does not need the strong consistency that assignment needs. Fairness and regulation add caps in some cities and a duty to show the multiplier before booking.

14. Realtime delivery to rider and driver

Polling is wasteful, so we use persistent connections (Chapter 6). WebSocket is the usual choice for bidirectional low-latency traffic: driver locations flow up, offers and trip updates flow down. Server-sent events would work for the rider but not for the driver upstream stream; push notifications (APNs and FCM) cover the case when the app is in the background or the socket is down.

14.1 How a message finds the right connection

The gateway servers are many; the trip service needs to push a message to "rider R". A presence/routing table in Redis maps user_id to gateway_id (written when the socket opens, with a TTL refreshed by pings). The trip service publishes to the gateway named in the table via a pub/sub channel or direct RPC. If no entry exists (user offline), it falls back to a mobile push notification. This is the same pattern as in the chat case study (Case study 7).

14.2 Live position of the driver for the rider

During a trip the rider needs to see the car move. Each driver update on an active trip is also fanned to the rider's gateway: the location service looks up the driver's trip_id (from the driver hash) and sends a message to the rider's connection every 2 to 4 seconds. The app interpolates between points for smooth animation, and the server sends a heading and speed to help. Because this stream is per active trip only (about 20 million per day, at peak maybe 400,000 trips in progress), it is a modest add-on to the 250,000 per second of uplink.

14.3 Reconnect and ordering

Mobile connections drop constantly. On reconnect the client sends its last seen trip version, and the server replies with the current trip document (idempotent state sync) instead of replaying every message. Position messages are "latest wins": the server never needs to deliver an old point, so if the socket is slow it can drop intermediate positions. State-change messages are important, so they are acknowledged and re-sent, and they also exist in the trip record so reconnect always recovers them. A push notification is sent for key transitions (driver arrived) as a backup.

15. Scaling, sharding and hot cells

15.1 Sharding the live index

The index is sharded for write throughput: 250,000 writes per second at peak, each a pipeline of a few commands, which is about 5 to 8 Redis shards worth of work if each handles 50,000 pipelined updates per second comfortably; run 16 or more for headroom and for skew. What is the shard key? Three choices:

Shard keyEffect on updatesEffect on a nearby queryVerdict
Hash of driver idPerfectly even; one shard per driverEvery query must ask all shards (scatter-gather), cost grows with shard countPoor for reads

I choose the coarse parent cell with a directory (consistent hashing or an explicit assignment table from coarse cell to shard, Chapter 25) so that we can rebalance specific cells. Queries at a border read two or three shards in parallel, which is cheap.

15.2 Hot cells

City centres, airports, stadiums after an event and train stations concentrate both drivers and requests. A cell with 10,000 drivers produces 2,500 updates per second on its own keys, which is within one core's capacity, but the reads are the bigger problem: a stadium emptying creates thousands of near-simultaneous requests to the same 9 cells, each reading hundreds of drivers. Remedies, in order of use:

  1. Cap what a query reads. A rider only needs the best 10 to 20. Keep a short per-cell list ordered by availability or read a sample, not all 500.
  2. Finer cells where dense. Move from level 8 to level 9 inside hot areas (the directory records it). Each query reads more but smaller cells in parallel; load spreads over more keys and shards.
  3. Replicas for the map. The "cars near me" map uses read replicas with a few seconds of lag (Chapter 24) and a small cache keyed by cell. Dispatch reads primaries.
  4. Coalesce requests. If 500 requests from a stadium arrive in one second, dispatch can batch them per cell and run a single read and a single assignment solve, which also improves the matching quality.
  5. Queue at the venue. Airports use explicit queues of drivers in a staging area; that is a product rule that removes the problem.

15.3 Multi-region

A trip involves one rider and one driver in one city, so the data is naturally regional. Each city belongs to a home region that holds its live index, dispatch, trips database, and realtime gateways. Users connect to the nearest edge, which routes to the home region of the city they are in (by the coordinates of the request). The global pieces are thin: user accounts and profiles (replicated read-mostly), payment methods, and the analytics pipeline (location events are shipped to a central lake asynchronously).

Key choices (Chapter 26, Chapter 42 for cell-based isolation): trips for a city are written in only one region at a time, so there are no conflicting writes and no need for multi-master conflict resolution. Trip rows replicate asynchronously (or synchronously within a region's availability zones) to the failover partner. The live index is not replicated across regions at all, because the next updates 4 seconds later rebuild it, and replicating 250,000 writes per second across oceans would be wasteful. A city on the border of two regions (rare) is assigned to exactly one. Cross-city trips are tied to the pickup city's region.

16. Variant: static nearby search (Yelp-style)

Now the interviewer says: "Forget cars. Design 'find restaurants near me'." Same geometry, very different workload, and showing that you adapt the design is the point of this section.

16.1 Requirements and numbers

  • Data: 200 million places worldwide, each about 1 KB of metadata (name, address, category, rating, hours, location): 200 GB. Photos and reviews live elsewhere (object storage, a reviews DB).
  • Changes: new or edited places are rare, perhaps 100,000 per day (about 1 per second). Writes are negligible.
  • Reads: 100 million searches per day, 1,200 per second on average, 5,000 at peak. The ratio is the reverse of the driver case: read-heavy, almost no writes.
  • Query: "restaurants within 3 km, open now, rating at least 4, sorted by relevance or distance, 20 per page".

16.2 Design

  • Index choice. Since the data barely changes, a quadtree becomes attractive: it adapts to density (Manhattan splits deeply, Nevada stays one leaf) and can be built once and held in memory. Rebuilding is cheap and happens offline. Alternatively store each place with its cell id (S2 or geohash prefix) in a search engine or relational table with an index on (cell_id), and combine the cell lookup with filters; this is simpler operationally and is how most production systems do it, with Elasticsearch-style geo support (Chapter 22, Chapter 58). I would pick the search engine for its ability to combine geo, text ("pizza"), category and "open now" filters in one query, and add a quadtree only for a custom in-memory service.
  • Sharding. Shard by geography (cell prefix), so a query reads one or two shards, and replicate shards for read capacity. A dense city shard can be split by finer prefix, the same hot-cell idea, but done offline on a schedule, not live. With 200 GB the full index fits on a handful of machines; shards exist for query throughput, not size.
  • Caching. Because places do not move and many users search the same downtown, results cache well: key = (cell id, category, filter hash, sort), TTL of minutes. Snap the rider's location to a cell centre before building the key, accepting that results are "near this cell" (Chapter 13). Hit rates in busy areas are high.
  • Expanding the radius. Start with a ring of cells; if fewer than 20 results after filtering, widen. Sparse areas (rural) may require a larger radius, so it is useful to store a density hint per cell.
  • Ranking. Mix distance, rating, number of reviews, popularity and personalisation. Exact distance is computed only for the candidates that survive the filters.
  • Freshness. A place edit lands in the database, a change-data-capture stream updates the index within seconds to minutes, and "open now" is evaluated at query time from stored hours and the place's timezone.

18. Security, abuse, monitoring and cost

18.1 Security and privacy

  • Authenticate every socket and request (Chapter 55); take the driver id from the token, never from the message. Rate-limit per user (Chapter 16) so a rooted phone cannot flood updates.
  • Do not expose exact driver ids or exact positions of idle drivers on the public map. Show jittered or snapped positions and masked ids. Reveal the driver's identity and exact position only to the rider with an active trip.
  • Location is sensitive personal data: encrypt in transit and at rest, limit retention (for example trip points kept long, idle points kept days), restrict internal access and audit it (Chapter 56).
  • Abuse: GPS spoofing to fake surge or claim phantom availability, fake requests to reduce competitors' supply, and drivers going online far from the area to farm surge. Detect with speed and plausibility checks, device attestation, and model-based fraud scoring on the history stream.

18.2 Monitoring and SLOs

Follow Chapter 54. Useful service level indicators for this system:

  • Update-to-visible lag: time from the driver's timestamp to the record being readable. Target p99 under 2 seconds.
  • Nearby query latency p99 under 100 ms; dispatch first-offer latency p99 under 1 s.
  • Match rate: fraction of requests that reach ACCEPTED within 2 minutes, per city. This is the business-level SLO.
  • Correctness counters that must be zero: double assignments, trips with two drivers, drivers with two active trips. Alert immediately on any non-zero value, and run a reconciliation job that scans for violations.
  • Offer acceptance rate, timeout rate and number of reassignments per trip (rising numbers point to bad ranking or a stale index).
  • Gateway connection count and reconnect rate; Redis shard CPU and per-cell skew.

18.3 Cost

The live index is small (hundreds of megabytes), so its cost is CPU and network, not memory: maybe 16 to 32 modest Redis nodes in total. The gateways dominate fleet size (1.5 million sockets), and cross-AZ and cross-region data transfer is a visible bill, which is another reason not to replicate the live index across regions. Location history storage is the largest by bytes (about 30 to 50 TB per year compressed at the rates above), handled with tiered storage and downsampling after a retention window. Mapping and routing APIs (if bought) are charged per call, so batching ETA calls and caching per cell matters.

19. Evolution, phasing and alternatives not chosen

19.1 What I would build first

  1. Phase 1 (one city): one Redis, one trips database, sequential offers, WebSocket gateway, straight-line ranking, polling fallback. Prove the state machine and the conditional-write claim.
  2. Phase 2: real ETA ranking, surge map, event log and history store, replicas for the map, push notifications.
  3. Phase 3: sharded index with a directory, hot-cell splitting, multiple regions with failover.
  4. Phase 4: batched global matching, pooled rides, predictive positioning of drivers, machine-learned ETA.

19.2 At 10 times the scale

  • 2.5 million updates per second. Send fewer: adaptive update rates (fast when moving near requests, slow when parked), and client-side dead reckoning that sends a fix only when the position deviates from the predicted path by a threshold. This can cut volume by half or more.
  • Split Redis by region of the world, more shards, and move the cell index from Redis hashes to a purpose-built in-process store (per-shard memory arrays, custom replication) if per-operation overhead matters.
  • Move from per-request greedy matching to batched optimisation with a regional solver.
  • Edge gateways closer to drivers so the TLS and keep-alive cost is local.

19.3 Alternatives not chosen

  • PostGIS or a relational geo index for live positions: excellent for static data and rich queries, but 250,000 updates per second would crush it; fine for the POI variant.
  • A quadtree for live drivers: adapts to density but suffers under constant movement and is harder to shard and replicate.
  • Polling instead of WebSocket: simpler infrastructure; costs battery, latency and requests. Acceptable only for a first prototype.
  • Peer-to-peer or driver-side search: pushing nearby requests to drivers to self-select (broadcast) is simpler but loses control over ranking and fairness.
  • Distributed lock for assignment: workable with fencing tokens but adds a component the conditional write already makes unnecessary.

20. Interview Q&A

Why not store driver locations in a relational database with a lat/lon index?

A B-tree index sorts on one dimension, so "within 2 km" degenerates into a scan of a band of latitudes, which is a large share of the table. Spatial indexes (R-tree in PostGIS) do work, but the real problem here is write rate: 250,000 updates per second that each rewrite an index entry and are obsolete four seconds later. Disk-based transactions and durability are paid for with no benefit. An in-memory store keyed by cell id turns each update into a few constant-time operations and each query into a handful of key reads. A relational spatial index is fine for the static place variant, where writes are rare.

How do you choose the cell size?

Cell size balances two costs. Smaller cells hold fewer irrelevant drivers per read and give a tighter search, but a query covers more cells, and more driver updates cross cell boundaries, each causing two writes instead of one. A good rule is to choose a cell about as wide as the typical search radius divided by 2 or 3, so that the home cell plus its ring covers the radius. For a 2 km radius that is cells about 1 km wide (H3 resolution 8, geohash length 6 or 7). Dense areas can use a finer level through the directory, and sparse areas a coarser one. The decision is also checkable with numbers: 1 million drivers over 1,500 active cities' cells gives tens of drivers per cell on average, which is comfortable to read in one call.

Two riders request at the same instant and the same driver is nearest to both. What happens?

Both dispatch flows read the index and both rank the driver first. Both try to offer; the first conditional update that sets the driver from AVAILABLE to OFFERED for its trip succeeds, and the other affects zero rows. The loser's dispatch sees the failure and moves to its second candidate, with no human involved. If instead both offers were somehow sent (broadcast mode), the accept step is the second guard: only one accept changes the driver to BUSY and the trip to ACCEPTED, and the other driver or rider gets a "no longer available" result. The database row, not the cached index, decides, so the answer is the same under retries, crashes and clock skew.

How do you detect that a driver went offline without telling you?

Every driver record has a time-to-live of about 15 seconds that each update refreshes, and each cell entry carries the last update timestamp. If the phone dies, the app is killed or the car enters a tunnel, updates stop and the record expires by itself. Queries also ignore entries older than about 10 seconds, so a driver disappears from searches before the physical expiry. For drivers who are on a trip, a missing heartbeat for more than a threshold (say 60 seconds) triggers an alert to the rider and a support workflow, but not an automatic cancel, because tunnels are normal. The TTL approach avoids a cleanup job and fails safe: stale means invisible.

Why use ETA instead of distance for ranking, and how do you keep it cheap?

Straight-line distance ignores rivers, one-way streets, closed roads, traffic and turn restrictions, so the nearest driver by distance is often not the quickest. ETA is what the rider experiences and what drives cancellations. Computing a road route for every driver in range would be expensive, so I pre-filter by straight-line distance to about 10 candidates and call the routing service in one batch for just those. A road graph with precomputed shortcuts answers each query in about a millisecond, so the whole step costs a few milliseconds. If the routing service fails, a circuit breaker falls back to a distance-based estimate times a city-specific factor, which is slightly worse but available.

How would you avoid the thundering herd when a stadium empties?

Several layers help. The nearby map reads from replicas and a per-cell cache, so thousands of riders opening the app do not hit the primary. Dispatch coalesces requests per cell into batches and reads each hot cell once per batch rather than once per request. The hot parent cell is split into finer children over several shards so no single core serves all the reads, and each query caps the number of candidates it reads. At the product level, surge pricing and pickup zones spread demand over time and space. Finally admission control sheds or delays excess requests with a clear "high demand" message rather than letting dispatch collapse, which keeps latency for the accepted requests healthy.

What consistency do you need for the location data versus the trip data?

They are opposite ends of the spectrum. Location data is eventually consistent, last-write-wins by sequence number, and may be a few seconds stale or occasionally lost; losing one point costs nothing because the next arrives soon. Trip and assignment data need strong consistency per record: a conditional write on a single row, durable replication before acknowledging, and monotonic versions so clients can order messages. This is the CAP and PACELC tradeoff made per data type (Chapter 28): availability and speed for positions, correctness for assignments. Mixing them, for example making location writes synchronously durable, would waste a lot of capacity, and the reverse would risk double assignment.

How does the system behave if a whole region goes down?

Users of that region's cities fail over to the paired region through DNS or the global edge. The trips database has a replica there, so open trips and assignment rows are available with a small possible loss of the most recent asynchronous writes, which is reconciled using trip versions and driver reports (a driver's app knows its own trip state and re-asserts it on reconnect). The live index needs no copy: within one or two update intervals every online driver has re-published its position into the new region's index. Gateways accept the reconnect storm using jittered backoff and admission control. In-progress trips continue because the apps hold state, and payment and history sync later from the event logs. The recovery objective is therefore minutes for dispatch and near zero for in-flight trips on the devices.

How would the design change for a Yelp-style place search?

The workload flips: writes almost vanish (about 1 per second) and the dataset is larger (200 GB) but static, so the index can be a search engine or a quadtree rebuilt offline, sharded by geography, replicated for reads, and fronted by a cache keyed by cell and filters. We drop the TTLs, the sequence checks and the hot-path memory store, and add text relevance, category filters, open-now logic and ranking by rating and popularity. Freshness requirements relax from seconds to minutes, so change-data-capture indexing is enough. The same ideas remain: convert the point to a cell, read the cell and its neighbours, filter by exact distance, expand rings when results are sparse.

How do you test and verify the "never two trips" rule in production?

Unit and integration tests cover concurrency by running many parallel claims against one driver row and asserting exactly one success; fault injection tests kill workers between offer and claim and pause them past expiry to check that fenced updates reject the stale worker. In production a continuous reconciliation job scans for drivers with more than one active trip or trips with more than one driver, and alerts on any non-zero count; the rate must be exactly zero. A small shadow percentage of traffic can also replay the state machine against the event log to find illegal transitions. Together these turn the invariant into an observable, alertable metric.

21. Recap and connections

Recap

  • Three data shapes drive three stores: a tiny, hot, overwrite-heavy live index in memory (200 MB, 250,000 writes per second), durable strongly consistent trips and assignments, and a huge cold location history in a log and columnar storage.
  • Index space by converting each point to a cell id (geohash, S2 or H3), read the home cell plus neighbours, filter by exact distance, expand rings if sparse. Quadtrees suit static data; fixed grids suit moving data.
  • Shard the live index by a coarse parent cell with a directory so queries touch one or two shards, split hot cells into finer children, serve the map from replicas and caches.
  • Drivers disappear automatically through TTLs; the index is a hint, never the authority.
  • Dispatch ranks by ETA, offers sequentially with timeouts that survive crashes, and reassigns on decline, timeout or cancel; batched matching is the scale-up step.
  • One driver, one trip is enforced by a conditional write on a durable assignment row with versions or fencing, not by a lock or the cache; every call is idempotent.
  • The trip is an explicit state machine with versioned, conditional transitions and outbox events; realtime delivery uses WebSockets with a presence table, version sync on reconnect and push as backup.
  • Surge is derived stream data computed per cell and smoothed; quotes lock the price.
  • A trip is local, so each city has a home region; the live index is not replicated across regions, only trip state is.
  • The static POI variant is read-heavy: search engine or quadtree, geographic shards, cell-keyed caches, CDC indexing.
