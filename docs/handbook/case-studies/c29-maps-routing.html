Case study 29 · Worked solutions

Design Maps and Routing

A maps product answers four questions at planet scale: what does the map look like here, where is this address, what is the fastest way from A to B, and how long will it take right now. This worked solution designs each answer in turn: tiles served from a CDN, a geocoder built on a search index, a partitioned road graph searched with Dijkstra, A* and contraction hierarchies, a live traffic pipeline that reweights the graph every minute, and an ETA service that turns routes into trustworthy minutes.

How to approach this problem (read this first)

What the interviewer is really testing. "Design Google Maps" is deliberately too big, so the first test is whether you can cut it into pieces. After that there are three hard parts. One is knowing that the world's road graph is small enough to sit in one machine's memory, yet a plain shortest-path search over it is still far too slow, so you must precompute. Another is keeping routing fast while traffic changes every minute, which clashes with that precomputation. The last is serving the map picture itself through a CDN so cheaply that it barely touches your servers. A candidate who can say "tiles are a caching problem, search is an index problem, routing is a precomputation problem, traffic is a streaming problem" has already shown the structure the interviewer wants.

The thinking order, step by step

  1. Split the product into subsystems and ask what is in scope. Say: "Maps is really four systems: drawing the map, finding places, routing, and live traffic. Which of these do you want in depth?" This comes first because without it you will wander. Ask about travel modes (driving only is fine), offline maps, and how fresh traffic must be.
  2. Pin down scale and latency targets. Say: "I will assume 500 million daily users, tiles feeling instant, and a route in well under a second." These two numbers decide almost everything later, so you fix them before drawing anything.
  3. Estimate the tile traffic first. Say: "Forty tiles per session, two sessions a day, gives about 1.4 million tile requests per second at peak, so this has to be a CDN." Do tiles first because they are the biggest number by far, and the number alone tells you the architecture: cache at the edge.
  4. Then estimate the road graph size. Say: "About 200 million edges at 16 bytes each is a few gigabytes, so the whole graph fits in one server's RAM." This is the surprising number and it changes the sharding talk: you partition for speed and blast radius, not capacity.
  5. Draft the APIs. Start with the tile URL, because its shape (style version, zoom, x, y) is what makes caching work. Then the route request and response. Say: "The tile URL must fully determine the bytes, so the CDN can cache it forever."
  6. Start with the naive design and break it. Say: "One server, Dijkstra from origin to destination. Across a country it settles tens of millions of nodes, so seconds per query. That is the first bottleneck." Then evolve: bidirectional search, A*, and finally contraction hierarchies with preprocessing.
  7. Add traffic on top. Say: "Preprocessing bakes in weights, so live speeds break it. I need a split where the structure is fixed and only the weights are recomputed each minute." That leads to customizable hierarchies or an overlay graph.
  8. Deep dive on one or two parts. Pick routing and traffic and ETA unless the interviewer steers you to tiles or search. Compare options in a table and pick one.
  9. Finish with failure, degradation and scale. Say: "If traffic is stale, fall back to typical speeds; if the CDN is down, the phone has cached tiles." Close with what changes at 10 times scale.

The decision points

  • Raster or vector tiles? Ask: do users need dark mode, languages and smooth zoom? Yes, so vector for the base map, raster only for satellite photos.
  • Pre-generate tiles or render on demand? Ask: how many tiles will anyone ever request? Low zooms are all requested, so pre-build them; very deep zooms are mostly empty, so render on demand and cache.
  • Which shortest-path algorithm? Ask: how many queries per second and how many milliseconds each? 20,000 per second at a few milliseconds each rules out plain Dijkstra and points to a hierarchy.
  • How do live speeds enter the precomputed graph? Ask: how often do weights change and how fast must they apply? Every minute and globally, so separate structure from weights.
  • Shard the graph or not? Ask: does it fit in memory? It does, so the reasons to partition are build time, locality and failure isolation, not capacity.

Common mistakes on this problem

  • Trying to design all of Maps at once. Fix: name the four subsystems in the first two minutes and ask which to go deep on.
  • Running Dijkstra and calling it done. Fix: state its cost on a continental graph and move to precomputation.
  • Minimizing distance instead of time. Fix: say that edge weights are travel times and the shortest distance is rarely the fastest.
  • Sharding the graph because it is "big". Fix: do the memory arithmetic and give the real reasons to partition.
  • Ignoring how traffic interacts with preprocessing. Fix: explain that shortcut weights depend on edge weights and name the split between structure and metric.
  • Forgetting that tiles need versioned URLs. Fix: put the style and data version in the URL so a release never needs mass invalidation.
Interview tip Do the two estimates early and say what each one decides: 1.4 million tile requests per second means CDN, and a graph of a few gigabytes means one machine can hold it. Everything after that is you responding to those two numbers, which shows the interviewer your design is driven by arithmetic and not by memorized diagrams.

1. Problem statement and clarifying questions

The prompt "Design Google Maps" is enormous, so the first job is to carve out a problem that fits in 45 minutes, following the framework in Chapter 1. The honest observation is that maps is really four loosely coupled systems that share one geographic base layer: a rendering system (draw the map), a search system (turn text into coordinates and back), a routing system (find paths on a graph), and a traffic system (measure how fast roads are right now). Each has different data, different traffic and a different bottleneck, so I would say that out loud and ask the questions below.

Question I askAssumed answer

Reverse geocoding (coordinates to address) is included because it is cheap once forward geocoding exists.

2. Requirements and scope

2.1 Functional requirements

  • Render a map at any zoom level for any viewport, with smooth pan and zoom, in light and dark styles and in the user's language.
  • Search: free-text query to ranked places and addresses, with autocomplete while typing; reverse geocode a coordinate.
  • Route: given origin, destination, optional waypoints and mode, return the best route plus a few alternatives, with turn-by-turn steps and a polyline.
  • Traffic: color roads by current speed; apply current and predicted conditions to route choice and ETA.
  • ETA: estimate the travel time of a route now or for a future departure; keep it updated during navigation and offer rerouting.

2.2 Non-functional requirements

  • Read-heavy and cacheable: map tiles are identical for everyone at a given zoom, location and style version, so they should be served almost entirely from CDN edge caches (Chapter 12).
  • Low-latency routing: a continental route must not need a graph search that touches tens of millions of nodes per query. This forces precomputation.
  • Freshness differs by layer: tiles may be minutes to days old; traffic must be about a minute old; road closures must propagate within minutes; base map edits within hours.
  • Availability over consistency: a slightly stale map or traffic value is far better than an error (Chapter 28). The only strong consistency need is that a single route computation sees one consistent graph version.
  • Graceful degradation: if live traffic breaks, routing falls back to historical typical speeds; if routing is slow, show a straight-line estimate.
  • Privacy: location probes are anonymized and aggregated (Chapter 56).

2.3 Out of scope

Transit timetables, street-level imagery, indoor maps, ads and business listings, reviews, fleet optimization (many stops, vehicle routing problem), turn-by-turn voice, and the cartographic compilation pipeline. Where they would attach I will say so.

3. Estimation

The method is from Chapter 2. The numbers are round on purpose; what matters is which resource each subsystem is bound by.

3.1 Tile traffic

  • 500 million daily users, each with about 2 map sessions per day and about 40 tiles fetched per session (an initial viewport shows roughly 12 to 20 tiles, then panning and zooming adds more; phones cache some). That is 500,000,000 x 2 x 40 = 40 billion tiles per day.
  • 40,000,000,000 / 86,400 is about 460,000 tiles per second on average. Using a peak of 3 times gives about 1.4 million tile requests per second worldwide.
  • At a 98 percent CDN hit rate, origin sees 2 percent of that, about 28,000 requests per second at peak. Each percentage point of hit rate is worth about 14,000 origin requests per second, which is why tile caching is the first-class design problem.
  • Average vector tile: about 20 KB on the wire after compression. Edge egress at peak: 1,400,000 x 20 KB = 28 GB/s, about 224 Gbit/s, spread over hundreds of edge locations. Large but ordinary for a CDN.

3.2 Tile storage

  • A tile pyramid has 4^z tiles at zoom z (each zoom doubles both axes). At zoom 14 that is 4^14 = 268,435,456 tiles. Much of the world is ocean, desert or ice with nearly empty tiles; assume 30 percent are non-empty: about 80 million tiles.
  • At about 15 KB average stored size, zoom 14 is about 1.2 TB. Lower zooms add a geometric series (1/4 + 1/16 + ...), so all zooms up to 14 total about 4/3 of that, about 1.6 TB. Trivial storage, so we precompute everything up to a middle zoom and generate the deepest zooms on demand.
  • The full tile set must be rebuilt whenever style or base data changes, which is a large batch job, not a storage problem.

3.3 Search and geocoding

  • Assume 50 million searches per day that end in a selection, and autocomplete sends one request per keystroke after the second character, about 5 requests per search: 250 million autocomplete requests per day, about 2,900 per second average and 9,000 per second at peak.
  • Index size: roughly 200 million addresses, places and administrative areas at about 200 bytes each (names in several languages, centroid, type, popularity) is about 40 GB, plus the inverted index overhead, so low hundreds of GB. A search cluster of a few dozen nodes handles it.

3.4 Routing

  • Say 10 percent of daily users request a route: 50 million routes per day, about 580 per second on average, about 1,700 per second at peak. Add ETA calls from other products (ride sharing, delivery, place details showing "12 min away"), which are far more frequent, perhaps 10 times: a combined budget of about 20,000 route or ETA queries per second at peak.
  • Road graph: assume about 200 million directed road segments (edges) and about 150 million intersections (nodes) worldwide after dropping paths irrelevant to cars. This is an assumption; real graphs depend on how fine the data is (a country such as the US alone has on the order of tens of millions of nodes).
  • Graph memory: in compact adjacency-array form an edge costs roughly 16 bytes (target node, travel time, flags), so 200 million edges is about 3.2 GB; contraction shortcuts (section 8) typically add about as many edges again, so the routing graph is about 8 to 10 GB with metadata. The whole world's road graph fits in the RAM of one ordinary server. That fact shapes the partitioning discussion: we partition mostly for preprocessing speed, regional isolation and cache locality, not because the graph cannot fit.
  • CPU: a contraction-hierarchy query takes on the order of a millisecond or less on a continental graph; with live traffic weights it is a few milliseconds. 20,000 queries per second times 5 ms is 100 core-seconds per second, so about 100 busy cores, or perhaps 300 cores with headroom. Compare plain Dijkstra at roughly seconds per cross-country query: it would need tens of thousands of cores.

3.5 Traffic probes

  • Peak concurrent devices sending location probes (navigation users, plus opted-in background users): 10 million. One fix every 5 seconds is 2 million probes per second at peak. Average maybe 1 million per second.
  • Probe size about 60 bytes (anonymous id rotated per trip, lat, lon, speed, heading, timestamp, accuracy). Peak ingest: 2,000,000 x 60 B = 120 MB/s. Per day at 1 million per second average: 86 billion points, about 5 TB per day raw.
  • Speed table: 200 million segments x 8 bytes (current speed, confidence, version) is 1.6 GB per snapshot, small enough to broadcast to every routing node every minute.
  • Historical profiles: per segment, a typical speed for every 15-minute slot of the week (672 slots) at 1 byte each is 200,000,000 x 672 = about 134 GB. Large but regional, readable, and sharded with the graph.
Key idea Four subsystems, four bottlenecks. Tiles are bounded by egress and cache hit rate, so the CDN does the work. Geocoding is bounded by index search latency, so a search engine does it. Routing is bounded by CPU per query, so we spend hours of preprocessing to save milliseconds per query. Traffic is bounded by ingest and aggregation, so it is a streaming pipeline. The road graph itself is small enough for one machine's memory.

4. API design

All requests are HTTPS (Chapter 5); tiles and route responses use compact binary or protobuf encoding where it pays (Chapter 7). Tiles must be plain cacheable GETs so the CDN can do its job.

    Cache-Control: public, max-age=86400, stale-while-revalidate=604800
    ETag: "h3f9a..."                              (content hash)

GET /v1/geocode?q=1600+amphitheatre+pkwy&bias=37.4,-122.1&lang=en&limit=5
    -> { results: [ { place_id, name, address, lat, lon, bbox, type, score } ] }

POST /v1/route
    { origin: {lat,lon,heading?}, destination: {...}, waypoints: [...],
      mode: "drive", depart_at: "now" | ISO-time,
      avoid: ["tolls"], alternatives: 2 }
    -> { routes: [ { id, distance_m, duration_s, duration_in_traffic_s,
                     polyline (encoded), steps: [ ... ], graph_version } ] }

POST /v1/eta-matrix     { origins: [...], destinations: [...], mode, depart_at }
    -> n x m table of { duration_s, distance_m }

POST /v1/navigation/{route_id}/reroute   { current_position, heading }
POST /v1/probes         [ { ts, lat, lon, speed, heading, acc } ... ]   (batched uploads)

Design notes. Tile URLs contain the style version, so changing a style never needs invalidation, it needs a new URL (the cache-busting-by-name idea from Chapter 12). The session token on autocomplete groups keystrokes of one search for billing, caching and relevance feedback. The route response includes graph_version so that a support engineer can reproduce what the router saw. The probe endpoint accepts batches: phones buffer points and upload every 10 to 30 seconds to save radio power, so the server does not see strictly one point per request.

5. Data model and storage choices

5.1 Base map: features and tiles

Source of truth is a versioned collection of features: roads, buildings, water, land use, places, boundaries, each with geometry, attributes and a stable id. It lives in a spatially indexed database (PostGIS-like, or a custom store) for editing and in immutable snapshot files for batch pipelines. Published output is the tile set: for each style version and tile coordinate, one binary blob, stored in object storage (Chapter 21) keyed by style_ver/z/x/y. Object storage fits perfectly: 1.6 TB, write once, read by key, enormous parallel read throughput, and the CDN pulls from it as the origin shield.

5.2 Place and address index

Geocoding documents live in a search engine (Chapter 22): one document per place or address range with names, normalized tokens, hierarchy (street, city, region, country), centroid, bounding box, category and a popularity prior. The search engine is a derived index, rebuilt from the feature store, so it can be sharded freely by geography and reindexed without risk.

5.3 Road graph and routing data

The routing graph is a compiled, read-only artifact, not a table. Nodes and edges are stored in flat arrays in compressed sparse row (CSR) form: a node array holds the offset of its first outgoing edge; an edge array holds target node, base length, speed class, and flags (one-way, toll, ferry). Turn restrictions and turn costs are stored separately. The artifact is versioned (graph_v2026_11_17_03), built offline, copied to routing servers and memory-mapped. Treating the graph as an immutable snapshot makes consistency trivial: a query pins one version for its whole lifetime.

5.4 Traffic data

  • Live speed table: segment id to current speed, held in memory on every routing node, refreshed about every minute from a message stream. Also kept in a key-value store for the tile service that draws traffic colors.
  • Historical profile store: per-segment typical speed by time-of-week slot, in a wide-column or columnar store (Chapter 20), sharded by geographic region (Chapter 25).
  • Raw probe archive: append-only files in object storage, partitioned by day and region, used for model training and replay.

6. A first simple design, then the scaled architecture

6.1 The single-box version

One server holds a city's data. A request for a tile runs a spatial query against a database, renders an image, and returns it. A route request loads the city graph into memory and runs Dijkstra from origin to destination. Geocoding is a text search over a table of addresses. Traffic does not exist; every road has its speed limit as its speed. This works for a small city and a few users, and it is exactly where each problem begins: rendering on demand is too slow and CPU heavy for millions of viewers, whole-planet Dijkstra takes seconds, text search over a table cannot do fuzzy prefix matching, and free-flow speeds make ETAs wrong at rush hour.

6.2 The scaled architecture

Each pain point yields one component: pre-rendering plus CDN for tiles, a search cluster for geocoding, a preprocessed, partitioned graph with a routing service for directions, a streaming pipeline that turns phone probes into segment speeds, and an ETA service that combines routes with traffic and learned corrections.

Solid arrows are requests, green arrows are the traffic data path, dashed arrows are the offline build path. 1. Phones send tile requests to the CDN edge, which pulls misses from the tile service, which reads the tile store. 2. Everything else goes through the API gateway to the search, routing or ETA service. 3. Search reads the place index; routing reads the in-memory graph and speeds; ETA asks routing and reads typical speeds. 4. Probes enter probe ingest, pass the traffic pipeline, and refresh the graph and speeds box. 5. The map build pipeline reads the feature store and publishes tiles, the place index and the graph. The design choice is to keep serving paths read-only and push all heavy work into the dashed side. On a whiteboard, draw the CDN first and the green path last. Remove the traffic pipeline and routing still works but ETAs fall back to typical speeds.

7. Deep dive 1: map tiles and the CDN

7.1 Why tiles

The world map is far too large to send, and most of it is irrelevant to any viewer. The standard answer is the tile pyramid. The world in the common Web Mercator projection is cut into a square. At zoom 0 the whole world is one tile. At zoom 1 it is 2 x 2 tiles, at zoom 2 it is 4 x 4, and at zoom z it is 2^z by 2^z tiles. A tile is addressed by three integers (z, x, y). The client computes which tiles cover its viewport (a phone screen typically needs a handful to about 20) and fetches each by URL. Because the URL fully determines the content, every user looking at the same place at the same zoom requests the same bytes, which is what makes the CDN effective.

Walkthrough. Read the diagram left to right as zoom increases. 1. Zoom 0 is one tile named 0/0/0 that covers the planet. 2. At zoom 1 it splits into four tiles, labeled by column and row. 3. At zoom 2 each of those splits again, giving 16. The green highlighted tile at zoom 1 and its four green children at zoom 2 show the parent and child rule: children of (z, x, y) are (z+1, 2x, 2y) and its three neighbours. The text lower down says which tiles stay in cache: low zooms everywhere, city centres mostly, rural deep zooms rarely. The design choice shown is a fixed grid of named objects, instead of cutting a custom picture for each viewport, which would make every response unique and uncacheable. When drawing it, sketch the three grids and mark one tile and its children. Without the fixed naming there is nothing for a CDN to key on.

7.2 Raster versus vector tiles

A raster tile is a finished image (PNG or JPEG, typically 256 or 512 pixels square). It is simple for any client but large, cannot be restyled, looks blurry between zoom levels and must be rebuilt for each style and each language. A vector tile contains geometry and attributes (road lines with class and name, building polygons, place points) encoded compactly, for example in the Mapbox Vector Tile protobuf format with coordinates quantized to a local grid. The client draws it with a GPU renderer using a style sheet. Vector tiles are typically several times smaller, scale smoothly between zoom levels (the app interpolates), rotate and tilt for 3D views, and let one tile serve many styles and languages because labels are drawn on the device. The cost is client complexity and on-device rendering work. Most modern mobile mapping uses vector tiles for the base map and keeps raster for satellite imagery (photographs are inherently raster).

7.3 Producing tiles: pre-generate versus on demand

There are two options. Pre-generate everything in a batch job (a map-reduce style pipeline from the feature snapshot, see Chapter 37) and store the results in object storage. Serving is then a pure read, latency is minimal, and the origin has no CPU-heavy work. The price is time and storage for rarely used tiles: zoom 17 and above is 4^17 = 17 billion tiles, mostly empty or unvisited. Generate on demand renders a tile when first requested and caches it. This saves storage and makes updates cheap, but the first viewer of each tile waits on rendering and a surge of cold requests can overload the renderers.

The chosen hybrid: pre-generate zoom 0 through about 14 (1.6 TB, as estimated), where every tile is likely to be requested and where one tile covers a lot of map; generate zoom 15 and beyond on demand from the feature store behind the origin shield, cache them in the CDN, and let the client over-zoom a parent tile (draw the zoom-14 data larger) while the deeper tile loads. Request coalescing at the origin shield (many simultaneous requests for one missing tile cause exactly one render, the others wait) is essential; it is the same protection against stampedes covered in Chapter 14.

7.4 Caching layers and freshness

A tile request meets several caches. The phone caches on disk (days). The CDN edge caches next (hours to days). A regional shield cache behind it collapses misses from hundreds of edge sites into few origin requests. Only then does the tile service fetch the object from storage or render it. Freshness uses the versioned-URL idea: base data changes with a monthly or weekly data_ver, styles with style_ver, and both appear in the URL or are bound into an ETag, so a new version is simply a new set of cache keys that fill over time. For urgent corrections (a wrongly mapped bridge closure) we need a targeted purge by tile coordinate, which the CDN supports; the build pipeline computes which tiles a feature touches (every zoom, the tile containing its bounding box) and purges just those.

Walkthrough. This is a sequence diagram with four lifelines: the phone, the CDN edge, the shield and the tile service with its store. 1. The phone sends a GET for one tile URL. 2. Interview tip Say the hit-rate arithmetic: at 1.4 million tiles per second peak, 98 percent hit means 28,000 origin requests per second, while 90 percent would mean 140,000. The justification for the shield layer and for long cache lifetimes is that every percentage point matters.

8. Deep dive 2: geocoding and search

8.1 What geocoding really is

Forward geocoding turns text such as "221b baker st london" into coordinates. Reverse geocoding turns coordinates into a nearby address or place. Autocomplete is forward geocoding on a prefix, under a 100 ms budget, with the user still typing. This is a text search problem with a geographic twist, so it belongs on a search engine (Chapter 22) with an inverted index, not on a relational table.

8.2 The pipeline

  1. Normalize. Lowercase, strip accents where appropriate, expand abbreviations ("st" to "street" or "saint", ambiguous, so keep both), transliterate scripts, and detect language.
  2. Parse. Tag tokens as house number, street, locality, region, postcode, country, or business name. A statistical or rule-based parser handles "pizza near me", "10 downing", or "94043".
  3. Retrieve candidates. Query the index: prefix and edge n-gram matching for the last token being typed, fuzzy matching for misspellings, exact matching for earlier tokens, and a filter or boost for the user's location and map viewport.
  4. Rank. Combine text match quality, place importance (a city outranks a street of the same name), distance to the user or viewport, and popularity learned from past selections.
  5. Resolve address ranges. Many street numbers are not individual records; the data stores a street segment with a number range, and the answer is interpolated along the segment geometry. Rooftop-precise points are used where available.

8.3 Hierarchy and sharding

Addresses form a hierarchy: country, region, city, street, number. A common technique indexes each place with its full ancestry so that "springfield" can be disambiguated by a second token ("springfield il"), and so that results can be grouped. For sharding (Chapter 25), partition the index by country or large region for locality: most queries concern the user's own region, so the primary shard is queried with a high boost and others only if too few good results exist. The alternative, hashing documents randomly across all shards, forces every query to touch every shard, so tail latency grows with shard count. Geographic sharding does create hot shards (a big country gets more traffic), which is fixed by splitting dense countries into multiple shards and adding replicas.

8.4 Reverse geocoding

Given a point, find the containing administrative polygons and the nearest address points or street. This is a spatial index query, using a grid or an R-tree, or the cell-based indexes in Chapter 58 (geohash, S2, H3-style cells). Precompute: store, per cell at a fixed level, the list of candidate features, then confirm with exact geometry tests. Results cache well because popular coordinates are rounded to a grid of about 10 meters for the cache key.

Walkthrough. Boxes are processing stages, green boxes are index shards, and dashed arrows are the optional fallback path. 1. The raw query, for example "10 dow lon", enters. 2. Normalize lowercases it, handles scripts and expands abbreviations. 3. Parse tags each token as number, street or city. 4. The query goes to shard A, which holds the user's region, with a location boost. 5. Only if shard A returns too few confident matches does the dashed path query shard B, the fallback region. 6. 9. Deep dive 3: the road graph and shortest paths

9.1 Modelling roads as a graph

Intersections are nodes; road segments between them are directed edges (a two-way street is two edges). Each edge has a length and a free-flow speed, so a base travel time in seconds, and the routing objective is the path with minimum total travel time (not distance, which is a common wrong answer; the shortest distance is rarely the fastest). Real routing also needs turn restrictions (no left turn here) and turn costs (a left across traffic takes longer). They are handled either by expanding each node into per-turn pseudo-nodes (an "edge-based" graph) or by storing penalty tables looked up at each relaxation step. Road class, tolls, ferries, and vehicle restrictions are edge flags that the query can filter.

9.2 Option 1: Dijkstra

Dijkstra's algorithm keeps a priority queue of nodes ordered by tentative distance from the origin. It repeatedly removes the closest unsettled node, then relaxes each outgoing edge: if going through this node gives a shorter path to a neighbour, update it. With non-negative weights, the first time a node is removed it has its final distance, so when the destination is removed the search can stop. The search expands in all directions equally, like a ripple, so the number of nodes settled grows with the area of the circle whose radius is the trip length. For a cross-country trip that means tens of millions of nodes; with a binary heap and arrays that is on the order of seconds, far too slow for 1,700 queries per second and an interactive latency budget.

9.3 Option 2: Bidirectional search and A*

Bidirectional Dijkstra runs one search forward from the origin and one backward from the destination (on the reversed graph) and stops when they meet. Two circles of half the radius cover about half the area of one big circle, a speedup of roughly 2 times. A* adds a heuristic: order the queue by distance_so_far + estimated_remaining, where the estimate never overestimates the true remaining cost (it is "admissible"). The straight-line distance divided by the maximum road speed is a safe estimate for travel time. The search then leans toward the destination rather than rippling in all directions. The weakness for road networks is that the estimate is weak: it assumes you can travel in a straight line at highway speed, so A* with this heuristic still explores a large fraction of the area. A better heuristic, ALT (A*, landmarks, triangle inequality), precomputes exact distances to and from a few dozen landmark nodes and uses the triangle inequality to get much tighter lower bounds, giving a speedup of an order of magnitude. This is useful but still far from the millisecond range.

9.4 Option 3: Contraction hierarchies

The key insight: long trips use highways, and highways are few. Humans route this way too (get on the motorway, travel far, get off). Contraction hierarchies (CH), introduced by Geisberger and colleagues in 2008, turn that into an algorithm. Preprocessing assigns every node an importance rank (roughly: how much of the shortest-path structure depends on it, with local streets low and major interchanges high). Nodes are then contracted in order of increasing importance. To contract node v means removing it from the graph, but for each pair of its neighbours (u, w), if the path u to v to w is the only shortest path between u and w (a "witness search" checks for an alternative), add a shortcut edge u to w with weight w(u,v) + w(v,w). After contracting all nodes, the original edges plus all shortcuts form the hierarchy graph.

A query runs a bidirectional Dijkstra in which the forward search from the origin may only follow edges going up in rank, and the backward search from the destination may only follow edges going up in the reversed graph. Both searches climb towards the important nodes, meet at the top of the hierarchy, and the shortest path is the best meeting node. Each search settles only a few hundred to a few thousand nodes, even on continental graphs, so queries take about a millisecond or less. The resulting path contains shortcuts, which are unpacked recursively into the original edges for display and turn instructions.

9.6 Making CH work with live traffic

Plain CH bakes the edge weights into shortcut weights, so a changed speed on one road invalidates every shortcut that passes through it, and full re-preprocessing takes far too long to repeat every minute. Three practical approaches exist.

  • Customizable contraction hierarchies (CCH). Split preprocessing in two phases: a slow metric-independent phase computes the node ordering and the shortcut structure once (stable until the road network itself changes), and a fast customization phase recomputes shortcut weights from current edge weights bottom-up, in seconds on a multicore server for a large region. Queries then use the customized weights. This is the approach that matches "reweight every minute".
  • Time-bucketed hierarchies. Preprocess several CH graphs with typical weights for different periods (weekday morning peak, midday, evening, night). Queries pick the bucket for their departure time. Cheap at query time but ignores today's incident.
  • Hybrid: CH for the static part, local search for live deviations. Run the CH on typical weights to get candidate routes, then re-time the candidates with live speeds, and run a local Dijkstra only near segments with large deviations (an accident). It is simple and robust, and fits the alternatives requirement because each candidate gets re-evaluated.

The design here: a CCH-style customized hierarchy in the routing servers, refreshed from the speed table every minute (or when a closure arrives), with the hybrid trick as the fallback for fast-changing local incidents and for departure-time-dependent routes, plus a straight Dijkstra fallback if the hierarchy is unavailable.

9.7 Partitioning the graph

Even though the planet graph fits in memory (section 3.4), partitioning is worth doing for four reasons: customization and preprocessing parallelize across regions; routing servers can be placed near their users and keep only the regions they serve in RAM (better CPU cache behaviour and fast restarts); an outage or bad data in one region does not affect others; and the memory for time-dependent profiles (about 134 GB, section 3.5) does not fit a single server. The question is how to cut.

  • Geographic grid or administrative cut. Simple, but cuts roads at arbitrary places, producing many border edges, and unbalanced pieces (a city is dense, a desert is empty).
  • Graph partitioning that minimises cut edges. Algorithms such as multilevel schemes (METIS-like), or inertial flow and natural-cut approaches designed for road networks, produce balanced cells with few border nodes. Fewer border nodes means a smaller overlay graph and less cross-partition work.

A query whose origin and destination lie in the same cell is answered within that cell. A query that crosses cells uses a multi-level overlay (the idea behind customizable route planning, CRP): inside the origin and destination cells, search the detailed graph out to the cell's border nodes; between cells, search an overlay graph whose nodes are only border nodes and whose edges are precomputed cell-crossing shortcut distances. Updating a traffic speed only requires recomputing the overlay shortcuts of the one cell it belongs to, which is cheap. CRP and CCH are the two well-known ways to get "fast preprocessing with fast metric updates"; I would name both and pick one rather than pretend they are the same.

9.8 Alternatives, waypoints and map matching

Alternative routes are not the second-best path (which is nearly identical, differing by one lane change). The standard method finds paths that are sufficiently different and not much slower: for example the via-node method evaluates candidate via nodes from the CH search spaces and keeps those whose path shares less than about 60 to 70 percent of edges with the best route and whose length stays within about 25 percent of the best time; another is the plateau method. Multi-waypoint routes chain point-to-point queries. And for navigation the app must continuously map match noisy GPS points to the road (usually a hidden Markov model that scores candidate road projections by distance and by whether consecutive projections form a plausible path), because a raw GPS dot is often 10 or more meters off the road and could be on a parallel street.

10. Deep dive 4: live traffic and ETA

10.1 The traffic pipeline

Phones that opt in send anonymous probes. The pipeline (Chapter 34 and Chapter 37) is a classic stream job.

  1. Ingest. Probe servers authenticate, validate, strip identifiers, drop impossible points, and append to a partitioned log, partitioned by geographic cell so one cell's data stays together.
  2. Map match. Each probe trace is matched to road segments. Matching a single point is unreliable; a short window of consecutive points per anonymous trip id is matched together.
  3. Derive segment observations. From a matched trace, compute the time the device took to traverse each segment (interpolated between points), giving one speed sample per segment per traversal. Discard samples from stopped devices (parked cars, red light waiting is real delay, but a parked car is not) using speed and trip heuristics.
  4. Aggregate. Per segment, per window (a sliding or tumbling one-minute window, using event time with allowed lateness because uploads are batched; see Chapter 27), compute a robust statistic: a median or trimmed mean, with a sample count that sets a confidence. A single sample is noisy; with few samples the output blends toward the typical speed, using something like an exponentially weighted average or Bayesian shrinkage.
  5. Fill gaps. Many segments have no probes in a given minute. Estimate from neighbouring segments (traffic is spatially correlated along a road), from the same road class, and from historical typical speed for this time of week.
  6. Publish. Write the new speed table snapshot, send deltas to routing servers (only segments changed beyond a threshold), and update the tile layer that colors roads.
  7. Incidents. Closures and crashes arrive from authority feeds, user reports and probe anomalies (many devices suddenly stop). They override speeds: a closure sets the edge weight to infinity.

Remove the log and a spike drops probes. Remove incident feeds and closures show up only after drivers get stuck.

10.2 ETA: more than adding up edge times

The naive ETA sums the current edge times along the route. Two things break this. First, traffic changes while you drive: a route that takes 90 minutes will reach its far end 90 minutes from now, so what matters is the speed there then, not now. A correct method is time-dependent evaluation: walk the path, track the clock, and look up each edge's speed for the time you will arrive at it, blending live data (valid for the next 15 to 30 minutes) into the typical profile for later segments. Second, physics and delays that speeds do not capture: traffic lights, stop signs, turns, parking and pickup. These are added as per-turn and per-intersection cost estimates, which can be learned from probe data per intersection and turn type.

A learned model is then stacked on top. The routing engine produces a base ETA and features (distance, road class mix, number of turns and signals, time of day, day of week, weather, live and typical speed along the path, region). A model (gradient-boosted trees are a strong, cheap baseline; graph neural networks over road segments have been published by large map providers for the same purpose) predicts a residual correction or the final time. It is trained offline on historical trips that were actually driven, with the label being real elapsed time. The metric is error distribution, typically the median absolute percentage error and the 90th percentile of error, tracked per region and per trip length. The model is retrained regularly and rolled out gradually, like any ranking model.

10.3 Rerouting during navigation

Once a user is navigating, the phone sends position updates, and the service periodically re-evaluates. Two triggers exist. Deviation: the user left the planned route (a missed turn), so recompute from the current position and heading. Improvement: traffic changed and an alternative now saves a meaningful amount (say more than a few minutes or 10 percent), so propose it. To keep cost bounded, the service does not re-run full routing for each of millions of navigating users every minute: it stores the active route's remaining edge list and checks whether any segment on it had a large speed change, using an index from segment to active routes. Only affected routes are recomputed. Hysteresis (require a larger gain before suggesting a switch than before the last switch) prevents flapping between near-equal routes.

11. Scaling, bottlenecks, hot spots

11.1 Tiles

The bottleneck is hit rate and shield capacity. Techniques: long TTLs with versioned URLs; tiered caches; coalescing; prefetching neighbours on the client; tile bundles at low zoom (small tiles at zoom 0 to 5 shipped inside the app); avoiding unique query parameters in tile URLs. Hot spots are city centres at rush hour and events; the CDN absorbs them since the same tile is requested by everyone. A cold spot problem appears after a base data release, when millions of new keys are all misses at once: warm the cache by pre-pushing the most popular tiles (known from request logs) before flipping the version pointer, and flip regions gradually.

11.2 Search

Replicas per shard scale reads. Hot prefixes (the first two characters of popular queries) are cached. Each autocomplete request is cancelled by the client when a new keystroke arrives, and the client debounces requests by 100 to 150 ms. Popular queries ("airport") are precomputed per region.

11.3 Routing

Routing servers are stateless apart from memory-mapped, read-only graph snapshots, so scaling is horizontal: add servers to a region. Route requests are sticky to a region by origin location (a consistent mapping from tile cell to region pool). Hot spots are metropolitan areas at commute hours; they have their own pools and autoscale (Chapter 43). A result cache helps more than expected: many requests are identical or nearly so (home to work, airport to downtown). Cache key: snapped origin cell, snapped destination cell, mode, a time bucket of a few minutes, and the speed snapshot version; entries live a minute or two. This also protects the service against bursts such as a stadium emptying. For huge origin-destination matrices (delivery, ride matching), use one-to-many hierarchy algorithms (compute the backward search from each target once, and reuse it) rather than n x m independent queries.

11.4 Traffic

Partition by geographic cell; late-arriving data is handled by event-time windows. A hot cell (a major city) is split into finer partitions, and aggregation is two-stage: partial aggregates per partition, then merge per segment. Backpressure and sampling: if ingest exceeds capacity in a region, sample probes uniformly, since aggregates are robust to subsampling. Speed table deltas are small (only segments whose speed changed beyond a threshold), so routing nodes ingest a few hundred thousand updates per minute rather than all 200 million.

12.1 Consistency and idempotency

Routing, search and tiles are read-only from the user's perspective, so retries are safe and no idempotency key is needed for them (Chapter 32). The consistency rule that matters is snapshot isolation of a route computation: one request reads one graph version and one speed snapshot. During a hot swap of snapshots, old and new live side by side until in-flight queries finish (reference counted), then the old one is unmapped. Probe uploads are at-least-once and therefore deduplicated by (anonymous trip id, sequence number) in the aggregation step, or tolerated, because a duplicated sample barely moves a median.

12.2 Multi-region

Maps are naturally regional: a route is within one continent usually, and a user is served by the nearest region (Chapter 26). Each region holds the tile origin copy, the place index for nearby geography, the routing graph for its area plus a coarse overlay for the whole world (so intercontinental routes can be decomposed, with the long ocean leg precomputed), and a live speed table fed by regional probe ingest. Probes stay in the region they originate in (also good for data-residency rules). Cross-region routes are rare and handled by a coordinator that routes to the origin region, finds the border crossings (airports, ferries, land borders) from the overlay, and stitches. Base data releases roll out region by region with canaries.

13. Security, abuse, monitoring, cost

13.1 Security and privacy

  • Location privacy: probes carry no account id, are tagged with a short-lived random id that rotates every trip or every few minutes, and the trip start and end sections are trimmed (so a home address cannot be inferred). Aggregates are published only for segments with enough distinct contributors. See Chapter 56.
  • Abuse: API keys per developer, per-key quotas and rate limits (Chapter 16) on the route, matrix and geocode endpoints, which are expensive; the matrix endpoint is the usual abuse target because one request costs n x m queries. Bulk scrapers of tiles are limited at the edge by key and referrer.
  • Integrity: signed probe batches and device attestation reduce spoofed traffic reports.

13.3 Cost notes

  • CDN egress is the largest line item: 28 GB/s at peak, which is why vector tiles (smaller) and cache-hit rate are optimized relentlessly. Compressing tiles with gzip or brotli typically saves 50 to 70 percent on text-like vector data.
  • Routing compute is modest (hundreds of cores) because preprocessing moved the cost offline; the build cluster is bursty and can use spot or preemptible capacity.
  • Probe storage: 5 TB per day raw is expensive if kept forever; keep raw points days to weeks, keep aggregated segment statistics long term.
  • Index and graph memory are small. Do not shard for capacity; shard for blast radius and locality.

14. Evolution, phasing and alternatives not chosen

14.1 What I would build first

  1. Phase 1: licensed vector tiles on a CDN, a managed search index for places, Dijkstra plus ALT on a single-region graph with speed-limit speeds. ETA from free-flow speeds with a typical-hour multiplier.
  2. Phase 2: contraction hierarchies with the hybrid live re-timing, probe ingest and a basic aggregated speed table, typical-speed profiles, on-demand tiles for deep zoom, shield caching.
  3. Phase 3: customizable hierarchy or overlay-based partitioning, time-dependent routing, learned ETA model, incident feeds, rerouting service.
  4. Phase 4: multi-modal routing, offline regions, personalised ranking, one-to-many and matrix services for platform partners.

14.2 What changes at 10x

  • Tiles: 14 million requests per second at peak. The same architecture holds, with more edge capacity, bundled low zooms in the client, and more aggressive client-side caching and prefetch; the origin must stay near 2 percent of the traffic, which needs the hit rate to improve to 99 percent or better with larger shield caches.
  • Traffic: 20 million probes per second. Sample per segment (cap contributions per device per minute and per segment), move aggregation closer to the edge (regional processing before global merge) and consider on-device pre-aggregation of traversal times.
  • Routing: 200,000 queries per second at 5 ms is 1,000 busy cores, still modest; the pressure moves to customization frequency and to matrix workloads.

14.3 Alternatives not chosen

  • Pre-computing all-pairs shortest paths: 150 million nodes squared is 2 x 10^16 pairs, impossible, and traffic would invalidate it anyway.
  • Only raster tiles: simpler client but 3 to 5 times more egress and a combinatorial cache for styles and languages.
  • Storing the road graph in a graph database or relational table: pointer-chasing search with millions of edge reads per query needs in-memory arrays; a database round trip per node would take minutes.
  • Pure Dijkstra with regional pruning: acceptable for small countries but not at planet scale without hierarchy.
  • Real-time hierarchy rebuild per minute: too slow; hence customizable variants.

15. Interview Q&A

Why not just run Dijkstra on the whole graph? What is the actual number?

Dijkstra settles nodes in order of distance from the origin, so for a long trip it processes nearly every node within the trip radius. On a continental network that is tens of millions of nodes, each popped from a priority queue and relaxed over several edges, which takes on the order of seconds even in optimized code. With a combined budget of about 20,000 route and ETA queries per second, plain Dijkstra would need tens of thousands of cores. Contraction hierarchies cut each query to hundreds or thousands of settled nodes, about a millisecond, at the cost of an offline preprocessing step. That is the central trade: spend hours of offline compute to save milliseconds of online compute on every one of billions of queries.

Explain contraction hierarchies in a minute, and what is the catch with traffic?

Rank all nodes by importance and remove them from least to most important. Whenever removing a node would break a shortest path between two of its neighbours, add a shortcut edge with the combined weight. A query then runs a forward search from the origin and a backward search from the destination, each allowed to follow only edges that go up in rank, and the paths meet near the top, in the highway-like nodes. The catch is that shortcut weights are sums of base edge weights, so when live traffic changes a speed, every shortcut built on that edge is stale. Rebuilding everything every minute is too slow, so we use a customizable variant that separates the structure (ordering and shortcut topology, stable) from the weights (recomputed bottom-up in seconds), and keep a hybrid fallback that re-times candidate routes with live speeds.

How do you partition the road graph, and does the whole graph fit on one machine?

The planet's car graph is roughly 200 million edges, about 3 to 10 GB in compact arrays, so the structure itself fits in one server's memory; I would say so and then explain why we partition anyway. Reasons are parallel preprocessing, regional blast radius, memory for time-of-week profiles (over 100 GB), and locality of reference. We cut with a balanced partitioner that minimizes border nodes, not with arbitrary rectangles, then build an overlay of border-to-border shortcuts so cross-cell queries do detailed search only in the origin and destination cells. When traffic changes inside a cell, only that cell's overlay edges are recomputed. The cost is more complex code and queries that cross cells doing a little extra work.

How do the tiles stay fast for a billion users without melting the origin?

Tiles are static objects whose URL contains zoom, x, y and a version, so every viewer of a place requests the same bytes and the CDN can cache them for a long time. At 1.4 million requests per second peak, a 98 percent hit rate leaves 28,000 per second for origin, and the shield tier plus request coalescing collapses simultaneous misses to a single fetch. We pre-generate tiles up to zoom 14 (about 1.6 TB) and generate deeper tiles on demand, while the phone over-zooms the parent tile in the meantime. New data goes out as a new version, warmed in the popular regions first, so there is never a mass invalidation.

How do you compute an ETA that is accurate for a trip that lasts an hour?

Summing current speeds is wrong, because the far end of the trip will be reached an hour from now, when traffic is different. I evaluate the route time-dependently: walk along the route keeping a clock, use live speeds for the first 15 to 30 minutes, and blend toward the typical speed for that time of week after that. Then I add intersection and turn delay estimates, and finally apply a learned correction model trained on completed trips that predicts the residual from features like road mix, time of day and weather. I judge it by the median and 90th-percentile absolute percentage error per region and trip length, and I log predicted versus actual for every completed navigation to retrain.

What if probe data is sparse on a road, or wrong?

Sparse: estimate with confidence. When a segment has few samples in a window, the output shrinks toward a prior built from neighbouring segments and the historical profile for that time slot, with a confidence value that routing can use (low confidence means rely on typical speeds). Wrong: use robust statistics such as the median, require a minimum number of distinct devices, compare against history to detect outliers, and treat sudden drops with caution unless several independent devices agree. Spoofing a traffic jam to divert others is a real abuse case, so device attestation and per-device rate limits matter. The fallback if the pipeline is unhealthy is always typical speeds, never an error.

How would you handle map data updates, such as a new road or a closed bridge?

Two speeds of update. Urgent changes like closures are applied as overrides: set the affected edges to infinite weight in the speed table, which reaches routing servers in a minute or two, and purge the related tiles by coordinate. Ordinary data changes (a new road) go through the build pipeline: edit the feature store, regenerate affected tiles, update the place index incrementally, and build a new routing graph snapshot on a daily or weekly schedule. The new graph is validated against a golden set of routes and canaried on shadow traffic before the pointer flips, and a snapshot swap keeps old and new in memory until in-flight queries finish. A small patch list lets us fix a known error in the live graph without waiting for the next full build.

How would you support route queries between continents or across many partitions?

Keep a coarse world overlay in every region: border nodes of cells plus precomputed distances between them, including long-distance edges such as ferry and flight-free links only where relevant. A coordinator takes the origin region's detailed search to its borders, the overlay for the middle, and the destination region's detailed search for the end, and stitches them. This is the same technique as inside a continent, with a multi-level overlay hierarchy. In practice cross-region requests are rare enough that I would accept a slightly slower path for them and avoid duplicating full graphs everywhere.

How would you decide between precomputing tiles and rendering on demand?

Look at the tile count, popularity and cost of a miss. Low zooms have few tiles which everyone requests, so precomputing is free benefit. Deep zooms have billions of tiles, most never requested, so on-demand rendering with caching stores only what is actually used. The risk of on-demand is a cold-start stampede after a release, so I coalesce requests at the shield, size the renderer pool for the peak miss rate, and warm known-popular tiles before switching versions. The threshold between the two regimes moves with measurements: choose the zoom where the fraction of tiles ever requested falls below a few percent.

How would the design change to support offline maps?

Offline needs a compact download for a region: vector tiles for zooms up to the detail level, a trimmed place index (names and addresses for search), and a routing graph with typical-speed profiles in a CH-style compact format that runs on a phone. Updates are delivered as diffs against the downloaded version. The phone cannot have live traffic offline, so ETAs use historical profiles by time of week, and the app clearly labels that. Storage per region is a few hundred MB to a couple of GB for a large country, which argues for letting users choose regions and for aggressive compression.

Recap

  • Maps is four systems on one base layer: tiles, search, routing, traffic. Name the bottleneck of each: egress and hit rate, index latency, CPU per query, ingest and aggregation.
  • Tiles are addressed by zoom, x and y, versioned in the URL, served from CDN with a shield tier; precompute up to about zoom 14 (about 1.6 TB), render deeper zooms on demand with request coalescing. Vector tiles beat raster for the base map.
  • Geocoding is a search-engine problem with location bias, hierarchy-aware indexing and geographic sharding; reverse geocoding is a spatial cell lookup.
  • The road graph (about 200 million edges) fits in memory. Dijkstra is too slow (seconds), A* is weak on roads, ALT helps; contraction hierarchies give about millisecond queries by climbing a precomputed hierarchy from both ends.
  • Live traffic breaks plain CH, so use customizable hierarchies or overlay partitioning with fast weight refresh, plus hybrid re-timing of candidates. Partition by minimizing border nodes, mostly for preprocessing, blast radius and memory for profiles.
  • Traffic is a stream pipeline: anonymous probes, map matching, windowed robust aggregation, gap filling by neighbours and history, publish a speed table about every minute.
  • ETA is time-dependent route evaluation plus delay estimates plus a learned residual, measured by error percentiles; reroute only when gains exceed a threshold, with hysteresis.
  • Failure modes are solved by degrading: stale tiles, typical speeds when traffic is stale, versioned snapshots for rollback, canaries on every data release.
