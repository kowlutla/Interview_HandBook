Design a Distributed Lock Service

We design a Chubby or etcd style service that lets many independent processes agree on who holds a lock right now. The hard part is not the lock table. It is making the answer stay correct when clocks drift, processes pause, networks split and the service's own leader dies.

How to approach this problem (read this first)

What the interviewer is really testing. A lock table is easy. The interview is about three hard parts. First, can you explain why a lock with a timeout is never fully safe, and what fixes that (a fencing token checked by the protected resource). Second, can you make the service itself survive failures, which means a replicated state machine with a majority commit, plus a clear story for what happens when the leader dies and when a client freezes. Third, can you spot where the load really is: not in the lock writes, but in heartbeats, reads and watch notifications.

The thinking order, step by step

  1. Ask what the lock protects. Say: "Is this lock for efficiency, where a duplicate is harmless, or for correctness, where two holders corrupt data?" You ask first because the answer decides whether fencing is required, and fencing shapes the whole API.
  2. Fix the safety rule in one sentence. Say: "At most one valid holder at any time, and when forced to choose I pick consistency over availability." This comes before any box is drawn, so every later choice can be checked against it.
  3. Estimate the three streams, heartbeats first. Say: "50,000 sessions with a 5 second heartbeat is 10,000 per second, and I will keep those off the consensus log." Heartbeats go first because they are the biggest number and they decide a design rule. Then writes (about 2,000 per second) and state size (about 1 GB, fits in RAM).
  4. Draft the API around sessions. Say: "Everything a client owns hangs off a session, so one heartbeat keeps all its locks alive." Draft CreateSession, Acquire returning a fencing token, Release carrying that token, and Watch. The token in the response is the detail that shows you understand the problem.
  5. Show the first simple design and break it. Say: "One server with a map and expiry times. It is a single point of failure, loses locks on restart, and a backup can split the brain." Then evolve it to five Raft replicas. Doing the simple version first shows the need for each later piece.
  6. Walk the acquire path through Raft. Say: "The leader appends the entry, a majority persists it, then it applies it and returns the token." Follow one request end to end so the interviewer sees the order of events.
  7. Deep dive on fencing, then leases. Say: "Client A pauses for 40 seconds, B gets token 34, and A's late write with 33 is rejected." This is the part they probe hardest, so do it while you still have time.
  8. Cover failures and scaling. Say: "Leader dies: new leader resets deadlines and clients get a grace window. At scale I add an edge proxy tier for watch fan out." Keep each failure to one sentence of cause and one of fix.
  9. Close with alternatives and evolution. Say: "Redis is fine for efficiency locks; for correctness I want consensus plus fencing." End with what you would build first.

The decision points

  • Efficiency lock or correctness lock? Ask what happens if two clients hold it. If data can be corrupted, you need fencing tokens and a consensus store. If not, a simple Redis key may do.
  • Are heartbeats log writes? Ask what a heartbeat is worth after one second. Nothing, so keep it in leader memory and accept a grace reset after failover.
  • One Raft group or many? Ask whether the write rate fits. 6,000 per second peak fits one group, and one group keeps multi lock atomicity simple, so do not shard yet.
  • Linearizable or stale reads? Ask whether the read feeds a decision. Decisions go through the leader; dashboards and config can use followers.
  • One region or global? Ask what a write may cost. A global group costs 70 to 150 ms per write, so default to regional clusters.

Common mistakes on this problem

  • Saying the TTL makes the lock safe. A paused client breaks it. Fix: name the zombie client and add fencing at the resource.
  • Putting heartbeats through consensus. It wastes most of the write budget. Fix: keep deadlines in leader memory.
  • Taking the token from a clock or a per leader counter. It can go backwards after failover. Fix: take it from the log index.
  • Using a stale follower read to decide to acquire. Fix: acquire always goes through the leader.
  • Replicating lock tables asynchronously across regions. Two regions can both grant the lock. Fix: regional clusters, or one consensus group.
  • Starting with Redlock and defending it. Fix: say it fits efficiency locks only.
Interview tip Spend your first two minutes on one sentence: "A timeout alone cannot make a lock safe, so I will build a lease plus a fencing token that the resource enforces." Every later section then hangs off that sentence.

1. Problem statement and clarifying questions

The prompt is short: "Design a distributed lock service." A strong candidate does not start drawing boxes. A lock service is a deceptively small product with a very sharp correctness requirement, so we first pin down what it is for. We are building the kind of service that Google's Chubby, Apache ZooKeeper and etcd provide: a small, strongly consistent, highly available cluster that many applications call to elect leaders, guard exclusive access to a resource, and publish small pieces of configuration or membership. It is not a general database and it is not a high-volume work queue.

Here are the questions we would ask the interviewer, and the answers we assume for the rest of the page.

QuestionAssumed answer
What is the lock used for: efficiency or correctness?Both kinds exist. Some callers only want to avoid duplicate work (a lost lock is a minor waste). Others protect shared state (a lost lock corrupts data). We must support the second kind, which forces fencing tokens (section 8).
Who are the clients?Internal services, about 50,000 client processes across the company, each holding a long lived connection to the service.
How many locks?About 1 million named lock nodes, but only a small fraction are contended at any moment.
Lock holding time?Seconds to hours. Leader election locks are held for days. Short critical sections of milliseconds should not use this service at all.
Availability and consistency target?Never grant the same lock to two live holders (safety). Stay available as long as a majority of the replicas is reachable. When forced to choose, choose consistency (CP in the terms of Chapter 28).
Regions?One cluster per region for regional work. A global lock is allowed but pays cross region latency (section 14).
Can clients trust their clocks?No. We assume bounded clock rate drift, but no synchronized wall clocks and no bound on process pauses.
Do we need fairness?Yes, first come first served among waiters, to avoid starvation.
Interview tip Say the central sentence early: "A lock with a timeout can never be perfectly safe by itself, because the holder can be paused after it checks the lock. So the design is a lease plus a fencing token enforced by the protected resource." Interviewers for this question are listening for exactly that insight.

2. Requirements and scope

2.1 Functional requirements

  • Sessions. A client opens a session, kept alive by heartbeats. Everything the client owns (locks, ephemeral nodes, watches) is tied to the session.
  • Lock operations. Acquire (blocking with a wait timeout), TryAcquire (return immediately), Release, and Renew (implicit through the session).
  • Waiters queue. Contending clients line up in order and are granted the lock one at a time.
  • Fencing token. Every successful acquire returns a token that strictly increases for that lock. Downstream resources use it to reject stale holders.
  • Ephemeral nodes. A small key value tree where a node disappears when the session that created it ends. This supports membership and leader election.
  • Watches. A client can subscribe to changes of a node or lock and be notified, instead of polling.
  • Linearizable reads and cheaper reads. The caller chooses between a read that reflects every completed write and a faster, possibly stale read.

2.2 Non-functional requirements

  • Safety first: at most one valid holder per lock at any time as seen through fencing tokens.
  • Availability: 99.99 percent for the write path, which means surviving the loss of any one replica in a five replica cluster, or any one zone.
  • Latency: acquire of an uncontended lock under 10 ms at p99 inside one region. Failure detection (a dead holder's lock becomes free) within the session TTL, typically 10 to 30 seconds.
  • Durability: an acknowledged lock grant survives any minority failure.
  • Scale: read heavy. Many more reads and heartbeats than writes. Many watchers.

2.3 Out of scope

We do not design a general purpose database, a transactional multi key store, a task queue, or a rate limiter (see Case study 3). We also do not design the client applications' business logic. We assume a trusted internal network, with authentication covered briefly in section 16.

3. Estimation

A lock service is sized by three streams: heartbeats (one per session per interval), writes through consensus (acquire, release, session create and expire), and reads plus watch notifications. Let us do the arithmetic. Estimation technique is covered in Chapter 2.

3.1 Sessions and heartbeats

50,000 client processes, each with one session. Session TTL is 15 seconds and the client sends a keepalive every 5 seconds (one third of the TTL, so two consecutive heartbeats can be lost before expiry). Heartbeat rate is 50,000 / 5 = 10,000 per second. Each is about 100 bytes on the wire, so 10,000 x 100 B = 1 MB/s inbound. That is trivial for bandwidth, but the important design point is that 10,000 per second must not go through the consensus log. If each one were a Raft write, we would spend most of the cluster's write budget on keeping sessions alive. Section 6 explains how the leader tracks lease times in memory instead.

3.2 Lock writes

Assume an average of 2,000 state changing operations per second (acquire, release, create, delete, session expiry), and a peak of 3x, so 6,000 per second. A single Raft group on SSDs with batching typically sustains roughly 10,000 to 30,000 small writes per second, so we have headroom of about 2x to 5x at peak. Each log entry is about 300 bytes, so the log grows at 2,000 x 300 B = 600 KB/s average, which is 600 KB x 86,400 = about 52 GB per day of raw write ahead log. We do not keep it: the state machine is snapshotted and the log truncated, so steady state disk is the snapshot (below) plus a few hundred megabytes of recent log.

3.3 State size

1,000,000 lock and config nodes at about 1 KB each (name, value, owner session, token counter, waiter list pointers) is 1 GB. That fits comfortably in memory on every replica. Plus 50,000 session records at 200 B is 10 MB. This small total is a deliberate design constraint: the whole state lives in RAM on every replica, and the service rejects values larger than 1 MB (practically a few KB).

3.4 Reads and watches

Assume 100,000 reads per second at peak (a 50:1 read to write ratio at the average), mostly "who holds this lock" and config reads. Assume 500,000 active watches (10 per session). Each write triggers watches on average 10 clients, so notification fan out is 2,000 x 10 = 20,000 notifications per second at the average and 60,000 at peak. A write to a popular config node watched by 40,000 clients creates a burst of 40,000 notifications at once, called a thundering herd, handled in section 12.

Conclusion: a single Raft group of five replicas is enough. We do not shard the core, which keeps cross lock atomicity simple. What we must engineer is the read, heartbeat and watch path, not the write path.

4. API design

The API is a small set of RPCs over a long lived, multiplexed connection (gRPC style streams, see Chapter 5). Heartbeats and watch events flow on the same stream so the client holds a single connection per process.

CreateSession(ttl_ms)                 -> { session_id, ttl_ms, lease_epoch }
KeepAlive(session_id)                 -> { ttl_ms }          // server may hold the call (long poll) and reply near expiry
CloseSession(session_id)              -> {}                  // releases all locks and deletes ephemerals

Acquire(lock, session_id, wait_ms, mode)  -> { granted, fencing_token, version }   // mode: EXCLUSIVE | SHARED
TryAcquire(lock, session_id, mode)        -> { granted, fencing_token, holder? }
Release(lock, session_id, fencing_token)  -> {}
GetLockInfo(lock, consistency)            -> { holder_session, token, waiters, version }

Create(path, value, ephemeral, sequential, session_id) -> { path, version }
Get(path, consistency)                    -> { value, version, mod_revision }
Set(path, value, expected_version)        -> { version }       // compare and set
Delete(path, expected_version)            -> {}
Watch(path | prefix, from_revision)       -> stream of { type, path, revision, value }
Txn(compares[], ops[])                    -> { succeeded, results[] }  // small atomic multi-op

consistency: LINEARIZABLE | SERIALIZABLE (follower, may be stale)

Notes on the choices. Release carries the fencing token so that a delayed release from a previous holder cannot release the lock a newer holder owns (the same stale actor problem as in writes). Set and Delete carry expected_version, which makes them compare and set operations and therefore idempotent under retry (see Chapter 32). Every response carries a revision, the global Raft log index at which the state last changed, which lets a client resume a watch exactly where it stopped. Acquire with a wait_ms is a server side wait: the request is parked and answered when the grant happens, so clients do not poll.

5. Data model and storage choice

All state is a small in memory tree, persisted through a replicated write ahead log and periodic snapshots. We choose an embedded storage engine (a B+tree or an append only log with an in memory index) on each replica, not an external database, because the service is the foundation other systems depend on. If it needed a database that itself needed a lock service, we would have a circular dependency. Storage engines are described in Chapter 19.

The fencing counter is the key persistent field. A common mistake is to derive the token from the clock or from a per holder counter. The correct approach is to make the token the Raft log index (revision) of the grant entry, or a per lock counter incremented inside the same entry. Either way it is assigned by the single linearized log, so it is monotonic for the lock even across leader changes. Using the global revision has the nice property that tokens are comparable even across different locks, which some protected resources like.

6. A first simple design, then the real one

6.1 Single box

The first design is one server holding a hash map from lock name to owner, with an expiry time per lock. Acquire sets the owner if absent or expired. It is simple and fast, and it is wrong for three reasons: the server is a single point of failure, which makes every locked system unavailable; when it restarts it loses the lock table, so two clients may now hold the same lock; and a time based expiry on the server tells us nothing about what the client believes. Doubling it as a primary and a backup does not help: if the primary is just slow and the backup promotes itself, both accept acquires, which is split brain (see Chapter 29).

6.2 Replicated state machine

The real design replicates the lock table as a state machine with Raft. All commands (create session, acquire, release, expire session) are entries in a replicated log. Each replica applies the same entries in the same order, so each ends with an identical lock table. A command is acknowledged to the client only after a majority has stored it durably, so a minority failure loses nothing. Section 7 covers how this works and what Raft offers us.

The edge proxy tier is a scaling device explained in section 12. At small scale clients can connect directly to the replicas, as ZooKeeper and etcd clients do. At our scale the proxies keep 50,000 connections off the five consensus nodes.

7. Raft replicated state machine

Chapter 29 covers Raft in depth. We recap only what the lock service depends on.

  • One leader per term. Followers elect a leader if they stop hearing from it. A candidate needs votes from a majority, which for five replicas means three. Each election increments the term, a number that acts as a logical clock.
  • Log replication. The leader appends a command to its log and sends it to followers. Once a majority (three of five) has persisted it, the entry is committed. The leader applies it to the state machine and replies.
  • Safety. A replica with a stale log cannot win an election, and a committed entry is present in the log of every future leader. So no acknowledged grant can be forgotten.
  • Fault tolerance. With five replicas, any two can fail. With three, only one can. We pick five for the lock service because it is critical infrastructure and because planned maintenance of one node should still leave tolerance for one unplanned failure.

7.1 Why the lock table is a deterministic state machine

Every command is applied identically on every replica, so the apply function must be deterministic: no wall clock reads, no random numbers, no external calls. Where a command needs a timestamp (for example a session creation time), the leader chooses it and puts it inside the log entry, so every replica uses the same value. The fencing counter is incremented as part of applying the acquire entry, not by the client. This is the "replicated state machine" idea: agreeing on the order of commands is enough to agree on all state.

7.2 Request flow: acquire

  1. The client calls Acquire(lock, session, wait) on its edge proxy, which forwards to the leader (a follower would redirect or forward).
  2. The leader validates the session is live and appends a log entry ACQUIRE(lock, session).
  3. The leader replicates it to four followers in parallel and waits for two acknowledgements (itself plus two is a majority of five).
  4. The entry commits. The leader applies it: if the lock is free, the session becomes holder and the fencing counter increments to, say, 34. Otherwise the session is appended to the waiter queue.
  5. If granted, the leader replies {granted, token 34}. If queued, the reply is held (parked) and sent later at grant time.

Latency check: inside one region the round trip between zones is about 1 ms, an SSD fsync with batching is about 1 to 2 ms, so a committed write takes roughly 3 to 6 ms, matching our 10 ms p99 goal for an uncontended acquire.

8. Sessions, leases, heartbeats and TTL

A lock must be released automatically if its holder crashes, otherwise one dead process blocks the lock forever. The mechanism is a lease: a promise that lasts for a limited time unless renewed (see Chapter 30). We attach the lease not to each lock but to the session, so one heartbeat keeps all of a client's locks alive. That is the Chubby model, and etcd's lease model is similar (a lease with a TTL to which many keys attach).

8.1 The session lifecycle

  • Create. The client creates a session with a TTL of 15 seconds. This is a Raft write. The server returns a session_id and a lease epoch.
  • Keepalive. Every 5 seconds the client sends a keepalive. The leader resets the session's deadline to now + TTL in leader memory. This is not a Raft write. Chubby does this too: the master holds the keepalive RPC open and replies near the end of the lease, which both saves messages and carries invalidations.
  • Expiry. If the leader sees no keepalive before the deadline, it appends EXPIRE_SESSION(id) to the Raft log. When that entry commits, every replica atomically releases all locks owned by that session, deletes its ephemeral nodes, and hands the locks to the next waiters, bumping their fencing tokens.
  • Close. A clean shutdown sends CloseSession, doing the same without waiting for the TTL.

8.2 Why TTL and heartbeat interval are chosen the way they are

SettingShort TTL (3 s)Long TTL (60 s)
Failure detectionFast: dead holder replaced in about 3 sSlow: a lock may stay stuck for a minute
False expiry from GC pause or network blipFrequent, causes lock churn and leader flappingRare
Heartbeat loadHigher (50,000 / 1 s = 50,000/s)Low
Typical useLatency sensitive leader electionBatch jobs, long critical sections

We pick 15 seconds as default and let callers choose between 5 and 60. A rule of thumb is a heartbeat every TTL / 3, so that two successive heartbeats can be lost before the session expires. Choosing a TTL shorter than the worst plausible GC pause or network hiccup just creates false expiries.

8.3 The clock assumption

The server decides expiry using its own monotonic clock: "no keepalive for 15 seconds since my last receipt". The client decides when it must stop trusting its lease using its own monotonic clock too, with a conservative rule: the client's local lease timeout starts counting from the time it sent the keepalive (not when the response arrived) and is shortened by an allowance for clock rate drift. The safety argument needs only the assumption that clocks run at nearly the same rate (drift of 100 ppm is typical, which is 1.5 ms over 15 s). We never compare wall clock timestamps from different machines. Time ordering issues are covered in Chapter 27.

Watch out A client that checks "do I still hold the lock?" and then acts is not safe, even with a perfect lease. A stop the world garbage collection, a VM live migration, a laptop suspend or a swap storm can pause the process between the check and the action for longer than the TTL. The lock service cannot prevent this. Only the resource, using fencing tokens, can.

9. Lock acquire, release, try, waiters and watches

9.1 Semantics

  • TryAcquire is one Raft write when the lock is free and a plain read when the lock is clearly held. It returns the current holder session so the caller can decide to back off.
  • Acquire with wait appends the session to the lock's waiter queue (itself a Raft write), parks the RPC, and completes it when the lock is granted or the wait timeout fires. A timeout is another log entry that removes the session from the queue, so the replicated waiter list is always exactly right.
  • Release by the holder appends RELEASE(lock, token). On apply, if the token matches the current holder, the first waiter becomes the holder, the counter increments, and its parked RPC is answered. A release with a stale token is rejected.
  • Shared mode (reader writer locks) allows many readers or one writer. The waiter queue keeps order, so a waiting writer blocks newer readers to prevent writer starvation.

9.2 Waiters queue and the herd effect

There are two ways to build a waiting line, and the difference is a classic interview point.

9.3 Watches

A watch tells a client that something changed so it need not poll. We follow etcd's model: a watch is a stream of ordered events from a given revision. If the client's stream breaks, it reconnects with from_revision = last_seen + 1 and the service replays missed events from the history, unless that history has been compacted, in which case the client gets a "too old" error and must re read the state and start a new watch. The client library hides this. Compare ZooKeeper's one time watches, which fire once and must be re registered (with a gap in which an event can be missed unless the client re reads). The streaming design avoids the gap.

Events are delivered in revision order and exactly once per revision to each watcher, with a guarantee that a client that sees event N has previously seen all events before N. That ordering is what makes watches useful for building higher level coordination.

10. Deep dive: fencing tokens and protecting downstream resources

This is the part an interviewer will probe hardest. See Chapter 30 for the general treatment; here we apply it.

10.1 The zombie client problem

Client A acquires the lock with token 33, then suffers a 40 second GC pause. Its session expires after 15 seconds. The service gives the lock to client B with token 34. B writes to the storage. Then A wakes up. Its code still believes it holds the lock (it checked a moment before the pause) and writes. Without protection, A's stale write overwrites B's work. No amount of lease tuning removes this, because the pause can be arbitrarily long and can occur at any instruction.

Walkthrough. Four vertical lines: Client A, the lock service, Client B and the storage. Green arrows are good paths, the red arrow is the stale write. 1. A acquires the lock and receives token 33. 2. A writes to storage with token 33. Storage accepts and records max_seen as 33. 3. A freezes in a 40 second garbage collection pause (red box). Its 15 second session expires meanwhile. 4. B acquires and receives token 34. 5. B writes with token 34, accepted, max_seen becomes 34. 6. A wakes up, still sure it holds the lock, and sends its write with token 33. 7. Storage compares 33 with 34 and rejects it. The key drawing habit is to put the red box and the final rejection box on the same page so the reader sees cause and effect. The choice avoids relying on any clock. If you remove the max_seen check at storage, step 6 overwrites B's data and nothing in the lock service can prevent it.

10.2 What the protected resource must do

The resource (a database row, an object store, a file server, a downstream API) keeps max_token_seen per protected object and applies this rule on every mutation: if the request token is smaller than max_token_seen, reject; otherwise accept and set max_token_seen = token. In a SQL database this is a compare in the same transaction: UPDATE t SET v=?, fence=? WHERE id=? AND fence <= ?. For object stores that support conditional writes, the token is carried in a version or ETag precondition. For resources that cannot be modified, we put a thin gateway in front of them that does the check.

We therefore ship the lock service with a documented contract: "the lock gives you the right to try; the token proves your right to succeed." The client library exposes the token on the lock handle and offers wrappers for common stores. For resources that cannot verify tokens, we state clearly that the lock is only advisory efficiency protection.

Key idea Monotonic tokens work because they come from the replicated log. Two holders can never receive the same token or tokens out of order, so "highest token wins" is a total order that the resource can enforce without trusting any clock.

11. Leader failover, session grace and read consistency

11.1 What happens to sessions when the leader dies

The leader holds all session deadlines in memory. When it crashes, a new leader is elected (typically in a few hundred milliseconds to a couple of seconds: an election timeout of 1 second plus a vote round). The new leader does not know when each session last sent a keepalive. If it simply trusted deadlines it could expire sessions immediately, causing a mass lock loss (up to 50,000 sessions at once) for something the clients did nothing wrong in.

The solution, taken from Chubby, is a grace period. On becoming leader, the new leader sets every live session's deadline to now + full TTL and treats that as the starting point. Clients that cannot reach a leader keep their local lease until it runs out, then enter a jeopardy state: they stop acting on locks but keep their session for an extra grace window (for example another 45 seconds, Chubby used 45 s) while they look for the new leader. If they reconnect inside the window, the session survives and the locks stay with the holder. If not, the session is dead.

Walkthrough. Time runs left to right along the black line. Red boxes are bad events, amber boxes are waiting states, green boxes are recovery. 1. The leader crashes (red box at the left). 2. An election runs for about 1 to 3 seconds (amber bar). 3. The new leader appears and resets every session deadline to a full TTL (green box above the line). 4. Meanwhile the clients, in the lower amber bar, first run on their local lease and then enter jeopardy, which means they stop starting new critical work but keep their session. 5. If they reconnect in time (green bar), nothing changes hands and no new token is issued. 6. If they come back too late (red box at the right), the session is dead and the locks have moved on. Point at the long lower bars: they show that clients outlast the election. Without the grace reset, the new leader would not know the deadlines and could expire up to 50,000 sessions at once.

This creates a safety rule: the new leader must not expire any session earlier than the old leader could have. Resetting every deadline to a full TTL from the start of the new term guarantees that, because the old deadlines were at most one TTL ahead of the last heartbeat. A trade off is that a client that truly died just before the failover has its lock freed up to one TTL later than usual.

11.2 Is the old leader dangerous?

A deposed leader may not know it was deposed (a network partition, a long pause). If it keeps answering reads from its memory it could return stale data, and might even confirm that a session is alive. Raft prevents wrong writes, since the old leader cannot reach a majority to commit anything. To protect reads we use either of two techniques: a read goes through the log, or the leader confirms leadership with a majority before answering (ReadIndex in etcd), or the leader relies on a leader lease (it assumes no other leader can exist for the election timeout after its last majority heartbeat, which requires a bound on clock rate drift). We choose ReadIndex by default and the leader lease as an opt in optimization.

12. Ephemeral nodes, scaling reads and watch fan out

12.1 Ephemeral nodes and recipes

An ephemeral node is a key owned by a session and deleted when that session ends. It turns "who is alive" into data. Typical uses: group membership (each worker registers /workers/w-17), service discovery (see Chapter 49), and leader election (candidates create sequential ephemeral nodes and the lowest is the leader). The sequential flag makes the server append a monotonically increasing number, assigned by the log. Because deletion on session expiry is a single committed log entry that removes all of the session's nodes together, observers see a consistent cut: either the whole worker is gone, or none of it.

12.2 Where the load really is

Our estimates showed that the consensus group is not the bottleneck: 6,000 writes per second at peak is a fraction of the capacity. The bottleneck is the number of connections, heartbeats, reads and watch notifications. Four techniques address it.

  1. Keep heartbeats out of the log. Already covered: 10,000 keepalives per second are served from leader memory.
  2. Edge proxy tier. Stateless proxies terminate the 50,000 client streams and multiplex them into a few connections to the replicas. A proxy can coalesce watchers: if 2,000 clients on 30 proxies watch the same key, each proxy holds one upstream watch and fans out locally, so the cluster sends 30 events instead of 2,000. This resembles the etcd gRPC proxy.
  3. Followers and observers. Serve serializable and ReadIndex reads from followers. For larger read volume, add non voting observer replicas (a ZooKeeper concept) that replicate the log but do not count toward quorum, so adding them raises read capacity without making writes slower or changing fault tolerance.
  4. Client side caching with invalidation. Chubby clients cache data and the master invalidates caches through the keepalive replies before accepting a write. We offer cached reads with watch based invalidation for config nodes.

12.3 Thundering herd on watches

If 40,000 clients all watch /config/flags and it changes, 40,000 notifications go out at once, and then all 40,000 clients read the new value, so the burst doubles. Mitigations: deliver the new value inside the event (no follow up read); fan out through the proxy tier; add random jitter to client reactions; rate limit watch registrations per session; and for locks specifically, prefer the server queue (one wake per release) over everyone watching the lock node.

Walkthrough. Left to right: the Raft leader (green), 30 proxies (blue, three drawn) and groups of watching clients (purple). 1. A key changes and the leader emits one event for the commit. 2. Each proxy holds just one upstream watch on that key, so the leader sends one event to each of the 30 proxies. 3. Each proxy copies the event to its own clients, about 1,300 each, since 40,000 divided by 30 is roughly 1,300. The number to remember is 30 events at the leader versus 40,000 if every client watched the cluster directly. On the whiteboard, draw the narrow left side and the wide right side to show the fan out happening at the edge. The alternative is clients watching replicas directly, which makes the leader spend its CPU on notifications instead of commits. If you remove the proxy boxes, a popular config change turns into a burst of 40,000 sends from the consensus nodes.

Split brain deserves a direct statement. The lock table itself cannot have two leaders both committing, because commits need a majority and two disjoint majorities do not exist. The split brain risk that remains is at the application level: two clients both acting as the holder, because one is stale. The service ensures that only one of them holds the latest token, and the resource decides by token. General resilience patterns are in Chapter 40 and availability in Chapter 41.

14. Client library behaviours and multi-region

14.1 What the client library must do

Most lock bugs are in the clients, so we ship a thick library and keep the semantics inside it.

  • Background keepalive thread that is isolated from application work (a dedicated thread or event loop) so that a busy application does not starve heartbeats. This does not defend against full process pauses.
  • Session state machine: CONNECTED, JEOPARDY (cannot reach the service, local lease still valid), and EXPIRED. The library publishes state changes as callbacks. In JEOPARDY the app should pause new critical work; in EXPIRED it must stop and drop the lock handle immediately.
  • Lock handle with a cancellation signal. The holder gets a token and a context that is cancelled as soon as the local lease is lost. Long operations should check it between steps.
  • Safe retries. Acquire is idempotent per session (re acquiring a held lock returns the same token). Release carries the token. Retries use backoff with jitter.
  • Endpoint discovery and leader redirect, caching of the last known leader, and fast failover to another replica or proxy.
  • Grace window: after reconnecting inside the grace period, the library re validates ownership of each lock with a linearizable read before resuming, and discards locks that were lost.

14.2 Multi-region

Consensus latency is bounded by the round trip to a majority. Within a region, zones are about 1 ms apart. Across regions, 60 to 150 ms. Therefore a single Raft group stretched over three regions makes every write cost around 70 to 150 ms and lets the service survive a full region loss. Two real choices exist.

Details. With single node Redis, if the master grants a lock and crashes before the replica sees it, the promoted replica has no record, so a second client can take the same lock. Redlock tries to fix this by asking five independent Redis masters and requiring a majority, but it depends on timing assumptions (bounded network delay, process pauses and clock drift) that real systems violate, and it produces no fencing token. So for a correctness lock, we prefer a real consensus system plus fencing. For a cheap, best effort "only one instance should run this cron job," Redis is a reasonable and much simpler choice, and we say so honestly. See Chapter 15.

Database advisory locks (for example Postgres pg_advisory_lock) are session scoped locks managed by the database. They are excellent when the thing being protected is in that same database, because the lock and the data share a failure domain and fate. Their weaknesses: they hold a database connection per lock; they depend on the database's availability; and they do not generalize to guarding other systems. We would offer them as the recommended answer for "serialize work on this row" and the lock service for "elect one leader among 200 pods." See Chapter 18.

ZooKeeper versus etcd as the implementation: ZooKeeper uses ZAB (an atomic broadcast protocol similar in spirit to Raft), sessions with tick based timeouts, one time watches and the znode tree with sequential and ephemeral flags. etcd uses Raft, leases attached to keys, a flat versioned key space with revisions, streaming watches with history, and multi key transactions. Our design borrows from both. Building from scratch is rarely right in a real organization: we would run etcd or ZooKeeper and wrap it. The interview asks us to explain what is inside.

16. Further deep dives

16.1 Why not make every lock a separate Raft group?

If one group becomes a bottleneck, we can shard locks by name hash across several Raft groups, each with its own leader and log (the pattern of Chapter 25). Each group would run on the same set of machines to share hardware. Our estimates say a single group is enough, and sharding costs us cross shard atomicity: a session expiry that must release locks on several groups becomes a multi group operation, and a multi lock transaction becomes a distributed transaction (Chapter 31). So we start with a single group, and design the session owner record so that sessions could later be homed on a single group, with locks routed by hash and expiry fanned out by that owner.

16.2 Tradeoff table for the heartbeat path

16.3 Security and abuse

Clients authenticate with mutual TLS, and each service identity is limited by an access control list to path prefixes (/payments/*), with separate permissions to read, write and watch (see Chapter 55). Abuse controls: per client quotas on sessions, nodes, watches and request rate (a runaway client creating a million nodes can fill memory), a maximum value size, and a cap on the waiters per lock. A lock held by a buggy client forever is caught by a "max hold" alert, and operators can revoke a session by hand. All administrative actions are audit logged.

16.4 Monitoring and SLOs

  • SLIs: acquire latency p50 and p99; commit latency; fsync latency (the number one cause of problems); election count per hour; session expiry rate; heartbeat lag; watch event delivery lag; proposals pending; database size.
  • SLOs: 99.99 percent of linearizable operations succeed over 30 days; p99 write under 25 ms; failover recovery under 5 seconds at p99; watch delivery lag under 500 ms at p99.
  • Alerts: more than 1 leader change per 10 minutes (flapping); fsync p99 above 50 ms; any follower more than 1,000 entries behind; session expiry spike (a sign of a client or network event, not service failure).

See Chapter 54.

16.5 Cost notes

The cluster is small and boring: five machines with 8 cores, 32 GB memory (state is 1 GB, the rest is page cache and headroom), and fast SSDs or NVMe with low fsync latency, which matters more than capacity. Proxy tier: 6 to 10 small stateless instances. The expensive part is operational: upgrades, backups and on call. This is why many companies run a shared lock service for the whole organization rather than one per team.

17. Scaling, evolution and phasing

17.1 What changes at 10x

At 500,000 clients: heartbeats reach 100,000 per second, which the leader can still handle if it only touches memory, but 500,000 connections demand a larger proxy tier (about 100 proxies at 5,000 connections each). Watches reach 5 million, so coalescing in the proxies becomes mandatory. Writes at 20,000 per second approach one group's ceiling, so we shard by lock prefix into several Raft groups and introduce a session owner design as in 16.1. State grows to 10 GB, so snapshots and catch up become minutes, and we move to incremental snapshots. We would also push more reads to observers and add per tenant isolation (see Chapter 42) so one team's watch storm cannot hurt another team.

17.2 What we build first

  1. Phase 1: adopt an existing Raft or ZooKeeper cluster as the core. Build the client library with sessions, local lease timers, jeopardy handling and the fencing token API.
  2. Phase 2: add the proxy tier and watch coalescing, quotas and access control, dashboards, and the documentation contract for fencing.
  3. Phase 3: add follower and observer reads, shared mode locks, and the multi region layout.
  4. Phase 4: sharding into several groups if growth demands it.

17.3 Alternatives not chosen

  • Lock on top of a general database with row locks: simple, but the database becomes the dependency and failure detection depends on connection timeouts.
  • Peer to peer or gossip based lock: gossip (Chapter 33) is eventually consistent, so it cannot give mutual exclusion.
  • Time based leases from synchronized clocks (as in Spanner's TrueTime): allows lock free reads but needs special hardware clocks and bounded uncertainty; too heavy for general use.
  • Avoiding locks entirely: use idempotent operations, optimistic concurrency with versions, or a single writer queue (Chapter 34). Often the best answer.

18. Interview Q&A

Can a lock with a TTL ever be perfectly safe on its own?

No. The holder can check the lock, then stall for a stop the world garbage collection, a VM pause, or a network delay on a write that was already sent, for longer than the TTL. Meanwhile the lock moves to another client. When the first client resumes, it acts on stale belief. The lock service cannot see or stop that. The fix is to make the protected resource participate: every grant carries a monotonic fencing token and the resource rejects any request carrying a token lower than the highest it has seen. The lock then gives mutual exclusion in practice and the token gives it in the worst case.

Why are heartbeats not written through Raft?

At 50,000 sessions with a 5 second interval that would be 10,000 extra writes per second, each needing disk and a majority round trip, consuming most of the capacity of the group and bloating the log with information that has no long term value. Instead the leader keeps deadlines in memory. The price is that a new leader does not know the deadlines, so it resets every session to a full TTL and clients get a grace window to reconnect. Detection of dead holders after a failover is slightly later, which is a good trade for safety and throughput.

What happens to held locks if the leader dies?

Nothing, if the election and reconnection fit inside the lease and grace windows. The committed lock table is on a majority, so the new leader has it. The new leader gives each session a fresh full TTL. Clients notice the broken connection, enter jeopardy (stop starting new critical work), find the new leader, and reconnect with the same session id. Their locks and tokens are unchanged. Only when a client fails to reconnect within TTL plus grace does its session expire and its locks pass to waiters with higher tokens.

How do you choose the fencing token, and why is it monotonic across leader changes?

The token is assigned inside the state machine when the acquire entry is applied, either as the Raft log index of that entry or as a per lock counter incremented in the apply function. Because the log is a single total order agreed by consensus, and a committed entry survives every future leader, two grants can never get equal or reversed tokens, even if the leader changes between them. A token taken from a wall clock or a per leader memory counter would not have that property, since clocks disagree and a new leader would restart its counter.

When is it fine to read from a follower, and when is it dangerous?

Follower reads are fine for observing data that tolerates bounded staleness: configuration, service discovery, dashboards, and cache refreshes. They are dangerous for any read that feeds a decision such as "is the lock free, so I will take it", because a lagging follower may show an old holder or an old value. Decisions must go through the leader via ReadIndex or a write. A middle path is the follower ReadIndex read, which asks the leader only for the current commit index and then serves from the follower after catching up, giving linearizable data while offloading the data read from the leader.

Why five replicas and not three or seven?

Three replicas tolerate one failure, but during planned maintenance on one node a second failure loses quorum, so critical infrastructure usually runs five, which tolerates two. Seven tolerates three but each write needs four acknowledgements, adds latency and replication load, and rarely increases real availability because correlated failures (a zone, a bad deploy) dominate. We spread five replicas over three zones as 2, 2, 1 so that losing any zone keeps a majority of three.

How would you stop a thundering herd when a popular lock is released?

Do not let all waiters watch the lock node. Use a server side queue so a release wakes only the head waiter, or the ZooKeeper style recipe where each contender creates a sequential ephemeral node and watches only its predecessor. For config style nodes watched by many clients, coalesce watches in a proxy tier, include the new value in the event so there are no follow up reads, and add client jitter. Rate limiting watch registration per session protects the service from a client bug that opens thousands of watches.

Why not just use Redis Redlock?

Redlock asks five independent Redis masters and needs a majority, but it has no consensus protocol, no fencing token, and its safety argument depends on bounded network delay, bounded pauses and bounded clock drift, which real systems do not guarantee. A client paused after acquiring can still act once its key has expired and another client has locked. For efficiency locks, such as preventing two cron instances from running the same report, plain Redis is fine and operationally simple. For correctness locks, I would use a consensus backed service with fencing tokens, or avoid the lock and use a compare and set on the data.

How do you handle multi-region?

Consensus latency equals the round trip to a majority, so a global group costs 70 to 150 ms per write. I would run a separate cluster per region for regional work, which keeps writes at a few milliseconds, and keep a small global cluster for the few truly global singletons. I would not replicate lock tables asynchronously between regions, since both sides could then grant the same lock. Remote readers can use follower or observer reads for configuration where staleness is acceptable.

How would you test that the service is actually safe?

Use deterministic simulation and Jepsen style fault injection: random partitions, process pauses, clock rate skew, leader kills and disk stalls while many clients acquire, write with tokens and release. A checker verifies that tokens strictly increase per lock, that no two accepted writes carry out of order tokens, and that the history of lock operations is linearizable. We also test the client library by injecting pauses between the "hold" check and the write to prove that the resource rejects the stale token.

19. Recap

  • A lock service is a small, strongly consistent, replicated state machine: five Raft replicas, all state in memory, about 1 GB, one group is enough for 2,000 to 6,000 writes per second.
  • Sessions with TTL and heartbeats own locks, ephemeral nodes and watches. Heartbeats (10,000 per second) live in leader memory, not in the log. A new leader resets deadlines and clients get a grace window.
  • Locks have a server side FIFO queue, try and blocking acquire, and watches with revision replay. Waking one waiter per release avoids the herd.
  • Safety in the face of pauses and clock errors comes from fencing tokens taken from the log and checked by the protected resource, not from the TTL.
  • Reads: linearizable via ReadIndex for decisions, follower or observer reads for observing; the real scaling work is in reads, heartbeats and watch fan out through a proxy tier.
  • Failure modes: partitions cannot produce two leaders that both commit; zombie clients are handled by fencing; clients must treat jeopardy and expiry as "stop work".
  • Regional clusters by default, a small global cluster for global singletons, no async active active locks.
  • Redis based locks are fine for efficiency; use consensus plus fencing, or a database compare and set, when correctness matters.
