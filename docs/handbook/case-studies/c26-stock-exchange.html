Design a Stock Exchange

We design the core of an electronic exchange: the order book, the matching engine, the sequencer that fixes one order of events, the market data feed that tells the world what happened, and the recovery story that rebuilds everything by replaying a log. This is the system design problem where the right answer is deliberately unlike a typical web service: one thread per order book, no database on the hot path, and every microsecond counted.

How to approach this problem (read this first)

What the interviewer is really testing. This is not a web-scale problem. Volume is small: about 12,800 messages per second on average and 250,000 at peak, which one core could almost handle. The interviewer wants to see whether you recognise that the hard parts are different. First, fairness: every order gets one official arrival order, so you need a sequencer. Second, determinism: matching is a pure function of an ordered input log, which gives you replication, recovery and audit almost for free. Third, latency in microseconds, which rules out databases, locks and kernel networking on the hot path. A candidate who reaches for load balancers, a SQL database and a cache has missed the point.

The thinking order, step by step

  1. Narrow the scope. Ask: is it the matching core, a brokerage app, or clearing? Which asset class, how many symbols, which matching rule? Say: "I will design the exchange core: gateways, sequencer, matching engine and market data, for cash equities with price-time priority." Do this first because "stock exchange" names four different systems.
  2. Name the two special requirements. Say: "Fairness and microsecond latency are hard requirements, and acknowledged orders must never be lost." These shape every later choice, so state them before numbers.
  3. Estimate messages per second first. Say: "300 million messages over a 6.5 hour session is about 12,800 per second, peak about 250,000." Then show that the busiest symbol is about 12,500 per second. The conclusion, that one thread suffices, is the surprise that justifies the whole design.
  4. Estimate memory and journal. Say: "The whole book is about 4 GB, so it lives in RAM; the journal is about 19 GB a day." This tells the interviewer that disk is only a log.
  5. Draft the order messages, not REST. New, cancel, replace, with integer prices and a client order id as the idempotency key. Do it before the data model because the message set defines the state machine.
  6. Show the naive design and why it fails. A web service with a SQL database fails on global order, locks, latency and non-determinism. Say: "Matching is sequential per symbol, so parallelism comes from partitioning by symbol."
  7. Build the pipeline. Gateways, sequencer, engine, hot standby, journal, publisher. Trace one order through it.
  8. Deep dive in order of risk. The order book and matching loop, then the sequencer and single thread, then replication and replay, then market data multicast.
  9. Finish with failure and scaling. Partition by symbol for blast radius, then walk through the loss of each component.

The decision points

  • Database or in-memory log plus state machine? Ask: what is the latency per commit? Milliseconds for a database against microseconds needed, so keep the book in RAM and persist only inputs.
  • Many threads or one per book? Ask: does locking help or hurt? Locks cost more than a match and break determinism, so one writer thread per book.
  • How durable is "accepted"? Ask: what is the cost of one network hop versus one fsync? Replicating to the standby's memory is the compromise, described in the replay section.
  • Unicast, queue or multicast for market data? Ask: must everyone see it at the same instant? Yes, so multicast with sequence numbers and an A/B pair.
  • Shard by symbol or by something else? Ask: do orders in different symbols interact? No, so symbol is the natural key.

Common mistakes on this problem

  • Putting a relational database on the order path. Fix: book in RAM, durable input log.
  • Letting many order servers decide arrival order. Fix: one sequencer assigns the sequence number.
  • Multi-threading one order book. Fix: one thread per book, parallelism by symbol.
  • Using wall clock time or random ids inside the engine. Fix: take time from the sequenced message and ids from a counter.
  • Sending market data to each subscriber over TCP. Fix: multicast, A/B feeds and a gap recovery service.
  • Promoting the standby without fencing the old primary. Fix: epoch numbers and out-of-band power off.
Interview tip Say early: "The engine is a deterministic state machine fed by one sequenced log." Every follow-up (standby, recovery, audit, testing) then has the same answer: replay the log.

1. Problem statement and clarifying questions

The prompt is "Design a stock exchange." That sentence hides several different systems: the matching core that pairs buyers and sellers, the brokerage front end that retail customers use, the clearing house that moves money and shares after the trade, and the market data distribution that vendors and trading firms consume. A strong candidate says which of these is in scope before drawing anything. We are designing the exchange itself: the part that accepts orders from member firms (brokers and trading firms), keeps an order book for each listed symbol, matches orders by strict rules, and publishes the result. We are not designing a retail brokerage app (that is a consumer of our API) and not the settlement system (we only hand it a trade record).

Two ideas make this problem different from the other case studies and are worth stating at the start. First, fairness is a hard requirement, not a nicety: two orders must be processed in exactly the order the exchange received them, and every participant must see the same sequence of events. That pushes us to one authoritative order of events per symbol. Second, latency is a product: trading firms pay for being microseconds faster, so the design budgets time in microseconds and removes anything slow (disks on the critical path, locks, garbage collection, kernel network stack, even cross-thread queues with contention) from the hot path.

2. Requirements and scope

2.1 Functional requirements

  • Place order. A limit order (buy or sell up to a quantity at a limit price or better) and a market order (buy or sell at whatever the book offers now). Time-in-force options: day (rests until the close), IOC (immediate or cancel: take what is available, cancel the remainder) and FOK (fill or kill: execute completely or not at all).
  • Cancel and replace. A participant can cancel a resting order. A replace changes price or quantity. Following common exchange practice, lowering the quantity keeps queue position; changing the price or raising the quantity loses it and counts as a new order at the back of the queue.
  • Match. Pair an incoming order with resting orders on the opposite side, best price first and, within a price, oldest first. Each match produces a trade at the price of the resting order.
  • Acknowledge. Tell the sender, with an exchange-assigned order id, that the order was accepted, rejected, partially filled, fully filled or cancelled.
  • Publish market data. Stream every change of the order book and every trade to subscribers, with sequence numbers so they can detect loss. Provide snapshots so that a late joiner can catch up.
  • Controls. Reject orders that violate tick size, lot size, price bands, or a firm's pre-trade risk limits. Halt a symbol (circuit breaker) when the price moves too far too fast. Prevent a firm from trading with itself (self-trade prevention).
  • Drop copy and clearing feed. Send each trade to the clearing house and to the participants' risk systems.

2.2 Non-functional requirements

  • Determinism and fairness. The same input sequence always produces the same output, and orders are processed strictly in arrival order. No participant can jump the queue by connecting through a faster gateway than another.
  • Low and predictable latency. Mean matters less than the tail. A stall of one millisecond once an hour is worse than a steady 30 microseconds.
  • Durability and consistency. No acknowledged order or trade is lost or duplicated. Every subscriber sees the same events in the same order.
  • High availability with fast failover. A hot standby takes over in seconds from the exact same state.
  • Auditability. Reconstruct the state of any book at any past instant from the stored log.
  • Throughput. Sustain the opening and closing auction bursts, around 20 times the average rate.

2.3 Out of scope

We do not design the broker-side order management, the clearing and settlement network (the legal movement of cash and shares one or two days later), the listing and corporate actions process, or the surveillance analytics that look for manipulation. We touch the edges where they receive our feeds. We also leave out options-specific and futures-specific mechanics such as implied (spread) matching, mentioning them only in the evolution section.

3. Estimation

An exchange is sized by three streams: inbound order messages, the events the engine produces from them, and the market data that fans those events out to thousands of subscribers. Estimation technique is covered in Chapter 2. The numbers here are deliberately modest compared with a web-scale system; the difficulty is latency, not volume.

3.1 Order flow

Assume 300 million inbound messages per day: roughly 100 million new orders, 150 million cancels and 50 million replaces. That ratio is realistic because market makers continuously update quotes by cancelling and re-placing them, so the messages-to-trade ratio is high. Trades are about 15 million per day, so about 20 inbound messages per trade.

The regular session is 6.5 hours, which is 6.5 x 3,600 = 23,400 seconds. Average rate: 300,000,000 / 23,400 = about 12,800 messages per second. Traffic is far from flat. The opening and closing auctions and news events compress activity, so we plan for a peak of about 20 times average: 12,800 x 20 = about 250,000 messages per second across all symbols. The busiest single symbol might see 5 percent of that at peak: 250,000 x 0.05 = about 12,500 per second. Remember this number: it is tiny for one modern CPU core.

Key idea A matching step (look up the price level, walk the queue, update a few fields, emit events) costs on the order of one microsecond when everything is in memory and in cache. One thread can therefore process roughly a million orders per second. Our whole peak of 250,000 per second would use a quarter of a single core. We still partition across machines, but for isolation, blast radius and growth, not because one engine could not keep up. This shapes everything: we do not need distributed consensus on the hot path for throughput, only for durability.

3.2 Journal (input log) volume

The only thing we must persist to rebuild everything is the sequence of inputs. An input message is about 64 bytes (message type, symbol id, side, integer price, quantity, participant id, client order id, timestamps). Daily journal: 300,000,000 x 64 B = 19.2 GB per day. Over 252 trading days: 19.2 GB x 252 = about 4.8 TB per year. That is small enough to keep on ordinary SSDs and then archive. The engine outputs (acknowledgements, fills, book updates) are a deterministic function of the inputs, so we do not need to store them in the journal, although we archive them separately for audit convenience.

3.3 Market data

Every accepted add, cancel, replace and trade changes the book or the tape, so we produce about one market data message per inbound message plus the trades: 300 million + 15 million, about 315 million, which we round to 320 million per day. At about 40 bytes per message that is 320,000,000 x 40 B = 12.8 GB per day, or 12.8 GB x 252 = about 3.2 TB per year. At peak, 250,000 messages per second x 40 B = 10 MB per second, which is 80 megabits per second per full-depth feed. That is a small stream per subscriber. The problem is the multiplier: if 2,000 subscribers each received their own copy over unicast, the exchange would have to send 2,000 x 10 MB/s = 20 GB/s, which is 160 gigabits per second. So we use multicast (one copy, replicated by network switches) as section 11 explains.

3.4 Memory

At any moment suppose 10,000 orders rest per symbol on average, so 5,000 x 10,000 = 50 million resting orders. At about 64 bytes per order record, that is 50,000,000 x 64 B = 3.2 GB. A hash index from order id to order record adds roughly 16 B per entry: 0.8 GB. Total working set is about 4 GB for the entire exchange, partitioned across engines into a few hundred megabytes each. It fits in RAM, and the hot part (the top few price levels of active symbols) fits in a CPU cache. The whole book lives in memory and the disk is only a log.

3.5 Replay time

If recovery replays the whole day's journal at 1 million events per second (a conservative rate since replay skips network and disk work), 300 million events take 300 seconds, five minutes. With a snapshot of engine state every 5 minutes, recovery is a snapshot load plus at most five minutes of journal: 5 x 60 x 12,800 = about 3.8 million events on average, which replays in under 4 seconds at 1 million per second. This is the number that justifies "recovery by replay".

4. API design

Participants do not call REST endpoints. They hold a long-lived session to an order gateway using a compact binary protocol (the industry uses FIX for broad compatibility and exchange-specific binary protocols such as OUCH or BOE-style formats for speed; see Chapter 7 for the cost of text versus binary encodings, and Chapter 3 for TCP behaviour). A TCP session gives ordered, reliable delivery of each participant's messages, and a session-level sequence number lets either side detect a gap after a reconnect. The message set is small.

// Participant -> exchange (order entry session, TCP, binary)
Logon(participant_id, credentials, next_expected_seq)
NewOrder(cl_ord_id, symbol, side, type, price_int, qty, tif, account, flags)
CancelOrder(cl_ord_id, orig_cl_ord_id)
ReplaceOrder(cl_ord_id, orig_cl_ord_id, new_price_int, new_qty)
MassCancel(participant_id, [symbol])        // kill switch for a firm
Heartbeat / Logout

// Exchange -> participant (same session)
Accepted(cl_ord_id, order_id, exchange_ts, seq)
Rejected(cl_ord_id, reason_code)
Executed(order_id, trade_id, fill_price_int, fill_qty, leaves_qty, liquidity_flag, exchange_ts)
Cancelled(order_id, reason)     // user cancel, IOC remainder, self-trade prevention, halt
Replaced(order_id, new_price_int, new_qty)

// Exchange -> everyone (market data, UDP multicast, binary)
AddOrder(seq, symbol, order_id, side, price_int, qty)
DeleteOrder(seq, order_id)  ModifyOrder(seq, order_id, qty)  Execute(seq, order_id, qty, trade_id)
Trade(seq, symbol, price_int, qty, trade_id)    Halt(seq, symbol, state)
Snapshot(symbol, last_seq, [levels or orders])     // over a separate TCP/UDP recovery channel

Notes on the choices. Prices are integers (price in ticks or in units of a fixed fraction such as 1/10,000 of a currency unit), never floating point, because binary floating point cannot represent 0.10 exactly and comparisons at price boundaries must be exact. The client order id (cl_ord_id) is chosen by the participant and must be unique per session per day. It is the idempotency key: if the participant resends an order after a disconnect, the gateway recognizes the id and returns the original outcome instead of creating a second order (see Chapter 32). The exchange order id is assigned inside the engine and is the key everything downstream uses. Every outbound message carries a sequence number, per session on order entry and per channel on market data. The liquidity flag on a fill says whether the order added or removed liquidity, which drives maker-taker fees.

5. Data model and storage choice

Unusually, the "database" of this system is a data structure in memory plus an append-only file. There is no relational store on the order path, and this is a decision to defend, not an omission. A database commit costs hundreds of microseconds to milliseconds even on fast disks, locks add contention, and the engine would spend its time in the storage layer instead of matching. We use the log-plus-state-machine pattern from Chapter 36 (event sourcing) and the write-ahead-log idea from Chapter 19.

5.1 The order record

The engine's in-memory order is a compact, fixed-size struct: order_id (8 B), participant_id (4 B), side and flags (1 B), price (8 B integer), remaining_qty (4 to 8 B), original_qty, arrival_seq (8 B, the sequencer's number, which is also the time priority), and the intrusive prev and next pointers or indices that link it into its price level's queue. Using indices into a pre-allocated array instead of heap pointers avoids garbage collection, avoids allocation on the hot path, and keeps neighbouring orders close together in memory.

5.2 The book

Each side of each symbol is a set of price levels. A price level is a FIFO queue of orders at that price plus a running total quantity. The bids are ordered from highest price down; the asks from lowest price up. The best bid and best ask are the "top of book", and their difference is the spread. We discuss the exact structure in section 8.

Key idea Because the book is derived state, correctness lives in the log. If the log is complete and ordered, the engine's memory is disposable: a crashed engine is replaced by loading a snapshot and replaying the tail. This is why we can keep the book in plain RAM without any fear of losing it.

6. A first simple design, then the real one

6.1 The naive design

The first design a candidate thinks of is a web-style service: participants send HTTPS requests to a load-balanced pool of stateless order servers, which read and write orders in a relational database, and a matching job queries "best opposite orders" with SQL inside a transaction. It would work for a toy and fails for an exchange for four reasons.

  • No global order. With many order servers and no single sequencer, "who arrived first" is decided by clock skew and network luck. That is unfair and unauditable.
  • Locks and contention. The best bid of a popular symbol is one row that every transaction wants to modify. Row locks serialize them anyway, but with large overhead (Chapter 18).
  • Latency. Each order costs several network round trips and a durable commit: milliseconds, three orders of magnitude over the target.
  • Non-determinism. The result depends on thread timing and query plans, so the outcome cannot be reproduced for an audit or a dispute.

The lesson: matching is an inherently sequential problem per symbol. Parallelism comes from partitioning by symbol, not from concurrency within a book. The single-threaded loop that processes an ordered stream is faster than any lock-based parallel design because it never waits.

6.2 The real design

The scaled design is a pipeline of small, specialized components joined by ordered streams:

  1. Order gateways terminate participant sessions, authenticate, validate syntax, apply pre-trade risk checks (fat-finger limits, credit limits), and translate to the internal binary format.
  2. The sequencer stamps each accepted inbound message with a monotonically increasing sequence number and a timestamp, and appends it to the journal. This is the moment of truth: the sequence number is the official arrival order.
  3. The matching engine consumes the sequenced stream and applies each message to the in-memory books in order, single-threaded, and emits output events (acks, fills, book updates, trades).
  4. A hot standby engine receives the same sequenced stream and applies it too, so its state is identical at all times. A third copy at the disaster recovery site applies it asynchronously.
  5. The market data publisher turns book events into multicast packets. Drop copy and clearing feeds receive trades.

7. Request flow: the life of an order

Follow one limit order, "buy 300 shares of ACME at 100.01", through the system.

  1. Arrive. The participant's session sends NewOrder. The gateway checks the session sequence number, authenticates (session credentials were verified at logon), and looks up the cl_ord_id in its small per-session table to catch a duplicate resend.
  2. Validate and risk-check. The gateway checks tick size, lot size, price band around the reference price, order size against the firm's per-order limit, and the firm's remaining credit or position limit. Rejected orders get a Rejected reply here and never reach the sequencer, which keeps the core stream clean. These checks must be fast (counters in memory, a few hundred nanoseconds), which is why risk limits are updated incrementally by the gateway itself rather than queried from a database.
  3. Sequence. The sequencer takes the validated message, assigns the next sequence number (say 9,000,001) and a timestamp from a hardware-synchronized clock, and writes it to the journal and to the replication stream.
  4. Replicate. The sequenced message is sent to the primary engine, the hot standby and the journal writer. We acknowledge to the engine only once the message is durable under our policy (section 10.3).
  5. Match. The engine finds the symbol's book, sees that the best ask is 100.01 with 100 + 400 + 100 shares queued, and matches: 100 against order D (fully filled, removed), then 200 against E (E has 200 left). The buy order is fully filled (300 = 100 + 200). Each match produces an Execute event at the resting order's price, 100.01.
  6. Output. The engine emits, in this order: the Accepted for the new order, two executions (one per counterparty side), and market data events (delete D, modify E, trade). All carry the input's sequence number as their cause.
  7. Deliver. The gateway routes acks and fills to the owning sessions. The publisher batches the market data events into multicast packets. The clearing feed gets the trade. The participant sees its fill typically tens of microseconds after sending.

If the sequencer is removed, steps 5 and 6 cannot agree on order across replicas.

Cancel flow is simpler and, critically, must be at least as fast as new order flow: a market maker that cannot cancel quickly is exposed to loss. The gateway forwards Cancel through the sequencer like any other input. The engine looks up the order id in its hash index, unlinks it from its price level in constant time (that is why the level queue is a doubly linked list), and emits Cancelled and a market data delete. If the order has already been fully filled by an earlier-sequenced message, the cancel is rejected as "too late to cancel". The sequence number decides, with no ambiguity, who won the race between a cancel and a fill.

8. Deep dive 1: the order book and matching rules

8.1 The structure

An order book must support four operations quickly: add an order at a price (usually near the top of the book), remove the best order (matching), cancel an arbitrary order by id, and read the best price. The standard solution is a pair of structures per side.

  • A price-ordered index of active levels. For an equity with a small number of distinct active prices, a plain array indexed by price tick (offset from a reference price) gives O(1) access for prices near the market, with a fallback ordered tree or skip list for far-away prices (Chapter 59). A balanced tree alone gives O(log P), where P is the number of levels; in practice P is a few dozen near the touch, so the cost is a handful of cache misses.
  • Per level, a doubly linked FIFO queue of orders with a cached total quantity. Append at the tail is O(1), and cancel by id is O(1) because the order knows its neighbours.
  • A hash map from order id to order record for cancels and replaces.
  • Cached best bid and best ask pointers, updated when a level empties or a better level appears.

8.2 The matching algorithm

For an incoming order, the engine runs this loop. If it is a buy, compare against the lowest ask; while the order has remaining quantity and the best ask price is at or below the buy's limit (or the order is a market order), take the oldest order at that level, trade min(incoming_remaining, resting_remaining) at the resting order's price, reduce both quantities, remove the resting order if it is empty, and emit events. If the best level empties, move to the next level. When the loop ends, any remainder rests on the book (for a limit day order), is cancelled (IOC or market), or the entire order is rejected if FOK could not be filled completely. FOK needs a pre-check: sum available quantity at acceptable prices before trading anything, so that no partial trade ever has to be undone.

Executing at the resting order's price is deliberate: the resting order showed its price first, and the aggressor who crosses gets "price improvement" if the book has better prices than its limit. The side that arrived second is called the taker (removes liquidity) and the resting side the maker (adds liquidity), which exchanges price differently.

RuleBehaviourProsConsUsed by

We choose price-time because the problem statement asks for the classic CLOB, it maps to the simplest correct data structure, and the fairness story is one sentence: first in, first out. The code structure (level queue plus allocation function) lets us swap the allocation function per product.

8.4 Details that interviewers probe

  • Self-trade prevention. If the incoming order would match a resting order from the same participant, the engine applies the configured policy (cancel the newest, cancel the oldest, cancel both, or decrement). Without it a firm could wash-trade by accident or on purpose.
  • Auctions. At the open and close, many exchanges collect orders for a period and then compute a single clearing price that maximizes executable volume, breaking ties with rules such as minimum imbalance. Auction logic is another state in the engine's per-symbol state machine (pre-open, auction call, continuous, halted, closed), switched by sequenced control messages, so it stays deterministic.
  • Circuit breakers. If the price moves more than a band (for example 5 percent) within a window, the symbol enters a halt or a short auction. The trigger is evaluated inside the engine, and the halt is itself a sequenced event, so every replica and subscriber sees the halt at the same point in the stream.
  • Order types beyond limit and market. Stop orders (dormant until a trigger price trades), iceberg orders (only a slice displayed, with the hidden part losing time priority when replenished), pegged orders (price follows the best bid). Each is an extension of the state machine and must never read the wall clock.
  • Decimal prices and rounding. All arithmetic is on integers. Notional value (price times quantity) uses a wide integer to avoid overflow.

9. Deep dive 2: the sequencer, determinism and the low-latency core

9.1 Why a sequencer

The sequencer is the system's single source of ordering. Its job is deliberately tiny: take validated messages from the gateways, assign consecutive sequence numbers, timestamp them, append them to the journal, and publish the ordered stream. By funnelling everything through one point we get fairness (one definition of "earlier"), determinism (all replicas see the same order), and a natural audit log. The concern is that it looks like a single point of failure and a bottleneck. It is neither, for two reasons. At 250,000 messages per second peak and about 64 bytes each, the sequencer handles 16 MB per second, trivial for one core and one NIC. And it is replicated: the sequencer itself has a hot standby and the sequence is only "official" once persisted and replicated (section 10).

The sequencer's ordering decision is the "arrival" time. Gateways connect over equal-length cables inside the same data centre, and some exchanges even equalize cable lengths so no participant gains by being closer. Order of arrival at the sequencer is the order of the exchange's fairness definition.

9.2 Why one thread per order book

Imagine the alternative: many threads matching the same book under locks. Each lock operation costs tens to hundreds of nanoseconds when uncontended and microseconds when contended, because cores must transfer cache lines and the operating system may deschedule a lock holder. Worse, threads reordering is non-deterministic: the same inputs could produce different trades on different runs. The single-writer principle (popularized by the LMAX Disruptor architecture and the "mechanical sympathy" school) avoids all of it: one thread owns the data, so there are no locks, no atomic operations on the hot path, the data stays in that core's L1 and L2 cache, and the result is a pure function of the input order.

The LMAX team reported processing on the order of six million orders per second on one thread with its business logic loop, which agrees with our estimate that one core could handle our entire exchange. Treat the exact number as a vendor-reported order of magnitude, not as a guarantee.

10. Deep dive 3: replication, determinism and recovery by replay

10.1 The state-machine argument

The engine is a deterministic function: (state, input) -> (new state, outputs). If two engines start from the same state and consume the same ordered input stream, they produce identical outputs and identical state at every step. This is the replicated state machine idea behind consensus-based systems (Chapter 29) and event sourcing (Chapter 36). It gives us three powers from one mechanism: a hot standby (apply the stream live), recovery (apply the stream from a snapshot), and testing and audit (replay a past day and diff the outputs).

Determinism has rules the code must obey. No reading the wall clock inside the engine (the sequencer stamps time into the message, and the engine uses that). No random numbers. No iteration over unordered hash maps where order affects output. No dependence on thread timing or on floating-point rounding that differs between CPUs. No calls to external services. Order ids are assigned from a counter inside the state, not from a UUID generator. A single violated rule causes a standby that quietly diverges from the primary, which is catastrophic and often only discovered at failover. So we continuously compare: the standby computes a rolling hash of its output events and the primary does too; they exchange hashes every second, and a mismatch raises a page.

10.2 Snapshots and replay

A snapshot is a consistent dump of all books plus the sequence number of the last applied message. Because the engine is single-threaded, taking one is easy: at a defined sequence number, fork the process (copy-on-write) or write the state while the next messages queue briefly, and record the number. Snapshots are taken on the standby, not the primary, so the primary's latency is untouched. Recovery then is: load the newest snapshot, say at sequence 8,950,000, then read the journal from 8,950,001 forward and apply each message. By section 3.5, the tail after a 5-minute snapshot is about 3.8 million messages, replayed in under 4 seconds. Replay must be exactly the same code path as live processing; a special "recovery mode" that takes shortcuts is a source of divergence.

10.3 Durability policy: what does "accepted" mean?

The sequencer must decide when a message is considered committed and may be passed to the engine. This is the central latency versus durability tradeoff, compared in the table.

10.4 Split brain and fencing

If the standby promotes itself because it cannot hear the primary, while the primary is actually alive behind a network partition, we have two engines that both think they are in charge: split brain. Each would accept different orders and publish different trades. The defence is a monotonically increasing epoch, held by a small coordination service (Chapter 30, Case study 21). Promotion requires obtaining epoch N+1; gateways, publisher and downstream consumers reject any message tagged with an older epoch; and the promoter tries to power off the old machine through an out-of-band controller before it begins. This is the fencing-token idea, applied to a whole engine. The detailed election protocol is in Chapter 29.

11. Deep dive 4: market data fan-out

11.1 The problem

Every market participant needs the same stream of book changes at nearly the same instant. Fairness again: if subscriber X receives an update 50 microseconds after subscriber Y, Y has an unfair advantage. Delivering the same bytes to 2,000 consumers with minimal and equal delay is the second core difficulty, and the answer is to push replication into the network.

11.2 Multicast, sequence numbers and gap recovery

The publisher sends each message once, to a multicast group address over UDP. Network switches duplicate the packet to every port that has subscribed, in hardware, with the same delay for each port (and some exchanges equalize cable lengths in the collocation room for the same reason). Our 10 MB per second peak is therefore transmitted once, not 2,000 times. UDP has no retransmission, so reliability is built at the application level, as in the well-known ITCH-style and similar feeds.

  • Sequence numbers. Every packet carries a channel sequence number and the count of messages inside. A receiver that sees 1,204 then 1,206 knows 1,205 is missing.
  • A/B arbitration. The same stream is sent on two independent multicast groups, A and B, over separate switches and links. Receivers read both and take whichever copy of each sequence number arrives first. A packet dropped on one path is almost always present on the other, so most loss never becomes visible. This is cheap, fast redundancy.
  • Gap recovery. If both copies are lost, the receiver asks a retransmission server over TCP (or a UDP request channel) for the missing range. The retransmission server is a separate process with a ring of the last few minutes of packets, so it never loads the matching path.
  • Snapshots. A subscriber that starts late or falls too far behind cannot replay from the open. It fetches a snapshot of the book (the current levels) tagged with the sequence number it reflects, then applies live messages with a greater sequence number, discarding duplicates. Snapshots are served from a separate service that itself consumes the feed, so it adds no load to the engine.
  • Heartbeats. When quiet, the feed sends periodic heartbeats with the current sequence number so that silence can be distinguished from loss.

11.3 Tiers of data

Not everyone needs everything. We offer tiers: the full order-by-order depth feed (every add, delete, modify and execute, which lets a subscriber rebuild the entire book), a top-of-book feed (best bid and offer and last trade, a tiny fraction of the bandwidth), and a delayed or consolidated feed for retail display (delayed by a regulatory period such as 15 minutes) distributed over ordinary TCP and WebSockets by a separate service tier (Chapter 6). The retail tier is the one that does scale like a web system: it subscribes to our feed once, fans out to millions of browsers through a pub-sub layer, and may throttle or conflate updates (send only the latest price per symbol per 100 ms). The conflation is allowed there and forbidden in the depth feed. Fan-out patterns are in Chapter 35 and Chapter 60.

12. Scaling, partitioning and bottlenecks

12.1 Partition by symbol

Matching has no cross-symbol dependency in the simple CLOB case: an order for ACME touches only the ACME book. That makes symbol the shard key (Chapter 25). We run 10 partitions, each owning about 500 symbols, each partition with its own sequencer pair, engine primary, standby and journal. A symbol-to-partition map, a small reference table loaded by the gateways at start of day, routes each order. The map is static during the session, which removes any need for dynamic rebalancing mid-day. Moves happen overnight when a heavy symbol is reassigned.

Why 10 when one thread could do it? First, blast radius: a bug triggered by one symbol takes down 500 symbols, not 5,000. Second, tail latency isolation: a flood in one symbol does not delay another partition's orders. Third, headroom: peak is 250,000 per second in total, so each partition sees an average of 25,000 per second at peak, about 2.5 percent of one core's capacity, leaving large safety margin for a 10x event. Fourth, operational flexibility: partitions can be upgraded one at a time. Fifth, the journal and publishing per partition are independent streams, so the consumer can subscribe only to the channels it needs.

Without the map being static, orders could be sent to two engines for the same symbol.

12.2 Hot symbols

Skew is the rule: a few hundred symbols carry most of the traffic. A single hot symbol on its own partition might peak at 12,500 per second, which is still easy. Larger loads, such as an index future with several million messages per second, push one engine to its limit. Options then are to dedicate a machine to that symbol, split the pipeline into stages (gateway decode and risk on many cores, matching on one), and shrink the per-message work; we do not shard a single book across threads because that destroys determinism. If the hardware ceiling is reached, the design says: speed up the single thread (leaner structures, FPGA), not parallelize it.

12.3 Other bottlenecks

  • Gateways. They scale out horizontally: sessions are partitioned by participant, and each gateway does CPU-heavy risk and encoding. The sequencer pairs the stream from many gateways; if one sequencer's NIC becomes a limit, the partition is split.
  • Risk state. A firm may send orders through many gateways, so its risk limit must be shared. We use per-firm risk "budgets" allotted to each gateway in chunks (similar to distributed token buckets, Chapter 16) with a conservative reservation, or route a firm's sessions to the same gateway.
  • Journal disk. 19.2 GB per day is a trivial sequential write rate (about 0.8 MB/s average, 16 MB/s at peak), so disks are not the constraint; fsync batching is. We batch by time (every few hundred microseconds) off the critical path.
  • Network. Each partition has its own links; the market data switches are the shared resource, so they are sized for line-rate bursts at the opening.

13.1 Consistency and idempotency decisions

  • Per-symbol linearizability. Every event for a symbol is totally ordered by sequence number. Reads of the book (the market data) lag the engine but are always a prefix of the true event sequence, never out of order.
  • No cross-symbol consistency promise. Two partitions have independent sequences. A consolidated tape that merges partitions is ordered by (partition timestamp, partition sequence), which is a best-effort total order with tolerances. This is acceptable because no trade depends on another symbol's order (Chapter 28).
  • Exactly-once effect through idempotency. The wire is at-least-once (resends after disconnect), the effect is exactly-once because of the cl_ord_id table and the session sequence numbers (Chapter 32). The trade id is derived from the sequence number of the input that caused it plus an index within the message, so replaying produces the same trade ids and downstream systems dedupe on them.
  • Trade finality. A trade, once the engine emits it, is final and sent to clearing. Cancelling a trade ("busting") is a separate, manual, rules-governed event, not an engine rollback.

13.2 Multi-region

The matching engines live in one data centre, because cross-region latency (tens of milliseconds) would ruin fairness and speed, and an active-active matching of one book across regions would require consensus on every order (Chapter 26). The DR site receives the journal stream asynchronously (a few milliseconds behind within a metro area, more across distance) and is rehearsed regularly. The failover to DR is a deliberate operational decision with participant notification, not an automatic flip, because of the possible lost tail. Different exchanges run different regions for different products, so the multi-region story is "each product has one home, with a DR sibling" (Chapter 41).

14. Security, monitoring, cost

14.1 Security and abuse

  • Authentication and authorization. Sessions use mutual TLS or equivalent credentials on private cross-connects, and each session is bound to a participant id and a list of allowed symbols and order types (Chapter 55). The gateway stamps the participant id; the engine never trusts an id from the payload.
  • Network isolation. Participants reach the exchange only through dedicated lines or collocated cross-connects. The order entry network is separate from the market data network and from administrative access.
  • Pre-trade risk checks protect both the firm and the market: maximum order size, maximum notional, price collar, rate limits and a firm-level kill switch. These are often legally required.
  • Market abuse. Spoofing (placing orders without intent to trade), wash trades, and quote stuffing are detected by surveillance that consumes the audit stream offline; the engine only enforces the cheap preventative controls (self-trade prevention, order-to-trade ratio fees).
  • Integrity of the journal. The journal is append-only and hash-chained (each batch includes a hash of the previous), so tampering is detectable by auditors.

14.2 Monitoring and SLOs

The golden signals here are latency distributions, not request counts (Chapter 54). We track: wire-to-wire latency per stage with p50, p99, p99.9 and max, taken from hardware timestamps; sequencer queue depth; standby replication lag (target: zero messages, alert at a few); journal flush lag; output-hash agreement between primary and standby; market data gap rate per subscriber channel; gateway reject rates by reason; and book-integrity checks (the sum of resting quantity per level equals the sum of orders in the level, crossed-book detection: best bid never above best ask outside an auction). Example SLOs: 99.99 percent of orders acknowledged within 100 microseconds during continuous trading; zero lost or duplicated acknowledged messages; failover to a caught-up standby within 5 seconds; market data gap-free for 99.999 percent of packets before recovery.

Continuous verification matters as much as metrics: every night the day's journal is replayed through the production binary on a test cluster and the output compared byte for byte with the archived outputs. Any difference is a determinism bug found at night instead of at failover.

14.3 Cost notes

The expensive parts are not storage or compute volume but the specialized pieces: collocation space with power and cooling, kernel bypass NICs, low-latency switches, GPS clocks, redundant fibre cross-connects, and a 24-hour operations staff. The software footprint is small: perhaps 10 partitions times 3 machines (primary, standby, DR) of high clock speed CPUs with 64 to 256 GB of RAM each, plus gateway farms. Storage for 4.8 TB per year of journal and 3.2 TB per year of market data is a rounding error; they age to object storage (Chapter 21) after the regulated hot period. Revenue comes from trading fees, data sales and collocation, so latency is a product spec worth paying for.

15. Evolution, phasing and alternatives

15.1 Build order

  1. Phase 1: the deterministic core. One partition, one engine, the book data structure, price-time matching, limit and market orders, a file journal and replay tool. Test with property tests (random order streams checked against a slow reference implementation) and with replay.
  2. Phase 2: gateways and sequencer. Binary protocol, sessions with sequence numbers, pre-trade risk, idempotency by cl_ord_id. Add the sequencer with its journal.
  3. Phase 3: market data. Multicast publisher, A/B feeds, gap recovery, snapshots.
  4. Phase 4: redundancy. Hot standby, output-hash comparison, fencing epochs, DR replication, rehearsed failover.
  5. Phase 5: more order types and auctions, circuit breakers, more partitions, tiered data products.
  6. Phase 6: latency work. Kernel bypass, core pinning, cache tuning, possibly FPGA gateways, once a metric shows where the time goes.

15.2 At 10x scale

At 2.5 million messages per second peak, we add partitions (each still easily within one thread) and scale the gateway farm and market data network. If one symbol becomes ten times hotter, we dedicate hardware to it and pipeline its stages. If we added derivatives with implied spread matching, orders in one product would create implied orders in another, so those products have to share a partition or use a deterministic cross-partition mechanism. For more participants, the multicast scheme is unchanged; the retail fan-out tier scales horizontally in the usual web way. For global distribution, we would not stretch one matching engine across regions but run regional venues and connect them with smart order routing at the brokers.

16. Interview Q&A

Why is the matching engine single-threaded? Is that not a bottleneck?

Matching for one symbol is inherently sequential, because each order's result depends on the book left by the previous order. A multithreaded design needs locks or atomic operations on the same price levels, and the contention costs more than the work itself, while also making the outcome depend on thread timing. A single thread that owns the data keeps it in its CPU cache, takes no locks and is deterministic, and can process on the order of a million orders per second, while our whole peak is 250,000 per second. We get parallelism where it is safe, across symbols through partitioning, and not within one book.

What exactly does the sequencer do, and is it a single point of failure?

It assigns a gap-free increasing sequence number and a timestamp to each validated inbound message and appends it to the journal and replication stream. That number is the official arrival order, which gives fairness, determinism and audit. It is a logical single point, but not a single machine: a hot standby holds the same stream and the next-number state, and promotion uses an epoch so that the old instance is fenced. Its throughput need is only about 16 MB per second at peak, so it is not a capacity bottleneck.

How do you recover after a crash without losing orders?

The journal of sequenced inputs is the source of truth, and the engine is a deterministic function of it. Because a message is not processed until it is on the standby and the journal writer, every acknowledged order is recoverable. In the common case the standby simply becomes primary since it is already caught up. For a fresh node we load the latest snapshot, which records the sequence number it reflects, then replay the journal after that number through the same code path as live traffic. With 5-minute snapshots the tail is about 3.8 million messages, so recovery takes seconds.

How do you keep the standby from silently diverging from the primary?

Determinism is enforced by rules: no wall clock reads in the engine, no randomness, no iteration over unordered collections that affects output, and ids generated from internal counters. We check it with rolling hashes of output events that the primary and standby exchange every second, so a divergence raises an alert within a second, not at failover. Every night we also replay the day's journal through the production binary and compare the output with what the live system produced. Any new release must pass the same replay test on recent production days before deployment.

How do you deliver market data to thousands of subscribers fairly and cheaply?

We use UDP multicast so the exchange sends each packet once and the network switches replicate it with the same delay to every subscriber port, which keeps outbound traffic at 10 MB per second per feed rather than 20 GB per second of unicast. Reliability is rebuilt on top: sequence numbers to detect gaps, two independent paths (A and B) arbitrated by the receiver, a TCP retransmission service for rare double loss, and a snapshot service for late joiners. Slow consumers cannot slow the engine because multicast has no per-receiver queue; they simply recover via snapshot.

What happens if the primary engine is partitioned from the standby but both are alive?

That is split brain: the standby may promote itself while the old primary keeps running. We prevent it with a monotonically increasing epoch obtained from a small consensus-backed coordinator, and every downstream component (gateways, publisher, clearing) rejects messages carrying an older epoch. The promoter also fences the old node out-of-band by powering it off or isolating its ports before it starts. If the coordinator cannot be reached by either side, trading halts rather than risking two sets of trades, which favours consistency over availability.

How do you handle a cancel racing with a fill?

The sequencer's order decides it, with no ambiguity. If the cancel is sequenced before the incoming order that would match, the resting order is gone and the incoming order does not trade with it. If the fill is sequenced first, the order is gone by the time the cancel is processed, and the participant receives a "too late to cancel" reject plus the execution report. The participant sees both messages in the same session sequence, so its own state converges with the exchange.

How would you test an engine like this?

Several layers. Unit and property tests generate random order streams and compare the engine's trades and final book with a simple, slow reference implementation (a sorted list), asserting invariants such as no crossed book, quantity conservation, and price-time priority. Replay tests run recorded production days through the new binary and diff outputs byte for byte. Fault injection kills the primary mid-stream, drops replication packets and delays the standby to verify failover and idempotent resends. Performance tests replay at peak and 10x rates while recording latency percentiles with hardware timestamps, and fail the build on a regression of the tail.

Why not use a database or Kafka for the order flow?

Both give durable ordered logs and are the right tools for downstream stages such as clearing, surveillance and analytics. On the hot path they cost milliseconds because of network round trips, broker replication and commit protocols, while our budget is tens of microseconds. We also want the book in memory and the log local and append-only. So we use a purpose-built journal for the matching path and stream the same events into Kafka and a database for the consumers that need queries, long retention and replay by many independent readers.

How do you make the exchange fair to participants at different distances?

We use collocation with equal-length cables from every rack to the gateways and the market data switches, so that propagation delay does not favour a participant. All orders pass through one sequencer, so arrival order is defined by one place, and the market data is replicated by switch hardware at equal delay. Pre-trade checks at the gateway are deterministic in cost, and no participant gets a special faster path. Some venues add a deliberately small, uniform delay (a speed bump) to blunt the advantage of the very fastest traders, which is a policy choice that we can add at the gateway.

What changes if the interviewer asks for a crypto or cloud-hosted exchange?

The logical design stays: sequencer, deterministic engine, journal, snapshot and replay. The physical choices change. Without multicast or kernel bypass, we publish market data over WebSockets from a fan-out tier with conflation, accept millisecond-class latency, and use a replicated log (for example Raft or a managed log service) as the sequencer so that failover is automatic across availability zones. We also gain easier elasticity for the gateway and data tiers but must manage noisy neighbours and clock quality, so we pin dedicated instances and use cloud time-sync services.

17. Connects to and recap

Recap

  • The exchange is a deterministic state machine: an ordered input log feeds a single-threaded engine per symbol, and everything else (replication, recovery, audit, testing) is replay.
  • A sequencer gives every message one global order; it is replicated and fenced by an epoch so it is neither a capacity nor an availability risk (about 16 MB per second at peak).
  • The book is a pair of price-ordered sets of FIFO queues plus an order id index, held in pre-allocated memory; matching is price-time priority at the resting order's price, with prices as integers.
  • Estimation: 300 M messages per day, 12,800 per second average, 250,000 peak, 15 M trades, 19.2 GB per day of journal, 4 GB of book memory, replay of a 5-minute tail in under 4 seconds.
  • Durability means present on two independent machines before processing, with the journal flushed in the background; the DR site is asynchronous and the one scenario where RPO is not zero.
  • Market data goes out by UDP multicast with sequence numbers, A/B paths, gap retransmission and snapshots, keeping fan-out cost at one copy and delay equal for all.
  • Scale by partitioning symbols across independent pipelines for isolation and headroom, not by sharding a single book across threads.
  • Latency is engineered in microseconds: kernel bypass, pinned cores, no garbage collection, cache-friendly layout, and tails measured at p99.9 and max.
