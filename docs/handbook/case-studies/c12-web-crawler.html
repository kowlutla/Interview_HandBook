Case study 12 · Worked solutions

Design a Web Crawler

A web crawler discovers pages by following links, downloads them politely, and hands them to an indexing system. This worked solution designs one that fetches 1 billion pages a month, and spends most of its time on the parts an interviewer probes: the URL frontier, politeness, deduplication, spider traps, and recrawl scheduling.

How to approach this problem (read this first)

Fetching 400 pages a second (1 billion a month) is the easy part. The interviewer is looking at what happens around the fetch. First, can you design the URL frontier so that important pages go first but no single host is ever hit faster than it allows? Second, can you cut the 16,000 to 40,000 link checks per second down with normalization, a Bloom filter and content fingerprints, and survive spider traps? Third, can you decide when to recrawl each page, given a budget that only covers each page every few months on average? Politeness and robots.txt, partitioning by host, and what happens when a fetcher dies run through all three.

The thinking order, step by step

  1. Ask what the crawler feeds. Ask the purpose (a search index), the scale, content types, JavaScript pages, freshness, and whether robots.txt must be obeyed. You say: "This feeds a search index at 1 billion pages a month, HTML first, polite by default, with a separate path for JavaScript pages." Why now: freshness and politeness are the two forces the frontier balances.
  2. Estimate the fetch rate, then the link rate. Compute 385 pages per second average, 1,000 at peak, 1,000 connections by Little's law, then 40 links per page, so 16,000 URL checks a second. You say: "Fetching is modest, but checking whether each link is new is the heavier job." Why now: this points your deep dive at dedup, not at HTTP.
  3. Do the politeness arithmetic. Show that at one request per second per host, 1,000 pages per second needs 1,000 hosts at once, and one 100 million URL host would take years. You say: "Politeness caps freshness for big sites, so I need a per-host crawl budget." Why now: this proves the frontier needs per-host state.
  4. Draft the internal contracts. Name a lease and acknowledge call on the frontier, a fetch-result event, and a discovered-links event. You say: "The frontier hands out leases, not deletions, so a dead worker's URLs reappear." Why now: it shows failure handling before any diagram.
  5. Draw the single-machine loop and break it. Queue, fetch, parse, seen set, disk. List one thread, FIFO impolite, FIFO ignores importance, seen set too big, no recrawl. You say: "Each failure becomes the frontier, async fetchers, a Bloom filter, and a recrawl scheduler." Why now: it gives the evolution path.
  6. Draw the scaled pipeline and partition by host. Frontier, fetchers, raw store, event log, parser, URL filter, content dedup, indexer, all partitioned by host hash. You say: "The frontier is the brain, fetchers are stateless, and the log decouples stages." Why now: all politeness state for a host lives in one place.
  7. Deep dive the frontier. Explain front queues by priority, back queues by host, and a heap by next allowed time. You say: "Priority picks what, the host heap says when, so important URLs do not hammer one site." Why now: this is the question most interviewers ask.
  8. Deep dive dedup and traps. Normalize, then a Bloom filter at 10 bits per URL, exact check in the store, exact content hash, then simhash. List trap defenses. You say: "A one percent false positive only skips a few new URLs, and the per-host budget bounds any trap." Why now: it covers the largest QPS in the system.
  9. Deep dive recrawl and failures. Adaptive intervals with conditional GET, budget by tier, then fetcher, parser and partition failures. You say: "I write the body before publishing the event, so an event always points at data that exists." Why now: it closes with correctness.

The decision points

  • One global priority queue or two levels. Ask yourself: does the top priority belong to a few hosts? Yes, so use front queues for priority and per-host back queues for politeness.
  • Partition by URL hash or host hash. Ask yourself: where must the per-host rate limit live? On one machine, so partition by host and make the limit a local variable.
  • Exact set or Bloom filter for seen URLs. Ask yourself: can I afford to skip one percent of new URLs? Yes, because pages have many inbound links, so use a Bloom filter in memory and the store as the truth.
  • Fixed or adaptive recrawl. Ask yourself: do pages change at very different rates? Yes, so halve the interval on change, stretch it on no change, and use conditional GET.
  • Fetch JavaScript pages inline or separately. Ask yourself: how much more does a render cost? 50 to 100 times more, so route only the pages that need it to a render pool.

Common mistakes on this problem

  • Using a plain FIFO or global priority queue. Fix: use front queues for priority and back queues per host.
  • Partitioning by URL hash. Fix: partition by host hash so politeness is local.
  • Storing every seen URL in one in-memory set. Fix: use a Bloom filter per partition with the URL store as truth.
  • Ignoring spider traps. Fix: limit depth and URL length, set per-host budgets, and detect duplicate content.
  • Recrawling everything on a fixed cycle. Fix: adapt intervals by change and importance and use conditional GET.
  • Publishing the event before storing the page. Fix: write the body first, then the event, then the acknowledge.

1. Problem statement and clarifying questions

The prompt is usually one sentence: "Design a web crawler." That sentence hides many decisions, so the first minutes go to questions, as described in Chapter 1. A web crawler (also called a spider or robot) is a program that starts from a set of known URLs, downloads each page, extracts the links in it, and repeats for the newly found links. Search engines use crawlers to build their index; other users are price comparison, archives such as the Internet Archive, security scanners, and machine learning data collection.

2. Requirements and out of scope

2.1 Functional

  • Accept seed URLs and discover new URLs by extracting links from fetched pages.
  • Fetch pages over HTTP and HTTPS, follow a bounded number of redirects, and honor robots.txt rules including Crawl-delay where given.
  • Avoid downloading the same URL twice in a crawl cycle, and avoid storing duplicate content found under different URLs.
  • Recrawl pages on a schedule driven by how often they change and how important they are.
  • Store the raw page in durable storage and publish an event so the indexer can pick it up.
  • Render JavaScript-dependent pages on a separate path.

2.2 Non-functional

  • Scalability: 1 billion fetches a month, growing horizontally by adding machines.
  • Politeness: never overload a single host. A small site must not feel a crawl as an attack.
  • Robustness: the open web is hostile and broken: malformed HTML, endless redirects, tarpit servers, infinite URL spaces. Nothing a remote server does should crash or stall the crawler.
  • Extensibility: new content types (images, PDFs) plug in as new processors without redesigning the core.
  • Freshness vs. cost: spend crawl budget where change and importance are highest.
  • Fault tolerance: a machine failure must lose at most a few minutes of work and never leave URLs permanently lost or permanently stuck.

2.3 Out of scope

Ranking, the inverted index, query serving, spam classification, and full-site archival of media. We also exclude the deep web behind logins and forms. We define the handoff to the indexer but not its internals.

3. Estimation

Estimation, covered in Chapter 2, tells us which parts are hard. Here the surprise is that raw fetch rate is modest; the hard parts are the bookkeeping per URL and per host.

3.1 Throughput

  • One month is about 30 x 86,400 = 2.59 million seconds.
  • Average fetch rate: 1,000,000,000 / 2,590,000 = about 385 pages per second. We round to 400.
  • Peak (catching up after an outage, or a recrawl wave): 2.5 x 400 = 1,000 pages per second.
  • JavaScript-rendered share: 10 percent = about 40 renders per second average, 100 at peak.

3.2 Concurrency and fleet size

A fetch is mostly waiting: DNS lookup, TCP and TLS handshakes, server think time, transfer. Assume the average end-to-end fetch takes 1 second, with slow hosts and timeouts pulling the mean up. By Little's law, in-flight requests = rate x latency = 1,000/s x 1 s = about 1,000 concurrent connections at peak (we will provision for 2,000 to absorb slow hosts). An asynchronous fetcher process on one machine comfortably handles 200 to 500 concurrent connections, so we need roughly 8 to 10 fetcher machines, and we plan for 16 for headroom and failures. Headless browsers are 50 to 100 times costlier: assume one browser tab uses about 300 MB and a render takes 4 seconds, so 100 renders per second means 400 concurrent tabs, around 120 GB of RAM, or about 15 machines with 8 to 16 GB each devoted to tabs.

3.3 Bandwidth

  • Average HTML page: about 500 KB uncompressed, about 100 KB on the wire when servers send gzip or brotli (typical 4 to 5x on HTML). We cap downloads at 5 MB.
  • Download: 400/s x 100 KB = 40 MB/s average = 320 Mbit/s. Peak 1,000/s x 100 KB = 100 MB/s = 800 Mbit/s. Modest: a few 10 Gbit NICs are plenty.
  • Monthly download: 1B x 100 KB = 100 TB.

3.4 Storage

  • Raw pages: we store the compressed form (about 100 KB). 1B x 100 KB = 100 TB per month. Keeping the latest 3 versions of recrawled pages raises long-run use, but only for pages that are recrawled. Assume the crawl corpus holds 3 billion distinct pages after some months (recrawls cover the same pages repeatedly): 3B x 100 KB x about 2 average versions = 600 TB. This is plainly object storage territory (Chapter 21), with a cheap infrequent-access tier for old versions.
  • URL metadata (one row per known URL): normalized URL (about 80 bytes on average), content hash 8 bytes, simhash 8 bytes, last fetch time, next fetch time, change-rate estimate, ETag/Last-Modified hint, HTTP status, depth, priority: about 200 bytes. If the system knows 6 billion URLs (many discovered but not yet fetched): 6B x 200 B = 1.2 TB. That fits a sharded key-value store (Chapter 20) but not one machine.
  • Link discovery rate: assume 40 outgoing links per page. 400 pages/s x 40 = 16,000 URL candidates per second that must be normalized and checked for "have I seen this?". Peak: 40,000/s. This number, not the fetch rate, drives the dedup design.

3.5 Dedup memory

Exact "seen URL" set for 6 billion URLs, storing 8-byte hashes: 6B x 8 B = 48 GB, still fine for a sharded cluster. A Bloom filter (Chapter 57) at 10 bits per element and 7 hash functions gives about a 1 percent false positive rate: 6B x 10 bits = 60 Gbit = 7.5 GB total, or about 120 MB per shard when there are 64 shards. Content fingerprints: 1B simhashes x 8 bytes = 8 GB. All cheap. The case for a Bloom filter is therefore speed and cache residency, not just memory.

3.6 Politeness arithmetic

If each host is fetched at most once per second (a common default), then 1,000 pages/s needs at least 1,000 distinct hosts being crawled at the same moment. The web has hundreds of millions of hosts, so that is easy overall, but the distribution is skewed: a single large site may have 100 million URLs. At 1 request per second, that one site alone would take 100,000,000 / 86,400 = 1,157 days. So for giant hosts, politeness caps freshness, and the crawl budget per host (section 12) becomes a real policy knob. We usually negotiate higher rates through Search Console style verification or by using the host's sitemaps and conditional requests rather than hammering.

4. API design

A crawler is mostly a batch system with no end-user traffic, but it still has interfaces: a control API for operators and customers, and internal contracts between stages.

4.1 Control API

GET  /v1/urls/{urlHash}   -> { url, status, lastFetch, nextFetch, contentHash, depth }
POST /v1/recrawl          { "url": "...", "reason": "operator|sitemap_ping" }   (priority bump)
PUT  /v1/hosts/{host}/policy  { "crawlDelayMs": 2000, "maxConcurrent": 1, "dailyBudget": 50000 }

4.2 Internal contracts

  • Frontier lease: lease(partition, n, leaseSeconds) returns up to n URLs that are due, each with a leaseId. ack(leaseId, outcome, nextFetchHint) completes it; an unacknowledged lease expires and the URL becomes due again. This is the heart of failure handling.
  • Fetch result event (on the queue, Chapter 34): {url, finalUrl, status, fetchedAt, contentHash, simhash, blobKey, etag, lastModified, headers subset, redirectChain}. The body is not in the event; it lives in object storage and the event holds its key.
  • Discovered links event: {sourceUrl, links: [{url, anchorText, rel}]}, routed to the frontier by host hash.
  • Page-stored event for indexing: {url, blobKey, version, contentType, language, fetchedAt}.

6. A first, simple design

Start with the textbook loop on a single machine: a queue of URLs, a worker that pops one, fetches it, parses links, adds unseen ones to the queue, and saves the page to disk.

Walkthrough. Boxes are stages and the arrows show one page's life. 1. An operator puts seed URLs into the FIFO queue. 2. One fetcher thread pops a URL and downloads it. 3. The parser extracts links. 4. Links go to the seen set in RAM, and unseen ones loop back to the queue along the dashed arrow at the top. 5. The page is written to local disk. This is the textbook loop and is drawn so you can list how it fails: one thread gives about one page per second when we need 400 to 1,000, FIFO sends hundreds of requests to one host in a row, there is no notion of importance, the seen set outgrows memory and is lost on a crash, and nothing is ever recrawled. On the whiteboard, draw it small and write the five failures beside it. Each one is replaced by a named component in the next diagram, and removing the seen set would make the loop run forever.

Why this fails at scale, in order of how soon it hurts:

  1. One thread is slow. With 1 second per fetch you get 1 page per second. We need 400 to 1,000.
  2. FIFO order is impolite. A breadth-first queue drains the links of one site together, so the crawler sends hundreds of consecutive requests to the same host and gets banned.
  3. FIFO order ignores importance. A press release and a spam page wait in the same line.
  4. The seen set outgrows RAM and a crash loses it.
  5. No recrawl. It never revisits anything.
  6. Traps. A calendar page that links to "next month" forever will consume the whole crawl.

The rest of the design replaces each box by a distributed, policy-aware version, with the URL frontier as the replacement for the naive queue.

7. Scaled high-level architecture

The pipeline has these components: frontier, fetcher fleet with DNS cache, a renderer pool for JavaScript pages, a raw store, a parser and link extractor, a URL filter and dedup stage, a content dedup stage, and an indexing handoff. Everything is partitioned by host hash, so that all the state needed to be polite to a host (its queue, robots rules, next allowed time) lives in one place.

Walkthrough. Follow the numbers left to right. 1. Seeds and sitemaps enter the amber URL frontier, which holds priority queues, per-host queues and robots and rate state, split into partitions by host. 2. Fetchers lease due URLs. JavaScript pages go to the render pool instead. 3. Fetchers write bodies to the raw page store and publish an event on the log. 4. The parser reads events and extracts links. 5. The URL filter uses a Bloom filter and rules, and survivors are written to the URL and host store (dashed arrows back to the frontier). 6. Content dedup decides what goes to the indexer. The design choices are that the frontier is the brain and fetchers are dumb workers, and that the log decouples stages so a slow parser never stops fetching. If you remove the log, every stage blocks the next. If you remove the frontier, politeness disappears.

Two design choices frame everything. First, the frontier is the brain: all scheduling, politeness, and priority decisions happen there, and fetchers are dumb workers that only fetch what they are leased. Second, the log decouples stages so a slow parser never blocks fetching, and we can replay events if the parser had a bug (Chapter 36).

7.1 Request flow for crawling one URL

Walkthrough. The six lifelines are the frontier, a fetcher, DNS and the target site, the object store, the log and the parser. 1. The fetcher asks the frontier for URLs. 2. The frontier returns due URLs with lease ids, already filtered for politeness. 3. The fetcher resolves DNS from its cache and checks robots rules. 4. It sends a conditional GET with If-None-Match. 5. The site replies with a 200 body or a 304. 6. The fetcher stores the compressed body. 7. It publishes the fetch result with the blob key and hash. 8. It acknowledges the lease with status and hints. 9. The parser consumes the event. 10. New links go back to the frontier, routed by host hash. The order matters: storage before event before acknowledge. If the fetcher dies before step 8, the lease expires and the URL is retried, which is safe because the output is deterministic. Point at the gap between steps 7 and 8 when asked about duplicates.
  1. The frontier partition owning a set of hosts returns URLs whose host is allowed to be contacted now.
  2. The fetcher resolves the host through its DNS cache, checks the cached robots rules, and sends a conditional GET using the stored ETag or Last-Modified.
  3. On 200 it computes a content hash, writes the compressed body to object storage, and publishes the event. On 304 it only publishes a "not modified" event and the frontier lengthens the revisit interval.
  4. It acknowledges with the outcome. The frontier updates the host's nextAllowedAt and the URL's nextFetchAt.
  5. The parser consumes the event, extracts links, normalizes them, and sends them to the owning frontier partition for the filter and enqueue.
Key idea Write the body to object storage before publishing the event and acknowledging. Then an event always points at data that exists. The cost of the opposite order is an event referring to a missing blob, which is a harder failure to recover from than a duplicate blob.

8. Deep dive 1: the URL frontier

The URL frontier is the data structure that decides which URL to fetch next. It must satisfy two conflicting goals at once. Priority: important and fast-changing pages should be fetched first. Politeness: no host should be contacted faster than its allowed rate, and ideally only one connection at a time. A single global priority queue serves the first goal and wrecks the second, because the top-priority URLs often belong to a handful of hosts. The classic solution, from the Mercator crawler, is a two-level structure: front queues for priority and back queues for politeness.

Walkthrough. This is the Mercator-style frontier. 1. The prioritizer on the left scores each incoming URL from 1 to 5 and places it in one of the five amber front queues, from breaking news to rarely changing. 2. The biased selector picks a front queue at random with weights, so high priority gets most of the throughput and low priority never starves. 3. The URL moves into a back queue, one per host. Green back queues are ready now, and red ones are waiting, for example b.org must wait 1.4 s and e.com has a robots delay of 10 s. 4. The host heap, ordered by next allowed time, tells the fetcher which host may be contacted. 5. After a fetch the host re-enters the heap with a new next allowed time. The design splits what to fetch from when to fetch, which a single priority queue cannot do. Remove the back queues and one popular host gets flooded.

8.1 Front queues: priority

The prioritizer assigns each URL a score using signals that are cheap to compute: the site's importance (link counts or a PageRank-like score from the previous crawl), the URL's depth from a seed (shallower is usually more valuable), the page's historical change rate, the type (news, forum, product), and whether it came from a sitemap with a recent lastmod. The score selects one of F front queues (say 5 to 10). The biased selector then picks a front queue randomly with weights (for example 50, 25, 12, 8, 5 percent) so high priority gets most throughput but low priority never starves. Strict priority would let a flood of important URLs starve everything else forever.

8.2 Back queues: politeness

Each back queue holds URLs of exactly one host. A host heap orders hosts by nextAllowedAt. A fetcher asks for work; the frontier pops the host with the earliest time that is already in the past, hands out one URL (or a small batch for a slow-start host), and later re-inserts the host with nextAllowedAt = now + delay. Good delay choices:

  • The Crawl-delay value from robots.txt when present. Note that Google ignores this directive, but many other crawlers honor it, and honoring it is the polite default for a new crawler.
  • Otherwise a default of 1 second, adaptive: a common rule is to wait about 10 times the duration of the last fetch, so a slow struggling server is automatically relieved, and a fast CDN-backed one is crawled faster, bounded by a configured ceiling.
  • Back off sharply on 429 (Too Many Requests) and 503 responses, honoring Retry-After, with exponential backoff (1 minute, 2, 4, up to hours), and reset after success.
  • At most one in-flight connection per host unless the host is known to be a large CDN-backed site with an agreed higher limit.

When a back queue empties, the frontier removes that host from the heap and refills a back queue for a new host by pulling URLs from the front queues, so the number of active back queues stays around the number of in-flight fetch slots times a safety factor (say 3x), keeping memory bounded.

8.3 robots.txt

robots.txt is a text file at the root of a host that tells crawlers which paths they may fetch (Disallow, Allow), optionally a crawl delay, and sitemap locations, grouped by User-agent. The robots exclusion protocol is now an IETF standard (RFC 9309). Implementation rules:

  • Fetch robots.txt before the first URL of a host, and refresh at most daily (cache lifetime up to 24 hours, honoring cache headers). A refresh is itself a polite fetch scheduled through the same back queue.
  • Per RFC 9309, a 4xx response (file missing) means "no restrictions"; a 5xx or unreachable robots.txt means treat the host as fully disallowed for now and retry later, and if it stays unavailable for a long time (the RFC suggests beyond 30 days) the crawler may treat it as missing. A temporary robots outage must not become a license to crawl everything.
  • Parse leniently, using the longest-match rule for Allow versus Disallow, and cap the parsed file size (the RFC says at least 500 KiB must be handled).
  • Check the rules on every URL at lease time, because a URL may have been enqueued before the host changed its rules.
  • Send an honest, identifiable User-Agent with a contact URL so a site owner can reach us.

8.4 Frontier storage and the lease

The frontier cannot live purely in RAM: 6 billion URLs at 200 bytes would be 1.2 TB. So the durable frontier is the URL store, with rows ordered by (hostHash, priority, nextFetchAt). Each frontier partition keeps only an in-memory working set: the heap of active hosts and the next few hundred URLs for each. When a back queue drains it is refilled from the store with a range scan. Leasing marks the row inFlight until T (T about 2 to 5 minutes), implemented as an atomic conditional update in the store. A crashed fetcher therefore costs only the lease duration; when the lease lapses the URL reappears. This is the same visibility-timeout idea used by message queues (Chapter 35).

9. Fetcher fleet, DNS, and failure at the HTTP layer

The fetcher is an asynchronous HTTP client. Using non-blocking I/O (an event loop, or lightweight threads) one process holds hundreds of open connections without hundreds of threads. Each fetch is bounded by several timeouts, because the open web contains tarpits (servers that send one byte per minute):

  • Connect timeout: 5 seconds. TLS handshake: 5 seconds. Time to first byte: 10 seconds.
  • Total deadline per fetch: 30 seconds.
  • Maximum body size: 5 MB, enforced while streaming, so a 10 GB file is cut off. A minimum transfer rate check kills slow-drip responses.
  • Maximum redirects: 5 (a redirect loop is detected by tracking visited URLs in the chain). Each hop is a new URL that must pass the robots and politeness checks for its host, because a redirect can cross hosts.
  • Accept only expected content types, determined from the header and verified by sniffing the first bytes.
  • Send Accept-Encoding: gzip, br and decompress with a size limit (guard against zip bombs by capping the decompressed size too).

9.1 DNS caching

A DNS lookup (Chapter 4) costs from a few milliseconds to over a second for a cold, distant name, and a crawler touches millions of distinct hostnames. If every fetch resolved its host, DNS would become the bottleneck, and might get us rate limited by public resolvers. The answer has layers. Each fetcher process holds an in-process cache keyed by host with a TTL. Because the frontier groups work by host, the same fetcher sees many URLs of one host in a row, so even a small cache has an extreme hit rate. Behind it runs a local caching resolver shared by the machine (and a few of our own recursive resolvers per data center) rather than a public one. We honor TTLs but clamp them: minimum 5 minutes to avoid churn, maximum 1 day. We also cache failures (NXDOMAIN for 1 hour; SERVFAIL for a few minutes) so dead hosts do not generate repeated lookups. Finally, prefetch: when the frontier selects the next batch of hosts, it can resolve them ahead of the lease. Connection reuse (HTTP keep-alive, and HTTP/2 where offered) shrinks handshakes: ten pages from the same host share one connection, which fits with our one-connection-per-host politeness rule.

Watch out Resolve, then connect to the resolved IP while sending the original Host header. Check the IP against a deny list of private ranges (10.0.0.0/8, 127.0.0.0/8, 169.254.0.0/16 and cloud metadata addresses) after resolution and on every redirect, or an attacker's page can make your crawler fetch internal services (server-side request forgery). Re-resolution tricks (DNS rebinding) are avoided by pinning the checked IP for the connection.

10. Parsing, link extraction, and URL normalization

The parser consumes fetch events, reads the body from object storage (or receives it in memory when co-located), and produces: cleaned text and structured metadata for the indexer, plus the list of outgoing links. HTML found in the wild is frequently invalid, so the parser must be a tolerant, standards-based HTML5 parser that never throws on bad markup, with a size limit and a time limit. Because parsing is CPU heavy and fetching is I/O heavy, they run on different fleets scaled separately; the log between them provides buffering.

Links come from <a href>, but also <link rel="canonical">, <link rel="next">, frames, image sources if we crawl images, sitemaps, and (with the render path) links created by JavaScript. The parser respects <base href>, resolves relative references against the page URL, honors rel="nofollow" (record it but do not use it for priority; many crawlers still may fetch), and the page-level <meta name="robots" content="noindex,nofollow"> and the X-Robots-Tag header.

10.1 URL normalization

The same page can be written as many different strings. Without normalization (canonicalization), the seen-URL check sees each spelling as a new page and the crawler downloads the same page many times. Apply, in a fixed order:

  1. Lowercase the scheme and host (HTTP://Example.COM becomes http://example.com); the path stays case sensitive.
  2. Remove the default port (:80 for http, :443 for https) and a trailing dot on the host.
  3. Decode percent-escapes of unreserved characters and uppercase the hex digits of the rest (%7e becomes ~, %c3%a9 becomes %C3%A9). Convert internationalized hostnames to punycode.
  4. Resolve dot segments (/a/b/../c becomes /a/c).
  5. Remove the fragment (#section), since fragments never reach the server.
  6. Sort query parameters alphabetically, and drop known tracking parameters (utm_*, fbclid, gclid) and session IDs (PHPSESSID, jsessionid). Keep a per-host learned list of parameters that do not change content (section 11.3).
  7. Normalize an empty path to /; optionally strip default index files (/index.html) only when the host is known to treat them the same.
  8. Prefer the rel=canonical target when the page declares one and it is on the same site (trust, but verify cross-domain claims).

Be conservative: over-aggressive rules merge distinct pages and silently lose content. Treat safe rules (1 to 5) as universal and the others (6 to 8) as policies with per-host overrides.

Example: HTTP://Example.com:80/a/./b/../c?b=2&a=1&utm_source=x#top becomes http://example.com/a/c?a=1&b=2. Each outgoing link is then hashed (64-bit hash, or 128-bit if collisions worry us) to a urlHash and routed by hostHash to its frontier partition.

11. Deep dive 2: deduplication of URLs and content

There are two distinct questions: "have I already got this URL?" (URL dedup, runs 16,000 to 40,000 times per second) and "does this page say the same thing as one I already have, under a different URL?" (content dedup, runs once per fetched page, 400 to 1,000 times per second).

If it says definitely new, the link goes to the green box, is added and written to the URL store, and an exact store check is the backup for important sources. 4. The frontier fetches the page. 5. 11.1 URL dedup with a Bloom filter

A Bloom filter (Chapter 57) is a bit array of m bits and k hash functions. To add an item, set the k bits its hashes select; to query, check whether all k bits are set. If any is zero the item was definitely never added; if all are set it was probably added, since other items may have set those bits (a false positive). There are no false negatives and no deletions. The false positive rate is approximately (1 - e^(-kn/m))^k, and the best k is (m/n) x ln 2. With m/n = 10 bits per item and k = 7, the rate is about 0.8 percent, near 1 percent.

For the crawler, a false positive means a genuinely new URL is wrongly considered seen and skipped. At a 1 percent rate that loses 1 percent of newly discovered URLs, which for a crawl is acceptable because those pages are usually reachable from other links (a page with 20 inbound links is missed only if all 20 hit false positives), and the miss is not permanent if the filter is rebuilt each cycle. It is a good trade because the filter answers in about a microsecond from RAM, absorbing 99 percent of the 16,000 to 40,000 lookups per second that would otherwise hit the URL store.

Our arrangement: one filter per frontier partition (so it covers only that partition's hosts and needs no cross-machine lookups), sized for 120 million URLs per partition at 10 bits each = 150 MB. Because Bloom filters cannot delete, and URLs do get recrawled, we split the roles. The filter answers only "is this URL known at all" for newly discovered links. Recrawls come from the store by schedule, never through the filter. When the filter's fill grows beyond its design capacity, the false positive rate climbs fast, so we use a scalable Bloom filter (add a bigger layer) or rebuild it periodically from the URL store, which is the source of truth. For known-new cases where a skip would be costly, the filter's "probably seen" can be double-checked against the store for high-priority sources such as sitemaps.

11.2 Content dedup

The web is full of duplicates: mirrors, the same article syndicated, the same product at five URLs, printer-friendly versions, HTTP and HTTPS versions, and "www" versus bare domain. Storing and indexing all copies wastes space, pollutes search results, and wastes crawl budget.

Exact duplicates: compute a strong hash (SHA-256 truncated to 128 bits, or a 64-bit hash for this purpose) of the cleaned body, ideally of the extracted main text, not the raw HTML, which carries ads, timestamps, and nonces that differ per request. Keep a table contentHash -> canonicalUrl. If the hash exists the new URL is marked a duplicate of the canonical one, its body is not stored again, and the indexer is told about the alias.

Near duplicates: pages that differ by a banner, a date, or a comment count have different exact hashes. Simhash (Charikar's locality-sensitive fingerprint, used at Google for crawling) produces a 64-bit fingerprint such that similar documents get fingerprints that differ in only a few bits. To compute: split the text into features (word shingles of 3 to 5 words), hash each to 64 bits, keep a vector of 64 counters; for every feature, add its weight to counter i if bit i is 1 and subtract it if 0; the fingerprint's bit i is 1 if counter i is positive. Two pages are near duplicates if their fingerprints differ in at most 3 bits (Hamming distance, tuned empirically; at 8 billion pages Google used 3 bits).

Finding all fingerprints within 3 bits of a query among a billion is the hard part, since scanning all is too slow. The standard trick uses the pigeonhole principle: split the 64 bits into 4 blocks of 16 bits. If two fingerprints differ in at most 3 bits, then at least one of the four blocks is identical. So keep 4 tables (or sorted permutations), each indexed by one 16-bit block; to query, look up each of the 4 block values, collect candidates (a small bucket each), and check the full Hamming distance. Each table has 65,536 distinct keys, so with 1 billion fingerprints a bucket holds about 15,000, which is still large; production systems use more blocks with a permuted layout (for example 6 blocks of about 11 bits, matching any 3 of the 6 combos) for smaller buckets. For this design we use a sharded simhash index with block-based lookups, accept a few milliseconds per page, which is easy at 1,000 pages per second.

11.3 Spider traps

A spider trap is a set of URLs that is infinite, or effectively so, and is sometimes deliberately malicious but usually accidental. Examples: a calendar with "next month" links forever (/cal?month=2031-04), session IDs appended to every link (every visit generates "new" URLs), relative-link loops (/a/b/a/b/a/b/... created by a misconfigured server that returns the same page for any path), faceted search with combinatorial filters (?color=red&size=m&sort=price... giving billions of combinations), and tarpits that generate pages on demand. A crawler without defenses will pour its budget into one site. Defenses, layered:

  • Maximum URL length (for example 2,048 characters) and a maximum number of path segments (for example 15); repeated segments (/a/b/a/b) are detected by pattern.
  • Maximum depth from a seed (for example 15 to 20 hops) and a lower depth ceiling for low-priority hosts.
  • Per-host crawl budget: a daily and total page cap scaled by the host's importance. A small blog gets at most a few thousand pages; a major news site gets millions. A trap thus costs at most its host's budget.
  • Duplicate-content ratio per host: if the last 1,000 fetches from a host produced 95 percent duplicate or near-duplicate content by simhash, or if the number of distinct URLs grows while distinct content does not, flag the host or the URL pattern and throttle it.
  • URL pattern clustering: convert URLs into templates (digits replaced by N, parameter values stripped) and count distinct URLs per template per host. A template producing 100,000 URLs with one-third of one percent distinct content is a trap; stop expanding it.
  • Parameter stripping learned per host: if toggling a parameter never changes the content hash, add it to the host's ignorable set and normalize it away.
  • Human review queue: hosts that trip alarms appear in a dashboard; an operator can add a block rule that applies to the host's partition.

No single rule catches every trap, so the budget is the safety net: the worst case is bounded.

12. Deep dive 3: recrawl scheduling by change frequency

Fetching a page once is not enough, since the web changes. But recrawling everything on a fixed cycle wastes crawl budget on pages that never change and starves pages that change hourly. With 1 billion fetches per month and a corpus of, say, 3 billion pages, the average page can only be fetched every 3 months if we spread evenly. The scheduler must decide which pages deserve more.

12.1 Estimating change rate

Treat page changes as a Poisson process with rate lambda (changes per day). Each visit observes only whether it changed since the last visit, not how many times. If the page was fetched at intervals of I days and changed in c out of n visits, a reasonable estimator is lambda about -ln(1 - c/n) / I (the maximum likelihood estimator for a detect-only process, biased low when c equals n, so cap it). Simple production heuristics approximate it with multiplicative interval adaptation: changed means interval x 0.5; unchanged means interval x 1.5 (or x2), clamped between a floor and a ceiling. The ceiling (for example 90 days) guarantees even stable pages are rechecked.

12.2 Choosing what to fetch given the budget

More frequent fetching of a page has diminishing returns. If a page changes with rate lambda and we recrawl every I days, the expected fraction of time our copy is stale is about 1 - (1 - e^(-lambda I)) / (lambda I). A well known result is that, with a fixed budget, the best policy does not simply revisit the fastest changing pages the most: pages that change faster than we can follow are not worth chasing because the copy is stale almost regardless, so the optimum visits moderately changing pages most. Practical systems therefore combine: expected benefit = importance x probability the page changed since last fetch, and sort the due queue by benefit per unit cost. Importance comes from link-based scores and query-log click data; probability of change is 1 - e^(-lambda x age).

We choose a hybrid: adaptive interval as the default for all pages; a Poisson style estimate plus importance only for the top few percent of pages; a fast lane for pages announced through sitemaps, feeds, or push pings; and conditional GET always. Conditional GET sends If-None-Match with the stored ETag and/or If-Modified-Since; the server answers 304 with no body. This costs a round trip but saves bandwidth and parser work, and when our unchanged fraction is high, a large share of fetches become cheap. For servers that do not support validators, we still skip downstream work when the content hash is unchanged.

Implementation: each URL row has nextFetchAt. A per-partition scanner moves rows whose nextFetchAt has passed into the frontier's front queues, scored by benefit. Because the table is ordered by (hostHash, ...) and also has a secondary index by due-time bucket (hour granularity), the scan is a small range read, not a full table sweep. To avoid thundering herds after downtime, we spread due times with random jitter of about 10 percent of the interval. Scheduling logic generally mirrors Chapter 38.

Crawl budget per tier, as an example split of 1B monthly fetches: 5 percent (50M) for the news and fast-changing tier recrawled hourly to daily; 25 percent (250M) for popular pages revisited weekly; 50 percent (500M) for the long tail revisited every 1 to 3 months; 20 percent (200M) for discovery of new URLs. Discovery has a deliberate share so the crawl keeps growing.

13. Distributed partitioning by host hash

All the per-host state (back queue, robots rules, next allowed time, error streak, budget, DNS entry, the host's slice of the URL table and the Bloom filter) benefits from living on one machine. So we partition the entire crawl by hash(host), not by URL hash. If URLs of one host were scattered, each machine would need to coordinate with all others to respect the per-host rate, which means distributed locks or constant communication; with host partitioning the rate limit is a purely local variable.

  • Hot hosts: a few giant hosts (a social site with 10^9 pages) concentrate on one partition.   • Geography: later we can place fetcher clusters near hosts (a European cluster for .eu hosts) to cut latency and to meet data-locality rules; the partition owner stays the same, the fetcher location is a policy field on the host.

14. Storage of raw pages and the indexing handoff

The raw page store is object storage (Chapter 21). Keys are hostHash/urlHash/fetchTime. Small objects are expensive in object stores (a request charge per PUT and per GET, plus per-object metadata), and 100 KB is small relative to the ideal. So the fetcher batches pages into larger WARC-style container files (WARC is the Web ARChive format used by the Internet Archive and Common Crawl) of 64 to 256 MB, each holding thousands of pages, each page compressed and with its HTTP headers and fetch metadata. The URL row stores (containerKey, offset, length), which lets a reader fetch one page by an HTTP range request. This cuts the object count from 1 billion per month to about 780,000 (100 TB / 128 MB), roughly a thousand times fewer.

Lifecycle: the latest version stays in the standard tier; older versions move to an infrequent-access tier after 30 days and expire after the 3 version limit or 1 year. A deleted or 410 page is tombstoned. Bodies from duplicate content are not stored; the row references the canonical one.

14.1 Indexing handoff

The crawler's contract with the indexer is an event log, not a database dump. When a page is stored and not a duplicate (or changed meaningfully), the system publishes PageStored{url, canonicalUrl, containerKey, offset, length, contentHash, simhash, fetchedAt, httpStatus, language, inlinkCount} to a topic partitioned by URL hash. The indexer (Chapter 22) consumes at its own speed. Design points:

  • At-least-once delivery with idempotent consumption: events may repeat after a retry; the indexer keys documents by urlHash and ignores events whose fetchedAt is not newer than what it holds (Chapter 32).
  • Backpressure: if the indexer falls behind, the log absorbs events (retention of several days). If lag crosses a threshold, the frontier lowers the share of recrawl work so storage and consumers are not flooded; discovery of important new content still continues.
  • Deletes and noindex: the crawler emits tombstone events for 404/410 and for pages with noindex directives, so the index removes them.
  • Replays: since bodies persist, the indexer can be rebuilt with a new analyzer by re-reading containers without refetching the web. This is the main advantage of keeping raw pages.

15. JavaScript-rendered pages

Many sites ship a nearly empty HTML shell and build the content in the browser with JavaScript (single-page applications). A plain HTTP fetch sees only the shell, without text and without most links. To see what a user sees, the crawler must execute the page in a headless browser (a real browser engine such as Chromium without a visible window), which loads scripts, runs them, waits for the page to settle, and then reads the resulting DOM (the live page structure).

Rendering is 50 to 100 times costlier than fetching: tens of requests per page (scripts, styles, API calls), seconds of CPU, hundreds of MB of RAM. So we do not render everything. We use a two-wave strategy:

  1. Wave 1: plain fetch and parse, as usual. Everything gets a cheap pass.
  2. Render decision: after parsing, a classifier flags the page as "needs rendering" if the visible text is tiny while the script payload is big, if the body is a known framework shell (a single root element and bundle script tags), or if the host is on a render-required list learned from earlier results. Only these go to the render queue, a separate lower-rate frontier lane (the 10 to 15 percent in our estimate, 40 to 100 renders per second).
  3. Wave 2: the renderer pool loads the URL in a sandboxed browser, blocks heavy irrelevant resources (images, fonts, media, analytics, ads), sets a hard timeout of 10 to 15 seconds, waits for network idle, extracts the final DOM, text, and links, and publishes the same event type, flagged rendered=true. New links go through the same normalizer and dedup.

Important details. Subresource requests made by the browser (scripts, API calls) count against the host's politeness budget and robots rules just like pages, so the renderer routes all its traffic through the same per-host limiter rather than reaching the internet directly. Each tab runs in a locked-down container (no access to our network, memory and CPU limits, destroyed after use), because we are executing untrusted code from the entire web. Infinite scroll and timers are bounded: scroll a fixed number of times, or not at all. Rendered results are cached by content hash of the shell plus script versions to avoid rendering unchanged pages again. An alternative that avoids rendering is to look for server-side rendered or "dynamic rendering" variants, a sitemap, or direct JSON API calls the page makes; cheaper but fragile. We pick the renderer for generality and limit its blast radius with budgets.

16. Scaling, bottlenecks, and hot spots

  • Fetch rate is not the bottleneck. 1,000 per second is a few machines. The bottlenecks are the URL store write rate (every fetch updates a row; every new URL inserts one: roughly 400 updates plus up to 16,000 insert candidates per second, reduced to a few thousand by the Bloom filter), per-host politeness limits, and the parser CPU.
  • URL store write amplification: batch updates per partition (group by host range into 100 to 500 row batches), and use an LSM-based store whose sequential writes handle this well (Chapter 19). Keep hot working state (next allowed time) in memory and flush to the store lazily; lease records need durability but only for minutes.
  • Parser CPU: scale the parser consumer group horizontally; 1,000 pages per second at 20 ms CPU each needs about 20 cores, trivial. HTML parse plus simhash plus text extraction is perhaps 30 to 50 ms in practice, so about 50 cores at peak.
  • Network egress: 800 Mbit/s at peak; ensure the crawler has multiple outbound IP addresses on separate subnets so sites do not see all traffic from one address and so IP-based blocks do not cripple everything. Publish the IP ranges and reverse DNS so sites can verify us.
  • Caching: robots rules (per host, daily), DNS, negative results, the host heap, and the Bloom filter are all caches in front of slower truth. Cache the parsed robots file as a compiled structure.
  • Hot hosts discussed in section 13: bounded by politeness; sub-partition large ones.
  • Rebalancing: moving a partition means moving its Bloom filter snapshot, its URL rows, and its frontier state; since the URL store is the truth and the rest is rebuilt from it, a move is "stop, copy rows, rebuild caches", taking minutes.

17.1 Consistency and idempotency

The crawler does not need strong consistency: the URL store can be eventually consistent between replicas, because the cost of a rare duplicate fetch is tiny. What matters is that the lease protocol is safe: each state change is a conditional write (compare-and-set on leaseId), so two fetchers never both complete the same lease and a late ack from a stale fetcher is rejected. Fetching and storing are idempotent: the blob key includes the fetch time and content hash, and the indexer ignores older versions. Link events can be delivered twice; inserting a URL that exists is a no-op. We therefore run the whole pipeline at-least-once with idempotent consumers, the cheaper and more robust choice than exactly-once. The one place needing care is the politeness limit: after a frontier restart the lost nextAllowedAt must be replaced by a conservative guess, otherwise a failover could momentarily burst on a host.

17.2 Multi region

Later, fetchers can run in several regions, each closer to some hosts, all leasing from the partition owners through an API (or the owner placed in each region for its hosts). The URL store replicates asynchronously to a second region for disaster recovery (Chapter 41, Chapter 26); on failover we lose seconds of updates, meaning a few URLs get refetched. Crawl output is stored per region and replicated to the indexer's region with an object-store replication rule, so cross-region transfer is done once in bulk, compressed, rather than per page.

18. Security, abuse, ethics, and legal

A crawler is a guest on other people's servers, and it also executes untrusted content. Both sides need attention.

18.1 Being a good citizen

  • Obey robots.txt and meta robots/X-Robots-Tag directives. Use a descriptive user agent such as ExampleBot/1.0 (+https://example.com/bot) and a working contact address; publish a page explaining what the bot does and how to opt out or request a lower rate.
  • Keep load low and adaptive: 1 connection per host, delays based on response time, instant back off on 429/503. A crawler that takes down a small site generates complaints and legal letters.
  • Provide a way to verify the crawler (published IP ranges and reverse DNS), since impostors use famous bot names to scrape.
  • Support opt-out requests promptly, including the removal of cached copies.
  • Respect noindex, nosnippet, and noarchive signals downstream.

18.2 Legal and policy considerations

These are design inputs to flag to an interviewer, not legal advice. Robots.txt is a convention, not law, but ignoring it weakens any legal position. Copyright: storing and indexing copies of pages is treated differently by jurisdiction; search indexing has often been held acceptable while republishing full content is not, so the stored raw copies are internal and the serving layer shows only snippets. Terms of service may forbid scraping and, in some cases, courts have addressed access to publicly available data differently from access to data behind a login; we never crawl behind authentication. Personal data: pages can contain personal information, so privacy law such as GDPR affects retention, deletion requests, and processing (Chapter 56); keep deletion tooling, and avoid storing anything from pages that signal not to. Respect the regional requirements on where data may be stored. Do not fetch known illegal-content sources; block lists and hash-matching against known abusive material are part of the content pipeline in a real product. AI training use of crawled data is an area of changing norms: sites increasingly use specific user-agent tokens in robots.txt to opt out, so the crawler should use separate user-agent names for separate purposes (search versus model training) so owners can choose.

18.3 Protecting ourselves

  • SSRF defense and egress allow lists, described in section 9.
  • Sandboxed renderers and parsers (separate processes with seccomp style syscall limits, no credentials on the machine, ephemeral containers) because a browser exploit is a real threat (Chapter 55).
  • Malware and phishing pages: never execute downloaded binaries; hash and scan content types we store; flag hosts known for malware so the indexer can demote.
  • Poisoning: a malicious site can stuff the crawl with spam pages and link farms, bounded by budgets and quality scoring.
  • Control API authentication and audit: only authorized operators may override robots-related policy or raise rate limits; such overrides are logged and need approval.

19.1 Cost

  • Fetcher machines: 16 instances. Parsers: about 10. Renderers: about 15 larger machines (the single largest compute line per page).
  • Storage: 100 TB new per month, at about 23 dollars per TB-month in a standard object tier means about 2,300 dollars for each month's batch, falling to a fraction in the cold tier.   • Network: inbound traffic is typically free; outbound is small. Crawling from a cloud region is cheap, but a few large providers throttle or block cloud IP ranges, so some crawlers rent dedicated ranges.

20. Evolution, phasing, and alternatives

20.1 What to build first

  1. Phase 1 (weeks 1 to 4): a single partition: URL store, a simple two-level frontier with per-host delay, a fetcher with timeouts and robots.txt, normalization, an exact seen-set, local object storage, a log for fetch events. Target 20 pages per second. Learn the real shape of the data.
  2. Phase 2: partition by host hash, add the Bloom filter, DNS cache, content hash dedup, conditional GET, adaptive recrawl, trap defenses and host budgets, and the indexer feed. Target 400 per second.
  3. Phase 3: simhash near-dup, render pool, sitemap and feed integration, priority scoring from link analysis, multi-IP and multi-region fetchers.

20.2 At 10x scale (10 billion pages a month, 4,000 per second average)

  • Fetchers go from 16 to about 150 machines; network to roughly 3.2 Gbit/s average.
  • The URL store grows to 12 TB and needs about 100 partitions with automatic splitting; the Bloom filter total is 75 GB, so more partitions of the same size.
  • Link candidates rise to 160,000 per second, so the router and log need partition-aware batching and the Bloom filter must be strictly local.
  • Politeness arithmetic changes meaning: at 4,000 per second and 1 per second per host, you need 4,000 hosts active at once; the long tail is plenty, but giant sites become the binding constraint on freshness, which pushes you toward push signals (sitemaps, IndexNow style pings, feeds) and cooperative agreements.
  • Storage reaches 1 PB of new data per month, so aggressive dedup, stronger compression (zstd with a shared dictionary can beat gzip noticeably on HTML), and a retention policy keeping only changed versions become necessary.

21. Interview Q&A

How do you make sure the crawler never hits one site too hard, even though many fetchers run in parallel?

We partition the whole frontier by host hash, so exactly one frontier partition owns each host, and that partition alone hands out URLs for that host. It stores a nextAllowedAt time per host in a heap, and a URL for a host is leased only when the time has passed, after which the host is reinserted with the delay added. Because the rate decision is one local variable rather than a distributed lock, parallel fetchers cannot violate it; they only receive work the owner has approved. The delay itself is the larger of the robots crawl delay and a multiple of the previous fetch time, with strong backoff on 429 or 503.

Why use a Bloom filter for seen URLs, and what are the downsides?

Each page yields about 40 links, so we must answer "have I seen this?" some 16,000 to 40,000 times per second, and a Bloom filter does so from memory in about a microsecond with roughly 10 bits per URL, so 6 billion URLs fit in 7.5 GB. The downside is the false positive: about 1 percent of new URLs are wrongly seen as known and skipped, and a Bloom filter cannot delete entries or tell you when a URL was last fetched. We accept the loss because pages usually have several inbound links and the filter is rebuilt from the URL store, and we use the store (not the filter) to drive recrawls. Fill must be monitored, because exceeding the designed capacity raises the false positive rate quickly.

How do you detect near-duplicate pages at billion scale?

We compute a 64-bit simhash of the main text, a fingerprint where similar texts differ in only a few bits, and call pages near duplicates if their Hamming distance is at most 3. Scanning a billion fingerprints per query is impossible, so we use the pigeonhole principle: split the fingerprint into blocks, and any two fingerprints within 3 bits differ in at most three blocks, so they must share at least one exactly equal block when we use four or more blocks. We keep tables indexed by blocks, look up candidates by each block, and verify the full distance. An exact hash of the extracted text is checked first because it is cheaper and certain.

What is a spider trap and how do you protect the crawl budget from one?

A spider trap is an effectively infinite URL space, such as endless calendar pages, session IDs in links, repeated path segments, or faceted filters with combinatorial parameters. We layer defenses: maximum URL length and depth, normalization that strips session and tracking parameters, URL template clustering to spot patterns that yield huge numbers of URLs with little unique content, a duplicate ratio per host, and above all a per-host crawl budget so that the worst case is bounded and the trap hurts only its own host. Suspect hosts go to an operator dashboard for rule changes.

How do you decide how often to recrawl each page?

We keep per-URL state with the last fetch time, the content hash, validators, and an interval. Each fetch compares the new content hash or receives a 304; a change halves the interval, no change multiplies it by about 1.5, clamped between a floor and a ceiling. For the most important pages we estimate a Poisson change rate and order the due queue by importance times the probability of change since the last fetch. Sitemap lastmod, feeds, and push pings jump the queue but are verified with a conditional GET. Fixed-interval recrawling wastes budget on static pages and leaves news stale, so adaptation is worth the extra state.

What happens if a fetcher crashes halfway through downloading a page?

Nothing permanent happens. The frontier gave the URL out under a lease with an expiry of a few minutes; the fetcher never acknowledged, so the lease lapses and the URL becomes due again. Since a GET is idempotent and the blob key and indexer events are keyed by URL and content hash, a repeat fetch produces at most a duplicate that is caught by the hash check. The only risk is the per-host politeness, which we keep by recording the host's next allowed time at lease time rather than at completion.

Why partition by host rather than by URL?

Politeness, robots rules, DNS, error streaks, budgets, and trap detection are all per-host concepts. If one host's URLs spread over many machines, every one of them would need to coordinate on a shared counter to respect a 1 request per second limit, which means distributed locking at 1,000 operations per second. Host partitioning puts all of that state on one node, makes range scans by host cheap, and keeps the dedup filters local. The cost is skew from giant hosts, which we handle with sub-partitions that each own a share of the host's rate.

How do you handle sites that render with JavaScript without making the crawler ten times more expensive?

Render selectively. Every page gets the cheap plain fetch and parse; a classifier flags pages with little visible text and a big script payload, or hosts that have been seen to need rendering, and only those go to a separate rendering lane with its own budget. The renderer blocks images, fonts, and trackers, uses short timeouts, runs in a locked-down sandbox, and sends all its network requests through the same per-host politeness limiter. Results are cached against the shell and script versions, so unchanged pages are not rendered again. For high-value hosts we may call their underlying JSON APIs directly.

How do you treat robots.txt failures: missing, error, or timeouts?

Following RFC 9309, a 4xx answer such as 404 means the site has no rules and we may crawl; a 5xx answer or an unreachable server means we must assume everything is disallowed for the moment and retry later, since an outage must not become a licence to crawl everything. We cache a good copy for up to a day, refresh it politely through the host's own queue, re-check rules at lease time for each URL, and limit the parsed size. If robots is unavailable for a long period (the RFC mentions about 30 days) we may treat the site as unrestricted.

How would the design change if you needed to crawl one very large site, such as a marketplace with 500 million pages, within a week?

The politeness limit would be the binding constraint: 500 million pages in 7 days is about 827 requests per second to one host, which no site should receive by default. We would negotiate an agreement or use the site's provided feeds, sitemaps, or an API, then raise the host's limit explicitly with its sub-partitions, each with a small share and connection pool, and watch response times and error rates for backoff. Without cooperation we cannot finish in a week politely, and we say so; the budget and priority policy decides which pages come first (new and popular items) and the rest arrive over months.

How do you test and roll out changes safely, given the crawler touches the whole internet?

Changes to politeness, normalization, and robots handling are the dangerous ones, because mistakes harm third parties or silently merge distinct pages. We run new versions in shadow mode on a replay of recorded fetch events, compare normalization output with the old version, and roll out per partition with a canary partition first. Rate limit logic has a hard safety layer in the fetcher (a global per-host cap that no frontier bug can exceed), and we have a kill switch that pauses a host or the entire fleet in seconds.

22. Recap

Recap

  • Numbers: 1B pages/month is about 400 per second average and 1,000 at peak, 1,000 connections, 800 Mbit/s, 100 TB of new compressed pages per month, 1.2 TB of URL metadata, and 16,000 to 40,000 URL checks per second. The bookkeeping, not the fetching, is hard.
  • Frontier: front queues for priority with a biased selector, back queues per host with a heap keyed by next allowed time; leases with expiry for crash safety; rate from robots crawl delay or 10x last fetch time, with strong backoff on 429 and 503.
  • Fetching: async fetcher with strict timeouts and size limits, DNS caching at several layers, SSRF protection, conditional GET, and outcome-specific handling.
  • URLs: normalize carefully, dedup with a per-partition Bloom filter (10 bits per URL, 1 percent false positives) backed by the exact URL store; recrawls never go through the filter.
  • Content: exact text hash then 64-bit simhash with block-based lookup; traps are bounded by length, depth, templates, duplicate ratios and per-host budgets.
  • Recrawl: adaptive intervals plus benefit-based ordering for important pages, sitemaps and push signals, jitter against herds.
  • Partition by host hash so all per-host state is local; stateless fetchers; big hosts sub-partitioned.
  • Storage: WARC-style containers in object storage, event log to the indexer, at-least-once with idempotent consumers, replay possible.
  • JS pages: two waves, render only flagged pages in sandboxes behind the same politeness limiter.
  • Ethics and law: obey robots.txt, identify the bot, stay gentle, honor opt-outs and privacy requests, never crawl behind logins.
