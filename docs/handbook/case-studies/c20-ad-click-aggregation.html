Case study 20 · Worked solutions

Design Ad Click Aggregation

Every time someone clicks an ad, an advertiser may owe money and a dashboard must change. This worked solution builds a pipeline that ingests a billion clicks a day, throws away duplicates and bots, counts clicks per ad per minute with correct handling of late events, stores the counts so advertisers can query them in under a second, and proves the numbers are billing-grade by reconciling the stream against a slower batch job.

How to approach this problem (read this first)

What the interviewer is really testing. Counting clicks sounds easy, so the interview is about the three things that make it hard. First, correctness with money involved: no click lost, none counted twice, even when machines crash and messages are retried. Second, time: clicks arrive late and out of order, so you must count by when the click happened, not when you saw it, and say when a minute is "done". Third, skew: one popular ad can swamp one worker. If you handle these three calmly, the rest (Kafka, a store, a query API) is routine.

The thinking order

  1. Ask what the number is used for. Say: "Is this count billed, or only shown on a dashboard?" Ask this first because "billed" changes everything: it forces exactness, an audit trail and a slow, correct recount next to the fast path.
  2. Pin down volume and lateness. Say: "How many clicks per day, and how late can a click arrive?" Volume sizes the system. Lateness decides the watermark and the allowed lateness. Also ask about duplicates and bots, since they decide whether a filter stage exists.
  3. Estimate the write rate first. Say: "One billion a day is about 11.6k per second on average, and I design for 50k per second at peak." Write rate comes first because this system is write-heavy. Then show that the bandwidth (about 10 MB per second) is small, which tells you partitions are about parallelism, not bandwidth.
  4. Draft the write API and the event, not the read API. Say: "The click URL carries a click id and a signature, and the endpoint logs the event and redirects." The click id is the key that makes dedup and idempotency possible, so introduce it early.
  5. State the first simple design and break it. Say: "The naive version does one UPDATE per click on one database. That fails on hot rows, coupling, retries and no history." Four named failures give you a reason for each later box.
  6. Evolve it: log first, then stream, then store. Say: "I write the raw event to a durable log, aggregate in a stream job, and upsert full counts into an OLAP store." Each move answers one of the four failures.
  7. Go deep on time and late data. Say: "I aggregate by event time with tumbling minute windows, a watermark, and a late path." This is the part you will be pressed on, so do it before the nice-to-haves.
  8. Make the effect exactly once, then handle the hot ad. Say: "At-least-once delivery plus idempotent writes of full counts gives an exactly-once effect. For a hot ad I salt the key and sum in a second stage."
  9. Close with reconciliation and failures. Say: "An hourly batch recount from the raw archive produces the final billed numbers, and the gap between stream and batch is my alarm." It ends the story with the answer to "how do you know the number is right".

Decision points

  • Count by event time or processing time? Ask: "Which clock does the contract use?" The contract says the minute the user clicked, so event time, which then needs a watermark.
  • Stream only, or stream plus batch? Ask: "Can the stream see everything it needs to decide?" It cannot see very late clicks, old duplicates or later fraud findings, and the number is billed, so add the batch recount.
  • Where does dedup state live? Ask: "Can the check be atomic with the write?" Keyed state in the stream job, snapshotted with the offsets, can. An external cache cannot.
  • Which store? Ask: "What queries are there?" Per-ad ranges and per-advertiser group-bys point to a columnar OLAP engine, not a pure key-value store.
  • Salt every key or only hot ones? Ask: "Does the long tail pay for a fix it does not need?" Salt only detected heavy hitters.

Common mistakes on this problem

  • Incrementing a counter per click. It is not idempotent and keeps no history. Fix: write events to a log, and write full revisioned counts.
  • Counting by processing time. Outages create fake spikes. Fix: use event time with a watermark.
  • Saying "exactly once" without saying how. Fix: name the three boundaries (producer, job, sink) and the fix for each.
  • Using a Bloom filter alone for dedup. A false positive drops a paid click. Fix: let a "maybe" fall through to an exact check.
  • Partitioning by ad id. Popular ads make hot partitions. Fix: key the raw topic by click id and salt hot keys.
  • Forgetting the batch path. Late clicks and later fraud findings never reach the bill. Fix: recount hourly from the archive.
Interview tip Open by asking whether the number is billed. Every later choice (exactness, the audit trail, the batch recount, idempotent upserts) follows from that one answer, and it shows you think about the business, not only the pipeline.

1. Problem statement and clarifying questions

An advertising platform shows ads on websites and apps. When a user clicks an ad, the browser or app is redirected through a click-tracking endpoint run by the platform, which records the click and then forwards the user to the advertiser's landing page. Advertisers pay per click (cost per click, CPC), so the number of clicks is literally money. Advertisers also want to watch campaigns live: "how many clicks did ad 4711 get in each of the last 60 minutes?" The task is to design the system that collects click events, aggregates them by ad and by minute, and serves the results.

The first five minutes of an interview should go into questions, because the answers change the design. These are the questions I would ask, with the answers I will assume for the rest of the page (the framework is in Chapter 1).

2. Requirements

2.1 Functional

  • Ingest click events from the redirect tier with very low added latency to the user.
  • Filter duplicate clicks (the same physical click delivered more than once) and invalid clicks (bots, click farms, abusive repeats).
  • Aggregate valid clicks into per-ad, per-minute counts, with rollups to hour and day.
  • Query by advertiser: time series for an ad or campaign over a range, plus the top K ads by clicks over the last N minutes.
  • Correct history: late events and fraud decisions made after the fact must be reflected in the numbers.
  • Replay: rebuild any past period from the raw log after a bug or a rule change.

2.2 Non-functional

  • Accuracy first. No click is lost, no click is counted twice. When speed and exactness conflict, exactness wins for billing and speed wins for the live dashboard (which later converges).
  • Throughput: sustain 50k clicks per second at peak, and survive a 3x surprise burst by buffering rather than dropping.
  • Latency: redirect path adds under 10 ms of our own time (p99). Dashboard freshness under 30 seconds after the minute closes. Query latency under 500 ms p99.
  • Availability: the click endpoint must be highly available (a lost click is lost revenue); the dashboard may degrade.
  • Durability: once the endpoint says "recorded", the event survives any single machine or zone failure.
  • Fault tolerance: any stage can crash and restart without changing the final counts.

2.3 Out of scope

Ad serving and auctions, budget pacing (stopping a campaign when its budget is spent, although it consumes our output), conversion attribution, the invoice generator, and the machine learning model that scores fraud (we treat it as a service that returns a score).

3. Estimation

All arithmetic is shown so each later choice can be defended (method in Chapter 2).

3.1 Traffic

  • 1 billion clicks per day. A day has 86,400 seconds, so the average is 1,000,000,000 / 86,400 = about 11,574 per second, which I round to about 11.6k per second.
  • Advertising traffic is diurnal and spiky (a sports final, a flash sale). Peak is about 4.3x average, so I take 50k per second as the design peak, and plan the pipeline to catch up from a short outage at 2x peak speed.
  • Read side: advertisers number in the hundreds of thousands, and a dashboard auto-refreshes about every 30 seconds. With 100k advertisers watching at once at peak, that is about 3.3k dashboard queries per second. Queries are far fewer than writes, but each touches many rows, so they matter for the store design.

3.2 Raw event storage

A click event carries a click id, ad id, advertiser id, campaign id, placement/publisher id, user or device id, IP, user agent, event timestamp, and a few flags. Assume 200 bytes in a compact binary encoding (Chapter 7).

  • Per day: 1e9 x 200 B = 200 GB. Per year: 200 GB x 365 = 73 TB. Compressed about 3 to 4 times in columnar files on object storage, roughly 20 TB per year.
  • Kafka retention of 7 days: 200 GB x 7 = 1.4 TB, times replication factor 3 = 4.2 TB across the brokers. Small.
  • Peak ingest bandwidth: 50k x 200 B = 10 MB per second. This is tiny for Kafka (a single broker handles tens to hundreds of MB per second), so partitions are chosen for consumer parallelism and key distribution, not for bandwidth. I choose 64 partitions for the raw topic.

3.3 Aggregate storage

Not every ad is clicked every minute. Assume that after aggregation there are about 300 million (ad, minute) rows per day, meaning the average non-empty row holds about 3 clicks. Each row is ad id (8 B), minute (4 B), count (8 B), plus a few columns such as advertiser id and a revision number, say 40 B stored.

  • Minute table: 300M x 40 B = 12 GB per day, 4.4 TB per year before compression. Keep minute granularity for 30 days (360 GB), roll up to hour (about 40x fewer rows) kept for 2 years, and day kept forever.
  • Dedup state: a click id is 16 bytes, plus overhead call it 40 B in the state backend. If we remember ids for 1 hour, the peak holds up to 50k x 3600 = 180 million ids, and 180M x 40 B = 7.2 GB, spread across 64 workers that is about 110 MB each. This fits comfortably in RocksDB state on local disk or even memory.

3.4 Stream job sizing

With 64 parallel tasks, each handles 50k / 64 = about 780 events per second at peak. Even with a 1 KB state lookup per event this is light; the real costs are checkpointing and the fraud model calls, not counting. I would still run 64 tasks (not 8) so that restarts, rescaling and catch-up after an outage have parallel headroom.

4. API design

4.1 Click ingestion (write path)

GET /c?ad=4711&cid=7f3a...e1&ts=1731800123456&sig=9be0...
  -> 302 Location: https://advertiser.example/landing?utm=...
  headers captured: IP, User-Agent, Referer, Cookie (device id)

The ad server embeds a click URL into each served ad. The query string contains the ad id, a click id (cid), generated at impression time when the ad was shown, and an HMAC signature of both with a secret key. The click id is the dedup key: if the user double-clicks or the browser retries, the same cid appears twice. The signature stops anyone from inventing click ids, so forged traffic can be rejected at the edge before it costs anything downstream. The endpoint writes to the log, then replies with a 302 redirect. The user does not wait for aggregation.

4.2 Event schema on the log

ClickEvent {
  click_id:    bytes16   // unique per impression, the dedup key
  ad_id:       int64
  advertiser:  int64
  campaign_id: int64
  publisher:   int64
  device_id:   bytes16
  ip:          bytes16
  user_agent:  string
  event_time:  int64     // when the click happened, client/edge clock (ms)
  ingest_time: int64     // when our edge received it
  sig_valid:   bool
}

4.3 Query API for advertisers (read path)

GET /v1/ads/{adId}/clicks?from=2026-11-17T10:00Z&to=2026-11-17T11:00Z&granularity=minute
  -> { "adId": 4711, "granularity": "minute",
       "points": [ { "t": "2026-11-17T10:00Z", "clicks": 12, "status": "provisional" }, ... ],
       "watermark": "2026-11-17T10:58Z" }

GET /v1/advertisers/{id}/clicks?from=...&to=...&groupBy=ad&granularity=hour
GET /v1/advertisers/{id}/top-ads?window=15m&k=10
  -> [ { "adId": 4711, "clicks": 9120 }, ... ]

Each point carries a status: provisional (from the stream, may still change within the lateness bound), or final (confirmed by the batch reconciliation). The response also returns the watermark, so the client can show "data complete up to 10:58". This honesty is a design feature: it lets us serve fast numbers and exact numbers without lying about which is which. Pagination and rate limits follow Chapter 5 and Chapter 16.

5.1 Why an OLAP store, not a key-value or time-series database

The base aggregate is a table (ad_id, minute_bucket, clicks) with advertiser and campaign columns. The queries are "this ad over a range" (a range scan on a sorted key) and "this advertiser grouped by ad" (a scan and a group-by across many ads). A pure key-value store such as DynamoDB or Cassandra serves the first very well (partition key ad_id, sort key minute) but makes the second expensive, because it requires a secondary index or scatter-gather. A classic time-series database is natural for metrics with few series, but we have tens of millions of distinct ads, a high-cardinality problem for many of them. A column-oriented OLAP engine handles both: data sorted by (advertiser, ad, minute), compressed per column, and aggregation queries vectorized. It also supports idempotent writes: a row keyed by (ad, minute) that is re-inserted with the same revision replaces the old one (a ReplacingMergeTree in ClickHouse, or a primary-key table in Pinot or Druid segments replaced atomically).

The table design, ordered by (advertiser_id, ad_id, minute), looks like this:

ad_minute_clicks (
  advertiser_id Int64, ad_id Int64, minute DateTime,
  clicks Int64, revision Int32, status Enum(provisional, final)
) ORDER BY (advertiser_id, ad_id, minute)  -- latest revision wins

6. A first simple design

Before the scaled design, start with the version that works on one or two machines and say out loud why it breaks. The naive design: the click endpoint receives a click, runs UPDATE ad_minute SET clicks = clicks + 1 WHERE ad = ? AND minute = ? against one relational database, and then returns the redirect. A dashboard runs SELECT on the same table.

This is correct at 100 clicks per second and fails in four ways at our scale.

  1. Write rate and hot rows. 50k updates per second against a single table, with a popular ad producing thousands of updates per second to one row, serializes on row locks. The database becomes the bottleneck and the click endpoint's latency grows with it.
  2. Coupling. If the database is slow or down, clicks are lost or users wait. Money is lost both ways.
  3. Retries double count. If an update succeeds but the response is lost, the client retries and the counter increments twice. An increment is not idempotent (Chapter 32).
  4. No filtering, no history. The raw click is not stored, so a bot decision made tomorrow cannot be applied to yesterday, and an audit has nothing to audit.

The fixes define the real architecture: write the raw event to a durable log first (decouple and keep history), aggregate in batches in a stream processor (not one row update per click), identify every click with an id so counting becomes a set-union problem rather than increments, and write the result as an idempotent upsert.

The components, in the order a click meets them:

  1. Click tier. Stateless web servers behind a load balancer (Chapter 9). It validates the signature, appends the event to Kafka, waits for the broker acknowledgment (all in-sync replicas, acks=all), and returns the 302 redirect. If Kafka is unreachable it falls back to a local disk spool and drains later, so a Kafka outage does not lose clicks.
  2. Raw topic. Partitioned by click_id hash. Choosing click id as the key spreads load evenly (ad id would create hot partitions for popular ads) and sends all duplicates of one click to the same partition, which is what makes the next stage's dedup cheap.
  3. Filter job. A stream job that drops duplicates and invalid clicks, annotates the rest, and writes to clicks.valid. Rejected events go to clicks.rejected with a reason code, never silently deleted.
  4. Aggregate job. Re-keys by ad id, counts per event-time window, emits results with a watermark, and upserts into the OLAP store and Redis.
  5. Archive and batch lane. A sink copies every raw event to object storage in hourly files. An hourly batch job recomputes exact counts for each closed hour from the archive and overwrites the provisional rows. Only finalized hours reach billing.
  6. Query API. Reads the OLAP store and Redis, adds the status and watermark fields.

8. Deep dive: event time, windows and late data

This is the heart of the problem and the part an interviewer will press. The general theory (windows, watermarks, triggers) lives in Chapter 37; here is how it applies.

8.1 Event time versus processing time

Event time is when the click happened. Processing time is when our job happens to see it. They differ because of network delay, retries, mobile clients that buffer clicks while offline, and our own backlogs. If we counted by processing time, then after a 10-minute pipeline outage the first minute after recovery would hold 10 minutes of clicks, and an advertiser would see a fake spike and fake gap. Billing by "the minute the click was processed" is also wrong when the contract says "the minute the user clicked". So we aggregate by event time, which means the job must decide when a minute's count is "complete enough" to emit. That decision is the watermark.

Walkthrough. This is a chart, not a flow, so read the two axes first. Along the bottom is processing time, when our job sees an event. Up the side is event time, when the click really happened. 1. Each black dot is one click. A click cannot be seen before it happens, so every dot sits on or below the grey dashed ideal line. 2. The distance below that line is the delay from network, retries or an offline phone. 3. The green line is the watermark. It trails the newest event time seen by 2 minutes, which is the tolerance we chose for out-of-order arrival. 4. The red dot is a click whose event time is older than the watermark at the moment it arrives. That click is late, and the window it belongs to may already have been emitted. The number to remember is the 2 minute gap between the grey and green lines: a bigger gap waits longer and is less often wrong, a smaller gap is fresher and drops more clicks into the late path. On a whiteboard, draw the axes and the two lines, then put one dot below the green line and say what happens to it. Without a watermark the job would never know when to close a minute.

8.2 Tumbling, hopping and sliding windows

A tumbling window is a fixed, non-overlapping interval: [10:00, 10:01), [10:01, 10:02), and so on. Each click belongs to exactly one. This is what the per-minute table needs, and it is the cheapest: one counter per (ad, minute). A hopping (sliding) window has a length and a smaller step, for example length 5 minutes and step 1 minute, so each click belongs to five windows. It answers "clicks in the last 5 minutes, refreshed every minute", used by the top-K board. Computing hopping windows by keeping a counter per window multiplies work by 5. The standard trick is to never aggregate hopping windows from raw events: keep the tumbling minute counts and compute the 5-minute sum by adding the last five minute counters at read time (or by a second, tiny, stage). The raw stream is touched once.

Walkthrough. The picture has two rows that share one timeline. The top row is the stored data: six blue boxes, one per minute, from 10:00 to 10:06. Each click is counted in exactly one of them. The lower rows are views, not stored data. 1. The first bar spans five boxes, 10:00 to 10:05, and is labelled as the window ending 10:05. Its value is the sum of those five counters. 2. The second bar is the same idea shifted right by one box: minutes 10:01 to 10:05, the window ending 10:06. 3. Moving the window by one minute only drops the oldest box and adds the newest. The choice shown is to keep the cheap tumbling buckets and add them at read time. The alternative is to assign each click to five overlapping windows, which multiplies the work by five for the same answer. When drawing it, draw the boxes first, then lay the long bars over them. If you removed the top row and kept only sliding windows, you would lose the base counts that the table, the rollups and the top-K board all depend on.

8.3 Watermarks and allowed lateness

A watermark is the job's running claim: "I do not expect any more events with event time earlier than W". A common heuristic is W = (largest event time seen) - D, where D is a bound on out-of-orderness, here 2 minutes. When W passes the end of a window, the window is closed and its result is emitted. With D = 2 minutes, the 10:00 to 10:01 window emits when the job sees an event stamped 10:03 or later, so freshness is about one minute of window plus 2 minutes of wait, which meets the "30 seconds after the minute closes" target only if we emit early, so we also emit early provisional results: a trigger fires every 10 seconds for the open window and upserts the running count with status provisional. The dashboard therefore shows a live number that is slightly low, then the final-for-stream value at window close.

Events arriving after W passed the window are late. Three policies exist:

PolicyBehaviourCost
DropLate clicks are discarded.Undercount; unacceptable for billing, acceptable only for approximate metrics.
Allowed lateness (retract/update)Keep window state for another L (we use 15 minutes). A late event updates the count and re-emits a new revision of the row.State held longer (15 more windows per ad); downstream must accept updates, which an upsert by (ad, minute) handles.
Side output + batchEvents later than L go to a side topic clicks.late, and the hourly batch job includes them from the archive.Live number stays low until the batch fixes it, but the final number is right.

I choose the last two together: allowed lateness of 15 minutes for the live path and the archive-based batch for everything later. This split is the reason the system is billing-grade without forcing the stream job to keep state forever. Because the archive keeps every raw event by its event time, a click that arrives six hours late is still counted in the right minute by the batch job, and the advertiser sees the row flip from provisional to final.

Watch out A watermark derived from the maximum event time seen is dangerous if one client has a wrong clock set far in the future: it drags the watermark forward and makes legitimate events look late. Always clamp event times: use the edge's ingest time as a sanity bound (reject or clamp events more than a few minutes ahead of ingest time) before they reach the job. See Chapter 27 on clock skew.

Another subtlety is an idle partition. Watermarks in a parallel job are the minimum across the input partitions. If one Kafka partition receives no events (a quiet night, a stalled producer), its watermark never advances and the whole job stops closing windows. The fix is an idle-timeout setting that excludes a partition from the minimum after it has been quiet for, say, 30 seconds. With 64 partitions keyed by click id, an idle partition at peak is unlikely, but a drained or unevenly sized topic at night is common.

9. Deep dive: dedup and fraud filtering

9.1 Duplicates

Duplicates appear for four reasons: the user double-clicks; the browser or a proxy retries the request; the click tier retried the Kafka send after a timeout though the first send succeeded; and the producer or a consumer replayed data after a failure. The click id, minted at impression time, identifies one click regardless of how many copies exist. The dedup rule is simple: for each click id, count only the first occurrence within a time horizon.

The design question is where the "seen ids" set lives and how long it is kept. Compare the options.

OptionHowProsCons
A. External KV (Redis SET key NX EX)Each event does a SETNX with a TTL; success means first.Easy to understand; shared by any consumer.50k round trips per second to a networked store; the check and the downstream write are not atomic, so a crash between them can lose or duplicate a click; the cache must be sized and replicated for 180M keys.
B. Keyed state in the stream jobPartition by click id; each task keeps a RocksDB set of recent ids with a TTL; state is checkpointed with the offsets.Local lookup, no network hop; state and offsets are snapshotted together, so dedup is consistent with exactly-once processing.State size grows with the horizon; rescaling moves state.
C. Bloom filter prefilterA Bloom filter (Chapter 57) says "definitely new" or "maybe seen".Tiny memory.False positives would silently drop real clicks, which is unacceptable for billing, unless a "maybe" falls back to an exact check.
D. Dedup in the sinkUse a unique key (click id) in the store.Strongest final guarantee.Billions of rows keyed by click id in the OLAP store; wasteful for aggregates that do not store clicks.

I choose B as the main mechanism with an optional Bloom prefilter in front of it to skip RocksDB reads for obviously new ids (a hit on "maybe seen" always falls through to the exact check, so no false drops). The horizon is 1 hour: duplicates from user retries and producer retries occur within seconds to minutes, and longer-range duplicates are caught by the batch job, which does a global SELECT DISTINCT click_id across the whole hour (and the previous and next hour) from the archive. State size, from section 3.3, is about 7 GB across 64 tasks at the peak rate, which is modest. Two defenses together are the usual pattern: approximate or windowed in the stream, exact in the batch.

9.2 Fraud and bot filtering

Invalid clicks come from simple bots, click farms, competitors clicking to drain a rival's budget, publishers inflating their own revenue, and buggy clients. The filter is a pipeline of increasingly expensive checks, so cheap rules remove most of the junk before costly ones run:

  1. Edge checks (click tier, microseconds): signature valid, ad id exists, click id not obviously forged, user agent not on a known bot list, IP not on a blocklist (data-center ranges, known proxies).
  2. Stateful rate rules (filter job, keyed state): more than N clicks per device per minute on any ad; the same IP clicking the same ad more than M times per hour; click-to-impression time under 300 ms (a human cannot read an ad that fast); a publisher whose click-through rate is ten times the norm. These are counters in keyed state with sliding windows, so they cost no external calls.
  3. Model scoring (asynchronous, sampled or batched): a machine learning service scores a click's fraud probability from many features. Calling it for every event at 50k per second is expensive and adds a failure dependency, so the job batches calls and uses a timeout; on timeout it passes the click through labeled unscored and lets the later batch stage score it.
  4. Offline fraud analysis (batch): graph and cohort analysis over days of data finds coordinated behavior invisible to a single-event rule. Its output is a list of invalidated click ids or (publisher, time range) pairs, applied during reconciliation.

Filtering is therefore split in the same way as counting: the stream applies quick, conservative rules so the dashboard is roughly right, and the batch applies the heavy ones so the bill is right. Every rejected click goes to clicks.rejected with a reason code. This matters in practice for two reasons: an advertiser may dispute a charge, and a bad rule that over-blocks (say, a corporate NAT sharing one IP among 5,000 real users) must be detectable and reversible by replaying with a fixed rule. See Chapter 55 for the general abuse model.

Interview tip Say explicitly that dropping a click is a financial decision with two error directions. Letting fraud through overcharges the advertiser; blocking a real click undercharges the platform. Real systems tune toward the advertiser first (credit-back policies exist for undetected fraud), but both errors are measured.

10. Deep dive: exactly-once counting

Delivery guarantees are covered in Chapter 32; the stream engine's snapshotting is in Chapter 37. The practical statement is: no system delivers a message exactly once over a network, but you can make the effect happen exactly once by combining at-least-once delivery with idempotent or transactional processing. There are three places where duplicates or losses can enter, and each has its own fix.

BoundaryRiskFix
Producer to KafkaA send times out, the producer retries, and the broker now has two copies.Idempotent producer (broker deduplicates by producer id and sequence number within a partition). Also, application-level dedup by click id in the filter job catches what remains.

Walkthrough. The top row is the job: Kafka source, Dedup task, Window task and the OLAP upsert, joined by arrows. The red box labelled barrier N is a marker inserted into the stream, not a real click. 1. The source records its offset (1,204,500) and sends the barrier downstream along with the data. 2. When the Dedup task sees the barrier, it saves its seen-id set. 3. When the Window task sees it, it saves its minute counters. 4. Some events are processed twice, but the final upsert writes the same full value, so the count does not change. The point to say aloud is that state and offsets are saved as one consistent cut. If they were saved separately, a restore could count some clicks twice or skip some. Remove the barrier idea and you have no way to know the saved pieces belong together.

Why store the full count rather than a delta? Suppose the sink received "ad 4711, 10:03, +3" twice. A delta applied twice yields +6. A message "ad 4711, 10:03, count = 11, revision 7" applied twice yields 11. Making the unit of write a complete, revisioned value is the single most useful idempotency habit in this design. The revision number (the window's emission count) also protects against out-of-order writes: the store keeps the row with the highest revision, so a delayed write from a zombie task that survived a network partition cannot overwrite a newer value.

There is a cost: checkpoint interval trades recovery time against overhead. A 30-second interval means a crash replays at most 30 seconds (about 1.5M events at peak, which the job re-reads in seconds), but the visible output of a transactional sink only advances at checkpoint boundaries, adding up to 30 seconds of latency for the output topic. For the OLAP upsert (idempotent, not transactional), provisional results can be written immediately. That is another reason to prefer the idempotent sink for the dashboard path.

11. Deep dive: hot ads and key skew

Partitioning the aggregate job by ad id means all clicks for an ad land on one task. Ad popularity is heavily skewed (a Zipf-like distribution): during a major event one ad can receive 5% of all clicks, which is 2,500 per second at the 50k peak. A single task can count 2,500 per second without trouble, since counting is cheap, but the skew still hurts in three ways: one task runs hot while others idle (so the slowest task sets the pipeline's latency), a hot key's checkpoint state is large and uneven, and a downstream write to a single OLAP row key receives a burst. A pathological case, such as a bot attack on one ad generating 40k clicks per second, can saturate one task entirely.

The standard remedy is two-stage aggregation with key salting (the general technique is in Chapter 60 and Chapter 25).

  1. Stage 1 (partial): key by (ad_id, salt) where salt = hash(click_id) mod S. Because the click id is unique per click, the salt spreads one ad evenly over S tasks. Each task keeps a local partial count per (ad, minute, salt).
  2. Stage 2 (final): key by ad_id only and sum the S partials per (ad, minute). The data into stage 2 is tiny: at most S partial records per ad per minute per emission, regardless of click volume.
Walkthrough. On the left is the input, clicks.valid, where ad 4711 is hot at 2,500 clicks per second. In the middle are four of the partial boxes (the picture shows salts 0, 1, 2 and 7, standing for all S = 8). On the right is one Final sum box and then the OLAP store. 1. Each click arrives with its click id. The job computes the salt as hash of the click id modulo 8, so the clicks of one ad spread evenly across the eight partial boxes. The caption under the stage 1 label gives the result: about 310 per second each (2,500 divided by 8). 2. Each partial box counts its share per minute. 3. Every partial sends its small total to the Final sum box, which is keyed by ad id only. 4. The Final sum adds eight numbers per minute and upserts one row. The choice shown avoids one task taking all 2,500 clicks per second, and it works because addition can be split and merged. On a whiteboard, draw the fan-out and the fan-in as a bow tie. If you remove stage 2 you would have eight partial counts and no single answer for the ad.

The salt count S does not have to be the same for every ad. Applying 8 salts to every key multiplies state and output for the long tail of ads (millions of ads with a few clicks per minute) for no benefit. The better design detects hot keys dynamically: a lightweight heavy-hitter counter (Count-Min Sketch or a Space-Saving counter, see Chapter 57) in front of stage 1 flags ads above a threshold, say 500 per second, and only those get salted (S = 8, rising to 64 for an attack). Cold ads use S = 1. Correctness is not affected by the choice of S because the second stage always sums.

Another important option is local pre-aggregation inside each stage 1 task. Rather than emitting one event per click, the task holds a map keyed by (ad, minute) and flushes it every second. A hot ad then produces at most one partial record per task per second regardless of click rate. This reduces shuffle traffic by orders of magnitude at the cost of at most one second of added latency.

11.1 Hot rows in the store

Because stage 2 emits one cumulative value per window per revision, the store sees at most a few writes per (ad, minute) per second, not thousands. Batching upserts (a few thousand rows per request) and writing to the OLAP store's native bulk interface keeps ingest efficient, since OLAP engines are poor at one-row-at-a-time writes. Query-side hot spots (a famous advertiser's dashboard loading continuously) are served by a short-lived cache keyed by (advertiser, range) with a TTL of 10 to 30 seconds (Chapter 13); stale by 10 seconds is invisible on a minute chart.

12. Deep dive: reconciliation and billing-grade accuracy

The stream layer is fast and approximately right. The batch layer is slow and exactly right. Running both and letting the batch layer overwrite the stream layer is the Lambda architecture; the term and its alternative, the Kappa architecture (one stream pipeline, replay for corrections), are discussed in Chapter 37. For this problem I choose Lambda-style reconciliation, and I will justify it against the alternative below.

12.1 Why the stream alone is not enough for billing

  • Clicks later than the allowed lateness are not in the live counts.
  • The stream's dedup horizon is one hour. A duplicate two hours later gets counted.
  • Fraud decisions improve with hindsight: a click farm is identified only after a day of analysis.
  • Code bugs happen. A deployment with a wrong filter, discovered after four hours, must be fixable.
  • Streaming state can be lost or corrupted in rare, ugly failure combinations (a checkpoint restore from the wrong version, an operator rescaling mistake).

12.2 The reconciliation job

Walkthrough. Two lanes run left to right from the same source. The top lane is fast, the bottom lane is slow and exact. 1. On the left, Kafka clicks.raw holds recent events (7 days). A downward arrow copies every event to the Raw archive, the hourly Parquet files. 2. The Stream path box reads Kafka and writes provisional rows to the OLAP store in the middle. 3. The Batch path box (hourly) reads the archive, deduplicates everything, applies the full fraud rules and recounts exactly. 4. Its green arrow writes a higher revision flagged final into the OLAP store, replacing the provisional row. 5. The OLAP store feeds Billing on the right, and billing reads only the final rows. 6. The red Diff monitor below the store compares the two answers and alerts when the gap grows above 0.5%. The design choice is two independent counts of the same input, so one can check the other. The alternative, a single stream pipeline, has no outside check. When drawing, mark the green arrow clearly, since it is the step that makes the number billable. Without the diff monitor, a stream bug would be found only when an advertiser complains.

The flow for hour H, starting after H plus 30 minutes (to cover the 15-minute lateness window with margin):

  1. Read archive files for H-1, H and H+1 (neighbors are needed because a late click for H may sit in H+1's file by ingest time and a duplicate may sit in H-1).
  2. Deduplicate by click id across that full range.
  3. Apply the full fraud rule set plus the latest offline invalidation lists.
  4. Group by (ad, minute of event time) and count.
  5. Compare with the stream's numbers for the hour and record the discrepancy per advertiser.
  6. Write the results to the OLAP store as revision max + 1 with status final (idempotent upsert), then publish a finalized-hour event; the billing service reads only finalized hours.

Because the batch recount is a pure function of (archive files, rule version), it is deterministic and rerunnable. If rules change or a bug is found, rerun the job for the affected hours; it writes a still higher revision. An audit table stores, per (advertiser, hour), the rule version, input file list and checksum, and count produced, so any billed number can be traced to its inputs. Billing adjustments after finalization (a rerun that lowers a previous charge) go through the ledger as credit entries, never by editing history.

For money, I take Lambda, and I reduce the drift problem by making both paths share one library of parsing, dedup-key and fraud-rule code, and by testing them against the same golden data set. If an interviewer pushes for Kappa, I say it is a fair choice when the batch engine and stream engine are the same (for example, the same Flink SQL job run in batch mode over the archive), which keeps one code path while still giving an independent run from immutable input.

12.4 Replay

Replay is the safety net for everything. Within 7 days, reset the consumer group offsets of the filter or aggregate job to a time and re-run into a new output (a shadow table or a new revision namespace), validate it against the live numbers, then swap or let the revision rule take over. Beyond 7 days the archive is the source. Replay needs three properties: the job must be deterministic given the same input (no wall-clock reads inside business logic; use event time), sinks must be idempotent (so replay overwrites), and replays should be throttled so a catch-up does not starve live traffic: run on separate resources and cap at about 2x peak rate.

13. Top-K ads

"Show the ten most-clicked ads in the last 15 minutes" is a different query shape: a global ranking across many ads, which the OLAP store can answer (ORDER BY sum(clicks) DESC LIMIT 10 over 15 minute-buckets) but not cheaply if called thousands of times per second across millions of ads. The structure and theory (heaps, sorted sets, mergeable sketches) are in Chapter 59.

My design uses the same minute counts, which the stage 2 task already produces. For each minute bucket m, a Redis sorted set top:m holds ad id as member and count as score, updated by ZADD with the cumulative value (idempotent, same reasoning as above). To get the top 10 over the last 15 minutes, the query service does ZUNIONSTORE over the 15 minute keys with sum aggregation, then ZREVRANGE 0 9. With millions of members that union is expensive, so I bound it: each minute set is trimmed to the top 10,000 ads (an ad outside the top 10,000 of every single minute cannot enter a 15-minute top 10 unless adversarially spread, so the result is approximate in an extreme edge case), and the merged result is cached for 5 to 10 seconds because all dashboards want the same answer. For exact top-K the batch job recomputes from the OLAP store. Per-advertiser top-K (their own best ads) is trivial and served directly from OLAP because it ranges over only that advertiser's few hundred ads.

14. Serving queries

The query service is a thin layer in front of the OLAP store and Redis. Design points:

  • Granularity choice. The service picks the table by range: up to 6 hours uses minute rows, up to 30 days uses hour rollups, beyond that uses day rollups. A 30-day minute-level chart would pull 43,200 points per ad, far more than a screen can show. Rollups are produced by the stream/batch pipeline itself (hour rollup computed from the finalized minute rows) rather than by the query at read time.
  • Merging provisional and final. The store holds, per (ad, minute), the highest revision only. The service just reads it and returns the row's status. For the current hour, rows are provisional; for hours older than about an hour they are final.
  • Partial data honesty. The response includes the watermark. A chart can draw the part after the watermark as a dashed "incomplete" region.
  • Multi-tenancy and authorization. Every query is scoped to the caller's advertiser id taken from the verified token, never from a request parameter (Chapter 55). A noisy advertiser is rate-limited (Chapter 16) and a query cost cap (maximum rows scanned) prevents one expensive request from hurting others.
  • Capacity. About 3.3k queries per second at peak, each scanning a few hundred rows sorted contiguously by (advertiser, ad, minute), is comfortable for a small OLAP cluster with replicas; the cache absorbs repeated dashboard refreshes.

15.1 Back-pressure and burst handling

If the aggregate job slows (a bad deploy, a downstream store outage), Kafka absorbs the backlog: 10 MB per second times a 1-hour outage is only 36 GB, far below the retention capacity. The job catches up at several times the real-time rate because it is CPU-bound counting. The important property is that nothing upstream is blocked: the click tier writes to Kafka and does not care how far behind consumers are. The dashboard shows a growing "data delay" via the watermark, so staleness is visible rather than silent. Compare with a design that writes straight to a database, where the same slowdown would propagate to users (Chapter 40 on load shedding and back-pressure).

16.1 Multi-region

Clicks must be accepted wherever the user is, so the click tier runs in every region and writes to a regional Kafka cluster. Counting, however, is by (ad, minute), which spans regions. There are two choices. Option one: mirror each region's raw topic to a central region (MirrorMaker-style replication) and run one global aggregation there. This is simplest and exact, and costs one cross-region hop of seconds. Option two: aggregate in each region and merge partial counts centrally, which is cheaper in bandwidth, works because counts are additive, but makes global dedup harder (the same click id could appear in two regions after a failover). I choose option one, because 10 MB per second of cross-region traffic is trivial, and a single place for dedup and billing is worth much more than saving bandwidth. For disaster recovery the central pipeline is restorable in another region from the archive plus the latest checkpoint, with a recovery time measured in tens of minutes and a recovery point of seconds, since the mirrored log is the source (Chapter 41, Chapter 26).

17. Security, abuse, monitoring, cost

17.1 Security and abuse

  • Signed click URLs prevent forged or modified clicks, and a timestamp inside the signed payload limits replay of captured URLs.
  • The redirect target is looked up server-side from the ad id, never taken from a request parameter, to avoid an open-redirect vulnerability.
  • Privacy: IP and device id are personal data. Keep them in the raw archive under access controls and delete or hash them after the fraud-analysis retention period (for example 90 days) while retaining the aggregates indefinitely (Chapter 56).
  • Rate limit the query API per advertiser. Authenticate with tokens and scope every query to the caller.

17.3 Cost

The dominant costs are not the counting. Kafka at 10 MB per second is cheap; the OLAP cluster for 360 GB of hot minute data plus rollups is modest; the large line items are the fraud model inference (if every click is scored), the cold archive (about 20 TB per year compressed at object storage prices), and the engineers who maintain two pipelines. Levers: tier the archive to colder storage after 90 days, sample-score with the expensive model only the clicks that cheap rules mark suspicious, and drop minute-level granularity after 30 days.

18. Evolution, phasing and alternatives

18.1 What I would build first

  1. Phase 1 (MVP): click tier, Kafka, a single stream job that dedups with keyed state and counts tumbling minute windows, idempotent upsert into the OLAP store, raw archive sink, basic query API. This already gives correct (if provisional) numbers with replay.
  2. Phase 2: allowed lateness, provisional/final status, the hourly batch reconciliation with a diff monitor, and billing integration on finalized hours only.
  3. Phase 3: rule-based fraud filtering with a rejected topic, hot-key salting, top-K in Redis, hour/day rollups.
  4. Phase 4: model-based fraud scoring, multi-region mirroring, the canary and audit tables, advanced replay tooling.

18.2 At 10x scale (10 billion clicks per day, 500k per second peak)

  • Kafka: 100 to 200 partitions and more brokers; traffic becomes 100 MB per second, still modest per broker.
  • Dedup state grows to about 70 GB at a 1-hour horizon, so shorten the stream horizon to 15 minutes (the batch covers longer duplicates), and use incremental RocksDB checkpoints.
  • Hot keys become routine, so dynamic salting and local pre-aggregation are mandatory, not optional.
  • OLAP: shard across more nodes, shift storage to tiered (SSD for 7 days, object storage beyond), and pre-aggregate rollups at ingest.
  • Batch reconciliation moves from hourly to a rolling 15-minute cadence, with per-hour partitioned work to bound its size.

19. Interview Q&A

Why is a Kafka log between the click tier and the counting, instead of counting directly in the click tier?

The log makes the system durable, decoupled and replayable. The click tier's only duty is to persist the event and redirect the user, which takes milliseconds, so a slowdown or crash in aggregation never affects users or loses revenue. Because Kafka retains events for days, we can replay after bugs, add new consumers (fraud analysis, archive) without touching the click tier, and rebuild state after a failure. Counting in the click tier would lose counts on a crash, would not allow dedup across servers, and would keep no raw data for audits.

How do you make sure a click is counted exactly once?

I combine at-least-once delivery with idempotent effects at each hop. The producer is idempotent, so retries do not duplicate in Kafka. The stream job deduplicates by click id in keyed state that is snapshotted together with the input offsets, so a crash restores a consistent cut and replays only the tail. The sink write is an upsert of the full revisioned count for (ad, minute), so replays overwrite with identical values instead of adding. Finally the hourly batch job recounts from the immutable archive with global dedup, which catches anything the streaming layer missed.

What is the difference between event time and processing time, and which do you use?

Event time is when the click happened and processing time is when our system handled it. After outages, retries or offline mobile buffering, the two diverge, and counting by processing time would shift clicks into the wrong minute and produce fake spikes. I aggregate by event time because both advertisers and billing care about when the click happened. That requires a watermark to decide when a window is complete, plus an allowed-lateness policy for stragglers. I also clamp event timestamps to a sane range around ingest time so a bad client clock cannot corrupt the watermark.

How do you handle late events?

There are three tiers. Events within the watermark delay (2 minutes) are simply part of the window. Events up to 15 minutes late are handled by allowed lateness: window state is retained, the late event updates the count, and a new revision of the row is upserted. Events later than that go to a late side output and are included by the hourly batch job, which reads the archive by event time and rewrites the row as final. The dashboard exposes a provisional or final status and the watermark so users know which numbers can still move.

One ad gets 5% of all clicks. How do you avoid a hot partition?

Aggregate in two stages. In stage 1 the key is (ad id, salt) where the salt is a hash of the click id modulo S, so one hot ad is spread across S tasks, each also doing local pre-aggregation and flushing once per second. Stage 2 sums the S partial counts per ad and minute, which is a tiny amount of data. This is exact because counts are additive. To avoid paying the cost for all ads, I detect heavy hitters with a sketch and salt only those. Since the partitioning of the raw topic is by click id, ingestion is already even.

Why keep a batch job if the stream job already counts exactly once?

Because "exactly once" in the stream is limited by the information the stream has at the time. It has a bounded dedup horizon, a bounded lateness window, and only real-time fraud rules, while billing needs hindsight: very late clicks, duplicates days apart, and fraud decisions made after analysis. The batch job also gives an independent recount from immutable files, which protects against stream bugs and state corruption and gives an audit trail. The diff between the two paths is my best monitoring signal for correctness.

How would you pick the dedup storage, and what about its size?

I keep a set of recent click ids in the stream job's local keyed state (RocksDB), partitioned by click id so that all copies of a click reach the same task, and snapshotted with the offsets. At the peak rate with a one-hour horizon that is about 180 million ids and about 7 GB total across 64 tasks, which is easy. An external Redis check adds a network call per event and is not atomic with the downstream write. A Bloom filter alone is risky because a false positive would drop a legitimate paid click, though it can sit in front as a prefilter if a positive always falls through to the exact check.

Which database holds the aggregates, and why not Cassandra or a time-series database?

I use a columnar OLAP engine such as ClickHouse, Druid or Pinot, sorted by advertiser, ad and minute. The workload is a high-volume batched upsert plus range scans and group-bys across many ads, which columnar engines do well. Cassandra serves the single-ad time series well but makes advertiser-level group-bys and rollups costly, and a classic time-series database struggles with tens of millions of series. If the product only needed per-ad charts, a wide-column store would be a fine and simpler choice, so I would say that tradeoff out loud.

How do you compute "clicks in the last 5 minutes" and a top-10 board efficiently?

I store only tumbling one-minute counts and derive sliding windows by adding the last N minute buckets, so the raw events are processed once. For the top 10, the aggregate job maintains a Redis sorted set per minute with ad id and cumulative count; the query merges the last N sets and takes the top ten, with each set trimmed to a few thousand members and the merged result cached for several seconds. It is approximate only in a contrived edge case, and the batch job can produce the exact board for reports.

What if a bug in your fraud rules is discovered after six hours?

Because every raw event and every rejection is retained with the rule version, I fix the rule and replay. For the last 7 days I can reset consumer offsets and re-run into a shadow output, compare, and swap; for older data, the batch job reruns over the archive for the affected hours and writes higher revisions. Billing reads only finalized hours, and if an hour was already billed, the difference goes through the ledger as an adjustment entry with the audit record explaining it. The monitoring that detects it early is the rejection-rate band and the stream-versus-batch diff.

How do you size the number of Kafka partitions and stream tasks?

Bandwidth is not the constraint: 50k events per second of 200 bytes is about 10 MB per second. Partition count sets maximum consumer parallelism and cannot be reduced, while increasing it later changes key-to-partition mapping, so I over-provision to 64 for the raw topic. That gives roughly 780 events per second per task at peak, with plenty of headroom for catch-up at 2x. At 10x scale I would grow to 128 to 256 partitions and rescale tasks by key group.

20. Connects to, and recap

Recap

  • Log first: the click tier appends a signed, id-carrying event to Kafka and redirects; everything else is asynchronous and replayable.
  • Numbers: 1B clicks per day, 11.6k per second average, 50k per second peak, about 200 GB per day raw, about 12 GB per day of minute aggregates, about 7 GB of dedup state.
  • Aggregate by event time with tumbling minute windows; derive sliding windows from the buckets; use a watermark with 2 minutes of tolerance, 15 minutes of allowed lateness, and a late side output for the rest.
  • Dedup by click id in checkpointed keyed state; fraud filtering in layers (edge, stateful rules, model, offline), recording every rejection with a reason.
  • Exactly-once effect: idempotent producer, checkpointed state plus offsets, idempotent upsert of full revisioned counts.
  • Hot ads: salt into S sub-keys, pre-aggregate locally, and sum in a second stage; salt only detected heavy hitters.
  • Store minute, hour and day aggregates in a columnar OLAP engine; top-K in Redis sorted sets; status and watermark in every response.
  • Lambda-style hourly batch recount from the immutable archive produces final numbers, feeds billing, and its diff against the stream is the main correctness alarm.
  • Failures degrade to lateness, not loss: Kafka buffers, the spool covers a Kafka outage, replay repairs bad logic.
