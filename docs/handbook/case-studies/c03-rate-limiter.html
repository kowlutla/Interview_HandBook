Design a Rate Limiter

A rate limiter is a small service that sits on the hot path of every request and answers one question in well under a millisecond: "may this caller proceed right now?" Chapter 16 taught the algorithms. This page designs the whole service around them: where it lives, how rules reach it, how counters stay correct across hundreds of machines, what happens when it breaks, and how it is operated.

How to approach this problem (read this first)

"Design a rate limiter" is a prompt where it is easy to recite an algorithm and stop. This section shows how to start, what order to think in, and where the real marks are.

What the interviewer is really testing

Knowing token bucket versus sliding window is only the entry ticket. The harder parts are these. First, correctness when many gateway nodes update the same counter at the same moment (the race). Second, staying inside a sub-millisecond budget when a shared store is a network hop away, which leads to the local plus global hybrid. Third, what the system does when the limiter itself fails, because it sits on the path of every request. A strong answer treats the limiter as a decision function, a state store and a control plane.

The thinking order, step by step

  1. Pin down what and who. Ask: is this a library or a platform, who is limited (user, key, tenant, IP), and are limits hard or soft? Say: "I want to know who we limit and how strict we must be before I pick an algorithm." This comes first because hard versus soft decides how much accuracy you may trade for speed later.
  2. Ask about scale, latency and failure. Say: "What is peak traffic, what latency may the check add, and should the API fail open or closed if the limiter dies?" These three questions drive the architecture, so get numbers: 600,000 requests per second at peak, under 1 ms, and a per-rule failure policy.
  3. Estimate evaluations, state and Redis operations. Say: "Two rules per request makes 1.2 million evaluations per second, and 50 million keys at about 150 bytes is only 7.5 GB, so memory is fine but operations per second is the constraint." Do traffic first, then state, because the comparison shows which resource is the bottleneck.
  4. Choose where the check runs. Say: "The gateway sees the authenticated identity, so it is the main enforcement point; the edge handles floods." Placement comes before algorithms because it decides what information you have.
  5. Pick the algorithm and the state layout. Say: "Token bucket by default, because it allows bursts and stores two numbers per key." Then show the key format and the control-plane API for rules.
  6. Show the race, then fix it. Say: "A read followed by a write lets two nodes both pass on one token; I will make it a single atomic script on the shard that owns the key." This is the first thing an interviewer probes, so reach it before they have to ask.
  7. Fix the latency problem. Say: "A Redis call per request costs most of the budget, so nodes lease blocks of tokens and decide locally." Present this as the response to the number you computed in step 3.
  8. Cover rules, hot keys, multi-region and failure. Briefly: versioned rules with shadow mode, key splitting for giants, regional budgets, and degraded local limits when Redis is down.

The decision points

  • Library or separate service? Ask: can I afford an extra network hop on every request? No, so embed the engine in the gateway and keep a thin RPC front for other languages.
  • Which algorithm? Ask: do customers need bursts, and is memory per key a concern? Token bucket for most rules, sliding window for strict smooth limits, a log only for tiny limits.
  • Exact global count or leased local count? Ask: how bad is a few percent over-admission? For commercial limits it is fine, so leases; for login attempts use exact checks.
  • Fail open or fail closed? Ask: is allowing unlimited traffic worse than an outage? Usually no, so degrade to local limits; fail closed only for security or costly endpoints.
  • One global store or per-region budgets? Ask: can the request wait 100 ms across regions? No, so split the limit into regional shares and rebalance in the background.

Common mistakes on this problem

  • Describing only the algorithm. Fix: add state, atomicity, rule distribution and failure policy.
  • Read-then-write on the counter. Fix: use one atomic script on the owning shard.
  • Calling Redis for every request and ignoring latency. Fix: compute the budget and add local leases.
  • Using only per-IP limits. Fix: layer IP, key, tenant and backend limits; IPs can be shared or rotated.
  • No answer for limiter failure. Fix: state the policy per rule and alert on fallback.
  • Timestamps from gateway clocks. Fix: take time from the store inside the script.

1. Problem statement and clarifying questions

The prompt is usually one line: "Design a rate limiter." That line hides a dozen decisions, so the first minutes of the interview are for narrowing it. A rate limiter restricts how many requests a caller may make in a period of time. The reasons to build one are protective (stop one noisy or malicious caller from exhausting a shared system), commercial (enforce what a customer paid for) and fairness-related (make sure one tenant cannot starve the others). Following the framework in Chapter 1, I would ask the questions below and state the answer I will assume for each.

QuestionAssumed answer
Is this a library inside one service, or a shared platform for many services?A shared platform used by an API gateway and by internal services. One team owns it, many teams configure rules.
Who is limited?Several identities: authenticated user, API key, tenant (an organization that owns many users and keys), and anonymous callers identified by IP address. A single request can be checked against several of these at once.
What is limited?Request counts per time window (for example 100 requests per second), with optional weighted cost per request (an expensive search costs 5 units). Also long-horizon quotas such as 1 million calls per month.
Hard or soft limits?Hard for abuse protection (must never be exceeded by much). Soft, meaning approximate by a few percent, is acceptable for commercial limits because the cost of being slightly generous is small.
What scale?200,000 requests per second on average across all APIs, with peaks of 600,000 per second. About 50 million distinct active keys in any hour.
Latency budget?The limiter adds under 1 ms at p99 to a request when the decision is made in the data path. It must not become the slowest part of a 20 ms API call.
Single region or global?Several regions, each serving its local users. Global limits (a tenant's total across regions) must exist but may be approximate.
What if the limiter itself is down?This is a product decision, so I will propose a default per rule: fail open for ordinary traffic, fail closed for expensive or security-critical endpoints (section 14).
Do callers need to see their state?Yes. Responses carry the remaining budget and, on rejection, how long to wait, so well-behaved clients can slow down on their own.
Interview tip Say out loud that "rate limiter" is really three things: a decision function (the algorithm), a state store (counters shared across machines) and a control plane (rules, plans, overrides). Most weak answers describe only the first.

2. Requirements

2.1 Functional

  • Check a request against one or more rules and return allow or deny, together with the remaining budget and a retry delay.
  • Rules are selected by dimension: endpoint or API group, HTTP method, identity type, plan tier. Example: "free tier, POST /v1/search, per API key: 10 per second, burst 20".
  • Support weighted cost (one request may cost more than one unit).
  • Rules can be created and changed at runtime, take effect within seconds everywhere, and can be rolled back. Per-customer overrides exist (a premium customer negotiates 5x the plan default).
  • Reject over-limit requests with HTTP 429 and standard headers.
  • Long-horizon quotas (daily and monthly) with usage reporting for billing and dashboards.
  • A "dry-run" or shadow mode in which a new rule logs what it would have blocked without blocking.

2.2 Non-functional

  • Latency: under 1 ms p99 added per check. Local in-process checks well under 100 microseconds.
  • Availability: higher than the services it protects, ideally 99.99 percent. A limiter outage must never cause an outage of the API (this drives the failure policy).
  • Accuracy: for hard rules, no more than a few percent over the configured rate in steady state; for burst edges slightly more is tolerable.
  • Scale: 600,000 checks per second at peak, 50 million live keys, horizontally scalable.
  • Consistency: concurrent requests from many gateway nodes must not be able to bypass the limit through races.
  • Operability: every decision observable, every rule change auditable.

2.3 Out of scope

Full DDoS mitigation at the network layer (volumetric attacks belong to the edge, CDN and scrubbing providers; see Chapter 12 and Chapter 55), bot-detection machine learning, billing and invoicing (we only emit usage), and concurrency limiting of in-flight work, which is related but a different mechanism (we mention it in Q&A).

3. Estimation

Estimation here tells us whether the state fits in one Redis, how many shards we need, and whether the network cost of a central check is acceptable. The method is from Chapter 2.

3.1 Traffic

  • Average: 200,000 requests per second. Peak factor 3 gives 600,000 requests per second.
  • Each request is checked against on average 2 rules (a per-key rule and a per-tenant rule; anonymous traffic adds a per-IP rule). That is 1.2 million rule evaluations per second at peak, 400,000 at average.
  • If every evaluation went to Redis, we would issue 1.2M Redis operations per second. We will show later that local pre-allocation of tokens cuts this by about 10x for hot keys.

3.2 State size

  • 50 million live keys. A token bucket stores two numbers (tokens and last-refill timestamp). With the key name (about 40 bytes, for example rl:t:acme:k:9f2c:search), a small hash structure and Redis per-key overhead, assume about 150 bytes per key.
  • 50,000,000 × 150 B = 7.5 GB. With one replica per primary the cluster holds 15 GB in RAM. This is small enough that memory is not the bottleneck: operations per second is.
  • Keys carry a time-to-live equal to twice the time to refill a full bucket, so idle keys disappear on their own. A key that has not been used for an hour holds no information we need.

3.3 Redis throughput and sharding

  • A single Redis primary executing small Lua scripts typically sustains on the order of 80,000 to 120,000 operations per second (it is single-threaded for command execution). Plan for 75,000 at peak for headroom.
  • Without any local optimization: 1,200,000 ÷ 75,000 = 16 primaries. With the hybrid design (section 10), roughly a tenth of evaluations reach Redis for hot keys. We still keep 16 primaries (plus 16 replicas) to absorb spikes, shard skew and failover, which gives 7.5 GB ÷ 16 = about 470 MB of data per shard.

3.4 Network and latency

  • A Redis round trip inside one availability zone is typically 0.2 to 0.5 ms; across zones about 0.5 to 1 ms. That alone eats most of a 1 ms budget, which is why the hybrid design keeps the common case in process.
  • Bandwidth: a check is about 100 bytes out, 50 bytes back. 1.2M × 150 B = 180 MB/s, about 1.4 Gbit/s across the cluster. Trivial per node.

3.5 Quota counters

Daily and monthly quotas are low-rate and high-cardinality. 5 million paying API keys × a few counters each is tens of millions of counters, updated asynchronously in batches (section 15), so they add under 5 percent to the request path load.

4. API design

4.1 Data-plane check

The gateway or service calls the limiter library (in-process) or, when a remote limiter service is used, a lightweight RPC (gRPC over a persistent connection, see Chapter 5):

CheckRequest {
  string  request_id;        // for tracing and idempotent retry
  string  tenant_id;         // "acme"
  string  principal_id;      // user id or API key id, empty if anonymous
  string  client_ip;         // already resolved by the trusted edge
  string  resource;          // "POST /v1/search" normalized to a route template
  uint32  cost;              // default 1
}
CheckResponse {
  bool    allowed;
  string  limited_by;        // rule id that denied, for diagnostics
  int64   limit;             // the policy limit of the tightest rule
  int64   remaining;         // tokens left in the tightest rule
  int64   reset_after_ms;    // time until bucket is full again
  int64   retry_after_ms;    // only when denied
}

The limiter evaluates all rules matching the request and returns the verdict of the tightest one. The response reports the tightest rule's numbers, because that is what the client must respect.

4.2 Control-plane API

PUT    /v1/rules/{rule_id}          { match, key_by, algorithm, limit, window, burst, mode: "enforce"|"shadow", fail_policy }
GET    /v1/rules?resource=...       list with versions
POST   /v1/rules/{rule_id}/rollback { to_version }
PUT    /v1/overrides/{tenant_id}    { rule_id, limit, expires_at }
GET    /v1/usage/{tenant_id}?period=2026-11  quota consumption

Rules are versioned and immutable once written; an update creates version N+1. That gives rollback, audit and a clean way for nodes to report "I am running version 412".

4.3 What the client sees

Over HTTP, an allowed request carries informational headers and a denied one returns status 429 (Too Many Requests), detailed in section 13.

5.1 Key design

The key encodes rule, identity and, for window algorithms, the window index:

rl:{tenant}:{rule_id}:{principal}            token bucket: hash {tokens, ts}
rl:{tenant}:{rule_id}:{principal}:{window}   fixed window counter: integer (TTL = 2 x window)
quota:{tenant}:{plan_period}                 monthly usage counter

The part in braces is the Redis Cluster hash tag: only the text inside the first braces is hashed to pick the shard, so all of a tenant's keys land on the same shard. That is convenient for multi-key scripts but dangerous for hot tenants (section 12). For per-principal rules I tag with the principal instead, so one big tenant's many keys spread across all shards.

6. A first simple design, then placement

6.1 The simplest thing that works

One application server keeps a hash map from key to a token bucket in memory and checks it before handling each request. This is correct, extremely fast (tens of nanoseconds) and needs no infrastructure. It breaks the moment we run two servers behind a load balancer: each has its own map, so a limit of 100 per second becomes 100 per second per server, and the effective limit changes whenever autoscaling adds a node. We need either shared state or coordination between the servers, and we need to decide where the check physically happens.

Decision. Build one limiter engine as a library plus a shared state store, and embed it in the gateway (primary enforcement) and, where needed, in services and sidecars. Edge limits are configured with the CDN vendor. Doing it as a library rather than a standalone "limiter service" removes a network hop from the data path: the decision is made inside the gateway process, and the only remote call is to Redis, and only when the local state cannot decide. A standalone service has real advantages (one implementation, many languages) and is a reasonable choice for polyglot internal callers, so I keep a thin gRPC front for those.

7. High-level architecture

Walkthrough. The upper area is the data plane, the part every request touches. 1. Clients reach a Gateway node, repeated N times. 2. Inside it the Limiter engine reads the Rule snapshot (in memory, versioned) and the Local buckets (leases and hot keys). 3. Only when local state cannot decide does the engine send a Lua check to the Redis Cluster, drawn as 16 shards each with a replica. 4. Allowed requests continue to the Backend. The lower area is the control plane: an Admin UI writes to the Rule DB, a Config service pushes snapshots to the gateways, and a Usage pipeline collects decisions through Kafka. The point of the layout is that the control plane never sits on the request path, so it can be down and requests still get decisions from the cached snapshot. Point at the snapshot push arrow. If you remove the local buckets, every check becomes a Redis call.

Components in one sentence each:

  • Limiter engine (library): matches the request to rules, computes keys, checks local state, falls back to Redis, returns a verdict. Pure logic plus two caches.
  • Rule snapshot: a compiled, versioned, read-only copy of all rules held in memory; lookups are a hash-map hit. Swapped atomically on update.
  • Local buckets: in-process token state, used for the hybrid mode (section 10) and for per-IP flood protection when Redis is unreachable.
  • Redis Cluster: 16 primary shards, each with a replica, holding the authoritative global counters.
  • Config service: serves the latest snapshot to nodes via a push stream with periodic polling as a backstop.
  • Usage pipeline: asynchronous, aggregates decisions and quota consumption for billing and dashboards.

8. Request flows

8.1 Check a request (allowed and denied paths)

Walkthrough. This sequence diagram has four participants: Client, Gateway plus engine, Redis shard and Backend. 1. The Client sends a request with an API key. 2. The gateway authenticates and resolves tenant and plan. 3. It matches rules from the in-memory snapshot and builds the keys. 4.   1. The request arrives at a gateway node with credentials.
  2. Authentication resolves the API key to a tenant and plan (cached; Chapter 55). The limiter runs after cheap authentication so it can key by identity, but before expensive work. Unauthenticated floods are caught by IP limits at the edge before this step.
  3. The engine finds the matching rules in the snapshot: for example "per-key 100/s on search" and "per-tenant 1,000/s across all APIs", plus an IP rule for anonymous callers.
  4. For each rule it builds the key and consults local state. If a local lease has enough tokens, it takes them and decides in microseconds.
  5. Otherwise it executes the atomic Lua script on the shard that owns the key.
  6. Redis refills, compares and decrements in one indivisible step.
  7. The verdict returns. The engine combines per-rule verdicts (deny if any rule denies) and, when denying, avoids having consumed tokens from the other rules (section 9.3).
  8. Allowed requests go to the backend with rate-limit headers attached to the response; denied ones return 429 immediately.

8.2 Update a rule

  1. An operator calls PUT /v1/rules/{id}. The control plane validates it (sane limits, matching syntax, no rule that matches everything with limit 0), writes version N+1 transactionally, and records who changed it.
  2. The config service compiles a new snapshot, and pushes it to subscribed nodes. Nodes also poll every 30 seconds, so a missed push heals itself.
  3. Each node validates the snapshot (checksum, schema), builds the new lookup structures off to the side, then swaps one pointer. In-flight checks finish on the old snapshot; new ones use the new snapshot. There is no lock on the read path (section 11).

9. Deep dive A: atomic counters and race conditions

The algorithms (token bucket, leaking bucket, fixed window, sliding window log and counter) are compared in Chapter 16. Here I assume we chose the token bucket as the default (allows a configured burst, needs only two numbers per key) and use the sliding window counter for rules where a smooth, strict window matters. The hard part at service level is making the shared counter correct under concurrency.

9.1 The race

The naive implementation reads the counter, decides, and writes it back as separate commands. Two gateway nodes doing this concurrently can both read "1 token left", both decide "allowed" and both write "0". The limit was 1, two requests passed. With 100 gateway nodes and a hot key this is not rare; it is the normal case.

Walkthrough. The figure has two halves. The left half is the broken approach with three columns: Node A, the Redis key and Node B. 1. Node A sends GET tokens and receives 1. 2. Node B sends GET tokens and also receives 1, before A has written anything. 3. A sets 0 and treats its request as allowed. 4. B also sets 0 and also treats its request as allowed. Two requests passed on one token. The right half shows the fix: both nodes send the same EVALSHA script. Redis runs the script as one unit, so A runs first, finds one token, takes it and is allowed; B runs second, finds none and is denied. The lesson is that the gap between read and write is where the bug lives, and the alternative of WATCH retries or a lock costs more round trips. On the whiteboard draw the two GET arrows crossing in time. Remove the script and the limit is only advisory under concurrency.

The token bucket script, in essence:

-- KEYS[1] = bucket key
-- ARGV[1] = capacity (burst), ARGV[2] = refill tokens per second, ARGV[3] = cost
local t   = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)       -- ms, from Redis's own clock
local d   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local cap, rate, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local tokens, ts = tonumber(d[1]), tonumber(d[2])
if tokens == nil then tokens = cap; ts = now end
tokens = math.min(cap, tokens + math.max(0, now - ts) * rate / 1000)
local allowed, retry = 0, 0
if tokens >= cost then tokens = tokens - cost; allowed = 1
else retry = math.ceil((cost - tokens) / rate * 1000) end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return { allowed, math.floor(tokens), retry }

Three details matter. First, the time source is Redis's own clock (TIME), not the gateway's. Gateway clocks drift and differ by milliseconds to seconds (Chapter 27); with a single authoritative clock per key, refill is monotonic and consistent. Second, the script is loaded once and called by its SHA hash (EVALSHA), so only a short identifier and the arguments cross the network; clients reload on a "script not found" error after a failover. Third, the TTL is refreshed on every call and set to twice the refill time: a key idle for longer than a full refill is indistinguishable from a new one, so deleting it loses nothing.

9.3 Multiple rules per request

If a request must pass a per-key rule and a per-tenant rule, checking them one after another can consume a token from the first rule and then be denied by the second, wasting a token and under-serving the caller. Options: (a) check the most restrictive or cheapest-to-recheck rule first and accept the small leak; (b) put all keys of one request on the same shard (same hash tag) and run one script over several keys, which is fully atomic but concentrates load; (c) check-then-refund: if a later rule denies, send a refund for earlier ones. In practice I choose (a) with a refund for the one case of a denied multi-rule request, because per-key and per-tenant keys usually live on different shards, and the over-consumption is a few tokens on a request that was going to be rejected anyway. State this tradeoff explicitly in an interview; it shows you saw the problem.

10. Deep dive B: local plus global hybrid

A remote check per request costs a network round trip (0.3 to 1 ms) and puts every request on Redis's critical path. At 1.2M evaluations per second we would also need a big cluster. The observation that fixes both: most traffic is concentrated in few keys, and for those keys an exact answer is not needed on every call. So we split the decision between a local layer in each gateway node and a global layer in Redis.

10.1 The lease (token prefetch) approach

A gateway node does not ask Redis "may this one request pass?". It asks "give me a lease of up to L tokens for this key". Redis atomically subtracts up to L tokens from the global bucket and returns the amount actually granted. The node then serves the next L requests for that key from its local copy, with no network at all. When the local lease runs out, it takes another. The global bucket still never hands out more than its configured rate; the error is only that tokens leased to one node may sit unused while another node is starved.

Walkthrough. Three Gateway nodes are drawn on the left, each with a local lease count: node 1 has 12 left, node 2 has 0 left, node 3 has 40 left. The Redis global bucket on the right holds 930 tokens for tenant acme on the search rule, with limit 1000 per second and burst 2000. 1. A request arrives at a node and takes one token from its local lease, deciding in about one microsecond with no network call. 2. Node 2 has run out, so it asks Redis for a lease of 50. 3. Redis grants 50 and the global count drops to 880. 4. Node 2 now serves its next 50 requests locally. The note at the bottom says lease size adapts and unused leases expire after roughly 100 ms. This design avoids both a Redis call per request and nodes dividing the limit by node count blindly. Point at the global bucket as the single record of grants. If you remove it, nothing bounds the total.

10.2 Sizing the lease and the error

  • For a key with limit R tokens per second spread over N nodes, a fair per-node share is R ÷ N. Take a tenant limited to 1,000 per second on 20 nodes: 50 per second per node. If a node leases 10 tokens at a time, it calls Redis about 5 times per second per key instead of 50, a 10x reduction. That is the source of the "about a tenth reach Redis" figure in section 3.3.
  • The worst-case over-admission is bounded by tokens held in unexpired leases. If leases expire after 100 ms, then stranded tokens are at most about R × 0.1 per second window, so about 10 percent of one second's budget in the worst case at the edge of a refill boundary, usually far less. For a hard security rule use L = 1 (always go to Redis); for a commercial rule 5 to 10 percent error is acceptable.
  • Small keys (low R) lease nothing and go to Redis every time, since they are rare and their exactness matters more. Rule of thumb: lease only when R × lease-time is at least a few tokens.

10.3 Alternatives compared

The lease design has a property that is easy to defend: the global bucket is still the single source of truth for what has been granted. A bug or a lost node can only strand tokens (under-admission) or, through lease expiry timing, slightly over-admit; it cannot multiply the limit by the number of nodes. In contrast, the periodic-sync approach lets all nodes spend freely between syncs and its overshoot grows with the node count.

10.4 Degraded mode

The same local state doubles as the fallback when Redis is unreachable: each node falls back to a conservative local rule (limit ÷ expected node count, with a safety factor), so protection degrades gracefully rather than vanishing. Section 14 builds on this.

11. Deep dive C: rule configuration and hot reload

Rules change daily in a busy platform: a new endpoint needs a limit, a customer upgrades, an incident calls for tightening a limit within minutes. The requirements are fast propagation, no downtime, safety against bad rules, and no dependence on the control plane at request time.

Walkthrough. Follow the left-to-right path. 1. An Operator sends PUT for rule version 413. 2. The Rule DB validates and records an audit entry. 3. The Config service compiles a new snapshot. 4. It pushes the snapshot to Gateway A, which applies version 413 within about a second. 5. Gateway B is late and still on version 412, but it polls every 30 seconds and heals. The box at the bottom lists what a node checks before applying: checksum, schema, a sane rule count (not zero) and no limit below a floor; then it builds the new index aside and swaps one reference, keeping the previous snapshot as a rollback target. Push gives speed and polling gives safety, which avoids relying on one mechanism. Point at the validation box, because a bad rule is the biggest risk here. Without the swap-one-reference step, a reader could see half of a new rule set.

11.1 Rule shape

{ "id": "search-per-key", "version": 413,
  "match":   { "resource": "POST /v1/search", "plan": ["free", "pro"] },
  "key_by":  ["api_key"],
  "algorithm": "token_bucket",
  "limit":   { "rate": 10, "per": "second", "burst": 20 },
  "cost":    1,
  "mode":    "enforce",           // or "shadow"
  "fail_policy": "open" }

11.2 Mechanics

  • Source of truth plus cache. The database holds all versions. Nodes hold the latest compiled snapshot in memory and never read the database on the request path. The snapshot is also persisted to local disk, so a node that restarts while the config service is down still starts with the last known rules.
  • Atomic swap. A snapshot is immutable. The engine reads one reference at the start of a check and uses it throughout. Publishing is one reference assignment, so readers never see half of a rule set and need no lock.
  • Match speed. Rules are indexed by resource and plan in hash maps so matching is a few lookups, not a scan over thousands of rules. Compile regex or path patterns once at snapshot build.
  • Changing limits live. Changing a rate must not reset buckets to full (that would hand every caller a burst). The key's identity does not include the limit; the script receives the limit as an argument each call, so the new limit applies on the next refill computation. Shrinking a burst caps tokens at the new capacity immediately via math.min in the script.
  • Safe rollout. New rules start in shadow mode (count and log would-be denials, never deny) for a day, then are flipped to enforce, optionally on a percentage of nodes first (canary; see Chapter 43). Validation rejects obviously dangerous rules (a wildcard match with limit 1 would deny nearly everything).
  • Overrides and expiry. A per-tenant override has an expiry timestamp, so temporary increases during a migration do not become permanent by accident.
  • Consistency across nodes. During propagation, nodes may briefly run different versions. This is harmless for limits (the shared counters in Redis do not care which node's snapshot computed the limit argument; they differ only transiently). Each response's decision event includes the snapshot version, so an incident review can tell exactly which rules applied.

More on config distribution and discovery patterns is in Chapter 49.

12. Identity keys, hot keys and abuse

12.1 Choosing the key

KeyGood forPitfalls
User idPer-user fairness on a logged-in productAvailable only after authentication; one human can make many accounts
API keyDeveloper APIs; maps to a planKeys leak and can be shared; a tenant can mint many keys, so also limit per tenant
Tenant / organizationThe unit that pays; stops one customer starving others (Chapter 42)A large tenant is a hot key; one noisy user inside a tenant can burn the tenant's budget
IP addressAnonymous traffic, login, signup, scrapingMany users behind one NAT or corporate proxy; attackers rotate IPs; IPv6 gives each client a huge range
Composite (for example tenant + endpoint)Different budgets per resourceKey explosion if a field is high-cardinality (never key by full URL or query string)

Apply limits in layers: a small per-IP limit before authentication, per-key limits after, a per-tenant ceiling over all keys, and a global limit protecting each backend. The tightest layer wins, and each layer protects a different failure: IP limits stop floods before auth work, key limits stop one script, tenant limits stop key farming, global limits stop everything stacking up.

12.2 Getting the real client IP

Behind proxies the socket address is the load balancer's. The limiter must use the client address that the trusted edge wrote (for example the right-most untrusted entry of X-Forwarded-For, counting only known proxy hops). Trusting the header blindly lets an attacker send a fake value per request and dodge any IP limit, or frame another user by spoofing their IP. For IPv6, key on a prefix (typically /64) because one subscriber controls a whole /64.

12.3 Hot keys

A hot key is one key receiving a disproportionate share of checks, such as one huge tenant at 50,000 requests per second. All its traffic lands on one Redis shard, because a key lives on exactly one. That shard may saturate even though the cluster is idle. Mitigations, in order of preference:

  1. Leases (section 10) cut calls to that shard roughly 10x, which usually solves it.
  2. Key splitting: divide a big tenant's limit into S sub-buckets (rl:acme:search#0 .. #7), each with limit/S, and pick a sub-bucket by random or by node. Calls spread over S shards at the cost of accuracy (a sub-bucket may be empty while another has tokens); retry once on a different sub-bucket to smooth it.
  3. Dedicated shard or local-only handling for known giants, with periodic reconciliation.
  4. Replica reads are not an option because a check writes; only the primary can serve it.

The general tools for skew are in Chapter 25 and Chapter 14.

12.4 IP rotation and distributed abuse

An attacker with a botnet or a rotating residential proxy pool uses a different IP per request, so each IP stays under its limit while the total is massive. Per-IP limits alone cannot stop this. Defences layered on top:

  • Limit by something the attacker cannot rotate cheaply: authenticated account, API key, device or session token, payment instrument. Require sign-in for expensive endpoints.
  • Aggregate limits at coarser granularity: per /24 subnet or per ASN (the network operator), per user agent fingerprint combined with TLS fingerprint, and a global limit per endpoint that protects the backend regardless of who is calling.
  • Progressive friction instead of a hard block: after suspicious behaviour, require a proof-of-work or CAPTCHA, or add delay, so legitimate users behind a shared IP are not locked out.
  • Reputation and anomaly signals fed from a separate system (known proxy lists, velocity of new accounts), which adjust the rule applied to that caller. We expose a hook to tighten a key's limit dynamically; the detection model itself is out of scope.
  • Cost asymmetry: make the expensive endpoint cost more tokens, so volume of cheap requests cannot be converted into expensive work.
Watch out Keying by IP alone punishes shared networks (a university or mobile carrier NAT with 100,000 users) and fails against rotation. Always pair IP limits with identity-based limits and use generous IP thresholds on endpoints that legitimate users share.

13. Headers and the 429 response

A limiter is a contract with client developers. The more clearly it communicates, the less retry traffic it has to absorb. The status code is 429 Too Many Requests, defined in RFC 6585. A denied response should carry:

HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 3
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 3

{ "error": "rate_limited", "message": "Per-key limit of 100 requests per second exceeded",
  "limit": "search-per-key", "retry_after_ms": 2400, "docs": "https://example.invalid/limits" }
  • Retry-After is a standard header giving seconds to wait (or an HTTP date). It is the one clients must honour.
  • RateLimit-Limit / Remaining / Reset follow an IETF draft for rate-limit header fields; many APIs still use the older de facto X-RateLimit-* names (reset is sometimes a Unix timestamp, sometimes seconds; document which you use). Because the draft is still evolving, say in an interview that you would publish whichever convention the API already uses and keep it stable.
  • Include the headers on successful responses too, so clients can slow down before hitting the wall.
  • The body names the rule that triggered (limited_by) so developers know whether they hit a per-key or per-tenant limit.
  • Use 503 with Retry-After for load shedding that is not tied to the caller's own rate, so the client does not conclude its own usage was at fault.

13.1 Making clients behave

Without guidance, clients retry instantly and make overload worse. SDKs should implement exponential back-off with jitter (random spread of retry times; see Chapter 40) and always prefer the server's Retry-After over their own guess. The server can also penalize pathological retry loops: deny responses are cheap, but a client hammering a denied key can be given a longer cool-down.

13.2 Cost of denial

A 429 should be the cheapest response the system produces: no body templating from a database, no logging at full detail for every one (sample them, section 17), no new connection work. Under attack, denial throughput is what keeps you alive.

14. Latency budget, failure modes and fail-open versus fail-closed

14.1 Sub-millisecond budget

Walkthrough. This is a stacked time budget, not a flow. The whole bar is 1,000 microseconds, the p99 added to a request. The small segments are the near-free parts: authentication id about 50, rule match about 20, local state about 30. The large segment is the Redis round trip, 400 to 500 microseconds, which only happens on a lease miss. The remainder is headroom, 200 to 300. Read it as two cases. In the common case, a lease hit covering about 90 percent of checks, the total is about 100 microseconds or less. In the slow case, a lease miss, the total is about half a millisecond. A hard 5 ms timeout on the Redis call turns a slow store into a failure that the fail policy handles, instead of an unbounded wait. The design avoids a design where every check pays the network cost. Point at the Redis segment and say everything else must be nearly free.

Practices that protect the budget: persistent pooled connections (no TCP or TLS setup per check), the script pre-loaded and called by hash, pipelining when several rules map to the same shard, deploying gateway and Redis in the same zone or preferring same-zone shards via replica placement, keeping the script O(1), avoiding large keys, and enforcing a strict client timeout (about 5 ms; a decision that is late is worse than a decision that is approximate). Requests are not delayed waiting on slow shards: after the timeout the fail policy decides.

14.3 Fail open versus fail closed

When the limiter cannot reach its state, the gateway must choose. Fail open means allow the request. Fail closed means deny it. Neither is universally right, and an interviewer expects you to choose per case and to explain why.

PolicyBehaviourPick it when
Fail openAllow, count locally, alertThe limiter is a protection layer, not a correctness layer; an outage of it should not become an outage of the product. Most read APIs and commercial limits.
Fail closedDeny with 503 and a short Retry-AfterAllowing unlimited traffic is more dangerous than an outage: password-guessing and OTP endpoints, SMS and email sends that cost real money, calls to a fragile or metered third party.
Degrade to local limits (default)Switch to conservative per-node limits derived from the ruleBest of both: keeps flood protection and keeps the service up. Use it for nearly everything and reserve strict fail-closed for security-critical rules.

Because the limiter is on the path of every request, its availability multiplies into the product's: if it were a hard dependency at 99.9 percent, the product could never exceed that. Failing open or degraded makes the limiter soft-dependent, so the API's availability is no longer capped by it. This reasoning is a good thing to say out loud. Track how often fallback is active as a first-class metric: a limiter that has silently been failing open for a week provides no protection.

15. Scaling: sharding, quotas, tiers and multi-region

15.1 Sharding the counter state

Redis Cluster splits the key space into 16,384 hash slots spread over the primaries; a key's slot is a hash of the key (or of its hash tag), so the client library routes each call to the right node and follows redirects when slots move. We use consistent distribution by key, which means each bucket lives on exactly one primary and every node that checks that key reaches the same shard; that single home is what makes the atomic script sufficient for correctness. Adding capacity means adding primaries and migrating slots online; during migration a slot's keys may be briefly unavailable or redirected, which the client handles. See Chapter 25 and Chapter 57 for the hashing background. If the client library does the routing itself (no proxy), each gateway node holds connections to all 16 primaries, a small number.

Two alternatives we did not choose: a proxy tier such as a Redis-aware proxy (adds a hop in the latency budget) and a bespoke limiter state service with its own storage (more to build; Redis already gives TTL, atomic scripting and replication).

15.2 Quotas versus rate limits

These are different tools and the interview often tests whether you separate them.

Rate limitQuota
Question answeredHow fast may you go?How much may you use in total?

Quota implementation: a counter per tenant per period in Redis, incremented by the request cost. Checking it on every request is cheap (one increment). To avoid hammering Redis, nodes accumulate usage locally and flush deltas to Redis and to the usage pipeline every second or so, while the lease mechanism applies to quota too (take a block of quota). Redis is not the billing record: usage events stream through Kafka into a durable aggregate (Chapter 34), keyed by an event id so replays are idempotent (Chapter 32). If Redis loses a counter, it is rebuilt from the durable aggregate plus recent events. Periods reset by key name (the period is part of the key, quota:acme:2026-11), not by a scheduled job that must run at midnight, so there is no reset race and old periods expire by TTL.

15.3 Tiered plans

Plans map to rules by data, not code. A plan is a named bundle of limits, and a tenant has a plan plus optional overrides:

The gateway resolves tenant to plan from a cached lookup (refreshed on plan change events) and builds keys from plan-specific rules. Upgrades take effect within the cache refresh interval. A rate limiter should also support cost weighting: an endpoint that fans out to 10 backend calls costs 10 tokens. Fairness between tenants is also served by reserving headroom: the sum of per-tenant ceilings may exceed system capacity (oversubscription is normal), so a global per-backend limit sits underneath to protect against many tenants peaking together.

15.4 Multi-region

Walkthrough. Three region boxes (US, EU, APAC) each hold a Redis with a local budget (60, 30 and 10) and gateways that check only their own Redis. Below is the Global reconciler. 1. A request arrives in its nearest region and is checked against that region's share, with no cross-region call. 2. Every few seconds the reconciler reads each region's usage. 3. It recomputes the split of the tenant's global limit of 100 per second by recent demand and moves budget between regions. The shares sum to the global limit, which is why the worst case is overshoot only within one rebalance interval. This avoids one global Redis, which would put 50 to 200 ms on remote requests, and avoids regions that never learn about each other. Point at the dotted reconciler lines as background only, off the request path. If the reconciler is removed, each region keeps its last share and a shifted workload gets wrongly throttled.

A cross-region round trip costs 50 to 200 ms, far above our 1 ms budget, so the request path must never call another region. Options:

My default: split each global limit into regional shares proportional to recent demand (with a minimum share per region so a quiet region can still serve a new burst), and rebalance every few seconds. The worst-case overshoot equals the demand shift within one rebalance interval. Per-IP and per-key limits that are naturally regional (users hit their nearest region) need no global coordination at all. Multi-region patterns and failover are covered in Chapter 26 and Chapter 41.

16. Observability and operations

  • Metrics (Chapter 54), always dimensioned by rule id, not by raw key (key cardinality would overwhelm the metrics system): checks per second, allow and deny counts, deny ratio per rule, shadow-deny counts, local-versus-remote decision ratio, lease hit rate, Redis call latency histogram and error rate, fallback activations, snapshot version per node and snapshot age, circuit breaker state.
  • Logs and events: a sampled decision event (for example every denial of a new key, then 1 in 100), with rule id, snapshot version, key hash, and limited_by. Hash or truncate identifiers where privacy policy requires (Chapter 56).
  • Top offenders: a streaming job (or a count-min sketch, Chapter 57) lists the heaviest keys and the most-denied keys per minute, which is the first question in any abuse incident.
  • Tracing: the check appears as a span inside the request trace with the verdict as an attribute, so a developer can see "request denied by search-per-key" instead of guessing.
  • SLOs: p99 check latency under 1 ms (and p99.9 under 5 ms); limiter-induced errors under 0.01 percent; rule propagation under 10 seconds p99; fallback time under 0.1 percent of the month. Alert on burn rate, not single spikes.
  • Alerts that matter: deny ratio suddenly 0 on a rule that normally denies (rules not applied or fail-open), deny ratio suddenly high (bad rule or attack), snapshot age above 5 minutes, Redis p99 above budget, a node on an old version for more than 2 minutes.
  • Customer-facing: a usage dashboard and warning emails at 80 and 100 percent of quota. Self-service visibility cuts support tickets.
  • Audit: every rule change records who, when, from-to, and reason; supports rollback and compliance review.

17. Security and cost notes

  • The limiter must not be an attack surface. Cap key length and the number of distinct keys one source can create (an attacker could send random API keys to create millions of buckets and fill memory). Unknown keys fall under a shared "unauthenticated" bucket or an IP bucket rather than creating per-key state before authentication succeeds.
  • Protect the control plane with strong authentication, authorization per team (only the owner of an API may change its rules), and change review for global rules.
  • Information leakage: headers reveal limits, which is intended; do not leak internal rule names or other tenants' data in error bodies.
  • Cost. About 32 Redis nodes (16 primaries, 16 replicas) at roughly 16 GB memory each is a small fraction of the compute that the protected APIs use; the limiter's cost is dominated by Redis nodes and cross-zone traffic. Leases cut Redis operations by about 10x, which would otherwise require a cluster several times larger. Keep TTLs tight, avoid storing request logs in Redis, and sample decision events: logging every decision at 600,000 per second is a bigger bill than the counters.

18. Evolution, phasing and alternatives not chosen

18.1 What to build first

  1. Phase 1 (week one): gateway plugin, token bucket with Redis Lua script on a single primary plus replica, rules from a static file reloaded on deploy, per-key and per-IP limits, 429 with headers, basic metrics. Fail open with a local fallback.
  2. Phase 2: versioned rule store, hot reload with shadow mode, per-tenant limits, overrides, plans, Redis Cluster sharding.
  3. Phase 3: hybrid leases, multi-rule checks with refunds, quota counters with the usage pipeline and customer dashboards.
  4. Phase 4: multi-region budgets and rebalancing, adaptive limits and abuse-signal integration, sidecar and library coverage for internal services.

18.2 At 10x scale (6M requests per second at peak)

  • The cluster would grow to about 32 to 64 primaries, but the real change is more aggressive local decision-making: bigger leases for hot keys and sampling-based approximate counting for the top keys, because the global store cannot keep up with exact accounting for the few giants.
  • Two-level hierarchy: a limiter tier per availability zone that aggregates gateways, so Redis sees zone aggregates, not individual nodes.
  • Move from per-request checks to asynchronous enforcement for very high-volume keys: count in memory, publish counts, enforce on a slightly delayed picture.
  • Dedicated shards or cells for the largest tenants so they cannot affect others (Chapter 42).

18.3 Alternatives not chosen

  • Fully centralized limiter service: simple and exact, but adds a network hop and a new critical dependency to every request.
  • Per-node local limits only: great latency, but the effective limit depends on node count and load-balancer skew, which customers notice.
  • Gossip-based sharing: removes the central store but convergence behaviour is hard to bound and debug.
  • A relational database for counters: cannot sustain the write rate cheaply, and row locking adds contention on hot keys.
  • Sliding window log for everything: exact, but memory grows with the limit; reserved for tiny limits.

19. Interview Q&A

Why do you embed the limiter in the gateway as a library rather than make it a separate service that the gateway calls?

A separate service adds a network hop to the data path of every request, typically 0.3 to 1 ms and a second thing that can fail, and that alone can consume the entire sub-millisecond budget. A library makes most decisions in process using local state and rule snapshots, and only talks to the shared store (Redis) when it must. The cost is that every language that needs limiting must have the library, so for polyglot internal callers I would still offer a thin gRPC front. The state store is shared in both designs, so correctness does not depend on this choice; only latency, deployment and ownership do.

Two gateway nodes check the same key at the same moment with one token left. How do you guarantee only one passes?

The read, compare, and write must be a single atomic step on the single node that owns the key. I use a Lua script executed in Redis: because Redis runs commands and scripts one at a time, no other command interleaves, so the first call takes the last token and the second sees none. The key lives on exactly one primary in a sharded cluster, so all nodes funnel to the same serialization point. Alternatives such as optimistic WATCH and retry or a distributed lock work but cost extra round trips and degrade under contention on hot keys.

Redis goes down. What does the gateway do?

It applies the rule's fail policy, with a bounded timeout so it never waits indefinitely. The default is to degrade to conservative local limits (the rule's limit divided by the expected node count with a safety margin), which keeps flood protection while keeping the API up. For rules protecting security-critical or costly operations such as login attempts or SMS sends I fail closed. A circuit breaker stops calling Redis after repeated failures and probes occasionally for recovery, with jittered retries to avoid a thundering herd. I also alert when fallback is active, since silently running without global limits defeats the purpose.

How do you avoid a Redis round trip for every request while staying accurate?

Use leases: a node takes a block of tokens from the global bucket and spends it locally, so it only calls Redis once per block. The global bucket remains the single record of how many tokens were granted, so the total cannot exceed the limit by more than the tokens held in unexpired leases. Lease size and expiry set the accuracy-versus-load tradeoff: large for hot, commercial keys, one (always global) for hard security limits. With a tenant limit of 1,000 per second across 20 nodes and leases of 10 tokens, calls to Redis drop from 1,000 to about 100 per second for that key.

How do rule changes reach hundreds of gateways quickly and safely?

Rules are stored as immutable versions in a database. A config service compiles a snapshot and pushes it to nodes, which also poll periodically, so a lost push heals within seconds to a minute. A node validates the snapshot, builds it aside and swaps one reference atomically, so in-flight checks are never affected. It persists the snapshot locally so a restart during a control-plane outage still has rules. New rules begin in shadow mode and roll out by canary, and rollback is just publishing the previous version. Changing a limit does not reset the existing buckets, so there is no accidental free burst.

An attacker rotates through 100,000 IP addresses. How do you still protect the service?

Per-IP limits cannot stop that, so I add layers keyed by things that are expensive to rotate: authenticated account or API key, device or session token, and per-tenant ceilings. I add aggregate limits by subnet or ASN, global per-endpoint limits that protect the backend regardless of source, and progressive friction (CAPTCHA, proof of work, delays) for suspicious traffic rather than hard blocks that hurt shared NATs. Expensive endpoints cost more tokens. Behavioural and reputation signals can tighten a key's limit dynamically. Volumetric floods are pushed down to the CDN or edge provider.

How would you handle a very large tenant that sends half of all traffic to one key?

A single key maps to a single Redis shard, so the shard becomes the hot spot. First, leases reduce its call rate by about 10x, which is usually enough. If not, split the key into several sub-buckets with each a fraction of the limit and spread calls over them, retrying on another sub-bucket when one is empty to smooth accuracy. For the biggest tenants I would give them a dedicated shard or cell. I would also check that the limit is not accidentally keyed by a low-cardinality field that funnels unrelated callers into one key.

What is the difference between a rate limit and a quota, and do they share infrastructure?

A rate limit bounds speed over short windows to protect the system and is ephemeral and approximate. A quota bounds total consumption over a billing period and has commercial and audit implications. They can share the check path and the Redis cluster, but quotas also stream usage events to a durable store with idempotent event ids so the billing record survives a Redis loss, and periods are encoded in the key name so they roll over without a scheduled reset job. Exceeding a rate limit usually means "try again in a second", while exceeding a quota means "wait until the period resets or upgrade".

How do you enforce a global limit across regions without adding 100 ms to each request?

Never call another region on the request path. Divide the global limit into regional budgets that each region enforces against its local Redis, and run a background reconciler that every few seconds moves budget toward regions with demand, keeping a minimum share everywhere. The error is bounded by how much demand can shift within a rebalance interval. If a hard global guarantee is truly needed, route that tenant's checks to a home region and accept latency for remote users, or use replicated mergeable counters that converge eventually and tolerate brief overshoot.

Why use Redis's clock inside the script instead of the gateway's?

Gateway clocks drift and differ, so two nodes can disagree on "now" by milliseconds or more. If each supplied its own timestamp, the refill calculation could move backward or credit tokens twice. Using the time reported by the Redis primary that owns the key gives a single monotonic reference per key, which makes refill consistent regardless of which node calls. The tradeoff is dependence on that server's clock, and after a failover the new primary's clock may differ slightly; the script guards by clamping negative elapsed time to zero.

Rate limiting versus load shedding and concurrency limits: how do they differ?

A rate limit is per caller and about the speed of arrivals. Load shedding is about the system's own health: when overloaded it rejects some requests regardless of who sent them, usually with 503, prioritizing critical traffic. A concurrency limit caps requests in flight, which is the better protection when slow requests pile up even though the arrival rate is modest. A complete defence uses all three: rate limits for fairness and abuse, concurrency limits per dependency to avoid queue build-up, and shedding as the last resort under overload.

Recap

  • A rate limiter is a decision function, a shared state store and a control plane. Design all three.
  • Enforce at the gateway with an embedded engine; add edge limits for floods and sidecar or library limits for internal dependencies. Layer limits by IP, key, tenant and backend.
  • Numbers: 600,000 requests per second at peak, 1.2M rule evaluations per second, 50 million keys at about 150 bytes (7.5 GB), 16 Redis primaries at under 75,000 operations per second each.
  • Correctness comes from one atomic Lua script on the single shard that owns the key, using the server's clock, refreshing a TTL on every call.
  • Latency comes from leases: most decisions are local, and Redis is called about a tenth as often, with accuracy traded within a few percent for commercial rules and exactness kept for hard rules.
  • Rules are versioned, pushed, validated, swapped atomically, started in shadow mode and always rollbackable; nodes survive control-plane outages.
  • Fail open or degrade to local limits by default; fail closed for security-critical and costly endpoints; alert on fallback.
  • Multi-region means regional budgets with background rebalancing, never a cross-region call per request.
  • Quotas are durable and billed; rate limits are ephemeral and protective. Plans are data bundles of limits, quotas and overrides.
  • Communicate clearly: 429, Retry-After, remaining-budget headers, cheap denials, and client back-off with jitter.
