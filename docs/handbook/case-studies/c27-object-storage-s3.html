Case study 27 · Worked solutions

Design Object Storage (S3-like)

We design a regional service that stores hundreds of billions of immutable blobs, promises eleven nines of durability, and still answers a listing request in milliseconds. The design hinges on one idea: split the small, strongly consistent index of objects (the metadata path) from the huge, cheap, append-only bytes (the data path), and then make every failure between the two safe.

1. Problem statement and clarifying questions

The prompt is "Design an object store like Amazon S3." The product is easy to describe and hard to build. A user creates a bucket (a named container), then uploads objects (an arbitrary sequence of bytes plus a few headers) under a key (a string such as photos/2025/cat.jpg). The user can read an object back by key, delete it, and list the keys in a bucket. There is no in-place edit: to change an object you upload a new one with the same key. That single restriction, immutability of an object once written, is what makes the whole design tractable, because it lets us store data in write-once files and never coordinate partial updates.

The conceptual background (buckets, storage classes, consistency, typical products) is in Chapter 21. This page is the worked solution: we make concrete numbers and choices. As in the earlier case studies, we start by asking the interviewer questions and fixing assumptions.

2. Requirements and scope

2.1 Functional requirements

  • Bucket operations. Create, delete (only when empty), list buckets, set configuration (versioning, lifecycle, policy).
  • Object operations. PUT (whole object), GET (whole or by byte range), HEAD (metadata only), DELETE, COPY (server side, no data movement through the client).
  • Listing. Return keys in lexicographic order with an optional prefix filter and a delimiter that rolls up "folders", paginated.
  • Multipart upload. Upload a large object as independent parts in parallel and in any order, then complete it atomically.
  • Integrity. Verify checksums on upload and detect corruption on read.
  • Lifecycle. Expire objects and abort abandoned multipart uploads automatically.

2.2 Non-functional requirements

  • Durability: 11 nines per object per year. The most important requirement and the one that drives the data layout.
  • Availability: 99.99 percent, tolerate one AZ failure with no data loss and ideally no read impact.
  • Throughput over latency. First byte under about 100 ms at p99 for a small object. The service is built for bandwidth, not for microsecond reads. A GET of a 1 GB object is dominated by streaming time.
  • Scalability: adding storage nodes and metadata shards increases capacity linearly with no downtime and without rebalancing everything.
  • Cost efficiency: raw capacity per user byte should be as low as durability allows. This is where erasure coding earns its place.

2.3 Out of scope

We do not design the identity and access management product, billing, a content delivery network in front (see Chapter 12), cold archive tiers with tape or multi-hour retrieval, an S3-compatible query engine such as SQL-on-objects, event notifications, or cross-region replication internals beyond a short mention in section 13. A file system view (POSIX semantics, rename, append) is also out: Case study 9 covers sync on top of blobs, and Chapter 23 covers distributed file systems.

3. Estimation

We follow the method of Chapter 2: state assumptions, compute, and check the result against hardware limits. The numbers here drive three decisions: how big the metadata tier is, how much raw disk we buy, and whether disk operations per second become the bottleneck.

3.1 Request rates

Average 50,000 requests per second, split as 35,000 GET or HEAD, 10,000 PUT, 2,500 DELETE and 2,500 LIST. The read to write ratio is therefore about 3:1 counting only data requests. Peak is 3x: about 105,000 GET, 30,000 PUT, 7,500 DELETE and 7,500 LIST per second, 150,000 in total.

3.2 Bandwidth and daily ingest

  • Ingest. 10,000 PUT/s x 500 KB = 5 GB/s average, which is 5 GB x 86,400 s = about 432 TB per day of logical ingest. Peak is 15 GB/s.
  • Egress. 35,000 GET/s x 500 KB = 17.5 GB/s average, which is 140 Gb/s. Peak is 52.5 GB/s, or 420 Gb/s. This is spread across front-end servers: at 25 Gb/s of usable network per server we need at least 17 servers for peak egress, and we will run well over 100 to stay below 30 percent utilization and survive failures.
  • Net growth. Many objects are overwritten or deleted. Assume net growth of 100 TB per day of logical data, or about 36 PB per year. We plan capacity one year ahead, so we size the fleet for 100 PB now and add roughly a third each year.

3.3 Metadata

Each object has a metadata record: key (about 100 bytes on average, up to 1 KB), size, ETag, content type, timestamps, user metadata, version id, storage class, and the chunk map (a list of chunk ids and their placement). Assume 500 bytes on average. 200 billion objects x 500 B = 100 TB of metadata. With 3 replicas that is 300 TB of SSD, about 40 to 50 servers with 8 TB of usable NVMe each. At peak the metadata tier sees roughly 150,000 operations per second (every data request touches it once; listing touches a range). Spread over 2,000 shards that is about 75 operations per second per shard on average, which is nothing. Metadata is bounded by size, not by request rate, except for hot prefixes (section 12).

3.4 Raw storage

Raw disk depends on the redundancy scheme, so we do this arithmetic now and justify it in section 8. Assume 90 percent of bytes live in objects of 1 MB or larger and 10 percent in smaller objects (about 70 percent of objects by count, but only a tenth of the bytes). Large objects use erasure coding 9 data + 6 parity fragments (overhead 15/9 = 1.67x). Small objects are 3-way replicated (overhead 3x).

Raw = 90 PB x 1.67 + 10 PB x 3 = 150 PB + 30 PB = 180 PB raw, a blended overhead of 1.8x. With 20 TB drives filled to 70 percent (we keep headroom for repair and growth), usable per drive is 14 TB, so 180,000 TB / 14 TB = about 12,900 drives. At 60 drives per storage server that is about 215 servers. For comparison, pure 3x replication would need 300 PB raw, about 21,400 drives. Erasure coding saves about 120 PB, roughly 8,500 drives, which is the economic argument for the whole complication.

3.5 Disk operations: the surprise bottleneck

A spinning disk delivers roughly 100 to 200 random reads per second. Reading a 9+6 erasure-coded object touches 9 fragments on 9 different disks. At peak, large objects are 30 percent of GETs (by count), small ones are 70 percent and need 1 disk read: average disk reads per GET = 0.7 x 1 + 0.3 x 9 = 3.4. So peak disk reads = 105,000 x 3.4 = about 357,000 per second, over 12,900 drives = about 28 reads per second per drive. That is comfortable. If every object were erasure coded, it would be 105,000 x 9 = 945,000 reads per second, about 73 per drive, uncomfortably near the limit once repair and scrubbing traffic are added. This is why we use the hybrid scheme.

3.6 Repair traffic

Annual drive failure rate (AFR) is about 2 percent in published fleet studies. 12,900 x 2 percent = about 260 failed drives a year, 0.7 per day. When one 14 TB drive fails, every fragment on it must be rebuilt, which for 9+6 means reading 9 surviving fragments per lost one: 14 TB x 9 = 126 TB read and 14 TB written. Daily repair read traffic is about 0.7 x 126 TB = 90 TB/day, versus client egress of 17.5 GB/s x 86,400 = 1.5 PB/day. Repair is about 6 percent of client traffic. If we want the rebuild done in 6 hours (the repair window used in section 8), the cluster must move 126 TB in 21,600 s = 5.8 GB/s, about 27 MB/s per storage server across 215 servers. Very feasible, but only because repair is declustered: the lost fragments' peers are spread over thousands of drives, not concentrated on a few (section 11).

4. API design

The API is HTTP with resource-style URLs, as in Chapter 5. We keep the S3 shape because every client library already speaks it.

PUT    /{bucket}                                   create bucket
PUT    /{bucket}/{key}                             upload object (up to 5 GB)
         headers: Content-Length, Content-MD5 or x-checksum-sha256,
                  Content-Type, x-meta-*, If-None-Match: *
         -> 200, ETag, x-version-id
GET    /{bucket}/{key}[?versionId=...]             download
         headers: Range: bytes=0-1048575, If-Match, If-None-Match
         -> 200 or 206 Partial Content
HEAD   /{bucket}/{key}                             metadata only
DELETE /{bucket}/{key}[?versionId=...]             delete (marker if versioned)
GET    /{bucket}?list-type=2&prefix=photos/&delimiter=/
         &max-keys=1000&continuation-token=...      list keys
POST   /{bucket}/{key}?uploads                     initiate multipart -> uploadId
PUT    /{bucket}/{key}?partNumber=7&uploadId=U     upload one part -> ETag of part
POST   /{bucket}/{key}?uploadId=U                  complete: body lists (partNumber, ETag)
DELETE /{bucket}/{key}?uploadId=U                  abort
GET    /{bucket}/{key}?uploadId=U                  list parts so far

Notes on the choices. Every request is authenticated by a signature over the request (a keyed hash of the method, path, headers and a timestamp), so we never send a long-lived secret and a replayed request expires. Responses are idempotent by construction: a retried PUT of the same key and bytes simply creates the same visible object (and a new version if versioning is on), and a retried multipart part overwrites the earlier copy of that part number. The conditional header If-None-Match: * makes "create only if absent" atomic, which clients use as a cheap compare-and-set primitive (see Chapter 32). Listing returns at most 1,000 keys per page plus an opaque continuation token, because an unbounded list would hold a shard scan open and starve other work. Range GET lets a client fetch part of a large object, which is how video players and parallel downloaders work, and we must support it without reading the whole object (section 7).

5. Data model and storage choice

Three kinds of data with very different shapes, so three stores. Deciding which technology to put where is the heart of the problem.

5.1 The metadata record

The metadata table's primary key is (bucket_id, key, version_inverse). The bucket id comes first so that each bucket is a contiguous key range. The inverse version (a number that decreases as versions get newer, for example the maximum timestamp minus the actual one) sorts the newest version first, so "get the latest version of this key" is the first entry in the key's range. For an unversioned bucket there is exactly one version.

row key:   (bucket_id, key, inverse_version)
value:     size, etag, content_type, created_at, user_meta, storage_class,
           is_delete_marker,
           layout: [ segment_0 = { chunk_id, scheme: EC(9,6) | REP(3), pg_id, length, checksum },
                     segment_1 = { ... }, ... ]

A segment is the unit of erasure coding: we cut the object byte stream into pieces of 9 MB (for erasure-coded objects), and each piece becomes 9 data fragments of 1 MB and 6 parity fragments of 1 MB. The placement group (PG) is a fixed set of 15 drives (for EC) or 3 drives (for replication) that will hold all fragments of a given chunk. The chunk id and PG id are enough to find the data, so storage nodes need no knowledge of object keys at all. This separation, nodes know chunks and the index knows keys, is what lets us repair, move and garbage collect data without touching keys.

5.2 Storage-node layout

Each storage node manages its drives as a set of extents: large (for example 1 GB) append-only files. A fragment write appends to the drive's currently open extent and records chunk_id, fragment_no -> (extent, offset, length, crc) in a local LSM index on SSD. When an extent is full it is sealed and becomes immutable. Facebook's Haystack paper used this same idea (many photos packed into big files, with an in-memory index) to avoid one filesystem inode per object and to reduce metadata reads per request to one. Immutable sealed extents also make checksumming, scrubbing, copying and compaction simple.

Key idea Because bytes are immutable, the data plane needs no locks and no consensus. A fragment is either fully written and checksummed or it is not there. All the difficult agreement, "is this object visible and where is it?", is concentrated in one small, replicated metadata commit.

6. From a first design to the real architecture

6.1 First design: one server

One web server accepts PUT and writes each object as a file on a local disk, with the key mapped to a file path. This works for a demo. The file system's directory structure is the index, so listing is a directory walk. It breaks immediately: a single disk fails and data is lost, a single machine's capacity is a few hundred TB at most, and a directory with a billion entries cannot be listed. Replicating to a second server does not fix the index scale problem and does not give 11 nines.

6.2 The scaled design

We apply the split from the lead: a front-end tier that speaks HTTP and orchestrates, a metadata service that owns the key index, a placement manager that decides which drives hold a chunk, storage nodes that hold fragments, and background workers that repair, scrub, garbage collect and apply lifecycle rules. Only the metadata service is strongly consistent. Front-ends are stateless and storage nodes are simple.

Front-end servers also act as the erasure-coding engine on writes (they compute parity from data as it streams through) and the reconstruction engine on degraded reads. This keeps storage nodes simple and puts CPU where it scales horizontally. Encoding at roughly several GB/s per core with vectorized instructions is typical for Reed-Solomon, so 15 GB/s peak ingest needs only a handful of cores; network is the limit, not coding.

7. Request flows

7.1 PUT of an object (a 40 MB example)

  1. The client sends PUT /bkt/video.mp4. The front-end verifies the signature, checks the bucket policy, and starts hashing the stream.
  2. The front-end cuts the stream into 9 MB segments (here 5 segments: four of 9 MB and one of 4 MB). For each segment it asks the placement manager for a PG, a set of 15 drives with 5 in each AZ, on different servers and racks. In practice placement answers are cached for a batch of chunk ids so this is not a round trip per segment.
  3. For each segment the front-end splits the bytes into 9 data fragments, computes 6 parity fragments, and sends all 15 fragments in parallel to the 15 drives. Each storage node appends the fragment to its open extent, checksums it, and fsyncs (or group-commits) before acknowledging.
  4. When at least 12 of 15 fragments are acknowledged for every segment, the segment is considered durable. The remaining slow fragments continue in the background, and if one fails the repair queue gets an entry. Waiting for 12 means that even immediately after the PUT returns, three more fragment losses are survivable.
  5. The front-end verifies the final checksum against the client-supplied one, then writes the metadata record (the key, the layout of five segments) to the owning metadata shard. This is a single Raft write on that shard, a few milliseconds. This write is the commit point.
  6. The front-end returns 200 OK with the ETag. From this instant any GET or LIST on any front-end sees the object, because reads of that shard are linearizable.

7.2 GET of an object, including a range

  1. The front-end verifies the signature and reads the metadata record for the key (a point read on one shard). A small hot cache of metadata on the front-ends cuts load, but entries are validated by version or have short lifetimes so a delete is seen quickly (see Chapter 13).
  2. For a range such as bytes 20,000,000 to 29,999,999, the front-end computes from the layout which segments overlap (segments 2 and 3 at 9 MB each) and, within them, which data fragments, since the data fragments are contiguous 1 MB slices of the segment. It reads only those data fragments, in parallel from the drives, not all 15.
  3. Each fragment is checksum-verified as it is read. On success the bytes stream straight to the client with no parity math.
  4. Degraded read: if a fragment is missing, corrupt or its drive is slow, the front-end also issues reads for parity fragments and reconstructs the missing slice from any 9 of the 15. Hedging, sending the extra read after a short delay such as the p95 latency rather than waiting for a timeout, trims tail latency (Chapter 40).

Small replicated objects are simpler: read any one of 3 replicas, preferring a replica in the local AZ, and fall over to another on a checksum failure or timeout.

8. Deep dive 1: erasure coding vs replication, and the durability math

8.1 How erasure coding works

Replication keeps full copies. Erasure coding is the generalization of parity. The simplest example: split a block into halves A and B and store a third block P = A XOR B. Lose any one of the three and you can recompute it (A = B XOR P). That is 3 pieces for 2 pieces of data, 1.5x overhead, tolerating one loss, where 2-way replication has 2x overhead and tolerates one loss too, so we already save space. Reed-Solomon (k, m) extends this using arithmetic in a finite field: from k data fragments it computes m parity fragments such that any k of the k+m fragments suffice to rebuild the original. It tolerates any m simultaneous losses. Overhead is (k+m)/k. The mathematics is a matrix multiplication over GF(256) and the property comes from every k by k sub-matrix of the code matrix being invertible; the interview-level takeaway is "any k of n".

Local reconstruction codes (LRC) add local parity fragments each covering a small group of data fragments, so rebuilding a single failed fragment reads only the group (about 6) rather than all k. Because single failures are by far the commonest event, this cuts repair traffic almost in half. We mention LRC as the 10x-scale evolution (section 15), but start with plain Reed-Solomon because it is easier to reason about and test.

8.2 Why 9+6 across three AZs

The scheme must survive an AZ outage. With RS(10,4) placed across 3 AZs we would put about 5 fragments in an AZ, and losing one AZ loses 5, which is more than the 4 parity fragments, so data is unreadable (not lost, but unavailable) until the AZ returns. To keep reads alive through an AZ loss, the number of fragments per AZ must be at most m, so with 3 AZs and equal spread we need m of at least n/3, which means (k + m) / 3 <= m, or equivalently m >= k/2. For k = 9 we need m = 6 (k/2 = 4.5, and we want one failure of slack beyond the AZ loss, so 6). The price is 1.67x instead of 1.4x. That is the real tradeoff in an interview: cross-AZ tolerance costs extra parity. A cheaper alternative is to erasure-code inside a single AZ and replicate whole objects across regions, which many cold tiers do, but then an AZ outage is a data outage for that bucket.

8.3 Why small objects are replicated

Two reasons. First, the IOPS arithmetic of section 3.5: erasure coding turns one read into k reads, which is cheap when the object is megabytes (the cost is bandwidth, which is plentiful) but wasteful when the object is 20 KB (the cost is seeks, which are scarce). Second, an object smaller than a fragment cannot be meaningfully split: a 20 KB object coded as 9+6 would write 15 tiny fragments with metadata and checksum overhead per fragment larger than the data. We therefore replicate objects below a threshold (1 MB here) three times, one replica per AZ, and optionally compact many small objects into a shared stripe later in the background. Tuning the threshold is a cost-versus-IOPS decision that can be revisited with real traffic data.

8.4 The durability math

What does "eleven nines" mean? It is the probability that a given object survives a year: 1 - 10^-11. With 200 billion objects, the expected annual loss is 200 x 10^9 x 10^-11 = 2 objects. Now compute what our schemes deliver under a simple model with independent failures.

  • Annual failure rate of a drive: 2 percent (AFR = 0.02).
  • Repair window: after a drive fails, the fragments it held are rebuilt in about 6 hours. During that window the object has reduced redundancy.
  • Probability that a given other drive fails inside one 6-hour window: p = 0.02 x 6 / 8,760 hours per year = 1.37 x 10^-5.

3x replication. The object has 3 copies. The rate of a first failure is 3 x 0.02 = 0.06 per year. The object is lost only if both other copies fail in the repair window: p^2 = (1.37 x 10^-5)^2 = 1.9 x 10^-10. Annual loss probability = 0.06 x 1.9 x 10^-10 = 1.1 x 10^-11, almost exactly 11 nines, with 3x overhead. This is why three copies became the folk standard.

RS(10,4) in one location. 14 fragments, first failure rate 14 x 0.02 = 0.28 per year. Loss needs 4 more of the other 13 fragments to fail within the window (5 total gone, more than m = 4): C(13,4) = 715 combinations x p^4 = 715 x 3.84 x 10^-20 = 2.7 x 10^-17. Times 0.28 gives 7.7 x 10^-18, about 17 nines, with only 1.4x overhead.

RS(9,6). 15 fragments, 0.3 first failures per year, loss needs 6 more of the other 14 within the window (7 gone): C(14,6) = 3,003 x p^6 = 3,003 x 6.6 x 10^-30 = 2 x 10^-26, times 0.3 gives about 6 x 10^-27.

Watch out Do not claim 26 nines to an interviewer as if it were real. The independence assumption is false. Real loss comes from correlated events: a firmware bug that corrupts a whole drive model, a bad software release that writes wrong fragments, an operator deleting the wrong thing, a rack or power failure that takes many fragments at once, silent bit rot found only after the other fragments also rotted, and repair itself falling behind. These make the true figure dominated by software and operations, not by the drive failure model. The design answers them with placement across failure domains (distinct servers, racks, AZs for each fragment), end-to-end checksums, background scrubbing, staged rollouts, and deletion safeguards. The math justifies the scheme; the processes justify the number.

8.5 The repair window is the hidden variable

Every formula above depends on the repair time T through p = AFR x T / 8,760. Halving T cuts p by half and the 3x loss probability by 4x and the RS(9,6) loss probability by 64x. So durability engineering is largely repair speed engineering: declustered placement (each drive's fragments have peers spread over thousands of other drives, so rebuilding reads from many sources and writes to many targets in parallel), repair prioritization (objects with the fewest remaining fragments are repaired first), and capacity headroom so there is somewhere to rebuild. Section 11 returns to this.

9. Deep dive 2: the metadata path and listing

If the data plane is dumb, the metadata plane must be right. It must be linearizable (so a GET after a PUT sees the object), sorted (so LIST works), and scalable to 100 TB. Those three requirements point at a range-sharded, consensus-replicated ordered key-value store. Chapter-level background: Chapter 25 (sharding), Chapter 24, Chapter 29, and a full key-value design in Case study 4.

9.1 Range sharding versus hash sharding

We choose range sharding because listing is part of the contract. The hotspot downside is handled by automatic range splitting: a shard splits when it exceeds a size (for example 50 GB) or a sustained request rate, and a coordinator moves the new half to a less loaded Raft group. The range map (which key interval lives on which shard) is small, about 2,000 entries plus splits, replicated to every front-end and refreshed through a version check: a shard that receives a request for a key outside its range returns "wrong shard" with the current map version and the front-end retries.

9.2 Executing a LIST

A request with prefix=photos/2025/, delimiter=/ and max-keys=1000 becomes an ordered scan of the key range from photos/2025/ up to the end of that prefix. The delimiter rolls up keys that share a "folder": if the scan sees photos/2025/jan/a.jpg and the delimiter occurs after the prefix, it emits the common prefix photos/2025/jan/ once and then seeks to the first key after that whole prefix (the prefix with its last byte incremented) instead of reading the possibly millions of keys in between. Without the skip, listing a bucket with one deep folder would scan every key under it. The response contains up to 1,000 entries plus a continuation token, which encodes the last key returned. The next request starts the scan strictly after that key, so pages are stable: they are defined by the key order, not by an offset that shifts when objects are inserted (the keyset pagination idea from Chapter 5).

9.3 Consistency of LIST and of the whole commit

A PUT that has returned 200 must appear in the next LIST and a DELETE must disappear. Because the object's metadata row lives in exactly one shard and the LIST reads shards with linearizable reads (a read that goes through the Raft leader, with a read-index or lease check, see Chapter 28), this holds without further work. The tricky case is a LIST scan that spans several shards at slightly different moments: it can return a result that never existed as a single state (a key added on shard 42 after the scan left shard 41). That is acceptable and matches S3's documented behaviour: a list is a series of ordered reads, each page strongly consistent, not a transactional snapshot of the bucket. Objects whose creation completed before the list started are guaranteed present; objects created during the list may or may not be.

Operations that touch two keys, such as COPY, are two independent steps: the data is not copied at all (the new metadata row points at the same chunks, with a reference count raised, see section 11), then one metadata write creates the destination key. Bucket deletion needs an emptiness check, which we do by a range scan that returns the first key, protected by marking the bucket "deleting" so no new object can slip in.

9.4 Versioning and delete markers

With versioning on, a PUT adds a new row with a newer inverse version rather than replacing the old one, and a DELETE without a version id adds a delete marker row (a version with no data) so the latest-version lookup returns "not found" while older versions remain recoverable. A DELETE with a version id physically removes that row, which is when garbage collection becomes responsible for its chunks. Versioning is the reason metadata cannot simply "update in place": the row set of a key is a short ordered list.

10. Deep dive 3: multipart upload

A single PUT of a 2 TB file is a bad idea: one TCP connection limits throughput, a failure at 99 percent restarts from zero, and the front-end would hold the transfer state for hours. Multipart upload solves this by making each part an independent, retryable, parallel upload.

10.1 The protocol

  1. Initiate. The client calls POST ?uploads. The metadata service creates an upload record keyed by (bucket, key, upload_id), where the upload id is a random string, and returns it. Nothing is visible in the bucket listing yet.
  2. Upload parts. The client uploads parts numbered 1 to 10,000, each from 5 MiB to 5 GiB except that the last may be smaller. Parts can be sent in any order, in parallel, from different machines. Each part is stored exactly like a standalone object (segments, EC or replication, fragments on drives), and a part record (upload_id, part_number) -> {etag, size, layout} is committed to the metadata store. Re-uploading the same part number replaces the earlier copy (last write wins), which makes retries trivial. Part sizes are not required to be equal.
  3. Complete. The client sends the list [(1, etag1), (2, etag2), ...]. The service checks that every listed part exists with a matching ETag, that all parts but the last meet the minimum size, and then performs one atomic metadata transaction that writes the final object row whose layout is simply the concatenation of the part layouts, and deletes the upload record. The data is never copied or re-encoded; completion is a metadata-only operation and takes milliseconds even for terabytes. If the client's Complete call times out and is retried, the service sees the upload id already completed and returns the same result.
  4. Abort. The client may abort. The upload and part records are deleted and the part chunks become garbage.

10.2 Details interviewers probe

  • The ETag of a multipart object. A single-part object's ETag is typically the MD5 of its bytes. For multipart objects it is conventionally the MD5 of the concatenated binary MD5s of the parts followed by a dash and the part count, so it is not a content hash of the whole file. We stick to that convention for compatibility, and offer a stronger additional checksum header per part and per object for end-to-end integrity.
  • Resuming. After a crash the client calls List Parts, sees which parts are stored with which ETags, and uploads only the missing ones.
  • Range GET of a multipart object. Easy, because the layout is a list of segments with lengths: the front-end does a prefix-sum search to find which segment holds a byte offset, regardless of part boundaries.
  • Cost of unfinished uploads. Parts occupy storage until completed or aborted, so a bucket lifecycle rule "abort incomplete uploads after 7 days" is a standard safeguard, and quota accounting must count in-flight parts.
  • Atomicity at Complete. If the final object's layout and the delete of the upload record live on different shards, we either keep upload records on the same shard as the final key (the upload row key is (bucket, key, upload_id), so it sorts right next to the object's rows) or use a transaction; co-locating by construction is the simpler and faster choice. Cross-shard transactions are covered in Chapter 31.

11. Deep dive 4: garbage collection, repair and scrubbing

Everything above creates chunks. Something must remove the ones nobody references and fix the ones that have lost fragments. The four sources of garbage are: overwritten or deleted objects, aborted or abandoned multipart parts, orphans from PUTs that wrote fragments but crashed before the metadata commit, and replaced chunks after repair or rebalancing. Because the commit is the metadata write, the rule is simple: a chunk is live if and only if some committed metadata record (an object row, a part record, or a copy's shared reference) names it.

11.1 Choosing a reclamation approach

ApproachHow it worksProsCons
Synchronous deleteDELETE removes the row and immediately tells storage nodes to drop the fragmentsSpace returns fast, simple mental modelCrash between steps leaks space; deleting 5 TB blocks the request; cannot handle COPY sharing or in-flight reads

We choose the hybrid. Counting alone is fragile, scanning alone is slow to reclaim, and together each fixes the other's weakness: the queue handles the 99 percent case within minutes, the periodic sweep makes the system self-healing so that no bug or crash can leak space forever.

11.2 The delete path

  1. DELETE removes (or marks) the metadata row in one Raft write and returns immediately. The object is invisible from this moment.
  2. The same transaction appends the object's chunk ids to a deletion queue row in the metadata store (or a log) with a timestamp. Writing it in the same transaction means we never lose the intent.
  3. A GC worker takes entries older than a safety delay (for example 24 hours, which also gives an undelete or recovery window for operator mistakes and lets slow in-flight reads of the old object finish). For a chunk with a shared reference (COPY), it decrements the count and stops unless it reaches zero.
  4. For each chunk it sends delete commands to the storage nodes in the PG. The node marks the fragment dead in its local index. Space is not freed yet.

11.3 Extent compaction

Extents are immutable and append-only, so a deleted fragment leaves a hole inside a sealed extent. Reclaiming the space means compaction: when a sealed extent's garbage ratio crosses a threshold (say 50 percent), the node copies the remaining live fragments into a fresh extent, updates its local index, and deletes the old file. This is the same write-amplification trade as in log-structured storage (Chapter 19): a lower threshold reclaims space sooner but copies more live data. Picking the extent with the highest garbage ratio first (a greedy policy) gives the best space per byte copied. Compaction runs at low priority with a rate limit so it never starves client reads.

11.4 Mark and sweep and the grace period

The sweep runs per placement-group range, for example weekly. It builds a Bloom filter or sorted set of chunk ids referenced by metadata in that range, asks the storage nodes for their chunk ids, and for each node chunk absent from the live set whose creation time is older than the grace period issues a delete. The grace period is the safety valve for the race that would otherwise delete live data: a PUT writes fragments (time t0) and commits its metadata row seconds or minutes later (t1). A sweep that sees the fragment in the window t0 to t1 would call it garbage. The rule "never delete anything younger than G" with G much larger than the longest legitimate PUT time prevents this. We use 7 days, which also covers multipart parts, because part chunks are kept alive by the upload table, not the final object row, so the live set includes them (they are named by part records) and the sweep must scan upload tables too. Forgetting that is the classic way to delete a customer's in-flight multi-terabyte upload.

11.5 Repair and scrubbing

Repair restores redundancy. Storage nodes report health by heartbeat; the placement manager treats a node as suspected after missing heartbeats (using a failure detector from Chapter 33) and as failed after a longer timeout, for example 15 minutes, to avoid rebuilding everything for a reboot. When a drive or node is declared failed, the manager enumerates the PGs that included it. Placement is declustered: with about 13,000 drives and fixed 15-drive PGs numbering in the hundreds of thousands, each drive belongs to many PGs and its peers are spread across essentially the whole fleet, so rebuilding is a many-to-many transfer rather than one hot replacement disk running at 100 MB/s. A repair worker reads 9 surviving fragments of each affected chunk, recomputes the missing one, writes it to a spare drive chosen in the same AZ and on a different rack than the other fragments, and updates the PG membership. Chunks with the fewest remaining fragments are repaired first.

Scrubbing finds silent corruption (bit rot). Drives can return wrong bytes without any error. Every fragment carries a checksum (CRC32C is typical and hardware accelerated) stored with it in the index. Reads verify it. Because cold data is rarely read, a background scrubber re-reads every fragment on a cycle, for example every two to four weeks, verifies the checksum, and queues a repair for any mismatch. With a 14 TB drive and a 30 day cycle the scrub reads 14 TB / 2.6 million seconds = about 5.4 MB/s per drive, which is under 5 percent of a drive's sequential bandwidth. Scrubbing is what converts "silent" into "repaired within a known window", which keeps the durability math honest.

12. Scaling, hot spots and caching

  • Front-ends are stateless: add servers behind a load balancer (Chapter 9). Because a large PUT streams for minutes, we use connection-count-aware balancing and drain connections gracefully during deploys.
  • Storage nodes scale by adding nodes; new empty nodes receive new PGs first, and only a bounded background rebalance moves existing chunks to even utilization. Because PGs are fixed groups, rebalancing moves whole PGs or individual fragments with the placement manager changing only the map.
  • Metadata hot prefixes. A customer writing a million keys per second with a timestamp prefix concentrates load on one range. The split-on-load mechanism divides the range as soon as sustained load exceeds a threshold, but a range can only split at key boundaries, and all new keys still append at the end. The pragmatic mitigations are to make keys less monotonic (a short hash prefix), and to let the service absorb bursts by returning HTTP 503 "SlowDown" with a retry hint so clients back off with jitter (Chapter 16). Splitting reacts in tens of seconds to minutes, so a sudden spike gets throttled briefly.
  • Hot objects. A viral object is read from the same fragments over and over. Put a CDN in front (Chapter 12) and keep a front-end RAM cache for small hot objects. The data plane additionally relies on the drives' page cache and a modest SSD tier for the hottest extents.
  • Metadata caching. Bucket configuration and the range map are cached everywhere. Object metadata for hot keys is cached on front-ends with short validity. We never cache LIST results across clients.
  • Multi-tenancy. Per-bucket and per-account request-rate limits protect shared shards, and metadata placement can isolate very large tenants on dedicated shard groups (cell style isolation, Chapter 42).
  • Large-object throughput. The client parallelizes with multipart (writes) and with several range GETs (reads). The service does not need to do anything special beyond supporting both.

13.1 Consistency and idempotency decisions

The linearization point of every state change is one metadata write. Reads go through the same shard, so read-after-write holds. Overwrites are last-writer-wins by the order the metadata shard applies them; two concurrent PUTs to the same key both succeed and the later commit wins, and the loser's chunks become garbage, which is the correct behaviour (S3 documents the same). Conditional requests (If-None-Match, If-Match) are evaluated inside the shard's write so they are atomic. Retried PUTs are safe because each attempt writes new chunk ids (a random id per attempt) and commits at most one row; there is no way to produce a duplicate visible object other than by an explicit version. Chunk ids are random 128-bit ids generated by the front-end rather than content hashes, because deduplication by content would require a global lookup and leaks information across tenants (section 14).

13.2 Multi-region

Cross-region replication is asynchronous. A change feed from each metadata shard (an ordered log of PUT and DELETE events per key) is consumed by replicator workers that copy the object to the destination region's bucket. It requires versioning on both sides to make ordering and idempotency safe: the replicator applies "put version V of key K" and ignores one it has already applied. The destination lags by seconds to minutes (monitor the lag), and the recovery point objective for a regional disaster is that lag. See Chapter 26 and Chapter 41. Strong consistency is a per-region promise.

14. Security, monitoring, SLOs and cost

14.1 Security and abuse

  • Authentication and authorization. Signed requests; bucket policies and per-user permissions evaluated at the front-end; default deny and a "block public access" account setting, because misconfigured public buckets are the most common real-world data leak (Chapter 55).
  • Presigned URLs. A signed, expiring URL lets a browser upload or download one key directly without credentials. The signature covers method, path and expiry.
  • Encryption. TLS in transit. At rest, envelope encryption: a unique data key per object encrypts the bytes, the data key is encrypted by a bucket or account key held in a key management service, and the wrapped key is stored in the metadata row. Deleting a customer's key makes their data unreadable (crypto-shredding), which helps privacy erasure requests (Chapter 56).
  • Dedup caution. Cross-tenant deduplication reveals whether somebody else already stored a file, a known side channel, and conflicts with per-object keys. We do not deduplicate across accounts.
  • Abuse. Per-account rate limits and quotas, protection against enumeration of keys, and request-size caps to stop a slow-loris style client holding a front-end connection forever.
  • Operator safety. Two-person review for bulk deletes, object lock or retention (WORM, write once read many) for compliance buckets where deletion is refused until a date.

14.3 Cost

The bill is dominated by drives, then by power and datacenter space, then by networking. Erasure coding avoids about 8,500 drives versus 3x replication (section 3.4). Cross-AZ bandwidth is a real cost in public clouds and a capacity limit in our own datacenters: each PUT of a 9 MB segment sends 15 MB, of which 10 MB crosses AZ boundaries, so cross-AZ ingest is about 1.1x the user bytes at the segment level and the rest of the 1.67x is intra-AZ spread, and a healthy GET prefers data fragments in the local AZ (5 of 9). Compaction and scrub I/O cost drive time rather than money directly. Storage classes (cold tiers using wider codes like RS(12,4) at 1.33x on slow high-density drives) are the lever for cost versus access latency, and lifecycle rules move data down tiers automatically.

15. Evolution: first build, 10x scale, alternatives

15.1 What to build first

  1. Phase 1 (MVP). Front-end, a replicated metadata store on an existing database (a Raft-based SQL or key-value product, ordered by key), 3x replicated chunks on storage nodes with whole-object chunks, checksums, PUT/GET/DELETE/LIST, simple delayed-delete GC. This already reaches 10 PB with 11 nines.
  2. Phase 2. Multipart upload, range GET, versioning, bucket policies, lifecycle, automatic range splitting, scrubbing and declustered repair.
  3. Phase 3. Erasure coding for large objects with a background re-encoder that converts older replicated objects, multi-AZ placement, mark and sweep, cross-region replication.
  4. Phase 4. Storage classes and tiering, local reconstruction codes, object lock, an own metadata engine tuned for the workload.

15.2 At 10x scale (1 EB, 2 trillion objects)

  • Metadata becomes 1 PB, so about 20,000 shards. The range map grows large; introduce a two-level (directory) map and move bucket-level routing into a cell-based design (Chapter 42), where each cell serves a subset of buckets with its own metadata and storage nodes, bounding blast radius.
  • Repair traffic grows with the fleet (about 2,600 failed drives per year), so we adopt LRC to halve repair reads and larger spare capacity.
  • Drive sizes keep growing (30 TB and larger), and a single failed drive takes longer to rebuild unless declustering gets wider; the larger the drive the more the repair window dominates durability, a trend to mention.
  • Shingled (SMR) drives, which are natural fits for append-only extents, lower cost per TB at the price of poor random writes that our design never does.
  • Small-object overhead: at 2 trillion objects, per-object metadata dominates; consider packing tiny objects into bundles with an index and keeping a small SSD tier for their metadata and data.

15.3 Alternatives not chosen

16. Interview Q&A

Why separate metadata from data, instead of storing both together in one distributed database?

The two have opposite shapes. Metadata is small (about 500 bytes per object), needs strong consistency, sorted order and random access, so it lives on SSD in a consensus-replicated, range-sharded store. Data is huge, write-once, read sequentially, and mostly needs cheap capacity and redundancy rather than consensus, so it lives on HDDs in append-only extents with erasure coding. Putting them in one store would either make bulk data pay for consensus and expensive SSDs, or make the index inherit the data tier's weak consistency. The split also lets us scale and tune each independently: metadata by shard count, data by drive count, and it makes the commit point crisp, one metadata write.

A PUT crashes after writing all fragments but before the metadata commit. What state are we in and who cleans up?

The object is not visible, because visibility is defined solely by the metadata row, and the client received no success response, so it will retry. The fragments are orphans: chunks on storage nodes that no metadata row names. They are harmless except for wasted space. The mark-and-sweep collector finds them, since they exist on nodes but are absent from the live set, and deletes them after the grace period (7 days here), which exists so that it cannot confuse an orphan with a PUT that is still in progress. This is why we write data first and metadata last: the failure leaves garbage, never a dangling pointer to missing data.

Why is erasure coding cheaper than replication, and when would you still replicate?

Reed-Solomon (k, m) keeps k data and m parity fragments, any k of which rebuild the object, so overhead is (k+m)/k, such as 1.4x or 1.67x, versus 3x for triple replication, while tolerating more simultaneous failures. The costs are CPU for encoding, more disk operations per read (k reads), and repair that must read k fragments to rebuild one. So I replicate small objects (the extra seeks and per-fragment overhead dominate), very hot data where a single read matters, and use erasure coding for large, warm and cold objects. I record the scheme per chunk so objects can be migrated between schemes.

Walk through the durability math for 3 replicas versus a (10,4) code. What assumption could make it wrong?

With a 2 percent annual drive failure rate and a 6 hour repair window, the chance a given drive fails inside the window is about 1.4e-5. For 3 replicas, loss needs the other two copies to both fail in the window after a first failure: 0.06 per year times (1.4e-5)^2, about 1.1e-11, so 11 nines. For RS(10,4), loss needs 4 more of 13 other fragments to fail: 0.28 times C(13,4) = 715 times (1.4e-5)^4, about 7.7e-18. The assumption that breaks is independence. Real losses come from correlated events such as a firmware bug, a rack or power failure, a bad software release, or operator error, and from repair being slower than assumed. That is why placement spreads fragments over failure domains, we verify checksums end to end, and we measure the age of the oldest under-redundant chunk as the key durability metric.

How does LIST with a delimiter work efficiently when a bucket has billions of keys?

Keys are stored sorted in a range-sharded store, so a prefix is a contiguous range and a list is a sequential scan of one or two adjacent shards. With a delimiter, when the scan meets a key containing the delimiter after the prefix, it records the common prefix once and then seeks directly past all keys that start with it, so the work is proportional to the number of distinct entries returned, not the number of keys underneath. Pagination uses a continuation token holding the last key, which stays correct as keys are inserted. The reason we did not use hash sharding is that it would force a scatter-gather across all 2,000 shards for every page.

How would you implement multipart upload so that Complete is fast and atomic for a 5 TB object?

Each part is stored as ordinary chunks and recorded in an upload table keyed by upload id and part number. Complete does not move any data: after checking every listed part exists with the matching ETag and that non-final parts meet the minimum size, it writes one metadata row whose layout is the concatenation of the part layouts and deletes the upload record, in a single transaction on one shard (we co-locate upload records with the final key's range to avoid cross-shard transactions). So it takes milliseconds regardless of size and is retry-safe: a second Complete for the same upload id returns the existing result. Superseded or abandoned parts become garbage, collected by the delayed-delete queue and by a lifecycle rule that aborts incomplete uploads after some days.

What does garbage collection need to be careful about, and what happens if it has a bug?

The dangerous direction is deleting live data. Races include a chunk that is written but not yet committed, multipart parts that are named only by upload records, chunks shared by a COPY, and reads still in flight on an object just deleted. We defend with several layers: deletion is delayed 24 hours after the row is removed, orphan cleanup requires a 7 day grace period, the live set includes upload tables and shared references, the worker rechecks that the chunk is unreferenced immediately before deleting, delete volume is rate limited with anomaly alarms, and new GC logic first runs in report-only mode. A GC bug that deletes live data is a data loss incident, so these safeguards matter more than reclamation speed.

Hot prefix: one tenant writes sequential keys at 100k per second. What happens and what do you do?

Sequential keys all land in the last range of the key space, so a single metadata shard (one Raft leader) takes all the writes. Automatic splitting divides a range when its load or size crosses a threshold, but because new keys always arrive at the end, the hot range keeps being the newest one. The service therefore returns 503 SlowDown to shed the excess so clients back off with jitter, and splits as quickly as it can, which spreads existing keys but not the append hot spot. The real fix is on the key design: add a short hash or random prefix, or shard by an id, which spreads writes across ranges at the cost of making a time-ordered listing a multi-prefix operation. We also document recommended request rates per prefix.

How do you provide strong read-after-write consistency, and what does it cost?

Every object's metadata lives on one shard replicated by Raft, and both the commit and the reads go through that shard's leader (or a lease or read-index confirmed read), so any read after an acknowledged write observes it. The cost is that a metadata read cannot be served from a stale follower or a long-lived cache without validation, so reads pay a leader hop and the shard leader is a bottleneck for a hot key, and a shard that loses quorum becomes unavailable (a CP choice). We soften this with leader leases to avoid a per-read quorum round trip, with CDN and front-end caches only for objects where staleness is acceptable (immutable versioned objects), and with replicas in three AZs so single-AZ failures do not break quorum.

How do you detect and handle silent data corruption?

Defense in depth. The client or front-end computes a checksum of the whole object, which is verified before the commit and stored in the metadata. Each fragment has its own CRC computed at write and stored next to it. Every read verifies the fragment CRC, and a mismatch triggers a degraded read from other fragments plus a repair job (read repair). A continuous scrubber re-reads all data about every 30 days so cold data does not rot unnoticed, at a bandwidth of only about 5 MB/s per drive. Corruption becomes an event with a detection time and a repair time, and those two numbers feed straight back into the durability math as the repair window.

How does the design change if the interviewer asks for cross-region durability?

I would add asynchronous replication driven by the metadata change feed, requiring versioning so applying an event is idempotent and ordered per key. Replicator workers copy new versions to the destination region, which stores them with its own erasure coding and its own metadata commit. The replication lag becomes an SLO that defines the recovery point objective for a regional disaster, with a priority option for critical buckets. Strong consistency stays within a region; across regions the second copy is eventually consistent, and a failover must decide how to handle the writes not yet replicated.

Recap

  • Split the system into a strongly consistent, range-sharded metadata index (100 TB, NVMe, Raft) and a dumb data plane of append-only extents on HDD. The PUT commits with one metadata write, so data goes first and the row goes last.
  • Use erasure coding for large objects (RS 9+6 across three AZs, 1.67x) and replication for small ones (3x) to keep both cost and disk operations per second in budget: about 180 PB raw, 12,900 drives, 28 reads per second per drive at peak.
  • Durability math: with a 2 percent AFR and a 6 hour repair window, 3 copies give about 11 nines, RS(10,4) about 17, and the real risk is correlated failure, so we place across failure domains, checksum end to end, scrub continuously, and repair fast with declustered placement.
  • Listing needs ordered keys, so shard by range, skip common prefixes, paginate by last key, and split hot ranges.
  • Multipart upload makes parts independent chunks and Complete a metadata-only atomic stitch. Abandoned parts are garbage.
  • Garbage collection is a hybrid of delayed deletion queues, extent compaction and a mark-and-sweep with a long grace period. Its bugs are the most dangerous ones, so layer safeguards.
  • Build in phases: replicated chunks first, then multipart and versioning, then erasure coding and tiering, then cells and local reconstruction codes at 10x.
