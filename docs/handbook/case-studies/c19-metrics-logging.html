Design Metrics and Log Aggregation

We design the system that every other system depends on when it breaks: a platform that collects numeric metrics and text logs from tens of thousands of machines, stores them cheaply, answers dashboard queries in a second, and wakes someone up within a minute when something is wrong. The hard parts are the write volume, the cost of storage, the explosion of label combinations, and the fact that this system must stay up exactly when everything else is down.

How to approach this problem (read this first)

What the interviewer is really testing. "Metrics and logging" is two systems wearing one name, and the first test is whether you notice. Metrics are many tiny numbers with labels, so the hard parts are compression and the explosion of label combinations (cardinality). Logs are huge amounts of text that are rarely read, so the hard part is cost: how little you can index. The third test is the unusual rule that this platform must keep working when everything else is failing, which shapes buffering, alerting and the question of who watches the watcher.

The thinking order, step by step

  1. Split the problem in two. Say: "I will treat metrics and logs as separate pipelines that share a buffer, tenancy and alerting." Then ask clarifying questions for each: number of sources, metric resolution, log volume, retention, freshness, and whether losing a few samples is acceptable. Do this first because the two workloads have opposite shapes.
  2. Pin down what loss is allowed. Say: "Telemetry must never block the product, so I assume bounded, visible loss for metrics and debug logs, and no loss for audit logs." This one answer decides the backpressure design later.
  3. Estimate series and samples first, then log bytes. Series times samples per second gives the write rate. Then multiply by bytes per sample after compression. Say: "Ten million series at a ten second interval is about a million samples a second, so cardinality and memory will matter more than disk." Do metrics first because they show why memory is the limit, then logs to show why storage cost is.
  4. Draft the write and query APIs. One batched write endpoint per signal with a tenant id, one range query endpoint, one rules endpoint. Say: "Writes are batched and safe to retry; a 429 tells agents to slow down."
  5. Sketch the one-box design and break it. One Prometheus-style server plus one search node. Say what fails: memory, single copy of data, alerting sharing a box with queries, no tenants.
  6. Add the pipeline. Agents, distributors, a Kafka buffer, ingesters, object storage, compactor, query frontend. Say: "The buffer lets storage be slow without losing data."
  7. Go deep on the metric engine. Head block with a write-ahead log, immutable blocks, an inverted label index, delta-of-delta and XOR compression. Then cardinality, because it is the classic production incident.
  8. Go deep on logs and alerting. Index labels only, store compressed chunks cheaply. Then alert rules, states, grouping, and an independent alert path.
  9. Close with tenancy, failures and the monitor of the monitor. Quotas, shuffle sharding, failure table, a second small stack and a Watchdog alert.

The decision points

  • Pull or push? Ask: do I need to know that a target is down, and do short jobs exist? Pull gives liveness, push covers short jobs and logs, so a node agent does both.
  • General database or a purpose-built time-series store? Ask: how regular is the data? Regular timestamps and slowly changing values compress to a couple of bytes per sample, which a general store cannot match.
  • Full-text index or labels plus compressed chunks for logs? Ask: how often are lines read? Rarely, so index only labels and scan, with a search engine for a curated subset.
  • Write directly to storage or through a buffer? Ask: what happens when storage is slow? A buffer turns slowness into lag instead of loss.
  • Reject, drop or charge when a tenant misbehaves? Ask: is this internal or a product? Internal platforms reject over a cap with a clear alert; vendors also charge.
Interview tip Raise cardinality yourself before the interviewer does: "series count is the product of label value counts, so one unbounded label like user id can bring down the ingesters, and I defend with per-tenant limits." It shows real operating experience.

Common mistakes on this problem

  • Designing one pipeline for metrics and logs. Fix: split them, and share only the buffer, tenancy and alerting.
  • Forgetting cardinality. Fix: state the product-of-labels rule and the defences.
  • Indexing every word of every log. Fix: compare storage cost with the label-index design before choosing.
  • Averaging percentiles. Fix: store histograms or sketches and merge them.
  • Running alerts on the same path as dashboards. Fix: give alerting a dedicated read path and a dead man's switch.
  • Letting the platform depend on what it monitors. Fix: separate failure domain and a small second stack.

1. Problem statement and clarifying questions

The prompt is usually one line: "Design a metrics and logging system like Prometheus plus Grafana plus an ELK stack, or like Datadog." That sentence hides two different workloads. Metrics are small numbers sampled over time (CPU at 63 percent, 412 requests served), identified by a name and a set of labels. Logs are free text or structured records describing individual events ("user 7 failed login from 10.0.0.4"). They differ in volume, shape, query pattern and cost, so a good answer builds two pipelines that share an ingestion buffer, an alerting engine, a tenancy model and a UI. We start by asking questions, as described in Chapter 1.

QuestionAssumed answer
Who are the users?Engineers and on-call responders of one large company (internal platform), roughly 500 teams, treated as tenants. We note how it changes for a SaaS vendor.
How many sources?50,000 hosts and containers, about 200 active metric series per process on average after labels, plus infrastructure and business metrics. Target: 10 million active time series and 1 million log lines per second on average.
Metric resolution?10 second default scrape or push interval, 1 second allowed for a few opt-in series.
Freshness?A metric sample should be queryable within 15 seconds of collection; a log line searchable within 30 seconds. Alerts fire within about 1 minute of a condition becoming true.
Retention?Metrics: raw 15 days, 1 minute rollups 90 days, 5 minute rollups 13 months. Logs: 7 days fully searchable, 30 days cheap and slower, 1 year archived for compliance on selected streams.
Is it acceptable to lose data?Metrics: small losses are tolerable (a gap of a few samples), never silent. Logs: audit logs must not be lost; application debug logs may be sampled or dropped under overload with a counter of what was dropped.
Query types?Metrics: range queries with aggregation ("p99 latency per service for the last 6 hours"). Logs: filter by time range plus labels plus text ("service=checkout, level=error, contains 'timeout'").
Traces?Out of scope; we mention where they plug in. See Chapter 54 and Chapter 52.

2. Requirements and scope

2.1 Functional

  • Collect metrics from hosts, containers and applications through agents, with both pull (scrape) and push paths.
  • Store time series with labels and answer range queries with aggregations (sum, rate, quantiles) and group-by on labels.
  • Collect logs, parse them into structured fields, store and search them by time, labels and text.
  • Dashboards: saved queries rendered as graphs, auto refreshing.
  • Alerting: user-defined rules over metrics (and optionally log-derived counts), notification routing to pager, chat and email, with deduplication, grouping, silencing and escalation.
  • Multi-tenancy: per-team isolation, quotas, and per-team cost visibility.

2.2 Non-functional

  • Write availability above all. Ingest must accept data during a storm. A monitoring system that goes blind during an outage is useless.
  • Dashboard queries return in under 2 seconds at p95 for the last 24 hours, under 5 seconds for 30 days.
  • The alerting path is more critical than dashboards and must be independent of the heavy query path.
  • Cost: the storage bill is the dominant cost. We will compress aggressively and tier data.
  • The system must survive the loss of one availability zone with no alert loss, and must not depend on the infrastructure it monitors (no circular dependency).

2.3 Out of scope

Distributed tracing storage, profiling, user-facing product analytics (see Case study 20 for stream aggregation with exactness), security information and event management detection rules, and anomaly detection by machine learning (we mention it only as a later extension).

3. Estimation with real arithmetic

Estimation drives the architecture here more than in most designs, so we do it carefully. Techniques are in Chapter 2.

3.1 Metrics volume

  • Active series: 10,000,000. Scrape interval 10 s, so each series gets 0.1 sample per second.
  • Sample rate: 10,000,000 × 0.1 = 1,000,000 samples per second on average. Peak (restarts, scrape alignment, a deploy that creates new series) is about 2×, so 2M samples/s. Design for 3M to leave headroom.
  • Raw sample: an 8 byte timestamp and an 8 byte double is 16 bytes. Per day: 1,000,000 × 86,400 = 86.4 billion samples. Uncompressed that is 86.4e9 × 16 B = about 1.38 TB per day.
  • Compressed with the delta-of-delta timestamp and XOR value scheme (section 7), real data averages about 1.4 to 2 bytes per sample. Take 1.5 B: 86.4e9 × 1.5 = about 130 GB per day. With 15 days raw: about 1.95 TB. With replication factor 3 for durability on local disks: about 6 TB of block storage. Small.
  • Series index: 10M series, each with about 10 labels at about 60 bytes of text (names and values dictionary encoded to far less). Say 150 bytes per series in the index: 1.5 GB, plus the postings (inverted) lists. Active-series state in memory: about 3 KB per head series in a Prometheus-like engine (labels, chunk, mapping) so 10M series is about 30 GB across the ingesters. Memory, not disk, is the real limit, and this is why cardinality dominates the design.
  • Rollups: 1 minute rollup stores per series per minute a few aggregates (min, max, sum, count; call it 4 values, about 6 bytes compressed). 10M × 1,440 minutes × 6 B = 86 GB per day for 90 days = 7.8 TB. 5 minute rollups: 10M × 288 × 6 B = 17 GB/day; 13 months is 395 days, so 6.8 TB. Rollups cost more than raw in total because they live much longer, which is why we only roll up series that are queried over long ranges.

3.2 Ingest network for metrics

Agents send batches. A batch sample is about 20 bytes on the wire after protobuf and snappy compression with label references interned per request. 2M samples/s peak × 20 B = 40 MB/s. Easy for a few dozen distributors; the pressure is on memory and CPU of ingesters.

3.3 Log volume

  • 1,000,000 lines per second average, 500 bytes per line (structured JSON including labels): 500 MB/s. Peak 3× during an incident, when everyone logs errors: 1.5 GB/s.
  • Per day: 500 MB/s × 86,400 = 43.2 TB raw. Per year: 15.8 PB raw.
  • Compression: general purpose block compression (zstd) on repetitive structured text typically gives 6 to 10×. Take 8×: 5.4 TB per day. 30 days: 162 TB in object storage. At about $23 per TB-month for standard object storage that is about $3.7k per month. Compare with indexing every token in a search engine: an inverted index plus stored fields is often 1× to 1.5× of raw size on fast replicated SSD. 7 days × 43.2 TB × 1.2 × 2 copies is roughly 730 TB of SSD, an order of magnitude more expensive. This one comparison decides the logs architecture (section 8).
  • Kafka buffer sizing: 500 MB/s × 3 replicas = 1.5 GB/s of replicated disk writes. Retention 6 hours of buffer: 500 MB/s × 21,600 s = 10.8 TB per copy, 32 TB with replication (compressed batches halve this to about 16 TB). Partitions at roughly 5 MB/s sustained each: 100 partitions at average, 300 to absorb peak with consumer parallelism.

3.4 Query load

Dashboards: 5,000 engineers, 2,000 open dashboards at any time, each with 12 panels refreshing every 30 seconds: 2,000 × 12 / 30 = 800 panel queries per second, a heavily repetitive load (identical queries, so a results cache helps). Alert rules: 50,000 rules at a 30 s evaluation interval = 1,670 evaluations per second. Ad hoc log searches: about 20 per second.

Key numbers to carry 10M series, 1M samples/s, 1.5 B per compressed sample, 130 GB/day metrics. 1M lines/s, 500 MB/s, 43 TB/day raw, 5 TB/day compressed. Logs outweigh metrics in bytes by about 40×, but metrics outweigh logs in query value per byte. Treat them separately.

4. API design

We need a write API for agents and a read API for dashboards and alerting. Both are authenticated, carry a tenant id, and follow the conventions in Chapter 5. The wire format is binary and compressed, per Chapter 7.

POST /v1/metrics/write            (Content-Encoding: snappy, body: protobuf)
Headers: X-Tenant-Id: team-checkout, Authorization: Bearer ...
Body: [ { labels: {__name__:"http_requests_total", service:"cart", code:"200", pod:"cart-7f"},
          samples: [ {ts_ms: 1700000000000, value: 4123.0}, ... ] }, ... ]
Response: 204 | 400 (bad labels) | 413 (too large) | 429 (quota, Retry-After) | 503 (retry)

POST /v1/logs/push                (body: protobuf or NDJSON, snappy)
Body: { stream_labels: {service:"cart", env:"prod", level:"error"},
        entries: [ {ts_ns, line, structured_metadata:{trace_id:"..."}} ] }

GET /v1/query_range?query=sum(rate(http_requests_total{service="cart"}[5m])) by (code)
        &start=...&end=...&step=60s
GET /v1/logs/query?query={service="cart",env="prod"} |= "timeout" | json | latency_ms > 500
        &start=...&end=...&limit=1000&direction=backward

PUT /v1/rules/{tenant}            (alert and recording rule groups, YAML)
POST /v1/alerts/silences          (matchers, start, end, creator, comment)

Two design points. First, the write path is batched and idempotent enough: re-sending the same (series, timestamp, value) is harmless because storage drops exact duplicates, so agents can retry freely. A different value at an identical timestamp is rejected as "out of order or conflicting". Second, a 429 with Retry-After is how quotas and backpressure are communicated to agents (section 12).

5. Data model and storage choices

A time series is identified by its full label set, including the special label __name__. The identity of a series is a hash of its sorted label pairs. A sample is (timestamp, float64). Everything else follows from these two facts.

6. A first simple design, then the scaled architecture

6.1 The single-box version

One Prometheus-style server scrapes about 1,000 targets every 10 seconds, stores 10 to 100 thousand series on local disk, evaluates alert rules, and serves a graph UI. Logs go to files that an agent ships to one search node. This works to roughly a few hundred thousand series and a few thousand log lines per second, and it is how most companies start. It fails in four ways: (1) a single machine's memory caps active series, (2) the disk is the only copy so loss of the node loses history, (3) the node is both the alerter and the query engine, so a heavy dashboard query can delay alerts, and (4) there is no tenant isolation. Scaling means solving those four, in the order that hurts.

6.2 The scaled architecture

Hosts and pods are watched by a node agent, which scrapes, tails logs and buffers. 2. The agent pushes batches to the distributors, which check the tenant, quota and pick a partition. 3. The distributors write to the Kafka buffer. 4. Three consumers read it separately: metric ingesters, log ingesters, and the rule evaluator. 5. The key structural choice is the decoupling at the Kafka buffer (Chapter 34). Without it, every ingester restart or slow disk turns into dropped writes at the edge. With it, ingesters consume at their own pace, the same data stream can feed multiple consumers (ingesters, a streaming rule evaluator, an archiver), and a regional outage of a downstream store only grows a lag that drains later. The cost is extra latency (a second or two) and operating Kafka.

6.3 Agents and collectors: push versus pull

This is the first design fork an interviewer expects you to discuss. In pull, a collector knows the list of targets (from service discovery, see Chapter 49) and fetches an HTTP endpoint (/metrics) from each target every interval. In push, each application or agent sends its data to a central endpoint.

Walkthrough. The left half is pull and the right half is push. Blue boxes are our components, purple boxes are the things being watched, and green is the service discovery list. In pull, 1. service discovery tells the collector which targets exist (dashed arrow). 2. The collector opens a request to each app's metrics endpoint on its own schedule (the two solid arrows). 3. If a request fails, the collector records the target as down, which is why the left list says liveness is free. In push, 1. each app or batch job sends its data to the gateway whenever it likes. 2. The gateway applies auth and quota. 3. If nothing arrives, the gateway cannot tell whether the app died or the network broke, which is the weakness on the right. The two are drawn side by side because the answer is not one or the other: the node agent in the text pulls from local targets and pushes outward. On a whiteboard, draw one arrow direction per half and write one plus and one minus beside each. Remove pull and you lose cheap liveness. Remove push and short-lived jobs vanish unseen.

Our answer is a hybrid built around a node agent. On every host a lightweight agent (a DaemonSet in Kubernetes) scrapes local targets by pull, which gives the "up" signal for free (a failed scrape records up=0) and keeps scrape load local. The agent also tails log files, reads the container runtime log streams, and accepts pushes from short lived batch jobs on localhost. It then does a single outbound push (remote write) of batched, snappy compressed data to the distributors. This gives the benefits of pull for liveness and rate control inside the host, and the benefits of push across the network boundary: agents initiate outbound connections only, which passes firewalls and means the central system need not know every target. Agents add jittered scrape offsets so that 50,000 hosts do not all fire in the same second, and they buffer on local disk (a few minutes to an hour) when the network or the platform is down. Compare the same trade in the chapters on microservice observability and resilience.

Interview tip Never say "pull is better" or "push is better". Say which signals each is good at: pull for liveness of long running services, push for ephemeral jobs and logs, and that the agent hybrid gives you both.

7. Request flows and time-series storage internals

7.1 Write flow

Walkthrough. This is a sequence diagram with five lifelines: agent, distributor, Kafka, ingester and object storage. Time runs downward. Solid arrows are requests, green arrows are acknowledgements, and the dashed loops are work done inside one machine. 1. The agent sends a compressed batch with its tenant id. 2. The distributor checks authentication and limits, then hashes the series to pick a Kafka partition. This is the loop on its own lifeline. 3. It produces to Kafka and waits for all replicas. 4. Kafka acknowledges, and only now does the distributor return success to the agent. 5. Later, the ingester that owns that partition consumes the data. 6. It appends to its write-ahead log and the in-memory head. 7. Every two hours it uploads a finished block to object storage. The key point is where the acknowledgement sits: after the durable Kafka write, before the ingester has applied anything. That is why a slow ingester only adds lag. On a whiteboard, draw a bracket around steps 1 to 4 as the part the agent waits for. If the acknowledgement were after step 6, a restarting ingester would stall every agent.
  1. The agent posts a batch (up to a few thousand samples) to a distributor chosen by load balancer (Chapter 9).
  2. The distributor authenticates the tenant, checks per-tenant limits (series count, rate, label size), validates labels, then computes hash(tenant, labels) to choose a Kafka partition so that every sample of a series lands on one partition and therefore one ingester (preserving per series order).
  3. It produces with acks=all, waits for the replicas to acknowledge, and returns 204. If Kafka is unavailable it returns 503 and the agent retries from its local buffer.
  4. The ingester that owns the partition appends to a write-ahead log and to the head block in memory.
  5. Every 2 hours the head is cut into an immutable block, uploaded to object storage, and the WAL is truncated.

7.2 Why a dedicated time-series engine

Time series data has properties a general store ignores. Writes are overwhelmingly appends of the newest timestamp. Reads ask for a time range of many series. Neighboring samples in one series are nearly identical (a counter increments slowly, a gauge barely moves, timestamps are regular). A B-tree storing (series, ts, value) rows pays tree maintenance for ordering that arrives for free, and stores about 16 bytes plus overhead per sample. See Chapter 19 for LSM versus B-tree. A TSDB instead stores per series a compressed stream of samples in a chunk, and keeps the series identity once.

7.3 Compression: delta-of-delta and XOR

The scheme from Facebook's Gorilla paper (and used in Prometheus and many others) compresses timestamps and values separately.

  • Timestamps, delta-of-delta. Scrapes are every 10,000 ms, so consecutive timestamps are t, t+10000, t+20000. The first difference (delta) is 10,000 every time. The difference of those deltas (delta of delta) is 0. A delta-of-delta of zero is encoded in 1 bit. Small deviations (jitter of a few ms) take 9 to 12 bits with a short prefix code. A series with perfectly regular timestamps therefore spends about 1 bit per sample on time.
  • Values, XOR. Interpret each float64 as 64 bits and XOR it with the previous value. If the value is unchanged the XOR is zero, stored as 1 bit. If it changed slightly (same sign, exponent, high mantissa bits) the XOR has long runs of leading and trailing zeros; store only the meaningful middle bits plus a few bits describing where they sit. Counters that increase by small integers and gauges that stay near a value compress very well; random noise compresses poorly.
Walkthrough. This is a worked example in rows, not a box diagram. The top block follows timestamps in milliseconds across five scrapes. 1. The first row is the raw time. 2. The second row, delta, is the gap from the previous scrape: 10000, 10000, then 10002 and 9999 because of small jitter. 3. The third row, dod, is the change in that gap: 0, then plus 2, then minus 3. 4. The fourth row shows the cost: a zero takes 1 bit and a tiny change about 9 bits. The bottom block does the same for values. A counter that stays at 4123.0 costs 1 bit, because XOR with the previous value is all zeros. When it moves to 4125.0, only a few middle bits differ, so about 14 bits are stored. The number to remember is that regular data costs about one bit per timestamp, which is how 16 raw bytes shrink toward 1.5 bytes. Read the caption's last line as the result. On a whiteboard, write the three timestamps and show the deltas being subtracted. Remove the delta step and each timestamp costs 64 bits again.

The arithmetic matters for the estimation: 130 GB per day instead of 1.4 TB is the difference between a cheap and a painful system. Note the limitation: compression works per chunk (typically 120 samples per series), so a series that is queried must decompress sequentially from the start of a chunk. That is fine because queries read ranges.

7.4 Block layout and the index

Walkthrough. The amber box on the left is the head: the newest two hours, held in memory and protected by a write-ahead log on disk, costing about 3 KB per active series. The green box on the right is one immutable block, with three blue parts inside. 1. New samples land in the head. 2. When two hours are full, the arrow labelled cut freezes the head into a block. 3. Inside the block, the chunks folder holds the compressed samples. 4. The index holds series and postings, meaning for each label pair a sorted list of series ids. 5. The meta file records the time range so a query can skip the block by time alone. The three lines at the bottom show the query order: pick blocks by time, intersect the posting lists, read only the matching chunks. It is drawn as head plus immutable blocks because immutable files can be cached, copied to object storage and deleted whole. Remove the write-ahead log and a crash loses two hours. Remove the postings and every query scans every series.

The postings lists are the same structure as a search engine's inverted index (Chapter 22): for each label pair, a sorted list of series ids. A selector like {service="cart", code=~"5.."} is evaluated by looking up the lists for each matcher and intersecting them with a merge, which is fast because lists are sorted. This is also why high cardinality is expensive: the index grows with the number of distinct label pairs and series.

8. Deep dive 1: cardinality explosion

Cardinality is the number of distinct time series. A metric with labels multiplies: http_requests_total with 50 services × 20 endpoints × 5 status codes × 3 methods is 15,000 series. That is fine. Add a user_id label with a million users and it is 15 billion potential series. Each new label value creates a new series with its own head chunk, index entry and posting list entries, costing about 3 KB of memory in the head. A developer who adds one innocent label (request id, URL with path parameter, container id that churns on every deploy) can create millions of series in minutes, push ingesters out of memory, and bring down monitoring for everyone. This is the most common production incident for metrics systems, and the interviewer wants to hear it.

Walkthrough. Read the top row as a multiplication. Blue boxes are the parts of a metric: the name, then labels with their number of distinct values. 1. The name is one value. 2. Service has 50 values. 3. Endpoint has 20. 4. Status has 5. 5. The product, in the green box, is 5,000 series, which is bounded and affordable. The bottom row repeats the multiplication with one extra label. 6. 8.1 Defenses, in layers

  1. Per-tenant active series limit enforced at the distributor using a cheap estimate (a HyperLogLog sketch per tenant, see Chapter 57) or an exact count by the ingester. Beyond the limit, new series are rejected with a clear error, while existing series continue to accept samples. This contains blast radius to the offending team (Chapter 42).
  2. Label hygiene validation: maximum labels per series (for example 30), maximum name and value length, forbidden label names.
  3. Agent-side relabeling and drop rules to strip known bad labels before they leave the host.
  4. Cardinality analysis UI: top metrics by series count, top labels by distinct values, growth rate. Alert when a metric's series count grows more than 3× in an hour. This is the feedback loop that educates teams.
  5. Churn control. Containers get a new pod name at each deploy, so a deploy creates a whole new generation of series and the old ones become inactive. Active series stay constant but total series ever created grows, bloating the index. Mitigation: drop the pod label (aggregate to deployment level in the agent) for most metrics, and let compaction drop series with no recent samples.
  6. Pre-aggregation (recording rules) turn a high cardinality input into a small result stored for dashboards ("requests per service, per code, per minute").
Option for handling excess cardinalityProCon
Reject new series over limitProtects the system; predictable; tenant sees the errorSome of the tenant's metrics silently missing until they fix it, so surface errors prominently
Aggregate away labels at ingest (drop the label, sum)Keeps the data, bounded costLoses detail; changes semantics for gauges (sum of gauges may be meaningless)
Allow, charge the tenant (usage based billing)Fair for a vendor product; simple policyDoes not protect memory in real time; a hard cap is still needed

We choose reject plus alert for an internal platform (a hard cap per tenant with a soft warning at 80 percent), and charge back for a vendor. The same dimension appears in logs: the set of stream labels must also be small, which is the lesson of section 10.

9. Deep dive 2: downsampling, rollups and retention tiers

Nobody needs 10 second resolution from 11 months ago. A graph of one year at a typical 1,000 pixel width has a point every 8.7 hours, so loading 3 million raw samples per series to draw it is pure waste. Downsampling stores long-range data at lower resolution. The compactor produces rollup blocks in the background.

9.1 What to keep per rollup point

If you store only the average, you lose spikes, and the average of averages is wrong when sample counts differ. Keeping min, max, sum and count lets you recompute averages correctly and still see the peak. Counters are special: you keep the last value of the window so that rate across the window still works (a rate is a difference of counter values over time, with resets handled). Percentiles are the trap: you cannot compute a p99 from p99s. The correct technique is to store histograms (bucket counts, which can be summed across series and windows) or mergeable sketches such as t-digest or DDSketch, then compute quantiles at query time from merged buckets. Averaging p99 values across 50 hosts yields a number that corresponds to nothing.

10.1 Metric query flow

Walkthrough. This sequence diagram follows one dashboard panel asking for 24 hours of data. The lifelines are the dashboard, query frontend, querier, ingesters and store gateway. 1. The query frontend does three things worth naming. It splits a long range into per-day sub-queries executed in parallel, caches results (past days never change, so they cache forever; only the last day is recomputed), and holds a fair queue per tenant so one tenant's expensive query cannot starve others. Queriers must also enforce limits: maximum series returned, maximum samples scanned, maximum time range, and a timeout, because an unbounded sum(rate(x[1y])) on raw data can scan billions of samples. Dashboard load is highly repetitive (800 panel queries per second with many identical expressions and refresh cycles), so the results cache gets a high hit rate, in the spirit of Chapter 13. Aligning query start and end to step multiples makes cache keys line up.

10.2 The logs path: structured logs and two storage designs

Logs are written once, read rarely (during incidents or audits), and contain huge amounts of text. The key idea for cost is to index little and scan well. First, make logs structured: JSON or key-value lines with fields like level, service, trace_id, latency_ms. Structure lets the platform extract fields once at ingest (or at query time) instead of regexes, and lets you correlate with traces and metrics by shared labels and ids (Chapter 52).

This favors analytics over text grep. Which of B or columnar you prefer depends on whether queries are mostly "show me the lines" (B) or "count and group by field" (columnar). State your assumption.

10.3 Parsing, structure and sampling

Parsing happens in the agent (cheap, scales with hosts) or a pipeline stage (central, easier to change). We parse in the agent for container logs (JSON decode, extract level and trace id), and enrich with Kubernetes labels. Sampling reduces volume at the source: keep all warnings and errors, keep 10 percent of info logs, 1 percent of debug logs, and make the rate dynamic (when a service produces more than its budget, the sampler increases the drop ratio of low-severity lines and emits a counter "dropped lines by reason"). Sampling by hash of trace id keeps all lines of a sampled request together, which makes sampled logs still debuggable. Never sample audit and security streams; route them to a separate topic with strict durability.

11. Deep dive 3: the alerting engine

Alerting converts data into pages. A bad alerting system either misses outages or trains engineers to ignore pages. Concepts from SLOs and burn rate alerts live in Chapter 54; here we focus on mechanics.

11.1 Rule evaluation

A rule is a query plus a condition plus a duration: "sum(rate(errors[5m])) / sum(rate(requests[5m])) > 0.02 for 5m". The rule evaluator runs every group at its interval (for example 30 s), executes the query, and tracks per series state. States: inactive, pending (condition true but not yet for the full duration), firing, and resolved. The "for" duration is the first noise filter. 50,000 rules at 30 s is about 1,670 evaluations per second, each a small query; they must run on dedicated evaluators reading directly from ingesters and recent blocks, not through the user facing query queue, so a dashboard storm cannot delay a page.

Walkthrough. The top row is the life of one alert, with green for healthy, amber for waiting, and red for firing. 1. The alert starts Inactive. 2. When the rule condition becomes true it moves to Pending, where it waits out the for duration. 3. If the condition stays true, it moves to Firing. 4. When the condition turns false it becomes Resolved. The dashed arrow under the row is the important shortcut: if the condition goes false while still Pending, the alert returns to Inactive and nobody is paged. The lower part shows what happens to a firing alert. 5. It goes to the alert manager, a cluster of three replicas that deduplicate, group, inhibit and silence. 6. The router picks the team and channel by severity and hours. 7. A page goes to the pager, or a message to chat. The two notes at the bottom say how replicas avoid double pages by gossip and how flapping is damped with hysteresis. Remove Pending and every blip pages someone. Remove grouping and a rack failure sends 200 pages.

11.2 Dedup, grouping, inhibition, silences, routing

  • Deduplication. The rule evaluators run as an HA pair and both send the same firing alert every interval. The alert manager identifies an alert by its label set and treats repeats as one, only re-notifying every repeat interval (for example 4 hours).
  • Grouping. When a rack fails, 200 pods fire "instance down" alerts. Group by (cluster, alertname) and send one page with a list. Wait a few seconds of group wait to collect initial members.
  • Inhibition. If "datacenter unreachable" is firing, suppress "service down" alerts in that datacenter. This reduces cascading noise.
  • Silences. Time bounded matchers created by humans during maintenance.
  • Routing. A tree of label matchers sends alerts to owners: team=payments, severity=page to the payments pager, severity=ticket to a queue. Escalate if unacknowledged after 10 minutes. Ownership comes from the service catalog, not from guessing.
  • Flapping. A metric oscillating around its threshold generates repeated fire and resolve pages. Tools: the "for" window, hysteresis with two thresholds, a short "keep firing" period after clearing, and evaluating over a longer range (rate over 5 minutes, not 1 minute).

The alert manager cluster is small (3 replicas), prioritises availability (AP in CAP terms, see Chapter 28): replicas gossip a notification log and silences (Chapter 33). If gossip partitions, the failure mode is a duplicate page rather than a missed one, which is the right bias. Important failure: what if the alerting pipeline itself is broken? Use a dead man's switch: an always-firing "Watchdog" alert sent to an external service (outside our infrastructure) that pages when it stops arriving. And alert on the platform's own SLIs (ingest lag, rule evaluation lag) from a second, tiny, independent monitoring stack.

Watch out Alert on symptoms users feel (error ratio, latency SLO burn) rather than causes (CPU high). Each cause alert is a page that may have no user impact, and the on-call learns to ignore pages.

12.1 Backpressure and loss tolerance

What happens when ingestion is faster than what storage can take? A system must pick between three behaviors per signal, on purpose, not by accident: block the producer, buffer, or drop. Producers here are applications that must never block on telemetry, so blocking is out at the app, and the correct stance is: losing telemetry is better than hurting the product, but loss should be bounded, visible and prioritized.

  1. App to agent: local, non-blocking, bounded in-memory queue. If full, drop and count.
  2. Agent to distributor: on 429/503, exponential backoff with jitter; buffer to local disk up to a cap (say 1 GB, or about 30 minutes at 500 KB/s per host). After the cap, drop oldest low priority data first (debug logs, then info), keep errors and metrics.
  3. Distributor to Kafka: if Kafka is down, return 503 so the agents hold the data. Kafka is the shock absorber: during a downstream slowdown, consumer lag grows from 0 into minutes, and recovers when consumers catch up. We alarm at lag above 60 s, page above 300 s.
  4. Consumers: if an ingester cannot keep up, it falls behind (freshness degrades) instead of losing data. Autoscale consumers on lag (Chapter 43).
  5. Overload shedding: if lag exceeds the Kafka retention buffer (6 hours), data would be lost, so before that point we shed: drop sampled debug logs at the distributor, then raise log sampling globally, in a documented priority order.

Loss tolerance differs per stream. Metrics: at-least-once delivery with duplicates harmless (same timestamp, same value is deduplicated). Logs: at-least-once, with duplicates removed by (stream, timestamp, line) identity, or tolerated. Audit logs: separate topic, replication factor 3, min.insync.replicas=2, no sampling, written also to a WORM (write once) bucket. See Chapter 32 for dedup keys and Chapter 35 for delivery semantics.

13. Scaling, bottlenecks and hot spots

  • Ingesters are memory bound. 10M series × 3 KB = 30 GB, with replication factor 3 for the in-memory head that is 90 GB across the fleet; spread over 30 ingesters of 8 GB heads each it is comfortable. Add ingesters, and partitions move by consumer group rebalance (Chapter 34) with series ownership following the partition.
  • Hot series. A single very busy series is just one partition's worth: samples per series are small. The real hotspot is a tenant whose series hash unevenly; sharding by series hash (not by tenant) spreads even a giant tenant.
  • Hot partitions in logs. A single noisy stream (one service printing 100 MB/s) saturates the partition that hashes to it. Fix: shard a stream across N partitions by adding a bucket suffix when the stream exceeds its per-stream rate and rely on timestamps for ordering at query time.
  • Index cache and store gateway. Old-block queries need index headers; we shard blocks across store gateways by block id hash with replication 2, and keep the compact index header (posting offsets) in memory, loading chunks from object storage on demand with a local cache. A cold query over 90 days reads tens of blocks in parallel.
  • Compactor. Merges 2 h blocks into 12 h and 24 h blocks to reduce the number of blocks queried and to remove duplicates produced by replicated ingestion. It is a batch job sharded by tenant, throttled to not starve the object store.
  • Query fanout. Large aggregations touch many series: push partial aggregation down to queriers and merge (a two level sum), set limits, and prefer recording rules.
  • Sharding strategy summary. Writes: hash(series) to partition. Reads: by time then by block then by tenant. See Chapter 25 for rebalancing without hotspots.

14.1 Consistency and idempotency

Monitoring data accepts eventual consistency: a dashboard may be 15 seconds behind and two replicas of a head may differ by a sample until merged. Queriers deduplicate replica data by series and timestamp (a "last one wins" or a "same value" check). Writes are idempotent as noted. The one place we need stronger guarantees is configuration (rules, silences, routes): a small replicated database (Chapter 24) with versioning, so an old rule set is never silently resurrected. Time itself is a consistency issue: agent clocks drift, so the distributor rejects samples more than a few minutes in the future and old ones beyond the out-of-order window, and uses server receive time for logs without usable timestamps (Chapter 27).

14.2 Who monitors the monitor?

Run the platform's control plane in a separate failure domain from the workloads it watches: its own Kubernetes cluster or VM pool, own DNS and credentials, no dependency on the service mesh it observes. Keep a minimal second stack (a small Prometheus-style instance plus an external pager integration) which scrapes only the platform's own health endpoints: Kafka lag, ingester memory, rule evaluation delay, Watchdog. If the main platform dies, the second stack pages. This avoids the circular dependency in which an outage of the compute platform also kills the monitoring that would report it. Deployments use cells and staged rollout (Chapter 43); config and rule changes are canaried against one tenant first.

15. Security, abuse, SLOs and cost

15.1 Security and abuse

  • mTLS between agents and distributors, with per-tenant tokens mapping to a tenant id; the tenant id is set by the gateway and never trusted from the payload (Chapter 55).
  • Logs contain secrets and personal data by accident: scrub known patterns (card numbers, tokens, emails) at the agent, deny list fields, and support deletion by user id for privacy laws (Chapter 56). Store logs per tenant prefix with per-tenant encryption keys for sensitive streams.
  • Query authorization: a tenant can only read its own data; cross-tenant queries require explicit federation grants.
  • Abuse: label bombs, huge lines (truncate at 256 KB), clock-skewed data, and expensive regex queries are all limited at the edge.

16. Evolution, phasing and alternatives

16.1 Build order

  1. Phase 1 (weeks): agents with scrape and log tail, one metrics server with remote storage, a log chunk store on object storage, dashboards, basic alert rules with an alert manager pair. No multi-tenancy.
  2. Phase 2: add Kafka, distributors and horizontally scaled ingesters; tenant ids and basic limits; query frontend with caching.
  3. Phase 3: downsampling and tiered retention, shuffle sharding, cardinality tooling, showback, dedicated evaluators, second stack for self monitoring.
  4. Phase 4: multi-region, exemplars linking metrics to traces, log to metric extraction, adaptive sampling, anomaly detection.

16.2 At 10× scale (100M series, 10M lines/s)

Ingestion scales linearly with more partitions and ingesters, but three things bend. First, the series index and head memory (300 GB of heads) force sharding the metric plane into multiple cells by tenant group, with a global query layer federating across cells. Second, the compactor and the number of blocks dominate; use larger blocks and per tenant sharded compaction. Third, log scan cost grows linearly, so skip indexes and columnar formats become mandatory rather than optional, and sampling policies tighten. At 100× you move to streaming pre-aggregation before storage (stream processing as in Chapter 37, and see Case study 20) so that only aggregates are stored for most metrics.

16.3 Alternatives not chosen

  • Everything in Elasticsearch (metrics and logs): simple operationally at small scale but too expensive per byte and slow for metric aggregations at our scale.
  • A general wide-column or key-value store for metrics (see Chapter 20): works, but loses the 10× compression and the index tailored to label queries unless implemented on top.
  • Pure push (agentless SDK to central): reduces moving parts but loses free liveness and complicates backpressure at the application.
  • No Kafka (agents write direct to ingesters): lower latency and fewer systems, but a restart or hot ingester creates loss and the write path couples to storage speed. Acceptable for smaller deployments.
  • Buy a SaaS vendor: the right answer for many companies; the cost model then is per series and per GB, so the same cardinality and sampling discipline applies, and the interview answer still shows you understand what is inside.

17. Interview Q&A

Why put Kafka between the distributors and the ingesters instead of writing directly?

Kafka decouples receiving from storing. Without it, a slow or restarting ingester forces the distributor to either block, which pushes failure back to every agent, or drop data. With Kafka, the write is acknowledged once it is durable in a replicated log, and ingesters consume at their own speed, so a downstream slowdown becomes lag instead of loss. It also lets several consumers read the same stream (ingesters, rule evaluators, an archiver) and allows replay after a bug or a crash. The costs are one or two seconds of added freshness latency, the extra replicated disk (about 16 to 32 TB for 6 hours of logs), and another system to operate. For small deployments I would skip it, but at 500 MB/s of logs the buffer pays for itself during the first incident. See Chapter 34.

A developer added a user_id label to a metric and ingesters are running out of memory. What do you do, and how do you prevent it?

First contain: identify the tenant and metric from per tenant series counters, and have the distributor reject new series for that metric or apply a drop rule on the offending label at the edge, so existing series continue and memory stops growing. Then restore: ingesters that restarted will replay from Kafka, so apply the drop rule before the replay or it recreates the series. Prevent it with a hard active series limit per tenant, label count and length limits, a cardinality dashboard with growth alerts, review of new metrics in the CI for instrumentation, and an education message that identifiers belong in logs and traces, not metric labels. Shuffle sharding limits which ingesters the tenant could have affected in the first place.

How do you compute a p99 latency over a year when you only store rollups?

You cannot derive a p99 from stored p99 values, or from averages, because quantiles are not additive. The fix is to store a mergeable representation: histogram bucket counts (cumulative counts of requests under each latency bound) or a sketch such as t-digest or DDSketch. Rollups then sum bucket counts over the window, and the quantile is estimated at query time from the merged buckets, with error bounded by bucket width. This costs more per series than a single gauge (for example 20 buckets means 20 series) but is the only correct approach; choose bucket boundaries around your SLO thresholds, for example 100 ms and 500 ms, so that SLO compliance is exact.

How does Gorilla style compression reach about 1.5 bytes per sample?

Timestamps are stored as delta of delta: with a regular scrape interval the second difference is zero and costs 1 bit. Values are XORed with the previous value: unchanged values cost 1 bit, and slowly changing ones leave few meaningful bits between long runs of leading and trailing zeros, so a dozen or so bits suffice. Averaged across real series, about 1.3 to 2 bytes remain per sample against 16 raw, which means one day of a million samples per second drops from 1.4 TB to about 130 GB. Noisy floating values and irregular timestamps compress worse, so the number is workload dependent, and I would say "typically".

Why not index logs in Elasticsearch? When would you?

An inverted index over every token makes any word searchable in milliseconds, but it roughly doubles to triples the storage on replicated SSD, burns ingest CPU on analysis and segment merging, and requires shard management. At 43 TB per day of raw logs, that is hundreds of terabytes of SSD for a week, an order of magnitude more than compressed chunks in object storage plus a small label index. Since most log lines are never read, paying to index all of them is wasteful. I would use Elasticsearch for streams where interactive free text search matters (security investigation, customer support lookup) at moderate volume and short retention, and use the label index plus scan design for everything else. Details of the engine are in Chapter 22.

How do you avoid alert storms and flapping?

Several layers. In the rule, use a "for" duration and evaluate over a window so a single blip does not fire. Add hysteresis (fire above 2 percent, clear below 1 percent) and a short keep-firing period. In the alert manager, group alerts by cluster and name so 200 pod alerts become one page, inhibit symptoms when a root cause alert is firing, deduplicate repeated sends of the same alert, and silence during maintenance. At the design level, alert on user visible symptoms and SLO burn rates, not on every internal cause, and review alerts that page without action as bugs. These choices are rooted in Chapter 54.

What happens to the alerting system if the metrics store is down?

The goal is that alerting degrades more gracefully than dashboards. Rule evaluators read from ingesters and the recent window directly, on a dedicated path, with their own capacity, so a long-range query storm or object storage failure does not affect them. If even ingesters are unavailable, the evaluators produce "no data" results; we configure critical rules to treat absent data as an alert condition, and we have a Watchdog (dead man's switch) alert sent continuously to an external system that pages when it stops arriving. Finally a second, small independent monitoring stack watches the platform's own health. The principle is that the failure of any single component must not make the platform silently blind.

How do you handle a tenant that suddenly sends ten times more logs?

The distributor applies per tenant and per stream token buckets. Within burst allowance the data is accepted; beyond it the distributor returns 429 with Retry-After, and agents slow down and buffer locally. Because the quota is per tenant, other tenants' Kafka partitions and ingester capacity are unaffected, and shuffle sharding keeps the tenant on its own subset of ingesters. If the surge is legitimate (an incident), the platform team can raise the limit temporarily; if it is a bug (a log loop), the agent side sampler and the quota stop the flood after a short time. The tenant receives a notification with the top streams by volume, and showback charges them, which discourages chronic over-logging.

Pull or push for metrics, and why?

I choose a hybrid. Pull from a node-local agent gives free liveness detection (a failed scrape is a down signal), central control of the interval, and no need for applications to know where the platform lives. Push is necessary for short lived batch jobs that finish before a scrape, for logs, and for crossing firewalls, so the agent also accepts local pushes and then pushes outbound to the distributors in batches. Pure push has an ambiguity problem: silence could mean the app is dead or the network is broken. Pure pull has reachability and discovery burdens at scale. The agent design removes the disadvantages of each, at the cost of running an agent per host.

How would you make the monitoring platform itself highly available across zones and regions?

Inside a region, run every component across at least three zones: Kafka with rack-aware replicas and min ISR 2, ingesters with replication factor 3 placed in different zones, stateless distributors and queriers behind a load balancer, and object storage that is zone redundant. Losing a zone then leaves quorum for writes and a replica for reads. Across regions, two options: active/active, where agents send to the local region and the query layer federates and deduplicates; or active/passive with replicated object storage and a warm standby. For alerting, evaluate rules in both regions with dedup in a shared alert manager cluster or via gossip, so a regional failure does not lose pages. Keep a small self monitor outside the primary failure domain. The relevant theory is in Chapter 41 and Chapter 26.

How do you keep dashboards fast when 800 panel queries per second hit the system?

Most of that load is repetitive, so caching is the main tool. The query frontend splits a range into per day pieces; historical days are immutable and cached for a long time, while only the current partial day is recomputed, and cache keys use step aligned boundaries so different users share entries. Recording rules precompute expensive aggregations for the busiest dashboards, and the planner uses coarse rollup tiers when the step is large. Per tenant fair queues and scan limits stop one heavy query from slowing everyone, and queriers are sharded so a query is split across many cores. If the cache hit rate falls, check whether dashboards use relative ranges that change the key every refresh and align them to the step.

Recap

  • Two workloads: metrics (10M series, 1M samples/s, 130 GB/day compressed) and logs (1M lines/s, 500 MB/s, 5 TB/day compressed). Design them separately, share the buffer, tenancy and alerting.
  • Node agents scrape locally (pull) and push outbound in batches: hybrid gets liveness, ephemeral job support and firewall friendliness.
  • Kafka absorbs bursts and decouples ingestion from storage; ack after the durable write, apply later; lag is the pressure gauge.
  • Time-series storage uses a memory head with WAL, immutable blocks with an inverted label index, and delta-of-delta plus XOR compression for about 1.5 bytes per sample.
  • Cardinality is the main threat: series = product of label values; enforce per tenant limits, label rules and cardinality dashboards; identifiers belong in logs.
  • Retention tiers: raw 15 days, 1 minute rollups 90 days, 5 minute rollups 13 months, with min/max/sum/count and histograms (never averaged percentiles).
  • Logs: index labels only, store compressed chunks in object storage, add sparse and bloom indexes, use a search engine only for a curated hot subset; sample low severity, never audit logs.
  • Alerting runs on an isolated path: for-durations, dedup, grouping, inhibition, routing, hysteresis against flapping, a replicated alert manager that prefers duplicates over loss, and a Watchdog dead man's switch.
  • Multi-tenancy through quotas, shuffle sharding and fair query queues; backpressure with bounded buffers, 429 with retry, and prioritized, counted loss.
  • Monitor the monitor from a separate failure domain; cost is driven by memory per series and bytes of logs, so showback and sampling are cost controls.
