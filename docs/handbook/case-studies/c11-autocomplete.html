Case study 11 · Worked solutions

Design Search Autocomplete

As a user types into a search box, the system suggests the most likely completions within a fraction of a second. This worked solution builds it from a single trie, to a sharded and cached serving tier, to a log-driven pipeline that keeps suggestions fresh, with the numbers and failure modes an interviewer will probe.

How to approach this problem (read this first)

Autocomplete looks small, but it is a latency problem wrapped around a data structure and a data pipeline. The interviewer is testing three things. First, can you make a prefix lookup fast enough (under 20 ms on the server) by precomputing the top 10 completions at every trie node, instead of scanning a subtree? Second, can you explain that the whole index is only about 16 GB, so you shard for throughput and blast radius, not for size? Third, can you keep suggestions fresh with a batch build plus a small trending overlay, while serving never depends on the pipeline? Caching at the browser and CDN, and a clean story for typos and offensive terms, finish the answer.

The thinking order, step by step

  1. Pin down what you suggest. Ask whether you suggest past queries or entities, how many suggestions, prefix only or fuzzy, how fresh trends must be, and the latency target. You say: "I will do query completion, top 10, prefix first, p99 under 100 ms, with trends visible in about 5 to 15 minutes." Why now: each answer sizes a later decision: the data structure, K in each node, and whether you need streaming.
  2. Estimate requests, then memory. Compute 2 billion searches a day, about 6 requests per search, 12 billion requests a day, 139,000 per second average, 350,000 peak, 140,000 after caches. Then compute the index at about 16 GB. You say: "The index fits on one machine, so I shard only for QPS and isolation." Why now: the memory number prevents you from over-engineering sharding, and the QPS number sizes the serving fleet.
  3. Draft the API. Show GET suggest with the prefix, language and limit, a short Cache-Control, and a trie version in the response. You say: "It is a GET so browsers and the CDN can cache it, and personalization stays out of the shared response." Why now: caching is the biggest latency win, so the API shape comes before the internals.
  4. Name the data structure. Draw a trie and say each node stores the ids of its top 10 completions, computed at build time. You say: "Lookup is walk the prefix, read one list, with no subtree scan and no sort at request time." Why now: this is the crux of the problem, so say it before the architecture.
  5. Start simple, then list what breaks. One server holds the trie and reloads nightly. List six failures: one server, restart to reload, stale data, one-machine builds, far-away latency, no filtering. You say: "Each failure becomes a component: replicas, hot swap, trending overlay, distributed build, caches, filters." Why now: it gives an evolution path the interviewer can follow.
  6. Split serving from building. Draw the online path (browser, CDN, gateway, service, trie shards) and the offline path (logs, Kafka, stream and batch jobs, builder, snapshots). You say: "If the pipeline fails, suggestions get stale, but autocomplete stays up." Why now: the separation is the most important structural decision.
  7. Deep dive sharding and caches. Bucket by the first two characters, map buckets to shards by measured load, add replicas for hot buckets, and add a latency budget. You say: "Server work is about 15 ms, so most of the budget is network and caching matters more than micro-optimizing the trie." Why now: it connects the numbers back to the target.
  8. Deep dive freshness and ranking. Explain batch snapshot plus streaming overlay, thresholds for trends, blocklist, and merge with user history. You say: "Trends must pass count, burst and distinct-user gates, so a bot cannot make a term trend." Why now: this is where abuse, privacy and quality come in.
  9. Close with failure and evolution. Cover bad snapshot rollback, hot prefix, and what you build first. You say: "Rollback is a pointer flip to the previous snapshot while it is still in memory." Why now: it shows operational judgment.

The decision points

  • Trie, Elasticsearch or Redis sorted sets. Ask yourself: do I need only prefix lookups with a tiny latency budget? A trie with precomputed top-K gives microsecond reads, while search engines give flexibility but cost more latency, so use the trie for the hot path.
  • Batch only or batch plus streaming. Ask yourself: how quickly must breaking news show up? In minutes, so keep stable batch snapshots and a small streaming trending overlay rather than mutating the live trie.
  • Shard by first letter or by hashed bucket. Ask yourself: is traffic even across letters? No, since s and c are far busier than x, so hash two-character buckets and map them to shards by measured QPS.
  • Cache where. Ask yourself: which layer removes the most load? Browser and CDN, which absorb about 60 percent, so keys must be normalized and carry no session ids.
  • Personalize in the shared response or beside it. Ask yourself: will personalization destroy cache hits? Yes, so merge the user's recent searches at the service or client.

Common mistakes on this problem

  • Scanning the subtree and sorting at request time. Fix: store the top 10 ids at every node during the build.
  • Sharding because the data is big. Fix: the index is about 16 GB, so shard for QPS and isolation, and replicate for availability.
  • Mutating the live trie from the stream. Fix: publish immutable snapshots and swap a pointer, and keep trends in a small overlay.
  • Putting user ids or timestamps in the cache key. Fix: normalize the prefix and keep personalization out of the shared cache.
  • Treating the pipeline as a serving dependency. Fix: if it breaks, serve the last good snapshot.
  • Forgetting filtering and privacy. Fix: apply a blocklist at build and serve time and require minimum distinct users.

1. Problem statement and clarifying questions

The prompt is short: "Design the typeahead (autocomplete) feature of a web search engine." Every keystroke in the search box should show a dropdown with, say, the 10 best query completions for what has been typed so far. If the user types wea, we might show weather, weather tomorrow, wear os, weasel. The feature looks tiny, but it is one of the hardest latency problems in product engineering: it fires several times per search, the budget is tens of milliseconds, and the data underneath it changes every minute.

A strong candidate does not start drawing. They ask questions first, and state the assumption that follows from each answer, as the framework in Chapter 1 recommends.

2. Requirements and scope

2.1 Functional requirements

  • Given a prefix (and optional language, locale, and user identity), return up to 10 ranked completions.
  • Rank by how often queries are searched, boosted for recent surges (trending).
  • Merge in a few of the signed-in user's own recent searches.
  • Remove blocked terms from the output, and never learn them in the first place.
  • Tolerate a small typo in the prefix (for example wheather still gets weather suggestions).

2.2 Non-functional requirements

  • Latency: p50 under 30 ms and p99 under 100 ms as seen by the client, because beyond roughly 100 to 150 ms the dropdown lags behind typing and feels broken.
  • Availability: 99.99 percent. Autocomplete is an enhancement; if it fails, search still works, so the failure mode is "no suggestions", never an error page.
  • Scalability: hundreds of thousands of requests per second at peak.
  • Eventual consistency is fine. Two users may briefly see different suggestions. No transactions are needed.
  • Freshness: trending queries within minutes.

2.3 Out of scope

The search results page itself, spelling correction of the full query on the results page ("did you mean"), voice input, rich suggestions with images, and ads in the dropdown. We mention where they plug in, but we do not design them.

3. Back-of-envelope estimation

We follow the method of Chapter 2: write the assumptions, then do the arithmetic and keep it consistent for the rest of the page.

3.1 Traffic

  • 200 million DAU times 10 searches each is 2 billion searches per day.
  • A typical query is about 20 characters, but the user does not trigger a request per character. With client debounce (section 10) and the fact that the user stops once they see their suggestion, we assume about 6 autocomplete requests per search. Total: 2 billion times 6 = 12 billion autocomplete requests per day.
  • Average QPS: 12 billion divided by 86,400 seconds is about 139,000 requests per second.
  • Peak: searching follows the daily cycle, so use a peak factor of 2.5: about 350,000 requests per second at the edge.

3.2 Cache effect

Short prefixes are heavily repeated. Roughly the first three characters cover a small space (a few tens of thousands of distinct prefixes), and a large share of all requests are for short prefixes. We assume the browser cache plus the CDN edge absorb about 60 percent of requests, so the serving tier sees about 140,000 requests per second at peak (350,000 times 0.4). This is the number we shard for.

3.3 Data volume

  • Search logs: 2 billion events per day times about 100 bytes (normalized query, timestamp, locale, anonymized user bucket) is 200 GB per day, about 73 TB per year. We keep 30 days of raw logs (6 TB) and aggregates beyond that.
  • Distinct queries: the long tail is huge. Suppose 15 percent of daily searches are distinct, about 300 million per day. Most are seen once and are useless as suggestions. We apply a minimum-frequency threshold (say, seen at least 5 times over the window, plus a privacy threshold of several distinct users). After thresholding we keep about 100 million suggestion candidates.
  • Raw text: 100 million times about 25 bytes is 2.5 GB. The trie nodes (about 150 million after compressing single-child chains) at roughly 40 bytes of structure, plus 10 four-byte query ids for the top-K list, is about 80 bytes per node, so about 12 GB. Add a query table (id to string plus score) at 100 million times 30 bytes = 3 GB. Total: about 15 to 16 GB per language/locale-wide trie.

The conclusion is important: the whole structure fits in the RAM of one ordinary server (64 GB). We do not shard because of size. We shard for QPS and for blast radius, and we replicate for availability.

3.4 Serving capacity

One in-memory trie lookup is a handful of pointer hops plus a copy of 10 small ids, a few microseconds. A single server is limited by network and HTTP handling, not by the lookup: assume 20,000 requests per second per server for a lean service. 140,000 divided by 20,000 is 7 servers of capacity. We run 8 shards times 3 replicas = 24 servers, with 17,500 requests per second per shard at peak, so each replica runs at about 6,000 requests per second, leaving more than 3 times headroom for a replica loss, a hot prefix, or a deploy.

4. API design

The API is one read endpoint and one write path that is mostly implicit.

GET /v1/suggest?q=wea&lang=en&locale=US&limit=10&session=abc123
Headers: Accept: application/json, Authorization: (optional)

200 OK
Cache-Control: public, max-age=60
{
  "prefix": "wea",
  "suggestions": [
    {"text": "weather",           "score": 9120000, "type": "global"},
    {"text": "weather tomorrow",  "score": 4410000, "type": "global"},
    {"text": "wear os",           "score": 1200000, "type": "trending"},
    {"text": "weather radar",     "score":  980000, "type": "global"}
  ],
  "trie_version": "2026-11-17T09:00Z"
}

Design choices that interviewers like to hear justified:

  • GET with the prefix in the query string, so responses are cacheable by browsers, CDNs, and intermediate proxies. The prefix is normalized (lowercased, Unicode NFKC form, whitespace collapsed) on the client and again on the server so that cache keys match.
  • Personalization is a separate concern. Anything that depends on the user must not make the whole response uncacheable. We call a second small endpoint (or the same service with a cookie) only for signed-in users and merge client-side or at the aggregation layer (section 11).
  • A short Cache-Control (30 to 120 seconds) trades a tiny amount of freshness for large load savings.
  • Write path: there is no suggestion "write" endpoint. When the user submits a search, the existing search request is logged. A separate fire-and-forget beacon records suggestion impressions and clicks (POST /v1/suggest/events) so the ranking model can learn click-through rate. Both feed the pipeline in section 7.
  • Versioning and observability: the response carries the trie version, which makes "which build served this" visible when debugging.

For protocol details, see Chapter 5. A persistent connection (HTTP/2 or HTTP/3) matters here because the client sends many small requests; reusing one connection avoids paying the TCP and TLS handshakes on each keystroke (Chapter 3).

5. Data model and storage choice

There are three kinds of data, and each has a different best store.

DataStoreReason
Raw query logs (search events, suggestion clicks)Kafka for transport, then object storage (columnar files) for the batch layer (Chapter 34, Chapter 21)High-volume append-only writes, replayable, cheap per GB.
Aggregated query counts (query, window, count, unique users)Distributed files from the batch job, plus a wide-column or key-value store for the streaming counters (Chapter 20)Keyed increments and range reads by time window.
Serving index (prefix to top-K)In-memory trie in each serving process, loaded from an immutable snapshot file in object storageSingle-digit-microsecond lookups, no network hop, trivially replicated by copying a file.
User history (recent queries per user)Redis list or sorted set keyed by user id, or a wide-column store (Chapter 15)Small per-user data with fast reads.
Blocklist and rulesA small versioned config store pushed to all servicesRare writes, must be consistent and quickly deployable.

The central data structure is a trie, also called a prefix tree. It is a tree where each edge is a character and each path from the root spells a prefix. All strings sharing a prefix share the path. To find everything that starts with wea, you walk three edges from the root, and you are standing at the node that represents that prefix.

The naive approach then collects every query in the subtree under that node and sorts it by popularity. For a short prefix such as a, the subtree contains millions of queries, so this is far too slow. The fix, and the crux of this problem, is to precompute the top-K list at every node during the build. Each node stores the ids of its K best completions. A lookup is then: walk the prefix (length L steps), read the list stored at the node, translate ids into strings. Time is O(L) with L usually under 20, independent of how many queries exist. We trade extra memory (K ids per node, which is what the 12 GB figure paid for) for constant-time reads. The text-search chapter describes the trie and its relatives (Chapter 58), and the ranking structures that top-K lists resemble, such as sorted sets, are in Chapter 59.

The amber boxes are internal nodes and each stores its top completions, such as weather and walmart at w. 3. The green box at the bottom is the node for wea, which already holds weather, weather tomorrow, wear os and others. The note on the right gives the rule: lookup is walk L characters and read one list, with no subtree scan and no sort at request time. This is drawn this way because the alternative, collecting every query below the node and sorting, is far too slow for a short prefix like a with millions of descendants. The cost is extra memory for the lists, which is already included in the 16 GB figure. On a whiteboard, draw only one path and write the top list on each node. Remove the lists and every request becomes a big scan.

5.1 Making the trie small

  • Radix compression: merge chains of single-child nodes into one edge labeled with a string. This cuts node count by several times for real query sets and is why we assumed 150 million nodes for 100 million queries.
  • Ids instead of strings in the lists: top-K lists hold 4-byte ids into a shared query table. A popular query like "weather" appears in the lists of the nodes for w, we, wea, and so on, so storing it once is a big saving.
  • Scores stored once in the query table, quantized to 16 bits if needed.
  • Depth cap: do not store top-K lists below a depth where the subtree has at most K queries; just scan the leaf set. Also cap the indexed prefix length (for example 40 characters); longer prefixes seldom benefit from suggestions.
  • Flat array layout: serialize the trie as contiguous arrays with integer offsets, not millions of heap objects. This removes garbage-collection pauses (a real p99 killer in Java or Go services) and lets the snapshot be loaded with a memory map in seconds.

6. A first simple design

Start with something one person could build in a day, and then say what breaks.

A single server holds a trie in memory. At startup it reads a file of "query, count" pairs, builds the trie with top-K lists, and exposes GET /suggest. A nightly cron job aggregates the day's logs and writes a new file; the operator restarts the server to load it.

This works for a demo and fails in production in clear ways, which gives the roadmap for the rest of the page:

  1. One server cannot take 140,000 requests per second and is a single point of failure, so we need replication and sharding.
  2. Restarting to load a new trie causes downtime and cold starts, so we need atomic hot swap of immutable snapshots.
  3. A nightly build misses breaking news, so we need a streaming trending layer.
  4. Building a trie over 200 GB of logs per day on one machine is impossible, so we need a distributed pipeline.
  5. Round trips to a far-away server blow the latency budget, so we need caching at the client and the edge.
  6. Nothing stops offensive terms, so we need filtering.

7. Scaled architecture and request flows

The architecture has two halves that meet only at a published artifact. The serving path (online) answers keystrokes and never touches the logs. The build path (offline and near-real-time) turns logs into immutable trie snapshots. Keeping them separate is the most important structural decision: serving stays simple and fast, and a failure in the pipeline makes suggestions stale but never takes autocomplete down.

Walkthrough. The top band is the online path and the bottom band is the offline path. 1. The browser debounces keystrokes and checks its local cache. 2. A miss goes to the CDN edge, which holds short popular prefixes. 3. The gateway authenticates and rate-limits, then the suggest service picks a trie shard and reads the trending overlay and user history in parallel. In the bottom band, search and click events go to Kafka. A stream job produces the trending overlay every few minutes (the green dashed line), and a batch job counts and scores logs, the trie builder makes top-K snapshots and the snapshot store holds immutable versions that shards pull and swap in (the green line). The two halves meet only at the snapshot file, which is the design choice: a pipeline failure makes data stale and never breaks serving. Remove Kafka and the stream job and trends disappear.

7.1 Request flow: a keystroke

  1. The user types w, e, a. The browser waits for a short pause (debounce, section 10), normalizes the prefix, and checks its in-memory map of prefix to suggestions. A hit returns immediately with no network traffic.
  2. On a miss, the browser sends GET /v1/suggest?q=wea over an already-open HTTP/2 connection to the nearest edge location.
  3. The CDN edge looks up the URL as a cache key. For short, popular prefixes the answer is cached for 60 seconds. A hit returns in about 10 to 20 ms of network time. See Chapter 12.
  4. On an edge miss the request goes to the gateway, which authenticates (if a token is present), rate-limits per client (Chapter 16), and forwards to the suggest service.
  5. The suggest service picks the shard by the first characters of the prefix (section 8), and calls one replica. It reads the top-K ids and strings. In parallel, it fetches the small trending overlay that matches the prefix, and, for signed-in users, the user's recent queries.
  6. It merges the three sources, removes anything on the live blocklist, applies final ranking, truncates to 10, and returns the JSON with Cache-Control.
Walkthrough. The five lifelines are browser, CDN edge, suggest service, trie shard and the overlay plus history store. 1. The browser sends the GET after the debounce pause. 2a. If the edge has a cached answer, it returns within about 20 ms and nothing else happens. This is the common case. 2b. On a miss the edge forwards to the suggest service. 3. The service looks up the prefix on the right trie shard, found by bucket. 4. At the same time it calls the overlay and user history. 5 and 6. Both reply. 7. The service merges, filters the blocklist, ranks and cuts to 10. 8. The JSON goes back with Cache-Control, so the edge can store it. The reason steps 3 and 4 are parallel is that total time is the slower call, not the sum. On a whiteboard, draw 2a as a short loop to show most traffic never reaches the service. Without the edge, all 350,000 requests per second hit the tier.

7.2 Build flow: logs to a live trie

The build side follows the lambda-style pattern of Chapter 37: a slow, complete batch layer and a fast, approximate streaming layer, merged at read time.

  1. Collect. The search service writes one event per submitted query to Kafka, partitioned by a hash of the normalized query so that all events for the same query land in the same partition. Click events on suggestions go to a second topic.
  2. Normalize and filter. Lowercase, trim, NFKC-normalize, drop queries that are too long, contain URLs or email addresses or digit strings that look like card or phone numbers, and apply the blocklist (section 9). Bots and obviously automated traffic are dropped by a user-agent and rate heuristic.
  3. Count. A batch job (Spark or MapReduce style) reads the last N days from object storage and computes, for each normalized query, a weighted count: more recent days weigh more, using exponential decay (for example, half life of 7 days). It also computes unique-user counts so that one noisy user cannot promote a query (privacy threshold).
  4. Score. Final score is a blend: decayed frequency, click-through rate of the query when it was suggested, and a quality prior (language model or dictionary score) to demote junk.
  5. Build. The trie builder sorts the candidates, inserts them, computes the top-K list for each node bottom-up (a node's top-K is the merge of its children's top-K lists and its own entry, so no subtree scan is needed), radix-compresses, and writes a flat snapshot file per shard plus a manifest with a checksum and a version.
  6. Publish and swap. The snapshot goes to the snapshot store. Each serving process notices the new manifest, downloads its shard file in the background, loads it into a second memory region, runs a smoke test (a list of canary prefixes must return sane results, and the size must be within 20 percent of the previous version), and then atomically flips a pointer. The old version is kept until in-flight requests drain, then freed.
Walkthrough. The top row is the build: logs for the last 30 days, then count and score (about an hour), then build the trie (about 20 minutes), then snapshot v43 with a checksum. On the right, one shard process holds the live version v42 in red and the loading version v43 in green. The bottom row is what each shard does. 1. Download the new file in the background. 2. Verify the checksum, size and canary prefixes. 3. Flip one pointer atomically so new requests read v43. 4. Drain readers and free v42. If any check fails (the red box and dashed arrow), the shard keeps v42 and raises an alert. The design avoids restarting servers and avoids mutating a live structure. Rollback is the same flip in reverse while v42 is still in memory. Point at the dashed failure path when explaining safety. Remove the checks and one bad build serves bad suggestions to everyone.

8. Deep dive 1: serving tier, sharding and caching

The whole trie fits in 16 GB, so the first question is whether to shard at all. The honest answer: shard for throughput and isolation, not for capacity. There are three strategies; the table compares them.

StrategyHow it worksProsCons
Full replicas, no shardingEvery server holds the whole trie; a load balancer sprays requests.Simplest; any server answers any prefix; no routing; perfect failover.Each server needs 16 GB and every deploy loads 16 GB everywhere; per-server cache locality is poor; the trie cannot grow past one machine.
Shard by first character(s)Shard i owns a range of prefixes, for example a to f.Easy to reason about; range queries stay on one shard.Badly skewed: s and c are far busier than x or q, and in other languages the distribution differs wildly. Needs manual rebalancing.
Shard by hash of a short prefix (first 2 or 3 chars), with a mapping tableHash the first 2 characters into 4,096 virtual buckets and map buckets to 8 physical shards, balanced from measured traffic.Balanced load; rebalancing moves whole buckets; a lookup still needs only one shard because every prefix of length 2 or more lands in one bucket.Prefixes of length 1 span many buckets, so length-1 answers are served from a tiny separately replicated "root" table (just 26 or a few thousand entries).

We choose the third option: bucket by the first two characters, with a weighted bucket-to-shard map built from observed traffic, and a tiny global table for one-character prefixes. This is the standard consistent bucketing idea from Chapter 25 and Chapter 57, but because we control the map we can rebalance by measured QPS rather than by hash luck. A mapping table is small, so every suggest-service instance caches it.

The "hot prefix" problem is real. A trending term such as a big event name makes one bucket take 20 times its normal traffic. Mitigations stack: the CDN and browser caches absorb most repeats; each shard has 3 replicas and the suggest service chooses by least outstanding requests; and a bucket that stays hot can be given extra replicas independently of the others, since replicas of a bucket are just copies of the same snapshot file.

Walkthrough. Start at the left box, the suggest service, which holds the bucket map. 1. It takes the first two characters of the prefix: we hash to bucket 1,207 and sp to bucket 3,890. 2. A weighted table maps each bucket to one of the shards, shown as Shard 1 (heavy buckets), Shard 2 and Shard 8 (many light buckets), each with 3 replicas. 3. A one-character prefix such as s is answered from a small replicated root table, so every lookup touches exactly one shard. The right panel gives the per-shard facts: about 17,500 QPS at peak, about 6,000 per replica, and a hot bucket gets more replicas instead of a re-shard. The design avoids sharding by first letter, which is badly skewed, and avoids plain hashing, which cannot be tuned. Draw the three-step mapping on the whiteboard. Remove the map and you lose the ability to move load.

8.1 Caching layers and the latency budget

Caching is applied at four levels, each with a different job (Chapter 13).

LayerKeyTTLExpected hit rateNotes
Browser memorynormalized prefixsession, plus HTTP max-age20 to 30 percent (backspacing and retyping, repeated prefixes)Free, and removes the network entirely.
CDN edgeURL with normalized prefix and language60 sabout 50 percent of what reaches itCombined with browser, about 60 percent of all requests never reach us (our estimation assumption).

Trie itselfn/auntil next snapshotn/aThe authoritative in-memory structure; a lookup is microseconds.

The edge TTL is the knob that trades freshness for load. A 60 second TTL means trending changes appear at most about a minute late at the edge, which is within our 5 to 15 minute freshness goal. Cache key hygiene matters: if the key includes a session id or timestamp, the hit rate collapses to zero. Personalized responses use Cache-Control: private or are fetched via a separate call so they never poison the shared cache. See Chapter 14 for stampedes and cache penetration; for autocomplete, the dangerous one is a newly viral prefix that misses everywhere at once, which request collapsing handles.

The sum is 77 ms, which leaves about 23 ms of slack in the 100 ms target. The note below says an edge hit is about 20 ms and a browser hit is zero network time. The number to remember is that server work is only about 15 ms, so network and caching dominate. On a whiteboard, draw bars proportional to size. If you remove the CDN, the first two bars appear on every request.

Tail latency tactics: hedged requests (if a replica has not answered by the p95 latency, send the same request to another replica and take the first answer), a hard timeout of 40 ms on the shard call after which we return the trending-and-cache fallback, and pre-warming a freshly loaded snapshot by touching the pages of the hot prefixes before it takes traffic. The general approach to tail latency is covered in Chapter 40.

9. Deep dive 2: the data pipeline, freshness, filtering and typos

9.1 Batch versus streaming, and the merge

A daily batch alone gives stable, high-quality ranking but is up to a day stale. Streaming alone is fresh but noisy and expensive to run for the whole long tail. We use both, in the lambda style of Chapter 37, with the streaming part kept deliberately small.

OptionFreshnessCost and complexityQualityVerdict
Batch only, daily rebuildup to 24 hLowestHigh, stableMisses breaking news; not acceptable alone.

The trending overlay works as follows. A stream job (Flink or Kafka Streams, see Chapter 34) counts queries in tumbling or sliding 5 minute windows, keyed by normalized query. For each query it compares the recent rate with its baseline rate (taken from the batch aggregate): the ratio, or a z-score, tells how unusual the current volume is. Only queries that pass all of these gates enter the overlay: a minimum absolute count, a burst ratio above, say, 5 times baseline, a minimum number of distinct users and distinct IP prefixes (so a single bot cannot manufacture a trend), and the blocklist. The overlay is a few thousand entries, not hundreds of millions, held as a small in-memory trie or map on each suggest-service instance and refreshed every minute or two. At query time, overlay entries matching the prefix are merged with the trie's top-K list and given a boost that decays over a few hours. Counting heavy hitters in a stream with bounded memory is a classic use for Count-Min Sketch and Space-Saving (Chapter 57), which let the stream job track the top candidates without a counter per distinct query.

9.2 Ranking details

Pure frequency ranks old, uniformly popular queries first and buries the newly relevant. A practical score for a candidate q at time t is: score = w1 * decayed_count + w2 * CTR_when_suggested + w3 * trend_boost + w4 * quality_prior. The decay uses a half-life; CTR comes from the impression and click beacons, and corrects for position bias; the quality prior comes from language models or dictionary checks so that gibberish and one-off typos do not surface. A clean explanation of why we compute this offline: the weights can be tuned by experiments (A/B testing click-through), and the serving path only reads a precomputed score. Because the weights live in the pipeline, changing the formula needs a rebuild, not a code deploy of the serving tier.

9.3 Filtering offensive and sensitive suggestions

Autocomplete is uniquely dangerous because the system appears to endorse what it shows. Defense is layered:

  • At learning time: normalized queries that match a blocklist (exact, normalized for leetspeak and spacing, and pattern-based), a toxicity classifier above a threshold, or a PII detector (emails, phone numbers, national id formats, card numbers via Luhn check) never enter the candidate set.
  • At build time: a second pass over the final top-K lists, since a query that is fine alone might become offensive combined with a prefix.
  • At serve time: a live blocklist, pushed through the config channel within a minute, is applied in the merge step. This is the emergency brake: a bad suggestion discovered at 3 pm must disappear at 3:01 pm, not at the next trie build. The CDN cache is purged for affected prefixes using a targeted invalidation, which is why the TTL is also kept short.
  • Privacy threshold: a query must be searched by at least N distinct users (for example 50) before it can be suggested, so one person's rare, possibly sensitive search cannot be revealed to others.
  • Manual and legal overrides: a small human-curated override list to remove or pin entries (for example, legal takedowns), applied at the same live layer. Also consider regional policy: the blocklist is per locale.

Anti-abuse matters too: coordinated groups can try to manufacture a trend ("search poisoning") by flooding a phrase. Defenses are distinct-user and distinct-network gates, per-user count caps per window (one user contributes at most a small number of counts per query per hour), and anomaly detection that sends suspicious spikes to a review queue before they reach the overlay. See Chapter 55.

9.4 Typo tolerance

A trie does exact prefix matching; wheather reaches no node at all. Options:

9.5 Multi-language

  • Separate tries per language and locale group (English US, English UK share a base with locale overlays; Hindi, Japanese, and so on separate). The client sends the UI language and the keyboard or input-method hint; the service routes accordingly. Mixed-language users can request two tries and merge.
  • Normalization: Unicode NFKC, case folding, accent folding as an option (cafe matches café), full-width to half-width mapping for Japanese and Chinese.
  • Trie alphabet: use Unicode code points (or bytes of UTF-8) as edge labels, with radix compression absorbing the wide alphabet. A raw array of children per node would waste memory; use sorted small arrays or hash maps for sparse nodes.
  • Scripts without spaces (Chinese, Japanese, Thai) need word segmentation for ranking but not for prefix lookup: the prefix is still just characters. For Chinese and Japanese, input-method composition (pinyin, romaji) generates intermediate text that should not trigger requests; the client waits for composition end events.
  • Right-to-left scripts: prefix semantics are by logical order, not visual order, and the stored strings are logical order. Nothing special is needed server side.
  • Transliteration: users type "namaste" for a Hindi query; build alias entries from romanized forms in the logs.

10. Deep dive 3: the client, debounce and personalization

10.1 Debounce, cancel, and local cache

The cheapest request is the one never sent. A user typing at 5 characters per second would trigger 5 requests per second per user without any control. Debounce means: restart a short timer (about 100 to 150 ms) on every keystroke and only send when the timer fires, i.e., when the user pauses. It is better than throttling for this case because it skips the intermediate prefixes the user typed past. Many implementations combine both: send immediately for the first character after a longer pause (feels instant), then debounce the rest.

Three more client rules matter:

  • Cancel stale requests. If the user typed wea and then weat, the response for wea may arrive after the one for weat. Each request carries a monotonically increasing sequence number; the client ignores any response older than the latest rendered one, and aborts in-flight requests when a newer one is sent.
  • Local prefix cache. Keep a map from prefix to results. If the cache has results for wea and the user types weat, the client can immediately filter the cached list by the new prefix while the real request is in flight (only valid when the cached list was complete, that is, fewer than K results, or as a temporary display).
  • Minimum length and idle fallback. Do not call the server for an empty box (show recent searches locally) or optionally require 1 to 2 characters; stop sending after a long prefix returns no suggestions, because a longer prefix cannot have more matches (a "dead prefix" optimization: remember that weatherxx is empty and skip calls for anything that extends it).

With debounce, a 20 character query produces about 6 requests rather than 20, which is the number our estimation assumed. A mobile client adds one more rule: on a poor connection, rely on local history and cached results, and consider a lighter payload (see Chapter 56).

10.2 Personalization

Personalization seems to conflict with the shared trie: a trie per user is impossible. The solution is layering, as in figure 6.

  1. Global base from the shared trie (cacheable, same for everyone in the locale).
  2. Recent history: the last 50 to 100 queries per signed-in user, stored in Redis (Chapter 15) as a list, or on the device itself (best for privacy and zero latency). On each request the service finds history entries starting with the prefix (a simple scan over 100 strings) and boosts them above generic suggestions, flagged so the UI can show a history icon.
  3. Segment-level personalization: instead of per-user tries, build a few dozen tries or overlays per segment (language, region, device, topical interest cluster). Cheap, still cacheable per segment.
  4. Contextual signals: time of day, location (nearby results), and the previous query in the session, applied as small score adjustments in the merge step.

Cacheability is the tension. A personalized response cannot be shared in the CDN, so the design splits the response: the global part is fetched from the cache-friendly endpoint, and the personal part is fetched separately (or computed on the client from local history) and merged in the browser. This keeps 95 percent of the work cacheable. Privacy rules apply: history respects the user's setting to pause or delete it, is excluded from the shared logs unless the user consents, and is deleted on account deletion (Chapter 56).

11. Alternatives: Elasticsearch and Redis sorted sets

An interviewer may ask, "Why build a custom trie service when Elasticsearch or Redis already exist?" The honest answer is that those are credible for smaller systems, and the tradeoffs are the heart of the question.

11.1 Redis sorted sets

Store one sorted set per prefix: key sugg:wea, members are full queries, score is popularity. A lookup is ZREVRANGE sugg:wea 0 9, an O(log N + 10) operation in memory. To build, for each query in the aggregate and for each of its prefixes, ZADD into that prefix key and trim to the top 10 with ZREMRANGEBYRANK. A streaming update is simply ZINCRBY on the score for each prefix. Sorted sets are described in Chapter 59 and Redis operations in Chapter 15.

It is in effect a trie flattened into a hash table: the prefix is the key, and the top-K list is the value. Cost: each query of length 20 is written under 20 keys, so 100 million queries means up to 2 billion member writes, and memory is large: each sorted-set entry is on the order of 50 to 100 bytes with overhead, so tens of GB to over 100 GB if you keep more than K members per key, though trimming every key to the top 10 keeps about 150 million keys times about 10 members. Rough memory: 150 million keys at about 100 bytes of key and structure overhead plus 10 entries at about 40 bytes is about 75 GB, versus our 16 GB trie. Strengths: trivial to build, real-time increments, Redis Cluster shards by key with no custom code. Weaknesses: memory heavy (about 5 times the trie), trimming loses information (a query that drops out of one prefix list cannot come back without recomputation), no atomic whole-index swap (you would write a new key namespace and switch a version prefix, which doubles memory during the switch), and per-update write amplification equal to the query length.

11.2 Elasticsearch

Index each candidate as a document with a field using an edge_ngram analyzer (indexing "w", "we", "wea", ...), or use the completion suggester (backed by an in-memory finite state transducer) or search_as_you_type. Rank by a numeric popularity field via function score. Fuzzy matching is built in. See Chapter 22.

Strengths: typo tolerance and multi-field matching for free, rich filtering (by category, language, locale) and operational tooling. Weaknesses: query latency is usually 5 to 30 ms at p50 and spikes under load, versus microseconds for the trie, and serving 140,000 QPS needs a large cluster; ranking per request by scoring is more expensive than reading a precomputed list; index updates are near-real-time (refresh interval typically 1 second) but heavy merging under constant updates hurts latency.

12. Scaling, hot spots and failure modes

12.1 Scaling

  • Read scaling: add replicas per shard; edge caching grows with traffic for free. The trie is read-only so no coordination is needed.
  • Data growth: raise the frequency threshold, raise the privacy threshold, or cap the prefix depth. Moving from 100 million to 400 million candidates grows memory to about 64 GB per full trie, which is when shard-by-bucket actually becomes necessary for size.
  • Build scaling: the batch job partitions by query hash; the trie builder partitions by bucket, so 8 shard files build in parallel. A hourly full build of about 20 to 30 minutes is realistic.
  • Geography: serve from each region with a local replica set pulling the same snapshot, so the network leg is short. Snapshots are small (16 GB) and are copied region to region via object-store replication (Chapter 26).

Consistency and idempotency: the system tolerates duplicates and reorderings because counts are approximate, but the build is made deterministic: the same input logs and the same config produce the same snapshot, and snapshot versions are immutable and monotonic, so every swap is idempotent (Chapter 32). Different replicas may briefly serve different versions during a rollout, which is fine for this product. For multi-region, each region builds nothing locally; one pipeline builds, replicas pull, and a region that cannot reach the store keeps its current snapshot.

13. Security, abuse, monitoring and cost

13.1 Security and abuse

  • Rate limit per client and per IP at the gateway; autocomplete is cheap per request but easy to scrape for harvesting what people search for. Cap response detail (no scores in public responses if scraping is a concern).
  • Never reflect the prefix unescaped into HTML on the client: render with text nodes, since the suggestions and prefix are untrusted (cross-site scripting).
  • Privacy: queries are anonymized in the pipeline (user id replaced by a rotating pseudonymous bucket), IP addresses truncated, and sensitive categories excluded (Chapter 55).

13.3 Cost

The cost drivers, in order: the edge and egress (175 MB/s peak at the edge, mostly cache hits, which are cheaper than origin egress), the batch and stream compute (about 200 GB a day of logs; a modest cluster for an hour or two per build), and the 24 serving instances with 16 GB-class memory (small). Log storage at 6 TB for 30 days is small. The biggest cost lever is the cache hit rate: every extra 10 points of hit rate removes about 35,000 requests per second from the origin. Second, prune the candidate set aggressively; most of the 300 million daily distinct queries are noise.

14. Evolution, phasing and alternatives not chosen

14.1 What to build first

  1. Phase 1 (weeks): daily batch job, one trie service with 2 replicas, edge caching, client debounce, blocklist. Covers the core product.
  2. Phase 2: hourly builds, snapshot swap with validation and rollback, sharding by bucket, hedging, per-locale tries.
  3. Phase 3: streaming trending overlay, personalization from history, click-through-based ranking.
  4. Phase 4: typo tolerance, transliteration, segment overlays, ML ranking model, multi-region.

14.2 At 10x scale

Traffic of 3.5 million requests per second at the edge needs a larger cache tier but the same architecture; the serving tier is about 240 instances. Candidates may grow to a billion, so memory rises to about 160 GB for a full index, and size-driven sharding becomes mandatory; the bucket map scales to 64 shards. Build time grows, so builds become incremental: only buckets whose counts changed meaningfully are rebuilt, and unchanged shard files are reused. A learned ranker (a small model scoring candidates using context features) replaces the linear score, running on the top 50 candidates from the trie instead of the top 10.

14.3 Alternatives not chosen

  • Neural query generation (a language model generating completions). Strong for rare queries and long text, but too slow and expensive per keystroke at this scale and risky for offensive output; used as a candidate generator offline to enrich the trie, not on the hot path.
  • Ternary search tree or finite state transducer instead of a trie: a finite state transducer (as in Lucene) is more compact still and supports weights, a good choice if memory is the main concern, but top-K per node is awkward to retrofit.
  • Computing top-K on demand with a heap over the subtree with caching: acceptable for small data, but a request for a touches millions of nodes, and the tail latency is unbounded.
  • Fully streaming index, no snapshots: fresher, but loses reproducibility, rollback and simple validation.

15. Interview Q&A

Why precompute the top-K list at every node instead of computing it at query time?

Without it, a lookup for a short prefix must walk the whole subtree below the node, which can contain millions of queries, and then sort them, so latency depends on the data size and is unbounded for the most common requests (the short prefixes). With precomputed lists the lookup is O(L) for prefix length L and returns a stored list, a few microseconds regardless of data volume. The cost is memory (K ids per node, about 12 GB here) and build time, and both are paid offline where they are cheap. Building the lists is also efficient: each node's list is the merge of its children's lists, computed bottom-up in one pass.

How do you update the trie without downtime and without serving a half-built structure?

Snapshots are immutable and versioned. The builder writes a complete new file; each shard downloads it in the background, verifies the checksum and sanity (size delta against the previous version, canary prefixes returning expected results), loads it into a second memory region, and flips one atomic pointer. Requests that started on the old version finish on it, and then it is freed. Rollback is flipping the pointer back while the old version is still resident. Because we never mutate the live structure, there are no locks on the read path and no intermediate states.

How do you surface a breaking-news query within minutes if the trie is rebuilt hourly?

A stream job counts queries in 5 minute windows and compares to baseline rates, and promotes only queries with an unusual burst ratio, a minimum count, and enough distinct users and networks. They go into a small trending overlay (thousands of entries) that every suggest-service instance reloads every minute or two and merges with the trie result using a decaying boost. The base trie stays immutable and stable. The overlay is small enough to keep in memory everywhere, and since it expires by TTL, a stream outage leaves suggestions stale but never wrong in a dangerous way.

How do you prevent offensive or private suggestions, and what do you do when one slips through?

Defense is layered: filtering at learning time (blocklists, toxicity classifier, PII detectors), a privacy threshold of distinct users before any query is eligible, a second pass on the final top-K lists at build time, and a live blocklist applied in the merge step at serve time. When a bad suggestion is reported, the on-call adds it to the live blocklist, which propagates in under two minutes, and purges the matching CDN keys. It is also removed from the learning set so the next build does not reintroduce it. The post-incident step is to find why classifiers missed it and expand rules; the key point is that the emergency brake does not wait for a rebuild.

Why shard by prefix bucket and not just replicate the whole trie everywhere?

At 16 GB the trie does fit on one machine, so replication is a valid start. Sharding wins for operational reasons: smaller snapshot files load and swap faster, a hot bucket gets extra replicas without copying the entire index, a bad shard has a smaller blast radius, and a growth in candidates does not force a hardware change. I avoid splitting by the first character because letter frequency is highly skewed and varies by language; instead I hash the first two characters into thousands of virtual buckets and assign buckets to shards using measured traffic, so rebalancing moves buckets, not data models. One-character prefixes are served from a tiny replicated root table, so a request never fans out to multiple shards.

How does the client decide when to call the server, and how do you handle out-of-order responses?

The client debounces: it restarts a 100 to 150 ms timer on each keystroke and sends only when typing pauses, so the intermediate prefixes are skipped and a 20 character query makes about 6 requests instead of 20. Every request carries an increasing sequence number and the client discards any response with a lower number than the last rendered, aborting older in-flight requests. It also keeps a prefix-to-results map for instant answers on backspace or retyping and remembers dead prefixes (those with no results), skipping calls for any extension of them.

How would you add personalization without making responses uncacheable?

Split the response. The global part (top-10 from the shared trie plus trending) stays cacheable at the browser and CDN and is the same for everyone in a locale. The personal part, the user's recent queries matching the prefix, is read from the device or from a small per-user store and merged on the client or in the aggregation step, with a boost and a history marker. For deeper personalization, use a limited number of segment overlays (language, region, interest cluster), which are also cacheable per segment. A trie per user is never viable: millions of copies of mostly the same data.

Redis sorted sets look simpler. Why not use them?

They are a good first version and I would ship them for a smaller product. The reasons to move on are cost and operations at our scale: writing each query under every one of its prefixes multiplies writes by the query length, and the memory is about five times that of a compact trie (roughly 75 GB versus 16 GB by my estimate). Trimming each key to the top 10 discards information, so an item that falls out of a list cannot return without recomputation, and there is no clean atomic swap or rollback of the whole index. Their strengths remain real-time increments and trivial sharding, which is why I would keep Redis for the user history and possibly the trending overlay.

How do you support typos without making every lookup slow?

The hot path stays an exact trie lookup. When it returns fewer than a few results, we fall back, with a strict time budget, to a corrected prefix. The cheapest fallback is a table of learned aliases mined from sessions where users search a misspelling and then the corrected phrase; it costs nothing at serve time. Next comes a bounded edit-distance walk (one edit, prefix at least 3 to 4 characters). Only if both fail do we consult Elasticsearch with fuzziness. Because most keystrokes find exact matches, the extra cost applies to a small fraction of requests.

What do you do during the first few seconds after a snapshot swap, when caches are cold?

We avoid cold starts by pre-warming: after loading and before the flip, the process touches the memory pages for the most frequent prefixes (we know them from the logs), so the first real request does not take page faults. Swaps are staggered across replicas with jitter so that not all replicas change at once, and the CDN and local caches continue to serve the older answers until their TTL expires, which smooths the transition. If error or latency rises on the canary replica, the rollout stops and rolls back automatically.

Recap

  • The core structure is a trie with the top-K completions precomputed at every node, so serving is an O(prefix length) walk and a list read; it takes about 16 GB for 100 million candidate queries.
  • Traffic estimate: 2 billion searches a day, about 12 billion requests, 139,000 QPS average, 350,000 peak at the edge, about 140,000 after caching; 8 shards by 3 replicas is enough with headroom.
  • Separate serving from building: immutable snapshots built by a log-driven batch pipeline, swapped atomically per shard with validation and instant rollback.
  • Freshness comes from a small streaming trending overlay with burst, volume and distinct-user gates, merged at request time with a decaying boost.
  • Latency is mostly network: browser cache, debounce, CDN edge, warm HTTP/2 connections, hedged requests and short timeouts matter more than the lookup itself; the miss path totals about 77 ms of the 100 ms budget.
  • Shard by hashed two-character prefix buckets mapped to shards by measured load; one-character prefixes come from a tiny root table.
  • Safety is layered: learning-time filters, privacy thresholds, a build-time pass and a live serve-time blocklist for emergencies.
  • Typos use learned aliases first, bounded edit distance second, fuzzy search as last resort; languages get separate tries with Unicode normalization.
  • Personalization is a merge layer on top of a cacheable global result; Redis sorted sets and Elasticsearch are valid for smaller scale or for fuzzy fallback, but cost more memory or latency than the custom trie at this scale.
