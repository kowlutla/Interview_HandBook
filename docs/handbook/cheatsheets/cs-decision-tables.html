Cheat Sheet: Decision Tables

Ten decisions that come up in almost every design interview, each as a table of "choose when" and "avoid when", with a link to the chapter that explains the reasoning. Use these to pick a defensible default fast, then state the tradeoff out loud. Every answer is a default, not a law: an interviewer wants to hear the condition that would flip your choice. Numbers to size these choices are on Numbers to Remember.

2. Which cache strategy

Owners: Chapter 13 (patterns), Chapter 14 (failure modes), Chapter 12 (edge caching).

StrategyHow it behavesChoose whenAvoid whenChapter
Cache-aside (lazy loading)app checks cache, on miss reads the DB and fills the cacheread-heavy, tolerate brief staleness, default choicecold-start misses are unaffordable; writes must be instantly visible13
Read-throughcache itself loads from the DB on a missyou want one access path and a library or service that supports ityou need custom miss logic per call site13
Write-throughwrite goes to cache and DB together, synchronouslyread-after-write must hit cache, data is read soon after being writtenwrite-heavy data that is rarely read (wastes cache); write latency is critical13
Write-back (write-behind)write to cache, flush to DB latervery high write rates, counters, tolerate small loss windowdata loss is unacceptable (cache crash loses unflushed writes)13
Write-aroundwrite straight to DB, skip the cachedata written once and rarely readreads follow writes immediately13
CDN / edge cachecopies at points of presence near usersstatic or cacheable content shared by many users, global audienceper-user private data, fast-changing content without versioned URLs12
Local in-process cachecache inside each app instancetiny hot data set, tolerant of per-instance stalenessyou need cross-instance invalidation or a big data set14

Protect the cache. Use TTLs with random jitter against avalanche, request coalescing against stampede, negative caching or Bloom filters against penetration (all in Chapter 14). Eviction defaults to LRU; Redis specifics are in Chapter 15.

3. Which queue or stream

Owners: Chapter 34, Chapter 35, Chapter 36, Chapter 37.

OptionChoose whenAvoid whenChapter
Log / stream (Kafka, Kinesis, Pulsar)very high throughput, replay needed, many independent consumer groups, event sourcing, per-key orderingyou need per-message delays, priorities, or complex routing; tiny scale where ops cost dominates34
Task queue (SQS, RabbitMQ work queue)background jobs, competing consumers, per-message acknowledgment, retries and DLQ, delayreplaying history or many consumers reading the same data independently34, 35
Pub/sub topic (SNS, Redis pub/sub)broadcast notification to many subscribers, fire-and-forgetdelivery must be guaranteed to offline subscribers35
Stream processor (Flink, Spark Streaming)windowed aggregations, joins over streams, continuous resultssimple per-message work a consumer can do37
Workflow engine (Temporal, Step Functions)long-running multi-step processes with timers and retriesone-shot jobs38
Change data capture + outboxpublish DB changes reliably without dual writesdata is not in a database first36, 31

Rule of thumb: if consumers must be able to rewind, use a log; if each message is a job to complete once, use a queue. Whatever you pick, consumers must be idempotent because delivery is at-least-once (Chapter 32).

4. Which consistency level

Owners: Chapter 28 (models), Chapter 24 (quorums), Chapter 29.

LevelGuaranteeChoose whenAvoid whenChapter
Linearizable (strong)every read sees the latest committed write, as if one copymoney, inventory, unique usernames, leader election, locksyou need low latency across regions or must stay available during partitions28, 29
Sequential / causaloperations that depend on each other appear in ordercomments and replies, chat threads, collaborative appsyou actually need a global real-time order28
Read-your-writes / sessiona user sees their own updates and does not go backwardprofile edits, posting then viewing, most user-facing appsreaders must see other users' writes instantly28
Eventualreplicas converge if writes stopfeeds, likes, counters, analytics, caches, DNScorrectness depends on the latest value28
Quorum tunable (R + W > N)reads overlap the latest write setleaderless stores where per-request tradeoffs are neededyou expect it to give full linearizability by itself24

Decide per feature, not per system: checkout can be linearizable while the recommendation panel is eventual. During a partition (CAP), the choice is consistency or availability; otherwise (PACELC) it is latency versus consistency.

5. Which replication and sharding approach

Owners: Chapter 24 (replication), Chapter 25 (sharding), Chapter 26 (multi-region).

ApproachChoose whenAvoid whenChapter
Single leader, async followersread scaling, simple failover, most OLTP systemsyou cannot tolerate lost writes on failover or stale follower reads24
Synchronous / semi-synchronous replicano acknowledged write may be lost, replicas are closereplicas are far away (latency) or numerous24
Multi-leaderwrites must be accepted in several regions or offlineconflicts are expensive to resolve24, 26
Leaderless quorumhigh availability, tunable consistencyyou need transactions or strict ordering24
Hash sharding (consistent hashing)even spread, key lookups, unknown growthyou need efficient range queries on the key25, 57
Range shardingrange scans, time-ordered or sorted accesskeys are monotonic (newest range becomes a hot spot)25
Directory / lookup shardingtenants of uneven size, need manual placementthe lookup service would be a bottleneck or single point of failure25, 42

Pick a shard key with high cardinality, even access, and the one you query by most; cross-shard queries and transactions are the cost you accept (Chapter 31).

Algorithm defaults: round robin for uniform stateless requests, least connections for variable-duration requests, consistent hashing when you want cache or session affinity. Always pair with health checks, and make the LB itself redundant.

8. Sync versus async

Owners: Chapter 47, Chapter 35, Chapter 48.

StyleChoose whenAvoid whenChapter
Synchronous call (request-response)the caller needs the answer now to continue; user is waiting; simple flowsthe callee is slow or unreliable, long chains of calls, or fan-out to many services47
Asynchronous via queue or eventswork can finish later (email, thumbnails, indexing); you need to absorb bursts, decouple teams, retry safelyuser needs an immediate result; debugging and ordering complexity is not worth it35, 36
Async API with job id (202 Accepted + polling or webhook)long operations exposed to external clientssub-second operations5
Saga across servicesa multi-service business transaction without 2PCone database can do it atomically48, 31

Rule: keep the critical user path short and synchronous, push everything that can wait onto a queue, and make each async step idempotent.

10. Monolith versus microservices

Owners: Chapter 44, Chapter 39, Chapter 45, Chapter 46, Chapter 53.

StyleChoose whenAvoid whenChapter
Monolith (single deployable)small team, early product, unclear boundaries, you want simple deploys and transactionsmany teams blocked on one release train; parts need very different scaling44
Modular monolithwant clean boundaries and one deployable; a safe stepping stonemodules share tables freely and boundaries are not enforced39
Microservicesmultiple teams, independent deploy cadence, distinct scaling or reliability needs, clear bounded contextssmall team, unstable domain boundaries, no platform or observability maturity (risk: a distributed monolith)44, 45
Serverless functionsspiky or low-volume event-driven work, minimal opssteady high load, long-running work, strict latency (cold starts)39
Strangler fig migrationmoving an existing monolith piece by piecea rewrite is small enough to do at once44

Microservices cost: network failure modes, data split across services (Chapter 46), distributed transactions (Chapter 48), and observability (Chapter 52). Default to a modular monolith and split along data ownership when a real pain appears.

Watch out A table gives a default, not a verdict. State the deciding assumption ("assuming under 5k writes per second, one primary is enough") so the interviewer can redirect you if the assumption is wrong. Also resist adding every component: each extra box needs a number that justifies it (Numbers to Remember).

11. Recap

  • Database: relational by default; leave it for scale, shape, or latency reasons, and add derived stores (search, cache, warehouse) rather than replacing the source of truth.
  • Cache: cache-aside by default; write-through for read-after-write; write-back only when small loss is acceptable.
  • Queue versus log: jobs go to queues, replayable event streams go to logs; make consumers idempotent.
  • Consistency is chosen per feature: strong for money and uniqueness, session guarantees for users, eventual for the rest.
  • Shard last, with a high-cardinality key; use hash for even load and range for scans.
  • IDs: Snowflake or ULID for sortable scale, UUID v4 for coordination-free, auto-increment for small systems.
  • Use DNS for regions, L4 for speed, L7 for routing; keep user paths synchronous and short, everything else async.
  • REST outside, gRPC inside, GraphQL for diverse clients; modular monolith until teams and boundaries justify services.
