Data Management in Microservices

Splitting code into services is the easy half of microservices. The hard half is splitting the data: once each service owns its own database, you lose joins, foreign keys and multi-table transactions, and you must replace them with API calls, events, copies and reconciliation. This chapter explains how to do that deliberately, and what breaks when you do it badly.

1. Database per service: the principle and why

In a monolith, one application talks to one relational database. Any piece of code can join orders to customers to products, and one transaction can update all three tables atomically. This is enormously convenient, and Chapter 18 explains why relational databases are so good at it. When a team splits the monolith into services (the decomposition techniques are in Chapter 45), the first temptation is to keep the single database and let every service connect to it. That keeps the convenience, but it quietly keeps the monolith too.

The database-per-service principle says: each service owns its data, and the only way to read or change that data is through the service's own interface (an API or events it publishes). No other service may connect to its database, read its tables, or write to them. The database becomes a private implementation detail, like the private fields of a class.

1.1 Why this is worth the pain

There are three main benefits, and each one is the reason microservices exist at all.

  • Autonomy. A team can deploy, scale, and operate its service without coordinating with others. If the orders service needs a bigger database, or a maintenance window, or a failover, only orders is affected. With a shared database, one team's heavy report query or runaway lock can slow every other service, and a database upgrade needs everyone to agree on a date.
  • Encapsulation. The service decides what is a valid state of its data and enforces those invariants in one place. If five services can write to the orders table, then "an order total must equal the sum of its lines" is enforced by five codebases, and sooner or later one forgets. A private database means one gatekeeper.
  • Independent schema evolution. Renaming a column, splitting a table, or changing a type is a local change when only one service reads the table. With a shared schema every column is a public API with unknown consumers, so nobody dares to change anything, and the schema ossifies. The service can instead keep its public contract (the API or event format) stable while freely reshaping its private storage.

A fourth benefit follows: each service can choose the storage technology that suits it (section 4), and each can be scaled, backed up, and secured separately (section 15).

Key idea The unit of ownership is not the table, it is the data and its invariants. "Database per service" really means "single owner per piece of data, with a published contract". Whether that owner uses a separate server, a separate schema, or a separate cluster is an operational choice (section 3); the rule that nobody else touches the tables is what delivers the benefits.

1.2 What you give up

Be honest about the cost, because interviewers will probe it. Without a shared database you lose: joins across service boundaries, foreign key constraints between them, and atomic transactions that span them. Every cross-service read becomes a network call or a locally kept copy, and every cross-service write becomes a distributed process that can half-finish. The rest of this chapter is the toolbox for living with those losses.

2. Shared database: tradeoffs and when it is tolerable

A shared database means several services read and write the same tables. It is the default in the first months of a split, and it is sometimes the right answer. Understanding exactly what it costs lets you decide when to accept it.

2.1 The specific damage a shared database does

Hidden coupling. Suppose the orders service adds a nullable column and the shipping service reads SELECT * from the same table. The shipping code now behaves differently, and nobody noticed because no API changed. The schema is an undeclared, unversioned API.

Performance interference. One service runs a large analytical scan; the buffer cache is flushed and the checkout service's queries slow down. Connection pools are shared, so one service leaking connections starves the rest. Lock waits propagate: a long transaction in one service blocks writes by another.

Blast radius. A bad migration, a full disk, or a failed primary takes every service down together. You have built a distributed system that fails like a monolith, which is the worst of both worlds.

Scaling limits. The single database is a shared bottleneck. Vertical scaling eventually runs out, and sharding it (Chapter 25) is much harder when every service has different access patterns on the same tables.

2.2 When it is tolerable

  • Transitional state. During migration from a monolith (section 14) you will run with a shared database for a while. Treat it as scaffolding with a removal date.
  • Very small teams and few services. If one team owns three services and deploys them together, strict separation costs more than it gives. A "modular monolith" with a single database and strict module boundaries inside the code is often the better design.
  • Read-only shared reference tables that change almost never (country codes, currencies), where every service is a pure reader and one team owns writes. Even here, a published library or a replicated copy is usually better.
  • Reporting replicas. Services do not share the operational database, but an analytics tool reads a replica or warehouse copy. That is reading a copy, not sharing the live schema (section 16).
Watch out A shared database where each service uses only its own tables (no cross-reads) is much safer than free-for-all sharing, and is the cheap first step toward separation. It still shares a failure domain and resources, so it only fixes the logical coupling, not the operational coupling.

3. Schema per service versus separate instances

"Own database" can mean several physical things. They form a spectrum from cheap and weakly isolated to expensive and strongly isolated.

3.1 Schema per service in one cluster

In PostgreSQL or MySQL you can create one schema (or database) per service inside a single cluster and give each service its own database user, granted rights only on its own schema. This is a pragmatic compromise: you pay for one cluster, one backup procedure, one monitoring setup, yet the database itself rejects any cross-schema query from the wrong user. The rule becomes enforceable rather than a gentleman's agreement. The weaknesses are shared resources (CPU, I/O, connection limit, the write-ahead log) and a shared failover, so a noisy service still hurts its neighbours, and a cluster outage takes everyone down.

3.2 Separate instances

Separate instances (separate servers, or separate managed database instances in a cloud) give true fault isolation, independent scaling and tuning, independent upgrade timing, and per-service backup and restore. The costs are real: more machines to pay for (many small, underused databases), more things to patch and monitor, and many more connection endpoints. Teams usually move a service to its own instance when it has a heavy or spiky load, different compliance needs (for example payment card data), a different engine, or when its availability target differs from its neighbours.

3.3 How to choose

A sensible default: begin with a schema per service and a dedicated database user per service, with permissions that make cross-schema reads impossible. Promote a service to its own instance when you can point to a reason: measured interference, a stricter recovery objective, a regulatory boundary, or a need for a different engine. Whichever you choose, treat connection strings as private. If another team's code ever holds your credentials, you have a shared database again.

4. Polyglot persistence

Polyglot persistence means each service uses the database technology that fits its own access patterns, instead of forcing everything into one engine. This is only practical because services own their data privately: nobody else cares which engine you chose, as long as the API is stable. 5. Cross-service queries: the join problem

The user opens an orders page that shows each order with the customer's name, the product titles and images, and the payment status. In the monolith this was one query with three joins. Now four services own that information. There are three families of solutions: compose at read time (call the services and merge), precompute a read model (listen to events and build a ready-made view), and keep a local copy of the little data you need (reference data replication). The remainder of this section covers the first; sections 6 to 8 cover the others.

5.1 API composition

API composition means a component (an API gateway, a backend-for-frontend, or a dedicated aggregator service) receives the request, calls each owning service, and merges the answers in memory. See Chapter 11 for the gateway itself and Chapter 47 for the call mechanics.

5.2 Latency and partial failure

The total latency is the sum of sequential steps plus the slowest of each parallel group. The orders call is sequential because you need the ids before you can ask for payments. After that, calls run in parallel, so the page waits for the slowest dependency, which is where the tail latency problem bites: if each of three services has a 99th percentile of 200 ms, the chance that at least one is slow on a given request is much higher than 1%. Mitigations:

  • Parallelism for independent calls, and batch endpoints (GET /customers?ids=...) instead of one call per row, which avoids the "N+1 calls" trap where a page of 20 orders triggers 20 customer calls.
  • Timeouts, deadlines and retries with budgets on every call, so a hung dependency cannot hold the request thread forever (see Chapter 40). Propagate one overall deadline, not independent ones.
  • Circuit breakers and bulkheads so a failing service is skipped quickly and its failure does not exhaust the aggregator's thread pool.
  • Graceful degradation. Decide per field whether the data is essential. The order list is essential; the payment badge can show "unknown", and the product image can fall back to a placeholder. Return partial results with an indicator of what is missing.
  • Caching of slow-changing parts (product titles, customer names) in the aggregator, with short time-to-live (Chapter 13).

Availability multiplies: if the aggregator requires four services each at 99.9%, the best the page can offer is about 99.6%, ignoring the aggregator itself. This is another reason to degrade instead of failing.

5.3 Pagination and sorting across services

Pagination is where composition becomes painful. Page 3 of "orders sorted by customer name" cannot be computed by the orders service, because customer name lives elsewhere. The options are:

  • Paginate on the primary entity, enrich afterwards. Sort and page by something the orders service owns (creation time, order id), then enrich each page with names and titles. This is cheap and covers most screens. Use cursor (keyset) pagination rather than offsets for stability.
  • Merge in memory when sorting by data from two services: fetch the top N from each, merge, and cut. This is correct only for small N and gets expensive as pages go deep, since you must over-fetch to be right.
  • Filter pushdown. If the user filters by "customer in Germany", the aggregator must first ask Customers for matching ids and then ask Orders for orders with those ids, which can be a very large id list. Past a modest size this stops working.
  • Build a read model (next section) when the screen needs filtering and sorting by attributes from several services. This is the main signal that composition has reached its limit.
Interview tip Say explicitly that composition is the simplest option and you would start there; then name the trigger for moving to a read model: cross-service filtering or sorting, deep pagination, or a latency target that the slowest dependency cannot meet.

6. CQRS read models and materialized views from events

CQRS (Command Query Responsibility Segregation) separates the model used to change data (commands) from the model used to read it (queries). In microservices it is a way to answer cross-service queries: a read service subscribes to the events published by the owning services, and maintains its own denormalized table already shaped for the screen. This is a materialized view built from events. The events themselves, their delivery guarantees and the log that carries them are covered in Chapter 36.

6.1 How the projector works

The projector consumes events in order per key (for example per order id), and applies each to the view with an idempotent update: "set the customer name on all rows for customer 42 to X", "set the payment status of order 9 to captured". Because brokers normally deliver at least once, the projector must tolerate the same event twice, which is why updates should be absolute assignments or guarded by an event version number, not increments (see section 10.4).

Events may arrive in an unexpected order across topics. A PaymentCaptured event might arrive before OrderPlaced. The projector either buffers it, creates a placeholder row with unknown fields to be filled in later, or uses version numbers so a late older event never overwrites a newer value. A placeholder row approach is the simplest robust one.

6.2 What you gain and what you pay

  • Gain: one local query answers the whole screen, with filtering, sorting and pagination on any field, at database speed. The read model can live in the best store for the job (a relational table, or a search index for text and facets), and scales independently of the write services. The read path no longer depends on the availability of four services.
  • Pay: the data is eventually consistent, so the screen can show a stale value for a moment. You have a new component to build, operate and monitor, including lag alerts. And you duplicate data, which raises the ownership questions in section 9.
  • Rebuild and evolve. A new screen means a new view, rebuilt by replaying history from the log (if retention allows) or from a snapshot plus the log tail. Keep the projector deterministic so a rebuild produces the same result.
Key idea A read model is a cache with a different philosophy: it is built by pushing changes into it from the source's own event stream, so it can be fully queryable and survive restarts, instead of being filled lazily on a miss. Treat it as derived data: the owners remain the source of truth, and the view must be rebuildable.

7. Replicating reference data: event-carried state transfer

Sometimes a service does not need a full view, only a small slice of someone else's data, again and again. The orders service needs the customer's shipping country on every order to compute tax; the catalogue's product titles appear on many pages. Calling the owner for every read adds latency and couples availability. The alternative is to keep a local copy of exactly the fields needed, updated by events. The pattern is called event-carried state transfer because the event carries enough of the new state that consumers never need to call back to the owner.

7.1 Event design: notification versus state transfer

There are two styles of event. A notification event says only "customer 42 changed"; consumers who care must call the Customers API to learn what changed. This keeps events small and the owner in control, but brings the runtime coupling back (and a thundering herd of callbacks after a bulk change). An event-carried state transfer event includes the new values, so consumers update their copy without calling back. It costs larger messages and commits you to a payload contract, but it gives real autonomy: the orders service keeps working while Customers is down. For reference data this is usually the right choice.

7.2 Bootstrapping a new replica

A new consumer, or one recovering from lost data, needs the current state, not just future changes. Common approaches: replay the topic from the beginning if the topic is a compacted log that retains the latest event per key; load a snapshot export from the owner and then apply events after the snapshot's offset; or page through the owner's API once, then switch to events. The snapshot and the stream must overlap safely, so use version numbers to discard anything older than what is already stored.

7.3 Staleness and what to do about it

The copy lags the truth by the publish delay, broker delay and the consumer's processing time, typically milliseconds to seconds but unbounded when something is broken. Ask for each field: what is the damage if this is stale?

  • A customer's display name shown a second late: harmless.
  • The product price used to charge the customer: the order should snapshot the price at order time and store it in the order, which also gives a correct historical record. Never recompute historical amounts from the current catalogue.
  • A user's permission or a suspended account: stale data can be a security problem, so either use short token lifetimes, check the owner synchronously for the critical action, or keep staleness tiny and monitored.

The general technique is to copy at the moment of decision: when an order is placed, store the address, the price and the tax rate that were used. That copy is not a replica waiting to be synchronized; it is a fact about the past and is never updated.

8. Search and reporting stores fed by CDC

Many data needs are not an API composition or a business event at all: "search products by text", "dashboard of revenue by region", "audit trail". These need a different store (a search index, a column store) fed with data from the operational databases. Change data capture (CDC) is the cleanest way to feed it: a tool reads the database's own transaction log (the binlog in MySQL, the write-ahead log in PostgreSQL) and turns every committed row change into an event on a stream, without the application writing any extra code and without adding query load to the tables. Debezium is the best known open source implementation.

8.1 CDC versus application events

CDC events are shaped like the internal table rows (before and after images), which leaks the private schema. That is acceptable for search indexes and warehouses owned or closely coordinated with the same team, but dangerous as the contract between services: the moment other teams build on your table layout, you are back to a shared schema through the side door. The usual guidance is: use CDC to feed derived stores and to implement the outbox (section 10.2); publish deliberate, versioned domain events for other services.

8.2 Operational points

  • Initial snapshot, then log. The connector first copies existing rows, then streams changes from the log position it recorded, so nothing is missed or duplicated beyond what idempotent writes tolerate.
  • Lag and log retention. A stalled connector makes the database retain log files, which can fill the disk. Monitor replication slot lag.
  • Schema changes in the source flow through to the stream. Use a schema registry and compatible changes, and expect the sink to handle added columns.
  • Deletes arrive as delete events (and often a tombstone); the sink must remove the document or mark it, or deleted products will keep appearing in search.

9. Duplication and ownership

Sections 6 to 8 all create copies. Copies are the price of autonomy, but unmanaged copies are how data becomes inconsistent. The discipline is simple to state: for every piece of data there is exactly one source of truth and exactly one writer, and every other representation is a derived copy that can be rebuilt from the owner.

9.1 Single writer, source of truth

Decide, for each entity, which service owns it. The customer's email belongs to the Customers service. The orders service may keep a copy for sending receipts, but it must never edit it; if a user changes their email on the order screen, the orders service sends a command or request to Customers and then receives the resulting event like everybody else. If two services both accept writes to the same fact, you have a conflict-resolution problem (last writer wins, version vectors, merges) that is very much harder than routing writes to one place. When geographic multi-writer replication is genuinely needed, see Chapter 24 and Chapter 26.

9.2 Keeping copies in sync

  • Push by events (sections 6 and 7): low lag, but needs reliable publishing (outbox) and idempotent consumers.
  • Pull on demand with a cache and TTL: simple, bounded staleness, but adds calls.
  • Periodic reconciliation (section 10.5) to repair what the other two missed.

Usually you combine events for freshness with reconciliation for safety.

9.3 Updates and deletes

An update event carries the new state with a version (or timestamp plus entity version); consumers apply it only if it is newer than what they hold, which makes redelivery and reordering harmless. A delete is harder because "nothing" cannot carry a version. Publish an explicit CustomerDeleted event (or a tombstone in a compacted topic) and make the owner keep a soft-delete marker for a retention window so that late consumers and rebuilds can still learn about it. Consumers must then decide what a delete means for them: remove the local copy, anonymise it, or keep historical order rows but drop the personal fields. Legal erasure (section 15) turns this into a hard requirement.

9.4 Versioned events

The event format is a public contract with consumers you may not know. Evolve it compatibly:

  • Add, do not change. New optional fields are safe; renaming, removing or changing the meaning of a field is a breaking change.
  • Tolerant readers. Consumers ignore unknown fields and supply defaults for missing optional ones.
  • Explicit version in the event type or a schema id (a schema registry with Avro, Protobuf or JSON Schema enforces compatibility rules at publish time).
  • Breaking change = new version side by side. Publish both CustomerChanged.v1 and .v2 for a deprecation window, migrate consumers, then retire v1.
  • Upcasting when replaying old events: convert old shapes to the current one in the consumer or when reading from the log.

The serialization formats and their compatibility behaviour are covered in Chapter 7.

10. Consistency across services

Inside one service you still have ACID transactions. Across services you do not, so you must design for eventual consistency: the system is allowed to be briefly inconsistent, and guaranteed to converge when updates stop. (The theory is in Chapter 28.) The tools are below.

10.1 Sagas

A saga breaks a business transaction that spans services into a sequence of local transactions, each in one service, with a compensating action defined for each step that undoes it if a later step fails. Placing an order might be: create order (pending), reserve stock, charge payment, confirm order; if payment fails, release the stock and cancel the order. Sagas can be choreographed through events or orchestrated by a coordinator. They give up isolation: other requests can see intermediate states (an order that is pending), so the design must make those states explicit. The full treatment is in Chapter 48, and the two-phase commit alternative and why it is rarely used between services is in Chapter 31.

10.2 The transactional outbox

A service often has to do two things: change its own database and publish an event about it. These are two systems, so doing both naively gives the dual-write problem: if the database commit succeeds and the publish fails (or the process dies between them), the world never hears about the change; if you publish first and the commit fails, the world hears about something that did not happen.

The transactional outbox fixes this by turning the two writes into one local transaction: the service inserts the business row and an event row in an outbox table in the same database transaction. A separate relay (a poller, or CDC tailing the outbox table) reads new outbox rows and publishes them to the broker, marking them sent. Either both the data and the event exist, or neither does.

10.3 The inbox pattern

Brokers retry, so a consumer can receive the same event more than once. The inbox is the consumer's mirror of the outbox: a table of already processed event ids. On receipt the consumer, in one local transaction, inserts the event id (with a unique constraint) and applies the business change. A duplicate insert violates the constraint, rolls back, and the message is acknowledged without being applied again. This is a durable form of deduplication; the broader theory of idempotency keys and unique ids is in Chapter 32.

10.4 Idempotent handlers

Even without an inbox table, design every handler so that applying it twice equals applying it once. Prefer absolute assignments ("status = paid") over relative changes ("balance = balance + 10"). Use natural business keys and upserts. Guard with versions ("update where version < incoming"). For external side effects (sending email, calling a payment provider) pass an idempotency key that the other side deduplicates on. Retries, redelivery, and consumer rebalances all become safe once this holds.

10.5 Reconciliation jobs

No pipeline is perfect: a bug drops an event, a consumer is down longer than the log retains, someone edits a row by hand. A reconciliation job periodically compares two sides and repairs the differences. A typical one reads the owner's records changed in the last day (or a checksum per range of ids) and compares them to the replica or read model, then re-emits or directly fixes mismatches; for money flows it compares your ledger to the payment provider's settlement report. Reconciliation turns "we hope the events worked" into "we verify and measure drift", and the mismatch count is an excellent health metric. It is the backstop that lets you accept eventual consistency with a straight face.

10.6 Designing for visible intermediate states

Eventual consistency becomes a user experience question. After the user presses Place Order, the confirmation page might read a read model that has not yet received the event. Standard remedies: return the new state from the write call and show it directly (read your writes from the response); route that user's next read to the owner for a short time; or show an honest "processing" status and update through polling or push. Do not silently show the old state.

11. Foreign keys without joins

A foreign key lets the database guarantee that an order points to an existing customer. Across databases no such guarantee exists. You replace it with references by id plus rules:

  • Store only the id (and optionally a snapshot of a few display fields), never a pointer into another service's table. The reference is a logical, not physical, relationship. The id must be stable and never reused (section 12).
  • Validate at write time where it matters. When creating an order, the orders service checks the customer exists (a synchronous call, or its local replica of customer ids). It cannot make this atomic with later events, so a customer could still be deleted a moment later.
  • Expect orphans. An order may refer to a customer that was later deleted, or whose creation event has not arrived. Code that reads references must tolerate "not found": show "unknown customer", skip the row, or fall back to the snapshot fields.
  • Soft deletes in the owner (a deleted_at or status flag) keep ids resolvable, so references do not dangle, and let consumers learn about the deletion by event rather than by a missing row. Purge physically after consumers have caught up and the retention period expires, subject to privacy law.
  • Referential cleanup via events. When a customer is deleted, the owner publishes an event and dependants decide what to do: cascade (delete the customer's carts), restrict (cancel the deletion workflow because open orders exist), or anonymise (keep orders, strip personal fields). Do this in the application layer; there is no database cascade across services.
  • Orphan detection. A scheduled query joins a service's ids against the owner's id list (or its replica) and reports dangling references, which is a form of reconciliation.

12. Distributed unique ids

Auto-increment integers from one database cannot be used when several services, and maybe several shards of one service, create entities, and they leak business volume and invite enumeration attacks. Requirements for ids: unique without central coordination on every insert, stable forever, and ideally roughly time-ordered so index inserts stay efficient. The usual options (details in Chapter 32):

Client-generated ids (a UUID created by the caller) can also double as idempotency keys for creation requests.

13. Transactions inside the service boundary

Inside the service, use the full power of the database. A good boundary is chosen so that the data that must change together lives together. The order and its order lines belong to one service, so "create order with 3 lines and update the total" is one ACID transaction, with constraints and foreign keys between the service's own tables. If you find that most operations need a saga because two services always change together, that is a design smell: the boundary is probably in the wrong place and the two should be merged or the data moved (see aggregate boundaries in Chapter 45).

Within a service the DDD aggregate is the usual unit: one transaction should change one aggregate, and anything else (other aggregates, other services) is updated afterwards through events. This also keeps transactions short and reduces lock contention, which pays off at scale (Chapter 18 covers isolation levels and locking). Combine local ACID with the outbox (section 10.2) so that state change and event are still atomic.

14. Migrating data when splitting a shared database

Most real systems start with a shared database and must split it. The safe sequence matters: split logically before physically, and move one step at a time with a rollback at each step. The overall strategy for extracting services is in Chapter 44; below are the data steps.

14.1 Split the schema first

Before you deploy a new service, separate the tables logically in the existing database: assign each table to one owner, move them into per-owner schemas, and create separate database users with grants only on their own schema. Failures now surface as permission errors in tests rather than as outages. Use query logs and static analysis to list every cross-owner query, join and foreign key; that list is your work plan.

14.2 Remove cross-table joins

For each cross-owner join choose a replacement: call the owner's API (composition), keep a replicated field, or build a read model. Drop cross-owner foreign keys (keep them as documented logical references with application-level checks). Convert cross-owner transactions into sagas or merge the data back if they truly belong together. This work can be done while everything still lives in one physical database, so it is fully testable and reversible.

14.3 Moving the data: dual writes and CDC

When the data finally moves to a new database, you need it to be in both places during transition, and the choice of mechanism matters:

  • CDC replication (preferred). Stream changes from the old tables to the new database. Writes still go to one place, so there is no divergence, and the lag is observable. Cut over reads first, verify, then flip the writer.
  • Application dual writes. The code writes to both stores. This is tempting but dangerous: the two writes are not atomic, so any failure between them creates silent differences. If you must, make one store authoritative, write it first, treat the second as best effort with a repair job, and run a comparison job continuously.
  • Backfill plus catch-up. Copy historical rows in batches while tracking a high-water mark, then apply the change stream from the marked position.

Verification is the heart of a safe migration: shadow reads (read both, return the old, log differences), row counts and checksums per range, and a staged cutover (1% of reads, then 10%, then all). Plan the rollback: keep the old store updated in reverse for a while after cutover, or at least keep it intact and read-only.

15. Data governance, PII ownership and retention

Database per service is also the foundation for governing data. When each category of data has one owner, you can answer the questions regulators and security teams ask: where is this person's data stored, who may read it, how long do we keep it, and how do we delete it. (Privacy law and cost considerations are covered in Chapter 56.)

  • PII ownership. Concentrate personally identifiable information in as few services as possible (typically identity or customer profile). Other services store only an opaque id or the minimum fields they need, rather than copies of names, emails and addresses. This reduces the blast radius of a breach and the number of places a deletion request must reach.
  • Classification and tagging. Mark fields as public, internal, confidential or regulated in the schema and in event definitions. Do not put regulated fields into broad events or logs. Prefer events that carry ids and let authorised services fetch the sensitive details.
  • Per-service retention. Each service defines how long it keeps each class of data, driven by its purpose: keep order history for tax law periods, session data for days, debug logs for weeks. Implement retention as scheduled deletion or TTL, and apply it to derived copies too: replicas, read models, search indexes, caches and backups.
  • Right to erasure. A deletion request must propagate: the owner deletes and publishes CustomerErased; every subscriber that holds a copy removes or anonymises it and confirms; the warehouse and lake have their own deletion jobs. Append-only logs complicate this: techniques include keeping personal data out of events (reference by id), encrypting personal fields with a per-user key and deleting the key (crypto-shredding), and bounded retention on topics.
  • Access control and audit. Per-service credentials, least privilege, encryption at rest and in transit, and access logs for sensitive reads. Data residency rules may require that a region's data stays in that region, which pushes you towards regional instances of the owning service.

16. Analytics, data lakes, data mesh and data products

The operational databases are the wrong place for analytics: heavy scans disturb users, and the data is spread over dozens of private schemas in different engines. The standard answer is to copy data out to an analytical platform.

  • Data warehouse: a column-oriented store with a curated, modelled schema (facts and dimensions), optimised for scans and aggregation, queried with SQL.
  • Data lake: cheap object storage (Chapter 21) holding raw and semi-structured data in open file formats, queried with engines on top; a lakehouse adds table formats with transactions to this.
  • Ingestion: CDC streams (section 8) or published domain events flow into the lake continuously, or batch extracts land nightly (see Chapter 37). Streaming gives freshness, batch is simpler and cheaper.

Data mesh applies the microservice idea to analytics: instead of a central team owning all pipelines, each domain team owns and publishes its analytical data as a data product: a discoverable dataset with a documented schema, an owner, quality checks, freshness targets and access policy. A shared platform team provides storage, pipelines, a catalogue and governance tooling, and a federated governance group sets global rules (identifiers, privacy classification). It scales organisationally for large companies, but is heavy for small ones; for most teams a central warehouse fed by CDC and domain events is enough. The key principle either way is the same as in the rest of this chapter: analytics reads copies, never the live operational databases, and each dataset has a clear owner.

17. Testing data contracts

With databases private, the contracts that matter are the APIs and the event formats. Without a shared schema, breaking changes appear at runtime in someone else's service. Test them explicitly:

  • Consumer-driven contract tests. Each consumer states the fields and semantics it relies on (a Pact file, for example). The provider's build verifies it can still satisfy every consumer's contract, so a removed field fails the provider's pipeline before release. Events get the same treatment: consumers declare the event shape they read.
  • Schema compatibility gates. A schema registry or CI check rejects schema changes that are not backward (new readers read old data) or forward compatible (old readers read new data), according to the rule you chose.
  • Replay tests. Keep a corpus of real historical events, including old versions, and verify that the current consumer processes them and produces the same view. This catches upcasting mistakes.
  • Idempotency and ordering tests. Feed the same events twice and in shuffled order; the result should be unchanged. Inject duplicates, drops and delays in integration tests.
  • Reconciliation as a runtime test. Production drift metrics are the last line of defence: alert when mismatch counts rise.
  • Migration tests. Run shadow comparisons and checksums, and rehearse the cutover and rollback in a staging copy of production data.

18. Worked example: the orders page

The product shows an "My orders" page: for each of the last 20 orders, the order number and date, the customer's display name and shipping country, the product title and thumbnail for each line, the line price, and the payment status. The target is a response under 300 ms at the 95th percentile, 2,000 page views per second at peak, and a design that survives a payments outage.

18.1 Ownership

DataOwner (single writer)How the page gets it
Order and lines, prices at order timeOrdersorder_view (own events)

18.2 Why this mix

A pure composition design would call four services, with the page waiting for the slowest. At 2,000 views per second and 20 orders per page, naive per-order calls would generate 40,000 customer calls per second, so batching is mandatory, and the slowest of four tail latencies determines the page. A pure read-model design would be fast and resilient, but payment status can change within seconds of a retry and users notice a wrong "failed" badge, plus the payments events would carry sensitive data into another store. So we split by volatility and sensitivity: names, titles and country change rarely, so they live in the view; payment status changes rapidly and is critical, so it is fetched live in one batch call, GET /payments?orderIds=..., with a 150 ms timeout and a short cache.

18.3 Numbers

  • Read model query: one indexed query (WHERE customer_id = ? ORDER BY created_at DESC LIMIT 20) at about 5 ms, served by a database sized for 2,000 reads per second (about 2 to 3 modest replicas).
  • Payments batch call: typically 20 to 40 ms, with a hard 150 ms deadline. Added in parallel with nothing else on the critical path after the view read, or even started in parallel with it using the order ids from a recent-orders cache.
  • Page latency: about 5 ms view plus about 40 ms payments plus 15 ms BFF overhead and network, around 60 ms typical, and bounded near 200 ms in the worst case because of the deadline.
  • Payments load: 2,000 views per second would be 2,000 payment batch calls per second; with a 5-second cache keyed by user, the repeated views from the same user collapse, perhaps to a few hundred per second.
  • Replica storage: 50 million orders at about 1 KB per denormalized row is roughly 50 GB, fine for one relational node with replicas. Customer replica (10 million customers, 100 bytes of relevant fields) is only about 1 GB.
  • Staleness: events typically apply within 1 to 2 seconds. If a user renames themselves, the old name may show for that moment, acceptable. Right after placing an order the confirmation response includes the new order directly so the first view does not depend on the projector.

18.4 Writes and consistency

Placing an order is a saga across Orders, Inventory and Payments (Chapter 48), using an outbox in each service and inbox-protected consumers. The order starts in a PENDING state, which the page shows as "processing" until the saga ends. Prices and product titles are copied into the order lines at placement, so later catalogue edits do not rewrite history. A nightly reconciliation job compares a sample (or per-range checksums) of order_view against the Orders database and the customer replica against Customers, repairing and counting mismatches.

20. Interview Q&A

Why should each microservice have its own database? Isn't a shared database simpler?

It is simpler at first, but a shared database couples services through a schema that nobody treats as an API. A column rename becomes a multi-team release, a heavy query by one service slows the others, and a failure takes everything down together, so you have a distributed monolith. A private database gives autonomy (independent deploy, scale and failure), encapsulation (one gatekeeper for invariants) and freedom to evolve the schema or change engines. The cost is losing joins and cross-service transactions, which I replace with composition, read models, events and sagas. For a small team with few services I would happily accept a shared database with strict per-service schemas as a stepping stone.

How do you show data from several services on one screen?

First choice is API composition: an aggregator or backend-for-frontend fetches the primary entity, then calls other services in parallel using batch endpoints, with timeouts and fallbacks so one slow dependency degrades a field instead of the page. If the screen needs filtering or sorting by fields from several services, or the latency or availability target cannot be met, I build a read model: a projector consumes events from the owners into a denormalized table shaped for the query. Rarely changing small fields may instead be replicated locally via events. I usually mix them, using local data for stable fields and a live call for volatile ones.

How does eventual consistency affect the user experience, and how do you handle it?

A user may act and then see old data because a read model or replica has not applied the event yet. I handle it by returning the updated entity in the write response so the client shows it immediately, by routing that user's next reads to the source of truth for a short window, or by showing an explicit "processing" state. I also decide per field what staleness is tolerable: a display name can lag, but prices and permissions should be snapshotted or checked synchronously. And I monitor replication lag so staleness is bounded and visible rather than discovered by customers.

What is the dual-write problem and how does the outbox pattern solve it?

A service that updates its database and then publishes to a broker is writing to two systems with no shared transaction. A crash between them leaves data changed but no event, or an event for something that never committed, and the other services drift permanently. With the outbox, the service writes the business row and an event row into an outbox table in one local transaction, so they are atomic. A relay, either a poller or CDC reading the log, publishes outbox rows to the broker at least once. Consumers handle duplicates with an inbox table or idempotent handlers, giving effectively-once processing.

How do you maintain referential integrity without foreign keys across services?

I keep only the id of the other entity, validate it at write time through the owner's API or a local replica, and accept that it can dangle later. Owners use soft deletes and publish deletion events so dependents decide whether to cascade, block or anonymise. Readers tolerate missing targets by showing a fallback or a snapshot taken when the record was created. A scheduled orphan scan and reconciliation job detect and repair anything that slipped through. The guarantee changes from "never violated" to "eventually repaired and always handled gracefully".

How would you split a shared database that a monolith has used for years?

I split logically before physically. First, assign tables to owners, move them into separate schemas with separate database users, and catalogue every cross-owner query and foreign key. Second, remove those dependencies one at a time using API calls, replicated fields or read models, while still on one physical database, so each step is testable and reversible. Third, move the tables to the new database using CDC replication rather than application dual writes, run shadow reads and checksums to prove parity, cut over reads first and writes next, with a rollback path. Finally I make the old tables read-only, watch for stragglers, and drop them.

When is CDC appropriate and when should services publish domain events instead?

CDC is excellent for feeding derived stores like search indexes and warehouses, and as the transport behind an outbox, because it captures every committed change without touching application code or adding query load. Its drawback is that events mirror internal table structure, so other teams that build on them become coupled to the private schema. For communication between services I prefer deliberately designed, versioned domain events, such as "OrderPlaced", that carry business meaning and a stable contract. In practice the outbox table holds the domain event, and CDC just ships it.

How do you handle personal data and the right to erasure in a system with many copies of data?

I minimise copies by making one service the owner of personal data and having others store ids plus only essential fields. Every copy, including replicas, read models, search indexes, caches, backups and the warehouse, has to be reachable by deletion. The owner publishes an erasure event, each subscriber deletes or anonymises and confirms, and warehouse jobs apply the same. For immutable logs I keep personal data out of events or encrypt personal fields per user so deleting the key makes them unreadable (crypto-shredding). Retention periods are defined per service and enforced with TTLs or scheduled jobs.

What are the signs that service boundaries are wrong from a data perspective?

If most business operations need a saga across the same two services, or two services always deploy together, they probably should be one service. If services call each other in chains just to read basic data, or one service has to read half of another's data to function, the data is on the wrong side of the boundary. Another signal is a service that needs write access to another's database, which means the owner is not truly the source of truth. The fix is to redraw boundaries around aggregates that must change together, or to move or replicate the data so each service can do its core job without synchronous calls to others.

How would you keep a local copy of reference data in sync, and what if it falls behind?

The owner publishes events carrying the new state with a version, and the consumer upserts its local table only when the incoming version is newer, so duplicates and reordering are harmless. A new consumer bootstraps from a snapshot or compacted topic, then follows the stream. If it falls behind, lag metrics alert us and the data is stale but still serving. If events were lost beyond retention, a reconciliation job or full resync from the owner repairs the copy. For anything where staleness is dangerous, such as prices at checkout, I snapshot the value into the transaction when the decision is made, or check with the owner synchronously.

21. Connections and recap

Recap

  • Each service owns its data and exposes it only through APIs and events; this gives autonomy, encapsulation and independent schema evolution, at the cost of joins, foreign keys and cross-service ACID.
  • A shared database is tolerable as a transitional step, for tiny teams, or for reference data and reporting copies, but it leaves coupling and a shared failure domain. Schema per service with separate credentials is a good first enforcement; move to separate instances for measured isolation, compliance or engine needs.
  • Polyglot persistence lets each service choose the fitting store, but each extra engine is an operational cost.
  • For cross-service reads, start with API composition (parallel, batched, with timeouts and graceful degradation), and move to event-built read models when you need cross-service filtering, sorting or tighter latency; replicate small reference data using event-carried state transfer; feed search and analytics stores with CDC.
  • Every fact has one source of truth and one writer; copies carry versions, handle deletes explicitly, and event schemas evolve compatibly with versioning.
  • Across services, accept eventual consistency and use sagas, the transactional outbox, inbox deduplication, idempotent handlers and reconciliation jobs. Keep one-aggregate ACID transactions inside the service.
  • Replace foreign keys with id references plus orphan tolerance and soft deletes; use globally unique, preferably time-ordered ids generated by the owner.
  • Split a shared database by schema first, remove joins, then sync with CDC (not blind dual writes), verify with shadow reads, and cut over with a rollback.
  • Concentrate PII, define per-service retention, propagate erasure to all copies, give analytics its own copies (lake, warehouse, data products), and test contracts with consumer-driven tests, compatibility gates and replay.
