Consensus and Leader Election

Consensus is how a group of unreliable machines agrees on one answer, such as who the leader is or what the next entry in a log is, even while some of them crash and the network drops messages. This chapter explains why that is hard, why a majority quorum is the tool that makes it possible, and walks through Raft step by step, with Paxos, leases, fencing and real systems around it.

1. The problem consensus solves

Imagine three servers that together store a small but critical fact: "the primary database is server B." A client asks any of them. If the three servers can ever disagree, say one says B and another says C, then two different clients may send writes to two different primaries and your data is corrupted. You need the servers to agree on a single value, to keep agreeing as new values are chosen, and to do so even if some servers crash or some messages are lost or delayed.

That is the consensus problem. In its textbook form, each process proposes a value, and the algorithm must satisfy three properties:

  • Agreement: no two correct processes decide different values.
  • Validity: the decided value was actually proposed by some process (the system cannot just invent an answer, or always answer "0").
  • Termination: every correct process eventually decides. This is the liveness property: the system does not hang forever.

The first two are safety properties: "nothing bad ever happens." Termination is a liveness property: "something good eventually happens." This split matters enormously later, because real consensus algorithms promise safety unconditionally and liveness only when the network behaves reasonably.

1.1 From one value to a log

Agreeing on a single value once is useful but rarely enough. What systems really need is to agree on an ordered sequence of values, a replicated log. Each entry in the log is a command ("set key x to 5", "add server D to the cluster", "acquire lock L for client 7"). If every server applies the same commands in the same order to the same starting state machine, they all end up in the same state. This approach is called a replicated state machine, and it is the foundation of almost every strongly consistent distributed system: etcd, Consul, ZooKeeper, Spanner's Paxos groups, CockroachDB ranges and Kafka's KRaft metadata quorum.

Key idea Consensus turns "many unreliable machines" into "one reliable machine" from the point of view of the application. It does this by agreeing on a single order of operations. Everything else in this chapter, leaders, terms, quorums, leases, is machinery to make that agreement safe when things fail.

2. Where consensus is used

Consensus shows up in a few recurring roles. Recognising them is half of answering interview questions about it.

  • Leader election. A group of workers must agree on exactly one leader (the primary database, the active scheduler, the controller). Electing a leader is itself a consensus problem: everybody must agree on who. Section 12 covers this.
  • Configuration and metadata. Cluster membership, shard maps, feature flags, service discovery data. This data is small, read often, and must never be inconsistent. Services such as etcd, ZooKeeper and Consul store it (Chapter 30 covers using them).
  • Replicated state machines. A database or queue replicates its writes via a consensus log so that no acknowledged write is ever lost, even if the leader's machine burns down. Spanner, CockroachDB and TiKV do this per data partition.
  • Distributed locks and leases. A lock service is a small replicated state machine that records "lock L is held by client 7 until time T."
  • Total order broadcast. Delivering the same messages in the same order to everybody. This is mathematically equivalent to consensus.

2.1 Consensus versus atomic commit

Interviewers often probe whether you can tell consensus from atomic commit, the thing two-phase commit (2PC) does. They sound similar, since both end with "everyone agrees," but they solve different problems:

3. FLP impossibility, in plain words

In 1985 Fischer, Lynch and Paterson proved a famous result, always called FLP. Stated carefully: in an asynchronous system (one with no upper bound on how long a message takes or how slow a process can be), no deterministic consensus algorithm can guarantee termination if even one process may crash.

Here is the intuition. Suppose you are waiting to hear from a server, and it has been silent for a long time. Either it has crashed, or it is just very slow, and in an asynchronous model you can never tell which. If you decide it is dead and move on, you may be wrong, and when it wakes up it might have already made a decision that conflicts with yours. If you keep waiting, you may wait forever. Any algorithm that always terminates must sometimes guess, and an adversarial schedule of delays can always make the guess wrong at the worst moment, or else keep the algorithm in an undecided state forever.

Watch out FLP does not say consensus is impossible in practice. It says you cannot have all three of: a purely asynchronous network, guaranteed termination, and guaranteed safety with crash failures. Real algorithms keep safety always and give up guaranteed termination under adversarial timing. The impossible situation requires an unlucky schedule that goes on forever, which almost never happens.

3.1 What real systems do about it

  • Keep safety unconditional, make liveness conditional. Raft and Paxos never produce two different decisions, regardless of delays or crashes. They only promise to make progress when the network is "partially synchronous": after some unknown point in time, messages are delivered and processes run within some bounded (but unknown) delays. This is the model from the Dwork, Lynch and Stockmeyer paper.
  • Use timeouts as failure detectors. A timeout is an imperfect guess at "this node is dead." A wrong guess costs only performance (an unnecessary election), never correctness.
  • Use randomness. FLP applies to deterministic algorithms. Raft randomises election timeouts so that competing candidates are unlikely to keep colliding. Some algorithms (Ben-Or's, and many Byzantine protocols) use random coin flips to guarantee termination with probability 1.

The interview-ready summary: "FLP says you can't have guaranteed liveness in a fully asynchronous system with failures. Practical protocols are always safe and live when the network is eventually well behaved, and they use timeouts and randomisation to get that liveness in practice." Chapter 27 builds the background on partial failure, timeouts and unreliable clocks that makes FLP feel natural.

4. Quorums and majority math

The tool that nearly every consensus protocol uses is the quorum: a subset of nodes whose agreement is enough to make a decision. The most common choice is a majority: more than half of all nodes. Chapter 24 introduced quorums for leaderless replication (R + W > N). Consensus uses the same overlap idea in a stricter way.

4.1 The overlap argument

Suppose a cluster has N nodes and a quorum is any set of at least floor(N/2) + 1 nodes. Take any two quorums. Together they would contain at least 2 × (floor(N/2) + 1) member slots, and that is greater than N, so by the pigeonhole principle at least one node must belong to both. That shared node is the crucial witness. If quorum 1 decided "the leader is A" and recorded it on every member, then any later quorum must include at least one node that remembers that decision, and the protocol forces the later quorum to respect it.

4.2 Why 2f + 1 nodes tolerate f failures

To keep making progress you need a quorum to be available. If up to f nodes can be down, the remaining nodes must still form a quorum, so the quorum size must be at most N minus f. We also need the quorum size to be a majority so any two overlap, so quorum is at least f + 1 when N = 2f + 1. Setting N = 2f + 1 gives a majority of f + 1, and with f nodes down, exactly f + 1 remain, which is just enough. With fewer than 2f + 1 nodes, for example 2f, two disjoint halves of size f could each form a "quorum" of f and decide differently, which is the split-brain disaster.

Interview tip When asked "why 2f + 1?" say: any two majorities intersect, so a new leader's quorum always contains at least one node that saw every committed decision. And when asked "why not an even number?" say: the extra node raises the quorum size without raising the number of failures you can survive.

5. Raft: the big picture

Raft was designed by Diego Ongaro and John Ousterhout (published 2014) with an explicit goal: be understandable. It is equivalent in fault tolerance and performance to Multi-Paxos, but it breaks the problem into three fairly independent pieces:

  1. Leader election: choose one server to be in charge.
  2. Log replication: the leader accepts commands, appends them to its log, and forces every follower's log to match.
  3. Safety: rules that guarantee a committed entry is never lost or overwritten, no matter who becomes leader later.

Raft is strongly leader-based. All client writes flow through one leader at a time, and log entries only travel in one direction, from leader to followers. This asymmetry simplifies reasoning dramatically.

5.1 Roles

Every server is always in one of three states:

  • Follower: passive. It answers requests from leaders and candidates and does nothing on its own. All servers start as followers.
  • Candidate: a follower that has stopped hearing from a leader and is now asking for votes to become the leader.
  • Leader: handles all client requests, replicates log entries, and sends periodic heartbeats to keep followers from starting elections. There is at most one leader per term.

5.2 Terms

Raft divides time into terms, numbered with consecutive integers. A term is a logical clock: it begins with an election and lasts until the next one. In each term there is at most one leader, and some terms have no leader at all (a split vote). Every message carries the sender's current term, and the rules are simple:

  • If a server sees a message with a higher term than its own, it updates its term and becomes a follower. This is how a stale leader that was partitioned away discovers it has been replaced.
  • If a server gets a request with a lower term, it rejects it and replies with its own higher term so the sender can step down.
  • A server votes for at most one candidate per term, first come first served. This single rule is what guarantees at most one leader per term, because two candidates cannot both gather a majority of single-use votes.

Terms are the same idea as the logical clocks of Chapter 27 applied to leadership: they give a total order to leaders even though real clocks cannot be trusted. They also double as a fencing token, as section 13 explains.

6. Leader election in Raft

A leader sends heartbeats (empty AppendEntries messages) to all followers at a regular interval, often around 50 to 150 ms. Each follower has an election timeout, typically 150 to 300 ms in the original paper, and often 1 to 10 seconds in production systems that value stability over fast failover. Every time a follower hears a valid heartbeat, it resets its timer. If the timer fires with no word from a leader, the follower assumes the leader is gone and starts an election.

6.1 Steps of an election

  1. The follower increments its current term, changes state to candidate, and votes for itself.
  2. It sends RequestVote to every other server, including its term, its id, and the index and term of the last entry in its log.
  3. Each receiving server grants its vote if: the candidate's term is at least its own, it has not yet voted in this term (or already voted for this candidate), and the candidate's log is at least as up to date as its own (the election restriction, section 8).
  4. The candidate becomes leader as soon as it holds votes from a majority (counting itself). It immediately sends heartbeats to establish authority and prevent new elections.
  5. If the candidate hears from another server claiming to be leader with a term at least as large as its own, it steps down to follower.
  6. If neither happens before its election timer fires again (a split vote), it increments the term and starts a new election.

6.2 Randomised timeouts

If all followers used the same timeout, they would all become candidates at the same moment, each vote for itself, and nobody would reach a majority. Raft picks each timeout at random from an interval (for example 150 to 300 ms). The server whose timer happens to fire first usually sends RequestVote to everyone before the others even become candidates, collects votes, and wins. Split votes still happen occasionally, but they resolve themselves quickly because each candidate re-randomises its timeout, so the collision is unlikely to repeat. This is the practical answer to FLP in Raft: randomisation breaks symmetry.

Watch out The election timeout must be comfortably larger than the heartbeat interval plus network round trip and any pause a process can suffer (garbage collection, disk fsync stalls, virtual machine hiccups). Set it too low and a busy leader looks dead, causing needless leader churn and write unavailability. Set it too high and real failures take long to detect. A common rule of thumb is a timeout of 10 times the typical network round trip, and at least 10 times the heartbeat interval.

6.3 Pre-vote and disruptive servers

A server that is partitioned away from the cluster keeps timing out and incrementing its term, over and over. When the partition heals, it arrives with a huge term number, and the current healthy leader sees a higher term and steps down, even though the isolated server could never have won. This disruption is real. The fix, which etcd and most production Raft libraries implement, is pre-vote: before incrementing its term a server asks "would you vote for me?" in a dry run. Only if a majority says yes does it start a real election. A node that cannot reach a majority never gets to inflate its term.

7. Log replication

Once a leader exists, it serves clients. Each client command becomes a new log entry containing the command and the term in which the leader received it, plus its position (index) in the log. The leader sends entries to followers using AppendEntries RPCs, the same message used for heartbeats.

7.1 The write path, step by step

  1. The client sends a command (for example set x = 5) to the leader.
  2. The leader appends the entry to its own log on disk (with fsync), assigning it index i and the current term.
  3. The leader sends AppendEntries to all followers in parallel. Each message carries the new entries plus prevLogIndex and prevLogTerm, which identify the entry immediately preceding the new ones, and leaderCommit, the leader's current commit index.
  4. Each follower checks that its log contains an entry at prevLogIndex with term prevLogTerm. If yes, it appends the new entries (overwriting any conflicting ones), persists them, and replies success. If not, it replies failure and the leader retries with earlier entries (section 9).
  5. When the leader has the entry stored on a majority of servers (counting itself), the entry is committed. The leader advances its commit index.
  6. The leader applies the committed entry to its state machine and replies to the client with the result.
  7. Subsequent AppendEntries messages (including heartbeats) carry the new leaderCommit, so followers learn the entry is committed and apply it to their own state machines.

7.2 What "committed" means

A log entry is committed once it is safely stored on a majority of servers. Raft's key guarantee is: a committed entry will be present in the logs of every future leader, so it will never be lost or rewritten. An entry that has been appended on the leader but not yet replicated to a majority is uncommitted, and if the leader crashes, it may or may not survive. The client never received an acknowledgement for it, so the system is not breaking any promise by losing it. The client must retry, which is why clients attach unique request ids so retries can be deduplicated (section 11).

One subtle rule: a leader only counts replicas to commit entries from its own current term. It commits older-term entries indirectly, when a current-term entry that follows them reaches a majority (the Log Matching property then guarantees the earlier ones are there too). This avoids a famous corner case (Figure 8 in the Raft paper) where an old entry stored on a majority could still be overwritten. In practice, a new leader appends a no-op entry at the start of its term to get this effect quickly.

7.3 The two log properties

  • Log Matching: if two logs contain an entry with the same index and term, then the logs are identical in all entries up to and including that index. The prevLogIndex/prevLogTerm consistency check is an inductive proof step: each accepted append extends a log known to match.
  • Leader Append-Only: a leader never overwrites or deletes entries in its own log. It only appends.

8. Safety: the election restriction

Replication alone is not enough. Suppose a follower that missed several committed entries (it was slow or briefly offline) wins an election. If it became leader, it would start overwriting the others' logs with its shorter one, destroying committed data. Raft prevents this with the election restriction:

Key idea A server grants its vote to a candidate only if the candidate's log is at least as up to date as the voter's own. "Up to date" compares the term of the last entry first (higher is newer), and if equal, the length of the log (longer is newer).

Why does this work? A committed entry lives on a majority. A candidate needs votes from a majority. Those two majorities overlap (section 4), so at least one voter holds every committed entry, and that voter will refuse any candidate whose log lacks the entry. Therefore only a candidate that already contains every committed entry can win. The leader therefore never needs to fetch missing committed entries from anyone, which is another reason log entries flow only from leader to followers.

9. Log repair after leader changes

When a leader crashes midway, followers can be left with logs that differ: some have entries the others do not, and some have uncommitted entries from an old term that never reached a majority. The new leader does not try to be clever. It simply forces all followers to copy its log. Safety is already guaranteed by the election restriction (the leader has every committed entry), so anything the leader lacks was never committed and is safe to discard.

Mechanically, the leader keeps a nextIndex per follower, initially one past its own last entry. It sends AppendEntries with prevLogIndex = nextIndex - 1. If the follower's consistency check fails, it replies failure and the leader decrements nextIndex and retries. Eventually it hits the last point where they agree (worst case, the very beginning). The follower then deletes any conflicting entries after that point and appends the leader's. Real implementations speed up the backing-up with hints: the follower returns the term and first index of its conflicting term, so the leader can skip a whole term at once instead of one entry per round trip.

10. Membership changes and snapshots

10.1 Changing the cluster membership

Clusters need to grow, shrink, and replace failed machines. The danger: servers do not all learn the new configuration at the same instant. If a 3-node cluster {A, B, C} is changing to {A, B, C, D, E}, then during the changeover some servers think the majority is 2 of 3, and others think it is 3 of 5. Two disjoint majorities could briefly coexist (for instance {A, B} under the old config and {C, D, E} under the new), electing two leaders in the same term.

Raft offers two safe approaches:

  • Single-server changes. Add or remove only one server at a time. Any majority of the old configuration and any majority of the new one (which differ by one node) always overlap, so no split is possible. Bigger changes are done as a sequence of single steps. The configuration is itself stored as a log entry and takes effect when the server appends it, not when it commits.
  • Joint consensus. The original paper's approach for arbitrary changes. The cluster first moves to a transitional configuration C(old,new) in which decisions need a majority of both the old and the new sets, then, after that is committed, to the new configuration alone. Both configurations can never decide independently during the transition.

Operational practice: add a new server first as a non-voting learner so it can catch up by copying the log or a snapshot, then promote it to voter. Adding a voter that is far behind can stall commits, because it counts toward the quorum but has nothing yet. When replacing nodes in a 3-node cluster, do add-then-remove, never remove-then-add, so you never drop below the fault tolerance you started with.

10.2 Snapshots and log compaction

A log that grows forever would eventually fill the disk and make restarts slow (replaying a billion entries). Servers therefore periodically take a snapshot: they write out the complete current state of the state machine along with the last included index and term, and then discard all log entries up to that point. Each server snapshots independently, based on its own applied state, for example when the log exceeds some size.

A slow follower may be so far behind that the leader has already discarded the entries it needs. In that case the leader sends its snapshot with an InstallSnapshot RPC (usually in chunks), the follower replaces its state with it, and normal AppendEntries resumes after that. Snapshotting a large state machine is expensive, so implementations use copy-on-write techniques or write the snapshot in the background to avoid stalling the server.

11. Client interaction and linearizable reads

11.1 Finding the leader and retrying safely

Clients send requests to the leader. A client that contacts a follower is redirected (the follower tells it who it believes the leader is) or the client simply tries other servers until one responds as leader. If the leader crashes after committing a command but before replying, the client times out and retries, and a naive retry would execute the command twice. Raft handles this with client sessions: each client has a unique id and numbers each request sequentially. The state machine remembers the latest sequence number and response for each client and, when it sees a duplicate, replies with the saved response without re-executing it. This gives exactly-once semantics on top of at-least-once retries (the same idempotency-key idea used at API level).

11.2 The stale read problem

Writes go through the log. What about reads? The simplest correct method is to put reads into the log too, so they are ordered with writes, but that costs a full replication round per read. Reading directly from the leader's state machine is much faster, but it has a hole: a leader may have been deposed without knowing it. Imagine the leader is partitioned from the majority. A new leader is elected in a higher term and accepts new writes. The old leader, still believing it is leader, serves reads from its stale state. A client reading from it sees old data, violating linearizability (Chapter 28), the guarantee that a read reflects every write that completed before it started.

There are two standard fixes:

ReadIndex (confirm leadership with a heartbeat)

  1. The leader records its current commit index as the read index. (First it must have committed an entry from its own term, which the start-of-term no-op provides.)
  2. It sends a round of heartbeats and waits for acknowledgements from a majority. That proves no higher-term leader existed at the moment the read arrived.
  3. It waits until its state machine has applied entries up to the read index.
  4. It serves the read from the state machine.

Cost: one heartbeat round trip, but no disk writes and no log growth, and many reads can share one heartbeat round. etcd uses this by default for linearizable reads.

Leader leases (time-based)

If the leader may assume that no other leader can be elected during a fixed interval, it can skip the heartbeat round. Every time a majority acknowledges a heartbeat, the leader extends a lease: "I am safely leader until time T." Followers promise not to vote for anyone else until their own election timeout elapses. So within the lease the leader serves reads straight from its state, with no network round trip at all. The price is a clock assumption: the lease is only safe if clocks run at roughly the same rate (bounded drift) on leader and followers. If the leader's clock runs slow, it may believe its lease is still valid after the followers' timers have expired and a new leader has been elected. Production systems using leases (Spanner with TrueTime, TiKV, CockroachDB) subtract a safety margin for clock drift. Section 12 returns to this tradeoff.

12. Paxos, Multi-Paxos and how they relate to Raft

Paxos, devised by Leslie Lamport (first circulated around 1989, published 1998), is the original practical consensus algorithm and is famously hard to understand. Raft was created partly because people found Paxos too hard to implement correctly from the paper. The two have the same fundamental guarantees and the same 2f + 1 requirement.

12.1 Single-decree Paxos

Basic Paxos agrees on one value. It has three logical roles (often all played by the same machines): proposers, acceptors and learners. It works in two phases, using proposal numbers that are unique and increasing (like Raft terms):

  1. Phase 1 (prepare). A proposer picks a number n and sends Prepare(n) to the acceptors. Each acceptor that has not already promised a higher number replies with a promise: it will ignore proposals numbered below n, and it reports the highest-numbered proposal it has already accepted, if any.
  2. Phase 2 (accept). If the proposer gets promises from a majority, it sends Accept(n, v). The value v is forced: if any acceptor reported a previously accepted value, the proposer must propose the value from the highest-numbered such proposal, not its own. Only if none reported one may it choose freely. Acceptors accept unless they have since promised a higher number.
  3. When a majority has accepted, the value is chosen.

The "forced value" rule is the safety mechanism, and it uses the same overlap argument as Raft: any new proposer's prepare quorum overlaps the quorum that accepted an earlier value, so it will learn about that value and re-propose it instead of choosing a different one.

12.2 Multi-Paxos

A real system needs a sequence of values, a log. Running a full two-phase Paxos per entry would cost two round trips each. Multi-Paxos elects a stable distinguished proposer (a leader) that runs phase 1 once for all future log slots, and thereafter only runs phase 2 per entry, one round trip, exactly like Raft's AppendEntries. The original papers left many details unspecified (leader election, log gaps, membership change, snapshots), so every implementation filled them in differently. Google's Chubby and Spanner, and Apache Cassandra's lightweight transactions (single-decree Paxos per key), use Paxos variants.

12.3 Zab, Viewstamped Replication and relatives

  • Zab (ZooKeeper Atomic Broadcast) is the protocol under Apache ZooKeeper. Like Raft it is leader-based: a leader orders all state changes into a stream of transactions and broadcasts them, and a new leader goes through a synchronisation phase to bring followers in line before serving. It was designed for ZooKeeper's needs: primary-backup ordering so that updates from one client are applied in order.
  • Viewstamped Replication (VR), by Oki and Liskov (1988), predates Paxos publication and is remarkably similar to Raft: a primary, numbered views (like terms), a log, and a view-change protocol when the primary fails. The revised 2012 version is quite readable, and Raft's authors acknowledge the kinship.
  • Others you may hear: EPaxos (leaderless, lets non-conflicting commands commit in one round trip from any replica), Fast Paxos, Flexible Paxos (the insight that phase-1 and phase-2 quorums only need to intersect each other, not be majorities).
Interview tip You are rarely expected to recite Paxos message formats. A strong answer says: "Raft and Multi-Paxos are equivalent in guarantees. Raft is Multi-Paxos with leader election, log shape and membership change spelled out, which is why most new systems pick it." Then show you can explain Raft concretely.

13. Leader election as a use of consensus: leases, clocks, split-brain and fencing

Raft elects its own leader internally. But consensus also provides a general service to other applications: "elect one primary among my workers." Think of a cluster of job schedulers where exactly one should be active, or a database with one primary. Rather than every application implementing Raft, they use a consensus-backed store (etcd, ZooKeeper, Consul) and a simple pattern: try to create a key or lock with a lease (a time-limited ownership). Whoever succeeds is the leader. It must keep renewing the lease with periodic heartbeats. If it stops (crashes or hangs), the lease expires and another candidate takes over. Chapter 30 covers the exact recipes in ZooKeeper, etcd and Consul.

13.1 Leases and clock assumptions

A lease is a lock with an expiry. It solves the problem that you can never tell a dead owner from a slow one: if the owner does not renew in time, everyone treats it as dead and the lease can be granted to someone else. But leases depend on time, and this is where subtle bugs hide:

  • The lock service grants a lease of 10 seconds according to its clock. The client measures 10 seconds on its clock. If the client's clock runs slow relative to the service, it believes the lease is valid after it has actually expired.
  • More dangerous, the client may be paused (a long garbage collection, a VM freeze, a stalled process) after checking its lease and before acting on it. When it wakes it believes it is still leader and writes to the database, while a new leader has been active for seconds.

Chapter 27 discusses clock skew, drift and monotonic versus wall clocks. The takeaway: a lease can tell a node "you should stop acting as leader soon" but can never by itself guarantee that the old leader has actually stopped, because the old leader can be asleep.

13.2 Split-brain

Split-brain is when two nodes both believe they are the leader and both accept writes, so the data diverges. It is the nightmare failure of any primary-backup system. Typical causes: a network partition where each side promotes its own primary, a failover tool that promotes a replica while the old primary is merely slow, or a lease expiring while the owner is paused. Consensus prevents split-brain in its own state via majority quorums and terms: the minority side of a partition simply cannot commit anything. But an external resource (a database, a file store) that does not take part in the consensus protocol can still be written to by a stale leader. That is the gap that fencing closes.

13.3 Fencing tokens

The robust fix is a fencing token: a monotonically increasing number issued with each lease grant (the Raft term, ZooKeeper's zxid or a lock's version number all work). The leader attaches its token to every request it sends to the protected resource. The resource remembers the highest token it has seen and rejects any request with a lower token. Now the paused old leader wakes up, sends a write with token 33, and the storage that has already seen token 34 from the new leader refuses it.

Watch out A lock or lease without fencing, protecting a resource that cannot check tokens, is only an efficiency optimisation, never a correctness guarantee. Use it to avoid duplicated work (two workers doing the same job is wasteful but harmless), not to protect data that must never be written twice. See Chapter 30 for lock pitfalls and the Redlock debate.

Also note that Raft itself behaves like a fencing system: a deposed leader with an old term has its AppendEntries rejected by followers who have moved to a higher term, and cannot commit anything because it cannot reach a majority. The stale leader is harmless to the replicated state, even though it may think it is leader for a while.

14. Performance: batching, pipelining and cluster size

The cost of a consensus write is bounded by: one network round trip from the leader to a majority (the slowest of the fastest quorum), plus a disk fsync on the leader and on those followers. Everything beyond that is optimisation.

  • Batching. The leader collects many client commands that arrive during a short window and puts them into one AppendEntries message and one fsync. One disk flush and one network round trip are amortised across hundreds of commands, so throughput climbs dramatically at the price of a tiny added latency.
  • Pipelining. Instead of waiting for acknowledgement of message 1 before sending message 2, the leader streams several AppendEntries without waiting, tracking per-follower progress. This keeps the network pipe full and hides round-trip latency. Followers still process in order.
  • Parallel disk and network. The leader can send entries to followers while it writes its own disk, since it only needs a majority to be durable in total.
  • Group commit and fast storage. fsync latency dominates in the same data center, so SSDs or NVMe (and avoiding noisy neighbours on the disk) matter more than CPU. etcd's documentation stresses disk write latency as the top performance factor.
  • Sharding the consensus. One Raft group has one leader and so a throughput ceiling. Large systems run many independent groups (one per data range, as in CockroachDB, TiKV and Spanner) and spread leaders over machines. See Chapter 25.

14.1 Why 3 or 5 nodes

Adding nodes does not add write throughput, it reduces it: the leader must send every entry to more followers and wait for a larger quorum, so the commit time is set by a slower node. Larger clusters buy only more fault tolerance. Three nodes tolerate one failure and cover most needs. Five tolerate two, which lets you take one node down for maintenance and still survive a surprise failure, and is common for critical metadata stores. Beyond five, the cost rises with little real-world benefit, since correlated failures (a whole rack or availability zone) are a bigger risk than independent ones. If you need more read capacity, add non-voting learners or read replicas that do not participate in the quorum.

14.2 Cross-region consensus latency

If replicas are in different regions, the commit latency is the round trip to the closest majority, not to the farthest node. This makes placement decisive.

This is why globally distributed databases take care over leader placement (put the leader near most writers, as Spanner's leader preferences and CockroachDB's leaseholder placement do) and why a three-region deployment with one replica in each region has 50-100+ ms write latencies that single-region apps never see. Designs that must keep writes fast across continents either accept that cost, partition data by region so that each partition's replicas are local (Chapter 26), or give up strong consistency for some data (Chapter 28).

16. Byzantine fault tolerance, briefly

Everything above assumes crash-fault behaviour: nodes may stop or be slow, but they do not lie. A Byzantine fault is when a node behaves arbitrarily: sends conflicting messages to different peers, forges data, or runs malicious code, because of bugs, corruption or an attacker. Byzantine fault tolerance (BFT) protocols tolerate this.

  • Cost in nodes. To tolerate f Byzantine nodes you need 3f + 1 replicas (not 2f + 1), and quorums of 2f + 1, so any two quorums overlap in at least f + 1 nodes, guaranteeing at least one honest node in the overlap. Tolerating one traitor needs four nodes.
  • PBFT (Practical Byzantine Fault Tolerance, Castro and Liskov, 1999) was the first practical protocol. A primary proposes an order; replicas go through pre-prepare, prepare and commit phases with all-to-all messages, with a view change if the primary misbehaves. Message count grows with the square of the replica count, so it only suits small groups. Modern descendants such as HotStuff reduce the communication to linear and underlie several blockchain systems.
  • Blockchains. Public blockchains must tolerate anonymous, possibly malicious participants. Bitcoin uses proof-of-work with the longest-chain rule, which gives probabilistic agreement rather than immediate finality. Proof-of-stake chains use BFT-style voting among staked validators for fast finality.

Almost all data center systems (databases, coordination services) deliberately do not use BFT. You trust your own machines and network, and BFT costs more nodes, more messages and much more complexity. BFT is for adversarial multi-party settings: cryptocurrencies, consortium ledgers, and some safety-critical aerospace systems. Say this in an interview to show you know when the extra cost is not warranted.

19. Worked example: a 5-node cluster surviving failures

A configuration store runs on five nodes S1 to S5 in three availability zones (S1, S2 in zone a; S3, S4 in zone b; S5 in zone c). Majority is 3. We follow it through a series of failures. The current term is 7, S1 is leader, and the log is committed through index 100.

19.1 Stage by stage

  1. Normal operation. S1 is leader of term 7. A client writes config/limit=500. S1 appends it at index 100, sends AppendEntries, S2 and S3 acknowledge, so 3 of 5 hold it. It commits and the client gets OK after one round trip plus fsync (about 2 to 5 ms within a region).
  2. Leader crash. S1 crashes while it has just appended index 101 locally and has sent it to nobody. The followers' election timeouts (say 1 second) expire at slightly different times because of the random jitter. S3 times out first at 1.12 s, becomes candidate for term 8, and asks for votes. S2, S4, S5 compare logs: S3's last entry is index 100, term 7, which is at least as up to date as theirs, so they grant it. S3 wins with 4 of 5 votes (itself plus three) and becomes leader. It appends a no-op to commit the term. Writes were paused for around 1.2 seconds. The client's write of index 101 was never acknowledged, so it times out, retries, and the retry is applied once.
  3. A second failure. S2 crashes. Now 3 nodes are alive: S3, S4, S5. That is exactly a majority, so the cluster still commits, but there is no spare. Operators would see alerts and replace nodes urgently, because one more failure stops the cluster.
  4. Third failure. A network fault isolates S5. Now S3 and S4 are alive and connected, only 2 of 5. S3 cannot gather 3 acks, so no new entry commits, and it steps down or stays leader without ability to commit. All writes and linearizable reads fail with timeouts. Importantly, nothing wrong is ever served. Hitting this state means the failure budget (f = 2) was exceeded.
  5. Recovery. S5 reconnects, so S3, S4, S5 are a majority again. S1 restarts and its log has index 101 of term 7 (never committed), but S3's log at index 101 is its term-8 no-op. In the first AppendEntries the consistency check fails at index 101, the leader backs up to the match at 100, and S1 deletes its conflicting entry and copies the leader's. Commits resume. No acknowledged write was lost.

19.2 What the partition variant looks like

Suppose instead S4 and S5 are cut off from {S1, S2, S3} while S1 is leader. The majority side (3 nodes) keeps working with no election at all. S4 and S5 time out, repeatedly start elections in rising terms, but each reaches only 2 votes, so they never win. With pre-vote enabled they would not even increment their terms. When the partition heals, S4 and S5 accept S1 as leader and catch up. Had S1 been on the minority side, it would keep receiving client writes but could not commit them, while the majority side elected a new leader in a higher term. When healed, S1 sees the higher term, steps down, and discards its uncommitted entries.

19.3 Capacity numbers

Take a metadata cluster handling 5,000 writes per second with 1 KB entries. Each write must be replicated to 4 followers (the leader still sends to all and counts the first two acks), so the leader sends about 5,000 × 4 × 1 KB = 20 MB/s of replication traffic, trivial for a modern NIC. The real limit is fsync: with 1 ms fsync and no batching, one disk handles about 1,000 sequential commits per second, so 5,000 writes per second is only reachable with batching (for example 20 commands per fsync, giving 250 fsyncs per second). That is why batching is the first optimisation in every production Raft implementation.

20. Interview Q&A

What problem does consensus solve, and why can't we just use one database server?

Consensus lets a group of machines agree on a single value or an ordered log even when some machines crash and messages are lost or delayed. A single server is a single point of failure: if it dies, the system is down, and if its disk is lost, data is gone. Replicating naively does not help because replicas can disagree about order after failures. Consensus gives you replicas that stay identical and continue to work as long as a majority survives, so you keep both availability under minority failures and strong consistency.

Explain the FLP result and why Raft works anyway.

FLP proves that in a fully asynchronous system, where message delays and process speeds have no bound, no deterministic algorithm can guarantee consensus terminates if even one process can crash, because you cannot distinguish a crashed node from a very slow one. Raft works because it keeps safety unconditionally, so it never decides two different values, and only needs timing assumptions for liveness. It uses timeouts as failure detectors and randomised election timeouts to break symmetry, so in a normal network it elects a leader quickly. In pathological timing it may stall, but it stalls safely.

Why do consensus clusters need 2f + 1 nodes, and why are odd sizes preferred?

To keep running with f failures, a quorum of size at most N minus f must suffice, but quorums must also be majorities so any two overlap and no two sides can decide independently. Both hold exactly when N is 2f + 1. An even size like four tolerates only one failure, the same as three, but requires three acknowledgements for each write, so you pay more for no extra tolerance. Furthermore, an even-sized cluster can split into two equal halves where neither has a majority, which stalls progress.

Walk me through a Raft leader election and why randomised timeouts matter.

Followers expect periodic heartbeats. When one does not hear from a leader for its election timeout, it increments its term, becomes a candidate, votes for itself and sends RequestVote to all. Each server votes for at most one candidate per term, and only if the candidate's log is at least as up to date as its own. A candidate with a majority becomes leader and sends heartbeats. If two candidates split the vote, nobody wins and they time out and retry. Randomising the timeouts means one node nearly always times out first and wins before others even start, so split votes are rare and resolve quickly.

How does Raft guarantee that a committed entry is never lost?

An entry is committed once a majority has stored it. A new leader must win votes from a majority, and the election restriction says a voter rejects any candidate whose log is less up to date than its own. Since any two majorities overlap, at least one voter has the committed entry and will only vote for a candidate that also has it. So every possible leader contains all committed entries, and since leaders only append and followers are brought into line with the leader's log, a committed entry is never overwritten.

A leader is partitioned away from the rest of the cluster. What happens to clients that are talking to it?

The old leader keeps accepting writes and appending them, but it cannot get acknowledgements from a majority so nothing it accepts gets committed, and it never tells those clients that the writes succeeded. Meanwhile the majority side times out, elects a new leader in a higher term, and carries on. When the partition heals the old leader receives a message with a higher term, steps down, and its uncommitted entries are overwritten by the new leader's log. For reads, a naive implementation could serve stale data from the old leader, which is why linearizable reads use ReadIndex or a lease to confirm leadership.

How do you perform a linearizable read in Raft without writing to the log?

With ReadIndex, the leader notes the current commit index, confirms it is still leader by exchanging a heartbeat round with a majority, waits for its state machine to apply up to that index, and then answers from local state. Because it proved leadership after the read request arrived, no newer write can have been committed by another leader. The alternative is a leader lease, where the leader skips the heartbeat round while its lease is valid, trading a round trip for a dependence on bounded clock drift. Reading from followers is cheaper but only gives stale, non-linearizable results.

How does Raft differ from Paxos, and which would you pick?

They give equivalent guarantees and both need a majority quorum. Basic Paxos decides a single value with a prepare and an accept phase, and Multi-Paxos extends it to a log by electing a stable leader that runs the first phase once. Raft specifies the complete system, with strong leadership, a contiguous log, log-aware election, membership changes and snapshots, so it is much easier to implement and reason about. I would choose Raft, via a proven library like etcd's, unless I had a specific reason, such as a leaderless design like EPaxos or compatibility with an existing Paxos system. I would almost never hand-roll either.

What is split-brain and how do fencing tokens prevent damage from it?

Split-brain is when two nodes both believe they are the leader and both write, causing divergent data. Consensus prevents it within its own replicated state, because the side without a majority cannot commit. But an external resource can still be written by a stale leader that was paused and woke up after its lease expired. A fencing token, a number that increases with each lease grant such as the Raft term, is attached to every write, and the resource rejects any token lower than the highest it has seen. That means even a stale leader cannot corrupt the data, which is something timeouts and leases alone can never guarantee.

Why not make a consensus cluster bigger, say 9 nodes, to be safer, or for more throughput?

Bigger clusters do not increase write throughput because each write still goes through a single leader that must replicate to everyone and wait for a larger quorum, so latency and leader load go up. They tolerate more simultaneous failures, but in practice correlated failures such as a zone outage are the real risk, and five nodes spread across three zones handle that case. If you need more read capacity, add learners or read replicas that are outside the quorum. If you need more write throughput, shard the data into many consensus groups rather than growing one group.

When would you use Byzantine fault tolerance instead of Raft?

Only when participants may be malicious or may behave arbitrarily, for example a public blockchain or a ledger shared by mutually distrusting organisations. BFT needs 3f + 1 replicas to tolerate f traitors and exchanges many more messages than crash-fault protocols. Inside one company's data center, you trust your own nodes and the failure mode is crash or slowness, so a crash-fault protocol like Raft is cheaper, faster and simpler. Bugs that corrupt a node's data are usually handled with checksums and replacing the node rather than a BFT protocol.

How does cross-region deployment affect consensus latency, and how do you design around it?

Each commit needs a round trip from the leader to enough replicas to form a majority, so latency is set by the nearest majority, not by the farthest replica. A five-replica deployment across continents therefore pays something like tens to hundreds of milliseconds per write, depending on where the leader sits. You design around it by placing the leader near the writers, choosing replica placement so that a nearby majority exists, partitioning data by region so each partition's replicas are local, and using bounded-stale follower reads for data that does not need to be linearizable.

21. Recap

  • Consensus makes unreliable machines agree on a value or an ordered log. Replicated state machines apply the same log in the same order, giving fault-tolerant, consistent services.
  • FLP says liveness cannot be guaranteed in a fully asynchronous system with failures. Real protocols keep safety always and need timing, timeouts and randomisation only for liveness.
  • A majority quorum of N = 2f + 1 nodes tolerates f failures, and any two majorities overlap, which carries earlier decisions into later ones. Use 3 or 5 nodes. Even sizes are wasteful.
  • Raft: followers, candidates, leaders; terms as a logical clock; one vote per term; randomised election timeouts; AppendEntries replication; commit on majority; election restriction ensures leaders hold every committed entry; log repair overwrites divergent followers.
  • Membership changes go one server at a time (or joint consensus). Snapshots compact the log and bring slow followers up to date. Clients use sessions for exactly-once effects. Linearizable reads use ReadIndex or leases.
  • Paxos and Multi-Paxos are equivalent in guarantees. Raft specifies the whole system. Zab and Viewstamped Replication are close relatives.
  • Leases give time-bounded leadership but depend on clocks and cannot stop a paused old leader. Fencing tokens (terms) make the protected resource reject stale leaders. Split-brain is prevented by quorums plus fencing.
  • Performance comes from batching and pipelining. Commit latency is the round trip to the nearest majority, so leader placement matters across regions. More nodes means more fault tolerance, not more throughput.
  • Without a majority the system stops safely. BFT needs 3f + 1 nodes and is for adversarial settings. etcd, Consul, ZooKeeper, Spanner, CockroachDB and Kafka KRaft all rest on these ideas.
