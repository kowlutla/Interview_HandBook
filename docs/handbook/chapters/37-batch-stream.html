Batch and Stream Processing

Most systems eventually need to compute over huge amounts of data: daily reports, click counts, fraud scores, search indexes. This chapter explains how batch engines (MapReduce, Spark) and stream engines (Flink, Kafka Streams, Spark Structured Streaming) work inside, how they handle state, time, late data and failures, and how to design a pipeline that gives correct numbers.

1. Batch, stream, micro-batch: the basic tradeoff

Data processing starts with one question: when do we compute the answer? There are two honest answers. Either we wait until a large pile of data has collected and then process the whole pile at once, or we process each piece of data as soon as it arrives. Everything in this chapter is a consequence of that choice.

1.1 Batch processing

A batch job reads a bounded input (a fixed set of files or a table snapshot, for example "all click events for yesterday"), computes a result, writes it out, and then ends. Because the input is finite and does not change while the job runs, the job can be planned globally: the engine knows how big the data is, can sort it, can retry any piece, and can use the whole cluster at full speed. Batch is optimized for throughput (how much data per hour per dollar), not for how quickly one record shows up in the result. Typical latency is minutes to hours.

1.2 Stream processing

A stream job reads an unbounded input: events keep arriving forever, and the job never finishes. It keeps long-running workers alive, processes each event (or a tiny group of events) as it arrives, and continuously updates its output. Stream is optimized for latency: results appear in milliseconds to seconds. The price is complexity. The engine cannot see "all the data", so it must reason about time, out-of-order arrivals, and state that survives failures.

1.3 Micro-batch: the middle road

Micro-batching treats a stream as a rapid series of tiny batch jobs. Every, say, 2 seconds the engine collects whatever arrived, runs a small batch computation on it, and emits the result. It inherits batch engine simplicity (retry a small batch if it fails) and gets latency in the seconds range. Spark Streaming and Spark Structured Streaming's default mode work this way. Flink and Kafka Streams instead process record at a time (true streaming) with latencies in the tens of milliseconds.

If it is "a dashboard that updates every few seconds" or "block fraud before the payment completes", say stream. Naming the freshness requirement first shows you pick technology from requirements.

2. MapReduce: the model that started it

Before Spark and Flink, there was MapReduce, published by Google in 2004 and popularized by Hadoop. Its importance today is mostly as a mental model: every modern engine still does "process pieces in parallel, regroup by key, process each group". It is worth understanding in detail because the same shuffle step is the main cost in Spark and in streaming joins.

2.1 The three phases

  1. Map. The input is split into chunks (often one per file block, 128 MB typical). Each chunk is given to a mapper task, which reads records and emits zero or more key-value pairs. Mappers know nothing about each other, so they can run on thousands of machines in parallel, preferably on the machine that already holds the data (data locality) so the input does not cross the network.
  2. Shuffle (and sort). The framework takes all the pairs from all mappers and routes them so that all pairs with the same key land on the same reducer. A hash of the key modulo the number of reducers decides the destination. Each mapper writes its output to local disk, partitioned by destination reducer; each reducer then pulls its partition from every mapper over the network and merges the sorted runs. This is the expensive step: it is an all-to-all network transfer plus disk writes and sorting.
  3. Reduce. Each reducer receives, for each key it owns, the key and the list of all values, and emits a result. Because every value for a key is in one place, the reducer can total, join, or deduplicate them.

2.2 Word count walkthrough

Count words in two lines of text: line A is "to be or not to be", line B is "be quick". Two mappers each take one line.

  • Mapper 1 emits (to,1) (be,1) (or,1) (not,1) (to,1) (be,1).
  • Mapper 2 emits (be,1) (quick,1).
  • With two reducers and a hash partitioner, suppose reducer 1 owns {to, or, quick} and reducer 2 owns {be, not}. Shuffle sends (to,1),(to,1),(or,1),(quick,1) to reducer 1 and (be,1)x3,(not,1) to reducer 2.
  • Reducer 1 outputs (to,2) (or,1) (quick,1). Reducer 2 outputs (be,3) (not,1).

An optimization is the combiner: a mini-reduce run on each mapper's own output before the shuffle. Mapper 1 can collapse its pairs to (to,2) (be,2) (or,1) (not,1), so six pairs become four and less data crosses the network. Combiners only work for operations that can be merged in any order and grouping (sum, max, count; not average, unless you carry sum and count separately).

2.3 Fault tolerance

MapReduce runs on commodity machines that fail constantly, so failure handling is built into the model rather than added on top. Tasks are deterministic and side-effect free and their inputs are immutable files in a distributed file system (HDFS, or object storage). Therefore:

  • If a mapper dies, the scheduler simply runs the same split on another machine. Its output was only on local disk, so any finished map output on a dead machine is also recomputed.
  • If a reducer dies, a new one is started and re-fetches its partition from all mappers.
  • Final output is written to a temporary path and atomically renamed on success, so a retried task cannot leave half-written duplicates.
  • If the coordinator (job master) dies, the job is restarted or resumed from its recorded state.

The cost of this safety is that every stage in a multi-stage pipeline writes its output to disk (and, for the final results, replicated storage) before the next stage reads it. That is why chained MapReduce jobs are slow, and why Spark's in-memory approach was a big step forward.

2.4 Stragglers and speculative execution

A job finishes only when its slowest task finishes. A straggler is a task that runs much longer than its peers because of a failing disk, a noisy neighbor, a bad network link, or data skew (one task has far more data). With 10,000 tasks, a few stragglers are nearly guaranteed. The standard remedy is speculative execution: when most tasks are done, the scheduler launches a duplicate of each remaining slow task on another machine and takes whichever copy finishes first, discarding the other. This works because tasks are deterministic and idempotent. It cannot fix straggling caused by key skew (the duplicate gets the same oversized input), which needs the techniques in section 3.6.

Watch out Speculative execution doubles work for the tasks it duplicates. If a task writes to an external system (a database insert, an API call), two copies mean two writes. Side effects inside map and reduce functions break the whole fault-tolerance model; write results to files and publish them in a separate, idempotent step.

3. Spark: in-memory, DAG-based batch

Apache Spark keeps the MapReduce idea (parallel tasks over partitions, with shuffles for regrouping) but removes two limits. First, it describes a job as a whole graph of operations, so it can optimize and pipeline several steps without writing intermediate results to storage after each one. Second, it can keep working data in memory between steps, which makes iterative algorithms and interactive queries far faster.

3.1 RDDs and DataFrames

The original abstraction is the RDD (Resilient Distributed Dataset): an immutable collection of records split into partitions spread across the cluster. "Resilient" means that if a partition is lost, Spark can rebuild it because the RDD remembers its lineage: the recipe of transformations that produced it from its source data. No replication of intermediate data is needed; recomputation from lineage is the recovery mechanism.

The modern API is the DataFrame (and typed Dataset): a distributed table with named, typed columns, queried through SQL-like operations. Because Spark understands the schema and the operations, its Catalyst optimizer can reorder filters before joins, prune unused columns, push predicates down into Parquet files, and choose join strategies, then generate efficient code. In practice you almost always use DataFrames or SQL, and drop to RDDs only for logic that cannot be expressed relationally.

3.2 Lazy evaluation and the DAG

Spark operations come in two kinds. Transformations (filter, map, join, groupBy) do not run anything; they only add a step to a plan. Actions (count, collect, write) trigger execution. This lazy evaluation lets Spark see the entire plan, build a DAG (directed acyclic graph) of stages, optimize it, and run it as one job. It also means a typo or an expensive step does not fail until the action runs, which surprises beginners.

3.3 Narrow and wide dependencies

The key to Spark performance is the difference between two dependency types.

  • A narrow dependency means each output partition depends on a single input partition (map, filter, a projection). These steps run inside the same task on the same machine, pipelined record by record, with no network traffic.
  • A wide dependency (a shuffle) means each output partition depends on many input partitions (groupBy, reduceByKey, join of two unpartitioned datasets, distinct, repartition). Data must move across the network, so Spark ends one stage and begins another at every wide dependency. Stage boundaries are shuffle boundaries.

3.4 Why shuffles cost so much

A shuffle writes data to local disk on the sending side, sends it over the network to the receiving side, and reads it back, with serialization and often sorting on both ends. It also forms a barrier: the next stage cannot start until all tasks of the previous stage finish, so stragglers hurt. A job's runtime is often well approximated by the bytes shuffled divided by cluster network and disk bandwidth. Practical ways to cut shuffles:

  • Filter and project early so fewer bytes are shuffled (Catalyst does much of this automatically).
  • Pre-aggregate before the shuffle: reduceByKey and DataFrame aggregates combine values inside each partition first (a combiner), whereas a naive groupByKey ships every record.
  • Broadcast join: if one side is small (tens to a few hundred MB), send a copy of it to every executor and join locally, avoiding a shuffle of the large side entirely.
  • Partition once, reuse: if two datasets are already partitioned by the same key and the same number of partitions, a join between them needs no further shuffle (bucketed tables use this).

3.5 Partitioning

The number of partitions sets the parallelism. Too few partitions means idle cores and tasks too big for memory; too many means scheduling overhead for thousands of tiny tasks. A common rule is two to four partitions per CPU core, with each partition holding roughly 100-200 MB. The default shuffle partition count in Spark SQL is 200, which is wrong for both small and very large jobs, so it is worth setting deliberately (or using adaptive query execution, which merges small shuffle partitions at run time).

3.6 Data skew

Skew means the keys are not evenly distributed, so a few partitions get most of the data. In click data, one viral ad or a null key might hold 40% of all rows. The reducer owning that key becomes a straggler that runs for an hour while the other 199 finish in a minute, and it may run out of memory. Remedies:

  • Salting. Append a random suffix (0 to N-1) to the hot key to spread it over N partitions, aggregate by (key, salt), then aggregate again by key alone. The two-step aggregation works for sums and counts. For a join, replicate the small side N times, once per salt value.
  • Isolate hot keys. Handle the few known heavy keys with a broadcast join and the rest with a normal one.
  • Filter nulls and junk keys first; "null" and "unknown" are the most common accidental hot keys.
  • Adaptive query execution can detect skewed shuffle partitions at run time and split them automatically for joins.

3.7 Caching and persistence

Because of lazy evaluation, if you use the same DataFrame in two actions, Spark recomputes it from the source each time. Calling cache() or persist() asks Spark to keep the computed partitions in memory (optionally spilling to disk) the first time they are produced. Cache when a dataset is reused several times and is expensive to compute, such as in iterative machine learning or when one cleaned dataset feeds many reports. Do not cache data used once; it wastes memory and can evict useful data. Remember to unpersist when done. Cached data lost with an executor is simply recomputed from lineage.

3.8 Spark's fault tolerance

If an executor dies, Spark reruns the lost tasks. For narrow dependencies only the lost partition's lineage is replayed, which is cheap. For a lost shuffle output, the stage that produced it must be rerun for the missing pieces, which can cascade through a long lineage. For very long jobs or iterative loops, checkpointing an RDD to reliable storage truncates the lineage so recovery does not replay everything from the start. An external shuffle service keeps shuffle files available even if the executor that wrote them is gone.

4. Stream processing engines

Stream processors apply the same ideas continuously. A streaming job is a graph of operators (read from a source, filter, key by some field, aggregate, write to a sink). It is deployed as long-running parallel tasks, each handling a subset of the input partitions or of the key space. The source is usually a durable, replayable log such as Kafka (see Chapter 34), which matters enormously for recovery, as section 5 shows.

4.1 Apache Flink

Flink is a true record-at-a-time engine with first-class support for event time, large managed state, and exactly-once state consistency. A Flink cluster has a JobManager (coordinator: schedules tasks, triggers checkpoints, handles recovery) and many TaskManagers (workers with task slots). Records flow between operators through network buffers with credit-based flow control, which is also what produces backpressure (section 9). It is the usual choice when you need low latency, big state (terabytes), complex time-based logic, or event-time windows with late data handling.

4.2 Kafka Streams

Kafka Streams is a library, not a cluster. You embed it in an ordinary Java application and run as many instances as you like. It uses Kafka itself for input, output, state changelogs and coordination, and the Kafka consumer group protocol to spread partitions across instances. State is held in local RocksDB stores backed by compacted Kafka changelog topics. It supports exactly-once processing within Kafka (reads, state updates and writes committed atomically with Kafka transactions). Pros: no separate cluster to operate, simple deployment. Cons: Kafka-to-Kafka oriented, and scaling is bounded by the number of input partitions.

4.3 Spark Structured Streaming

Structured Streaming lets you write the same DataFrame query you would write for batch, and runs it incrementally, by default as micro-batches (with an experimental continuous mode for lower latency). It supports event-time windows, watermarks, stateful aggregations and joins, and exactly-once output with idempotent or transactional sinks and checkpointed offsets. It is attractive when a team already uses Spark, wants to share code between batch and streaming, and can accept latency of about a second or more.

4.4 Stateless versus stateful operations

A stateless operation (filter, map, parse JSON) looks at one record at a time and needs nothing remembered, so it scales trivially and recovery is simple. A stateful operation (count per key, window aggregate, deduplicate, join two streams) needs memory of past records. State is where almost all of the difficulty of stream processing lives, so the next section is devoted to it.

5. State, state backends and checkpoints

5.1 Keyed state

Stream engines partition state by key. After a keyBy(ad_id) step, all events with the same ad_id are routed (by hash) to the same parallel task, and that task holds the counter, the window buffers, or the dedup set for those keys in local storage. Because each task only touches its own keys, there are no locks and no remote lookups: this is the same shuffle-by-key idea as MapReduce, applied continuously. It also means parallelism is capped by the number of distinct keys and skewed by hot keys.

5.2 State backends

The state backend decides where that local state physically lives:

  • In-memory (heap) backend. State is objects in the JVM heap. Extremely fast, but limited by memory, and large state causes long garbage collection pauses. Fine for small state, such as counters for a few thousand keys.
  • RocksDB backend. State is stored in an embedded RocksDB key-value store (an LSM tree, see Chapter 19) on local SSD, with a memory cache. It handles state far larger than memory (hundreds of GB per task) at the cost of serialization on each access, so it is several times slower per access than heap. It also supports incremental checkpoints, uploading only files changed since the last checkpoint.

State is local for speed, but local disks are lost when a machine dies. So the engine must also persist copies elsewhere, which is the job of checkpoints.

5.3 Checkpoints and barriers

A checkpoint is a consistent snapshot of the entire job: the state of every operator plus the position in the input (for Kafka, the offset of each partition) at one logical instant. Taking a consistent snapshot of a distributed, continuously running system without stopping it is done with the Chandy-Lamport idea, which Flink implements with barriers:

  1. The coordinator tells every source to start checkpoint number N.
  2. Each source records its current input offset, then injects a special barrier N marker into its output stream between two records. Everything before the barrier belongs to checkpoint N; everything after belongs to later ones.
  3. Barriers flow through the graph with the data. When an operator receives barrier N on all its input channels, it snapshots its state (asynchronously, to durable storage such as object storage) and forwards the barrier. If one input is faster, the operator aligns: it holds back records from channels whose barrier has already arrived until the slower channels catch up, so the snapshot contains exactly the records before the barrier on every channel. (Newer versions offer unaligned checkpoints that put in-flight records into the snapshot to avoid alignment stalls under backpressure.)
  4. When every operator, including the sinks, has acknowledged barrier N, the coordinator marks checkpoint N complete.

5.4 Recovery and exactly-once state semantics

When a task or machine fails, the engine stops the job, restores every operator's state from the last completed checkpoint, rewinds the sources to the saved offsets, and resumes. Records processed after the checkpoint are processed again, but because the state was also rolled back to the same instant, each record affects the state exactly once in the final result. Precisely, this is "exactly-once state semantics": the engine guarantees its internal state looks as if every record was applied once, even though some records were physically processed twice. It does not by itself guarantee that an external system (a database, an email, a Kafka output topic) saw each effect once. That is the end-to-end problem in section 11.

Checkpoint interval is a tradeoff. Frequent checkpoints (every few seconds) mean less to replay and faster recovery but more overhead and more load on the storage; infrequent ones (several minutes) are cheap but recovery replays a lot and exactly-once sinks hold output back longer. Tens of seconds to a couple of minutes is typical. A savepoint is a manually triggered, portable checkpoint used for planned upgrades, rescaling, or migrating a job.

Key idea Exactly-once in stream processing means: replayable source + snapshotted state + coordinated offsets. The log makes input replayable, the checkpoint makes state restorable to a known point, and the barrier makes both of those the same point. Without a replayable source, there is nothing to rewind to.

6. Time: event time, windows, watermarks, late data

6.1 Two clocks

Every event has two different times, and mixing them up is the most common source of wrong numbers in stream jobs.

  • Event time is when the thing actually happened, as recorded by the producer (a timestamp inside the click event, set by the phone or the web server).
  • Processing time is when the stream engine happens to see the event, by the wall clock of the machine running the job.

In a perfect network they would be almost equal. In reality they differ, by a variable amount: a phone goes through a tunnel and uploads its clicks three minutes later; a Kafka partition falls behind and its events are processed ten minutes after they happened; a deploy pauses the job for five minutes and then it races to catch up. If you count "clicks per minute" by processing time, then after the pause one minute appears to contain 10 minutes of clicks, and the result changes every time you replay the data. If you count by event time, the answer describes what really happened and is reproducible, but the engine now needs a way to know when it has seen all events for a given minute. That is what watermarks do.

6.2 Windows

An unbounded stream has no end, so you cannot compute "the total". Instead you cut it into finite pieces called windows and compute per window. The three standard kinds:

  • Tumbling window. Fixed size, no overlap, no gaps: 12:00-12:01, 12:01-12:02, and so on. Every event belongs to exactly one window. Used for "clicks per minute" and hourly counts.
  • Sliding (hopping) window. Fixed size that advances by a smaller step: a 5-minute window every 1 minute. An event belongs to size/step windows (five here), so state and output are several times larger. Used for moving averages and "errors in the last 5 minutes, refreshed every minute".
  • Session window. Not fixed in size: a session continues while events keep arriving within a gap (for example 30 minutes of inactivity), and closes after the gap passes with no event. Sizes differ per key, and a late event can merge two sessions into one. Used for user sessions.

6.3 Watermarks: when is a window complete?

With event-time windows, the engine must decide when it is safe to emit the result for the 12:00-12:01 window. Late events might still be in flight, and waiting forever is not an option. A watermark is the engine's moving estimate of event-time progress: "I believe I have now seen all events with timestamp less than W." Watermark W is carried through the stream as a special marker, much like a checkpoint barrier. When W passes the end of a window (W ≥ 12:01:00), the window is considered complete and fires.

The most common strategy is bounded out-of-orderness: watermark = (largest event time seen so far) minus a fixed delay such as 10 seconds. That says "events are at most 10 seconds out of order". If the largest event time seen is 12:01:12, then W = 12:01:02, so the 12:00 window fires and its result is emitted. An event with timestamp 12:00:55 arriving now is late (its window already fired), but one arriving with 12:01:05 is not.

The delay is a pure tradeoff between latency and completeness. A 1-second delay gives fast results but many late events; a 5-minute delay is almost complete but every result is five minutes stale. With several input partitions, an operator's watermark is the minimum over its inputs, so a single idle or slow partition stalls all windows. Engines therefore have an "idle source" timeout that excludes silent partitions from the minimum.

6.4 Late data: allowed lateness and side outputs

What happens to an event that arrives after its window fired? Three layered options exist, and a robust pipeline uses all of them.

  1. Allowed lateness. Keep the window's state for an extra period (say 5 minutes) after the watermark passes its end. If a late event arrives within that period, the engine updates the window and emits a corrected result (a "late firing"). Downstream systems must therefore accept updates to a result they already received, which means the sink should do upserts keyed by (key, window), not appends.
  2. Side output (dead-letter stream). Events later than even the allowed lateness are not silently dropped; they are routed to a separate output, such as a Kafka topic or a file. They can be counted (a metric for "late events dropped"), inspected, and fed to a corrective batch job.
  3. Periodic reconciliation. A nightly batch job recomputes the day from the raw log, which has every event regardless of lateness, and overwrites the stream's approximate numbers. This is the idea behind the Lambda architecture (section 12).
Watch out Watermarks are heuristics, not guarantees. A watermark that is too aggressive causes data to be classed as late; one that is too conservative delays all results. Producer clocks can be wrong (a phone with the date set to 2031 can push the watermark far into the future, if the max-timestamp strategy is used and nothing filters bad timestamps), so validate timestamps and clamp or reject outliers.

7. Joins in streams

Joining two datasets in batch is easy to reason about: both are finite, so you hash or sort them and match rows. In a stream, neither side ever ends, so the engine cannot hold "all rows" of either. There are three practical patterns.

7.1 Stream-stream join (windowed)

To join, for instance, ad impressions with ad clicks (match the click to the impression that caused it), both streams are keyed by the same id (for example impression id) so matching records reach the same task. Each side buffers its records in state for a bounded time window (say, clicks arrive within 30 minutes of the impression). When a record arrives, it is matched against the buffered records of the other side, and the join emits matches immediately. State for records older than the window (as judged by the watermark) is discarded. Without that time bound the state would grow forever, which is the most common way streaming joins run out of memory. Outer joins must wait until the window expires to know that no match came, so they emit later.

7.2 Stream-table join (enrichment)

Here one side is a stream of events (clicks) and the other is a slowly changing table (ad metadata: campaign, advertiser). Two ways to do it: look up each event in an external database or cache (simple, but adds a network call per event and can overload the store; use an async client plus a local cache), or load the table into the stream job as a changelog stream (a compacted Kafka topic of the table's changes, kept as local state), so enrichment is a local lookup with no remote call. The second approach is faster and replay-friendly: it gives the join result "as of" the event's time if the changelog is also time-aligned, whereas an external lookup always returns the table's current value, which makes reprocessing non-deterministic.

7.3 Broadcast of small data

If the table is small (a few thousand rules or country codes), broadcast it to every parallel task, which avoids routing by key. Updates to the table are themselves broadcast. This is the stream version of Spark's broadcast join.

Interview tip When asked to enrich a stream, mention the tradeoff directly: remote lookup is simple but couples throughput to the database and returns today's value on replay; a changelog-backed local state join is faster and deterministic, at the cost of extra state and a bootstrap phase.

8. Aggregation and top-K

The bread-and-butter streaming query is "group by key, window by time, aggregate". The aggregate function determines how cheap this is.

  • Incremental (algebraic) aggregates such as sum, count, min, max keep a tiny accumulator per (key, window): one integer for a count. Each event updates it in O(1) and the raw events can be discarded immediately. Average is kept as (sum, count). These are what you want.
  • Holistic aggregates such as exact median or exact distinct count need all values, so state grows with data. Use sketches instead: HyperLogLog for approximate distinct counts (about 12 KB for ~1% error, regardless of cardinality), t-digest or similar for percentiles, Count-Min Sketch for approximate frequencies.

8.1 Top-K

"Top 10 most-clicked ads in the last hour" looks simple and is surprisingly tricky at scale. A single global counter would be a hot spot, so the standard solution is two-level:

  1. Partition by ad_id and compute exact counts per (ad, window) in parallel, as above. Each partition then keeps its own local top-K (a small heap of K entries) for each window.
  2. Send only each partition's local top-K (K items, not millions) to a single global task, which merges them and produces the final top-K. This is correct because any ad in the global top-K must be in the top-K of the partition that owns it (each ad is owned by exactly one partition).

When ads may be split over partitions (because of salting, section 10), the counts must be combined before local top-K is taken, or the merge becomes approximate. For very large cardinality where even per-key counters are too heavy, algorithms such as Space-Saving or Count-Min Sketch with a heap give approximate heavy hitters in small memory. Details of that design are worked in the ad click aggregation case study.

9. Backpressure

A pipeline is only as fast as its slowest stage. If a sink (a database, say) can accept 20,000 writes per second but the source delivers 50,000 events per second, something must give. Backpressure is the mechanism by which a slow downstream stage tells the upstream stages to slow down rather than letting data pile up in memory until the process crashes.

In Flink, each connection between tasks has bounded network buffers. When a downstream task is slow, its input buffers fill, it stops granting credit to the upstream sender, the sender's output buffers fill, and so on back to the source, which simply stops reading from Kafka. The events wait safely in the Kafka log, which is a very large, durable buffer, and consumer lag grows. Kafka-based systems rely on pull: a consumer reads only as fast as it can process. Systems that push data over plain sockets without flow control must drop data or fail.

Backpressure is a symptom, not a disease. It tells you where the bottleneck is (find the first operator with a full input buffer and an idle output). Fixes include raising parallelism of that operator, batching writes to the sink, caching lookups, removing a hot key, or increasing sink capacity. Backpressure also makes checkpoint barriers slow to travel (barriers wait in the same queues), so checkpoints take longer or time out, which is why a long-running slowdown can turn into a restart loop. Alert on consumer lag growth and on checkpoint duration.

10. Scaling, partitioning and key skew

Stream jobs scale horizontally by partitioning. The source topic has P partitions (see Chapter 34); the job runs with parallelism up to P for the source operators, and after a keyBy, up to a fixed number of key groups (Flink hashes keys into, say, 128 or 32,768 key groups, and assigns ranges of key groups to tasks). Having more key groups than tasks makes rescaling possible: to go from 24 tasks to 48, you take a savepoint, and the engine redistributes whole key groups, moving state with them, then restarts. Kafka Streams scales by adding instances up to the number of input partitions; it moves partitions and rebuilds state from the changelog topic, which can be slow for large state unless standby replicas are configured.

10.1 Sizing

Estimate three things: input throughput (events per second times bytes per event), CPU per event (a simple aggregation may do 50-200k events per second per core; heavy JSON parsing or ML scoring far fewer), and state size (distinct keys times bytes per key times open windows). Add headroom of about 2x for traffic peaks and catch-up after an outage, since a job that exactly matches peak input can never reduce lag after downtime. Partition count is hard to raise later (changing it re-maps keys), so choose it generously at creation, for example 2-3x the parallelism you need today.

10.2 Key skew in streams

If one key (a celebrity account, a viral ad, an "unknown" bucket) carries a large share of the traffic, its task is saturated while the others idle. Because state and ordering are per key, you cannot simply add tasks. Techniques:

  • Two-phase (local/global) aggregation. First aggregate by (key, random sub-id) over a short interval in many tasks, then re-aggregate the partials by key. For sums and counts this reduces the hot key's load on the final task from the event rate to the number of sub-ids per interval. This is the streaming form of salting (section 3.6).
  • Mini-batch pre-aggregation. Each task buffers events for 100 ms or a few thousand records and combines same-key records before they are sent over the network, shrinking traffic to the hot key.
  • Dedicated handling. Detect heavy hitters (with a Count-Min Sketch) and route them through a separate, wider path.

Ordering caveat: splitting a key across tasks gives up per-key ordering, so use it only for commutative, associative aggregates.

10.3 Autoscaling and elasticity

Streaming jobs have stateful tasks, so scaling is not instant; it involves a savepoint or state movement and a pause of seconds to minutes. Reactive modes exist, but the usual practice is to scale on consumer lag with a cooldown, and to over-provision slightly instead of flapping.

11. Delivery guarantees, sinks and idempotent writes

Section 5 showed that the engine's internal state is exactly-once. A real pipeline writes results somewhere, and the failure window between "write to the sink" and "record the checkpoint" creates the end-to-end problem. Three possible guarantees:

  • At-most-once: output may be lost, never duplicated (commit the offset before processing; a crash loses the in-flight record). Acceptable for sampled metrics.
  • At-least-once: nothing lost, but duplicates after a failure (process, write, then commit the offset; a crash between write and commit makes the record be processed and written again). The default, and the simplest to get right.
  • Exactly-once: the visible effect is as if each input was processed once. Strictly, delivery is never "exactly once" over a failing network; what we build is at-least-once delivery plus idempotence or transactions, so duplicates have no effect.

11.1 Two ways to get exactly-once effects at a sink

  1. Idempotent writes. Make writing the same result twice harmless. For window aggregates the natural key is (ad_id, window_start), so the sink does an upsert: INSERT ... ON CONFLICT (ad_id, window_start) DO UPDATE SET clicks = excluded.clicks. The value written is the total for the window, not an increment, so replays overwrite the same row with the same value. Writing increments ("add 5") is not idempotent and is the classic bug. Event-level idempotency uses a unique event id as a dedup key; see Chapter 32 for generating and storing such ids and for dedup windows.
  2. Transactional (two-phase commit) sinks. The sink participates in the checkpoint protocol. As data arrives it is written to a pre-committed transaction (a Kafka transaction, or temporary files in a staging directory). When the checkpoint barrier reaches the sink, it flushes and votes "ready". Once the coordinator confirms the whole checkpoint is complete, every sink commits its transaction, which makes the data visible. On failure, the job restarts from the last completed checkpoint and aborts uncommitted transactions, so nothing from the failed attempt is ever visible. Kafka's transactional producer plus consumers using read-committed isolation implement exactly this. The cost: output becomes visible only at checkpoint boundaries, so end-to-end latency is at least the checkpoint interval.

12. Lambda versus Kappa, reprocessing and backfill

Teams commonly want both fresh and fully accurate results. Two architectures answer that.

12.1 Lambda architecture

Run two parallel paths over the same raw data. The speed layer (stream job) produces approximate results within seconds; the batch layer (a nightly Spark job over the immutable raw log) produces exact results hours later. A serving layer merges them: use the batch result for finished periods and the stream result for the recent period the batch has not covered yet. When the batch result for today arrives it replaces the stream's. Strength: robustness; the batch layer corrects any stream error, including late data. Weakness: two codebases that must compute exactly the same logic, twice the operational work, and subtle discrepancies between them.

12.2 Kappa architecture

Use one stream pipeline for everything. The raw events live in a durable, long-retention log (Kafka with long retention or tiered storage, or an object store). To fix a bug or change logic, deploy the new job version, have it replay the log from the beginning (or from the needed point) into a new output table, and when it has caught up, switch readers to the new table and retire the old one. Strength: a single code path. Weakness: replay needs the log retained for as long as you may want to reprocess, replaying months of history through a stream engine can be slow and costly, and exact reproduction requires event-time processing and deterministic logic.

12.3 Backfill and reprocessing in practice

Whatever the architecture, you will need to backfill: recompute history after a bug fix, a new metric, a schema change, or a data outage. Guidelines that make backfill safe:

  • Keep immutable raw data (the event log or raw files in object storage). Never overwrite the source of truth; derive everything from it.
  • Make jobs deterministic and parameterized by time range, so "rerun 2026-11-03" gives the same answer every time. Use event time, not "now()", and avoid reading mutable external tables without a time-travel snapshot.
  • Write outputs idempotently, partition by partition (overwrite the date partition atomically) so reruns replace rather than duplicate.
  • Run the backfill beside the live job, in a separate table or with lower priority and throttled, so it does not starve the live pipeline or the sink.
  • Validate before the switch: compare counts and sums of the new output with the old for overlapping periods.

Modern practice leans toward "batch for correctness, stream for freshness" with shared code: engines such as Spark and Flink offer the same SQL/DataFrame API in both modes, and table formats (Iceberg, Delta, Hudi) allow a stream to write incrementally and a batch to rewrite the same table, reducing the cost of Lambda's duplication.

13. Data pipelines: ETL, ELT, orchestration, quality, schema

13.1 ETL versus ELT

ETL (extract, transform, load) transforms data in a processing engine before it is loaded into the destination; the warehouse holds only clean, modeled data. ELT (extract, load, transform) loads raw data into the warehouse or lake first and transforms it there using SQL. ELT became popular because cloud warehouses and lakehouses scale compute cheaply and separately from storage, raw data stays available for reprocessing, and analysts can own the transformations in SQL (tools such as dbt). ETL still fits when data must be filtered or masked before it may be stored (privacy), or when the transformation is not expressible in SQL. A typical modern layout keeps layers: raw (bronze) as-is copies, cleaned (silver) deduplicated and typed, and modeled (gold) business tables and aggregates.

13.2 Ingestion: batch extracts and change data capture

Getting data out of operational databases is its own topic. Periodic full or incremental extracts (select rows where updated_at is greater than the last run) are simple but miss deletes and put read load on the database. Change data capture (CDC) reads the database's replication log (MySQL binlog, Postgres WAL) and publishes every insert, update and delete as an event to Kafka, giving low latency and no extra query load; tools such as Debezium do this. CDC events then feed stream jobs or land in the lake and are merged into tables. See Chapter 36 for event-driven patterns such as the outbox pattern, which solve the related problem of publishing events reliably from application code.

13.3 Orchestration

A real pipeline is many jobs with dependencies: ingest, then clean, then aggregate, then publish, plus checks. An orchestrator (Airflow, Dagster, Prefect, or a cloud equivalent) represents this as a DAG of tasks, runs them on a schedule or when upstream data arrives, retries failures with backoff, alerts on failure, records run history, and supports backfills by running the DAG for past dates. Principles for robust orchestration:

  • Tasks must be idempotent and parameterized by the logical date, so retries and reruns are safe.
  • Prefer data-aware triggering (run when the partition exists) over fixed clock times, which break when upstream is late.
  • Define SLAs and freshness checks, and alert when a table has not been updated, since silent staleness is more dangerous than a loud failure.
  • Keep the orchestrator as the scheduler, not the compute: it should launch Spark or SQL jobs, not run heavy processing itself.

13.4 Data quality

Bad data silently produces confident wrong numbers. Build checks into the pipeline: schema checks (columns and types present), null and range checks (no negative prices, timestamps not in the future), uniqueness of keys, referential checks (every ad_id exists in the ads table), volume and freshness (today's row count within a band of the last weeks'), and reconciliation between systems (stream total versus batch total within 0.5%). Decide for each check whether failure should block publishing (the "circuit breaker" pattern: stop before bad data reaches dashboards) or only warn. Quarantine bad records into a dead-letter table with the reason, rather than dropping them or failing the entire job for one malformed row.

13.5 Schema management and evolution

Producers and consumers evolve independently, so the data format needs rules. Use a self-describing, versioned format (Avro, Protobuf, or Parquet for files) with a schema registry that checks each new version for compatibility before it is accepted. Backward compatible changes let new readers read old data (adding an optional field with a default); forward compatible changes let old readers read new data. Safe evolution adds optional fields; renaming or changing a type needs a new field and a migration period. Without enforcement, one producer changing a field type breaks every downstream job at 3 a.m. See Chapter 7 for the encoding formats themselves.

14. Feeding warehouses and lakes

Processed data usually ends up in an analytic store (see Chapter 23 for column stores and warehouses). The feed design affects cost and correctness.

  • Data lake on object storage. Stream and batch jobs write columnar files (Parquet) partitioned by date (and sometimes by hour or tenant) to object storage. Cheap and durable, and queried by Spark, Trino, or warehouse external tables. Problem: streams produce many small files, which slow queries, so a compaction job merges them periodically into files of roughly 128 MB-1 GB.
  • Table formats (Iceberg, Delta Lake, Hudi). Add a transaction log on top of files, giving atomic commits (readers never see half-written output), schema evolution, time travel (query the table as of yesterday, which makes reproducible reprocessing possible), and row-level upserts and deletes (needed for CDC merges and privacy deletion requests). This is what makes "exactly-once into the lake" practical: a streaming sink commits a table snapshot per checkpoint.
  • Warehouse loads. Bulk-load files rather than inserting row by row; micro-batch every few minutes is typical, or use the warehouse's streaming ingestion API when seconds matter, at higher cost.
  • Real-time OLAP stores (Druid, Pinot, ClickHouse) ingest directly from Kafka and answer dashboard queries in milliseconds over fresh data, often fed by the same stream job's output. They suit "clicks per ad per minute" dashboards.
  • Serving stores. For product features (an ad's counter shown to an advertiser), write the aggregates to a key-value store keyed for the read pattern.

Partitioning the files by event date rather than ingestion date keeps late-arriving data in the correct partition, at the cost of having to rewrite old partitions. Partition granularity matters: partitioning by minute for a year creates hundreds of thousands of tiny partitions and slows planning, so most lakes partition by day or hour.

  5. Assume 0.3% of events are more than 10 s late (about 3,600 per minute) and 0.01% are later than 5 minutes (about 120 per minute, 2 per second). The latter go to the side output topic. They never reach the dashboard but remain in the raw log.

At 02:00 the batch job reads the 345 GB (about 70 GB as Parquet, assuming roughly 5x compression) of yesterday's raw files, deduplicates by click_id, counts by (ad_id, minute of event time), and overwrites yesterday's billing partition. A 20-executor Spark job reading at about 100 MB/s per executor scans 70 GB in about 35 seconds of read time; shuffling the grouped data and writing makes it a few minutes in total.

15.4 Failure drill

A TaskManager dies at 12:05:20 while checkpoint 10 (taken at 12:05:00) is the last complete one. Flink restores all state to checkpoint 10 and resets Kafka offsets to those stored in it. About 20 seconds of data, 400,000 events, is replayed at several hundred thousand events per second, taking a few seconds. The counters then match what they would have been without failure. The sink is idempotent, so rows rewritten for windows 12:04 and 12:05 are identical to those already stored. Dashboard staleness during recovery: about 30 seconds including restart. No data is lost or double counted.

17. Interview Q&A

When would you choose batch over streaming, and the other way around?

I start from the freshness requirement. If consumers are happy with hourly or daily results (finance reports, model training, search index rebuilds) I choose batch, because it has the best throughput per dollar, simple failure recovery (rerun the task), and a bounded, reproducible input. I choose streaming when the value of data decays quickly: fraud detection, live dashboards, alerting, or user-facing counters. Streaming costs more to run (always-on workers, state, checkpoints) and is harder to get right because of time and ordering. Often the answer is both: stream for the fast approximate view and batch for the corrected, authoritative one.

Explain shuffle and why it dominates the cost of distributed jobs.

A shuffle redistributes records across the cluster so that all records with the same key end up on the same node, which is needed for group-by, joins and distinct. Every sender writes partitioned output to local disk, every receiver pulls its pieces from all senders over the network, and both sides serialize, sort or hash, and possibly spill to disk. It is an all-to-all transfer that is limited by network and disk bandwidth, and it is a barrier, since the next stage waits for the slowest task. To reduce it I filter and project early, pre-aggregate with combiners (reduceByKey rather than groupByKey), use broadcast joins when one side is small, and rely on data already partitioned or bucketed by the join key.

What is data skew and how do you fix it in Spark or Flink?

Skew means keys are unevenly distributed so one partition receives far more data than others, which makes that task a straggler and may exhaust its memory. In batch I first check for accidental causes such as null or default keys. Then I use salting: add a random suffix to the hot key, aggregate by (key, salt), and combine the partials, or for joins replicate the small side across the salts. Alternatively, broadcast-join the hot keys separately, or use adaptive query execution to split skewed partitions automatically. In streaming the same idea shows up as two-phase local and global aggregation, with mini-batch pre-aggregation to cut the traffic to the hot key. Splitting a key gives up per-key ordering, so it only suits commutative, associative aggregates.

How does a stream processor achieve exactly-once state semantics?

It combines a replayable source, periodic distributed snapshots, and coordinated offsets. A coordinator injects checkpoint barriers into the stream at the sources, which record their offsets. When a barrier passes each operator, the operator snapshots its state to durable storage, so the snapshot contains exactly the effects of records before the barrier. On failure the job restores all operator state from the last complete checkpoint and rewinds the sources to the saved offsets, then reprocesses. Records after the checkpoint are processed twice physically but affect the restored state once. This covers internal state; external effects need an idempotent or transactional sink to complete the end-to-end guarantee.

What is a watermark and what happens to late events?

A watermark is the engine's estimate that no more events with timestamps below W will arrive. It is usually the maximum event time seen minus an allowed out-of-orderness, such as 10 seconds. When the watermark passes the end of a window the window fires. Events arriving after that are late. I handle them in layers: allowed lateness keeps the window state for a while and emits corrected results, which requires an upserting sink; events later than that go to a side output so they are counted and not lost silently; and a periodic batch job recomputes from the raw log to correct any residual error. The watermark delay trades latency for completeness, so it is set from the measured lateness distribution.

Event time or processing time: which should a metric use, and why?

Event time almost always, since it reflects when things actually happened and gives the same answer on replay, delay, or backfill. Processing-time windows are cheaper and need no watermarks, and they are acceptable for operational monitoring of the pipeline itself, such as "events processed per second", where what matters is what the system saw. For business metrics like clicks per minute, processing time would put a 10-minute outage's backlog into one window and make reprocessing give different answers. The price of event time is handling out-of-order data with watermarks and keeping window state longer.

Compare Lambda and Kappa architectures.

Lambda runs a batch layer over the full immutable data for accuracy and a speed layer for low latency, then merges their views. It is robust, because the batch result fixes any streaming mistakes and late data, but it needs two implementations of the same logic that tend to drift apart. Kappa uses only a stream job; to change logic or repair errors you replay the retained log through a new version of the job into a new output and then switch over. That has one codebase but needs long log retention, and replaying large history can be slow and expensive. In practice I choose Kappa-style single logic where the streaming engine can reproduce exact results deterministically, and keep a batch reconciliation job where money or compliance is involved.

How do you get exactly-once results into a database or data lake?

Delivery itself is at-least-once, so I make the write effect idempotent or transactional. For a database I write window totals with an upsert keyed by (key, window), so replays overwrite the same row; I avoid incremental updates. For append-only targets like Kafka topics or lake files I use a two-phase commit sink: data goes into an uncommitted transaction or staging files, the sink pre-commits when the checkpoint barrier arrives, and commits only after the checkpoint is globally complete, so a failure aborts the partial output. Table formats such as Iceberg give atomic snapshots for the same purpose. Any non-idempotent external call, like sending an email, needs an idempotency key so the receiver can discard repeats.

How do you handle backpressure and a consumer that cannot keep up?

First, backpressure is the system working correctly: bounded buffers propagate the slow-down to the source, which reads from the Kafka log more slowly, so the backlog accumulates as lag instead of memory. I find the bottleneck by looking for the first operator whose input is full and whose output is empty. Then I fix that operator: increase its parallelism, remove a hot key, batch writes to the sink, add async IO with caching for lookups, or scale the sink. I also watch checkpoint duration, because barriers queue behind the data, and set lag alerts based on the trend. Capacity planning should leave about 2x headroom so the job can drain backlog after an outage.

Design the top 10 trending hashtags per minute across the world.

Parse tweets into hashtag events, key by hashtag, and compute counts in one-minute tumbling or sliding event-time windows in parallel, using local pre-aggregation to handle celebrity hashtags. Each partition keeps a small heap of its local top K per window and emits only that. A single global operator merges the local top-K lists into the final top 10, which is correct because each hashtag lives on exactly one partition. For very high cardinality I would use a Count-Min Sketch plus heap for approximate heavy hitters. Results are upserted into a key-value store keyed by window, with a watermark delay of a few seconds and late events ignored or reconciled in batch. I would mention spam filtering and per-region variants as extensions.

How do you size a streaming job and decide the partition count?

I compute peak events per second and bytes per event for bandwidth, estimate CPU per event for the heaviest operator to get the number of cores, and estimate state as distinct keys times bytes per key times open windows, which decides heap versus RocksDB. I add about 2x headroom for peaks and catch-up. Partition count must be at least the desired parallelism and is hard to raise later, so I choose it with growth in mind, say 2 to 3 times today's need, while avoiding thousands of tiny partitions. I use many key groups so the job can be rescaled with a savepoint, and I verify the choice against the largest single key's rate, since one key cannot be split across tasks without special handling.

18. Recap

  • Pick batch, micro-batch or streaming from the freshness requirement; slower is cheaper and simpler. A batch is a bounded stream.
  • MapReduce is map, shuffle, reduce; fault tolerance comes from deterministic, side-effect free tasks and immutable inputs; stragglers are handled with speculative execution but not skew.
  • Spark builds a lazy DAG; wide dependencies (shuffles) cut stages and dominate cost. Reduce shuffles with early filtering, combiners and broadcast joins, and fix skew with salting.
  • Stateful streaming relies on keyed state in a backend (heap or RocksDB) and periodic barrier-based checkpoints; recovery restores state and rewinds the replayable source, giving exactly-once state semantics.
  • Use event time with windows (tumbling, sliding, session), watermarks for completeness, allowed lateness for corrections, side outputs for the rest, and batch reconciliation for the remainder.
  • Stream joins need bounded state: windowed stream-stream joins, changelog-based enrichment, broadcast for small tables. Top-K uses local heaps merged globally.
  • Backpressure is the signal of a bottleneck, and with a log source it turns into lag; scale by partition and key group, and break hot keys with two-phase aggregation.
  • End-to-end exactly-once equals at-least-once delivery plus idempotent upserts (total values, deterministic keys) or transactional sinks tied to checkpoints.
  • Lambda duplicates logic for safety; Kappa replays one pipeline. Make backfills deterministic, idempotent and validated.
  • Pipelines need orchestration, data quality checks, schema compatibility and compaction in the lake; the raw immutable log is what makes all repair possible.
