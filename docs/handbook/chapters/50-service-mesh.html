Service Mesh

A service mesh moves the repetitive networking work of microservices (retries, timeouts, encryption, identity, routing, metrics) out of every application and into a layer of proxies that the platform team controls. This chapter explains how that layer is built, what it gives you, what it costs, and how to decide whether you need one.

1. The problem: the same network code in every service

Imagine a company with 200 microservices written in Java, Go, Python, and Node. Every one of them makes calls to other services over the network, and every call has to deal with the same set of questions. How long should I wait before giving up? If the call fails, should I try again, how many times, and with what delay? Is the service I am talking to really the one I think it is, and is the conversation encrypted? Should I be allowed to call it at all? Which instance should I pick? How do I record how long the call took and whether it succeeded, so that someone can later see it on a dashboard?

Before service meshes, each team answered these questions inside its own code, usually by importing a library. Netflix's Hystrix, Ribbon, and Eureka clients were the famous example for Java. This works, but it has serious weaknesses that grow with the number of services:

  • One implementation per language. A retry library for Java does nothing for the Python team. Each language needs its own port of the library, and the ports behave slightly differently. One treats a timeout as retryable, another does not.
  • Upgrades require redeploying every service. If a security fix or a new default is needed in the client library, 200 teams must each upgrade, test, and deploy. In practice, some never do, and the fleet runs five different versions of the library for years.
  • Configuration is scattered. The timeout for calling the payment service lives in 30 different config files. Changing it during an incident means finding and editing all of them.
  • Behavior depends on developer discipline. A new service written in a hurry might forget to set a timeout, and the first slow dependency will exhaust its threads. See Chapter 40 for what happens next.
  • Security is hard to prove. An auditor asks "is all internal traffic encrypted and authenticated?" The honest answer is "it depends on each team", which is the wrong answer.

The idea behind a service mesh is to take all of that cross-cutting network behavior and implement it once, in a small program that runs next to each service instance and handles that instance's network traffic. The application keeps its business logic and speaks plain HTTP or gRPC to what it thinks is a local neighbor. The proxy beside it does the retries, the encryption, the telemetry, and the routing. Because the proxy is the same program everywhere, the behavior is the same for every language, and because it is configured centrally, the platform team can change it for the whole fleet without asking 200 teams to redeploy.

Key idea A service mesh is an infrastructure layer for service-to-service (east-west) traffic. It does for internal calls what a CDN or API gateway does for external calls, but it does it for every hop, language-independently, without changing application code.

2. The sidecar proxy model

2.1 What a sidecar is

A sidecar is a second container that runs in the same Kubernetes pod as the application container. Containers in one pod share a network namespace, which means they share the same IP address and can talk to each other over localhost. The sidecar is a general-purpose network proxy; in Istio and in most meshes it is Envoy, an open-source proxy written in C++ that was created at Lyft. (Linkerd is the notable exception: it uses its own lightweight proxy written in Rust, called linkerd2-proxy.)

Every byte that goes into or out of the application container passes through the sidecar. The sidecar can therefore see each request, measure it, encrypt it, retry it, and apply rules to it, without the application knowing. It is a "man in the middle" that you installed on purpose.

2.2 How traffic is intercepted

The application does not know a proxy exists. It calls http://payments:8080/charge exactly as before. So how does the packet end up in the proxy? The answer is packet redirection rules in the pod's network namespace.

  1. When the pod starts, an init container runs first. In Istio this is istio-init; it needs the network-admin capability (NET_ADMIN) for a short time. Linkerd has a similar init container, or a CNI plugin that does the same job without needing elevated rights in each pod.
  2. The init container installs iptables rules (the Linux packet-filter tables) in the pod. The rules say: any outbound TCP connection made by the application is redirected to the sidecar's outbound port (Istio uses 15001), and any inbound connection arriving at the pod is redirected to the sidecar's inbound port (15006).
  3. The init container exits. The application and the sidecar start. From now on, the redirect is in force for the life of the pod.
  4. The sidecar needs to know the original destination of a redirected connection, because the packet was addressed to payments:8080 but arrived at the proxy. Linux keeps this in the connection's tracking data (the SO_ORIGINAL_DST socket option), and the proxy reads it.
  5. To avoid an infinite loop, the proxy's own outbound traffic is excluded from redirection, typically by running the proxy under a specific user ID that the rules skip.

2.3 Alternatives to a sidecar in every pod

Running one proxy per pod is simple conceptually but expensive, and it has operational annoyances: the proxy version is tied to pod restarts, so upgrading the mesh means restarting every workload. Several newer designs try to reduce that cost, and an interviewer may ask about them at the concept level.

  • Node-level (per-host) proxy. One proxy runs on each Kubernetes node and serves all pods on that node. This uses much less memory in total and upgrading the proxy does not restart application pods. The cost is weaker isolation: one proxy handles traffic of many tenants, so a noisy or compromised workload has a larger blast radius, and one busy pod can starve its neighbors of proxy capacity.
  • Ambient mesh (Istio ambient mode). Splits the mesh into two layers. A small per-node component (called ztunnel) handles layer 4 work: mTLS, identity, basic authorization on connections. It is cheap and always on. Layer 7 features (header routing, retries, HTTP-level authorization) are optional and handled by separate shared waypoint proxies that you deploy only for namespaces or services that need them. The point is that you do not pay the full proxy cost for services that only need encryption.
  • eBPF-based dataplane. eBPF lets small verified programs run inside the Linux kernel. A mesh such as Cilium can do connection-level identity, load balancing, and policy in the kernel, without sending packets through a user-space proxy at all. Layer 7 processing still needs a proxy, generally a shared per-node Envoy, because parsing HTTP in the kernel is limited.
  • Proxyless gRPC. The gRPC library itself can speak the same configuration protocol (xDS, section 3) and apply routing, retries, and load balancing in-process. You get mesh-like central control with no extra hop, but only for languages and libraries that support it, which gives back part of the language-coupling problem.
Interview tip Say that the sidecar model is the classic one and the industry is moving toward shared per-node layers because the per-pod proxy costs memory and complicates upgrades. Name the tradeoff in one sentence: sharing a proxy saves resources but weakens isolation and makes the proxy a larger failure domain.

3. Data plane and control plane

Every mesh has two halves, and keeping them separate is the most important idea in the architecture.

3.1 The data plane

The data plane is the set of proxies that actually carry application traffic. Each proxy handles live requests, makes per-request decisions (which instance, whether to retry, whether the caller is allowed), and emits metrics. It must be fast and must not depend on anything remote to handle a request. It holds in memory the rules it needs, so a request never waits on the control plane.

3.2 The control plane

The control plane is a small set of services that configure the data plane. It does not see application traffic. In Istio it is a single binary called istiod, which combines three jobs:

  1. Configuration distribution. It reads high-level rules written by humans (Kubernetes custom resources such as VirtualService, DestinationRule, AuthorizationPolicy), merges them with the list of running endpoints from the Kubernetes API (service discovery, see Chapter 49), translates everything into Envoy's own configuration model, and pushes it to each proxy.
  2. Certificate authority. It issues and signs a short-lived certificate for each workload, which becomes that workload's identity (section 4).
  3. Policy and validation. It validates configuration before accepting it and holds the authorization and security policy that gets compiled into proxy config.

3.3 xDS: how config reaches the proxies

Envoy is configured through a family of gRPC streaming APIs called xDS (the "x" stands for any of several resource types). Each proxy opens a long-lived stream to the control plane and subscribes to the resources it needs:

  • LDS (listeners): what ports and protocols to accept connections on.
  • RDS (routes): HTTP routing rules, such as "path prefix /v2 goes to cluster X" or "send 5 percent to the canary".
  • CDS (clusters): the logical upstream services, with their load balancing, timeout, circuit-breaker, and TLS settings.
  • EDS (endpoints): the actual IP addresses of the instances behind each cluster. This changes constantly as pods start and stop.
  • SDS (secrets): certificates and private keys, delivered over the stream so they never need to be written to disk.

Because it is a streaming push, a change (a new pod, a new routing rule) reaches the relevant proxies within about a second or a few seconds, and updates are applied without dropping existing connections. Large meshes avoid pushing everything to everyone: a proxy for service A only needs to know about the services A may call. Istio's Sidecar resource and incremental xDS limit the scope; without it, a mesh with thousands of services makes every proxy hold a huge configuration and the control plane push enormous updates on every pod restart.

4. mTLS and workload identity

4.1 Why the network is not a trust boundary

Many companies once relied on a firewall: everything inside the private network was trusted. That fails when one container is compromised, because the attacker then sits inside the perimeter and can call any service. Zero trust says every call must prove who is calling and be checked against policy, regardless of where it comes from. A mesh is one of the most practical ways to get that for internal traffic. Chapter 55 (Security for System Design) covers the broader picture of authentication, authorization, and encryption; here we focus on how the mesh delivers it.

4.2 Mutual TLS

Ordinary TLS, as used by browsers, authenticates only the server: the client checks the server's certificate. In mutual TLS (mTLS) both sides present certificates, so the server also knows exactly who the client is. In the mesh, the client's sidecar and the server's sidecar perform the mTLS handshake with each other. The two application containers speak plain text to their local proxy over localhost, which never leaves the pod. Across the network, everything is encrypted and both ends are authenticated. No application code or certificate handling is needed.

4.3 Workload identity with SPIFFE

A certificate is only useful if it says something meaningful. Meshes use SPIFFE (Secure Production Identity Framework For Everyone), a standard that defines a workload identity as a URI. In Istio the identity of a service looks like:

spiffe://prod.example.com/ns/payments/sa/payments-api

That reads as: trust domain prod.example.com, Kubernetes namespace payments, service account payments-api. The identity is placed in the certificate's Subject Alternative Name field (the SPIFFE term for such a certificate is an SVID, a SPIFFE Verifiable Identity Document). The identity is tied to what the workload is (its service account), not to where it runs (an IP address that changes every restart). This is what makes policy readable and stable.

4.4 Issuance and rotation

  1. When a sidecar starts, it generates a private key locally; the private key never leaves the pod.
  2. It sends a certificate signing request to the control plane's CA, along with proof of who it is. On Kubernetes, the proof is the pod's service-account token, which the CA verifies against the Kubernetes API.
  3. The CA signs a certificate for that identity and returns it over the xDS secret stream.
  4. Certificates are short-lived, typically 24 hours in Istio's default (Linkerd defaults to 24 hours too). The sidecar asks for a new one well before expiry, often at about half of the lifetime, and swaps it in without dropping connections.

Short lifetimes are a security feature. A stolen key is useful for hours, not months, so you need no revocation lists for most cases. They are also an operational risk: if the CA is unavailable for longer than the remaining lifetime, every certificate expires and all mesh traffic starts failing. Monitoring the CA and expiry margins is therefore important. The mesh's root certificate (the trust anchor) is long-lived and must be managed carefully; many organizations use an intermediate CA signed by their corporate root or by a secrets system such as Vault, so that the root key is kept offline.

4.5 Authorization policy

Authentication answers "who are you?"; authorization answers "what may you do?". Because the sidecar now knows the verified identity of the caller, it can enforce rules without the application. An Istio example that allows only the web service account to call POST /charge on the payments workload:

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: payments-allow-web, namespace: payments }
spec:
  selector: { matchLabels: { app: payments-api } }
  action: ALLOW
  rules:
  - from:
    - source: { principals: ["prod.example.com/ns/web/sa/web-frontend"] }
    to:
    - operation: { methods: ["POST"], paths: ["/charge"] }

Once any ALLOW policy exists for a workload, everything not matching is denied, which gives a "default deny" posture. A typical rollout starts with the mesh in permissive mode (accepts both mTLS and plain text, so nothing breaks while workloads are being enrolled), then moves namespace by namespace to strict mTLS, then adds a default-deny policy and explicit allows. End-user authentication (JWT validation of the user's token, see Chapter 55) can also be enforced at the proxy, though most designs still pass the user's token to the service so that it can make business-level decisions.

Watch out mTLS proves that a particular service is calling, not that the user is allowed to see the data. Service identity and user authorization are separate layers. A mesh policy that says "web may call orders" does not stop web from asking for another customer's orders; that check still belongs in application code.

5. Traffic management

Since all traffic passes through proxies that are centrally configurable, the mesh can change where requests go and how failures are handled without touching application code or deployments. In Istio the main objects are a DestinationRule (what a destination looks like: subsets of versions, connection pool, outlier detection) and a VirtualService (how requests are routed to those destinations).

5.1 Weighted routing and traffic shifting

Two versions of the same service run side by side, labeled v1 and v2. The routing rule sends a percentage to each:

apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: reviews }
spec:
  hosts: [reviews]
  http:
  - route:
    - destination: { host: reviews, subset: v1 }
      weight: 95
    - destination: { host: reviews, subset: v2 }
      weight: 5

This is different from how Kubernetes alone does a canary. With a plain Kubernetes Service, traffic splits in proportion to the number of pods: to give a new version 5 percent you need about 1 canary pod per 19 stable pods, and the split is only approximate. A mesh decouples traffic percentage from replica count: one canary pod can receive 1 percent or 50 percent, and the split is exact and changes in seconds. See Chapter 43 for the deployment strategies themselves; the mesh is the traffic-control mechanism that makes fine-grained canaries and blue/green switching practical.

5.2 Header and attribute routing

Rules can match on path, method, headers, or cookies. Examples: send requests with x-beta-user: true to v2 (so internal testers see the new version in production while customers do not), route /api/v2 to a new service during an API migration, or send mobile clients to a different backend. Combined with weighted routing, this supports "dark launches" where only a chosen group experiences a change.

5.3 Traffic mirroring (shadowing)

The proxy sends the live request to the stable version and, in addition, a copy to the new version. The response from the copy is discarded; the user only sees the stable response. This tests a new version against real production traffic with no user risk. Caveats: the shadow service must not cause side effects (double charges, duplicate emails), so it is usually pointed at test downstream systems or limited to read paths, and mirrored traffic adds real load, so the shadow needs capacity.

5.4 Timeouts, retries, circuit breaking, outlier detection

These are the resilience patterns of Chapter 40 and Chapter 51, expressed as configuration instead of library code. Examples of the settings that matter:

  • Timeout. Total time allowed for a request through this route, for example timeout: 2s. This should come from the overall latency budget of the user request, not be guessed per hop.
  • Retries. attempts: 2, perTryTimeout: 500ms, retryOn: connect-failure,refused-stream,503. Retry only conditions that are safe to retry. Retrying on a plain timeout of a non-idempotent POST can charge a customer twice (see Chapter 32). The proxy adds jittered backoff between tries by default.
  • Retry budget. Linkerd limits retries to a fraction of total traffic (for example, at most 20 percent extra requests) to keep a failing service from being buried under retries. Envoy has a similar retry budget and a circuit breaker on concurrent retries.
  • Circuit breaking (connection pool limits). In Envoy, a "circuit breaker" is a hard cap, not a state machine: maximum concurrent connections, pending requests, and requests to one upstream. When the cap is hit, extra requests fail immediately with 503, protecting the server and freeing the caller's resources.
  • Outlier detection. The proxy watches each endpoint, and if one returns, say, 5 consecutive 5xx errors, it is ejected from the load balancing pool for a base time (for example 30 seconds, growing with repeated ejections), with a cap on the percentage of endpoints that can be ejected at once (for example 50 percent) so the pool is never emptied. This is passive health checking and it is the closest thing in the mesh to the state-machine circuit breaker of Chapter 40.
kind: DestinationRule
spec:
  host: payments
  trafficPolicy:
    connectionPool:
      http: { http1MaxPendingRequests: 100, maxRequestsPerConnection: 50 }
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 10s
      baseEjectionTime: 30s
      maxEjectionPercent: 50

5.5 Fault injection

The mesh can deliberately break things for testing. A rule can make 10 percent of requests to a service wait an extra 3 seconds (delay injection) or fail with HTTP 500 (abort injection). Because it happens in the proxy, you can test how callers behave when a dependency is slow, without writing a fake server. This is a small chaos-engineering tool; always scope it by header or namespace so it does not hit real users.

5.6 Rate limiting

Envoy supports local rate limiting, a token bucket inside each proxy (cheap, no network call, but each proxy counts separately), and global rate limiting, where proxies ask a shared rate-limit service backed by Redis (accurate across the fleet, but with an extra call per request). Algorithms and tradeoffs are in Chapter 16. In a mesh, rate limits are mostly used to protect a service from a misbehaving internal caller. Per-customer limits on the public API usually remain a job for the gateway.

6. Observability from the proxy

Because every request goes through a proxy, the mesh can produce uniform telemetry for every service, in every language, with no instrumentation. Out of the box, each sidecar emits:

  • The golden signals per service pair: request rate, error rate (by response code), latency histograms (p50, p90, p99), and, for TCP, bytes and connection counts. Metrics are labeled with source and destination workload, so you can draw a dependency graph and answer "who is calling me and who is failing?" immediately. These are the RED metrics (rate, errors, duration) defined in Chapter 54, and they give per-service SLO inputs for free (see Chapter 52).
  • Access logs: one line per request with method, path, response code, upstream host, duration, and flags that explain proxy-side failures (for instance, a flag showing the upstream timed out versus a circuit breaker tripped). Logging every request at high volume is costly, so teams often log only errors or sample.
  • Trace spans: each proxy can create a span for its hop, reporting to a tracing backend (Jaeger, Zipkin, or an OpenTelemetry collector).
Watch out The mesh cannot trace across a service on its own. When service A receives a request and then calls B, the sidecar sees two unrelated connections: one inbound and one outbound. Only the application knows that the outbound call was caused by the inbound one. So the application must copy the trace headers (traceparent in the W3C standard, or x-request-id and the B3 x-b3-* headers) from the incoming request to every outgoing request. If it does not, traces break into disconnected fragments. This one small piece of code, usually a line in an HTTP client wrapper or an OpenTelemetry library, is the thing the mesh cannot remove. See Chapter 52 for propagation details.

7. Ingress and egress gateways

The sidecar model handles traffic between services inside the mesh. Two edges need special handling.

7.1 Ingress gateway

An ingress gateway is an Envoy proxy running at the edge of the mesh as a standalone deployment (not a sidecar). External traffic from the load balancer enters through it. It terminates TLS for public hostnames, applies routing rules (the same VirtualService objects used inside), and then forwards into the mesh over mTLS. Because it uses the same configuration model, a canary rule can apply at the very first hop. Kubernetes now has a standard Gateway API for this, and Istio supports it.

7.2 Egress gateway

Calls from inside the mesh to external destinations (a payment processor, a SaaS API) can be sent through an egress gateway. This gives one choke point with a stable source IP that partners can allowlist, central logging of outbound calls, and the ability to block everything not explicitly registered (outboundTrafficPolicy: REGISTRY_ONLY). It limits data exfiltration: a compromised pod cannot freely connect to an arbitrary host. The cost is one more hop and another component to scale.

7.3 Mesh versus API gateway

These are often confused because both are proxies that route and apply policy. The difference is who the client is and what the concerns are. Chapter 11 covers the API gateway in depth; the comparison below is the interview-ready summary.

8. Multi-cluster and multi-region mesh

A single Kubernetes cluster is a failure domain and has scale limits. Large companies run several clusters, across zones, regions, or clouds, and still want services to find and call each other securely. Meshes support this in two main topologies:

  • Single mesh with a shared control plane (or replicated control planes), shared trust. All clusters trust the same root CA, so a workload in cluster 1 can present a certificate that cluster 2 accepts. Each control plane watches the Kubernetes API of every cluster to learn the endpoints, so a service called payments can have instances in both clusters in one pool.
  • Multi-network. If pod IPs in different clusters are not directly routable (the common case across regions and clouds), traffic goes through east-west gateways: a gateway in each cluster exposes services to the others, and mTLS carries across. The proxies use SNI (the server name in the TLS handshake) to route to the right service through the gateway without the gateway needing to decrypt.

Two behaviors matter for design. First, locality-aware load balancing: by default the proxy prefers endpoints in its own zone, then region, and only fails over to a remote one when local endpoints are unhealthy (outlier detection and health data feed this). This keeps latency and cross-zone transfer charges down while giving automatic cross-cluster failover. Second, a shared root CA is a large shared secret; compromise of it affects all clusters, so some designs use separate trust domains with explicit federation instead. For the data side of multi-region (replication, consistency) see Chapter 26; the mesh only moves requests, it does not make state replicate.

9. A request through the mesh, and what it costs

Take a call from web to payments with mTLS and a retry policy. The request passes through two proxies even though the code shows one call.

9.1 Latency overhead

Each proxy traversal adds work: copying data between kernel and user space, parsing the HTTP headers, evaluating route and policy rules, encrypting or decrypting, and recording metrics. Published benchmarks and vendor documentation generally report an added latency of roughly 0.5 to 3 ms per proxy hop at the median for Envoy-based sidecars under moderate load, and often well under 1 ms for Linkerd's lighter proxy. Because a call passes through two proxies, expect about 1 to 6 ms per service-to-service call, and a higher tail (p99 can reach several milliseconds, more when proxies are CPU throttled). These numbers vary with request size, number of active routes, whether L7 parsing is on, and whether CPU limits are tight, so treat them as an order of magnitude and say "measure in your own environment" in an interview.

The effect compounds with call depth. A user request that fans through a chain of 6 services, each one hop, picks up roughly 6 × 2 × 1 to 3 ms = 12 to 36 ms of extra latency. For a 200 ms request that is acceptable; for a latency-critical path with a 20 ms budget it is a real cost.

9.2 Resource overhead

Each sidecar consumes memory and CPU even when idle, and more under load. Typical figures reported for an Envoy sidecar are on the order of 40 to 100+ MB of memory in a small mesh (growing with the number of services it knows about, which is why scoping config matters) and about 0.5 to 1 vCPU per 1,000 requests per second of proxied traffic (counting both directions). The Linkerd proxy is typically around 10 to 20 MB of memory. A sidecar is usually given a small baseline request (for example 100m CPU and 128 MiB).

10. Costs and risks

10.1 Complexity and the learning curve

A mesh adds a new layer that every engineer eventually has to understand. Istio alone has dozens of custom resource types and a large number of configuration fields, and the interactions between them (a VirtualService that references a subset defined in a DestinationRule that selects pods by a label) are easy to get wrong. Misconfiguration often fails silently: a typo in a subset name makes traffic return 503 with an error flag, not a helpful message. The platform team needs real expertise, and application teams need at least a mental model of what the sidecar does to their traffic.

10.2 Debugging gets harder

When a call fails, there are now more places it could have failed: the application, its sidecar, the network, the remote sidecar, the remote application, or the control plane's configuration. A "connection reset" might be a proxy policy, an expired certificate, an mTLS mode mismatch, or a protocol detection error (a proxy treating a server-first protocol such as MySQL as HTTP). Teams need tools such as istioctl proxy-status, istioctl analyze, and the proxy's admin endpoint to see the actual config a given proxy holds, and they need to learn the proxy's response flags. The positive side is that the mesh also provides the metrics and access logs that make these problems diagnosable once the team is trained.

10.3 Upgrades

The sidecar lives in every pod. Upgrading the mesh means restarting every workload so it picks up the new proxy, which is a fleet-wide rolling restart that must be coordinated with team schedules. Control plane and data plane versions must stay within a supported skew. Istio supports canary control plane upgrades (run two control plane versions side by side with revision labels and move namespaces one at a time), and this is the recommended approach. Ambient mode and node proxies reduce the problem because the proxy upgrades separately from application pods.

10.4 Control plane failure behavior

This is a classic interview probe. If the control plane crashes or becomes unreachable:

  • Existing traffic continues. Each proxy keeps the last configuration it received and continues to route, retry, and enforce policy with it. The data plane does not depend on the control plane for requests.
  • New changes stop. New routing rules, policy changes, and certificate issuance do not happen. New pods that start while the control plane is down cannot fetch their initial config or certificate, so they may fail to become ready. Autoscaling scale-outs and node replacements during the outage therefore break.
  • Endpoint updates stop. Proxies cannot learn about pods that die, so they keep sending traffic to dead addresses until their own passive health checks (outlier detection) eject them. This makes failure of the control plane during a rolling deployment particularly hurtful.
  • Certificates eventually expire. With 24-hour certificates there is a time bomb; a control plane outage of many hours risks a mesh-wide mTLS failure. Hence run multiple control plane replicas across zones, alert on expiry margins, and have a runbook.

Because the control plane is not in the request path, it is much less critical than a gateway. But it is still "critical for change", so design it like any highly available service (see Chapter 41).

10.5 Misconfiguration blast radius

Mesh configuration is global and propagates fast. A wrong AuthorizationPolicy or a strict mTLS setting applied at the mesh root namespace can cut off traffic to every service in a minute. A wrong default timeout of 100 ms mesh-wide would break every slow endpoint at once. The mitigations are the same as for any dangerous config: validate with istioctl analyze in CI, review policy changes, roll out per namespace, use a staged policy mode (for example an audit or dry-run action that logs what would be denied), and keep the config in version control with GitOps so rollbacks are one commit.

10.6 Retry multiplication with application retries

The most common real-world mesh bug: both the application library and the mesh retry. Suppose service A's HTTP client retries 3 times, and the mesh sidecar retries 3 times, and service B (called by A) is also configured with 3 mesh retries to C. A single user request to a failing C can become 3 × 3 × 3 = 27 calls to C. That multiplies load exactly when C is struggling, which is how a small failure turns into a retry storm (see Chapter 51). The rule: retry at exactly one layer, and prefer to retry only at the outermost caller or only in the mesh, with a retry budget, and a total timeout that bounds the whole chain.

10.7 Other risks

  • Protocol and compatibility surprises. Server-first protocols, long-lived connections, and non-HTTP traffic need explicit configuration. Applications that bind to localhost only, or that start network calls before the sidecar is ready, fail at startup (the classic "app container starts before the proxy" race; most meshes offer a hold-until-proxy-ready setting).
  • Batch jobs and short-lived pods. A job that finishes while its sidecar keeps running never exits, so the pod hangs. Newer Kubernetes versions support native sidecar containers to handle this.
  • A proxy is a new place for bugs and CVEs. Envoy vulnerabilities require fleet-wide patching, and the proxy is now in the trust path of all data.
  • Hidden hops in latency analysis. A mesh makes your latency graphs contain proxy time. Measure application time separately from proxy time to avoid blaming the wrong thing.

11. When to adopt a mesh, and when not

A mesh solves a problem of scale and heterogeneity. Its value rises with the number of services, the number of languages, and the strictness of security and compliance requirements. For a handful of services it is usually a poor trade.

SituationRecommendation
Fewer than about 10 to 20 services, one or two languages, one teamDo not adopt a mesh. Use a shared client library and a gateway. The mesh costs more than it saves.
Many services, many languages, large fleet, compliance requires encryption and authenticated internal trafficStrong candidate. mTLS-everywhere and uniform telemetry are the headline benefits.
You only need encryption and identity, nothing elseConsider ambient or a minimal mesh (Linkerd). Do not take the full L7 feature set if you will not use it.
Need canary and traffic splitting but little elseA progressive delivery tool with an ingress controller (for example Argo Rollouts with an ingress or Gateway API) may suffice without a mesh.
Ultra-low-latency path (single-digit milliseconds budget)Be cautious; per-hop overhead matters. Exclude those services from the mesh, or use proxyless or eBPF modes.
No platform team capacityDo not adopt. A mesh needs owners. Consider a managed offering if you must.

11.1 Alternatives

  • Client libraries. Good when you have one or two languages and a strong platform library team. No extra hop, easy to debug, but upgrades require redeploys and coverage depends on discipline.
  • Gateway only. Many systems get along fine with a gateway for the edge and libraries for the inside. If your pain is all at the edge (auth, rate limits), a mesh does not help.
  • Platform features. Kubernetes network policies give basic L3/L4 allow rules; cloud load balancers and service-discovery products give some routing; a cloud provider's managed identity can give workload identity; cert-manager can issue certificates for in-app TLS. These cover partial needs at lower complexity.

The honest summary: the mesh trades runtime cost and platform complexity for uniformity and decoupling. 12. Migration and rollout strategy

Do not turn on a mesh for the whole fleet at once. A cautious path that fits most organizations:

  1. Install the control plane and observe only. Use a pilot namespace with a few non-critical services. Inject sidecars, leave mTLS in permissive mode, and verify that nothing breaks and that metrics appear. This builds team skill with low risk.
  2. Get telemetry first. The earliest value is visibility: dependency graphs, error rates, and latency per pair. This often justifies the project and shows unexpected callers.
  3. Expand namespace by namespace. Enable automatic sidecar injection per namespace and roll restarts gradually. Watch for startup races, unsupported protocols, and resource limits. Keep an escape hatch (an annotation to opt a workload out) for odd cases.
  4. Switch to strict mTLS gradually. First confirm from metrics that all traffic to a service is already mTLS, then flip that namespace to strict. Handle the stragglers (legacy non-mesh clients, health checks, jobs) with explicit exceptions.
  5. Add authorization policies, default deny. Use the traffic graph from step 2 to write the allow rules, run them in dry-run or audit mode first, then enforce.
  6. Adopt traffic management selectively. Start with timeouts and outlier detection, then canaries. Remove duplicate application-level retries as you go (section 10.6), service by service.
  7. Plan operations. Define who owns the mesh, an upgrade cadence with canary control plane revisions, alerts for certificate expiry and control plane health, and a runbook for "disable mesh for this workload".
Interview tip In a design interview, present the mesh as something you grow into: "We start with a gateway and a shared library. When we have enough services and languages that consistent mTLS and telemetry become a problem, we adopt a mesh, starting with observability, then mTLS, then traffic management." That shows you weigh cost, not just features.

13. Worked example: automatic canary 5, 25, 100 percent

Setting. The payments service runs version v1 with 10 pods at about 500 requests per second in total. Version v2 changes the fee calculation. We want a progressive rollout with automatic rollback based on measured error rate and latency, using a mesh to split traffic and a controller (such as Flagger or Argo Rollouts with mesh integration) to drive the steps.

13.1 Setup

  • v2 is deployed as 2 pods, labeled version: v2. v1 keeps its 10 pods.
  • A DestinationRule defines subsets v1 and v2. A VirtualService carries the weights, initially 100 / 0.
  • The controller's analysis rules, evaluated every 60 seconds from the mesh's own metrics:
    • Success rate (non-5xx responses) of v2 must be at least 99.5 percent.
    • p99 latency of v2 must be under 300 ms (v1 baseline is 220 ms).
    • Three failed checks in a row cause rollback.

13.2 The steps with numbers

StepWeights (v1 / v2)v2 requests per secondHold timeGate
0. Baseline100 / 00until pods are readyreadiness checks pass
1. Canary95 / 525 (5% of 500)10 minutessuccess at least 99.5%, p99 under 300 ms
2. Expand75 / 2512510 minutessame gate; scale v2 to 4 pods first
3. Promote0 / 10050015 minutessame gate; v2 scaled to 10 pods
4. Finalizev2 is now the stable release500-v1 pods scaled to zero after a soak period

13.3 Why numbers at 5 percent are meaningful

At 25 requests per second for 10 minutes, v2 sees 15,000 requests. If the true error rate were 1 percent (twice the allowed 0.5 percent), we would expect 150 errors, which is statistically clear against a gate of 75. If the bug affects only 0.1 percent of requests, the canary sees about 15 errors, which is within noise at this sample size; such a subtle bug is caught only at higher traffic. This is why a canary stage must have enough traffic to detect the failure rate you care about, and why very low-traffic services need longer holds or synthetic load. Note that the canary exposed only about 5 percent of users to the problem, a limit of roughly 25 failed requests per second at a 100 percent failure rate, instead of 500.

13.4 Automatic rollback

Suppose at step 2 (25 percent) a database index is missing in v2's new query path. After 90 seconds, p99 for v2 climbs to 900 ms and 3 percent of requests time out. The controller's checks fail at the next three 60-second evaluations (the success rate is 97 percent, below 99.5). After the third failure it sets the weights back to 100 / 0 in a single update, which the control plane pushes to all proxies within seconds; no pods need to restart and no image rollback is needed, because v1 never went away. Total exposure: about 5 minutes at 25 percent, in which roughly 3 percent of 125 requests per second failed, around 4 failed requests per second for about 3 to 4 minutes, in the order of 700 failed requests. The team gets an alert with the metrics and the failing step.

13.5 Pitfalls in the example

  • The canary must be compared to the stable version in the same time window, not to an old baseline, because traffic mixes shift during the day.
  • Sticky behavior: if requests of one user bounce between v1 and v2, a database schema change that is not backward compatible will cause errors. Schema changes must be compatible with both versions (see Chapter 47 on compatibility). Where needed, route by a header or hash of user ID so that a user sees only one version.
  • The mesh splits traffic per request, which does not match "per user" experiments; use header or cookie routing for that.
  • If the services involved retry at the mesh and the application, the error rate seen at the gate is hidden by retries: users might see success while the canary silently burns capacity. Measure per-try failures too.

15. Interview Q&A

What problem does a service mesh solve, and why not just use a library?

It centralizes cross-cutting network behavior such as retries, timeouts, mTLS, routing, and telemetry in a proxy that runs beside each service. With libraries you need an implementation per language, you depend on every team upgrading, and configuration is scattered. With a mesh the behavior is uniform in every language and a platform team can change it through one control plane. The tradeoff is added latency, resource usage, and operational complexity, so libraries remain a sound choice for small, single-language systems.

How does the sidecar intercept traffic without changing the application?

An init container runs at pod start with network-admin rights and installs iptables rules in the pod's network namespace. Those rules redirect all outbound TCP connections to the sidecar's outbound port and all inbound connections to its inbound port. The proxy recovers the original destination from the kernel's connection tracking data and forwards the traffic, with its own traffic excluded from redirection to avoid loops. Alternatives such as a CNI plugin, ambient mode, or eBPF achieve the same redirection with fewer privileges or without a per-pod proxy.

Explain data plane versus control plane, and what happens if the control plane dies.

The data plane is the proxies that carry requests; the control plane computes configuration, distributes it over xDS streams, and issues certificates. Requests never pass through the control plane. If it dies, proxies keep running with their last configuration and certificates, so existing traffic continues. What stops is change: new routes, policy updates, new pod configuration, endpoint updates, and certificate renewal. A long outage becomes dangerous when short-lived certificates start expiring, so the control plane is run with several replicas and monitored.

How does a mesh provide zero trust between services?

Each workload gets a short-lived certificate carrying a SPIFFE identity derived from its service account, issued by the mesh CA after verifying the pod's token. Sidecars use these certificates for mutual TLS, so each side knows the verified identity of the other and traffic is encrypted. Authorization policies on the server's sidecar then allow only specific identities, methods, and paths, with default deny. This removes reliance on network location, though it does not replace user-level authorization inside the application.

How would you do a canary release with a mesh, and how is it better than plain Kubernetes?

Deploy the new version as a separate set of pods with a version label, then set weighted routes, for example 95 to 5, and increase in steps while a controller checks success rate and latency from mesh metrics, rolling back automatically if checks fail. With plain Kubernetes the traffic share is tied to pod counts, so small percentages need awkward replica ratios and cannot be exact. The mesh splits per request independent of replicas, supports header-based routing for testers, mirroring for shadow testing, and rolls back by changing a weight in seconds.

What is the retry amplification problem and how do you avoid it?

If the application, the sidecar, and downstream services each retry three times, one failing request fans out into 27 attempts against the broken dependency, which pushes it further into overload. To avoid it, retry in only one layer, usually the mesh or the outermost caller, retry only on safe conditions such as connection failures and idempotent operations, use jittered backoff, and enforce a retry budget and an overall deadline that propagates down the chain. Outlier detection and circuit breaking add protection by stopping traffic to endpoints that are already failing.

What overhead should I expect from a sidecar mesh?

Each call crosses two proxies, adding roughly one to a few milliseconds per hop with Envoy-based sidecars in typical conditions, less with lighter proxies, and the tail is worse under CPU throttling. Each sidecar uses tens of megabytes of memory to over a hundred and some CPU that grows with traffic, so a few hundred pods can use tens of gigabytes just for proxies. These numbers depend on configuration and load, so measure in your own environment, and consider ambient, eBPF, or excluding latency-critical services if the overhead matters.

How is a service mesh different from an API gateway?

A gateway handles north-south traffic from external clients and covers user authentication, per-customer quotas, aggregation, API versioning, and the product-level contract of the public API. A mesh handles east-west traffic between your own services using workload identity, mTLS, retries, and telemetry, with a proxy beside every instance. They overlap on routing and rate limiting, and large systems use both, with the gateway at the edge and the mesh behind it. A mesh ingress gateway can fill a simple gateway role, but it is not a full API management product.

When would you decide not to adopt a mesh?

When there are few services, one or two languages, no strong compliance driver, and no platform team to operate it. The cost in complexity, debugging difficulty, resource overhead, and upgrade coordination exceeds the benefit. A shared library and a gateway, plus Kubernetes network policies and a progressive-delivery tool for canaries, usually cover the needs. I would also avoid it for ultra-low-latency paths and revisit the decision when the number of services, languages, or audit requirements grows.

How does tracing work with a mesh, and what must the application still do?

Sidecars generate spans and metrics for each hop automatically, but they cannot tell that an outbound call was triggered by a particular inbound request. The application must copy the trace context headers, such as W3C traceparent, from incoming to outgoing requests. Without it, each hop becomes an isolated trace. In practice teams put this into a shared HTTP client or an OpenTelemetry library, and the mesh then supplies uniform timing and error data for each hop.

How do you roll out strict mTLS safely in a running system?

Start in permissive mode, which accepts both plain text and mTLS, and inject sidecars namespace by namespace. Use the mesh's metrics to confirm that all callers of a service are already using mTLS, and identify stragglers such as legacy clients, health probes, and batch jobs. Then switch that namespace to strict mode, with specific exceptions where needed, and roll back at once if errors spike. Authorization policies follow afterwards, tested in audit or dry-run mode before enforcement.

16. Recap

  • A mesh centralizes retries, timeouts, mTLS, routing, and telemetry in proxies beside each service, so behavior is uniform across languages and managed from one place.
  • Traffic is intercepted with iptables rules installed by an init container (or CNI); alternatives are per-node proxies, ambient mode, eBPF, and proxyless gRPC.
  • The data plane carries requests and keeps working on the last known config if the control plane fails; the control plane pushes xDS configuration and issues short-lived certificates.
  • Workload identity (SPIFFE IDs in certificates) enables mTLS and default-deny authorization, supporting zero trust, but does not replace user-level authorization.
  • Traffic management includes weighted routing, header routing, mirroring, timeouts, retries, outlier detection, connection limits, fault injection, and rate limiting, all by configuration.
  • Metrics and access logs come free, but trace-header propagation still needs application code.
  • Costs: about 1 to 6 ms per call, tens to hundreds of MB per sidecar, operational complexity, harder debugging, fleet-wide upgrades, and a large blast radius for misconfiguration.
  • Retry at one layer only, or retries multiply across the stack.
  • Adopt for large, polyglot, compliance-driven fleets with a platform team; avoid for small systems. Roll out observe first, then mTLS, then policy, then traffic management.
