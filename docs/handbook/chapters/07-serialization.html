Chapter 7 · Module 1 · Networking and communication

Serialization, Compression and Batching

Every byte that crosses a network or lands on disk was produced by some encoding, and every encoding is a bet about CPU, size, readability, and how the data will change over the years. This chapter explains how data is turned into bytes, how those bytes are shrunk and grouped, and how to choose well in a design interview.

1. Why serialization matters

Inside a running program, data lives as objects: a User with an integer id, a string name, and a list of orders. These objects are made of pointers, memory addresses, and language-specific layouts. None of that can be sent over a network cable or written to a disk file as it is. A pointer that is valid in one process means nothing in another. So before data leaves a process, it must be converted into a flat sequence of bytes, and the receiver must convert those bytes back into objects. The first step is called serialization (also encoding or marshalling), and the second is deserialization (decoding, unmarshalling, or parsing).

This looks like plumbing, and many engineers treat it as an afterthought: "we just use JSON". But the choice of format quietly controls three large properties of a system.

1.1 CPU

Encoding and decoding are real work. A text format like JSON must walk every character, find quotes and braces, convert the text "12345" into the integer 12345, unescape strings, and allocate many small objects. In a service that does little else besides receive a request, call a database, and answer, parsing and building JSON is often one of the top entries in a CPU profile. Binary formats usually decode several times faster because they do not scan for delimiters: lengths are written first, and integers are already in a form the machine can read quickly. At small scale this does not matter. At 50,000 requests per second it can be the difference between three servers and ten (section 14 works through numbers). It also matters for garbage collection: a format that creates fewer temporary objects causes fewer pauses, which improves tail latency (Chapter 40).

1.2 Bytes

Size affects three things at once. First, network bandwidth, which you pay for in cloud egress fees and in saturated links. Second, latency: a payload that fits in one TCP segment (about 1,460 bytes of data on a typical path) can arrive in one round trip, while a larger one needs more segments, and during TCP's early slow-start phase each extra window of data can cost another round trip (see Chapter 3). Third, storage: the same events written to Kafka or to object storage take disk space for as long as retention lasts, and replication multiplies it. If a 1 KB record shrinks to 300 bytes, you store, replicate, and read 70 percent less data forever.

1.3 Evolution

The third property is the one that bites longest. In a real system, the sender and the receiver are deployed independently, often by different teams, and data written years ago is still sitting in a log or a database. When you add a field to a message, some readers will not know about it yet; when you remove one, some old data will still have it. A format must give clear rules for what happens in these cases. Formats differ enormously here: some tolerate change by design, and some silently corrupt data. Section 5 covers this in depth.

Key idea Choosing a serialization format is choosing a point in a three-way tradeoff between CPU time, bytes, and human and evolutionary friendliness. Text formats like JSON are easy to read and debug but larger and slower. Binary schema-based formats like Protocol Buffers and Avro are small, fast, and evolve by explicit rules, but you cannot read them with your eyes and you must manage schemas.

Two more ideas frame the rest of the chapter. Compression is a separate, optional step applied to the encoded bytes to make them smaller at the cost of more CPU (sections 8 and 9). Batching is the practice of grouping many small items into one bigger unit so that fixed per-message costs, such as a network round trip, a system call, or a disk seek, are paid once instead of many times (sections 10 and 11). Together, the three techniques are how high-throughput systems such as Kafka, Cassandra, and gRPC services move large volumes of data cheaply.

2. Text formats: JSON, XML, CSV

A text format encodes data as characters (usually UTF-8) that a person can read in an editor. The main ones are JSON, XML, and CSV.

2.1 JSON

JSON (JavaScript Object Notation) represents objects (key/value maps), arrays, strings, numbers, booleans, and null. It dominates web APIs because browsers parse it natively, every language has a library, and a developer can read a response with curl. It is self-describing: each value carries its field name, so a reader needs no external schema to make sense of it. That is also its main cost, because the field names are repeated in every single record. A list of one million users will contain the string "name" one million times.

JSON also has weak typing. There is one number type with no distinction between integer and float, no date type, no binary type (binary must be base64 encoded, which inflates it by a third), and no comment syntax. Section 13 shows the practical traps that follow from this. JSON has no built-in schema either, although JSON Schema and OpenAPI can describe it, and nothing forces a producer to follow them at runtime.

A useful JSON variant for streams is NDJSON or JSON Lines: one complete JSON value per line, separated by newline characters. It lets you append records to a file, process a huge file line by line without loading it, and split logs easily. Many log pipelines use it.

2.2 XML

XML uses opening and closing tags, attributes, and namespaces. It has mature schema languages (XSD), transformation (XSLT), and query (XPath), and it was the standard for enterprise integration and SOAP web services. It is more verbose than JSON because every element name appears twice, once in the open tag and once in the close tag. It is still common in older enterprise systems, document formats, and configuration, but new APIs rarely choose it. Parsers also need care: XML allows entity expansion, which has been abused for the "billion laughs" attack, a tiny document that expands to gigabytes (section 9.4 returns to this idea for compression).

2.3 CSV

CSV (comma-separated values) is rows of values separated by commas, optionally with a header row. It is compact for flat tables because field names appear once, and spreadsheets and databases import it everywhere. But it has no types (everything is text), no nesting, and a famously loose standard: how to escape commas and newlines inside a value, which character set, and how to represent null all vary by tool. It is good for data export and simple bulk loads and poor for anything that needs structure or safe evolution, because adding a column in the middle silently shifts everything after it.

2.4 When text wins

Text formats win when humans are in the loop: public APIs where third-party developers must experiment with curl, browser clients, configuration files, logs you will grep, and low-volume service calls where CPU and bandwidth are not the bottleneck. A good default in an interview is: "JSON for the external, public API, because clients can use it without any tooling; a binary format between internal services if the volume or latency justifies it." Interviewers like hearing you separate the edge format from the internal format, because the two audiences have different needs. The API gateway (Chapter 11) is frequently where a JSON request from outside is translated into binary calls inside.

3. Binary formats and how they differ

A binary format encodes data in a compact byte layout designed for machines. Most use a schema, a separate definition of which fields exist and what types they have, so the bytes do not need to carry field names. The main formats you should know:

3.1 What makes them smaller and faster

Three techniques explain most of the gain over JSON. First, field identification by number rather than name: instead of writing "active" (8 bytes with quotes), Protobuf writes a one-byte tag that stands for "field 3". Avro goes even further and writes no identification at all, relying on the schema to say that the third thing in the record is the boolean. Second, compact integers: a number like 150 takes 3 characters in JSON but a variable-length binary encoding can store small numbers in 1 byte (section 4). Third, length-prefixed strings: the decoder reads a length, then copies exactly that many bytes, instead of scanning forward for a closing quote and handling escape characters.

3.2 Zero-copy formats

FlatBuffers and Cap'n Proto take a different approach. Instead of making the encoding compact, they make it directly usable. The serialized buffer is laid out in memory exactly the way the program wants to read it, with offsets instead of pointers, so "decoding" is nothing more than following offsets inside the buffer. There is no parse step and often no allocation. The tradeoff is that the buffers are somewhat larger than Protobuf's (alignment padding is added) and the API is slightly more awkward. They shine when you have a very large message and want only a few fields from it, or when loading a file from disk by memory mapping it, which is why games and mobile apps like them.

3.3 Self-describing versus schema-required

A format is self-describing if the bytes contain enough information to be decoded without any external definition. JSON and MessagePack are self-describing: you can parse them and see names and types. Protobuf, Thrift, and FlatBuffers are schema-required in the sense that, without the .proto file, you can still split the bytes into (field number, value) pairs, but you do not know field names or whether a length-delimited chunk is a string, bytes, or a nested message. Avro is the extreme case: without the exact writer schema, the bytes are meaningless, because there are no tags at all.

The tradeoff is direct. Self-describing formats cost more bytes but are easy to debug and forgiving about tooling. Schema-required formats are smaller and enforce a contract, but you must distribute schemas to every reader, keep versions straight, and have a way to look up the right schema for old data. This is exactly the problem that schema registries solve (section 6). Files can solve it a different way: an Avro container file or a Parquet file stores its schema once in the header or footer, so the file is self-describing even though each record is not.

4. Inside Protocol Buffers: bytes, varints, tags

It is worth understanding one binary format at the byte level, because it shows concretely where savings come from and why evolution rules look the way they do. Protobuf is the best choice for this because it is widely used and its encoding is simple.

Take this schema:

syntax = "proto3";
message User {
  int32  id     = 1;
  string name   = 2;
  bool   active = 3;
}

and the record id = 150, name = "Ada", active = true. The JSON form {"id":150,"name":"Ada","active":true} is 37 bytes. The Protobuf encoding is 10 bytes:

08 96 01   12 03 41 64 61   18 01

4.1 Tags: field number plus wire type

Every field begins with a tag, a varint holding two pieces of information packed together: (field_number << 3) | wire_type. The low three bits are the wire type, which tells the decoder how to find the end of the value without knowing the schema. The remaining bits are the field number you chose in the .proto file. For field 1 with wire type 0, the tag is (1 << 3) | 0 = 8 = 0x08. For field 2 with wire type 2 it is (2 << 3) | 2 = 18 = 0x12. For field 3 with wire type 0 it is 24 = 0x18. Because the tag uses 3 bits for the type, field numbers 1 to 15 fit in a single tag byte, which is why Protobuf advice says to give your most frequent fields small numbers.

Wire typeNameUsed forHow the decoder finds the end
0VARINTint32, int64, uint32, uint64, sint32, sint64, bool, enumRead bytes until one has its high bit clear
1I64fixed64, sfixed64, doubleExactly 8 bytes
2LENstring, bytes, nested messages, packed repeated fieldsRead a varint length, then that many bytes
5I32fixed32, sfixed32, floatExactly 4 bytes

The wire type is what makes forward compatibility possible. A decoder that meets a field number it does not recognise still knows, from the wire type, how many bytes to skip, so it can ignore the unknown field safely and move on (and many implementations even preserve it to write back out).

4.2 Varints: small numbers in few bytes

A varint (variable-length integer) stores a number in one to ten bytes, using 7 bits of the number per byte. The eighth, high bit of each byte is a continuation flag: 1 means "more bytes follow", 0 means "this is the last byte". The groups are written least significant group first. Numbers below 128 take exactly one byte; numbers below 16,384 take two; and so on. Since most integers in real data are small (counts, ids in the thousands, enum values), the typical cost is one or two bytes instead of the 4 or 8 of a fixed-width integer, or the 1 to 10 characters of text.

Varints have a catch with negative numbers. A negative int32 such as -1 is stored in two's complement, where all the high bits are 1, so as a varint it always takes the full 10 bytes (the value is sign-extended to 64 bits). For fields that are often negative, Protobuf offers sint32 and sint64, which use ZigZag encoding: it maps signed numbers to unsigned ones so that small magnitudes stay small, using the rule 0 becomes 0, -1 becomes 1, 1 becomes 2, -2 becomes 3, and so on. A field declared int32 holding -1 costs 10 bytes; declared sint32 it costs 1. Conversely, when values are typically huge and uniformly spread, such as hashes or random 64-bit ids, a varint wastes a byte or two, and fixed64 (always 8 bytes) is better.

4.3 Length-delimited fields and defaults

A string is written as its tag, a varint byte length, and the UTF-8 bytes. A nested message is encoded exactly the same way: tag, length, and then the nested message's own bytes. This recursive structure is why you can skip a whole sub-message without understanding it. A repeated numeric field is by default packed in proto3: one tag, one total length, then the values back to back, so a list of 100 small integers costs about 102 bytes, not 200.

In proto3, a field that equals its default value (0, empty string, false) on a plain field is not written at all. That makes records smaller again, but it also means the reader cannot tell "field was set to 0" from "field was never set" unless you declare the field optional, which adds explicit presence tracking. This distinction matters for partial updates: if you send an update message where age = 0 is omitted, does that mean "set age to zero" or "do not change age"? Use optional or a field mask to be explicit.

Then add the cost: "You give up readability and need schema management." That shows you know the tradeoff, not just the slogan.

5. Schema evolution and compatibility

Schemas change. Business adds a field, a team renames a concept, an old field is retired. In a monolith deployed all at once, you change both sides in one commit. In a distributed system you cannot, because three things are true simultaneously: services are deployed gradually (rolling upgrades mean old and new versions run side by side for minutes or days), mobile apps in the field stay on old versions for years, and persisted data (Kafka topics, files, database columns) lives far longer than any code version. Therefore, readers will meet data written by other versions of the schema, and the format and your discipline must make that safe.

5.1 The vocabulary: backward, forward, full

These terms are easy to mix up, so define them by who reads whose data:

  • Backward compatible: a new reader (new code) can read data written by an old writer. You can upgrade readers first and old data still works. This is the property you need for reading old rows from a database or replaying an old Kafka topic from the beginning.
  • Forward compatible: an old reader can read data written by a new writer. You can upgrade writers first, and old consumers that have not been updated yet keep functioning. This is what you need when producers deploy before consumers, or when old mobile apps receive responses from a new server.
  • Full compatible: both directions hold. It is the safest and the most restrictive, and it is what you want when you do not control the order of deployment.

Schema registries add transitive variants (for example backward transitive), which check the new schema against all previous versions rather than only the latest one. This matters when old data is retained for a long time, because a change that is compatible with version 5 might not be compatible with version 2.

Backward compatibility protects new code reading old data; forward compatibility protects old code reading new data. A rolling deploy needs both at once.

5.2 The rules for common changes

The details differ per format, but for Protobuf (and similarly Thrift) the working rules are these.

  • Adding a field: safe. Give it a new, never-used field number. Old readers skip the unknown tag (forward compatible), and new readers see the default when it is absent (backward compatible).
  • Removing a field: safe only if you never reuse its number or name. Mark the number reserved in the schema so nobody can assign it again. If a future field reused number 5 with a different type, old stored data with the old field 5 would be silently misread as the new one, which is data corruption with no error.
  • Renaming a field: safe in the binary format, because names are not on the wire, only numbers. But it is not safe for the JSON mapping or for any text format, where the name is the identity. It also breaks source-level code that uses the generated accessor. Treat a rename in a text API as "add new, deprecate old, remove later".
  • Changing a field's type: mostly unsafe. A few conversions are wire-compatible, for example int32, int64, uint32, uint64, and bool all share the varint wire type and can be read as each other (with truncation if the value does not fit), but changing int to string is not. When in doubt, add a new field instead.
  • Changing the field number: never. The number is the field's identity.
  • Making a field required: a trap, covered next.

5.3 Required fields and why they are harmful

Protobuf version 2 had a required keyword, meaning a message without the field is invalid. In practice it caused outages and was removed from proto3, and Google's own guidance is to never use it. The reason is that "required" is permanent: once a field is required, you can never remove it (old readers would reject messages without it) and never add one (old writers' messages would be rejected by new readers). It makes every schema change a coordinated, flag-day operation, which is exactly what independently deployed services cannot do. The better pattern is to make every field optional at the wire level and enforce business rules in application code or in a separate validation step, which can evolve independently of the format.

5.4 Avro: writer schema and reader schema

Avro takes a different approach to evolution. Because the encoded bytes have no field identifiers, a reader needs the exact schema the data was written with (the writer schema) and also has its own reader schema (what it wants). Avro's resolution rules reconcile the two: fields are matched by name; a field in the writer but not in the reader is skipped; a field in the reader but not in the writer takes its declared default; and certain type promotions (int to long, for example) are allowed. This gives powerful evolution, but it means every reader must be able to obtain the writer schema. For a single file, the schema sits in the file header. For a stream of independent messages in Kafka, it is looked up from a registry using an identifier (section 6). Renaming a field in Avro uses aliases to tell the resolver that the old name maps to the new one. Removing or adding fields with defaults follows the rules above: a field you might later delete should be given a default now, because a field without a default can never be removed safely in a backward-compatible way.

5.5 JSON evolution

With JSON there is no machine-enforced rule, only convention, but the same discipline applies. Readers should ignore unknown fields (a property sometimes called the "tolerant reader" pattern), producers should only add optional fields within a version, and anything breaking (removing or retyping a field, changing meaning) should require a new API version (Chapter 5). A large share of production incidents in microservices are caused by a deserializer configured to fail on unknown properties, which turns a harmless new field into an outage. Turn that setting off for inbound data you do not control.

Watch out The two most expensive schema mistakes are reusing a retired field number or name (silent corruption of old data) and changing the meaning of an existing field without changing its name or number (for example from seconds to milliseconds). No compatibility checker catches the second, because the types still match. Treat semantic changes as new fields.

6. Schema registries and distributing schemas

If the format requires a schema to read, then every reader needs a reliable way to get the right one. For a handful of services you can share a Git repository of .proto files and generate code from it, and for gRPC this is the normal practice: the schema is compiled into both client and server, and field numbers keep old and new versions compatible. But the problem is harder for event streams and data lakes, where thousands of producers and consumers, written in many languages, exchange data through a shared log such as Kafka, and where a record written last year must still be readable today.

A schema registry is a small service that stores versioned schemas and gives each one a numeric id. The best-known implementation is Confluent Schema Registry, with equivalents from AWS (Glue Schema Registry), Apicurio, and others. It supports Avro, Protobuf, and JSON Schema. It does two jobs.

  1. Lookup by id. Instead of embedding the schema in every message, the producer writes a few bytes of header, and the consumer fetches the schema once and caches it. In the Confluent wire format a message value starts with one magic byte (zero), then a four-byte schema id (big endian), then the encoded payload. That is 5 bytes of overhead identifying a schema that may be several kilobytes.
  2. Compatibility enforcement. When a producer registers a new schema version under a subject (typically the topic name plus -value), the registry compares it with earlier versions under the configured compatibility mode (backward, forward, full, or their transitive forms, or none) and rejects an incompatible one. A breaking change is therefore stopped at the producer's CI or startup instead of discovered later as broken consumers.

Operationally, the registry is a critical dependency at startup and on new schema ids, not on every message. Run it replicated (it stores its data in a Kafka topic or a database), cache schemas in the clients, and decide what producers do if it is unreachable (usually they fail to register but can still send with cached ids). Compatibility mode choice follows deployment order. For a Kafka topic where consumers may need to replay history from the start, backward (and usually backward-transitive) is the default and the right choice: upgrade consumers first, then producers. If you cannot control consumer upgrades and producers must go first, you need forward, and if both orders can happen, full.

Key idea A schema registry turns "schema agreement" from a social process (a wiki page and good intentions) into an enforced one (a gate that rejects incompatible changes). The price is one more piece of infrastructure and a 5-byte header on every message.

7. Columnar formats: Parquet and ORC

Everything so far describes row-oriented encodings, where all the fields of one record sit together. That layout is right for transactional work: to fetch an order you read one contiguous record. It is wrong for analytics. A query like "average order value by country over one billion orders" needs only two fields (amount and country) out of perhaps fifty. A row layout forces the engine to read and discard the other forty-eight fields of every row.

A columnar format stores all the values of one column together. Apache Parquet and Apache ORC are the standard on-disk columnar file formats for data lakes, warehouses, and engines such as Spark, Trino, Hive, and Snowflake external tables. (Chapter 23 covers warehouses; Chapter 37 covers the processing engines that read these files.) Their benefits come from three properties.

  • Column pruning. A query reads only the column chunks it names. If you select 2 of 50 columns, you read roughly 4 percent of the file.
  • Better compression and encoding. Within a column, values share a type and are often similar. A country column with five distinct values can be stored with dictionary encoding (a small table plus tiny integer codes), then run-length encoding for repeated codes, then a general compressor on top. Timestamps stored sorted compress with delta encoding (store the difference from the previous value). Columnar files commonly compress several times better than the same data in rows.
  • Predicate pushdown and skipping. Each chunk records its minimum and maximum value. A query with WHERE date = '2026-01-05' can skip every row group whose min and max range excludes that date without reading it. Combined with partitioning files by date in directories, a query over one day of a year of data reads about 0.3 percent of it.

The tradeoffs: columnar files are poor at single-record lookups and at frequent small writes, because to assemble a row you gather pieces from many column chunks, and because the encodings assume large immutable batches. That is why the usual pattern is to write events to a row-oriented log (Kafka with Avro or Protobuf) and then batch them into Parquet files every few minutes or hours, which also illustrates the batching theme of this chapter. Parquet and ORC are close cousins (ORC grew out of the Hive world and uses "stripes" where Parquet uses "row groups"; Parquet has wider cross-engine adoption). Apache Arrow is related but different: it is a columnar layout for in-memory data and zero-copy exchange between processes, not a storage format.

8. Compression: algorithms and tradeoffs

Compression re-encodes bytes into a smaller form by removing redundancy, and decompression restores the original exactly (this is lossless compression, the only kind appropriate for structured data and text; JPEG and MP3 are lossy and handled elsewhere). Compression works because real data is repetitive: JSON repeats field names, logs repeat prefixes, text repeats common words. Most general-purpose algorithms combine two ideas. LZ77-style matching replaces a repeated sequence with a short reference to where it appeared earlier ("go back 200 bytes and copy 12"). Entropy coding (Huffman or finite-state entropy coding) then spends fewer bits on frequent symbols and more on rare ones. Fast algorithms such as LZ4 and Snappy do only the matching with a simple format; slower, stronger ones such as gzip, Brotli, and Zstandard add entropy coding and search harder for matches.

8.1 The three-way tradeoff

Every algorithm trades compression ratio (original size divided by compressed size; higher is better), compression speed, and decompression speed. Most can be tuned with a level: higher levels search more and compress smaller but take much longer to compress, while decompression speed usually stays about the same. That asymmetry matters: for data compressed once and read many times (a static file served from a CDN, a Parquet file), pay for a high level at write time. For data compressed on every request (a dynamic API response), you need a fast level.

The point to remember is the ordering: LZ4 and Snappy are for "make it somewhat smaller at nearly no CPU cost", gzip is for "works everywhere", Zstandard is the modern general-purpose choice because it can sit at either end, and Brotli at a high level is for "compress once, serve a million times".

8.3 Compression stacks with the encoding choice

Compression and a compact format are independent levers and they overlap. JSON compresses spectacularly well because of repeated keys, so gzipped JSON may end up within 1.5 to 2 times the size of gzipped Protobuf, even though raw JSON is 3 times larger. Protobuf compresses less because it has already removed the redundancy, but it still benefits when strings or repeated records dominate. A rule of thumb: compress when the bytes cross a slow or metered link or sit on disk for a long time; choose a binary format when parsing CPU or tail latency is the problem. The CPU part of the story does not go away with compression: gzip adds CPU on both sides on top of JSON parsing, so a gzipped JSON API spends more CPU per request than plain JSON, and only wins on network.

9. When and where to compress

9.1 Decision by location

  • HTTP responses. The browser sends Accept-Encoding: gzip, br; the server (or the CDN, Chapter 12) replies with Content-Encoding: br or similar. This is almost always worth it for text such as HTML, CSS, JavaScript, JSON, and SVG, and a waste for already-compressed content such as JPEG, PNG, MP4, and ZIP (it burns CPU and can slightly grow the output). Static assets should be precompressed at the highest Brotli level during build; dynamic responses use gzip or Brotli at a low level. Compressing the request body is rarer, since clients are less likely to send it and servers must opt in to accept it.
  • Kafka. The producer compresses a whole batch of records (setting compression.type to lz4, snappy, zstd, or gzip). The broker stores the batch compressed and, if the codec matches, does not recompress; consumers decompress. This saves network between producer and broker, between brokers for replication, disk, and consumer fetch traffic, all with one compression step. Because compression works on the batch, larger batches compress better (section 10). A common production choice is lz4 or zstd.
  • Storage (databases, object storage, files). Compress at rest with a block-level or column-level codec. Snappy or LZ4 for hot data where CPU matters, zstd for colder or larger data, and a high zstd level for archival data that is written once. Columnar files layer encodings and a codec (section 7).
  • Caches (Redis, Memcached). Memory is the expensive resource, so compressing large values (tens of kilobytes of JSON, rendered HTML fragments) with LZ4 or zstd can double effective capacity at a cost of microseconds per access. Do not compress small values: the CPU and the header overhead outweigh the savings, and you lose the ability to inspect values by eye. See Chapter 13 for caching patterns.
  • Service-to-service RPC. gRPC supports per-message compression (gzip by default, others pluggable). Inside a data center with ample bandwidth it is often off; across regions or over metered links it is often on.

9.2 Compressing small payloads

Compression has a fixed overhead: headers (gzip adds an 18-byte wrapper), and, more importantly, an empty history window. The algorithm finds savings by pointing back at earlier data, and in a 200-byte message there is almost no earlier data. A 200-byte JSON object might compress to 160 bytes, a saving of 20 percent for a real CPU cost, and some tiny inputs even grow. Compression becomes worthwhile from roughly a kilobyte upward, and really pays off at tens of kilobytes. Below about 150 to 200 bytes, many servers skip it entirely (nginx's gzip_min_length and similar settings exist for this reason).

9.3 Dictionaries

The small-payload problem has a clever fix: give the compressor a shared dictionary, a block of typical content that both sides already have. The first bytes of a message can then refer into the dictionary instead of starting from nothing. Zstandard has a dictionary training tool: you feed it thousands of sample messages (for example 100,000 small JSON events), it extracts the commonly shared strings (field names, common values), and it produces a dictionary file of, say, 100 KB. Compressing 300-byte messages with that dictionary can reach ratios of 3 to 5x where plain compression gives 1.2x. Brotli does the same thing for the web with its built-in static dictionary, and the HTTP community is standardising negotiated shared dictionaries so a site can ship its own. The costs are operational: the dictionary becomes part of your schema. Every message must record which dictionary version compressed it, and old dictionaries must be kept as long as old data exists, which is the same discipline as schema evolution. Dictionary compression is therefore most useful for stores of many small, similar records such as session blobs, small events, and rows in RocksDB-style stores.

9.4 Compression bombs and security

A compression bomb (a "zip bomb") is a small input that expands to an enormous output, designed to exhaust memory or disk on whatever decompresses it. DEFLATE can reach a ratio of about 1,032 to 1, so a 1 MB upload can claim to be a gigabyte, and nested archives do far worse. Any service that decompresses data it did not produce (uploaded files, gzip-encoded request bodies, messages from the internet) must defend itself: set a hard limit on decompressed size and stop reading when it is exceeded; stream the output instead of buffering it; limit nesting depth for archives; check the declared uncompressed size but do not trust it; and apply timeouts and memory limits per request. The related idea applies to parsers: deeply nested JSON or XML entity expansion can have the same effect without any compression, so cap the document size and depth.

A second security caution is that compression can leak secrets when an attacker can influence part of the plaintext. The BREACH and CRIME attacks measure the compressed size of responses that contain both a secret (a CSRF token) and attacker-chosen text, and infer the secret from size changes. The mitigations are to avoid compressing responses that mix secrets with reflected user input, to randomise or mask tokens, and to disable TLS-level compression (which is now off by default).

Watch out Do not double-compress. Gzipping a Parquet file whose pages are already Snappy-compressed, or a JPEG, spends CPU for roughly nothing. Also remember that compression changes latency twice: it adds CPU time on both ends and subtracts transfer time. On a fast local network with large CPUs the subtraction can be smaller than the addition.

10. Batching

Batching means collecting several small items and handling them together as one operation. It is among the most powerful and most general performance techniques in systems, and it appears in nearly every component in this handbook. The reason is that most operations have a fixed cost that does not depend on how much data they carry:

  • A network round trip (half a millisecond inside a data center, 100 ms or more across continents) plus per-request headers and TLS record framing.
  • A system call, a context switch, a lock acquisition.
  • A disk operation: a seek on a spinning disk, or an fsync to make data durable on any disk, which can take about a millisecond on an SSD.
  • A transaction commit, which in a database means flushing the write-ahead log.

If you send 1,000 records one at a time, you pay the fixed cost 1,000 times. If you send them as one batch, you pay it once and the per-record cost is only the marginal bytes. Batching also helps compression (more history to match against), and it lets a server amortise parsing, authentication, and logging.

10.1 The cost: latency

Batching has one unavoidable price. The first item in a batch must wait for others to arrive, or for a timer. You trade per-item latency for throughput and efficiency. This is why systems expose two knobs rather than one.

10.2 Size and time triggers

A batch is flushed when either condition is met: a size trigger (the batch has reached N items or N bytes) or a time trigger (the oldest item has waited T milliseconds). The size trigger bounds memory and gives the efficiency; the time trigger bounds latency when traffic is light. Without the time trigger, a quiet period leaves a half-full batch waiting forever. Without the size trigger, a burst makes a single enormous batch.

A useful way to size them is Little's law intuition: if items arrive at rate R per second and you want batches of B items, then a batch fills in about B / R seconds. At 10,000 messages per second, a batch of 100 fills in 10 ms, so a 5 ms linger rarely fires and the size trigger rules. At 100 messages per second, the same batch needs a full second, so the time trigger will always fire first with about 1 item and 5 ms of latency, in which case batching hardly helps and costs 5 ms. Batching is a high-throughput technique and gives little at low load.

10.3 Batching in Kafka producers

The Kafka producer (Chapter 34) is the textbook case. Calling send() does not send anything immediately. It places the record in an in-memory buffer for the destination partition, and a background sender thread ships a batch per partition when ready. The relevant settings are batch.size (maximum bytes per partition batch, default 16 KB) and linger.ms (how long to wait for the batch to fill, historically 0 by default, which means "send as soon as the sender is free" but still batches records that arrive while a request is in flight; newer versions raise the default to a few milliseconds). Raising linger.ms to 5 to 20 ms and batch.size to 64 to 256 KB usually multiplies throughput for a modest latency cost. Compression is applied per batch (compression.type), so bigger batches also shrink better. Related knobs include buffer.memory (total buffered, beyond which send() blocks or fails: this is backpressure) and max.in.flight.requests.per.connection (how many unacknowledged requests may be pipelined, section 11). The durability setting acks interacts with batching: waiting for all in-sync replicas makes each batch slower, which makes large batches even more attractive.

On the consumer side, fetch.min.bytes and fetch.max.wait.ms are the same pair of triggers in reverse: the broker holds a fetch request until enough bytes are available or the wait expires, and max.poll.records controls how many records the application receives per call.

10.4 Database bulk writes

Imagine inserting 10,000 rows from an application to a database 0.5 ms away. One insert per statement, each in its own transaction, costs at least 0.5 ms of network plus a commit with a log flush each time, so around 10,000 x (0.5 + ~1) ms = 15 seconds. Sending the same rows as multi-row INSERT ... VALUES (...), (...), ... statements of 500 rows, inside one transaction, makes about 20 round trips and a single commit, which finishes in well under a second. Other forms of the same idea: JDBC addBatch/executeBatch (and driver options such as rewriteBatchedStatements for MySQL, or reWriteBatchedInserts for PostgreSQL), PostgreSQL's COPY for bulk load, and bulk APIs in Elasticsearch (_bulk) and DynamoDB (BatchWriteItem, which accepts up to 25 items). Databases themselves batch internally: group commit lets many concurrent transactions share one log flush. Limits to respect: huge batches hold locks longer, produce giant transactions that are slow to roll back and replicate, and risk hitting statement or packet size limits. Typical sweet spots are hundreds to a few thousand rows per batch. Handle failure explicitly: if row 4,000 violates a constraint, does the whole batch fail? Many bulk APIs return per-item results, and you must check them rather than assuming that an HTTP 200 means every item succeeded.

10.5 Request batching across services

Batching also applies to service calls. A client that needs data for 100 ids should send one GET /users?ids=1,2,...,100 or a POST /users:batchGet, not 100 requests, which is the N+1 problem across a network. GraphQL servers use a DataLoader pattern: within one request, individual lookups for different ids are collected for a very short moment (one tick of the event loop) and then issued as a single batched query. Clients can also batch writes such as analytics events, queuing them locally and uploading every 30 seconds or when 50 are queued. Design batch APIs with care: set a maximum batch size, define partial-failure semantics (per-item status codes in the response body), keep the operation idempotent so a retried batch does not double-apply (Chapter 32), and make sure one very slow item cannot hold the rest hostage. At the TCP level the same idea shows up as Nagle's algorithm, which delays small writes to coalesce them into larger segments; latency-sensitive applications disable it with TCP_NODELAY and do their own explicit batching instead.

Interview tip When you add batching to a design, always say both halves out loud: "I batch for throughput by flushing at N items or T milliseconds, whichever comes first, which adds at most T of latency, and the batch needs idempotent handling because retries resend the whole batch." Interviewers listen for the latency cost and the failure semantics.

11. Pipelining, framing and length-prefixing

11.1 Pipelining

Pipelining is a different way to amortise round trips: instead of waiting for the response to request 1 before sending request 2, you send several requests back to back and read the responses as they arrive. The batch is not one bigger message but many requests in flight at once. Redis clients pipeline commands: sending 1,000 GET commands in one write and reading 1,000 replies takes roughly one round trip instead of 1,000 (Chapter 15). Kafka's max.in.flight.requests.per.connection is the same idea. The danger is ordering and failure: if request 3 fails and requests 4 and 5 were already sent, a retry of 3 may land after 4 and 5, so strict ordering needs the idempotent-producer or sequence-number features. In HTTP/1.1, pipelining existed but was almost never used because responses had to come back in request order, so one slow response blocked all the ones behind it (head-of-line blocking). HTTP/2 replaced this with multiplexing: many independent streams share one connection and responses may interleave (Chapter 3).

11.2 Framing: where does one message end?

TCP is a byte stream, not a message stream. If a sender writes two 100-byte messages, the receiver might read 200 bytes at once, or 60 then 140, or 100 then 100. The protocol on top must therefore define message boundaries, called framing. There are three common ways.

  • Delimiter-based: a special byte or sequence marks the end, such as the newline in NDJSON and in many text protocols, or \r\n\r\n ending HTTP headers. Simple and human friendly, but the delimiter must never appear inside the data, so you need escaping, and the reader has to scan every byte to find the end.
  • Length-prefixed: each message starts with a fixed-size field stating how many bytes follow, such as a 4-byte unsigned big-endian integer. The reader reads 4 bytes, learns the length N, then reads exactly N bytes. No scanning, no escaping, binary-safe, and the reader can allocate the right buffer in advance. This is the default for binary protocols.
  • Fixed-size or type-length-value (TLV): every record has a type tag, a length, and a value, as Protobuf fields do internally (section 4).

Length-prefixing has two details worth knowing. First, always cap the length: a malicious or corrupted prefix claiming 3 GB would make a naive reader allocate 3 GB, which is a cheap denial-of-service attack (the same defence as for compression bombs). Second, agree on byte order (network byte order, big endian, is the convention) because a multi-byte length written on one CPU architecture must be read identically on another. Framing is also what lets batching and compression compose cleanly: a batch is a frame whose payload is a list of frames, optionally compressed as a unit, which is precisely how Kafka's record batch format is built.

12. Payload design for mobile and constrained clients

Mobile clients stress every theme of this chapter at once. Networks have high and variable latency (a cellular round trip of 100 to 300 ms is common), bandwidth can be poor or metered, battery drain is dominated by how often the radio wakes up, and the app code may be years out of date, so evolution rules are not theoretical. The design principles follow.

  • Fewer, fatter requests. Since latency, not bandwidth, usually dominates, return everything a screen needs in one response instead of making ten calls. A backend-for-frontend or an API gateway (Chapter 11) composes the screen payload server-side. GraphQL pursues the same goal by letting the client name the fields it wants.
  • Send only what the screen needs. A list screen needs thumbnails, titles, and ids; the detail comes on tap. Avoid returning the 60 fields of a full entity to a view that displays four. Field selection (sparse fieldsets, GraphQL, field masks) and list-versus-detail representations are the main tools.
  • Paginate and use cursors so the first screen loads fast (Chapter 5). Prefetch the next page while the user reads.
  • Compact encoding. Protobuf (or FlatBuffers for very large payloads that are read lazily) cuts bytes and parse CPU, which also saves battery. Where JSON must stay, enable gzip or Brotli and shorten gratuitously long keys only if you can measure a benefit; compression handles most of the repetition for you.
  • Delta and conditional requests. Use ETags and If-None-Match so an unchanged resource costs a tiny 304 response, or sync using a cursor ("give me everything changed since version 9,812") so the app downloads only differences.
  • Batch and defer uploads. Queue analytics and non-urgent writes locally and send them together, ideally while the radio is already awake or when on Wi-Fi. Each separate transmission keeps the radio in a high-power state for seconds afterwards (the "radio tail"), so many tiny uploads cost far more battery than one bigger one.
  • Tolerate old clients. Because you cannot force upgrades, treat every field as optional on the client, ignore unknown fields, keep old endpoints alive for a published support window, and use enums that have an "unknown" default so a new value in a response does not crash an old app.
  • Right-size media. Images usually dominate payload bytes. Serve responsive sizes and efficient formats (WebP, AVIF) from a CDN (Chapter 12) rather than inflating API responses with embedded base64 images.

13. Numeric, time and ID pitfalls

Many bugs that look like "the network corrupted our data" are really data-model mismatches between serializers. These are the ones that come up repeatedly.

13.1 64-bit integers in JSON

JSON the format has just one numeric syntax and puts no limit on digits. But most JSON parsers, notably JavaScript's, convert numbers to IEEE 754 double-precision floating point, which has a 53-bit significand. Integers are exact only up to 253 - 1 = 9,007,199,254,740,991. Above that, nearby integers collapse into the same double. A 64-bit id like 1234567890123456789 becomes 1234567890123456800 after a trip through JavaScript, and two different ids can become identical. Snowflake-style ids and database bigints are routinely this large (Chapter 32). The fixes: send 64-bit ids as strings in JSON (Twitter's API adds an id_str field for this reason; Protobuf's standard JSON mapping encodes int64 as a string for exactly this reason), or use a typed binary format, or use a parser that supports big integers. Do the same for any value that must not lose precision.

13.2 Floating point and money

Binary floating point cannot represent most decimal fractions exactly: 0.1 + 0.2 equals 0.30000000000000004 in doubles. Float32 holds only about 7 significant decimal digits. JSON also has no representation for NaN or Infinity, so a library may emit invalid output or null. For money, never use floats: store integer minor units (cents, as an integer 1999 for 19.99) together with a currency code, or use a decimal string, and agree on rounding rules. For measurements, document the unit in the field name (duration_ms, size_bytes) so nobody has to guess.

13.3 Timestamps and time zones

Time is the most common source of silent disagreement. Options: Unix epoch numbers (seconds or milliseconds since 1970-01-01 UTC), compact and unambiguous but unreadable, and with the seconds-versus-milliseconds confusion (the same number can mean 1970 or 2026, and a field in the wrong unit is a classic bug); ISO 8601 / RFC 3339 strings like 2026-11-17T09:30:00Z, readable and sortable when in UTC with a fixed format. Practical rules: store and transmit instants in UTC, always include the zone designator (Z or an offset), never send local times without a zone, convert to the user's zone only at the display edge, keep a time zone name (like Europe/Berlin) separately if you must schedule future local-time events (offsets change with daylight saving rules), and note that clock skew between servers means timestamps are not a reliable order of events (Chapter 27). Protobuf has a google.protobuf.Timestamp (seconds plus nanoseconds) to avoid the ambiguity.

13.4 Other traps

  • Null versus missing versus default. In JSON, {"x": null}, a missing x, and "x": 0 are three different statements; in proto3 a zero value and an absent one look the same unless the field is marked optional. Partial update APIs (PATCH) need explicit rules, for example a field mask.
  • Enums. A client that sees an enum value it does not know should not crash. Keep a meaningful zero value such as UNKNOWN, and never reorder or reuse numeric values.
  • Strings and encoding. Always use UTF-8; be aware that the same visible text can be written with different Unicode normalisation forms, so compare after normalising; and that "length" may mean bytes or characters depending on the API.
  • Binary data in JSON must be base64 encoded (a 33 percent size increase) and is a sign you probably want a binary format or a separate blob upload.
  • Duplicate keys and ordering. JSON objects with repeated keys are handled differently by different parsers, and key order is not guaranteed; so never sign or hash a JSON document without first putting it in a canonical form.
  • Endianness and alignment only matter if you hand-roll a binary protocol, which is a reason to use an established format rather than writing one.
Watch out A design that serves browser clients with large numeric ids will be wrong in JSON unless the ids are strings. This is a favourite "did you notice" probe in interviews, and the answer is one sentence: "Ids go over the wire as strings because JavaScript numbers lose precision above 2^53."

14. Worked example: JSON versus Protobuf at 50,000 requests per second

Suppose an internal pricing service receives 50,000 requests per second. Each response carries a list of about 20 line items with ids, quantities, and prices. We will compare plain JSON, gzipped JSON, Protobuf, and Protobuf compressed with Zstandard. All the per-message numbers below are illustrative assumptions consistent with typical measurements; in a real design you would benchmark with your own payloads.

14.1 Assumptions

  • JSON response: 1,200 bytes on average. The same data in Protobuf: about 480 bytes (40 percent, because field names vanish and numbers become varints).
  • gzip on the JSON: about 300 bytes (ratio 4 on repetitive JSON). Zstd on the Protobuf: about 300 bytes (the more compact data compresses less, so the two compressed versions end up close).
  • CPU per request on the server for decoding the request and encoding the response: JSON about 60 microseconds, Protobuf about 15 microseconds. Compression adds about 40 microseconds for gzip on this payload, and about 10 for zstd at a fast level.
  • Egress is priced at an illustrative $0.05 per GB, and a month is 30 days (2,592,000 seconds).

14.4 Conclusions and recommendation

  • If this is a public API consumed by browsers and third parties, keep JSON, enable Brotli or gzip at the edge (or in the CDN), and spend the effort on pagination and payload trimming. Savings from a binary format would not reach external clients.
  • If this is an internal, high-volume service-to-service call, use Protobuf over gRPC. The gain is not dramatic in cores at this scale, but it is a 60 percent cut in bytes, a 4x cut in parse CPU, schema enforcement, generated clients in every language, and clean evolution rules. Add compression only if the link is metered or cross-region.
  • For events landing in Kafka, use Avro or Protobuf with a schema registry, compress batches with lz4 or zstd, and batch into Parquet for analytics.
  • Cost ranking depends on scale: at 500 rps all of this is noise and JSON wins on simplicity; at 500,000 rps it is a major line item. Say the scale before choosing.

15. Interview Q&A

Why would you choose Protobuf over JSON for internal services, and when would you not?

Protobuf gives smaller messages (no field names, varint integers), faster encode and decode, a machine-checked schema that generates typed clients in many languages, and explicit evolution rules based on field numbers. It pairs naturally with gRPC. I would choose it for high-volume or latency-sensitive internal calls and for long-lived data like event logs. I would not choose it for a public API aimed at browsers and third-party developers, where being able to try the API with curl and read it by eye matters more than a few hundred bytes, or for tiny-scale systems where the tooling and schema management cost outweighs the saving. The usual answer is to keep JSON at the edge and Protobuf inside, with the gateway translating between them.

Explain how Protobuf encodes a field, and why field numbers must never be reused.

Each field is written as a tag followed by a value. The tag is a varint equal to (field number shifted left by 3) OR the wire type, so it tells the decoder both which field this is and how to find the end of the value: varint, fixed 32 or 64 bit, or length-delimited. Field names are not on the wire; the schema maps numbers to names. Because the number is the field's only identity, reusing a retired number for a new field means that old stored records, or old writers still running, will have their old data interpreted as the new field, possibly with a different type, producing silent corruption. That is why removed fields are marked reserved in the schema so no one can reuse the number.

What is the difference between backward and forward compatibility, and which do you need in a Kafka pipeline?

Backward compatible means new readers can read data written by old writers; forward compatible means old readers can read data written by new writers. In a Kafka pipeline topics retain history and consumers may replay it from the start, so new consumer code must read old records, which is backward compatibility, and the registry default and usual recommendation is backward (often transitive so that all old versions are checked). The deployment order is consumers first, then producers. If producers may be upgraded before some consumers, as with many independent teams, you additionally need forward compatibility, and the safest setting is full compatibility, which restricts you to adding or removing optional fields with defaults.

How does a schema registry work and what are its failure modes?

The registry stores versioned schemas under subjects and assigns each a global id. Producers register their schema, the registry checks it against earlier versions using the configured compatibility mode and rejects breaking changes, and the producer then prefixes each message with a magic byte and the four-byte schema id. Consumers read the id, fetch the schema once, cache it, and decode with the writer schema resolved against their own reader schema. The registry is not on the per-message path, so a short outage mostly affects new producers or new schema ids; clients with cached schemas continue. The real failure modes are an unreplicated registry (a single point of failure at startup), a too-permissive compatibility mode that lets breaking changes through, and semantic changes that no checker can catch, such as changing a field from seconds to milliseconds.

You have a service that compresses all responses with gzip and CPU usage is high. What do you look at?

First, find out what is being compressed: already-compressed content like images, or tiny responses under a few hundred bytes, waste CPU for nothing, so I would add a content-type allow list and a minimum size. Second, check the compression level; levels above 6 cost a lot more CPU for small ratio gains, so dynamic responses should use a low level, while static assets should be compressed once at build time at a high level and cached. Third, consider moving compression to the CDN or load balancer, or switching to Zstandard or Brotli at a low level, which give better ratios per CPU. Finally, I would verify that bandwidth savings actually matter on that path; inside a data center it is often better to turn compression off and rely on a compact format.

What is a compression bomb and how do you defend against it?

It is a small compressed input that expands into a huge output, such as a 1 MB upload that inflates to a gigabyte or more, intended to exhaust memory, disk, or CPU of the service that decompresses it. DEFLATE can reach about a thousand to one, and nested archives are far worse. The defence is to enforce a hard cap on decompressed bytes and stop as soon as it is exceeded, stream the decompression instead of loading it all into memory, limit archive nesting and file counts, set CPU and time limits per request, and not trust the size declared in a header. The same principle of capping sizes and depth applies to parsers for JSON, XML, and length-prefixed frames.

How do Kafka producers batch, and how would you tune them for throughput versus latency?

A producer appends records to a per-partition in-memory batch and a sender thread ships a batch when it reaches batch.size bytes or has waited linger.ms, whichever happens first. Compression is applied to the whole batch, so a larger batch also compresses better, and the broker stores it compressed. For throughput I would raise linger.ms to roughly 5 to 20 ms, raise batch.size to tens or hundreds of kilobytes, and enable lz4 or zstd. For latency I would keep linger.ms near zero, accept smaller batches, and watch that acks and in-flight request settings do not serialize sends. The tradeoff is that linger directly adds up to that many milliseconds to each record at low load, so the benefit only appears when traffic is high enough for batches to fill.

Why can a JSON API corrupt 64-bit ids and how do you prevent it?

JSON allows arbitrarily long numbers, but many parsers, including every JavaScript engine, read numbers as 64-bit floating point doubles, which represent integers exactly only up to 2 to the 53 minus 1. A Snowflake-style or bigint id above that value is rounded to a nearby representable number, so two distinct ids may become equal or an id may no longer match the database. The prevention is to transmit such ids as strings in JSON, which is what Protobuf's JSON mapping does for int64, to use a binary format with real 64-bit types for service-to-service traffic, and to add contract tests that round-trip large ids through the browser client.

How would you design the payload for a mobile feed screen?

I would optimise for fewer round trips and fewer bytes, because mobile latency and radio power dominate. One request returns the first page of the feed, composed server-side by a backend-for-frontend, containing only the fields the list needs (ids, titles, small thumbnail URLs), with a cursor for the next page and an ETag or sync token so unchanged data costs a tiny response. I would use Protobuf or compressed JSON, serve images separately from a CDN in responsive sizes and efficient formats, and batch analytics events to upload together later. Because old app versions linger, every field is optional on the client, unknown fields and enum values are tolerated, and I keep old API versions alive for a published support window.

When is batching a bad idea?

Batching is a bad fit when load is low, because the time trigger always fires first and every item simply pays the added wait with none of the efficiency gain. It is also unsuitable when per-item latency is a hard requirement, such as an interactive keystroke or a payment confirmation the user is staring at, unless the batch window is tiny. Large batches also raise failure cost: a failed batch must be retried as a whole or handled with per-item results, retries need idempotency to avoid duplicates, and huge database batches hold locks and bloat transactions. Finally, a batch that grows without bound causes memory pressure and head-of-line delays, so every batcher needs a size cap and backpressure.

How do columnar formats like Parquet make analytic queries faster?

They store each column's values together, so a query reads only the columns it names (column pruning), and similar values stored together compress and encode very well through dictionary, run-length, and delta encoding. Each chunk keeps min and max statistics in the file footer, so the engine can skip whole row groups that cannot match a filter (predicate pushdown), and partitioning files by date skips whole files. The cost is that fetching or updating a single full record is slow and files are best written in large immutable batches, so they suit data lakes and warehouses rather than transactional lookups.

16. Recap

  • Serialization turns in-memory objects into bytes; the format decides CPU cost, size, and how safely data can change over time.
  • Text formats (JSON, XML, CSV) are readable and self-describing but large and slower; binary formats (Protobuf, Avro, Thrift, MessagePack, FlatBuffers) are compact and fast, usually needing a schema.
  • Protobuf encodes each field as a tag (field number and wire type) plus a value; integers are varints; defaults are omitted. The 37-byte JSON record became 10 bytes.
  • Schema evolution: add fields with new numbers and defaults, never reuse numbers (reserve them), avoid required fields, and treat meaning changes as new fields. Backward means new readers read old data; forward means old readers read new data.
  • Schema registries store versioned schemas, hand out ids carried in a 5-byte header, and reject incompatible changes before they ship.
  • Parquet and ORC store data by column, enabling column pruning, strong compression, and min/max skipping for analytics.
  • Compression trades ratio against CPU: LZ4 and Snappy for speed, gzip for compatibility, Zstandard as the flexible modern choice, Brotli at high levels for static web assets. Skip it for small or already-compressed data, use dictionaries for small similar messages, and cap decompressed size against bombs.
  • Batching amortises fixed per-operation costs; flush on size or time, whichever first; it adds latency and needs idempotent, partial-failure-aware handling. Kafka batches per partition and compresses per batch.
  • Pipelining keeps many requests in flight; TCP is a stream, so protocols need framing, usually a length prefix with a size cap.
  • Mobile payloads: fewer requests, only needed fields, deltas and ETags, batched uploads, tolerance of old clients.
  • Pitfalls: 64-bit ids as strings in JSON, no floats for money, UTC timestamps with explicit units, careful null versus default semantics.
