Service Discovery and Configuration

In a system of many small services that start, stop and move all day, two questions decide whether anything works: "where is the service I need to call right now?" and "what settings and secrets should I run with?" This chapter explains how registries and platforms answer the first, how configuration and secrets systems answer the second, and how each can fail.

1. Why static addresses fail

In the simplest deployment, the orders service calls the payments service at a fixed address, say 10.0.4.17:8080, written in a config file. That works when payments runs on one long-lived machine that nobody ever replaces. A modern system breaks every part of that assumption.

  • Autoscaling. The number of payment instances changes with load, as described in Chapter 43. At 3 a.m. there may be 4 instances; at noon there may be 40. A fixed list of addresses is wrong within minutes of being written.
  • Containers and orchestration. A container scheduler places each container on whichever machine has room, and gives it an address from a pool. When the container restarts, it usually gets a different address. The address belongs to the instance, not to the service.
  • IP churn from deployments. A rolling deployment replaces every instance, one by one. After a full rollout, none of the old addresses exist any more.
  • Failures. A machine dies, and its address now leads nowhere (or, worse, is reassigned to a different service entirely).
  • Multiple environments and regions. The same logical service lives at different addresses in dev, staging and production, and in each region.

Hand-editing config files, or even automating them with a deploy script, does not keep up. Callers would need to be redeployed every time any dependency moved. The core idea of service discovery is a level of indirection: callers ask for a logical name (payments), and a system that always knows the current set of healthy instances turns that name into one or more addresses at the moment of the call.

Key idea Service discovery separates identity (a stable logical service name) from location (the current, changing set of instance addresses). Everything in the first half of this chapter is a different answer to "who maintains the name-to-location mapping, and who consults it?"

2. The service registry

The central building block is the service registry: a database of the form "service name → list of live instances (address, port, metadata)". Metadata can include the version, the availability zone, weights, or tags such as canary. Only two operations really matter: write (an instance joins, leaves or reports it is alive) and read (a caller asks for the instances of a name). Reads vastly outnumber writes, because every outgoing call potentially needs a lookup, while writes happen only when instances change or send periodic heartbeats.

The registry is unusual among databases because it holds soft, constantly decaying state. A record such as "payments instance at 10.0.4.17 is alive" is true only for as long as that process is alive and reachable. So a good registry does not trust that records stay correct; it keeps them fresh with heartbeats and expires them when the heartbeats stop (section 3).

Examples you should be able to name: Netflix Eureka, HashiCorp Consul, etcd and Apache ZooKeeper (general coordination stores used as registries), the Kubernetes API server (a registry of Pods, Services and endpoints), AWS Cloud Map, and the control planes of service meshes (Chapter 50).

3. Registration, heartbeats and deregistration

3.1 Who registers an instance

There are two registration models.

  • Self-registration. The service instance itself calls the registry on startup ("I am payments at 10.0.4.17:8080"), keeps sending heartbeats, and tells the registry when it shuts down. Netflix Eureka clients work like this. The advantage is simplicity: no extra infrastructure, and the service knows its own health best. The downsides: every service in every language needs registry client code (or a library), registration logic is coupled to application code, and a process that hangs without crashing may keep heartbeating from a background thread even though it cannot serve requests.
  • Third-party (platform) registration. Something other than the instance watches for instances starting and stopping and updates the registry on their behalf. In Kubernetes, the control plane sees Pods become Ready and adds them to the Service's endpoints; the application contains no registration code at all. Consul can do this with an agent or a sidecar, and tools such as Registrator watch the container runtime. The advantage is that services stay unaware of discovery, so any language works and the policy lives in one place. The cost is another component that must be operated and trusted.

Modern platforms overwhelmingly favour third-party registration, because the orchestrator already knows precisely when containers start and stop.

3.2 Heartbeats, TTLs and health checks

How does the registry know an instance is still alive? There are two designs.

  • Heartbeat with TTL (instance pushes). The instance renews its registration every N seconds (Eureka defaults to 30 seconds with a 90 second expiry, typically). Each renewal resets a time-to-live (TTL) timer. If the timer reaches zero, the registry removes the record. This detects crashes, machine loss and network isolation without any special handling, because a dead process simply stops sending.
  • Active health check (registry or agent pulls). The registry (or a local agent) calls a health endpoint on each instance, for example GET /health every 10 seconds, and marks the instance unhealthy after a number of consecutive failures. This is stronger than a heartbeat because it proves the instance can actually respond, not merely that some thread is running. Consul and Kubernetes (readiness probes) work this way.

A healthy design separates two questions. Liveness: is the process alive, or should it be restarted? Readiness: can it take traffic right now? A service that is starting up, loading a cache, or temporarily overloaded should stay registered as alive but not ready, so that it receives no traffic until it recovers. Registering an instance before it is ready is a classic cause of errors during deployments.

3.3 Graceful and ungraceful departure

On a clean shutdown the instance deregisters first, waits a short time for callers to notice (see section 9 on propagation delay), finishes in-flight requests, and only then exits. This is called connection draining. On a crash nothing is deregistered, so the record lingers until the TTL expires or health checks fail. A stale entry is a record that still claims an instance is available after it has gone. Callers that pick a stale entry see connection refused or timeouts. Because stale entries cannot be eliminated completely, callers need retries and timeouts with a different instance on each retry (Chapter 47).

Watch out Short TTLs find failures faster but cost more heartbeat traffic and risk false evictions when a healthy instance misses a beat during a garbage-collection pause or a network blip. Long TTLs are cheap but leave a long stale window. Typical systems choose tens of seconds and rely on client-side retries to cover the gap.

4. Client-side discovery

In client-side discovery, the caller does the lookup itself. A discovery library inside the caller asks the registry for the list of instances of payments, caches that list locally, picks one using a load-balancing algorithm (round robin, least connections, random of two, zone-aware), and sends the request directly to that instance.

Well-known examples: Netflix Eureka as the registry with Ribbon (later Spring Cloud LoadBalancer) as the in-process balancer; gRPC, whose channels use pluggable resolvers (DNS, xDS, custom) and built-in balancing policies such as round_robin; and Consul clients using the Consul API.

Advantages. There is no extra network hop and no shared load balancer to become a bottleneck or a single point of failure, so latency is lower and capacity scales with the number of callers. The client can use application knowledge to choose well (prefer same-zone, avoid instances that recently errored, use request-aware hashing).

Disadvantages. Every language and framework in the company needs a correct, up-to-date client library, and fixing a bug in it means redeploying every caller. Callers hold registry connections, which creates many watchers on the registry. And each caller makes independent decisions on a slightly different view of the instance list, so load is not perfectly balanced.

5. Server-side discovery

In server-side discovery, the caller sends the request to one stable address, a load balancer or router, and that component does the lookup and picks an instance. The caller needs no discovery code; it simply uses a well-known name or virtual IP.

Examples: an AWS Application Load Balancer with a target group (instances register to the target group, either automatically via Auto Scaling or ECS, and the ALB health-checks them); Kubernetes Services, where kube-proxy programs rules on every node so that a virtual IP forwards to a healthy Pod (section 7); and Envoy or NGINX acting as a gateway or sidecar, fed by a control plane. See Chapter 9 for balancer internals, algorithms and health checks.

Advantages. Callers stay simple and language-agnostic, and policy (retries, timeouts, TLS, rate limits) can be applied in one place. Disadvantages. An extra hop adds latency, and the balancer must itself be made highly available and scaled; it becomes critical infrastructure on every request path.

6. DNS-based discovery

DNS is the oldest and most universal discovery system. Every language, every operating system and every tool already knows how to resolve a name to an address (Chapter 4 covers resolution in depth). Pointing callers at payments.internal.example.com and keeping the DNS records updated is the lowest-friction form of discovery: no client library at all.

6.1 Record types

  • A / AAAA records map a name to one or more IP addresses. A name with several A records is a primitive load balancer, because resolvers typically rotate or shuffle the order.
  • SRV records add what A records lack: a port, plus a priority and weight per target (_payments._tcp.internal.example.com). They are what lets DNS answer "which host and which port", which matters when containers get dynamic ports. Consul and Kubernetes (for named ports) publish SRV records, but many HTTP clients ignore them and use only A records, so the port ends up fixed by convention.

6.2 The TTL and caching problem

DNS was designed for data that changes rarely, so answers are cached aggressively at many layers: the recursive resolver, the operating system, and the application runtime. Every cached answer is valid for the record's TTL. If an instance dies, clients keep receiving its address from caches until the TTL runs out. Lowering the TTL to a few seconds shortens the stale window but increases query load on the DNS servers, and, importantly, some clients ignore TTLs altogether. The classic example is a Java virtual machine that, under some security settings, caches successful lookups forever, or a long-lived connection pool that resolved the name once at startup and never again.

Other limits of plain DNS: UDP responses are small, so a name with hundreds of instances may be truncated or require TCP; DNS has no notion of health beyond what the server decides to publish; and clients that take only the first A record concentrate load on one instance.

DNS is therefore a good fit for coarse-grained discovery (a regional endpoint, a managed database cluster endpoint, a load balancer's address) and a weak fit for fast-moving fleets of tiny instances, unless a platform such as Kubernetes keeps the answers stable by returning a virtual IP rather than instance addresses, as the next section shows.

7. Kubernetes service discovery in detail

Kubernetes is the most common place you will meet discovery in practice, and it uses third-party registration plus server-side discovery plus DNS together. The pieces:

  1. Pods are the running instances, each with its own IP, created and destroyed by Deployments. A Pod's IP changes on every restart.
  2. A Service is a stable object with a name, a label selector (app=payments), and by default a virtual ClusterIP. The ClusterIP does not belong to any machine; it is a stable address that exists only in forwarding rules.
  3. Endpoints / EndpointSlices are the registry. A controller watches Pods matching the selector and records the IP and port of each Pod that is Ready (its readiness probe passes). Readiness is how the platform implements health-based registration. Large Services are split into EndpointSlices (typically up to 100 endpoints each) so that one Pod change does not force re-sending a giant object to every node.
  4. kube-proxy runs on every node. It watches Services and EndpointSlices through the API server and programs the node's kernel (iptables rules, IPVS tables, or an eBPF data plane in some CNIs) so that a packet to the ClusterIP is rewritten to one of the ready Pod IPs. This is the server-side discovery part, performed in every node's kernel with no central balancer machine.
  5. CoreDNS is the cluster DNS server. It watches the API and answers payments.shop.svc.cluster.local with the Service's ClusterIP. Pods are configured so that the short name payments also resolves (search domains), so a caller just writes http://payments.

7.1 Headless Services

Setting clusterIP: None creates a headless Service: no virtual IP, no kube-proxy rules. DNS instead returns the individual Pod IPs as multiple A records. This is for cases where the client must talk to a specific instance or do its own balancing: a gRPC client that wants to spread long-lived streams over all backends, or a StatefulSet (database, Kafka, ZooKeeper) where each member needs a stable identity such as kafka-0.kafka.shop.svc.cluster.local. The trade-off is that you are back to DNS caching problems, because clients hold Pod IPs directly.

7.2 Practical points

  • A ClusterIP balances connections, not requests. Because HTTP/2 and gRPC multiplex many requests over one long connection, a plain ClusterIP can send all traffic from one caller to a single Pod; use a headless Service with client-side balancing or an L7 proxy.
  • Readiness, not liveness, controls membership. A Pod that fails readiness is removed from endpoints but not restarted.
  • Removal is not instant. Terminating Pods leave endpoints, but kube-proxy updates take a moment on each node, so well-behaved apps keep serving for a few seconds after receiving the shutdown signal (a preStop delay) so in-flight and late-arriving requests still succeed.
  • Ingress controllers and gateways (also server-side discovery) watch the same EndpointSlices for external traffic.

8. Consul, etcd and ZooKeeper, and AP versus CP registries

Three general-purpose stores are commonly used as registries. ZooKeeper and etcd are strongly consistent coordination stores, built on consensus protocols (Zab and Raft respectively), and are covered in Chapter 30. A service registers by creating an ephemeral node (ZooKeeper) or a key attached to a lease (etcd). If the instance's session or lease expires because heartbeats stop, the key is deleted automatically, giving heartbeat-and-TTL expiry for free. Callers watch the key prefix and are notified of changes. Consul adds service-discovery features on top of Raft: a catalog, agents on every node performing health checks, DNS and HTTP query interfaces, and a key-value store.

8.1 CP versus AP: what should the registry do during a partition?

The CAP trade-off (Chapter 28) applies sharply here. A CP registry (ZooKeeper, etcd, Consul servers) requires a quorum. If a network partition leaves a node on the minority side, it cannot read or write reliably, and may refuse to answer. Data is never wrong, but a service may be unable to find its dependencies exactly when the network is already unhealthy.

An AP registry keeps answering from whatever it knows, accepting that the answer may be stale or that replicas may disagree briefly. Netflix Eureka deliberately chose AP. Netflix's reasoning: a stale list that contains a few dead instances is much less harmful than no list at all, because a caller can try another instance on error, but a caller with no list cannot do anything. Eureka servers replicate peer-to-peer without a leader, and clients cache the full registry locally.

8.2 Eureka self-preservation mode

Eureka removes instances that miss heartbeats. But imagine a network partition that cuts the Eureka server off from many healthy instances at once. Removing them all would empty the registry, and callers would find nothing even though the instances are fine. So Eureka tracks the expected number of renewals per minute. If renewals fall below a threshold (85 percent of expected by default), it concludes the problem is probably itself and the network, not the instances, and stops expiring entries. This is self-preservation mode. The registry then retains possibly dead instances (the dashboard warns about it), and clients must cope with failed calls. The principle is worth remembering: when a mass of failures looks correlated, be suspicious of the observer before trusting the observation.

Which should you pick? A pragmatic rule: discovery reads should be AP-like even if the registry writes are CP. Consul does this: servers use Raft for the catalog, but agents and clients cache and can serve stale reads on request. Kubernetes does this too: the API server and etcd are CP, but every node and client keeps a locally cached copy of Services and EndpointSlices, so if the control plane is down, existing traffic keeps flowing on the last known forwarding rules. You pay with the inability to see changes while the control plane is down, not with an outage.

9. Consistency and propagation delay

Whatever registry you choose, a change does not reach every caller instantly. Think of a single instance dying and follow the information through the chain of caches, each with its own delay:

Two consequences. First, the discovery system never replaces error handling: callers need connect and request timeouts, retries that choose a different instance, and ideally outlier detection (temporarily stop sending to an instance that returns errors, a feature of Envoy and Ribbon-style balancers). Second, new instances need a warm-up: they join late, and when they do, a naive least-connections balancer sends them a flood because they have zero connections, so good balancers use slow-start ramps.

Stronger consistency is available (reads through a consensus leader, as in etcd and Consul's default mode), but it costs latency and availability and still cannot fix the client's own cache. For almost all discovery needs, eventual consistency plus resilient callers is the right design.

10. Failure modes

10.1 The registry is down

If every lookup goes to the registry at call time, a registry outage stops the whole company at once: this is why the registry sits near the top of any list of critical dependencies. The universal mitigation is caching the last known good list on the client or in a local agent and continuing to use it while the registry is unreachable. A caller that can still reach its dependencies with a slightly old list is almost always better off than one that fails closed. Run the registry as a replicated cluster across at least three failure domains, keep it small and simple, and never put business logic in it.

10.2 Stale instances

Covered in section 3 and 9: crashes leave entries until expiry. Mitigate with sensible TTLs, readiness checks that actually exercise the dependency path, client retries, and outlier ejection. A subtler version is the zombie instance: it heartbeats happily but cannot serve (deadlocked request threads). This is why a health check should call a real endpoint and not rely on a background heartbeat.

10.3 Thundering herd of lookups

Imagine 5,000 callers each caching a list with a 30 second expiry. If they all expire at the same moment (after a restart of a fleet, or after a registry recovers), they all query the registry together, and the registry, perhaps already struggling, falls over again. Standard defences are: add random jitter to cache expiries and poll intervals; use watches or long polls (the registry pushes deltas) so that no one polls; put a local caching agent on each node so that thousands of processes share one connection; and make the registry's read path cheap and horizontally scalable (followers or caching tiers can serve reads). Kubernetes uses watches against the API server, with EndpointSlices keeping each update small. A related herd is a retry storm: when callers fail at once, naive immediate retries multiply the load. Use exponential backoff with jitter and retry budgets.

10.4 Flapping and bad health checks

A health check that is too sensitive removes instances under load; the remaining instances then take more load and fail the check too, and the whole pool is gone: a cascading failure. Counter with a minimum healthy fraction (a "panic threshold": if fewer than, say, half the instances are healthy, balancers such as Envoy ignore health status and spread traffic over all of them) and with hysteresis (require several consecutive failures to remove, and several successes to add back).

11. Service mesh discovery and multi-region discovery

11.1 Service mesh

A service mesh (Chapter 50) moves discovery out of application libraries and into a sidecar proxy (for example Envoy) beside every service instance. A central control plane (Istio's istiod, Consul, Linkerd) watches the registry (in Kubernetes, the API server) and pushes the up-to-date endpoint lists to every sidecar through a streaming API. In Envoy this family of APIs is called xDS: endpoints are served by EDS, clusters by CDS, routes by RDS. The application simply calls http://payments, the sidecar intercepts the call, picks an endpoint from its pushed list, applies retries, timeouts, circuit breaking, locality preference and mutual TLS, and forwards the request. This gives client-side discovery behaviour (no extra central hop, rich balancing) with server-side simplicity for the developer. The cost is operational: more moving parts, more memory per Pod, and a control plane whose outage leaves sidecars running on their last configuration.

11.2 Multi-region and multi-cluster discovery

Once you run in several regions or clusters, discovery must answer "which payments should I call: the local one or a remote one?" Common patterns:

  • Local first, remote on failure. Callers prefer instances in their own zone and region (lower latency, no cross-zone data charges) and spill over to another region only if local capacity is unhealthy or exhausted. Locality-aware balancing in Envoy, Eureka zones and Consul prepared queries all support this.
  • Per-cluster registries, federated. Each cluster has its own registry for its own instances, and a federation layer exposes selected services across clusters. Consul has WAN federation and cluster peering; Kubernetes uses multi-cluster Services, mesh gateways, or global load balancing in front.
  • Global DNS or global load balancers for entry points. The cross-region decision for external traffic uses geo or latency-based DNS and health-checked failover (Chapter 4, Chapter 9), while internal calls stay regional.
Watch out Failover across regions can overload the surviving region: if A fails and all its traffic spills into B, B needs the headroom to absorb it, and its data stores need to be reachable and consistent enough (Chapter 26). Spillover should be tested and capped, not left as a silent default.

12. Configuration management

The second half of the chapter covers the other thing every instance needs at start-up: its settings. Which database should I connect to, how many threads, what timeout, which features are on, what is the downstream address, what are my credentials?

12.1 Config versus code

The guiding principle, from the twelve-factor app methodology, is a strict separation: code is the same artifact in every environment; configuration is whatever differs between environments (and deploys). The same container image that passed testing must be promoted unchanged to staging and then production, with only the config switching. If you rebuild the image per environment, what you tested is not what you ship. Twelve-factor also recommends storing config in the environment (environment variables) rather than checked into the code as constants or per-environment files in the app, and never grouping config into named environments like "staging" in code, because those multiply combinatorially.

A useful distinction: static config is read at start-up and requires a restart to change (port, database URL). Dynamic config can change while running (log level, rate limit, timeout, feature flags). The more you can make dynamic, the faster you can react in an incident, but each dynamic setting is a way of changing production behaviour without a deploy, which calls for the same safety as a deploy (section 14).

12.3 Push versus pull

How do changes reach running instances? In a pull model, each instance polls the config store every N seconds (or on an interval with a version tag so that it downloads only when something changed). Pull is simple, robust (a missed message is repaired at the next poll) and puts the burden on clients, so the store can be dumb and cacheable. In a push model, the store notifies instances using watches, long-polling, or a message bus (Spring Cloud Bus broadcasting a refresh event, etcd watches, Consul blocking queries). Push is faster, but requires persistent connections and a design for lost notifications; most mature systems combine push for speed with periodic pull as a safety net.

Applying a new value also takes care. Instances should validate the new config before using it and keep the previous value if the new one is invalid, and should apply changes atomically (swap a whole immutable object rather than mutating fields piece by piece, so a request never sees half of one version and half of another).

12.4 Versioning and rollback

Treat config as versioned data. Store it in Git or in a store with immutable versions, so that every change has an author, a time, a reason and a diff, and rollback is "make version 41 current again". Each running instance should expose which config version it is using (in a metrics label or a status endpoint), so that during an incident you can see whether a bad change has reached everybody. Rollback speed matters: a config change you cannot revert in seconds is a risk you are carrying.

13. Config safety

Large public post-mortems repeatedly find that a configuration change, not a code bug or hardware failure, triggered the outage: a bad firewall or routing rule pushed everywhere, an expired setting, a typo that sets a limit to zero, a feature flag flipped for all users. The reason is structural. Config changes often bypass the testing, code review and gradual rollout that code deployments go through, and they take effect everywhere simultaneously when pushed through a central system. Safe operation treats a config change as a deployment.

  1. Review. Changes go through pull requests, with an approver other than the author.
  2. Schema validation and semantic checks. Reject changes that do not match a type schema, and add rules: a timeout must be between 100 ms and 30 s, a pool size cannot be zero, a region must exist.
  3. Staged rollout. Apply to a canary slice (one instance, then one percent, then a zone, then a region, then everyone), watching error rate and latency at each stage, with automatic halt and rollback on alarm.
  4. Fast rollback. One action to return to the previous version, rehearsed in advance.
  5. Safe defaults and last-known-good. If the config service is unavailable or the new value fails to parse, the service runs on built-in defaults or its cached last-good config, and never refuses to start because it cannot reach a config server.
  6. Blast-radius limits. Segment configs by service and region, so one bad file cannot change everything at once.

13.1 Feature flags versus config

A feature flag is a special kind of dynamic config: a boolean (or a small rule) that turns code paths on or off at runtime, so that code can be deployed dark and enabled gradually, per user or per percentage. Ordinary config tunes how the system runs (timeouts, pool sizes); flags choose which behaviour runs. They share infrastructure and risks, but a flag usually has rule evaluation (user id, tenant, percentage buckets, region), is evaluated per request (so SDKs cache rules locally and evaluate in-process), and has a short lifespan: stale flags become tangled dead branches and should be removed once fully rolled out. Release flags (temporary), ops flags (kill switches that stay), and experiment flags (A/B tests) have different lifetimes. How flags support progressive delivery is covered in Chapter 43.

13.2 Per-environment and per-tenant overrides

Config is layered. A typical resolution order, from lowest to highest priority, is: built-in defaults, then global config, then environment (dev, staging, prod), then region or cluster, then service instance group, then tenant, with the most specific value winning. Multi-tenant systems regularly need per-tenant overrides: one large customer gets a higher rate limit, another a longer retention period, another a feature enabled early. Keep three rules: make the layering order explicit and documented, make it possible to see the effective value and where it came from (which layer), and put guardrails on overrides (maximum values, expiry dates for temporary exceptions) so the override table does not become an unmanageable set of special cases. High-cardinality per-tenant settings belong in a database or a flag service with caching, not in a giant config file that every instance loads.

14. Secrets management

A secret is a piece of configuration that grants access: database passwords, API keys, signing keys, tokens, private keys for TLS. Secrets deserve special treatment because their exposure is a security incident, not just a misconfiguration. The broader security picture is in Chapter 55; here is what discovery-and-config design needs.

14.1 Where secrets must not be

  • In source control. Git history is permanent and widely readable, and scanners harvest leaked keys from public and private repos. Deleting a committed secret does not remove it from history, so the secret must be rotated.
  • In container images. Anyone who can pull the image can read every layer, and images get copied, cached and pushed to many registries.
  • In plain environment variables. They are easily dumped by crash reports, debug endpoints, /proc, child processes and orchestration UIs. They are acceptable only as a delivery mechanism of last resort, not as the store.
  • In ordinary config files, logs or tickets. Mask secrets in logs and error output.

14.2 Secret stores

A dedicated secrets manager stores secrets encrypted, controls who can read each one, and records every access in an audit log. Examples: HashiCorp Vault, AWS Secrets Manager and Parameter Store, Google Secret Manager, Azure Key Vault. Underneath, they use a KMS (key management service) and the pattern called envelope encryption: each secret is encrypted with its own data key, and the data keys are encrypted by a master key that never leaves the KMS or hardware security module. So even someone who steals the stored data cannot read it without being authorised by the key service, and every decryption is logged.

14.3 Short-lived credentials and rotation

A long-lived password shared by many systems has a large blast radius and is almost never rotated in practice, because rotation is scary. The better design is short-lived, per-workload credentials. Vault's dynamic secrets create a fresh database user on demand with a lease of, say, one hour; when the lease ends, Vault deletes the user. A leaked credential is therefore useless soon after, and each credential is attributable to one workload. Where credentials must be long-lived, rotate them automatically on a schedule, with a design that supports two valid credentials at once during the switchover (issue the new one, let consumers pick it up, then retire the old one), so that rotation causes no downtime.

14.4 Workload identity: solving "how does the app prove who it is?"

Every secrets store raises a chicken-and-egg question: to fetch the database password, the app must authenticate to the store, but that needs a credential, which is itself a secret. The answer is workload identity: the platform vouches for the workload. In Kubernetes, each Pod runs under a ServiceAccount and receives a short-lived, signed token. Vault's Kubernetes auth method, AWS IAM Roles for Service Accounts (IRSA) or EKS Pod Identity, and GCP Workload Identity all validate that platform-issued identity and map it to a policy ("pods of service payments in namespace shop may read secret payments/db"). On virtual machines, cloud instance roles do the same through the metadata service. Mesh systems use SPIFFE identities (Chapter 50). No static bootstrap secret is shipped with the application at all.

14.5 Getting secrets into the process

  • Sidecar or init agent injection. A Vault Agent (or similar) sidecar authenticates using the Pod's identity, fetches the secrets, writes them to a shared in-memory volume (a tmpfs), and keeps them renewed. The app reads a file. The app has no store-specific code.
  • CSI Secrets Store driver. A Container Storage Interface driver mounts secrets from Vault, AWS or other providers as a volume into the Pod at start, and can sync to rotating files.
  • Direct SDK call. The app fetches at start-up and refreshes periodically. Most flexible, but ties code to the provider.

Whichever way, the application must re-read rotated secrets (watching the file, or refreshing the connection pool on authentication failure) rather than reading once at start and holding the old value until restart.

14.6 Certificate management (preview)

TLS certificates are secrets with an expiry date, and expiry is a top cause of avoidable outages. The modern approach is automation: certificates are short-lived (hours to a few months), issued automatically by an internal certificate authority or a public one via the ACME protocol (Let's Encrypt, cert-manager in Kubernetes), and renewed well before expiry without humans. In a mesh, the control plane issues each sidecar a short-lived workload certificate and rotates it continuously, enabling mutual TLS between services. Chapter 55 covers certificate chains, trust stores and revocation; the discovery-and-config lesson is that anything with an expiry must have automated renewal and an alert for upcoming expiry.

15. The bootstrapping problem

A service must find the registry to find everything else, and must find the config store to know its settings, and must prove its identity to read its secrets. But how does it find the registry or the config server in the first place? Something has to be known without being looked up. This is the bootstrapping problem, and every system solves it with a small number of layers of increasingly dynamic knowledge:

Common techniques:

  • Well-known DNS names. The only thing hard-wired is a name like consul.service.internal or config.internal. DNS itself is the "registry of last resort" because it exists everywhere. Behind the name sits a load balancer or a set of stable nodes.
  • Seed nodes. Clustered systems such as Consul, Cassandra and Eureka peers are told one or a few seed addresses, join through them, and learn the full membership by gossip or replication. If the seeds are down, existing members keep working; only new joins are blocked.
  • Platform-provided environment. Kubernetes injects the API server address and a ServiceAccount token into every Pod; cloud VMs read from the metadata service at a fixed link-local address. The platform is the root of trust.
  • Local agents. A Consul agent or a node-level proxy on localhost gives every process a fixed address (127.0.0.1:8500) for the registry, hiding where the servers really are.
  • Fail-safe start. If the config service is down at start-up, the instance falls back to baked-in safe defaults or a cached copy on disk, or waits with backoff, rather than crash-looping and generating load on the already-troubled service. Beware circular dependencies: a config service that needs to be discovered through the registry, which needs config from the config service, will deadlock after a full-region restart. Core infrastructure (registry, config, secrets, DNS) must depend only on the layers below it.

16. Worked example

An e-commerce company runs 120 microservices on Kubernetes in two regions. Take the call from orders to payments, and follow the design end to end.

16.1 Discovery

payments runs 12 Pods per region (6 per zone across 2 zones). Each Pod has a readiness probe at /ready every 5 seconds, failing after 3 consecutive misses. The Service payments has a ClusterIP, and Pods are registered as Ready in EndpointSlices. The orders service uses Envoy sidecars. The mesh control plane watches EndpointSlices and streams updates to each sidecar within about a second. Traffic stays in the same zone while the zone has at least 70 percent of healthy capacity, and the sidecar retries a failed request once on a different Pod.

Failure timing: a payments Pod crashes at t=0. The kubelet notices in at most 15 seconds (3 probes x 5 s), the endpoint controller removes it in about 1 second, and the control plane pushes the update within about 1 second. So about 17 seconds of requests may target a dead Pod; the sidecar's connection errors cause immediate retry on another Pod, and outlier detection ejects the dead endpoint after 3 consecutive errors, so users see almost no failures. Without the mesh, callers using plain kube-proxy would still follow the same 15 to 17 seconds, and rely on application retries.

16.2 Thundering herd check

There are 120 services x about 15 Pods x 2 regions, so around 3,600 sidecars watching. With watches, a single endpoint change creates 1 delta per interested sidecar, not polling. If instead each sidecar polled the registry every 30 s, that would be 3,600 / 30 = 120 requests per second at idle, harmless; but if a registry restart synchronised them all, 3,600 requests would land at once. Hence jittered intervals (30 s plus or minus 10 s random) and watches.

16.3 Configuration

Each service has a Git repository folder of YAML: defaults.yaml, prod.yaml, prod-eu.yaml. A CI check validates types and ranges: payments timeoutMs must be 200 to 5000. Merging produces an immutable versioned bundle in the config store. Services poll every 30 seconds for the version tag and hot-reload dynamic values (timeouts, rate limits) atomically. A change from 800 ms to 400 ms for the timeout is rolled out to 1 percent of Pods for 5 minutes, then 25 percent, then everyone; an alarm on payments p99 latency or 5xx rate above baseline automatically reverts to version 41. Per-tenant exceptions (the tenant "BigRetailer" gets 2x rate limit) live in a tenant-override table with an expiry date, loaded by a flag service SDK with local caching.

16.4 Secrets

Payments needs a database credential and an API key for the card processor. Pods authenticate to Vault with their ServiceAccount token. Vault policy allows only payments in namespace shop to read payments/*. A Vault Agent sidecar writes a database username and password (dynamic, TTL 1 hour, renewed at 40 minutes) to a tmpfs file, and the app reloads its connection pool when the file changes. The card-processor key is a static secret rotated every 90 days using a dual-key window of 24 hours. Nothing is in Git, the image or plain environment variables. If 2,000 Pods each fetch a new credential hourly, Vault sees about 2,000 / 3,600 = 0.6 requests per second, trivial, but the database must tolerate user creation at that rate and the Vault cluster must be highly available since the renewals happen on a clock.

16.5 Bootstrap

A Pod starts with only: the Kubernetes API address, its ServiceAccount token, and the DNS names vault.internal and config.internal. It authenticates, fetches config and secrets, reports ready, and gets traffic only once readiness passes. If Vault is unreachable at start, the Pod stays not-ready and retries with exponential backoff and jitter instead of crash-looping, while already-running Pods continue with cached credentials until their leases expire (the 1 hour TTL is therefore the time operators have to restore Vault).

17. Interview Q&A

Why can't services just use a fixed list of IP addresses?

Because instance addresses are temporary. Autoscaling adds and removes instances, container restarts assign new IPs, rolling deployments replace every instance, and failures remove machines without warning. A fixed list is out of date within minutes and would require redeploying every caller whenever any dependency moves. Service discovery inserts a level of indirection: callers use a stable logical name, and a registry or platform maintains the current mapping to healthy instances. That mapping is kept fresh by registration, heartbeats and health checks.

Compare client-side and server-side discovery. When would you pick each?

In client-side discovery the caller queries the registry, caches the list and balances requests itself; it saves a network hop and scales with the number of callers, but every language needs a good library and policy changes require redeploying callers. In server-side discovery the caller sends traffic to a stable load balancer or router, which does the lookup; callers stay trivial and policy is central, but there is an extra hop and a component to scale and keep available. I would pick server-side (Kubernetes Services, an ALB) for polyglot fleets and simplicity, client-side for homogeneous, latency-sensitive internal traffic such as gRPC, and a service mesh when I want client-side behaviour without library code.

How does a registry know when an instance has died, and what is a stale entry?

Either the instance sends periodic heartbeats that renew a TTL, so silence causes expiry, or the registry or an agent actively probes a health endpoint and removes the instance after several failures. A crash does not deregister, so the entry stays until expiry or failed probes; during that window the entry is stale and callers may be sent to a dead address. Because that window can never be zero, callers need connect timeouts, retries that choose a different instance, and ideally outlier ejection. Tuning is a trade-off: short TTLs detect failure faster but cost more traffic and risk false evictions.

What are the problems with DNS for service discovery?

DNS answers are cached by resolvers, the operating system and applications for the TTL, so changes propagate slowly and dead instances keep receiving traffic. Some clients ignore TTLs completely or resolve only once and keep connections forever. Plain A records carry no port, so you need SRV records, which many clients ignore, and DNS has no real notion of instance health or weights. It works well for coarse, slow-changing endpoints, and Kubernetes makes it work for fast-changing Pods by having DNS return a stable ClusterIP while the fast-changing mapping is handled by kube-proxy.

Walk through how a call to a Kubernetes Service finds a Pod.

The caller resolves the Service name through CoreDNS, which returns the Service's virtual ClusterIP. The caller connects to that IP. The Pod list behind the Service is kept by the EndpointSlice controller, which includes only Pods passing their readiness probe. kube-proxy on every node watches these slices and programs iptables, IPVS or eBPF rules, so the kernel rewrites the destination to one of the ready Pod IPs. A headless Service has no ClusterIP, so DNS returns the Pod IPs themselves for clients that need to balance or address instances directly, such as for StatefulSets or gRPC.

Should a service registry be CP or AP? Why did Eureka choose availability?

Discovery data is soft state that callers can verify by trying it: if a listed instance is dead, the call fails and the caller can try another. Therefore a slightly stale list is much more useful than no answer during a partition, which is why Eureka chose AP, with peer replication and client-side caching. Its self-preservation mode stops expiring instances when heartbeats drop sharply, assuming the registry or network is at fault rather than every instance. CP stores such as etcd, ZooKeeper and Consul servers are better for the things that must be correct, like leader election and locks, so a good design keeps writes consistent but lets reads be cached and tolerate staleness.

What happens when the service registry goes down, and how do you design for it?

If callers consult the registry on every call, everything stops, so registries are among the most critical infrastructure. The key mitigation is client-side or local-agent caching of the last-known-good instance list so that existing traffic continues during the outage, with the cost that changes are not seen until recovery. The registry should run as a replicated cluster across failure domains, and reads must scale through watches, followers and jittered refresh to avoid thundering herds when it comes back. Kubernetes and meshes behave this way: when the control plane is down, nodes and sidecars keep forwarding with their last configuration.

Why is configuration such a common cause of outages, and how do you make changes safe?

Config changes often skip the review, testing and gradual rollout that code receives, and when pushed through a central system they take effect everywhere at once, so one wrong value (a zero limit, a bad route, an incorrect flag) becomes a global outage within seconds. To make them safe I treat config as code: Git review, schema and range validation in CI, immutable versions, staged rollout from a canary slice with automatic rollback on health alarms, instance-side validation with last-known-good fallback, and a rehearsed one-step rollback. I also expose the config version each instance runs so incidents can be correlated with changes.

How should an application get its database password?

Not from source control, the image or plain environment variables. The app should use workload identity, where the platform issues a short-lived signed identity (a Kubernetes ServiceAccount token or a cloud role) that a secrets manager like Vault or a cloud secrets service verifies against a policy. The secrets manager returns a credential, ideally a dynamic, short-lived one that expires on its own, and every access is audited. The secret is delivered by a sidecar or CSI volume into an in-memory file, and the app reloads on rotation. This removes the need for any long-lived bootstrap secret and limits damage if a credential leaks.

What is the bootstrapping problem in discovery and configuration?

A service needs to find the registry and config store before it can discover anything else, but those themselves must be located without a registry. The fix is a minimal layer of fixed knowledge: well-known DNS names, a few seed nodes, an identity token and environment injected by the platform, or a local agent on a fixed localhost port. Everything beyond that is dynamic. I also make start-up fail-safe, using cached or default config and retrying with backoff, and I avoid circular dependencies where core services depend on each other in a loop, which causes deadlock after a full restart.

How do feature flags differ from configuration, and what are the per-tenant implications?

Both are dynamic settings changed without a deploy, but configuration tunes how the system runs (timeouts, pool sizes), whereas flags choose which behaviour executes, with rule evaluation by user, tenant or percentage and typically a short lifetime that ends in cleanup. Flags are evaluated per request inside SDKs with locally cached rules, and need the same safety as config: review, staged exposure, audit. For tenants, I layer defaults, environment, region and tenant overrides with the most specific winning, show the effective value and its source, and cap overrides with expiry dates so exceptions do not accumulate.

18. Recap

  • Static addresses fail because instances are disposable: autoscaling, containers, rollouts and failures all change addresses. Discovery separates stable names from changing locations.
  • A registry stores live instances; registration is self or platform-driven, kept fresh by heartbeats/TTL or active health checks, and always leaves a stale window after a crash.
  • Client-side discovery saves a hop and scales with callers but needs libraries; server-side discovery (ALB, kube-proxy, Envoy) keeps callers simple but adds a hop. Meshes combine both through sidecars.
  • DNS is universal but suffers from caching and TTL-ignoring clients; Kubernetes combines a stable ClusterIP with EndpointSlices of Ready Pods, kube-proxy and CoreDNS, and uses headless Services when clients need individual Pods.
  • Registries can be CP (etcd, ZooKeeper, Consul) or AP (Eureka); for discovery reads, availability and cached last-known-good data usually beat strict consistency. Plan for propagation delay, registry outages, zombies, flapping and thundering herds.
  • Config is everything that differs between deploys; keep it out of code, version it, validate it, roll it out in stages with fast rollback, and treat it as a leading cause of outages. Flags are dynamic config with rules; overrides are layered.
  • Secrets belong in a managed store with audit, KMS-backed encryption, short-lived dynamic credentials, rotation, and workload identity; inject by sidecar or CSI, never via Git, images or plain environment variables. Certificates need automated renewal.
  • Bootstrapping uses a minimal set of well-known names and platform-issued identity, with fail-safe start-up and no circular dependencies.
