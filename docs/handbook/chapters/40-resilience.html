Chapter 40 · Module 6 · Reliability

Resilience Patterns and Tail Latency

In a distributed system something is always slow, broken or overloaded. This chapter explains the toolbox that keeps one sick component from taking down everything else: timeouts, retries, circuit breakers, bulkheads, fallbacks, load shedding, hedging, and the testing habits that prove they work. It also explains why the slowest one percent of requests matters far more than it seems.

1. Why resilience is its own discipline

A single program on a single machine mostly either works or crashes. A system made of many services talking over a network has a third, nastier state: partially working. A database that answers in 8 seconds instead of 8 milliseconds, a network link that drops 2 percent of packets, or one server in a pool that has quietly run out of memory are all examples. Nothing has crashed, so nothing triggers an obvious alarm, yet users are suffering and, worse, the other services that depend on the sick one start to suffer as well.

Resilience is the set of design habits that make a system keep giving useful answers while parts of it are slow or broken, and recover by itself when those parts come back. It is different from high availability (Chapter 41), which is mostly about having redundant copies so a failed component can be replaced. Resilience is about what the callers do while a dependency is misbehaving: how long they wait, whether they try again, whether they stop calling, and what they show the user instead.

The guiding observation, used throughout this chapter, is that the most dangerous failure is not a dead dependency but a slow one. A dead dependency refuses connections instantly, and the caller can react in microseconds. A slow dependency holds on to the caller's threads, connections and memory for seconds. Because the caller is now stuck, its own callers get slow, and the slowness travels up the call chain like a traffic jam traveling backwards along a motorway.

Key idea Every resilience pattern in this chapter does one of three things: it limits how long you wait (timeouts, deadlines), it limits how much you send or accept (retry budgets, bulkheads, load shedding, backpressure), or it gives you something else to do (fallbacks, degradation, hedging). Good designs use all three, layered.

This page assumes you know what a load balancer does (Chapter 9), how caches fail (Chapter 14), and how rate limiters work (Chapter 16). It covers the single-service toolbox and the mathematics of tail latency. Chapter 51 shows how these patterns are applied across a whole microservice estate.

2. A taxonomy of failures

You cannot choose the right defence until you know what you are defending against. Failures differ in how visible they are and how long they last, and each combination wants a different response.

2.1 Transient, intermittent and persistent

Failures also differ in duration. A transient failure disappears on its own within moments: a single dropped packet, a leader election lasting two seconds, a connection reset by a load balancer. Retrying quickly works well. An intermittent failure comes and goes, such as a single bad node in a pool that fails one request in ten. Retrying on a different node works well. A persistent failure lasts until a human or an automatic recovery fixes it, such as a bad deploy or a full disk. Retrying a persistent failure only adds load to something that is already struggling, which is why retries must be paired with circuit breakers.

2.2 The fallacies behind these failures

Almost every real incident traces back to a hidden assumption from the well-known "fallacies of distributed computing": the network is reliable, latency is zero, bandwidth is infinite, topology does not change. Resilience engineering is the practice of deleting those assumptions from your code, one call site at a time. Each remote call should have an explicit answer to four questions: how long will I wait, what if it fails, what if it fails again, and what if it is so slow that many callers are waiting at once?

3. Timeouts: the foundation

A timeout is the maximum time a caller is willing to wait for something. Without one, a caller waits as long as the operating system allows, which for a TCP read can be many minutes or forever. Every other pattern in this chapter assumes timeouts exist, because "no answer within the timeout" is the only failure signal a caller receives.

3.1 Connect timeout versus read timeout

A network call has distinct phases and each deserves its own limit.

  • Connect timeout: how long to wait for the TCP (and TLS) handshake to complete. If the target host is alive and reachable in the same data center, this takes about one round trip, well under a millisecond to a few milliseconds. A connect timeout of 100 to 500 ms is typical inside a region. A connect that does not finish quickly almost always means the host or network path is unhealthy, so there is no benefit in waiting seconds. A short connect timeout lets the caller try another replica fast.
  • Read (response) timeout: how long to wait for the response bytes after the request is sent. This must cover the server's real processing time. It should be set from measured latency, for example a little above the dependency's p99.9, not from a guess.
  • Write timeout and idle timeout: limits on sending the request body and on how long a pooled connection may sit unused. Idle timeouts matter because a load balancer may silently drop idle connections after, say, 60 seconds; if your client believes the connection is still open it will write into a dead socket and discover this only through an error.
  • Total (overall) timeout: a cap on the whole operation including retries, queueing for a connection from the pool, and DNS lookup. Many libraries only offer connect and read timeouts, and a slow trickle of bytes can reset the read timer forever, so the total timeout is the one that actually bounds user-visible latency.
Watch out A read timeout that resets every time a byte arrives does not bound the call. A server that sends one byte per second can keep a client waiting indefinitely. Always add an overall deadline on top of the per-read limit.

3.2 Choosing a timeout value

Too short and you create false failures, which trigger retries, which add load. Too long and the caller's resources stay pinned while the dependency is sick. A practical method is to look at the dependency's measured latency distribution and set the timeout just beyond the point where a successful response is unlikely to still be coming. For example, if the dependency has p50 = 20 ms, p99 = 120 ms and p99.9 = 300 ms, a timeout of 400 to 500 ms means about one request in a thousand is cut off wrongly, and a hung call frees its resources in half a second. A timeout of 30 seconds, which is a frequent library default, would let a sick dependency pin 60 times more concurrent calls.

The link between timeouts and capacity is Little's law, introduced in Chapter 2: the average number of requests in flight equals the arrival rate times the average time each spends in the system. We return to it in section 11, but note now that the timeout is the maximum time a hung call spends in your system, so it directly caps how many hung calls can accumulate.

3.3 Deadlines and propagation

Imagine a user request that passes through a gateway, a web service, an order service and a payment service. If each hop applies its own fresh 5-second timeout, the outermost caller may give up after 5 seconds while the deepest service keeps working for another 15 seconds on a result nobody will read. That wasted work is pure load on an already slow system.

The fix is to carry a deadline, an absolute point in time by which the whole user request must finish, down the entire call chain. Each hop subtracts the time already used and passes the remainder to the next hop. gRPC has this built in (the deadline travels in request metadata and surfaces as a cancelled context). With plain HTTP you pass the remaining budget in a header, for example a custom X-Request-Deadline or X-Timeout-Ms, and each service reads it, caps its own outgoing timeouts to it, and refuses to start work that cannot finish in time.

3.4 The timeout budget rule

A useful rule: the timeout at each layer must be shorter than the timeout of the layer above it, with room for its retries. If the client waits 2 seconds, the service it calls should wait less than 2 seconds on any of its dependencies, or the client times out while the service is still retrying, and the retry is wasted. The budget can be written as an inequality. For a caller that makes up to k attempts each limited to t seconds with backoff b between them, the caller's own timeout T must satisfy roughly T ≥ k·t + (k − 1)·b, and the timeout of its caller must be larger still. Writing this budget down on a whiteboard, hop by hop, is one of the most convincing things a candidate can do in an interview.

Interview tip When you draw a call chain, annotate each arrow with a timeout and make the numbers shrink as you go deeper (for example 2 s, 1 s, 400 ms, 150 ms). Say out loud: "inner timeouts are smaller than outer ones so that outer layers can still retry or degrade before their own deadline."

4. Retries

When a call fails, trying again is often the right thing. A transient failure such as a dropped packet will vanish on the second attempt, and a request routed to one bad replica will succeed on another. Retries turn many short-lived faults into non-events. But retries are also the single biggest cause of self-inflicted outages, because they multiply load exactly when a dependency is least able to handle it.

4.1 When is a retry safe?

Two conditions must hold. First, the failure should be retryable: a timeout, a connection reset, an HTTP 503 or 429 with a Retry-After header, or a gRPC UNAVAILABLE status. A 400 Bad Request or 404 will fail identically every time, so retrying it only wastes work. Second, the operation must be safe to run twice, which is the idempotency question.

A timeout is especially tricky: the caller does not know whether the server never received the request, received it and is still working, or finished it and the reply was lost. If the operation is "charge this card" and you retry blindly after a timeout, you may charge the customer twice. Reads and naturally idempotent writes (set a value, delete by key) are safe. Non-idempotent writes need an idempotency key: the client generates a unique identifier once per logical operation and sends it with every attempt, and the server remembers the result for that key and returns it instead of repeating the work. Chapter 32 covers the mechanism in detail.

4.2 Backoff: do not retry immediately

If a server is overloaded and 1000 clients all retry the instant they fail, the server receives another 1000 requests immediately. Exponential backoff spaces retries out: wait base, then 2×base, then 4×base, up to a cap. For example with a base of 100 ms and a cap of 10 s the waits are 100, 200, 400, 800, 1600 ms and so on. This gives the server breathing room, and it reduces the retry rate geometrically.

Backoff alone has a flaw. If 1000 clients all failed at the same instant (because the server blipped), they all wait exactly 100 ms and retry together, then all wait 200 ms and retry together. The retries stay synchronised in sharp waves. The remedy is jitter, a random component in the wait.

  • Full jitter: sleep = random(0, min(cap, base × 2attempt)). The wait is spread uniformly from zero up to the exponential bound. This is simple and works very well at breaking up synchronised waves, at the cost that an individual retry may happen almost immediately.
  • Equal jitter: sleep = half the exponential bound plus random(0, half). Guarantees some minimum delay but spreads less.
  • Decorrelated jitter: sleep = min(cap, random(base, previous_sleep × 3)). Each wait depends on the previous wait rather than the attempt number, which keeps clients decorrelated even if they start in lockstep. Widely recommended in published analyses of contention-heavy workloads.

4.3 Retry budgets and limits

A fixed "retry 3 times" rule is dangerous at scale. Suppose a dependency starts failing every call. With three retries each client now sends four times its normal traffic to a service that is already failing. A retry budget limits retries as a proportion of normal traffic instead: for example, "retries may add at most 10 percent on top of first attempts, measured over the last minute." When the dependency is healthy, almost no retries are needed and the budget is barely used. When it is failing broadly, the budget runs out quickly, and the client stops adding load. Envoy and gRPC implement this idea (a token bucket of retry tokens that refills as successes arrive and drains on retries), as does the Finagle library.

Other sensible limits: a maximum attempt count (usually 2 or 3 in total), a maximum total elapsed time tied to the deadline, and retry only at one layer of the stack (see next section).

4.4 Retry amplification across layers

The most expensive mistake is retrying at every layer. Consider a chain of four services, A calls B, B calls C, C calls D, and D calls the database. Each layer is configured, reasonably, to make up to 3 attempts. If the database fails every request, how many database queries does one user request cause?

The multiplication is 3 × 3 × 3 × 3 = 81 database attempts for one user action. If the system takes 1000 user requests per second, a database that was healthy at 1000 queries per second suddenly has to absorb 81,000 per second precisely when it is failing. Even a partial failure, say 50 percent of calls failing, produces large amplification. The database cannot recover because the retry traffic keeps it saturated.

4.5 Retry storms

A retry storm is the feedback loop that results when retries push a dependency from "slow" to "down". The sequence is: a dependency slows slightly, some calls time out, clients retry, the extra load slows the dependency further, more calls time out, more retries follow, and the load grows until the dependency collapses. Removing the original trigger does not end the storm, because the retries alone now keep the system saturated. This is a metastable failure, described in section 14. The defences are exactly the ones already described: jittered backoff, retry budgets, single-layer retries, circuit breakers that stop calls entirely, and load shedding on the server.

Watch out Client-side retries inside a mobile app or a browser are invisible to your server-side budgets. A million phones that each retry three times after a brief outage deliver a large synchronised spike. Include jitter and a server-supplied Retry-After value in client libraries too.

5. Circuit breakers

An electrical circuit breaker cuts power when current is dangerously high, so the house does not burn down, and you reset it after fixing the fault. A software circuit breaker does the same for calls to a dependency. It watches recent results, and when too many fail it stops sending requests for a while and fails immediately instead. This protects two parties: the caller (which does not waste threads waiting for doomed calls) and the dependency (which gets quiet time to recover instead of being pounded by retries).

5.1 The three states

  • Closed is normal operation. The breaker keeps a rolling record of recent outcomes, either the last N calls (count-based window) or the last T seconds (time-based window).
  • Open means the failure rate crossed a threshold. Every call is rejected immediately with an exception or fallback value, in microseconds, without touching the network. This lasts for a configured wait duration.
  • Half-open is the trial period. The breaker allows a limited number of calls (for example 5). If they succeed, the dependency is assumed healthy and the breaker closes. If any fail beyond a tolerance, it opens again for another wait duration.

5.2 Thresholds and what counts as failure

The settings that matter, using Resilience4j names as an example:

  • Failure rate threshold (for example 50 percent): trip if at least this share of calls in the window failed.
  • Minimum number of calls (for example 20): do not trip on small samples. One failure out of two calls is a 50 percent failure rate but means nothing statistically.
  • Slow call threshold and slow call rate: treat calls longer than, say, 2 seconds as failures for breaker purposes. This is how a breaker catches the dangerous "slow" failure, not only the explicit errors.
  • Wait duration in open state (for example 30 seconds), often with an increasing schedule.
  • Permitted calls in half-open (for example 5) and the failure tolerance among them.
  • Which exceptions count: timeouts, connection errors and 5xx responses count; a 404 or a validation error is the caller's fault and must not trip the breaker.

5.3 Scope: per endpoint, per host

One breaker for an entire downstream service is too coarse. If only the /export endpoint is slow, tripping the breaker for the whole service also blocks healthy /lookup calls. Using one breaker per endpoint (or per operation, or per tenant shard) limits the blast radius. Similarly, a client talking to ten replicas should ideally keep a breaker per replica or use outlier detection, so one bad host is ejected while nine remain in use. Envoy does this with outlier detection: hosts that return consecutive 5xx responses are temporarily ejected from the load-balancing pool (see Chapter 9), with a cap on the percentage ejected so that a global problem does not eject everything.

Watch out Breakers that all reopen at the same instant produce a synchronised probe wave. Use jitter on wait durations, limit half-open trial calls, and when the breaker is distributed across many client instances remember each instance decides independently, so the dependency sees many small probes at once.

5.4 What to do when open

Failing fast is only half the value. The other half is what happens next: return a cached value, a default, a reduced response, or a clear error that the caller's caller can handle. Section 7 covers the fallback menu. A breaker without a fallback just converts slow errors into fast errors, which is still better, but a well-chosen fallback converts them into success.

6. Bulkheads: isolating resources

On a ship, bulkheads are watertight walls that divide the hull into compartments. A hole floods one compartment instead of sinking the ship. In software a bulkhead means giving each dependency, endpoint or tenant its own limited pool of resources, so exhaustion of one pool cannot starve the others.

Without a bulkhead, a service that calls three dependencies shares one thread pool of, say, 200 threads. If dependency C becomes slow, requests to C each hold a thread for the full timeout. Within seconds all 200 threads are stuck waiting on C, and requests that only needed healthy dependencies A and B also cannot run. One slow dependency has taken out the entire service.

6.1 Flavours of bulkhead

  • Thread-pool bulkhead: each dependency gets its own thread pool and queue. A call is submitted to that pool; if the pool and queue are full the call is rejected immediately. It offers strong isolation and lets you abandon a stuck call by timing out the future, but it adds a thread hand-off, which costs a little latency and memory.
  • Semaphore bulkhead: a counter of permitted concurrent calls (for example 50). Calls run on the caller's own thread and a call beyond the limit is rejected or waits briefly. It is cheaper and works well with asynchronous or non-blocking code, where there are no thread pools to separate in the first place. In event-loop runtimes you bound in-flight requests per dependency instead.
  • Connection-pool bulkheads: separate HTTP or database connection pools per dependency or per workload. A reporting query that grabs every database connection should not be able to starve the checkout path. Many teams run analytic queries against a read replica or a separate pool for this reason.
  • Process, container and cell isolation: run risky or noisy workloads in separate processes, pods or node groups. In a cell-based architecture the whole stack is replicated into independent cells, each serving a slice of customers, so an outage hits a small fraction (Chapter 41 discusses cells and regions).

6.2 Per-tenant bulkheads

In multi-tenant systems the biggest threat to a well-behaved tenant is a noisy neighbour. A per-tenant concurrency limit or quota means one tenant that launches a huge job can consume at most its own share. Combine it with fair queuing so each tenant gets a turn, and with rate limits (Chapter 16) at the entry point. For heavy tenants, shuffle sharding assigns each tenant to a small random subset of workers, so any two tenants share only a few workers and a poisonous tenant can only hurt the few that overlap with it.

The cost of bulkheads is capacity efficiency. Separate pools mean idle threads in one pool cannot help a busy one. Accept this: you are paying a small utilisation tax for a large reduction in blast radius. Size each pool with Little's law and review them as traffic changes.

7. Fallbacks and graceful degradation

When a dependency is unavailable, the choice is not just "work or error". A product that degrades gracefully keeps its core promise and sheds the nice-to-haves. A recommendation panel that cannot load is replaced by popular items; the shopping cart still works. Designing this deliberately requires deciding in advance, per dependency, what the user experience is when it is gone.

7.1 The fallback menu

  • Cached or stale data: serve the last known good answer. A product page can show yesterday's price list or review count when the review service is down, labelling or silently accepting the staleness. Caches that are allowed to serve expired entries when the origin fails are called "stale-if-error" or "serve-stale" (Chapter 14 discusses cache behaviour under failure).
  • Static default: return a safe constant, such as an empty list of recommendations, a generic avatar, or a "feature flags off" default configuration.
  • Simplified computation: use a cheaper approximation, for example non-personalised ranking when the personalisation model is unavailable.
  • Alternative source: read from a replica, a different region, or a secondary provider (a backup payment gateway, a second email vendor).
  • Queue for later: accept the request, store it durably and process it when the dependency returns (the order is "received", the confirmation email comes later). This pairs with queue-based load levelling in section 10.
  • Fail closed versus fail open: decide, per dependency, which direction to fail. A fraud-scoring timeout might fail open (allow small payments) to preserve revenue, while an authorisation check must fail closed (deny). Make this a conscious, documented choice.

7.2 Feature shedding

Under heavy load or partial outage you can turn features off in priority order, often via feature flags that operators or automation flip. A typical order for a retail site might be: disable personalised recommendations, then recently-viewed lists, then live inventory counts (show "in stock" generically), and finally throttle search suggestions, while protecting search results, cart and checkout to the end. The important design step is to classify features by criticality ahead of time so that when a bad day comes the on-call engineer is executing a plan instead of inventing one.

Watch out A fallback that has never run in production is a hidden outage waiting to happen. Fallback code paths are rarely exercised, often make assumptions that no longer hold, and sometimes call the very dependency that failed. Test them regularly with failure injection (section 17), and make sure a fallback does not itself add heavy load, such as a cache fallback that stampedes the database (see Chapter 14).
Interview tip Whenever you design a read path with several dependencies, say what the page looks like if each one is down. "If recommendations fail we show trending items from a cache refreshed every five minutes; if the price service fails we show the cached price with a note and block checkout until it recovers." That one sentence demonstrates graceful degradation, criticality ranking and staleness thinking.

8. Load shedding and admission control

Every service has a maximum throughput. Past that point, accepting more work does not make more work finish; it makes everything slower, because requests queue, memory fills, garbage collection runs more often and context switching grows. If a server can complete 1000 requests per second and receives 1500, a naive server tries all 1500, each is slower, most time out on the client side, and the useful completion rate (goodput) can fall far below 1000. This collapse is called congestion collapse or the overload cliff.

Load shedding is the deliberate refusal of some requests so the rest can succeed. It is better to answer 1000 requests well and tell 500 "try later" than to answer 1500 requests badly. Admission control is the decision point that determines which requests get in. Rate limiting (Chapter 16) enforces fixed per-client quotas; load shedding is the adaptive, server-protecting counterpart that reacts to actual current overload regardless of whose traffic it is.

8.1 How to decide what to shed

  • Concurrency limit: allow at most N requests in flight (N from Little's law, section 11). Beyond that, reject immediately with 503 or 429. Adaptive versions (Netflix's concurrency-limits library, Envoy's adaptive concurrency filter) raise and lower N automatically using observed latency, in the style of TCP congestion control.
  • Queue time or CoDel-style control: measure how long requests sit in the queue; if the minimum queue delay stays above a target (for example 5 ms), start dropping. The controlled-delay idea keeps queues short without a fixed length.
  • Priority-based shedding: classify requests (health checks and payments critical; batch exports and prefetches sheddable). Shed the lowest class first. Many gateways tag traffic with a priority header at the edge.
  • LIFO under overload: when the queue is long, serve the newest request first. Old requests are likely abandoned by the client already, so serving them is wasted work. Serve fresh ones that can still succeed, and drop the oldest.
  • Deadline awareness: drop any request whose propagated deadline has already passed, or cannot be met given current queue delay. Doing work for a dead request is the worst use of capacity.
  • Client-aware shedding: reject early and cheaply, ideally before expensive parsing, authentication or database access. The cost of saying no must be tiny compared with the cost of saying yes.

Tell the client what happened. A 429 (Too Many Requests) or 503 (Service Unavailable) with a Retry-After header lets well-behaved clients back off intelligently, and the client's retry budget can recognise shedding responses and not retry them aggressively. Shedding at the load balancer or gateway (Chapter 9) protects the application servers behind it.

9. Backpressure

Backpressure is the mechanism by which a slow consumer tells a fast producer to slow down, so that the buffer between them does not grow without limit. Water pipes work this way: a closed tap downstream raises pressure upstream. In software the alternatives to backpressure are unbounded queues (memory grows until the process dies) or silent dropping (data loss). Backpressure makes the limit visible and pushes the decision to the party that can best handle it.

Forms you will meet:

  • TCP flow control: the receiver advertises a window size; the sender cannot have more unacknowledged bytes in flight than that window. A slow reader shrinks the window to zero and the writer blocks.
  • Blocking bounded queues: a producer calling put on a full bounded queue blocks until space appears. Simple and effective inside one process.
  • Reactive streams and pull-based consumption: the consumer requests N items at a time (request(n) in Reactive Streams, prefetch counts in message consumers). The producer may send only what has been requested.
  • HTTP/2 and gRPC flow control: per-stream and per-connection windows, plus limits on concurrent streams.
  • Explicit signals: returning 429 or 503, or a "slow down" response code, so the client chooses to wait, drop or retry later.
  • Consumer lag as a signal: with a log system such as Kafka, producers can be throttled based on consumer group lag (Chapter 34).
Key idea Every queue in a system must be bounded, and the behaviour at the bound must be a design decision: block the producer, reject the newest, drop the oldest, or spill to disk. An unbounded queue is not a resilience feature; it is a delayed out-of-memory crash and a source of enormous latency, because items wait behind everything already queued.

10. Queue-based load levelling

Many workloads are spiky: a flash sale, an end-of-month batch, a viral post. Sizing the processing tier for the peak wastes money the rest of the time, and sizing it for the average fails at the peak. Queue-based load levelling places a durable queue between the producers and the consumers. Producers write at whatever rate arrives; consumers pull at the rate they can sustain. The queue absorbs the difference.

This pattern pairs with backpressure: if the queue depth reaches its limit, producers must be told (reject, slow, or degrade) rather than letting the queue grow forever. It also pairs with the idempotency work of Chapter 32, because queue consumers see duplicates when messages are redelivered. Details of queue internals are in Chapter 34.

11. Timeouts, queue lengths and Little's law

Little's law (Chapter 2) says that for any stable system, L = λ × W: the average number of items in the system (L) equals their arrival rate (λ) times the average time each spends inside (W). It is the best single tool for sizing thread pools, connection pools and queues, and for seeing why slowness destroys capacity.

11.1 A worked example: when latency rises, concurrency explodes

A service receives λ = 400 requests per second and normally each one takes W = 50 ms to finish (calling a database). The average in-flight work is L = 400 × 0.05 = 20 concurrent requests. A thread pool of 50 therefore has comfortable headroom.

Now the database becomes slow and each call takes 2 seconds (hitting a 2 s timeout in some cases). The arrival rate has not changed, but L = 400 × 2 = 800 concurrent requests. The pool of 50 is exhausted within a tenth of a second. The extra 750 requests either queue (adding more delay, which increases W further) or are rejected. Nothing was wrong with the traffic; the latency of one dependency multiplied the required concurrency by forty.

11.2 Using it to size things

  • Pool size ≥ λ × Wnormal × headroom (typically 2 to 3 for bursts and tail latency). With λ = 400, W = 50 ms and headroom 3, a pool of 60 is reasonable.
  • Queue bound in front of that pool: queue length should be small enough that the wait at the back is still within the caller's timeout. If the pool processes 400 requests per second, a queue of 200 adds up to 500 ms of waiting; if the caller times out at 300 ms, then deeper queued items are guaranteed wasted work. Set queue length ≤ throughput × (timeout − typical service time).
  • Timeout as a cap on pinned resources: worst-case concurrent hung calls is roughly λ × timeout, which tells you how large the damage can be and justifies a lower timeout.
  • Deriving the overload point: if a service has N workers and a mean service time S, its maximum throughput is N / S. With 50 workers and S = 50 ms, that is 1000 requests per second; above that the queue grows without bound, which is the moment shedding must begin.
Key idea Slowness converts directly into held resources. A dependency that is 40 times slower needs 40 times the concurrency to carry the same traffic, so a caller with a fixed pool always runs out first. Short timeouts, bounded queues and concurrency limits are what stop that arithmetic from taking the caller down.

12. Tail latency and percentiles

Chapter 2 introduced percentiles. Quick recap: the p50 (median) is the latency that half of requests beat. The p99 is the latency that 99 percent of requests beat, so 1 request in 100 is slower. The p99.9 is slower than all but 1 in 1000. The slow end of the distribution is the tail.

Averages hide the tail. A service with a mean of 40 ms may have a p50 of 20 ms and a p99 of 400 ms. Latency distributions are typically right-skewed (long tail to the slow side), roughly log-normal, caused by things such as garbage-collection pauses, cache misses, lock contention, background compaction, noisy neighbours, network retransmits (a TCP retransmit timeout can add 200 ms or more), and queueing. You cannot average percentiles across servers either: the p99 of a fleet is not the mean of each server's p99. Store histograms and merge them (HDR histogram, t-digest, or fixed Prometheus buckets) and compute percentiles after merging.

12.1 Why the tail matters more than it seems: fan-out

If a single request to a backend has a 1 percent chance of being slow (it is slower than the backend's p99), that sounds tolerable. But a modern user request rarely makes one call. A search page might fan out to 100 shards; a social feed to dozens of services; a checkout to a dozen. The user's request is only as fast as the slowest of its sub-requests.

The maths is simple. Let each sub-call independently be "fast" (below its p99) with probability 0.99. The probability that all N sub-calls are fast is 0.99N, so the probability that at least one is slow is 1 − 0.99N.

With a fan-out of 100, 63 percent of user requests include at least one backend call that is slower than the backend's p99. The backend's p99 has effectively become the front end's median. The same logic with p99.9 (0.999N): at N = 100, 9.5 percent of user requests hit a p99.9-slow call. This is the "tail at scale" effect described by Dean and Barroso in their well-known paper: at large fan-out, rare backend events become common user events. To keep a fan-out of 100 mostly fast, each backend must have a good p99.9 or better, or the system must use hedging and other tail-cutting tricks (section 13).

12.2 Sequential chains also add up

Series calls add rather than take a maximum. A chain of 5 services each with p99 = 100 ms does not have an overall p99 of 100 ms; the tail of the sum is typically near 300 to 500 ms when each stage's tail event is independent, and the probability of experiencing at least one tail event along the chain is 1 − 0.995 ≈ 4.9 percent. Deep call chains therefore damage tail latency, and setting latency objectives (SLOs) at p99 per hop is often not enough: set them for the end-to-end path and budget each hop (section 3.4).

12.3 Where the tail comes from, and general remedies

  • Queueing delays: utilisation near 100 percent makes waiting explode. Keep utilisation of any shared resource below roughly 70 to 80 percent so queues stay short. The relationship is nonlinear: in a simple single-server queue, mean waiting time grows like ρ/(1−ρ), so at 90 percent utilisation it is nine service times, and at 99 percent it is ninety-nine.
  • Garbage collection and runtime pauses: tune or choose low-pause collectors; stagger restarts; avoid sending requests to a node in a long pause (health checks, outlier ejection).
  • Background activity: compactions, backups, cron jobs, log rotation. Throttle them or schedule them per replica so not every replica is busy at once.
  • Head-of-line blocking: one slow request in a shared queue or connection delays those behind it. Use multiple queues, per-request deadlines, and HTTP/2 or HTTP/3 multiplexing.
  • Cold caches and cold JITs: pre-warm new instances before adding them to the load balancer (see readiness in section 15).
  • Replica variance: some instances are simply slower (noisy neighbour, bad disk). Load balancing that considers load (least outstanding requests, "power of two choices") routes around them (Chapter 9).

13. Hedged requests, backup requests and coalescing

13.1 Hedged (backup) requests

If one replica might be slow, ask two. A hedged request sends the request to one replica, and if no reply arrives within a short delay, sends a second copy to a different replica. Whichever answers first wins, and the other is cancelled. The delay is chosen near the service's p95 or p99 latency so that only a small fraction of requests (roughly 1 to 5 percent) are hedged, adding a few percent of load but cutting the tail dramatically.

Variants: tied requests send both immediately to two replicas that know about each other and cancel each other's queue entry as soon as one starts executing, which avoids the duplicated work but needs server cooperation. Hedging gRPC and Envoy both support configurable hedge policies. Use hedging with care: it is only safe for idempotent operations (Chapter 32), and during a widespread overload it makes things worse, since hedges add load. Therefore combine hedging with a budget, and disable it when the system is shedding.

13.2 Request coalescing (single flight)

If 1000 concurrent requests ask for the same expensive thing (the same cache key, the same report), do the work once and share the result. Request coalescing, also called single flight or collapsed forwarding, makes the first request do the work while later identical requests wait on its result. It is the central defence against the cache stampede in Chapter 14 and is built into CDNs and proxies as "request collapsing". Go's singleflight package, Caffeine's loading cache and Varnish's request coalescing all implement it. Combine it with a timeout on the waiters and a short stale-serving window so that a slow leader does not hold everyone hostage.

14. Cascading and metastable failures

A cascading failure is one in which the failure of one component raises the load or error rate on its peers, making them fail too, and so on, until a large portion of the system is down. The classic trigger is a node failure in a pool: the remaining nodes take on its traffic, a few of them tip over from the extra load, which puts yet more load on the survivors. A metastable failure is the nastiest cousin: the system enters a bad state that persists even after the original trigger is removed, because a feedback loop (usually retries or cache misses) sustains the overload by itself.

14.1 Walkthrough of a typical cascade

Consider a service tier of 10 servers, each able to handle 1000 requests per second, serving a steady 7000 rps (70 percent utilisation) from users, backed by a database fronted by a cache.

  1. Trigger. A small deploy briefly slows the cache layer. Cache lookups that took 1 ms now take 800 ms and time out at 500 ms.
  2. Fallthrough. Timed-out cache lookups are treated as misses. All 7000 rps now go to the database, which normally sees 700 rps (a 90 percent hit rate). The database is asked to carry ten times its usual load and its latency rises from 5 ms to 2 s.
  3. Thread exhaustion. By Little's law each app server now holds 700 requests × 2 s = 1400 in-flight calls but has only 200 threads. Requests queue and time out.
  4. Retries. Clients and upstream layers retry the timed-out requests: three attempts each. Offered load climbs from 7000 to 21,000 rps.
  5. Health checks fail. A server whose threads are all stuck cannot answer the load balancer's health check, so the balancer removes it. With 9 servers left, each now receives more load; they too fail their checks. The pool shrinks toward zero.
  6. Restart herd. Operators restart servers. Cold servers with empty caches and cold connection pools are added back all at once, and immediately overwhelmed by the retry backlog, so they fail again.

14.2 Why metastability happens, and how to prevent it

Metastable states exist when a sustaining effect is stronger than the trigger. Common sustaining effects are retry amplification, a cache that is empty and therefore sends all load to the database (the database cannot refill the cache fast enough because it is overloaded), and GC thrash under memory pressure from long queues. Prevention strategies map directly onto earlier sections: retry budgets and jitter (4), circuit breakers (5), concurrency limits and shedding (8), bounded queues (9), short timeouts (3), and avoiding hard dependence on cold caches by warming and by request coalescing (13). A rule of thumb from capacity planning: keep enough headroom that the system survives losing its biggest failure domain (one AZ, one cache node group) without crossing the overload cliff, the N+1 or N+2 sizing described in Chapter 41.

14.3 Thundering herd on recovery

Recovery is dangerous too. When a dependency returns, every waiting client, queued job, paused consumer and tripped breaker tries to proceed at once, a thundering herd. A database with 20 minutes of backlog and 50,000 clients all reconnecting in the same second will fall over again. Defences:

  • Jittered retry delays and jittered breaker wait times so clients return gradually.
  • Slow start / ramp-up in load balancers: a newly healthy instance receives a gradually increasing share of traffic over, say, 60 seconds (supported by Envoy, NGINX Plus and cloud load balancers).
  • Rate-limit queue consumers on restart, and drain backlog at a controlled speed instead of the maximum.
  • Pre-warm caches and connection pools before taking traffic, and use request coalescing for the first misses.
  • Stagger restarts and deploys (rolling in small batches) so not all instances are cold simultaneously.
  • Operationally, bring traffic back in steps (10, 25, 50, 100 percent), watching error rates at each stage.

15. Health checks, readiness and graceful shutdown

15.1 Liveness versus readiness

Orchestrators such as Kubernetes distinguish the questions "is this process alive?" and "is it ready for traffic?" and use different probes.

  • Liveness probe: "Is the process stuck beyond repair?" If it fails repeatedly, the orchestrator restarts the container. It should check only the process's own internal health (the event loop responds, no deadlock), not dependencies. A liveness probe that checks the database will restart every pod during a database outage, turning a dependency failure into a total outage plus a restart herd.
  • Readiness probe: "Can this instance serve requests right now?" If it fails, the instance is removed from load balancing but not restarted. It can include warm-up completion, loaded configuration and caches, and (carefully) dependency checks. Temporary overload can legitimately flip readiness to false so the instance can drain its queue.
  • Startup probe: gives slow-starting applications time to boot before liveness checks begin, so they are not killed during initialisation.

15.2 Deep versus shallow health checks

A shallow check returns 200 if the process is up. A deep check exercises dependencies (a trivial database query). Deep checks catch more problems but are dangerous at fleet scale: if the shared database blips, every instance fails its deep check and the load balancer removes the entire fleet, even though a degraded response would have been better than none. A good compromise: shallow checks in the load balancer, deep checks as a separate dashboard signal, and a per-instance decision to go unready only for instance-local problems. Many load balancers also support a panic threshold: if more than, say, 50 percent of hosts are unhealthy, ignore health status and send traffic to all of them, assuming the health checks are the problem. Details about balancer health checks are in Chapter 9.

15.3 Graceful shutdown and connection draining

Deploys, autoscaling and node maintenance all stop instances. If an instance is killed while handling requests, those requests fail, which shows up as a burst of errors at every deploy. A graceful shutdown sequence avoids this:

  1. The instance receives a termination signal (SIGTERM in containers).
  2. It immediately marks itself not ready so the load balancer or service registry stops sending new requests. Because deregistration takes time to propagate (seconds for endpoint lists and DNS), the instance should keep serving for a short grace period, often a 5 to 15 second sleep, before closing listeners.
  3. It stops accepting new connections, tells HTTP/1.1 clients Connection: close or sends HTTP/2 GOAWAY, and lets in-flight requests finish (connection draining), up to a drain timeout.
  4. It flushes buffers, finishes or hands back queue messages (negative acknowledge so they are redelivered), closes database connections and exits cleanly.
  5. If the drain timeout expires, the orchestrator sends SIGKILL. The drain timeout must exceed your longest normal request, and the deregistration delay should not exceed the orchestrator's termination grace period (30 seconds by default in Kubernetes), so set both deliberately.
Watch out Clients holding long-lived keep-alive connections to a draining instance can keep sending requests into it. Close idle connections, send GOAWAY, and set maximum connection age on servers and proxies (for example 5 minutes) so connections naturally rebalance, which also helps spread load after scale-out.

16.1 Library versus mesh

Putting policies in a proxy or mesh gives consistency across languages and lets operators change them without a redeploy, but the proxy sees only the network call, not application meaning. It cannot know a particular call is idempotent unless told, nor can it provide business-level fallbacks (show cached recommendations). Application libraries can do both but must be kept consistent across teams. Many organisations use both: the mesh for timeouts, retries and outlier detection, application code for fallbacks and degradation. Be careful that retries are not enabled in both places, which would reintroduce the multiplication of section 4.4.

16.2 A composition order that works

The order of decorators matters. A common, sensible nesting from outermost to innermost is: Fallback wraps Bulkhead wraps Retry wraps Circuit breaker wraps Timeout wraps the actual call. Reading from the inside: each attempt has a timeout; the breaker records the outcome of each attempt and rejects when open; the retry policy re-attempts (and treats a breaker rejection as non-retryable, so it does not spin); the bulkhead caps total concurrency; and the fallback produces a degraded response if everything else failed. Placing retry outside the breaker is deliberate: the breaker sees every attempt and can trip, while retry stops once the breaker is open. Resilience4j and Polly document equivalent orderings, and getting this order wrong is a common review comment.

17. Chaos engineering, game days and resilience testing

A resilience mechanism that has never been exercised under real failure should be assumed broken. Chaos engineering is the discipline of running controlled experiments on a system to build confidence that it withstands turbulent conditions. It was popularised by Netflix (Chaos Monkey terminated random instances; the wider Simian Army injected latency and killed whole regions in tests).

17.1 The experiment loop

  1. Define steady state as a measurable business or service metric, such as orders per minute or p99 latency, not "CPU is fine".
  2. Form a hypothesis: "If one of three cache nodes dies, steady state is unchanged and p99 rises less than 20 percent."
  3. Limit the blast radius: start in staging, then in production for a small slice (one cell, 1 percent of traffic) with a clear abort button and watching alarms.
  4. Inject the failure and observe.
  5. Learn and fix: if the hypothesis fails you found a weakness before customers did. Fix it, then repeat the experiment as a regression test.

17.2 Kinds of failure injection

  • Resource: kill processes, pods or instances; fill a disk; exhaust memory, CPU or file descriptors.
  • Network: add latency (for example 500 ms to a dependency), packet loss, bandwidth limits, partition two services, break DNS. Tools: Linux tc netem, Toxiproxy, Envoy fault injection, service-mesh fault injection.
  • Application-level: make a dependency return 500s or time out for a percentage of calls, corrupt responses, throw exceptions in chosen code paths (fault-injection filters in a gateway or mesh do this without code changes).
  • Dependency and platform: take away a whole availability zone, a database failover, expire a certificate, stop a clock sync, throttle a cloud API. Managed services exist for this (AWS Fault Injection Service, Azure Chaos Studio, Gremlin, Chaos Mesh, LitmusChaos).
  • Human and process: restore from backup, rotate secrets, run failover drills (these overlap with Chapter 41).

17.3 Game days

A game day is a scheduled, cross-team exercise where a realistic failure is simulated (or injected) while engineers respond using real runbooks and dashboards. It tests people and process as much as software: do the alerts fire, does the right person get paged, is the runbook accurate, can the team find the cause in the observability tools, does anyone know how to flip the feature flags that shed load. Typical output is a list of fixes to alerts, dashboards, runbooks and code. Run them regularly, record what was learned, and include on-call engineers who do not own the failing component.

17.4 Other resilience testing

  • Load and stress tests that push past capacity to find the overload cliff and verify that shedding keeps goodput flat (section 8). Include a soak test for slow leaks.
  • Retry and timeout tests in CI using fault-injecting proxies: assert that a dependency returning 503 produces bounded extra load, not 81 times.
  • Recovery tests: stop a dependency for ten minutes and restore it; verify there is no thundering herd (section 14.3).
  • Canary deploys and progressive rollout to catch a faulty release (the Byzantine failure of section 2) while it affects 1 percent of traffic, with automatic rollback.
  • Static review: search code for network calls with no timeout, unbounded queues and thread pools, retries at multiple layers, and health checks with dependency calls. This catches most production incidents before they start.
Good practice Pair each resilience pattern with the metric that proves it is working: breaker state and rejection counts, retry rate as a percentage of calls, queue depth and age, shed request count, hedge rate, bulkhead rejections, and p99 versus p50 gap. A pattern you cannot observe will eventually fail silently.

20. Checklists

20.1 Per outbound call

  • Connect timeout, read timeout and an overall deadline are set, and the deadline is propagated to the callee.
  • Each timeout is shorter than its caller's timeout, with room for the retries in the budget.
  • The operation is classified as idempotent or carries an idempotency key before any retry is enabled.
  • Retries use exponential backoff with jitter, a small attempt cap, a retry budget, and happen at a single layer.
  • A circuit breaker (per endpoint) with slow-call detection guards the call, and a fallback is defined.
  • A bulkhead (pool, semaphore or per-tenant quota) isolates the call from others.

20.2 Per service

  • All queues and thread pools are bounded, with defined behaviour when full.
  • Concurrency limit and load shedding exist; overload returns fast 429/503 with Retry-After; expired deadlines are dropped.
  • Liveness checks are internal only; readiness reflects warm-up and local overload; shutdown drains gracefully.
  • Capacity headroom survives the loss of the largest failure domain; utilisation targets leave queues short.
  • Features are classified by criticality, and shedding switches are tested.
  • Dashboards show retry rate, breaker state, queue depth and age, p50/p99/p99.9, shed counts, and saturation.

20.3 Per organisation

  • Failure injection in CI and staging; regular production game days with written findings.
  • Runbooks for load shedding, traffic ramp-up and disabling features, rehearsed by on-call engineers.
  • Post-incident reviews that ask which pattern was missing, and add a regression experiment.

21. Interview questions and answers

Why is a slow dependency more dangerous than a dead one?

A dead dependency usually refuses connections immediately, so the caller learns about it in microseconds and can fail over or use a fallback. A slow dependency accepts the call and then holds the caller's thread, connection and memory until the timeout. By Little's law, the concurrency needed equals arrival rate times latency, so a dependency that is 40 times slower needs 40 times as many workers. The caller runs out of workers, becomes slow itself, and the slowness spreads up the call chain. This is why timeouts, bulkheads and breakers with slow-call detection exist.

How do you decide whether it is safe to retry a request?

First check that the failure is plausibly transient (timeout, connection reset, 503, 429), not a deterministic client error. Then check that running the operation twice is harmless. Reads and set-style writes are naturally idempotent; payments, order creation and counter increments are not, so they need an idempotency key that the server uses to deduplicate. I would also check that this layer is the only one retrying, otherwise attempts multiply, and that a retry budget limits the added load during widespread failure.

Explain exponential backoff with jitter and why jitter is needed.

Exponential backoff increases the wait between attempts (100 ms, 200 ms, 400 ms and so on up to a cap), giving a struggling server time to recover. Without jitter, every client that failed at the same moment retries at the same moments, producing synchronised bursts. Jitter randomises the wait; with full jitter each wait is a random value between zero and the exponential bound, which spreads the retries into a smooth stream and lowers peak load. Decorrelated jitter bases each wait on the previous one, which also works well when clients start in lockstep.

A request passes through four services that each retry three times. What happens when the database fails?

Attempts multiply: 3 × 3 × 3 × 3 = 81 database calls per user request. At 1000 user requests per second the failing database receives 81,000 attempts per second, which prevents its recovery and may form a metastable retry storm. The fix is to retry at one layer only (typically the closest to the user, or the layer nearest the failing call), use retry budgets of about 10 percent of traffic, add jittered backoff, and use circuit breakers so deeper layers stop calling once the dependency is clearly down.

Describe how a circuit breaker works and how you would configure one.

It has three states. Closed passes calls and records outcomes over a rolling window. When the failure or slow-call rate exceeds a threshold (say 50 percent over at least 20 calls) it opens, rejecting calls instantly for a wait period (say 30 seconds) while a fallback serves. Then it goes half-open and admits a handful of trial calls; if they succeed it closes, otherwise it reopens. I would scope breakers per endpoint or host so one bad operation does not block healthy ones, count only timeouts and 5xx as failures, include slow calls, and add jitter to wait durations to avoid synchronised probing.

What is the bulkhead pattern and when would you use thread pools versus semaphores?

A bulkhead gives each dependency or tenant a separate, capped resource pool so one failing component cannot consume everything. Thread-pool bulkheads provide strong isolation and allow timing out a stuck call, but cost context switches and memory. Semaphore bulkheads are just a limit on concurrent calls on the caller's thread: cheap, suitable for non-blocking code, but they cannot interrupt a hung call. I use pools for blocking calls to risky dependencies and semaphores for cheap, fast calls and async code, sizing both using Little's law with headroom.

What is load shedding, and how is it different from rate limiting?

Rate limiting enforces a per-client or per-key quota regardless of server state, which is fairness and abuse control. Load shedding is the server protecting itself: when current load or queue delay exceeds what it can handle, it rejects some requests quickly so the rest still meet their latency targets, keeping goodput at capacity instead of collapsing. Good shedders prioritise (shed batch before interactive), drop requests whose deadline has already passed, reject cheaply before expensive work, and return 503 or 429 with Retry-After so clients back off.

Why does fan-out make tail latency worse? Give the numbers.

A user request that waits for N parallel sub-calls is as slow as the slowest one. If each sub-call is slower than its p99 with probability 1 percent, the chance that at least one of N is slow is 1 minus 0.99 to the N. For N = 10 that is about 9.6 percent, for N = 100 it is about 63 percent, so the backend's p99 becomes the front end's typical latency. To cope, reduce fan-out, tighten backend p99.9, use hedged requests, set per-call deadlines with partial results, and keep utilisation low enough to avoid queueing.

What are hedged requests and what are the risks?

A hedged request sends a duplicate to a second replica if the first has not answered within roughly the p95 latency, takes whichever reply arrives first and cancels the other. Because only the slow few percent are duplicated, extra load is small, while the tail latency drops substantially. The risks are that the operation must be idempotent, that hedging increases load in overload (so it must be budgeted and disabled while shedding), and that the cancel must actually free server work. Tied requests, where replicas cancel each other, reduce duplicated work further.

What is a metastable failure and how do you recover from one?

A metastable failure is a state where the system stays overloaded after the initial trigger is gone because a feedback loop sustains it, typically retries multiplying load, or an empty cache sending all traffic to the database so that it cannot refill the cache. Fixing the original cause is not enough. You must cut load below capacity, by shedding, disabling retries, turning off non-critical features or temporarily blocking clients, then ramp traffic back gradually with warm caches. Prevention is retry budgets, circuit breakers, bounded queues, concurrency limits and headroom.

What is the difference between liveness and readiness probes, and why does it matter?

Liveness asks whether the process is irrecoverably stuck, and failing it causes a restart. Readiness asks whether the instance should receive traffic now, and failing it removes the instance from load balancing without restarting. If a liveness probe checks a shared dependency like the database, a database blip restarts every instance and turns a partial problem into a total outage with a cold-start herd. So liveness should be internal and cheap, and readiness should cover warm-up and local overload, with care about dependency checks.

How would you shut a service down without dropping requests?

On SIGTERM, the instance first flips to not-ready so the load balancer or registry stops routing new requests, and keeps serving for a few seconds because deregistration takes time to propagate. Then it closes listeners, signals clients to reconnect (Connection close or HTTP/2 GOAWAY), and waits for in-flight requests to finish within a drain timeout. It flushes buffers, returns unacknowledged queue messages for redelivery, closes connections and exits. The drain timeout must exceed the longest normal request and fit inside the orchestrator's termination grace period before SIGKILL.

How do you test that your resilience mechanisms actually work?

I treat untested fallbacks as broken. I use failure injection in staging and CI (latency, errors and partitions via Toxiproxy, mesh fault injection or tc netem), asserting bounded retry load and breaker behaviour. I run load tests beyond capacity to find the overload cliff and confirm shedding keeps goodput flat. In production I run chaos experiments with a defined steady state, a hypothesis and a limited blast radius, and periodic game days so humans, alerts and runbooks are exercised too. Findings become regression experiments.

22. Recap

  • The dangerous failures are slow and partial ones. A caller can only see "no answer in time", so timeouts underpin everything else.
  • Use separate connect and read timeouts plus an overall deadline that propagates down the call chain, with inner timeouts smaller than outer ones.
  • Retry only retryable failures on idempotent (or keyed) operations, with exponential backoff and jitter, a retry budget, and at one layer. Layered retries multiply: 3 attempts across 4 layers is 81 times the load.
  • Circuit breakers (closed, open, half-open, per endpoint, counting slow calls) stop pounding a sick dependency and enable fast fallbacks.
  • Bulkheads cap resources per dependency or tenant, so one failure is confined; size pools and queues with Little's law, because latency times arrival rate equals concurrency.
  • Plan fallbacks and feature shedding ahead of time: cached or stale data, defaults, deferral, and conscious fail-open or fail-closed choices.
  • Shed load, apply backpressure and keep every queue bounded; queue-based levelling smooths spikes for asynchronous work at the cost of delay.
  • At fan-out N, a per-call 1 percent tail hits 1 − 0.99N of requests (63 percent at N = 100), so fight the tail with low utilisation, hedging, coalescing and lower fan-out.
  • Metastable failures need load reduction and slow ramp-up, not just a bug fix; thundering herds on recovery are prevented by jitter, slow start and staged traffic.
  • Liveness is internal and restarts; readiness controls routing; shutdown drains. Verify all of it with chaos experiments, game days and failure injection.
