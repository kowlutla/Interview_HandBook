Gossip, Failure Detection and Merkle Trees

In a large cluster nobody is in charge, yet every node must agree on who is alive, where data lives, and whether its copy of the data matches its neighbours'. This chapter shows how nodes spread information by gossiping like a rumor, how they decide a peer is dead without being fooled by a slow network, and how they find the few differing records among billions by comparing hash trees.

1. The problem: who is in the cluster, and who is alive?

Imagine a database made of 1,000 servers. A client asks one of them for a key, and that server must know which other server owns the key (see Chapter 25). It must also know which of those servers are currently healthy, because sending a write to a dead machine wastes time. So every node needs a reasonably fresh answer to two questions: membership (which nodes belong to the cluster, and what tokens or ranges does each own?) and liveness (which of those members are working right now?).

The obvious design is a central authority. One service, a "monitor", receives a heartbeat (a small "I am alive" message) from every node every second and keeps the member list. Everyone else asks the monitor. This is simple and is how many systems start, and it is often the right choice at small scale. In fact, ZooKeeper, etcd and similar coordination services are used exactly this way for modest clusters.

But a central monitor has well-known weaknesses at scale:

  • Single point of failure. If the monitor dies or is partitioned away, nobody knows who is alive. You fix this by replicating the monitor, which means running a consensus group (Chapter 24), which itself needs care.
  • Bottleneck. A thousand nodes sending one heartbeat per second is only 1,000 messages per second, which is easy. But with 100,000 nodes, or a heartbeat every 100 ms, or a member list that has to be pushed back out to every node, the monitor becomes the hot spot.
  • Wrong vantage point. The monitor sees the network from its own position. If the link between the monitor and node A breaks, the monitor declares A dead although A is perfectly reachable from all its peers. What matters for a database is whether peers can talk to A, not whether one observer can.
  • Coupling. Every node's view of the world depends on one component being reachable. In a multi-datacenter deployment, a cross-ocean link failure would make an entire region believe the other region is dead or, worse, lose track of its own members.

The other extreme is all-to-all heartbeating: every node pings every other node every second. With N nodes that is N × (N − 1) messages per second. For N = 1,000 that is nearly one million messages per second, and every node must process 999 incoming messages each second just to learn that nothing happened. The cost grows with the square of the cluster size, so this collapses well before a few thousand nodes.

Key idea Decentralized membership tries to give every node a good-enough view of the cluster with constant work per node, no single point of failure, and views formed from many vantage points. Gossip (also called epidemic) protocols are the standard tool. The price is that information spreads in rounds, so views are eventually consistent rather than instantly consistent.

2. Gossip: spreading information like a rumor

The idea comes from how rumors, or diseases, spread. Suppose one person learns a piece of news. Every minute, each person who knows the news tells it to a randomly chosen friend. At first only one person knows. After one minute, two know. After two minutes, up to four. The number of informed people roughly doubles each round until most people know, at which point new tellings increasingly hit people who already know. Within a surprisingly small number of rounds, nearly everyone knows, even though nobody coordinated anything and nobody had to talk to more than one person per minute.

Translate this to a cluster. Every node runs a loop on a timer (typically once per second, sometimes faster). Each gossip round, the node picks a small number of random peers, called the fanout (commonly 1 to 3), and exchanges state with them. The state is whatever the cluster must agree on: membership entries, heartbeat counters, tokens, schema versions, load figures. When a node learns something new from a peer, it simply includes it in its own future exchanges, and so the information spreads outward from its origin.

2.1 Push, pull and push-pull

When two nodes gossip, there are three ways to exchange data.

  • Push. The initiator sends what it knows to the peer. This is fast at the start (a node that knows something actively spreads it) but slow at the end: when almost everybody is informed, the few uninformed nodes are rarely chosen as targets by anyone, so the last stragglers take a while.
  • Pull. The initiator asks the peer "what do you know that I do not?" and the peer answers. This is slow at the start (few nodes have anything to give, so most pulls return nothing new) but very fast at the end: an uninformed node asks a random peer, and by then most peers are informed, so it learns immediately.
  • Push-pull. Both directions in one exchange: each side tells the other what it has and receives what it lacks. It combines the fast start of push with the fast finish of pull and is the most common choice in production systems (Cassandra's three-message handshake and memberlist's periodic full state exchange are both push-pull flavours).

2.2 Why it converges in O(log N) rounds

Take pure push with fanout 1 and N nodes. Early on, when few nodes know the news, almost every message lands on an uninformed node, so the informed count doubles each round: 1, 2, 4, 8, ... After about log2 N rounds roughly half of the cluster is informed. Then the dynamics reverse: the informed fraction is large, and the chance that a given uninformed node is hit by at least one push in a round is about 1 − e−1 ≈ 63%, so the uninformed fraction shrinks by a constant factor (about e) each round. Clearing the remaining nodes takes about ln N more rounds. The known result for push is that full dissemination takes about log2 N + ln N rounds with high probability.

Plug in numbers. For N = 1,000: log2 1000 ≈ 10 and ln 1000 ≈ 6.9, so about 17 rounds with fanout 1. For N = 1,000,000: 20 + 13.8 ≈ 34 rounds. A thousand times more nodes costs only twice the rounds. That is the whole appeal of gossip: dissemination time grows with the logarithm of the cluster size. With a one-second round, news reaches 1,000 nodes in under 20 seconds with a single message per node per second.

Raising the fanout to k means the informed set multiplies by about (k + 1) per round early on, so the exponential phase takes logk+1 N rounds. With k = 3 and N = 1,000, that is log4 1000 ≈ 5 rounds for the growth phase, plus a shorter tail, so roughly 8 to 10 rounds in total. Push-pull shortens the tail dramatically, to roughly log2 N plus a very small additive term (about ln ln N), because in the tail pulls find the news almost immediately.

2.3 Rumor mongering versus anti-entropy

There are two classic gossip styles, named in the 1987 Xerox paper that introduced epidemic algorithms for replicated databases.

  • Rumor mongering (also called dissemination). A node that learns a new update treats it as "hot" and forwards it to random peers for a limited number of rounds, or until it hits several peers that already know it, then stops treating it as news. It is cheap and fast because only fresh updates are sent, but it is probabilistic: there is a small chance that a given update dies out before reaching everyone.
  • Anti-entropy. Periodically, each node picks a peer and the two compare their entire state and reconcile any differences. It never forgets, so it guarantees that two replicas eventually converge even if every earlier message was lost. It is more expensive per round because it must compare everything, which is exactly where Merkle trees (section 7) come in: they make the comparison cheap.

Real systems combine them: rumor mongering for speed, and a slower anti-entropy background process as the safety net that repairs whatever the rumors missed. You will see this pattern again in replicated stores, where read repair and hinted handoff play the "fast" role and full anti-entropy repair plays the "safety net" role.

Interview tip When asked "how do nodes learn about each other without a coordinator?", say: periodic random exchange, constant cost per node, O(log N) rounds to spread news, and probabilistic rather than absolute guarantees. Then volunteer that gossip is paired with a slower anti-entropy pass for correctness. That shows you understand both speed and eventual guarantees.

2.4 What gets gossiped

The simplest gossip state for membership is a table with one row per node: the node's address, a heartbeat counter that the owner increments regularly, and a local timestamp of when this node last saw the counter increase. When two nodes exchange tables, for each row they keep the entry with the higher heartbeat counter. Because only the owner increments its own counter, a higher counter always means newer information, which sidesteps clock synchronization: nobody compares wall clocks, only counters (more on version conflicts in Chapter 27). If a row's counter has not increased for a long time, the observer concludes the owner may be dead. This is the original gossip-style failure detector from van Renesse, Minsky and Hayden (1998).

The problem with sending whole tables is that size grows with N. Production systems therefore exchange digests (just node names and version numbers) first and transfer full rows only for entries that differ. Cassandra's three-message handshake does exactly this and is described in section 3.

3. Gossip in real systems

3.1 Cassandra (and Dynamo)

Amazon's Dynamo paper (2007) popularized using gossip for membership in a key-value store, and Cassandra inherited the idea. In Cassandra, each node runs a gossip task about once per second. In each round it picks one random live node, and with some probability also a random unreachable node (to detect recovery) and a seed node (to prevent the cluster from splitting into islands that never hear of each other). The exchange is a three-message handshake:

  1. SYN: the initiator sends a digest, a compact list of (node, generation, max version) it knows about.
  2. ACK: the receiver compares the digest with its own state, replies with full data for entries where it is newer, and with a request for entries where the initiator is newer.
  3. ACK2: the initiator sends the requested entries.

That is push-pull with a digest step, so bandwidth is spent only on actual differences. The state gossiped per node includes its status (normal, joining, leaving, moving), its tokens (which hash ranges it owns), its data center and rack, its schema version, its load, and a heartbeat version. Each node has a generation number (the timestamp of its last start) and a version counter that increases with every change; comparing (generation, version) pairs tells which information is newer, even across restarts. Seed nodes are simply well-known addresses given to new nodes so they have somewhere to start gossiping; they are not special leaders.

3.2 Serf, memberlist and Consul

HashiCorp's memberlist library implements a SWIM-based protocol (next section) with extensions, and Serf is a tool built on it that offers cluster membership, failure detection and custom events. Consul uses Serf/memberlist for its agent cluster: every Consul agent in a datacenter joins a "LAN gossip pool", and the servers additionally join a "WAN gossip pool" across datacenters. Gossip handles membership and failure detection among hundreds or thousands of agents, while Consul's actual data (the service catalog and key-value store) is kept consistent by a small group of server nodes using Raft consensus. This division of labour is a pattern worth remembering: use gossip for cheap, wide, approximate knowledge, and consensus for small, critical, exact state. Memberlist also runs periodic full-state push-pull syncs over TCP (typically every tens of seconds) as an anti-entropy backstop for the fast but lossy UDP gossip, and it includes the Lifeguard improvements, which make a node that is itself overloaded less likely to falsely accuse others (section 5.4).

3.3 Where else you will see it

Riak and ScyllaDB use gossip similar to Cassandra's. Redis Cluster nodes exchange gossip over a cluster bus to share slot ownership and failure reports, and a node is marked as failed only when a majority of master nodes report it unreachable. Many service meshes and orchestration tools use SWIM-style membership under the hood. Bitcoin and other peer-to-peer networks use gossip to propagate transactions and blocks. Kubernetes does not use gossip for node health; it uses a central API server with kubelet heartbeats, a good example of the central design working fine because clusters are limited to a few thousand nodes.

4. SWIM: failure detection scaled and separated from dissemination

The gossip-heartbeat approach above has a weakness: every node's table grows with N, and detection of a failure waits for a counter to go stale and then for that suspicion to be gossiped. In 2002 Das, Gupta and Motivala proposed SWIM (Scalable Weakly-consistent Infection-style process group Membership), which splits the problem into two independent parts: a failure detector with constant cost per node, and a dissemination component that spreads membership changes.

4.1 The probe cycle

Every protocol period (say 1 second), each node Mi picks one random member Mj and sends it a ping. If Mj replies with an ack within a short timeout, all is well. If not, Mi does not immediately accuse Mj. Instead it asks k other randomly chosen members (k is often 3) to probe Mj on its behalf with ping-req. Each helper sends its own ping to Mj and, if it receives an ack, relays it back to Mi. If Mi hears no ack by the end of the period, either directly or through any helper, it marks Mj as suspect.

The indirect probe is the clever part. A single failed ping can mean B is dead, but it can equally mean the A to B link dropped a packet, or A itself is overloaded. Asking k helpers gives k independent vantage points; the chance that all k paths fail by coincidence is small, so false positives drop sharply. And the cost stays constant: per period, each node sends one ping, receives about one ping on average, and only occasionally sends ping-reqs.

4.2 Dissemination by piggybacking

SWIM does not run a separate gossip round for membership updates. It piggybacks them on the ping, ack and ping-req messages that the failure detector is sending anyway. Each message carries a small bounded list of recent membership events ("B suspect", "E joined", "F left"). A node keeps each event in a buffer and attaches it to outgoing messages a limited number of times, roughly λ · log N transmissions for some small constant λ (memberlist uses a "retransmit multiplier" that works this way), preferring events that have been sent fewest times. Because probe targets are random, this is exactly an infection-style spread, and the log N retransmission count is enough for the news to reach all nodes with high probability. Piggybacking means zero extra messages for dissemination and a message size that stays small, which is why this scales so well.

4.3 Suspicion, incarnation numbers and refutation

Declaring a node dead is costly: its data may be re-replicated, its traffic rerouted. SWIM therefore adds a suspicion stage. Rather than going straight from alive to dead, the target is marked suspect and given a grace period (the suspicion timeout) to prove it is alive. During that time:

  • The suspicion is gossiped to everyone, including B itself.
  • If B hears it is suspected, it refutes the claim by broadcasting "I am alive" with an incremented incarnation number.
  • Message precedence is: an alive message with a higher incarnation beats a suspect message with a lower one; a suspect message beats an alive message with the same incarnation; a confirmed-dead message beats everything for that incarnation. So a refutation overrides the suspicion, but a stale refutation cannot override a newer suspicion, and old rumors never resurrect a decision.
  • If the timeout elapses without a refutation, the node is declared dead (a "confirm" message is gossiped). Memberlist scales the suspicion timeout with log N, and it shortens the timeout as more independent nodes confirm the suspicion.
Watch out SWIM and gossip detectors give weak guarantees. A node declared dead may still be running (it was just slow or partitioned), and it may keep accepting requests from clients that can still reach it. Never treat "declared dead" as proof that the node has stopped. If you need exclusive ownership, for example a single leader or a lock holder, use consensus and fencing tokens (Chapter 27), not a membership view.

5. Failure detection in depth

5.1 Why failure detection is fundamentally uncertain

From a node's point of view, "B is dead" and "B is slow, or the network between us is slow" look identical: in both cases no message arrives. In an asynchronous network, with no upper bound on delay, it is provably impossible to tell the two apart with certainty (this is part of why consensus is hard). A failure detector can therefore only guess, and it can be wrong in two ways:

  • False positive (false suspicion): a healthy node is declared dead. The cluster does needless work, such as moving data, electing a new leader, or failing over traffic, and a healthy node may be shut out.
  • False negative / slow detection: a dead node is believed alive for too long. Requests are sent to it and time out, and writes may be lost or delayed.

The two errors trade against each other. Detect faster and you will make more false positives; wait longer and failures hurt longer. The designer picks a point on this curve to match the cost of each mistake.

5.2 Fixed timeouts and their weaknesses

The simplest detector: if no heartbeat arrives within T seconds, declare the node dead. This is easy to implement and easy to reason about, but a single number T is a poor fit for real networks.

  • Network conditions change. A timeout of 2 seconds is fine on a quiet LAN, but during a traffic spike or a garbage-collection pause heartbeats may be delayed by 3 seconds, and every node in the cluster flaps to "dead" at once.
  • Different links differ. Heartbeats across regions take 150 ms with high jitter; within a rack, 0.2 ms with little jitter. A single T must be generous enough for the worst link, which makes detection slow on the best links.
  • Binary output. A fixed timeout answers only "dead or alive". The application cannot choose its own tolerance: a cache client wants to avoid suspicious nodes quickly, while a data-migration job wants to be very sure before moving 2 TB.

5.3 The phi-accrual detector

The phi accrual failure detector (Hayashibara et al., 2004), used by Cassandra and Akka among others, replaces "dead or alive" with a continuous suspicion level called phi (φ), computed from the actual heartbeat history. The word accrual means suspicion accumulates the longer a heartbeat is overdue.

Intuition. Suppose heartbeats from node B usually arrive every 1.0 second, give or take 0.1 s. If the last heartbeat was 1.2 s ago, you are not worried; that is within normal variation. If it was 3 s ago, that is far outside anything you have seen, so you are quite suspicious. If B's heartbeats are normally very jittery (anywhere from 0.5 to 4 s), then 3 s of silence is unremarkable. The detector formalises this: it keeps a sliding window of recent inter-arrival times for each peer, estimates their distribution, and asks, "given this history, how probable is it that a healthy node's next heartbeat would be this late?" Then:

phi(t) = -log10( P(next heartbeat arrives later than t) )

where t is the time since the last heartbeat. Because it is a base-10 logarithm, phi is easy to read: phi = 1 means a 10% chance that a healthy node would be this late; phi = 2, 1%; phi = 8, one in a hundred million. As silence continues, the probability of "still healthy" falls and phi rises smoothly without bound.

A worked feel for the numbers. Cassandra models heartbeat gaps as roughly exponentially distributed, which simplifies the formula to about phi ≈ 0.434 × t / mean, where mean is the average gap observed. With the default conviction threshold of 8 and a mean gap of 1 second, a node is convicted after about 8 / 0.434 ≈ 18 seconds of silence. If the network gets noisier and the observed mean gap grows to 2 seconds, the same threshold waits about 37 seconds. The timeout stretches automatically with conditions, rather than being a fixed constant.

Two further benefits. First, separation of concerns: the monitoring component outputs a continuous number, and each consumer decides what to do. A load balancer might avoid a node at phi 2, while a repair scheduler waits for phi 10. Second, no manual tuning per link, because the distribution is learned. The costs: it needs a history window per peer (a little memory), it assumes the learned distribution is a reasonable model (heavy-tailed pauses such as long GC stalls or VM freezes can still fool it), and a threshold still has to be chosen.

5.4 False positives, detection time and Lifeguard

It helps to think about the cost of each error. A cache cluster can tolerate false positives (a spurious removal costs a few cache misses), so aggressive detection is fine. A database that re-replicates terabytes on suspicion can be wrecked by false positives, so it prefers a high threshold and longer detection time, accepting that clients may wait on a dead node for 10 to 30 seconds. Common practice is to make a cheap decision fast and an expensive decision slow: stop routing reads to a suspicious node quickly (cheap and reversible), but do not stream data to new replicas until the node has been down for minutes or hours (expensive).

Detectors suffer especially from self-inflicted false positives: if node A is itself overloaded, swapping, or paused by garbage collection, it processes acks late and wrongly concludes that many healthy peers are dead. HashiCorp's Lifeguard extensions address this by making each node track its own health (a "local health multiplier" raised when its own probes time out or when it is accused), and then lengthening its own probe timeouts and being slower to accuse others while it is unhealthy. The lesson for interviews: a failure detector must also consider that the observer may be the broken one.

6. Membership changes and cluster metadata propagation

6.1 Joining, leaving and failing

Gossip is not only a failure detector; it is also how structural changes reach everyone. Consider a new node X joining a hash-ring database:

  1. X is configured with the addresses of a few seed nodes (or a DNS name that resolves to some existing nodes).
  2. X contacts a seed, announces itself with a fresh generation number and a "joining" status, and learns the current member table through an initial push-pull exchange.
  3. X claims tokens (its positions on the hash ring, see Chapter 57) and begins streaming the data it will own from the current owners. Its gossip state says "joining", so coordinators do not yet send normal reads to it.
  4. When streaming finishes, X changes its status to "normal". This new state spreads by gossip in O(log N) rounds, and from then on nodes route requests to X as an ordinary owner.

A graceful leave is the mirror image: a node sets "leaving", streams its data to its successors, then announces "left" with a higher version, so peers drop it immediately without waiting for a failure detector. A crash is discovered only through failure detection, and the node is marked down, but it normally remains a member (its tokens still belong to it) until an operator explicitly removes it. This distinction matters: a down node and a removed node are different states, because a node that is merely down for twenty minutes should return to the same ranges and only need to catch up on what it missed (via hints and repair, section 8), not have its data reshuffled.

6.2 Tombstones for departures

When a node is removed, peers cannot simply forget it, since a lagging peer may still gossip the old "alive" entry back and resurrect it. So the "removed" state is retained as a tombstone for a while (Cassandra keeps removed endpoints around for days) so that the deletion wins the version comparison until the whole cluster has heard. This is the same reason deletions in replicated data need tombstones (Chapter 24).

6.3 Metadata propagation and its limits

The same machinery carries other small pieces of cluster metadata: the schema version, per-node load, the data-center and rack map, feature flags and software versions. Each is a (key, value, version) entry attached to a node's state, and merging is "higher version wins". Because everything converges in O(log N) rounds, gossip works well for metadata that changes rarely and tolerates a few seconds of disagreement.

It works badly when the metadata must be exactly the same everywhere at a defined instant. During propagation, node A may use new topology and node B the old one, so two coordinators could route the same key to different replica sets for a few seconds. Systems tolerate this because quorum reads and writes overlap, and repair fixes the damage later. Cassandra's schema changes illustrate the risk: if two nodes apply conflicting schema changes concurrently, gossip may leave nodes with different schema versions ("schema disagreement"), and operators must wait for or force convergence. Newer designs therefore move the most critical metadata (for example, Cassandra's newer transactional cluster metadata work, or Kafka's controller quorum) onto a consensus log, and keep gossip for what tolerates lag. As a rule of thumb: gossip for liveness and soft state; consensus for the authoritative topology and schema.

7. Anti-entropy and Merkle trees

7.1 The problem: finding differences cheaply

In a replicated store (Chapter 24), copies of the same data can drift apart. A replica was down during writes, a message was dropped, a disk silently corrupted a block. The process of detecting and fixing such drift is anti-entropy repair. The naive way is to have two replicas send each other all their keys and values and compare. With 1 TB per replica that is 1 TB of network traffic and a huge read load, repeated for every pair of replicas, to find perhaps a handful of differing records. We need a way to learn whether two big datasets match, and where they differ, while sending a tiny amount of data.

7.2 What a Merkle tree is

A Merkle tree (hash tree), invented by Ralph Merkle, is a tree of hashes. It is built bottom-up:

  1. Split the key space into ranges, and compute a hash of the data in each range. These are the leaves. For example, with 8 leaves, leaf L0 is the hash of all rows whose keys fall in the first eighth of the range.
  2. Each parent node holds the hash of the concatenation of its two children's hashes. So H01 = hash(H0 + H1).
  3. Continue up to a single root hash that summarizes the entire range. A change to any one row changes its leaf hash, which changes every ancestor up to the root, because hashes of different content differ (with overwhelming probability, assuming a cryptographic or good hash).

The property that makes it useful: if two replicas have the same root hash, their data is identical (up to hash collisions, which are negligible). One comparison of a few dozen bytes proves a terabyte matches.

7.3 Comparing two replicas by descending the tree

If the roots differ, the replicas compare the two children of the root. A matching child means that whole half is identical, so it is skipped entirely. A differing child is explored further, and so on, until the leaves are reached. Only the leaf ranges that differ are then streamed and reconciled (typically by taking the newest version of each row according to timestamps, see Chapter 27).

7.4 Cost savings in numbers

Suppose a replica owns 1 billion rows of about 1 KB, so 1 TB. A full comparison transfers 1 TB, or at least 1 billion row hashes of 16 bytes each (16 GB). With a Merkle tree of depth 30 (a binary tree has about 230 ≈ 1 billion leaves), if exactly one row differs, the walk exchanges one hash per level on each side: about 30 levels × 2 children × 16 bytes ≈ 1 KB, and then the one differing row. Even with 1,000 scattered differences, the walk touches at most 1,000 × 30 ≈ 30,000 hashes, around 500 KB. That is savings of several orders of magnitude, and the cost scales with the number of differences, not with the size of the data. If the replicas are identical, one root comparison of 16 bytes is all that is needed.

7.5 Real-world details: ranges, depth, and rebuild cost

  • Trees are per key range. Dynamo keeps a separate Merkle tree for each key range (virtual node) that a node hosts, and two replicas of the same range exchange trees for that range. In Cassandra a repair works on token ranges and builds one tree per range per table being repaired. Comparing replicas of different ranges is meaningless, so the range is the unit of repair.
  • Depth is limited. A tree with a billion in-memory leaves is itself large. Cassandra builds trees with a fixed maximum depth (on the order of 215 = 32,768 leaves per range in older versions), so each leaf covers a bucket of many rows. When a leaf differs, the whole bucket (here about 30,000 rows if the range has a billion rows) must be streamed or compared row by row, even if only one row changed. So tree depth is a tradeoff between memory and over-streaming.
  • Building the tree is expensive. To compute leaf hashes, a node must read and hash all the data in the range. That is a full scan of the table's SSTables (Chapter 19), heavy on disk I/O and CPU, which is why repair is a notorious background load and operators schedule it carefully (for example, once per gc_grace period, which is the window by which every replica must have seen deletions so that tombstones are not lost).
  • Trees go stale. The data changes while the tree is built or after it is built. Dynamo-style systems either snapshot the data at a point in time (Cassandra builds trees from a snapshot-consistent view) or maintain the tree incrementally: when a key is written, update only the one leaf and its path to the root, an O(log N) update. Incremental trees avoid rescans but cost memory and complicate crash recovery. Riak's active anti-entropy kept persistent on-disk hash trees updated as data was written, which avoided the full scan but added write overhead.
  • Hash choice. Anti-entropy trees need only a hash that makes accidental collisions negligible, so fast hashes (even non-cryptographic) are usual. Systems that must resist an adversary (git, certificate transparency, blockchains) use cryptographic hashes such as SHA-256.
  • Inconsistency in the tree itself. Because replicas may be constantly receiving writes, a difference seen in the tree may be only a write still in flight. Repairs deal with this by comparing against a point-in-time view and by rechecking before heavy streaming.

8. Repair in practice: read repair, hinted handoff and full repair

Merkle-tree anti-entropy is the slowest and most thorough of three layers that keep replicas converged in leaderless stores such as Dynamo and Cassandra. Each layer catches what the previous one missed. Replication models and quorum rules are covered in Chapter 24; here we focus on how repair works.

8.1 Hinted handoff

When a coordinator writes a key and one of its replicas is down, it still succeeds if enough other replicas acknowledge (the quorum). But the down replica is now missing the write. With hinted handoff the coordinator stores a hint, a note saying "this write belongs to node N; deliver it when N returns", in a local hints store. A node's recovery is noticed through gossip (its status turns alive again), and the holder then replays the hints to it. This repairs short outages quickly and cheaply, because only the missed writes are sent, not a comparison of full state.

Limits: hints take storage and are kept only for a bounded time (Cassandra's default hint window is about three hours), so a node that is down longer must be repaired by full repair. Hints can also be lost if the node that held them dies. And in Dynamo's "sloppy quorum" variant, hinted writes go to a stand-in node outside the key's normal replica set, so an acknowledged write may not be on any "real" replica yet; hints make it eventually reach them but reads in the meantime may be stale.

8.2 Read repair

When a client reads a key at a consistency level above one, the coordinator asks several replicas (often one for full data and others for digests, which are hashes of the answer). If the digests disagree, the coordinator fetches full values, picks the newest version (by timestamp or version vector), returns it, and writes the winning value back to the stale replicas. This repair is free in the sense that the read already touched those replicas, and it targets exactly the data being accessed, so hot data heals fast. But it fixes nothing about data that is never read, and some systems only run it on a random fraction of reads to limit overhead.

8.3 Full anti-entropy repair

For everything else there is the scheduled, Merkle-tree-based repair from section 7. It finds differences in cold data that is never read and in writes whose hints expired. It is the guarantee of eventual convergence, and the part operators must run regularly, because hints and read repair alone cannot provide it.

9. Other uses of hash trees

The idea "summarize a big structure with a hash so that comparison and verification are cheap" appears throughout engineering. Hash trees are also covered in the data-structure survey of Chapter 59; here are the main applications.

  • Git. A commit points at a tree object; a tree object lists entries by name with the hash of each file (blob) or subtree. The commit hash therefore depends on the whole repository state. Two repositories can tell they are identical by comparing one commit id, and fetch/push only need to transfer objects whose hashes the other side lacks. Git's object graph is technically a Merkle DAG (a directed acyclic graph), a generalization of the tree.
  • Blockchains. Bitcoin groups the transactions of a block into a Merkle tree and puts the root in the block header. A lightweight client (SPV) that stores only headers can verify that a transaction is in a block by receiving a Merkle proof: the sibling hashes along the path from the leaf to the root, about log2 N hashes. Verifying inclusion of one of 4,000 transactions needs about 12 hashes.
  • Certificate Transparency. Public logs of issued TLS certificates are append-only Merkle trees. A log can give an inclusion proof (this certificate is in the log) and a consistency proof (the new tree extends the old one, nothing was rewritten), both of size O(log N). Auditors can therefore detect a log that tries to hide or alter entries without downloading it all.
  • Object stores and deduplication. Backup and sync tools (and the content-addressed stores behind them) split files into chunks, hash each chunk, and combine chunk hashes in a tree. A chunk whose hash already exists is not uploaded again (deduplication), and the root hash verifies an entire file's integrity. S3's multipart uploads and checksums, and download tools that verify large files in pieces, follow the same shape, although S3's multipart ETag is a hash of part hashes rather than a full Merkle tree. Peer-to-peer download tools and distributed file systems also verify blocks against tree hashes.
  • Filesystems and databases. ZFS and Btrfs checksum each block and store the checksum in the parent pointer, forming a Merkle-style tree that detects silent corruption ("bit rot") and enables cheap snapshot comparison. Some key-value stores and verifiable databases (such as ones with authenticated data structures) use trees for tamper-evident storage.

The shared principle: the root hash is a compact commitment to everything beneath it, and a path of siblings is a small proof that some piece belongs to it. Anti-entropy uses the first property to find differences; blockchains and transparency logs use the second to prove membership.

10. Gossip for aggregation, configuration and CRDT state

10.1 Aggregation (counts, sums, averages)

Gossip can compute global quantities without a coordinator. The classic method is push-sum averaging: each node holds a pair (value, weight), and every round it keeps half and sends half to a random peer, which adds the pair into its own. Each node's ratio value/weight converges to the global average, and because mass is conserved, multiplying by N gives the sum. Counting nodes works by having exactly one node start with weight 1 and everyone else with weight 0, so the ratio converges to 1/N. Convergence is again O(log N) rounds to reach a fixed precision. Applications include estimating cluster size, average load for balancing, or the total number of connected clients. The result is approximate and the estimate changes under node failures, since a node that dies while holding mass takes that mass with it. For distinct counts, systems gossip mergeable sketches such as HyperLogLog (Chapter 57), which are idempotent and so survive duplicate delivery, something plain sums do not.

10.2 Configuration and feature flags

Small configuration values can be gossiped as versioned key-value entries, "the highest version wins". This is how a fleet can learn about a new feature flag or a changed rate limit in about log N rounds with no push infrastructure. The caveat is that the flag flips at different times on different nodes, so features must tolerate a mixed-state window.

10.3 Gossiping CRDT state

Gossip pairs naturally with CRDTs (conflict-free replicated data types, see Chapter 59). A CRDT defines a merge operation that is commutative (order does not matter), associative (grouping does not matter) and idempotent (applying twice is harmless). Those are precisely the properties gossip needs: messages may arrive in any order, be duplicated, or be delayed, and replicas still converge. A node simply gossips its state (or deltas) and merges what it receives. Examples: a grow-only counter (each node holds its own count; merge takes the per-node maximum), an add-wins set, or the per-node "highest version wins" entries used for membership. Riak's data types and Akka Distributed Data use gossip to spread CRDT state this way. Without such a merge, gossiping arbitrary updates can silently lose or reorder writes, which is why timestamps or version vectors are attached (section 11).

13. Worked example: a 1,000-node cluster

Design the membership layer for a 1,000-node key-value store using SWIM-style gossip, with a protocol period of 1 second and a fanout of 3 for dissemination. Let us work out the numbers an interviewer would expect.

13.1 Message load

  • All-to-all heartbeats at 1 per second: 1,000 × 999 ≈ 1.0 million messages per second cluster-wide, and every node processes about 1,000 incoming messages per second just to say "nothing changed".
  • SWIM probing: each node sends 1 ping and receives about 1 ping per second, plus an ack each way. That is about 2 messages sent and 2 received per node per second, or about 2,000 messages per second cluster-wide, 500 times less. It does not grow with N per node.
  • Digest-based gossip at fanout 3 (the Cassandra style): each node sends 3 SYN messages per second with a digest of maybe 50 bytes per node known. A 1,000-entry digest is about 50 KB at worst. In practice, digests are compressed or limited, and the data actually transferred is small; assume 20 KB per exchange, so 60 KB per second per node outbound, or 60 MB per second for the cluster, well within a data center network.

13.2 Detection and dissemination time

  • Detection: A node B dies at time 0. The expected time until some node probes B is about 1 period (each of the 999 other nodes picks one random target per period, so B is probed by about 1 node per period on average, and with high probability within a few periods). Direct ping times out (say 500 ms), ping-req adds up to another timeout, and the node marks B suspect after roughly 1 to 2 seconds. Strictly, the probe-selection scheme in SWIM uses a shuffled round-robin so every node is probed within N periods at worst, which bounds the time even in unlucky cases, but the typical first detection is within a few seconds.
  • Suspicion timeout: With a base of about 5 periods scaled by log10 N (memberlist-style, here 3), the suspicion timer is on the order of 15 seconds, shortened if several peers independently confirm.
  • Dissemination: The suspect and dead messages are piggybacked on probe traffic. Each message carries them, and each node retransmits an event about λ log N times (with λ = 4 and ln 1000 ≈ 7, about 28 sends, which fits easily). News reaches all 1,000 nodes in about log2 1000 + a few ≈ 12 to 17 periods for fanout 1, or about 8 to 10 periods at the higher fanout. Total time from failure to every node knowing: about 15 + 10 = 25 seconds.

13.3 Repair costs

Say each node stores 500 GB and replication factor 3. A node is down for 20 minutes while the cluster takes 10,000 writes per second, of which that node is a replica for about 3 out of every 1,000 nodes' worth, i.e. around 30 writes per second (10,000 × 3 / 1,000). That is about 36,000 missed writes. Hinted handoff stores these at the coordinators and replays them on recovery in seconds, a few tens of MB. No tree comparison is required. Now say it was down for 8 hours (beyond the 3-hour hint window): about 864,000 missed writes. Hints are gone, so the operator runs repair. Each of its replica ranges builds a Merkle tree (reading perhaps 150 GB of data per range-set in total), exchanges tree hashes in KBs, and streams only the leaf buckets that differ. With trees limited to 32,768 leaves over a range of 100 million rows, each leaf bucket holds about 3,000 rows, so if the 864,000 missed writes were all in one such range, they would land in far more rows than there are leaves (32,768) and so would touch almost every leaf, meaning nearly every bucket differs and the repair streams most of that range. (Spread over many ranges, each range sees fewer differences and the tree saves more.) This shows a real limit: when the number of differences exceeds the tree resolution, the tree stops saving much, and the choice is either deeper trees or simply streaming the data (which is what bootstrapping a fresh replica does).

14. Interview Q&A

Why not just have a central service track which nodes are alive?

A central monitor is simple and works well for small or medium clusters, and it is common (Kubernetes does it). At large scale it becomes a single point of failure unless you replicate it with consensus, it can become a bottleneck for heartbeats and for pushing membership changes to everyone, and it observes the cluster from one vantage point, so a broken link between it and a healthy node causes a wrong verdict. Gossip gives each node constant work, has no leader to lose, and forms opinions from many vantage points. The cost is eventual consistency of the view, so I would use gossip for liveness and soft state and keep critical metadata, like leadership and schema, on a consensus-backed store.

Why does gossip converge in O(log N) rounds? Give the intuition and a number.

In the early phase each informed node infects about one new node per round, so the informed count doubles and half the cluster is informed after about log2 N rounds. In the late phase, the fraction of uninformed nodes shrinks by a constant factor (about e for push with fanout 1) each round, so finishing takes about ln N more rounds. The total is about log2 N + ln N: roughly 17 rounds for 1,000 nodes and about 34 rounds for a million nodes. A thousand times more nodes only doubles the time, which is why it scales. Larger fanout reduces the base of the logarithm, and push-pull shrinks the tail.

Compare push, pull and push-pull gossip.

Push spreads fast at the beginning because informed nodes actively send, but it has a slow tail since the few uninformed nodes are rarely selected as targets. Pull is slow at the beginning because most pulls hit nodes that know nothing new, but it finishes quickly because an uninformed node usually hits an informed one. Push-pull does both in one exchange and is the usual production choice, requiring slightly more bandwidth per exchange but fewer rounds. Anti-entropy versions of these compare full state, while rumor mongering sends only recent updates.

What is the difference between rumor mongering and anti-entropy, and why do real systems use both?

Rumor mongering forwards each fresh update to a few random peers for a limited time. It is fast and cheap but probabilistic, so an update may occasionally die out before reaching everyone. Anti-entropy periodically compares full state between pairs of nodes, so it eventually fixes any difference regardless of what was lost earlier, but each exchange is more expensive, which is why Merkle trees are used to make the comparison cheap. Combining them gives speed in the common case and a guarantee in the worst case. In Cassandra the analogues are hinted handoff and read repair for speed, and scheduled Merkle repair as the safety net.

Explain how SWIM detects failures and why it uses indirect probes and a suspect state.

Each period a node pings one random member. If there is no ack, it asks k other members to ping the target for it, and only if every path fails does it mark the target suspect. Indirect probes give independent network vantage points, so a lost packet on one link, or a problem local to the prober, does not cause a false accusation. The suspect state gives the target time to refute by broadcasting that it is alive with a higher incarnation number, and only after a timeout is it declared dead. Membership changes are piggybacked on the probe messages, so dissemination costs no extra messages. Per-node load stays constant regardless of cluster size.

What is the phi-accrual failure detector and why is it better than a fixed timeout?

It keeps a window of recent heartbeat inter-arrival times for each peer and outputs phi, the negative base-10 logarithm of the probability that a healthy node would be silent for this long. Phi 1 means a 10% chance, phi 8 means one in a hundred million, and phi grows continuously with silence. A fixed timeout is a single number that cannot fit both quiet and jittery links and gives only a binary answer, so it either flaps under load or is too slow on good links. Phi adapts to each link's measured behaviour, and different consumers can use different thresholds. Its weaknesses are that it assumes a reasonable distribution and can still be fooled by long pauses such as garbage collection or frozen VMs.

How do you trade off false positives against detection time?

They move in opposite directions: lowering the timeout or threshold finds real failures faster but wrongly condemns more slow nodes, and raising it does the reverse. I choose by the cost of each error. If a wrong "dead" verdict triggers cheap reversible actions like routing around the node, aggressive detection is fine. If it triggers expensive actions like re-replicating terabytes, I use a high threshold and a suspicion stage. A good practice is to make cheap decisions fast and expensive decisions slow: avoid a suspect node immediately, but start data movement only after it has been down for a long time. Also use multiple observers, as SWIM and Redis Cluster do, to cut false positives without slowing detection.

How does a Merkle tree make replica comparison cheap? What does it cost?

Each leaf hashes a range of keys, each parent hashes its children, and the root summarizes everything, so equal roots mean equal data. If the roots differ, the replicas compare children and descend only into differing subtrees, so the number of hashes exchanged is roughly the tree depth times the number of differences instead of the data size. For a billion rows with one difference, that is about 30 levels and around a kilobyte of hashes. The cost is building the tree, because every row in the range must be read and hashed, which is heavy disk and CPU work, and trees have limited depth so each leaf covers a bucket of rows that must all be compared when it differs. The trees also go stale as writes arrive, so systems use snapshots or incremental updates.

Describe hinted handoff and read repair, and when you still need full repair.

With hinted handoff, when a replica is down during a write, the coordinator saves a hint and replays it when gossip reports the replica is back, so short outages heal fast. Read repair compares replica responses during a read and writes the newest value back to stale replicas, so hot data heals itself. Neither covers all cases: hints expire after a bounded window or can be lost with the coordinator, and read repair never touches data that is not read. Full Merkle-tree repair, run regularly, is therefore needed for cold data, long outages, and to make sure deletion tombstones reach every replica within the retention window.

Where else are Merkle trees used?

Git uses a Merkle DAG so that a commit hash identifies the whole repository state and fetches only transfer missing objects. Bitcoin puts a Merkle root of transactions in each block header, so light clients can verify one transaction with a logarithmic-sized proof. Certificate Transparency logs are append-only Merkle trees with inclusion and consistency proofs. Filesystems such as ZFS checksum blocks in a tree to detect silent corruption, and backup or dedup systems hash chunks to avoid re-uploading and to verify integrity. The shared idea is that a root hash commits to everything below it and a short path of sibling hashes proves membership.

What can go wrong with gossip in production?

Views converge only after several rounds, so nodes briefly disagree about membership. A network partition splits the cluster into two sides that each think the other is dead, and gossip alone does nothing to prevent split brain. Mass failures or reconnect storms can flood the gossip channel and cause more false suspicions, and flapping nodes cause repeated alive/dead transitions and data movement. Version comparisons based on wall-clock time break under clock skew, so systems use per-node counters, generations and incarnation numbers, and need tombstones to stop removed nodes from being resurrected. Mitigations are suspicion stages, bounded messages and jitter, Lifeguard-style local health checks, and keeping critical state on consensus.

Can gossip be used for aggregation or for replicating state?

Yes. Push-sum gossip computes averages, sums and counts: each node splits its (value, weight) pair with a random peer each round, and the ratio at every node converges to the global average in O(log N) rounds, with approximate results that degrade when nodes fail holding mass. Mergeable sketches such as HyperLogLog are even better for distinct counts because merging is idempotent. For replicated state, gossip works best with CRDTs, whose merge operation is commutative, associative and idempotent, so duplicated, reordered or delayed messages do not matter and all replicas converge. For non-mergeable data you need version vectors or timestamps and a conflict resolution rule.

15. Recap

  • Centralized heartbeats create a single point of failure, a bottleneck and a single viewpoint, and all-to-all heartbeats cost N squared messages. Gossip gives each node constant work and many vantage points.
  • Gossip spreads information in O(log N) rounds: about log2 N + ln N for push with fanout 1 (about 17 rounds for 1,000 nodes). Push-pull is fastest overall; rumor mongering is fast but probabilistic, and anti-entropy is the guaranteed safety net.
  • SWIM separates failure detection (ping, then ping-req through k helpers, then suspect) from dissemination (piggybacked on probe messages), with incarnation numbers letting a node refute a false suspicion. Serf, memberlist and Consul use it; Cassandra uses digest-based gossip with phi accrual.
  • Fixed timeouts do not fit variable networks. Phi accrual outputs a continuous suspicion level learned from heartbeat history, and each consumer picks a threshold. The core tradeoff is false positives against detection time, so make cheap decisions fast and expensive ones slow.
  • Membership changes (join, leave, tombstones) and soft metadata travel by gossip, but authoritative topology and schema belong on consensus.
  • Merkle trees compare large replicas by descending only differing subtrees, so cost scales with the number of differences. The price is the scan to build trees, limited depth, and staleness.
  • Repair works in layers: hinted handoff for short outages, read repair for hot data, and scheduled Merkle repair for everything else. Hash trees also underpin git, blockchains, certificate transparency and integrity checking.
  • Gossip can aggregate counts and averages and replicate CRDT state. Pitfalls are convergence delay, partitions, message storms, flapping nodes, clock-based version conflicts and resurrected tombstones.
