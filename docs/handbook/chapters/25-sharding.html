Sharding and Partitioning

When one database machine can no longer hold your data or absorb your writes, you split the data across many machines. This chapter explains how to split it, how to choose the key that decides where each row lives, how requests find the right machine, and what you give up in return: cheap joins, cheap transactions, and simple operations.

1. Why shard, and when not to

A single database server has hard limits. It has a finite amount of disk (a few tens of terabytes is practical for most deployments), a finite amount of memory for caching hot pages, a finite number of CPU cores, and a finite write rate that its disks and its single write-ahead log can sustain. Reads are easy to scale: you add read replicas (see Chapter 24), and each replica holds a full copy and answers queries. But every replica must still apply every write. Adding replicas therefore does nothing for write throughput and does nothing for data size, because each replica holds the whole dataset.

Sharding attacks both limits at once. You divide the dataset into disjoint pieces called shards, and each shard lives on its own set of machines. A write for a given row goes to exactly one shard, so total write capacity grows roughly in proportion to the number of shards. The data on each machine shrinks to a fraction of the whole, so it fits on disk and the hot part fits in memory.

There are two distinct reasons to shard, and it matters which one you have:

  • Data size. The dataset will not fit on one machine, or it fits but backups, restores, index builds, and schema changes take so long that they become operational hazards. A 40 TB single node that takes three days to restore is a risk even if it performs well.
  • Write throughput. A single leader cannot keep up with the write rate. Typical signals are sustained disk utilization near its limit, replication lag growing because followers cannot apply the leader's write stream fast enough, or lock contention on hot tables.
Do not shard early Sharding is one of the most expensive decisions in a system's life. It permanently changes what queries are cheap, removes easy joins and transactions, complicates every migration, and multiplies operational work. Try everything else first: add the right indexes; fix slow queries; add a cache (Chapter 13); move reads to replicas; archive or delete old data; move large blobs to object storage; upgrade to a bigger machine (modern servers offer terabytes of RAM and tens of terabytes of NVMe); split by function (put the orders tables on one database and the user tables on another, which is called vertical partitioning). Shard only when these are exhausted, or when you can compute that they will be exhausted within the planning horizon.

A useful rule of thumb in interviews: if the dataset is under roughly one terabyte and writes are under a few thousand per second, a single well-tuned primary with replicas is almost certainly enough, and saying so shows judgment. If the numbers are in tens of terabytes or hundreds of thousands of writes per second, sharding is justified, and the interesting question becomes how to do it well.

Two more terms matter. The shard key (also called partition key) is the column, or combination of columns, whose value decides which shard a row belongs to. A logical shard is a unit of data placement (for example, bucket number 417), while a physical node is a machine. Good systems have many more logical shards than physical nodes, and move logical shards between machines as needed. That one design choice makes most of the rest of this chapter easier, as section 5 shows.

Key idea Every sharded system answers three questions. (1) How is the data divided into pieces (the partitioning scheme and shard key)? (2) How does a request find the piece that owns a key (the routing layer and mapping)? (3) How do pieces move when load or capacity changes (rebalancing)? The rest of this chapter is these three questions, plus the cost you pay for asking them.

3. Partitioning schemes

The scheme is the rule that turns a shard key value into a shard. The main families are range, hash, a composite of the two, directory lookup, and geography or tenant based. Each is right for some workloads and a trap for others.

3.1 Range partitioning

In range partitioning, you sort the key space and cut it into contiguous ranges, each owned by one shard. For example, with user names as the key, shard 1 owns A to F, shard 2 owns G to M, and so on. With timestamps, each shard owns one day or one month. This is how Bigtable, HBase, and Spanner arrange data, and how MongoDB offers range-based sharding.

The great strength is ordered scans. Because neighbors in key order live next to each other, a query such as "all events between 9:00 and 9:05" or "all users whose name begins with Sm" touches one shard, or a few adjacent ones, and reads them sequentially from disk. Range boundaries can also be chosen by data volume rather than by key space, so a dense part of the key space gets many small ranges and a sparse part gets few large ones.

The great weakness is hotspots with sequential keys. If the key is a timestamp or an auto-increment ID, all new writes have keys larger than every existing key, so they all land in the last range, on one shard. The cluster might have 50 machines, but 49 sit idle while one takes all the inserts. Time-series data and "recent first" access patterns suffer from this unless the key is designed to avoid it (section 4 shows common fixes, such as prefixing the timestamp with a bucket value).

3.2 Hash partitioning

In hash partitioning, you run the key through a hash function and use the result to pick a shard. A good hash function turns similar keys into wildly different numbers, so keys spread evenly over shards no matter how skewed or sequential they were. The sequential-ID hotspot disappears: user 1001, 1002, and 1003 land on three unrelated shards. Cassandra, DynamoDB, and Redis Cluster all hash their keys by default.

The price is lost range queries. Adjacent keys no longer live together, so "all users with ID between 1000 and 2000" must ask every shard. Ordering is destroyed on purpose. If your workload is almost all point lookups by key, this costs nothing; if it needs ordered scans across the shard key, it is a bad fit.

Note that the hash function must be stable across machines and restarts, which rules out the language's built-in randomized string hashing. Systems use fixed functions such as MurmurHash3, xxHash, or MD5 (used for distribution only, not for security).

3.3 Composite and hybrid keys

Many real systems combine the two. A composite key has two parts: the first part is hashed to choose the shard, and the second part sorts the rows within that shard. Cassandra calls them the partition key and clustering columns. DynamoDB calls them the partition key and sort key. For a chat application, use (conversation_id, message_time): all messages of one conversation live on one shard, sorted by time, so "the last 50 messages of this conversation" is a single-shard ordered read, while different conversations spread evenly across the cluster because conversation_id is hashed.

This pattern gives you the best of both worlds along the dimension you care about: even spread across entities, ordered scans within one entity. Its limit is that one entity must fit on one shard and must not be so hot that one shard cannot serve it (section 7).

3.4 Directory (lookup) based sharding

Instead of computing the shard from the key, keep an explicit table, the directory, that records for each key (or each group of keys) which shard owns it. To find user 8841, you look up "user 8841 lives on shard 12". This is the most flexible scheme: you can place any key anywhere, move one big customer to a dedicated machine, and rebalance in tiny steps by updating directory entries.

The cost is that the directory is now critical infrastructure. Every request depends on it, so it must be fast (cached heavily in routers), highly available (replicated, usually in a consensus-backed store), and consistent (a stale entry sends writes to the wrong shard). It can also become large if it has one entry per key; most systems therefore map keys to a modest number of buckets or ranges first, and keep the directory at that coarser level. MongoDB's config servers, Vitess's topology service, and HBase's meta table are all directories of this kind.

3.5 Geographic and tenant based sharding

Sometimes the natural shard key is a business concept. Tenant sharding in a multi-tenant SaaS product puts each customer (tenant) on a particular shard, so all of one customer's data is together, queries never cross tenants, and a noisy or very large customer can be moved to its own shard. Geographic sharding places data in the region where its users are, which cuts latency and can satisfy data residency laws (European users' data stays in Europe). Both are usually implemented as a directory (tenant to shard, region to cluster) rather than a hash.

The danger is skew: tenants differ enormously in size, so one huge tenant can overload its shard while others are nearly empty, and the shard cannot be split further because the shard key is the tenant. Plan an escape hatch, such as the ability to give a giant tenant a sub-key (tenant plus customer ID) so it can be spread over many shards.

4. Choosing the shard key

The shard key is the most consequential decision in a sharded design, because it is very hard to change later (changing it means rewriting and moving all the data). Judge a candidate key against four criteria.

4.1 The four criteria

  1. High cardinality. Cardinality is the number of distinct values. There must be far more distinct key values than shards, ideally millions. A key such as country has maybe 200 values and some of them (one country with a third of your users) are enormous; you cannot spread such data over 500 shards. A boolean or a status field is worse still.
  2. Even distribution of data and of load. Values should be spread so that no shard holds a disproportionate amount of data, and, more importantly, receives a disproportionate share of requests. Distribution of data and of traffic are different things: a user table spread evenly by ID may still have one celebrity account receiving a thousand times the reads.
  3. Query locality. Most queries should include the shard key, so the router can send each to one shard. A query without the key must be broadcast to all shards (scatter-gather, section 9). Choose the key that appears in the filters of your most frequent and most latency-sensitive queries. Also try to keep data that is read or written together on the same shard (all of one user's orders under the user ID), so common transactions stay single-shard.
  4. Immutability. The key value of a row should never change. If it changes, the row must physically move to another shard, which is a delete plus an insert across machines, possibly with a transaction. Keys that users edit (email address, username, city) are poor choices. Use a stable surrogate such as a user ID.

4.3 Common fixes

When the natural key is poor, engineers manufacture a better one. To spread sequential timestamps, prefix the key with a bucket: the key becomes (hash(device_id) mod 16, timestamp), so writes spread over 16 ranges while each device's data stays ordered within its bucket. To avoid a hot entity, append a salt (section 7). To keep related data together while spreading unrelated data, use a composite key such as (user_id, order_id), where user_id chooses the shard. To avoid mutable keys, use an immutable surrogate ID and keep the mutable attribute (email) in a separate lookup structure.

Interview tip State the shard key, then immediately justify it against all four criteria, and name the one query that the choice makes expensive. For example: "Shard orders by customer ID: high cardinality, immutable, and the dominant query is 'orders of this customer'. The price is that 'all orders for product X' becomes scatter-gather, so I will maintain a secondary index or a separate product-keyed table for it."

5. Mapping keys to nodes

Once you have a hash or a range, you still need a rule that says which machine serves it, and a way to change that rule when machines come and go. This is where many naive designs fail.

5.1 Modulo hashing and why it breaks

The first idea everyone has is node = hash(key) mod N, where N is the number of nodes. It is simple, and it spreads keys evenly. It breaks the moment N changes. Suppose you have 4 nodes and add a fifth. A key whose hash is 10 was on node 10 mod 4 = 2, and is now on node 10 mod 5 = 0. In general, going from N to N+1 nodes relocates a fraction N/(N+1) of all keys; from 4 to 5 nodes that is about 80 percent. Nearly the whole dataset must move over the network at once, while the cluster is already under enough load that you wanted to grow it. If caches are involved, nearly every cache entry becomes a miss at once and the database behind them receives the full load.

5.2 A fixed number of partitions

A simple and widely used fix is to separate the two questions. Create a fixed, large number of logical partitions up front (for example 1,024 or 4,096), and map every key to a partition with partition = hash(key) mod 1024. This never changes. Then keep a separate assignment table that says which node hosts which partition. To add a node, you do not rehash anything; you move a few whole partitions from existing nodes to the new one, and update the table. Only the moved partitions' data travels, which is roughly 1/(N+1) of the total, the minimum possible.

This is what Elasticsearch (the number of primary shards fixed at index creation), Couchbase (1,024 vBuckets), Redis Cluster (16,384 hash slots), Kafka (a fixed partition count per topic), and Riak use. The limitation is the word "fixed": the partition count caps your eventual parallelism (you cannot have more nodes than partitions), and picking too few early is painful, while too many adds metadata and per-partition overhead. Choose a count that is a generous multiple of the largest cluster you foresee, such as 10 to 100 partitions per node at the maximum size.

5.3 Consistent hashing with virtual nodes

Consistent hashing is a different answer to the same problem, designed so that changing the number of nodes moves only a small fraction of keys without any central assignment table. (Chapter 57 covers the algorithm and its probabilistic cousins in more depth; this section gives what you need for sharding.)

Imagine the output range of the hash function bent into a circle, the ring, so that the largest value wraps around to the smallest. Hash each node's name onto the ring to give it a position. To place a key, hash the key onto the same ring and walk clockwise until you meet a node; that node owns the key. Each node therefore owns the arc of the ring between its predecessor and itself.

Now see what happens when the cluster changes. If a node is added, it lands at one point on the ring and takes over only the arc between its predecessor and itself, keys that previously belonged to its clockwise neighbor. Every other key stays exactly where it was. If a node is removed, only the keys it owned move, all to its clockwise neighbor. On average only about 1/N of the keys move, instead of nearly all.

With only a few nodes, though, random positions give uneven arcs: one node might own 40 percent of the ring and another 8 percent. The standard remedy is virtual nodes (vnodes). Each physical node is hashed onto the ring many times (commonly 64 to 256 positions, under names like nodeA#1, nodeA#2, and so on). Each node now owns many small, scattered arcs, and by the law of large numbers its total share is close to the average. Vnodes also help with removal: when a node leaves, its many small arcs pass to many different neighbors, so the extra load is shared rather than dumped on one machine (which could otherwise overload it and cause a cascading failure). You can give a bigger machine more vnodes to make it take a proportionally larger share.

5.4 Rendezvous hashing

Rendezvous hashing (highest random weight) reaches the same goal with no ring. For a given key, compute a score hash(key, node) for every node, and pick the node with the highest score. Every client computes the same answer, with no shared state besides the list of nodes. When a node is removed, only keys whose top score was that node move, and each moves to its own second-best node, so the redistribution is spread evenly over the survivors. Adding a node steals exactly those keys for which the new node scores highest, about 1/(N+1) of them.

It is simple to implement and gives naturally even balance without virtual nodes; it also generalizes to picking the top k nodes, which is handy for replica placement. Its drawback is cost: one lookup computes N hashes, so it is O(N) per key, where a ring lookup is a binary search (O(log N)). For clusters of tens to a few hundred nodes this is fine, and it is common in load balancers and caches.

6. Rebalancing and online resharding

Data grows, traffic shifts, machines fail, and new machines are added. Rebalancing is the process of moving data between shards so that load and storage stay even. A good rebalancing process meets three requirements: the system keeps serving reads and writes during the move; only the necessary data moves; and the move can be throttled so it does not starve live traffic of disk and network.

6.1 Strategies

  • Move whole fixed partitions. With the fixed-partition scheme of section 5.2, adding a node means picking some partitions from the busiest nodes and copying them to the new node. The partition boundaries never change; only the assignment table does. This is the simplest and most robust method, and the one to propose by default.
  • Split and merge ranges dynamically. In range-partitioned stores (HBase, Bigtable, CockroachDB, TiKV, MongoDB), a range that grows past a size threshold (for example, a few hundred megabytes up to several gigabytes) is split in two at a median key. Two small neighboring ranges can be merged. After a split, one of the halves can be moved to a less loaded node. This adapts to skew automatically, because dense regions of the key space split into many small ranges. Some systems also split on load (requests per second), not only size, so a hot but small range is divided too.
  • Add nodes with vnodes. In consistent hashing systems the new node takes over many small arcs, streaming each from its previous owner.
  • Automatic versus manual. Fully automatic rebalancing is convenient but dangerous: moving terabytes while the cluster is already strained (for example, because a node looked slow and was declared dead) can turn a small incident into an outage. Many systems keep a human in the loop, or at least require a person to approve a plan, or throttle moves heavily.

6.2 The online resharding procedure

The hardest case is changing the scheme itself on a live system, for example going from 8 shards to 32, or moving a table from an unsharded database into a sharded one. The standard approach is a staged, reversible migration, similar to the one the migrations chapter describes in general. Vitess's MoveTables and Reshard workflows, and MongoDB's resharding, follow this shape.

  1. Provision the target shards. Create the new, empty shards (and their replicas) with the new topology.
  2. Copy a snapshot. Take a consistent snapshot of the source data and bulk-copy it to the targets, applying the new routing function to decide which target gets each row. The source keeps taking live writes.
  3. Stream changes. Capture every change made on the source since the snapshot (from its replication log or change data capture stream) and apply them continuously on the targets. This is the catch-up phase; the lag shrinks until it is a second or less. An alternative is the double-write approach, in which the application writes to both old and new locations; it is simpler to explain but riskier, because a failure between the two writes leaves them inconsistent, and the writer must handle that.
  4. Verify. Compare row counts and checksums between source and target, ideally while changes are still flowing. Run shadow reads: read from both, compare results, and report differences without affecting users.
  5. Cut over. Briefly pause or fence writes on the source (typically seconds), let the last changes drain, then flip routing so reads and writes go to the targets. The routing flip is a single metadata change, which is why a directory or topology service makes this clean.
  6. Keep a way back. For a while, replicate changes in the reverse direction (target to source) so you can switch back if something is wrong. Only after a soak period do you drop the old data.
Watch out Rebalancing competes with production traffic for disk, network, and CPU. Throttle the copy rate, schedule heavy moves off-peak, and watch latency percentiles during the move. Also watch for rebalancing during an incident: if a node is only slow, not dead, treating it as failed and re-copying its data can double the pain.

7. Hot partitions, hot keys, and the celebrity problem

Even with a perfect hash, load is not uniform. Some keys are simply more popular: a celebrity's profile, a viral post, a flash-sale product, the tenant with ten thousand employees. A hot key is a single key that receives a disproportionate share of traffic. A hot partition is the shard that owns it (or that owns many moderately hot keys together). Because one key lives on one shard, adding more shards does not help: the hot key is still on one machine, and that machine's capacity is the ceiling for that key.

Hot keys are especially insidious because average utilization looks healthy. A cluster at 20 percent average load can still have one shard at 100 percent, throttling or failing requests for everyone who happens to share it. DynamoDB, for example, notes that its partitions have per-partition throughput limits, so a hot key can be throttled even when the table has plenty of provisioned capacity overall.

7.1 Reads: cache and replicate

For hot reads, the cheapest remedy is a cache in front of the shard (Chapter 14 discusses hot-key handling in caches). A small in-process cache on each application server, with a short TTL such as a few seconds, can absorb nearly all reads of one popular item. Adding extra read replicas of just the hot shard, or replicating hot keys to several nodes and choosing one at random on each read, also spreads load.

7.2 Writes: salting and splitting

Writes cannot be cached, so the key itself must be split. Key salting appends a small random or computed suffix, so one logical key becomes several physical keys. A counter for a viral post, likes:post42, becomes likes:post42#0 through likes:post42#9. A write picks a random suffix and increments that sub-counter; ten shards now share the write load. A read must fan in: read all ten sub-counters and add them. You trade a more expensive read for a scalable write. Choose the number of salt buckets according to the write rate, and ideally apply salting only to keys known to be hot (a small list, or detected dynamically), so that ordinary keys keep cheap single-key reads.

The same idea applies when a whole entity is hot: give a large tenant a composite key (tenant, sub-bucket) so its data spreads across many shards, and accept that tenant-wide queries become scatter-gather for that tenant only.

7.3 The celebrity problem

In a social network, a user with 50 million followers posts. If the design fans out on write (copy the post into each follower's timeline), one post triggers 50 million writes, an enormous burst that also hits the shards of all those followers. If it fans out on read (each follower's timeline fetches posts from everyone they follow at read time), then the celebrity's post table is read by tens of millions of timelines and becomes a hot key. The usual compromise is hybrid: fan out on write for ordinary users, and for celebrities skip the write fan-out and merge their posts into followers' timelines at read time, served from a heavily cached, replicated copy. This is a recurring pattern in feed design, covered in the case studies.

8. Secondary indexes in a sharded store

A primary-key lookup is easy: hash the key, go to one shard. But applications also search by other attributes: "find the user with this email", "all orders with status = shipped", "all products in category = shoes". These need secondary indexes, and in a sharded store there are two ways to build them, with opposite trade-offs.

8.1 Local (document-partitioned) indexes

In a local index, every shard indexes only its own rows. When you insert a row, the shard that owns it updates its own index, with no cross-shard work. Writes stay fast and single-shard. But a query on the indexed attribute cannot know which shards hold matches, because matching rows can be anywhere. The router must send the query to every shard and merge the results. This is called scatter-gather. Cassandra's secondary indexes, MongoDB's per-shard indexes, and Elasticsearch work this way.

8.2 Global (term-partitioned) indexes

In a global index, the index itself is sharded, but by the indexed value, independently of how the base data is sharded. The index entries for email = "ana@example.com" live on whichever index shard owns that value, and point to the primary key of the row, wherever it is. A lookup by email goes to exactly one index shard and then one data shard: two hops, no broadcast. Reads are efficient. But a write to a row must now update index entries on other shards (one for each indexed attribute), so a single logical write touches several shards, and keeping them consistent either needs a distributed transaction or accepts that the index is updated asynchronously and may briefly lag behind the data. DynamoDB's global secondary indexes work this way, and are eventually consistent with the base table.

A third approach, common when you only need one extra access path, is to keep a separate lookup table sharded by the other attribute (for example, email_to_user_id sharded by email). This is a hand-built global index, and Vitess formalizes it as a lookup vindex. You must update it yourself, for instance in the same transaction or via an outbox (Chapter 31).

Key idea Scatter-gather latency is governed by the slowest shard, not the average. With 100 shards each having a 1 percent chance of being slow on a given request, about 63 percent of scatter-gather queries will hit at least one slow shard (1 - 0.99^100). Fan-out to many shards multiplies tail latency, which is why query design avoids it on the hot path.

9. Cross-shard queries, joins, and transactions

9.1 Queries and aggregations

A query that includes the shard key goes to one shard. A query that does not is a scatter-gather: the router (or coordinator) sends the query to all or many shards in parallel, then merges. Merging is straightforward for filters, harder for ordering and limits (to get the global top 10 sorted by price, each shard must return its own top 10, and the coordinator picks the best 10 from those), and tricky for aggregates (an average needs each shard's sum and count, not each shard's average). Deep pagination is expensive: page 1,000 with offset requires every shard to return 1,000 times the page size. Use keyset pagination (Chapter 5) to avoid it.

9.2 Joins

A join between two tables is cheap only if matching rows are on the same shard. The usual remedies are:

  • Co-locate related tables by giving them the same shard key. Orders and order items both shard by customer ID, so a customer's join stays on one shard. Vitess and Citus call the tables co-located or in the same sharding group.
  • Replicate small reference tables to every shard (countries, currencies, product categories). Each shard joins against its local copy. Citus calls these reference tables.
  • Join in the application. Fetch from one table, collect IDs, and query the other in a batch. This is the common choice in practice, and works well when you can tolerate two round trips.
  • Denormalize. Store the joined data redundantly in the row you read most, accepting the update work (Chapter 17).
  • Push analytics elsewhere. Heavy cross-shard joins and aggregates usually belong in a warehouse or a search index fed by change events, not in the serving path.

9.3 Transactions across shards

Within one shard, you get the database's normal ACID transactions. A transaction that updates rows on two shards needs an atomic commit across machines, most commonly two-phase commit (2PC): a coordinator asks every participant to prepare, and only if all vote yes tells them to commit. This works, and Spanner, CockroachDB, and Vitess (optionally) provide it, but it is slower (extra round trips, locks held across them) and has a blocking failure mode if the coordinator dies between phases. Chapter 31 covers 2PC, sagas, and the outbox pattern in detail.

The design discipline is therefore: choose the shard key so that your most important transactions stay within one shard. Put a user's account, balance, and ledger entries under the same key. For the rare unavoidable cross-shard operation, such as a transfer between two users on different shards, prefer a saga (a sequence of local transactions with compensating actions) or the transfer pattern with a pending state, over distributed locking.

10. Unique IDs across shards

A single database hands out IDs with an auto-increment counter. Once the data is split, each shard has its own counter and the values collide: shard 1 and shard 2 both create "order 1001". There are several ways to generate IDs that are unique across the whole cluster. Chapter 32 compares them fully; the sharding-relevant summary is:

  • Interleaved counters. Shard k of N hands out k, k+N, k+2N, and so on. Unique and simple, but it hard-codes N, so adding shards breaks the pattern.
  • Random UUIDs (version 4). No coordination, practically collision-free, but 128 bits long, unordered, and when used as a key in a B-tree index they scatter inserts across the index, hurting cache locality.
  • Time-ordered IDs such as Snowflake, ULID, or UUIDv7. A Snowflake-style 64-bit ID packs a timestamp, a machine or shard number, and a per-millisecond sequence. IDs are unique without coordination, roughly sorted by creation time (good for index locality and for "newest first"), and compact. They require unique machine numbers and sane clocks.
  • A ticket server or ID service that hands out ranges. Centralized, so it needs its own replication and is a possible bottleneck, but ranges can be cached by clients in blocks.

An important interaction: if an ID will also be the shard key under range partitioning, a time-ordered ID reproduces the sequential-hotspot problem of section 3.1. Either hash it for placement or put a bucket prefix in front. Some designs embed the shard number inside the ID (as Instagram's ID scheme does with a logical shard number), so the router can find the shard from the ID alone, without any lookup.

11. The routing layer

Clients should not need to know the cluster layout, yet each request must reach the right shard. The component that does the mapping is the routing layer. It needs access to the current mapping (the ring, partition assignment, or directory) and must keep up as the mapping changes. There are three common arrangements.

11.1 Client-side routing

The client library holds the mapping and sends each request straight to the owning node. This is the fastest design, with no extra hop. Cassandra drivers (which learn the token ring from the cluster) and the Redis Cluster clients (which cache the slot table and follow MOVED redirections when it is stale) work this way. The cost is that every client language needs a smart library, and a stale mapping must be handled gracefully. Rolling out routing changes means upgrading every client.

11.2 Proxy routing

Clients talk to a stateless proxy tier that speaks the database protocol and forwards each query to the right shard. Applications stay simple, any standard driver works, and the proxy can also pool connections, enforce limits, and rewrite queries. Examples are Vitess's vtgate, MongoDB's mongos, and ProxySQL-based setups. The cost is an extra network hop and another tier to run and scale (though it is stateless, so it scales horizontally behind a load balancer, Chapter 9).

11.3 Coordinator-style routing

Any node in the cluster can receive a request and acts as the coordinator for it: it knows the mapping and forwards the request to the owning replicas. Cassandra and DynamoDB-style systems behave this way. Clients can connect to any node, which removes a dedicated proxy tier, at the cost of an extra internal hop when the contacted node does not own the data.

In all three, the authoritative mapping lives in a small, strongly consistent store. MongoDB keeps it on config servers; Vitess in a topology service backed by etcd or ZooKeeper; HBase in a meta table; Kafka in the controller. Routers cache it and refresh on change or when they get a "wrong shard" error. The mapping store must be highly available, but because it is read mostly through caches, it is not on the per-request critical path.

12. High availability of each shard

Sharding multiplies the number of things that can fail. If a single database is down with probability p, and you have 100 shards that each must be up for the whole system to be fully working, the chance that some shard is down at any moment is far higher. A shard with no redundancy is therefore a single point of failure for a slice of your data, and the outage looks to the user like "my account is missing".

Every shard should be its own replica group: a leader plus followers, or a quorum group, as Chapter 24 describes. If the leader fails, a follower is promoted. Systems differ in how they do this. MongoDB shards are replica sets with automatic election. Vitess shards are a primary and replicas managed by an orchestrator. CockroachDB, TiKV, and Spanner run a consensus group (Raft or Paxos) per range, so each range has its own leader and loses no committed data if one replica dies. Cassandra and DynamoDB replicate each partition to several nodes (commonly three) in leaderless fashion with tunable quorums.

Spread the replicas across failure domains (racks, availability zones) so one failure does not remove the whole group. The effect is that a node loss degrades one shard's redundancy for a short time, but never makes data unavailable. When you size the cluster, remember to multiply: 20 shards with 3 replicas each are 60 machines, and the capacity plan must include them.

15. Worked example: sharding 50 TB and 200k writes per second

The problem. A messaging product stores 50 TB of message data, growing about 5 percent a month, and receives 200,000 writes per second at peak. Reads are about five times the writes, 1 million per second, mostly "the latest messages of a conversation". We must decide whether and how to shard.

15.1 Do we need to shard?

One primary cannot absorb 200,000 durable writes per second of typical row size on a single set of disks; a tuned database might manage a few tens of thousands. And 50 TB exceeds comfortable single-node limits (restore time and index size). Replicas do not help with either. Caching helps the reads but not the writes. So yes, sharding is justified.

15.2 Sizing the shard count

  • By data. Aim for 500 GB to 1 TB per shard, which keeps backups, restores, and moves manageable. 50 TB ÷ 0.5 TB gives about 100 shards today; 5 percent monthly growth is about 80 percent a year, so a year ahead needs about 90 TB, or about 180 shards at 0.5 TB each.
  • By writes. Assume a shard sustains roughly 5,000 writes per second with comfortable latency, including index maintenance. At 200,000 per second that needs 40 shards; with 50 percent headroom for peaks and skew, about 80.
  • Take the larger. The data dimension dominates: about 100 shards now. To avoid resharding every year, create 1,024 logical partitions (section 5.2), initially placed about ten to a node on 100 nodes, so growth means moving whole partitions to new nodes with no key remapping.
  • Replication. Three replicas per shard for availability across zones: 100 × 3 = 300 machines for the data tier, and raw storage of 150 TB.

15.3 Choosing the key

The dominant query is "latest messages in conversation C". Use the composite key (conversation_id, message_time): hash conversation_id to a logical partition and sort by time within it. Check against the criteria: cardinality is hundreds of millions of conversations (high); distribution is even across conversations; query locality is perfect for the main query because one conversation lives in one partition and is already time-ordered; conversation_id is immutable. A candidate such as user_id would split a conversation's messages across two users' shards, forcing cross-shard reads, and message_time alone would create a hot tail shard.

15.4 Problems and answers

  • Giant group chats. A conversation with a million members is a hot key. Bucket its messages: partition key (conversation_id, day), so each day spreads and old days can move to cold storage. If a single conversation's write rate still exceeds one shard, add a salt suffix and merge on read.
  • "All conversations of a user." This is not keyed by conversation. Keep a second table, user_conversations, sharded by user_id, updated when a message is sent (a global-index style structure maintained asynchronously through an outbox, Chapter 31). It is allowed to lag by a second.
  • Message IDs. Use time-ordered 64-bit Snowflake-style IDs (Chapter 32) so IDs are unique across shards and roughly sorted.
  • Search. Full-text search over messages goes to a search index fed by change events (Chapter 22), not scatter-gather on the primary store.
  • Routing. A stateless proxy tier with a cached copy of the partition-to-node table; the table lives in a consensus store.
  • Growth. At 80 percent yearly growth, add nodes about every two months, each time moving a few dozen partitions with throttled copy; no application change.

16. Interview Q&A

When should you shard, and what would you try first?

Shard when data size or write throughput exceeds what one primary can handle and cheaper options have run out. Before that I would fix queries and indexes, add caching, move reads to replicas, archive old data, move blobs to object storage, split by function, and consider a larger machine. Sharding permanently complicates joins, transactions, and operations, so I treat it as a last resort justified by numbers, such as tens of terabytes or hundreds of thousands of writes per second.

What is the difference between replication and sharding?

Replication keeps full copies of the same data on several machines, which improves availability and read capacity but not data size or write capacity, because each replica applies every write. Sharding divides the data so each machine holds a different part, which scales size and writes. Real systems use both: each shard is replicated. Saying this in one breath shows you understand they are complementary rather than alternatives.

Compare range and hash partitioning.

Range partitioning keeps keys in sorted order across shards, so range scans are cheap, but sequential keys such as timestamps create a hot last shard. Hash partitioning spreads keys evenly regardless of pattern, which removes that hotspot, but adjacent keys scatter so range queries must visit every shard. A composite key combines them: hash the first part to pick the shard, and sort by the second part within it, giving even spread across entities and ordered scans within one entity.

How do you choose a shard key?

I check four things: high cardinality so there are many more values than shards; even distribution of both data and traffic; query locality, meaning the common queries include the key so they hit one shard; and immutability so rows never need to move. I then name the query the choice makes expensive. For orders, customer ID usually fits; order date or status do not, because they are low cardinality, hot, or mutable.

Why does hash(key) mod N fail when you add a node, and what do you use instead?

Changing N changes the result for most keys: going from 4 to 5 nodes remaps about 80 percent of them, forcing a massive data move and, with caches, a flood of misses. Better options are a fixed number of logical partitions with an assignment table, where adding a node moves whole partitions, or consistent hashing with virtual nodes, where a new node takes only about 1/(N+1) of the keys from its ring neighbors. Rendezvous hashing offers a similar guarantee without a ring.

What are virtual nodes and why use them?

Instead of one point on the hash ring per machine, each machine is placed at many points. With few random points the arcs would be uneven, so some machines would own much more than others. With many virtual nodes each machine's total share approaches the average, and when a machine leaves its many small arcs pass to many different neighbors, so no single machine inherits the whole load. They also let you weight machines by capacity by giving bigger ones more points.

How do you handle a hot key such as a celebrity account?

For reads, cache the hot item close to the application with a short TTL and add replicas of the hot shard. For writes, which cannot be cached, split the key: add a salt suffix so one logical counter becomes several physical keys on different shards, and sum them on read. For feeds, mix push and pull: precompute timelines for normal users, but merge celebrity posts at read time. I also detect hot keys automatically so salting applies only to those.

Explain local versus global secondary indexes.

A local index covers only the rows on its own shard, so writes are cheap, but a query by that attribute must scatter to every shard and its latency is that of the slowest one. A global index is sharded by the indexed value, so a lookup goes to one index shard and then one data shard, but each write also updates index shards elsewhere, which makes writes costlier and often asynchronous and eventually consistent. I pick global when selective lookups by that attribute are frequent, and local when they are rare.

How do you perform joins and transactions across shards?

I try to avoid them by design: co-locate tables that are joined by giving them the same shard key, replicate small reference tables to every shard, and keep each key-scoped transaction inside one shard. When a join must cross shards, I do it in the application with batched lookups, or move that workload to a warehouse. For unavoidable cross-shard writes I use a saga with compensating steps, or two-phase commit where strict atomicity is required, accepting the latency and blocking risks.

How would you reshard a live system with no downtime?

Create the new shards, copy a consistent snapshot, and stream ongoing changes from the old shards until lag is near zero. Verify with counts, checksums, and shadow reads. Then briefly fence writes, drain the last changes, and flip the routing metadata in one step. I keep reverse replication running for a soak period so I can roll back, and only then drop the old data. Throughout, the copy is throttled so it does not harm live traffic.

How do you generate unique IDs when data is spread over many shards?

Per-shard auto-increment values collide, so I use a scheme that needs no coordination. A Snowflake-style 64-bit ID combines a timestamp, a machine or shard number, and a sequence, giving globally unique, roughly time-ordered, compact IDs. UUIDs also work but are larger and unordered. If the ID is also the range-partitioning key I hash it or add a bucket prefix, so time-ordered IDs do not create a hot last shard.

17. Recap

  • Shard for data size or write throughput only after caching, replicas, indexing, archiving, and bigger machines are exhausted. Replication scales reads and availability; sharding scales size and writes. Use both.
  • Range partitioning gives ordered scans but hotspots with sequential keys; hash partitioning gives even spread but no range scans; composite keys hash the entity and sort within it; directories give full flexibility at the cost of a critical lookup service.
  • A good shard key has high cardinality, even load, query locality, and immutability. Name the query it makes expensive.
  • Never use hash mod N for a changing cluster. Use fixed logical partitions with an assignment table, consistent hashing with virtual nodes, or rendezvous hashing, so adding a node moves only about 1/(N+1) of the keys.
  • Rebalance by moving whole partitions or splitting ranges, throttled. Reshard online with snapshot, change streaming, verification, one-step cutover, and a rollback path.
  • Hot keys defeat even hashing: cache reads, salt writes, treat celebrities specially, and give large tenants their own space.
  • Secondary indexes are local (cheap writes, scatter-gather reads) or global (cheap reads, multi-shard writes). Avoid cross-shard joins and transactions by co-locating related data; use sagas or 2PC when unavoidable.
  • Use coordination-free unique IDs, route via client, proxy, or coordinator with an authoritative mapping store, and replicate every shard for availability.
