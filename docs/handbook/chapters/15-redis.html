Redis Deep Dive

Redis is an in-memory data structure server: a very fast single process that keeps strings, hashes, lists, sets, sorted sets and more in RAM and lets many clients manipulate them with atomic commands. This chapter explains why it is fast, what each data structure is really made of, how it survives restarts and failures, how it scales with replication, Sentinel and Cluster, and where it hurts in production.

1. What Redis is, and when to use it

Redis (REmote DIctionary Server) is a server program that stores data in memory and answers commands over a simple text-based network protocol called RESP. Unlike a plain cache that only maps a key to an opaque blob, Redis understands the shape of the value. A value can be a counter, a list you can push to and pop from, a set with membership tests, or a sorted set ordered by a score. You do not fetch the whole value, change it in your application, and write it back. You send a small command such as "add 1 to this counter" or "add this member to that sorted set", and Redis performs the change itself, atomically, close to the data.

That one design choice, moving the operation to the data instead of moving the data to the operation, is why Redis is useful far beyond caching. It saves network round trips, it removes whole classes of read-modify-write race conditions, and it lets you build leaderboards, rate limiters, queues and session stores from a few cheap commands.

1.1 What it is not

Redis is primarily a memory-resident store. The entire dataset must fit in the RAM of the machine (or, with clustering, in the combined RAM of the shards). RAM costs roughly one to two orders of magnitude more per gigabyte than SSD, so Redis is the wrong place for terabytes of cold data. It is also not a relational database: there are no joins, no ad hoc queries over arbitrary fields, and no multi-statement transactions with rollback. Persistence exists, but its guarantees are weaker than those of a database built around a write-ahead log and fsync on every commit, unless you configure it carefully and accept the cost.

2. Why Redis is fast

A single Redis instance routinely serves 100,000 or more simple operations per second on one CPU core, with typical latencies well under a millisecond on a local network. There is no single trick behind this. Several design decisions stack up.

2.1 Everything lives in memory

A read from RAM takes on the order of 100 nanoseconds. A random read from an SSD takes tens to hundreds of microseconds, and from a spinning disk several milliseconds. Redis never has to go to disk to answer a command, so the dominant cost per command is not storage at all. It is parsing the request, running a short piece of CPU code, and sending the reply over the network.

2.2 Single-threaded command execution

Redis executes commands on one main thread, one at a time. This sounds like a limitation, but it removes enormous overhead and complexity. There are no locks around data structures, no mutexes to contend on, no cache-line ping-pong between cores, and no context switching in the hot path. Because only one command runs at a time, every command is automatically atomic: no other client can see the data half-modified. That is the property that makes INCR, LPUSH, ZADD and Lua scripts safe without any extra coordination.

The price is that one slow command blocks everyone. If one client runs an O(N) command over a million elements, taking 200 ms, then every other client waits 200 ms. This is the root cause of most Redis production incidents and is why section 4 spends time on command complexity.

2.3 The event loop and I/O multiplexing

One thread can serve tens of thousands of connections because it never blocks waiting on a single client. Redis uses an event loop built on the operating system's readiness notification facility (epoll on Linux, kqueue on BSD and macOS). The loop asks the kernel "which of my sockets have data ready to read or room to write?", receives a list, and handles each ready socket in turn: read the request bytes, parse the command, execute it against memory, and queue the reply. Then it asks again. Between those steps it also runs timers for housekeeping such as expiring keys and checking replication.

2.4 I/O threads

As networks got faster, a measurable share of the main thread's time went to the system calls that read and write sockets, not to running commands. Starting with Redis 6, you can enable I/O threads (the io-threads setting). These helper threads take over reading requests from sockets, parsing them, and writing replies back, while the main thread still executes every command serially. This keeps the atomicity guarantee and lock-free data structures, and it can raise throughput substantially (often up to about 2x in network-heavy workloads) on multi-core machines. It is off by default, and it helps only when the main thread is saturated by network handling. Newer releases (Redis 8) improved this threading further. If your commands themselves are expensive (big sorted sets, Lua), I/O threads do not help, because the bottleneck is command execution.

Redis also does other work in separate threads or processes: lazy freeing of large objects (so UNLINK does not stall), the fsync of the append-only file, and forked child processes for snapshots. Those are background tasks, not command execution.

2.5 Efficient data structures and encodings

Redis chooses a compact internal encoding for small values and switches to a more scalable one as they grow. A small hash is stored as one contiguous array of bytes (a listpack), which is cache-friendly and has almost no per-entry overhead. When it grows past a threshold it is converted to a real hash table. You see the details in section 3. The effect is that millions of small objects cost much less memory than naive pointer-based structures, and CPU caches work better.

2.6 Pipelining and a lean protocol

RESP is trivial to parse. And because it is request and response over a stream, a client can send many commands without waiting for replies (pipelining), paying one network round trip for hundreds of commands. On a 0.5 ms round-trip network, 1,000 sequential commands take about 500 ms of pure waiting. The same 1,000 commands pipelined take roughly one round trip plus server time, which is a few milliseconds. For this reason, in practice network round trips, not Redis CPU, are usually the bottleneck.

Interview tip A strong answer to "why is Redis fast if it is single-threaded?" has four parts: data in RAM, no lock contention because one thread runs commands, an epoll event loop that multiplexes thousands of sockets, and compact encodings. Then mention that I/O threads exist only to offload network handling, and that single-threaded execution means a slow command blocks everyone.

3. Data structures, internals, and use cases

Every key in Redis maps to a value of one type. The keyspace itself is a big hash table (called the dictionary) that maps key names to value objects. Each value object records its type and its current encoding. The table below is the map for this section, and the following subsections explain each type.

3.1 Strings

The string is the basic type, and it is binary safe: it can hold text, a JSON document, a serialized protobuf, or an image, up to 512 MB. Internally there are three encodings. If the string is an integer that fits in a 64-bit signed number, Redis stores it as a plain number (int), which is what makes INCR cheap. Short strings (up to 44 bytes) use embstr, where the object header and bytes live in one memory allocation. Longer strings use raw with a separately allocated buffer.

Commands: GET, SET (with EX, PX, NX, XX options), MGET, INCR, INCRBY, APPEND, GETSET/GETDEL. Use cases: cache entries, counters, flags, and locks. A caution about big strings: reading or writing a 100 MB string blocks the main thread while it is copied and sent.

3.2 Hashes

A hash is a map from field names to values under one key, like a small row or object. It lets you update one field (HSET user:42 email a@b.com) without rewriting the whole object, and read selected fields with HMGET. Small hashes (by default up to 128 fields, each value up to 64 bytes, set by hash-max-listpack-entries and hash-max-listpack-value) are stored as a listpack: a single compact byte array of field, value, field, value. Lookups scan the array linearly, which is fast because it is tiny and contiguous. Beyond the limits it converts to a hash table with O(1) average lookups.

A well-known memory trick follows: storing many small objects as fields inside a modest number of listpack-encoded hashes (for example bucketing IDs) uses far less memory than one top-level key per object, because each top-level key carries overhead for the dictionary entry, key string and value object header (often 50 to 100 bytes). Redis 7.4 also added per-field expiry for hashes, but do not rely on that on older versions.

3.3 Lists

A list is an ordered sequence of strings with fast push and pop at both ends (LPUSH, RPUSH, LPOP, RPOP) in O(1). Internally it is a quicklist: a doubly linked list whose nodes are small listpacks. This combines the cheap end operations of a linked list with the memory efficiency of arrays. Access by index (LINDEX, LRANGE) walks nodes, so it is O(N) in the distance from the nearest end. Blocking variants (BLPOP, BRPOP, BLMOVE) make a list into a simple work queue: a consumer waits until an item arrives. Use cases: simple job queues, a capped "latest 100 events" feed (LPUSH then LTRIM 0 99).

3.4 Sets

A set is an unordered collection of unique strings, with O(1) add, remove, and membership test (SADD, SREM, SISMEMBER). If all members are integers and the set is small, Redis uses an intset, a sorted array of integers; small sets of strings can use a listpack; otherwise a hash table. Set algebra is built in: SINTER, SUNION, SDIFF compute intersections, unions, differences (cost grows with the sizes of the sets, so be careful with big ones). SRANDMEMBER and SPOP give random picks. Use cases: unique visitors for small cardinalities, tags, "who liked this" with common-friends via intersection, and a random-draw raffle.

3.5 Sorted sets and the skip list

A sorted set (ZSET) is a set where each member has a floating-point score, and members are kept ordered by score (ties by member name). It supports adding or updating (ZADD), rank lookups (ZRANK), and range queries by rank or score (ZRANGE, ZRANGEBYSCORE, ZREVRANGE). This is the structure behind leaderboards and many scheduling designs.

The trick is how it supports both "find this member's score in O(1)" and "walk members in score order in O(log N)". Large sorted sets are stored as two structures sharing the same data. A hash table maps member to score, giving O(1) score lookup. A skip list keeps members ordered by score.

A skip list is a linked list with express lanes. The bottom level is an ordinary sorted linked list of every element. A random subset of elements (each element is promoted to the next level with probability 1/4 in Redis) also appears in a second, sparser linked list above it, a smaller subset appears above that, and so on. To search, start at the top level, move right while the next element is not past your target, and drop down a level when it would overshoot. On average this takes O(log N) steps, like a balanced tree, but it is simpler to code than rebalancing trees, and range scans are easy: find the start, then walk right along the bottom level. Redis also stores a span on each link (how many bottom-level nodes it jumps), so it can compute the rank of an element in O(log N) while descending.

Costs: ZADD and ZREM are O(log N); ZRANGE is O(log N + M) where M is the number of elements returned; ZSCORE is O(1); ZCARD is O(1). Small sorted sets (by default up to 128 entries) use a listpack instead. Use cases: leaderboards (score is points), rate limiting sliding windows (score is timestamp), delay queues (score is the run-at time, poll with ZRANGEBYSCORE up to "now"), and autocomplete over lexicographic ranges using equal scores.

3.6 Bitmaps

A bitmap is not a separate type. It is a string treated as an array of bits: SETBIT key offset 1, GETBIT, BITCOUNT (population count), BITOP AND/OR/XOR, and BITPOS. One bit per user ID means 100 million users fit in 12.5 MB. A classic use is daily activity: key active:2026-11-17, bit userId set when the user was seen. BITCOUNT yields daily active users, and BITOP AND across seven day-keys yields users active all week. The caveat: the string must grow to hold the highest offset, so a sparse ID such as 4 billion allocates 512 MB at the first write. Use dense IDs or shard the bitmap by ID range.

3.7 HyperLogLog

A HyperLogLog (HLL) estimates the number of distinct elements in a stream using a fixed, tiny amount of memory, about 12 KB per key regardless of whether you have a thousand or a billion elements, with a standard error of about 0.81 percent. You add items with PFADD, read the estimate with PFCOUNT, and merge several with PFMERGE. It works by hashing each item and tracking, in each of 16,384 registers, the longest run of leading zero bits seen; rare long runs imply many distinct items. The cost is that you cannot list members or remove one. Use it for "unique visitors per page per day" when approximate is fine. Chapter 57 covers the algorithm in depth (Chapter 57).

3.8 Streams

A stream (Redis 5) is an append-only log of entries, each with an auto-generated ID of the form millisecondTime-sequence and a set of field-value pairs. Internally it is a radix tree whose nodes hold listpacks of entries, so appends and range reads by ID are efficient. XADD appends, XRANGE and XREAD read, and XTRIM caps length. The important feature is consumer groups: several consumers cooperate on one stream. XREADGROUP delivers each entry to exactly one consumer in the group, tracks it in a pending entries list until the consumer calls XACK, and lets another consumer take over abandoned entries with XAUTOCLAIM (or XCLAIM) after a timeout. That gives at-least-once delivery with retry, which a plain list cannot. Streams are much lighter than Kafka (Chapter 34), with no partitioning across nodes for one stream, all data in memory, and weaker durability, but they are a good fit for moderate-volume event pipelines.

3.9 Geospatial indexes

Geo commands (GEOADD, GEODIST, GEOSEARCH) are built on top of a sorted set. Each longitude and latitude pair is converted to a 52-bit geohash, an integer that interleaves the bits of both coordinates so that nearby points get numerically close values, and that integer is the member's score. A radius or box query then becomes a handful of score range scans over the neighbouring geohash cells, followed by an exact distance filter. Use it for "drivers within 2 km". The limits: it is a single key, so one sorted set holds all points and cannot be spread across cluster shards unless you partition it yourself (by region, for example). More on geospatial indexing is in Chapter 58.

3.10 Pub/Sub

Publish/subscribe lets a client SUBSCRIBE to a channel name (or pattern) and receive every message that other clients PUBLISH to it. Redis stores nothing: a message is pushed to whoever is connected at that moment and then forgotten. Delivery is at most once. A disconnected subscriber misses messages, and a slow subscriber can be dropped when its output buffer limit is exceeded. That is fine for cache invalidation hints, live presence, or chat fan-out where a reconnect refetches state. It is the wrong tool when you cannot lose messages; use streams or a real message broker. In a Cluster, classic PUBLISH is broadcast to every node, which is wasteful, so Redis 7 added sharded pub/sub (SPUBLISH/SSUBSCRIBE) tied to a hash slot.

4. Command complexity and dangerous commands

Because one thread runs every command, the time complexity of a command is a direct measure of how long it can stall every other client. The Redis documentation lists the Big-O of each command. A practical way to think: O(1) and O(log N) commands are safe at any scale; O(N) commands are safe only when N is small and bounded; O(N) over a collection that can grow without limit is a latent outage.

4.1 KEYS and why SCAN exists

KEYS user:* walks the entire keyspace and returns every match in a single reply. With 50 million keys that takes seconds, during which the server answers nobody, and the reply itself can be hundreds of megabytes. The safe replacement is SCAN: a cursor-based iterator that returns a small batch per call (the COUNT hint, default 10) and gives you a cursor to continue with. Each call is cheap, so other clients interleave. SCAN guarantees that elements present for the entire iteration are returned, but it may return an element more than once, and elements added or removed during the scan may or may not appear. Its sibling commands SSCAN, HSCAN, ZSCAN do the same inside one collection. Where an application needs to enumerate related keys, a better design is to maintain an index set explicitly.

4.2 Big collections

A hash with 5 million fields is only one key, but HGETALL on it returns 5 million entries, blocks for a long time, and floods the network. The same goes for deleting it: DEL frees memory synchronously. UNLINK removes the key from the keyspace immediately and frees memory in a background thread; the settings lazyfree-lazy-eviction, lazyfree-lazy-expire, and lazyfree-lazy-server-del make eviction, expiry and implicit deletes behave the same way. Design rule: bound every collection. Cap lists with LTRIM, cap streams with XTRIM MAXLEN, bucket huge hashes into many smaller ones, and page through results.

4.3 Other commands to restrict

FLUSHALL, DEBUG, CONFIG, SHUTDOWN and MONITOR (which echoes every command and can halve throughput) should be hidden or renamed using ACLs (Redis 6) in any shared environment. Also use SLOWLOG GET to see recent commands that exceeded slowlog-log-slower-than (10 ms by default is a typical choice) and LATENCY DOCTOR for diagnosis.

Watch out A command that is fast in testing with 1,000 elements may take 300 ms in production with 10 million. Always reason about the worst-case size of a collection, not the average.

5. Expiration and eviction

These two words are often confused. Expiration removes a key because its time-to-live you set has passed. Eviction removes keys, even ones with no TTL, because memory is full. They work differently.

5.1 How expiration works

You attach a TTL with EXPIRE key seconds, SET key v EX 60, or PEXPIRE for milliseconds. Redis stores the absolute expiry time in a separate dictionary of keys with a TTL. It would be too costly to keep a timer per key, so it uses two cooperating strategies.

  • Lazy (passive) expiry: whenever a command touches a key, Redis first checks its expiry time. If it has passed, the key is deleted and treated as absent. This guarantees you never read an expired value.
  • Active expiry: a periodic job, run about 10 times per second, samples a number of keys (20 per round) from the set of keys with TTLs, deletes the expired ones, and if more than about 25 percent of the sample was expired, repeats immediately (within a bounded time budget). This reclaims memory of keys nobody reads again.

Consequences: expired keys can occupy memory for a short while after their deadline; and a mass expiry (say 10 million keys all given the same TTL at once) can cause a burst of deletion work that raises latency. The usual fix is TTL jitter, adding a random few percent to each TTL, which also prevents the synchronized cache stampede discussed in Chapter 14. In a replicated setup, replicas do not expire keys on their own clock: the primary generates an explicit DEL (or UNLINK) and propagates it. Replicas may still logically hide a key whose time has passed for reads.

5.2 Memory limit and eviction policies

Set maxmemory to bound the dataset size. When a write would exceed it, Redis consults maxmemory-policy:

PolicyBehaviour
noevictionDefault. Refuse writes (return an error) when full; reads still work. Right when Redis is a datastore and silent data loss is unacceptable.
allkeys-lruEvict the least recently used key among all keys. The common choice for a pure cache.
volatile-lruSame, but only among keys that have a TTL. Keys without TTL are never evicted, so you can mix cache and durable data in one instance (but if the volatile keys run out, writes fail).
allkeys-lfuEvict the least frequently used key. Better when a few keys are very popular and scans of cold keys should not push them out.
volatile-lfuLFU among keys with TTL.
allkeys-random, volatile-randomEvict a random key.
volatile-ttlEvict keys with the nearest expiry among those with TTL.

5.3 Approximated LRU and LFU

True LRU needs a linked list ordering every key by last access, updated on every read, which costs memory (two pointers per key) and CPU. Redis instead uses an approximation. Each object has a small 24-bit field holding a coarse last-access clock. When eviction is needed, Redis samples a few random keys (maxmemory-samples, default 5), and evicts the one with the oldest access time. Larger samples (10) approximate true LRU closely at some CPU cost; since Redis 3.0 a small pool of good candidates is also carried across rounds to improve accuracy.

For LFU, the same 24-bit field is split: 16 bits record a last-decrement time, and 8 bits hold a logarithmic counter. Each access increments the counter probabilistically, so the small counter can represent very large frequencies (lfu-log-factor, default 10, controls how fast it saturates). The counter also decays over time (lfu-decay-time, default 1 minute per decrement), so keys that were hot long ago lose their standing. A brand-new key starts with a small initial counter so that it is not evicted instantly. OBJECT FREQ key shows it under an LFU policy.

Interview tip Say which policy you would pick and why. A pure cache with skewed popularity: allkeys-lfu (or allkeys-lru). Redis as a primary store: noeviction plus alerts on memory. Mixed use in one instance: volatile-lru, with a note that mixing is better avoided by running separate instances.

6. Persistence: RDB, AOF, and the hybrid

Memory is lost when the process dies or the machine reboots. Redis offers two ways to write data to disk so it can reload at startup. They can be used separately or together. Neither makes Redis behave like a fully synchronous database, and the point of this section is to understand exactly how much you can lose.

6.1 RDB snapshots

An RDB file is a compact binary snapshot of the whole dataset at one moment. Redis creates it with BGSAVE, or automatically by rules such as save 3600 1 300 100 60 10000 (snapshot if at least 1 change in an hour, 100 in 5 minutes, or 10,000 in a minute). To snapshot without stopping the world, Redis calls fork(). The operating system creates a child process that shares the parent's memory pages. The child walks its frozen view and writes the file, while the parent keeps serving clients.

The child's frozen view works because of copy-on-write (COW). The pages are shared read-only. When the parent modifies a key, the OS copies just that 4 KB page for the parent, and the child keeps the old one. Two costs follow. First, fork() itself must copy the page table, which is roughly 8 bytes per 4 KB page, so about 20 MB of page table for each 10 GB of memory; this can pause the main thread for tens to hundreds of milliseconds on a large dataset or a virtual machine with slow fork (some hypervisors are much slower). Second, during the snapshot every page that the parent writes to is duplicated. In a write-heavy workload, memory usage can climb toward 2x the dataset in the worst case. If the machine has no spare memory, the kernel's out-of-memory killer terminates Redis. So leave headroom: a common guideline is to keep data under about 50 to 60 percent of RAM if you snapshot under heavy writes. Transparent Huge Pages should be disabled, because 2 MB pages make COW copy far more per write. Also set vm.overcommit_memory=1 so fork does not fail for lack of "promised" memory.

RDB strengths: compact, fast to load, ideal for backups and for starting replicas. Weakness: you lose everything since the last snapshot, which could be minutes.

6.2 AOF, the append-only file

The append-only file logs every write command as it is executed (appendonly yes). On restart, Redis replays the log to rebuild the dataset. How soon a write is truly on disk depends on appendfsync:

SettingBehaviourLoss on crashCost
alwaysfsync after every command (batched per event loop iteration)Essentially none acknowledgedSlowest; throughput limited by disk sync latency
everysecfsync once per second in a background threadAbout 1 second of writes (possibly up to 2)Small; the usual default choice

The log grows forever, so Redis periodically performs an AOF rewrite: a child process writes a new, minimal log that reproduces the current dataset (for example one SET instead of a thousand INCR commands), and the changes made meanwhile are appended to it. This also uses fork and copy-on-write, with the same memory implications. Since Redis 7 the AOF is split into a base file plus incremental files tracked by a manifest (multi-part AOF), which makes rewrites and recovery tidier.

6.3 The hybrid format

With aof-use-rdb-preamble yes (the default in modern versions), a rewrite writes the base as an RDB snapshot, followed by the AOF commands since. Loading is fast like an RDB and loses little like an AOF. This is why a typical configuration is "AOF with everysec and RDB preamble".

7. Replication

Redis replication is asynchronous, primary to replica. A replica is a copy that connects to a primary and receives the stream of write commands. Replicas serve read traffic (reads may be slightly stale), give a hot standby for failover, and offload snapshotting (you can run RDB or AOF rewrite on a replica rather than on the primary). Configure with replicaof host port.

7.1 Initial sync and PSYNC

When a replica connects, it sends PSYNC replid offset, announcing the replication ID of the history it follows and how far it has applied (its offset). The primary then picks one of two paths.

  • Full resynchronization: if this is a new replica, or the primary cannot continue from the offset, the primary forks and produces an RDB snapshot (or streams it straight to the replica's socket with diskless replication, repl-diskless-sync yes), meanwhile buffering new writes. The replica discards its old data, loads the RDB, then receives the buffered writes and continues with the live stream. This costs a fork, CPU, bandwidth, and replica load time, and for a big dataset can take many minutes.
  • Partial resynchronization: if a replica disconnects briefly and reconnects with a known replid and an offset still inside the primary's replication backlog (a ring buffer of recent writes, repl-backlog-size, default 1 MB which is small for busy systems), the primary sends only the missing commands. This is cheap, so size the backlog to cover the longest network blip you expect at your write rate.

7.2 Replication lag and consistency

The primary acknowledges a write to the client before replicas have it. The delay is replication lag, usually sub-millisecond on a healthy local network but growing with big writes, slow replicas, network saturation, or a replica busy loading data. Consequences you must design for:

  • Reading from a replica can return stale data, including data you just wrote (no read-your-writes guarantee). Route read-after-write paths to the primary.
  • If the primary dies before sending recent writes, a promoted replica lacks them. Acknowledged writes can be lost on failover. WAIT numreplicas timeout blocks the client until that many replicas have acknowledged, narrowing the window but not making it a consensus protocol (a replica can still fail after acknowledging, and a failover might choose another replica).
  • You can bound the damage: min-replicas-to-write 1 and min-replicas-max-lag 10 make the primary refuse writes if it has no healthy replica, which limits how much an isolated old primary can accept.

Replication chains are possible (replicas of replicas) to reduce load on the primary. Replicas are read-only by default. Details of replication in general are covered in Chapter 24.

8. Sentinel: automatic failover for a single shard

Replication alone gives you copies but not recovery: someone must notice the primary died, choose a replica, promote it, and tell clients. Redis Sentinel is a set of separate monitoring processes that automate this for one primary and its replicas (no data sharding). Sentinel also acts as a configuration provider: clients ask Sentinel "who is the primary of mymaster right now?" instead of using a fixed address.

8.1 How failover happens

  1. Detection. Each Sentinel pings the primary, replicas and other Sentinels. If the primary does not answer validly for down-after-milliseconds (say 5000), that Sentinel marks it subjectively down (SDOWN).
  2. Agreement. The Sentinel asks the others. If at least quorum Sentinels agree, the primary is objectively down (ODOWN). The quorum only decides failure detection.
  3. Leader election. The Sentinels elect one of themselves to run the failover, using a Raft-like voting scheme with epochs. The leader must be authorized by a majority of all Sentinels, regardless of the quorum number, so a minority partition can never act.
  4. Replica selection. The leader picks the best replica: connected recently, lower replica-priority, larger replication offset (most data), then the smallest run ID as tiebreak.
  5. Promotion and reconfiguration. It sends REPLICAOF NO ONE to that replica, points the other replicas at it, publishes the new configuration with a higher configuration epoch, and clients learn the new address. The old primary, when it returns, is reconfigured as a replica.

8.2 Operational points

  • Run an odd number, at least 3, of Sentinels on independent machines or zones. Two Sentinels cannot form a majority after losing one.
  • Sentinel does not prevent write loss. It is built on asynchronous replication. Also, during a network partition the old primary may keep accepting writes from clients on its side until it learns of the new epoch, and those writes are later discarded when it is demoted. min-replicas-to-write limits this.
  • Clients must be Sentinel-aware (ask Sentinel, and reconnect on failover). Failover typically takes down-after-milliseconds plus a few seconds of election and promotion, so budget about 10 to 30 seconds of write unavailability.
  • Sentinel does not scale memory or write throughput. When one node's RAM or CPU is not enough, you need Cluster.

9. Redis Cluster: sharding and failover together

When the dataset or the write rate outgrows one machine, Redis Cluster splits the keyspace across many primaries, each with its own replicas, and builds failover into the same system (no separate Sentinel needed). Sharding concepts in general are in Chapter 25; this section is how Redis does it.

9.1 Hash slots

Instead of consistent hashing on a ring, Redis defines 16,384 hash slots. The slot of a key is CRC16(key) mod 16384. Each primary owns a set of slot ranges (with three primaries, for example, 0-5460, 5461-10922, 10923-16383). Because the unit of movement is a slot, adding or removing a node means moving whole slots, not rehashing everything. The number 16,384 was chosen because each node regularly gossips a bitmap of the slots it owns, and 16,384 bits is only 2 KB per heartbeat message, while remaining plenty of granularity for the recommended cluster size of up to about 1,000 nodes.

9.2 Client routing, MOVED and ASK

There is no proxy in the standard design. The client library fetches the slot map (CLUSTER SLOTS or CLUSTER SHARDS), hashes each key itself, and connects directly to the owning primary. If the map is stale, the node answers with a redirection:

  • -MOVED slot host:port: the slot permanently lives elsewhere. The client updates its map (usually refreshes entirely) and retries there.
  • -ASK slot host:port: the slot is being migrated and this particular key has already moved. The client sends ASKING followed by the command to the target for this one request only, without updating its map.

9.3 Resharding

To add capacity you add a node and move slots to it (redis-cli --cluster reshard, or an operator or managed service doing it). For each slot, the source marks it MIGRATING and the target marks it IMPORTING, then keys are moved in batches with MIGRATE, which atomically transfers a key. While this happens the cluster stays online: keys still on the source are served by it; keys already moved result in ASK redirections. Finally the new ownership is announced. Cost: MIGRATE of a big key blocks both nodes for its duration, which is another reason to avoid huge keys. Rebalancing in advance of load, not during an incident, is the wise approach.

9.4 Hash tags and multi-key limits

Multi-key commands (MGET, SUNION, transactions, Lua scripts touching several keys) require all keys to be in the same slot, otherwise the node replies CROSSSLOT. To force related keys together, use a hash tag: if a key contains {...}, only the text inside the first braces is hashed. So cart:{user42}:items and cart:{user42}:meta share a slot and can be used together. The tradeoff is skew: if you tag by a tenant that is huge, one slot, and therefore one shard, becomes a hot spot that cannot be split. Also, Cluster supports only database 0 (no SELECT).

9.5 Gossip, failure detection and failover

Cluster nodes talk to each other on a second port (client port plus 10000) using a binary gossip protocol. Each node pings a few others regularly, including slot ownership and what it believes about the state of other nodes. If a node does not answer within cluster-node-timeout (commonly 5 to 15 seconds), the pinging node marks it PFAIL (possible failure). When a majority of primaries have reported PFAIL for the same node within a window, it is promoted to FAIL and the news is broadcast. A replica of a failed primary then requests votes from the other primaries, and if it wins a majority it takes over the slots with a higher configuration epoch. This resembles Sentinel, built into the data nodes.

  • Minority partitions stop serving writes. A primary that cannot reach a majority of primaries stops accepting writes after the node timeout; this limits divergence. But writes sent to an isolated primary during the window just before it notices are lost, because replication is asynchronous.
  • If a slot has no reachable owner, by default (cluster-require-full-coverage yes) the whole cluster stops accepting writes. Many operators set it to no so that other slots continue.
  • Need at least three primaries (to have a majority), and each primary should have at least one replica in a different failure domain. Replica migration can rebalance replicas to protect orphaned primaries.
  • Replicas can serve reads after the client sends READONLY, with the usual staleness.
Watch out Cluster trades functionality for scale: no multi-key operations across slots, no multiple databases, one big sorted set stays on one shard, and clients must be cluster-aware. For a dataset that fits on one large machine, Sentinel or a managed primary-replica setup is simpler and often better.

10. Transactions and Lua scripts

10.1 MULTI and EXEC

MULTI starts queuing commands, and EXEC runs them all in a row. Because of single-threaded execution, no other client's command runs in the middle, so the batch is isolated. But, unlike a relational transaction, there is no rollback. If a command in the batch fails at runtime (for example INCR on a non-numeric string), the others still run. Only syntax errors found during queueing abort the whole batch. Think of MULTI/EXEC as "run these commands together without interleaving", not as ACID.

10.2 WATCH: optimistic locking

WATCH key tells Redis to remember the key's version. If the key is modified by anyone before your EXEC, the whole transaction is cancelled (EXEC returns null) and you retry. This implements check-and-set: read the balance, compute in the client, then update only if it did not change. It works well under low contention, but under high contention retries pile up.

WATCH balance:42
GET balance:42          # client computes new value
MULTI
SET balance:42 90
EXEC                    # nil if someone else changed balance:42

10.3 Lua scripts and functions

Often the read-compute-write logic is better done server-side. EVAL runs a Lua script atomically: the script executes on the main thread without interleaving, can read and write many keys, and can branch on what it reads, which MULTI cannot. EVALSHA runs a script cached by its SHA1 to avoid resending it. Redis 7 added Functions, named libraries stored in and replicated with the server. Scripts must declare their keys in the KEYS array (so Cluster can route them), and in Cluster all of those keys must be in the same slot. The big caution: a slow script blocks everything, and Redis kills a script only after busy-reply-threshold (default 5 seconds) and then only with an explicit SCRIPT KILL if it has not yet written.

The classic example is safe lock release, which must check ownership and delete as one atomic step:

-- KEYS[1] = lock key, ARGV[1] = my token
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
Key idea Reach for single commands first, then MULTI/EXEC for batching, WATCH for low-contention check-and-set, and Lua for anything with real logic. All are atomic only on the node (or slot) that executes them, and atomic is not the same as durable or replicated.

11. Common patterns

11.1 Cache

Use SET key value EX ttl with jitter, an eviction policy such as allkeys-lfu, and the cache-aside flow. The strategies (cache-aside, write-through, write-behind) are in Chapter 13, and the dangers (stampede, penetration, avalanche, hot key) are in Chapter 14. Not repeated here. Use hashes or compressed JSON for objects, and keep values small.

11.2 Distributed lock

The standard single-instance recipe: acquire with SET lock:order:42 <random-token> NX PX 30000 (set only if absent, expire in 30 seconds so a crashed holder cannot block forever). Release with the Lua script above so you never delete someone else's lock. If the work may take longer than the TTL, a watchdog thread extends the TTL while the holder is alive.

Watch out: caveats A lock with a TTL is a lease, not a guarantee of mutual exclusion. If the holder pauses (garbage collection, a stalled VM) beyond the TTL, another client acquires the lock while the first still believes it holds it. Failover makes it worse: the lock write may not have reached the replica that becomes primary. The multi-instance Redlock algorithm tries to address node failure, but it assumes bounded clock drift and pauses, and is criticized for that. For correctness-critical exclusion, use a fencing token checked by the protected resource, or a consensus system. See Chapter 30.

11.3 Rate limiter

Fixed window: INCR rl:user42:<minute> and EXPIRE on first increment, reject when above the limit. Simple, but allows a double burst at a window boundary. Sliding window log: a sorted set of request timestamps, ZREMRANGEBYSCORE to drop old ones, ZCARD to count; precise but uses memory per request. Token bucket: store tokens and last-refill time in a hash and update both in a Lua script so concurrent requests cannot race. Algorithms and tradeoffs are in Chapter 16.

11.4 Leaderboard

One sorted set per board. ZINCRBY board:daily 50 player7 adds points; ZREVRANGE board:daily 0 9 WITHSCORES returns the top ten in O(log N + 10); ZREVRANK returns a player's rank in O(log N). Combine boards with ZUNIONSTORE (weekly from dailies). For huge boards, shard by region or season, since one sorted set lives on one node. The data-structure view is in Chapter 59.

11.5 Session store

A session is a small object keyed by a random session ID, stored as a hash or a JSON string, with TTL equal to the idle timeout and EXPIRE refreshed on each request (sliding expiry). Every web server reads the same store, so servers stay stateless. Sessions are not usually critical (users re-login on loss), so AOF everysec or even RDB is a sensible durability level.

11.6 Queues

  • List queue: producers LPUSH, workers BRPOP. Simple, but a popped job vanishes if the worker crashes. The safer form is BLMOVE queue processing (atomically move to a processing list), then remove it on success and a reaper requeues stale entries.
  • Stream with consumer group: XADD, XREADGROUP, XACK, XAUTOCLAIM for retry. At-least-once, so make handlers idempotent.
  • Delay queue: a sorted set with run-at time as score; a poller takes members with score up to now using a Lua script that also removes them.

For high-volume, durable, replayable messaging, use a real broker; see Chapter 34.

11.7 Counters

INCR is atomic, so counting page views, likes or inventory units works across thousands of clients. For extremely hot counters, shard the counter into several keys (views:1 to views:8, pick randomly, sum on read) and flush totals to a database periodically. Approximate unique counts use HyperLogLog (section 3.7).

12. Memory management, big keys and hot keys

12.1 Where memory goes

Used memory is more than your data. Each key costs a dictionary entry (about 24 to 32 bytes of pointers and metadata), the key string, a value object header (16 bytes), plus the allocator's rounding. A small string value of 100 bytes under a 20-byte key typically consumes 150 to 200 bytes in total. On top come client buffers, the replication backlog, the AOF rewrite buffer, and the fork's copy-on-write pages. Tools: INFO memory, MEMORY USAGE key, MEMORY DOCTOR, and redis-cli --bigkeys or --memkeys.

12.2 Fragmentation

Redis uses the jemalloc allocator, which groups allocations into size classes. After many keys of varying sizes are created and deleted, free memory is scattered in small holes that the OS cannot reclaim. INFO memory shows mem_fragmentation_ratio = resident set size divided by used memory. Around 1.0 to 1.5 is normal. Well above 1.5 means a lot of waste (and the same machine will run out of RAM sooner than used_memory suggests). A ratio below 1.0 means the OS is swapping Redis memory to disk, which is a severe latency problem. Mitigation: activedefrag yes (online defragmentation in the background, moving values into compact pages with a CPU cost), restart through a replica failover during a quiet period, or avoid patterns that churn many differently sized values.

12.3 Big keys

A big key is a single key whose value is huge: a list with 10 million elements, a 200 MB string, a hash with millions of fields. Problems: reading, deleting, or migrating it blocks the server; replication and RDB writes of it cause latency spikes; in Cluster it makes slots uneven; expiring it stalls the active expiry cycle unless lazy-free is on. Detect with --bigkeys or MEMORY USAGE sampling. Fix by splitting (hash buckets user:{id}:part:N), paging, using UNLINK, and setting size caps in application code.

12.4 Hot keys

A hot key receives a disproportionate share of traffic. In Cluster a key lives on one primary, so adding shards does not help; that shard's single thread saturates. Detect with redis-cli --hotkeys (needs an LFU policy), OBJECT FREQ, or sampling at the client. Mitigations: a short-lived local in-process cache in front of Redis (even 1 second absorbs most traffic); replicating the key under N names (config:v1#0..#7, with clients choosing randomly) so traffic spreads across shards; reading from replicas; and the client-side caching feature (CLIENT TRACKING) where the server tells clients when their local copy is invalid.

  • Azure Cache for Redis, Google Memorystore, Redis Cloud / Redis Enterprise, and serverless options such as Upstash.

Managed services remove patching, failover orchestration, and backups, but you still own key design, memory sizing, and client behaviour, and you pay for the replicas and the headroom. Check what each offers on max node size, cluster resharding without downtime, cross-region replication (often active-passive), and which commands are restricted.

16. Worked example: sizing a session and counter store

Requirement. A consumer app has 20 million active sessions at peak. Each session is a hash of about 8 fields totalling roughly 800 bytes of payload, with a 30-minute sliding TTL. Peak traffic is 100,000 session reads per second and 20,000 session writes per second (TTL refresh and updates). Availability matters: a node loss must not log everyone out, but losing a second of data is acceptable.

16.1 Memory

  1. Per-session cost: payload 800 B, plus key string (about 40 B, for example sess:<32 hex>), key dictionary entry and object headers (about 70 B), plus the TTL entry (about 40 B), plus allocator rounding (about 10 percent). That is roughly 800 + 40 + 70 + 40 = 950 B, times 1.1 = about 1.05 KB.
  2. Dataset: 20,000,000 x 1.05 KB = 21 GB.
  3. Headroom: for fork and copy-on-write under 20,000 writes per second, plus fragmentation and buffers, assume data should be at most about 55 percent of RAM. So total RAM needed across primaries = 21 / 0.55 = about 38 GB.

16.2 Throughput and shard count

  1. Total operations: 100,000 + 20,000 = 120,000 per second. Session operations are O(1) and tiny, so a single instance with network round-trip overhead can handle on the order of 50,000 to 100,000 per second. We want no shard above about 30 to 40 percent of that at peak, to leave room for failover surges and slow commands.
  2. Network: 120,000 ops/s x about 1 KB = 120 MB/s, about 1 Gbit/s total reply traffic. Split across shards this is comfortably inside a single NIC, though a single node at 10 Gbit/s has headroom.

Memory says about 38 GB of RAM; throughput says at least 3 shards. We choose 4 primary shards in Redis Cluster, each a 16 GB machine (data is about 5.25 GB per shard, which is 33 percent of RAM, comfortably under 55 percent). Each shard then serves 30,000 ops/s, which is moderate.

16.3 High availability and cost

  • One replica per primary in a different availability zone: 8 nodes total of 16 GB. Total RAM purchased 128 GB for 21 GB of data, a 6x overhead, reflecting replication (2x) and headroom (about 3x). This ratio is typical and worth stating to an interviewer.
  • Persistence: AOF everysec with RDB preamble, snapshots taken on the replica. Loss on failover is about 1 second plus any unreplicated writes; acceptable because the user simply logs in again.
  • Failover: cluster-node-timeout of 5 seconds, so a primary loss means about 5 to 10 seconds of errors for that quarter of users. The client retries with backoff and a short timeout of 50 ms per call.
  • Sessions use the key as the routing key, so there is no multi-key use; no hash tags needed, which avoids skew.
  • TTL jitter of plus or minus 10 percent on the 30-minute TTL spreads expiry work.

16.4 Sanity checks

Growth: 50 percent more users means 31 GB of data, still at about 49 percent of RAM on four shards, so we have some room, and adding a fifth shard by resharding later is possible online. Cold start: if all of Redis were lost, 20 million users would need re-login; the login service must handle a spike, so rate limiting and queuing at the login endpoint are part of the design. The cost of the worst-case question "what if one shard becomes hot?" is low here because session IDs are random and spread evenly.

17. Interview Q&A

If Redis is single-threaded, how does it handle 100,000 requests per second?

Each command is tiny and operates on in-memory data, so it takes only a few microseconds of CPU, and a single core can therefore execute hundreds of thousands per second. The thread never waits on disk or locks, and an epoll-based event loop multiplexes thousands of connections without blocking on any of them. Since Redis 6, optional I/O threads handle socket reads and writes in parallel while command execution stays serial. The real limit is usually network round trips, which pipelining and connection pooling reduce.

Why does a single slow command matter so much, and how do you avoid it?

Because one thread executes all commands, an O(N) command on a large collection, like KEYS * or HGETALL on a million fields, blocks every other client until it finishes, so the whole application sees timeouts. You avoid it by choosing O(1) or O(log N) operations, bounding collection sizes, using SCAN-style iteration, deleting large keys with UNLINK, and watching the slowlog. ACLs should deny dangerous commands, and client timeouts with circuit breakers contain the impact when something slips through.

How does a sorted set work internally, and why is it good for a leaderboard?

Large sorted sets combine a hash table mapping member to score with a skip list ordered by score. The hash table gives O(1) score lookup, and the skip list gives O(log N) insertion, removal, rank calculation, and range scans, because spans stored on links allow rank to be computed while searching. A leaderboard needs exactly those operations: add points, get the top K, get a player's rank, and get the neighbours around a player. For huge boards you shard by region or season, since one sorted set sits on one node.

Compare RDB and AOF. What would you use for a session store, and for a primary database?

RDB is a periodic compact snapshot made by a forked child, which is fast to load but can lose minutes of writes. AOF logs every write and with everysec loses about a second, at the cost of a larger file and periodic rewrites. For a session store I would use AOF everysec with the RDB preamble, or even RDB only, since losing a few seconds just forces some logins. For a primary database I would not rely on open-source Redis alone, because replication is asynchronous and failover can drop acknowledged writes. I would use a service with a multi-AZ durable log, or a database designed for that guarantee.

What happens during a fork for a snapshot, and why can it cause an out-of-memory kill?

The child shares the parent's memory pages copy-on-write. When the parent modifies a page while the child is still writing, the OS must duplicate that 4 KB page, so under heavy writes memory approaches twice the dataset size. If the machine lacks that headroom, the OOM killer may terminate Redis. The fork itself also copies page tables, which pauses the main thread briefly, more on large instances and slow hypervisors. Mitigations are keeping data to about half of RAM, disabling transparent huge pages, and taking snapshots on a replica.

Explain how Redis Cluster routes a key and what MOVED and ASK mean.

The key is hashed with CRC16 and taken modulo 16,384 to give a slot, and each primary owns ranges of slots. Cluster-aware clients cache the slot-to-node table and send commands directly to the owner. If the table is stale, the node replies MOVED with the right address, and the client updates its map and retries. During a resharding migration, a node may reply ASK for a key that already moved; the client sends ASKING and the command to the target just once without changing its map. Multi-key commands require all keys in one slot, which hash tags such as {user42} enforce.

Sentinel versus Cluster: when do you choose each?

Sentinel gives automatic failover and service discovery for a single primary with replicas, but the whole dataset and all writes still live on one node. It is simple, supports multi-key operations and multiple databases, and is right when the data fits in one machine's RAM and one core can handle the write rate. Cluster shards data across many primaries with built-in failover, so it scales memory and write throughput, but restricts multi-key operations to one slot and requires cluster-aware clients. I would start with Sentinel or a managed primary-replica and move to Cluster when I hit memory or throughput limits.

How would you implement a distributed lock with Redis, and what can go wrong?

Acquire with SET key token NX PX ttl using a unique token, and release with a Lua script that deletes the key only if the token still matches. The danger is that the lock is a time-based lease. If the holder stalls longer than the TTL, someone else acquires the lock and both act. A failover can also lose the lock because replication is asynchronous. For correctness-critical work I would add fencing tokens that the downstream resource verifies, or use a consensus-based service; Redis locks are good for efficiency-oriented locking where occasional double execution is harmless.

A single key is overloaded in a Redis Cluster. What do you do?

Adding shards does not help, since one key maps to one slot on one primary. First confirm it is a hot key with --hotkeys, OBJECT FREQ or client-side sampling. Then put a small in-process cache with a short TTL in front, which usually removes most of the load. If it is a counter, split it into N sub-keys and sum on read. If it is a read-mostly value, write it under several key names and have clients pick one randomly, or read from replicas where staleness is tolerable.

When would you pick Memcached over Redis?

When the use is a plain, large, ephemeral cache of opaque values and you value simplicity and multi-core scaling in one process. Memcached is multithreaded, has predictable memory via slabs, and has a smaller feature surface to operate. Redis wins whenever you need data structures, atomic operations such as counters and Lua, persistence, built-in replication, pub/sub or streams. In practice many teams standardize on Redis because it covers caching well and adds those capabilities, with the tradeoff of one core per instance for command execution.

How do eviction and expiration differ, and which policy would you choose for a cache?

Expiration deletes keys whose TTL elapsed, lazily on access and by a periodic active sampler. Eviction deletes keys to stay under maxmemory when it is full, according to maxmemory-policy. For a cache with skewed popularity I would choose allkeys-lfu, since it protects frequently used keys from being pushed out by one-time scans, and allkeys-lru is a good simple alternative. Both are approximations that sample a handful of keys per eviction, so they cost almost nothing. If Redis holds data that must not vanish, use noeviction and alert on memory.

Can Redis lose acknowledged writes? Under what circumstances?

Yes. A write is acknowledged once the primary has applied it in memory, before it reaches replicas or is fsynced (unless AOF is set to always). If the primary crashes before replicating, the promoted replica lacks the write. With AOF everysec a machine crash loses about a second, and with RDB alone minutes. During a partition, an old primary may also accept writes that are discarded when it rejoins. WAIT, min-replicas-to-write and AOF always narrow these windows but do not give consensus-level guarantees.

18. Recap

  • Redis is an in-memory data structure server. Its speed comes from RAM, single-threaded lock-free command execution, an epoll event loop, optional I/O threads, compact encodings, and pipelining. The cost is that any slow command blocks all clients.
  • Pick the right structure: strings and hashes for objects, lists and streams for queues, sets for membership, sorted sets (hash table plus skip list) for ranking and scheduling, bitmaps and HyperLogLog for compact analytics, geo for proximity, pub/sub for lossy fan-out.
  • Avoid O(N) commands on unbounded collections: use SCAN instead of KEYS, UNLINK instead of DEL for big keys, and page results.
  • Expiry is lazy plus sampled; eviction obeys maxmemory-policy with approximate LRU or LFU by sampling. Add TTL jitter.
  • Persistence: RDB for compact snapshots, AOF for a smaller loss window (everysec is typical), hybrid for fast load. Fork and copy-on-write demand memory headroom. Even so, replication is asynchronous and failover can lose acknowledged writes.
  • Replication uses PSYNC with a replication ID, offset, and backlog; partial resync is cheap, full resync is expensive. Sentinel automates failover for one shard; Cluster shards over 16,384 slots with MOVED and ASK redirections, hash tags, gossip, and majority-based failover.
  • MULTI/EXEC isolates but does not roll back; WATCH gives optimistic check-and-set; Lua gives atomic server-side logic. Locks in Redis are leases that need fencing for correctness.
  • Watch for big keys, hot keys, fragmentation, fork pauses, and thundering herds after failover. Size with data at about half of RAM, add replicas, and monitor hit rate, memory and latency.
