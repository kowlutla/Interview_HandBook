Observability for Microservices

In a monolith, one process holds the whole story of a request. In a microservice system that story is scattered over dozens of processes, machines and queues, and you must deliberately stitch it back together. This chapter covers the parts of observability that are specific to distributed systems: correlation IDs, distributed tracing, sampling, centralized structured logs, per-service metrics, exemplars, dependency maps, alerting without storms, async and saga visibility, and how to debug a real incident from metrics to traces to logs.

Scope Chapter 54 already explains what logs, metrics and traces are, the RED and USE methods, alerting philosophy, and SLI/SLO/SLA arithmetic. This chapter assumes that and does not repeat it beyond a short recap. Here we ask a different question: what changes when the thing you observe is not one program but a web of independently deployed services?

1. Why microservices make debugging hard

Suppose a user taps "Place order" and waits eight seconds instead of one. In a monolith, you open the application log, find the request, and read what happened in order, in one file, on one machine, with one stack trace. In a microservice system, the same tap fans out. The API gateway calls an order service, which calls inventory, pricing and a payment service; payment calls a fraud service and an external card network; the order service also publishes an event that a notification service consumes a few seconds later. Every one of those hops runs in a different process, usually on a different machine, owned by a different team, written in a different language, and logging in a different format.

Five specific things go wrong compared with a monolith:

  • No single place holds the request. The evidence is split across many logs, and nothing links the line in the gateway log to the line in the fraud log unless you built that link.
  • Causality is hidden. A slow response from the order service might be its own code, a slow database, or a slow dependency three hops down. Without a record of who called whom and how long each call took, you can only guess.
  • Failures propagate and mutate. A slow fraud service causes payment threads to pile up, which causes timeouts in the order service, which causes retries from the gateway, which makes the fraud service even slower. The service that alerts first is rarely the one that is broken (see Chapter 47 on timeouts, retries and cascading failure).
  • Partial failure is the normal state. With 60 services, something is always degraded. Aggregate error rates hide a single failing tenant, endpoint, version or availability zone.
  • Time and ownership are fragmented. Clocks differ between hosts, async work finishes long after the request returned, and the person on call for the symptom does not own the cause.

Observability for microservices therefore has one core job: reconstruct the path of a single request through the system, and relate that path to the health of each service along it. Everything else in this chapter, from IDs to sampling to exemplars, serves that job. A useful way to remember it: metrics tell you that something is wrong and roughly where, traces tell you which path and which hop, and logs tell you why. The art is moving between the three quickly, which requires them to share identifiers.

2. Correlation IDs and context propagation

The simplest tool is the correlation ID (also called a request ID): a unique string generated at the edge of the system, when a request first arrives, and passed along to every service that handles that request. Every log line, every outgoing call and every emitted event carries it. To see everything that happened for one user action, you search for that one string across all logs.

Three rules make correlation IDs work:

  1. Generate it once, at the entry point (the gateway or load balancer), unless the caller already supplied a trusted one. Use a random value with enough bits to avoid collisions, such as a UUID or 128 random bits written as 32 hex characters.
  2. Propagate it on every hop, without exception. One service that forgets to forward it breaks the chain for everything downstream, and the gap is usually discovered during an incident, which is the worst time.
  3. Attach it to every log line automatically, using a logging context (for example Java's MDC, Go's context.Context, or Python's contextvars), so developers do not have to remember it per statement.

2.1 Propagation across HTTP, gRPC and messaging

The ID travels in the metadata of whatever transport is used. The mechanism differs, but the idea is identical: the request body is business data; identifiers for observability live beside it in headers or metadata.

  • HTTP: a request header such as X-Request-ID, or the standard W3C traceparent header (section 3.3). The server reads it on arrival, stores it in the request context, and writes it onto every outgoing HTTP call.
  • gRPC: the same values are sent as metadata, which is the gRPC equivalent of headers. Interceptors (middleware) on the client and server copy context into and out of metadata so application code does not do it by hand. See Chapter 47 for gRPC itself.
  • Messaging (Kafka, RabbitMQ, SQS): the ID goes in message headers or attributes, not in the payload. Kafka has record headers; RabbitMQ has message properties and headers; SQS has message attributes. The producer writes them when publishing, and the consumer restores them into its logging and tracing context before processing.
  • Thread and task boundaries inside a service: context is lost when work moves to a thread pool, a reactive pipeline, or a scheduled job. The context must be copied across explicitly, which is a very common source of missing IDs.

2.2 Pitfalls

  • Trusting client-supplied IDs. A client can send any value. Accept it only from trusted internal callers, or generate your own at the edge and record the client's value as a separate field. Never let a client-supplied ID collide with or overwrite internal ones, and never use the ID for security decisions.
  • Header allow-lists. Proxies, gateways and some frameworks drop unknown headers. Check that your headers survive the full path, including service mesh sidecars (Chapter 50), which can help by forwarding and even generating tracing headers, but cannot read your application's thread context.
  • Sidecars do not remove the application's duty. A mesh proxy sees each hop's network call, but when your order service receives request A and then makes outgoing call B, only your code knows that B was caused by A. So the application must copy the incoming headers onto outgoing calls, normally via a tracing library. This is the single most misunderstood point about meshes and tracing.
  • Batch and fan-in work. A job that processes 500 messages together has 500 parents, not one. A single ID cannot express this, which is why tracing has links (section 6).

A correlation ID gives you a join key. It does not give you timing, hierarchy, or causality: you can find all the log lines for one request, but not which call was inside which, or how long each took. That is what distributed tracing adds.

3. Distributed tracing in depth

3.1 Traces and spans

A trace is the complete record of one request's journey through the system. It is made of spans. A span represents one unit of work with a start time and a duration, for example "HTTP GET /orders handled by order-service", "SQL query on the orders table", or "call to the fraud service". Each span has:

  • a trace ID shared by every span in the same trace;
  • its own span ID;
  • a parent span ID, which names the span that caused it (empty for the first, or root, span);
  • a name, start timestamp and duration;
  • attributes (key-value tags such as http.method, db.system, tenant.tier);
  • events (timestamped notes inside the span, such as "retry 2") and a status (ok or error, with an exception record when relevant);
  • a kind: client, server, producer, consumer or internal. A client call and the server handling it are two spans, which lets you measure network and queueing time as the difference between them.

The parent-child links form a tree. Siblings under the same parent either ran in parallel or one after another, which you read from their start times. The root span's duration is roughly the user-visible latency.

3.2 Why the tree has to be rebuilt after the fact

No service sees the whole tree. Each one only creates its own spans and sends them, independently and asynchronously, to a tracing backend. The backend collects spans with the same trace ID and links them using the parent IDs. That is why every span must carry both IDs, and why propagating them (next section) is the entire foundation. A service that drops the context starts a new, unrelated trace, and you see two half-traces instead of one whole.

3.3 W3C Trace Context and the traceparent header

Before a standard existed, each tracing system invented its own headers (Zipkin's B3, Jaeger's uber-trace-id, AWS X-Amzn-Trace-Id), which broke traces at the boundary between systems. The W3C Trace Context standard fixes this with a header named traceparent:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             |  |                                |                |
             |  trace-id (16 bytes, 32 hex)      |                flags (01 = sampled)
             version                             parent span-id (8 bytes, 16 hex)

When service A calls service B, A puts its own current span ID in the parent-id slot. B creates a new span whose parent is that ID and keeps the same trace ID. The flags byte carries the sampled bit, which tells downstream services whether this trace is being recorded (section 4). A second header, tracestate, carries optional vendor-specific key-value data. A third mechanism, baggage (a separate W3C header), lets you carry small application values, such as a tenant ID, across all services automatically. Baggage is copied into every hop's outgoing calls, so keep it tiny and never put secrets in it: it travels to every downstream service, including third parties you call.

3.4 Instrumentation: auto versus manual

Instrumentation means adding code that creates spans and propagates context. There are two styles, and real systems use both.

Agree on attribute names across teams (OpenTelemetry's semantic conventions define standard names, such as http.request.method and db.system), because a search for tenant.id only works if every team spelled it the same way.

3.5 OpenTelemetry architecture

OpenTelemetry (OTel) is the vendor-neutral, open standard for generating and shipping traces, metrics and logs. It merged the earlier OpenTracing and OpenCensus projects and is now the common choice. Its aim is that you instrument your code once and can send the data to any backend. It has these pieces:

  • API: the small interface application and library code calls ("start a span"). It is stable and has no heavy dependencies, so library authors can depend on it safely. If no SDK is installed, API calls do nothing.
  • SDK: the implementation inside your process. It creates the spans, applies the sampler, batches finished spans and hands them to an exporter. It also holds the resource, which describes the process: service.name, service.version, environment, pod name.
  • Exporter: sends data out, most often using the OTLP protocol (OpenTelemetry Protocol, over gRPC or HTTP).
  • Collector: a separate standalone process (a binary you run) that receives data, processes it and forwards it to one or more backends. Its pipeline has receivers (accept OTLP, Jaeger, Prometheus and others), processors (batch, add or remove attributes, redact, sample, retry) and exporters (to Jaeger, Tempo, Elasticsearch, a vendor). It can run as an agent beside each app (a DaemonSet or sidecar) or as a central gateway tier, and commonly both.

Why a collector rather than exporting straight from the SDK to the backend? It decouples applications from backend choice and credentials, it takes retry and buffering load away from the app, it centralizes policy (redaction, sampling, routing), and it lets you switch vendors by editing one config file instead of redeploying fifty services.

4. Sampling: keeping traces affordable

Every request in a busy system can produce dozens of spans. At 20,000 requests per second with 30 spans each, that is 600,000 spans per second. At roughly 500 bytes per span that is 300 MB per second, about 26 TB per day, before indexing. Almost nobody stores all of it. Sampling decides which traces to keep. The tension is simple: you want every interesting trace (errors, slow requests) but the interesting ones are rare and you cannot know in advance which they are.

4.1 Head-based sampling

The decision is made at the very start of the trace, at the root span, before anything is known about how it will turn out. A common form is a fixed rate: "keep 1 in 100". The root service rolls the dice and writes the result into the sampled flag of traceparent; every downstream service honours it (the parent-based sampler in OpenTelemetry). Deterministic variants hash the trace ID so that all services reach the same decision even without the flag.

  • Pros: cheap and simple, no buffering, decided before data is generated so unsampled traces cost almost nothing, and traces are always complete.
  • Cons: blind. A 1 percent rate keeps 1 percent of errors too. If an error occurs once per 10,000 requests, you keep one error trace per million requests, which may be none when you need it.

4.2 Tail-based sampling

The decision is delayed until the trace is finished, then made with full knowledge. A typical policy: keep 100 percent of traces that contain an error, keep 100 percent of traces slower than 2 seconds, keep 1 percent of the rest. To do this a component (usually the gateway collector tier) must buffer all spans of a trace until it is complete, wait for a decision window (for example 30 seconds after the last span arrives), and then keep or drop the whole trace.

  • Pros: keeps what you actually need, the errors and slow outliers.
  • Cons: it needs memory to hold in-flight traces, and all spans of one trace must reach the same collector instance, which means a load-balancing layer that routes by trace ID (the OpenTelemetry collector has a load-balancing exporter for this). It adds latency before data appears, handles very long traces badly, and you still generate and ship every span across your network before dropping it, so the app and network cost remain even though storage cost falls.

4.3 Rate-limited and adaptive sampling

A fixed percentage behaves badly when traffic changes: at night it keeps too few traces to be useful, during a spike it floods the backend. Rate-limited (also called reservoir) sampling keeps at most N traces per second, regardless of traffic. Adaptive sampling adjusts the rate automatically per service or per operation so that each endpoint gets a fair share, so a rarely called endpoint is still seen while a chatty health check is thinned out heavily. Many systems also add per-attribute rules: always keep traces of a given debug flag, a canary version, or a specific customer under investigation.

4.4 Cost and benefit

ApproachStorage costKeeps errors and slow traces?Operational complexity

One more detail: when you sample traces, metrics derived from traces are biased. If you count requests from stored traces, you undercount. Never compute request rate or error rate from sampled traces; compute them from metrics that count every request (section 11), and use traces for examples and structure.

Watch out Sampling interacts with propagation. If a service ignores the incoming sampled flag and makes its own random decision, the result is traces with missing middle spans, which look like bugs in your tracing but are really inconsistent sampling. Make every service use the same parent-based rule.

5. Trace storage, indexing and cardinality

Traces are written heavily and read rarely, and most reads are one of two kinds: "fetch trace X by ID" (a simple key lookup) or "find traces where service=payment and duration > 2s and tenant=acme in the last hour" (a search over attributes). Backends differ in how they serve the second kind.

  • Full-index stores (Jaeger or Zipkin on Elasticsearch or Cassandra, many commercial vendors) index many attributes so searches are fast, but indexing is expensive in disk and CPU. See Chapter 22 for how an inverted index works and why every indexed field costs space.
  • Object-storage-first stores (for example Grafana Tempo) keep spans as compressed blocks in cheap object storage with a minimal index, mostly by trace ID, and scan columns for attribute queries. Storage is far cheaper, and the trade is slower arbitrary searches; they lean on metrics, logs and exemplars (section 12) to find the trace ID first.
  • Retention is usually short for traces, commonly days rather than months, because their value decays quickly: nobody debugs last quarter's request by its waterfall. Keep long-term aggregate numbers in metrics instead.

5.1 Cardinality

Cardinality is the number of distinct values a field takes. A http.method attribute has about 7 values; a user.id attribute has millions. In traces, high-cardinality attributes are welcome, since each span stores its own values and you need order.id or user.id to find the one request a customer complains about. The danger is in indexing them: an index on a field with millions of values grows large and slows writes. The usual policy is to store everything as span attributes but index only a few well-chosen ones (service, operation, status, duration, a handful of business keys).

Cardinality is much more dangerous in metrics, covered in section 11, because there every unique label combination becomes its own time series held in memory. Remember the rule: traces and logs tolerate high cardinality; metrics do not. That is exactly why you look up per-request detail in traces and logs, and keep metric labels coarse.

5.2 Other costs and limits of tracing

  • Overhead in the app: creating spans costs CPU and memory. With asynchronous batch export it is typically a small, low-single-digit percentage, but chatty instrumentation (a span per loop iteration or per cache hit) can hurt. Do not trace inside hot loops.
  • Span limits: a trace with 100,000 spans (a batch job) overwhelms viewers; SDKs cap the number of attributes and events per span.
  • Clock skew: spans are timestamped by the clocks of different machines. If one host's clock is 50 ms ahead, a child can appear to start before its parent. Run NTP or chrony everywhere, and treat tiny negative gaps in waterfalls as skew rather than a mystery.
  • Trace completeness: a lost span leaves a hole. Backends show orphan spans (children whose parent never arrived) and mark them as missing.

6. Tracing asynchronous work: parent versus link

A synchronous call has a clear shape: the caller waits, so the callee's span sits inside the caller's span. Asynchronous messaging breaks this. The producer publishes a message and moves on; the consumer may process it milliseconds or hours later, possibly in a batch with many other messages. Two modelling choices exist.

  • Parent-child. The consumer span is made a child of the producer span. The whole thing appears as one trace, and the waterfall includes a long gap, the time the message waited in the queue. This is natural for one-message-one-handler flows where the work is logically part of the original request, such as "order created, then send confirmation email".
  • Link. The consumer starts a new trace (or a new root span) and adds a span link pointing to the producer's span context. The two traces stay separate, and you can navigate between them. This is the right model when one consumer span relates to many producers (a batch of 500 messages), when the consumer work runs much later, or when one producer fans out to many independent consumers. A single trace stretched across hours is hard to read, slow to assemble and can break tail sampling's wait window.

Practical rules: propagate the trace context in message headers (section 2.1); decide per queue whether the consumer joins the producer's trace or links to it; record queue wait time explicitly as an attribute or span (enqueue time versus start time) because it is often the largest latency in an async flow; and put consumer-side retries and redeliveries as events or as separate spans, so that "this message was attempted three times" is visible rather than hidden.

7. The trace-based debugging workflow

The most useful output of a trace is the waterfall view: spans drawn as horizontal bars on a shared time axis, indented by parent-child depth. You read it left to right as time, and top to bottom as call depth. It answers three questions at once: what called what, what ran in parallel versus in sequence, and where the time went.

7.1 Finding the slow service and the critical path

The critical path is the sequence of spans such that, if any one of them got faster, the whole request would get faster. Spans that ran in parallel with a longer sibling are not on it. To find it:

  1. Start at the root and look at its children. Find the child that finishes last, since the parent cannot finish before it.
  2. Descend into that child and repeat, until you reach a span with no slow child. That span's self time (its duration minus the time covered by its children) is where the work or waiting really happens.
  3. Check the gaps: white space between a client span and its server span is network or queueing; white space inside a parent with no children is time spent in the parent's own code (garbage collection, lock waits, thread pool starvation, a missing instrumented call).
  4. Look for patterns: many identical short database spans in a row means an N+1 query problem; a retry shape (two similar spans, the first ending in error or timeout) means a timeout policy is compounding latency.

A good debugging session usually does not start in the trace viewer. It starts at a symptom in metrics, narrows in traces, and ends with a precise question answered by logs. Section 18 walks through one in full. The general sequence is: detect with metrics, localize with traces, explain with logs.

8. Structured logging for distributed systems

Structured logging means writing each log event as a machine-readable record, almost always JSON, rather than as a free-form sentence. A sentence such as Payment failed for order 123 after 3 retries is easy for a human but hard for a machine to filter, count or join. As JSON the same event becomes fields you can query.

{
  "timestamp": "2026-11-17T09:14:03.218Z",
  "level": "ERROR",
  "service": "payment-service",
  "version": "2.14.1",
  "env": "prod",
  "region": "eu-west-1",
  "pod": "payment-7d9f-x2k",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "tenant_id": "acme",
  "order_id": "o-88231",
  "event": "card_charge_failed",
  "error.type": "UpstreamTimeout",
  "retry_count": 3,
  "duration_ms": 3012,
  "message": "card network timed out"
}

The fields that matter most in a distributed setting:

  • trace_id and span_id: they let you jump from a trace span to the exact log lines emitted inside it, and from any log line to the full trace. Most logging libraries have OpenTelemetry integrations that inject them automatically.
  • service, version, env, region, instance: identify where the line came from. version is vital for spotting that errors began with one release.
  • tenant_id (or customer id): in multi-tenant systems, issues are often confined to one tenant; filtering by tenant isolates it. Use an internal ID, not personal data.
  • event or error code: a stable, short name (card_charge_failed) that you can count and alert on, unlike the free-text message, which changes whenever someone edits the wording.
  • duration and outcome: numeric fields allow aggregation in the log store.
Interview tip Say that logs should be events with stable field names and a shared schema across all services. "We agreed one JSON schema and a shared logging library" is a strong answer, because it is the difference between a searchable platform and fifty dialects.

Other habits: log to standard output and let the platform collect it (do not manage files and rotation per service); use levels consistently (ERROR means someone may need to act, not "an exception was caught and handled"); log at service boundaries (request in, request out, outgoing call result) rather than inside every function; and log once per failure, where it is handled, instead of at every layer it passes through, which produces five copies of the same stack trace.

9. The log aggregation pipeline

Logs written on each pod's disk are useless once the pod is replaced, which in Kubernetes happens constantly. All logs must be shipped to a central, searchable store. The typical pipeline has these stages.

  1. Emit: each service writes JSON lines to standard output.
  2. Collect: a node-level agent (Fluent Bit, Vector, Filebeat, the OpenTelemetry Collector in agent mode, Promtail or Grafana Alloy) reads container logs from the host, adds Kubernetes metadata (namespace, pod, labels), parses, and forwards. Running one agent per node (a DaemonSet) is cheaper than a sidecar per pod.
  3. Buffer (optional but common at scale): a durable queue such as Kafka sits between collectors and storage. It absorbs bursts, lets storage be down or slow without losing logs or back-pressuring services, and lets several consumers (search, archive, security analytics) read the same stream independently. See Chapter 34 for queue and Kafka fundamentals.
  4. Process: an aggregator or stream processor (Logstash, Vector, Fluentd, or a custom consumer) can enrich, drop, redact and route events.
  5. Store and index: usually Elasticsearch or OpenSearch for full-text search (see Chapter 22 for shards, replicas and index lifecycle), or Loki for a cheaper label-indexed approach.
  6. Query and visualize: Kibana or Grafana for search, dashboards and alerts.
  7. Archive: cold, compressed copies in object storage for compliance and rare investigations.

10. Log volume, cost control and sensitive data

Logs are usually the largest line item in an observability bill, because volume grows with traffic times the number of services times verbosity. A system with 200 services each writing 50 GB a day produces 10 TB a day. Controlling it is a design concern, not an afterthought.

  • Log levels in production: INFO and above by default, with the ability to turn DEBUG on for one service, one tenant or one trace for a limited time without a deploy (a dynamic log-level setting).
  • Do not log what traces and metrics already say. A request-in and request-out line per hop duplicates span data. Keep request logs for errors and slow requests, or sample the successful ones.
  • Sampling and dropping at the processor: drop health-check noise, sample repetitive messages, cap repeated identical errors (log the first, then a count).
  • Tiered retention: hot (fast, expensive) for 3 to 7 days, warm for a few weeks, cold object-store archive for months, per compliance rules. Index lifecycle management automates the moves.
  • Per-team quotas and visibility: show each team its own volume and cost. When teams see the bill for a log line that fires 20 million times a day, they fix it.
  • Smaller records: short field names, no giant payloads or full stack traces repeated per retry, and compression in transit.

10.1 Sensitive data in logs

Logs are copied to many systems, retained for long periods, and readable by many engineers, so they are a classic place for data leaks. Passwords, access tokens, API keys, session cookies, full card numbers, national IDs, and personal data such as emails and addresses must never be logged in clear text; privacy rules (GDPR, PCI DSS, HIPAA) apply to logs as much as to databases, including deletion obligations that are hard to meet if personal data is spread across archives.

  • Prevent at the source: never log whole request or response bodies, or whole headers (the Authorization header carries credentials); log selected fields. Use typed logging helpers that mask known sensitive types.
  • Redact centrally as a safety net: pattern-based redaction in the agent or processor (card number and token patterns) catches mistakes, but it is not complete, so it is a second line of defence, not the first.
  • Use identifiers, not data: log an internal user ID or a hash, not an email address.
  • Control access and retention: restrict who can search production logs, audit those searches, and keep retention as short as policy allows.
  • Remember traces and baggage: span attributes and baggage values can leak data just like logs. Apply the same rules, and scrub attributes in the collector.

11. Metrics per service

A quick recap of Chapter 54: metrics are numbers sampled over time, cheap to store and fast to query, ideal for alerting and dashboards. For request-driven services use RED (Rate, Errors, Duration); for resources use USE (Utilization, Saturation, Errors). In a microservice system, the new questions are how to standardize them across services and how to see dependencies.

11.1 A standard set for every service

Give every service the same baseline automatically through a shared library, framework or mesh, so that a dashboard built for one works for all:

  • Request rate, error rate and latency distribution per endpoint (use the route template such as /orders/{id}, never the raw URL).
  • Saturation: thread pool utilization and queue length, connection pool usage (waiting count), CPU throttling, memory and garbage-collection pauses, and for consumers the consumer lag (how many messages behind the queue head).
  • Dependency metrics: for each downstream (database, cache, other service, external API): call rate, error rate, latency, circuit-breaker state, retry count, timeout count.
  • Business metrics: orders placed, payments succeeded, because technical health can look fine while the business is broken.

11.2 Client-side versus server-side metrics

Each call is measured twice: by the caller (client-side) and by the callee (server-side). They differ, and the difference is information. The server-side duration starts when the request reaches the service; the client-side duration includes DNS, connection setup, network, load-balancer and sidecar queueing, and the client's own waiting for a free connection. If the client sees 900 ms and the server saw 80 ms, the problem is between them, not in the callee. Also, a request that timed out on the client may never have been counted by a server that was overloaded and dropped it, or may still be running on the server after the client gave up. Client-side metrics are therefore the true picture of what a caller experienced, while server-side metrics show the callee's own work. Collect both, label them clearly (peer.service on the client side), and compare.

11.3 Histograms and the percentile aggregation trap

Averages hide slow outliers, so latency is reported as percentiles: p50 (the median), p95, p99. In a microservice system, many instances each have their own percentiles, and here lies a classic mistake: you cannot average percentiles. Suppose instance A handled 9,000 requests with a p99 of 100 ms and instance B handled 1,000 requests with a p99 of 900 ms. The average of the two p99 values is 500 ms, which is meaningless: the true fleet p99 is somewhere near 100-200 ms or higher, depending on distributions, and the "average" matches nothing. Taking the max of p99 is also misleading. The same error happens when you roll up per-minute p99 values into an hourly value.

The correct approach is to aggregate histograms, not percentiles. Each instance records counts of requests falling into latency buckets (for example under 10 ms, under 50 ms, under 100 ms, under 500 ms, under 1 s, and so on). Buckets from all instances and all time windows can be added together, and the percentile is computed from the combined buckets afterwards (Prometheus does this with histogram_quantile over summed bucket rates). Pitfalls remain: percentiles are only as precise as the bucket boundaries (a p99 between 500 ms and 1 s is estimated by interpolation), so choose boundaries around your SLO threshold; and "summary" metrics that pre-compute quantiles in each process cannot be merged at all. Newer exponential (native) histograms and mergeable sketches such as t-digest or DDSketch give better accuracy without hand-chosen buckets.

The last line of that diagram is worth understanding: if each of 20 downstream calls is slow on 1 percent of requests and they are independent, the chance that at least one is slow is 1 minus 0.99 to the power 20, about 18 percent. This tail-latency amplification is why fan-out architectures need tight per-service latency objectives and why p99 of a service is more important in a deep graph than in a monolith.

11.4 Cardinality explosion in metrics

In a time-series database such as Prometheus, every unique combination of metric name and label values is a separate time series held in memory and indexed. Adding a label multiplies the series count by its number of values. A request counter with labels service (100), endpoint (30), status (6), method (5) yields 100 x 30 x 6 x 5 = 90,000 series, which is fine. Add user_id with a million users and you create up to 90 billion series: memory exhausts, queries time out, and the bill explodes. Common culprits are user or order IDs, raw URLs with embedded IDs, error message strings, pod names in long-churn deployments, and unbounded tenant IDs.

  • Rule: labels must have a small, bounded set of values. Put unbounded identifiers in logs and trace attributes instead.
  • Controls: enforce a per-service series budget, reject or drop labels at the collector, alert on series growth, and review new metrics in code review.
  • When per-tenant visibility is essential, use a bounded label such as tenant tier, track the top N tenants only, or rely on exemplars and logs for the specific tenant.

12. Exemplars: linking metrics to traces

A latency histogram tells you that 1 percent of requests take over 2 seconds, but not which requests. An exemplar is a sample attached to a metric data point: when the service records an observation into a histogram bucket, it can also attach the current trace_id as an exemplar for that bucket. In a dashboard such as Grafana, the latency graph shows small dots on the high-latency buckets; clicking one opens that exact trace. This closes the biggest gap between the three signals: you no longer guess a trace to look at, you click one that is provably in the slow bucket.

Two caveats. First, the linked trace must still exist: if it was not sampled or has been expired, the link is dead, so record exemplars only for sampled traces (or sample the exemplar-bearing ones preferentially). Second, only a few exemplars are kept per series, so they are illustrative samples, not a complete list.

13. Dependency maps, per-service SLOs, dashboards and ownership

13.1 Service dependency maps

A service map is a graph of services (nodes) and calls between them (edges), annotated with request rate, error rate and latency per edge. It is generated automatically from trace data (each client span to server span pair is an edge), or from mesh telemetry (Chapter 50). Its uses are practical: during an incident, you see which downstream is red and whether the red propagates upstream; during design review, you spot an unexpected dependency, a cycle, or a shared database; during a migration, you see who still calls the old API. Because it comes from live traffic, it stays accurate where hand-drawn architecture diagrams rot. Its limits: rarely called paths are missing in short windows, and sampling can hide edges.

13.2 Per-service SLIs and SLOs

Each service should publish its own SLIs (measurable indicators, such as the fraction of requests answered successfully under 300 ms) and own SLOs (targets, such as 99.9 percent over 30 days). Chapter 54 covers the mechanics and error budgets. What matters in a microservice context:

  • Serial dependencies multiply availability. If an endpoint calls five services in sequence and each is 99.9 percent available, the endpoint is at best 0.999 to the fifth, about 99.5 percent. So a service's SLO must be tighter than the product's SLO that depends on it, or the dependency must be optional (degrade gracefully, use a fallback or cache).
  • Measure from the consumer's view. Set the SLI on what callers see (client-side or load-balancer measurement), not only on the service's own view, which misses failures where requests never arrive.
  • User journey SLOs on top. Per-service SLOs are not enough; define a few SLOs for critical journeys such as "checkout completes", measured at the edge, and use traces to attribute misses to services.
  • Internal contracts. A published SLO is a contract between teams; if payment depends on fraud, fraud's latency SLO should be agreed and visible to payment.

13.3 Dashboards

Standardize dashboards, because a different layout per team makes cross-team incidents slow. A common structure has three levels: a global overview (golden journeys and their SLO burn, top-level error rate), a service template dashboard generated for every service (RED, saturation, dependencies, deploy markers, with a service selector), and deep-dive pages for the team's specifics. Keep each dashboard answering a question; ten graphs that all say "CPU" are noise. Include links that jump straight to filtered logs and traces for the same service and time range.

13.4 Ownership

Every service needs a named owner team, an on-call rotation, a runbook, and its dashboards and alerts linked together in a service catalog (for example Backstage or an internal registry). That catalog also supplies the metadata used to route alerts and to label logs and metrics (team, tier, oncall). Without clear ownership, an alert fires and nobody knows whom to page. See Chapter 53 for on-call and ownership practices.

13.5 Health and synthetic checks

  • Liveness says whether the process should be restarted; readiness says whether it should receive traffic; a startup check protects slow starts. Keep these shallow: if readiness checks the database and the database blips, every pod goes unready at once and a small problem becomes a total outage. Check critical dependencies in a separate, informational deep health endpoint.
  • Synthetic checks (also called probes or canaries) are scripted fake users that run a critical journey every minute from outside, for example log in, add to cart, check out in a test account. They find outages when there is no real traffic (night, new region) and verify the whole path including DNS, certificates and the CDN. They are useful as black-box alerts: if the synthetic journey fails, users are likely affected whatever your internal dashboards show.

14. Deploy markers and change correlation

The majority of incidents are caused by change: a new deployment, a configuration flip, a feature flag toggle, a schema migration, an infrastructure change. With many teams deploying independently several times a day, "what changed just before it broke?" becomes the first and most productive question. To answer it, record every change as an event and overlay it on graphs.

  • The CI/CD system emits an event on each deploy, flag change and config push, with service, version, time, author and a link to the diff. Dashboards draw these as vertical lines (deploy markers) on every graph of that service.
  • Telemetry carries the service.version resource attribute, so you can break down errors and latency by version. During a canary or progressive rollout (Chapter 53), comparing version 2.14 against 2.13 side by side is the fastest regression detector there is, and can be automated to halt or roll back a rollout.
  • A central change feed (one searchable timeline of all changes across all teams) lets the incident responder see that the pricing team deployed at 09:12 and the problem started at 09:13, even though the symptom is in checkout.

Correlation is not causation, so treat the marker as a lead to test, not proof. But a policy of "first, check what changed" resolves a large share of incidents within minutes.

15. Alerting for microservices

The principles of good alerting are in Chapter 54: alert on symptoms users feel, page only when a human must act now, and tie alerts to SLOs with burn rates. The distributed-system twist is that failure travels, so one root cause can trigger dozens of alerts.

15.1 Symptom over cause

Page on "checkout success rate below SLO" or "p99 latency of the API over its threshold for 5 minutes", measured at the edge, not on "CPU on payment pod above 80 percent". Cause-level signals (CPU, queue length, pod restarts) belong on dashboards and as low-urgency tickets, used for diagnosis. A service can be unhealthy without hurting users (redundancy absorbs it), and paging for that causes fatigue.

15.2 Alert storms

When a core dependency fails, every service that calls it, and every service that calls those, may alert at once. Fifty pages for one fault buries the one alert that names the cause and wastes the time of fifty people. Techniques to prevent this:

  • Page at the edge, ticket at the middle. Only user-facing symptoms and a few critical backends page. Internal services alert at lower urgency unless they directly threaten their own SLO.
  • Dependency-aware suppression (inhibition). If the database alert is firing, suppress the alerts of services that depend on it. Alertmanager's inhibit rules and similar features do this, using the dependency data from your service catalog.
  • Grouping. Combine alerts that share a label (cluster, dependency, incident) into a single notification, with a short grouping delay so that the first burst arrives as one message.
  • Distinguish your fault from an upstream's. Alerts should say whether errors come from the service itself or from a dependency (error type, peer service label), so a team can immediately hand off.
  • Hold-down and burn-rate windows. Require the condition to last long enough to be real, and use multi-window burn-rate alerts (a fast window and a slow window) instead of thresholds on single data points.
  • Circuit breakers and timeouts that fail fast reduce the cascade in the first place, so there are fewer symptoms to alert on (Chapter 47).

15.3 Ownership routing

Every alert carries a team label (from the service catalog) and a route sends it to that team's pager, chat channel and runbook. Cross-cutting incidents get an incident commander and a shared channel, with the alert system adding a link to the service map, the change feed, and the relevant dashboards. Alerts without an owner are a defect to fix.

16. Observing asynchronous flows and sagas

Synchronous requests end when the caller gets an answer. Asynchronous flows, and especially sagas (multi-step business transactions made of local transactions and compensating actions, see Chapter 48), may run for seconds, minutes or days, cross many queues, and fail halfway. Plain request metrics do not capture them. Several things are needed.

  • A business correlation ID. Alongside the trace ID, give each saga instance (for example an order) an ID that every step and every message carries, in headers and in every log line. Traces may be sampled, split by links, or expired; a business ID in logs lets you reconstruct the saga even without a trace.
  • Saga state as data. Persist each saga's current step and history in a state table or event log (an orchestrator holds this naturally). Then you can query "how many sagas are stuck in PAYMENT_PENDING for more than 10 minutes?", which is a metric no request counter can produce.
  • Flow-level metrics: sagas started, completed, compensated and failed; duration from start to completion (as a histogram); count by current step; age of the oldest in-progress saga; compensation rate (a rising compensation rate is an early warning of trouble in a downstream).
  • Queue health: consumer lag and age of the oldest message per consumer group (more informative than depth alone, since a deep queue that drains quickly is fine); dead-letter queue (DLQ) size and arrival rate, which must alert; redelivery count and processing duration per message.
  • Stuck-flow detection: a timer-based job or alert for "a saga did not progress within its expected time". Absence of an event is invisible to ordinary error alerts, so you must test for it explicitly.
  • End-to-end latency SLO for async journeys: for example "95 percent of orders are confirmed by email within 60 seconds of payment", computed from timestamps (event time versus processed time) carried in the message.

17. Cost, and platform versus team responsibility

Observability is often the second or third largest infrastructure cost after compute and storage, and it grows faster than traffic as services multiply. The main cost drivers and levers:

SignalWhat drives costMain levers
LogsGB ingested, indexed fields, retentionLevel discipline, drop and sample at the pipeline, tiering, label-only indexing (Loki), per-team quotas
MetricsActive time series (cardinality), scrape frequency, retentionBounded labels, series budgets, longer scrape intervals for low-value metrics, downsampling for old data, histograms with sensible buckets
TracesSpans per second, sampling rate, indexed attributes, retentionTail sampling, rate limits, index few attributes, short retention, object-storage backends
People and toolingVendor per-host or per-GB pricing, engineers maintaining pipelinesOpen standards (OTLP) for portability, a managed or self-run choice made on total cost

A useful principle: spend on signal, not volume. Ask for each stream what decision it supports. Data that nobody has queried in 90 days is a candidate for deletion.

17.1 Who owns what

If every team builds its own pipeline, you get fifty incompatible systems; if a central team does everything, it becomes a bottleneck that cannot understand each service. The usual split is:

  • Platform team provides the paved road: the telemetry pipeline (collectors, Kafka, storage), the standard libraries or agent images with tracing and logging preconfigured, a log schema, naming conventions, the dashboard templates, the alerting platform, cost reporting, quotas, security redaction, and documentation. The goal is that a new service gets decent observability with zero effort.
  • Service teams own the meaning: which business spans and attributes to add, their service's SLIs and SLOs, alert rules and thresholds, runbooks, dashboards for their domain, log quality and volume, and responding to their pages.
  • Shared contract: the platform enforces minimum standards (required fields, bounded labels, trace propagation) through libraries and CI checks, and teams are accountable for staying within quotas.

18. Worked example: debugging a checkout incident

The scenario: it is Tuesday 09:20. A page arrives: "Checkout success SLO fast burn: p99 latency 7.4 s, error rate 4 percent". The platform has about 60 services; checkout involves the gateway, order, inventory, pricing, payment, fraud, and an external card network. We follow the three-step method: metrics to find where, traces to find which hop, logs to find why.

18.1 Step by step

  1. Confirm and scope with metrics. The edge dashboard shows p99 at 7.4 s (normal 900 ms) and errors at 4 percent, starting 09:13. Breaking down by endpoint shows only POST /orders is affected; GET /products is fine, so it is not a global network or gateway problem. Breaking down by region and tenant shows all regions and all tenants: not an isolated zone or customer.
  2. Find the offending service with the service map and per-service RED. On the service map, edges into payment are red, and the fraud edge is amber; inventory and pricing are green. Payment's server-side p99 rose from 400 ms to 6 s; the order service's client-side latency to payment matches it. Payment's saturation shows its thread pool near full, which is a consequence of slow calls, not a cause.
  3. Check what changed. The deploy markers on payment's graphs show version 2.14 rolled out at 09:12. Breaking latency down by service.version confirms it: pods on 2.14 have p99 near 7 s while the still-unfinished rollout's remaining 2.13 pods are at 400 ms. The strongest lead is already in hand, and rolling back could begin now (mitigation first, diagnosis second).
  4. Open a trace through an exemplar. Clicking an exemplar dot in the slow bucket of payment's latency histogram opens one trace. The waterfall (section 7) shows the payment charge span at 5.5 s, containing a card network call that ended at exactly 3.0 s with a timeout, then a second attempt that succeeded after 1.9 s. Fraud scoring took only 0.6 s. The critical path is the timed-out call plus the retry. We now know which hop and which pattern, a timeout followed by a retry.
  5. Explain with logs. Searching logs for that trace_id across all services returns a handful of lines. The payment service logged event=card_charge_retry, error.type=UpstreamTimeout, timeout_ms=3000, attempt=1, and its startup log showed card_client.timeout_ms=3000 in the config for 2.14, versus 10000 before. A search on the event field for the last hour shows the retry events spiking from 09:13 across all pods of v2.14.
  6. Mitigate, then fix. Roll back payment to 2.13 (or flip the config flag if configuration is separated), watch p99 return in the dashboard, and resolve the page. Retries from the card network slowdown are visible in the card client's dependency metrics, which prove the external service was slower than usual but within the old 10 s timeout.
  7. Learn. Follow-ups: review timeouts and retry budgets (retry amplification: with 3 attempts at 3 s, the worst case is 9 s plus backoff, which exceeds the order service's own timeout, so retried work continues after the caller has given up); add an alert on retry rate per dependency; add a canary gate that compares error and latency by version before completing a rollout.

Notice what made it fast: standard dashboards per service, deploy markers, version labels, exemplars linking metrics to traces, a trace ID in every log line, and a shared log schema. Remove any one and the investigation gets slower. Remove all and it becomes hours of grepping unrelated logs.

Worked numbers Time to detect: about 3 minutes (fast burn alert). Time to localize to payment: about 4 minutes. Time to a rollback decision: about 8 minutes from the page. Customer impact window: 09:13 to 09:31, so around 18 minutes, with about 4 percent of requests failing during peak at, say, 600 checkouts per minute, roughly 24 failed checkouts per minute and about 430 in total, which fits inside a 99.9 percent monthly budget only partly (see Chapter 54 for the arithmetic).

19. Interview Q&A

Why is debugging harder in microservices than in a monolith, and what is the minimum you need to fix that?

In a monolith the whole request runs in one process, so one log and one stack trace tell the story. In microservices a request crosses many processes, machines and queues, each with its own logs, clocks and owners, and failures cascade, so the service that shows symptoms is rarely the cause. The minimum is a request or trace ID created at the edge, propagated through every call and message, and attached to every log line. Beyond that you add distributed tracing to see structure and timing, and standard per-service metrics to see where the problem sits. Without propagation everything else is much less useful.

How does trace context propagate, and what breaks it?

The caller writes the trace ID, its own span ID and the sampled flag into the W3C traceparent header for HTTP, into metadata for gRPC, or into message headers for queues. The callee reads them and starts its child span with the same trace ID. It breaks when a service forgets to forward the headers, when a thread pool or async executor loses the context, when a proxy strips unknown headers, when a consumer does not restore the context from message headers, or when a service makes its own sampling decision instead of honouring the incoming one. A service mesh helps with network-level spans, but the application must still copy incoming context onto outgoing calls.

Explain head-based versus tail-based sampling and when you would choose each.

Head-based sampling decides at the root of the trace, usually with a fixed probability, and the decision travels downstream in the sampled flag. It is cheap and simple but blind to outcomes, so it throws away errors at the same rate as everything else. Tail-based sampling buffers a whole trace and decides after it ends, so it can keep all errors and slow traces, but it needs stateful collectors, trace-ID-aware routing and memory, and it still pays the cost of generating and shipping all spans. For small or low-traffic systems head sampling is enough. At scale, a common design is a modest head rate in the SDK to cap cost, plus tail sampling in a gateway collector tier that keeps all error and high-latency traces.

When would you use a span link instead of a parent-child relationship?

Parent-child fits a one-to-one synchronous or near-synchronous flow where the child's work is part of the parent's duration, and it gives one trace with a visible queue gap. A link fits when the relationship is not strictly nesting: a batch consumer handling messages from many producers, work that runs much later, or one event fanning out to many independent consumers. Forcing these into a single trace creates huge, hours-long traces that are slow to assemble and break tail-sampling windows. With links each unit of work keeps a bounded trace and you navigate between them by the link.

Why can you not average p99 latencies from different instances, and what do you do instead?

A percentile describes the shape of one distribution, so combining percentiles from instances with different traffic and different distributions produces a number that corresponds to no real set of requests. For example, a busy fast instance and a quiet slow one average to a value that is wrong for both. The correct approach is to have each instance export histogram bucket counts, add the counts across instances and time windows, and compute the percentile from the merged histogram at query time. You also pick bucket boundaries near your SLO thresholds for accuracy, or use mergeable sketches or native exponential histograms. End-to-end latency should come from the root span or an edge metric, not from combining per-service percentiles.

What is a cardinality explosion, and how do you prevent it for metrics, traces and logs?

Cardinality is the number of distinct values of a field. In a metrics system each unique label combination is a separate time series held in memory, so a label like user ID or raw URL multiplies the series count and can exhaust the database. Prevention is bounded label values, route templates instead of raw URLs, series budgets per service, and dropping or rejecting offending labels at the collector. Traces and logs tolerate high-cardinality fields because each record stores its own value, so put user IDs, order IDs and request IDs there, and in traces index only a few fields to limit cost. Exemplars and trace links connect the cheap metric to the detailed record.

How do exemplars help, and what are their limits?

An exemplar attaches a real trace ID to a metric data point, typically to a histogram bucket, so from a latency graph you can click a point in the slow bucket and open a trace that was actually slow. It removes the guessing step in moving from metrics to traces. The limits are that only a few exemplars are retained per series, the linked trace must still be stored (so link only sampled traces), and the metrics backend and client library must support them. They show examples, not complete lists.

How do you avoid an alert storm when a shared dependency fails?

First, page on user-facing symptoms measured at the edge or on SLO burn rate, and treat internal-service alerts as lower urgency, so only a few alerts can fire at once. Second, use dependency-aware inhibition so that when a database or shared service alert is active, alerts from its callers are suppressed, and group the remainder into a single notification by incident or dependency. Third, label alerts with the owning team and whether the error originated locally or from a peer, so routing is clear. Finally, fail-fast timeouts and circuit breakers reduce the cascade so fewer symptoms appear at all.

How would you observe a saga that spans several services and queues over minutes?

Give every saga instance a business ID that is carried in message headers and every log line, and keep trace context or links as a secondary tool since traces may be sampled or too long. Persist saga state, step and timestamps so you can query for sagas that are stuck longer than the step timeout, and export metrics: started, completed, compensated, failed, duration histogram, count by step and age of the oldest. Add queue signals, namely consumer lag, oldest message age, redeliveries and dead-letter queue growth, and alert when a saga makes no progress, because a missing event never raises an error by itself. Define an end-to-end SLO such as 95 percent of orders confirmed within 60 seconds.

What is the split of responsibility between a platform team and service teams for observability?

The platform team runs the telemetry pipeline and storage, ships standard libraries or agents that emit consistent traces, logs and metrics with the correct context propagation, defines the log schema and naming conventions, provides dashboard and alert templates, enforces quotas and redaction, and reports costs. Service teams decide what is meaningful for their domain: business spans and attributes, SLIs and SLOs, alert thresholds, runbooks, and the quality and volume of their logs, and they respond to their own pages. The platform makes the right thing the default path, while teams remain accountable for their service's signal quality and cost.

You get paged for high latency at checkout. Walk through your investigation.

I confirm scope from edge metrics (which endpoints, regions, tenants and versions are affected), then use the service map and per-service RED and client-side dependency metrics to find which service's latency rose. I check the change feed and version breakdown for recent deploys or flag changes, since that is the most common cause, and mitigate by rolling back if a candidate fits. To understand the mechanism I open a slow trace through an exemplar, find the critical path and self time, and look for gaps, retries and N+1 patterns. Then I read the logs for that trace ID to get the real error or configuration value, and finish with follow-ups such as alerts, timeout fixes and canary checks.

What should and should not go into logs in a multi-tenant microservice platform?

Logs should be structured JSON with a shared schema, including timestamp, level, service, version, environment, trace and span IDs, tenant ID, a stable event name or error code, and numeric fields such as duration. They should never contain credentials, tokens, full authorization headers, full card numbers, or personal data in clear text; use internal IDs or hashes, mask at the source, and redact centrally as a safety net. Request and response bodies should not be logged wholesale. Retention and access to logs should be limited, since logs are copied widely and are subject to privacy and compliance rules.

21. Recap

  • Microservices scatter one request over many processes; observability must reconstruct the path using shared identifiers and then relate it to per-service health.
  • Generate a correlation or trace ID at the edge and propagate it through HTTP headers, gRPC metadata and message headers, and into every log line. Preserve context across threads and queues.
  • A trace is a tree of spans with trace, span and parent IDs. Use the W3C traceparent header. Combine auto-instrumentation for coverage with manual spans for business meaning. OpenTelemetry provides the API, SDK, OTLP and the collector.
  • Sample to control cost: head sampling is cheap and blind, tail sampling keeps errors and slow traces but needs buffering and trace-ID routing. Do not compute rates from sampled traces.
  • Use parent-child for simple async hops and links for batches, delays and fan-in. Record queue wait time explicitly.
  • Debug by reading the waterfall: find the critical path, self time, gaps, retries and N+1 patterns.
  • Log structured JSON with trace_id, service, version, tenant and stable event names; ship through agents, a Kafka buffer, and Elasticsearch or Loki; control volume; never log secrets or personal data.
  • Metrics: standard RED, saturation and dependency metrics per service, both client-side and server-side; aggregate histograms, never percentiles; keep label cardinality bounded.
  • Exemplars link metric points to traces. Service maps, per-service SLOs, standard dashboards, ownership metadata, synthetic checks and deploy markers make triage fast.
  • Alert on symptoms, group and inhibit by dependency, route by owner. Observe sagas with business IDs, state tables, queue lag and DLQ alerts.
  • The platform team provides the paved road; service teams own meaning, SLOs and alerts. Detect with metrics, localize with traces, explain with logs.
