Failure, Time and Ordering

On one machine, a function call either returns or crashes, and "before" and "after" are decided by one clock. Across machines neither is true: calls vanish without a trace, clocks disagree, and nobody can say for certain which of two events happened first. This chapter explains why, and then builds the tools (failure detectors, logical clocks, version vectors, bounded-uncertainty time) that real systems use to reason about it anyway.

1. Why distributed systems are different

A program on one computer lives in a comfortable world. If it calls a function, one of two things happens: the function returns a result, or the whole process dies, and then nobody is left to be confused. All the threads read the same memory and the same clock. If you ask "did operation A happen before operation B?", there is an answer, because the hardware gives every instruction a place in one sequence.

A distributed system is a set of machines that cooperate by sending messages over a network. Three facts about that setting break the comfortable assumptions, and nearly every topic in the rest of this module (Chapter 28 on CAP and consistency, Chapter 29 on consensus, Chapter 24 on replication) is a response to one of them.

1.1 Partial failure

On one machine, failure is mostly all-or-nothing. In a distributed system, part of the system can fail while the rest keeps running. One node loses power while nine others are fine. One network cable is cut. One process is stuck in a long garbage-collection pause. This is called partial failure, and it is the defining difficulty: the surviving parts must continue to make correct decisions without knowing exactly what the failed part did or is doing. Worse, failures are often nondeterministic: the same request might succeed now and fail a second later, which makes them hard to reproduce and test.

1.2 Unreliable networks

The network lets you send a message but promises almost nothing about it. A message may be lost, delayed for an arbitrary time, delivered twice, delivered out of order, or corrupted (usually detected by checksums). TCP hides some of this by retransmitting lost packets and ordering bytes inside a single connection, but TCP cannot rescue you if the connection itself breaks, if the other side crashes after receiving data but before acting on it, or if a middlebox silently drops state. Every layer above TCP still has to assume that any request or response can disappear.

1.3 No shared clock, no shared memory

Each machine has its own hardware clock, a quartz crystal that counts oscillations. Crystals run at slightly different speeds, so clocks drift apart; protocols such as NTP pull them back together, but only to within some error, and that error is not zero. There is also no shared memory: machine A cannot look at machine B's state, it can only send a message and wait for a reply, and the reply describes the past. By the time it arrives, B's state may have changed.

Key idea A distributed system is defined by what you cannot assume: you cannot assume a call returns, you cannot assume a lost message was not processed, you cannot assume two clocks agree, and you cannot assume the answer you received is still true. The craft of the field is designing protocols that stay correct under those uncertainties, and being honest about the guarantees that remain.

Interviewers like this topic because it is where hand-waving gets exposed. "We will just use timestamps to pick the latest write" and "we will retry on timeout" both sound reasonable and both cause real data loss, as sections 6 and 3 will show.

2. Fault types and network partitions

To reason about failures, we classify them by how badly the failed component misbehaves. A protocol designed for a mild fault model is simpler and faster; a protocol designed for a harsh model costs more. You should always say which model you assume.

Blockchains and systems spanning mutually distrusting parties are the main places where Byzantine tolerance is worth paying for. Slow nodes deserve special attention, because they are the most common real-world fault and the hardest to distinguish from a dead one (section 3.2).

2.1 Network partitions

A network partition is a failure of the network (not of any node) that splits the machines into groups that can each talk internally but not across the split. Each side is alive and healthy; each side thinks the other side died. Partitions in the wild are rarely a clean cut in half. They are asymmetric (A can reach B but B cannot reach A), partial (A reaches B and C, but B cannot reach C), or intermittent (flapping). Causes include a failed switch, a misconfigured firewall rule, a congested link dropping heartbeats, a bad deployment of a routing change, or cross-region links breaking.

The dangerous outcome of a partition is split brain: both sides conclude the leader is gone, both elect a new leader, and both accept writes that later conflict. Defences are majority quorums (only a side with more than half the nodes may proceed), fencing tokens (section 4.3), and leases that expire.

Watch out Partitions are not exotic. Large operators report that network faults (including partial and brief ones) are among the most frequent causes of serious incidents. "The network is reliable" is the first of the classic fallacies of distributed computing. Design as if partitions will happen, because they will, and decide in advance what each side does.

3. The two generals problem, timeouts, and slow versus dead

3.1 The two generals problem

Two armies, led by two generals, sit on opposite hills with an enemy in the valley between them. They will win only if both attack at the same time; if only one attacks, it loses. They can communicate only by sending messengers through the valley, and any messenger may be captured. General 1 sends "attack at dawn". If General 2 receives it, should General 2 attack? Only if General 1 knows the message arrived. So General 2 sends an acknowledgement. But now General 2 does not know if the acknowledgement arrived. General 1 could acknowledge the acknowledgement, and so on forever: no finite number of messages can make both generals certain that the other will attack.

The result is a proof that no protocol can guarantee agreement over a channel that may lose messages if the answer has to be certain after a bounded number of steps. This is why distributed systems never promise "exactly-once delivery" at the network level: that would require solving the two generals problem. What systems do instead is accept the uncertainty and engineer around it: they repeat messages until acknowledged (at-least-once) and make repeats harmless (idempotency, Chapter 32), or they accept possible loss (at-most-once). Real consensus protocols (Chapter 29) reach agreement not by beating this proof but by assuming messages are eventually delivered if you keep retrying, and by tolerating a minority of failures.

3.2 Timeouts and why slow looks like dead

You send a request and wait. Nothing comes back. What happened? There are at least four possibilities, and from the caller's side they are indistinguishable: the request was lost on the way; the server crashed before processing it; the server processed it and crashed before replying; the server processed it and the reply was lost or is merely slow. The only evidence you have is silence.

This leads to a fundamental limit: in an asynchronous network (no upper bound on delay) you cannot distinguish a crashed node from a very slow one. A timeout is therefore only a guess. If you set it too short, you declare healthy but slow nodes dead, trigger needless failovers, and in the worst case cause a cascading failure: a slow node is declared dead, its load moves to the others, they become slow, and are declared dead in turn. If you set it too long, real failures take long to notice and users stare at spinners.

Practical guidance for timeouts:

  • Derive the timeout from measured latency, for example a little above the 99.9th percentile of healthy latency, not from a round number.
  • Use deadlines, not just per-hop timeouts. A request carries a total time budget; each downstream call gets what remains, so a chain of three services cannot silently multiply the wait.
  • Retry with exponential backoff and jitter, and only for idempotent operations or with an idempotency key. Without jitter, thousands of clients retry in lockstep and hammer a recovering server.
  • Treat a timeout as "unknown", not "failed". Before retrying a write, you either need idempotency or a way to ask "did my earlier attempt apply?".

4. Failure detectors

Since certainty is impossible, systems use a failure detector: a component that gives each node a running opinion on which peers are alive. Its output is a suspicion, and it can be wrong in two ways: false positives (suspecting a node that is actually fine) and false negatives (not yet suspecting a node that already died). Detectors are judged on completeness (every crashed node is eventually suspected by everyone) and accuracy (healthy nodes are not wrongly suspected). You cannot maximise both at once in an asynchronous network, so you tune the tradeoff.

4.1 Heartbeats

The simplest design: each node sends a small "I am alive" message to a monitor every interval (say, every second), or the monitor pings each node. If no heartbeat arrives within a timeout (say, 5 intervals), the node is suspected. This is cheap and easy, but a fixed timeout is brittle: it is wrong whenever network latency changes, for example during a busy period.

4.2 Adaptive detection: phi accrual

The phi accrual failure detector (used by Cassandra and Akka) replaces the yes/no answer with a continuous number. It keeps a history of recent heartbeat arrival intervals for each peer, models their distribution, and computes phi, a value that grows the longer the current silence is compared to the normal pattern. Phi of 1 means roughly a 10 percent chance the silence is normal; phi of 8 means roughly a one in 100 million chance. Each application picks the threshold it wants (Cassandra's default is around 8). The point is that the detector adapts: on a jittery network the learned distribution is wide, so it waits longer before suspecting, and on a stable network it reacts fast.

4.3 Gossip-based detection and what to do with a suspicion

A central monitor is itself a single point of failure and does not scale. Large clusters let nodes gossip: each node periodically tells a few random peers what it knows about everyone else's liveness, so a failure rumour spreads to the whole cluster in a logarithmic number of rounds. Variants such as SWIM add indirect probes: before suspecting node X, node A asks several other nodes to ping X on its behalf, which filters out failures that are just a broken A-to-X link. The mechanism, along with anti-entropy via Merkle trees, is covered in Chapter 33.

A suspicion is only an opinion, so what you do with it matters. Never let a suspected node's old authority linger:

  • Leases. A node holds a lock or leadership only for a bounded time (for example 10 seconds) and must renew it. If it is paused and the lease expires, others may take over.
  • Fencing tokens. Each time a lock or leadership is granted, the coordinator issues a monotonically increasing number. The protected resource (a database, a file store) rejects any request carrying a number lower than one it has already seen. Then a zombie leader that wakes up after a long pause cannot corrupt data, because its token is stale. This is how you stay safe even when the failure detector was wrong. (More in Chapter 30.)

5. Physical clocks: drift, skew, NTP, leap seconds

Every computer has a hardware clock built from a quartz crystal. The operating system turns its oscillations into a count of time. Two terms describe how two such clocks disagree:

  • Drift is the rate difference. A typical server crystal gains or loses on the order of tens of parts per million (commonly quoted as around 10 to 200 ppm depending on temperature and quality). At 50 ppm that is 50 microseconds per second, or roughly 4 seconds per day. Temperature and load change the rate.
  • Skew is the offset between two clocks at one instant: "machine A reads 12:00:00.000 while machine B reads 12:00:00.037, so the skew is 37 ms". Drift is what makes skew grow over time.

5.1 NTP and its limits

The Network Time Protocol (NTP) keeps clocks roughly synchronised. A client asks a time server for its time, records when it sent the request and when the reply came back, assumes the network delay was symmetric (half each way), and estimates its own offset. It does this against several servers and discards outliers. Servers are organised in strata: stratum 0 is a reference such as a GPS receiver or atomic clock, stratum 1 servers are attached to it, and so on down.

On a good data-center network NTP typically keeps clocks within a few milliseconds; across the public internet the error can be tens or even hundreds of milliseconds. The protocol's limits are important for design: the symmetry assumption is often false (congestion on only one direction), the sync happens only every few minutes so drift accumulates in between, and a misconfigured, firewalled, or failed time source can leave a machine wrong by seconds or more without any alarm. NTP also corrects in two ways: it can slew (gradually speed up or slow down the clock until it matches) or, if the error is large, step (jump immediately), and a step can move the clock backwards. For tighter bounds, the Precision Time Protocol (PTP) with hardware timestamping reaches microseconds, and cloud providers now offer GPS or atomic clock backed time services.

5.2 Leap seconds

The Earth's rotation is slightly irregular, so UTC occasionally inserts a leap second, making one minute 61 seconds long (23:59:60 exists). Software that assumes a minute has 60 seconds can crash, loop, or see time go backwards or repeat. Several well-known outages were caused by leap seconds. Large operators avoid the problem by smearing: spreading the extra second over many hours so the clock never shows 23:59:60 and never steps. The lesson is that even wall-clock time is not monotonic or uniform.

5.3 Wall clocks versus monotonic clocks

6. Why timestamps lie

It is tempting to say "each write gets the time it was made, and the write with the latest time wins". This policy is called last write wins (LWW), and several real databases (Cassandra by default, DynamoDB global tables, many caches) offer it because it is simple and needs no coordination. But it is only as trustworthy as the clocks behind it, and clocks are untrustworthy in several specific ways.

6.1 Four ways a timestamp misleads

  1. Clock skew between machines. Node A's clock is 300 ms ahead of node B's. A user updates a record via B at real time 100 ms later than an update via A, but B stamps it with an earlier number, so the newer write loses.
  2. Clocks stepping backwards. After an NTP step, a node produces timestamps lower than ones it created earlier, so its newest write may lose to its own older one.
  3. Process pauses. A thread reads the clock, then is paused by a stop-the-world garbage collection, an OS scheduler delay, a container CPU throttle, or a VM live migration, and acts seconds later. Its timestamp or lease check is now stale. A classic bug: a client checks "my lease has 8 seconds left", then pauses for 15 seconds, then writes believing it still holds the lease.
  4. Low resolution and ties. Two writes within the same millisecond receive the same timestamp, and the tie-break (often arbitrary, such as by value) silently drops one.
Watch out LWW does not just risk picking the "wrong" winner in a close race: it also silently discards the loser with no error and no record. Concurrent writes that should have been merged (two people adding different items to a cart) lose data. Worse, a node whose clock is far in the future can write values that will beat every correct write for a long time, because nothing can overwrite a timestamp from the future until real time catches up.

Can you fix this by synchronising clocks better? Only partially. Even with a tight bound, two events that happen within the error bound of each other cannot be ordered by timestamp. Systems that need a true order therefore either avoid physical time for ordering (logical clocks, sections 7 to 9), or make the uncertainty explicit and wait it out (TrueTime, section 10). The worked example in section 14 shows a concrete lost update caused by LWW and its fix.

7. Logical time: happens-before and Lamport clocks

Leslie Lamport's key insight (1978) was that for most purposes we do not need to know when something happened in wall-clock terms. We need to know the causal order: could event A have influenced event B? Causality needs no clock at all, only the knowledge of what information could have flowed where.

7.1 The happens-before relation

Define the relation "A happens before B", written A → B, by three rules:

  1. If A and B occur on the same process and A comes first in that process's local order, then A → B.
  2. If A is the sending of a message and B is the receipt of that same message, then A → B.
  3. It is transitive: if A → B and B → C then A → C.

If neither A → B nor B → A, the events are concurrent (written A ∥ B). Concurrent does not mean "at the same instant"; it means "no chain of messages connects them, so neither could have known about the other". If A → B, then A might have caused B. If they are concurrent, neither caused the other and the system is free to order them either way, but must be careful not to lose either.

7.2 Lamport clocks

A Lamport clock is a single integer counter kept by each process, giving every event a number that respects happens-before. The rules:

  1. Start the counter at 0.
  2. Before each local event (including sending a message), increment the counter by 1. The event's timestamp is the new value.
  3. When sending a message, attach the current counter value to it.
  4. When receiving a message with timestamp m, set the counter to max(local counter, m) + 1. That is the crucial step: the receiver jumps past anything the sender had seen, so the receive is ordered after the send.

Guarantee: if A → B then L(A) < L(B). Read the arrow only one way. The converse is false: L(A) < L(B) does not tell you A happened before B, because they might be concurrent and simply have drawn counters that happen to be ordered. Lamport timestamps can be turned into a total order by breaking ties with the process id: order by (counter, process id). Every node computes the same total order without coordination, and that order is consistent with causality. But it is arbitrary for concurrent events, and it cannot detect concurrency.

Check understanding with one more point: P3's local event (1) and P1's send m1 (2) have 1 < 2, yet they are concurrent: no message links them. That is exactly the limitation vector clocks remove. You can try this yourself in the stepper widget in section 13.

8. Vector clocks and detecting concurrency

A Lamport clock compresses the entire causal history of an event into one number, and that loses information. A vector clock keeps more: each process maintains an array with one counter per process, [c1, c2, ..., cn]. Entry ci means "the number of events of process i that I know about (that are in my causal past)".

8.1 Rules

  1. Each process starts with all zeros.
  2. On a local event at process i: increment its own entry, vi[i] += 1.
  3. On sending: do the local-event step, then attach a copy of the whole vector.
  4. On receiving a vector m: set each entry to max(own[k], m[k]), then increment its own entry (the receive is itself an event).

8.2 Comparing two vectors

Given the vectors of events A and B:

  • A happened before B (A → B) if every entry of A is less than or equal to the matching entry of B, and at least one is strictly less.
  • B happened before A if the reverse holds.
  • They are identical if all entries are equal (the same event or a copy).
  • Otherwise, each has some entry larger than the other: the events are concurrent (A ∥ B).

This is the property Lamport clocks lack: vector clocks are exact. A → B if and only if V(A) < V(B). That means they can reliably tell a system "this update is a descendant of that one, keep the newer" versus "these two updates are siblings that neither saw, so you must merge or preserve both".

8.3 Cost and limits

The vector has one slot per process, so its size grows with the number of participants. For a handful of replicas that is fine; if every client or short-lived process gets a slot, the vectors grow without bound and need pruning (which can reintroduce errors) or a switch to per-replica identifiers (next section). Vector clocks also tell you that two versions are concurrent, but not how to merge them. That decision belongs to the application or to a data type designed to merge automatically (section 12).

9. Version vectors, dotted version vectors and hybrid clocks

9.1 Version vectors: causality for replicated data

Vector clocks order events in a message-passing computation. Replicated storage has a related but slightly different need: ordering versions of a data item that live on several replicas. A version vector has the same shape and the same comparison rules as a vector clock, but its entries count updates accepted by each replica for that one item, and it is attached to the item (and to each client read) rather than to every message. The flow is:

  1. A client reads key cart and gets the value along with its version vector, say {A:2, B:1}. This vector is the causal context: "this is everything I have seen".
  2. The client modifies the value and writes it back, sending the context it read.
  3. The replica that accepts the write increments its own entry, producing {A:3, B:1}. Since the new vector dominates the context the client supplied, this write is a descendant that replaces the old version.
  4. If a different client wrote concurrently to replica B, producing {A:2, B:2}, then {A:3, B:1} and {A:2, B:2} are concurrent. Neither dominates, so the store keeps both as siblings and returns both on the next read, so the application can merge them.

9.2 Dotted version vectors, briefly

Plain version vectors have a subtle weakness when replicas, not clients, are the identities: two clients writing through the same replica without having seen each other's writes can end up with the second write wrongly replacing the first, or the system can generate more and more siblings ("sibling explosion"). The cause is that the vector entry "A:3" conflates "I have seen A's first three events" with "this specific write is A's third event".

A dotted version vector (DVV) separates the two. It stores the causal context as an ordinary vector, plus one extra dot, a single pair such as (A, 4), naming exactly the event that created this version. When comparing, a write replaces exactly the versions that its context covers, and any version whose dot is not covered by the writer's context remains as a sibling. The result is precise sibling tracking with a vector that stays the size of the number of replicas. Riak adopted dotted version vectors for this reason. For an interview, remember the one-line summary: a dot names the single event; the vector says what was seen.

9.3 Hybrid logical clocks (HLC)

Logical clocks respect causality but have no relation to real time, so you cannot ask "show me the state as of 3 pm" or expire a record after 24 hours. Physical clocks have meaning but can skew or step back. A hybrid logical clock combines them. Each timestamp is a pair (l, c):

  • l is the largest physical time the node has seen, either its own wall clock or one received in a message. It stays close to real time.
  • c is a small counter used only to break ties when l does not advance (many events within one millisecond, or the wall clock stepped back).

On a local or send event: take pt as the node's current wall time. If pt is greater than l, set l = pt and c = 0; otherwise keep l and increment c. On receiving a timestamp (lm, cm): set l to the maximum of the old l, lm and pt; if that maximum equals one or both of the old values, set c to one more than the larger matching counter, otherwise set c = 0. Timestamps compare lexicographically: first by l, then by c.

What you get: the Lamport guarantee (if A → B then HLC(A) < HLC(B)), a value that is within the clock skew bound of real wall time (so time-based queries and TTLs make sense), and compactness (fits into 64 or 96 bits, no per-node vector). What you do not get is concurrency detection: like Lamport clocks, HLC gives an order consistent with causality but cannot prove two events were concurrent. CockroachDB and MongoDB use hybrid logical clocks for exactly this reason: a causally consistent, time-meaningful timestamp without special hardware.

10. TrueTime and bounded uncertainty (Spanner commit-wait)

Google Spanner takes a different approach: instead of avoiding physical time, it makes the uncertainty explicit and small. Each data center has time-master machines equipped with GPS receivers and atomic clocks, and every server regularly syncs with them. The TrueTime API does not return a single time. It returns an interval: TT.now() gives [earliest, latest], with the guarantee that the true absolute time lies somewhere inside. The interval half-width, called ε (epsilon), is typically a few milliseconds (the published figures are in the range of about 1 to 7 ms) and it grows between synchronisations.

Spanner wants external consistency: if transaction T1 commits (and the client is told so) before T2 begins, then T2 must get a larger commit timestamp than T1, in true real-time order, across the whole planet. Using timestamps this way is dangerous if clocks are uncertain, so Spanner adds commit-wait:

  1. When a transaction is ready to commit, the coordinator picks a commit timestamp s no smaller than TT.now().latest. Since the true time is at most latest, s is not in the past.
  2. The coordinator then waits until TT.after(s) is true, meaning TT.now().earliest is greater than s, so s has definitely passed in real time everywhere.
  3. Only then does it make the commit visible and acknowledge the client.

Any transaction that starts after this acknowledgement will pick a timestamp greater than s, because its own latest is greater than the true time, which already exceeds s. Real-time order and timestamp order are therefore guaranteed to agree. The cost is the wait, on the order of 2ε, so a few milliseconds up to roughly ten. The design trades a small latency tax for a global total order with no coordination message between unrelated transactions. Reducing ε (better clocks) directly improves commit latency.

You can approximate the idea without special hardware, but the bound is looser. CockroachDB, for example, assumes a configured maximum clock offset and uses uncertainty intervals: when a read sees a value stamped within the uncertainty window of its own timestamp, it cannot tell whether that write came earlier, so it restarts the read at a later timestamp. Cloud providers now also offer time services with microsecond-scale bounds. The principle is the same: bound the error, then either wait it out or retry.

11. Total order, partial order, and ordering guarantees in practice

11.1 Partial versus total order

A total order ranks every pair of events: for any A and B, either A is before B or B is before A. A partial order ranks only some pairs; the others are incomparable. Happens-before is a partial order, and that is honest: concurrent events really have no order. Total orders are easier to program against (everyone agrees on one history, like entries in a bank ledger) but cost more, because manufacturing a total order means making independent events agree, which requires coordination. The cheapest total orders (Lamport timestamps with tie-breaks) are arbitrary for concurrent events, which is fine for some uses (unique ordering of mutex requests) but not for others (deciding whose bank withdrawal succeeded, which needs the order everyone agrees on and that matches what clients observed, a consensus problem, Chapter 29).

Between these sits causal ordering (or causal consistency): every node sees causally related events in the same order, while concurrent ones may appear in different orders at different nodes. For example, if you post a question and someone posts a reply, no replica should ever show the reply without the question. Causal consistency needs only metadata (vectors or HLC-derived dependencies) and no global coordination, which is why it is the strongest consistency that stays available during a partition. The full consistency hierarchy is in Chapter 28.

11.2 Ordering guarantees you actually get

In practice, engineers do not carry vector clocks everywhere. They choose a scope within which order is guaranteed, and give up order outside it.

  • Per-key ordering. All operations on one key (one user, one order id, one account) are routed to the same partition or leader, which processes them in arrival order. Different keys proceed in parallel with no order between them. Kafka guarantees order within a partition and messages with the same key land in the same partition; databases using one leader per shard order writes to a row the same way. This is the workhorse because most invariants are per-entity, and it scales by adding partitions (Chapter 25).
  • Sequence numbers. A single authority (a database sequence, a leader, a ticket server) hands out increasing numbers. Order by number gives a total order on everything that passes through that authority. Replication logs use this: each write receives a log sequence number, and followers apply in that order (Chapter 24). Per-sender sequence numbers also allow a receiver to detect gaps and duplicates and to reorder out-of-order arrivals, and they pair naturally with idempotency keys (Chapter 32).
  • Ordering via a single log. Funnel every change through one append-only log, and let every consumer read it in log order. The log's offsets are the total order. Distributed log systems partition the log for scale, restoring a per-partition order and giving up a global one. The mechanics are in Chapter 34; consensus-based logs (Raft, Paxos) give a replicated total order that survives node failure (Chapter 29).
Interview tip When a requirement says "events must be processed in order", ask "in order with respect to what?" Almost always the answer is per user, per order or per account, not global. That lets you shard by that key and keep order for free, rather than paying for a global total order.

12. Causality tracking in practice: Dynamo, Riak and CRDTs

12.1 Dynamo-style stores

Amazon's original Dynamo paper (the system behind the shopping cart) chose availability: any replica accepts writes even when others are unreachable. That means concurrent versions of a key will arise, and Dynamo tracks them with vector clocks of (node, counter) pairs attached to each version. A read returns every version that is not dominated by another, together with the combined clock as context. The client merges them (for the cart, take the union of items) and writes back with that context, which collapses the siblings. The paper noted that a rare deleted item could reappear after a merge, which is the price of favouring "never lose an add". To bound growth, Dynamo truncated the oldest pairs once a clock exceeded a threshold, accepting a small risk of lost precision.

12.2 Riak and its evolution

Riak followed the Dynamo design. Early versions attached a vector clock keyed by client id, which let vectors grow with the number of clients and caused sibling explosion when clients reused or lacked ids. Riak 2.0 moved to dotted version vectors keyed by server id, and added built-in CRDT data types (counters, sets, maps) so the database could merge for you. Many other systems made a different choice: Cassandra, for example, uses per-cell LWW timestamps by default for simplicity, which is exactly the danger from section 6, and relies on careful client usage, lightweight transactions, or a time-ordered write model to stay safe.

12.3 CRDTs: making merge automatic

Vector clocks detect conflicts; they do not resolve them. A conflict-free replicated data type (CRDT) is a data structure whose merge operation is designed to be commutative, associative and idempotent, so replicas can apply updates in any order, any number of times, and still converge to the same state. Examples: a grow-only counter (each replica has its own slot, merge by max per slot, total is the sum), an observed-remove set (each add is tagged with a unique dot, and a remove only deletes the tags it observed, so a concurrent add survives), and sequence types for collaborative text. Notice that the unique dot is the same idea as a dotted version vector. CRDTs buy availability and convergence at the cost of restricted semantics: you cannot express "balance must stay at or above zero" without coordination. The full treatment, including sorted-set CRDTs, is in Chapter 59.

14. Worked example: a lost update by LWW, and the fix

Consider an inventory counter for one product, replicated on two nodes, A and B, of a multi-leader database that resolves conflicts by last write wins. Node A's clock runs 200 ms ahead of true time (NTP has not corrected it); node B's clock is accurate. The stock is 6.

  1. At real time 100 ms, a warehouse worker sells one unit through node A. The application reads stock 6 and writes stock = 5. Node A stamps the write with its own clock: 100 + 200 = 300.
  2. At real time 250 ms (150 ms later, so truly after), another worker sells a second unit. This request is routed to node B, which has not yet received the first write. The application reads stock 6 (the old value, since replication has not arrived), and because this worker also sells one unit and fixes a counting error found earlier, it writes stock = 4. Node B stamps it 250.
  3. The replicas exchange their updates. Both compare timestamps: 300 versus 250. The write stamped 300 is "later", so stock = 5 wins on both nodes. The newer, correct write of 4 is discarded without any error.

Notice two separate bugs here. The first is the skew, as above. The second, deeper, is that a read-then-write of a counter is not safe under concurrency even with perfect clocks: if both workers had read 6 at nearly the same moment, each sale writes 5, and one sale is lost regardless of timestamps. Both are lost-update problems, and the fixes address different layers.

14.1 The fixes, from cheapest to strongest

  1. Do not use timestamps to resolve conflicts on data that matters. Switch the field to one of the approaches below.
  2. Make the operation commutative. Instead of "set stock to 5", send "decrement stock by 1". Model stock as a PN-counter CRDT (Chapter 59): each replica tracks its own increments and decrements, merge takes the max per slot, and the value is the sum. Both sales are counted, in any order. This stays available during a partition, but cannot enforce "never below zero".
  3. Use causality tracking. Each read returns a version vector; each write sends it back. Worker 1 reads {} and writes at A, producing {A:1}. Worker 2 read from A earlier (seeing {A:1}), writes to B, producing {A:1,B:1}, which dominates {A:1} and cleanly replaces it. If instead worker 2 never saw the first write, the vectors {A:1} and {B:1} are concurrent, and the store keeps both siblings for the application to merge (here: sum the deltas from the common base).
  4. Compare-and-set with a version number. The write says "set stock to 4 only if the current version is 7". The database applies it atomically against one authoritative copy, and a stale writer gets a conflict error and must re-read and retry. This needs a single leader (or consensus) for the key, so it gives up availability across partitions.
  5. Single writer per key, or consensus. Route every update for a product to one leader (per-key ordering, section 11). No concurrency on the key, no conflicts, and a total order for free; the cost is that the key is unavailable while its leader is being replaced. Add idempotency keys (Chapter 32) so a retried decrement after a timeout is not applied twice.
Rule of thumb Pick the weakest mechanism that preserves the invariant. Independent, mergeable data (carts, counters, presence) is a fit for CRDTs or siblings. Invariants spanning values ("do not oversell") need a single authority for that key. LWW is acceptable only where losing a concurrent write is harmless, such as a cache entry, a last-seen timestamp, or sensor readings where only the newest matters.

15. Interview Q&A

Why can't a client tell whether a server crashed or is just slow, and what should it do about it?

In an asynchronous network there is no upper bound on message delay, so silence is consistent with a crash, a lost message, and an extremely slow reply. A timeout therefore does not detect failure, it only expresses a guess that waiting longer is not worth it. The client should treat a timeout as an unknown outcome, not as a failure: for reads it can safely retry, perhaps against another replica; for writes it should retry only with an idempotency key so the second attempt cannot double-apply, or first query the status of the earlier attempt. It should also use deadlines, exponential backoff with jitter, and a circuit breaker so retries do not overload a struggling server.

Explain the two generals problem and why it matters for real systems.

Two parties must agree to act simultaneously but can communicate only over a channel that may lose messages. Any acknowledgement can itself be lost, so neither side can ever be certain the other received the last message, and no finite protocol guarantees agreement. In real systems this means "exactly-once delivery" over an unreliable network is impossible as a pure network guarantee. We get the effect by combining at-least-once delivery (retry until acknowledged) with idempotent processing or deduplication, and we reach agreement in practice using consensus protocols that assume eventual message delivery and a majority of working nodes, rather than certainty.

What is the difference between a wall clock and a monotonic clock, and which would you use for a timeout?

A wall clock reports calendar time and can be adjusted by NTP, by an administrator, by leap-second handling, or by VM migration, so it can jump forward or backward. A monotonic clock only counts forward from an arbitrary start point on that machine, so differences between two readings are reliable durations, but the values cannot be compared across machines. A timeout, lease timer, or elapsed-time measurement should use the monotonic clock. Wall-clock time is for showing times to humans and for expiry timestamps stored in data, where you accept the skew.

Why is last-write-wins dangerous, and when is it still acceptable?

LWW picks a winner by timestamp, so correctness depends on clocks that are skewed, can step backward, and may tie. A write that truly happened later can lose to one stamped with a faster clock, and the loser is dropped silently with no error. Even with perfect clocks it destroys one of two genuinely concurrent updates that should have been merged. It is acceptable when losing a concurrent write is harmless: caches, last-seen markers, idempotent overwrites of the same value, or telemetry where only the freshest value matters. For anything with business meaning, use version vectors, CRDTs, compare-and-set, or a single writer.

How do Lamport clocks work, and what can't they tell you?

Each process keeps a counter. It increments before every local event and stamps outgoing messages with it, and on receipt it sets its counter to the maximum of its own value and the message's value, plus one. This ensures that if event A happened before B then L(A) is less than L(B). The converse fails: a smaller timestamp does not mean "happened before", because two concurrent events can have any relation between their numbers. So Lamport clocks give a consistent total order (with process id tie-breaks) but cannot detect concurrency. For that you need vector clocks.

How do vector clocks detect concurrent updates, and what is their cost?

A vector clock stores one counter per participant. Comparing two vectors: if every entry of A is at most the matching entry of B (and one is smaller), then A happened before B; the reverse means B before A; if each has some entry larger than the other, the events are concurrent. This lets a store distinguish a descendant update, which safely replaces its ancestor, from a sibling, which must be preserved and merged. The cost is metadata whose size grows with the number of writers, which is why systems key vectors by replica rather than by client, prune old entries, or use dotted version vectors to stay compact and avoid sibling explosion. Also, detecting a conflict does not resolve it; the application or a CRDT must merge.

What problem does a hybrid logical clock solve, and what does it not solve?

Pure logical clocks respect causality but carry no real-time meaning, so you cannot do "as of 3 pm" queries or time-based expiry; pure physical clocks have meaning but break causality under skew and backward steps. An HLC pairs the largest physical time seen with a small counter, which keeps the timestamp close to wall time, monotonic, and consistent with happens-before, in a compact fixed size. It does not detect concurrency, since it still yields a total order for concurrent events, and its closeness to real time is only as good as the bounded clock skew. Databases such as CockroachDB and MongoDB use it for causally consistent timestamps without special hardware.

Explain how Spanner's TrueTime and commit-wait provide external consistency.

TrueTime returns an interval guaranteed to contain true time, with a small uncertainty epsilon obtained from GPS and atomic clock references. To commit, the coordinator picks a timestamp s at least as large as the interval's latest bound, then waits until the interval's earliest bound exceeds s, so s is certainly in the past everywhere, before making the commit visible. Any transaction that starts after the client sees the acknowledgement therefore receives a larger timestamp, so timestamp order matches real-time order across the globe. The price is a commit latency of roughly twice epsilon, a few milliseconds to about ten, and the benefit is a global total order without extra coordination between unrelated transactions.

You need messages processed in order in a high-throughput pipeline. How do you get ordering without a global bottleneck?

First clarify what must be ordered; usually it is order per entity such as per user, per account or per order. Partition the stream by that key so all of its events go to one partition, and have a single consumer instance process each partition sequentially. This gives strict order per key and parallelism across keys, scaling by adding partitions. Add sequence numbers so consumers can detect gaps or reorder after retries, and idempotent handling so redelivery after a timeout is harmless. A true global order requires either a single partition (limited throughput) or a consensus-based sequencer, which is rarely worth it.

How does a system stay safe when its failure detector is wrong, for example a leader paused by garbage collection?

Assume the detector will sometimes be wrong, and make safety independent of it. Leadership is granted through a lease that expires, and each grant carries a monotonically increasing fencing token. The shared resource, such as a database or storage layer, remembers the highest token it has seen and rejects any request with a lower one. A paused old leader that wakes up and still believes it leads will be rejected, so no corruption occurs; at worst, the system sees a brief unavailability or a failed write. Liveness depends on timing, but safety depends only on the token check.

16. Recap

  • Distributed systems differ from single machines because of partial failure, an unreliable network, and no shared clock or memory. Design for what you cannot assume.
  • Fault models range from crash and crash-recovery through omission and slowness to Byzantine. Most internal systems assume the first four. Partitions split a healthy cluster; majorities and fencing prevent split brain.
  • The two generals problem shows certainty is impossible over a lossy channel. A timeout is only a guess because slow and dead look identical, so treat it as "unknown", retry with idempotency, backoff and jitter, and use deadlines.
  • Failure detectors (heartbeat, phi accrual, gossip with indirect probes) produce suspicions, not facts. Protect against wrong suspicions with leases and fencing tokens.
  • Physical clocks drift and skew; NTP steps can go backwards; leap seconds break assumptions. Use monotonic clocks for durations; never trust wall-clock timestamps for ordering, and remember GC and VM pauses make "now" stale.
  • Happens-before defines causality. Lamport clocks give a causally consistent total order but cannot detect concurrency. Vector clocks (and version vectors, dotted version vectors) detect it exactly, at a metadata cost.
  • Hybrid logical clocks give causal order plus real-time meaning in a compact form. TrueTime exposes bounded uncertainty and uses commit-wait to give external consistency.
  • In practice choose a scope of order: per-key ordering via partitioning, sequence numbers, or a single log. Resolve conflicts with siblings, CRDTs, compare-and-set or a single writer; reserve LWW for data that can afford silent loss.
