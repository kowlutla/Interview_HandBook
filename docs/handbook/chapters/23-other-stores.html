Other Specialized Stores

A general-purpose database is a good default, but some workloads are so different in shape that a purpose-built store wins by a factor of ten or a hundred. This chapter covers the four you will meet most often in interviews: distributed file systems, data warehouses, time-series databases and vector databases, plus a short look at in-memory grids and ledger databases, and how data gets into all of them.

1. Why specialized stores exist

A relational database such as PostgreSQL or MySQL stores data as rows in B-tree pages, optimizes for many small transactions, and gives strong guarantees (Chapter 18). That design is excellent when you read and write a few rows by key. It becomes a poor fit when the access pattern changes in one of four ways:

  • The unit of data is a huge file (gigabytes, read sequentially, written once). The answer is a distributed file system.
  • The query scans billions of rows but touches only a few columns and computes sums and averages. The answer is a columnar data warehouse.
  • Every record is a measurement stamped with a time, arriving continuously, queried by time range and thrown away after a while. The answer is a time-series database.
  • The question is "which items are most similar to this one", where similarity is geometric distance between vectors of numbers. The answer is a vector database.

Each of these stores makes one deliberate trade: it gives up general flexibility (arbitrary updates, joins, secondary indexes, strict transactions) to get an order-of-magnitude advantage on its narrow workload. Understanding which trade each one makes is the heart of the interview answer. Two neighbours are covered elsewhere and are not repeated here: Chapter 21 covers object storage (S3-style), which today often replaces the distributed file system as the storage layer, and Chapter 22 covers search engines and the inverted index. The broader map of NoSQL families lives in Chapter 20.

Key idea Pick the store from the access pattern, not from fashion. Ask three questions: how is the data written (single rows, batches, streams), how is it read (by key, by range, by scan, by similarity), and how long does it live. The answers point at one of these specialized stores or confirm that your general-purpose database is enough.

2. Distributed file systems: GFS and HDFS

2.1 The problem they solve

Imagine you must store 5 petabytes of web crawl data or log files and run analysis jobs that read all of it. A single disk holds a few terabytes, so the data must spread across thousands of machines. Those machines will fail constantly: with 5,000 servers and a typical disk failure rate of a few percent per year, you lose several disks every day. The system therefore has to treat failure as the normal case, store each piece of data several times, and repair itself automatically. It also has to let a program read a huge file at the combined speed of many disks, not the speed of one.

Google described this design in the 2003 paper on the Google File System (GFS). The open-source Hadoop Distributed File System (HDFS) follows the same ideas. Both assume a workload with these properties: files are very large (hundreds of megabytes to terabytes), they are written once by appending and then read many times, reads are mostly long sequential scans rather than random lookups, and throughput matters more than the latency of a single operation. That assumption lets them drop features (in-place edits, POSIX semantics, small-file efficiency) and gain simplicity and scale.

2.2 Architecture: one NameNode, many DataNodes

An HDFS cluster has two kinds of machine.

  • The NameNode (called the master in GFS) holds all the metadata: the directory tree, which files exist, which blocks make up each file, and which DataNodes currently hold each block. It does not store file contents. For speed it keeps the whole namespace in RAM.
  • The DataNodes (chunkservers in GFS) store the actual bytes. Each DataNode keeps blocks as ordinary files on its local disks and reports to the NameNode.

A file is cut into fixed-size blocks, 128 MB by default in HDFS (64 MB in the original GFS, which called them chunks). The block is large on purpose. A big block means the NameNode needs fewer metadata entries per terabyte, and a client spends its time streaming data instead of seeking. A 1 GB file is just eight 128 MB blocks. The last block of a file is only as large as the remaining data; it does not waste space on disk.

Each block is replicated, by default three times, on three different DataNodes. Replication gives two things at once: durability (losing a machine loses no data) and read bandwidth (three machines can serve the same block, so a job can read from whichever is closest or idle).

DataNodes send the NameNode a heartbeat every few seconds (3 seconds by default) and a full block report listing all their blocks at start-up and periodically afterwards. If heartbeats stop for roughly ten minutes, the NameNode declares the node dead, notices that every block it held is now under-replicated, and instructs other DataNodes to copy those blocks until three replicas exist again. This re-replication is the self-healing loop.

2.3 Rack awareness and replica placement

Servers sit in racks, each rack sharing one top-of-rack network switch and often one power feed. Traffic inside a rack is fast and cheap; traffic between racks crosses a slower, shared uplink. Failures also correlate by rack: a switch or power failure takes out every machine in it. If all three replicas of a block landed in one rack, a single switch failure would make the block unavailable.

Rack awareness means the NameNode is given the network topology (an administrator supplies a mapping from machine to rack) and uses it for placement. The default policy for three replicas is:

  1. The first replica goes on the writer's own node (or a random node if the client is outside the cluster). This is cheapest for the writer.
  2. The second replica goes on a node in a different rack, so the block survives the loss of a whole rack.
  3. The third replica goes on a different node in the same rack as the second. This keeps the cross-rack traffic to one transfer instead of two while still keeping two racks involved.

The same topology information drives reads: the NameNode sorts the replica list by network distance from the client, so a task usually reads from its own node, otherwise from its own rack, and only then from a remote rack. Compute frameworks use this for data locality: they try to run a task on the machine that already holds its block, moving the computation to the data instead of the data across the network.

2.4 The write path

Writing is a pipeline, designed so that the client uploads each byte only once.

  1. The client asks the NameNode to create the file. The NameNode checks permissions and that the name is free, then records it.
  2. For each new block, the client asks the NameNode for a list of target DataNodes (three, chosen by the placement policy above).
  3. The client sends data to the first DataNode in small packets (about 64 KB). The first node writes locally and forwards each packet to the second, which forwards it to the third. This is the replication pipeline.
  4. Acknowledgements flow back along the pipeline in reverse. The client treats a packet as safe when the acks have come back from all nodes in the pipeline.
  5. When the block is full, the client asks the NameNode for the next block and repeats. On close, the file is finalized in the namespace.

The pipeline means the client's outbound bandwidth is used once, not three times, and the cluster-internal bandwidth does the copying. If a DataNode in the pipeline fails mid-block, the client rebuilds the pipeline with the surviving nodes, continues writing, and the NameNode later re-replicates the block to restore the count. Each block carries checksums (a short hash per 512 bytes by default) so corruption is detected on read and on a background scan; a corrupt replica is discarded and re-copied from a good one.

2.5 The read path

The client asks the NameNode for the block locations of the byte range it wants. The NameNode replies with each block's replica list, ordered nearest first. The client then connects directly to the nearest DataNode and streams the block, verifying checksums as it goes. If that DataNode is down or the data is corrupt, it silently falls back to the next replica and reports the bad one. Because the NameNode is touched only once per block (not per byte), a handful of metadata servers can support thousands of readers each pulling gigabytes per second from the DataNodes. Clients cache the block locations for the open file.

2.6 The small files problem

The NameNode keeps every file, directory and block as an object in memory. A common rule of thumb is about 150 bytes of heap per object. Consider 100 million small files of 1 MB each. Each file is one block, so there are about 200 million objects (files plus blocks), costing roughly 200,000,000 × 150 bytes = 30 GB of NameNode memory, to store only 100 TB of data. Compare that with 100 TB stored as 128 MB blocks: about 800,000 blocks and under 1 GB of metadata. The metadata cost depends on the number of objects, not their size, so millions of tiny files exhaust the NameNode long before the disks fill. They also hurt job performance, because each file becomes a separate task with start-up overhead.

The remedies:

  • Merge before storing. Pack many records into big container formats (Avro, Parquet, SequenceFile, or Hadoop Archive files) so a file is at least a block in size.
  • Compact later. Run a periodic job that rewrites small files into large ones. Table formats (section 3.9) automate this.
  • Federation. Use several independent NameNodes, each owning a part of the namespace, to spread metadata memory. DataNodes serve all of them.
  • Use object storage for the file layer, where metadata is a distributed service rather than one process's RAM (Chapter 21).

2.7 High availability of the NameNode

The single master is the famous weak point. In the first Hadoop versions the NameNode was a single point of failure: lose it and the whole file system is unavailable until it restarts and rebuilds its memory state, which can take tens of minutes on a large cluster. GFS handled this with a replicated operation log and a shadow master. Modern HDFS uses an active/standby pair:

  • Every change to the namespace is written as an entry in an edit log. Instead of a local disk, the active NameNode writes the log to a quorum of JournalNodes (usually three or five small processes), and a write succeeds when a majority acknowledge. This is the Quorum Journal Manager, the same majority idea you will see in Chapter 29.
  • The standby NameNode continuously reads the edit log and applies it, so its in-memory namespace stays almost current. It also receives block reports from all DataNodes, so it knows block locations too. It periodically merges the log into a checkpoint (an image of the namespace) so restarts are fast.
  • A ZooKeeper Failover Controller on each NameNode monitors health and holds a lock in ZooKeeper (Chapter 30). When the active dies, the standby wins the lock and becomes active, typically within seconds.
  • Fencing prevents split-brain: before the new active takes over, the old one is cut off, and the JournalNodes accept writes only from the newest epoch, so a zombie ex-active cannot corrupt the log.

GFS and HDFS differ slightly in details (GFS used leases so that one chunkserver, the primary, orders concurrent mutations to a chunk and supports atomic record append; HDFS allows a single writer per file with append only). The shared lesson for interviews: separate the small, hot metadata plane from the large, bulk data plane, so the control plane can be a replicated single logical service while data scales out freely.

HDFS 3 also offers erasure coding for cold data: instead of three full copies (200 percent overhead), a Reed-Solomon scheme such as 6 data blocks plus 3 parity blocks tolerates three losses at 50 percent overhead, at the cost of CPU and slower recovery and loss of data locality. The principle is the same as in object stores (Chapter 21).

2.8 When to use a distributed file system today

HDFS is the foundation of the Hadoop ecosystem (MapReduce, Spark, Hive, HBase) and is still common on-premises. In the cloud, most new designs store the bytes in object storage and run compute separately, because object stores are cheaper, more durable, effectively infinite and need no NameNode to operate. The cost is higher latency per request and weaker rename and listing semantics. Choose HDFS or a similar file system when you need cheap sequential bandwidth with data locality inside your own data center, or when an existing Hadoop ecosystem already runs there. Do not choose it for small files, random updates, low-latency lookups or a user-facing serving path.

3. Data warehouses and OLAP

3.1 OLTP versus OLAP

There are two very different jobs a database can be asked to do. OLTP (online transaction processing) runs the live application: place an order, update a balance, fetch a user profile. Each operation touches a few rows, must complete in milliseconds, and must be correct under concurrency. OLAP (online analytical processing) answers business questions: total revenue per region per month over three years, the 95th percentile of checkout latency by country. Each query reads millions or billions of rows but only a few columns, runs for seconds, and is read-only.

Running big analytical scans on the production OLTP database is a classic mistake: the long scans evict useful pages from cache and compete for I/O with customer requests, so latency for users rises. The standard answer is to copy the data into a separate analytical store (section 8).

3.2 Columnar storage

A row store keeps all the fields of one row together on disk: (id, date, region, product, amount, ...) then the next row. To sum amount over a billion rows it must read every byte of every column, because the amount values are interleaved with everything else. A column store keeps all values of one column together: all the amounts in one contiguous region, all the regions in another. The query reads only the columns it names. If the table has 100 columns and the query needs 3, it reads about 3 percent of the data before any other optimization.

Columnar storage costs something: reconstructing a whole row means reading from many column regions, and single-row inserts and updates are expensive because they touch every column file. That is why columnar stores favour bulk, append-style loading and treat updates as rare. Real systems store data in large batches (a row group or segment of, say, a million rows), with each column stored contiguously inside the group, along with min and max statistics per column per group. A query with WHERE date = '2025-06-01' can skip every group whose min and max exclude that date without reading it at all (zone maps or data skipping). Sorting or clustering the table by a commonly filtered column makes this skipping highly effective.

3.3 Compression

Values in one column are the same type and often repetitive, which suits compression. Warehouses use light, fast encodings chosen per column, then often a general compressor on top:

  • Dictionary encoding: a column of country names with 200 distinct values is stored as small integers plus a 200-entry dictionary. Comparisons run on integers, not strings.
  • Run-length encoding (RLE): if a sorted column holds EU a million times in a row, store "EU × 1,000,000".
  • Delta encoding: store timestamps or increasing ids as differences from the previous value, which are tiny numbers that need few bits.
  • Bit-packing: store integers in the minimum number of bits that fit the range.
  • General codecs such as LZ4 (fast) or ZSTD (stronger) on the encoded blocks.

Compression ratios of 5 to 10 times are routine, versus perhaps 2 to 3 times for row stores. This helps twice: less disk space and, more importantly, less data to move from disk or the network into memory, which is the bottleneck. Many engines can even evaluate a filter directly on the compressed data (for example, compare dictionary codes) without decompressing it.

3.4 Vectorized execution

A classic database executes a query one row at a time: for each row, call the next operator, evaluate the expression, pass the row up. Each step involves function calls and branches, and the processor spends more time on that overhead than on arithmetic. Vectorized execution processes a batch of values (often 1,000 to a few thousand) per call. A tight loop adds a thousand numbers from a column array. This keeps data in the CPU caches, avoids per-row call overhead, and lets the processor use SIMD instructions that perform the same operation on 4, 8 or 16 values at once. Some engines instead compile the query into machine code; both approaches attack the same per-row overhead. Together with columnar layout, this is why a warehouse can scan a billion rows per second per machine for simple aggregates, while a row store on the same hardware is many times slower.

3.5 Schema design: star and snowflake

Analytical data is usually modeled as a star schema. In the center is a fact table: one row per event or measurement (a sale, a click, a shipment), with numeric measures (amount, quantity) and foreign keys. Around it are dimension tables that describe the context: date, product, customer, store. Analysts "slice and dice" by joining the fact table to dimensions and grouping by dimension attributes: revenue by product category by month by region.

A snowflake schema further normalizes the dimensions into sub-tables (category in its own table, referenced from product). It removes duplication but adds joins, so queries are more complex and usually slower. Because storage is cheap and columnar compression makes repeated text almost free, most designs prefer the plain star, or even a single wide denormalized table. Two details are worth knowing: surrogate keys (small integer ids rather than natural keys) keep fact tables compact, and slowly changing dimensions track history, for example a customer who moves city, by adding a new dimension row with validity dates instead of overwriting.

3.6 MPP: massively parallel processing

One machine cannot scan a petabyte quickly. A massively parallel processing (MPP) warehouse splits both the data and every query across many nodes. A leader (coordinator) node parses and plans the query, then sends fragments to compute nodes. Each node scans and aggregates its own slice of the data in parallel, producing partial results, and the leader (or a tree of nodes) combines them. A sum, for instance, becomes many partial sums added at the end.

The hard part is the join, because matching rows may live on different nodes. The engine picks a strategy:

  • Broadcast join: if one side (a small dimension table) fits in memory, copy it to every node; each node joins its slice of the big fact table locally. No fact data moves.
  • Shuffle (repartition) join: if both sides are big, redistribute both by the join key so matching rows meet on the same node, then join locally. This moves a lot of data over the network and is the usual cost center.
  • Co-located join: if both tables were already distributed by the same key when loaded (for example both by customer_id), the join needs no network movement at all. This is why warehouses let you choose a distribution key per table.

The tradeoff to remember is data skew: if one customer owns half the rows, the node holding that key does half the work and the whole query waits for it, like any partitioned system (Chapter 25).

3.7 Snowflake, BigQuery and Redshift: concepts, not marketing

The three big cloud warehouses show different points on one design axis: how tightly storage and compute are coupled.

  • Amazon Redshift began as a classic MPP cluster: nodes with local disks, you choose a distribution key and sort key, and you resize the cluster for more capacity. Newer node types and a serverless option keep data in managed storage that can be scaled separately, but the cluster mental model (provisioned compute, distribution and sort keys, vacuum of deleted rows) remains.
  • Snowflake separates storage (compressed columnar files in object storage, cut into immutable micro-partitions with min and max metadata) from compute (independent clusters called virtual warehouses that you start, stop and size). Several teams can run separate virtual warehouses on the same data without competing, and an idle warehouse costs nothing. A metadata service holds the catalog and partition statistics so queries prune partitions.
  • Google BigQuery is serverless: you submit SQL and the service allocates compute slots from a large shared pool. Data lives in a columnar format on a distributed file system, and a very fast internal network shuffles intermediate data between workers. You pay by data scanned (on-demand) or reserve slots for a flat price. Partitioning and clustering a table cut the bytes scanned and therefore cost.

The common ideas matter more than product names: columnar immutable files, metadata-driven pruning, separation of storage and compute so each scales and is billed independently, and elastic parallelism. The tradeoff of separation is that every query starts by pulling data across a network from object storage, so engines add caches on local SSD and in memory.

3.8 ETL versus ELT, and data lakes

A warehouse is fed by pipelines. Two orderings exist:

  • ETL (extract, transform, load): pull data from sources, clean and reshape it in a separate processing engine, then load only the finished tables into the warehouse. This made sense when warehouse compute was scarce and expensive, and it keeps raw sensitive data out of the warehouse. The downside is that the transformation logic lives in an extra system, and a mistake means re-extracting from the sources.
  • ELT (extract, load, transform): load the raw data first, then transform it inside the warehouse using SQL (tools like dbt formalize this). Cloud warehouses have elastic compute, so it is simple, raw data is kept for reprocessing, and transformations are version-controlled SQL that analysts can maintain. The downside is cost control and the need to govern raw data inside the warehouse.

A data lake is a large store of raw data in open file formats (Parquet, ORC, JSON, CSV), usually on object storage (Chapter 21) or HDFS. It is cheap and flexible: you store everything first and decide the schema when you read it (schema-on-read), contrasted with the warehouse's schema-on-write. Lakes hold structured, semi-structured and unstructured data, and serve data science and machine learning as well as SQL. Their weakness historically was reliability: a bare folder of files has no transactions, so a job that fails halfway leaves half-written files, readers see inconsistent partial data, there is no safe way to update or delete a row (a problem for privacy deletion rules), and schema drift silently breaks readers. The two-tier approach of a lake plus a separate warehouse also copies data and creates two versions of the truth.

3.9 Lakehouse table formats: Iceberg and Delta

The lakehouse idea is to add a reliable table layer on top of cheap lake files so one copy of data serves both warehouse-style SQL and open data processing. Open table formats such as Apache Iceberg, Delta Lake and Apache Hudi do this with a metadata layer kept next to the data files:

  • Data stays in immutable Parquet files. Metadata files list exactly which data files belong to the table at each version, with per-file statistics (min, max, row counts).
  • A commit writes new data files, then atomically publishes a new metadata version (a new snapshot in Iceberg, a new entry in the transaction log in Delta). Readers see either the old or the new snapshot, never a mix: this provides ACID transactions over plain files.
  • Because old snapshots remain until cleaned up, you get time travel (query the table as of yesterday) and easy rollback.
  • Row-level updates and deletes are supported by rewriting affected files, or by writing small delete files merged at read time.
  • Schema evolution (add, rename, drop columns) and partition evolution are tracked in the metadata, and the metadata lets engines skip files using statistics without listing directories.
  • Concurrent writers use optimistic concurrency: each commit assumes no one else committed, and if the table version changed underneath, the loser retries or fails with a conflict.
  • Compaction jobs merge the many small files that streaming writes create, which also answers the small-files problem of section 2.6.

Spark, Flink, Trino, and the cloud warehouses can all read these formats, which reduces lock-in: the data and its table metadata are open and sit in your own object storage.

Interview tip When asked "where do analytics go", walk the pipeline: operational databases, then CDC or batch extract, then a lake or warehouse (section 8), with a columnar format and a star schema, and mention that you do not run reports on the OLTP primary. Naming the reason (row layout versus column layout, scan versus lookup) shows you know why, not just what.

4. Time-series databases

4.1 What a time series is

A time series is a sequence of measurements of one thing over time: the CPU usage of one server sampled every 10 seconds, the temperature of one sensor, the price of one stock. Monitoring, IoT, finance and product analytics all produce enormous volumes of them. The workload has distinctive properties: data arrives in time order and almost only as appends; recent data is queried constantly and old data rarely; queries ask for ranges ("the last 6 hours") and aggregates ("the 99th percentile per minute"); individual points are never updated; and old data is deleted or summarized on a schedule. A general database can store this, but a specialized engine exploits each of those properties.

4.2 Data model

The common model has four parts. A metric (or measurement) names what is measured, such as http_requests_total. Tags (called labels in Prometheus) are key-value pairs that identify which thing is measured: service="checkout", region="eu", instance="web-17". One metric plus one exact set of tags defines one series. Each series holds a list of samples, which are (timestamp, value) pairs. Some systems (InfluxDB, TimescaleDB) also allow several fields per point, such as temperature and humidity measured together.

http_requests_total{service="checkout",region="eu",instance="web-17"}
   -> (t0, 10231) (t0+15s, 10244) (t0+30s, 10260) ...

Tags are indexed so you can find series quickly ("all series where service is checkout"); values are not indexed but stored compactly.

4.3 Ingestion and storage

Ingestion volume is high, so these engines buffer incoming samples in memory, protect them with a write-ahead log (Chapter 19), and periodically flush an immutable block covering a fixed time window to disk. Prometheus, for example, keeps roughly the last two hours in memory (and WAL) and then writes a block containing an index and compressed chunks for that window; older blocks are later merged by compaction. InfluxDB uses a similar LSM-like structure (the time-structured merge tree). TimescaleDB takes a different path: it is a PostgreSQL extension that automatically partitions a table into chunks by time (and optionally by a space key), called a hypertable, so you keep full SQL, joins and PostgreSQL tooling, with the benefit that the newest chunk's indexes stay small and fit in memory, and old chunks can be dropped or compressed as a unit.

Because values in a series change slowly and timestamps arrive at regular intervals, specialized compression works spectacularly. Facebook's Gorilla paper describes delta-of-delta timestamp encoding (a regular 10-second interval has a second difference of zero, which costs one bit) and XOR encoding of floating-point values (consecutive values share most bits, so the XOR is mostly zeros). Gorilla-style compression averages around 1.4 bytes per sample versus 16 bytes uncompressed, more than ten times smaller. Prometheus and others use the same idea.

4.4 Downsampling and retention

Retention is the rule for how long data is kept. Because storage is partitioned by time, deleting data older than 30 days is just removing whole blocks or chunks, an instant operation, instead of a huge row-by-row delete that fragments a general database. Downsampling (rollup) replaces fine-grained old data by summaries: for example, keep raw 15-second points for 15 days, then 5-minute aggregates for 90 days, then hourly for two years. Store several aggregates per window (min, max, sum, count, so that averages can still be recomputed correctly) rather than a single average, because an average of averages is wrong when windows hold different counts, and percentiles cannot be recovered from averages at all. Keep histograms or sketches if you will need percentiles over old data. The tradeoff is explicit: you lose the ability to ask a fine-grained question about the past in exchange for bounded storage and fast long-range charts.

4.5 High cardinality: the main failure mode

Cardinality is the number of distinct series. It is the product of the distinct values of each tag. A metric with tags service (100 values), region (5), endpoint (200) and status code (10) can produce up to 100 × 5 × 200 × 10 = 1,000,000 series. Each active series costs memory for its index entry and its in-memory chunk (often a few kilobytes), so a million series is on the order of several gigabytes. Now add one more tag: user_id with ten million values. The series count explodes toward billions, memory is exhausted, the index becomes enormous, queries slow down, and the server crashes. This is called a cardinality explosion.

It usually happens innocently: someone adds a request id, user id, full URL with query string, or container id that changes on every deploy, as a tag. Churn is also a problem: Kubernetes pods that restart with new names create new series continually even if the live count is stable. Rules of thumb and mitigations:

  • Tags must come from a small, bounded set. Never put unbounded identifiers (user id, order id, trace id, raw URL) in a tag. Put them in logs or traces instead (Chapter 54).
  • Enforce a per-tenant or per-metric series limit and drop or reject beyond it, so one bad producer cannot take down the database.
  • Normalize labels at the source (route templates such as /users/:id instead of the concrete path), and drop unused labels at ingestion.
  • Use pre-aggregation (recording rules) to compute a low-cardinality summary and keep only that for long-term storage.
  • When you truly need high-cardinality analysis (per-user), use an engine designed for wide events (columnar stores such as ClickHouse or a log/trace system) rather than a metrics TSDB.

5. Vector databases

5.1 Embeddings and similarity

A machine learning model can turn a piece of content (a sentence, an image, a product, a user's behaviour) into a list of numbers called an embedding or vector, typically 128 to 3,072 numbers long. The model is trained so that items with similar meaning map to nearby points in this high-dimensional space. "How do I reset my password" and "I forgot my login" land close together although they share few words. That makes semantic search possible: embed the query, then find the stored vectors nearest to it.

"Nearest" needs a distance measure. The common ones are cosine similarity (the angle between two vectors, ignoring length), dot product (angle and length combined; for vectors normalized to length one it ranks identically to cosine), and Euclidean (L2) distance (straight-line distance). The embedding model usually specifies which to use.

5.2 Why exact search does not scale

The honest, exact approach is brute force (a flat index): compare the query with every stored vector and keep the closest k. For N vectors of dimension D this costs about N × D multiply-adds per query. With 100 million vectors of dimension 768, that is about 77 billion operations per query and 300 GB of memory reads: far too slow for an interactive service. Unlike a B-tree lookup on one number, there is no useful sort order in 768 dimensions, and the classic spatial trees degrade badly as dimensions grow (the "curse of dimensionality": distances between points become nearly equal, so tree pruning stops working).

The practical answer is approximate nearest neighbour (ANN) search: build an index that finds the true nearest neighbours most of the time while examining only a tiny fraction of the data. You accept that a few results may be missing in return for a speedup of a hundred or a thousand times.

5.3 HNSW: navigating a layered graph

HNSW (Hierarchical Navigable Small World) is the most widely used ANN index. Each vector becomes a node in a graph, linked to a limited number of nearby vectors. Search is a greedy walk: start at an entry node, look at its neighbours, move to whichever is closest to the query, and repeat until no neighbour is closer. This works because the graph is a "small world": a few long-range links let you cross the space quickly, then short links refine the position.

To make the walk fast from the start, HNSW stacks several layers. The top layer holds a small random sample of the vectors with long links, and each lower layer holds more, with the bottom layer containing all vectors. A query enters at the top, greedily descends to the closest node in that layer, drops to the next layer using that node as the starting point, and continues. By the bottom layer it is already near the answer and does a wider local search there. Three parameters control behaviour:

  • M: the maximum number of links per node. Higher M gives better recall and a bigger index (memory), and slower builds.
  • efConstruction: how many candidates are examined while inserting each vector. Higher makes a better graph and a slower build.
  • efSearch: how many candidates are kept during a query. Higher means better recall and higher latency; it can be changed per query.

HNSW gives excellent recall at low latency (often under 10 ms on millions of vectors) but the graph must live in memory, inserts are costlier than for a flat list, and deletes are awkward (nodes are usually marked deleted and the graph repaired or rebuilt later).

5.4 IVF and quantization

IVF (inverted file index) takes a different approach: cluster first, search later. A training step runs k-means to split the vectors into, say, 4,096 clusters, each with a centroid (its centre point). Each vector is filed in the list of its nearest centroid. At query time the engine finds the few closest centroids (a small comparison) and scans only those lists. The parameter nprobe sets how many lists to scan: more lists mean better recall and slower queries. If the true nearest neighbour sits just across a cluster boundary and that cluster is not probed, it is missed, which is the source of approximation error.

IVF indexes are smaller and cheaper to build than HNSW and handle huge data sets, but the clusters need training on representative data and drift as the data changes. IVF is often combined with product quantization (PQ), which compresses each vector: split the 768 dimensions into, say, 96 sub-vectors, and replace each with a one-byte code that points into a learned codebook. A 3,072-byte float vector becomes 96 bytes, a 32-fold reduction, with some loss of precision. Distances are computed approximately from the codes. Compression lets billions of vectors fit in memory, and a common pattern is to retrieve many candidates with the compressed index and then re-rank the top few using the full-precision vectors. Another family, DiskANN, keeps a graph on SSD with compressed vectors in memory, for data sets too large for RAM.

5.5 Recall versus latency

Recall is the fraction of the true top-k neighbours that the approximate search actually returns. If the exact top 10 are known and the ANN returns 9 of them, recall at 10 is 0.9. Every ANN index exposes knobs (efSearch for HNSW, nprobe for IVF) that move along a curve: more work per query means higher recall and higher latency and CPU cost. A realistic target is 0.95 to 0.99 recall, and the right setting is found empirically by measuring against a held-out set of queries with exact answers. Chasing the last percent of recall is expensive: going from 0.95 to 0.99 can double the work. For retrieval-augmented generation (below) a slightly lower recall is often acceptable because the downstream model is robust to a missing marginal passage; for deduplication or fraud matching it may not be.

5.6 Filtering

Real queries are rarely "nearest anything". They are "nearest documents in this tenant, in English, published this year", or "similar products that are in stock and under $50". Combining a metadata filter with ANN search is difficult because the graph or cluster structure knows nothing about the filter. Three strategies exist:

  • Post-filtering: run ANN for the top K, then discard results that fail the filter. Simple, but a selective filter may leave you with fewer than k results, even none. You can fetch a larger K to compensate, at higher cost.
  • Pre-filtering: find the allowed ids first (using a normal index) and search only among them. Exact for the filter, but when the allowed set is small, the engine falls back to brute force over it, which is fine for small sets and slow for medium ones.
  • Filtered (in-graph) search: the engine applies the predicate while traversing the index, skipping non-matching nodes but still walking through them to stay connected. This is the approach most modern engines implement; it works well unless the filter is extremely selective.

A common practical split is to partition by an obviously isolating field (a collection or namespace per tenant) so most filtering becomes "search this smaller index", and use in-index filtering only for the rest. Also consider hybrid search: combine ANN with keyword search (BM25, Chapter 22) and merge the rankings, because embeddings can miss exact terms such as product codes and names, while keyword search misses paraphrases.

5.7 Use in RAG and recommendations

Retrieval-augmented generation (RAG) lets a language model answer using your own documents. Offline, you split documents into chunks (a few hundred tokens each), embed every chunk and store the vectors with the original text and metadata. Online, the question is embedded, the vector database returns the top-k most similar chunks, and those chunks are placed in the prompt so the model grounds its answer in them. The vector store is the memory of the system; its recall directly limits answer quality, and its freshness (how quickly new documents are indexed) determines how current the answers are. The design issues are chunk size (too small loses context, too large dilutes meaning), re-embedding when you change the embedding model (vectors from different models are not comparable, so you must re-embed the whole corpus), access control (filter by the caller's permissions so the model never sees documents the user cannot), and evaluation of retrieval separately from generation.

Recommendations use the same engine differently. A model learns embeddings for users and items so that a user's vector is near items they would like. Candidate generation is then "fetch the 500 nearest items to this user's vector" in a few milliseconds, followed by a heavier ranking model that scores those 500 using many features, then business rules and filtering of already-seen items. "Similar items" and "visually similar" features, near-duplicate detection and image search follow the same retrieve-then-rank shape.

5.8 pgvector versus a dedicated vector database

pgvector is a PostgreSQL extension that adds a vector column type, distance operators, and HNSW and IVFFlat indexes. A dedicated vector database (Pinecone, Milvus, Qdrant, Weaviate, Vespa and others, or the vector features of Elasticsearch/OpenSearch) is built around ANN from the start.

6. In-memory data grids

An in-memory data grid (IMDG) such as Hazelcast, Apache Ignite, Oracle Coherence or Infinispan keeps data in the RAM of a cluster of nodes, partitioned across them with each partition replicated to a backup node. It looks like a distributed hash map but adds features beyond a plain cache such as Redis (Chapter 15): compute collocation (ship a function to the node that owns the data instead of pulling the data over the network), distributed locks and queues, SQL or predicate queries over the in-memory data, near caches on the client, and optional write-through to a backing database, with transactions in some products. They are used for very low-latency state in trading systems, session stores, real-time risk calculations and as a speed layer in front of a slow system of record.

The tradeoffs are plain: RAM is expensive and bounded, so you hold the working set rather than the whole history; data is lost on a full-cluster crash unless you persist or write through; node joins and leaves cause partition rebalancing that consumes bandwidth; and a network partition forces a choice between availability and consistency (Chapter 28). If you only need a cache, a simpler cache (Chapter 13) is usually enough; reach for a grid when you need computation next to the data or a queryable distributed state.

7. Ledger and immutable databases

A ledger database records every change as an append-only entry and never overwrites history. The goal is an audit trail you can prove is untampered: for financial balances, regulatory records, supply-chain provenance or medical logs. The usual mechanism is a hash chain or Merkle tree (Chapter 33): each block of entries includes the hash of the previous block, so altering any past record changes every later hash and is detectable by anyone holding a recent digest. Examples are Amazon QLDB (a managed ledger service that AWS has announced it is retiring, so check current status), Azure SQL ledger tables, immudb, and the ledger in a blockchain (which adds decentralized consensus among mutually distrusting parties, a different problem from a single trusted operator).

You can get most of the benefit without a special product. Model money as an append-only journal of double-entry postings in an ordinary database: each transaction is a set of debits and credits that sum to zero, corrections are new compensating entries, never edits, and current balances are derived by summing (or from a maintained snapshot). Revoke update and delete permissions on the journal table and periodically publish a hash of it to external storage. The ideas are the same as event sourcing (Chapter 36): the log of facts is the source of truth, and other views are derived. The tradeoffs are storage growth (history never shrinks, though old segments can be archived), the cost of deriving current state, and conflict with erasure rules such as GDPR, which is why personal data is often kept outside the immutable log and referenced by an id that can be deleted (Chapter 56).

8. Feeding these stores: CDC and streams

None of these stores is usually the system of record for user-facing transactions. Data originates in OLTP databases and services, then is copied into them. How you copy it determines freshness, load on the source, and correctness. The options, from oldest to newest:

  • Batch extract: a nightly job queries the source (or reads a replica) and writes a full or incremental dump into the lake or warehouse. Simple, but data is a day old and large queries load the source.
  • Dual write: the application writes to the database and also to the second store. This is fragile: if one write fails the stores disagree, and ordering between concurrent updates is not guaranteed (Chapter 31). Avoid it.
  • Change data capture (CDC): read the database's own replication log (the write-ahead log or binlog) and turn each committed insert, update and delete into an event. Tools such as Debezium do this. Because it follows the commit order of the source, it is correct and low-impact: no queries on the tables, just log reading. Events are published to a durable log such as Kafka (Chapter 34), and each target store has its own consumer. Chapter 36 covers CDC and the outbox pattern in depth.
  • Application events: services publish domain events (OrderPlaced) to a stream; consumers project them into whatever shape each store needs.

Between the stream and the stores you often run stream or batch processing (Chapter 37): clean and enrich events, compute windowed aggregates, join streams, and write results in the format the store wants. The same stream can fan out to many stores at once.

Several practical points apply. Deliveries are at least once, so loads must be idempotent (use upserts keyed by primary key and version, Chapter 32). Event order matters per key, so partition the stream by entity id. Warehouses and lakehouses prefer micro-batches of files (every minute or so) over single-row inserts, which would produce the small-files problem again. Schema changes in the source must be handled through a schema registry and compatible evolution (Chapter 7). Deletes need explicit treatment: a CDC delete becomes a tombstone event, and each target must apply it (delete the vector, the row, mark the file). And you need a backfill path: an initial snapshot plus the log from that point, or a replay of retained history.

10. Capacity examples

10.1 HDFS: sizing a cluster

Requirement: store 2 PB of logical data with replication factor 3. Raw capacity needed is 2 PB × 3 = 6 PB. Leave about 25 percent headroom for temporary files, rebalancing and failures, giving 6 / 0.75 = 8 PB raw. With 12 disks of 16 TB per node (192 TB raw each), that is 8,000 TB / 192 TB, about 42 DataNodes. Block count: 2 PB / 128 MB = 2,000,000 GB / 0.128 GB, roughly 16 million blocks, or 48 million block replicas. NameNode metadata is about 16 million blocks plus perhaps a few million files, so at 150 bytes per object a few GB of heap, easily handled. Now suppose instead the data is 2 billion small files: that is 4 billion objects, about 600 GB of heap, which is impossible on one NameNode and shows why the small-files problem dominates the design.

10.2 Warehouse: scan cost

A fact table has 20 billion rows and 100 columns. Assume an average of 8 bytes per column value: 800 bytes per row, 16 TB uncompressed. A query sums one column grouped by two others (3 columns). A row store reads all 16 TB. The column store reads 3 × 8 bytes × 20 billion = 480 GB uncompressed; with 5 times compression that is about 96 GB on disk. If a date filter lets zone maps skip 90 percent of the row groups, only about 10 GB is read. On 20 nodes each scanning 1 GB/s of compressed data (20 GB/s total), that takes under a second of I/O, plus decompression, aggregation and shuffle, so a result in a few seconds is realistic. The same query on a row store would spend 16 TB / 20 GB/s, about 800 seconds in perfect conditions. This is the quantitative reason warehouses exist.

10.3 Time series: monitoring a fleet

Take 2,000 servers, each exposing 500 metrics, scraped every 15 seconds. Series = 2,000 × 500 = 1,000,000. Ingest rate = 1,000,000 / 15, about 67,000 samples per second. Samples per day = 67,000 × 86,400, about 5.8 billion. At about 1.5 bytes per compressed sample, that is roughly 8.7 GB per day, so 15 days of raw retention is about 130 GB, which fits on one well-provisioned Prometheus node. Memory for 1 million active series at a few KB each is a few GB. Long-term storage of a year at 5-minute rollups (20 times fewer samples, plus several aggregates) adds only a few tens of GB. Now a mistake: adding a pod-name label where pods churn daily multiplies series over time even if live pods stay constant, so cardinality is judged over the retention window as well as at an instant.

10.4 Vectors: memory for an index

One hundred million documents, 768-dimension embeddings, 4 bytes per float. Raw vectors take 100,000,000 × 768 × 4 bytes = about 307 GB. HNSW with M = 16 adds roughly 16 to 32 four-byte neighbour ids per vector on the bottom layer, about 100 to 150 bytes, or another 10 to 15 GB, so about 320 GB in memory: several large nodes, plus replicas for availability, so perhaps 6 to 8 machines. Using product quantization at 96 bytes per vector brings the vectors to about 9.6 GB (a 32 times reduction), small enough for one big node, at some recall cost that re-ranking from SSD-resident full vectors can recover. At one million vectors of 1,536 dimensions, raw data is 6 GB: pgvector on a normal PostgreSQL instance is entirely adequate. Query throughput scales with replicas; index builds and re-embedding when changing models are the costly events, so budget for them.

12. Interview Q&A

Why does HDFS use such a large block size, and what breaks if you make it small?

A large block (128 MB) keeps the NameNode's metadata small, because the number of block objects per terabyte falls as blocks grow, and it makes reads efficient, since the time to seek to a block is tiny compared with the time to stream it. With small blocks such as 4 KB, a petabyte would need hundreds of billions of metadata objects that could never fit in the NameNode's memory, and clients would spend most of their time asking for locations and seeking. The cost of big blocks is that small files waste metadata and tasks, and that parallelism is limited to the number of blocks in a file, so tuning is a balance. HDFS is designed for large sequential reads, so the large block fits it.

Walk through what happens when a DataNode dies in the middle of a write and later when it is gone for good.

During a write, the client notices that the pipeline stopped acknowledging, removes the failed node, and continues writing the current block through the remaining DataNodes; the NameNode learns that the block has fewer than three replicas. After the write, the NameNode schedules a copy of the block onto another node, chosen by the rack-aware policy, until three replicas exist. If a node later disappears, the NameNode stops receiving its heartbeats and, after the timeout (roughly ten minutes by default), marks it dead and re-replicates every block it held from the surviving copies. Throttling matters, because re-replicating a full node of several terabytes can saturate the network.

Why are column stores so much faster for analytics, and when are they the wrong choice?

A column store reads only the columns a query names, stores same-typed values together so they compress five to ten times, skips whole row groups using min and max statistics, and processes data in vectorized batches that use CPU caches and SIMD instructions. Together these cut the bytes read and the CPU per row by orders of magnitude for scans and aggregates. It is the wrong choice for workloads that fetch or update single complete rows at high rates, such as an order service, because rebuilding a row touches every column and small updates are expensive. For those, use a row-oriented transactional database and copy data to the column store for analysis.

Explain ETL versus ELT and where a data lake and a lakehouse fit.

In ETL you transform data in a separate engine before loading cleaned tables into the warehouse; in ELT you load raw data first and transform with SQL inside the warehouse, which suits elastic cloud warehouses and keeps raw data for reprocessing. A data lake stores raw files in open formats on cheap storage with schema applied at read time, which is flexible but historically unreliable because plain files lack transactions, updates and consistency. A lakehouse adds an open table format such as Iceberg or Delta Lake with a metadata layer that provides ACID commits, snapshots, time travel, schema evolution and row-level changes, so a single copy of the data can serve both warehouse-style SQL and data science. The choice between them is about governance and cost: a managed warehouse is the simplest, a lakehouse gives openness and avoids copying data.

How would you design the monitoring storage for 5 million active series, and what would you do about cardinality?

I would use a time-series database in a clustered or sharded form (for example Prometheus instances with a long-term backend such as Thanos, Mimir or VictoriaMetrics), sized by memory per active series, which at a few kilobytes each puts 5 million series at tens of gigabytes spread over several nodes. Ingest is 5 million divided by the scrape interval, so with 15-second scrapes about 330,000 samples per second, which compression handles at roughly 1.5 bytes per sample on disk. For cardinality I would define a naming and labelling policy that forbids unbounded values such as user ids and raw URLs, enforce per-tenant series limits that reject excess, alert on series growth rate, and pre-aggregate with recording rules. Raw data would be kept for about two weeks, and downsampled data for a year, with high-cardinality debugging done through logs and traces instead.

What is the difference between HNSW and IVF, and how do you choose?

HNSW is a layered proximity graph: a query walks greedily from a sparse top layer down to a dense bottom layer, which yields very high recall at low latency but needs the whole graph in memory and has awkward deletes. IVF clusters the vectors with k-means and scans only the nprobe nearest clusters; it builds faster, uses less memory, and combined with product quantization scales to billions of vectors, but its recall depends on cluster quality and nprobe and needs retraining as data drifts. For up to tens of millions of vectors with plenty of RAM and a need for top recall and speed I would pick HNSW; for very large corpora under a memory budget I would use IVF-PQ or a disk-based graph with re-ranking. In either case I tune the search-time parameter against measured recall on real queries.

How do you handle metadata filters, such as tenant or permission, in vector search?

Post-filtering the top K results is simple but can return too few results when the filter is selective, and pre-filtering with a fallback to brute force is exact but slow for mid-sized candidate sets. Most modern engines apply the filter during graph or list traversal, which works well unless the filter is extremely selective. In practice I partition by tenant (separate collection or namespace) so most queries search a smaller index, apply the finer filters in the index, and over-fetch candidates before filtering where needed. For permissions in RAG the filter is mandatory, not an optimization, so I make it part of the query and test that unauthorized chunks can never be retrieved.

When would you use pgvector and when a dedicated vector database?

I would use pgvector when the data already lives in PostgreSQL, the corpus is up to a few million to low tens of millions of vectors, and I benefit from transactions and joins between vectors and relational rows, because it avoids a new system and a synchronization pipeline. I would move to a dedicated vector database when I need hundreds of millions or billions of vectors, sharding and quantization, high query throughput isolated from the transactional workload, rich filtered or hybrid search, and managed scaling. Either way I treat the vector index as derived data that can be rebuilt from the source, and I keep the embedding model version so I can re-embed when it changes.

How do you keep a warehouse, a search index and a vector store in sync with the primary database?

I avoid dual writes from the application, because partial failures leave stores inconsistent. Instead I capture changes from the database log with CDC, publish them to a durable stream such as Kafka partitioned by entity id, and let each store have its own consumer that applies idempotent upserts and deletes. This keeps the primary lightly loaded, preserves commit order per key, lets each consumer fall behind or fail independently, and allows replay for backfills and rebuilds. I monitor consumer lag, handle deletes as explicit events, version the schema through a registry, and load warehouses in micro-batches rather than single rows.

What is the downside of a single NameNode design, and how do modern deployments mitigate it?

A single master simplifies consistency, since one process orders all namespace changes, but it is a single point of failure and a memory and throughput ceiling for the namespace. HDFS addresses availability with an active and a standby NameNode sharing an edit log through a quorum of JournalNodes, automatic failover through ZooKeeper, and fencing so the old active cannot write. It addresses scale with federation, which splits the namespace across several independent NameNodes, and by encouraging large files. Cloud designs often sidestep the problem by using object storage, where metadata is itself a distributed service.

What is a ledger database for, and how would you get immutability without a special product?

A ledger database keeps an append-only history with cryptographic hash chaining so that any later tampering with a past record is detectable, which is valuable for financial, audit and compliance data. Without a special product, I would model transactions as double-entry postings in an append-only journal table, make corrections as new compensating entries, remove update and delete rights, derive balances from the journal, and periodically store a hash of recent entries in an external write-once location. The main tradeoffs are ever-growing storage and conflict with erasure laws, which I handle by keeping personal data outside the immutable log and referencing it by an id that can be deleted.

13. Recap

  • Specialized stores win by dropping general flexibility to fit one access pattern: giant sequential files, wide scans and aggregates, timestamped appends, or similarity search.
  • HDFS and GFS split a small, memory-resident metadata master from many data-holding nodes, store 128 MB (or 64 MB) blocks replicated three times with rack-aware placement, pipeline writes, read directly from the nearest replica, suffer from small files, and reach high availability with a standby NameNode, a JournalNode quorum and fencing.
  • Warehouses are columnar, compressed and vectorized, run in parallel (MPP) over star-schema data, separate storage from compute in the cloud, are fed by ETL or ELT, and lakehouse formats (Iceberg, Delta) add transactions and time travel to files in a lake.
  • Time-series databases exploit append-only, time-ordered data with time-chunked blocks, delta and XOR compression, downsampling and cheap retention; their enemy is high cardinality from unbounded tags.
  • Vector databases index embeddings for approximate nearest-neighbour search: HNSW (graph, fast, memory-hungry) and IVF with quantization (clusters, compact), trading recall against latency, with filtering as the hard part; start with pgvector, go dedicated at large scale.
  • In-memory grids add co-located compute and queryable distributed RAM; ledger stores add tamper-evident history through hash chains and append-only journals.
  • Feed these derived stores with CDC and event streams, never dual writes, with idempotent consumers, explicit deletes and a rebuild path.
  • Every added store is an operational burden; choose it from measured need and keep the ability to rebuild it from the source of truth.
