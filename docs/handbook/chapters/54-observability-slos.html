Chapter 54 · Module 8 · Cross-Cutting Concerns

Observability and SLOs

A system you cannot see into is a system you cannot run. This chapter explains how to instrument a service with logs, metrics and traces, how to turn raw numbers into service level objectives that mean something to users, how error budgets and burn-rate alerts replace noisy threshold paging, and what to say about monitoring in every system design interview.

1. Monitoring versus observability

When you draw a design on a whiteboard, everything works. In production, things fail in ways you did not draw: a disk fills up, one dependency gets slow, a bad deploy corrupts a fraction of requests, one customer sends a pattern you never imagined. Observability is the property that lets you work out what is happening inside the system, and why, from the data it emits, without shipping new code first.

The two words are related but not identical. Monitoring is the practice of watching a predefined set of signals and reacting when they cross a line. You decide in advance which questions matter ("is CPU above 90%?", "is the error rate above 1%?") and build dashboards and alerts for them. Monitoring answers known unknowns: failure modes you already anticipated. Observability is the broader ability to ask new questions after the fact: "why are requests from tenant 4471 on the Android app slow, but only for the checkout endpoint, only since 14:05?" That is an unknown unknown: nobody wrote an alert for it. You can answer it only if the telemetry is rich enough (high-detail events, traces with attributes, the ability to slice and group by arbitrary fields).

In a design, state what each component emits (metrics, structured logs, trace spans), where it goes, and which alerts and objectives are built on it. A design with no answer to "how will we know it is broken, and why?" is incomplete.

2. The three pillars, plus events and profiles

Telemetry is usually grouped into three kinds, called the three pillars. They are not rivals. Each is best at one job, and a good incident uses all three in sequence: a metric tells you something is wrong, a trace shows where in the request path, and logs show the exact detail.

2.1 Logs

A log is a timestamped record of a discrete thing that happened: "payment 8841 declined, reason insufficient_funds". Logs carry the most detail and context, and they are the right tool for answering "what exactly happened to this one request?" They are also the most expensive per unit of insight: they are large, they are written for every event (not summarized), and searching across terabytes is slow and costly. Logs are best for forensic detail, audit trails, and errors with stack traces.

2.2 Metrics

A metric is a number measured over time: requests per second, error count, queue depth, memory in use. A metric is an aggregate: it throws away the individual events and keeps a compact summary, one data point per time interval. That makes metrics cheap, fast to query, and ideal for dashboards, trend analysis and alerting. The price is lost detail: a metric can say "p99 latency rose", but not which request was slow. Metrics are best for detecting and alerting and for long-term trends and capacity.

2.3 Traces

A trace records the path of one request as it crosses components. It is a tree of spans, each span being one unit of work (an HTTP handler, a database query, a call to another service) with a start time, a duration and attributes. Traces answer "where did the time go for this request?" and "which downstream call failed?". They are essential in microservices, where no single log file shows the whole story. Chapter 52 (Observability for Microservices) covers context propagation, sampling at scale, and trace pipelines in depth; here we only need the basics (section 7).

2.4 Events and profiles

Two further signals are worth naming. A structured event (sometimes called a "wide event" or canonical log line) is one rich record emitted per unit of work, such as one per request, with dozens of fields: user id, tenant, endpoint, build version, region, each downstream latency, outcome. Because every field is queryable, you can group and filter on any combination, which is exactly what unknown-unknown debugging needs. Many teams treat the wide event as the core observability primitive and derive metrics and traces from it. Business events (order placed, payment captured) are a related idea: they let you measure outcomes the user cares about rather than technical proxies.

Profiles record where a process spends CPU time or memory at the code level (which functions, which allocation sites). Continuous profiling, with low overhead sampling, answers "why is this service using so much CPU?" at a level that metrics and traces cannot. See section 15.

Interview tip If asked "how would you monitor this?", do not list tools. Say which signal answers which question: metrics for detection and SLOs, traces for locating latency across services, logs for exact detail, profiles for CPU or memory hot spots. Then name the user-facing SLO that anchors it all.

3. Metrics in depth

3.1 Metric types

Almost every metrics system (Prometheus, StatsD, OpenTelemetry, CloudWatch) offers the same handful of types. Choosing the right type matters because it decides what you can compute later.

CounterA value that only goes up (resets to zero on process restart)http_requests_total, errors_total, bytes_sent_totalQuery it as a rate (per second over a window). The raw value is meaningless; the rate is the signal. Resets are detected and handled by the rate function.
GaugeA value that goes up and down; a snapshot of the current statequeue_depth, memory_in_use, active_connections, temperatureRead the current value, or its min/max/avg over time. Be careful: sampling a gauge every 15 s can miss a spike between samples.

3.2 Dimensions (labels) and cardinality

A metric alone ("request count") is rarely useful. You attach labels (also called tags or dimensions) such as service, endpoint, status, region. Each distinct combination of label values is a separate time series, stored and indexed on its own. The number of distinct series is the metric's cardinality.

Cardinality is the single most common way metrics systems fall over. Series count multiplies across labels. If you have 20 endpoints, 5 status classes and 3 regions, that is 20 × 5 × 3 = 300 series: fine. If you add a user_id label with 1,000,000 users, you now have 300 × 1,000,000 = 300 million series. Every series costs memory in the index and storage on disk (typically a few kilobytes of memory each in a Prometheus-style system), so the server runs out of memory or the bill explodes. The rule: labels must have a small, bounded set of values. Never put user ids, request ids, emails, full URLs with ids, or timestamps in labels. Normalize the route (/orders/{id} rather than /orders/8841). High-cardinality detail belongs in logs, traces or wide events, which are designed to hold it.

3.3 Push versus pull collection

There are two ways metrics get from your service into the metrics store.

  • Pull (scrape), as in Prometheus. Each service exposes an HTTP endpoint (often /metrics) that lists its current metric values as text. The Prometheus server, on a schedule (commonly every 15 or 30 seconds), discovers targets through service discovery (Kubernetes, Consul, cloud APIs) and fetches each endpoint. Advantages: the monitoring system controls the load and rate; a failed scrape is itself a signal (the built-in up metric turns 0, so you detect dead services for free); you can curl an endpoint by hand to debug; services need no knowledge of the monitoring backend. Disadvantages: short-lived jobs may finish before being scraped; targets behind NAT or firewalls are hard to reach; very large fleets need sharded scrapers.
  • Push, as in StatsD, OpenTelemetry exporters, CloudWatch agents. Each service (or a local agent) sends its metrics to a collector on its own schedule. Advantages: works for short-lived batch jobs, serverless functions and clients behind firewalls; the sender decides when. Disadvantages: the backend can be overwhelmed by a burst of senders; a silent service looks the same as a healthy quiet one unless you add explicit heartbeat checks; you must configure the destination in every service.

In practice both coexist: Prometheus scrapes long-running services, and batch jobs push their final numbers to a small intermediary (the Pushgateway) which Prometheus then scrapes. OpenTelemetry collectors can do either and fan data out to several backends.

3.4 Time-series storage and rollups

Metrics are stored in a time-series database (TSDB): Prometheus' own TSDB, VictoriaMetrics, InfluxDB, M3, Mimir/Thanos for scale-out, or a managed service. A series is identified by its metric name plus its labels, and its data is a list of (timestamp, value) pairs. Because values change slowly and timestamps are regular, TSDBs compress extremely well: delta-of-delta encoding for timestamps and XOR-style encoding for floating-point values (the Gorilla technique) commonly get a sample down to one or two bytes on average instead of 16.

A back-of-envelope estimate (see Chapter 2 for the method): 100,000 active series, each scraped every 15 s, produce 100,000 / 15 ≈ 6,700 samples per second, or about 576 million samples per day. At roughly 1.5 bytes per compressed sample that is under 1 GB per day. Storage is rarely the problem; the number of active series and the cost of queries are.

Retention and rollups. Keeping every 15-second sample forever is wasteful. The usual policy is to keep raw resolution for a short time (for example 15 days), then downsample to coarser rollups: 5-minute averages (plus min, max, count) kept for months, and 1-hour rollups kept for years. Dashboards for last-week debugging use raw data; capacity planning over a year uses the rollups. Note the catch: you can roll up counters and histogram buckets safely (sums stay correct), but a rolled-up percentile is wrong. This is why you store histogram buckets, not precomputed percentiles.

4. Percentiles, and why averages lie

The average (mean) of latency hides the experience of the unlucky users. Latency distributions are not bell-shaped; they have a long tail of slow requests caused by garbage collection pauses, cache misses, lock contention, retries, cold starts, and slow dependencies. A percentile describes the value below which a given share of observations fall: p50 (the median) means half of requests are faster; p99 means 99% are faster and 1% are slower.

A small example. Take 1,000 requests: 980 finish in 100 ms and 20 finish in 10,000 ms (a slow dependency timing out). The mean is (980 × 100 + 20 × 10,000) / 1,000 = (98,000 + 200,000) / 1,000 = 298 ms. That number describes nobody: no request took 298 ms. The median is 100 ms, which hides the 2% in trouble. The p99 is 10,000 ms, which exposes it. And 2% sounds small until you realize a page that makes 30 backend calls will, with probability 1 - 0.9830 ≈ 45%, hit at least one slow call. Tail latency is amplified by fan-out, which is why Chapter 40 treats it as a first-class problem. Percentile arithmetic was introduced in Chapter 2.

4.1 Which percentiles, and what they cost

p50 shows typical experience, p95 and p99 show the experience of a meaningful tail, and p99.9 matters at high volume (one in a thousand of a billion requests is a million unhappy requests). Higher percentiles need more samples to measure accurately and are noisier. Always report latency per outcome: a flood of fast failures (an instant 500) drags percentiles down and makes a broken service look fast, so measure the latency of successful requests separately from errors.

4.2 Aggregating percentiles

This is a classic trap. Suppose server A handled 100 requests with a p99 of 200 ms, and server B handled 900 requests with a p99 of 2,000 ms. What is the fleet p99? Averaging gives (200 + 2,000) / 2 = 1,100 ms; weighting by traffic gives about 1,820 ms. Neither is right. A percentile of percentiles has no mathematical meaning. The true fleet p99 depends on the full distributions, and it could be anywhere between the two values.

The correct approach is to aggregate the underlying distribution, not the summary. Each server exports a histogram with the same bucket boundaries. You add the bucket counts across servers (counts are additive), then compute the percentile from the merged histogram by finding the bucket where the cumulative count crosses 99% and interpolating inside it. This is what Prometheus' histogram_quantile does over summed buckets. The cost is accuracy limited by bucket width: if one bucket spans 500 ms to 1 s, a p99 inside it is only known to that range, so choose boundaries around your SLO threshold (for example, a bucket edge exactly at 300 ms if the SLO says "under 300 ms"). Newer designs (Prometheus native histograms, HDR histograms, t-digest, DDSketch) use mergeable sketches with bounded relative error and no hand-chosen buckets.

Watch out Never average percentiles across hosts, regions or time windows. Store histograms (or sketches), sum them, then derive the percentile. Also beware averaging the averages of unequal-traffic groups: weight by request count.

5. Frameworks: RED, USE and the four golden signals

With thousands of possible metrics you need a checklist for what to put on the first dashboard of any service. Three well-known frameworks give it to you.

5.1 RED (for request-driven services)

Coined by Tom Wilkie, RED says: for every service that handles requests, track the Rate (requests per second), Errors (failed requests per second or as a fraction), and Duration (the latency distribution, as percentiles). It measures the service from the point of view of its callers. It is the right default for APIs and microservices.

5.2 USE (for resources)

Brendan Gregg's USE method applies to resources (CPU, memory, disk, network interface, connection pool, thread pool): for each one, check Utilization (percent of time or capacity in use), Saturation (extra work queued that cannot be served yet, such as run-queue length or pending connections), and Errors (error events such as dropped packets or disk errors). It measures the system from the inside. A resource at 100% utilization with a growing queue is the classic bottleneck.

5.3 The four golden signals

From Google's SRE book: latency (time to serve a request, tracked separately for successes and errors), traffic (demand on the system, such as requests per second), errors (rate of failing requests, including wrong content and policy failures such as responses slower than a limit), and saturation (how full the service is, emphasizing the most constrained resource and often a leading indicator of trouble). The golden signals are essentially RED plus saturation.

FrameworkApplies toSignalsAnswers

USEResources (CPU, disk, pool)Utilization, Saturation, ErrorsWhich resource is the bottleneck?

6. Logging best practices

6.1 Structure the logs

Free-text lines like Payment failed for user 8841 because card declined are readable by humans but painful for machines: to count declines per reason you need fragile regular expressions. Structured logging writes each event as key-value data, usually JSON, so every field is indexed and queryable:

{"ts":"2026-11-17T14:05:09.311Z","level":"WARN","service":"payments",
 "version":"v412","region":"us-east-1","trace_id":"4bf92f3577b34da6",
 "request_id":"req-77f1","tenant":"t-4471","event":"payment_declined",
 "reason":"insufficient_funds","amount_cents":4599,"duration_ms":212}

Use a stable schema and consistent field names across all services (the same name for the trace id and tenant everywhere), or cross-service queries become impossible. Log one event per fact, not a paragraph of prose.

6.2 Use levels with discipline

LevelMeaningTypical use
ERRORAn operation failed and needs attention; the request or job did not succeedUnhandled exception, dependency failure after retries
WARNSomething unexpected but handled; may become a problemRetry succeeded, fallback used, deprecated call
INFONormal, significant business or lifecycle eventsService started, order placed (not every function call)
DEBUG / TRACEDeveloper detail, very chattyOff in production by default; switchable at runtime per service or per request

The error level should be trustworthy: if ERROR fires for expected conditions such as a user typing a wrong password, people stop looking at it. A single ERROR per failed request (logged where it is handled, not at every layer it passes through) avoids the duplicate stack traces that inflate volume.

6.3 Correlation ids

A correlation id (request id or trace id) is generated at the edge (gateway or first service) and attached to every log line, every downstream call (as an HTTP header such as traceparent), and every message produced. Searching for one id then returns every log line produced by every service for that request. Without it, reconstructing a request across ten services means guessing from timestamps. Put it in the logging context (a thread-local or async context) so developers do not have to pass it manually. Chapter 52 goes deeper on propagation.

6.4 Sampling and volume

Logging everything at INFO for a service doing 5,000 requests per second adds up quickly. Suppose each request writes 5 lines of 500 bytes: 5,000 × 5 × 500 B = 12.5 MB per second, about 1.08 TB per day for one service. Control volume with: lower default levels; head sampling (keep 1 in N of routine success events); tail-aware sampling (always keep errors and slow requests, sample the rest); rate-limiting repeated identical messages; dropping health-check noise; and keeping debug logs in a short-retention tier. Keep 100% of errors and security or audit events.

6.5 Cost, privacy and safety

Log storage and indexing is often the largest observability bill (section 16). Tier it: hot indexed storage for a few days, cheap object storage for months. Never log secrets or personal data (passwords, tokens, full card numbers, health data); redact or hash at the logging layer, because logs are widely readable, are copied into third-party tools, and are covered by privacy regulation. Log asynchronously to a buffer so a slow log pipeline cannot block requests, and decide explicitly what to do when the buffer fills (drop logs, never block the request path).

7. Tracing basics

A trace answers "where did this request spend its time?". Each unit of work is a span. When service A calls service B, A passes the trace context (trace id and the id of the calling span) in a header, standardized as W3C traceparent. B starts a child span with that parent, so the spans link into a tree. Each span records start, duration, a name, attributes (such as http.status_code, db.statement shape, tenant), and an error flag. Spans are sent asynchronously to a collector and a backend (Jaeger, Tempo, Zipkin, vendor tools), which assemble them by trace id. OpenTelemetry is the vendor-neutral standard for generating and exporting this data.

Two key practical points. First, sampling: tracing every request at high volume is costly, so you keep a fraction. Head-based sampling decides at the start (for example keep 1%); it is cheap but may discard the interesting slow or failed requests. Tail-based sampling decides after the trace completes, keeping all errors and slow traces, but needs a collector that buffers whole traces. Second, exemplars link metrics to traces: a latency histogram bucket can carry the trace id of one representative slow request, so you click from a p99 spike on a graph straight to an example trace. For propagation across queues, async boundaries, baggage, and the pipeline architecture, read Chapter 52.

8. SLI, SLO and SLA

Raw metrics tell you what the system is doing. They do not tell you whether that is good enough. Three terms turn measurements into agreements.

  • SLI (Service Level Indicator): a carefully chosen measurement of one aspect of service quality, expressed as a ratio of good events to valid events over a window. For example, "the fraction of checkout requests that returned a non-5xx response in under 800 ms".
  • SLO (Service Level Objective): a target value for an SLI over a period. For example, "99.9% of checkout requests are good, measured over a rolling 30 days". It is an internal engineering goal.
  • SLA (Service Level Agreement): a contract with customers that states consequences (refunds, credits) if a promise is missed. An SLA is usually looser than the internal SLO, so you have a safety margin: you might promise 99.5% externally while running to 99.9% internally.

8.1 What makes a good SLI

A good SLI reflects what a user experiences, is measured as close to the user as practical (at the load balancer or client rather than deep in a service), and is expressed as a proportion: good events / valid events. A proportion makes every SLI directly comparable to a percentage target and makes error budgets simple arithmetic. CPU usage and "server up" are poor SLIs: a server can be up and serving errors, and users do not care about CPU.

CategoryExample SLI (good / valid)Notes
AvailabilityRequests answered without a server error (not 5xx, not timed out) / all valid requestsExclude client mistakes (4xx) from "bad" but count them as valid only if they are the user's fault; decide explicitly.
LatencyRequests served successfully in under 300 ms / all successful requestsUse a threshold form ("fraction faster than X") rather than a raw percentile; it is additive and fits budget math. Use two thresholds (for example 95% under 300 ms and 99% under 1 s).
FreshnessData records updated within 5 minutes of source change / all records (or minutes during which the newest data is under 5 minutes old)For caches, search indexes, replicas, dashboards, ML features.

Key idea Define SLIs from the user's journey, not from component health. The question is "was this user request good?", not "is this box healthy?". Components can be 99.99% healthy each while the end-to-end journey is far worse, because failures multiply along the path.

8.2 Choosing SLO targets

The most common mistake is aiming at 100%. It is impossible (the user's own phone and network fail more often than that), it costs enormously more with each extra nine, and it leaves no room to ship changes. Targets should come from user need and cost, not ambition.

Each extra nine cuts the allowed downtime tenfold, which usually means a different architecture (multi-region active-active instead of one region with backups, see Chapter 41). Over a 30-day month (43,200 minutes):

Set different targets for different journeys (section 10.4) rather than one number for the whole product. Remember that your SLO cannot exceed what your dependencies allow (section 10.2).

9. Error budgets and policy

The error budget is the complement of the SLO: the amount of unreliability you are allowed. With a 99.9% SLO the budget is 0.1% of requests (or 43.2 minutes of full outage per 30 days). The budget reframes reliability as a resource to spend rather than a quantity to maximize. Spend it on risky launches, experiments, migrations, and deploys; if you are not using it, you are probably moving too slowly. If you are burning it too fast, you must slow down and invest in reliability.

The budget is made operational by an error budget policy, agreed in advance by engineering and product so it is not renegotiated during a crisis. A typical policy:

  • Budget remaining above 50%: ship normally, take planned risk.
  • Below 25%: extra review for risky changes; prioritize reliability work in the next sprint.
  • Exhausted (0%): freeze feature releases; only fixes for reliability, security and the cause of the burn may ship, until the budget recovers or the window rolls forward.
  • A single incident that consumes more than, say, 20% of the budget requires a blameless postmortem with tracked follow-ups.

Numeric example. A service averages 100 requests per second. Over 30 days that is 100 × 86,400 × 30 = 259,200,000 requests. At a 99.9% SLO the budget is 0.1% = 259,200 bad requests. If a bad deploy makes 20% of requests fail for 10 minutes, bad requests = 100 × 600 × 0.20 = 12,000, which is 12,000 / 259,200 ≈ 4.6% of the monthly budget. A full outage for 43.2 minutes would use exactly all of it.

Interview tip Mention that the error budget aligns incentives: developers want to ship, SRE wants stability, and the budget gives a neutral, numeric rule. It ends arguments of the form "is this risky?" with "do we have budget?".

10. Designing SLOs: windows, dependencies, async work, journeys

10.1 Rolling versus calendar windows

A calendar window (this month, this quarter) resets to a full budget on a fixed date. It matches business reporting and SLAs, but it creates odd behavior: a disaster on the 2nd leaves the team frozen for four weeks, while a disaster on the 29th is forgiven in two days, and teams gamble near the reset. A rolling window (the trailing 28 or 30 days) always looks at the recent past, so old incidents age out gradually and the budget reflects current health. Rolling windows are better for operations and alerting; calendar windows are often kept for contractual SLAs. A common choice is a rolling 28 days, which always contains exactly four weeks and so the same number of each weekday. Shorter windows (7 days) react faster but are noisier; longer windows (90 days) smooth out but forgive recent problems.

10.2 Composite SLOs and dependencies

If a request needs several components in series, its availability is roughly the product of theirs. A checkout that depends on the API gateway (99.99%), the order service (99.95%), the payment provider (99.9%) and the database (99.99%) has at best 0.9999 × 0.9995 × 0.999 × 0.9999 ≈ 0.9983, about 99.83%. That is below 99.9% even though every part looks excellent. So you cannot promise more than your hard dependencies deliver unless you remove them from the critical path.

Ways to do better than the product: make dependencies soft with timeouts, retries, circuit breakers and fallbacks (Chapter 40); take work off the synchronous path by queuing it; add redundancy so that two independent providers in parallel give 1 - (0.001 × 0.001) = 99.9999% for that hop in the ideal independent case; and use multi-AZ or multi-region designs (Chapter 41). Each internal service should also have its own SLO, and the SLO of a caller should be justified by the SLOs of its callees. Beware of correlated failure: two providers sharing one cloud region are not independent.

For a user-facing composite SLO, you can either compute it from component SLOs (a model) or, better, measure it end to end at the edge, since measurement beats arithmetic.

10.3 SLOs for async and batch pipelines

Request/response SLIs do not fit a nightly job or a Kafka consumer, where no user is waiting on a single call. Use SLIs that express timeliness and completeness:

  • Freshness: the age of the newest data in the output. "99% of the time, the analytics table is no more than 15 minutes behind the source."
  • Lag: consumer group lag (messages or seconds behind) kept under a limit; for queues, the age of the oldest message.
  • Deadline success: "98% of nightly batch runs finish before 06:00."
  • Completeness and correctness: the fraction of input records that appear correctly in the output (compared by counts, checksums or reconciliation); the fraction of messages that go to a dead-letter queue.
  • Throughput / time to process: events handled within N seconds of arrival at the 99th percentile.

Alert on the SLI breach trend, for example a growing lag whose projected catch-up time exceeds the deadline, rather than on a single failed run. Batch pipelines are covered in Chapter 37.

10.4 SLOs per user journey

A product has many journeys with very different importance. Browsing a catalog and paying for an order should not share one number. Pick critical user journeys (CUJs): the handful of paths that define value (sign in, search, add to cart, checkout, view order). Define an availability and latency SLI for each, and set targets by importance: checkout might be 99.95% and 1 s at p95 while recommendations are 99.5% and degrade gracefully. This focuses effort and alerts where the business is hurt, and it lets you deliberately degrade the less important journey to protect the critical one during overload.

11. Alerting

An alert is a request for a human to do something. Its purpose is to get the right person to act on a problem that matters, in time, with enough context, and not otherwise. The art is mostly in what you do not alert on.

11.1 Symptoms versus causes

A symptom is what a user feels: errors, slowness, wrong data. A cause is an internal condition that might lead to a symptom: high CPU, a full disk, a slow replica, a pod restart. The guidance from Google's SRE practice: page on symptoms, investigate causes. High CPU on one node is not necessarily a problem (the load balancer may be fine); paging for it wakes someone for nothing, while a real user-visible failure from an unforeseen cause would never fire a cause-based alert. Symptom alerts cover every cause, including ones you never thought of. Cause-based alerts still have value for leading indicators that are certain to become symptoms soon (a disk 95% full and filling, a certificate expiring in 3 days) and for dashboards used in diagnosis.

11.2 Paging versus ticket

Not every alert deserves a 3 a.m. phone call. A simple rule: page only if the condition is urgent (users are hurt now or the budget will be exhausted soon), actionable (a human can do something) and needs a human right now. Everything else becomes a ticket (handled in business hours) or a dashboard annotation / email digest. A slow burn that will exhaust the budget in a week is a ticket; a fast burn that will exhaust it in two hours is a page.

11.3 Static thresholds versus burn-rate alerts

The naive alert is "error rate above 1% for 5 minutes". It has two problems. It is blind to the SLO: 1% might be a disaster for a 99.99% objective or harmless for a 99% one. And it either fires on every harmless blip (short window, noisy) or reacts too slowly (long window). Burn-rate alerting ties the alert directly to the error budget.

The burn rate is how fast the budget is being consumed relative to the "exactly on budget" speed. A burn rate of 1 means that, if the error rate persists, the budget will be fully used exactly at the end of the SLO window. A burn rate of 10 means the budget would be gone in one tenth of the window. Formally: burn rate = observed error ratio / allowed error ratio (1 - SLO).

Example for a 99.9% SLO over 30 days (allowed error ratio 0.001, window 720 hours): if the observed error ratio over the last hour is 1.44%, the burn rate is 0.0144 / 0.001 = 14.4. At that speed the whole budget lasts 720 / 14.4 = 50 hours, and in one hour you have already spent 14.4 / 720 = 2% of the monthly budget.

11.4 Multi-window, multi-burn-rate alerts

One burn-rate rule is still not enough. A very high burn needs a fast, sensitive alert; a modest burn that continues for days needs a slower, more patient one. And any rule using only a long window keeps firing for a long time after the problem is fixed (the long window still contains the bad period), while a short window alone is noisy. The solution, recommended in Google's SRE Workbook, is to combine several burn rates, each requiring two windows to agree: a long window to prove the problem is significant, and a short window (about one twelfth of the long one) to prove it is still happening now, so the alert resets quickly after recovery.

SeverityBurn rateLong windowShort windowBudget spent at firingError ratio needed (99.9% SLO)
Page (fast burn)14.41 hour5 min2%1.44% (14.4 × 0.001)
Page (medium burn)66 hours30 min5%0.6%
Ticket (slow burn)13 days6 hours10%0.1%

How the budget percentages arise: budget spent = burn rate × window length / SLO window. For the first row: 14.4 × 1 h / 720 h = 2%. Second: 6 × 6 / 720 = 5%. Third: 1 × 72 h / 720 h = 10%. Each rule fires when both its long and short windows exceed the threshold.

Walk through. At 14:00 a bad deploy makes 3% of requests fail. After 5 minutes the 5-minute error ratio is about 3%, above 1.44%, but the 1-hour ratio is only about (5 min × 3%) / 60 min = 0.25%, below the threshold, so the page does not fire yet. As bad minutes accumulate, the 1-hour ratio reaches 1.44% after about 29 minutes (29 × 3% / 60 = 1.45%). At that moment both windows exceed the 14.4x threshold and the page fires, with about 2% of the monthly budget already spent. When the team rolls back at 14:40, the 5-minute window drops under the limit within about 5 minutes, so the alert clears quickly even though the 1-hour window still holds the old errors. Meanwhile a quiet 0.2% error ratio sustained for days would trip only the ticket rule. A total outage (burn rate 1,000) is caught much faster: the 1-hour ratio reaches 1.44% after only 0.0144 × 60 min ≈ 0.9 minutes of failure, so the page fires in about a minute once the short window also confirms.

Why this works Burn-rate alerts are tied to what you promised users: they fire fast for big outages (precision, detection time in minutes), stay quiet for blips that cost almost no budget (fewer false pages), catch slow leaks that thresholds miss (recall), and reset quickly (the short window). Low-traffic services need care: a few failures out of ten requests make ratios jumpy, so add a minimum request count or use longer windows or synthetic traffic.

11.5 Alert fatigue, runbooks, grouping and on-call

Alert fatigue is what happens when humans receive more alerts than they can act on: they start ignoring them, and a real page gets lost in the noise. It is a reliability risk, not just an annoyance. Counter it with a ruthless review: every alert must be actionable, urgent, and tied to a user symptom; track the signal-to-noise ratio (fraction of pages that led to action); delete or downgrade alerts that do not; keep pages per on-call shift small (a common target is at most two incidents per 12-hour shift).

  • Runbooks: every page links to a runbook: what the alert means, how to confirm, dashboards to open, the first mitigation steps (rollback, fail over, scale, disable a feature flag), who to escalate to. Good runbooks make the 3 a.m. responder effective; the best runbooks become automation.
  • Deduplication and grouping: one root cause (a database failing) can trigger hundreds of alerts across dependent services. Alert managers (Prometheus Alertmanager, PagerDuty, Opsgenie) group alerts by labels (cluster, service) into one notification, deduplicate repeated firings of the same alert, inhibit dependent alerts when a parent alert is active (do not page about 40 services being slow if the shared database is already paging), and silence alerts during planned maintenance.
  • Routing and escalation: alerts route to the owning team's rotation; if not acknowledged within, say, 5 minutes, they escalate to a secondary and then a manager.
  • On-call health: follow-the-sun rotations where possible, a primary and secondary, reasonable load, time off after a rough night, and compensation. A burned-out on-call rotation is itself an availability risk. Review every page in a weekly handoff meeting.

12. Dashboards that work, and health endpoints

12.1 Dashboards

A dashboard is a tool for answering a question quickly; a wall of 60 graphs answers none. Build a small hierarchy, each level with a purpose:

  1. Service overview (the top of every on-call session): SLI and SLO status with remaining error budget, then RED: request rate, error ratio, latency p50/p95/p99, all split by the dimensions you will want when something breaks (endpoint, region, version). Put the most important graph at the top left.
  2. Dependency and resource panels (USE): saturation of pools, queues, CPU, memory, disk; health and latency of each downstream call, so you can tell "I am slow" from "my dependency is slow".
  3. Deploy and change markers: overlay deploys, config changes and feature-flag flips as vertical lines. Most incidents start with a change, and seeing it on the graph saves minutes.
  4. Drill-down dashboards: per-endpoint, per-tenant, per-shard views reached by clicking through, with links to logs and traces filtered to the same time range and labels.

Rules of thumb: show percentiles and rates, not averages; use consistent time ranges and aligned axes; draw the SLO threshold as a line on the graph; show the unit on every axis; avoid pie charts and decorative gauges; put counts next to ratios (a 50% error rate on 2 requests is not an emergency); and delete dashboards nobody opens. A dashboard is for diagnosis, not for alerting: do not depend on someone staring at a screen.

12.2 Health endpoints

Orchestrators and load balancers need a cheap way to ask a process "are you OK?". Distinguish the questions, because answering the wrong one causes outages:

ProbeQuestionIf it failsWhat it should check
LivenessIs the process alive and not deadlocked?Orchestrator restarts itOnly the process itself. Never check dependencies; if the database is down, restarting every app server makes things worse.
ReadinessCan it take traffic right now?Load balancer stops routing to it (no restart)Warm-up finished, local caches loaded, critical connections up. Be careful with dependency checks: if all instances fail readiness because a shared dependency blips, you create a total outage.
StartupHas it finished booting?Delays other probesSlow-starting apps (JVM warm-up, migrations).
Deep / dependency checkIs each dependency reachable?Informational, for dashboards and humansRun less often, with timeouts, and do not wire it to automatic restarts.

Health endpoints must be fast, unauthenticated or lightly authenticated within the network, and cheap, since they are hit constantly. They also support graceful shutdown: on termination, a service fails readiness first, drains in-flight requests, then exits, so deploys do not drop traffic (see Chapter 40 and the deployment chapter).

13. Synthetic monitoring, real-user monitoring and capacity

13.1 Synthetic monitoring and canaries

Synthetic monitoring means you run scripted fake users on a schedule from several locations and record success and timing: ping the health URL every minute, or run a full scripted journey (log in, add an item to the cart, check out against a test account). Because the traffic is constant and known, it detects problems even when real traffic is zero (at night, in a new region, on a rarely used endpoint). It gives a clean availability baseline unaffected by user behavior, and it tests what internal metrics cannot: DNS, TLS certificate expiry, CDN, and whether the site is reachable from outside your network. Limitations: it covers only the paths you scripted, and a green probe does not prove every real user is fine.

A canary is synthetic or real traffic used to judge a change. During a rollout, a small slice (1-5%) of real traffic is sent to the new version while the SLIs of canary and baseline are compared automatically; if the canary's error ratio or latency is significantly worse, the rollout halts and rolls back. This turns observability into a deployment safety net and keeps bad releases from consuming much error budget. Synthetic probes against a canary instance also validate it before it takes real traffic.

13.2 Real-user monitoring (RUM)

Real-user monitoring collects measurements from actual users' browsers and apps: page load phases and Core Web Vitals (largest contentful paint, interaction responsiveness, layout shift), JavaScript errors, API call durations as seen from the client, crash rates, and geography, device and network type. It reveals what server-side metrics cannot: a 40 ms backend can still mean a 4 s page because of a heavy script, a bad CDN node in one country, or a slow mobile network. RUM data is sampled, aggregated by beacons sent to a collector, and must respect privacy (consent, no personal data). Synthetic and RUM complement each other: synthetic is controlled and always-on; RUM is the truth about real conditions but depends on traffic.

13.3 Capacity and saturation monitoring

Saturation is the leading indicator: systems degrade sharply as a resource approaches full, because queues grow nonlinearly (see Little's Law and utilization in Chapter 2). A server at 60% CPU may have mild queueing; at 95% latency can explode. Track, for each constrained resource, its utilization and its queue or wait: CPU run queue, thread-pool queue length and rejections, database connection-pool wait time, disk IOPS and latency, network bandwidth, memory and garbage-collection pauses, Kafka consumer lag, file descriptors, and quota limits on managed services (cloud API limits are a classic surprise).

Use it two ways. Alerting: alert on predicted exhaustion ("disk full in under 4 hours at the current growth", using a linear projection) as a ticket or page by urgency. Planning: compare peak demand to capacity with headroom. If peak traffic is 3x average and a node saturates at 70% target utilization, size the fleet for the peak plus N+1 or N+2 for failures; track the growth trend from long-retention rollups to forecast when to add capacity. Load tests find the real saturation point; autoscaling (see Chapter 43) reacts to it but needs headroom and warm-up time.

14. Incident response lifecycle

An incident is an event that harms or threatens users, such as a spike in checkout errors. Observability exists to make incident response shorter and calmer. The lifecycle has recognizable stages, and good teams practice each.

  • Detect: a symptom or burn-rate alert (or a customer report, which is the sign your detection failed). The metric is MTTD, mean time to detect.
  • Triage: acknowledge, assess severity (how many users, which journey, is data at risk), assign an incident commander who coordinates rather than debugs, and pull in the owners. Severity levels (SEV1 to SEV4) define response expectations.
  • Mitigate: stop the bleeding first, find the root cause later. Prefer reversible, fast actions: roll back the last deploy, flip a feature flag, fail over, shed load, scale up, block a bad client. The goal is restoring service, not a perfect fix. The commonly reported metric is MTTR (mean time to restore or recover; note that "R" is also read as repair, resolve or respond, so define it explicitly). Because means are skewed by rare long incidents, track medians and percentiles too.
  • Communicate: a status page and regular updates to stakeholders and affected customers, with a named communications owner so the responders can focus. State what is known, the impact, what is being done, and when the next update is. Silence erodes trust faster than bad news.
  • Resolve and review: fix the underlying cause, confirm via the SLIs that the service is healthy, and close the incident.
  • Postmortem (blameless): within a few days, write down the timeline, impact in error-budget terms, root and contributing causes, what went well, what did not, and action items with owners and dates. Blameless means assuming people acted reasonably with the information they had and asking "how did the system allow this?" rather than "who did this?". Blame causes people to hide mistakes and the same failures to recur. Follow-ups go into the backlog and are tracked, since a postmortem without closed actions is theater.
Interview tip Say "mitigate first, diagnose second" and "roll back is the default response to a bad deploy". Mention that observability is what makes both fast: the burn-rate page detects, the deploy marker plus trace points to the change, and the rollback restores.

15. Profiling and debugging in production

Sometimes metrics and traces show that one service is slow but not why. Profiling samples the program's call stacks (for CPU) or allocations (for memory) many times per second and aggregates them into a flame graph, where each box's width is the share of time spent in that function and its callees. It points at the exact hot function, an accidental O(n squared), a lock held too long, or excessive garbage collection. Continuous profiling runs a low-overhead sampler (typically a small percentage of CPU) always on in production and stores profiles over time, so you can compare "before and after the deploy" and look back at a spike that already ended. Other production debugging tools include on-demand thread or heap dumps, eBPF-based tracing of system calls and network behavior with very low overhead, and live log-level changes.

Principles for debugging live systems safely: prefer read-only, low-overhead tools; avoid attaching a debugger that pauses the process; be careful with heap dumps (they pause the JVM and contain sensitive data); reproduce on one instance by draining it from the load balancer first; use feature flags and per-request debug headers (limited to authorized users) to turn on detailed logging or tracing for a single request or tenant rather than everyone; and capture evidence (a profile, a dump) before restarting, since a restart destroys the state you need. Heavier techniques (dynamic instrumentation, shadow traffic replay in staging) are used when the issue cannot be seen otherwise.

16. The cost of observability, and sampling strategy

Observability is not free: telemetry is often among the top two or three infrastructure bills, sometimes 10-30% of total cloud spend in organizations that log and trace without discipline. Costs come from ingest (bytes shipped and processed), indexing (making logs searchable), storage and retention, query compute, per-series charges for metrics (cardinality), and the overhead in the application itself (CPU, memory, network for emitting it).

SignalMain cost driverLevers
MetricsNumber of active series (cardinality), scrape frequencyBound labels, drop unused metrics, scrape less often for low-value targets, aggregate at ingestion, rollup old data
LogsVolume in bytes and indexingLevels, sampling, drop noisy lines, index only key fields, tier hot/warm/cold, short retention, compress
TracesSpans per request x request volumeHead and tail sampling, fewer spans per request, drop attributes, shorter retention
ProfilesSample rate, number of servicesSample a fraction of instances, low frequency sampling

16.1 A sampling strategy

You cannot keep everything, so decide what matters and sample the rest deliberately. A sound default:

  1. Keep all metrics aggregates (they are cheap and complete). SLIs must be computed from unsampled counts at the edge (or from sampling-corrected counts), never from a sampled subset, otherwise your SLO is wrong.
  2. Keep 100% of errors, slow requests and security/audit events in traces and logs. These carry the debugging value.
  3. Sample routine successes: for example 1-10% of normal traces and 1% of INFO logs, with the sample rate recorded on each record so counts can be re-scaled.
  4. Use tail-based sampling in a collector to decide after seeing the whole trace, plus dynamic sampling: keep a higher fraction of rare event types and a lower fraction of the most common ones, so rare behaviors stay visible.
  5. Tier retention: raw data 7-15 days hot, derived aggregates and a sample of traces for months, archived logs in cheap object storage for compliance.
  6. Make it observable: monitor the cost of observability itself (series count, bytes per service per day) and give teams a budget and visibility into what they spend.

Example: 5,000 req/s, 12 spans per request, 300 bytes per span: 5,000 × 12 × 300 = 18 MB/s = 1.55 TB/day. Keeping every trace is rarely justified. Keep 5% of normal traffic plus all errors (assume 0.5% of requests) and all traces over 2 s (assume 1%): kept fraction about 5% + 0.5% + 1% = 6.5%, so about 100 GB/day, a 15x reduction while retaining the traces that matter.

17. What to say about monitoring in an interview

Almost every design question ends with a few minutes on operations, and many interviewers use it to separate seniors from juniors. A short, structured answer beats a tool list. Use this checklist and tailor it to the system:

  1. Name the user-facing SLIs and SLOs first. "Checkout availability 99.95% and 99% of successful calls under 1 s, over a rolling 30 days." For pipelines, add freshness or deadline SLIs.
  2. Metrics (RED plus saturation): rate, errors, latency percentiles from histograms for each service, with USE for the key resources (queue depth, connection pools, replication lag, consumer lag, cache hit rate).
  3. Traces and correlation ids: propagate a trace id across services and queues; sample tail-based, keeping errors and slow requests (Chapter 52).
  4. Structured logs: JSON, with trace id, tenant and version; levels and sampling; no secrets.
  5. Alerting: burn-rate alerts on the SLOs (fast burn pages, slow burn tickets), symptom-based, each with a runbook; alert manager grouping and inhibition.
  6. Business and correctness signals: orders per minute, payment success, reconciliation mismatches, dead-letter queue depth, since "up" is not "right".
  7. Outside-in checks: synthetic probes of the critical journey from multiple regions, plus RUM for client-side truth.
  8. Safe delivery: canary or staged rollout gated on SLIs with automatic rollback, feature flags, and health probes (liveness, readiness).
  9. Capacity: saturation dashboards, growth forecasts, headroom, load tests, and autoscaling thresholds.
  10. Incident process: on-call, severity levels, mitigate-first, blameless postmortems, error-budget policy.
  11. Cost: label cardinality limits, sampling, retention tiers.

Tailor the answer: for a payment system emphasize correctness and reconciliation; for a feed or search system emphasize freshness and tail latency; for a data pipeline emphasize lag and deadlines; for a multi-tenant SaaS emphasize per-tenant metrics (with care for cardinality) and noisy-neighbor detection (see Chapter 42).

18. Worked example: SLOs and burn-rate alerts for a checkout API

Setting: an e-commerce POST /checkout API behind a gateway, calling an order service, an inventory service and a third-party payment provider. Traffic averages 100 requests per second over a month, peaking at 300 req/s. Users abandon after a few seconds, and failure directly loses revenue.

18.1 Pick SLIs

  • Availability SLI: good = checkout responses with status other than 5xx and not timed out at the gateway; valid = all checkout requests excluding 4xx caused by invalid input and excluding known synthetic test traffic. Measured at the load balancer or gateway so it includes failures that never reach the app (the app cannot count requests it never saw).
  • Latency SLI: good = successful checkouts served in under 1 s; valid = all successful checkouts. Latency is measured only for successes, so fast errors do not flatter it.
  • Correctness SLI (supporting): daily reconciliation job: the fraction of paid orders whose payment record matches the payment provider's settlement. This detects silent data errors (charged but no order) that availability cannot.

18.2 Pick SLOs

Dependency check: gateway 99.99%, order service 99.95%, inventory 99.95%, and payment provider 99.95% (assumed). Product ≈ 0.9999 × 0.9995 × 0.9995 × 0.9995 ≈ 99.84%, so promising 99.95% for checkout requires mitigating the providers: retry payment with idempotency keys (Chapter 32), timeouts and a circuit breaker to a queued "pending payment" fallback, and a stock reservation that tolerates inventory blips (Chapter 40). With those, set:

  • Availability: 99.95% over a rolling 30 days.
  • Latency: 99% of successful checkouts under 1 s over the same window.
  • Correctness: 99.99% of paid orders reconcile within 24 hours.

The external SLA to merchants is 99.9%, giving a margin.

18.3 Compute the budget

Requests per window: 100 × 86,400 × 30 = 259,200,000. Availability budget: 0.05% = 129,600 bad requests (or 21.6 minutes of full outage). Latency budget: 1% slow allowed = 2,592,000 slow requests.

18.4 Burn-rate alert thresholds

Allowed error ratio = 0.0005. The thresholds are the burn rate times 0.0005:

RuleWindows (long and short)Error ratio aboveBudget spent when firingAction
Fast burn1 h and 5 min14.4 × 0.0005 = 0.72%2% (2,592 failed of 129,600)Page
Medium burn6 h and 30 min6 × 0.0005 = 0.30%5%Page
Slow burn3 d and 6 h1 × 0.0005 = 0.05%10%Ticket

Check the first row at 100 req/s: one hour is 360,000 requests; 0.72% of them is 2,592, which is 2% of 129,600. Time to detect: a total outage makes the 1-hour error ratio reach 0.72% after 0.0072 × 60 min ≈ 26 seconds of failures, so the page fires after roughly a minute with window evaluation delays. A partial failure of 3% of requests reaches 0.72% in the 1-hour window after 0.0072 / 0.03 × 60 = 14.4 minutes. A bad deploy causing 0.4% errors for a day would not page (below 0.72%), but fires the medium rule (above 0.30%). The 6-hour window reaches 0.30% once the bad period fills 0.003 / 0.004 = 75% of it, which is 4.5 hours, and the page fires then, with about 5% of the budget spent (a burn rate of 8 for 4.5 hours is 8 × 4.5 / 720). The same logic applies to the latency SLO, with an allowed slow ratio of 0.01: fast burn pages when more than 14.4% of successes in 1 h and 5 min exceed 1 s.

18.5 Budget policy and operations

  • Policy: below 25% budget remaining, non-essential releases to checkout need approval; at 0%, freeze feature releases until budget recovers; payment-provider-caused burn leads to a vendor review.
  • Dashboard: SLO status and budget remaining, RED by endpoint and region, payment provider latency and error panel, circuit-breaker state, queue of pending payments, DB pool saturation, deploy markers.
  • Runbook for the fast-burn page: check deploy markers (roll back if a deploy was in the last 30 minutes); check the payment provider panel (if it is the cause, enable the pending-payment fallback); check DB saturation; open a trace of a failed request via the exemplar link; declare an incident if not mitigated in 15 minutes.
  • Verification: the canary stage gates on the same availability and latency SLIs; a game day injects payment timeouts to prove the fallback and the alert.
Result Users are protected by SLOs on what they feel; the team gets pages only for budget-threatening symptoms, with a runbook and a rollback path; slow leaks become tickets; and release speed is governed by a numeric budget instead of opinion.

19. Interview Q&A

What is the difference between monitoring and observability?

Monitoring watches predefined signals and alerts when they cross thresholds, so it answers questions you thought of in advance, such as whether the error rate is high. Observability is the property of a system that lets you ask new questions about its internal state from the telemetry it emits, such as why one tenant on one app version is slow. It needs rich, high-detail data (traces, structured events) that you can slice by arbitrary fields. In practice you use monitoring to detect and observability to diagnose, and a system with only dashboards and fixed alerts struggles with novel failures.

When do you use logs, metrics and traces?

Metrics are cheap aggregated numbers over time, the right tool for dashboards, alerting and SLOs. Traces show the path and timing of one request across services, the right tool for locating where latency or errors arise. Logs hold the detailed context of individual events, the right tool for exact forensics and errors. A typical investigation moves from a metric alert, to an exemplar trace showing which span is slow, to the logs of that span for the specific error. I would also mention wide events and profiles as enrichments.

Why are averages misleading for latency, and how do you aggregate percentiles correctly?

Latency has a long tail, so the mean sits between the fast majority and the slow minority and describes no real request. For example, 98% of requests at 100 ms and 2% at 10 s give a mean near 300 ms, while the p99 is 10 s and shows the pain. Percentiles themselves cannot be averaged across hosts or time windows, because a percentile of percentiles has no meaning. Instead each instance exports histograms with identical buckets, you sum the bucket counts, and compute the percentile from the merged histogram, or use mergeable sketches like t-digest or DDSketch. Bucket edges should be placed at SLO thresholds for accuracy.

What is metric cardinality and why does it matter?

Cardinality is the number of distinct time series, which is the product of the number of values of each label. Each series consumes index memory and storage, so an unbounded label such as user id or raw URL can multiply a few hundred series into hundreds of millions, crashing or bankrupting the metrics backend and slowing queries. Keep labels bounded, normalize routes, and move high-cardinality identifiers into logs, traces or wide events. Cardinality limits and monitoring of series growth should be in place as guardrails.

Explain SLI, SLO and SLA, and give a good SLI example.

An SLI is a measurement of service quality expressed as good events over valid events, such as the fraction of checkout requests that return non-5xx within one second. An SLO is the internal target for that SLI over a window, for instance 99.9% over a rolling 30 days. An SLA is the contractual promise to customers with penalties, normally looser than the SLO to leave a safety margin. Good SLIs reflect user experience and are measured near the user, not component health like CPU.

What is an error budget and what do you do when it is exhausted?

The error budget is the allowed unreliability, one minus the SLO, for example 0.1% of requests or about 43 minutes per 30 days at 99.9%. It turns reliability into a resource shared by product and engineering: when budget remains, ship quickly and take risks; when it is exhausted, the agreed policy applies, typically freezing feature releases and prioritizing reliability work until the budget recovers. The key is that the policy is agreed beforehand so it is not argued during an incident. It also tells you when you are being too conservative if the budget goes unused.

Why use burn-rate alerts instead of simple thresholds, and how does multi-window multi-burn-rate work?

A fixed threshold such as 1% errors for 5 minutes ignores the SLO and trades noise against detection time. The burn rate is the observed error ratio divided by the allowed ratio, so it says how fast the budget is being consumed: a burn rate of 14.4 on a 99.9%, 30 day SLO means 2% of the monthly budget spent per hour. Multi-window multi-burn-rate combines several levels, for example 14.4x over 1 hour, 6x over 6 hours (both page) and 1x over 3 days (ticket). Each requires its long window and a short window of about one twelfth to both be above the threshold, so fast big outages page within minutes, slow leaks create tickets, and alerts reset quickly after recovery.

Should you alert on causes like high CPU?

Generally no, page on symptoms that users feel, such as error ratio and latency SLO burn, and use cause metrics for diagnosis dashboards. High CPU may be harmless, while real failures from unanticipated causes would never trip a cause-based rule, so symptom alerts cover them all. There are exceptions where a cause is a certain leading indicator that needs human action soon, such as disk filling within hours, an expiring certificate, or exhausted quota; those should be tickets or low-urgency pages by time remaining. Every page should be actionable, urgent and linked to a runbook.

How do you set SLOs for a service that depends on several others, and for a batch pipeline?

For serial hard dependencies, availability multiplies, so four components at 99.9 to 99.99% can yield only about 99.8% end to end; you cannot promise more than that unless you add redundancy, fallbacks, caching, or take work off the synchronous path (see the HA and resilience chapters). Prefer to measure the composite SLO at the edge rather than compute it. For batch or streaming pipelines, use freshness (age of newest output), lag, deadline success (98% of runs finish by 06:00), and completeness or correctness measured by reconciliation. Alert on the trend that predicts a missed deadline, not each transient failure.

How do you cut observability cost without losing the ability to debug?

Keep metrics aggregates complete and cheap but bound cardinality, because SLIs must come from unsampled data. For logs and traces, keep every error, slow request and audit event and sample routine success traffic, ideally with tail-based sampling and recording the sample rate on records. Reduce volume at the source with levels and dropping noisy lines, index only key fields, tier retention from hot to cold storage, and shorten retention for low-value data. Finally, monitor the cost itself per team so it stays visible. A typical result is a 10x or greater reduction while retaining the data that incidents need.

Walk through how you respond to a page for checkout burn rate.

Acknowledge, check the SLO dashboard to confirm user impact and scope, and look for recent changes on the deploy marker overlay. If a deploy happened, roll back first since mitigation comes before diagnosis. Otherwise check the dependency panels, such as the payment provider and database saturation, and use an exemplar trace and correlated logs to find the failing span; apply a mitigation like enabling a fallback or shedding load. Communicate status updates through the incident channel and status page, then resolve, and write a blameless postmortem with owned action items and the error budget impact.

What is the difference between liveness and readiness probes, and why does it matter?

A liveness probe asks whether the process is alive, and failure causes a restart, so it must not check external dependencies; otherwise a database blip causes every instance to restart and a small outage becomes a big one. A readiness probe asks whether the instance can serve traffic now, and failure only removes it from load balancing, which is used for warm-up, draining on shutdown, and temporary overload. Even readiness should be careful with shared-dependency checks, because failing all instances at once removes all capacity. Startup probes protect slow-booting services from being killed early.

20. Recap

  • Monitoring detects known problems; observability lets you explain novel ones. Instrumentation is part of the design.
  • Metrics are cheap aggregates for alerting and SLOs, traces locate latency and errors across services, logs give exact detail; add wide events and profiles.
  • Keep metric labels bounded (cardinality is a product), use histograms and sum buckets to aggregate percentiles, never average percentiles, and prefer percentiles to means.
  • Use RED for services, USE for resources, and the four golden signals as a general checklist.
  • Log structured JSON with a correlation id, use levels carefully, sample, and never log secrets.
  • SLIs are good over valid events measured from the user's view; SLOs set targets (not 100%); SLAs are looser contracts.
  • Error budgets (1 minus SLO) turn reliability into a spendable resource with an agreed policy such as a release freeze.
  • Serial dependencies multiply availability; use redundancy, fallbacks and async to beat the product; set SLOs per journey and use freshness and deadlines for pipelines.
  • Page on symptoms with multi-window multi-burn-rate alerts (14.4x/1h and 6x/6h page, 1x/3d tickets), group and inhibit, link runbooks, and protect on-call from fatigue.
  • Complement internal telemetry with synthetic probes, canaries, RUM, health probes and saturation monitoring.
  • Incidents: detect, triage, mitigate first, communicate, then a blameless postmortem; track MTTD and MTTR.
  • Control observability cost with sampling (keep errors and slow requests), retention tiers and cardinality limits.
