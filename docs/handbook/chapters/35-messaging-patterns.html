Chapter 35 · Module 5 · Asynchronous Architecture

Messaging Patterns

A message broker moves bytes between services, but the interesting engineering is in the patterns built on top of it: how to fan a message out, share work among consumers, keep order, retry safely, quarantine bad messages, and survive duplicates. This chapter is the practical toolbox for designing asynchronous flows that keep working when things go wrong.

1. Why patterns: the broker is not the design

Chapter 34 explained what queues, logs, and brokers are: how messages are stored, how partitions and consumer groups work, and what delivery guarantees the products give. This chapter assumes that background and asks the next question: given a broker, how do you design the conversation between services so that it is correct, scalable, and operable?

A broker alone does not solve the hard parts. It will happily deliver the same message twice, deliver messages out of order across partitions, fill up with a backlog nobody reads, or hold a malformed message that crashes every consumer that touches it. Each of these is a recurring problem with a well-known answer, and those answers are called messaging patterns. Knowing them lets you design in an interview by naming the problem, naming the pattern, and stating its cost.

Some vocabulary used throughout:

  • Producer (publisher): the service that sends a message.
  • Consumer (subscriber): the service that receives and processes a message.
  • Queue: a buffer where each message is processed by one consumer, then removed (SQS, RabbitMQ queues).
  • Topic: a named channel that many independent subscribers can read (SNS, Kafka topics, Pub/Sub topics).
  • Acknowledgement (ack): the consumer's signal to the broker that processing finished, so the message may be removed or the offset advanced.
  • Visibility timeout / lease: in queue systems, the period after delivery during which the message is hidden from other consumers while the first one works on it. If no ack arrives in time, the message reappears and is delivered again.
  • Command vs event: a command says "do this" and is addressed to one handler (ChargeCard). An event says "this happened" and has no particular addressee (OrderPlaced). Commands usually travel on queues, events on topics. Chapter 36 covers event design itself.
Key idea Almost every pattern in this chapter exists because of one fact: a message system gives you at-least-once delivery, not exactly-once, and no global ordering. Consumers must therefore tolerate duplicates, reordering, delays, and poison input. Design for that and the rest follows.

2. Point-to-point versus publish/subscribe

2.1 Point-to-point

In a point-to-point model, a message goes into a queue and exactly one consumer receives it. If ten consumers are attached to the queue, they share the messages: each message goes to one of them. This is the model for work distribution: "resize this image", "send this email", "charge this card". The sender usually expects that the work gets done exactly once by someone, and does not care who.

2.2 Publish/subscribe

In publish/subscribe (pub/sub), the producer publishes to a topic and every subscriber receives its own copy. The producer does not know who the subscribers are, and adding a new subscriber needs no change in the producer. This is the model for notification of facts: "an order was placed", and billing, shipping, analytics, and email each react independently.

Interview tip Say "a command has one owner and goes on a queue; an event has zero-to-many listeners and goes on a topic." It shows that you choose the model from the semantics, not from the product name.

3. Fan-out

Fan-out means one incoming message causes many downstream deliveries. There are two levels to think about.

3.1 Topic fan-out

The simplest form is a topic with many subscribers, as above. With a log-based broker like Kafka, fan-out is cheap: the message is stored once and each consumer group reads it with its own offset. Ten groups cost ten reads, not ten writes.

3.2 SNS plus SQS: durable fan-out

A pure notification topic such as Amazon SNS pushes to subscribers but does not retain messages for slow ones. If a subscriber is down, delivery retries for a limited time and then the message may be lost to that subscriber. The standard fix is to give every subscriber its own queue and subscribe the queue to the topic. The topic does the broadcast, and each queue provides durability, buffering, retry, and a dead-letter queue for that one consumer.

Two refinements are worth knowing. First, subscription filters: subscribers can declare attribute conditions (for example region = EU) so the topic only delivers matching messages, which saves consumer work. Second, with large fan-out the producer-side cost is small but the total work multiplies: a message fanned out to 20 subscribers causes 20 deliveries and 20 processing runs, so capacity planning must count them all.

3.3 Fan-out on write versus fan-out on read

A recurring design choice (it appears in news-feed case studies) is whether to copy a message into every recipient's mailbox at write time (fan-out on write: fast reads, expensive writes for celebrities) or to assemble the view at read time (fan-out on read: cheap writes, slower reads). Messaging systems implement the first; the second is a query pattern. Hybrid designs fan out on write for ordinary users and on read for very high-follower accounts.

4. Competing consumers and scaling consumers

The competing consumers pattern attaches several identical consumer instances to one queue. Each message is given to one of them; they "compete" for work. This is how you scale throughput horizontally: if one worker handles 100 messages per second and you need 1,000, run about ten (plus headroom).

4.1 How it works in queue brokers

In SQS-style queues, a consumer receives a message and the broker starts the visibility timeout. The consumer processes the message and deletes it (the ack). If the consumer crashes, the timeout expires and the message becomes visible again for another worker. This is what makes the pattern fault tolerant: a dead worker's job is automatically retried by a live one. It is also why duplicates happen: a worker that is slow, not dead, may finish after the timeout expired, by which time another worker has already received the same message.

Rule of thumb: set the visibility timeout to comfortably more than the p99 processing time, and for long jobs extend the lease (heartbeat) while still working.

4.2 How it works in logs (Kafka)

In Kafka, parallelism is capped by the partition count. A partition is read by at most one consumer in a group at a time, so a topic with 12 partitions supports at most 12 useful consumers in one group; a 13th sits idle. The partition count is therefore a long-lived capacity decision: you can add partitions, but that changes key-to-partition mapping and so disturbs per-key ordering for existing keys.

4.3 Scaling consumers

Scale on the signal that actually reflects need, which is backlog, not CPU. A practical formula:

consumers needed = arrival rate (msg/s) x average processing time (s) / target utilization

Example: 2,000 msg/s x 0.050 s / 0.7 = about 143 concurrent handlers

Autoscalers commonly use "queue depth divided by consumers" or "age of oldest message" as the metric. Scale-out helps only if the bottleneck is the consumers. If every consumer calls the same database that is already saturated, adding consumers makes it worse. Cap concurrency to what the downstream can take (see backpressure, section 9).

Watch out Competing consumers give up ordering. Two workers can finish messages in a different order from which they were read. If order matters, you need the per-key techniques in the next section, not just more workers.

5. Ordering

5.1 Why order is lost

A single queue read by a single consumer, with no failures, is ordered. Order breaks when you add (a) multiple consumers, since processing speeds differ; (b) multiple partitions or shards, since there is no order across them; (c) retries, since a failed message is redelivered after later ones succeeded; and (d) multiple producers or network paths, since messages can arrive at the broker in a different order than they were created.

5.2 Do you need global order?

Almost never. What applications usually need is order per entity: all events for order 42 must be processed in sequence, but order 42's events and order 43's events are independent. That is much cheaper to provide.

5.3 Per-key partitioning

The standard solution: choose a key (order id, account id, device id), hash it to pick a partition, and let exactly one consumer read each partition. All messages with the same key go to the same partition, in publish order, to one consumer, so their order is preserved while different keys run in parallel. Kafka does this with the message key. SQS FIFO does it with a message group id: messages in one group are delivered in order and one at a time, while groups proceed in parallel. Kinesis uses the partition key; RabbitMQ can use consistent-hash exchange or single-active-consumer queues.

5.4 Sequence numbers and resequencing

Sometimes the transport cannot guarantee order (multiple paths, multiple partitions, or retries). Then the producer stamps each message with a sequence number per entity (1, 2, 3 ...), and the consumer enforces order:

  • If the message's number equals expected next, process it and advance.
  • If it is lower than expected, it is a duplicate or stale message: ignore it (or acknowledge and skip).
  • If it is higher, there is a gap. Either buffer it (a resequencer holds early arrivals until the missing ones come, with a timeout) or reject it for later redelivery.

For state-carrying events there is a cheaper trick: put a version on each entity update and apply a message only if its version is higher than the stored one ("last write wins by version"). Out-of-order older messages are then harmless. This works when each message contains the full new state, not a delta.

5.5 The ordering versus parallelism tradeoff

Strict ordering forces serial processing of the ordered group. If processing one message takes 50 ms, a single key can sustain at most 20 messages per second, no matter how many consumers you own. Retries make it worse: with strict order, a failing message blocks everything behind it in its partition (head-of-line blocking). You then must choose between blocking (keep order, halt progress), skipping to a retry queue (progress, but order broken for that key afterward), or dead-lettering. Many systems accept "order broken after a failure" and make handlers tolerant instead, by using versions or commutative updates.

6. Retries

Consumers fail for two very different reasons, and the pattern depends on which one applies. A transient failure (database timeout, downstream 503, lock conflict) will probably succeed if tried again. A permanent failure (malformed payload, business rule violation, missing referenced record that will never appear) will fail forever. Retrying a permanent failure only burns resources, so the first job of the handler is to classify the error: retry the transient, dead-letter the permanent.

6.1 Immediate retry

Retry in-process a small, bounded number of times (say 2 or 3), with no waiting or a very short one. It handles blips such as a connection reset. It is cheap, but if the downstream is actually overloaded, immediate retries add load at the worst moment.

6.2 Delayed retry and visibility timeout

If the handler simply does not ack, a queue like SQS redelivers after the visibility timeout. That is a built-in delayed retry, but the delay is fixed and equal for everyone. Better is to explicitly choose the delay: change the message's visibility to a longer value on each failure, or publish it to a delay queue.

6.3 Exponential backoff with jitter

Exponential backoff doubles the wait after each failed attempt: 1 s, 2 s, 4 s, 8 s, up to a cap. It gives a struggling dependency time to recover. Pure backoff has a flaw: if 10,000 messages failed at the same moment, they all retry at the same moments again, producing synchronized waves (a "thundering herd"). Jitter randomizes each delay. The common "full jitter" formula:

delay = random(0, min(cap, base x 2^attempt))
Example: base 1 s, cap 60 s: attempt 3 gives a random delay between 0 and 8 s

The result spreads retries evenly over time. See Chapter 40 for the same idea on synchronous calls, including retry budgets.

6.4 Retry topics and tiers

Brokers such as Kafka have no per-message delay, and blocking a partition while waiting would stall every other message. The usual pattern is retry tiers: separate topics or queues, each representing a longer delay, such as orders.retry.10s, orders.retry.1m, orders.retry.10m, followed by the dead-letter topic. On failure the consumer publishes the message to the next tier (carrying an attempt counter and the original timestamp in headers) and commits the original, so the main topic keeps flowing. A retry-tier consumer waits (pauses its partition) until the message is old enough, then reprocesses it.

6.5 Bounding retries

Retries must always have a limit, both in attempts and in total age. Unbounded retry is an anti-pattern (section 19): a message that can never succeed will circulate forever, consuming capacity and hiding the problem. Combine max attempts (for example 5), max age (give up after 24 h), and a circuit breaker so that, when a dependency is clearly down, consumers pause instead of retrying every message into a wall.

7. Dead-letter queues and poison messages

A poison message is one that a consumer cannot process successfully, no matter how often it is retried: corrupt JSON, an unknown enum value, a reference to deleted data, or a payload that triggers a bug and crashes the handler. In a naive setup it is delivered, fails, reappears, fails again, forever, and in an ordered partition it blocks every message behind it.

A dead-letter queue (DLQ) is a separate queue where such messages are moved after the retry policy is exhausted. It converts an infinite loop into a quarantined record.

7.1 Detect

Detection is mostly counting. The broker or the consumer tracks the delivery attempt count (SQS has maxReceiveCount on the redrive policy; RabbitMQ dead-letter exchanges; Kafka needs an attempt header you maintain). When the count exceeds the limit, or when the handler throws a known non-retryable exception, the message is routed to the DLQ. Crashing handlers are the nasty case: the process dies before it can report anything, so the broker's delivery count is the only evidence.

7.2 Quarantine with context

A dead letter that loses its context is almost useless. Store the original payload unchanged plus metadata: the source queue or topic, partition and offset, first-failure and last-failure time, attempt count, exception class and message, stack trace summary, consumer version, and trace id. With that, an engineer can reproduce the failure without guessing.

7.3 Alert and triage

A DLQ nobody watches is a graveyard. Alert on DLQ depth above zero or on the rate of arrivals, and on the age of its oldest message. Each message in a DLQ represents a user action that did not complete, so treat it like a bug ticket: classify (bad data, code bug, dependency bug), fix, then redrive or discard.

7.4 Redrive tooling

Redrive means moving dead letters back to the source queue after the cause is fixed. Good tooling provides: a way to inspect and search messages; redrive of all or a selected subset; a rate limit so the redrive does not overload the system (a thousand messages released at once is a spike); preservation of the original message id and idempotency key so consumers can dedup; and an audit log of who redrove what. SQS offers a console and API redrive to the source queue; for others you write a small tool. Because redriven messages are processed again, consumers must be idempotent (next section).

Watch out Dead-lettering breaks order. If message 2 of key A is dead-lettered and message 3 proceeds, the later redrive of message 2 arrives after message 3. Either design handlers to tolerate it (versions), or for strictly ordered streams halt the key's partition until a human resolves the failure.
Interview tip When you add a queue to a design, say in one breath: "with a retry policy, a DLQ with alerting, and idempotent consumers." That sentence covers most of what interviewers probe about failure handling.

8. Idempotent consumers and deduplication

With at-least-once delivery, the same message can arrive more than once: lease expiry, a lost ack, a producer retry after a timeout, a redrive, or a replay. An idempotent consumer produces the same final state whether it processes a message once or five times. Chapter 32 covers idempotency keys and delivery semantics in depth; here is how they apply to messaging.

8.1 Techniques

  • Naturally idempotent operations. "Set status to SHIPPED" or "upsert row by id" can be repeated safely. "Add 10 to balance" cannot. Prefer designing messages as state assertions rather than deltas where you can.
  • Processed-message table (inbox). Each message carries a unique id. The consumer, in the same database transaction as its business change, inserts the id into a table with a unique constraint. A duplicate violates the constraint, the transaction rolls back (or is skipped), and nothing changes twice. This is the strongest approach because the dedup record and the effect commit atomically.
  • Conditional update. UPDATE ... WHERE version = 6 succeeds once; a replay finds version 7 and does nothing.
  • Dedup cache with TTL. Remember recent ids in Redis for, say, 24 h. It is cheap but leaky: if the entry expires or the cache loses data, a late duplicate gets through. Use it only where an occasional duplicate is tolerable.
  • Broker-side dedup. SQS FIFO deduplicates by a deduplication id within a five-minute window, and Kafka's idempotent producer prevents producer-retry duplicates within a session. These protect only the producer-to-broker hop, not your consumer's side effects.

8.2 Side effects outside the database

If the handler calls an external API (send email, charge a card), a database inbox cannot make that call atomic. The usual answer is to pass the message id (or a derived key) to the external system as an idempotency key so it dedups on its side, as payment providers do. If the external system has no such feature, you must accept either at-most-once (mark done first, then call, risking a lost effect) or at-least-once (call, then mark, risking a duplicate), and pick according to which error is cheaper.

Key idea "Exactly-once" in practice means at-least-once delivery plus idempotent processing. The broker supplies the first half; you supply the second.

9. Backpressure and consumer lag

Consumer lag is the gap between what has been produced and what has been consumed: in Kafka, the difference between the latest offset and the group's committed offset; in SQS, the approximate number of visible messages, or better, the age of the oldest message. If producers outpace consumers for long enough, lag grows without bound. A queue only moves the pressure from the producer to the queue; it does not remove it.

Backpressure is any mechanism that pushes that pressure back so the system slows gracefully rather than collapsing. Options, from the consumer outwards:

  1. Bounded in-flight work. The consumer fetches only as many messages as it can process (prefetch count in RabbitMQ, max.poll.records in Kafka, a semaphore limiting concurrent handlers). It never accepts more than it can hold.
  2. Pause and resume. When a downstream database or API is failing, the consumer stops polling (Kafka pause()) rather than pulling messages it can only fail. A circuit breaker (Chapter 40) can drive this.
  3. Scale out consumers, up to the partition count and what the downstream tolerates.
  4. Shed or defer low-value work. Drop or delay messages that are stale or less important (priority queues and TTL, section 10).
  5. Throttle producers. Where the producer is a service you control, rate-limit it or return 429 to its clients once the queue is too deep. This is the only option that truly stops growth.
  6. Bound the queue. Set a maximum size or retention. An infinite queue hides overload until it becomes an outage with a 6-hour recovery.

9.1 Lag as the key health metric

Alert on lag in time, not only count. A backlog of 1 million messages is fine if the group drains 50,000 per second; a backlog of 10,000 is a crisis if each takes a second and the SLA is a minute. Estimated drain time = backlog ÷ (consume rate − produce rate). If consume rate is not greater than produce rate, the backlog never drains and you must scale or shed.

9.2 Rebalances and lag spikes

In Kafka, consumers joining or leaving trigger a rebalance during which processing pauses. Frequent rebalances (caused by slow handlers exceeding max.poll.interval, or autoscaler flapping) look like sawtooth lag. Remedies are keeping handlers fast, using cooperative rebalancing and static membership, and smoothing autoscaling.

10. Load leveling, priority, delay and TTL

10.1 Queue-based load leveling

Traffic is bursty. A flash sale may send 10,000 orders per second for two minutes against a baseline of 500. Sizing synchronous services for the peak is costly. Putting a queue between the front end and the worker tier lets the front end accept work at burst speed while the workers drain at a steady, affordable rate. The queue acts as a shock absorber. The cost is latency: work waits, so this applies only where the user does not need an immediate result (and where you can tell them "we received your order").

Sizing check: a 120-second burst at 10,000/s against 2,000/s of capacity builds up (10,000 − 2,000) × 120 = 960,000 messages. After the burst, if arrivals return to 500/s, the net drain is 1,500/s, so clearing takes 960,000 ÷ 1,500 = 640 s, about 11 minutes. Decide if that wait is acceptable, or scale workers up during the burst.

10.2 Priority queues

Not all messages deserve equal waiting. A password-reset email should not sit behind a million marketing emails. Many brokers have no true per-message priority (SQS has none; RabbitMQ has priority queues with limited levels, which cost performance). The robust pattern is separate queues per priority (high, normal, low), with consumers that poll high first, or with dedicated capacity such as 70 percent of workers on high and 30 percent shared, so low priority is never completely starved. Pure strict priority starves the low tier whenever high traffic is constant, so give it a minimum share or an aging rule (a message waiting too long is promoted).

10.3 Delayed messages

Sometimes a message should not be processed until later: send a reminder in 24 hours, cancel an unpaid order in 30 minutes, retry after a backoff. Options: SQS delay seconds (up to 15 minutes per message); RabbitMQ delayed-message plugin or TTL plus dead-letter trick; Service Bus scheduled enqueue time; Kafka has no native delay, so use retry-tier topics or an external scheduler (a database table of due times polled by a timer, or a workflow engine). For long delays (days) a durable scheduler is more reliable than keeping messages hidden in a broker, and easier to cancel when the order gets paid.

10.4 Message TTL

A time-to-live says "if this message is not processed within T, it is worthless". A surge-pricing update from 10 minutes ago, an OTP code that expired, or a "driver nearby" notification for a ride already taken should be discarded rather than processed late. Set TTL on the message or queue, and decide what happens on expiry: silently drop, or route to a dead-letter queue to count how often it happens. The consumer should also check the message's timestamp itself, because TTL enforcement in brokers is often lazy (expired messages are removed only when they reach the head of the queue).

11. Request-reply over messaging

Messaging is naturally one-way, but sometimes you need an answer, and want queue benefits (buffering, decoupling, retry) while doing so. Request-reply uses two channels: the requester sends a request message to a request queue, including a reply-to address (a queue only it listens on) and a correlation id. The responder processes it and publishes the response to the reply-to address, copying the correlation id. The requester matches responses to its outstanding requests by that id.

Rules that matter: always set a timeout, because a missing reply is a normal event; make the request idempotent, since a timed-out request may still have been executed; and treat late replies as expected. If you find the whole system turning into synchronous request-reply over a broker, ask whether plain HTTP or gRPC (Chapter 40 for the resilience side) would be simpler. Request-reply over messaging earns its place when the responder is a slow or bursty worker pool, or when you want the buffering during spikes.

11.1 Correlation ids in general

The correlation id is useful beyond request-reply. Stamp a correlation id (the business flow, such as the order id) and a trace id (the distributed trace) on every message in a flow, and copy them to every message a handler produces. That is what allows you to reconstruct a flow that hops through six queues (section 18).

12. Claim check for large payloads

Brokers are built for small messages. SQS caps at 256 KB, Kafka's default is about 1 MB, and even where larger sizes are permitted, big messages hurt: they inflate broker memory and replication traffic, slow every consumer in the partition behind them, and make retries and DLQs expensive. The claim check pattern stores the large payload (a video, a PDF, a 5 MB JSON document) in object storage such as S3, and puts only a small reference in the message. The consumer presents the reference to fetch the payload, as one presents a ticket to claim luggage.

Operational details: upload the object before sending the message (otherwise a consumer may follow a dangling reference); include size and a checksum so the consumer can verify; give the object a lifecycle rule that deletes it after the retention period of the message plus a margin, since nothing cleans it automatically; and make the reference immutable (never overwrite the same key) so replays see the same bytes. Access control matters too: the consumer needs read permission, or the message carries a short-lived pre-signed URL. Some SDKs (the SQS extended client) implement this pattern for you.

13. Envelopes, schema registry and evolution

A message outlives the code that wrote it. It may sit in a queue for hours, or in a log for months, and consumers deployed at different times read it. So its structure must be explicit and evolvable. Serialization formats and compatibility rules are covered in Chapter 7; this section is how they apply to messaging.

13.1 The envelope

Wrap every business payload in a standard envelope of metadata, so that infrastructure (routers, DLQ tools, tracers) can work without understanding the payload:

{
  "id":            "0f8c...-uuid",        // unique message id, for dedup
  "type":          "order.placed",        // what it is
  "schemaVersion": 3,                     // payload version
  "source":        "order-service",
  "time":          "2026-11-17T10:15:30Z",
  "correlationId": "ord-8841",
  "traceId":       "4bf9...",
  "partitionKey":  "ord-8841",
  "payload":       { ... business data ... }
}

The CloudEvents specification standardizes such fields. The point is consistency across teams.

13.2 Schema registry

A schema registry (Confluent Schema Registry, AWS Glue, Apicurio) stores the schemas for each topic with versions. Producers register or look up a schema and send only a small schema id with each binary message (Avro or Protobuf); consumers fetch the schema by id. The registry can also enforce compatibility when a new schema is registered, rejecting a change that would break existing readers, which moves breakage from a production incident to a failed CI build.

13.3 Evolution rules

  • Backward compatible: new consumers can read old messages. Adding an optional field with a default is safe.
  • Forward compatible: old consumers can read new messages. They must ignore unknown fields.
  • Never reuse or change the meaning or type of a field. Add a new field and deprecate the old.
  • Removing a required field, renaming, or changing a type is a breaking change: publish a new event type or a new topic version (order.placed.v2) and run both until consumers migrate.
  • Upgrade consumers first, then producers, so consumers are ready for the new fields before they appear.
  • Consumers should be tolerant readers: ignore the unknown, default the missing, and send unparseable messages to the DLQ rather than crashing in a loop.

14. Transactional outbox and inbox

A service often needs to change its database and publish a message, for example insert an order row and publish OrderPlaced. These are two systems with no shared transaction. If you write the row and then publish, a crash between them loses the message. If you publish first, a crash leaves a message about an order that does not exist. Chapter 31 explains why two-phase commit across a database and a broker is usually avoided; the transactional outbox is the standard answer.

The relay is either a polling publisher (a loop selecting unsent rows, simple, adds latency and database load) or change data capture (Debezium tails the database log and emits outbox rows to Kafka, low latency, more infrastructure; see Chapter 36). Either way the guarantee is at-least-once, so the inbox on the consumer closes the loop, giving effectively-once results. Practical notes: add a periodic cleanup of old outbox and inbox rows, publish in per-key order so ordering is preserved, and index unsent rows so the poller is cheap.

15. Replay and reprocessing

Sometimes you need to process old messages again: a bug corrupted a downstream table, a new consumer needs history, or a DLQ has been fixed. How easy that is depends on the broker.

  • Log-based (Kafka, Kinesis): messages stay for the retention period (days to forever with compaction or tiered storage). Replay means resetting the consumer group's offset to an earlier point or timestamp. A new consumer group can read from the start. This is a major advantage of logs.
  • Queue-based (SQS, RabbitMQ): messages are deleted after ack, so there is nothing to replay unless you archive. Common practice is to also write every message to durable storage (an archive subscription to S3), and re-inject from there when needed.

Replay rules: (1) the consumer must be idempotent, because replay re-delivers messages it has already handled; (2) replay into a separate topic or group where possible, so the live flow is not disturbed; (3) rate limit the replay so downstream systems are not flooded; (4) be careful with side effects: replaying an OrderPlaced event must not send customers a second confirmation email, so separate pure state rebuilding from outbound side effects, or add a replay flag that suppresses them; (5) record what was replayed and why.

16. Routing and composition patterns

Small, single-purpose messaging components can be assembled into larger flows. These patterns come from the classic Enterprise Integration Patterns catalogue and still describe what stream processors and workflow tools do.

16.1 Content-based routing

A router inspects a message and sends it to one of several destinations: orders over 10,000 dollars go to the manual review queue, EU orders to the EU processor, type = refund to the refunds queue. Implement with broker features (RabbitMQ topic and headers exchanges, SNS filter policies, Kafka routing in a small stream processor) rather than hard-coding in every producer. Keep routing rules in one place, since scattered rules become unreadable.

16.2 Splitter and aggregator

A splitter breaks one message into many: an order with 20 line items becomes 20 item messages for parallel processing. An aggregator collects related messages back into one, using a correlation id and a completion rule: "all 20 items processed", or "wait at most 30 seconds". The aggregator needs state (which parts have arrived), a timeout (what to do with partial results), and idempotent handling (a duplicated part must not count twice).

16.3 Scatter-gather

Scatter-gather sends one request to several recipients in parallel and gathers their replies into one result: ask five shipping carriers for a quote and pick the cheapest, or query several shards. It is a splitter (scatter) plus an aggregator (gather) with a correlation id and a deadline. Choose the completion policy deliberately: wait for all, wait for the first N, or take whatever arrived at the deadline. Tail latency is set by the slowest participant, so the deadline matters (see Chapter 40).

16.4 Pipes and filters

Pipes and filters decomposes processing into a chain of small stages (filters), connected by queues or topics (pipes): validate, enrich, price, persist. Each stage can be scaled, deployed, and tested independently, and the queues buffer between stages of different speeds. The costs are extra latency per hop, more moving parts to monitor, and the need to handle failure at every stage. Stream processors (Kafka Streams, Flink) are essentially a managed way to build these chains.

17. Sagas via messages

When a business process spans several services, each with its own database, you cannot use one ACID transaction. A saga splits the process into local transactions, each followed by a message that triggers the next, with compensating actions (refund, release stock) when a later step fails. In a choreographed saga, services react to each other's events with no central controller. In an orchestrated saga, a coordinator sends commands and tracks state. All of the patterns in this chapter are the plumbing a saga relies on: each step must be reliably published (outbox), delivered at least once (retries), safe on repeat (idempotent consumer), and compensatable, with timeouts for missing replies and a DLQ for steps that cannot proceed. The overview is in Chapter 31 and the full treatment in Chapter 48.

18. Testing and observability of async flows

Asynchronous flows are harder to debug than call stacks: the cause and the failure are separated by queues and time. Plan for it from the start.

18.1 Observability

  • Propagate context. Put the trace id and correlation id in message headers, and continue the trace in the consumer (as a linked span, since the producer's span has already ended). Then one trace id shows the whole path.
  • Queue metrics: depth, age of oldest message, publish rate, consume rate, in-flight count, redelivery count, and DLQ depth. Age of oldest message and lag in time are the most meaningful.
  • Handler metrics: processing latency percentiles, success, retry, and dead-letter rates, grouped by message type and error class.
  • End-to-end latency: measure from the message's creation time to the completion of processing, not just handler time. It includes queue wait.
  • Structured logs with message id, type, key, attempt number, and outcome, so you can answer "what happened to message X?".
  • Alerts on lag age beyond SLA, DLQ non-empty, consumer count zero, and poison-loop signs (the same message id with a growing attempt count).

18.2 Testing

  • Unit-test handlers as pure functions with the same message delivered twice, and delivered out of order, to prove idempotency and order tolerance.
  • Contract tests between producer and consumer on the schema (consumer-driven contracts, or registry compatibility checks in CI).
  • Integration tests with a real broker in a container (Testcontainers) to exercise acks, visibility timeouts, and redelivery.
  • Fault injection: kill a consumer mid-message, drop acks, delay the downstream, send a malformed message, send a duplicate, and verify the system recovers and the DLQ receives the right things.
  • Load tests that include a burst and a recovery, to verify lag drains within SLA.
  • Asserting async outcomes: poll with a timeout for the expected final state rather than sleeping a fixed time.

20. Worked example: an order processing pipeline

An e-commerce site takes orders. Requirements: normal load 300 orders/s, flash-sale peak 3,000 orders/s for 5 minutes, accept the order in under 200 ms, then payment, inventory, shipping, email, and analytics must follow reliably. No order lost, no double charge.

20.1 Sizing the burst

  • Checkout writes 3,000 orders/s at peak to a partitioned database; the response returns after the commit, around 50 ms. The user sees "order received".
  • Fan-out: 3,000 events/s into 5 queues = 15,000 deliveries/s at peak.
  • Payment is the slowest: 150 ms average per call to the payment provider, which is limited to 800 requests/s. Needed concurrency by Little's law: 800 × 0.15 = 120 workers at the cap. The payment queue is therefore drained at 800/s, not 3,000/s.
  • Backlog from the 5-minute peak: (3,000 − 800) × 300 = 660,000 messages in q-payment. Baseline arrival 300/s leaves net drain of 500/s, so clearing takes 660,000 ÷ 500 = 1,320 s, about 22 minutes. Is 22 minutes of payment delay acceptable? If not, negotiate a higher provider limit, or prioritize (below). Meanwhile checkout stays fast because the queue absorbs the burst.
  • Email, analytics, and shipping have no hard external limit: scale each to clear in under 2 minutes after the burst.

20.2 Correctness choices

  • Partitioning and order: events keyed by order id, so an order's Placed, Paid, and Shipped events stay in order for each consumer. With 24 partitions on the topic and 8 per-queue-group consumers per partition-set, throughput comes from the many orders.
  • Idempotency: the payment worker sends the order id as the provider's idempotency key, and records the message id in an inbox row in the same transaction as the payment record. A redelivered message becomes a no-op, so a double charge cannot occur.
  • Retries: payment provider 503s retry at 5 s, 30 s, and 5 min with jitter, then DLQ. A declined card is a permanent business outcome, not an error: it emits PaymentFailed, and the saga cancels the order and releases stock (Chapter 48).
  • Priority: a separate q-payment-priority for orders from customers with express shipping, which gets 30 percent of payment capacity.
  • TTL: the email queue drops "your order is on its way" messages older than 24 hours.
  • Schema: the envelope carries schemaVersion; the registry enforces backward compatibility; consumers are deployed before producers.
  • Claim check: the invoice PDF is stored in object storage and only its reference travels in the shipping message.

20.3 Failure walk-through

  1. The relay crashes after publishing 100 rows but before marking them sent. On restart it republishes them. Duplicates reach the consumers, which dedup by message id. No loss.
  2. The inventory service is down for 10 minutes. Its queue grows to 1.8 million messages at 3,000/s; other consumers are unaffected, which is the benefit of one queue per consumer. When it returns, it drains at its own capacity; alerts fired on age of the oldest message at 2 minutes.
  3. A deploy introduces a bug that crashes on orders with an empty address. Those messages hit max receive count (5) and land in q-shipping-DLQ. Alert fires. The team fixes the bug and uses the redrive tool at 100 messages/s. Because the handler is idempotent, redriven messages that had partly succeeded are safe.

21. Interview Q&A

When would you choose a queue versus a topic with subscribers?

Choose a queue when the message is a command with one logical owner: "resize this image" should be done once by one worker out of a pool. Choose a topic when the message is a fact that several independent parties might care about and the producer should not know who they are. In practice you combine them: publish the event to a topic and give each subscribing service its own queue, which gives broadcast plus per-consumer buffering, retry, and DLQ. The deciding question is who must act and whether the sender needs to know.

How do you preserve message order while still scaling consumers?

Do not seek global order; require order per entity. Choose a key such as order id, hash it to a partition (or use a FIFO group id), and have one consumer own each partition. Messages for one key stay ordered, while different keys process in parallel across partitions and consumers. The limits are that parallelism cannot exceed the number of partitions, a hot key throttles one partition, and a failing message blocks its partition. If the transport cannot guarantee order, add per-entity sequence numbers or versions and have the consumer buffer, skip stale messages, or apply versioned state so that disorder is harmless.

Design the retry strategy for a consumer calling a flaky downstream service.

First classify errors: transient (timeouts, 503) are retried, permanent (validation, bad data) go straight to the DLQ. For transient errors, do one or two quick in-process retries, then use delayed retries with exponential backoff and full jitter, implemented via retry tiers (10 s, 1 min, 10 min topics) so the main queue is not blocked. Cap attempts and total age, and after the last tier dead-letter the message. Add a circuit breaker so that when the downstream is clearly down the consumer pauses instead of cycling every message through the tiers. Jitter matters because otherwise a burst of failures synchronizes into repeated retry waves.

What is a poison message and how do you handle one in an ordered stream?

A poison message is one that can never be processed successfully, for example malformed data or a payload that triggers a handler bug, so every retry fails. Left alone it blocks its partition or loops forever. You detect it with a delivery-attempt counter or a non-retryable error type, move it to a DLQ with full context (payload, error, offsets, attempts), alert, and then fix and redrive at a controlled rate. In a strictly ordered stream, skipping it means later messages for that key run first, so you either accept that and make handlers version-aware, or halt that key until a human resolves it. The choice depends on whether correctness or availability matters more for that data.

How can you achieve exactly-once processing when the broker is at-least-once?

You cannot make the network deliver exactly once, but you can make the effect happen once. Combine at-least-once delivery with an idempotent consumer: give every message a unique id, and in the same database transaction as the business change insert that id into an inbox table with a unique constraint, so a duplicate is rejected and rolled back. For external side effects, pass the id as an idempotency key to the other service. On the producing side, use the transactional outbox so the event is published if and only if the state change committed. Kafka transactions give exactly-once within Kafka read-process-write pipelines, but they do not extend to side effects in other systems.

Your consumer lag is growing. How do you diagnose and respond?

First determine whether production rose or consumption fell. Check the produce and consume rates, handler latency, error and retry rates, rebalance frequency, and downstream health. If handlers are slow because a dependency is slow, adding consumers may worsen things, so throttle concurrency and fix or protect the dependency. If the consumers are the bottleneck and the partitions allow it, scale out. If lag is only a burst, estimate the drain time (backlog divided by consume rate minus produce rate) and decide if it is within the SLA. Long term, apply backpressure to producers, shed low-value or expired work with TTL, and alert on age of the oldest message rather than raw depth.

Why does the transactional outbox exist, and what are its costs?

A service that updates its database and then publishes to a broker can crash between the two, losing the event, and publishing first risks announcing something that never committed. Two-phase commit across a database and a broker is usually unavailable or too fragile. The outbox writes the event into a table in the same local transaction as the state change, and a relay (poller or change-data-capture) publishes it afterwards. The costs are an extra table and relay to operate, added publishing latency, at-least-once publishing (so consumers need an inbox or idempotency), and cleanup of old rows. In exchange the system never loses or invents events.

When would you use the claim check pattern, and what can go wrong with it?

Use it when payloads are large relative to broker limits and efficiency, such as documents, images, or big JSON: store the payload in object storage and send a small reference with a checksum. This keeps messages small, so throughput, retries, and DLQ handling stay cheap. Failure modes include sending the message before the upload completes (a dangling reference), objects deleted before the message is processed or replayed (so lifecycle rules must outlive message retention), overwritten objects that change replay results (use immutable keys), and permission gaps for consumers. Also remember the storage is a second system whose availability and cost you now depend on.

How would you implement request-reply over a message queue, and when is it a bad idea?

The requester sends a message to a request queue with a reply-to address and a correlation id, the responder processes it and publishes the answer to the reply-to queue with the same correlation id, and the requester matches it to the pending call. It needs a timeout, idempotent requests (a timed-out request may still run), and tolerance for late or duplicate replies. It is a good fit when the responders are a slow or bursty worker pool and you want buffering. It is a bad idea as a general replacement for synchronous calls on a hot path, since it adds latency and operational complexity, and a plain RPC with timeouts and retries is simpler.

Why is "one shared queue for several teams" a problem, and what is the alternative?

A shared queue couples the teams: one team's slow consumer or poison message delays everyone, a schema change breaks unrelated readers, nobody owns capacity or the DLQ, and competing consumers from different teams would each steal messages meant for others. The alternative is a published topic or event stream owned by the producing team, with each consuming team given its own queue or consumer group, its own retry policy and DLQ, and a documented schema contract checked in a registry. Each team can then deploy, scale, and fail independently.

22. Recap

  • Brokers give at-least-once delivery and partial ordering; patterns exist to make consumers correct anyway.
  • Queues carry commands to one consumer; topics carry events to many. SNS plus SQS (or Kafka groups) gives durable fan-out with per-consumer isolation.
  • Competing consumers scale throughput, bounded by partitions and downstream capacity; scale on backlog age.
  • Require order per key, not globally: key partitioning, sequence numbers, or versioned state; ordering costs parallelism and invites head-of-line blocking.
  • Retry only transient errors, with bounded attempts, exponential backoff with jitter, and retry tiers; dead-letter the rest with context, alert, and redrive at a controlled rate.
  • Idempotent consumers (inbox table, conditional updates, idempotency keys) turn at-least-once into effectively-once.
  • Handle load with backpressure, bounded queues, queue-based load leveling, separate priority queues, delays, and TTL.
  • Use correlation ids for request-reply and tracing, claim check for big payloads, envelopes plus a schema registry for evolution, and the outbox for atomic state-plus-publish.
  • Compose flows with routers, splitters, aggregators, scatter-gather, and pipes and filters; sagas rely on all of the above.
  • Test duplicates, reordering, and crashes; observe lag age, DLQ depth, and end-to-end latency; avoid queue-as-database, giant messages, unbounded retries, and shared queues.
