Caching I: Patterns

Caching is the single most common technique for making a system faster and cheaper to run. This chapter explains why it works, where caches sit, the ways data moves in and out of them, how a full cache decides what to drop, and how to keep cached data from going stale.

1. The problem caching solves

Start with a concrete system. You run an online store. Every product page shows the product name, price, photos, description, average rating, and stock status. All of that lives in a relational database, spread over several tables: products, prices, reviews, inventory.

Here is what happens, without any cache, each time someone opens a product page:

  1. The request reaches an app server.
  2. The app server sends a query to the database. To build one page, the query joins several tables and computes the average rating from thousands of review rows.
  3. The database reads from its tables and indexes (partly from memory, partly from disk), does the join and the aggregation, and sends the result back.
  4. The app server turns the result into HTML or JSON and replies.

Suppose that query takes about 20 ms and uses a measurable amount of database CPU. A single database server can only do so much work at once. If it can run roughly 3,000 of these queries per second, then at 3,000 requests per second it is fully busy. At 20,000 requests per second, which is a normal peak for a popular store, the database falls behind. Queries queue up, each one waits longer, pages load slowly, and eventually the database stops responding and the whole site goes down.

Now notice something about this workload. The product page for a popular phone is requested thousands of times per minute, and it is the same page every time. The database does the same expensive join, produces the same answer, and throws it away, thousands of times. Only a handful of times per day does the answer change (when the price or stock is updated).

That is the opportunity. If we remember the answer after computing it once, and hand back the remembered answer for the next requests, we skip nearly all of the work. The place where we keep the remembered answers is a cache.

Definition A cache is a storage layer that keeps copies of data that is expensive to fetch or compute, in a place that is much faster to read from than the original source. The original source (here, the database) is called the source of truth. The cache never replaces it. It only holds copies.

Think of the papers on your desk versus the filing cabinet in the next room. You keep the few papers you use all day on the desk. When you need something else, you walk to the cabinet, and often bring a copy back to the desk in case you need it again. The desk is small, but because most of your work uses the same few papers, it saves you hundreds of walks.

Caching helps a system in three separate ways:

  • Lower latency. Memory is thousands of times faster than disk, and avoiding a database round trip removes tens of milliseconds from the response. Users feel this directly.
  • Higher throughput. One cache server holding data in memory can answer on the order of 100,000 simple reads per second. A database doing real query work answers far fewer. Moving reads to the cache raises how many requests the whole system can handle.
  • Protection for the backend. The database only receives the requests the cache could not answer. If 95% of reads are served from the cache, the database sees one twentieth of the load. That often means you can run a smaller database, or put off the difficult work of sharding it (Chapter 25) for a long time.

To feel the size of the gap, compare how long different operations take. These are rough figures, and they vary by hardware and network, but the ratios are what matter:

2. Why caching works: access is uneven

A cache is much smaller than the full dataset. If you have 50 million products, you cannot keep all of them in memory on a few cache servers. So why does a small cache help so much? Because real traffic is highly uneven. Two properties of how programs and people access data explain it.

Temporal locality. Data that was used recently is likely to be used again soon. A product that was just viewed is likely to be viewed again in the next few minutes, because it is trending, or was shared in a link, or is simply popular.

Skewed popularity. A small share of items receives most of the requests. In many systems, a rough rule of thumb is that about 20% of the items account for about 80% of the reads. The exact ratio varies, and for some workloads (a viral video, a front page) it is far more extreme, but the shape is almost always the same: a few very popular items and a very long tail of items that are rarely requested.

Together these mean that a cache holding only the popular 5–20% of the data can answer most of the requests. The long tail still goes to the database, but it is a small share of the traffic.

Key idea Caching only pays off when some data is requested far more often than other data. If every item were requested exactly once, a cache would never be hit and would be wasted. Always check the access pattern before adding a cache: is the same data read again and again?

3. What caching costs

Caching is not free, and in an interview it is worth showing that you know the costs, not just the benefits.

  • Stale data. The cache holds a copy. If the original changes and the copy does not, readers see old data. Most of the engineering effort in caching goes into controlling this (see Invalidation, section 8).
  • Extra moving parts. A cache is another system to deploy, monitor, size, secure, and keep available. It has its own failure modes.
  • Memory cost. RAM is much more expensive than disk. Caching everything is rarely affordable.
  • More complicated code and debugging. When a user reports a wrong value, you must now ask whether it came from the database or from a stale cache entry.
  • New failure scenarios. If the cache goes down or is emptied, all traffic suddenly hits the database. A system that only works because of its cache can collapse when the cache disappears (Chapter 14).
When not to cache Do not cache data that is almost never read twice, data that must always be exactly current (for example, the available balance right before a payment is authorized), or data that is cheap to read from the source anyway. A cache is an optimization for a measured problem, not a default.

4. Where can a cache live?

A request travels through several layers on the way from a user to the database, and a cache can sit at almost any of them. The general rule: the closer to the user, the faster the answer, but the harder it is to keep fresh and the less you control it.

4.1 Browser cache

The user's own browser keeps copies of files it has downloaded: images, scripts, stylesheets, and sometimes API responses. The server controls this with HTTP headers. For example:

Cache-Control: public, max-age=86400
ETag: "v42-abc"

max-age=86400 tells the browser it may reuse this response for 86,400 seconds (one day) without asking the server at all. After that, the browser can send a conditional request with If-None-Match: "v42-abc". If the content has not changed, the server replies 304 Not Modified with no body, which is very cheap. If it has changed, the server sends the new content.

This layer is free and instant, but you cannot reach into a user's browser and delete an entry. If you serve a file with a one-day lifetime and then need to change it right now, some users will keep the old copy. The usual fix is to put a version or content hash in the file name (app.3f9c1a.js), so a new version is a new URL.

4.2 CDN (content delivery network)

A CDN is a network of cache servers placed in many cities around the world. A user in Singapore is served from a nearby edge server instead of from your data center in Virginia, which removes a long network round trip. With a pull CDN, the edge fetches content from your origin the first time someone asks for it, then keeps it for the configured lifetime. With a push CDN, you upload the content to the CDN ahead of time. CDNs are best for static or rarely changing content: images, video segments, scripts, and public pages. Chapter 12 covers them in detail.

4.3 In-process (local) cache

This is a data structure, such as a hash map with a size limit, inside your application's own memory. A read is just a memory access, with no network at all, so it takes microseconds or less. The catch: if you run 20 app servers, there are 20 separate local caches. Each one fills up on its own, wastes memory by holding duplicate copies, and can disagree with the others (server 3 may hold the old price while server 7 already has the new one). A local cache is a good fit for small, hot, rarely changing data, such as configuration, feature flags, or a list of countries, and usually with a short lifetime.

4.4 Distributed cache

This is a separate cluster of cache servers, such as Redis or Memcached, shared by all your application servers. Every app server sees the same cached data, so there is one copy to keep fresh, and the cache can be far larger than any one machine by spreading keys across several nodes (Chapter 25 explains how, with consistent hashing). The cost is one network hop per access, around 0.5–1 ms inside a data center. This is the layer most interview questions mean when they say "add a cache".

4.5 Database-level caches

Databases already cache internally. A relational database keeps recently used data pages in a buffer pool in memory, so repeated reads of the same rows avoid disk access. This is automatic and helps, but it still pays for query parsing, planning, joins, and the network round trip. An application cache stores the final, assembled answer, which skips all of that.

CDNImages, video, scripts, public pagesClose to users worldwideInvalidation is slow and can be costly

Interview tip Strong answers use layers: "static assets go to a CDN, hot reference data sits in a short-lived local cache, and per-entity query results sit in Redis." Layering shows you understand that each cache protects the next layer down.

5. Hit ratio, miss types, and sizing

Every lookup in a cache ends in one of two ways:

  • A hit: the data was in the cache and is returned directly.
  • A miss: the data was not in the cache, so the system has to fetch it from the source, and usually stores it in the cache for next time.

The hit ratio is the fraction of lookups that are hits: hits ÷ (hits + misses). It is the single most important number for judging whether a cache is working.

5.1 Why a few percent of hit ratio matters so much

Take a 1 ms cache in front of a 20 ms database. Every request pays for the cache lookup (1 ms). Only the misses also pay for the database (20 ms). So the average latency is 1 + (miss ratio × 20), and the load reaching the database is requests × miss ratio.

Hit ratioMiss ratioAverage latencyDB load at 10,000 req/s
50%50%1 + 0.5 × 20 = 11 ms5,000 req/s
90%10%1 + 0.1 × 20 = 3 ms1,000 req/s
99%1%1 + 0.01 × 20 = 1.2 ms100 req/s

Going from 90% to 99% sounds like a small improvement, but it cuts the database load by a factor of ten. Think about it in terms of misses, not hits: 99% means one miss per 100 requests, 90% means ten. The database cares about the misses.

Try it: hit-ratio calculator

5.2 Three reasons a lookup misses

Knowing why misses happen tells you how to reduce them.

  1. Cold (compulsory) miss. The data has never been requested, or the cache was just started or emptied. Every item has to be loaded at least once. You reduce these with cache warming (section 10).
  2. Capacity miss. The item was in the cache, but the cache was full and evicted it to make room, and then it was requested again. You reduce these with more memory, a better eviction policy, or by caching smaller values.
  3. Invalidation miss. The item was deliberately removed or expired because the data changed or its lifetime ended. This is correct behavior, but a very short lifetime or very frequent updates cause many of these.

5.3 Sizing a cache

You do not need to cache everything, only the working set: the data actively being used over a period of time. A back-of-envelope example:

  1. The catalog has 10 million products. Each cached product object (name, price, rating, a few fields) is about 2 KB.
  2. Caching all of them would take 10,000,000 × 2 KB = 20 GB.
  3. If traffic follows the 80/20 pattern, caching the hot 20% takes about 4 GB and serves about 80% of reads. Caching the hottest 5% (1 GB) may already cover 60–70%.
  4. Real caches carry overhead for keys, pointers, and fragmentation, so budget roughly 1.3–2× the raw data size. 4 GB of values becomes about 6–8 GB of memory.
  5. Then check the other limit: throughput. If a single Redis node comfortably handles about 100,000 operations per second and you need 200,000, you need at least a few nodes regardless of memory.

The right way to confirm the numbers is to measure the real hit ratio as you grow the cache. The returns diminish: past a point, doubling the memory adds only a point or two of hit ratio, and it stops being worth the cost.

6. Caching patterns: how data gets in and out

The word "caching" hides a design decision: who is responsible for putting data into the cache and keeping it correct, and when does that happen? There are five standard answers. Each one is a pattern, and each has different effects on speed, freshness, and risk. Learn them as a group, because interviewers expect you to pick between them with reasons.

6.1 Cache-aside (also called lazy loading)

This is the most common pattern in practice. The application code is in charge. The cache is a passive key-value store and knows nothing about the database. The cache is filled "lazily", meaning only when someone asks for the data.

How a read works

  1. The app asks the cache for product:123.
  2. Hit: the cache returns the value and the app responds. The database is never touched.
  3. Miss: the cache says it has nothing. The app queries the database.
  4. The app stores the result in the cache with a TTL (a time after which it expires), so the next request is a hit.
  5. The app returns the result.

How a write works

  1. The app updates the row in the database. The database is the source of truth, so it is updated first.
  2. The app deletes the cached entry for that key.
  3. The next read finds no entry (a miss), reads the fresh value from the database, and caches it again.

A concrete example

A user opens their profile. The app looks up user:42 in Redis and gets nothing (the first visit today). It runs SELECT * FROM users WHERE id = 42, gets the row, stores it in Redis for 10 minutes, and returns it. The next 50 requests for that profile in the next 10 minutes are answered from Redis in about 1 ms each. If the user edits their name, the app updates the database and deletes user:42. The following request reloads the new name.

Why delete on write, instead of updating the cached value?

Updating the cache to the new value looks more efficient, since the next read would be a hit. But it opens a race condition, and it wastes work if the value is rarely read again. The diagram below shows the race that deleting avoids and that updating would make worse.

This race is rare, because it needs the reader's database read and cache write to straddle a writer's update, and the window is short. But under heavy traffic it will happen eventually, which is the main reason every cache entry should have a TTL: it puts a ceiling on how long a mistake like this can survive. Deleting is the safer choice than updating, because with updates two concurrent writers can also leave the cache holding the older of the two values.

Strengths and weaknesses

  • Resilient. If the cache is down, the app can still read from the database. It is slower, but it works.
  • Efficient on memory. Only data that has actually been requested is cached, so the cache fills with what users use.
  • Flexible. You can cache any shape of data, such as an assembled object built from several queries.
  • Cold misses. The first request for each key always goes to the database.
  • Staleness. Between a database change that bypassed the app and the next expiry, the cache can be wrong.
  • Caching logic lives in every code path. If one service forgets to delete the key on update, readers see stale data. Wrapping cache calls in one shared library helps.

6.2 Read-through

Read-through is the same idea as cache-aside, but the loading logic moves into the cache layer. The application only ever asks the cache for data. If the cache has it, it returns it. If not, the cache itself calls a loader function (configured once) that reads the database, stores the result, and returns it. The app never talks to the database for reads.

Why choose it? Application code becomes simpler (one call instead of get, check, query, set), and the loading logic lives in one place, so it cannot be done inconsistently. It also lets the cache layer do smart things on its own, such as making sure that when 100 requests miss the same key at the same moment, only one actually calls the database (Chapter 14).

Costs: it needs a cache product or library that supports loaders, so you cannot use a plain key-value store as is. The cache also becomes a hard dependency for reads. Every read path goes through it.

Real example: many managed caches and in-process libraries (such as Caffeine in Java with a LoadingCache) work this way.

6.3 Write-through

The two patterns above are about reads. Write-through is about writes. Every write goes to the cache and to the database as one synchronous operation. The caller is told "success" only after both are updated.

Step by step

  1. The app writes the new value to the cache layer.
  2. The cache layer writes the same value to the database.
  3. When the database confirms, the cache layer confirms to the app.

What you gain: the cache is never stale for data written through it, because it was updated in the same operation. A read right after a write is a hit with the newest value. This removes the delete-then-reload gap of cache-aside.

What you pay: every write now costs two operations in sequence, so write latency is the cache's time plus the database's time. And you cache every written item even if nobody reads it. If your app writes 1 million log entries and reads 100, you filled the cache with 999,900 useless items, which may push out useful data.

Failure case: what if the cache write succeeds and the database write fails (or the other way around)? The two are now out of sync. Real implementations must either make both steps one transaction, or roll back the cache entry if the database write fails. This is why write-through is usually offered by a cache product that handles it, rather than coded by hand.

Good fit: data that is read a lot soon after it is written, where staleness is unacceptable, such as user session data or a user's own settings page.

6.4 Write-back (also called write-behind)

Write-back optimizes for write speed. The app writes to the cache, and the cache acknowledges immediately. The database is updated later, asynchronously, often by collecting many changes and writing them in one batch.

Why it is attractive

Consider a video site counting views. Each view is a tiny write, and a popular video can get thousands per second. If every view required a database write, the database would be overwhelmed by trivial updates. With write-back, the cache increments the counter in memory (fast), and every few seconds a background job writes the latest total to the database in one operation. A thousand increments become one database write. This is called write coalescing and is the biggest benefit: many writes to the same key collapse into one.

The danger

Until the flush happens, the newest data exists only in cache memory. If that cache node crashes or restarts, the unflushed writes are gone forever. For view counts, losing a few seconds is acceptable. For a payment or an order, it is not. You can reduce the risk by replicating the cache across nodes or writing a log of pending changes to disk, but that adds complexity, and it never fully equals the safety of writing straight to the database.

Other consequences: the database is briefly out of date, so anything reading the database directly (reports, other services) sees older data than the cache has.

Good fit: high-volume writes where small loss is tolerable and write coalescing helps: counters, "last seen" timestamps, analytics events, game scores.

6.5 Write-around

With write-around, writes go directly to the database and skip the cache entirely. The cache is only filled when something is read (as in cache-aside).

Why do it? To avoid cache pollution: filling the cache with data that will probably never be read, and thereby evicting data that would have been. Imagine users uploading photos: each photo is written once, and most are viewed rarely or never. Caching each at write time would waste memory. Instead, you cache a photo only if someone actually looks at it.

Downside: the first read after a write is a guaranteed miss, because the data was never put in the cache. If data is read right after being written (a user uploads a photo and immediately views it), write-around is a poor choice.

In practice, write-around is usually combined with cache-aside for reads, and cache-aside's "delete on write" is effectively a form of it.

6.6 A sixth idea: refresh-ahead

Instead of waiting for an entry to expire and then making the next user wait for a reload, the cache refreshes popular entries in the background before they expire. If an entry has a 10-minute lifetime and gets requested again in minute 9, the cache quietly reloads it from the database so it never actually expires. Users always see a hit for popular keys. The cost is wasted work refreshing entries that nobody asks for again, and the complexity of predicting what to refresh. It is useful for a small set of very hot, expensive-to-compute keys, and it helps avoid the stampede problem covered in Chapter 14.

View counters use write-back, because losing a few seconds of counts is acceptable and it saves a huge number of database writes."

7. Eviction: what to remove when the cache is full

A cache has a fixed amount of memory. Once it is full, adding a new item means removing an existing one. The rule for choosing which item to remove is the eviction policy. A good policy removes the items least likely to be needed again, which keeps the hit ratio high. A bad policy throws away useful data and fills the space with data nobody wants.

Do not confuse eviction and expiry. Expiry (TTL) removes an item because it has become too old, even if the cache has plenty of room. Eviction removes an item because the cache is out of room, even if the item is still fresh. Real caches use both.

7.1 The common policies

PolicyWhat it evictsStrengthWeakness
LRU (Least Recently Used)The item that has gone unused the longestMatches temporal locality. A good default.A one-time scan over lots of data can push out the real hot items
LFU (Least Frequently Used)The item used the fewest timesProtects consistently popular items from a scanOld items that were once popular can linger forever unless counts decay; new items start with low counts and may be evicted too soon
FIFO (First In, First Out)The item that was added earliestTrivial to implementIgnores usage, so it can evict the most popular item just because it is old
RandomA random itemNo bookkeeping at allNo intelligence, but often performs surprisingly close to LRU
TTL-basedItems closest to expiringFits time-limited dataIgnores usage

7.2 LRU in detail

LRU rests on a simple belief: if you have not used something for a long time, you probably will not use it soon. It keeps items in order of how recently they were used. Every time an item is read or written, it moves to the "most recent" end. When space is needed, the item at the "least recent" end is dropped.

Here is a cache of capacity 3, processing these accesses one at a time. The list is shown most recent first:

StepAccessWhat happensCache contents (most recent → least recent)
1put ARoom available, add AA
2put BRoom available, add B at the frontB, A
3put CRoom available, add C at the frontC, B, A
4get AHit. A moves to the frontA, C, B
5put DFull. Evict the least recent (B), add DD, A, C
6get BMiss, because B was evicted. Load it, which evicts CB, D, A

Step 4 is the important one: reading A "saved" it. Without that read, A would have been the one evicted at step 5.

Making LRU fast: O(1) operations

A naive version, scanning a list to find or reorder an item, would be slow for a big cache. The standard design uses two structures together:

  • A hash map from key to list node: finds any item in constant time.
  • A doubly linked list of items ordered by recency: because each node knows both its neighbors, a node can be unlinked and moved to the front in constant time, and the tail (the least recent item) can be dropped in constant time.

7.3 LFU, and why neither LRU nor LFU is perfect

LFU counts how often each item is used and evicts the one with the lowest count. Imagine a cache that serves a news site. Last week's big story had 5 million views, so its count is huge. Today, nobody reads it. Under pure LFU it stays in the cache for a very long time because of its old count, wasting space. Real LFU implementations fix this by decaying the counts over time, so old popularity fades.

LRU has the opposite weakness. Suppose a batch job reads 10 million rarely used rows once. Each read moves a row to the "most recent" end, pushing out the genuinely hot items that real users need. This is called cache pollution by a scan. Smarter variants (such as 2Q, ARC, or TinyLFU) address both problems, and you rarely need to know their internals for an interview, but it is worth knowing that "LRU" in a production system is often a refined version.

7.4 What real systems do

Redis does not keep a perfect LRU list, because that would cost extra memory per key. Instead, when it needs to evict, it samples a small number of random keys (5 by default, set by maxmemory-samples) and evicts the least recently used of that sample. This approximate LRU is much cheaper and gets close to the result of real LRU. You choose the behavior with the maxmemory-policy setting:

Policy name in RedisMeaning
noevictionNever evict. When full, writes fail with an error. Reads still work.
allkeys-lru / allkeys-lfuEvict from all keys by LRU or LFU. The usual choice for a pure cache.
volatile-lru / volatile-lfuEvict only from keys that have a TTL set. Keys with no TTL are safe.
allkeys-random / volatile-randomEvict a random key.
volatile-ttlEvict keys with the shortest remaining TTL first.

The volatile-* policies are useful when the same Redis holds both disposable cache data (with a TTL) and data you must not lose (no TTL), though mixing the two in one instance is usually discouraged.

8. Invalidation: keeping cached data correct

"There are only two hard things in computer science: cache invalidation and naming things."

Every cached value is a copy. The moment the original changes, the copy is wrong. Invalidation is the work of making sure users do not keep seeing wrong copies. There is no single perfect solution, because it is a tradeoff between how fresh the data must be, how much work you can afford, and how complex the system can get. Here are the main techniques, from simplest to most involved.

8.1 Time-based expiry (TTL)

Give every entry a time to live. After that many seconds, the cache discards it automatically, and the next read reloads fresh data. It needs no coordination at all, and it also acts as a safety net for every other technique, because even if you forget to invalidate something, it eventually corrects itself.

The tradeoff is that data can be stale for up to the TTL. A 60-second TTL means a price change can take up to a minute to show. A shorter TTL means fresher data but more misses and more database load. A longer TTL means a better hit ratio but older data. Choose the TTL from the business answer to "how stale is acceptable?"

8.2 Explicit invalidation on write

When the data changes, the code that changed it also deletes (or updates) the cached copy. This keeps data fresh within milliseconds, which TTL alone cannot. The difficulty is completeness: one fact can be cached in many places. If a product's price changes, you must remove product:123, but also the cached category page that lists it, the cached search results that include it, and a cached cart total. Missing one leaves stale data behind. For this reason, explicit invalidation is best for simple, well-understood keys, and combined with a TTL as a backstop.

8.3 Event-driven invalidation

Instead of the writing code knowing every cache to clear, the database change is published as an event (for example through change data capture, covered in Chapter 36, or a message queue). Any interested service listens and clears or refreshes its own cache entries. This works well across many services, because the writer does not need to know who is caching its data. The costs are infrastructure and the need for reliable delivery: if an event is lost, a cache may stay stale until its TTL expires.

8.4 Versioned keys

Instead of deleting an entry, include a version in the key: user:42:v7. When the user changes, the version becomes v8 and the app starts reading user:42:v8, which does not exist yet and is loaded fresh. The old v7 entry is never read again and is cleaned up by its TTL or by eviction. This avoids race conditions like the one shown earlier, since no one ever overwrites a key with stale data. You need to know the current version, which is usually stored in a small, fast place of its own (for example a counter in the database row or a tiny cache entry). The same idea is used for web files with content hashes in their names.

Interview tip Before choosing a TTL or an invalidation approach, ask the interviewer: "How stale can this data be?" That one question shows that you treat caching as a business tradeoff and not a purely technical trick.

9. Designing cache keys and values

9.1 Keys

A cache is a lookup table, so the key decides whether two requests share an entry. Two rules: the key must contain everything that changes the answer, and it must not contain anything that does not.

  • If the product page differs by language and currency, then the key needs both: product:123:en-US:USD. Leaving out the language would show French users the English page.
  • If you put something irrelevant in the key (a tracking parameter, a timestamp), every request gets a unique key, nothing is ever shared, and the hit ratio falls to zero.
  • Use a clear, consistent naming scheme with a namespace prefix: service:entity:id:variant. It makes keys easy to find, delete in groups, and debug.
  • Include a schema version (v2) when the shape of the cached value may change after a deployment, so new code does not try to read old-format data.
  • Keep keys reasonably short. Millions of long keys use real memory.

9.2 Values

  • Cache the final answer, not the raw pieces. If a page needs data from three queries, cache the assembled result, since the assembly is the expensive part.
  • Choose a compact format. JSON is easy to read and debug but larger and slower to parse. Binary formats such as Protocol Buffers or MessagePack are smaller and faster. For large values, compression trades CPU time for memory.
  • Avoid very large values. A single multi-megabyte value takes longer to transfer and can block a single-threaded server such as Redis while it is processed. Break large objects into parts, or keep them in object storage and cache only references.
  • Cache "not found" results too. If a product ID does not exist, store a short-lived "empty" marker. Otherwise every request for that missing ID reaches the database, which is also a way an attacker can bypass your cache by requesting random IDs. This is called negative caching, and Chapter 14 covers it.
  • Think about shared vs per-user data. A key like product:123 is shared by all users and caches well. A key like user:42:recommendations serves a single user, so it gets far fewer hits for the same memory.

9.3 TTL with jitter

Always set a TTL, and add a small random amount (jitter) to it. Suppose you load 100,000 keys at startup, each with an exact 10-minute TTL. Ten minutes later they all expire at the same instant, and 100,000 requests hit the database together. With jitter (a TTL of 10 minutes ± up to 1 minute at random), expirations are spread out over time. Chapter 14 covers this "avalanche" in depth.

10. Cold start and cache warming

A new or restarted cache is empty, so at first nearly every request is a miss. The hit ratio starts at 0% and climbs as popular items are loaded. During this period the database takes the full load that the cache normally absorbs. If the system relies on the cache to survive normal traffic, an empty cache at peak time can overload the database, and the problem gets worse because slow responses cause retries, which add even more load.

Ways to handle it:

  • Cache warming. Before sending traffic to a new cache, load it with the data you know will be needed: the most popular products, the previous day's top keys, or the result of replaying recent real queries.
  • Gradual traffic shift. Route a small share of traffic to the new cache, let it fill, then increase.
  • Persistence. Some caches (Redis with snapshots or an append-only log) can reload their data from disk after a restart, so they do not start empty.
  • Protect the database. Rate limiting and load shedding (Chapter 16) keep a cold start from becoming an outage.

11. Putting it together: a worked example

Problem. A product detail page receives 20,000 reads per second at peak and about 50 writes per second (price and stock changes). A single database handles about 3,000 of these queries per second. Design the caching.

Step 1: Look at the workload

20,000 reads against 50 writes is 400 reads for every write. It is strongly read-heavy and the same pages are read repeatedly, so caching is a good fit. The database can handle 3,000/s, so we need to remove at least 17,000/s of reads from it, which is 85% of them. We need a hit ratio comfortably above 85%.

Step 2: Pick patterns

Reads use cache-aside on a Redis cluster. Writes update the database, then delete the key. Every entry gets a 5-minute TTL with jitter as a safety net.

Step 3: Check the load

Step 4: Size the cache

With 2 million products at about 2 KB each, the full set is 4 GB. Because traffic is skewed, caching all of it may be affordable here, which gives an excellent hit ratio. With overhead, plan around 8 GB. Throughput: 19,000 reads per second at 95% means about 19,000 cache lookups per second, which a few Redis nodes handle easily, and two or more nodes give redundancy.

Step 5: Add a second layer for the hottest items

The top ~100 products might receive 30% of all traffic. A tiny in-process cache on each app server, with a 10-second TTL, answers those without even the Redis hop. The 10-second TTL limits the inconsistency between servers.

At 1,000 requests per second on one key, what happens at the moment the entry expires and hundreds of requests all miss together? 12. What can go wrong (preview of Chapter 14)

Caches create their own failure modes. You do not need the solutions yet, but you should recognize the names:

  • Cache stampede (thundering herd): a popular entry expires and many requests all miss at once and hit the database together.
  • Cache avalanche: a large number of entries expire at the same time, or the whole cache goes down, and the database takes the full load.
  • Cache penetration: requests for data that does not exist always miss, so each one reaches the database.
  • Hot key: one key receives so much traffic that the single cache node holding it becomes the bottleneck.
  • Inconsistency: the cache and database disagree because of races or lost invalidations.

13. Common interview questions

What is the difference between cache-aside and read-through?

They give the same result. The difference is who is responsible for loading data on a miss. In cache-aside, the application checks the cache, queries the database itself, and fills the cache. In read-through, the application only talks to the cache, and the cache layer loads from the database through a configured loader. Cache-aside is more flexible and works with any plain cache. Read-through is simpler for the application but needs cache support, and makes the cache a hard dependency for reads.

Why delete the cached entry on a write, instead of updating it?

Updating risks leaving the wrong value in the cache. With concurrent operations, a slower earlier operation can overwrite a newer value, and the cache stays stale until the TTL expires. Deleting is safe: the next read reloads whatever the database holds at that moment. It is also cheaper when the value might never be read again, because you avoid building and storing a value nobody asks for.

When would you choose write-back, and what is the risk?

Write-back fits very high write volumes where losing a short window of recent writes is acceptable, and where many writes hit the same key, such as view counters. The cache acknowledges writes immediately and flushes to the database in batches, turning thousands of writes into one. The risk is that unflushed data exists only in cache memory and is lost if the cache node crashes. Reduce that risk with replication or a write-ahead log on the cache, but do not use write-back for data like payments or orders.

How do you choose a TTL?

Start from the business: how stale may this data be before users or money are affected? Then consider how often the data changes and how expensive a miss is. Choose the longest TTL the business accepts, since longer TTLs raise the hit ratio. Add random jitter so entries do not expire together, and treat the TTL as a safety net even when you also invalidate explicitly.

What is the difference between eviction and expiry?

Expiry removes an entry because its time to live has run out, even if the cache has free space. Eviction removes an entry because the cache is full and needs room, even if the entry is still fresh. Eviction is chosen by a policy such as LRU or LFU.

How does an LRU cache achieve O(1) operations?

By combining a hash map from keys to nodes with a doubly linked list ordered by recency. The map finds an entry in constant time. Because each node links to both neighbors, it can be unlinked and moved to the head in constant time on every access, and the tail node is always the eviction candidate.

What happens to your system if the cache goes down?

With cache-aside, the application falls back to the database and keeps working, but slowly, and the database suddenly takes the full read load. If it cannot handle that, the whole system fails. So you need: redundant cache nodes, rate limiting and load shedding to protect the database (Chapter 16), and capacity planning that considers the no-cache case. The recovery problem is the cold cache (section 10).

When should you not use a cache?

When data is rarely read more than once, when it must always be exactly current (such as balances used for authorization), when the source is already fast enough, or when the added complexity and staleness outweigh the gain. Measure first, and add a cache to fix a measured problem.

Where would you put caches in a typical web system?

In layers: the browser and CDN for static assets and public pages, a small in-process cache for tiny hot reference data, a distributed cache such as Redis for query results and entities, and the database's own buffer pool underneath. Each layer shields the next one.

14. Recap

  • Caching works because access is skewed: a small set of data gets most of the reads. It buys lower latency, higher throughput, and a protected database, and costs you freshness, memory, and extra failure modes.
  • Caches live in layers: browser, CDN, in-process, distributed, and database buffer. Closer to the user is faster but harder to keep fresh.
  • The hit ratio is the key measure. Small improvements near the top cut backend load dramatically, so think in misses.
  • There are five core patterns: cache-aside and read-through for reads, write-through, write-back, and write-around for writes. They combine, and each trades speed, freshness, and loss risk differently.
  • Delete on write instead of updating, and always keep a TTL as a safety net.
  • LRU is the usual eviction policy (hash map plus doubly linked list for O(1)). Eviction (no room) differs from expiry (too old).
  • Invalidation is the hard part. Decide a staleness budget for each kind of data, and use TTL, explicit delete, events, or versioned keys accordingly.
  • Design keys to contain everything that changes the answer, jitter your TTLs, and plan for a cold cache.
