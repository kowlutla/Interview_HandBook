Chapter 53 · Module 7 · Microservices in depth

Operating Microservices

Splitting a system into services is the easy part; running dozens or hundreds of them without drowning is the hard part. This chapter explains how teams keep services independently deployable, how they test and secure them, who owns what, and which organizational and platform practices make the whole thing sustainable.

1. Independent deployability: the core goal

Every benefit that microservices promise comes from one property: a team can change, test, release, and roll back its service without asking anyone else for permission and without coordinating a release with other teams. This is called independent deployability. If you have it, teams move at their own speed, a bug in one release only affects one service, and you can scale the organization by adding teams. If you do not have it, you have paid the full price of a distributed system (network calls, partial failures, many pipelines, hard debugging, as described in Chapter 44) and received almost nothing back. That outcome has a name: a distributed monolith.

A useful test is the "Tuesday question": can team A deploy its service on a Tuesday afternoon, while team B is mid-release and team C is on vacation, and be confident nothing breaks? If the honest answer needs a meeting, a shared release calendar, or a change-approval board that looks at multiple services together, independence has been lost somewhere.

1.1 What breaks independent deployability

Independence is lost in a small number of recurring ways. Knowing them lets you spot them in a design review:

  • Lock-step API changes. Service A changes a response field name and service B, which reads it, must be deployed at the same moment. Any change that requires two services to ship together is a coupling. The cure is backward-compatible changes and the expand and contract technique (section 4).
  • Shared database or shared schema. Two services reading and writing the same tables cannot change those tables independently. Database ownership is covered in Chapter 46; the operational rule is one service owns its data and exposes it only through an API or events.
  • Shared libraries that force upgrades. A common library containing business logic, with a breaking change, forces every consuming service to upgrade and redeploy in the same window. Libraries for cross-cutting technical concerns (logging, tracing) are acceptable; libraries holding domain models are a trap (section 2.4).
  • Synchronous dependency chains. If A calls B calls C calls D for every request, then a slow release of D degrades A. This is runtime coupling, not deployment coupling, but it feels the same to the owner of A. See Chapter 47 and Chapter 51.
  • Shared release trains and shared environments. A single staging environment where everything must be at a compatible version, or a quarterly "integration release", turns many pipelines back into one.
  • Orchestrated end-to-end test gates. If every service must pass a giant shared end-to-end suite before shipping, the slowest and flakiest suite sets the pace for everyone (section 5.2).
  • Hidden ordering requirements. "Deploy the producer, then the consumer, then the migration" written in a wiki page is coupling in disguise. Some ordering is unavoidable and must be made explicit and safe (section 4.3).
  • Tooling and platform coupling. A shared deployment tool that only one central team can configure makes every service wait in a queue behind that team.
Key idea Independent deployability is the success metric of a microservice architecture. Whenever you evaluate a practice in this chapter (a pipeline layout, a test strategy, a shared library, a governance rule), ask: does it preserve or erode the ability of one team to ship alone, safely?

2. CI/CD per service

Continuous integration (CI) means every change is merged into the main branch frequently and automatically built and tested. Continuous delivery (CD) means every change that passes the pipeline is releasable at the push of a button; continuous deployment goes one step further and releases it automatically. With microservices each service gets its own pipeline, so a change to Payments triggers only the Payments pipeline, never the whole company's build.

2.1 Anatomy of a service pipeline

A typical pipeline moves one change through increasingly expensive and increasingly realistic checks. Cheap checks run first so a bad change fails fast:

  1. Build and unit tests. Compile, run fast in-process tests, run linters and static analysis. Target: a few minutes.
  2. Security and quality scans. Dependency vulnerability scan, static application security testing, secret scanning, license checks (section 8.6).
  3. Package. Build one immutable artifact, usually a container image, tagged with the commit hash. The same artifact is promoted through every environment; it is never rebuilt per environment. Environment differences are supplied as configuration at runtime (Chapter 49).
  4. Component and contract tests. Start the service with its dependencies replaced by fakes and verify its behavior and its contracts (section 5).
  5. Deploy to a pre-production environment and run a few smoke tests against the real deployment.
  6. Progressive production rollout. Canary or blue/green with automated analysis and automatic rollback (Chapter 43).
  7. Post-deploy verification. Synthetic checks and SLO burn-rate watchers confirm the release is healthy; the pipeline only finishes when they stay green.

2.2 Monorepo versus polyrepo

Where the source code lives shapes the pipeline. In a polyrepo every service has its own repository; in a monorepo many or all services live in one repository (Google, Meta and many others do this, with serious tooling). Microservices work with either. The deployment independence comes from separate pipelines and artifacts, not from separate repositories.

A monorepo is only fine for independent deployability if the pipeline understands boundaries: it must build and deploy only the services whose code or dependencies changed (using a build graph tool such as Bazel, Nx, or Pants, or simple path filters), and teams must not import each other's internals. Without that discipline a monorepo becomes a monolith with extra steps. Polyrepos suit organizations with strong team boundaries and mixed languages; monorepos suit organizations that value atomic cross-cutting changes and can invest in tooling.

2.3 Build caching and speed

Pipeline speed directly limits how often teams can deploy, which is one of the DORA metrics (section 15). Practices that keep builds fast:

  • Dependency and layer caching. Cache downloaded packages and container image layers. Order a Dockerfile so rarely changing layers (base image, dependencies) come before frequently changing ones (your code).
  • Remote build caches. Build systems that hash inputs can reuse the output of an identical earlier build, even from another developer or another CI machine, so unchanged modules are never rebuilt.
  • Affected-only builds. Compute which modules a diff touches and test only those and their dependents.
  • Test parallelism and splitting. Shard the test suite over runners; run slow suites after fast ones.
  • Hermetic, reproducible builds. Pin dependencies and base images so the same commit produces the same artifact. This makes caching safe and rollbacks trustworthy.

2.4 Shared libraries, templates and golden paths

Dozens of services all need the same plumbing: logging format, metrics, tracing headers, health endpoints, authentication middleware, retries and timeouts, graceful shutdown. If each team writes it, you get inconsistency and wasted effort. If one giant shared library carries it all, you get lock-step upgrades. Teams resolve this with layers:

  • Platform pipeline templates. A reusable pipeline definition that every service includes: build, scan, sign, deploy, canary analysis. A team customizes only the variable parts. Security and compliance checks improve once, centrally, and reach everyone on the next run.
  • Service templates (scaffolding). A generator creates a new repository with the standard skeleton, the pipeline, dashboards, alerts, and a Dockerfile already wired. A new service starts at "production-grade" in minutes.
  • Thin shared libraries for purely technical, stable concerns, versioned semantically, with a policy that services may lag by a version or two without breaking anything.
  • Sidecars and meshes move some cross-cutting concerns (mTLS, retries, telemetry) out of code entirely, so no library upgrade is needed (Chapter 50).

The combination of these is called a golden path (or paved road): the supported, easiest, well-documented way to build and run a service. Teams are free to leave the path but then carry the extra work and the support burden themselves. The path wins because it is genuinely less effort, not because it is mandated.

Watch out Never put domain models or business rules in a shared library used by many services. A change to a shared "Customer" class forces every service to rebuild and redeploy in sync, which recreates the distributed monolith. A little duplication of simple data structures is cheaper than that coupling. Share contracts (schemas) and technical plumbing, not business logic.

3. Versioning services and APIs

3.1 What gets versioned

Three different things carry versions and people often mix them up. The build version identifies a specific deployed artifact (a commit hash or semantic version of the container image); it is what you roll back. The API version identifies a contract shape that consumers depend on (for example /v1/payments or a protobuf package version). The event or schema version identifies the shape of messages on a broker. A service can ship hundreds of build versions without ever changing its API version, and that is the healthy case: the API version should change rarely, because each new one is a promise to consumers that must be supported for months or years.

3.2 Evolving without versioning: backward compatibility first

The cheapest way to evolve an API is to never need a new version. A change is backward compatible if existing consumers, unmodified, keep working. In practice that means:

  • Adding new optional fields, new endpoints, or new enum-free values is safe, provided consumers ignore fields they do not know (the "tolerant reader" rule: be strict in what you send, liberal in what you accept).
  • Removing or renaming a field, changing its type or meaning, making an optional field required, or tightening validation is breaking.
  • Adding a value to an enum that consumers switch on can break them; document that consumers must handle unknown values.
  • Binary formats such as protobuf and Avro have explicit rules (never reuse a field number, add fields with defaults) covered in Chapter 7 and Chapter 47.

3.3 When you must break: versioning strategies

When a genuinely incompatible change is needed, publish a new version alongside the old one. Common styles are URL versioning (/v2/orders), header or media-type versioning (Accept: application/vnd.shop.v2+json), and, for gRPC, a new package or service name. URL versioning is the most visible and easiest to route, cache, and debug; header versioning keeps URLs stable but hides the version from casual inspection. Whichever you choose, the API gateway (Chapter 11) can route by version to different backends.

Running several versions at once has real cost: every old version is code you still test, secure, and operate. The usual approach is for the new version to be a thin adapter over the same core logic, so only the translation layer is duplicated. Set an explicit support policy (for example, "a version is supported for 12 months after its successor ships"), measure which consumers still call the old version using traffic metrics keyed by client identity, and contact them before switching it off (section 12).

3.4 Versioning shared code

Libraries use semantic versioning (MAJOR.MINOR.PATCH): patch for fixes, minor for compatible additions, major for breaking changes. Consumers pin versions so builds are reproducible, and an automated dependency bot proposes upgrades as pull requests. The bot is what keeps hundreds of services from drifting onto ancient versions, and it is also how a security fix in a shared library rolls out within days instead of quarters.

4. Backward-compatible rollouts and dependency-ordered deploys

Even with compatible changes, deployment is not instantaneous. During a rolling or canary rollout (Chapter 43) old and new versions of a service run side by side for minutes or hours, and a consumer may call either. Every change must therefore be safe in both directions: new code must work with old data and old callers, and old code must survive new data written by the new version if you roll back.

4.1 Expand and contract (parallel change)

The standard technique for a breaking change in tiny safe steps is expand and contract. Imagine renaming the field amount to amount_minor in the Payments API:

  1. Expand. The provider starts returning both fields and accepting both on input. Nothing breaks, because old consumers still use amount. Deploy and verify.
  2. Migrate. Each consumer team switches to amount_minor at its own pace. The provider tracks which clients still read the old field.
  3. Contract. Once metrics show no remaining use of amount (and the support window has passed), the provider stops sending it. This final deploy is safe because nobody depends on it.

The same pattern applies to database schemas inside one service: add the new column, write both, backfill, switch reads, stop writing the old column, drop it in a later release. Each step is a separate deploy that can be rolled back alone.

4.2 Rollback safety

A release is only truly independent if you can undo it. Rollback is easy for stateless code and difficult when the new version has already written data in a new format. Two rules help. First, make writes forward compatible: the new version writes data that the previous version can still read (for example by only adding optional fields). Second, separate deploy from release using feature flags: ship the code dark, then turn the feature on gradually, then turn it off in seconds if it misbehaves, without redeploying. Flags themselves need cleanup discipline or they pile up as hidden configuration states.

4.3 Dependency-ordered deploys

Some ordering is unavoidable. The rule of thumb is: deploy providers before consumers when adding capability, and consumers before providers when removing it. Adding an optional field: ship the provider first so the data exists when consumers start asking. Removing one: update every consumer to stop using it first, then remove it from the provider. Messaging systems add a twist (Chapter 47): upgrade consumers to understand a new event version before producers begin emitting it, because messages already in the broker will be read by whichever consumer version is running.

Rather than hand-maintaining ordering lists, make the order enforced and visible. Contract tests in the pipeline (section 5.3) fail a provider build that would break a known consumer, and a "can I deploy?" check queries the contract broker to confirm the version about to ship is compatible with what is currently in production. This converts tribal knowledge into an automated gate that is cheap and local to one service.

5. Testing strategy for microservices

A monolith can be tested mostly in one process. A set of services cannot: correctness depends on the interaction between independently changing parts, and the way to verify that without a giant fragile suite is the central testing question of this chapter. The aims are fast feedback, confidence per service, and early detection of integration breakage, all without making teams wait on each other.

5.1 The pyramid, adapted

The classic test pyramid says: many fast unit tests at the bottom, fewer slower integration tests in the middle, very few end-to-end tests at the top. For microservices the layers are refined:

  • Unit tests. Test one class or function in memory with no network or database. They are very fast (milliseconds) and cover business rules, edge cases, and algorithms. The largest in number.
  • Integration tests (service-internal). Test your code against one real infrastructure piece: your repository class against a real database in a container, your producer against a real broker. They check the seams you own, such as SQL, serialization, and configuration.
  • Component tests. Start the whole service as a black box, replace every other service it calls with a stub or fake, and exercise it through its public API. This verifies the service end to end in isolation, quickly and deterministically.
  • Contract tests. Check that the interface between a consumer and a provider matches what each side expects, without running both together (section 5.3).
  • End-to-end (E2E) tests. Drive the full system through a real entry point (UI or public API) with real services. Keep these few, covering only the handful of critical user journeys, such as "sign up, add to cart, pay".

Many teams find that a pure pyramid underweights the middle, because in microservices most bugs live in integration and contracts, not in pure logic. A testing honeycomb (popularized by Spotify) puts the emphasis on integration and component tests, with fewer unit tests of trivial glue code and very few E2E tests. The principle is the same: test each thing at the cheapest layer that can catch the bug.

5.2 Why end-to-end suites become brittle

Teams often respond to distributed-system anxiety by writing a large E2E suite that runs against a shared staging environment. This almost always degrades over time, for structural reasons:

  • Many moving parts, one verdict. A test passes only if every service in the path is up, correctly configured, and compatible. The probability of a spurious failure multiplies with the number of services.
  • Slow and non-deterministic. Real network calls, asynchronous events that complete "eventually", and shared data lead to timing flakiness. Teams add sleeps and retries, which make suites slower and hide real bugs.
  • Unclear ownership. When the suite goes red, whose bug is it? Failures get ignored, then the suite is disabled or tolerated at an 80 percent pass rate, which means it no longer gates anything.
  • It serializes releases. If every service must pass the suite before deploying, teams queue behind each other and against whichever service broke staging. This is the shared-gate coupling from section 1.1.
  • Slow feedback. A thirty-minute or multi-hour suite means a developer learns about a bug long after they have moved on.

The remedy is not "no E2E" but very few of them, restricted to critical journeys, run after deploy (as monitoring) rather than as a gate before it, with each failure routed to an owner. The confidence you used to buy from E2E tests you now buy from contract tests, component tests, and strong production observability.

5.3 Consumer-driven contract tests

A contract test verifies that a provider and a consumer agree on the interface between them without deploying both. In the consumer-driven style (the tool Pact is the best-known example), the consumer writes down what it actually needs from the provider: "when I call GET /payments/42, I expect a 200 with an id string and an amount_minor integer". Running the consumer's tests against a mock generates a contract file. The consumer publishes it to a contract broker. The provider's pipeline then downloads every consumer's contract and replays the requests against the real provider code, checking the responses. If a provider change would break any consumer's recorded expectation, the provider build fails before it ships.

Why consumer-driven? Because providers otherwise guess which fields matter, and either freeze everything (slow) or break someone (unsafe). With the contracts in hand the provider knows exactly which fields are used and by whom, and can change the unused parts freely. Contracts are also living documentation of who depends on you. They cost effort to maintain and only cover what consumers write down, so they complement, not replace, a few higher-level tests. The ideas are introduced in Chapter 47.

5.4 Test doubles, service virtualization and test data

Component tests need stand-ins for the services they call. The options sit on a spectrum. A stub returns canned answers. A mock additionally verifies that specific calls were made. A fake is a lightweight working implementation (an in-memory payment gateway that approves unless the amount ends in .99). Service virtualization takes this further: a tool records real traffic to a dependency, then replays it as a standalone simulator, including latency and error behavior, which is useful for third-party or legacy systems you cannot run locally and that charge money or have rate limits. The danger of any double is drift: the fake slowly stops matching the real service and tests pass against fiction. Contract tests exist precisely to keep doubles honest, by verifying the same expectations against the real provider.

Test data is the quiet source of most flakiness. Good practice: each test creates its own data through the public API (never relying on rows another test left behind), uses unique identifiers so parallel runs do not collide, and cleans up or uses disposable databases. Shared long-lived test databases rot. Where realistic data volume matters, use synthetic data generators or masked and sampled copies of production data with personal information removed. Never copy raw production personal data into lower environments; that is both a compliance and a security risk (Chapter 55).

5.5 Load and resilience testing

Functional tests say a service is correct; they say nothing about whether it survives. Two further kinds of tests are needed per service and per critical path:

  • Load and capacity testing. Replay realistic traffic at expected peak and at two to three times peak against an environment sized like production. Find the knee of the curve where latency rises sharply, validate that autoscaling reacts in time (Chapter 43), and record capacity per instance so you can do capacity planning from numbers instead of hope. Include soak tests (hours at steady load) to reveal memory leaks and connection exhaustion.
  • Resilience and chaos testing. Deliberately inject failures: kill instances, add latency to a dependency, return errors, partition the network, exhaust a connection pool. Verify that timeouts, retries, circuit breakers, bulkheads and fallbacks behave as designed (Chapter 51). Begin in pre-production with a clear hypothesis ("if Inventory is down, checkout still works with a cached stock value"), then graduate to controlled experiments in production with a small blast radius and an abort switch. Regular game days practice the human side: can the on-call engineer find and fix the injected fault with the dashboards and runbooks that exist?

6. Testing in production and staging fidelity

6.1 Why staging lies

A staging environment is supposed to be a rehearsal for production, but fidelity is chronically poor. It has a fraction of the data volume (so slow queries stay hidden), a fraction of the traffic variety (so rare request shapes never appear), smaller instance counts (so concurrency bugs do not show up), different third-party sandboxes, stale or unrealistic configuration, and often versions of dependencies that do not match production because other teams deploy freely. Keeping staging faithful across dozens of independently deploying services is expensive, and the more services, the worse it gets. A green staging run is weak evidence; a bad assumption here is the root of many "it worked in staging" incidents.

6.2 Testing in production, safely

The mature response is to accept that production is the only real environment and to make testing there safe by limiting exposure and making reversal instant. The key techniques:

  • Progressive delivery. Canary releases send one percent of traffic to the new version, compare error rate and latency against the old version automatically, and expand or roll back (Chapter 43).
  • Feature flags and dark launches. Deploy code switched off, then enable for employees, then a small cohort, then everyone.
  • Shadow traffic (mirroring). Copy real production requests to the new version and discard its responses, comparing them with the old version's answers. This tests correctness and performance on real data with no user impact, but requires care for side effects (the shadow must not charge cards or send emails) and for data written.
  • Synthetic monitoring. Scripted users run critical journeys against production continuously, using clearly labeled test accounts, so a broken path is detected before customers report it.
  • Observability as the test oracle. You can only test in production if you can see what happened: distributed traces, structured logs and per-service SLO dashboards (Chapter 52, Chapter 54).
Interview tip When asked how you would test a system of many services, avoid saying "a big E2E suite". Describe layers: unit and component tests per service, consumer-driven contracts between services, a handful of critical-path E2E checks, and progressive rollout with automated rollback plus observability for production verification.

7. Environments and local development

7.1 Dev, stage, prod, and their limits

The traditional promotion ladder is development (engineers experiment, may be broken), staging or pre-production (a production-like environment for final checks), and production. Some organizations add QA, performance, and regional environments. Each rung should differ from production only in scale and data, never in topology or configuration mechanism; otherwise tests prove nothing. As section 6.1 explained, shared long-lived environments suffer contention ("who broke staging?") and version drift.

7.2 Ephemeral environments

A strong alternative is the ephemeral (preview) environment: for each pull request the platform creates a short-lived, isolated copy of the service, plus the dependencies it needs, runs tests against it, and destroys it on merge. Because it is created from code (container images and infrastructure as code) it is always clean and cannot be corrupted by another team's half-finished work. Dependencies are handled by a mix of strategies: deploy only the changed service and point it at stable shared "baseline" versions of its neighbors; route requests by a header so a request to the preview version flows through shared baseline services except for the one service under test (sometimes called request-level or tenant-level routing); or substitute fakes for distant dependencies. This gives developers production-like checks without a full-system clone per developer, which would be far too costly.

7.3 Local development with many services

Running fifty services on a laptop is not realistic. Teams combine several approaches, and most pick one or two:

  • Run only the service you work on locally and use fakes or the contract-test doubles for its dependencies. Fast and the default recommendation.
  • Compose a small slice using container tooling: the service, its database, a broker, and two neighbors, started with one command.
  • Remote-connect to a shared dev cluster: the local process runs on the laptop but is attached to the cluster network, so it can call real dependencies there and receive routed traffic.
  • Cloud development environments: a full environment in remote machines with the editor connected, avoiding the laptop limit and making setup reproducible.

The sign of a healthy setup is that a new engineer can clone a repository, run one command, and have a working service with realistic dependencies in minutes. If onboarding takes days of wiki instructions, developer productivity and deployment frequency will suffer, and that is a platform team concern (section 13).

8. Security between services

Inside a monolith, a function call is trusted because it is in the same process. In microservices every call crosses a network, and the "trusted internal network" assumption fails: an attacker who compromises one service, or any machine inside the network, can otherwise talk to everything. Broader security design (OAuth, encryption, WAF) lives in Chapter 55; here we cover what is specific to service-to-service traffic.

8.1 Zero trust

Zero trust means no request is trusted merely because of where it comes from. Being inside the cluster or the VPC grants nothing. Every call must prove who is calling (authentication), and the receiver decides whether that caller may do this specific thing (authorization), on every request. Traffic is encrypted in transit even inside the data center. This limits the blast radius of a breach: a stolen foothold in a low-value service cannot freely reach the Payments database.

8.2 Service identity and mutual TLS

Each workload needs a cryptographic identity that is not a shared password. Platforms issue every service instance a short-lived certificate that says "this is the payments service in the production namespace". A common standard is SPIFFE, which defines such identities (a SPIFFE ID) and how workloads obtain them. With mutual TLS (mTLS), both sides of a connection present certificates: the client verifies the server (as in ordinary HTTPS) and the server verifies the client. The result is an encrypted channel where each side knows the peer's service identity, with no application code involved if a mesh sidecar handles it (Chapter 50). Certificates are short lived (hours) and rotated automatically by a certificate authority inside the platform, so a leaked certificate is useful for only a short time and there is no manual renewal outage waiting to happen.

8.3 Propagating end-user identity: authN and authZ

Service identity answers "which service is calling". Often the downstream service also needs to know "for which user", for example to check that the user may refund this particular payment. There are three common ways:

  • JWT forwarding. The gateway validates the user's access token (a signed JSON Web Token) and each service passes it along on downstream calls. Simple, but the token is powerful: every hop can replay it against any service that accepts it, so a compromised mid-tier service can impersonate the user widely. Tokens should be short lived and have a restricted audience claim naming the intended recipient.
  • Token exchange. A service presents the incoming user token to a token service (the OAuth 2.0 token exchange pattern) and receives a new token with a narrower scope and audience for the next hop, for example "may read payment 42, audience: payments". This follows least privilege and lets the chain record the full path of callers (who is acting for whom), at the cost of an extra call that must be cached and made highly available.
  • Internal identity assertion. The edge validates the external token once and then mints a signed internal token or header carrying trusted claims (user id, roles, tenant). Downstream services trust it because they trust the platform, and because it can only arrive via authenticated mTLS channels from services allowed to forward it. This keeps outside token formats away from internal code, but if the trust boundary is weak it becomes a forgery risk.

For background tasks and asynchronous events there is no live user token. Carry a signed record of the original user and permission context, or run the work under the service's own identity with rules that explicitly state what the service may do for whom, and never leave tokens sitting in queues where they will expire or leak.

8.4 Per-service authorization

Authentication at the gateway is not enough. A common mistake is to check permissions only at the edge, so any internal caller is implicitly allowed to do anything. Instead, each service enforces authorization for its own resources, at two levels. First, which services may call which endpoints: Payments accepts calls to /charge only from Orders and Billing, expressed as mesh policy or an allow-list over SPIFFE identities. Second, which end users may access which data: the service checks that this user owns this order, in the business logic that understands the data. Policy engines (for example Open Policy Agent) let policy be written declaratively, versioned like code, and evaluated near the service, which avoids hard-coding rules in dozens of codebases.

8.5 Network policies and secrets

Network-level controls are a second line of defense, not a substitute for identity. Network policies (Kubernetes NetworkPolicy, security groups, or mesh authorization) default to deny: a service may open connections only to the specific services and ports it needs. Databases accept connections only from their owning service. Egress is also restricted, so a compromised pod cannot freely send data to the internet. Segmenting by environment and by sensitivity (the PCI cardholder zone, for example) keeps high-risk services behind tighter rules.

Secrets such as database passwords, API keys and signing keys must never be in source control, container images, or plain environment dumps. A secrets manager (Vault, a cloud KMS and secrets service) stores them encrypted, issues them to a workload based on its identity, supports rotation, and records access in an audit log. Better still are dynamic secrets, where the manager creates a database credential valid for a few hours for each service instance, so there is nothing long lived to steal. Delivery mechanics and configuration are in Chapter 49.

8.6 Supply chain security

A service is mostly other people's code: libraries, base images, build tools. Attackers increasingly compromise those rather than your code. Defenses sit in the pipeline (section 2.1):

  • Dependency scanning for known vulnerabilities, with automated upgrade pull requests, and a policy for how fast critical fixes must ship.
  • Software bill of materials (SBOM): a generated list of every component inside each artifact, so that when a new vulnerability is announced you can query "which services contain this version?" within minutes.
  • Minimal, pinned base images from trusted registries, rebuilt regularly to pick up patches.
  • Signed artifacts and provenance: the pipeline signs each image and records how it was built; the cluster admission controller refuses to run anything unsigned or built outside the official pipeline.
  • Secret scanning and least-privilege pipelines: the build system itself is a high-value target, so give CI jobs narrowly scoped, short-lived credentials.

9. Ownership: you build it, you run it

The operational heart of microservices is a cultural rule: the team that builds a service also runs it in production, including being on call for it. This principle, popularized by Amazon as "you build it, you run it", closes the feedback loop. A team that gets paged at 3 a.m. for its own flaky retry logic fixes the flaw; a team that throws code over a wall to a separate operations group never feels the pain, and operations cannot fix what they did not write. It also removes the handoff delays that destroy independent deployability.

Ownership must be explicit and findable. Every service has exactly one owning team (not an individual, because people leave), with a contact channel and an escalation path. Orphaned services, whose owners reorganized away, are among the most dangerous things in a large estate: nobody patches them, and nobody knows what depends on them.

9.1 The service catalog

A service catalog (a developer portal such as Backstage is a common implementation) is the system of record that answers, for every service: who owns it, what it does, which tier it is, where its repository, dashboards, runbooks and API docs live, what it depends on and what depends on it, on-call rotation, and its current SLO status and production-readiness score. It is generated as far as possible from code (a metadata file checked in beside the service) so that it does not rot. During an incident, the catalog is how a responder finds the owner of an unfamiliar dependency in seconds. For governance, it is how leadership sees the whole estate: how many services exist, which are unowned, which lag on security patches.

9.2 Service tiering and SLOs

Not all services deserve equal investment. Tiering classifies services by business impact and sets the standards each tier must meet:

TierExampleTypical expectations
Tier 0 / criticalPayments, authentication, checkoutHighest availability target, multi-zone or multi-region, 24x7 paging, strict change controls, full game-day testing, formal readiness review
Tier 1 / importantSearch, recommendations, order historyHigh availability, paging during extended hours or 24x7, on-call, tested rollback
Tier 2 / standardInternal reports, notification preferencesBusiness-hours support, tickets rather than pages, lighter review
Tier 3 / best effortExperiments, internal toolsNo paging; may be turned off with notice

Each service defines SLIs (measured indicators such as the fraction of requests that succeed, and latency under a threshold), sets SLOs (the target, for example 99.95 percent of requests succeed over 30 days), and tracks an error budget, the allowed unreliability. When budget remains the team ships features quickly; when it is exhausted, the team slows feature work and invests in reliability. A key tiering rule: a service's availability cannot exceed that of its hard dependencies. A Tier 0 service must not have a synchronous hard dependency on a Tier 3 one without a fallback. The mechanics of SLOs are in Chapter 54, and the per-service signals in Chapter 52.

10. On-call, runbooks, incidents and postmortems

10.1 On-call

On-call means a named engineer is reachable and responsible for responding to production alerts during their shift. Healthy practice: a rotation of at least five or six people so no one is permanently burdened; a primary and a secondary responder; clear handoffs; pages only for conditions that are urgent, user-affecting, and actionable (alert on symptoms such as SLO burn rate, not on every CPU spike); compensation or time off for out-of-hours work; and tracking of pages per shift as a health metric. Persistent noisy alerts are a bug to be fixed, not a fact of life, because alert fatigue makes people ignore the one real page.

10.2 Runbooks

A runbook is a short, tested document attached to an alert that says what the alert means, how to confirm it, the first diagnostic steps (which dashboard, which logs, which trace query), safe mitigations (roll back the last deploy, fail over, shed load, disable a flag, scale out), who to escalate to, and how to verify recovery. The best runbooks are becoming automation: a repeated manual mitigation should turn into a script or a self-healing action. Runbooks decay quickly, so verify them in game days and update them in every postmortem.

10.3 Incident management

For serious incidents, structure beats heroics. Typical roles: an incident commander who coordinates and decides but does not debug; operations responders who investigate and fix; a communications lead who updates stakeholders and the status page on a fixed cadence; and a scribe who keeps the timeline. The commander enforces priorities: first mitigate (stop the customer impact: roll back, fail over, turn off the feature), only then find the root cause. Incidents are graded by severity (for instance SEV1 for a major outage affecting many customers) which determines who is paged and how fast. In a microservice estate the first question is often "which service is the actual source?", answered with traces and dependency maps (Chapter 52); the second is "what changed recently?", answered by a change log and deploy markers on dashboards, since most incidents follow a deploy or a configuration change.

10.4 Blameless postmortems

After an incident the team writes a postmortem (incident review). It is blameless: it assumes people acted reasonably with the information they had and asks how the system allowed a mistake to cause an outage, rather than who made it. A good document contains a timeline, the impact (users, duration, money), the contributing causes (there is rarely a single root cause), what went well, what went badly, and action items with owners and dates, focused on durable fixes such as automation, safer defaults, better alerts and added tests. Reviews are shared widely so other teams learn; without that, the same failure repeats in ten different services. Track the action items to completion, because unfulfilled follow-ups are the most common failure of the process.

11. Production readiness reviews and checklists

A production readiness review (PRR) is a structured check, before a new service takes real traffic (and periodically afterwards), that it meets the operating standard for its tier. Its origin is Google's site reliability practice. The purpose is not bureaucracy but a shared definition of "ready" that catches the things teams forget when excited about a launch. A good PRR is a conversation with a checklist, led by peers or SRE-minded engineers, with automation checking everything that can be checked automatically (the service catalog can show a readiness score from live data). The categories typically include:

  • Ownership and documentation: named team, on-call rotation, escalation path, architecture notes, API documentation, runbooks.
  • Reliability design: timeouts and retries with budgets, circuit breakers, bulkheads, graceful degradation, idempotent operations, no single point of failure, multi-zone deployment, known limits.
  • Observability: structured logs with correlation identifiers, golden-signal metrics (latency, traffic, errors, saturation), distributed tracing, dashboards, SLOs and alerts with runbook links.
  • Deployment: automated pipeline, canary and rollback tested, feature flags, backward-compatible schema changes, infrastructure as code.
  • Capacity and performance: load tested to a multiple of the forecast peak, autoscaling configured, dependencies' capacity confirmed, cost estimate.
  • Security and compliance: mTLS and per-service authorization, secrets in a manager, least privilege, dependency scans clean, data classification and retention, audit logging, threat model for sensitive services.
  • Data: backups taken and a restore actually tested, defined recovery point and time objectives, migration and rollback plan (Chapter 41).
  • Failure and recovery: failure-injection results, a game-day run, a defined disaster recovery plan for its tier.

A worked checklist for a high-stakes service appears in section 16.

12. Deprecating and decommissioning services

Services are cheap to create and expensive to keep. Without a deliberate end-of-life process, estates accumulate zombie services: running, unpatched, unowned, and still receiving a trickle of traffic from someone's forgotten batch job. A disciplined retirement process has these steps:

  1. Decide and announce. State the reason, the replacement, and the timeline in the catalog and in channels consumers watch. Mark the API as deprecated in its documentation and, where possible, in responses (a deprecation header with a sunset date).
  2. Find the consumers. Use traffic metrics keyed by calling service identity (mTLS makes this trivial), gateway logs, contract broker records and static code search. Do not rely on memory.
  3. Migrate them. Support consumers with docs, adapters or even pull requests from the owning team. Track the migration to completion like a project.
  4. Brownout. Briefly and deliberately turn the old service off at scheduled times, which flushes out hidden consumers who ignored the announcements, while remaining quickly reversible.
  5. Scale to zero, then switch off. Keep data and config for a grace period, then remove deployments, DNS entries, alerts, credentials, pipelines and dashboards.
  6. Archive and delete data. Respect retention rules: archive what compliance requires, delete what privacy law requires, and revoke the service's identity so that old credentials stop working.

The final step is easy to forget: remove the service from the catalog, or mark it retired, so the estate list stays truthful.

13. Platform engineering, cost and documentation

13.1 Platform engineering and the internal developer platform

If every team must independently master Kubernetes, pipelines, service meshes, secrets, observability and compliance, the cognitive load is enormous and most of the effort goes into plumbing instead of the product. Platform engineering is the response: a dedicated team builds an internal developer platform (IDP), a set of self-service capabilities that product teams consume. The platform team treats developers as customers and the platform as a product, with roadmaps, documentation, support and adoption metrics. A typical IDP offers:

  • Scaffolding to create a new production-grade service from a template in minutes.
  • Standard CI/CD pipelines and progressive delivery.
  • Runtime: container orchestration, autoscaling, service mesh, ingress, certificates.
  • Self-service provisioning of databases, queues, caches and buckets with safe defaults.
  • Built-in observability: logs, metrics, traces and SLO dashboards wired by default.
  • Secrets, identity and policy enforcement.
  • The service catalog and scorecards.

The danger is a platform team that becomes a gatekeeper or builds what it finds interesting rather than what teams need. Mitigations are to measure adoption and developer satisfaction, keep the paved path optional but better, and have the platform provide capabilities with guardrails instead of tickets with approvals.

13.2 Dependency and cost management (FinOps per service)

Microservices make cost visible in a new way: each service has a runtime bill (compute, storage, network, managed services, observability data) and a human bill (on-call, maintenance). FinOps is the practice of making that cost visible and owned. The elements:

  • Tagging and allocation. Every cloud resource carries the owning service and team tag, so the bill can be split per service. Shared costs (a Kubernetes cluster, a mesh) are allocated by usage, for instance CPU and memory requests.
  • Unit economics. Express cost per business unit: cost per thousand requests, per order, per tenant. A rise in cost per order is a signal even if the total bill is flat because traffic grew.
  • Right-sizing and autoscaling. Services typically request far more CPU and memory than they use. Measure real utilization, lower the requests, scale down off-peak, and use cheaper capacity classes (spot or preemptible instances) for fault-tolerant, stateless work.
  • Hidden multipliers. Cross-zone and cross-region data transfer, verbose logging and high-cardinality metrics, chatty service-to-service calls, and over-provisioned replicas for every environment (including ephemeral ones left running) often cost more than the compute.
  • Showback and chargeback. Showback reports cost to teams; chargeback bills it to their budget. Visibility alone changes behavior.

Dependency management in the cost sense means also tracking the dependency graph: how deep are the call chains, which service is the hub on which everything depends (and therefore the most critical), which dependencies are on third-party vendors with their own cost and risk. The catalog and traces (Chapter 52) feed this view and highlight risky patterns such as a Tier 0 service with a deep synchronous chain.

13.3 Documentation and API portals

Independent teams survive only if they can understand each other's services without meetings. Good practice: every service publishes a machine-readable API description (OpenAPI for HTTP, protobuf definitions for gRPC, AsyncAPI or a schema registry for events); an API portal aggregates them so developers can browse, search, read examples and try calls in a sandbox; docs live in the repository next to the code ("docs as code") and are built and published by the pipeline so they cannot silently diverge; and the catalog links to a short architecture overview, the data it holds, its SLOs, and the contact channel. Generated clients and mock servers derived from the specification reduce the integration effort for consumers further. Treat an API as a product: it has a changelog, a deprecation policy and a support channel.

14. Sprawl, governance and team design

14.1 How many services is too many?

There is no magic number; companies run from a handful to thousands. The better question is whether the operational capacity matches the count. Warning signs of too many services: most services are tiny and change together (a sign of wrong boundaries, see Chapter 45); a single feature needs changes in five repositories; teams spend more time on plumbing, release coordination and cross-service debugging than on features; the same cross-cutting code is copied everywhere; nobody can draw the dependency graph; services outnumber engineers. Common heuristics: a service should be owned by one team, and a team should comfortably own a few services (often two to five) rather than a dozen; services should be big enough to justify their fixed overhead of pipeline, monitoring, on-call and security patching. When overhead exceeds value, merge services. Several well-known companies have publicly consolidated overly fine-grained services back into larger ones, a normal and healthy correction. The decision framework for splitting and merging is in Chapter 44.

14.2 Governance without bottlenecks

Large organizations need consistency in security, reliability, data handling and APIs, but a central architecture review board that approves every change makes the whole estate slow and drives teams around it. The alternative is governance as code and guardrails:

  • Automate the rules. Policy checks in the pipeline and admission controllers enforce standards (signed images, no privileged containers, required labels, mTLS on, tags present) with immediate feedback instead of review meetings.
  • Make the right way the easy way. Golden paths and templates mean compliance comes by default.
  • Scorecards, not gates, for softer standards: the catalog shows each service's readiness score, and leadership attention goes to the lowest scores.
  • Lightweight decision records. Teams document significant decisions in short architecture decision records, and an advisory group of architects offers guidance and reviews only the few high-risk, hard-to-reverse choices (a new datastore technology, a new cross-domain API).
  • Tight bounds, wide freedom. Standardize interfaces and operational behavior (health checks, telemetry, authentication) rigorously; allow free choice of language and framework within the supported set, or support a small number of paved ones.

14.3 Team topologies and organizational scaling

Architecture and organization shape each other (Conway's Law, Chapter 44). The Team Topologies model gives four team types and three interaction modes that fit microservices well:

  • Stream-aligned teams own a flow of business value end to end (a product area) and own the services within it. Most teams should be this type.
  • Platform teams provide the self-service capabilities of section 13.1 to reduce stream teams' cognitive load.
  • Enabling teams are specialists (security, SRE, testing, data) who temporarily coach stream teams and then move on, instead of doing the work for them.
  • Complicated-subsystem teams own a part that needs deep expertise (a pricing engine, a video codec).

Interaction modes are collaboration (work closely for a time), X-as-a-service (consume with minimal coordination, the target steady state), and facilitating (coach). The guideline of the "two-pizza team" (small enough, about six to ten people, to feed with two pizzas) and cognitive-load limits imply that a team can only own so much; as the product grows you add teams and split domains along business capabilities, keeping each team's service set small enough to hold in mind. An organization of fifty engineers and one with five thousand need different mechanisms: the former can rely on informal communication; the latter needs the catalog, platform, scorecards and clear domain boundaries so that coordination cost grows far more slowly than headcount.

15. Measuring delivery: DORA metrics

The research program called DORA (DevOps Research and Assessment) found four metrics that together predict software delivery performance and organizational outcomes. They are the right scoreboard for whether microservices are paying off:

MetricWhat it measuresHealthy direction and how microservices help or hurt
Deployment frequencyHow often a team ships to productionHigher is better. Independent pipelines should raise it. If it stays low, independence is missing.
Lead time for changesTime from commit to running in productionShorter is better. Slow shared test gates or release trains lengthen it.
Change failure rateShare of deployments that cause a failure needing remediationLower is better. Contract tests, canaries and small changes lower it.
Time to restore serviceHow quickly a failure is recovered fromShorter is better. Fast rollback, good observability, runbooks and clear ownership help; deep dependency chains hurt.

Newer versions of the research add reliability (meeting SLOs) as a further dimension. Use the metrics to compare a team with its own past and to find bottlenecks, never to rank or reward individuals, which invites gaming (splitting changes artificially, or hiding failures). The speed metrics and the stability metrics move together in high performers: going faster in small safe steps is what makes systems more stable, not less. A rough pattern in elite teams is on-demand deploys, several per day, lead times under a day, low single-digit failure rates and recovery in under an hour.

16. Worked example: production readiness for a new Payments service

A team is launching a new Payments service that authorizes and captures card charges for the Orders service by calling an external payment provider. It is Tier 0: a failure loses revenue and can double-charge customers. Expected load is 300 charges per second at peak, with a target of 99.95 percent success (about 22 minutes of error budget per 30 days; 0.05 percent of 43,200 minutes is 21.6 minutes). 18. Interview Q&A

What does independent deployability mean, and how would you check a system really has it?

It means a team can build, test, release and roll back its service without coordinating a release with any other team. To check it, ask whether services share a database, whether any change requires two services to ship at the same moment, whether a shared staging environment or end-to-end gate controls every release, and whether a shared library with business logic forces simultaneous upgrades. Measuring helps as well: if deployment frequency per service is low and lead times are long, coupling exists somewhere. A system that fails these checks is a distributed monolith and has the cost of distribution without the benefit.

How do you change an API field that many consumers use without breaking anyone?

Use expand and contract. First the provider adds the new field and keeps the old one, accepting and returning both, so every existing consumer continues to work. Then consumers migrate in their own time, and the provider tracks usage of the old field per client. Only after usage reaches zero, and a published support window has passed, does the provider remove the old field. Each step is an independent deployment that can be reverted, and contract tests in the provider's pipeline catch accidental removal while consumers still depend on it.

Why are end-to-end test suites a poor primary strategy for microservices, and what do you do instead?

An E2E test passes only if every service on the path is healthy and compatible, so spurious failures multiply with service count, they depend on timing and shared data, they are slow, and when red nobody clearly owns the failure. Used as a release gate they also serialize all teams behind one suite. Instead I would put most tests at unit, integration and component level inside each service, use consumer-driven contract tests to protect the interfaces, keep a handful of E2E checks for critical journeys running as post-deploy monitoring, and rely on canary releases and observability to verify behavior in production.

Explain consumer-driven contract testing and what problem it solves.

Each consumer records the exact requests it makes and the response shape it relies on; these are published as contracts to a broker. The provider's pipeline replays every consumer's contract against the real provider code, and a failure blocks the build before a breaking change ships. It solves the problem of knowing who depends on which fields without running all services together in a shared environment. Providers can freely change anything no consumer uses, and a can-i-deploy check confirms compatibility with what is currently in production. Its limit is that it only covers what consumers wrote down, so it complements rather than replaces some higher-level tests.

How should user identity be propagated across service calls, and what are the risks?

The gateway validates the user's token. Downstream, services can forward the same token, exchange it for a narrower one per hop, or receive an internal signed assertion from the edge. Forwarding is simple but dangerous, since any compromised service can replay a powerful token, so tokens must be short lived with a restricted audience. Token exchange gives least privilege and an audit trail of the caller chain, at the cost of another dependency. On top of user identity, mTLS gives each call a verified service identity, and each service enforces its own authorization rather than trusting the edge alone.

What is zero trust in a microservice environment and how is it implemented in practice?

Zero trust means network location grants no privilege; every call is authenticated and authorized. In practice each workload gets a short-lived certificate identity (for example SPIFFE based) from an internal certificate authority, mTLS encrypts and authenticates both ends, allow-list policies say which services may call which endpoints, default-deny network policies restrict connectivity, and secrets come from a manager with rotation and audit. A service mesh can supply much of this without application code. The payoff is that compromising one service does not hand an attacker the whole estate.

How do you decide the right number of services, and what do you do when you have too many?

I judge by operational capacity and boundary quality, not a number. Too many shows up as tiny services that always change together, features spanning many repositories, more time spent on plumbing and cross-service debugging than on product, and services outnumbering the people who can run them. Each service has fixed overhead for pipeline, monitoring, on-call and patching, so it must carry enough value to pay that. When the balance is wrong I merge services along business-domain lines, reduce the number each team owns, and strengthen the platform to lower per-service overhead.

What makes a good postmortem and how do you make sure it improves reliability?

It is blameless, with a factual timeline, impact quantified, multiple contributing causes instead of a single scapegoat, what worked, what did not, and concrete action items with owners and due dates. The value comes from durable fixes such as automation, safer defaults, new alerts and tests, rather than reminders to be careful. I make sure it works by tracking action items to completion, sharing the writeup across teams, updating runbooks, and reviewing recurring themes across incidents so systemic weaknesses become visible.

How do you govern a hundred teams without an architecture review bottleneck?

Turn rules into automation and defaults. Policy checks in the pipeline and admission controllers enforce security and reliability standards immediately; templates and golden paths make the compliant way the easiest way; the service catalog publishes scorecards so lagging services are visible; teams record decisions in lightweight decision records; and a small advisory group reviews only the high-risk, hard-to-reverse choices. This preserves consistency where it matters (interfaces, security, telemetry) while leaving teams free to move without waiting for a committee.

Which metrics would you use to know whether your microservice adoption is working?

The four DORA metrics: deployment frequency, lead time for changes, change failure rate and time to restore service, ideally per service and team, plus SLO attainment. If microservices are working, deployment frequency rises and lead time falls without a rise in failure rate. I would add operational health measures such as pages per on-call shift, share of services with an owner and a passing readiness score, and cost per business unit. These are for finding bottlenecks and not for ranking people, which would encourage gaming.

How would you test and roll out a risky change to the Payments service?

Cover logic with unit and component tests, verify contracts with Orders and Billing through the broker, and run chaos and load tests including provider failure at several times peak traffic. In production, deploy the change behind a feature flag, mirror traffic to the new version in shadow mode and compare results without side effects, then canary at one percent with automated comparison of error rate and latency against the old version, expanding in stages and rolling back automatically on regression. Expand and contract keeps schema and API changes reversible, and idempotency keys protect customers from duplicate charges during retries.

19. Recap and connections

Recap

  • Independent deployability is the point of microservices; shared databases, shared libraries with business logic, lock-step API changes and shared test gates destroy it and produce a distributed monolith.
  • Give every service its own pipeline producing one immutable, signed artifact; use templates and golden paths for shared plumbing; choose monorepo or polyrepo, but build only what changed.
  • Evolve APIs by backward-compatible changes and expand and contract; run multiple versions only with an explicit support policy; deploy providers before consumers when adding, consumers first when removing.
  • Test at the cheapest layer: unit, integration and component tests per service, consumer-driven contracts between services, very few E2E checks; add load and chaos testing and accept that production is the real test environment, made safe by canaries, flags, shadowing and observability.
  • Use ephemeral environments and thin local setups rather than one fragile shared staging.
  • Secure service traffic with zero trust: workload identity, mTLS, token exchange or narrow tokens, per-service authorization, default-deny networks, managed secrets and a protected supply chain.
  • Run what you build: explicit ownership, a service catalog, tiers and SLOs, sensible on-call, tested runbooks, structured incident response, blameless postmortems and production readiness reviews.
  • Manage the estate: FinOps per service, an internal developer platform, API portals, orderly decommissioning, resisting sprawl, governance by guardrails, team topologies, and DORA metrics as the scoreboard.
