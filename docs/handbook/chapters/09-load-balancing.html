Chapter 9 · Module 2 · Scaling the Stateless Tier

Load Balancers

A load balancer spreads incoming traffic over many identical servers, hides failed servers from users, and gives you one stable address in front of a changing fleet. This chapter explains how it works at layer 4 and layer 7, which algorithm to choose, how health checks really behave, how the balancer itself avoids becoming the weak point, and what goes wrong in production.

1. Why load balancers exist

Imagine a web service that runs on one server. That server can handle, say, 2,000 requests per second. When traffic grows to 5,000, you have two choices. You can buy a bigger machine (vertical scaling), which gets expensive quickly and always has a ceiling. Or you can run several copies of the same server and share the traffic between them (horizontal scaling). Horizontal scaling is the standard answer for the stateless tier, meaning servers that keep no important data of their own between requests (they read and write shared stores such as databases and caches instead).

Horizontal scaling immediately raises a question: if you have ten servers, which one does a client talk to? You could give clients a list of all ten addresses, but then every client needs to know the list, pick a server, notice when one is dead, and update when you add a server. That logic would be copied into every browser and phone app, and you could never change it. The load balancer (LB) solves this by being one stable address in front of the fleet. Clients talk only to the LB. The LB decides which server gets each request.

A load balancer gives you at least five things at once:

  • Capacity: total throughput is roughly the sum of all servers behind it. Need more? Add servers.
  • Availability: if a server crashes, the LB notices and stops sending it traffic. Users see no error (or at worst a few failed requests during detection).
  • Easy deployment: you can take servers out of rotation one at a time, upgrade them, and put them back (a rolling deploy) without downtime.
  • Abstraction: clients do not know how many servers exist or where they are. You can add, remove, or replace servers freely.
  • A central place for cross-cutting work: terminating TLS, compressing, rate limiting, logging, and collecting metrics can all happen at the LB so each server does not repeat them.
Key idea A load balancer is not just a traffic splitter. It is the component that turns a pile of unreliable machines into one reliable service. Everything in this chapter is about doing that well: choosing a server fairly, detecting bad servers quickly, and not becoming a bad component yourself.

A load balancer works best with stateless servers. If a server holds data that only it has (for example a user's login session in its own memory), requests from that user must always return to it, which fights the whole idea. Section 8 returns to this. The related topic of how to keep servers stateless is part of the scaling story in the surrounding chapters; DNS-based distribution is covered in Chapter 4.

2. Layer 4 versus layer 7

The internet is described in layers. For load balancing only two matter. Layer 4 is the transport layer: TCP and UDP, where a connection is identified by source address, source port, destination address, and destination port (the "4-tuple"). Layer 7 is the application layer: HTTP, gRPC, and similar protocols, where there are URLs, headers, cookies, and request bodies. Load balancers come in both flavors, and the difference decides what the LB can do.

2.1 What a layer 4 load balancer sees

A layer 4 LB looks only at the packet headers. When a client opens a TCP connection to the LB's address, the LB picks a backend using the 4-tuple (and its algorithm) and then forwards every packet of that connection to that backend. It does not read the bytes inside. It cannot tell whether the connection carries HTTP, a database protocol, or encrypted traffic; it does not know the URL or any cookie.

Because it does so little, a layer 4 LB is very fast and cheap. It can handle millions of connections per second on modest hardware, adds microseconds of delay, and works for any protocol: HTTP, MySQL, MQTT, game traffic, DNS over UDP. There are two common ways to forward packets. With NAT mode the LB rewrites the destination address to the backend and rewrites the replies on the way back, so all traffic passes through the LB in both directions. With direct server return (DSR) the LB only handles the incoming packets; the backend sends its reply straight to the client, bypassing the LB. DSR is attractive because replies are usually much larger than requests (think of a video or a large page), so the LB only carries a small fraction of the bytes. The cost is more complicated network setup: each backend must be configured to accept packets addressed to the LB's address.

2.2 What a layer 7 load balancer sees

A layer 7 LB terminates the client's connection, fully reads the HTTP request, and then opens (or reuses) a separate connection to a backend and sends a request on it. Because it understands HTTP, it can make decisions from the content:

  • Route /api/* to the API fleet and /images/* to the media fleet (path-based routing), or route by the Host header so one LB serves many domains.
  • Route by header, cookie, or query parameter, for example to send 5% of traffic to a canary version, or to keep a user on a given backend using a cookie.
  • Rewrite URLs, add headers (such as X-Forwarded-For carrying the real client address), compress responses, and enforce rate limits.
  • Retry a failed request on another backend, because it holds the whole request and can replay it.
  • Spread the individual requests of one long-lived HTTP/2 or gRPC connection over many backends, which a layer 4 LB cannot do (see section 6.3).
  • Record rich metrics: per-route latency, status codes, error rates.

The price is CPU and latency. Parsing HTTP, holding buffers, and (usually) doing TLS costs far more than forwarding packets. A layer 7 LB handles perhaps tens to hundreds of thousands of requests per second per machine, rather than millions of connections. It also needs to understand the protocol: a layer 7 HTTP LB cannot balance an arbitrary binary protocol.

3. Hardware, software, and cloud load balancers

The same job is done by three kinds of products.

3.1 Hardware appliances

Vendors such as F5 and Citrix sell dedicated boxes with special network chips. They offer very high throughput per box, vendor support, and rich built-in features, and were the default in enterprise data centers for years. Downsides: they are expensive, have fixed capacity (you buy for peak and pairs for redundancy), need specialist skills, and do not fit well with automated, elastic infrastructure. Today they remain in traditional data centers; most new designs use software or cloud balancers.

3.2 Software load balancers

  • HAProxy: a very fast, mature, open source LB for TCP and HTTP. Known for fine-grained configuration, detailed health checks, and stick tables for affinity and rate limiting. A common choice when you run your own LB tier.
  • Nginx: a web server and reverse proxy that is often used as an LB. Strong at HTTP, static content, and TLS. The open source edition has simpler health checking (mostly passive), while the commercial edition adds active checks and more.
  • Envoy: a modern proxy designed for service-to-service traffic. It is configured dynamically through APIs, supports HTTP/2 and gRPC well, and has rich observability, retries, circuit breaking, and outlier detection. It is the data plane of many service meshes (section 11).
  • Linux IPVS, and kernel- or eBPF-based balancers: layer 4 balancing in the kernel for very high packet rates. Several large companies built their own layer 4 balancers in this style (Google's Maglev, Facebook's Katran are public examples).

Software LBs run on ordinary servers or containers, are cheap, scriptable, and can be scaled by adding machines. You operate them yourself, though: patching, capacity, and their own high availability (section 9).

3.3 Cloud load balancers

Cloud providers offer balancers as managed services. You do not run machines; the provider scales and replaces them. You pay per hour plus per unit of traffic.

  • AWS Application Load Balancer (ALB): layer 7 for HTTP/HTTPS and gRPC, with host and path rules, redirect, authentication integration, and target groups for instances, containers, or Lambda.
  • AWS Network Load Balancer (NLB): layer 4 for TCP/UDP/TLS, very high throughput and low latency, supports static IP addresses per availability zone, and preserves the client source address.
  • AWS Gateway Load Balancer: a layer 3-style balancer for inserting fleets of network appliances such as firewalls.
  • Google Cloud Load Balancing: offers both proxy-based (layer 7 global external, regional) and passthrough (layer 4) options. The global external HTTP(S) balancer uses a single anycast IP address that serves traffic from the Google edge worldwide, which makes multi-region setups simple.
  • Azure has analogous products (Application Gateway for layer 7, Load Balancer for layer 4, Front Door for global).

Managed balancers hide the hard parts (HA, scaling, patching) but come with limits: you cannot tune every setting, they are scaled by the provider in steps (so a sudden huge spike may need a "pre-warm" request in some cases), and cost grows with traffic. They are the default recommendation in a cloud-based interview answer: "an ALB in front of an autoscaling group, in multiple availability zones".

4. Balancing algorithms

Once the LB has a pool of healthy backends, it needs a rule for choosing one. The rule is the algorithm. No algorithm is best everywhere: the right choice depends on whether requests are similar or very different in cost, whether servers are identical, and whether you need requests from the same key to go to the same place.

4.1 Round robin

Go through the servers in order: 1, 2, 3, 1, 2, 3, and so on. It is simple, needs no state beyond a counter, and gives each server an equal share of requests. It assumes that every request costs about the same and every server is equally powerful. When some requests are heavy and some light, one server can by bad luck receive several heavy ones in a row and fall behind, while the algorithm keeps feeding it because it only counts turns, not load.

4.2 Weighted round robin

Give each server a weight that reflects its capacity. A server with weight 3 gets three turns for every one turn of a server with weight 1. Use this when the fleet is heterogeneous: a mix of large and small instances, or while shifting a small percentage of traffic to a canary (weight 1 versus 99). Implementations interleave the turns smoothly so a weight-3 server does not get three requests in a burst.

4.3 Least connections

Send the request to the server that currently has the fewest open (active) connections or in-flight requests. This reacts to reality: a server stuck on slow requests accumulates connections and automatically receives fewer new ones. It is the best simple choice when request durations vary widely, or for long-lived connections such as WebSockets. The LB must track the count per server, and if several LBs run side by side each sees only its own connections, which is a good approximation but not exact. A weighted version divides the active count by the weight.

4.4 Least response time

Prefer the server that has recently answered fastest, often combining measured latency with active connections (some products use an exponentially weighted moving average of response time times active requests). It naturally steers traffic away from a server that is slow because of a noisy neighbor, garbage collection, or a cold cache. The risk: a server that fails fast (returns errors immediately) looks wonderfully quick and attracts even more traffic. Combine it with error tracking or outlier ejection.

4.5 Power of two choices

Choosing the globally least-loaded server needs a view of every server, which is costly with many backends and many LBs, and it has a subtle flaw: if all LBs see the same "emptiest" server at the same moment, they all pile onto it (the herd effect). The power of two random choices trick: pick two servers at random, then send the request to the one with fewer active requests. A well-known result in probability shows this gives load that is almost as even as full least-connections, and dramatically better than a purely random choice, with a tiny amount of work and no herd. Envoy and several other proxies offer this as "least request" with two choices. It is an excellent answer to the question "how do you balance across hundreds of backends with many independent LBs?".

4.6 Source IP hash

Compute a hash of the client's IP address and map it onto a server, for example hash(ip) mod N. The same client always reaches the same server, as long as the server list does not change. It needs no cookie and works at layer 4. Problems: when N changes (a server is added or dies), the modulo changes and most clients move to a different server, losing any state or cache on the old one. Also, many users behind one corporate network or mobile carrier gateway share one IP address, so one backend can get a disproportionate load.

4.7 Consistent hashing

Consistent hashing fixes the "most keys move" problem. Imagine a circle (a hash ring) with positions from 0 to 232. Place each server on the ring at one or more points (several points per server, called virtual nodes, make the spread smoother). To route a key (a user ID, a URL, a session ID), hash it to a point on the ring and walk clockwise to the first server. When a server is added or removed, only the keys between it and its neighbor move; with N servers, roughly 1/N of the keys change owner instead of nearly all of them. Use it when the backend holds a cache or partition that is valuable for a given key: a cache fleet, or a sharded service, so that the same key keeps hitting the same warm server. A variant, bounded-load consistent hashing, caps how much extra load any one server takes, so a hot key cannot overload its owner. Chapter 25 discusses the technique in depth for sharded data, and Chapter 14 covers hot keys.

4.8 Random

Pick any server uniformly at random. It is stateless, needs no coordination between several LBs, and is surprisingly decent for large numbers of similar requests. With few requests the spread is lumpy (some servers get noticeably more), which is why two random choices (4.5) are better. It is mostly useful as the building block of 4.5 or in client-side balancing (section 11).

5. Health checks and removing bad servers

An LB that sends traffic to a dead server is worse than no LB, so it must know which servers are healthy. There are two complementary approaches.

5.1 Active health checks

The LB itself probes every backend on a schedule, for example every 5 seconds. A probe can be a bare TCP connect (is the port open?), or an HTTP request to a path such as /healthz that must return status 200 within a timeout. TCP checks only prove the process listens; an HTTP check can verify the application is actually working, and a good health endpoint also checks things the server cannot work without (can it reach its database or cache?). Be careful here: if the endpoint fails whenever a shared dependency such as the database is slow, then every server fails at once and the LB removes the whole fleet, turning a partial problem into a total outage. Most teams make the health check test only the local process and fixed essentials, and use separate monitoring for shared dependencies. Many LBs also keep a "panic mode": if too many backends are unhealthy (Envoy's default threshold is around half), the LB ignores health status and spreads load over all of them, on the theory that sending traffic anywhere is better than nowhere.

5.2 Passive health checks

The LB also watches real traffic. If a backend returns connection errors, timeouts, or a run of 5xx responses, the LB marks it bad for a while, with no probe needed. Envoy calls this outlier detection: eject a host after, say, five consecutive 5xx responses, for a base time that grows each time the host is ejected again. Passive checks react to real user-facing failures in a fraction of a second, whereas an active check might need many seconds to notice. Their weakness is that a user request has to fail first, so they are used together with active checks and with retries (the retried request hides the failure from the user).

5.3 Thresholds

One failed probe should not eject a server (a single packet can be lost), and one success should not instantly re-admit a server that is still starting. So LBs use counts: for example unhealthy threshold 3 (three consecutive failures to remove) and healthy threshold 2 (two consecutive successes to restore). With a 5 second interval and an unhealthy threshold of 3, a crash is detected in about 10 to 15 seconds. During that time, a share of requests (one over the number of servers) goes to a dead server. Shorter intervals and lower thresholds detect faster but cause flapping: a server that is merely slow under load fails a probe, is removed, its traffic shifts to the others, it recovers, comes back, and the cycle repeats. Section 13 shows how that makes outages worse. Choose a check timeout comfortably above normal latency and a healthy threshold above the unhealthy one so that a server must prove itself before returning.

5.4 Slow start

A freshly started server is cold: its caches are empty, its JIT compiler has not optimized hot code, and connection pools are unopened. If least-connections suddenly sees a new server with zero connections, it floods the newcomer with traffic, and the cold server may time out and be ejected again. Slow start ramps the server's effective weight from a small value to full over a window such as 30 to 60 seconds. HAProxy, Nginx Plus, Envoy, and ALB (through its slow start setting) offer it. It is especially important after a deploy and for autoscaling.

5.5 Connection draining

When you intentionally remove a server (a deploy, a scale-in, a maintenance), you do not want to cut requests that are in flight. Connection draining (also called deregistration delay) tells the LB to stop sending new requests to the server while letting existing requests finish, up to a timeout (commonly 30 to 300 seconds). Only after that is the server stopped. The sequence in a rolling deploy is: mark draining, wait for in-flight work to finish, stop the process, start the new version, wait for health checks to pass, slow start. Skipping drain is why some deploys cause a burst of 502 errors. Long-lived connections (WebSocket) need either a longer drain or a protocol-level "please reconnect" message.

6. Connection reuse, keep-alive, and HTTP/2

6.1 Why connections are expensive

Opening a connection costs a TCP handshake (one round trip), a TLS handshake (one or two more), and then a slow ramp-up as TCP discovers how fast it can send. Closing connections after every request wastes all of that. Keep-alive keeps a connection open so many requests reuse it. This is covered in Chapter 3; here we look at what it means for a balancer.

6.2 Two sides, two pools

A layer 7 LB manages two sets of connections. On the front side, thousands of clients each hold a connection (often idle for long stretches, such as mobile apps). On the back side, the LB keeps a pool of persistent connections to each server and multiplexes many client requests over them. This has real benefits. The backends see a few hundred steady connections rather than tens of thousands of short ones, which saves their memory and file descriptors. The LB-to-backend path is inside one data center, so connections are cheap to keep and very fast. And the LB absorbs slow clients: a client on a bad network may take seconds to send a request; the LB buffers it and sends it to the backend in one quick burst, so the backend's worker is busy for milliseconds rather than seconds.

Idle timeouts must be consistent. If the LB's idle timeout on the backend connection is longer than the backend's own keep-alive timeout, the backend will close the connection just as the LB sends a request on it, producing sporadic 502 errors that are hard to reproduce. The rule: the backend's keep-alive timeout should be longer than the LB's idle timeout. The same applies to the client side (LB idle timeout versus the client's expectation, for example 60 seconds on ALB by default).

6.3 HTTP/2, gRPC, and why layer 4 balancing fails them

HTTP/2 and gRPC multiplex many requests over one long-lived connection. A client opens a single connection to a server and sends thousands of requests down it. A layer 4 LB balances connections, so it assigns that one connection to one backend, and every request on it goes there, even if you have twenty backends. The result is badly uneven load: new backends added during a scale-up receive nothing, because existing connections never move. The fixes are to use a layer 7 LB that understands HTTP/2 and balances each request or stream across backends, or to use client-side balancing (section 11). Long connections also need a maximum lifetime (the server sends a "go away" so the client reconnects), which lets load rebalance over time.

7. TLS termination versus passthrough

Most traffic is encrypted with TLS. The LB can handle it in three ways.

  • TLS termination: the LB holds the certificate and private key, decrypts incoming traffic, and sends plain HTTP to the backends over the private network. The LB can then read the request (required for layer 7 routing), and the backends are freed from cryptographic work and certificate management. Certificates live in one place and are easy to rotate. The downside is that traffic is unencrypted inside your network, which some compliance regimes forbid, and the LB holds sensitive keys.
  • TLS passthrough: the LB forwards the encrypted bytes untouched to the backend, which terminates TLS. The LB works at layer 4, cannot read anything except the SNI hostname that the client sends in clear at the start of the handshake (which can be used for coarse routing), and so cannot do path routing, header changes, or HTTP retries. It gives true end to end encryption, and the private key never sits on the LB.
  • Re-encryption (TLS bridging): terminate at the LB, inspect and route, then open a new TLS connection to the backend. This gives both layer 7 features and encrypted internal traffic, at the cost of encrypting twice. Many security-conscious organizations use this, or use a service mesh (section 11) to provide mutual TLS between all services.

Other points worth knowing. TLS handshakes are the expensive part, so terminating at the LB with session resumption saves server CPU. Modern CPUs make the bulk encryption cheap, so the main cost is handshakes of new connections, not data. The LB should pass the original client IP in X-Forwarded-For (or use the PROXY protocol for layer 4) because backends otherwise see only the LB's address, which breaks logging, geolocation, and per-client rate limits. The proxy layer in general, including forward proxies and caching, is discussed in Chapter 10.

8. Session affinity and why to avoid state

Session affinity (sticky sessions) sends a given client to the same backend for repeated requests. People reach for it when the server stores something per user in memory: a login session, a shopping cart, a half-uploaded file, a WebSocket subscription. There are two common mechanisms.

  • Cookie-based: the layer 7 LB inserts a cookie (for example AWSALB or a name you choose) holding the chosen backend or a hash of it. The browser returns it on each request and the LB routes accordingly. It is precise per browser and not affected by many users sharing an IP address.
  • IP hash: works at layer 4 with no cookie, but is coarse (section 4.6).

Affinity causes real problems. Load becomes uneven because heavy users stick to one server, and the LB can no longer balance them. If the pinned server dies, its users lose their in-memory state (logged out, cart gone). Deploys and scale-ins disrupt pinned users. Autoscaling is less effective, because new servers receive only new sessions while old ones stay busy. The cookie also expires or is dropped, and the user silently moves.

Key idea Prefer stateless servers: keep sessions in a shared store such as Redis (see Chapter 15) or in a signed token (JWT or an encrypted cookie) that the client carries. Then any server can handle any request, the LB can use simple algorithms, and failures cost nothing. Use affinity only where you cannot avoid it, and treat it as an optimization (a warm local cache) rather than a correctness requirement: if the pinned server vanishes, the request must still work, only slower.

Legitimate uses: WebSocket and other long-lived connections (naturally pinned for their lifetime, covered in Chapter 6), servers that cache per-user data where locality raises the hit rate, and systems where state really is partitioned (use consistent hashing on the key). Scaling and statelessness are discussed further in Chapter 8.

9. The load balancer as a single point of failure

We introduced the LB to remove single points of failure from the servers, but it is now the one component every request passes through. If it fails, everything fails. It must therefore be redundant itself. How depends on the kind of LB.

9.1 Active-passive with a floating IP (VRRP)

Run two LBs. Clients know a virtual IP address (VIP). Normally LB A owns the VIP and handles all traffic, and LB B is on standby. The two exchange heartbeats using a protocol such as VRRP (Virtual Router Redundancy Protocol, implemented by keepalived on Linux). If B stops hearing A for a few seconds, B takes over the VIP, announcing the new owner to the network (a gratuitous ARP), and traffic now flows to B. Failover takes a few seconds. It is simple and well understood, and for stateful balancers the two can share connection state so existing connections survive. The cost: half your capacity sits idle, and a failover is visible as a brief interruption. There is also a risk of split brain, where a network problem makes both think they are active and both claim the VIP; careful heartbeat design and fencing are needed.

9.2 Active-active with ECMP and anycast

For scale, run many LBs that all work at once. A router in front uses ECMP (equal-cost multi-path routing) to spread incoming traffic over them, hashing each connection's 4-tuple so every packet of a connection reaches the same LB. The balancers can all announce the same VIP by BGP (the same technique CDNs use, see Chapter 12), and if one stops announcing, routers shift its share to the others. This is the model used by large layer 4 balancers: a small group of routers and a pool of balancer machines with no idle capacity. A subtle problem: when an LB is added or removed, ECMP hashing can send an ongoing connection to a different LB that has never seen it. Solutions are consistent hashing in the LB tier so every LB picks the same backend for the same connection, plus connection tracking and state sharing. Cloud providers do all this for you.

9.3 DNS in front

Another tier of redundancy sits above: publish several LB addresses in DNS (or use health-checked DNS), so clients spread across them and a failed LB's address can be withdrawn. DNS has caching delays set by TTL, so it is slow to react and some clients ignore it (see Chapter 4). It is better as a coarse layer than as the main failover mechanism.

Within a cloud, availability zones add another dimension: a managed LB places nodes in each zone, and you should run backends in at least two or three zones so a zone outage leaves capacity. Cross-zone balancing (spreading evenly over all backends, regardless of zone) gives even load but adds cross-zone latency and sometimes data transfer cost; keeping traffic within a zone is cheaper and faster but can be uneven. High availability in general is a chapter of its own: Chapter 41.

10. Global server load balancing and multi-region

One regional LB spreads traffic within a region. Serving the whole world adds a higher level: global server load balancing (GSLB) decides which region or data center should serve each user. The goals are low latency (nearest region), disaster recovery (shift away from a failed region), compliance (keep EU users in EU), and capacity (relieve an overloaded region).

The three main mechanisms:

  • DNS-based: a smart DNS service answers with the address of the best regional LB, based on the resolver's location, health checks of each region, latency measurements, or weights. See GeoDNS and latency-based routing in Chapter 4. Failover speed is limited by DNS caching, so TTLs are short (30 to 60 seconds), and clients and resolvers that ignore TTLs will lag.
  • Anycast: every region announces the same IP; the network sends users to the nearest. Failover is fast because withdrawing the announcement redirects traffic in seconds, and Google's global load balancer works this way. See Chapter 12 for the technique.
  • Application-level redirection and edge steering: a CDN or edge proxy terminates the user's connection nearby and forwards to a chosen region over a private backbone, choosing based on live health and load. The user's first hop is fast, and the edge can retry in another region.

Multi-region adds hard questions beyond routing: the failover region needs spare capacity (a US region that suddenly takes Asia's load needs headroom, or it fails too), data must already be replicated there (the subject of Chapter 26), and sticky data such as sessions must be available everywhere. Practical advice: route users to the nearest healthy region, keep each region able to survive on its own, and rehearse failover regularly because an untested failover usually fails.

11. Internal and external balancers, client-side balancing, and service meshes

11.1 External and internal

An external (internet-facing) LB takes traffic from the public internet and sits in a public subnet, hardened against attack and usually combined with a web application firewall and DDoS protection. An internal LB has only private addresses and balances traffic between your own services (web tier to API tier, API tier to a database proxy). A typical architecture has an external LB at the edge, then an API gateway (Chapter 11) that handles authentication, rate limits, and routing between services, and internal LBs or a mesh between the services behind it. Static content is better served by a CDN (Chapter 12) before it ever reaches an LB.

11.2 Client-side load balancing

With many internal services, putting a central LB between every pair adds a hop, a cost, and another thing to scale. In client-side load balancing the calling service itself holds the list of backends (learned from a service registry such as Consul, Eureka, or Kubernetes endpoints, or from DNS) and chooses one for each call, usually with power of two choices or round robin, and does its own health tracking and retries. It saves a network hop and removes the central bottleneck. The costs: every client language needs a library (gRPC has one built in), each client has only a partial view of load, and upgrading the logic means redeploying clients. Kubernetes shows both styles: a Service of type ClusterIP load-balances at layer 4 using kube-proxy rules, which is poor for long-lived gRPC connections (section 6.3), so people add a proxy or mesh.

11.3 Service mesh

A service mesh (Istio, Linkerd, Consul Connect) moves client-side balancing out of application code into a sidecar proxy (often Envoy) running next to each service instance. All traffic into and out of the service passes through the sidecar, which performs load balancing, retries with budgets, timeouts, circuit breaking, mutual TLS, and metrics. A central control plane pushes the routing and policy configuration to the sidecars, the data plane. You get uniform behavior across languages and rich traffic control (canary percentages, fault injection) without changing application code. The cost is extra CPU and memory per pod, one or two proxy hops of added latency (typically around a millisecond or less), and real operational complexity. Newer designs run the proxy once per node, or in the kernel, to reduce this.

12. Capacity and scaling of the load balancer

The LB has limits too. Know which limit you will reach first:

  • Throughput (bits per second): a 10 Gbps network card caps a software LB at about 1.25 GB/s of traffic unless it uses DSR so responses bypass it.
  • Connections per second: each new connection costs CPU, particularly with TLS handshakes. Layer 7 LBs reach tens of thousands of new TLS connections per second per core at best, typically less.
  • Concurrent connections: each held connection uses memory and a file descriptor. Millions are possible with tuned software, but the figure depends on buffers and tuning.
  • Requests per second: for layer 7, parsing and routing cost. Tens to hundreds of thousands per second per machine, depending on features.
  • Ephemeral ports: a proxy opening connections to one backend address uses a port for each, and a single source address and destination pair has about 64,000 ports. With many short connections this can run out; keep-alive or more addresses solve it.

To scale: scale up (bigger machines) first because it is easy; then scale out by adding LB nodes behind ECMP or DNS (section 9.2); put a cheap layer 4 tier in front of expensive layer 7 proxies; terminate TLS on dedicated nodes if handshakes dominate; offload static content to a CDN; and keep connections alive to reduce handshakes. Managed LBs scale automatically but not instantly: ALB and similar add capacity within minutes, so a sudden tenfold spike (a flash sale, a push notification) can see errors until it scales. The remedy is to ask the provider to pre-warm, to use NLB (which handles abrupt spikes better), or to smooth the spike with queues and rate limits (Chapter 16). Always watch LB metrics: active connections, new connections per second, 4xx and 5xx counts split between LB-generated and backend-generated, backend response time, healthy host count, and rejected or queued requests.

13. Common failure modes

13.1 Thundering herd on recovery

A backend (or a whole tier) recovers after an outage, and the LB at once sends it its full share. If least-connections is used, a freshly healthy node with zero connections absorbs everything. The cold server is overwhelmed, fails its checks, is ejected, recovers, and the cycle repeats. A related herd happens when many clients that were waiting reconnect simultaneously. Mitigations: slow start (section 5.4), requiring several successful probes, a limit on concurrent connections per backend, client retry with exponential backoff and jitter (Chapter 40), and warming caches before returning to rotation.

13.2 Uneven load

Round robin with variable request cost, a few heavy clients stuck by affinity, hash collisions, one backend on a noisy host, HTTP/2 connections pinned by a layer 4 LB, or fleet changes that leave old long-lived connections on old servers. Diagnose by comparing per-backend request rate, active connections, and latency. Fixes: least connections or power of two choices, layer 7 request-level balancing, maximum connection age, weights for different sizes, and bounded-load hashing.

13.3 Health check flapping

A server hovering near its limit fails a probe, is removed, load shifts to the others, pushing them over their limit, so they fail probes too. The fleet oscillates, or collapses completely. Causes: probe timeout too tight, a health endpoint that does expensive work or competes with real traffic for the same worker pool, too-low thresholds. Fixes: simple dedicated health endpoint on its own thread or port, sensible thresholds with hysteresis, panic mode that stops ejecting when too many are out, and enough headroom (N+1 or N+2 capacity) that losing one server does not overload the rest.

13.4 Retry storms

When a backend slows down, clients and the LB retry. Each retry adds work to an already struggling system, so more requests time out and are retried: load multiplies. If each of three layers (browser, gateway, service) makes three attempts, one user request can become 27 backend requests. Mitigations: limit retries to one extra attempt, use a retry budget (retries allowed only up to, say, 10% of normal traffic), retry only idempotent requests, use exponential backoff with jitter, add circuit breakers that stop calling a failing backend, and shed load at the edge (Chapter 16). Only retry on failures that are safe: connection refused (nothing was processed) is safe, a timeout after sending a POST is not unless the operation is idempotent.

13.5 Other traps

  • Mismatched idle timeouts cause intermittent 502s (section 6.2).
  • Lost client address when the backend sees only the LB IP; use X-Forwarded-For or the PROXY protocol.
  • Slow clients and request smuggling: an LB and backend that disagree on where one request ends can allow smuggled requests; keep software current and normalize requests.
  • Misconfigured health path that returns 200 from a static page even when the app is broken, or 401 because it requires login.
  • LB as bottleneck without anyone noticing, because its limits are not graphed.
  • Config pushed to all LBs at once: roll out configuration gradually and keep the last good version, since a bad config can take down the front door.

14. Worked example with numbers

Design the front door for an API with a peak of 60,000 requests per second, average response 20 KB, average request 1.5 KB, 80% of requests reusing an existing connection, and servers that each handle 1,500 requests per second at a comfortable 60% CPU.

14.1 Backend fleet size

60,000 ÷ 1,500 = 40 servers at normal load. We want to survive the loss of one availability zone out of three, so after a zone loss the remaining two zones must carry the full peak. Each zone then needs 40 ÷ 2 = 20 servers, and three zones means 60 servers (versus 40 if no zone failure were tolerated). That is 50% extra, the price of surviving a zone loss. With two zones, each would need 40 servers (80 total, 100% extra), so three zones is the cheaper way to get zone-level resilience.

14.2 Bandwidth through the LB

Responses: 60,000 × 20 KB = 1.2 GB/s, which is 9.6 Gbps. Requests: 60,000 × 1.5 KB = 90 MB/s, about 0.72 Gbps. If all traffic passes through the LB (not DSR), it carries about 10.3 Gbps outbound plus inbound. A single 10 Gbps NIC is therefore already over its limit, and we want headroom, so we need at least 3 LB nodes (3 × 10 Gbps = 30 Gbps, running near 35% utilization, enough to lose one node and still have 20 Gbps for 10.3).

14.3 Connection rate and TLS

If 80% of requests reuse a connection, then 20% of requests open a new one: 60,000 × 0.2 = 12,000 new TLS connections per second. If one core can do roughly 2,000 to 4,000 full handshakes per second (a typical order of magnitude, depending on key type), we need 3 to 6 cores for handshakes at peak, trivial for three LB nodes with 8 or more cores each. Encryption of the data stream itself (10 Gbps) costs more CPU than handshakes in this example, which is why nodes with several cores are used. Raising the keep-alive reuse from 80% to 95% would cut new connections to 3,000 per second.

14.4 Health check and failure detection

Active probes every 5 s, unhealthy threshold 3: a hard crash is detected within 15 s at worst. During detection the dead server receives 1/60 of requests, which is 60,000 ÷ 60 = 1,000 requests per second, all failing. With one retry on connection errors (safe because nothing was processed), the users see nearly no errors. Passive outlier detection (eject after 5 consecutive 5xx) would remove it within about 5 failed requests, well under a second at 1,000 per second. The combined design: active checks plus outlier detection plus one retry with a retry budget.

14.5 Choice of algorithm and deployment

Requests vary from a 5 ms read to a 400 ms report, so round robin is risky. We pick least requests with two random choices. Rolling deploys drain for 60 s, and slow start ramps over 45 s. For LB high availability: a managed layer 7 balancer spanning three zones (or three self-run nodes behind ECMP) with the global address in DNS, and static content moved to a CDN, which at 80% of the 1.2 GB/s being static would cut LB bandwidth to about 2 Gbps and let us use fewer LB nodes. Finally, test: kill a server, kill a zone, and run a load test at 1.5 times the peak.

15. Interview questions and answers

What is the difference between a layer 4 and a layer 7 load balancer, and which would you choose?

A layer 4 balancer works on TCP or UDP connections and sees only addresses and ports, so it forwards packets quickly without understanding the content. A layer 7 balancer terminates the connection, reads the HTTP request, and can route by path, host, header, or cookie, retry, and balance individual requests. I choose layer 7 for HTTP services because routing, TLS handling, and retries are valuable, and layer 4 for non-HTTP protocols, extreme connection counts, or as a fast tier in front of layer 7 proxies. In large systems both are stacked.

Round robin versus least connections: when does each fit?

Round robin is fine when requests cost about the same and servers are identical, because equal turns give equal work. When request durations vary a lot, round robin can overload a server that happens to get several slow requests. Least connections tracks in-flight requests and naturally sends less to a server that is behind, so it is better for variable work and long-lived connections like WebSockets. With many independent balancers a pure least-connections choice can cause a herd, so power of two choices is a good compromise.

Explain the power of two choices and why it works.

For each request, pick two backends at random and send the request to the one with fewer active requests. It needs only two lookups instead of a view of the whole fleet, and it avoids every balancer choosing the same emptiest server at once. Probability theory shows the maximum load drops from roughly log n over log log n with one random choice to log log n with two, which is nearly as good as perfect balancing. That makes it attractive for big fleets and for client-side balancing.

How do health checks work, and how do you avoid flapping?

Active checks probe each backend periodically (TCP connect or an HTTP path with a timeout); passive checks watch real responses and eject a host after consecutive errors. Thresholds require several consecutive failures to remove a host and several successes to restore it, so one lost packet does not matter. To avoid flapping, keep the health endpoint cheap and independent of shared dependencies, set timeouts above normal latency, use hysteresis (healthy threshold above unhealthy), add slow start, and keep enough spare capacity that removing one server does not overload the rest. A panic mode that ignores health when too many hosts fail prevents a total self-inflicted outage.

Why should you avoid sticky sessions, and what do you do instead?

Sticky sessions pin a user to one server, which makes load uneven, loses state when that server dies, and complicates deploys and autoscaling. The better design is stateless servers with session data in a shared store like Redis or in a signed token the client holds, so any server can handle any request. When affinity is unavoidable (WebSockets, local caches), treat it as an optimization and make sure the system still works correctly, only slower, if the user lands elsewhere. Cookie-based affinity is more accurate than IP hash because many users share an IP address.

The load balancer is a single point of failure. How do you fix that?

Run several balancers. The simple way is an active-passive pair sharing a virtual IP using VRRP, so the standby takes the address within seconds when heartbeats stop. For more scale, run active-active nodes behind routers using ECMP, or announce the same address from all of them using anycast, so a failure removes only a fraction of capacity. Cloud managed balancers already do this across zones. DNS can also list multiple balancer addresses, but its caching makes it slow, so it is a coarse outer layer. You also need to avoid split brain in active-passive designs.

TLS termination at the LB versus passthrough: what are the tradeoffs?

Termination lets the LB read requests for layer 7 routing, centralizes certificates, and offloads cryptographic work from servers, but traffic inside is unencrypted unless re-encrypted and the LB holds private keys. Passthrough keeps encryption end to end and keys off the LB, but the LB only sees addresses and the SNI name, so it cannot route by path or retry HTTP. Many designs terminate and then re-encrypt to the backend, or use mutual TLS through a service mesh, getting both visibility and internal encryption.

Why does gRPC or HTTP/2 traffic often balance badly through a layer 4 load balancer?

HTTP/2 multiplexes many requests over a single long connection, and a layer 4 balancer assigns each connection, not each request, to a backend. A client with one connection sends all its traffic to one server, and newly added servers get nothing because existing connections never move. The fix is a layer 7 balancer that understands HTTP/2 and distributes streams, client-side balancing where the client holds several connections, and a maximum connection age so connections are periodically re-established.

How would you do global load balancing across regions, and what are the catches?

Use health-checked, latency- or geography-based DNS, or anycast, or edge proxies to direct each user to the nearest healthy region, with regional balancers inside. Failover by DNS is limited by TTL and clients that ignore it; anycast fails over faster. The real catches are capacity (the surviving region must absorb the extra load), data (it must already be replicated, see the multi-region chapter), and testing, since an unrehearsed failover often fails. Also consider data residency rules that restrict where certain users can be served.

What is a retry storm, and how does the load balancer layer contribute to it?

When a backend slows, each layer retries failed or timed out requests, and because retries multiply across layers (three attempts at each of three layers gives 27), the load on an already struggling service can grow far beyond normal and prevent recovery. The balancer contributes if it retries aggressively. I limit retries to one attempt, use a retry budget tied to a fraction of normal traffic, retry only idempotent or clearly safe failures, use backoff with jitter, add circuit breakers, and shed load at the edge so the system degrades instead of collapsing.

When would you use consistent hashing in a load balancer instead of round robin?

When the backend keeps valuable state per key, such as a cache or a shard, so that sending the same key to the same server raises the hit rate or is required for correctness. Plain hash modulo N reshuffles nearly every key when the server count changes, which would cool every cache at once. Consistent hashing moves only about one over N of the keys. A hot key can overload its owner, so bounded-load consistent hashing or replicating hot keys across several servers is a common refinement.

16. Recap

  • A load balancer provides one stable address over many servers, giving capacity, availability, easy deploys, and a central place for TLS and observability.
  • Layer 4 forwards connections quickly without reading content; layer 7 reads requests and routes, retries, and balances per request. Large systems often stack both.
  • Choose algorithms by workload: round robin for uniform work, least connections or power of two choices for variable work, consistent hashing when locality by key matters, weights for mixed hardware.
  • Health checks combine active probes and passive outlier detection with thresholds, slow start, and connection draining so servers enter and leave rotation safely.
  • Prefer stateless servers over sticky sessions; keep keep-alive timeouts consistent; use layer 7 or client-side balancing for HTTP/2 and gRPC.
  • Terminate TLS at the LB for visibility, pass it through for end-to-end secrecy, or re-encrypt for both.
  • The LB must itself be redundant: VRRP pairs, ECMP or anycast pools, managed multi-zone services, and DNS or global tiers above.
  • Know the failure modes: thundering herds, uneven load, flapping health checks, and retry storms, and the limits (bandwidth, connections, handshakes, ports) that cap an LB.
