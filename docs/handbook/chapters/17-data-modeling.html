Chapter 17 · Module 3 · The Data Layer

Data Modeling

Data modeling is the act of deciding what your tables or collections look like, which fields they hold, and how they point at each other. In an interview it is the step that turns vague requirements into a design you can actually build. This chapter teaches you to model from the questions you must answer, to normalize and denormalize on purpose, to choose keys, timestamps, deletes and statuses well, to shape data for sharding and NoSQL, and to walk through three complete worked models.

1. Why data modeling comes first

Every system design eventually reduces to data: what is stored, how it is found, and how it changes. Code can be rewritten in a sprint, but a data model, once millions of rows exist and many services read them, is the hardest thing to change. A wrong index can be dropped. A wrong service boundary can be refactored. A wrong primary key or a wrong way of splitting data across shards can take a quarter of migration work, so it deserves care early.

A data model has three layers, and it helps to name them because interviewers sometimes jump between them:

  • Conceptual model: the real-world things and how they relate. "A customer places orders. An order contains products." There are no types, no keys, no database yet. This is what you draw on a whiteboard in the first minutes.
  • Logical model: the conceptual model made precise: entities become tables or collections, each with named attributes, primary keys and relationships. It is still independent of any specific product.
  • Physical model: the logical model adapted to one database engine: column types, indexes, partition keys, how rows are laid out on disk, which columns are compressed. This is where Postgres, DynamoDB and Cassandra differ.

A frequent beginner mistake is to start from the objects ("I have users, posts, comments, so I need a users table, a posts table, a comments table") and never ask how the data will be read. That produces a model that looks tidy but may need five joins to render one screen. The central rule of this chapter is the opposite: start from the questions the system must answer and model so those questions are cheap.

Key idea A good data model is not the one that most faithfully mirrors the real world. It is the one that makes your most frequent and most latency-sensitive reads and writes simple, while keeping the data correct. The workload decides the model.

2. Model from access patterns

An access pattern is one concrete question or update the application performs, written with its inputs, its output, how often it runs and how fast it must be. Writing them down before any schema is the single most useful habit in data modeling. It works for relational databases and is mandatory for NoSQL stores, where the schema is shaped by the queries.

2.1 The procedure

  1. List the entities in plain nouns from the requirements: customer, product, order, payment.
  2. List the access patterns as sentences, each with inputs and outputs: "Given a customer id, return their 20 most recent orders with status and total." Include writes: "Place an order that decrements stock for each line item atomically."
  3. Attach numbers: reads per second, writes per second, latency target, how large the result is, how stale it may be. A pattern run 10 times a day by an admin is different from one run 20,000 times a second by a mobile app.
  4. Draft the schema that serves the hottest patterns directly (one primary-key lookup or one index range scan).
  5. Check every pattern against the draft: for each, name the table and the index it uses. A pattern with no index is a full scan, and you must either add an index, change the model, or consciously accept it for a rare admin report.
  6. Check the writes: how many places must change for one logical update, and is that set inside one transaction or one shard?

2.2 Example list for an e-commerce system

#Access patternRateNeeds
A1Get a product by id (product page)5,000 per secondPrimary key lookup, cacheable
A2List a customer's recent orders, newest first, 20 at a time500 per secondIndex on (customer, created time)
A3Get one order with all its line items300 per secondOrder key plus children by order key
A4Place an order, reducing stock for every line atomically100 per second peakTransaction across order, items, stock
A5Move an order through statuses (paid, shipped, delivered)200 per secondSingle-row update with a check of the current status

Notice how patterns differ in kind. A1 to A5 are OLTP (online transaction processing) patterns: small, keyed and latency sensitive. A6 is an analytic pattern that scans a lot of data and tolerates minutes. Mixing them in one schema is a classic mistake: you denormalize the transactional tables for the report and slow every checkout. The usual answer is to model the OLTP store for A1 to A5 and feed the analytic need from a copy, such as a warehouse fed by change data capture.

Interview tip Say the access patterns out loud before drawing a schema. "These are the queries I must serve, with these rates. Let me model so each is one lookup." It shows the interviewer you design from the workload, and it gives you a checklist to validate against at the end.

3. Entities, relationships and ER basics

An entity is a thing you store facts about; it becomes a table (or collection). An attribute is a fact about it; it becomes a column (or field). A relationship says how entities connect, and its cardinality says how many of one connect to how many of the other.

3.1 Cardinality

  • One-to-one (1:1): a user has exactly one profile settings record. Often these are simply merged into one table, unless you split them for a reason (rarely read large columns, or PII isolation as in section 14).
  • One-to-many (1:N): a customer has many orders, but each order belongs to one customer. Modeled with a foreign key on the "many" side: the order row stores customer_id.
  • Many-to-many (M:N): an order has many products, and a product appears in many orders. Relational databases cannot store this with one column, so you introduce a junction table (also called a join, link or associative table) with one row per pairing. For orders and products that table is order_items, and it naturally carries facts about the pairing: quantity and the price at the time.

An ER diagram (entity-relationship diagram) draws entities as boxes and relationships as lines labeled with cardinality. The common notation, crow's foot, shows "many" as a three-pronged end. Every interview whiteboard model is an ER diagram in disguise, so be fluent in reading one.

3.2 Keys and constraints

A primary key uniquely identifies a row and is what other tables point at. A foreign key is a column that holds another table's primary key, and a foreign-key constraint makes the database reject an order whose customer does not exist. A unique constraint enforces natural uniqueness such as one account per email. A check constraint enforces a rule such as quantity > 0. Constraints are free correctness: one line in the schema replaces bugs in every service that writes the table. Two caveats matter at scale. Foreign keys cannot be enforced across shards or across databases, so sharded systems enforce them in application code or by routing related rows to the same shard. And some very high-write systems drop foreign keys deliberately to avoid lock overhead, trading integrity checks for speed; say so explicitly if you do.

4. Normalization and denormalization

4.1 What normalization is for

Normalization is organizing tables so each fact is stored in exactly one place. The reason is to avoid three anomalies. Imagine one wide table orders_flat where every row repeats the customer's name and address, one row per order line:

  • Update anomaly: the customer moves. You must update the address in every one of their thousands of rows, and if one update is missed, the data contradicts itself.
  • Insert anomaly: you cannot record a new product that nobody has ordered yet, because a row needs an order to exist.
  • Delete anomaly: deleting the only order for a product also deletes the only record of that product's name and price.

The normal forms are a ladder of rules that remove these problems step by step.

4.2 The normal forms in plain language

  • First normal form (1NF): every column holds one atomic value, and there are no repeating groups. A column phones = "555-1,555-2" or columns item1, item2, item3 violate it. The fix is a child table with one row per phone or per item.
  • Second normal form (2NF): in 1NF, and every non-key column depends on the whole primary key, not just a part of it. This matters when the key has several columns. In order_items(order_id, product_id, quantity, product_name) the key is the pair, but product_name depends only on product_id. Move it to the products table.
  • Third normal form (3NF): in 2NF, and non-key columns depend only on the key, not on other non-key columns. In orders(order_id, customer_id, customer_city, customer_zip), the city depends on the customer, not on the order. A memorable phrase: every non-key attribute depends on "the key, the whole key, and nothing but the key."

Beyond 3NF there is Boyce-Codd normal form (a stricter version of 3NF) and fourth and fifth forms for multi-valued dependencies. Interviews almost never go past 3NF; stating that 3NF is the practical target for transactional data is enough.

4.3 The price of normalization: joins

A fully normalized model spreads one screen of data over many tables, and a read must join them. On one machine with indexes, joins are fast and usually fine. The problem arrives with scale. A join that touches data on two different shards becomes a network scatter-gather. A join of a large table to another during a peak read workload burns CPU and latency. So at scale you denormalize: deliberately duplicate data so a read touches fewer tables.

4.4 When to denormalize

  • Read-heavy workloads. If a page is read 1,000 times for each write, paying a little extra at write time to precompute the read shape is a good trade.
  • Joins that cross shards. If orders are sharded by customer and products by product id, the join is a network operation. Copying the product name and price into the order item avoids it.
  • Document and wide-column stores that have no join at all. There, denormalization is the normal way to model, not an optimization.
  • Derived data such as counters and aggregates (section 15).

Denormalization has a cost you must name: every copy must be kept correct. Choices are to update all copies in the same transaction (needs one shard or one database), to update copies asynchronously from an event or change stream (the copies are briefly stale, so eventually consistent), or to accept that the copy is a historical record that is not supposed to change.

Watch out "Denormalize for speed" without a measured problem is premature. Start normalized in a relational database, add indexes, add a cache (Chapter 13), and denormalize only the specific hot reads that are still too slow. In NoSQL you start denormalized because you must.

4.5 Snapshots are not duplication

Some copied data is not redundancy but history. When a customer buys a product at 19.99, the order item must record 19.99 forever, even if the product price later rises to 24.99. If order_items only pointed at the product's current price, last year's invoices would silently change. The same applies to the shipping address on an order and the tax rate applied. These snapshot columns are correct by design, and they are the reason a pure 3NF order model is actually wrong. Mention this: it shows you model for business meaning, not just for form.

5. Embedding versus referencing in document stores

A document store (MongoDB, Couchbase, Firestore; see Chapter 20) stores records as nested JSON-like documents. Where a relational design has a child table, a document design chooses between two shapes:

  • Embedding: the child data lives inside the parent document, such as order items as an array in the order document.
  • Referencing: the child is its own document, and the parent stores its id (like a foreign key). Reading both takes two queries or an application-side join.

5.1 How to choose

SituationPreferReason
Child is always read with the parent and has bounded size (order items, an address)EmbedOne read, one atomic write, data that changes together stays together.
Children are unbounded (comments on a post, events for a device)ReferenceAn ever-growing array hits the document size cap and makes each update expensive.
Child is queried on its own (find all reviews by a user)ReferenceQuerying inside arrays of many parents is awkward or slow.
Child is shared by many parents and changes (a product referenced by many orders)Reference, plus snapshot of values that must stay historicalEmbedding copies must all be updated when it changes.
Parent-child must update atomicallyEmbedSingle-document updates are atomic in virtually every document store; multi-document transactions are costlier.

A good rule of thumb: embed what you read together and what is bounded; reference what is unbounded, shared or independently accessed. A hybrid is common: embed the most recent five comments inside the post for the fast first view, and keep the full list in a separate collection. This is the "subset pattern": duplicate only the part the hot read needs.

6. Modeling one-to-many and many-to-many

6.1 One-to-many

In SQL the foreign key lives on the many side, and you add an index on that foreign key, because "list all orders of customer X" is otherwise a full scan. This is a very common omission: a foreign key constraint does not automatically create the index in most databases, and the unindexed join column makes both lookups and deletes of the parent slow. In a key-value or wide-column store, the "many" rows share the parent's partition key and are ordered by a sort key (section 12), so the one-to-many is a single range read.

6.2 Many-to-many

Use a junction table whose primary key is the pair of foreign keys, and add the reverse index if you query from both directions. Examples: user_roles(user_id, role_id), post_tags(post_id, tag_id), or a follow graph follows(follower_id, followee_id). Whenever the pairing itself has facts (quantity, role granted on, start date), those columns belong on the junction row, and that is a sign the junction is really its own entity (an enrollment between students and courses).

A many-to-many in a document store is usually stored as arrays of ids on one side or both, with the caveat that arrays of ids must be bounded. For a heavily skewed relation (a celebrity with 50 million followers) the array is impossible, and you use a separate edge collection, as in the follow-graph example below.

6.3 Self-referencing and hierarchical data

A tree such as an org chart or comment thread references itself with parent_id. The adjacency list (just parent_id) is simple and writes are cheap, but "give me the entire subtree" needs a recursive query. Alternatives: a materialized path column such as /1/7/19/ that makes subtree queries a prefix match; a closure table storing every ancestor-descendant pair; or nested sets. Choose by the read pattern: if you mostly read direct children (threaded comments loaded one level at a time), the adjacency list is enough.

7. Identifiers: surrogate versus natural, and ordering

The primary key choice has outsized consequences. There are two families:

  • Natural key: a real-world value that is already unique, like an email address, a phone number, a country code or a government id. Appealing because it needs no extra column, but real-world values change (people change emails), may be reused (phone numbers are recycled), may not be as unique as believed, and may be sensitive (leaking an email in every URL and foreign key). Natural keys also tend to be long, which bloats every index that includes them.
  • Surrogate key: an identifier invented by your system with no business meaning: an auto-increment integer, a UUID, or a time-sortable id. It never changes, and it is small and uniform. This is the default choice for entities that matter. You still put a unique constraint on the natural attribute (email) so duplicates are rejected, and you keep the surrogate as the key others point to.

7.1 Which surrogate

OptionStrengthsProblems
Auto-increment integerSmall (4 or 8 bytes), ordered, inserts append at the end of the index so they are cache friendlyOne node must hand out numbers, which is a bottleneck and a coordination point across shards; guessable, so it leaks volume and invites enumeration attacks
Random UUID (version 4)Generated anywhere without coordination, unguessable16 bytes; random values scatter inserts all over a B-tree index, causing page splits and poor cache locality on big tables
Time-ordered id (Snowflake, ULID, UUID version 7)Generated anywhere, roughly sorted by creation time, so inserts stay near the end of the index and "newest first" queries are range scansLeaks creation time; needs a clock and, for Snowflake, a worker-id assignment

The internals of these generators, clock-skew risks and bit layouts are covered in Chapter 32. For modeling, remember three rules. First, if you shard, avoid ids that depend on a single counter. Second, if the table is large and written constantly, prefer ids that are roughly time ordered so index writes are localized (Chapter 19 explains why random inserts hurt B-trees). Third, never expose an internal sequential id in a public URL when enumeration matters; use an opaque public id, or a time-ordered id that is not guessable by incrementing.

7.2 Composite keys and idempotency

A composite key combines columns, such as (order_id, line_no). It is natural for child rows and for wide-column sorted storage. Separately, a client-supplied idempotency key stored with a unique constraint lets a retried "place order" request be recognized and not create two orders; this is a modeling feature (a unique column) as much as a protocol one, and Chapter 32 covers the full pattern.

8. Timestamps and time zones

Time bugs are among the most common data bugs. A few firm rules prevent most of them:

  • Store instants in UTC. An instant is a precise point on the global timeline ("the order was created at this moment"). Store it as a UTC timestamp (or as epoch milliseconds, a 64-bit integer of milliseconds since 1970-01-01 UTC). Convert to the user's zone only at display. Never store a local time string without a zone.
  • Store the user's zone separately when it matters. A recurring event "every Monday 9:00 in Berlin" is not an instant. It is a wall-clock rule: store local time (09:00), a zone identifier such as Europe/Berlin (an IANA name, not an offset like +01:00, because the offset changes with daylight saving time), and a recurrence rule. Converting this to UTC once and repeating every 7 days breaks twice a year at the daylight saving switch.
  • Use the right granularity. A birthday or a billing date is a calendar date, not a timestamp; storing it as midnight UTC makes it the wrong day in some zones.
  • Keep two timestamps when meaning differs. created_at (when the row was inserted) differs from event_time (when the thing actually happened on a device that may have been offline) and from processed_at. Analytics and late-arriving data need the event time.
  • Do not trust client clocks for ordering or for security decisions. Use server time, or a logical order such as a per-conversation sequence number.
  • Money and time are alike: store money as integer minor units (cents) plus a currency code, never floating point, and store amounts with the currency of the transaction.

Ordering rows by timestamp has a hidden problem: two rows can share the same millisecond. Pagination by created_at alone can skip or repeat rows at a boundary, so break ties with the id: order by (created_at, id) and use the last row's pair as the cursor.

9. Soft delete, hard delete and tombstones

A hard delete removes the row. A soft delete keeps the row and marks it, usually with a deleted_at timestamp (null means live) or an is_deleted flag. Which to use depends on needs:

ConcernSoft deleteHard delete
Undo or restoreEasyNeeds a backup
Audit and legal recordsPreserves historyLoses it unless logged elsewhere
Privacy erasure (right to be forgotten)Does not satisfy it by itself; personal data must still be removed or anonymizedSatisfies it
Query complexityEvery query must remember WHERE deleted_at IS NULL; forgetting leaks deleted dataQueries are plain

Table size and index bloatGrows forever unless purged by a jobStays compact

A practical pattern: soft delete for a retention window (say 30 days) so users and support can restore, then a scheduled purge job hard deletes and also removes the personal data in backups on their own retention cycle. Mitigate the "forgot the filter" risk with a database view or an ORM default scope that applies the filter automatically, and with a partial index on live rows.

9.1 Tombstones in distributed stores

In LSM-tree stores such as Cassandra and HBase (Chapter 19), data files are immutable, so deleting cannot erase a row in place. The database writes a special marker, a tombstone, saying "this key was deleted at time T." Reads must see the tombstone to hide the older value, and compaction eventually removes both once it is safe. Tombstones carry modeling consequences. A queue modeled as a table where you insert and delete rows creates a pile of tombstones that every range scan must read through, which makes scans slow (the "queue as a table" anti-pattern). Tombstones also must outlive the replication repair window: if a tombstone is purged before a lagging replica has learned of the delete, the old value can come back to life ("zombie data"). So design deletes in these stores around TTLs and time-bucketed partitions that you can drop whole, instead of mass deleting individual rows.

10. Audit trails, history tables and temporal data

Many systems must answer "what did this record look like last Tuesday?" or "who changed this and when?" Three common modeling choices:

  1. Audit log table: an append-only table of changes: (entity_type, entity_id, actor, action, before, after, at). Simple, and can live in a separate store. It answers "who did what" but makes "state as of time T" a replay.
  2. History (versioned) table: each update inserts a new version row with a validity interval: valid_from, valid_to, where the current row has valid_to null. "State as of T" is a single query: valid_from <= T AND (valid_to IS NULL OR valid_to > T). This is a temporal table design; some databases offer it built in as system-versioned tables.
  3. Event sourcing: the events are the source of truth, and the current state is derived by folding them. Maximum fidelity, more machinery (Chapter 36).

There are two kinds of time in temporal data and mixing them up causes errors. Valid time is when a fact is true in the real world (the price was 10 from March 1 to April 1). Transaction time is when the database learned it (we recorded that on March 3). A model with both is called bitemporal and is used where corrections to the past must be traceable, such as finance and insurance. Most systems need only one, and you should say which.

Keep audit data append-only and, where regulators care, tamper evident. Move old history to cheaper storage on a retention schedule (section 11), and keep personal data in history subject to the same erasure rules as the main table.

11. TTL and retention

TTL (time to live) is a per-row or per-item expiry time after which the store deletes data automatically. DynamoDB has a TTL attribute, Cassandra has a per-row or per-table TTL, Redis has key expiry, and MongoDB has TTL indexes. TTL suits session tokens, one-time codes, caches, idempotency keys (keep them 24 hours), and recent-activity feeds. Know these points: expiry is usually lazy and background, so an expired row may remain visible for a short while, and your code should still check the expiry when reading if exactness matters. TTL deletes in LSM stores still create tombstones. And TTL is a modeling decision: if you add it later, you must backfill expiry on existing rows.

Retention is the broader policy: how long each class of data is kept, and where. A typical tiering: hot data in the primary database for 90 days, then archived in object storage (Chapter 21) in a columnar format for 7 years for audit, then destroyed. Retention is driven by business need and by law (some data must be kept for years, personal data must not be kept longer than needed). For large append-only tables, time-based partitioning (one partition per day or month) turns retention into a cheap metadata operation: dropping a partition is instant, while deleting millions of rows one by one is slow and bloats the table.

12. Enums, status fields and state machines

Almost every business entity has a lifecycle: an order is created, paid, shipped, delivered, perhaps cancelled or refunded. Modeling this as a status column is easy. Modeling it well means treating it as a state machine: a fixed set of states and a fixed set of allowed transitions between them.

Practical guidance for the data model:

  • Guard transitions in the write itself. Use a conditional update: UPDATE orders SET status='PAID' WHERE order_id=? AND status='CREATED', and treat zero rows changed as "someone else got there first or the move is illegal." This is a compare-and-set that makes concurrent payment callbacks safe without locks. Document stores and DynamoDB offer the same through conditional writes.
  • Store the enum as a small integer or short string, not as a free-text field. Use a database enum or check constraint, or a lookup table, to reject typos. Be aware that adding a value to a native database enum is an easy migration, while removing or reordering one is painful. Never use the enum's ordinal position as the stored value if you may reorder code.
  • Keep the history of transitions in an order_status_history(order_id, from, to, at, actor) table when you need to answer "when was it shipped" or compute time in each state. The status column is the current state; the history is the log.
  • Index for the common filter. "All orders in PAID waiting to ship" is a hot ops query. A low-cardinality column alone is a poor index; use a partial index on the few actionable states, or a composite (status, created_at).
  • Add terminal states and timeouts. A payment pending state needs an expiry so abandoned orders move to a terminal state, or they accumulate forever.

For cross-service long-running workflows, the state machine becomes a saga; see Chapter 48.

13. Polymorphism and JSON columns

13.1 Modeling polymorphic entities

Sometimes one concept has several kinds with different attributes: payments can be card, bank transfer or wallet; notifications can be email, SMS or push; a content feed contains posts, photos and polls. There are four standard relational patterns:

PatternHow it worksGood forCost
Single tableOne table with a type column and the union of all columns, mostly nullFew kinds, mostly shared columns, simple queries across all kindsMany nullable columns; cannot enforce required fields per type without check constraints
Table per type (concrete)A separate table per kind, no shared tableKinds queried separately"All payments" requires a union; foreign keys to "a payment" are awkward
Class table (shared plus extension)A payments table with shared columns, plus card_payments, bank_payments sharing the same idStrict typing per kind plus a unified keyA join to read the full details
Shared columns plus JSONShared columns in the table, kind-specific details in a JSON columnMany kinds, evolving attributesWeaker validation and indexing for the JSON part

A tempting shortcut is the "polymorphic foreign key": columns target_type and target_id that can point to any table. The database cannot enforce it, joins need conditional logic, and orphan rows appear. It is sometimes acceptable for comments or audit entries, but use it knowingly. In a document store polymorphism is trivial: documents in one collection simply have different shapes, with a type field to discriminate.

13.2 JSON columns

Modern relational databases (PostgreSQL jsonb, MySQL JSON) can store a JSON document in a column. This is a useful middle path: keep the entity relational and put the flexible, sparse or externally defined part in JSON. Good uses: per-tenant custom fields, event payloads, provider-specific response blobs, feature flags and preferences. Bad uses: anything you filter, join, sort or enforce uniqueness on regularly, because the engine cannot give it the same statistics, constraints and plans as real columns.

  • You can index inside JSON (a GIN index in PostgreSQL, or an index on an extracted expression), which makes occasional filters acceptable.
  • There is no schema, so the application owns validation and versioning. Store a schema_version inside the document so readers can handle old shapes.
  • Updating one field often rewrites the whole value, so very large documents in hot rows hurt.
  • Promote on use: when a JSON attribute becomes a frequent filter, migrate it into a real column. Treat JSON as the place new attributes start, not where they live forever.

14. Multi-tenant keying and PII separation

14.1 Tenant keys

A multi-tenant system serves many customers (tenants, organizations) from shared infrastructure. The data model must make tenant isolation hard to get wrong. The deployment-level isolation models (shared everything, schema per tenant, database per tenant, cell per group of tenants) are in Chapter 42. For the shared-table model, the data modeling rules are:

  • Put a tenant_id on every tenant-owned table, including child tables, even when it looks redundant because the parent already has it. It lets every query be filtered and every index be tenant-leading, and it lets you move or delete one tenant's data cleanly.
  • Make tenant_id the first column of the primary key and of composite indexes: (tenant_id, order_id). Then a tenant's rows are physically clustered together, one tenant's queries do not scan other tenants, and the same column is a natural shard key (section 16).
  • Enforce uniqueness per tenant: unique (tenant_id, email), not unique email. Foreign keys should include the tenant as well, so a row cannot point at another tenant's parent.
  • Enforce the filter below the application where possible: PostgreSQL row-level security policies, or a data-access layer that cannot issue a query without a tenant. A forgotten WHERE tenant_id = ? is a cross-tenant data leak, the worst class of multi-tenant bug.
  • Plan for the large tenant: one tenant holding 30 percent of the data makes a single shard hot. Allow a big tenant to be assigned its own shard or cell, so keep a tenant-to-location mapping rather than computing placement from a hash alone.

14.2 PII separation

PII (personally identifiable information: names, emails, phone numbers, addresses, government ids, precise locations) carries legal duties such as access, correction and erasure, and it raises the stakes of a breach. The modeling response is to separate PII from behavioral and operational data:

  • Keep identity data in a small, tightly controlled user_profile store, and let other tables (orders, events, logs) refer only to the opaque user_id. Erasing a user then means deleting or anonymizing one record, while historical aggregates remain intact.
  • Encrypt sensitive columns, and consider crypto-shredding: encrypt each user's data with a per-user key, and "delete" the user by destroying the key, which makes every copy, including backups, unreadable.
  • Never put PII in identifiers, partition keys, URLs or logs. An email used as a primary key is copied into every index, foreign key and log line.
  • Choose the storage region by residency rules: EU users' profile data may have to stay in the EU even if the order metadata is global.
  • Mark PII columns in the schema (a naming convention or a data catalog tag), so retention jobs and export tools can find them.

The legal and operational details (consent, DSAR requests, residency) belong to Chapter 56; in this chapter the point is that the shape of the model decides how easy compliance is later.

15. Counters, aggregates and derived data

Features like "like count", "unread messages", "order total", "followers" ask for a number derived from many rows. Two strategies:

  • Computed on read: run SELECT COUNT(*) or SUM(...) when needed. Always exact and no extra storage, but cost grows with the rows counted; counting 10 million likes on every page view is unacceptable.
  • Precomputed: store the number in a column or a separate counter row and update it as events happen. Reads are one lookup, but you must keep the number correct, and counters are a write hotspot: one viral post's counter row receives thousands of increments per second, serialized by the row lock.

Ways to keep precomputed values healthy:

  • Update in the same transaction as the base row (insert like and increment count together). Exact, but the counter row contends.
  • Shard the counter: keep N sub-counters for a hot key (post_17#0 ... post_17#9), increment a random one, and sum them on read. Throughput multiplies by N; reads touch N rows.
  • Batch asynchronously: increments go to a queue or in-memory buffer (a Redis counter, see Chapter 15) and are flushed periodically. Cheap, slightly stale, and the count may be lost in a crash unless it is rebuildable.
  • Reconcile: run a periodic job that recomputes the true count from base rows and corrects drift. Treat a precomputed count as a cache of the truth, never the truth, so there is always a way to repair it.
  • Approximate when exactness is not required: "1.2M views" can be a rounded or sampled number; unique counts can use a probabilistic structure (Chapter 57).

Rule of thumb: money and inventory are exact and transactional; engagement counters are approximate and asynchronous.

16. Schema design for sharding

When data no longer fits one database, it is split across shards (Chapter 25 covers how). The data model decides whether sharding is easy or agonizing, because the shard key determines which queries stay on one shard. Principles:

  • Choose the shard key from your hottest access pattern. If 90 percent of queries are "everything for customer X," shard by customer id so all of a customer's orders, items and addresses land together. Then the common query touches one shard and transactions on a customer are local.
  • Co-locate related rows. Child tables carry the parent's shard key (order_items gets customer_id or tenant_id) so a join of parent and child never leaves the shard.
  • Avoid cross-shard joins and transactions on hot paths. A query by order id alone, when sharded by customer, would have to ask every shard; fix with a global secondary index (a lookup table from order_id to customer_id), by encoding the shard in the order id, or by reading through a lookup service.
  • Choose a key with high cardinality and even spread. Sharding by country puts half the load on two values. Sharding by timestamp sends all current writes to the newest shard. Hashing the key (or a high-cardinality id) evens load but loses range scans.
  • Global uniqueness no longer comes for free: auto-increment per shard collides, so use ids that embed a shard or machine component or come from a generator (Chapter 32). Unique constraints on non-shard-key columns (email) need a separate global index or a dedicated table sharded by that column.
  • Plan for resharding: using many more logical partitions than physical nodes (for example 1,024 logical shards mapped to 8 machines) lets you move whole logical shards later without rewriting every key.

17. Modeling for NoSQL access patterns

Key-value, wide-column and many document stores are modeled query first, and the structure that makes queries fast is the key. The two-part key used by DynamoDB, Cassandra and similar stores is worth knowing exactly (store families are compared in Chapter 20):

  • Partition key: hashed to decide which node holds the data. All items with the same partition key live together. A query must name the partition key (equality only) to be efficient.
  • Sort key (clustering key): orders items within one partition, enabling efficient range reads: "items with this partition key and sort key between A and B," "latest N," "begins with prefix."

17.1 Design rules

  • List queries, then design keys to answer them. Each distinct query that the base key cannot serve needs a secondary index (a second copy of the data keyed differently; its cost is extra writes and eventual consistency in some stores) or a separate denormalized table.
  • Avoid hot partitions. A partition key like date or status funnels all traffic into one partition. Prefer high-cardinality keys, or add a salt/bucket suffix (DATE#2026-11-17#3 with 10 buckets), at the cost of querying all buckets on read.
  • Bound partition size. A partition that grows without limit (all messages ever for one busy chat) becomes huge. Add a time bucket to the key (CHAT#9#2026-11), so each partition holds a bounded slice.
  • Duplicate freely, update carefully. The same fact may appear under several keys. Keep the number of duplicates small and update them from one write path or one stream consumer.
  • No ad hoc queries. If a new question arrives that no key serves, expect to add an index or table and backfill it. That is the real cost of the model's speed, and it is why access patterns must be written first.

18. Schema evolution and migrations (preview)

The model will change: new fields, renamed columns, split tables, changed keys. Because production never stops, changes must be backward compatible in steps. The detailed mechanics (online schema change tools, dual writes, backfills, cutover) are in Chapter 26. A preview of the safe pattern, called expand and contract:

  1. Expand: add the new column or table, nullable or with a default, with no behavior change. Old code ignores it.
  2. Write both: deploy code that writes the old and the new shape.
  3. Backfill: copy existing rows into the new shape in small batches that do not overload the database.
  4. Switch reads to the new shape, watching for differences.
  5. Contract: stop writing the old shape, then later drop the old column.

Design habits that make evolution cheap: add columns rather than repurposing them; never reuse an enum value's meaning; keep a schema_version in JSON and in events; avoid adding a column with a volatile default to a huge table in a way that rewrites it (behavior varies by database and version); and treat primary keys and shard keys as nearly immutable, because changing them means rewriting and moving every row.

19. Worked example 1: e-commerce orders

Requirements and patterns. From section 2: A1 product by id, A2 a customer's recent orders, A3 one order with items, A4 place an order atomically with stock, A5 status transitions, A6 reporting. Assume 2 million orders per day at peak 100 orders per second, 5 line items on average, and 50 million customers.

Choose the store. The order flow needs transactions (stock must not go negative, payment and order must agree) and has a modest write rate, so a relational database is the base. 2 million orders per day is about 730 million per year; at roughly 1 KB per order plus items that is under a terabyte per year, which a sharded relational setup handles.

Schema decisions.

  • order_items carries customer_id so order and items co-locate. Its key is (customer_id, order_id, line_no).
  • Money as integer cents with currency. unit_price and name_snapshot are frozen copies (section 4.5), so changes to the product catalog never rewrite history.
  • The order id is a time-ordered id (Chapter 32), so a customer's orders sort newest first and inserts append. The id contains no PII.
  • A client-supplied idempotency key with a unique constraint on (customer_id, idempotency_key) prevents double orders on retry.
  • Status is a small state machine (section 12) updated with guarded writes, with a status-history table for the timeline shown in the app.
  • Inventory uses a conditional decrement: UPDATE inventory SET stock = stock - ? WHERE product_id = ? AND stock >= ?. Zero rows updated means out of stock.

Queries.

-- A2: recent orders (one shard, index range scan, keyset pagination)
SELECT order_id, status, total_cents, created_at
FROM orders
WHERE customer_id = :c AND (created_at, order_id) < (:last_ts, :last_id)
ORDER BY created_at DESC, order_id DESC
LIMIT 20;

-- A3: one order with items (same shard)
SELECT * FROM order_items WHERE customer_id = :c AND order_id = :o ORDER BY line_no;

-- A5: guarded transition
UPDATE orders SET status = 'PAID'
WHERE customer_id = :c AND order_id = :o AND status = 'CREATED';

Numbers. A2 at 500 per second with 20 rows each, indexed on one shard, is a few milliseconds per query. The checkout write touches roughly 1 order row, 5 item rows, 5 stock rows, and 1 status-history row, about 12 row writes per order, so 100 orders per second is about 1,200 row writes per second, small for a sharded cluster. The global order_lookup index doubles one write and is worthwhile because support tools and webhooks usually know only the order id.

Where the model could be wrong. Sharding by customer makes "all orders for product X" and "all orders today" expensive, so those go to the warehouse (A6). Flash sales concentrate writes on one inventory row; solve by splitting stock into sub-counters (section 15) or by queueing purchases for that product.

20. Worked example 2: social follow graph

Requirements. A user can follow other users. Access patterns: B1 follow or unfollow; B2 "who does user U follow" (to build the home feed), paginated; B3 "who follows U" (to fan out a new post, or display the list); B4 "does A follow B" (checked on every profile view); B5 follower and following counts on every profile. Scale: 500 million users, average 200 follows, with celebrities at 50 million followers. That is about 100 billion edges. At roughly 20 bytes per edge, the raw edge data is 2 TB, large but shardable, and each edge must be stored in both directions to serve B2 and B3.

A follow is a many-to-many relationship, so the table is a junction table of edges. Two directions mean two keyings of the same fact:

Decisions explained.

  • Two edge tables. A single table indexed only by follower cannot list followers without a full scan. A secondary index would give the same effect. Writing both from one follow event is the explicit form.
  • Bucketed follower partitions. A celebrity with 50 million followers in a single partition is a hot, enormous partition. Appending a bucket number (hash of follower id modulo 64) spreads the edges. Reading all followers queries 64 buckets in parallel; for fan-out, workers each take a bucket.
  • Counts are precomputed and not derived by counting 50 million edges. They are updated asynchronously and may lag by seconds; a periodic job recomputes them. For the hottest accounts the counter is itself sharded (section 15).
  • Unfollow deletes both edges. In an LSM store, heavy churn creates tombstones, so use a TTL-aware strategy or accept compaction (section 9.1). If you need "unfollowed at" for analytics, record it in a separate log.
  • Consistency. If the two writes fail halfway, a user could appear in following but not in followers. Make the write idempotent and retry from a durable queue, or write the primary direction synchronously and the reverse asynchronously.

A graph database (Chapter 20) becomes attractive for multi-hop questions such as "friends of friends who also follow X," which are painful on edge tables. For one-hop lookups at this scale, sharded key-value edge tables are the standard answer. Feed generation uses these tables but belongs to the news-feed case study.

21. Worked example 3: chat messages

Requirements. One-to-one and group conversations. Access patterns: C1 send a message (write at very high rate); C2 load the latest 50 messages of a conversation, then older pages on scroll; C3 list a user's conversations ordered by latest activity, with the last message preview and unread count; C4 mark a conversation as read; C5 search is separate and goes to a search engine (Chapter 22). Scale: 50 million daily active users, 40 messages sent per user per day, so 2 billion messages per day, about 23,000 per second on average and perhaps 70,000 at peak. At 300 bytes each that is 600 GB per day, and this enormous, append-heavy, partition-by-conversation workload fits a wide-column or key-value store (Chapter 20) better than a single relational database.

Decisions explained.

  • Partition by conversation. C2 always asks about one conversation, so all its messages sit together in order. The partition key does not use the user, because a group conversation would then be duplicated and out of sync.
  • Time bucket in the key. An active group chat can accumulate millions of messages. Adding the month to the partition key caps partition size. To page backwards across a month boundary, the client or server queries the previous bucket when the current one is exhausted.
  • Message ids are time ordered (Chapter 32), so the sort key gives send order. Because clocks differ, strict ordering inside a conversation may need a per-conversation sequence number assigned by the server that owns the conversation, rather than client timestamps.
  • Inbox table (a materialized view per user) denormalizes the last message preview and unread count so the conversation list is one range read. It costs a write per member per message. For two-person chats that is 2 writes, for a 200-person group, 200 writes, so very large groups use another strategy.
  • Unread counts are derived from last_read_message_id against the latest message id, or stored as a counter in the inbox row. Storing the counter is cheap to read but must be reset on read and can drift, so a reconcile path is needed (section 15).
  • Retention and deletes. A message TTL or a monthly partition drop implements "messages older than 2 years are removed." "Delete for me" is a per-user hidden marker, not a hard delete of a shared row. "Delete for everyone" overwrites the body with a tombstone-like marker so the sequence stays intact.
  • PII. Message bodies are sensitive; encrypt at rest, and for end-to-end encrypted products the server stores only ciphertext and cannot index or search it, which is a modeling constraint that shapes C5.

Numbers. 70,000 writes per second for messages plus an average of three inbox updates each is about 280,000 writes per second, which is why the inbox is the real scaling cost, not the messages. A cluster handling roughly 10,000 writes per second per node needs on the order of 30 nodes before replication; with replication factor 3 the cluster is roughly three times that. These are estimates to make the structure of the argument clear, not product benchmarks.

23. Common mistakes

  • Modeling objects, not queries. A schema that mirrors the domain but cannot serve the hot read without a five-way join or a scan.
  • Over-normalizing a read-heavy path, or over-denormalizing early and then fighting update bugs. Start from the measured workload.
  • Missing indexes on foreign keys and tenant columns. Slow lookups and slow parent deletes.
  • Storing local times and offsets instead of UTC instants plus an IANA zone where needed; storing money as floating point.
  • Natural keys that change (email as a primary key), or sequential ids exposed publicly.
  • Soft delete without a filter strategy, leading to leaks of deleted data and broken unique constraints; or soft delete as the only answer to a privacy erasure request.
  • Unbounded growth: unbounded arrays in documents, partitions without a time bucket, history tables with no retention.
  • Hot keys: a single counter row, a date-valued partition key, a celebrity partition.
  • Status as free text with no transition guard, so concurrent updates produce impossible states.
  • JSON as a dumping ground for attributes later used in filters and joins.
  • Forgetting the tenant id on child tables, or putting PII into keys, URLs and logs.
  • Treating a precomputed counter as the truth with no reconciliation.
  • Choosing a shard key from the data, not the queries, which makes the hottest query scatter across every shard.

24. Interview Q&A

How do you start data modeling in an interview?

I begin by listing the entities from the requirements and then, before drawing tables, writing the access patterns: each query or update with its inputs, expected rate and latency. Then I draft the schema so the hottest patterns are a single key lookup or index range scan, and I verify each pattern against it at the end. This makes the design driven by the workload and gives me a checklist to prove coverage. It also reveals early whether a relational store is adequate or whether the write rate and shape point toward a key-value or wide-column store.

When would you denormalize, and what do you do about the consistency problem?

I denormalize when a read path is hot and measurably too slow because of joins, when joins would cross shards, or when the store has no joins at all. The consistency problem is that duplicated values must be kept in sync. I handle it in one of three ways: update all copies in one transaction when they share a shard, update them asynchronously from a change stream and accept brief staleness, or make the copy a deliberate snapshot that should never change, like the price on an order line. I also keep a source of truth and a repair job so drift can be fixed.

Explain 1NF, 2NF and 3NF briefly and say which you target.

First normal form requires atomic values and no repeating groups. Second normal form removes attributes that depend on only part of a composite key. Third normal form removes attributes that depend on other non-key attributes, so every column depends on the key, the whole key and nothing but the key. For transactional data I target 3NF, because it prevents update, insert and delete anomalies, then I relax it deliberately for hot reads and for historical snapshots.

Embed or reference in a document database?

I embed when the child is read with the parent, is bounded in size and should update atomically with it, such as order lines or an address. I reference when children are unbounded, shared across parents, or queried independently, such as comments on a viral post or products referenced by many orders. A hybrid is common: embed a small subset, like the latest few comments, for the fast path and keep the complete list in its own collection. The guard rails are the document size limit and the cost of rewriting a growing document.

Surrogate or natural primary key, and which kind of surrogate?

I use surrogate keys for important entities because natural values like email or phone change, can be reused and may be sensitive. I still put a unique constraint on the natural attribute. For the surrogate, auto-increment integers are compact but need central coordination and are guessable. Random UUIDs need no coordination but scatter writes in a B-tree index. Time-ordered ids such as Snowflake, ULID or UUID version 7 give coordination-free generation and mostly sequential inserts, so they are my default for large sharded tables, with the caveat that they reveal creation time.

How do you model time correctly?

I store instants as UTC timestamps and convert to local time at display. For recurring or future wall-clock events I store the local time, an IANA zone name such as Europe/Berlin, and the recurrence rule, because fixed offsets change with daylight saving. I use a date type for calendar dates like birthdays, keep separate event time and ingestion time when data can arrive late, avoid relying on client clocks, and break timestamp ties with the id when paginating.

Soft delete or hard delete?

Soft delete allows undo and keeps audit history, but it forces every query to filter, breaks naive unique constraints unless the index is partial, and does not satisfy a privacy erasure request on its own. Hard delete is simpler and compact but irreversible. I usually combine them: soft delete for a retention window so support can restore, then a purge job that hard deletes and removes personal data. In LSM-based stores I remember that deletes create tombstones, which slow scans and must live long enough for replicas to converge, so I prefer TTLs and droppable time partitions to mass row deletes.

How do you design a table for sharding?

I pick the shard key from the hottest access pattern, usually the tenant or the owning user, with high cardinality and even spread. I put that key on every related table so parent and child rows co-locate and common queries and transactions stay on one shard. For queries that do not know the shard key, I add a global lookup index. I avoid sequential global counters for ids, plan for hot tenants by allowing them their own shard, and use many logical partitions per node so I can rebalance later without rekeying data.

How would you model counters such as likes or follower counts at scale?

I do not count rows on read for big tables. I keep a precomputed counter, updated asynchronously from the event that creates or removes the base row, and treat it as a cache of the truth with a reconciliation job that recomputes it from the base rows. For very hot keys I split the counter into several sub-counters and sum them on read, or buffer increments in memory and flush in batches. Where exactness is required, such as inventory and money, I update transactionally with a conditional write instead.

How do you separate PII and why?

I keep identity data in a small, tightly access-controlled store keyed by an opaque user id, and have orders, events and logs reference only that id. That makes erasure and export requests a change to one record rather than a hunt through many tables, reduces blast radius in a breach, and lets me place profile data in the region residency rules require. I also avoid putting PII in keys, URLs or logs, encrypt sensitive columns, and consider per-user keys so that destroying the key renders all copies unreadable.

How do you change a schema without downtime?

I use expand and contract. First I add the new column or table in a backward-compatible way, then deploy code that writes both shapes, backfill old rows in small throttled batches, switch reads to the new shape while comparing results, and finally stop writing the old shape and drop it in a later release. Primary keys and shard keys are the hardest to change, so I choose them carefully at the start. The detailed mechanics are covered in the chapter on multi-region data and migrations.

25. Recap and connections

Recap

  • Model from access patterns: list queries with rates first, draft keys and indexes so each is a lookup or range scan, then verify every pattern.
  • Entities and cardinality: 1:N with a foreign key (indexed), M:N with a junction table that may carry its own facts.
  • Normalize to 3NF to avoid update, insert and delete anomalies; denormalize on purpose for read-heavy paths, cross-shard joins and NoSQL, and keep a way to repair copies. Snapshots such as order prices are history, not redundancy.
  • Documents: embed what is read together and bounded; reference what is unbounded, shared or accessed alone.
  • Use surrogate ids (time-ordered for big, sharded tables) with unique constraints on natural keys; store instants in UTC plus zone names where needed; money as integer minor units.
  • Choose soft or hard delete consciously; know tombstones in LSM stores; use audit or temporal tables for history; use TTL and time partitions for retention.
  • Statuses are state machines enforced with guarded conditional writes; JSON columns are for sparse, flexible attributes, and promoted to columns when queried.
  • Put the tenant id first in keys; separate PII behind opaque ids; pick shard keys from the hottest query and co-locate related rows; in NoSQL, design partition key and sort key together and bound partition size and heat.
  • Counters are precomputed caches of truth with reconciliation; evolve schemas with expand and contract.
