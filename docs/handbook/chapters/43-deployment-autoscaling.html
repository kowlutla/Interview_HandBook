Chapter 43 · Module 6 · Reliability and operations

Deployment and Autoscaling

Most outages are caused by change, and most overload is caused by demand that moved faster than capacity. This chapter explains how to ship code safely (pipelines, canaries, feature flags, database changes, graceful shutdown, rollbacks), how containers and Kubernetes package and run that code, and how autoscaling adds and removes capacity without falling over while it does so.

1. Why deployment and scaling are design problems

A system design interview often ends with the question "and how do you deploy it?" Weak answers say "we use Kubernetes and CI/CD". Strong answers recognize that deployment is the moment when your running, serving system is deliberately altered while users are still using it. Every deploy is a small, planned experiment on production. Industry post-incident reviews repeatedly find that a large share of serious outages (often quoted as a majority) trace back to a change: a code release, a configuration push, a schema migration, a certificate rotation. So the design question is not "how do I get code onto servers" but "how do I make change cheap, frequent, observable, and reversible".

Scaling has the mirror-image problem. Demand is not constant: it has daily cycles, weekly cycles, launches, marketing campaigns, and sudden spikes. Capacity (servers, containers, database connections) takes time to add. If capacity is fixed and sized for the peak, you pay for idle machines most of the day. If it is sized for the average, you fail at the peak. Autoscaling is the automatic adjustment of capacity to demand, and it is itself a control system with delays, feedback, and failure modes that you must design for. The two topics belong in one chapter because they share machinery (containers, orchestrators, health checks, load balancers) and because a scale-up event is, in effect, a mini-deployment: new instances start, must prove they are healthy, and begin receiving traffic.

Key idea Safe delivery rests on three habits: make each change small (so a failure has few suspects), expose it to a little traffic first (so a failure has a small blast radius), and keep a fast way back (so a failure has a short duration). Autoscaling rests on the dual: measure demand with a signal that leads the problem, react quickly enough, and never remove capacity faster than you can safely get it back.

This chapter builds on Chapter 8 (horizontal scaling and stateless services), Chapter 40 (timeouts, retries, load shedding), Chapter 41 (availability zones, failover) and Chapter 42 (cells as a unit of blast radius). The operational view of running many services is in Chapter 53.

2. The CI/CD pipeline

Continuous Integration (CI) means every change is merged into a shared main branch frequently (at least daily) and is automatically built and tested on each merge. Continuous Delivery means that every change that passes the pipeline is releasable at the push of a button. Continuous Deployment goes one step further: every change that passes the pipeline is released to production automatically, with no human approval. Many organizations practice delivery for regulated or high-risk systems and deployment for the rest.

A pipeline is an ordered series of stages, each of which is a gate. The idea is to fail as early and cheaply as possible: a typo should be caught in seconds by a linter, not hours later in production.

2.1 Build once, promote the same artifact

The single most important pipeline rule is build the artifact once and promote that exact artifact through environments. If you rebuild for staging and again for production, you are no longer testing what you ship; a changed dependency or build machine could produce a different binary. The pipeline produces a container image (or package), stores it in a registry under an immutable tag (usually the git commit hash, not a moving name like latest), and every environment simply runs that image. Differences between environments live in configuration, injected at start time (section 14), never in the artifact.

2.2 Test pyramid and flaky tests

Fast unit tests form the wide base; fewer integration tests sit above; a small number of slow end-to-end tests sit on top. A pipeline that depends mostly on slow end-to-end tests becomes slow and unreliable. A flaky test (passes and fails on the same code) is poisonous: engineers learn to re-run and ignore failures, and a real failure then gets ignored too. Quarantine and fix flakes quickly. Target a commit-to-production time measured in minutes to an hour; the longer the pipeline, the larger the batches engineers combine, and the riskier each release becomes. The widely used "DORA" metrics capture this: deployment frequency, lead time for changes, change failure rate, and time to restore service. Healthy teams ship often and have a low failure rate, which shows speed and safety are not opposites.

2.3 Pipeline security and trunk-based development

The pipeline holds the keys to production, so treat it as production. Use short-lived credentials, sign images and verify signatures at deploy time (so only images built by your pipeline can run), and generate a software bill of materials so you can answer "which services contain library X?" when a vulnerability is announced. Pair this with trunk-based development: short-lived branches merged to main daily, with unfinished work hidden behind feature flags (section 4) instead of living for weeks on a branch. Long-lived branches create large, risky merges, which is the opposite of the small-change habit.

3. Deployment strategies

"Deploying" means replacing version N of a service with version N+1 while serving traffic. Strategies differ in how much capacity they need, how long both versions coexist, how many users see the new version first, and how fast you can undo.

3.1 Recreate

Stop all instances of the old version, then start the new version. It is simple and guarantees that only one version ever runs, which is convenient when versions cannot coexist (for instance a destructive schema change). The price is downtime equal to shutdown plus startup plus warm-up. It is acceptable for internal batch systems or off-hours maintenance windows, and unacceptable for most user-facing services.

3.2 Rolling update

Replace instances gradually: start a few new ones, wait until they are healthy, remove the same number of old ones, repeat. At every moment some capacity is serving, so there is no downtime, and it needs little extra capacity. This is the default in Kubernetes. The trade-offs: old and new versions run side by side during the rollout, so they must be compatible (section 6), and a rollback is itself another rolling update, which takes as long as the original. Rolling updates have no built-in notion of "is the new version actually good", only "does it pass its health check", so a bug that passes health checks rolls out to everyone unless you add analysis.

3.3 Blue/green

Run two full environments. Blue is live; green is a complete copy running the new version, receiving no user traffic. You test green (smoke tests, synthetic traffic), then flip the router (load balancer, DNS weight, or service selector) so all traffic goes to green. Blue is kept idle for a while. Rollback is flipping the router back, which takes seconds and needs no restart. The costs are double capacity during the switch and the "all at once" exposure: after the flip, 100% of users hit the new version immediately, so a bug that only shows under real load hurts everyone before you notice. Blue/green is therefore often combined with a gradual weight shift, which is effectively a canary. Databases are the hard part: both colors usually share one database, so schema changes must work for both versions (section 5).

3.4 Canary with automated analysis

Named after the canary in the coal mine, a canary release sends a small slice of real traffic (commonly 1-5%) to the new version while the rest stays on the old one. You compare the two groups on the metrics that matter: error rate, latency percentiles, saturation (CPU, memory), and business metrics such as checkout success. If the canary looks no worse than the baseline, raise the share in steps (5%, 25%, 50%, 100%); if it looks worse, route all traffic back, with at most a small slice of users having been affected.

Doing this by human eyeballing a dashboard is slow and biased, so mature systems use automated canary analysis. Tools in this space (Kayenta with Spinnaker, Argo Rollouts, Flagger) run the comparison for you. The key design points are:

  • Compare canary against a fresh baseline, not against production history. The best baseline is a few instances of the old version launched at the same time as the canary, so both have the same age, cache warmth, and traffic mix. Comparing a cold canary to a long-running fleet produces false alarms.
  • Use several metrics with thresholds and a statistical test. One metric can be noisy. The analyzer scores each metric (for example with a rank-sum or similar non-parametric test) and combines them into a verdict: pass, fail, or inconclusive. An inconclusive result on low traffic should lengthen the step, not pass it.
  • Fix the step duration and minimum sample size up front. Five minutes at 1% of a low-traffic service may hold only a few hundred requests, which cannot show a 0.2% error increase. Duration must cover enough requests and also enough time for slow problems (memory leaks, cache expiry, a periodic job).
  • Automatic abort. A failed verdict triggers the rollback without waiting for a human.

3.5 Shadow (traffic mirroring) and dark launches

In a shadow deployment the proxy or mesh duplicates each production request to the new version, but the new version's response is thrown away; users only ever see the old version's answer. You get realistic load and inputs with zero user impact, and you can diff the two responses to find behavioural differences. This is excellent for rewrites and for validating a new data store or search index. The cautions are important: shadow traffic must not cause side effects (do not send duplicate emails, charge cards twice, or write to the real database; stub or sandbox those calls), it doubles load on shared dependencies, and it cannot test anything that depends on the user seeing the result (UI, latency as perceived by users).

3.6 A/B testing

An A/B test is not primarily a safety mechanism; it is a way to learn which variant produces a better business outcome. Users are assigned to variant A or B by a stable hash of their id, so each user consistently sees one variant, and you compare conversion, retention, or revenue with statistical significance. It uses the same routing machinery as a canary, but the decision metric differs: a canary asks "is the new version not worse technically?" while an A/B test asks "is it better for the product?". Run them in order: canary first for safety, then A/B for value.

4. Feature flags

A feature flag (or toggle) is a condition in code that decides at runtime whether a feature is on, evaluated from configuration that can be changed without a deployment. This separates two things that are otherwise glued together: deploying code (making it present on servers) and releasing a feature (making users experience it). You can deploy on Tuesday with the flag off, and release on Thursday by flipping it, with no new build.

if (flags.isEnabled("new-checkout", user)) {
    return newCheckout(cart);      // new code path, deployed but dark
}
return legacyCheckout(cart);       // old path stays until the flag is retired

4.1 Kinds of flags

  • Release flags hide unfinished work so it can be merged to main early (trunk-based development). They are short-lived.
  • Progressive rollout (percentage) flags turn a feature on for 1%, 10%, 50% of users, chosen by a stable hash of the user id so that a user does not flip-flop between experiences. Rollout can also be targeted: employees first, then one region, then everyone.
  • Kill switches (operational flags) exist to turn off a risky or expensive behaviour in an emergency, such as a recommendation call that is overloading a dependency. A kill switch is a pre-built mitigation: disabling a feature in seconds is far faster than a rollback, and it works even when the bug is in a dependency rather than your code. Good kill switches degrade gracefully to a simpler path (see Chapter 40 on graceful degradation). They are long-lived and should be tested periodically, because an untested kill switch fails when you need it.
  • Experiment flags drive A/B tests (section 3.6).
  • Permission flags gate paid tiers or entitlements; these are really product configuration and live forever.

4.2 Dark launches

A dark launch runs a new code path in production against real traffic without exposing its results to users. For example, the backend calls the new pricing engine in addition to the old one, logs both answers, compares them, and still returns the old answer. It is the in-process cousin of shadow traffic (section 3.5) and has the same side-effect cautions. When the comparison shows agreement, a flag switches the user-visible answer.

4.3 Flag infrastructure and its dangers

Flag evaluation must be fast and must not become a new single point of failure. The usual design is: a flag service holds the rules; each application instance runs an SDK that downloads rules and caches them in memory, refreshing by polling or a streaming connection, and evaluates locally with no network call per request. If the flag service is down, the SDK keeps using the last known rules, and falls back to a safe default baked in the code for flags it has never seen. Decide for every flag what the safe default is (usually "off", but for a kill switch protecting a mandatory function it may be "on").

The dangers are real:

  • Flag debt. Every flag doubles the number of code paths: ten independent flags imply 1,024 combinations, of which you test a handful. Flags that stay after their rollout completes become dead branches that confuse readers and hide bugs. Give each release flag an owner and an expiry date, track the count, and delete the flag and the old path soon after reaching 100%. Several well-known outages involved reviving or reusing an old flag name or a dormant code path.
  • A flag change is a deployment. Flipping a flag in production changes behaviour for users instantly and globally, so it needs the same care: audit log, access control, staged rollout, and ideally review for risky flips. Treat configuration pushes with the same safety rules as code (section 8).
  • Inconsistent evaluation. If different instances have different flag versions for a few seconds, a multi-step request may see mixed behaviour. Design so that a single request evaluates a flag once and carries the result.
  • Testing. Test both sides of important flags, and test the transition (flag turning on while requests are in flight).

5. Database changes during a deploy

Application instances are replaceable; the database is not. You cannot run two copies of your database "blue and green" and flip, because it holds the live data. Yet schema changes (adding a column, renaming a field, splitting a table) must coexist with a rolling or canary release in which old and new application versions run simultaneously against the same schema. The solution is to never make a change that breaks either version, by splitting it into several small, individually safe steps. This pattern is called expand and contract (also "parallel change").

5.1 Example: renaming a column

Suppose you want to rename users.fullname to users.display_name. A direct ALTER TABLE ... RENAME COLUMN breaks the old version the instant it runs, and rolling back the code would then break too. Instead:

  1. Expand: add the new nullable column display_name. This is backward compatible: old code ignores it. Deploy the migration first, on its own.
  2. Dual write: deploy application version N+1 that writes both columns and still reads the old one. Old and new versions can coexist because both keep fullname correct.
  3. Backfill: copy existing values into the new column with a throttled batch job (small batches, pause on replica lag, so you do not overload the primary; see Chapter 24). Verify counts and checksums.
  4. Switch reads: deploy N+2 that reads the new column (ideally behind a flag, with a shadow comparison against the old). If something is wrong, flip back: the old column is still being written.
  5. Stop writing the old column: deploy N+3 that no longer touches fullname. Rolling back to N+2 is still safe if you keep writing for a period.
  6. Contract: after a bake period when no deployed version needs the old column, drop it in a final migration. This is the only irreversible step, so it is done last and deliberately.

5.2 Rules of thumb

  • Separate schema deploys from code deploys. Run migrations as their own pipeline step, before the code that needs them (for additive changes) or after the code that stops using them (for removals).
  • Additive changes are safe; destructive ones are not. Adding a nullable column or a new table is compatible. Dropping, renaming, tightening a constraint, or changing a type is not, until the code no longer depends on the old shape.
  • Beware locking. Some DDL statements take a lock that blocks reads and writes for as long as they run (for example rewriting a large table). Use online schema change tools or database features that do so without a long lock, build indexes concurrently, and set a lock timeout so the migration fails fast instead of queuing behind a long transaction and blocking everything behind it.
  • Backfills are production traffic. Throttle them, make them resumable and idempotent (Chapter 32), and run them separate from the deploy.
  • Large moves between stores or regions follow the same dual-write, backfill, verify, cut over pattern, scaled up; see Chapter 26 for online migrations across databases and regions.

6. Backward and forward compatibility during a rollout

During any rolling, canary, or even blue/green deployment, two versions of your code exist at once, plus possibly old versions of mobile apps and cached data. Compatibility is the discipline that lets them coexist. Two directions matter:

  • Backward compatibility: the new version can handle data and requests produced by the old version. (The new server reads old rows and old messages.)
  • Forward compatibility: the old version can handle data and requests produced by the new version. (The old server tolerates a message with a field it has never heard of.) This is the one teams forget, and during a rollout it is required, because new instances begin writing new-shaped data while old instances are still running and reading it, and during a rollback the old version must read what the new version wrote.

Practical rules: in serialization formats (Chapter 7) add new fields as optional with defaults, never reuse a field number or name for a different meaning, ignore unknown fields rather than rejecting them, and treat enums as open (an old consumer must handle an unknown enum value gracefully). For APIs between services, add new fields and endpoints first, migrate callers, and remove old ones only after telemetry shows zero use. For events on a queue (Chapter 34), consumers must be upgraded before producers start emitting the new shape, or the new shape must be tolerated by old consumers. The general ordering is "deploy readers before writers": make everything able to understand the new format first, and only then produce it.

Also consider in-flight state: a user's session, a cached object in Redis, a job in a queue, a workflow mid-execution. These were created by an old version and may be read by a new one (or the reverse after a rollback). Version your cache keys or values and your persisted workflow state, and test upgrade and downgrade, not only fresh installs.

Watch out "It works in staging" usually means staging only ever ran one version at a time. The bugs that matter in rollouts are mixed-version bugs. Add a test that runs the old and new versions together against one database and one queue.

7. Graceful shutdown, connection draining and health probes

Replacing an instance means stopping the old one. If you simply kill it, every request it was handling fails, and clients that were about to send it traffic get connection errors. Even a "zero downtime" strategy produces a burst of errors at every instance swap if shutdown is not graceful. Meanwhile new instances that start must not receive traffic until they are truly ready. Two mechanisms cover this: graceful shutdown with connection draining and health probes.

7.1 Graceful shutdown

The orchestrator (or the operating system) signals the process to stop by sending SIGTERM, a polite request, and later SIGKILL, which cannot be caught, after a deadline. A well-behaved service, on SIGTERM:

  1. Fails its readiness check (or deregisters), so the load balancer stops sending new requests. Load balancers and service registries learn of this with a delay (seconds), so the service keeps accepting connections for a short grace period.
  2. Drains: stops accepting new work but lets in-flight requests finish, up to a timeout. For HTTP/1.1 it adds Connection: close on responses; for HTTP/2 it sends a GOAWAY frame so clients open new connections elsewhere. Long-lived connections (WebSockets, streams, see Chapter 6) are asked to reconnect, ideally with jitter so they do not all reconnect at the same instant.
  3. Finishes background work: commits or hands back queue messages (a consumer should stop polling, finish current messages, and acknowledge or release them), flushes buffers and logs, and closes database pools.
  4. Exits with a clean status before the deadline.

The timing detail trips many teams: removing a pod from a Service's endpoints and sending SIGTERM happen in parallel, not in order. For a few seconds after the signal, proxies and load balancers may still route requests to a pod that has begun shutting down. A short pre-stop sleep (a hook that waits a few seconds before the app begins refusing connections) is the standard remedy. The pod's overall termination grace period (30 seconds by default in Kubernetes) must exceed pre-stop plus the longest legitimate request, otherwise the forced kill cuts requests in the middle.

7.2 Readiness, liveness, and startup probes

A probe is a periodic check that the orchestrator runs against each instance (an HTTP call, a TCP connect, or a command). Kubernetes defines three, and confusing them is a classic cause of self-inflicted outages.

ProbeQuestion it answersAction on failureWhat it should check
Readiness"Can this instance serve traffic right now?"Remove from load balancing; do not restart.Warmed up, can reach critical dependencies it needs for most requests, not shutting down, not overloaded.
Liveness"Is this process stuck beyond recovery?"Kill and restart the container.Only the process itself: event loop responsive, no deadlock. Not dependencies.
Startup"Has this slow-starting app finished booting?"Keep other probes disabled until it passes; restart if it never does.Completion of long initialization (loading a model, replaying a log).

Why the distinction matters: if a liveness probe checks the database and the database slows down, every instance fails liveness at once, the orchestrator restarts the entire fleet, and a database slowdown becomes a total outage with a cold-start stampede on top. Liveness should be cheap and local; dependency health belongs in readiness, and even there, be careful: if all instances fail readiness because a shared dependency is down, you remove all capacity, and clients receive errors from the load balancer rather than a degraded answer from your service. Many designs make readiness reflect only the instance's own ability and let circuit breakers and fallbacks (Chapter 40) handle dependency failures.

Tune probes with an initial delay or, better, a startup probe for slow boots; a period of a few seconds; and a failure threshold of several consecutive failures so that one slow response does not trigger action. Too aggressive means flapping; too lax means slow detection.

8. Rollback, roll-forward, and deployment safety

8.1 Rollback versus roll-forward

Rollback means redeploying the previous known-good version. It is fast and mentally simple, and it should be a rehearsed, one-command operation, ideally automatic when canary analysis fails. But rollback is only safe if the previous version can still work with the current state of data: if the new version already wrote data in a new format, or a migration dropped something, the old code may break (this is why expand and contract keeps old columns until late, and why forward compatibility matters). Roll-forward means shipping a quick fix as a new version instead. It is the right choice when rollback is unsafe (an irreversible migration has run), when the fix is trivial and already understood, or when the fault is not in the code at all. A good incident practice is: if a recent change plausibly caused the problem and rollback is safe, roll back first and debug afterwards; restoring service beats understanding the cause.

Keep the previous version's image and configuration available, keep rollback paths tested (an untested rollback is a hope, not a plan), and make the deploy tool itself resistant to the failures you are guarding against (a deploy system that depends on the very service it deploys cannot fix it).

8.2 Deployment safety practices

  • Bake time. After a change reaches a stage, wait a fixed period before promoting to the next, even if the metrics look fine. Some failures are slow: memory leaks that take hours, cache entries that expire on a daily cycle, batch jobs that run at night, a peak-hour load pattern. Bake time converts "no errors in the last five minutes" into "no errors over a full usage cycle". Typical practice is minutes for early stages and hours for the final ones, longer for riskier changes.
  • Stage by blast radius. Deploy first to a place where failure is cheap and then widen. A typical order: staging, then an internal "dogfood" environment or employee-only cell, then one small cell in one region, then the rest of that region, then other regions in waves. Do not deploy to all regions at the same time, and prefer one availability zone (Chapter 41) at a time within a region, so a bad deploy cannot destroy all redundancy at once.
  • Use cells as the unit of rollout. If your system is partitioned into independent cells (Chapter 42), each cell is a ready-made blast radius: deploy to one cell, watch, then proceed. Because cells share nothing, a bug is confined to the cell where it was deployed, and you can choose low-risk or volunteer tenants for the first cells.
  • Automatic gates. Promotion proceeds only if health and SLO metrics (Chapter 54) are green; an alarm during a rollout halts and reverts it automatically. Also block deploys during active incidents, during an exhausted error budget, and at peak business periods (a "change freeze" policy), because changes made while the system is already unhealthy make diagnosis harder.
  • Treat configuration and flags like code. Many large outages came from a configuration change pushed globally in one step. Config goes through the same review, staging, canary, and bake process, and the system should validate config before applying and keep the last good copy if the new one is rejected.
  • Observe deploys. Annotate dashboards with deploy markers, so that a sudden change in a graph can be correlated with a release in seconds.

9. Containers

9.1 The problem containers solve

Historically, deploying meant installing an application onto a server and hoping the server had the right runtime version, libraries, and settings. "It works on my machine" and "snowflake servers" (each configured by hand, slightly differently) were routine causes of failed deploys. A container packages the application together with everything it needs to run (runtime, libraries, files) and runs it as an isolated process, so it behaves the same on a laptop, in CI, and in production. Compared with virtual machines, which each carry a whole guest operating system and boot in minutes, containers share the host's kernel, so they start in about a second, use far less memory, and let you pack many per machine.

9.2 Images and layers

A container image is the read-only template; a container is a running instance of an image. Images are built from a recipe (a Dockerfile) as a stack of layers, each layer being the filesystem changes made by one instruction (install packages, copy the app). Layers are identified by a content hash and shared: ten services built on the same base image store that base once, and a machine that already has a layer does not download it again. At run time the layers are stacked read-only with a thin writable layer on top using a union filesystem, so writes made by the container are discarded when it is removed (state must live in volumes or external stores).

Practical consequences for design: order the Dockerfile so rarely changing layers (OS, dependencies) come before frequently changing ones (your code), so rebuilds and pulls move only a small layer; use small base images and multi-stage builds (compile in one stage, copy only the binary into a minimal runtime image) to reduce size and attack surface; pin versions; tag with the commit hash. Image size matters for scaling speed: a 1.5 GB image can take a minute to pull onto a new node, which directly increases scale-up lag (section 13).

9.3 Namespaces and cgroups

Containers are not a kernel feature of their own; they are built from two Linux mechanisms. Namespaces give a process its own private view of system resources: a separate process id space (so the container's main process thinks it is PID 1 and cannot see others), network interfaces and ports, mount points, hostnames, and user ids. Control groups (cgroups) limit and account for resources used by a group of processes: a CPU share or hard quota, a memory ceiling, block I/O limits. If a container exceeds its memory limit, the kernel kills it (an "out of memory kill"); if it exceeds its CPU quota, it is throttled (paused until the next scheduling period), which shows up as latency spikes rather than errors. Understanding throttling is valuable in interviews: a service with a CPU limit set too low can show high latency while average CPU looks modest.

9.4 Why containers help

  • Consistency: the tested artifact is the deployed artifact, with the same dependencies everywhere.
  • Fast startup and density: seconds to start, many per host, which is what makes frequent deploys and fast scale-up practical.
  • Immutability: to change something you build a new image instead of editing a running machine, so you can always say exactly what is running (section 14).
  • Isolation and resource accounting: noisy-neighbour effects are bounded by limits.
  • A standard unit for orchestrators: schedulers can place, restart, and scale anything that is a container.

Containers also bring concerns: a vulnerable base image affects every service using it (scan and rebuild regularly), containers should run as a non-root user with a read-only filesystem where possible, and the shared kernel means they are a weaker security boundary than virtual machines (for untrusted multi-tenant code, use lightweight VM sandboxes; see Chapter 55).

10. Kubernetes concepts

Kubernetes is an orchestrator: you declare the desired state ("run 6 copies of this image, reachable at this name") and a set of control loops continuously compare desired against actual state and take action to close the gap. This declarative, reconciling design is the same idea as an autoscaler or any thermostat. A cluster has a control plane (API server, a consistent key-value store called etcd that holds all state, a scheduler, and controllers) and many worker nodes that run the containers via an agent called the kubelet.

10.1 The core objects

  • Pod: the smallest deployable unit, one or more tightly coupled containers that share a network address and storage volumes and are scheduled together (for example an app plus a logging sidecar). Pods are ephemeral: they get new IPs and can vanish at any time, which is why you never address a pod directly.
  • Deployment (with ReplicaSet): declares "N identical replicas of this pod template" and manages rolling updates. A ReplicaSet ensures N pods exist; a Deployment creates a new ReplicaSet per version and shifts replicas between them, keeping old ReplicaSets for rollback (rollout undo). It is the right object for stateless services.
  • Service: a stable virtual IP and DNS name in front of a changing set of pods, chosen by label selector. It load-balances across ready pods only (readiness probes feed this). Types include ClusterIP (internal), NodePort, and LoadBalancer (provisions a cloud load balancer). Discovery is covered further in Chapter 49.
  • Ingress: rules that map external hosts and paths to Services, with TLS termination, handled by an ingress controller (a reverse proxy; see Chapter 10 and Chapter 9). Newer Gateway API objects generalize this.
  • ConfigMap and Secret: configuration kept outside the image and injected as environment variables or mounted files, so the same image runs in every environment. Secrets are for sensitive values; by default they are only base64-encoded, so enable encryption at rest, restrict access with RBAC, and prefer an external secret manager.
  • StatefulSet: like a Deployment but for stateful workloads (databases, brokers). Pods get stable identities (db-0, db-1), stable network names, and their own persistent volumes that follow them across restarts, and they are started and updated in order. Scaling stateful sets is much harder than scaling stateless ones (section 17).
  • DaemonSet, Job, CronJob: one pod per node (log or metrics agents), run-to-completion tasks, and scheduled tasks.
  • Namespace: a logical partition of the cluster for teams or environments, with its own quotas and access rules. Do not confuse with the Linux namespaces of section 9.3, although the idea of scoping is similar.

10.2 Requests, limits, and the scheduler

Each container declares resource requests (the amount the scheduler reserves for it) and limits (the cap enforced at run time by cgroups). The scheduler places a pod on a node that has enough unrequested capacity to fit its requests, also honouring constraints such as node labels, taints and tolerations (keep ordinary pods off special nodes), and anti-affinity or topology spread rules (spread replicas across zones and nodes so one failure does not take them all, tying to Chapter 41). Important consequences:

  • Scheduling is based on requests, not actual usage. If requests are far above real usage, nodes look full while idle (wasted money); if far below, nodes are overcommitted and pods fight for resources.
  • CPU is compressible: exceeding the limit causes throttling. Memory is not: exceeding the limit causes an out-of-memory kill and a restart. Many teams set memory request equal to limit, and set a CPU request but a generous or no CPU limit, to avoid throttling latency.
  • Quality of service classes follow from these settings: pods with request equal to limit are "guaranteed" and evicted last under node pressure; pods with no requests are "best effort" and evicted first.
  • If no node has room, the pod stays Pending. That is the signal the cluster autoscaler reacts to (section 11).

10.3 Node pools

A node pool is a group of nodes with the same machine type and settings. Clusters usually have several: a general-purpose pool, a memory-heavy pool for caches, a GPU pool, a spot (preemptible) pool for fault-tolerant work, and a small stable pool for system components. Pods are steered to pools using labels, taints, and tolerations. Separate pools let each scale independently and keep expensive hardware from being consumed by workloads that do not need it.

10.4 Rolling update parameters

A Deployment's rolling update is governed by a few knobs that map directly to the strategy trade-offs of section 3.2:

  • maxSurge: how many pods above the desired count may exist during the update (absolute number or percent). Higher is faster but needs extra capacity.
  • maxUnavailable: how many pods may be below the desired count. Setting it to 0 with surge of 1 guarantees full capacity throughout, at the cost of needing a spare slot.
  • minReadySeconds: how long a new pod must stay ready before it counts as available, giving slow-burning faults a chance to appear.
  • progressDeadlineSeconds: how long to wait before declaring the rollout stuck (new pods never become ready); the controller then marks it failed so tooling can roll back.
  • PodDisruptionBudget (a separate object): the minimum number or percentage of replicas that must stay available during voluntary disruptions such as node drains and upgrades, so cluster maintenance cannot evict every replica at once.

With 10 replicas, maxSurge=25% and maxUnavailable=0, Kubernetes starts up to 3 extra pods (rounding up), waits for them to be ready, then terminates 3 old ones, and repeats; capacity never dips below 10. Native Deployments provide only this rolling behaviour; canary and blue/green with automated analysis come from add-ons such as Argo Rollouts, Flagger, or a service mesh that can split traffic by weight (Chapter 50).

11. The three autoscalers: HPA, VPA, cluster autoscaler

"Autoscaling" in Kubernetes is really three cooperating control loops working at different levels. Mixing them up is a common interview mistake, so keep the layers straight: pods (how many, how big) and nodes (how many machines hold the pods).

11.1 Horizontal Pod Autoscaler (HPA)

The HPA changes the number of replicas of a Deployment (or StatefulSet). Every sync period (about 15 seconds) it reads a metric for the pods, compares it to a target, and computes the desired replica count with a simple proportional formula:

desiredReplicas = ceil( currentReplicas * currentMetric / targetMetric )

For example, 10 replicas averaging 90% CPU against a target of 60% gives ceil(10 × 90 / 60) = 15. If the ratio is within a small tolerance (about 10%) of 1, nothing happens, to avoid constant jitter. The HPA also applies limits: minimum and maximum replicas, and behavior policies that cap how fast it may scale up (for example "at most double, or add 4 pods, per minute") and down (for example "remove at most 10% per minute"), plus a stabilization window (by default 5 minutes for scale-down) during which it uses the highest recommendation seen, so a brief dip does not remove capacity you will need again moments later. Because the formula is proportional, it behaves like a feedback controller with a built-in assumption that load per pod scales linearly with the metric; if that does not hold (a pod saturated on something other than the chosen metric), the HPA is steering by the wrong gauge.

HPA scales out (more copies), which suits stateless services and is the main tool (Chapter 8). It needs pods to have resource requests set when using utilization percentages, since utilization is expressed relative to the request.

11.2 Vertical Pod Autoscaler (VPA)

The VPA changes the size (requests, and optionally limits) of each pod based on observed usage history. Its main value is right-sizing: teams routinely guess requests wrongly, wasting money or causing throttling and OOM kills, and the VPA recommends or applies better values. Traditionally applying a new size requires restarting the pod, which is disruptive, so many teams run VPA in recommendation-only mode, or use it for workloads that cannot scale horizontally (a single-writer database, a singleton job). Newer releases support in-place resizing for some resources. Do not let the HPA and the VPA both act on the same metric (such as CPU) for the same workload, because they fight: the HPA adds replicas as CPU is high while the VPA enlarges requests, changing the utilization the HPA sees.

11.3 Cluster autoscaler (and node provisioners)

The HPA can ask for 20 more pods, but if the nodes are full, those pods sit Pending. The cluster autoscaler watches for pods that are unschedulable because of insufficient resources, simulates which node type from which node pool would fit them, and asks the cloud to add nodes. When nodes are underused for a while (commonly about 10 minutes below a utilization threshold) and their pods can be moved elsewhere, it drains and removes them, respecting PodDisruptionBudgets. Newer provisioners (such as Karpenter) skip fixed node groups and choose an instance type and size directly from the pending pods, often starting nodes faster and packing them better. The important property is that the cluster autoscaler works on requests, not live usage, and on Pending pods, which means that a node must boot, join the cluster, pull images, and start containers before capacity arrives, a delay measured in minutes (section 13).

12. Autoscaling signals and reactive versus predictive scaling

12.1 Choosing the signal

The signal is the most consequential autoscaling design choice. A good signal is correlated with the work each instance does, moves early (before users suffer), and is stable (not noisy) and cheap to measure.

A helpful quantitative frame is Little's law: the average number of requests in a system equals arrival rate times average time in the system (L = λ × W). If a pod handles each request in 50 ms on average, it can finish 20 per second per worker thread; with 8 worker threads, about 160 RPS at full occupancy. Capacity planning from this gives a per-pod ceiling; you then target maybe 60-70% of it to leave room for variance and failures. For queue workers, the calculation is: required workers = (arrival rate × processing time) / target utilization, and extra workers to drain any backlog within the allowed time.

Interview tip When asked how to autoscale a service, do not say "on CPU" and stop. Say: "I would scale on the metric that represents saturation of this service: for a CPU-bound API, CPU or RPS per pod; for queue consumers, backlog divided by per-worker throughput; and I would add a latency or error alarm as a safety net, not as the trigger."

12.2 Reactive, scheduled, and predictive scaling

  • Reactive scaling responds to measured load as in section 11. It needs no forecast and handles surprises, but it always acts after demand arrives, and the response lag (section 13) means users feel a degraded period during a fast ramp.
  • Scheduled scaling raises or lowers capacity at fixed times, for known patterns: scale up at 08:30 before the business day, before a planned marketing event, or before a nightly batch. It is simple and effective for predictable load, and it removes the lag by being early. It should raise the floor (minimum replicas) rather than replace the reactive policy, so surprises are still handled.
  • Predictive scaling fits a model (typically on weeks of history capturing daily and weekly seasonality) and provisions capacity ahead of the forecast, as some cloud providers' predictive autoscaling features do. It works well for strongly periodic traffic, and badly for novel events (a viral spike, a new launch), so combine it with reactive scaling as a backstop and with generous headroom for big events. Always compare forecasts with outcomes, and fall back to higher minimums if the model is wrong.

In practice the strongest design layers all three: scheduled or predictive scaling sets a floor ahead of the known curve, reactive scaling handles deviations, and a load-shedding policy (Chapter 40) protects the system during the minutes that scaling cannot cover.

13. Scaling lag, warm-up, cooldowns and flapping

13.1 Scaling lag

Section 11's figure showed that capacity arrives minutes after the load that required it. Break the lag into parts and attack each: detection lag (shorten metric scrape and aggregation; scale on a leading signal such as RPS or queue depth rather than a lagging one such as latency), decision lag (more aggressive scale-up policies), provisioning lag (keep spare node capacity; use smaller images, cached images on nodes, and fast-booting machine images; use a provisioner that can start nodes in parallel), and readiness lag (reduce application start time, covered next). The structural fix for a spike that is faster than the lag is not faster scaling but headroom and buffering: spare capacity ready now, and queues or load shedding to hold requests while capacity arrives.

13.2 Warm-up

A newly started instance is not at full speed. A JVM or similar runtime compiles hot code gradually; caches are empty so most requests hit the database; connection pools are not yet established; a service that loads a model or index from storage may need a minute. If the load balancer immediately sends a new instance its full fair share, it may be slow or fail, and a slow instance under "least connections" balancing can attract even more load as its connections pile up. Remedies: slow start in the load balancer (ramp traffic to a new target over, say, 30-120 seconds; see Chapter 9), warm-up requests or pre-loading before readiness passes, a startup probe, and an HPA setting that ignores the not-yet-ready pods' metrics so their initial high CPU does not trigger further needless scaling.

13.3 Cooldowns, stabilization and flapping

Flapping (also called thrashing) is a rapid cycle of scaling up, then down, then up. It wastes money, repeatedly pays warm-up costs, and can itself cause errors as instances are removed while still serving. It arises because the scaling action changes the metric it measures: adding replicas lowers per-pod load, which then looks low enough to remove replicas, which raises load again. The controls:

  • Asymmetric policies: scale up fast, down slow. The cost of too little capacity is an outage; the cost of too much is a few percent of spend for a few minutes. A typical setup allows doubling per minute upward and removal of 10% per several minutes downward.
  • Stabilization window / cooldown: after a scale event, ignore further actions in the same direction for a period, or for scale-down take the maximum desired value over the last several minutes, so a short lull does not trigger removal.
  • Hysteresis: use different thresholds for up and down (scale up above 70%, scale down below 40%) so the system does not sit on a single boundary. With the HPA's proportional formula the equivalent is a tolerance band and a sensible target.
  • Smoothing: average the metric over a window rather than reacting to single samples.
  • Right target: a target of 90% leaves no room, so any noise triggers actions; targets of 50-70% are typical.

14. Infrastructure as code, immutable infrastructure, config management

14.1 Infrastructure as code (IaC)

Infrastructure as code means that networks, clusters, databases, load balancers, and permissions are defined in version-controlled text files and created by tools (Terraform, Pulumi, CloudFormation, Crossplane, and similar), not by clicking in a console. It brings the discipline of software to infrastructure: changes are reviewed in pull requests, tested, applied by a pipeline, and recorded in history, and an entire environment can be reproduced, which is also the foundation of disaster recovery (Chapter 41: rebuilding a region from code is far faster than from memory). Tools are usually declarative: you state the desired end state, and the tool computes a plan (the diff between desired and real) which you review before applying. Key practices:

  • Remote, locked state. Tools that keep a record of what they manage must store it in a shared location with locking so two people cannot apply at once.
  • Plan before apply, with the plan reviewed; protect destructive operations (deleting a database) with explicit guards.
  • Detect drift. If someone changes a resource by hand, reality diverges from code. Periodically compare and either revert or import the change. GitOps (Argo CD, Flux) makes this continuous: the cluster pulls its desired state from a git repository and reconciles it, so git is the source of truth and a rollback is a git revert.
  • Modules and environments. Reuse tested modules; keep environments structurally identical, differing only in parameters, and promote infrastructure changes through the same staged waves as application code (section 8).
  • Blast radius for infrastructure. Split state into small stacks (network, cluster, app) so an error in one apply cannot delete everything.

14.2 Immutable infrastructure

With mutable servers you log in and update them in place, so over time each drifts into a unique "snowflake" that nobody can recreate. With immutable infrastructure, a running server or container is never modified: to change anything, you build a new image, launch new instances from it, and discard the old ones. Containers make this natural, and the same idea applies to machine images for virtual machines. Benefits: what is running is exactly what was tested; rollback is launching the previous image; there is no configuration drift; and a compromised or misbehaving instance can simply be replaced rather than repaired. The "cattle, not pets" slogan captures it: instances are interchangeable and disposable. Immutability requires that state live elsewhere (databases, object storage, volumes), and that logs and metrics are shipped off the instance before it disappears.

14.3 Configuration management

Distinguish three kinds of change: code (the image), configuration (values that differ by environment: endpoints, pool sizes, feature flags), and secrets (credentials, keys). The twelve-factor rule is to keep configuration out of the image and supply it from the environment so one artifact serves all environments. Options: environment variables and mounted files from ConfigMaps and Secrets; a central configuration service with dynamic reload (Chapter 49); and an external secret store with short-lived, rotated credentials. Principles: version and review configuration like code; validate it before it is applied and keep the last known good; roll it out in stages (a global config push is a global deployment); and prefer a restart or controlled reload over arbitrary hot edits so that what is running is reproducible. Older tools such as Ansible, Chef, and Puppet configure existing machines in place and are common for managing hosts and building images, whereas in a container platform most of their role is replaced by the image build plus the orchestrator.

15. Scale-to-zero, headroom, spot instances, and cost

15.1 Scale-to-zero

Scale-to-zero removes all instances of a service when it receives no traffic and starts one when a request arrives. Serverless platforms (functions, and request-driven container platforms such as Knative-style systems) do this. It is ideal for infrequent, spiky, or per-tenant workloads, development environments, and cost-sensitive internal tools, since idle cost drops to nearly nothing. The price is the cold start: the first request waits for an instance to be created, code loaded, and runtime initialized, from tens of milliseconds to several seconds depending on runtime and image size. Mitigations include keeping a minimum of one warm instance for latency-sensitive paths, provisioned concurrency, smaller images, lighter runtimes, snapshot-based starts, and a request buffer or activator component that holds the first request while the instance starts. Do not scale to zero on the user-facing critical path of a latency-sensitive service; do so for background and bursty work. Also remember that a cold start in a large fleet during an outage recovery behaves like a thundering herd (section 17).

15.2 Capacity headroom

Headroom is deliberately unused capacity that absorbs the load growth during the scaling lag and the loss of failure domains. Size it from three factors: (1) lag growth: how much demand can grow in the time it takes new capacity to arrive; if traffic can rise 30% in 3 minutes and scale-up takes 4 minutes, you need about 30% spare; (2) failure tolerance: if the service runs across 3 zones and must survive one zone loss (Chapter 41), the remaining two must carry 100% of the load, so each zone should run at no more than about 67% utilization, meaning 50% overprovision relative to peak when measured as the whole; (3) deploy overhead: rolling updates and canaries temporarily remove or add instances. Techniques to hold headroom without paying for idle machines in the cluster: low-priority placeholder pods ("pause" pods) that occupy spare node capacity and are evicted instantly when real pods need the room, giving immediate scheduling while the cluster autoscaler adds a replacement node in the background; and a modest minimum replica count.

15.3 Spot and preemptible instances

Cloud providers sell spare capacity at a large discount (commonly 60-90% off) with the condition that they may reclaim it on short notice (often 30 seconds to 2 minutes of warning). It suits fault-tolerant, stateless, interruptible work: batch jobs, stream workers that checkpoint, CI runners, web replicas beyond a stable base. Design rules: keep a baseline of on-demand or reserved capacity for the minimum load; run the elastic portion on spot spread across multiple instance types and zones (so one reclaim wave does not remove everything); handle the interruption notice as a graceful shutdown (section 7); keep work idempotent and checkpointed; and never put single-copy stateful data on spot without replication. Spot supply can vanish for a given type in a given zone, so diversification and fallback to on-demand are essential.

16. Worked example: canary rollout and an autoscaling policy with numbers

Scenario: a checkout API serves a peak of 6,000 requests per second (RPS) and a daily low of 1,500 RPS. It runs on Kubernetes across 3 availability zones. We need (a) a canary policy for releases and (b) an autoscaling policy.

16.1 Capacity per pod

Load tests show one pod (2 vCPU request, 2 GiB) sustains 150 RPS at p99 latency of 200 ms; above about 190 RPS latency climbs steeply (saturation). We choose a planning target of 100 RPS per pod (about two thirds of the 150 RPS comfortable ceiling, and roughly half of the saturation point), which leaves room for variance and the loss of a zone.

  • Peak pods needed at the target: 6,000 / 100 = 60 pods.
  • Lowest: 1,500 / 100 = 15 pods.
  • Zone loss check: with 3 zones and 60 pods (20 per zone), losing a zone leaves 40 pods carrying 6,000 RPS = 150 RPS per pod, which is right at the comfortable ceiling but below saturation, acceptable for a short failover. To be safer we set maxReplicas to 90 and let the HPA rise during a zone loss. For a hard guarantee we would instead provision 90 pods at peak (30 per zone), costing 50% more; the decision is a business one, and we choose the cheaper option plus fast scaling and load shedding.

16.2 The HPA policy

  • Metric: RPS per pod (custom metric), target 100, with CPU target 65% as a second metric (HPA takes the larger recommendation).
  • minReplicas = 18 (6 per zone; above the 15 needed at the low so a sudden morning ramp has headroom), maxReplicas = 90.
  • Scale-up behaviour: allow +100% or +10 pods per 60 seconds, whichever is larger, no stabilization window. Scale-down: at most 10% per 5 minutes, stabilization window 10 minutes.
  • Scheduled floor: at 07:30 local time set minReplicas = 40 (traffic ramps from 1,500 to 5,000 RPS between 08:00 and 09:00, about +1 RPS per second, so reactive scaling alone could follow it, but the floor removes the lag risk at the start of the ramp).
  • Headroom for the spike case: low-priority placeholder pods reserving room for 12 pods (about 20% of peak), so new pods schedule immediately. Pod start-to-ready time is 45 s (image cached on node), so a spike that doubles load in 60 s is covered by headroom plus fast scale-up rather than by node provisioning, which would take 3-4 minutes.

Check the spike: traffic jumps from 3,000 to 4,500 RPS in a minute. Pods at 3,000 RPS: 30, load 100 each. At 4,500 RPS with 30 pods: 150 RPS each (comfortable ceiling). HPA computes ceil(30 × 150 / 100) = 45 pods and adds 15 (allowed: +100% means up to 30). Pods are ready after about 45 s plus about 15 s metric and decision delay: about one minute, during which the pods run at up to 150 RPS, a degraded but not failing state. This is exactly what the headroom target buys.

16.3 The canary policy

New release v2 of the checkout API (rolled out by a rollout controller with mesh traffic splitting). At each step the analysis compares canary pods to a baseline of v1 pods started at the same time.

16.4 What changes during the rollout

During steps 1-3 the HPA scales v1 and v2 separately according to their share of traffic; the rollout controller must not fight the HPA (it sets the traffic weights and the ReplicaSet counts together). The database migration used by v2 (adds a nullable column) was applied a day earlier, and v2 reads it behind a flag defaulting to off. If the canary fails, the controller routes 100% back to v1 in seconds, and nothing needs to be undone in the database because the migration was additive.

17. Failure modes

17.1 The bad deploy

Typical forms: a code bug that passes tests but fails under real data; a configuration error (wrong endpoint, expired credential); a performance regression (a new query without an index, an N+1 call pattern); a memory leak that appears after hours; a dependency incompatibility; a mixed-version bug during rollout; or a bad migration that locks a table. The defenses are the chapter's earlier sections working together: small changes, canary analysis against a same-age baseline, bake time long enough for slow faults, automatic rollback, staged waves by cell and region, flags with kill switches, expand and contract migrations, and alerts annotated with deploy markers so that the first question "what changed?" is answered immediately. The most dangerous bad deploys are those that pass health checks but corrupt data or make wrong decisions silently (incorrect prices, wrong permissions); they need business-metric checks and shadow comparisons, because error rate will not show them.

17.2 The deploy that cannot roll back

If a release includes an irreversible migration, or the new version wrote data the old version cannot read, rolling back may make things worse. Prevent it with expand and contract, forward-compatible readers, and by keeping "contract" steps far from the code release. When you cannot avoid a one-way change, treat it as a high-risk event with a rehearsed forward plan, a backup, and explicit sign-off.

17.3 Thundering herd on scale-up

When many instances start at once (a scale-up from 20 to 80 pods, a restart of the whole fleet, recovery after an outage, a zone failover), each performs the same startup work: loading configuration, opening connection pools, warming caches, fetching secrets, registering with discovery. The combined burst can overwhelm the very dependencies the system needs, such as the database (connection limits are hit, see Chapter 18), a config service, or an image registry, and the failures cause pods to crash and restart, repeating the stampede. A related herd occurs when a cache is cold after a scale-up and all new pods miss at once (Chapter 14), and when clients reconnect simultaneously after a drain. Defenses:

  • Limit the growth rate (HPA scale-up policies, rollout surge limits) so new instances join in steps.
  • Randomize and back off: add jitter to startup delays, reconnects, and retries (Chapter 40).
  • Protect shared dependencies: use a connection proxy or pooler in front of databases so 80 pods do not open 80 × 20 connections; cap per-pod pools; rate limit startup calls; cache configuration locally.
  • Warm gradually: readiness gating, slow start at the load balancer, and cache pre-warming or request coalescing.
  • Pre-position: cache images on nodes, and use headroom pods so that scaling does not also need node provisioning.
  • Avoid synchronized scaling: if many services scale on the same trigger (a traffic spike), their downstream demand multiplies. Scale downstream capacity first or in proportion, and use load shedding at the edge.

17.4 Stateful scaling

Stateless pods are interchangeable; stateful ones are not. Adding a node to a database, broker, or cache cluster requires moving data (rebalancing partitions or shards, see Chapter 25), which consumes network and disk and slows the very cluster you are trying to relieve. Therefore: do not autoscale stateful systems on the same quick loop as stateless ones; scale them ahead of need with capacity planning and schedules; throttle rebalancing; add capacity before saturation, not at it; scale down only with great care (draining and replicating data first, one node at a time, respecting quorum, see Chapter 29); and rely on managed services with built-in elasticity where possible. Read replicas (Chapter 24) add read capacity but not write capacity, and each new replica adds replication load. Also note that a StatefulSet update is ordered and slow, and that a persistent volume is tied to a zone, so a pod that needs its volume can only be scheduled in that zone; a zone with no spare node leaves it unschedulable.

Other related failures: autoscaler pushes into a downstream limit (more pods than the database can serve: the scale-up makes things worse, so cap max replicas by downstream capacity and use backpressure); metrics outage (the HPA cannot read its metric and stops acting, or acts on stale data; set sane minimums so a metrics failure leaves you safe, not at the minimum); quota or capacity exhaustion (the cloud cannot supply the requested instance type; diversify types and zones); pending pods from fragmentation (a pod requesting 6 CPUs fits on no node although total free CPU is large); and runaway scale-up from a bug or attack (cap maximums, alarm when near them, and prefer rate limiting at the edge, Chapter 16, to infinite spending). Operating many such services at once is the subject of Chapter 53.

18. Interview Q&A

How would you deploy a new version of a service with zero downtime and minimal risk?

I would build one immutable image in CI, run unit, integration and contract tests, scan and sign it, and promote that same image through staging. In production I would use a canary: send about 2% of traffic to the new version beside a same-age baseline of the old version, and have an automated analyzer compare error rate, latency percentiles, saturation, and one or two business metrics. If it passes, traffic steps up (for example 10%, 50%, 100%) with a bake time at each step, then the release proceeds in waves by cell and region, one zone first. Readiness probes and graceful shutdown with connection draining prevent errors during instance swaps, and a failed analysis automatically routes traffic back. Any schema change ships separately using expand and contract so old and new versions both work.

What is the difference between blue/green and canary, and when would you pick each?

Blue/green keeps two complete environments and flips all traffic at once; its strengths are an instant, simple rollback and a clean separation of versions, and its weaknesses are double capacity during the switch and that every user is exposed the moment you flip. A canary exposes a small share of real traffic first and grows it while comparing metrics, so it limits blast radius and catches problems that only show up under real load, at the cost of needing good metrics, enough traffic to be statistically meaningful, and the ability to run two versions together. I would use canary for most production services, and blue/green when versions truly cannot coexist or when a fast, full-environment switch is wanted, often combining them by shifting weights from blue to green gradually.

How do you change a database schema while the application is being rolled out?

You never make a change that breaks the version that is currently running. Use expand and contract: first add the new column or table in a backward-compatible way; deploy code that writes both old and new shapes; backfill existing data in throttled, resumable batches; switch reads to the new shape, ideally behind a flag; stop writing the old shape after a bake period; and only then drop the old structure in a final, deliberate step. Because any two adjacent versions work with the same schema, rolling updates, canaries and rollbacks stay safe. I would also watch for locking DDL, use online schema change tools, and run backfills as separate, throttled jobs.

What is the difference between readiness, liveness and startup probes, and what goes wrong if you confuse them?

Readiness decides whether an instance should receive traffic and removes it from the load balancer when it fails, without restarting it. Liveness decides whether the process is irrecoverably stuck and triggers a restart. Startup gives a slow-booting application time to initialize before the other probes begin. The classic mistake is putting a dependency check, such as the database, in the liveness probe: when the database is slow, every pod fails liveness, the whole fleet restarts together, and a partial slowdown becomes a full outage with a cold-start stampede. Liveness should be cheap and local; readiness should reflect the instance's own ability to serve, and dependency failures are better handled by timeouts, circuit breakers and fallbacks.

Why can you still see errors during a rolling update even though the strategy is "zero downtime", and how do you prevent them?

Because stopping a pod and removing it from load balancing happen concurrently, so for a few seconds routers and proxies still send requests to a pod that has begun shutting down, and in-flight requests are cut if the process exits immediately. The fix is graceful shutdown: on the termination signal, the pod keeps serving for a short pre-stop delay while routing converges, fails its readiness check, drains in-flight requests (using connection close or HTTP/2 GOAWAY), finishes or releases queue messages, and exits before the grace period expires. The grace period must exceed the pre-stop delay plus the longest legitimate request, and clients should retry idempotent requests safely. Pod disruption budgets and surge settings keep enough capacity during the swap.

How do feature flags improve deployment safety, and what are their risks?

Flags separate deploying code from releasing a feature, so unfinished work can merge to main behind an off switch, new behaviour can be rolled out to a percentage of users or one tenant at a time, and a misbehaving feature can be turned off in seconds with a kill switch, which is faster than any rollback. The risks are flag debt, where old flags and dead paths accumulate and combinations explode; the fact that a flag change is itself a production change needing audit, access control and staged rollout; inconsistent evaluation across instances; and dependence on the flag service, which is why SDKs cache rules locally with safe defaults. I would give every release flag an owner and expiry, delete it after full rollout, and test kill switches periodically.

How does the Horizontal Pod Autoscaler decide how many replicas to run, and what are its limits?

It periodically reads a metric, compares it with the target, and scales proportionally: desired replicas equal the current count times current metric divided by target, rounded up, within minimum and maximum bounds and subject to scale-up and scale-down rate policies and a stabilization window. Its limits are that it reacts after load has changed, so there is metric delay, decision delay, and the time to start pods and possibly nodes; it assumes load per pod scales linearly with the chosen metric, so a wrong metric (such as CPU for an I/O-bound service) mis-steers it; and it needs the cluster autoscaler to supply nodes, which takes minutes. I would add headroom, scheduled or predictive floors for known peaks, and load shedding to cover the lag.

What signals would you scale on for an API service versus a queue consumer?

For a CPU-bound API, CPU utilization or requests per second per pod are reasonable, with RPS preferred because it leads CPU and maps directly to a measured per-pod capacity; for I/O-bound services, concurrency or in-flight requests is better since CPU stays low while they saturate. Latency and error rate serve as safety alarms, not the trigger, because they lag. For a queue consumer, scale on backlog or message age relative to per-worker throughput, so the number of workers is chosen to drain the backlog within the required time, bounded by partition count and downstream capacity. In both cases I would verify that adding instances really increases capacity, rather than moving the bottleneck to a database.

How do you prevent autoscaling from flapping?

Make scaling asymmetric: scale up quickly and scale down slowly, because too little capacity causes outages while too much merely costs a bit. Use a stabilization window so that scale-down uses the highest recommendation of the last several minutes, apply hysteresis with separate up and down thresholds or a tolerance band, smooth the metric over a window, choose a target such as 60-70% instead of 90%, and ignore the metrics of pods that are not yet ready so warm-up load does not trigger more scale-up. Limiting the scale-down rate (for instance 10% per few minutes) also avoids removing instances faster than you could get them back.

What is a thundering herd on scale-up and how would you design against it?

It is the burst of simultaneous work generated when many instances start together: each opens database connections, loads configuration, fetches secrets, and misses a cold cache, so the combined burst overloads a shared dependency, which makes pods fail health checks and restart, restarting the stampede. I would limit how fast capacity is added, add jitter and backoff to startup, reconnects and retries, put a connection pooler in front of the database with fixed total connections, use slow start in the load balancer, pre-pull images and pre-warm caches or coalesce cache misses, hold headroom so scaling does not also require node provisioning, and shed load at the edge during the ramp.

Can you autoscale a database the way you autoscale a web tier? Why or why not?

Not in the same way. Web pods are stateless and interchangeable, so adding one is cheap and quick, whereas adding a database node requires moving or replicating data, which consumes I/O and network and temporarily degrades the cluster, and removing one risks losing quorum or data. Writes cannot be scaled by just adding replicas, since replicas only add read capacity and increase replication load. So stateful tiers are scaled ahead of need based on capacity planning and trends, rebalancing is throttled, scale-down is done manually or carefully one node at a time, and where possible a managed or natively elastic service is used. Vertical scaling or sharding changes are planned events, not reactive loops.

When would you roll forward instead of rolling back?

Rollback is my default for a bad release when the previous version is known good and can still operate on current data, because it restores service fastest and keeps people calm while debugging. I would roll forward when rollback is unsafe, for example after an irreversible migration or because the new version has written data the old one cannot read, when the fault is not in the code (configuration, a dependency, an expired certificate), or when the fix is tiny, understood and can pass through the fast pipeline quickly. The ability to roll back safely is designed in advance through expand and contract migrations and forward-compatible readers, and the rollback path should be rehearsed rather than assumed.

How do requests, limits and the scheduler interact, and what mistakes do you see?

The scheduler places pods based on requests, the amount reserved on a node, while limits are enforced at run time by cgroups. Exceeding a CPU limit throttles the container and shows up as latency spikes, while exceeding a memory limit gets the container killed. Common mistakes are requests set far above real usage, which wastes money because nodes appear full, requests set too low, which overcommits nodes and causes contention and evictions, CPU limits so tight that p99 latency suffers under throttling, and no requests at all, which makes pods best-effort and first to be evicted. I would measure real usage, set memory request equal to limit, set CPU requests from observed percentiles, and use the VPA recommendations to refine them.

How do cells and regions influence your deployment approach?

They define the unit of blast radius and therefore the unit of rollout. If the system is split into independent cells, I deploy to one low-risk cell first, bake, check health gates, and widen in waves, so a defect affects only the cells that have received it and the rest remain on the known-good version. Regions are rolled out one at a time, and within a region one availability zone at a time, so a bad release cannot remove all redundancy simultaneously. Configuration and feature flag changes follow the same waves, and the deploy system itself should be independent per region so one failure in tooling does not block remediation everywhere.

19. Recap

  • Change is the main cause of outages, so make it small, gradual, observable, and reversible; build one immutable artifact and promote it unchanged through the pipeline.
  • Strategies trade capacity, exposure, and rollback speed: recreate (downtime), rolling (default, version overlap), blue/green (instant switch, double cost), canary with automated analysis (smallest blast radius), shadow (no user impact, beware side effects), A/B (product learning).
  • Feature flags separate deploy from release and give kill switches, but need ownership, expiry, safe defaults, and the same change control as code.
  • Database changes use expand and contract with dual writes and backfills; readers are deployed before writers; adjacent versions must always be compatible both backward and forward.
  • Graceful shutdown (pre-stop delay, readiness fails, drain, exit before the deadline) and correct probes (readiness for traffic, liveness for stuck processes, startup for slow boots) prevent self-inflicted errors.
  • Stage rollouts by cell, zone, and region with bake time and automatic gates; prefer rollback when safe, roll forward when not.
  • Containers are layered images run as isolated processes (namespaces limit visibility, cgroups limit resources); Kubernetes reconciles declared state with pods, deployments, services, ingress, config, statefulsets, requests and limits, and node pools.
  • HPA scales replica count, VPA right-sizes pods, the cluster autoscaler adds nodes for Pending pods; choose signals that lead saturation (RPS, concurrency, queue depth), layer scheduled and predictive floors under reactive scaling.
  • Lag, warm-up, and flapping are the practical problems: scale up fast and down slowly, damp with stabilization windows, hold headroom, and cap growth rate to avoid thundering herds; stateful tiers scale ahead of need.
  • IaC, immutable infrastructure, and managed configuration make environments reproducible; spot instances, right-sizing, commitments, and scale-to-zero are the main cost levers, balanced against reliability.
