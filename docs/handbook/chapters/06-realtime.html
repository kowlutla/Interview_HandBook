Chapter 6 · Module 1 · Networking and Communication

Real-Time Communication

Ordinary web traffic is the client asking and the server answering. Chat, live scores, collaborative editing, and notifications need the server to speak first. This chapter explains every common technique for that (polling, long polling, Server-Sent Events, WebSockets, WebRTC, MQTT, push notifications), and then the hard part: running millions of long-lived connections, routing messages to the right one, surviving deploys and reconnect storms, and sizing the fleet.

1. Why real-time is hard over request/response HTTP

HTTP, as most people use it, is a request/response protocol. The client opens a connection (or reuses one), sends a request, and the server sends back exactly one response. The server never sends anything unless the client asked for it first. That model is wonderful for loading web pages and calling APIs, because it keeps servers simple: each request is independent, so any server behind a load balancer can answer it (this is the stateless design from Chapter 9).

Now consider a chat message. Alice sends "hello" to Bob. Alice's client can send it with a normal POST. But Bob's phone is sitting idle. Bob did not ask for anything, so under pure request/response the server has no way to deliver the message. The server needs some way to push data to a client at the moment the data exists. The same need appears in many products:

  • Chat and messaging (a message arrives from someone else).
  • Live dashboards, stock tickers, sports scores (the data changes on the server's schedule, not the client's).
  • Collaborative editing and multiplayer games (many clients must see each other's actions within tens of milliseconds).
  • Notifications, order and ride status, delivery tracking.
  • Progress of a long job (export, build, video encode).

There are two ways to bridge the gap. Either the client asks very often (polling and its variants), or the connection is kept open so the server can write to it whenever it likes (SSE, WebSockets). Each approach moves cost around. Frequent asking wastes requests and adds delay. Keeping connections open makes the server stateful: a connection is a piece of memory on one specific machine, and that machine now matters. A load balancer can no longer treat servers as interchangeable, deployments disconnect users, and a message for Bob must be delivered by the one server that happens to hold Bob's connection. Most of this chapter is about the consequences of that single fact.

Key idea Real-time delivery means the server must be able to reach a specific client at an arbitrary moment. The cheap way is to make the client ask often. The responsive way is to keep a connection open, which turns your servers from stateless workers into stateful holders of millions of sockets. Almost every real-time design question is about managing that state.

1.1 What "real-time" means here

In interviews, "real-time" is soft. It rarely means hard real-time (guaranteed deadlines as in a pacemaker). It usually means low latency delivery: a chat message in under a few hundred milliseconds, a live score within a second or two, a game state update within 50 ms. Always ask the interviewer what delay is acceptable, because it decides the technique. A dashboard that refreshes every 10 seconds does not need WebSockets; a multiplayer shooter cannot live without something faster than TCP-based protocols.

2. Short polling and long polling

2.1 Short polling

In short polling, the client sends a normal request on a timer, for example every 5 seconds: "anything new for me?" The server replies immediately with new data or with an empty result. Nothing about the server changes. It is the simplest technique and works through every proxy, firewall, and CDN ever built.

Its costs are easy to compute. Suppose 1 million users have the app open and poll every 5 seconds. That is 200,000 requests per second, and if new data arrives for each user once every few minutes, the vast majority (often over 95 percent) of those responses are empty. You pay for the TLS, the headers (hundreds of bytes to a few KB per request), the authentication check, and a database or cache lookup, all to say "nothing". Worse, the average delay before a user sees an update is half the polling interval (2.5 seconds here), and shortening the interval to cut delay multiplies the cost. Short polling is acceptable when freshness requirements are loose (say 30 seconds or more), when the user count is small, or as a fallback.

2.2 Long polling

Long polling keeps the same request/response shape but changes the server's behavior. The client sends a request "anything new since event 105?" If there is nothing, the server does not answer yet. It holds the request open (for typically 20 to 60 seconds). The moment an event appears, the server completes the held request with that data. The client processes it and immediately sends a new request. If the hold time expires with nothing to say, the server returns an empty response, and the client simply re-polls.

This delivers events with near-zero delay, since the response is waiting on the server side when the event happens. It still works over plain HTTP and was the workhorse of early chat and Gmail-style apps (often called Comet). But it has costs:

  • Each event costs a full request cycle. After every delivered event the client must re-issue a request, so under heavy event rates it degrades into frequent polling with headers on each message. Between the response and the next request there is a small window where the server cannot push; events in that window must be buffered and returned when the new request arrives, which is why the client sends a cursor ("since event 105").
  • The server holds one open request per client. That is already the stateful-connection problem, just using HTTP machinery. Thread-per-request servers cannot afford it; you need an event-driven server (Chapter 8).
  • Intermediaries time out. Load balancers and proxies close idle connections after 30 to 120 seconds, so the hold time must be shorter than the shortest idle timeout on the path.
  • Ordering and duplicates. If a response is lost after the server considers it delivered, the event is lost unless the client's cursor semantics make the server resend. Use cursors, not "delete after sending".

2.3 Server-Sent Events (SSE)

Server-Sent Events standardize the "hold a response open" idea. The client makes one ordinary HTTP GET with Accept: text/event-stream. The server replies with status 200 and Content-Type: text/event-stream and then never finishes the response: it keeps writing small text records as events occur. In browsers the EventSource object handles it. The wire format is plain text, one field per line, with a blank line ending each event:

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 105
event: price
data: {"sym":"ACME","px":41.07}

: heartbeat comment (ignored by the client, keeps the connection alive)

id: 106
retry: 5000
data: {"sym":"ACME","px":41.09}

Three features make SSE more than a trick. First, the id: field: the browser remembers the last id it received, and when the connection breaks it reconnects automatically and sends the header Last-Event-ID: 106, so the server can resume from the right place (section 9.3). Second, retry: lets the server tell the client how long to wait before reconnecting. Third, lines starting with a colon are comments, a convenient place for a keep-alive ping every 15 to 30 seconds so proxies do not close the idle stream.

Limits to know. SSE is one-directional: server to client only. The client sends data with ordinary POST requests on separate connections. It carries text only (binary must be encoded, such as base64). The browser EventSource cannot set custom request headers, so authentication usually relies on cookies, or on a token in the URL (which leaks into logs), or on using a fetch-based SSE client instead. Over HTTP/1.1 browsers allow only about six connections per host, so several tabs can exhaust the allowance; over HTTP/2 many streams share one connection and the problem disappears. Finally, some proxies buffer responses; the server should disable buffering (for example X-Accel-Buffering: no for nginx) and send Cache-Control: no-cache.

SSE is an excellent default for server-to-client streams: notifications, live feeds, dashboards, and the token-by-token streaming of AI model responses. It rides on plain HTTP, so load balancers, authentication, compression, and observability all work as usual.

3. WebSockets in depth

A WebSocket (RFC 6455) is a persistent, full-duplex (both directions at once) message channel between a browser or app and a server, running over a single TCP connection (and TLS, when the URL starts with wss://). Unlike SSE it carries both text and binary messages and the client can send as freely as the server. Unlike HTTP there is no per-message request line or header block: after setup, a message costs only a 2 to 14 byte frame header.

3.1 The upgrade handshake

A WebSocket does not use a new port. It begins life as an HTTP/1.1 request on port 80 or 443 and asks to upgrade the connection. That is clever because it passes through the same firewalls and the same load balancers as web traffic. The client sends:

GET /chat HTTP/1.1
Host: chat.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.example.com
Authorization or Cookie: ...   (credentials, see section 14)

If the server agrees, it answers with status 101 Switching Protocols:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

The Sec-WebSocket-Key is a random 16-byte value, base64 encoded. The server must prove it understood the WebSocket protocol by computing Sec-WebSocket-Accept as the base64 of the SHA-1 hash of the key concatenated with a fixed GUID string from the RFC. This is not security against attackers; it prevents a confused HTTP server or cache from accidentally treating a non-WebSocket exchange as a success. After the 101 response, the same TCP connection stops speaking HTTP and speaks the WebSocket frame protocol. The handshake is also where you do authentication and origin checks (section 14), because it is the last moment the connection is still an ordinary, inspectable HTTP request.

3.2 Framing

TCP is a byte stream with no message boundaries. WebSocket adds frames so that messages have boundaries. Each frame starts with a small header:

  • FIN bit and opcode. The opcode says what the frame is: 0x1 text (UTF-8), 0x2 binary, 0x0 continuation (a later piece of a fragmented message), 0x8 close, 0x9 ping, 0xA pong. The FIN bit marks the final fragment of a message, so a large message can be split into several frames and interleaved with control frames.
  • Mask bit and payload length. The length is stored in 7 bits for payloads up to 125 bytes; the value 126 means a 16-bit length follows; 127 means a 64-bit length follows. So the header is 2 bytes for small messages, up to 14 bytes in the worst case with masking.
  • Masking key. Every frame sent from the client to the server must be masked with a random 4-byte key (each payload byte is XORed with the key). This is not encryption. It exists to stop a malicious page from crafting bytes that a buggy intermediate proxy might mistake for an HTTP request, poisoning its cache. Server-to-client frames are not masked.

Control frames (close, ping, pong) are limited to 125 bytes of payload and cannot be fragmented, so they can always be sent between pieces of a large data message.

3.3 Ping, pong and why you still need your own heartbeat

TCP will happily sit forever on a connection whose other side has silently vanished (a phone that moved out of range, a NAT table entry that expired, a crashed laptop). Neither side is told, because no packet announces it. A ping frame asks "are you there?" and the peer must answer with a pong carrying the same payload. If no pong arrives within a deadline, the connection is considered dead and closed, freeing its memory. Pings serve a second purpose: they keep the connection from looking idle to load balancers and carrier NATs that drop quiet connections after one to a few minutes.

Browsers answer pings automatically but their JavaScript WebSocket API cannot send or observe ping frames. So applications commonly add their own application-level heartbeat: a tiny JSON or binary message every 20 to 30 seconds, which also lets the application measure round-trip time and detect a "half-open" connection from the browser side. Section 9 treats heartbeats and their tuning in detail.

3.4 Closing

Either side can start a clean close by sending a close frame with a 2-byte status code and an optional short reason. The receiver replies with its own close frame, and then the TCP connection is closed (typically by the server). Useful codes: 1000 normal closure, 1001 going away (a server shutting down or a page navigating away), 1008 policy violation (for example failed authorization), 1009 message too big, 1011 unexpected internal server error. Code 1006 is special: it is never sent on the wire, but reported locally when the connection dropped without a close frame, which means a network failure or crash. Client logic should treat 1001 and 1006 as "reconnect" and 1008 as "do not blindly retry; refresh credentials".

3.5 What WebSockets do not give you

The protocol gives you a pipe and nothing else. It defines no message acknowledgments, no ordering across reconnects, no replay of missed messages, no routing by topic, no authentication scheme, and no automatic reconnect. All of that is application design, which is why Socket.IO, SignalR, and similar libraries exist, and why most of this chapter is about what to build around the pipe. WebSockets over HTTP/2 (RFC 8441) let many sockets share one TCP connection but are less widely deployed than the HTTP/1.1 upgrade, and typical designs assume one TCP connection per WebSocket.

4. WebRTC, MQTT, and push notifications

4.1 WebRTC overview

WebRTC (Web Real-Time Communication) lets browsers and apps exchange audio, video, and arbitrary data directly peer to peer with very low latency. Video calls are its main use, and it is also used for game data and file transfer. Several mechanisms combine:

  • Signaling. The peers must first exchange descriptions of what they can do (codecs, network addresses). WebRTC deliberately does not define how; applications use their own WebSocket or HTTP channel to relay these offer/answer messages through a server.
  • NAT traversal with ICE. Most devices sit behind NAT (Chapter 3) and cannot be reached directly. ICE gathers candidate addresses. A STUN server tells a peer its public address as seen from the internet, which works for many NAT types. When direct paths fail (symmetric NATs, strict firewalls), a TURN server relays all media, which costs the operator real bandwidth; typically a minority of calls (often quoted as 10 to 20 percent) need it.
  • Transport. Media flows over UDP, encrypted (DTLS key exchange, SRTP for media), preferring timeliness to reliability: a late audio packet is useless, so it is not retransmitted. Data channels run over SCTP on top of DTLS and can be configured reliable or unreliable, ordered or unordered.

Pure peer-to-peer does not scale to group calls (each participant would upload N-1 streams). Production systems put a media server in the middle: an SFU (selective forwarding unit) receives each participant's stream once and forwards it to the others without decoding, or an MCU mixes streams into one. In an interview, mention WebRTC for audio/video and ultra-low-latency data, with WebSockets used only for signaling. Do not use it for ordinary chat.

4.2 MQTT overview

MQTT is a lightweight publish/subscribe protocol over TCP (with TLS) built for constrained devices and unreliable networks: sensors, vehicles, smart home gear, and also some mobile messaging systems. Clients connect to a central broker. Messages are published to hierarchical topics such as home/livingroom/temperature, and subscribers use wildcards (home/+/temperature, home/#). The broker routes; clients never address each other. Features that matter:

  • Three QoS levels per message: QoS 0 at most once (fire and forget), QoS 1 at least once (acknowledged, duplicates possible), QoS 2 exactly once between client and broker (a four-step handshake, costly). QoS applies per hop, not end to end.
  • Retained messages. The broker stores the last message on a topic and gives it to new subscribers immediately, so a new dashboard sees the current value without waiting for the next reading.
  • Last will and testament. A client registers a message the broker publishes if the client disconnects abnormally; this is a built-in presence signal.
  • Keep-alive and persistent sessions. The client states a keep-alive interval; the broker drops the session if silent for about 1.5 times that. A persistent session lets the broker queue QoS 1 and 2 messages for an offline client and deliver them on reconnect.

MQTT's small header (as little as 2 bytes) and its built-in delivery guarantees make it attractive for IoT. For a general web product, WebSockets plus your own backplane is more common; brokers such as EMQX and HiveMQ scale to millions of connections with the same fleet ideas as section 6.

4.3 Push notifications (APNs and FCM)

A WebSocket only works while the app is running and the connection is up. A phone with the app closed has no connection to you. Mobile operating systems solve this with one shared, OS-managed connection per device: Apple's APNs (Apple Push Notification service) for iOS and Google's FCM (Firebase Cloud Messaging) for Android (and web push through browsers). The OS keeps a single efficient persistent connection to the vendor, which is far kinder to battery than every app holding its own.

The flow: the app asks the OS for a device token and sends it to your backend, which stores it against the user. To notify, your server calls the vendor API (HTTP/2 for APNs, HTTPS for FCM) with the token and a small payload (roughly 4 KB maximum). The vendor delivers it to the device, which displays a notification or wakes the app. Key properties:

  • Best effort. There is no guaranteed delivery or delivery receipt to you in the general case. Vendors keep one or a few messages for an offline device with a time-to-live you set, then drop them. Options like APNs collapse identifiers and FCM collapse keys replace older undelivered messages ("3 new messages" instead of three).
  • Tokens change and expire. The vendor returns errors for invalid or unregistered tokens; you must delete those.
  • Priority and rate. High priority wakes the device but is throttled by the OS if abused. Silent data pushes are rate limited.
  • Privacy. Payloads pass through the vendor; send identifiers and fetch the sensitive content from your API after the app wakes.

The typical hybrid for messaging apps: use a WebSocket while the app is in the foreground and a push notification when it is not (the server checks presence: no live connection means send a push). Chapter 56 covers push notifications and offline sync on mobile in more depth (Chapter 56).

5.1 Decision guide

  1. Does the data need to arrive faster than every 15 to 30 seconds? If not, short polling is the cheapest correct answer. Do not over-engineer.
  2. Is traffic mostly server to client (notifications, tickers, feed updates, streamed AI output)? Choose SSE. Add ordinary POSTs for the occasional client action.
  3. Is the client also sending frequently and interactively (chat, collaborative editing, games, trading UIs)? Choose WebSockets.
  4. Audio, video, or sub-100 ms game state with loss tolerance? Use WebRTC (or a custom UDP/QUIC protocol).
  5. Fleets of devices with tiny payloads and flaky links? Use MQTT.
  6. User may have the app closed? Add APNs/FCM. This is always a complement, never a replacement.
  7. Hostile network where only plain HTTP works? Fall back to long polling. Many libraries negotiate this automatically.
Interview tip Say which two or three you considered and why you picked one. "I would use SSE for the notification feed because it is one-directional and keeps standard HTTP infrastructure; for chat I would use WebSockets because the client sends constantly; for offline users I add push." That demonstrates tradeoff reasoning, not memorization.

6. Scaling stateful connections

The moment you hold connections open, your capacity planning changes. Stateless HTTP capacity is measured in requests per second. A real-time tier is measured in concurrent connections and in the messages per second flowing through them. Let us see what limits a single server.

6.1 Connections per server

Modern event-driven servers (Netty, Go, Node.js, Erlang/Elixir, Nginx, Envoy) use the operating system's scalable I/O notification (epoll on Linux) so that one thread can watch tens of thousands of sockets, waking only when one has data. The old model of one thread per connection collapses around a few thousand connections because of per-thread stack memory and context-switch cost. With the event-driven model, a tuned commodity server (say 8 to 16 cores, 16 to 64 GB of memory) can hold hundreds of thousands of mostly idle connections; the famous "C10K" and "C1M" benchmarks showed one million on a single box. In practice, production gateways run at 50,000 to 200,000 connections each, deliberately far below the maximum, for three reasons: when a server dies all its connections reconnect at once (a smaller blast radius means a gentler storm), a busy connection costs far more CPU than an idle one, and headroom is needed for deploys and spikes.

6.2 Memory per connection

An idle connection is not free. Rough accounting for one TLS WebSocket:

ComponentTypical costNotes

So 100,000 connections cost about 3 GB of memory. That is manageable, which is why real-time gateways are usually limited by CPU (TLS handshakes, message encoding, fan-out) or by bandwidth, not memory.

6.3 File descriptors and other limits

On Unix, each socket is a file descriptor. A process has a limit (ulimit -n), often defaulting to 1,024, and the system has a global cap (fs.file-max). A gateway must raise both well above the target connection count (for example 200,000 to 1,000,000). Other limits to tune: the size of the accept backlog, kernel connection tracking tables (conntrack) in NATs and firewalls that can fill up and silently drop new connections, and the ephemeral port range. The last is a trap on the load balancer to gateway hop: a single source IP can have only about 64,000 connections to one destination IP and port, because the connection is identified by the tuple of source IP, source port, destination IP, destination port. A reverse proxy opening 200,000 connections to one backend address needs multiple source IPs or multiple backend ports. Clients reaching the gateway directly do not hit this, because they come from many different IPs.

6.4 Load balancing long-lived connections

Load balancing (Chapter 9) works at connection granularity here, not request granularity, and that changes the tradeoffs:

  • Round robin spreads new connections, not load. Connections last hours. After a deploy or a scale-out, old servers keep their old connections while new servers sit empty. The fleet becomes imbalanced and stays so. Prefer least connections for new connections, and expect to occasionally shed connections from heavy servers (ask clients to reconnect gradually).
  • Stickiness is needed only for the lifetime of the connection, and a TCP connection is naturally sticky: once established, all its frames flow to the same backend. You do not need cookie stickiness for the WebSocket itself. But if you use long polling or fallback transports, consecutive requests of one session can land on different servers, so sticky sessions or a shared session store is required. Many libraries (Socket.IO) require sticky routing for their HTTP fallback.
  • L4 or L7. An L4 (TCP) balancer passes bytes through, supports enormous connection counts cheaply, and is the usual choice in front of gateways that terminate TLS themselves. An L7 (HTTP) balancer can route by path or header and terminate TLS, but it holds two sockets per client connection (client side and backend side), roughly doubling memory and descriptor use. At 10 million connections that doubling is real money.
  • Idle timeouts. Set the balancer's idle timeout longer than your heartbeat interval (for example 120 seconds against 30-second pings), or it will cut healthy connections.
  • Connection draining. Balancers must support removing a backend from rotation for new connections while existing ones continue, which section 13 relies on.

6.5 A connection gateway tier, separate from business logic

The most important architectural move is to separate the machines that hold connections from the machines that implement the product. A connection gateway (also called an edge or realtime server) does only a few things: terminates TLS, authenticates the handshake, keeps the socket alive with heartbeats, registers "user U is connected to me", decodes and forwards inbound messages to backend services, and writes outbound messages to the right socket. It contains no business logic about chat rooms, billing, or search.

Why split? First, deployment cadence: business logic changes daily, but every restart of a connection holder disconnects users. A thin gateway changes rarely, so connections survive most releases. Second, independent scaling: gateways scale with connection count and message volume; business services scale with CPU work. Third, blast radius and simplicity: a bug in message ranking cannot drop 100,000 sockets. Fourth, language and runtime fit: gateways are written in runtimes good at massive concurrency; business services use whatever suits the team.

Inbound traffic flows from gateway to business services over normal RPC or a queue. Outbound traffic (a service wants to send something to a user) is the harder direction, because the service does not know which gateway holds the user. That is the subject of the next section.

7. Routing a message to the server that holds the connection

Alice is on gateway G1. Bob is on gateway G3. Alice's message arrives at G1, passes to the chat service, and now somebody must write it to Bob's socket on G3. Gateways cannot talk to every other gateway directly (that is a fully connected mesh). Two components solve this together.

7.1 The connection registry

A connection registry is a fast key-value map from user id (or device id, or session id) to gateway id (and perhaps a connection id). Usually it lives in Redis (Chapter 15) or a similar store. When a connection is established and authenticated, the gateway writes user:bob -> G3 with a TTL (say 60 to 120 seconds) and refreshes it on every heartbeat. When the connection closes cleanly the gateway deletes the entry. If the gateway crashes, nobody deletes anything, but the TTL expires and the entry disappears on its own. That self-healing property is why you use TTLs and refresh, rather than relying on delete-on-disconnect.

One user may have several devices (phone, laptop, tablet), so the registry often maps a user to a set of device connections, for example a Redis hash conns:bob with fields per device. Registry entries can be stale: Bob may have reconnected to G5 a second ago while the old G3 entry lingers. Delivery code must treat the registry as a hint: the gateway that receives a message for a user it no longer holds must drop it or report "not here", and the sender falls back to the offline path (store and push, section 10).

7.2 The pub/sub backplane

The backplane is a message bus that every gateway is connected to. The simplest scheme: each gateway subscribes to its own channel, such as gw.G3. To deliver to Bob, a service reads user:bob -> G3 from the registry and publishes {to: bob, payload} on gw.G3. Only G3 receives it; G3 finds Bob's socket in an in-memory hash map and writes the frame. Each message costs one registry read and one publish, regardless of the number of gateways.

The alternative broadcast scheme skips the registry: publish every message on a channel all gateways subscribe to, and each gateway discards messages for users it does not hold. That is simple but multiplies traffic by the number of gateways, so it only suits small fleets or topic-based fan-out where most gateways have subscribers anyway.

A middle path for group messaging: gateways subscribe to topics for rooms that have at least one local member (room:42). The service publishes once to room:42, and every gateway with a member of that room receives one copy and fans it out to its local sockets. This reduces cross-gateway traffic from one message per member to one message per gateway holding members, which is critical for big rooms and live-event audiences.

A common and sound design uses both. The chat service writes the message durably first (to its database or a Kafka topic), so no accepted message can be lost. Then it uses Redis pub/sub (or a lightweight per-gateway queue) purely as a delivery hint to push it to online recipients. If the push is lost, the recipient picks the message up on reconnect from the durable store using its last sequence number (section 10). Thus the backplane may be lossy without compromising correctness. Redis Cluster pub/sub broadcasts messages across all nodes in classic mode, which limits scaling; sharded pub/sub (available in newer Redis versions) pins channels to shards. Say "I'd verify the throughput limits" rather than inventing numbers.

8. Delivery guarantees and ordering

Because a connection can break at any moment, a design must say precisely what it promises. Three guarantees are possible, discussed in detail in Chapter 32 (Chapter 32):

  • At most once: send and forget. Messages can be lost, never duplicated. Fine for typing indicators, cursor positions, and ephemeral presence.
  • At least once: the sender retries until acknowledged. Messages are never lost but can arrive twice. This is the standard for chat and notifications.
  • Exactly once (effect): you cannot get exactly-once delivery over an unreliable network, but you get exactly-once effect by combining at-least-once delivery with deduplication on the receiver.

8.1 Acknowledgments and sequence numbers

The mechanism is the same as TCP's idea lifted to the application. The server assigns each message in a conversation (or each user's inbox) a monotonically increasing sequence number. The sender attaches a client-generated message id so that retries of the same send can be recognized and de-duplicated by the server (an idempotency key). The recipient acknowledges the highest contiguous sequence number it has processed. The server keeps unacknowledged messages and re-sends them on timeout or on reconnect.

TCP guarantees ordered delivery within one connection, but not across reconnects, devices, or gateways. So ordering must be rebuilt: the client keeps the last sequence number it applied, ignores anything at or below it (duplicate), and if it sees a gap (receives 4015 after 4012) it knows it missed 4013 and 4014 and asks the server to resend from 4013. Sequences are assigned per conversation (or per inbox) by a single writer, for instance the database partition that owns that conversation, because a global counter would be a bottleneck, and ordering across unrelated conversations is not needed.

8.2 Reasons for out-of-order or duplicate delivery

Real systems produce disorder in several ways: two paths to the same client (live push on the socket versus a catch-up fetch after reconnect, racing each other), the backplane delivering concurrently from different publishers, and client retries after a timeout when the first attempt had in fact succeeded. The cure is always the same: let the sequence number be the source of truth, apply messages by sequence, and treat each message as idempotent so that seeing it twice is harmless.

Watch out A socket write succeeding does not mean the user received the message. The bytes may sit in a kernel buffer of a connection that is already dead. Only an application-level acknowledgment proves receipt. Mark messages "delivered" on ack, not on write.

9. Heartbeats, reconnects, and resume

9.1 Heartbeats and dead-connection detection

A heartbeat is a small periodic message. It has three jobs: keep intermediaries from closing the idle connection, let each side detect a dead peer, and (in the registry) refresh a TTL. Common settings: ping every 20 to 30 seconds, declare dead after missing two or three. The tradeoffs are straightforward. A shorter interval detects failures sooner and keeps NAT mappings alive, but costs battery on phones (each ping wakes the radio) and bandwidth and CPU at scale. A longer interval is cheaper but leaves dead connections, and "ghost" presence, around longer. Mobile carrier NATs often drop idle TCP mappings after about 5 minutes or sometimes less, so intervals longer than a few minutes are unsafe. Many mobile apps adapt: frequent heartbeats in the foreground, none in the background (relying on push notifications instead).

At 10 million connections with a 30-second heartbeat, the fleet receives 10,000,000 / 30 = about 333,000 pings per second, and the same number of pongs. Individually trivial, but it is real load and shows why the interval is a cost lever (the sizing example in section 16 uses this).

9.2 Reconnect with exponential backoff and jitter

Clients will lose connections constantly: tunnels, Wi-Fi to cellular handover, server deploys, load balancer resets. The client must reconnect automatically, but how it reconnects decides whether a small incident becomes a large one. The standard recipe:

  1. On unexpected close, wait a short base delay (for example 500 ms to 1 second), then try.
  2. On each consecutive failure, double the delay (exponential backoff) up to a cap (for example 30 to 60 seconds).
  3. Apply jitter: choose the actual wait randomly, for example uniformly between 0 and the current delay ("full jitter"). Without jitter, every client that lost its connection at the same instant retries at the same instants (1 s, 2 s, 4 s...), producing synchronized waves.
  4. Reset the delay only after a connection has stayed healthy for a while, not merely after the handshake succeeded, so a flapping server does not trigger a tight loop.
  5. Honor server hints: a Retry-After value, an SSE retry: field, or a close reason that says "do not reconnect for 60 s".

9.3 Resume: last event id and sequence numbers

After reconnecting, the client must not lose what happened in the gap, and the server must not resend everything. The client therefore tells the server where it left off. In SSE this is built in: the browser sends Last-Event-ID. In WebSockets you design it: the first message after the handshake is a resume request carrying the last sequence number per stream, for example {"type":"resume","since":4012}. The server replays from its durable store or a bounded replay buffer (for example the last N minutes of events kept in Redis streams or Kafka). If the gap is too large for the buffer, the server replies "gap too large", and the client does a full resync by fetching current state from a normal API (the snapshot), then continues live from the snapshot's sequence number. The combination of snapshot plus incremental stream is the robust pattern, because it handles both short blips and long absences with the same machinery.

One subtle point is to avoid the "lost update in the handoff" race: subscribe to live events first (buffering them), then fetch the snapshot, then apply buffered events whose sequence is higher than the snapshot's. Doing it in the other order risks missing an event that happens between the snapshot and the subscription.

10. Offline users and the durable path

A real-time channel is an optimization on top of durable storage, never the system of record. Every accepted message is stored first. If the recipient is online, push it; if the registry has no entry, do not wait: leave it in their inbox and send a mobile push notification (APNs/FCM) so the app can wake and sync. When the user opens the app, the client connects, sends its last sequence number, and pulls everything missed. This one rule, "durable write first, live push as best effort, resume from sequence on connect", makes the lossy parts of the pipeline (backplane, sockets, push vendors) safe, and is the core of chat designs (see the chat case study).

11. Presence and typing indicators

11.1 Presence

Presence is the "online / last seen" status next to a user's name. It sounds trivial and is surprisingly expensive, for two reasons: it must be detected reliably (a user who closes the laptop lid does not announce departure) and it must be fanned out to everyone who is watching that user.

Detection with heartbeat TTLs. Each live connection's heartbeat refreshes a key such as presence:bob with a TTL slightly longer than the heartbeat interval (for example heartbeat every 20 s, TTL 45 s). While Bob's client is alive the key keeps renewing. If the client vanishes, no refresh arrives, the key expires on its own, and Bob is now "offline" about 45 seconds after the last heartbeat. Explicit sign-off (a clean close) can delete the key immediately for a faster, more accurate result. The delay is a deliberate tradeoff: a short TTL tracks reality closely but flaps on transient network blips (users appearing to go offline and back online repeatedly); a longer TTL is steadier but shows ghosts. Many products add a grace period: on disconnect, wait 10 to 30 seconds for a reconnect before announcing "offline", which absorbs refreshes, page reloads, and tunnels.

With multiple devices, a user is online if any device is, so presence is computed from a set of per-device entries.

11.2 The fan-out cost

Detection is cheap. Distribution is not. If Bob has 500 friends and each is watching, every Bob status change must be sent to 500 clients. With 10 million users who each flap online/offline a few times per day, and an average of 200 watchers, the totals reach billions of presence events per day. Strategies to contain this:

  • Pull rather than push for most views. Show presence only for the people currently on screen (the open conversation or the visible part of the contact list). The client subscribes to presence of a few dozen users, not all friends, and fetches status in bulk when it opens a view.
  • Limit by audience. Do not broadcast presence for huge groups or public channels; show "n online" as an approximate count instead.
  • Coalesce and debounce. Collapse flapping within a short window; send at most one change per user per few seconds.
  • Lazy "last seen". Store last-seen time coarsely (minutes granularity) and update only when it changes meaningfully, to avoid writing the database on every heartbeat. Heartbeats go to Redis with a TTL, not to the primary database.
  • Subscribe via the backplane. A gateway subscribes to presence channels only for users that at least one of its local clients is watching, so presence events travel gateway-to-gateway only where needed.

Presence is explicitly best effort and eventually consistent. An approximate answer a few seconds stale is acceptable, which is why a cache with TTLs, not a transactional database, is the right store.

11.3 Typing indicators

"Alice is typing..." is the cleanest example of ephemeral data. It needs low latency, it is worthless a few seconds later, and losing one is harmless. So: send it over the existing socket with at-most-once semantics (no persistence, no acknowledgment, no replay on reconnect); throttle the sender (one "typing" event per 3 seconds while keys are pressed, not one per keystroke); and make the receiver expire it automatically after a few seconds, so a lost "stopped typing" does not leave a stuck indicator. Send it only within the active conversation, directly to the other participants (a one-to-one fan-out of a tiny message), and skip it entirely for large groups.

12. Backpressure and slow consumers

A gateway writes to thousands of sockets, and not all clients read at the same speed. A phone on a bad network may accept only a few KB per second. If the server keeps producing messages for that client faster than they drain, the data accumulates in the connection's outbound queue and in kernel buffers. This is the slow consumer problem. Left unchecked, a few slow clients consume gigabytes of memory, trigger garbage collection storms, and take the entire gateway down, harming healthy users. In event-driven servers, "write" typically means "copy into an application buffer and return", so nothing automatically pushes back on the producer.

Principles for handling it:

  • Bound every per-connection queue in both bytes and message count (for example 1 MB or 500 messages).
  • Choose a policy when the bound is hit. For state-like data (presence, a stock price, a game position), drop old messages or coalesce: only the latest value matters, so keep one slot per key and overwrite. For must-deliver data (chat), do not buffer without limit on the gateway; stop pushing and disconnect the slow client with a close code, trusting that the durable store and resume will repair the gap when it reconnects on a better network. Conflating "reliable" with "unbounded memory" is a common mistake.
  • Use the transport's signals. Check whether the socket is writable and the size of the pending write buffer before enqueueing; in Node.js this is bufferedAmount/backpressure on the stream, in Netty the channel's writability flag, in Go a bounded channel with a non-blocking send.
  • Isolate slow consumers from fast ones. Never let one blocked socket write stall a loop that serves others. Use per-connection queues and per-connection write timeouts.
  • Apply backpressure upstream too. If a topic or room produces more than recipients can absorb (a viral live event), batch or sample updates, lower the update rate (send a snapshot every 200 ms instead of every event), or shed low-priority traffic.
  • Limit inbound too. A malicious or buggy client can flood the gateway; enforce per-connection rate limits and maximum message size (see Chapter 16).

13. Deployment and draining of WebSocket servers

For stateless services, a deploy replaces servers one by one and nobody notices. For a gateway, restarting a server severs all of its connections. If you restart 100,000-connection servers carelessly, you create 100,000 simultaneous reconnects per server, which is the first step toward a reconnect storm (section 15). The goal is to move users off a server gradually and politely.

  1. Remove from rotation. Tell the load balancer to stop sending new connections to the old server (connection draining, "deregistration delay"). Existing connections stay.
  2. Announce. The server sends each client a "reconnect soon" message or close frame with code 1001 (going away), preferably with a hint of a random delay.
  3. Drain slowly. Close connections in batches over several minutes (for example 1 to 5 percent per second), not all at once. Each client reconnects, with jitter, to a different healthy server through the load balancer.
  4. Clean up. Delete this gateway's registry entries (or let TTLs expire) and unsubscribe from the backplane. Messages in flight are protected by the durable store plus resume.
  5. Hard deadline. After a maximum drain time (say 10 to 15 minutes), terminate the stragglers.

For a rolling deploy, replace only a small fraction of the fleet at once so that surviving servers have capacity for the connections moving over (with 10 percent of the fleet draining, the other 90 percent needs at least 11 percent headroom). In Kubernetes, this means a generous terminationGracePeriodSeconds, a preStop hook that starts the drain, readiness probes that fail early, and a maxUnavailable setting that is small. Blue/green is also viable: bring up a full new gateway fleet, direct all new connections to it, and let the old fleet drain on its own as clients churn, which takes longer but is the gentlest. Because gateways are thin (section 6.5), most releases touch business services and never need this procedure at all.

14. Security

Long-lived connections introduce security problems that short requests do not have. General treatment is in Chapter 55; these are the real-time specifics.

  • Check the Origin header on the upgrade. Browsers allow a page on any website to open a WebSocket to any host, and they automatically attach the user's cookies to the handshake for that host. That enables cross-site WebSocket hijacking: a malicious page makes a victim's browser open an authenticated socket to your service and read or send data as the victim. The same-origin policy does not protect WebSockets. The server must verify that Origin matches an allow-list, and use CSRF-style protections where cookies are the credential. Non-browser clients can forge Origin, so it is only a protection against browser-borne attacks, not a replacement for authentication.
  • Authenticate during the handshake, not after. Reject unauthenticated upgrades with 401 before allocating a long-lived connection. Browsers' WebSocket API cannot set an Authorization header, so options are: a session cookie (with Origin check and SameSite settings), a short-lived one-time ticket obtained from an authenticated HTTP endpoint and passed in the URL query once (it is single-use and expires in seconds, so leaking into logs is harmless), or a first-message authentication where the server drops the connection if no valid auth message arrives within a few seconds. Avoid putting long-lived bearer tokens in the URL.
  • Authorize every message and subscription, not only the connection. Being connected as Alice does not entitle you to subscribe to room:secret. Check membership on each subscribe and publish, server-side.
  • Token refresh on a long connection. Access tokens are short lived (minutes) but sockets last hours. Choices: validate once at connect and let the socket live on (simple, but a revoked or fired user stays connected); have the client send a fresh token over the socket periodically (for example every 10 minutes) and close the connection with an auth error if it lapses; or have the server track the token expiry and ask the client to refresh before it runs out. For revocation, the server needs a way to close specific users' connections quickly: publish a "kick user" event on the backplane that gateways act on.
  • Use TLS everywhere (wss://). Plain ws:// can be tampered with by intermediaries, and many networks block it.
  • Defend resources. Cap message size, per-connection message rate, connections per user and per IP, subscriptions per connection, and time allowed for the handshake and for authentication (to resist slowloris-style attacks that open many half-finished connections). Put DDoS protection (Chapter 55) in front, since each connection costs memory.
  • Validate and bound payloads: treat all frames as untrusted input; escape output to avoid injecting script into other users' pages.

15. Failure modes: reconnect storms and friends

15.1 Reconnect storms (thundering herd)

The signature failure of real-time systems. A gateway, a zone, or the load balancer fails and drops many connections at once. Every client reconnects. A reconnect is much more expensive than an idle connection: a TCP and TLS handshake (CPU-heavy public-key math), an authentication call to the identity service, a registry write, subscriptions, and a catch-up read of missed messages from the database. If thousands of clients do this simultaneously, the surviving gateways run out of CPU, the auth service and database overload, timeouts occur, clients that failed retry, and the retries add to the overload. The system can stay down even after the original fault is fixed, because the retry load alone exceeds capacity (a metastable failure).

Defenses, layered:

  • Client jitter and backoff (section 9.2), the most important single defense.
  • Admission control at the gateway: limit new handshakes per second (a token bucket); excess get a fast rejection with a Retry-After hint rather than queuing. Fast failure is cheaper than slow failure.
  • Cheap reconnect path: cache authentication results briefly or use signed tokens validated locally (no auth service call), serve resume from a replay buffer, and avoid per-connect database writes. Use TLS session resumption (tickets) so repeat clients skip the expensive full handshake.
  • Smaller blast radius: many gateways with moderate connection counts and spread across zones, so one failure displaces 1 to 2 percent of users, not 30 percent. Consider cell-based design (Chapter 42).
  • Load shedding and degradation: under storm, prioritize reconnects of active users, defer catch-up fetches, and temporarily disable non-essential features such as presence.
  • Server-directed spreading: when the server initiates the close (deploys), it includes a random delay for each client.

15.2 Other failure modes

  • Half-open connections: the peer died but your side never learned. Heartbeat deadlines clean these up; without them memory leaks until the file descriptor limit is hit.
  • Stale registry: entry points to a gateway the user left. Messages vanish into a gateway that no longer has the socket. Mitigate with TTLs, the gateway refusing unknown users and reporting back, and the durable store plus push as the backup path.
  • Registry or backplane outage: real-time delivery stops, but because messages are stored durably, clients that poll or reconnect still receive them. Degrade to slower catch-up (clients fall back to periodic fetch) rather than failing sends.
  • Hot rooms: one conversation with a million viewers makes one backplane channel and a few gateways do all the work. Shard the room's audience across gateways with per-gateway sub-channels and batch updates; send snapshots at a fixed rate instead of every event.
  • Gateway memory leak or GC pause: a pause longer than the heartbeat deadline makes every client think the server is dead. Watch pause times, and set the deadline above worst-case pauses.
  • Clock and ordering: never order messages by client timestamps; use server-assigned sequences (Chapter 27).
  • Proxy and middlebox interference: corporate proxies that strip Upgrade headers or buffer responses. Keep a fallback transport (long polling or SSE over plain HTTP) in the client library.

16.4 Failure scenario: lose a zone

One of three zones fails, taking 3.3 million connections with it. Without jitter: all 3.3 million clients reconnect within a couple of seconds, which is more than 1.5 million handshakes per second against about 100 surviving gateways. With full jitter spread over 60 seconds: 3,300,000 / 60 = 55,000 reconnects per second, or about 550 per surviving gateway. A TLS 1.3 handshake with elliptic-curve keys costs on the order of 1 ms of CPU (assume 2 ms with the surrounding work), so 550 per second consumes about 1.1 cores of a 16-core machine: very manageable. The real bottlenecks are elsewhere: the authentication service must handle 55,000 token validations per second (so use locally validated signed tokens), and catch-up reads of 55,000 users per second hit the message store (so rate-limit resume, bound the replay window, and prefer cached recent messages). The gateways must be sized to absorb the extra 3.3 million connections (150 gateways at 67,000 each with all three zones, 100 at 100,000 each in two zones, exactly what the headroom rule provided).

Result 10 million concurrent connections needs roughly 150 gateways (spread over three zones, 100,000 sockets each when one zone is down), about 300 GB of socket memory in total, a registry of about 1 GB across several shards, and a small pub/sub backplane. The cost drivers are connection state and failure headroom rather than raw message throughput.

17. Interview Q&A

Why can't I just use normal HTTP requests for a chat application?

HTTP request/response only lets the client initiate, so the server cannot deliver Bob's incoming message until Bob's client asks. You could make Bob's client ask every few seconds (short polling), but that wastes enormous request volume (most polls return nothing) and still adds delay equal to half the interval. Holding a connection open lets the server send instantly. That is why chat uses WebSockets, or long polling or SSE for receiving, with normal POSTs for sending if you want simpler infrastructure.

When would you choose SSE over WebSockets?

Choose SSE when data flows mainly from server to client: notifications, live feeds, dashboards, progress updates, streamed text. It runs over plain HTTP, so authentication, compression, logging, and load balancers work normally, and it gives automatic reconnect with a Last-Event-ID resume mechanism for free. WebSockets are better when the client also sends frequently and interactively (chat, games, collaborative editing), when you need binary data, or when you want one connection for both directions. If most of the traffic is downstream, SSE plus occasional POSTs is simpler to operate and has fewer ways to fail.

Explain how the WebSocket handshake works and why it starts as HTTP.

The client sends an HTTP/1.1 GET with Upgrade: websocket and Connection: Upgrade headers, a random Sec-WebSocket-Key, the protocol version, and the Origin. The server replies 101 Switching Protocols with Sec-WebSocket-Accept, which is a base64 SHA-1 of the key plus a fixed GUID, proving it understands WebSocket. After that the same TCP connection carries WebSocket frames. Starting as HTTP lets it use ports 80 and 443, pass through the existing firewalls and load balancers, and reuse cookie and header based authentication. It also gives the server a final chance to inspect the request, check Origin, and authenticate before committing resources.

You have 10 million connected users across many gateway servers. How does a message from one user reach another?

The sender's gateway forwards the message to a chat service, which first persists it and assigns a sequence number. The service then looks up the recipient in a connection registry (a fast key-value store, with TTL entries refreshed by heartbeats) to find which gateway holds the recipient's socket. It publishes the message to that gateway's channel on a pub/sub backplane such as Redis. The gateway looks up the socket in memory and writes the frame, and the client acknowledges it. If the registry shows no entry, the user is offline, the message stays in their inbox, and a push notification via APNs or FCM is sent. The durable write comes first, so a lost live delivery is repaired when the client reconnects and resumes from its last sequence number.

Why separate a connection gateway from the business logic services?

Connection holders are stateful: restarting one disconnects every user on it. Business logic changes often and needs frequent deploys, so mixing them would turn every release into a mass disconnect. A thin gateway that only terminates TLS, authenticates, tracks heartbeats, and moves messages changes rarely, so connections survive most deploys. It also lets you scale the two tiers independently (sockets and fan-out for gateways, CPU and data work for services), limits the blast radius of bugs, and lets each tier use the best technology for its job.

What happens when a client's network drops and it reconnects? How do you avoid losing or duplicating messages?

The server assigns each message a monotonically increasing sequence number per conversation or inbox, and the client remembers the last one it applied. On reconnect the client sends a resume request with that number (SSE does this with Last-Event-ID). The server replays everything after it from the durable store or a replay buffer, then continues live. The client ignores any sequence at or below what it has already applied, which handles duplicates, and detects gaps when numbers jump so it can request missing ones. For sends, the client attaches a unique message id so a retried send is deduplicated by the server. If the gap is too large to replay, the client fetches a fresh snapshot and continues from its sequence.

What is a reconnect storm and how do you prevent it?

It is the overload caused when many clients lose their connections at once (a gateway crash, a zone failure, a deploy) and all reconnect simultaneously. Reconnecting is expensive because of TLS handshakes, authentication calls, registry writes, and catch-up reads, so the surge overloads the survivors and the dependencies, causes failures, and the failures cause more retries, so the system can remain down after the original fault ends. Prevention starts with clients using exponential backoff with full jitter, then adds server-side admission control that rejects excess handshakes quickly, cheap reconnect paths (locally validated tokens, TLS session resumption, bounded replay), spreading disconnects during deploys, and a small blast radius via many gateways across zones.

How do you implement presence for millions of users without melting the system?

Detection is done by having each connection's heartbeat refresh a key with a TTL slightly above the heartbeat interval, in a fast in-memory store such as Redis. When heartbeats stop, the key expires and the user is offline, and a short grace period avoids flapping on brief disconnects. The expensive part is fan-out to watchers, which is multiplied by friends count and status-change frequency. To contain it, subscribe to presence only for users currently on screen, fetch statuses in bulk when a view opens, debounce rapid changes, skip presence in large groups in favor of approximate counts, and treat the data as best-effort and slightly stale instead of strongly consistent.

What is a slow consumer and what do you do about it?

A slow consumer is a client that reads from its socket more slowly than the server produces data for it, so outbound data piles up in memory on the gateway. Since a gateway serves many clients, a few of these can exhaust memory or stall loops and hurt everyone. The fix is to bound the per-connection outbound queue, and when it fills, apply a policy suited to the data: for state-like updates drop or coalesce old values and keep only the latest; for must-deliver messages stop pushing and disconnect the client, relying on durable storage and resume to deliver the rest when it reconnects. Also use per-connection write timeouts and keep one connection's blocking from stalling others.

How do you deploy new code to a WebSocket gateway fleet without dropping everyone?

You cannot avoid disconnects on the instances being replaced, but you can control the rate. First remove the instance from load balancer rotation so no new connections arrive, then tell clients to reconnect (a close frame with code 1001 or an application message), closing connections gradually in batches over minutes, each client reconnecting with jitter to healthy servers. Replace only a small fraction of the fleet at a time so the rest has headroom, and set a hard deadline for stragglers. Make gateways thin so they rarely need deploys, and use blue/green when you want the gentlest transition. The durable store plus resume means no messages are lost during the move.

What security issues are specific to WebSockets?

Browsers do not apply the same-origin policy to WebSocket connections and automatically send cookies in the handshake, so a malicious site can open an authenticated socket to your service on a victim's behalf (cross-site WebSocket hijacking). The server must validate the Origin header against an allow-list and use CSRF protections when cookies authenticate the user. Authentication belongs in the handshake, using a cookie or a short-lived single-use ticket rather than a long-lived token in the URL. Because connections outlive access tokens, you need a refresh strategy and a way to kick revoked users. You should also authorize every subscription and message, enforce size and rate limits, and use TLS.

Why use Redis pub/sub for routing but not as the system of record?

Redis pub/sub is fast and cheap for dynamic subscriptions, but it has no persistence or delivery guarantee: if a subscriber is briefly disconnected or the server restarts, messages published in that moment are gone. That is fine for a delivery hint on top of a durable store, since a missed push is recovered by resume from the sequence number. For the record of messages you use a database or a durable log such as Kafka, which supports replay and retention. Putting the durable write first and the pub/sub hint second gives low latency without risking correctness.

18. Recap

  • Request/response HTTP cannot push. The options are to ask often (short polling), hold the request (long polling), stream a response (SSE), or upgrade to a full-duplex socket (WebSocket). Choose the simplest one that meets the latency requirement.
  • SSE is one-way, text, plain HTTP, with built-in reconnect and Last-Event-ID. WebSockets are two-way and binary, started by a 101 upgrade, with frames, masking from client to server, ping/pong, and a close handshake, but with no built-in acknowledgments, ordering across reconnects, or routing.
  • WebRTC is for audio, video, and peer data over UDP with ICE, STUN, TURN, and SFUs. MQTT is lightweight pub/sub with QoS levels for devices. APNs and FCM reach apps that are closed, on a best-effort basis, and complement live connections.
  • Stateful connections change capacity planning: tens to hundreds of thousands per server, about 30 KB each, file descriptor and port limits, least-connections balancing, and heartbeat settings that outlast idle timeouts.
  • Split thin connection gateways from business services. Route with a TTL-based registry (user to gateway) and a pub/sub backplane (Redis for ephemeral hints, Kafka or a database for the durable record).
  • Persist first, then push. Use sequence numbers, acknowledgments, client message ids, and resume (snapshot plus incremental) to get at-least-once delivery with effectively-once results.
  • Reconnect with exponential backoff and jitter; protect the fleet with admission control, cheap reconnect paths, and a small blast radius to survive reconnect storms.
  • Presence is cheap to detect (heartbeat TTL) and expensive to fan out; typing indicators are ephemeral at-most-once messages. Bound outbound queues to handle slow consumers; drain gateways gradually on deploy.
  • Secure the handshake: Origin checks, authentication on upgrade, per-message authorization, token refresh, and limits. 10 million connections needs about 150 gateways, 300 GB of socket memory, and a modest registry and backplane.
