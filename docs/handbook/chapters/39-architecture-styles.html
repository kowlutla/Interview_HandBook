Architecture Styles and DDD

An architecture style is a repeatable way of dividing a system into parts and deciding how those parts may talk to each other. This chapter walks through the major styles (layered, hexagonal, clean, monolith through microservices, event-driven, serverless, BFF, pipes and filters, space-based, CQRS), then teaches domain-driven design, the main tool for deciding where the boundaries between parts should be, and finally how to keep an architecture healthy as it evolves.

1. Why styles exist, and how to choose one

Every program has a structure, even if nobody chose it. When many people work on the same code for years, the structure decides how fast they can change things, how often a change in one place breaks something far away, and how much it costs to run. An architecture style is a named, well-understood answer to the question "how do we divide this system into parts, and which parts are allowed to depend on which?" Because the answer has a name, a team can discuss it in one sentence ("we are a modular monolith with hexagonal modules") instead of re-explaining the whole design.

It helps to separate three scales at which the word "architecture" is used, because the styles in this chapter live at different scales and are often combined:

  • Inside one deployable unit (one process): layered, hexagonal, clean/onion, package by feature. These styles govern how the code is organised so it stays testable and changeable.
  • Between deployable units: monolith, modular monolith, SOA, microservices, serverless, space-based. These govern how many things you deploy and how they communicate.
  • How data and control flow: event-driven, pipes and filters, CQRS, BFF. These are patterns for the shape of interactions, and they apply at either of the two scales above.

A real system picks one choice from each scale. For example: an e-commerce backend might be a modular monolith (between units), with each module built hexagonally (inside a unit), publishing domain events (flow), and fronted by a BFF per client type. None of those choices contradicts another.

Key idea No style is "best". Each style buys some quality (testability, independent deploys, throughput, simplicity) by paying with another (operational cost, latency, consistency, learning curve). The interview skill is naming what a style costs, and choosing the cheapest style that meets the requirements you actually have, not the ones you imagine having in five years.

The forces that should drive the choice are usually these: the size and structure of the organisation (Conway's law, see section 15), the rate and independence of change in different parts of the product, the scaling shape (does one hot component need 100 times the capacity of the rest?), consistency needs (does a business rule need one atomic transaction across the data?), and operational maturity (is there a platform team, tracing, automated deploys?). Keep these five in mind; the rest of the chapter keeps returning to them.

2. Layered (n-tier) architecture

The oldest and most common style. The code is split into horizontal layers, each with a single responsibility, and a layer may only call the layer directly beneath it. A classic web application has four layers:

  1. Presentation: HTTP controllers, views, request parsing, response formatting. It knows nothing about SQL.
  2. Application / service: orchestrates a use case ("place an order"): start a transaction, call several pieces of business logic, send a notification.
  3. Domain / business logic: the rules of the business ("an order total is the sum of its lines minus discounts"; "a cancelled order cannot ship").
  4. Data access / persistence: turns objects into rows and back; talks to the database.

"Layered" and "n-tier" are related but not identical. Layers are a logical split inside code. Tiers are a physical split across machines or processes: a browser tier, an application server tier, a database tier. A three-tier deployment is usually a three-layer-or-more code base running on those separate machines. In conversation people use the words loosely; if the distinction matters, say "logical layer" versus "physical tier".

2.1 Why teams like it

Layering is easy to explain, matches how most frameworks are organised, and gives a clear place for each kind of code. It supports separation of concerns: a front-end developer can change a view without reading SQL. It is the default for CRUD-heavy line-of-business applications, and for small teams it is often entirely sufficient. Layers can also be scaled as tiers: stateless application servers behind a load balancer (Chapter 9) with a shared database behind them.

2.2 Where layered architecture hurts

  • Database-centric dependency. In the classic form the domain layer depends on the data access layer, so domain code ends up shaped by the table design and the ORM. You cannot test business rules without a database, or you must mock the persistence layer heavily.
  • The "sinkhole" anti-pattern. Many requests simply pass through layers that add nothing: the controller calls a service method that calls a repository method that runs a query. If most requests behave this way, the layers are ceremony. A little of it is normal; if 80 percent of calls are sinkholes, reconsider.
  • Horizontal slicing fights vertical features. A feature such as "add coupon codes" touches every layer, so one change edits files in four packages, and teams that own layers (a "UI team", a "DB team") must coordinate on every feature. This is the reason package by feature (section 15) exists.
  • Layer-skipping erodes the structure. Nothing in the language stops a controller from importing a repository. Without an automated check (section 16), strict layering decays into a tangle.
Interview tip If asked to design a typical web service, saying "layered" is fine for the internal structure, but follow it with one sentence on how you protect the domain logic from the database, such as the dependency inversion used by hexagonal architecture in the next section. It shows you know the limitation.

3. Hexagonal architecture (ports and adapters)

Alistair Cockburn proposed hexagonal architecture to fix the layered style's main weakness: the business logic depends on technical details. Instead of a stack with the database at the bottom, picture the application as a core in the middle, surrounded by the outside world. The core contains the use cases and the domain model. It does not know about HTTP, SQL, Kafka, or any vendor SDK.

The core talks to the outside only through ports, which are interfaces defined by the core in its own vocabulary. There are two kinds:

  • Inbound (driving) ports describe what the application can do: for example an interface PlaceOrder with a method place(command). Something outside "drives" the application by calling it.
  • Outbound (driven) ports describe what the application needs from the world: OrderRepository, PaymentGateway, Clock, EventPublisher. The core calls them without knowing what stands behind them.

An adapter is a piece of code that connects a port to a concrete technology. An inbound adapter (a REST controller, a Kafka consumer, a CLI command, a test) translates an outside request into a call on an inbound port. An outbound adapter (a JDBC repository, a Stripe client, an in-memory fake) implements an outbound port using a real technology. The hexagon shape has no meaning other than "more than four sides, so there is no top and bottom".

3.1 The dependency inversion that makes it work

Normally the high-level code (the business rules) calls the low-level code (the database), so the high-level code depends on the low-level code. Hexagonal architecture inverts this. The core declares the interface OrderRepository; the JDBC adapter imports that interface and implements it. Now the source-code dependency points from the adapter toward the core, even though at runtime the core still calls the adapter. This is the Dependency Inversion Principle, and it is the one idea that all of hexagonal, onion, and clean architecture share.

3.2 What you gain

  • Fast, honest tests. Because outbound ports are interfaces, tests inject in-memory fakes. The whole "place order" use case runs in milliseconds with no database, no network, no container.
  • Replaceable technology. Swapping a relational store for a document store, or a payment provider for another, means writing a new adapter; the rules are untouched. Be honest about this claim: it is valuable for the edges that really do change (payment vendors, notification channels), and less valuable for the database in a system that will never change it.
  • Multiple front doors. The same use case can be driven from REST, a message queue, a scheduled job, and a test, with identical behaviour.

3.3 What it costs

More files and more indirection: a port interface, an adapter, and often mapping code between the adapter's data shape and the domain's. For a thin CRUD service where no rules exist, this is overhead. Use it where there is real domain logic worth protecting, and keep it simple where there is not.

4. Clean architecture and onion architecture

Onion architecture (Jeffrey Palermo) and clean architecture (Robert C. Martin) are close relatives of hexagonal architecture. They draw the same idea as concentric rings and state it as a single strict rule: source-code dependencies point only inward. Inner rings know nothing about outer rings.

The rings, from the inside:

  • Entities: the most general business rules, which would exist even if the application did not. They change least often.
  • Use cases: the rules specific to this application ("transfer money, check the limit, write an audit record"). They orchestrate entities. A use case defines the input and output data shapes it needs as plain structures.
  • Interface adapters: convert between the shapes used by use cases and the shapes used by outer mechanisms: controllers turn HTTP into use case input; presenters turn use case output into view models; gateways implement repository interfaces.
  • Frameworks and drivers: the web framework, the database engine, the message broker, the UI toolkit. They are details. Martin's phrase is that the framework is "a detail" you plug in at the edge.

Watch out Clean architecture can be over-applied. Four rings and a mapper between each pair means a simple field addition touches six files. Apply the full ceremony to the complex core of the product, and let simple supporting areas be plain layered CRUD. Section 12 gives a principled way to decide which is which (core versus supporting subdomains).

5. Monolith, modular monolith, SOA, microservices

The previous styles organise code inside a unit. This section is about the number of deployable units and how they relate. Think of it as a spectrum from "one thing" to "very many things".

5.1 Monolith

A monolith is a single deployable unit: one build artifact, one process (replicated for scale), usually one database. This is not an insult. A monolith has the lowest latency (calls are function calls), the simplest consistency (one ACID transaction can span everything), the simplest debugging (one stack trace), and the cheapest operations (one pipeline to build and one thing to monitor). Its problems appear with scale of people more than scale of traffic: builds and test suites grow slow, any change requires redeploying everything, one team's bug can take down the whole process, and without internal boundaries the code becomes a "big ball of mud" where everything depends on everything.

5.2 Modular monolith

A modular monolith is still one deployable unit, but the code inside is split into modules with enforced boundaries. Each module has a small public API (an interface, a facade, or published events), and everything else in the module is private. Modules do not read each other's tables: each owns its own schema or set of tables, and other modules ask through the public API. The boundaries are checked automatically (section 16). The result: you keep monolith simplicity (one deploy, in-process calls, local transactions where truly needed) while getting most of the organisational benefit of services (teams own modules, changes stay local). It is also the ideal waiting room for later extraction: a module with a clean API and its own data can be lifted into a separate service with modest effort. This is why many experienced architects say "start with a modular monolith".

5.3 SOA

Service-oriented architecture, popular in the 2000s, split enterprise systems into coarse-grained services that expose reusable business capabilities, typically with SOAP/XML contracts and an enterprise service bus (ESB) in the middle handling routing, transformation, and orchestration. The aim was reuse across a whole company. In practice the ESB became a centralised, heavily configured bottleneck full of business logic ("smart pipes"), services were often large and shared a database, and releases were coordinated centrally. Microservices are best understood as a reaction: smaller services, each owning its data, independently deployed, "smart endpoints and dumb pipes" (plain HTTP or a message broker with no business logic in the transport).

5.4 Microservices

A microservice architecture splits the system into many small services, each built around one business capability, owning its own data store, deployable on its own, and communicating over the network. The payoff is independent deployability and independent scaling, which lets many teams move without coordination. The price is large: every call can fail or be slow; data is spread out, so there are no cross-service transactions (see sagas in Chapter 48); and you must operate service discovery, tracing, deployment automation, and more. This chapter keeps the treatment short on purpose. Module 7 owns the details, beginning with Chapter 44: Monolith to microservices and Chapter 45: Decomposition.

5.5 Decision criteria

Choose by the forces, not by fashion. Questions to ask, in the order they usually matter:

  1. How many engineers, in how many teams? Under about 10 to 20 engineers, one deployable unit almost always wins. Microservices solve a coordination problem among many teams; if you do not have that problem, you buy the cost without the benefit.
  2. Do parts need to deploy on different cadences? If checkout must ship daily and the reporting module monthly, and releasing together creates real friction, separate deployment has value.
  3. Do parts scale differently? If image processing needs 50 machines and everything else needs 3, extract that part. Otherwise a monolith scaled horizontally copies the whole thing, which is wasteful only if the hot part is much larger or has a different resource profile (CPU, memory, GPU).
  4. Do parts need different technology or isolation? A machine-learning inference step in Python next to a Java core, or a PCI-regulated payment component that must be isolated for compliance, are legitimate reasons.
  5. Are the boundaries known? Drawing service boundaries wrongly is expensive, because network contracts are hard to change. If the domain is new and still shifting, a modular monolith lets you move a boundary by refactoring instead of by migrating data between services.
  6. Is the operational platform ready? Automated CI/CD, centralised logging, distributed tracing, and on-call practice must exist before the second service, not after the twentieth.
Watch out The "distributed monolith" is the worst outcome: many services that must be deployed together, share a database, or call each other synchronously in long chains. You pay the network and operations cost of microservices and keep the coupling of a monolith. It is almost always caused by splitting along technical layers or by splitting before understanding the domain. Sections 12 and 14 use DDD to avoid it.

6. Event-driven architecture

In a request-driven (synchronous) design, service A calls service B and waits for the answer: A must know B exists, B must be up, and A is slowed by B. In an event-driven architecture, components communicate by events: immutable facts that something happened ("OrderPlaced", "PaymentCaptured"). A producer publishes an event to a broker and does not know or care who consumes it. Consumers subscribe and react in their own time. The mechanics of brokers and delivery guarantees are in Chapter 34 and Chapter 35, and the event-driven patterns in depth (event sourcing, outbox, choreography) are in Chapter 36. Here is the architectural view.

6.1 Three flavours people confuse

  • Event notification: a small event says only that something happened ("order 123 placed"). Consumers call back for details if needed. It is the loosest coupling but can cause chatty follow-up calls.
  • Event-carried state transfer: the event carries the data consumers need, so they can keep a local copy and never call the producer. This improves availability and latency but means copies can lag.
  • Event sourcing: the events are the system of record; current state is derived by replaying them. It is a persistence approach, not a requirement of event-driven design, and it is covered in Chapter 36.

6.2 Benefits and costs

Benefits: producers and consumers are decoupled in time (a consumer can be down and catch up later), in knowledge (the producer does not know consumers), and in scaling (consumers scale by partition independently). Bursts are absorbed by the broker. New features are added by adding consumers.

Costs: the system is eventually consistent: after the order is placed, inventory is not reserved yet, and users may see stale views. The flow of a business process is no longer visible in one place; it is spread across subscriptions, so debugging requires distributed tracing with correlation IDs. Events become a public contract: changing their shape needs versioning discipline. Delivery is typically at-least-once, so consumers must be idempotent (Chapter 32). Finally, "event-driven" can hide a tangle of implicit dependencies: nobody knows which of 40 consumers will break if a field is renamed.

6.3 When to choose it

Choose it when many independent reactions follow one fact, when producers and consumers have different availability or speed, when you want an audit trail, or when workload is bursty. Avoid it for flows needing an immediate answer and strong consistency (a user waiting for a yes/no on a payment authorization is better served by a synchronous call, perhaps with events used for the downstream effects).

7. Serverless and Function-as-a-Service

Serverless means you write functions or small containers and the cloud provider runs them on demand, with no servers for you to provision or patch. FaaS (Function as a Service, such as AWS Lambda, Google Cloud Functions, Azure Functions) is the compute form: you upload a function, bind it to a trigger (an HTTP request through an API gateway, a queue message, a file upload, a schedule), and the platform starts an instance when an event arrives, runs your code, and may stop the instance afterwards. Serverless also covers managed back-end services (managed queues, object storage, serverless databases) that scale and bill by use.

7.1 Cold starts

The platform keeps some function instances warm after use, but when there is none free (the first request, a burst beyond current capacity, or after idle time) it must create one. A cold start is the extra latency: allocate a sandbox (a micro-VM or container), download your code, start the language runtime, and run your initialisation code (load libraries, open connections). Typical cold starts range from tens of milliseconds for small functions in light runtimes, to a second or more for heavier runtimes with large dependency trees, and longer still if the function attaches to a private network. A warm start reuses a live instance and skips all this.

7.2 Limits you design around

  • Execution time limit. Functions have a maximum duration per invocation (on the order of minutes to 15 minutes depending on the platform). Long jobs must be split or run elsewhere.
  • Memory and CPU are coupled. You usually choose memory; CPU share scales with it. There are caps on memory, package size, and temporary disk.
  • Concurrency limits. Each concurrent request typically needs its own instance. Accounts and regions have a concurrency ceiling, and scale-out is fast but not instant. A traffic spike can exhaust the limit and cause throttling.
  • Payload size and protocol limits. Request and response bodies are capped; streaming and long-lived connections (WebSockets) usually need extra managed services.
  • Downstream pressure. A function can scale to thousands of instances instantly and overwhelm a relational database with connections. Use a connection proxy, a queue as a buffer, or reserved concurrency to cap fan-out.

7.3 State

Functions are stateless by contract: an instance may be reused or discarded at any time, and two requests may run on different instances. In-memory state may survive for a warm instance, which is useful as an opportunistic cache (reuse a connection, a loaded config) but must never be the only copy of anything. Durable state lives in external services: object storage, a key-value or document database, a queue. Workflows that need state across steps use an orchestration service (see Chapter 38) rather than one long-running function.

7.4 Cost model

You pay per invocation plus per unit of compute consumed (memory multiplied by duration, rounded to a small time unit), and you pay nothing when idle. Consider a function using 512 MB that runs 200 ms. Per-unit prices change over time, so reason in ratios: at low or spiky traffic (a webhook receiver that gets a few thousand calls a day) serverless is dramatically cheaper than an always-on server. At steady high traffic the equation flips: a function running at constant load 24 hours a day costs several times more than the equivalent compute rented as a container or virtual machine, because you are paying the provider's premium for elasticity you do not use. A rough break-even is found by computing the cost of the same sustained utilisation in both models. There are also hidden costs: API gateway charges per request, data transfer, logging volume, and the engineering cost of testing and observability across many small functions.

8. Backend for Frontend (BFF) and the edge

When one back end serves a web app, a mobile app, a partner API, and a smart TV, a single general-purpose API tends to fit none of them. Mobile wants small payloads and few round trips on poor networks; the web page wants a rich aggregate; a partner wants a stable, versioned, rate-limited contract. A Backend for Frontend is a thin server layer built for one specific client experience, owned by the team that builds that client. It calls the underlying services, aggregates and reshapes data, and returns exactly what its client screen needs.

8.1 BFF versus a general API gateway

The gateway (Chapter 11) is a shared component that handles cross-cutting concerns: authentication, rate limiting, routing, TLS, request logging. It generally contains no client-specific business shaping. A BFF is the opposite: it contains client-specific aggregation, field selection, and sometimes protocol translation (for example exposing GraphQL to the mobile app while the services speak REST). They are often used together, with the gateway in front of the BFFs, as in the diagram. GraphQL is a common alternative that lets a single flexible API serve many clients, at the price of query-cost control and caching complexity; a BFF per client remains simpler to reason about when clients are very different.

8.2 Pitfalls

  • Logic creep. If business rules migrate into BFFs, each client implements them differently. Keep BFFs to composition and presentation shaping; rules stay in domain services.
  • Duplication. Three BFFs repeat the same aggregation code. Accept some duplication, or extract a shared library carefully, rather than building a single BFF that serves everyone (which recreates the original problem).
  • Ownership. A BFF works best when the team that builds the client also owns its BFF, so a screen change does not wait for a back-end team.

8.3 The edge

"The edge" is everything between the user and your core: CDN points of presence (Chapter 12), the web application firewall, the API gateway, and increasingly edge compute, small functions run in the CDN's locations close to users. Edge compute is a serverless variant that suits request rewriting, A/B test assignment, authentication token checks, personalisation of cached pages, and geo-routing. Its limits are strict (short run time, small memory, limited data access), because the data lives far away in your regions. Architecturally, the edge is the place to terminate things that do not need to travel to your core.

9. Pipes and filters

In pipes and filters, processing is broken into independent steps (filters), each of which reads input, transforms it, and writes output. Pipes are the connectors that carry data from one filter to the next. The Unix shell is the classic example: cat access.log | grep 500 | sort | uniq -c. Each program does one small job and knows nothing about the others; the pipe is just a byte stream.

Why it works: each filter is testable alone, filters are reusable and recomposable, and the slowest filter can be scaled independently. It fits ETL pipelines, compilers (lex, parse, optimise, emit), image and video processing, log processing, and stream processing frameworks (Chapter 37). Weak points: it suits one-directional flows, not interactive request and response; error handling across stages is awkward (where does a bad record go? usually a dead-letter queue); sharing state between filters violates the style; and the intermediate data format becomes the contract every filter must agree on.

10. Space-based architecture and a CQRS preview

10.1 Space-based architecture

Space-based architecture (also called tuple space or cloud-style "in-memory data grid" architecture) targets the situation where the database is the bottleneck under extreme, spiky concurrency, such as ticket sales or an online auction at the moment of a launch. Instead of every request hitting a central database, the data is held in memory, replicated across a grid of processing units. Each processing unit contains application code plus an in-memory slice of the data. A virtual middleware layer provides messaging, data replication, and processing orchestration, and a data writer asynchronously persists changes to the database behind the scenes. Units are added and removed elastically, because each unit is self-sufficient.

Strengths: extreme elasticity and no database bottleneck on the hot path. Costs: significant complexity, data synchronisation and conflict handling across units, a risk of data loss if memory fails before the async write (so you need replication within the grid), difficulty running complex queries and reports over the whole dataset, and a small ecosystem of tools. It is a specialised choice; in interviews, mention it when you meet "huge spiky load on a small hot dataset", and note that caches plus queues (Chapter 13, Chapter 34) solve many such cases more simply.

10.2 CQRS preview

CQRS (Command Query Responsibility Segregation) means using different models for writing and reading. Commands change state ("place order") and go through a write model that enforces business rules. Queries read state ("show my orders with product names") and go to a separate read model, shaped and indexed for the screens that use it. The read model is updated from the write side, typically by events, so it is eventually consistent. Reasons to use it: reads and writes have very different load and shape; the read side needs denormalised views, search indexes, or a different store (a search engine, a cache); or the write model is rich with rules that you do not want contorted for reporting.

Keep a sense of proportion: CQRS adds a second model, a synchronisation mechanism, and lag. Many systems only need the lightweight form (a read replica or a few denormalised tables). It often pairs with event sourcing and domain events, which is why it is previewed here and developed in Chapter 36 and Chapter 46.

12. Domain-driven design: the strategic ideas

Domain-driven design (DDD), introduced by Eric Evans, is an approach for tackling complexity in the business logic of a system. The earlier sections told you what shapes of architecture exist; DDD helps you decide where the boundaries go and what is inside them. It has two halves: strategic design (the large-scale structure: bounded contexts, subdomains, context maps) and tactical design (the building blocks inside one context: entities, value objects, aggregates, and so on). Strategic design is the part that matters most for system design interviews.

12.1 Ubiquitous language

The central practice is a ubiquitous language: a precise vocabulary shared by developers and domain experts, used in conversation, documents, and the code itself. If the business says "a policy is bound when the premium is paid", the code has a method bind() on a Policy, not setStatus(3). The reason it matters is that most expensive software mistakes are misunderstandings, and a translation layer between "what the business says" and "what the code says" is where misunderstandings breed. When a developer and an expert use the same word, a disagreement becomes visible early. Note the important subtlety: the language is only consistent within a bounded context, which leads to the next idea.

12.2 Bounded context

The word "Customer" means different things to different parts of a company. To Sales, a customer is a lead with a pipeline stage and a sales rep. To Billing, a customer is a payer with a tax id, a payment method, and invoices. To Support, a customer is a person with tickets and a satisfaction score. Trying to build one Customer class that satisfies everybody produces a huge object with hundreds of fields, where every change risks breaking another department. DDD's answer: do not unify; instead, draw explicit boundaries. A bounded context is a boundary within which a particular model and its language are consistent and have precise meaning. Inside "Billing", Customer means payer. Inside "Sales", Customer means a lead or account. Same word, different models, and that is fine as long as the boundary is explicit.

A bounded context is a linguistic and model boundary, not automatically a deployment boundary. It can live as a module in a monolith or as a service. Its rule of thumb: one team, one model, one language, one codebase and, ideally, one owned data store.

12.3 Subdomains: core, supporting, generic

The domain is the whole problem space of the business. It divides into subdomains, which are areas of the business. This is a view of the problem; bounded contexts are the chosen parts of the solution. DDD classifies subdomains by their strategic value, which tells you how much design effort each deserves:

  • Core subdomain: what makes the business different and wins customers. For a ride-hailing company: matching riders and drivers and pricing. Invest the best people, use full DDD, build it in-house, and expect it to change often.
  • Supporting subdomain: necessary for the business but not a differentiator, and specific to your company, so you cannot buy it off the shelf. Example: driver onboarding workflow. Build simply, often plain CRUD; no need for elaborate modelling.
  • Generic subdomain: a solved problem that many companies share: authentication, payment processing, email delivery, invoicing, search. Buy or use an open-source product. Do not build.

This classification gives direct design advice: put your best engineering and the cleanest architecture (hexagonal or clean) into the core, accept simple layered code for supporting parts, and integrate generic ones through an adapter. It also answers "build versus buy" in a principled way.

12.4 Context maps

Bounded contexts must still work together. A context map is a diagram, plus a naming of the relationship between each pair of contexts, that records who depends on whom and how. The relationships matter more than the picture, because they reveal political and technical risk. The standard patterns:

  • Upstream and downstream. In any relationship one context is upstream (it influences the other: its changes ripple down) and the other downstream. Understanding who is upstream tells you who can force change on whom.
  • Shared kernel: two contexts share a small, explicitly agreed piece of model and code (for instance a common Money type or pricing rules). Both teams must coordinate any change to it. Use rarely and keep it tiny, because it couples the teams and can slide into a shared mutable ball of code.
  • Customer-supplier: the upstream (supplier) provides what the downstream (customer) needs, and the downstream's needs are taken into account in the upstream's planning, usually with negotiated, contract-tested interfaces. It is a healthy, cooperative relationship.
  • Conformist: the downstream has no influence on the upstream (a third-party API, another department that will not listen) and simply conforms to its model without translation. It is cheap and quick, but the downstream's model is now shaped by someone else's. Acceptable when the upstream model is good enough.
  • Anti-corruption layer (ACL): when the upstream model is poor or unstable (a legacy system, a vendor with odd concepts), the downstream builds a translation layer (facade, adapter, translator) so the foreign model never leaks inside. It is the hexagonal adapter at the context boundary. Costly to write but protects the domain; it is the standard tool when strangling a legacy system.
  • Open host service (with published language): the upstream exposes a well-documented, stable, general protocol for many consumers (a public API with a versioned schema) instead of custom integrations for each. The published language is the shared, documented model (an OpenAPI schema, a JSON schema, an event catalogue).
  • Separate ways: contexts decide not to integrate at all because the integration cost exceeds its value. Also a legitimate choice.
Interview tip When you draw boundaries in an interview, name the relationship on at least the two or three most important arrows: "Orders is a customer of Inventory; Billing talks to the legacy ERP through an anti-corruption layer". It turns a box diagram into evidence that you understand how teams and models interact.

13. DDD tactical building blocks

Inside one bounded context, DDD offers a small vocabulary of building blocks for rich business logic. Use them where rules are complex (the core subdomain), not everywhere.

13.1 Entities and value objects

An entity is an object defined by its identity, which persists through change. Two orders with identical contents are still different orders. An order keeps its order id as its status, lines, and address change over its life. A value object is defined only by its attributes: it has no identity, is immutable, and two with the same values are interchangeable. Money (100 USD), an address, a date range, a coordinate, an email address are value objects. You do not "change" a Money; you create a new one. Good value objects also contain their own validation and behaviour: Money.add(other) refuses to add different currencies. Prefer value objects wherever possible, because they are simple, safe to share, and carry rules; this also fights "primitive obsession" (passing raw strings and numbers everywhere and forgetting units).

13.2 Aggregates

An aggregate is a cluster of entities and value objects treated as one unit for changes, with one aggregate root that is the only entry point. The root enforces the invariants (rules that must always be true) for the whole cluster. For an Order aggregate: the root is Order; OrderLines are internal entities; the invariant "the total never exceeds the customer's credit limit, and lines must have positive quantity" is enforced by Order's methods. Outside code may not modify an OrderLine directly; it must call order.addLine(...), so the root can check the rule.

The practical rules of aggregate design:

  1. One aggregate per transaction. Update one aggregate in one database transaction. If a business operation must change two aggregates, make the second change eventually consistent via a domain event instead of a single transaction. This is what makes aggregates the natural unit for sharding and for service splitting.
  2. Keep aggregates small. A giant aggregate (a Customer containing every order ever) means every change contends for the same lock or version, and loading it is slow. Include only what an invariant needs. If two things do not have to be consistent at the same instant, they belong in separate aggregates.
  3. Reference other aggregates by id. This keeps boundaries clear and avoids loading half the database.
  4. Protect invariants in the root and make internal parts unreachable from outside.
  5. Concurrency: use optimistic locking with a version number on the root, so two concurrent updates to the same aggregate do not silently overwrite each other.

13.3 Domain events

A domain event records something meaningful that happened in the domain, named in the past tense in the ubiquitous language: OrderPlaced, PaymentCaptured, ShipmentDispatched. They are immutable. Within a context they let one aggregate announce a fact so that another reacts, which keeps aggregates small and decoupled. Across contexts, a subset of them becomes integration events published to a broker, forming the public contract (section 6). A reliable way to publish them is the outbox pattern: write the event to an outbox table in the same transaction as the state change, then relay it, so there is never a state change without its event (Chapter 36).

13.4 Repositories, domain services, factories

  • A repository makes persistence look like an in-memory collection of aggregates: orders.findById(id), orders.save(order). There is one repository per aggregate root, never per internal entity. The interface belongs to the domain (an outbound port); the database implementation is an adapter. This links DDD directly to hexagonal architecture.
  • A domain service holds domain logic that does not naturally belong to one entity or value object, such as TransferService coordinating two Account aggregates, or a pricing calculation spanning several objects. It is stateless.
  • A factory encapsulates complex creation so that an aggregate is born valid.
  • An application service (use case) sits outside the domain: it loads aggregates via repositories, calls their methods, saves them, and publishes events. It contains orchestration but no business rules.
Watch out The "anemic domain model" is the common failure: entities are bags of getters and setters, and all rules live in service classes. You then have a layered CRUD application wearing DDD vocabulary. If a class has no behaviour, it is probably not modelling anything; move the rules onto the aggregate that owns the data.

14. Finding boundaries: event storming and mapping to services

14.1 Event storming

Event storming (Alberto Brandolini) is a workshop technique for discovering the domain quickly. Developers, product owners, and domain experts gather around a very long wall with a large supply of sticky notes. The method runs in steps:

  1. Chaotic exploration: everyone writes domain events (orange notes, past tense: "Order Placed", "Payment Failed", "Parcel Delivered") and puts them on the wall in rough time order. Disagreements about names expose different mental models, which is the point.
  2. Timeline: events are ordered and duplicates merged. Gaps appear: "who actually decides the refund?"
  3. Add commands, actors, policies: a command (blue note: "Place Order") causes an event; an actor (small yellow note) issues it; a policy (lilac note: "whenever payment fails, notify the customer") is a reaction that triggers a new command. Hot spots (pink notes) mark confusion or conflict.
  4. Find aggregates: a cluster of commands and events that act on the same data, enforcing the same rules, suggests an aggregate (a pale-yellow note: "Order").
  5. Draw boundaries: where the language shifts (the word "account" changes meaning), or where the people who care about the events are different, draw a line: a candidate bounded context.

14.2 Mapping DDD to service boundaries

If you do decide to split into services, DDD gives the most defensible first guess: a bounded context is a good candidate for one service (or, early on, one module). Reasons: the context already has its own model and language, its own data, and an owning team, so most calls stay inside it and the contract to the outside is small. Splitting inside a context, with several services sharing one model, tends to produce chatty services and shared databases (the distributed monolith). Splitting across contexts follows natural seams.

Some practical refinements:

  • Aggregates are the smallest unit you may not split. One aggregate must live inside one service and one transaction. A service boundary that cuts through an aggregate forces a distributed transaction for what was a local invariant.
  • A context may be bigger than the right service. A large context can later be split into several services if scale or team size demands it, along sub-capability lines, but never across an aggregate.
  • Several small contexts can share one early deployment. Starting with one service per context is a ceiling on granularity, not a requirement to deploy that many things on day one.
  • Use the context map for integration style. An upstream/downstream pair with a customer-supplier relationship suggests a versioned API or event contract; an ACL suggests an adapter service; a shared kernel is a warning that the two may really be one context.
  • Align with teams. Aim for one team owning one or a few related contexts; this is Conway's law used deliberately (section 15).

The full methods for decomposition, including decomposition by business capability, by subdomain, and the strangler migration, are the topic of Chapter 45; the migration journey is in Chapter 44. This chapter gives the language they rely on.

15. Dependencies, coupling, cohesion, and package structure

15.1 Coupling and cohesion

Cohesion measures how strongly the things inside a module belong together. High cohesion means a module does one coherent job, and the code that changes together lives together. Coupling measures how much one module depends on the internals of others. Low coupling means a change in one module rarely forces a change in another. The aim is high cohesion inside, low coupling between. Every architecture style in this chapter is a different way of achieving it.

It helps to know kinds of coupling, from worst to best:

  • Content coupling: one module reads or writes another's internals or tables directly. The worst; a shared database is a large-scale example.
  • Common/shared-state coupling: modules share global or mutable state.
  • Data / contract coupling: modules share only a small, stable, explicit interface or message schema. This is the target.
  • Temporal coupling: A requires B to be available right now. Asynchronous events relax it.
  • Deployment coupling: A and B must be released together, a hidden cost in distributed monoliths.

Afferent coupling (how many things depend on me) and efferent coupling (how many things I depend on) give a useful instability measure: a module with many outgoing dependencies and few incoming is unstable and should change freely; a module with many incoming dependencies is stable and should change rarely, so stable modules should be abstract, and dependencies should point toward stability. This is the quantitative form of the dependency rule from section 4.

15.2 Public API versus internal modules

A module has two faces. Its public API is the small set of operations, types, and events other modules may use; it is a promise, versioned and changed carefully. Everything else is internal and free to change. Without this separation, "reuse" becomes accidental dependency on internals, and a refactor breaks distant code. Enforce it with tooling: in Java use module systems or package-private visibility and architecture tests; in other languages use access modifiers, workspace boundaries, or lint rules. A module should also own its data: other modules do not read its tables; they call its API or consume its events. Treat the module boundary as if it were already a network boundary, and extraction later is cheap.

15.3 Package by layer versus package by feature

Two ways to arrange folders:

Package by layerPackage by feature (or by component)
controllers/, services/, repositories/, models/, each holding code for every featureorders/, catalog/, billing/, each holding its own controller, service, repository, model

Package by feature is the foundation of a modular monolith: top-level folders are business modules, and inside each module you may still apply layering or hexagonal structure.

15.4 Conway's law

Melvin Conway observed that organisations design systems that mirror their own communication structure. Four teams building a compiler will produce a four-pass compiler. The consequence for architecture is practical: if your boundaries conflict with your team structure, the teams will win. The inverse Conway manoeuvre means structuring teams deliberately around the architecture you want, for example one stream-aligned team per bounded context, so the organisation produces the desired boundaries rather than fighting them.

16. ADRs, fitness functions, and evolutionary architecture

16.1 Architecture decision records

Architectural decisions are made once and then misunderstood for years: "why on earth did we pick this?" An architecture decision record (ADR) is a short, dated document capturing one significant decision, kept in the repository next to the code. A common template has these parts:

  • Title and status: proposed, accepted, deprecated, or superseded by a later ADR.
  • Context: the forces and constraints at the time (team size, traffic, deadlines).
  • Decision: what was decided, in a sentence or two.
  • Consequences: both the good and the bad, including the cost accepted and the conditions under which to revisit.
  • Alternatives considered: and why they were rejected.
ADR-014: Keep Orders and Billing in one deployable (modular monolith)
Status: Accepted (2026-03-02)
Context: 12 engineers, 3 teams. Boundaries between Orders and Billing
  still shifting. No platform team; on-call is shared.
Decision: Run as one deployable with separate modules and schemas.
  Modules talk only through public interfaces and domain events.
Consequences: (+) one pipeline, local debugging, cheap refactors.
  (-) shared release train, shared scaling. Revisit when team count
  exceeds 6 or Billing needs independent compliance audits.
Alternatives: split into services now (rejected: no tracing, no
  platform capacity).

ADRs are valuable because they record why, so later engineers can tell whether the reasons still hold. Supersede decisions rather than editing them, so history stays readable. Keep them short: a page, written in minutes.

16.2 Fitness functions

Diagrams and ADRs rot unless something checks them. An architectural fitness function is an automated test of an architectural property, run in the build pipeline like any unit test. Examples:

  • Dependency rules: a test that fails if any class in domain imports a class from infrastructure or a web framework; or if module billing imports internals of orders. Tools such as ArchUnit in the Java world, or dependency-cruiser and import-linter in other ecosystems, express these as code.
  • No cycles: fail the build if the module dependency graph contains a cycle.
  • Performance budget: a load test fails the build if the p95 latency of checkout exceeds 300 ms.
  • Coupling limits: fail if a service has more than N synchronous downstream dependencies.
  • Operational properties: chaos or restart tests asserting that the service recovers within a target time; a check that every service exposes health endpoints and trace headers.
  • Security and data rules: fail if a module reads another module's tables.

The principle: whatever you care about structurally, make it an executable test. That turns architecture from a wall poster into a guardrail, and it is what keeps the strict layering of section 2 from decaying.

16.3 Evolutionary architecture

No architecture is right forever, because requirements, traffic, and teams change. An evolutionary architecture is designed for guided, incremental change: rather than predicting the future, you keep the system easy to change and use fitness functions to guide it. Its practices include:

  • Defer irreversible decisions until the last responsible moment, and prefer reversible ones (a modular monolith is easier to unwind than ten services). Jeff Bezos' phrasing, "one-way and two-way doors", is a useful frame.
  • Small, frequent, safe changes through continuous delivery, feature flags, and automated tests.
  • Strangler fig migration: grow the new system around the old, routing slices of traffic one at a time until the old part can be removed (Chapter 44).
  • Anticipate change axes: put the abstraction (a port) where change is likely, such as payment providers, not everywhere.
  • Measure and revisit: let evidence (deploy lead times, incident rates, p99 latency) trigger the next architectural step, not fashion.
Key idea Start with the simplest structure that meets today's needs, put strong boundaries inside it, record decisions in ADRs, and protect the boundaries with fitness functions. Then you can move along the spectrum in section 5 when the evidence says so, at a cost you chose in advance rather than a crisis.

17. Worked example: evolving an e-commerce system through the styles

Follow one company, ShopCo, as it grows. The point is that the right style changes at each stage, and the earlier stage is not a mistake.

Stage 1: layered monolith (5 engineers)

ShopCo launches with one Rails or Spring-style application: controllers, services, ORM, one PostgreSQL database. Catalog, cart, orders, payments, and users are packages in one deployable. This is correct: five people need speed, one transaction can cover "create order, decrement stock, record payment intent", and there is one pipeline. Traffic is perhaps 20 requests per second at peak, trivially served by two instances behind a load balancer. The code is organised by layer, which is fine for now.

Stage 2: modular monolith (20 engineers)

Four teams now collide on the same files. Builds take 25 minutes, and an unrelated bug in promotions blocked a release. Instead of splitting into services, the team runs an event-storming session with the business, and finds contexts: Catalog, Orders, Payments, Identity. They reorganise to package by feature, define a public interface per module, and give each module its own schema (no cross-module joins; the "orders" module stores a product snapshot rather than joining to the catalog table). Modules communicate through public interfaces and in-process domain events (OrderPlaced), using an outbox table inside the same database. They add architecture tests (fitness functions) that fail the build if Orders imports Catalog internals. The core Orders module is rebuilt hexagonally with an Order aggregate and a repository port; Catalog stays simple CRUD (a supporting subdomain). They record the decision in ADR-014 (the example in section 16). Deploys remain one artifact, but teams now rarely touch each other's code.

Stage 3: extract the pieces with a real reason (60 engineers)

Black Friday traffic reaches 4,000 product searches per second against 150 order placements per second. Search load is 25 times order load, uses a different technology (a search engine, Chapter 22), and wants different scaling. It is extracted as a service fed by ProductChanged events: a CQRS-style read model. The Payments module wraps a third-party gateway (a generic subdomain) and is extracted behind an anti-corruption layer, partly for compliance isolation. Image resizing, which spikes when merchants upload catalogs, becomes a serverless function triggered by object-store uploads, scaling to zero between uploads. Orders and Identity remain in the core monolith, since their boundaries are still being learned and they need transactions. Events flow through a broker (Chapter 34). Notice what did not happen: not everything was split. Only parts with a clear force (scale shape, technology, compliance) were extracted.

Stage 4: services per context (150 or more engineers)

With many teams, deployment coupling to the core monolith becomes the main drag. Orders, Pricing, Inventory, Shipping, and Promotions become services, each owning its data, mapped one-to-one to bounded contexts. Cross-service flows such as "place order, reserve stock, capture payment" use choreographed events and a saga (Chapter 48) rather than a distributed transaction. Because mobile and web screens differ a lot, each gets a BFF behind the gateway (Chapter 11). A platform team supplies deployment, tracing, and service templates. Fitness functions in CI check contract compatibility, dependency cycles, and latency budgets. The Orders aggregate stays intact inside the Orders service, never split across two services.

18. Interview Q&A

Should a new product start as microservices?

Usually no. At the start the domain is poorly understood, so any service boundary you draw is likely to be wrong, and moving a boundary between services means migrating data and changing network contracts, which is far costlier than moving code between modules. A small team also lacks the platform (automated deploys, tracing, discovery) that microservices require. A modular monolith gives enforced boundaries and in-process simplicity, and it makes later extraction cheap. The exceptions are when you already know the boundaries from a prior system, or when a strong force (compliance isolation, a very different scaling profile) demands separation from day one.

What is the difference between layered and hexagonal architecture, and why does it matter?

In classic layered architecture, dependencies run top to bottom, so the domain logic depends on the persistence layer and is hard to test or evolve without the database. In hexagonal architecture the core defines ports (interfaces) in its own terms, and adapters for HTTP, databases, and vendors implement or call them, so source dependencies point inward toward the core. The consequence is that you can test the whole use case with fakes in milliseconds and swap technology at the edges without touching the rules. The price is extra interfaces and mapping code, so I would apply it to a complex core domain and keep it plain layered for simple supporting CRUD.

What is a bounded context and how does it relate to a microservice?

A bounded context is an explicit boundary inside which one domain model and one language are consistent: "Customer" means a payer in Billing and a lead in Sales. It is a model and language boundary, not necessarily a deployment boundary; it may be a module or a service. A bounded context is the best first candidate for a microservice because its model, data, and team are already cohesive, so cross-boundary traffic is small. Splitting within one context usually produces chatty services sharing data, while splitting across contexts follows natural seams. Also never split an aggregate across services, since that turns a local invariant into a distributed transaction.

What is an aggregate, and why do you keep aggregates small?

An aggregate is a cluster of entities and value objects that must be consistent together, guarded by a single root that enforces invariants, and saved in one transaction. Aggregates are kept small because the aggregate is also the unit of locking and concurrency: a large aggregate means many users contend for the same version, loading is slow, and the transaction grows. You include only what a true invariant requires, reference other aggregates by id, and let anything that can be eventually consistent update through domain events. This also gives you natural partition keys for sharding and the smallest safe unit for later service splitting.

Explain core, supporting, and generic subdomains and why the distinction helps.

The core subdomain is what differentiates the business and wins customers, such as matching and pricing for a ride-hailing company. Supporting subdomains are necessary and company-specific but not differentiating, such as internal onboarding workflows. Generic subdomains are solved problems like authentication, email, or payments processing. The distinction directs investment: build the core in-house with your best people and rich modelling, keep supporting parts simple, and buy or adopt generic ones behind an adapter. It prevents the common mistake of spending months building a bespoke identity system while the real competitive logic remains an afterthought.

When would you use an anti-corruption layer versus being a conformist?

A conformist adopts the upstream's model directly because the upstream is good enough and you cannot influence it; it is cheap and fast but couples your model to theirs. An anti-corruption layer translates the upstream model into your own so the foreign concepts never leak into your domain. I choose an ACL when the upstream is a messy legacy system, a vendor with awkward concepts, or an unstable API, and especially when the area is part of my core domain. I accept being a conformist when the upstream model is clean, stable, and the area is peripheral, since the translation code would cost more than it protects.

When is serverless a bad choice?

It is a poor fit for steady, high, predictable load, because always-busy functions cost several times more than equivalent containers or virtual machines. It is also risky for latency-critical paths where cold starts hurt the tail latency, for long-running jobs that exceed execution time limits, and for workloads that need heavy in-memory state or special hardware. Another trap is scaling too well: thousands of concurrent instances can exhaust database connections, so you need a proxy, a queue buffer, or reserved concurrency. It shines for spiky, event-triggered, and scale-to-zero workloads such as file processing, webhooks, and scheduled glue.

What is the difference between a BFF and an API gateway?

An API gateway is a shared entry point handling cross-cutting concerns such as authentication, rate limiting, TLS, and routing, with no client-specific business shaping. A Backend for Frontend is a thin server built for one client experience, owned by that client's team, that aggregates calls to several services and shapes the response for that screen: fewer round trips and smaller payloads for mobile, richer aggregates for web. They are complementary, with the gateway commonly in front of the BFFs. The main risk is business rules creeping into the BFFs, so each client implements them differently; rules should stay in the domain services.

How do you stop an architecture from decaying over time?

Write the intended structure down as decisions in ADRs, so the reasoning is preserved, and then encode the structural rules as automated fitness functions that run in the build. Examples are tests that fail when the domain imports infrastructure, when modules form a dependency cycle, or when one module reads another's tables, plus performance budgets in load tests. This works because reviewers cannot catch every violation by eye, while a failing build is immediate and objective. Combine this with ownership by team (Conway's law) and a regular review to supersede ADRs when the forces change.

How does CQRS relate to event-driven architecture and DDD?

CQRS separates a write model that enforces business rules (the aggregates and commands of DDD) from one or more read models shaped for queries. The usual way to keep the read models current is by publishing domain events from the write side, which is event-driven architecture, so read models are eventually consistent. It pays off when read and write loads or shapes differ strongly, for example a normalised order write model and a denormalised search index for browsing. It is not required for every system; a read replica or a few denormalised tables often suffices, and the extra lag and moving parts must be justified.

What is a distributed monolith and how do you avoid one?

A distributed monolith is a set of services that cannot be deployed or scaled independently because they share a database, call each other in long synchronous chains, or must be released together. It combines the network, latency, and operations costs of microservices with the coupling of a monolith. It usually results from splitting by technical layer, splitting before the domain is understood, or cutting through aggregates. You avoid it by drawing boundaries around bounded contexts, giving each service its own data, preferring asynchronous events across boundaries, enforcing contracts with tests, and starting from a modular monolith so the boundaries are proven before the network is introduced.

19. Recap

  • Styles live at three scales: code structure inside a unit (layered, hexagonal, clean, package by feature), number of deployables (monolith to microservices, serverless, space-based), and interaction shape (event-driven, pipes and filters, CQRS, BFF). Real systems combine one of each.
  • Layered is simple but tends to make the domain depend on the database; hexagonal, onion, and clean fix this with dependency inversion and the single rule that source dependencies point inward.
  • Choose the deployment style by team size, deploy independence, scaling shape, boundary certainty, and operational maturity. A modular monolith is the strong default; microservices solve a many-team coordination problem and cost latency, consistency, and operations.
  • Event-driven decouples in time and knowledge but costs eventual consistency, traceability, and contract discipline. Serverless is great for spiky, event-driven work and poor for steady load, with cold starts, limits, statelessness, and per-use pricing as the key facts.
  • BFFs give each client its own shaped API behind a shared edge; pipes and filters fit one-way processing; space-based serves extreme spiky load on hot data; CQRS separates write and read models.
  • DDD strategic design: ubiquitous language, bounded contexts, core/supporting/generic subdomains, and context maps with named relationships (shared kernel, customer-supplier, conformist, anti-corruption layer, open host). Tactical design: entities, value objects, small aggregates guarded by a root, domain events, repositories.
  • Map bounded contexts to modules or services, never split an aggregate, and align contexts with teams (Conway's law).
  • Keep high cohesion and low coupling, expose a small public API per module with data ownership, and prefer package by feature.
  • Record decisions in ADRs, enforce structure with fitness functions, and evolve in measured steps, extracting only what has a concrete force behind it.
