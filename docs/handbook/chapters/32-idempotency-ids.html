Idempotency, Delivery Semantics and ID Generation

In a distributed system a request can be sent twice even though the user only meant it once, and every record needs an identifier that no two machines ever hand out twice. This chapter explains why duplicates are unavoidable, how idempotency keys and consumer-side deduplication make them harmless, and how production systems generate unique IDs (auto-increment, UUIDs, ULID, Snowflake, ticket servers, short URL codes) without a central bottleneck.

1. Why retries create duplicates

Start with the simplest scenario. A mobile app sends POST /payments to charge a customer 50 dollars. The server receives the request, charges the card, writes the payment row, and sends back 201 Created. Somewhere on the way back, the response is lost: the phone went through a tunnel, a load balancer dropped the connection, or the client's timeout (say 5 seconds) expired a moment before the reply arrived. The client now holds a single piece of information: "I did not get an answer."

That sentence hides three completely different realities, and the client cannot tell them apart:

  1. The request never reached the server. Nothing happened. Retrying is correct.
  2. The server received it, started working, and crashed before finishing. Maybe nothing was committed, maybe half of it was. Retrying is probably correct.
  3. The server completed everything, and only the acknowledgement (the "ack") was lost. Retrying will do the work a second time. The customer is charged twice.

The client has to choose between two bad options. If it retries, it risks a duplicate in case 3. If it gives up, it risks a lost operation in cases 1 and 2. There is no third option available from inside the client, because the network gives no way to distinguish a slow reply from a missing one. This is a restatement of a classic result: you cannot tell a crashed or unreachable peer from a slow one (see Chapter 27 on failure detection).

1.1 Where duplicates come from in real systems

Duplicates are not an exotic bug. They are the normal output of reliable design. Every layer that tries to be reliable adds retries, and every retry is a potential duplicate:

  • Client retries: mobile SDKs, browsers with a "resubmit" prompt, a user double-clicking a Pay button, or an impatient user pressing it again.
  • Proxy and gateway retries: load balancers and service meshes often retry automatically on connection resets or 503 responses (see Chapter 9 and Chapter 40).
  • Message broker redelivery: a queue hands a message to a consumer; if the consumer crashes before acknowledging, or the ack is lost, the broker delivers it again, possibly to a different consumer.
  • Producer retries: a service publishes an event, the broker's ack is lost, the producer publishes again, and the log now contains the event twice.
  • Workflow and job engines: a worker's lease expires while it is slow (a long garbage collection pause, say), the scheduler assigns the same task to another worker, and now two workers run it.
  • Replays and backfills: an operator replays a day of events after a bug fix, deliberately re-sending messages that were already processed.
  • Webhooks: a third party such as a payment provider will resend a webhook until it receives a 2xx, so your endpoint will see the same event several times by design.
Key idea You cannot prevent duplicate delivery in an unreliable network while also guaranteeing delivery. Since you want delivery to be reliable, the realistic goal is to make duplicates harmless. That property has a name: idempotency.

2. Delivery semantics: at-most-once, at-least-once, exactly-once

When one component sends a message or command to another over an unreliable link, the sender can choose how to behave when it does not hear back. The three possible policies are called delivery semantics.

2.1 At-most-once

The sender transmits once and never retries. If the message is lost, it stays lost. Each message is processed zero or one times, never more. This is "fire and forget". It is the right choice when losing a message is cheap and duplicates are costly or meaningless: a metrics sample, a heartbeat, a UDP-based game position update, a log line you can afford to drop. It has the best latency and the simplest implementation, but it cannot be used for anything where loss matters, such as payments.

2.2 At-least-once

The sender keeps retrying until it receives an acknowledgement. Nothing is lost (assuming the sender itself survives or the message is durably stored), but a message may be delivered and processed more than once, exactly the scenario in section 1. Most real messaging systems default to this: SQS standard queues, RabbitMQ with manual acks, Kafka consumers that commit offsets after processing, HTTP clients with retry. It is the practical baseline for reliable systems. The cost is moved to the receiver, which must tolerate duplicates.

2.3 Exactly-once: what it really means

"Exactly-once delivery" means every message has its effect applied exactly one time, never lost and never duplicated. As a property of the network this is impossible to achieve in the general case, because of the lost-ack problem: the sender can never know whether the last attempt landed. (This is a close cousin of the Two Generals problem.) A broker advertising "exactly-once" is therefore never promising that a message crosses the wire once. What it can legitimately promise is exactly-once processing effect: although the message may be delivered several times, the visible outcome is as if it were processed once.

The formula that engineers use is:

at-least-once delivery  +  idempotent (or deduplicating) processing  =  effectively-once

That is the only recipe that works across arbitrary systems. Everything marketed as exactly-once is an implementation of this formula inside some boundary.

2.4 Kafka: idempotent producer and transactions, in concept

Apache Kafka is the best-known system that offers "exactly-once semantics", and it is worth understanding what it actually does (the broker itself is covered in Chapter 34). There are two building blocks.

The idempotent producer. When enabled (and it is the default in recent Kafka versions), the broker assigns each producer a producer ID. The producer stamps every record batch sent to a given partition with an increasing sequence number. The broker remembers the last sequence numbers it accepted for each producer and partition. If a retry arrives with a sequence number the broker has already written, the broker discards it and returns success. If a sequence number skips ahead, the broker rejects it, because that signals a gap. The effect: producer retries after lost acks cannot create duplicate records in a partition's log. The guarantee is scoped to one producer session writing to one partition; if the producer process restarts and gets a new producer ID, the broker cannot connect the old and new sessions.

Transactions. A producer configured with a stable transactional.id can write to several partitions and topics atomically: either all records become visible or none. Crucially, it can include the consumer offsets in the same transaction. This enables the "consume, process, produce" loop: read a record from input topic A, compute a result, write it to output topic B, and commit the offset of A, all as one atomic unit. If the application crashes in the middle, the transaction aborts, the output is never seen by consumers that read with isolation.level=read_committed, and the input is re-read and re-processed after restart. Observed from outside, each input record affected the output exactly once. Transactional producers also fence out "zombie" instances with the same transactional id by using an epoch number.

Watch out Kafka's exactly-once covers data that stays inside Kafka (topic to topic, with offsets stored in Kafka). The moment your consumer calls an external system, such as sending an email, charging a card, or writing to a database, Kafka's transaction cannot undo or deduplicate that side effect. For external effects you still need idempotency keys or a dedup table on the receiving side. An interviewer who hears "I will use Kafka exactly-once" for a payment flow will immediately ask what happens at the database write.

3. Idempotency: definition and examples

An operation is idempotent if performing it many times has the same effect on system state as performing it once. In math: f(f(x)) = f(x). The important word is effect on state. The response may differ between the first and later calls (the second call might say "already done"), but the state of the world after N calls equals the state after one.

3.1 Naturally idempotent versus not

OperationIdempotent?Why
SET balance = 100, PUT /users/42 with a full bodyYesThe result is the same regardless of how often it runs. It writes an absolute value.
DELETE /users/42Yes (state-wise)After the first call the user is gone; later calls leave it gone. The response may change from 200 to 404, but the state is identical.
Reading data, GETYes (and safe)No state change at all.
INSERT ... ON CONFLICT DO NOTHING with a deterministic keyYesThe second insert hits the unique key and is ignored.
balance = balance + 50, "increment counter"NoEach execution changes the result. Two runs add 100.
POST /payments, "create new order", "send email"NoEach call creates a new thing with a new identity.
append item to listNoThe list grows with each repeat.

Notice the pattern: operations that describe a target state ("make it be 100") are idempotent, while operations that describe a change ("add 50") or create something new are not. HTTP encodes this convention: GET, PUT, DELETE, HEAD and OPTIONS are defined as idempotent, POST and (in general) PATCH are not (see Chapter 5). The definition is a promise by the API designer, not enforced by the protocol, so your PUT implementation must really be idempotent.

3.2 Making a non-idempotent operation idempotent

Three techniques cover most cases:

  1. Convert the change into a target state. Instead of "add 50 to balance", record "payment P-123 of 50 was applied" and compute the balance as the sum of payments. Applying P-123 twice does nothing the second time, because the row already exists. Ledger-style designs work this way.
  2. Attach an identity to the operation and remember it. Every attempt carries the same operation ID, and the receiver records which IDs it has already processed. This is the idempotency key, the main subject of the next section.
  3. Make the operation conditional on the current state: "set status to SHIPPED only if status is PAID" or "update only if version is 7". A repeat finds the precondition false and does nothing (section 5).

4. Idempotency keys: design in depth

An idempotency key is a unique token that the client attaches to a request to say "all attempts that carry this token are the same logical operation". The server uses it to detect that a request is a retry and, instead of redoing the work, returns the result of the first attempt. Stripe popularised the pattern in its public API with an Idempotency-Key header, and it has since become the standard approach for payment, order and booking APIs.

4.1 Who generates the key, and what it looks like

The key is generated by the client, not the server. This is essential: if the server generated it, the client would have to call the server first to get a key, and that first call could itself be duplicated. The client creates the key before the first attempt, stores it with the pending operation, and reuses the same key on every retry. A random UUID (version 4) is a typical choice; for UI forms, a key generated when the form is rendered works well, because a double-click or a page resubmit then carries the same key. The key must have enough entropy that two different logical operations never collide, which is why one uses 122 random bits (a UUID) rather than a timestamp.

Important: a new logical action must get a new key. If a client mistakenly reuses a key for a different payment, the server will think it is a retry and return the first payment's response. This is the single most common integration mistake and is why servers check the request fingerprint (4.3).

4.2 Scope

Keys must be namespaced. The same string from two different customers must not collide, so the store key is usually (tenant or account id, endpoint or operation name, idempotency key). Scoping per account also prevents one customer from probing for another's keys, and prevents a malicious client from "poisoning" a key that a victim might later use. Some APIs scope per user and per route, so the same key used on /payments and /refunds does not conflict.

4.3 The request fingerprint

Along with the key, the server stores a fingerprint: a hash of the request's essential content (method, path, body, relevant parameters). When a request arrives with a known key, the server compares fingerprints. If equal, it is a genuine retry. If different, the client has reused a key for a different request, and the server must refuse with an error (Stripe returns an error describing that the key was used with different parameters) instead of silently replaying the old answer. Without this check, a bug in the client can cause one customer's order to be answered with another's response.

4.4 Storage

The key store maps key to {fingerprint, state, response status, response body, created_at}. Where does it live?

  • In the same database as the business data. This is the strongest option. The key row and the business rows are written in the same transaction, so either both exist or neither does. A crash can never leave the work done but the key unrecorded (which would allow a duplicate) or the key recorded but the work not done (which would make retries return a false success). Use this whenever the operation is a local database change.
  • In a fast external store such as Redis. Cheaper and faster, using SET key value NX EX ttl for the atomic claim (see Chapter 15). The weakness is that the key store and the business database are two systems, so there is a window between "did the work" and "recorded the result" in which a crash causes a duplicate on retry. This is acceptable for low-stakes operations, and unacceptable for money unless the downstream operation is itself idempotent.

4.5 TTL: how long to remember

Keys cannot be stored forever, because the store would grow without bound. A time to live is chosen to cover the longest plausible retry window: how long the client might keep retrying plus a safety margin. Stripe, for example, documents that keys can be removed after at least 24 hours. A mobile client that queues operations while offline for a day needs a longer TTL than a server-to-server call that gives up after 30 seconds. Once the key expires, a retry would be treated as brand-new, so the TTL is a contract: "retries are safe for N hours". Document it in the API.

4.6 Concurrent duplicates and in-flight requests

The hard case is not the sequential retry (first request finished, then the second arrives). It is the concurrent duplicate: the client times out at 5 seconds while the server is still working on the first request (it takes 8 seconds), the client retries, and now two copies are in flight at the same time. If both check "is key present?" before either writes it, both proceed. The fix is an atomic claim: insert the key row with state IN_PROGRESS using a unique constraint or SET NX. Exactly one request wins the insert. For the loser, there are two designs:

  • Reject fast: return 409 Conflict (or 425/429 depending on the API) with a message "a request with this key is in progress; retry shortly". The client's retry logic backs off and tries again, by which time the first request has likely finished and the retry gets the stored response. Simple and stateless.
  • Wait and replay: the second request blocks (polling the key row or waiting on a lock) until the first completes, then returns the same stored response. A friendlier client experience, but it holds a connection and thread, and it needs a timeout.

Also handle crashed first attempts. If the first server dies after claiming the key and before completing, the row would stay IN_PROGRESS forever and block every retry. The remedy is a lock expiry (a "lease"): the IN_PROGRESS row carries a timestamp, and after, say, 60 seconds a retry may take over. The work itself must then be safe to resume or redo, which is why the local transaction approach (all or nothing) is easier than multi-step external workflows.

4.7 Storing the response

For a true replay, the server stores the status code and body of the first completed response and returns exactly those on later attempts, even if the underlying data has since changed. That way the client cannot tell the difference between the original and the retry, which is the whole point. Should errors be stored too? Stripe saves the result of the first request regardless of success or failure, including 500 errors, so that behaviour is deterministic. A reasonable middle path: store definitive outcomes (success, or validation errors that will not change) and do not store transient failures (a 503 from a dependency, timeouts), so the client can retry with the same key and get a real attempt. Be explicit in your design about which class each failure belongs to.

Interview tip When you add a payments or order-creation API on the whiteboard, volunteer the idempotency key before being asked. Say it in this order: client generates the key, server atomically claims it with a unique constraint in the same transaction as the business write, stores the fingerprint and response, returns the saved response on retries, and expires keys after about a day. That sequence shows you know the failure mode and the details.

5. Implementation patterns for deduplication

An idempotency key tells you what to deduplicate on. The patterns below are how the storage layer enforces it. They apply equally to API requests and to message consumers.

5.1 Dedup table with a unique constraint

Create a table processed_keys(key PRIMARY KEY, created_at). In one database transaction, first insert the key, then perform the business change. If the key already exists, the database raises a unique-violation error, you roll back (or treat it as "already done") and return the saved result. Because the constraint is enforced by the database engine under its own locking, even two simultaneous transactions with the same key cannot both succeed: one blocks on the other's uncommitted insert and then fails. This is the workhorse pattern. It works with any relational store and is the simplest to reason about. The cost is one extra indexed write per operation and a table that must be pruned.

5.2 Conditional writes

Many stores support "write only if". DynamoDB has condition expressions (attribute_not_exists(pk)), Cassandra has lightweight transactions (IF NOT EXISTS), S3 supports conditional puts, and SQL has INSERT ... ON CONFLICT DO NOTHING. The idea is the same: you let the storage engine perform the existence check and the write as one atomic step, avoiding the race of "read then write". Whenever you see yourself writing "if not exists(key): insert(key)" as two statements in application code, you have a race; collapse it into one conditional statement.

5.3 Versioning and compare-and-set

Give each mutable row a version number (or use its last-modified timestamp or a hash of its contents). An update says "set X, but only if the version is still 4", and bumps the version to 5. If a duplicate or stale update arrives, the version no longer matches, zero rows are affected, and the writer knows the change was already applied or that someone else changed the row. This pattern, known as optimistic concurrency control or compare-and-set (CAS), also protects against lost updates between different users, not just duplicates. State machines use the same idea: "move from PAID to SHIPPED" is a conditional update on the current state, so repeating it is harmless (see Chapter 31 for how such steps are chained across services).

5.4 The inbox pattern (idempotent receiver)

The inbox pattern is the consumer-side partner of the transactional outbox described in Chapter 31. The consumer has an inbox table containing the message ids it has handled. When a message arrives, the consumer opens a local transaction, inserts the message id into the inbox, applies the business effect, and commits. Only then does it acknowledge the message to the broker. Three crash points illustrate why it works:

  • Crash before the transaction commits: nothing was recorded or applied. The broker redelivers, and the retry processes it normally.
  • Crash after commit but before the ack: both the inbox row and the business effect exist. The broker redelivers, the insert hits the unique constraint, and the consumer simply acknowledges without redoing the work.
  • Two consumers receive the same message simultaneously: the unique constraint lets exactly one commit.

5.5 Sequence numbers per producer

Instead of remembering every message id, each producer numbers its messages 1, 2, 3, and so on. The receiver keeps only the highest sequence number processed per producer. A message with a number at or below it is a duplicate and is dropped; the next expected number is accepted; a number that skips ahead signals a gap and triggers a wait or a resend. TCP uses this idea for byte streams and Kafka's idempotent producer uses it for batches. The storage cost is one counter per producer rather than one row per message, which is why it scales to very high rates. The limits: it needs ordered delivery per producer, a stable producer identity, and a way to handle producer restarts (Kafka solves the restart case with transactional ids and epochs).

5.6 Dedup windows and their cost

Remembering every message id forever is impossible at scale, so almost all systems use a dedup window: they remember ids for a bounded time and assume that a duplicate can only arrive within that window. SQS FIFO queues, for example, deduplicate messages with the same deduplication id within a five minute interval. Choosing the window is a tradeoff:

  • Too short: a late retry or a replay after an outage falls outside the window and is processed twice.
  • Too long: storage and index size grow in proportion to rate times window.

Worked estimate: a consumer handling 5,000 messages per second with a 24 hour window must remember 5,000 x 86,400 = 432 million ids. At 16 bytes for a UUID plus roughly 30 bytes of index and row overhead, that is around 46 bytes each, about 20 GB. That is comfortable for a database table with partitioning and a daily drop of old partitions, but heavy for an in-memory set. A Bloom filter (see Chapter 57) can shrink memory a lot, but it has false positives, which would wrongly drop genuinely new messages, so it is used only as a first-level filter in front of an exact check, never alone for money. Sequence numbers (5.5) avoid the problem entirely when they are applicable.

5.7 Idempotent consumers, end to end

Put the pieces together for a consumer that reads events from a queue and updates a database. The safest recipe is: (1) make the handler's effect idempotent on its own where possible (upserts rather than inserts, absolute values rather than increments); (2) where it is not, use the inbox pattern so the dedup record and the effect commit atomically; (3) acknowledge only after the transaction commits, so a crash leads to redelivery rather than loss; (4) for effects on external systems (an email, a card charge), pass a deterministic idempotency key derived from the message id, such as "payment-" + messageId, so that even if your handler runs twice the downstream system sees the same key and deduplicates it. That last point is the general rule for chains: every hop in the chain must either be idempotent or be handed a stable key.

5.8 Safe retries

Idempotency is what makes retrying legal. A retry policy without it is a duplicate generator. Retries themselves must be designed carefully, and that topic is covered in Chapter 40 (and again for microservices in Chapter 51); the short version is:

  • Retry only operations that are idempotent or carry an idempotency key. Retrying a bare POST is unsafe.
  • Retry only errors that are likely transient (timeouts, connection resets, 503, 429), never validation errors (400, 422) or authorisation failures.
  • Use exponential backoff with jitter, so a thousand clients that failed together do not all retry on the same millisecond and keep the server down.
  • Cap the number of attempts and set a total deadline, and avoid retrying at every layer of a deep call chain, since three layers each retrying three times produce 27 attempts at the bottom (a retry storm).
  • Use a retry budget or circuit breaker so retries cannot exceed a small fraction of normal traffic.

6. ID generation: why it is a design problem

Every row, event, order, file and message needs an identifier. On a single database server this is trivial: let the database count. In a distributed system, many machines create records at the same time, often in different data centers, and the identifiers must still never collide. Worse, the choice of ID format quietly affects index performance, storage cost, security and how you can shard the data (Chapter 25). This second half of the chapter walks through the requirements and the main designs.

6.1 Requirements

  • Uniqueness. The non-negotiable one. Two different records must never receive the same ID, even if created on different machines at the same instant.
  • Rough sortability (k-sortable). Many systems want IDs that increase roughly with creation time. Then "newest first" is an index scan, range queries by time are cheap, and B-tree inserts land at the right edge of the index instead of at random places. "K-sortable" means sorted to within some small tolerance (for example, to the millisecond), not strictly ordered.
  • Size. A 64-bit integer takes 8 bytes. A UUID takes 16 bytes as binary and 36 characters as text. The ID is copied into every secondary index, every foreign key and every cache entry, so size multiplies (section 12).
  • No coordination (or very little). Generating an ID should not need a network round trip to a central server for every record, because that becomes a latency cost and a single point of failure. Ideally each node generates IDs locally.
  • High throughput and availability. Large systems create hundreds of thousands to millions of IDs per second and must keep generating them during partial failures.
  • Privacy and unguessability. Sometimes IDs are exposed in URLs. Sequential integers leak business volume and allow enumeration (section 11). Sometimes you want opaque IDs; sometimes you want IDs that reveal nothing about creation time.
  • Human or URL friendliness. Short, case-safe, easy to read or type, no special characters.

These goals conflict. Random IDs are unguessable and need no coordination but are unsorted and large; sequential IDs are small and sorted but need coordination. Most of the designs below are different compromises.

7. Auto-increment and why it breaks at scale

The default in every relational database is an auto-incrementing integer (AUTO_INCREMENT in MySQL, SERIAL or identity columns in PostgreSQL). The database keeps a counter and hands out 1, 2, 3, and so on. It is small (4 or 8 bytes), perfectly ordered, and fast on a single node. For a monolith with one primary database, it is often the correct answer, and you should not over-engineer past it.

It breaks when the system grows beyond one writer:

  • Single point of contention and failure. Every insert must take the next value from one counter on one primary. That limits write throughput to what one node's counter can do, and if that node is down, no one can create records.
  • Sharding. With ten database shards, each shard has its own counter, so shard 1 and shard 2 both produce ID 1. IDs are no longer globally unique, so you cannot move rows between shards, and foreign references become ambiguous.
  • Multi-region and multi-primary replication. Two primaries accepting writes both count upward from the same value and collide. The standard workaround is to give each primary a different offset and step, for example with two nodes, node A produces odd numbers and node B even numbers (auto_increment_increment = 2, offsets 1 and 2). That works but is fragile: adding a third node means reconfiguring the step, IDs from different nodes are no longer in time order, and gaps appear.
  • Enumeration and leakage. Sequential IDs let an outsider guess neighbours (/orders/1001, /orders/1002) and estimate your total volume.
  • Client-side generation is impossible. The ID exists only after the insert round trip, which complicates idempotent creation (the client cannot choose the ID in advance) and offline-first applications.
Key idea Auto-increment couples "creating an ID" to "talking to one particular database". Every scalable scheme below breaks that coupling by letting each node generate IDs independently, or by handing out ranges of IDs in bulk so the central counter is touched rarely.

8. UUIDs, ULID and KSUID: coordination-free IDs

8.1 UUID version 4 (random)

A UUID (universally unique identifier) is a 128-bit value, usually written as 32 hexadecimal digits in five groups, such as 3f2b8c1e-9a47-4d3e-8b61-7c0d5e2fa913. Version 4 fills 122 of the 128 bits with random data (the remaining 6 bits mark the version and variant). Any machine can generate one with no coordination at all. The collision probability is negligible for practical purposes: to have even a one-in-a-billion chance of any collision you would need on the order of 100 trillion UUIDs (the birthday bound is roughly the square root of 2^122, about 2.3 x 10^18 IDs for a 50 percent chance). That makes UUIDv4 attractive: trivial to implement, safe to generate on clients, and unguessable.

The cost is index locality. Databases that organise a table or index as a B-tree (InnoDB's clustered primary key in MySQL, and every ordinary secondary index) keep entries sorted by key. With a sequential key, every new row goes to the rightmost leaf page, which stays hot in memory and fills up neatly. With a random key, each new row lands on a random leaf page somewhere in the whole index. Consequences:

  • Cache misses. The "hot" part of the index is the entire index, not its right edge. Once the index is larger than memory, a large share of inserts need a disk read to fetch the target page.
  • Page splits and fragmentation. Inserting into the middle of a full page forces a split, leaving two half-empty pages. Over time the index becomes larger (often 20 to 40 percent) and less dense than a sequential one.
  • Write amplification. Random page writes dirty many different pages, inflating the amount written to the write-ahead log and to disk (see Chapter 18 and Chapter 19).
  • Size. 16 bytes instead of 8, copied into every secondary index of an InnoDB table, since secondary indexes store the primary key.

This is invisible with a million rows and very visible with a billion.

8.2 UUIDv7

The newer UUID version 7 (standardised in RFC 9562) keeps the 128-bit UUID format but puts a 48-bit Unix timestamp in milliseconds in the most significant bits, followed by the version bits and about 74 bits of randomness (some implementations use part of the random field as a counter to keep IDs within one millisecond ordered). Because the timestamp comes first, UUIDv7 values sort by creation time as plain bytes, giving the B-tree behaviour in the lower half of the figure, while still needing no coordination and fitting any column that already stores UUIDs. It is today the sensible default when you want UUID compatibility plus index friendliness. The tradeoff is that the creation time is readable from the ID, which can be a privacy leak (section 11).

8.3 ULID

ULID (Universally Unique Lexicographically Sortable Identifier) predates UUIDv7 with the same idea: 48 bits of millisecond timestamp followed by 80 bits of randomness, 128 bits total. It is written as a 26-character string in Crockford base32 (digits and uppercase letters without confusing ones like I, L, O, U), which is shorter than the 36-character UUID text and sorts correctly as a string. Within the same millisecond, a monotonic ULID generator increments the random part so IDs from one process stay strictly ordered. Compared with UUIDv7, ULID's main advantages are the compact text form and no dependency on a standard; UUIDv7's are native database types and library support.

8.4 KSUID

KSUID (K-Sortable Unique ID, from Segment) uses 160 bits: a 32-bit timestamp counted in seconds from a custom epoch in 2014, followed by 128 bits of randomness, rendered as a 27-character base62 string. Second granularity is coarser, so IDs created within the same second are not ordered relative to each other, but the very large random part makes collisions practically impossible without any counter. Its longer 20-byte size is the price.

9. Snowflake: 64-bit time-ordered IDs

Twitter created Snowflake in 2010 when it moved away from a single MySQL auto-increment and needed IDs that were small enough for a 64-bit column, roughly time-ordered, and generated by many machines without a call to a central server. The idea has been copied across the industry (Discord, Instagram's variant, Sonyflake, Baidu's UidGenerator, and many in-house versions).

9.1 The bit layout

A Snowflake ID is a 64-bit integer built by packing several fields into fixed bit ranges. In Twitter's original layout:

FieldBitsMeaning
Sign bit1Always 0, so the value fits a signed 64-bit integer and stays positive.
Timestamp41Milliseconds since a custom epoch chosen by the system (not 1970). 2^41 ms is about 2.2 x 10^12 ms, roughly 69.7 years of range.
Datacenter id532 possible data centers.
Machine (worker) id532 workers per data center. Together with the data center, 1,024 distinct generators.
Sequence12A counter that restarts at 0 every millisecond. 4,096 IDs per millisecond per worker.

9.2 How a worker generates an ID

Each worker keeps two pieces of state in memory: the timestamp of the last ID it issued and the current sequence number. To make an ID it reads the current time in milliseconds and then:

  1. If the current time equals the last timestamp, increment the sequence. If the sequence overflows past 4,095, spin-wait until the next millisecond so the counter can restart.
  2. If the current time is greater, reset the sequence to 0.
  3. Compute ((now - epoch) << 22) | (datacenter << 17) | (machine << 12) | sequence, store the timestamp as the new last one, and return the value.

This runs entirely in local memory, takes a few hundred nanoseconds, and requires no network call, which is why it scales to millions of IDs per second per node. The only synchronisation is a lock or atomic around the two state variables within one process.

9.3 The clock problem

Snowflake trusts the machine's clock. Clocks can move backwards: an NTP correction steps the clock back a few milliseconds, a virtual machine resumes after pause, or a leap second is smeared. If the clock goes back to a timestamp the worker has already used, it might regenerate an ID it issued before (same timestamp, same worker, same sequence), a collision. Real implementations handle it explicitly:

  • Refuse and wait. If now < lastTimestamp, the generator throws or blocks until the clock catches up. For small rollbacks (a few milliseconds) waiting is fine. Twitter's original code throws an error when the clock moves backwards.
  • Keep using the last timestamp. Continue issuing IDs from the stored last timestamp and an incrementing sequence, ignoring the real clock until it catches up. This preserves uniqueness and availability at the cost of IDs briefly "living in the future", and it is bounded by the sequence capacity.
  • Persist the last timestamp. Write the last issued timestamp periodically to disk or a coordination service, so that after a crash and restart the worker refuses to issue anything earlier. Without this, a restarted worker on a machine with a slightly earlier clock could duplicate.
  • Alert and take the node out of rotation when the rollback is large (seconds), since something is wrong with time on that host.
  • Use a monotonic clock for the delta (elapsed time since start) combined with a wall-clock reading at start, which avoids most step adjustments from NTP.

Also note that Snowflake order is only approximate across workers: two workers with clocks 5 ms apart produce IDs that are 5 ms out of true order. That is normally fine ("k-sortable"), but it means you cannot use the ID as a strict causal ordering. For causality you need the tools of Chapter 27, such as logical or hybrid clocks.

9.4 Assigning worker ids

The scheme depends on no two live workers sharing the same (datacenter, machine) pair. How the pair is assigned is the one place coordination appears, but only once per worker startup, not per ID:

  • Static configuration. A config file or environment variable per host. Simple, but error-prone: copying a config duplicates the id, and autoscaled or containerised fleets make static assignment awkward.
  • Coordination service. On startup each worker registers in ZooKeeper or etcd (Chapter 30), for example by creating an ephemeral sequential node, and uses the assigned sequence number as its worker id. When the worker dies, the ephemeral node disappears and the id can be reused. Often combined with a lease so a worker that is partitioned from the coordinator stops issuing IDs before its id is handed to a newcomer.
  • Database table. A worker inserts a row to claim the smallest free id and heartbeats to renew it. Cheap if you already have a database.
  • Derived from the environment. Use the low bits of the pod IP, the Kubernetes StatefulSet ordinal, or a cloud instance number. Sonyflake, for instance, uses the lower 16 bits of the private IP address by default, which is quick but risks collisions across subnets.

Take care that the bit budget fits the fleet. If you autoscale to thousands of short-lived containers, 10 bits (1,024 ids) can be exhausted, so you may need to give up some sequence or timestamp bits for more worker bits, a tradeoff the calculator below lets you explore.

9.5 Variants in the wild

  • Twitter Snowflake: 41 + 10 + 12 as above. Open sourced, now mostly a reference.
  • Instagram: 41 bits of milliseconds since a custom epoch, 13 bits for the logical shard id, and 10 bits for a sequence. Instead of a separate service, the ID is computed inside PostgreSQL by a stored function in each logical shard, using that shard's own sequence modulo 1,024. The shard id is embedded in the ID, so given any ID you know which shard holds the row, which fits naturally with sharding (Chapter 25).
  • Sonyflake: 39 bits of time in units of 10 ms (so about 174 years instead of 69), 8 bits of sequence (256 IDs per 10 ms per machine, much lower throughput) and 16 bits of machine id (65,536 machines). It trades per-node speed for lifetime and fleet size.
  • Discord: uses a Snowflake layout with a 2015 epoch, worker and process ids, and a 12-bit increment.

10. Ticket servers and range allocation

Another family keeps a central counter but avoids calling it for every ID by using it only to hand out blocks.

10.1 Flickr's ticket server

Flickr's well-known design uses a dedicated MySQL table whose only job is to produce numbers. The table has an auto-increment id column and a single-row-per-stub trick: application code runs REPLACE INTO Tickets64 (stub) VALUES ('a'); SELECT LAST_INSERT_ID();. REPLACE deletes the old row and inserts a new one with the next auto-increment value, so the table stays one row big while the counter keeps climbing. To avoid a single point of failure, Flickr runs two ticket servers, one configured to produce odd numbers and the other even (auto_increment_increment = 2 with offsets 1 and 2), and clients alternate between them (round robin). If one dies, the other keeps issuing. The IDs are small, 64-bit integers, nearly sequential, and ordered per server. The costs: a network call per ID (usually mitigated with batching), and the two servers can drift so that IDs are only roughly ordered.

10.2 DB range allocation (segment mode, hi-lo)

Rather than asking the central server for each ID, a node asks for a block. The central table stores (name, next_value). A node runs UPDATE counters SET next = next + 1000 WHERE name = 'order' in a transaction and receives the range [next, next + 999]. It then hands out those 1,000 IDs from memory with no network call, and goes back for another block when exhausted. This is the segment approach used by systems such as Meituan's Leaf, and it is essentially the same as the hi-lo algorithm in ORMs like Hibernate (the "hi" part comes from the central source, the "lo" part counts locally from 0 to block size minus 1).

Properties: IDs are compact and ordered within a node but only roughly ordered across nodes (a node holding an older block issues smaller numbers later), gaps appear when nodes crash or restart, and a node that cannot reach the central database can keep issuing until its block runs out. Some implementations pre-fetch the next block when the current one is about 10 percent consumed, so there is no pause at the boundary. The central counter is still a dependency, but replicating it and widening the block size makes it tolerable.

11. Short IDs for URLs and exposure concerns

11.1 Short codes (base62)

A URL shortener (the URL shortener case study) needs very short IDs such as aZ3k9Q, which rules out 128-bit UUIDs. The standard approach is to produce a number and encode it in base62, using the 62 characters 0-9, a-z and A-Z, which are safe in URLs. The capacity is 62^n:

LengthCombinations
6 characters62^6, about 56.8 billion
7 characters62^7, about 3.5 trillion
8 characters62^8, about 218 trillion

Three ways to get the underlying number:

  • Counter. A global counter (or range-allocated counters as in section 10) is incremented per new URL, then base62-encoded. No collisions by construction, compact codes. The downside is that codes are sequential and so guessable, which matters when links are private. One mitigation is to scramble the counter with a reversible bijection (multiply by a large odd number modulo 2^k, or a small Feistel network) before encoding, which keeps uniqueness but hides the order.
  • Hash of the long URL. Hash the URL (MD5 or SHA-256) and take the first 6 to 8 characters of the base62 or base64 encoding. The same URL maps to the same code, which gives free deduplication, but collisions are possible because you truncate the hash. By the birthday bound, with N possible codes, a collision becomes likely after about 1.2 times the square root of N entries: for 7 characters (N around 3.5 x 10^12) that is roughly 2 million links, a tiny number. So the system must check the database and, on collision, re-hash with a salt or append a counter and retry.
  • Random code. Pick random characters and insert with a unique constraint, retrying on conflict. Unguessable, no coordination, but collision chance rises as the keyspace fills, so use 7 or more characters and keep the fill ratio low.

11.2 ID exposure and enumeration

Whatever you choose, remember what the ID reveals when it appears in a URL or API response:

  • Enumeration (IDOR). If /invoices/1001 is valid, an attacker tries 1002, 1003 and so on. The root defence is authorisation checks on every object access, never obscurity. Unguessable IDs are defence in depth only, not a substitute (see Chapter 55).
  • Business intelligence leakage. Sequential IDs tell competitors how many orders you handle: they place two orders a week apart and subtract (the "German tank problem").
  • Time leakage. UUIDv7, ULID, KSUID and Snowflake all embed a creation timestamp. That is usually harmless, but for sensitive objects (user accounts, password-reset tokens) it can leak signup time, or make tokens easier to predict.
  • Machine leakage. Snowflake IDs reveal datacenter and worker bits, hinting at your topology.

A common pattern separates the two roles: an internal, compact, time-ordered ID (bigint or Snowflake) used for storage and joins, plus a separate random public identifier (a UUIDv4 or a random short string) exposed in URLs and APIs. You pay one extra indexed column to get fast storage and unguessable external names. For security tokens such as password resets, never use any of these ID schemes; use a cryptographically secure random generator with at least 128 bits.

12.1 Capacity math: what an ID really costs

Take a table of 10 billion rows with three secondary indexes. With an 8-byte key, the primary key column is 80 GB. With a 16-byte UUID it is 160 GB. In InnoDB every secondary index entry also contains the primary key, so three secondary indexes add the key three more times: 8 bytes gives about 240 GB extra and 16 bytes gives about 480 GB extra. Total key-related storage: roughly 320 GB for bigint compared with 640 GB for UUID, before per-entry overhead. That difference is real money and also real memory pressure, because the buffer pool holds fewer index pages. Combine this with the random-insert behaviour from section 8.1 and the case for compact, time-ordered keys on very large tables is clear.

12.2 Capacity math: Snowflake limits

  • Lifetime: 41 bits of milliseconds is 2,199,023,255,552 ms. Dividing by 31,557,600,000 ms per year gives about 69.7 years from the chosen epoch. Choose an epoch near the launch date, not 1970, or you waste 55 years of range.
  • Per-worker rate: 12 sequence bits give 4,096 IDs per ms, so 4.096 million per second. Real workloads rarely approach this; when they do, the generator waits for the next millisecond, which slows callers slightly.
  • Fleet rate: 1,024 workers times 4.096 million is about 4.2 billion IDs per second, orders of magnitude more than almost any system needs.
  • Bit trade: if you need 8,192 workers you take 3 bits from the sequence (down to 512 IDs per ms per worker, 512,000 per second), which is still ample.

12.3 Capacity math: collision probability

For random IDs with b random bits, the chance of any collision among n IDs is approximately n^2 / 2^(b+1). For UUIDv4 (122 bits) and n = 10^12 (a trillion IDs) this is 10^24 / 2^123, about 10^24 / 10^37, which is 10^-13, effectively zero. For a 7-character base62 code (about 41.7 bits) and n = 10^6 it is 10^12 / 2^42.7, about 10^12 / 7 x 10^12, around 14 percent. This is why short random codes always need a uniqueness check, and 128-bit IDs never do.

14. Worked example: payments API and order IDs

Put both halves of the chapter together. You are designing the order and payment service for a shop with 2,000 orders per second at peak, in three regions, with an order table that will grow to about 20 billion rows.

  1. Order IDs. Auto-increment is out: three regions write locally and the table will be sharded by user (Chapter 25). Choose Snowflake-style 64-bit IDs with the shard or region encoded in the worker bits. At 2,000 per second the sequence is barely touched, so a layout of 41 timestamp, 12 worker (4,096 pods) and 10 sequence (1,024 per ms per worker, over a million per second) is generous. The worker id is claimed from etcd with a lease at pod start. Clock rollbacks over 5 ms take the pod out of rotation. A separate random public order token (a UUIDv4) is exposed in URLs, so competitors cannot count orders and users cannot enumerate neighbours.
  2. Payment API. POST /payments requires an Idempotency-Key header. The server inserts (account_id, key, fingerprint, state=IN_PROGRESS) into the same database as the payment row, protected by a unique constraint, inside one transaction. The card network call has its own stable key derived from the payment id so a retry cannot double-charge. The completed response is stored, and keys expire after 24 hours.
  3. Events. After commit, the service publishes PaymentCaptured to Kafka via a transactional outbox (Chapter 31). Consumers (shipping, email, ledger) are at-least-once. Each uses an inbox table keyed by event id in the same transaction as its own effect, with a 7-day retention.
  4. Numbers. 2,000 payments per second times 86,400 seconds is 172.8 million keys per day. At about 100 bytes per key row including the stored response, that is roughly 17 GB per day, kept for one day, with a partition dropped each night. The inbox for a consumer with the same rate over 7 days is 1.2 billion ids, about 55 GB at 46 bytes each, which is why partitioning by day matters.
  5. Failure walk-through. The client times out after a successful charge and retries with the same key: the server finds state COMPLETED with a matching fingerprint and replays the original 201. The client retries while the first attempt is still running: the claim insert conflicts, and the client receives 409 and backs off with jitter. A consumer crashes after committing but before acking: redelivery hits the inbox's primary key and is acknowledged without a second effect.

15. Interview Q&A

Why is "exactly-once delivery" considered impossible, and what do systems that claim it actually provide?

Between two nodes on an unreliable network, a sender that gets no acknowledgement cannot know whether the message was lost on the way there or the ack was lost on the way back. To guarantee delivery it must retry, which can produce a second copy; to avoid duplicates it must not retry, which can lose the message. So delivery on the wire is either at-most-once or at-least-once. What systems like Kafka provide is exactly-once processing effect inside a boundary: the idempotent producer discards retried batches using producer id and sequence numbers, and transactions make consume, process and produce atomic together with offset commits. Outside that boundary, for example when calling a payment provider, you still need idempotency keys to get an effectively-once outcome.

Design an idempotency-key mechanism for a payment API. What can go wrong?

The client generates a unique key per logical payment and sends it in a header with every retry. The server stores a row keyed by (account, key) with a request fingerprint, a state, and eventually the response. It claims the key atomically with a unique constraint in the same database transaction as the payment itself, so a crash cannot leave one without the other. Retries with a completed key and the same fingerprint get the stored response replayed, a different fingerprint is rejected, and a key whose first attempt is in progress yields a conflict or waits. Things that go wrong are concurrent duplicates if the claim is not atomic, stuck IN_PROGRESS rows after a crash (fixed with a lease timeout), a TTL shorter than the client's retry window, a key reused for different requests, and storing the key in a different system than the business data so a crash between the two causes duplicate or phantom success.

What is the difference between idempotent and safe operations, and how does HTTP treat them?

A safe operation does not change server state at all, like GET and HEAD. An idempotent operation may change state, but repeating it leaves the state the same as doing it once, like PUT (replace with this exact representation) and DELETE. All safe methods are idempotent, but not the other way round. POST is neither, because each call may create a new resource, and PATCH depends on how it is defined: "set field to X" is idempotent while "increment field" is not. These classifications are conventions that clients, proxies and browsers rely on to decide when automatic retries are acceptable, so the server must actually honour them. A POST that must be retried safely needs an explicit idempotency key.

How would you make a message consumer idempotent?

First prefer naturally idempotent effects such as upserts and absolute values over inserts and increments. When that is not possible, use the inbox pattern: in one local transaction insert the message id into a table with a unique constraint and apply the business effect, then commit and only afterwards acknowledge the message. A redelivered message fails the unique insert and is acknowledged without being reprocessed. Where the consumer calls an external service, pass a deterministic idempotency key derived from the message id. Keep ids for a dedup window that exceeds the maximum redelivery delay, partition the table by time so old ids can be dropped cheaply, and use per-producer sequence numbers if ordering is guaranteed, which needs only one counter per producer.

Why are random UUIDs bad as primary keys in large B-tree databases, and what would you use instead?

A B-tree keeps keys sorted, so a random key sends each insert to an unpredictable leaf page. Once the index outgrows memory, many inserts cause disk reads, pages split in the middle and leave half-empty pages, and write amplification rises. In InnoDB the primary key is also copied into every secondary index, so the 16-byte size multiplies. A time-ordered ID turns inserts into appends at the right edge, where the hot pages are cached and pages fill completely. I would use a 64-bit Snowflake-style ID when I control the infrastructure and want 8 bytes, or UUIDv7 when I need the UUID format and no coordination. If the ID must be unguessable externally, I keep a separate random public identifier.

Explain the Snowflake layout and how you would handle clock rollback and worker id assignment.

A Snowflake ID is 1 unused sign bit, 41 bits of milliseconds since a custom epoch, 10 bits split into datacenter and machine, and a 12-bit sequence that resets each millisecond. Time in the high bits makes IDs roughly sorted, the worker bits make generators disjoint, and the sequence allows 4,096 IDs per millisecond per worker. For clock rollback the generator remembers the last timestamp; if the clock reads earlier, it waits for small rollbacks, keeps using the last timestamp and increments the sequence, or refuses and alerts for large jumps, and it persists the last timestamp so a restart cannot issue earlier values. Worker ids are claimed once at startup, for instance as an ephemeral sequential node in ZooKeeper or etcd or a leased row in a database, so that two live workers never share an id and a dead worker's id is eventually reclaimed.

Compare a ticket server, range allocation and Snowflake. When would you pick each?

A ticket server such as Flickr's centralises a counter and calls it for each ID or batch, giving compact sequential integers, with a pair of servers using odd and even steps for availability. Range allocation (segment or hi-lo) has each node reserve a block of numbers from a central counter in one update and issue them from memory, so the database sees one write per thousand IDs; gaps appear on crashes and order is only per node. Snowflake avoids per-ID or per-block calls entirely by encoding time, worker and sequence, needing coordination only for worker ids and trusting clocks. I would choose range allocation when I want dense, mostly sequential numbers and already have a reliable database; Snowflake when throughput, multi-region and no runtime dependency matter and roughly time-ordered IDs are useful; a ticket server only when simplicity matters more than removing the central dependency.

Design the ID scheme for a URL shortener with 7-character codes. How do you avoid collisions and guessing?

Seven base62 characters give about 3.5 trillion codes, enough for tens of billions of URLs with a low fill ratio. The most predictable approach is a counter, ideally allocated in blocks per application node so there is no hotspot, base62 encoded, which makes collisions impossible by construction. To avoid sequential, guessable links I would pass the counter through a reversible scrambling step before encoding. Hashing the long URL and truncating gives deduplication but needs collision handling, since the birthday bound makes a collision likely after only about two million entries at that length, so each insert must be checked against a unique index and retried with a salt on conflict. Random codes work with a unique constraint and a retry. The case study in the URL shortener chapter explores the tradeoffs further.

How long should you retain idempotency keys and dedup records, and what happens if the window is too short?

The retention must exceed the longest period over which a duplicate of the same operation can still arrive, which is the client's maximum retry horizon plus the broker's maximum redelivery delay plus any replay you plan to run, with a safety margin. Public payment APIs commonly keep keys for around a day; queue systems with built-in dedup can use as little as minutes, which is only valid if redelivery is guaranteed to happen quickly. If the window is too short, a late retry looks like a brand-new request and is executed again, creating exactly the duplicate you built the mechanism to prevent. If it is too long you pay in storage and index size, so I would estimate rate times window times row size, partition by time, and drop old partitions. The window is part of the API contract and should be documented.

Can you give an operation that looks idempotent but is not, and how do you fix it?

"Send a welcome email when a user signs up" looks fine until the signup event is delivered twice and the user gets two emails; sending an email is a side effect that cannot be rolled back. Similarly an UPDATE accounts SET balance = balance + 50 triggered by a retried message adds money twice. A subtler case is a PUT whose handler also appends an audit row or fires a webhook, so the resource state is idempotent but the side effects are not. The fixes are to record the fact that the effect happened under a stable id (an emails_sent table with a unique key on user and email type, checked in the same transaction as the signup), to turn increments into insertions of uniquely identified ledger entries and compute the balance by summing, and to pass idempotency keys to every external call. The principle is to make every side effect either naturally idempotent or guarded by a recorded identity.

16. Recap

  • Retries are needed for reliability, and lost acks and timeouts make duplicates unavoidable. The client cannot tell "not delivered" from "delivered, reply lost".
  • At-most-once can lose messages, at-least-once can duplicate them, and true exactly-once delivery on a network is impossible. Practical exactly-once means at-least-once plus idempotent or deduplicating processing, which is what Kafka's idempotent producer and transactions do inside Kafka.
  • Naturally idempotent operations set absolute state (PUT, DELETE, upserts). Increments and creates are not, and need a key or a conditional write.
  • Idempotency keys are client-generated, scoped per account and operation, stored with a request fingerprint and the response, claimed atomically in the same transaction as the business write, and expire after a documented TTL. Concurrent duplicates are handled by a state machine with conflict responses or waiting, and stuck in-progress records by leases.
  • Enforcement patterns: unique-constraint dedup table, conditional writes, version-based compare-and-set, the inbox pattern, and per-producer sequence numbers. Dedup windows trade storage for safety.
  • Retry only idempotent operations, only on transient errors, with backoff and jitter and a budget (Chapter 40).
  • IDs must be unique and ideally compact, time-ordered and coordination-free. Auto-increment breaks with sharding and multi-primary writes. UUIDv4 is simple but wrecks B-tree locality; UUIDv7, ULID and Snowflake are time-ordered.
  • Snowflake packs 41 bits time, worker bits and a 12-bit sequence into 64 bits; it needs clock rollback handling and one-time worker id assignment via a coordination service. Ticket servers and range allocation reduce central calls by handing out blocks.
  • Short URL codes use base62 of a counter, a hash or random bytes, and need collision handling. Separate internal ordered IDs from public random ones, and never rely on unguessable IDs instead of authorisation.
