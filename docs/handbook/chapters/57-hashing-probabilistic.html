Hashing and Probabilistic Structures

Hashing turns any piece of data into a number, and that one trick powers hash tables, sharding, caches, deduplication, and a family of tiny data structures (Bloom filters, HyperLogLog, Count-Min Sketch) that answer questions about billions of items using kilobytes of memory. This chapter explains how each one works, how to size it, and when to reach for it.

1. Hash functions: what they promise

A hash function takes an input of any size (a string, a user id, a whole file) and returns a fixed-size number, called the hash or digest. A 32-bit hash is a number between 0 and about 4.29 billion; a 64-bit hash is a number up to about 1.8 × 1019. The function is a deterministic recipe: the same input always produces the same output, on every machine, every time.

Almost every large-scale system in this handbook leans on hashing. Sharding (Chapter 25) uses a hash of the key to pick a partition. Caches use it to find a bucket. Load balancers use it to keep a client on the same backend. Deduplication, integrity checks, and the probabilistic structures in the second half of this chapter are all built from it. Before using it, you need to know which properties a good hash function has and which kind to choose.

1.1 Properties that matter

  • Determinism. Same input, same output, always. This sounds trivial, but it has a trap: some language runtimes randomize their built-in string hash per process start (to resist attacks). If you use such a hash to route data between machines, two processes will disagree. For anything that crosses a process boundary, pick an explicit, stable algorithm and fix its seed.
  • Uniformity. Outputs should spread evenly across the whole range. If you hash a million different keys into 1,000 buckets, each bucket should get close to 1,000 keys. A hash that favors some buckets creates hot spots and wastes memory.
  • Avalanche effect. Changing one bit of the input should flip about half of the output bits, unpredictably. Without avalanche, similar keys (user1001, user1002) land in neighboring buckets, and the pattern in your data shows up as lumps in your distribution. Good hash functions mix input bits thoroughly through multiplications, rotations, and XORs.
  • Speed. Hashing sits on the hot path of every lookup, so it must be cheap. Non-cryptographic hashes run at several gigabytes per second per core.
  • Low collision rate. Different inputs should rarely map to the same output. Section 2 puts numbers on "rarely".

1.2 Cryptographic versus non-cryptographic

Hash functions split into two families with different goals.

Non-cryptographic hashes are built for speed and good distribution. Examples: MurmurHash3 (long the default in many databases and libraries), xxHash and its newer XXH3 variant (often the fastest, around 10 GB/s or more for large inputs on modern CPUs), CityHash and FarmHash, and FNV-1a (very simple, fine for short keys). They make no promise against an adversary: someone who knows the function can craft many inputs that collide on purpose.

SipHash sits in between. It is a keyed hash designed to be fast enough for hash tables while resisting hash flooding attacks. In a flooding attack, an attacker sends thousands of keys that all land in one bucket, turning your O(1) lookups into O(n) and burning CPU. A secret random key chosen at process start makes the collisions unpredictable. Python, Rust, and Ruby use SipHash variants for exactly this reason. It is several times slower than xxHash, though.

Cryptographic hashes such as SHA-256 (part of SHA-2), SHA-3, and BLAKE3 add security properties: preimage resistance (given a digest, you cannot find an input producing it), second preimage resistance (given an input, you cannot find another input with the same digest), and collision resistance (you cannot find any two inputs with the same digest). They are slower, typically 0.5 to 2 GB/s for SHA-256 without hardware help, though dedicated CPU instructions speed it up. MD5 and SHA-1 are broken for collision resistance and must not be used for security; they remain acceptable only as fast checksums where no adversary exists.

2. Collisions and the birthday bound

A collision happens when two different inputs produce the same hash. Collisions are unavoidable by simple counting: there are infinitely many possible inputs and only 2b outputs for a b-bit hash. The real question is how soon they appear.

Most people guess that you need about half the output space (2b-1 items) before a collision becomes likely. That is wrong. The birthday paradox shows it takes only about the square root of the space. In a room of just 23 people, the chance that two share a birthday is already over 50%, even though there are 365 possible birthdays, because the number of pairs grows quadratically: 23 people form 253 pairs.

For n items hashed uniformly into N possible values, the probability of at least one collision is approximately:

p(collision) ≈ 1 - e^( -n² / (2N) )

n for a 50% chance ≈ 1.177 × sqrt(N)

Work through the 32-bit row: with 77,000 items, the number of pairs is about 77,000²/2 = 3 billion, and each pair collides with probability 1/4.29 billion, so the expected number of collisions is about 0.69, giving a probability near 1 - e-0.69 = 50%. This is why 32-bit hashes are fine for bucketing (collisions are expected and handled) but dangerous as identifiers: a system with 100,000 objects keyed only by a 32-bit hash is more likely than not to have a clash.

Watch out Two consequences for design. First, never treat a short hash as a unique id: if you need identity, use a wide hash (128 bits or more) or keep the original key and compare it on lookup. Second, the birthday bound applies to accidental collisions only. A malicious party can find collisions in weak or non-keyed functions far faster, which is why untrusted input calls for SipHash or SHA-2.

3. Hash tables: the basics

A hash table (dictionary, map) stores key-value pairs in an array of buckets. To insert or find a key, you compute hash(key) mod bucket_count and go straight to that bucket instead of searching. With a good hash and enough buckets, lookup, insert, and delete take constant time on average, written O(1). Because two keys can land in the same bucket (a collision, which the birthday bound says is common once the table has more than a few dozen entries), the table needs a collision strategy.

3.1 Chaining

Each bucket holds a small list (a linked list, or a balanced tree in Java's HashMap once the chain gets long) of all entries that hashed there. To look up a key, hash it, jump to the bucket, and scan the short list comparing keys. Chaining is simple and degrades gracefully, but every entry costs an extra pointer and the scattered nodes hurt CPU cache performance.

3.2 Open addressing

Every entry lives directly in the array. If the target slot is taken, you probe for another: linear probing tries the next slot, quadratic probing jumps by growing steps, and double hashing uses a second hash as the step. Lookups follow the same probe sequence until they find the key or hit an empty slot. This layout is very cache-friendly (modern designs such as Swiss tables and Robin Hood hashing build on it) but it needs a lower load factor, and deletes must leave a tombstone marker so later probes do not stop too early.

3.3 Load factor and resizing

The load factor is entries divided by buckets. It controls the speed versus memory tradeoff. With chaining, the average chain length equals the load factor, so a load factor of 0.75 means about 0.75 entries per bucket and lookups stay fast. With open addressing, the expected number of probes for a miss grows sharply as the table fills (for linear probing, roughly (1 + 1/(1-α)²)/2 where α is the load factor): about 8.5 probes at α = 0.9 compared with 2.5 at α = 0.5. That is why open-addressing tables resize at 0.5 to 0.9 depending on design, and Java's chained HashMap resizes at 0.75.

When the load factor passes the threshold, the table resizes: it allocates a larger array (usually double), then rehashes every entry into it, since each entry's bucket depends on the array size. One resize costs O(n), but because the array doubles, resizes get exponentially rarer and the amortized cost per insert stays O(1). The catch is the latency spike: a single insert can pause for the whole rehash. Real-time systems avoid it with incremental rehashing, where the table keeps old and new arrays side by side and migrates a few buckets per operation. Redis does exactly this for its main dictionary (Chapter 15).

The painful part of "bucket = hash mod size" is that changing the size changes the bucket of almost every key. In a single process this just costs CPU. Across machines it would mean moving almost all your data, which leads directly to consistent hashing.

4. Consistent hashing in depth

Chapter 25 (Sharding) introduces consistent hashing and has an interactive ring. This section goes through the mechanics and the variants an interviewer might ask about.

4.1 The problem with mod N

The naive way to spread keys over N servers is server = hash(key) mod N. It spreads load evenly, and it works until N changes. Add one server to a 4-server cluster and hash mod 5 gives a different answer from hash mod 4 for about 80% of keys (a key stays put only when both remainders agree, roughly 1 key in 5, so about N/(N+1) of keys move). For a cache, that means a sudden mass miss and a stampede on the database (Chapter 14). For a sharded database, it means copying most of your data around.

4.2 The ring

Consistent hashing fixes this by hashing both servers and keys onto the same circular space, typically 0 to 232-1 or 264-1 with the ends joined. Each server is placed at the position hash(server id). To find the owner of a key, compute hash(key), then walk clockwise to the first server position you meet. That server owns the key. Each server therefore owns the arc between its predecessor and itself.

4.3 Key movement math

Suppose K keys are spread over N nodes. When a node is added, it takes over a slice of the ring from its clockwise neighbor, and on average it receives K/(N+1) keys, the fair share. Nobody else gives up anything. When a node is removed, its K/N keys move to the next node clockwise, and no other key changes owner. Compare with mod N, where changing N from 10 to 11 moves about 91% of keys, whereas consistent hashing moves about 9%. Of 1 billion keys, that is roughly 91 million rather than 910 million.

4.4 Virtual nodes

The plain ring has two problems. With only a few nodes, their random positions leave arcs of very different lengths, so some nodes get far more than 1/N of the keys. Also, when a node dies, all of its keys go to one neighbor, which may double that neighbor's load and perhaps topple it too (a cascading failure).

The fix is virtual nodes (vnodes). Each physical server is hashed onto the ring many times, for example 100 to 256 positions, using ids like nodeA#0, nodeA#1, and so on. Each position is a vnode that maps back to its physical server. The effect:

  • Smoother balance. The load on a server is the sum of many small random arcs, so by the law of large numbers its relative deviation shrinks roughly as 1/sqrt(v) for v vnodes. With one position per node the busiest node often carries 2 to 3 times the average on a modest cluster; with about 100 vnodes it is typically within 10% to 15%.
  • Spread on failure. A dead server's vnodes are scattered around the ring, so its load is split across many survivors instead of landing on one.
  • Heterogeneity. A machine with twice the capacity can simply be given twice as many vnodes.
  • Faster rebuild. A new server receives small pieces from many peers in parallel rather than one big piece from one peer.

The costs: the ring metadata grows (a 100-node cluster with 256 vnodes has 25,600 entries, still tiny, kept in a sorted array and searched by binary search in O(log) time), and operations such as repair need to reason about many small ranges. Cassandra historically used 256 vnodes per node and later lowered the default to 16 with a smarter token allocation, because many tiny ranges made repair and streaming heavy.

4.5 Replication on successor nodes

Dynamo-style stores (Dynamo, Cassandra, Riak) use the ring for replication as well. A key is stored on the node that owns it plus the next R-1 distinct physical nodes clockwise (the "preference list"). When vnodes are in use, the walk must skip positions that belong to a physical server already chosen, otherwise two replicas could sit on the same machine. Rack and availability-zone awareness adds one more filter: skip nodes in a rack already used. Reads and writes then coordinate with quorums (Chapter 28). When a node dies, its replicas on the successors let the cluster keep serving, and a hinted handoff or repair process fills the gap later.

4.6 Bounded loads

Even with vnodes, a very popular key or random imbalance can overload a node. Consistent hashing with bounded loads (published by Google researchers, 2016, and used in Vimeo's video serving and HAProxy) sets a capacity cap per node of ceil((1 + ε) × average load), for instance ε = 0.25 meaning at most 125% of average. When a key's owner is at capacity, the assignment walks clockwise to the next node that has room. The assignment stays mostly stable, and no node ever exceeds the cap. The cost is that the lookup depends on current load and so needs shared state or a central assigner, and a key may live on a node that is not its pure ring owner.

4.7 Alternatives to the ring

Jump consistent hash (Lamping and Veach, Google 2014) maps a 64-bit key to one of N buckets numbered 0 to N-1 using about five lines of code, no memory, and nearly perfect balance. When N grows to N+1, exactly 1/(N+1) of keys move, all of them to the new bucket. Its limits: buckets must be numbered contiguously, so you can only add or remove the last bucket, and it cannot express arbitrary node failure. It suits sharded storage where shards are numbered and replaced in place rather than removed from the middle.

int jump_hash(uint64 key, int num_buckets) {
    long b = -1, j = 0;
    while (j < num_buckets) {
        b = j;
        key = key * 2862933555777941757ULL + 1;
        j = (b + 1) * ((double)(1L << 31) / (double)((key >> 33) + 1));
    }
    return b;
}

Rendezvous hashing, also called highest random weight (HRW), is simpler in concept. For a key, compute a score hash(key, node) for every node and pick the node with the highest score. Removing a node moves only that node's keys, each to its own runner-up, so the spread on failure is automatically even. Adding a node steals exactly the keys for which it now scores highest, 1/(N+1) of them. There is no ring and no vnodes to tune. The cost is O(N) hash computations per lookup, which is fine for tens or hundreds of nodes (and can be reduced with hierarchical variants) but wasteful for thousands. To get replicas, take the top R scores.

Maglev hashing (Google's software load balancer, 2016) prioritizes lookup speed and even balance over minimal disruption. Each backend generates a pseudo-random permutation of the slots of a fixed-size lookup table (size M, a prime such as 65,537). The backends take turns claiming their next unclaimed preferred slot until the table is full. A packet then needs just table[hash(connection) mod M], a single array read. Balance is nearly perfect (each backend's slot count differs by at most one) and when a backend leaves only a small share of other entries change, though more than ideal. It fits load balancers that must forward millions of packets per second, with a table rebuilt on backend changes.

5. Locality-sensitive hashing and similarity

Ordinary hashes deliberately scatter similar inputs. Locality-sensitive hashing (LSH) does the opposite: it is designed so that similar items get the same hash with high probability and dissimilar items rarely do. That lets you find near-duplicates among billions of items without comparing every pair, which would take n² comparisons.

5.1 Measuring similarity: Jaccard

Treat a document as a set of shingles, which are overlapping chunks such as every run of 5 words. The Jaccard similarity of two sets is the size of their intersection divided by the size of their union. Identical sets score 1, disjoint sets 0. Two web pages that share 90% of their shingles are near-duplicates (a mirror site, the same article with different ads).

5.2 MinHash

Comparing full shingle sets is expensive, because a page can have thousands of shingles. MinHash compresses each set into a short signature of, say, 128 numbers. To build it, choose 128 independent hash functions. For each function, hash every shingle in the set and keep the minimum value. The signature is the list of 128 minimums.

The magic fact: for any one hash function, the probability that two sets have the same minimum equals their Jaccard similarity. (The minimum hash belongs to a random element of the union; the two sets agree exactly when that element is in the intersection.) So the fraction of the 128 positions where two signatures match is an unbiased estimate of the Jaccard similarity, with standard error about 1/sqrt(128) ≈ 9%. More hash functions give a tighter estimate, and the signature stays 512 bytes to 1 KB regardless of document size.

5.3 LSH banding: finding candidates without all-pairs

Signatures are small, but comparing every pair is still n². Banding fixes that. Cut each 128-number signature into b bands of r rows (for example 32 bands of 4 rows). For each band, hash the r numbers to a bucket. Two documents become a candidate pair if they share a bucket in at least one band. Documents with Jaccard similarity s match in a given band with probability sr, so they become candidates with probability 1 - (1 - sr)b. This is an S-shaped curve whose steep part sits near (1/b)1/r: with 32 bands of 4 rows, pairs of similarity 0.8 are almost always found (probability about 1 - (1 - 0.41)32 ≈ 100%), while pairs of similarity 0.3 are found with probability only 1 - (1 - 0.0081)32 ≈ 23% and those below 0.1 are nearly never found. You tune b and r to put the threshold where you want it. Only candidate pairs get a precise comparison afterwards.

5.4 SimHash

SimHash (used by Google for web crawl deduplication, from Charikar's work) produces a single 64-bit fingerprint per document. For each feature (word or shingle), compute its 64-bit hash. Keep a vector of 64 counters; for each feature, add +1 to counter i if bit i of its hash is 1 and -1 if it is 0 (optionally weighted by importance). The final fingerprint sets bit i to 1 if counter i is positive. Similar documents share most features, so their fingerprints differ in only a few bits. Two pages are near-duplicates when the Hamming distance (number of differing bits) is small, for example 3 or fewer out of 64. To search billions of fingerprints for ones within distance 3, split the 64 bits into blocks and index by block, which exploits the fact that close fingerprints must agree exactly on at least one block.

6. Bloom filters in depth

A Bloom filter (Burton Bloom, 1970) answers one question, "have I seen this item?", using far less memory than storing the items. The price is a small chance of a false positive (it says "maybe yes" when the answer is no). It never gives a false negative: if it says "no", the item is definitely not in the set. That one-sided error makes it ideal as a cheap guard in front of an expensive lookup.

6.1 How it works

The structure is a bit array of m bits, all zero at the start, plus k independent hash functions, each mapping an item to a position between 0 and m-1.

  • Add(x): compute the k positions h1(x) ... hk(x) and set each of those bits to 1.
  • Query(x): compute the same k positions. If any bit is 0, x was definitely never added (it would have set that bit). If all are 1, x is "probably present": those bits might have been set by other items, which is the false positive.

In practice you do not need k separate hash functions. The standard trick (Kirsch and Mitzenmacher) computes two base hashes ha and hb and derives position i as (h_a + i × h_b) mod m, which gives the same false positive rate with the cost of two hash computations.

6.2 The false positive formula

Take n items inserted into m bits using k hash functions. After inserting everything, each individual bit is still 0 with probability (1 - 1/m)kn ≈ e-kn/m, since each of the kn writes misses that bit with probability 1 - 1/m. So the fraction of bits that are 1 is about 1 - e-kn/m. A query for an item that was never added gets a false positive only if all k of its positions are 1:

p ≈ ( 1 - e^( -k·n / m ) )^k

For a given m and n, there is a best k. Too few hash functions means each item gives weak evidence; too many fills the array with ones. Minimizing p over k gives:

k_opt = (m / n) · ln 2  ≈ 0.693 · (m / n)

At the optimum, exactly half of the bits are 1, and
p = (1/2)^k = 0.6185^(m/n)

Sizing for a target p and n items:
m = - n · ln(p) / (ln 2)^2  ≈ 1.44 · n · log2(1/p)  bits

The last line says the memory needed is about 1.44 bits per item for every halving of the error rate, regardless of item size. A 1% error rate (p = 0.01, log2(100) ≈ 6.64) needs 9.6 bits per item; 0.1% needs 14.4 bits per item; 0.01% needs 19.2 bits.

6.4 Limits, and the variants that address them

  • No deletes. You cannot clear an item's bits, because other items may share them; clearing would create false negatives. If you need removal you can rebuild periodically, or use a variant.
  • No enumeration or counts. It cannot list members or say how many times something was added. (Estimating count of distinct members from the bit fill is possible but rough.)
  • Cannot grow. Positions depend on m, so adding capacity means rebuilding from the source of truth.

Counting Bloom filter. Replace each bit with a small counter, usually 4 bits. Add increments the k counters, delete decrements them, and a position counts as set when its counter is above zero. This allows deletion at about 4 times the memory. Counters can overflow if too many items share a position (4-bit counters saturate at 15), which is a known hazard to handle by freezing a saturated counter.

Cuckoo filter. Stores a short fingerprint (for example 8 to 16 bits) of each item in a cuckoo hash table, where every item has two candidate buckets and can be kicked between them. It supports deletion, and for target false positive rates under about 3% it often uses less space than a Bloom filter, and lookups touch only two buckets (better cache behavior than k scattered bit reads). Weaknesses: inserts can fail when the table gets very full (around 95% load), and deleting an item that was never inserted can remove another item's fingerprint, causing a false negative, so deletes must only be issued for items known to be present.

Scalable Bloom filter. Starts with one small filter and, as it fills, adds another larger one with a tighter error target (each layer gets the error rate multiplied by a ratio such as 0.5, so the total stays bounded by a geometric series). Queries check all layers. This handles unknown set sizes at the cost of slower queries as layers accumulate.

Other relatives. Blocked Bloom filters confine all k bits for an item to one cache line (64 bytes), trading a slightly higher error rate for much faster queries. Xor filters and Ribbon filters are immutable, built once from a known key set, and use about 1.23 bits per item times log2(1/p) instead of 1.44. RocksDB uses Ribbon filters for this reason.

6.5 Where Bloom filters are used

  • LSM read path (Chapter 19). An LSM tree such as Cassandra, RocksDB, LevelDB, or HBase keeps many immutable sorted files (SSTables). A read for a key that is not in the newest file would otherwise check file after file on disk. Each SSTable has a Bloom filter in memory (or cached): if the filter says "no", the file is skipped with zero disk I/O. With a 1% false positive rate per file, a lookup for an absent key touches about 1% of files by mistake rather than all of them. This is the single most important use in storage systems.
  • Cache penetration (Chapter 14). Requests for keys that exist nowhere (random or malicious ids) miss the cache every time and hit the database. A Bloom filter holding all valid ids is checked first; ids that get "no" are rejected immediately. A 1% false positive rate lets only 1% of invalid requests through.
  • Crawler deduplication. A web crawler must not fetch the same URL twice. A Bloom filter of seen URLs holds billions of them in a few GB. The failure mode is acceptable: a false positive means occasionally skipping a never-seen page, which costs little. See Case study 12.
  • Bigtable and similar stores. Bigtable lets you enable Bloom filters per locality group, so a read for a row or column that is not in an SSTable avoids a disk seek.
  • Malicious URL and password checks. Browsers historically shipped a local filter of known-bad URLs; only a "maybe" triggers a precise server check, which also protects privacy because most URLs are never sent. Services also use filters of breached passwords or of already-recommended items.
  • Distributed joins and set reconciliation. Send a compact filter of one table's keys to the other side to filter out rows that cannot match, saving network traffic.

7. HyperLogLog: counting distinct items

The cardinality of a stream is its number of distinct items: unique visitors, unique IPs, unique search queries. Counting exactly requires remembering every item seen, so 1 billion distinct 16-byte ids need 16 GB or more. HyperLogLog (HLL) estimates the answer using a fixed 12 KB or so, whatever the stream size, with an error of around 1%.

7.1 The idea: rare patterns reveal scale

Hash each item to a uniform random bit string. Look at the number of leading zeros. A string starting with at least one zero has probability 1/2, with at least two zeros 1/4, with at least z zeros 1/2z. If the longest run of leading zeros you have seen across all items is 10, you have likely seen on the order of 210 ≈ 1,000 distinct items, since only about 1 in 1,024 hashes has such a run. Duplicates give the same hash, so repeated items change nothing. That is the essential trick: the maximum leading-zero count is a statistic that depends only on how many distinct items you saw.

One such estimate is noisy: a single lucky hash with 20 leading zeros would wildly inflate it. HyperLogLog reduces the variance by splitting the stream into m registers (buckets), by taking the first p bits of the hash as the register index (m = 2p), and using the remaining bits for the leading-zero count (plus one). Each register stores the maximum count it has seen. The final estimate combines all registers using a harmonic mean, which dampens the effect of outliers:

E = α_m · m² / ( Σ_j 2^(-M[j]) )      where M[j] is register j, and α_m ≈ 0.7213 / (1 + 1.079/m)

standard error ≈ 1.04 / sqrt(m)

Because the error shrinks only with the square root of the register count, accuracy costs memory slowly: quadrupling m halves the error.

7.2 Accuracy and memory

The size does not depend on the number of items: the same 12 KB counts 10 thousand or 10 billion. Compare with an exact set of 1 billion 16-byte ids at 16 GB or more, about a million times larger.

7.3 Bias, small ranges, and large ranges

The raw formula is biased at the extremes. When the count is small compared with m, many registers are still zero, and the formula overestimates; implementations switch to linear counting (estimate m × ln(m / V) where V is the number of zero registers), which is accurate there. For very large counts near the hash space limit, collisions in the hash cause underestimates, and the original paper adds a correction (unnecessary with 64-bit hashes). Google's HyperLogLog++ improves on this with a 64-bit hash, an empirical bias-correction table, and a sparse representation that stores only the non-zero registers while the set is small, so small counts use even less memory. Redis uses a sparse encoding for small counts too, then converts to the dense 12 KB form.

7.4 The merge property

HLLs are mergeable. To get the cardinality of the union of two streams, take the element-wise maximum of their registers; the result is exactly the sketch you would have got by feeding both streams into one HLL. This is what makes HLL so useful at scale: each server keeps a sketch of its own traffic, each hour or each region keeps a sketch, and you merge on demand. Daily unique visitors become the merge of 24 hourly sketches; unique visitors across a week become the merge of 7 daily ones. Exact counting would require shipping and deduplicating raw ids. Merging is also commutative, associative and idempotent (merging the same sketch twice changes nothing), the properties of a CRDT, which Chapter 59 discusses.

Intersections are harder. You can estimate them with inclusion-exclusion (|A ∩ B| = |A| + |B| - |A ∪ B|), but the error is relative to the larger sets, so small intersections are unreliable. HLL also cannot list members or remove items.

7.5 HyperLogLog in Redis

Redis (Chapter 15) exposes HLL as a built-in type: PFADD visitors:2026-11-17 user42 user99 adds elements, PFCOUNT visitors:2026-11-17 returns the estimated distinct count, and PFMERGE week visitors:day1 visitors:day2 ... merges sketches (PFCOUNT with several keys merges on the fly). Each key uses at most about 12 KB, with a standard error of 0.81%, and PFADD is O(1). The "PF" prefix honors Philippe Flajolet, the inventor of the underlying algorithms. Other systems with HLL built in include BigQuery (APPROX_COUNT_DISTINCT), Presto/Trino (approx_distinct), Druid, Elasticsearch (cardinality aggregation), and Postgres via extensions.

8. Count-Min Sketch: counting frequencies

Another common question is "how many times has this item appeared?", for example how many views a video has had or how many requests each client IP made. An exact map from item to count needs memory proportional to the number of distinct items, which may be hundreds of millions. A Count-Min Sketch (CMS) (Cormode and Muthukrishnan, 2003) answers approximately in fixed memory.

8.1 Structure and operations

The sketch is a two-dimensional array of counters with d rows and w columns, all starting at zero, and d independent hash functions, one per row, each mapping an item to a column between 0 and w-1.

  • Increment(x, c): for each row i, add c to the counter at row i, column h_i(x).
  • Estimate(x): read the d counters row i, column h_i(x) and return their minimum.

Why the minimum? Every counter that x touches holds at least x's true count, because x added its count to it. But a counter may also include counts from other items that hashed to the same column (a collision), which can only make it bigger. So every counter is an overestimate, and the smallest one is the least contaminated. The sketch therefore never underestimates, and the estimate is the true count plus some noise from collisions.

8.2 Error bounds and sizing

Let N be the total of all increments (the stream length). Choose the width w = ceil(e / ε) (where e ≈ 2.718) and the depth d = ceil(ln(1 / δ)). Then, with probability at least 1 - δ, the estimate exceeds the true count by at most ε × N. For one row, the expected inflation of a counter is N/w (the other items spread evenly over w columns), and Markov's inequality gives a bound; each additional row makes failing all rows exponentially unlikely.

Example: ε = 0.001 (error within 0.1% of the stream) with 99% confidence (δ = 0.01) gives w = 2,719 and d = 5, which is 13,595 counters. With 4-byte counters that is about 54 KB. For a stream of 1 billion events the additive error is at most 1 million, an error that is negligible for an item with 50 million occurrences but useless for an item with 100 occurrences. That is the crucial caveat: the absolute error is proportional to the total stream, so CMS is accurate for heavy items and unreliable for rare ones.

A useful refinement is conservative update: when incrementing, only raise the counters that are currently at the minimum among the item's d cells. It cuts overestimation noticeably while keeping the never-underestimate guarantee (but it makes merging sketches by addition less exact and does not support decrements).

8.3 Heavy hitters and top-K

A common goal is the top-K or heavy hitters: the items with the highest counts, such as trending hashtags or the noisiest client IPs. A CMS alone cannot list items, since it stores only counters, not keys. The standard pattern combines it with a small min-heap of size K:

  1. For each incoming item, increment the CMS and read back its estimate.
  2. If the heap has fewer than K entries, or the estimate beats the smallest count in the heap, insert or update the item in the heap (evicting the smallest if needed).
  3. The heap always holds the current candidates for the top K, with estimated counts.

Memory is the sketch plus K entries. Because heavy hitters are exactly the items where CMS error is small relative to the count, the approach works well. Alternatives built for the same job include the Space-Saving (Misra-Gries family) algorithm, which keeps K or so counters directly and replaces the minimum counter when a new item arrives, and is often more accurate for pure top-K with less memory. Sketches merge by adding the arrays, so each shard can sketch its own traffic and a combiner sums them (for the ad click aggregation design see Case study 20).

Watch out A Count-Min Sketch overestimates; a Count-Sketch (a related structure using random plus and minus signs) is unbiased but can err in either direction. If someone says "the count is exact or too low", they are not describing CMS. And the width and depth must be sized for the expected total stream length: a sketch sized for a million events and fed a billion quietly degrades into mostly noise.

9. Other sketches worth knowing

9.1 Quantile sketches: t-digest, DDSketch, KLL

Latency dashboards need percentiles (p50, p95, p99), not averages. Exact percentiles require holding all the values, or at least a sorted copy, and percentiles cannot be combined: the p99 of the whole fleet is not the average of each server's p99. Quantile sketches keep a compact summary from which any percentile can be read, and which can be merged.

  • t-digest (Dunning) stores a few hundred centroids, each a mean plus a count, with centroids kept small near the tails (p1, p99, p99.9) and larger in the middle. This gives high accuracy exactly where latency analysis cares. It is used in Elasticsearch and several monitoring tools. Its accuracy is empirical rather than a guaranteed bound.
  • DDSketch (Datadog) guarantees a relative error, such as every reported percentile within 1% of the true value, by bucketing values on a logarithmic scale. Merging is just adding bucket counts.
  • KLL and similar compactor-based sketches give provable rank-error bounds in space independent of stream length.
  • Histograms with fixed buckets (as in Prometheus) are the simplest alternative: cheap and mergeable, but accuracy depends on picking good bucket boundaries in advance.

9.2 Reservoir sampling

Sometimes you simply want a uniform random sample of k items from a stream of unknown length, in one pass and with k items of memory. Reservoir sampling does it: keep the first k items. For item number i (counting from 1) after that, generate a random integer j between 1 and i; if j is at most k, replace reservoir slot j with the new item; otherwise skip it. By induction, at every moment each of the i items seen so far has probability exactly k/i of being in the reservoir. It is used to sample logs, trace requests, or build training sets from endless streams. Weighted variants exist where items have different importance.

9.3 Sliding-window counters

Rate limiting and "events in the last 5 minutes" need counts over a moving window. Storing every timestamp is exact but costs memory proportional to event volume. Cheaper approximations (Chapter 16) include the sliding window counter, which keeps just two fixed-window counts and estimates the current window as current + previous × (fraction of the previous window still inside the window), and exponential histograms or bucketed counters, which keep a small ring of per-slice counts (for example sixty 1-second buckets for a one-minute window) and drop the oldest slice as time advances. The error is bounded by the slice size.

9.4 Merkle trees

A Merkle tree is hashing used for comparison rather than estimation. Each leaf is the hash of a data block, and each internal node is the hash of its children, so the root hash summarizes the whole data set. Two replicas compare roots: equal roots mean identical data, and unequal roots lead to descending only into the subtrees whose hashes differ, finding the divergent blocks in logarithmic time. Dynamo-style stores, Git, and blockchains rely on this. It needs a cryptographic or at least well-mixed hash, and is covered in Chapter 33.

10.1 Accuracy versus memory

All of these structures trade accuracy for space, and the trade is generally logarithmic or square-root shaped, which is why they are so effective:

  • Bloom filter: every extra 1.44 bits per item halves the false positive rate. Going from 1% to 0.01% costs 2x the memory but cuts errors 100x.
  • HyperLogLog: error falls with the square root of memory. Four times the registers halves the error. Beyond about 12 KB, returns diminish quickly.
  • Count-Min Sketch: halving the error ε doubles the width. Raising confidence (reducing δ) only grows the depth logarithmically, so confidence is nearly free while precision costs linearly.
  • Exact structures (hash sets, maps) cost memory proportional to the distinct items. At small scale, choose them: they are simpler, exact, and cheaper to reason about.
Interview tip Use a sketch when (1) the volume is big enough that exact tracking is costly, (2) an approximate answer is acceptable to the business, and (3) you can say which direction the error goes. Stating "a Bloom filter may say yes wrongly but never says no wrongly, so a false positive costs one extra database lookup" is the sentence that shows you understand the structure. Do not propose a sketch for money, inventory, or anything that needs exact numbers.

11. Worked example: unique visitors and trending hashtags at scale

Suppose a social platform has 500 million daily active users generating 50 billion events per day (about 580,000 per second on average, with peaks maybe 3 times higher). The product team wants two things on a dashboard: unique visitors per page, per country, per day, week, and month; and the trending hashtags in the last hour, per region, updated every minute.

11.1 Unique visitors with HyperLogLog

Exact approach. One daily set of user ids for the whole platform: 500 million ids at 8 bytes is 4 GB before hash-set overhead (realistically 10 to 20 GB), and the number of dimensions multiplies it. If we track 1 million pages x 200 countries in some combination, exact sets are infeasible.

Sketch approach. Keep one HLL (12 KB) per (page, day). For 1 million active pages that is 12 GB per day, which is stored in Redis or a columnar store, and far smaller in practice because most pages are tiny and the sparse encoding keeps small sketches under 1 KB. A tiny page with 50 visitors costs a few hundred bytes. Processing flow:

  1. Each event reaches a stream processor (Kafka consumers, Chapter 34) partitioned by page id, so one worker owns each page.
  2. The worker adds the user id to the page's HLL for the current hour (PFADD), an O(1) update.
  3. An hourly sketch is stored per page. The daily number is the merge of 24 hourly sketches; weekly and monthly numbers are merges of daily ones. Merging is idempotent, so a replayed batch after a failure does not inflate the count (a major reason to prefer HLL over naive counters).
  4. Dashboards read PFCOUNT across a set of keys to get, for example, unique visitors across a group of pages, correctly deduplicating users who visited several pages.

The answer is within about 0.8% (standard error), which is fine for a dashboard. Billing-grade numbers would be reconciled with exact batch jobs.

11.2 Trending hashtags with Count-Min Sketch and a heap

Every post can contain hashtags, so the system sees maybe 100,000 hashtag mentions per second, across hundreds of millions of distinct tags over time. An exact map of tag to count per region per hour would be large and hot. The sketch pipeline:

  1. Hashtag events go to a Kafka topic partitioned by region and tag.
  2. For each region, a stream job maintains a CMS (for example 2,719 x 5 counters, 54 KB, ε = 0.001, δ = 0.01), for each time slice of one minute. The last hour is the sum of 60 slice sketches (sketches add), and expiry just drops the oldest slice. This is a sliding window built from mergeable pieces.
  3. Each worker also keeps a min-heap of the top 100 candidates. On each event the worker increments the sketch, reads the estimate, and updates the heap if the estimate qualifies.
  4. Every minute, a combiner merges the per-partition heaps: it sums each candidate's estimates from the partitions' sketches, takes the global top K, and writes them to a cache for the API to serve.
  5. To prefer trending (rising) over merely popular tags, compare the current hour's count with the baseline of the same hour over previous days, and rank by the ratio, since "#news" is always large.

Error check: if the region produces 100,000 mentions/s x 3,600 = 360 million events in the hour, the additive bound is εN = 0.001 x 360 million = 360,000. A real trending tag will have millions of mentions, so a 360,000 worst-case overcount (with 99% confidence, and usually far lower) hardly changes the ranking near the top. Tags with under 360,000 mentions might look inflated, but they are not top candidates anyway.

12. Interview Q&A

Why can't you use hash(key) mod N to place data on servers in a growing cluster, and what do you use instead?

With modulo placement the owner of almost every key changes when N changes: going from N to N+1 servers moves about N/(N+1) of all keys, which for a cache means a near-total miss storm and for a database means copying nearly all data. Consistent hashing places servers and keys on one ring and assigns each key to the next server clockwise, so adding a server moves only about 1/(N+1) of the keys, all of them to the new server. In practice I would add virtual nodes (around 100 to 256 per server) for even balance and failure spreading, and replicate each key on the next few distinct servers clockwise. If the shards are numbered and I only ever grow by appending, jump consistent hash gives the same movement guarantee with no memory.

What is the birthday bound and why does it matter when choosing a hash width?

The birthday bound says that with n items hashed uniformly into N values, the chance of some collision is about 1 - e-n²/2N, so a collision becomes likely after about 1.18 times sqrt(N) items, not after half of N. For a 32-bit hash that is only about 77,000 items, so 32-bit hashes cannot serve as unique ids for anything large. A 64-bit hash reaches 50% at roughly 5 billion items, which is acceptable for bucketing and many dedup uses with a verification step, and 128 bits or more makes accidental collision practically impossible. The takeaway is to match the width to the number of items and to compare the original keys when a wrong match would be costly.

Explain virtual nodes. What problems do they solve and what do they cost?

A virtual node is one of many positions a physical server takes on the hash ring. With one position per server, arc lengths vary a lot, so load is uneven, and when a server fails its entire load lands on its single clockwise neighbor, which may then fail too. With around a hundred positions per server, the load on each server is the sum of many small random arcs, so it concentrates tightly around the average (the relative deviation shrinks like 1/sqrt(v)), a failed server's load spreads over many survivors, and a bigger machine can simply take more vnodes. The costs are larger ring metadata, more complicated repair and streaming across many small ranges, and care to ensure replicas land on distinct physical nodes and racks.

How does a Bloom filter work, and how would you size one for 100 million items at a 1% false positive rate?

A Bloom filter is a bit array with k hash functions: adding an item sets k bits, and a query reports "maybe present" only if all k bits are set, while any zero bit proves the item was never added. So errors are one-sided: false positives are possible, false negatives are not. The false positive rate is about (1 - e-kn/m)k, minimized at k = (m/n) ln 2, and the required size is m = -n ln p / (ln 2)2. For n = 100 million and p = 1%, that is about 9.6 bits per item, roughly 960 million bits or 120 MB, with k = 7. A hash set with the actual items would be many gigabytes, which is the entire point.

Where are Bloom filters used in real systems, and what happens on a false positive?

The classic use is the LSM read path: every SSTable has a Bloom filter in memory, and a read for an absent key skips any file whose filter says no, saving a disk seek per file. They are also placed in front of a database to stop cache penetration from non-existent keys, used in crawlers to avoid refetching URLs, and in Bigtable to avoid disk reads. A false positive is harmless in each of these designs because the filter is only a guard: the system performs the real lookup, finds nothing, and wastes one read or skips one rarely-wrong page. The design requirement is that a false positive should be cheap and a false negative must be impossible, and that is exactly the filter's error profile.

How can a Bloom filter support deletions, and what are the alternatives?

A plain Bloom filter cannot delete, because clearing an item's bits could clear bits shared with other items, creating false negatives. A counting Bloom filter replaces each bit with a small counter, incrementing on add and decrementing on delete, at about four times the memory and with a risk of counter overflow. A cuckoo filter stores short fingerprints in a cuckoo hash table, supports deletion natively, and is often smaller than a Bloom filter at low error rates, but inserts can fail when it is nearly full and you must only delete items that were really inserted. If deletes are rare, periodically rebuilding a plain filter from the source of truth is often the simplest answer.

How does HyperLogLog estimate the number of distinct elements in 12 KB?

Each item is hashed, and the hash is split into a register index and a remainder. The register stores the maximum number of leading zeros seen in the remainders routed to it, because seeing a run of z leading zeros suggests roughly 2z distinct items passed through. Duplicates produce the same hash and so never change anything. Averaging many registers with a harmonic mean cancels the noise from single lucky hashes, giving a standard error of about 1.04 divided by the square root of the register count; with 16,384 six-bit registers that is 12 KB and about 0.81% error. Sketches from different servers merge by taking the register-wise maximum, which makes it perfect for distributed unique counts.

What does a Count-Min Sketch guarantee, and why is the min the right way to read it?

Every item increments one counter per row, and different items can share a counter, so each counter is at least the item's true count plus noise from colliding items. The minimum across rows is the counter with the least collision noise, so the estimate never undercounts and overcounts by at most εN with probability 1 - δ when you use width e/ε and depth ln(1/δ). Because the error is relative to the total stream length N, the sketch is accurate for heavy items and poor for rare ones. For top-K you pair it with a small heap of candidate keys, since the sketch stores no keys itself.

Compare consistent hashing, rendezvous hashing, jump hash, and Maglev. When would you pick each?

A ring with virtual nodes is the general-purpose choice when nodes join and leave arbitrarily and you need O(log n) lookups, as in Cassandra or a cache client library. Rendezvous hashing scores each node per key and takes the highest; it is simpler, spreads a failed node's keys evenly with no vnode tuning, and gives replicas as the top R scores, but costs O(N) per lookup, so it suits tens to hundreds of nodes. Jump hash needs no memory and balances almost perfectly, but only supports adding or removing the last numbered bucket, so it suits numbered shards. Maglev builds a fixed lookup table for single-array-read lookups and near-perfect balance with small disruption on change, which fits layer-4 load balancers handling packets at line rate.

How would you find near-duplicate documents among a billion pages?

Comparing every pair is n² and impossible, so I would first remove exact duplicates by content hash, then use MinHash with LSH banding for near-duplicates. Each page becomes a set of word shingles and then a signature of around 128 minimums, where the fraction of matching positions estimates the Jaccard similarity. Splitting the signature into bands and hashing each band makes similar pages collide in at least one bucket, and I run an exact comparison only on those candidate pairs, tuning bands and rows to set the similarity threshold. SimHash is the alternative: a single 64-bit fingerprint per page, where near-duplicates differ in only a few bits, searched by indexing on bit blocks. Crawlers use these to avoid indexing the same story under many URLs.

When should you not use a probabilistic structure?

Avoid them whenever the exact answer is required or the data is small enough that exact is cheap: billing, inventory, balances, access control decisions, and anything audited. Also avoid them when the error direction would be harmful, such as using a Bloom filter to decide whether a user is banned (a false positive would block an innocent user) without a confirming lookup. If the data fits in memory in a plain hash set or map, the exact structure is simpler and easier to debug. When you do use a sketch, document its error type and size it for the maximum expected volume, because a sketch overfilled beyond its design capacity degrades quickly.

13. Recap

  • A good hash is deterministic, uniform, and shows the avalanche effect. Use fast non-cryptographic hashes (xxHash, Murmur) for tables, sharding, and sketches; SipHash when keys come from untrusted sources; SHA-256 when you need integrity or content addressing.
  • Collisions appear after about sqrt(N) items (the birthday bound): about 77,000 items for 32 bits, about 5 billion for 64 bits. Do not use short hashes as identities.
  • Hash tables use chaining or open addressing, resize by rehashing when the load factor passes a threshold, and amortize the cost to O(1). Resizing is where mod N sharding breaks down across machines.
  • Consistent hashing moves only about K/(N+1) keys when a node is added. Virtual nodes smooth balance and spread failures; replicas go on the next distinct nodes clockwise; bounded loads cap hot nodes. Jump hash, rendezvous hashing, and Maglev give alternative tradeoffs of memory, lookup cost, and flexibility.
  • MinHash estimates Jaccard similarity from short signatures, LSH banding finds candidate pairs without all-pairs comparison, and SimHash gives one 64-bit fingerprint where small Hamming distance means near-duplicate.
  • A Bloom filter has no false negatives and a tunable false positive rate p ≈ (1 - e-kn/m)k; the best k is (m/n) ln 2. For 100M items at 1% it needs about 120 MB and k = 7. It cannot delete (counting and cuckoo filters can) and it guards LSM reads, caches, and crawlers.
  • HyperLogLog estimates distinct counts from leading zeros in 12 KB at 0.81% error, and merges by register-wise maximum. Count-Min Sketch estimates frequencies by taking the minimum across rows, overestimates by at most εN, and pairs with a heap for top-K.
  • Quantile sketches (t-digest, DDSketch) give percentiles that merge; reservoir sampling gives uniform samples; Merkle trees compare large datasets by hash.
  • Choose by question: membership, cardinality, frequency, quantile, similarity. Use a sketch only when volume is high, approximation is acceptable, and you know which way the error points.
