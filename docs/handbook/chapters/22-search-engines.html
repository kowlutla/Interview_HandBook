Search Engines (Elasticsearch)

A search engine answers questions such as "find the products that mention waterproof trail shoes, best matches first" in milliseconds across hundreds of millions of documents. This chapter explains why a normal database cannot do that well, how the inverted index makes it possible, how Elasticsearch and OpenSearch spread the index over a cluster, how to feed it from your real database, and what breaks in production.

1. Why databases are poor at full-text search

Suppose you run an online shop with 50 million products in a relational database. A user types waterproof trail running shoes into the search box. What does the database do with that?

The obvious first attempt is a LIKE query: WHERE description LIKE '%waterproof%'. The leading % wildcard means "anything may come before the word", so a normal B-tree index (which keeps values sorted from their first character, see Chapter 18) cannot be used. The database has to read every row and scan every description, character by character. At 50 million rows with an average description of 500 bytes that is 25 GB of text read for every keystroke-triggered search. This is a full table scan and it takes seconds to minutes, not milliseconds.

Even if speed were fixed, LIKE is the wrong tool for quality reasons:

  • No language understanding. Searching for shoe does not match shoes, and running does not match run or ran. Upper and lower case differ in some collations. Accents (cafe versus café) are different characters.
  • No ranking. A row either matches or it does not. A product that mentions "waterproof" once in a long description and one named "Waterproof Trail Shoe" both just "match". Users expect the best match first, and with 20,000 matches only the first page matters.
  • No typo tolerance. wateproof finds nothing.
  • Multi-word queries are awkward. You must write one LIKE per word, combine them with AND or OR, and still get no notion of "these words close together matter more".
  • Faceting is expensive. The side panel that says "Brand: Nike (1,204), Adidas (873) ... Price: $0-50 (3,400) ..." needs counts of the matching rows grouped by several fields at once, each a separate expensive query.

Relational databases do offer built-in full-text features (PostgreSQL tsvector with GIN indexes, MySQL FULLTEXT). They use the same core idea this chapter explains, an inverted index, and they are a perfectly good answer for a small dataset (up to a few million rows) where search is a side feature. Reach for a dedicated search engine when you need richer relevance tuning, typo tolerance, faceting at scale, high query rates that you do not want to run on your primary database, or horizontal scaling of the index itself.

Key idea A database index answers "given this exact value, where is the row?" A search index answers "given these words, which documents contain them, and which are the best matches?" The trick is to do the expensive work (splitting text into words, normalizing them) once at write time, and store the result in a structure that is organized by word instead of by document. That structure is the inverted index.

2. The inverted index, step by step

Think of the index at the back of a textbook. It does not list pages and the words on them; it lists words, each followed by the pages where it appears. That is an inverted index: it inverts the "document contains words" relationship into "word appears in documents".

We will build one from three tiny product documents. The same steps apply to three million.

Doc IDText
1Running shoes for men
2Men's trail running shoe, waterproof
3Waterproof jacket for the trail

2.1 Step 1: tokenization

Tokenization splits the raw text into tokens, usually words. A standard tokenizer splits on whitespace and punctuation, so Men's trail running shoe, waterproof becomes Men's, trail, running, shoe, waterproof. (The standard tokenizer follows Unicode text segmentation rules and keeps Men's as one token; later steps clean it up.) Each token gets a position, its index in the original text: for document 2 the positions are 0 to 4.

2.2 Step 2: normalization

Normalization makes tokens comparable. The most common step is lowercasing, so Running and running become one term. Others include removing accents (café to cafe) and stripping possessives (men's to men).

2.3 Step 3: stop words

Stop words are extremely common words such as the, for, a, of that carry little meaning. Dropping them shrinks the index and avoids huge posting lists. We drop for and the. Important detail: the positions of the remaining words are not renumbered, so the engine still knows there was a gap. Modern engines often keep stop words by default because scoring (section 5) already down-weights common words, and removing them breaks exact phrases such as "to be or not to be". Treat stop word removal as a tunable choice.

2.4 Step 4: stemming

Stemming reduces words to a root form so that related forms match each other: running becomes run, shoes becomes shoe. A stemmer is a set of rules (the Porter and Snowball families are common), not a dictionary, so it is fast but sometimes imperfect: it may reduce university and universe to the same stem. A heavier alternative, lemmatization, uses a dictionary and part-of-speech information (ran to run), at higher cost.

2.5 Step 5: posting lists with positions

After analysis, each document is a list of (term, position) pairs. The engine now builds a term dictionary, a sorted list of every distinct term, and for each term a posting list: the documents that contain it, plus the positions within each document. Storing the term frequency (how many times it appears) and positions costs space, but positions are what make phrase queries possible.

2.6 Answering a query

Take the query waterproof trail. It goes through the same analysis as the documents (this is critical, otherwise terms would not line up), giving waterproof and trail. The engine looks up each in the term dictionary (a binary search or a finite state transducer in Lucene, so the lookup is fast even with tens of millions of terms) and gets two posting lists: [2, 3] and [2, 3]. For an AND query it takes the intersection; for OR the union. Because posting lists are stored sorted by document ID, intersection is a fast merge, and Lucene uses skip pointers to jump over long runs. In this tiny example both documents match; ranking (section 5) decides the order.

Beyond the postings, Lucene also keeps other structures per field, and knowing their names helps in interviews:

  • Stored fields: the original document (the _source JSON), used to return results.
  • Doc values: a column-oriented, per-field structure (document to value) used for sorting, aggregations and faceting. The inverted index is bad at "give me the price of doc 17", so doc values answer that.
  • Norms: a small per-field number recording field length, used in scoring.
  • Points (BKD trees): used for numeric, date and geo range queries.
Key idea Search is fast because the index is organized around the question being asked. The price is paid at write time (analysis, building structures) and in storage. This is why search engines are write-heavy per document, and why you rarely want one as your only copy of the data.

3. Analyzers

The pipeline in section 2 is called an analyzer. An analyzer has three parts, run in order:

  1. Character filters work on the raw string before tokenization, for example stripping HTML tags or mapping & to and.
  2. A tokenizer (exactly one) splits the string into tokens and records positions and character offsets.
  3. Token filters transform the token stream: lowercase, stop words, stemming, synonyms, ASCII folding, edge n-grams (section 4.6).

3.1 Choosing analyzers

Elasticsearch ships with a standard analyzer (Unicode tokenizer plus lowercase), simple, whitespace, keyword (the whole string as one token), and language analyzers (for example english, which adds stop words and stemming). You can compose a custom analyzer. Real systems often index the same field several ways using multi-fields: for instance title analyzed as English text for relevance, title.exact as a keyword for sorting and exact filters, and title.autocomplete with edge n-grams for type-ahead.

3.2 Synonyms

A synonym filter maps sneakers, trainers and running shoes to a shared meaning. It is usually applied at query time, because changing synonyms then needs no reindex (index-time synonyms bake the expansion into the stored terms, so each change forces a full reindex). Multi-word synonyms are a known source of subtle bugs because positions are shifted; test them.

3.3 text versus keyword

This distinction causes more production confusion than any other. A text field is analyzed and is meant for full-text search ("contains these words"). A keyword field is stored as a single untouched term and is meant for exact match, sorting and aggregations (a brand name, a SKU, a status). A match query on a keyword field for nike will not find the value Nike, because no lowercasing was done. Strings that you need both ways get both mappings.

4. Query types

Elasticsearch queries are written as JSON (the "Query DSL"). They fall into two families: full-text queries (analyzed, scored) and term-level / filter queries (exact, not scored). Understanding which is which is the core skill.

4.1 Term query: exact and unanalyzed

A term query looks up one exact term in the index without analyzing the query. It is right for keyword, number, boolean and date fields: {"term": {"brand": "Nike"}}. It is a common mistake to run term against an analyzed text field: the indexed terms are lowercased and stemmed (nike), the query is not (Nike), and nothing matches.

4.2 Match query: analyzed full text

A match query analyzes the query string with the field's analyzer, then looks up each resulting term and combines the results, by default with OR. {"match": {"title": "waterproof trail shoes"}} finds documents containing any of waterproof, trail, shoe, and scores those with more (and rarer) terms higher. Setting operator: and demands all of them, and minimum_should_match (for example 75%) gives a middle path that is usually the best default for user queries. A multi_match query runs the match across several fields, such as title and description, with different weights.

4.3 Phrase query

A match_phrase query requires the terms to appear adjacent and in order, which it checks with the stored positions. "trail running" matches document 2 (positions 1 and 2) but a document with "running on a trail" does not. A slop value allows a few positions of looseness. Positions are the reason section 2.5 stored them.

4.4 Boolean query

The bool query combines clauses and is the workhorse of real search:

  • must: the clause has to match, and it contributes to the score.
  • should: optional; each match raises the score (or, with minimum_should_match, at least some must match).
  • must_not: excludes documents; not scored.
  • filter: has to match but does not affect the score, and the result can be cached as a bitset. Use filter for everything that is a yes/no condition: in stock, price range, category, tenant ID.

A typical product search is a bool with a must match on the text, several filter clauses for facets the user selected, and a few should clauses that boost in-stock or popular items.

4.5 Fuzzy query: typo tolerance

A fuzzy query (or fuzziness: "AUTO" inside a match query) matches terms within a small edit distance: the number of single-character insertions, deletions, substitutions or swaps needed to turn one word into another. wateproof is one edit from waterproof. Lucene builds a small automaton of all strings within the allowed distance and walks the term dictionary with it, which is efficient. "AUTO" allows 0 edits for words up to 2 characters, 1 edit for 3 to 5, and 2 for longer words. Fuzziness costs CPU and can add noise, so many systems apply it only when the exact query returns few results.

4.6 Prefix and autocomplete with edge n-grams

A prefix query matches all terms starting with a string, found by a range scan over the sorted term dictionary. It works but is expensive for short prefixes on large dictionaries. For type-ahead the better approach is to pay at index time using an edge n-gram token filter. For the word shoe with min 1 and max 4 it emits s, sh, sho, shoe. At query time the user's partial input sho is looked up as an ordinary term and found at once. The tradeoff is a larger index. You index with the n-gram analyzer but search with a plain analyzer, so the user's input is not itself n-grammed (otherwise sho would match everything containing s). Alternatives are the search_as_you_type field type, which builds these sub-fields for you, and the completion suggester, an in-memory structure for very fast prefix suggestions. The dedicated design is in the autocomplete case study.

4.7 Range queries

A range query handles numbers and dates: price between 50 and 120, created after 2025-01-01. It uses the BKD-tree points structure rather than the inverted index and belongs in a filter clause.

4.8 Aggregations and facets

Aggregations compute summaries over the matching documents in the same request: counts per brand (terms aggregation), price histogram, min/max/average, percentiles, counts per day (date_histogram), and nested combinations. They read doc values, the columnar structure, not the inverted index. This is how a product page shows facet counts without a second system. Two cautions: aggregating on a high-cardinality field (user ID, URL) uses lots of memory, and terms aggregation counts across shards are approximate for the top N because each shard reports only its own top entries (the response includes an error bound you can inspect). You can raise shard_size to improve accuracy.

5. Relevance scoring

For each matching document the engine computes a number, the score, and sorts descending. How is it chosen? Start from two intuitions.

5.1 TF-IDF intuition

Term frequency (TF): if a document mentions "waterproof" five times, it is probably more about waterproofing than one that mentions it once. Inverse document frequency (IDF): a word found in nearly every document tells you nothing, while a rare word is a strong signal. In a shoe catalogue "shoe" is in 90 percent of documents and so carries little weight, while "gore-tex" is in 1 percent and carries a lot. Multiply them: a document scores high for a term that appears often in it and rarely elsewhere. This is TF-IDF. IDF is computed as roughly the logarithm of (total documents / documents containing the term), so it grows slowly for rarity and never explodes.

5.2 BM25: the modern default

Since Elasticsearch 5 and Lucene 6 the default is BM25, which improves TF-IDF in two ways that are easy to remember:

  • Term frequency saturates. In plain TF-IDF, 20 mentions are worth four times 5 mentions. In BM25 the benefit flattens quickly: the first few mentions matter, later ones add little. This stops keyword stuffing from winning. A parameter k1 (default 1.2) controls how fast it flattens.
  • Length normalization. A word appearing once in a 5-word title is far more meaningful than once in a 5,000-word description. BM25 divides by the field length relative to the average length, with parameter b (default 0.75) controlling how strongly. This is why a match in a short title field outranks the same match in a long body.

For a multi-term query, the per-term scores are added up. You never need to recite the formula in an interview; you do need to explain these three effects: rare terms count more, repeated terms help with diminishing returns, and shorter fields count more.

5.3 Boosting

Raw BM25 knows nothing about your business. You adjust with boosts. A field boost multiplies the score from a field: title^3, description^1. A should clause on in_stock: true adds to the score of in-stock items. A function_score (or rank_feature field) blends in numeric signals such as popularity, rating, recency or sales velocity, typically through a log or saturation function so one huge value cannot dominate. Decay functions reduce the score gradually with distance from a target such as "newer is better" or "closer is better".

Large systems separate retrieval (cheaply fetch the top few hundred candidates with the inverted index) from re-ranking (run an expensive machine-learned model over just those candidates). Elasticsearch supports a learning-to-rank rescoring phase and a general rescore query for this pattern. Never evaluate an expensive model over all matches.

Interview tip When asked "how would you improve relevance", answer with a loop: log queries and clicks, define a metric (click-through rate on the top results, or NDCG against labelled judgments), change one thing (analyzer, boost, synonym), compare offline against a judged query set, then A/B test. Relevance is tuned empirically, not guessed.

6. Segments, refresh, flush and near-real-time search

Elasticsearch is built on Apache Lucene, a Java search library. Everything an Elasticsearch shard does at the storage level is a Lucene index, so Lucene's design decides how writes behave.

6.1 Immutable segments

A Lucene index is a collection of segments. A segment is a small, complete, self-contained inverted index (term dictionary, postings, stored fields, doc values) over some set of documents. The defining property: a segment is immutable. Once written it is never modified. This sounds restrictive but brings large benefits: no locking between readers and writers, the files can be cached aggressively by the operating system, compression is simple, and caches such as filter bitsets stay valid for the life of the segment. It is the same idea as the immutable sorted files of an LSM tree (see Chapter 19).

A search runs against every segment of the shard and merges the results. New documents never get added to an existing segment; they go into a new one.

6.2 The write path: buffer, translog, refresh

  1. An index request reaches the primary shard. The document is analyzed and added to an in-memory indexing buffer. It is not yet searchable.
  2. The same operation is appended to the translog (transaction log), a write-ahead log on disk. By default Elasticsearch fsyncs the translog on every request (the request durability setting), so an acknowledged write survives a crash. The alternative async setting syncs every few seconds, trading durability for throughput.
  3. A refresh happens by default every 1 second (if the index has been searched recently). Refresh writes the buffer out as a new small segment and opens it for search. The segment sits in the operating system's file cache and has not necessarily been fsynced to disk. After refresh the documents are searchable.
  4. A flush is a Lucene commit: it fsyncs all segments to disk, writes a commit point listing them, and then trims the translog since those operations are now durable in segments. Flushes happen automatically when the translog grows large (by default 512 MB) or after a time interval. After a crash, Elasticsearch restarts from the last commit point and replays the translog to recover the operations since.

6.3 Near-real-time search

Because visibility waits for the next refresh, Elasticsearch is near real time, not real time: a just-indexed document typically appears within about a second. A get-by-ID request is real time (it can read from the translog), but a search is not. If you need read-your-writes in a test or a UI, the index API accepts refresh=wait_for (wait until the next scheduled refresh includes the document) or refresh=true (force one now; costly if used per document, since it creates many tiny segments). During large bulk loads, a common tuning is setting refresh_interval to -1 (off) or 30 s, then restoring it, so the engine builds fewer, larger segments.

6.4 Merges

One new segment per second would soon mean thousands of segments, and every search must visit all of them. A background merge process picks several similar-sized segments and rewrites them into one larger segment, then deletes the old ones. Merging uses disk I/O and CPU, so it is throttled, and it is why heavy indexing can slow searches. The merge policy groups segments in tiers so the total count stays in the tens rather than thousands. A force merge down to one segment is an option for indices that will never be written again (such as yesterday's logs), giving the fastest searches.

6.5 Deletes and updates as tombstones

Because segments are immutable, you cannot remove a document from one. A delete only marks the document as deleted in a per-segment bitmap (a tombstone). Searches skip marked documents. The data is physically removed only when that segment is merged. An update is therefore a delete of the old version plus an index of a new version into a fresh segment. Consequences: updating a large document frequently is costly, a document being updated constantly creates a stream of tombstones, and disk usage can temporarily grow after bulk deletes until merges catch up. Elasticsearch also keeps a per-document _version and, for concurrency control, _seq_no and _primary_term, so that conflicting updates can be detected.

Watch out Elasticsearch does not support multi-document transactions, and a "partial update" still rewrites the entire document internally. Design documents so that fields that change very frequently (a view counter, a live stock level) are not inside a huge document that otherwise never changes, or store them outside the index and apply them at rank time.

7. Cluster architecture

A single Lucene index lives on one machine. Elasticsearch (and its fork OpenSearch, which shares nearly all of this design) turns many machines into one distributed search service. The vocabulary:

  • Node: one running server process. Nodes join a cluster, a named group that shares state.
  • Index: a logical collection of documents with a shared mapping, roughly comparable to a database table (for example products).
  • Shard: a slice of an index. Each shard is a complete Lucene index. An index with 6 primary shards stores its documents divided over 6 Lucene indices. The shard is the unit of distribution and parallelism.
  • Primary shard and replica shard: every document belongs to exactly one primary shard. A replica is a copy of a primary, placed on a different node. Replicas serve two purposes: high availability (if a node dies, a replica is promoted to primary) and read throughput (searches can go to either copy).

7.2 Routing: which shard owns a document?

When you index a document, Elasticsearch computes shard = hash(_routing) mod number_of_primary_shards, where _routing defaults to the document ID (a murmur3 hash is used). Every node can compute this, so any node can forward the request to the right primary without a lookup table. This is the classic hash-partitioning of Chapter 25, and it has its classic consequence: the number of primary shards is fixed at index creation. If you changed it, the modulo would map existing IDs to different shards and you could not find your data. (Split and shrink APIs exist, but they create a new index with a compatible shard count; the fix in general is reindexing, section 11.)

You can supply a custom routing value, such as a tenant ID, so all of a tenant's documents land on one shard and a tenant-scoped search touches one shard instead of all. The cost is risk of uneven shard sizes if one tenant is huge.

7.3 The indexing request path

A write goes to the coordinating node, which routes it to the primary shard. The primary indexes the document, then forwards the operation in parallel to all in-sync replicas, and replies success once the replicas have acknowledged. The cluster tracks an "in-sync" set of copies; a replica that falls behind is dropped from it and rebuilt. By default a write needs only the primary to be active (wait_for_active_shards=1), though you can require more. Replication is synchronous within the in-sync set, which gives strong per-document behaviour on writes, but the document is only searchable after the refresh on each copy. See Chapter 24 for replication theory.

8. How a search executes: scatter-gather

A search cannot be answered from one shard, because the matching documents are spread across all of them. Elasticsearch uses a scatter-gather in two phases, called query then fetch.

  1. Request. The client sends the search to any node, which becomes the coordinating node for this request.
  2. Query phase (scatter). The coordinator sends the query to one copy of every shard of the index (primary or replica, chosen by adaptive replica selection, which prefers the faster, less loaded copy). Each shard runs the query locally against its segments and builds a priority queue of its top from + size hits. It returns only document IDs and scores, not the documents.
  3. Merge (gather). The coordinator merges the per-shard lists into one globally sorted list and picks the winning page.
  4. Fetch phase. The coordinator asks only those shards that own a winning document to return the full _source (and highlights) for exactly those IDs. It assembles the final response.

8.1 Why the cost grows with the number of shards

The query latency is determined by the slowest shard (the tail-latency effect described in Chapter 8): the coordinator has to wait for all of them. Adding shards parallelizes the per-shard work but adds coordination overhead and more chances for one slow shard. A search for 10 hits over 100 shards makes the coordinator merge 1,000 candidates; this is the root of the deep pagination problem in section 14.

8.2 A subtlety: scores are per shard

BM25's IDF uses document counts from the shard being searched, not the whole index. With small or unevenly filled shards, the same term may get slightly different IDF on different shards, producing odd rankings. On large indices the statistics converge and the effect vanishes. The dfs_query_then_fetch search type runs an extra step to gather global statistics first, which is worth it only for small datasets or testing.

9. Shard sizing and the too-many-shards problem

The shard count is the most consequential decision you make for an index, and it cannot be changed cheaply. Each shard is a full Lucene index with its own open files, memory structures (term dictionary, caches), and cluster-state entry. Two opposite mistakes occur.

9.1 Too many shards (oversharding)

Teams frequently create an index per customer, per day, or give each index 10 shards "to be safe". The cluster ends up with tens of thousands of tiny shards. Problems: every shard costs heap memory on its node, even when idle; the master must store and publish a huge cluster state to every node on each change, making shard moves and index creation slow and risking master instability; each search fans out to every shard, so latency and thread-pool pressure grow; and recovery after a node loss involves many small shard copies. A widely quoted guideline is to keep no more than about 20 shards per GB of heap on a node, and the current guidance prefers fewer, larger shards.

9.2 Too few or too large shards

One giant shard cannot be spread across nodes, so search over it is single-threaded per shard and cannot use the whole cluster. Recovery and rebalancing of a 500 GB shard moves hundreds of gigabytes over the network and takes hours. Merges on huge shards are heavy.

9.3 Rules of thumb

  • Target shard sizes of roughly 10 to 50 GB for search workloads (up to around 50 GB for log-style data; Elastic's guidance is often 10 to 50 GB), and avoid exceeding about 200 million documents per shard.
  • Choose primary shards so the index reaches a few tens of GB per shard at its expected size, and so shard count is a small multiple of data node count to spread load evenly.
  • Plan from the data size: 300 GB of expected index at 30 GB per shard is 10 primary shards.
  • Replicas are changeable at any time; primary count is not. Start with 1 replica, add more for read-heavy load.
  • If you have many small tenants, do not make an index each. Put them into shared indices with a tenant ID field, a custom routing value, and filtered aliases (section 11), and give only the very large tenants their own index.

10. Mappings and dynamic mapping pitfalls

A mapping is the schema of an index: it lists every field, its type (text, keyword, long, double, date, boolean, nested, dense_vector, ...), and its analyzer and options. The mapping decides which structures are built (inverted index, doc values, points).

10.1 Dynamic mapping

By default Elasticsearch is schema-on-write: if you index a document with a field it has not seen, it guesses a type and adds the field to the mapping. A string becomes both a text field and a keyword sub-field (up to 256 characters), a whole number becomes long, a decimal becomes float, and a string that looks like a date becomes date. This is convenient for experiments and dangerous in production.

  • Wrong guesses are permanent. You cannot change the type of an existing field. If the first document has "price": "12" (a string) and later ones have numbers, indexing errors follow. The fix is to create a new index with the right mapping and reindex.
  • Mapping explosion. If you index arbitrary JSON keys (for example a map keyed by user ID or by log label), each new key becomes a new field. Tens of thousands of fields bloat the cluster state and heap and can destabilize the master. There is a safety limit (index.mapping.total_fields.limit, default 1,000), but raising it just moves the problem. Fix by modelling variable keys as a list of key/value objects, using the flattened type, or setting dynamic: strict.
  • Wasted indexing. Every string becomes a text field and a keyword field, even when you only filter on it. That doubles storage.

Best practice in production: define an explicit mapping through an index template, set dynamic: strict (reject unknown fields) or false (store but do not index them), disable indexing on fields you will never search (index: false), and turn off doc_values or _source overheads only with care.

10.2 Nested objects

Elasticsearch flattens JSON arrays of objects. A product with variants [{color: red, size: S}, {color: blue, size: L}] is stored as color: [red, blue] and size: [S, L], so a query for "red and L" falsely matches. The nested type indexes each element as a hidden separate Lucene document so the correlation is kept, at the price of more documents and slower queries and updates. Prefer denormalizing into flat documents; use nested only when you truly need correlated sub-fields. Real SQL-style joins are limited (the join field type is slow and discouraged), so search documents should be denormalized: put the brand name and category name directly into the product document rather than referencing other indices.

11. Reindexing and aliases for zero-downtime changes

Since primary shard count and field types cannot change in place, you will need to reindex: create a new index with new settings or mapping, copy all data into it, and switch over. The _reindex API copies documents from one index to another (it reads from the source and bulk writes to the destination, optionally transforming), and it runs as a throttle-able background task.

The switch is made safe with an alias: a name that points to one or more indices. Applications never use the real index name; they query and write to the alias products, which today points to products_v1. The change flow:

  1. Create products_v2 with the new mapping and shard count.
  2. Reindex from products_v1 to products_v2 while v1 keeps serving traffic.
  3. Keep v2 up to date with changes that arrived during the copy. Typically the indexing pipeline dual-writes to both, or you replay the change stream from the moment the copy started (section 13).
  4. Verify counts and sample queries on v2.
  5. Swap the alias in a single atomic call that removes products from v1 and adds it to v2. Readers see no gap.
  6. Keep v1 for a while as a rollback, then delete it.

Aliases have other uses: a filtered alias embeds a filter (for example tenant_id: 42) so a tenant's code can query only its own slice; a write alias designates one index among several as the write target (used by rollover, next section); and an alias may span several indices to search them as one.

12. Time-based indices and Index Lifecycle Management

Logs, metrics, events and other time-series data have a distinctive pattern: they are written once, mostly queried while recent, and eventually deleted. Putting them all into one growing index is a mistake, because deleting old documents leaves tombstones and needs expensive merges, and shards grow without bound. Instead, use time-based indices: logs-2026.11.17, or better, a data stream, a managed abstraction that routes writes to the current backing index and searches across all of them.

Dropping old data then becomes deleting a whole index: a cheap metadata operation that frees disk at once, with no tombstones.

Index Lifecycle Management (ILM) (OpenSearch has the similar ISM) automates the phases by policy:

PhaseTypical actionHardware
HotReceives writes; rollover to a new index when it reaches, say, 50 GB or 1 day oldFast SSDs, many CPUs
WarmNo more writes; shrink shard count, force merge to fewer segmentsCheaper disks
Cold / frozenRarely searched; reduce replicas, or mount from a snapshot in object storage (Chapter 21) as a searchable snapshotLarge cheap storage
DeleteDelete after the retention period (for example 90 days)n/a

Product catalogs are not time-series, so they use the alias-and-reindex pattern from section 11. Event and log data uses ILM. Snapshots to object storage are the backup mechanism for both.

13. Indexing pipeline: keeping search in sync with the source of truth

The central architectural rule: the search index is a derived view, not the system of record. Your orders, products and users live in a primary database (see Chapter 20 and Chapter 18). The search cluster holds a copy shaped for querying. If the index is lost or corrupted you must be able to rebuild it from the source. This has design consequences for how data gets in.

13.1 Options for feeding the index

ApproachHow it worksProblem
Dual writeThe application writes to the DB and then to Elasticsearch in the same request.Not atomic. If the second write fails or the process dies between them, the two stores silently diverge. Concurrent updates can land in opposite order in the two stores. Avoid.
Periodic batch syncA job queries "rows changed since last run" and bulk indexes them.Delay equal to the schedule; hard-deleted rows are missed unless you use soft deletes; load on the DB.
Transactional outboxThe app writes the business row and an "event" row in one DB transaction; a relay publishes the events to a queue.Needs an extra table and relay, but is atomic and works with any DB.
Change data capture (CDC)A tool such as Debezium reads the database's own write-ahead log and emits an event per row change to Kafka. An indexer consumes them and updates the index.Operational complexity, but no application changes, captures deletes, and keeps order per row.

13.2 Making the indexer correct

  • Idempotent writes. Queues deliver at least once, so the same event may arrive twice. Index the document using the database primary key as the document _id: replaying an event simply overwrites the same document with the same content.
  • Ordering and stale writes. If events for one row are processed out of order, an old version could overwrite a newer one. Key the Kafka topic by row ID so one row's events are ordered within a partition, and use external versioning: index with version_type=external and the row's version or update timestamp, so Elasticsearch rejects any write whose version is not higher than what is stored.
  • Bulk requests. Index through the _bulk API in batches of roughly 5 to 15 MB (or a few thousand documents), not one document at a time. Handle partial failures: a bulk response reports a status for each item, and a 429 means the cluster is overloaded and you must back off and retry.
  • Deletes. Propagate deletes as events (CDC provides tombstone events). Otherwise deleted products linger in search.
  • Denormalization. The search document usually joins data from several tables (product, brand, category, price). A change in a brand name must update every product of that brand; design the indexer to find and re-emit the affected documents, or tolerate brief staleness.

13.3 Backfill and reindex

You will need to rebuild the index: after a mapping change, after a bug in the indexer, or on first launch. Build the new index (products_v2) off to the side: record the current position of the change stream, scan the source table in primary-key ranges and index each row, then start consuming the change stream from the recorded position so edits made during the scan are applied on top. External versioning ensures a late-arriving old scan result never overwrites a newer change. When v2 has caught up, swap the alias (section 11). This pattern also appears in Chapter 26 for data migrations.

13.4 Eventual consistency in the product

Between a database commit and the search index showing it there is lag: CDC delay, queue wait, indexing, and the refresh interval. It is usually one to a few seconds but grows under load, and you must design for it. A seller who edits a product and immediately searches for it may not see the change. Common mitigations: show the user's own edits from the database on the confirmation page, not from search; for key flows read the final state from the DB by ID after a search returns the ID (and filter out items that no longer exist); and monitor lag as a first-class metric. This is the same pattern as event-driven read models in Chapter 36 and ties into Chapter 46.

14. Deep pagination and search_after

The simple pagination parameters are from and size: from=10000, size=10 shows page 1,001. To honour it, every shard must collect its top from + size = 10,010 hits and send IDs and scores to the coordinator, which merges 10,010 × (number of shards) entries to pick 10. With 10 shards that is 100,100 entries held in memory for one page. Cost grows linearly with depth, and many queries at once can exhaust memory. Elasticsearch therefore refuses from + size beyond 10,000 by default (index.max_result_window). Raising the limit is the wrong fix.

14.1 Alternatives

  • search_after: each request returns a sort value for its last hit, and the next request passes it back: "give me the 10 documents that sort after this one". Each shard only needs to find the top 10 after that position, so cost is constant regardless of depth. You need a deterministic total order, so add a unique tiebreaker such as the document ID to the sort. Limits: you can only move forward, not jump to page 500.
  • Point in time (PIT): opens a frozen view of the index so that pages are consistent while documents are being indexed; combine PIT with search_after.
  • Scroll: the older bulk-export mechanism, which holds a snapshot open. Now recommended only for big exports, not for user-facing paging.

For user interfaces, the honest product answer is that nobody looks past page 10: cap the depth, show "refine your search" instead, and offer "next / previous" with search_after. Interviewers like to hear that "jump to page N" is intentionally unsupported at scale. The same trade-off, offset versus cursor, appears in Chapter 5.

15. Consistency and durability: why it is not a primary database

Elasticsearch is excellent at search and acceptable as a datastore for logs, but you should not make it the only home of data you cannot lose. Reasons to state clearly:

  • Near-real-time visibility. Section 6.3: writes are searchable after a refresh, not immediately, and there is no read-your-writes guarantee for searches.
  • No multi-document transactions or constraints. There are no foreign keys, no unique constraints beyond the document ID, and no atomic updates across documents. Updates to one document are atomic.
  • Replication is per-shard; the cluster is not a CP database in the strict sense. Writes are acknowledged by the primary and in-sync replicas, and the cluster handles a node failure well, but historic split-brain bugs, mapping conflicts, and corruptions after a crash have meant that practice is "snapshot regularly and keep a rebuild path". With default settings and a single replica, losing two nodes that hold both copies of a shard loses that shard.
  • Translog durability is configurable. If you set async, you may lose the last few seconds of acknowledged writes in a crash.
  • Schema pitfalls (section 10) and reindex-only changes make it costly to correct mistakes.
  • Distributed counts. Aggregation counts across shards can be approximate (section 4.8), and the total hit count is capped to 10,000 unless track_total_hits is requested because exact counting is expensive.

Therefore: keep the source of truth in a database, treat the index as rebuildable, take snapshots to object storage, and rehearse a full rebuild. See Chapter 28 for the vocabulary of consistency models.

16. Scaling and a capacity sizing example

Scaling levers, in rough order of use: add replicas for read throughput and availability; add data nodes so shards spread out and each carries less; add shards through a reindex when a single shard is too big; separate hot and warm tiers; add dedicated masters and coordinating nodes as the cluster grows; and cache hot queries upstream (a filter cache lives inside; an application cache like Redis in front handles repeat top queries, see Chapter 13).

16.1 Worked sizing: product search for a marketplace

Requirements: 50 million products, average search document 2 KB of source; 5,000 searches per second at peak; 200 product updates per second on average (bursts to 2,000); p99 search latency under 200 ms; survive one node failure.

  1. Raw data. 50 M × 2 KB = 100 GB of source JSON. The index on disk is typically comparable to or somewhat larger than the source once inverted index, doc values and stored fields are included; we use a factor of about 1.3 and get roughly 130 GB of primary data. (Always measure with a sample; the factor varies widely.)
  2. With one replica. 130 GB × 2 copies = 260 GB. Add 15 to 25 percent of free-disk headroom for merges and watermarks (Elasticsearch stops allocating shards at about 85 percent full by default), giving about 340 GB of disk across the cluster.
  3. Shard count. At about 30 GB per shard, 130 GB gives about 4 to 5 primary shards. For growth (we expect 2x in two years) and even spread over 6 data nodes, pick 6 primary shards, each starting around 22 GB. With one replica that is 12 shard copies, 2 per node.
  4. Query load. 5,000 searches per second, each fanning out to all 6 shards, means 30,000 shard-level searches per second spread over 6 nodes: 5,000 per node. A node with 16 cores, a good page cache and a well-formed bool-with-filters query can serve in the order of a few thousand simple shard queries per second, so this is near the edge. Add headroom: choose 6 data nodes of 16 vCPU / 64 GB RAM (about 31 GB heap, rest left for the OS page cache) and a second replica if load tests show saturation, or reduce fan-out by caching the top queries (a 30 to 50 percent hit rate removes a large share of load).
  5. Memory. Give the JVM heap no more than half of RAM and no more than about 31 GB (to keep compressed object pointers). The rest of the RAM becomes the OS file cache, which is what makes search fast: ideally the hot parts of the 260 GB index fit in the cache across the cluster (6 × ~30 GB = 180 GB of cache), so most reads avoid disk. SSDs are mandatory.
  6. Indexing load. 200 updates per second average, 2,000 at burst, is trivial for bulk indexing (a node can ingest thousands to tens of thousands of small documents per second). The concern is merge and refresh pressure, not raw throughput. The CDC pipeline absorbs bursts in Kafka.
  7. Masters and failures. Add 3 small dedicated master nodes (2 vCPU / 8 GB). If one data node dies, its 2 shards' replicas on other nodes are promoted, then new replicas are copied (about 22 GB each over a 10 Gbps link takes a few minutes), so capacity should be planned for N-1 nodes: 5 nodes must still hold p99 under 200 ms.

Result: roughly 9 nodes (6 data, 3 master) plus the Kafka consumers. The interview point is not the exact figure but the method: data size, then shard count from target shard size, then fan-out multiplication of query load, then memory split between heap and page cache, then failure headroom.

18. Failure modes

18.1 Split brain (historic) and the cluster manager

In old Elasticsearch (before version 7), master election was based on a setting minimum_master_nodes that operators had to set correctly to a majority. If it was misconfigured, a network partition could let two groups each elect a master, and each accepted writes: split brain, producing divergent data that could not be merged. Version 7 introduced a new coordination layer that automatically uses voting-configuration quorums (majority of master-eligible nodes), removing the manual setting. The lesson: run an odd number (3) of master-eligible nodes so a majority always exists on one side of a partition, the same principle as consensus protocols. Never put master and heavy data roles on the same overloaded nodes.

18.2 Heap pressure and garbage collection

Elasticsearch runs on the JVM. Large aggregations, a huge number of shards, big fielddata on text fields, deep pagination, and giant bulk requests all use heap. When the heap fills, garbage collection pauses grow, a node stops responding to the master's pings, is considered dead, and is removed; its shards are reassigned, creating more load on other nodes, a possible cascade. Circuit breakers reject requests that would exceed memory limits. Mitigations: heap at or below 31 GB and half of RAM; avoid fielddata (use keyword with doc values); limit aggregation cardinality; fewer shards; monitor GC time and heap after collection.

18.3 Hot shards and hot nodes

If custom routing sends a big tenant's data to one shard, or time-based indices put all current writes on a few hot-tier nodes, one node's CPU and disk saturate while the rest idle, and the slowest-shard rule (section 8.1) drags every search down. Mitigations: even routing, more shards or splitting large tenants into their own indices, balancing of shard allocation by disk and load, and routing reads to the less loaded replica.

18.4 Mapping explosion

As described in section 10, unbounded dynamic field names inflate the cluster state until the master struggles and indexing slows. Prevent it with strict mappings and field-count limits and alert when field count rises.

18.5 Other incidents

  • Disk watermarks. At about 85 percent disk the node stops receiving new shards; at 90 percent shards are moved away; at 95 percent the index is made read-only to protect it. The first symptom is often "indexing suddenly fails". Alert at 70 percent.
  • Expensive queries. Leading wildcards, regular expressions, script scoring over millions of documents, and huge terms filter lists can monopolize search threads. Set query timeouts and limit what clients may send.
  • Thread pool rejections (HTTP 429). The search or write queue fills when load exceeds capacity; clients must back off with jitter (Chapter 40) instead of retrying instantly.
  • Unassigned shards / red cluster. A red cluster has a missing primary shard; yellow means a replica is unassigned. Use the allocation explain API to find why.
  • Node restarts causing rebalancing storms. A brief restart triggers shard copying; set delayed allocation so the cluster waits a few minutes before rebuilding replicas.

19. Worked example: product search end to end

We design search for the 50 million product marketplace used in section 16. The user types waterproof trail runing shoes, then filters by brand and price.

19.1 Index design

Each product is one denormalized document: id (keyword), title (text with English analyzer, plus title.autocomplete using edge n-grams), description (text), brand and category (keyword, for facets), price (scaled float), in_stock (boolean), rating, sales_30d and updated_at (numbers/date), and tenant_id if sellers are separated. The mapping is explicit and dynamic: strict. Six primary shards and one replica, written through the alias products.

19.2 The query

The application builds one request: a bool query. The must clause is a multi_match over title^3, brand^2, description with fuzziness: AUTO and minimum_should_match: 75% (so runing still finds "running"). The filter clauses carry the chosen brand and the price range, plus in_stock: true; these are cached bitsets and are not scored. A should clause boosts rating above 4. A function_score adds log1p(sales_30d) as a gentle popularity boost. The request also asks for terms aggregations on brand and category and a price histogram to fill the facet sidebar, computed over the same hits. Results are sorted by score then by id as tiebreaker, and paging uses search_after.

19.3 What happens inside

  1. The query text passes through the English analyzer: waterproof, trail, runing, shoe. The fuzzy match expands runing to the dictionary term run within edit distance.
  2. The coordinator sends the query to 6 shards (one copy each). Each shard intersects posting lists (filters first, as cheap bitsets), scores candidates with BM25 plus boosts, and returns its top 10 IDs, scores and its partial aggregation buckets.
  3. The coordinator merges, runs the fetch phase for the 10 winners (and highlights matched words), and returns results with facet counts. Typical latency is tens of milliseconds.

19.4 Keeping it fresh

The catalog service writes to PostgreSQL. Debezium streams row changes to Kafka topic product-changes keyed by product ID. An indexer consumer groups changes into bulk requests with external versioning (updated_at as the version) and writes to the products alias. Inventory changes arrive on a separate topic and update only the in_stock field via a partial update. A nightly reconciliation job compares row counts and a sample checksum between DB and index and alerts on drift. Deletes arrive as tombstone events.

19.5 Changing the design later

When the team wants to add a new analyzer and double the shard count, it creates products_v2, backfills through the same Kafka pipeline, verifies, and swaps the alias with no downtime. Autocomplete is served by title.autocomplete plus a small cache for the top prefixes. Semantic search is added later as a vector field and a hybrid query that merges keyword and vector rankings. The result is a system where the database remains authoritative and the search cluster can be wiped and rebuilt on demand.

20. Interview Q&A

Why not just use LIKE or a database index for search?

A B-tree index sorts values from the first character, so a pattern with a leading wildcard cannot use it and the database scans every row. Even with a scan you get no stemming, no typo tolerance, and no relevance ranking, only match or no match. A search engine does the analysis once at index time and stores an inverted index mapping each term to the documents containing it, so a lookup costs time proportional to the matches rather than to the table size. For small datasets, database full-text indexes (such as PostgreSQL GIN) use the same idea and may be enough.

Explain the inverted index and how a multi-word query uses it.

The engine tokenizes each document, normalizes tokens (lowercasing, stemming, optionally dropping stop words), and records for every term the sorted list of document IDs containing it, plus term frequencies and positions. A query goes through the same analysis. The engine looks up each query term in the sorted term dictionary and gets its posting list, then intersects the lists for an AND query or unions them for an OR query, scoring each result. Positions let it verify phrases by checking that terms are adjacent and in order.

How does BM25 differ from TF-IDF, and why does a title match outrank a body match?

Both reward terms that are frequent in a document and rare across the collection. BM25 adds saturation, so repeating a word many times gives diminishing returns, and length normalization, so a match in a short field counts more than the same match in a long one. A title is short, so one occurrence there is a stronger signal than one in a long description. On top of that you usually apply explicit field boosts such as title^3 to encode that you trust titles more.

What happens between indexing a document and being able to search it? What if a node crashes?

The document is analyzed into an in-memory buffer and appended to the translog, which is fsynced on each request by default. About once a second a refresh turns the buffer into a new immutable segment and makes it searchable, which is why search is near real time. A flush later fsyncs segments to disk, writes a commit point and trims the translog. If a node crashes, it recovers from the last commit and replays the translog, so acknowledged writes are not lost with the default durability setting.

How are deletes and updates implemented, and what is the cost?

Segments are immutable, so a delete only flags the document as deleted in a bitmap and searches skip it. The space is reclaimed when background merges rewrite the segment. An update is a delete of the old version plus the indexing of a new full document, even if you changed one field. Workloads with constant updates to big documents therefore create many tombstones and merge pressure, so you should keep volatile fields small or out of the index.

Walk through how a distributed search is executed.

The client sends the request to any node, which acts as coordinator. In the query phase the coordinator forwards the query to one copy of every shard; each shard returns its top from+size document IDs and scores. The coordinator merges these into the global top results. In the fetch phase it asks only the shards owning the winning documents for the actual source. Latency is set by the slowest shard, and deep pages are costly because each shard must return from+size entries.

How do you choose the number of shards, and what goes wrong if you choose badly?

Estimate the final index size and divide by a target shard size of about 10 to 50 GB, then round to a number that spreads evenly across data nodes. The primary shard count is fixed at creation because documents are placed by hash mod shard count, so changing it requires a reindex. Too many tiny shards waste heap, bloat the cluster state and increase fan-out per search; too few giant shards cannot be parallelized or moved quickly. Many small tenants should share indices with routing or filtered aliases rather than get one index each.

How do you change a mapping or shard count with zero downtime?

Applications use an alias rather than the concrete index name. You create a new index with the desired mapping and settings, copy the data with the reindex API or by replaying from the source database through the normal indexing pipeline, and keep applying live changes during the copy. After validating counts and queries, you swap the alias to the new index in one atomic operation. Rollback is another swap, and the old index is deleted after a safe period.

How do you keep Elasticsearch in sync with the primary database?

Avoid dual writes from the application because failures between the two writes cause silent divergence. Use change data capture or a transactional outbox to produce an ordered change stream per row into Kafka, and a consumer that bulk-indexes using the row ID as document ID and external versioning so replays and out-of-order events are harmless. Include deletes, a backfill path that uses the same code, a dead-letter queue, and a reconciliation job. Accept and monitor eventual consistency of a few seconds.

Why is deep pagination a problem and what do you do instead?

With from and size, every shard must build and return from+size candidates, and the coordinator must merge shards times from+size entries, so memory and time grow with page depth. That is why there is a default cap of 10,000. Use search_after with a unique tiebreaker sort so each page costs the same, combined with a point in time for a consistent view. The trade-off is that you can only go to the next page, which suits infinite scroll and is fine because users rarely go deep.

Can Elasticsearch be the primary database? Why or why not?

It is usually a poor choice as the only copy. It offers near-real-time rather than immediate visibility, no multi-document transactions or constraints, schema changes that need reindexing, and a history of data issues under partitions and misconfiguration. The right pattern is a primary database as source of truth, the search index as a rebuildable derived view, and regular snapshots. For logs and metrics, where losing a little data is tolerable and retention is by time, using it as the main store is common and acceptable.

What are the common production failure modes?

Heap pressure from large aggregations, too many shards or fielddata causes long garbage collection pauses and nodes dropping out, which cascades. Hot shards from skewed routing or hot-tier concentration make the slowest shard dominate latency. Mapping explosion from unbounded dynamic field names overloads the master. Disk watermarks make indices read-only. Historically, a wrong minimum master setting could cause split brain; modern versions use quorum-based elections, and you should run three dedicated master-eligible nodes.

21. Recap

  • Databases scan for substrings and cannot rank; a search engine builds an inverted index at write time from analyzed tokens (term to posting list with positions).
  • An analyzer (character filters, tokenizer, token filters) must match at index and query time. Use text for full-text and keyword for exact values, sorting and facets.
  • Use bool queries with scored must/should and unscored, cacheable filter; fuzzy for typos, edge n-grams for autocomplete, aggregations over doc values for facets.
  • BM25 rewards rare terms, saturates repeated terms and favours short fields; business signals are added through boosts and rescoring.
  • Lucene segments are immutable. Writes go to a buffer and translog; refresh (about 1 s) makes them searchable, flush commits them, merge compacts and purges tombstones.
  • An index has fixed primary shards (hash of ID mod N) and changeable replicas; a search is a scatter-gather in query then fetch phases through a coordinating node.
  • Size shards at roughly 10 to 50 GB; avoid oversharding; define mappings explicitly and use aliases plus reindex for zero-downtime changes; use data streams and ILM for time-based data.
  • Keep the database as the source of truth; feed the index with CDC or outbox through a queue using idempotent, versioned bulk writes; plan backfills; accept eventual consistency.
  • Use search_after for deep paging, treat the cluster as rebuildable with snapshots, and watch for heap pressure, hot shards, mapping explosion and disk watermarks.
