API Gateway and BFF

An API gateway is the single front door to a set of backend services: it checks who you are, limits how much you can ask, routes you to the right service, and handles dozens of chores so that each service does not have to. This chapter explains what a gateway does, how a request moves through it, how it differs from a proxy, a load balancer and a service mesh, how the Backend-for-Frontend pattern works, and how gateways fail.

1. Why a gateway exists

Imagine a company that started with one application and has now split it into forty services: users, orders, payments, catalog, search, recommendations, notifications, and so on. Clients (a mobile app, a web app, partner systems) need to call these services. The simplest approach is to let every client talk to every service directly. It works for a week, and then the problems appear.

  • The client must know the internal layout. The mobile app has to know the address of the orders service, the catalog service and the payments service. If you split or merge services, or move one to a new address, every client must be updated. Mobile apps are especially bad here, because old versions stay installed for years.
  • Every service repeats the same chores. Each of the forty services has to validate login tokens, enforce rate limits, write access logs, terminate TLS, and reject malformed requests. That is forty implementations in several languages, with forty chances to get one subtly wrong. A security fix then means forty deployments.
  • Every service is exposed to the internet. Forty public endpoints means forty attack surfaces, forty certificates, and forty firewall rules.
  • Clients make many round trips. To draw one screen, the app may call five services. Each call crosses the slow, unreliable public internet (the latency and handshake costs are discussed in Chapter 12).
  • Internal protocols leak out. Internally you may prefer gRPC or a message format that browsers cannot speak. Clients want plain HTTP and JSON.

An API gateway is a server that sits between external clients and your backend services and is the single entry point for all API traffic. Clients know exactly one address. The gateway receives each request, applies the shared chores (called cross-cutting concerns because they cut across every service rather than belonging to one), and forwards the request to the correct backend. The response travels back through the gateway to the client.

Key idea A gateway gives you one place to enforce policy (who may call, how often, with what data) and one stable public contract that hides how the backend is organized. The price is that this one place now sits on the path of every request, so it must be fast, highly available, and kept free of business logic. Most of this chapter is about getting those three things right.

2. What a gateway is responsible for

Different products offer different features, but the same dozen responsibilities appear again and again. Interviewers often ask you to list them and to say which ones belong in a gateway and which do not, so each is explained here.

2.1 Routing

The most basic job: look at the incoming request (the host name, the path, the HTTP method, headers, sometimes query parameters) and decide which backend service should receive it. A rule might say "any request whose path starts with /orders goes to the orders service" or "requests with header X-Beta: true go to the new version of the catalog service". The gateway then picks a healthy instance of that service, using service discovery (see Chapter 49) and a load balancing algorithm (see Chapter 9). Routing rules also make gradual rollouts possible: send 5 percent of traffic to a new version (a canary release) and watch the error rate before sending more.

2.2 Authentication and authorization offload

Authentication answers "who are you?" and authorization answers "are you allowed to do this?". Doing the first at the gateway means backend services never see unauthenticated traffic.

The most common scheme is a signed token. With OAuth 2.0, a client first obtains an access token from an authorization server (a separate login service). With OpenID Connect the token set also carries identity. The access token is frequently a JWT (JSON Web Token): three base64 parts, a header, a payload of claims (user id, tenant, scopes, expiry time), and a cryptographic signature. The gateway validates a JWT locally, without calling anyone: it checks the signature against the issuer's public key (fetched once from a published key set and cached), checks that the token has not expired, and checks that the issuer and audience are the expected ones. Because this is pure computation (typically well under a millisecond) there is no network call on the hot path.

The alternative is token introspection: for an opaque token (a random string), the gateway asks the authorization server "is this token valid and what does it represent?". This allows immediate revocation but adds a network call to every request, so gateways usually cache the answer for a short time. The tradeoff is discussed again in section 11.3.

After validating the token, the gateway typically strips the original credential and forwards the facts to the backend in trusted headers, for example X-User-Id: 8841 and X-Tenant: acme, or a short-lived internal token. Backend services read these headers instead of validating tokens themselves. This is only safe if services are reachable only through the gateway (a private network, or mutual TLS as in Chapter 50), and if the gateway removes any client-supplied copy of those headers. Otherwise an attacker simply sends X-User-Id: 1 directly.

Coarse authorization (does this token have the orders:read scope? is this an admin route?) fits well in the gateway. Fine-grained authorization ("may this user see this particular order?") needs the data, so it belongs in the service. Security design in general is covered in Chapter 55.

2.3 Rate limiting and quotas

Rate limiting caps how many requests a caller may make per unit of time, protecting backends from abuse, bugs (a client stuck in a retry loop) and noisy neighbours. A quota is a longer-horizon allowance, such as 1 million calls per month on a paid plan. The gateway is the natural enforcement point because it sees all traffic and already knows the caller's identity (an API key, a user id, a tenant). The algorithms (token bucket, sliding window) and the distributed counters behind them are the subject of Chapter 16. Gateway-specific points: limits can be applied per key, per user, per IP, per route or per tenant; rejected requests receive HTTP 429 (Too Many Requests) with a Retry-After header; and a request rejected at the gateway costs the backend nothing.

2.4 Request and response transformation

The gateway can rewrite requests and responses on the way through: add or remove headers, rewrite the URL path (the public /v2/orders becomes the internal /orders), convert field names, remove internal fields from a response, or mask sensitive values. This lets the public contract stay stable while internals change. Use it sparingly. Light, declarative rewriting is healthy; deep restructuring of payloads is the first step toward the anti-patterns in section 9.

2.5 Protocol translation

Browsers and partners speak HTTP with JSON (often called REST), while internal services frequently use gRPC, a binary protocol built on HTTP/2 with strongly typed messages defined in .proto files. The gateway can accept a REST call such as GET /orders/42, convert it to a gRPC call GetOrder(id=42) on the orders service, and convert the binary reply back to JSON. Envoy's gRPC-JSON transcoder and AWS API Gateway integrations are examples. Other translations include WebSocket to a message broker, SOAP to REST for legacy systems, and HTTP/2 or HTTP/3 on the client side while using HTTP/1.1 to old backends. The benefit is that each side uses the protocol that suits it. Service-to-service protocol choices are covered in Chapter 47.

2.6 Aggregation and composition

One screen in an app often needs data from several services. Rather than make the phone call three services over a cellular network, the gateway can receive one request, call the three services itself over the fast internal network in parallel, merge the results, and return one response. The latency of the combined call is roughly the slowest of the parallel calls instead of the sum of three internet round trips. This is the idea behind the BFF pattern in section 6. It is also the feature most likely to be abused, because merging data involves logic.

2.7 Caching

The gateway can cache responses for safe, popular requests (for example a product listing that changes rarely), honouring Cache-Control headers and keying on the URL plus selected headers. This is a small, local, short-lived cache; large-scale caching of static content belongs to a CDN (Chapter 12) and shared application data to a cache tier (Chapter 13). Gateway caching is useful for per-API-product acceleration and for absorbing bursts, and it can also serve stale data during a backend outage, as discussed in section 11.

2.8 TLS termination

TLS encrypts traffic between client and server. Termination means the gateway performs the TLS handshake and decryption, then speaks to backends either in plain HTTP on a trusted private network or over a second TLS (or mutual TLS) connection. Doing this at the gateway centralizes certificate management: one place to install, renew and rotate certificates, and one place to enforce modern protocol versions and cipher suites. For sensitive systems the gateway re-encrypts to the backend ("TLS re-encryption") so traffic is never plain even inside the data center.

2.9 API versioning

APIs change, and old clients cannot be forced to upgrade. The gateway can expose several versions side by side and route by version: by path (/v1/orders and /v2/orders), by a header (Accept: application/vnd.shop.v2+json), or by a query parameter. It can also route old versions to an adapter that translates to the current backend, keeping backend code free of legacy branches. It also supports deprecation: it can add Deprecation and Sunset headers, count calls per version so you know when it is safe to retire one, and finally return 410 Gone.

2.10 Observability

Because all traffic passes through it, the gateway is the best vantage point for the first layer of monitoring: request counts, error rates by route, latency histograms, response sizes, and per-consumer usage. It also starts a trace: it generates a request id (and a trace context header such as W3C traceparent) if the client did not send one and passes it downstream so that logs and spans from every service can be tied together. See Chapter 52 and Chapter 54. Gateway metrics measure what the client experiences, which is why they make good SLO indicators.

2.11 WAF integration

A Web Application Firewall inspects HTTP requests for known attack patterns: SQL injection, cross-site scripting, path traversal, bad bots, oversized bodies, and requests from blocklisted addresses. Some gateways embed WAF rules (Kong, Nginx with ModSecurity, Envoy filters); in cloud deployments a managed WAF (AWS WAF, Cloudflare, Cloud Armor) is placed in front of the gateway. Either way the gateway should also enforce basic hygiene itself: maximum body size, maximum header size, allowed methods, and request timeouts to defeat slow-sending clients (the "slowloris" attack).

2.12 Circuit breaking, timeouts and retries

The gateway talks to many backends and must not let one sick backend drag everything down. A timeout bounds how long it waits. A circuit breaker counts recent failures to a backend and, past a threshold, opens: for a cool-down period it fails requests immediately (or serves a fallback) instead of waiting on a service that is probably down, then lets a few trial requests through (half-open) to see whether it recovered. A bounded retry policy re-sends idempotent requests that failed for transient reasons. Bulkheads limit how many concurrent connections any one backend may consume so that a slow service cannot use up all of the gateway's capacity. These patterns are explained in depth in Chapter 40 and Chapter 51; the gateway-specific dangers (retry storms, cascading timeouts) are in section 11.

3. The request lifecycle: the plugin or filter chain

Internally, nearly every gateway is built the same way: a small core that accepts connections and moves bytes, plus an ordered list of plugins (Kong, Nginx modules) or filters (Envoy HTTP filters, Spring Cloud Gateway filters). Each plugin does one job. A request passes through the chain in order on the way in, the request is sent to the backend, and the response passes back through the chain, often in reverse order, on the way out. Because each plugin is independent, you enable exactly the features each route needs, and you can write your own.

The order matters, and a good ordering is a design decision in itself.

  1. TLS termination first, because nothing else can read an encrypted request.
  2. Cheap rejections early. Size limits, blocked IPs and malformed-request checks cost almost nothing and discard junk before expensive steps run.
  3. Authentication before rate limiting by user. To limit per user you must know who the user is. But also keep a coarse per-IP limit before authentication, otherwise an attacker can burn your CPU on signature checks with garbage tokens.
  4. Routing after policy, so rejected requests do no routing work. Some gateways must route first because policies are attached per route; in that case route matching is a cheap lookup and the chain is selected from the matched route.
  5. Upstream call with timeout, retry and circuit breaker logic wrapped around it.
  6. Response phase: transform the response, update the cache, record metrics and logs, and send the response to the client.

Here is a configuration sketch in the declarative style that Kong uses, to show how little code each concern needs. The exact syntax differs by product; the shape is what matters.

services:
  - name: orders
    url: http://orders.internal:8080
    routes:
      - name: orders-route
        paths: [/v2/orders]
        strip_path: true
    plugins:
      - name: jwt                 # validate signature, exp, iss locally
      - name: rate-limiting       # per consumer
        config: { minute: 600, policy: redis }
      - name: request-transformer
        config: { remove: { headers: [X-User-Id] } }   # never trust client copy
      - name: correlation-id
      - name: prometheus
Watch out Every plugin adds latency and a way to fail, and plugins run on every request. A plugin that makes a network call (introspection, an external authorization service, a remote rate-limit store) is on the critical path of every request. Decide for each such call what happens when it is slow or down: fail open (let the request through) or fail closed (reject it). The answer differs by plugin; see section 11.

4. Gateway vs reverse proxy vs load balancer vs service mesh

These four terms overlap, and interviewers like to check that you can separate them. The cleanest way is to look at what each one is aware of and where it sits.

  • A reverse proxy accepts requests on behalf of servers and forwards them. It is the general mechanism: the client talks to the proxy, never directly to the server. It may add TLS, compression and caching. See Chapter 10.
  • A load balancer spreads traffic across several identical instances of one service and removes unhealthy ones. It is aware of instances and health, and generally not of users or API semantics. Layer 4 balancers see only connections; layer 7 balancers see HTTP. See Chapter 9.
  • An API gateway is a reverse proxy with API-management awareness: it knows about consumers, API keys, scopes, plans and quotas, versions, and routes that map to different services. It sits at the boundary between external clients and the whole system ("north-south" traffic: into and out of the data center).
  • A service mesh manages "east-west" traffic: calls between internal services. A small proxy (a sidecar) runs beside each service instance and handles mutual TLS, retries, timeouts, circuit breaking and telemetry for that service, controlled by a central control plane. See Chapter 50.

In practice the lines blur, because the same software plays several roles: Nginx and Envoy are both reverse proxies, load balancers, and (with plugins or control planes) gateways or mesh data planes. Do not memorize products; reason from role. A good answer in an interview is: "A gateway is a reverse proxy plus API management at the north-south boundary. A load balancer sits in front of the gateway instances, and a mesh handles east-west traffic. They compose; they do not replace one another."

Interview tip If asked "do we still need a gateway if we have a service mesh?", the answer is usually yes: the mesh identifies services, while the gateway identifies external consumers and enforces plans, quotas, key management and public versioning. Many meshes now ship an ingress gateway (Istio's, for example) that blurs the distinction, but the responsibility split remains.

5. Deployment topologies

"Where does the gateway run and how many of them are there?" has three common answers, and real systems often mix them.

5.1 Edge gateway

One logical gateway at the boundary of the system, in front of everything. It is the best start: one place for TLS, WAF, authentication and rate limits, one public hostname. Its weakness grows with the organization: every team that adds a route changes shared configuration, and a mistake affects everyone (the "shared-release bottleneck" of section 9).

5.2 Internal gateway

A gateway placed inside the network, in front of a group of services owned by one domain or business unit, reached through the edge gateway or from other internal systems. It lets a domain team publish and version an internal API, set its own quotas for internal callers, and manage its own routes, without touching the edge. Internal gateways also help when an organization has acquired companies or has legacy systems: the internal gateway presents a clean contract in front of messy backends.

5.3 Per-team and per-client gateways

Each team (or each kind of client) runs its own gateway or gateway configuration, deployed independently. This removes the central bottleneck and allows tailored behaviour per client, at the cost of duplicated infrastructure and the risk of policies drifting apart. A common compromise is a shared thin edge (TLS, WAF, global auth, coarse rate limits) in front of team-owned gateways that handle routing and composition for their domain. Many platforms also run a separate gateway for third-party partners with stricter quotas and key management (the "partner" gateway in the figure), and a separate one for internal admin tools.

Key idea Topology is mostly about ownership, not technology. Start with one edge gateway. Split it when release coordination, not traffic volume, becomes the pain: when teams wait on each other to change routes.

6. Backend-for-Frontend (BFF) in depth

6.1 The problem a general gateway cannot solve

A single shared gateway offers one API to all clients. But clients differ greatly:

  • A mobile app on a slow cellular network wants few round trips, small payloads, and only the fields it displays. A product detail screen might need name, price, one thumbnail, and a stock flag.
  • A web app on broadband can afford richer payloads, and its pages need other combinations of data, such as reviews, related products and large images.
  • A smart TV or watch app has tiny screens and limited memory.
  • Partner systems want a stable, versioned, documented, contract-first API with strict quotas, not something that changes with the UI.

If one generic API tries to serve all of them, it becomes a compromise: the mobile app downloads fields it never shows (over-fetching), or it must make several calls to assemble a screen (under-fetching). Adding client-specific parameters to a shared API turns it into a tangle of special cases, and every client team has to negotiate changes with a central API team.

6.2 The pattern

The Backend-for-Frontend pattern (named by Sam Newman and used widely at companies such as SoundCloud and Netflix) says: build a separate backend for each kind of frontend. The BFF is a small server, owned by the same team that builds the client, whose only job is to serve that client's needs. It sits between that client and the shared domain services, calling them over the internal network, aggregating, trimming and reshaping data into exactly what the client's screens need.

6.3 A concrete example

The mobile product page needs: product name and price (catalog service), a stock flag (inventory service), the average rating (reviews service), and whether the user has it in their wishlist (users service). Without a BFF the app makes four calls, each paying a cellular round trip of perhaps 100 ms plus connection setup, and parses four large JSON documents. With a mobile BFF the app makes one call, GET /mobile/product/42. The BFF calls the four services in parallel over a 1 ms network, picks only the needed fields, and returns around 2 KB. If the reviews service is down, the BFF can still return the rest with rating: null (graceful degradation), a decision that only the client-aware BFF is placed to make.

6.4 What a BFF should and should not do

A BFF owns client-specific presentation logic: which services to call for a screen, how to combine and trim their data, how to paginate for that client, how to degrade, what to cache for that client, and client-specific authentication handling (for example a web BFF can hold the session cookie and the OAuth tokens server-side so tokens never reach the browser, the "token handler" pattern). It must not own domain rules such as how a discount is computed or whether an order is valid. That logic lives in the domain services so every client gets the same behaviour. Think of the BFF as a translator and curator, never a decision maker.

6.5 BFF versus gateway: how they fit together

They are complementary, not competing. A common layout is the shared edge gateway (TLS, WAF, global rate limits, authentication) in front of several BFFs; each BFF is a thin application written in the client team's language (often Node.js or the same language as the client team's other code). Alternatively the BFFs are themselves deployed as separate gateway configurations (topology C above). The edge gateway enforces company-wide policy; the BFF composes data for one client.

6.6 Costs and when not to use it

  • Duplication. Similar aggregation code ends up in several BFFs. Mitigate by pushing genuinely shared logic down into domain services or shared libraries, and accept some duplication as the price of independence.
  • More services to run. Each BFF needs deployment, monitoring and on-call ownership. If you only have one client type, a BFF adds little.
  • Risk of drift. Web and mobile behaviours can diverge unintentionally; contract tests and shared design guidelines help.
  • Use it when clients have clearly different needs, client teams are blocked by a central API team, or payloads and round trips matter (mobile). Skip it for a small system with one client or when a GraphQL layer (next section) solves the same problem with less code.

7. GraphQL gateway and federation

GraphQL is a query language for APIs in which the client states exactly which fields it wants, and the server returns just those. A mobile client can ask for product { name price rating } and a web client for a larger selection, using the same endpoint. This addresses over-fetching and under-fetching directly, which is why a GraphQL layer is sometimes used instead of per-client BFFs: one flexible API, with clients choosing the shape. A GraphQL server describes its data in a typed schema and uses resolvers, small functions that fetch each field from wherever the data lives.

A GraphQL gateway is a GraphQL server placed in front of REST or gRPC services; its resolvers call those services. This gives clients a unified graph without rewriting backends. It becomes hard to run centrally when many teams must edit one giant schema. Federation (Apollo Federation is the best-known approach; others include schema stitching and GraphQL Mesh) solves that by splitting the schema across teams.

In federation, each team owns a subgraph: a small GraphQL service with its own part of the schema. A subgraph can extend a type owned by another (the reviews team adds a rating field to Product, which the products team owns), using shared keys such as the product id. A router (the gateway) composes the subgraph schemas into one supergraph, and for each query it builds a query plan: which subgraphs to call, in what order (some calls depend on the output of earlier ones) and which can run in parallel. Teams deploy subgraphs independently, which removes the central schema bottleneck.

7.1 Tradeoffs of GraphQL gateways

  • The N+1 problem. A query for a list of 50 products with a rating each can cause one resolver call per product (51 calls). The standard fix is batching (for example a data loader that collects the 50 ids and issues one batched call).
  • Unpredictable cost. Clients can write expensive, deeply nested queries. Protect the service with query depth limits, complexity scoring, and persisted queries (an allowlist of approved queries identified by hash). Rate limiting by request count is not enough because one request can cost a thousand times another.
  • HTTP caching is harder. Everything is a POST to one URL, so CDNs and the gateway cannot cache by URL as easily; persisted queries sent with GET restore some of it.
  • Error handling. A response can be partly successful: data for some fields and errors for others, often still with HTTP 200. Monitoring must look inside the body.
  • The router is a hot spot. It sees every query and does planning; it needs the same scaling and HA care as any gateway.
Interview tip When asked "BFF or GraphQL?", say: both address client-specific data needs. BFFs give strong team autonomy and tailored behaviour at the cost of more services; GraphQL gives one flexible API at the cost of query-cost control and caching complexity. They also combine: a BFF can be a GraphQL server, and many teams run a federated graph behind an edge gateway that does auth and rate limiting.

8.2 Build versus buy

Buy or adopt open source is the right default. A gateway is infrastructure that must be extremely reliable and secure, and getting TLS, HTTP edge cases, connection handling, slow-client defence and authentication right is a large engineering effort that mature products have already done. Writing your own proxy means taking on HTTP parsing bugs, request smuggling vulnerabilities and years of hardening.

Consider building a thin layer only when your needs are narrow and specific: for example a BFF is normally custom code (it is application logic by nature), or you need a custom policy (an unusual authorization scheme) that you can add as a plugin or filter to an existing proxy instead of writing a whole proxy.

The decision between managed and self-hosted:

  • Managed (AWS API Gateway, Apigee X, Azure APIM): no servers to run, built-in scaling and HA, integrates with the cloud's identity and WAF. Costs: per-request pricing that becomes large at high volume, limits you cannot change, vendor lock-in, and less control over latency and tail behaviour.
  • Self-hosted (Kong, Envoy, Nginx): predictable cost at high volume, full control, portable across clouds and on premises. Costs: you operate, patch, scale and monitor it, and you must design its HA yourself.

A rough rule: at low and spiky volume, managed is cheaper in people time; at sustained high volume (tens of thousands of requests per second), the per-request fee of a managed gateway usually exceeds the cost of running your own fleet. Do the arithmetic for your price list rather than trusting a rule: requests per month times price per million requests, compared to the monthly cost of the gateway instances plus the share of an engineer's time to run them.

9. Gateway anti-patterns

9.1 Business logic in the gateway

The temptation is strong: the gateway already sees every request, so "just add a little logic" there: apply a discount, validate an order's rules, call three services and decide something. Over time the gateway accumulates domain rules written by many teams in a plugin language, tested poorly, and deployed with the shared gateway. Now a pricing change means redeploying the front door, and a bug in a discount rule can take down all traffic. The rule of thumb: the gateway may know about requests, callers and routes; it must not know about orders, prices or customers. Cross-cutting means "applies to all APIs regardless of domain". If the logic is domain-specific, it belongs in a service (or in a BFF if it is purely presentation).

9.2 The god gateway

A single gateway that does everything for everyone: routes for hundreds of services, orchestration of workflows, data aggregation for each client, custom scripts per team. It becomes the most critical and most fragile component, understood by nobody completely. Symptoms: huge configuration files, a long list of plugins nobody dares remove, request handling that takes 50 ms because of chained policies, and an operations team that is the bottleneck for every change. This is the old enterprise service bus mistake repeated with HTTP. The cure is to keep the gateway thin and to split by ownership (topologies B and C, BFFs).

9.3 The shared-release bottleneck

If all teams must edit and deploy one gateway configuration, every route change queues behind the others. A bad change by one team (a malformed route, an overly broad regular expression) can break every API. Releases get slow, risky and political. Mitigations: configuration as code with per-team directories and automated validation; per-team gateways or per-team configuration scopes (Kubernetes Gateway API supports route objects owned by different teams attached to a shared gateway); progressive rollout of config changes (section 11.4); and clear ownership rules.

9.4 Other mistakes

  • Gateway as the only security layer. If services trust anything that reaches them, one gateway misconfiguration or one internal compromised host exposes everything. Use defense in depth: network isolation, mutual TLS, and service-level authorization checks (Chapter 55).
  • Chatty aggregation. The gateway calls 20 services in sequence for one request, so latency adds up and any failure fails the whole response. Aggregate in parallel, bound the fan-out, and tolerate partial failure.
  • Unbounded retries. Retrying at the gateway and at every service multiplies load during an outage (section 11.2).
  • No per-route timeouts. A single global timeout is either too long for fast routes or too short for slow ones.
  • Gateway for east-west traffic. Sending every service-to-service call through the central gateway doubles hops and creates a bottleneck. Use direct calls with a mesh or client libraries internally (Chapter 47).
  • Treating the gateway as a database or session store. Keep it stateless (section 10) so any instance can serve any request.

10. Scaling and high availability of the gateway

10.1 Stateless instances behind a load balancer

A gateway should be a stateless tier (see the Module 2 theme, scaling the stateless tier): any instance can handle any request, so you scale by adding more identical instances behind a load balancer. The state that does exist is kept out of the instance or is safely reconstructable: configuration (pulled from a control plane or config store), cached public keys (refetched on demand), and rate limit counters (in a shared store such as Redis, or approximated locally). See Chapter 8 for the principles of scaling stateless services.

10.2 Scaling signals and practices

  • What limits a gateway? Usually CPU (TLS handshakes, JWT signature verification, JSON or protocol transformation, compression) and the number of open connections (memory per connection, file descriptors). Event-driven proxies like Nginx and Envoy handle tens of thousands of concurrent connections per instance, but per-request CPU still bounds throughput.
  • Autoscale on CPU and on requests per second or concurrent connections per instance (Chapter 43). Scale out ahead of known peaks, because new instances need time to start and to warm connection pools.
  • Keep-alive connections to backends. Reusing connections avoids repeating TCP and TLS handshakes on the internal hop. Size pools per backend.
  • Connection draining on deploys and scale-in: stop sending new requests, finish in-flight ones, then terminate. Otherwise users see errors on every rollout.
  • Plan for N+1 or zone loss. Run with enough headroom that losing an instance or an entire zone does not push the rest above safe utilization. Section 12 does this arithmetic.
  • Multi-region. Run a gateway fleet in each region and steer users to the nearest healthy one with DNS or anycast (as in Chapter 12); see Chapter 26 and Chapter 41.
  • Rate limit state. A shared Redis gives exact counts but adds a network call (typically around a millisecond) and a dependency; local counters per instance are fast but approximate (each instance sees only part of the traffic). A common hybrid is local token buckets that periodically sync with Redis, which stays within a few percent accuracy and keeps the hot path free of network calls. See Chapter 16.

10.3 The latency overhead budget

The gateway adds a hop to every request, and you should be able to state how much. Think of a latency budget: the whole request has an end-to-end target (say 200 ms at p99), and each component gets a slice. A healthy gateway adds a small amount to the median, usually a few milliseconds, and somewhat more at the tail.

The practical lessons: keep per-request network calls out of the hot path where possible, favour local validation and cached decisions, watch the tail (p99 and p99.9), where garbage collection pauses, connection setup, and cold caches show up, and track gateway added latency as its own metric: time at the gateway minus time spent waiting on the backend. If that figure is more than a few milliseconds at p99, a plugin is doing too much.

11. Failure modes and mitigations

11.1 The gateway as a single point of failure

Because everything flows through it, an outage of the gateway is an outage of the product, no matter how healthy the services are. The causes are rarely "the machine died" (a fleet handles that) and more often a bad deploy, an expired certificate, resource exhaustion, or a shared dependency failing. Mitigations:

  • Redundancy at every level: multiple instances, multiple zones, and for critical systems multiple regions, with health checks that remove sick instances automatically.
  • Keep the gateway simple and stateless, so instances are replaceable and there is little to go wrong.
  • Remove avoidable dependencies from the hot path. Every external call (auth server, Redis, config service) is a way to fail. Cache, and decide fail-open or fail-closed explicitly.
  • Certificate automation and expiry monitoring. Expired certificates are a classic, embarrassing cause of total outages.
  • Canary and blue-green deploys of the gateway itself (Chapter 43), and an instant rollback path.
  • Static fallback: for critical read-only content, a CDN in front (Chapter 12) can keep serving cached responses while the gateway is down.
  • Isolation: separate gateways (or separate instance groups) for critical APIs (checkout) and less critical ones, so a flood on one cannot starve the other.

11.2 Cascading timeouts and retry storms

Suppose the gateway calls the orders service, which calls the inventory service, which has become slow (it responds in 20 seconds instead of 20 ms). If timeouts are generous or missing, here is what happens: the inventory calls pile up; orders threads wait on inventory and are all consumed; orders stops answering the gateway; the gateway's connections to orders pile up; the gateway runs out of connections or threads, and now even requests for the healthy catalog service cannot be served. One slow dependency has taken down the whole front door. This is a cascading failure.

Mitigations, in order of importance:

  1. Short, explicit timeouts on every call, per route, with the outer layer's timeout longer than the sum of what it waits on only when the inner ones are bounded. Propagate a deadline (remaining time) downstream so that services stop work that nobody is waiting for.
  2. Circuit breakers so a failing backend is cut off quickly and given time to recover (Chapter 51).
  3. Bulkheads: cap the concurrent requests and connections per backend. If orders is slow it can occupy at most, say, 20 percent of the gateway's capacity, leaving the rest for other services.
  4. Bounded retries with backoff and a retry budget. If a layer retries three times and a downstream layer also retries three times, one failing call becomes nine. When a service is overloaded, this multiplication makes it worse (a retry storm). Retry only idempotent requests, cap retries at a small fraction of traffic (for example 10 percent extra), add jitter, and retry in one layer, not all of them. See Chapter 32.
  5. Load shedding: when the gateway is saturated, reject excess low-priority requests early with 503 rather than queueing everything and timing out all of it.

Little's law shows why timeouts matter in numbers: concurrent in-flight requests equals arrival rate times time in the system. At 10,000 requests per second, a backend that responds in 50 ms means 500 requests in flight; if it hangs for a 30 s timeout, in-flight requests would grow toward 300,000 and exhaust memory and connections long before the timeout fires.

11.3 Auth service outage

If the gateway calls the authorization server on every request (opaque tokens with introspection) and that server goes down, no request can be authenticated: a total outage caused by a dependency. Options:

  • Validate JWTs locally, with cached signing keys, so the auth server is only needed to issue tokens, not to check them. Existing sessions keep working during the outage. The tradeoff: revoking a token before expiry is hard, so keep access tokens short-lived (for example 5 to 15 minutes) and use refresh tokens, or keep a small revocation list that gateways sync.
  • Cache introspection results for a short time (seconds to a minute), keyed by token, so a brief outage is invisible and load on the auth server falls dramatically.
  • Cache the signing keys for longer than their normal rotation, and keep serving with the last known keys if the key endpoint is unreachable.
  • Fail closed for security. Do not fall back to "allow" when authentication cannot be checked, except perhaps for explicitly public routes. Failing open on authentication is a security hole; failing closed is an outage; JWT with local validation and caching narrows the window where you must choose.
  • Contrast with rate limiting: if the rate-limit store (Redis) is down, failing open (allow, perhaps with local limits only) is usually the right choice, because dropping all traffic to protect against abuse is worse than briefly allowing it.

11.4 Configuration push errors

Gateways are controlled by configuration (routes, plugins, certificates), and a bad configuration is the single most common cause of large gateway outages: a route that matches everything, a malformed regular expression that consumes all CPU, an authentication plugin accidentally detached from a route (silently exposing it), or a certificate swapped for the wrong one. Because configuration is pushed to all instances quickly, a mistake becomes a global outage in seconds. Mitigations:

  • Configuration as code in version control, reviewed like any change, with automated validation (schema checks, linting, policy tests such as "every route must have an authentication plugin").
  • Test in staging with replayed or synthetic traffic, including contract tests for key routes.
  • Progressive rollout: push to one instance or a small slice (a canary), watch error rates and latency, then proceed in waves, with automatic rollback if the error rate rises.
  • Keep the last known good config. If an instance receives an invalid config it should reject it and keep running the old one rather than crash. Data planes like Envoy do this for dynamic updates.
  • Decouple the control plane from the data plane. If the control plane (the system distributing config) goes down, the gateway instances should keep serving with their current configuration. Instances should also be able to start from a cached copy of config when the control plane is unreachable.
  • Limit blast radius with per-team config scopes and separate gateways for critical APIs.

11.5 Other failure modes, briefly

  • Thundering herd after recovery: when the gateway or a backend returns, all clients reconnect and retry at once. Use jittered backoff on clients, slow-start for new instances and warm-up of caches.
  • Hot tenant or abusive client: one consumer saturates shared capacity. Per-consumer limits and concurrency caps, and isolating big tenants into their own gateway pool, contain it (Chapter 42).
  • Large bodies and slow clients: uploads and slow readers tie up connections. Enforce size limits, body timeouts, and stream where possible instead of buffering.
  • Clock skew: JWT expiry and not-before checks depend on clocks. Allow a small leeway (tens of seconds) and keep time synchronized.
  • DDoS: volumetric attacks should be absorbed upstream by a CDN or DDoS protection service before they reach the gateway; the gateway handles the application-layer part with rate limits and WAF rules.

12. Worked example: sizing a gateway for a shopping platform

Let us size a gateway fleet and check its latency and failure behaviour with concrete numbers. The inputs below are assumptions chosen for the exercise; in a real design you would state them to the interviewer and invite correction.

12.1 Requirements and assumptions

  • 20 million daily active users; each makes about 60 API calls per day (a mix of mobile and web), so 20,000,000 × 60 = 1.2 billion requests per day.
  • Average rate: 1.2 billion ÷ 86,400 s ≈ 13,900 requests per second. Traffic is bursty and evening-peaked; assume a peak of about 3 times the average, so roughly 40,000 requests per second.
  • Gateway work per request: TLS (mostly on kept-alive connections), JWT validation, local rate limit with Redis sync, routing and logging. Assume load testing shows one 4-vCPU instance sustains about 10,000 requests per second at 100 percent CPU. We never plan to run hot, so we target 50 percent, which is 5,000 requests per second per instance.
  • Availability target: survive the loss of one availability zone with no user-visible degradation.

12.2 Instance count

Minimum for peak at target utilization: 40,000 ÷ 5,000 = 8 instances. But we must survive a zone loss. With three zones, if one is lost, the two remaining zones must carry the full 40,000 requests per second, which needs 8 instances in those two zones, 4 per zone. Provision 4 per zone in each of three zones: 12 instances. In normal operation each instance sees 40,000 ÷ 12 ≈ 3,300 requests per second (33 percent CPU). After losing a zone, the 8 survivors each see 5,000 (50 percent), still within target. The cost of this resilience is 50 percent extra capacity (12 instead of 8), which is the usual price of surviving a zone failure with three zones. (With two zones you would need to run 16 for the same guarantee, so three zones is more efficient.)

Autoscaling then trims the fleet at night (down to perhaps 6 to 9 instances) and adds during the day, while never dropping below a floor that covers a zone loss at the current traffic.

12.3 Latency budget

The product target is a p99 of 300 ms for the product-page API from the client's perspective, of which most should be backend work. For the gateway, budget at most 10 ms added at p99.

12.4 The mobile BFF aggregation

The mobile product page needs catalog (15 ms), inventory (10 ms), reviews (30 ms) and wishlist (8 ms). Called sequentially from the phone, that is 63 ms of service time plus four cellular round trips at about 100 ms each, roughly 460 ms. A BFF at the edge makes one phone round trip (about 100 ms) and calls the four services in parallel in about 30 ms (the slowest, reviews), plus about 3 ms to merge and trim: about 135 ms in total, a reduction of around 70 percent. It also lowers the payload from perhaps 40 KB to 2 KB, which matters on weak connections. If the reviews call has a 100 ms deadline and fails, the BFF returns the other three fields with rating: null after 100 ms instead of failing the page.

12.5 What happens when something breaks

Slow inventory service. Inventory latency goes from 10 ms to hanging. Without protection, at the product-page traffic share of 8,000 requests per second, in-flight requests to inventory would grow by 8,000 per second until memory runs out (Little's law: arrival rate times wait time; with a 3 s timeout the steady state is 8,000 × 3 = 24,000 stuck requests, or 2,000 per instance across 12 instances, which is within reach of exhausting a connection pool). With a 300 ms inventory timeout, a bulkhead of 500 concurrent calls per instance, and a circuit breaker that opens after 50 percent failures over 10 seconds, the stuck population is capped at 500 per instance, the breaker opens within seconds, and the BFF returns inStock: unknown while the rest of the site works normally.

Auth server outage. Access tokens last 10 minutes and are validated locally with cached keys, so existing users continue unaffected; only logins and token refreshes fail. Over the 10-minute window the share of users who cannot refresh grows, which is why the auth service has its own HA design and why the key cache is allowed to serve stale keys for several hours.

Bad config push. A route change that detaches the JWT plugin is caught by a CI policy test ("every route outside /public must have the jwt plugin"). If something subtler slips through, the canary instance (1 of 12, about 8 percent of traffic) shows a spike in 5xx within a minute and the automatic rollback stops the rollout, so the blast radius is about 8 percent of traffic for under two minutes instead of 100 percent of traffic until a human notices.

12.6 Cost sanity check: managed versus self-hosted

Average 13,900 requests per second is about 36 billion requests per month (13,900 × 2,592,000 s). If a managed gateway charged on the order of a few dollars per million requests, that is a bill of roughly ten thousand dollars or more per month for requests alone, before data transfer; check current prices. Twelve mid-sized instances cost on the order of a few thousand dollars per month. Self-hosting is cheaper at this scale in hardware, but you are paying with operations effort; at a tenth of this volume the comparison reverses. That is the build-versus-buy arithmetic from section 8.

13. Interview questions and answers

Why do we need an API gateway when we already have load balancers?

A load balancer spreads connections across identical instances of a single service and removes unhealthy ones, but it knows little about users or API semantics. A gateway works at the level of the API: it authenticates callers, applies per-consumer rate limits and quotas, routes different paths to different services, rewrites requests, versions the API, and collects per-API metrics. They are used together: a load balancer sits in front of the gateway fleet (to spread traffic and fail over between gateway instances), and the gateway uses its own balancing to pick instances of each backend service.

What belongs in a gateway, and what does not?

Cross-cutting, domain-agnostic concerns belong in the gateway: TLS termination, authentication and coarse authorization, rate limiting, routing, request id and tracing, basic validation such as size limits, and resilience policies like timeouts and circuit breaking. Domain logic does not: pricing, order validation, workflows, or fine-grained "can this user see this record" checks. A useful test is whether the rule applies to every API regardless of what it does. If it needs knowledge of a business entity, put it in a service, or in a BFF if it is purely about presenting data to one client. Violating this turns the gateway into a god component that every team must change and that nobody can safely deploy.

How does the gateway validate a JWT, and what happens if the auth server goes down?

The gateway checks the signature using the issuer's public key (fetched from a published key set and cached), then verifies the expiry, issuer, audience and required scopes. All of this is local computation that takes well under a millisecond, with no call to the auth server. Because of that, an auth server outage does not affect requests carrying valid unexpired tokens; only issuing and refreshing tokens fails. The tradeoff is revocation: a stolen token stays valid until it expires, so access tokens are short-lived (minutes) and refresh tokens carry the long-lived session, with an optional revocation list for emergencies. If you must use opaque tokens and introspection, cache the introspection results briefly so an outage is survivable, and fail closed rather than allowing unauthenticated traffic.

Explain the Backend-for-Frontend pattern and when you would choose it over a single shared gateway.

A BFF is a dedicated backend for one type of client (mobile, web, partner), owned by the team that builds that client. It calls the shared domain services, aggregates and trims their data to match exactly what that client's screens need, and handles client-specific behaviour such as pagination style, caching, and graceful degradation. You choose it when clients have clearly different needs, when a central API team is a bottleneck for client teams, or when round trips and payload size matter, as on mobile networks. It avoids a one-size-fits-all API full of special cases. The costs are more services to run, some duplicated aggregation code, and the risk of behaviours diverging, so it is not worth it for a system with a single client type. The BFF must hold presentation logic only; domain rules stay in the domain services.

How do you compare a GraphQL gateway with per-client BFFs?

Both solve over-fetching and under-fetching. GraphQL gives one flexible endpoint where each client requests exactly the fields it wants, and federation lets each team own part of the schema, with a router that plans and merges sub-queries. The drawbacks are unpredictable query cost (needing depth limits, complexity scoring or persisted queries), the N+1 resolver problem (solved with batching), harder HTTP caching, and partial-error responses that hide failures behind HTTP 200. BFFs give predictable, tailored endpoints and clear ownership but multiply the number of services. A pragmatic answer is that they combine well: a federated graph or a GraphQL BFF behind an edge gateway that handles authentication, rate limiting and WAF.

What is the difference between an API gateway, a reverse proxy, and a service mesh?

A reverse proxy is the basic mechanism of accepting client requests and forwarding them to servers, often adding TLS and caching. An API gateway is a reverse proxy with API-management features: consumer identity, keys and plans, quotas, versioning and per-route policies, sitting at the boundary for north-south traffic from external clients. A service mesh governs east-west traffic between internal services using sidecar proxies that provide mutual TLS, retries, timeouts and telemetry under a central control plane. They are layers that compose, not substitutes: the gateway knows external consumers, the mesh knows internal service identities. The same software, such as Envoy, can serve in more than one role, so reason from the role rather than the product.

The gateway is a single point of failure. How do you design around that?

First, make it a stateless fleet of identical instances across multiple availability zones (and regions for critical systems) behind a load balancer with health checks, sized so losing a zone leaves enough capacity. Second, keep external dependencies off the hot path: validate JWTs locally, cache decisions, and choose explicit fail-open or fail-closed behaviour for each dependency, such as failing open for a rate-limit store but closed for authentication. Third, treat configuration and certificates as the real risk: validate config in CI, roll it out progressively with automatic rollback, keep the last known good config, and automate certificate renewal with expiry alerts. Fourth, isolate critical APIs onto their own gateway pool so a flood or a fault elsewhere cannot starve them, and put a CDN in front for cacheable content.

How do cascading timeouts happen at a gateway and how do you prevent them?

If a slow dependency makes calls hang, every layer above holds threads and connections while it waits. With long or missing timeouts the resources fill up from the bottom to the top until the gateway itself cannot serve even healthy routes. To prevent this, set short explicit timeouts per route that shrink as you go deeper, propagate a deadline so downstream services drop work the client has abandoned, add circuit breakers to cut off failing backends quickly, use bulkheads to cap how much of the gateway one backend can consume, and bound retries with backoff and a retry budget so retries do not multiply load across layers. Shedding excess load early with a fast 503 is better than queueing until everything times out. Little's law helps quantify it: in-flight requests equal arrival rate times wait time, so a 30 second hang at 10,000 requests per second means hundreds of thousands of stuck requests.

How much latency does a gateway add, and how do you keep it small?

A well-run gateway adds roughly a millisecond or so at the median and single-digit milliseconds at p99: one extra network hop, JWT verification, a local rate-limit check, routing and logging. The way to keep it small is to avoid network calls on the hot path (use local JWT validation, local or asynchronously synced rate limit counters, cached introspection), reuse keep-alive connections to backends, keep plugin chains short, avoid heavy body transformation, and watch the tail where garbage collection, connection setup and cold caches appear. Measure gateway-added latency as its own metric (time in the gateway minus time waiting on the backend), and alert if it grows. If aggregation is done there, make calls in parallel so latency is the slowest call, not the sum.

How would you roll out a risky configuration change to a gateway used by every team?

Treat configuration like code. Keep it in version control with review, run automated validation and policy tests in CI (for example every non-public route must have authentication, no regular expressions that can cause catastrophic backtracking), and test in staging against synthetic or replayed traffic. Deploy progressively: apply to a canary instance or a small percentage of traffic, compare error rates and latency with the baseline, then widen in waves, with automatic rollback on regression. The data plane should reject invalid config and keep the last good one, and keep running if the control plane is unreachable. Splitting configuration ownership per team and isolating critical APIs reduces the blast radius if something still gets through.

Should you build your own gateway or use a product?

Default to using a mature product. Handling TLS, HTTP edge cases, slow clients, request smuggling and authentication at the edge is hard to get right, and products have years of hardening. Choose between managed offerings (AWS API Gateway, Apigee), which remove operations work but charge per request and impose limits, and self-hosted ones (Kong, Envoy, Nginx), which cost more effort but give control and better economics at sustained high volume. Custom code is appropriate for a BFF, which is application logic by nature, or for a custom plugin or filter inside an existing proxy, not for writing a new proxy from scratch.

14. Recap

  • A gateway is the single, stable front door for external clients. It hides the internal service layout and does the cross-cutting chores once: routing, TLS, authentication offload, rate limiting, transformation, versioning, observability, WAF integration and resilience policies.
  • Requests flow through an ordered chain of plugins or filters, with cheap rejections first, authentication before per-user limits, and the response passing back through the chain. Any step can short-circuit.
  • A gateway is a reverse proxy with API-management awareness for north-south traffic. A load balancer spreads load over instances, and a service mesh governs east-west calls. They compose.
  • Topologies follow ownership: start with one edge gateway, then add internal or per-team gateways when shared releases become the bottleneck.
  • BFFs give each client type a backend tailored to it, owned by the client team, doing presentation logic only. GraphQL and federation offer one flexible graph at the cost of query-cost control and caching difficulty.
  • Use proven products (Kong, Envoy-based, AWS API Gateway, Apigee, Nginx); build only a BFF or a custom plugin. Do the per-request price arithmetic when comparing managed and self-hosted.
  • Avoid business logic in the gateway, the god gateway, and the shared-release bottleneck.
  • Run a stateless fleet across zones with headroom for a zone loss; keep network calls off the hot path; track gateway-added latency separately.
  • The main failure modes are the gateway as a SPOF, cascading timeouts and retry storms, auth outages, and bad config pushes. Counter them with redundancy, deadlines, breakers, bulkheads, local JWT validation, explicit fail-open or fail-closed choices, and progressive config rollout.
