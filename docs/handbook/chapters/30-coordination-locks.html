Coordination Services and Distributed Locks

Many servers sometimes need to agree on a small fact: who is the leader, which servers are alive, what the current configuration is, who holds a lock. This chapter explains the services built for that job (ZooKeeper, etcd, Consul), how they behave when things fail, and why a distributed lock is far harder, and far less often needed, than it looks.

1. The problem: small facts that everyone must agree on

Most of the data in a large system is bulky and tolerates some disagreement: millions of user rows, billions of log lines, cached pages that may be a few seconds stale. A different, much smaller category of data has the opposite requirements. It is tiny (a few bytes to a few kilobytes), but every server must see the same value, and a wrong or stale answer causes real damage. Examples:

  • Who is the leader? A database cluster has one primary that accepts writes. If two servers both believe they are the primary, they accept conflicting writes and the data diverges (a situation called split-brain).
  • Who is alive? A scheduler needs to know which workers are up, so it can reassign the work of a dead worker. Guessing wrong in either direction is costly: reassigning work of a live worker duplicates it, and not reassigning work of a dead worker loses it.
  • What is the current configuration? A fleet of 500 servers must all switch from one feature setting to another in a controlled way, and a newly started server must read the right value immediately.
  • Who holds this lock? Two workers must not both rebuild the same report, charge the same customer, or compact the same storage shard at the same time.

Every team could implement these agreements itself, and many tried. The result was usually subtle bugs: a leader election built on a database row that breaks under a network partition, a heartbeat scheme whose timeouts are wrong under load, a lock that two clients both think they own. The correct implementations all rest on a consensus protocol (a protocol that lets a group of machines agree on a value even when some of them crash or messages are lost; Chapter 29 explains the algorithms, Raft and Paxos, in detail). Consensus is hard to implement correctly, and an application should not embed it.

The industry's answer is a coordination service: a small, dedicated cluster (typically 3 or 5 machines) that runs consensus internally and exposes a simple, higher-level API such as "store this small value under this name, tell me when it changes, and delete it automatically if I disappear". Application servers use that API to build leader election, locks, membership lists, and configuration distribution, without ever touching a consensus protocol themselves. This chapter covers the three well-known services (Apache ZooKeeper, etcd, and HashiCorp Consul), then spends considerable time on the most requested and most misunderstood thing built on top of them: the distributed lock.

Key idea A coordination service is a tiny, strongly consistent, highly available key-value store with two special features: change notifications (watches) and automatic cleanup of the data owned by a client that disappears (ephemeral nodes or leases). Almost every coordination pattern, including locks and leader election, is built from those two features plus the guarantee that all clients see one consistent order of changes.

Before going further, a note on prerequisites. This chapter assumes you know that machines fail independently, that messages can be delayed or lost, and that clocks on different machines disagree. If those ideas are new, read Chapter 27 first. Nearly every pitfall in the lock sections below is a consequence of those three facts.

2. What a coordination service is, and how it uses consensus

2.1 The shape of the system

A coordination service runs as a cluster of servers (often called an ensemble in ZooKeeper, a cluster in etcd, a set of server agents in Consul). Exactly one server is the leader at any moment, and the others are followers. The application processes are clients; each client connects to one server, sends requests over a long-lived connection, and receives notifications on the same connection.

Two kinds of request exist, and they follow different paths:

  • Writes (create a node, set a value, delete a key, acquire a lease) are forwarded to the leader. The leader appends the change to its log, sends it to the followers, and when a majority (a quorum) has durably recorded it, the change is committed and applied to every server's in-memory state. Only then is the client told "success". This is the consensus protocol at work: ZooKeeper uses its own protocol called ZAB (ZooKeeper Atomic Broadcast), while etcd and Consul use Raft. Both achieve the same guarantee: a committed write survives the crash of any minority of servers and is applied in the same order everywhere.
  • Reads can be served by the follower the client is connected to, from its local copy of the state, which makes reads cheap and scalable. The catch is that a follower may be slightly behind the leader, so a plain read can return a slightly stale value. Each system offers a way to demand a fresher read, at higher cost (section 2.3).

2.2 Why the data must be small

Every server keeps the entire data set in memory (ZooKeeper and Consul) or in a single memory-mapped file (etcd), because the consensus log is replicated to all members and applied identically on all of them. Adding more servers does not add capacity: a 5-server cluster stores no more than a 3-server cluster, and each write needs to reach a majority of servers, so more members make writes slightly slower. The cluster exists for fault tolerance, not for scale-out. This is the single most important sizing fact, and section 6 turns it into numbers.

2.3 Consistency guarantees to know

These systems give strong guarantees about ordering. All writes are totally ordered (every server applies them in the same sequence), and each system exposes that order as a number: ZooKeeper's zxid, etcd's revision, Consul's raft index. Clients can use this number to detect change and, as section 12 shows, to build fencing tokens.

The read guarantees differ. ZooKeeper gives sequential consistency by default: a client never sees time go backwards on its own connection, but a follower read can lag other clients' writes, so a client that needs the latest value first issues a sync call. etcd defaults to linearizable reads (the read goes through the leader and confirms leadership via a quorum round, so it reflects every committed write), with an optional cheaper serializable mode that reads local state and may be stale. Consul offers default (leader serves, may be briefly stale if the leader was just deposed), consistent (confirmed with a quorum), and stale (any server) modes. Knowing which mode your code uses is a classic interview probe: a leader-election check that uses a stale read is a bug.

3. ZooKeeper: znodes, ephemeral and sequential nodes, watches

ZooKeeper, created at Yahoo and later donated to Apache, is the oldest and most widely deployed of the three. It was designed as "a file system for coordination". Hadoop, HBase, Kafka (in its older architecture), Solr, and many internal systems have used it.

3.1 The data model

ZooKeeper's data is a tree, like a file system, of znodes. Each znode has a path such as /services/orders/instance-7, a small byte payload (limited by default to about 1 MB, and in practice you keep it to kilobytes), a version number, and metadata including creation and modification zxids. Unlike a file system, every znode can have both data and children.

Three flavours of znode matter:

  • Persistent: exists until explicitly deleted. Used for configuration and for directories such as /election.
  • Ephemeral: exists only as long as the session of the client that created it. When the session ends (the client disconnects and does not return within its timeout, or closes cleanly), ZooKeeper deletes the node automatically. Ephemeral nodes cannot have children. This is the core primitive for liveness: "this node exists" means "the client that made it is still alive, as far as the cluster can tell".
  • Sequential: when created, ZooKeeper appends a ten-digit, ever-increasing counter, maintained by the parent, to the name. Two clients that create /election/n_ at the same time get n_0000000007 and n_0000000008, and the order is decided by the cluster, not by clocks. Ephemeral and sequential are combined for locks and leader election (section 11).

3.2 Watches

Polling a coordination service to see whether something changed would waste its precious write-and-read capacity. Instead a client sets a watch: "tell me when this znode's data changes, or when its set of children changes, or when it is deleted". ZooKeeper delivers a notification to the client over its connection. Two details trip people up. First, a ZooKeeper watch is one-shot: it fires once, and the client must re-register it (after re-reading the data) if it wants to keep watching. Between the notification and the re-registration further changes can occur, so the correct pattern is "read the current state and set the watch in the same call, and treat the notification as a hint to reread, not as the new value". Second, the notification says what kind of change happened but not the new content; the client reads it separately. The guarantee ZooKeeper gives is that a client sees a watch event before it sees the new state, which prevents acting on stale data after being told it changed.

3.3 Versions and conditional updates

Every znode carries a version counter. A write may specify "apply only if the version is still N". This is compare-and-set (CAS) at the znode level, and it gives optimistic concurrency without a lock: two clients read version 4, both try to write version 4's successor, and only one succeeds; the loser rereads and retries. This is also the right building block for anything that can be expressed as a small atomic update.

3.4 Sessions

A client connects and receives a session with a negotiated timeout (typically 10 to 40 seconds in production; the server enforces bounds relative to its tick time). The client sends heartbeats (pings) on its connection. If the cluster sees no traffic or ping from the session for the timeout duration, it expires the session and deletes the session's ephemeral nodes. If the client's connection to one server breaks but it reconnects to another server within the timeout, the session survives, because session state is replicated. Section 7 examines what this means for correctness.

4. etcd: keys, revisions, leases, watches, transactions

etcd is the coordination store behind Kubernetes: the entire cluster state (every pod, service, secret) lives in it. It is written in Go, uses Raft for consensus, and exposes a gRPC API. Its design is a deliberate modernisation of the ZooKeeper ideas.

4.1 Flat keys with a revision

etcd's data model is a flat ordered key space (keys are byte strings; hierarchy is by convention, such as /services/orders/7) rather than a tree. Range queries by prefix make "list the children" easy. The central concept is the revision: a single global 64-bit counter that increases with every committed write transaction. Each key records its create_revision, mod_revision, and a version (how many times it was changed since creation). etcd keeps old revisions until they are compacted, so a client can read the state as of a past revision, which makes consistent snapshots and gap-free watching possible.

4.2 Leases

Where ZooKeeper ties ephemeral nodes to a client session, etcd uses leases. A client asks for a lease with a time to live (TTL), say 15 seconds, and receives a lease ID. It can attach any number of keys to that lease. The client must periodically send keep-alive requests to refresh the TTL. If keep-alives stop, the lease expires after the TTL, and all keys attached to it are deleted. A lease is thus a generalised, explicit version of a session, and it can be shared by many keys or revoked deliberately. Importantly, the lease TTL countdown is managed by the cluster leader, not by the clock of the client.

4.3 Watches as streams

An etcd watch is a long-lived stream, not one-shot. A client says "watch this key or prefix starting at revision R" and receives every subsequent event in order, including events that happened since R, so no change is missed even if the client was briefly disconnected: it reconnects and resumes from the last revision it processed. (If R has been compacted away, the watch fails and the client must re-list and restart; this is why Kubernetes controllers use the "list then watch from the list's revision" pattern.) This streaming design is generally easier to use correctly than one-shot watches.

4.4 Transactions

etcd offers a transaction: an atomic "if / then / else" made of comparisons and operations. For example: if the key /locks/report has create_revision == 0 (it does not exist), then put it with my lease, else read it to see who owns it. The comparison and the action happen atomically on the leader. This is more expressive than a single CAS and is how etcd's lock and election recipes are implemented.

5. Consul: coordination with a service-discovery focus

HashiCorp Consul also uses Raft for its server cluster, but its main purpose is service discovery and health checking, with a key-value store as a supporting feature. Its distinctive pieces:

  • Agents on every node. Each machine runs a Consul agent. Servers (3 or 5) run Raft; client agents forward requests to the servers and run local health checks.
  • Gossip layer. Agents learn who is alive using a gossip protocol (Serf, based on SWIM) running between all agents. Failure detection is distributed and cheap, so thousands of nodes can be tracked without every node sending heartbeats to the servers. Gossip is not consensus; the servers' Raft log holds the authoritative catalog.
  • Sessions and locks. Consul KV supports sessions with a TTL and optional health-check linkage. A key can be acquired by a session (acquire), and it is released if the session is invalidated. This supports locks and leader election in the same style as the other two.
  • Services, health, DNS. Services register with health checks; clients discover healthy instances via an HTTP API or a DNS interface. (See Chapter 49.)

All three give the same core guarantee: consistent small data with ephemeral ownership and change notification.

6. Sizing and limits: not a general database

A coordination service is a precision instrument, and the most common mistake is treating it as a general-purpose database. Its limits follow directly from the design in section 2.

6.1 Cluster size: 3 or 5, never even

A consensus cluster of N members needs a majority, floor(N/2) + 1, to commit. With 3 members the majority is 2, so it tolerates 1 failure. With 5, the majority is 3, so it tolerates 2. With 4 members the majority is 3, so it still tolerates only 1 failure, the same as 3, while costing more and being slower; with 6 it tolerates 2, the same as 5. That is why you run an odd number. Three is common for most systems, five for critical ones where you want to survive one planned maintenance and one unplanned failure at the same moment. Seven is rare, because each extra member slows every write and adds little. If members are spread across failure domains, three zones with one or two servers each is the standard layout, so that losing one zone leaves a majority.

6.2 Limits to remember

  • Data size. The whole data set fits in memory on each server. Typical guidance is megabytes to a few gigabytes (etcd recommends keeping its database to roughly 8 GB or less; ZooKeeper's per-znode limit is about 1 MB, and designs keep values under a few kilobytes). Store pointers (an S3 key) rather than blobs.
  • Write throughput. Every write is a consensus round that includes a durable disk sync on a majority of servers. A well-provisioned cluster on SSDs reaches on the order of thousands to low tens of thousands of writes per second; real deployments are far below that. The disk fsync latency of the slowest majority member is the dominant factor, so these services want fast, dedicated disks and a low-latency network (usually one region, spread over zones; multi-region clusters pay cross-region latency on every write).
  • Read throughput. Much higher than writes since followers serve reads locally, but linearizable reads still involve the leader.
  • Number of watches and clients. Tens of thousands of clients with watches are feasible; hundreds of thousands put pressure on the servers. Use caching proxies or a hierarchy (Consul's agents, ZooKeeper observers, a "config sidecar" that watches once per host) to fan out.
  • Not for high-churn data. Counters, user sessions, rate-limit state, and job queues with millions of items belong in Redis, a database, or a real queue. Put into the coordination service only the data whose correctness depends on strong consistency and that changes rarely.
Watch out A coordination cluster is a shared dependency of everything built on it. If it slows down, leader elections time out, sessions expire, services deregister, and you can turn a small hiccup into a fleet-wide outage. Treat it as critical infrastructure: dedicated machines, fast disks, monitoring of commit latency and leader changes, and strict quotas so one tenant cannot flood it with writes.

7. Sessions, leases and expiry: the failure semantics that matter

The feature that makes coordination services powerful is automatic cleanup: if a client dies, its ephemeral nodes or leased keys vanish and others can take over. But the cluster cannot distinguish "the client crashed" from "the client is alive but slow or partitioned". It can only observe that it has not heard from the client for the timeout. This section spells out what that implies.

7.2 What each side knows

  • The cluster knows exactly one thing: it has or has not received a renewal within the TTL. It is consistent about this: all members agree that the lease is expired and that the key is deleted.
  • The client knows that its last successful renewal was at some local time. It can estimate when its lease will expire, but it cannot be sure: its clock might run fast or slow, and it might be paused between checking the time and acting.
  • The client library typically tells the application about connection trouble. ZooKeeper clients surface states Disconnected (connection lost, session may still be alive; do not assume you lost the lock yet, but stop acting as owner if you require safety) and Expired (session definitely gone; locks are lost). Handling "disconnected" conservatively is the core of using these services correctly: a careful client treats the moment it loses contact as the moment it must stop doing protected work, rather than waiting to hear it has expired.

7.3 Choosing the timeout

A short timeout (2 to 5 seconds) detects real failures quickly, but a brief garbage-collection pause or network blip expires healthy sessions, causing needless leader changes ("flapping") and, if the client does not react correctly, split ownership. A long timeout (30 to 60 seconds) is stable but slows recovery: after a leader crashes, nobody else becomes leader until the timeout passes. A typical production compromise is 10 to 30 seconds with a client heartbeat interval of one third of the timeout. The important design conclusion is that no timeout makes expiry perfectly safe; it only trades unavailability against the probability of overlap. Safety must come from elsewhere, namely fencing (section 12).

8. Distributed locks: why you need them, and what they promise

A lock on a single machine is a familiar idea: before touching shared data, a thread acquires the lock; other threads wait; the holder releases it. The operating system makes this reliable, because the threads share one memory and one clock, and a crashed process's locks are cleaned up with it.

A distributed lock tries to give the same promise to processes on different machines: at most one holder at a time. It is wanted for two quite different reasons, and distinguishing them is the most useful thing a candidate can do:

  • Efficiency. The lock avoids doing the same work twice. For example, two workers both about to generate the same expensive daily report. If the lock occasionally fails and both run, the cost is some wasted computation, but the result is still correct. For this purpose a simple, approximate lock is fine.
  • Correctness. The lock protects data from corruption. For example, two clients both updating the same file or the same account balance as read-modify-write. If the lock fails and both proceed, data is lost or corrupted. For this purpose the lock must be truly safe, and, as we will see, a lock alone cannot be: it must be paired with a fencing token checked by the resource itself.

The properties we want from a distributed lock are:

  1. Mutual exclusion (safety): at most one client holds the lock at a time.
  2. Deadlock freedom (liveness): if the holder crashes, the lock is eventually released so others can proceed. This is why every distributed lock needs a time limit or a session tied to liveness.
  3. Fault tolerance: as long as a majority of the lock service is up, clients can acquire and release locks.

Property 2 directly collides with property 1: to release the lock of a crashed client you must declare it dead based on silence, but silence is also what a paused or partitioned client looks like. This tension is the root of every problem in this chapter.

9. Locks with a TTL, and the Redis SET NX PX lock

9.1 The TTL lock idea

The simplest design that satisfies deadlock freedom: store a key representing the lock in some shared store, with an expiry time. A client acquires the lock by creating the key only if it does not exist. If it crashes, the key expires on its own. If the work is longer than expected, the client extends the expiry (renews the lease). The store can be a coordination service (etcd lease, Consul session, ZooKeeper ephemeral node) or a plain cache such as Redis.

9.2 The Redis lock in detail

Redis is single-threaded per instance and executes each command atomically, so it is popular for quick locks. The standard single-instance pattern is:

SET lock:report:2026-11-17  <random-token>  NX  PX 30000

NX means "set only if the key does not exist", so exactly one client succeeds. PX 30000 sets a 30,000 ms expiry, so a crashed holder's lock disappears. The value is a random token unique to this acquisition (such as a UUID). The token matters for release. A naive client that simply deletes the key could delete a lock that now belongs to someone else: client A's lock expired, client B acquired it, then A finishes and deletes B's lock. To prevent that, release must be "delete only if the value is still my token", and that check-and-delete must be atomic, so it is done with a small server-side Lua script:

if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end

This is perfectly reasonable as an efficiency lock. What it does not do, even in the single-instance version, is guarantee exclusion in the face of pauses and failures:

  • If the Redis instance is the single point, its failure means no one can acquire locks (availability loss), and if it restarts without persistence, locks are forgotten and a second client can acquire a lock the first still believes it holds.
  • If Redis is replicated asynchronously to a replica and the primary dies right after granting a lock, the promoted replica may not have the key, and a second client acquires the "same" lock. This is a real, documented hazard of asynchronous replication.
  • The holder can still stall after acquiring (section 13), so the TTL expires while it believes it is working.

9.3 Renewal (the watchdog)

Because the protected work may take longer than any fixed TTL you can choose, libraries start a background watchdog thread that periodically extends the TTL while the owner is still working (for example, Redisson renews every third of the TTL). This lessens expiry mid-work in normal operation, but note what it does not fix: if the whole process is frozen, the watchdog is frozen with it, and the lease expires anyway. Also, a lock renewed forever by a stuck-but-alive thread blocks everyone; give work an upper bound.

10. The Redlock debate, explained fairly

To remove the single-point-of-failure problem of one Redis instance, Salvatore Sanfilippo (known as antirez, the creator of Redis) proposed an algorithm called Redlock. The idea: run N independent Redis masters (typically 5; not replicas of each other, no shared failure). A client acquires the lock by:

  1. Recording the current time.
  2. Trying to SET key token NX PX ttl on each of the N instances in turn, using a small per-instance timeout so a dead instance does not stall it.
  3. Computing how long acquisition took. The lock is considered acquired only if the client got it on a majority (at least 3 of 5) and the elapsed time is less than the lock's TTL. The remaining validity time is TTL minus elapsed time (minus a small allowance for clock drift).
  4. If acquisition failed, release on all instances (even ones where it seemed to fail) and retry after a random delay.

The reasoning mirrors consensus: a majority of independent nodes agreeing makes it unlikely that two clients both hold a majority.

10.1 Martin Kleppmann's critique

Martin Kleppmann (author of Designing Data-Intensive Applications) published an analysis arguing that Redlock is unsuitable for correctness-critical locking. His points, summarised:

  • It depends on timing assumptions that real systems violate. Redlock assumes bounded network delay, bounded process pauses, and bounded clock error. Real systems have unbounded stalls: a long garbage-collection pause, a VM migration, a page fault, a congested network. A client can acquire the lock, stall past the TTL, wake up, and act as if it still held it, while another client now holds a valid lock.
  • It relies on wall-clock time. The TTL on each Redis node is measured with that node's clock. If a node's clock jumps forward (an NTP adjustment, an administrator changing the time), the key can expire early, and two clients could each hold a majority. (Antirez's counter: use of a monotonic clock source and sane operational practice make large jumps unlikely.)
  • It provides no fencing token. Redlock gives you a random string, not a monotonically increasing number. Without a number that the storage layer can compare, you cannot reject a stale writer. A fencing token (section 12) is the only way to make a lock safe against pauses, and Redlock has no natural way to produce one, because the independent instances do not share a counter.

His conclusion: if you want the lock for efficiency, Redlock is heavier than needed (a single Redis node is enough); if you want it for correctness, Redlock is not safe enough, and you should use a real consensus-based system (ZooKeeper, etcd) with fencing tokens.

10.2 Antirez's response

Antirez replied that the critique was partly aimed at a different bar than Redlock claims. His arguments:

  • Redlock's validity-time check does account for delays during acquisition, and a client can check remaining validity before using the resource to guard against some delays. A pause that occurs after the last check and before the write is a problem for every lock, including ZooKeeper's, not specific to Redlock.
  • The fencing-token argument applies equally to any lock service: if the storage layer cannot check tokens, none of them are safe. So it is not a defect unique to Redlock.
  • The clock concerns are manageable: Redlock only needs the clocks to advance at roughly the same rate (bounded drift) over a short period, not to be synchronised to each other.
  • Many applications want exactly the "efficiency" level of protection, and Redlock is pragmatic for them.

10.3 How to read the debate

The two positions are less opposed than they sound. Both agree that no lock based on timeouts is safe against an arbitrarily long pause unless the protected resource participates. They disagree about how bad the failure modes are in practice and what the algorithm claims. The takeaway an interviewer wants to hear is the decision rule: use a lock for efficiency freely, but if mutual exclusion protects correctness, you need a fencing token validated by the resource, and a lock service that can issue monotonic tokens (ZooKeeper's zxid or sequential node number, etcd's revision, a database sequence).

Interview tip If asked "is Redlock safe?", do not take a side with a slogan. Say: it is fine for efficiency locks; for correctness, no timeout-based lock is safe by itself, and Redlock additionally lacks a fencing token and leans on clock assumptions, so I would use etcd or ZooKeeper plus fencing, or avoid the lock entirely using a conditional write.

11. Lock recipes on ZooKeeper and etcd

11.1 ZooKeeper: ephemeral sequential nodes

The naive ZooKeeper lock is: everyone tries to create /lock as an ephemeral node; the one that succeeds holds the lock; the others watch /lock and retry when it is deleted. It works but has the herd effect: when the lock is released, all N waiting clients get a notification and all rush to create the node, causing a burst of N requests of which N-1 fail. With hundreds of waiters this wastes cluster capacity and increases latency.

The standard recipe removes the herd:

  1. Each client creates an ephemeral, sequential node under the lock directory: /lock/c_ becomes /lock/c_0000000041, /lock/c_0000000042, and so on.
  2. The client lists the children of /lock. If its node has the lowest number, it holds the lock.
  3. Otherwise it sets a watch on the node with the next lower number (its predecessor only) and waits.
  4. When the predecessor is deleted (released or its client's session expired), the watcher is notified, re-lists the children, and checks again whether it is now lowest. Usually it is.
  5. To release, the client deletes its node.

Only one client is woken per release, so there is no herd, and the waiters form a fair FIFO queue in the order the sequence numbers were assigned. If a waiter in the middle of the queue dies, its node disappears and its successor wakes, rechecks, finds it is still not lowest (someone ahead of it exists), and re-watches the new predecessor. Note the subtle case: a client that creates its node but whose create call reports a connection failure may not know whether the node exists; robust recipes embed a unique client ID in the node name so the client can look for its own node after reconnecting, preventing a "ghost" node that blocks the queue until the session expires.

11.2 etcd: lease-attached key with revision ordering

etcd's lock recipe has the same structure using different primitives. A client obtains a lease and writes a key such as /locks/report/<lease-id> attached to that lease. The write's create_revision is globally ordered. The client lists all keys under the prefix; if its key has the smallest create revision it owns the lock; otherwise it watches the key with the next-smaller revision (the same predecessor trick) and waits until that key is deleted. Releasing is deleting the key; a crashed client's lease expires and the key is removed. Because the transaction machinery in section 4.4 can express "create the key only if no key with a lower revision exists", the check is atomic. The ownership key's revision is a ready-made monotonically increasing fencing token, which is one reason etcd is well suited to the correctness-grade lock.

11.3 Consul: session-bound key

Consul's lock is simpler: create a session (TTL plus optional health-check linkage), then PUT /kv/lock?acquire=<session>. The call succeeds only if no other live session holds the key. Waiters use a blocking query on the key's index to learn about release. The ModifyIndex of the key can serve as the token. There is no built-in fair queue, so contention on a popular lock produces some herd behaviour.

12. Fencing tokens: making a lock safe against pauses

Section 7 showed that a lock holder can lose the lock without knowing it. For an efficiency lock that is tolerable. For a correctness lock it is a disaster: a paused client wakes up and overwrites data that the new lock holder has since changed. The cure is to make the resource itself refuse stale clients, rather than trusting clients to know they are stale.

A fencing token is a number issued by the lock service that increases every time the lock is granted. Client A gets token 33; after A's lease expires, client B gets token 34. Every request that a client makes to the protected resource includes its token. The resource remembers the highest token it has seen, and rejects any request carrying a lower token. So after B writes with token 34, a late write from A with token 33 is refused, even though A is convinced it still holds the lock.

12.1 Where the token comes from

  • ZooKeeper: the sequence number of the lock node, or the zxid (czxid) of its creation. Both strictly increase.
  • etcd: the create_revision or mod_revision of the lock key.
  • Consul: the LockIndex / ModifyIndex of the key.
  • A database: a sequence or an incrementing integer on a lock row, updated in the same transaction that grants the lock.
  • Redis: INCR on a counter next to the lock can produce a token, but the guarantee degrades with Redis failover (the counter may roll back after an asynchronous failover); this is one reason Redis is used for efficiency locks.

12.2 What the resource must do

This is the part people forget: the protected resource must be able to check and store the token. A database can do it with a conditional update (UPDATE ... SET data=?, last_token=? WHERE id=? AND last_token <= ?, checking the row count). A storage service might accept a token as a request header and compare it with the stored maximum. A file or an external API that you do not control cannot enforce it; then you cannot get correctness from a lock, and must rely on idempotency or a different design (section 14). If every write is also idempotent, then even a stale write that slips through does no harm.

Key idea A lock tells you who should be working. A fencing token lets the resource verify who is allowed to write at the moment of the write. Only the second is safe against pauses, clock errors, and lease expiry.

13. Lock pitfalls

13.1 Garbage-collection and other pauses

A process can stop executing for seconds, with no way for it to notice. Causes include stop-the-world garbage collection in a managed runtime, the operating system swapping the process, a virtual machine being paused or live-migrated, a laptop being suspended, a container being CPU-throttled by its cgroup limit, or the process being stopped by a debugger or SIGSTOP. Pauses of many seconds have been measured in production. The pattern "check I still hold the lock, then act" has a window between the check and the act in which a pause turns the check false. No amount of checking inside the client closes the window; only a token verified by the resource does.

13.2 Clock drift and jumps

Lock expiry with TTLs depends on clocks. Each machine's clock drifts (typically up to some tens of parts per million), and synchronisation (NTP) can step the clock forward or backward. If the lock service computes expiry using its own clock and the client computes its remaining validity using a different one, they will disagree. Practical rules: measure durations with a monotonic clock (not wall-clock time-of-day) on the client; let the service own the expiry decision; have the client treat its lock as lost earlier than the nominal expiry (a safety margin of drift plus network delay); and never compare timestamps from different machines to decide who holds a lock. Chapter 27 covers clock behaviour in depth.

13.3 Lease expiry in the middle of work

If the job may take longer than the lease, the client must renew while working, which requires a thread that can run during the job, and a plan for the case when renewal fails (network lost): the client must abort the protected work promptly, rather than finish and hope. Design work in small steps with a lock check (and token) at each step, or make the work resumable and idempotent so that being preempted halfway is harmless.

13.4 Lost unlock

If a client crashes or its release call is lost, the lock stays held until its lease expires. This is acceptable and is the whole reason for TTLs; but choose the TTL to match how long you can tolerate the resource being blocked. The opposite bug is a release that deletes someone else's lock after expiry; that is why release checks the token (section 9.2). Also release in a finally block so exceptions do not leak locks.

13.5 Reentrancy

A local mutex in many languages is reentrant: the same thread can acquire it again without deadlocking itself. A naive distributed lock is not: if method a() takes the lock and calls b(), which tries to take the same lock, it waits for itself forever (until the TTL expires). Reentrant locks track the owner identity (client ID plus thread ID) and a hold count in the lock value. Recommended practice is to avoid needing reentrancy by taking the lock at one clear boundary and passing a "I already hold it" context inward.

13.6 Deadlock

With a TTL, a true permanent deadlock cannot occur, but stalls can: client A holds lock X and waits for lock Y, client B holds Y and waits for X; both stall until a TTL fires, then retry, possibly colliding again (livelock). Prevent it as in local code: acquire multiple locks in a global, consistent order; acquire with a bounded wait and back off with random jitter; prefer one coarse lock to many fine ones when possible.

13.7 Other traps

  • Thundering herd on release (fixed by the queue recipe, section 11).
  • Too-fine granularity. A lock per record at 100,000 requests per second would overwhelm the coordination service. Locks are for coarse, infrequent decisions.
  • Treating a failed acquire as success when the service times out. A timeout means "unknown", not "got it": the grant may have happened, so check or release.
  • Lock service unavailable. Decide in advance whether the work should proceed (risking duplication) or stop (risking an outage). For correctness locks the answer is stop.

14. When you do not need a lock

The best distributed lock is the one you avoid. Locks add a dependency, a failure mode, and subtle bugs. Ask first whether the problem can be solved by a mechanism that is naturally safe.

TechniqueHow it removes the need for a lock
IdempotencyMake the operation safe to run twice, usually with an idempotency key so the second run is recognised and ignored. Then "two workers both did it" is harmless. See Chapter 32. This turns a correctness lock into an efficiency lock, which is cheap.
CAS / optimistic concurrencyRead a value and its version, compute, then write "only if the version is unchanged". Conflicting writers see a failure and retry. No lock is held across the computation, and no lease can expire mid-work. Works in SQL (WHERE version = ?), DynamoDB (conditional writes), ZooKeeper and etcd (version or revision comparison).
Single consumer queueIf all work for an entity goes through one queue partition read by one consumer at a time, ordering and exclusion are by construction. Kafka partitions assigned to one consumer in a group, or a FIFO queue with a message group, give "one at a time per key" without an explicit lock.
Database row locksIf the data lives in a relational database, SELECT ... FOR UPDATE or a unique constraint uses the database's own lock manager and transaction, which already cleans up on disconnect and ties the lock to the data. See Chapter 18. The lock and the data are in the same system and the same transaction, so there is nothing to fence.
Unique constraints"Only one of these may exist" is an insert that fails on duplicate. The first inserter wins. Often this is all a leader election or dedupe needs.
Partitioning / shardingAssign each entity to exactly one owner (consistent hashing, partition assignment). Within a shard there is only one writer, so no lock is required; coordination happens only when ownership changes.
Interview tip When an interviewer says "add a distributed lock here", a strong answer first states what the lock is protecting and whether it is for efficiency or correctness, then proposes whether a conditional write or idempotency key would remove the need. Only then, if it is really required, describe the lease, the fencing token, and the failure behaviour.

15. Leader election and lease renewal

Leader election picks one member of a group to perform a role that must have a single performer: the primary of a database, the scheduler, the coordinator of a rebalance, the single writer of an index. It is a distributed lock held for a long time, with the added requirement that the others find out quickly when leadership changes.

15.1 The recipe

  1. Every candidate attempts to create the same key (or enqueue a sequential node, as in the lock recipe), attached to its session or lease. Exactly one wins and becomes leader. It writes its own address into the node so others can find it.
  2. The others watch the leader node (or only their predecessor, to avoid a herd) and wait as followers or standby.
  3. The leader keeps its session alive or renews its lease every fraction of the TTL (typically every TTL/3). Renewal is the proof of liveness.
  4. If the leader crashes or can no longer reach the coordination service, renewals stop, the lease expires, the key disappears, the watchers fire, and a new election runs. The recovery time is roughly the TTL plus a small election time.
  5. If the leader finds it cannot renew (service unreachable, renewal rejected), it must immediately step down: stop doing leader work before its lease can expire at the service. Because of clock error, it should step down a safety margin early, for example after 2/3 of the TTL passes without a successful renewal.

15.2 Safety of the leader

The leader has the same pause problem as any lock holder: a leader that stalls can wake up after a new leader has been elected and still act as leader (a "zombie leader"). Therefore leader election is also paired with a fencing token, often called an epoch or term (the same concept as the term number in Raft). Every action the leader takes on shared state carries the epoch, and followers or storage reject messages from older epochs. Most databases and queue systems do exactly this internally; if you build your own leader-based service, include an epoch in every write.

15.3 Do you need to build this?

Often the answer is no. Kubernetes offers a lease-based leader election object that controllers use through client libraries. Libraries such as Apache Curator (ZooKeeper), the etcd concurrency package, and Consul's lock helper implement the recipe, including the awkward reconnection cases. Use them rather than writing your own, and remember that if your whole service is stateful and replicated, the better design may be to embed Raft rather than delegate to an external service. Chapter 29 covers how leaders are chosen inside consensus protocols.

16. Config distribution, membership, and the rate of watch events

16.1 Config distribution and dynamic config

Storing configuration in a coordination service gives three benefits over files baked into images: all servers see one consistent version, changes take effect without a redeploy, and a changed value can be pushed instantly through watches. The pattern:

  1. At startup the application reads the config key (with a consistent read) and keeps it in memory.
  2. It watches the key. On a change event it rereads the value, validates it, and swaps it in atomically (replace a reference to an immutable config object, rather than mutating fields in place, so request threads see either the whole old or the whole new config).
  3. It keeps a local copy on disk as a fallback, so a server restarting while the coordination service is down can still start with the last known good configuration.

Practical advice: keep each value small; version the whole config document and allow rollback; roll out risky changes gradually (a per-cell key or percentage) rather than to all servers in the same second; and distinguish dynamic operational settings (rate limits, feature flags, timeouts) from secrets, which need a proper secret store with access control and rotation. Chapter 49 goes into central configuration, secrets, and the client-side caches that make this resilient.

16.2 Group membership

For membership, each member creates an ephemeral node under a group path, with its address as data. The member list is the list of children; a watch on the children tells interested parties when someone joins or leaves. This gives an authoritative, consistent view, which is different from gossip-based membership (Consul's Serf, Cassandra's gossip), which is eventually consistent but scales to thousands of nodes without loading a central cluster. Choose consensus-based membership when exact agreement matters (who is in the current voting group), and gossip when approximate liveness suffices.

16.3 The rate of watch events

Watches look free but are a load multiplier. Suppose 10,000 clients watch one config key and it changes once. That single write produces 10,000 notifications, and each client then rereads the value, so 10,000 reads arrive within a short window. If a misbehaving job rewrites the key every second, the service pushes 10,000 notifications per second. With a one-shot watch, a client that is slow to re-register can miss intermediate states, which is fine for config (only the latest matters) but not for an event log.

Mitigations: put a hierarchy in the middle (one agent per host or per rack watches the key and republishes locally, so the cluster sees hundreds of watchers, not tens of thousands); coalesce changes by writing config as one key rather than many keys changed in a burst; apply rate limits and quotas on writers; add random jitter to client rereads so they do not stampede; and watch a version key that points to a payload stored elsewhere when the payload is large.

18. Worked example: a single-active cron scheduler

Problem. A platform runs a recurring job scheduler. Jobs such as "send daily invoices at 02:00" must fire exactly once per scheduled time, even though the scheduler runs on 3 instances for availability. Running a job twice sends duplicate invoices. Missing a run is also unacceptable, but a few seconds of delay is fine. (Chapter 38 covers scheduling and workflow engines more broadly; here we focus on the coordination part.)

18.1 Design

  1. Single-active leader. The three scheduler instances run leader election through a 3-node etcd cluster. A lease of 15 seconds, renewed every 5 seconds, backs the key /scheduler/leader. Only the leader scans the schedule table and enqueues due jobs. The two standbys watch the key.
  2. Epoch as fencing token. The leader's lease revision at election is its epoch (for instance, 9812). It is stored with every job it enqueues.
  3. Exactly-once enqueue by conditional write. For each due job, the leader inserts a row into a job_runs table with a unique key (job_id, scheduled_time), plus the epoch. If a zombie leader or an overlapping failover tries to insert the same run, the unique constraint rejects it. The database insert is the real mutual exclusion; the leader election merely reduces contention and duplication of effort.
  4. Epoch check on writes. The insert is conditioned on epoch >= (SELECT max(epoch) FROM scheduler_state), and each new leader first writes its epoch to scheduler_state. A stale leader's writes fail the check once the new leader has announced itself.
  5. Workers are idempotent. Workers consume runs from a queue and execute them using the run's ID as an idempotency key, so even a rare double delivery does not send two invoices.
  6. Catch-up. A new leader scans for runs whose scheduled time has passed and have no job_runs row (a gap from the failover) and enqueues them, so nothing is missed.

18.2 Numbers

  • Load on etcd: one lease renewal per 5 seconds from one leader, plus watches from 2 standbys. That is 0.2 writes per second, trivial, so a small 3-node cluster with default settings is ample (and it could be shared with other tenants without strain).
  • Failover time: the old lease runs up to 15 seconds after the last renewal; the standby is notified immediately when it expires, and the election takes a few tens of milliseconds. Expect roughly 10 to 16 seconds without a leader after a crash. Jobs due in that window run late by at most that amount plus catch-up time, which is acceptable by the requirements.
  • Leader self-fence: the leader steps down if it has not renewed successfully for 10 seconds (two thirds of the TTL), so a partitioned old leader stops before the new one starts at 15.
  • Throughput: if there are 20,000 jobs and the busiest minute has 3,000 due, the leader inserts 3,000 rows (about 50 per second), which any relational database handles easily.

18.3 Failure walkthrough

  • Leader crashes at 01:59:58. Lease expires by about 02:00:13; scheduler 2 wins, writes epoch 9813, scans runs scheduled up to now, finds the 02:00 invoices missing, inserts them. Invoices go out roughly 15 seconds late, once.
  • Leader pauses for 40 seconds (GC), wakes at 02:00:30. Meanwhile scheduler 2 has become leader and inserted the 02:00 runs. The old leader tries to insert the same runs: the unique key rejects them, and its epoch check fails; it sees its lease is gone and steps down. No duplicates.
  • etcd cluster loses quorum. No one can renew. After the safety margin the leader steps down; no jobs are started until quorum returns. This is a deliberate choice of consistency over availability: it is better to run late than to run twice. After recovery the catch-up scan runs the missed jobs.
  • Network partition isolates the leader from etcd only. Same as the previous case for that node; another scheduler on the majority side takes over.
Good design note Notice that the correctness guarantee does not rest on the lock. It rests on a unique constraint in the database, which is a conditional write. The election exists for efficiency and tidy operation. This "lock for efficiency, constraint for correctness" layering is the pattern to reach for.

19. Interview questions and answers

Why not just use a database table or a Redis key for leader election instead of ZooKeeper or etcd?

You can, and for low-stakes cases it is fine, but a coordination service gives you things that are hard to build correctly yourself. It is replicated by consensus, so the lock state survives the loss of a minority of its servers without forgetting who the leader was. It ties ownership to a session or lease so that a crashed owner is cleaned up automatically, and it provides watches so followers learn about changes promptly without polling. A single database row or a single Redis node is a single point of failure, and an asynchronously replicated Redis can lose the lock record on failover, letting two nodes believe they are leader. If the data store you already run offers a conditional write or a unique constraint, that is often enough, and it avoids a new dependency.

Why do coordination clusters use 3 or 5 servers, and why not 4 or 100?

Consensus needs a majority to commit, so a cluster of N tolerates floor((N-1)/2) failures. Three servers tolerate one failure, and five tolerate two. Four servers still tolerate only one failure (majority is three), so the extra machine adds cost and write latency without more tolerance. A hundred servers would be slower, not bigger, because every server stores all data and every write must be acknowledged by a majority of them. Capacity does not scale with members; for more throughput you shard across separate clusters or reduce the load placed on the cluster by caching and hierarchy.

What is an ephemeral node or a lease, and what happens when a client is merely slow rather than dead?

An ephemeral znode (ZooKeeper) or a lease-attached key (etcd) exists only while the owning client keeps proving it is alive through heartbeats or renewals. If the proofs stop for longer than the timeout, the service deletes the node. The service cannot tell dead from slow, so a client that is paused, garbage-collecting, or partitioned will be expired just like a crashed one, while still believing it is the owner. That is why the client must stop protected work as soon as it loses contact, and why correctness-critical resources must verify a fencing token, because the lease alone cannot prevent a stale client from acting after it wakes.

Explain the herd effect in a ZooKeeper lock and how the standard recipe avoids it.

If all waiters watch a single lock node, then when it is released every waiter is notified at once and they all race to acquire it, producing a burst of requests of which all but one fail. With hundreds of waiters this can overload the ensemble. The recipe has each client create an ephemeral sequential node and watch only the node immediately before its own. Release then notifies exactly one client, which checks whether it is now lowest. The result is a fair first-in-first-out queue with constant work per release, and it also handles a waiter dying in the middle of the queue gracefully.

What is a fencing token and why is a lock without one unsafe?

A fencing token is a number that the lock service increases each time it grants the lock. The client attaches it to every write to the protected resource, and the resource rejects any write with a token lower than the highest it has seen. Without it, a client that paused past its lease expiry can wake up and overwrite data written by the new owner, because nothing tells the resource that this client is stale. A lock only reduces the chance of overlap; the token makes the resource itself enforce exclusion, which is the only approach that holds up under arbitrary pauses and clock errors. It requires the resource to be able to compare and store the token, such as a conditional database update.

Summarise the Redlock debate. Would you use Redlock?

Redlock acquires a lock on a majority of several independent Redis instances within a time bound. Kleppmann argued that it is unsafe for correctness locking because it assumes bounded pauses, delays and clock drift, and it provides no fencing token, so a stalled client can still act on an expired lock. Antirez answered that the validity-time check handles delays during acquisition, that clock requirements are modest, and that the fencing objection applies to every lock service equally. Both agree no timeout-based lock is safe against an unbounded pause without resource-side checks. I would use a single Redis lock for efficiency purposes, and for correctness I would use etcd or ZooKeeper with fencing tokens or, better, a conditional write that avoids the lock.

When would you not use a distributed lock at all?

When the operation can be made idempotent, a duplicate execution is harmless and the lock is unnecessary. When the data lives in a database, a compare-and-set on a version column, a unique constraint, or a row lock inside a transaction gives exclusion that is tied to the data and cleaned up on disconnect. When work can be routed so that a single consumer handles all events for a key (a partitioned queue, or sharding by owner), exclusion comes from the structure. I would add a distributed lock only when work has side effects on a resource that cannot enforce a condition itself, and even then I would pair it with a fencing token and a bounded lease.

How does leader election work with leases, and how do you handle a leader that cannot renew?

Candidates try to create a single key attached to a lease; the winner is leader and renews the lease, typically every third of the TTL. Standbys watch the key. If the leader dies, renewals stop, the lease expires, the key vanishes, and the standbys race again. A leader that fails to renew must step down on its own, earlier than the nominal expiry to leave room for clock error, because the service will hand leadership to someone else once the lease expires. All leader actions should carry an epoch or fencing token so that a zombie leader's late writes are rejected. Failover time is roughly the TTL, which you tune against the tolerance for needless failovers.

How would you distribute dynamic configuration to 10,000 servers using a coordination service?

Store the config as a small versioned value, have each server read it at start and watch it, and swap in the new immutable config object on a change event. Writing straight to 10,000 watchers makes each change cost 10,000 notifications and 10,000 rereads, so I would add a per-host or per-rack agent that watches once and fans out locally, add jitter to rereads, and keep a last-known-good copy on disk so servers can start when the coordination service is down. I would roll out risky changes gradually by cell or percentage, and keep secrets in a dedicated secret store, not in the coordination service.

What happens to services built on ZooKeeper or etcd if the cluster loses quorum?

Writes and linearizable reads stop, because they need a majority. Existing sessions cannot be renewed, so clients see disconnection and, once their timeouts pass without a quorum to re-establish them, expiry. Locks and leaderships built on them can no longer be safely held, so well-written clients step down, and the application typically pauses leader-only work rather than risk split-brain. Clients with cached data can often keep serving reads of configuration. This is the consistency-over-availability tradeoff of the CP design (see Chapter 29), and it is why the cluster must be sized, placed across zones, and monitored as critical infrastructure.

20. Recap

Recap

  • A coordination service (ZooKeeper, etcd, Consul) is a small, strongly consistent store, replicated by consensus (ZAB or Raft) across 3 or 5 servers, offering watches and automatic cleanup of data owned by vanished clients.
  • Data must be small and relatively slow-changing. More servers add fault tolerance, never capacity. Use odd cluster sizes. It is not a general database, and it is a critical shared dependency.
  • ZooKeeper offers a tree of znodes (persistent, ephemeral, sequential) with one-shot watches; etcd offers a flat key space with global revisions, leases, streaming watches and transactions; Consul adds gossip, health checks and service discovery.
  • Sessions and leases expire based on silence, which cannot distinguish a crash from a pause or partition. A client must stop protected work when it loses contact; no timeout is perfectly safe.
  • A distributed lock is either for efficiency (approximate is fine) or for correctness (needs a fencing token checked by the resource). Redis SET NX PX with a random token and a Lua release is good for efficiency; Redlock's safety for correctness is contested because of timing assumptions and no token.
  • ZooKeeper locks use ephemeral sequential nodes with predecessor watches to avoid the herd effect and give FIFO fairness; etcd uses lease-attached keys ordered by revision, which also provide fencing tokens.
  • Pitfalls: pauses, clock drift, lease expiry mid-work, lost or foreign unlock, reentrancy, deadlock, and too-fine granularity.
  • Prefer to avoid locks: idempotency, conditional writes, unique constraints, row locks, single-consumer queues, partitioning. Layer them: a lock for efficiency, a constraint or token for correctness.
  • Leader election is a long-held lock with lease renewal, self step-down before expiry, and an epoch on all writes. Config and membership use the same primitives; control the watch fan-out with local agents.
