Relational Databases In Depth

Most systems you will design keep their most important data in a relational database. This chapter opens the box: how a query actually runs, how indexes make it fast or useless, how transactions stay correct when many clients collide, and how far one database can scale before you must split it.

1. When to choose a relational database

A relational database stores data in tables made of rows and typed columns, links tables through keys, and is queried with SQL. Well-known examples are PostgreSQL, MySQL (with the InnoDB storage engine), MariaDB, Oracle, and SQL Server. They have been the default for decades for good reasons, and in an interview your default answer for "where does the core data live?" should be a relational database unless you can name a concrete reason against it.

What you get from one:

  • Transactions with strong guarantees. You can change several rows in several tables as one all-or-nothing unit (section 6). This is the single biggest reason: money, inventory, bookings, and permissions all need it.
  • A declarative query language. You describe what you want (orders for this customer in the last week, with their items) and the database figures out how to fetch it. New questions can be answered later without redesigning storage, which matters because product requirements change.
  • Constraints that protect data. Primary keys, unique constraints, foreign keys, NOT NULL, and CHECK rules make the database refuse invalid data no matter which application bug tries to write it.
  • Joins and ad-hoc analysis. Normalized data (Chapter 17) can be recombined in any way with joins.
  • Mature tooling. Backups, point-in-time recovery, replication, monitoring, and a large pool of engineers who know it.

Their limits are equally important to know. A single relational primary (the one node that accepts writes) is bounded by one machine's CPU, memory, disk, and network. Writes do not scale out by simply adding servers; reads can, through replicas (Chapter 24); writes need sharding (Chapter 25), which gives up some of the relational conveniences. Schema changes on huge tables need care. And the model is a poor fit for a few shapes of data.

Then name the specific pressure that would make you leave it: write volume beyond one primary, a data shape such as time-series or graph, or a latency target that only an in-memory store meets. "I would use NoSQL because it scales" without a number is a weak answer; most products never outgrow one well-tuned primary with replicas (section 12 has numbers).

2. How a query executes

When you send SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10, the text passes through a fixed pipeline. Knowing the stages explains most performance behaviour you will be asked about.

2.1 Parser

The parser checks that the text is valid SQL and turns it into a tree. It then resolves names: does table orders exist, does it have a column customer_id, are you allowed to read it. Errors such as a typo in a column name are reported here, before any data is touched.

2.2 Planner (optimizer)

SQL does not say how to get the data. The planner generates several candidate strategies and estimates a cost for each, using statistics the database collects about each table: row count, the number of distinct values per column, the most common values, and a histogram of value distribution. For our query it could scan the whole table and filter, or use an index on customer_id, or use an index on (customer_id, created_at) that also returns rows already in sorted order. It also chooses join order and join algorithm when several tables are involved (section 5.2). The plan with the lowest estimated cost wins.

The key phrase is estimated. If statistics are stale (a big load just happened and the table was not re-analyzed), the planner can believe a filter returns 10 rows when it returns 10 million and pick a catastrophic plan. Keeping statistics fresh (ANALYZE in Postgres, automatic in most setups) is basic hygiene.

Many databases also cache plans for prepared statements: you send the query shape once with placeholders and then run it many times with different values, saving parse and plan time and preventing SQL injection because values never mix with the query text.

2.3 Executor

The executor runs the chosen plan as a tree of small operators (scan, filter, sort, join, aggregate). Each operator asks its children for rows, typically one row at a time in a "pull" style, so a LIMIT 10 can stop the whole tree early once ten rows have been produced. Operators that must see all input before emitting anything, such as a full sort or a hash build, hold memory; if they exceed their memory budget they spill temporary data to disk, which is a common cause of sudden slowness.

2.4 Pages and the buffer pool

Databases do not read individual rows from disk. Storage is divided into fixed-size blocks called pages (8 KB in PostgreSQL, 16 KB in InnoDB by default). A page holds many rows (or many index entries). The smallest unit that is read or written is a whole page. A row fetch therefore costs one page read, and reading 100 rows that sit on the same page costs one read, not 100.

The buffer pool (also called shared buffers or the page cache) is a region of RAM holding recently used pages. When the executor needs a page, it looks in the buffer pool first. A hit costs about a microsecond; a miss means a disk read: roughly 100 microseconds on SSD, around 10 ms on a spinning disk. Pages modified in memory are called dirty; a background process writes them to disk later (section 7 explains why that is safe). The practical rules that follow:

  • If your working set (the hot data and indexes) fits in RAM, almost every read is a hit and the database is fast. When it no longer fits, the hit ratio falls and latency jumps. A cache hit ratio below roughly 99% on an OLTP database deserves attention.
  • Index pages compete with data pages for the same memory, so unneeded indexes also hurt cache efficiency.
  • A single large scan can push hot pages out of the pool. Databases use tricks (ring buffers for big scans) to limit this, but a rogue report query on the primary can still hurt everyone.

3. Indexes and the B-tree

An index is a separate, sorted data structure that lets the database find rows by some column values without reading the whole table. The analogy is the index at the back of a textbook: instead of reading every page looking for "deadlock", you look up the word in a sorted list and jump to the page numbers.

Without an index, finding the orders of customer 42 means a sequential scan: read every page of the table and test every row. With 100 million rows that is gigabytes of reading. With an index it is typically 3 to 4 page reads. That difference, milliseconds versus minutes, is why indexing is the first tool for query performance.

3.1 How a B-tree works

Nearly every relational index is a B-tree (strictly a B+tree). It is a balanced tree whose nodes are pages. Each internal page holds sorted keys and pointers to child pages; each key range tells you which child to descend into. The bottom level, the leaf pages, holds all the keys in sorted order together with a pointer to the actual row (or the row itself, see clustered indexes below). Leaf pages are chained left to right in a linked list, so scanning a range is just walking along the leaves.

Why does this work so well? A page is 8 to 16 KB, and an index entry for an integer key is a few dozen bytes, so one page holds hundreds of entries. This is the fanout. With a fanout of 300, one level covers 300 keys, two levels 90,000, three levels 27 million, and four levels 8 billion. So finding any row among billions costs about 4 page reads, and the root and upper levels are so hot that they live permanently in the buffer pool, so in practice only the leaf and the table page require disk I/O. The tree stays balanced because when a leaf page fills up it is split in two and a new separator key is pushed to the parent, possibly splitting that too, up to the root. Lookups, inserts, and deletes are all logarithmic.

A B-tree supports: exact match (id = 5), range (created_at BETWEEN a AND b), prefix match (name LIKE 'Smi%'), and returning rows in sorted order for ORDER BY without a separate sort. It does not help with a suffix or middle match such as LIKE '%son', because the sorted order is by the beginning of the string.

3.2 Clustered versus secondary indexes

Where do the row's other columns live? Two designs exist, and the difference is a classic interview topic.

  • Clustered index (InnoDB, SQL Server). The table itself is stored as a B-tree ordered by the primary key; the leaf pages are the rows. Looking up by primary key is one tree walk with the full row at the end. Rows with nearby primary keys sit physically near each other, so range scans on the key are efficient. Secondary indexes in InnoDB store the indexed columns plus the primary key value; to get the full row the database performs a second lookup in the clustered index (a "bookmark lookup"). Consequence: a wide or random primary key (such as a random UUID) is copied into every secondary index, bloating them, and random inserts split pages all over the tree. Sequential or time-ordered keys insert at the right edge and are far kinder.
  • Heap table plus indexes (PostgreSQL). The table is an unordered heap of pages. Every index, including the primary key index, is a separate B-tree whose leaf entries point to a physical row location (a tuple identifier, page number plus slot). A lookup is: walk the index, then fetch the heap page. PostgreSQL can optionally cluster a table once with the CLUSTER command, but the ordering is not maintained afterwards.

4. Designing indexes

4.1 Composite indexes, column order and the leftmost prefix

A composite (multi-column) index sorts entries by the first column, then by the second within equal first values, and so on, exactly like a phone book sorted by last name then first name. This ordering gives the leftmost prefix rule: an index on (a, b, c) can efficiently serve conditions on a; on a and b; on a, b and c. It cannot efficiently serve a condition on b alone or c alone, because entries with the same b are scattered throughout the index, just as you cannot find everyone named "John" in a phone book sorted by last name without reading it all.

The rule for choosing column order:

  1. Put columns used with equality (=) first.
  2. Then put the column used for a range or for sorting (>, BETWEEN, ORDER BY) last. Columns after a range column cannot narrow the scan, because the range already spans many distinct values of the earlier column.
  3. Among equality columns, prefer an order that lets one index serve several queries (the leftmost prefix reuse).

Example. For "this customer's orders, newest first" (WHERE customer_id = ? ORDER BY created_at DESC LIMIT 10), the index (customer_id, created_at) is perfect: the database descends to customer 42, then reads the ten newest entries straight off the end of that customer's section, no sort, no extra rows read. An index on (created_at, customer_id) would be nearly useless for this query. The same (customer_id, created_at) index also serves plain WHERE customer_id = ?, so a separate index on customer_id alone is redundant and only adds write cost.

4.2 Covering indexes

If an index contains every column the query needs, the database can answer from the index alone and never touch the table. This is a covering index, shown in plans as an "index-only scan" (Postgres) or "Using index" (MySQL). It avoids the random heap or clustered lookup per row, which is often the dominant cost when a query returns many rows. PostgreSQL and SQL Server allow adding non-key columns with INCLUDE (col): they are stored in the leaf entries for covering but are not part of the sort order. The tradeoff is a bigger index and more write work, so cover only your hottest queries. (PostgreSQL index-only scans also depend on the visibility map, which vacuum maintains; see section 9.)

4.3 Partial and expression indexes

  • Partial index (PostgreSQL, SQLite; filtered index in SQL Server): indexes only rows matching a condition, e.g. CREATE INDEX ON orders (created_at) WHERE status = 'PENDING'. If only 1% of orders are pending, the index is 100 times smaller, cheaper to maintain, and fits in cache. A partial unique index also expresses rules such as "a user can have at most one active subscription".
  • Expression (functional) index: indexes the result of a function, e.g. CREATE INDEX ON users (lower(email)). The query must use the same expression (WHERE lower(email) = ?) for the planner to use it. Without it, wrapping a column in a function defeats a normal index (section 4.6).

4.5 What indexes cost, and selectivity

Indexes are not free. Every insert must add an entry to every index on the table; every delete or update of an indexed column must change them; each index consumes disk and competes for buffer-pool memory. A table with eight indexes does roughly nine times the write work of an unindexed one (the heap plus eight trees), and write amplification translates directly into lower write throughput, longer replication lag, and bigger backups. The discipline is: index for the queries you actually run, drop unused indexes (databases expose usage statistics), and avoid redundant prefixes.

Selectivity is the fraction of rows a condition matches: low fraction means high selectivity (good for indexing). A lookup by email returns one row in millions: highly selective, an index is a huge win. An index on a boolean is_active where 95% of rows are true is nearly worthless on its own, because reading 95% of the table through an index (a random page fetch per row) is slower than just scanning the table sequentially. The planner knows this and will skip the index. The common trick is to index the rare value with a partial index (WHERE is_active = false), or combine the low-selectivity column as the first column of a composite index with a selective one.

4.6 When an index is not used

If a query is slow despite an index, the usual culprits are:

  • A function or arithmetic on the column. WHERE date(created_at) = '2025-01-01' or WHERE price * 2 > 100 hides the raw column from the index. Rewrite as a range (created_at >= '2025-01-01' AND created_at < '2025-01-02') or add an expression index.
  • Type mismatch or implicit casts. Comparing a string column to a number, or columns with different collations or character sets across a join, can force conversion of every row.
  • Leading wildcard. LIKE '%abc' cannot use a B-tree. Use a trigram or full-text index, or a search engine.
  • Leftmost prefix violated. The query filters on the second column of a composite index only.
  • Low selectivity. The planner correctly decides a scan is cheaper.
  • Stale statistics. The planner misjudges row counts and picks a scan or a bad join.
  • OR across different columns and NOT / != conditions are often unindexable or need a combination (bitmap) plan.
  • Large OFFSET. OFFSET 100000 LIMIT 10 still reads and discards 100,000 entries. Use keyset pagination: WHERE (created_at, id) < (last_seen_created_at, last_seen_id) ORDER BY created_at DESC, id DESC LIMIT 10.

5. Reading query plans

You ask the database for its chosen plan with EXPLAIN, and for the plan together with real timings and actual row counts with EXPLAIN ANALYZE (PostgreSQL; MySQL has EXPLAIN and EXPLAIN ANALYZE too). Note that EXPLAIN ANALYZE actually runs the statement, so wrap data-changing statements in a transaction you roll back. A simplified Postgres output:

EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10;

Limit  (cost=0.57..8.30 rows=10 width=64) (actual time=0.04..0.06 rows=10 loops=1)
  -> Index Scan Backward using idx_orders_cust_created on orders
       (cost=0.57..412.1 rows=533 width=64) (actual time=0.04..0.05 rows=10 loops=1)
       Index Cond: (customer_id = 42)
Planning Time: 0.2 ms   Execution Time: 0.1 ms

Read it from the innermost, most indented node outward. The pieces to look at: the node type (how rows are fetched), the estimated rows versus actual rows (a large mismatch means bad statistics and probably a bad plan), the actual time, and the loops count (a node inside a nested loop runs many times, so multiply). Also watch for "Rows Removed by Filter" being huge (you read many rows to keep few) and for sorts that report "external merge Disk" (spilled to disk).

5.1 Scan types

  • Sequential scan: read the whole table. Fine for small tables or when a large fraction of rows is needed; a red flag on a big table with a selective filter.
  • Index scan: walk the index and fetch each matching row from the table. Good for few rows; random I/O if many.
  • Index-only scan: answered entirely from a covering index.
  • Bitmap scan (Postgres): collect the matching row locations from one or more indexes into a bitmap, sort them by physical page, then read pages in order. A middle ground when too many rows for an index scan but too few for a full scan, and the way two separate indexes are combined for an AND or OR.

5.2 Join algorithms

A join combines rows from two inputs. The planner picks among three algorithms, and which one is right depends on input sizes and available indexes.

  • Nested loop join. For each row of the outer input, look up matching rows in the inner input. If the inner side has an index on the join column, each lookup is a cheap tree walk, so the cost is about outer rows × log(inner). Excellent when the outer side is small (a few rows) and the inner is indexed; terrible if both are large and there is no index (cost outer × inner).
  • Hash join. Build an in-memory hash table from the smaller input keyed on the join column, then scan the larger input once, probing the hash table for each row. Cost is roughly the sum of the two sizes. Excellent for large unsorted inputs with equality joins; needs memory (spills to disk in batches if the hash table is too big); only works for equality.
  • Merge join. Sort both inputs on the join key (or read them already sorted from indexes) and walk through them together like merging two sorted lists. Cost is linear after sorting. Good when both inputs are large and already ordered, and it handles range-style join conditions.

5.3 The N+1 query problem

The most common real-world slowdown is not in the database engine at all but in application code. N+1 happens when code runs one query to fetch a list of N items, then one more query per item to fetch related data. Example: load 50 orders (1 query), then loop and load each order's customer (50 queries) and each order's items (50 more). Each query is individually fast, maybe 1 ms, but the total is 100+ round trips, each paying network latency, and under load this multiplies into connection exhaustion.

The fixes: fetch with a join (one query returning orders with customers), or use a batched lookup (WHERE id IN (...) with all the ids gathered first, giving 2 queries total instead of 51). ORMs name these "eager loading" or "prefetch"; GraphQL servers use a batching layer (often called a data loader). If you see an interview design where a list endpoint calls the database inside a loop, call it out.

5.4 Common causes of slow queries

  1. Missing or unusable index (section 4.6); the plan shows a sequential scan on a big table.
  2. Too much data returned: SELECT * on wide rows, no LIMIT, giant OFFSET.
  3. Bad plan from stale statistics or skewed data (estimated rows far from actual).
  4. Sorts or hashes spilling to disk because per-operation memory is too small.
  5. N+1 patterns and chatty application code.
  6. Lock waits: the query is not slow, it is blocked behind another transaction (section 10).
  7. Long transactions and bloat (section 9) making scans read dead rows.
  8. Working set no longer fits in memory; cache hit ratio drops.
  9. Overloaded connections: too many concurrent queries thrashing CPU (section 11).

The practical workflow: find the slow queries from the slow query log or statistics view (pg_stat_statements in Postgres), run EXPLAIN ANALYZE on the worst, fix the index or query, and verify in the plan.

6. ACID explained with real failures

A transaction is a group of reads and writes that the database treats as one logical unit, bracketed by BEGIN and COMMIT (or ROLLBACK to abandon it). The guarantees are summarized by the acronym ACID. Each letter is easiest to understand by the failure it prevents.

6.1 Atomicity: all or nothing

Transferring 100 dollars means two writes: subtract from account A, add to account B. If the server crashes after the first write, without atomicity the money has vanished. With atomicity the database guarantees that either both writes take effect or neither does; after a crash, the half-finished transaction is undone. It also covers application errors: if the second statement fails a constraint, ROLLBACK erases the first. Note this is different from the "atomic" of concurrency (nothing else sees a half-done state), which is isolation.

6.2 Consistency: invariants hold

Here "consistency" means that a transaction moves the database from one valid state to another valid state, where valid is defined by your constraints: balance cannot go negative, every order references an existing customer, emails are unique. The database enforces the rules it knows about (unique, foreign key, CHECK, NOT NULL) and refuses a transaction that would break them. Rules the database does not know about, such as "total of all accounts is constant", are the application's responsibility, which is why ACID's C is partly a promise by you. (This is unrelated to the "C" in CAP, which is about replicas agreeing; see Chapter 28.)

6.3 Isolation: concurrent transactions do not trip over each other

Two customers buy the last ticket at the same instant. If both transactions read "1 left" and both write "0 left", you sold one ticket twice. Isolation controls how much concurrent transactions can see of each other's work. Perfect isolation (serializable) makes the outcome identical to running the transactions one after another, but costs performance, so databases offer weaker levels with known anomalies (section 8).

6.4 Durability: committed means it survives

Once COMMIT returns success, the data must survive a crash or power loss. The example failure: the database says "committed", the customer is shown a confirmation, then the machine loses power and, on restart, the order is gone. Durability is implemented by flushing a log record to non-volatile storage before acknowledging the commit (next section). It does not protect against losing the disk itself; that needs replication and backups.

Watch out Durability is configurable. PostgreSQL's synchronous_commit = off and InnoDB's innodb_flush_log_at_trx_commit = 2 acknowledge commits before the log is flushed, which is faster but can lose the last fraction of a second of commits on a crash (the database stays consistent, just slightly behind). Know that this knob exists and that the default is the safe setting.

7. Write-ahead log and crash recovery

Here is the engineering puzzle. Data pages live in the buffer pool and are modified in memory. Writing every changed page to disk at commit would be slow, because a single transaction may touch pages scattered across the disk (random writes), and a page is 8 to 16 KB even if only 50 bytes changed. But if we only keep changes in memory, a crash loses them. The solution is the write-ahead log (WAL), called the redo log in InnoDB.

The rule is: before a modified data page may be written to disk, and before a commit is acknowledged, the log record describing the change must be safely on disk. The log is an append-only file. Appending to the end of a file is a sequential write, the fastest thing a disk does, and one flush can cover the log records of many transactions at once (group commit). The big scattered data pages are written later, lazily, by a background writer and at periodic checkpoints.

7.1 Crash recovery

Suppose the server loses power. On restart the database reads the log from the last checkpoint (a point at which all earlier changes were known to be on disk) and replays it, re-applying changes whose data pages never reached disk (redo). Transactions that were in flight and never committed have their changes rolled back (undo, using stored old values in InnoDB's undo log, or by simply treating their row versions as invisible in Postgres). The classic algorithm that defines this is called ARIES. The result is a state that contains every committed transaction and no uncommitted ones. Recovery time is bounded by how much log accumulated since the last checkpoint, which is why checkpoint frequency trades steady-state write cost against restart time.

7.2 What else the log is used for

  • Replication. Physical replicas in PostgreSQL stream and replay the WAL; MySQL replicates a separate logical binary log (binlog). Lag is the time a replica takes to apply what the primary logged. See Chapter 24.
  • Point-in-time recovery. Keep a base backup plus all WAL since, then replay up to just before the accidental DROP TABLE. This is how you recover from human error, which replication cannot (a replica faithfully replays the mistake).
  • Change data capture. Tools read the log to stream row changes into Kafka and search indexes.

The same append-first idea underlies log-structured storage engines and is covered from the storage side in Chapter 19. A subtle durability point: the log flush must really reach the device. fsync asks the operating system to push data to stable storage; disks and SSDs with volatile write caches can lie, which is why servers use battery or capacitor-backed caches.

8. Transactions and isolation levels

When transactions run at the same time, their reads and writes interleave. Without protection, interleaving produces results no serial order could produce. The SQL standard defines isolation levels in terms of which of these anomalies they permit. Learn the anomalies first.

8.1 The anomalies

  • Dirty read. Transaction T1 reads a value that T2 has written but not yet committed. If T2 then rolls back, T1 acted on data that never existed.
  • Non-repeatable read. T1 reads a row, T2 commits a change to that row, T1 reads the same row again and gets a different value within the same transaction.
  • Phantom read. T1 runs a query for a set of rows (all bookings in a time window), T2 commits a new row matching that condition, T1 runs the same query again and sees an extra row. The row itself is new, so locking existing rows could not have prevented it.
  • Lost update. Two transactions read the same value, each computes a new value from it, and each writes; the second write silently overwrites the first. Example: both read stock = 10, both subtract 1, both write 9; one sale vanished.
  • Write skew. Two transactions read an overlapping set of rows, then each writes a different row, and together they violate an invariant that each alone preserved. Example: a hospital requires at least one doctor on call. Two doctors, Alice and Bob, both on call, each check "are there at least 2 on call?" (yes), and each removes themselves. Both commit; nobody is on call. Neither wrote the row the other wrote, so row-level conflict detection never fires.

  • Read uncommitted: you may see uncommitted data. Rarely used; PostgreSQL silently treats it as read committed.
  • Read committed: every statement sees only data committed before that statement began. The default in PostgreSQL, Oracle, and SQL Server. Two statements in one transaction can see different data. Good enough for many applications, but a read-then-write pattern is unsafe.
  • Repeatable read: the standard says a row you read stays the same. Implementations differ: PostgreSQL's repeatable read is really snapshot isolation: at the transaction's first statement it takes a consistent snapshot of the database, and every read sees that snapshot, so even phantoms cannot appear. If you try to update a row that someone else committed a change to after your snapshot, Postgres aborts you with a serialization failure and you must retry. MySQL InnoDB's default is repeatable read: plain reads use a snapshot, but locking reads and writes see the latest committed data and use gap locks to block phantoms (section 10).
  • Snapshot isolation as a named level (SQL Server has it; Oracle's "serializable" is really this): each transaction works from a point-in-time snapshot and conflicts are detected only when two transactions write the same row. It stops most anomalies and allows reads that never block writes, but still permits write skew.
  • Serializable: outcomes equal some serial order. Implemented either by heavy locking (MySQL InnoDB turns plain reads into shared-lock reads; SQL Server) or, in PostgreSQL, by Serializable Snapshot Isolation (SSI), which runs on snapshots but tracks read-write dependencies between transactions and aborts one when it detects a dangerous cycle. In both cases, the application must be prepared to retry aborted transactions.

8.3 Two anomalies as sequences

Key idea Isolation level is a dial between safety and concurrency. The default level of your database is usually weaker than people assume. Rather than raising the level globally, identify the specific read-then-write patterns that matter (counters, balances, uniqueness, "at least one" rules) and protect those with atomic updates, explicit row locks, or constraints. Use serializable for the few transactions where reasoning about interleavings is too hard, and always code retries.

9. MVCC, vacuum and bloat

How can a database give one transaction a consistent snapshot while another is writing, without making readers wait for writers? The answer in PostgreSQL, MySQL InnoDB, Oracle, and others is MVCC, multi-version concurrency control. Instead of overwriting a row in place, an update creates a new version of the row and keeps the old version around for as long as some running transaction might still need it. Each version is stamped with the transaction ids that created and (if superseded) removed it. A reader compares those stamps to its snapshot and sees only the version that was current when its snapshot was taken. The result: readers do not block writers, and writers do not block readers. Only writers to the same row block each other.

9.2 Vacuum and bloat

In PostgreSQL an UPDATE is internally an insert of a new version plus a mark on the old one, and a DELETE only marks a row dead. Dead versions occupy space until VACUUM reclaims it for reuse. Autovacuum runs in the background, triggered by the number of dead rows. It also freezes very old transaction ids; without that, the 32-bit transaction counter would eventually wrap around and make old rows appear to be in the future, so Postgres will force aggressive vacuum or even stop accepting writes to prevent data loss. That is the famous "transaction id wraparound" emergency.

Bloat is the accumulation of dead space: tables and indexes much larger than their live data, meaning more pages to read and a lower cache hit ratio. Causes and cures:

  • Long-running transactions (an idle-in-transaction session, a forgotten report) hold back the oldest snapshot, so vacuum cannot remove any version newer than it. This is the number one cause. Set idle_in_transaction_session_timeout and alert on old transactions.
  • Heavy update/delete workloads outrun default autovacuum settings. Tune thresholds per table, use HOT-friendly designs (do not index frequently updated columns needlessly, leave free space with a lower fillfactor).
  • Plain VACUUM makes space reusable but rarely shrinks files; a badly bloated table needs a rewrite (VACUUM FULL takes an exclusive lock, so teams use online tools such as pg_repack) or a rebuilt index.
  • Queue-like tables with constant insert and delete bloat quickly; consider partitioning and dropping old partitions instead of deleting rows (section 12).

10. Locking, deadlocks and concurrency control

MVCC lets readers proceed freely, but writers still need to coordinate. Databases use locks for that, at several granularities.

10.1 Lock types

  • Row locks. Taken automatically by UPDATE and DELETE on the rows they change, and explicitly by SELECT ... FOR UPDATE. A second transaction trying to modify the same row waits until the first commits or rolls back. Different rows never conflict, which is why row-level locking scales.
  • Table locks. Coarser. Many DDL statements (ALTER TABLE, DROP, TRUNCATE, some index builds) take a strong lock that blocks reads and writes. A dangerous pattern: an ALTER TABLE waits behind one long-running transaction, and then every new query queues behind the waiting ALTER, so the whole table appears frozen. Set a lock_timeout for schema changes, and prefer online techniques such as CREATE INDEX CONCURRENTLY (Chapter 26).
  • Gap and next-key locks (InnoDB). To prevent phantoms at repeatable read, InnoDB locks not just matching index records but also the gaps between them, so that nobody can insert a new row into the range you scanned. A locking query such as SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE blocks inserts of ids 11 to 19 even though those rows do not exist. This prevents anomalies but surprises people with unexpected lock waits and deadlocks on inserts. Using read committed in MySQL disables most gap locking.
  • Shared versus exclusive. Shared locks (FOR SHARE) let many readers hold them but block writers; exclusive locks block everything else on that row. Foreign key checks take light shared-style locks on the referenced row.

10.2 Deadlocks

A deadlock occurs when two transactions each hold a lock the other needs, so neither can ever proceed. The database detects such cycles (by examining the wait-for graph after a short delay) and kills one transaction, which receives an error that your code must handle by retrying.

How to avoid deadlocks, in order of effectiveness:

  1. Acquire locks in a consistent global order. If every transfer locks the lower account id first, a cycle cannot form. Use SELECT ... WHERE id IN (1, 2) ORDER BY id FOR UPDATE.
  2. Keep transactions short. Do no network calls, user waits, or slow computation while holding locks. Open the transaction late and commit early.
  3. Touch fewer rows and use indexes so locking queries do not lock (or gap-lock) many extra rows.
  4. Use atomic single statements (UPDATE ... SET x = x - 1) in place of read-modify-write.
  5. Retry on deadlock with a small randomized backoff. Even careful designs deadlock occasionally; treat it as an expected, retryable error rather than a bug.

10.3 Pessimistic versus optimistic concurrency

Pessimistic control assumes conflicts are likely and prevents them by locking before touching data. SELECT ... FOR UPDATE reads the rows and takes an exclusive lock on them so that no one else can change them until you commit. Variants: NOWAIT fails immediately if the row is locked, and SKIP LOCKED skips locked rows, which is the standard trick to build a job queue where many workers pull different tasks without waiting for each other (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 10).

Optimistic control assumes conflicts are rare, does not lock while thinking, and checks at write time that nothing changed. The usual implementation is a version column:

SELECT id, stock, version FROM items WHERE id = 7;      -- version = 12
UPDATE items SET stock = 9, version = 13
 WHERE id = 7 AND version = 12;                          -- affected rows = 0 means someone else won

If zero rows were updated, someone changed the row since you read it, so you re-read and retry (or tell the user). This works across long gaps, such as a user editing a form for several minutes, where holding a database lock would be unacceptable. HTTP ETags and compare-and-set in key-value stores follow the same idea.

10.4 Unique constraints and upserts

The only reliable way to guarantee uniqueness (one account per email, one vote per user per poll, one idempotency key per request) is a unique constraint or index enforced by the database. An application check ("SELECT, and if none then INSERT") has a race: two requests both see none and both insert. With the constraint, the second insert fails with a duplicate-key error, which your code treats as "already exists".

An upsert performs "insert, or update if it exists" atomically: INSERT ... ON CONFLICT (key) DO UPDATE ... in PostgreSQL, INSERT ... ON DUPLICATE KEY UPDATE in MySQL, MERGE in standard SQL and others. Use ON CONFLICT DO NOTHING for idempotent inserts, which pairs naturally with retries and at-least-once message processing (Chapter 32). A subtle cost: in Postgres every attempted insert that conflicts still consumes a sequence value, so ids can have gaps; never rely on gap-free ids.

11. Connection pooling

Each database connection is expensive. In PostgreSQL every connection is a separate operating-system process using several megabytes of memory, with its own backend state; MySQL uses a thread per connection. Opening one also costs a TCP and TLS handshake plus authentication, tens of milliseconds. And a database can only make use of a limited number of concurrent queries: beyond roughly a small multiple of the CPU core count, extra active connections just contend for CPU and locks and reduce total throughput. A common guideline for the useful number of concurrently active queries is a few times the core count, so a 16-core server is best served by dozens of active connections, not thousands.

The problem appears when you have hundreds of application instances (or serverless functions), each with a pool of 20 connections: 200 instances times 20 is 4,000 connections, far beyond what the database handles well. A connection pooler sits between applications and the database, accepting many client connections and multiplexing them over a small set of real server connections. PgBouncer is the standard for PostgreSQL; ProxySQL and the cloud proxies (RDS Proxy, Cloud SQL's pooling) play this role for MySQL and managed services.

PgBouncer has three modes:

  • Session pooling: a server connection is held for the client's whole session. Safe but gives little multiplexing.
  • Transaction pooling: a server connection is assigned only while a transaction runs, then returned. This gives the large multiplexing win and is the usual choice, but breaks features that rely on session state: session-level prepared statements (in older versions), SET variables, advisory locks held across transactions, LISTEN/NOTIFY, and temporary tables. Code must not depend on them.
  • Statement pooling: returns the connection after every statement; multi-statement transactions are not allowed. Rare.

Operational notes: size the pool from the database's capacity, not from client count; add a client-side pool limit and a timeout so that when the pool is exhausted requests fail fast instead of piling up; keep pooler instances redundant (it is a new component that can fail, so run several behind a load balancer); and remember that a pooler does not fix slow queries, only connection storms. A related failure is a thundering herd after a restart, when every app instance reconnects at once; connection limits and jittered retry help.

12. Scaling a relational database

Scale in this order, cheapest and least risky first. Many systems stop at step three.

12.1 Vertical scaling and its limits

Buy a bigger machine: more cores, more RAM, faster NVMe storage. It is the simplest move and goes surprisingly far. Rough, order-of-magnitude numbers for a well-tuned single node with SSD storage and a mostly in-memory working set: tens of thousands of simple indexed reads per second per node, and on the order of several thousand to low tens of thousands of write transactions per second, falling sharply for large rows, many indexes, or synchronous replication. Commodity cloud instances reach hundreds of cores and terabytes of RAM, and managed databases support multi-terabyte storage, though operations (backup restore time, vacuum, schema change, failover) get painful beyond a few terabytes. Treat these as rough guides; real workloads vary by a factor of ten either way, and your answer in an interview should be "measure it", with a ballpark.

12.2 Read replicas

Most applications read far more than they write. Add replicas that replay the primary's log and send read-only queries to them (Chapter 24). Caveats: replication is usually asynchronous, so a replica lags by milliseconds, occasionally seconds; a user who just wrote data may not see it on a replica (read-your-writes), so route a user's reads to the primary briefly after a write, or read from the primary for critical paths. Replicas do not scale writes, and each replica must apply every write, so write-heavy workloads gain little. Replicas also give availability: promote one when the primary dies.

12.3 Partitioning

Partitioning splits one logical table into smaller physical pieces within the same database server, by a key: range (by month), list (by region), or hash (by user id modulo N). Queries that filter on the partition key touch only the relevant partitions (partition pruning), and each partition has smaller indexes that fit in memory better. The most valuable property for time-series-like data is cheap retention: dropping a month-old partition is an instant metadata operation, whereas deleting hundreds of millions of rows would generate huge logs and bloat. Costs: the partition key must be part of unique keys, queries without the key hit every partition, and too many partitions slow planning. Partitioning is not sharding; it does not add machines (the distinction and the cross-machine version are in Chapter 25).

12.4 Sharding

When one primary cannot take the write volume or data size, split the data across several independent database servers by a shard key, with the application or a routing layer sending each query to the right shard. This scales writes and storage almost linearly, but you lose or must rework: cross-shard joins, cross-shard transactions (needing two-phase commit or sagas), global unique constraints, and simple secondary indexes; and resharding is operationally heavy. A well-chosen key (such as tenant id) keeps most queries and transactions inside one shard. Details, hot shards, and rebalancing are the subject of Chapter 25.

13. NewSQL: distributed SQL databases

NewSQL systems try to keep SQL and ACID transactions while scaling out horizontally, so you get sharding without writing the shard logic yourself. Representative products are Google Spanner, CockroachDB, YugabyteDB, TiDB, and Amazon Aurora DSQL.

The common design: data is automatically split into small ranges (tablets, ranges, regions). Each range is replicated across machines (typically three or five) using a consensus protocol such as Raft or Paxos (Chapter 29), with one replica as the range's leader accepting writes. A transaction touching several ranges commits using a distributed protocol (a form of two-phase commit across the leaders involved, itself made fault tolerant by consensus). Ranges split and move automatically as data grows or load shifts.

  • Spanner additionally uses synchronized atomic-clock-based time (TrueTime) to give externally consistent, serializable transactions across continents; a write waits out a small clock-uncertainty window before commit becomes visible.
  • CockroachDB offers serializable isolation by default, Postgres-compatible SQL, and survives the loss of a node, zone, or region depending on configuration; it uses hybrid logical clocks (Chapter 27) instead of special hardware.

The tradeoffs matter in interviews. Every committed write needs a consensus round to a majority of replicas, so write latency is at least one round trip to the nearest majority: a few milliseconds within a region, tens to hundreds of milliseconds across regions. Cross-range transactions are slower than single-node ones. The systems are more complex to operate, and not every single-node feature or extension is available. Choose NewSQL when you need relational semantics with horizontal write scaling, built-in automatic failover, or multi-region consistency, and you can accept higher per-transaction latency. A single-node Postgres is faster and simpler for everything that fits on one machine.

15. Worked example: decrementing inventory under concurrency

Scenario. A flash sale offers 1,000 units of a product. Table items(id, stock, version). At peak, 2,000 requests per second try to buy the same product. Each purchase must decrement the stock exactly once and must never oversell. Let us walk through four implementations, from wrong to right, with numbers.

15.1 Attempt 1: read, then write (broken)

BEGIN;
SELECT stock FROM items WHERE id = 7;      -- app checks stock > 0
UPDATE items SET stock = :stock - 1 WHERE id = 7;
COMMIT;

At read committed, many transactions read the same stock (say 500) before any of them writes. Each writes 499. After 100 purchases the stock has dropped by maybe 1 or 2. This is the lost update from section 8. Oversold by roughly the concurrency level. Never do this.

15.2 Attempt 2: atomic conditional update (usually the right answer)

UPDATE items SET stock = stock - 1
 WHERE id = 7 AND stock > 0;
-- check affected rows: 1 = success, 0 = sold out

A single statement reads and writes under the row lock, so concurrent statements on the same row run one after another and each sees the previous result. The stock > 0 condition makes overselling impossible; you can add a CHECK (stock >= 0) constraint as a second safety net. Cost: all 2,000 requests per second queue on one row lock. If each update holds the lock for about 0.5 ms (a log flush shared via group commit may stretch the row's lock hold to about a millisecond because the lock is released only at commit), the single row can sustain very roughly 1,000 to 2,000 updates per second. Latency for a request at the back of a queue is the queue length times the hold time; with 100 waiting that is about 100 ms. So one hot row is bounded by serialized lock hold time, not by CPU, and that is the real ceiling.

15.3 Attempt 3: pessimistic lock, when business logic is needed

BEGIN;
SELECT stock FROM items WHERE id = 7 FOR UPDATE;   -- lock the row
-- apply rules: per-customer limit, price checks, insert order, insert reservation
UPDATE items SET stock = stock - 1 WHERE id = 7;
INSERT INTO orders (...) VALUES (...);
COMMIT;

Use this when the decision involves several tables or rules that cannot be written as one conditional update. The lock is held for the whole transaction, so keep it short (no payment call inside!). Throughput on the hot row is now bounded by the entire transaction time, say 3 ms, giving only about 300 purchases per second per item. Better to reserve stock quickly and take payment afterwards (a reservation with expiry), as in the booking case studies.

15.4 Attempt 4: optimistic version check

Read stock and version, then UPDATE ... WHERE id = 7 AND version = :v. Under low contention this works, but with 2,000 concurrent buyers on one row almost every attempt fails the version check and retries, creating a retry storm that burns CPU and connections for the same final throughput. Optimistic control is the wrong tool for a hot row; it is right for the edit-a-profile case.

15.5 Going beyond one hot row

  • Split the counter. Store the 1,000 units across 10 rows (100 each). A buyer picks a random row and decrements it with the conditional update; if that one is empty, try another. Row-lock contention falls tenfold, and the ceiling rises to roughly 10,000 per second, at the cost of slightly more complex "total remaining" reads.
  • Admission in front. Use an atomic decrement in Redis (Chapter 13) as a fast gate that admits only 1,000 buyers plus a margin, and write only the admitted orders to the database. The database remains the source of truth and the conditional update still guards correctness; Redis just absorbs the herd.
  • Queue. Place purchase intents on a queue processed in order by a few workers, so the database sees a steady, serial stream instead of a stampede (Chapter 34).
  • Idempotency. Give each purchase an idempotency key with a unique constraint so a client retry after a timeout cannot decrement twice.

Result. The answer interviewers want: an atomic conditional update (or a row lock for multi-table rules), a CHECK constraint as a backstop, an idempotency key, and, if one row cannot take the load, a split counter or an upstream gate, with the reasoning about why read-then-write and naive optimistic locking fail.

16. Interview Q&A

Why would you choose PostgreSQL or MySQL over a NoSQL store for a new product?

Because the core data of most products is relational, needs multi-row transactions, and has query patterns you cannot fully predict yet. A relational database gives you constraints that protect integrity, joins for new features, and ACID transactions, so correctness work is done by the database instead of scattered across application code. A single well-tuned primary with replicas and a cache handles very large traffic, so the scale argument for NoSQL usually applies later, if ever. I would move specific data to another store only when a concrete need appears, such as huge write volume, time-series retention, or full-text search.

Walk me through what happens when I run a SELECT.

The parser checks syntax and resolves table and column names. The planner uses table statistics to enumerate candidate plans (scan versus index, join order, join algorithm) and picks the lowest estimated cost. The executor runs the plan as a tree of operators, asking the buffer pool for pages; pages already in memory are hits and others are read from disk and cached. Rows are returned as they are produced, so a LIMIT can stop work early. Performance problems come from a bad plan (stale statistics, missing index), too much data touched, or a working set larger than memory.

Why does the column order of a composite index matter?

The index is sorted by the first column, then the second within it, so it can only narrow a search along a leftmost prefix. An index on (customer_id, created_at) serves queries by customer and queries by customer plus time range, and can return a customer's rows already sorted by time, but it cannot help a query filtering only on created_at. The rule of thumb is equality columns first, then the range or sort column last, and to check the plan to confirm it is used. One composite index often replaces several single-column ones and costs less to maintain.

You added an index but the query is still slow. Why might that be?

First read the plan. Common reasons: the query wraps the column in a function or does a cast so the index cannot match; the filter is not selective, so the planner correctly prefers a scan; the leftmost prefix is violated; a leading wildcard in LIKE; stale statistics lead to a bad estimate; or the cost is elsewhere, such as sorting a huge result, a large OFFSET, N+1 calls from application code, or waiting on locks. I would run EXPLAIN ANALYZE, compare estimated and actual rows, and fix the specific cause instead of adding more indexes.

Explain the WAL and why it makes commits fast and durable.

The write-ahead log is an append-only record of every change, and the rule is that the log record reaches disk before the commit is acknowledged and before the corresponding data page is written. Appending to a log is a sequential write and one flush can cover many transactions, so commits are fast, while the big scattered data pages are written lazily in the background. After a crash the database replays the log from the last checkpoint to redo committed work and undo unfinished transactions. The same log feeds replication, point-in-time recovery, and change data capture.

Describe the isolation levels and which anomalies each allows.

Read uncommitted allows dirty reads; read committed prevents them but allows non-repeatable reads and phantoms because each statement sees the latest committed data. Repeatable read or snapshot isolation gives each transaction a stable snapshot, which prevents non-repeatable reads and, in Postgres, phantoms, but still allows write skew since two transactions can write different rows based on the same stale premise. Serializable prevents all of them, either with locking or with Postgres SSI, at the cost of aborts that the application must retry. Defaults are read committed in Postgres and repeatable read in InnoDB, and I would not assume they protect a read-then-write pattern.

What is write skew, and how do you prevent it?

Write skew is when two transactions read overlapping data, each decides an action is safe, and each writes a different row, so together they break an invariant, such as two on-call doctors both going off call. Row-level conflict detection misses it because no single row was written by both. Prevention options are the serializable level, locking the rows that were read with SELECT FOR UPDATE, materializing the invariant into one row that both transactions must update (so they conflict), or a database constraint or exclusion constraint where the rule can be expressed.

How does MVCC work, and what is the operational cost?

Updates create new row versions instead of overwriting, and each transaction reads the versions visible to its snapshot, so readers do not block writers. The cost is cleanup of old versions. In Postgres they sit in the table until vacuum removes them, so long-running transactions that hold an old snapshot cause bloat and slower scans, and vacuum must also prevent transaction id wraparound. In InnoDB, old versions live in the undo log and a purge thread removes them, so a long transaction makes the undo history grow. Either way, keeping transactions short is the main operational discipline.

How do you avoid deadlocks?

The most effective way is a consistent lock ordering, for example always locking accounts in ascending id order, so a cycle cannot form. Beyond that, keep transactions short and avoid slow work while holding locks, touch as few rows as possible with good indexes (which matters especially with InnoDB gap locks), and prefer single atomic statements. Because it can never be reduced to zero, the application should treat a deadlock error as retryable and retry with backoff. The database detects the cycle and aborts one victim, so deadlocks cost latency, not corruption.

Optimistic versus pessimistic locking: when do you use each?

Pessimistic locking (SELECT FOR UPDATE) takes the lock up front, which is right when contention on the same rows is high or when a conflict is expensive, as long as the transaction is short. Optimistic locking uses a version column and a conditional update, and fits low-contention cases or long user think times, like editing a document, where holding a lock is unacceptable. Under heavy contention optimistic control degrades into retry storms. For a plain counter, an atomic UPDATE with a condition beats both.

Why do you need a connection pooler like PgBouncer?

Database connections are heavy: in Postgres each is a process with its own memory, and throughput falls when too many are active at once. With many app instances each holding a pool, the total connection count can reach thousands. PgBouncer multiplexes many client connections onto a few server connections, typically in transaction mode, and queues clients in front of the database so it stays at a healthy concurrency. The tradeoff is losing session-level features such as session prepared statements, session variables, and advisory locks across transactions, and adding another component to keep highly available.

Your relational database is at its limits. What do you do, in order?

First measure and tune: slow queries, missing indexes, N+1 patterns, connection pooling, and a bigger instance. Then add read replicas for read-heavy load and a cache for hot reads, accepting replica lag. Move bulky or specialized data (blobs, search, time-series) to better stores. Partition large tables to keep indexes and retention manageable. Only if write volume or total size still exceeds one primary do I shard, choosing a shard key that keeps common queries and transactions within a shard, or adopt a distributed SQL database that does that splitting for me, accepting higher commit latency.

When would you pick CockroachDB or Spanner over sharded Postgres?

When I need relational transactions across a dataset too large or write-heavy for one node and do not want to build and operate routing, resharding, and cross-shard transaction logic myself. They replicate each range with consensus, so they give automatic failover and can survive zone or region loss with strongly consistent reads and writes. The price is higher write latency from the consensus round and cross-range commits, more operational complexity, and some feature gaps. If the data fits on one primary with replicas, plain Postgres is simpler and faster.

17. Recap

  • Default to a relational database for core data: transactions, constraints, joins, flexible queries. Leave it for a concrete reason such as write volume beyond one primary or a specialized data shape.
  • A query flows through parser, planner (cost-based, driven by statistics), executor, and buffer pool; data moves in 8 to 16 KB pages, and a working set that fits in RAM is the main performance lever.
  • A B-tree index gives logarithmic lookups with a very high fanout (3 to 4 levels for billions of rows). InnoDB clusters the table on the primary key; Postgres uses a heap with separate indexes.
  • Composite indexes follow the leftmost prefix rule: equality columns first, range or sort column last. Covering, partial, and expression indexes cut cost further; every index taxes every write.
  • Indexes fail when columns are wrapped in functions, selectivity is low, or statistics are stale. Read EXPLAIN ANALYZE, compare estimated to actual rows, know nested loop, hash, and merge joins, and eliminate N+1 queries.
  • ACID: atomicity and durability come from the write-ahead log (append first, replay after a crash); isolation is a dial with real anomalies: dirty read, non-repeatable read, phantom, lost update, write skew.
  • MVCC gives readers a snapshot without blocking writers, at the cost of vacuum/purge; keep transactions short to avoid bloat and lock trouble.
  • Prevent lost updates with atomic UPDATE statements, row locks, or version checks; prevent deadlocks with consistent lock order and retries; enforce uniqueness with constraints and upserts.
  • Pool connections (PgBouncer in transaction mode) so thousands of clients share dozens of server connections.
  • Scale in order: tune, replicas, cache, partition, then shard or use NewSQL (Spanner, CockroachDB), which trade commit latency for horizontal scale.
