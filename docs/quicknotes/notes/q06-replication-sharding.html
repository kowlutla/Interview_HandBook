0. Key definitions (know these cold)

TermDefinition
Replica / replicationA replica is a copy of the data on another machine. Replication is the work of keeping the copies in step as data changes. Reasons: stay up when a machine dies, read from a nearby copy, spread read load.
Leader (primary) and followerThe leader is the one copy that accepts writes. Followers (replicas, standbys) copy what the leader did and serve reads.
Replication logThe ordered list of changes the leader sends to followers (for example the write-ahead log or a row-change stream).
Synchronous / asynchronousSynchronous: the leader waits for the follower to confirm before telling the client "done". Asynchronous: the leader answers first and copies later. Semi-synchronous: wait for one follower only.
Replication lagHow far behind a follower is (in time or log position). Reads from a lagging follower can be stale.
FailoverReplacing a dead leader with a follower. Needs detection, choosing a new leader, and redirecting clients.
Split-brainTwo nodes both believe they are the leader and both accept writes, so the data diverges. Fenced off with epochs or tokens.
Multi-leader / leaderlessMulti-leader: several nodes accept writes and copy to each other (conflicts possible). Leaderless: any node accepts writes and a quorum rule decides success (Dynamo style).
Quorum (n, w, r)n copies; a write needs w acks; a read asks r copies. If w + r > n the read set and write set must overlap, so a read sees the newest acknowledged write (with caveats).
Conflict / LWW / CRDTConflict: two copies changed the same item at once. LWW (last write wins) keeps the newest timestamp and silently drops the other. A CRDT is a data type designed so concurrent updates always merge cleanly (counters, sets).
Read-your-writesAfter you write something, your own next read must show it. The most common lag rule to enforce.
Sharding (partitioning)Splitting one big dataset into pieces (shards), each on its own group of machines, so no machine holds everything. Replication copies the same data; sharding splits different data.
Shard keyThe field used to decide which shard a row lives on (for example user_id). The most important sharding decision.
Range vs hash partitioningRange: neighbouring keys stay together (good for range scans, risk of hot spots). Hash: keys are spread evenly (no range scans).
Consistent hashing / virtual nodesKeys and nodes sit on a ring; a key goes to the next node clockwise. Adding a node moves only about 1/N of keys. Virtual nodes give each machine many ring points for even load.
Hot partition / hot keyOne shard or one key gets far more traffic than the rest, so it overloads while others sit idle.
Resharding / rebalancingMoving data between shards when you add or remove machines or when shards become uneven.
Scatter-gatherA query without the shard key is sent to every shard and the answers are merged. Slow, and the slowest shard sets the latency.
Active-passive / active-activePassive: one region takes writes, another is on standby. Active-active: several regions take writes (needs conflict handling or key ownership).
RPO / RTORPO: how much data you may lose in a disaster (in time). RTO: how long you may be down. Async replication means RPO above zero.
Home regionThe one region that owns the writes for a given user or tenant. Removes conflicts, costs a longer trip for users who travel.
Expand and contractThe safe way to change a schema without downtime: add the new thing, write both, backfill, switch reads, then remove the old thing.
CDC (change data capture)Reading the database change log and turning each change into an event. Used to copy data to a new store while the old one stays live.
Dual writeThe app writes to the old and new store itself. Risky: one write can fail and the two drift apart.

1. Replication Ch 24

One line: replication keeps copies of the same data on several machines for availability, lower latency and more read capacity; the hard part is that data changes while copies are being made, so copies can lag or disagree.

Why replicate (name the real reason)

Availability

  • A machine dies or is patched; a copy takes over after a short switch.
  • Outage becomes a blip.

Latency

  • A copy near the user answers in a few ms instead of 150 ms across an ocean.

Read scale

  • Many followers share the read load.
  • Does not help write load: every write still goes to every copy.

Durability

  • The data survives a lost disk or a lost data centre.

Single-leader: the default

One node, the leader, takes all writes and writes them to its log. Followers read that log and apply the same changes in the same order. Reads can go to followers. It is the default because there are no write conflicts: one node decides the order.

Sync vs async vs semi-sync

ModeWrite waits forGoodBadUse when
AsynchronousOnly the leaderFast writes; a slow follower does not blockIf the leader dies, recent writes can be lost; followers lagCross-region copies, read replicas
SynchronousAll followersNo data lossOne dead or slow follower stops all writesRarely with more than one follower
Semi-synchronousOne chosen followerNo loss of acknowledged writes, still tolerates others being slowExtra 1 to 2 ms inside a regionThe common production setting for important data
Numbers: round trip between zones in one region about 1 to 2 ms; across regions about 60 to 250 ms (US east to west about 60 to 70, US to Europe about 80 to 100, US to Asia 150 to 250). So: sync inside a region, async across regions. Typical failover with a tool like Patroni: detection up to about 30 s, promotion 5 to 10 s, repointing 2 to 5 s, so roughly 40 to 60 s.

Replication lag: the three surprises

With async followers, a read can hit a follower that has not yet applied the latest changes. Users see odd things. The three standard fixes:

AnomalyWhat the user seesFix
Read-your-writes brokenI posted a comment and it vanished when I reloaded.For a few seconds after a write, send that user's reads to the leader; or pass the write's log position and read only from a follower that has reached it.
Monotonic reads brokenPage shows a new item, refresh, the item is gone (second read hit a more lagged follower).Pin each user to one follower (hash of user id).
Consistent prefix brokenAn answer appears before the question it answers.Keep causally related writes in the same shard or partition; send them through one log.

What travels in the log

FormatIdeaCatch
Statement-basedSend the SQL textNOW(), RANDOM() and triggers give different results per replica. Mostly avoided.
WAL shippingSend the storage-engine byte logTied to one database version and layout; replicas must match.
Logical (row-based)Send "row X changed from A to B"Version independent; also the base for CDC. Preferred.

Failover: replacing a dead leader

  1. Detect: missed heartbeats for a timeout (too short causes false alarms, too long means long outage).
  2. Choose: the most up-to-date follower wins an election.
  3. Redirect: clients, proxy or DNS point to the new leader.
  4. Fence the old leader so it cannot take writes if it comes back (it must step down or be shut off).
Traps: (1) async failover loses the writes the new leader never received; (2) the old leader returns still thinking it leads, so you get split-brain (fix with fencing tokens or epoch numbers, and STONITH); (3) auto-increment ids or caches that already saw the lost writes; (4) failover caused by a slow leader that then makes the load worse (a failover storm).

Adding a follower: take a snapshot of the leader, copy it, then ask the leader for every change since the snapshot position and catch up. No downtime for the leader.

Multi-leader and leaderless

ModelHow it worksGood forCost
Single-leaderOne writer, many readersMost systems; simpleWrites cross the ocean; one leader is the write ceiling
Multi-leaderA leader in each data centre; they copy to each other asynchronouslyWrites close to users; each region survives a cut link; offline apps; collaborative editingWrite conflicts; tricky topologies; surprising constraint violations
LeaderlessClient (or a coordinator) writes to n nodes and needs w acks; reads ask r nodesVery high availability; no failover step (Cassandra, Dynamo)Conflicts and stale reads need repair mechanisms

Resolving conflicts

ApproachHowWatch out
Avoid themRoute all writes for one record to one region (home region)Best answer when possible; fails if the home region is down
Last write winsHighest timestamp winsSilently loses data; clocks drift; fine only for caches or idempotent fields
Merge / app logicKeep both versions (siblings) and merge, for example union of shopping cartsThe application must handle siblings
CRDTTypes whose merge is always correct (counters, sets, text)Limited set of types, metadata grows

Quorums (leaderless)

With n copies, a write must be acknowledged by w and a read asks r. If w + r > n the sets overlap in at least one node, so the read sees the latest acknowledged write (when the overlapping node answers with the highest version).

SettingEffect
n=3, w=2, r=2Balanced; survives one node down for both reads and writes.
w=n, r=1Fast reads, writes stop if any node is down.
w=1, r=nFast writes, slow reads, reads stop if any node is down.
w=1, r=1Fastest, no overlap, stale reads likely.
Traps: a quorum is not strict linearizability. Sloppy quorums (writing to stand-in nodes with hinted handoff when the home nodes are down) break the overlap guarantee until hints are delivered. Concurrent writes, failed partial writes and clock-based LWW can all still give stale or lost data. Repair uses read repair (fix stale copies when a read notices them) and anti-entropy (background comparison, often using Merkle trees).

Replication in real systems

SystemModel
PostgreSQLSingle leader; WAL streaming; sync or async standbys; logical replication for selective copy. Patroni for failover.
MySQLSingle leader; binary log (row based); semi-sync option; Group Replication; Orchestrator for failover.
MongoDBReplica set with built-in elections (about 10 s); write concern chooses how many acks.
Cassandra / DynamoDB styleLeaderless, tunable quorum, hinted handoff, read repair.
KafkaLeader per partition, in-sync replicas (ISR), acks=all with min.insync.replicas.
Raft systems (etcd, Consul, CockroachDB ranges)Leader plus majority commit: a write is durable once a majority has it; automatic election.
Say: "I start with single-leader replication, one synchronous standby in another zone so no acknowledged write is lost, async read replicas, and I protect read-your-writes by sending a user's reads to the leader for a few seconds after they write. I monitor lag against a budget and remove any replica more than 5 seconds behind from the read pool."
Sizing example from the handbook: if one node serves about 8,000 reads/s and you keep 40% headroom for a failure, plan about 5,000 reads/s per replica in normal operation. Alert when p99 lag is above 3 s for 2 minutes (warn) and 5 s for 5 minutes (page).

2. Sharding Ch 25

One line: when the data or the write rate no longer fits one machine, split it by a shard key into pieces; replication gives copies, sharding gives capacity.

When to shard (and when not)

Try first

  • A bigger machine (scale up)
  • Read replicas and caching
  • Archive old data, better indexes, partition tables inside one server

Shard when

  • Data too big for one node's disk (tens of TB)
  • Write rate above what one leader can do (tens of thousands of writes/s)
  • Working set larger than memory

The price

  • Cross-shard queries and transactions get hard
  • Resharding is a project
  • Operations multiply by shard count

Partitioning schemes

SchemeHowGoodBad
RangeKey ranges (A to F, G to M, ...)Range scans stay on one shardHot spots: new timestamps or ids all hit the last range
Hashhash(key) decides the shardEven spreadNo range scans; point lookups only
CompositeHash the first part, range-sort the second (user_id, then time)Even spread and per-user ordered scansScans across users still scatter
Directory (lookup table)A table says which shard owns each key or tenantTotal flexibility; move one tenant at a timeThe directory is a critical, cached dependency
Geographic / tenantBy region or customerData residency, isolation, local latencyBig tenants make hot shards

Choosing the shard key: four tests

  1. High cardinality: many distinct values (not country or boolean).
  2. Even load: no single value gets most of the traffic.
  3. Query fit: your most common queries include the key, so each hits one shard.
  4. Stable: the value never changes (moving a row between shards is painful).
Bad keys: timestamp or auto-increment id with range sharding (all new writes hit one shard); country or status (low cardinality, skew); a celebrity user id (one key far hotter than the rest). Fixes: hash it, add a salt (key + random 0..N-1) for write-hot keys, or use a composite key.

Mapping keys to nodes

MethodIdeaVerdict
hash(key) mod NSimpleBreaks when N changes: almost all keys move (about N-1 out of N)
Fixed number of partitionsMany more partitions than nodes (for example 1,024); move whole partitions between nodesSimple, used by Redis Cluster (16,384 slots), Kafka, Elasticsearch
Consistent hashing + virtual nodesRing; each node has many pointsAdding a node moves only about 1/N of keys; even load via vnodes
Rendezvous hashingEach key picks the node with the highest hash(key, node)Simple, even, no ring state

Rebalancing and online resharding

  • Fixed partitions: add a node, then move some whole partitions to it. Limit the copy speed so live traffic is not hurt.
  • Split and merge: a partition that grows too big or hot splits in two (HBase, MongoDB chunks, CockroachDB ranges).
  • Online procedure: copy a snapshot to the new shard, stream changes made meanwhile, verify, switch routing for that slice, then delete from the old shard after a safety wait. Be careful to make the switch atomic through the routing layer.
  • Do it automatically only with throttles; automatic rebalancing plus an overloaded cluster can cause a cascade.

Hot keys and the celebrity problem

Hot onFix
ReadsCache in front; replicate the hot shard or key; local in-process copy
WritesSalting: add a random suffix to spread one key over N sub-keys, merge on read (counters, likes). Cost: reads must query N sub-keys.
A celebrity (millions of followers)Treat them specially: do not fan out writes to every follower; let readers pull the celebrity's posts and merge them at read time (hybrid fan-out).

Secondary indexes, joins, transactions

TopicOptions
Secondary indexLocal (document-partitioned): each shard indexes its own rows. Writes are cheap, but a query on the index must ask every shard (scatter-gather). Global (term-partitioned): the index itself is sharded by the indexed value. Reads hit one shard, but one write may update several shards and the index is often updated asynchronously (slightly stale).
JoinsCo-locate by the same shard key (orders and order items by order_id); copy small reference tables to every shard; otherwise join in the application or in an analytics store.
Transactions across shardsAvoid by design (choose a key that keeps related rows together). If unavoidable: two-phase commit (blocking, slow, coordinator is a risk) or sagas (a chain of local steps with compensating undo steps, eventually consistent).
Unique idsNo central counter. Use UUIDs, Snowflake-style ids (time + machine + sequence, roughly sortable), or ranges handed out per shard.

Routing layer

StyleHowExample
Client-sideClient library knows the map and goes straight to the shardRedis Cluster clients (follow MOVED redirects), Cassandra drivers
ProxyA stateless router in front looks up the shardVitess, mongos, Twemproxy
Coordinator / any nodeAny node accepts the request and forwards itCassandra, DynamoDB

Each shard is itself replicated (a leader and followers, or a Raft group), so a single machine failure does not lose a shard. Shard-level HA is just chapter 24 repeated per shard.

Worked example (handbook): 50 TB and 200,000 writes/s. If one node comfortably holds about 2 TB and takes about 10,000 writes/s, then 50 TB needs at least 25 nodes by size and 20 by write rate. Round up with headroom (for example 32 shards, a power of two so later splits are clean), shard by hash of user id, replicate each shard 3 times.
Traps: sharding too early; choosing a key that does not match the main query; forgetting that unsharded queries become scatter-gather; using mod N; no plan for resharding; a router that is a single point of failure.
Say: "I would not shard until replicas, caching and a bigger machine are exhausted. When I do, I shard by hash of the tenant or user id so the common query stays on one shard, use many more virtual partitions than nodes so I can move data without rehashing, and replicate every shard. Cross-shard transactions I avoid by choosing the key, or use sagas."

3. Multi-region Ch 26

One line: running in more than one region gives survival of a regional disaster, lower latency for far-away users, and data-residency compliance, at the cost of cross-ocean delay (60 to 250 ms), conflicts, and a bigger bill.

Topologies

TopologyHowRPO / RTOCost and catch
Single region + backups (DR)Backups copied to another regionHours of loss, hours to restoreCheapest; slow recovery
Active-passive (warm standby)One region serves; the other has a live async copy and idle capacitySeconds to minutes of loss (async lag); minutes to recoverPay for idle capacity; failover must be practised
Active-activeEvery region serves reads and writesNear-zero downtimeHighest cost; conflicts or ownership rules needed
Follower readsOne write region, local read replicas elsewhereAs active-passiveFast reads for everyone; writes still far; reads can be stale
Home region per userEach user or tenant is owned by one region for writesPer-tenant failoverNo conflicts; travelers get slower writes

Global databases in one line each

SystemIdea
SpannerConsensus (Paxos) per shard plus TrueTime (clocks with bounded error); strongly consistent global transactions, writes wait out the clock uncertainty and pay cross-region round trips.
CockroachDB / YugabyteDBSpanner-like: Raft per range, SQL; you choose where replicas and leaseholders live.
DynamoDB global tablesMulti-region, multi-writer, async replication, last writer wins on conflicts.
Cosmos DBMulti-region with five tunable consistency levels from strong to eventual.
Aurora Global DatabaseOne writer region, read-only replicas in others with usually under 1 s lag; promote on disaster.

What cross-region latency does

  • A write that needs a quorum or consensus across regions pays at least one cross-region round trip (about 60 to 150 ms) on every write. That limits a transaction chain: 10 sequential writes could cost over a second.
  • Async replication hides that cost but lag appears (often tens to hundreds of ms, seconds under load), and a regional disaster can lose that window of writes.
  • Design per feature: strong consistency only for what needs it (payments, inventory, unique usernames), eventual for the rest (feeds, likes, profile views).
FeatureTypical consistency
Payments, balances, inventoryStrong, single owner region or consensus
Profile editsRead-your-writes in the home region; eventual elsewhere
Feeds, likes, countersEventual; CRDT counters
Catalog, configEventual, cached

Routing users, residency, failover

  • Routing: geo or latency-based DNS, anycast, or a global load balancer to the nearest healthy region. For home-region designs look up the user's home (token claim or a small global directory) and forward to it. Keep sessions sticky or in a shared store.
  • Data residency: laws (for example GDPR) can require that some data stays in a place. Pin those tenants to a region, never replicate their rows elsewhere, and keep derived data and logs in mind.
  • Failover sequence: detect (health checks from several vantage points), decide (automatic or a human approving), promote the standby, shift traffic, warm caches. Failback is harder than failover: the old region must be resynced before it takes traffic back.
  • Split-brain across regions: a network cut makes each region think the other is dead. Fix with a majority vote (an odd number of regions or an external tie-breaker) and fencing epochs.
  • Cost: duplicated compute, storage and cross-region data transfer. Active-active can cost two to three times a single region. Say that out loud and ask whether the business needs it.
Traps: LWW in active-active silently drops writes; promising zero data loss with async replication; a failover plan that was never rehearsed; forgetting the failed region's queue and cache state; a dependency (auth, config store) that lives in only one region and makes the "multi-region" system single-region in practice.
Say: "I would ask what survival level the business needs. For most systems I recommend active-passive or home-region ownership: each user's writes go to one region so there are no conflicts, other regions hold async copies for reads and disaster recovery. I name the RPO as the replication lag, practise the failover, and keep strongly consistent features such as payments in one owner region."

4. Online migrations and schema changes Ch 26

One line: change a live system in small, reversible steps where old and new code and old and new data work together, never one big switch.

Expand and contract (schema change with no downtime)

  • Safe rules: add columns as nullable or with defaults; never rename or drop in one step; keep readers tolerant of unknown fields; batch backfills with throttling so replicas do not lag.
  • Big-table DDL: tools like gh-ost and pt-online-schema-change build a shadow copy of the table, stream changes into it, then swap names at the end, avoiding long locks.

Migrating data to a new database

PhaseWhat happens
1. Snapshot / bulk copyCopy existing data to the new store while the old one serves traffic.
2. Catch-upStream changes (CDC from the old log) until the new store is nearly caught up.
3. VerifyCompare row counts, checksums, sampled records; shadow-read from the new store and diff.
4. Shift readsMove a small percent of reads, watch errors and diffs, increase.
5. Cutover writesShort pause or fenced switch so only one store takes writes; then reverse replication so you can roll back.
6. Retire oldAfter a soak period and a backup.
ApproachProsCons
Dual write from the appEasy to startPartial failures and ordering differences make the stores drift; hard to prove correct
CDC from the old database logCaptures every change in order, no app changeExtra infrastructure, small lag, needs care with schema mapping
  • Changing the shard key: a new key means every row may move: build a new sharded store keyed correctly, copy plus CDC, verify, cut over. Same key and more shards is easier (split ranges or move partitions).
  • Verification: counts and checksums per chunk, sampled field-level diffs, shadow reads, and a rollback path at every step.
Traps: dual writes without reconciliation; cutting writes over with no way back; one huge backfill that makes replicas lag; dropping the old column while an old app version still runs; forgetting that during the copy the old store keeps changing.
Say: "I never do a big-bang migration. I expand the schema, dual write or stream changes with CDC, backfill in throttled batches, verify with checksums and shadow reads, move reads gradually, cut writes over with a fence, keep reverse replication for rollback, and only then contract."

5. Say-aloud script (45 seconds in an interview)

  1. "First I ask what I am protecting against: a machine failing, read load, distance to users, or data too big for one machine. Replication solves the first three, sharding solves the last."
  2. "I start with single-leader replication. One synchronous standby in another zone so no acknowledged write is lost, async read replicas for scale and for other regions."
  3. "Async replicas lag, so I protect read-your-writes by sending a user's reads to the leader for a few seconds after they write, and I alert on lag."
  4. "If one leader cannot take the writes or the data is too large, I shard by a high-cardinality key that appears in the main query, with hash partitioning and many more partitions than nodes, so adding machines moves whole partitions instead of rehashing everything."
  5. "Hot keys get a cache or a salted key; cross-shard transactions I avoid by key choice or use sagas."
  6. "For multiple regions I prefer home-region ownership with async copies elsewhere: no write conflicts, a clear RPO, and a rehearsed failover. Only truly global features get consensus across regions."
  7. "Any change on the live system is expand, copy with CDC, verify, shift, and only then contract, with a rollback path at each step."

6. Interview Q&A (detailed answers)

Click a question to open the answer. Grouped as: concepts, design scenarios, failure and real-time (production) situations, and trade-off or "why" questions.

A. Concept questions

1. What is the difference between replication and sharding?

Replication keeps full copies of the same data on several machines. It helps availability, read capacity and distance to users, but every copy still has to take every write, so it does not raise the write limit or the total data size. Sharding splits the data into pieces and puts each piece on a different machine, so both storage and write load are shared. Real systems use both: the data is split into shards, and each shard is replicated, typically three times. A quick way to say it: replication is for safety and reads, sharding is for size and writes.

2. Explain single-leader replication and why it is the default.

One node, the leader, accepts all writes and records them in an ordered log. Followers read that log and apply the same changes in the same order, and they serve reads. It is the default because one node decides the order of all writes, so there are no write conflicts and the model is easy to reason about. The costs are that all writes go through one machine (a write ceiling), writes from far away cross the ocean, and if the leader dies you need a failover. For most products those costs are acceptable and the simplicity is worth a lot.

3. Synchronous, asynchronous and semi-synchronous replication: what is the difference?

In synchronous replication the leader waits until the follower confirms it has the change before telling the client the write succeeded. You lose no acknowledged data, but a slow or dead follower blocks writes. In asynchronous replication the leader answers right away and sends the change later. Writes are fast and robust against slow followers, but if the leader dies the recent writes that were not copied are lost, and followers can be stale. Semi-synchronous waits for one follower only, usually in another zone. That gives durability for acknowledged writes with only 1 to 2 ms extra, and if that follower is slow another one takes its place. This is what I choose for important data inside a region, and I use async across regions.

4. What is replication lag and what problems does it cause?

Lag is the delay between a change being committed on the leader and being visible on a follower. Usually it is tens of milliseconds, but it grows under heavy writes, long transactions on the follower, a slow network or a catch-up after a restart. The user-visible problems are three. Read-your-writes: you save something and it is missing on reload. Monotonic reads: data appears and then disappears because the next read hit a more lagged follower. Consistent prefix: effects appear before causes, such as an answer before its question. I fix them with leader reads after a write, sticky follower per user, and keeping related writes in the same partition and log.

5. What are the main log formats for replication and which would you pick?

Statement-based replication sends the SQL text. It is small, but things like NOW(), RANDOM() or triggers can give different results on each replica, so it is mostly avoided. WAL shipping sends the storage engine's byte log. It is exact and fast, but it ties leader and followers to the same database version and layout. Logical or row-based replication sends "row X changed from A to B". It is independent of the storage layout, allows different versions during an upgrade, and the same stream can feed CDC pipelines, search indexes and caches. I prefer logical replication when I need those extras, and plain WAL streaming for simple same-version standbys.

6. How do quorums work in a leaderless system?

Data is stored on n nodes. A write is successful when w nodes acknowledge, and a read asks r nodes and takes the newest version. If w plus r is greater than n, the nodes written and the nodes read must share at least one node, so the read normally sees the latest acknowledged write. With n=3, w=2 and r=2 you tolerate one node down for both reads and writes. You can tune: w=1 for fast writes, or r=1 for fast reads, giving up some overlap. It is not a full guarantee: sloppy quorums, failed partial writes, clock-based conflict resolution and concurrent writes can still give stale or lost data. Read repair and anti-entropy slowly fix the differences.

7. What is a good shard key and what makes a bad one?

A good key has high cardinality (many different values), spreads traffic evenly, appears in the most common queries so that each query goes to one shard, and never changes. User id or tenant id is the classic choice for a user-centric product. Bad keys are timestamps or auto-increment ids with range sharding (all new writes land on the last shard), low-cardinality fields such as country or status (a few huge shards), and anything where one value is far hotter than others, such as a celebrity account. If the natural key is bad you hash it, add a composite part, or add a salt.

8. Range vs hash partitioning: when would you use each?

Range partitioning keeps neighbouring keys together, so a range scan like "all events for this user from last week" reads one shard. The danger is hot spots when keys grow in order, because all new writes go to the last range. Hash partitioning spreads keys evenly, which protects against hot spots, but a range query must ask every shard. A common compromise is a composite key: hash the first part (user id) to choose the shard and sort by the second part (time) inside it, so you get even spread and ordered scans per user. I choose range for scan-heavy, naturally spread data and hash for point lookups and heavy writes.

9. Why does hash(key) mod N fail, and what do we use instead?

If you place a key on node hash(key) mod N and then change N from 3 to 4, nearly every key maps to a different node, so almost all data must move (or all cache entries become misses). Better options: a fixed large number of partitions (for example 1,024 or Redis's 16,384 slots), where adding a node just moves whole partitions; or consistent hashing, where nodes and keys sit on a ring and a key belongs to the next node clockwise, so adding a node takes only about 1/N of the keys. Virtual nodes give every machine many points on the ring so the load is even and a new node takes small slices from many neighbours. Rendezvous hashing is a simple alternative: each key chooses the node with the highest hash of key and node.

10. Local vs global secondary indexes in a sharded database?

A local index (document-partitioned) lives with each shard and indexes only that shard's rows. Writes are cheap because one shard handles the row and its index, but a query by the indexed field must go to all shards and merge (scatter-gather), and the slowest shard sets the latency. A global index (term-partitioned) is itself sharded by the indexed value, so a read goes to one shard. The cost is that one row write may touch the data shard and one or more index shards, and the index is often updated asynchronously, so it can be slightly stale. I choose local indexes when most queries include the shard key, and global when I need fast lookup by another field and accept lag.

B. Design scenarios

11. Design replication for a user database that must not lose acknowledged writes, serving 30,000 reads/s and 1,500 writes/s.

Single-leader with semi-synchronous replication to one standby in a second zone, so every acknowledged write exists on two machines for about 1 to 2 ms extra. Add several asynchronous read replicas. If a node handles about 8,000 reads/s, plan about 5,000 reads/s per replica to keep 40% headroom for a failure, so around 6 to 8 replicas for 30,000. Reads go through a router that removes any replica more than about 5 seconds behind. Read-your-writes: after a write, that user's reads go to the leader for about 10 seconds; since only a few percent of reads come from recent writers, the leader handles it. Failover through a tool such as Patroni with fencing, practised in game days. Alert on lag and on replica count.

12. You must shard a 50 TB table with 200,000 writes/s. Walk through it.

First check that I truly need it: 50 TB and 200k writes/s are beyond one node, so yes. If one node holds about 2 TB and takes about 10,000 writes/s, I need at least 25 shards by size and 20 by writes, so I plan 32 with headroom (a power of two splits cleanly later). I choose the shard key from the main queries, for example user id, hashed so load is even. I use many logical partitions (for example 1,024) mapped to the 32 machines, held in a shard map in a small replicated config store and cached by routers. Each shard has a leader and two followers. Unique ids come from a Snowflake-style generator. Queries not including user id go to a separate index or search system rather than scatter-gather. Then I describe hot-key and resharding plans.

13. How would you handle a celebrity or hot key in a sharded system?

I first separate reads and writes. For reads, put a cache or CDN in front, add a short-lived local cache in each app server, and replicate the hot item to several nodes. For writes, such as a counter everyone increments, use salting: write to key#0 through key#N-1 at random and add them up on read; the cost is N reads, which you can cache. For a social feed, do not push every post of a celebrity to millions of follower timelines; instead keep their posts separate and merge them into the follower's feed at read time (hybrid fan-out). Detect hot keys automatically by sampling request counts per key and promote them to the special path.

14. Design a multi-region setup for a consumer app with users in the US, Europe and Asia.

I would ask the RPO, RTO and whether any data must stay in region. A practical answer is home-region ownership: each user belongs to one region, chosen at signup, and their writes go there. The other regions have async copies for disaster recovery, and a global directory (or a token claim) tells the edge which region owns the user. Reads of content that is not user-private can be served from the nearest replica. Global state such as usernames needs a single owner or consensus. Traffic goes by latency-based DNS or anycast to the nearest edge, which forwards to the home region when needed. Failover per region: promote the standby, accept losing the last replication-lag window of writes, and rehearse. This avoids write conflicts and keeps cost lower than full active-active.

15. How would you add a column and change its meaning on a 2 TB table with no downtime?

Use expand and contract. Step one, add the new nullable column with an online DDL tool (gh-ost or pt-online-schema-change, or a native online operation) so there is no long lock. Step two, deploy code that writes both old and new fields and still reads the old one. Step three, backfill existing rows in small throttled batches, watching replica lag and pausing if it rises. Step four, switch reads to the new column behind a flag and compare results for a while. Step five, stop writing the old column and, after a safe period when no old code version runs, drop it. Every step can be rolled back except the last, which is why I wait before it.

16. Migrate a live user table from one database to a new sharded store with no downtime.

Plan: build the new sharded store with the right shard key. Bulk copy a snapshot while the old database serves traffic. Start CDC from the old database's log from the snapshot position and apply changes to the new store until lag is tiny. Verify with row counts, per-chunk checksums and sampled field diffs; also shadow-read from the new store and compare answers without serving them. Move a small share of reads, then more. For the write cutover, briefly fence writes on the old store (or switch the routing atomically), let CDC drain, then send writes to the new store and set up reverse replication back to the old one so a rollback is possible. Keep the old store for a soak period and take a final backup before decommission.

C. Failures and real-time production scenarios

17. The primary database dies at peak time. What happens and what do you do?

The failover tool notices missed heartbeats (up to about 30 seconds with a conservative lease), picks the most caught-up follower, promotes it, and repoints the proxy; the whole thing takes roughly 40 to 60 seconds. During this time writes fail, so the app should retry with backoff and show a degraded state rather than pile up. With a semi-synchronous standby no acknowledged write is lost; with only async replicas the last few writes may be gone, so I compare logs and tell the business. After promotion I must fence the old leader so it cannot accept writes if it returns, rebuild it as a follower, check caches and sequences for anything the lost writes touched, and run a post-incident review on detection time.

18. Users say "my comment disappeared after I posted it". What is going on?

That is a read-your-writes failure: the write went to the leader, and the next read hit a follower that had not yet applied it. Check replication lag metrics first; a spike would tell you the cause (a big batch job, a long transaction on the follower, network trouble). The fix in the app is to route a user's reads to the leader for a short window after they write, or to pass the log position (LSN) from the write to the next read and choose a follower that has reached it. Also optimistically show the new comment in the user interface. For the lag itself, throttle the batch job, add replica capacity, and remove laggy replicas from the read pool.

19. The old primary comes back after failover and both think they are leader. What do you do?

This is split-brain and it can corrupt data, because two nodes accept different writes. Stop it first: shut down or fence the old leader (cut its network or storage access, or use a power or cloud API "STONITH" action). Prevent it by design: every leader has an epoch or term number, followers and storage reject writes from a lower epoch, and a leader must keep a lease from a consensus store (etcd, ZooKeeper) and stop serving when the lease expires. After the incident, compare the two histories, decide which writes to keep, replay or manually merge the writes made on the old leader, and rebuild it as a follower from the new leader.

20. One shard is at 95% CPU while the others are at 20%. How do you respond?

Stabilise first: shed non-critical load, turn on or extend caching for the hot data, and add read replicas for that shard if reads dominate. Then diagnose: find the top keys on that shard by sampling. If it is one hot key (a celebrity, a viral item), use cache, key replication or salting. If the key distribution is skewed (a big tenant, sequential ids with range sharding), split that shard or move that tenant to a dedicated shard using the directory. If a bad query is scanning, fix it. Longer term: change to a better key or add a hash prefix, enable automatic splitting with throttles, and alert on per-shard imbalance, not only on averages.

21. You add a node to your cluster and latency doubles. Why, and what do you do?

Rebalancing is moving data: copying partitions uses disk, network and CPU on both the source and the target, and cold caches on the new node cause misses. If the cluster was already near its limit, the extra work pushes latency up. Immediately lower the rebalance rate (stream throttle) or pause it, and keep serving from the old owner until a partition is verified on the new one. In the future, add capacity before you are at the limit, move a few partitions at a time, rebalance in off-peak hours, warm the new node, and use a fixed-partition or consistent hashing scheme so only about 1/N of the data moves, not everything.

22. A whole region goes down. How do you recover?

Detect with health checks from several places so you do not confuse a bad probe with a real outage. Decide fast: automatic if the system was designed and tested for it, otherwise an on-call leader approves. Promote the standby region's database (the write window that was not yet replicated is the RPO loss), move traffic by changing DNS or the global load balancer, and bring up capacity because the surviving region now takes double load; autoscaling and pre-warmed caches matter here. Disable features that depend on the lost region. Afterwards, failback carefully: resync the old region as a follower, verify, and move traffic back during a quiet period. A failover that has never been rehearsed usually fails, so run game days.

23. Replicas are minutes behind and keep growing. How do you debug?

Compare the leader's write rate with the follower's apply rate. Common causes: the follower applies changes on a single thread while the leader writes in parallel (enable parallel apply); a long-running query on the follower blocks apply (conflicts with replay on PostgreSQL hot standby); a large batch job or schema change on the leader; follower hardware or disk slower than the leader; a saturated network link, especially across regions. Immediate actions: take the lagging replica out of the read pool so users do not see stale data, pause the batch job, and kill long queries on the follower. Then fix the root cause, and keep a lag alert (for example p99 above 3 s for 2 minutes warns and above 5 s for 5 minutes pages).

24. During a migration the new store shows fewer rows than the old one. What now?

Do not cut over. Check how far CDC lags: rows still in flight would explain a small gap. If the gap is stable, find which keys are missing by comparing checksums per chunk and then per row in the bad chunks. Likely causes: a write path that bypasses the log (a bulk loader or admin script), events dropped by a consumer error or schema mismatch, a backfill that skipped a range, deletes applied in the wrong order, or a filter bug. Fix the cause, replay from the log position, and re-verify. Keep shadow reads and the diff dashboard running until the diff stays zero for a full cycle including peak and batch hours.

25. A network cut separates two regions in an active-active setup. What happens?

Both regions keep accepting writes, because each can still reach its own users. When the link heals, the same items may have been changed on both sides, so you get conflicts. If you used last-writer-wins, one version silently disappears. Mitigations: do not let two regions write the same item (home region), use CRDTs for counters and sets, keep both versions and merge in application logic, and log every conflict so you can audit it. For items that must stay unique or correct, such as account balances, require a single owner or a quorum, and refuse the write in the minority region during the partition (choose consistency over availability for that feature).

D. Trade-offs and why-questions

26. Why not just use synchronous replication everywhere?

Because every write would wait for the slowest copy and any dead copy would stop writes. Across regions each write would cost a full 60 to 250 ms round trip. The availability of the whole system becomes lower than the availability of one machine, because all of them must be up. Semi-synchronous replication gets most of the safety: one nearby follower confirms, the rest copy later. The decision rule I give: synchronous to one standby in the same region for durability, asynchronous to other regions, and accept that a regional disaster loses the lag window; if the business says zero loss across regions, use a consensus database and pay the latency on writes.

27. Single-leader vs multi-leader vs leaderless: how do you choose?

Single-leader is the default: simple and conflict-free, but one write location. I move to multi-leader only if I need writes accepted in several regions with local latency, or I need offline clients or collaborative editing, and I accept conflict handling work. Leaderless (Dynamo style) fits very high availability and write throughput with simple key-value access, where eventual consistency and quorum tuning are acceptable, and where there is no single node to fail over. Choosing multi-leader just to "be more available" is a trap: conflict resolution is hard, and many constraints (uniqueness, balances) cannot be enforced across leaders. Often home-region ownership with single-leader per region gives most of the benefit.

28. Last write wins vs CRDTs vs application merge: how do you pick?

LWW keeps the value with the newest timestamp. It is trivial to build but silently drops one of two concurrent writes and trusts clocks that drift, so I use it only where losing a concurrent update is fine, such as a cache or a "last seen" field. CRDTs are data types designed so that concurrent updates always merge to the same result on every copy: counters, sets, registers, sequences for text. They fit likes, carts and collaborative editing but have a limited set of operations and metadata overhead. Application-level merge keeps both versions (siblings) and lets business code decide, for example union two carts or ask the user. It is the most flexible, but you must write and test it. Best of all is to avoid conflicts by giving each record one owner.

29. Range sharding vs hash sharding vs a directory: why choose one over the others?

Range is best when range scans matter and the data spreads naturally, but it risks hot ranges and needs splitting. Hash is the safest default for even load and simple routing, but range queries become scatter-gather. A directory (lookup table) gives full control: you can move one big tenant, mix sizes and place data by region, at the cost of a new critical component that must be fast, cached and replicated. Many real systems combine them: hash the tenant into many logical partitions, and keep a small table that maps partitions to machines, which gives even spread plus flexible movement. I describe that hybrid in interviews because it answers rebalancing and hot tenant questions together.

30. Active-active vs active-passive: which should I recommend and why?

Active-passive is simpler, cheaper and has no conflicts: one region owns writes, and the standby takes over in a disaster with a short outage and a small loss window. Active-active gives near-zero downtime and local writes for every user, but costs two to three times as much, needs conflict handling or ownership rules, and is harder to test. Unless the business truly needs writes in several regions or cannot accept minutes of recovery, I recommend active-passive or home-region ownership, with follower reads for far-away users. I choose full active-active for products where every second of downtime is very expensive and the data fits conflict-free types, and I keep strongly consistent data (payments) on a single owner region or a consensus database.

31. Dual write or CDC for a migration?

Dual write means the application writes to both stores. It is quick to start but there is no transaction across two stores: if the second write fails or arrives in a different order, they silently drift, and the code has to handle retries and races everywhere writes happen. CDC reads the old database's committed log, so it sees every change in the right order from every write path, including scripts, and the application does not change. The cost is more infrastructure and a little lag. I choose CDC with a verification job, and use dual write only for a short controlled phase, or with an outbox table so the second write is derived from a committed record.
