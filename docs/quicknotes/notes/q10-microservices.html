Microservices in depth

0. Key definitions (know these cold)

TermDefinition
MonolithOne application built, tested and deployed as a single unit. All features live together and call each other as normal function calls, usually over one shared database.
MicroserviceA small service that can be released on its own, owns one business capability and its own data, and talks to others over the network.
Modular monolithOne deployable unit, but with strict inside walls between modules. A cheap middle step before splitting.
Distributed monolithThe worst of both worlds: many services that must still be released together or share a database. All the network pain, none of the freedom.
Bounded contextA part of the business where words have one clear meaning (for example "Order" in Shipping is not the same as "Order" in Billing). A good service boundary.
Strangler figMigration style: put a router in front, move one feature at a time to a new service, and let the old monolith shrink until it can be removed.
Database per serviceEach service has private tables. Others must call its API or listen to its events; no reaching into its database.
Eventual consistencyCopies of data in different services may disagree for a short time but become the same if no new changes arrive.
SagaA multi-service business action done as a chain of small local transactions. If a step fails, earlier steps are undone by "compensations".
CompensationA new action that undoes the business effect of an earlier step (refund a charge, release stock). It does not roll back; it adds a reversing step.
Outbox patternWrite the data change and the "message to send" in the same local database transaction; a relay then publishes the message. Avoids "saved but never announced".
IdempotentDoing the same request twice has the same result as doing it once. Needed because messages and retries repeat.
Service registry / discoveryA live phone book of which instances of each service exist and where. Callers look up addresses instead of hard-coding them.
Sidecar / service meshA small proxy beside every service instance that handles retries, encryption, routing and metrics, managed by a central control plane.
mTLSMutual TLS: both sides prove who they are with certificates and the traffic is encrypted.
Circuit breakerA switch that stops calling a failing service for a short time so it can recover and callers fail fast.
BulkheadSeparate pools of threads or connections per dependency so one slow dependency cannot use up everything.
Cascading failureOne slow or broken service makes its callers slow, which makes their callers slow, until the whole system is down.
Retry stormMany callers retrying at once multiplies load on an already struggling service.
Trace / span / correlation idA trace is the full path of one request; a span is one step in it; a correlation id is the one id stamped on every log line and call of that request.
Consumer-driven contract testThe caller writes down what it expects from the provider; the provider's build checks it still satisfies that. Catches breaking changes before release.
Conway's LawSystems end up shaped like the communication structure of the teams that build them.
SLOA target for how good a service should be (for example 99.9% of requests succeed in 300 ms).

1. Monolith to microservices Ch 44

One line: microservices are a trade of team independence for operational complexity. Split because of real pain, not because it is fashionable.

A monolith is one deployable thing. It is simple: one repo, one deploy, function calls are fast and safe, one database transaction can change many tables together, and debugging is one stack trace. Many companies run happily on a (modular) monolith. Real pain appears when many teams share it: releases queue up, one bug breaks everyone, one part needs very different scaling, or the build and tests take hours.

A microservice gives you independent release, independent scaling and failure isolation per capability. But every function call became a network call. Networks are slow, can fail halfway and can duplicate messages. You also pay for data split across services, many pipelines, tracing, on-call and more machines.

SituationChoiceWhy
Small team (under about 10 to 15), new productMonolith, ideally modularSpeed matters; boundaries are not known yet; a wrong split is costly.
Many teams blocked by shared releasesSplit along team and business linesIndependent deploys remove the waiting.
One hot part needs 50x the scaleExtract only that partScale it alone; leave the rest.
Parts need different tech or compliance (payments, PII)Extract with its own data and accessSmaller audit scope.
You cannot yet deploy, monitor and roll back one service wellDo not split yetYou would build a distributed monolith.

Migration techniques

  • Strangler fig: route by feature through a proxy or gateway; migrate slice by slice.
  • Branch by abstraction: hide the old code behind an interface inside the monolith, build the new implementation (a call to the new service) behind the same interface, then switch.
  • Parallel run / dual-run: send the same request to old and new, compare answers, serve only the old one until they match.
  • Extract the edges first: start with parts that have few dependencies (notifications, search, image processing). Extract the tangled core last.
  • Data last, carefully: first make the code use an API, then split the tables (see section 3).
Numbers and rules of thumb: a team can run about one or two services well (the "two-pizza team" idea, about 5 to 9 people). If every release needs 3 teams to agree, you have a distributed monolith. Measure success with deploy frequency, lead time, change failure rate and time to restore (the four DORA numbers), not with the count of services.
Trap: "big bang rewrite". Freezing features for a year to rewrite everything almost always runs late and loses behaviour nobody remembered. Also a trap: one service per database table (too small) and a shared database between services.
Say: "I would not start with microservices. I would build a modular monolith, find the real boundaries from pain, and strangle out one slice at a time behind a router, with a rollback switch at every step."

2. Decomposition: finding the boundaries Ch 45

One line: draw the lines around business capabilities where data and change stay together, so most changes touch one service only.
ApproachHowGood for
By business capabilityList what the business does: catalog, cart, orders, payments, shipping.The default starting point.
By bounded context (DDD)Group by where the same word means the same thing; talk with domain experts (event storming).Finding the true seams.
By subdomainCore (your edge), supporting, generic (buy it).Deciding where to invest and what to buy.
By data ownershipWho writes this data? That service owns it.Checking a cut is clean.
By scaling or riskHot read path, PCI payments, batch jobs.Extra reason to separate.

Good boundary signs

  • High cohesion: things that change together live together
  • Low coupling: few calls across the line
  • One team owns it end to end
  • It can be released alone

Boundary smells

  • Two services always deployed together
  • Chatty calls: ten calls per user action
  • A change in one forces a change in another
  • Shared tables or a shared "common" library full of business logic
  • Circular dependencies (A calls B calls A)

Granularity

  • Too big: a mini-monolith, slow releases
  • Too small (nano-services): all network, no value
  • Fix wrong cuts by merging; that is normal
Quick tests: can one team own it? Can it deploy alone? Does one user action need more than about 3 to 5 synchronous calls? If a number of services must always change together, merge them.
Trap: splitting by technical layer (UI service, logic service, database service). Every feature then touches all of them. Also: splitting before you know the domain; boundaries are cheap to move inside a monolith and costly across services.
Say: "I cut along business capabilities and data ownership, validate with change history (what usually changes together) and call counts, and I accept that I will merge or move a boundary later."

3. Data across services Ch 46

One line: every service owns its data. You get independence, and you give up cross-service joins and cross-service transactions.
OptionProsCons / when
Shared databaseEasy joins and transactionsHidden coupling; one schema change breaks many teams. Tolerable only briefly during migration.
Schema per service, same instanceCheap; clear ownership if enforced by permissionsShared hardware means noisy neighbours.
Separate database per serviceTrue isolation, own tech (polyglot)More to run and back up.

How do I get data I do not own?

TechniqueHow it worksTrade-off
API callAsk the owner at request time.Always fresh; adds latency and a runtime dependency.
API compositionA gateway or BFF calls several services and merges the answers.Simple; slow if many calls; no big joins.
Event-carried state / local copyOwner publishes changes; others keep a small read copy of what they need.Fast and available; eventually consistent; copy can be stale.
CQRS read modelBuild a ready-made view (denormalized) from events from many services.Fast queries; extra pipeline; delay.
CDC into search / analyticsRead the database change log and feed Elasticsearch or a warehouse.No dual write; small lag.
  • Foreign keys without joins: store only the other service's id; check it by API or event; accept that an id may point to something deleted, and handle it.
  • Unique ids: use UUIDs or time-ordered ids (Snowflake style) so services do not need a central counter.
  • Transactions: keep one aggregate (for example an order and its lines) inside one service so one local transaction covers it. Draw boundaries so that need for cross-service transactions is rare.
  • Splitting a shared database: make everyone use an API first; then copy tables, dual-write or use CDC, compare, switch reads, then switch writes, then drop the old tables.
  • PII: one owner of personal data; others hold ids or minimal copies; deletion requests must flow to every copy.
Numbers: read-model lag is typically milliseconds to a few seconds. A page that needs 5 sync calls each at 99.9% availability is at about 99.5% (0.999^5). A local copy removes that dependency from the read path.
Trap: "just share the database for now, we will fix it later" (it stays forever). And dual-writing to a database and a queue in two separate steps: one can succeed and the other fail. Use the outbox or CDC.
Say: "Each service owns its tables. For cross-service reads I use local copies built from events or a CQRS view, and I state the staleness. For cross-service writes I use a saga, not a distributed transaction."

4. Service communication Ch 47

One line: choose sync (ask and wait) when the caller needs the answer now, async (send a message) when it does not, and write the contract down so teams can release alone.
StyleUse whenCost
REST / HTTP+JSONPublic or simple internal APIs; easy to debug.Text format, larger, slower than binary.
gRPCInternal, high volume, low latency; typed contracts, streaming.Harder to debug by hand; browser support needs a proxy.
GraphQL / BFFClients need to shape data from many services.Needs query-cost limits; the gateway can become a mini-monolith.
Messages / events (Kafka, queue)The caller can continue without an answer; fan-out; spikes.Eventual results; harder to follow the flow; duplicates possible.

Contracts and safe change

  • Backward compatible changes: add optional fields, add endpoints. Breaking: remove or rename fields, change meaning, make an optional field required.
  • Be liberal in what you accept: consumers ignore unknown fields (tolerant reader).
  • Expand and contract: add the new thing next to the old, move all callers, then remove the old.
  • Consumer-driven contract tests (Pact): catch a breaking change in the provider's build.
  • Versioning: avoid new versions when possible; if needed, version in the path or header and set a deprecation date.
  • Safe calls: a timeout on every call, retries only for idempotent work, with backoff and jitter; pass an idempotency key for writes; pass a deadline down the chain.
  • Errors: clear error codes; separate "you sent bad data" (4xx, do not retry) from "I failed" (5xx, maybe retry).
Numbers: 5 chained services at 99.9% each give about 99.5% (about 3.6 hours of downtime per month instead of 43 minutes). Binary formats (protobuf) are typically several times smaller than JSON. Aim for call depth of 3 or less.
Trap: "async over sync" faking: a service publishes an event and then the caller polls and blocks for the result: you took the cost of both. Also: one request fans out to 20 services (chatty API); fix with composition, local copies or coarser calls.
Say: "Sync for queries on the critical path, async events for state changes others care about, a contract per API with consumer tests, and every call has a timeout, a retry rule and an idempotency key."

5. Sagas and distributed transactions Ch 48

One line: with no shared database, a business action is a series of local transactions plus compensations for undo. It is eventually consistent, not isolated.

Placing an order touches Orders, Payments, Inventory and Shipping, each with its own database. A classic two-phase commit (2PC) would lock all of them and needs every participant up; it is slow and fragile across services. A saga trades that for local steps. If step 3 fails, run compensations for steps 2 and 1 in reverse.

ChoreographyOrchestration
HowEach service reacts to events and emits the next one.A coordinator (saga orchestrator) tells each service what to do next.
Good forShort flows, 2 to 4 steps, few teams.Longer flows, many branches, need to see the state.
CostThe flow is hidden; cycles are easy to create; hard to debug.A central component to run and keep available; risk of putting business logic in it.

Step types and key rules

  • Compensatable steps can be undone (reserve stock). Pivot step is the point of no return (charge succeeded). Retriable steps after the pivot must be retried until they succeed (send the email, ship).
  • Order work: put steps that are easy to undo or likely to fail first; put the hard-to-undo step last.
  • Persist saga state (a state machine in a database) so it can resume after a crash.
  • Timeouts per step and a deadline for the whole saga. No answer is not a failure, it is unknown: query or retry carefully.
  • Idempotent steps and compensations: they will be delivered more than once.
  • Outbox plus inbox: outbox publishes reliably; inbox (a table of processed message ids) drops duplicates.
  • Missing isolation: other requests can see half-done work. Counter with "semantic locks" (status PENDING), commutative updates, re-reading before acting, and versions.
  • If a compensation fails: retry with backoff, then park it in a dead-letter queue and alert a human. Never drop it silently.
  • Workflow engines (Temporal, Step Functions, Camunda) give durable state, timers and retries for orchestration.
Numbers: typical timeouts per step are seconds; whole sagas often finish in under a second to a few seconds. Human-in-loop sagas can last days, so they must be durable. Aim for under about 5 steps in one saga.
Trap: treating compensation as a perfect rollback (an email sent cannot be unsent; you send an apology or a cancel). Another trap: calling the next service and publishing an event as two unrelated steps, with no outbox.
Say: "I use an orchestrated saga with a persisted state machine, idempotent steps, an outbox for reliable events, and compensations ordered so the risky step comes first. I accept visible intermediate states and design the UI around PENDING."

6. Discovery and configuration Ch 49

One line: instances start and stop all the time, so callers find them through a registry or DNS; configuration and secrets are kept outside the code and changed safely.
PatternHowPros / cons
Client-side discoveryClient asks the registry and picks an instance itself.Fewer hops, smart balancing; every language needs the library.
Server-side discoveryClient calls a load balancer, which knows the instances.Simple clients; extra hop and a component to run.
DNS-basedName resolves to the instances.Universal; caching delays updates.
KubernetesA Service gives a stable name and virtual address; readiness checks decide who gets traffic.Built in; the default today.
MeshThe sidecar handles discovery from the control plane.No code in apps; adds the mesh.
  • Registration: an instance registers and sends heartbeats; if they stop it is removed. Use health checks that test readiness, not just "process is alive".
  • Registries: Consul, etcd and ZooKeeper (consistent, CP) versus Eureka (available, AP). A stale entry is usually better than no registry, so clients should cache the last known list.
  • Failure modes: stale entries send traffic to dead instances (use retries to another instance); registry down (clients keep cached lists); a start-up storm after restart.
  • Config: keep it outside the build, separate per environment, versioned, and rolled out gradually like code. Hot reload is handy but a bad value spreads fast, so validate and canary config.
  • Secrets: use a vault or cloud secret manager; short-lived credentials; never in git or images; rotate without redeploy.
  • Bootstrap problem: to read config you need to find the config service; solve it with a few well-known addresses (DNS name, platform-injected env).
Numbers: heartbeat interval often 5 to 30 seconds; deregistration after 2 to 3 missed beats. DNS caching can hold old answers for the TTL (often 30 to 60 s) or longer if clients ignore TTL.
Trap: a bad config pushed to every instance at once is an outage. Roll config out slowly. Another: liveness probe that checks dependencies, so a database blip restarts every pod.
Say: "On Kubernetes, a Service plus readiness probes is my discovery. Config lives outside the image, is rolled out in stages, and secrets come from a vault with short-lived credentials."

7. Service mesh Ch 50

One line: move retries, timeouts, encryption, routing and metrics out of every app into a proxy next to it, managed from one control plane.

What you get

  • mTLS between all services, with workload identity
  • Retries, timeouts, circuit breaking in one place
  • Canary and traffic split (5%, 25%, 100%)
  • Uniform metrics and traces
  • Authorization rules: who may call whom

What it costs

  • An extra hop: about 1 to a few ms per call
  • CPU and memory per sidecar
  • A complex system to learn and upgrade
  • Misconfigured retries can create storms

Adopt when

  • Dozens of services, many languages
  • You need mTLS and policy across the board
  • A platform team can run it

Skip when

  • A handful of services; libraries are enough
Trap: retries in the app, in the mesh and in the gateway all stacked (3 x 3 x 3 = 27 attempts). Pick one layer for retries. Also: assuming the mesh fixes bad service boundaries.
Say: "A mesh is worth it when many services need the same security and traffic rules. I roll it out namespace by namespace in permissive mode, then enforce mTLS, and I keep retries in one layer."

8. Microservice resilience Ch 51

One line: assume every dependency will be slow or down. Limit damage with timeouts, budgets, breakers, bulkheads, shedding and fallbacks.
ToolWhat it doesGotcha
TimeoutStop waiting after a set time. Set shorter than the caller's own timeout.Missing timeouts are the top cause of cascades. Use a time budget: each hop gets less than its parent.
Deadline propagationPass the remaining time down so work that is already too late is skipped.Needs support in every client.
Retry with backoff and jitterTry again for brief faults.Retry only idempotent calls; cap with a retry budget (for example at most 10% extra traffic); retry in one layer.
Circuit breakerOpen after many failures; fail fast; try again after a pause (half-open).Tune the thresholds; give a useful fallback.
BulkheadSeparate pools per dependency or per caller.Too many pools waste capacity.
Load shedding / priorityReject low-priority work early when overloaded.Reject fast and with a clear code (503 / 429).
FallbackCached or default answer (stale-if-error, default recommendations).Do not fall back for money or stock decisions.
Async decouplingUse a queue so downtime does not block callers.Needs idempotent consumers.
BackpressureTell upstream to slow down (bounded queues, 429).Unbounded queues just hide the problem.
  • Dependency tiers: mark each dependency critical (must have) or optional (can skip). The product page works without recommendations; checkout does not work without payments.
  • Health checks: a readiness check should not call dependencies, or one failure takes everyone out of rotation.
  • Recovery: after an outage, warm caches and ramp traffic slowly to avoid a herd.
  • Test it: fault injection, load tests, game days, chaos experiments.
Numbers: a retry storm: 3 attempts per layer across 3 layers is up to 27 requests for one user action. Little's law: threads in use = rate x latency. If latency goes from 50 ms to 5 s at 200 req/s, you need 100 times more threads than before, so the pool is gone in seconds.
Trap: a default timeout of 30 seconds or none; an infinite queue; a breaker with no fallback (users just see errors faster).
Say: "Every call has a timeout inside a deadline budget, retries with backoff in one layer under a budget, a breaker and bulkhead per dependency, optional dependencies degrade gracefully, and the service sheds load before it falls over."

9. Observability Ch 52

One line: a request crosses many services, so you need one trace id, structured logs, per-service metrics and alerts on user pain.
SignalAnswersNotes
MetricsIs something wrong? How much?Cheap; use RED (rate, errors, duration) per service and USE (utilization, saturation, errors) for resources. Avoid high-cardinality labels such as user id.
LogsWhat exactly happened?Structured JSON with trace id, service, version; central pipeline; do not log secrets or PII.
TracesWhere did the time go across services?Propagate context (W3C traceparent); sample (head or tail) to control cost.
  • Correlation id: created at the edge, forwarded in headers and in message metadata, printed in every log line.
  • Async work: use a "link" from the consumer span back to the producer span since the work is not a simple parent-child call.
  • Sampling: head sampling (decide at start, cheap, may miss rare errors) versus tail sampling (decide at the end, keeps errors and slow ones, costs more memory).
  • Exemplars: attach a trace id to a metric point so you can jump from a latency spike to a real slow trace.
  • Deploy markers: draw deploys on dashboards; most incidents follow a change.
  • Alerting: alert on SLO burn rate and user-facing symptoms, not every CPU blip. Each alert has an owner and a runbook.
  • Dependency map and per-service SLOs show who depends on whom.
Numbers: typical trace sampling is 1% to 10% plus keep all errors and slow traces. Logs usually dominate observability cost, so set levels and retention (for example 7 to 30 days hot).
Trap: a correlation id that is lost at a queue or thread pool boundary; logging every request body (cost and privacy); alerts on causes instead of symptoms.
Say: "Start from the symptom alert, open the exemplar trace, find the slow span, read logs for that trace id, and check deploy markers for what changed."

10. Operating microservices Ch 53

One line: the goal is safe, independent, frequent deploys; the team that builds a service runs it.
  • CI/CD per service: own pipeline, own repo (or own path with its own pipeline), automated tests, one-click rollback.
  • Rollout: rolling, blue-green or canary with automatic rollback on SLO breach. Feature flags separate deploy from release.
  • Backward compatible deploys: deploy the provider that accepts both old and new first; then the consumers; then remove the old path (expand and contract). Database changes the same way.
  • Testing pyramid: many unit tests, some component tests, contract tests between services, a few end-to-end tests. Avoid a giant shared staging end-to-end suite as the only gate. Test in production carefully with canaries, flags, synthetic checks and shadow traffic.
  • Security: mTLS and service identity, least-privilege per service, tokens that carry the user, secrets in a vault, network policy.
  • Ownership: each service has an owner team, an on-call rotation, a runbook and an SLO. Blameless postmortems.
  • Production readiness review: a checklist before launch: health checks, dashboards, alerts, capacity, rollback, data backup, security, runbook.
  • Retire services: deprecate, watch traffic fall to zero, remove. Orphan services cost money and risk.
  • Platform team: a paved road (templates, pipelines, observability defaults) so each team does not reinvent it. Guard against sprawl with a service catalog.
  • DORA metrics: deploy frequency, lead time, change failure rate, time to restore.
Numbers: elite teams deploy many times a day, with change failure rate under about 15% and recovery within an hour. A canary typically takes 1% to 5% of traffic first.
Trap: "who owns this?" services nobody on-call knows; lock-step releases; a shared integration environment that is always broken.
Say: "I measure success by independent deploys and recovery time. Each service has an owner, an SLO, a pipeline with canary and rollback, contract tests, and a runbook."

Say-aloud script (about 60 seconds)

Say: "I would not start with microservices. They trade team independence for operational complexity, so I earn them: first a modular monolith, then I split where there is real pain, such as teams blocking each other or one part needing different scale. I draw boundaries around business capabilities and data ownership, and I migrate with a strangler router so every step can be rolled back. Each service owns its data. For cross-service reads I use local copies or CQRS views from events and accept a small delay. For cross-service writes I use a saga with an orchestrator, idempotent steps, compensations and an outbox, not two-phase commit. Calls are sync only on the critical path, always with a timeout inside a deadline, retries with backoff in one layer, a circuit breaker and bulkhead per dependency, and graceful fallback for optional parts. Discovery comes from Kubernetes, and a mesh gives mTLS and canaries once there are enough services. To run it, I need trace ids everywhere, SLO-based alerts, contract tests, canary deploys with automatic rollback, and a clear owner on call for every service."

Interview Q&A (32)

A. Concepts

1. What is a microservice, and how is it different from just a small service?

A microservice is a service you can release on its own, that owns one business capability and its own data, and talks to others over a network. Size is the least important part. The real tests are: can I deploy it without asking anyone, and does it keep its data private? If two services must always ship together, or three of them read the same tables, they are one system in disguise. A small service that shares a database is not a microservice; a medium-sized service with its own data and its own release is. In the interview I name those two tests first because they show I understand the point is independence, not tiny code.

2. What do microservices give you, and what do they cost?

They give independent releases (a team ships when ready), independent scaling (scale only the hot part), failure isolation (a crash in recommendations need not take down checkout) and freedom to pick tech per service. They cost a lot: every call is now a network call that can be slow, fail halfway or repeat; you lose easy transactions and joins; you need tracing, central logs, service discovery, many pipelines and more on-call work. The honest summary is that you pay operational complexity to buy organizational speed. If you have one small team, you pay without getting the benefit.

3. What is a distributed monolith and how do you spot one?

It is a set of services that are still tightly tied: they must be released together, they share a database, or one change forces edits in five repos. You get network failures and slower calls but none of the freedom. Signs: release trains across teams, a shared "common" library holding business rules, a database table touched by many services, synchronous call chains six deep, and the whole system failing when one small service fails. The cure is to fix the boundaries: give data to one owner, replace some sync calls with events, merge services that always change together.

4. Explain the strangler fig pattern.

You put a router (gateway or proxy) in front of the monolith. For each feature, you build it as a new service and then change the route so that feature goes to the new service while everything else still goes to the monolith. You repeat until the monolith is empty and can be switched off. The big advantages are that each step is small, can be rolled back by flipping the route, and delivers value right away instead of at the end of a big rewrite. You can also run both in parallel and compare answers before switching. I usually start with a part that has few dependencies, like notifications or search, to practise the pipeline before touching the tangled core.

5. How do you decide where to draw service boundaries?

I start from business capabilities and bounded contexts: groups where the same words mean the same thing, found by talking to domain experts. Then I check data ownership (who writes this data?), change history (which files change together in the same commits?) and call graphs (which pairs call each other the most?). A good boundary has high cohesion inside and few calls across. I also check that one team can own it and release it alone. Smells that a cut is wrong are chatty calls, circular dependencies and lock-step releases. I also say that boundaries will be moved later, so I keep them cheap to change, for example by starting in a modular monolith.

6. Why does each service need its own database?

A shared database makes the schema a hidden public API. If I rename a column, every other service may break, so nobody can change anything safely, and the services cannot be released independently. Private data also lets each service pick the right store (SQL, document, search) and scale it alone. The price is that you lose cross-service joins and transactions, so you use APIs, events, local copies, CQRS views and sagas instead. It does not have to be separate database servers on day one; separate schemas with separate permissions can be a first step, as long as nobody reads another service's tables.

7. What is a saga and how is it different from two-phase commit?

Two-phase commit locks resources in every participant, asks them all to "prepare", and then commits everywhere. It gives strong consistency but blocks if the coordinator or one participant fails, and many modern stores and message systems do not support it. A saga splits the business action into local transactions, each committed at once. If a later step fails, earlier ones are undone by compensating actions. The result is eventually consistent and other requests can see the in-between state, but it stays available and scales. In microservices, sagas are the normal choice for cross-service writes.

8. Choreography versus orchestration for sagas: which do you choose?

In choreography each service listens for events and emits the next one; there is no central brain. It is simple for 2 to 4 steps and has no extra component, but the overall flow is spread across services and is hard to see, change or debug, and cycles can sneak in. In orchestration one coordinator holds the saga state and tells each service what to do next. The flow lives in one place, which makes timeouts, retries, branching and monitoring easier, at the price of one more component to keep available. I choose choreography for short, simple flows and orchestration for longer flows with branching, deadlines or human steps. I keep business rules in the services, not in the orchestrator.

9. What is the outbox pattern and what problem does it solve?

The problem is the dual write: a service must save data in its database and also publish an event, and these are two systems, so one can succeed while the other fails. Then the data changed but nobody hears, or an event goes out for data that was never saved. With an outbox, the service writes the data and a row in an "outbox" table in the same local transaction. A separate relay (a poller or change-data-capture) reads the outbox and publishes to the broker, retrying until it works. This gives at-least-once publishing, so consumers must be idempotent, usually by recording processed message ids in an inbox table.

10. How do services find each other?

Instances come and go as they scale and restart, so addresses cannot be hard-coded. In Kubernetes, a Service object gives a stable name and virtual address, and readiness probes decide which pods receive traffic. In other setups, instances register with a registry (Consul, Eureka, etcd) and send heartbeats; callers either look up the list and choose an instance (client-side discovery) or call a load balancer that does it (server-side discovery). DNS can also work but its caching delays updates. A service mesh moves this into the sidecar. Whatever the method, clients should cache the last known list so a registry outage does not stop traffic.

B. Design scenarios

11. Scenario: you have a 10-year-old monolith with 80 engineers. Release takes two weeks. How do you split it?

First I find out the real pain: which modules cause the queues and incidents, and what changes together. I make sure we can already deploy, monitor and roll back well, otherwise splitting will make things worse. Then I enforce module walls inside the monolith (a modular monolith) so dependencies become visible. I pick the first slice with few dependencies and clear value, say notifications or catalog search, and put a gateway in front. I build the new service, run it in parallel to compare results, then move traffic gradually with a rollback switch. For each later slice I first make the code call an API instead of the tables, then split the data with CDC or dual-run, then switch reads, then writes. I track deploy frequency, lead time and change failure rate to prove it is working, and I stop splitting when the pain is gone.

12. Scenario: extract Payments from the monolith. Walk me through it.

Payments is a good candidate: strict compliance, clear data, separate scaling. Step 1: hide payment code behind an interface in the monolith (branch by abstraction). Step 2: build the Payments service with its own database, idempotent endpoints (idempotency key per order) and its own provider integration. Step 3: route a small share of traffic or shadow calls to compare results. Step 4: move the payment tables: copy them with CDC, verify, then make Payments the only writer. Step 5: Orders now talks to Payments over an API or events and handles "payment pending", "failed" and "unknown" states, because it is no longer one transaction. Step 6: remove the old code. Throughout, keep the old path for rollback until metrics are stable.

13. Scenario: the "My orders" page needs data from Orders, Payments and Shipping. How do you build it?

Options: call all three at request time and merge (API composition), or keep a ready-made view. Composition is simplest but slow and fragile: three calls, and the page fails or slows if any one does. For a high-traffic page I build a read model: a builder subscribes to order, payment and shipping events and writes one row per order into a fast store. The page does one lookup. The view is a few seconds behind, so I show a status like "payment processing" and let the page fall back to a direct call for the order the user just placed (read-your-writes). The builder is idempotent and can be rebuilt from the event log if the view is wrong.

14. Scenario: design the order placement flow across Orders, Inventory, Payments and Shipping.

I use an orchestrated saga. Orders creates the order as PENDING and starts the saga. Step 1 reserves stock in Inventory (compensation: release). Step 2 charges the card in Payments with an idempotency key (compensation: refund). That is the pivot. Step 3 creates a shipment, which is retriable and must eventually succeed. After step 3 the order becomes CONFIRMED. If payment fails, the orchestrator releases stock and marks the order FAILED. Each step is idempotent, each message goes through an outbox, state is stored so the saga resumes after a crash, and each step has a timeout. I put the cheap, reversible step first and the money step as late as possible before the point of no return.

15. Scenario: how do you add a new field to an API used by 12 other services?

Add it as optional, so no existing caller breaks, and make consumers tolerant readers that ignore unknown fields. Publish the change and let consumers adopt it. If the change is breaking (rename, removal), use expand and contract: add the new field beside the old and fill both, move consumers over one by one (tracked by metrics on who still uses the old one), and finally remove the old field after a deprecation date. Consumer-driven contract tests tell me, before I deploy, whether any consumer relies on what I am about to change. That is how 12 teams stay independent without a coordinated release.

16. Scenario: you must choose between REST, gRPC and messaging for a new internal call.

I ask if the caller needs the answer to continue. If not (notify, update a search index, fan-out to many), use messaging: it decouples availability and absorbs spikes. If yes and it is a high-volume internal call where latency and typed contracts matter, gRPC. If it is a public or lightly used API or humans need to debug it, REST. For client-facing aggregation I would add a BFF or GraphQL layer. I also check call depth: if it creates a sync chain of more than three hops, I rethink the boundary or use local copies.

17. Scenario: how do you handle config and secrets safely across 100 services?

Config is kept out of the image in a central store, per environment, versioned and reviewed like code. Changes roll out gradually (a canary percentage first) because a bad value pushed everywhere at once is a global outage; I add validation and an easy revert. Secrets come from a vault or cloud secret manager, are fetched at start or on rotation, are short-lived where possible and never stored in git or logs. Each service has its own identity and can read only its own secrets. For bootstrap I use a platform-injected address or DNS name for the config store, so the service can find it at startup.

C. Failures and real-time production scenarios

18. Incident: a payment call times out. Did the customer get charged? How do you handle it?

A timeout is "unknown", not "failed". The charge may have gone through. So I never just retry blindly and I never just fail the order. Every payment request carries an idempotency key, so retrying the same request returns the original result and cannot charge twice. After a timeout the saga marks the step as pending and either retries with the same key or queries the provider's payment status by that key. If still unknown after a limit, the order stays in a "payment pending" state, a reconciliation job compares our records with the provider's, and if a charge exists without an order, we complete the order or refund. The customer sees "processing", not a duplicate charge.

19. Incident: a saga stops half way (orchestrator crashes after charging but before shipping). What now?

This is why saga state is persisted. When the orchestrator restarts it loads unfinished sagas from its database and continues from the last recorded step. Because steps are idempotent, repeating the "create shipment" call is safe. Since payment was the pivot, the remaining steps are retriable, so we keep retrying (with backoff) rather than refunding. If it still cannot finish within a deadline, an alert goes to a human with the saga id and a dashboard of stuck sagas. A periodic sweeper that finds sagas with no progress for N minutes is a safety net. I also test this exact crash in a game day.

20. Incident: a compensation fails (refund call errors). What do you do?

A failed compensation is the most dangerous state because money or stock is wrong. First, compensations must be idempotent and retriable, so I retry with exponential backoff for a bounded time. If it keeps failing, I move the task to a dead-letter queue, mark the saga as "needs manual action", and page someone, with all details to fix it by hand. I never silently drop it. I also add a reconciliation job that finds orders where state in Orders and Payments disagree. In design, I reduce the chance by ordering steps so the compensation of the risky step is easy, and by making the compensation call a different, simpler code path than the original.

21. Incident: cascading failure. One service gets slow and then the whole site is down. How do you stop it now, and how do you prevent it?

Now: find the original slow service from the dependency map and traces, then cut its blast radius. Open the circuit breaker or turn off the caller feature with a flag, shed non-critical traffic, stop retries (reduce the retry budget), scale or roll back the bad deploy, and restart only if pools are stuck. Prevention: timeouts on every call shorter than the caller's own, a deadline budget through the chain, a circuit breaker and a bulkhead per dependency so one slow dependency cannot eat all threads, retries with backoff and a budget in one layer, load shedding when queues grow, and fallbacks (cached or default data) for optional dependencies. Also test it with fault injection so we find missing timeouts before customers do.

22. Incident: a retry storm after a short outage keeps the service down. Why and how do you fix it?

When a service recovers, all callers retry at once, plus new traffic, so load can be several times normal and it falls over again. If retries are nested in three layers, each failure becomes 3 x 3 x 3 attempts. Fixes: retries only in one layer, exponential backoff with random jitter, a retry budget (retries allowed only as a small share of normal traffic), circuit breakers that stay open for a while, load shedding on the server, and a slow ramp-up (warm-up, gradual traffic return) after recovery. Short term, I temporarily cut traffic (rate limit at the gateway) so the service can come back, then raise it slowly.

23. Incident: data is inconsistent between two services (order says PAID, payments says no record). How do you investigate and fix it?

I take the order id and follow its trace id and logs across Orders, the bus and Payments, looking for the first point where they diverge. Common causes: an event published but never consumed (dead-letter queue), a consumer that is not idempotent and rejected a duplicate wrongly, a dual write without an outbox, an out-of-order event overwritten by an old one, or a deploy that changed the event format. To fix the data, I replay events from the log for that range or run a repair job, guided by the owner's data as the source of truth. To fix the cause I add an outbox, idempotency, version numbers on events, a dead-letter alert, and a reconciliation job that continuously compares both sides and reports mismatches.

24. Incident: a deploy of Service A broke Service B, though tests passed. What was missed?

Probably an unnoticed breaking change in a contract: A removed or renamed a field, tightened validation, or changed an error code, and B relied on it. Unit tests in each repo cannot see this. I stop the bleed first: roll back A (it should be one click) or turn off the flag. Then I add consumer-driven contract tests so A's build fails if it breaks B's expectations, and I make B a tolerant reader. For the process, I use canary deploys with automatic rollback on error rate, and the expand and contract method for any breaking change, so old and new shapes are supported together while consumers move.

25. Incident: p99 latency of checkout doubled after midday, no errors. How do you debug it?

I start with the symptom dashboard, then look at an exemplar or sampled slow trace for checkout, and read the waterfall to see which span grew. I compare with deploy markers to see what changed near that time. If one downstream (say Inventory) is slow, I look at its own metrics: saturation (CPU, pools, queue depth), database slow queries, cache hit ratio dropping. I also check whether retries or a new caller increased load. A fix might be to roll back, add cache, scale out, or add a timeout and fallback. Afterwards I write down the finding and add an alert on the slow-span behaviour.

26. Incident: the service registry or config service is down. What happens?

Good design means running services keep going. Clients cache the last list of instances, so calls continue; new instances may not register and dead ones may not be removed, so retries to another instance are needed. Config is read at startup and cached, so existing pods keep their values; the risk is new pods that cannot start because they cannot fetch config, so I keep a last-known-good copy baked or cached. I make the registry highly available (3 or 5 nodes with consensus) and I decide per tool whether it favours consistency or availability; for discovery, availability usually wins.

27. Incident: mTLS certificates expired across the mesh. Why, and how do you avoid it?

Likely the certificate authority or the rotation job failed silently, so short-lived workload certificates were not renewed and proxies began rejecting each other. Immediate action: restore the CA or renewal component, force-renew certificates, and if needed temporarily switch the mesh to permissive mode so plain traffic is allowed while you fix it (a conscious, tracked exception). Prevention: monitor certificate expiry with alerts well ahead, alert when rotation fails, test rotation regularly, keep the control plane highly available, and practise the recovery procedure.

D. Trade-offs and why-questions

28. Why not start with microservices from day one?

Because at the start you do not know the right boundaries, and moving a boundary inside one codebase is cheap while moving it across services means changing APIs, data and teams. A small team also gets little from independent deploys but pays the full price of networks, tracing, many pipelines and eventual consistency. You will move faster with a well-structured modular monolith, and you can split later when real pain shows. There are exceptions: strong compliance isolation, or a team that has the platform already built. I describe it as "monolith first, with clean seams".

29. Why prefer events and local copies over synchronous calls between services?

With a sync call the caller's availability is the product of every dependency, latency adds up, and failures flow upward. With events and a local copy, the caller reads its own data, which is fast and works while the owner is down. The cost is that the copy can be stale and you need to handle ordering, duplicates and rebuilds. So I use local copies for data that changes slowly and tolerates a small delay (product names, user display names), and sync calls where I need the latest truth (current stock at purchase time, payment authorization).

30. Sagas versus two-phase commit: when would you ever use 2PC?

2PC is acceptable inside one organization's system when all participants support it (for example several databases of the same engine), the transaction is short, and strong consistency is a must. It does not suit many independently owned services, message brokers, or external parties like a card network. For those, a saga is the realistic answer, with careful design for visible intermediate states. If an interviewer pushes for strict consistency, I try to move the entire invariant into one service so a local transaction is enough, which is usually the best answer of all.

31. Is a service mesh worth it? Library versus mesh for resilience?

A library (such as a client with retries and breakers) is cheap, in-process and fast, but needs a version per language and every team must upgrade it. A mesh puts the same behaviour in a sidecar for all languages, adds mTLS, traffic splitting and uniform metrics, and is controlled centrally. The mesh costs extra hops and resources, and a new complex thing to run and debug. With under about 10 to 20 services in one or two languages I would use libraries and platform defaults. With many services, many languages, and security rules like "all traffic encrypted and authorised", the mesh pays off. In both cases I keep retries in one layer.

32. How do you know whether the microservices migration worked?

I measure outcomes, not service counts. The delivery numbers: deploy frequency should go up, lead time from commit to production should go down, change failure rate should not rise, and time to restore should shrink. I also check that teams can release without asking others (the number of cross-team release dependencies) and that on-call load is acceptable. Cost per request and infrastructure bill are tracked too, since microservices can raise them. If the metrics do not improve, or services must still ship together, then the split is wrong and I merge or fix boundaries. Some companies have moved back to larger services, which is fine when the data says so.
