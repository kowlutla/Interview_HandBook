0. Key definitions (know these cold)

TermDefinition
Access patternA question the app asks the data over and over ("get the last 50 messages of chat X"). Design the data around these questions first.
NormalizationStoring each fact in exactly one place and pointing to it by id. Prevents the copies from disagreeing. Costs joins when reading.
DenormalizationKeeping copies of data on purpose so one read is enough. Faster reads, but you must keep the copies in sync.
IndexA sorted side structure (usually a B-tree) that lets the database find rows without reading the whole table. Like the index at the back of a book.
B-treeA shallow, wide, sorted tree of disk pages. Finds a key in 3 to 4 page reads even with billions of rows. Updates pages in place.
LSM treeLog-structured merge tree. Writes go to memory plus a log, then are flushed as sorted immutable files that are merged later. Very fast writes.
WAL (write-ahead log)An append-only file where a change is written first, before the real data pages. After a crash the database replays it. This is how "committed" survives power loss.
ACIDAtomic (all or nothing), Consistent (rules hold), Isolated (concurrent transactions do not trip each other), Durable (committed means saved).
Isolation levelHow much one running transaction can see of another's work. Read committed, repeatable read, serializable are the common ones.
MVCCMulti-version concurrency control. Keep several versions of a row so readers do not block writers. Old versions are cleaned up later (vacuum).
ShardingSplitting one big dataset across many servers by a key. Each server holds a slice (a shard).
Partition keyThe field whose hash decides which server holds a row. Choose it so load spreads evenly and the common query touches one partition.
Hot partitionOne partition that gets far more traffic than the others, so it becomes the bottleneck while other servers sit idle.
Write amplificationHow many bytes the disk really writes for each byte the app writes. B-trees and LSM trees both have it, in different ways.
CompactionThe background job in an LSM tree that merges sorted files, drops old versions and deleted keys, and keeps reads fast.
TombstoneA small marker that says "this key is deleted". Needed because immutable files cannot be edited. The real data goes away at compaction.
Bloom filterA tiny in-memory structure that says "definitely not here" or "maybe here". Lets an LSM read skip most files.
Object storageA huge, cheap, very durable store of whole files (objects) addressed by key over HTTP (like S3). You cannot edit part of an object; you replace it.
Erasure codingSplitting data into k data pieces plus m parity pieces so any k pieces rebuild it. Like RAID across servers. Cheaper than keeping 3 full copies.
Inverted indexA map from each word to the list of documents containing it. The core of search engines. The reverse of "document to words".
AnalyzerThe text pipeline (split into words, lowercase, remove endings) used when indexing and searching so "Running" matches "run".
OLTP vs OLAPOLTP: many small reads and writes of single records (orders). OLAP: few big queries scanning huge amounts of data (monthly revenue).
CDC (change data capture)Reading the database's own change log to feed other systems (search, cache, warehouse) without dual writes.
Vector databaseA store that finds the items whose number-lists (embeddings) are closest to a query, for "find similar" and AI retrieval.

1. Data modeling Ch 17

One line: list the questions the app must answer (reads and writes, with rates), then shape the tables or documents so each important question is one cheap lookup.

Procedure. (1) Write the access patterns with how often each runs and how fast it must be. (2) Find the entities (users, orders, messages) and how they relate: one to one, one to many, many to many. (3) Pick keys. (4) Normalize first, then denormalize only where a measured read path needs it. (5) Plan how the data grows, is deleted, and changes shape over time.

DecisionChooseWhen not
Normalize (3NF)Default for OLTP data that changes: orders, accounts, inventoryRead paths that join 5+ tables at high rate
DenormalizeA hot, read-heavy path; counters; feed rows; data that is a snapshot in timeFields that change often and must be right everywhere
Embed (document store)Child data read together with parent and bounded in size (order lines)Unbounded lists (all comments of a viral post), or children read alone
Reference by idShared, large or fast-changing child dataNeeds a join the store cannot do cheaply
Many-to-manyA join table (user_id, group_id) with a unique key and an index in each directionStoring an array of ids in a column when you must query the reverse direction

Keys, ids, time and deletes

  • Surrogate vs natural key. A surrogate is a meaningless generated id; a natural key is a real attribute such as an email. Prefer surrogate ids because natural keys change. Keep a unique constraint on the natural key.
  • Which id. Auto-increment is small and ordered but leaks counts and does not work across shards. Random UUIDv4 spreads writes but scatters B-tree inserts. Time-ordered ids (UUIDv7, ULID, Snowflake) are unique without coordination and roughly sorted, which is friendly to B-trees.
  • Idempotency. A unique key on a client-supplied request id turns a retried "create order" into a harmless duplicate rejection.
  • Time. Store timestamps in UTC; convert at the edge. Keep the user's time zone name separately if local time matters.
  • Deletes. Soft delete (a deleted_at flag) allows undo and audit but every query must filter it and unique keys get awkward. Hard delete is required for privacy law. In LSM and wide-column stores a delete is a tombstone, and too many tombstones slow reads.
  • History. For audit, write an append-only history table or event log instead of overwriting; for expiry use TTL or partition drops, not giant delete jobs.
  • Status fields. Model a status as a small state machine (created, paid, shipped) and allow only legal transitions, with a conditional update.
  • JSON columns. Good for sparse, flexible attributes; bad for fields you filter on a lot (index them or promote them to real columns).
  • Multi-tenant. Put the tenant id first in the key and in every index so one tenant's data is together and cannot leak. Keep PII (names, emails) in a separate table so it can be encrypted, restricted or erased.
  • Counters and aggregates. A likes count is derived data. Keep it as a separate counter updated asynchronously, not a COUNT(*) on every page view.
Sharding key rule: the shard key must (1) appear in the common query so one shard answers it, (2) have many distinct values, (3) not make one value hot. Example: orders by user_id is good; orders by created_date is bad (today's shard takes all writes).
Traps: designing tables before listing queries; one giant "status" column that means five things; unbounded arrays inside a document; shard key chosen for convenience (country, date) that creates a hot shard; storing money as floating point (use integer cents or decimal).
Say: "I start from the access patterns and rates, normalize the source of truth, and denormalize only the measured hot read paths, with a clear owner for keeping each copy in sync."

2. Relational internals Ch 18

One line: a relational database parses SQL, picks a plan using statistics, reads pages through a memory cache, and protects data with a write-ahead log and transaction rules.

Indexes

Index ideaWhat it meansGotcha
Clustered (primary)Table rows are stored in key order inside the index itself (InnoDB). Lookup by primary key is one tree walk.Random primary keys cause page splits; big primary keys bloat every secondary index
SecondarySeparate tree from column value to primary key or row pointer. Needs a second hop to fetch the row.Each one slows every write and uses space
CompositeIndex on (a, b, c). Works for a; a,b; a,b,c (leftmost prefix). Put equality columns first, then the range or sort column.Not usable for b alone
CoveringThe index holds every column the query needs, so the table is never touched (index-only scan).Wider indexes cost more on writes
Partial / expressionIndex only some rows (WHERE active) or a computed value (lower(email)).Query must match the same expression
Hash, GIN, GiST, etc.Equality only; full-text or array contents; geo ranges.Pick for the query type, not by habit

When the index is not used: a function on the column (WHERE lower(email)=... with a plain index), a leading wildcard (LIKE '%abc'), a type mismatch, low selectivity (the filter matches most rows so a scan is cheaper), stale statistics, or OR conditions across columns. Check with EXPLAIN.

Join algorithms: nested loop (good for few outer rows plus an index on the inner), hash join (builds a hash of one side; good for big unsorted inputs), merge join (both sides sorted). N+1 problem: one query for a list, then one query per row. Fix with a join or a batched IN query.

Transactions and isolation

LevelPreventsStill possible
Read committedDirty reads (seeing uncommitted data)Non-repeatable reads, phantoms, lost updates, write skew
Repeatable read / snapshotNon-repeatable reads (you see one snapshot)Write skew (and phantoms in some engines)
SerializableAll anomalies; acts as if run one by oneMore aborts or locking, lower throughput
  • Lost update: two transactions read the same value, both write; one write vanishes. Write skew: two transactions each check a rule on different rows and both pass, but together break it (two doctors both go off call).
  • MVCC keeps old row versions so readers never block writers. Postgres leaves old versions in the table until VACUUM cleans them (bloat if vacuum falls behind or a long transaction blocks it). InnoDB keeps old versions in an undo log.
  • Locks and deadlocks. Two transactions each waiting for the other's lock. Databases detect this and abort one. Prevent by taking locks in a consistent order and keeping transactions short.
  • Pessimistic vs optimistic. Pessimistic: SELECT ... FOR UPDATE locks the row first. Optimistic: read a version number, update with WHERE version=old, retry if 0 rows changed. Optimistic wins when conflicts are rare.
Inventory example (best answer): UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0. One atomic statement; if 0 rows changed, it is sold out. Beats read-then-write, which loses updates under concurrency. For one extremely hot row, split the count into N sub-counters or queue the requests.

Scaling a relational database

StepWhatLimit

Traps: reading from a replica right after a write (read-your-writes broken); a long-running transaction that blocks vacuum or holds locks; adding an index for every column; running a schema migration that locks a big table (use online, step-by-step migrations); too many connections.
Say: "I would keep this in Postgres: the data is relational and needs transactions. I would index for the access paths, pool connections, add read replicas with a read-your-writes rule, and shard by tenant or user only when one primary cannot take the writes."

3. Storage engines: B-tree vs LSM Ch 19

One line: B-trees update pages in place and read fast; LSM trees only append and merge, so they write fast but pay in background work and slower reads.

Why disks shape everything. Reading in order (sequential) is far faster than jumping around (random), and storage works in pages (often 4 to 16 KB), so engines try to turn many small random writes into big sequential ones. RAM is roughly 100 ns, an SSD read about 100 microseconds, and a spinning disk seek about 10 ms.

B-tree (Postgres, MySQL InnoDB)LSM tree (RocksDB, Cassandra, HBase, LevelDB)
WriteFind the page, change it in place, log to WAL. Page splits. Random I/O.Append to log, insert in memory, flush sequentially. Very fast.
ReadOne tree walk, predictable, 3 to 4 pagesMay check memtable plus several files; Bloom filters help
Write amplificationModerate (page rewrite plus WAL, doublewrite)High over time from repeated compaction (often 10x or more)
SpaceSome waste from half-full pagesOld versions linger until compaction (temporary extra space)
Range scansExcellent (leaf pages linked)Good after compaction; merges many files
Best forMixed read/write OLTP, point reads, transactionsWrite-heavy, logs, time-series, messaging, huge ingest
Worry aboutRandom write cost at high rates, bloatCompaction stalls, tombstones, read latency spikes

Three amplifications trade against each other: read amplification (how many places a read looks), write amplification (extra bytes written), space amplification (extra bytes stored). You cannot minimise all three; pick for the workload.

  • Durability. A write is only safe after fsync (asking the OS to push data to the device). fsync is slow, so engines batch it (group commit). A "torn write" (half a page written at power loss) is why InnoDB has a doublewrite buffer and why pages carry checksums.
  • Row vs column layout. Rows are stored together (good for fetching one record, OLTP). Columns stored together compress very well and let a query read only the few columns it needs (good for OLAP, warehouses).
  • In-memory engines (Redis, Memcached) are fast because there is no disk on the read path; persistence uses snapshots or an append log.
Numbers: B-tree depth for billions of rows is about 3 to 4 levels (each page holds hundreds of keys). A Bloom filter with about 10 bits per key gives about 1% false positives. SSD-based RocksDB commonly does hundreds of thousands of writes per second per node.
Traps: choosing LSM for a read-heavy workload with random point reads and no Bloom filters; ignoring compaction disk budget (you need headroom, often 30 to 50% free space); piling up tombstones (queue-like delete-heavy tables); random UUID primary keys in a B-tree.
Say: "For a write-heavy time-series or message store I would pick an LSM-based engine, accepting compaction cost and slightly slower reads; for a general transactional store a B-tree engine gives predictable reads and good range scans."

4. NoSQL families Ch 20

One line: NoSQL stores give up joins and often multi-row transactions to get easy horizontal scale and a data model that fits one access style; pick the family from the access pattern.
FamilyExamplesModelPick it whenAvoid when
Key-valueRedis, DynamoDB, Riakkey to opaque valueSessions, carts, profiles by id, caches, feature flagsYou need queries on value fields or joins
DocumentMongoDB, Couchbase, DynamoDB docsJSON-like documents with nested dataVaried shapes, read the whole object together, catalogs, CMSHighly relational data with many cross-links
Wide-columnCassandra, HBase, Bigtablepartition key + clustering key + columns; sorted within a partitionHuge write rates, time-ordered data, messages, events, known queriesAd-hoc queries, strong transactions, small data
GraphNeo4j, Neptunenodes and edgesFriends-of-friends, fraud rings, recommendations, deep pathsSimple lookups; huge sharded graphs are hard
Time-seriesPrometheus, InfluxDB, TimescaleDBseries (name + labels) of timestamped pointsMetrics, sensors; downsampling and retention built inGeneral records; very high label cardinality

Wide-column and Dynamo-style design

  • Partition key decides which node holds the data (by hash). Clustering key decides the sort order inside the partition. A query for one partition with a clustering range is fast and sequential.
  • Query-first modeling: one table per query, with copies of data. Example: chat messages table with partition key (chat_id, time bucket) and clustering key message_id descending.
  • Unbounded partition is a classic bug (one partition grows forever). Bucket by time (chat_id + month) to cap it.
  • Tunable consistency (Cassandra-style): with N replicas, write to W and read from R. If R + W is greater than N, the read overlaps the latest write (quorum). Example N=3, W=2, R=2. Lower values give speed and availability, weaker consistency.
  • Why writes are fast: LSM tree underneath (see section 3).

DynamoDB essentials

  • Items live in partitions chosen by hashing the partition key; an optional sort key orders items within it. Reads by key are single-digit milliseconds at any scale.
  • GSI (global secondary index): another partition and sort key, separate storage, eventually consistent. LSI: same partition key, different sort key, must be defined at table creation.
  • Hot partition: one key takes too much traffic; fix with a better key or write sharding (key + random suffix 1..N).
  • Capacity: on-demand (pay per request, spiky or unknown load) or provisioned (cheaper when steady). Transactions exist but cost double and are limited in size.
  • Single-table design: store several entity types in one table with generated keys so one query fetches related items. Fast, but hard to evolve; use when access patterns are known and fixed.
Numbers: DynamoDB has a per-partition limit of about 3,000 read units and 1,000 write units per second, and an item size limit of 400 KB. Cassandra partitions should stay under about 100 MB. Keep MongoDB documents under 16 MB (and far smaller in practice).
Traps: using MongoDB like SQL (normalized with many lookups); a low-cardinality or date-only partition key; unbounded partitions; too many secondary indexes (each one is extra writes and, in Cassandra, scatter-gather reads); picking NoSQL only because it is "web scale" when Postgres would do.
Say: "I pick the store from the access pattern. Known key lookups at huge scale: DynamoDB or Cassandra, designed query-first. Relational and transactional: Postgres. I will not mix without a sync story: CDC from the source of truth."

5. Object storage Ch 21

One line: object storage (S3, GCS, Azure Blob) keeps whole immutable files in a flat key space over HTTP, very cheap and extremely durable; you keep the file in object storage and its metadata in a database.
TypeWhat you getUse for
BlockA raw disk volume attached to one serverDatabase disks, boot volumes
FileShared folders, paths, locks, edit in place (NFS)Shared home dirs, legacy apps
ObjectBucket + key + bytes + metadata, whole-object read/replace, HTTPImages, video, backups, logs, data lakes, static sites
  • Flat namespace. "folders" are only key prefixes (photos/2026/a.jpg). There is no real rename: it is copy then delete. Listing is by prefix.
  • Immutable objects. You cannot edit bytes in the middle. A write replaces the whole object. Versioning keeps old copies; object lock prevents deletion for a period.
  • Range reads fetch part of an object (video seeking, resume download). Conditional requests (ETag, If-Match) avoid overwriting someone else's change. Presigned URL: a temporary signed link that lets a client upload or download directly, so big bytes skip your servers.
  • Multipart upload: split a big file into parts (for example 8 to 100 MB each), upload in parallel, retry only failed parts, then complete. Faster and resumable.
  • Dedup by hash: hash the content (SHA-256); if that hash exists, skip the upload and add a reference.
  • Consistency: modern S3 gives strong read-after-write for new objects and overwrites, and strong list consistency.
Durability methodOverheadProsCons
3x replication3x storageSimple, fast reads, easy repairExpensive for cold data
Erasure coding 6+31.5x storage (9 shards for 6 data)Survives any 3 lost shards; about 12 nines in the handbook estimate, better than 3x copies at half the costRepair reads many shards; reconstruct adds latency
HybridHot data replicated, aged data erasure-codedBest cost and speed balanceBackground conversion work
  • Metadata is the hard part. It must be strongly consistent and sharded by key range (so prefix listing works). Data nodes just store chunks.
  • Integrity. Checksums on every chunk; background scrubbing re-reads and verifies; repair rebuilds lost shards. Wait a bit before repairing after a node vanishes, since many outages are short.
  • Delete. Mark in metadata first, then garbage collect the chunks later (also reclaims failed multipart parts, so set a lifecycle rule to abort incomplete uploads).
Numbers: S3-class durability is stated as 11 nines per year; availability about 99.9% to 99.99%. Typical object up to 5 TB; single PUT up to 5 GB, so multipart above that (and sensible above 100 MB). Latency tens of milliseconds first byte. Cost: roughly a couple of cents per GB-month for standard class, much cheaper for archive.
Traps: using object storage as a database or a filesystem (no append or partial edit, slow per-object metadata ops); millions of tiny objects (request cost and slow); routing big uploads through your own servers instead of presigned URLs; forgetting lifecycle rules and versioned-bucket cost; storing files inside the SQL database.
Say: "Files go to object storage through presigned multipart uploads; the database stores the object key, size, hash and owner. Serving goes through a CDN. Old data moves to cheaper tiers by lifecycle rules."

6. Search engines Ch 22

One line: a search engine (Elasticsearch, OpenSearch, Solr over Lucene) builds an inverted index from words to documents, ranks results by relevance, and spreads shards across a cluster. It is a derived copy for searching, not your source of truth.

Why not just SQL LIKE? A query like LIKE '%shoes%' cannot use a normal index, so it scans every row. It also has no ranking, no stemming ("running" matches "run"), no typo tolerance and no fast faceting.

ConceptSimple meaning
AnalyzerSame text pipeline at index and query time; mismatch means "no results" surprises
Relevance (BM25)Score rises with how often the term appears in the document, falls for common words, and adjusts for document length
SegmentImmutable chunk of index files; new documents make new segments, merged in the background (same idea as LSM)
RefreshMakes new documents searchable (about every 1 second by default): this is why search is near-real-time, not instant
Translog / flushLog for durability between refresh and a full commit to disk
Shard / replicaPrimary shard splits data; replicas copy it for failover and more read capacity. Shard count is fixed at index creation (reindex to change).
MappingThe schema: field types. Dynamic mapping can explode field counts and guess types wrongly.
AliasA stable name pointing to an index; swap it for zero-downtime reindexing
ILM / time-based indicesOne index per day or month for logs; roll over, shrink, then delete old ones cheaply
search_afterCursor-based deep paging; from+size paging gets slow and memory-heavy for deep pages
  • Keeping it in sync: the source of truth is the database. Feed search through CDC or a queue (outbox pattern), with idempotent upserts by document id and versioning so an old event cannot overwrite a newer one. Keep a full reindex path for repair.
  • Shard sizing: aim for shards of roughly 10 to 50 GB. Too many tiny shards waste memory and slow the cluster (the "too many shards" problem); a few giant shards recover slowly.
  • Why not a primary DB: no real transactions, near-real-time visibility, split-brain and data-loss risks historically, and mapping changes need reindexing.
  • Alternatives: database full-text (Postgres tsvector) for small cases; vector search for meaning-based retrieval; Algolia/Typesense for hosted simplicity.
Numbers: refresh about 1 s. Shard target 10 to 50 GB. Heap about half of RAM, with a ceiling near 30 GB so pointers stay compact. Deep paging default limit 10,000 results (from + size).
Traps: treating the search index as the only copy of data; dynamic mapping on user-supplied keys (mapping explosion); one shard per tiny index; deep pagination with from/size; heavy wildcard queries that start with *; expecting a write to be searchable instantly.
Say: "Writes go to Postgres. A CDC stream updates Elasticsearch with idempotent versioned upserts. Search is near-real-time, and reindexing is a swap of an alias, so I can always rebuild the index from the source of truth."

7. Other specialized stores Ch 23

One line: when one workload dominates (analytics, huge files, metrics, similarity, audit), a purpose-built store beats a general database; feed it from the source of truth through CDC or a stream.

  • Warehouse loading: ETL (transform first) vs ELT (load raw, transform inside the warehouse). Modern default is ELT.
  • Approximate vector search: HNSW is a layered graph that finds near neighbors fast; recall (how many true neighbors it finds) trades against speed and memory.
  • Capacity habit: compute raw data per day, replication factor, and retention to size the cluster in your estimate.

8. Say-aloud script (45 seconds in an interview)

  1. "First I list the access patterns with their rates: what is read by id, what is searched, what is aggregated."
  2. "The core business data, such as orders and accounts, goes into Postgres: it needs transactions, constraints and joins. I index for the hot queries and pool connections."
  3. "If writes outgrow one primary, I add read replicas first, then shard by user or tenant id, avoiding hot keys. For a very write-heavy log-like workload, I would use an LSM-based store such as Cassandra, modeled query-first with bounded partitions."
  4. "Images, video and exports go to object storage with presigned multipart uploads; the database keeps only the key and metadata; a CDN serves reads."
  5. "Search is a derived Elasticsearch index fed by CDC with idempotent upserts. It is near-real-time and always rebuildable from the source."
  6. "Analytics runs in a columnar warehouse fed from the same change stream, so reports never load the OLTP database."
  7. "For each store I state its consistency and how stale it can be."

9. Interview Q&A (detailed answers)

Click a question to open the answer. Grouped as: concepts, design scenarios, failure and real-time (production) situations, and trade-off or "why" questions.

A. Concept questions

1. How do you approach data modeling in a system design interview?

I start from the access patterns, not from the tables. I write down what the app must read and write, how often, and how fast. Then I list the entities and relationships, choose keys, and begin with a normalized model for the source of truth so each fact lives in one place. After that I denormalize only the read paths that I can show are too slow or too expensive with joins, and I say who keeps each copy up to date. I finish with growth: which tables get big, how old data is expired, and what the shard key would be. This order keeps the design honest and gives the interviewer clear places to probe.

2. Normalization vs denormalization: what are the trade-offs?

Normalization stores each fact once and links by id, which prevents copies from disagreeing and keeps updates cheap and simple. The cost is that reads need joins, and joins get expensive at scale or across shards. Denormalization duplicates data so a read is a single lookup, which is faster, but every update must change all copies, and a failure can leave them different. So I normalize writes and the source of truth, and denormalize for hot reads, using a derived table, cache or search index that can be rebuilt. A snapshot, such as the price or address at order time, is different: it is meant to stay frozen, so it is not duplication.

3. What does an index do and what does it cost?

An index is a sorted structure, usually a B-tree, that maps column values to rows so the database can jump to matching rows instead of scanning the whole table. A lookup in a table of billions takes only 3 to 4 page reads. The costs are extra disk and memory, and slower writes, because every insert, update or delete must also update each index. Indexes help most when the filter is selective, that is, it matches a small fraction of rows. So I index for the real queries and avoid indexing every column.

4. Explain composite indexes and the leftmost prefix rule.

A composite index on (a, b, c) is sorted by a, then b within a, then c within b. It can answer queries that filter on a, or on a and b, or on all three, but not queries on b alone, because b alone is not sorted across the whole index. I put the columns with equality filters first and the range or sort column last, so the index serves both the filter and the ORDER BY. A covering index adds the selected columns so the database never reads the table at all. I verify with EXPLAIN and not by guessing.

5. What is ACID and what does each letter really protect?

Atomicity: a transaction fully happens or fully does not, so a crash in the middle of a transfer does not leave money removed but not added. Consistency: the database rules (constraints, foreign keys) hold after each transaction. Isolation: concurrent transactions do not see each other's half-done work in harmful ways; how strong this is depends on the isolation level. Durability: once committed, the data survives a crash, which the write-ahead log and fsync provide. In practice, atomicity and durability come from the log, and isolation comes from locks or MVCC.

6. What are the isolation levels and which anomalies do they allow?

Read committed prevents dirty reads, but a row you read twice can change between reads, and a count can change as new rows appear. Repeatable read or snapshot gives you one consistent view for the whole transaction, but write skew can still happen: two transactions check a rule on different rows and both succeed, together breaking the rule. Serializable behaves as if transactions ran one after another and prevents everything, at the price of more aborts or locks. Most systems default to read committed, and I raise the level or use explicit locks or atomic conditional updates only where correctness needs it.

7. What is MVCC and why does Postgres need vacuum?

MVCC keeps several versions of a row so readers see a consistent snapshot without blocking writers. In Postgres an update writes a new row version and leaves the old one in the table, so dead versions pile up. VACUUM reclaims the space and also keeps transaction ids from wrapping around. If vacuum cannot keep up, often because of a long-running transaction that still needs old versions, the table and indexes bloat and queries slow down. InnoDB instead keeps old versions in an undo log. I would mention monitoring bloat and long transactions.

8. B-tree vs LSM tree: how do they differ?

A B-tree keeps sorted pages on disk and updates them in place, with a write-ahead log for safety. Reads are predictable and range scans are good, but random in-place writes are costly at very high write rates. An LSM tree writes to a log and an in-memory table, then flushes sorted immutable files and merges them in the background (compaction). Writes are fast and sequential, but reads may check several files and compaction adds background I/O, so write amplification can be high. I pick B-tree for mixed OLTP and LSM for heavy ingestion such as events, messages and time-series.

9. Why are writes so fast in Cassandra or RocksDB, and what is the catch?

A write is just an append to a commit log plus an insert into a sorted structure in memory; there is no random disk write on the hot path. Later the memory table is flushed as one sequential file. The catch is paid afterwards: compaction must rewrite data repeatedly, reads may need to consult several files (helped by Bloom filters), deletes leave tombstones that linger, and if compaction falls behind the engine may stall writes. So I leave disk headroom and watch pending compactions.

10. What are the four NoSQL families and what is each for?

Key-value stores give very fast lookups by key (sessions, carts, caches). Document stores hold nested JSON that you read together (catalogs, profiles). Wide-column stores such as Cassandra spread huge write-heavy, time-ordered data by partition key and need queries known up front. Graph databases make relationship traversal cheap (friends of friends, fraud rings). Time-series databases are a fifth specialization for timestamped metrics. The common trade is giving up joins and general transactions for easy horizontal scale, so I pick the family from the access pattern.

11. What is an inverted index and how does search ranking work?

An inverted index maps each normalized word to the list of documents containing it, so a query looks up a few words and intersects short lists instead of scanning every document. An analyzer lowercases, splits and stems the text the same way at index and query time. Ranking commonly uses BM25: a document scores higher when the query term appears more often in it, lower when the term is common across all documents, and adjusts for document length. Extra signals such as freshness or popularity can be blended in.

12. Block, file and object storage: when do you use each?

Block storage is a raw disk attached to a server, used for database volumes. File storage offers paths and in-place edits for shared folders. Object storage holds whole files by key over HTTP, is cheap and highly durable, and scales almost without limit, but you cannot edit part of an object and there are no real folders. For user uploads, images, video, backups and logs, I choose object storage and keep only metadata in the database.

B. Design scenarios

13. Design the data model for e-commerce orders.

Core tables: users, products, orders, order_items, payments. Orders hold user_id, status, totals and a snapshot of the shipping address. Order_items hold order_id, product_id, quantity and the price at purchase time (a snapshot, so later price changes do not rewrite history). Status is a small state machine updated with conditional updates. A unique idempotency key on order creation makes retries safe. Inventory uses an atomic update such as qty = qty - 1 where qty is positive. Reads like "my orders" use an index on (user_id, created_at desc). For scale I shard by user_id so a user's orders are together, and build a search or analytics copy through CDC.

14. Model a social follow graph and a chat history.

Follow graph: a table of (follower_id, followee_id, created_at) with a unique key on the pair and two indexes, one for "who do I follow" and one for "who follows me". Celebrity followers produce huge lists, so keep counts as separate counters and page the lists. For deep traversals use a graph store, but for one or two hops, a sharded table is enough. Chat: query-first in a wide-column store with partition key (chat_id, time bucket) and clustering key message_id descending, so "last 50 messages" reads one partition in order. The time bucket keeps partitions bounded. Per-user inbox tables are separate copies written for fast reads.

15. How would you handle the inventory of a hot item in a flash sale?

Never read then write. Use one atomic conditional update (decrement where quantity is above zero) and check that one row changed. For a single super-hot row this still serializes on one lock, so I split stock into N sub-counters (sub-stock buckets) and pick one at random, or put requests in a queue with a fixed worker, or reserve stock in Redis with a Lua script and settle to the database asynchronously. I also add a reservation with timeout so abandoned carts return stock, and I rate limit at the edge.

16. Choose a database for a shopping cart at big-retailer scale.

The cart is accessed by user id, read and written whole, needs very high availability, and can tolerate some eventual consistency. That fits a key-value or document store like DynamoDB: partition key user id, item value as a map, TTL for abandoned carts. Writes should merge carefully so two devices do not erase each other (use a version check or merge by item). At checkout the cart is converted to an order in the relational system, where transactions matter.

17. Design uploads and downloads of large files (videos, photos).

The client asks the API for a presigned multipart upload. It uploads parts in parallel straight to object storage, retries only failed parts, then calls complete. The API stores the object key, size, content hash, owner and status in the database; a notification triggers processing such as thumbnails or transcoding. Downloads go through a CDN with signed URLs for private files and range requests for seeking. Dedup by content hash saves space. Lifecycle rules move old data to cheaper tiers and clean up incomplete uploads.

18. Design product search for an e-commerce site.

The product catalog stays in the relational database. A CDC stream or outbox sends changes to Elasticsearch, which holds one document per product with analyzed title and description, keyword fields for brand and category, and numeric fields for price. Queries combine full-text matching with filters and facets and a ranking function that blends text score with popularity. Updates are idempotent upserts with versions. Shards are sized around 10 to 50 GB. Reindexing uses a new index and an alias swap. Search is near-real-time, so price and stock are re-checked from the database at checkout.

19. Design storage for metrics from 50,000 hosts.

Each host sends a few hundred points every 10 seconds, which is millions of points per second overall, so I use a time-series database or an LSM store with time-window compaction. Data is labeled by series (metric name plus labels), compressed heavily, and kept at full resolution for a short time, then downsampled to minute and hour averages with retention rules. I avoid high-cardinality labels such as request id. Dashboards read recent data from hot storage and older data from downsampled or object storage.

C. Failures and real-time production scenarios

20. A query that used to take 10 ms now takes 5 seconds. What do you do?

First check what changed: a deploy, data growth, or a plan flip. Run EXPLAIN (ANALYZE) on the query and look for a sequential scan where an index scan should be, a bad join order, or estimated rows far from actual rows, which means stale statistics (run ANALYZE). Check for a missing or unusable index (function on the column, type mismatch), lock waits, a long-running transaction, or table bloat. Short-term, add the index or kill the blocker, and consider a query hint or cached result. Long-term, add slow-query logging and alerts on p99 latency and plan changes.

21. The primary database CPU is at 100% and connections are maxed out. What now?

Stabilise first: find the heaviest and longest queries (pg_stat_activity or the slow log), cancel runaway ones, and shed load with rate limits or by turning off non-essential features. Put a connection pooler in front, because each connection costs memory and too many make it slower. Move read traffic to replicas and cache hot results. Then look for the root cause: a new query without an index, an N+1 pattern after a deploy, or a retry storm making the problem worse. Fix with indexes, batching and exponential backoff with jitter on clients.

22. Users see stale or missing data right after saving. Why?

Most likely reads go to a replica that lags behind the primary, or the cache was not invalidated, or a search index updates only on refresh. For the user who just wrote, I route their reads to the primary for a short time, or pass a version or timestamp token so a replica waits until it has caught up (read-your-writes). I monitor replica lag, and I tell the user interface to show the new data optimistically while the system catches up.

23. Two users bought the last item. How did that happen and how do you fix it?

The code read the stock, checked it in application code, then wrote it back, so two transactions both saw one left (a lost update or write skew). Fix with an atomic conditional update (decrement where quantity is above zero), or SELECT ... FOR UPDATE, or an optimistic version column with retry, or a unique constraint. Add an idempotency key so retries do not double charge. For the customers already affected, reconcile and refund or backorder.

24. Cassandra reads suddenly get slow and timeouts rise. What do you check?

Look at pending compactions and the number of files per read (compaction debt), tombstone counts per query (delete-heavy or queue-like tables), partition size (an unbounded partition), a hot partition from a skewed key, GC pauses, disk I/O saturation, and a node that is down so quorum reads wait. Remedies: add compaction capacity or disk headroom, change the model to use time buckets and TTL instead of mass deletes, split hot keys, repair, and add nodes. Confirm with per-table latency and partition-size metrics.

25. The Elasticsearch cluster turns red or becomes very slow. What do you do?

Check cluster health to see which shards are unassigned and why: a node left, disk reached the watermark, or a shard is corrupt. Free disk or add nodes, let replicas be promoted, and avoid heavy reindexing during recovery. If it is slow, look for expensive queries (leading wildcards, deep pagination, giant aggregations), too many small shards using memory, or long garbage collection. Because the index is derived, the last-resort recovery is rebuilding from the source of truth, which is why keeping a reindex path matters. Prevent it with shard sizing, ILM for old data, circuit breakers and query limits.

26. Disk fills up on the database or object-store nodes. What happens and what do you do?

In an LSM store compaction needs temporary extra space, so a nearly full disk can stop compaction and then writes. In Postgres a full disk can crash the server and stop WAL writes. Immediately remove safe data (old logs, temp files), expand the volume, or drop old partitions, which is instant. Then fix the cause: retention policies, partition-by-time with automated drops, alerts at 70 to 80% usage, and capacity planning that includes replication and compaction headroom. For object stores, lifecycle rules and cleanup of incomplete multipart uploads recover space.

27. A schema migration on a huge table locked everything. How should it be done?

Use online, step-by-step changes. Add new columns as nullable with no default rewrite, backfill in small batches, create indexes concurrently, then switch the code to use the new column, and only later remove the old one (expand and contract). Each step is backward compatible, so you can roll back and run old and new code at once. Set lock timeouts so a migration fails fast rather than blocking queries. For huge tables, tools such as online schema change utilities copy the table in the background and swap.

D. Trade-offs and why-questions

28. SQL or NoSQL for a new system?

I default to a relational database because most products need transactions, constraints, joins and flexible queries, and one well-run Postgres scales further than people think, with replicas and partitioning. I choose NoSQL when a specific need pushes me: huge write rates or data sizes beyond one primary, simple known access patterns, very high availability across regions, or a data shape that fits (documents, graph, time-series). Choosing NoSQL early means giving up ad-hoc queries and transactions, so I need a reason. In many designs the answer is both: SQL as the source of truth and specialized stores derived from it.

29. Why shard by user id or tenant id rather than by date or country?

The shard key should appear in most queries so one shard answers each query, have many distinct values, and spread load evenly. User or tenant id does that and keeps a user's data together, so a single-shard transaction is possible. Date as a key sends all new writes to the newest shard, creating a hot shard. Country has few values and is very uneven. The trade-off with user id is that cross-user queries become scatter-gather, which I handle with a separate analytics or search copy. Hashing the key spreads load; range sharding keeps ranges together but risks hotspots.

30. Replication vs erasure coding for durability: which one and why?

Three-way replication is simple, reads are fast and repair is just copying, but it uses three times the storage. Erasure coding such as 6 data plus 3 parity shards uses only 1.5 times the storage and can survive any three lost shards, which gives even higher durability per byte; the price is more CPU, reads from many nodes when rebuilding, and slightly higher latency on degraded reads. So big object stores erasure-code the bulk of cold data and often keep small or hot objects replicated. For a database serving low-latency reads, replication is the usual choice.

31. Pessimistic or optimistic locking?

Pessimistic locking (SELECT ... FOR UPDATE) blocks others while you work, so it is right when conflicts are common and the cost of a retry is high, but it risks waits and deadlocks, and holds locks during user think time if misused. Optimistic locking reads a version, then updates only if the version is unchanged, and retries on conflict. It scales better when conflicts are rare, and works well across HTTP requests. For a simple counter, neither is needed: use an atomic update expression.

32. Should the search index or cache be written directly by the application?

I avoid dual writes, because if the database write succeeds and the second write fails (or the order is reversed), the two stores disagree and nobody notices. Instead the application writes only the source of truth, and a change stream (CDC or an outbox table) updates the cache or index asynchronously with idempotent, versioned operations. It adds some delay, but it is reliable, replayable and rebuildable. For caches I delete keys on write with a TTL as the safety net.

33. When would you not use Elasticsearch, a vector database, or a graph database?

I skip Elasticsearch when simple database full-text search handles the volume (Postgres text search for small catalogs), because it adds a whole system to run and keep in sync. I skip a vector database when exact filters answer the question, or when pgvector in the existing database is enough for a small corpus. I skip a graph database when relationships are one or two hops deep, which a join table handles, or when the graph is huge and must be sharded across machines. The rule: add a specialized store only when a measured need justifies the sync and operations cost.

34. How do consistent hashing and tunable quorums fit with these stores?

Dynamo-style stores such as Cassandra and DynamoDB place each key on a ring of nodes by hashing, so adding a node moves only a small share of keys, and each key has N replicas on following nodes. With a write quorum W and a read quorum R where R + W is greater than N, a read overlaps at least one replica with the newest write, which gives strong-ish consistency; lowering them favors latency and availability. Conflicts from concurrent writes are resolved by last-write-wins timestamps or versions, so I point out that clock skew can silently drop a write.
