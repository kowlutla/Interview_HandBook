Algorithms and data structures for system design

Revision sheet for the day before the interview: hashing and sketches, geo and text indexes, sorted sets and top-K, and conflict-free editing. Full explanations: Handbook Chapters 57–59.

0. Key definitions (know these cold)

TermDefinition
Hash functionA recipe that turns any input (a name, a file) into a fixed-size number. The same input always gives the same number, and outputs should look evenly spread.
CollisionTwo different inputs give the same hash. Unavoidable, because there are more inputs than outputs.
Birthday boundCollisions show up after only about the square root of the output space. A 32-bit hash collides after about 77,000 items; a 64-bit one after about 5 billion.
Load factorItems divided by buckets in a hash table. When it gets too high the table doubles and rehashes.
Consistent hashingA way to place keys on servers so that adding or removing a server moves only a small share of keys (about 1/N), instead of almost all of them.
Virtual node (vnode)One server takes many positions on the hash ring. This evens out load and spreads a dead server's work over many neighbours.
Probabilistic structureA small structure that answers a question approximately, using far less memory than the exact answer needs.
Bloom filterA bit array that says "definitely not seen" or "probably seen". No false negatives; a small, tunable rate of false positives. You cannot delete from a plain one.
HyperLogLog (HLL)Counts distinct items (unique visitors) in about 12 KB with roughly 0.8% error, and sketches can be merged.
Count-Min Sketch (CMS)A small table of counters that estimates how often each item appeared. It can only overcount, never undercount.
Heavy hitter / top-KThe K most frequent (or highest scoring) items.
GeohashA short string (like ezs42) naming a rectangular map cell. A longer string means a smaller cell, and cells with the same prefix are inside the same bigger cell.
QuadtreeA tree that splits a square into 4 smaller squares, but only where there are many points. Dense areas get small cells, empty areas stay big.
S2 / H3Google S2 (square-ish cells on a cube projection) and Uber H3 (hexagon cells). Both give cells of near-uniform size across the globe.
Trie (prefix tree)A tree where each step down is one letter. All words with the same prefix share the same path, so prefix lookups are fast.
Inverted indexA map from each word to the list of documents containing it (the posting list). It is how search engines work.
Edit distanceThe least number of single-letter inserts, deletes or swaps to turn one word into another. Used for typo-tolerant search.
Skip listA sorted linked list with extra "express lane" levels, built by coin flips. Gives O(log n) search, insert and rank. Redis uses it for sorted sets.
Heap / priority queueA structure that always gives you the smallest (or largest) item quickly. Not good for finding rank or an arbitrary item.
Sliding-window counterA count over "the last N seconds", kept as small time buckets that are added up and dropped as they age out.
OT (operational transformation)Editing approach where a server orders concurrent edits and adjusts (transforms) each one so all users end with the same text.
CRDTConflict-free replicated data type: a data structure whose copies can be changed independently and merged in any order, always ending with the same result.
TombstoneA marker left in place of a deleted item, so that other copies know it was deleted and not just missing.
Merkle treeA tree of hashes. If two copies have the same root hash they are identical; if not, walk down to find the differing parts.

1. Hashing and consistent hashing Ch 57

One line: a good hash spreads keys evenly; consistent hashing uses a hash ring so that changing the number of servers moves only about 1/N of the keys.

What a hash function must do

  • Deterministic: same input, same output, every time and on every machine.
  • Uniform: a million keys into 1,000 buckets should give about 1,000 per bucket. A lopsided hash makes hot spots.
  • Avalanche: changing one input letter flips about half the output bits.
  • Fast: for hash tables and routing use a fast non-cryptographic hash (for example murmur or xxHash). Use a cryptographic one (SHA-256) only when you need security: content addressing, integrity, signatures.
KindExamplesUse forDo not use for
Non-cryptographicmurmur, xxHashHash tables, sharding, Bloom filters, sketchesPasswords, anything with an attacker
CryptographicSHA-256, SHA-3, BLAKE3Content addressing, Merkle trees, signatures, integrityHot paths where speed matters and no one attacks you
Numbers: birthday bound: about 77,000 items for 50% chance of a collision in 32 bits; about 5 billion in 64 bits. So never use a short hash as a unique id. Hash table: chaining or open addressing; resize (usually double) when load factor passes about 0.7 to 0.75; resizing costs O(n) once but is O(1) amortized per insert.

The problem with hash mod N

The simple way to pick a server is server = hash(key) mod N. It works until N changes. Going from 4 to 5 servers changes the answer for about 80% of keys (only about 1 in 5 stays put). For a cache, that is a mass cache miss: the database suddenly takes almost all the traffic. For a database, it means moving most of the data.

The hash ring

Put both servers and keys on a circle (the hash space, say 0 to 232). A key belongs to the first server found going clockwise from it. When a server is added it takes over only the arc between itself and the server before it. When one dies, only its arc moves, to the next server clockwise.

TechniqueIdeaPick whenCatch
Ring with vnodesEach server has many points on the ringGeneral purpose; nodes join and leave freely (Cassandra, cache clients)Ring metadata to keep in sync
Rendezvous (HRW)Score every server per key, take the highestSmall server sets; simple and evenO(N) work per lookup
Jump hashFew lines of code, no memory, almost perfect balance, moves exactly 1/(N+1)Numbered shards that only growCannot remove an arbitrary node, only the last one
MaglevFixed lookup table filled from per-server permutationsLoad balancers where lookup speed mattersSlightly more keys move on change
Bounded loadsCap each server at about 1.25x average, spill extra to the nextHot-key skew on a ringSome lookups go to a second server
Numbers: add one server to N: about 1/(N+1) of keys move on a ring. One position per server can leave the busiest node with 2 to 3 times the average load; 100 to 256 vnodes per server brings imbalance down to a few percent (error shrinks roughly as 1/sqrt(v)). For replication, store a key on the next R distinct physical servers clockwise (skip vnodes of the same machine).
Traps: (1) one point per server gives bad balance and a cascade when it dies; (2) forgetting that replicas must land on different machines, not different vnodes of the same machine; (3) consistent hashing fixes data movement, not a single hot key (that needs caching or key splitting); (4) using a 32-bit hash as an id.
Say: "I would not shard with mod N because adding a node remaps about 80% of keys. I would use consistent hashing with around 100 virtual nodes per server, so a new node takes about 1/N of the keys, taken evenly from everyone, and a failure spreads over many neighbours."

Similarity hashing (short version)

  • Jaccard similarity: shared items divided by all items in two sets. 1 means identical, 0 means nothing in common.
  • MinHash: shrinks each set to a small signature (say 128 numbers) so that matching positions estimate Jaccard.
  • LSH banding: cut the signature into bands (for example 32 bands of 4). Two documents that match in any whole band become a candidate pair. This finds near-duplicates without comparing all pairs. With 32 bands of 4: similarity 0.8 is almost always a candidate; 0.3 only about 23%.
  • SimHash: one 64-bit fingerprint; a small Hamming distance (few differing bits) means near-duplicate. Good for web-crawler dedup.

2. Bloom filter Ch 57

One line: a bit array plus k hash functions that tells you "definitely not here" or "probably here", using about 10 bits per item for a 1% error.

Add: hash the item k ways, set those k bits to 1. Check: hash the same k ways; if any bit is 0 the item was never added; if all are 1 it is probably there (other items may have set those bits). That wrong "probably" is a false positive. A false negative is impossible.

Numbers: bits per item m/n = 1.44 × log2(1/p): 1% error needs about 9.6 bits per item, 0.1% about 14.4, 0.01% about 19.2. Best k is about (m/n) × 0.69, so about 7 for 1%. Example: 100 million items at 1% is about 960 million bits, about 120 MB, versus several GB for a hash set (about 10 GB with 100-byte URLs).
VariantAddsCost
Counting BloomDeletes (small counters instead of bits)About 3 to 4 times the memory
Cuckoo filterDeletes, often smaller at low error ratesInsert can fail when nearly full
Scalable BloomGrows as items growLayers of filters, slightly more error

Use it for

  • LSM trees (Cassandra, RocksDB): skip disk files that cannot contain the key
  • Cache penetration: reject keys that never existed before they hit the DB
  • Crawler "seen URL" check
  • Username or email "maybe taken" pre-check

Not for

  • When a false positive is harmful and you cannot double check the real store
  • When you need to delete, list or count items (plain Bloom)
  • Small sets where a hash set fits easily
Traps: sizing for n items and then inserting far more (error rate climbs fast); treating "probably present" as "present" without checking the real store; forgetting that a plain Bloom cannot delete, so a cache with frequent deletes needs rebuilds or a counting/cuckoo variant.
Say: "A Bloom filter in front of the database for non-existent keys: 'no' is certain so we skip the DB, 'maybe' goes to the cache and DB as usual. For 100 million keys at 1% that is about 120 MB."

3. HyperLogLog, Count-Min Sketch and friends Ch 57

One line: when exact counting costs too much memory, use a sketch: HLL for "how many different", CMS for "how many times", and know the error and the memory.

HyperLogLog: how many distinct items

Hash each item to a random-looking bit string. A string that starts with many zeros is rare (k zeros happens about 1 in 2k), so the longest run of leading zeros hints at how many different items were seen. One guess is noisy, so HLL splits the stream into m buckets (registers) using the first p bits of the hash, keeps the largest zero-run per register, and averages them. Duplicates hash the same way, so they change nothing.

Numbers: 16,384 registers (p = 14) at 6 bits each is 12 KB, standard error about 0.81% (error = 1.04 / sqrt(m)). 4,096 registers is 3 KB at about 1.6%. Four times the memory halves the error. Merge = take the max per register, which is safe to repeat (idempotent), so you can merge hourly sketches into daily ones. Redis: PFADD, PFCOUNT, PFMERGE.

Count-Min Sketch: how many times

A grid of d rows by w columns of counters, with one hash function per row. To count an item, add 1 in one counter per row. To ask, take the minimum across the d counters. Other items can share counters and push them up, so the answer can be too high but never too low; the minimum picks the least polluted row.

Sizing: width w = e / ε, depth d = ln(1/δ). For ε = 0.001 and 99% confidence: w = 2,719 and d = 5, about 13,600 counters, about 54 KB with 4-byte counters. Overcount is at most ε × N (events seen) with that confidence. For 360 million events in an hour the bound is about 360,000, which is small next to a truly trending tag (millions).

Trending hashtags recipe: per region and hour keep a CMS plus a small heap of size K. On each event update the CMS, read the estimate, and if it beats the heap minimum put it in the heap. Memory: 54 KB plus a 100-entry heap, instead of a map with tens of millions of entries.

Say: "Unique visitors per page per hour is HyperLogLog: 12 KB each, merged up to day and week, 1% error is fine for a dashboard. Trending tags are Count-Min plus a small heap per region. Billing needs exact numbers, so there I count exactly."

4. Geospatial indexes Ch 58

One line: a normal sorted index works on one number, but "near me" is two-dimensional, so either flatten the map into cell ids (geohash, S2, H3) or use a spatial tree (quadtree, R-tree).

Why latitude and longitude indexes fail: an index on latitude returns a stripe around the whole world; one on longitude returns a stripe from pole to pole. The true answer is the small overlap, but the database has to read both big stripes and intersect them.

Geohash

Cut the range of longitude in half again and again (0 for the lower half, 1 for the upper), and do the same for latitude. Interleave the bits (longitude first), then write every 5 bits as one base-32 character. Example: a point becomes a string like ezs42. Each extra character makes the cell 32 times smaller. Because cells nest, all points inside a cell share its string as a prefix, so "everything in this area" becomes a prefix range query on any ordinary index.

Cell sizes at the equator (approx.): 4 characters about 39 km × 20 km; 5 about 5 km × 5 km; 6 about 1.2 km × 0.6 km; 7 about 150 m × 150 m. Cells get narrower towards the poles. Redis GEO stores members in a sorted set with a 52-bit geohash as the score; GEOSEARCH does the cells plus distance filter for you.
OptionIdeaStrengthWeaknessPick when
GeohashZ-order string keyEasy, any key-value store, prefix queriesBoundary jumps, cell size varies with latitudeDefault answer; moderate scale
QuadtreeSplit squares where crowdedAdapts to density; good nearest-neighbourIn-memory, rebalancing, harder to shardVery uneven density, one server's memory

Why hexagons: every neighbour of a hexagon is the same distance away (a square has diagonal neighbours that are further), so "ring of neighbours" and radius estimates are smoother. Real databases: PostGIS for relational plus shapes; Elasticsearch for text plus location; Redis GEO or an in-memory grid for live positions; a key-value store with geohash or S2 keys for global simple points.

Moving objects (drivers updating every few seconds)

  • Do not write every ping to a disk database. Keep the latest position in memory: a map cell-id to set of driver ids, plus a map driver-id to (position, cell). An update moves the id between cells only when the cell changes.
  • Give each entry a TTL (for example 10 to 30 seconds) so a driver whose phone died disappears by itself.
  • Shard by a coarse cell (for example geohash length 4) so a nearby query touches one or two shards. Log pings to a stream for history and analytics.
  • Sparse areas: if the 3 × 3 search finds too few drivers, widen the search ring by ring (or step to a bigger cell) until enough are found or a maximum radius is reached.
Worked example: 1 million drivers, one ping per 4 s = 250,000 writes/s. Payload about 50 bytes, so about 12.5 MB/s and about 100 MB of state. One node handles about 100,000 simple ops/s, so use about 8 shards. A driver at 36 km/h moves 40 m in 4 s; with 600 to 1,200 m cells only about 3 to 7% of updates change cell, about 7,500 to 17,500 set changes per second. A nearby query reads 9 cells, filters by distance and sorts in under 1 ms.
Traps: forgetting the 8 neighbours; using one huge cell in a city centre (thousands of results) or tiny cells in a rural area (empty); updating a disk-based index 250,000 times per second; forgetting TTL so ghost drivers stay forever; ignoring the antimeridian (longitude wraps at 180).
Say: "I flatten location to a cell id, geohash at about 1 km, keep live drivers in an in-memory map cell to drivers, query the rider's cell plus 8 neighbours, then sort by real distance. Shard by coarse cell. Positions have a TTL, and history goes to a stream."

6. Sorted sets, leaderboards, top-K and trending Ch 59

One line: when you need things in order with fast rank, use a skip list or balanced tree (Redis sorted set); when you only need the biggest few, use a heap; when the stream is huge, use per-shard top-K and merge.

The skip list

A sorted linked list is slow to search (walk one by one). A skip list adds higher "express" levels: each item is promoted to the next level by a coin flip (half the items reach level 1, a quarter level 2, and so on). To search, start at the top level, move right while the next item is not too big, drop down a level, repeat. Expected time is O(log n). Insert is a search plus splicing the new node into a few levels. No rotations are needed, which makes it simpler than a balanced tree and easier to make concurrent.

StructureSearch / insertRankBest forNote
Balanced tree (red-black, AVL)O(log n)With size countsIn-memory ordered mapsRotations make concurrency harder
B+ treeO(log n), very shallowNot naturalDisk indexesWide nodes minimize page reads
Skip listO(log n) expectedWith spans on pointersRedis ZSET, concurrent listsSimple code, easy range scans
HeapInsert O(log n), peek O(1)NoTop-K, schedulers, merge K listsCannot find arbitrary items

Redis sorted set (ZSET) = a skip list (ordered by score) plus a hash table (member to score). ZSCORE is O(1); ZADD, ZREM, ZRANK, ZRANGE are O(log n). Small sets use a compact packed layout.

Leaderboards

  • Single board: ZADD or ZINCRBY to update, ZREVRANGE 0 99 for the top 100, ZREVRANK for a player's rank. One Redis node handles about 100,000 ops/s, enough for many millions of players.
  • Too big for one node: shard by player id (writes spread evenly). Then the top 100 is spread everywhere: ask every shard for its top 100 and merge (scatter-gather). A single player's exact global rank needs counts from all shards.
  • Approximate rank for huge boards: keep a histogram of scores (for example 10,000 buckets). Rank = players in higher buckets plus a fraction of the player's own bucket. Updates are two counter changes. Good enough for "you are in the top 3%".
  • Time windows: one sorted set per window with the window in the key (lb:2026-11-17, lb:2026-W47); ZINCRBY on each active key; EXPIRE old ones.

Top-K and trending

SituationApproach

Traps: arbitrary partitioning plus per-shard top-K (a globally popular item can be fifth on every shard and miss all local top-Ks, so the merged list is wrong); using a heap when you need rank; resetting counters on the hour (a big cliff) instead of sliding; sorting the whole data set to get 10 items; one giant sorted set that becomes a hot key.
Say: "Leaderboard: Redis sorted set, ZINCRBY on score events, ZREVRANGE for the top 100. At very large scale I shard by player, scatter-gather the top 100, and give players an approximate rank from a score histogram. Windows are separate keys with TTL."

7. OT and CRDTs for shared editing Ch 59

One line: two people edit the same text at the same time; OT lets a server fix up positions in order, CRDTs give every character a permanent id so copies can merge in any order.

The problem: the text is "Hi". Ana inserts "!" at position 2. Ben inserts "Oh, " at position 0 at the same time. If Ana's insert at position 2 is simply applied after Ben's, "!" lands in the wrong place. Someone has to adjust positions.

OT (operational transformation)CRDT (conflict-free replicated data type)
Core ideaTransform an incoming edit against edits that happened first, so intent is keptGive each item a unique id; merge rules are built so any order gives the same result
Needs a central server?Practically yes (server gives one order)No, works peer to peer and offline
MetadataSmallLarger: ids per character, tombstones for deletes
Hard partTransform functions are tricky to get right (peer to peer is very hard)Metadata growth and garbage collection
Used byGoogle Docs style systemsYjs, Automerge, Redis CRDB, Riak, many offline-first apps

CRDT building blocks

  • G-Counter: one slot per replica; each only increases its own slot; value = sum; merge = max per slot. Grow-only.
  • PN-Counter: two G-Counters, one for increments and one for decrements.
  • Sets: G-Set (add only); 2P-Set (an element once removed cannot come back); OR-Set (each add gets a unique tag, remove deletes only the tags it saw, so a concurrent re-add wins).
  • Registers: LWW (last write wins by timestamp, simple but can silently drop a write) or multi-value (keep both and let the app or user decide).
  • Text: RGA (a linked list of characters with ids built from a logical clock plus replica id), Logoot/LSEQ (dense positions between neighbours), Yjs and Automerge (optimized RGA-style).
  • Cost: tombstones for every deleted character; without cleanup a document that has been edited for years grows without bound, so periodically compact once every replica has seen the deletes.
Numbers: a 100,000-character document can carry ids for every character plus tombstones; typical optimized libraries compress runs of consecutive typing into one record. The CALM idea: a computation that only grows (monotonic) needs no coordination to be consistent, which is why counters and add-only sets are easy and deletes are hard. Also related: presence and cursors are not part of the document; send them as short-lived ephemeral messages.
Traps: using last-write-wins for text (loses someone's edit); forgetting that CRDT delete needs tombstones (or a deleted item can reappear); promising peer-to-peer OT without a server (very hard to get right); storing cursors in the document so they pollute history.
Say: "For a Google-Docs-style editor with a central server I would use server-ordered OT: simple and compact. If we need offline editing or peer to peer, I would use a sequence CRDT like Yjs. I would send cursors and presence over a separate lightweight channel."

Say-aloud script (30 to 60 seconds)

Say: "For routing keys to servers I use consistent hashing with virtual nodes, so adding a server moves only about one over N keys and a failure spreads across many neighbours. To avoid expensive lookups, I put a Bloom filter in front: a no is certain, a yes goes on to the real store; 100 million keys is about 120 MB at 1% error. For analytics, unique visitors use HyperLogLog, 12 KB and under 1% error, mergeable across time and shards, and trending uses Count-Min Sketch plus a small heap. For nearby search I flatten location to a cell id, geohash or S2 or H3, keep live positions in memory by cell with a TTL, and query the cell plus its 8 neighbours, then sort by true distance. Autocomplete is a compressed trie with top-K stored at each node and rebuilt in batches. Leaderboards are a Redis sorted set, which is a skip list plus a hash. For shared editing I choose server-ordered OT if we have a server, or a sequence CRDT if we need offline or peer to peer."

Interview Q&A (35)

A. Concepts

1. Why is hash(key) mod N a bad way to shard, and how does consistent hashing fix it?

With mod N every key's server depends on N. If N goes from 4 to 5, only about one key in five keeps its server, so about 80% of keys move. For a cache that is a wave of misses that crushes the database; for a database it is a huge data migration. Consistent hashing puts servers and keys on a circle, and a key belongs to the next server clockwise. Adding a server takes only the arc just before it, so about 1/N of the keys move, and they all move to the new server. Removing a server moves only that server's keys to its neighbour. This is why Cassandra, Dynamo-style stores and many cache clients use it.

2. What are virtual nodes and why do we need them?

A virtual node is one of many points a physical server owns on the ring. With one point per server the arcs are random sizes, so the busiest server can carry two or three times the average, and when it dies its whole load lands on one neighbour, which may then fail too. With, say, 100 to 256 points per server the load averages out and a dead server's work spreads over many machines. Vnodes also let you give bigger machines more points. The cost is more ring metadata and slightly more complicated replica placement, since replicas must go on different physical machines.

3. How does a Bloom filter work, and what are its error guarantees?

It is a bit array with k hash functions. To add an item, set the k bits its hashes point to. To check, look at the same k bits: if any is 0 the item was never added, which is certain. If all are 1 it is probably there, but other items may have set those bits, which is a false positive. It never gives a false negative as long as nothing is deleted. The error rate depends on bits per item: about 9.6 bits for 1%, 14.4 for 0.1%. You size it from the number of items and the error you can accept. If you insert far more than planned, the error rate rises quickly.

4. How can HyperLogLog count millions of distinct users in 12 KB?

It hashes each item and looks at the number of leading zeros. Seeing a hash with many leading zeros is rare, so the longest run suggests how many different items were seen, like guessing how many coins were flipped from the longest run of tails. One guess is noisy, so it splits items into thousands of buckets using the first bits of the hash, keeps the longest run per bucket, and combines them with a harmonic mean. With 16,384 six-bit registers that is 12 KB and about 0.8% standard error. Repeated items hash the same way and change nothing, so duplicates are free. Two sketches merge by taking the maximum per register.

5. What does a Count-Min Sketch give you, and which way does it err?

It estimates how many times each item appeared, using a small grid of counters and one hash per row. An event adds one to one counter in each row; a query takes the minimum of that item's counters. Different items can share a counter, which only adds to it, so the estimate is never below the truth but can be above. The size comes from the error you accept: width about e divided by epsilon and depth about ln(1/delta). For 0.1% error with 99% confidence it is about 54 KB. It works well for heavy items and badly for rare ones, because the noise can be bigger than a small real count.

6. Why can't a latitude index and a longitude index answer "find places near me"?

A normal index orders values along a single line. An index on latitude returns a band that circles the whole Earth, and one on longitude returns a band from pole to pole. The true answer is only the small spot where they cross, but the database must read both huge bands and intersect them. Proximity is two-dimensional. So we either flatten the plane into one number that mostly keeps neighbours close (geohash, S2, H3), or we build a tree over space (quadtree, R-tree, k-d tree).

7. How does geohash work and what is the boundary problem?

Repeatedly halve the longitude range and the latitude range, writing 0 or 1 each time. Interleave the two bit lists and turn every five bits into a base-32 character. You get a string like ezs42 that names a rectangle, and a longer string names a smaller rectangle inside it, so the shared prefix means the same bigger cell. The problem is at cell edges: two points 10 metres apart can be in cells with completely different strings, and the Z-shaped ordering means nearby cells are not always nearby in the sorted list. The fix is to always query the centre cell and its 8 neighbours, then compute true distance.

8. Geohash vs quadtree vs S2 vs H3: how do you choose?

Geohash is the easy default: a string key you can use in any key-value store or database, with prefix queries; weaknesses are the boundary jumps and cells that get narrower near the poles. A quadtree adapts to density, giving small cells in busy areas, but it lives in memory and is harder to shard and update. S2 projects the globe on a cube, gives near-uniform cells and a Hilbert curve order, and is excellent for covering regions, at the cost of a more complex library. H3 uses hexagons, so every neighbour is equally far, which suits ride-hailing, heat maps and surge pricing. In an interview I start with geohash and mention S2 or H3 when asked about accuracy or global scale.

9. Why does Redis use a skip list for sorted sets, and what are the complexities?

A skip list keeps items sorted with extra express levels built by random coin flips, giving O(log n) expected search, insert and delete. It also supports rank queries if each pointer stores how many nodes it jumps over, and range scans are natural because level 0 is a sorted linked list. Compared with a balanced tree, it needs no rotations, so the code is simpler and it is easier to change just a few local pointers. Redis pairs it with a hash table from member to score, so ZSCORE is O(1) while ZADD, ZREM and ZRANK are O(log n).

10. What is the difference between OT and a CRDT?

Both make concurrent edits converge. OT keeps edits as operations with positions, and when two edits happen at the same time it transforms one against the other (for example shifting a position by the length of the other insert). It normally needs a server to decide a single order, and the transform functions are hard to get right. A CRDT gives every item a unique id and defines merge so that applying edits in any order gives the same result, so it needs no central server and works offline. The price is metadata: ids for each character and tombstones for deleted ones.

11. What is a tombstone and why do CRDTs need them?

A tombstone is a marker that keeps a deleted item's place and id. If we simply removed the item, another copy that has not yet heard of the delete could send it back in a merge, and we could not tell "deleted" from "never seen". With the marker, the delete is a fact that merges like any other. The cost is that data never shrinks on its own, so systems run garbage collection after all replicas confirm they have seen the delete, or periodically rebuild the document state.

B. Design scenarios

12. Design "find nearby drivers" for 1 million drivers who report every 4 seconds.

That is 250,000 writes per second, so I do not write them to a disk database. I keep the latest state in memory: a map from cell id (geohash around 1 km) to the set of driver ids, and a map from driver id to position and cell. An update only changes the sets if the driver crossed a cell, which at city speeds is only about 3 to 7% of updates. Entries have a TTL of tens of seconds so dead phones vanish. I shard by a coarse cell, around 8 shards, so queries touch one or two shards. A query reads the rider's cell plus its 8 neighbours, computes true distances, sorts and returns the top few; this takes about a millisecond. History goes to a stream for analytics. See the nearby-search case sheet.

13. Design search autocomplete for a large site.

I use a trie where each node stores its precomputed top-K completions (say 5 or 10) with scores. When the user types a prefix, I walk to that node in time proportional to the prefix length and return its list, with no subtree scan. The scores come from query logs, aggregated offline in batches (every few minutes or hours), and the trie is rebuilt and swapped in, so live typing never writes to it. To save memory I use a compressed radix trie, shard by prefix, and cache hot short prefixes in a CDN or Redis. I add a debounce on the client and perhaps personalization on top. See the autocomplete case sheet.

14. How would you count unique visitors per page per day for a very large site?

An exact set per page would hold every user id, which is gigabytes for popular pages. I use one HyperLogLog per page per hour, about 12 KB each, updated with PFADD as events arrive. Daily and weekly numbers come from merging hourly sketches, and merging is safe to repeat, so a replayed batch after a failure does not inflate counts. Error is under 1%, fine for a dashboard. Where exact numbers matter (billing, legal) I would use a precise path, for example a batch job on the raw log. I would also state that HLL cannot list users or subtract one set from another.

15. Design trending hashtags for a social network.

Events arrive at about 100,000 per second. Per region and hour I keep a Count-Min Sketch (about 54 KB) and a small heap of the top 100 tags. For each event I update the sketch, read the estimated count, and update the heap if the tag beats its minimum. The estimate can only be too high, by at most epsilon times events (for 360 million events and 0.1% that is at most about 360,000), which is small next to a real trending tag. Sketches merge across regions by adding counters. To find tags that are rising rather than just big, compare the current window with a baseline.

16. Design a global leaderboard for a game with 100 million players.

Start with a Redis sorted set: ZINCRBY on score events, ZREVRANGE 0 99 for the top 100, ZREVRANK for a player's rank, all O(log n). One node can hold tens of millions of entries and do about 100,000 operations per second. At 100 million with high write rates I shard by player id so writes spread evenly. The top 100 becomes a scatter-gather: each shard returns its top 100 and we merge. Exact rank for any player would need counts from all shards, so for "you are in the top 3%" I keep a histogram of scores and estimate rank from bucket counts. Daily, weekly and all-time boards are separate keys with TTL.

17. Design a "seen URL" check for a web crawler with 10 billion URLs.

Storing 10 billion URLs exactly takes terabytes. A Bloom filter at 1% error needs about 9.6 bits per URL, so about 12 GB total, which can be split across a few machines by hashing the URL. The crawler asks the filter: a no means crawl it for sure; a yes means skip it. A false positive means about 1% of new URLs are wrongly skipped, which is usually acceptable for a crawler. I would size for the final count, not the current one, partition by host so each shard is separate, and rebuild periodically. If skipping must never happen, then a "yes" has to be verified in the exact store.

18. How would you build a typo-tolerant search box?

I would keep the normal inverted index, and add a fuzzy layer. For each query term, find candidate dictionary words that share many character n-grams (for example 2- or 3-letter pieces), or use a Levenshtein automaton against the term dictionary, as Lucene does. Then verify each candidate with edit distance (allow 1 for short words, 2 for longer) and rank by distance and word popularity. Running edit distance against the whole dictionary is too slow, so candidate generation is the key step. I would also add a query log based "did you mean" for common mistakes.

19. Design a shared document editor for up to 50 simultaneous users.

With a central server I would use server-ordered OT. Each client sends operations tagged with the document version it saw; the server transforms them against operations that arrived since, assigns the next version, applies and broadcasts. Clients keep a local pending queue and transform incoming edits against it. State is small and the server is the single authority. If we need strong offline editing or peer-to-peer sync, I would use a sequence CRDT like Yjs instead. Either way, cursors and presence travel on a separate light channel, we snapshot the document periodically, and we store an operation log for history and recovery.

20. How would you pick a database for geo plus text queries ("coffee shops near me that serve vegan food")?

Elasticsearch handles this well: it combines an inverted index for text with geo-point indexing, and can filter by distance and rank by text score together. If the data is relational with polygons (delivery zones, city boundaries) and needs transactions, PostGIS fits. For live moving positions, Redis GEO or an in-memory grid. For huge global point lookups, a key-value store with geohash or S2 keys works. In an interview I name the access pattern first, then pick, and mention that I might feed a search index from the primary database through change events.

C. Failures and production scenarios

21. You add a cache node and the database load triples. What happened?

Most likely the cache clients use mod N sharding, so adding a node remapped about 80% of keys, and all of those suddenly miss. The cold keys flood the database. Immediate steps: slow the rollout, throttle or shed load, warm keys, or roll back the node. The fix is to move to consistent hashing with virtual nodes, so only about 1/N of the keys move, add nodes gradually, and protect the database with single-flight requests and rate limits during topology changes.

22. Your Bloom filter's false positive rate is far above the design target. Why, and what do you do?

The usual cause is that more items were inserted than the filter was sized for, so too many bits are 1 (a filter half full of ones is near its design limit; much more and errors grow fast). Other causes: weak or correlated hash functions, or reusing a filter across a changed key format. First measure the fraction of bits set. Then rebuild a larger filter from the source of truth, ideally sized with headroom (for example 2x expected growth), or switch to a scalable Bloom filter which adds layers. Meanwhile, keep correctness by treating a "yes" as "check the real store", so the filter only saves work and never decides.

23. Dashboard numbers from HyperLogLog differ from the exact SQL count by 1 to 2%. Is something broken?

No, that is expected: standard error of about 0.8% for 12 KB means about 2% is within three standard deviations. First confirm the numbers are being compared for the same window and the same id definition (user id vs device id, time zone boundaries, bots filtered). If the business needs exact numbers for a specific view such as billing, use an exact path for that view and keep HLL for the large, exploratory ones. If more accuracy is wanted, more registers help, but error only falls with the square root of memory, so four times the memory halves the error.

24. Nearby-driver searches return nobody in a busy area, even though drivers exist. What do you check?

First check the boundary problem: if the code only searches the rider's cell and not the 8 neighbours, nearby drivers across an edge are missed. Then check TTL and liveness: stale heartbeats may have removed drivers. Check cell size versus radius (cells much smaller than the search radius mean too few cells searched), and whether one shard is overloaded or lagging so updates are delayed. Check the antimeridian or pole handling if the location is unusual. Look at the lag between update and index. For sparse areas, widen ring by ring until enough drivers are found.

25. One cell in the city centre has 50,000 drivers and the shard for it is overloaded. What now?

That is a hot cell. Use finer cells in dense areas: a quadtree-style adaptive split, or a higher geohash or S2 level only where the count passes a threshold. Spread the hot cell over several shards by also hashing the driver id, and have queries fan out to those shards then merge. Add read replicas for the busy region, and cap query results (we only need the closest 10 to 20). Also check that update handling does not rewrite more than necessary: only changes of cell or a throttled position change need to touch the index.

26. Autocomplete suggestions are stale and miss a news event from an hour ago. How do you handle it?

The offline rebuild cadence is too slow for fresh trends. Add a small second source: a fresh in-memory trending trie or a Count-Min Sketch with recent queries over a short window (say 5 to 15 minutes) and blend its results with the main trie when ranking. Keep the big trie rebuilt on its normal schedule. Protect against abuse by requiring a minimum number of distinct users. The trade-off is added complexity and some noise, so apply the fresh source only for the top few suggestions.

27. A top-10 trending list, built by merging per-shard top-10s, shows wrong items. Why?

If events are spread arbitrarily across shards (round robin or by user), one item's count is split among shards. A globally popular item might be only fifth on each shard and miss every local top 10, so the merge never sees it. Fixes: partition by item id so each item is counted on exactly one shard, so local top-K is exact for those items; or have each shard return a longer list (top 100 or more) and merge, accepting approximations; or merge Count-Min Sketches (add the counters) and then take the top from the merged sketch.

28. Two users edit the same paragraph offline and then reconnect. What happens in OT and in a CRDT?

With server-ordered OT, the reconnecting client sends a long list of pending operations against an old version. The server must transform each against everything that happened in between, which works but can be costly and fragile, and many OT systems limit how long offline edits are allowed. With a sequence CRDT, each character already has an id and a position relative to neighbour ids, so the two histories just merge, and both users' text survives, ordered by ids. The result may need human review if both rewrote the same sentence, but nothing is lost silently, which is a benefit over last-write-wins.

29. A collaborative document is getting slow and its file size keeps growing, even though the visible text is small. Why?

In a CRDT, deleted characters stay as tombstones, and each character carries an id, so a heavily edited document accumulates metadata far bigger than the visible text. Fix by compacting: once every replica has acknowledged a version, drop tombstones before it and merge runs of consecutive characters into one record; use libraries that already do run-length compression (Yjs, Automerge). Snapshot the document state periodically and truncate the operation log. Also check that cursors or presence are not being written into the document.

D. Trade-offs and why-questions

30. Why use a Bloom filter instead of a hash set, and when would you not?

A hash set stores every item and is exact, but it costs a lot: 100 million 8-byte ids is about 1.6 to 4 GB with overhead, and with 100-byte URLs it can pass 10 GB. A Bloom filter holds the same membership question in about 120 MB at 1% error. Use it when a "no" saves expensive work (disk reads, DB calls) and a rare false "yes" is harmless because you double check. Do not use it when you must delete items, list them, count them, or when even one false positive is unacceptable. For small sets, an ordinary hash set is simpler and exact.

31. Geohash vs a quadtree for nearby search: why would you pick one?

I would pick geohash when I want something simple that works inside any store and shards naturally by prefix: moving objects, millions of updates, and cell sizes that I choose by search radius. I would pick a quadtree when density is very uneven and I want cells to split on their own, and the whole structure can live in the memory of one machine or a small cluster. The quadtree is harder to update at 250,000 writes per second and to shard, because the tree is dynamic. A fixed grid keyed by geohash is usually the more robust answer for live positions.

32. Redis sorted set vs a SQL ORDER BY for a leaderboard: why?

A SQL ORDER BY score LIMIT 100 with an index works for small boards, but rank for a given player needs a count of rows with a higher score, which is a slow range count at big sizes, and every score update rewrites an index entry on disk. A Redis sorted set holds scores in memory in a skip list, so update, top-N and rank are O(log n) in microseconds. The trade-off is memory cost and durability: Redis needs persistence or a rebuild path from the source of truth. A common design keeps the database as the record and Redis as the fast ranking view.

33. Heap vs sorted set vs sketch for top-K: how do you choose?

A heap of size K is the right tool when you can see all data in one place and only need the K biggest, with O(K) memory and O(n log K) time, but it cannot give a player's rank. A sorted set supports rank, range reads and updates by key, at the cost of holding all items. A Count-Min Sketch plus a heap handles a stream with far too many distinct items, trading exactness for tiny memory, with counts that can be a little high. In a distributed setting each approach needs a merge step: merge heaps from shards, scatter-gather sorted sets, or add sketches.

34. Why would you choose OT over CRDT, or the opposite?

OT is attractive when there is a central server anyway: it keeps documents compact, and a single server order simplifies correctness. Its weakness is complex transform code and difficulty without a server. CRDTs work peer to peer and offline, and merging is mathematically safe in any order, but they carry per-character metadata and need garbage collection, and some features (such as undo and permission checks) need extra care. For a product like Docs with always-online clients, server OT is fine; for offline-first apps, local-first notes or multi-region active-active, a CRDT is the natural choice.

35. When is approximate good enough, and how do you say that in an interview?

Approximation is fine when the error is small compared with the decision made from the number: dashboards, trending, "about how many", dedup that errs on the safe side. It is not fine for money, inventory, security decisions or anything audited. I would say the error bound out loud (HLL about 0.8%, Bloom 1% false positives and no false negatives, CMS overcount of at most epsilon times N), name the memory saved (12 KB vs gigabytes), and name the exact fallback path for cases that need precision. That shows that I know the error direction and the limits, not just the names.
