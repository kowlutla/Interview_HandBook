0. Key definitions (know these cold)

1. Observability: logs, metrics, traces Ch 54

One line: monitoring tells you something is wrong (known questions); observability lets you ask why (new questions). Use a metric to detect, a trace to find where, a log to see exactly what.

Metric types

  • Counter: only goes up (requests total). Read it as a rate.
  • Gauge: goes up and down (queue depth, memory).
  • Histogram: counts per range (bucket). Use for latency; can be added across servers.
  • Summary: percentiles computed in one process; cannot be merged across servers.

Logs done well

  • Structured (JSON) with the same field names everywhere
  • Levels with discipline: ERROR needs a human, WARN is handled but odd, INFO is business events, DEBUG is off in production
  • A correlation (trace) id on every line
  • Never log passwords, tokens or card numbers

Traces

  • Each unit of work is a span with a start, duration, attributes
  • The trace id travels in a header (W3C traceparent)
  • Head sampling: decide at the start, cheap. Tail sampling: decide after, keeps errors and slow ones
  • Exemplars link a slow histogram bucket to one example trace

Cardinality: the way metrics systems fall over

TopicOption AOption BPick
Metric collectionPull (Prometheus scrapes /metrics): server controls load; a failed scrape is itself a signalPush (agent sends): works for short jobs and clients behind firewallsPull for long-running services; push (or a gateway) for batch jobs and serverless
Latency numberAverage: hides the tailPercentiles from merged histogramsAlways percentiles (p50, p95, p99), per outcome
FrameworkRED: rate, errors, duration (caller's view)USE: utilization, saturation, errors (resource's view)RED to detect, USE to find the bottleneck. Golden signals = RED + saturation
Numbers: 1,000 requests, 980 at 100 ms and 20 at 10,000 ms: mean is 298 ms (nobody's real latency), p50 is 100 ms, p99 is 10,000 ms. A page making 30 backend calls with a 2% slow chance each hits at least one slow call 1 - 0.98^30 = about 45% of the time. Logs: 5,000 req/s x 5 lines x 500 B = 12.5 MB/s = about 1 TB/day for one service. Metrics: 100,000 series scraped every 15 s is about 6,700 samples/s, under 1 GB/day compressed.
Trap: averaging p99 values across servers. A percentile of percentiles means nothing. Add the histogram bucket counts across servers first, then compute the percentile. Also never compute SLIs from sampled data, and measure latency of successes separately, because a flood of instant 500s makes a broken service look fast.
Say: "Metrics for detection and SLOs, traces for where the time went, logs for the exact detail. I keep metric labels bounded and put high-detail fields like user id in logs and traces."

Logging and tracing in practice

  • Volume control: lower levels, drop health-check noise, rate-limit repeated lines, sample routine successes, always keep 100% of errors and audit events. Tier storage: hot and searchable for days, cheap object storage for months.
  • Never block the request on logging. Write to a buffer; when the buffer is full, drop logs, not requests.
  • Wide events: one rich record per request with dozens of fields (tenant, version, region, downstream times). You can then slice by any field, which is what unknown problems need.
  • Profiling: continuous low-overhead sampling of call stacks gives a flame graph that shows the exact hot function when metrics and traces say "this service is slow" but not why.

2. SLIs, SLOs, error budgets and alerts Ch 54

One line: measure what users feel (SLI), set a target (SLO), treat the gap to 100% as a budget you may spend, and page people only when that budget is burning fast.
SLOError budgetBad time per 30 daysTypically needs
99%1%7 h 12 minOne region, manual recovery is fine
99.9%0.1%43.2 minMulti-AZ, automated failover, safe deploys
99.95%0.05%21.6 minFast rollback, strong on-call
99.99%0.01%4.3 minMulti-region, automation only (humans are too slow)
99.999%0.001%26 sExtreme engineering, rarely worth it end to end

Good SLIs by type

  • Availability: non-5xx answers / valid requests
  • Latency: successes under 300 ms / all successes (threshold form, not a raw percentile)
  • Freshness: records updated within 5 min / all records
  • Correctness: outputs matching known-good answers
  • Batch: jobs done before deadline; consumer lag; oldest message age

Error budget policy (agreed in advance)

  • Over 50% left: ship normally, take planned risk
  • Under 25%: extra review, reliability work first
  • Zero: freeze feature releases; only reliability and security fixes
  • One incident using over about 20%: blameless postmortem with tracked actions

SLO design

  • Rolling window (28 or 30 days) for operations; calendar window for contracts
  • Serial dependencies multiply: 0.9999 x 0.9995 x 0.999 x 0.9999 = about 99.83%
  • One SLO per user journey: checkout 99.95%, recommendations 99.5%
  • Never aim at 100%

Burn-rate alerts

The naive alert "error rate above 1% for 5 minutes" ignores what you promised. A burn-rate alert asks: at this speed, when does the budget run out? Burn rate = observed error ratio / allowed error ratio (1 - SLO). Each rule needs two windows to agree: a long one to prove the problem is big, and a short one (about one twelfth) to prove it is still happening now, so the alert clears soon after you fix it.

ActionBurn rateLong windowShort windowBudget gone at firingError ratio (99.9% SLO)

Numbers: 100 req/s for 30 days = 259.2 million requests. At 99.9% the budget is 259,200 bad requests. A deploy failing 20% of requests for 10 minutes = 100 x 600 x 0.2 = 12,000 bad = about 4.6% of the budget. Burn rate example: 1.44% errors on a 0.1% budget is burn rate 14.4; budget lasts 720 / 14.4 = 50 hours.
Trap: paging on causes (CPU 90%, one pod restarted). Page on symptoms users feel; use cause alerts only for sure-to-become-a-problem signals such as a disk filling or a certificate expiring. Also: low-traffic services make ratios jumpy, so add a minimum request count or synthetic traffic.
Say: "Checkout SLO is 99.95% availability and 99% of successful calls under 1 s, rolling 30 days. I page on fast burn rate, ticket on slow burn, and freeze risky releases when the budget is gone."

  • Incident order: detect, triage (name an incident commander), mitigate first (roll back, flip a flag, fail over, shed load), communicate (status page), resolve, then a blameless postmortem with owned, dated actions.
  • Dashboards: overview first (SLO status, remaining budget, RED), then resources (USE), deploy markers on every graph, drill-down links to logs and traces.
  • Alert hygiene: every page links a runbook; group and deduplicate in the alert manager; silence a parent failure's children; target at most two pages per 12-hour shift.
  • Observability cost: 5 to 15% of the infra bill is normal; 40% is a smell. Example: 5,000 req/s x 12 spans x 300 B = about 1.55 TB/day of traces; keep 5% normal plus all errors plus slow ones (about 6.5%) = about 100 GB/day.

3. Security: thinking, passwords, sessions, JWT Ch 55

One line: list what you protect and who attacks it, then use layers (defense in depth), least privilege, and "never trust input or the network".
  • Threat modeling (STRIDE-lite): pretend to be someone else (spoofing), change data (tampering), deny an action (repudiation, so keep audit logs), leak data (disclosure), knock it over (denial of service), gain more rights (elevation).
  • Authentication is not authorization. Prove identity first, then check each action against permissions. Check on every request, on the server.

Passwords

  • Store a slow, salted, memory-hard hash: Argon2id (best), bcrypt or scrypt, tuned to a few hundred ms
  • Salt: random per user, stored with the hash. Pepper: a secret kept outside the DB (in a KMS)
  • Defend login: rate limit, lockout with care, breached-password check, MFA or passkeys
  • Encoding (Base64) and fast hashes (plain SHA-256) are not password protection

Sessions vs tokens

  • Server session: random id in a cookie, state on the server. Easy to revoke, needs a shared store
  • Stateless token (JWT): carries claims, checked by signature. Scales easily, hard to revoke
  • Cookie flags: HttpOnly (script cannot read), Secure (HTTPS only), SameSite (limits cross-site sends)

Browser attacks

  • XSS: attacker script runs in your page. Fix: escape output, Content Security Policy, HttpOnly cookies
  • CSRF: another site makes the browser send your cookie. Fix: SameSite, anti-CSRF token, check Origin
  • CORS: a browser rule, not a security wall for your API

JWT checklist

A JWT has a header (algorithm, key id kid), a payload of claims (iss issuer, aud audience, sub subject, exp expiry) and a signature. A correct validator checks, in order: algorithm is on a server-side allow-list; signature verifies with the key found by kid from a trusted key set (JWKS); iss matches; aud includes this service; exp and nbf are valid (allow about 60 s clock skew).

IssueWhat goes wrongFix
alg: none / algorithm confusionAttacker picks the algorithm, even "no signature", or signs with the public key as if it were a shared secretNever let the token choose the algorithm; fix it per key
Long-lived access tokenA stolen token works for hours; revoking is hard because nobody asks the issuerShort access token (5 to 15 min) plus a rotating refresh token; small deny list for urgent revokes
Token in local storageXSS can read itRefresh token in an HttpOnly, Secure, SameSite cookie
Key leak or old keyForged tokensPublish keys via JWKS and rotate (for example every 90 days)
Trap: "JWTs are stateless so we do not need revocation." You do. State the trade-off: short lifetime, refresh rotation, a deny list for the rare emergency, and sender-constrained tokens (DPoP or mTLS-bound) for high risk.

4. OAuth, service identity, access control, encryption Ch 55

One line: users log in with OIDC and get short tokens; services prove themselves with mTLS and workload identity; every request is checked against roles or relationships; data is encrypted in transit and at rest with managed keys.
FlowUse forNote
Authorization code + PKCEWeb, mobile, single-page apps (all user logins)Current default. Implicit flow is deprecated
Client credentialsService to service, no userPrefer signed client assertion or mTLS over a plain secret
Device codeTVs, consoles, CLIs with no browserUser approves on another device
API keyIdentify a calling app or customerWeak identity: hash it at rest, scope it, allow rotation, rate limit per key

Service to service

  • mTLS: each service proves who it is; short-lived certificates from a workload identity CA (a mesh does this)
  • Token exchange: narrow the user's token to each downstream audience
  • Do not trust plain identity headers; strip client-supplied ones at the gateway

Access models

  • RBAC: roles (admin, editor). Simple, can explode into many roles
  • ABAC: rules on attributes (same department, business hours)
  • ReBAC: relationships (viewer of folder implies viewer of its files), Zanzibar-style tuples doc:readme#viewer@user:alice
  • Multi-tenant: put tenant id in every query, enforce in the data layer too

Where to enforce

  • Gateway: authentication, coarse scopes, rate limits, schema and size checks
  • Each service: fine-grained "can this user touch this object" (it knows the data)
  • Both: defense in depth

Encryption, keys, secrets

ToolPurposeReversible?Example
HashCheck integrity, store passwords (slow hash)NoArgon2id, SHA-256 of a file

  • Secrets: keep them in a secrets manager, not in code, images or env files in git; short-lived dynamic credentials; rotate; audit access.
  • API risks to name: broken object-level authorization (changing an id in the URL, the top one), mass assignment (client sets fields like isAdmin), injection (use parameterized queries), SSRF (server fetches a URL the attacker chose, aimed at internal or metadata addresses: block private ranges and use an egress proxy), and no rate or size limits.
  • DDoS and bots: CDN absorbs floods, WAF filters known bad patterns, rate limits per IP, user and tenant.
  • Audit log: who did what, when; append-only and tamper evident; separate from application logs; no secrets inside.
  • Supply chain: pin and scan dependencies, sign builds, limit what CI can do.
  • Safe file upload: upload straight to object storage with a pre-signed URL, check type and size, scan for malware, serve from a separate domain.
Trap: checking permissions only on the page or gateway. The attacker calls the API directly with another user's object id. Authorize on the object, on the server, every time.
Say: "Login by authorization code with PKCE, a 10-minute JWT, rotating refresh token in an HttpOnly cookie. Gateway validates and rate-limits, services mint internal tokens and use mTLS. Data uses envelope encryption with a key per tenant."

5. Privacy: personal data, deletion, residency Ch 56

One line: collect less, keep personal data in one place, and design deletion from day one, because data is copied into caches, search indexes, logs, events and backups.
  • What is personal data: names, emails, phone numbers, but also IP addresses, device ids, cookie ids and location. It hides in logs, analytics events, URLs, error messages, search indexes and support tickets.
  • GDPR and CCPA as design needs: know what you hold and why; let people see, export and delete it; delete in a stated time (30 days is a common promise); breach notice to the regulator within 72 hours (GDPR); keep a record of consent.
  • Minimization: do not collect what you do not need. Choose between pseudonymization (replace the name with an id but a mapping exists, still personal data), anonymization (cannot be linked back, no longer personal data, hard to do well), tokenization (swap a card number for a random token held in a vault), and plain hashing (weak for small input spaces like phone numbers).

Deleting a user everywhere

StoreHow to delete
Main DBSoft delete first, then purge. Anonymize rows other users depend on (author becomes "deleted user")
Cache and CDNShort TTL; explicit purge; do not cache PII in shared edge caches
Search indexDelete documents by user id
Object storageDelete the user's prefix and all versions, then a CDN purge
LogsKeep PII out with redaction, short retention (14 to 30 days), then deletion is "wait for expiry"
Event streams (immutable)Store only user id; encrypt payloads with a per-user key and delete the key (crypto-shredding); tombstone latest-state topics

Numbers: 100M users, 0.05% delete per month = 50,000 jobs a month, under 2,000 a day, about one a minute. A simple durable job queue is enough. Residency: keep a user's personal data in their region (cells), replicate across regions only non-personal data; this conflicts with global active-active replication.
Trap: saying "we delete the row". Event logs, caches, search, analytics, backups and vendors still hold the person. Say the retention number out loud: "backups roll off after 35 days, so a delete is fully effective within 35 days."
Say: "Personal data lives in one vault, everything else holds an opaque id. Deletion is a soft delete, a grace period, then an event that every store owner handles idempotently, with a sweep to prove it."

Worked example: 1M daily users x 50 requests = 50M requests a day (about 580/s average).   • Build vs buy: buy what is not your edge (identity, email, search) when the bill is smaller than the engineers it would take; build when it is core or the bill is huge.
  • Unit economics: if a free user costs 4 cents a month to serve and a paying user pays 10 dollars, it works. Show cost per user, per request, per GB stored.
Trap: optimizing app servers while egress, storage and logs dominate; moving data to a cold tier that you read again next week (retrieval fees and minimum duration cost more).

7. Mobile: bad networks, offline, push Ch 56

One line: a phone is slow, unreliable, battery-limited and in the user's hand, so the app writes locally first, syncs deltas, retries politely, and uses push only as a hint.
  • The environment: connections drop mid-request, latency swings from 30 ms to seconds, the OS kills background apps, battery and data plans matter, and old app versions live for years (so APIs must stay backward compatible and a kill switch must exist).

Notes sync example: 20M users x 200 notes x 5 KB = 1 MB each = 20 TB (about 60 TB with 3 copies). 8. Say-aloud script (about 60 seconds)

  1. "For operations, I would set SLOs from user journeys: checkout at 99.95% availability and 99% of successful calls under 1 second over a rolling 30 days."
  2. "Every service exports rate, errors and latency histograms, plus saturation for queues and pools. Trace ids flow through every call and queue, with tail sampling that keeps errors and slow requests."
  3. "I page on fast and medium burn rate of the error budget and file a ticket on slow burn. Each page has a runbook, and the default fix for a bad deploy is rollback."
  4. "On security: authorization code with PKCE, short-lived JWTs, mTLS between services, authorization checked on the object in each service, and envelope encryption with a key per tenant."
  5. "For privacy, personal data lives in one vault, other services hold opaque ids, and deletion is an idempotent event pipeline with a sweep, with backups rolling off in 35 days."
  6. "On cost, I would check egress, storage and logs first, use a CDN, tier and expire data, and use spot for retry-safe work. On mobile, local-first with delta sync, backoff with jitter, and push as a hint."

9. Interview Q&A (30)

A. Concepts

1. What is the difference between monitoring and observability?

Monitoring watches a list of signals you chose in advance and tells you when one crosses a line, such as error rate above 1%. It answers known questions. Observability is a property of the system: its telemetry is rich enough that you can ask new questions after something strange happens, like "why are Android users of tenant 4471 slow on checkout since 14:05?" To get there you need detailed events or traces with attributes you can group by. In an interview I say you need both: monitoring wakes you up, observability gets you from the symptom to the cause quickly.

2. When do you use logs, metrics and traces?

Metrics are cheap numbers over time, so they are best for alerts, dashboards, trends and SLOs. Traces follow one request through many services, so they show where the time went or which downstream call failed. Logs hold the full detail of single events, so they answer what exactly happened for one request, and they serve as audit records. A real incident uses all three in order: a metric alert says the error rate is up, a trace shows the payment call is slow, and a log line shows the card network returned a timeout. Detail and cost both rise from metrics to traces to logs, so I detect with the cheap one and explain with the expensive one.

3. Why do averages lie for latency, and how do you aggregate percentiles?

Latency has a long tail. With 1,000 requests where 980 take 100 ms and 20 take 10 seconds, the average is 298 ms, which matches nobody. The p99 of 10 seconds shows the real pain. The tail also matters more with fan-out: a page making 30 calls with a 2% slow chance each is slow about 45% of the time. You cannot average p99 values from different servers. Instead each server exports a histogram with the same buckets, you add the bucket counts, and then you compute the percentile from the merged histogram. Put a bucket edge exactly at your SLO threshold so the answer is accurate there.

4. What are SLI, SLO, SLA and error budget?

An SLI is a measurement of good events over valid events, such as requests that succeeded in under 300 ms. An SLO is the internal target for that measurement, for example 99.9% over a rolling 30 days. An SLA is the contract with customers, with credits if broken, and it is normally looser than the SLO so you have a margin. The error budget is 100% minus the SLO, so 0.1%, which is about 43 minutes of full outage a month. The budget turns reliability into something you can spend on launches and risky changes, and it gives product and engineering a neutral rule for when to slow down.

5. Explain a burn-rate alert and why it uses two windows.

Burn rate is the observed error ratio divided by the allowed error ratio. A burn rate of 1 uses the whole budget exactly at the end of the window; 14.4 on a 30-day budget means the budget is gone in about 50 hours and 2% is spent each hour. A single window has a trade-off: long windows are slow to clear after a fix, short windows are noisy. So each rule needs a long window to prove the problem is large and a short window, about one twelfth as long, to prove it is happening now. Typical rules are 14.4x over 1 hour and 5 minutes (page), 6x over 6 hours and 30 minutes (page), and 1x over 3 days and 6 hours (ticket).

6. What is the difference between authentication and authorization, and where do you do each?

Authentication proves who the caller is: a password with MFA, a passkey, a token, or a service certificate. Authorization decides what that caller may do with a specific thing. The gateway typically does authentication, validates tokens, applies coarse scopes and rate limits. Each service then does the fine check, such as "may this user read this order", because it knows the object and its owner. If you only check at the gateway, one bug or one internal caller skips it. Missing object-level checks, where changing an id in the URL shows another user's data, is the most common API flaw.

7. How does OAuth 2.0 authorization code with PKCE work, and why PKCE?

The app sends the user to the login server along with a hash of a random secret (the code challenge). The user logs in there, and the server redirects back with a short code. The app then calls the token endpoint directly, sending the code plus the original secret (the verifier). The server checks the hash matches and returns a short-lived access token and a refresh token. Phones and browser apps cannot keep a client secret, so if someone intercepts the code, without the verifier it is useless. Current advice is to use PKCE for every client. The implicit flow, which put tokens in the URL, is deprecated.

8. What is envelope encryption and why use it?

You encrypt the data with a data key, and you encrypt (wrap) the data key with a master key held in a KMS or hardware module. The wrapped data key is stored beside the data. This is used because the master key never leaves the key service, big data never travels to it, and each tenant or object can have its own data key. Rotating the master key means re-wrapping small data keys instead of re-encrypting terabytes. It also makes deletion simple: destroy the data key and the data is unreadable. Large customers can bring their own master key.

B. Design scenarios

9. How would you set up monitoring for a new checkout service?

First I define the SLIs from the user's view: share of checkout requests that return non-5xx, and share of successful ones under 1 second, with a 99.95% and 99% target over a rolling 30 days. Then each service exports RED metrics with latency histograms, and USE metrics for the pools, queues and replicas it depends on. Trace ids go through every call and message, and logs are structured with the trace id and tenant. Alerts are burn-rate based: fast and medium burn page, slow burn is a ticket. A synthetic checkout runs every minute from several regions, deploys are marked on graphs, and each alert links to a runbook. Rollout is by canary against the same SLIs.

10. Design the authentication for a multi-tenant SaaS API.

Users log in with a password hashed by Argon2id, plus MFA or passkeys, through authorization code with PKCE. They get a 10-minute JWT signed with an asymmetric algorithm whose keys are published through JWKS and rotated, plus a rotating refresh token in an HttpOnly, Secure, SameSite cookie. The gateway checks the signature, algorithm allow-list, issuer, audience, expiry and scopes, strips any client-supplied identity headers, rate-limits per IP, user and tenant, and mints a short internal token with tenant id and user id. Services talk over mTLS from a workload identity. Every query includes the tenant id, and data is encrypted with a per-tenant key.

11. Design GDPR "delete my account" for an app with many data stores.

I start with a data map of every store: main DB, media, search, warehouse, notification tokens, event streams, backups and vendors. The request returns fast: verify the user, soft delete, revoke sessions and tokens, hide data behind a deletion filter, and queue a job with a 14-day recovery window. After that, a deletion event goes to every store owner, each handler is idempotent and retried with backoff. Immutable logs hold only user ids with payloads encrypted under a per-user key, so deleting the key shreds them. A sweeper checks each store for zero rows, records a hashed-id entry in a ledger, and the job closes only when all owners confirm. Backups roll off at 35 days and the ledger is replayed after any restore.

12. Design an offline-first notes app sync.

The app writes every edit to local SQLite and adds a mutation to an outbox, each with a unique id, note id and base version. The sync engine pushes the outbox when online, with backoff and jitter on failure, and the server remembers recent mutation ids per device so repeats return the earlier result. Each user has a change log with an increasing sequence number, and the client's sync token is the last number it has seen. After pushing, the client pulls changes since its token, applies them in one transaction, and only then saves the token. Conflicts merge by field or by a three-way text merge, and if that fails the server keeps a conflicted copy. Push or a WebSocket only says "changes exist", it does not carry note content.

13. Design push notifications for a mobile app at scale.

The notification service takes "tell user 42 about this comment", applies preferences, rate limits and deduplication, builds the platform payload with a title, body, deep link and collapse key, and sends it to APNs or FCM over HTTP/2 using signing credentials. Device tokens are stored per user and device and removed when the platform says a token is invalid. For a broadcast to 50 million devices, I split the audience into batches processed by many workers, and spread the sending over time so the origin of the follow-up requests is not hit all at once. I say clearly that push is best effort, may be delayed or dropped, so the app also pulls on launch.

14. How would you cut the cloud bill of a service that doubled in cost?

I do not guess. I break the bill down by line: compute, database, storage, egress, observability, and per request and per user. Then I go for the biggest line. Typical wins: put a CDN and cache in front of reads so the origin sees a twentieth of the traffic, compress and tier old data with lifecycle rules, cut log volume and sample traces, right-size fleets that run at 15% CPU, buy commitments for the steady baseline, and move retry-safe batch work to spot instances. I also check for a runaway cost such as a loop of retries or cross-zone traffic. I report the result as cost per active user so the trend is clear.

C. Failures and real-time production scenarios

15. You get paged: checkout error rate jumped. What do you do?

First I look at the alert, user impact and which journey or region is hit, and I name an incident commander if it is serious. Then I check the deploy and config markers on the dashboard, because most incidents start with a change. If a deploy lines up, I roll back first and investigate afterwards, since restoring users is the goal. If not, I use traces to find the slow or failing span and logs for the exact error, and I check dependencies and saturation of pools and queues. I post updates on the status page, mitigate with a feature flag, failover or load shedding if needed, then confirm recovery on the SLI and write a blameless postmortem with owned actions.

16. The monitoring bill suddenly tripled. What happened and how do you fix it?

The usual causes are a metric with a new unbounded label (user id, full URL) that created millions of series, a debug log level left on, a retry loop writing errors, or a new service tracing every request. I check series count per metric, bytes per service per day, and spans per trace, and compare with the last deploy. The fix is to remove or bound the label, drop the noisy log lines, set sampling (keep errors and slow requests, sample routine successes), and shorten retention for raw data. Afterwards I add a budget and an alert on series count and log volume per team so it cannot happen silently again.

17. A stolen access token is being used. What do you do?

I first limit the damage: revoke the user's refresh tokens and sessions, and add the user or token id to the deny list that the gateway checks, because a short-lived JWT would otherwise be valid until it expires. Because access tokens last only about 10 minutes, the window is small. I check audit logs for what the token did, force a password reset or re-authentication if needed, and notify the user. Then I find how it leaked (XSS, logs, a bad client) and fix it. Longer term I would use sender-constrained tokens (DPoP or mTLS-bound), so a stolen token is useless without the private key.

18. Your signing key may have leaked. What now?

I treat it as an emergency. I generate a new key pair, publish the new public key in the JWKS with a new key id, switch signing to it, and remove the old key from the trusted set, which makes all tokens signed with the old key fail. Users will have to log in again, which is acceptable. I check logs for tokens signed by the old key after the suspected leak time, find the cause of the leak, and move the key into a KMS or HSM so that code never sees the private key. Regular rotation, for example every 90 days, makes this a routine event and not a crisis.

19. A user says they were deleted, but their name still shows in search. Why?

Most likely one store did not process the deletion event, or the search index copy is updated asynchronously and the document stayed. Another possible cause is a cache or CDN holding a copy, or a denormalized copy in another index. I check the deletion job: which store owners acknowledged and which did not, and whether a handler failed and retried. The deletion filter should already hide the user in reads, so I also check that. The fix is to delete by user id in the index, purge the caches, and add the sweeper check for that store so a miss is caught. I also alert on any job older than 20 days.

20. After an outage, a million phones hammer the API and it cannot recover. Why, and how do you fix it?

This is a retry storm. Clients retried every second without waiting longer, so the load after recovery is far bigger than normal, and the server falls over again. On the client the fix is exponential backoff with random jitter and a cap, retrying only network errors, timeouts, 5xx and 429, with a circuit breaker. On the server I shed load with 429 or 503 and a Retry-After header, rate-limit per client, and bring traffic back gradually. For the future, the app should respect Retry-After and have a remote kill switch to pause noisy features.

21. Alerts fire all night and the team ignores them. What do you change?

Alert fatigue is a reliability risk because a real page gets lost. I review every alert against three questions: is it urgent, can a human act on it, and does it map to a user symptom? Cause-based alerts like CPU above 90% become dashboards or tickets. I replace static thresholds with burn-rate alerts, group and deduplicate in the alert manager, and inhibit child alerts when a parent such as a shared database is already paging. Every page gets a runbook. I measure the share of pages that led to action and aim for no more than two incidents per 12-hour shift.

22. A restore from backup brought back users who had been deleted. How do you prevent this?

Backups are immutable copies, so a restore brings back everything that existed when they were taken. The rule is to keep a deletion ledger, a log of hashed user ids and timestamps that lives outside the backups. After any restore, and before the database serves traffic, you replay the ledger so deleted users are removed again. You also keep backup retention short and bounded, for example 35 days, so old data ages out, and you use crypto-shredding for long archives so a deleted user's key is gone and the restored data cannot be read.

D. Trade-offs and why-questions

23. Why not set the SLO to 100%?

It is impossible in practice, because the user's own phone, network and browser fail more often than that, so the user cannot see the difference. Each extra nine costs far more, often needing a different architecture such as multi-region active-active. And with a zero error budget you could never ship a change, since every change carries risk. I choose a target from user need and cost, set it slightly below what I reliably achieve, use different targets for different journeys, and revise it. For example, checkout might be 99.95% while recommendations are 99.5% and degrade gracefully.

24. Why page on symptoms instead of causes?

A symptom, such as errors or slowness, is what users feel. A symptom alert covers every cause, including ones you never predicted. A cause alert, such as high CPU on one node, may fire when nothing is wrong, waking someone for no reason, and stays silent when an unexpected cause breaks users. So I page on symptoms (burn rate on the SLI) and keep cause metrics on dashboards for diagnosis. I make an exception for causes that are certain to become symptoms soon, like a disk that will be full in four hours or a certificate expiring in three days, and those usually go to a ticket or a lower-urgency page.

25. Pull or push for metrics?

Pull, as in Prometheus, lets the monitoring system decide when and what to collect, so a flood of senders cannot overload it. A failed scrape is itself a signal, because the up metric drops to zero, and you can open the /metrics URL by hand to debug. Push works better for short-lived batch jobs and serverless functions that finish before a scrape, and for clients behind firewalls. The weakness of push is that a silent service looks the same as a healthy quiet one unless you add heartbeat checks. In practice I pull from long-running services and let batch jobs push to a small gateway that is then scraped.

26. Server sessions or JWTs?

A server session is a random id in a cookie with state in a shared store. Revoking is easy: delete the entry. The cost is a lookup on every request and a store that must be highly available. A JWT carries its claims and is checked by signature, so any service can validate it without a lookup, which scales well across many services. The cost is that you cannot easily revoke it before it expires. I pick JWTs for service-to-service and API access with short lifetimes (5 to 15 minutes), and keep a server-side, revocable refresh token. For a simple single web app with one backend, a server session is often the simpler and safer choice.

27. RBAC, ABAC or ReBAC?

RBAC assigns permissions to roles such as admin or editor. It is simple to explain and audit, but can lead to a huge number of roles. ABAC writes rules over attributes, such as "same department and during business hours", which is flexible but harder to reason about. ReBAC models relationships, such as "viewers of a folder can view its documents", which fits sharing models like documents or drives, and Zanzibar-style systems store relation tuples for it. I start with RBAC for coarse access, add ReBAC for object sharing, and use a policy engine so rules are code that is tested and versioned. In multi-tenant systems, the tenant id check is enforced in every query as well.

28. Why put personal data in a vault instead of in each service?

If every service stores names and emails next to its own data, deletion, export, access control and breach impact all multiply across services. With a vault, only one small, heavily protected service holds personal data, and every other service stores an opaque random user id. Deletion becomes mostly "delete the vault record", after which activity data elsewhere cannot be linked to a person. A stolen orders table holds no names. Residency is easier, because only the vault must be in the user's region. Auditing is also one choke point. The cost is an extra network hop, which you reduce with short, safe caching of non-sensitive fields.

29. On-demand, reserved or spot instances?

On-demand has no commitment, so I use it for unpredictable or new workloads. Reserved or savings plans save roughly 30 to 60% for a 1 to 3 year commitment, so I use them for the steady baseline I am sure to run, such as databases and a minimum fleet. Spot saves roughly 60 to 90%, but the provider can take the instance back with about 2 minutes' notice, so it is for retry-safe work: batch, CI, queue workers and stream processing with checkpoints. To use spot safely, make tasks idempotent, checkpoint progress, spread across instance types and zones, and drain on the termination notice. I mix all three, with autoscaling on top.

30. Why delta sync and push-as-a-hint for mobile, instead of polling or sending full data?

Full downloads waste battery, data and money. In the notes example, re-downloading everything costs about 8 TB a day of avoidable egress, roughly 700 dollars a day, while delta pulls are a few hundred bytes. Constant polling wakes the radio, drains the battery and loads the server. Push is efficient but not guaranteed, and platforms may delay or throttle it, so putting the real data in it would lose updates. So the design is: push or WebSocket says "something changed", then the app pulls changes since its token, and it also pulls on launch and foreground. That gives low cost, low battery use, and no lost updates.
