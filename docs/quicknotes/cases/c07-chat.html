Case Sheet 7: Design a Chat System

One-page revision of the WhatsApp / Messenger style design. Full write-up: Handbook case study 7.

ProblemRequirementsEstimationAPIDataArchitectureFlowsDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: build a chat service for 500 M users (300 M daily): 1:1 and group chat, instant delivery when online, safe delivery when offline, the same order for everyone in a conversation, and read receipts.
  • The hard parts are holding about 100 million open connections, keeping order, and never losing or duplicating a message.
  • Do not start drawing. Spend about 5 minutes turning the vague prompt into precise requirements.
Ask thisAssume this
1:1 only or groups?Both. Groups up to 1,000 members. Broadcast channels of up to 1 M subscribers as an extension.
Which clients? Devices per user?Mobile and web or desktop. Up to 4 linked devices per user.
How many users?500 M registered, 300 M daily active users (DAU).
Message types and size?Text up to 4 KB. Media (image, video, voice, file) up to 100 MB.
Delivery promise?Online recipient sees it in under 500 ms at p99 in one region. Nothing lost after "sent". No duplicates shown.
Ordering?Same order for all members of one conversation. No promise across conversations.
Receipts, presence?Yes: sent, delivered, read; online and last seen; typing.
History and encryption?History kept (about 5 years default). End-to-end encryption (E2EE): server cannot read bodies.
Geography?Global, so several regions.
Say this: "I will state my assumptions on the board. The two that drive everything are 100 million simultaneous connections and order inside each conversation."

2. Requirements

Functional

  • Send and receive text, 1:1 and group, in real time
  • Status: sent (server stored it), delivered (device got it), read (user opened it)
  • Offline delivery plus a push notification
  • Media attachments
  • Presence and typing
  • Multi-device sync
  • History and search

Non-functional

  • Latency p99 under 500 ms in region, under 1 s across continents
  • Durable once acked: survives a machine or zone loss
  • At-least-once delivery plus dedupe, so it feels exactly once
  • 99.99% available
  • Total order per conversation
  • 100 M connections, about 1 M deliveries per second at peak
  • E2EE and TLS

Out of scope

  • Voice and video calls (WebRTC media path)
  • Payments
  • Stories or status posts
  • Bots and third-party APIs
  • Moderation of E2EE bodies (only metadata and user reports)

4. API (a few lines)

Two interfaces. A WebSocket (one long-lived two-way connection) carries messages, acks, presence and typing. Plain HTTPS REST does everything that is not latency critical.

client -> server  send          {client_msg_id, conv_id, body(ciphertext), media[]}
server -> sender  ack_sent      {client_msg_id, msg_id, conv_id, seq}
server -> device  msg           {conv_id, seq, msg_id, sender, ts_server, body}
device -> server  ack_delivered {conv_id, up_to_seq}      (cumulative)
device -> server  ack_read      {conv_id, up_to_seq}      (cumulative)
client -> server  typing / presence_sub                   (never stored)
client -> server  sync          {cursors:[{conv_id,last_seq}]}  on reconnect
RESTPurpose
POST /v1/devicesRegister device, E2EE keys, push token
GET /v1/ws-endpointNearest, least loaded gateway plus short-lived token
GET /v1/conversations/{id}/messages?before_seq=&limit=50History paging by sequence cursor
POST /v1/conversations, /membersCreate group, add or remove members
POST /v1/media/upload-urlPre-signed upload URL and blob_id
GET /v1/searchSearch
  • client_msg_id is chosen by the sender. It makes retries safe (idempotency): a resend returns the same msg_id and seq.
  • Receipts are cumulative ("up to N"), so one small frame covers many messages and a lost one is repaired by the next.

5. Data model and store choices

DataStoreWhy
Messages (the log)Wide-column store (Cassandra, Scylla, HBase style), partition key (conv_id, bucket), clustered by seqHuge append volume, range reads inside one conversation, linear scaling
Users, devices, groups, membershipSharded relational DB or strongly consistent KVSmall, relational, correctness matters
Session registry (user to gateway)Redis cluster10 GB, fast lookups, TTL expiry is natural
Sequence counters, device cursorsOwner shard memory plus durable log, or Redis/etcdAtomic increment with no gaps
MediaObject storage plus CDNCheap per GB, resumable upload, edge caching
SearchOn-device index (E2EE) or a search engineServer cannot read E2EE text
  • messages: PRIMARY KEY ((conv_id, bucket), seq), seq descending. "Latest 50" is one partition read. "After seq N" is a contiguous scan. No joins.
  • Why a time bucket? One endless partition for a busy group gets too big (over about 100 MB or 100 K rows hurts compaction and repair). A monthly bucket for a 1,000-member group is about 6 MB. Hot groups use day or hour buckets.
  • inbox(device_id, conv_id, last_seq_delivered, last_seq_read): the cursor table, one row per device per conversation.
  • pending(device_id, enqueue_ts, conv_id, seq): pointers only; the body lives once in messages.
  • dedupe(sender_device, client_msg_id) to (msg_id, seq), TTL about 7 days.

6. Architecture

  • L4 load balancer only spreads new connections (least connections, slow start). A socket then stays on its gateway for hours.
  • Gateway: TLS, token check, pings, rate limit. A crash loses connections, never messages. Chat logic can be deployed without dropping 100 M sockets.
  • Chat service: validate, dedupe, assign seq, write, route.

6b. Main request flows

  1. Alice's app sends with a fresh client_msg_id. If offline it queues locally and retries with the same id.
  2. The chat service checks the dedupe table. If the key exists, it replays the old ack. Otherwise it takes the next seq and appends with QUORUM (2 of 3 copies).
  3. Store confirms, so the message is durable. Alice gets ack_sent.
  4. For each recipient device (and Alice's other devices), look up the registry. Live gateway: internal RPC, write to socket. Offline: add a pending pointer and send a push.
  5. Bob's device stores it and acks cumulatively. Alice's devices are told "delivered". Read receipts travel the same way.
Say this: "Persist first, deliver second. If the service crashes after the ack, the message is in the store and the recipient's next sync finds it. Delivering first could show Bob a message Alice thinks was never sent."

7. Deep dives

7.1 Ordering: where does the sequence number come from?

Clocks fail: client clocks drift, server clocks differ by milliseconds, and two concurrent sends have no true "first". So each conversation has one place that hands out consecutive integers. seq is the order; the timestamp is display only.

OptionProsCons
A. Timestamp or Snowflake idNo coordinationDepends on clock skew; gaps are invisible so a lost message cannot be noticed
B. Counter per conversation (Redis INCR or DB)Simple, consecutive, gap detection worksExtra hop and failure point; hot for huge groups
C. Single owner per conversation shard (lease or consensus)Fastest, consecutive, can batch and drive fan-outNeeds leader election and fencing; a few seconds of pause on failover

Choice: C (B is fine to say at moderate scale). Shard by conv_id so one owner is the only writer. On failover the new leader reads the max seq from the store and continues after it. The store rejects writes from an older leader epoch, and a conditional insert (IF NOT EXISTS on conv_id, seq) is the fence. The client keeps the last contiguous seq per conversation; if it sees 48215 while holding 48213, it asks for 48214.

7.2 Routing: how does a message find Bob's socket?

OptionProsCons
Session registry (Redis) plus direct RPC to gatewayCheap, explicit, scalesEntries can be stale; needs a fallback
Pub/sub topic per userSimple to reason about100 M topics; brokers handle that badly
Hashed buckets (10,000 topics, filter locally)Middle pathEach gateway subscribes to many buckets and filters

Choice: registry plus RPC. TTL about 120 s, refreshed in batches every 60 s (not each 30 s heartbeat) to halve writes. Reads: 1 M/s at peak, so about 20 Redis nodes plus a short-TTL local cache. If the registry is stale, the gateway answers "no such socket" and we use the offline path. The registry is a hint; the store plus sync is the truth.

7.3 Delivery guarantees, offline and sync

PieceHow
Sender to serverRetry until ack_sent; dedupe by (sender_device, client_msg_id)
Server to deviceKeep the pending pointer until the device acks; device dedupes by (conv_id, seq) and still acks duplicates
ReceiptsStore only max up_to_seq per device per conversation; merge by max, so they converge

Choice: at-least-once on the wire plus dedupe at both ends gives exactly-once to the user. Exactly-once on the network is impossible because acks themselves get lost.

7.4 Group chat and fan-out

ApproachStorage per messageFits
Shared log per conversation (chosen)1 row; per-member state is only a cursorGroups and 1:1
Per-user inbox copyN rowsEmail-like systems with heavy per-user state; too costly at 1,000 members
  • Cache membership in the owner's memory. Skip registry lookups for members known offline.
  • Huge channels (1 M subscribers): one log plus a head seq. Send once per gateway that holds a subscriber, each gateway fans out locally. Offline subscribers do nothing at write time and compare their cursor to the head on reconnect (pull). Turn off receipts, typing, presence.

7.5 Presence and typing

NaiveBetter (chosen)
Broadcast every connect, disconnect and heartbeat to all contactsClient subscribes only to the contacts on screen. Server sends updates only to subscribers.
Write each heartbeat to a databaseKeep it in memory with a TTL. Write last-seen only on disconnect.
Show "offline" on any blipDebounce 20 to 30 s
Users watched by thousandsNo push; clients poll every 30 to 60 s or show nothing

Typing is ephemeral: never stored or retried. Refresh every 3 to 5 s, and the receiver hides it after about 6 s. Shed presence and typing first under load.

8. Scaling and bottlenecks

  • Gateways: limits are file descriptors, memory and TLS CPU. Use epoll-based runtimes, L4 only (no L7 proxy per frame), drain gradually on deploy.
  • Chat service: 4,096 virtual shards by hash(conv_id), assigned with consistent hashing. About 20 K msgs/s per server, so about 21 servers for 420 K/s; run 100 or more for fan-out and spare capacity.
  • Store: about 13 PB raw over about 2,500 nodes. Partitions are spread by hashed conv_id. Hot groups use smaller buckets. Old buckets are immutable, so compaction is cheap and they can move to cheaper disks.
  • Cache: last 50 messages of recently active conversations. About 1 TB at most across Redis. The phone's local database is the first-level cache; sync only the delta.
  • Media: separate path (pre-signed upload, CDN download), the biggest cost. Client encrypts first; forwarding reuses the blob id and key so a viral photo is stored once.
  • Multi-region: each conversation has a home region where its sequencer runs. A far sender pays one WAN trip (about 80 to 150 ms). A relay sends the message to the recipient's region. Store replication across regions is asynchronous. Registry and presence are regional.
  • 10x scale: cells (independent slices of gateways, registry and chat shards) limit blast radius.

9. Failure modes

Store slow or downSends stallReturn an error (no false "sent"); client keeps it in its outbox and retries. Shed typing and presence. Never ack before the quorum write.
Registry down or staleCannot find gatewaysTreat everyone as offline: pending plus push; sync still delivers. Slower, still correct.
Push provider outageNo wake-upsRetry with backoff; collapse keys; messages appear when the app opens

Common mistake: acking "sent" before the quorum write, or writing every heartbeat to a database. Both are classic ways chat designs fail.

10. Things to say to impress

  • "Numbers first: connections and media dominate, not message rate. That is why the connection tier is separate and media never touches the WebSocket."
  • "Order is a decision, not a fact. One sequencer per conversation gives consecutive integers, which also lets clients detect gaps."
  • "The registry is a hint with an always-correct fallback: the durable log plus cursor sync. A registry outage costs latency, not messages."
  • "At-least-once plus idempotency keys and sequence-based dedupe gives exactly-once to the user. Cumulative, max-merged receipts converge with no coordination."
  • "Push is only a wake-up with no plaintext. Correctness never depends on APNs or FCM."
  • "CAP per data type: refuse to ack when the log cannot reach quorum, but keep presence available and eventually consistent."
  • "Reconnect storms are the real outage risk. I design jitter, admission control and gradual drains from day one."
  • "Phasing: MVP 1:1 in one region, then groups and media, then leases, E2EE and abuse systems, then multi-region."
  • "E2EE costs us server search and scanning. Search moves on-device; reports carry the plaintext the user chooses to share."

11. Interview Q&A

Why WebSocket and not polling or long polling?

Chat needs server-to-client pushes and frequent small sends. Polling every 3 seconds for 100 million clients is about 33 million requests per second, mostly empty, with an average 1.5 seconds of added delay. Long polling cuts delay but re-opens a request after every message and repeats headers. A WebSocket is one connection with tiny frames both ways, costing a few KB of memory per user and a heartbeat every 30 seconds. We keep long polling as a fallback for networks that block WebSocket upgrades.

How does a message find the right gateway for Bob?

Gateways write user to device to gateway entries in a Redis session registry on connect and remove them on disconnect, with a TTL as a safety net. The chat service looks up Bob's devices, groups them by gateway and sends one internal RPC per gateway. If the entry is stale, the gateway replies "unknown socket" and we take the offline path. The registry is only an optimization. Correctness comes from the durable log and sync on reconnect.

How do you guarantee the same order for everyone in a group, even across regions?

We do not trust timestamps. Each conversation has a home region and an owner shard that hands out consecutive sequence numbers. Every sender, wherever they are, sends to the owner, which appends in arrival order and returns the number. Everyone renders by seq. A faraway sender pays one WAN round trip, about 80 to 150 ms, which fits the 1 second cross-continent goal. We avoid running consensus across regions for every message. If the owner dies, a new leader starts after the highest stored seq, and fencing stops the old one.

The sender's connection drops right after sending, before the ack. What happens?

The client cannot know if the server stored it. It keeps the message in a local outbox and, after reconnect, resends with the same client_msg_id. The chat service checks the dedupe table. If the key exists, it returns the original seq without writing again. If not, it processes it normally. The result is exactly one copy. The key is made by the client, not the server, precisely so a retry can be recognized.

Why store a group message once instead of once per member?

A 500-member group would multiply storage and write load by 500. The shared log keeps one row per message, and each member holds only a small cursor of last delivered and last read seq. Delivery is fan-out at send time to online members plus pending pointers for offline ones. The trade-off is that per-user state such as "delete for me" lives in a separate small table. Per-user copies only make sense when per-user state is heavy, as in email.

A whole zone fails and millions of clients reconnect at once. What do you do?

First, prevent it: clients use exponential backoff with random jitter (a random delay up to a cap that doubles, to about 30 seconds) and honor a retry_after hint. Servers add admission control: the load balancer limits new handshakes per second and gateways reject extra connections cheaply. During the incident I watch connections per gateway, TLS CPU, registry latency and sync queue depth. I shed typing and presence frames, and pace sync in batches so the store is not hammered. Nothing is lost, because every message was saved before it was acked.

How would presence work for a user with 5,000 contacts?

We never broadcast to all contacts. Online status comes from the registry plus fresh heartbeats, debounced for 20 to 30 seconds so tunnels do not cause flapping. Updates go only to clients that subscribed because they currently show that user. For very widely watched users we stop pushing and let clients poll slowly, or drop the feature. Presence lives in memory with TTLs and only last-seen is written durably on disconnect. It is eventually consistent and the first thing we shed under load.

How do offline delivery and push fit together?

If Bob has no live socket, the message is already stored. The service adds a pointer to Bob's pending queue and asks the push service to send an APNs or FCM notification. Because of E2EE the push carries no plaintext, only "new message" and a conversation id. It may be delayed or dropped, which is fine. The real delivery happens when the app opens a socket and sends its cursors, and the server streams what is after them. There is one catch-up path whether he was away ten seconds or ten days.

How does multi-device work with E2EE?

Each device is its own cryptographic endpoint with its own keys. The sender encrypts once per recipient device (or uses group sender keys) and the server fans out the ciphertext to all of Bob's devices and Alice's other devices. Each device has its own cursor and pending queue. A new device cannot read old history because it has no keys, so history moves device to device through an encrypted export or a client-encrypted backup. When the device list changes, contacts' apps are told so they encrypt to the new device and may show a warning.

Why a wide-column store and not just a relational database?

The access pattern is the same in both: append and range scan inside one conversation. A relational table keyed by (conv_id, seq), sharded by conv_id, works at moderate scale and needs no cross-shard transactions. At 12 billion messages a day, the sharding and rebalancing work is large, so a wide-column LSM store that partitions natively wins. The logical model does not change; we pick the engine for write throughput and operational ease. Kafka is not a good message store here because a partition per conversation does not scale to hundreds of millions of conversations.

How do you support a channel with a million subscribers?

Writing a pending pointer per subscriber would mean a million writes and lookups per post. Instead the channel has one log and a head seq. The owner sends once to each gateway that has at least one subscriber (a few thousand RPCs) and each gateway pushes to its local sockets. Offline subscribers cost nothing at write time; when they reconnect they compare their cursor to the head and fetch the difference. Receipts become counters or are disabled, and typing and presence are off. It is the same push and pull hybrid used for celebrities in news feeds.

Delivery is slow for some users. How do you debug it?

I follow one message with a trace id from the client frame through gateway, chat service and store, and compare steps. Then I check the likely suspects: store write latency at p99, pending queue depth and age, registry hit rate (misses push us to the slow offline path), relay lag between regions, and churn on the affected gateways. A rising gap-resync rate means frames are being lost on the wire. If only one region is slow, I look at the WAN relay and replica lag. I mitigate by shedding low-priority frames and moving load off the hot gateway.

Why not use timestamps or Snowflake ids for ordering?

They depend on clocks. Phones can be set to any time, and servers differ by milliseconds, enough to swap two messages typed a heartbeat apart. Also, with ids that have gaps, a client cannot tell whether a message is missing. Consecutive per-conversation sequence numbers fix both: everyone agrees on one order and a client sees a hole the moment seq 48215 arrives after 48213. We keep the timestamp only for display.
