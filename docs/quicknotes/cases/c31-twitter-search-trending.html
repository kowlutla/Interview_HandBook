Case sheet 31: Design Tweet Search and Trending Topics

One-page cheat sheet: find any post seconds after it is written, and show what the world is talking about right now. Full write-up: Handbook case study 31.

ProblemRequirementsEstimationAPIDataArchitectureDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: two features on one firehose of new tweets: search (which tweets contain these words, newest or best first) and trending (which terms are suddenly much more popular than normal).
  • Search needs an inverted index: a dictionary from each word to the list of tweets that contain it. Trending needs approximate counting of how fast a word is growing, over time windows.
  • Both must show events within seconds and survive spikes (a goal in a final, an earthquake) many times the average rate.
  • The defining requirement is freshness: a new tweet must be searchable within 10 seconds, so a nightly batch build is out.

Clarifying questions to ask (and the answers we assume)

2. Requirements

Functional

  • Index every public tweet by words, hashtags, mentions, phrases
  • Page of results by Top (relevance) or Latest (time), cursor paging
  • Filters: language, author, time range, media, minimum engagement
  • Deletes, suspensions, privacy changes show up in results
  • Trending list per place, refreshed about every minute

Non-functional

  • Freshness p99 under 10 s
  • Query p50 under 100 ms, p99 under 300 ms (recent tier)
  • 99.95 percent available. Fewer shards beats an error
  • Absorb 10x tweet spikes by buffering, not dropping
  • Eventually consistent. The index is derived data and can be rebuilt

Out of scope

  • Storing tweets and timelines (case 6)
  • Social graph, ads, people search
  • Image and video understanding
  • Typeahead as you type (case 11)

3. Estimation (same numbers as the handbook)

Write side: 500 M / 86,400 = about 5,800 tweets per second; peak 20,000 (3.4x). Tweet record about 1 KB: 20 MB per second at peak, 500 GB per day. About 15 index terms per tweet, so 500 M x 15 = 7.5 B postings per day (a posting means "term T is in tweet D").
Read side: 1 B / 86,400 = 11,600 per second; peak factor 3 gives 35,000. A result cache (5 to 30 s) absorbs about 40 percent, so the backend sees about 21,000 per second. Fan-out of 16 means about 336,000 partition-queries per second. A page of 20 tweets at 1.5 KB is 30 KB, so about 1 GB per second at the edge.
Index size: real-time posting about 4 bytes, so 7.5 B x 4 = 30 GB per day. Seven days: 210 GB postings + 84 GB attributes (3.5 B tweets x 24 bytes) + 8 GB dictionary (200 M terms x 40 bytes) = about 300 GB. Archive postings about 2.5 bytes: 182 B tweets per year x 15 x 2.5 = 6.8 TB, so about 10 TB per year; 5 years is 50 TB, 100 TB with two replicas.
Cluster: 16 partitions by hash of tweet id, each about 220 M tweets and 19 GB; 3 replicas, so 48 nodes. Each replica set serves 21,000 QPS, about 7,000 per replica. At about 1 ms CPU per partition-query on 16 cores (about 16,000 per second capacity) that is under 45 percent busy. Indexing is only 1,250 tweets per second per partition.
Trending: 3 candidate terms per tweet: 17,400 events per second average, 60,000 peak, 18 M in a 5-minute window at peak. One Count-Min Sketch per 5-minute bucket per worker is about 1 MB; 288 buckets (24 h) is under 300 MB. Kafka tweet topic: 500 GB per day, 3 days, 3 copies, about 4.5 TB.

Conclusion to say aloud: the hot index fits in the RAM of a modest cluster, so we shard for query throughput and fan-out, not for capacity. The archive is large enough to need SSD and a different structure. That gap is the argument for tiers.

4. API

GET /v1/search?q=world+cup+final&sort=top|latest&lang=en
    &since=...&until=...&from=user123&filter=media&limit=20&cursor=...
-> { results: [{id, author, text, created_at, metrics, score}],
     next_cursor, tiers_searched: ["realtime"], partial: false }

GET /v1/trends?place=us-ny&limit=20     (Cache-Control: public, max-age=30)
-> { as_of, trends: [{term, rank, volume_estimate, window: "1h", category}] }

Internal only: TweetCreated, TweetDeleted, EngagementDelta events on Kafka.
  • Cursor paging, not page numbers. New tweets keep arriving, so offsets would shift and repeat results. For Latest the cursor is "tweets with id below this"; for Top it holds the last score and id.
  • Tweet ids are time-ordered (Snowflake style). Sorting by id is sorting by time, a date filter becomes an id range, and picking a tier is a range check.
  • Partial results are explicit (partial: true) so a client can show a hint instead of silently showing less.
  • Trends are the same for everyone in a place, so the CDN caches them for 30 s and the origin sees almost no traffic.

5. Data model and store choices

Why tweets are easy to index: they are tiny (about 15 terms), their text never changes (postings are append-only; only counters and delete flags change), users want the newest matches (store postings newest first and stop early), and time-ordered ids split old from new for free.

6. Architecture and main flows

Write flow: tweet to searchable (1 to 3 s)

  1. Tweet service stores the tweet, then publishes TweetCreated to Kafka keyed by tweet id (duplicates are harmless because the id is carried).
  2. The ingester does the heavy work once: normalize text, detect language, tokenize (hashtags, mentions, URLs, emoji), spam and quality score. Doing it once saves 3x the CPU.
  3. It writes an index message (id, terms with positions, attributes) to a second topic, keyed by hash(tweet id) mod 16.
  4. Each of the 3 replicas of that partition reads the log independently and applies it to its own memory. They agree because they apply the same ordered log, so no replica-to-replica protocol is needed.
  5. A snapshot plus the log offset is saved now and then, so a restarted node loads the snapshot and replays only the tail.

Read flow: a search (budget about 300 ms)

  1. Gateway checks auth and rate limit. Result cache key is normalized query + sort + filters + locale. A hit returns in a few ms.
  2. On a miss the search root parses the query and picks tiers (real-time first unless the date filter is older than 7 days).
  3. Scatter to one replica of each of the 16 partitions (least busy), with a hedged duplicate to another replica if no answer by the p95 latency.
  4. Each partition intersects lists, applies filters and delete flags, scores cheaply, stops early, and returns its best 50.
  5. Gather 16 x 50 = 800 candidates, keep the best 200, send to the ranker. If too few hits and the query allows older data, also query the archive.
  6. Hydrate the top 20 ids from the tweet cache or store, drop deleted or blocked ones, return the page plus cursor.

7. Deep dives

7.1 The real-time index: one writer, many lock-free readers

  • Mutable fields: likes and reposts live in side arrays and are updated in place, batched about 1 s per tweet. A viral tweet costs the same index work as a quiet one.
  • Deletes: a flag bit plus tombstone event. Postings stay; the query path skips flagged docs; compaction drops them when the segment is sealed.
  • Early termination: for Latest, the first 50 matches are the answer, so cost depends on page size, not list length. For Top, scan a budget (for example newest 100,000 matches or 20 ms).
  • Segments: about 16 M docs each. Only the newest is writable. A full segment is sealed (delta-encoded, bit-packed, 4 bytes drops to about 2 to 2.5) and uploaded. Segments older than 7 days are dropped.

Stage one: w1*log(1+likes) + w2*log(1+reposts) + w3*quality + w4*recencyDecay - w5*spam, keep 50 per partition. Stage two: a gradient-boosted tree or small neural model on the best 200, with personal features (does the searcher follow the author), engagement velocity, text match quality. Latest skips the ranker. Top adds a diversity pass (cap per author, collapse near-duplicates). Safety filters run after ranking.

7.4 Trending: windows, Count-Min Sketch, top-K

  • Count-Min Sketch (CMS): a grid of counters, d rows by w columns, one hash per row. Add: bump one counter per row. Estimate: take the minimum over rows. It can only over-count, never under-count, in fixed memory. With w = e/epsilon and d = ln(1/delta), the estimate exceeds the truth by at most epsilon x N with probability 1 minus delta.
  • Our numbers: 8 workers, each sees 18 M / 8 = 2.25 M events per bucket at peak. Pick w = 65,536, d = 4: epsilon = 4.1e-5, error at most about 93 events with about 98.2 percent probability, memory 1 MB per bucket. 288 buckets is 288 MB per worker.
  • It cannot list its keys, so pair it with a min-heap of size K (about 1,000 per worker). On each event: bump the sketch, read the estimate, update the heap if the term is in it, or replace the heap minimum if the estimate beats it. Every minute compute surge scores for the heap candidates only, each worker emits its top 100, a coordinator merges and writes the top 20 per place to Redis.

Defences against gaming: count distinct authors with a HyperLogLog (about 1.5 KB for 2 percent error, minimum say 500 in the window), weight events by author quality, cluster near-duplicate terms (#WorldCup, World Cup), blocklists and classifiers, human review of the top slots, a kill switch, and hysteresis (enter after 2 minutes above a high threshold, leave only below a lower one). Per-place trends count keys (place, term) at city, country and global levels (about 3x keys; sketch memory does not grow).

Consistency: search is eventually consistent. Two stronger promises: deletes are prioritized on a separate small topic (gone within about a minute, and hydration re-checks the tweet store), and a user's own new tweet is merged into their first page by the client. For multi-region, keep a complete index copy per region fed from mirrored Kafka (the hot tier is only 300 GB), and share the archive between two or three regions.

10. Things to say to impress (senior and lead level)

  • "We shard for throughput and fan-out, not capacity: the 7-day hot index is only about 300 GB."
  • "One writer per partition and a published-doc-id pointer written last gives lock-free readers and a consistent snapshot."
  • "Replicas are state machines on the same Kafka log, so there is no replica protocol and a new replica is just snapshot plus replay."
  • "Newest-first postings plus early termination make Latest cost depend on page size, not on how common the word is."
  • "Trending is change versus the term's own baseline, not volume. 'The' never trends."
  • "A Count-Min Sketch only over-counts, so the risk is a rare term looking bigger. A volume floor and distinct-author check handle that."
  • "Because the index is derived data and the hot tier is one week, a bad analyzer is a replay, not a disaster."
  • "Degrade, do not fail: partial results, stage-one ranking, an older trend list."
Common mistakes: using page-number paging on a moving feed; term partitioning (hot terms, 15-way write fan-out); ranking trends by raw count; counting events instead of distinct authors; trying to read keys out of a sketch; ML model on every candidate; dropping a day from the real-time tier before the archive is verified.

11. Interview Q&A

Why not simply use Elasticsearch for the real-time index?

I would start with it, and for a smaller product I would stay with it. At 20,000 documents per second the problems show up. New documents become visible only on a refresh (about every second) and the engine creates many small segments that merge in the background, using I/O and CPU in unpredictable bursts that cause latency spikes. A single-writer, append-only, in-memory index makes a new tweet visible the moment one pointer moves, with predictable latency. The old read-only archive is a good fit for a standard engine.

How do you guarantee a deleted tweet disappears quickly?

A delete goes on its own small high-priority topic, keyed by tweet id so it lands on the same partition as the create. The replica sets a flag bit in the document table and every query checks it before returning a candidate, so the tweet vanishes within seconds. The postings stay until the segment is sealed. As a second safety, hydration reads the current tweet from the store and cache and drops anything deleted or from a suspended account. For the archive, a tombstone list is applied when segments are rebuilt.

Why does a Count-Min Sketch only over-count, and how do you size it?

Each term bumps one counter in every row, and other terms that hash to the same cell also bump it, so every counter is at least the true count. Taking the minimum across rows picks the least polluted cell. Width comes from the error you accept (w = e / epsilon) and depth from the confidence (d = ln(1/delta)). With 65,536 columns, 4 rows and 2.25 M events per bucket, the over-count is at most about 93 events with about 98 percent probability, in 1 MB. Doubling the width halves the error; one more row improves confidence but costs one more memory access per update.

A sketch cannot list its keys. How do you find the top-K trending terms?

Keep a bounded min-heap of K terms (about 1,000 per worker) with a map for lookup next to the sketch. On each event I bump the sketch and read the new estimate. If the term is in the heap I update it; if not and its estimate beats the heap minimum, it replaces the minimum. A real heavy hitter keeps growing, so it will cross the threshold and get captured. Each minute I compute surge scores for heap candidates only, so the expensive baseline lookups cover about 1,000 terms per worker, not millions. Space-Saving, which keeps K counters and evicts the smallest, is the alternative.

How do you stop a botnet from making a hashtag trend?

I use several layers because no single signal is reliable. First, a HyperLogLog counts distinct authors per term, and a term needs a minimum number of them and a sane ratio of authors to events; 200 accounts posting 100,000 times fails. Second, events are weighted by author quality, so new or flagged accounts barely count. Third, near-duplicate text is clustered, since campaigns repeat strings. Fourth, a kill switch and human review cover the top slots. Hysteresis means one short burst cannot flicker into the list. Removals are logged and reviewed to tune thresholds.

How do you rank Top results when new tweets have no engagement yet?

A pure engagement score would bury every fresh tweet. So the score uses signals that do not need accumulated engagement: author quality, text match, the searcher's link to the author, and a recency decay. I also use engagement velocity (likes in the last few minutes versus the author's normal) and smooth the engagement term with a prior, such as log(1 + likes + prior), so a strong author's new tweet can beat an older mediocre one. Some systems reserve a few slots to explore new tweets and collect early signals. The stage-two model learns the trade-off from click data.

What happens during a huge event when tweet volume jumps 10x?

Writes are buffered in Kafka so nothing is lost. Index lag grows from seconds to maybe a minute while each single writer works through the backlog, then it catches up because it has 10 to 20 times headroom. Reads rise too but concentrate on a few queries, so the result cache with request coalescing absorbs most of them, and I warm it for current trends. If partitions are still overloaded I shed in order: deep pagination and complex queries first, smaller candidate budgets for Top, then skip the ranker. First-page results for popular queries are served last.

Why feed each replica from Kafka instead of copying from a leader?

Replicas are deterministic state machines applying the same ordered log, so they converge with no inter-replica protocol. Copying from a leader means shipping every in-memory change over the network and running a leader election, with all the failure cases that brings. Independent consumption gives simple failover (any replica is as good as another), simple scale-out (snapshot plus replay), and fault isolation. The cost is applying events 3 times, which is small because tokenization was already done once in the ingester. I verify convergence by comparing document counts and sealed-segment checksums.

How do you support phrase search such as "world cup"?

Each posting stores the position of the term in the tweet. Tweets are at most 280 characters, so positions need only a few bits. The engine first intersects the lists of all terms, which is cheap with newest-first early termination. For each match it then checks that the second term sits at the first position plus one (or within a window for a proximity query). The position check runs only on the small intersection result. For very common phrases, such as popular hashtags and entity names, I can index them as their own terms and turn the query into one list lookup.

How do you rebuild the index after a bad analyzer release?

The index is derived data, so a rebuild is a controlled replay. I fix and version the analyzer, start a parallel set of partitions, and feed them seven days of tweets from the tweet store (or Kafka if retention covers it) in id order. They seal segments as usual. When the new set has caught up with live traffic and canary queries and document counts match, the root shifts traffic gradually and keeps the old set for instant rollback. The archive does the same in batch, segment by segment. Keeping the hot tier to one week is what makes this a matter of hours.

Why is the trend score a ratio against a baseline, not just the highest count?

The highest counts are always common words and standing hashtags, which are not news. Users want change, so I compare the current rate with the term's own normal (the last day, ideally also the same hour yesterday and last week). Smoothing keeps tiny baselines from giving infinite ratios, and a volume floor with a distinct-author minimum stops a term going from 1 to 30 mentions from trending. A z-score or a seasonal forecast are variants; the smoothed ratio is the simplest that works well and is easy to explain.

Why document partitioning with only 16 partitions?

Document partitioning means a tweet is written to one partition and hot terms spread evenly, and early termination over newest-first lists stays local. The price is that every query goes to all partitions, so each extra partition adds fan-out cost and tail-latency risk. Each partition is only 19 GB, so 16 is plenty. If I outgrow it I build a parallel 32-partition set and switch over. I would not use term partitioning: one tweet would need up to 15 writes, and a hot term would sit on one node.
