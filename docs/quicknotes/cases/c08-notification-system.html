Case sheet: Design a Notification System

One-page revision of the full Handbook case study: push, SMS, email and in-app at 2 billion a day, with priorities, preferences, retries and no duplicates.

ProblemRequirementsEstimationAPIDataArchitecture and flowDeep divesScalingFailuresSay to impressQ&ALinks

1. Problem in 3 lines

One line: we are a middleman between our own services and outside delivery networks (APNs, FCM, email providers, SMS carriers). We must send lots of messages, respect each user's wishes, survive outages, and never let a marketing blast delay a login code.
  • Prompt: "Design a system that sends push, SMS, email and in-app notifications to users."
  • Scale: 500M registered users, 150M daily active, 2 billion notifications a day, peak 10 million per minute.
  • We promise: hand each message to a provider at least once and suppress duplicates. We cannot promise the phone shows it (the last hop is best-effort).
Question to askAssumed answer
Who sends?Internal services and event bus, plus a marketing campaign tool. No outside customers.
Channels?Push (APNs, FCM), SMS, email, in-app inbox.
Latency?Critical (login code, fraud): handed to provider in 2 s at p99. Transactional: 30 s. Marketing: minutes, often scheduled.
User control?Per channel and category opt-ins, quiet hours, global opt-out, legal unsubscribe (email footer, SMS STOP). Some security messages cannot be turned off.
Templates, regions?Yes, localized templates. Three regions (Americas, Europe, Asia-Pacific) with EU data residency.

2. Requirements

Functional

  • Accept a request (one user, a list, or a segment) by API or by internal event.
  • Find the user's channels, device tokens, email, phone, locale.
  • Render versioned, localized templates.
  • Apply preferences, quiet hours, caps, legal suppression.
  • Deliver with priority, retries, provider failover, dead letter queue.
  • Schedule and batch into digests.
  • Track delivery state and provider webhooks.
  • Manage device tokens; serve an in-app inbox.

Non-functional

  • Ingestion 99.99% available; never lose an accepted message (durable before we answer).
  • Latency isolation: a blast must never delay a security code. The central requirement.
  • Sustain 10M per minute, scale out beyond.
  • Suppress duplicates (exactly-once at the device is impossible).
  • Opt-out takes effect at once; consent and history auditable.
  • Adding a channel or provider is a plug-in.

Out of scope

  • The push providers themselves, client SDK internals.
  • Content authoring UI.
  • Audience segmentation engine (we consume its result).
  • Two-way chat.
  • Email deliverability consulting (only a mention of IP pools, SPF, DKIM).

Say: "Peak is 167,000 a second, but the design must protect the 100 a second of security codes inside it. Throughput comes from partitions and workers. Latency of important messages comes from priority isolation, not from raw capacity."

4. API

POST /v1/notifications     Idempotency-Key: 7f3c-...
{ "template_id": "order_shipped", "category": "transactional",
  "priority": "high",                 // critical | high | normal | low
  "recipients": [{"user_id": "u_123"}],   // or {"segment_id": ...}
  "variables": {"order_id": "A991"}, "channels": ["push","email"],
  "send_at": "...", "ttl_seconds": 3600,
  "dedup_key": "order_shipped:A991", "collapse_key": "order:A991" }
-> 202 Accepted {"notification_id": "n_01HX...", "status": "queued"}
  • 202, not 200: stored and queued, not delivered. The caller never waits for the phone.
  • Idempotency-Key: a retry after a timeout is safe. dedup_key: the caller's business meaning of "same notification". ttl_seconds: a late "your driver is arriving" is worse than none, so stale messages are dropped. collapse_key: a newer message replaces an older one on the device.
  • Others: POST /v1/campaigns (segment, template, schedule, rate; pause and cancel), GET /v1/notifications/{id} (status per channel), PUT /v1/users/{id}/preferences, POST /v1/devices and DELETE /v1/devices/{token}, GET /v1/users/{id}/inbox?cursor=, POST /v1/webhooks/{provider} (signature checked).
  • Most triggers are events (for example order.shipped). An event adapter maps event to request using config rules, so product teams never learn our API.

Message record: (user_id, notification_id, channel, template_id, template_version, status, provider, provider_message_id, attempt_count, created_at, sent_at, delivered_at, error_code). Keep an index on provider_message_id so a webhook "message abc bounced" finds our record.

State machine: queued, rendered, sent, delivered. Side exits: suppressed (preference, quiet hours, cap), failed (permanent), expired (TTL), dead (retries used up). Updates only move forward (conditional write on state rank), so a late "sent" never overwrites "delivered".

6. Architecture and main flow

Naive version: the caller waits while one service calls the provider. It breaks: caller latency depends on a slow third party, no retries, a blast starves password resets, a retry sends twice, preferences are checked inconsistently, provider limits get exceeded. The fix: accept quickly, queue durably, process asynchronously in stages.

Main flow: one transactional notification

  1. Caller sends the request with an idempotency key. Ingestion authenticates, validates template and variables, runs SET key NX EX 24h in Redis. Key already there: return the original notification id.
  2. Append to the intake log (partitioned by user_id) and wait for the replicated acknowledgement. Then answer 202. If the log is down, answer 503; never say "accepted" without a durable write.
  3. A pipeline worker loads preferences (cache first), checks quiet hours, caps, legal suppression. Result: send, delay, batch or drop. Drops are recorded as suppressed with a reason.
  4. Render the template in the user's locale; look up tokens or address.
  5. Put the rendered message in the per-channel priority queue. State: rendered.
  6. A channel worker pops it, checks TTL, calls the provider, stores the provider message id. State: sent. Receipts and webhooks later move it to delivered or bounced.

Broadcast flow: a campaign to 80M users is one campaign record, not 80M API calls. The fan-out service reads the segment in shards (for example 1,000 shards of 80,000 users), writes batches to the intake log with dedup key (campaign_id, user_id), checkpoints progress, and obeys a send rate (for example 100,000 per second). Messages use the lowest priority.

7. Deep dives

7.1 Priority queues and channel isolation

Priorities: P0 critical (OTP, fraud), P1 high (orders, mentions), P2 normal (social), P3 low (marketing, digests). Each channel has four queues. Mixing them in one queue means 20M marketing messages sit in front of an OTP, whatever the worker count.

OptionStrengthWeakness
One queue with a priority fieldSimpleMost log brokers do not order by priority; head-of-line blocking remains.
Separate queues, shared pool (chosen)Real isolation, tunable weights, uses idle capacityMore queues and metrics; weights need tuning.
Fully separate pools per tierStrongest isolationIdle capacity wasted; cost.

Choice: separate queues plus shared pool, plus a small dedicated P0 pool with its own provider connections and credentials. Back-pressure: when queues grow, throttle P3 producers (the campaign rate drops), never P0 or P1. Alert on the age of the oldest message, which beats queue depth.

7.2 Providers: rate limits, retries, failover

Each worker is an adapter with send(message) returning accepted, retryable failure, permanent failure, or throttled (retry-after). Use a token bucket per provider account, set below the documented limit. On 429 with retry-after, pause that bucket.

Error classExamplesAction
PermanentDead token (APNs 410, FCM UNREGISTERED), hard bounce, bad payloadNo retry. Mark failed, delete token or flag address.
TransientTimeout, 500, 503, reset, 429Retry with exponential backoff and jitter (about 1 s, 5 s, 30 s, 2 min, 10 min, plus or minus 20%), bounded by TTL.
AmbiguousTimeout after sendingRetry with the same collapse id or provider idempotency key; accept a rare duplicate. Critical: prefer duplicate over loss.

Retries go to a delay queue, not a sleeping thread. After 5 attempts or TTL expiry: dead letter queue (DLQ), monitored and replayable.

Failover strategyProsCons
Active-passiveSimple; reputation stays on primarySpare is cold: unproven limits, poor email delivery at first.
Active-active weighted, for example 80/20 (chosen for email, SMS)Spare is warm; more capacityTwo integrations with different receipts and error codes.
Cheapest route per message (SMS)Saves money by countryComplex routing table.

Choice: weighted active-active (10 to 20% on the secondary keeps it warm); a circuit breaker (for example 20% errors over 30 s) shifts 100% to the secondary, with half-open probes. APNs and FCM have no alternative, so the fallback is another channel (in-app or SMS for critical). Failover can duplicate if the primary accepted but the answer was lost; accept that for critical, delay for marketing. Separate IP pools for transactional and marketing mail.

7.3 Preferences, dedup, caps and digests

  • Opt-out and consent: store a consent record per user, channel, category (time, source, text version). Keep a global suppression list keyed by address. STOP and unsubscribe webhooks update it within seconds. Opt-out writes go to the primary store and invalidate the cache at once: a stale "yes" is a legal problem, a stale "no" only a lost message.
  • Quiet hours: need the user's time zone. Delay to the end of the window plus jitter, unless the TTL would expire first (then drop).
  • Dedup in layers: (1) Idempotency-Key with Redis SET NX; (2) business dedup_key; (3) deterministic message id hash(notification_id, user_id, channel, device) plus a compare-and-set from rendered to sending; (4) collapse key at the device.
  • Caps: for example 5 marketing per week, 10 pushes per day, 1 per type per 10 minutes, as Redis INCR counters with expiry. Since the log is partitioned by user, a local counter with write-back works.
  • Digests: a buffer keyed by (user, digest_type) opens a window (for example 15 min), later items append, one message is rendered at flush ("Alice, Bob and 7 others liked your post").
Delayed sendsTradeoff
Broker delay featureEasy, but days-long delays and cancel are poorly supported.
Durable scheduled table (chosen)Rows by (time bucket, id), scheduler polls and republishes. Handles days and cancellation; needs sharded pollers and claim logic.
In-memory timersFast, lost on crash.

8. Scaling and bottlenecks

  • Intake log: partition by user hash. 167,000 x 1 KB = about 167 MB/s; at about 5 MB/s per partition that is at least 34, so provision 256 (changing the count later is disruptive).
  • Hot spots: write campaigns by hash, not sorted id. A "celebrity" event to 50M followers is a campaign, never 50M API calls.
  • Preferences cache: about 150 GB hot set in Redis, over 99% hit rate, plus a 30 s in-process cache. At 99% hits, only about 1,700 database reads per second.
  • State store: about 3 updates per message gives about 500,000 writes per second. Write on state change only, batch updates.
  • Workers: stateless, autoscaled on queue age. Provider connection pools scale slowly, so pre-warm them.
  • Team budgets: per-team quotas so one team's buggy loop hits its own limit (cells idea).
  • Multi-region: home region per user, so data and processing stay in one region (EU stays in EU). Callers hit the nearest region, which forwards by user id. Campaigns fan out inside each region for its own users. Only campaign definitions and templates replicate.

10. Things to say to impress

Say: "Bulk traffic is isolated by queue, paced by a campaign rate limit, and moved to lower-priority workers, so it can be as slow as it wants without touching OTPs."
Say: "The honest guarantee is at-least-once with duplicate suppression, effectively once. Exactly-once to a human is impossible because the last hop is third parties whose acknowledgements can be lost. For critical messages I prefer a rare duplicate over a loss."
Say: "We alert on the age of the oldest message in each queue, not on depth, and every suppressed message is stored with a reason, because support will ask why a user did not get it."
Trap: answering 200 before the message is durable, mixing priorities in one queue, retrying by sleeping a thread, retrying permanent errors (dead tokens), and trusting open rates as exact.
  • Stale notifications are harmful, so every message has a TTL.
  • Money goes to SMS (about $600,000 a day), so favor push first and SMS only for critical or opted-in cases. Fewer unwanted messages is the best cost and retention lever.
  • Defence in depth on compliance: final suppression check just before sending, short suppression cache TTL.
  • Callers pass template id and variables, not free text, so a hacked service cannot phish every user. Watch for SMS pumping fraud (per-number limits, country allow-lists).
  • Phasing: MVP (API, one queue, one provider each), then priorities, retries, DLQ, caps, then second providers, scheduling, campaigns, then multi-region.

11. Q&A: follow-ups an interviewer asks

How do you make sure a marketing campaign does not delay password reset codes?

Isolation happens at several layers. Bulk traffic carries a low priority label and goes to its own queues per channel, so a multi-million backlog never sits in front of critical messages. Workers always drain the critical queue first, and a small dedicated worker group with its own provider connections and credentials serves only P0. The fan-out service paces campaigns with a rate limit and slows itself when downstream queue age grows. We also use separate email IP pools and SMS routes for transactional traffic. The promise we measure is P0 queue age, which should stay under a second.

What happens when APNs or an email provider goes down?

Workers see rising errors and the circuit breaker for that provider opens once the error rate crosses a threshold in a short window. For email and SMS, traffic shifts to the secondary provider, which is kept warm with a small share. APNs and FCM have no equivalent for their platform, so messages wait in the queue within their TTLs, and critical ones can fall back to another channel like SMS or in-app. Low-priority queues are paused first to save provider budget. When the provider recovers, a half-open probe checks it and traffic ramps back. Messages whose TTL ran out are dropped, because stale notifications do harm.

How do you prevent duplicate notifications?

I layer defences because none is enough alone. At the API, an idempotency key stored with set-if-absent makes caller retries safe. A business dedup key catches two services reporting the same event. Inside the pipeline, the message id is deterministic and a conditional state change lets only one worker proceed to send it. At the device, collapse ids make two deliveries show as one notification. Still, a crash between the provider accepting and us recording it cannot be fully removed, so the guarantee is at-least-once with duplicate suppression, and I would rather duplicate an OTP than lose it.

Why partition the queue by user id?

It gives three benefits. All messages for one user reach the same consumer in order, so caps, quiet hours and digests see a consistent stream and can use local state instead of distributed locks. Load spreads evenly because users are numerous and hash uniformly. And the state store is partitioned the same way, so per-user history reads are local. The cost is a possible hot partition for an extremely heavy user, which is rare. Broadcasts avoid hot spots because the fan-out service writes through the hash rather than in sorted id ranges.

How would you implement quiet hours and "send at 9 AM local time"?

Both need the user's time zone from the profile or device. For quiet hours, if local time is inside the window and the message is not critical, the pipeline writes it to the scheduler with a release time at the window end plus jitter, unless the TTL would expire first, in which case it drops it. For "9 AM local" campaigns, fan-out splits the audience by time zone into waves, which also flattens the peak. Scheduled items sit in a durable time-bucketed table scanned by sharded pollers, so multi-day delays and cancellations work. The opt-out check runs again at release time.

How do you handle invalid device tokens?

The provider tells us on a later send: APNs returns 410 or BadDeviceToken, FCM returns UNREGISTERED. The worker treats this as a permanent error, does not retry, and deletes the token by token value. We also remove a token on logout and reassign it if another user logs in on the same device (unique index on token). Tokens not refreshed for about 60 days are expired by a background job. Cleaning matters because dead tokens waste capacity and quota and can make providers throttle us. A sudden spike in invalidations is alerted on, since it often means our bug or an app release problem.

How do you scale to a broadcast to 100 million users?

A broadcast enters as a campaign, not as individual API calls. A fan-out service reads the audience in shards, publishes batches to the intake log with a deterministic per-campaign key so re-runs are safe, and checkpoints progress. A configured rate limits output, say 100,000 per second, so 100 million takes about 17 minutes. Messages use the lowest priority queues so they cannot hurt other traffic. The campaign can be paused, cancelled or throttled when queue age rises. Where possible the audience is split by time zone and region so each region fans out its own users in parallel.

Can you guarantee exactly-once delivery? What do you tell a product manager?

No system relying on APNs, FCM, carriers and mailbox providers can promise a human sees a message exactly once, because acknowledgements can be lost at any hop and the device controls display. We promise at-least-once processing of each accepted request, with duplicates suppressed by idempotency keys, deterministic ids, conditional state changes, and collapse keys. I would present it as effectively once, with a measured duplicate rate under a target such as 0.01%, and a rule that critical messages prefer a rare duplicate to a loss.

How do preferences stay fast and still legally correct?

Preferences are read on every send, so they are cached in Redis and in process. For correctness, opt-out writes go to the primary store and immediately invalidate or update the cache through an event. A global suppression list keyed by address is consulted again just before sending as a final defence. The risk is a stale cache saying "opted in", so the suppression TTL is short and the invalidation path is monitored. Consent changes are stored with time, source and text version so we can prove what the user agreed to. Security categories may go out on allowed channels, but legal blocks such as an SMS STOP still apply.

How would you track whether a notification was delivered or opened?

Each channel gives different signals. For push, the provider only acknowledges acceptance, so the client SDK reports received and opened events with the notification id. Email providers send webhooks for delivered, bounced, complaint, open and click. SMS gateways send carrier receipts, sometimes late or missing. A small webhook service verifies the signature, queues the raw event and answers 200 quickly. A consumer maps the provider message id to our record and moves state forward only, ignoring duplicates and out-of-order events. Events stream to analytics, and per-provider delivery rates feed routing. Open rates are approximate because privacy features preload tracking pixels.

Production incident: queue age for push P1 is climbing and users complain of late order updates. What do you do?

First check where the time is going: provider error rate and latency, breaker state, token bucket throttling, and worker count against queue age. If the provider is slow or throttling, the breaker or a 429 retry-after is the cause, and I cannot just add workers, since that would worsen throttling. If we are simply short of workers, autoscale on queue age and check that connection pools are warm. Meanwhile pause or slow P3 and P2 to free provider budget for P1, and check whether a campaign is running that should have been paced. Messages past their TTL are dropped so the backlog does not turn into stale notices. Afterward, review weights and alert thresholds.

Why a queue between pipeline and delivery, instead of one service doing both?

The two stages have different bottlenecks. The pipeline (preferences, render, route) is CPU and cache bound and fast. Delivery is bound by outside latency and provider limits. If one process did both, a slow APNs connection would hold threads and stall rendering. With a queue between them, delivery can lag while the queue absorbs the difference, and each stage scales and fails on its own. The queue also gives us the place to put priorities, retries, and per-channel isolation.
