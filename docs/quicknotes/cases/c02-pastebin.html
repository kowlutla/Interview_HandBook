Case sheet: Design Pastebin

One-page revision of Handbook Case study 2. Store text, give a short link, expire it later. Small traffic, big storage, tricky keys and abuse.

ProblemRequirementsEstimationAPIDataArchitectureFlowsDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: a user pastes text, we store it and return a short URL such as paste.example/aZ3kP9xQ. Anyone with the link (or only the owner, if private) can read it until it expires.
  • It looks like a toy. It hides four real problems: small hot metadata versus big cold text, making unique unguessable keys, expiry at scale, and abuse.
  • The hard promise is durability: a paste that has not expired must never be lost.
  • Say the key assumption out loud: reads are 10 times writes, and most pastes are read only a few times.

Clarifying questions to ask (and the answer to assume)

AskAssume
Scale?1 million new pastes a day, 10 reads per write (10 million reads a day)
Paste size?Average 10 KB, hard maximum 1 MB
Who writes?Anonymous and logged-in. Logged-in users get history, delete and edit
Visibility?Public (listed), unlisted (anyone with the link), private (owner only)
Expiry?10 minutes, 1 hour, 1 day, 1 week, 1 month, never. Default 1 month for anonymous
Extras?Syntax highlighting, versions on edit, custom URLs optional
Targets?Reads 99.95 percent available, cached read p99 under 200 ms, writes under 500 ms
Where are users?Worldwide. One primary region plus a CDN (a network of servers near users that keeps copies of pages) is enough to start

2. Requirements

Functional

  • Create a paste (title, language, visibility, expiry) and get a key and URL
  • Read by key: HTML page and raw text
  • Delete (owner, or anonymous with a secret delete token)
  • Auto-expire; after expiry return "gone"
  • List my pastes; list recent public pastes
  • New versions on edit; old versions stay readable
  • Report abuse; moderators can remove

Non-functional

  • Read-heavy and highly available
  • Durable (object storage, about eleven nines per year)
  • Cheap per paste: storage is the main cost, so limits, expiry and dedup (not storing the same bytes twice) are cost features
  • Unguessable keys: no sequential ids
  • Abuse-resistant: spam, malware, leaked passwords

Out of scope

  • Binary file hosting
  • Real-time collaborative editing
  • Full-text search over all pastes (an evolution option)
  • Comments, payments

Findings: traffic is tiny (one database could serve 600 reads a second). Text is 20 times bigger than metadata (10 KB versus 500 B). So the system is hard because of storage growth, key correctness, expiry and abuse, not QPS. A random 8-character guess hits a live paste about 1 time in 60,000. Cost: object storage about 2 to 3 cents per GB-month, so 18 TB is roughly $400 to $550 a month with no expiry. Treat prices as order of magnitude.

4. API

POST /v1/pastes          (Idempotency-Key header)
  { content, title?, language?, visibility, expires_in }
  201 { key, url, version, expires_at, delete_token? }
GET  /v1/pastes/{key}              metadata + content
GET  /raw/{key}                    text/plain only
GET  /{key}                        HTML page
GET  /v1/pastes/{key}/versions/{n}
PUT  /v1/pastes/{key}              new version (If-Match: n)
DELETE /v1/pastes/{key}            owner or delete_token
GET  /v1/users/me/pastes?cursor=   cursor pagination
POST /v1/pastes/{key}/report
  • 413 above 1 MB, 429 when rate limited, 404 unknown key, 410 Gone expired or deleted (so crawlers learn the difference).
  • Private paste of someone else: return 404, not 403, so we do not confirm the key exists.
  • Idempotency-Key means a client retry after a timeout does not make a duplicate paste. Lists use cursors, not offsets.

5. Data model and store choices

MetadataContent (the text)
Sizeabout 500 Babout 10 KB (up to 1 MB)
Accesslookup by key, by owner, by expiry timeread or write the whole object
Changes?yes (status, expiry, view count)never, immutable
StoreRelational database with read replicasObject storage (S3-like), named by hash
Whysmall, queryable, needs indexes and a transaction for the version countercheap per GB, replicated across zones, lifecycle rules, CDN friendly
  • pastes(key PK, owner_id, title, language, visibility, status, current_version, created_at, expires_at, delete_token_hash, size_bytes, view_count)
  • paste_versions(key, version, content_hash, size_bytes, created_at), primary key (key, version)
  • blobs(content_hash PK, object_key, ref_count, first_seen_at)
  • Indexes: (owner_id, created_at DESC) and a partial index on expires_at for active rows only.
  • The row holds the hash of the text, not the text. The hash is the object name, spread like blobs/ab/cd/abcd... so the store spreads load evenly. Text is stored compressed (gzip or zstd, about 3x to 5x smaller).
Say this: "Metadata is small, hot, queried and mutable, so it lives in a database. Content is large, cold, immutable and fetched whole, so it lives in object storage. The row points to the blob by content hash." Small pastes inline in the row is an optimisation, not the baseline: two code paths and a migration pain when a paste grows.

6. Architecture

  • CDN: caches public and unlisted pastes at the edge, never private ones.
  • Load balancer + rate limiter: spreads traffic, limits per IP and account, rejects oversize bodies early.
  • Write API vs Read API: split because reads are 10x more frequent and must stay up if writes are degraded.
  • Key service, metadata DB, object storage, Redis, queue + workers: as in the diagram.

7. Main request flows

Create a paste

  1. Edge rejects bodies over 1 MB and applies rate limits.
  2. Write API validates, normalises line endings, compresses, and computes the SHA-256 hash of the content.
  3. It takes the next key from its in-memory batch from the key service.
  4. If the hash is new, it PUTs the blob to object storage (safe to repeat, same name and bytes).
  5. One database transaction: insert paste row, version 1 row, and raise the blob reference count by 1.
  6. Return 201 with the URL (and delete token if anonymous). Publish a "paste created" event for the async abuse scan.
Order matters: blob first, then metadata. A crash in between leaves an orphan blob, which garbage collection removes later. The other order could leave a row pointing at a missing blob, which users see.

Read a paste

The Read API must check status and expires_at against the clock before returning anything. Raw reads use text/plain, nosniff and a safe Content-Disposition.

8. Deep dives

8.1 Key generation

OptionProCon
A. Random 8 chars, insert, retry on duplicateNo extra service, stateless, unguessableCollision costs a retry; database is the referee on the hot path
B. Truncated hash of textFree dedupSame text gets the same key (bad for private and delete); truncation collisions; guessable if you know the text
C. Counter plus base62No collisions, shortest keysSequential, so unlisted pastes can be scanned; counter is a coordination point
D. Pre-generated key service (KGS)No collision handling on writes; random; fastOne more component; must never hand out the same key twice

Choice: D, with A as the fallback. At 12 writes a second A would work; D shows how to remove a race at scale.

  • Atomic hand-out: one transaction (or SELECT ... FOR UPDATE SKIP LOCKED). Test this part hardest.
  • Crashed server: its unused keys are abandoned, never recovered. Losing 1,000 of 218 trillion is harmless; recovery logic breeds double-use bugs.
  • Batch math: peak 60 writes a second over about 6 servers is about 10 keys a second each, so 1,000 keys last about 100 seconds. Prefetch the next batch at 20 percent left.
  • Last defence: the primary key on pastes.key rejects a duplicate; discard, take the next, and alert.
  • Use a secure random source. Never reuse keys after expiry (stale links and cached copies would show someone else's text).

8.2 Expiry and cleanup

ApproachHowTradeoff
Periodic queryEach minute, select active rows with expires_at < now in batches of 1,000, mark expired, release blob refsSimple, cheap index scan; many single-row deletes cause bloat
Time-partitioned tablesPartition by expiry day, drop old partitions wholeVery cheap bulk delete; expiry must be known up front; "never" needs its own partition
Store-native TTLDynamoDB TTL, S3 lifecycle rulesAlmost no code; best effort, can lag hours or days

Choice: lazy expiry for correctness, background cleanup for space. Every read compares expires_at to the clock and returns 410. Cache TTL is min(default_ttl, expires_at - now), so no cache serves a paste past its time. Explicit deletes and blocks are different: they purge the CDN and Redis by key. The sweeper only reclaims space, so if it lags we pay money, not correctness.

  • Sweeper must be idempotent, resumable and rate limited. Workers each own a key-hash range, or claim batches with SKIP LOCKED.
  • Blobs are deleted only when the reference count has been zero for a grace period (guards the race with a new identical paste).

8.3 Caching, CDN, and dedup

VisibilityCDNRedis
PublicCache, TTL capped by expiryYes
UnlistedCache, TTL capped, X-Robots-Tag: noindexYes (the key is the credential)
PrivateNever (private, no-store; bypass when auth cookie present)Metadata only; content after the auth check
  • Pasted content is immutable per version, so there is nothing to invalidate on update: an edit makes a new version. Version URLs cache for a year (immutable, still capped by expiry); the latest-version URL gets a short TTL of about 60 seconds, plus a purge on edit.
  • Redis holds metadata and text under 64 KB, LRU eviction. CDN request collapsing makes 10,000 simultaneous misses produce one origin fetch.
  • If the CDN hits 90 percent and Redis catches 90 percent of the rest, 10 million daily reads become about 100,000 at the origin: about 1 per second.
  • Dedup: blob name is the SHA-256 of content, so identical text is stored once. Keys and metadata stay per paste; only bytes are shared. Needs transactional reference counts, a periodic recount job, and a grace period. Expect about 10 to 30 percent byte savings. Bonus: block one bad hash and every copy is blocked.
  • Highlighting: client-side by default (cheap, raw endpoint free), capped at about 200 KB; language detected once at write time and stored. Pre-render in a worker only if SEO needs it.

9. Scaling and bottlenecks

  • API tier: stateless, scale out and autoscale on CPU and latency.
  • Metadata DB: one primary plus replicas lasts years (about 900 GB in 5 years, 60 writes per second peak). Later shard by hash of key; random keys spread load. "My pastes" uses an owner-keyed secondary table; each shard sweeps its own expiry.
  • Object storage: effectively unlimited. Hash-prefixed names avoid hot prefixes. At billions of tiny objects, request cost dominates; pack small pastes into segment files.
  • Hot key: a front-page paste is absorbed by the CDN; then Redis; then a small in-process cache per Read API instance.
  • Hot writes: view counts are buffered with Redis INCR and flushed every minute (approximate).
  • Recent public list: a capped list or sorted set in Redis, not a database scan.
  • At 100x: reads scale by CDN and cache; shard the DB; partition the key pool by prefix; expiry via partition drop; abuse handling needs automation and people.

10. Failure modes

What failsWhat happensFix
CDN edge or purgeLatency and origin load up; stale content after deleteFallback to origin, short TTLs for deletes, purge retries, origin sized for 10x miss rate
Redis nodeMore reads reach DB and storageCache is optional: timeouts, circuit breaker, replicas, jittered TTLs
Metadata primary crashWrites fail; reads continue from replicas and cachesAutomatic failover; write API returns 503 with retry-after
Replica lagFresh paste returns 404 on a lagging replicaRead-your-writes: creator reads from primary, or retry on primary once before 404
Object storage outageCannot fetch or write contentCache hides most reads; cross-region bucket replication; clean 503 on writes (blob is written first)
Key allocator downWriters run out of keys after minutesPrefetch, several allocators, fallback to random key plus retry
Crash between blob PUT and DB commitOrphan blob, no user harmBlob-first order; GC removes old unreferenced blobs
Client retry after timeoutDuplicate pasteIdempotency-Key stored 24 hours returns the original key
Sweeper or GC diesStorage bill growsAlert on lag; correctness unaffected by lazy expiry
Ref count too low (drift)Blob deleted too early: data lossGrace period, reconciliation recount, soft-delete retention of a few days
Abuse pipeline slowBad content stays up longerQueue buffers; hold content as pending for risky accounts

Consistency: metadata is strongly consistent on the primary; replicas and caches are eventually consistent, fine because content is immutable. Exceptions (delete, block, visibility change) get explicit purges. No distributed transaction across database and object store: only ordered, idempotent steps plus reconciliation. Write order: blob then metadata. Delete order: metadata state, then cache purge, then blob release. Crashes leave garbage, not dangling pointers. For disaster recovery, replicate the database and bucket asynchronously to a second region; avoid active-active writes.

11. Things to say to impress

Say this:
  • "The QPS is tiny, so the design is about bytes, keys, expiry and abuse. I will prove that with the numbers first."
  • "Never make correctness depend on a background job. Reads enforce expiry; the sweeper only saves money."
  • "I order writes so a crash leaves garbage, not a dangling pointer: blob first, then metadata."
  • "Dedup is on content, never on identity. Two users get two keys and two rows; only bytes are shared."
  • "Private pastes get 404 not 403, and are never in a shared cache. A public-to-private change purges immediately."
  • "Unlisted is a capability URL: random key, noindex, no-referrer. It is not private."
  • "Raw text is served as text/plain with nosniff from a cookieless separate domain, to stop stored cross-site scripting."
  • "I would start with random key plus retry (phase 1), and add the key service, dedup and versioning in phase 3."
Common mistakes: putting all the text in the database; relying on the sweeper for expiry; sequential keys for unlisted pastes; caching private responses at the CDN; deduping by key; no abuse plan; reusing expired keys.

Abuse layers: rate limits (for example 20 creates an hour anonymous), async content scan (malware signatures, credential formats, spam), a hash blocklist, report queue and moderators, TLS and encryption at rest. Optional end-to-end encrypted mode (key in the URL fragment) gives up scanning, highlighting and search.

12. Q&A: follow-ups an interviewer asks

Why not just store the paste text in the database row?

For a small project you should. At 10 GB of new text a day, the database grows about 3.65 TB a year of cold bytes that never change. That makes backups and replica rebuilds slow, fills the memory buffer with text nobody reads, and costs several times more per GB than object storage. If we split, the database keeps a small metadata table that stays in memory and object storage gives cheap, durable, huge capacity. The price is two systems to keep consistent, which we handle by writing the blob first and running garbage collection for orphans.

How do you guarantee two pastes never get the same key?

Two layers. The key service moves keys from the unused table to the allocated table in one atomic step, so a key goes to only one writer. Separately, the primary key on the paste table rejects a duplicate insert; if that ever fires, the writer discards the key, takes the next one and raises an alert, because it means a bug. Plain random keys with insert-and-retry also work at this scale. Pre-generation just takes collision handling off the hot path and avoids a read-before-write race.

What happens to the keys held by a crashed app server?

They are thrown away. Each server holds about 1,000 keys in memory. Out of 218 trillion possible keys, losing a few thousand per crash costs nothing. Trying to recover them means tracking exactly which were used, and that is where double-allocation bugs come from. So we leak keys and never reuse them.

Expired pastes must vanish, but what if cleanup is delayed?

Correctness does not depend on cleanup. Every read compares the expiry time to the clock and returns 410 Gone. Cache lifetimes are capped at the remaining life, so Redis and the CDN stop serving it on time too. The sweeper later marks rows expired and releases blob references, and a garbage collector removes unreferenced blobs after a grace period. If the sweeper falls behind, we pay for extra storage, but nobody sees expired data. We alert when the oldest undeleted expired row is over one hour old.

How do you stop a private paste leaking through the CDN?

Private responses carry Cache-Control: private, no-store, and the CDN is set to bypass cache when an auth cookie or authorization header is present, so one misconfiguration cannot leak data. The origin checks authorization on every request. For big content, it hands out a short-lived signed URL (about 60 seconds) only after that check. Other people's private keys return 404 so we do not confirm they exist. When a paste turns from public to private we purge the CDN and Redis straight away, because waiting for a TTL would be too slow.

Is deduplication worth it, and what are the pitfalls?

It saves about 10 to 30 percent of bytes on a general site, mostly spam, common logs and scripts, and it lets us block every copy of bad content by blocking one hash. The pitfalls are reference counting (update counts in the same transaction as metadata, recount regularly, and delete only after a grace period), a privacy side channel if the API ever says "already exists" to a client that sent only a hash, and keeping identity and permissions per paste. I would add it after the basics work.

How do edits work without breaking caches?

Each version is an immutable blob with its own URL. A version URL can be cached for a year because it never changes. The unversioned URL points to the latest version, so it has a short TTL and an edit deletes the Redis entry and purges the CDN URL. Two editors at once are handled with optimistic concurrency: the client sends the version it edited in If-Match, and a mismatch returns 409 so no update is lost silently. History is limited to about 50 versions per paste.

How would you add search over public pastes?

Publish created, deleted, expired and blocked events to a queue. An indexer writes only public, non-blocked pastes into a search engine, indexing just the first few KB to control cost. Because it is fed by events, it is eventually consistent, and the result page re-checks status before showing anything. Search is separate and optional, so its outage never affects create or read. Abuse scanning must finish before indexing, since search makes bad content easier to find.

Traffic is suddenly 100 times higher. What changes?

Reads are handled by scaling the CDN and cache, which are horizontal. The metadata database is sharded by key hash, easy because lookups are by key. The key pool is split by prefix so the allocator is not a bottleneck. Expiry moves to dropping whole partitions. Object-store request cost rather than bytes becomes the big bill, so we pack small pastes into segment files. In the end, abuse handling and moderator capacity are usually the real limit.

How do you make sure a created paste is never lost?

The blob goes to a replicated object store first, and only then is the metadata row committed, so a visible paste always has content. The store keeps copies across availability zones, and we replicate the bucket and database to a second region. A scheduled audit reads a sample of non-expired blobs and checks their hash; any miss pages someone. Deletes use a grace period and soft-delete retention to protect against counter bugs.

Hot incident: users report 404 right after creating a paste. What do you check?

First suspect replica lag: the row is on the primary but the replica serving reads has not caught up. Check replication lag graphs and whether the 404s come from replicas. The fix is read-your-writes: on a miss, retry once on the primary before returning 404, or send the creator's first reads to the primary with a short-lived cookie. Next, check negative caching: an earlier 404 may be cached at the CDN or Redis, so keep negative TTLs short. Then check that the blob-first order is intact and that the create flow is not returning 201 before commit.

Why serve raw text from a different domain?

If a user pastes HTML with scripts and we serve it as a page on our own domain, the script runs with our cookies. That is stored cross-site scripting. We serve raw content as text/plain with nosniff, escape text on the page, use a strict content security policy, and serve raw bytes from a separate cookieless domain so even a mistake cannot read user sessions.

Why not reuse a key after a paste expires?

The key space is huge (62^8), so there is no need. Reuse causes stale links, search engine copies and CDN copies suddenly showing a stranger's text. Never recycling also keeps the 410 Gone answer meaningful: "this existed and is gone" versus "never existed".
