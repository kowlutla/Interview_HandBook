Case sheet 32: Design a Gaming Leaderboard

One-page cheat sheet: ranking 100 million players of an online game, with rank answers in milliseconds while scores change thousands of times a second. Full write-up: Handbook case study 32.

ProblemRequirementsEstimationAPIDataArchitectureDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: players finish matches and their scores change. Millions ask "what is my rank?", "who is in the top 100?" and "who is near me?". Every answer must come back in a few milliseconds.
  • In plain SQL the top 100 is easy (ORDER BY score DESC LIMIT 100). The hard part is "my exact rank", which means counting how many players beat me, on 100 million rows, for millions of refreshes.
  • Key idea to say early: ranking is an order-statistic query (position in a sorted list). A Redis sorted set (a skip list, which is a linked list with express lanes) answers rank, top K and range in O(log N).

Clarifying questions to ask (and the answers we assume):

QuestionAssumed answer
How many players?100 million registered, 30 million daily active (DAU). One global board per game mode, plus regional boards.
What is a score?Non-negative integer, at most about one billion, set by the game server (never the client, clients cannot be trusted).
Which views?Top K (up to 100, paged to 1,000), my rank, around me (5 above and 5 below), friends board.
Which windows?Daily, weekly, season. They reset on a schedule, and past winners must stay readable.
How fresh?My own rank within about 1 second of a match. Public top 100 may lag a few seconds.
Ties?Equal scores: whoever reached it first ranks higher, so every position is unique.
Exact rank for everyone?Exact for the top 10,000 and inside one shard. For a player ranked 40 millionth, "top 40 percent" is fine. This answer decides how hard sharding is.
Can we lose data?Redis can be rebuilt, but not from nothing. We need a durable source of truth.

2. Requirements

Functional

  • Submit a score (add points, or keep the best, depending on mode).
  • Top K with paging.
  • My exact rank and score.
  • Around me window.
  • Friends board.
  • Daily, weekly, season boards with archives of finished periods.

Non-functional

  • Read p99 under 50 ms; own rank updated within 1 s.
  • Reads 99.95 percent available. A slightly stale board beats an error page; the game must never depend on it.
  • Counted exactly once, even with retries and duplicates.
  • A Redis crash must not lose confirmed scores.

Out of scope

  • Matchmaking.
  • The anti-cheat engine itself (we only show where it plugs in).
  • In-game economy and money prizes (need stronger audit).
  • Live rank push: mentioned as an extension only.

4. API

POST /internal/v1/scores                  (game server only, mTLS)
  { event_id, player_id, board, delta, match_id, ts }  -> 202 accepted
GET /v1/boards/{board}/top?window=weekly&offset=0&limit=100
  -> { window_id, as_of, entries: [ {rank, player_id, name, score} ] }
GET /v1/boards/{board}/me?window=season
  -> { rank, score, percentile, exact: true }
GET /v1/boards/{board}/around?window=daily&span=5
GET /v1/boards/{board}/friends?window=weekly
GET /v1/boards/{board}/archive?window=weekly&window_id=2026-W45
  • event_id is the idempotency key (a unique id so a repeated request counts once).
  • Send a delta for add-points modes. A best-score mode sends an absolute score and uses "keep max".
  • Write returns 202 because processing is async through a queue.
  • Reads return window_id, as_of and exact, so the UI can say "top 40 percent" when only an estimate exists.

5. Data model and store choices

StoreHoldsWhy
Redis sorted setsOne key per board and window. Member = player id, score = encoded scoreRank, range and update are O(log N) in memory. A SQL index cannot match this update rate and latency.
Kafka event logEvery score event, partitioned by player idDurable and replayable. Absorbs bursts, can rebuild any board, keeps one player's events in order.
Score table (wide-column or relational)Current score per (board, window, player); archived final standingsSource of truth. Cheap point reads, bulk scan for rebuilds.
Dedupe storeProcessed event_id values (TTL 48 hours)Makes the consumer idempotent.
Top-K cacheRendered top 100 per board and windowIdentical for all users, so one computation serves millions.
Profile cacheNames, avatarsKeeps strings out of the sorted set; renames never touch ranking.

Keys look like lb:{ranked-eu}:season:2026S4, lb:{ranked-eu}:week:2026-W46, lb:{ranked-eu}:day:20261117. Braces are a hash tag so related keys share a Redis Cluster slot. Weekly keys expire 8 weeks after the week ends, daily keys 14 days after.

How a sorted set works: a hash table (member to score, O(1) lookup) plus a skip list ordered by score. Each forward pointer stores a span (how many bottom nodes it skips). Adding spans along the search path gives the rank, so ZREVRANK is O(log N), not a count. With N = 100M, log2 N is about 27 hops.
CommandUseCost
ZINCRBYAdd points atomicallyO(log N)
ZADD ... GTKeep-best update; naturally idempotentO(log N)

Trap: a huge ZREVRANGE (say 1 million rows) blocks Redis's single thread for tens of milliseconds and stalls every other command. Cap limit at 1,000 and never run unbounded range reads on the live primary.

6. Architecture and main flows

Write flow (submit a score):

  1. Match ends. The game server calls POST /scores with a unique event_id.
  2. Ingest validates, appends to Kafka keyed by player, replies 202 once Kafka acks. The game never waits for Redis.
  3. A worker claims the event with SET dedupe:{event_id} NX EX 172800. If the key existed, skip it.
  4. Worker updates the score table with a conditional update that also records the event id.
  5. Worker sends one pipeline of three ZINCRBY (day, week, season) to Redis.
  6. Worker commits the Kafka offset last. A crash before this means a replay, which the dedupe and the conditional update turn into a no-op.

Why this order: the durable table is written before Redis, so Redis can always be rebuilt and never gets ahead of the truth. At-least-once delivery plus idempotent apply gives an exactly-once effect. ZINCRBY is not idempotent, so the guard must come first.

Read flow: top K is a cached ZREVRANGE 0 K-1 (refreshed at most once a second per board, single-flight so only one caller refreshes). My rank is ZREVRANK + 1 plus ZSCORE on a replica. Around me runs rank and slice in one Lua script so an update cannot slip between them. Friends: one ZMSCORE with the friend ids (a few hundred), sort in the API. Avoid ZINTERSTORE on the hot path.

7. Deep dives

7.1 Ties and score encoding

Redis breaks ties by member bytes (player id), which is arbitrary and unfair. Options:

PolicyScores 900, 800, 800, 700 give ranksHow
Earliest achiever first (our choice)1, 2, 3, 4Pack time into the low bits of the score
Competition ranking1, 2, 2, 4Rank = 1 + count of strictly higher pure scores (ZCOUNT)
Dense ranking1, 2, 2, 3Needs a histogram of score to count
Encoding: a Redis score is a 64-bit double, exact for integers up to 2^53 (53 bits). Use 30 bits for the score (max 1,073,741,823, above our one billion cap) and 23 bits for inverted time. A season is at most about 90 days = 7,776,000 seconds, below 2^23 = 8,388,608. encoded = score x 2^23 + (2^23 - 1 - seconds_since_season_start). Decode with floor(encoded / 2^23).
Pitfalls: you cannot ZINCRBY an encoded value (the time part drifts). Read the pure score, add the delta, re-encode, ZADD inside a short Lua script. Cap scores at ingest so they never pass 2^30.

7.2 Daily, weekly and season windows

OptionProsCons
A. Fan out on write (3 ZINCRBY per event)Reads are a single key. Windows are independent. Rollover is "write to a new key".3x write cost (42,000 per second) and extra memory
B. ZUNIONSTORE of 7 dailies on demandLess steady memoryUnion of 30M-member sets blocks the single thread for seconds
C. One set, subtract expired points by jobOne key to readPer-event expiry bookkeeping, drifts if a job is missed
D. Dailies plus a pre-merged weekly refreshed off-peakCheaper than BWeekly is stale, breaking the 1 second own-rank goal

Choice: A. The cost is linear and predictable, and fits one primary. Rollover steps: (1) route each event by match end time, not processing time, so a match ending 23:59:58 still counts for the old day; (2) keep the old window writable for a grace period (about 10 minutes) for late events; (3) seal it, read the final top N from a replica, write it to the archive and publish window_closed for rewards; (4) let a TTL expire the set. Boards use one UTC calendar. Season start is the biggest spike, so pre-warm the new key and stagger client refreshes with a random delay.

7.3 Sharding one huge board

Redis Cluster does not split one sorted set (one key is one slot on one node), so at 1 billion players (a 100 GB set, 420,000 updates per second) we split it ourselves.

ConcernHash by player idRange by score
Write1 shard, simple1 shard, or a 2-key move when a score crosses a boundary (not atomic)
Top KAsk all N shards for their top K, merge (16 x 100 = 1,600 items)1 or 2 calls to the top shard
Exact rank1 + sum of ZCOUNT of higher scores over N shardsCounts table of higher shards + one ZREVRANK
Around meN calls, tricky merge with tiesUsually 1 call
LoadEven by designSkewed: low shard huge (about 96M of 100M), hot middle shard
One shard downAbout 1/N of players missing; mark exact:falseTop or my own region unavailable

Choice: a hybrid that follows user attention. A small dedicated top set (say the top 100,000 players) is fed by a filter when a score crosses the cutoff: exact top K and exact rank in one call. Everyone else lives on hash shards, and their rank is approximate, from a score histogram (counts per score bucket, refreshed every few seconds from ZCOUNT): players in higher buckets plus interpolation inside the bucket. The UI shows "top 40 percent". The exact N-way count runs only when a player explicitly asks.

Say this: "Leaderboard attention is very skewed: everyone looks at the top and at their own neighbourhood. So I make the answer exact where people look and approximate in the deep tail. That is what makes sharding affordable."

8. Scaling and bottlenecks

  • Read replicas serve rank, top and around-me (async copies, a few ms behind). For "my rank right after my match", route to the primary or retry once if the score is older than the client's.
  • Hot key: the top list is read by everyone, so a 1 second in-process cache plus a shared tier turns tens of thousands of reads into a handful of Redis calls. The season key is written by everyone, bounded by one primary's single thread (42,000 of about 100,000 per second).
  • Write batching: workers take 100 to 500 events, collapse several events of one player into one ZADD, send one pipeline. Cheapest scaling lever.
  • Partitions: Kafka keyed by player keeps one player in order; partition count (for example 64) caps worker parallelism.
  • Replication cost: the primary pays CPU per replica, so keep 2 to 3 replicas per shard.
  • Regional boards live in regional clusters; the global board is a periodic merge of regional top lists, a few seconds old.
  • At 10x (300M DAU, 140,000 events per second): hash shards (16 to 64), top set plus histogram, a few hundred partitions, regional boards by default, a CDN for public hall-of-fame pages.
  • Persistence: AOF with everysec plus periodic RDB snapshots loses at most about 1 second. Keep memory headroom (dataset 50 to 60 percent of RAM) for fork copy-on-write.

Consistency: the score table is strongly consistent per player. Redis boards are eventually consistent with it (normally under 1 second). Say so in the API with as_of.

10. Things to say to impress

Say these:
  • "Ranking is an order-statistic query. A skip list with spans gives rank in O(log N), and that is the whole design."
  • "Redis is a derived view. The Kafka log and the score table are the truth, and we rehearse a rebuild weekly into a shadow key and compare checksums. A backup you never restored is not a backup."
  • "We get exactly-once effect from at-least-once delivery plus an idempotent apply. The table is written before Redis."
  • "I would not shard at 100M players. The numbers say one primary per board works; I design the sharding path for 10x."
  • "Precision follows attention: exact at the top and around me, approximate in the deep tail."
  • "Route events by match end time with a grace period, so rollover never loses a late match."
  • "Anti-cheat: only authoritative servers write over mTLS, plausibility checks at ingest, shadow-list outliers with ZREM, and delay archiving so bans reach the final standings."
  • "Cost is mostly memory: use short numeric ids (a UUID string costs about 30 more bytes), trim inactive players, expire daily and weekly sets."
Numbers to remember: 30M DAU; 3,500 events/s average, 14,000 peak; 42,000 ZINCRBY/s with 3 windows; 28,000 reads/s peak; about 100 B per member, 19 GB per mode; 30 + 23 = 53 bits; grace 10 minutes; dedupe TTL 48 hours.

11. Interview Q&A

Why a Redis sorted set instead of a SQL table with an index on score?

The most common question is "how many players beat me?", which is an order-statistic query. A sorted set keeps a skip list whose pointers carry spans, so rank, insert and range are all O(log N) in memory, in tens of microseconds. A B-tree index is fast for ordered scans, but counting the rows above a key usually walks the index range, which grows with N. Every update also pays for the write-ahead log and index upkeep. At 100 million players and 14,000 updates a second at peak, SQL needs heavy replication and caching to approximate what the sorted set gives natively. I would still keep a relational or wide-column table as the durable score store, because Redis is memory first.

How do you break ties fairly?

Redis orders equal scores by member bytes, so it would rank by player id, which is arbitrary. I pack a time component into the score: 30 bits of score and 23 bits of inverted seconds since season start, 53 bits total, the exact-integer limit of a double. A higher score ranks first, and among equal scores the earlier achiever wins. Pitfalls: ZINCRBY cannot work on the encoded value, so a script reads the pure score, adds, re-encodes and writes with ZADD. Scores above 2^30 would overflow, so ingest caps them. If product wants shared ranks, compute competition ranking from the count of strictly higher pure scores.

How do you serve around-me consistently?

Take the rank with ZREVRANK, then read the slice from rank minus 5 to rank plus 5 with ZREVRANGE. Both run in one Lua script, so no update can move the player between the calls and misalign the window. The cost is two logarithmic steps plus eleven rows. Names come afterwards from a profile cache in one batch, so the sorted set stays free of strings. On a hash-sharded board the neighbours are scattered across shards, so I would give exact around-me only inside the top set and bucket-based approximate windows for deep ranks.

One sorted set has outgrown one node. What now?

Redis Cluster cannot split a single key, so I split the board myself. Hash sharding by player id spreads load evenly and makes writes single-shard, but top K and exact rank need all shards (merge per-shard top K, sum ZCOUNT results). Range sharding by score makes reads cheap with a counts table, but creates skew, a hot middle shard and non-atomic moves at boundaries. I would combine them: an exact top set for the top 100,000, hash shards for the rest, and an approximate rank from a score histogram for the deep tail. This matches where users actually look.

Do daily and weekly boards triple the cost? How do you manage that?

Yes, I accept the amplification. Each event updates day, week and season sets in one pipelined round trip, so reads are single-key lookups and each window expires on its own. Building the weekly board with ZUNIONSTORE of dailies looks cheaper, but it blocks a single-threaded Redis for seconds on tens of millions of members. The real mitigations are batching, collapsing several events of one player into one write, smaller daily and weekly sets (only active players), and TTLs. Windows are picked by match end time with a grace period before archiving.

Redis loses data, or the whole cluster goes down. What do you do?

Redis is a derived view of the Kafka log plus the score table. For a node crash, a replica is promoted and workers re-apply uncommitted events idempotently. For a lost shard, I load the last snapshot and replay Kafka from its offset, which takes minutes. For corruption, I scan the score table and bulk load with pipelined ZADD into a new key, then RENAME it into place; at about 500,000 adds a second that is roughly 200 seconds for 100 million players. A nightly reconciliation job samples players and alerts on drift, and a weekly shadow rebuild proves recovery works.

How do you make score updates exactly-once?

True exactly-once delivery is not available over a network, so I get the same effect with at-least-once delivery and idempotent processing. Every match result has a unique event id. The worker claims it with an atomic set-if-absent on a dedupe key whose TTL (48 hours) is longer than the retry window. Then it applies a conditional update to the score table that also records the event id, then updates Redis, then commits the Kafka offset. A replay after a crash hits the dedupe key or the conditional update and does nothing. Because ZINCRBY is not idempotent, the guard must come first. In best-score modes ZADD GT is naturally idempotent.

Production incident: top-100 p99 latency suddenly jumps from 5 ms to 400 ms. What do you check?

First I look at Redis command latency and the slow log, because a single slow command stalls everything on that node. Likely causes: someone ran a huge ZREVRANGE or ZUNIONSTORE, a fork for a snapshot is running with heavy copy-on-write (check memory and fork duration), or the node is swapping. Then I check the top-K cache hit ratio, since a broken TTL or single-flight would send every request to Redis. Short term, serve the stale cached top list, kill the offending command, and shed load. Long term, cap range sizes, add alerts on fork time and memory above 70 percent, and keep admin tools off the live primary.

Production incident: players say their rank is wrong right after a match. Why?

Two likely causes. One is consumer lag: the event is still waiting in Kafka, so check the lag metric (alert above 10 seconds). The other is replica lag: the rank read hit a replica that is a few milliseconds behind. For the "my rank right after my match" screen I route that call to the primary, or retry once if the returned score is older than the score the client expects. If lag is normal, I sample the player against the score table to see whether Redis drifted, which the reconciliation job should already flag.

How do you detect and handle cheaters?

First remove the trust problem: only authoritative game servers write, over mutual TLS with signed events, so a modified client cannot post a score. Second, validate plausibility at ingest by rejecting deltas outside what one match can award, and run offline anomaly detection on score velocity. Third, make removal cheap: a flagged player is taken out of the public sorted sets with ZREM (shadow listing) and banned players leave all windows. Ranks of everyone below shift automatically, so nothing needs reordering. I delay final archiving a little so bans from review reach the permanent standings and rewards.

How do you build the friends leaderboard?

The social service returns the friend ids, usually a few hundred. I fetch their scores with one ZMSCORE call, sort the small result in the API and attach names from the profile cache. Rank among friends is the position in that list. I avoid ZINTERSTORE against a friends set on the hot path because it writes a temporary key and costs more as sets grow. For players with thousands of friends I cap or page the list. On a sharded board I group the batch by shard so each shard gets one call.

How would you add live rank updates?

I would not stream the whole board. After a score is applied the worker can compute that one player's new rank with ZREVRANK and push it over the existing WebSocket or push channel, only if it changed by more than a threshold and rate limited per player. For the public top 100, clients poll the cached endpoint every few seconds, or subscribe to a channel that publishes one diff per second. That keeps fan-out proportional to meaningful changes, not to the 14,000 events a second at peak.

Why not Cassandra or DynamoDB for the whole thing, or Flink for the top K?

Wide-column stores scale writes well, but rank needs counting, which they do not offer natively, so they are good as the durable score table and not as the ranking engine. A stream processor such as Flink is excellent for a global top K over a huge stream (like heavy hitters in ad click aggregation), but it cannot answer "what is my rank?" for an arbitrary player. Distributed transactions across Kafka, table and Redis would give exactly-once, but idempotent consumers achieve the same effect with far less cost.
