Case 18: Design a Job Scheduler

One-page cheat sheet. A system that runs tenant jobs (cron, one-off, delayed) at the right time, even when machines crash. Full write-up: Handbook case study 18.

ProblemRequirementsEstimationAPIData and storesArchitecture and flowsDeep divesScalingFailuresImpressQ&A (11)Links

1. Problem in 3 lines, and what to ask

One line: tenants register jobs (run this at 02:00 every day, run this once at a time, run this in 10 minutes). The scheduler must start each one on time, never lose one, and almost never run one twice, with 10 million jobs and 100 million runs a day.
AskAssume
Who uses it?Many tenants (teams or customers) who register jobs by API. They do not run the machines.
Job kinds?Cron (recurring, with a time zone), one-off (absolute time), delayed (N seconds from now; a one-off with the time worked out at submit).
What is "run"?Call a target: an HTTP endpoint, a queue topic, or a container. The job body is the tenant's code; we never look inside.
Timing accuracy?Start within about 1 s at p99 and 5 s at p99.9. Soft real time.
Delivery?At-least-once. Never lose a due run; a rare repeat is allowed, so jobs must be idempotent (safe to run twice).
Dependencies, long jobs, regions?Optional DAG (jobs that wait on other jobs). Jobs from seconds to hours. One primary region plus a warm standby.

2. Requirements

Functional

  • Create, update, pause, resume, cancel, delete jobs
  • Each run is visible: scheduled, queued, running, succeeded, failed, cancelled, timed out
  • Retry with exponential backoff, then a dead state with manual re-run
  • Dependencies (DAG) and a catch-up policy for missed runs
  • Cancel, "run now", history and metrics

Non-functional

  • No lost runs on any crash
  • One dispatcher per run; duplicates only in rare windows and made harmless
  • Start latency p99 under 1 s
  • 99.95% availability of the scheduling path
  • Fairness: one tenant's 5 million jobs must not delay others
  • 10M jobs, 100M runs/day, spikes at the top of the hour

Out of scope

  • The tenant's job code and image building
  • Workflow authoring UI, billing
  • Active-active across regions
  • Long business processes with human steps (use a workflow engine)

4. API (a few lines)

POST /v1/jobs   (Idempotency-Key header so a retried create does not make two jobs)
{ name, schedule: {cron expr + timezone | once at | delay seconds},
  target, payload, retry: {max_attempts, backoff, base_ms, max_ms},
  timeout_s, priority: high|normal|low,
  catch_up: skip|run_latest|run_all, concurrency: forbid|allow|replace,
  depends_on: [job ids] }
-> 201 { job_id, next_run_at }

GET /v1/jobs/{id}   PATCH /v1/jobs/{id} (bumps version)   DELETE /v1/jobs/{id}
POST /v1/jobs/{id}/pause | /resume | /run
GET /v1/jobs/{id}/executions?cursor=...
POST /v1/executions/{run_id}/cancel | /retry

Worker protocol (gRPC): Poll, Heartbeat(run_id, lease_token), Complete(run_id, lease_token, result)

The lease token is a number that goes up every time a run is handed out. The store uses it to reject a stale worker.

5. Data model and store choices

Table / storeKey and columnsWhy this store
job_defPK job_id; tenant, schedule, target, payload, retry, timeout, priority, catch_up, version, stateSource of truth for what the tenant asked. Rarely written; cached by (job_id, version).
schedulePK (shard, next_run_at, job_id); status, def_versionThe time index. A sorted index answers "due rows in shard S, oldest first" as a cheap range scan. Small and hot.
executionPK (job_id, run_id); state, attempt, lease_owner, lease_token, lease_expires_at, errorOne row per run. Time-partitioned so dropping old data is a cheap metadata step, not a giant delete.
dep_edge(downstream, upstream) plus a counter per runFor DAGs.
Job storeSharded relational DB: 64 logical shards on 8 to 16 primaries, with replicasTransactions let us claim a due row and create the execution atomically. Data is small; indexes are easy.
Coordinationetcd or ZooKeeper (a few hundred keys)Shard-owner leases and epochs. Consensus-backed, so only one owner wins.
Dispatch queueKafka or SQS-like, one queue per priorityDurable buffer for spikes; lets workers scale on their own.
Key idea: the database decides, the queue only carries. The queue can be lost and rebuilt from the database.
Why not the simple design: one process that runs SELECT ... WHERE next_run_at <= now() every second and runs jobs in threads. It is a single point of failure; two copies both run every job; a slow job starves scheduling; and a crash between "ran" and "updated next_run_at" loses or repeats a run. The rest of the design repairs these one by one.

6. Architecture and main flows

Flow A: create a cron job

  1. API checks the tenant, quotas (max jobs, minimum interval) and validates the cron and time zone.
  2. It computes the first run: next matching instant in that zone, stored as UTC.
  3. One local transaction on shard hash(job_id) mod 64 inserts job_def and schedule (same shard, so no distributed transaction).
  4. Returns 201 with next_run_at; a retry with the same idempotency key returns the stored answer.

Flow B: a run becomes due and executes

Flow C: cancel

  • Not yet due: mark the schedule row cancelled; the claim query ignores it.
  • Queued: state becomes cancelled; the worker checks state when taking the lease and drops it.
  • Running: set cancel_requested; the next heartbeat reply tells the worker to stop. Best effort, because the tenant's code may already have caused effects.

7. Deep dives

Deep dive 1: finding due jobs without double scheduling

OptionPrecisionDurable?Cancel / editVerdict
Poll an indexed tablePoll interval (about 0.5 s)ExcellentOne row updateThe foundation
Timer wheel (circular array of time slots in memory)Tick size (1 ms to 1 s)None; rebuild from tableRemove from slotAccelerator for the next few seconds
Delay queue (broker hides a message until a time)Broker dependentBroker dependentHard; delay limits; 10M hidden messages is heavyOnly for short retry backoffs

Choice: the table is the truth. Each scheduler loads the next 5 seconds of due rows into a small in-memory wheel and fires at the exact tick. A restart just reloads the window. Polling costs only 64 shards x 2 per second = 128 cheap queries per second.

No double scheduling needs two layers:

  • Layer 1, shard ownership. Each of the 64 shards has one owner at a time, held by a lease in the coordination store. Every new owner gets a higher epoch (fencing token). With 20 schedulers each owns about 3 shards; a dead one's shards spread over the survivors. This is one leader per partition, not one global leader.
  • Layer 2, atomic claim. In one transaction: select due rows FOR UPDATE SKIP LOCKED (batch of 500), insert an execution with the deterministic run id = job_id + scheduled_for (a unique key, so a second insert does nothing), and compare-and-set next_run_at to the next cron time. Then enqueue.
The enqueue gap: commit then crash before enqueue leaves a run QUEUED with no message. Fix with an outbox sweep: the reaper (and a restarted scheduler) re-enqueues runs that sit in QUEUED with no lease for a few seconds. Always commit first, then enqueue; the reverse can run a job the database does not know about.

Zombie worker: one that stalled past its lease can still finish its call to an outside system after a second worker did the same. Fencing protects our records only. The target must deduplicate on the idempotency key.

The "now" edge of the index64 edges instead of one, batches of 500, skip-locked claiming.

Build in phases: (1) one DB, one leader, queue, a few workers; (2) 64 shards with leases, epochs, outbox, priorities; (3) fair dispatch, DAGs, catch-up, canary jobs; (4) standby region and workflow-engine hand-off.

Consistency: claim and next-run update are one local transaction, so no distributed transaction is needed. Queue and database are not atomic together, hence the outbox and deterministic run id. State only moves forward because the result write is conditional on the lease token. Dashboards may read replicas a few hundred ms behind.

10. Things to say to impress

Say this:
  • "The database row is the truth; the queue is a pipe. Everything else follows from that direction."
  • "I separate finding due work from running it. The scheduler never runs tenant code."
  • "Ownership is per shard, not one global leader or a lock per job. That moves the coordination cost from per job to per shard."
  • "A lease gives failover, but a paused owner does not know it expired, so I add a fencing epoch and a deterministic run id (job id plus scheduled time)."
  • "Exactly-once is not possible at the scheduler. I choose at-least-once and make the effect exactly-once with an idempotency key."
  • "Priority is not fairness. A noisy tenant needs per-tenant weighted dispatch and running caps."
  • "Time is the quiet killer: UTC storage, cron in the tenant's zone, database clock for due-ness, explicit daylight-saving and catch-up rules."
  • "The metric I watch first is scheduling lag (start time minus due time). Any missed run alerts, and a canary job runs every minute in every shard."
  • "Security: block internal addresses for HTTP targets (SSRF), cap jobs and minimum interval per tenant, sandbox container jobs, store secrets by reference."

11. Q&A: follow-ups an interviewer asks

How do you make sure two scheduler instances do not run the same job?

Two independent layers. First, each shard has one owner at a time, held by a lease in a consensus store with an increasing epoch, and instances never scan shards they do not own. Second, the claim is atomic in the database: the run id is job id plus scheduled time with a unique key, and the next run time is advanced by compare-and-set. If a paused old owner wakes up, its writes carry an old epoch and the store rejects them. Even if all of that failed, a worker must take a lease on the run id before running, so only one worker executes it, and the target sees the same idempotency key.

Why not put every job in a delay queue and let the broker handle time?

It looks easy because the broker already holds messages until a time. In practice many brokers cap the delay, and a cron job has no end. Ten million hidden messages are heavy to run. Editing or cancelling one is awkward or impossible, while a table row is one update. Questions like "what runs tomorrow?" are also hard to answer. A delay queue is fine for short retry waits, where the message is created at failure time and lasts seconds.

The scheduler crashes right after it commits a run as queued. What happens?

That is the enqueue gap: the database says QUEUED but the message may not exist. We commit before enqueueing on purpose, so nothing runs that the database does not know about. A recovery sweep re-enqueues runs that stay QUEUED without a lease for more than a few seconds. Because the run id is deterministic and workers take a lease first, a duplicate message is harmless: the second worker fails to get the lease and drops it. The cost is a small delay, not a lost or double run.

Can you give exactly-once execution?

Not as a pure guarantee at the scheduler. If a worker calls an outside system and crashes before reporting, we cannot tell whether the effect happened. So we pick between at-most-once, which can lose runs, and at-least-once, which can repeat them. Losing a run silently is worse, so we choose at-least-once. We then get exactly-once effects through idempotency: the same key (the run id) on every attempt, which the target uses to ignore repeats. Inside our platform, the lease token fences the final state write so a stale worker cannot overwrite a newer result.

A tenant schedules five million jobs at midnight. What do you do?

Fairness is enforced in the dispatcher, not by queue order. Each tenant has a virtual queue and the dispatcher serves tenants by weighted round robin, so a small tenant waits at most one round. We cap running executions per tenant (for example 500) and dispatch rate, which slows the heavy tenant without rejecting its jobs. At registration, limits on job count and minimum interval stop abuse at the source. Jobs marked flexible get deterministic jitter to spread them over a window. Autoscaling on queue depth handles the rest.

How are missed runs handled after an outage?

The tenant picks a catch-up policy per job. With skip, anything older than a grace period is ignored. With run_latest, only the latest missed slot runs once. With run_all, every missed slot runs in order, up to a bound. In every case recovery is throttled and at lower priority than on-time work, so a ten-minute backlog released at once does not become a second spike. The next run time is computed from the previous scheduled time, so the cadence does not drift after catching up.

How do you deal with clock skew between machines?

I do not trust any machine's clock for cross-machine decisions. Whether a run is due is decided by the database clock inside the claim query, and lease expiry is judged by the store. Workers use a monotonic clock for local timeouts, which does not jump when NTP adjusts the wall clock. Ordering between machines comes from epochs, lease tokens and the run id, not from timestamps. I still alert on NTP offset, since large skew distorts lateness metrics and logs even if it does not break correctness.

Why a short lease with heartbeats instead of one long timeout?

A long timeout finds a dead worker only after the whole expected runtime, which could be an hour, so a crash would delay the retry by that much. A 30-second lease renewed every 10 seconds finds the death within about 30 seconds, whatever the job length. The separate job timeout still handles a worker that is alive but stuck, because heartbeats cannot tell real work from a hang. Together they bound the cost of both crashes and hangs.

How would you build job dependencies at scale?

Each downstream run is created in a WAITING state with a counter of unmet upstreams. When an upstream run succeeds, the worker finds the outgoing edges and does conditional decrements; at zero the run moves to QUEUED. Cycles are rejected at registration with a graph search. By default a failed upstream blocks downstream runs, with an option to run anyway, and waiting has a timeout so nothing waits forever. For branching, loops, human steps or long waits, I would hand off to a workflow engine instead of growing the scheduler.

Real-time incident: jobs are starting 30 seconds late. How do you debug?

Scheduling lag is the first metric, so I look at it per shard and per priority to see if it is one shard or all. If one shard: check shard ownership churn (a flapping scheduler), job store slow queries, and failover. If all: check queue depth and age of the oldest message, and worker utilization, since late starts with a deep queue mean too few workers. Also check the lease-expiry rate and the canary job. Then act: scale workers, shed or delay low priority, fix the slow index scan, and rely on the catch-up policy for runs already missed.

What would you change at ten times the scale?

I would raise logical shards to 256 or 512 so each stays small, and make the in-memory timer wheel the main dispatch path with the table as its recovery log. History would reach about 300 GB per day, so it moves to a column or log-structured store with heavy tiering. Finally I would add cells: independent full copies of the system for groups of tenants, which limits blast radius and makes capacity planning simpler, with the worker queue partitioned by cell.
