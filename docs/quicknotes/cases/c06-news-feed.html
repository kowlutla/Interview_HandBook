Case sheet 6: Design a News Feed

One-page cheat sheet: the home feed of a social network for 500 million users. Full write-up: Handbook case study 6.

ProblemRequirementsEstimationAPIDataArchitectureDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: show each user a personal, mostly recent list of posts from the accounts they follow. One post must appear in many lists, and opening the app must feel instant.
  • The prompt hides two problems: a write path (spread a post to followers) and a read path (build one page). The design is a choice of how much work to do on each side.
  • Scale: 500 M users, 300 M daily active users (DAU). Follows are one-way (like Twitter or Instagram). Average user follows about 200 accounts, but a few accounts have tens of millions of followers.
  • Feed is ranked by default, with a "latest first" toggle.

Clarifying questions to ask (and the answers we assume)

AskAssume
How many users?500 M registered, 300 M DAU
Follow type?Directed, about 200 follows each, very skewed follower counts
Ranked or chronological?Ranked by default, latest toggle must also work
How fresh?Normal post in followers' feeds in seconds (p99 under 10 s); celebrity post within about 30 s
Read latency?p99 under 300 ms server side, first page of 20 posts

Media? Edits? Deletes?Text plus optional photo or video. Short edit window, deletes allowed
Global?Yes. One region in depth, multi-region in a short note

2. Requirements

Functional

  • Publish a post (text plus optional media)
  • Follow, unfollow, block, mute
  • Open the feed and scroll page by page, without end
  • Edit or delete a post, and every feed reflects it
  • Emit events a notification service can use

Non-functional

  • Read-heavy and fast first page
  • Highly available: a slightly stale feed beats an error page
  • Eventually consistent, but the author sees their own post at once (read-your-writes)
  • Handles skew: a 50 M follower account must not melt the system
  • Durable: an accepted post is never lost

Out of scope

  • Comment and like storage
  • Ad insertion
  • Full-text search
  • Direct messages
  • Moderation model internals
  • Media transcoder internals

3. Estimation (same numbers as the handbook)

4. API

POST /v1/posts            { text, media_ids[], client_request_id }  -> 201 { post_id, created_at }
GET  /v1/feed?mode=ranked|latest&limit=20&cursor=OPAQUE
                          -> { items[], next_cursor, has_more }
PUT /v1/posts/{id}   (edit, within 30 min)     DELETE /v1/posts/{id}
POST|DELETE /v1/users/{id}/follow              POST|DELETE /v1/users/{id}/block
GET /v1/users/{id}/posts?cursor=...            (profile timeline, not home feed)
  • client_request_id makes posting idempotent (a retry after a timeout makes no duplicate).
  • The cursor is opaque and signed, so we can change its insides later and clients cannot forge it.
  • User id comes from the token, never the body. Media is uploaded separately and only referenced by id.

5. Data model and store choices

DataStoreWhy
Follow graphSharded key-value or wide-column, two tablesAccess is only by user id, no joins, huge size, cheap scans per user
PostsSharded wide-column or sharded MySQL, key post_idPoint lookups by id, append-heavy, spreads load; author index for profiles

Feed cacheRedis sorted set per user, sharded by user idOrdered by score, cheap range reads and trims, memory speed
MediaObject store plus CDNBig immutable blobs, cheap per GB, CDN cuts latency and origin cost
Fan-out workKafkaDurable, replayable, absorbs bursts, workers scale on their own
posts:     post_id (64-bit time-ordered) | author_id | text | media[] | created_at | edited_at | deleted | visibility
following: (user_id, followee_id)      -- "whom do I follow", partition key user_id
followers: (followee_id, follower_id)  -- "who follows me", partition key followee_id
feed:      ZSET feed:{user_id}   member = post_id, score = timestamp (or coarse rank score)
user_flags: user_id | last_active_at | is_celebrity | follower_count
  • Time-ordered id (Snowflake style: 41 bits of milliseconds, 10 bits machine, 12 bits sequence): sorting by id is almost sorting by time, so it works as a score and a cursor.
  • Graph stored twice: fan-out needs "all followers of X"; feed rebuild needs "everyone I follow". One table cannot do both with a single-partition scan. The second write may lag; a repair job reconciles.
  • The feed holds ids only (8 bytes). An edit changes one record instead of 200 copies.

6. Architecture and main flows

Write flow: publish a post

  1. Client sends the post with a client_request_id. The gateway authenticates and rate-limits.
  2. Post service makes the id and writes the row with quorum durability. It saves the PostCreated event in the same transaction (transactional outbox) so a row is never saved without its event. A relay sends it to Kafka.
  3. The author's own feed is written synchronously (read-your-writes). Client returns 201 now.
  4. Workers consume the event, read the author's followers 1,000 at a time, drop inactive and blocked ones, and send pipelined ZADD calls grouped by Redis shard, then trim to 500.

Read flow: open the feed

  1. Feed service range-reads the user's sorted set (newest about 300) and, in parallel, fetches recent posts of the celebrities the user follows.
  2. Merge and dedupe by post id. Ranking service scores about 300 candidates (budget about 100 ms).
  3. Batch-fetch 20 post bodies from the post cache. Filter deleted and blocked ones; over-fetch (about 30 ids) so the page still has 20.
  4. Return the page plus a signed next_cursor.

7. Deep dives

7.1 Fan-out: push, pull or hybrid

One line: push for normal authors, pull for celebrities, merge at read time.
PropertyPush (write)Pull (read)Hybrid
Feed read costOne range readAbout 200 lookups plus mergeOne range read plus 5 to 20 hot reads
Post write costO(followers)O(1)O(followers) normal, O(1) celebrity
Wasted workHigh unless filteredNoneLow (active-only push)
Celebrity freshnessDelayed by queueImmediateImmediate
StorageLarge (copies)SmallMedium (about 5 TB)
ComplexityLowLowHigher: two paths, flag management

Choice: hybrid. Cost is driven by skew: a tiny share of accounts (say over 100 K followers, about 0.01%) make push expensive. A celebrity flag turns on at 100 K and off at 50 K (hysteresis, so it does not flap). A hard cap per post (for example 100 K inserts) routes the rest to pull. Make push cheap with: active-only push (20 B to 12 B per day), pipelined batches per Redis shard (about 4,200 commands/s per primary, far under the roughly 100 K/s a shard can do), chunked idempotent tasks for big authors, and separate Kafka lanes for large authors.

7.2 Feed cache structure and pagination

OptionGoodBad
Redis list (LPUSH, LTRIM 500)Cheap append, trim, small memoryOffset paging drifts as items arrive; removing one item is O(N); no score for ranked mode; cannot insert late items in order
Redis sorted set (ZADD, trim)Ordered by score; stable range-by-score cursors; ZREM is O(log N); idempotent re-insert; backfill lands in orderAbout 2 to 3x memory per entry; O(log N) insert (fine for N = 500)

Choice: sorted set, key feed:{user_id}, member post id, score timestamp, trimmed to 500, TTL about 14 days. Cursor by value, not offset: latest mode cursor is (last score, last id), next page is "20 items strictly older". New posts land at the head and never shift page 2. Ranked mode: snapshot the top 100 ranked ids under a session id (30 minute TTL), cursor is (session_id, position); build a new snapshot, excluding seen ids, when it runs out. If the cursor is older than the trimmed tail, fall back to the post store.

7.3 Ranking, deletes and repair

StageWhat happens
1. CandidatesPushed ids plus celebrity posts, about 300 ids
2. FeaturesPost age, author affinity, engagement, media type, from a feature store
3. ScoringModel predicts like, reply, dwell; weighted into one score
4. Re-rankDiversity, dedupe, safety, ad slots; top 100 snapshot

Ranking budget is about 100 ms; if the ranker times out, sort by recency. Ranking works at read time on a few hundred ids, so the write path stays untouched.

EventHow it is handled
EditUpdate post row, evict cache. Feeds hold ids, so every feed shows it on next read; no fan-out
DeleteSoft delete (tombstone); hydration skips it at once; background job later does ZREM for memory
Block / unfollowRead-time filter against cached block and follow sets (mandatory for privacy); cleanup job removes entries; workers check blocks before pushing
FollowBackfill the new followee's last 20 posts into the follower's ZSET
Cache lost / user returnsRebuild: followees x last 20 posts (about 4,000 candidate ids), bulk ZADD top 500; single-flight per user, rate limited, show a partial feed first

Choice: ids in the feed plus read-time filtering. Correctness for deletes and blocks lives at read time; cleanup is only an optimisation. Media goes straight to object storage by pre-signed URL, is scanned and resized asynchronously, and is served by the CDN with content-hash URLs (immutable, cacheable for a year).

8. Scaling and bottlenecks

DataShard keyNote
Feed cacheHash of user_idOne user's feed on one shard, so a read is one call. Even load because feeds are bounded at 500
PostsHash of post_idA celebrity's posts spread out. Author index is a separate table
Graphfollowing by user_id; followers by followee_idHuge celebrity follower partitions split by hash(follower_id) mod 256 for parallel scans
KafkaAuthor id; random key for chunk tasksScores make per-author order unnecessary
  • Hot celebrity timeline: read by millions of loads. Keep it in an in-process cache on every Feed service instance (TTL a few seconds) plus replicated Redis copies.
  • Viral post: near caches, request coalescing, counters served by a separate counter service.
  • Hot Redis shard: watch per-shard QPS, add read replicas, reshard slots.
  • Fan-out burst (final, election): Kafka absorbs it, workers autoscale on consumer lag, least active followers are dropped first.
  • Latency budget for a normal post: DB write 100 ms + outbox relay 100 ms + Kafka 50 ms + queueing 1 to 3 s + worker work 50 ms = about 2 to 4 s. Alarm on fan-out lag p99 over 10 s.
  • Multi-region: each user has a home region; writes go there and replicate asynchronously (usually under a second); each region builds feed caches from the replicated stream; after a region failure users rebuild, with a stale feed for some minutes.
  • Biggest costs: feed RAM (200 nodes), media storage (22 PB/year), CDN egress (a 95% vs 90% hit ratio halves origin egress), ranking compute (30 M scored items/s at peak).

Common mistake: storing full post bodies in the feed (edits and deletes then rewrite hundreds of millions of copies, memory grows 30 to 100x), or using offset paging (repeats and skips when new posts arrive).

10. Things to say to impress

Say this:
  • "Feed is two problems, a write path and a read path. Numbers say reads are 30:1 by requests and 600:1 by items, so I do work at write time, then bound it for celebrities."
  • "Fan-out cost follows skew, so I use a hybrid: push for normal authors to active followers only, pull for celebrities, with a flag that has hysteresis and a hard cap as a safety net."
  • "The feed cache is derived data, not a source of truth, so I can rebuild it. That is why I can run it with weak durability and treat a node loss as a rate-limited rebuild, not an outage."
  • "Feeds hold ids, so edits are free. Deletes and blocks are enforced at read time because privacy cannot wait for a fan-out; cleanup is only for memory."
  • "Cursors by value, signed and opaque, with a session snapshot for ranked mode. I choose cursors on day one because changing pagination later breaks clients."
  • "I would watch fan-out lag, short-page rate, cache hit rate and rebuild rate, and I know the 10x plan: cell-based deployment and a lower celebrity threshold."
  • "Phasing: one database with pull at 1 M users, Redis and push by 50 M, then the celebrity path, ranking and multi-region at 500 M."

11. Interview Q&A

Why not compute the feed on read with a join, like a normal database app?

A join is fine when a user follows a few accounts. Here a user follows about 200, and each load needs the newest posts of 200 authors spread across many shards. At 100 K loads per second that is about 20 million probes per second, and each page is as slow as the slowest of 200 parallel calls, so the tail latency is poor. Precomputing at write time turns it into one sorted-set range read. The price is write amplification, which the hybrid bounds. I would still keep the pull code, because it is also the rebuild path.

How do you decide who is a celebrity, and what happens at the boundary?

I use follower count, since it directly measures fan-out cost. The threshold is around 100,000, where one post costs about 100,000 inserts. To stop flapping I use hysteresis: on above 100 K, off below 50 K. Accounts near the line work with either strategy, only at different cost. Posts pushed before the flag flipped stay in sorted sets and are deduplicated by post id when merged. As a safety net the worker caps inserts per post and sends the rest of the followers to the pull path.

A user follows 3,000 accounts, 20 of them celebrities. How does the read change?

The pushed part is unchanged: one range read from their sorted set. For the 20 celebrities the Feed service reads 20 small, hot timelines in parallel, mostly from in-process or Redis memory, which adds a few milliseconds. We take only the last few posts of each, merge by score and dedupe against the pushed list. If someone follows hundreds of celebrities, I limit the pull to the most engaged 50 and use a per-user celebrity candidate list refreshed every minute.

How does pagination stay correct while new posts keep arriving?

The cursor records a position by value, not an offset. In latest mode it holds the last score and post id seen, and the next page is the 20 items strictly older. New posts go to the head, so older pages do not shift and nothing repeats. In ranked mode the order comes from a model, so I snapshot the top 100 ids under a session id and page by position, building a new snapshot (excluding seen ids) when it runs out. The cursor is opaque and signed, so I can change the format and clients cannot forge it.

A user deletes a post or blocks someone. How fast does it vanish, and how do you guarantee it?

Feeds store only ids, and every page is hydrated against the post store or cache, where deletes are tombstones and block sets are checked. So the post is gone on the next read, however many feed copies exist, without a fan-out of removals. A background job later removes stale ids from sorted sets to save memory. The key decision is that correctness for privacy changes lives in read-time filtering and the cleanup is only an optimisation. Because filtering can shorten a page, the Feed service over-fetches, for example 30 ids for 20 slots.

What happens if a Redis feed shard fails?

A replica is promoted, usually in seconds. Replication is asynchronous, so a few of the latest inserts may be lost. If the data is gone, the Feed service treats an empty or missing list as a miss and rebuilds it from the graph and author timelines. I guard that with single-flight per user and a global rate limit, so losing a shard of several million users does not become a stampede on the graph and post stores, and I return a partial feed from the newest authors first. The cache is derived and recoverable, which is why it does not need strong durability.

Fan-out lag suddenly goes from 3 seconds to 2 minutes. What do you do?

First I look at consumer lag in Kafka and see whether workers are slow or the input jumped. If a big event caused a burst, I scale workers up and check that the large-author lane is separate so normal posts are not stuck behind it. I check Redis shard health and per-shard QPS, because a slow shard slows every pipelined batch. If it is a wrong celebrity flag, I apply the per-post cap so the rest goes to pull. Meanwhile reads still work and authors see their own post at once, and if needed I drop pushes to the least active followers first.

How do you stop fan-out from delaying the author, or creating duplicates?

The request returns after the durable write and the stored event (outbox pattern), and fan-out runs asynchronously, so the author never waits. Their own feed is written synchronously for read-your-writes. Duplicates cannot appear because a sorted-set member is unique, and a replayed fan-out adds the same member with the same score, which does nothing. Client retries are covered by the client request id that makes post creation idempotent.

How would you add "recommended posts from accounts you do not follow"?

It is one more candidate source, not a storage change. A recommender produces candidate ids per user, either stored in a per-user list or served on demand. The ranking service merges them with followed content and marks their source, and the re-ranking stage enforces a mix, for example at most one in four. Since the feed stores ids and ranking runs at read time, this plugs in without touching the fan-out pipeline.

How do you handle a new user, or one who returns after a month?

A new user follows nobody, so we show onboarding and a trending feed built from popular posts, and as they follow accounts we backfill each followee's recent posts into their sorted set. A returning user was dropped from active-only push, so their list is expired or stale. On first open the Feed service detects that and runs the rebuild path: a quick partial result from the newest authors, with the rest filled in the background. The rebuild rate limit caps the cost, and an opened push notification can warm the feed in advance.

Why Redis sorted sets and not lists for the feed? Why store ids and not full posts?

A list is cheap to append but paging by offset drifts when new items arrive, removing one item is O(N), and there is no score to support ranked mode or to insert a late item in order. A sorted set orders by score, gives stable cursors by value, removes one post in O(log N), and makes re-inserts harmless. It costs about 2 to 3x more memory per entry, which is acceptable at 500 entries. Storing ids rather than bodies keeps entries at 8 bytes, makes edits and deletes touch one record, and avoids 30 to 100x memory growth.

The interviewer asks for a strictly consistent feed. What do you say?

I would ask which guarantee really matters. For a social feed it is read-your-writes for the author, monotonic reads within a session, and prompt effect of deletes and blocks. We give those with a synchronous author write, sticky routing to one replica per session, and read-time filtering. A single order seen identically by all followers at the same instant needs cross-shard coordination on every post. That costs latency and availability and gives users no visible benefit, so I choose availability and explain it with the CAP trade-off.

What would you change at 10x scale (5 B users, 3 M feed QPS)?

Graph and feed cache shard counts grow 10x, and fan-out lag becomes the main risk. I would move to cell-based deployment, where each cell owns a slice of users with its own Redis, Kafka and workers, so a failure or a hot spot stays inside one cell. The celebrity threshold is lowered because total fan-out cost grows with followers. More ranking moves to precomputed candidate pools per user, and feed entries stay as small as possible, ids plus a few features.
