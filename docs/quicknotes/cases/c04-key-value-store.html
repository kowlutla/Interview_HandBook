Case Sheet: Design a Key-Value Store

A Dynamo-style, always-writable, leaderless store. One page to revise before the interview. Full solution: Handbook case study 4.

1 Problem2 Requirements3 Estimation4 API5 Data and stores6 Architecture and flows7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines and clarifying questions

Problem: Store and fetch opaque values by key (no joins, no SQL). Hold far more data than one machine, answer in a few milliseconds, and keep taking writes while machines die. A key-value (KV) store is the simplest database interface, so all the interest is inside.
AskAssumeWhy it matters
One machine or many?Many. Data far exceeds one box.Forces partitioning (split data) and replication (copies).
Key and value size?Key up to 256 B, value up to 1 MB, average 2 KB, opaque.Sets storage and bandwidth.
Read:write ratio?About 4:1, bursty.Picks compaction style and cache design.
Consistency?Availability first. Eventual consistency is fine; the app resolves conflicts.The AP side of CAP.
Latency?p99 under 10 ms in region.No cross-region wait on the hot path.
Regions?2 to 3 data centers, each with a full copy.Needs data-center-aware replicas.
Transactions or range scans?No. Point get/put/delete only.Allows hash partitioning.
Cache or database?Durable database.Needs a write-ahead log and disk.

2. Requirements

Functional

  • put(key, value, context): context is version info from an earlier read.
  • get(key): returns the value, or all conflicting values plus a context.
  • delete(key, context): really a write of a marker called a tombstone.
  • Caller picks how many replicas must answer (tunable consistency).
  • Optional TTL per key.

Non-functional

  • Writes succeed during failures; 99.99% request availability.
  • p99 under 10 ms in region.
  • Add nodes to add capacity; only a small share of data moves.
  • Acknowledged write survives loss of any one node.
  • Replicas converge after a partition heals, with no operator.
  • No master: every node can take any request.

Out of scope

  • Multi-key transactions, secondary indexes, range queries.
  • Strong (linearizable) consistency. We only contrast with it.
  • Deep security and key management.
Key idea: "always writable" plus "eventually consistent" forces replicas to accept writes on their own. That creates conflicts, which need versioning, merging, and background repair. Everything else follows from this.

4. API

GET    /v1/kv/{key}?r=2
  200 { "values": [ {"value": "base64", "ts": 1731800000123} ], "context": "opaque" }
  // several entries = concurrent versions (siblings); 404 if missing or deleted

PUT    /v1/kv/{key}?w=2
  { "value": "base64", "context": "opaque-or-empty", "ttl_seconds": 86400 }
  200 { "context": "new-opaque" }     503 if fewer than w acks in time

DELETE /v1/kv/{key}?w=2   { "context": "opaque" }   204
  • Opaque context: the client reads it from a get and sends it back unchanged. Inside is a version vector. Hiding it lets the server change the format later.
  • r and w: how many replicas must reply. Default N = 3, r = 2, w = 2.
  • Idempotent: retrying the same put with the same context writes the same version, so it is safe.

6. Architecture and main flows

All 40 nodes run the same software. Any node can be the coordinator for a request: it finds the key's replicas, forwards the work, collects replies, and answers. A smart client library can hold the ring map and call a replica directly, saving one network hop.

Put flow (W = 2)

  1. Client sends put(key, value, context, w=2) to a coordinator, ideally one of the three replicas.
  2. Coordinator hashes the key and reads its preference list (the N nodes that own the key) from the ring map.
  3. It builds the new version: bumps its own counter in the version vector and stamps its wall-clock time.
  4. It writes locally (commit log, then memtable) and sends the record in parallel to the other two replicas.
  5. Each replica appends to its log, updates its memtable, and acks.
  6. After 2 acks the coordinator says success. The slow or dead third replica is repaired later.
  7. If fewer than 2 acks come before the timeout (say 50 ms), return an error. The write may still sit on one replica; a retry is safe.

Get flow (R = 2)

  1. Coordinator asks the closest replica for the full value and the others for a digest (a hash of what they hold).
  2. With 2 replies, equal digests mean return the value.
  3. If they differ, fetch full versions and compare version vectors: a descendant wins; concurrent ones go back as siblings.
  4. Read repair: write the winner to any stale replica, in the background.

7. Deep dives

Deep dive 1: partitioning (consistent hashing with virtual nodes)

Picture the hash space as a circle. Each node owns positions on it called tokens. Hash the key, walk clockwise to the first token: that node is the primary. The next two distinct machines clockwise are the other replicas (that list is the preference list). A virtual node (vnode) is one token; each machine owns many, here 256.

StrategyProsConsVerdict

Range partitionSupports scansHot rangesNot needed
Choice: ring with 256 vnodes per node (10,240 tokens, about 6.4 GB per range across replicas, a handy unit for streaming and repair). Too many tokens slows repair; newer systems use 16 or fewer with smart allocation.

Deep dive 2: versioning and conflicts (vector clocks)

Any W of N replicas can take a write, and sloppy quorums let other nodes take it too, so two clients can update one key at once. A vector clock is a list of (node, counter) pairs on each value. A coordinator copies the vector from the client's context and bumps its own counter. If X has every counter at least as big as Y, X is newer and Y is dropped. If neither covers the other, they are concurrent: keep both as siblings and return both.

Example: cart [milk] is {A:1}, then [milk, eggs] is {A:2}. Client 1 adds bread via A, giving {A:3}. Client 2, cut off, adds juice via B, giving {A:2, B:1}. These are concurrent, so the next get returns both. The client merges to [milk, eggs, bread, juice] and writes back with {A:3, B:1}, which beats both.

Choice: vector clocks with client merge by default, LWW per bucket for data where a lost concurrent update is harmless (sessions, last-seen). Cap vector size (for example 10 entries; truncation only causes extra siblings, never lost data) and alert on sibling counts.

Deep dive 3: healing replicas (hints, read repair, Merkle trees, gossip)

LayerTriggerScopeCatches
Hinted handoffNode returns after short outageOnly writes it missedMinutes to hours of downtime
Read repairA read sees stale replicasKeys that are readDrifting hot keys
Merkle anti-entropyScheduled, or after a long outageWhole key rangeCold keys, expired hints, silent corruption
  • Sloppy quorum and hinted handoff: if a replica is down, write to the next healthy node on the ring with a hint saying who really owns it. When gossip says the owner is back, stream the hints over and delete them. Hints expire (say 3 hours) and can be lost, so they never replace repair. Cost: a read may miss the parked write until handoff.
  • Merkle tree: a tree of hashes over key buckets. Replicas compare root hashes; equal means identical. If not, descend only into differing subtrees and exchange keys in the differing leaf. Cost is proportional to the differences, not the data.
  • Gossip: about once a second each node swaps its cluster view (heartbeat counters, state, tokens) with a few random peers. News reaches 40 nodes in a handful of seconds.
  • Phi accrual detector: instead of a fixed timeout, it scores how late a heartbeat is against its usual rhythm, and marks down above a threshold (for example 8). Down is a local, reversible opinion. Removal from the ring is an explicit operator action, so a flaky network never triggers mass data movement.

Deep dive 4: storage on each node (LSM tree and tombstones)

Size-tieredLowHigher (key in many files)Up to 2x free for big mergesWrite-heavy, time-series

Choice: leveled compaction, because the mix is 4:1 reads and p99 is 10 ms; NVMe has plenty of write bandwidth. Commit log sync by group commit (every few ms).
Tombstones: SSTables are immutable, so a delete writes a versioned "deleted" marker. Drop it too early and a replica that missed the delete copies the old value back (the key resurrects). Keep it for a grace period (for example 10 days) longer than repair interval plus longest tolerated downtime.
Raft contrast (know the one-liner): Raft-based stores (etcd, TiKV) have one leader per key range ordering writes in a log, so reads and writes are linearizable and compare-and-set works. In a partition the minority side cannot write, and elections pause writes briefly. Choose by the cost of a stale read: cart, pick leaderless; lock or balance, pick Raft. Real platforms use both.

10. Things to say to impress (senior and lead level)

  • "R + W > N gives overlap, not linearizability. A write acked by one node and reported failed can still be read later, and sloppy quorums break the overlap during failures."
  • "Down and removed are different states. A flaky link triggers hints, not a rebalancing storm."
  • "Tombstone grace must exceed repair interval plus longest downtime, or deleted data comes back."
  • "Vector clocks do not use wall clocks, which is why they are safe under skew; LWW does, which is its weakness."
  • "Keep the ring topology in a small Raft group (strongly consistent control plane) while the data path stays leaderless."
  • "I would build in phases: single-node LSM, then ring plus quorums with LWW, then gossip and hints, then Merkle repair and vector clocks, then multi-region and quotas."
  • "Cost: storage dominates (160 TB raw for 66 TB of data). Every extra copy or data center multiplies it, so ask whether each key space needs 9 copies."
  • "Observe: pending compactions, SSTables per read, hints backlog, read repair rate (a rising rate means drift), time since last repair per range, sibling count."

11. Interview Q&A

Why consistent hashing with virtual nodes instead of hash modulo N?

With modulo, changing N changes the answer for almost every key, so adding one node to 40 would move about 97.5% of the data. On a ring, a new node only takes the ranges next to its tokens, about 1/(N+1) of the data. One token per node still gives uneven load and dumps a dead node's whole load on one neighbour. With hundreds of vnodes per machine, load evens out, data streams from many peers at once when a node joins, and bigger machines can simply get more tokens.

How do you pick R and W, and does R + W > N mean strong consistency?

R = 2 and W = 2 with N = 3 is the balanced default: every read set overlaps every write set, and one replica can be down. R = 1 and W = 3 favours reads; R = 3 and W = 1 favours writes. But overlap is not an ordering guarantee. A write that reached one node and was reported failed can still show up, concurrent writes both succeed and become siblings, and sloppy quorums remove the overlap during failures. If you need a total order or compare-and-set, use consensus.

What is a sloppy quorum and what does it cost?

When some of the key's own replicas are unreachable, the coordinator writes to the next healthy nodes on the ring and attaches a hint naming the true owner. That keeps writes alive even with two of three replicas down. The price is that a later read from the usual replicas may miss the parked write until handoff finishes, and hints can expire or be lost. So it trades consistency for availability and must be paired with read repair and anti-entropy.

Explain vector clocks with an example. When would you use last-write-wins instead?

A vector clock is a set of per-node counters on each value. A write bumps the coordinator's counter on top of the version the client read. If one vector covers another, the covered one is obsolete. If not, the writes were concurrent and both are kept. For example {A:3} and {A:2,B:1} are concurrent, because each has a counter the other lacks. The client merges and writes back with both in its context. I would use LWW only where losing a concurrent update is harmless, such as session heartbeats, because it trusts wall clocks and silently drops one write.

A node was down for two days. How does it catch up?

Hints only cover a few hours, so they have expired. The node restarts and replays its commit log. Then Merkle-tree anti-entropy compares each of its ranges with the other replicas, finds the differing leaf buckets with a few hash exchanges, and streams just those keys. Read repair also fixes keys as clients read them. The key operational rule is to finish repair before the tombstone grace period ends, or deleted keys can come back.

Why do we need tombstones, and what goes wrong if they are removed early?

Files are immutable and a delete must reach replicas that may be down, so a delete is a versioned marker that spreads like any write. If it is dropped before every replica has it, a replica that missed the delete still holds the old value, and repair treats that as the only version and copies it back. So we keep tombstones longer than the repair interval plus maximum downtime. The downside is that many tombstones slow reads and use space, so delete-heavy loads need tuning or time-bucketed tables.

How does the LSM tree give fast writes and still fast reads?

A write is a sequential append to the commit log plus an insert in the in-memory memtable, so there is no random disk write. Full memtables flush to immutable sorted files, and background compaction merges them to keep the count small. A read checks the memtable, then asks each file's bloom filter whether the key could be there, which skips nearly all files that do not hold it, then uses the index to read one block. Leveled compaction keeps about one candidate file per level, so read latency is predictable, at the cost of more write amplification.

One key gets 100,000 reads per second. What do you do?

Three replicas cannot absorb that while the cluster idles. First put a short-TTL cache in front: a 1-second TTL cuts it to about one read per second per cache. Then let reads use R = 1 across all three replicas and coalesce identical in-flight reads at the coordinator. If still too hot, store several copies under suffixed keys and read a random one; for hot counters, shard and sum on read. Finally sample per-key request rates so such keys are found automatically.

How do you add a node with no downtime?

The new node contacts seed nodes, learns the ring by gossip, and picks its tokens. It enters a joining state and streams each of its small ranges from the current owners while also receiving new writes for them. It does not serve reads until streaming is done. Because the ranges come from many peers, each sends a little, and throttling protects foreground latency. Old owners delete the moved data only after the join completes. Topology changes are done one at a time so ownership views never conflict.

When would you pick a Raft-based store instead?

When a stale read or conflict is unacceptable: locks, leader election, configuration, unique-name constraints, balances, or the ring metadata itself. Raft has one leader per range ordering a replicated log, so reads and writes are linearizable and compare-and-set works. The cost is a leader hop plus majority write on each write, a pause during elections, and no writes on the minority side of a partition. The leaderless store stays writable on both sides with lower cross-region latency, at the cost of siblings. Many systems use both.

How does failure detection work, and what happens when a node is marked down?

Nodes gossip heartbeat counters. Each node records when heartbeats arrive, and a phi accrual detector turns the gap since the last one into a suspicion score compared with a threshold. This adapts to network jitter far better than a fixed timeout. Marking down is local and reversible: peers stop sending requests there and start storing hints, but no data moves. Only an operator action or a long-outage policy removes the node from the ring and starts re-replication.

Production incident: read latency suddenly doubles across the cluster. How do you investigate?

I would check node-level signals first: pending compactions, SSTables touched per read, disk fill, and bloom filter false-positive rate. A compaction backlog or a recent node rebuild is a common cause, since compaction steals I/O and leaves many files per key. Next I would look at tombstones scanned per read after a big delete job, at one slow node dragging tail latency (fix with speculative retry), and at read repair rate in case replicas are drifting. Mitigate by throttling ingest and repair, shifting reads to healthy replicas, and adding nodes if disk is the limit.

Why leaderless replication rather than a primary per range, for this workload?

The requirement is 99.99% write availability with single-digit-millisecond latency in every region. In a leaderless design any replica can take a write, so a dead node or a partition never blocks it, and there is no leader election pause. A primary-per-range design is simpler to reason about and gives ordering, but writes stall while a new primary is chosen and cross-region writes pay a round trip. We accept siblings and eventual consistency to get availability, and give applications tunable R and W plus vector clocks to manage conflicts.
