Case Sheet 15: Ticket Booking / Flash Sale

One-page cheat sheet. One million people click "buy" for 50,000 seats at the same second. Full solution: Handbook Case study 15.

ProblemRequirementsEstimationAPIDataArchitectureDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

Say it: Design Ticketmaster or BookMyShow, focused on the on-sale moment. Many buyers fight for a few individually numbered seats. The one hard rule: a seat is never sold twice. Speed and fairness may bend; that rule may not.
  • Core difficulty: contention. All the traffic hits the same few thousand rows, not a billion rows spread out.
  • Main ideas: a waiting room to shape load, a short-lived hold on a seat while paying, a database as the final judge, and a payment saga.

Clarifying questions to ask

AskAssume
Reserved seats or general admission?Both. Reserved is the hard case. General admission (just a count) is the flash-sale variant.
Biggest event?50,000 seats, 1,000,000 buyers at on-sale (20:1).
Can a user hold a seat while paying?Yes, for 10 minutes. No payment means the seat goes back.
Tickets per order?Up to 6, about 2 on average.
Is a stale seat map OK?Yes. A stale "free" seat just fails politely on click. Selling twice is never OK.
Payments?External provider. We do not build it (see Case 14).
Fairness and bots?Roughly first come first served for real people. Limit bots and scalpers.
Regions?Each event has one home region that owns its inventory writes.

2. Requirements

Functional

  • Browse events and see the seat map
  • Place a time-limited hold on seats (or a count)
  • Pay: seats become sold and tickets issue; fail or timeout releases them
  • View and cancel orders
  • Virtual waiting room for big sales

Non-functional

  • Correctness first: no double sale, no charge without a seat
  • Browse and queue stay up at 100x load
  • Seat map under 1 s; hold under 300 ms p99
  • Fair: close to arrival order, 50 tabs do not help
  • Durable: confirmed orders survive any single failure

Out of scope

  • Resale market, dynamic pricing
  • Venue seat-map editor, tax
  • Payment provider internals
  • Barcode scanning at the gate

3. Estimation (worked out)

Key point: normal load is tiny (about 385 requests/s average, 2,000 at peak, about 3 tickets/s). The design is about the spike, not the average.

Numbers to remember: 1M users, 50,000 seats, 500 admits/s, about 1,500 hold attempts/s, 150 orders/s, 300,000 raw requests/s, 200,000 availability reads/s. One event's seat bitmap is about 6 KB, so a whole event fits in one Redis node.

Plain meaning: the part that must be correct (holds and orders) is small, a few hundred to 1,500 writes a second. The scary part (300,000 requests/s) must be soaked up by the CDN, caches and the waiting room before it touches inventory.

4. API (short)

GET  /v1/events/{id}                    cacheable, CDN
GET  /v1/events/{id}/availability       {version, sections:[{id, free, price}]}  stale OK
GET  /v1/events/{id}/sections/{s}/seats seat-level map (cached)
POST /v1/queue/{id}/join                -> {queueToken, position, estWaitSec}
GET  /v1/queue/{id}/status?token=...    -> WAITING | ADMITTED + admitToken
POST /v1/events/{id}/holds              (admitToken, Idempotency-Key) {seatIds} or {section, quantity}
                                        -> 201 {holdId, expiresAt} | 409 {unavailable:[seatIds]}
POST /v1/holds/{holdId}/checkout        (Idempotency-Key) -> 202 {orderId, PENDING_PAYMENT}
GET  /v1/orders/{orderId}               PENDING | CONFIRMED | FAILED | EXPIRED
DELETE /v1/holds/{holdId}               release early
POST /webhooks/payments                 signed provider callback
  • Every write takes an Idempotency-Key, so a retry or double click makes one hold or one charge.
  • 409 names the failed seats so the UI can offer alternatives. Checkout returns 202 because payment may finish later by webhook.
  • admitToken is a short-lived signed proof that the caller passed the waiting room. Availability carries a version so late old responses are dropped.

Shard key = event_id. A hold touches several seats of one event, so it is a single-shard transaction with no distributed coordination. Weak spot: one hot event lands on one shard (see section 8).

6. Architecture and main flows

Flow A: browse

  1. CDN serves the static event page. No origin hit.
  2. /availability is cached 1 to 2 s at the CDN (max-age=2, stale-while-revalidate), so 200,000 polls/s become a handful of origin requests.
  3. Only when the user clicks a seat do we call the booking service.

Flow B: place a hold (the critical write)

Flow C: checkout and confirm

  1. Client posts checkout. Order is created as PENDING_PAYMENT. The hold gets a short grace extension (about 3 min, capped).
  2. Order service charges the provider using the order id as the idempotency key.
  3. On success (response or webhook), ONE database transaction moves seats HELD to SOLD, writes tickets, marks the order CONFIRMED, and writes an outbox row. A relay publishes it to Kafka.
  4. On decline: release the hold, order FAILED. If step 3 fails after a charge: refund.

7. Deep dives

7.1 Virtual waiting room

One line: a rate limiter in front of a bounded resource, with a visible queue as the overflow behaviour instead of an error page.
  • Join: counter INCR gives a ticket number, returned in a signed token. Wait: status reads one cached number ("admitted up to") and compares, with no per-user database work. 1M users polling every 8 s is 125,000 requests/s, so it must be very cheap. Admit: raise the counter by the rate each second; issue a signed admitToken (about 15 min).
  • Adapt: lower the rate if latency or errors rise; stop and tell everyone "sold out" at once when stock is gone. Estimated wait = (my number minus admitted number) / rate, shown as a range.
Fairness optionProsCons
Strict FIFOSimple, cheap, easy to explainRewards fast networks and bots; spike at exactly on-sale time
Random order within an early-join windowFair to slow connections; flattens the spikeFeels arbitrary; needs a window and a shuffle
No queue, just 429 errorsSimplestRetry storm; fastest retrier wins; awful experience
Verified-fan pre-registrationBest against bots; demand known earlyHeavy operations; only for the biggest events

Choice: random order in an early-join window for mega sales, plain FIFO otherwise. One verified account gets one place (token bound to account and device).

7.2 Preventing oversell

CorrectnessStrong (ACID)Strong (ACID)Strong on one node, weak across failover
Throughput on a hot eventLow, about 1,000 to 3,000/sMedium, about 5,000 to 10,000/sHigh, 50,000+/s

Throughput figures are order-of-magnitude for one well-tuned node, for comparison only.

UPDATE seats SET state='HELD', hold_id=:h, hold_expires_at=:exp, version=version+1
 WHERE event_id=:e AND seat_id=:s AND state='AVAILABLE';   -- 1 row = won, 0 = lost

Choice: Redis in front, conditional UPDATE behind, UNIQUE on tickets as the last net. For a normal event the UPDATE alone is enough (1,500 attempts/s is easy for one shard). For a hot event, Redis rejects about 60% of losers cheaply, so the DB sees about 600 conditional updates/s. A multi-seat hold succeeds only if rows updated equals seats requested. If Redis and DB disagree, the DB wins: delete the Redis key and tell the buyer. After a Redis restart, rebuild keys from the DB and send holds straight to the DB meanwhile.

Hold expiry (three layers)

  • Redis TTL: precise, free
  • Expiry predicate in the query: an expired hold never blocks a buyer
  • Sweeper job: tidies rows, emits SeatReleased. Not needed for correctness

Hot event tricks

  • Own shard, Redis and booking pool (a cell)
  • Split seats by section if needed
  • "Best available" mode spreads picks
  • Show seats in randomised order so no one clicks the same front row
Trap: payment succeeds at 9:59 and the hold expires at 10:00. The confirm transaction checks the hold is still valid. If the seat was lost, auto-refund and apologise. The grace period makes this rare.

7.3 Payment saga

OrderingResult
Reserve then charge (hold, charge, confirm)Seat is ours while money moves. Only compensations: release the seat, or refund on a rare race. Chosen.
Charge then reserveCan charge people for nothing and force many refunds.
  • Orchestrated saga: the order service owns the state machine (PENDING, PAID, CONFIRMED, FAILED, REFUNDED). One place that knows the story is easier to audit with money involved. Use events (Kafka) for after-confirmation steps.
  • Idempotency everywhere: charge key = order id; unique idempotency_key on orders.
  • Unknown outcome (timeout): leave PENDING; a reconciler asks the provider by order id. Never guess.
  • Webhook plus poll; verify signature; dedupe on event id. Outbox so a sold seat always gets its ticket event. Tight timeout, circuit breaker and own thread pool for the payment call.

7.4 Flash-sale variant (no seat identity)

10,000 sneakers or general admission: no seat map, so one hot counter. Load stock into Redis; an atomic Lua script decrements only if stock is enough; losers (990,000 of 1M) get "sold out" in microseconds without touching the DB. Winners go to Kafka, then order workers and payment. Failed or expired payment increments the counter back. A reconcile job checks counter = total minus sold minus active reservations. The DB keeps a conditional guard so sold never exceeds total: a counter bug can under-sell but not oversell. If one key is too hot (say 500,000 attempts/s), split into N bucket keys (for example 10 x 1,000) and sweep all buckets for the last units.

8. Scaling and bottlenecks

LayerBottleneckMitigation
Edge / CDN300,000 req/sStatic content and availability cached 1-2 s; static waiting page
Queue service25,000 joins/s, then 125,000 polls/sA couple of Redis ops per join; status reads one cached number; jittered polling or push; separate Redis
Booking tier1,500 holds/s, 150 orders/sStateless, admission capped; pre-scale for the known on-sale time, not on CPU
Inventory shardAll writes on one event's rowsRedis gate, conditional updates, short transactions, hot-event cell, section partitions
Payment providerRate limit, 250 charges/sAdmission caps it indirectly; back-pressure; fallback provider
After the saleEmail and tickets for 25,000 ordersAsync via Kafka, consumers scale alone
  • Capacity math: 1,500 attempts/s on one shard is about 30% load even without Redis. Without the waiting room it would be about 100x more, and the 200-connection pool would starve.
  • Sharding: directory service maps event to shard, so hot events are pinned by hand to dedicated shards. "My orders" needs a per-user table fed from Kafka (eventually consistent; the confirmation screen reads the primary).
  • Multi-region: one home region per event owns writes (extra 100 to 200 ms for far users). Browse is served near the user. DR by async replica; reconcile recent seconds against provider records.
  • Replicas serve non-critical reads; hold and confirm always use the primary.

Consistency split: seat transitions are linearizable on the event's primary, and we refuse holds if it is unreachable rather than risk two owners. Availability counts, "my orders", search and analytics are eventually consistent. Strong where a wrong answer costs money and trust, weak where it costs one extra click.

10. Things to say to impress

Say this:
  • "Average load is 3 tickets a second. The whole design is about the shape of the spike, and the real problem is contention on 50,000 rows, not data volume."
  • "The waiting room is a rate limiter in front of a bounded resource, with a user-visible queue as the overflow. Autoscaling cannot react in seconds, and the bottleneck (inventory rows, payment limit) does not scale by adding web servers."
  • "Fast gate, authoritative store. Redis rejects losers, the conditional UPDATE decides, and a UNIQUE constraint on (event_id, seat_id) makes a double ticket physically impossible."
  • "Stale reads are fine for the map and never for hold or confirm. Strong where wrong costs money, weak where it costs a click."
  • "Reserve then charge, with idempotency keys, an outbox, and a reconciler for unknown outcomes. We never guess."
  • "Bots: layered defences raise their cost; I cannot promise zero bots." Also mention a continuous audit job that alerts if any seat has more than one ticket, and a load test with a realistic arrival curve before the real day.
  • Name rejected alternatives: distributed locks (extra failure mode, no more correct than a conditional UPDATE), all-in-Redis (weaker durability), serializable everywhere (retries hurt throughput), event sourcing (extra read-model cost).
Traps: trusting Redis as the source of truth; GET then DECR (race makes stock negative); hold with no expiry; letting the booking API be called without an admit token; guessing the result of a timed-out charge.

11. Interview Q&A

How do you guarantee a seat is never sold twice?

I use several layers, with the database as the final judge. The hold is a conditional update, UPDATE ... WHERE state='AVAILABLE', and I only treat it as won when the number of rows changed equals the number of seats asked for. Moving to SOLD is also conditional on the hold id and state. Last, a unique constraint on tickets (event_id, seat_id) makes a duplicate impossible to insert. Redis in front just rejects losers cheaply, and if it loses data the database layers still protect us. I would also run an audit job that alerts if any seat ever has more than one ticket.

Why not just use SELECT FOR UPDATE?

It is correct, and fine for ordinary events. Under heavy contention, though, transactions queue behind the winner and each one holds a database connection while it waits. A single hot seat can exhaust the connection pool and stall unrelated work. Multi-seat holds can also deadlock when they lock rows in different orders. A conditional update gives the same atomic result in one statement, and losers fail at once. If I used row locks I would lock in sorted seat order, set a short lock timeout and keep transactions tiny.

Why a waiting room instead of just autoscaling?

Autoscaling takes minutes and the spike lasts seconds. Even unlimited servers would not help, because the bottleneck is contention on the same inventory rows and the payment provider's rate limit. Neither scales by adding web servers. The waiting room turns the stampede into a steady 500 users a second, which also gives fairness and a clear experience: a position and an estimated wait, not errors and refresh storms. The price is some complexity and a short delay, but the alternative is an outage at the most visible moment of the year.

How do you make the queue fair and stop bots jumping it?

Speed should not decide the order. For the biggest sales I randomise order among everyone who joined in a window around the start time. One verified account gets one place, because the signed token is tied to the account and device. The booking API rejects calls without a valid admit token, so bots cannot skip the queue. On top I add WAF bot scoring, a challenge at join time, per-account ticket limits and post-sale fraud review. I would say honestly that this raises the cost for bots but cannot remove them.

Is it acceptable to show stale seat availability?

Yes, on purpose. The map is only a hint; the hold step is the real judge. Serving it from the CDN and a Redis snapshot refreshed every second or so protects inventory from 200,000 reads a second. The cost is that sometimes a user clicks a seat that is already gone. We return a precise 409 naming the lost seats and show nearby alternatives. The hold, checkout and confirm path is never cached and always runs against the authoritative store.

What happens when a user abandons checkout?

The hold has a TTL of about 10 minutes. The Redis key expires on its own, the query treats a past-expiry hold as available, and a sweeper tidies the rows and publishes SeatReleased so caches and the waiting room learn about the free seats. The countdown the user sees comes from the server's expiry time, not the client clock. If they start paying near the deadline, checkout adds a short, capped grace period so a slow payment does not lose the seat. If a charge still succeeds for a lost seat, we refund automatically.

Payment succeeded but our service crashed before confirming the seat. What now?

The order sits in PENDING_PAYMENT with a stored idempotency key, and the provider has a record of the charge. On restart, or when the webhook arrives, the order service runs the confirm transaction, which moves the seat to SOLD and writes tickets and the outbox event in one step. A reconciliation worker also checks pending orders older than a minute and asks the provider for their status by order id, so nothing depends on a lost webhook. If the hold was lost meanwhile, we refund. Every step is idempotent and every unclear state is resolved by asking the source of truth.

How do you handle one hot event overloading a shard?

First, the waiting room already caps the load that arrives. Second, I pin the hot event to its own shard, Redis nodes and booking pool, a dedicated cell, so it cannot hurt other sales, and I provision before the known on-sale time. Third, the Redis gate absorbs rejections so the database sees mostly likely winners. If that is still not enough, partition the event's seats by section and steer buyers to single-section holds, or offer best-available so the server picks uncontended seats. In the flash-sale variant I split the hot counter into bucket keys.

Redis fails over and loses some hold keys. Can we oversell?

No, because Redis is a gate and not the authority. A lost key may let a second buyer pass the Redis check, but their conditional UPDATE in the database changes zero rows because the seat is already HELD or SOLD, so they get a 409. The cost is extra database load until Redis is rebuilt. During recovery I rebuild seat keys from the database (unexpired HELD and all SOLD) and route holds straight to the DB path, at a lower admission rate. The unique constraint on tickets is the final net.

How does the flash-sale variant differ from reserved seating?

There is no seat identity, so contention is on one counter rather than many rows. I preload stock into Redis and decrement with an atomic script that never goes below zero. Each of a million requests gets an answer in microseconds, and only winners go to Kafka for order creation and payment. Failed or expired payments add the unit back. Because Redis can drift from the database, a reconcile job repairs the counter and the DB keeps a conditional guard so sold can never exceed stock. If one key is too hot I split it into several bucket keys.

A user says they were charged twice. How do you prevent and handle it?

Prevention first: the client sends an idempotency key for checkout so double clicks collapse into one order, and the charge to the provider uses a key derived from the order id so a retry after a timeout cannot make a second charge. A unique constraint on the key backs this up. If it still happens, say through a provider bug, the reconciliation job compares our orders with the provider's settlements, spots the extra capture and refunds it. We detect through reconciliation as well as prevent, because no prevention is perfect.

Why orchestration and not choreography for checkout?

Checkout has few steps and involves money, so I want one place, the order service, that owns the state machine (PENDING, PAID, CONFIRMED, FAILED, REFUNDED) and decides the next step. That is easier to reason about, test and audit than events bouncing between services. Choreography is fine after confirmation, for ticket email, search indexing and analytics, and that is where Kafka comes in. The outbox makes sure the confirmed event is never lost.

Hold success rate suddenly drops during a sale. What do you check?

I look at the dials in order. First, is the inventory primary healthy: latency, connection pool, failover? Second, is Redis healthy, and is its state drifting from the DB (a spike in "Redis said free, DB said no")? Third, did the admission rate outrun the booking tier, so queue depth and admit rate need slowing? Fourth, the payment decline and timeout rate, since stuck checkouts keep holds alive. The runbook levers are lowering the admission rate, switching to the DB-only hold path, and enlarging the hold grace. Users stay in the queue throughout.
