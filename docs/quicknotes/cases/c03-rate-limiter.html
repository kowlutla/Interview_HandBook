Case Sheet: Design a Rate Limiter

One-page revision of Handbook Case Study 3. A rate limiter answers "may this caller go ahead right now?" in well under a millisecond, for every request.

ProblemRequirementsEstimationAPIDataArchitectureDeep divesScalingFailuresImpressQ&ALinks

1. Problem in 3 lines

One line: a rate limiter caps how many requests a caller may make in a period, to protect the system (abuse), enforce what a customer paid for (plans), and keep one tenant from starving the others (fairness).
  • Say out loud that it is three things: a decision function (the algorithm), a state store (counters shared by many machines) and a control plane (rules, plans, overrides). Weak answers describe only the first.
  • It sits on the hot path of every request, so it must be fast, and it must never become the reason the API is down.

Clarifying questions to ask (and the answer to assume)

AskAssume
Library in one service or shared platform?Shared platform: used by an API gateway and internal services. One team owns it, many teams set rules.
Who is limited?User, API key, tenant (an organization owning many users and keys), and anonymous callers by IP. One request may be checked against several at once.
What is limited?Requests per time window, with optional weighted cost (an expensive search costs 5). Plus daily or monthly quotas.
Hard or soft limits?Hard for abuse protection. Soft (off by a few percent) is fine for commercial limits.
Scale?200,000 requests per second on average, peak 600,000. About 50 million active keys in an hour.
Latency?Under 1 ms at p99 added to a request.
Regions?Several. Global limits must exist but may be approximate.
If the limiter is down?Product decision. Default: fail open or degrade to local limits; fail closed for security-critical endpoints.
Should clients see their state?Yes: remaining budget and how long to wait on a rejection.

2. Requirements

Functional

  • Check a request against one or more rules; return allow or deny, remaining budget, retry delay
  • Rules chosen by endpoint, method, identity type, plan tier
  • Weighted cost per request
  • Change rules at runtime, live in seconds, with rollback and per-customer overrides
  • Over-limit gives HTTP 429 plus standard headers
  • Daily and monthly quotas with usage reporting
  • Shadow (dry-run) mode: log what would be blocked, block nothing

Non-functional

  • Latency under 1 ms p99 per check; local checks under 100 microseconds
  • Availability above the services it protects (about 99.99 percent)
  • Accuracy: a few percent over the rate at most for hard rules
  • Scale: 600,000 checks per second, 50 million live keys
  • Concurrent nodes must not bypass the limit through races
  • Every decision observable, every rule change auditable

Out of scope

  • Network-level DDoS (edge, CDN, scrubbing providers)
  • Bot-detection machine learning
  • Billing and invoicing (we only emit usage)
  • Concurrency limits on in-flight work (related, different mechanism; see Q&A)

Keys get a time-to-live (TTL, an automatic expiry) of twice the full-refill time, so idle keys vanish on their own: a key idle for a full refill holds no information we need.

4. API

// data plane: library call, or gRPC when a remote limiter is used
CheckRequest  { request_id, tenant_id, principal_id, client_ip, resource, cost=1 }
CheckResponse { allowed, limited_by, limit, remaining, reset_after_ms, retry_after_ms }

// control plane
PUT  /v1/rules/{rule_id}            { match, key_by, algorithm, limit, window, burst, mode: enforce|shadow, fail_policy }
GET  /v1/rules?resource=...         list with versions
POST /v1/rules/{rule_id}/rollback   { to_version }
PUT  /v1/overrides/{tenant_id}      { rule_id, limit, expires_at }
GET  /v1/usage/{tenant_id}?period=  quota consumption
  • The engine checks all matching rules and returns the numbers of the tightest one, since that is what the client must respect.
  • Rules are versioned and immutable: an update creates version N+1. That gives rollback, audit and "node X runs version 412".
  • A denial is 429 Too Many Requests with Retry-After, RateLimit-Limit/Remaining/Reset (or older X-RateLimit-*; keep whichever the API already uses). Send the headers on successful responses too.

The text in braces is the Redis Cluster hash tag: only that part decides the shard. Tagging by tenant keeps one tenant's keys together (handy for multi-key scripts, dangerous for a huge tenant). For per-principal rules, tag by the principal so a big tenant's keys spread over all shards.

6. Architecture and request flow

Start simple: one server with an in-memory map of buckets works until a second server appears; then a limit of 100 per second becomes 100 per second per server and changes when autoscaling adds nodes. We need shared state and a decision on where the check runs.

PlacementGood forWeak because
Client-sidePolite back-off after a 429Never trusted
Edge / CDN / WAFPer-IP caps, anti-flood, login protection; cheapest rejectionKnows IP and headers, not the user
API gatewayPer-key, per-tenant, per-plan limits (primary point)Critical path; cannot see internal fan-out
Sidecar / meshProtecting internal services from internal callersExtra hop, rules scattered
In-service libraryPer-operation cost, protecting a DB or third partyOne client per language

Decision: one limiter engine as a library plus shared state, embedded in the gateway (and in services where needed). No extra network hop in the data path; the only remote call is to Redis, and only when local state cannot decide. Keep a thin gRPC front for polyglot internal callers.

Main flow: check a request

  1. Request arrives at a gateway node with credentials (floods by IP were already cut at the edge).
  2. Cheap authentication resolves the API key to tenant and plan (cached). The limiter runs after that, but before expensive work.
  3. The engine matches rules from the snapshot (for example per-key 100/s and per-tenant 1,000/s) and builds the keys.
  4. If a local lease has enough tokens, it decides in microseconds.
  5. Otherwise it runs the atomic Lua script on the Redis shard that owns the key (one round trip).
  6. Redis refills, compares and subtracts in one indivisible step and returns {allowed, remaining, retry_ms}.
  7. Deny if any rule denies; on a deny, refund tokens already taken from the other rules.
  8. Allowed: forward with rate-limit headers. Denied: 429 with Retry-After; the backend is never touched.

Flow: update a rule

  1. Operator calls PUT; control plane validates (sane limits, no match-everything rule with limit 0), writes version N+1 in one transaction, records who.
  2. Config service compiles a snapshot and pushes it; nodes also poll every 30 seconds so a lost push heals.
  3. Node validates (checksum, schema, rule count not zero), builds the new index aside, then swaps one pointer. In-flight checks finish on the old one. No lock on the read path.

7. Deep dives

A. Atomic counters and races

The race: read counter, decide, write back as separate commands. Two nodes both read "1 token left", both allow, both write 0: limit 1, two passed. With 100 gateways and a hot key this is the normal case.

OptionProsConsVerdict
Single command (INCR + EXPIRE, fixed window)FastestOnly counters; INCR then EXPIRE is two commands, so a crash between leaves a key that never expires; 2x boundary burstSimple fixed windows only
WATCH / MULTI / EXEC, retryNo scriptingRetries explode on hot keys; extra round tripsNo
Distributed lock per keyFamiliar2 to 3 round trips, lock expiry hazards; too slowNo
Lua scriptOne round trip, any algorithm, atomicScript blocks the shard, so keep it tiny and O(1)Chosen
  • Use Redis's own clock (TIME) inside the script, not the gateway's: gateway clocks drift, so refill could go backward or double-credit. Clamp negative elapsed time to zero.
  • Load the script once, call by hash (EVALSHA); reload on "script not found" after a failover.
  • Refresh the TTL every call, set to twice the refill time.
  • Multiple rules per request: checking one after another can take a token from rule 1, then be denied by rule 2. Choice: check the strictest rule first, and refund earlier rules on a multi-rule deny. The leak is a few tokens on a request that was rejected anyway. (Alternative: same hash tag and one multi-key script: atomic but concentrates load.)

B. Local plus global hybrid (leases)

A remote check per request costs 0.3 to 1 ms and loads Redis with 1.2M ops per second. Most traffic is concentrated in few keys, and those do not need an exact answer on every call. So the node asks Redis for a lease: "give me up to L tokens for this key". Redis subtracts them from the global bucket and returns the amount granted; the node then serves the next L requests locally with no network.

ApproachLatencyAccuracyRedis loadVerdict
Always global0.3 to 1 msExactHighestHard rules, low-rate keys
Purely local (limit ÷ nodes)MicrosecondsPoor: load skew, node count changes itNoneEmergency fallback only
Lease hybridMicrosecondsWithin a few percentAbout 10x lower on hot keysChosen for commercial and hot keys
Periodic sync of deltasMicrosecondsOvershoot up to nodes × rate × intervalLowVery high keys; bigger overshoot
Gossip between nodesMicrosecondsEventually consistentNoneNiche; hard to bound
  • Why it is defensible: the global bucket is still the single record of what was granted. A lost node can only strand tokens or, via expiry timing, slightly over-admit. It cannot multiply the limit by node count.
  • Sizing: tenant limit 1,000 per second on 20 nodes is 50 per node per second. Leases of 10 tokens mean about 5 Redis calls per node per second instead of 50: the 10x cut.
  • Error bound: tokens in unexpired leases, with a 100 ms expiry about 10 percent of one second's budget at the worst moment. Hard security rule: L = 1 (always global). Commercial: 5 to 10 percent is fine. Low-rate keys lease nothing.

Say this: "Rules are immutable versions pushed to nodes, validated, and swapped by one pointer. Nodes keep the last good snapshot, so the control plane is never on the request path."

Identity, hot keys and abuse

  • Layer the limits: small per-IP limit before auth, per-key after, per-tenant ceiling over all keys, global limit per backend. Each layer stops a different failure (floods, one script, key farming, everything stacking up).
  • Real client IP: use the address written by the trusted edge (right-most untrusted entry of X-Forwarded-For), never a header the client can fake. For IPv6 key on the /64 prefix.
  • Hot key (one tenant at 50,000 per second hits one shard): first leases (about 10x fewer calls); then split into S sub-buckets with limit/S each and retry once on another; then a dedicated shard. Replica reads do not help because a check writes.
  • IP rotation: per-IP limits fail. Add limits on things costly to rotate (account, API key, device, session), aggregates by /24 or network operator, a global per-endpoint limit, progressive friction (CAPTCHA, delay) instead of hard blocks, and higher token cost for expensive endpoints.
  • Do not let the limiter be an attack surface: cap key length; unknown keys share an unauthenticated or IP bucket instead of creating per-key state before auth succeeds.
Trap: IP-only limits punish shared networks (a carrier NAT with 100,000 users) and fail against rotation. Always pair IP limits with identity-based ones and keep IP thresholds generous on shared endpoints.

8. Scaling and bottlenecks

  • First bottleneck is operations per second on Redis, not memory. Leases cut it about 10x; keep 16 primaries for spikes, skew and failover.
  • Sharding: Redis Cluster has 16,384 hash slots; each key lives on exactly one primary, so every node reaches the same shard, and that single home is what makes the atomic script enough for correctness. Add primaries and migrate slots online. Not chosen: a proxy tier (extra hop) or a custom state service (Redis already gives TTL, scripting, replication).
  • Quotas versus rate limits: a rate limit answers "how fast?" (seconds to minutes, protective, ephemeral). A quota answers "how much in total?" (day or month, commercial, durable). Quota usage streams through Kafka to a durable aggregate with event ids so replays are idempotent; Redis is rebuilt from it if lost. The period sits in the key name (quota:acme:2026-11), so there is no midnight reset job and old keys expire by TTL.

Plans are data (bundles of limits), not code. Oversubscription is normal (sum of tenant ceilings may exceed capacity), so a global per-backend limit sits underneath.

Multi-region

A cross-region round trip is 50 to 200 ms, far over the 1 ms budget, so the request path never calls another region.

ApproachAccuracyLatencyFailure behaviour
One global RedisExactTerrible for remote regionsOne region outage hurts all
Regional budgets + background rebalanceApproximate (rebalance interval, a few seconds)LocalRegions independent; a partition keeps the last share
Replicated mergeable countersEventually exact; overshoot during lagLocalConverges after partitions; more machinery
Home region per tenantExactFast only at homeGood for regional tenants, poor for global ones

Choice: split each global limit into regional shares by recent demand (with a minimum share per region), rebalance every few seconds. Example: limit 100/s split 60 / 30 / 10. Per-IP and per-key limits are naturally regional and need no coordination. Worst overshoot equals the demand shift in one rebalance interval.

Latency budget (1000 microseconds p99)

Budget: auth id 50 + rule match 20 + local state 30 = about 100 microseconds when a lease hits (about 90 percent of checks). On a lease miss add a Redis round trip of about 400 to 500 microseconds, leaving 200 to 300 headroom. Hard Redis timeout 5 ms: a timeout counts as a failure and the fail policy decides. Use pooled connections, a preloaded script, O(1) script, same-zone shards.

10. Things to say to impress (senior / lead)

Say: "A rate limiter is a decision function, a state store and a control plane, and I will design all three."
Say: "The check must be one atomic step on the single shard that owns the key, using that server's clock. I use a Lua script, not read-then-write, WATCH retries or locks."
Say: "The latency budget forces a hybrid: leases keep most decisions in process and cut Redis calls about 10x. The global bucket stays the source of truth, so error is bounded by unexpired leases."
Say: "Fail open or degrade to local limits by default, fail closed for login and paid sends, and I alert on fallback so we know when we are unprotected."
Say: "Multi-region uses regional budgets rebalanced in the background. I never make a cross-region call per request."
  • Separate rate limits from quotas (billing needs durable, idempotent usage events).
  • Mention shadow mode, canary and rollback for rules, and that the limit is passed per call so changing it never resets buckets.
  • Note cheap 429s, Retry-After, client back-off with jitter, and metrics dimensioned by rule id (not by raw key).
  • Mention the multi-rule token leak and the refund, and the hot-tenant sub-bucket split. Naming small problems shows you saw them.
  • Evolution: phase 1 gateway plugin plus one Redis plus static rules; phase 2 versioned rules and cluster; phase 3 leases and quotas; phase 4 multi-region and abuse signals. At 10x scale: bigger leases, a limiter tier per zone, asynchronous enforcement for giant keys, cells for the largest tenants.

11. Interview Q&A

Why embed the limiter in the gateway as a library instead of calling a separate limiter service?

A separate service adds a network hop to every request, typically 0.3 to 1 ms, and a second thing that can fail. That alone can use the whole sub-millisecond budget. A library decides most requests in process from local state and the rule snapshot, and talks to Redis only when it must. The cost is that every language needs the library, so for polyglot internal callers I would still offer a thin gRPC front. The shared state is the same in both designs, so correctness does not depend on this choice; only latency, deployment and ownership do.

Two nodes check the same key at the same moment with one token left. How do you make sure only one passes?

The read, compare and write must be one atomic step on the node that owns the key. I run a Lua script in Redis. Redis runs commands and scripts one at a time, so nothing interleaves: the first call takes the last token and the second sees none. In a sharded cluster the key lives on exactly one primary, so all gateways funnel to the same serialization point. Optimistic WATCH with retry or a distributed lock also work but cost extra round trips and get worse under contention on a hot key.

Redis goes down. What does the gateway do?

It applies the rule's fail policy with a bounded timeout, about 5 ms, so it never waits forever. The default is to degrade to conservative local limits: the rule's limit divided by the expected node count, with a safety margin. That keeps flood protection and keeps the API up. For login attempts or paid SMS sends I fail closed. A circuit breaker stops calling Redis after repeated failures and probes now and then, with jittered retries so recovery is not a stampede. I alert whenever fallback is active, because running without global limits silently defeats the purpose.

How do you avoid a Redis round trip per request and still stay accurate?

Use leases. A node takes a block of tokens from the global bucket and spends it locally, calling Redis once per block. The global bucket stays the single record of what was granted, so the total cannot exceed the limit by more than the tokens in unexpired leases. Lease size and expiry set the accuracy against load tradeoff: large for hot commercial keys, one token (always global) for hard security limits. Example: a limit of 1,000 per second across 20 nodes with leases of 10 tokens drops Redis calls for that key from about 1,000 to about 100 per second.

How do rule changes reach hundreds of gateways quickly and safely?

Rules are immutable versions in a database. A config service compiles a snapshot and pushes it to nodes, which also poll every 30 seconds so a lost push heals. A node validates the snapshot (checksum, schema, rule count not zero), builds it aside and swaps one reference, so in-flight checks are untouched. It also saves the snapshot to local disk so a restart during a control-plane outage still has rules. New rules begin in shadow mode and roll out by canary; rollback is just publishing the previous version. Because the limit is passed to the script on every call, a change does not reset buckets to full.

An attacker rotates through 100,000 IP addresses. How do you still protect the service?

Per-IP limits cannot stop that, so I add layers keyed by things that are costly to rotate: authenticated account or API key, device or session token, and per-tenant ceilings. I add aggregate limits by subnet or network operator and a global per-endpoint limit that protects the backend whatever the source. For suspicious traffic I use progressive friction (CAPTCHA, proof of work, delay) rather than hard blocks that hurt shared NATs. Expensive endpoints cost more tokens, so volume of cheap calls cannot be turned into expensive work. Volumetric floods are pushed to the CDN or edge provider.

One huge tenant sends half the traffic on a single key. What do you do?

One key maps to one Redis shard, so that shard becomes the hot spot even when the cluster is idle. First I rely on leases, which cut calls to that shard about 10x and are usually enough. If not, I split the key into several sub-buckets, each with a fraction of the limit, spread calls over them, and retry once on another sub-bucket when one is empty to smooth the accuracy loss. For the biggest tenants I would give a dedicated shard or cell. I would also check that the limit is not keyed by a low-cardinality field that funnels unrelated callers into one key.

What is the difference between a rate limit and a quota? Do they share infrastructure?

A rate limit bounds speed over short windows to protect the system, and is ephemeral and approximate. A quota bounds total use over a billing period and has commercial and audit meaning. They can share the check path and the Redis cluster. Quotas additionally stream usage events to a durable store with idempotent event ids, so the billing record survives a Redis loss, and the period is part of the key name so it rolls over with no reset job. Exceeding a rate limit means "try again in a second"; exceeding a quota means "wait for the reset or upgrade".

How do you enforce a global limit across regions without adding 100 ms per request?

Never call another region on the request path. Split the global limit into regional budgets, each enforced against the local Redis, and run a background reconciler that every few seconds moves budget toward regions with demand while keeping a minimum share everywhere. The error is bounded by how much demand can shift in one rebalance interval. If a tenant truly needs a hard global guarantee, route its checks to a home region and accept the latency for remote users, or use replicated mergeable counters that converge eventually and tolerate a brief overshoot.

Why use Redis's clock inside the script rather than the gateway's?

Gateway clocks drift and disagree by milliseconds or more. If each node supplied its own timestamp, the refill calculation could move backward or credit tokens twice. The time from the primary that owns the key is one reference per key, so refill stays consistent whichever node calls. The tradeoff is dependence on that server's clock; after a failover the new primary's clock may differ slightly, so the script clamps negative elapsed time to zero.

How do rate limiting, load shedding and concurrency limits differ?

A rate limit is per caller and about how fast requests arrive. Load shedding is about the system's own health: when overloaded it rejects some requests whoever sent them, usually with 503, and protects the critical ones. A concurrency limit caps requests in flight, which is the better guard when slow requests pile up even though the arrival rate is modest. A full defence uses all three: rate limits for fairness and abuse, concurrency limits per dependency to avoid queue build-up, and shedding as the last resort.

Production incident: the deny ratio on a rule that normally denies drops to zero. What do you check?

A deny ratio of zero on a busy rule means the rule is not being applied or the limiter is failing open. I check the fallback-active metric and the Redis error and timeout rate first, then the circuit breaker state. Next I look at the snapshot version and age per node: a bad or stale snapshot, or a rule that flipped to shadow mode, would do this. I also look at whether a recent rule publish changed the match. If it is fail-open, I restore Redis or tighten local fallback limits now; if it is a rule problem, I roll back to the previous version, which is a single publish.

Production incident: a rule change blocks many legitimate customers. How do you respond?

I roll back first, by publishing the previous version, which reaches nodes in about a second by push and within 30 seconds by poll at worst. Then I confirm from the snapshot version on decision events that all nodes returned to the old rules. After that I find out why it passed: validation should reject match-everything rules or tiny limits, and the rule should have gone through shadow mode and a canary first. I add the missing check, and I review the audit log to see who changed what and why.
