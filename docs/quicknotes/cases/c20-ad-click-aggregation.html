Design Ad Click Aggregation

Count a billion ad clicks a day per ad per minute, drop duplicates and bots, handle late events, and make the numbers exact enough to bill.

1 Problem2 Requirements3 Estimation4 API5 Data6 Architecture7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines Handbook case

One line: when a user clicks an ad, we record it, forward the user to the advertiser, and count clicks per ad per minute so advertisers can watch campaigns live and be billed correctly.
  • Advertisers pay per click, so the count is literally money. Missing a click loses revenue; counting one twice overcharges a customer.
  • Key idea: write every click to a durable log first, count in a stream job by event time (when the click happened), and fix the numbers later with a slower batch recount from the raw archive.
  • The user never waits for counting. The click endpoint only logs the event and sends a redirect.

Clarifying questions to ask (and the answers we assume):

QuestionAssumed answer
How many clicks per day?1 billion per day, about 11.6k per second average, 50k per second at peak.
Is it used for billing?Yes. Billed numbers must be exact and auditable. The live dashboard may be slightly low, then converge.
Granularity?Clicks per ad per minute. Hour and day totals are rollups of that.
Freshness?Dashboard within about 30 seconds of the minute closing. Billing can wait hours for the final number.
How late can a click arrive?Up to 15 minutes into the live path. Later ones are fixed by the batch job.
Count invalid clicks?No. Duplicates and bots are not billed, but raw clicks are kept so a decision can be redone.
Queries?Time series per ad, totals per advertiser, top K ads in the last N minutes.
Attribution (purchases after a click)?Out of scope. Only counting clicks.

2. Requirements

Functional

  • Ingest clicks with almost no added user latency.
  • Filter duplicate clicks and invalid (bot, abusive) clicks.
  • Aggregate per ad per minute, with hour and day rollups.
  • Query time series and top K ads.
  • Correct history after late events or fraud decisions.
  • Replay any past period from the raw log.

Non-functional

  • Accuracy first: no click lost, none counted twice (exactness wins for billing; speed wins for the dashboard).
  • 50k per second at peak, survive 3x bursts by buffering, not dropping.
  • Redirect adds under 10 ms p99 of our time. Query p99 under 500 ms.
  • Click endpoint highly available; dashboard may degrade.
  • Durable after "recorded": survives one machine or zone failure.
  • Any stage can crash and restart without changing final counts.

Out of scope

  • Ad serving and auctions.
  • Budget pacing (it consumes our output).
  • Conversion attribution.
  • Invoice generation.
  • The fraud ML model itself (we call it as a service that returns a score).

4. API

GET /c?ad=4711&cid=7f3a...e1&ts=1731800123456&sig=9be0...
  -> 302 Location: https://advertiser.example/landing   (target looked up server-side)

GET /v1/ads/{adId}/clicks?from=...&to=...&granularity=minute
  -> { "points": [ { "t": "10:00Z", "clicks": 12, "status": "provisional" } ],
       "watermark": "10:58Z" }
GET /v1/advertisers/{id}/clicks?from=...&to=...&groupBy=ad&granularity=hour
GET /v1/advertisers/{id}/top-ads?window=15m&k=10
  • The click id (cid) is made when the ad is shown. It is the dedup key: a double-click or retry carries the same id.
  • An HMAC signature (a keyed hash only we can make) over ad and click id stops forged clicks at the edge.
  • Each point says provisional (may still change) or final (confirmed by batch), and the response carries the watermark, so the chart can show "complete up to 10:58".

Why not key-value or a time-series DB? A key-value store (Cassandra, DynamoDB) is great for one ad's time series but makes "all ads of an advertiser grouped" costly. A classic time-series database struggles with tens of millions of series (ads). Columnar OLAP does both.

First design that fails: UPDATE ... SET clicks = clicks + 1 per click on one database. It dies on hot rows (locks), couples users to the database, double counts on retry (increments are not idempotent), and keeps no raw history. Each failure maps to a fix in the real design.

6. Architecture and main flow

Main flow of one click:

  1. Browser calls /c?ad&cid&sig. The click tier checks the signature.
  2. It appends the event to Kafka and waits for the all-replicas ack (acks=all). If Kafka is down it writes to a local disk spool and drains later.
  3. It returns a 302 redirect. Steps 1 to 3 take a few milliseconds. The user never waits for counting.
  4. The filter job reads the batch, drops duplicates by click id, scores fraud, and writes survivors to clicks.valid. Rejects go to clicks.rejected with a reason, never silently deleted.
  5. The aggregate job counts per (ad, event-time minute) and upserts to OLAP and Redis, first as provisional every 10 seconds, then at window close.
  6. Every raw event is also copied to the archive. An hourly batch job recounts and writes the final revision.

7. Deep dives

7.1 Event time, windows and late data

The crux: count by when the click happened (event time), not when we saw it. After a 10 minute outage, processing-time counting would show a fake spike and a fake gap. A watermark tells the job when a minute is complete enough to emit.
OptionBehaviourCost
Drop late eventsDiscard them.Undercount. Not acceptable for billing.
Allowed latenessKeep window state 15 more minutes; update and re-emit.More state; sink must accept updates (upsert handles it).
Side output plus batchVery late events go to clicks.late; batch includes them.Live number stays low until batch fixes it.

Choice: allowed lateness 15 minutes plus the archive batch for everything later.

  • Windows: store only tumbling (fixed, non-overlapping) 1 minute counts. A sliding "last 5 minutes" is the sum of 5 buckets at read time, so raw events are touched once.
  • Clock trap: one client clock far in the future drags the watermark ahead and makes good events look late. Clamp event time to ingest time plus a few minutes.
  • Idle partition trap: the job watermark is the minimum over partitions, so one silent partition stalls everything. Use an idle timeout (about 30 s) to ignore quiet partitions.

7.2 Dedup and fraud filtering

Dedup optionProsCons
A. Redis SETNX per clickSimple, shared.50k network calls per second; check and downstream write are not atomic; 180M keys to hold.
B. Keyed state in the stream job (RocksDB)Local lookup; snapshotted together with offsets, so consistent with exactly-once.State grows with the horizon; moves on rescale.
C. Bloom filter aloneTiny memory.False positives would drop real paid clicks.
D. Unique key in the sinkStrongest guarantee.Billions of click-id rows in OLAP; wasteful.

Choice: B, with an optional Bloom prefilter in front (a "maybe seen" always falls through to the exact check). Horizon is 1 hour (about 7 GB across tasks). Longer-range duplicates are caught by the batch job with a global distinct over the hour and its neighbours. Pattern: approximate or windowed in the stream, exact in the batch.

Fraud is layered, cheap checks first: (1) edge: signature, ad exists, bot user agents, blocked IP ranges; (2) stateful rate rules in keyed state: too many clicks per device per minute, same IP clicking one ad too often, click within 300 ms of the impression, publisher click-through ten times the norm; (3) ML model, batched with a timeout, and on timeout the click passes as unscored for the batch to score; (4) offline graph analysis that yields lists of invalid clicks applied in reconciliation.

Trap: a fraud rule that over-blocks (a company network sharing one IP among 5,000 real users) silently undercharges. That is why every rejection is stored with a reason and the rule version, so you can fix the rule and replay.

7.3 Exactly-once counting

The crux: no network gives exactly-once delivery, but we can make the effect happen once by combining at-least-once delivery with idempotent steps (safe to repeat) at every hop.
BoundaryRiskFix
Producer to KafkaTimeout, retry, two copies.Idempotent producer (broker dedups by producer id and sequence). Click-id dedup catches the rest.
Kafka to job to KafkaCrash after processing, before committing offsets.Checkpoint: snapshot state and input offsets as one unit; on restart restore both and rewind. Output via two-phase commit tied to the checkpoint.
Job to OLAPRestart replays recent window results.Idempotent upsert of the full count keyed by (ad, minute), never "add 3".
  • Full value, not a delta: "+3" applied twice gives +6; "count = 11, revision 7" applied twice gives 11.
  • Revision number fences zombies: the store keeps the highest revision, so a stale task cannot overwrite a newer value.
  • Checkpoint trade-off: 30 s interval means a crash replays at most about 30 s (about 1.5M events at peak). A transactional output only advances at checkpoint boundaries, so the dashboard path uses the idempotent sink instead and writes provisional values immediately.

7.4 Hot ads and reconciliation

Hot key choiceGoodBad
Partition by ad id onlySimple.One task gets 5% of traffic; a bot attack of 40k per second saturates it.
Salt every ad with S = 8Even load.8x state and output for the long tail for no gain.
Salt only detected heavy hitters (above about 500 per second; S up to 64 in an attack)Cost only where needed. Correct for any S because stage 2 always sums.Needs a sketch (Count-Min or Space-Saving) to detect them.

Add local pre-aggregation: each stage 1 task keeps a map of (ad, minute) counts and flushes every second, so a hot ad sends at most one record per task per second.

Reconciliation (Lambda style). The stream is fast and roughly right; the batch is slow and exactly right. Why the stream alone fails for billing: very late clicks, a dedup horizon of only 1 hour, fraud found later with hindsight, code bugs, rare state corruption. The hourly batch job (starting H plus 30 min):

  1. Read archive files for H-1, H and H+1 (late clicks and duplicates can sit in neighbours).
  2. Deduplicate by click id across that range.
  3. Apply the full fraud rules and the latest offline invalid lists.
  4. Group by (ad, event-time minute) and count.
  5. Compare with the stream numbers and record the gap per advertiser.
  6. Write revision max plus 1 with status final; billing reads only finalized hours.
AspectLambda (stream + batch)Kappa (stream only, replay)
CodeTwo implementations that can drift.One implementation.
ExactnessBatch is an independent check.Depends entirely on the stream job and log.
Late and fraud fixesNatural, with hindsight.Needs unlimited lateness or replays.
Audit storyStrong: recount from immutable files.Weaker: same code run twice.

Choice: Lambda for money, with one shared library of parsing, dedup-key and fraud-rule code and a shared golden test set to limit drift. If pushed to Kappa: fine when one engine runs both modes (the same SQL job in batch mode over the archive). The batch is a pure function of (archive files, rule version), so it can be rerun; an audit table stores rule version, input files and checksum per advertiser-hour. Adjustments after billing go through the ledger as credit entries, never by editing history.

Top-K: a Redis sorted set per minute (ad as member, cumulative count as score, set with ZADD so it is idempotent). The query unions the last N minute sets and reads the top 10. Each minute set is trimmed to the top 10,000 and the merged answer is cached 5 to 10 seconds. It is approximate only in a contrived edge case; batch gives the exact board.

OLAP storeShard by advertiser (hash of advertiser and ad if some are huge); replicas for reads.Many small writes: batch upserts.
Archive and batchParallel by hour and click-id hash.Peak hour dedup shuffle: about 40M events x 200 B = 8 GB, small.
  • Range choice at query time: up to 6 hours use minute rows, up to 30 days hour rollups, beyond that day rollups (30 days of minutes is 43,200 points per ad, more than a screen shows). A 10 to 30 s cache on (advertiser, range) absorbs dashboard refreshes.
  • Back-pressure: if counting slows, Kafka holds the backlog. 10 MB per second for a 1 hour outage is only 36 GB. Nothing upstream blocks, and the watermark makes the delay visible.
  • Multi-region: click tier in every region writing to a regional Kafka; mirror raw topics to one central region for a single place to dedup and bill (10 MB per second cross-region is trivial). Recovery in another region from archive plus latest checkpoint: minutes to tens of minutes, recovery point of seconds.
  • At 10x (500k per second): 128 to 256 partitions, dedup horizon cut to 15 minutes (state would be about 70 GB), dynamic salting mandatory, tiered OLAP storage, batch every 15 minutes.

10. Things to say to impress

Say this:
  • "Dropping a click is a financial decision with two error directions. Fraud let through overcharges the advertiser; a real click blocked undercharges us. We measure both and tune toward the advertiser."
  • "I make every write an idempotent upsert of a full, revisioned value. Replays, retries and zombies then cannot change the answer."
  • "The API labels every number provisional or final and returns the watermark, so we serve fast and exact numbers without lying about which is which."
  • "Stream is approximate or windowed, batch is exact. The gap between them is my best correctness alarm."
  • "Because billing reads only finalized hours and corrections go through credit entries, every billed number traces to input files and a rule version."
  • "I would run a synthetic canary: a test ad with a known click count per minute, asserted end to end on dashboard and batch output."
  • "I phase it: MVP with Kafka, one stream job and an idempotent upsert; then lateness and batch reconciliation; then salting, top-K and rule-based fraud; then model scoring and multi-region."
Trap: do not offer an approximate structure (HyperLogLog, Count-Min) for the billed figure. They are fine for unique reach and for hot-key detection, not for exact money.

Privacy and security notes: signed URLs with a timestamp limit replay; the redirect target is looked up server-side to avoid an open redirect; IP and device id are hashed or deleted after about 90 days while aggregates stay; every query is scoped to the advertiser in the verified token.

11. Q&A: follow-up questions

Why put Kafka between the click tier and the counting?

The log makes the system durable, decoupled and replayable. The click tier only has to save the event and redirect, which takes milliseconds, so a slow or crashed counting job never hurts users or loses revenue. Kafka keeps events for days, so after a bug we can replay, add new readers such as fraud analysis or the archive without touching the click tier, and rebuild state after a failure. Counting inside the click tier would lose counts on a crash, could not dedup across servers, and would keep no raw data for audits.

How do you make sure a click is counted exactly once?

I use at-least-once delivery plus idempotent effects at each hop. The producer is idempotent, so retries do not create copies in Kafka. The stream job dedups by click id in keyed state that is snapshotted together with the input offsets, so a crash restores one consistent cut and replays only the tail. The sink write is an upsert of the full revisioned count for (ad, minute), so replays overwrite with identical values instead of adding. Finally the hourly batch recount from the immutable archive, with global dedup, catches anything the stream missed.

What is the difference between event time and processing time, and which do you use?

Event time is when the click happened; processing time is when our system handled it. After outages, retries or mobile phones that were offline, the two differ a lot, so counting by processing time would push clicks into the wrong minute and draw a fake spike. Advertisers and billing care about when the click happened, so I use event time. That needs a watermark to decide when a minute is complete and a lateness policy for stragglers. I also clamp timestamps near ingest time so one bad client clock cannot damage the watermark.

How do you handle late events?

There are three tiers. Events inside the watermark delay of 2 minutes are just part of the window. Events up to 15 minutes late use allowed lateness: the window state is kept, the late click updates the count, and a new revision of the row is upserted. Anything later goes to a side topic and the hourly batch job counts it from the archive by event time, then marks the row final. The dashboard shows provisional or final status and the watermark, so people know which numbers can still move.

One ad gets 5% of all clicks. How do you avoid a hot partition?

Aggregate in two stages. Stage 1 keys by (ad id, salt) where salt is a hash of the click id modulo S, so the hot ad spreads over S tasks, and each task pre-aggregates locally and flushes once per second. Stage 2 sums the S partial counts per ad and minute, which is a tiny amount of data. It is exact because counts are additive. To avoid paying the cost for every ad, a sketch detects heavy hitters and only those get salted. Ingestion is already even because the raw topic is keyed by click id.

Why keep a batch job if the stream already counts exactly once?

The stream's exactly-once is limited by what it knows at that moment. It has a bounded dedup horizon (1 hour), a bounded lateness window (15 minutes) and only quick fraud rules, while billing needs hindsight: very late clicks, duplicates hours apart, and fraud found after analysis. The batch also gives an independent recount from immutable files, which protects against stream bugs and corrupted state and gives an audit trail. The difference between the two paths is the best monitoring signal for correctness.

How do you choose the dedup storage, and how big is it?

I keep recent click ids in the stream job's local RocksDB state, partitioned by click id so all copies reach the same task, and snapshotted with the offsets. At peak with a 1 hour horizon that is about 180 million ids, about 7 GB over 64 tasks, which is easy. An external Redis check adds a network call per event and is not atomic with the downstream write. A Bloom filter alone is risky since a false positive drops a real paid click, but it can sit in front if a "maybe" always falls through to an exact check.

Which database holds the aggregates, and why not Cassandra or a time-series database?

A columnar OLAP engine such as ClickHouse, Druid or Pinot, sorted by advertiser, ad and minute. The workload is batched upserts plus range scans and group-bys across many ads, which columnar engines do well. Cassandra serves a single ad's time series nicely but makes advertiser-level group-bys and rollups costly. A classic time-series database struggles with tens of millions of series. If the product only needed per-ad charts, a wide-column store would be simpler and fine, and I would say that trade-off out loud.

How do you compute "last 5 minutes" and a top-10 board efficiently?

I only store tumbling one-minute counts and build a sliding window by adding the last N buckets, so raw events are processed once. For the top 10, the aggregate job keeps a Redis sorted set per minute with ad id and cumulative count. The query merges the last N sets and takes the top ten; each set is trimmed to a few thousand members and the merged result is cached for several seconds. That is approximate only in a contrived edge case, and the batch job can produce the exact board for reports.

A bug in a fraud rule is found six hours after deploy. What do you do?

Every raw event and every rejection is kept with its rule version, so I fix the rule and replay. Within 7 days I reset consumer offsets and re-run into a shadow output, compare it with live numbers, then swap. For older data the batch job reruns over the archive for the affected hours and writes higher revisions. Billing reads only finalized hours; if an hour was already billed, the difference goes through the ledger as an adjustment with an audit record. Early detection comes from the rejection-rate band and the stream-versus-batch diff alert.

Dashboard numbers suddenly look too low for everyone. How do you investigate?

First check freshness: is the watermark lagging because the job is behind or a partition is idle? If lag is normal, look at the invalid click ratio; a jump points to an over-aggressive rule or bad deploy. Next compare stream output with the hourly batch for the same hours; a growing gap says the stream logic is wrong, not the traffic. Check the canary ad: if its known count is off, the pipeline is losing data. Then fix by rolling back, and replay from Kafka or the archive for the affected window.

How do you size Kafka partitions and stream tasks?

Bandwidth is not the limit: 50k events per second of 200 bytes is about 10 MB per second. The partition count sets maximum consumer parallelism and cannot be reduced, and raising it later changes the key to partition mapping, so I start at 64. That is about 780 events per second per task at peak, leaving headroom for catching up at 2x. At 10x scale I would move to 128 to 256 partitions and rescale tasks by key group.

Multi-region: aggregate in each region or centrally?

Each region runs its own click tier and regional Kafka so users are served nearby. I then mirror raw topics to one central region and aggregate there. Counts are additive, so regional aggregation then merging would save bandwidth, but it makes global dedup harder, since the same click id could appear in two regions after a failover. With only about 10 MB per second to move, one place for dedup and billing is worth far more than the saved bandwidth.
