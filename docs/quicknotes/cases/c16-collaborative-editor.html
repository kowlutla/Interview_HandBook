Case 16: Design a Collaborative Editor (Google Docs)

One-page cheat sheet: many people type in one document at the same time, and everyone ends up with the same text.

1 Problem2 Requirements3 Estimation4 API5 Data6 Architecture7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines and questions to ask

One line: shrink "Google Docs" to the hard part: many people edit one rich-text document at once, typing feels instant, and all copies end up identical (this is called convergence).
  • The hard part is not size. It is that edits happen at the same time against versions of the text that the other person has not seen yet. Positions stop meaning what the author meant.
  • Everything in the design keeps the author's intent (where they wanted the text) while still converging.
  • Never allow: two people looking at different text without knowing it.
AskAssume
Document typeRich text (paragraphs, bold, lists, links). Spreadsheets and drawings out.
Editors per documentTypically 1 to 3. Soft cap 100 editors, up to 10,000 read-only viewers.
Scale50 M daily users, about 2 M concurrent connections at peak, 500 M documents.
LatencyLocal typing instant (0 ms). Remote edit visible within 200 ms at p99, same continent.
OfflineYes. Conflicts must merge, not be rejected.
ConsistencyAll copies converge. Every acknowledged edit is durable.
History and sharingVersion history with restore, per-user undo. Roles: owner, editor, commenter, viewer, link sharing.
RegionsOne home region per document, disaster recovery elsewhere.

2. Requirements

Functional

  • Create, open, edit rich text
  • See others live, plus their cursors (presence)
  • Undo and redo only my own edits
  • Offline editing, merge on reconnect
  • Share by user, group, or link with roles
  • Version history: browse, name, restore

Non-functional

  • Convergence: all copies reach the same state
  • Intent preservation: a concurrent edit lands where its author meant
  • Durability: once acked, never lost
  • Latency: local echo instant, remote under 200 ms p99
  • Availability: 99.95% editing, 99.99% reading. A few seconds of editing pause on one document during failover is fine

Out of scope

  • Spreadsheet formulas, drawings
  • Comment threads (separate store)
  • Full-text search over documents
  • End-to-end encrypted editing (server cannot read, so it cannot transform; mention under evolution)

4. API

REST for metadata and sharing. One WebSocket per open document for live edits (a WebSocket is a long-lived two-way connection, so no polling).

CallPurpose
POST /docsCreate. Returns docId.
GET /docs/{id}Metadata, my role, WebSocket URL of the owning server.
PUT /docs/{id}/aclGrant or revoke access.
GET /docs/{id}/versionsList versions, paginated.
POST /docs/{id}/versions/{v}/restoreAppend new operations that rewrite the text to version v (history is never rewritten).
client -> server  join   { docId, token, lastKnownRev }
                  op     { clientId, opId, baseRev, ops:[...] }
                  cursor { range:[from,to] }          // lossy, not logged
                  undo   { opId }
server -> client  snapshot { rev, content }   catchup { fromRev, ops }
                  ack { opId, rev }   remote { rev, author, ops }   presence { user, range }
Say: "Each operation has a client-made opId. If the connection drops after the server accepted it but before the ack came back, the client resends the same id and the server returns the old ack instead of applying it twice."

Log row: {docId, rev, authorId, clientId, opId, baseRev, ops, timestamp}. rev is a dense counter 1, 2, 3 assigned only by the owner. The document is, by definition, the replay of operations 1 to N.

6. Architecture and main flow

Four rules: (1) one sequencer per document, (2) one owner server per document, (3) log is the truth, snapshots are a speed-up, (4) clients are replicas that apply their own edits instantly.

Main flow: one edit

  1. User types. Client applies it locally at once. If nothing is in flight it sends op{opId, baseRev, ops}; otherwise it buffers.
  2. Gateway forwards the frame to the owning server (routed at join time).
  3. Owner checks the role from its in-memory ACL, validates bounds and size, and drops duplicate opId.
  4. If baseRev is behind head, owner transforms the op against every committed op after baseRev.
  5. Owner assigns rev = head + 1, appends to the log, and waits for the quorum-durable write.
  6. Only then: apply in memory, send ack to the author, broadcast remote to others.
  7. Each receiving client transforms the incoming op against its own pending ops and shows it.

7. Deep dives

7.1 OT or CRDT: how to merge concurrent edits

OT (operational transformation) = edits are positions like insert(1,"X"); a transform function rewrites a concurrent edit so it still hits the right text. CRDT = every character has a permanent id and edits refer to ids, so edits can be applied in any order and still give the same result.

Worked example. Text ABCD at rev 5. Alice: insert(1,"X"). Bob: delete(2) (removes C). Server gets Alice first: AXBCD, rev 6. Bob's delete (base 5) is transformed against Alice's insert: insert at 1 is at or before 2, so the delete shifts right to delete(3). Result AXBD, rev 7. Bob transforms Alice's insert against his own pending delete (the delete is to the right, no change). Everyone ends with AXBD. Two inserts at the same position need a fixed tie-break (for example client id) or copies would show XY and YX.

AspectOT + central serverCRDT
Needs a central ordererYesNo (server still useful for storage, auth)
Offline / peer to peerHarder, long histories need many transformsNatural, merge is applying the set
MetadataNoneId per character plus tombstones (deleted markers), often 10 to 30 times raw text unless compacted
Correctness workTransform for every op pair, subtle bugsMerge easier to prove; rich text and moves are subtle
CleanupNoneTombstones must be pruned
Permissions, historyEasy, server sees every op in orderPossible, harder
In productionGoogle Docs, enterprise editorsLocal-first editors, Figma style
Choice: OT with server sequencing. We have a server per document anyway (auth, durability, history), documents stay small, and transform work stays bounded. Keep CRDT as the path for offline-heavy or local-first needs. Do not say one is simply better; state the trade-off.

7.2 Sequencing protocol and one server per document

OptionHowTrade-off
Consensus on every edit across serversMany servers agree on orderExpensive per keystroke, unneeded: one document has a tiny write rate.
Hash docId on a ringEach gateway computes the ownerNo lookup, but gateways may briefly disagree after a membership change, so needs fencing.
Lease in etcd with an epochServer acquires owner/D with a TTL and renewsSingle strong owner, easy migration and placement. Extra lookup (cached).

Choice: leases with epoch numbers. Each takeover gets a higher epoch (fencing token). Every log write carries it, and the log rejects lower epochs, so a paused "zombie" old owner cannot write. The order per document is just an in-memory counter. Clients send at most one op in flight, so the server only transforms against revisions since the client's baseRev.

Trap: sticky routing from a load balancer is not enough. Here one-owner-per-document is a correctness rule, enforced by the lease, not a hint.

7.3 Operation log plus snapshots (and history)

OptionOpen costVerdict
Store only the logReplay millions of opsToo slow to open.
Store only latest stateFastNo history, cannot rebuild, loses audit trail.
Log + snapshot every about 2,000 ops (or idle 30 s)One blob read + short tail replayChosen. Snapshots are derived and rebuildable.

Log first, snapshot second; never ack before the log append is durable. A lost snapshot costs load time, not data. Version history: nearest snapshot at or below V, then replay forward. Restore commits new ops that turn the current text into version V, so history is never rewritten. After 30 days compact: keep snapshots, bundle ops between them (thin to one a day for a year, then one a week).

7.4 Presence, offline, undo (short)

  • Presence: not sequenced, not logged, memory only. Cursor updates at most 5 per second, coalesced; cursors are transformed like zero-length ops; heartbeat 10 s, expire at 30 s; show 20 most recent cursors plus a count.
  • Offline: client keeps editing and stores pending ops locally (IndexedDB). On reconnect send join{lastKnownRev}, get catchup (or a snapshot if the gap is over about 5,000 revisions), transform, resend in-flight op with same opId. Long offline: compose history into one delta, or keep a CRDT on the device. If edit rights were removed, reject but keep a local copy for export.
  • Undo: per-user stack; invert my last op, transform the inverse against everything committed since, send as a new op. If someone deleted my text, the undo is a no-op.

8. Scaling and bottlenecks

PartHow it scales
GatewaysStateless, behind L4 balancer, tens of thousands of connections each; sized by connection count.
Document serversAdd servers, leases rebalance. About 400 for 2 M connections. Add at 60% CPU or 10,000 connections each. Place new leases on the least loaded server (under 70% CPU), since load per document varies enormously.
Op log store130 k writes/s average, 400 k peak, partitioned by docId; sequential appends suit LSM engines.
Metadata storeRead-heavy, cached in the owner. Not a bottleneck.
Lease service1.2 M leases renewing every 10 s is about 120 k writes/s, too much for one etcd. Use one lease per server plus a per-document record written only on acquire or move, or shard the service.
Mega-documentsEditors stay on the owner. Owner publishes ops to pub/sub; edge relay servers hold the 10,000 viewer sockets (about 20 ms later). 10,000 editors is out of scope.
Fan-out batching100 editors can cause about 20,000 messages per second from one document. Batch broadcasts in 20 to 50 ms windows.
MemoryThe owner's memory is the cache; evict a cold document after 10 minutes with no clients, after a final snapshot.

Consistency: strong for order within a document (one sequencer, quorum log); eventual for what each client sees. In a partition, the minority side stays available for local editing, and its edits join the shared document when it reaches the owner again.

10. Things to say to impress (senior / lead)

Say: "The problem is intent preservation under concurrency, not scale. Load is many tiny independent documents, so I avoid global ordering and give each document exactly one sequencer."
Say: "Acked means durable: I ack only after the quorum log append, and clients keep unacked ops and retry by opId, so an op is never in neither place."
Say: "Ownership is a lease plus epoch enforced at the log (fencing), so even a paused zombie cannot commit. I would also self-fence before lease expiry."
  • I run a rolling hash divergence check, because a silent transform bug is the one failure that must never go unnoticed.
  • Restore and undo append new operations; history is never rewritten.
  • Lease renewals per server, not per document, to avoid 120 k renewals per second.
  • Hybrid path: CRDT on device for offline merge while the server still orders and stores updates.
  • Phasing: 1 single server with in-memory OT and relational log; 2 leases, gateways, permissions, presence, history; 3 offline, relay tier, compaction, divergence detection; 4 multi-region and local-first sync.
  • At 10x: shard the lease service, hierarchical owner-map cache, pin each document to a home region near its editors.

11. Interview Q&A

Why not lock the document or paragraph while someone edits?

Locks give no conflicts, but people wait for each other and a user who walks away blocks everyone. Getting a lock also costs a round trip before the first keystroke, which breaks "typing feels instant". OT or CRDTs let everyone type at once and fix conflicts in the data, which is the point of a collaborative editor.

Why a central server for OT? Can clients transform among themselves?

Peer-to-peer OT needs transform functions correct for every interleaving of many peers, and many published algorithms were later found wrong. A central server gives one total order, so each client only reconciles its own pending ops against one stream. The server is also where we want auth, durability, and history, so it costs almost nothing extra.

What if two users insert at exactly the same position?

The transform must break the tie the same way on every copy, or one screen shows XY and another YX. Typical rules: the op the server committed first goes first, or compare client ids. Which one wins matters less than every copy using the same rule.

How do you guarantee an edit is never lost after the user sees it accepted?

The server sends the ack only after a quorum-durable append to the log. Anything not yet acked stays in client memory and local storage, and is resent with the same opId, so the retry is safe. So an op is either acked and durable, or still held by the client and being retried. There is no moment when it exists nowhere.

How do you stop two servers both owning a document?

Ownership is a lease in a strongly consistent store, and each takeover raises an epoch number. Every log write carries the epoch and the log rejects older ones. A server paused by garbage collection that wakes up thinking it owns the document is rejected on its first write. The old owner also stops serving when its own clock says the lease is close to expiring.

A document has 10,000 viewers and 50 editors. What do you do?

Editors stay on the owning server, where ops are sequenced. The owner publishes each committed op to a pub/sub layer, and a fleet of relay servers holds the viewer sockets and forwards ops. Viewers never send edits, so they only need ordered delivery, which revision numbers give. Presence for viewers is reduced to a count. The owner then fans out to tens of sockets, not ten thousand.

Why snapshot at all if the log is the truth?

Replaying a million ops to open a document is too slow. A snapshot is a cached replay result at a revision, so opening is one blob read plus a short tail replay. It can always be rebuilt from the log, so losing one hurts speed, never data. Snapshots also make version history and compaction cheap.

How does undo work when others have edited since my change?

Each client keeps a stack of only its own ops. To undo, it builds the inverse of its last op and transforms it against everything committed afterward so it hits the right text now. It is sent as a normal new op. Undo touches only my changes, history stays append-only, and if someone deleted my text the inverse does nothing.

How do you detect silent divergence between copies?

Every few hundred revisions the client hashes its document at a known revision and sends it. The server compares with its own copy at that revision. A mismatch means a transform bug or corrupt state, so the server tells the client to reload from snapshot plus log and raises an alert. We also fuzz-test every operation pair with random concurrent sequences before release.

Would you use CRDTs instead? When?

With a reliable server per document and needs for permissions, history, and compact storage, I pick server-sequenced OT. I would pick CRDTs if offline and peer-to-peer were first-class, if the server must not read content (end-to-end encryption), or if edits must merge across regions with no coordinator. The costs are per-character metadata, tombstone cleanup, and harder server-side validation. A hybrid is common: CRDT on the client, ordered log on the server.

What does a user see when the document server dies mid-edit?

Typing keeps showing locally because the client applies edits at once, and the status flips to "reconnecting". In about 5 to 15 seconds another server takes the lease, loads the snapshot and log tail, and accepts the reconnect. The client catches up, transforms, and resends its in-flight op with the same opId. Nothing acked is lost, and nothing unacked was ever lost since the client still held it.

A user was offline for hours. How do you merge their edits without a huge cost?

Replaying thousands of buffered ops against thousands of catch-up ops one by one is quadratic. The client first composes its offline history into one compact delta, so the server transforms a single op against the catch-up. Or the device keeps a CRDT so merges are well defined. At reconnect the server also rechecks permissions; if rights were removed, the batch is rejected and the client keeps the text as a local copy to export.

Real-time incident: users report two people seeing different text. What do you do?

First check the divergence detector for hash mismatches and see which documents and revisions are affected. Force the affected clients to reload from snapshot plus log, which restores a correct view because the log is authoritative. Then find the cause: a recent deploy to transform code, a bad operation type, or two owners writing (check epoch and lease churn). Roll back the transform change if needed, add the failing case to the fuzz tests, and treat it as an incident since divergence should be zero.
