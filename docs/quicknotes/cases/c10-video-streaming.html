Case sheet C10: Design YouTube / Netflix

A video platform is a slow, parallel "factory" that turns an upload into many playable versions, plus a huge read-only delivery network. The bill is dominated by bytes leaving your network.

1 Problem2 Requirements3 Estimation4 API5 Data6 Architecture7 Deep dives8 Scaling9 Failures10 Impress11 Q&A12 Links

1. Problem in 3 lines and questions to ask

Three lines: (1) A creator uploads a big video file. (2) We turn it into many sizes and qualities, store them, and mark it ready. (3) Hundreds of millions of viewers on phones and TVs play it with fast start, few stalls, and quality that adapts to their network.

YouTube takes uploads from anyone and has a huge "long tail" of videos almost nobody watches. Netflix has a small licensed catalog served to subscribers. The design underneath is the same: ingest, convert, store, deliver through a CDN (a network of caches close to viewers) with adaptive bitrate streaming. We design the YouTube-style version and note where Netflix differs.

AskAssume
Who uploads, how big?Any user. 10 seconds to 12 hours, up to about 10 GB per file.
Scale?500M daily viewers, 3 billion video starts per day, 5M uploads per day.
Devices and networks?Phones, browsers, TVs, consoles. From 500 kbit/s mobile to gigabit fiber.
Quality targets?Start in under 2 s (p95). Stalls under 0.5 percent of play time.
Live? DRM?Live is a side note. DRM only for premium and licensed content.
Multi-region?Yes. Viewers are global; originals stored in at least two regions.

2. Requirements

Functional

  • Resumable upload with title, description, visibility
  • Process into many resolutions, bitrates, codecs, plus thumbnails; mark "ready"
  • Play on any device; quality adapts; fast seek
  • Search, home feed, view counts, likes
  • DRM for premium titles

Non-functional

  • Playback availability 99.99 percent (a failed play is a headline; a failed upload is annoying)
  • Start under 2 s p95, rebuffer under 0.5 percent
  • Originals never lost (eleven nines durability)
  • Read to write about 600 : 1; processing is bursty
  • Cost: bandwidth and storage dominate
  • Counts, likes, search can be eventually consistent. Upload state and permissions need strong consistency.

Out of scope

  • Ad serving and auctions
  • Payments and subscriptions
  • Comment threads
  • Moderation ML models (we leave a hook stage)
  • Creator analytics, video editor

6. Architecture and main flows

One line: three planes that scale separately. Upload and processing (async, compute heavy). Delivery (CDN, bandwidth heavy). Metadata and discovery (cacheable APIs).

Upload flow

  1. Client calls POST /uploads. API checks quota, creates an upload session and a video row in UPLOADING, returns part size and upload id.
  2. Client cuts the file into 8 MB parts and sends several in parallel, direct to object storage with signed URLs. Storage checks each part checksum.
  3. If the connection drops, client asks which parts exist and sends only the missing ones.
  4. Client calls complete with part numbers and etags. Storage assembles the object. API does a compare-and-set UPLOADING to PROCESSING and publishes video.uploaded.
  5. Orchestrator runs the DAG. At the end it sets READY and emits video.ready for search, notifications and recommendations.

Play flow

  1. Player calls GET /videos/{id}. API reads cached metadata, checks permission, returns manifest URL and steering info (which CDN host to use).
  2. Player fetches the manifest from the nearest edge, picks a starting quality, then fetches one 4 s segment at a time over plain HTTP.
  3. Edge hit: served locally. Miss: edge asks the shield, shield asks origin, one request per object is merged and the copy is stored along the way.
  4. Player sends a view beacon (async). Premium: player also asks the license server for a key.

7. Deep dives (pick 2 or 3)

7.1 Upload path: where do the bytes go?

OptionHowProsCons
A. Through our servers (own chunk protocol, like tus)Our upload servers append chunks and track offsetsFull control; can inspect bytes earlyWe pay ingress bandwidth and CPU; stateful servers; sticky routing
B. Direct to object storage with signed URLs (chosen)API hands out part URLs; storage tracks partsServers only do tiny control calls; durable and scalable alreadyLess control per byte; validate after completion
Choice and why: B. At 2.5 PB per day we must not proxy bytes. Validation (format check, virus scan, policy) is the first stage of the DAG anyway, run in a sandbox. Keep the session row so a creator can resume days later. Add a lifecycle rule to abort unfinished multipart uploads after about 7 days so orphan parts stop costing money.
  • Integrity: every part has a checksum; a bad part is rejected and re-sent. Re-sending the same part is harmless (same bytes).
  • Idempotent complete: a second call returns the existing state and does not publish a second job.
  • Fast for creators: as soon as the 360p rung is ready, mark the video "playable in low quality" and keep building higher rungs (the "HD processing" message).

7.2 Transcoding pipeline: how to parallelize

Transcoding means re-encoding the original into a ladder of versions (for example 144p at 200 kbit/s up to 1080p at 5 Mbit/s, 4K at 12 to 16 Mbit/s for selected videos), cut into short segments so the player can switch quality at segment edges. Six rungs add up to about 10.6 Mbit/s; for 8 minutes that is about 640 MB, which matches the "about 1 GB per video" estimate.

OptionDescriptionProsCons
A. One whole-file encode per rung6 tasks per videoSimple; no seams3 hour video takes hours; a failure at 95 percent redoes all
B. Chunk x rung (chosen)Split at key frames (GOP boundaries), encode each chunk and rung as its own taskLatency falls with worker count; cheap retries; fits spot instancesMore tasks and state; need identical key-frame alignment; rate control can vary a little between chunks
C. Hardware-only single streamFixed-function encoderVery fast, low powerLower compression than best software; capex
  • Workers: stateless, pull a task from the queue, read the chunk, encode, write to a fixed output key, acknowledge. A fixed key makes retries safe (same bytes overwrite).
  • Lease: if a worker dies (spot instance reclaimed) the lease expires and another picks the task up. Only that chunk is redone.
  • Autoscale on backlog age. Target: first playable rung within 5 minutes (p95) for typical uploads. Cap per-user concurrency so a 12 hour upload cannot starve others.
  • Poison tasks: after N failures go to a dead letter queue and mark the video FAILED with a reason.
  • Fan-in: "all chunks done" is a compare-and-set on the DAG stage, so two finishing workers do not both trigger packaging.
CodecSize vs H.264Encode costDevice support
H.264baselinelowuniversal
HEVCabout 30 to 40 percent smallerhighermodern phones, TVs; patchy in browsers

Choice and why: B for parallelism, with hardware encoders where speed matters more than size. Encode everything in H.264 first so it plays everywhere. Re-encode with VP9 or AV1 only after a video passes a view threshold: encode is a one-time cost, but the byte saving is earned on every view. Use per-title encoding (a cartoon needs far fewer bits than a football match) to save more bandwidth. Netflix, with a small catalog and huge audience per title, encodes aggressively up front.

7.3 Adaptive streaming and the CDN

Adaptive bitrate (ABR): the video is stored as short segments (about 4 s) in several qualities. A manifest (the table of contents) lists them. The player picks the quality of each next segment using plain HTTP GETs. Because the files are static, any ordinary CDN can cache them. This is why it beat stateful streaming servers (RTMP).

HLSDASH
Manifest.m3u8 text playlists.mpd XML
WhereRequired on Apple devicesAndroid, Chrome, many TVs
DRMFairPlayWidevine, PlayReady
SegmentsWith CMAF (fragmented MP4) both use the same segment files, so only two small manifests differ. Produce both from one set.

The player keeps a buffer (about 20 to 30 s for VOD, video on demand). Simple rule: pick the highest rung under about 80 percent of measured throughput; also step down when the buffer shrinks. Start low for a fast first frame, then ramp up. Shorter segments adapt faster but mean more requests; 4 s is the usual compromise.

Choice and why: at 60 Tbit/s peak, own appliances pay off, but the path is rent first, multi-CDN second, own appliances last. Key tricks: request coalescing (5,000 viewers ask for the same missing segment, the edge sends one request upstream), an origin shield, long TTL for immutable segments (days to a year) and short TTL for manifests (minutes), a cache key of the path only (signed URL signature excluded), and admit-on-second-hit so one-time videos do not push out hot ones. YouTube's long tail gives lower edge hit ratio (about 85 to 95 percent by bytes) than a curated catalog (95 percent or more).

8. Scaling and bottlenecks

  • Segments (3 to 10M requests per s): never reach app servers. Even at 95 percent edge hit ratio the origin side still sees about 3 Tbit/s, so a shield tier is needed to cut it further.
  • Play API (100K per s peak): stateless servers, cached metadata (hit above 99 percent because reads are about 600x writes), metadata sharded by video_id; owner queries use a secondary index.
  • Hot videos (premiere): manifest is tiny and held in edge memory; hot segments are replicated over several servers in a site and kept in RAM.
  • Upload burst: object storage absorbs ingest, the queue absorbs processing, autoscaling adds workers. If backlog grows, do only low rungs first and delay AV1.
  • Transcode reads: have the split stage write each chunk as its own object so tasks read only their chunk; run workers in the same region as the storage.
  • Search and recommendations: fed by the event stream, kept off the playback path.
Cost (per day, illustrative): egress 340 PB at about $0.005 per GB is about $1.7M (about $6.8M at list price). Encode 280K cores x 24 h x $0.01 is about $67K on spot. Storage standing 1 EB at $0.004 per GB-month is about $4M per month. Egress is over 90 percent, so every saving must cut bytes per view or price per byte. A 30 percent bitrate cut saves about $510K per day.
Trap: optimizing servers first. A small cut in bytes per view (better codec, per-title ladder, higher hit ratio) beats almost any server tuning.

10. Things to say to impress (senior/lead)

Say:
  • "The hard part is not requests, it is bytes: 60 Tbit/s at peak and 340 PB per day out. So I design the delivery plane first and treat the app tier as small."
  • "Egress is over 90 percent of the bill, so the cost levers are codecs, per-title ladders, hit ratio and peering, not servers."
  • "Upload and playback are separate failure domains on purpose. A failed upload is annoying; a failed play is a headline."
  • "Encode is a one-time cost; delivery is paid on every view. So spend expensive AV1 encodes only on videos that prove popular."
  • "Everything in processing is idempotent with deterministic output keys, so at-least-once delivery and spot instances are safe."
  • "Segments are immutable, so a very long TTL is safe. Anything that changes gets a new path."
  • "Measure quality on the client (time to first frame, rebuffer ratio), since a 200 from the server does not mean the video played."
  • "Phasing: rent a CDN with a small H.264 ladder first; then chunked DAG, per-title, multi-CDN; then own appliances and cells."

11. Interview Q&A (follow-ups)

Why upload directly to object storage instead of through your servers?

Proxying multi-gigabyte uploads would make our app tier carry 2.5 PB per day, which needs big stateful servers with sticky routing just to support resuming. With signed URLs the API issues small control messages and the object store, which is built for durable high-throughput ingest, takes the bytes. We still need validation, so it becomes the first stage of the processing DAG, run in a sandbox. The trade is less inline control for a simpler, cheaper, more scalable system.

How do you make an upload resumable, and what if the client loses all its state?

The file is cut into fixed parts and each part is its own request. The object store (or our session row) records which parts arrived with their checksums. After a failure the client asks for the list of finished parts and sends only the missing ones. If the app was reinstalled, it can still ask by upload id, or by user plus file fingerprint, and then just re-read the local file. Parts are idempotent so duplicates are harmless, and a lifecycle rule expires unfinished sessions so orphan parts do not cost money forever.

Why split into chunks for transcoding, and what is the catch?

Encoding time grows with video length, so one machine encoding a three hour film takes hours, and a failure near the end repeats everything. Cutting at key frames lets hundreds of workers encode chunks at once, so time is about one chunk plus overhead, and a dead worker redoes only seconds of video. The catches: all rungs must use the same key-frame alignment so the player can switch, rate control can differ slightly between chunks (fixed with constrained two-pass or look-ahead), and there are hundreds of tasks per video to track, so we use a durable workflow engine.

Explain HLS versus DASH and what the manifest does.

Both split the video into short HTTP segments in several qualities and let the player choose the next one. HLS uses text playlists: a master listing each rung's bandwidth, resolution and codec, then one playlist per rung listing segment URLs. DASH uses an XML file with the same data. HLS is required on Apple devices, DASH is common on Android and TVs. With CMAF the media bytes are identical, so we store one set of segments and generate two small manifests. The manifest also enables seeking (compute the segment number), several audio languages and subtitles, DRM signalling, and adding new renditions later without touching the player.

A new blockbuster is released. How does the origin survive?

Several layers stack. Each edge merges simultaneous requests for the same missing segment into one upstream fetch. A regional shield does the same across edges, so the origin sees at most one request per object per region. For known releases we push the segments to caches during off-peak hours, so the first viewer already gets a hit. Segments are immutable with long TTLs, so they never need revalidation, and manifests use short TTLs with stale-while-revalidate so they do not all expire at the same moment. What reaches the origin is only the truly cold part.

Why would a company put its own servers inside ISPs?

At tens of Tbit/s the cost and congestion of moving bytes over the internet backbone dominate. A cache box inside the ISP serves local viewers over the ISP's own network. The ISP avoids paying for upstream traffic, viewers get lower delay and fewer stalls, and we avoid per-GB CDN fees and gain full control of caching and steering. It only pays off at very high volume because of the hardware and operations cost, so smaller services rent a CDN. The box holds the locally popular catalog and fills itself overnight; anything it lacks falls back to a regional PoP.

How do you count views for a viral video without melting the database?

Never increment a DB row per view. Players send beacons to a collector that validates and removes duplicates, then writes events to a stream keyed by video id. Aggregators sum counts in windows of a few seconds and write one increment per video per window to a sharded counter store, and the shown total is served from cache. A video getting 100,000 events per second becomes about one write per window. The number is eventually consistent by design. Exact numbers for payments and ads come later from the raw event log in the data lake, which can be replayed after a bug.

What is your codec and encoding cost strategy?

Encode is a one-time cost, delivery is paid on every view, so spend depends on expected views. Everything gets H.264 first for universal playback and a fast "ready". Videos that pass a popularity threshold are re-encoded with VP9 or AV1, which are about 30 to 50 percent smaller at the same quality, so the bandwidth saving soon beats the extra CPU. Per-title encoding fits the ladder to how complex the content is. A catalog like Netflix, with few titles each watched millions of times, uses expensive settings up front; a user-upload platform does it lazily.

How do you do DRM without breaking CDN caching?

Segments are encrypted once with a content key using common encryption, so every viewer downloads identical encrypted bytes and the CDN caches them normally. Access control moves to a license server: it checks the viewer's entitlement and returns a license with the key to the device's protected decryption module, using Widevine, FairPlay or PlayReady as the device needs. That makes the access check a small, low-bandwidth service instead of part of the byte path. Because it sits on the critical path of start-up, it is multi-region and caches entitlement checks. DRM raises the cost of piracy; it does not stop screen recording.

What changes for live streaming?

Ingest is a continuous stream and the encoder must keep up with the clock, so you cannot fan out into chunks freely; each stream gets a dedicated encoder with a hot standby. Segments appear every 2 to 6 seconds and the manifest is a sliding window with a very short TTL. Delay is a design choice: normal HLS or DASH is 15 to 30 seconds behind, low-latency variants get to 2 to 5 seconds, and WebRTC goes under 1 second at higher cost. The CDN sees everyone asking for the newest segment at once, so coalescing and shield tiers are critical. The stream is also recorded so it becomes a normal video after the event.

A takedown arrives for a video cached all over the CDN. What do you do?

First flip the status in the metadata store so the play API stops returning manifest URLs, and explicitly invalidate the metadata cache. Then purge the manifest paths in the CDN (and segment prefixes if the CDN supports it). Segment URLs are hard to find without the manifest, and sensitive content uses short-lived signed URLs, so exposure is limited by purge time and signature lifetime. We log the action for audit and block re-uploads of the same content using fingerprint matching.

Production incident: rebuffering jumps from 0.5 percent to 3 percent in one region. What do you do?

First split the signal: is it one ISP, one device type, one CDN, or all? Client quality data broken down by ISP, CDN and rung tells me quickly. If one edge site or appliance is overloaded or down, steering should already be removing it; I check that and add headroom if needed. If one CDN vendor is bad, shift traffic to another using multi-CDN. If the origin side is slow (fills failing, hit ratio fell), I look for a stampede or a bad manifest change and roll it back. As a quick relief I lower the default starting rung for that region for a short time so playback keeps going while I fix the root cause.

Why not store videos in a database, or use peer-to-peer delivery?

A database is the wrong tool for huge immutable blobs: it costs far more per GB, gives poor throughput, and has no easy range reads or tiering. Object storage for bytes plus a database for metadata is the right split. Peer-to-peer lowers egress but is complex, drains phone batteries and upload bandwidth, and raises security and privacy issues. As CDN prices fell and ISP appliances arrived, most platforms dropped it. Plain HTTP segments from caches scale simply and work on every device.
