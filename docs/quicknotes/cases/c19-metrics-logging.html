Case Sheet 19: Design Metrics and Log Aggregation

A platform like Prometheus + Grafana + an ELK stack (or Datadog) that collects numbers and text logs from 50,000 machines, stores them cheaply, answers dashboards in seconds and pages someone within a minute.

1 Problem · 2 Requirements · 3 Estimation · 4 API · 5 Data model · 6 Architecture · 7 Deep dives · 8 Scaling · 9 Failures · 10 Impress · 11 Q&A · 12 Links

1. Problem in 3 lines

One line: two workloads in one prompt. Metrics are small numbers over time (CPU 63 percent) named by labels. Logs are text records of single events. Build two pipelines that share a buffer, alerting, tenancy and a UI.
  • The hard parts: huge write volume, storage cost, label explosion ("cardinality"), and the fact that this system must stay up exactly when everything else is down.
  • Write availability comes first. A monitor that goes blind in an outage is useless.

Clarifying questions to ask (and the assumed answers)

QuestionAssumed answer
Users?One big company, about 500 teams as tenants (note how a SaaS vendor differs).
Sources and scale?50,000 hosts and containers. 10 million active series, 1 million log lines per second.
Resolution?10 s default, 1 s for a few opt-in series.
Freshness?Metric queryable in 15 s, log searchable in 30 s, alert within about 1 minute.
Retention?Metrics: raw 15 days, 1 min rollups 90 days, 5 min rollups 13 months. Logs: 7 days searchable, 30 days cheap and slower, 1 year archive for chosen streams.
Loss allowed?Metrics: tiny gaps ok, never silent. Debug logs may be sampled with a drop counter. Audit logs must not be lost.
Traces?Out of scope, but say where they plug in (shared trace ids).

2. Requirements

Functional

  • Collect metrics (pull and push) and logs through agents.
  • Store labeled time series; range queries with sum, rate, quantiles, group-by.
  • Parse, store and search logs by time, labels and text.
  • Dashboards: saved, auto-refreshing queries.
  • Alert rules, routing to pager/chat/email, dedup, grouping, silences, escalation.
  • Multi-tenancy: isolation, quotas, cost per team.

Non-functional

  • Ingest stays up during a storm.
  • Dashboards: p95 under 2 s for 24 h, under 5 s for 30 days.
  • Alert path independent of the heavy query path.
  • Cost: storage is the main bill, so compress and tier.
  • Survive loss of one zone; no circular dependency on what it watches.

Out of scope

  • Trace storage, profiling.
  • Product analytics (see case 20 for exact stream counting).
  • Security detection rules (SIEM).
  • ML anomaly detection (later extension).
Say: "Losing telemetry is better than hurting the product, but the loss must be bounded, visible and prioritized. And alerting must work even when the dashboards do not."

4. API

POST /v1/metrics/write   (snappy, protobuf; X-Tenant-Id, bearer token)
  [ {labels:{__name__:"http_requests_total", service:"cart", code:"200"},
     samples:[{ts_ms, value}, ...]} ]
  -> 204 | 400 bad labels | 413 too large | 429 quota + Retry-After | 503 retry

POST /v1/logs/push
  { stream_labels:{service,env,level}, entries:[{ts_ns, line, structured_metadata:{trace_id}}] }

GET /v1/query_range?query=sum(rate(http_requests_total{service="cart"}[5m])) by (code)&start&end&step=60s
GET /v1/logs/query?query={service="cart"} |= "timeout" | json | latency_ms > 500&limit=1000
PUT /v1/rules/{tenant}        (alert and recording rules)
POST /v1/alerts/silences      (matchers, start, end, comment)
  • Writes are batched and safe to retry: the same (series, time, value) is dropped as a duplicate. A different value at the same timestamp is rejected.
  • 429 with Retry-After is how quotas and backpressure reach agents. The tenant id is set by the gateway, never trusted from the body.

5. Data model and store choices

One line: a series is identified by its full label set (including the name); a sample is (timestamp, float64). Everything else follows.

6. Architecture and main flows

Start simple: one Prometheus-style server scrapes about 1,000 targets and holds 10 to 100 thousand series on local disk; logs go to one search node. It fails four ways: memory caps series, the disk is the only copy, one box both alerts and serves heavy queries, and there is no tenant isolation.

Write flow

  1. The agent posts a batch (snappy, tenant id) to a distributor via the load balancer.
  2. The distributor checks auth and limits (series count, rate, label size), validates labels, then hashes (tenant, labels) to pick a Kafka partition. All samples of one series go to one partition, so one ingester keeps their order.
  3. It produces with acks=all and returns 204 once the write is durable. If Kafka is down it returns 503 and the agent retries from its disk buffer.
  4. The owning ingester appends to the write-ahead log and the in-memory head block.
  5. Every 2 hours the head is cut into an immutable block, uploaded to object storage, and the log is truncated.
Key point: the agent is acknowledged after the Kafka write. A slow ingester delays freshness but never loses data.

Read flow

  1. The dashboard sends a range query to the query frontend.
  2. The frontend splits it into per-day pieces, checks the cache (past days never change), and queues work per tenant fairly.
  3. Queriers read the last 2 hours from ingesters and older data from blocks through the store gateway (index headers cached).
  4. They merge, remove replica duplicates, evaluate and return; results are cached by day.

Pull versus push (expect this question)

Pull (collector scrapes)Push (agents send)
Good atFree liveness: a failed scrape means "down". Central rate control.Short-lived jobs, logs, firewalled networks.
Weak atNeeds reachability and discovery; misses short jobs.Silence is ambiguous: dead app or dead network?

Choice: a hybrid node agent. It scrapes local targets by pull (so up=0 comes free), tails logs, accepts local pushes from batch jobs, then makes one outbound batched push to the distributors. Outbound-only passes firewalls; scrape offsets are jittered so 50,000 hosts do not fire in the same second; it buffers to local disk when the platform is down.

7. The deep dives

7.1 Cardinality explosion

Cardinality is the number of distinct series: the product of the label value counts. 50 services x 20 endpoints x 5 codes = 5,000 series (fine). Add a user_id label with 1M values and you could get 5 billion series, each costing about 3 KB of memory. One innocent label (request id, raw URL, a pod name that changes at each deploy) can crash ingesters for everyone. This is the most common metrics incident.

OptionProCon
Reject new series over the limitProtects the system, predictable, tenant sees the errorSome metrics missing until fixed, so show errors loudly
Drop the label at ingest and sumKeeps data, bounded costLoses detail; summing gauges can be meaningless
Allow and charge the tenantFair for a vendorDoes not protect memory in real time

Choice: reject plus alert for an internal platform (hard cap per tenant, warning at 80 percent); charge back for a vendor but still keep a hard cap. Other layers: label count and length limits, agent-side drop rules, a cardinality dashboard that alerts when a metric grows more than 3x in an hour, dropping churny pod labels, and recording rules that pre-aggregate.

7.2 Downsampling, rollups and retention

ApproachGood forWeakness
Background downsampling in the compactorAny series, long-range queries, no user effortCosts storage for series nobody queries
Recording rules (scheduled query writes a new series)Cheap dashboards and alerts; cuts cardinalityMust be defined in advance

Choice: both. Auto rollups after 15 days, recording rules for the top 200 dashboards. Keep min, max, sum, count (average of averages is wrong). A p99 cannot be computed from stored p99s: store histograms or mergeable sketches (t-digest, DDSketch) and compute the quantile at query time. A year chart at 1,000 pixels needs a point only every 8.7 hours, so reading raw data is waste. Retention is deleting whole blocks.

7.3 Log storage: full index versus label index plus chunks

DimensionA: Inverted index (Elasticsearch)B: Label index + object storage (Loki style)
Storage at 43 TB/day raw40 to 60 TB/day on SSD with replicas; 7 days is 300+ TBabout 5.4 TB/day; 30 days about 160 TB
"timeout" in checkout, last 1 hTens of ms to 1 sReads matching chunks: a few seconds in parallel
Rare token across all services, 7 daysSecondsMinutes unless bloom or skip indexes help
Ingest CPUHigh (analysis, segment merges)Low (compress and batch)
OperationsShard rebalancing, mapping blowups, heap pressureStateless queriers; object store gives durability
Best forSecurity search, short retention, small volumeOperational logs where most lines are never read

Choice: B by default (about 1/10 the cost), A only for a small curated set of streams. Speed up B with per-chunk min/max and bloom filters on tokens or trace ids. A columnar format (Parquet, ClickHouse style) compresses 10 to 30x and is better for "count and group by a field"; B is better for "show me the lines". State your assumption.

Sampling and parsing: parse in the agent (JSON, level, trace id, Kubernetes labels). Keep all warnings and errors, 10 percent of info, 1 percent of debug, adaptive when a service goes over budget, with a "dropped lines" counter. Sample by trace id hash so a sampled request stays whole. Never sample audit or security streams.

7.4 Alerting engine (short)

  • Rule = query + condition + "for" duration. States: inactive, pending, firing, resolved. The "for" window is the first noise filter.
  • Evaluators run on a dedicated read path straight from ingesters, never through the user query queue.
  • Alert manager (3 replicas, gossip): dedup by label set, group (200 pod alerts become one page), inhibit (datacenter down hides service down), silence, route by team and severity, escalate after 10 minutes unacknowledged.
  • Flapping: longer "for", hysteresis (fire at 2 percent, clear below 1 percent), keep-firing window, evaluate over 5 minute rates.
  • AP bias: if gossip splits, the failure is a duplicate page, not a missed one.
  • Watchdog (dead man's switch): an always-firing alert sent to an external service that pages when it stops arriving.

8. Scaling and bottlenecks

BottleneckWhyFix
Ingester memory10M x 3 KB = 30 GB; x3 replication = 90 GB, over 30 ingestersAdd ingesters; partitions move by consumer rebalance, ownership follows
Hot series or tenantUneven hashingShard by series hash, not by tenant, so a giant tenant spreads out
Hot log partitionOne service printing 100 MB/sAdd a bucket suffix to split the stream over N partitions; order by timestamp at query time
Old-block queriesNeed index headersShard blocks across store gateways by block id, replication 2, header cache in memory, chunk cache on local disk
CompactorMany small blocks, duplicates from replicationMerge 2 h into 12 h and 24 h blocks; shard by tenant, throttle
Query fan-outBig aggregations touch many seriesPartial sums in queriers, limits, recording rules
Dashboard load800 queries/s, repetitiveDay-split result cache with step-aligned keys, per-tenant fair queue

Tenancy and quotas: token bucket per tenant for samples/s (burst 2x, 429 on excess); active series soft 80 percent, hard 100 percent; log bytes (for example 20 MB/s tenant, 3 MB/s stream); active streams (for example 100k); query limits on samples, range and concurrency. Use shuffle sharding: each tenant gets a random subset (say 5 of 60 ingesters), so a bad tenant only hurts its own subset. Very large tenants get a dedicated cell. The same counters give per-team cost showback.

Backpressure ladder: app to agent uses a bounded non-blocking queue (drop and count). Agent to distributor uses backoff with jitter and a disk buffer (about 1 GB, 30 minutes), dropping debug then info first. Distributor to Kafka returns 503 so agents hold data. Consumers fall behind rather than lose data; autoscale on lag (alarm at 60 s, page at 300 s). Before lag passes the 6 hour buffer, shed in a documented order.

At 10x (100M series, 10M lines/s): head memory 300 GB forces cells by tenant group with a global query layer; larger blocks and sharded compaction; skip indexes and columnar logs become mandatory. At 100x, aggregate in a stream processor before storing.

9. Failure modes

Monitoring data is eventually consistent (15 s behind is fine; queriers dedup replicas). Only configuration (rules, silences, routes) needs a versioned replicated store. Run the platform in a separate failure domain (own cluster, DNS, credentials) with a minimal second stack that watches only its health: Kafka lag, ingester memory, rule evaluation delay, Watchdog.

10. Things to say to impress

Design stance

  • "Two workloads, two pipelines, one shared buffer, tenancy and alert path."
  • "Ack after the durable Kafka write; apply later. Lag is the pressure gauge."
  • "Losing telemetry beats hurting the product, but loss must be bounded, counted and prioritized."

Numbers

  • 16 B raw to about 1.5 B per sample: 1.4 TB to 130 GB per day.
  • 3 KB per series in memory: cardinality is the real limit.
  • Full text index about 730 TB SSD versus about 160 TB object storage.

Senior traps to name

  • Never average percentiles; store histograms or sketches.
  • Alert on symptoms (SLO burn), not causes (CPU high).
  • Who monitors the monitor: Watchdog plus a second stack.
  • Prefer a duplicate page to a missed one.
Common mistakes: saying "push is better" or "pull is better" with no reasoning; indexing every log word; user ids as metric labels; one query path for dashboards and alerts; no plan for the monitor failing.
Say: "Agents scrape locally and push outbound to distributors, which write to Kafka and acknowledge. Ingesters build compressed time-series blocks and ship them to object storage. Logs index only labels and keep compressed chunks cheaply. Alerting runs on its own path with an external dead man's switch, and per-tenant limits plus shuffle sharding stop one team from taking everyone down."

11. Q&A: follow-up questions

Why put Kafka between the distributors and the ingesters instead of writing directly?

Kafka decouples receiving from storing. Without it, a slow or restarting ingester makes the distributor either block, which pushes failure back to every agent, or drop data. With Kafka, the write is acknowledged once it sits in a replicated log, and ingesters read at their own pace, so a downstream slowdown becomes lag instead of loss. Several consumers can read the same stream (ingesters, rule evaluators, an archiver), and you can replay after a bug. The costs are one or two seconds of extra freshness delay, about 16 to 32 TB of extra disk for 6 hours of logs, and one more system to run. For a small deployment I would skip it, but at 500 MB/s of logs it pays for itself in the first incident.

A developer added a user_id label and ingesters are running out of memory. What do you do?

First contain it. Find the tenant and metric from per-tenant series counters, then reject new series for that metric or drop the label at the edge, so existing series keep working and memory stops growing. Apply the drop rule before restarted ingesters replay from Kafka, or they will recreate the series. Then prevent it: a hard active-series limit per tenant, label count and length limits, a cardinality dashboard with growth alerts, and guidance that identifiers belong in logs and traces. Shuffle sharding also limits which ingesters the tenant could have hurt.

How do you compute a p99 over a year when you only keep rollups?

You cannot, from stored p99 values or averages, because quantiles do not add up. Store a mergeable form instead: histogram bucket counts (how many requests were under each latency bound) or a sketch such as t-digest or DDSketch. Rollups then sum the bucket counts over the window and the quantile is estimated at query time, with error bounded by bucket width. It costs more series (20 buckets means 20 series), so choose bucket edges around your SLO thresholds, for example 100 ms and 500 ms, to make SLO compliance exact.

How does the compression reach about 1.5 bytes per sample?

Timestamps use delta of delta. With a regular 10 s scrape the second difference is zero, which costs 1 bit. Values are XORed with the previous value: an unchanged value costs 1 bit, and a small change leaves only a few meaningful bits between long runs of zeros, about a dozen bits in all. Across real fleets that averages about 1.3 to 2 bytes versus 16 raw. Noisy values and irregular timestamps compress worse, so I say "typically". It is the difference between 1.4 TB and 130 GB a day.

Why not index all logs in Elasticsearch? When would you?

A full inverted index makes any word searchable in milliseconds, but it needs about 1 to 1.5 times the raw size on replicated SSD, burns CPU on analysis and segment merges, and needs shard management. At 43 TB a day that is hundreds of terabytes of SSD for a week, about ten times the cost of compressed chunks plus a small label index. Since most lines are never read, indexing them all is wasteful. I would use Elasticsearch for streams that need fast free-text search at moderate volume and short retention (security, support lookups) and the label-plus-scan design for the rest.

How do you avoid alert storms and flapping?

In layers. In the rule, use a "for" duration and a window so a blip does not fire; add hysteresis (fire above 2 percent, clear below 1 percent) and a keep-firing period. In the alert manager, group alerts so 200 pod alerts are one page, inhibit symptoms when a root-cause alert fires, dedup repeats, and use silences for maintenance. At the design level, alert on user-visible symptoms and SLO burn rates rather than every internal cause, and treat any page that needed no action as a bug to fix.

What happens to alerting if the metrics store is down?

Alerting should degrade more gracefully than dashboards. Evaluators read from ingesters and the recent window on a dedicated path with their own capacity, so a query storm or object storage outage does not touch them. If even ingesters are gone, rules see "no data", and critical rules are set to treat absent data as an alert. A Watchdog alert is sent continuously to an external system that pages when it stops. And a small independent second stack watches the platform's own health. The rule is that no single failure may make the platform silently blind.

A tenant suddenly sends ten times more logs. What happens?

The distributor applies per-tenant and per-stream token buckets. Inside the burst allowance data is accepted; beyond it the distributor returns 429 with Retry-After, and agents slow down and buffer locally. Because the quota is per tenant, other tenants' partitions and ingesters are unaffected, and shuffle sharding keeps the tenant on its own subset. If the surge is a real incident, the platform team can raise the limit for a while; if it is a log loop, the agent sampler and the quota stop it quickly. The tenant is told which streams are biggest, and showback charges them, which discourages chronic over-logging.

Pull or push for metrics, and why?

A hybrid. Pull from a node-local agent gives free liveness (a failed scrape means down), central control of the interval, and no need for apps to know where the platform lives. Push is needed for short batch jobs that end before a scrape, for logs, and for crossing firewalls, so the agent also accepts local pushes and then sends outbound in batches. Pure push has an ambiguity problem: silence could be a dead app or a broken network. Pure pull has reachability and discovery burdens at scale. The agent removes both weaknesses, at the cost of running one per host.

How do you make the platform highly available across zones and regions?

Inside a region, spread every part over three zones: Kafka with rack-aware replicas and min ISR 2, ingesters with replication factor 3 in different zones, stateless distributors and queriers behind a load balancer, and zone-redundant object storage. Losing a zone leaves write quorum and a read replica. Across regions, either active/active (agents send to the local region, the query layer federates and dedups) or active/passive with replicated storage and a warm standby. Evaluate rules in both regions with dedup so a regional loss does not lose pages, and keep a small self-monitor outside the primary failure domain.

How do you keep dashboards fast with 800 panel queries per second?

Most of that load repeats, so caching is the main tool. The query frontend splits ranges into days; past days are immutable and cached long, and only today is recomputed. Cache keys use step-aligned boundaries so different users share entries. Recording rules precompute heavy aggregations for the busiest dashboards, and the planner uses coarse rollups for big steps. Per-tenant fair queues and scan limits stop one heavy query from hurting others. If the hit rate falls, check whether dashboards use relative ranges that change the key on every refresh.

Why is the alert path kept separate from the query path?

The two have different jobs and different failure costs. Dashboards are used by thousands of people and can be bursty and heavy, for example a one-year sum over raw data. Alerts are small, regular and critical. If they share a queue, a dashboard storm during an incident, exactly when everyone opens graphs, delays the pages. So evaluators get their own capacity and read from ingesters directly. I also monitor evaluation lag as its own SLI at 99.9 percent of rules evaluated within one interval.

How do you handle a very noisy log stream that saturates one partition?

Streams are hashed to partitions, so one service printing 100 MB/s can saturate one partition and its ingester. First, a per-stream rate limit (about 3 MB/s in the example) returns 429 or drops low severity lines. If the volume is legitimate, split the stream over N partitions by adding a bucket suffix when it crosses its rate, and restore the order at query time using timestamps. Also check with the owner whether the service is logging something it should not, because the cheapest line is the one never emitted.

How would you protect against secrets and personal data in logs?

Scrub at the agent, before data leaves the host: known patterns such as card numbers, tokens and emails, plus a deny list of field names. Use mTLS from agents, with tenant ids set by the gateway. Store logs under per-tenant prefixes, with per-tenant encryption keys for sensitive streams, and support deletion by user id for privacy laws. Limit query access to the tenant's own data, and require explicit grants for cross-tenant queries. Truncate huge lines (256 KB) and limit expensive regex queries at the edge.
