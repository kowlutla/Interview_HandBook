Case Sheet 12: Design a Web Crawler

One-page revision of Handbook case study 12: 1 billion pages a month, with the frontier, politeness, dedup, traps and recrawl as the deep dives.

ProblemRequirementsEstimationAPIData and storesArchitecture and flowDeep divesScalingFailuresImpressQ&A (12)Links

1. Problem in 3 lines

One line: A web crawler starts from known URLs, downloads each page, pulls out the links, and repeats, while being polite to every site and handing pages to a search indexer.
  • Scale: 1 billion pages fetched per month, kept fresh by revisiting them.
  • The fetching is easy. The hard parts are the URL frontier (what to fetch next), politeness, dedup, spider traps and recrawl scheduling.
  • Ranking and the inverted index belong to the search engine, not to us.

Clarifying questions to ask

AskAssumed answer
What is it for?A general web search index, with reasonably fresh content.
Scale and bursts?1B pages a month, bursts to about 2.5x the average.
Content types?HTML first. PDFs and images are stored but not parsed in v1.
JavaScript pages?10 to 15 percent need a headless browser (a real browser with no window), on a separate costly path.
Freshness?News in minutes to hours, normal pages in days to weeks, static pages monthly or less.
Obey robots.txt?Yes. This is a hard rule.
Regions and history?One region at first. Keep the latest version plus about 3 older ones.

2. Requirements

Functional

  • Take seed URLs, find new URLs from links
  • Fetch HTTP and HTTPS, follow a few redirects, honor robots.txt and Crawl-delay
  • Do not fetch the same URL twice in a cycle; do not store duplicate content
  • Recrawl on a schedule based on change rate and importance
  • Store raw pages, publish an event for the indexer
  • Render JavaScript pages on a separate path

Non-functional

  • Scale out by adding machines
  • Politeness: never overload one host
  • Robust against a hostile, broken web (tarpits, endless redirects, infinite URL spaces)
  • Extensible to new content types
  • Spend crawl budget where change and importance are highest
  • A machine failure loses minutes of work, never URLs forever

Out of scope

  • Ranking, inverted index, query serving
  • Spam classification
  • Deep web behind logins and forms
  • Full archival of media

Key insight: the fetch rate is modest. The link check rate (16,000 to 40,000 per second) and the per-host bookkeeping drive the design. Politeness arithmetic: at 1 request per second per host, one site with 100 million URLs needs about 1,157 days, so politeness limits freshness on giant sites.

4. API (a few lines)

POST /v1/seeds            { "urls": ["https://example.com/"], "priority": 5 }
GET  /v1/urls/{urlHash}   -> { url, status, lastFetch, nextFetch, contentHash, depth }
POST /v1/recrawl          { "url": "...", "reason": "operator|sitemap_ping" }
PUT  /v1/hosts/{host}/policy  { "crawlDelayMs": 2000, "maxConcurrent": 1, "dailyBudget": 50000 }
GET  /v1/hosts/{host}/stats -> { fetched24h, errors24h, avgLatencyMs, robotsAge }
  • Frontier lease: lease(partition, n, leaseSeconds) returns due URLs with a leaseId; ack(leaseId, outcome, nextFetchHint) finishes it. An unacknowledged lease expires and the URL is due again. This is the crash-safety trick.
  • Events on the log (Kafka): FetchResult (body is in object storage, the event holds its key), DiscoveredLinks (routed by host hash), PageStored (for the indexer).
Say: "The frontier hands out leases, not deletions. If a fetcher dies, the lease runs out and the URL comes back."

6. Architecture and main flow

Request flow for one URL

  1. Fetcher asks the frontier partition for due URLs. It only gets URLs whose host may be contacted now.
  2. It resolves DNS from cache, checks the cached robots rules, sends a conditional GET (If-None-Match with the stored ETag).
  3. On 200: hash the body, write the compressed body to object storage first, then publish the event. On 304: publish "not modified" and the revisit interval grows.
  4. Ack the lease. The frontier updates the host's nextAllowedAt and the URL's nextFetchAt.
  5. Parser reads the event, extracts and normalizes links, routes each to the partition owning its host, where the filter and enqueue happen.
Trap: publishing the event before the body is saved. An event pointing at a missing blob is much harder to repair than a duplicate blob.

7. Deep dives

7.1 The URL frontier: priority plus politeness

DesignProsConsVerdict
One global priority queueTrivial, strict priorityNo politeness, hot hosts dominateReject
Per-host queues onlyPerfectly politeNo importance; huge hosts fill everythingNot enough alone
Front priority queues + back host queues (Mercator)Both goals, bounded memory, provenMore moving partsChosen
Message broker with delayed messagesOff the shelfPer-host rate state still custom; no range scan by hostEvents only
  • Priority: score from site importance, depth from a seed, change history, page type, sitemap lastmod. Selector weights about 50, 25, 12, 8, 5 percent.
  • Politeness: after a fetch, host re-enters the heap with nextAllowedAt = now + max(crawlDelay, 10 x last fetch time). Back off on 429 and 503 (honor Retry-After, then 1 min, 2, 4 and so on). One connection per host.
  • robots.txt (RFC 9309): 4xx means no limits; 5xx or unreachable means treat as fully disallowed and retry; refresh daily; recheck rules at lease time.
  • Durable: truth lives in the URL store; a lease marks the row inFlight for 2 to 5 minutes using an atomic conditional write.

Choice and why: Mercator two-level frontier, because it gives importance ordering and per-host rate control together, and memory stays bounded.

7.2 Deduplication: URLs, content, traps

OptionMemory / costErrorsUse
Exact set of 8-byte hashes48 GB plus overhead (about 100 GB)NonePossible but costly
Bloom filter, 10 bits per URL, 7 hashes7.5 GB for 6BAbout 1 percent false positives (a new URL wrongly skipped), no false negativesFirst-level filter
Exact check in URL store1.2 TB on disk, 0.2 to 2 msNoneBacking truth for survivors and sitemap sources
Exact hash of extracted textTrivialMisses edited copiesContent check one
Simhash 64 bit, distance 3 or less8 GB for 1BMisses reworded copies and very short pagesContent check two (near-duplicates)
  • Normalize first: lowercase host, drop default port and fragment, resolve dot segments, decode safe escapes, sort query parameters, drop utm_*, gclid, session IDs. Safe rules are universal; aggressive ones are per-host policy. Be careful: over-merging loses real pages.
  • Bloom filter per partition (about 120 million URLs, 150 MB). It cannot delete, so it answers only "known at all?" for newly found links. Recrawls come from the store schedule, never through the filter. Rebuild it from the store when fill passes capacity.
  • Simhash lookups: split 64 bits into blocks; two fingerprints within 3 bits must share at least one identical block (pigeonhole), so look up by block and then check the full distance.
  • Spider traps (calendars, session IDs, repeated path segments, faceted filters): max URL length 2,048 and about 15 segments, max depth about 15 to 20, per-host crawl budget, duplicate ratio per host, URL template clustering, learned ignorable parameters, an operator review queue.

Choice and why: Bloom filter first (microseconds, absorbs 99 percent of lookups), exact store as truth, exact text hash then simhash for content. The budget is the safety net: a trap costs at most its own host's budget.

7.3 Recrawl scheduling

PolicyStrengthWeakness
Uniform intervalSimple, even loadNews stale, static pages over-crawled
Adaptive interval (halve on change, x1.5 on no change)One number per page, self-tuningSlow for new pages; bursty pages oscillate
Poisson change rate + importanceNear-optimal for a fixed budgetNeeds statistics and tuning
Push signals (sitemap lastmod, feeds, pings)Cheapest and freshestNot all hosts publish; lastmod can lie, so verify
  • Choice: hybrid. Adaptive interval for everyone (floor about 15 minutes for news, ceiling about 90 days); Poisson-style benefit = importance x chance of change for the top few percent; a fast lane for pushed signals; conditional GET always (304 means no body).
  • Pages that change faster than we can follow are not worth chasing, so the best policy favors moderately changing pages.
  • Add about 10 percent jitter to due times to avoid thundering herds after downtime.
  • Example budget of 1B fetches a month: 5 percent news tier, 25 percent popular weekly, 50 percent long tail every 1 to 3 months, 20 percent new URL discovery.

Other design points

  • Partition by host hash, not URL hash, so the queue, robots, rate, DNS, budget and Bloom slice of a host sit on one node and the rate limit is a local variable. Use 256 partitions on 16 machines so rebalancing moves whole partitions. Giant hosts are sub-partitioned, each with a share of the rate.
  • Fetcher limits: connect 5 s, first byte 10 s, total 30 s, max body 5 MB (also cap decompressed size), 5 redirects, each hop re-checked for robots and politeness.
  • DNS: in-process cache, shared local resolver, TTL clamped 5 minutes to 1 day, cache failures, prefetch. SSRF defense: after resolution and on every redirect, block private and metadata IP ranges, and pin the checked IP.
  • JavaScript pages: two waves. Plain fetch for all; only pages flagged (tiny text, big scripts, known shell) go to a sandboxed render pool that blocks images and trackers, has a 10 to 15 second timeout, and sends all traffic through the same per-host limiter.

8. Scaling and bottlenecks

  • Not the fetch rate. The real limits are URL store writes, per-host politeness and parser CPU (about 50 cores at peak).
  • Store writes: batch updates per partition (100 to 500 rows), use an LSM store, keep nextAllowedAt in memory and flush lazily.
  • Egress: 800 Mbit/s at peak; use several outbound IPs and publish IP ranges and reverse DNS so sites can verify the bot.
  • Hot hosts are bounded by politeness; the issue is URL count, solved with sub-partitions.
  • Rebalancing: stop, copy rows, rebuild caches from the store, in minutes.
  • At 10x (4,000 per second): about 150 fetchers, 12 TB URL store, 160,000 link checks per second, 1 PB new data a month. Giant sites then limit freshness, which pushes toward push signals and agreements.

9. Failure modes

What failsWhat happensFix
Fetcher crashLeased URLs in flightLease expires in minutes; GET is safe to repeat; duplicates caught by content hash.
Fetcher hangs on slow hostConnection slots tied upHard timeouts, minimum transfer rate, per-host in-flight limit.
Frontier node diesIts hosts are not crawledRebuild from the replicated URL store in minutes; other partitions continue.
Frontier RAM lostHeap and queues goneRebuild by range scan, with jitter and a conservative per-host delay.
Bloom filter lostKnown URLs re-enqueuedRebuild from the store (under an hour); meanwhile exact check on every new link.
URL store slowResults cannot be recordedLog is the write-ahead record; pause leasing when lag is high; replay.
Object store downBodies unsavedRetry with backoff; do not ack until stored, so the URL is fetched again.
Parser bugWrong or missing linksRaw pages and events kept; fix and replay; poison pages to a dead-letter queue.
Soft 404, cloaking, truncated bodyJunk indexedTemplate classifier, length checks, compare with prior version, quarantine big changes.
DNS outageAll fetches failSeveral resolvers, stale-if-error answers, a breaker pauses the fleet.

Consistency: eventual consistency is fine (a rare duplicate fetch is cheap). The lease needs a compare-and-set on leaseId so a late ack from a stale fetcher is rejected. The whole pipeline is at-least-once with idempotent consumers. After a restart, guess a conservative nextAllowedAt so a failover does not burst on a host.

10. Things to say to impress

Say: "The fetch rate is only about 400 per second. The hard numbers are 16,000 to 40,000 link checks per second and the per-host state, so I partition everything by host hash."
Say: "Politeness is a hard requirement, and for a giant site it caps freshness. I would use sitemaps, feeds and conditional GET instead of hammering."
Say: "Bloom filter false positives only lose about 1 percent of newly found URLs, and pages have many inbound links, so the loss is acceptable. The URL store stays the truth, and recrawls never go through the filter."
Say: "The per-host budget is the safety net for every trap I did not predict. The worst case is bounded."
  • Write the body before the event; at-least-once plus idempotent beats exactly-once.
  • Pack pages into 128 MB containers: 780,000 PUTs a month instead of 1 billion, about a thousand times fewer objects.
  • Defend yourself too: SSRF checks, sandboxed renderers and parsers, zip-bomb caps.
  • Honest user agent, published IPs, opt-out support, never crawl behind a login, separate bot names for search and for AI training.
  • Phase it: single partition at 20 per second, then host partitioning at 400, then simhash, rendering and multi-region.
Trap: a single global FIFO or priority queue. It sends hundreds of requests to one host, gets you banned, and ignores importance.

11. Interview Q&A

How do you make sure the crawler never hits one site too hard, even with many fetchers in parallel?

Every host is owned by exactly one frontier partition, chosen by host hash. That partition keeps a nextAllowedAt time per host in a heap and only gives out a URL for the host once that time has passed. After the fetch the host goes back in with the delay added. Because the decision is one local variable and not a distributed lock, parallel fetchers cannot break it. They only receive work the owner approved. The delay is the larger of the robots Crawl-delay and about 10 times the last fetch time, with strong backoff on 429 and 503. A hard per-host cap in the fetcher itself is a second layer, so even a frontier bug cannot exceed it.

Why a Bloom filter for seen URLs, and what are the downsides?

Each page has about 40 links, so we answer "have I seen this?" 16,000 to 40,000 times a second. A Bloom filter does that from memory in about a microsecond using 10 bits per URL, so 6 billion URLs take 7.5 GB. The downside is a false positive of about 1 percent: a new URL is wrongly treated as known and skipped. We accept that because pages usually have several inbound links and the filter is rebuilt from the store. It also cannot delete entries or say when a URL was last fetched, so recrawls come from the store schedule. We watch the fill ratio, because going past the designed capacity makes the error rate climb fast.

How do you find near-duplicate pages at billion scale?

First compare an exact hash of the extracted main text, which is cheap and certain. For the rest, compute a 64-bit simhash, a fingerprint where similar texts differ in only a few bits, and call pages near-duplicates when they differ in at most 3 bits. Scanning a billion fingerprints per query is too slow, so we use the pigeonhole idea: cut the fingerprint into blocks, and two fingerprints within 3 bits must share at least one identical block. Keep a table per block, look up candidates by each block, then check the full distance. Production systems use more, smaller permuted blocks to keep each bucket small.

What is a spider trap and how do you protect the crawl budget?

A spider trap is an effectively endless set of URLs, such as a calendar with a "next month" link forever, session IDs in every link, repeated path segments, or filters that combine into billions of URLs. We layer defenses: maximum URL length and depth, normalization that strips session and tracking parameters, URL template clustering to spot patterns that make many URLs with little new content, and a duplicate ratio per host. The strongest defense is a per-host crawl budget, so the worst case hurts only that host. Suspect hosts go to an operator dashboard where someone can add a block rule.

How do you decide how often to recrawl a page?

Each URL row stores the last fetch time, content hash, validators (ETag, Last-Modified) and an interval. After every fetch, a change halves the interval and no change multiplies it by about 1.5, clamped between a floor and a ceiling. For the most important pages we estimate a Poisson change rate and sort the due queue by importance times the chance the page changed since the last fetch. Sitemap lastmod, feeds and push pings move a page forward but we verify with a conditional GET. Fixed intervals waste budget on static pages and leave news stale.

What happens if a fetcher crashes halfway through a download?

Nothing permanent. The frontier handed out the URL under a lease that lasts a few minutes. The fetcher never acknowledged, so the lease lapses and the URL becomes due again. A GET is safe to repeat, and the blob key and indexer events use URL and content hash, so at worst we get a duplicate that the hash check catches. To keep politeness, we record the host's next allowed time when we lease, not when we finish.

Why partition by host and not by URL?

Politeness, robots rules, DNS, error streaks, budgets and trap detection are all per-host ideas. If one host's URLs were spread over many machines, they would need a shared counter to respect one request per second, which means distributed locking at about 1,000 operations a second. Host partitioning puts all that state on one node, makes range scans by host cheap and keeps Bloom filters local. The cost is skew from giant hosts, which we handle with sub-partitions that each own a share of the host's rate.

How do you handle JavaScript sites without making the crawler ten times more expensive?

Render only when needed. Every page gets the cheap plain fetch and parse. A classifier flags pages with little visible text and a big script payload, or hosts known to need rendering, and only those go to a separate render lane with its own budget. A render costs 50 to 100 times a plain fetch. The renderer blocks images, fonts and trackers, uses short timeouts, runs in a locked-down sandbox, and routes all its requests through the same per-host limiter. Results are cached against the shell and script versions so unchanged pages are not rendered again. For high-value hosts we may call their JSON APIs directly.

How do you treat robots.txt that is missing, broken or unreachable?

Following RFC 9309: a 4xx such as 404 means no rules, so we may crawl. A 5xx or an unreachable server means assume everything is disallowed for now and retry later, because an outage must not become permission to crawl everything. If it stays unavailable for a long time (the RFC mentions about 30 days) we may treat the site as unrestricted. We cache a good copy for up to a day, refresh it politely through the host's own queue, recheck the rules at lease time for each URL, and cap the size we parse.

Production incident: crawl throughput suddenly drops and the frontier lag grows. What do you check?

First split the problem by stage using the metrics: fetch success ratio, DNS cache hit rate and latency, lag per priority class, URL store latency, and indexer lag. If DNS lookups are slow, the whole fleet stalls, so check the resolvers and the breaker. If the store is slow, leases and acks back up, so look at write latency and compaction. If a few hosts return many 429s or timeouts, the error streaks may be pushing them out of rotation, which is correct behavior. Also check for a new trap eating the budget (a host with a huge duplicate ratio). Only after that look at fetcher machine health. Pause leasing for broken parts rather than burning retries.

How would you crawl one huge site with 500 million pages in a week?

That is about 827 requests per second to one host, which no site should get by default, so politeness is the binding limit. We would ask for cooperation: sitemaps, feeds or an API, and an agreed higher rate. Then we raise the host's limit through sub-partitions, each with a small share and its own connections, and watch response times and errors to back off. Without cooperation we cannot finish in a week politely, and we say so. Priority decides what comes first (new and popular items) and the rest arrives over months.

How do you roll out changes safely when the crawler touches the whole internet?

Changes to politeness, normalization and robots handling are the risky ones, because mistakes harm other people's sites or silently merge distinct pages. We run new versions in shadow mode on recorded fetch events and compare the output with the old version, then roll out per partition with a canary first. The fetcher has a hard global per-host cap that no frontier bug can exceed, and a kill switch that pauses a host or the whole fleet in seconds.

Why at-least-once with idempotent consumers and not exactly-once?

A repeated fetch of a page is cheap and harmless, while exactly-once across a crawler, object store, log and indexer is costly and fragile. So events may repeat, the blob key includes fetch time and content hash, inserting an existing URL is a no-op, and the indexer ignores events that are not newer than what it holds. The one strict piece is the lease, which uses a compare-and-set on leaseId so a late ack from a stale fetcher is rejected.
