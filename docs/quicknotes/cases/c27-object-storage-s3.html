Case sheet 27: Design Object Storage (S3-like)

One-page revision of the full handbook case: store hundreds of billions of write-once blobs, never lose them, and still list keys fast.

1 Problem · 2 Requirements · 3 Estimation · 4 API · 5 Data · 6 Architecture · 7 Deep dives · 8 Scaling · 9 Failures · 10 Impress · 11 Q&A · 12 Links

1. Problem in 3 lines

Say this first: object storage is two systems glued together. A small, strongly consistent, sorted index (the metadata) maps keys to chunk locations. A huge, cheap, append-only data plane of simple storage nodes holds erasure-coded pieces. A PUT is "committed" when one metadata row is written. Repair, cleanup and listing all follow from that.

  • A bucket is a named container. An object is bytes plus a few headers, stored under a key such as photos/2025/cat.jpg. You can PUT, GET (whole or a byte range), DELETE and LIST. You cannot edit in place: you upload a new object with the same key. Objects are immutable, and that one rule makes the design tractable.
  • Targets: 11 nines of durability (we expect to lose at most about 2 of 200 billion objects a year), 99.99 percent availability, survive losing one whole availability zone (AZ, an isolated datacenter in a region).
Question to askAssumed answer
Scale?One region, 100 PB of user data, 200 billion objects, mean size about 500 KB, tail up to 5 TB.
Request rate?50,000/s average, 150,000/s peak (3x). Mix: 70% GET or HEAD, 20% PUT, 5% DELETE, 5% LIST.
Consistency?Strong: read-after-write for new objects, overwrites and deletes, and strong list-after-write.
Big objects?Single PUT up to 5 GB, multipart up to 5 TB.
Extras?Optional versioning and simple lifecycle rules. Multi-tenant, signed HTTPS requests.

2. Requirements

Functional

  • Bucket create, delete (only when empty), config.
  • PUT, GET (with Range), HEAD, DELETE, server-side COPY.
  • LIST with prefix, delimiter ("folders"), pages.
  • Multipart upload, completed atomically.
  • Checksums on upload, corruption detection on read.
  • Lifecycle: expire objects, abort stale uploads.

Non-functional

  • Durability: 11 nines per object per year. It drives the data layout.
  • Availability 99.99 percent, tolerate one AZ down.
  • Built for bandwidth: first byte about 100 ms at p99 for small objects.
  • Linear scale-out without moving everything.
  • Low raw bytes per user byte (erasure coding).

Out of scope

  • IAM product, billing.
  • CDN in front, cold tape tiers.
  • SQL-on-objects, event notifications.
  • POSIX file system view (rename, append).
  • Cross-region internals beyond a short mention.

Key insight: metadata is limited by size, not request rate. Data is limited by network bandwidth and by disk operations per second (seeks), which is why small objects stay replicated.

4. API (S3 shape, plain HTTP)

PUT    /{bucket}/{key}            upload (up to 5 GB); If-None-Match: * = create only if absent
GET    /{bucket}/{key}            download; Range: bytes=0-1048575 gives 206
HEAD   /{bucket}/{key}            metadata only
DELETE /{bucket}/{key}[?versionId=]
GET    /{bucket}?list-type=2&prefix=photos/&delimiter=/&max-keys=1000&continuation-token=...
POST   /{bucket}/{key}?uploads                  start multipart, returns uploadId
PUT    /{bucket}/{key}?partNumber=7&uploadId=U  upload one part, returns part ETag
POST   /{bucket}/{key}?uploadId=U               complete (list of part number + ETag)
DELETE /{bucket}/{key}?uploadId=U               abort
  • Every request is signed (a keyed hash of method, path, headers, timestamp). No long-lived secret travels, and a replayed request expires.
  • Retries are safe: a retried PUT makes the same visible object; a retried part overwrites that part number.
  • LIST returns at most 1,000 keys plus an opaque token (the last key). An unbounded list would hold a shard scan open.

5. Data model and store choices

DataStoreWhy
Object metadata (key to chunk map), 100 TBRange-sharded, Raft-replicated ordered key-value store on NVMe (LSM engine)LIST needs sorted keys, so no hash sharding. Strong reads need consensus per shard. Records are small and index-like.
Object bytes (fragments), 180 PBAppend-only extent files (about 1 GB each) on HDD nodes, local index on SSDNo updates means no random writes. Appending turns many small writes into sequential I/O (the Haystack idea).
Placement and cluster stateSmall consensus groupTiny, rarely changes, needs linearizable updates when drives fail.
metadata row key: (bucket_id, key, inverse_version)   // newest version sorts first
value: size, etag, content_type, created_at, user_meta, storage_class, is_delete_marker,
       layout: [ segment_i = { chunk_id, scheme: EC(9,6) | REP(3), pg_id, length, checksum } ]
  • Segment: a 9 MB slice of the object. EC turns it into 9 data fragments plus 6 parity fragments, 1 MB each.
  • Placement group (PG): a fixed set of 15 drives (EC) or 3 drives (replication) holding all fragments of a chunk. Nodes know chunks, the index knows keys, so repair and cleanup never touch keys.

Because bytes are immutable, the data plane needs no locks and no consensus. All the hard agreement ("is this object visible, and where is it?") lives in one small metadata commit.

6. Architecture and main flows

PUT flow (a 40 MB object)

  1. Front-end checks the signature and bucket policy and starts hashing the stream.
  2. It cuts the stream into 9 MB segments (here 4 of 9 MB and one of 4 MB) and gets a PG for each (15 drives, 5 per AZ, different servers and racks).
  3. For each segment it computes 6 parity fragments and sends all 15 fragments in parallel. Each node appends to its open extent, checksums and syncs before acking.
  4. When 12 of 15 acks arrive for every segment, the segment is durable. The slow ones finish in the background, or go to the repair queue.
  5. Front-end verifies the end-to-end checksum, then writes the metadata row (one Raft write). This is the commit point.
  6. Returns 200 with the ETag. From now on any GET or LIST sees the object.

GET flow

  1. Verify signature, read the metadata row (point read on one shard; short-lived front-end cache, validated so deletes are seen fast).
  2. For a Range, find which segments overlap and read only those data fragments (data fragments are contiguous 1 MB slices, so no parity maths on a healthy read).
  3. Verify each fragment checksum while streaming to the client.
  4. Degraded read: if a fragment is missing, corrupt or slow, also read parity and rebuild from any 9 of 15. Hedging (send the extra read after about the p95 latency, not after a timeout) trims tail latency. Small replicated objects: read any one of 3 copies, prefer the local AZ.

7. Deep dives

7.1 Erasure coding versus replication, and the durability math

Simple picture: split a block into A and B and store P = A XOR B. Lose any one of three and you can rebuild it. Reed-Solomon (k, m) generalizes this: k data fragments plus m parity fragments, and any k of the k+m rebuild the object. Overhead is (k+m)/k, and it tolerates any m losses.

SchemeOverheadFailures toleratedReads per GETRepair read per lost fragment
3x replication3.0x211
RS(10,4)1.4x41010
RS(9,6), 3 AZs x 51.67x6, or a whole AZ plus 199
LRC(12,2,2)1.33xany 3, many 4126 (local parity)

Choice: hybrid by size. Objects of 1 MB or more use RS(9,6) across 3 AZs (5 fragments per AZ). Smaller objects use 3 replicas, one per AZ. Why: EC turns one read into k reads, which is cheap in bandwidth for megabytes but wasteful in seeks for 20 KB, and a tiny object cannot be split into 15 useful fragments. The scheme is stored per segment so a background mover can re-encode objects that cool down.

Why 9+6 and not 10+4? To survive an AZ loss, fragments per AZ must be at most m. With RS(10,4) over 3 AZs, losing an AZ drops 5 fragments, more than 4 parity, so data is unavailable. 9+6 loses 5 and keeps 10, with one fragment of slack. The price is 1.67x instead of 1.4x: cross-AZ tolerance costs extra parity.

Durability math (2% annual drive failure, 6 hour repair, so p = 0.02 x 6 / 8,760 = 1.37e-5 per other drive per window):
3 copies: 0.06 x p^2 = about 1.1e-11 (11 nines).
RS(10,4): 0.28 x C(13,4) x p^4 = 0.28 x 715 x 3.84e-20 = about 7.7e-18 (17 nines).
RS(9,6): about 6e-27 (the handbook chart shows about 26 nines).
Trap: never claim 26 nines as real. Independence is false. Real loss comes from correlated events: a firmware bug in a drive model, a bad software release, an operator deleting the wrong thing, a rack or power failure, bit rot found late, repair falling behind. The maths justifies the scheme; placement across failure domains, end-to-end checksums, scrubbing and careful deploys justify the number. The repair time T is the hidden variable: halving T cuts the 3x loss probability by 4x and the RS(9,6) one by 64x.

7.2 Metadata path and listing

CriterionHash sharding on (bucket, key)Range sharding on (bucket, key)
Point GET and PUTEven load, one shardOne shard (range map lookup)
LIST with prefixAsk all 2,000 shards and merge for every pageOne or two adjacent shards, sequential scan
Hot spotsRare, except one hot keySequential keys (timestamps) hammer the last range
RebalanceMove hash slicesSplit a hot range, move one half

Choice: range sharding, because listing is part of the contract. Hot ranges split automatically (for example above 50 GB or a sustained request rate). The range map (about 2,000 entries) is cached on every front-end. A shard that gets a key outside its range replies "wrong shard" plus the new map version, and the front-end retries.

  • Consistency: each object row lives on one shard and reads go through the leader (lease or read-index), so a 200 PUT shows in the next LIST. A list that spans shards is a series of ordered reads, each page strongly consistent, not a snapshot of the whole bucket (same as S3).
  • COPY copies no data: a new row points at the same chunks with a reference count raised.
  • Versioning: a PUT adds a row with a newer inverse version. A DELETE without a version id adds a delete marker. A DELETE with a version id removes that row, and GC then owns its chunks.

7.3 Multipart upload

StepWhat happens
InitiateCreate an upload record keyed (bucket, key, upload_id). Nothing visible yet.
Upload partsParts 1 to 10,000, 5 MiB to 5 GiB each (last may be smaller), any order, in parallel. Each part is stored like a normal object and gets a part record (etag, size, layout). Re-uploading a part number replaces it, so retries are easy.
CompleteCheck every listed part exists with the right ETag and the size rule, then one atomic metadata transaction writes the final row whose layout is the parts concatenated and deletes the upload record. No data is copied, so it takes milliseconds even for terabytes.
AbortDelete the records. The part chunks become garbage.
  • Upload rows sort next to the final key, so Complete is a single-shard transaction.
  • Multipart ETag is the MD5 of the part MD5s plus "-partcount", not a hash of the whole file. Offer a stronger extra checksum.
  • Range GET works by prefix-sum over segment lengths, regardless of part boundaries.
  • Lifecycle rule "abort incomplete uploads after 7 days" is a standard safeguard, and quota must count in-flight parts.

7.4 Garbage collection, repair and scrubbing

Rule: a chunk is live if and only if some committed metadata record names it (object row, part record, or a copy's shared reference).

ApproachProsCons
Synchronous deleteSpace returns fastA crash leaks space, a 5 TB delete blocks the request, breaks COPY sharing and in-flight reads
Reference countingExact, handles COPYCounters drift after crashes
Mark and sweepSelf-healing, catches every leakSlow, heavy scan, needs a grace period
Hybrid (chosen)Fast common path plus a safety netTwo mechanisms to run
  • Delete path: DELETE removes the row and queues the chunk ids in the same transaction. A worker acts after 24 hours (gives a recovery window and lets in-flight reads finish). Nodes mark the fragment dead. Extent compaction later copies live data out of a sealed extent once its garbage ratio passes about 50 percent, picking the worst extents first, rate limited.
  • Sweep: compare live chunk ids (including upload tables) against ids on nodes, and delete the difference only if older than a 7 day grace period. The grace period protects a PUT that wrote fragments but has not committed yet.
  • Repair: a node is "suspected" after missed heartbeats and "failed" after about 15 minutes (so reboots do not trigger rebuilds). PGs are declustered over the whole fleet, so a rebuild reads from and writes to thousands of drives in parallel. Rebuild reads 9 survivors, writes one fragment to a spare in the same AZ on a different rack. Fewest remaining fragments first.
  • Scrub: re-read every fragment about every 30 days and verify the CRC. For a 14 TB drive that is about 5.4 MB/s, under 5 percent of drive bandwidth. This turns silent bit rot into "repaired within a known window".

8. Scaling and bottlenecks

  • Front-ends: stateless, add servers behind a load balancer. Use connection-count-aware balancing and drain on deploy because big PUTs stream for minutes. They also do the EC encode (several GB/s per core), so network is the limit, not CPU.
  • Storage nodes: add nodes. New empty nodes get new PGs first, and a bounded background rebalance evens out the rest.
  • Hot prefix: sequential keys always append to the last range, so splitting helps only partly. Return 503 SlowDown so clients back off with jitter, and advise a short hash prefix on keys.
  • Hot objects: CDN in front plus a front-end RAM cache for small hot objects. Never cache LIST across clients.
  • Multi-tenancy: per-bucket and per-account rate limits. Isolate giant tenants on dedicated shard groups (cells).
  • Cost: drives dominate, then power, then network. Cold classes use wider codes such as RS(12,4) at 1.33x. Capacity rule: order hardware at 60 percent full, hard stop at 80 percent, because repair needs headroom.

Consistency and idempotency: the linearization point of every change is one metadata write. Overwrites are last-writer-wins by shard order and the loser's chunks become garbage. If-None-Match and If-Match are evaluated inside the shard write. Retries are safe because every attempt uses fresh random chunk ids and commits at most one row. We do not use content-hash chunk ids, because global dedup needs a global index and leaks across tenants.

Multi-region: asynchronous, driven by a per-shard change feed, versioning required on both sides so replicas apply "put version V of key K" idempotently. Replication lag is the recovery point objective. Strong consistency is a per-region promise.

10. Things to say to impress

Say this:
  • "Data first, metadata last. The metadata write is the commit point, so a crash leaves garbage, never a pointer to missing data."
  • "Durability is repair-speed engineering: the repair window T enters the loss formula as a power of the number of extra failures needed. Declustered placement shortens T."
  • "The independent-failure maths says 26 nines, but real risk is correlated: bad releases, firmware, operators. So I add checksums end to end, scrubbing, staged rollouts and delayed deletes."
  • "The most dangerous code is garbage collection. I layer a 24 hour delay, a 7 day grace period, dry runs and rate limits."
  • "Cross-AZ tolerance is paid for in parity: 9+6 at 1.67x instead of 10+4 at 1.4x."
  • "Hybrid by size keeps disk reads at 28 per drive instead of 73, because EC multiplies seeks."
  • "The key SLI for durability is the age of the oldest under-redundant chunk against the 6 hour target."
  • "Evolve in phases: replicated chunks and a simple metadata store first, then multipart and versioning, then erasure coding, then cells and LRC at 10x (about 1 EB, 2 trillion objects, 1 PB metadata, 20,000 shards)."

Alternatives not chosen: hash-sharded metadata (breaks LIST); an HDFS-style file system (single namenode limits object count); Dynamo-style eventual consistency (stale reads and listing burden every client); content-addressed global dedup (global index, tricky GC, cross-tenant leak); waiting for all 15 acks (slowest drive sets PUT time); tiny objects inside metadata rows (fine under about 4 KB, bloats SSD).

Security in one breath: signed requests, default deny plus "block public access", presigned URLs, TLS in transit, envelope encryption at rest (per-object data key wrapped by a bucket key, so deleting the key shreds the data), no cross-tenant dedup, object lock for compliance.

Monitoring: availability burn rate, GET first-byte p50 about 30 ms and p99 about 100 ms, under-replicated chunk count and age, repair backlog, scrub coverage and failure rate, orphan bytes per sweep, shard skew, fill percentage per AZ.

11. Interview Q&A

Why separate metadata from data instead of one distributed database?

They have opposite shapes. Metadata is small (about 500 bytes per object) and needs strong consistency, sorted order and random access, so it lives on SSD in a consensus-replicated, range-sharded store. Data is huge, write-once and read in big sequential pieces, so it lives on cheap HDDs in append-only extents with erasure coding and does not need consensus. One store would either make bulk bytes pay for consensus and SSDs, or give the index the weak consistency of the data tier. The split also lets each scale on its own (shards for metadata, drives for data) and gives one crisp commit point.

A PUT crashes after writing all fragments but before the metadata commit. What state are we in?

The object is not visible, because visibility is defined only by the metadata row, and the client got no success so it will retry. The fragments are orphans: stored but named by nothing. They only waste space. The mark-and-sweep collector finds them and deletes them after the 7 day grace period, which exists so it never mistakes an in-progress PUT for garbage. This is why we write data first and metadata last: failure leaves garbage, never a dangling pointer.

Why is erasure coding cheaper than replication, and when would you still replicate?

Reed-Solomon keeps k data and m parity fragments and any k rebuild the object, so overhead is (k+m)/k, for example 1.67x, against 3x for three copies, with more failures tolerated. The costs are CPU for encoding, k reads per GET, and repair that must read k fragments to rebuild one. So I replicate small objects (seeks and per-fragment overhead dominate) and very hot data, and use EC for large warm and cold objects. The scheme is recorded per segment so objects can move between schemes later.

Walk through the durability maths. What assumption could make it wrong?

With a 2 percent annual drive failure rate and a 6 hour repair window, the chance that a given other drive fails in the window is about 1.4e-5. For 3 copies, loss needs both other copies to fail in that window after a first failure: 0.06 times the window chance squared, about 1.1e-11, so 11 nines. For RS(10,4), loss needs 4 more of 13 fragments to fail: about 7.7e-18. The weak assumption is independence. Real losses are correlated: firmware bugs, rack or power events, bad releases, operator error, repair running slower than planned. That is why we spread fragments over failure domains, checksum end to end, scrub, and watch the age of the oldest under-redundant chunk.

How does LIST with a delimiter stay fast with billions of keys?

Keys are sorted in a range-sharded store, so a prefix is a contiguous range and a list is a sequential scan of one or two adjacent shards. When the scan meets a key that contains the delimiter after the prefix, it records that common prefix once and seeks past every key starting with it. So the work grows with the number of entries returned, not the keys underneath. The continuation token holds the last key, so pages stay correct as keys are inserted. Hash sharding would force a scatter-gather over all 2,000 shards for every page.

How do you make Complete fast and atomic for a 5 TB multipart object?

Each part is stored as ordinary chunks and recorded in an upload table by upload id and part number. Complete moves no data. It checks that every listed part exists with the matching ETag and that non-final parts meet the minimum size, then in one transaction writes a final row whose layout is the concatenation of the part layouts and deletes the upload record. Upload rows sort next to the final key, so this is a single-shard transaction. It takes milliseconds at any size, and a retried Complete returns the existing result. Replaced or abandoned parts become garbage, cleaned up by the delete queue and by a lifecycle rule that aborts incomplete uploads.

What must garbage collection be careful about, and what if it has a bug?

The dangerous direction is deleting live data. Races include a chunk written but not yet committed, multipart parts named only by upload records, chunks shared by a COPY, and reads still running on a just-deleted object. Defenses: a 24 hour delay after the row is removed, a 7 day grace for orphans, a live set that includes upload tables and shared references, a recheck that the chunk is unreferenced just before deleting, rate limits and alarms on delete volume, and report-only dry runs for new logic. A GC bug that deletes live data is a data loss incident, so safety matters more than how fast space returns.

One tenant writes sequential keys at 100k per second. What happens?

All the keys land in the last range, so one shard leader takes every write. Automatic splitting divides ranges by load or size, but new keys keep arriving at the end, so the newest range stays hot. The service sheds excess with 503 SlowDown so clients back off with jitter, and splits as fast as it can, which spreads old keys but not the append hot spot. The real fix is key design: add a short hash prefix or shard by an id. That costs time-ordered listing, which becomes a multi-prefix operation. We also publish recommended per-prefix request rates.

How do you give strong read-after-write consistency, and what does it cost?

Each object's metadata lives on one Raft-replicated shard, and both the commit and reads go through its leader (confirmed by a lease or read-index), so any read after an acknowledged write sees it. The costs: reads cannot come from a stale follower or an unvalidated cache, the leader is a bottleneck for a hot key, and a shard that loses quorum is unavailable (a CP choice). We soften this with leader leases, caches only for immutable versioned objects, and replicas in three AZs so one AZ failure does not break quorum.

How do you detect and handle silent data corruption?

Several layers. The whole-object checksum is verified before commit and stored in metadata. Each fragment has its own CRC (typically CRC32C) written beside it. Every read verifies it, and a mismatch triggers a degraded read from other fragments plus a repair (read repair). A scrubber re-reads all data about every 30 days at about 5 MB/s per drive so cold data does not rot unseen. Corruption becomes an event with a detection time and a repair time, and those feed straight into the durability maths as the repair window.

Why range sharding and not consistent hashing for metadata?

Listing is part of the product. With hash sharding, keys under one prefix are scattered over every shard, so each LIST page needs a scatter-gather and a merge. Range sharding keeps a prefix contiguous, so a list is a sequential scan. The cost is hot ranges for sequential keys, which we handle with automatic splits, SlowDown throttling and key-prefix advice. A hash scheme could add a secondary sorted index, but then every PUT becomes a two-shard write.

An AZ goes down. What do users see?

Reads keep working: each EC segment has 5 fragments per AZ, so 10 of 15 remain and 9 are enough. Replicated small objects have a copy in each AZ. Writes continue as long as 12 acks can be gathered, with the missing fragments marked for repair when the zone returns. Metadata shards have replicas in three AZs, so each still has quorum with 2 of 3. We keep about 30 percent headroom so the surviving AZs can absorb the repair load without filling up.

How would you add cross-region durability?

Add asynchronous replication driven by the metadata change feed. It needs versioning so applying an event is ordered per key and idempotent. Replicator workers copy new versions to the destination region, which stores them with its own erasure coding and its own metadata commit. The replication lag is an SLO that defines the recovery point objective for a regional disaster. Strong consistency stays inside one region. On failover you must decide what to do with writes not yet replicated.
