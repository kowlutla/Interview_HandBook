# 003. Design an API Rate Limiter

## 1. Problem Statement & Requirements
### Functional Requirements:
- Limit the number of requests an API client can send within a timeframe.
- Return HTTP 429 (Too Many Requests) when limit is exceeded.
- Support different rate-limiting rules (by IP, user ID, API endpoint).

### Non-Functional Requirements:
- Low latency (must not add noticeable overhead to requests).
- High availability and scalability (rate limiter should be distributed).
- Fault tolerance (if rate limiter fails, API should still work).

## 2. High-Level Architecture
- Placed at the API Gateway layer (e.g., Envoy, Kong, custom Nginx module).
- Uses **Redis** as a distributed counter storage because of in-memory speed and atomic operations (INCR, TTL).

## 3. Rate Limiting Algorithms
- **Token Bucket**: Allows bursts; tokens refilled at fixed rate.
- **Leaky Bucket**: Smooths out traffic bursts into steady flow.
- **Fixed Window Counter**: Simple, but vulnerable to traffic surges at window boundaries.
- **Sliding Window Log / Counter**: Highly accurate, prevents boundary spikes.

## 4. Distributed Considerations
- Race conditions in Redis handled via Lua scripts or Sorted Sets.
- Local in-memory caching combined with centralized Redis sync to reduce network hops.
